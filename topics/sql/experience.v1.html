How to read the tier chip. It is the altitude the answer is pitched at, not the seniority of whoever lived it. A Mid answer finds the cause and fixes the query; a Senior answer proves the cause with a measurement and stops the class of query from being written again; a Staff answer changes the schema, the platform or the deployment pipeline so the failure cannot recur, and gets other teams to adopt it; a Principal answer changes what the organisation buys, staffs and standardises on, and defends that to people who will never open a query plan. Most of these stories can be told at two adjacent tiers — the drill chain is where the altitude actually shows.

The one-line version of the engine difference, so you never blur it under pressure. PostgreSQL is multi-version at the row level with readers that never block writers and writers that never block readers, so its costs surface as bloat, vacuum and transaction-ID age; SQL Server defaults to pessimistic locking with lock escalation, so its costs surface as blocking and deadlocks — unless you turn on read-committed snapshot isolation, at which point its costs move to the tempdb version store and start to look like Postgres. Almost every story below is a consequence of that one sentence.

01The plan that flipped at 03:00

Senior Performance problem diagnosed

(a) Worked example EXAMPLE — replace with your own

Nothing was deployed. That is the detail I lead with, because it is the whole story. At 03:04 the p99 on the order-search endpoint went from 180 ms to 26 seconds and stayed there; CPU on the primary sat at 95 percent with no increase in request rate. The only thing that had happened at 03:00 was the statistics maintenance job, and the only thing that job does is invalidate cached plans. One procedure — usp_SearchOrders, about 40,000 executions an hour — had recompiled, and the first call after the recompile happened to come from a background reconciliation job passing @CustomerId = NULL and a two-year date range. The optimiser did exactly what it was told: it built a plan for that shape, a parallel clustered index scan with a hash match, cached it, and then served it to 40,000 point lookups an hour that each wanted a seek returning nine rows.

That is parameter sniffing, and the reason it is worth understanding rather than memorising is that it is not a bug — it is the price of a shared plan cache. SQL Server compiles once per statement text and caches by plan handle, so the parameter values present at compile time become the assumptions baked into every later execution. PostgreSQL gets to the same place by a different road: it has no cross-session plan cache at all, so an ad-hoc query is planned fresh every time and cannot suffer this, but a prepared statement (which every driver and every ORM using the extended protocol creates for you) is custom-planned five times and then switches to a generic plan if the generic plan's estimated cost is not worse. The Postgres version of my 03:00 therefore looks like a query that is fast in psql and slow from the application, which is a far more confusing symptom than a plan that flipped for everyone at once. The lever there is plan_cache_mode = force_custom_plan, set on the session or the role or, best, the one query that needs it.

The diagnosis took eleven minutes because Query Store was on. The regressed-queries view showed one query_id with two plans, the old one averaging 4 ms of CPU and the new one 900 ms, with the switchover timestamped at 03:04. I forced the old plan — that is a tourniquet, not a fix, and I said so in the incident channel while I was doing it — which put us back under 200 ms by 03:20. The actual fix took a week and had three parts: the reconciliation job stopped calling the interactive procedure and got its own, the interactive path got a filtered index that made the point-lookup plan trivially cheapest, and I added a Query Store alert on plan-change-with-regression so the next one pages someone in minutes instead of being discovered by customers. What I would do differently: I would not have left the forced plan in place for six weeks. Forced plans are invisible technical debt — they silently stop the optimiser from ever improving that query, and they fail open in ways nobody notices until an index change makes the forced plan impossible.

-- SQL Server: the shape that sniffs badly, and the three tools, weakest first.
CREATE OR ALTER PROCEDURE dbo.usp_SearchOrders

AS
SELECT TOP (200) o.OrderId, o.PlacedAt, o.Total
FROM   dbo.Orders o
WHERE  (@CustomerId IS NULL OR o.CustomerId = @CustomerId)   -- the "kitchen sink" predicate

ORDER BY o.PlacedAt DESC;

-- SQL Server 2025 (compat 170): Optional Parameter Plan Optimization targets exactly the shape
-- above, deferring the "@p IS NULL OR col = @p" branches to run time.
ALTER DATABASE CURRENT SET COMPATIBILITY_LEVEL = 170;

What the interviewer is really probing. Whether you diagnose or guess. The signal they want is a named first measurement — Query Store regressed queries, sys.dm_exec_query_stats, pg_stat_statements ordered by total_exec_time — followed by a hypothesis, followed by a confirmation, and only then a change. The classic failures on this archetype: telling the story as "I added an index and it was fast" with no evidence the index was the cause; being unable to say what the plan actually did; treating a mitigation as a fix and never returning to it; and not knowing why the query was fast yesterday, which is the actual question being asked.

(c) Recall prompts

When did a query you own get slower without anyone changing the code?

Hint: statistics refresh, a data-volume threshold crossed, a plan evicted after failover or restart, a parameter set arriving from a new caller, auto-vacuum finally running on a table, an index rebuild changing cardinality estimates, or a compatibility-level change nobody announced.

What is the first thing you open when someone says "the database is slow"?

Hint: a strong answer names a tool and a sort order — Query Store by total duration for the last hour, pg_stat_statements by total_exec_time, wait statistics (sys.dm_os_wait_stats deltas, pg_stat_activity.wait_event_type) — and explains why you look at waits before you look at queries.

Have you ever mitigated with a hint or a forced plan? What happened to it afterwards?

Hint: the honest answers are "it is still there" and "I removed it in the follow-up PR". Both are usable; only pretending you never needed one is not. Say what the hint was buying and what it cost you the next time the data changed.

Can you describe a plan you have actually read, operator by operator?

Hint: pick one you can draw — a nested loop with a huge outer estimate error, a hash spill to tempdb, a sort that spilled, a bitmap heap scan with a big Rows Removed by Filter. The specificity is the point; interviewers can tell within two sentences whether you have opened a plan or read about them.

(d) Follow-up drill chain

Why not just put OPTION (RECOMPILE) on everything?

Because compilation is CPU you pay on every execution, and on a hot OLTP statement running tens of thousands of times an hour that is a bigger bill than the bad plan was. It also throws away the plan-reuse that makes SQL Server's cache worth having, and it hides the underlying problem: if a query genuinely needs a different plan per call, that is usually a signal the workload is two workloads wearing one procedure. I use RECOMPILE deliberately on low-frequency, high-variance statements — reports, admin procedures, anything with a date range chosen by a human — and I treat its appearance on a hot path as a code smell to be explained in the PR.

At what scale does the "split the procedure per access pattern" fix stop working?

It stops when the access patterns multiply faster than you can enumerate them — a search screen with nine optional filters is 512 shapes, and nobody writes 512 procedures. At that point the choices are dynamic SQL that produces one statement text per actually-used filter combination (parameterised, so it still caches, and the cache bloat is bounded by real usage), or letting the engine do it: SQL Server 2025's Optional Parameter Plan Optimization exists precisely for the @p IS NULL OR col = @p shape, and in PostgreSQL you build the SQL in the application and let it plan each variant. The other end of the scale matters too: past a few hundred thousand distinct statement texts you start caring about plan cache pressure and single-use plans, and that is when parameterisation and cache-size monitoring become the story.

What did forcing the plan trade away?

Optimiser freedom and future adaptability. A forced plan is a promise that today's shape stays correct forever, which is false the moment the data distribution moves or the index it depends on changes; SQL Server will silently stop forcing it if the plan becomes invalid, and unless you are monitoring sys.query_store_plan.force_failure_count you will find out from a customer. It also masks the measurement: with the plan pinned, nobody feels the pain that funds the real fix. So I force plans with a ticket, an owner and a date, and I check the forcing status in the same dashboard as the query's latency.

How would you have caught this before it reached customers?

Three layers, cheapest first. Detection: an alert on Query Store plan changes where the new plan's average duration regressed beyond a threshold — that is a handful of lines against the Query Store views and it turns a 40-minute customer-reported outage into a page. Prevention: separate the batch and interactive paths so a nightly job can never seed the plan cache for an online query, which was the actual root cause here. And rehearsal: run the top queries under both parameter extremes in a pre-production copy with production-shaped statistics, because the failure mode is not "the query is slow", it is "the query is slow for one shape and nobody tested that shape".

Same symptom in PostgreSQL — walk me through it.

The first thing I check is whether the slow path is prepared, because ad-hoc SQL cannot have this problem: no shared plan cache. If it is prepared, I compare EXPLAIN of the generic plan against a custom plan with real values, and look for the generic plan's tell — estimates computed from average selectivity rather than the actual parameter, typically a sequential scan where a custom plan would seek. From PostgreSQL 12 there is plan_cache_mode, so force_custom_plan is the direct lever, scoped as narrowly as I can manage. But I would also check whether the real cause is statistics: a stale or absent extended statistics object on correlated columns produces the same "estimated nine rows, actual three million" symptom, and CREATE STATISTICS on the correlated pair is a better fix than defeating the plan cache. In PostgreSQL 18 that investigation is faster because EXPLAIN ANALYZE now includes buffer counts by default and reports index searches per node.

Your team is 20 people and this keeps happening. What do you change organisationally?

I make plan stability a property of the deployment, not of individual heroics. Concretely: Query Store on everywhere with a retention policy and a regression alert wired to the on-call rotation, pg_stat_statements plus auto_explain with a sane log_min_duration on the Postgres side, and a rule that any query on a hot path ships with its access pattern documented and a test that runs it at both parameter extremes against production-sized data. Then I make the review question explicit — "what happens to this query when the parameter is NULL, or matches half the table?" — because the cheapest place to fix a sniffing problem is in the pull request that introduces the optional filter.

02Nineteen hundred deadlocks an hour

Senior Production incident / outage

(a) Worked example EXAMPLE — replace with your own

Month-end, 09:40, and the checkout service started returning 500s on about twelve percent of requests. The application log said "Transaction (Process ID 84) was deadlocked on lock resources with another process and has been chosen as the deadlock victim", and the rate was climbing: 1,900 deadlocks in the first hour against a baseline of maybe five a day. The tempting read was "too much traffic". It was not: traffic was up 20 percent, deadlocks were up 400-fold. Something non-linear was happening, and non-linear in a lock manager almost always means lock escalation.

The deadlock graphs were already in the system_health extended events session — they always are, which is the single most useful thing to know when this happens to you — and they showed two participants: the checkout procedure taking a row lock on Inventory then updating Orders, and a month-end allocation job updating Orders in a single statement that touched about 90,000 rows and then reading Inventory. Two things combined. First, the classic opposite lock ordering. Second, and the reason this month was different from every other month, the allocation batch had crossed the 5,000-lock threshold at which SQL Server escalates row and page locks to a table lock on Orders, so instead of colliding with a handful of checkout rows it collided with all of them. Escalation is not a bug either: holding five thousand individual locks costs memory, so the engine trades granularity for memory whenever a single statement passes the threshold — but the trade is invisible until the day it converts a rare collision into a storm.

Mitigation was three commands in ten minutes: I killed the batch, restarted it in 5,000-row chunks with a WAITFOR DELAY between them so no statement crossed the escalation threshold, and set LOCK_ESCALATION = AUTO on the partitioned Orders table so future escalations stop at the partition rather than the table. The durable fix over the following fortnight was more interesting: we made both code paths acquire objects in the same order (inventory before orders, written down in the service's README and asserted by a review checklist), and we turned on read-committed snapshot isolation for the database, which removed the entire reader-blocks-writer half of the problem. RCSI is not free — it moves version storage into tempdb, it adds 14 bytes per row and it changes read-committed semantics from "wait for the truth" to "read the statement-start snapshot" — so we sized tempdb, put it on its own storage, and audited the handful of places where code was relying on blocking as an accidental mutex. What I would do differently: I would have run the escalation math before month-end rather than during it. The 5,000-lock threshold is public and the batch size was ours to choose.

-- SQL Server: the escalation math, and the three levers.
-- Escalation triggers at ~5,000 locks in ONE statement (or under memory pressure).
UPDATE dbo.Orders SET AllocatedAt = SYSUTCDATETIME()
WHERE  AllocationBatchId = @batch;                  -- 90,000 rows -> table lock on Orders

-- 1) Batch below the threshold: the fix that needs no database-level change.
WHILE 1 = 1
BEGIN
    UPDATE TOP (4000) dbo.Orders SET AllocatedAt = SYSUTCDATETIME()
    WHERE  AllocationBatchId = @batch AND AllocatedAt IS NULL;
    IF @@ROWCOUNT = 0 BREAK;
    WAITFOR DELAY '00:00:00.100';                   -- let the OLTP traffic through
END

-- 2) Escalate to the partition, not the table (partitioned tables only).
ALTER TABLE dbo.Orders SET (LOCK_ESCALATION = AUTO);

-- 3) Remove reader/writer conflicts entirely. Not free: tempdb version store + 14 bytes/row.
ALTER DATABASE CURRENT SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;

-- SQL Server 2025: optimized locking (TID locking + lock-after-qualification) cuts lock
-- memory and blocking further - it REQUIRES accelerated database recovery, is off by default,
-- and only reaches its full benefit with RCSI on, because LAQ leans on row versions.
ALTER DATABASE CURRENT SET ACCELERATED_DATABASE_RECOVERY = ON;
ALTER DATABASE CURRENT SET OPTIMIZED_LOCKING = ON;
-- PostgreSQL: no lock escalation, ever. The failure mode is different, so the story is different.
-- Deadlocks are found by a timer, not prevented: deadlock_timeout (default 1s) then a graph check.
SHOW deadlock_timeout;

-- The Postgres equivalents of "the batch collided with everything":
--   * a foreign key makes every child insert take FOR KEY SHARE on the parent row ->

--   * an unindexed FK makes a parent DELETE scan and lock the child table;

SELECT * FROM jobs WHERE status = 'ready'
ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 100;   -- the queue pattern that scales

(c) Recall prompts

When did concurrency, not volume, take something down for you?

Hint: deadlocks, blocking chains, a hot row every request updates (a counter, a sequence table, a "last used" timestamp), a queue table without SKIP LOCKED, an advisory lock held too long, or a migration waiting on a lock and blocking everyone behind it.

Have you read an actual deadlock graph? What was in it?

Hint: two processes, the resources each held and each wanted, the statements, and the victim. If you have not, the system_health session on any SQL Server you can reach already has some; on PostgreSQL grep the log for "deadlock detected". Half an hour with a real one is worth more than any explanation.

Have you turned on RCSI or snapshot isolation in production? What did you check first?

Hint: tempdb sizing and placement, the 14 bytes of row overhead appearing on the next update of every row, code that relied on blocking as a mutex, and anything doing UPDLOCK/HOLDLOCK patterns deliberately. If you have only ever inherited it already on, say that — knowing what it costs is the real answer.

What is the hottest single row in a system you know, and what protects it?

Hint: an invoice-number table, a stock level, a wallet balance, an idempotency ledger. The good answer names the contention pattern and the mitigation actually used — a sequence instead of a counter table, sharded counters, an append-only ledger summed on read, or an outbox.

(d) Follow-up drill chain

Why chunk the batch instead of just disabling lock escalation?

Because disabling escalation trades a blocking problem for a memory problem, and the memory problem is harder to see coming. Every retained row lock costs lock-manager memory, and a statement holding hundreds of thousands of them under memory pressure can escalate anyway or push other work out of the buffer pool. Chunking is also strictly better operationally: it makes the batch restartable, it caps the size of any rollback if it fails, and it lets OLTP traffic through between chunks. I use LOCK_ESCALATION = AUTO on partitioned tables as a safety net for the case I did not think of, not as the primary control.

You turned on RCSI. What broke, or what could have?

Three things I look for. Code that used read-committed blocking as an accidental mutex — "read the balance, then update it" is correct under blocking reads and racy under snapshot reads, so those paths need UPDLOCK or an explicit UPDATE ... OUTPUT. Then tempdb: the version store lives there, it grows with the longest open transaction rather than with throughput, and one forgotten transaction can fill it — so tempdb gets its own fast storage, multiple data files and an alert on version store size. And finally the 14 bytes of versioning overhead added to each row as it is updated, which on a large, tightly packed table means page splits and a temporary jump in fragmentation and log volume. None of that is a reason not to do it; all of it is a reason to do it on a Tuesday with a rollback plan rather than at 09:40.

At what scale does "always acquire locks in the same order" stop being achievable?

It holds beautifully inside one service with a handful of tables and breaks down as soon as ordering depends on data — a transfer between two accounts must lock both, and the order depends on which accounts. There the technique is to impose a deterministic order on the data itself (lock the lower account id first), which is provably deadlock-free for that pattern. It breaks down completely when the transaction spans services or queues, and at that point the answer is not better locking but a different model: single-writer ownership per aggregate, an outbox with idempotent consumers, or optimistic concurrency with a version column and a retry. Above a certain size I would rather have a retry policy on a documented, cheap-to-retry conflict than a global lock ordering nobody can enforce.

How would this incident have looked on PostgreSQL?

Not as a deadlock storm, because there is no lock escalation to convert a narrow collision into a global one, and because readers never block writers. The same batch would have shown up as a long-running transaction holding back xmin, which stops autovacuum from cleaning any table in the database and produces bloat, growing index scans and, if it ran long enough, the wraparound alarm in story 06. The genuinely Postgres-shaped deadlock risk in a checkout flow is foreign-key row locks: every child insert takes a FOR KEY SHARE lock on the parent, so a hot parent row plus a concurrent parent update produces multixact contention and, with two code paths touching parents in different orders, deadlocks. The diagnosis path is different too — pg_stat_activity with pg_blocking_pids() and the deadlock graph in the server log rather than an extended events session.

What would you have told the business at 09:45, before you knew the cause?

Three sentences and a next-contact time: what customers are experiencing (about one checkout in eight fails and can be retried), what we are doing (we have identified a batch job as the likely contributor and are stopping it), and what we do not yet know (whether stopping it is sufficient, and whether any orders were lost — no, because the failing transactions rolled back cleanly). I would not give an ETA for the root cause in the first fifteen minutes, and I would say explicitly that the rollback means no partial orders exist, because that is the question the business actually has and nobody asks it out loud.

03One Postgres, or the SQL Server estate we already had

Principal Hard architectural trade-off

(a) Worked example EXAMPLE — replace with your own

We were standing up a new product line next to an eleven-year-old platform running on SQL Server Enterprise: three availability groups, a DBA team of two who were genuinely good, backup and DR runbooks that had been tested, and a monitoring stack that understood nothing else. The new team wanted PostgreSQL, and their reasons were real ones: JSON ergonomics, extensions (PostGIS was a hard requirement for one feature), no per-core licence on the twelve non-production environments they wanted, and honestly, hiring. My job was not to pick my favourite database. It was to decide what we would be able to operate at 03:00 in three years, with whoever is on call then.

I made the decision on four axes and wrote them down before looking at any product: operational surface (how many distinct failure modes must on-call know), cost shape (licence versus people versus cloud spend, and how each scales with environments rather than with load), capability fit (what the workload genuinely needs that only one engine has), and exit cost (what it takes to undo this in three years). The capability axis is the one that had changed most since the last time we ran this argument, and it had changed in SQL Server's favour: SQL Server 2025 shipped a native json type with JSON indexes rather than nvarchar(max) with computed columns, native regular expressions (REGEXP_LIKE, REGEXP_REPLACE) instead of CLR functions, and a native VECTOR type with DiskANN indexing. Several of the "we need Postgres for this" arguments that would have won in 2022 no longer hold; PostGIS still has no real equivalent, and that one did.

We landed on a boundary rather than a winner: the transactional core stayed on SQL Server, and the new product ran on PostgreSQL as its own service with its own data, communicating over the network and never over a linked server. What made that defensible was the boundary condition I insisted on — no distributed transaction, no cross-engine join, no shared table, and a single owning service per dataset — because a polyglot estate only pays off if the seam is a service boundary rather than a query. I also budgeted the second on-call skill set explicitly: two people trained on Postgres operations, a runbook parity checklist, and a rule that the Postgres side would use exactly one managed service rather than a hand-rolled cluster. The honest cost: our mean time to diagnose on the Postgres side was roughly three times worse for the first year, and we had one incident that was purely "nobody knew autovacuum needed tuning". What I would do differently: I would have made the DR drill mandatory in month one rather than month seven. We proved backups worked; we had not proved we worked.

(d) Follow-up drill chain

Why not standardise on one engine everywhere? Isn't polyglot persistence just entropy?

Mostly, yes — which is why my default is one engine, and why the burden of proof sits with the second one. I accept a second engine when there is a capability the first genuinely lacks and the workload genuinely needs (PostGIS here), when the data has a clean owner so the seam is a service boundary rather than a query, and when the organisation can fund the second operational skill set rather than hoping. What I will not accept is a second engine adopted for developer preference and then discovered to be load-bearing at 03:00 by someone who has never seen it before. The failure mode of standardisation, incidentally, is the mirror image: teams smuggling in a datastore anyway and running it badly because it is unofficial.

You put the boundary at the service. What breaks when the business asks for a report joining both?

That request arrives within a quarter, every time, so I plan for it rather than being surprised. The wrong answers are a linked server or a foreign data wrapper used as a permanent join — they turn a network partition into a query failure, they plan badly across the boundary, and they quietly reintroduce the coupling I just paid to remove. The answer I use is a third place: change data capture or logical replication into an analytics store where both datasets land and can be joined honestly, with an explicit staleness contract. That costs a pipeline and some latency, and it buys the property that neither production database can be taken down by a report — see story 20.

At what scale does the licence-cost argument actually decide it?

When environments multiply rather than when load grows. Per-core Enterprise licensing is charged on production cores, so a single large production instance is often cheaper than people expect and the argument is weaker than juniors assume. It becomes decisive when you want twenty ephemeral environments per team, when you want a read replica per consumer, when you want to run a copy per customer, or when the elastic pattern is scale-out-many-small rather than scale-up-one-big. My rule of thumb: if the architecture wants many database instances, the licence model will eventually pick the engine for you; if it wants one big one, choose on operations and capability, because the licence is a rounding error against a two-person DBA team.

Three years later it is going badly. How do you know, and what do you do?

I defined the signals when I made the decision, which is the part people skip: mean time to diagnose per engine, incidents attributable to the newer platform, on-call bus factor, and how often somebody asks for a cross-engine join. Going badly looks like a bus factor of one, most incidents coming from the smaller estate, and joins being requested monthly. The response is not a religious migration, it is a scoped one: move the workloads back that never needed the second engine, keep the ones that did, and be honest in the write-up that the boundary was drawn in the wrong place. Migrations are cheapest when they are partial and expensive when they are a statement about who was right.

I also gave them something concrete: ownership of the operational standard for Postgres across the company, which turned "we were constrained" into "we set the pattern". The mandate came down as a cost decision — move the billing platform off SQL Server Enterprise onto managed PostgreSQL — and the estimate that came with it was four months. It took fourteen. The schema conversion was the easy part and was done in three weeks with a conversion tool plus review; what consumed the other thirteen months was the set of behavioural differences that no tool can convert because they are not in the DDL, they are in the assumptions the application makes about how the database behaves.

Four of those cost us most of the time, and they are the four I would ask about in an interview. Collation and case sensitivity: the SQL Server database was SQL_Latin1_General_CP1_CI_AS, so WHERE email = 'Bob@x.com' matched bob@x.com, and roughly 900 places in the application relied on that without knowing it. PostgreSQL comparisons are case-sensitive by default; the modern fix is an ICU non-deterministic collation (CREATE COLLATION ... (provider = icu, deterministic = false)) applied to those columns, and the legacy fix you will meet in older code is citext or lower() everywhere with expression indexes. NULL ordering: ORDER BY x ascending puts NULLs first on SQL Server and last on PostgreSQL, which silently reordered several paginated screens. Isolation semantics: the application had accidental serialisation everywhere because SQL Server's default read committed blocks; on PostgreSQL nothing blocked, and two race conditions that had existed in the code for years became reachable in week one of the pilot. And identity versus sequences: SCOPE_IDENTITY() patterns, gaps behaving differently, and one import process that depended on identity values being contiguous.

The migration mechanics were the safe part precisely because we made them boring. We ran change data capture from SQL Server into PostgreSQL for four months, replaying live traffic, and every night a reconciliation job compared row counts and checksums per table and posted a diff. Then we ran shadow reads: production traffic hit SQL Server for real and PostgreSQL for comparison, and we logged every response that differed. That is where the collation and ordering bugs were found — not in testing, in shadow. Cutover itself was 40 minutes with a documented rollback that we kept viable for three weeks by continuing to replicate backwards. What I would do differently: I would have written the behavioural difference catalogue in week one and turned it into lint rules and tests, instead of discovering the items one at a time over a year. And I would have quoted the estimate as a range with the reason for the range — "four months if the application makes no assumptions about engine behaviour, and it certainly does" — because the four-month number followed us the whole way and made every honest status update sound like an excuse.

(d) Follow-up drill chain

Why CDC and shadow reads rather than a maintenance window and a dump/restore?

Because the risk in a cross-engine migration is not the data, it is the behaviour, and a dump/restore proves nothing about behaviour. Shadow reads gave us production's own traffic as the test suite, including the odd shapes no test author invents, and CDC gave us a target that was continuously current so the cutover window was minutes rather than hours. The cost is real: two systems live for months, a reconciliation pipeline to maintain, and the discipline to look at the diff every morning. For a same-engine move of a small database I would happily take the maintenance window — the technique should match the risk, and the risk here was correctness, not duration.

How did you decide what to rewrite versus what to translate mechanically?

By call frequency and by blast radius. Anything hot or financially load-bearing got rewritten by a person who understood both engines, because a mechanically translated procedure carries the old engine's assumptions inside it — cursors that were fine because of blocking reads, temp-table patterns that behave differently, error handling that no longer aborts the same way. Everything cold and simple got translated and covered by a characterisation test. The line I drew: if a mechanical translation would leave a comment saying "this works because SQL Server does X", it gets rewritten. That is also a useful rule for reviewers, because it is checkable.

At what point in the fourteen months should you have stopped the project?

The honest answer is that I should have forced a re-decision at month five, when it was clear the estimate was wrong by a factor rather than a margin. Not to cancel — the licence saving was real and the analysis still held — but to re-approve it at the true cost, because a project that survives by nobody looking at the number again is a project that has stopped being a decision. The stop conditions I would write today: the saving no longer exceeds the remaining cost, the behavioural defect rate found in shadow is not falling month over month, or the rollback stops being viable. Two of those were measurable and I was not measuring them.

What was the hardest thing to get right that had nothing to do with SQL?

The drivers and the connection layer. Timeouts behave differently, cancellation behaves differently, the pool has different semantics (see story 13), the ORM emits different SQL and different parameter types — and parameter types are where you get the silent performance cliffs, because a mistyped parameter defeats an index on either engine. Then the operational layer: monitoring, alerting thresholds, backup verification, and the runbooks. Migrating the data was a project; migrating the team's instincts was the actual work, and it kept going for six months after cutover.

Would you do it again?

For that system, yes, with a corrected estimate — the saving was real and the platform is genuinely better suited to how the team wants to build now. But I would not generalise it into a policy, and I pushed back when the success was used as an argument to move two more systems: one of them was heavy on availability groups and Agent jobs and a decade of T-SQL, and the cost profile there was completely different. The transferable lesson is that migration cost scales with how much the application depends on engine behaviour, not with data volume, and almost every estimate I have seen — including mine — gets that backwards.

So I made the upgrade falsifiable. The plan separated two things that people conflate and that must never be done in the same change: moving the binaries and changing the compatibility level. We restored the databases onto a SQL Server 2025 instance (GA 18 November 2025; we went in on CU8 from 13 August 2026 rather than RTM, because there is no prize for being on the original build) with the compatibility level left exactly where it was, so the cardinality estimator and the query-processing behaviour were unchanged. The genuinely new thing, and the fact I would use in an interview: PostgreSQL 18 carries planner statistics across pg_upgrade. (d) Follow-up drill chain

Why not raise the compatibility level in the same window as the restore?

Because they fail differently and you want to know which one failed. Moving the binaries changes the surface — drivers, TLS, agent jobs, permissions — and raising the compatibility level changes the optimizer, which is where the "everything got slow" folklore comes from. Doing them together means any regression has two candidate causes and your rollback has to undo both. Separating them also gives you a genuinely fast escape hatch: reverting a compatibility level is one statement and takes effect on the next compilation, whereas reverting an instance move is a failback with data loss implications. In PostgreSQL you do not get this luxury — the planner comes with the binaries — which is exactly why the baseline and the staged rollout matter more there.

Query Store is your safety net. What does it cost, and when does it hurt?

It costs write overhead on every query's statistics, disk for the store, and occasional pain when the store fills and flips to read-only — which is the most common way teams get burned, because a read-only Query Store silently stops capturing and your safety net is gone without an alarm. So I size MAX_STORAGE_SIZE_MB deliberately, set a stale-query threshold, use the size-based cleanup policy, and alert on the store's mode changing. On workloads with an enormous number of unique statement texts — heavy ad-hoc or unparameterised SQL — capture mode matters a lot: AUTO or a custom policy rather than ALL, or you spend real capacity recording queries that ran once.

At what scale does pg_upgrade --link stop being the answer?

When the downtime it needs — minutes, but minutes that scale with catalogue size rather than data size — exceeds the budget, or when the risk of a one-way door is unacceptable because --link shares the data files and a failed upgrade can leave you restoring from backup. At that point the technique is logical replication: build the new-version cluster as a subscriber, let it catch up, then flip the application with seconds of downtime, keeping the old cluster intact and able to take traffic back. That costs more setup, needs primary keys or replica identities on every replicated table, and historically did not carry sequence values across — which is precisely what PostgreSQL 19 addresses by replicating sequence values, and it is the single change that will most simplify these cutovers once 19 is GA.

Your CFO asks why upgrading is worth spending money on. What do you say?

I do not lead with features. I lead with the two things that have a number attached: the security exposure of running without patches — after 14 July 2026 a SQL Server 2016 instance gets nothing unless you buy extended security updates, and those cost real money per year and cover critical fixes only — and the compounding cost of being unable to hire, integrate or use current tooling against a dead version. Then I add the upside in their language: on this engine generation the optimizer and storage improvements typically let us defer a hardware or service-tier increase, and features like optimized locking or the current intelligent query processing set remove work we would otherwise pay engineers to do. The framing that works is that the upgrade is not a project, it is the rent on staying current, and estates that skip it pay it later with interest and under duress.

Something regressed a month after the upgrade, long after your window. How do you know it was the upgrade?

I can compare, because the baseline is still there: Query Store retains the pre-change plans and their runtime statistics, so "this query used to take 4 ms with plan 88 and now takes 300 ms with plan 91" is a query, not an argument. On the PostgreSQL side I keep a snapshot of pg_stat_statements from before the upgrade for the same reason, because it resets and without a snapshot you have nothing to compare against. If the evidence says the upgrade did it, the fix is the same triage as any regression — statistics, a rewrite, an index — and I resist the reflex to lower the compatibility level again, because that trades a specific problem for a permanent one.

06The wraparound warning nobody could read

Staff Data-corruption scare

(a) Worked example EXAMPLE — replace with your own

The log line was "database is not accepting commands that assign new XIDs to avoid wraparound data loss", and by the time somebody escalated it we were about four hours from a database that would refuse all writes. The alarming part was not the message; it was that three people had seen the earlier warning — the one that starts appearing tens of millions of transactions before the wall — and nobody had known what it meant. That is the real story here, and it is the one interviewers care about: an unfamiliar warning that stayed unread.

The mechanism is worth being able to explain cleanly, because it is the most PostgreSQL-shaped failure there is and it has no SQL Server equivalent. PostgreSQL identifies transactions with a 32-bit counter, so visibility is decided by comparing transaction ids modulo 232: a row is visible if the transaction that wrote it is "in the past". Since the space is circular, rows must be frozen — marked as unconditionally visible — before the counter laps them, and vacuum is what does the freezing. Anything that stops vacuum from advancing therefore consumes the runway. In our case three things held it back at once: a reporting session that had been idle in transaction for eleven days, an orphaned prepared transaction from a distributed-transaction experiment that nobody remembered enabling, and a logical replication slot for a consumer that had been decommissioned in March. Each of those pins the oldest transaction id the system may reclaim; all three together meant autovacuum had been running constantly and freezing nothing for months.

The fix took twenty minutes once the cause was named: ROLLBACK PREPARED on the orphan, terminate the idle session, drop the dead replication slot, then let aggressive vacuum run — it caught up in about ninety minutes on the biggest table because it was reading pages it had already scanned dozens of times without being permitted to freeze anything. Then the durable work: an alert on age(datfrozenxid) crossing 500 million (against autovacuum_freeze_max_age of 200 million and the failsafe at 1.6 billion, so 500 million is early and calm rather than late and loud), alerts on the oldest xmin holder of any kind, idle_in_transaction_session_timeout set globally, and a monthly review of replication slots. What I would do differently: I would have written the runbook entry the first time the warning appeared. It had been in the log for six weeks, and the honest root cause of the incident is not the replication slot — it is that our log alerting matched on the word "ERROR" and these were warnings.

(d) Follow-up drill chain

Explain wraparound to a developer in three sentences.

PostgreSQL decides whether you can see a row by comparing transaction ids, and that counter is 32 bits, so it wraps around roughly every four billion transactions. To stop old rows becoming "in the future" and vanishing, vacuum marks them frozen — permanently visible — long before the wrap. If anything prevents vacuum from freezing (a long-open transaction, an abandoned replication slot, a prepared transaction), the runway shrinks, and rather than risk showing wrong data the database stops accepting new writes.

Why not just raise autovacuum_freeze_max_age and move on?

Because that is spending the runway rather than fixing what is consuming it. Raising it delays aggressive vacuum, which reduces the frequency of the scans but increases the amount of work each one has to do and shrinks the margin you have when something genuinely goes wrong. There are legitimate reasons to move it — a very large, mostly-static table where a full freeze scan is expensive, on a version before the visibility-map improvements — but that is a tuning decision made with a monitoring story attached, not a response to an alarm. The alarm is telling you something holds xmin; the correct answer is to find it.

At what scale does this stop being a hygiene issue and become an architecture issue?

Roughly when a single table's freeze scan cannot finish inside your maintenance appetite, or when transaction volume is high enough that four billion ids is weeks rather than years — a system doing ten thousand write transactions a second burns the space in about five days, and at that point wraparound handling is a design constraint, not a chore. The architectural answers are the usual ones: partition so that freezing happens per partition and old partitions freeze once and stay frozen, keep long-running analytical work off the primary so nothing holds xmin, and be deliberate about hot_standby_feedback, which trades primary bloat for replica query survival. It is also the honest place to mention that 64-bit transaction ids have been a long-running community effort and are not in core today, so this remains a real operational property of PostgreSQL in 2026.

What is the SQL Server version of this problem?

There is no transaction-id wraparound, but the same underlying shape — the oldest open transaction pins version cleanup — produces a very familiar incident. With RCSI or snapshot isolation on, row versions live in the tempdb version store and cleanup cannot advance past the oldest active snapshot transaction, so one forgotten transaction fills tempdb and the whole instance stops. With accelerated database recovery enabled the versions live in the database's own persistent version store instead, which moves the failure from tempdb to the user database's file growth and makes sys.dm_tran_persistent_version_store_stats the thing to watch. The operational lesson transfers exactly: alert on the age of the oldest active transaction, and put a timeout on anything that can hold one.

How did you stop the next unfamiliar warning from being ignored?

Two changes, one mechanical and one cultural. Mechanically, log-based alerting stopped matching on severity words and started matching on an explicit allowlist of known-benign patterns, so anything unrecognised pages someone during business hours — noisy for a fortnight, then quiet, and the noise is what produced the runbook entries. Culturally, I made "I do not know what this message means" a legitimate and expected escalation, and I demonstrated it myself in the channel a few times, because the reason three people scrolled past that warning was that admitting unfamiliarity felt more expensive than ignoring it. That is a fixable property of a team and it is worth saying out loud in an interview.

07Random UUIDs as the clustering key

Senior Technical disagreement with a colleague

(a) Worked example EXAMPLE — replace with your own

His reasons were good ones and I want to be fair to them: identifiers could be created client-side before the row existed, merges between environments could not collide, and nothing leaked business volume the way a sequential integer does. My objection was narrower than "UUIDs are bad" — it was that on SQL Server, making a random UUID the clustered index key means every insert lands on a random page of a table that is physically ordered by that key, which is a page-split machine. We were arguing from anecdotes, and both of us could cite a blog post. So I stopped arguing and built the measurement, which is the part of this story worth telling.

The harness inserted fifty million rows into four table shapes on identical hardware and measured insert throughput, index fragmentation, final size and write-ahead log volume. On SQL Server the random-UUID clustered table ended around 40 percent larger than the sequential one with average fragmentation in the high nineties, and insert throughput degraded steadily as the table grew because each insert dirtied a different page and the buffer pool could not keep the working set. On PostgreSQL the same test was much less dramatic — heap tables are not stored in primary-key order, so there is no clustering key to fight — but the effect was still visible in the B-tree index itself and, more interestingly, in WAL volume: random insertion touches many more distinct index pages, and with full-page writes after a checkpoint that turns into measurably more bytes written and shipped to replicas. That was the number that changed the conversation, because it had a cost attached in replica lag rather than in an abstract fragmentation percentage.

The resolution was not that I won. It was UUIDv7: time-ordered UUIDs keep the client-side generation and the merge-safety he wanted while restoring insert locality. We also separated two decisions that had been tangled: the primary key (logical identity, what foreign keys reference) and the clustering key (physical ordering, what the table is sorted by) — on SQL Server you can keep a non-clustered UUID primary key and cluster on something naturally increasing, and that is often the right answer for a table that is inserted in time order and read by time range. What I would do differently: I would have shown him the harness before writing the opinion. (d) Follow-up drill chain

Why is this so much worse on SQL Server than on PostgreSQL?

Because a SQL Server clustered index is the table: rows are stored in clustered-key order, so inserting a random key means finding a random page, and when that page is full the engine splits it — allocating a new page, moving half the rows, logging all of it. That produces fragmentation, wasted space, more pages for the same data and therefore a bigger memory footprint. PostgreSQL heap tables have no such physical ordering: a new row goes wherever there is free space, so inserts stay cheap regardless of key order. The cost there is confined to the index structure and to WAL — random insertion dirties far more distinct index pages per checkpoint cycle, so full-page writes multiply. Same underlying principle, very different magnitude, and being able to say which and why is the difference between having read about this and having measured it.

Would you ever accept random UUID keys?

Yes, in three situations. When identifiers must be genuinely unguessable and are created offline or on many uncoordinated writers, and the table is small enough that locality does not matter. When the table is write-once and read by key — a document store shape — where clustering buys little. And when the alternative is a distributed sequence generator that adds a coordination dependency to the write path, which is a worse trade for the same problem. What I will not accept without a fight is a random UUID as the clustering key on a large, high-insert table on SQL Server, because that is the one combination where the cost is structural rather than marginal.

UUIDv7 embeds a timestamp. Is that a problem?

It is a real trade and worth naming before someone else does. A v7 identifier leaks its creation time to anyone who can see it, which for most systems is harmless and for some — anything where the sequence of records is itself sensitive — is a genuine information disclosure. It also does not hide volume as well as people assume: v7 randomises the tail, so it does not leak a count the way a sequential integer does, but a collector of identifiers learns your timeline. If that matters, the answer is the two-key pattern: an internal ordered key and an opaque external identifier, which is more work and completely defensible. What I would not do is choose v4 for privacy reasons without writing down what the privacy requirement actually is, because that is how systems end up paying a structural cost for a threat nobody has articulated.

At what table size does this argument start mattering?

It is invisible below roughly a million rows and becomes a production issue when the table plus its indexes exceed what fits comfortably in memory, because that is when random insert locality turns into physical reads. For SQL Server there is a second threshold that arrives earlier: the point where fragmentation makes range scans and index maintenance expensive, which shows up in maintenance-window duration before it shows up in query latency. My practical rule is that under a few million rows you should choose whatever the team finds clearest, and above a hundred million you should have measured. The mistake is arguing about it at either extreme with the intensity that only the middle deserves.

He shipped it and you changed it. How did you keep him on side?

By making the requirement he cared about non-negotiable in my own proposal. His actual need was client-side generation and merge-safety, so I never proposed removing UUIDs — I proposed a UUID that also had locality, which meant he lost nothing he had argued for. I also gave him the harness and let him run it himself, because a result you produce is more convincing than a result you are shown, and he found an effect I had missed on the index-only-scan side. Then I put his name first when we wrote it up as a schema guideline. The general principle: if your proposal requires the other person to have been wrong, it is a worse proposal than one that requires them to have been incomplete.

Mid Nasty debugging session

(a) Worked example EXAMPLE — replace with your own

Finance reported that the daily settlement total was wrong by small amounts — never more than a few hundred out of several million — and only on some days. It reconciled against the ledger on about 98 percent of runs. That intermittency is what made it nasty: a query that is always wrong is a bug, a query that is wrong two days in ten is a race, and races in a database are a small, learnable set of causes.

There were two, layered, and the first one hid the second. The report query carried WITH (NOLOCK) on three tables — added years earlier by someone who believed it meant "go faster". What NOLOCK actually means is read uncommitted, and beyond the well-known dirty-read problem it has a less-known one that exactly matches our symptom: a scan running without shared locks can follow the allocation order of pages while another transaction is splitting or moving them, so it can read the same row twice or miss a row entirely — not dirty data, but duplicated and skipped committed data. On a settlement run that overlaps the evening batch that updates those same rows, that is a total that is off by a few rows' worth. Reproducing it took a day: I ran the report in a loop against a copy while a writer updated rows in the range, and counted mismatches, which is the technique I would use again for any "wrong sometimes" complaint.

Under it was a second, quieter fault. The join between the payments table and the ledger compared an nvarchar column to a varchar column, so the plan showed CONVERT_IMPLICIT on the indexed side and a seek had silently become a scan — which is why the report took eleven minutes and therefore had a long window in which to overlap the batch at all. The fix was three changes: delete every NOLOCK from the reporting path and run the report in snapshot isolation (a genuine point-in-time read that blocks nobody, which is what the original author actually wanted), align the column types so the join could seek, and move the report to a schedule that does not overlap the batch as a belt-and-braces measure. Runtime went from eleven minutes to under twenty seconds, and the reconciliation has matched on every run since. What I would do differently: I spent the first afternoon assuming the application was double-counting, because "the database returned the wrong rows" felt like an unlikely explanation. I should have tested the query in isolation against a static copy on hour one — if the report is correct against frozen data and wrong against live data, you have localised the bug to concurrency in ten minutes.

(d) Follow-up drill chain

Explain exactly why NOLOCK can return a row twice.

Because a scan without shared locks can be walking pages in allocation order at the same moment another transaction splits a page. A split moves roughly half the rows from a full page to a newly allocated page, and if that new page sits ahead of the scan's current position, the scan reads those rows again; if the rows move behind it, it never sees them. The rows involved are fully committed — this is not the dirty-read problem people cite — so the result is silently, plausibly wrong. That property is exactly why the hint is dangerous in reporting: dirty reads make you nervous, but duplicated committed rows look like real data.

Snapshot isolation was your fix. What did that cost?

Version-store space in tempdb for the duration of the report, which for an eleven-minute report over a busy table was not trivial and is exactly why fixing the type mismatch mattered — shortening the transaction shrank the version store need by roughly the same factor as the runtime. It also introduces update-conflict errors if a snapshot transaction writes to a row that changed after its snapshot began, which is fine for a read-only report and needs care anywhere else. And it changes the semantics: I am now reading a consistent point in the past rather than the present, so the report has to state the moment it represents, which finance considered an improvement over "approximately now, mostly".

At what point does this reporting query stop belonging on the primary at all?

When its resource profile stops looking like OLTP: large scans that evict the buffer pool, a runtime long enough that its snapshot or its xmin holds cleanup back, or a schedule that must not compete with the write path. Twenty seconds once a day is fine on the primary; eleven minutes overlapping the evening batch was not. Beyond that, the move is a read replica with an explicit staleness contract (story 15), or a real analytical copy — and on SQL Server there is a middle option worth knowing: a nonclustered columnstore index on the OLTP table for real-time operational analytics, which changes the resource profile of the report rather than moving it (story 20).

How do you stop NOLOCK from coming back?

Detection plus a better default. Detection is a CI check that greps migrations and application SQL for the hint and fails with a link to a one-paragraph explanation — cheap, and the link matters more than the failure, because people add it in good faith. The better default is RCSI on the database, so that the blocking problem the hint was reaching for no longer exists; without that, the check just makes people fight you. I also make the reporting path's isolation level explicit in the code rather than inherited, because the third way this comes back is a new report copied from an old one.

The same complaint arrives on PostgreSQL. What is your first hypothesis?

Not dirty reads, since READ UNCOMMITTED is treated as read committed, so that class is off the table by design. My first hypothesis is a multi-statement report running in read committed, where each statement takes its own snapshot and the numbers therefore come from two different instants; the test is to wrap it in a single repeatable-read transaction and see whether the discrepancy vanishes. My second is OFFSET-based pagination with a non-unique sort key, which duplicates and skips rows under concurrent inserts and produces exactly this class of small, intermittent error. Third is a join fanning out on a non-unique key, which is not concurrency at all — and I check it early because it is the cheapest to rule out with a count of the join key on both sides.

09Twelve billion rows and a nightly DELETE

Staff Scaling challenge

(a) Worked example EXAMPLE — replace with your own

The events table had 12 billion rows and a retention policy of 90 days, enforced by a nightly job that ran DELETE ... WHERE created_at < now() - interval '90 days'. When I inherited it, that job took about four hours, occasionally did not finish before the morning, and had twice filled the transaction log. Everyone knew it was bad. What made it interesting is that the obvious fixes — chunk the delete, run it more often, add an index — are all improvements to the wrong thing. Deleting rows is the most expensive way to remove data from a relational database, and on a table that size it should not be happening at all.

The reason is worth stating precisely because it is the technical core of the story and it differs by engine. On PostgreSQL a DELETE does not remove anything: it marks tuples dead, which are then vacuumed, which rewrites visibility maps and index entries and leaves the table physically the same size with holes in it. So a nightly 200-million-row delete generates enormous WAL, produces bloat, keeps autovacuum busy all day, and never returns disk. On SQL Server the delete is fully logged, so it grows the log, it takes locks that escalate past 5,000 rows per statement (story 02), and on a clustered index it leaves ghost records for the cleanup task. In both engines the correct operation is not deletion but detaching a partition: metadata, no row-by-row work, effectively constant time.

We partitioned by day. On PostgreSQL that is declarative range partitioning with a scheduled job creating tomorrow's partition and running DETACH PARTITION CONCURRENTLY on the one that aged out — concurrently matters, because a plain detach takes a lock that stops all access to the parent table. On SQL Server it is a partition function and scheme with a sliding window: SWITCH the oldest partition out to an empty staging table (a metadata operation), then drop the staging table. The nightly cleanup went from four hours to under 200 milliseconds. Two things surprised us. First, partition pruning turned out to be the bigger win: dashboards querying the last 24 hours went from scanning an index over 12 billion rows to touching one partition, and p95 fell by roughly an order of magnitude. Second, the constraint that cost us most design time was uniqueness — on PostgreSQL a unique index on a partitioned table must include the partition key, so our natural unique key on event_id alone was not expressible and we had to decide whether to widen it or enforce uniqueness elsewhere. What I would do differently: I sized partitions by convenience (a day) rather than by measurement. Daily partitions over 90 days is 90 partitions, which is fine — but the same team later partitioned another table hourly and discovered that planning time grows with partition count, and that thousands of partitions makes every query slower. Choose the granularity from the retention unit and the query pattern, and check the plan afterwards.

(d) Follow-up drill chain

You could not express a global unique constraint on event_id. How did you handle that?

Three options were on the table and I would defend any of them in context. Widen the key so uniqueness is (created_at, event_id), which is what we did — it is honest, it is enforced by the engine, and it means the identifier is only unique together with its day, which we made explicit in the API. Alternatively, generate identifiers that are unique by construction (UUIDv7, or a snowflake-style id containing the timestamp), so a database constraint is not the mechanism preventing collisions. Or keep a small separate table holding just the identifiers with a real unique index, which reintroduces a write to an unpartitioned hot table and was the option I liked least. What I would not do is pretend the constraint exists when it does not, which is how you end up with duplicate identifiers discovered by an analyst two years later.

At what partition count does this design turn against you?

Planning time and catalogue overhead grow with the number of partitions, and although runtime pruning has improved a lot, both engines still do work proportional to partition count during planning. My rule of thumb is that a few hundred partitions is comfortable, a few thousand needs measurement, and tens of thousands is a design smell — usually someone partitioning hourly for a retention policy expressed in months. The fix when it happens is a two-level scheme, or coarser partitions with an index that supports the hot query, or accepting that the truly hot recent data belongs in a different, smaller table. It is also worth checking the queries that do not filter on the partition key, because those now scan every partition, and a report that was merely slow before can become pathological.

How did you migrate 12 billion existing rows into the partitioned table without downtime?

Not by copying them all. On PostgreSQL the trick is that the existing table can become a partition: create the partitioned parent, then ATTACH the old table as the partition covering all history, with a matching CHECK constraint added as NOT VALID and validated first so the attach itself does not have to scan under an exclusive lock. New days land in new partitions and the old monolith ages out naturally over the retention period — the migration cost is nearly zero and time does the work. On SQL Server the equivalent is to build the partitioned table alongside, batch-copy history with minimal logging into the aligned staging tables and SWITCH them in, then flip the application with a rename. Both approaches share one property I insist on: at every point there is a state you can stop in.

What if the retention rule is not time, but "delete everything for this customer"?

Then partitioning by time does not help you at all and you have a different problem — one that is increasingly common because of erasure requests. The options are to partition by customer (works when customers are few and large, fails when they are many and small, because you get the partition-count problem), to keep erasure-scoped data in its own tables so deletion is a small number of narrow deletes, or to encrypt per customer and delete the key, which turns erasure into a metadata operation at the cost of making that key material load-bearing forever. In practice I design for both axes separately: time-based retention through partitioning, and subject erasure through a data map that says exactly which tables hold personal data and a tested procedure per table. Conflating them produces a partition scheme that serves neither.

The nightly job still exists. What does it do now, and how do you know it worked?

It creates tomorrow's partition and detaches the one that aged out, and the important part is that it is idempotent and monitored on both directions. Monitored on both directions means: alert if the newest partition does not extend at least N days into the future (the failure mode that hurts most is running out of future partitions, because inserts then fail or land in a default partition and quietly ruin pruning), and alert if the oldest partition is older than the retention policy, which is a compliance issue rather than a performance one. I also assert the row count of a partition before dropping it, so a bug that detaches the wrong range is loud rather than silent. Cheap checks, and they are exactly the ones nobody writes until the first incident.

10One connection pool, forty tenants

Staff Security issue found and fixed

(a) Worked example EXAMPLE — replace with your own

The multi-tenant design was the standard one: shared schema, a tenant_id column on every table, and row-level security in the database as the backstop so a forgotten WHERE clause in application code could not leak across tenants. It had been reviewed, it had tests, and it was correct — in a single-session test harness. In production, behind a transaction-pooling connection pooler, it was not. I found it while investigating something unrelated: a support engineer reported seeing a row that belonged to another tenant appear once in a list and never again.

The mechanism is a beautiful trap, and it is the technical core of this story. PostgreSQL row-level security policies read the tenant from a session variable — current_setting('app.tenant_id') — which the application sets after checking out a connection. SET is session-scoped. Under PgBouncer in transaction pooling mode a "session" is not yours: connections are handed back to the pool at the end of each transaction, so the variable you set outlives your request and is inherited by whoever gets that connection next. The correct primitive is SET LOCAL, which is transaction-scoped and reset at commit — and therefore requires that every query run inside an explicit transaction, which was the actual code change and the actual argument. There is a second, independent trap in the same feature: the table owner bypasses row-level security unless you enable FORCE ROW LEVEL SECURITY, and application roles are very often the owner because that is what the migration tool connected as. We had both problems. Only the first one had ever fired.

SQL Server's version of this is worth knowing because interviewers like the comparison: predicate functions read from SESSION_CONTEXT, set with sp_set_session_context and — crucially — @read_only = 1, so application code cannot overwrite the tenant after the framework sets it. The built-in .NET connection pool calls sp_reset_connection when a connection is reused, which clears session context, so the equivalent leak is much harder to create by accident; you reintroduce it by building your own pooling, by multiplexing tenants over one connection, or by caching a connection across requests. I fixed ours in three parts: SET LOCAL inside a mandatory transaction wrapper, FORCE ROW LEVEL SECURITY plus a non-owning application role, and a canary test in CI that opens two pooled connections, sets tenant A on one, and asserts the other cannot see A's rows. Then a log-based check: for one week we logged the tenant claim from the request alongside the tenant of every row returned, and alerted on mismatch. Zero hits after the fix, three hits from a background job before it, which is how we knew the support report was not a one-off. What I would do differently: I would have tested the security control through the pooler from the beginning. We had tested it against the database, which is a different system from the one running in production.

-- PostgreSQL: the policy is correct. The way the variable is set is what leaks.
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE  ROW LEVEL SECURITY;   -- without this, the TABLE OWNER bypasses RLS
CREATE POLICY tenant_isolation ON invoices USING (tenant_id = current_setting('app.tenant_id')::uuid);

-- WRONG under a transaction-pooling pooler: session-scoped, survives into the next borrower.

-- RIGHT: transaction-scoped, discarded at COMMIT. Requires an explicit transaction per request.

  SET LOCAL app.tenant_id = '11111111-1111-1111-1111-111111111111';

GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_rw;

(d) Follow-up drill chain

Why keep row-level security at all if the application already filters by tenant?

Because they fail independently and for different reasons, which is the whole argument for defence in depth. Application filtering fails by omission — a new endpoint, a raw SQL report, a migration script, an engineer in a console — and row-level security fails by misconfiguration, which is a single, reviewable, testable property rather than a per-endpoint discipline. Having both means an incident needs two failures. I also value it for a non-security reason: it makes the isolation rule explicit and centrally readable, so a new engineer can find out how tenancy works in one place instead of inferring it from sixty query builders.

SET LOCAL requires an explicit transaction on every request. What did that cost?

A real change in how the data-access layer works, and some latency. Every read now opens and commits a transaction, which is cheap but not free, and it forced us to be honest about a handful of endpoints that were doing multi-second work with a database connection checked out. It also interacts with the pooler: transaction pooling gives you a connection per transaction, so long transactions now hold pool slots and a slow endpoint can starve the pool (story 13). The alternative some teams use is session pooling, which makes SET safe again at the cost of far fewer effective connections. I would take the transaction wrapper again, because it makes the security property structural rather than dependent on which pooling mode someone configured.

At what tenant count does shared-schema-with-RLS stop being the right design?

It scales well upward in tenant count — thousands is fine — and breaks on the axes that have nothing to do with row filtering: noisy neighbours (one tenant's query plan or data volume degrading everyone), per-tenant restore (you cannot restore one tenant from a shared backup without a lot of bespoke work), per-tenant data residency, and per-tenant schema variation. Those push you toward schema-per-tenant or database-per-tenant, which trade the isolation problem for a migration and connection-management problem: applying a schema change to 4,000 databases is its own engineering programme, and connection pooling across them is genuinely hard. My default is shared schema with row-level security until one of those four axes bites, and then a hybrid — the largest or most regulated tenants get their own database, everyone else stays shared.

You found three historical occurrences. How do you handle disclosure?

The escalation is mine; the disclosure decision is not. Same day, I take it to whoever owns risk with the concrete evidence — what leaked, to whom, when, for how long, and what the retention limits are on my ability to answer that — and I say explicitly which parts I cannot prove. In this case the three occurrences were a background job reading a stale session variable rather than a customer seeing another customer's data through the UI, which materially changes the assessment, so I would lead with that distinction rather than with the headline. What I insist on regardless of the disclosure outcome is that an incident record exists, because that record is what funds the systemic work — the canary test, the role separation — in the next planning cycle.

How would you find every other instance of this bug class across the estate?

Three passes, cheapest first. A configuration pass: enumerate every database, list tables without row-level security enabled and every role with BYPASSRLS or table ownership, which is a query and gives you a ranked review list in an afternoon. A test pass: package the two-connection canary as a shared test that any service can adopt, run against a seeded fixture in CI — that is the one that keeps working after everyone forgets the incident. And a runtime pass: log the request's tenant claim alongside the tenant of returned rows and alert on mismatch, first in staging, then production, because it observes actual behaviour rather than intent and catches the cases the other two miss.

(d) Follow-up drill chain

Why start with estimated versus actual rows rather than with index design?

Because it is the diagnostic that explains the most plans with the least theory. Nearly every catastrophic plan is the optimizer being confident about a number that is wrong — a nested loop chosen because it expected one row and got three million, a hash join with a memory grant sized for a fraction of the real data. How do you teach this to someone who resists it?

I find out what the resistance is about, because it is rarely the material. For the first, I shrink it: fifteen minutes on their own query, in a pull request, with me asking the questions rather than giving the answers. For the second, I make them succeed once, quickly, on something real, because one experience of finding the answer yourself dissolves more resistance than any argument. If someone genuinely does not want to learn it, I stop pushing and make sure the team has enough people who can; not everyone has to be good at everything, and forcing it wastes both of us.

Around three teams, in my experience. Sessions do not scale past the people in the room, and the second cohort always gets a worse version of the material. It is mine before it is theirs, publicly, and theirs before it is mine, privately. Publicly I own the gap: I taught the technique and not its limits, which is a real failure mode of quick training — people learn to spot the row discrepancy and then add an index in every situation because that is the tool they now have. The database was not busy. CPU was 30 percent, there were no blocking chains, and the slow query log was quiet. The pool was full and the database was idle, which sounds contradictory until you think about what a connection is for.

The cause was a single endpoint that opened a connection, then called an external pricing API, then used the connection. At 09:00 the pricing provider's own morning peak pushed their p99 to about eight seconds, so each of our requests held a pooled connection for eight seconds doing nothing. With a default maximum pool size of 100 per connection string, per process, arithmetic decides the rest: at 40 requests per second to that endpoint, each holding a connection for eight seconds, you need 320 connections to keep up and you have 100. The queue grows, everything else that wants a connection waits behind it, and the whole service degrades because of one endpoint's dependency. This is Little's law doing what it always does, and it is the single most useful mental model for pool incidents: concurrency = arrival rate × hold time. You almost never fix these by raising the pool size; you fix them by shortening the hold time.

Mitigation at 09:10 was to move the external call outside the connection scope — a one-line change in that handler, shipped as a hotfix — plus a command timeout so a single slow call could no longer hold a connection indefinitely. (d) Follow-up drill chain

Why not just raise the pool size to 400?

Because it moves the queue rather than removing it, and it moves it somewhere worse. The endpoint still holds a connection for eight seconds; with 400 slots you now have 400 mostly-idle connections against a database that has its own limits — worker threads on SQL Server, one process each on PostgreSQL, memory per connection on both — and when the dependency degrades further you saturate again, this time with enough concurrency to hurt the database itself. Raising the pool is a legitimate short-term action while you fix the hold time, and I have done it under pressure, but on its own it converts a fast, clear failure into a slow, murky one. The general principle: when a queue is full, look at service time before you look at capacity.

What is the right timeout, and what breaks when you set it?

Shorter than the caller's patience and longer than the legitimate p99 — which means you need to know the p99, and most teams set timeouts without measuring it. The trap is that a too-short timeout on a write turns a slow success into an ambiguous failure: the statement may still be running on the server after the client gives up, so anything non-idempotent needs an idempotency key or a way to determine the outcome, otherwise you get duplicate orders under load. So I pair timeouts with cancellation that actually reaches the server, and with idempotent writes. On PostgreSQL I also set statement_timeout and idle_in_transaction_session_timeout server-side, because a client-side timeout alone leaves the server doing the work anyway.

At what scale does client-side pooling stop working on PostgreSQL?

As soon as you have more application instances than you have connection budget, which arrives quickly with containers: thirty pods each with a pool of twenty is 600 connections against a max_connections that is realistically a few hundred, and every one of those is a backend process with its own memory. That is why an external pooler is effectively mandatory in a Kubernetes-shaped deployment, and it is the point where you have to choose a pooling mode and live with the consequences — transaction pooling gives the big multiplexing win and takes away session state, which is exactly the trap in story 10. SQL Server has more headroom here because connections are threads rather than processes, but it is not unlimited either, and the same arithmetic applies once you have enough services.

How do you detect this before customers do?

By monitoring the pool as a resource in its own right, which almost nobody does until after their first incident: utilisation, wait time to acquire, and hold-time percentiles per endpoint, all exported from the client. A pool at 95 percent utilisation is an incident in about ten minutes and it is completely invisible from the database side. On the server side I pair it with the number of connections by state — the idle in transaction count on PostgreSQL is a leading indicator of a whole family of problems — and an alert on the oldest open transaction. Together those two dashboards would have caught this weeks earlier, because the 09:00 pattern was visible in hold time long before it crossed the pool ceiling.

The pricing API is slow again next month. What is different?

Nothing about the database, which is the point of the fix. The connection is taken after the call returns, so a slow provider now shows up as slow responses on that one endpoint and nothing else — and because that endpoint has its own pool, even a total provider outage cannot consume the shared capacity. Beyond that I would want a circuit breaker so we stop calling a dead dependency, a cached or stale-acceptable price where the product allows it, and an explicit decision about the degraded behaviour: fail the quote, or issue it with yesterday's price and a flag. That last decision is a product call, not an engineering one, and getting it made in advance is what separates a designed degradation from an outage.

Why itemise before optimising? That took two weeks with no saving.

Because without it the effort goes where the folklore points, which is almost always at query tuning, and query tuning was worth about a third of what switching things off was worth. The itemisation also produced the thing that made the saving durable: a named owner per instance. Dropping 34 indexes sounds risky. How did you not break anything?

By treating it as a reversible experiment with a long observation window. At what point does cost optimisation become false economy?

When you start spending engineer-months to save infrastructure-thousands, and when the savings start eating headroom rather than waste. The arithmetic that keeps me honest is straightforward: a team of five costs far more per year than most database line items, so an optimisation that consumes a quarter of that team's capacity must save an enormous amount to break even. Beyond that, there is a reliability floor — capacity headroom for traffic spikes, replicas for failover rather than for reads, backup retention that matches the recovery objective — and I treat that floor as non-negotiable and say so explicitly, because it is the first thing that gets traded away when cost becomes a target. The version of this that I actively resist is a cost target set without a reliability constraint attached.

How do you stop the cost from growing straight back?

Ownership plus visibility plus a default. Ownership means every instance has a named team and a tag, and an untagged instance gets a ticket and eventually gets stopped. Visibility means the unit cost sits on the same dashboard as latency and error rate, so a cost regression is noticed by the team that caused it rather than by finance a quarter later. The default means new non-production environments come with a shutdown schedule and a small size unless someone opts out with a reason. None of that is clever, and all of it works better than a periodic cleanup campaign, because campaigns depend on attention and defaults do not.

An executive asks you to cut the bill by another 40 percent. What do you say?

I say what it would cost, in their currency, with the reliability consequences named. After the easy two thirds is gone, another 40 percent is not an optimisation, it is an architectural change: consolidating instances (noisy neighbours, blast radius), moving to a fundamentally cheaper storage or service tier (slower restores, less headroom), or removing a replica (reduced failover capability). Each of those is a real option and I will cost them honestly, but I will insist the trade is written down and accepted by someone who owns the outcome, not absorbed silently by engineering. And I would offer the alternative framing: the unit cost is the number the business should care about, and if volume is growing, holding unit cost flat while absolute spend rises is a win, not a failure.

15The replica that was forty minutes behind

Staff Cross-team / integration dependency

(a) Worked example EXAMPLE — replace with your own

Another team consumed our data from a read replica we owned. One Tuesday their reconciliation started failing, and the ticket said "your database is returning stale data". It was: replay lag had reached about forty minutes. The interesting part is that both teams were behaving reasonably. We had never told them what staleness to expect, and they had built a workflow that assumed the replica was the primary with better availability. Nobody had written down a contract, so we had an integration failure dressed as a database problem.

The cause was theirs, mechanically, and this is where the engine details matter. On PostgreSQL a hot standby that runs long queries hits a conflict: replay wants to remove rows that a running query on the standby still needs to see. The engine resolves it by either cancelling the query after max_standby_streaming_delay or, if hot_standby_feedback is on, by telling the primary to hold those rows back — which stops the primary from vacuuming and creates bloat there instead. Their nightly job ran a four-hour analytical query on the standby, we had hot_standby_feedback off and a generous max_standby_streaming_delay, so replay simply waited. Forty minutes of lag was the system doing exactly what it had been configured to do. The SQL Server equivalent on an availability group replica is the same story with different names: a long-running read on a readable secondary takes a schema stability lock that can block the redo thread, and you watch it as redo queue size in sys.dm_hadr_database_replica_states.

The fix was one third technical and two thirds contractual. Technically: their long query moved to a dedicated replica where lag does not matter, we set a bounded max_standby_streaming_delay on the shared one so replay wins over queries there, and we exposed replay lag as a first-class metric in a health endpoint they could read. Contractually — and this is the part I would lead with in an interview — we wrote a two-page agreement: the replica is eventually consistent with a stated objective of under five seconds at p99, lag is published and alertable, reads that require read-your-own-writes go to the primary, and the consumer must handle a stale response rather than assuming freshness. Then we gave them a mechanism instead of a rule: the write path returns a log position, and their client can either wait until the replica has replayed past it or route that one read to the primary. What I would do differently: I would have published the lag metric before the incident. We knew the number internally and treated it as an implementation detail, and by keeping it private we made it impossible for a competent team to build correctly against us.

(d) Follow-up drill chain

Why not just turn on hot_standby_feedback and be done?

Because it moves the pain to the primary and it is a bad trade in exactly this scenario. With feedback on, the standby's long query pins rows on the primary so they cannot be vacuumed, which produces bloat and, if the query is long enough, contributes to the transaction-id age problem in story 06. That is a fine trade when the standby's queries are short and cancellations are painful; it is a terrible one when the standby runs four-hour analytical jobs, because you are letting a reporting query degrade the write path of the whole system. The general rule I apply: keep the primary's health independent of what anyone does on a replica, and give long analytical work its own replica where the answer to "what if it lags" is "nobody cares".

The consuming team says "just give us access to the primary". What do you say?

No, and here is what you get instead — because the answer has to come with an alternative or it is just a gate. Their real need was two things: reconciliation reads that are internally consistent, and confidence that a specific write is visible. The first is served better by an as-of read against a replica than by "now" against a primary, because a consistent point in time is exactly what a reconciliation needs. The second is the log-position mechanism. Primary access solves neither problem well and creates a new one: their analytical scans on our write path, which is the incident in story 20. If they had a genuine need that only the primary could serve, I would rather discover that in the conversation than refuse on principle — but I have not yet met one that survived the question "what consistency property do you actually require?"

At what scale does the log-position technique break down?

It works well within one database and one replication topology and it becomes awkward the moment the read path spans systems — a search index, a cache, a downstream service — because there is no shared position to wait on. At that point the honest answer is that you are building a distributed system and the mechanism becomes per-consumer: a version or sequence number carried in the event, an idempotent consumer that can tell whether it has seen the update, or explicit staleness surfaced in the user interface. It also breaks down when the wait would be long: waiting up to five seconds for a replica is acceptable inside a request, waiting for a nightly pipeline is not, and at that point the interface has to change from "read after write" to "subscribe to the change".

How did you avoid this becoming a blame fight?

By opening with the half that was ours, in writing, before anyone asked. The undocumented behaviour was our failure and saying so first changed the conversation from defence to design; it also made it much easier to say the harder thing, which is that their four-hour query on a shared replica was the mechanical cause and had to move. I also insisted the output be a document both teams signed rather than a ticket that closed, because the failure mode of these conversations is that they resolve socially and the next person inherits the same implicit assumption. Six months later a new engineer on their team asked a question and got pointed at the contract, which is the only real proof it worked.

Same situation on SQL Server availability groups — what changes?

The vocabulary and one significant behaviour. Lag is visible as log send queue and redo queue rather than as a replay timestamp, and the failure I would look for first is the redo thread being blocked by a long-running read on the readable secondary, which produces a growing redo queue and therefore staleness that recovers suddenly when the query ends. Synchronous-commit replicas change the trade entirely: there the cost of a slow replica is paid by the primary's commit latency rather than by staleness, so "the replica is behind" becomes "writes got slower", which is a different incident with a different urgency. Read-only routing gives me the same isolation move as a dedicated PostgreSQL replica, and the read-your-writes mechanism is analogous but coarser, since you are reasoning about commit LSNs and configured read intent rather than a value you can wait on as directly.

17The DELETE that ran without its WHERE

Staff Data-loss scare / recovery

(a) Worked example EXAMPLE — replace with your own

16:40 on a Thursday. An engineer running a cleanup script against production selected the statement in their editor, missed the last line, and executed DELETE FROM customer_notes without its WHERE. 1.4 million rows, committed, because the tool was in autocommit. They told the channel within about ninety seconds, which is the single most important fact in this story and the thing I would want any candidate to emphasise: the culture that produced a fast confession is worth more than any technical control, and I have seen the alternative — an hour of quiet attempts to fix it — turn a recoverable incident into an unrecoverable one.

The recovery decision came first and it is the one people get wrong. The instinct is to restore the database to a point in time before the mistake. That is almost always the wrong move on a live system, because you would also discard every legitimate transaction from the last forty minutes across every other table. What you want is a side restore: recover a copy to the moment before the delete, extract the missing rows, and merge them back into the live database. On PostgreSQL that is a base backup plus WAL replay with recovery_target_time — or better recovery_target_lsn if you can identify the transaction, because a timestamp is ambiguous and an LSN is not. On SQL Server it is a restore chain with STOPAT, and if you have the exact log record you can use STOPBEFOREMARK with the transaction's log sequence number, which you can locate in the log records. Either way the restore goes to a spare instance, never over the top of production.

Ours took just under six hours, against a stated recovery time objective of one hour, and that gap was the real finding of the incident. The objective had been written down years earlier and never tested at the current data size: the restore itself was 90 minutes, and the other four and a half hours were locating the right backup, provisioning capacity, replaying WAL, and — the part nobody had costed — reconciling. The merge back was not a straight insert, because forty minutes of live traffic had created a few hundred rows in the same table with overlapping identifiers, so we had to reconcile row by row on a natural key. Afterwards we changed five things: quarterly restore drills with the actual duration published, production write access removed in favour of reviewed and logged scripts, a session default that starts a transaction so the engineer's mistake needs an explicit COMMIT, delete-guard tooling that refuses an unqualified DELETE or UPDATE in an interactive session, and — the one I would fight for hardest — an explicit rule that nobody debugs a data-loss incident alone. What I would do differently: I would not have let the engineer drive the recovery. They wanted to, they felt responsible, and they were the least suited to it in that moment; I should have put them on documenting the timeline instead, which is useful work that does not require a steady hand.

(d) Follow-up drill chain

Why not restore the database to the moment before the delete?

Because the delete was not the only thing that happened in those forty minutes. Restoring in place rolls the entire database back, discarding every legitimate transaction from every other user and table since the target point — you would fix one table by losing orders, payments and audit records. It also takes the whole system down for the duration of the restore, converting a one-table problem into a full outage. The only situations where I would restore in place are when the damage is genuinely global (a bad migration that corrupted everything) or when the system was idle apart from the mistake. Otherwise: restore a copy, extract, merge, and accept the reconciliation work as the price of not losing anyone else's data.

Your recovery time objective was one hour and it took six. What do you tell the business?

The truth, with the decomposition, because "we missed it by five hours" is not actionable and "90 minutes of restore, 45 minutes of provisioning, two hours locating backups and replaying, 90 minutes reconciling" is. Then I give them the choice in their terms: getting to one hour means a warm standby that can be promoted, or more frequent backups with faster storage, or a delayed replica sitting deliberately an hour behind so that logical corruption can be read out of it without a restore at all — each with a price. What I refuse to do is quietly restate the objective to match what we achieved. An untested objective is a wish, and the value of this incident was converting a wish into a measured number the business can decide about.

At what data size does this recovery approach stop working?

When the restore exceeds the outage the business can tolerate, which for most teams arrives somewhere in the multi-terabyte range depending on storage. Past that the technique changes: cloud snapshot-based restores that are near-instant because storage is copy-on-write, a delayed replica you can query directly (PostgreSQL's recovery_min_apply_delay is the cheapest insurance against exactly this class of mistake and almost nobody uses it), or per-table backups so you can restore one table without the whole database. It also changes the design: at that scale I would want the important tables to be append-only with a history, or covered by SQL Server temporal tables, so that undoing a logical mistake is a query rather than a restore.

Removing interactive write access to production, with cleanup performed by reviewed, logged scripts run through the pipeline. We did not have it because it was inconvenient during incidents, which is the genuine trade — you want a human to be able to fix things at 03:00 — and because there is a real cost to the friction. The compromise I now favour: break-glass access that is time-limited, logged, alerts a channel, and starts every session inside a transaction with an unqualified-statement guard. That preserves the incident capability and removes the routine use, which is where the accidents happen. The second control, cheaper and almost as effective, is making the tooling default to a transaction so that a mistake needs an affirmative COMMIT.

By putting my own name on the incident record as the accountable person, saying in the channel within the first few minutes that the design let this happen, and running the review as a systems analysis rather than a narrative with a protagonist. Concretely that meant the write-up talked about "an interactive session with autocommit and no guard against unqualified statements" rather than about a person, and every action item was a control rather than a training item. I also asked them to present the postmortem, which sounds counterintuitive and is the single best thing you can do for someone in that position — it converts them from the person who broke it into the person who taught everyone how not to. They are still there, and they built the delete-guard tooling.

Principal Introducing a new tool

The ask was semantic search over about 8 million support documents, and the proposal on the table was a dedicated vector database. It was a reasonable proposal and I did not dismiss it; what I refused to accept was that it was the default. Adding a datastore is not a feature decision, it is an operational commitment: a second consistency problem (the documents live in the relational database, the embeddings would live elsewhere, and now they can disagree), a second backup and restore story, a second thing to be woken up for, and a new failure mode where search returns results for documents that were deleted last week.

So I ran an evaluation with a written decision rule agreed in advance: we keep the vectors in the primary database unless we cannot hit p95 under 150 ms with recall@10 above 0.95 at 8 million vectors and a projected 25 million. On the PostgreSQL side that is pgvector with an HNSW index; on the SQL Server side, SQL Server 2025's native VECTOR type with a DiskANN-backed vector index — and there is an important currency detail to get right in an interview: the VECTOR type itself with VECTOR_DISTANCE is generally available, while CREATE VECTOR INDEX, VECTOR_SEARCH and the half-precision base type are preview features that require ALTER DATABASE SCOPED CONFIGURATION SET PREVIEW_FEATURES = ON. That distinction changes the recommendation materially: exact search is production-ready, approximate index-backed search is something you adopt with your eyes open. The measurement harness mattered more than either product: 500 real queries with human-labelled relevant documents, exact brute-force search as the ground truth, and recall measured against it — because an approximate index that is fast and wrong is easy to build and easy to ship by accident.

We hit 118 ms at p95 with recall@10 of 0.96 on PostgreSQL with HNSW at m = 16, ef_construction = 64 and ef_search = 100, and the vectors stayed in the primary database. The wins were the ones I had predicted and one I had not: a single transaction writes the document and its embedding so they cannot diverge, deletes are automatic, and filtered search — "semantic match, but only within this customer's documents and only from the last year" — is a plain WHERE clause rather than a metadata-filtering feature of a separate system, which turned out to be the requirement that mattered most in practice. The costs were real too: index build on 8 million vectors needed a large maintenance_work_mem and took hours, the index is memory-hungry, and re-embedding when the model changes is a bulk operation that has to be planned. What I would do differently: I would have written the exit criteria for the decision as well as the entry criteria. We agreed what would keep vectors in Postgres; we never agreed what would make us move them out later, and that conversation had to be had again from scratch eighteen months on.

(d) Follow-up drill chain

How did you know your approximate search was actually good?

Ground truth from exact search. For a fixed set of 500 real queries I computed the true top-10 by brute-force distance over the whole corpus — slow, but you only need it once — and then measured what fraction of that true top-10 the index returned, which is recall@10. Without that number, tuning HNSW is guesswork: raising ef_search improves recall and costs latency, and you cannot trade along a curve you have not measured. I also checked recall on the filtered queries separately, because that is where approximate indexes degrade worst — a highly selective filter combined with an approximate index can return very few results, or none, if the engine filters after retrieving neighbours rather than searching within the filter. At what scale does keeping vectors in the primary database stop being right?

Three signals, any one of which moves me. Memory: HNSW wants its graph in memory, and when the vector index starts competing with the OLTP working set for the buffer pool, everything else slows down and you have imported a search problem into your transaction path. Build cost: re-embedding after a model change means rebuilding the index, and when that takes long enough to need its own capacity plan, it wants its own home. And scale itself — somewhere around the hundreds of millions of vectors, the specialist stores' index structures and quantisation options genuinely outperform. Before moving out entirely, though, the intermediate step is usually better: put the vectors on a replica or a second instance of the same engine, which isolates the load while keeping one operational skill set.

You relied on a preview feature in one engine. Is that acceptable?

Only with the trade stated in writing and a fallback that works. Preview means the surface can change, support is limited, and an upgrade can alter behaviour — so my rule is that a preview feature may be adopted when the fallback is a supported path we have actually tested, not a theoretical one. Here that fallback is exact search with VECTOR_DISTANCE, which is generally available and is fine at smaller corpus sizes or with a selective filter, so a forced retreat degrades latency rather than breaking the feature. What I will not do is let a preview feature become load-bearing for a customer commitment without the business knowing that is what happened, because the conversation after an upgrade changes behaviour is much worse than the conversation before adoption.

The team wanted the dedicated vector database. How did you carry them?

By making the decision rule theirs to challenge before the evaluation, not after. I also gave them a real concession: if the projected 25-million-vector scale had missed the thresholds, we would have moved, and I committed to re-running the harness at that scale rather than re-litigating. The thing that actually settled it was not my argument, it was the filtered-search requirement: once we measured how much of the workload was "semantic and tenant and date range", keeping vectors next to the metadata stopped being a compromise and started being the better design.

What is the operational cost of a second datastore, concretely?

Six things I count every time: a backup and restore procedure that has been tested, a monitoring and alerting integration, an upgrade calendar, an on-call skill set with a bus factor above one, a consistency mechanism between it and the source of truth including a way to detect and repair drift, and an access-control model that satisfies whatever the data requires. Each of those is small; together they are typically a quarter of an engineer indefinitely, and that is the number I put in the comparison. It is also the number that gets omitted from most adoption proposals, which is why the honest version of this argument tends to win — not because a second datastore is wrong, but because the comparison is usually made against a zero that is not a zero.

19Migrations that stopped taking the site down

Staff CI / test / reliability improvement

(a) Worked example EXAMPLE — replace with your own

Three deployments in one quarter caused customer-visible outages, all from schema migrations, all on tables that were fine in staging. The pattern was identical every time: a migration asked for a lock, could not get it immediately because a long-running query held the table, and then — the part people do not know until it bites them — every subsequent query queued behind the waiting migration. That is the detail worth being able to explain: a pending exclusive lock request in PostgreSQL blocks the readers arriving after it, so a migration that is merely waiting takes the table down as thoroughly as one that is running. Staging never reproduced it because staging had no long-running queries and a thousandth of the data.

The fix was a set of rules with automation behind each one, because rules without automation last about six weeks. First, every migration sets lock_timeout and retries: if it cannot get the lock in three seconds, it fails fast, releases the queue, and tries again — a failed deployment is vastly cheaper than a locked table. Second, expand/contract for anything that changes shape: add the new column, backfill in batches, dual-write, switch reads, then drop the old column in a later release, so no deployment requires the code and the schema to change at the same instant. Third, indexes are built without blocking writes — CREATE INDEX CONCURRENTLY on PostgreSQL, WITH (ONLINE = ON, RESUMABLE = ON) on SQL Server Enterprise — and the trade-offs are stated in the migration's comment, because a concurrent build can fail and leave an invalid index that needs cleaning up, and people who have not met that once will not check for it. Fourth, a CI job runs every migration against a restored production-sized copy and fails the build if it takes longer than 30 seconds or acquires an exclusive lock on a table above a size threshold.

That last job is the one that changed behaviour, and it caught things nobody expected: an ALTER TABLE that would have rewritten a 400-million-row table because of a subtle type change, and a foreign key addition that would have taken an exclusive lock on both tables for eleven minutes. A migration linter runs alongside it and catches the well-known hazards statically — adding a column with a volatile default, changing a column type, adding NOT NULL directly instead of via a validated check constraint. The result over the following year: zero migration-caused outages, and, less obviously but more valuably, migrations stopped being scary, so people stopped batching six of them into one risky quarterly release. What I would do differently: I introduced the CI gate before the tooling that made compliance easy, so for the first month the gate was something people worked around. Ship the paved road first, then the gate — in the other order, the gate teaches people that the rule is the enemy.

-- PostgreSQL: the two lines that prevent a waiting migration from taking the site down.
SET lock_timeout = '3s';          -- fail fast; a failed deploy beats a locked table
SET statement_timeout = '30s';
ALTER TABLE orders ADD COLUMN priority smallint;   -- metadata-only; a non-volatile DEFAULT is fine too

-- NOT NULL without a long exclusive lock: validate first, then promote.
ALTER TABLE orders ADD CONSTRAINT orders_priority_nn CHECK (priority IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_priority_nn;   -- weaker lock, scans concurrently

-- Indexes without blocking writes. Note: this cannot run inside a transaction block, and a
-- failure leaves an INVALID index behind that you must drop and rebuild.
CREATE INDEX CONCURRENTLY orders_priority_idx ON orders (priority);
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;   -- check after every failure

ALTER TABLE order_lines ADD CONSTRAINT fk_order FOREIGN KEY (order_id)
  REFERENCES orders(order_id) NOT VALID;
ALTER TABLE order_lines VALIDATE CONSTRAINT fk_order;

ALTER INDEX IX_Orders_PlacedAt ON dbo.Orders

(d) Follow-up drill chain

Why does a waiting migration take the site down?

Because lock requests queue in order. When a migration asks for an exclusive lock on a table and cannot get it — some long-running query holds a weaker lock — the request waits, and every subsequent query needing any conflicting lock queues behind it rather than jumping ahead of it. So a migration that would have taken 5 milliseconds to execute can block all reads and writes for as long as the original blocker runs. That is why lock_timeout is the single highest-value line in a migration script: it converts an unbounded outage into a failed deployment. The same physics applies on SQL Server, which is what WAIT_AT_LOW_PRIORITY is for — it lets the schema-modification lock wait without blocking the queue behind it, and then abort itself or its blockers according to what you specify.

Expand/contract needs a deployment to be backward compatible. What does that cost?

Two releases instead of one for every shape change, and a window where the code must handle both shapes, which is genuinely more work and occasionally produces a bug in the compatibility path itself. It also requires discipline about the contract phase: the number of systems carrying a "drop this column later" comment from three years ago is not small, and unfinished contractions accumulate as a specific kind of debt. I mitigate that with a ticket created automatically at expand time with a due date, and by treating the contraction as part of the original work rather than as a follow-up. The cost is real and I still take it every time, because the alternative is coupling a schema change to a code deployment at the same instant, and that coupling is what makes rollbacks impossible.

At what table size do these rules start mattering?

The lock-queue rule matters at any size, because it depends on concurrency rather than on rows — a small, extremely hot table is more dangerous than a large, quiet one, which is the intuition people get backwards. The rewrite rules start mattering when a full table scan exceeds your outage tolerance, which for most systems is somewhere in the tens of millions of rows and depends entirely on storage speed. My practical stance is to apply the rules universally, because the cost of doing so is a few extra lines in a migration and the cost of maintaining a size-based exception is that someone applies the wrong rule to a table that grew. Uniform rules that are cheap to follow beat conditional rules that require judgment under deployment pressure.

How did you get other teams to adopt this?

By making the compliant path shorter than the non-compliant one before I asked anyone for anything. That meant migration templates with the timeouts and retries already in them, a linter with a link to a one-paragraph explanation per rule, and the CI job that runs against a restored copy — which teams wanted anyway, because it also catches migrations that simply fail on production data. I did the first three teams' conversions myself, which is the part that buys credibility, and only then made the gate mandatory. The mistake I made and would not repeat was making the gate mandatory first: for a month the rule was an obstacle rather than a tool, and I spent political capital I did not need to spend.

What is different about this on SQL Server?

The mechanisms are edition-dependent, which changes the plan. Online index operations and resumable rebuilds are Enterprise features, so on Standard edition a large index rebuild is an offline operation and the strategy shifts to partition-level maintenance, building alongside and switching, or an accepted maintenance window — and it is worth knowing which edition you are on before designing the process. Adding a nullable column, or a NOT NULL column with a constant default, has been metadata-only since 2012 Enterprise, so a lot of the PostgreSQL rewrite anxiety does not apply; the analogous danger is the schema-modification lock and the queue behind it, which WAIT_AT_LOW_PRIORITY addresses directly. The universal parts transfer exactly: expand/contract, never rename in place, never couple a shape change to a code deploy, and test against production-sized data.

That conversation took forty minutes and changed the requirement completely. Of the twenty tiles, sixteen were daily context that nobody would act on within an hour. Four were genuinely operational — orders failing, payment provider errors, queue depth, active incidents — and for those, "live" meant "I want to know within a minute", not five seconds. So the real requirement was four metrics at up to sixty seconds of staleness, and sixteen at daily granularity, which is a completely different engineering problem from twenty live tiles on the primary. I also had a concrete cost to put on the original ask, because we had run the experiment: a similar dashboard six months earlier had run twenty aggregate scans a minute against the orders table, evicting the OLTP working set from the buffer pool and raising checkout p95 by about 40 percent while it was open. That is the argument that lands — not "it will be slow", but "here is the measured cost to checkout, in milliseconds, while your dashboard is open".

What we built: the four operational metrics came from counters the services already emitted, in the monitoring system, with sub-minute latency and no database queries at all; the sixteen daily tiles came from a materialised view refreshed every fifteen minutes on a read replica. On the SQL Server side of the estate the same request had a third option worth knowing about, because it is the genuine middle path — a nonclustered columnstore index on the OLTP table, which gives real-time operational analytics against live data with a batch-mode plan, at the cost of write overhead and delta rowgroup management. I offered it, we measured it, and for this workload the replica was cheaper. The director got their dashboard two weeks before the board meeting and, as far as they were concerned, they got what they asked for. What I would do differently: I would have brought the earlier incident's measurement to the first meeting. I spent the first conversation arguing from principle and only produced the number in the second, and the number is what actually moved the conversation.

What the interviewer is really probing. Whether you can say no without becoming an obstacle, by finding the need under the request. Task

Action

(c) Recall prompts

When did you push back on someone more senior, and how did it go?

Hint: a deadline, an architecture direction, a vendor choice, direct production access, a feature with an unacceptable data cost. The good answers include the alternative you offered and what you conceded.

When has a stakeholder asked for a solution rather than a problem?

Hint: "we need a cache", "put it in Elasticsearch", "can we get direct database access", "it has to be real time". Say what the underlying need turned out to be and how you found it.

What is the measured cost of analytics on a transactional system you know?

Hint: buffer-pool eviction, plan cache pollution, a long transaction blocking cleanup, replication lag, CPU during business hours. If you have a before-and-after number from an actual incident, that number is one of the most useful things you can carry into an interview.

When did you say yes to something you thought was wrong, and what happened?

Hint: the calibration answer. Sometimes yes is correct — the cost was lower than you feared, or the relationship mattered more than the technical purity. What did you learn about when to spend the capital?

(d) Follow-up drill chain

Why not just give them a read replica and be done?

It was on the table and it was the right answer for sixteen of the twenty tiles, which is where it ended up. It was the wrong answer for the four operational ones, for two reasons: replica lag makes an incident dashboard misleading exactly when it matters most (during an incident, when lag tends to be worst), and those four numbers already existed as application counters, so querying the database for them was doing expensive work to recompute something we were already emitting for free. The general principle: operational signals should come from the application's own telemetry, and analytical aggregates should come from a replica or an analytics store. A read replica is not a universal answer, it is one of three, and knowing which question each answers is the actual skill.

What if they had insisted on the primary anyway?

Then I would write down the risk in one paragraph — the measured latency impact on checkout, the conditions under which it degrades further — name the person accepting it, and implement it with the strongest guard rails I can: a resource governor pool or a statement timeout so the dashboard's queries cannot consume unbounded resources, a separate login so I can throttle or kill it independently, and an alert that fires when checkout latency crosses a threshold while the dashboard is active. I would not sulk, and I would not sabotage it with deliberate slowness. My accountability is the quality of the input to the decision, not ownership of the decision; what I insist on is that the acceptance is explicit and recorded, because the alternative is that six months later the incident is attributed to the database team.

At what point does the materialised view stop being enough?

When the refresh cost approaches the query cost it saves, which happens when the underlying data is large and the view is refreshed often — a full refresh scans everything, so a fifteen-minute refresh over a 30-day window is real work every fifteen minutes. Then the options are incremental maintenance (roll up into a summary table by appending only the new window rather than recomputing), moving the aggregation into the ingestion path so the numbers are maintained as events arrive, or accepting a longer refresh interval. It also stops being enough when the questions stop being fixed: a materialised view answers the queries you anticipated, and the moment analysts want to slice arbitrarily, you need a real analytical store rather than a growing collection of views nobody can retire.

How did you keep the relationship good after saying no?

By never actually saying no to the outcome, only to the mechanism, and by being visibly on their side about the deadline — I offered a date before they had to ask for one, and I beat it. I also gave them something they had not asked for and valued: the four operational tiles updated in seconds rather than the five they had requested, because coming from counters they were both cheaper and fresher. The other thing I did deliberately was to explain the trade-off once, in their language, and then stop; engineers frequently keep justifying after the decision is made, which reads as either insecurity or condescension. Six months later that director came to me first with the next data request, phrased as a question rather than a requirement, which is the actual measure of whether this went well.

Same request, but the company has no replica and no monitoring stack. Now what?

Then the honest answer is that the dashboard is the cheap part and the platform gap is the expensive part, and I would say so rather than heroically building a fragile thing. In the short term I would serve the four operational numbers from the application — a counter and an endpoint is a day of work and touches no database — and the sixteen daily tiles from a scheduled job writing into a small summary table, running once an hour at a quiet time, which is crude and safe. Then I would use the request as the funding argument for the replica, because a named stakeholder with a board deadline is the best sponsor a piece of platform work will ever have. Turning someone's request into the business case for the thing you needed anyway is one of the more useful moves available at this level, and it is entirely honest as long as the short-term answer genuinely serves them.

21The big behavioural Q&A

22 cross-cutting prompts not tied to one story

These are the prompts that do not map to a single incident — where the interviewer is sampling your values, your judgment and your self-knowledge rather than your diagnosis. Each answer below names the prepared story to reach for and what the question is actually measuring. Do not memorise wording; memorise which story you are deploying and what it has to demonstrate. Where two stories are named, the first is the safer choice and the second is the one that shows more range.

Failure & ownership

Tell me about a time you caused a production problem.

Deploy: story 16 (you approved the sharding project on an untested premise) for a judgment failure, or the six-week-old forced plan in story 01 for an operational one. They want: a real failure with your name on it, told without either self-flagellation or diffusion of blame, and a change of method rather than of intention. The disqualifier is a failure that is secretly a strength ("I care too much about data quality"). Say what it cost in concrete terms — money, time, an engineer's morale — then say what you now do differently at the decision point, not at the effort level.

Tell me about a technical decision you got wrong.

Deploy: story 16, or the partition granularity in story 09. They want: that you can distinguish a bad decision from a bad outcome. Explain what you knew at the time, why the decision was reasonable on that information, and the specific signal you now go looking for earlier. The strongest version admits the trade-off was never written down where anyone else could challenge it.

Tell me about an incident where you were the one in command.

Deploy: story 02 (deadlock storm) for lock-and-concurrency command, story 17 (the DELETE) for a data-loss incident with a human at the centre. They want: ordered actions with the reasoning for the order, containment before understanding, explicit statements of uncertainty, a communication cadence, and a postmortem that changed something structural. Mention who you woke up and why — solo heroics read badly at lead level.

When did you have to tell a customer or an executive that something was wrong?

Deploy: story 10 (the cross-tenant leak) or story 17 (data loss). They want: composure, precision about what you did and did not know, and no over-reassurance. Have the shape ready: here is what we know, here is what we do not yet know, here is when you will hear from me next — plus evidence you kept that appointment.

What did you miss that someone else caught?

Deploy: story 10 (a support engineer's one-off report turned out to be a real isolation bug) or story 08 (finance noticed the reconciliation drift before engineering did). They want: that you treat other people's findings as information rather than as a threat, and that you name the person. Then describe the mechanism you added so that class is caught systematically rather than by attentiveness.

Conflict & influence

Tell me about a technical disagreement with a colleague.

Deploy: story 07 (random UUIDs as the clustering key). They want: whether you can state the other position at its strongest — his reasons for client-side identifiers were good — and whether you win in a way that leaves the relationship usable. Include the part where your approach was socially wrong (leading with a critique instead of an experiment) and the landing that gave him what he actually cared about.

Tell me about pushing back on someone more senior.

Deploy: story 20 (the live dashboard on the primary). They want: that you can decline a mechanism without declining the outcome, that you reframe to the underlying need, and that you bring a measurement rather than a principle. Have the boundary ready too: the point at which you stop persuading, write the risk down, and name who accepted it.

How do you get another team to change something that only benefits you?

Deploy: story 19 (migration rules adopted across teams) or story 15 (the staleness contract). They want: influence without authority — doing the first conversions yourself, shipping the paved road before the gate, and framing the benefit in their currency. "I escalated to their manager" as a primary tool is a weak answer.

Tell me about a time you were wrong in a technical argument.

Deploy: the load test in story 16 that contradicted your own approved plan, or a case where a colleague's benchmark beat your intuition. They want: calibration. Engineers who have never been wrong have usually never been measured. Describe how you noticed and what changed in how you assess claims — for me, requiring a demonstration before approving anything justified by a limit.

How do you handle a team that keeps ignoring your recommendations?

Deploy: story 12 (index-by-guessing) and story 19 (the gate people worked around). They want: the instinct to ask why the recommendation is being ignored rather than to escalate compliance. The strong answer treats adoption as a product problem — effort, feedback speed, signal quality — and includes an example of you removing friction rather than adding enforcement.

Leadership & mentoring

How have you raised the capability of a team, not just fixed a system?

Deploy: story 12 (teaching plans) plus story 19 (defaults and templates that make the safe path easy). They want: both halves — people and mechanisms — and evidence the change outlived your attention. The sentence that lands: someone else taught it from your write-up, or the safe pattern arrived in a pull request without anyone asking.

Tell me about someone you mentored.

Deploy: story 12, specifically the engineer who diagnosed a regression alone and then taught two others. They want: a specific person, a specific capability, and something they did later without you. Narrate what they became able to do, not what you explained, and include what it cost you that quarter.

How do you decide what the team works on next quarter?

Deploy: story 14 (itemise before optimising) and story 16 (stop conditions). They want: a method rather than a wish list — decompose the problem, rank by expected value per unit of effort, prefer removing a class of work over doing it faster, and write down what you are deliberately not doing.

How do you build a culture where people admit mistakes quickly?

Deploy: story 17 (the ninety-second confession) and story 06 (making "I do not understand this warning" a legitimate escalation). They want: concrete mechanisms, not values statements — who owns the incident record, what happened to the person, whether the postmortem named a human or a control, and whether you have modelled it yourself.

You are the only person who can do something. How do you fix that?

Deploy: story 12. They want: that you consider a bus factor of one a defect you own rather than job security. Name what you are currently the bottleneck for, and the plan: sessions against real work, written material, then defaults and tooling that make the skill less necessary.

Ambiguity, prioritisation & trade-offs

How do you decide between two databases, or two designs, when both would work?

Deploy: story 03 (SQL Server versus PostgreSQL) and story 18 (vectors in the primary versus a dedicated store). They want: criteria written before the evaluation, an operational cost counted honestly, a boundary condition that makes the decision survivable, and an answer to "what would have changed your mind".

Tell me about working with requirements that kept changing.

Deploy: story 20 (twenty live tiles that were really four operational metrics) and story 04 (an estimate that could not hold). They want: that you find the invariant under the churn by asking what decision the requirement supports — and that you re-forecast in public rather than absorbing the slip silently.

How do you balance shipping speed against doing it properly?

Deploy: story 01 (a forced plan as a deliberate tourniquet with an expiry) and story 11 (a strangler over fourteen months). They want: that you treat it as a real trade with owners rather than a moral position. Concrete tools: reversible mitigations with tickets attached, ratcheting standards on new code, expand/contract, and a stop condition for the cleanup.

How do you prioritise performance work?

Deploy: story 14 (top queries by total time, not average) and story 09 (change the operation, do not optimise it). They want: a measurement-first ranking and an instinct for eliminating work rather than accelerating it. The detail that signals experience: total time over average time, because the cheap query executed ten million times is the real cost.

What do you do when there is no clear owner for a risk?

Deploy: story 15 (the undocumented replica contract) or story 14 (the replica nobody owned). They want: that you take temporary ownership to stop the drift, then engineer a permanent owner — and that you can tell the difference between a gap you should fill and one you should escalate.

Values, motivation & currency

How do you keep current with these engines?

Deploy: be specific and dated. SQL Server 2025 went GA on 18 November 2025 with a native json type, native regex, optimized locking (which needs accelerated database recovery), and a VECTOR type whose approximate index is still a preview feature; SQL Server 2016 left extended support on 14 July 2026. PostgreSQL 18 brought asynchronous I/O, uuidv7(), B-tree skip scan, OAuth authentication and statistics carried through pg_upgrade; 18.6 shipped on 13 August 2026, PostgreSQL 19 is in beta with sequence replication and FOR PORTION OF, and PostgreSQL 14 reaches end of life on 12 November 2026. They want: primary sources, a habit rather than a newsletter list, and one thing you changed at work because of something you read.

What is your biggest weakness with databases?

Deploy: something true and bounded. For many leads it is over-indexing on the engine they know best and reaching for its mental model on the other one — assuming lock escalation exists in PostgreSQL, or looking for a missing-index warning that SQL Server provides and PostgreSQL does not. They want: self-knowledge plus a compensating habit, such as deliberately asking "what is the equivalent failure mode on the other engine?" in every design review because it is not your instinct.

The two questions that decide these interviews. "What did that cost you?" and "how do you know?". Every story in this bank should have an answer to both before you walk in: the thing that got worse when you fixed the thing that was wrong, and the measurement that tells you the fix worked. Candidates who can answer those two questions about any story they tell are read as senior regardless of the story's scale.

22Night-before cheat sheet

10 speakable rules read this last

Ten sentences to read the night before, and to say out loud once each so they are in your mouth rather than on the page.

  1. Open with the situation in one line, then stop. "A twelve-billion-row events table with a nightly delete that had stopped finishing in its window" buys you thirty seconds of full attention; three minutes of company background spends it.
  2. Name the first thing you measured, every time. Query Store's regressed queries, pg_stat_statements by total time, wait statistics, the deadlock graph, pool utilisation. Database stories live or die on whether you diagnosed or guessed, and the measurement is the proof.
  3. Quantify both ends. Four hours to 200 milliseconds; p99 180 ms to 26 seconds; 1,900 deadlocks an hour against a baseline of five a day; 61 percent off the bill. Then quantify what got worse — tempdb, bloat, an extra index, two systems live for a quarter.
  4. Say which engine, and say it early. "On SQL Server this is lock escalation; on PostgreSQL there is no escalation and the same batch shows up as held-back vacuum" is the single sentence that most reliably marks you as someone who has run both rather than read about both.
  5. Separate "I" from "we" deliberately and out loud. Say what you personally decided, wrote or argued; hand the rest to the team by name. Interviewers are calibrated for inflation on exactly this and will drill it.
  6. Own the failure in the same breath as the fix. The forced plan left in for six weeks, the project you approved without a load test, the estimate you defended for too long, the engineer you let drive their own recovery. A database story with no mistake in it sounds rehearsed, because real operations is full of them.
  7. Name the trade-off, never just the control. Every answer should contain a sentence shaped like "that bought us X and cost us Y": RCSI costs tempdb, partitioning costs a widened unique key, a second engine costs an on-call skill set, a timeout costs ambiguous writes. Controls without costs signal someone who has read about this rather than shipped it.
  8. Prefer structural fixes and say why. Replace the operation rather than optimising it — detach a partition instead of deleting rows, move the external call out of the connection scope instead of enlarging the pool, put isolation in the database instead of in every handler.
  9. Have one very recent, checkable fact ready and use it once. SQL Server 2016 out of support on 14 July 2026; PostgreSQL 14 end of life on 12 November 2026; PostgreSQL 18 carrying planner statistics through pg_upgrade; SQL Server 2025's vector index still being a preview feature. One fact, dated correctly, deployed once — not a recital.
  10. Finish every story with what you would do differently, and make it a change of method. Not "I would be more careful" but "I now require a measured demonstration of the limit before approving a scaling project", "I now put an expiry date on every mitigation", "I now ship the paved road before the gate".

The last check before you walk in. Pick five stories from the coverage table that are genuinely yours, and for each be able to say in ten seconds: the situation, the number, the trade-off, and the thing you would do differently. Five stories you can tell cold beat twenty you half-remember, and the drill chains are what let you improvise the sixth. If you only have time for two, make them an incident you commanded and a decision you got wrong — those two carry the most weight at lead level, and most candidates prepare neither.
