SQL (SQL Server & PostgreSQL)

study · PostgreSQL 18.6 (released 2026-08-13) · SQL Server 2025 / 17.x CU8 (GA 2025-11-18)

This guide covers the two engines side by side and calls out every place they diverge; where a statement is unqualified it holds for both. Assumption, since the topic names products rather than editions: “SQL Server” means the Microsoft box product, currently SQL Server 2025 (17.x), GA on 2025-11-18 and on CU8 (17.0.4075.5) as of August 2026, with Azure SQL Database noted where its defaults differ; “PostgreSQL” means community PostgreSQL, currently 18.6 (2026-08-13), with 19 Beta 3 in the field and GA expected in late September 2026. The two engines have converged hard in the last two releases and diverged in one big way: PostgreSQL 18 rewrote the read path around an asynchronous I/O subsystem and taught B-trees to skip-scan, while SQL Server 2025 brought optimized locking, optional parameter plan optimization, a native json type, regex functions and a native vector type into the engine. The interview-relevant fault line is still concurrency: PostgreSQL is MVCC-always and pays for it in vacuum; SQL Server is lock-based by default and pays for it in blocking unless you turn on RCSI. Everything below is written for a lead/principal conversation — trade-offs, incident decisions and code-review judgment — with the fundamentals present but treated as things you verify in ten seconds, not learn here.

01 Two engines, one SQL: architecture and the 2026 landscape

Both products speak roughly the same declarative language and then implement it with almost opposite engineering instincts. Hold this picture and most of the differences you will be asked about fall out of it on their own.

SQL Server is one process with its own operating system inside it. A single sqlservr process hosts SQLOS: a user-mode scheduler per logical CPU, cooperative (non-preemptive) scheduling of workers, its own memory manager, its own I/O completion handling. Sessions are tasks bound to workers, not OS processes, so a connection is cheap — a few tens of KB — and ten thousand of them is a configuration question, not an architecture crisis. The price is that everything shares one address space and one buffer pool, and one runaway query can starve the scheduler for everyone (SOS_SCHEDULER_YIELD, THREADPOOL). Since 2017 the same binaries run on Linux through SQLPAL, a host-extension layer that maps Windows kernel calls onto Linux — which is why SQL Server on Linux behaves identically rather than being a port.

PostgreSQL is a family of processes coordinated through shared memory. The postmaster forks a dedicated backend process per connection; alongside them run the checkpointer, background writer, WAL writer, autovacuum launcher and its workers, logical replication launcher, and — new in 18 — I/O workers. Shared memory holds shared_buffers, the lock table, and WAL buffers. This gives you brutal isolation (a crashed backend takes down only itself, and the postmaster restarts the cluster to be safe) and an extension model nothing else matches: PostGIS, pgvector, Citus, TimescaleDB, pg_stat_statements all load into the server as first-class citizens. The price is that a connection costs a process — several MB of private memory plus a slot in every shared array — so past a few hundred you need PgBouncer or an equivalent pooler in front. That single fact drives more PostgreSQL production incidents than any other.

The version numbers you will actually be asked to reason about

Compatibility level is SQL Server's most misunderstood knob. Upgrading the instance to 2025 does not change a database's behaviour: ALTER DATABASE … SET COMPATIBILITY_LEVEL = 170 does, and it is what switches on the current cardinality estimator and most intelligent-query-processing features. The professional upgrade sequence is: restore onto the new engine at the old compat level, turn on Query Store, capture a baseline, raise the compat level, and use Query Store to find and force plans for the handful of queries that regress. PostgreSQL has no equivalent dial — a major upgrade is a real upgrade — which is why the PostgreSQL answer is "test on a copy, and keep the old cluster around until you are sure".

Interview trap

"PostgreSQL doesn't have an enterprise edition, so it's free." The licence is free; the operations are not. Nothing in core PostgreSQL does automatic failover — that is Patroni, repmgr, pg_auto_failover or CloudNativePG, all of which you own. There is no TDE in core, no built-in job scheduler (that is cron or pg_cron), no query hints, and no first-party equivalent of Query Store. The honest lead-level answer is: PostgreSQL trades licence cost for platform-engineering cost, and whether that is a win depends on whether you have a team that wants to own it. Say that, and then say which you would choose for the specific workload in the question.

Try it

  1. On a scratch PostgreSQL 18 instance, open 400 idle connections with a loop of psql sessions (or a tiny script) and watch RSS on the host plus SELECT count(*) FROM pg_stat_activity. Then put PgBouncer in transaction mode in front with default_pool_size = 20 and repeat.
  2. On SQL Server, run a deliberately parallel-heavy query while a second session runs a trivial SELECT 1 in a loop; watch sys.dm_os_wait_stats for SOS_SCHEDULER_YIELD and CXCONSUMER.
What you should see

PostgreSQL: roughly 5–10 MB of resident memory per idle backend plus a fixed shared cost, and connection setup latency in the low milliseconds because each one is a fork(). Behind PgBouncer the same 400 clients hold 20 server processes and host memory flattens; that is the entire argument for a pooler in one experiment. SQL Server: the trivial query keeps running with only scheduler-yield waits, because SQLOS is cooperatively multitasking thousands of tasks over a few dozen schedulers — connections are not the scaling limit there, memory grants and worker threads are.

Interview Q&A

Explain the process model difference and one production consequence of each.

SQL Server is a single multi-threaded process with its own user-mode scheduler, SQLOS; PostgreSQL forks a backend process per connection. The consequence on SQL Server is shared fate: one query with a huge memory grant can put every other session into RESOURCE_SEMAPHORE, and worker-thread exhaustion shows up as THREADPOOL waits that even block new logins — so you govern with MAXDOP, cost threshold and Resource Governor. The consequence on PostgreSQL is connection cost: each backend is a process with private memory, and work_mem is per sort/hash node per worker, so 500 connections running a three-way hash join can multiply a "safe" 64 MB setting into tens of gigabytes. That is why a pooler is not optional at scale, and why I would treat "we have 2,000 app connections straight to Postgres" as a P2 waiting to happen.

A team wants to move a large OLTP system from SQL Server to PostgreSQL to save licence cost. How do you frame the decision?

I would separate three costs: licence, migration and operations. Licence is real and easy to quantify — but SQL Server 2025 Standard now goes to 32 cores and 256 GB with Resource Governor included, so the first question is whether Enterprise is even needed any more. Migration cost is dominated by T-SQL surface area: stored-procedure volume, MERGE, temp tables, SQL Agent jobs, SSIS, linked servers, and the silent killer, case-insensitive collation — a case-sensitive Postgres will surface real data bugs on day one. Operations cost is the part teams underestimate: you now own failover, backups, connection pooling and extension lifecycle. My recommendation usually depends on whether the org already runs PostgreSQL somewhere; a first-and-only PostgreSQL estate to save licence fees is often a net loss for two years.

What is compatibility level and why does it matter during an upgrade?

It is a per-database setting that pins query-processing behaviour to a specific SQL Server generation — 160 for 2022, 170 for 2025. Moving the instance forward does not change it, so you can run the 2025 engine with 2016 query behaviour. That decoupling is the safe upgrade path: restore at the old level, enable Query Store to capture a baseline, then raise the level and compare. If a handful of queries regress you force the old plan from Query Store rather than rolling the whole database back. It also gates features — new cardinality-estimator behaviour and most IQP features only appear at recent levels — which is why "we upgraded but saw no improvement" almost always means nobody raised the compat level.

How does PostgreSQL's extension model change the architecture conversation?

It moves capability decisions from "which product" to "which extensions", which is powerful and dangerous in equal measure. pgvector turns Postgres into an adequate vector store, PostGIS into a serious GIS platform, Citus into a sharded cluster, TimescaleDB into a time-series database — without a second system to operate or a second copy of the data. The danger is lifecycle: extensions are C code in your server process, they pin you to versions, and managed providers only offer an allowlist, so an extension choice can quietly become a cloud-provider lock-in. My rule is that anything in the critical write path needs an owner, an upgrade plan and a "what if this extension is abandoned" answer before it ships.

What actually changed in PostgreSQL 18 that you would exploit?

Three things. Asynchronous I/O: io_method defaults to worker with only three I/O workers, and on modern NVMe hardware raising that — or moving to io_uring on Linux 5.1+ — meaningfully speeds up sequential scans, bitmap heap scans and vacuum, with pg_aios to observe it. B-tree skip scan: multi-column indexes are now usable when the leading column is unconstrained, which retires a pile of redundant indexes that existed purely to satisfy the old leading-column rule. And pg_upgrade now carries optimizer statistics across major versions, which removes the classic post-upgrade cliff where the first hour after cutover was slow because nobody had run ANALYZE yet. Extended statistics are still not carried across, so I would still script an ANALYZE for tables that have them.

And what would you exploit in SQL Server 2025?

Optimized locking first: it uses transaction-ID locking plus lock-after-qualification so a big update holds far fewer row locks, which removes lock escalation as a class of incident — but it wants Accelerated Database Recovery on and works best with RCSI, so it is a change you stage. Optional parameter plan optimization is the second: the WHERE (@p IS NULL OR col = @p) pattern that infests every "search screen" procedure has plagued plan quality for twenty years, and OPPO finally generates multiple plans for it instead of one bad compromise. Third, the native json type with JSON indexes, because until 2025 JSON in SQL Server was nvarchar(max) with functions bolted on, and everyone paid for parsing on every read.

How do you decide between SQL Server on Linux and on Windows?

Functionally they are the same engine via SQLPAL, so I decide on operations. Linux wins where the rest of the estate is Linux and containers: smaller images, no domain-join ritual, cheaper OS licensing, and 2025 adds tempdb on tmpfs plus a custom password policy that used to be Windows-only. Windows wins when you need Active Directory authentication without extra work, FCI with Windows Server Failover Clustering, Distributed Transaction Coordinator, FILESTREAM, or the SSIS/SSAS/Reporting stack. I would also weigh the team's muscle memory: a shop that has never debugged SQL Server on Linux will find its first SIGSEGV in a dump file a lonely experience.

Someone proposes standardising on one database engine across the company. Argue both sides.

For: operational leverage is real. One engine means one backup story, one HA runbook, one set of monitoring dashboards, one on-call skill set, one migration tool, one set of hard-won gotchas. Most estates are not big enough to justify deep expertise in two engines, and "polyglot persistence" often decays into "nobody is expert in anything". Against: standardisation applied retroactively means rewriting working systems for no user-visible benefit, and it locks you out of genuinely better fits — a heavy geospatial or vector workload really is better on PostgreSQL, a shop deep in .NET, SSIS and Power BI really is cheaper on SQL Server. My usual landing: standardise for new systems, grandfather existing ones, and set a bar ("a second engine needs a named owner and a documented reason") rather than a ban.

What does the 2026 support calendar force onto your roadmap?

Two hard dates. SQL Server 2016 left extended support in July 2026, so anything still on it is unpatched — that is a compliance conversation, not a performance one, and the target should be 2022 or 2025 rather than an incremental hop. PostgreSQL 14 reaches EOL on 2026-11-12, and because PostgreSQL support is a firm five years with no paid extension from the community, "we'll deal with it later" means running an unsupported database. I would plan the PostgreSQL major upgrade with logical replication so the cutover is a few seconds of connection draining rather than a maintenance window, and I would do it well before the deadline so the fallback plan is still "stay on 14 for another month".

How do you keep a team current on database releases without chasing every feature?

I run it as a small, boring ritual rather than enthusiasm. Once a quarter someone reads the release notes for whatever we run and produces one page: what is newly stable, what is newly default, what is deprecated, what has a CVE. Defaults changing matter more than features arriving — PostgreSQL 18 turning on data checksums in initdb, making generated columns virtual by default and warning on MD5 passwords are all things that change behaviour without anyone opting in. Then we adopt on need, not on novelty: a feature enters the codebase when it removes an existing workaround, and every adoption names the minimum version it pins us to. That keeps the "are you current" interview question answerable without the team living on the bleeding edge.

02 Storage internals: pages, rows and the cost of an update

Almost every performance answer eventually bottoms out in "how many 8 KB pages did we have to touch, and did we have to write new ones". Both engines use 8 KB pages — SQL Server fixed, PostgreSQL compiled in as BLCKSZ and effectively always 8192 — and both read and write whole pages. Where they part company is what an update does, and that single difference explains vacuum, bloat, index maintenance, replication lag and half the tuning advice for each product.

The running example

Picture an orders table with 50 million rows and six indexes, and a nightly job that sets status = 'shipped' on two million of them. On PostgreSQL, an UPDATE never modifies a row in place: it writes a new tuple version, marks the old one dead by stamping xmax, and — unless the update qualifies as a HOT (Heap-Only Tuple) update — inserts a new entry into every one of the six indexes. Two million updates can therefore mean fourteen million writes, a doubling of the table's physical size until vacuum reclaims it, and a corresponding flood of WAL. On SQL Server the row is updated in place if it still fits, the six indexes are only touched if their key columns changed, and the previous version goes to the tempdb version store only if a snapshot-based isolation level or Accelerated Database Recovery needs it.

HOT is the escape hatch on the PostgreSQL side, and it is worth being able to state its two conditions exactly: no indexed column changed, and the new version fits on the same page. Under HOT the new tuple is chained from the old one within the page and no index is touched at all. The second condition is why fillfactor exists — leaving 15–20% of each page free on an update-heavy table buys you HOT updates and is one of the highest-leverage one-line changes in PostgreSQL tuning. PostgreSQL's default fillfactor is 100 for tables (90 for B-tree indexes), which is right for append-only tables and wrong for hot ones.

Clustered index or heap — the SQL Server decision PostgreSQL never makes

In SQL Server the clustered index defines the physical order of the table, and every nonclustered index stores the clustering key as its row locator. Two consequences a lead should be able to derive on the spot: a wide clustering key (say a uniqueidentifier plus a datetime) is duplicated into every nonclustered index, silently inflating the whole database; and a random clustering key causes page splits on insert, which fragment the table and generate extra log. Hence the classic criteria — narrow, unique, static, ever-increasing — and hence NEWSEQUENTIALID() or a sequence rather than NEWID(). Heaps are almost always a mistake for tables that get updated, because a row that grows beyond its page leaves a forwarding pointer behind and every nonclustered-index lookup then costs two reads instead of one.

PostgreSQL has no clustered index, so the equivalent problem shows up differently: random primary keys hurt index locality and inflate WAL through full-page writes, and there is no way to keep the heap in key order permanently. That is precisely the gap uuidv7() in PostgreSQL 18 closes — a UUID whose leading bits are a millisecond timestamp, so inserts land at the right-hand edge of the index like a sequence would, while remaining a globally unique client-generatable identifier.

-- PostgreSQL 18: time-ordered UUID keys, no extension needed
CREATE TABLE orders (
  id          uuid PRIMARY KEY DEFAULT uuidv7(),   -- v7: timestamp-prefixed, index-friendly
  customer_id bigint NOT NULL,
  placed_at   timestamptz NOT NULL DEFAULT now(),
  total       numeric(12,2) NOT NULL
) WITH (fillfactor = 85);

SELECT uuidv7(), uuidv4();       -- uuidv4() is the new explicit spelling of gen_random_uuid()

Interview trap

"PostgreSQL updates are cheap because it's MVCC." The opposite is closer to the truth: an update is an insert plus a delete plus index maintenance, and the cleanup bill arrives later, asynchronously, from autovacuum. The candidates who get this right can explain why a queue table implemented as UPDATE … SET claimed = true at 2,000/second in PostgreSQL will bloat to ten times its live size and start seq-scanning, while the same design on SQL Server merely blocks. The mirror-image trap is the SQL Server one: "in-place updates mean no version overhead" — false once RCSI, snapshot isolation, ADR, triggers, or change tracking are on, at which point you are paying into tempdb's version store and tempdb becomes your new bottleneck.

Try it

  1. PostgreSQL: create a 1M-row table with an index on a column you will not update, run UPDATE t SET payload = payload and record pg_relation_size, n_tup_hot_upd and WAL generated (pg_current_wal_lsn() before/after). Repeat with fillfactor = 70, and again with an index on the column you are updating.
  2. SQL Server: create the same table as a heap, update a varchar column so rows grow, then check forwarded_record_count in sys.dm_db_index_physical_stats. Add a clustered index and repeat.
Expected outcome

PostgreSQL run 1 at fillfactor 100: HOT percentage near zero because there is no room on the page, table size roughly doubles, WAL is large. At fillfactor 70 the HOT percentage jumps toward 90%+, the table stops growing after the first pass, and WAL drops sharply because no index entries are written. Add an index on the updated column and HOT collapses back to zero no matter what the fillfactor is — that is the "no indexed column changed" condition made visible, and it is the argument for not indexing volatile columns. SQL Server: the heap accumulates forwarded records equal to roughly the number of rows that outgrew their page, and each one costs an extra logical read; the clustered version has none, because the row simply moves within the B-tree.

Interview Q&A

Walk me through what physically happens during an UPDATE in each engine.

PostgreSQL: the backend pins the page, writes a new tuple with xmin = current transaction id, sets xmax on the old tuple, and writes a WAL record. If no indexed column changed and the new tuple fits on the same page, it is a HOT update and the indexes are untouched; otherwise every index gets a new entry pointing at the new ctid. The old tuple stays until vacuum removes it and the free space map is updated. SQL Server: the row is updated in place if it still fits, which touches one data page and only the indexes whose keys changed; if it no longer fits, the clustered index splits the page or the heap leaves a forwarding record. The prior image is copied to the tempdb version store only when RCSI, snapshot isolation, ADR, triggers or change tracking require it. The lead-level punchline: PostgreSQL defers cleanup and pays in bloat, SQL Server does the work inline and pays in log and tempdb.

What is TOAST and when does it bite you?

TOAST is PostgreSQL's mechanism for values too large to fit in a page: above roughly 2 KB the value is compressed and, if still too big, sliced into chunks in a side table, leaving a pointer in the main tuple. It bites in three ways. First, an update that does not touch the TOASTed column does not rewrite it, which is good — but a column-wide update of a big jsonb rewrites all the chunks and generates a lot of WAL. Second, TOAST access is a separate index lookup per chunk, so SELECT * on a wide table is far more expensive than selecting the columns you need. Third, compression choice matters: lz4 (available since 14) is several times faster to decompress than the default pglz, and switching default_toast_compression is a cheap win on read-heavy JSON workloads — though it only applies to newly written values.

How do you choose a clustering key in SQL Server?

Narrow, unique, static and ever-increasing, in that priority order, because the key is copied into every nonclustered index as the row locator. An int or bigint identity is the default right answer; a uniqueidentifier from NEWID() is the classic wrong one, because it is 16 bytes, random, and causes page splits on every insert. The interesting cases are where the natural access pattern argues for something else — a clustered index on (tenant_id, created_at) for a multi-tenant table gives you physical co-location per tenant and cheap range scans, at the cost of a wider locator and split risk when a tenant back-dates rows. I would take that trade when the dominant query is "everything for one tenant in a date range", and I would add a surrogate uniquifier column rather than let SQL Server add a hidden one.

Why does PostgreSQL not have clustered indexes, and how do you compensate?

Because MVCC keeps multiple versions of a row in the heap and updates move rows, a permanently ordered heap would require moving rows on every update — which is exactly what the design avoids. CLUSTER gives you a one-off physical sort that decays as soon as writes resume. In practice you compensate three ways: use uuidv7() or a sequence so inserts are naturally ordered by time; use BRIN indexes on naturally correlated columns like created_at, which are tiny and only work because the physical order correlates with the value; and use declarative partitioning so "recent" data is a physically separate, small relation. Range partitioning is really the PostgreSQL answer to what clustering solves in SQL Server.

A colleague wants to store 5 MB PDFs in the database. What do you say?

I ask what problem it solves, because the honest answer is usually transactional consistency between the blob and its metadata. If that is the requirement, both engines can do it: SQL Server with varbinary(max) or FILESTREAM/FileTable, PostgreSQL with bytea (TOASTed) or large objects. But the costs are the same in both: your backups, your replication stream and your buffer cache all inherit the blobs, restore time balloons, and the cache hit rate for the actual working set drops. My default is object storage plus a row holding the key and a checksum, with an outbox or a "pending delete" table to keep the two consistent — and I make the failure mode explicit: orphaned blobs are cheap, missing blobs are not, so always write the blob first and the row second.

What is fillfactor and when do you change it?

Fillfactor is how full a page is allowed to get when it is built. PostgreSQL defaults to 100 for tables and 90 for B-tree indexes; SQL Server defaults to 0, which means 100. You lower it when you have update-heavy or insert-in-the-middle patterns: on PostgreSQL to buy room for HOT updates on the same page, on SQL Server to reduce page splits in a clustered index with a non-sequential key. The cost is proportional: fillfactor 70 makes every scan read roughly 40% more pages and inflates the buffer cache footprint, so it is a bad idea on read-heavy or append-only tables. I treat it as a targeted fix for a table where I have measured a low HOT ratio or a high split rate, never as a database-wide setting.

Explain SQL Server columnstore in one minute and say when you would reach for it.

Columnstore stores data column-by-column in rowgroups of about a million rows, compressed per segment with min/max metadata that lets the engine skip whole segments, and it enables batch-mode execution which processes ~900 rows per CPU instruction stream instead of one. That gives 10× compression and order-of-magnitude scan speedups on analytic queries. I reach for a clustered columnstore on fact tables that are appended and aggregated, and a nonclustered columnstore on an OLTP table when I need real-time analytics without a separate warehouse — 2025 adds ordered nonclustered columnstore and online builds, which makes that far less disruptive. What I do not do is put it on a table with heavy single-row updates: those land in the delta store and the rowgroups degrade until someone reorganises them. PostgreSQL has no equivalent in core, so the honest comparison is "SQL Server can be a decent small warehouse; PostgreSQL needs an extension or a separate system".

How do you detect and fix table bloat in PostgreSQL?

Detect with pg_stat_user_tables (n_dead_tup versus n_live_tup, and whether last_autovacuum is recent) plus pgstattuple for a precise, if expensive, answer; the estimate queries in check_postgres or pgwatch are fine for alerting. Fixing has three tiers: make autovacuum keep up (lower autovacuum_vacuum_scale_factor per table, raise autovacuum_vacuum_cost_limit, add workers) — that is the real fix, since a reclaim without it just refills; reclaim space online with pg_repack, or with REPACK CONCURRENTLY once 19 ships; and only as a last resort VACUUM FULL, which takes an ACCESS EXCLUSIVE lock and rewrites the table. I would also look for the cause: a long-running transaction or an abandoned replication slot holding back the xmin horizon makes vacuum unable to remove anything, and no amount of tuning fixes that.

What is the version store in SQL Server and how does it fail?

It is a set of internal tables in tempdb holding prior row versions, populated when RCSI or snapshot isolation is on, when triggers fire, when online index rebuilds run, or by Accelerated Database Recovery's persistent version store (which lives in the user database instead). It fails when a long-running transaction or an open snapshot prevents cleanup: the version store grows, tempdb fills, and every write in the instance starts failing — a single-instance-wide outage caused by one forgotten session. I monitor sys.dm_tran_version_store_space_usage and the longest-running transaction, set tempdb on fast local storage with multiple equally-sized data files, and treat "oldest active transaction" as a first-class alert. It is the direct analogue of PostgreSQL's xmin horizon problem, and describing them as the same problem in two costumes is a strong interview move.

Why does a random UUID primary key hurt, and does uuidv7 actually fix it?

A random key scatters inserts across the whole index, so every insert dirties a different leaf page. That destroys cache locality (your working set becomes the entire index rather than its right edge), causes page splits in a SQL Server clustered index, and in PostgreSQL inflates WAL through full-page writes because each newly-dirtied page must be written whole after a checkpoint. uuidv7() fixes the locality half of the problem: its leading 48 bits are a Unix millisecond timestamp, so inserts append at the right edge like a sequence. It does not fix the size half — 16 bytes is still twice a bigint, and in SQL Server it is still copied into every nonclustered index. So my rule is: bigint identity/sequence when the database generates keys, uuidv7 when clients must generate them offline or you need to merge data across systems, and uuidv4 only when unguessability is a security requirement.

03 Indexing: the structures and the choices behind them

An index is a bet: you pay on every write and in storage, to make some reads cheaper. Lead-level indexing is therefore less about knowing that B-trees exist and more about being able to say what a given index costs, which existing indexes it makes redundant, and how you would prove it was worth it. The single most useful mental model is that a B-tree lets the engine do exactly one thing — find a contiguous range of keys and walk it — so every index question reduces to "can this predicate and this ordering be expressed as one contiguous range in this key order?"

That model explains the column-order rule (equality predicates first, then the one range predicate, then columns needed only for ordering), the covering-index idea (if everything the query needs is in the leaf, you never leave the index), and why WHERE UPPER(email) = @e or WHERE date_col + interval '1 day' > now() cannot use a plain index — the predicate is not a range over the stored key. It also explains what changed in PostgreSQL 18: skip scan lets a multi-column B-tree be used when the leading column is unconstrained, by internally iterating the distinct values of that leading column and doing a range search under each. If the leading column has 10 distinct values, an index on (status, created_at) now serves WHERE created_at > … at roughly 10 range scans instead of a sequential scan. That retires a whole category of duplicate indexes that existed only to satisfy the old leading-column rule.

Index-only scans and the visibility map

Here is a connection worth making explicitly, because it links this section to the MVCC story. In SQL Server a covering index answers the query outright. In PostgreSQL an index-only scan must still check whether each row is visible to your snapshot — and the index does not store visibility. The engine consults the visibility map, a bitmap with one bit per heap page meaning "every tuple on this page is visible to everyone". If the bit is set, the heap fetch is skipped. Vacuum is what sets those bits. So in PostgreSQL, index-only scans only work on tables that are being vacuumed, and a table starved of autovacuum silently loses them: the plan still says "Index Only Scan" but the Heap Fetches: counter in EXPLAIN ANALYZE climbs toward the row count and performance collapses. That is a genuinely good thing to notice out loud in an interview.

Interview trap

Blindly implementing SQL Server's missing-index DMVs (or Database Engine Tuning Advisor output). Those suggestions are generated per query with no knowledge of the indexes you already have, no de-duplication, and no accounting for write cost — following them literally produces tables with twenty overlapping indexes, a doubled write path, and a bloated backup. The right use is as evidence: read sys.dm_db_missing_index_details for the columns being asked for, then decide whether an existing index can be widened or its INCLUDE list extended instead of creating a new one. The equivalent PostgreSQL trap is adding indexes without ever checking pg_stat_user_indexes.idx_scan; I have never audited a mature PostgreSQL database that did not have several gigabytes of never-scanned indexes slowing down every write.

Interview Q&A

How do you decide the column order in a composite index?

Equality predicates first, then the single range or inequality predicate, then columns needed only for ORDER BY, then everything else in INCLUDE. The reason is that a B-tree can only walk one contiguous key range, so the first column with a non-equality predicate ends the useful prefix — anything after it can be used as a residual filter but not to narrow the range. Secondary considerations: put the more selective column first when both are equality, because it reduces the range faster; and prefer an ordering that serves several queries so you can delete two indexes instead of adding one. PostgreSQL 18's skip scan softens this rule for low-cardinality leading columns, but it does not repeal it — skipping over a million distinct values is still worse than a sequential scan.

When is a filtered/partial index the right tool, and what is the catch?

When a small fraction of the table is interesting and every query that matters carries the same predicate: pending jobs in a queue table, non-deleted rows in a soft-delete design, one tenant's rows in a lopsided multi-tenant table. The index becomes a fraction of the size, fits in cache, and costs nothing to maintain for rows outside the filter. The catch in SQL Server is that the optimizer must prove the query predicate implies the filter, and it is fussy — a parameterised WHERE status = @s will not match WHERE status = 'pending', which is a classic silent failure that ships to production and then never uses the index. PostgreSQL's proof machinery is more capable but has the same fundamental limitation. Both also refuse to use them for constraint enforcement in the ways people expect, so I always test with the actual parameterised statement, not a literal.

Explain INCLUDE versus adding a column to the key.

Key columns are stored at every level of the B-tree, participate in ordering and in uniqueness, and inflate the internal pages — which reduces fan-out and adds levels. INCLUDE columns live only in the leaf: they cannot be used to seek or to satisfy ORDER BY, but they let the index cover a query without widening the tree. So the rule is: columns you filter or sort on go in the key; columns you merely return go in INCLUDE. There is also a subtle SQL Server benefit — INCLUDE can carry types that are illegal in a key, and it does not count against the 900/1700-byte key limit. PostgreSQL gained the same syntax in version 11, with the extra property that an INCLUDE column on a unique index does not participate in uniqueness, which is occasionally exactly what you want.

A table has 14 indexes. How do you get it down to five without breaking anything?

I gather evidence before touching anything: sys.dm_db_index_usage_stats or pg_stat_user_indexes over a full business cycle including month-end, plus the definitions so I can spot exact duplicates and left-prefix subsets — an index on (a) is redundant if (a, b) exists and nothing needs the narrower one for uniqueness. Duplicates and unused indexes go first; then I look for pairs that differ only by an INCLUDE list and merge them. For anything I am not certain about, SQL Server lets me ALTER INDEX … DISABLE, which keeps the definition and drops the storage so re-enabling is one statement; PostgreSQL has no disable, so I script the CREATE INDEX CONCURRENTLY statement into the same change as the drop and keep it in the rollback. Finally I do it in stages with a week between, so a regression is attributable.

When would you use a GIN index, and what are its downsides?

GIN is an inverted index: one entry per element inside a value, pointing at the list of rows containing it. That makes it the right structure for jsonb containment (@>), array membership, and full-text search over tsvector. The downsides are real: GIN indexes are slow to build and to update, because one row insert can touch many index entries, which is why they have a "pending list" (fastupdate) that batches insertions and then gets flushed — occasionally in the middle of a user's INSERT, producing a mysteriously slow statement. They are also large; if you only need containment, jsonb_path_ops gives you a much smaller index by hashing the whole path. PostgreSQL 18 added parallel GIN builds, which helps the build side — with the caveat that 18.6 fixed a real bug where parallel GIN builds left bogus reltuples values that stopped autovacuum from processing the table, so that is a patch you want.

What is a BRIN index and when is it a great answer?

BRIN stores summary information (typically min and max) per range of physical pages — 128 pages by default — so it is measured in kilobytes for a table measured in gigabytes. Scanning it tells the engine which page ranges could contain matching rows, and everything else is skipped. It is a great answer for very large append-only tables where the physical order correlates with the indexed column: event logs, telemetry, ledger tables ordered by created_at. It is a terrible answer when the correlation is weak, because every range then looks like a candidate and you have paid for a full scan plus an index read. The check is one query against pg_stats.correlation for the column; above roughly 0.9 BRIN is worth trying, below 0.5 it is not. The nearest SQL Server analogue is columnstore segment elimination, which works on exactly the same principle.

How do you build a large index without taking an outage?

PostgreSQL: CREATE INDEX CONCURRENTLY, which does two table passes and waits for concurrent transactions, so it takes longer and cannot run inside a transaction block. The critical operational detail is that if it fails it leaves an INVALID index behind that still costs writes but is never used — so any automation must check pg_index.indisvalid and drop-and-retry. It also cannot proceed while a long-running transaction is open, which is the usual reason it appears to hang. SQL Server: WITH (ONLINE = ON), which is Enterprise-only for most index types, plus RESUMABLE = ON so you can pause a build at the end of a maintenance window and resume it later — that pairing is genuinely excellent and underused. On both, I would build during low write volume anyway, watch replication lag, and have a documented abort step.

Your query has a good index but the plan ignores it. Name five reasons.

One: the predicate is not sargable — a function or implicit conversion wraps the column (WHERE CAST(created_at AS date) = …, or an nvarchar parameter against a varchar column, which is the single most common cause in SQL Server). Two: the estimated row count is high enough that a scan is genuinely cheaper, usually because statistics are stale or the estimate is skewed. Three: the index does not cover the query and the optimizer prices the key lookups above a scan — the tipping point is famously low, often around 1% of the table. Four: the leading column is not constrained (softened but not removed by PostgreSQL 18 skip scan). Five: something disqualifies it outright — a filtered index whose predicate cannot be proven, a mismatched collation or operator class, a partitioned table with an unaligned index, or a parameterised query whose cached plan was compiled for a different value. I would diagnose in that order, because the first two cover most real cases.

How do you handle index maintenance, and what is the modern consensus?

The consensus has moved a long way from "rebuild everything above 30% fragmentation every weekend". On SQL Server, logical fragmentation matters mainly for large range scans; for a workload dominated by seeks it is nearly irrelevant, while the statistics update that a rebuild happens to do as a side effect matters a lot. So the modern approach is Ola Hallengren's solution with sensible thresholds, or simply updating statistics regularly and rebuilding rarely, and treating page density (avg_page_space_used_in_percent) as the more useful signal. On PostgreSQL, index bloat is a real and separate problem from table bloat, and the tool is REINDEX CONCURRENTLY (12+), scheduled against the specific indexes that measurement shows are bloated. In both cases I would rather spend the maintenance window on statistics quality and on removing unused indexes than on rebuilding.

How would you approach indexing for a vector-search feature in each engine?

PostgreSQL with pgvector is the mature path: pick HNSW over IVFFlat as the default because it needs no training step and degrades gracefully as data changes, size m and ef_construction for build cost versus recall, and tune hnsw.ef_search at query time as the recall dial. Use halfvec to halve storage when your embeddings tolerate it, and remember that the index is approximate — you need a recall measurement, not just a latency measurement. SQL Server 2025 brings a native vector type with VECTOR_DISTANCE as GA, while CREATE VECTOR INDEX and VECTOR_SEARCH (DiskANN-based) sit behind the PREVIEW_FEATURES database-scoped configuration — so exact brute-force distance is production-ready today, approximate search is a preview. Either way the architectural point I would make is that keeping embeddings next to the relational data removes an entire synchronisation problem, and that is usually worth more than the last few percent of ANN throughput.

04 The optimizer: statistics, plans and parameter sensitivity

Both engines use a cost-based optimizer: enumerate candidate plans, estimate how many rows flow between operators, price each operator with a cost model, pick the cheapest. Everything that goes wrong goes wrong in the estimate. Costs are stable and arbitrary units; row counts are guesses derived from statistics, and a guess that is wrong by 1,000× at the bottom of a plan produces a plan that is wrong by 1,000× at the top — a nested loop where a hash join was needed, a memory grant a hundred times too small, a sort that spills. So the practical skill is: read a plan, find the first operator where estimated and actual rows diverge, and explain why the estimate was wrong.

Where the estimates come from

SQL Server keeps one histogram of up to 200 steps per statistics object, plus a density vector for multi-column correlation. Statistics are auto-created on predicate columns and auto-updated when enough rows change — since 2016 (or compat level 130) the threshold is a square-root formula rather than the old flat 20%, which finally made auto-update usable on large tables. PostgreSQL keeps default_statistics_target (100) most-common values and 100 histogram buckets per column, gathered by ANALYZE and by autovacuum's analyze pass. You raise it per column with ALTER TABLE … ALTER COLUMN … SET STATISTICS 1000 when a column is skewed and important.

The estimator's fatal assumption in both engines is independence between predicates. Given WHERE city = 'Oslo' AND country = 'Norway', each engine multiplies the two selectivities and arrives at an estimate far below reality, because the columns are perfectly correlated. Each has a fix: PostgreSQL's CREATE STATISTICS … (dependencies, ndistinct, mcv) since 10–12, SQL Server's multi-column statistics and filtered statistics, plus 2022's cardinality-estimation feedback and 2025's CE feedback for expressions, which learns the right model from previous executions and applies it to future ones. Knowing that this class of error exists — and that it is why your three-table join estimates one row and returns four million — is more valuable than memorising any syntax.

Reading a plan: what to look for, in order

  1. Estimated vs actual rows, bottom-up. The first big divergence is the root cause; everything above it is a symptom.
  2. Physical reads — Buffers: shared read= in PostgreSQL, SET STATISTICS IO ON in SQL Server. Logical reads are the workload-independent measure of "how much work"; wall-clock time on a warm cache lies.
  3. Spills: Sort Method: external merge Disk: 84000kB, or a SQL Server sort/hash warning triangle. Both mean the memory grant or work_mem was too small for the real row count — usually a downstream symptom of item 1.
  4. Loops: a nested loop whose inner side runs 400,000 times with a key lookup each is the classic "index seek, still slow" plan. In SQL Server multiply the operator's cost by the actual execution count; in PostgreSQL remember actual time is per loop and must be multiplied by loops.
  5. Parallelism: SQL Server's CXCONSUMER/CXPACKET and skewed row distribution across threads; PostgreSQL's Workers Planned versus Workers Launched — if fewer launched than planned, you are out of max_parallel_workers.

Interview trap

"Index Seek is good, Index Scan is bad." A seek that runs 4 million times inside a nested loop is far worse than one scan; and a "seek" with a residual predicate may be reading most of the index anyway. The related trap is trusting the percentage costs in a SQL Server graphical plan — those are estimated costs even on an actual plan, so the operator burning all your time frequently shows as 2%. The reliable signals are actual rows versus estimated rows, actual executions, and logical reads. On the PostgreSQL side, the equivalent trap is quoting actual time from an inner node without multiplying by loops, which under-reports the real cost by whatever the loop count is.

Try it

  1. Build a skewed table (one status value on 95% of rows, five values on the rest). On SQL Server, wrap a query in a stored procedure, run it first with the rare value, then with the common value, and compare durations and the cached plan. Then add OPTION (RECOMPILE) and repeat.
  2. On PostgreSQL, create two perfectly correlated columns, run EXPLAIN on an AND of both, note the estimate versus actual, then add extended statistics and re-run.
Expected outcome

Exercise 1: sniffing the rare value produces an index seek plan; reusing it for the common value produces millions of key lookups and a runtime 50–500× worse. RECOMPILE fixes it at the cost of a compile per execution — fine at ten calls a minute, catastrophic at ten thousand, which is exactly the trade-off PSPO and OPPO were built to remove. Exercise 2: the estimate before extended statistics is roughly (rows × sel_a × sel_b), often off by two or three orders of magnitude; after CREATE STATISTICS … (dependencies) and ANALYZE it lands close to actual, and the join method usually flips from nested loop to hash.

Interview Q&A

Explain parameter sniffing to a mid-level engineer, then tell me how you would fix it at scale.

The optimizer compiles a plan using the parameter values from the first execution and caches it; later executions with very different values reuse a plan that was never right for them. It is not a bug — reuse is what makes SQL Server fast — it is a consequence of caching under skew. At the level of one procedure the fixes are OPTION (RECOMPILE) when call volume is low, OPTIMIZE FOR a representative value when the distribution is known and stable, or splitting the procedure so each branch gets its own plan. At scale I would rather change the system: turn on Query Store, use it to find the queries with multiple plans and bimodal durations, force the good plan for the worst offenders as a stopgap, move to compat level 160+ so PSPO handles the skewed-predicate cases, and to 170 so OPPO handles the optional-parameter procedures. Then fix the code paths that remain, because a forced plan is a debt with no expiry date.

PostgreSQL has no plan cache across sessions. Is that a strength or a weakness?

Both, and I would say so. The strength is predictability: there is no cross-session sniffing pathology, no "someone ran the report and now everything is slow", and no plan cache to bloat or flush. The weakness is compilation cost — a high-frequency OLTP workload recompiles the same statement in every backend, which shows up as CPU you cannot see in any query's runtime. Prepared statements recover most of it, but they introduce PostgreSQL's own version of the problem: after five custom plans the planner may switch to a generic plan whose cost looked acceptable on average and is terrible for your skewed parameter. The tell is a query that is fast for the first five executions of a connection and slow thereafter, and the lever is plan_cache_mode. There is also an operational wrinkle: transaction-mode PgBouncer historically broke server-side prepared statements, which is why so many .NET and Java shops silently ran unprepared for years — PgBouncer 1.21+ supports protocol-level prepared statements and is worth the upgrade.

What is optional parameter plan optimization and why does it matter?

OPPO is a SQL Server 2025 feature that targets the WHERE (@p IS NULL OR col = @p) pattern — the standard way people write an optional filter, and a pattern that historically forced the optimizer into one plan that had to work whether the parameter was supplied or not, so it usually chose a scan. OPPO reuses the multi-plan (adaptive) infrastructure introduced for parameter-sensitive plan optimization in 2022 to generate several plans making different assumptions about which parameters are null, and dispatches at execution time. It matters because the alternative for twenty years was either OPTION (RECOMPILE) on every call or hand-built dynamic SQL, both of which have real costs, and because "search screen" procedures are ubiquitous in enterprise codebases. It requires compatibility level 170, which is the practical hook: the feature is a reason to actually raise compat level after upgrading.

Estimated rows says 1, actual says 4 million. Give me your diagnostic sequence.

First I find the lowest operator where the divergence starts, because everything above inherits it. Then I check the usual causes in order of likelihood: stale statistics (when did they last update, how many rows changed since); a correlated multi-column predicate being multiplied under the independence assumption; a non-sargable or type-converted predicate where the engine falls back to a fixed guess; an ascending key problem where the newest rows are outside the histogram's last step; a join on an expression or across a type boundary; or a table variable / multi-statement TVF, which in SQL Server historically estimated exactly one row (deferred compilation since 2019 fixed the table-variable case at compat 150+). On PostgreSQL I would add: is this a partitioned table where per-partition statistics exist but the parent's do not, and is the estimate coming from a default selectivity constant like 0.005, which is a tell that the planner has no information at all.

How do you use Query Store as a lead, beyond looking at slow queries?

Three ways. As a change-safety net: capture a baseline before a compat-level bump, an index change or a major deployment, then use the regressed-queries report to attribute any degradation to a specific change rather than arguing about it. As a stabiliser: force plans for the handful of queries that flip between good and bad, which buys time without a code deploy — and track those forcings as debt, with a review date. As a source of truth for capacity conversations: total duration × executions tells you where your CPU actually goes, which is almost never where the team assumes. Since 2022 it also works on readable secondaries, and in 2025 that is on by default, so you can finally see what the reporting replica is doing. The one discipline I insist on is retention and capture policy tuning; left at defaults on a chatty ad-hoc workload it fills and starts evicting the data you need.

PostgreSQL has no hints. Defend the design, then tell me what you do when you need one.

The defence is that hints are a way of freezing today's data distribution into the source code, and they age badly: the query that needed a nested-loop hint in 2022 needs a hash join in 2026, but nobody revisits it, so the hint becomes a permanent handicap. Forcing developers to fix the estimate instead of the plan produces a healthier system. In practice, when I need one, the escalation is: fix statistics first (extended statistics, higher statistics targets, an ANALYZE that was never scheduled); rewrite the query so the estimate is derivable (materialise a CTE, split a query with an OR into a UNION ALL, avoid the expression on the join column); adjust cost parameters that are actually wrong for the hardware — random_page_cost at 4.0 is a spinning-disk default and should be 1.1 on NVMe, and effective_cache_size should reflect real RAM. Only then, and only for a specific query, would I reach for pg_hint_plan, with a comment saying why and when to remove it.

What planner settings would you check first on a PostgreSQL server you have just inherited?

shared_buffers (25% of RAM is the usual starting point), effective_cache_size (about 50–75%, it is an estimate not an allocation), random_page_cost (1.1 on SSD/NVMe, still 4.0 on far too many servers), work_mem (per node per worker — the multiplication trap), max_parallel_workers_per_gather, and whether jit is doing more harm than good. JIT has been on by default since 12 with jit_above_cost at 100000, and on OLTP-ish queries that happen to estimate high it adds compilation time to every execution for no benefit; disabling it is one of the most common single-line wins on an inherited server. I would also check autovacuum settings and default_statistics_target, and run SELECT name, setting, source FROM pg_settings WHERE source NOT IN ('default','override') to see what a predecessor changed and, ideally, find out why.

When is OPTION (RECOMPILE) the right answer and when is it a trap?

Right when the statement is expensive relative to its compile cost and its optimal plan genuinely depends on the parameter values: a nightly report, a complex search executed a few times a minute, an ad-hoc admin query. It gives the optimizer the actual literal values, which also enables constant folding and better estimates than any hint. It is a trap on high-frequency OLTP statements, because compilation is CPU-bound and single-threaded per statement and you can turn a plan problem into a CPU saturation problem — the pathological version is a compile storm where thousands of concurrent calls all compile at once. SQL Server 2025 added optimized sp_executesql specifically to serialise that compilation and blunt storms, which is a useful thing to know exists. My rule of thumb: below a few hundred executions per minute it is usually fine, above that I want PSPO/OPPO, a forced plan, or a code change.

How do you keep statistics healthy on a very large table?

On SQL Server the auto-update threshold at compat 130+ is roughly the square root of 1,000 × rows, so a billion-row table updates after about a million changes — reasonable but still leaves the ascending-key gap where today's rows fall past the last histogram step. My answers are: a scheduled UPDATE STATISTICS with a sampling rate high enough to matter on the tables that drive plan choice, persisted sample rates (2016 SP1+) so a manual full scan is not undone by the next auto-update, and filtered statistics on the hot recent range. On PostgreSQL, autovacuum's analyze pass is driven by autovacuum_analyze_scale_factor at 0.1, which is far too lazy for a huge table, so I lower it per table; I raise SET STATISTICS on the specific skewed columns rather than globally, because default_statistics_target raises ANALYZE cost everywhere; and I add extended statistics where correlation matters. On both, partitioning helps enormously because each partition gets its own, much more accurate, statistics.

A query got 100× slower overnight with no deployment. Walk me through it.

I start by establishing whether the plan changed or the data did. Query Store answers that instantly on SQL Server; on PostgreSQL I compare the current EXPLAIN against a stored plan or auto_explain logs, and check pg_stat_statements for whether mean time or call count moved. If the plan changed, the candidates are: statistics updated and shifted an estimate, a new index appeared or an old one was dropped, the data crossed a tipping point, a parameter-sniffed recompile happened after a cache flush (a failover, a restart, a memory-pressure eviction, an index rebuild, or a settings change all flush the cache). If the plan did not change, look at volume, blocking, and the environment: a growing table crossing out of memory, autovacuum falling behind so an index-only scan started hitting the heap, a failed-over replica running with a cold cache, or storage latency. I would take the fastest safe mitigation — force the old plan, or update statistics — and only then do root cause, because a 100× regression is an incident, not a puzzle.

05 Transactions, isolation and concurrency control

If you only prepare one section deeply, make it this one. It is where the two engines differ most, where the differences cause the worst production surprises, and where a lead is expected to reason from first principles rather than recite the four ANSI levels.

The first-principles version: a transaction needs to see a consistent view of the database while other transactions are changing it. There are exactly two families of answers. Pessimistic: take locks so nobody can change what you are reading — readers block writers and writers block readers. Optimistic / multiversion: keep old versions of rows around so readers see a snapshot and never block — readers do not block writers at all, but you now have to store, and later reclaim, those versions. PostgreSQL chose multiversion for everything, always. SQL Server was born pessimistic and bolted multiversioning on in 2005 as an opt-in database setting, which is why the single most consequential fact in this whole guide is: on-premises SQL Server ships with READ COMMITTED using locks, and RCSI turned off, while Azure SQL Database ships with RCSI on by default. The same application, the same isolation level name, and completely different blocking behaviour.

Write skew is the anomaly that separates the people who have read about isolation from the people who have debugged it. Two doctors are on call; the rule is at least one must remain. Both transactions read "2 on call", both conclude it is safe to go off call, both write. Under snapshot isolation each transaction saw a valid state and wrote a different row, so no conflict is detected — and the invariant is broken. Snapshot isolation in SQL Server does not catch this. PostgreSQL REPEATABLE READ does not catch it. Only PostgreSQL SERIALIZABLE (SSI) or explicit locking catches it. The practical fixes, in order of preference: put the invariant in a constraint the database can enforce; take an explicit lock on the row or aggregate you are guarding (SELECT … FOR UPDATE, UPDLOCK, HOLDLOCK); or run the transaction SERIALIZABLE and retry on 40001.

-- PostgreSQL: the guarded write, three ways
-- 1. Explicit row lock (works at READ COMMITTED)
BEGIN;
SELECT count(*) FROM shifts WHERE on_call AND ward_id = 7 FOR UPDATE;
UPDATE shifts SET on_call = false WHERE id = 42;
COMMIT;

-- 2. Serializable + retry (the application MUST handle SQLSTATE 40001)
BEGIN ISOLATION LEVEL SERIALIZABLE;
  -- … same logic, no explicit locks …
COMMIT;

-- 3. Job queue without contention: skip what someone else has claimed
BEGIN;
SELECT id, payload FROM jobs
WHERE  state = 'pending'
ORDER  BY created_at
LIMIT  10
FOR UPDATE SKIP LOCKED;          -- 9.5+; the correct way to build a queue on Postgres
UPDATE jobs SET state = 'running' WHERE id = ANY($1);
COMMIT;
-- SQL Server: the equivalents
-- Guarded read-then-write
BEGIN TRAN;
SELECT COUNT(*) FROM dbo.shifts WITH (UPDLOCK, HOLDLOCK) WHERE on_call = 1 AND ward_id = 7;
UPDATE dbo.shifts SET on_call = 0 WHERE id = 42;
COMMIT;

-- Queue: READPAST is the SKIP LOCKED analogue
UPDATE TOP (10) dbo.jobs WITH (READPAST, UPDLOCK)
SET    state = 'running'
OUTPUT inserted.id, inserted.payload
WHERE  state = 'pending';

Locking, escalation, and what 2025 changed

SQL Server locks at row, page, partition and table granularity, with intent locks (IS, IX) at higher levels so the engine can test compatibility without walking the hierarchy. Lock escalation triggers when a single statement acquires about 5,000 locks on one object: the engine trades them for a single table lock, which is memory-efficient and catastrophic for concurrency. Every "our nightly batch blocks the whole application" story is escalation. The classic mitigations are batching the DML into chunks of a few thousand rows, or ALTER TABLE … SET (LOCK_ESCALATION = DISABLE), or partition-level escalation on a partitioned table.

Optimized locking, new in SQL Server 2025 on-premises, changes the shape of this problem. Instead of holding a row lock per modified row for the life of the transaction, it takes a single transaction-ID (TID) lock and qualifies rows after evaluating the predicate (Lock After Qualification), so a large update holds a handful of locks rather than millions. That removes escalation as a failure mode and cuts lock memory dramatically. It builds on Accelerated Database Recovery, so ADR must be on, and it is most effective with RCSI so readers are not taking locks either. This is a genuinely good "what's new and why does it matter" answer.

PostgreSQL has no lock escalation at all — row locks live in the tuple header rather than a lock manager table, so a million-row update costs no lock memory. What it has instead is the xmin horizon: any transaction still open, any replication slot not advancing, any prepared transaction left behind, prevents vacuum from removing versions newer than that point across the entire cluster. One psql window left in idle in transaction can bloat every table in the database. The mitigations are idle_in_transaction_session_timeout, statement_timeout, max_slot_wal_keep_size, and monitoring the oldest transaction age as a first-class metric.

Interview trap

WITH (NOLOCK) as a performance setting. It is not a hint about locking speed; it is READ UNCOMMITTED, and it permits dirty reads and, because allocation-order scans can race with page splits, it can return committed rows twice or skip them entirely — silent wrong answers in a report, not a crash. Candidates who say "it's fine, it's just a report" have not thought about the finance team reconciling it. The correct answer is: if readers are blocking, turn on RCSI so readers take a statement-level snapshot from the version store; that is the same non-blocking read you wanted, without the wrong answers. The only defensible uses of NOLOCK are ad-hoc diagnostics on a system already in trouble, and even then I say it out loud. The PostgreSQL-side trap is the mirror image: assuming READ COMMITTED gives you a consistent view across two statements. It does not — each statement gets its own snapshot — so a read-then-write pattern needs FOR UPDATE or REPEATABLE READ.

Try it

  1. Reproduce write skew. Two sessions, a table with two on-call rows, each session reading the count and then updating a different row, at SNAPSHOT on SQL Server and REPEATABLE READ on PostgreSQL. Then re-run at PostgreSQL SERIALIZABLE.
  2. Deliberately deadlock two sessions by updating two rows in opposite orders. Capture the deadlock graph from the system_health extended event session on SQL Server, and the deadlock detected log entry with log_lock_waits = on on PostgreSQL.
Expected outcome and the lesson

Exercise 1: both sessions commit successfully under SNAPSHOT / REPEATABLE READ and the ward now has zero doctors on call — the invariant is broken with no error anywhere. Under PostgreSQL SERIALIZABLE, one transaction fails with SQLSTATE 40001 could not serialize access due to read/write dependencies, which is the database telling you it detected a dangerous dependency cycle; your application must retry. The lesson to state in an interview: snapshot isolation prevents anomalies about rows you read and wrote, not anomalies about invariants across rows. Exercise 2: both engines pick a victim and abort it; the difference is that SQL Server's deadlock graph names the exact resources and the lock modes, while PostgreSQL's log gives you the process ids and statements. Either way the fix is almost always "acquire objects in a consistent order" or "shorten the transaction", not a hint.

Interview Q&A

Compare READ COMMITTED in SQL Server and PostgreSQL.

They share a name and almost nothing else. PostgreSQL's READ COMMITTED takes a fresh snapshot at the start of each statement; readers never block and never take shared locks on rows they read. SQL Server's default READ COMMITTED takes shared locks and releases them as it goes, so a reader blocks behind an uncommitted writer and a writer blocks behind a long reader — this is the source of most SQL Server blocking incidents. Turning on READ_COMMITTED_SNAPSHOT makes SQL Server behave like PostgreSQL: statement-level snapshots served from the tempdb version store. The catch when you enable it is that you have moved the cost, not removed it — tempdb now carries the version store, and code that implicitly relied on readers blocking (a home-made "lock by selecting" pattern) silently changes behaviour. So I would enable RCSI, but with a load test and with tempdb sized and monitored first.

What is write skew and how do you defend against it?

Write skew is two concurrent transactions each reading an overlapping set, each deciding a write is safe, and each writing a different row, so no write-write conflict is detected — yet the combined result violates an invariant that spanned those rows. The on-call doctors example is canonical; so is "two bookings for the same room at overlapping times" and "two withdrawals that each leave the joint balance non-negative individually". Snapshot isolation and PostgreSQL REPEATABLE READ do not prevent it, which surprises people, because the anomaly is not about stale reads of rows you wrote. My defence in order: express the invariant as a constraint the engine enforces — a unique index, a CHECK, or in PostgreSQL an exclusion constraint with a GiST index for the overlapping-booking case, and from 18 a temporal PRIMARY KEY … WITHOUT OVERLAPS; failing that, lock the guard explicitly; failing that, run SERIALIZABLE with a retry loop and accept the abort rate.

How do you build a reliable job queue in each engine?

PostgreSQL: SELECT … FOR UPDATE SKIP LOCKED LIMIT n inside a transaction, then mark the rows claimed and commit. SKIP LOCKED means workers never queue behind each other, which is what makes this scale; without it, N workers serialise on the head of the queue. SQL Server: UPDATE TOP (n) … WITH (READPAST, UPDLOCK) … OUTPUT inserted.*, which claims and returns in one statement — READPAST is the SKIP LOCKED analogue. In both, the hard parts are the same and are what I would actually discuss: idempotent handlers because at-least-once delivery is all you get; a visibility timeout or lease column so a crashed worker's rows are re-claimable; a dead-letter path after N attempts; and an index on (state, created_at) — partial or filtered on the pending state — so the queue head stays cheap as the table grows. And the PostgreSQL-specific warning: a high-throughput queue table is an update-heavy table, so set a low fillfactor, tune autovacuum aggressively for it, and be ready for it to be your first bloat incident.

Explain lock escalation and how you would handle a nightly batch that triggers it.

SQL Server converts many fine-grained locks into one coarse lock when a statement passes roughly 5,000 locks on an object, to bound lock memory. The result is a table lock and a stalled application. My first move is not a setting, it is batching: rewrite the batch as a loop over chunks of two to five thousand rows, keyed on the clustered index so each chunk is a range, with a commit and a short delay between chunks — that also bounds log growth and replication lag, which is why it is the right answer even on engines without escalation. If batching is not possible, SET (LOCK_ESCALATION = DISABLE) on the table trades lock memory for concurrency, and on a partitioned table AUTO escalates to the partition instead of the table. On SQL Server 2025, optimized locking largely removes the problem at the source by holding a TID lock instead of per-row locks — but it requires ADR and I would still batch, because unbounded transactions are bad for other reasons. PostgreSQL never escalates, so the same batch there is a bloat and replication-lag problem rather than a blocking one.

What causes deadlocks and how do you fix them systematically?

A cycle in the waits-for graph: two transactions each holding something the other needs. The overwhelming majority come from inconsistent ordering — one code path updating parent then child, another child then parent — or from lock upgrades, where a transaction reads with a shared lock and later upgrades to exclusive, so two readers deadlock on upgrade. Systematically: capture them (the system_health extended event session already has your deadlock graphs; on PostgreSQL turn on log_lock_waits and read the detail lines), find the two statements, and fix the ordering or take the stronger lock up front with UPDLOCK / FOR UPDATE on the initial read. Then reduce the exposure: shorter transactions, no user interaction or HTTP calls inside a transaction, covering indexes so scans do not take locks on rows they will discard, and RCSI to remove reader-writer conflicts entirely. Finally, accept that some deadlocks are inherent and make the application retry idempotently — a retry policy on error 1205 or SQLSTATE 40P01 is a legitimate part of the design, not an admission of defeat.

What is the xmin horizon and why should a lead care?

PostgreSQL can only remove a dead row version once no transaction could still need it. The oldest such point is the xmin horizon, and it is held back by the oldest running transaction, the oldest snapshot on a hot standby with hot_standby_feedback on, the oldest inactive replication slot, and any orphaned prepared transaction. When it stops advancing, vacuum runs and reclaims nothing, tables bloat, index-only scans stop working, and eventually you approach transaction-ID wraparound and the cluster starts refusing writes. A lead should care because the cause is usually not the database: it is an application holding a transaction open across a network call, a BI tool with a 12-hour session, or a replica that was decommissioned without dropping its slot. So the controls are organisational as much as technical: idle_in_transaction_session_timeout set to something like 60 seconds for application roles, max_slot_wal_keep_size so a dead slot cannot fill the disk, and an alert on oldest transaction age long before it is an emergency.

When would you actually use SERIALIZABLE?

When correctness across rows matters more than throughput and the invariant cannot be expressed as a constraint: financial postings that must respect an aggregate limit, inventory allocation, scheduling systems. On PostgreSQL, SSI makes this genuinely practical — it is optimistic, so it does not block, and the cost is an abort rate you must handle with a retry loop and, ideally, a metric so you notice when it climbs. On SQL Server, SERIALIZABLE is pessimistic key-range locking, so the cost is blocking and deadlocks rather than aborts, and it scales much worse; there I would usually take explicit UPDLOCK, HOLDLOCK on the narrow guard instead of raising the level for the whole transaction. In both cases I would first ask whether a unique index, an exclusion constraint, or a single atomic statement could carry the invariant, because a constraint costs nothing at review time and never forgets.

A team reports "the app is slow" and you find blocking. Walk me through the first ten minutes.

Find the head of the blocking chain, not the victims: on SQL Server sp_WhoIsActive or sys.dm_exec_requests joined to sys.dm_os_waiting_tasks, following blocking_session_id to the root; on PostgreSQL pg_blocking_pids() against pg_stat_activity. Then classify the root: is it running (a slow query — this is now a query-tuning problem), or is it idle in a transaction (an application bug — someone opened a transaction and went off to call an API), or is it waiting on something external? Mitigate proportionally: kill the root session if it is safe and idle, and be explicit that killing a long-running write means a rollback that can take as long as the work did — unless ADR is on, which is exactly the scenario ADR was built for. Then prevent: RCSI if readers were the victims, a lock_timeout/SET LOCK_TIMEOUT so waiters fail fast instead of piling up, and a transaction-duration alert. I would also capture the evidence before killing anything, because the postmortem needs it.

What is Accelerated Database Recovery and why does it matter to concurrency?

ADR (2019+) changes crash recovery and rollback from "replay the log backwards" to "use a persistent version store in the user database", so rolling back a huge transaction takes seconds instead of hours, and the active log stops growing without bound behind one long transaction. It matters to concurrency for two reasons. First, the classic worst-case incident — a batch job cancelled after two hours, followed by a two-hour rollback during which the database is effectively unavailable — largely disappears. Second, it is a prerequisite for optimized locking in 2025, and 2025 extends ADR to tempdb, which helps workloads that lean on temp tables. The cost is that the persistent version store lives in your database and consumes space, and its cleanup can fall behind, so it is one more thing to monitor rather than free. The PostgreSQL analogue is instructive: rollback there is nearly free because the aborted transaction's tuples are simply never visible — but you pay the same money later, to vacuum.

How do you decide transaction boundaries in application code?

The rules I enforce in code review: a transaction contains exactly the writes that must be atomic, and nothing else — no HTTP calls, no message publishing, no user interaction, no cache warming, no waiting on a lock you took for convenience. Reads that only inform a decision go outside where possible, and where they cannot, the guard is an explicit lock rather than a raised isolation level. Transactions have a bounded, small number of statements and a bounded, small duration, with statement_timeout / SET LOCK_TIMEOUT configured so a pathological case fails rather than hangs. And side effects that must be atomic with the write but cannot be inside the database — publishing an event, calling a payment provider — go through an outbox table written in the same transaction and drained by a separate process, because two-phase commit across a database and a broker is a distributed-systems problem I would rather not own. That last point is usually what an interviewer is actually fishing for.

06 Bloat, vacuum and the version store: paying the MVCC bill

Section 05 established that both engines create row versions and both must eventually reclaim them. This section is the operational half of that: who does the reclaiming, when, and what happens when it falls behind. It is the number-one source of PostgreSQL production incidents and, in the tempdb guise, a top-three source on SQL Server — so an interviewer asking about it is asking whether you have actually run these systems.

PostgreSQL: autovacuum is a background garbage collector you must size

Vacuum does three distinct jobs, and conflating them is a common mistake. It reclaims dead tuples so their space can be reused (not returned to the OS — that is VACUUM FULL's job). It updates the visibility map, which is what makes index-only scans work. And it freezes old tuples, rewriting their transaction ids so the 32-bit transaction counter can wrap around safely. Autovacuum runs a table when dead tuples exceed autovacuum_vacuum_threshold (50) plus autovacuum_vacuum_scale_factor (0.2) × rows. On a 500-million-row table that means waiting for 100 million dead rows — which is why the single most important PostgreSQL tuning change on large tables is lowering the scale factor per table.

-- Per-table autovacuum tuning: the actual fix for a big, hot table
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor  = 0.01,   -- vacuum at 1% dead, not 20%
  autovacuum_vacuum_threshold     = 1000,
  autovacuum_analyze_scale_factor = 0.02,
  autovacuum_vacuum_cost_delay    = 0,      -- do not throttle this table
  fillfactor                      = 85      -- and buy HOT updates while we are here
);

-- Cluster-wide: give autovacuum enough throughput to keep up on modern hardware
-- (postgresql.conf) autovacuum_max_workers = 6, autovacuum_vacuum_cost_limit = 3000,
--                  maintenance_work_mem = 1GB

-- Who is holding back the horizon? This is the query to have memorised.
SELECT 'transaction' AS kind, pid::text AS id, now() - xact_start AS age, state, left(query, 60) AS detail
FROM   pg_stat_activity WHERE xact_start IS NOT NULL
UNION ALL
SELECT 'slot', slot_name, NULL, active::text, restart_lsn::text FROM pg_replication_slots
UNION ALL
SELECT 'prepared', gid, now() - prepared, NULL, NULL FROM pg_prepared_xacts
ORDER  BY 3 DESC NULLS LAST;

-- How close is any table to wraparound trouble?  Emergency vacuum starts around 200M.
SELECT relname, age(relfrozenxid) AS xid_age,
       round(100.0 * age(relfrozenxid) / 2000000000, 1) AS pct_to_wraparound
FROM   pg_class WHERE relkind IN ('r','m','t') ORDER BY 2 DESC LIMIT 10;

Transaction ID wraparound deserves its own paragraph because it is the PostgreSQL failure mode that takes a business offline. Transaction ids are 32-bit and compared modulo 2³¹, so a tuple whose xmin is more than about two billion transactions old would appear to be in the future. Freezing marks such tuples as permanently visible. If freezing cannot keep up — because autovacuum is disabled, starved, or blocked by a stuck xmin horizon — PostgreSQL first warns, then refuses new write transactions entirely and requires a single-user-mode vacuum. Recovery is measured in hours on a large database. Modern versions have made this far less likely (aggressive autovacuum kicks in at autovacuum_freeze_max_age, 200 million by default, and 17 substantially reduced vacuum's memory use and WAL volume), but the failure mode still exists, and monitoring age(relfrozenxid) is non-negotiable.

SQL Server: version store, ghost cleanup and statistics

SQL Server's equivalent bill arrives in tempdb. With RCSI or snapshot isolation on, every modified row's prior image goes to the version store, and the store can only be trimmed past the oldest active snapshot — the exact analogue of the xmin horizon, with the same root causes and the same fix. Additionally, deleted rows are first marked as ghost records and physically removed later by a background task, which can fall behind on a heavily-deleted table and leave pages full of nothing. The maintenance work SQL Server actually needs is therefore: keep tempdb fast and correctly sized (multiple equally-sized data files, on the fastest local storage, with autogrowth uniform — trace flags 1117/1118 behaviour became the default in 2016); keep statistics fresh; and rebuild or reorganise indexes far less often than folklore suggests.

Interview trap

Two of them, one per engine. PostgreSQL: "we run VACUUM FULL weekly to keep things tidy." VACUUM FULL takes an ACCESS EXCLUSIVE lock, rewrites the entire table and its indexes, needs as much free disk as the table, and is an outage on anything large — and if autovacuum is the real problem, the table simply bloats again. The right answer is to fix autovacuum, use pg_repack (or REPACK CONCURRENTLY from 19) for a one-off reclaim, and treat VACUUM FULL as a scheduled-downtime tool. SQL Server: "we shrink the database every night to reclaim space." DBCC SHRINKFILE moves pages from the end of the file to the front in the worst possible order, fragmenting every index, generating enormous log, and the file just grows again — a maintenance plan that shrinks and then rebuilds indexes is doing two expensive things that undo each other. Shrink is an exceptional response to a one-off event (a huge archive delete), not a routine.

Try it

  1. PostgreSQL: open a session, run BEGIN; SELECT 1; and leave it. In another session, churn a table with repeated updates and run VACUUM (VERBOSE) t. Read the "dead row versions cannot be removed yet, oldest xmin" line. Close the first session and vacuum again.
  2. SQL Server: turn on RCSI in a test database, start a SET TRANSACTION ISOLATION LEVEL SNAPSHOT; BEGIN TRAN; SELECT … and leave it open; churn the table from another session and watch version_store_reserved_page_count climb.
Expected outcome

PostgreSQL: vacuum reports it scanned the table and removed zero row versions, naming the oldest xmin it is blocked behind — that one line is the diagnostic for the majority of "vacuum is running but bloat keeps growing" incidents, and being able to say "I'd read the VACUUM VERBOSE output for the oldest xmin" is a strong signal in an interview. After the idle transaction ends, the next vacuum removes everything. SQL Server: the version store grows without bound for as long as the snapshot transaction is open, and it does not shrink when the churning session commits — only when the oldest snapshot ends. Same physics, different filesystem.

Interview Q&A

Explain autovacuum to someone who has only used SQL Server.

It is a background garbage collector for row versions, and it has no SQL Server equivalent because SQL Server updates in place. Three jobs: remove dead tuples so the space is reusable, maintain the visibility map that makes index-only scans possible, and freeze old transaction ids so the 32-bit counter can wrap. It is triggered per table by a threshold plus a scale factor of the row count, runs in a limited number of workers, and throttles itself with a cost-delay budget so it does not swamp foreground I/O. The two things that go wrong are that it is not triggered often enough on big tables (the 20% default scale factor), and that it is throttled too aggressively for modern storage (the cost limit defaults assume spinning disks). If I inherit a PostgreSQL estate, per-table scale factors on the ten biggest tables and a raised cost limit are usually the first change I make.

Your largest table is 40% dead tuples and autovacuum runs constantly. What now?

Constantly running and not reclaiming means it is blocked, not slow, so I check the xmin horizon first: the oldest open transaction, replication slots that are not advancing, prepared transactions, and whether a standby with hot_standby_feedback is running a long report. Nine times out of ten it is an application connection idle in transaction or an abandoned slot from a decommissioned replica. Once the horizon moves, I let autovacuum catch up, then tune it per table so it does not fall behind again. Only then do I reclaim the existing bloat, and I reach for pg_repack (or REPACK CONCURRENTLY on 19) rather than VACUUM FULL, so the table stays available. Finally I add the two alerts that would have caught it earlier: oldest transaction age, and replication slot lag in bytes.

What is transaction ID wraparound and how do you prevent it?

Transaction ids are 32-bit and compared in a circular space, so a tuple older than about two billion transactions would look like it came from the future. Freezing rewrites those tuples as unconditionally visible, and it is vacuum's third job. If freezing does not happen, PostgreSQL warns as the age climbs, then stops accepting write transactions and requires a manual vacuum, potentially in single-user mode — hours of downtime. Prevention is unglamorous: never disable autovacuum "temporarily", monitor age(relfrozenxid) per table with an alert well below autovacuum_freeze_max_age (200 million), keep the xmin horizon moving, and pay attention to tables that are never updated — a static lookup table still needs freezing, and it never crosses the dead-tuple threshold, which is exactly why aggressive anti-wraparound vacuum exists. Note also that anti-wraparound vacuum does not yield to a conflicting lock request the way a normal autovacuum does, so it can block DDL, which is a nasty surprise at the worst moment.

How often should you rebuild indexes on SQL Server?

Far less often than the folklore says, and only where measurement justifies it. Logical fragmentation matters for large read-ahead range scans and barely at all for a seek-dominated OLTP workload; on flash storage the random-versus-sequential penalty that made fragmentation scary is largely gone. Page density is the more meaningful metric, because a half-empty index doubles the pages you must read and cache. So my policy is: reorganise or rebuild the specific large indexes whose density is poor, keep statistics fresh on a separate and more frequent schedule (a rebuild updates statistics with a full scan as a side effect, which is why rebuilds sometimes "fix" a problem that was really a statistics problem), and stop running blanket maintenance plans. Ola Hallengren's scripts with thresholds are the standard implementation. And whatever the schedule, use ONLINE = ON, RESUMABLE = ON so a rebuild cannot become an outage.

What is the equivalent of the xmin horizon on SQL Server?

The oldest active snapshot transaction pinning the tempdb version store, plus the oldest active transaction pinning the log. The mechanism is different but the shape is identical: one long-lived reader prevents cleanup, cleanup falls behind, and something fills — tempdb in the snapshot case, the transaction log in the long-write case. And it can be held from a readable secondary, because a long report on a replica delays the primary's version cleanup unless you accept stale reads. That parallel is worth drawing explicitly in an interview: it shows you understand that MVCC is not a PostgreSQL quirk but a general trade, and that the operational discipline — bound transaction duration, monitor the oldest one, never hold a transaction across an external call — is the same on both.

When is DBCC SHRINKFILE acceptable?

When a genuinely one-off event freed a large, permanent amount of space — archiving five years of history, dropping a huge table, migrating a workload off the instance — and you actually need that disk back. Even then I shrink in small increments, during a quiet period, with TRUNCATEONLY first if the free space is at the end of the file, and I plan an index maintenance pass afterwards because shrink will have fragmented everything. What makes it unacceptable is scheduling it: a database that shrinks nightly will regrow nightly, and every autogrowth is a blocking event (unless instant file initialisation is enabled, which only helps data files, never the log). The log has its own version of this conversation — a log that keeps growing is a symptom, usually of a missing log backup in full recovery model or a long-running transaction, and shrinking it treats the symptom.

What did PostgreSQL 17 and 18 change about vacuum, and does it change your advice?

17 replaced vacuum's dead-tuple array with a memory-efficient radix tree (TidStore), which removed the old 1 GB cap on maintenance_work_mem effectiveness and means a large vacuum can now finish in one pass instead of several — a real improvement on huge tables. It also cut the WAL volume vacuum generates. 18's asynchronous I/O speeds up vacuum's read phase, since vacuum is exactly the kind of large sequential reader that benefits from queued reads. My advice changes in one way: on 17+ it is worth giving vacuum substantially more maintenance_work_mem than the old folklore allowed, because it can now use it. Everything else stays — the horizon still blocks it, the scale factor is still too high by default, and 19's REPACK CONCURRENTLY will change the reclaim story rather than the prevention story.

How do you size and configure tempdb?

Fast local storage (NVMe, and on a cloud VM the ephemeral disk is usually the right place), multiple data files of equal size with equal autogrowth to spread allocation-page contention, and enough pre-allocated space that it never has to grow during business hours. The old advice of one file per core caps out around eight files; start at eight (or four on a small box) and add only if you measure PAGELATCH contention on allocation pages. Since 2016, uniform growth across files and single-extent allocation are the default, so trace flags 1117 and 1118 are history. Then size for the workload: RCSI and snapshot isolation put the version store there, spills put sorts and hashes there, and every temp table and table variable lives there. SQL Server 2025 adds two relevant things — tempdb space resource governance so one runaway workload cannot consume it all, and ADR for tempdb — and on Linux you can now put tempdb on tmpfs, which is excellent if you have the RAM and understand that it is recreated on restart.

How do you archive or delete 500 million rows from a live table?

Never in one statement. I batch: a loop deleting a few thousand rows per transaction, driven by the clustered index or primary key so each batch is a contiguous range, with a short pause between batches so replication and log backups keep up. On SQL Server that avoids lock escalation and unbounded log growth; on PostgreSQL it avoids a single enormous transaction pinning the xmin horizon for hours and then leaving the whole range as dead tuples at once. If the deletion is by time and this is a recurring need, the right answer is not deletion at all — it is partitioning, so archiving becomes ALTER TABLE … SWITCH on SQL Server or DETACH PARTITION on PostgreSQL, both metadata-only and instant. Retro-fitting partitioning is work, but it converts a recurring multi-hour maintenance job into a one-second operation, and that is the argument I would make to a product owner.

What monitoring would you put in place specifically for this area?

Six signals, and I would want them on a dashboard before I would call an estate production-ready. PostgreSQL: dead-tuple ratio and time since last autovacuum on the top tables; age(relfrozenxid) maximum across the cluster; oldest transaction age; replication slot lag in bytes. SQL Server: tempdb free space and version store size; oldest active transaction and oldest snapshot transaction; log space used per database and time since last log backup; and the date of the last successful DBCC CHECKDB. On both I want alerting thresholds set where a human still has hours to act, not minutes — the entire point is that these are slow-moving failures that are trivially preventable and extremely expensive once they land. And I would rehearse the response, because "vacuum the cluster in single-user mode" is not something to read for the first time at 3am.

07 Writing SQL that scales: set-based patterns and modern syntax

Everything so far has been about the engine. This section is about the code you and your team actually write, and about the fact that the two dialects have converged sharply in the last three years — SQL Server 2025 finally has regex, native JSON, || concatenation and CURRENT_DATE; PostgreSQL 15–17 gained MERGE, JSON_TABLE and the SQL/JSON constructors. A lead is expected to know both the modern spelling and the legacy one still sitting in the codebase.

The one rule that matters: think in sets, and let the engine choose the loop

The dominant performance mistake in enterprise SQL is not a missing index, it is row-by-agonising-row processing: a cursor, a WHILE loop, or — far more common today — an ORM iterating entities and issuing one statement per row. A single set-based statement gives the optimizer the whole problem, lets it choose a hash join over 400,000 nested-loop iterations, and turns 400,000 round trips into one. The counter-argument a good candidate raises unprompted: a single statement over millions of rows is also a single enormous transaction, with all the lock-escalation, log-growth and bloat consequences from sections 05 and 06. So the mature answer is set-based, in bounded batches — not one row at a time, and not all rows at once.

Interview trap

MERGE on SQL Server. It reads beautifully and it has a long, documented history of bugs and surprises: it is not atomic against concurrent inserts unless you add WITH (HOLDLOCK) to the target, so under concurrency it produces primary-key violations; it can fire triggers in unexpected ways; WHEN NOT MATCHED BY SOURCE without a filter will happily delete rows you never intended to be in scope; and filtered indexes plus MERGE have produced incorrect results in shipped versions. The interview-grade answer is: I would use MERGE for a controlled, single-threaded ETL load, and UPDATE-then-INSERT under an explicit UPDLOCK, HOLDLOCK for anything concurrent. On PostgreSQL, ON CONFLICT is genuinely atomic and is the right default — MERGE there (15+) is for the multi-action ETL case where ON CONFLICT cannot express the logic.

Try it

  1. Write the same "assign the next available slot to each pending request" logic three ways — a cursor, a set-based UPDATE … FROM with a window function, and a batched loop — and compare duration, logical reads and log bytes on a 1M-row table.
  2. PostgreSQL: write a CTE that references itself twice (WITH x AS (SELECT … expensive …) SELECT * FROM x a JOIN x b …), read the plan, then add MATERIALIZED and read it again. On SQL Server, put NEWID() inside a CTE referenced twice and compare the values you get back.
Expected outcome

Exercise 1: the cursor is typically 50–500× slower and generates far more log records; the single set-based statement is fastest but holds one long transaction and, on SQL Server, escalates to a table lock; the batched version is close to the set-based time with bounded locks and log — which is why it is the production answer. Exercise 2: on PostgreSQL 12+, the CTE is inlined and the expensive subquery may be evaluated twice, so MATERIALIZED can be a genuine optimisation (and NOT MATERIALIZED can be the opposite, when inlining lets predicates push down). On SQL Server the NEWID() CTE returns different GUIDs for the two references, because the CTE is a macro, not a temporary result — a bug that has shipped in a lot of production code.

Interview Q&A

A developer's ORM issues 3,000 queries to render one page. How do you approach it?

First I confirm it with data — pg_stat_statements by call count, or Query Store, rather than the developer's description — because the fix depends on whether it is N+1 lazy loading, a per-row round trip in application code, or a chatty pagination pattern. N+1 is fixed with eager loading (Include/join fetch) or a split query; a per-row loop is fixed by rewriting it as one set-based statement, often with a table-valued parameter or an array parameter to pass the ids in. Then I decide how far to go: an ORM is worth keeping for the 90% of CRUD it does well, and the right architecture is usually "ORM for writes and simple reads, hand-written SQL behind a repository for the queries that matter". What I would push back on is a blanket "rewrite everything in raw SQL" — that trades a measurable problem for an unmeasurable one. I would also add a guardrail: a test or middleware that fails the build when a request exceeds a query-count budget, because this problem always comes back.

Explain the CTE difference between the two engines and why it matters.

Until PostgreSQL 11, a CTE was an optimisation fence: it was always materialised, predicates could not be pushed into it, and people exploited that deliberately to force execution order. PostgreSQL 12 changed the default to inlining for non-recursive, side-effect-free CTEs referenced once, and added MATERIALIZED/NOT MATERIALIZED to control it — which means a query that was fast on 11 can be slow on 12+, or vice versa, and it is a real thing to check during a major upgrade. SQL Server has always inlined CTEs, and the consequence people miss is that a CTE referenced twice may be executed twice: put NEWID(), RAND() or a call to a nondeterministic function inside and you get different values per reference. Where I actually want materialisation on SQL Server, I use a temp table, which also gives the optimizer real statistics on the intermediate result — often the bigger win.

When do you use a window function instead of a self-join or subquery?

Whenever the calculation is "something about this row relative to its group": running totals, rank within a partition, previous/next value, percent of group total, gap-and-island analysis, deduplication by ROW_NUMBER() OVER (PARTITION BY key ORDER BY recency). A self-join computes the same thing by scanning the group once per row; the window function does it in a single ordered pass, so it is usually an order-of-magnitude difference on large partitions. Two nuances worth raising: ROWS versus RANGE in the frame clause changes results when there are ties, and the default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which silently sums all peers — a genuine correctness bug in running-total code. And windows need their ordering to come from somewhere, so a supporting index on (partition_key, order_key) is what turns a good query into a fast one.

What changed for JSON in SQL Server 2025, and how does it compare to jsonb?

Until 2025, JSON in SQL Server was text: you stored nvarchar(max), and every JSON_VALUE parsed the whole document at read time; the standard optimisation was a persisted computed column over JSON_VALUE with an index on it. 2025 introduces a native binary json type plus JSON indexes and the JSON_OBJECTAGG/JSON_ARRAYAGG aggregates, which closes most of the gap. PostgreSQL's jsonb has been binary and GIN-indexable since 9.4, with containment operators and jsonpath, and 16–17 added the SQL-standard constructors and JSON_TABLE. So they are now comparable, and my design advice is the same on both: JSON is for genuinely variable or externally-shaped data, not a way to avoid designing a schema. Columns you filter, join or constrain on should be columns — extract them into generated/computed columns with indexes, and keep the document for the rest.

PostgreSQL 18 made generated columns virtual by default. Why does that matter?

Before 18, GENERATED ALWAYS AS (…) required STORED: the value was computed on write and physically stored, so it could be indexed and read cheaply. 18 adds VIRTUAL, computed on read, and — importantly — makes it the default when neither keyword is given. That matters in two directions. Practically, virtual columns cost nothing to write and no storage, which is right for a value derived cheaply from columns in the same row and read rarely; stored is still right when you need to index it or when the expression is expensive. As a migration hazard, a script written against 12–17 that omits STORED now creates a different kind of column, so anything relying on indexing that column will fail or silently degrade. It is exactly the sort of "new default" change I said earlier matters more than new features.

How do you pass a list of 5,000 ids into a query?

Not by string-concatenating an IN list — that defeats plan reuse, hits parameter and batch-size limits, and is an injection surface. On SQL Server the right tool is a table-valued parameter: a user-defined table type passed from the client, which arrives as a real table the optimizer can join and, with a primary key on the type, estimate properly. On PostgreSQL it is an array parameter with WHERE id = ANY($1), or unnest($1) joined as a table when you need it as a relation — one parameter, one plan, no injection. For very large sets on either engine, a temporary table bulk-loaded first (COPY, SqlBulkCopy) beats both, because you also get statistics and can index it. The estimate is the subtle part: a TVP or array of unknown length is estimated with a fixed guess, so on huge sets I sometimes add OPTION (RECOMPILE) or materialise to a temp table specifically to get a real row count.

What do you flag in code review of a T-SQL stored procedure?

In rough order of how often it matters: missing SET XACT_ABORT ON with explicit transactions and a TRY…CATCH, so a failure leaves an open transaction; string-concatenated dynamic SQL instead of sp_executesql with parameters and QUOTENAME for identifiers; cursors or WHILE loops doing work a single statement could do; NOLOCK anywhere; scalar user-defined functions in a WHERE clause or SELECT list, which historically forced row-by-row execution and killed parallelism (inlined automatically at compat 150+, but only if the function qualifies — check sys.dm_exec_function_stats); implicit type conversions on join or filter columns; SELECT *; and MERGE without HOLDLOCK. Then the design questions: is this transaction as short as it can be, does it do anything non-transactional inside it, and is the error contract clear to the caller. On the PostgreSQL side the list rhymes: SECURITY DEFINER functions without a pinned search_path, missing ON CONFLICT where a race exists, and unbounded DELETEs.

How do you write a query that must return a stable page of results?

Offset pagination (OFFSET 10000 LIMIT 20 / OFFSET … FETCH NEXT) has two problems: cost grows linearly with the offset because the engine must produce and discard those rows, and results shift when rows are inserted or deleted between pages, so users see duplicates and gaps. Keyset (seek) pagination fixes both: order by a unique, stable key — usually (sort_column, id) — and ask for rows after the last key you saw, WHERE (sort_col, id) > ($1, $2) ORDER BY sort_col, id LIMIT 20. PostgreSQL supports that row-comparison form directly; SQL Server needs it expanded into the equivalent OR form or a >= plus tiebreak, which is uglier but the same idea. The cost is that you cannot jump to page 500, which is almost always an acceptable trade for a UI and a mandatory one for an API. I would also insist on a supporting index that exactly matches the order-by, otherwise you have moved the work rather than removed it.

When is a temp table better than a CTE or a subquery?

When you want the optimizer to know how many rows are actually in the intermediate result. A CTE or an inline view is estimated, and if that estimate is wrong the plan above it is wrong; a temp table is materialised with real statistics, so the second half of the query is planned on facts. That is why breaking a monstrous eight-join query into two steps with a #temp in between often produces a dramatic speedup with no other change. It is also the right structure when the intermediate is used several times, or when you want to index it. The costs: tempdb pressure, a recompile when the temp table's statistics change, and the loss of a single atomic statement. On PostgreSQL the equivalent is a real temporary table plus an explicit ANALYZE on it, since PostgreSQL will not analyze it for you — a step almost everyone forgets, and a good detail to mention.

Your team wants to standardise on one dialect across both engines. Good idea?

Only for the boring 80%. Standard SQL covers most CRUD, joins, window functions and aggregation, and writing that portably is nearly free — so a shared style guide and shared review standards are worth having. But forcing portability on the hard 20% means giving up ON CONFLICT, SKIP LOCKED, jsonb operators, APPLY, filtered indexes and Query Store hints, which is where the actual value is. My preferred structure is an abstraction at the repository boundary rather than in the SQL: one interface, two implementations for the handful of engine-specific queries, tested against both. I would also be honest about the real motivation — if it is "we might switch engines one day", that day rarely comes, and paying a permanent tax for an option you will probably never exercise is a bad trade. If it is "we genuinely ship the same product on both", then the abstraction is justified and should be explicit and tested, not accidental.

08 Schema design, constraints and partitioning

Schema is the one decision that is genuinely hard to reverse. Indexes can be added on a Tuesday; a wrong key type or a missing constraint propagates into every application, every report and every integration, and unwinding it is a multi-quarter programme. So this is where lead-level judgment is most visible, and interviewers know it.

Keys: the decision you make once

The choice is between a database-generated sequential key and a client-generated identifier, and it is a distributed-systems question disguised as a data-type question. A bigint from an identity or sequence is 8 bytes, perfectly ordered, cache-friendly, and requires a round trip to the database before the entity has an identity. A UUID is 16 bytes, can be generated anywhere — in the client, in an offline mobile app, in another service — and until recently destroyed index locality. PostgreSQL 18's uuidv7() and SQL Server's NEWSEQUENTIALID() both restore ordering; only uuidv7() also works client-side, which is the point.

-- PostgreSQL: the modern spellings, and the legacy one you will still meet
CREATE TABLE customers (

  public_id  uuid NOT NULL DEFAULT uuidv7() UNIQUE,             -- 18: time-ordered, safe to expose
  email      citext NOT NULL,                                   -- or text + a unique index on lower(email)
  created_at timestamptz NOT NULL DEFAULT now(),                -- ALWAYS timestamptz, never timestamp
  CONSTRAINT customers_email_key UNIQUE (email)
);

Constraints are the cheapest correctness you will ever buy

Both engines let you add a constraint without validating existing rows — PostgreSQL with NOT VALID plus a later VALIDATE CONSTRAINT that takes only a share lock, SQL Server with WITH NOCHECK. These are not equivalent in one crucial way. PostgreSQL's NOT VALID constraint is still enforced for new rows and, once validated, is fully trusted. SQL Server's WITH NOCHECK leaves the constraint untrusted (sys.check_constraints.is_not_trusted = 1), and an untrusted constraint is ignored by the optimizer — so you lose the join eliminations and predicate simplifications a trusted foreign key gives you, permanently, until someone runs ALTER TABLE … WITH CHECK CHECK CONSTRAINT …. Auditing for untrusted constraints is a genuinely valuable ten-minute job on an inherited SQL Server database.

PostgreSQL 18 adds a third mode: NOT ENFORCED constraints, which are declared and visible to tools but never checked. That is for documenting a relationship the application guarantees, and it should make you nervous for the same reason SQL Server's untrusted constraints should — the optimizer cannot rely on it either.

-- PostgreSQL: add a foreign key to a huge table without a long lock
ALTER TABLE orders ADD CONSTRAINT fk_orders_customer
  FOREIGN KEY (customer_id) REFERENCES customers(id) NOT VALID;   -- brief lock, enforced from now on
ALTER TABLE orders VALIDATE CONSTRAINT fk_orders_customer;        -- scans, but only SHARE UPDATE EXCLUSIVE

-- Exclusion constraint: no two bookings for the same room may overlap
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE bookings ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (room_id WITH =, during WITH &&);

-- PostgreSQL 18: the SQL-standard temporal form of the same idea
CREATE TABLE bookings18 (
  room_id int,
  during  tstzrange,

-- SQL Server: find constraints the optimizer is quietly ignoring
SELECT OBJECT_NAME(parent_object_id) AS tbl, name, 'FK' AS kind

SELECT OBJECT_NAME(parent_object_id), name, 'CHECK'
FROM   sys.check_constraints WHERE is_not_trusted = 1 AND is_disabled = 0;

-- Make them trusted again (this scans, so batch it into a maintenance window)
ALTER TABLE dbo.orders WITH CHECK CHECK CONSTRAINT FK_orders_customer;

Partitioning

Partitioning is a data-management feature that sometimes helps performance — the order of that sentence matters, because candidates who pitch it as a performance feature usually get the follow-up wrong. What it reliably buys you is instant archival and load: ALTER TABLE … SWITCH on SQL Server and ATTACH/DETACH PARTITION on PostgreSQL are metadata operations, so dropping a month of history is a second rather than a six-hour DELETE. It also gives you per-partition statistics, per-partition maintenance, per-partition lock escalation on SQL Server, and partition pruning when the partition key is in the predicate.

Interview trap

"We'll partition the table to make queries faster." Partitioning makes queries faster only when the partition key is in the predicate and pruning actually happens; otherwise you have replaced one B-tree with fifty smaller B-trees and the planner now has to consider all of them, which is measurably slower. Worse, on PostgreSQL every unique constraint must include the partition key, so a table partitioned by created_at can no longer have a plain unique constraint on email — a requirement that has forced more than one team to unwind a partitioning project late. Two hundred partitions is comfortable; several thousand starts to cost planning time and lock-table entries. The right pitch is: partition when you need cheap archival or per-partition maintenance on a table measured in hundreds of gigabytes, and when almost every query filters on the partition key.

Try it

  1. Build a range-partitioned events table by month on PostgreSQL with 24 partitions. Run a query with and without a created_at predicate and compare the plans; then drop a month with DETACH PARTITION and time it against DELETE FROM events WHERE created_at < ….
  2. On SQL Server, create the same by partition function/scheme, load a staging table with identical structure and aligned indexes, and SWITCH IN. Then deliberately mismatch one index and observe the error.
Expected outcome

With the predicate you will see Subplans Removed: 23 (PostgreSQL) or an actual partition count of 1 (SQL Server); without it, every partition is scanned and the query is slower than the unpartitioned equivalent because of the per-partition overhead. DETACH PARTITION completes in milliseconds regardless of size and generates no WAL for the data; the DELETE takes minutes to hours, writes as much log as data, and leaves the space as bloat until vacuum. The SQL Server mismatch produces a precise error naming the difference — which is the real lesson: SWITCH is metadata-only because the engine verifies structural identity up front, so partition switching is only as easy as your discipline about keeping the staging table in lockstep.

Interview Q&A

bigint identity or UUID for primary keys? Defend your answer.

My default is bigint from an identity or sequence: 8 bytes, ordered, cheap in every index, and it makes debugging and support conversations easy. I move to a UUID when identity must be created away from the database — offline clients, multiple services generating rows that later merge, or an idempotency key that the caller supplies — and then I use uuidv7() on PostgreSQL 18 or NEWSEQUENTIALID() on SQL Server so I keep index locality. The nuance I would raise is that these are two different questions: the physical key and the identifier you expose. A perfectly good design is a bigint clustered primary key plus an indexed uuid "public id" in the API, which gives you compact internal joins and non-enumerable external ids. And if unguessability is a security control, it must be v4 — v7's timestamp prefix is by design not random.

What is the single biggest gotcha migrating SQL Server to PostgreSQL?

Collation. SQL Server databases are overwhelmingly created with a case-insensitive, accent-sensitive collation, so WHERE email = 'Bob@x.com' matches bob@x.com, unique constraints treat the two as duplicates, and ORDER BY ignores case. PostgreSQL is case-sensitive by default. The migration therefore silently changes the meaning of a large fraction of the application's queries and constraints, and the failures are logic errors rather than syntax errors — logins that stop working, duplicates that suddenly insert, sort orders that change. The remedies are citext, a unique index on lower(email) with normalisation at write time, or a case-insensitive ICU collation, and my strong preference is normalising at write time because it keeps the index a plain B-tree and the semantics explicit. Second place goes to datetime/timestamp handling and third to identity/sequence semantics, but collation is the one that produces silent wrong answers.

timestamptz or timestamp? Make the case.

timestamptz, essentially always, for anything representing an instant. It does not store a time zone — it stores UTC and converts to the session's zone on input and output — which is exactly what you want, because "the moment this happened" is absolute and its rendering is a presentation concern. timestamp (without zone) is only right for a genuinely zoneless wall-clock value: a recurring 09:00 alarm, a date-of-birth-like local time. Getting this wrong is insidious because it works until a daylight-saving boundary or a second deployment region. The SQL Server equivalent conversation is datetime2 versus datetimeoffset: datetime2 is naive, so the discipline is to store UTC everywhere and be rigorous about it, or use datetimeoffset when the originating offset itself is data. And in both, avoid the legacy types — datetime has 3.33 ms rounding that makes range predicates subtly wrong.

How do you model soft deletes without ruining the schema?

First I ask whether it is really deletion or really a state machine — most "soft delete" requirements are actually "archived", "cancelled" or "superseded", and naming the state properly prevents a lot of confusion. Given a deleted_at column, the three things I insist on are: a partial or filtered index on the active rows so the common query stays cheap; unique constraints that account for it, which is where the engines diverge sharply, because PostgreSQL allows many NULLs in a unique index (so UNIQUE (email, deleted_at) does not do what you want, and you need a partial unique index WHERE deleted_at IS NULL) while SQL Server allows only one NULL and needs a filtered unique index; and a view or a repository layer so no developer ever forgets the predicate. The alternative worth considering is moving deleted rows to a history table, which keeps the hot table small and the constraints simple, at the cost of an extra write path.

When do foreign keys become a problem, and would you ever drop them?

They cost on write — each insert or update of a child row takes a lock on the parent to check the reference, which under high concurrency on a hot parent row becomes contention, and cascading deletes can turn one statement into an enormous one. They also complicate partitioning, bulk loads and partition switching. But dropping them is almost always the wrong trade: they are what lets the optimizer eliminate joins it can prove are unnecessary, they are the only durable guarantee against orphaned rows, and every team that has removed them has discovered the orphans later. What I do instead is index every foreign key column (SQL Server does not do this for you and unindexed FKs make cascades and parent deletes catastrophically slow), avoid cascading deletes in favour of explicit application logic, and use NOT VALID/deferred validation to add them without downtime. The one legitimate exception is a bulk-load window where I disable and then re-validate — and re-validate is not optional, or on SQL Server you have left an untrusted constraint behind.

How would you design multi-tenancy?

Three models, and the choice is about the blast radius you can tolerate. A shared schema with a tenant_id column on every table is cheapest to operate and hardest to get isolation right — it needs tenant_id as the leading column of nearly every index, ideally the clustering key on SQL Server, and row-level security as a backstop so one missing predicate is not a data breach. Schema-per-tenant gives clean separation and per-tenant restore, but tens of thousands of schemas is a catalog-bloat and migration nightmare — every deployment now touches N schemas. Database-per-tenant gives the best isolation, per-tenant backup and restore, and per-tenant scaling, at the cost of connection-pool fragmentation and operational multiplication; it is the right answer for a small number of large enterprise tenants, and Azure SQL elastic pools exist precisely to make it economical. I usually recommend shared schema with RLS plus the ability to promote a large tenant to its own database, because it lets you start cheap without foreclosing the escape.

Explain PostgreSQL's collation-version problem.

PostgreSQL delegates string comparison to a collation provider, historically the operating system's libc. When glibc changed its collation rules in version 2.28, the sort order of strings changed — so every B-tree index built on a text column under the old rules became silently corrupt on the new OS: lookups miss rows that are physically present. This bites during OS upgrades and container base-image bumps, not database upgrades, which is what makes it so dangerous. PostgreSQL now records datcollversion/collversion and warns when it detects a mismatch, and the remedy is REINDEX of every affected text index. The modern mitigation is to use the ICU provider, which is versioned explicitly and travels with the database rather than the OS, or the built-in C.UTF-8 provider added in 17 for the cases where you only need byte ordering. I would raise this unprompted in any conversation about running PostgreSQL on containers, because "we upgraded the base image" is a very ordinary thing to do.

How do you decide the partition key and granularity?

The key must be the column that appears in almost every query's predicate and that also defines the lifecycle — which for the overwhelming majority of cases is a timestamp. Granularity is then a trade-off between partition count and partition size: I aim for partitions of a few tens of gigabytes and a total in the low hundreds, so monthly for a table growing a few hundred gigabytes a year, daily for one growing that per month. Too many partitions costs planning time, lock-manager entries and catalog bloat on PostgreSQL; too few means the archival unit is too coarse to be useful. I also check the constraint consequences before committing — on PostgreSQL every unique key must include the partition key, which sometimes kills the design outright — and I automate creation ahead of time (pg_partman, or a scheduled job), because the classic partitioning incident is the night nobody created next month's partition and inserts started failing.

What is your position on database-enforced business rules versus application-enforced?

Invariants that must hold regardless of who writes belong in the database: uniqueness, referential integrity, domain checks, non-overlapping ranges. They are declarative, they cannot be forgotten by the next service that writes to the table, and they survive bulk loads and manual fixes at 3am — which is exactly when they matter. Complex, changeable, workflow-dependent rules belong in the application, because they need testing, versioning and readable error messages, and encoding them as triggers produces a system nobody can reason about. The line I draw is: if violating it corrupts data, the database enforces it; if violating it is a business decision, the application decides. I would also point out the optimizer benefit, which people forget — a trusted foreign key or check constraint lets the engine eliminate joins and simplify predicates, so constraints are a performance feature as well as a correctness one.

You inherit a database with no constraints and no documentation. First week?

I would spend it building a map, not changing anything. Profile the data to discover the implied constraints: which columns are actually unique, which are never null, which pairs behave as foreign keys, what the cardinalities are — a few hours of queries tells you more than any document. In parallel I capture the workload (Query Store or pg_stat_statements) so I know which twenty queries matter, and I check the fundamentals that could be actively dangerous: last successful backup and last successful restore test, last DBCC CHECKDB, autovacuum health, untrusted constraints, unused and duplicate indexes. Then I would add constraints incrementally, starting with the ones the data already satisfies, using NOT VALID/NOCHECK-then-validate so nothing blocks. The critical discipline is that every constraint I add must be validated, and I would write the profiling queries down as a repeatable script — because the second and third inherited database will need the same map.

09 Schema change and migrations without downtime

Section 08 was what the schema should be; this is how you get there while the system is serving traffic. It is the area where a lead is most obviously distinguishable from a strong senior, because the correct answers are procedural — expand/contract, lock timeouts, batched backfills, N-1 compatibility — rather than syntactic.

The governing physics: DDL takes locks, and locks queue

The non-obvious killer on PostgreSQL is lock queueing. ALTER TABLE requests an ACCESS EXCLUSIVE lock. If a long-running SELECT holds an ACCESS SHARE lock, the ALTER waits — and every subsequent query, including trivial reads, queues behind the pending ALTER, because lock requests are granted in order. So a migration that would have taken 2 ms takes down the application for as long as that one analytics query runs. The mitigation is a one-line habit and everyone should know it:

-- PostgreSQL: never run migration DDL without these
SET lock_timeout = '3s';          -- fail fast instead of building a queue behind us
SET statement_timeout = '30s';
ALTER TABLE orders ADD COLUMN discount_code text;   -- retry the whole thing on failure

-- Metadata-only since 11: a non-volatile default no longer rewrites the table
ALTER TABLE orders ADD COLUMN currency text NOT NULL DEFAULT 'EUR';

-- Adding NOT NULL to an existing column: two-phase, no long lock (18 allows NOT VALID here)
ALTER TABLE orders ADD CONSTRAINT orders_email_nn CHECK (email IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_email_nn;   -- SHARE UPDATE EXCLUSIVE, concurrent-safe
-- then, cheaply, promote it:
ALTER TABLE orders ALTER COLUMN email SET NOT NULL;       -- uses the validated CHECK, no full scan

Expand / contract, in concrete steps

The pattern that makes every non-trivial schema change safe. Renaming customers.name to full_name, for example, is not one migration; it is five deployments:

  1. Expand. Add full_name as nullable. No default, no constraint, metadata-only. Deploy.
  2. Dual write. Application writes both columns; reads still come from name. Deploy. (A trigger can do this instead if you cannot change all writers, but a trigger is a hidden write path and I would rather change the code.)
  3. Backfill. Batched update of historical rows, a few thousand at a time, keyed on the primary key, with a pause between batches and a check on replication lag. Not a deployment — a job.
  4. Switch reads. Application reads full_name, still writes both. Deploy, and now you can roll back safely because both columns are current.
  5. Contract. Stop writing name, add the NOT NULL constraint on full_name via the two-phase route, and drop name in a later release once you are certain nothing reads it.

Every step is independently deployable and independently reversible, and at no point is the application incompatible with the database. That last property — the database must be compatible with both the currently deployed application and the next one — is the whole rule; everything else is a technique for satisfying it.

-- The backfill loop, PostgreSQL. Bounded batches, keyset-driven, replica-aware.
DO $$
DECLARE last_id bigint := 0; n int;
BEGIN
  LOOP
    WITH batch AS (
      SELECT id FROM customers WHERE id > last_id AND full_name IS NULL
      ORDER BY id LIMIT 5000 FOR UPDATE SKIP LOCKED
    )
    UPDATE customers c SET full_name = c.name
    FROM batch b WHERE c.id = b.id
    RETURNING c.id INTO last_id;      -- illustrative; in practice capture max(id) and row count
    GET DIAGNOSTICS n = ROW_COUNT;
    EXIT WHEN n = 0;
    COMMIT;                            -- procedures can commit; a DO block cannot — use a procedure
    PERFORM pg_sleep(0.05);            -- let autovacuum and replicas breathe
  END LOOP;
END $$;
-- The same loop in T-SQL, with the two things people forget:
-- a bounded batch driven by the clustered key, and a delay so log backups and AGs keep up.
DECLARE @last bigint = 0, @n int = 1;
WHILE @n > 0
BEGIN
    UPDATE TOP (5000) c
    SET    c.full_name = c.name, @last = c.id
    FROM   dbo.customers c WITH (ROWLOCK, READPAST)
    WHERE  c.id > @last AND c.full_name IS NULL;
    SET @n = @@ROWCOUNT;
    WAITFOR DELAY '00:00:00.100';
END

Interview trap

Letting the ORM's migration tool run DDL automatically at application startup. It looks tidy and it fails in exactly the ways that matter: several application instances start simultaneously and race on the same migration; the migration runs with the application's credentials, so that account needs DDL rights permanently, which is a security finding; a long-running migration blocks the health check and the orchestrator kills the pod mid-DDL; and there is no lock timeout, so the first slow query turns a deploy into an outage. The professional shape is: generate an idempotent SQL script from the tool (dotnet ef migrations script --idempotent, Flyway, Liquibase), review it like code, run it as a separate pipeline step with a distinct high-privilege identity and an explicit lock timeout, and let the application start only after it succeeds. The related trap is data motion inside a migration — a migration that backfills ten million rows will time out, and it belongs in a separate, restartable job.

Try it

  1. PostgreSQL: open a transaction running SELECT pg_sleep(60) FROM orders LIMIT 1, then in a second session run ALTER TABLE orders ADD COLUMN x int;, then in a third session run SELECT count(*) FROM orders. Observe. Repeat with SET lock_timeout = '2s' in session two.
  2. SQL Server: add a NOT NULL column with a default to a 20M-row table on Standard edition and on Developer (Enterprise) edition, and compare duration and log growth.
Expected outcome

Exercise 1: session three blocks — even though it only wants a shared lock and session one already holds a compatible one — because the pending ACCESS EXCLUSIVE request sits between them in the queue. That is the entire mechanism behind "a harmless migration took the site down", and demonstrating it once makes the lock_timeout habit permanent. With the timeout set, the ALTER gives up after two seconds and nothing else is affected; you retry, possibly in a loop with jitter. Exercise 2: on Enterprise the operation is metadata-only and finishes in milliseconds; on Standard it is a full table rewrite generating gigabytes of log. Edition-dependent behaviour on a DDL statement is exactly the kind of thing that makes a staging environment on a different edition worse than useless.

Interview Q&A

Take me through a zero-downtime column rename.

It is never a rename; it is expand, dual-write, backfill, switch reads, contract, across at least three deployments. Add the new nullable column (metadata-only), deploy code that writes both, backfill history in bounded batches as a separate restartable job, deploy code that reads the new column while still writing both, and only then stop writing the old column and drop it in a later release. The property that makes it safe is that the database is simultaneously compatible with the currently running application and the one about to be deployed, so any single step can be rolled back without a data migration. I would also point out what makes it fail in practice: forgetting a writer (a reporting job, an integration, a stored procedure), and dropping the old column too eagerly — I leave it in place for at least one full release cycle and confirm zero reads with logging or extended events before dropping it.

Why is CREATE INDEX CONCURRENTLY not a free lunch?

It takes roughly twice as long because it makes two passes over the table, and between them it waits for every transaction that started before it to finish — so one long-running transaction stalls it indefinitely, and it looks hung when it is actually waiting. It cannot run inside a transaction block, which means your migration tool must be told to run it outside one. And if it fails or is cancelled, it leaves behind an INVALID index that is fully maintained on every write but never used for reads — pure cost — so any automation must check pg_index.indisvalid and drop-and-recreate. It also cannot be used to create a primary key directly; the trick is to build a unique index concurrently and then ALTER TABLE … ADD CONSTRAINT … PRIMARY KEY USING INDEX. None of this makes it the wrong tool — it is the only safe tool on a live table — but "concurrently" means "does not block", not "free".

How do you back-fill 500 million rows safely?

Bounded batches of a few thousand rows, driven by the primary key so each batch is a contiguous range and the loop is restartable from a checkpoint, with a small delay between batches. The delay is not superstition: it lets log backups, replication and autovacuum keep up, and it gives foreground traffic a window. I make the job idempotent (a WHERE new_col IS NULL predicate does that naturally) and restartable, run it from outside the deployment pipeline so a slow backfill never blocks a release, and instrument it with progress plus a kill switch. Then I watch the right signals while it runs: replication lag, log space or WAL generation rate, dead-tuple growth on PostgreSQL, and tempdb/version-store size on SQL Server. If it is a very large table and this is a recurring shape, I would consider writing to a new table and swapping it in instead — on a partitioned table that swap is metadata-only.

State-based (DACPAC/SSDT) or migration-based tooling?

Migration-based for anything with real data, because the ordered scripts are the artefact you review, test and roll back, and because data motion, backfills and expand/contract simply cannot be expressed as a desired end state. State-based tools are seductive — the schema in source control looks like the truth — but the deployment diff is generated at deploy time by a tool that cannot know your data, and its idea of "change this column's type" is frequently a table rebuild or a drop-and-create. Where state-based tooling earns its place is drift detection and greenfield or read-only databases, and the hybrid I have seen work is: migrations are the source of truth for change, and a state comparison runs in CI purely to detect that someone changed production by hand. Whatever the choice, the non-negotiables are the same: the script is reviewed, it is tested against a production-sized copy, and it is idempotent.

How do you test a migration before production?

Against a restored copy of production at production size, not against a seeded development database — because everything that goes wrong here is a function of data volume and concurrency. I time it, capture the log/WAL it generates, and check the lock it takes. Then I test it under load, ideally by replaying captured traffic, because the interesting failure is not "does the DDL work" but "does the DDL work while 500 sessions are querying the table". I also test the rollback, which is the step teams skip, and I write down the abort criteria in the change ticket: how long is too long, what I watch, and what I do at that point. For high-risk changes I would run the migration on a replica first where possible, or use a blue/green cutover so the fallback is a routing change rather than a reverse migration.

What is your rollback plan when a migration is not reversible?

I try very hard to make it reversible by construction, which is exactly what expand/contract buys: every step until the final drop is a no-op to reverse. For the genuinely irreversible ones — a destructive type change, a data transformation that loses information, a drop — the plan is a verified backup or snapshot taken immediately before, with the restore time measured rather than assumed, plus a decision point written down: how long we give it before we restore, and who makes that call. On PostgreSQL a filesystem or cloud snapshot plus WAL archiving gives point-in-time recovery to the second before the migration; on SQL Server a full backup plus log backups gives STOPAT, or a database snapshot if the change is short-lived, since reverting from a snapshot is far faster than a restore. And I would say the uncomfortable part out loud: if the restore would take four hours and the business cannot tolerate four hours, then the migration must be split until each step is individually reversible.

How do you do a major-version upgrade of PostgreSQL with minimal downtime?

Three options with very different downtime. pg_dump/restore is simplest and scales terribly — hours for a large database. pg_upgrade --link is the usual answer: it hard-links the data files instead of copying them, so downtime is minutes regardless of size, and as of 18 it also carries optimizer statistics across, which removes the post-upgrade slowness cliff (extended statistics are still not carried, so I script an ANALYZE for those tables). For near-zero downtime, logical replication: build the new-version cluster as a subscriber, let it catch up, then cut over in a few seconds of connection draining — 17's pg_createsubscriber makes converting a physical standby into a logical subscriber dramatically easier, and 16 allowed logical decoding from a standby so you can build it without loading the primary. The caveats worth naming: logical replication does not replicate DDL or sequences automatically, so sequence values must be advanced at cutover, and large objects and tables without a replica identity need special handling.

Who should own database migrations — developers or DBAs?

Developers write them, because they know the intent and the application compatibility; a specialist reviews them, because they know the locking and the data volumes; and the pipeline runs them, because humans running scripts by hand is how environments drift. What I insist on is the review gate, not the ownership: a checklist covering lock behaviour, expected duration on production data volume, whether it is metadata-only, whether a backfill is separated out, whether the application is compatible in both directions, and what the rollback is. That gate scales, whereas a DBA-writes-everything model becomes the bottleneck and a nobody-reviews model produces the 3am incident. Where the organisation has no DBA, I would encode as much of the checklist as possible into automation — a linter that rejects ALTER TABLE without a lock timeout is cheap and catches the most common mistake.

What is a blue/green database deployment and when is it worth it?

You run two database environments, replicate from the live one to the new one, cut traffic over at a routing layer, and keep the old one warm so rollback is another routing change rather than a restore. It is worth it for changes that cannot be made incrementally — a major version upgrade, a storage or region migration, a large-scale restructuring — and it is what AWS's Blue/Green Deployments and the equivalent logical-replication patterns automate. The hard parts are the ones people underestimate: writes that arrive during the cutover window, sequence and identity values on the green side, replication lag at the moment of switch, and reverse replication if you want a real rollback path rather than a theoretical one. My rule is that blue/green is for changes measured in hours of risk; anything that expand/contract can express should use expand/contract instead, because it is cheaper and the rollback is proven by construction.

How do you introduce migration discipline to a team that has never had it?

Start with the incident, not the process. Find the last outage or near-miss caused by a schema change, walk through what would have prevented it, and let that motivate exactly one rule — usually "no DDL without a lock timeout" or "migrations run in the pipeline, not at app startup". Automate that rule so compliance is the default rather than a memory test. Then add the next rule after the next near-miss, and keep the total small enough that people can recite it. In parallel I would make the safe path the easy path: a template migration script with the timeouts already in it, a batched-backfill helper, and a staging environment restored from production so testing at real volume takes no effort. What does not work is arriving with a twelve-point checklist and a policy document; teams route around process they did not help write, and you end up with the same changes happening in a SQL client at 2am, unreviewed.

10 High availability, replication and recovery

Start every HA conversation with two numbers, because interviewers are listening for whether you lead with technology or with requirements. RPO is how much data you can afford to lose; it is determined by how often changes leave the primary durably. RTO is how long you can afford to be down; it is determined by detection plus decision plus recovery. Every technology below is just a way of buying a particular RPO/RTO at a particular cost, and the most common architectural mistake is buying availability (a replica) and calling it durability (a backup).

The two philosophies

SQL Server ships a complete, integrated HA product: Always On availability groups do failure detection, quorum, automatic failover, readable secondaries and read-only routing, all configured from the engine. PostgreSQL ships the replication primitives — WAL streaming, synchronous commit levels, replication slots, hot standby — and deliberately leaves failover orchestration to external software, because promoting a standby is a policy decision that requires a distributed consensus the database does not want to own. That is why every serious PostgreSQL deployment includes Patroni with etcd/Consul, repmgr, pg_auto_failover, or CloudNativePG on Kubernetes. If a candidate says "PostgreSQL has automatic failover", the follow-up will be "shipped by whom", and the honest answer is "not by core".

Interview trap

Confusing replication with backup. A synchronous replica protects you from a node failing; it does not protect you from DELETE FROM orders with a missing WHERE, because that statement replicates faithfully and instantly to every replica you own. Ransomware and a bad migration are the same category. You need point-in-time recovery — a base/full backup plus a continuous log or WAL archive — and it must be immutable or at least on separate credentials, which is exactly why SQL Server 2025 added backup to immutable blob storage. The second half of the trap: an untested backup is a hypothesis. The only real question is "when did you last restore it, and how long did it take", and I would treat a documented, timed, scheduled restore rehearsal as a hard requirement rather than a nice-to-have. If nobody can answer that question, that is the first thing I fix on any estate I inherit.

Try it

  1. Build a PostgreSQL primary plus one standby with a physical replication slot. Stop the standby, generate WAL on the primary, and watch retained_wal grow. Then set max_slot_wal_keep_size and repeat to see the slot get invalidated instead of filling the disk.
  2. Do a full recovery drill on either engine: restore last night's backup to a new instance, roll forward to a chosen timestamp, and record the wall-clock time from "decision" to "application connected". Compare that number to the RTO in your SLA.
What you learn

Exercise 1: the slot faithfully retains every WAL segment for a standby that no longer exists, and the primary's disk fills — an entirely self-inflicted outage that has taken down many production clusters. With max_slot_wal_keep_size the slot is marked invalid instead, and you lose the standby rather than the primary, which is the correct trade. Exercise 2: the number is almost always several times what people assume, because the assumed number is restore time while the real one includes locating the backup, provisioning storage, applying logs, rebuilding indexes on a cold cache, and the twenty minutes of deciding to do it. That gap, written down, is the most persuasive artefact you can bring to a conversation about DR budget.

Interview Q&A

Define RPO and RTO and derive an architecture from them.

RPO is the maximum acceptable data loss, RTO the maximum acceptable downtime. If RPO is zero you need synchronous replication — an AG synchronous-commit replica, or PostgreSQL synchronous_commit = on with a named standby — and you must accept that every commit now pays a network round trip, so the replica needs to be close and the link needs to be reliable, or your write latency becomes the WAN's latency. If RPO is fifteen minutes, asynchronous replication plus log shipping every five minutes is far cheaper and survives a cross-region link. If RTO is under a minute you need automatic failover with a health model and a client that reconnects — a listener with multi-subnet failover on SQL Server, or a Patroni-managed VIP/HAProxy on PostgreSQL — because a human paging in cannot meet that. If RTO is four hours, a restore procedure is enough. The discipline is to make the business state both numbers per system rather than "always up", because different systems genuinely deserve different money.

What breaks when you enable synchronous commit?

Write latency becomes primary-commit plus network plus standby-flush, so a 1 ms commit across a 10 ms link becomes an 11 ms commit, and any workload doing many small transactions feels it immediately. Worse, availability now depends on the standby: with a single synchronous standby on PostgreSQL, if it dies, commits hang until it returns or you change synchronous_standby_names — you have bought durability and lost availability. The fixes are quorum commit (ANY 2 (s1,s2,s3)) so any one node can fail, and on SQL Server keeping at least two synchronous replicas so automatic failover remains possible. The subtler point I would raise is what synchronous actually guarantees: PostgreSQL's default on means the standby has flushed the WAL, not applied it, so a read on the standby immediately after commit can still miss the row — remote_apply guarantees visibility, at a further latency cost.

How do you use readable secondaries without breaking the primary?

Understand the conflict first. On PostgreSQL, a long query on a hot standby conflicts with the primary's vacuum removing rows the query still needs; the default is to cancel the standby query after max_standby_streaming_delay, and the alternative, hot_standby_feedback = on, holds the primary's xmin horizon back so the primary bloats instead. You must pick which side pays, per replica — so I would run reporting on a dedicated replica with feedback on and accept the bloat, keep the HA replica with feedback off, and monitor both. On SQL Server, readable secondaries add row-versioning overhead on the primary (a 14-byte version tag per row) and push the version store into the secondary's tempdb; long reports there also delay ghost cleanup on the primary. Then there is the application-level issue on both: replicas are behind, so read-your-writes breaks, and the fix is routing writes and subsequent reads for the same user to the primary for a bounded window rather than pretending the lag is zero.

Explain PostgreSQL replication slots and their failure mode.

A slot is the primary's record of how far a consumer — a physical standby or a logical subscriber — has got, and it guarantees the primary retains the WAL that consumer still needs. That guarantee is the feature and the failure mode: if the consumer disappears without the slot being dropped, the primary retains WAL forever and fills its disk, which is a primary outage caused by a dead replica. It also holds back the xmin horizon for logical slots, so vacuum stops reclaiming. The controls are max_slot_wal_keep_size (13+), which invalidates the slot instead of filling the disk, and monitoring retained WAL per slot as a first-class alert. The counter-argument to running without slots is real too — wal_keep_size alone can let a standby fall irrecoverably behind — so the answer is slots plus a bound plus monitoring, not one or the other.

When would you choose logical replication over physical?

When you need selectivity or heterogeneity: replicating a subset of tables, filtering rows or columns (15+), feeding a different major version, or feeding something that is not PostgreSQL at all. The two cases where it is transformative are near-zero-downtime major upgrades — build an 18 subscriber from a 15 publisher, catch up, cut over in seconds — and blue/green migrations. Physical replication remains the right default for HA and DR because it is byte-identical, cheaper, and cannot drift. The caveats to state: logical replication does not replicate DDL or sequence values, tables need a replica identity (a primary key, or REPLICA IDENTITY FULL which is expensive), large objects are not supported, and initial synchronisation of a huge table is a real load. 16's ability to decode from a standby and 17's failover slots plus pg_createsubscriber have removed the worst of the operational friction.

Describe a solid backup strategy for each engine.

SQL Server: full recovery model for anything where losing an hour is unacceptable, weekly full plus daily differential plus log backups every 5–15 minutes, all with CHECKSUM, compressed (ZSTD from 2025), written to storage with separate credentials — immutable blob storage if available — and a retention policy that survives a ransomware dwell time, meaning weeks not days. Verify with RESTORE VERIFYONLY and, more importantly, with an automated restore to a scratch instance that also runs DBCC CHECKDB there rather than on production. PostgreSQL: pgBackRest or Barman rather than hand-rolled archive_command scripts, full plus incremental (17 added incremental base backups in core too), continuous WAL archiving for PITR, retention enforced by the tool, and the same automated restore rehearsal. On both, the two questions I would want answered on a dashboard are "how old is the newest recoverable point" and "when did a restore last succeed".

An availability group failed over at 3am. What do you check first?

First, is the application actually healthy on the new primary — connections routed, no orphaned users, the workload running — because restoring service beats explaining it. Then why it happened: the cluster log and sys.dm_hadr_availability_replica_states for the health event, and whether the trigger was a genuine node failure, a lease/health-check timeout (frequently caused by the instance being unresponsive under memory or scheduler pressure rather than actually dead), or a network partition. Then the state left behind: is the old primary now a healthy secondary or is it stuck resolving, is the synchronisation state healthy, has the redo queue on the remaining secondaries caught up, and are backups still being taken from the right node. SQL Server 2025 helps here with improved health-check timeout diagnostics and a RestartThreshold = 0 option for immediate failover on persistent health issues, which is worth knowing about. Finally, the boring but decisive question: did we lose data, which for an async replica means checking the log send queue at the moment of failure.

How do you handle read-your-writes with replicas?

Accept that the replica is behind and design for it rather than hoping. The simplest robust pattern is sticky routing: after a write, route that user's reads to the primary for a bounded window — a few seconds, tracked in the session or a cookie. A more precise version uses the log position: capture the LSN at commit (pg_current_wal_insert_lsn(), or the equivalent on SQL Server) and route the read to a replica only if it has replayed past it, otherwise fall back to the primary. At the application level you can also avoid the problem by returning the written entity from the write itself instead of re-reading it, which removes an entire class of bug for free. What I would not do is quietly accept an eventually-consistent read path for a user-facing flow that reads immediately after writing, because the resulting bug reports ("I saved it and it vanished") are expensive and intermittent, and the team will spend months on them.

What does Patroni actually do, and what do you own if you run it?

Patroni turns a set of PostgreSQL nodes into a managed cluster by putting the cluster state in a distributed consensus store — etcd, Consul or ZooKeeper — and having each node's agent enforce it: leader election with a TTL lease, automatic promotion of the most advanced standby, reconfiguration of the others to follow, and a REST API that a proxy such as HAProxy or a connection router can poll to find the current leader. What you own is everything around it: the consensus store's own quorum and operational health (this is now a distributed system with its own failure modes), the connection routing layer, fencing so a partitioned old primary cannot accept writes, the promotion policy including whether you allow failover to a lagging replica, and testing all of it. Kubernetes users generally get this bundled through CloudNativePG, which is the closest thing to "PostgreSQL HA that ships as a product". The honest framing for an interview: PostgreSQL HA is achievable and well-trodden, but it is an assembly, and the assembly is the job.

How do you protect against an accidental destructive statement?

Layered, because no single control is sufficient. Prevention: application accounts have no DELETE on tables they should not delete from and no DDL at all; humans do not have standing write access to production but request it through just-in-time elevation; a client configured to require explicit transactions so a bare DELETE is not auto-committed; and a review gate for scripts run against production. Detection: auditing on the destructive operations, and alerts on unusual row-change volume. Recovery: PITR that can land on the second before the statement, tested; on SQL Server a database snapshot before a risky operation gives a very fast revert; on PostgreSQL a filesystem or cloud snapshot does the same. And the process control that matters most in practice: soft-delete or a two-step archive for the operations that people actually run by hand, so the destructive version is never the convenient one. I would also make sure the runbook says who authorises a restore, because the delay in an incident is almost never technical.

Interview trap

Treating high CPU or high disk as the diagnosis. They are symptoms, and both are usually caused by the same thing: reading far more data than necessary because of a bad plan or a missing index. The candidate who says "we added more CPU" has usually paid a monthly bill to avoid a one-hour fix — and once the workload grows another 30%, they pay again. The related trap is tuning from averages: a query averaging 20 ms over a million calls costs more total time than a 4-second report run twice a day, and the report is what everyone complains about. So sort by total_exec_time or duration × executions, not by mean, and then check the p99 separately because averages hide the parameter-sniffing bimodality from section 04. Interview Q&A

Give me your triage sequence for "the database is slow".

First, define slow and scope it: everything or one feature, since when, and does it correlate with a deploy, a data volume threshold, or a schedule. Then look at waits over a recent window rather than cumulative, because that tells me the category — I/O, locking, CPU, memory, log. In parallel, check the cheap environmental facts: is a replica down or lagging, has a job or a backup gone long, is storage latency normal, did a failover happen, is autovacuum blocked. Then, and only then, the query level: top queries by total time from Query Store or pg_stat_statements, and the plan for the offender. Mitigate before root cause if there is an obvious safe lever — force a known-good plan, kill a runaway session, update statistics — but capture evidence first. And I would say out loud what I am not doing: I am not restarting the instance, because that destroys the evidence and usually returns the problem an hour later.

What do you put in place before you need it?

Five things, and I would call them non-negotiable. A query-level flight recorder: Query Store on with tuned capture and retention, or pg_stat_statements plus auto_explain in shared_preload_libraries with a sampled log_analyze. Wait statistics sampled into a time series so I can compare today to last Tuesday. A small set of health metrics with alerts that fire hours before an outage: oldest transaction, replication lag, tempdb/version store or dead-tuple ratio and relfrozenxid age, log/WAL space, backup age. Slow-query and lock-wait logging with thresholds that produce a readable log rather than a firehose. And a baseline: what normal looks like for throughput, latency and cache hit ratio, because "is this bad?" is unanswerable without it. Everything else is nice to have; without these you are diagnosing from anecdotes.

How do you decide between fixing a query and adding hardware?

I quantify the query's cost in resource terms — logical reads or buffers per execution, times executions per hour — and compare it to the total. If one query is 40% of your reads and can be made 100× cheaper with an index, hardware is a bad trade. If the workload is broadly efficient and simply larger than the machine, hardware is the right answer and I would rather spend a week's engineering time elsewhere. The tie-breaker is direction of travel: hardware buys a fixed multiple, and if the workload grows 50% a year you will buy it again, while a fix to a fundamentally wrong access pattern compounds. I would also name the third option people forget: shedding work. Caching, pagination limits, killing an unused report, or moving analytics off the OLTP box frequently beats both, and is often the cheapest to implement.

Explain memory grants and RESOURCE_SEMAPHORE.

Before a SQL Server query runs, the engine reserves memory for its sorts and hash joins based on the estimated row counts. If the estimate is far too high, one query reserves a large slice of the workspace memory and other queries queue behind it — that queue is RESOURCE_SEMAPHORE. If the estimate is far too low, the operator spills to tempdb mid-flight and the query crawls. Both are the cardinality-estimation problem from section 04 wearing a different hat, which is why the durable fix is statistics and query shape rather than memory settings. The mitigations available: Memory Grant Feedback (2017+ for batch mode, 2019+ for row mode) learns the right size across executions; Resource Governor caps what any one workload group can take, and it is now available in Standard edition as of 2025; and the MIN_GRANT_PERCENT/MAX_GRANT_PERCENT hints for a specific offender. PostgreSQL has no grant mechanism at all — work_mem is a per-node, per-worker limit, applied optimistically — which means it never queues but can over-commit memory catastrophically under concurrency, and that trade-off is worth naming.

What do you configure for connection management?

On PostgreSQL, a pooler is architecture, not tuning. I would size max_connections modestly — typically a few hundred — and put PgBouncer in transaction mode in front, sized around a small multiple of CPU cores, because the server does more total work with 40 busy backends than with 800 contending ones. The caveats to know: transaction pooling breaks session-level state (SET, advisory locks, LISTEN/NOTIFY, and historically prepared statements — PgBouncer 1.21+ handles protocol-level prepared statements, which is worth the upgrade), and it silently changes semantics if application code assumes a persistent session. On SQL Server, pooling lives in the client driver: I would check Max Pool Size against the real concurrency, make sure connection strings are identical so pools are shared rather than fragmented, enable connection resiliency and, on Azure, MultiSubnetFailover where relevant. On both, the most valuable thing is an alert on pool exhaustion, because the symptom — application timeouts with an idle-looking database — sends teams to investigate the wrong system.

How do you tune parallelism?

On SQL Server, the two settings that matter are cost threshold for parallelism and MAXDOP. The default cost threshold of 5 dates from 1990s hardware and causes trivial queries to go parallel, burning workers and producing CXPACKET noise; raising it to something like 50 is one of the safest wins available. MAXDOP should reflect the machine and workload — Microsoft's guidance of up to 8, not exceeding the cores per NUMA node, is a good starting point, and OLTP workloads often want less. On PostgreSQL, max_parallel_workers_per_gather (default 2) plus the pool limits max_parallel_workers and max_worker_processes; if EXPLAIN ANALYZE shows fewer workers launched than planned, you are exhausting that pool and the plan's costing assumptions no longer hold. On both, parallelism helps analytic queries and hurts short OLTP ones, so if you can separate those workloads — Resource Governor, a replica, or per-role settings on PostgreSQL — do that instead of picking one compromise number.

A query is fast when you run it and slow from the application. Why?

The classic causes, in the order I would check them. Different SET options: SSMS and the .NET driver differ on ARITHABORT, and because plan cache entries are keyed partly on SET options, the application gets a different cached plan than your session — the "it's fast in SSMS" phenomenon, and it usually means the application's cached plan was compiled for a bad parameter value. Parameterisation itself: your literal-valued run gets a fresh, well-estimated plan while the application reuses a sniffed one. Data type mismatch: a .NET string parameter arrives as nvarchar against a varchar column, causing an implicit conversion that kills the seek — a genuinely common production bug. Then the non-plan causes: the application is fetching all rows over a slow link while you fetched the first page, it runs the query 200 times where you ran it once, or it is blocked by another session that is not there at 4pm when you test. On PostgreSQL the same list applies with the generic-plan switch replacing sniffing, plus search_path differences resolving to a different object.

What is pg_stat_io and why does it matter?

Introduced in 16, it breaks I/O down by backend type (client backend, autovacuum, checkpointer, background writer) and by context (normal, vacuum, bulk read, bulk write), reporting reads, writes, extends, hits and evictions. Before it, PostgreSQL could tell you how much I/O happened but not who did it, so "is the storage saturated by autovacuum or by user queries?" was guesswork. That makes it the right first stop for questions like whether checkpoints are too aggressive, whether the background writer is doing anything useful, or whether bulk loads are evicting the working set. 18 adds pg_aios on top, showing in-flight asynchronous I/O, which is how you tell whether the new AIO subsystem is actually being used and whether io_workers is a bottleneck. Together they close most of the observability gap that SQL Server's sys.dm_io_virtual_file_stats has covered for years — and I would call that gap-closing out as one of the more consequential recent changes for anyone operating PostgreSQL at scale.

How do you performance-test a database change before shipping it?

Against production-sized data, with a workload that resembles production concurrency, measuring the metrics that matter rather than a single wall-clock number. The cheapest useful version is capture-and-replay: an Extended Events or Distributed Replay capture on SQL Server, or reconstructing the top statements from pg_stat_statements with realistic parameter distributions on PostgreSQL, then replaying against a restored copy before and after the change. I care about logical reads or buffers per execution as the workload-independent measure, p95/p99 latency rather than mean, and whether the plan shape changed. The two mistakes I would call out: testing on a small dataset, where every plan is a seek and nothing that matters is visible; and testing single-threaded, which hides every locking and memory-grant interaction. Where a full harness is not affordable, I would at least compare plans and per-execution reads for the top twenty statements, which catches most regressions for an hour of work.

How do you build a performance culture rather than a performance firefight?

Make performance visible and attributable. A weekly ten-minute review of the top queries by total time, with the owning team named, changes behaviour far more than a document about best practices. Put query-count and latency budgets into the test suite so a regression fails a build rather than a pager. Make the flight recorder standard in every environment so investigation costs minutes rather than a day of instrumentation. And do the education through concrete artefacts — the plan for the specific query the team owns, not an abstract talk about indexes. The organisational half matters too: someone must own the database's health explicitly, and there must be a route for "this needs a schema change" that does not take a quarter, or teams will work around the database with caches and denormalisation and you will inherit a worse problem. As a lead, my most useful contribution is usually removing the friction, not doing the tuning.

12 Security and access control

Database security in an interview is rarely about naming encryption algorithms; it is about whether you can reason about blast radius. The framing I would use: authentication decides who, authorisation decides what, encryption decides who can read the bytes if they get them another way, and auditing decides what you can prove afterwards. Most real breaches involve none of the exotic features and all of the boring ones — an application account with far too many rights, a connection string in a repository, a missing WHERE tenant_id, and an injection point.

Authorisation and least privilege

-- PostgreSQL: a least-privilege application role, done properly
CREATE ROLE app_rw LOGIN PASSWORD :'pw';
REVOKE ALL ON SCHEMA public FROM PUBLIC;         -- 15+ already revokes CREATE from PUBLIC by default
GRANT USAGE ON SCHEMA app TO app_rw;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO app_rw;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA app TO app_rw;

-- The step everyone forgets: this only covers tables that exist TODAY.
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA app
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;

-- Row-level security. Note the FORCE: without it the table OWNER bypasses every policy.
ALTER TABLE app.invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE app.invoices FORCE  ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON app.invoices
  USING (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);

-- SECURITY DEFINER functions must pin search_path, or they are a privilege-escalation bug
CREATE FUNCTION app.rotate() RETURNS void
  LANGUAGE plpgsql SECURITY DEFINER SET search_path = app, pg_temp AS $$ … $$;
-- SQL Server: the equivalents
CREATE USER app_rw FOR LOGIN app_rw WITH DEFAULT_SCHEMA = app;
GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA::app TO app_rw;   -- schema-level, so new tables inherit
DENY  ALTER, CONTROL ON SCHEMA::app TO app_rw;

-- Row-level security via a predicate function + security policy
CREATE FUNCTION sec.fn_tenant(@tenant_id bigint) RETURNS TABLE WITH SCHEMABINDING AS
  RETURN SELECT 1 AS ok WHERE @tenant_id = CAST(SESSION_CONTEXT(N'tenant_id') AS bigint);

CREATE SECURITY POLICY sec.tenant_filter
  ADD FILTER PREDICATE sec.fn_tenant(tenant_id) ON app.invoices,
  ADD BLOCK  PREDICATE sec.fn_tenant(tenant_id) ON app.invoices AFTER INSERT
  WITH (STATE = ON);

-- Dynamic SQL without an injection hole
DECLARE @sql nvarchar(max) = N'SELECT * FROM ' + QUOTENAME(@schema) + N'.' + QUOTENAME(@table)
                           + N' WHERE status = @status';
EXEC sys.sp_executesql @sql, N'@status varchar(20)', @status = @status;  -- values are parameters, never concatenated

Interview trap

Row-level security treated as a complete tenant-isolation boundary. Two ways it fails. On PostgreSQL, policies do not apply to the table's owner unless you also run ALTER TABLE … FORCE ROW LEVEL SECURITY, and applications very often connect as the owner — so the policy exists, looks right in the schema, and does nothing. On both engines, superusers and members of high-privilege roles bypass RLS entirely, and a SECURITY DEFINER function owned by a privileged role is a hole straight through it. The second trap is treating dynamic data masking as a security control: it rewrites the presented value, but a user who can query can binary-search the real value with predicates (WHERE salary > 100000), so it is obfuscation for a support UI, not protection. State RLS as defence in depth behind a correctly-scoped connection identity, and you will be answering the question the interviewer meant.

Try it

  1. Enable RLS on a table without FORCE, connect as the table owner, and confirm you see every tenant's rows. Add FORCE and repeat. Then connect as a superuser and see it bypassed again.
  2. Write a deliberately vulnerable stored procedure that concatenates a parameter into dynamic SQL, exploit it with a classic '; DROP TABLE …-- payload against a scratch database, then rewrite it with sp_executesql parameters and QUOTENAME for the identifier and confirm the exploit fails.
What you should conclude

Exercise 1: the connection identity is the real control, and RLS is a backstop for a mistake in one query — not a substitute for connecting as a role that has no business seeing other tenants. Write that down as a design rule: the application connects as a non-owner, non-superuser role, always. Exercise 2: parameterisation defeats value injection completely, but identifiers cannot be parameterised — that is why QUOTENAME (or quote_ident/format(%I) on PostgreSQL) exists, and why an allowlist of permitted column names is better still. The most valuable takeaway is that "we use an ORM so we're safe" is only true until someone writes one raw string-concatenated query, which every codebase eventually contains.

Interview Q&A

What rights should an application's database account have?

Exactly the DML it needs on exactly the schema it owns, and nothing else: no DDL, no rights on other schemas, no server-level roles, no db_owner, no superuser. Migrations run as a separate, higher-privileged identity used only by the deployment pipeline, so a compromised application server cannot alter the schema. Where the application has genuinely separate read and write paths, two roles are worth the extra configuration, because it makes a read-only reporting endpoint provably read-only. On PostgreSQL I would add the two things people miss: ALTER DEFAULT PRIVILEGES so tables created by the migrator tomorrow are accessible without a manual grant, and revoking CREATE on the public schema (already the default from 15). And credentials should come from a managed identity or a secret manager with rotation, not from a connection string in configuration — SQL Server 2025's Arc-enabled managed identity support and cloud IAM auth for PostgreSQL both make "no password anywhere" achievable, which is a much stronger control than any rotation policy.

How do you prevent SQL injection in a codebase you have just inherited?

Find it first: grep for string concatenation into command text and for dynamic SQL in stored procedures, and run a static analyser — this is one of the few security problems where automated detection genuinely works. Then fix by parameterising values everywhere, and for the identifiers that cannot be parameterised, use an allowlist mapped from a caller-supplied token to a known column name, with QUOTENAME or quote_ident as the second layer. Then prevent recurrence: a lint rule or analyser in CI that fails the build on raw concatenation, and a code-review standard. The defence in depth behind all of that is least privilege — an account with no DDL rights and no access to other schemas turns a successful injection from a catastrophe into an incident. What I would not rely on is escaping input or a web application firewall; both are bypassable and both encourage the belief that concatenation is acceptable if you are careful.

Compare TDE and Always Encrypted. When do you use each?

TDE encrypts the data and log files at rest, transparently to every query, so it protects you when a disk, a VM image or a backup file leaves the building. It does nothing against anyone who can connect and query, and it does not protect data in memory or on the wire — so it is a compliance and physical-media control, and it is close to free operationally. Always Encrypted moves encryption to the client driver: the keys live in a key store the database cannot reach, so even a compromised instance or a malicious DBA sees ciphertext. The cost is severe query restrictions — deterministic encryption allows equality only, randomised allows none — and secure enclaves (2019+) relax that to range and pattern matching at the price of enclave configuration and attestation. So: TDE by default for regulated data at rest, Always Encrypted for the narrow set of columns where the platform operator is explicitly in the threat model, such as national identifiers or payment data. PostgreSQL has no TDE in core, so the equivalent is full-disk or filesystem encryption plus an encrypted backup tool, which covers the same threat with different plumbing — and that gap is a legitimate reason some regulated shops stay on SQL Server or a commercial PostgreSQL fork.

What is your position on ORMs and database security?

ORMs are a net positive because they parameterise by default, which removes the most common injection vector at scale. The risks they introduce are different: developers drop to raw SQL for the hard queries and that is where concatenation reappears; the ORM's account often accumulates rights because migrations run through the same connection; and mass-assignment style bugs let a caller update columns the API never intended to expose. So my position is: keep the ORM, ban raw string concatenation with a lint rule, split the migration identity from the runtime identity, and be explicit about which columns are writable rather than mapping whole entities from request bodies. I would also review the generated SQL for the top queries — not for security, but because the same review usually finds the N+1 and the missing index, and it is a good habit to attach to the security review so it actually happens.

How do you handle secrets and connection strings?

The goal is no long-lived password anywhere. Best case, there is no secret at all: a managed identity or workload identity that the platform issues and rotates, which SQL Server 2025 supports on Arc-enabled servers for both inbound and outbound connections, and which Azure Database for PostgreSQL and AWS RDS provide through Entra/IAM token authentication. Where a password is unavoidable, it lives in a secret manager with automated rotation and short TTL, is injected at runtime rather than baked into an image, and never appears in source control, logs or error messages — a connection string in an exception trace is a very common real-world leak. I would also separate credentials by environment and by purpose so that a leaked staging credential is not a production incident, and I would make the audit question answerable: who can read this secret, and when was it last used. If rotation has never been rehearsed, it does not work; I would test it deliberately rather than discover it during an incident.

What would you audit, and how do you keep it useful?

Privileged actions and schema changes always: logins and failures, role and permission changes, DDL, and access to the specific tables holding regulated data. That is SQL Server Audit with server- and database-level specifications, or pgaudit on PostgreSQL, writing to storage the database account cannot modify. What makes auditing useless is volume: auditing every SELECT on a busy system produces terabytes nobody reads and measurable overhead, so I scope it to the sensitive objects and the privileged principals. Then the part that actually determines whether it was worth anything: the logs ship off the box to a system with retention and alerting, someone owns a small number of alerts on the events that should never happen — a new sysadmin, a permission grant outside the pipeline, access to a sensitive table from an unexpected principal — and there is a documented, rehearsed procedure for answering "who touched this row and when". SQL Server's ledger tables (2022+) are worth mentioning where tamper-evidence rather than logging is the requirement.

A developer asks for read access to production to debug an issue. What do you do?

I try very hard to make the answer unnecessary, because standing production access is the control most estates get wrong. The order I would go through: can they get what they need from observability — logs, traces, Query Store, a plan capture — without touching data; can they use a masked or subsetted copy in a lower environment; can we build the one specific query they need as a supported endpoint. If direct access is genuinely required, it is time-boxed and just-in-time through an approval workflow, read-only, on a replica rather than the primary, scoped to the schema in question, with the session audited and the reason recorded. And I would treat a recurring request as a signal about a gap rather than a nuisance — if people need production access weekly to do their jobs, the observability is inadequate, and fixing that is a better use of my time than administering exceptions. Saying no without providing the alternative is how you end up with a shared credential in a wiki.

How do you approach compliance requirements (GDPR-style deletion, data residency)?

Start from the data map: which tables hold personal data, where they are replicated to, and what the retention rule is per category. Deletion is the hard part, because personal data does not stay in one table — it is in backups, in replicas, in read models, in logs, in analytics extracts. My design answer is usually crypto-shredding for the backup problem: encrypt per-subject data with a per-subject key and delete the key, so historical backups become unreadable for that subject without needing to rewrite them. For live data, a deletion pipeline that walks the map and is testable, plus a tombstone so a re-import cannot resurrect the record. Residency drives topology: separate databases or regions rather than a region column, because a column does not stop a backup landing in the wrong jurisdiction, and read replicas and DR sites must respect the same boundary. And I would insist that this is designed in, not retrofitted — retrofitting subject deletion into a system with fifteen downstream copies is a multi-quarter programme, which is exactly the argument for raising it early.

What is the security significance of PostgreSQL's search_path?

It determines which schema an unqualified object name resolves to, and it is evaluated at execution time — so if a function runs with SECURITY DEFINER and does not pin its search_path, an attacker who can create objects in a schema earlier in the path can substitute their own table or, worse, their own operator or function, and have it execute with the definer's privileges. That is a genuine, repeatedly-exploited privilege-escalation class, and it is why every SECURITY DEFINER function should carry SET search_path = schema, pg_temp and why pg_temp belongs last. The related hardening is revoking CREATE on the public schema, which PostgreSQL 15 finally made the default. I would also mention that this is the kind of thing a code-review checklist catches cheaply and a penetration test catches expensively, so it belongs in the review standard for any repository containing PL/pgSQL.

How do you convince a team to take database security seriously without stopping delivery?

Make the safe path the default path and the unsafe one visible. Ship a project template where the application role already has minimal rights, the migration identity is separate, secrets come from the secret manager, and TLS verification is on — so a new service is secure without anyone thinking about it. Add a small number of automated checks that fail loudly: raw string concatenation, a connection string committed, a role granted db_owner. Then pick the two or three controls with the best ratio of risk reduced to friction added — least privilege, no standing production access, verified TLS — and be willing to trade away the rest for now, because a twenty-point standard nobody follows is worth less than three that everyone does. And frame it in blast-radius terms rather than compliance terms: "if this service is compromised, what can the attacker reach" is a question engineers engage with, whereas "the policy says" is a question they route around.

13 Scaling out and the platform edge

Everything so far assumed one database doing its job well. This section is about what happens when one database is not enough, and about the two things that have changed the edges of the relational platform most in the last two years: managed cloud services that separate compute from storage, and vector search arriving inside both engines. A lead is expected to know the scaling ladder, to climb it in the right order, and to say where they would stop.

The scaling ladder, in the order you should actually climb it

  1. Make the work smaller. Fix the top queries, add the missing index, remove the N+1, cache what is genuinely cacheable, delete the report nobody reads. Almost always the cheapest step, and almost always skipped.
  2. Scale up. More memory is the single most effective database purchase, because it converts I/O into cache hits. Modern hardware goes very far — a two-socket machine with a few terabytes of RAM and NVMe handles workloads people assume need a cluster.
  3. Move work off the primary. Read replicas for reporting and analytics, with the read-your-writes discipline from section 10; a separate analytics store fed by CDC or logical replication when the query shapes genuinely conflict.
  4. Partition. Not for speed, for manageability: bounded maintenance, instant archival, per-partition statistics — section 08.
  5. Split by domain. Give a bounded context its own database. This is a service-boundary decision, and it costs you cross-database joins and distributed transactions, so it must be worth it.
  6. Shard. Last, because it changes the programming model permanently: cross-shard queries, rebalancing, global uniqueness, and schema changes across N shards all become your problem.

Vector search and the AI edge

This is the fastest-moving part of the topic and the one most likely to come up as "what's new". Both engines now let you keep embeddings next to the relational data, which removes an entire class of synchronisation bug — the vector store and the source of truth drifting apart — and that is usually a bigger win than the last few percent of approximate-nearest-neighbour throughput.

-- PostgreSQL with pgvector: the mature path
CREATE EXTENSION IF NOT EXISTS vector;
ALTER TABLE documents ADD COLUMN embedding vector(1536);
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

SET hnsw.ef_search = 100;             -- the recall/latency dial, per query
SELECT id, title, embedding <=> $1 AS distance   -- the <=> operator is cosine distance
FROM   documents
WHERE  tenant_id = $2                 -- filter first: this is why keeping it in Postgres wins
ORDER  BY embedding <=> $1
LIMIT  10;
-- SQL Server 2025: vectors and embeddings generated inside the engine
CREATE TABLE dbo.documents (
  id        bigint IDENTITY PRIMARY KEY,
  title     nvarchar(400),
  body      nvarchar(max),
  embedding vector(1536)                 -- native type, GA in 2025
);

-- Register an inference endpoint as a first-class database object
CREATE EXTERNAL MODEL embedder
WITH ( LOCATION = 'https://myfoundry.openai.azure.com/openai/deployments/text-embedding-3-small/embeddings',
       API_FORMAT = 'Azure OpenAI', MODEL_TYPE = EMBEDDINGS, MODEL = 'text-embedding-3-small',
       CREDENTIAL = [https://myfoundry.openai.azure.com] );

UPDATE dbo.documents
SET    embedding = AI_GENERATE_EMBEDDINGS(body USE MODEL embedder);

SELECT TOP (10) id, title, VECTOR_DISTANCE('cosine', embedding, @q) AS distance
FROM   dbo.documents ORDER BY distance;

Getting data out: CDC and streaming

Every scale-out story eventually needs changes to leave the database. PostgreSQL's answer is logical decoding — pgoutput for native subscribers, or Debezium reading the same WAL stream into Kafka — and it is the de facto industry standard. SQL Server's classic answers are Change Tracking (lightweight: which rows changed) and CDC (heavier: what they changed to, read from the log by a capture job). SQL Server 2025 adds change event streaming, publishing each row change as a CloudEvent with old and new values to Azure Event Hubs or Fabric Eventstream, and Fabric mirroring, which continuously replicates an on-premises database into Microsoft Fabric — notably, Synapse Link is discontinued in 2025 and mirroring is its replacement. Both change event streaming and vector indexes sit behind the PREVIEW_FEATURES database-scoped configuration, which is a precision worth having.

Interview trap

Reaching for sharding — or for a distributed SQL database — before exhausting the cheap rungs of the ladder. Sharding is not a scaling technique you add; it is a programming model you adopt, and it permanently costs you cross-shard joins, distributed transactions, global uniqueness, rebalancing, and schema changes multiplied by N. Meanwhile a single well-tuned PostgreSQL or SQL Server instance on current hardware handles tens of thousands of transactions per second and many terabytes, and most "we need to shard" conversations turn out to be one missing index and an N+1. The senior version of this answer names the specific signal that would actually justify it — a write rate that exceeds what one primary's WAL/log can absorb, or a dataset whose working set cannot fit any single machine's memory — and says that read scaling, partitioning and domain splits should be exhausted first. The mirror-image trap is refusing to ever leave one database when the workload genuinely has two conflicting shapes; a heavy analytics query on the OLTP primary is a real reason to move it, not a failure of tuning.

Try it

  1. Load 100k embeddings into PostgreSQL with pgvector, build an HNSW index, then measure both latency and recall against a brute-force scan at hnsw.ef_search values of 20, 100 and 400.
  2. Set up Debezium (or native logical replication) against a test PostgreSQL database, then take the consumer offline for an hour while writes continue, and watch the replication slot's retained WAL.
Expected outcome

Exercise 1: latency and recall both climb with ef_search, and the interesting result is that recall at the default is often lower than people assume — 90-something percent rather than the 100% they were mentally assuming — which is exactly why an approximate index needs a recall measurement in the acceptance criteria, not just a p95 latency. Exercise 2: the retained WAL grows monotonically and the primary's disk is now on a countdown, which is section 10's slot failure mode reappearing in a CDC costume. The lesson to carry: any CDC consumer is now a component whose availability affects your primary database, so it needs monitoring, a bound (max_slot_wal_keep_size), and a documented decision about what you do when it has been down for a day.

Interview Q&A

At what point would you shard, and how would you pick the key?

When a single primary can no longer absorb the write rate or the working set cannot fit any available machine — and only after read replicas, partitioning and domain splits have been used. The key must be something almost every query filters on and that distributes evenly: tenant or customer id for a SaaS product, user id for a social graph. What I would examine before committing is the query inventory — if 20% of queries cannot include the key, those become scatter-gather across every shard and will dominate your latency. I would also design for rebalancing from day one, usually by hashing into a large fixed number of logical shards mapped onto a smaller number of physical nodes, so growth is a remapping rather than a re-shard. And I would strongly prefer an existing implementation — Citus for PostgreSQL — over hand-rolled routing, because the parts people underestimate are distributed transactions, schema migration across shards, and rebalancing without downtime.

Should a new service use a managed database or self-hosted?

Managed, by default, and the burden of proof is on self-hosting. You are buying patching, backups, failover, monitoring and a support contract for less than an engineer's time, and — for PostgreSQL especially — the HA assembly that is otherwise your problem. Self-host when you need something the service does not offer: an extension outside the allowlist, superuser, a specific version, filesystem access, a version that has not landed yet, or extreme cost sensitivity at very large scale. I would also weigh the lock-in gradient explicitly: RDS or Flexible Server running community PostgreSQL is portable; Aurora and Hyperscale are architecturally different and moving off them is a project. And I would be honest about the fact that managed is not managed-away — you still own schema, indexing, query performance, connection management and the migration process, which is where most incidents actually come from.

How do you serve analytics without destroying OLTP performance?

Separate the workloads, because they want opposite things: OLTP wants small, indexed, latency-sensitive access, analytics wants large scans and doesn't care about a few seconds. The cheapest separation is a read replica dedicated to reporting, accepting lag and, on PostgreSQL, deciding explicitly whether to pay for hot_standby_feedback or accept cancelled queries. The next step is a different storage shape: on SQL Server, a nonclustered columnstore index gives real-time analytics on the OLTP table with batch-mode execution — 2025's ordered nonclustered columnstore and online builds make that much less disruptive to adopt. Beyond that, a dedicated analytics store fed by CDC or logical replication: Fabric mirroring from SQL Server 2025, or Debezium into whatever the platform is. What I would resist is the middle ground where analysts have direct access to the primary with no governor, because a single unbounded query is then a production incident — and where that must exist, Resource Governor (now in Standard edition as of 2025) is the containment.

PostgreSQL with pgvector, or a dedicated vector database?

Start with pgvector, because the dominant cost in most retrieval systems is not ANN throughput, it is keeping the vectors consistent with the source data and filtering by business predicates. If the embeddings live in the same transaction as the row, they cannot drift, and a query can filter by tenant, permission and date before or during the vector search rather than post-filtering a top-k from another system and discovering you have three results left. A dedicated vector database earns its place at scales where that stops holding — hundreds of millions of vectors, very high query concurrency, or a need for features like multi-vector or late-interaction retrieval that pgvector does not implement. On the SQL Server side the equivalent judgment applies, with the extra precision that the native vector type and VECTOR_DISTANCE are GA in 2025 while the DiskANN-based CREATE VECTOR INDEX and VECTOR_SEARCH are behind PREVIEW_FEATURES — so exact search is production-ready and approximate search is not yet, which materially affects whether you can use it at scale today.

How do you evolve from a shared database to service-owned databases?

Incrementally, and with reads and writes handled separately. First, establish ownership on paper: each table has exactly one owning service that may write to it. Then cut the write paths — other services call the owner's API instead of writing directly — which is usually the hard organisational part and takes months. Then cut the read paths, which is where you need a replacement: an API for point reads, and events or a replicated read model for the join-heavy cases that used to be a cross-table query. Only then do you physically separate the schema, and only then the server. The pattern I would warn against is separating the databases first and rebuilding the joins with distributed transactions or synchronous cross-service calls, because you get all of the cost and none of the isolation. And I would be clear that some joins should not be broken up at all: if two "services" always query each other's tables together, they are one service, and the correct action is to merge them rather than to build a distributed join.

What is Azure SQL Hyperscale and when does it matter?

It re-architects Azure SQL Database by separating the compute node from a set of page servers and a dedicated log service. The consequences are the interesting part: storage grows to 100 TB and beyond without repartitioning, backups are snapshot-based so they are near-instantaneous regardless of size and restores are minutes rather than hours, and read replicas can be added in minutes because they attach to the same page servers rather than copying data. That matters when database size has made your backup and restore times unacceptable, or when you need to add read capacity quickly. What you give up is portability — this is not something you can run on-premises — and some behaviours differ enough that you must test rather than assume. The conceptual parallel worth drawing is Aurora on the PostgreSQL side and Neon's storage-compute separation: three different vendors reaching the same conclusion that decoupling durable storage from the query engine is how you make a relational database elastic.

How would you introduce CDC to a system that has never had it?

Start by naming the consumer and the contract, because CDC without a downstream owner becomes an unmonitored component that eventually fills your primary's disk. Then pick the mechanism by fidelity needed: Change Tracking on SQL Server if the consumer only needs "these rows changed, go read them", CDC or change event streaming if it needs before/after values, and logical replication or Debezium on PostgreSQL. Then design for the operational realities: the replication slot or capture job is now on the critical path of the primary's disk usage, so it needs a bound and an alert; the consumer must be idempotent because delivery is at-least-once; schema changes must be coordinated because the stream carries a schema; and the initial snapshot of a large table is a real load event. I would also decide up front what happens when the consumer is down for a day — do we retain and catch up, or drop the slot and re-snapshot — because that decision made calmly in design is very different from the one made at 2am with a full disk.

When is a relational database the wrong choice?

When the access pattern genuinely does not need what it provides. Very high-volume append-only telemetry with time-window queries is better served by a time-series store or a columnar warehouse — though TimescaleDB and columnstore indexes both blur that line, and the blur is often worth taking to avoid a second system. Full-text search at scale with relevance tuning, faceting and synonyms goes to a search engine, because Postgres full-text and SQL Server full-text are good enough for "find the document" and not for "be Google". A cache is a cache. Graph traversal of many hops is genuinely awkward, though PostgreSQL 19's SQL/PGQ property graph queries will make the shallow cases much more pleasant. What I would push back on is choosing a document or key-value store to avoid designing a schema — the schema does not go away, it moves into every reader, and you discover it three years later when the data has six shapes. My default is: start relational, and move a workload out when you can name the specific property the relational engine cannot provide.

What does SQL Server 2025's AI story actually give you, in engineering terms?

Three concrete things and one caveat. A native vector type with distance functions, so embeddings are a column rather than a foreign system. CREATE EXTERNAL MODEL plus AI_GENERATE_EMBEDDINGS and AI_GENERATE_CHUNKS, which move embedding generation and text chunking into T-SQL against Azure AI Foundry, Azure OpenAI, Ollama or OpenAI — so a RAG pipeline can be a stored procedure rather than an application service. And a SQL MCP server through Data API builder, which lets agents query the database through a governed interface. The caveat is the one I keep returning to: the approximate vector index and VECTOR_SEARCH require PREVIEW_FEATURES, so at production scale today you are doing exact distance calculations. My architectural take is that generating embeddings inside the database is convenient and couples your database to an external endpoint's availability and latency — I would keep that call in an application service with retries and a queue, and use the database for storage and search.

A team wants to add a caching layer in front of the database. What do you ask?

What is the actual read pattern and hit rate you expect, and what is the invalidation strategy — because caching is easy and invalidation is where the bugs live. Then: have you exhausted the free cache you already have, which is the buffer pool, because a cache miss that hits a well-indexed warm database is often sub-millisecond and a Redis round trip is not obviously faster. Then the correctness questions: what happens on a stale read, is there a user-visible flow that reads immediately after writing, and how do you handle a cache stampede when a hot key expires. And the operational ones: the cache is now on the critical path, so what happens when it is down — does the database survive the full uncached load, and have you tested that. My default position is that caching is right for expensive derived results and for reducing a genuine hot-key read amplification, and wrong as a substitute for fixing a slow query, because it hides the problem while adding a distributed-systems failure mode.

14 The big Q&A

Twenty-two questions that do not belong to any single building block: ecosystem and architecture decisions, tooling, the legacy reality of enterprise database estates, and the judgment scenarios that dominate lead and principal loops. The answers here are deliberately opinionated — an interviewer at this level is testing whether you can hold a position and name its costs, not whether you can list options.

Architecture & ecosystem decisions

Greenfield service, .NET stack, no existing database estate. SQL Server or PostgreSQL?

PostgreSQL, unless something specific argues otherwise. Npgsql and EF Core support it as a first-class provider, the licence cost is zero at every scale, every cloud offers a managed version, and the extension ecosystem means capabilities like geospatial and vector search do not require a second system. The specific things that would flip me to SQL Server: a team already deep in the Microsoft data platform (SSIS, SSRS/Power BI Report Server, SQL Agent, Always Encrypted, Fabric mirroring), a hard requirement for TDE that a fork or filesystem encryption cannot satisfy, a workload that genuinely benefits from columnstore and batch mode without adding a warehouse, or an organisation with SQL Server DBAs and no PostgreSQL experience — because the operating model matters more than the engine. What I would not do is choose on benchmark numbers; at the scale most services operate, both engines are far faster than the application around them.

How do you evaluate whether to adopt a database extension or a new engine feature?

Four questions. Does it remove an existing workaround, or is it new capability we merely find interesting — the first is worth adopting, the second usually is not yet. What version does it pin us to, and is that version supported for long enough. Who owns it: a core feature, a widely-deployed extension with a real maintainer, or one person's GitHub repository — because a C extension in the server process with an absent maintainer is an unpatched CVE waiting to happen. And how do we get out: is there a migration path if we stop using it, or does it become load-bearing in a way we cannot reverse. I would also check whether our managed provider even allows it, since a decision that quietly rules out RDS or Flexible Server is an architecture decision disguised as a technical one.

Your organisation runs both engines. How do you avoid the worst of both worlds?

Standardise the operating model, not the SQL. One monitoring stack with equivalent metrics for both — waits, top queries, replication lag, backup age; one migration process with the same review gate; one backup and restore-rehearsal standard; one incident runbook shape with engine-specific steps inside it. Then be explicit about which engine is the default for new systems and what evidence justifies the other, so the estate stops growing accidentally. What I would not attempt is a portable SQL layer across both, because it taxes every query to preserve an option nobody exercises. And I would invest in cross-training deliberately: the concepts transfer almost completely — MVCC, snapshots, statistics, plan stability, the horizon problem — so an engineer who understands one deeply can be productive on the other in weeks, provided someone explicitly maps the vocabulary for them.

How do you decide between an OLTP database and a warehouse for a reporting requirement?

By the query shape and the freshness requirement. If reports scan large fractions of a table, aggregate across long time ranges, and can tolerate minutes or hours of staleness, they belong in a columnar store — a warehouse, Fabric, or a columnstore index if it can stay on SQL Server. If they are narrow, indexed, and must be current to the second, they belong on the OLTP database or a replica of it. The trap is the middle case, "real-time dashboards", which is usually a requirement nobody has costed: asking what decision is made from the number and how often almost always relaxes it to five minutes, which changes the architecture completely. I would also insist on a boundary: analysts querying the transactional primary directly, with no resource governance, is how a routine query becomes a production incident.

Security & compliance

You find production credentials committed to a repository. What is your sequence?

Treat it as a live incident, not a hygiene issue. Rotate the credential first — the secret is compromised the moment it is committed, regardless of whether the repository is private, and removing the commit does not un-leak it. Then determine exposure: how long it was there, who had repository access, whether the repository was ever public or mirrored, and whether the credential was used from any unexpected source, which the database's own login auditing should be able to answer. Then contain: check what that account could actually do, which is the moment least privilege pays for itself, and look for signs of use. Then the systemic fix: secret scanning in CI and on the server side so the next one is blocked at push time, and a move to managed identity or a secret manager so there is no long-lived credential to commit. And a blameless writeup, because the reason it happened is almost always that the safe path was harder than the unsafe one.

How do you provide realistic data to development and test environments?

Not by restoring production, which is the default in most organisations and is a standing data-protection breach. The options in order of preference: generated synthetic data that matches the shape and cardinality of production, which is the only genuinely safe answer and takes real effort to make representative; a masked and subsetted copy, produced by an automated, audited pipeline that runs on the secure side and only emits the masked result; and, for performance testing specifically, a full copy in an environment with production-grade access controls, treated as production for security purposes. I would push hard for the middle option as the practical default, and I would automate it, because a manual masking process is one forgotten column away from a breach. The performance point from section 09 matters here too: a development database with a thousand rows hides every plan problem, so "realistic" has to mean realistic volume, not just realistic values.

An auditor asks you to prove who read a particular customer's record last month. Can you?

Only if that was designed in — and the honest answer in most estates is no, because auditing SELECTs on everything is prohibitively expensive. So the design is targeted: identify the tables holding regulated data, audit reads on those specifically with SQL Server Audit or pgaudit, ship the logs off-box to storage the database account cannot modify, and retain them for the compliance period. The second half is that the audit record must identify a human, which fails when every application connects as one shared service account — so the application needs to propagate the acting user, either through SESSION_CONTEXT/current_setting written at the start of each request, or by auditing at the application layer and correlating. I would say all of this plainly in an interview, including the part where retrofitting it is expensive, because the interviewer is usually testing whether you understand that observability of access is an architectural requirement rather than a switch.

Performance & debugging

Storage latency is fine, CPU is at 30%, and the application still times out. Where do you look?

Concurrency and connections, in that order. Timeouts with an idle-looking database usually mean the request never reached the engine — connection pool exhaustion in the application, or PgBouncer's pool saturated with clients waiting — so I check pool metrics and pg_stat_activity/sys.dm_exec_connections counts before anything else. If connections are fine, look for blocking chains: a long transaction holding a lock makes everything queue while the server looks unbusy, which is precisely the shape of low CPU plus high latency. Then look for a resource that is not CPU or disk: memory grants queueing on SQL Server, worker thread exhaustion (THREADPOOL), lock manager contention, or a single hot page. And do not forget the boring causes — a DNS or TLS handshake problem, a saturated NAT gateway, or a network path change — because "the database is slow" is where every latency problem in a system gets reported first.

Give me a specific example of a query rewrite that produced an order-of-magnitude improvement.

The one I have used most often is turning a correlated per-row lookup into a single windowed pass. A "latest status per order" query written as a subquery per row — WHERE updated_at = (SELECT max(updated_at) FROM history h WHERE h.order_id = o.id) — scans the history table once per order; rewritten with ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) and a filter on rank 1, or with LATERAL/CROSS APPLY and a supporting index on (order_id, updated_at DESC), it becomes one ordered pass. On a few million history rows that is routinely 50–200×. The second most common is splitting an OR across two indexed columns into a UNION ALL of two seekable queries, because a single OR predicate frequently forces a scan. Both illustrate the same principle from section 03: the win comes from making the work expressible as a contiguous index range rather than from any engine feature.

How do you find the query that is causing an incident when everything looks slow?

Slowness is usually a symptom of one resource being consumed, so I find the consumer rather than the victims. Sort currently-running requests by resource use — reads, CPU time, or duration — rather than by start time, and look for the one session doing a hundred times what the others are doing. In parallel, check the blocking graph, because if there is a chain then the head of it is the answer and everything else is noise. And check what changed: a deploy, a job, a failover, a data volume threshold, a statistics update. What I would resist is the instinct to look at aggregate top-query reports during an incident — those are for prevention and for the postmortem; live triage needs live state. Once I have a candidate I would capture its plan and its parameters before killing it, because the postmortem is worthless without them, and then mitigate.

How do you tell whether a problem is the database or the application?

Compare the database's own accounting of time with the client's. If pg_stat_statements or Query Store says a statement took 8 ms and the client reports 900 ms, the time is outside the engine — connection acquisition, network, TLS, driver-side result materialisation, or the application doing something with each row. Distributed tracing with a span around the database call makes this a two-minute question rather than a two-day argument, which is why I would put that in place early. The classic non-database causes that masquerade as database problems: fetching a million rows and materialising them into objects, a chatty ORM issuing hundreds of round trips, a pool that is too small so requests wait for a connection, and a client-side timeout shorter than the query's normal duration. Being able to say "the engine's own timing says this is not us, here is the evidence" is a much better position than an opinion.

Tooling

What tools do you actually reach for, and why those?

On SQL Server: Query Store first for anything historical, sp_WhoIsActive for live triage, the First Responder Kit (sp_Blitz and friends) for a fast health assessment of an unfamiliar instance, Ola Hallengren's maintenance solution rather than maintenance plans, Extended Events over Profiler, and SSMS or Azure Data Studio depending on what the task is. On PostgreSQL: pg_stat_statements and auto_explain as always-on instrumentation, pgBadger or a hosted service like pganalyze for log analysis, explain.depesz.com or explain.dalibo.com for reading a large plan, pgBackRest for backups, PgBouncer for pooling, and Patroni or CloudNativePG for HA. The common thread is that they are boring, widely deployed and well documented — in an incident, an unusual tool nobody else on the team knows is a liability, not an advantage.

How do you keep local development close enough to production?

Same engine, same major version, in a container, seeded from the same migration scripts that run in production — that is the floor, and skipping it produces the "works on my machine, deadlocks in production" class of bug. Beyond that, realistic volume for the tables that matter, because plan behaviour is entirely a function of data size; a subset of production shape rather than a handful of rows. And test the concurrency-sensitive paths in an integration test with actual parallel sessions, since deadlocks, race conditions and isolation bugs are invisible single-threaded. Where the gap cannot be closed locally — edition differences on SQL Server, the exact managed-service configuration, hardware — I would make sure there is a shared environment restored from production that catches it before release, and I would be explicit that CI passing on SQLite or an in-memory provider proves nothing about the database.

What belongs in source control for a database?

The migration scripts, in order, with the same review process as application code. The stored procedures, functions and views as files, so they are diffable and reviewable rather than existing only in the server. The reference or seed data that the application depends on, as idempotent scripts. The configuration that matters, so a rebuild is reproducible. And the operational scripts — the health-check queries, the backfill helper, the runbook queries — because those are exactly what you want to find at 3am rather than reconstruct. What should not be in source control: credentials, production data, and generated deployment diffs. The test of whether you have this right is a simple question: can you build an empty database that matches production's schema from a clean checkout, and does CI actually do that on every commit? Most estates cannot, and it is the single most useful thing to fix.

Legacy & migration reality

You inherit a database with 800 stored procedures and no tests. How do you make it safe to change?

Establish a safety net before touching anything. Capture the real workload — Query Store or pg_stat_statements — so you know which procedures are actually called and which are dead; typically a third of them have not run in a year, and knowing that reduces the problem substantially. Then build characterisation tests for the ones that matter: call them with representative inputs against a restored copy and record the outputs, so you have a regression harness without understanding the logic first. Then change only under that harness, smallest change first, and add a real test for each procedure as you touch it. The strategic decision that goes alongside this is whether logic should stay in the database at all — my usual answer is that new logic goes in the application, existing logic moves only when it needs to change, and pure data-shaping stays where it is because rewriting working SQL for aesthetic reasons is not a good use of anyone's quarter.

What actually goes wrong in a SQL Server to PostgreSQL migration?

In order of how much pain they cause: collation, because case-insensitivity silently changes query results and constraint behaviour; T-SQL surface area, since procedures, MERGE, temp tables, table-valued parameters and error handling all need rework and there is a lot of it; the peripheral estate that nobody inventoried, meaning SQL Agent jobs, SSIS packages, linked servers, reports and the integrations that connect directly rather than through the application; identity and sequence semantics, including gaps and reset behaviour; and date/time handling. Tools like Babelfish or ora2pg-style converters get you a mechanical translation of the easy 70% and create false confidence about the rest. My approach is to migrate incrementally where possible — move one bounded context at a time behind the application, running both engines during the transition with CDC to keep them in step — because a big-bang cutover of a large estate has a failure mode with no rollback, and the dual-running period is where you find the collation bugs cheaply.

A legacy system uses NOLOCK everywhere. How do you fix it?

Not by removing the hints, which would immediately introduce the blocking they were papering over. The sequence is: turn on RCSI in a maintenance window, having sized tempdb and load-tested first, so readers get a consistent statement-level snapshot without locks — that gives the non-blocking reads the hints were chasing, but with correct answers. Then remove the hints incrementally, starting with the reports where a wrong answer is most expensive, verifying performance as you go. The one thing to check before enabling RCSI is code that relied on readers blocking as an accidental serialisation mechanism — a home-grown "lock by selecting" pattern — because its behaviour will change silently. I would also use the opportunity to have the conversation about why they were added: usually one blocking incident years ago, followed by a blanket search-and-replace, and the cultural fix is making sure the next incident produces a diagnosis rather than a hint.

How do you handle a database nobody understands and nobody owns?

Give it an owner first; everything else is downstream of that. Then produce the map from section 08 — profile the data for implied constraints, capture the workload to find what is actually used, and inventory who connects and from where, which is often the biggest surprise because half the connections come from systems nobody remembered. Establish the safety fundamentals immediately regardless of understanding: verified backups with a timed restore rehearsal, monitoring, and least-privilege review of who has write access. Then reduce surface area — drop what is provably unused, after a deprecation period with logging to prove it — because a smaller system is easier to understand than a documented large one. And write down what you learn as you learn it, in the repository, not a wiki that will rot. The mistake I would avoid is a big-bang documentation or modernisation project; those produce a document and no change, whereas incremental ownership produces a system that gets better every month.

Judgment & scenarios

How do you introduce a database review gate to a team that resents process?

By making it fast, useful and evidently valuable rather than by mandating it. I would start as a service rather than a gate — "send me your migration and I will look at it in an hour" — and use those reviews to find the two or three recurring problems that actually cause incidents in this codebase. Then automate exactly those checks so they run in CI and give feedback in seconds without a human. Only then, if it is still needed, formalise a gate for the highest-risk category — DDL on large tables, say — and leave everything else automated. The framing matters: the pitch is not "your changes need approval", it is "here is a check that would have caught last month's outage, and it runs in four seconds". Teams accept constraints whose value they have seen, and route around constraints imposed on principle.

What do you do when a product deadline conflicts with database safety?

Separate the risk into what is reversible and what is not, and negotiate on the reversible part. Shipping without an index is a performance risk you can fix on Tuesday; shipping a destructive migration without a tested restore is a risk you cannot. So I will trade away polish, monitoring coverage and even some performance work to hit a date, and I will not trade away a verified backup, a rollback plan or a data-loss-capable change without an explicit, named decision by someone accountable. The way to make that conversation productive is to quantify: "this saves two days and carries a 1-in-20 chance of a four-hour outage during launch week" is a decision a product owner can make, whereas "it's not safe" is a position they will overrule. And whatever gets deferred goes on the board with an owner and a date, because the alternative — an informal promise to fix it later — is how estates accumulate the debt I spend my time paying down.

How would you run the first 90 days as a lead over an unfamiliar database estate?

Weeks 1–2: inventory and safety. What exists, what version, who owns it, when was the last successful restore, is anything unsupported, who has write access. Fix anything actively dangerous immediately — an unverified backup, an unpatched end-of-life instance, a shared admin credential. Weeks 3–6: observability. Query Store or pg_stat_statements plus auto_explain everywhere, wait statistics in a time series, and the six health alerts from section 06, so that from here on I am arguing from data. Weeks 6–12: the top three problems that data reveals, done properly and visibly, plus one process improvement — usually the migration review gate — introduced as a service rather than a rule. Throughout: talk to the teams, because the real constraints are organisational, and the reason nobody fixed the obvious thing is usually a reason. I would explicitly avoid a large restructuring proposal in the first quarter; credibility comes from fixing things people already know are broken.

What would you flag in a design review of a new high-write service?

The key choice, because random UUIDs will cost you page splits or WAL amplification and it is expensive to change later. The update pattern, because a table updated as often as it is read is a bloat problem on PostgreSQL and a version-store problem on SQL Server, and it wants a low fillfactor and aggressive autovacuum from day one. Transaction boundaries, especially anything doing network I/O inside a transaction. Whether writes are batched or one round trip per row. The archival plan, because a table with no retention policy becomes an operational problem in eighteen months and partitioning is much cheaper to design in than to retrofit. Index count, since every index is a tax on every write. And the read path's isolation expectations, because "we'll read from the replica" plus "we read immediately after writing" is a bug waiting to be filed. Finally: what the failure mode is when the database is briefly unavailable, because a high-write service usually needs a queue in front of it rather than a retry loop.

15 Night-before cheat sheet

Ten sentences to read on the train. Each is a complete, speakable claim you can say out loud and then defend from the sections above.

  1. “The current stable releases are PostgreSQL 18.6, shipped 2026-08-13 — 18.5 was pulled for a regression — with 19 Beta 3 in the field and GA expected in late September 2026, and SQL Server 2025 (17.x), GA on 2025-11-18 and now on CU8.”
  2. “The architectural fault line is concurrency: PostgreSQL is multiversion always, so an update writes a new tuple and the cleanup bill arrives later from autovacuum; SQL Server updates in place and locks by default, so its bill arrives as blocking unless you turn on RCSI — and RCSI is off on-premises but on by default in Azure SQL Database.”
  3. “PostgreSQL 18's headline changes are an asynchronous I/O subsystem with io_method defaulting to worker, B-tree skip scan that makes multi-column indexes usable without a leading-column predicate, virtual generated columns by default, uuidv7(), RETURNING old.*/new.*, temporal WITHOUT OVERLAPS constraints, and statistics carried across pg_upgrade.”
  4. “SQL Server 2025's headline changes are optimized locking — TID locking plus lock-after-qualification, which removes lock escalation as a failure mode but needs ADR — optional parameter plan optimization for the (@p IS NULL OR col = @p) pattern, a native json type, the REGEXP_* functions, a native vector type, and ZSTD backup compression; the approximate vector index and change event streaming are still behind PREVIEW_FEATURES.”
  5. “Almost every plan problem is an estimation problem: find the lowest operator where estimated and actual rows diverge, and the cause is usually stale statistics, correlated predicates being multiplied under the independence assumption, a non-sargable predicate, or a cached plan compiled for a different parameter value.”
  6. “PostgreSQL's characteristic outage is the xmin horizon — one idle-in-transaction session or one abandoned replication slot stops vacuum reclaiming anything, tables bloat, index-only scans stop working, and eventually you approach transaction-ID wraparound; SQL Server's is the same physics in tempdb, where one long snapshot transaction grows the version store until the instance cannot write.”
  7. “Safe schema change is a procedure, not a statement: expand, dual-write, backfill in bounded batches, switch reads, contract — with a lock_timeout set on every PostgreSQL migration, because a pending ACCESS EXCLUSIVE lock makes every subsequent query queue behind it.”
  8. “A replica is not a backup: DELETE without a WHERE replicates perfectly, so you need point-in-time recovery — full plus differential plus log backups, or a base backup plus WAL archive — and the only meaningful question about a backup is when you last restored it and how long it took.”
  9. “Diagnose from waits before queries: cumulative wait statistics diffed over a window tell you whether you have an I/O, locking, memory-grant, log or CPU problem, and only then does it make sense to open a plan — and never tune from averages, because total time and p99 are where the pain actually is.”
  10. “Climb the scaling ladder in order — fix the queries, scale up, move reads off the primary, partition for manageability, split by domain, and only then shard — because sharding is a programming model you adopt permanently, and most 'we need to shard' conversations turn out to be one missing index and an N+1.”

If you remember nothing else

Two sentences carry most of the interview. PostgreSQL trades write cost and vacuum for never blocking readers; SQL Server trades blocking for in-place updates, unless you enable RCSI and move that cost into tempdb. And every hard question — bloat, the version store, replication lag, index-only scans, cancelled queries on a standby — is the same question about how long the oldest transaction has been open. If you can derive an answer from those two, you can answer questions you never rehearsed.
