SQL (SQL Server & PostgreSQL)

cheatsheet · PostgreSQL 18.6 & SQL Server 2025 (17.x) CU8 17.0.4075.5 · released 2026-08-13

Two engines side by side on every row: the DDL, query syntax, JSON and regex, index and locking idioms, plan-reading commands, CLI flags and maintenance knobs an engineer touches weekly, each tagged with the version where it became true. It reflects PostgreSQL 18.6 (2026-08-13 — 18.5 was skipped after a regression) with 19 Beta 3 already out and GA due this month, and SQL Server 2025 (17.x), GA 2025-11-15, at CU8 (17.0.4075.5, 2026-08-13). Where the two dialects agree the row is written once; where they diverge — upsert, isolation defaults, JSON, identifier folding — both are spelled out, and rows marked PG or MSSQL apply to that engine only.

Connection strings worth memorising

# PostgreSQL — libpq URI; sslmode=verify-full is the only one that checks the hostname
postgresql://app:secret@db.internal:5432/orders?sslmode=verify-full&application_name=api&connect_timeout=5

# SQL Server — ADO.NET; Encrypt=Strict is TDS 8.0 (2022+), Encrypt=True is TLS-over-TDS
Server=tcp:db.internal,1433;Database=Orders;Authentication=Active Directory Default;Encrypt=Strict;
  TrustServerCertificate=False;Application Name=api;Connect Timeout=5;Max Pool Size=200

Pooling differs structurally. PostgreSQL forks a process per connection (~5–10 MB each): put pgbouncer in transaction mode in front and keep max_connections ≈ 100–300. SQL Server is thread-per-request with client-side pooling built into the driver — the equivalent mistake is leaking pooled connections, not opening too many server-side.

DDL that will not take the table down

-- PostgreSQL 18: add NOT NULL without an AccessExclusive full scan (was CHECK (c IS NOT NULL) NOT VALID)
ALTER TABLE orders ADD CONSTRAINT orders_email_nn NOT NULL (email) NOT VALID;  -- instant, rejects new NULLs
ALTER TABLE orders VALIDATE CONSTRAINT orders_email_nn;                        -- ShareUpdateExclusive, reads+writes continue

-- PostgreSQL: same trick for FK and CHECK (all versions)
ALTER TABLE orders ADD CONSTRAINT fk_cust FOREIGN KEY (customer_id) REFERENCES customer(id) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT fk_cust;

-- PostgreSQL: adding a column with a non-volatile default is metadata-only since 11; dropping is metadata-only too
ALTER TABLE orders ADD COLUMN currency text NOT NULL DEFAULT 'EUR';
SET lock_timeout = '3s';  -- ALWAYS, before DDL: a queued AccessExclusive lock blocks every reader behind it

-- SQL Server: adding a NOT NULL column with a default is metadata-only in Enterprise since 2012
ALTER TABLE dbo.Orders ADD Currency char(3) NOT NULL CONSTRAINT DF_Orders_Currency DEFAULT 'EUR';
-- Untrusted constraint after WITH NOCHECK: the optimizer stops using it. Check for them:
SELECT name, is_not_trusted FROM sys.check_constraints WHERE is_not_trusted = 1
UNION ALL SELECT name, is_not_trusted FROM sys.foreign_keys WHERE is_not_trusted = 1;
ALTER TABLE dbo.Orders WITH CHECK CHECK CONSTRAINT fk_cust;  -- re-trust it
SET LOCK_TIMEOUT 3000;  -- milliseconds

03Query syntax you use daily

docs: PG SELECT · docs: T-SQL SELECT

Upsert — the one real dialect fork

-- PostgreSQL: ON CONFLICT is atomic and needs a unique index on the conflict target
INSERT INTO inventory (sku, qty) VALUES ('A-1', 5)
ON CONFLICT (sku) DO UPDATE SET qty = inventory.qty + EXCLUDED.qty, updated_at = now()
WHERE inventory.qty <> EXCLUDED.qty            -- skip no-op writes: no dead tuple, no WAL
RETURNING sku, qty;
-- ON CONFLICT DO NOTHING still burns a sequence value; MERGE exists since 15 but has no ON CONFLICT's atomicity.

-- SQL Server: the safe upsert is NOT bare MERGE. Take the key lock in the same statement.
BEGIN TRAN;
  UPDATE dbo.Inventory WITH (UPDLOCK, SERIALIZABLE) SET Qty += @qty WHERE Sku = @sku;
  IF @@ROWCOUNT = 0 INSERT dbo.Inventory (Sku, Qty) VALUES (@sku, @qty);
COMMIT;

MERGE on SQL Server has a long tail of open bugs (unique-violation races without HOLDLOCK, wrong results with filtered indexes, halloween-protection costs). It is fine for a single-threaded ETL batch; it is not the concurrent upsert. On PostgreSQL the ranking is the reverse: ON CONFLICT first, MERGE 15 only for multi-action ETL — and MERGE ... RETURNING plus WHEN NOT MATCHED BY SOURCE arrived in 17.

Paging, dedup, hierarchy

Keyset (seek) pagination both
WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 50 — O(1) per page. OFFSET 200000 reads and throws away 200 000 rows.
Latest row per group PG
SELECT DISTINCT ON (customer_id) * FROM orders ORDER BY customer_id, created_at DESC; — PG-only, and the cheapest form.
Latest row per group portable
ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) = 1, or CROSS APPLY/LATERAL + TOP 1/LIMIT 1 when the outer set is small.
Correlated sub-select
MSSQL CROSS APPLY / OUTER APPLY · PG JOIN LATERAL / LEFT JOIN LATERAL ... ON true.
Recursive CTE
PG needs WITH RECURSIVE; MSSQL does not, but caps at OPTION (MAXRECURSION 100) by default — set it to 0 deliberately, never blindly.
CTE materialisation PG
Inlined since 12. Force with WITH x AS MATERIALIZED (...) / NOT MATERIALIZED. On SQL Server a CTE is always just a name — it is re-evaluated per reference.
Generate a series
PG generate_series('2026-01-01'::date, '2026-12-31', '1 day') · MSSQL GENERATE_SERIES(1, 100, 1) 2022, else a numbers table.
Window frame reuse
Both support the WINDOW w AS (...) clause — SQL Server got it in 2022. ROWS BETWEEN ≠ RANGE BETWEEN: RANGE ties peers together and is the default.
NULL-safe equality
a IS NOT DISTINCT FROM b — PG always, SQL Server 2022. Replaces (a = b OR (a IS NULL AND b IS NULL)).
Aggregate to string
STRING_AGG(name, ',') WITHIN GROUP (ORDER BY name) MSSQL 2017, ordering 2022 · string_agg(name, ',' ORDER BY name) PG.
Explicit ordering of NULLs
PG ORDER BY x DESC NULLS LAST (NULLs sort high by default). MSSQL has no clause — NULLs sort low; emulate with ORDER BY CASE WHEN x IS NULL THEN 1 ELSE 0 END, x.

JSON, both engines

-- PostgreSQL: jsonb. -> keeps json, ->> returns text, #>> takes a path.
SELECT doc ->> 'id', doc -> 'items' -> 0 ->> 'sku', doc #>> '{shipping,city}' FROM events;
SELECT * FROM events WHERE doc @> '{"status":"paid"}';            -- containment; GIN-indexable
CREATE INDEX ix_events_doc ON events USING gin (doc jsonb_path_ops);  -- @> only, ~2x smaller
CREATE INDEX ix_events_status ON events ((doc ->> 'status'));         -- expression index for one key
SELECT * FROM json_table(doc, '$.items[*]' COLUMNS (sku text PATH '$.sku')) t;  -- SQL/JSON, PG 17

-- SQL Server 2025: native json type, no more nvarchar(max) + ISJSON
ALTER TABLE dbo.Events ALTER COLUMN Doc json NOT NULL;
SELECT JSON_VALUE(Doc, '$.id'), JSON_QUERY(Doc, '$.items') FROM dbo.Events;
SELECT e.Id, i.sku FROM dbo.Events e CROSS APPLY OPENJSON(e.Doc, '$.items')
  WITH (sku nvarchar(50) '$.sku', qty int '$.qty') i;
SELECT JSON_OBJECTAGG(k VALUE v), JSON_ARRAYAGG(v ORDER BY k) FROM dbo.Settings;  -- 2025
-- Indexing JSON on SQL Server is still a PERSISTED computed column + an index on it.

Rule of thumb both sides: anything you filter or join on gets promoted out of the document into a real column (generated/computed, indexed). JSON is for the tail of attributes you only project — not for your access paths.

-- SQL Server: rebuild vs reorganize. Fragmentation alone is a weak signal; page density matters more.

FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'SAMPLED') s

docs: PG EXPLAIN · docs: Query Store 
-- PostgreSQL: the only EXPLAIN worth typing. 18 shows BUFFERS in ANALYZE by default.
EXPLAIN (ANALYZE, BUFFERS, SETTINGS, WAL, VERBOSE, FORMAT TEXT) SELECT ...;

SELECT query, calls, round(total_exec_time) ms, round(mean_exec_time,2) avg_ms, rows
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;   -- extension, load in shared_preload_libraries

ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;       -- more histogram buckets on a skewed column
CREATE STATISTICS st_city_zip (dependencies, ndistinct) ON city, zip FROM addr;  -- extended stats for correlated columns
SELECT pid, state, wait_event_type, wait_event, now()-query_start AS age, left(query,80)
FROM pg_stat_activity WHERE state <> 'idle' ORDER BY age DESC;

-- SQL Server: measure first, then read the plan
SET STATISTICS IO, TIME ON;                        -- logical reads is the tuning currency, not duration
-- Query Store (on by default for new DBs since 2022; for readable secondaries by default since 2025)
ALTER DATABASE Orders SET QUERY_STORE = ON (OPERATION_MODE = READ_WRITE, QUERY_CAPTURE_MODE = AUTO);
SELECT TOP 20 qt.query_sql_text, rs.avg_duration/1000.0 AS avg_ms, rs.count_executions
FROM sys.query_store_runtime_stats rs
JOIN sys.query_store_plan p ON p.plan_id = rs.plan_id
JOIN sys.query_store_query q ON q.query_id = p.query_id
JOIN sys.query_store_query_text qt ON qt.query_text_id = q.query_text_id
ORDER BY rs.avg_duration DESC;
EXEC sp_query_store_force_plan @query_id = 42, @plan_id = 77;      -- plan stability without a plan guide
-- Blocking / waits right now
SELECT session_id, blocking_session_id, wait_type, wait_time, last_wait_type, command
FROM sys.dm_exec_requests WHERE blocking_session_id <> 0;
Parameter sniffing MSSQL
Diagnose with Query Store regressed queries. Fixes in order: fix the index → PSPO 2022 and OPPO 2025 (multiple plans per statement) → OPTION (RECOMPILE) on the one statement → OPTIMIZE FOR UNKNOWN last.
Compile storms MSSQL
OPTIMIZED_SP_EXECUTESQL 2025 serialises compilation of identical sp_executesql batches — the fix for a thundering herd of ad-hoc parameterised SQL.
Plan hints PG
There are none. You get enable_seqscan = off (session-level, a diagnostic not a fix), pg_hint_plan, or better stats. PG 19 adds pg_plan_advice — the first supported way to nudge plans.
Cost knobs PG
random_page_cost = 1.1 on SSD (default 4.0 assumes spinning disks), effective_cache_size = 0.75 × RAM, effective_io_concurrency = 200.
Intelligent query processing MSSQL
Free with the compat level: adaptive joins + memory grant feedback (2017), batch mode on rowstore + scalar UDF inlining + table variable deferred compilation (2019), PSPO + CE feedback + optimized plan forcing (2022), CE feedback for expressions + OPPO + DOP feedback on by default (2025).
Kill a runaway query
PG SELECT pg_cancel_backend(pid); then pg_terminate_backend(pid) · MSSQL KILL 57; (watch estimated_completion_time for rollback).
Block a known-bad query MSSQL
ABORT_QUERY_EXECUTION Query Store hint 2025 — refuse a nonessential query outright instead of chasing its owner.

The one-sentence contrast: PostgreSQL pays for MVCC in vacuum and bloat, SQL Server pays for locking in blocking — so the PG incident is “autovacuum can’t keep up behind a long transaction” and the SQL Server incident is “a head blocker is holding an X lock while the app waits”. RCSI moves SQL Server onto the PostgreSQL trade-off, with the version store in tempdb.

08Transactions & procedural code

docs: PL/pgSQL · docs: TRY…CATCH 
-- PostgreSQL: a function is always inside the caller's transaction; only a PROCEDURE can COMMIT.
CREATE OR REPLACE PROCEDURE settle_batch(p_day date)
LANGUAGE plpgsql AS $$
DECLARE v_id bigint;
BEGIN
  FOR v_id IN SELECT id FROM invoice WHERE due = p_day LOOP
    BEGIN
      UPDATE invoice SET settled = true WHERE id = v_id;
      COMMIT;                                   -- procedures only, PG 11+
    EXCEPTION WHEN serialization_failure THEN   -- 40001: retry is the caller's job in PG
      RAISE NOTICE 'retry %', v_id;
    END;
  END LOOP;
END $$;
-- Any BEGIN...EXCEPTION block creates a subtransaction (XID). Millions of them = SLRU contention. Avoid in hot loops.
SET default_transaction_isolation = 'read committed';
SAVEPOINT sp1;  ROLLBACK TO SAVEPOINT sp1;      -- after ANY error the whole tx is aborted until you roll back

-- SQL Server: the header every procedure should have
CREATE OR ALTER PROCEDURE dbo.SettleBatch @Day date AS
BEGIN
  SET NOCOUNT ON;                 -- stop DONE_IN_PROC chatter
  SET XACT_ABORT ON;              -- make errors roll back the transaction; without it some errors leave it open
  BEGIN TRY
    BEGIN TRAN;
      UPDATE dbo.Invoice SET Settled = 1 WHERE Due = @Day;
    COMMIT;
  END TRY
  BEGIN CATCH
    IF XACT_STATE() <> 0 ROLLBACK;
    THROW;                        -- 2012+; RAISERROR loses the original error number
  END CATCH
END
Retryable errors
PG SQLSTATE 40001 serialization failure, 40P01 deadlock · MSSQL 1205 deadlock victim, 1222 lock timeout, 49918/40501/40613 on Azure SQL. Retry with jitter, cap at 3–5.
Nested transactions
Neither engine has them. MSSQL @@TRANCOUNT only counts; an inner ROLLBACK rolls back everything. PG uses SAVEPOINT.
Set-returning function
PG RETURNS TABLE (...) LANGUAGE sql — inlined when it is a plain SQL function, so prefer LANGUAGE sql over plpgsql. MSSQL inline TVF (RETURNS TABLE AS RETURN SELECT ...) is inlined; a multi-statement TVF is not and estimates 100 rows (1 before 2014).
Scalar UDFs MSSQL
Historically a per-row interpreter call and a silent parallelism killer. Froid inlining 2019 fixes many; check sys.sql_modules.is_inlineable before you trust it.
Bulk parameters
PG unnest($1::bigint[], $2::text[]) or COPY · MSSQL table-valued parameter (CREATE TYPE ... AS TABLE) or SqlBulkCopy. Never a loop of single-row round trips.
Change data out
PG logical replication / wal2json / Debezium on the replication slot. MSSQL CDC, change tracking, or change event streaming to Event Hubs / Fabric Eventstream as CloudEvents 2025, PREVIEW_FEATURES.
Returning modified rows
PG RETURNING, and 18 both versions: UPDATE ... RETURNING OLD.qty AS before, NEW.qty AS after. MSSQL OUTPUT inserted.*, deleted.* — but OUTPUT ... INTO a table with triggers or FKs silently forbids the direct form.

11Gotchas, one line each

docs: PG “Don't do this”

PostgreSQL

  • An idle in transaction session pins xmin: vacuum stops, bloat grows, wraparound clock ticks. Set idle_in_transaction_session_timeout.
  • COUNT(*) on a big table is a full scan — the visibility map only helps index-only scans; use pg_class.reltuples for an estimate.
  • work_mem is per node per worker: 64 MB × 8 nodes × 4 workers × 50 sessions is not 64 MB.
  • Unquoted identifiers fold to lower case; ORMs that quote "CamelCase" force you to quote forever.
  • char(n) pads with spaces and is never faster than text; timestamp without a zone loses the offset; money depends on lc_monetary.
  • A DDL statement waits for an AccessExclusive lock — and every reader queues behind it. Always SET lock_timeout first and retry.
  • Deep OFFSET pagination is O(offset); keyset pagination is O(1).
  • REINDEX without CONCURRENTLY takes an exclusive lock; VACUUM FULL rewrites the table and takes one for the whole rewrite (PG 19's REPACK CONCURRENTLY finally fixes this).
  • A dropped or inactive replication slot is either retaining WAL until the disk fills, or losing you the subscriber. Monitor both.
  • Upgrading the OS can change ICU/glibc collation ordering and silently corrupt text indexes — REINDEX after any libc change.
  • PG 18 defaults generated columns to virtual: an existing script that assumed STORED now computes at read time. Say STORED explicitly.

SQL Server

  • WITH (NOLOCK) is not "read uncommitted, no big deal": it can return a committed row twice or skip it entirely. RCSI is the answer.
  • Implicit conversion kills seeks: an nvarchar parameter against a varchar column scans. Check the plan for CONVERT_IMPLICIT.
  • Non-SARGable predicates: WHERE YEAR(d) = 2026, WHERE col + 0 = @x, WHERE LEFT(name,3) = 'abc' — rewrite as a range.
  • Naming a user procedure sp_something makes the engine look in master first and defeats plan caching.
  • MERGE without HOLDLOCK races; several optimizer bugs remain open. Prefer explicit UPDATE+INSERT.
  • Table variables estimate 1 row (100 with deferred compilation, 2019+); temp tables get statistics. Use #temp for anything over a few hundred rows.
  • A unique index allows only one NULL; use a filtered unique index for "unique when present".
  • SET XACT_ABORT ON or an error can leave a transaction open holding locks; SET NOCOUNT ON or clients pay for row-count messages.
  • Shrinking a data file fragments every index and the space comes straight back — it is not maintenance.
  • Auto-growth in percent, or a 1 MB default, means growth storms; pre-size and set fixed increments, with instant file initialisation enabled.
  • Constraints added WITH NOCHECK are untrusted and the optimizer ignores them for good.
  • SQL Server 2025 features marked preview (vector index, VECTOR_SEARCH, change event streaming, fuzzy matching) need ALTER DATABASE SCOPED CONFIGURATION SET PREVIEW_FEATURES = ON — do not design production around them.
