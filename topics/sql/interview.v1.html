01SQL semantics, joins & grouping

The universal screener. Everyone gets two or three of these in the first thirty minutes, and the point is not whether you know LEFT JOIN — it is whether you reason about SQL as set logic with a defined evaluation order rather than as a sequence of steps. At mid level, correct answers plus one gotcha (NULLs in NOT IN) is enough; at senior and above the interviewer expects you to spot the semantic bug in a query on sight and explain why the optimizer is free to reorder joins but not to change results.

Walk me through the logical processing order of a SELECT, and why it matters.screener

Logically SQL evaluates FROM/JOIN → WHERE → GROUP BY → HAVING → window functions → SELECT (including aliases) → DISTINCT → ORDER BY → OFFSET/FETCH. That order explains three things interviewers actually care about: you cannot use a SELECT alias in WHERE (it does not exist yet) but you can in ORDER BY; WHERE filters rows and HAVING filters groups; and window functions run after HAVING, so you cannot filter on a window result without wrapping the query. This is logical order only — the optimizer physically executes whatever equivalent plan is cheapest, and both engines will happily push a HAVING predicate down to WHERE when it is safe. PostgreSQL is slightly more permissive than SQL Server: it allows GROUP BY on a select-list alias or ordinal and supports functional dependency on the primary key, so GROUP BY t.id lets you select any other column of t; SQL Server requires every non-aggregated column in the GROUP BY list.

Example

-- fails everywhere: the alias does not exist during WHERE
SELECT price * qty AS total FROM line_item WHERE total > 100;

-- correct: repeat the expression, or wrap it
SELECT price * qty AS total FROM line_item WHERE price * qty > 100;

-- PostgreSQL 9.1+ only: functional dependency on the PK
SELECT c.id, c.name, count(o.id)
FROM customer c LEFT JOIN "order" o ON o.customer_id = c.id
GROUP BY c.id;                 -- c.name is implied by the PK; T-SQL needs it listed

Follow-ups

  • Where does DISTINCT fit? — After SELECT, which is why SELECT DISTINCT x ORDER BY y is an error unless y is in the select list.
  • Why can't you filter a window function in WHERE? — Windows are computed after the row set is fixed; wrap it in a CTE/derived table and filter outside.
  • Does the order affect performance? — No; it defines meaning. Physical order is the optimizer's choice, constrained only by producing the same result.

Wrong answer that gets people rejected: “HAVING is just WHERE for aggregates, so it is slower — always use WHERE.” The two do different things, and both engines push non-aggregate HAVING predicates into the filter anyway; claiming a performance rule where there is a semantic one signals cargo-cult SQL.

What is the difference between INNER, LEFT, RIGHT, FULL and CROSS JOIN — and when does a LEFT JOIN silently become an INNER JOIN?screener

INNER keeps only matched pairs; LEFT keeps every left row, padding unmatched right columns with NULL; RIGHT is its mirror; FULL keeps unmatched rows from both sides; CROSS is the unrestricted Cartesian product. The trap interviewers set is the predicate placement: a condition on the right table in the WHERE clause is evaluated after the join, and because the padded NULLs fail it, the outer join degrades to an inner join. The fix is to move the condition into the ON clause, where it participates in matching instead of filtering. A predicate on the left table is fine in WHERE — and there the difference is only readability. Identical in both engines; nothing vendor-specific here.

Example

-- BUG: customers with no 2026 orders disappear entirely
SELECT c.id, o.total
FROM customer c LEFT JOIN "order" o ON o.customer_id = c.id
WHERE o.placed_at >= DATE '2026-01-01';

-- correct: the date is part of "what counts as a match"
SELECT c.id, o.total
FROM customer c LEFT JOIN "order" o
  ON o.customer_id = c.id AND o.placed_at >= DATE '2026-01-01';

-- and if you really wanted "customers with no such order":
... LEFT JOIN ... ON ... WHERE o.customer_id IS NULL;   -- anti-join

Follow-ups

  • How do you write an anti-join? — NOT EXISTS (safest), or LEFT JOIN ... WHERE right.key IS NULL; avoid NOT IN on a nullable column.
  • Is RIGHT JOIN ever justified? — Rarely; teams normalize on LEFT for readability, and reviewers treat a RIGHT JOIN as a smell to check.
  • What does the optimizer do with an outer join? — It cannot freely reorder outer joins the way it reorders inner joins, so a chain of LEFT JOINs constrains the plan space more than the same query with inner joins.

Wrong answer: “ON and WHERE are equivalent, the optimizer sorts it out.” For inner joins that is true; for outer joins it changes the result set, and saying otherwise is the single most common way candidates fail the join question.

EXISTS vs IN vs JOIN for “rows that have a related row” — which do you use and why?mid

Prefer EXISTS/NOT EXISTS: it expresses semi-join and anti-join semantics exactly, is NULL-safe, and cannot duplicate rows. IN with a subquery is usually optimized into the same semi-join, but NOT IN is a trap — if the subquery returns even one NULL the whole predicate evaluates to UNKNOWN and you get zero rows. A JOIN is the wrong tool unless you need columns from the other table, because a one-to-many join multiplies rows and people then paper over it with DISTINCT, which forces a sort or hash the plan did not need. Both SQL Server and PostgreSQL implement semi-joins natively, so EXISTS does not mean “runs the subquery once per row”; the plan shows a semi-join operator that stops at the first match.

Example

-- returns NOTHING if any customer_id in "order" is NULL
SELECT * FROM customer WHERE id NOT IN (SELECT customer_id FROM "order");

-- NULL-safe, and the plan is an anti semi-join
SELECT * FROM customer c
WHERE NOT EXISTS (SELECT 1 FROM "order" o WHERE o.customer_id = c.id);

Follow-ups

  • Does SELECT 1 vs SELECT * inside EXISTS matter? — No; both engines ignore the select list of an EXISTS subquery.
  • When is IN (list of literals) a problem? — Very long lists blow up compile time and defeat plan reuse; pass a table-valued parameter (SQL Server) or = ANY($1) with an array (PostgreSQL).
  • When would you still join? — When you need the related columns, or when a hash join over the whole set beats per-row probing for a large batch.

Wrong answer: “EXISTS is faster than IN because it short-circuits row by row.” The performance story is essentially identical after optimization; the real reason to prefer EXISTS is NULL semantics and row multiplication, and reciting the folklore version signals you have never read a plan.

Explain UNION vs UNION ALL, and INTERSECT/EXCEPT — including how they treat NULLs.screener

UNION concatenates and then de-duplicates, which costs a sort or hash aggregate over the combined set; UNION ALL just concatenates and is the default choice unless you have proven duplicates are possible and unwanted. INTERSECT and EXCEPT (SQL Server and PostgreSQL both spell it EXCEPT; Oracle's MINUS is not portable) also remove duplicates. The set operators use distinctness, not equality: two NULLs are considered the same value, so NULL matches NULL in INTERSECT/EXCEPT and collapses under UNION — the opposite of what = does. This makes EXCEPT a neat NULL-safe row-comparison tool for reconciliation and migration verification.

Example

-- NULL-safe "are these two result sets identical?" check
(SELECT * FROM staging.customer EXCEPT SELECT * FROM dbo.customer)
UNION ALL
(SELECT * FROM dbo.customer EXCEPT SELECT * FROM staging.customer);
-- empty result = the sets match, NULLs included

Follow-ups

  • Cost of UNION over two indexed sources? — It usually adds a distinct sort/hash; with UNION ALL plus a proven-disjoint predicate you keep a streaming plan.
  • Column matching rules? — By position and count, not by name; types must be implicitly convertible, and the result takes the higher-precedence type.
  • PostgreSQL-only nicety? — IS DISTINCT FROM gives you the same NULL-safe comparison inline; SQL Server has no such operator, so you emulate it with EXISTS (SELECT a INTERSECT SELECT b).

Wrong answer: “UNION and UNION ALL return the same rows, UNION ALL is just faster.” They differ in results whenever duplicates exist, and the de-duplication is exactly what costs the sort.

Why does adding a join to a query sometimes multiply the rows, and how do you fix an aggregate that is now wrong?mid

A join produces the Cartesian product of matching rows on both sides, so joining a one-to-many child table multiplies each parent row by its child count. When you then SUM a parent column you sum it once per child — the classic “my revenue report doubled after we added shipments” bug. Two clean fixes: aggregate each child in its own subquery/lateral before joining, or use SUM(DISTINCT ...) only when the value is genuinely unique per parent (usually it is not, so avoid it). Both engines support the pre-aggregation shape, and PostgreSQL's LEFT JOIN LATERAL and SQL Server's OUTER APPLY are the same tool for a correlated per-parent aggregate.

Example

-- SQL Server
SELECT o.id, o.total, s.n_shipments
FROM [order] o
OUTER APPLY (SELECT COUNT(*) AS n_shipments FROM shipment s WHERE s.order_id = o.id) s;

-- PostgreSQL
SELECT o.id, o.total, s.n_shipments
FROM "order" o
LEFT JOIN LATERAL (SELECT count(*) AS n_shipments FROM shipment s WHERE s.order_id = o.id) s ON true;

Follow-ups

  • Why not just SELECT DISTINCT? — It hides the fan-out, breaks any aggregate, and adds a sort; reviewers treat a DISTINCT added to fix a count as a defect.
  • APPLY/LATERAL cost? — It is a correlated nested loop; fine for a few thousand outer rows with a supporting index, bad for millions — then pre-aggregate with GROUP BY and hash join.
  • How do you catch this in review? — Any query joining two or more child tables and aggregating is guilty until proven otherwise; ask for the row count before and after.

Wrong answer: “Add DISTINCT and the numbers come out right.” DISTINCT fixes duplicate rows, never a duplicated sum, and it masks the modelling error underneath.

MERGE / UPSERT: how do you write an idempotent insert-or-update, and what are the pitfalls?senior

PostgreSQL's idiomatic form is INSERT ... ON CONFLICT (key) DO UPDATE SET ... , which is atomic against a unique index and is the correct answer there; MERGE exists since PG 15 (and gained RETURNING and a WHEN NOT MATCHED BY SOURCE clause in PG 17) but it is not concurrency-safe in the way ON CONFLICT is — under concurrent inserts MERGE can raise a unique violation, so you still need a retry. SQL Server has MERGE, and the honest senior answer is that many teams avoid it: it has a long history of bugs, and it is not atomic by itself — without HOLDLOCK/SERIALIZABLE on the target two concurrent MERGEs can both take the NOT MATCHED branch and produce duplicate-key errors or lost updates. The safe T-SQL patterns are MERGE ... WITH (HOLDLOCK), or an explicit UPDATE then INSERT ... WHERE NOT EXISTS inside a transaction with the right lock hint, plus retry on 2601/2627.

Example

-- PostgreSQL: atomic against the unique index on (tenant_id, sku)
INSERT INTO inventory (tenant_id, sku, qty)
VALUES ($1, $2, $3)
ON CONFLICT (tenant_id, sku)
DO UPDATE SET qty = inventory.qty + EXCLUDED.qty, updated_at = now()
RETURNING id, qty;

-- SQL Server: HOLDLOCK is not optional
MERGE dbo.inventory WITH (HOLDLOCK) AS t
USING (VALUES (@tenant, @sku, @qty)) AS s (tenant_id, sku, qty)
   ON t.tenant_id = s.tenant_id AND t.sku = s.sku
WHEN MATCHED THEN UPDATE SET t.qty = t.qty + s.qty, t.updated_at = SYSUTCDATETIME()
WHEN NOT MATCHED THEN INSERT (tenant_id, sku, qty) VALUES (s.tenant_id, s.sku, s.qty);

Follow-ups

  • What must exist for ON CONFLICT to work? — A unique index or constraint on exactly the inferred columns; there is no “conflict on an arbitrary predicate”.
  • Does ON CONFLICT DO NOTHING still burn sequence values? — Yes; the nextval is consumed before the conflict is detected, so identity gaps are expected and are not a bug.
  • Bulk upsert of 100k rows? — Stage into a temp/unlogged table, then one set-based MERGE/ON CONFLICT; never row-by-row round trips.

Wrong answer: “MERGE is atomic, that is the whole point.” In SQL Server it is a single statement but not automatically serializable, and in PostgreSQL it is explicitly documented as able to fail with a unique violation under concurrency — a lead who deploys unhinted MERGE upserts will meet duplicate-key alerts at peak traffic.

How do you page through a large result set correctly?senior

OFFSET n ROWS FETCH NEXT m (both engines; SQL Server since 2012, requires an ORDER BY) is fine for the first few pages and terrible deep in the set, because the engine still produces and discards the first n rows — page 10,000 costs 10,000 pages of work. The senior answer is keyset (seek) pagination: order by a unique, indexed tuple and pass the last row's values as the cursor, so every page is an index seek of constant cost. Keyset paging also avoids the correctness bug in offset paging — rows inserted or deleted between requests shift the window, so users see duplicates or skip records. The price is that you cannot jump to an arbitrary page number, which is usually an acceptable trade for an infinite-scroll or API cursor; if the product truly needs numbered pages, cap the depth or precompute a row-number snapshot.

Example

-- keyset: ORDER BY must match a unique index prefix, ties broken by the PK
SELECT id, placed_at, total
FROM "order"
WHERE (placed_at, id) < ($1, $2)      -- PostgreSQL row-value comparison
ORDER BY placed_at DESC, id DESC
FETCH FIRST 50 ROWS ONLY;

-- SQL Server has no row-value comparison; expand it
WHERE placed_at < @last_at
   OR (placed_at = @last_at AND id < @last_id)
ORDER BY placed_at DESC, id DESC
OFFSET 0 ROWS FETCH NEXT 50 ROWS ONLY;

Follow-ups

  • Why must the sort key be unique? — Otherwise the cursor is ambiguous and rows are skipped or repeated at page boundaries; append the PK.
  • How do you return a total count? — You usually should not; an exact COUNT(*) over the same predicate doubles the work. Use an approximate count or “more results” semantics.
  • The old T-SQL pattern? — ROW_NUMBER() OVER (...) in a CTE filtered by range; still common in pre-2012 codebases and it has the same deep-page cost as OFFSET.

Wrong answer: “OFFSET/FETCH is efficient because the database skips those rows.” It does not skip them, it produces and throws them away — and the candidate who believes otherwise ships the API that times out on page 500.

A junior sends you a query with SELECT *, a scalar subquery in the select list and implicit conversions. What do you say in review, in priority order?principal

Lead review is about ordering the objections by blast radius, not listing style nits. First the correctness and stability risk: SELECT * couples the app to column order and to any future column, breaks covering indexes, and silently changes the contract when someone adds a wide column. Second the plan risk: an implicit conversion on a column (say WHERE varchar_col = @nvarchar_param in SQL Server, or WHERE text_col = 123 in PostgreSQL) makes the predicate non-SARGable and turns a seek into a scan — in SQL Server it shows up as a CONVERT_IMPLICIT and a Type conversion may affect CardinalityEstimate warning in the plan. Third, the scalar subquery in the select list is a per-row correlated execution; rewrite it as a join or lateral so the optimizer can choose a hash aggregate. Then I'd ask what the query is for, because the real fix is often that the endpoint should not return that shape at all.

Example

-- SQL Server: nvarchar parameter against a varchar column = index scan
DECLARE @sku nvarchar(50) = N'ABC-123';
SELECT * FROM dbo.product WHERE sku = @sku;    -- CONVERT_IMPLICIT(nvarchar, sku)

-- fixed: match the types (or fix the column), and name the columns
DECLARE @sku2 varchar(50) = 'ABC-123';
SELECT id, sku, name, price FROM dbo.product WHERE sku = @sku2;

Follow-ups

  • Why is nvarchar→varchar worse than the reverse? — Data-type precedence converts the lower-precedence side, so the column gets converted and the index is unusable; the reverse converts only the parameter.
  • Is SELECT * ever fine? — In EXISTS, in ad-hoc exploration, and in a view you fully control; never in application code paths.
  • How do you make this systemic? — A lint rule in CI plus a plan-regression check; a review comment fixes one query, a rule fixes the class.

Wrong answer: leading with “SELECT * is bad practice” and stopping there. Style-only feedback at lead level reads as not having looked at the plan; the implicit conversion is the thing that will page someone at 3am.

02Indexes & index design

The single most-asked technical area, and the one where the gap between “knows the words” and “has fixed a production incident” is most visible. Expect to be handed a table and a query and asked for the index — then asked what it costs on writes, how you would prove it helped, and how you decide which of the 14 existing indexes to drop. At mid level you need composite key order and covering indexes; at senior and principal you need index maintenance strategy, online rebuild semantics, and the judgment to say “no index — fix the query”.

Clustered vs nonclustered index — and how does PostgreSQL differ from SQL Server here?screener

In SQL Server a clustered index is the table: the leaf level holds the full rows in key order, so there is exactly one per table, and a table without one is a heap. Nonclustered indexes store the key columns plus a row locator — the clustering key if there is a clustered index, or a RID if it is a heap — so a nonclustered seek that needs extra columns performs a key lookup back into the clustered index. PostgreSQL has no clustered indexes at all: the heap is unordered, every index is secondary and stores a tuple id (ctid), and CLUSTER table USING index is a one-off physical reorder that is not maintained afterwards. The practical consequence is that PostgreSQL always does a heap fetch unless the query is satisfied by an index-only scan on an all-visible page, whereas SQL Server's clustered index gives ordered range scans for free on the clustering key.

Example

-- SQL Server: narrow, ever-increasing clustering key keeps NC indexes small
CREATE TABLE dbo.[order] (
  id bigint IDENTITY CONSTRAINT PK_order PRIMARY KEY CLUSTERED,
  customer_id int NOT NULL, placed_at datetime2(3) NOT NULL, total decimal(19,4) NOT NULL);
CREATE NONCLUSTERED INDEX IX_order_customer ON dbo.[order] (customer_id, placed_at)
  INCLUDE (total);      -- covering: no key lookup

-- PostgreSQL: the PK is just a unique btree index over the heap
CREATE TABLE "order" (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, ...);
CREATE INDEX ON "order" (customer_id, placed_at) INCLUDE (total);  -- INCLUDE since PG 11

Follow-ups

  • Why keep the clustering key narrow in SQL Server? — Every nonclustered index carries it as the row locator, so a wide GUID key inflates all of them.
  • Is a heap ever right in SQL Server? — Staging tables written once and bulk-read; otherwise the lack of an ordered access path and forwarded-record problem outweigh the write savings.
  • What does PG's CLUSTER actually cost? — A full table rewrite holding an ACCESS EXCLUSIVE lock; pg_repack is the online alternative.

Wrong answer: “PostgreSQL's primary key is a clustered index like SQL Server's.” It is not, and the follow-on beliefs — that range scans on the PK are physically sequential, that there is one index “per table” — lead to wrong capacity and tuning decisions.

You have a query filtering on A = ? and B > ? and sorting by C. What composite index do you create, and in what column order?mid

Equality columns first, then the range column, then the sort — the classic “equality, range, order-by” rule — so here (A, B) with C only useful if it follows a column the index can still be ordered by. The reason is mechanical: a B-tree can seek on a leading equality prefix and then scan a contiguous range, but once you hit a range predicate the remaining key columns are no longer in globally sorted order, so a trailing C cannot provide the sort. If the sort matters more than the range, (A, C) with B evaluated as a residual predicate can win. Add the extra selected columns as INCLUDE to make the index covering — supported in SQL Server since 2005 and PostgreSQL since 11 — because included columns live only at the leaf and do not widen the tree. This applies identically to both engines; PostgreSQL 18 adds B-tree skip scan, which can use an index whose leading column is unconstrained, but it is a safety net, not a reason to get the order wrong.

Example

-- WHERE tenant_id = ? AND created_at >= ? ORDER BY created_at DESC
CREATE INDEX IX_event_tenant_created ON dbo.event (tenant_id, created_at DESC) INCLUDE (payload_size);
-- tenant_id equality → seek; created_at range AND sort are both served, because the
-- range column is also the sort column and the index direction matches.

Follow-ups

  • How many columns before it stops paying? — Once the leading columns are selective enough that the residual filter is cheap; each extra key column widens every level of the tree.
  • Key vs INCLUDE? — Key columns support seeking, ordering and uniqueness; included columns only avoid the lookup. Put anything you merely return in INCLUDE.
  • Does index direction matter? — Both engines can scan an index backwards, so a single-column sort rarely needs DESC; a mixed ORDER BY a ASC, b DESC does need the matching declaration.

Wrong answer: “Put the most selective column first.” That folklore ignores the access pattern: a highly selective column that is not in the predicate at all is useless as a leading key, and equality-before-range beats raw selectivity every time.

What makes a predicate non-SARGable, and how do you rewrite the common cases?mid

A predicate is SARGable (search-argument-able) when the indexed column appears alone on one side, so the engine can convert it into a seek range. Wrapping the column in a function, doing arithmetic on it, or forcing an implicit conversion destroys that: WHERE YEAR(created_at) = 2026, WHERE total * 1.2 > 100, WHERE CAST(id AS varchar) = '42' all scan. The rewrites are mechanical — turn function-on-column into a half-open range, move arithmetic to the constant side, fix the type. Leading wildcards (LIKE '%foo') are inherently non-SARGable in both engines; the answers are a trigram index in PostgreSQL (pg_trgm + GIN) or full-text search / a computed reversed column in SQL Server. Both engines also offer the escape hatch of indexing the expression itself: PostgreSQL has true expression indexes, SQL Server needs a persisted computed column with an index on it.

Example

-- non-SARGable
WHERE YEAR(created_at) = 2026
-- SARGable half-open range (also correct across time zones and fractional seconds)
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'

-- PostgreSQL: index the expression instead
CREATE INDEX ON customer (lower(email));   -- then WHERE lower(email) = lower($1)
-- SQL Server equivalent
ALTER TABLE dbo.customer ADD email_lower AS LOWER(email) PERSISTED;
CREATE INDEX IX_customer_email_lower ON dbo.customer (email_lower);

Follow-ups

  • Is LIKE 'foo%' SARGable? — Yes, it becomes a range seek — but in PostgreSQL only if the index uses a text_pattern_ops operator class or the database is in the C collation.
  • How do you spot it in a plan? — SQL Server shows the predicate under Predicate rather than Seek Predicate, plus a CONVERT_IMPLICIT; PostgreSQL shows Filter rather than Index Cond.
  • Does sargable matter on a 10k-row table? — No, and saying so is part of the right answer: a full scan of a small table is fine, and index advice must be sized to the data.

Wrong answer: “Add an index on created_at and the YEAR() query will use it.” It will not — the function hides the column — and this is the most common index recommendation that fails in production.

Explain covering indexes, key lookups and the tipping point.senior

A covering index contains every column the query touches, so the engine never has to visit the base table: SQL Server shows a pure index seek with no Key Lookup, PostgreSQL an Index Only Scan. When it is not covering, each matched row costs a random lookup into the clustered index (SQL Server) or a heap fetch (PostgreSQL). Because those lookups are random I/O, there is a tipping point: past roughly a quarter to a third of the table's pages, the optimizer decides a full scan is cheaper and abandons the index entirely — which is why an index that works for a narrow customer suddenly stops working for the biggest one. The lead-level nuance is that PostgreSQL's index-only scan is conditional: it must consult the visibility map, and if pages are not marked all-visible (recently updated, vacuum behind) it falls back to heap fetches, so an index-only scan that regressed is usually a vacuum problem, not an index problem.

Example

-- PostgreSQL: check the heap fetches, they are the tell
EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, placed_at FROM "order" WHERE customer_id = 42;
--  Index Only Scan using ix_order_customer  (actual rows=118 ...)
--    Heap Fetches: 0        <-- 0 = truly index-only; a big number = vacuum lag

Follow-ups

  • Why not just include every column? — The index becomes a second copy of the table: writes double, cache is wasted, and maintenance windows grow.
  • How do you find missing covering columns in SQL Server? — The plan's Key Lookup operator lists the output columns; those are your INCLUDE list. (Do not blindly trust sys.dm_db_missing_index_details, which over-suggests and never proposes drops.)
  • What raises the tipping point? — Better correlation between index order and physical order, and a covering index, which removes the lookups from the cost entirely.

Wrong answer: “The index exists so the query will use it; if it does not, force it with a hint.” Forcing an index past its tipping point converts a fast scan into millions of random lookups — the classic self-inflicted outage after an “optimization”.

When would you use a filtered index (SQL Server) or a partial index (PostgreSQL)?senior

When the query set only ever touches a small, well-defined subset — soft-deleted rows excluded, status = 'pending' work queues, a sparse column that is non-NULL for 2% of rows. The index becomes a fraction of the size, fits in cache, and skips the write cost for rows outside the predicate. PostgreSQL's partial indexes are the more flexible of the two: the predicate can use almost any immutable expression, and the planner will use the index whenever it can prove the query predicate implies the index predicate. SQL Server's filtered indexes are more restricted — the WHERE supports only simple comparisons, no OR against different columns, no expressions — and they have a real gotcha: a parameterized query will not match a filtered index unless the optimizer can prove the match at compile time, so the parameter must be an inlined literal or the statement needs OPTION (RECOMPILE). Also required: the connection must have the correct SET options (ANSI_NULLS, QUOTED_IDENTIFIER etc. ON) or DML against the table fails outright.

Example

-- PostgreSQL: unique only among live rows (soft delete)
CREATE UNIQUE INDEX ON "user" (lower(email)) WHERE deleted_at IS NULL;

-- SQL Server: a small hot queue index over a huge table
CREATE NONCLUSTERED INDEX IX_job_pending ON dbo.job (created_at)
  INCLUDE (payload_id) WHERE status = 'pending';

Follow-ups

  • Killer use case? — A partial unique index: uniqueness that applies only to active rows, which a plain unique constraint cannot express.
  • Why did my filtered index get ignored? — Parameter sniffing cannot prove the predicate; add OPTION (RECOMPILE) or include the filter column in the index key and the query.
  • Maintenance implications? — Statistics on a filtered index only describe the filtered subset, so SQL Server's auto-update threshold is computed on full-table modifications and can leave them stale.

Wrong answer: “Filtered and partial indexes are the same feature with different names.” The predicate expressiveness and the parameterization behaviour differ enough that a design that works in PostgreSQL can quietly never be used in SQL Server.

Which index types beyond B-tree do you reach for, and for what?senior

PostgreSQL ships six: B-tree (default, ordering and equality), GIN (inverted — jsonb containment, arrays, full-text, trigram search), GiST (geometric, range types, exclusion constraints, nearest-neighbour), SP-GiST (non-balanced, e.g. quadtrees, text prefix), BRIN (block range — tiny indexes over huge naturally-ordered tables such as append-only time series) and Hash (equality only; WAL-logged and crash-safe since PG 10, still rarely worth it over B-tree). SQL Server's set is different in shape: rowstore B-trees, columnstore (clustered and nonclustered, the answer for analytical aggregation over hundreds of millions of rows), full-text, XML and spatial indexes, memory-optimized hash and range indexes for In-Memory OLTP, and — new in SQL Server 2025 — vector indexes via CREATE VECTOR INDEX for approximate nearest-neighbour search (currently gated behind the PREVIEW_FEATURES database-scoped configuration).

Example

-- PostgreSQL: BRIN over an append-only 2 TB events table
CREATE INDEX ON events USING brin (created_at) WITH (pages_per_range = 32);
-- a few MB instead of tens of GB, as long as physical order tracks created_at

-- PostgreSQL: containment queries on jsonb
CREATE INDEX ON doc USING gin (body jsonb_path_ops);   -- WHERE body @> '{"state":"open"}'

-- SQL Server: analytics over a big fact table
CREATE CLUSTERED COLUMNSTORE INDEX CCI_fact_sales ON dbo.fact_sales;

Follow-ups

  • When does BRIN fail? — When physical and logical order diverge (heavy updates, random inserts); correlation drops and the index degenerates to a scan.
  • GIN write cost? — High; mitigate with fastupdate and a sized gin_pending_list_limit, or accept slower inserts for much faster search.
  • Columnstore caveat? — It is batch-mode and delta-store based; point lookups and frequent single-row updates are its worst case, so keep an OLTP rowstore alongside if you need both.

Wrong answer: “Hash indexes are faster than B-trees for equality, so use them for lookups.” In PostgreSQL they cannot support uniqueness, ordering or multicolumn keys, and a B-tree equality probe is already O(log n) with far more optimizer support — this suggestion marks a candidate who has read a data-structures page but not a plan.

How do you decide an index should be dropped?senior

Start from usage telemetry, not opinion: SQL Server's sys.dm_db_index_usage_stats gives seeks/scans/lookups versus updates, and PostgreSQL's pg_stat_user_indexes.idx_scan gives scan counts — an index with zero reads and heavy writes over a full business cycle (including month-end and the annual report) is a candidate. Then check for redundancy: an index on (A) is fully covered by one on (A, B), and duplicates differing only in INCLUDE should be merged. The judgment part is the caveats you name unprompted: SQL Server's usage DMVs reset on restart and were historically cleared by index rebuilds, PostgreSQL's counters reset with pg_stat_reset(), and a unique index may exist to enforce a constraint rather than to be read. My practice is to disable (SQL Server: ALTER INDEX ... DISABLE) or mark invisible-by-proxy rather than drop first, keep the DDL to recreate it, and watch a full cycle.

Example

-- PostgreSQL: never-scanned indexes with their size
SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes JOIN pg_index USING (indexrelid)
WHERE idx_scan = 0 AND NOT indisunique AND NOT indisprimary
ORDER BY pg_relation_size(indexrelid) DESC;

Follow-ups

  • Cost of a redundant index? — Write amplification on every DML, more log/WAL, more to back up and rebuild, and a bigger plan search space.
  • How long do you observe? — At least one full business cycle; quarter-end reporting is where the “unused” index turns out to be load-bearing.
  • Replicas? — Usage stats are per-instance; an index unused on the primary may be the only thing keeping the read replica's reporting query alive.

Wrong answer: “Run the missing-index DMV, create everything it suggests, drop everything with zero seeks.” The missing-index feature only looks at individual compiled plans, never proposes column order well and never proposes drops; blindly applying it is how tables end up with 20 overlapping indexes.

Index maintenance: rebuild, reorganize, REINDEX — what is your actual policy?senior

My policy is that fragmentation is mostly a solved-by-modern-storage myth and statistics are the thing that actually needs regular attention. In SQL Server I update statistics frequently and rebuild selectively: ALTER INDEX ... REORGANIZE (always online, resumable by nature, compacts pages) for moderate fragmentation, REBUILD WITH (ONLINE = ON) for genuinely damaged indexes, on Enterprise, using RESUMABLE = ON (2017+) so a long rebuild can be paused, and WAIT_AT_LOW_PRIORITY so the online rebuild's schema-modification lock does not queue behind and in front of the whole workload. In PostgreSQL the equivalent is REINDEX INDEX CONCURRENTLY (PG 12+), which avoids the ACCESS EXCLUSIVE lock of a plain REINDEX; bloat from dead tuples is handled by autovacuum, and table-level bloat needs pg_repack or VACUUM FULL (which does take an exclusive lock). The senior framing: rebuilds are expensive, generate enormous log/WAL, and reset the very usage statistics you use to make decisions — so do them for a reason, not on a Sunday cron.

Example

-- SQL Server 2017+: pausable, low-priority online rebuild
ALTER INDEX IX_order_customer ON dbo.[order]
REBUILD WITH (ONLINE = ON (WAIT_AT_LOW_PRIORITY (MAX_DURATION = 5 MINUTES, ABORT_AFTER_WAIT = SELF)),
              RESUMABLE = ON, MAXDOP = 4);

-- PostgreSQL 12+
REINDEX INDEX CONCURRENTLY ix_order_customer;

Follow-ups

  • Does a rebuild update statistics? — In SQL Server a rebuild updates them with a full scan as a side effect; a reorganize does not. That side effect is often the real reason the rebuild “fixed” things.
  • What if REINDEX CONCURRENTLY fails? — It leaves an invalid index (_ccnew); you must drop it, and monitoring should alert on pg_index.indisvalid = false.
  • Fill factor? — Lower it only for indexes with genuinely random insert patterns; on an ever-increasing key it just wastes cache.

Wrong answer: “Rebuild every index over 30% fragmentation every night.” The 5%/30% guidance was documentation boilerplate, not a benchmark; on SSDs it mostly buys log growth and a maintenance window while the real win — updated statistics — could have been had for a fraction of the cost.

How do you create an index on a busy production table without downtime?senior

PostgreSQL: CREATE INDEX CONCURRENTLY. It takes only a SHARE UPDATE EXCLUSIVE lock so writes continue, at the cost of two table passes and a wait for all transactions older than the build. Two things I say unprompted: it cannot run inside a transaction block (which trips up migration frameworks that wrap everything), and if it fails it leaves an invalid index behind that must be dropped and retried — so the migration must be idempotent. SQL Server: CREATE INDEX ... WITH (ONLINE = ON), an Enterprise/Developer-edition feature; it still needs a brief schema-modification lock at the start and end, so pair it with WAIT_AT_LOW_PRIORITY, and use RESUMABLE = ON (2017+) to survive a failover or a maintenance-window overrun. On Standard edition you have no online build, so the honest options are a maintenance window, or building on a secondary and failing over.

Example

-- PostgreSQL, outside a transaction; retry-safe migration step
DROP INDEX CONCURRENTLY IF EXISTS ix_order_customer;   -- clean up a failed prior attempt
CREATE INDEX CONCURRENTLY ix_order_customer ON "order" (customer_id, placed_at);

Follow-ups

  • Why does CONCURRENTLY wait? — It must wait out transactions that could still see rows it has not indexed; a long-running analytics transaction can stall the build for hours.
  • Long-running index build and replication? — In PostgreSQL a long build on the primary can cause replication conflicts/lag on hot standbys; in SQL Server an AG's redo can fall behind on a large rebuild.
  • How do you validate before switching traffic? — Create it, force a test query with a hint (or SET enable_seqscan = off) on a session, compare plan and buffers, then let the optimizer choose.

Wrong answer: “CREATE INDEX CONCURRENTLY is lock-free, just run it in the migration.” It cannot run in a transaction block, it can fail and leave debris, and it does block DDL and vacuum on the table — describing it as free is how a “safe” migration hangs a deployment.

A table has 14 indexes and slow writes. How do you approach the consolidation, and how do you sell it to the team?principal

I start by quantifying the cost so the conversation is not about taste: measure write latency and log/WAL volume, then attribute — each nonclustered index is an extra B-tree maintained on every insert and on every update touching its key columns. Then I build the picture from three inputs: usage stats over a full business cycle, the actual query workload (Query Store in SQL Server 2016+, pg_stat_statements in PostgreSQL), and structural redundancy (prefix-duplicate keys, indexes differing only by INCLUDE). The output is a ranked plan: merge the redundant pairs first (lowest risk), then disable the never-read ones behind a feature-flagged migration with the recreate DDL committed alongside, one change per deploy with plan-regression monitoring in between. Selling it is about framing the risk symmetrically — “we can revert an index in 90 seconds; we cannot revert a Friday outage” — and about giving the team a rule for the future (an index needs a named query and an owner) so the count does not climb back.

Example

-- SQL Server: reads vs writes per index, the consolidation input
SELECT OBJECT_NAME(i.object_id) AS tbl, i.name,
       s.user_seeks, s.user_scans, s.user_lookups, s.user_updates
FROM sys.indexes i
LEFT JOIN sys.dm_db_index_usage_stats s
  ON s.object_id = i.object_id AND s.index_id = i.index_id AND s.database_id = DB_ID()
WHERE i.object_id = OBJECT_ID('dbo.[order]')
ORDER BY s.user_updates DESC;

Follow-ups

  • What is the safe order of operations? — Merge redundancies, then disable (not drop) the unused, then drop after a cycle; keep DDL in source control so revert is a deploy.
  • How do you catch a regression fast? — Baseline the top queries in Query Store / pg_stat_statements before the change and diff after; Query Store's forced plans give you a same-day rollback.
  • Who owns indexes going forward? — The team that owns the query. An index without a named query in the PR description is not merged.

Wrong answer: “Drop them all and see what breaks; we can always recreate.” Recreating a multi-hundred-GB index on a busy table is hours of load and — on SQL Server Standard — an outage, so “we can recreate it” is not the cheap rollback it sounds like.

03Execution plans & query tuning

If indexing is the most-asked area, plan reading is the most-differentiating one: the interviewer pastes a plan or a slow query and watches how you think. Mid-level candidates name operators; senior candidates compare estimated to actual rows and find the first place they diverge; principals talk about how the team gets plan regressions caught before production. Know both dialects — SQL Server's graphical/XML plans plus Query Store, and PostgreSQL's EXPLAIN (ANALYZE, BUFFERS).

How do you read an execution plan? Walk me through your first 60 seconds.mid

I get an actual plan, not an estimated one, then look for the first operator where estimated and actual row counts diverge by an order of magnitude — everything downstream of that is a consequence, not a cause. Next I look at what the rows cost: physical reads/buffers, spills to disk, and whether the access is a seek, a scan or a lookup. Then the join strategies, which are chosen from the estimates: nested loops on a big outer input means the optimizer thought it was small. In PostgreSQL I always run EXPLAIN (ANALYZE, BUFFERS) — buffers turn “slow” into “read 4 GB from disk” — and read the tree inside-out; in SQL Server I read the graphical plan right to left, check the warning triangles (implicit conversion, spill, no join predicate, excessive memory grant) and the operator with the largest actual row count rather than trusting the cost percentages, which are estimates and can be wildly wrong on the very plan you are debugging.

Example

-- PostgreSQL: the two lines that matter most
EXPLAIN (ANALYZE, BUFFERS, SETTINGS)
SELECT ... ;
--  Hash Join  (cost=... rows=1200 width=..) (actual time=.. rows=980431 loops=1)
--                       ^ estimate 1.2k, actual 980k  → the plan below this is built on a lie
--  Buffers: shared hit=812 read=214877        → 1.6 GB of reads

Follow-ups

  • Why not trust cost percentages in SQL Server? — They are derived from the same estimates that are wrong; a 2% operator can be 95% of the runtime.
  • What does loops=N mean in PostgreSQL? — Actual rows and times are per loop; multiply by loops to get the real total, which is the most common misreading.
  • Estimated vs actual plan in SQL Server? — The estimated plan has no runtime rows; use Live Query Statistics or sys.dm_exec_query_statistics_xml to inspect a query that is currently running and will not finish.

Wrong answer: “I look for the operator with the highest cost percentage and optimize that.” That is exactly the trap: when the estimates are wrong — which is why the query is slow — the percentages are wrong too.

Nested loops, hash join, merge join: when does the optimizer choose each, and what goes wrong?mid

Nested loops probe the inner side once per outer row: right when the outer input is small and the inner side has a selective index; catastrophic when the outer estimate was too low, because the cost is linear in a number the optimizer got wrong. Hash join builds a hash table from the smaller (build) input and probes with the other: the workhorse for large unsorted inputs and equality predicates, but it needs a memory grant and spills to tempdb / work_mem-limited temp files when the build side was underestimated. Merge join streams two inputs already sorted on the join key: cheapest of the three when the sort is free from indexes, expensive when the optimizer has to add explicit sorts. Both engines have all three; PostgreSQL exposes per-node tunables (work_mem, enable_hashjoin) while SQL Server manages memory grants centrally and has since 2017 added adaptive joins that defer the loops-vs-hash choice to runtime for the first execution.

Example

-- PostgreSQL: a hash join spilling because work_mem is too small
--  Hash  (actual rows=4200000 ...)
--    Buckets: 65536  Batches: 32  Memory Usage: 4096kB   <-- Batches > 1 = spilled to disk
-- SQL Server equivalent: the plan carries a "Hash spill" / "Sort spill" warning
-- and sys.dm_exec_query_memory_grants shows the grant vs used.

Follow-ups

  • Fix for a spilling hash join? — Fix the estimate first (statistics, rewrite, filtered index); only then consider raising work_mem per statement or a memory-grant hint.
  • Why is a nested loop with 5M outer rows fatal? — 5M index probes, each a few random reads; the plan looks “indexed” while doing more I/O than a scan.
  • What is SQL Server's adaptive join? — Since 2017 (batch mode) and extended to rowstore in 2019: a threshold on actual build rows decides loops vs hash at runtime, hedging exactly this misestimate.

Wrong answer: “Nested loops is the slow one; hash join is the fast one.” Each is optimal in its regime; the interesting question is always which estimate drove the choice, and a candidate ranking operators by speed has never debugged one.

EXPLAIN vs EXPLAIN ANALYZE in PostgreSQL — and what does BUFFERS add?mid

EXPLAIN only plans: it prints the optimizer's estimates and executes nothing. EXPLAIN ANALYZE actually runs the statement and reports actual rows, times and loops — which means it also performs the writes if you point it at an UPDATE, so you wrap it in BEGIN; ... ROLLBACK;. BUFFERS reports shared/local/temp block hits, reads, dirtied and written, and it is the option that turns guesswork into arithmetic: shared read × 8 kB is the I/O the query actually did, and temp written is a spill. In PostgreSQL 18 the buffer numbers are shown by default with ANALYZE, and EXPLAIN (ANALYZE, VERBOSE) now also reports per-worker and per-node I/O timing when track_io_timing is on; SETTINGS prints the non-default planner GUCs, which is how you catch the session that has enable_seqscan = off.

Example

BEGIN;
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS, FORMAT TEXT)
UPDATE "order" SET status = 'cancelled' WHERE id = 42;
ROLLBACK;                -- ANALYZE really executed the UPDATE

Follow-ups

  • SQL Server equivalent? — SET STATISTICS IO, TIME ON plus the actual plan; logical reads is the closest analogue to shared hit + read.
  • What is Rows Removed by Filter telling you? — How much work the node did for nothing; a large number next to an index scan usually means the wrong index or a missing predicate column.
  • How do you explain a query that only misbehaves in production? — auto_explain with log_min_duration and log_analyze in PostgreSQL; Query Store plus lightweight query profiling in SQL Server.

Wrong answer: “EXPLAIN ANALYZE is safe, it just explains in more detail.” It executes the statement; running it on a production DELETE without a transaction is a career-defining mistake.

What is Query Store and how do you use it?senior

Query Store (SQL Server 2016+, on by default for new databases since 2022, and available on readable secondaries by default in 2025) persists query texts, plans and runtime statistics inside the database, surviving restarts and cache eviction. It is the answer to “this was fast last week”: you compare plans for the same query over time, find the regression, and force the good plan — either manually or via Automatic Plan Correction, which forces the last known good plan when it detects a regression. At lead level the important part is policy: forcing a plan is a tourniquet, not a cure, so every forced plan gets a ticket, an owner and an expiry; forced plans can also silently fail (sys.query_store_plan.is_forced_plan_failure-style monitoring is mandatory). PostgreSQL has no equivalent built in — the closest is pg_stat_statements for aggregate statistics plus auto_explain for plans, with extensions such as pg_store_plans or a plan-management extension if you need forcing.

Example

-- SQL Server: regressed queries in the last day
SELECT TOP 20 q.query_id, rs.avg_duration, rs.count_executions, p.plan_id
FROM sys.query_store_runtime_stats rs
JOIN sys.query_store_plan p ON p.plan_id = rs.plan_id
JOIN sys.query_store_query q ON q.query_id = p.query_id
JOIN sys.query_store_runtime_stats_interval i ON i.runtime_stats_interval_id = rs.runtime_stats_interval_id
WHERE i.start_time > DATEADD(day, -1, SYSUTCDATETIME())
ORDER BY rs.avg_duration DESC;

EXEC sp_query_store_force_plan @query_id = 1234, @plan_id = 5678;

Follow-ups

  • Overhead? — A few percent with sensible capture policy (AUTO); the risk is disk growth, so set MAX_STORAGE_SIZE_MB and a cleanup policy or it flips to READ_ONLY.
  • What does upgrading break? — A new cardinality estimator or compatibility level can change plans wholesale; Query Store is exactly the safety net for that, which is why the documented upgrade flow is “enable QS, upgrade, raise compat level, fix regressions”.
  • PostgreSQL alternative for the same job? — pg_stat_statements baselines plus auto_explain samples, and a discipline of pinning behaviour with query rewrites rather than plan forcing.

Wrong answer: “Query Store is just a nicer version of the plan cache DMVs.” The point is persistence across restarts and the ability to force plans; describing it as a UI misses why it changed how upgrades are done.

A query is fast in your session and slow from the application. What are the causes you check, in order?senior

Four causes cover almost every real case. (1) Different plan from different parameters — parameter sniffing: the cached plan was compiled for an atypical value. (2) Different SET options: in SQL Server a client with ARITHABORT OFF (the old ADO/ODBC default) gets a different cache entry than SSMS, so you are literally comparing two plans; check sys.dm_exec_plan_attributes. (3) Type mismatch from the driver: .NET sends string parameters as nvarchar by default, so a varchar column gets an implicit conversion and loses its seek — one of the most common and most invisible production regressions. (4) Blocking or resource contention that only exists under concurrency. My order is: capture the actual production plan (Query Store / auto_explain), compare it to mine, then look at parameters, SET options and waits before touching anything.

Example

// the classic .NET cause of "fast in SSMS, slow in the app"
cmd.Parameters.AddWithValue("@sku", sku);            // → nvarchar(4000), scans a varchar index
cmd.Parameters.Add("@sku", SqlDbType.VarChar, 50).Value = sku;  // → seeks

Follow-ups

  • How do you prove it is the sniffed plan? — Compare the cached plan's compiled parameter values (in the plan XML) with the runtime ones; they will differ wildly.
  • Is OPTION (RECOMPILE) the fix? — It is a valid targeted fix for a low-frequency, highly parameter-sensitive statement; it is a CPU disaster on a statement executed thousands of times a second.
  • PostgreSQL version of this? — Generic vs custom plans for prepared statements: after five executions the planner may switch to a generic plan; plan_cache_mode = force_custom_plan is the escape hatch.

Wrong answer: “The app is slow because of network or ORM overhead.” Sometimes true, but jumping there without comparing the two plans is how teams spend a week on the wrong layer; the SET-options and parameter-type causes are far more common and are invisible from the app side.

When do you use query hints, and which ones are defensible?senior

Hints are a way of saying “I know something the optimizer cannot”, and the defensible ones are the ones that state a fact rather than dictate a plan. In SQL Server: OPTION (RECOMPILE) for genuinely parameter-sensitive, low-frequency statements; OPTIMIZE FOR (@p = value) or OPTIMIZE FOR UNKNOWN when you know the representative value; MAXDOP to contain a parallel query; FAST n for a UI that needs the first page. Hints I avoid: forcing a specific index or join order, because they encode today's data distribution into the code and break when the data grows. In PostgreSQL there are no planner hints by design — you steer with statistics (CREATE STATISTICS, raised default_statistics_target), with cost settings (random_page_cost, work_mem per statement), with query rewrites, and if you truly must, with the third-party pg_hint_plan extension. In SQL Server 2016+ the better lever is often Query Store hints, which apply a hint to a query without changing the application's SQL.

Example

-- SQL Server: apply a hint without touching application code
EXEC sys.sp_query_store_set_hints @query_id = 1234, @query_hints = N'OPTION(RECOMPILE)';

-- PostgreSQL: state the correlation the planner cannot infer
CREATE STATISTICS stx_order (dependencies, ndistinct) ON tenant_id, region FROM "order";
ANALYZE "order";

Follow-ups

  • Why is FORCESEEK dangerous? — It removes the optimizer's ability to switch to a scan past the tipping point, so it fails exactly when data volume grows.
  • Governance for hints? — Every hint gets a comment with the ticket, the date and the evidence; a quarterly review removes ones whose premise no longer holds.
  • What is SQL Server 2025's OPPO? — Optional Parameter Plan Optimization: the engine generates multiple plans for statements with optional (“@p IS NULL OR col = @p”) filters, which is exactly the pattern people previously fixed with RECOMPILE or dynamic SQL.

Wrong answer: “Add WITH (NOLOCK), it makes queries faster.” It is not a performance hint but an isolation-level change (read uncommitted) that permits dirty reads, missed rows and duplicate rows from page splits during a scan — see unit 04.

How do you decide between fixing a query, adding an index, changing the schema, or caching?principal

I order by reversibility and blast radius. A query rewrite is local, reviewable and revertible with a deploy — try it first, especially since the most common wins (a non-SARGable predicate, an accidental fan-out, an N+1) cost nothing in storage. An index is cheap to add and easy to revert but taxes every write on that table forever, so it needs a named query and an owner. A schema change is the big hammer: it fixes classes of problems (a denormalized counter, a partition scheme, a narrower key) but it is a migration with a rollback plan and coordination cost. Caching is last, not because it is bad but because it moves the problem — it adds invalidation, a consistency question, and a second failure mode — and it is often used to avoid diagnosing the actual issue. The extra dimension I raise at lead level is whether the query should exist: many “tuning” problems are an API returning the wrong shape, or a report running against OLTP that belongs on a replica or in a columnstore.

Example

-- classic N+1 discovered as "the database is slow": 1 + 500 round trips
-- fix in one statement, no schema, no index, no cache
SELECT o.*, c.name
FROM "order" o JOIN customer c ON c.id = o.customer_id
WHERE o.id = ANY($1);        -- PostgreSQL array parameter
-- SQL Server: a table-valued parameter, not a 500-element IN list

Follow-ups

  • When is caching the right first move? — When the data is genuinely read-mostly and stale-tolerant and the query is already optimal; then a short TTL beats a heroic index.
  • How do you decide on a read replica? — When the workload is analytical and the staleness budget is stated in the SLO; do not send read-your-writes traffic to an async replica.
  • What if the fix needs a schema change nobody has time for? — Ship the reversible mitigation now, book the structural fix with the measured cost of not doing it; the number, not the opinion, gets it prioritized.

Wrong answer: “Put Redis in front of it.” Adding a cache to hide an un-diagnosed query moves an availability risk into a consistency risk, and at lead level it reads as avoiding the work.

What is parallelism costing you, and how do you tune MAXDOP / parallel workers?senior

Parallelism trades CPU for latency, and it goes wrong in two ways: too eager (small OLTP queries going parallel, burning schedulers and producing CXCONSUMER/CXPACKET waits) and skewed (one worker gets most of the rows, so eight threads take as long as one plus coordination). In SQL Server the levers are the instance/database MAXDOP and cost threshold for parallelism — the default threshold of 5 is a 1997 number and raising it to something like 40–50 is standard practice, while MAXDOP should follow the documented guidance around NUMA node size (commonly 8 or fewer) rather than being left at 0. In PostgreSQL the equivalents are max_parallel_workers_per_gather, max_parallel_workers, min_parallel_table_scan_size and parallel_setup_cost; workers come from max_worker_processes, and a query that wanted workers but got none (because the pool was exhausted) shows Workers Planned: 4, Workers Launched: 0 in the plan — a subtle cause of “sometimes slow”.

Example

-- SQL Server: sane instance defaults for an OLTP box
EXEC sp_configure 'cost threshold for parallelism', 50; RECONFIGURE;
ALTER DATABASE SCOPED CONFIGURATION SET MAXDOP = 8;

-- PostgreSQL: let a reporting query use more, per session
SET max_parallel_workers_per_gather = 8;

Follow-ups

  • Is CXPACKET a problem? — Not by itself; since 2017 the benign portion is split into CXCONSUMER. Look for skew and for the waits that actually block.
  • Why does a parallel plan spill more? — The memory grant is divided among workers, so a skewed distribution makes one worker exceed its share and spill.
  • Should OLTP ever run MAXDOP 1? — For specific workloads (some ERP vendors mandate it) yes, but at instance level it removes your ability to run maintenance and reporting in reasonable time.

Wrong answer: “Set MAXDOP to 1, parallelism causes waits.” It cures a symptom by removing a capability; the actual problem is usually a cost threshold of 5 letting trivial queries go parallel, or a bad estimate producing a huge plan.

How do you benchmark a query change so the result is trustworthy?senior

Measure the right thing on a realistic dataset and a warm cache, repeatedly. I compare logical reads (SQL Server: SET STATISTICS IO ON) or buffers (PostgreSQL: EXPLAIN (ANALYZE, BUFFERS)) rather than wall-clock first, because those are stable across a noisy machine; then wall clock across at least a few dozen runs with the parameter distribution the production workload actually has — a single “typical” parameter is how people ship a plan that is great for one tenant and fatal for the biggest one. Data volume and distribution have to be production-like: a query that is fine on 100k rows can flip plans at 10M. Then I verify on the real workload: Query Store's regressed-query report, or pg_stat_statements deltas over a window, so I catch the queries the change made worse as well as the one I targeted.

Example

-- PostgreSQL: reset, run the workload, read the deltas
SELECT pg_stat_statements_reset();
-- ... run the load ...
SELECT calls, round(total_exec_time) AS ms, round(mean_exec_time, 2) AS avg_ms, query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;

Follow-ups

  • Why not clear the cache between runs? — Because production runs warm; cold-cache numbers measure your storage, not your query. (And DBCC DROPCLEANBUFFERS on a shared server is an outage.)
  • How do you handle plan variance? — Report a distribution (p50/p95), not a mean; parameter-sensitive queries have bimodal timing by design.
  • What about the write cost of a new index? — Measure insert/update throughput and log/WAL bytes before and after, not just the read win.

Wrong answer: “It ran in 40 ms instead of 900 ms on my laptop, ship it.” One run, one parameter, one data volume — the three ways a benchmark lies, and a lead who accepts that number owns the regression.

The same query is fine on one tenant and terrible on the biggest tenant. How do you architect around that?principal

This is data skew meeting a shared plan, and there are four levers in increasing order of cost. First, make the plan per-value: SQL Server's Parameter Sensitive Plan optimization (2022+) caches multiple plans keyed by predicate cardinality buckets, and 2025's OPPO extends the multi-plan machinery to optional-parameter patterns; a targeted RECOMPILE or Query Store hint does the same by hand. Second, help the estimates: filtered statistics per big tenant in SQL Server, or extended statistics in PostgreSQL where columns are correlated. Third, change the physical layout: partition or index by tenant so the big tenant's rows are physically separated, or give it its own covering index via a filtered/partial index. Fourth, isolate: move the largest tenants to their own database or shard, which also fixes the noisy-neighbour blast radius and the backup/restore time. At principal level I would also name the operational part — per-tenant SLOs and per-tenant query telemetry — because “the app is slow” tickets from one tenant are otherwise invisible in the aggregate.

Example

-- PostgreSQL: a partial index dedicated to the whale tenant
CREATE INDEX CONCURRENTLY ix_order_whale ON "order" (placed_at DESC)
  INCLUDE (total) WHERE tenant_id = 4711;

-- SQL Server: filtered statistics so the big tenant gets its own histogram
CREATE STATISTICS ST_order_whale ON dbo.[order] (placed_at) WHERE tenant_id = 4711;

Follow-ups

  • When do you shard the whale out? — When its working set no longer fits shared cache, or when its maintenance windows dictate everyone else's; that is a capacity fact, not a preference.
  • Does OPTIMIZE FOR UNKNOWN help? — It gives every tenant the average plan: it removes the catastrophic case and the excellent case at once, which is sometimes exactly the trade you want.
  • How do you detect it early? — Track p95 latency per tenant, not global p95; skew is invisible in an aggregate dominated by small tenants.

Wrong answer: “Add OPTION (RECOMPILE) everywhere so every tenant gets its own plan.” On a high-frequency statement that converts an I/O problem into a CPU problem and takes the whole instance down at peak — the classic over-correction.

04Transactions, isolation & MVCC

The area that separates people who have run a database from people who have used one. Interviewers ask the ACID/isolation-level question as a screener, then immediately go concrete: which anomaly does READ COMMITTED still allow, what does SQL Server's default do that PostgreSQL's does not, and what actually happens under load. Know the two engines' concurrency models as models — SQL Server is lock-based by default with an optional MVCC mode, PostgreSQL is MVCC always — because almost every difference follows from that one fact.

Name the isolation levels and the anomalies each one prevents.screener

The SQL standard defines four levels against three anomalies: READ UNCOMMITTED allows dirty reads, non-repeatable reads and phantoms; READ COMMITTED prevents dirty reads; REPEATABLE READ additionally prevents non-repeatable reads; SERIALIZABLE prevents phantoms too. What matters in interviews is the implementation reality. SQL Server's default is READ COMMITTED using shared locks (so readers block writers), and it offers READ_COMMITTED_SNAPSHOT (RCSI) and SNAPSHOT isolation as row-versioning alternatives. PostgreSQL implements only three distinct levels — READ UNCOMMITTED behaves as READ COMMITTED because MVCC never exposes uncommitted rows — its REPEATABLE READ is a true snapshot that also prevents phantoms, and its SERIALIZABLE uses Serializable Snapshot Isolation (SSI), which detects dangerous read-write dependency cycles and aborts a transaction with 40001 rather than blocking. So “REPEATABLE READ” means materially different things in the two engines, and saying so is what marks a senior answer.

Example

-- PostgreSQL: SERIALIZABLE can fail; the app MUST retry
BEGIN ISOLATION LEVEL SERIALIZABLE;
  ...
COMMIT;   -- may raise SQLSTATE 40001 "could not serialize access due to read/write dependencies"

-- SQL Server: turn readers into snapshot readers database-wide
ALTER DATABASE app SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;

Follow-ups

  • What is a write skew? — Two transactions each read a set, each writes based on it, and both commit — legal under snapshot isolation, prevented by PostgreSQL's SSI, not prevented by SQL Server's SNAPSHOT.
  • Default in each engine? — READ COMMITTED in both; but SQL Server's is lock-based unless RCSI is on, and Azure SQL Database has RCSI on by default.
  • Cost of SERIALIZABLE in PostgreSQL? — Predicate-lock tracking memory and a serialization-failure rate that grows with conflict; it needs a retry loop, not a longer timeout.

Wrong answer: “SERIALIZABLE means transactions run one at a time.” It guarantees an equivalent serial order; PostgreSQL achieves it optimistically with aborts and SQL Server with range locks — and the difference dictates whether your application needs retry logic.

Explain MVCC in PostgreSQL. What is the cost?mid

Every write creates a new row version (tuple) stamped with the inserting transaction's xmin and, when superseded or deleted, an xmax; a transaction's snapshot decides which versions it can see, so readers never block writers and writers never block readers. The cost is that dead tuples accumulate and must be reclaimed: that is VACUUM's job, run automatically by autovacuum, which also advances the frozen-transaction horizon to prevent transaction-ID wraparound. The failure modes follow directly — a long-running transaction (or an abandoned replication slot, or hot_standby_feedback from a busy replica) holds back the xmin horizon, vacuum cannot remove tuples newer than it, tables and indexes bloat, and index-only scans stop working because the visibility map is not maintained. That is why “my PostgreSQL got slow” is so often “someone left a transaction open in a psql window”.

Example

-- the query every PostgreSQL on-call has bookmarked
SELECT pid, state, xact_start, now() - xact_start AS age, left(query, 60)
FROM pg_stat_activity
WHERE state <> 'idle' OR backend_xid IS NOT NULL
ORDER BY xact_start;         -- 'idle in transaction' with an old xact_start = your bloat source

Follow-ups

  • What is HOT? — Heap-Only Tuples: if no indexed column changed and the new version fits on the same page, PostgreSQL chains it without touching indexes; a lower fillfactor on hot-update tables makes it more likely.
  • Wraparound? — At ~2 billion transactions of age the cluster refuses writes to protect data; monitor age(datfrozenxid) and treat aggressive autovacuum-to-prevent-wraparound as a page-worthy event.
  • Does SQL Server have this problem? — Only when row versioning is on, and its versions live in tempdb (or in-row for ADR since 2019), so the failure mode is tempdb growth rather than table bloat.

Wrong answer: “VACUUM frees disk space back to the OS.” Plain VACUUM marks space reusable inside the relation; only VACUUM FULL (exclusive lock, full rewrite) or pg_repack returns it — a distinction that decides whether your fix needs a maintenance window.

What is READ_COMMITTED_SNAPSHOT and would you turn it on?senior

RCSI changes SQL Server's default READ COMMITTED from shared-lock-based to row-versioning: readers see a statement-level snapshot and stop taking shared locks, so readers no longer block writers. In most OLTP systems I would turn it on — it removes an entire class of blocking incidents and is the default in Azure SQL Database — but it is a database-wide behaviour change and needs three things said out loud. First, version stores live in tempdb, so tempdb sizing and I/O become critical and a long-running transaction inflates them. Second, the semantics change: patterns that relied on readers blocking (a home-grown queue that did SELECT-then-UPDATE assuming a shared lock held the row) can now produce lost updates, so queue code must use UPDLOCK/READPAST or OUTPUT. Third, switching it on requires exclusive database access (WITH ROLLBACK IMMEDIATE), so it is a scheduled change. SNAPSHOT isolation is the separate, transaction-scoped level that gives a consistent view across statements and can raise update conflicts (error 3960).

Example

-- a queue pop that is still correct under RCSI
UPDATE TOP (1) dbo.job WITH (READPAST, UPDLOCK, ROWLOCK)
SET status = 'running', locked_by = @worker
OUTPUT inserted.id, inserted.payload
WHERE status = 'pending';

Follow-ups

  • RCSI vs SNAPSHOT? — RCSI: a fresh snapshot per statement. SNAPSHOT: one snapshot for the whole transaction, with optimistic update-conflict detection.
  • How much tempdb? — Monitor sys.dm_tran_version_store_space_usage; plan for the largest concurrent write volume times the longest reader.
  • Does ADR change this? — Accelerated Database Recovery (2019+, and extended to tempdb in 2025) moves versions in-row and makes long-transaction rollback near-instant, which removes the worst RCSI/tempdb failure mode.

Wrong answer: “RCSI is the same as NOLOCK but safe.” NOLOCK reads uncommitted data; RCSI reads a committed, consistent version. Conflating them signals the candidate does not understand versioning.

Why is WITH (NOLOCK) dangerous, and what do you tell a team that uses it everywhere?senior

NOLOCK is READ UNCOMMITTED with a table hint. It permits dirty reads — rows from transactions that later roll back — but the less-known and worse behaviours are the ones to name: an allocation-order scan can miss committed rows or return the same row twice if a page split moves rows during the scan, and it can even fail with error 601 (“could not continue scan with NOLOCK due to data movement”). So a financial total computed with NOLOCK is not “slightly stale”, it is arbitrarily wrong. My message to a team is not “stop it” but “you adopted it to fix blocking; the correct fix for that is RCSI”, then I turn RCSI on, remove the hints in the paths where correctness matters, and leave them only where an approximate answer is explicitly acceptable and documented. PostgreSQL has no equivalent: READ UNCOMMITTED is accepted syntactically but behaves as READ COMMITTED, because MVCC gives non-blocking reads for free.

Example

-- what people write
SELECT SUM(amount) FROM dbo.ledger WITH (NOLOCK) WHERE account_id = @a;
-- what they should have done, once, at the database level
ALTER DATABASE app SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;

Follow-ups

  • Is NOLOCK ever fine? — On an append-only log table for a rough count, or in a diagnostic query during an incident when the alternative is being blocked. State the tolerance explicitly.
  • Does it take no locks at all? — It still takes a schema stability lock, so it does not save you from a blocking DDL, which surprises people mid-incident.
  • How do you find it? — Grep the codebase and Query Store text; then measure the actual blocking it was hiding before removing it.

Wrong answer: “NOLOCK just means you might see slightly out-of-date data.” The missed-row and duplicate-row behaviours are the reason it is disqualifying in reporting, and a candidate who only knows “dirty reads” will keep approving it.

Optimistic vs pessimistic concurrency: how do you implement each and when?senior

Pessimistic means taking a lock for the duration of the business operation: SELECT ... FOR UPDATE in PostgreSQL, WITH (UPDLOCK, ROWLOCK) in SQL Server. It is correct and simple, and it is right when conflicts are frequent, the critical section is short, and a retry would be expensive or user-visible — inventory decrements, seat reservations, queue pops. Optimistic means detecting the conflict at write time with a version token: a rowversion/timestamp column in SQL Server, or a monotonically increasing version integer or xmin in PostgreSQL, compared in the WHERE clause so an update affecting zero rows means “someone else changed it”. That is right when conflicts are rare, when the “transaction” spans user think-time (never hold a database lock across a UI round trip), and in distributed or stateless settings. The lead-level point is that this is a product decision as much as a technical one: optimistic concurrency needs a defined user experience for the conflict.

Example

-- optimistic, SQL Server (EF Core maps this to a concurrency token)
UPDATE dbo.document SET title = @t, rowver_check = DEFAULT
WHERE id = @id AND rowver = @original_rowver;
IF @@ROWCOUNT = 0 THROW 50001, 'Concurrency conflict', 1;

-- pessimistic, PostgreSQL: skip rows another worker already holds
SELECT id FROM job WHERE status = 'pending'
ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 10;

Follow-ups

  • What does SKIP LOCKED buy? — A correct multi-consumer queue without a scheduler; PostgreSQL 9.5+, and SQL Server's equivalent is READPAST.
  • Why never hold a lock across user think-time? — Lock duration becomes unbounded and human-paced; a single abandoned browser tab blocks the table.
  • Where does the ORM fit? — EF Core concurrency tokens and Hibernate @Version implement the optimistic pattern; the failure surfaces as a DbUpdateConcurrencyException your UI must handle.

Wrong answer: “Optimistic is always better because it does not lock.” Under high contention optimistic concurrency degenerates into a retry storm that is slower and less fair than a queue of lock waiters; the choice is a function of the conflict rate.

What happens to an open transaction that the application forgets to commit?senior

In PostgreSQL the backend sits idle in transaction: it holds its snapshot, so it pins the xmin horizon and blocks vacuum from cleaning any dead tuple newer than it — bloat grows across the whole database, not just the tables it touched — and it holds every lock it has taken, including any ACCESS EXCLUSIVE from a DDL, which then queues every subsequent query on those tables. The defences are idle_in_transaction_session_timeout, statement_timeout and lock_timeout, set per role or per application. In SQL Server the open transaction holds its locks and, critically, pins the transaction log: the log cannot truncate past the oldest active transaction, so the log file grows until the disk fills, which is one of the classic ways a SQL Server database goes read-only at 2am. Both engines have the same root cause — application code with a transaction scope wider than the work — and the same lead-level fix: timeouts by default, plus monitoring on oldest-transaction age.

Example

-- PostgreSQL: bound the damage per application role
ALTER ROLE app_api SET idle_in_transaction_session_timeout = '30s';
ALTER ROLE app_api SET statement_timeout = '15s';
ALTER ROLE app_api SET lock_timeout = '3s';

-- SQL Server: what is pinning my log?
SELECT name, log_reuse_wait_desc FROM sys.databases WHERE name = 'app';  -- ACTIVE_TRANSACTION
DBCC OPENTRAN('app');

Follow-ups

  • Why does the SQL Server log grow even in SIMPLE recovery? — Truncation still cannot pass the oldest active transaction; recovery model does not rescue you from an open transaction.
  • Is killing the session safe? — It triggers a rollback that can take as long as the work did; SQL Server 2019+ ADR makes this near-instant, plain PostgreSQL rollback is fast because it just abandons versions.
  • How do you prevent it in code? — Transactions opened and closed in the same function, no user interaction or HTTP call inside, and a linter/review rule for transaction scope.

Wrong answer: “The database will time it out eventually.” Neither engine has a default idle-transaction timeout; without explicit configuration it sits there until the log or the disk gives out.

Explain lock escalation and lock granularity in SQL Server, and PostgreSQL's equivalent concerns.senior

SQL Server locks at row, page, partition or table level and escalates to a table (or partition, with LOCK_ESCALATION = AUTO) lock when a single statement acquires around 5,000 locks on an object, or when lock memory is under pressure. That is why a 50,000-row UPDATE that took row locks suddenly blocks everyone: the escalation converted fine-grained locks into one coarse one. The standard mitigations are batching the DML into chunks below the threshold, partitioning with partition-level escalation, or in a controlled case ALTER TABLE ... SET (LOCK_ESCALATION = DISABLE). In SQL Server 2025 the deeper answer is optimized locking: with transaction-ID locking plus lock-after-qualification, a large transaction holds very few locks, so escalation is largely avoided — but it is off by default, requires Accelerated Database Recovery, and must be enabled per database. PostgreSQL never escalates row locks (they live in the tuple header, not in a lock table), so the equivalent concern is different: table-level lock modes from DDL, where an ALTER TABLE taking ACCESS EXCLUSIVE queues behind one long query and then blocks everything behind itself.

Example

-- SQL Server: batch a big delete to stay under escalation and keep the log small
WHILE 1 = 1
BEGIN
  DELETE TOP (2000) FROM dbo.audit_log WHERE created_at < @cutoff;
  IF @@ROWCOUNT = 0 BREAK;
  WAITFOR DELAY '00:00:00.100';    -- give the log and replicas room
END

-- SQL Server 2025: fewer locks by design (needs ADR)
ALTER DATABASE app SET OPTIMIZED_LOCKING = ON;

Follow-ups

  • How do you see escalation happen? — Extended Events lock_escalation, or sys.dm_tran_locks showing an OBJECT-level X lock where you expected KEY locks.
  • Why is PostgreSQL DDL so dangerous then? — A queued ACCESS EXCLUSIVE request blocks all later requests behind it; always set a short lock_timeout before DDL and retry.
  • Does ROWLOCK prevent escalation? — No, it is a hint about the initial granularity; escalation can still occur.

Wrong answer: “Disable lock escalation on the busy tables and the blocking goes away.” You trade a coarse lock for potentially millions of fine locks and enormous lock memory — a different, harder outage. Batch the work instead.

How do you implement a reliable work queue in a relational database?senior

The correct shapes are small and well known. PostgreSQL: SELECT ... FOR UPDATE SKIP LOCKED LIMIT n inside a transaction, update the claimed rows' status, commit — SKIP LOCKED lets N workers take disjoint batches without blocking each other. SQL Server: a single UPDATE ... WITH (READPAST, UPDLOCK, ROWLOCK) ... OUTPUT inserted.*, which claims and returns rows atomically in one statement. Around that core you need the same four things in both: an index that matches the claim predicate and ordering (typically partial/filtered on the pending status, so it stays tiny), a visibility timeout or heartbeat so a crashed worker's rows return to the queue, an attempt counter with a dead-letter destination, and aggressive cleanup — the queue table is the highest-churn table in the system, so in PostgreSQL it will bloat without a tuned autovacuum, and in SQL Server it will fragment. The judgment answer: a database queue is excellent up to a few thousand messages a second and buys you transactional enqueue with your business data; past that, or when you need fan-out and long retention, use a broker.

Example

-- PostgreSQL: claim and return in one round trip
WITH claimed AS (
  SELECT id FROM job
  WHERE status = 'pending' AND run_after <= now()
  ORDER BY priority DESC, run_after
  FOR UPDATE SKIP LOCKED LIMIT 20)
UPDATE job j SET status = 'running', started_at = now(), attempts = attempts + 1
FROM claimed c WHERE j.id = c.id
RETURNING j.id, j.payload;

CREATE INDEX ON job (priority DESC, run_after) WHERE status = 'pending';
ALTER TABLE job SET (autovacuum_vacuum_scale_factor = 0.01, fillfactor = 70);

Follow-ups

  • Why not LISTEN/NOTIFY alone? — Notifications are not durable and are lost if no listener is connected; use them to reduce polling latency on top of a durable table.
  • Exactly-once? — Not achievable end-to-end; aim for at-least-once delivery plus an idempotent handler keyed by job id.
  • When does the queue table become the bottleneck? — When vacuum cannot keep up with the dead-tuple churn; watch n_dead_tup and consider partitioning by day with drops instead of deletes.

Wrong answer: “SELECT the top pending row, then UPDATE it to running.” Without FOR UPDATE SKIP LOCKED / READPAST two workers select the same row and both process it; under RCSI or MVCC the read takes no blocking lock at all, so this “works” in testing and duplicates in production.

Transactions across service boundaries: how do you keep a database write and a message publish consistent?principal

You cannot get atomicity between a database and a broker without distributed transactions, and distributed transactions (MSDTC, XA) buy availability problems — a coordinator outage leaves in-doubt transactions holding locks — so the standard answer is the transactional outbox: write the business row and an outbox row in one local transaction, then a relay publishes the outbox rows and marks them sent, giving at-least-once delivery with an idempotent consumer. In PostgreSQL you can go further and drive the relay from logical decoding, so the outbox is read from the WAL rather than polled; in SQL Server 2025 the built-in equivalent is change event streaming, which publishes row-level changes as CloudEvents to Azure Event Hubs or Fabric Eventstream (currently behind the PREVIEW_FEATURES database-scoped configuration), with Change Data Capture as the mature alternative. The trade-offs I would name unprompted: ordering guarantees (per-key only), duplicate delivery, the relay's lag becoming an SLO, and the fact that the outbox table is now a high-churn table with all the vacuum/fragmentation consequences of a queue.

Example

BEGIN;
  UPDATE "order" SET status = 'paid' WHERE id = $1;
  INSERT INTO outbox (aggregate_id, type, payload, created_at)
  VALUES ($1, 'OrderPaid', $2, now());
COMMIT;   -- one local transaction: either both or neither

Follow-ups

  • Why not two-phase commit? — It converts two independent availability domains into one joint one and adds in-doubt recovery; almost never worth it for a service boundary.
  • How do you get ordering? — Partition by aggregate id and publish per-key in sequence; global ordering is a much stronger and much more expensive requirement.
  • Sagas? — For multi-service business transactions: local transactions plus compensating actions, with the outbox as the transport. Name idempotency and compensation explicitly.

Wrong answer: “Commit the transaction, then publish the message.” The process can die between the two, and the message is lost with no trace — the single most common source of “the payment succeeded but the email never went out” bugs.

05Schema design, keys & normalization

Asked in almost every round, and the one place where interviewers happily spend 30 minutes on a whiteboard. Screener depth is “what is 3NF”; the real test is defending choices — surrogate vs natural key, when you denormalize, how you model soft deletes, temporal data and multi-tenancy. At principal level the question becomes governance: how the schema stays coherent across a dozen teams and how you keep the migration path open.

Explain normalization to 3NF, and when you would deliberately denormalize.screener

1NF: atomic column values, no repeating groups. 2NF: no non-key column depends on part of a composite key. 3NF: no non-key column depends on another non-key column (no transitive dependency) — informally, every non-key column depends on the key, the whole key and nothing but the key. BCNF tightens 3NF for the overlapping-candidate-key case. Normalization is the default because it makes updates local and anomalies impossible by construction, which is worth more than the joins it costs. I denormalize deliberately and narrowly: a cached aggregate that would otherwise require scanning millions of rows on every page load, an immutable snapshot of data that must not change with its source (the price and address on a historical order), or a read model materialized for a specific query. The discipline is that every denormalized value has a named owner, a defined refresh mechanism (trigger, materialized view, application write) and a reconciliation job that can detect drift.

Example

-- correct denormalization: the order snapshots what was true at purchase time
CREATE TABLE order_line (
  order_id     bigint  NOT NULL REFERENCES "order"(id),
  product_id   bigint  NOT NULL REFERENCES product(id),
  unit_price   numeric(19,4) NOT NULL,   -- NOT a lookup to product.price
  product_name text    NOT NULL,         -- snapshot: the catalogue may be renamed
  qty          int     NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, product_id));

Follow-ups

  • How do you keep a denormalized counter correct? — A trigger or a single statement that updates both, inside the same transaction, plus a nightly reconciliation; never an application-level “we always remember to update it”.
  • Materialized view refresh? — PostgreSQL: REFRESH MATERIALIZED VIEW CONCURRENTLY (needs a unique index). SQL Server: indexed views maintain themselves synchronously, at write cost, with strict schema-binding requirements.
  • Is 3NF enough? — For OLTP, yes in practice; star schemas for analytics are deliberately denormalized and belong in a different store or a columnstore table.

Wrong answer: “Denormalize for performance; joins are slow.” Joins on indexed keys are cheap; the expensive things are wrong estimates and unnecessary rows. Blanket denormalization trades a solved problem for an unsolvable consistency one.

Surrogate key vs natural key, and int vs bigint vs UUID — what do you pick and why?mid

Surrogate keys by default, because natural keys change (email addresses, VAT numbers, ISBNs get reissued) and a changing key cascades through every referencing table; keep the natural key as a unique constraint so the business rule is still enforced. For the surrogate: bigint identity/sequence is the right default — narrow, sequential, cache-friendly, and it keeps every SQL Server nonclustered index small since they all carry the clustering key. Random UUIDs (v4) are the classic mistake as a clustered key: they scatter inserts across the whole index, causing page splits, fragmentation and write amplification. The modern answer is UUIDv7, which is time-ordered and therefore insert-friendly, and it is now first-class: PostgreSQL 18 ships a built-in uuidv7() function (with uuidv4() as an explicit alias), and SQL Server has had the same idea for years as NEWSEQUENTIALID() — which, note, is only monotonic within a Windows boot and is guessable, so it is not a secret.

Example

-- PostgreSQL 18: time-ordered identifiers, no extension needed
CREATE TABLE "order" (
  id         uuid PRIMARY KEY DEFAULT uuidv7(),
  public_ref text UNIQUE,                 -- the natural/business key, separately unique
  ...);

-- SQL Server: keep the clustered key sequential, expose a GUID separately
CREATE TABLE dbo.[order] (
  id       bigint IDENTITY CONSTRAINT PK_order PRIMARY KEY CLUSTERED,
  ext_id   uniqueidentifier NOT NULL DEFAULT NEWID() UNIQUE NONCLUSTERED, ...);

Follow-ups

  • Why is a random GUID clustered key so bad? — Every insert lands on a random page: splits, ~2× the writes, poor cache locality, and 16 bytes copied into every nonclustered index.
  • int or bigint? — bigint; the 4 extra bytes are noise next to the outage caused by an identity overflow at 2.1 billion.
  • Composite natural PKs? — Reasonable for junction/link tables where the pair is the identity, but every additional referencing table inherits the width.

Wrong answer: “Use UUIDs everywhere so we can generate ids in the client and shard later.” The client-generation benefit is real; skipping the ordering question (v4 vs v7) and the width cost is what turns it into a fragmentation incident 18 months later.

How do you model soft deletes, and what do they break?senior

A nullable deleted_at timestamptz is better than an is_deleted bit because it carries when as well as whether. What it breaks is the interesting part, and it is three things. Uniqueness: a plain unique constraint on email now blocks re-registration after deletion, so you need a partial/filtered unique index scoped to live rows. Foreign keys: the database will happily let a live row reference a soft-deleted parent, since the row still exists — that invariant now lives in application code or a trigger. Every query: forgetting WHERE deleted_at IS NULL is a data-leak-shaped bug, so you either route all access through views (or PostgreSQL row-level security) or accept that the rule is enforced by review. My default at scale is to avoid soft delete as a global pattern and instead move deleted rows to an archive table, or use it only where the product genuinely needs undelete, because the cost is paid by every query forever.

Example

-- PostgreSQL: uniqueness among live rows only
CREATE UNIQUE INDEX ON "user" (lower(email)) WHERE deleted_at IS NULL;
-- SQL Server equivalent
CREATE UNIQUE NONCLUSTERED INDEX UX_user_email ON dbo.[user] (email) WHERE deleted_at IS NULL;

Follow-ups

  • How do you stop the missing-filter bug? — Expose only v_user (filtered view) to the app role and revoke select on the table, or use RLS with a policy in PostgreSQL.
  • GDPR erasure? — Soft delete is not erasure; you need a real deletion or crypto-shredding path, and interviewers like to check you know the difference.
  • Index impact? — Soft-deleted rows stay in every index forever; on a table with high churn that is a slow, permanent tax.

Wrong answer: “Add is_deleted and filter it in the ORM's global query filter — done.” It leaves uniqueness and referential integrity silently broken, and global filters are routinely bypassed by raw SQL, reports and other services reading the same database.

How would you model temporal / historical data — “what did this row look like on 1 June”?senior

Three options, in increasing order of how much you build yourself. SQL Server has system-versioned temporal tables (2016+): declare the period columns and a history table, and the engine maintains it, with FOR SYSTEM_TIME AS OF queries — the cheapest correct answer if you are on SQL Server, and worth naming the caveats (history grows without bound unless you use a retention policy or partition it; schema changes must be applied to both tables). PostgreSQL has no built-in system versioning: you either build audit triggers into a history table, use an extension such as temporal_tables, or model validity explicitly with a tstzrange column. The modelling option is the most powerful for business time (as opposed to system time): a range column plus an exclusion constraint guarantees non-overlapping periods, and PostgreSQL 18 adds standard SQL temporal constraints — PRIMARY KEY (id, valid_period WITHOUT OVERLAPS) and temporal foreign keys with PERIOD — which express exactly this without a hand-rolled constraint.

Example

-- PostgreSQL 18: non-overlapping validity, enforced by the PK itself
CREATE TABLE price (
  product_id int NOT NULL,
  valid      tstzrange NOT NULL,
  amount     numeric(19,4) NOT NULL,
  PRIMARY KEY (product_id, valid WITHOUT OVERLAPS));

-- SQL Server: system-versioned, engine-maintained
CREATE TABLE dbo.price (
  product_id int NOT NULL PRIMARY KEY, amount decimal(19,4) NOT NULL,
  valid_from datetime2 GENERATED ALWAYS AS ROW START NOT NULL,
  valid_to   datetime2 GENERATED ALWAYS AS ROW END   NOT NULL,
  PERIOD FOR SYSTEM_TIME (valid_from, valid_to))
WITH (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.price_history));
SELECT * FROM dbo.price FOR SYSTEM_TIME AS OF '2026-06-01';

Follow-ups

  • System time vs business time? — System time is when the database knew it; business time is when it was true. Audit needs the first, pricing and contracts need the second, and bitemporal needs both.
  • Pre-18 PostgreSQL? — EXCLUDE USING gist (product_id WITH =, valid WITH &&), which needs the btree_gist extension.
  • How big does history get? — As big as your update rate times retention; partition the history table by period and drop partitions, do not DELETE from it.

Wrong answer: “Add created_at and updated_at and we have history.” Those record the latest change only; the question is about reconstructing a past state, which needs versions, not timestamps.

Multi-tenancy: shared schema with a tenant_id, schema per tenant, or database per tenant?principal

Shared tables with a tenant_id leading every index is the cheapest to operate and the easiest to migrate — one schema change, one connection pool — and it is the right default for many small tenants; the risks are noisy neighbours, a whale tenant skewing every plan, and the fact that one missing WHERE tenant_id is a cross-tenant data breach (PostgreSQL row-level security is a genuine defence-in-depth here; SQL Server's row-level security predicates play the same role). Schema per tenant gives cleaner isolation and per-tenant restore, but migrations become N migrations and PostgreSQL's catalog grows uncomfortably past a few thousand schemas. Database per tenant gives the strongest isolation, per-tenant backup/restore and per-tenant tuning, and it is the natural answer for enterprise contracts with data-residency clauses — at the cost of connection sprawl, N× maintenance and painful cross-tenant reporting. My actual recommendation is usually a hybrid: shared for the long tail, dedicated for the largest and the regulated, with the code written so a tenant can be moved between the two.

Example

-- PostgreSQL RLS: the database enforces tenant isolation, not the ORM
ALTER TABLE "order" ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON "order"
  USING (tenant_id = current_setting('app.tenant_id')::bigint);
-- the app sets: SET LOCAL app.tenant_id = '4711';  per transaction

Follow-ups

  • Does RLS cost anything? — The policy becomes a predicate on every query; keep it index-friendly and beware that BYPASSRLS superuser roles silently defeat it.
  • Connection pooling with database-per-tenant? — Pool per database explodes; you need a proxy (PgBouncer) or a pool-per-tenant strategy with strict caps.
  • How do you migrate a tenant out? — Design for it from day one: logical replication of that tenant's rows, or an export/import path tested quarterly.

Wrong answer: “Database per tenant is safest, so always do that.” At 5,000 tenants it is an operational catastrophe — 5,000 schema migrations, 5,000 backup chains, connection exhaustion — and the safety it buys can be had with RLS plus review discipline.

Where do you enforce constraints — database, application, or both?senior

In the database for anything that must always be true, in the application for anything that is a user experience concern. The database is the only place with transactional visibility of all writers — the batch job, the other service, the DBA's fix script, next year's rewrite — so foreign keys, NOT NULL, CHECK and unique constraints stay in the schema even when the ORM also validates them. The argument I hear against it, “constraints slow down writes and complicate migrations”, is real but small compared to the cost of orphaned rows discovered two years later. What I do concede at scale: foreign keys can be a genuine problem for very high-throughput ingest and for partitioned/sharded tables where the parent lives elsewhere, and both engines now let you soften them explicitly — PostgreSQL 18 added NOT ENFORCED constraints and NOT NULL ... NOT VALID, and SQL Server has long had WITH NOCHECK/untrusted constraints. Those are deliberate, documented exceptions, not the default.

Example

-- SQL Server: an untrusted constraint the optimizer cannot use — find them
SELECT OBJECT_NAME(parent_object_id), name FROM sys.foreign_keys WHERE is_not_trusted = 1;
ALTER TABLE dbo.order_line WITH CHECK CHECK CONSTRAINT FK_order_line_order;  -- re-validate

-- PostgreSQL: add the FK cheaply, validate later without a long exclusive lock
ALTER TABLE order_line ADD CONSTRAINT fk_order FOREIGN KEY (order_id) REFERENCES "order"(id) NOT VALID;
ALTER TABLE order_line VALIDATE CONSTRAINT fk_order;

Follow-ups

  • Why do untrusted constraints matter beyond integrity? — The optimizer uses trusted constraints to eliminate joins and prune partitions; an untrusted one is invisible to it.
  • Do FKs need indexes? — On the referencing (child) side, yes — neither engine creates one automatically, and without it every parent delete scans the child.
  • Cascading deletes? — Useful for genuinely owned children, dangerous when a cascade can touch millions of rows in one statement; prefer explicit deletion in batches for large hierarchies.

Wrong answer: “The application enforces it, so foreign keys are redundant overhead.” It presumes one writer forever. Every codebase that says this has orphan rows, and the cleanup is always someone's weekend.

EAV, JSON columns, or proper columns for “customers need custom fields”?senior

Three real options with different failure modes. Entity-attribute-value (a row per attribute) is maximally flexible and destroys everything else: no types, no constraints, queries become self-joins per attribute, and the optimizer has no idea what it is estimating — I would only accept it for a genuinely open metadata catalogue. A JSON/JSONB column is the modern middle ground: PostgreSQL's jsonb with a GIN index supports containment and path queries efficiently, and SQL Server 2025 finally has a native binary json data type plus JSON indexes rather than only nvarchar(max) with computed columns. Real columns remain right whenever the field is known, queried and constrained. My rule: known and queried → column; known-per-tenant and occasionally filtered → JSON with an index on the specific paths that matter; arbitrary and only ever displayed → JSON, unindexed. And whichever you choose, decide who validates the shape — a JSON schema check constraint beats “the app knows”.

Example

-- PostgreSQL: index the paths that are actually filtered
CREATE INDEX ON customer USING gin (custom jsonb_path_ops);         -- containment
CREATE INDEX ON customer ((custom->>'loyalty_tier'));               -- one hot path, btree

-- SQL Server 2025: native json type
CREATE TABLE dbo.customer (id bigint PRIMARY KEY, custom json NULL);
CREATE JSON INDEX IX_customer_custom ON dbo.customer (custom) FOR ('$.loyalty_tier');

Follow-ups

  • json vs jsonb in PostgreSQL? — json stores the text verbatim (preserves key order and duplicates, no indexing of structure); jsonb is parsed binary, indexable, and the correct default.
  • Estimation problem? — The planner has poor statistics inside JSON; a hot filter deserves a generated/computed column with its own statistics.
  • How do you migrate a JSON field into a column later? — Add the column, backfill in batches, dual-write, then flip readers — the same expand/contract dance as any migration.

Wrong answer: “Use EAV so we never need a migration again.” You trade a scheduled, reviewable migration for permanent query and integrity pain — and you still migrate, only now in application code with no constraints to catch you.

Twelve teams share one database and the schema is drifting. What do you do as the principal engineer?principal

I would separate three problems that get conflated. Ownership: every table needs exactly one owning team, recorded somewhere machine-readable; a shared database with no owners is how you get four customer tables. Coupling: teams reading each other's tables directly is the actual drift engine, because it makes every schema change a cross-team negotiation — the fix is a published interface (a view or an API) per owned area, so the physical schema can change behind it. Process: migrations in version control, reviewed, expand/contract by default, applied by one pipeline, with a CI check that fails on a destructive change without an approved plan. Then the boring but decisive part: measure the drift you already have (duplicate concepts, orphan tables, untrusted constraints, indexes with no owner), publish it, and fix it incrementally with the owning teams rather than in a big-bang “schema cleanup” project that will be cancelled. If the coupling is structural rather than cultural, the long-term answer is splitting the database along ownership lines — but only after the interfaces exist, otherwise you have distributed the problem.

Example

-- the interface: other teams read the view, never the table
CREATE SCHEMA billing_api;
CREATE VIEW billing_api.invoice AS
  SELECT id, customer_id, total, status, issued_at FROM billing.invoice WHERE void = false;
REVOKE ALL ON SCHEMA billing FROM other_team;
GRANT USAGE ON SCHEMA billing_api TO other_team;
GRANT SELECT ON billing_api.invoice TO other_team;

Follow-ups

  • How do you handle a team that needs a join across two owners? — Give it a read replica and a documented read model, or an owned reporting schema fed by CDC — not direct coupling to someone's physical tables.
  • What belongs in CI? — Migration linting (no DROP COLUMN without a deprecation window, no non-concurrent index on a big table), plus a drift check between the migration history and the live schema.
  • When is splitting the database right? — When the ownership boundaries are stable, the interfaces are used, and the shared failure domain is the actual constraint on release velocity.

Wrong answer: “Set up a schema review board so all changes are approved centrally.” It creates a queue, teams route around it, and drift continues — the leverage is in ownership plus automation, not in a gate staffed by humans.

06Window functions, CTEs & set thinking

The “can you actually write SQL” round: a live exercise like “top 3 orders per customer” or “running balance” or “gaps and islands”. Window functions are the expected tool at every level above junior, and interviewers watch whether you reach for a cursor or a self-join instead. At senior level they also probe the performance side — frame clauses, sorts, and whether a recursive CTE is a good idea on a million-row hierarchy.

Get the top N rows per group. Show me the query.mid

Window function, filtered outside the window: ROW_NUMBER() OVER (PARTITION BY group ORDER BY key DESC) in a CTE, then WHERE rn <= N. Know the three ranking functions and their differences, because that is the immediate follow-up: ROW_NUMBER gives distinct 1..n with arbitrary tie-breaking, RANK gives ties the same number and leaves gaps, DENSE_RANK gives ties the same number without gaps. If “top 3” means “including ties” the answer is RANK, and being asked which one the business means is a good sign in an interview. For a small number of groups and a supporting index, both engines have a faster shape: CROSS APPLY/LATERAL with TOP N/LIMIT N per group, which does N index seeks instead of sorting the whole table.

Example

-- portable: window function
WITH ranked AS (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY total DESC, id) AS rn
  FROM "order" o)
SELECT * FROM ranked WHERE rn <= 3;

-- often much faster with an index on (customer_id, total DESC): seek per customer
SELECT c.id, o.*
FROM customer c
CROSS APPLY (SELECT TOP (3) * FROM dbo.[order] o
             WHERE o.customer_id = c.id ORDER BY o.total DESC) o;   -- LATERAL in PostgreSQL

Follow-ups

  • Why can't you put the window function in WHERE? — Windows are evaluated after WHERE/HAVING; you must wrap in a CTE or derived table. (PostgreSQL's QUALIFY does not exist; that is Snowflake/BigQuery.)
  • Which is faster? — The window version does one pass plus a sort; APPLY/LATERAL does one seek per group. Few groups over a big table → APPLY wins; many groups → window wins.
  • Deterministic output? — Always add a unique tie-breaker to the ORDER BY, or the same query returns different rows run to run.

Wrong answer: a correlated subquery counting “how many rows are bigger” per row, or a cursor loop. Both work and both are O(n²)-ish; reaching for them in 2026 says you have not written SQL since window functions became universal (SQL Server 2005/2012, PostgreSQL 8.4).

Explain window frames: ROWS vs RANGE, and the default frame.senior

When a window has an ORDER BY and no explicit frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — and RANGE means “all rows with the same ORDER BY value as the current row”, so a running total over duplicate timestamps includes all of that timestamp's rows, not just the ones before. That surprise is the reason interviewers ask. ROWS counts physical rows and is what people usually mean; it is also cheaper because it does not need peer-group detection. PostgreSQL additionally supports GROUPS mode and RANGE with an offset (RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW) since version 11, which is the neat way to write a moving time window; SQL Server supports ROWS/RANGE but not offset-based RANGE or GROUPS, so the time-window equivalent needs a join or APPLY.

Example

-- running total, deterministic
SUM(amount) OVER (PARTITION BY account_id ORDER BY posted_at, id
                  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)

-- PostgreSQL 11+: true 7-day moving sum, gaps and all
SUM(amount) OVER (PARTITION BY account_id ORDER BY posted_at
                  RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW)

Follow-ups

  • Performance difference? — In SQL Server ROWS uses the fast in-memory window spool; RANGE forces the on-disk spool in tempdb, which is a documented and measurable regression.
  • What does LAG/LEAD cost? — Nothing extra beyond the sort; they are the idiomatic way to compute deltas and detect state changes.
  • Multiple different windows in one query? — Each distinct OVER clause may need its own sort; name them with WINDOW w AS (...) and keep the ordering consistent so one sort serves all.

Wrong answer: “ROWS and RANGE are the same thing, RANGE is just the newer syntax.” They give different numbers on ties, which is exactly how a running-balance report ends up wrong for the busiest second of the day.

Are CTEs optimization fences? What do you need to know about materialization?senior

In SQL Server, no: a non-recursive CTE is essentially an inline view, expanded into the query, and it can be evaluated more than once if referenced more than once — so a CTE containing a non-deterministic function or an expensive scan is not “computed once”. In PostgreSQL the answer changed at version 12: before it, CTEs were always materialized and therefore genuine optimization fences (a well-known way to force an evaluation order, and a well-known performance trap); from 12 onward a CTE referenced once and free of side effects is inlined by default, with explicit MATERIALIZED / NOT MATERIALIZED keywords to override. The practical consequences: old PostgreSQL tuning advice that relies on the fence is now wrong, and if you actually want the fence — to stop the planner pushing a predicate into an expensive function, say — you must ask for it. Neither engine guarantees a temporary table's semantics from a CTE; if you need one evaluation and reuse, use a temp table.

Example

-- PostgreSQL 12+: keep the old fence behaviour explicitly
WITH expensive AS MATERIALIZED (
  SELECT * FROM huge WHERE slow_udf(col))
SELECT * FROM expensive a JOIN expensive b ON ...;   -- computed once

Follow-ups

  • When is a temp table better than a CTE? — When the intermediate is large and reused, when you want statistics on it, or when you need an index on it — all three are common in batch/ETL code.
  • Recursive CTEs? — Both engines support them (PostgreSQL requires WITH RECURSIVE); use for hierarchies and graph walks, always with a depth guard (MAXRECURSION in SQL Server, an explicit level column in PostgreSQL) or a cycle detection clause.
  • Do CTEs improve performance? — They improve readability; performance changes come from what they let the planner do or stop it doing.

Wrong answer: “A CTE is materialized once, so referencing it twice is free.” True in PostgreSQL before 12, never true in SQL Server, and the belief produces queries that run an expensive subtree several times.

Solve gaps and islands: find consecutive runs of activity per user.senior

The standard trick is to build a group key that is constant within a run. For consecutive integers or dates, subtract a ROW_NUMBER() from the value: within an unbroken run both increase in lockstep, so the difference is constant, and grouping by it collapses each run. For “a new island whenever the gap exceeds X”, use LAG to compute the gap, a boolean “this row starts a new island” flag, and a running SUM of that flag as the island id — that variant is the one interviewers escalate to. Both work identically in SQL Server and PostgreSQL. The reason this question is popular is that it has an elegant set-based answer and an obvious procedural one, so it separates people who think in windows from people who think in loops.

Example

-- islands = sessions, new session when the gap since the last event exceeds 30 minutes
WITH marked AS (
  SELECT user_id, occurred_at,
         CASE WHEN occurred_at - LAG(occurred_at) OVER (PARTITION BY user_id ORDER BY occurred_at)
                   > INTERVAL '30 minutes' THEN 1 ELSE 0 END AS is_new
  FROM event),
sessioned AS (
  SELECT *, SUM(is_new) OVER (PARTITION BY user_id ORDER BY occurred_at
                              ROWS UNBOUNDED PRECEDING) AS session_no
  FROM marked)
SELECT user_id, session_no, min(occurred_at) AS started, max(occurred_at) AS ended,
       count(*) AS events
FROM sessioned GROUP BY user_id, session_no;

Follow-ups

  • The integer-gap variant? — value - ROW_NUMBER() OVER (ORDER BY value) as the group key; explain why it is constant within a run.
  • Scaling it? — It is one sort per partition; with an index on (user_id, occurred_at) the sort is free and it streams.
  • SQL Server < 2012? — No LAG; you would self-join on row numbers — worth knowing because you will meet it in legacy code.

Wrong answer: a cursor that walks rows in order and accumulates sessions in a variable. It gives the right answer, it is O(n) round trips in the engine's slowest execution mode, and in an interview it signals procedural thinking.

Pivot and unpivot: how do you do it in each engine, and when should you not?mid

SQL Server has PIVOT/UNPIVOT operators; PostgreSQL does not, and uses conditional aggregation (sum(CASE WHEN ... END) or filter (WHERE ...)) plus the crosstab() function from the tablefunc extension. Conditional aggregation is the portable form and I prefer it in both engines, because it reads clearly, supports several aggregates at once, and does not need the column list to be a literal. That is the real constraint: pivoting requires knowing the output columns at parse time, so “pivot by whatever categories exist” means dynamic SQL, which brings injection risk and plan-cache churn. My usual recommendation is to stop before that point: return the long/narrow result set and let the presentation layer (or the BI tool) pivot it, because that is where the column set is genuinely dynamic and cheap to change.

Example

-- portable pivot: conditional aggregation
SELECT customer_id,
       SUM(CASE WHEN status = 'paid'      THEN total ELSE 0 END) AS paid,
       SUM(CASE WHEN status = 'cancelled' THEN total ELSE 0 END) AS cancelled
FROM "order" GROUP BY customer_id;

-- PostgreSQL 9.4+ shorthand
SELECT customer_id,
       sum(total) FILTER (WHERE status = 'paid')      AS paid,
       sum(total) FILTER (WHERE status = 'cancelled') AS cancelled
FROM "order" GROUP BY customer_id;

Follow-ups

  • Dynamic pivot safely? — Build the column list from the catalog, quote every identifier (QUOTENAME, format('%I')), and parameterize all values; never concatenate user input.
  • Unpivot alternative? — CROSS APPLY (VALUES ...) in SQL Server and LATERAL (VALUES ...) or unnest in PostgreSQL are clearer than the UNPIVOT operator.
  • Why is FILTER nice? — It is standard SQL, avoids the ELSE-0 noise, and works with any aggregate including count(*).

Wrong answer: generating the pivot with string concatenation of user-supplied category names. It is both an injection hole and a plan-cache polluter — and the interviewer asking about pivot is usually testing whether dynamic SQL makes you careful.

How do you deduplicate rows, keeping the newest per key?mid

Rank within the key and delete everything that is not rank 1 — and in both engines you can delete directly from the CTE, which is the neat form people do not expect. Two operational points make it a senior answer: do it in batches so you do not take a table-sized lock or blow up the log/WAL, and add the unique index afterwards so the duplicates cannot come back (in PostgreSQL, CREATE UNIQUE INDEX CONCURRENTLY). PostgreSQL also offers DISTINCT ON (key) ... ORDER BY key, ts DESC, which is a compact non-standard way to select the newest row per key — very idiomatic and worth knowing, though it is a SELECT tool rather than a dedupe tool.

Example

-- delete all but the newest per (tenant_id, email)
WITH d AS (
  SELECT ctid, ROW_NUMBER() OVER (PARTITION BY tenant_id, lower(email)
                                  ORDER BY updated_at DESC, id DESC) AS rn
  FROM "user")
DELETE FROM "user" u USING d WHERE u.ctid = d.ctid AND d.rn > 1;

-- PostgreSQL's compact "newest per key" SELECT
SELECT DISTINCT ON (tenant_id, lower(email)) *
FROM "user" ORDER BY tenant_id, lower(email), updated_at DESC;

Follow-ups

  • Why batch the delete? — Lock escalation (SQL Server), log/WAL growth, and replication lag; a DELETE of 10M rows in one statement is an incident.
  • What if there are FK children? — Repoint the children to the surviving row first; a dedupe that ignores references creates orphans or fails at the last row.
  • How do you prevent recurrence? — The unique index is the fix; the dedupe is only cleanup, and an interviewer will ask which one you would do first.

Wrong answer: DELETE FROM t WHERE id NOT IN (SELECT MIN(id) FROM t GROUP BY key) on a large table. It is a self-join over the whole table with NOT IN's NULL trap, and it runs as one enormous transaction.

A report joins seven tables and takes four minutes. How do you decide between rewriting it, materializing it, or moving it off the OLTP database?principal

First, decide what it is: an operational query that must be fresh, or an analytical one where minutes-old data is fine. That single question determines the answer more than any plan detail. If it must be live, I read the plan and look for the fixable shape — a missing index, an accidental fan-out, a non-SARGable predicate, a bad estimate on a filtered join — because a four-minute report is usually a four-second one with two fixes. If it is analytical, the correct move is to stop running it against the OLTP tables at all: a materialized view refreshed on a schedule (PostgreSQL REFRESH MATERIALIZED VIEW CONCURRENTLY) or an indexed view / columnstore table (SQL Server), or a read replica, or a downstream warehouse fed by CDC. The trade-offs I would name unprompted: staleness budget agreed with the business, the cost of the refresh on the primary, whether the replica's lag is bounded, and who is paged when the refresh fails — a materialized view that silently stops refreshing is worse than a slow report.

Example

-- PostgreSQL: refreshable read model, no exclusive lock during refresh
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT tenant_id, date_trunc('day', placed_at) AS d, sum(total) AS revenue, count(*) AS orders
FROM "order" WHERE status = 'paid' GROUP BY 1, 2;
CREATE UNIQUE INDEX ON daily_revenue (tenant_id, d);   -- required for CONCURRENTLY
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;

Follow-ups

  • Indexed views in SQL Server? — Maintained synchronously, so writes to the base tables pay for them; strict requirements (schemabinding, deterministic, no outer joins/subqueries) and Standard edition needs NOEXPAND to use them automatically.
  • Replica or columnstore? — A replica isolates the load; a columnstore index changes the algorithm (batch mode, segment elimination) and can be 10–100× on aggregation. They compose.
  • How do you avoid a zoo of materialized views? — Own them like tables: naming, refresh schedule, monitoring, and a review that asks whether an existing one already answers the question.

Wrong answer: “Add indexes until it is fast.” A seven-table aggregation over the full history is not an index problem; you would add write cost to the OLTP path and still scan the same rows.

07Deadlocks, blocking & hot rows

The incident-response unit, and a favourite for lead and principal loops because it doubles as a “how do you behave under pressure” probe. Expect a scenario: “production is stalled, the app is timing out, go”. What is being assessed is whether you distinguish blocking from deadlocking, whether you diagnose before you act, and whether your fix is a code change or a hint that moves the problem.

What is a deadlock, how does the engine resolve it, and what is your first move?mid

A deadlock is a cycle in the wait-for graph: two or more transactions each hold a lock the other needs, so neither can proceed. Both engines detect it automatically and break it by aborting one transaction — SQL Server's deadlock monitor picks the lowest-cost victim (influenceable with SET DEADLOCK_PRIORITY) and raises error 1205; PostgreSQL's detector fires after deadlock_timeout (default 1s) and raises SQLSTATE 40P01. My first move is never to change locking: it is to capture the deadlock graph, because it names both statements, the resources and the lock modes, and the fix is almost always visible in it. Then the application must retry — a deadlock victim is a transient, expected error in any concurrent system, and code without a retry policy turns a 30ms hiccup into a user-visible failure.

Example

-- SQL Server: the deadlock graph is already being captured
SELECT CAST(target_data AS xml) FROM sys.dm_xe_session_targets t
JOIN sys.dm_xe_sessions s ON s.address = t.event_session_address
WHERE s.name = 'system_health' AND t.target_name = 'ring_buffer';

-- PostgreSQL: log it with the statements involved
ALTER SYSTEM SET log_lock_waits = on;        -- logs waits > deadlock_timeout
-- deadlock details go to the server log automatically with both queries

Follow-ups

  • Which errors do you retry? — SQL Server 1205 (deadlock) and 3960 (snapshot update conflict); PostgreSQL 40001 (serialization) and 40P01 (deadlock). Retry with jitter and a cap.
  • Is a deadlock a bug? — A few per day under load is normal; a rate that grows with traffic is a design problem, usually inconsistent lock ordering.
  • Does deadlock_timeout tune anything? — Only detection latency; raising it hides waits, it does not reduce deadlocks.

Wrong answer: “Deadlocks mean the database is overloaded; add hardware or increase the lock timeout.” Deadlocks are a cycle, not a queue — a faster machine reaches the same cycle sooner, and a longer timeout only delays the abort.

How do you actually eliminate a recurring deadlock?senior

Four techniques, in the order I try them. (1) Consistent access order: if every transaction touches parent before child, and accounts in ascending id order, the cycle cannot form — this fixes the majority of application deadlocks and costs nothing at runtime. (2) Shorten the transaction: acquire locks late, release early, never do an HTTP call or a user round trip inside; a shorter critical section makes the collision window smaller. (3) Change the access path: many deadlocks are caused by a scan taking locks on rows the statement does not need, so adding the covering index that turns the scan into a seek removes the overlap entirely — the classic non-obvious fix. (4) Change isolation or use versioning: turning on RCSI in SQL Server removes read/write deadlocks wholesale. Only after these do I consider explicit lock hints or serializing the work through a queue. And in every case the app keeps its retry loop, because you reduce deadlocks, you do not abolish them.

Example

-- lock in a canonical order so a cycle cannot form
UPDATE account SET balance = balance - @amt WHERE id = @lo;   -- always the lower id first
UPDATE account SET balance = balance + @amt WHERE id = @hi;
-- (@lo, @hi) = sorted(@from, @to)

Follow-ups

  • Why does an index fix a deadlock? — Fewer rows touched means fewer locks; a seek that touches 3 rows cannot conflict with a scan's 30,000.
  • Key-lookup deadlocks? — A SQL Server classic: reader seeks the nonclustered index then looks up the clustered, while a writer goes the other way; covering the query breaks the cycle.
  • Escalation-induced deadlocks? — Batching a large DML keeps it below the escalation threshold and stops it colliding with everything.

Wrong answer: “Set DEADLOCK_PRIORITY LOW on the batch job so it always loses.” That makes one side the reliable victim without reducing collisions; the batch now fails constantly and the underlying ordering bug is untouched.

Blocking vs deadlocking: how do you tell them apart during an incident?senior

Blocking is a queue: one session holds a lock and others wait, possibly forever, and nothing is aborted — the symptom is rising latency and connection-pool exhaustion, not errors. A deadlock is a cycle and resolves itself in under a second with an error. During an incident I go straight to the head of the blocking chain: in SQL Server, sys.dm_exec_requests joined to sys.dm_exec_sessions gives blocking_session_id, and I follow it up to the root — often a session that is sleeping with an open transaction, which means the culprit is application code, not a slow query. In PostgreSQL the equivalent is pg_blocking_pids() on pg_stat_activity, and the same tell applies: a blocker in state idle in transaction is an application bug. The action is to fix or kill the root, never the victims, and then to add the timeouts that would have bounded it.

Example

-- PostgreSQL: who is blocking whom, root first
SELECT a.pid, a.state, now() - a.xact_start AS xact_age,
       pg_blocking_pids(a.pid) AS blocked_by, left(a.query, 80) AS query
FROM pg_stat_activity a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0 OR a.state = 'idle in transaction'
ORDER BY xact_age DESC;

-- SQL Server
SELECT r.session_id, r.blocking_session_id, r.wait_type, r.wait_time, r.command,
       t.text FROM sys.dm_exec_requests r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) t WHERE r.blocking_session_id <> 0;

Follow-ups

  • When do you kill a session? — When it is the root, the rollback cost is understood, and you have captured what it was doing; killing a victim just restarts the queue.
  • What bounds this permanently? — lock_timeout and statement_timeout per role in PostgreSQL; SET LOCK_TIMEOUT and sensible command timeouts in SQL Server; plus alerting on longest-blocking-chain duration.
  • Blocked by DDL? — In PostgreSQL a waiting ACCESS EXCLUSIVE request blocks everything queued behind it, so one ALTER TABLE can freeze a table it never got to touch.

Wrong answer: “Restart the database / recycle the app pool to clear it.” It clears the symptom, destroys the evidence, and guarantees a repeat — and at lead level it is the answer that ends the interview.

A single hot row (a counter, a balance, a sequence table) is serializing the whole system. What do you do?principal

Recognize that this is contention on one lock, so no amount of hardware helps — the fix is to stop needing that lock. Options, roughly in order of how much they change the model: use the engine's native sequence/identity instead of a counter table (a sequence is designed for concurrent allocation and does not take a row lock for the duration of the transaction); shard the counter into N sub-counters summed on read, which turns one hot row into N warm ones; make the write append-only and compute the value from an aggregate or a materialized rollup (an events-plus-balance model, where the balance is a periodically snapshotted read model); or batch the updates so each transaction touches the row once instead of per item. If the value must be strongly consistent and exact — a bank balance, an inventory decrement with no oversell — then serialization is the requirement, and the honest engineering answer is to make the critical section as short as possible and to queue the work, accepting throughput limits per key while scaling across keys.

Example

-- sharded counter: N rows instead of one, summed on read
INSERT INTO counter_shard (name, shard, n) VALUES ('page_views', floor(random()*16), 1)
ON CONFLICT (name, shard) DO UPDATE SET n = counter_shard.n + 1;

SELECT sum(n) FROM counter_shard WHERE name = 'page_views';

Follow-ups

  • Why is a sequence not a hot row? — Allocation is not transactional (gaps on rollback are expected), and caching (CACHE n) means most allocations touch no shared state at all.
  • Trade-off of sharded counters? — Reads become an aggregate and exactness under concurrent read is approximate; fine for metrics, wrong for money.
  • Inventory without oversell? — Keep the decrement serialized per SKU but make it a single statement with a CHECK (qty >= 0), and reserve rather than deduct where the business allows.

Wrong answer: “Move the counter to Redis.” It relocates the contention and adds a consistency boundary — now a crash between the database write and the Redis increment silently loses data, which is worse than the throughput problem you started with.

How do you safely run a large DELETE or UPDATE on a busy table?senior

In batches, keyed by an indexed column, with a pause between batches and a stop condition. Batching bounds three things at once: lock scope (staying under SQL Server's ~5,000-lock escalation threshold), transaction log / WAL growth (one giant transaction cannot be truncated until it commits), and replication lag (a replica must replay the whole change). Practical shape: a loop of DELETE TOP (2000) / DELETE ... WHERE id IN (SELECT id ... LIMIT 2000), committing each batch, with a short sleep so other work gets scheduler time, and an operator-visible progress counter. If the operation removes most of the table, the better plan is usually a swap: create the new table, copy the rows to keep, then rename — turning an O(deleted) operation into an O(kept) one. And if the table is partitioned by the deletion key, the correct answer is neither: drop or switch out the partition, which is a metadata operation.

Example

-- PostgreSQL: bounded batches, indexed predicate, committed per batch
DO $$
DECLARE n int;
BEGIN
  LOOP
    DELETE FROM audit_log WHERE id IN (
      SELECT id FROM audit_log WHERE created_at < now() - interval '90 days' LIMIT 5000);
    GET DIAGNOSTICS n = ROW_COUNT;
    EXIT WHEN n = 0;
    COMMIT;                       -- procedures can COMMIT since PG 11
    PERFORM pg_sleep(0.05);
  END LOOP;
END $$;

Follow-ups

  • Why does PostgreSQL not shrink after a big delete? — Dead tuples are only marked reusable; the file stays. VACUUM reuses the space, pg_repack/VACUUM FULL returns it.
  • SQL Server log in FULL recovery? — Batches do not help unless log backups run frequently during the operation; otherwise the log still grows to hold everything.
  • How do you make it resumable? — Drive it from a checkpoint table or a key watermark so a killed job restarts where it stopped.

Wrong answer: “Run it overnight in one statement; there is no traffic then.” The log or WAL still has to hold the whole transaction, replicas still fall behind, and a rollback at 04:00 takes as long as the work did — three ways “quiet hours” does not save you.

You are on call. Latency is up 10×, CPU is normal, no deadlocks. Talk me through the first ten minutes.principal

Normal CPU with high latency points at waiting, so I go to waits and blocking before anything else. Minute 1–2: check the blocking chain root and the oldest open transaction; check for a session idle in transaction or a queued ACCESS EXCLUSIVE DDL. Minute 3–4: look at wait types in aggregate — SQL Server sys.dm_os_wait_stats deltas or dm_exec_requests live; PostgreSQL pg_stat_activity.wait_event_type — because LCK_*/Lock means contention, PAGEIOLATCH/IO means storage, RESOURCE_SEMAPHORE means memory grants, and ASYNC_NETWORK_IO/ClientWrite means the application is not consuming results fast enough. Minute 5–6: what changed — a deploy, a migration, a plan flip (Query Store's regressed-query view is one click), a stats update, a backup or index job running long. Minute 7–10: apply the smallest reversible mitigation — kill the blocking root, force the previous plan, pause the batch job — then communicate: what is affected, what I did, what I still do not know. I do not restart the instance, and I do not change two things at once.

Example

-- SQL Server: what is everyone waiting on, right now
SELECT r.wait_type, COUNT(*) AS sessions, SUM(r.wait_time)/1000.0 AS total_wait_s
FROM sys.dm_exec_requests r WHERE r.session_id > 50
GROUP BY r.wait_type ORDER BY total_wait_s DESC;

Follow-ups

  • Connection pool exhausted — cause or symptom? — Almost always a symptom: queries hold connections longer because they are waiting; fixing the wait releases the pool.
  • When do you fail over? — When the instance itself is degraded (storage, memory, corruption), not for a query problem — a failover restarts the same workload against a cold cache.
  • What goes in the postmortem? — The wait profile, the change that triggered it, the detection gap, and one systemic fix (a timeout, an alert, a CI check), not just “we killed the session”.

Wrong answer: jumping straight to “update statistics and clear the plan cache”. It sometimes appears to work, it destroys the evidence and the warmed cache, and it means the next occurrence starts from zero knowledge.

08NULLs, types, collation & text

Small, sharp questions that catch people out, and the source of a disproportionate share of real production bugs. Interviewers use them as truth-serum: a candidate who has actually shipped systems has been burned by three-valued logic, by float money, and by a collation mismatch across a join. At principal level the question widens to policy — what your schema standards say about types, time zones and collation, and how you enforce them.

Explain three-valued logic and where NULL surprises people.screener

NULL means “unknown”, so any comparison with it yields UNKNOWN, not true or false — hence NULL = NULL is not true, and you must use IS NULL. The knock-on effects are where the bugs live: WHERE status <> 'closed' silently excludes rows whose status is NULL; NOT IN (subquery) returns nothing if the subquery yields a single NULL; CHECK constraints pass when the predicate is UNKNOWN, so CHECK (qty > 0) allows NULL. Aggregates skip NULLs — COUNT(col) counts non-NULLs while COUNT(*) counts rows, and AVG divides by the non-NULL count. But GROUP BY, DISTINCT and set operators treat NULLs as equal to each other, and so does a UNIQUE constraint in… no, that is exactly where the engines differ: both allow multiple NULLs in a unique constraint per the standard, except SQL Server, which allows only one NULL in a unique index — a portability trap worth naming.

Example

-- PostgreSQL 15+: choose the semantics explicitly
CREATE UNIQUE INDEX ON t (a, b) NULLS NOT DISTINCT;   -- two NULLs now collide
-- NULL-safe comparison
WHERE a IS DISTINCT FROM b            -- PostgreSQL
WHERE EXISTS (SELECT a INTERSECT SELECT b)   -- SQL Server has no IS DISTINCT FROM

Follow-ups

  • Sorting? — PostgreSQL puts NULLs last in ASC by default and supports NULLS FIRST/LAST; SQL Server puts them first and has no such clause (you emulate with a CASE in the ORDER BY).
  • Concatenation? — NULL || 'x' is NULL in PostgreSQL; in SQL Server it depends on CONCAT_NULL_YIELDS_NULL, and CONCAT() treats NULL as an empty string.
  • Should columns be NOT NULL by default? — Yes: make nullability a deliberate decision, because every nullable column adds a case to every query that touches it.

Wrong answer: “NULL is like empty string or zero.” It leads directly to = '' comparisons, broken NOT IN filters and reports that quietly drop rows — and interviewers ask this specifically to find it.

Which type do you use for money, and why not float?screener

decimal/numeric with an explicit precision and scale, chosen from the business rules (for example numeric(19,4) to survive multi-currency rounding and unit prices). Binary floating point cannot represent 0.1 exactly, so sums drift and equality comparisons fail — the classic symptom is a reconciliation report that is off by fractions of a cent and gets “fixed” with a rounding hack. SQL Server also has money/smallmoney, which I avoid: it is a fixed 4-decimal scaled integer with well-documented rounding errors in division and no advantage over decimal. PostgreSQL has a money type too, and it is worse — its output depends on the lc_monetary setting, so the same value renders differently on different servers. Two more things a senior answer includes: store the currency alongside the amount (a bare number is not money), and consider integer minor units when the domain is a single currency with fixed scale.

Example

-- the float trap, live
SELECT 0.1::float8 + 0.2::float8 = 0.3::float8;   -- false
SELECT 0.1::numeric + 0.2::numeric = 0.3::numeric; -- true

CREATE TABLE payment (
  amount   numeric(19,4) NOT NULL CHECK (amount > 0),
  currency char(3)       NOT NULL REFERENCES currency(code));

Follow-ups

  • Cost of decimal? — Slower arithmetic than float and more bytes; irrelevant next to correctness for financial data, relevant for scientific workloads where float is the right choice.
  • Rounding rules? — Decide half-up vs banker's rounding explicitly; PostgreSQL's round() on numeric is half-up, on double precision it is half-to-even — a genuine source of penny differences.
  • Division and scale? — SQL Server has documented scale-reduction rules for decimal division that can truncate; wrap intermediate results with explicit casts.

Wrong answer: “Use money, it is the type designed for money.” Both engines' money types are legacy; naming them as the right choice suggests the candidate has not dealt with rounding or localization issues.

How do you store timestamps, and how do you handle time zones?senior

Store instants in UTC with an offset-aware type: PostgreSQL's timestamptz (which stores UTC and converts on input/output using the session TimeZone) and SQL Server's datetimeoffset (which stores the local time plus its offset). Avoid PostgreSQL's plain timestamp and SQL Server's datetime: the former silently drops zone information, the latter also has 3.33 ms rounding and a 1753 lower bound — datetime2 superseded it in 2008 and there is no reason to choose it in new code. The senior nuance is that not everything is an instant: a birthday is a date, a shop's opening time is a local wall-clock time, and a future appointment in Berlin must be stored as local time plus the IANA zone name, because governments change offsets and “09:00 local” must survive that. SQL Server's AT TIME ZONE (2016+) uses Windows zone names on Windows and IANA names on Linux, which is a real portability wrinkle; PostgreSQL uses IANA everywhere.

Example

-- PostgreSQL: instants in UTC, rendered per user
SELECT created_at AT TIME ZONE 'Europe/Budapest' FROM event;   -- timestamptz → local

-- SQL Server 2016+
SELECT created_at AT TIME ZONE 'UTC' AT TIME ZONE 'Central European Standard Time'
FROM dbo.event;   -- Windows zone id; on Linux use 'Europe/Budapest'

Follow-ups

  • Why is GETDATE()/now() risky? — They return server-local time; use SYSUTCDATETIME() in SQL Server, and remember now() in PostgreSQL is transaction start time (clock_timestamp() is the real clock).
  • Storing a recurring event? — Store the rule plus the zone, materialize instances; never precompute UTC instants years ahead across a DST rule change.
  • Range queries? — Half-open intervals (>= start AND < end) always, because BETWEEN plus fractional seconds is a boundary bug factory.

Wrong answer: “Store local time and convert in the UI.” It makes ordering, deduplication and DST-ambiguous hours (2:30am occurring twice) unresolvable in the data, and it is the most common time bug in production systems.

What is collation, and what breaks when it is wrong?senior

Collation defines sort order and comparison semantics — including case and accent sensitivity — for character data. Three things break when it is inconsistent. Joins and comparisons: in SQL Server, joining two varchar columns with different collations raises a “cannot resolve the collation conflict” error, and applying COLLATE to fix it makes the predicate non-SARGable, killing the index. Index validity: in PostgreSQL, an operating-system glibc upgrade can change the locale's sort order, which silently corrupts every text index built under the old order — this is why PostgreSQL now tracks collation versions and warns, and why the ICU provider (default-capable since PG 15) and C collation exist as stable alternatives. Uniqueness semantics: a case-insensitive collation makes Bob and bob the same key, which is either exactly what you want for emails or a nasty surprise for identifiers. SQL Server's default is often case-insensitive (SQL_Latin1_General_CP1_CI_AS) while PostgreSQL is case-sensitive by default, so people migrating between them hit this immediately.

Example

-- PostgreSQL: after a glibc upgrade, this is a real alarm
-- WARNING: database "app" has a collation version mismatch
REINDEX DATABASE app;                        -- then:
ALTER DATABASE app REFRESH COLLATION VERSION;

-- PostgreSQL: case-insensitive uniqueness without a CI collation
CREATE UNIQUE INDEX ON "user" (lower(email));
-- SQL Server: column-level collation override
ALTER TABLE dbo.[user] ALTER COLUMN email varchar(320)
  COLLATE Latin1_General_100_CI_AS_SC_UTF8 NOT NULL;

Follow-ups

  • What is citext? — A PostgreSQL extension type that compares case-insensitively; workable, but a lower() expression index or a nondeterministic ICU collation is usually cleaner.
  • UTF-8 in SQL Server? — Since 2019 there are _UTF8 collations, so varchar can hold UTF-8; before that, Unicode meant nvarchar and double the bytes.
  • Why does LIKE 'x%' not use my PostgreSQL index? — Non-C collations need text_pattern_ops on the index for pattern prefix matching.

Wrong answer: “Collation only affects ORDER BY.” It affects equality, uniqueness, index usability and cross-database joins, and treating it as a display concern is how a migration ends with duplicate users.

char, varchar, nvarchar, text — what do you actually choose?mid

In PostgreSQL the honest answer is that text, varchar and varchar(n) are the same underlying type with different length checks and no performance difference; use text with a CHECK constraint if you want a limit that is easy to change, and avoid char(n), which pads with spaces. In SQL Server the choice matters more: varchar is single-byte-per-char in a legacy collation (or true UTF-8 in a _UTF8 collation since 2019), nvarchar is UTF-16, and mixing them across a predicate causes the implicit conversion that kills index seeks. Length is not free there either: nvarchar(max) is stored off-row past 8,000 bytes, cannot be an index key, and disables some optimizations, so declare realistic lengths. Both engines agree on one rule interviewers like: pick the length from the domain (an email is 320 characters by RFC, an ISO country code is 2), not from a habit of varchar(255).

Example

-- PostgreSQL: the idiomatic form
name text NOT NULL CHECK (length(name) BETWEEN 1 AND 200)
-- changing the limit is a constraint change, not a table rewrite

-- SQL Server: match the app's parameter type or lose the seek
sku varchar(50) NOT NULL      -- .NET must send SqlDbType.VarChar, not the nvarchar default

Follow-ups

  • Is varchar(50) faster than varchar(4000) in SQL Server? — Not in storage, but the declared length feeds memory-grant estimates, so oversized declarations inflate grants and cause spills elsewhere.
  • PostgreSQL and long values? — TOAST compresses and moves large values out of line automatically; a wide text column you rarely select is cheap.
  • When is char(n) right? — Genuinely fixed-width codes where padding is harmless; rarely worth the surprise.

Wrong answer: “Use nvarchar(max) everywhere so we never hit a limit.” It blocks indexing, forces off-row storage, wrecks memory grants, and hides data-quality bugs that a length constraint would have caught at the boundary.

A team wants to change a column's type on a 500M-row table. How do you plan it?principal

First I ask what the change actually is, because both engines have cheap cases and catastrophic ones. In PostgreSQL, widening varchar(50) to varchar(100) or to text is a catalog-only change; int → bigint is a full table rewrite under ACCESS EXCLUSIVE, which on 500M rows means hours of downtime. In SQL Server, increasing a varchar length is metadata-only, while changing int to bigint historically rewrote the table (it became metadata-only for certain cases with ALTER COLUMN in later versions, but the safe assumption is a rewrite). So the plan for the expensive case is the expand/contract dance: add a new nullable column, backfill in bounded batches with a throttle, dual-write from the application (or a trigger), verify equality with a reconciliation query, switch reads, then drop the old column in a later release. Every step is independently revertible, and none takes a long exclusive lock. I would also name the alternative — a shadow table plus logical replication or a tool like pg_repack for the swap — and the fact that the identity/sequence, indexes, constraints, views and any ORM mapping all need to move with it.

Example

-- PostgreSQL: int → bigint without an ACCESS EXCLUSIVE rewrite
ALTER TABLE event ADD COLUMN id_big bigint;                     -- fast, nullable
-- backfill in batches (id ranges), with sleeps, monitoring replication lag
UPDATE event SET id_big = id WHERE id BETWEEN $1 AND $2 AND id_big IS NULL;
CREATE UNIQUE INDEX CONCURRENTLY ux_event_id_big ON event (id_big);
-- then: dual-write, verify count(*) FILTER (WHERE id_big IS DISTINCT FROM id) = 0, swap, drop

Follow-ups

  • How do you throttle the backfill? — Batch size plus a sleep, and a feedback loop on replication lag and lock waits; a backfill that pushes a replica an hour behind is an outage.
  • What breaks with the ORM? — Model and migration must tolerate both shapes during the transition; that is why dual-write is a code change, not just a DDL script.
  • When would you take the downtime instead? — When the maintenance window is genuinely available and cheaper than three weeks of dual-write complexity; that is a legitimate, defensible choice.

Wrong answer: “Just run ALTER TABLE ... ALTER COLUMN, it is one statement.” On a rewrite case it holds an exclusive lock for the whole rewrite, doubles the disk usage, floods the WAL/log, and cannot be interrupted without redoing it — the single-statement framing is what causes the incident.

09Statistics, cardinality & parameter sniffing

The “why did the plan change?” unit. It is asked less often than indexing but it is where senior candidates prove they understand the optimizer as an estimator rather than a black box. Expect: how estimates are produced, what makes them wrong, what parameter sniffing is, and how you stop a plan regression from taking down a release. Deep knowledge here is what makes an upgrade or a compatibility-level change a planned event rather than a surprise.

How does the optimizer estimate row counts, and where does it go wrong?senior

From statistics: a histogram of the leading column's value distribution plus density/n-distinct information, sampled rather than complete. Selectivity for a predicate is looked up in the histogram; for multiple predicates the estimator has to combine them, and that is where it goes wrong. The classic failure is correlated columns — city = 'Budapest' AND country = 'Hungary' — where independence assumptions multiply the selectivities and underestimate by orders of magnitude. Others: expressions and function calls the estimator cannot see through (it falls back to fixed guesses), local variables in T-SQL (unknown at compile time, so density-based averages), multi-statement table-valued functions (historically a fixed guess of 1 or 100 rows), out-of-range predicates beyond the last histogram step (the ascending-key problem on a date column loaded daily), and stale statistics after bulk loads. SQL Server 2014's new cardinality estimator changed several of these assumptions, which is why compatibility level is a plan-affecting setting.

Example

-- PostgreSQL: teach the planner that these columns are correlated
CREATE STATISTICS stx_city (dependencies, ndistinct, mcv) ON city, country FROM address;
ANALYZE address;

-- SQL Server: look at what the histogram actually says
DBCC SHOW_STATISTICS('dbo.[order]', IX_order_placed_at) WITH HISTOGRAM;

Follow-ups

  • Histogram size? — SQL Server caps at 200 steps regardless of table size, which is coarse on a billion-row table; PostgreSQL's default_statistics_target (100 by default) can be raised per column.
  • How do you detect a bad estimate quickly? — Compare estimated to actual rows in the plan; a factor of 100+ at a leaf node is your culprit.
  • Multi-column statistics in SQL Server? — A composite index creates a multi-column density vector, but the histogram still covers only the leading column.

Wrong answer: “The optimizer knows the data, so if the plan is bad the query is bad.” The optimizer knows a sample, summarized; almost every mysterious plan regression is a story about that summary being wrong or out of date.

When do statistics update automatically, and when do you update them manually?senior

SQL Server auto-updates a statistic when a threshold of modifications is crossed: historically 20% of the rows plus 500, and since 2016 (or earlier with trace flag 2371) a dynamic square-root-based threshold that triggers much sooner on large tables. PostgreSQL's autovacuum daemon runs ANALYZE when changes exceed autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × reltuples (10% by default). I update manually in three situations: right after a bulk load or a large batch job, because the next query will otherwise compile against pre-load statistics; on ascending-key columns where today's data is always beyond the last histogram step; and on tables so large that the default scale factor means “never in practice” — for those I lower the per-table scale factor rather than scheduling a script. The related lever is sampling rate: SQL Server 2016+ supports WITH PERSIST_SAMPLE_PERCENT so auto-updates keep your chosen rate, and PostgreSQL's per-column SET STATISTICS raises the target where it matters.

Example

-- PostgreSQL: make a huge, hot table analyze often enough
ALTER TABLE event SET (autovacuum_analyze_scale_factor = 0.01,
                       autovacuum_vacuum_scale_factor  = 0.01);
ALTER TABLE event ALTER COLUMN tenant_id SET STATISTICS 500;

-- SQL Server: keep a higher sample rate on auto-updates
UPDATE STATISTICS dbo.[order] WITH SAMPLE 30 PERCENT, PERSIST_SAMPLE_PERCENT = ON;

Follow-ups

  • Does updating statistics invalidate plans? — Yes, it triggers recompilation of dependent plans, which is both the fix and the risk (a recompile storm on a busy instance).
  • Async update? — SQL Server's AUTO_UPDATE_STATISTICS_ASYNC lets the query run with old stats while the update happens in the background; good for latency-sensitive OLTP, bad if the first plan is catastrophic.
  • PostgreSQL after a restore? — Statistics historically were not carried over by pg_upgrade; PostgreSQL 18 changed that and now preserves optimizer statistics (though not extended statistics), which removes the classic “terrible for an hour after upgrade” window.

Wrong answer: “We rebuild all indexes nightly, so statistics are always fresh.” A rebuild refreshes only the statistics attached to those indexes, at full scan, at enormous cost — and it does nothing for column statistics created automatically on non-indexed predicates.

What is parameter sniffing, and how do you handle it?senior

On first compilation the engine “sniffs” the actual parameter values and builds a plan optimal for them; that plan is then cached and reused for every other value. When the data is skewed — one tenant with 10 million rows, the rest with a thousand — the cached plan can be catastrophic for the other side. It is not a bug: caching is what makes OLTP fast, and the same mechanism gives you a good plan most of the time. Fixes, from targeted to blunt: OPTION (RECOMPILE) on the specific statement (perfect plan per execution, CPU cost per execution); OPTIMIZE FOR (@p = <typical>) to pin a representative value; OPTIMIZE FOR UNKNOWN to use average density and get a mediocre plan for everyone; splitting the procedure into branches per shape; or Query Store plan forcing. Since SQL Server 2022, Parameter Sensitive Plan optimization handles the common single-predicate case automatically by caching multiple plans keyed by cardinality buckets, and SQL Server 2025's OPPO extends multi-plan support to optional-parameter (“kitchen sink”) queries. PostgreSQL's analogue is generic vs custom plans: a prepared statement is planned per-execution for its first five runs and may then switch to a generic plan, controlled by plan_cache_mode.

Example

-- PostgreSQL: force per-value planning for a skewed prepared statement
SET plan_cache_mode = force_custom_plan;

-- SQL Server: the targeted fix, on the statement that needs it
SELECT ... FROM dbo.[order] WHERE tenant_id = @tenant AND placed_at >= @from
OPTION (RECOMPILE);

Follow-ups

  • How do you confirm it? — The cached plan's XML records the compiled parameter values; compare them with the runtime values in sys.dm_exec_query_stats/Query Store.
  • Why is clearing the cache a bad fix? — It re-sniffs whatever value happens to arrive first; you get a coin flip, and you lose every other plan on the instance.
  • Does the local-variable trick still work? — Assigning a parameter to a local variable defeats sniffing and gives density-average estimates; it is the old workaround, equivalent to OPTIMIZE FOR UNKNOWN and just as blunt.

Wrong answer: “Add WITH RECOMPILE to every stored procedure so plans are always optimal.” It removes plan reuse across the whole instance and converts an occasional bad plan into permanent, unbounded compilation CPU — the fix that causes the next outage.

Plan cache and plan reuse: what causes cache bloat and recompilation storms?senior

Ad-hoc SQL with inlined literals is the main cause: every distinct literal produces a distinct cache entry, so a system that concatenates values into SQL fills the plan cache with single-use plans, evicting the ones that matter. The fixes are parameterization in the application, optimize for ad hoc workloads (stores a stub on first execution), and, as a last resort on a codebase you cannot change, forced parameterization at the database level. Recompilation is the other side: it is triggered by schema changes, statistics updates, SET option changes mid-batch, temp table DDL inside a procedure, and explicit RECOMPILE hints — a storm shows up as high SQL Compilations/sec relative to batches, and as RESOURCE_SEMAPHORE_QUERY_COMPILE waits. In PostgreSQL there is no shared plan cache at all: plans are cached per session for prepared statements, so the equivalent problems are per-connection memory and the generic-plan switch, and with a connection pooler in transaction mode you often lose prepared-statement reuse entirely — which is a real, measurable cost people forget when adopting PgBouncer.

Example

-- SQL Server: single-use plans hogging the cache
SELECT objtype, COUNT(*) AS plans, SUM(CAST(size_in_bytes AS bigint))/1024/1024 AS mb
FROM sys.dm_exec_cached_plans WHERE usecounts = 1 GROUP BY objtype ORDER BY mb DESC;

EXEC sp_configure 'optimize for ad hoc workloads', 1; RECONFIGURE;

Follow-ups

  • What does SQL Server's simple parameterization cover? — Only trivially safe statements; anything with joins or complex predicates stays ad-hoc unless you force parameterization.
  • PgBouncer and prepared statements? — Transaction pooling historically broke them; modern PgBouncer (1.21+) supports protocol-level prepared statements, which is worth knowing before you blame the app.
  • Is clearing the cache ever right? — In an emergency, DBCC FREEPROCCACHE scoped to a single plan handle; never instance-wide on a busy production server.

Wrong answer: “Dynamic SQL is fine because the plan cache handles it.” It handles it by storing one plan per literal combination, which is exactly the bloat; the missing piece is parameterization.

You upgrade SQL Server and 5% of queries regress. What is your process?principal

This is a solved problem with a documented path, and knowing it is the point of the question. Before the upgrade: enable Query Store and collect a baseline at the current compatibility level. Upgrade the engine but keep the old compatibility level, so the query optimizer behaviour does not change with the binaries. Then raise the compatibility level as a separate, scheduled change, watch Query Store's regressed-queries view, and fix the outliers individually — force the previous plan for a quick save, then address the root cause (statistics, a rewrite, a hint) with a ticket per forced plan. Automatic Plan Correction can do the forcing for you if you have validated it. The same discipline applies to PostgreSQL major upgrades, minus the plan store: baseline with pg_stat_statements, upgrade, immediately run ANALYZE (less critical since PG 18 carries statistics through pg_upgrade), then diff the top queries by total time. In both cases the principal-level content is the sequencing and the rollback plan, not the individual query fixes.

Example

-- SQL Server: decouple the binaries from the optimizer behaviour
ALTER DATABASE app SET COMPATIBILITY_LEVEL = 160;   -- stay on the old level after upgrade
ALTER DATABASE app SET QUERY_STORE = ON (OPERATION_MODE = READ_WRITE);
-- later, deliberately:
ALTER DATABASE app SET COMPATIBILITY_LEVEL = 170;   -- SQL Server 2025
ALTER DATABASE app SET AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = ON);

Follow-ups

  • What if you cannot raise the compatibility level at all? — You can adopt the new CE selectively with database-scoped configurations (LEGACY_CARDINALITY_ESTIMATION, QUERY_OPTIMIZER_HOTFIXES) instead of an all-or-nothing switch.
  • How do you test before production? — Distributed Replay or a captured workload replayed against a restored copy at both levels, compared through Query Store.
  • How long do forced plans live? — Until someone removes them; put an expiry and an owner on each, or they become permanent invisible debt.

Wrong answer: “Upgrade and set the newest compatibility level at the same time; if something breaks, roll back the server.” Rolling a database back after an upgrade is not possible without a restore, and coupling the two changes means you cannot tell which one caused the regression.

PostgreSQL cost settings: what are random_page_cost and work_mem, and how do you set them?senior

random_page_cost (default 4.0) expresses how much more expensive a random page read is than a sequential one, relative to seq_page_cost (1.0). That 4:1 ratio models spinning disks; on SSD or NVMe the right value is typically 1.1–2.0, and leaving it at 4 systematically biases the planner away from index scans towards sequential scans — one of the highest-leverage single settings on modern hardware. effective_cache_size (not an allocation, just a hint about how much OS cache exists — commonly 50–75% of RAM) pushes the same way. work_mem is per sort/hash node, not per query or per connection, so the worst case is roughly work_mem × nodes × parallel workers × connections; that is why raising it globally to 1 GB is how people OOM a server. The right approach is a modest global value and per-statement or per-role overrides for the analytical queries that need it. In PostgreSQL 18 the I/O picture also changed: with the new asynchronous I/O subsystem and io_method (worker-based by default), sequential and bitmap scans read ahead far more effectively, which is another reason the old disk-era cost defaults deserve revisiting.

Example

ALTER SYSTEM SET random_page_cost = 1.1;          -- NVMe
ALTER SYSTEM SET effective_cache_size = '48GB';   -- a hint, not an allocation
ALTER SYSTEM SET work_mem = '32MB';               -- modest default...
ALTER ROLE reporting SET work_mem = '512MB';      -- ...raised only where it pays
SELECT pg_reload_conf();

Follow-ups

  • How do you know work_mem is too low? — Batches > 1 on a Hash node, or Sort Method: external merge Disk: ... in EXPLAIN ANALYZE.
  • SQL Server equivalent? — There is no per-node knob; memory grants are computed from estimates and governed by Resource Governor, so the fix there is fixing the estimate.
  • shared_buffers? — Commonly ~25% of RAM; PostgreSQL relies on the OS page cache too, so unlike SQL Server's buffer pool it is not meant to hold everything.

Wrong answer: “Set work_mem high so nothing spills.” It is per node per worker; a few dozen concurrent complex queries then request many times the machine's RAM and the OOM killer takes the postmaster down.

10Storage internals, WAL/log & vacuum

Asked when the interviewer wants to know whether you understand the machine under the SQL. It comes up naturally from “why is my table 4× bigger than its data”, “why did the log fill up” and “what does a commit actually do”. Mid-level candidates need the write-ahead log concept and page basics; senior and principal candidates are expected to reason about durability settings, checkpoint tuning and vacuum strategy as capacity and risk decisions.

What happens on COMMIT? Explain write-ahead logging.mid

Both engines use write-ahead logging: the change is written to the log (SQL Server's transaction log, PostgreSQL's WAL) and flushed to durable storage before the data pages are, so the commit is durable even though the modified pages are still dirty in memory. Data pages are written later, in bulk, by the checkpoint process and the background/lazy writer. This is what makes commits fast (sequential log writes) and recovery possible (redo committed transactions from the log, undo uncommitted ones). The two operational consequences are the questions that follow: log throughput and latency are the ceiling on write throughput, so the log belongs on the fastest storage you have; and the log cannot be reused until the changes are both flushed and no longer needed — by backups, by replicas, by replication slots, or by an open transaction — which is why “the disk filled up” is almost always “something is holding the log”.

Example

-- SQL Server: why can't the log be truncated?
SELECT name, recovery_model_desc, log_reuse_wait_desc FROM sys.databases;
-- LOG_BACKUP | ACTIVE_TRANSACTION | REPLICATION | AVAILABILITY_REPLICA ...

-- PostgreSQL: what is holding WAL?
SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;

Follow-ups

  • Group commit? — Both engines batch concurrent commits into one flush; PostgreSQL exposes commit_delay/commit_siblings, SQL Server does it internally and offers delayed durability as an explicit option.
  • What is a checkpoint? — Flushing dirty pages so recovery has less to redo; tuned by checkpoint_timeout/max_wal_size in PostgreSQL and by recovery-interval/indirect checkpoints in SQL Server.
  • Why is the log on its own volume? — Sequential write pattern versus the data files' random pattern, and so a full data volume does not stop commits.

Wrong answer: “COMMIT writes the data to the data file.” It writes the log; getting this backwards means the rest — checkpoints, recovery time, log growth, replication — cannot be reasoned about correctly.

The SQL Server transaction log has grown to fill the disk. What do you do?senior

Diagnose before shrinking: log_reuse_wait_desc in sys.databases names the reason directly. The common causes are LOG_BACKUP (the database is in FULL recovery and nobody is taking log backups — by far the most common, and the fix is to start taking them, not to switch to SIMPLE in a panic), ACTIVE_TRANSACTION (an open transaction, so find and resolve it), REPLICATION/AVAILABILITY_REPLICA (a stalled replica or CDC capture job holding log records), or CHECKPOINT. Only after removing the cause does shrinking make sense, and then with DBCC SHRINKFILE once, back to a sensible size with pre-sized growth — repeated shrink/grow cycles cause VLF fragmentation and slow recovery. The lead-level answer includes the prevention: FULL recovery requires a log backup schedule as part of the definition of “database exists”, log free-space alerting is not optional, and the log file should be pre-sized with a fixed growth increment rather than a percentage.

Example

SELECT name, log_reuse_wait_desc, recovery_model_desc,
       size * 8 / 1024 AS size_mb FROM sys.master_files mf
JOIN sys.databases d ON d.database_id = mf.database_id WHERE mf.type_desc = 'LOG';

-- after fixing the cause, and only once:
BACKUP LOG app TO DISK = 'L:\app_log.trn';
DBCC SHRINKFILE (app_log, 8192);      -- back to a pre-sized 8 GB

Follow-ups

  • Why is switching to SIMPLE a bad emergency fix? — It breaks the log-backup chain, so point-in-time recovery is gone until the next full backup — you have traded an availability incident for a data-loss risk.
  • VLFs? — Too many virtual log files (from small percentage autogrowth) slow recovery and log backups; check sys.dm_db_log_info.
  • PostgreSQL equivalent? — WAL fills pg_wal, usually because of an inactive replication slot or archiving failure; max_slot_wal_keep_size (PG 13+) bounds the damage.

Wrong answer: “Shrink the log; it grew for no reason.” It grew for a reason, which shrinking does not address — so it grows again, now with fragmented VLFs and, if you switched to SIMPLE, without a recovery chain.

Explain autovacuum: what it does, why it falls behind, and how you tune it.senior

Autovacuum does three jobs: reclaim dead tuples so space is reusable, update the visibility map (which is what makes index-only scans possible), and freeze old transaction ids to prevent wraparound. It falls behind for identifiable reasons: too few workers for the number of busy tables (autovacuum_max_workers, and each table is processed by one worker), throttling by the cost-delay settings (the defaults are conservative for modern hardware — autovacuum_vacuum_cost_limit is the main lever), scale factors that mean a billion-row table needs 200 million dead tuples before it is even considered, and — the big one — a long-running transaction, an abandoned replication slot or hot_standby_feedback holding the xmin horizon so vacuum is allowed to remove nothing. Tuning is per-table for the hot tables (low scale factors, sometimes a fixed threshold) plus a global raise of the cost limit, and monitoring pg_stat_user_tables.n_dead_tup and last_autovacuum. PostgreSQL 19 (in beta as of September 2026) adds parallel autovacuum for indexes, which targets exactly the “one worker cannot keep up with a huge table” case.

Example

-- who is bloated and when were they last vacuumed?
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / NULLIF(n_live_tup, 0), 1) AS dead_pct,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables WHERE n_dead_tup > 10000 ORDER BY n_dead_tup DESC;

ALTER TABLE job SET (autovacuum_vacuum_scale_factor = 0.02, autovacuum_vacuum_cost_delay = 0);

Follow-ups

  • Wraparound protection? — Monitor age(datfrozenxid); at autovacuum_freeze_max_age a non-cancellable anti-wraparound vacuum starts, and at ~2 billion the cluster stops accepting writes.
  • Does vacuum block? — Plain VACUUM takes a SHARE UPDATE EXCLUSIVE lock (concurrent with DML, conflicts with DDL); VACUUM FULL takes ACCESS EXCLUSIVE and rewrites the table.
  • Index bloat? — REINDEX ... CONCURRENTLY; B-tree deduplication (PG 13+) and bottom-up index deletion (PG 14+) reduced how often this is needed.

Wrong answer: “Turn autovacuum off and vacuum in a nightly window instead.” It is the fastest route to wraparound and to unusable index-only scans; every experienced PostgreSQL operator has seen the outage that follows, so this answer is disqualifying.

What is table and index bloat, and how do you measure and fix it?senior

Bloat is space occupied by dead tuples and partially-empty pages: the relation on disk is much larger than the live data it holds, so every scan reads more pages, the cache holds less useful data and backups grow. In PostgreSQL you estimate it with pgstattuple (exact, expensive) or the well-known estimation queries against pg_class/pg_statistic (cheap, approximate); a table at 30–40% dead space with vacuum running normally is usually just steady state, while 3× the live size means vacuum is being prevented. Fixes: fix the cause first (long transactions, slots, cost limits), then reclaim with pg_repack (online, needs disk for a copy) or VACUUM FULL (offline for that table). SQL Server's equivalent concerns are internal and external fragmentation plus forwarded records in heaps; sys.dm_db_index_physical_stats measures them, and the fix is a rebuild or, for heaps, adding a clustered index. Worth naming: the SQL Server 2025 answer to a different flavour of this problem is that optimized locking and ADR keep version storage in-row, so long transactions no longer bloat tempdb the way they used to.

Example

CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT * FROM pgstattuple('public.job');       -- dead_tuple_percent, free_percent
-- online rebuild without an exclusive lock (external tool)
--   pg_repack --table public.job --no-superuser-check app

Follow-ups

  • Why does DELETE not shrink the file? — Space is marked reusable, not returned; only a rewrite returns it to the filesystem.
  • fillfactor? — Leaving free space per page enables HOT updates in PostgreSQL and reduces page splits in SQL Server; worth lowering on update-heavy tables only.
  • Partitioning as bloat control? — Dropping an old partition is instant and returns all its space, which beats deleting and vacuuming an equivalent range.

Wrong answer: “Run VACUUM FULL weekly to keep tables tidy.” It takes an ACCESS EXCLUSIVE lock and rewrites the whole table — a scheduled outage that also invalidates the argument for having autovacuum tuned properly in the first place.

How does a row get stored? Pages, fill factor, row overflow, TOAST.senior

Both engines store rows in fixed-size pages — 8 kB in both SQL Server (with 8 pages to an extent) and PostgreSQL by default — and a row cannot span pages. SQL Server handles oversized rows with row-overflow storage: variable-length columns are pushed off-row into ROW_OVERFLOW_DATA pages with a 24-byte pointer left in row, and LOB types go to LOB_DATA pages. PostgreSQL uses TOAST: values over roughly 2 kB are compressed and, if still too big, sliced into chunks in a side table, transparently — with the storage strategy selectable per column (PLAIN, MAIN, EXTERNAL, EXTENDED) and, since PG 14, LZ4 as an alternative to the historical pglz. Two practical consequences a senior answer draws: a wide table with many rarely-used large columns is fine because they live elsewhere and are not read unless selected; and fillfactor reserves free space per page, which matters for HOT updates in PostgreSQL and page splits in SQL Server, but wastes cache when the insert pattern is append-only.

Example

-- PostgreSQL: keep a big blob out of line and uncompressed (already-compressed data)
ALTER TABLE document ALTER COLUMN pdf_bytes SET STORAGE EXTERNAL;
ALTER TABLE "order" SET (fillfactor = 90);      -- room for HOT updates

-- SQL Server: what is actually on the page?
SELECT index_id, index_type_desc, avg_fragmentation_in_percent, avg_page_space_used_in_percent
FROM sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('dbo.[order]'), NULL, NULL, 'SAMPLED');

Follow-ups

  • Page split? — An insert into a full page splits it, moving half the rows: extra I/O, log records and fragmentation; sequential keys avoid it, random GUID keys cause it constantly.
  • Why are narrow rows faster? — More rows per page means fewer pages read for a scan and better cache density; this is the argument behind vertical partitioning of wide tables.
  • Compression? — SQL Server has row/page compression and columnstore; PostgreSQL compresses only TOASTed values, so table-level compression means an extension or the filesystem.

Wrong answer: “Large text columns slow down every query on the table.” They do not if they are stored out of line and you do not select them — which is exactly why SELECT * is more expensive than people think.

What are the durability knobs, and when would you relax them?principal

PostgreSQL: synchronous_commit (on / remote_apply / remote_write / local / off) controls whether a commit waits for the WAL flush and for replicas; fsync and full_page_writes control whether you are crash-safe at all. SQL Server: delayed durability (2014+) makes commits return before the log flush, at database or transaction scope. The rule is that relaxing durability buys throughput and costs a bounded window of committed-but-lost transactions on a crash — bounded, not corrupt: with synchronous_commit = off or delayed durability you may lose the last fraction of a second of commits, but the database stays consistent. Turning off fsync or full_page_writes is different in kind: that risks corruption, and it belongs only in throwaway environments. Where I would relax: bulk loads and ETL into staging tables, high-volume telemetry where a lost second is acceptable, and test environments. Where I would not: anything a user is told succeeded — an order, a payment, an audit record. It is a per-transaction decision in both engines, which is the right granularity and the answer interviewers want.

Example

-- PostgreSQL: relax for this transaction only
BEGIN;
  SET LOCAL synchronous_commit = off;
  INSERT INTO telemetry SELECT * FROM staging_batch;
COMMIT;

-- SQL Server: same idea, per transaction
BEGIN TRANSACTION;
  INSERT INTO dbo.telemetry ...;
COMMIT WITH (DELAYED_DURABILITY = ON);

Follow-ups

  • What does synchronous_commit = remote_apply give you? — Read-your-writes on the synchronous standby, at the cost of the round trip plus replay; the strongest and slowest setting.
  • Unlogged tables? — PostgreSQL UNLOGGED tables skip WAL entirely and are truncated after a crash; excellent for derived/staging data, never for source of truth, and they are not replicated.
  • How do you decide? — Write the data-loss budget into the SLO with the business; “we may lose up to 200 ms of telemetry on a crash” is an agreement, not a config change.

Wrong answer: “Set fsync = off for speed; the replica protects us.” The replica replicates what the primary wrote, and with fsync off a crash can leave the primary's data files inconsistent — that is corruption, not lag.

How would you detect and respond to database corruption?principal

Detection has to be proactive, because corruption is usually silent until the page is read. SQL Server: PAGE_VERIFY CHECKSUM on every database plus scheduled DBCC CHECKDB (often run against a restored copy to avoid the I/O on production), with alerts on error 823/824/825 and on the suspect_pages table. PostgreSQL: data checksums, which in PostgreSQL 18 are finally enabled by default at initdb (you must pass --no-data-checksums to opt out) — before 18 the default was off, so any older cluster likely has none unless someone enabled it with pg_checksums. Response, in order: stop making it worse (take the affected object out of the write path if possible), determine scope (DBCC CHECKDB output, or amcheck for PostgreSQL indexes), and prefer restore over repair — restore from the last good backup plus log/WAL to a point before the corruption. DBCC CHECKDB ... REPAIR_ALLOW_DATA_LOSS is the last resort and it means what it says. Then find the cause, which is nearly always storage, firmware or memory, because a database that corrupts itself twice will corrupt itself a third time.

Example

-- SQL Server: verify and check
ALTER DATABASE app SET PAGE_VERIFY CHECKSUM;
DBCC CHECKDB ('app') WITH NO_INFOMSGS, ALL_ERRORMSGS, DATA_PURITY;
SELECT * FROM msdb.dbo.suspect_pages;

-- PostgreSQL: are checksums on, and are indexes sane?
SHOW data_checksums;
CREATE EXTENSION amcheck; SELECT bt_index_check('ix_order_customer'::regclass, true);

Follow-ups

  • Can you restore a single page? — SQL Server supports page-level restore in FULL recovery, which is the surgical option for a handful of bad pages.
  • Do backups validate anything? — BACKUP ... WITH CHECKSUM and RESTORE VERIFYONLY in SQL Server; in PostgreSQL, restore-and-check is the only real validation, which is an argument for automated restore testing.
  • What is the actual root cause usually? — Storage layer: a failing controller, a lying cache, or an unclean host failure — and it recurs until the hardware is replaced.

Wrong answer: “Run REPAIR_ALLOW_DATA_LOSS and move on.” It deletes what it cannot fix, with no record of what was lost, and it converts a recoverable incident into permanent silent data loss — the restore path exists precisely so you do not do this.

11Migrations & zero-downtime change

Increasingly asked at senior and lead level, because it is where database knowledge meets delivery practice. The question is rarely “which migration tool” and usually “how do you rename a column in a system that never stops”. What is being tested: expand/contract thinking, knowledge of which DDL takes which lock, and whether you treat a migration as code with a rollback plan.

How do you rename a column with zero downtime?senior

You do not rename it — you run expand/contract across at least three releases. Expand: add the new column, backfill it in bounded batches, and make the application write both. Migrate: switch reads to the new column once the backfill is verified equal. Contract: stop writing the old column, then drop it a release later. Each step is independently deployable and revertible, and at no point do old and new application versions disagree about the schema — which is the actual requirement, because during a rolling deploy both versions are running at once. The same shape covers splitting a column, changing a type, moving a column to another table, and introducing a normalized replacement for a denormalized field. If you have a database trigger available, it can do the dual-write instead of the application, which shortens the middle phase at the cost of hidden logic.

Example

-- release 1 (expand)
ALTER TABLE customer ADD COLUMN full_name text;             -- nullable, instant
-- backfill in batches, app writes both name and full_name

-- release 2 (migrate): app reads full_name; verify first
SELECT count(*) FROM customer WHERE full_name IS DISTINCT FROM name;  -- must be 0

-- release 3 (contract)
ALTER TABLE customer DROP COLUMN name;

Follow-ups

  • Can a view shortcut this? — Sometimes: rename the table and expose the old shape as an updatable view, buying time. It is still a multi-step plan, just with the compatibility layer in the database.
  • How do you know the backfill is done? — A reconciliation query as an explicit gate in the pipeline, not a human's judgement.
  • What about the ORM? — Its model must tolerate both shapes in the middle release; that constraint often decides how long the transition lasts.

Wrong answer: “ALTER TABLE ... RENAME COLUMN is instant, so it is safe.” The DDL is instant; the outage comes from every currently-running instance of the old application version suddenly querying a column that no longer exists.

Which DDL statements are safe on a large busy table, and which are not?senior

You have to know the lock and the rewrite behaviour per statement and per engine version. PostgreSQL safe/instant: adding a nullable column; adding a column with a constant default (rewrite-free since PG 11); dropping a column (marks it dropped, space reclaimed later); adding a NOT VALID constraint then validating separately; CREATE INDEX CONCURRENTLY. Dangerous: adding a column with a volatile default, most type changes, SET NOT NULL on a big table (a full scan under ACCESS EXCLUSIVE — though PG 12+ can use an existing equivalent CHECK constraint to skip it, and PG 18 adds NOT NULL ... NOT VALID for a two-phase path), and VACUUM FULL/CLUSTER. The subtlety that bites hardest is queueing: a blocked ACCESS EXCLUSIVE request blocks everything behind it, so always SET lock_timeout and retry. SQL Server: adding a nullable column is metadata-only, and since 2012 adding a NOT NULL column with a default is also metadata-only for most types; widening varchar is metadata-only; but adding a computed persisted column, changing a type that alters storage, or adding a clustered index rewrites the table.

Example

-- PostgreSQL: never let DDL queue behind a long query and freeze the table
SET lock_timeout = '3s';
ALTER TABLE "order" ADD COLUMN channel text;   -- retry on 55P03 lock_not_available

-- two-phase NOT NULL, no long exclusive scan
ALTER TABLE "order" ADD CONSTRAINT order_channel_nn CHECK (channel IS NOT NULL) NOT VALID;
ALTER TABLE "order" VALIDATE CONSTRAINT order_channel_nn;   -- SHARE UPDATE EXCLUSIVE

Follow-ups

  • Why is a short lock_timeout mandatory for DDL? — Without it the DDL waits, and every subsequent query queues behind the DDL's pending exclusive lock — a table-wide stall caused by a statement that never even started.
  • How do you know if a PostgreSQL DDL rewrites? — Check pg_class.relfilenode before and after in a test, or consult the per-version documentation; assumptions age badly across versions.
  • Enum changes? — ALTER TYPE ... ADD VALUE is cheap but historically could not run in a transaction block; removing a value requires recreating the type — a reason to prefer a lookup table.

Wrong answer: “DDL is transactional in PostgreSQL, so it is safe — I can always roll back.” Transactional DDL protects consistency, not availability: the rollback still happens after the lock has already blocked production for ten minutes.

How do you manage migrations in a CI/CD pipeline?senior

Migrations are versioned, ordered, immutable-once-merged files in the same repository as the code, applied by one automated path — never by hand, never from a developer's laptop. Two schools exist: state-based (SSDT, EF Core model diffs) where you declare the desired schema and the tool generates the diff, and migration-based (Flyway, Liquibase, EF Core migrations checked in, Alembic) where each change is an explicit script. I prefer migration-based for production databases because the generated diff is exactly where data-loss surprises hide — a rename becomes a drop-and-add, and a column reorder becomes a table rebuild. Around it: apply migrations as a separate pipeline step before the application deploy (so the schema is always one step ahead and backwards-compatible), require every migration to be forward-only with a documented undo path rather than relying on down-scripts, run them against a restored production-sized copy in CI to catch lock and duration problems, and gate destructive statements on an explicit approval.

Example

migrate:
  script:
    - flyway -url=$DB -locations=filesystem:./migrations validate
    - flyway -url=$DB migrate            # separate stage, runs before app deploy
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
deploy_app:
  needs: [migrate]                        # app only ships onto a schema it can use

Follow-ups

  • Do you write down-migrations? — Rarely useful in production: reverting a schema change after data has been written is a data problem, not a DDL problem. Forward-fix with a new migration.
  • How do you handle long-running migrations? — Out of the deploy path entirely: a separate, resumable, throttled job with its own monitoring, gated by a feature flag in the app.
  • Multiple services, one database? — Ownership again: one team owns each table's migrations; others get views. Otherwise two pipelines race on the same schema.

Wrong answer: “EF Core (or the ORM) generates and applies migrations at application startup.” Auto-migrate on startup means N app instances racing to migrate, no review of the generated SQL, and a schema change happening during a rolling deploy — three ways to break production at once.

How do you backfill 500 million rows without hurting production?senior

As a throttled, resumable, observable job — not a migration script. Concretely: iterate over an indexed key range with a fixed batch size, commit per batch, and sleep between batches; keep a watermark row so a restart resumes where it stopped; make the update idempotent (WHERE new_col IS NULL) so re-running a batch is harmless. The throttle should be adaptive, not a constant: watch replication lag, lock waits and the transaction log / WAL generation rate, and back off when they rise — that feedback loop is what distinguishes a senior answer, because a fixed 10 ms sleep is either too slow at 3am or too fast at peak. Two more things: batch size should be chosen so each transaction stays well under SQL Server's lock-escalation threshold and short enough not to hold back PostgreSQL's vacuum horizon, and the job needs a kill switch that on-call can flip without a deploy.

Example

-- one batch, idempotent, key-ranged, index-supported
UPDATE "order" SET channel = 'web'
WHERE id >= $1 AND id < $1 + 5000 AND channel IS NULL;

-- the throttle input
SELECT client_addr, pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_bytes
FROM pg_stat_replication;                -- back off when this grows

Follow-ups

  • Why not UPDATE the whole table once at night? — One transaction's worth of WAL/log, an hours-long rollback risk, replicas hours behind, and vacuum blocked for the duration.
  • PostgreSQL-specific cost? — Every updated row is a new tuple: a full-table backfill doubles the table's size until vacuum catches up, so plan the disk headroom.
  • How do you verify? — A reconciliation query with an explicit expected result, run as a pipeline gate, plus a sampled comparison during the run.

Wrong answer: “Run it in one transaction so it is atomic — if it fails we just roll back.” The rollback of a 500M-row update is itself an hours-long operation that cannot be interrupted, and the log growth alone may end the incident before you do.

Blue/green or rolling deploys: what does the database need to support them?principal

The invariant is that the schema must be compatible with N-1 and N application versions simultaneously, because during a rolling deploy both are live and, during a rollback, only the old one is. That single rule generates all the practices: additive changes only in the release that ships them, no column drops or renames in the same release that stops using them, defaults and nullability chosen so old code's inserts still succeed, and new constraints added NOT VALID/untrusted first so pre-existing rows written by old code do not block the deploy. For blue/green with two databases the problem is harder — you need bidirectional replication or a cutover window, because the two environments diverge the moment both take writes — which is why most teams do blue/green on the application tier and single-database expand/contract underneath. The parts people forget: stored procedures and views are also an interface with versions, feature flags let you decouple the code path from the deploy, and the rollback plan must be tested, because “we can roll back” is only true if the schema still supports it.

Example

-- release N: the new NOT NULL column that old code does not know about
ALTER TABLE "order" ADD COLUMN channel text NOT NULL DEFAULT 'unknown';
-- old code's INSERT (without channel) still succeeds; new code sets it explicitly
-- release N+2, once old code is gone:
ALTER TABLE "order" ALTER COLUMN channel DROP DEFAULT;

Follow-ups

  • Does a default column add cost? — In PostgreSQL 11+ and SQL Server 2012+ a constant default is metadata-only, so no rewrite; a volatile default still rewrites.
  • How long do you keep N-1 compatibility? — Long enough to cover your worst rollback window plus any long-lived clients (mobile apps, partner integrations) — often much longer than a deploy cycle.
  • Feature flags and schema? — The flag controls the code path; the schema must support both sides of the flag for the flag to be usable at all.

Wrong answer: “We deploy the schema and the app together, so compatibility is not an issue.” They are never atomic — instances roll one at a time, and a rollback moves the app back while the schema stays forward.

A migration is halfway through and production is degrading. What do you do?principal

Stabilize, then decide — and know before you start which of the two directions is even available. First: is the degradation caused by the migration holding a lock, by the volume of WAL/log it is generating, or by a plan change it caused? The blocking-chain and wait queries answer that in a minute. If it is a lock, cancelling is usually safe and immediate for a not-yet-committed DDL, though the rollback of a rewrite can take as long as the work done so far — which is exactly why long rewrites are avoided. If it is a throttled backfill, pause it with the kill switch: no rollback needed because each batch was committed. If it already committed a destructive change, you are in restore territory, and that decision belongs to the incident commander with the business, not to the engineer at the keyboard. Afterwards the systemic fixes: dry-run migrations against a production-sized restore, put a duration/lock budget in CI, split destructive steps into their own gated release, and keep the kill switch out of the deploy path.

Example

-- PostgreSQL: cancel the offending statement, not the connection, first
SELECT pg_cancel_backend(pid) FROM pg_stat_activity
WHERE query ILIKE 'alter table%' AND state = 'active';
-- pg_terminate_backend() only if cancel does not take

-- SQL Server
SELECT session_id, status, command, wait_type, percent_complete
FROM sys.dm_exec_requests WHERE command IN ('ALTER TABLE', 'CREATE INDEX');
KILL 87;    -- and expect a rollback that takes as long as the work done

Follow-ups

  • How do you estimate the rollback time? — SQL Server's percent_complete on the KILL/rollback; in PostgreSQL, roughly the elapsed time of the work so far for a rewrite.
  • What if the migration is not cancellable? — An anti-wraparound autovacuum or an already-committed DDL cannot be undone; the answer is capacity and communication, not heroics.
  • Who decides? — Declare an incident and let the commander decide between degraded service and a restore; a unilateral restore is how you lose the last hour of orders.

Wrong answer: “Kill it immediately, the rollback is free.” For a table rewrite the rollback costs as much as the work already done and cannot be interrupted — killing blindly can double the outage.

12HA, replication, backup & DR

Standard at lead level and in any platform or SRE-flavoured loop. The screener version is “what is the difference between backup and replication”; the real version is “what are your RPO and RTO, and how do you know”. Interviewers listen for whether you have actually restored something, whether you understand synchronous versus asynchronous trade-offs, and whether you can talk about failover as a decision with consequences.

Define RPO and RTO, and derive a backup strategy from them.screener

RPO (recovery point objective) is how much data you can afford to lose, RTO (recovery time objective) is how long you can afford to be down. They are business inputs, and every technical choice follows from them. An RPO of 5 minutes means log backups every 5 minutes (SQL Server FULL recovery) or continuous WAL archiving / streaming (PostgreSQL) — a nightly full backup alone gives an RPO of 24 hours no matter how good the storage is. An RTO of 15 minutes usually rules out “restore a 2 TB backup” and implies a standby you can fail over to, because restore time scales with database size while failover does not. The standard shape in both engines is full + differential + log (SQL Server) or a base backup plus continuous WAL with point-in-time recovery (PostgreSQL, via pgBackRest, Barman or pg_basebackup plus archiving). The sentence that makes this a senior answer: a backup you have never restored is not a backup, so restore testing is scheduled and automated, and the RTO number is the measured restore time, not an estimate.

Example

-- SQL Server: point-in-time restore to just before the bad DELETE
RESTORE DATABASE app FROM DISK = 'F:\app_full.bak' WITH NORECOVERY, REPLACE;
RESTORE DATABASE app FROM DISK = 'F:\app_diff.bak' WITH NORECOVERY;
RESTORE LOG app FROM DISK = 'F:\app_log.trn'
  WITH STOPAT = '2026-09-08T14:31:00', RECOVERY;

Follow-ups

  • Does a replica replace a backup? — No: replication faithfully copies your DELETE FROM orders to the replica in milliseconds. Only backups (or delayed replicas) protect against logical errors.
  • 3-2-1? — Three copies, two media, one offsite; add immutability — SQL Server 2025 supports backup to immutable Azure blob storage, which is a direct ransomware control.
  • How do you validate? — Automated restore into a scratch environment plus DBCC CHECKDB / a consistency query, with the result reported as a metric.

Wrong answer: “We take nightly full backups and have a replica, so we are covered.” That is a 24-hour RPO for logical errors and an untested RTO — the two numbers the question was actually about.

Synchronous vs asynchronous replication: what does each guarantee?senior

Synchronous means the primary waits for the standby to acknowledge before the commit returns, so a failover loses nothing (RPO 0) — at the cost of adding the network round trip to every commit and, crucially, of making the primary's availability depend on the standby's. In PostgreSQL, synchronous_commit = on with synchronous_standby_names set will block commits if the sole synchronous standby is down, which is why quorum forms (ANY 1 (s1, s2)) exist; in SQL Server, an availability group replica in synchronous-commit mode behaves the same way, and automatic failover requires synchronous commit plus a healthy quorum. Asynchronous means the primary does not wait: commits stay fast and a standby failure cannot stall production, but a failover loses everything not yet shipped — the lag, which you must measure and alert on. The senior framing is that this is a per-replica choice: one synchronous replica in the same availability zone for RPO 0 plus an asynchronous one in another region for disaster recovery is the common, sensible topology.

Example

-- PostgreSQL: quorum synchronous commit, so one dead standby cannot stall the primary
ALTER SYSTEM SET synchronous_standby_names = 'ANY 1 (standby_a, standby_b)';
ALTER SYSTEM SET synchronous_commit = 'on';

-- lag, in bytes and seconds
SELECT application_name, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes,
       replay_lag FROM pg_stat_replication;

Follow-ups

  • Does synchronous mean the standby has applied it? — Not necessarily: PostgreSQL distinguishes remote_write, on (flushed) and remote_apply (visible to readers); only the last gives read-your-writes on the standby.
  • Cost of cross-region synchronous? — The round trip is added to every commit; at 30 ms RTT your write throughput per session collapses. Cross-region is asynchronous in practice.
  • What is the failover trigger? — A quorum decision (WSFC for SQL Server AGs, Patroni/etcd for PostgreSQL); never a single observer, or you get split brain.

Wrong answer: “Synchronous replication has no downside, so use it everywhere.” It couples your primary's availability and latency to the standby's; a candidate who does not name that has not operated one.

Physical vs logical replication in PostgreSQL — when do you use which?senior

Physical (streaming) replication ships WAL and replays it byte-for-byte: the standby is an exact block-level copy of the whole cluster, same major version, all databases, read-only. It is the right choice for HA and for read replicas, it is cheap, and its lag is easy to reason about. Logical replication decodes the WAL into row-level changes and applies them via publications and subscriptions: it can replicate selected tables, into a different schema shape, across major versions, and into a writable target. That makes it the tool for major-version upgrades with near-zero downtime, for feeding a data warehouse or a service's read model, and for moving a tenant. Its limitations are the interview follow-up: sequences were historically not replicated (PostgreSQL 19, in beta as of September 2026, adds sequence replication), DDL is not replicated, and a replica must have a suitable replica identity (a primary key, or REPLICA IDENTITY FULL) for updates and deletes. And the operational hazard in both cases is the replication slot: an inactive slot retains WAL forever and fills the disk, which max_slot_wal_keep_size (PG 13+) exists to bound.

Example

-- publisher
CREATE PUBLICATION app_pub FOR TABLE "order", order_line;
-- subscriber (may be a newer major version)
CREATE SUBSCRIPTION app_sub
  CONNECTION 'host=primary dbname=app' PUBLICATION app_pub;

-- the hazard, bounded
ALTER SYSTEM SET max_slot_wal_keep_size = '64GB';

Follow-ups

  • SQL Server analogues? — Availability groups are the physical-ish HA answer; transactional replication and Change Data Capture play the logical role, and SQL Server 2025 adds change event streaming to Event Hubs/Fabric.
  • What breaks a logical subscription? — A conflicting row (duplicate key) stops replication until resolved; monitor pg_stat_subscription and the subscriber's log.
  • Upgrade with logical replication? — Replicate old → new, verify, then a brief cutover; the downtime is the DNS/connection switch, not the upgrade.

Wrong answer: “Logical replication is just a newer, better physical replication.” They solve different problems, and using logical for HA means hand-managing sequences, DDL and conflicts that physical replication handles for free.

Explain SQL Server Always On availability groups and their failover semantics.senior

An availability group replicates a set of databases from a primary replica to one or more secondaries, using the same log-shipping-then-redo principle: log blocks are hardened on the secondary and replayed. Synchronous-commit replicas support automatic failover (and are prerequisites for it), asynchronous ones support only manual failover with possible data loss; the whole thing sits on a Windows Server Failover Cluster (or a Linux cluster with Pacemaker) whose quorum model decides whether a failover is allowed at all. Readable secondaries offload reporting — with a real caveat, that read queries there run under snapshot isolation and can block redo, and that statistics on secondaries were historically temporary (SQL Server 2025 adds persisted statistics for readable secondaries, and Query Store on secondaries is now on by default). SQL Server 2025 also allows full and differential backups on any secondary, not just copy-only ones, which changes how backup load is distributed. The lead-level content: failover is not free — plan cache is cold, connections must be redirected via the listener, and the application needs retry logic and MultiSubnetFailover=True.

Example

-- health and lag of every replica
SELECT ar.replica_server_name, drs.synchronization_state_desc, drs.synchronization_health_desc,
       drs.log_send_queue_size, drs.redo_queue_size
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_replicas ar ON ar.replica_id = drs.replica_id;

Follow-ups

  • What is the redo queue? — Log received but not yet applied on the secondary; it is your real failover time, and it is the number to alert on.
  • Distributed AGs? — An AG of AGs for cross-region DR; SQL Server 2025 adds distributed AGs between contained AGs and better synchronization behaviour.
  • What does the app need? — Connect through the listener, MultiSubnetFailover=True, and retry on the transient errors a failover produces (connection reset, 4060, 40613 on Azure).

Wrong answer: “Failover is transparent to the application.” In-flight transactions are lost, connections break, the new primary's cache is cold, and without retry logic users see errors — describing it as transparent means never having watched one.

How do you serve reads from a replica without breaking the application?senior

The hard part is not routing, it is consistency. An asynchronous replica is behind by a variable amount, so any code that writes and then immediately reads its own write can see stale data — the “I saved it and it disappeared” bug. The pattern I use is explicit read-your-writes handling: route to the primary for a short window after a write (session-sticky), or capture the write's log position and wait for the replica to reach it. PostgreSQL supports the second precisely — the client can capture pg_current_wal_insert_lsn() after the commit and the replica can check pg_last_wal_replay_lsn() — and SQL Server 2019+ has an equivalent via sys.fn_hadr_.../commit LSN tracking, or you simply set a stickiness window. Beyond that: expose replica reads as a deliberate API choice (this endpoint tolerates N seconds of staleness), alert on replication lag as a first-class SLO, and never send transactional writes through the read path. Also worth naming: on PostgreSQL, long read queries on a hot standby can conflict with WAL replay, so you either cancel queries (default) or turn on hot_standby_feedback and accept bloat on the primary.

Example

-- PostgreSQL: has the replica caught up to my write?
-- on the primary, right after COMMIT:
SELECT pg_current_wal_insert_lsn();              -- e.g. 3/AB12C4F8
-- on the replica, before serving the read:
SELECT pg_last_wal_replay_lsn() >= '3/AB12C4F8'::pg_lsn;

Follow-ups

  • What lag is acceptable? — Whatever the product agrees to; the point is that it is written down and monitored, not that it is small.
  • Can you write to a replica? — Physical standbys are read-only; a logical subscriber is writable, which makes conflicts your problem.
  • Connection routing? — Read-only routing on an AG listener (ApplicationIntent=ReadOnly), or a proxy/pooler for PostgreSQL; keep it in infrastructure, not in scattered connection strings.

Wrong answer: “Point all SELECTs at the replica and all writes at the primary.” It breaks read-your-writes on the very next page load, and the resulting bug reports are intermittent and nearly impossible to reproduce.

Someone ran a DELETE without a WHERE clause 20 minutes ago. Walk me through the recovery.principal

First, stop the bleeding and preserve options: confirm the scope (which table, how many rows, is the transaction still open — if it is, do not kill it, roll it back deliberately), and stop any process that would overwrite the evidence or truncate the log/WAL. Then restore to a point in time, but not over production: restore a copy to a scratch instance at a timestamp just before the statement, verify the row counts, and copy the missing rows back — a full production restore is the last resort because it discards the 20 minutes of legitimate work that followed. In SQL Server that is a full + differential + log restore with STOPAT; in PostgreSQL a base backup plus WAL replay with recovery_target_time, which pgBackRest or Barman automates. If you happen to have a delayed replica (PostgreSQL recovery_min_apply_delay) you may be able to read the pre-delete state directly, which is exactly why some teams run one. Then the incident work: how did a human have unrestricted DML on production, and where was the guard — a read-only default role, a review requirement for data fixes, a mandatory transaction-with-explicit-commit habit, or a proxy that refuses unqualified DML.

Example

# PostgreSQL: restore a copy to just before the statement
restore_command = 'pgbackrest --stanza=app archive-get %f "%p"'
recovery_target_time = '2026-09-08 14:30:55+02'
recovery_target_action = 'promote'

Follow-ups

  • Can you undo it from the log? — Third-party log readers exist for SQL Server and pg_waldump can show you what happened, but neither is a supported undo; restore-and-copy is the reliable path.
  • What if the table was truncated? — Same answer; TRUNCATE is minimally logged but still recoverable via point-in-time restore.
  • What prevents a recurrence? — Least privilege by default, a change process for data fixes, and safeguards in the tooling; blaming the human is not a control.

Wrong answer: “Restore last night's backup over production.” It converts a 20-minute problem into a full day of lost transactions, and it is the reflex that turns a recoverable incident into a business event.

How do you plan capacity and growth for a database that doubles yearly?principal

I would separate the three things that actually break at different times, because “the database is getting big” is not one problem. Working set versus memory is usually first: performance degrades sharply when the hot data no longer fits in the buffer pool / shared buffers plus OS cache, and that inflection is predictable from the cache hit rate trend. Maintenance windows break next: backup, restore, index rebuild, vacuum and statistics jobs all scale with size, and the RTO quietly grows past its SLO — which is why measured restore time is a capacity metric. Write throughput and log/WAL break last but hardest. The structural answers, in order of how far they take you: archival and retention (most tables have a long tail nobody queries), partitioning so maintenance and deletion become metadata operations, separating analytical load onto replicas or columnstore, and only then sharding. I would present it as a roadmap with trigger points — “at 60% of memory for the working set we start partitioning; at a measured restore time of 4 hours we split” — because that turns an argument about opinions into a monitoring rule.

Example

-- PostgreSQL: is the working set still cached?
SELECT sum(heap_blks_hit) / NULLIF(sum(heap_blks_hit + heap_blks_read), 0) AS hit_ratio
FROM pg_statio_user_tables;
-- SQL Server: Page life expectancy and buffer pool size trend, per NUMA node
SELECT object_name, counter_name, cntr_value FROM sys.dm_os_performance_counters
WHERE counter_name IN ('Page life expectancy', 'Buffer cache hit ratio');

Follow-ups

  • When do you shard? — When a single node cannot hold the working set or absorb the write rate, and after retention, partitioning and read offloading are exhausted — it is the change that costs the most engineering forever.
  • What does retention actually buy? — Smaller indexes, faster maintenance, cheaper backups and a smaller blast radius; it is the highest-leverage and least glamorous lever.
  • Cloud elasticity? — It buys time, not architecture; vertical scaling ends, and the bill grows faster than the data.

Wrong answer: “We will scale up the instance when it gets slow.” It works twice and then stops, and by the time it stops you have no runway to do the structural work — which is precisely what the question is testing.

13Connections, pooling & the ORM boundary

The unit where database and application engineering meet, and where full-stack interviews spend real time. Expect: why connections are expensive, what a pooler does, and how ORM defaults produce the queries you spend the rest of the interview tuning. Senior answers connect a database symptom (idle connections, plan cache bloat, N+1) to the application code that caused it.

Why is a database connection expensive, and what does a connection pool actually do?mid

A connection costs a TCP handshake, TLS negotiation, authentication and server-side session setup — but the durable cost is memory and scheduling. PostgreSQL forks a full OS process per connection, so each idle connection consumes memory and adds to the work of taking snapshots and scanning the process array; a few hundred connections is a lot and a few thousand is a problem. SQL Server uses threads with a shared pool and tolerates more connections, but each still holds memory and a scheduler slot. A pool keeps a small set of established connections and hands them out for the duration of a request, so the per-request cost is a checkout instead of a handshake — and, just as importantly, it caps concurrency, which is what protects the database from a traffic spike. Sizing is the interesting part: the right pool is small (roughly a low multiple of the CPU cores, not one per application thread), because more concurrent queries than the machine can execute just adds context switching and lock contention.

Example

# PgBouncer: many app connections, few server connections
[databases]
app = host=primary dbname=app
[pgbouncer]
pool_mode = transaction        # session | transaction | statement
default_pool_size = 20         # server-side connections per user/db
max_client_conn = 5000

Follow-ups

  • Which pool mode? — Transaction pooling gives the big win but breaks session state: SET, advisory locks, LISTEN, temp tables and (historically) prepared statements do not survive between transactions.
  • Why is a bigger pool not better? — Past the point where the database is saturated, queueing in the pool is cheaper than thrashing inside the engine; the classic guidance is a pool in the tens, not the hundreds.
  • What about serverless / lambda? — Function-per-request architectures multiply connections; a pooler in front (PgBouncer, RDS Proxy, Azure SQL's built-in pooling) is effectively mandatory.

Wrong answer: “Set the pool to 500 so we never wait for a connection.” You move the queue from the pool into the database, where it becomes lock contention and memory pressure — and the failure is much harder to see.

What is the N+1 query problem and how do you find it?mid

One query fetches N parents, then the code touches a lazily-loaded navigation property per parent, producing N more queries — so a page that looks like “one list” issues 201 round trips. Each is individually fast, which is why it never shows up in slow-query logs; the cost is latency × N and connection occupancy. You find it by counting queries per request, not by looking at query duration: an application-side counter or an APM trace per HTTP request is the reliable detector, and on the database side you see a suspiciously high execution count for a trivial query in pg_stat_statements or Query Store. The fixes are eager loading (Include in EF Core, joinedload/selectinload in SQLAlchemy), a projection that fetches exactly what the view needs, or batching the ids into one query with WHERE id = ANY(...)/a table-valued parameter. The senior nuance: eager loading everything is the opposite mistake — a single query with five Includes produces a Cartesian explosion, which is why EF Core added split queries.

Example

// N+1: one query for orders, then one per order for lines
var orders = db.Orders.Where(o => o.CustomerId == id).ToList();
foreach (var o in orders) Console.WriteLine(o.Lines.Count);   // lazy load per order

// fixed, and split so the join does not fan out
var orders = db.Orders.Where(o => o.CustomerId == id)
    .Include(o => o.Lines)
    .AsSplitQuery()
    .ToList();

Follow-ups

  • Why is AsSplitQuery not the default? — Multiple round trips lose transactional consistency between the parts unless you are in an explicit transaction; it is a trade, which is why EF Core makes you choose.
  • How do you prevent it systemically? — Disable lazy loading, add a per-request query-count assertion in integration tests, and fail CI over a threshold.
  • What is the database-side symptom? — A very high calls count with a tiny mean_exec_time in pg_stat_statements; total time dominated by a “fast” query.

Wrong answer: “It is fine because each query is 1 ms and the ORM caches.” 200 × 1 ms plus round-trip latency is a slow page, and first-level caching does not help across requests — this is the single most common performance defect in ORM-based applications.

When do you drop out of the ORM and write SQL?senior

When the query is the product rather than plumbing. Concretely: set-based bulk operations (an ORM that loads 100k entities to update them is doing the wrong thing — ExecuteUpdate/ExecuteDelete in EF Core 7+ exist for this), reporting and analytics with window functions and CTEs, anything needing engine-specific features (FOR UPDATE SKIP LOCKED, ON CONFLICT, MERGE, full-text or vector search, recursive CTEs, hints), and any query whose plan you need to control. Conversely I keep the ORM for CRUD, for change tracking, for mapping, and for the 90% of queries where the generated SQL is fine — abandoning it wholesale means reimplementing identity maps and unit-of-work by hand. The governance answer that plays well at lead level: hand-written SQL lives in a reviewed, named location (a query class, a repository, a .sql file), always parameterized, with a test that asserts its shape — not scattered as string literals through controllers.

Example

// EF Core 7+: one UPDATE statement, no entities loaded
await db.Orders.Where(o => o.Status == "pending" && o.CreatedAt < cutoff)
               .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, "expired"));

// engine-specific SQL, parameterized, in one reviewed place
var rows = await db.Database.SqlQuery<JobDto>(
    $"SELECT id, payload FROM job WHERE status = 'pending' ORDER BY created_at " +
    $"FOR UPDATE SKIP LOCKED LIMIT {batch}").ToListAsync();

Follow-ups

  • How do you keep raw SQL safe? — Parameters only, never string concatenation; EF Core's FromSql interpolation parameterizes, FromSqlRaw with concatenation does not.
  • Stored procedures instead? — A legitimate choice when the DBA team owns query performance, at the cost of versioning SQL outside the application's deployment unit.
  • How do you keep the two in sync? — Integration tests against a real database (Testcontainers) so a schema change breaks the hand-written SQL in CI, not in production.

Wrong answer: “Never use raw SQL, the ORM can express everything.” It cannot express SKIP LOCKED, window frames, or a plan-stable rewrite — and forcing a LINQ expression to emit a specific plan is far harder to review than the SQL it replaces.

How do you prevent SQL injection, and where does it still appear in 2026?senior

Parameterized statements, always — the parameter value never becomes part of the parsed statement, so no escaping is needed and none can be forgotten. That is the whole defence; input validation and escaping functions are secondary. Where it still appears: dynamic SQL that must interpolate identifiers (table or column names, an ORDER BY built from a query string) because those cannot be parameterized — the answer there is an allowlist mapped to literal identifiers, or the engine's quoting function (QUOTENAME() in T-SQL, format('%I', ...) in PostgreSQL). It also appears in dynamic SQL inside stored procedures (a procedure is not automatically safe; sp_executesql with parameters is, string concatenation is not), in reporting tools and admin panels that build filters, and in ORM escape hatches such as FromSqlRaw with a concatenated string. Defence in depth: the application's database role should not be able to read tables it does not need or execute DDL, so an injection is a bounded incident rather than a total one.

Example

-- T-SQL: parameterized dynamic SQL, identifier quoted from an allowlist
DECLARE @sql nvarchar(max) = N'SELECT id, name FROM dbo.' + QUOTENAME(@tableFromAllowlist)
      + N' WHERE tenant_id = @tenant AND name LIKE @pattern';
EXEC sys.sp_executesql @sql, N'@tenant int, @pattern nvarchar(100)', @tenant, @pattern;

-- PL/pgSQL equivalent
EXECUTE format('SELECT id, name FROM %I WHERE tenant_id = $1', v_table) USING v_tenant;

Follow-ups

  • Is an ORM automatically safe? — Its normal API is; raw-SQL escape hatches and string-built predicates are not.
  • Second-order injection? — Stored data that is later concatenated into SQL; the fix is the same, parameterize at every use, not sanitize at input.
  • How do you detect it? — Static analysis for string concatenation into query APIs, plus a review rule; and least privilege so the blast radius is small when one slips through.

Wrong answer: “We escape single quotes and strip keywords like DROP.” Blocklists are bypassable in a dozen documented ways, and escaping by hand fails on encodings and numeric contexts — this answer is why the vulnerability is still in the OWASP Top 10.

Retries, timeouts and idempotency: what does a database client need to be resilient?principal

Four things, and they have to be designed together. Timeouts at every layer, set shorter as you go up: a statement timeout in the database bounds the damage of a bad plan, a command timeout in the client, and an overall request budget — with the database timeout lower than the client's so the engine, not the network, cancels the work. Retries only for genuinely transient failures — deadlock victim (1205 / 40P01), serialization failure (40001), connection reset during a failover, Azure SQL's 40613/40501 — with exponential backoff and jitter and a hard cap, never for a constraint violation or a syntax error. Idempotency, because a retry after a timeout may be re-running a statement that actually committed: an idempotency key with a unique constraint is the standard answer, and it is the piece most people omit. Circuit breaking, so a database that is down does not receive a retry storm from every instance at once — which is how a 30-second failover becomes a 20-minute outage.

Example

// EF Core / SqlClient: transient-only retries with a bounded strategy
services.AddDbContext<AppDb>(o => o.UseSqlServer(cs, sql => {
    sql.EnableRetryOnFailure(maxRetryCount: 5, TimeSpan.FromSeconds(10), null);
    sql.CommandTimeout(15);
}));
// and the idempotency key that makes a retry safe
// UNIQUE (tenant_id, idempotency_key) on the payments table

Follow-ups

  • Why must the database timeout be shorter? — Otherwise the client gives up while the query keeps running, holding locks nobody is waiting for any more.
  • Retrying inside a transaction? — You cannot: after a failure the transaction is aborted, so the retry must restart the whole unit of work, which is why the work must be idempotent and side-effect free until commit.
  • How do you test this? — Fault injection: kill the primary during a load test and assert error rates and duplicate rates, rather than assuming the library handles it.

Wrong answer: “Set a long timeout and retry everything three times.” Long timeouts hold locks and connections during an incident, and retrying non-idempotent writes creates duplicate orders — a data-integrity bug produced by a resilience feature.

Docs: SqlClient connection pooling · PostgreSQL — Connection settings

14Observability, waits & incident command

Asked in platform, SRE and lead loops, and increasingly in ordinary senior loops because on-call is part of the job. The core skill is wait-based analysis — the database tells you what it is waiting on, and reading that beats guessing from CPU graphs. Principal-level answers add what you monitor before the incident and how you make the knowledge repeatable for the team.

What do you monitor on a production database, and what pages someone?senior

I separate symptoms (page) from causes (dashboard). Paging signals are user-visible or unrecoverable: error rate and p95 latency on the application's database calls, connection pool saturation, replication lag beyond the agreed SLO, disk free on the data and log/WAL volumes, backup failure, and — PostgreSQL-specific — transaction-id age approaching wraparound and an inactive replication slot retaining WAL. Diagnostic signals fill the dashboard: wait profile over time, top queries by total time (Query Store, pg_stat_statements), cache hit rate / page life expectancy, deadlock rate, blocking chain duration, checkpoint and autovacuum activity, and index usage trends. Two principles I would state: every alert names the runbook step it implies, or it gets deleted; and the numbers must be diffable across a deploy, which means retaining query-level telemetry long enough to compare last week with today.

Example

-- PostgreSQL: the two numbers most worth an alert
SELECT datname, age(datfrozenxid) AS xid_age FROM pg_database ORDER BY 2 DESC LIMIT 5;
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_retained
FROM pg_replication_slots;

Follow-ups

  • Why not alert on CPU? — It is neither necessary nor sufficient; a database can be pinned at 30% CPU and completely stalled on locks.
  • What is the single best leading indicator? — Query-level total time by query id: it catches plan regressions and new N+1s before users complain.
  • Cardinality of metrics? — Aggregate by normalized query id, not by literal SQL text, or your metrics store dies before the database does.

Wrong answer: “We monitor CPU, memory and disk — the standard three.” Those are host metrics; they tell you nothing about lock waits, plan regressions or replication, which is where database incidents actually come from.

Explain wait-based analysis. Which waits matter and what do they mean?senior

The idea is simple: a session is either running or waiting, so if latency is up and CPU is not, the database can tell you exactly what it waited on. SQL Server aggregates this in sys.dm_os_wait_stats (cumulative — take deltas) and live in sys.dm_exec_requests. The ones worth memorizing: PAGEIOLATCH_* = reading data pages from storage (I/O or not enough memory), WRITELOG = log flush latency (storage, or too many small transactions), LCK_M_* = blocking, RESOURCE_SEMAPHORE = queries queuing for memory grants, SOS_SCHEDULER_YIELD = CPU pressure, ASYNC_NETWORK_IO = the client is not consuming the result set fast enough (almost always an application problem, not a network one), THREADPOOL = worker starvation, usually caused by blocking. PostgreSQL exposes the same idea per-session in pg_stat_activity.wait_event_type/wait_event (LWLock, Lock, IO, Client, IPC), and the pg_wait_sampling extension aggregates it over time. The method: take a delta over the incident window, rank, and let the top wait choose your next query.

Example

-- SQL Server: current wait profile, benign waits excluded
SELECT TOP 10 wait_type, wait_time_ms/1000.0 AS wait_s, waiting_tasks_count
FROM sys.dm_os_wait_stats
WHERE wait_type NOT IN ('CLR_SEMAPHORE','SLEEP_TASK','BROKER_TASK_STOP','XE_TIMER_EVENT',
      'SQLTRACE_INCREMENTAL_FLUSH_SLEEP','LAZYWRITER_SLEEP','WAITFOR','DIRTY_PAGE_POLL')
ORDER BY wait_time_ms DESC;

Follow-ups

  • Why take deltas? — The DMV is cumulative since startup; the absolute numbers are dominated by weeks of idle waits.
  • Is ASYNC_NETWORK_IO the network? — Almost never: it means the client is fetching rows slowly (row-by-row processing, a huge result set, a debugger paused).
  • PostgreSQL sampling? — pg_stat_activity is a point-in-time snapshot; sample it every second or use pg_wait_sampling to get a profile rather than a photograph.

Wrong answer: “High CXPACKET means parallelism is hurting us, so lower MAXDOP.” A large part of it is benign coordination (split into CXCONSUMER since 2017); acting on the label instead of the skew is the classic wait-stats misread.

How do you find the query that is causing the problem right now?mid

Two views: what is running, and what has been expensive. Running: sys.dm_exec_requests joined to sys.dm_exec_sql_text and sys.dm_exec_query_plan in SQL Server; pg_stat_activity filtered to active states in PostgreSQL, ordered by how long the query has been running. Cumulative: Query Store or sys.dm_exec_query_stats for SQL Server, pg_stat_statements for PostgreSQL, ordered by total time rather than mean — because the query that is killing you is often a 3 ms query executed 200,000 times, not a 4-second one executed twice. That ordering choice is the tell of someone who has done this. For a query that will never finish, SQL Server can show its live plan with actual row counts via sys.dm_exec_query_statistics_xml, and PostgreSQL's auto_explain can log the plan of anything over a duration threshold.

Example

-- PostgreSQL: what is expensive overall, not just what is slow once
SELECT calls, round(total_exec_time)::bigint AS total_ms,
       round(mean_exec_time, 2) AS mean_ms, rows, left(query, 90) AS query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 15;

-- and what is running right now
SELECT pid, now() - query_start AS run_time, wait_event_type, wait_event, left(query, 90)
FROM pg_stat_activity WHERE state = 'active' ORDER BY run_time DESC;

Follow-ups

  • Why total time, not mean? — Aggregate load is what saturates the server; a fast query at huge volume beats a slow one at low volume every time.
  • What if pg_stat_statements is not installed? — Install it (it is in contrib and cheap); until then, log_min_duration_statement plus log analysis is the fallback.
  • How do you correlate with the application? — Tag queries with a comment carrying the endpoint/trace id (sqlcommenter style); it survives into pg_stat_activity and the logs.

Wrong answer: “Sort by average duration and fix the slowest query.” The slowest query is often a nightly report nobody is waiting for, while the actual incident is a trivial query running 5,000 times a second.

How do you trace a slow request from the application down to the query?senior

By propagating identity into the database, so the two sides can be joined. In practice: the application sets an application name and, per query, adds a structured comment carrying trace id, endpoint and controller (the sqlcommenter convention, supported by EF Core interceptors, Npgsql, Hibernate and others); those comments appear in pg_stat_activity, in the PostgreSQL log and in Query Store's query text, so a trace id in the APM leads directly to the statement, its plan and its waits. On the OpenTelemetry side, the database client emits spans with db.statement and db.system attributes, so the request waterfall shows exactly how much time is database time and how many round trips there were — which is also how N+1 becomes visible. Two practical cautions: never put user data in the comment (it lands in logs), and normalize query text for metrics so the cardinality stays sane.

Example

-- what the database sees, and can be joined back to a trace
SELECT * FROM "order" WHERE tenant_id = $1
/*traceparent='00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01',
  controller='OrdersController',action='List'*/

Follow-ups

  • Does the comment change the plan? — In PostgreSQL the comment is part of the query text, so it can defeat pg_stat_statements grouping unless you normalize; SQL Server's plan cache likewise treats different text as different queries.
  • How do you measure “database time” per endpoint? — Sum the client spans per request; if it is 80% of latency the problem is here, if it is 5% it is not.
  • Round trips? — Count spans per request; that number, not duration, is what catches chatty ORM code.

Wrong answer: “We log slow queries in the database and slow requests in the app, then match by timestamp.” That works until there is concurrency — which is exactly when you need it.

How do you build a team's database on-call capability?principal

Three artefacts and one habit. The artefacts: a runbook per alert that states the first three queries to run and the decision the responder has to make (never a wall of prose); a saved query pack — blocking chain, wait profile, top queries by total time, replication lag, oldest transaction — so nobody writes diagnostic SQL under pressure; and a known-safe mitigation list with the authority to use it (kill a blocking root, force a previous plan, pause a batch job, scale a pool) so responders are not waiting for permission at 3am. The habit is practice: game days where we induce a failover, a lock storm, a full log volume on a staging clone, and rotate who leads. I would also set the cultural expectation that the database is not one person's domain — the fastest way to a fragile system is a single DBA-shaped bottleneck — and that every incident produces one systemic fix (an alert, a timeout, a CI check), not just a resolution note.

Example

-- runbook step 1 for "api latency high, cpu normal" (PostgreSQL)
SELECT pid, state, now() - xact_start AS xact_age, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocked_by, left(query, 80)
FROM pg_stat_activity
WHERE state <> 'idle' ORDER BY xact_age DESC NULLS LAST LIMIT 20;
-- decision: if blocked_by is non-empty, follow to the root; if the root is
-- 'idle in transaction', terminate it and open a bug against the owning service.

Follow-ups

  • How do you avoid runbook rot? — Every incident review touches the runbook it used; an untouched runbook after three incidents is a signal it is not being read.
  • Who owns the database in a product team model? — The owning team, with a platform group providing tooling, defaults and review — not a gatekeeper.
  • How do you measure readiness? — Time-to-first-useful-query during game days, and how many responders can run the pack unaided.

Wrong answer: “We escalate to the DBA.” It is not a capability, it is a dependency — and at principal level the question is explicitly about removing it.

15Partitioning & very large tables

Comes up whenever the conversation reaches scale, and it is a favourite trap: candidates recommend partitioning as a performance feature when it is primarily a manageability feature. Expect to be asked what partitioning actually buys, how you choose the key, and when you would shard instead. Depth expected: senior should design a rolling-window scheme; principal should be able to say no.

What does partitioning actually buy you, and what does it not?senior

It buys manageability: dropping or switching out an old partition is a metadata operation instead of a massive DELETE, maintenance (vacuum, index rebuild, statistics) works partition by partition, and backups or storage tiers can be aligned to partitions. It can buy performance through partition elimination — if the query filters on the partition key, the planner skips the rest — and in SQL Server through partition-level lock escalation. It does not make an arbitrary query faster: a query that does not filter on the partition key now touches N indexes instead of one, and a poorly chosen key makes things worse. It also does not replace an index: within a partition you still need the right index. And it adds real constraints — in PostgreSQL, unique constraints must include the partition key, which frequently forces a schema change, and older versions had significant planning overhead with many partitions (much improved from PG 12 onward, with runtime pruning and partitionwise joins).

Example

-- PostgreSQL declarative partitioning, monthly range
CREATE TABLE event (id bigint, tenant_id int, created_at timestamptz NOT NULL, payload jsonb)
PARTITION BY RANGE (created_at);
CREATE TABLE event_2026_09 PARTITION OF event
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
-- retention becomes instant:
DROP TABLE event_2025_09;                     -- or DETACH PARTITION CONCURRENTLY

Follow-ups

  • How many partitions is too many? — Thousands are workable in modern PostgreSQL but planning cost and catalog size grow; a few hundred is a comfortable target.
  • SQL Server differences? — Partition functions and schemes, SWITCH for instant archival (same filegroup, identical structure required), and partition-level LOCK_ESCALATION.
  • Partitionwise joins? — PostgreSQL can join partition-to-partition when both sides share the partition key and enable_partitionwise_join is on — a real win in a data-warehouse-ish schema.

Wrong answer: “The table is big and slow, so partition it.” Without a filter on the partition key nothing gets eliminated, and you have added complexity, more indexes and a constraint on uniqueness for no gain.

How do you choose the partition key, and how do you run a rolling window?senior

The key is whatever appears in the retention rule and in the dominant query filter — usually a timestamp, occasionally a tenant id for isolation. A rolling window then has three moving parts: create future partitions ahead of time (automation, not a human; a missed partition means inserts fail or land in the default partition), attach/detach at the edges, and archive or drop the oldest. In PostgreSQL, DETACH PARTITION CONCURRENTLY (PG 14+) avoids the long exclusive lock, and a DEFAULT partition is a safety net that you should monitor rather than rely on — attaching a new partition when the default already holds matching rows requires scanning it. In SQL Server the same pattern uses SWITCH PARTITION to move data into a staging table instantly, then a MERGE RANGE/SPLIT RANGE on the partition function; the requirement that the staging table match structure and filegroup exactly is the classic operational trip-up. Either way it is scheduled automation with monitoring, because the failure mode is silent until an insert fails at midnight.

Example

-- SQL Server: instant archival of the oldest month
ALTER TABLE dbo.event SWITCH PARTITION 1 TO dbo.event_archive_202509 PARTITION 1;
ALTER PARTITION FUNCTION pf_event() MERGE RANGE ('2025-09-01');
-- and add the next window ahead of time
ALTER PARTITION SCHEME ps_event NEXT USED [FG_2026_11];
ALTER PARTITION FUNCTION pf_event() SPLIT RANGE ('2026-11-01');

Follow-ups

  • What if a partition is missing? — PostgreSQL raises “no partition of relation found for row” unless a default exists; SQL Server routes to the boundary partition, which quietly makes it huge.
  • Indexes on partitioned tables? — PostgreSQL creates a partitioned index that propagates to children; a unique index must include the partition key.
  • Can you partition an existing table in place? — PostgreSQL: not directly, you create the partitioned table and migrate (or use ATTACH of the old table as one partition). SQL Server: rebuild the clustered index onto the partition scheme.

Wrong answer: “We create partitions on demand when the insert fails.” That is an outage as a scheduling mechanism; partition creation belongs in automation running weeks ahead with its own alert.

Partitioning vs sharding: when do you cross that line?principal

Partitioning splits a table within one database; sharding splits data across independent databases, and the difference is that sharding gives you more machines and takes away cross-shard transactions, joins and unique constraints. I cross the line only when a single node is genuinely the limit — the working set no longer fits in memory, or the write rate saturates the log device — and after the cheaper levers are exhausted: retention, partitioning, read replicas for read scaling, and moving analytical load off the OLTP store. When I do shard, the decisions I would name are the shard key (usually tenant, because it makes almost every query single-shard), how rebalancing works (consistent hashing or a lookup/directory table — the directory is more operationally flexible), how cross-shard queries and reporting are served (usually a downstream warehouse, not scatter-gather), and how transactions spanning shards are avoided by design. And I would say the honest thing: sharding is a permanent tax on every future feature, so the last thing to try, not the first.

Example

-- directory-based sharding: the lookup that keeps rebalancing possible
CREATE TABLE shard_map (
  tenant_id bigint PRIMARY KEY,
  shard     text   NOT NULL,          -- 'db-eu-3'
  state     text   NOT NULL DEFAULT 'active'  -- active | migrating | readonly
);
-- moving a tenant: set 'migrating', copy, verify, flip, delete source

Follow-ups

  • Hash or directory? — Hash is simple and rebalances badly; a directory adds a lookup and makes moving a single tenant a routine operation. For multi-tenant systems, directory usually wins.
  • Managed options? — Citus for PostgreSQL distributes tables across nodes; Azure SQL elastic pools and sharding libraries do similar work — worth naming so you are not proposing to build it from scratch.
  • How do you keep the option open before sharding? — Make tenant id part of every key and every query now; retrofitting it later is the expensive part.

Wrong answer: “We should shard from day one so we never have to migrate.” You pay full complexity immediately for a scale you may never reach, and you lose transactions and joins for the entire life of the product.

How do you archive old data without a maintenance window?senior

If the table is partitioned on the archival key, the answer is a metadata operation: detach or switch out the partition, then move the detached table wherever it belongs — instant and lock-light. If it is not partitioned, it is a throttled batch copy-then-delete: copy a bounded range into the archive table, verify the copy, delete the same range, commit, sleep, repeat, with the same adaptive throttle as any backfill (replication lag, lock waits, log/WAL rate). Two details that matter: the delete must be driven by an indexed predicate on the same key ranges (never a full scan per batch), and in PostgreSQL the deleted space is not returned to the OS, so a large archival campaign should be followed by pg_repack if you actually need the disk back. The strategic answer is to make this unnecessary — partition new tables by time from the start, and treat retention as a property of the schema rather than a project.

Example

-- PostgreSQL 14+: detach without holding an exclusive lock on the parent
ALTER TABLE event DETACH PARTITION event_2025_09 CONCURRENTLY;
-- now it is an ordinary table: move, compress, export to object storage, or drop

Follow-ups

  • Where does archived data live? — A separate table, database or object storage (Parquet in a lake), depending on how it will be queried; “archive” without a read path is just deletion with extra steps.
  • Foreign keys to archived rows? — They block the move; either archive the whole object graph together or design the FKs to stop at the archival boundary.
  • Legal retention? — Retention rules cut both ways: some data must be deleted by a deadline and some must be kept — encode both as automation with an audit trail.

Wrong answer: “DELETE FROM t WHERE created_at < '2024-01-01' during the quiet period.” One statement, tens of millions of rows: lock escalation, log growth, replica lag and an uninterruptible rollback — the incident this whole unit exists to prevent.

When is a columnstore index (or a separate analytical store) the right answer?senior

When the workload is aggregation over many rows and few columns, and the data is append-mostly. SQL Server's columnstore stores data column-by-column in compressed segments with min/max metadata, so a SUM over a billion-row fact table reads only the needed columns and skips whole segments — routinely 10× compression and 10–100× on scan-heavy aggregation, executed in batch mode. It is the wrong choice for point lookups and frequent single-row updates, which land in the delta store and degrade compression, so the standard shape is a clustered columnstore for the fact table plus nonclustered rowstore indexes for the few seek paths, or a real-time operational analytics setup (a nonclustered columnstore on an OLTP table). PostgreSQL has no native columnstore in core: the options are BRIN indexes for time-ordered scans, extensions (Citus columnar, Hydra, TimescaleDB's compression), or the increasingly common answer of exporting to a lakehouse/warehouse and querying there. That last option is often the honest recommendation, and saying so scores better than pretending PostgreSQL is a warehouse.

Example

-- SQL Server: analytics on the OLTP table without a second system
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_order
  ON dbo.[order] (tenant_id, placed_at, total, status)
  WHERE status = 'paid';        -- filtered NCCI keeps the hot rows out of it

Follow-ups

  • What is the delta store? — A rowstore staging area for small inserts; the tuple mover compresses rowgroups at 1,048,576 rows, so trickle inserts leave you with poorly compressed data until reorganized.
  • Segment elimination? — Works on min/max per segment, so data loaded in key order eliminates far better than randomly ordered loads — ordered columnstore indexes (improved in SQL Server 2025) target this.
  • Why not just a warehouse? — Latency and cost: real-time operational analytics on the OLTP store avoids an ETL hop, which for dashboards over recent data is often the better trade.

Wrong answer: “Add a columnstore index to speed up our OLTP queries.” Point lookups and single-row updates are its worst case; applied to a transactional table without an analytical workload it costs write throughput and buys nothing.

16Security, least privilege & encryption

Asked in most senior loops and every regulated-industry loop. The screener is injection (covered in unit 13); the substance here is authentication, authorization models, encryption at rest and in transit, and what you actually do about secrets and auditing. Principal-level answers connect controls to threat models rather than listing features.

How do you design database permissions for an application?senior

Least privilege with roles, never per-user grants, and never the application connecting as an owner or superuser. The shape I use: a role that owns the schema and objects (used only by migrations), and a separate application role with exactly SELECT/INSERT/UPDATE/DELETE on the tables it needs and EXECUTE on the functions it calls — no DDL, no access to other schemas. In PostgreSQL that means being explicit about default privileges (ALTER DEFAULT PRIVILEGES) so new tables inherit the grants, and — important since PG 15 — knowing that CREATE on the public schema is no longer granted to everyone by default. In SQL Server it means database roles plus schema-level grants, contained users where possible, and avoiding db_owner for the app. Separate roles for read-only reporting and for the migration pipeline; secrets from a managed identity or a vault rather than a connection string in config; and an actual review of who has production access, because that list is always longer than anyone expects.

Example

-- PostgreSQL: app role that cannot change the schema
CREATE ROLE app_rw LOGIN PASSWORD NULL;             -- auth via IAM/cert
GRANT USAGE ON SCHEMA app TO app_rw;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO app_rw;
ALTER DEFAULT PRIVILEGES IN SCHEMA app
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

Follow-ups

  • Why separate the migration role? — So a compromised application cannot alter or drop the schema, and so DDL is auditable to one identity.
  • Row-level security? — PostgreSQL RLS and SQL Server's row-level security add per-tenant/per-user filtering in the engine; defence in depth behind the application's own checks.
  • Passwordless? — Managed identity (SQL Server 2025 supports Arc-enabled managed identity for inbound and outbound connections) or IAM auth in cloud PostgreSQL removes the stored secret entirely.

Wrong answer: “The app uses one account with full rights; the application layer enforces permissions.” It means any injection, any bug and any leaked connection string is a total compromise — and it is exactly the finding auditors look for.

Encryption at rest and in transit: what do TDE, Always Encrypted and pgcrypto each protect against?senior

Be precise about the threat model, because that is what is being tested. Transparent Data Encryption (SQL Server; and disk/volume encryption for PostgreSQL, which has no native TDE in core) encrypts the data files and backups, so it protects against stolen media and leaked backup files — it does not protect against anyone who can query the database, because the engine decrypts transparently. TLS in transit protects the wire; SQL Server 2025 adds TLS 1.3 with TDS 8.0 across the stack, and PostgreSQL should be configured with ssl = on and clients with sslmode=verify-full — the mode matters, since require does not verify the certificate and therefore does not stop a man in the middle. Always Encrypted (SQL Server) is the different one: encryption happens in the client driver with keys the server never sees, so a DBA or a compromised server cannot read the values — at the cost of losing most query capabilities (equality only, via deterministic encryption; ranges need the enclave-based version). PostgreSQL's pgcrypto gives column encryption but the key usually passes through the server, so it protects backups more than it protects against a compromised server.

Example

-- PostgreSQL: require a verified server certificate, not just "encrypted"
-- connection string: sslmode=verify-full sslrootcert=/etc/ssl/ca.pem
SHOW ssl;

-- SQL Server: TDE, protecting files and backups
CREATE DATABASE ENCRYPTION KEY WITH ALGORITHM = AES_256
  ENCRYPTION BY SERVER CERTIFICATE TDECert;
ALTER DATABASE app SET ENCRYPTION ON;

Follow-ups

  • Does TDE satisfy “encrypt PII”? — Only against the media threat; a regulator asking about insider access wants column-level encryption or tokenization.
  • Key management? — External key managers (Azure Key Vault / EKM, KMS) so keys are not in the same blast radius as the data; rotation must be exercised, not just documented.
  • Performance cost? — TDE is a few percent CPU; Always Encrypted's cost is functional (no range queries, no indexes on randomized columns), which is usually the deciding factor.

Wrong answer: “We have TDE, so the data is encrypted and we are compliant.” TDE is invisible to anyone with query access, which is most attack paths — presenting it as blanket protection is the answer that fails a security-minded interviewer.

How do you handle PII: masking, tokenization, and the right to erasure?senior

Start with classification — you cannot protect what is not inventoried — then choose per field. Dynamic data masking (SQL Server, and view-based masking in PostgreSQL or the anon extension) hides values from unprivileged readers at query time; it is a convenience control, not a security boundary, since a determined user can often infer values through predicates. Tokenization or encryption replaces the value so the database never holds the plaintext — the real control for card numbers and national ids. For non-production environments the answer is anonymized restores: a scrubbing pipeline that runs as part of the restore, not a promise that nobody queries production. For erasure, the practical pattern is crypto-shredding — encrypt each subject's sensitive fields with a per-subject key and destroy the key — because chasing every copy through backups, replicas, logs and warehouses is not achievable. And name the parts people forget: backups, read replicas, search indexes, event streams and application logs all hold the data too.

Example

-- SQL Server: masked to unprivileged readers (a convenience, not a boundary)
ALTER TABLE dbo.customer ALTER COLUMN email
  ADD MASKED WITH (FUNCTION = 'email()');
GRANT UNMASK TO support_lead;

-- PostgreSQL: a masked view for the support role
CREATE VIEW support.customer AS
SELECT id, left(email, 1) || '***@' || split_part(email, '@', 2) AS email FROM app.customer;

Follow-ups

  • Why is masking not a boundary? — WHERE email LIKE 'a%' still filters on the real value, so the data can be extracted one predicate at a time.
  • Auditing? — SQL Server Audit and PostgreSQL's pgaudit record who read what; required in regulated environments and useful evidence in an incident.
  • Test data? — Generated or scrubbed, never a production restore with “we trust the team”; the restore itself is the disclosure.

Wrong answer: “We delete the row when a user asks to be forgotten.” The data still exists in backups, replicas, logs and the warehouse; a plan that does not address those is not an erasure capability.

What is your policy on production database access for engineers?principal

Default read-only, time-bound, audited, and through a path that leaves a record. Concretely: no standing write access; elevation is requested, justified and expires (just-in-time access), ideally via a break-glass role that alerts when used; all access is through an identity provider so it is attributable to a person rather than a shared account; and every query is logged. Data fixes are code — a reviewed migration or a script in version control, applied by the pipeline — not a human typing an UPDATE against production. To make that policy livable rather than theatre, you have to invest in the alternatives: good observability so people rarely need to log in, a safe read replica for investigation, and a fast path for legitimate data fixes so the process is not the reason someone bypasses it. The framing I would use with a team: the goal is not distrust, it is that a mistake at 3am should require two people and leave a trail.

Example

-- PostgreSQL: a genuinely read-only investigation role
CREATE ROLE oncall_ro NOLOGIN;
GRANT USAGE ON SCHEMA app TO oncall_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA app TO oncall_ro;
ALTER ROLE oncall_ro SET default_transaction_read_only = on;
ALTER ROLE oncall_ro SET statement_timeout = '30s';
-- humans get oncall_ro by default; write access is a separate, expiring grant

Follow-ups

  • What about emergencies? — Break-glass exists, alerts loudly, and the use is reviewed afterwards — never removed, because a policy with no escape hatch gets bypassed permanently.
  • Shared accounts? — Never for humans; they destroy attribution, which is the entire point of the audit trail.
  • How do you enforce it? — Access through a bastion/proxy that logs statements, plus periodic access reviews; the review is what catches the grant everyone forgot.

Wrong answer: “Senior engineers need full access to be effective.” It confuses capability with standing privilege; just-in-time elevation gives the same capability with attribution and a time bound.

What are the modern authentication options, and what would you deprecate?senior

Move away from passwords stored in connection strings. SQL Server: Windows/Entra ID (formerly Azure AD) authentication, and for on-prem SQL Server 2025 the notable addition is managed identity via Azure Arc, usable for both inbound connections and outbound calls to Azure resources — plus PBKDF2 password hashing now on by default for application roles. PostgreSQL: scram-sha-256 is the correct password method (MD5 is deprecated in PG 18 — CREATE ROLE/ALTER ROLE now emit a deprecation warning, and removal is planned), certificate authentication for service-to-service, and PostgreSQL 18's new OAuth 2.0 authentication method in pg_hba.conf, which lets a cluster validate bearer tokens from an external identity provider — the first native path to token-based auth without a proxy. Cloud-managed instances add IAM authentication that mints short-lived tokens. What I would deprecate everywhere: shared service accounts, MD5 authentication, trust in any non-local context, and any connection string with a literal password when a managed identity is available.

Example

# PostgreSQL 18: OAuth-based authentication in pg_hba.conf
hostssl app app_rw 10.0.0.0/8 oauth issuer="https://idp.example.com" scope="pg.app"
# and the safe password fallback
hostssl all all 0.0.0.0/0 scram-sha-256

Follow-ups

  • Why is MD5 deprecated? — The scheme is weak and the stored verifier is directly usable; SCRAM adds channel binding and does not expose an equivalent.
  • Token expiry with pooling? — Short-lived tokens interact badly with long-lived pooled connections; the pool must refresh credentials on reconnect, which is a real integration detail.
  • Certificate auth? — Good for service-to-service, but rotation is the hard part; automate it or it becomes an outage on expiry day.

Wrong answer: “SQL authentication with a strong password is fine.” It is a long-lived secret that lives in configuration, gets copied into laptops and CI logs, and cannot be revoked per-session — which is why every platform is moving to tokens and identities.

17JSON, search & vector workloads

Rarely the core of an interview, but increasingly a differentiator — especially the AI-adjacent part, where “can we do vector search in our existing database?” is a live architectural question in 2026. Treat this unit as breadth: know what each engine offers natively, what it costs, and when a dedicated system is the honest answer.

How do you query and index JSON in each engine?mid

PostgreSQL: jsonb is the type to use (binary, indexable), with the containment operator @>, path extraction (->, ->>, #>), SQL/JSON path expressions (jsonb_path_query, @?, @@) and, since PG 17, the standard JSON_TABLE for turning JSON into rows. Indexing: a GIN index (jsonb_path_ops for containment-only, smaller and faster) covers arbitrary containment queries, and a plain B-tree on an extracted expression covers one hot path. SQL Server historically stored JSON in nvarchar(max) with JSON_VALUE/OPENJSON/ISJSON and required a persisted computed column plus an index to make a path searchable; SQL Server 2025 changes that with a native binary json data type, JSON indexes, and aggregate functions JSON_OBJECTAGG/JSON_ARRAYAGG. The judgment part is unchanged in both: JSON is for genuinely variable structure, and anything you filter, join or constrain on should be promoted to a column.

Example

-- PostgreSQL: containment, index-supported
SELECT id FROM doc WHERE body @> '{"state":"open","priority":1}';
CREATE INDEX ON doc USING gin (body jsonb_path_ops);

-- SQL Server 2025: native type
SELECT id FROM dbo.doc WHERE JSON_VALUE(body, '$.state') = 'open';
CREATE JSON INDEX IX_doc_body ON dbo.doc (body) FOR ('$.state');

Follow-ups

  • Why are estimates bad on JSON predicates? — There are no per-path statistics; the planner uses fixed selectivity guesses, so a hot path deserves a generated column with real statistics.
  • Validation? — A CHECK with a JSON schema function or a constrained set of keys; without it the “flexible” column becomes undocumented and unqueryable.
  • Update cost? — Updating one key rewrites the whole value (and re-TOASTs it in PostgreSQL); frequently-updated fields belong in columns.

Wrong answer: “We store everything as JSON so the schema is flexible.” You have moved the schema into application code where nothing enforces it, and made every filter a full scan unless someone remembers to index the path.

How do you implement full-text search without adding Elasticsearch?senior

Both engines have capable built-in search. PostgreSQL: tsvector/tsquery with a GIN index, a language configuration for stemming and stop words, ts_rank for relevance and ts_headline for snippets; store the tsvector as a generated column so it stays current. For fuzzy or typo-tolerant matching, pg_trgm with a GIN/GiST index gives similarity search and also makes LIKE '%foo%' indexable — often the actual requirement behind “we need search”. SQL Server: full-text indexes with CONTAINS/FREETEXT and semantic search, plus 2025's regex and fuzzy-matching functions (REGEXP_LIKE, EDIT_DISTANCE, JARO_WINKLER_SIMILARITY) for the lighter cases. When would I still add a dedicated engine? When search is the product: complex relevance tuning, faceting, synonyms and multilingual analysis at scale, or when search traffic would otherwise compete with transactional load. Naming that boundary is the point of the question.

Example

-- PostgreSQL 12+: generated tsvector, always in sync
ALTER TABLE article ADD COLUMN search tsvector
  GENERATED ALWAYS AS (to_tsvector('english', coalesce(title,'') || ' ' || coalesce(body,''))) STORED;
CREATE INDEX ON article USING gin (search);

SELECT id, ts_rank(search, q) AS rank
FROM article, websearch_to_tsquery('english', 'postgres "index only" -mysql') q
WHERE search @@ q ORDER BY rank DESC LIMIT 20;

Follow-ups

  • Why websearch_to_tsquery? — It parses user-style queries (quotes, or, -) without throwing syntax errors at your users, unlike to_tsquery.
  • Index write cost? — GIN inserts are expensive; fastupdate batches them into a pending list, which then needs vacuum to flush.
  • Ranking beyond ts_rank? — Combine it with business signals (recency, popularity) in the ORDER BY; pure lexical rank rarely matches user expectations.

Wrong answer: “Use LIKE '%term%'; it is simpler.” It cannot use a normal index, has no stemming, ranking or phrase handling, and turns into a full scan on every keystroke of a type-ahead.

Can you do vector search in SQL Server or PostgreSQL, and would you?senior

Yes, and in 2026 it is a reasonable default for small and medium corpora. PostgreSQL uses the pgvector extension: a vector column type, distance operators (<-> L2, <=> cosine, <#> inner product) and approximate indexes — IVFFlat (fast to build, needs training data and a tuned list count) and HNSW (better recall/latency, slower and more memory-hungry to build). SQL Server 2025 brings this into the engine: a native vector data type (1–1998 dimensions, single- or half-precision), vector functions (VECTOR_DISTANCE, VECTOR_NORM, VECTOR_NORMALIZE), CREATE VECTOR INDEX and VECTOR_SEARCH for approximate nearest-neighbour, plus CREATE EXTERNAL MODEL and AI_GENERATE_EMBEDDINGS/AI_GENERATE_CHUNKS so embeddings can be produced from T-SQL — note that the index and search parts require the PREVIEW_FEATURES database-scoped configuration. Would I? For up to a few million vectors, yes — one system, transactional consistency between the row and its embedding, and filters combined with the search in the same query. Beyond that, or when the index must be rebuilt constantly, a dedicated vector database earns its keep.

Example

-- PostgreSQL + pgvector: filtered ANN search
CREATE TABLE chunk (id bigserial PRIMARY KEY, tenant_id int, body text, embedding vector(1536));
CREATE INDEX ON chunk USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);

SELECT id, body, embedding <=> $1 AS distance
FROM chunk WHERE tenant_id = $2 ORDER BY embedding <=> $1 LIMIT 10;

Follow-ups

  • What breaks with a filter? — Pre-filtering can defeat the ANN index and post-filtering can return too few rows; partial indexes per tenant or a higher ef_search are the usual mitigations.
  • Recall vs latency? — ANN is approximate by definition: ef_search/probe counts trade recall for speed, and the right value is measured against a labelled set, not guessed.
  • Storage? — 1536 float32 dimensions is ~6 kB per row before the index; a few million rows is tens of gigabytes, which is a capacity conversation.

Wrong answer: “Vector search in a relational database is a toy; you need a dedicated vector database.” That was defensible in 2023; with pgvector's HNSW and SQL Server 2025's native vector type it is out of date, and the transactional-consistency argument now runs the other way.

The database is being used as a message bus / cache / file store. What do you say?principal

I would judge each on its merits rather than reciting purity. A queue in the database is legitimate and often correct up to meaningful volume, because it gives transactional enqueue with the business data (see unit 04) — the caution is churn and vacuum/fragmentation, and the exit criteria are throughput and retention. A cache in the database is usually a mistake: you get none of the eviction, expiry or memory efficiency of a real cache, and you add write load to the most contended resource you own. Files are the clearest case: large blobs bloat backups, restore time and the buffer pool, so the default is object storage with a row holding the key, metadata and a checksum — SQL Server's FILESTREAM/FileTable exist for the cases where transactional consistency with the file genuinely matters, and PostgreSQL large objects have their own vacuum and permissions quirks. The general principle I would offer the team: keeping something in the database buys transactional consistency and one system to operate, and costs blast radius, backup size and the ability to scale that workload independently — decide with those three, not with a slogan.

Example

-- the boring, correct blob pattern
CREATE TABLE attachment (
  id           bigserial PRIMARY KEY,
  order_id     bigint NOT NULL REFERENCES "order"(id),
  storage_key  text   NOT NULL UNIQUE,      -- s3://bucket/tenant/uuid
  content_type text   NOT NULL,
  bytes        bigint NOT NULL,
  sha256       bytea  NOT NULL,
  uploaded_at  timestamptz NOT NULL DEFAULT now());

Follow-ups

  • What breaks first with blobs in the database? — Backup and restore time, which quietly moves your RTO past its SLO long before query performance suffers.
  • How do you keep object storage and rows consistent? — Write the object first, then the row (orphan objects are cheap to garbage-collect); the reverse leaves rows pointing at nothing.
  • When is a database cache defensible? — A small, rarely-changing lookup that must be transactionally consistent with the data — and even then, name it a table, not a cache.

Wrong answer: “The database is not a queue / not a file store, full stop.” It is dogma without numbers; a database-backed queue is the right answer for a large fraction of systems, and a principal engineer is expected to say when, not just no.

Which PostgreSQL extensions would you consider standard, and what is the SQL Server equivalent thinking?senior

My default set: pg_stat_statements (non-negotiable — you cannot tune what you cannot see), auto_explain for plans of slow statements, pg_trgm for fuzzy and LIKE-indexable search, btree_gist/btree_gin for exclusion constraints and mixed indexes, pgcrypto where needed, amcheck for index verification, and pgvector when embeddings are in scope. Beyond core: pg_repack for online bloat removal, pgaudit for regulated environments, PostGIS for anything spatial, TimescaleDB or Citus when the shape genuinely calls for time-series or distribution. The governance point matters as much as the list: every extension is a dependency on upgrade day, so I check that the managed platform supports it (cloud providers allow a fixed set) and that it is actively maintained. SQL Server has no extension model — the equivalent decisions are which engine features to enable (Query Store, ADR, optimized locking, columnstore) and which are gated behind edition or, in 2025, behind the PREVIEW_FEATURES database-scoped configuration, which is a compatibility decision of the same kind.

Example

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS amcheck;
-- auto_explain must be preloaded
ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements,auto_explain';
ALTER SYSTEM SET auto_explain.log_min_duration = '3s';
ALTER SYSTEM SET auto_explain.log_analyze = on;

Follow-ups

  • Cost of pg_stat_statements? — Small and bounded (a shared memory hash of normalized queries); the visibility is worth it in every environment.
  • Extension risk on upgrade? — A major upgrade needs matching extension builds; an unmaintained extension can pin your whole cluster to an old version.
  • Managed cloud? — The allowed extension list is a real constraint on architecture; check it before designing around one.

Wrong answer: “Install whatever extension solves the problem; that is the point of PostgreSQL.” Each one is an operational and upgrade dependency, and the team that installs freely discovers on upgrade day that one of them has no build for the new major version.

Rarely a whole round, but it appears as “what is new in the version you use” or “how do you decide when to upgrade”, and it is a cheap way for an interviewer to check whether you keep current. Have two or three concrete recent facts ready per engine — with version numbers and dates — and a defensible upgrade policy.

What is current in each engine as of today, and what changed recently?mid

SQL Server 2025 (17.x) reached general availability on 18 November 2025 (build 17.0.1000.7), with cumulative update 8 (17.0.4075.5) released on 13 August 2026. Its headline themes are AI in the engine (native vector type, vector indexes, VECTOR_SEARCH, external models and AI_GENERATE_EMBEDDINGS), developer surface (native binary json type, regular-expression functions, fuzzy string matching, || string concatenation, CURRENT_DATE, PRODUCT(), change event streaming), and engine work (optimized locking, tempdb space resource governance, ADR in tempdb, ZSTD backup compression, optional parameter plan optimization, DOP feedback on by default). Editions changed too: Web edition is discontinued, Express now allows 50 GB databases, and Standard gained Resource Governor. PostgreSQL 18 was released on 25 September 2025; the current minor is 18.6 (13 August 2026 — note 18.5 was not shipped due to a regression), and PostgreSQL 19 is in beta (beta 3 on 13 August 2026) with general availability expected around the end of September 2026. PG 18's highlights: asynchronous I/O (up to ~3× faster sequential scans), uuidv7(), virtual generated columns by default, B-tree skip scan, temporal constraints with WITHOUT OVERLAPS, OAuth 2.0 authentication, RETURNING OLD/NEW, data checksums enabled by default at initdb, and pg_upgrade preserving optimizer statistics.

Example

-- PostgreSQL 18: RETURNING can now name both versions of the row
UPDATE "order" SET status = 'paid'
WHERE id = $1
RETURNING id, old.status AS was, new.status AS now;

-- SQL Server 2025: ANSI concatenation and a real CURRENT_DATE
SELECT first_name || ' ' || last_name AS full_name, CURRENT_DATE AS today FROM dbo.customer;

Follow-ups

  • What is newly on by default? — PostgreSQL 18: data checksums at initdb, and generated columns are virtual unless declared STORED. SQL Server 2025: DOP feedback and Query Store on readable secondaries.
  • What is newly deprecated? — PostgreSQL 18 deprecates MD5 password authentication (warnings on CREATE/ALTER ROLE); SQL Server 2025 discontinues Data Quality Services, Master Data Services, Synapse Link and Web edition, and deprecates hot-add CPU and lightweight pooling.
  • What is still preview in SQL Server 2025? — Vector indexes and VECTOR_SEARCH, change event streaming, fuzzy-match functions — all gated behind the PREVIEW_FEATURES database-scoped configuration, so they are not yet production commitments.

Wrong answer: naming a version without a date, or describing a preview feature as generally available. Interviewers checking currency will follow up on exactly that, and “SQL Server 2025 has vector search” without “behind PREVIEW_FEATURES” is the answer that unravels.

How do you decide when to upgrade a major version?senior

Two forcing functions and one opportunity. The forcing functions are support lifecycle — PostgreSQL supports a major version for five years after release, so PG 13 went end-of-life in November 2025 and each November another one follows; SQL Server has 5 years mainstream plus 5 years extended — and any security fix that only lands in a supported version. The opportunity is a feature that removes real work: PG 18's async I/O and statistics-preserving pg_upgrade, or SQL Server 2025's optimized locking, are worth planning around. My policy is to stay within one major version of current and never to run an unsupported one; to upgrade on a schedule rather than in a crisis; and to decouple risk — upgrade the binaries first and change the plan-affecting behaviour (compatibility level, or a post-upgrade ANALYZE plus plan review) as a separate step. The method matters as much as the timing: PostgreSQL upgrades via pg_upgrade (with PG 18's --swap mode for the fastest path) or via logical replication for near-zero downtime; SQL Server via an in-place upgrade or, safer, a new instance plus an availability-group failover.

Example

# PostgreSQL 18: fastest in-place path, statistics preserved
pg_upgrade -b /usr/lib/postgresql/17/bin -B /usr/lib/postgresql/18/bin \
           -d /var/lib/postgresql/17/main -D /var/lib/postgresql/18/main \
           --swap --jobs 8
# (before 18 you also had to run ANALYZE across the cluster immediately afterwards)

Follow-ups

  • How do you test? — Restore production into a staging clone, replay a captured workload, and diff query-level telemetry between versions; that is the evidence, not the release notes.
  • Rollback plan? — A major upgrade is one-way; the rollback is a restore or a failback to a still-running old primary, which is why logical replication upgrades are attractive.
  • Extension and driver compatibility? — Check both before scheduling; an extension without a build for the new major is a hard blocker.

Wrong answer: “We upgrade when we need a new feature.” That guarantees you eventually run an unsupported version, and the upgrade then happens under emergency conditions with several majors to cross at once.

Managed cloud database or self-hosted — how do you choose?senior

Managed services (Azure SQL Database / Managed Instance, RDS and Aurora, Cloud SQL, Azure Database for PostgreSQL) take over patching, backups, HA and failover, which for most teams is a clear win: those are exactly the tasks that get deprioritized until they cause an incident. The trade-offs to name are concrete, not philosophical — no superuser or sysadmin, so certain extensions, trace flags and filesystem-level tools are unavailable; upgrade timing partly controlled by the provider; behaviour differences from the on-prem product (Azure SQL Database has RCSI on by default and no cross-database queries, Aurora replaces the storage engine entirely and changes replication and vacuum characteristics); and cost that scales with I/O in ways that reward good indexing far more than self-hosting does. I self-host when there is a hard requirement the platform cannot meet: a specific extension, data residency in a location without a region, an unusual hardware profile, or a cost profile at large scale where the managed premium exceeds the salary cost of running it well.

Example

-- portability check: are you relying on something the platform will not give you?
SELECT name, setting FROM pg_settings
WHERE name IN ('shared_preload_libraries', 'max_connections', 'wal_level');
SELECT extname FROM pg_extension;   -- compare against the provider's allowed list

Follow-ups

  • What surprises people about Aurora? — The custom storage layer changes replication, backup and failover behaviour; PostgreSQL knowledge transfers, but operational assumptions do not always.
  • Azure SQL Database vs Managed Instance? — Database is the PaaS with the biggest behaviour delta; Managed Instance is much closer to the box product (SQL Agent, cross-database queries, CLR).
  • Lock-in? — Manage it by staying on standard SQL and portable extensions where you can, and by keeping an exported-backup restore path tested.

Wrong answer: “Managed is always better, you get HA and backups for free.” They are configured, not free — untested restores and unmonitored replication lag fail the same way on a managed service, and the loss of superuser is a genuine constraint you must check against your design.

A team wants to move from SQL Server to PostgreSQL. What is your advice?principal

First, establish the reason, because it determines whether the project is worth it: licence cost and cloud portability are legitimate drivers; “PostgreSQL is more modern” is not. Then scope honestly — the schema and simple queries port easily, and the work is concentrated in five places: T-SQL procedural code (T-SQL to PL/pgSQL is a rewrite, not a translation), identity and error-handling semantics, the concurrency model (SQL Server's lock-based READ COMMITTED versus MVCC changes behaviour under load, and code that relied on readers blocking may now race), collation and case sensitivity (a case-insensitive SQL Server default becomes case-sensitive PostgreSQL, which surfaces as duplicate users and failed lookups), and everything around the database — SQL Agent jobs, SSIS packages, SSRS reports, backup tooling, monitoring, and the team's operational knowledge, which is often the largest cost. My recommended shape is incremental: port the schema, run both in parallel with logical replication or CDC, migrate read traffic first, then writes by bounded slice, with a tested rollback at each step — and a pilot on one real service before committing the organization. Tools (AWS SCT/DMS, Babelfish for a T-SQL-compatible surface, ora2pg-style converters) reduce the mechanical work but not the semantic risk.

Example

-- a semantic difference that bites on day one
-- SQL Server (default CI collation): these are the same row
SELECT * FROM dbo.[user] WHERE email = 'Bob@Example.com';   -- matches bob@example.com
-- PostgreSQL: case-sensitive; you need an explicit index and predicate
CREATE UNIQUE INDEX ON "user" (lower(email));
SELECT * FROM "user" WHERE lower(email) = lower($1);

Follow-ups

  • What is Babelfish? — A TDS/T-SQL compatibility layer for PostgreSQL (Aurora, and open source); it shortens the port but coverage is partial, so it is a bridge, not a destination.
  • What surprises teams most? — Operations, not SQL: vacuum, bloat, connection limits and the absence of Query Store are all new disciplines to learn.
  • How do you de-risk the decision? — Migrate one non-critical service end to end and measure the real effort; extrapolate from that, not from a vendor's assessment tool.

Wrong answer: “Run a schema conversion tool, fix the errors, and cut over on a weekend.” The tool handles syntax; the risks are semantic (isolation, collation, NULL and identity behaviour) and operational, and a big-bang cutover has no rollback once writes have landed on the new system.

19Judgment calls

Open-ended questions with no single right answer, used in lead and principal loops to see how you reason rather than what you recall. There is no “wrong answer” label here — the hidden part of each block says what a strong answer demonstrates and which trade-offs an interviewer expects you to name without being prompted. Answer all of them out loud before the interview; the failure mode is not being wrong, it is being vague.

SQL Server or PostgreSQL for a new greenfield system — how do you choose?principal

What a strong answer demonstrates: that the decision is mostly non-technical and you know it. The engines are close enough in capability that the deciding factors are the team's existing expertise, the surrounding stack (a .NET shop with Entra ID, SSRS and existing SQL Server licences has real gravity), licence and cloud cost at your expected scale, the hosting target and which managed offerings you can use, and the operational model you can staff. Then a few genuine technical discriminators: PostgreSQL's extension ecosystem (PostGIS, pgvector, TimescaleDB, Citus) and MVCC-by-default; SQL Server's Query Store, columnstore, In-Memory OLTP and the tooling depth around them.

Trade-offs to name unprompted

  • Licence cost versus operational cost — PostgreSQL is free to licence, not free to operate; SQL Server Standard's limits (memory cap, no online index rebuild) shape architecture more than people expect.
  • Team capability is the dominant risk: an unfamiliar engine means learning vacuum, bloat and connection limits during your first incident.
  • Hiring and community: which is easier to hire for in your market, and whose documentation and answers your team will actually find.
  • Exit cost: whichever you choose, migrating later is expensive, so state the reversibility honestly rather than pretending it is a small decision.
Business logic in the database (stored procedures, triggers) or in the application?principal

What a strong answer demonstrates: that you can argue both sides and then pick based on context. The case for the database: one enforcement point for all writers, dramatically less data movement for set-based work, and the ability to fix a query without an application deploy. The case against: SQL is harder to unit-test and refactor, version control and deployment are weaker, code review culture is thinner, and logic hidden in triggers is the classic source of “why did that column change?”. My usual position: constraints and integrity in the database always; set-based data processing in the database when moving the data would dominate; business rules and workflow in the application, where they are testable and observable. Triggers reserved for auditing and for maintaining derived data that must never drift.

Trade-offs to name unprompted

  • Testability and CI: database code needs the same pipeline as application code, or it becomes the untested part of the system.
  • Scaling: application tiers scale horizontally, the database usually does not — pushing logic down concentrates load on the scarcest resource.
  • Portability and hiring: heavy T-SQL or PL/pgSQL is a lock-in and a skills dependency.
  • Observability: a trigger's work is invisible to the application's tracing unless you deliberately instrument it.
When is “just add an index” the wrong answer?senior

What a strong answer demonstrates: that you think about the whole workload, not the one query in front of you. Wrong when the table is write-dominated and the read is rare; when the query is non-SARGable and the index cannot be used at all; when an existing index already covers the need with a different column order (consolidate instead); when the real problem is a bad estimate or an N+1 and the index just moves the symptom; when the query returns most of the table, so a scan is genuinely optimal; and when the query should not exist — a report against OLTP, an endpoint returning too much, an ORM fetching what it does not need.

Trade-offs to name unprompted

  • Every index is a permanent write tax, more log/WAL, more backup and more maintenance time.
  • Index count raises the optimizer's search space and can itself cause plan instability.
  • An index is easy to add and politically hard to remove; the count only ever grows without an ownership rule.
  • Sometimes the correct fix is deleting data (retention), which makes the index unnecessary.
How much consistency do you actually need — and where would you accept staleness?principal

What a strong answer demonstrates: that consistency is a per-use-case product decision with a number attached, not a global setting. You would work through the read paths and assign each one a staleness budget: a user's own data immediately after a write must be read-your-writes (route to the primary or wait for the LSN); a dashboard can be 30 seconds stale; a monthly report can be a day stale; a fraud check must be strongly consistent because the cost of being wrong is asymmetric. Then you would say what enforces each budget — replica routing rules, replication-lag alerts tied to the SLO, and cache TTLs — rather than leaving it as an aspiration.

Trade-offs to name unprompted

  • Synchronous replication costs latency on every write and couples primary availability to the standby.
  • Read replicas scale reads but introduce a class of bug that only appears under lag, which is hard to reproduce.
  • Caching moves an availability problem into an invalidation problem, and the invalidation is the hard part.
  • The budget must be observable: without a lag SLO and an alert, “eventually consistent” means “unbounded”.
You inherit a 5 TB database with 200 stored procedures, no tests and no documentation. What do you do first?principal

What a strong answer demonstrates: restraint and sequencing. First, safety: verify backups by actually restoring one, check the recovery model and log backup chain, confirm monitoring and alerting exist, and find out who has production access. Second, visibility: turn on Query Store or pg_stat_statements, capture a workload baseline, and inventory what is actually called — usually a small fraction of those 200 procedures carries all the traffic. Third, a risk register: unsupported version, missing indexes on foreign keys, untrusted constraints, single points of failure, the one procedure everybody is afraid of. Only then improvement, driven by the telemetry, with characterization tests written around whatever you touch first. What you do not do is start rewriting, or propose a migration, in month one.

Trade-offs to name unprompted

  • Stability versus velocity early on: you have no test net, so change slowly until you build one.
  • Documentation has a shelf life; telemetry does not — prefer instrumenting over documenting.
  • The 80/20 of usage means most of the system can be left alone indefinitely, and saying that out loud is a maturity signal.
  • Organizational risk: the person who knows the system is the real single point of failure, and that is addressed with pairing and runbooks, not with a rewrite.
When do you say no to a schema change a product team wants?principal

What a strong answer demonstrates: that “no” is a last resort and usually means “not like that”. The cases where I would hold the line: a change that cannot be rolled back and has no migration path; one that breaks N-1 compatibility during a rolling deploy; a destructive change without a verified backup and a tested restore; a change that makes a cross-team interface unstable without a deprecation window; and a design that encodes a temporary business rule into a structure that will be expensive to unwind. In almost every case the productive response is to offer the expand/contract version that gets them the same outcome safely, with the extra time cost stated explicitly so the trade-off is theirs to make.

Trade-offs to name unprompted

  • Delivery pressure is real: a “no” without an alternative gets routed around, and then you have neither safety nor influence.
  • Reversibility is the currency: prefer changes that can be undone with a deploy over ones that need a restore.
  • Technical debt is a legitimate choice when it is recorded, owned and has a repayment trigger.
  • Your credibility is finite — spend the veto on data loss and availability, not on modelling taste.
Is the relational database still the right default in 2026?principal

What a strong answer demonstrates: that you can defend the default without being dogmatic. Yes, for most systems: transactions, constraints, a mature optimizer, forty years of operational knowledge, and the fact that both engines have absorbed most of the reasons people left — JSON documents, full-text search, time-series patterns, geospatial, and now vector search. The honest exceptions are workloads whose shape genuinely differs: very high-volume append-only telemetry, graph traversal at depth, global multi-master writes with regional latency requirements, and analytical scans over petabytes, where a purpose-built store wins. The strongest version of the answer adds the operational argument: one well-understood database is usually better than three specialized ones that nobody is on call for.

Trade-offs to name unprompted

  • Polyglot persistence multiplies operational surface: backups, upgrades, monitoring and on-call for each store.
  • Consistency across stores becomes an application problem (outbox, sagas, reconciliation).
  • “PostgreSQL can do it” is not the same as “PostgreSQL should do it at your scale” — name the volume at which you would change your mind.
  • Vendor and cloud gravity: the default that fits the platform you already run is worth real points.
How do you handle a disagreement about a database design with a senior colleague?principal

What a strong answer demonstrates: that you convert opinion into evidence and keep the relationship intact. Start by making sure you can state their position better than they can — most database arguments are two people optimizing for different constraints (write latency versus read simplicity, delivery date versus operability). Then find the cheapest experiment: a benchmark on production-sized data, a prototype of both schemas, a prior incident that tests the claim. Agree in advance what result would change each of your minds, because a disagreement with no falsifiable outcome is a status contest. If it remains genuinely undecidable, pick the more reversible option, write down why, and set a review point. And be explicit about who decides — an unresolved technical disagreement that blocks delivery is a management problem you should escalate rather than litigate.

Trade-offs to name unprompted

  • Speed versus certainty: some decisions do not deserve a benchmark, and knowing which is the skill.
  • Reversibility beats correctness under uncertainty.
  • Team cost: winning an argument badly makes the next ten reviews worse.
  • Documented reasoning is what lets a future team revisit the decision instead of re-arguing it.
Should the team standardize on one ORM, one query style, one migration tool?senior

What a strong answer demonstrates: that you know where standardization pays and where it costs. Standardize hard on the things that create shared risk: migration tooling and process (one pipeline, one history), connection and pooling configuration, timeout and retry policy, observability conventions, and naming. Be looser about query style, because a reporting-heavy service legitimately writes different SQL from a CRUD service, and forcing one ORM across very different workloads produces workarounds. The framing that lands well: standardize the interfaces and the operational contract, not the craftsmanship — and make the standard easy to follow by shipping it as a template or a library rather than as a document.

Trade-offs to name unprompted

  • Standards have carrying cost: they need an owner and a way to change, or they become folklore people route around.
  • Diversity is a hiring and onboarding tax, but forced uniformity is an innovation tax.
  • Migration tooling is the one place where inconsistency is genuinely dangerous — two histories on one database is a corruption risk.
  • Enforce with automation (linters, templates, CI checks); a standard enforced by review is enforced unevenly.
Your database is at 80% CPU at peak and the business wants double the traffic in six months. What is the plan?principal

What a strong answer demonstrates: that you diagnose before you buy. First, find out what the CPU is doing: a handful of queries usually dominate, and the top-10-by-total-time list plus their plans typically contains a 30–50% win in a week — bad estimates, missing indexes, N+1s, a query going parallel when it should not. Then structural levers in ascending cost: caching what is genuinely cacheable, moving analytics to replicas or a columnstore, retention and archival to shrink the working set, partitioning, and connection-pool sizing so the database is not thrashing. Buying hardware is a legitimate parallel track that buys time, but it should be a deliberate purchase of runway, not the plan itself. Then a capacity model with trigger points and a load test that proves the target rather than assuming linearity — because contention rarely scales linearly.

Trade-offs to name unprompted

  • Query tuning has the best cost/benefit ratio but is bounded; architecture changes are unbounded but slow.
  • Scaling up ends: name the largest instance available and how much headroom it actually buys.
  • Caching and replicas introduce consistency work that must be budgeted, not assumed.
  • Doubling traffic does not double contention — locks, latches and hot rows can go superlinear, which is why the load test matters.

Three exercises where this topic meets system design. Attempt each one first: read the prompt, ask the clarifying questions out loud, sketch the schema and the access paths, and only then open the solution. The hidden part is a strong outline plus the trade-offs an interviewer expects you to raise without being asked — in these rounds, naming the trade-off scores higher than picking the “right” option.

Exercise 1 — Multi-tenant SaaS order management

Prompt: Design the database for a B2B order-management SaaS. 5,000 tenants, from 10-user shops to one enterprise with 40% of all data. Orders, order lines, products, customers, invoices. Requirements: sub-200 ms p95 for the order list and order detail screens, a nightly per-tenant revenue report, full audit of who changed what, and a contractual promise that one tenant's data can be exported and deleted on request. Which engine you choose is up to you; justify it.

Clarifying questions to ask: What is the read/write ratio and the absolute peak write rate? What is the retention requirement, and can old orders be archived? Is the report allowed to be stale, and by how much? Do tenants share a region or is data residency per tenant? What is the RPO/RTO? Does “audit” mean row history, or an event log of user actions? Is there any cross-tenant functionality (marketplace, benchmarking) that would break strict isolation?

Show a strong solution outlineprincipal

Shape. Shared schema with tenant_id as the leading column of every primary key and every index, plus row-level security as a second line of defence — with the largest tenant moved to its own database once it crosses the agreed threshold, which is why the code must treat “which database” as a lookup from day one. Surrogate bigint keys (or uuidv7 if ids must be client-generated), natural keys as separate unique constraints scoped by tenant. Order lines snapshot price and product name so history is immutable. Money as numeric(19,4) with an explicit currency column; timestamps as timestamptz/datetimeoffset in UTC.

Access paths. Order list: index on (tenant_id, placed_at DESC) INCLUDE (status, total, customer_id) so the list screen is covered; keyset pagination, never OFFSET. Order detail: PK seek plus a seek on (tenant_id, order_id) for lines. Search by customer: (tenant_id, customer_id, placed_at DESC). The whale tenant gets its own filtered/partial index and filtered statistics so its plans are not the small tenants' plans.

Reporting. Not against the OLTP tables: a materialized view or summary table refreshed nightly (PostgreSQL REFRESH MATERIALIZED VIEW CONCURRENTLY, or an indexed view / columnstore in SQL Server), or a read replica, with the staleness budget written into the requirement.

Audit. Two different things, decided separately: an append-only audit_event table for user actions (who, what, when, before/after as JSON), partitioned monthly with a retention rule; and row history where it is legally required — SQL Server temporal tables, or triggers/PG 18 temporal constraints in PostgreSQL.

Export and delete. Every table carries tenant_id, so export is a scripted set of range queries and delete is a scripted set of range deletes in dependency order — batched, throttled, and covering replicas, backups (via a documented retention window) and the warehouse. If per-subject erasure is in scope, encrypt sensitive fields per tenant so crypto-shredding is available.

Growth. Partition order and audit_event by month once retention is defined, so archival becomes a partition drop; measure restore time as the capacity metric that triggers splitting tenants out.

Trade-offs to name unprompted

  • Shared schema optimizes cost and migration effort but concentrates blast radius; RLS is defence in depth, not a substitute for correct queries.
  • The whale tenant will skew every plan — say this before the interviewer does, and name filtered statistics, per-tenant indexes and eventual isolation as the ladder.
  • Snapshotting prices denormalizes deliberately; the alternative (join to a temporal price table) is more correct and slower, and either is defensible if you say why.
  • Nightly reporting buys simplicity at the cost of freshness; if the business wants live numbers, that is a replica or a streaming rollup, with its own failure mode.
  • Per-tenant delete must include backups and derived stores, or the promise is not kept — most candidates forget everything downstream of the primary.

Exercise 2 — Event ingestion and time-series analytics

Prompt: Your product emits 50,000 events per second at peak (device telemetry: device id, timestamp, metric name, value, tags). Requirements: keep raw events for 30 days and hourly rollups for two years; dashboards query “last 24 hours for one device” and “p95 across a fleet for the last 7 days”; the team already runs PostgreSQL and would prefer not to add a new system. Design it, and tell me when you would add one anyway.

Clarifying questions to ask: Is ingest bursty or steady, and can it be buffered? Is exactly-once required or is at-least-once with idempotent writes acceptable? How many distinct devices and metrics (cardinality)? Are late-arriving events possible, and how late? What query latency do the dashboards need? Is data loss on a crash acceptable for raw events? What is the storage budget?

Show a strong solution outlineprincipal

Ingest. Buffer in a broker or in-process queue and write in batches — 50k rows/s as individual inserts is a losing shape; batched COPY (PostgreSQL) or bulk insert (SQL Server) of a few thousand rows per transaction is an order of magnitude cheaper. Relax durability deliberately for raw telemetry (synchronous_commit = off per transaction, or delayed durability), with the accepted loss window written into the SLO. Minimal indexing on the raw table: the primary access path is time plus device, and every extra index is a tax paid 50,000 times a second.

Storage. Declarative range partitioning by time — daily partitions for raw (30 kept, dropped on a schedule by automation that also creates future partitions ahead), monthly for rollups. Index the raw table on (device_id, ts) for the single-device query; add BRIN on ts for the fleet-wide scans, since the data is naturally time-ordered and BRIN is a few MB where a B-tree would be tens of GB. Tags in jsonb only if genuinely variable; otherwise columns, because filters on tags will be common.

Rollups. A scheduled job (or continuous aggregate if you adopt TimescaleDB) that computes hourly min/max/avg/count and a sketch for percentiles per device and metric, written to the rollup table and made idempotent by an upsert on (device_id, metric, hour) so re-runs and late data are safe. Dashboards query rollups by default and raw only inside the last hours.

Percentiles. Exact p95 across a fleet over 7 days from raw is a scan of billions of rows; use a mergeable sketch (t-digest or HLL-style, available as PostgreSQL extensions) stored per hour so fleet queries aggregate sketches instead of rows — and say plainly that this makes the answer approximate within a known error.

When to add a system. When ingest exceeds what one node's WAL can absorb, when retention or cardinality makes storage cost dominate, or when the analytical queries start to interfere with ingest — then TimescaleDB/Citus inside the PostgreSQL family, or ClickHouse-class storage outside it, is the honest recommendation.

Trade-offs to name unprompted

  • Relaxed durability buys throughput and costs a bounded loss window — acceptable for telemetry, unacceptable for billing events derived from it.
  • Rollups trade storage and freshness for query speed, and introduce a correctness question about late-arriving data that must have an explicit policy.
  • Sketches make percentiles cheap and approximate; if someone will make a contractual claim from that number, the approximation matters.
  • Partition automation is a new failure mode: a missed future partition is an ingest outage, so it needs its own alert.
  • Staying on PostgreSQL keeps one operational surface; the cost is that you will hand-build what a purpose-built store gives you, and you should name the volume at which that flips.

Exercise 3 — Payments ledger with strict correctness

Prompt: Design the data model and concurrency strategy for a double-entry ledger: accounts with balances, transfers between accounts, idempotent payment initiation from an API that may retry, and a hard requirement that balances never go negative and always reconcile. Peak of 2,000 transfers per second, with hot merchant accounts receiving thousands of credits per second. Auditors must be able to reconstruct any account's balance at any past point in time.

Clarifying questions to ask: Is the ledger single-currency or multi-currency? Must the balance be exact and immediately readable, or is a slightly stale displayed balance acceptable? Are transfers always between two accounts in this system, or do some legs go to external systems? What is the settlement model — can a transfer be pending? What are the regulatory retention and audit requirements? What is the acceptable failure behaviour if the database is degraded — reject, or queue?

Show a strong solution outlineprincipal

Model. Append-only ledger_entry (id, account_id, transfer_id, amount signed, currency, posted_at, sequence) as the source of truth — never an updatable balance as the primary record. A transfer row groups the two (or more) entries and carries the idempotency key; a CHECK or a deferred constraint asserts that the entries of a transfer sum to zero. Balances are a derived account_balance row updated in the same transaction as the entries (a materialized aggregate), reconcilable at any time by summing entries — that reconciliation job is a first-class, alerting piece of the system.

Idempotency. A unique constraint on (client_id, idempotency_key) on transfer. The API inserts the transfer first; a duplicate insert violates the constraint and the handler returns the original result instead of creating a second payment. This is what makes client retries and network timeouts safe, and it is the piece most candidates omit.

Concurrency. Pessimistic per-account locking in a canonical order (always lock the lower account id first) to make deadlocks structurally impossible; the negative-balance rule enforced by the database, not by a read-then-write in application code — a single conditional UPDATE ... WHERE balance >= amount plus a CHECK (balance >= 0), so a race cannot slip through. Retry on deadlock and serialization failure with jitter.

Hot accounts. A merchant account taking thousands of credits per second is a hot row: credits (which cannot make the balance negative) can be written as entries and aggregated asynchronously or into sharded sub-balances, while debits take the exact serialized path. That asymmetry — strict where the invariant lives, relaxed where it does not — is the key insight of the exercise.

History. The entry log already reconstructs any past balance by summing to a timestamp; add periodic balance snapshots per account so “balance as of” is a snapshot plus a short tail rather than a full scan. Partition entries by month for retention and for snapshot-aligned queries.

Cross-system legs. An outbox for events to downstream systems in the same transaction as the ledger write, with at-least-once delivery and idempotent consumers; never a distributed transaction with the payment processor.

Trade-offs to name unprompted

  • Serialization per account caps throughput per account, and that is a requirement, not a bug — you scale across accounts, not within one.
  • Materialized balances are denormalization for read speed; the price is a reconciliation job that must run and alert, or drift becomes invisible.
  • Asynchronous credit aggregation makes the displayed balance briefly stale — acceptable for merchants, unacceptable for a debit authorization, and the design must distinguish them.
  • Strict correctness argues against read replicas for any balance check; say where reads may be stale and where they may not.
  • Money must never be soft-deleted or updated in place; corrections are reversing entries, which auditors expect and which also keeps the log append-only.

21Night-before cheat sheet

The ten questions most likely to be asked in some form, with a one-sentence answer each. If you can say these cleanly and then go one level deeper on request, you will pass the screen and have room to think in the harder rounds.

  1. Clustered vs nonclustered index? — In SQL Server the clustered index is the table (leaf = rows, one per table) and nonclustered indexes carry the clustering key as their row locator; PostgreSQL has no clustered index at all, so every index is secondary over an unordered heap.
  2. What index for WHERE a = ? AND b > ? ORDER BY b? — Equality first, then range/sort: (a, b), with the returned columns as INCLUDE so the query is covered and there is no key lookup or heap fetch.
  3. Why is my index not used? — Usually a non-SARGable predicate (function or implicit conversion on the column), a query past its tipping point where a scan is genuinely cheaper, or a stale/wrong estimate — check the plan for Filter versus Index Cond, or CONVERT_IMPLICIT.
  4. Isolation levels? — READ UNCOMMITTED / READ COMMITTED / REPEATABLE READ / SERIALIZABLE prevent progressively more anomalies; SQL Server's default is lock-based READ COMMITTED (with RCSI as the versioning alternative), while PostgreSQL is MVCC always and its SERIALIZABLE aborts conflicting transactions with 40001 instead of blocking.
  5. Is WITH (NOLOCK) okay? — No: it is READ UNCOMMITTED, so besides dirty reads it can miss committed rows or return them twice during page splits — if the goal was to stop readers blocking writers, turn on RCSI instead.
  6. Deadlock vs blocking? — Blocking is a queue that resolves when the holder finishes; a deadlock is a cycle the engine breaks by killing a victim (1205 / 40P01), and the fix is consistent lock ordering, shorter transactions and better indexes, plus a retry loop.
  7. Why did the plan change overnight? — Statistics updated, data volume crossed a threshold, a parameter was sniffed differently on recompile, or a compatibility level / version changed — Query Store (SQL Server) or pg_stat_statements plus auto_explain (PostgreSQL) is how you prove which.
  8. What is parameter sniffing? — The plan is compiled for the first parameter values seen and then reused for all others, so skewed data gets a plan optimal for one tenant and catastrophic for another; fix with targeted RECOMPILE, OPTIMIZE FOR, Query Store hints, or PSPO/OPPO in newer SQL Server.
  9. What does VACUUM do and why does the table still grow? — It marks dead tuples reusable and maintains the visibility map and freeze horizon, but it does not return space to the OS (that needs VACUUM FULL or pg_repack), and it can remove nothing while a long-running transaction or an inactive replication slot holds the xmin horizon back.
  10. How do you delete 50 million rows safely? — In throttled, indexed batches with a commit per batch (or by dropping a partition if the table is partitioned on the key) — never one statement, which escalates locks, fills the log/WAL, lags replicas and rolls back for as long as it ran.
