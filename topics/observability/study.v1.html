Observability & prod debugging

01What observability actually is

The word is borrowed from control theory: Kálmán (1960) called a system observable when its internal state can be reconstructed from its external outputs. Ported to software, that gives you the only definition worth defending in an interview: a system is observable to the degree that you can answer new questions about its internal state, from the outside, without shipping new code. That framing is doing real work. It makes observability a property of the system plus its telemetry, not a product you buy. It makes "we have Grafana" irrelevant on its own. And it gives you a falsifiable test: take the last three incidents, write down the question you actually needed answered at minute five, and check whether today's telemetry answers it.

The useful contrast is monitoring. Monitoring answers known-unknowns: you predicted a failure mode, so you built a dashboard and an alert for it — disk fills, queue backs up, error rate rises. It is closed-ended and it is still essential; every alert you have is a monitoring artefact. Observability targets unknown-unknowns: the failure nobody predicted, where the question is "why are 0.3% of checkouts timing out, and what do those 0.3% have in common?" You cannot dashboard your way to that in advance, because the discriminating attribute — a specific tenant, a canary pod, a TLS version, a feature flag combination — was not a dimension anyone thought to add.

That difference reduces to two numbers, and lead candidates are expected to use them precisely. Cardinality is how many distinct values a field can take: http.response.status_code has maybe 15, user.id has millions. Dimensionality is how many fields you attach to each observation. Metrics are pre-aggregated at write time, so a high-cardinality attribute multiplies the number of stored time series and destroys them economically; per-request records (spans, wide events) store the attributes raw and aggregate at read time, so high cardinality is exactly what makes them useful. "Should this be a metric or a span attribute?" is really "do I need to slice by this later, and can the storage model afford it?"

The familiar "three pillars" (metrics, logs, traces) is a useful vocabulary and a bad architecture. Pillars are data types, not capabilities, and treating them as three separate products is how organisations end up with three bills, three query languages, and no way to get from a spiking latency graph to the twelve requests that caused it. The modern framing — pushed hardest by the "Observability 2.0" / wide events camp, and visible in Stripe's older "canonical log line" pattern — is that you emit one rich, high-cardinality event per unit of work and derive metrics, logs and traces from it. In 2026 the honest, interview-safe position is: the pillars are how the data is stored and billed; the wide event is how you should think about what to record; OpenTelemetry's resource-plus-attributes data model lets you have both, because the same attributes ride on spans, log records and now profiles.

Profiles are the reason the pillar count keeps moving. Traces tell you which service and which call was slow; profiles tell you which line of code burned the CPU or allocated the memory while that span was open. OpenTelemetry's Profiles signal entered public alpha in March 2026, with an eBPF whole-system profiler running as a Collector receiver and samples carrying trace_id / span_id so a slow span links straight to its flame graph. Calling profiles "the fourth signal" is now a statement of fact about the OTLP protocol, not a marketing line.

A running example

Keep one system in your head for the whole guide, and use it in interviews instead of speaking abstractly: a checkout flow. Browser → CDN → API gateway → checkout-api → synchronous call to an external payments provider → writes to orders-db (PostgreSQL, behind PgBouncer) → publishes order.placed to a queue → fulfilment-worker consumes it. Six hops, one external dependency, one datastore, one async boundary. Every concept below has a concrete home in it: the async boundary is where trace context propagation breaks, the external provider is where tail latency and timeouts live, the connection pool is where saturation hides, and the queue is where "the service is healthy but the customer is not" becomes true.

Interview trap

Two versions of the same mistake. The first is answering "what is observability?" with "metrics, logs and traces" — that is a list of file formats, and every interviewer has heard it. Say what the property is (answering unanticipated questions without a deploy), then use the pillars as implementation detail. The second is conflating volume with cardinality. A firehose of 10 million identical log lines is high volume and low cardinality; one metric with a user_id label is low volume and catastrophic cardinality — it can create millions of active series from a trickle of traffic. When someone says "our observability bill exploded", the first diagnostic question is which of the two happened, because the fixes are opposite: sampling and compression for volume, label removal and aggregation for cardinality.

Try it

1. Take your last three production incidents. For each, write the single question you needed answered at minute five ("which pods?", "which tenant?", "which version?"). Now try to answer each one against today's telemetry, timing yourself. 2. Pick a service and add deployment.environment.name, service.version and one business dimension (tenant, plan tier) as span attributes — not metric labels — then ask a question you have never asked before, e.g. "p99 latency for tenant X on version 1.42".

Expected outcome

The typical result of (1) is that one of three questions is answerable in seconds, one takes ten minutes of log grep, and one is unanswerable — which is precisely the gap to fix, and a great story to bring to an interview. In (2) you should find the query is instant and costs nothing extra, because the attribute lives on spans, not on a time series; if you had added the same dimension as a Prometheus label you would have multiplied your active series by the number of tenants. That asymmetry is the whole argument for high-cardinality, per-request telemetry.

Interview Q&A

What is the difference between monitoring and observability, in one minute?

Monitoring is asking questions you already knew to ask: you predicted a failure mode, so you built a signal and an alert for it. Observability is the property that lets you ask questions you did not anticipate, from outside the system, without deploying new code. In practice monitoring gives you detection — an SLO burn alert fires — and observability gives you the explanation, because you can slice per-request data by attributes you never dashboarded. They are complementary, not sequential: you still need a small set of high-quality alerts, and you need rich enough telemetry that the alert can be explained. The lead-level nuance is that observability is a property of the system's instrumentation, not of the vendor you bought, so it is something you design in, review in code review, and budget for.

Why do people say the "three pillars" model is wrong, and what do you actually believe?

The pillars describe three storage and billing models, not three capabilities, and taken literally they push you into three siloed tools with no path from a graph to an example. The critique — "Observability 2.0", wide events, canonical log lines — says you should record one rich event per unit of work with as many dimensions as you can afford, and derive dashboards from it at read time. My working position is that the pillars are real as a cost model and useless as a mental model: I design instrumentation around per-request events with high dimensionality, then aggregate down to metrics for alerting because metrics are cheap and predictable to alert on. What makes that practical today is OpenTelemetry's shared resource-and-attribute model, so the same semantic attributes appear on spans, logs and profiles and correlation is a join, not a heuristic. The trade-off to name out loud is that wide-event storage is more expensive per byte and less mature operationally than a Prometheus install.

Define cardinality and explain why it matters more than data volume.

Cardinality is the number of distinct values of a field, and for metrics the thing that actually matters is the product of cardinalities across all labels on a metric, because each unique label combination is a separate stored time series. Volume — bytes per second — is largely a compression and retention problem and scales gracefully; cardinality is a memory and index problem and scales cliff-like, because time-series databases keep an in-memory index of active series. A single unbounded label like customer ID or URL path with IDs in it can take a service from 5,000 series to 5 million and OOM the ingester, at unchanged traffic. That is why unbounded dimensions belong on spans and log records, where they are stored as attributes and aggregated at query time, and why OpenTelemetry ships a default per-metric cardinality limit of 2,000 with an otel.metric.overflow bucket as a safety net.

How do you decide whether a new dimension should be a metric label or a span attribute?

I ask two questions: is it bounded, and do I need to alert on it. If the value set is small, stable and something I want a threshold on — status code class, route template, region, cluster — it is a metric label. If it is unbounded or only interesting when explaining a specific case — user ID, order ID, tenant, SQL statement, feature-flag set — it goes on the span or log record where storage is per-event rather than per-combination. The middle case is a bounded-but-large dimension like tenant on a multi-tenant platform: there I usually keep it off the base metric, expose the top-N tenants via a recording rule or a separate purpose-built metric, and rely on traces for the long tail. Concretely, adding tenant to a metric with 500 tenants and 20 routes and 5 status classes is 50,000 series per instance, and you multiply that by replicas.

A team says "we have 200 dashboards, we're observable". What's your response?

Dashboards are frozen answers to questions someone asked in the past; 200 of them usually means nobody can find the right one during an incident, and that the real knowledge lives in three people's heads. I would run a simple audit: which dashboards were opened during the last ten incidents, and which question did each answer? In most estates 90% of the value sits in a handful of service-level views plus ad-hoc querying, and the rest is decoration that still costs query load and maintenance. The constructive move is to standardise a single generated per-service dashboard from a template — RED for request-driven services, USE for resources — delete or archive the rest, and invest the saved effort in exemplar links and trace search, because that is what actually answers novel questions.

What changed in observability in the last year that you'd bring up in a design review?

Three things. OpenTelemetry graduated CNCF on 21 May 2026, which matters practically because it removes the last "is this safe to standardise on?" objection and because vendors now compete on backend and analysis rather than on agents. Profiles reached public alpha in March 2026 as a first-class OTLP signal with eBPF collection and trace correlation, so continuous profiling is finally something you can plan into a platform instead of bolting on. And the Span Events API was deprecated in March 2026 in favour of emitting events through the Logs API correlated to the active span, which changes what I tell teams to write in new instrumentation, even though existing span events keep working.

How do you measure whether your observability investment is working?

I avoid vanity metrics like "GB ingested" and track outcomes: time to detect (alert fires before or after the first customer report), time to mitigate, and the proportion of incidents where the root cause was found from telemetry versus by guessing and redeploying. I also track alert precision — what fraction of pages were actionable — because alert fatigue silently destroys detection time. On the cost side I watch spend per service and per signal so that the platform team can push back with data rather than blanket retention cuts. A good target to state in an interview is directional: cut median time-to-mitigate, keep page precision above roughly 80%, and keep telemetry cost growing sublinearly with traffic.

What is the difference between an SLI, a signal and a metric?

A metric is a stored measurement, a signal is a category of telemetry (metric, log, trace, profile), and an SLI is a carefully chosen ratio of good events to valid events that represents user experience. The distinction matters because most metrics are not SLIs — CPU usage is a metric and a terrible SLI, since users do not experience CPU. An SLI has to be defined from the user's perspective at a boundary they cross: successful checkouts over attempted checkouts, requests served under 300 ms over requests served. Getting that boundary right is the single highest-leverage decision in the whole alerting stack, because everything downstream — error budget, burn-rate pages, prioritisation — inherits its definition.

Your telemetry bill doubled after a release. Walk me through the diagnosis.

First I separate the three cost drivers, because they have different fixes: active metric series, log bytes, and post-sampling spans. For metrics I look at series growth by metric name and by label — usually a new label with an unbounded value, or a new instance dimension from an autoscaler — and I would expect the OpenTelemetry overflow attribute or the backend's cardinality report to point at it in minutes. For logs I look at bytes by service and level, and the usual culprit is a debug log left enabled or an exception loop printing stack traces. For traces I check whether someone changed the sampler or added a hot instrumentation library. The lead move is to fix it in the pipeline first — drop or aggregate at the Collector so the bleeding stops today — and then fix the instrumentation properly, because pipeline rules are reversible and code changes take a release cycle.

How do you explain the value of observability to a CFO or a sceptical VP?

I translate it into minutes of outage and engineer-hours. If a typical severity-1 costs the business a known amount per minute and observability work reliably removes ten minutes from time-to-mitigate, that number is the return, and it is usually far larger than the tooling bill. I also quantify the hidden cost of not having it: engineers reproducing bugs locally, "just add a log line and redeploy" cycles, and the on-call attrition that comes from noisy pages. Then I give them the lever back — telemetry cost is controllable at the pipeline with sampling, aggregation and tiered retention, so the conversation is about a dial, not a blank cheque. Framing it as risk reduction with a controllable unit cost is what gets budgets approved.

02Instrumentation & OpenTelemetry

OpenTelemetry is two things that get confused constantly, and the distinction is the first thing a good interviewer probes. The API is the surface your code and your libraries call — start a span, record a measurement, emit a log. The SDK is the implementation that samples, batches and exports. They are separately versioned, and the API is deliberately a no-op when no SDK is installed. That is not a curiosity, it is the entire reason library authors can instrument their code: a library that depends on the OTel API adds no exporter, no configuration and no runtime cost to a user who has not opted in, so instrumentation can live upstream instead of in a vendor's agent. The whole ecosystem is downstream of that design choice.

You have three ways to get telemetry out of a process, and a lead is expected to mix them deliberately rather than pick one.

  • Zero-code (auto) instrumentation — a JVM -javaagent, a .NET profiler-based agent, opentelemetry-instrument for Python, --require hooks for Node, or the Kubernetes Operator injecting it for you. It patches known libraries (HTTP servers and clients, database drivers, message brokers) and produces the entire service-to-service call graph on day one, with no code change. This is how you get 80% of the value in a week.
  • Manual / native instrumentation — you call the API yourself to add the spans and attributes that describe your domain: which pricing rule fired, which tenant, how many items in the cart. Auto-instrumentation cannot know any of that, and it is exactly what makes the difference between "the database was slow" and "the database was slow for carts with more than 200 lines".
  • eBPF — OpenTelemetry eBPF Instrumentation (OBI), the project Grafana donated from Beyla, watches HTTP, gRPC and SQL traffic from the kernel with no library, no redeploy and no language SDK. It reached v0.8.0 in April 2026 with 1.0 targeted for late 2026. It is the answer for legacy binaries, third-party images and languages with no SDK; it cannot see inside your business logic, and it needs privileged access, so it complements SDKs rather than replacing them.

Whatever route you take, the telemetry is worthless unless it is identified. Every SDK produces a Resource: the immutable set of attributes describing the entity emitting the data — service.name, service.version, service.namespace, deployment.environment.name, plus whatever the resource detectors add for host, container, Kubernetes pod and cloud provider. service.name is the only required one, and if you forget it the SDK reports unknown_service, which is the single most common self-inflicted wound in a first rollout: every service collapses into one blob and the service map is meaningless. Treat resource attributes as deployment configuration, not code — they come from the environment, so the same artefact can run in staging and production.

    activity?.SetTag("enduser.pseudo.id", cart.CustomerHash);
    activity?.SetTag("checkout.cart.line_count", cart.Lines.Count);
    activity?.SetTag("checkout.payment.provider", cart.PaymentProvider);

    {

What changed in 2026 is that declarative configuration became stable: a single YAML file, shared across languages, that describes providers, processors, samplers and exporters, pointed at by an environment variable. Interview trap

Three that come up constantly. (1) Wrapping OpenTelemetry in your own facade. It feels like good architecture — "we might swap vendors" — but you already have the vendor-neutral abstraction; the wrapper just breaks context propagation, hides semantic conventions, and means every upstream instrumentation library talks to the real API while your code talks to yours. OpenTelemetry published a post in 2026 titled almost exactly that: don't wrap it. (2) Instrumenting without a Resource. No service.name means unknown_service, and no service.version means you can never answer "did this start with the deploy?" — which is the most valuable question in production debugging. (3) Double instrumentation. Running the auto-instrumentation agent and a hand-rolled HTTP client wrapper produces two spans per call, inflates your span bill and skews every latency percentile. Check for duplicate spans the day you turn an agent on.

Try it

1. Run the OpenTelemetry demo (docker compose up from open-telemetry/opentelemetry-demo), then kill one downstream service and watch what the trace of a failing checkout looks like end to end. 2. Take any service of yours, add the zero-code agent with only OTEL_SERVICE_NAME and an OTLP endpoint, then add exactly three manual attributes to your most important handler and query for a slice you could not query before.

Solution sketch

In (1) the failing span shows ERROR status and the parent chain stays intact, so you can see the retry storm the failure induces upstream — the demo's own "we broke the OTel demo" exercise is built around exactly this. In (2) the agent alone gives you server and client spans with http.route, http.response.status_code and DB statements; your three attributes are what let you ask "p99 for tenant acme on version 1.42 when the cart had over 200 lines". Time both steps: the first should take under an hour, the second under a day, and that ratio is the argument you use when a team says instrumentation is too expensive to start.

Interview Q&A

Explain the OpenTelemetry API/SDK split and why it exists.

The API is the call surface — tracers, meters, loggers — and it is designed to be a no-op when no SDK is registered; the SDK is the implementation that samples, batches, and exports. The split exists so that third-party libraries can instrument themselves against the API without imposing any dependency, cost or vendor choice on their users; if you do not install an SDK, those calls compile to nothing meaningful and cost roughly nothing. It also lets the API stay stable for years while the SDK evolves, which is what made it safe for framework authors to adopt. The practical consequence for an application team is that the SDK belongs in exactly one place — the executable's composition root — and libraries should depend only on the API.

Auto-instrumentation, manual, or eBPF — how do you choose?

I use all three deliberately. Zero-code agents first, because they produce the whole service call graph in days and prove the pipeline works; manual instrumentation second, on the handful of code paths that carry business meaning, because that is the only source of the attributes that actually explain incidents; and eBPF via OBI where I cannot change the process — legacy binaries, vendor images, languages without a mature SDK. The trade-offs I name are that agents cost a few percent CPU and some startup time and occasionally break on framework upgrades, manual instrumentation costs engineering time and can be inconsistent without a review standard, and eBPF needs privileged access and a recent kernel and cannot see inside your logic. The wrong answer is to insist on one route for purity.

What is a Resource and why does it matter more than people think?

A Resource is the immutable identity of the thing producing telemetry — service name, version, namespace, deployment environment, plus detected host, container, pod and cloud attributes — and it is attached to every span, metric and log the process emits. It matters because every correlation, every service map, every "compare this version with the previous one" query is a group-by on resource attributes. The two that pay for themselves immediately are service.name, without which everything shows up as unknown_service, and service.version, which turns "is this new?" from a guess into a query. I treat resource attributes as deployment configuration injected by the platform, so the same image can run anywhere and no engineer has to remember to set them.

Should we build an internal wrapper around the OpenTelemetry API?

Almost never, and I would push back hard in a design review. The stated reason is usually vendor portability, but OTLP plus the API is already the portability layer, and the wrapper actively hurts: it breaks context propagation in subtle ways, it hides semantic conventions so your attribute names drift from everyone else's, it lags upstream features, and it does nothing for the instrumentation that ships inside your libraries and frameworks, which will keep calling the real API. Where a thin helper is justified is enforcing house rules — a function that starts a span with your standard business attributes, or a logging bridge — as long as it wraps a use case, not the API itself. If a team has already built one, my migration is to freeze it, make the raw API allowed, and let it wither.

How do you configure the SDK across a polyglot fleet?

Environment variables are the baseline and they are consistent across languages — service name, OTLP endpoint, sampler, resource attributes — and for a simple container that is enough. For anything with structure I now use declarative configuration, which became stable in 2026: a single YAML file describing providers, processors, samplers, views and exporters, identical across languages and pointed at by one environment variable. It makes the configuration reviewable in a pull request, lets the platform team ship a golden config as a ConfigMap, and expresses things env vars cannot, like multiple exporters or per-instrument metric views. The migration story is friendly, because env vars still work and I roll the file out service by service.

What is OBI and when would you reach for it?

OBI is OpenTelemetry eBPF Instrumentation, the upstream project donated by Grafana from Beyla, which observes HTTP, gRPC and SQL traffic from the kernel and emits OTLP without touching the application. It hit v0.8.0 in April 2026 and is aiming at 1.0 by the end of the year, and Grafana's Beyla continues as a downstream distribution. I reach for it when the process is not mine to change: a vendor container, an old binary nobody can rebuild, a language with no mature SDK, or a compliance boundary where injecting an agent is a fight. The limits I would state up front are that it needs privileged access and a reasonably current kernel, it sees protocol-level facts only, and TLS termination inside the process makes some of it harder — so I treat it as a floor of coverage, not a replacement for SDK instrumentation on the services that matter.

How would you roll instrumentation out to fifty services without a two-year programme?

I sequence it so value arrives before effort does. First the pipeline: a Collector deployment, an endpoint, and a cost guard, so nothing that follows is blocked on infrastructure. Second, zero-code agents everywhere by default through the platform — a Kubernetes Operator injecting them, or a base image — with resource attributes supplied by the deployment system so no team has to think about it. Third, a small golden-path library or template for manual spans plus a code-review checklist, and then I only ask the ten services on the critical user journey to do manual work. I would set an explicit non-goal — we are not chasing 100% coverage — because the last 40% of services generate a fraction of the incidents and chasing them is how these programmes die.

What's the performance cost of instrumentation, and how do you defend it?

The honest numbers: a typical zero-code agent costs a few percent CPU and some added startup latency; manual spans are cheap individually — allocation plus a sampling decision — but a span per loop iteration is not; metrics cost is dominated by attribute allocation and cardinality, not by the counter increment; and the exporter's batching means the network cost is amortised. The real risks are not steady-state CPU but pathological cases: unbounded attributes causing allocations, a synchronous exporter blocking a request path, and a Collector that is down causing memory to accumulate in the queue. I defend the cost by measuring it in a load test with instrumentation on and off, and by pointing at the sampling and pipeline levers, so the answer to "it's too expensive" is a dial rather than an argument.

What do you look for in code review of new instrumentation?

Semantic-convention names rather than invented ones, because non-standard attribute names quietly break every dashboard and processor that expects the standard. Bounded values on anything that becomes a metric label, and unbounded ones pushed to span attributes. Span names that are low-cardinality templates — GET /orders/{id}, not the URL with the ID in it — since span name is effectively a grouping key. Error status actually set on failure, because tail sampling and error dashboards key off span status, not off an exception being logged somewhere. And no personal data in attributes without a redaction rule in the pipeline, because telemetry leaves your security boundary.

A library you depend on emits terrible telemetry. What are your options?

In order of preference: contribute upstream, since OpenTelemetry instrumentation lives in public repositories and a fix helps everyone; wrap the call site with your own span if the library is small and the surface is narrow; or fix it in the pipeline, which is the fastest and most under-rated option. With OTTL in the Collector I can rename attributes, drop noisy spans, rewrite a high-cardinality span name into a template, or filter an entire instrumentation scope, without touching the application or waiting for a release. The trade-off is that pipeline rules are invisible to the developer reading the code, so I document them next to the Collector config and treat them as temporary until upstream lands.

03Tracing & context propagation

A trace is a directed acyclic graph of spans, each one a timed operation with a name, a kind, a status, a bag of attributes and a parent. The identity is deliberately dumb: a 16-byte trace ID that every span in the request shares, and an 8-byte span ID unique to each. What makes distributed tracing work is not the data model, it is context propagation — the discipline of carrying the current trace and span ID across every boundary the request crosses, in-process through the language's context mechanism (Go's context.Context, .NET's AsyncLocal, Java's thread locals plus instrumentation, JavaScript's async hooks) and cross-process through headers.

The wire format is the W3C Trace Context standard, and you should be able to read one out loud:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^  ^                                ^                ^
             |  trace-id (16 bytes, 32 hex)      parent span-id   flags: 01 = sampled
             version

tracestate: rojo=00f067aa0ba902b7,congo=t61rcWkgMzE,ot=th:8
            ^ vendor-specific key/value list, 32 entries max
                                              ^ OTel consistent-sampling threshold

Three details in that header are interview gold. The 01 sampled flag is a recommendation from upstream, not a fact about your service — which is why a ParentBased sampler applied to traffic from the public internet is a denial-of-service vector: anyone can set the flag and force you to record every request. The tracestate list is where vendors and OpenTelemetry stash extra state, including the ot=th: consistent-sampling threshold that lets independently-sampling services agree on which traces survive, so you get complete traces instead of half of one. And baggage — a separate baggage header — is not the same thing: it carries arbitrary user-defined key/value pairs to every downstream service, which is superb for propagating a tenant ID or a "this is a synthetic test" flag, and dangerous because it travels to third parties, inflates every request, and will happily carry personal data into a vendor's storage if you let it.

Span kind is more load-bearing than its two-line documentation suggests. SERVER and CLIENT mark the two ends of a synchronous call, and backends use them to build service maps and to compute "time spent in dependency". PRODUCER and CONSUMER mark asynchronous boundaries, and INTERNAL is everything else. The async boundary is where naive tracing falls over: in our checkout example, checkout-api publishes order.placed and returns; fulfilment-worker picks it up eight seconds later, possibly in a batch of 50 messages. If you make the consumer span a child of the producer, you get a trace whose root span lasts eight seconds and a batch consumer with 50 parents, which is impossible. The correct model is a new trace per consumed message, joined to the origin with a span link — links express "related to" without implying "caused by within this timing tree".

// Producer: inject context into the message headers, exactly as you would into HTTP.
func Publish(ctx context.Context, msg *Message) error {
    ctx, span := tracer.Start(ctx, "order.placed publish",
        trace.WithSpanKind(trace.SpanKindProducer),
        trace.WithAttributes(
            semconv.MessagingSystemKey.String("rabbitmq"),
            semconv.MessagingDestinationName("orders"),
        ))
    defer span.End()
    // The carrier is whatever your broker calls headers; the propagator does the rest.
    otel.GetTextMapPropagator().Inject(ctx, propagation.HeaderCarrier(msg.Headers))
    return broker.Publish(ctx, msg)
}

// Consumer of a BATCH: one new trace per message, linked back to its producer.
func Consume(ctx context.Context, batch []*Message) {
    for _, msg := range batch {
        upstream := otel.GetTextMapPropagator().Extract(ctx, propagation.HeaderCarrier(msg.Headers))
        link := trace.LinkFromContext(upstream)
        // NOT a child: the producer finished long ago and a batch has many parents.
        _, span := tracer.Start(context.Background(), "order.placed process",
            trace.WithSpanKind(trace.SpanKindConsumer),
            trace.WithLinks(link))
        process(msg)
        span.End()
    }
}

Then there is sampling, which is where cost meets forensics. Head sampling decides at the root, before anything has happened: cheap, deterministic, and blind — it throws away the 0.1% of requests that were about to fail. Tail sampling buffers all spans of a trace until it is complete, then decides using what actually happened: keep every error, keep everything slower than 2 seconds, keep 1% of the boring remainder. It is strictly better forensically and strictly more expensive operationally, because the Collector must hold every in-flight trace in memory and all spans of a trace must reach the same Collector instance — which forces a two-tier deployment with a trace-ID-aware load balancer in front of the tail-sampling gateway. That single fact ("how do you make tail sampling work behind a load balancer?") is one of the most reliable senior-versus-lead discriminators in this topic.

What changed in 2026: the Span Events API is deprecated (announced 17 March 2026). Interview trap

Trusting an inbound traceparent at the edge. A ParentBased sampler honours the upstream sampled flag, so a public endpoint that respects external trace context lets anyone force 100% sampling — a cheap way to run up your bill or overload your pipeline — and lets them inject a trace ID they choose, which pollutes your traces and can be used to probe. At an internet-facing boundary either start a fresh trace and link to the incoming one, or accept the context but apply your own root sampler. The related trap is partial traces: if service A samples at 10% and service B samples independently at 10%, you keep complete traces only 1% of the time and get a lot of orphaned fragments. The fix is ParentBased everywhere below the root, or OpenTelemetry's consistent probability sampling with the threshold carried in tracestate.

Try it

1. Break propagation on purpose: in a two-service setup, strip the traceparent header in the caller and watch the trace split into two disconnected roots — then re-add it and note how the service map changes. 2. Put a queue between two services and implement it twice, first with the consumer as a child of the producer, then with a linked new trace, and compare the waterfalls.

Expected outcome

In (1) you get two traces where the downstream one has no parent and your dependency graph loses an edge — this is exactly what a missing propagator, a proxy that strips unknown headers, or a hand-built HTTP client looks like in production, and recognising the symptom saves hours. In (2) the parent-child version shows a root span whose duration includes queue dwell time, so your "checkout latency" silently becomes "checkout plus however long the queue was backed up" — which then poisons any SLI built on root-span duration. The linked version keeps the two timings separate and still lets you navigate between them, which is why links exist.

Interview Q&A

Walk me through what happens to trace context across an HTTP call.

The caller has an active span in its context; the instrumented HTTP client asks the configured propagator to inject that context into the outgoing request, which writes a W3C traceparent header containing version, trace ID, the caller's span ID as parent, and the sampled flag, plus tracestate for vendor and sampling state. On the server side the instrumentation extracts those headers into a remote span context and starts a SERVER span whose parent is the caller's span, sharing the trace ID. In-process, the context flows through the language's ambient mechanism — context.Context, AsyncLocal, async hooks — which is where propagation usually breaks, typically at a thread-pool hand-off or a fire-and-forget task. If any hop drops the headers, you do not get an error; you get a second, orphaned trace, which is why "two traces where there should be one" is the classic propagation symptom.

Head versus tail sampling: what do you run, and why?

I run both. Head sampling with a parent-based ratio sampler gives cheap, uniform coverage and keeps client-side cost near zero because unsampled spans are never built; I typically start at 10% and tune. Tail sampling in a gateway Collector then adds the forensic value: keep 100% of errors, everything above a latency threshold, and traces from tenants or journeys that matter, plus a small probabilistic baseline so aggregate statistics are not entirely biased. The cost I call out explicitly is that tail sampling forces you to export every span from the app and buffer whole traces in memory, so it needs a memory limiter, a sized num_traces, and a load-balancing exporter that routes by trace ID so all spans of a trace reach one instance. If a team cannot run that two-tier topology, head sampling with error-biased local rules is the pragmatic fallback.

How do you trace across a message queue?

Inject the trace context into the message headers at publish time with a PRODUCER span, and extract it at consume time — the propagator API is transport-agnostic, so the code is the same shape as HTTP. The design decision is whether the consumer span is a child or a linked new trace. For a single message consumed promptly, a child is acceptable and gives you one continuous trace. For batch consumption, long queue dwell, or retries, I start a new trace with a span link to the producer, because a span cannot have two parents and because otherwise queue latency inflates the root span duration and corrupts any SLI derived from it. I also set the messaging semantic-convention attributes so the backend can compute queue-specific views, and I make sure the message ID is an attribute so I can find the exact message later.

What is baggage, and when is it dangerous?

Baggage is a separate W3C-standard header carrying arbitrary key/value pairs that propagate to every downstream service in a request, independent of trace sampling. It is the right tool for cross-cutting context that services need but did not receive as a parameter: tenant ID, plan tier, a synthetic-traffic flag, a debug flag that turns up sampling for one request. The dangers are real and three-fold: it is a header on every single call, so size directly costs latency and bandwidth; it propagates to third parties and vendors, so anything personal in it leaks past your boundary; and it is trivially forgeable, so it must never be used for authorisation decisions. My rule is that baggage carries small, non-sensitive, non-authoritative hints, and there is an allowlist of keys enforced in the pipeline.

Why were span events deprecated, and what should new code do?

OpenTelemetry had two overlapping mechanisms for point-in-time records — span events on the Tracing API and log-based events on the Logs API — which meant instrumentation authors had to choose, backends had to render both, and the two had different attribute limits and processing paths. In March 2026 the project deprecated the Span Events API and settled on the simpler mental model: an event is a named log record, correlated to the active span through context. Nothing existing breaks; span events already recorded keep working and waterfalls keep showing them, so this is a guidance change, not a removal. In new code I emit events through the logging bridge, which gets me the trace and span IDs automatically, and I stop using recordException in favour of an error log plus a span status.

How do you name spans, and why does it matter?

Span name is effectively a grouping key, so it must be low-cardinality and describe the operation, not the instance: GET /orders/{id}, not GET /orders/8134; SELECT orders, not the full SQL text. Putting an identifier in the name explodes cardinality in every backend that aggregates by name and makes "p99 of this operation" impossible to compute. The identifiers belong in attributes, where they are stored per span and can be filtered on. The semantic conventions specify the name shape for HTTP, database and messaging spans, and following them is what makes vendor dashboards and the Collector's span-metrics connector work without configuration — inventing your own names is a slow-acting poison that only shows up when someone tries to build a dashboard six months later.

You see traces that stop halfway down the call graph. What are your suspects?

In rough order of likelihood: a hop that is not instrumented at all, such as a hand-rolled HTTP client or a raw socket call; a proxy, service mesh or CDN stripping unknown headers; in-process context loss at an async boundary — a task queued to a thread pool, a fire-and-forget, a callback that escapes the scope; independent sampling decisions between services so the child is dropped; and clock skew or an exporter dropping spans under backpressure, which shows up as gaps rather than truncation. I diagnose it by taking one trace ID and checking each service's own logs for it, which immediately tells me whether the span was never created or was created and lost. The Collector's own metrics — refused and dropped spans, queue size — settle the export-side half of that question.

What are span links, and give me a real use for them beyond queues.

A link is a reference from one span to another span context that is causally related but not a parent — it carries a trace ID, span ID and its own attributes. Beyond batch messaging, the cases I use are fan-in jobs, where a scheduled batch processes work created by hundreds of unrelated traces and links back to all of them; retries, where the retry attempt is a new trace linked to the original so you can see the whole story without one span spanning minutes; and long-lived workflows or sagas, where each step is its own trace linked to the workflow root. The general rule is: if joining them as parent-child would produce a span whose duration is a lie, use a link.

What are span limits and why would you tune them?

The SDK enforces caps — by default 128 attributes per span, 128 events, 128 links, and a limit on attribute value length — to prevent a bug from turning one request into a megabyte of telemetry. You notice them when attributes silently vanish from spans, which is a confusing symptom because nothing errors; the SDK records a dropped-attribute count that most people never look at. I tune them upward only deliberately, for example on a wide-event-style span that intentionally carries 200 dimensions, and I tune the value-length cap down when a library insists on attaching full SQL or full request bodies. The related lever is the attribute value length limit as a cheap defence against accidentally exporting a large payload.

How do you handle clock skew across services in a trace?

Spans carry start and end timestamps from each host's own clock, so a child span can appear to start before its parent or to end after it if clocks differ by tens of milliseconds. Good backends clamp children into their parent's window when rendering, but the underlying numbers are still wrong, so any calculation like "time spent in the network" has real error bars. The mitigations are operational — run NTP or PTP everywhere and alert on clock offset as a fleet health metric — and analytical: prefer durations measured within a single process, such as the client span's own duration for a downstream call, over differences computed across two hosts. I mention this in interviews when someone asks how to measure network time, because the correct answer is that you infer it from the gap between a client span and the server span it wraps, and that gap includes your clock error.

04Metrics, cardinality & PromQL

Metrics are the cheap signal, and they are cheap because they throw information away at write time. A counter increment does not store an event; it mutates a number attached to one label combination. That is why metrics can be scraped every 15 seconds for years at trivial cost, why they are the right substrate for alerting, and why a single unbounded label is fatal. Everything else about metrics follows from that one trade.

OpenTelemetry gives you a small instrument vocabulary and expects you to pick correctly. A Counter only goes up (requests served, bytes sent); an UpDownCounter can go both ways (queue depth, active connections); a Histogram records a distribution (request duration, payload size); a Gauge samples a current value (temperature, pool utilisation), and its asynchronous form takes a callback the SDK invokes at collection time. The classic mistake is using a gauge for something that should be a counter: gauges lose everything that happened between two collections, so a gauge of "errors since last time" silently drops data during a scrape gap, while a monotonic counter is reconstructable because the consumer computes rates from differences and can detect resets.

Aggregation temporality is the concept that separates people who have wired OTLP metrics into a Prometheus-shaped world from people who have only read about it. Cumulative means each export carries the running total since process start; delta means it carries only what happened since the last export. Prometheus is natively cumulative — rate() exists precisely to differentiate a cumulative counter and to handle resets when a process restarts. Many commercial backends prefer delta because it makes stateless ingestion and short-lived processes (a Lambda that lives 200 ms) work. OpenTelemetry lets you choose per instrument via the exporter's temporality preference, and the failure mode of getting it wrong is not an error message: it is graphs that look plausible and are wrong by a factor of the reporting interval.

// Instrument choice and bounded attributes, Java SDK.

    .setUnit("{order}")                     // UCUM units; annotations in braces

Cardinality has a built-in safety net that most people discover the hard way. The OpenTelemetry metrics SDK applies a default cardinality limit of 2,000 attribute sets per metric. Once a metric hits it, further attribute combinations are not dropped — their measurements are folded into a single overflow series marked otel.metric.overflow=true, so totals stay correct while the dimensions are lost. The symptom is a dashboard where a breakdown suddenly stops showing new values and a mysterious overflow bucket appears; the diagnosis is "someone added an unbounded label". You can raise the limit per instrument through a View, but the right response is nearly always to remove the offending attribute, not to raise the ceiling.

On the storage side, Prometheus 3.x (3.14.0, released 17 August 2026) is the reference. The two changes that matter for interviews are native histograms, stable since 3.8.0, and native OTLP ingestion. A classic Prometheus histogram is a set of pre-declared cumulative buckets — you choose the boundaries at instrumentation time, you get one time series per bucket, and if your latency moves outside the range you chose you cannot compute a useful quantile without a code change and a redeploy. A native histogram stores exponentially-spaced buckets with a resolution parameter, in a single series, so it covers many orders of magnitude, adapts automatically, and costs dramatically less: you get better accuracy and roughly an order of magnitude fewer series. Prometheus 3 also accepts OTLP directly on /api/v1/otlp/v1/metrics, supports UTF-8 metric and label names (so http.server.request.duration no longer has to become http_server_request_duration), and Remote-Write 2.0 carries metadata, exemplars, created timestamps and native histograms.

Exemplars are the bridge that makes metrics stop being a dead end. An exemplar attaches a trace ID (and timestamp and value) to a histogram bucket observation, so a spike on a latency graph carries a handful of concrete trace IDs you can click straight into. Getting from "p99 is up" to "here is a request that was slow" in one click is the single highest-value correlation feature in the whole stack, it is supported end-to-end by OTel SDKs, Prometheus (with exemplar storage enabled) and Grafana, and it costs almost nothing. If an interviewer asks how you connect metrics to traces, exemplars is the first word out of your mouth.

Interview trap

Averaging percentiles. The p99 of a service is not the average of the p99s of its ten instances, and no amount of dashboarding makes it so — quantiles are not linear, so you must aggregate the underlying buckets and compute the quantile last. That is why histogram_quantile(0.99, sum by (le) (rate(...[5m]))) has the sum inside: sum the bucket rates, then take the quantile. The same error appears as "average latency looks fine" when the mean hides a bimodal distribution — one fast path and one pathological path — which is exactly the shape a connection-pool or GC problem produces. Two related gotchas: rate() over a window shorter than about four scrape intervals produces gaps and noise (a 1-minute window on a 30-second scrape is a classic self-inflicted flapping alert), and irate() is for graphing fast-moving signals, never for alerting, because it uses only the last two samples.

Try it

1. Add a label with an unbounded value — request ID or full URL path — to a metric in a test service, run traffic for ten minutes, and watch active series and the otel.metric.overflow bucket appear. 2. Instrument the same latency twice, once as a classic histogram with default buckets and once as a native histogram, then shift your service's real latency to 8 seconds and compute p99 from both.

Expected outcome

In (1) you should see series count climb roughly linearly with unique requests until the SDK's 2,000-per-metric limit clamps it, after which your breakdown stops gaining new values and everything new lands in the overflow series — a much friendlier failure than the OOM you would get from a backend without that guard, and a good story about why the limit exists. In (2) the classic histogram's default buckets top out well below 8 seconds, so histogram_quantile returns the upper bound of the last bucket, i.e. a confident wrong answer, while the native histogram tracks the shift without a code change. That difference is the practical argument for native histograms in a design review.

Interview Q&A

Counter, gauge, histogram, up-down counter — how do you choose?

Counter for anything monotonically accumulating that I will differentiate later: requests, errors, bytes, retries. UpDownCounter for a level that legitimately moves in both directions: queue depth, active connections, items in a cache. Histogram for anything where the distribution matters and an average would lie — latency, payload size, batch size. Gauge, especially the asynchronous callback form, for values I sample rather than accumulate, like pool utilisation or a temperature from an external source. The mistake I watch for in review is a gauge used for a count of events, because a gauge loses everything between collections and cannot be rate-computed reliably, whereas a counter survives scrape gaps and process restarts because consumers detect resets.

Explain aggregation temporality and where it bites.

Cumulative exports carry the total since process start; delta exports carry only the change since the previous export. Prometheus is cumulative by design — rate() differentiates and handles counter resets — while many SaaS backends prefer delta because it lets them ingest statelessly and handle very short-lived processes like serverless functions, where a cumulative counter that resets every 200 ms is useless. OpenTelemetry lets you set a temporality preference per exporter and per instrument kind, and the failure mode of a mismatch is silent: numbers that look reasonable but are off by the interval, or counters that appear to reset constantly. My rule is to match temporality to the backend deliberately and to write it down, because it is invisible in code review otherwise.

What is metric cardinality, and how does OpenTelemetry protect you?

Cardinality is the number of distinct attribute combinations on a metric, and since each combination is a stored series, it is the dominant cost and memory driver in any time-series database. OpenTelemetry's SDK applies a default limit of 2,000 attribute sets per metric; beyond that, new combinations are aggregated into a single overflow series flagged otel.metric.overflow=true rather than dropped, so the totals stay accurate while the breakdown is lost. That is a deliberate design: protect the process from unbounded memory growth without silently corrupting sums. You can override it with a View per instrument, but I treat hitting the limit as a bug report about the instrumentation, and I also enforce it at the pipeline with a Collector transform that drops or hashes the offending attribute so the fix ships in minutes rather than in a release.

Why can't you average p99s, and what do you do instead?

Quantiles are order statistics, not means, so they do not compose — the 99th percentile of the union of two populations is not the mean of their 99th percentiles, and it can be wildly off when the populations differ in size or shape. The correct approach is to aggregate the raw distribution and compute the quantile at the end: with classic histograms, sum the per-bucket rates across instances keeping the le label, then apply histogram_quantile; with native histograms, sum the histogram series and do the same. This is also why pre-computed quantiles from a summary type are nearly useless in a distributed system: they cannot be re-aggregated at all. Whenever I see avg(p99) on a dashboard I treat it as a signal that nobody has audited that dashboard.

What are exemplars and why do they matter?

An exemplar is a sample observation attached to a histogram bucket that carries the trace ID and span ID of the request that produced it, plus its value and timestamp. It matters because it collapses the most common workflow in production debugging — "latency is up, show me a slow request" — from a multi-tool archaeology exercise into one click from the graph into the trace. The plumbing is cheap: the SDK records them when a span is sampled, Prometheus stores them in a separate exemplar store, and Grafana renders them as dots on the graph with a link. The caveat I would state is that exemplars are only as useful as your sampling — if the slow request was not sampled, there is no trace to jump to, which is a concrete argument for tail-sampling on latency.

Classic or native histograms for a new service in 2026?

Native, if the whole path supports them — client library, Collector, and a Prometheus 3.x or compatible store — because they became stable in Prometheus 3.8.0, cover many orders of magnitude automatically, and collapse a dozen bucket series into one, which is a real cardinality saving multiplied across every instance. The classic histogram's flaw is that you must guess bucket boundaries at instrumentation time, and when real latency moves outside them your quantile silently pins to the last bucket's upper bound. I still use classic buckets when I need compatibility with an older backend or an exporter I do not control, and during a migration I sometimes emit both for a period to validate that the numbers agree before cutting over.

RED, USE, and the four golden signals — do you actually use all three?

They are three lenses on the same idea, chosen by what you are looking at. RED — rate, errors, duration — is for request-driven services and is what I template every service dashboard on. USE — utilisation, saturation, errors — is for resources: CPU, memory, disks, thread pools, connection pools, and it is the lens that catches the problems RED only shows as symptoms. The four golden signals — latency, traffic, errors, saturation — are essentially RED plus saturation, and the saturation term is the important addition because it is the leading indicator: queue depth and pool utilisation move before latency does. In practice I alert on RED at the user boundary and use USE and saturation for diagnosis and for capacity work, which keeps pages symptom-based while leaving the causal signals available.

Push or pull for metrics collection?

Pull, as Prometheus does it, gives you a built-in liveness signal — a target that stops responding is instantly visible as up == 0 — plus a central, declarative view of what is supposed to exist, and it makes it trivial to scrape ad hoc. Push, as OTLP does it, is required for anything short-lived or unreachable: serverless functions, batch jobs, clients behind NAT, and anything where the scraper cannot see the target. The modern answer is that you do not choose globally: applications push OTLP to a local Collector, and the Collector either exposes a scrape endpoint or remote-writes onward, so you get push semantics at the edge and pull semantics in the platform. The one thing to preserve when you push is an explicit heartbeat or an up-equivalent, because you lose the free liveness check.

How do you keep metric costs under control as the estate grows?

Four levers, applied in order of bluntness. First, attribute hygiene at the source: no unbounded labels, route templates rather than URLs, and the SDK's cardinality limit left enabled. Second, pipeline-side control: drop metrics nobody queries, aggregate away an instance or pod dimension where per-instance detail is not used, and enforce allowlists with OTTL in the Collector, which is reversible and ships in minutes. Third, recording rules for expensive queries so dashboards read pre-aggregated series instead of scanning raw ones. Fourth, retention tiers — high resolution for two weeks, downsampled for a year. I also instrument the cost itself: series per metric name and per service, published so teams see their own footprint, because visibility changes behaviour faster than policy does.

What's new in Prometheus 3 that changes how you design metrics?

Three things. Native histograms are stable as of 3.8.0, which changes latency instrumentation from "pick buckets and hope" to a single adaptive series. UTF-8 support for metric and label names means OpenTelemetry's dotted names such as http.server.request.duration survive ingestion instead of being mangled into underscores, which finally makes semantic-convention names portable end to end. And native OTLP ingestion on /api/v1/otlp/v1/metrics, together with Remote-Write 2.0 carrying metadata, exemplars, created timestamps and native histograms, means Prometheus is a first-class OTLP backend rather than something you bolt a translation layer onto. Practically, that lets me standardise on OTLP from the application everywhere and treat the choice of metric store as a swappable decision.

05Logs, events & wide events

Logs are the oldest signal and the one most organisations do worst. The reason is historical: logs began as human-readable strings for a person reading a terminal, and most codebases still emit them that way, then pay a search engine enormous amounts of money to reverse-engineer structure out of prose at query time. The single highest-leverage change any team can make is to stop writing sentences and start writing structured events: a stable event name plus typed key/value attributes, rendered as JSON or an equivalent binary form, where the message is a constant and everything variable is a field.

OpenTelemetry approached logs differently from traces and metrics, and understanding why is a genuine signal of depth. For traces there was no incumbent, so OTel shipped an API for developers to call. For logs, every language already has one or three mature logging libraries with a decade of adoption, so OTel deliberately did not ask you to rewrite your logging calls. Instead it defines a log data model and ships bridges (appenders) that plug into Serilog, log4j, Logback, slog, Python logging, Winston and the rest. Your code keeps calling the logger it always called; the bridge attaches the current trace and span ID from context, adds the Resource, and exports over OTLP. The Logs API in OTel is explicitly aimed at bridge authors and instrumentation, not at application developers — with one exception, which is the new home for events after the March 2026 deprecation of span events.

Notice what that record is: not "an error happened", but a complete, self-describing account of one decision, carrying the trace ID that ties it to the rest of the request. Push that idea to its conclusion and you get the wide event — also called the canonical log line, a pattern Stripe popularised — where each unit of work emits exactly one very rich record at the end, with 50 to 300 dimensions: the route, the user's plan tier, the feature flags in effect, cache hit counts, the number of database queries and their total time, the downstream services called, the payload sizes, the build SHA, the region, the queue dwell. One row per request, extremely wide.

The argument for it is that debugging is mostly differential: you have a set of bad requests and a set of good ones, and you want to know what distinguishes them. If every dimension is on one row, that question is a group-by. If the same information is scattered across twelve log lines, three metrics and a trace, it is an afternoon. The argument against is cost and maturity: wide events want a columnar store that indexes everything, which is more expensive per byte than a Loki-style label index, and the tooling landscape is less standardised. The lead-level position is a hybrid you should state plainly: emit one wide canonical event per request as your primary debugging substrate, keep a small number of cheap metrics for alerting, and keep tracing for the cross-service call graph — recognising that a span with a hundred attributes is a wide event, which is why OpenTelemetry makes the hybrid natural rather than contradictory.

Cost control for logs is a pipeline problem, and the Collector has grown the tools for it. The log deduplication processor collapses identical records emitted in a window into one with a count — brutally effective against retry loops and per-item error logs, which are the two shapes that produce 90% of a log bill spike. Interview trap

Using logs to compute things metrics should compute. "We count errors by grepping the logs" works until traffic grows, and then you are paying to index millions of records so a dashboard can produce a number a counter would have given you for free — and the query gets slower exactly when you need it most, during an incident. The inverse trap is just as common: trying to put a customer ID into a metric so you can "find the affected users", which is the cardinality explosion from unit 04. The rule to state crisply: metrics answer "how many / how bad", events answer "which ones and why". A third trap, and the one that costs real money in production, is logging inside a loop over a collection — a single bad request with 10,000 line items becomes 10,000 log records, and under retry that becomes a self-inflicted denial of service against your own logging pipeline.

Try it

1. Take one request handler and replace all its log lines with a single canonical event emitted at the end, carrying every dimension the handler knew about — then answer a question you could not previously answer with one query. 2. Deliberately create a retry storm (make a downstream dependency fail and let a client retry three times with a per-attempt error log), measure the log volume, then turn on the deduplication processor and measure again.

Solution sketch

For (1) the practical trick is to accumulate a per-request context object as the handler runs (counts, timings, flags, IDs) and emit it in a middleware's finally block, so the pattern is applied once and cannot be forgotten. The question that suddenly becomes easy is the differential one: "what do the slow requests have in common?" answered as a group-by over a single table. In (2) expect an order-of-magnitude difference: three attempts multiplied by per-item errors multiplied by a fan-out is how a 20 GB/day service becomes a 300 GB/day service in one incident, and the dedup processor collapses it to one record with a count attribute — which is also a better artefact for a human to read.

Interview Q&A

Why did OpenTelemetry treat logs differently from traces and metrics?

Because logging was a solved problem with entrenched incumbents in every language, so asking developers to rewrite millions of log statements against a new API would have killed adoption. Instead OTel specified a log data model and shipped bridges — appenders that hook into Serilog, log4j, Logback, slog, Python's logging — so existing calls are enriched with trace context and resource attributes and exported over OTLP without touching call sites. That is why the Logs API is documented as being for bridge and instrumentation authors rather than application developers. The practical upside is that adopting OTel logs is usually a dependency and a config change rather than a refactor, which makes it the easiest of the three signals to land in a legacy estate.

What is a wide event, and would you actually adopt the pattern?

A wide event is one very high-dimensional record per unit of work — a request, a job, a message — carrying everything the process knew: identifiers, timings, counts, flags, versions, downstream results. I would adopt it selectively, on the services where debugging pain is highest, because it makes differential diagnosis a group-by instead of a join across log lines. The cost is real: you need a store that can handle high cardinality across many columns, and you have to be disciplined about what you put in it, particularly personal data. The nuance I would offer is that this is not a new religion — a richly attributed span in OpenTelemetry is already a wide event, so for most teams the pragmatic version is "stop emitting eight log lines per request, attach those fields to the span, and emit one canonical record at the end".

How do you correlate a log line with a trace?

The log record carries the trace ID and span ID from the active context, which the OTel logging bridge attaches automatically, and both carry the same resource attributes. In the backend that becomes bidirectional navigation: from a span, show the log records with that trace ID; from a log record, open the trace. Where it breaks is code that logs outside any span — background threads, startup, static initialisers — and code that hops threads without propagating context, where you get a record with a zeroed trace ID. My checks are to look for the proportion of log records with a trace ID as a health metric of the instrumentation itself, and to make sure the logging bridge is installed before anything else logs.

What log level do you run in production, and how do you get more detail when you need it?

INFO by default for the request path plus WARN and ERROR, and a strict rule that INFO means "a business-meaningful thing happened", not "I am here". For more detail I use dynamic verbosity rather than a redeploy: an admin endpoint or config watcher that raises the level for one logger or one service at runtime, a feature-flag-driven debug mode, and per-request debug via a baggage flag so a single synthetic transaction can be traced verbosely through the whole system without changing anything for real traffic. I also cap the blast radius by time-boxing elevated levels automatically, because the number one source of surprise log bills is a DEBUG left on after an incident. If none of that exists yet, the cheapest first step is making the level configurable without a restart.

How do you keep personal data out of telemetry?

Defence in depth, because a single control always fails. At the source, a review rule that identifiers are pseudonymised — a hashed user ID rather than an email — and structured fields rather than interpolated strings, since prose is what smuggles data in. In the pipeline, OTTL redaction and deletion rules in the Collector for known-sensitive keys and pattern matches for emails, card numbers and tokens, applied before anything leaves the trust boundary. In storage, retention limits and access control, plus a deletion path so a subject-access or erasure request is actually satisfiable. And a detective control: periodic sampling of telemetry scanned for patterns, reported as a compliance metric. The reason to insist on the pipeline layer is that it is the only one you can change in minutes when someone finds a leak.

Your log bill tripled overnight. What do you do in the first hour?

Stop the bleeding at the pipeline first: find the top emitters by service and severity, and apply a filter or deduplication rule in the Collector so the cost stops now — that is a config rollout, not a release. Then diagnose the shape: a retry storm producing repeated identical records, a per-item loop, a newly enabled debug level, or a genuine traffic increase, and the dedup ratio usually tells you which within minutes. Then fix the source properly and remove the temporary rule, because permanent pipeline hacks become invisible technical debt. Afterwards I would add a guardrail — a budget alert on log bytes per service and a cardinality/volume check in CI or in the platform — so the same class of incident is detected in minutes rather than on the invoice.

Structured logs versus span attributes — where does a given piece of information go?

If it describes the operation as a whole — how long it took, which route, which tenant, how many items — it belongs on the span, because that is the record of the operation and it is where correlation and sampling already work. If it describes a discrete moment inside the operation — a retry happened, a cache was invalidated, a payment was declined — it is an event, which after the 2026 deprecation of span events means a log record correlated to that span. If it is something the process knows independent of any request, like a config value at startup or a background job outcome, a plain log record is right. The practical anti-pattern is duplicating the same fields into both, which doubles cost and creates two versions of the truth that drift.

Should logs be sampled?

Yes, for the high-volume, low-information tiers, and no for the ones you need to be complete. I sample or drop health checks, successful readiness probes and repeated identical records aggressively, and I keep 100% of errors and of anything that carries an audit or compliance obligation. The subtlety worth raising is consistency: if you sample logs independently of traces you get requests where you have the trace but not its logs, which is worse than either alone, so the right approach is to make the sampling decision once per request and honour it across signals — the trace's sampled flag is the natural carrier. And audit logs should be on a separate pipeline entirely, because they have retention and integrity requirements that have nothing to do with debugging.

How do you handle exceptions now that recordException is on the deprecated path?

Two things must happen and they are separate. First, the span's status must be set to error, because span status is what drives error dashboards, tail-sampling policies and service-level views — an exception that is logged but leaves the span green is invisible to all of them. Second, the detail — type, message, stack trace, retry attempt — goes into an error-severity log record, which is correlated to the span through context and is the 2026-recommended home for what used to be a span event. In practice a small helper in the exception filter or middleware does both, so no developer has to remember. The related discipline is not logging the same exception at every level as it propagates, which produces five records for one failure and makes error counts meaningless.

How do you make logs searchable at scale without paying to index everything?

Separate the index from the payload. Systems in the Loki family index only a small set of labels — service, environment, level, maybe route — and brute-force scan the compressed body within that narrow slice, which makes ingestion cheap and queries fast enough as long as your labels are well chosen and low-cardinality; the failure mode there is putting a high-cardinality label on a stream, which fragments storage badly. Column-store systems index far more and cost more per byte but make arbitrary slicing fast, which is what wide events want. I usually run tiered storage: errors and canonical events into the searchable tier with short retention, bulk records into cheap object storage with a slow query path for the rare deep investigation, and everything keyed by trace ID so the two tiers can be joined when it matters.

06Continuous profiling

Tracing narrows a problem to a service and an operation; profiling narrows it to a line of code. That is the whole reason profiles became the fourth OTLP signal: the last mile of "the checkout API's p99 doubled" is "a regex in the address validator is being recompiled on every call", and no amount of span nesting will tell you that unless somebody happened to wrap the regex in a span. A profiler answers it without any instrumentation at all, because it works by statistical sampling of stacks: many times a second, capture what every thread is executing, aggregate identical stacks, and the result is a distribution of where the process spends its resources.

The output convention is the flame graph, and misreading it is one of the most common interview tells. The x-axis is not time — it is sorted alphabetically so that identical subtrees merge. Width means "share of samples", i.e. share of the resource. The y-axis is stack depth, with callers below callees. So a wide box means that function was on the stack in a large fraction of samples, and a wide box with nothing above it (a wide plateau) means that function itself was doing the work rather than calling something else. That plateau is what you look for. The second thing to look for is a differential flame graph, which colours the delta between two profiles — before and after a deploy, canary versus baseline, incident window versus the hour before — and turns "where does time go?" into "what changed?", which is a far more answerable question.

Not all profiles measure the same resource, and choosing the wrong one wastes an incident:

Profile typeSamplesFinds
CPU (on-CPU)Stacks of threads actually runningHot loops, serialization, regex, crypto, GC burn
Wall clockStacks of all threads, running or notLatency that is mostly waiting; the honest latency view
Off-CPUStacks at the moment a thread blocks, weighted by blocked timeLock contention, I/O waits, pool starvation
AllocationStacks at allocation sites, weighted by bytesGC pressure, allocation churn, oversized buffers
Heap / in-useLive objects and what allocated themMemory leaks, retained caches
Lock / mutexStacks contending on a lock, weighted by waitSerialization bottlenecks that CPU profiles hide

The classic mistake is reaching for a CPU profile when latency is the complaint. If your service spends 90% of a request waiting on a downstream call, the CPU profile shows the 10% and looks fine; wall-clock or off-CPU profiling is what reveals the wait. "CPU profile looks flat but latency is terrible" is a diagnostic statement, not a dead end — it tells you the problem is blocking, not computation.

Continuous profiling is the practice of running this in production, always, at low sample rates — typically 19 to 100 Hz — so overhead is around 1% and, crucially, so you have a profile of the incident window after the incident. Profiling on demand fails in production for the obvious reason: by the time you attach, the pathological condition is gone. This is where OpenTelemetry's 2026 work lands.

OTLP Profiles entered public alpha in March 2026. The protocol is built on pprof's model but normalised for the wire: a deduplicated stack representation so each unique call stack is stored once, dictionary tables for strings and locations (roughly 40% smaller on the wire), timestamped samples, resource attributes shared with the other signals, and — the part that matters most — samples that can carry trace_id and span_id, so a slow span links directly to the stacks that were executing during it. Collection is served by the eBPF profiling agent running as a Collector receiver: it profiles every process on the host with no per-application agent, does automatic on-target symbolization for Go executables, and covers a growing language set including Node.js on ARM64, BEAM, .NET and Ruby. The k8sattributes processor decorates the profiles with pod metadata and OTTL can transform them like any other signal. Two honest caveats to state in an interview: the signal is alpha, so the project itself says do not build critical workflows on it yet, and eBPF profiling needs privileged access and a modern kernel.

Interview trap

Reading the flame graph as a timeline. If a candidate says "you can see it starts here on the left and then moves right", the interview is effectively over — the x-axis is sorted for merging, not chronological, and the thing that carries meaning is width. (Icicle graphs invert the y-axis; flame charts, confusingly, are time-ordered — worth naming the difference.) The second trap is missing symbols: stripped release binaries and containers without debug info produce flame graphs full of hex addresses, and the fix is a build-and-deploy decision — keep build IDs, ship a symbol server or debug package, and enable on-target symbolization — made long before the incident. The third is safepoint bias on the JVM: profilers that sample only at safepoints systematically attribute time to the wrong methods, which is exactly why async-profiler exists and why "we used the built-in sampler and it said Thread.run" is a familiar dead end.

Try it

1. Write a service with one deliberately hot path — compile a regex inside the request handler rather than once — put load on it, take a CPU profile, and find the plateau. Then fix it and take a differential profile against the first. 2. Make a handler spend 90% of its time sleeping or waiting on a slow dependency, then take a CPU profile and a wall-clock profile of the same window and compare what each one claims.

Expected outcome

In (1) the regex compilation appears as a wide plateau under your handler, usually 30–60% of samples, and the differential profile after the fix shows that subtree collapsing to near zero while everything else stays roughly constant — that pair of images is the most persuasive artefact you can bring to a performance review. In (2) the CPU profile is nearly empty and tells you almost nothing, because the thread is not running; the wall-clock profile shows the wait dominating, with the stack pointing at the blocking call. Internalising that contrast is what stops you from spending an hour optimising code that was never the bottleneck.

Interview Q&A

How do you read a flame graph?

Bottom to top is caller to callee; width is the fraction of samples in which that frame was on the stack; the x-axis is sorted for merging, not time. I look first for the widest plateau — a frame that is wide with little above it, meaning it was doing the work itself rather than delegating — and then walk down to understand which call path led there. I check the total sample count and duration to know how much statistical confidence I have, since a 5-second profile of a low-traffic service is noise. Then, if I have a baseline, I switch immediately to a differential view, because "what changed since the last deploy" is almost always the actual question, and a delta graph answers it in seconds where a raw graph takes minutes of interpretation.

CPU profile shows nothing interesting but latency is bad. What now?

That is a strong signal the process is blocked rather than computing, so I switch profile types: wall-clock or off-CPU profiling, which sample threads that are waiting and attribute the wait time to the stack that caused it. Typical findings are lock contention, a connection pool with no free connections, synchronous I/O on a request thread, or a downstream call with a long timeout. I would corroborate with saturation metrics — thread-pool queue depth, pool wait time, run-queue length — and with the trace, which shows whether the time is inside my process or inside a dependency. The general lesson is that CPU profiling answers "what is expensive" while latency questions usually need "what is waiting", and confusing the two wastes the first thirty minutes of an incident.

What is continuous profiling and what does it cost?

It is profiling production continuously at a low sample rate — typically 19 to 100 Hz — and storing the aggregated stacks, so that you can look at any past window rather than trying to reproduce a problem after it has gone. Overhead is usually around 1% of CPU with a sampling profiler at those rates, and storage is modest because identical stacks are deduplicated and aggregated. The real cost is operational: symbol management, agent deployment, and the privileged access an eBPF-based collector needs. I justify it by the class of problem it uniquely solves — regressions that only appear under production traffic shapes, memory growth over days, and the "we cannot reproduce it" bucket — and by the fact that a differential profile against last week is the fastest known way to find a performance regression introduced by a deploy.

What did OpenTelemetry ship for profiles, and would you build on it today?

OTLP Profiles reached public alpha in March 2026: a pprof-derived data model normalised for the wire with deduplicated stacks and dictionary tables — roughly 40% smaller — timestamped samples, shared resource attributes, and the ability to carry trace and span IDs so a slow span links to the stacks that ran during it. Collection is via an eBPF agent that runs as a Collector receiver and profiles every process on a host with automatic Go symbolization, plus a pprof receiver for applications that already expose endpoints. I would pilot it now on non-critical paths and keep an existing profiler for anything I depend on, because the project itself says alpha means do not build critical workflows on it yet. What I would not do is design a bespoke profiling pipeline in 2026, since the standard is clearly converging here.

How do profiles connect to traces, and why does that matter?

Samples can carry the trace ID and span ID that were active when the stack was captured, which means a backend can answer "show me the CPU profile for just the requests in this slow trace" or "profile only the requests for tenant X". That is qualitatively different from a whole-process profile, because in a multi-tenant service the interesting 1% of traffic is invisible in an aggregate. Practically, the workflow becomes: SLO alert fires, exemplar takes you from the metric to a slow trace, the trace shows which service and span, and the span links to the flame graph of exactly that work. Being able to describe that four-step path end to end — and noting that each hop depends on shared resource attributes and consistent IDs — is what a lead-level answer on correlation looks like.

How do you find a memory leak in production?

First confirm it is a leak and not a cache or a tuning artefact: a leak shows monotonic growth in live heap across GC cycles, whereas a large but stable working set is just configuration. Then take in-use heap profiles at two points hours apart and diff them, which points at the allocation sites of objects that survived — this is where allocation profiles alone mislead, because high churn with prompt collection is a GC-pressure problem, not a leak. If the runtime supports it, a heap dump gives dominator trees and retention paths, which answer "what is holding a reference" rather than "who allocated it". Common culprits are unbounded caches without eviction, event subscriptions or listeners never removed, thread-locals on pooled threads, and native memory held by a client library that is never disposed. I would also check whether the growth correlates with a deploy, since a diff against the previous version is usually faster than reading heap dumps.

Why does symbolization matter and how do you get it right?

Because without symbols a flame graph is a wall of hexadecimal addresses and is useless exactly when you need it. Release builds are usually stripped for size, containers rarely ship debug info, and JIT-compiled code needs a runtime map that only exists while the process lives. The fixes are all upstream of the incident: keep build IDs in binaries, publish debug symbols to a symbol server or keep a debug package alongside each image, enable on-target symbolization where the collector supports it — the OTel eBPF agent does this for Go — and for JIT runtimes make sure the profiler runs in-process or with the runtime's map file. I treat symbol availability as a release-engineering requirement with an owner, because it is invisible until the day it costs you an hour.

Where does profiling fit relative to tracing and metrics in a debugging workflow?

Metrics tell me something is wrong and how widely; traces tell me where in the call graph the time or the error is; profiles tell me which code inside that hop is responsible. They narrow in that order, and each step reduces the search space by roughly an order of magnitude. Skipping steps is what causes flailing: profiling a whole fleet before knowing which service is slow is a needle-in-haystack exercise, and staring at traces when the problem is a single hot function wastes time you could have spent on a differential flame graph. I would also note that the causality runs both ways — profiling sometimes reveals that a service is wasting CPU that never shows up as latency until a traffic spike, which is a capacity finding rather than an incident.

Is it safe to profile production? How would you convince a nervous team?

Yes, with a sampling profiler at a low frequency, and the way to convince people is to measure rather than argue: run a load test with profiling off and on and show the latency and CPU deltas, which typically land around 1%. I would start on one non-critical service, with a documented kill switch, and roll forward from evidence. The genuine risks worth acknowledging are that some profilers need privileged access or a kernel capability, that allocation profiling at high rates is much more expensive than CPU sampling, and that heap dumps — which are not sampling — can pause a process for seconds and must be treated as a deliberate, coordinated action. Being the person who names the real risks rather than dismissing them is what gets the change approved.

What's the difference between a flame graph, an icicle graph and a flame chart?

A flame graph is aggregated stacks drawn with callers at the bottom, width equal to share of samples, x-axis sorted for merging. An icicle graph is the same data drawn top-down, which is common in browser and JVM tooling and is purely a rendering choice. A flame chart is genuinely different: the x-axis is time, each box is an individual sample or event in chronological order, and it is what browser devtools show for a recorded session. The distinction matters because the questions they answer differ — flame graphs answer "where does the resource go overall", flame charts answer "what happened in this specific 200 ms" — and mixing them up leads to the timeline misreading that trips people up in interviews.

07Pipelines & the Collector

Once instrumentation is in place, the telemetry pipeline becomes the most strategically important component you own, and this is the unit where lead-level candidates separate themselves. The OpenTelemetry Collector is a standalone process that receives telemetry, transforms it, and exports it, and the reason to insist on one — rather than letting applications export straight to a vendor — comes down to five arguments you should be able to give in ten seconds each:

  • Decoupling. Applications know one endpoint: the local Collector. Changing vendors, adding a second backend, or splitting traffic becomes a config change in one place rather than a redeploy of two hundred services.
  • Credentials. The vendor API key lives in the Collector, not in every application's environment, which shrinks the secret's blast radius from hundreds of processes to one deployment.
  • Buffering and retry. The Collector absorbs backend outages with a queue and exponential backoff, so a vendor incident does not become your incident. With a persistent queue on disk it survives its own restarts.
  • Enrichment. Kubernetes metadata, cloud resource attributes, environment tags — added once, consistently, by k8sattributes and resourcedetection, rather than by every team getting it slightly wrong.
  • Cost and safety control. Sampling, filtering, deduplication, aggregation and PII redaction applied centrally, in minutes, without a release. This is the lever, and it is why the pipeline is where the money is saved.

Internally the Collector is four component types wired into named pipelines: receivers (OTLP, Prometheus scrape, filelog, Jaeger, the eBPF profiling agent), processors (batch, memory limiter, filters, transforms, tail sampling), exporters (OTLP onwards, Prometheus remote write, object storage, vendor-specific), and connectors, which are the underrated one: a connector is an exporter on one pipeline and a receiver on another, so it turns one signal into another. The spanmetrics connector generates RED metrics from spans, which means you get request rate, error rate and latency histograms for every service with no metric instrumentation at all; servicegraph builds a dependency graph with edge latencies from the same spans. Both are standard answers to "how do you get metrics coverage across a large estate quickly?"

# A gateway Collector, in the order the components actually run.
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }

      processors: [memory_limiter, k8sattributes, transform/hygiene, filter/noise, batch]
      exporters: [otlp/vendor, spanmetrics]

Processor order is semantics, not style. memory_limiter goes first because its job is to refuse data before anything downstream allocates for it; put it after batch and you have already built the batch that kills you. batch goes last because batching is an export optimisation and everything upstream should see individual records. Enrichment goes before filtering so filters can match on the attributes enrichment added. Getting asked "what order do you put processors in and why?" is common, and it is a fast credibility check.

The deployment topology question is equally standard. The agent pattern runs a Collector next to every workload — a DaemonSet on each node, or a sidecar — so it can add host and pod metadata, absorb the application's exports over localhost, and fail independently. The gateway pattern runs a horizontally scaled pool that does the heavy, stateful work: tail sampling, aggregation, fan-out to multiple backends, egress through one network path. Almost every serious deployment runs both, agents feeding gateways, and the reason is that tail sampling and cross-service aggregation need all of a trace in one place while enrichment needs to happen where the data is born.

OTTL — the OpenTelemetry Transformation Language — is the scripting layer that makes all of this expressive: statements with a path syntax over the data model, conditions with where, and functions for setting, deleting, hashing, converting and matching. In 2026 it gained lambda-powered functions and context inference in the filter processor, which removes a lot of the boilerplate of saying which context you are operating in. Treat OTTL as production code: it runs on every record, a bad regex is a CPU incident, and it belongs in version control with tests.

Two more things a lead should mention. First, monitor the Collector itself — refused and dropped spans, queue size, exporter failures, memory — because a silently dropping pipeline looks exactly like a healthy system with less traffic, and that is the worst possible failure mode. Second, build a minimal binary: the OpenTelemetry Collector Builder produces a distribution containing only the components you use, which shrinks the image, the attack surface and the supply chain you have to justify to a security review. The upstream cadence is fast — the September 2026 releases are around v1.66.0 core with the v0.160.0 contrib line — so pin versions and treat Collector upgrades like any other infrastructure dependency.

Interview trap

An unbounded queue is not resilience, it is a delayed OOM. Candidates often say "the Collector buffers, so a backend outage is fine" without naming the limits. In reality: the sending queue has a fixed size, and when it fills the Collector applies backpressure or drops; without a persistent queue everything in memory is lost on restart, which is precisely when you most want the data; and with memory_limiter misconfigured you get a crash loop instead of graceful degradation. The correct answer names the three settings — queue size, persistent storage, memory limiter — and states the deliberate choice: telemetry is lossy by design and should never be allowed to take down the application or the node. The corollary trap is a Collector that is a single point of failure for the whole estate; if it goes down and applications block on export, you have coupled your availability to your observability, which is the wrong direction.

Try it

1. Run a Collector locally, point a service at it, then stop the backend and watch the queue metrics, the retry backoff and — after restarting the Collector — whether data survives with and without file_storage. 2. Add the spanmetrics connector to a service that has traces but no metrics, and build a RED dashboard from the generated metrics alone.

Solution sketch

In (1) you should see otelcol_exporter_queue_size climb, retries back off exponentially, and then otelcol_exporter_send_failed_spans increment once the queue saturates; with the in-memory queue a restart loses everything, with file storage it drains after recovery. That experiment is the whole argument for persistent queues, and it takes ten minutes. In (2) you get request rate, error rate and latency histograms per service and route without touching application code — note the caveats you should state unprompted: the metrics are computed post-sampling unless you place the connector before the sampler, and the dimensions you add become metric labels, so the cardinality rules from unit 04 apply directly.

Interview Q&A

Why run a Collector at all instead of exporting straight to the backend?

Five reasons I would give in order: decoupling, so switching or adding a backend is one config change instead of two hundred redeploys; credential containment, so the vendor key lives in one deployment; buffering and retry, so a backend outage does not become an application problem; consistent enrichment with Kubernetes and cloud metadata; and central control of cost and privacy through sampling, filtering and redaction that can ship in minutes. The counter-argument is one more component to run and monitor, and for a very small estate direct export is legitimately simpler. The moment you have more than a handful of services, or any compliance requirement about what leaves your network, the Collector stops being optional.

What order do processors go in, and why does it matter?

memory_limiter first, because its entire purpose is to refuse work before anything downstream allocates memory for it. Then enrichment such as k8sattributes and resourcedetection, because later stages want to filter and route on what enrichment adds. Then transforms and filters, so you drop and redact before paying to batch and export. Then sampling decisions, and batch last, immediately before the exporter, since batching is purely an export efficiency concern. Getting it wrong is not a syntax error, it is a subtle behavioural bug: batching before limiting means the limiter sees fewer, larger allocations and reacts too late, and filtering before enrichment means your filter conditions cannot see the attributes they need.

Agent, gateway, or both?

Both, in a two-tier topology. Agents run per node or as sidecars so applications export over localhost — cheap, resilient to network problems, and the only place where host and pod metadata can be added accurately — and they do light work: enrichment, batching, forwarding. Gateways run as an autoscaled pool doing the stateful and expensive work: tail sampling, cross-service aggregation, fan-out to several backends, and controlled egress through a single network path where security can inspect it. The constraint that forces the split is tail sampling: all spans of a trace must reach the same gateway instance, so tier one uses a load-balancing exporter that routes by trace ID. For a small estate a single gateway tier is fine, and I would say so rather than over-engineering.

What is a connector and give me two you'd actually deploy?

A connector is a component that acts as an exporter on one pipeline and a receiver on another, so it converts or derives one stream from another inside the Collector. The two I deploy are spanmetrics, which generates request rate, error rate and duration histograms from spans and gives an entire estate RED metrics without any metric instrumentation, and servicegraph, which builds a service dependency graph with per-edge latency and error rates from the same span stream. The caveats I would raise unprompted are that both compute from whatever spans reach them, so sampling upstream biases the numbers, and that every dimension you add becomes a metric label with the usual cardinality consequences. Used carefully they are the fastest way to give a hundred services a baseline dashboard.

How do you make the pipeline resilient to a backend outage?

A sending queue with an explicit size, retry with exponential backoff and a bounded elapsed time, and persistent file storage for the queue so an in-flight buffer survives a Collector restart — which matters because restarts and outages correlate. I set the memory limiter so the Collector sheds load rather than OOMs, and I accept explicitly that telemetry is lossy: under sustained backend failure, data is dropped, and that is preferable to unbounded memory growth or to backpressure reaching the application. On the application side, exporters must be non-blocking with their own bounded queue so a Collector problem can never add latency to a user request. Finally I alert on the Collector's own dropped and failed counters, because otherwise a silently failing pipeline looks like a quiet system.

What is OTTL and where do you draw the line on using it?

OTTL is the Collector's transformation language: path-based statements over the telemetry data model with conditions and functions, used by the transform, filter and routing processors to rename attributes, delete or hash sensitive fields, template high-cardinality span names, and drop noise. It is the fastest lever you have, because a pipeline change ships in minutes while an instrumentation fix takes a release cycle. The line I draw is that OTTL should not become a permanent shadow instrumentation layer: rules that fix a genuine upstream defect are fine and should be tracked with a removal ticket, but business logic in the pipeline is invisible to the developers reading the code and will confuse someone six months later. I treat OTTL as production code — reviewed, version-controlled, and load-tested, because a pathological regex applied to every record is a CPU incident waiting to happen.

How do you monitor the observability pipeline itself?

The Collector exposes its own metrics, and the four I alert on are refused and dropped records by signal, exporter send failures, queue size relative to capacity, and process memory against the limiter's threshold. I also watch the ratio of accepted to exported records per pipeline, because a steadily widening gap is the signature of silent dropping. On top of that I run synthetic end-to-end checks: emit a known span or metric on a schedule and assert it becomes queryable in the backend within an SLO, which is the only test that covers the whole path including the vendor. And I make sure the pipeline's own telemetry does not go through itself in a way that makes failures invisible — that circularity is a classic gap.

How would you migrate from a proprietary agent to OpenTelemetry with no downtime?

Run both in parallel and cut over per service, never big bang. Concretely: deploy the Collector with two exporters, one to the incumbent vendor and one to the new destination, so both backends receive the same data and dashboards can be compared side by side. Then replace the proprietary agent with OTel instrumentation service by service, starting with something low-risk, verifying that key dashboards and alerts produce the same numbers before moving on. The gotchas to plan for are attribute name differences between the vendor's model and semantic conventions, which OTTL can bridge during the transition, and duplicated spans if both agents run at once. The migration ends when the old exporter is removed, and I would keep the parallel period short enough that nobody starts depending on both.

How do you scale the Collector, and what breaks first?

Stateless tiers scale horizontally on CPU, and CPU is usually the binding constraint because of serialisation, compression and OTTL evaluation. What breaks first is memory in the tail-sampling tier, because it buffers every in-flight trace: memory is roughly the number of concurrent traces times spans per trace times span size, so num_traces and decision_wait are the two dials that matter and both trade recall for RAM. The second thing that breaks is routing: if trace-ID-aware load balancing is misconfigured, spans of one trace land on different instances and sampling decisions become inconsistent, which shows up as mysteriously incomplete traces rather than as an error. I also watch for a hot receiver on a single instance from a very chatty service, which argues for spreading via the agent tier rather than letting applications hit the gateway directly.

Do you use the upstream Collector image or build your own?

I build my own with the OpenTelemetry Collector Builder, containing only the receivers, processors and exporters we actually use. The reasons are supply chain and size: the contrib distribution carries hundreds of components, each one code you are shipping into a privileged part of your infrastructure, and a security review is much easier when the manifest is ten components long. A custom build also makes the upgrade story explicit, since you pin component versions deliberately rather than inheriting whatever contrib moved. The cost is a small build pipeline to maintain and the discipline of adding components consciously — which is arguably a feature. For a proof of concept I would start with the contrib image and switch before production.

08Correlation & semantic conventions

Correlation is what turns four signals into one system, and it is entirely mechanical: it works when identifiers and attribute names agree, and it fails silently when they do not. There are exactly three joins that matter, and you should be able to name them without hesitating.

  • Trace ID. Joins spans to log records to profile samples. Everything within one request finds everything else through this.
  • Exemplars. Join metrics to traces, by attaching a trace ID to a histogram bucket observation. This is the only bridge from an aggregate to a concrete example.
  • Resource attributes. Join everything to the thing that produced it, and to everything else that thing produced. service.name plus service.version plus k8s.pod.name is what lets you ask "show me all telemetry from the pods running the new version".

The reason the third one works at all is semantic conventions: a shared, versioned dictionary of attribute names, units and meanings. Without it, one team writes http_status, another statusCode, a third http.response.status_code, and no dashboard, processor or vendor feature can be written once. With it, a Collector processor, a backend's automatic service map and a community dashboard all work on your data with no configuration. The current release is semantic conventions 1.44.0 (4 August 2026), and the release cadence is roughly monthly.

Conventions carry per-attribute stability levels, and knowing the ladder is a real differentiator because it tells you what you may depend on:

The newer structural idea is entities. A Resource today is a flat bag of attributes describing "the thing that emitted this", but a bag cannot express that a pod belongs to a deployment which belongs to a cluster, nor can it express that the pod was created at 09:14 and deleted at 11:02. The entities work adds identity and lifecycle: entity events describe an entity appearing, changing state and disappearing, so the backend can build a real inventory rather than inferring one from whatever telemetry happened to arrive. The practical payoff is asking "what was running when this incident started?" and getting an answer even for a pod that emitted nothing — the blind spot every attribute-only model has.

One more naming discipline that pays for itself: distinguish resource attributes (immutable per process — service, version, host, pod, environment) from signal attributes (per operation — route, status, tenant). Putting a per-request value on the resource is a data-model error that some backends will accept and then produce nonsense from, because resources are used as the grouping key for the entity emitting data. And when you genuinely need an attribute that no convention covers — and you will, because business concepts are yours — namespace it with your company or domain prefix (checkout.cart.line_count), never with a bare word that might collide with a future convention.

Interview trap

Assuming everything in the registry is safe to build on. The GenAI conventions are the live example: as of mid-2026 every gen_ai attribute, span, metric and event still carries the Development stability badge — not one is stable — and in semconv 1.42.0 (June 2026) they were moved out to a dedicated repository entirely. If you build alerting and billing dashboards on gen_ai.* today, plan for renames. The general form of the trap is treating the semantic conventions as one monolithic "stable standard" rather than a registry where each attribute has its own maturity. The second trap is subtler: silently mixing conventions versions across an estate, so half your services emit http.status_code and half emit http.response.status_code, and every dashboard quietly under-counts by exactly the fraction of services on the other version. Normalising at the gateway is the cheap fix; a fleet-wide instrumentation upgrade is the real one.

In (2) the interesting result is where the chain breaks: usually no exemplars configured, so there is no way from a metric to a trace except guessing by timestamp, or log records without trace IDs because a bridge is not installed. Each broken link is a specific, cheap piece of work — enabling exemplars, installing a logging bridge, standardising resource attributes — and the audit is what turns "improve observability" from a vague objective into a three-ticket plan.

Interview Q&A

What are semantic conventions and why should a team follow them strictly?

They are a versioned dictionary of attribute names, units and meanings — http.request.method, server.address, db.query.text — so that telemetry from different languages, libraries and vendors describes the same thing the same way. Following them is what makes everything else work without configuration: Collector processors, automatic service maps, community dashboards, vendor features and the span-to-metric connectors all key off standard names. The cost of inventing your own names is invisible on day one and painful later, because every dashboard becomes bespoke and every tool integration becomes a mapping exercise. My rule is: use the convention if one exists, propose one upstream if the gap is general, and namespace your own attribute if it is genuinely business-specific.

Walk me through the stability levels and what you're allowed to depend on.

Development means it can change or be renamed without notice; release candidate means feature-complete and expected to stabilise soon; stable means no incompatible changes; deprecated means superseded but still emitted by older instrumentation. I build alerts, SLOs and billing dashboards only on stable attributes, and treat RC as usable with a review reminder. As of semantic conventions 1.44.0 in August 2026, HTTP has been stable since 1.23.0, core Kubernetes and container-registry resource attributes went stable in 1.42.0, CI/CD, VCS and process metrics are release candidates, and the entire GenAI set is still Development — which is exactly the thing to check before promising a stakeholder a stable AI-cost dashboard. Knowing that per-attribute maturity exists at all is the real point.

How do you handle an estate with mixed semantic-convention versions?

First measure it: query the distinct attribute keys per signal to see how many spellings are actually in flight, since teams always guess low. Then normalise forward at the gateway Collector with OTTL, copying legacy keys to current ones and deleting the old, so every dashboard and alert can assume one spelling from that day onward. In parallel, upgrade instrumentation service by service so the normalisation rules can eventually be deleted, and track them as debt with an owner rather than letting them ossify. Where the SDKs support it, the schema URL on the resource lets a backend do the translation for you, which is cleaner but depends on the backend implementing schema transformation. The failure to avoid is dual-spelling dashboards with an or in every query, which nobody maintains.

Resource attributes versus span attributes — what's the rule?

Resource attributes describe the entity emitting telemetry and are immutable for the process lifetime: service name, version, namespace, instance ID, environment, host, container, pod, cloud region. Span or metric attributes describe one operation or measurement: route, status code, tenant, retry attempt. The rule is that anything that varies per request must never be on the resource, because the resource is the grouping key for "who produced this" and backends index and bill on it; putting a request ID there creates a new logical entity per request. The inverse mistake, repeating service.name on every span, wastes bytes and is usually a sign that someone bypassed the SDK's resource mechanism.

What are entities in OpenTelemetry and what problem do they solve?

A Resource today is a flat attribute bag with no identity and no lifecycle, so a backend cannot tell that a pod is part of a deployment, nor when that pod started and stopped, except by inference from the telemetry that happened to arrive. Entities add explicit identity, type, hierarchy and lifecycle events — entity created, state changed, deleted — so the platform can maintain a real inventory. The practical payoff is answering "what was running when the incident started?" including for things that emitted no telemetry at all, which is the blind spot that makes post-hoc incident timelines so painful. It also cleans up the modelling of things that are not services — hosts, clusters, queues, databases — which currently get shoehorned into resource attributes.

How do you get from a metric spike to a specific slow request?

Exemplars: the histogram bucket carries trace IDs from actual observations, so the graph point is clickable straight into a trace. If exemplars are not enabled, the fallback is to query traces filtered by the same time window, service and route with a latency predicate, which works but is slower and biased by sampling. The prerequisite chain is worth stating: the SDK must record exemplars, the metric store must accept and retain them, the sampler must have kept the trace, and the UI must render them — a break anywhere means "no exemplars" with no error message. This is why I audit the correlation chain explicitly rather than assuming it works, and why tail-sampling on latency and exemplars complement each other: the exemplar is useless if the slow trace was dropped.

Where do you put business-specific attributes?

On the span for the operation they describe, namespaced under a prefix I own — checkout.cart.line_count, billing.plan.tier — never as a bare noun that might collide with a future convention, and never on the resource unless it is genuinely per-process. I keep them bounded where I intend to aggregate on them and accept unboundedness where they are only for filtering a specific case. I also treat them as a reviewed vocabulary rather than a free-for-all: a short registry in the repo, so that "tenant" means the same key everywhere and does not appear as tenant, tenant_id and customer.id in three services. That small piece of governance is what makes cross-service queries possible at all.

What is a schema URL and have you actually used one?

It is a URL emitted alongside the resource and instrumentation scope that declares which semantic-convention version the telemetry was written against, and it lets a consumer apply published transformation files to translate old attribute names into new ones automatically. In principle it removes the need for hand-written migration rules; in practice backend support is uneven, so most teams — including ones I have worked on — do the translation explicitly in the Collector with OTTL because it is visible and immediate. I would still make sure SDKs emit it, because it is free and it makes the data self-describing, and because a backend that does implement schema transformation can then do the work for you. It is a good example of a spec feature whose value depends entirely on the ecosystem catching up.

How do you correlate telemetry with deployments?

Two mechanisms. First, service.version and ideally the build SHA as resource attributes, so every signal can be grouped by version and a canary can be compared with the baseline in the same query — this is what makes "did the deploy cause it?" a filter rather than an argument. Second, deployment events as annotations in the observability system, emitted by CI/CD, so graphs show a marker at each release; the CI/CD semantic conventions reached release-candidate status in semconv 1.43.0, which makes that a standardised stream rather than a bespoke webhook. With both in place the first question of nearly every incident — what changed — is answered from a dashboard instead of from Slack archaeology. I would also feed feature-flag changes into the same annotation stream, because flags change behaviour without a deploy and are otherwise invisible.

A vendor feature needs an attribute name that contradicts the conventions. What do you do?

Emit the standard name as the source of truth, and add the vendor's name in the pipeline with a copy rule if the feature is worth having — the Collector is exactly the right place for vendor-specific accommodation, because it keeps the application code portable and makes the coupling explicit and deletable. I would not change the instrumentation to speak the vendor's dialect, because that is how you get locked in one attribute at a time and how a future migration becomes a rewrite. I would also push the requirement back to the vendor, since most of them are converging on OTLP and semantic conventions and treat such gaps as bugs. If the vendor cannot be accommodated cheaply, that is a data point in the procurement conversation rather than an instrumentation decision.

09SLOs, error budgets & alerting

Everything so far was about being able to answer questions. This unit is about deciding when to wake someone up, and it is the part of observability that is really an organisational design problem wearing a technical hat. The framework is small and worth knowing exactly.

An SLI is a ratio: good events over valid events, measured at a boundary the user actually crosses. An SLO is a target for that ratio over a window — 99.9% of checkout requests succeed over 28 days. The error budget is the complement: 0.1% of requests, which over a month of ten million requests is ten thousand failures you are allowed to spend. That reframing is the whole point. Reliability stops being a moral question ("we must not have errors") and becomes a budget you allocate: spend it on risky deploys, on chaos experiments, on a migration — and when it is exhausted, the error budget policy says what changes, usually a freeze on feature releases until reliability work restores the margin.

That table is the most useful thing you can put in front of a stakeholder who asks for five nines: 26 seconds a month is less than the time it takes a human to read a page and open a laptop, so it is a statement about automation, not about effort. It also exposes the dependency arithmetic — a service that synchronously depends on three others, each at 99.9%, cannot itself exceed roughly 99.7% without redundancy or graceful degradation, because their failures compound.

Latency SLIs must be expressed the same way — as a ratio, not a percentile. "p99 < 300 ms" is not an SLI, because percentiles cannot be aggregated across windows or instances (unit 04) and because it says nothing about how many users were affected. "99% of requests complete in under 300 ms" is an SLI: count the requests under the threshold, divide by valid requests, and it composes cleanly. That reformulation is one of the most reliable "have you actually done this?" checks in an interview.

Then there is the alerting mechanism, and the modern answer is multi-window, multi-burn-rate alerting. Burn rate is how fast you are consuming the error budget relative to the rate that would exactly exhaust it over the SLO window: burn rate 1 means you will finish the budget precisely at the end of the period; burn rate 14.4 means you will finish it in 2% of the period. You alert on burn rate rather than on raw error rate because it automatically scales with your SLO and traffic, and you use two windows per alert — a long one for signal and a short one to confirm the problem is still happening — so that alerts fire fast on catastrophes, fire slowly on slow leaks, and reset promptly when the incident ends.

The other half of alerting is editorial: alert on symptoms, not causes. A page should mean "users are being hurt, or will be within minutes, and a human must act now". CPU at 90% is not that — it might be perfectly fine, and if it is hurting users then the SLO alert already fired with better context. Cause-based signals belong on dashboards and in tickets, where they help diagnosis without waking anyone. The exceptions worth naming are predictive alerts for things with long lead times and hard walls: a disk that will fill in four hours, a certificate expiring in seven days, a licence or quota approaching its ceiling. Those are legitimately cause-based because the symptom, when it arrives, is total and unrecoverable in the moment.

Alert quality is measurable and should be managed like any other product surface. Track precision (what fraction of pages led to action), track pages per on-call shift, and review both in every operational review. The healthy targets to quote: fewer than roughly two pages per shift, precision above about 80%, and every alert carrying a link to a runbook and a dashboard. An alert nobody can act on is worse than no alert, because it trains people to ignore the ones that matter — and once that habit exists, your mean time to detect quietly doubles regardless of how good your telemetry is.

Interview trap

Setting an SLO at 100%, or setting it from what the system currently does. A 100% target makes the error budget zero, which makes the whole framework meaningless and guarantees you are always in violation. Equally wrong is measuring current performance and declaring that the SLO: SLOs come from what users need and what the business will pay for, and the current number is an input to the conversation, not the answer. The subtler trap is the wrong measurement point — measuring at the load balancer means you miss failures that never reach it, like DNS or CDN problems, so the graphs are green while customers cannot connect. The strongest answer combines server-side SLIs for precision with synthetic probes and real-user monitoring for the part of the journey your servers cannot see, and states clearly that a green dashboard during a customer-visible outage is a measurement-boundary bug.

Try it

1. Write a real SLO for one service: the SLI as a ratio with an explicit definition of "valid" and "good", the target, the window, and the error budget policy — one paragraph on what happens when the budget is exhausted. 2. Audit your last month of pages: for each, was it symptom or cause based, did the responder take action, and would a burn-rate alert have fired earlier or later?

Solution sketch

The hard part of (1) is always "valid": do you count health checks, bot traffic, requests that failed because the client disconnected, 4xx responses caused by bad input? Writing those exclusions down is 80% of the work and is exactly what interviewers probe, because it is where teams quietly game their own numbers. In (2) the typical finding is that a third of pages were cause-based and non-actionable — disk, CPU, a restarted pod — and that a burn-rate alert would have fired later than a threshold alert on a fast incident but would have suppressed the entire class of brief blips that nobody needed to see. Bringing the actual numbers from such an audit to an interview is far more persuasive than reciting the framework.

Interview Q&A

Define SLI, SLO, SLA and error budget, and how they relate.

An SLI is a measured ratio of good events to valid events at a user-facing boundary; an SLO is the internal target for that ratio over a window; an SLA is a contractual commitment with financial consequences, and it should always be looser than the SLO so you have room to react before money is at stake. The error budget is one minus the SLO, expressed as an allowance of failures over the window, and it is the mechanism that makes the whole thing operationally useful: it converts reliability from an absolute into a resource you spend deliberately on release velocity and risk. The policy attached to it — what the team does when the budget is exhausted — is what gives it teeth; without a policy, an SLO is a dashboard nobody acts on.

How do you choose an SLO target?

From the user's need and the cost of meeting it, never from what the system currently achieves. I start by asking what users notice and what the business loses when it breaks, then look at current performance as an input, then price the next nine — each one typically costs an order of magnitude more in redundancy, automation and engineering time. The dependency arithmetic constrains the answer: a service synchronously depending on three others at 99.9% each cannot reliably beat about 99.7% without redundancy or graceful degradation, so the honest conversation is often about degrading rather than about adding nines. And I keep the target below 100% deliberately, because a zero error budget removes every incentive to ship and makes the framework unusable.

Explain burn-rate alerting and why it beats threshold alerting.

Burn rate is the ratio of your current error rate to the rate that would exactly exhaust the error budget over the SLO window, so an alert on burn rate scales automatically with the SLO and with traffic and expresses severity in terms of consequence rather than of an arbitrary number. Multi-window means each alert combines a long window for signal quality with a short window for currency, so it fires quickly on a catastrophe and stops firing quickly when the incident ends, rather than smearing for an hour. The standard configuration is 14.4× over 1 hour with a 5-minute confirmation and 6× over 6 hours with 30 minutes as pages, and 1× over 3 days as a ticket. It beats a fixed threshold because a 1% error rate might be catastrophic for one service and unremarkable for another, and because it naturally suppresses brief blips that consume a negligible slice of budget.

Why is "p99 < 300 ms" a bad SLI?

Because a percentile is not a ratio of good events to valid events, so it does not compose: you cannot aggregate p99 across instances or across time windows correctly, and you cannot build an error budget from it. It also hides the size of the affected population — p99 exceeding the threshold tells you nothing about whether 10 or 10,000 users were slow. The correct formulation is "99% of valid requests complete in under 300 ms", which is a count of good over valid, aggregates cleanly, and converts directly into an error budget of slow requests. With a histogram you compute it straight from the bucket at the threshold, which is also cheaper than computing a quantile.

Symptom-based or cause-based alerting?

Symptom-based for anything that pages, because a page should mean users are being hurt and a human must act now; the symptom is also stable while the causes change constantly, so symptom alerts do not need maintenance every time the architecture moves. Cause-based signals belong on dashboards and in tickets, where they accelerate diagnosis without waking anyone. The exceptions I would defend are conditions with a long lead time and a hard wall — a disk filling in four hours, a certificate expiring next week, a quota approaching its limit — because by the time the symptom appears it is total. In practice I aim for a small number of SLO-derived pages per service plus that short list of predictive alerts, and everything else demoted.

Your team gets 40 pages a week and ignores most of them. What do you do?

Treat it as an incident in its own right, because alert fatigue destroys detection time far more effectively than any missing dashboard. First, measure: classify a month of pages by actionability and by alert rule, and you will usually find that five rules produce most of the noise. Then delete or demote aggressively — non-actionable alerts go to a dashboard or a ticket queue, flapping alerts get a longer for duration or a burn-rate reformulation, and duplicates get grouped and inhibited in the alert manager so one incident produces one page. Then rebuild upward from SLOs so the remaining pages mean something, and put a standing agenda item in the operational review to keep it from regrowing. I would also make the on-call load visible to leadership as a number, because that is what gets the reliability work funded.

How do you set SLOs for an internal service nobody uses directly?

By tracing the dependency to the user-facing journeys it supports and deriving a target from what those journeys need — if checkout needs 99.9% and depends synchronously on the auth service for every request, auth needs a materially better number than checkout does. If several journeys with different needs depend on it, I take the strictest, or split the SLO by API surface or by criticality class rather than pretending one number fits. Where the dependency is asynchronous or degradable — a recommendation service that can be skipped — the required target drops sharply, and saying that explicitly is often the most valuable output of the exercise. The failure mode I avoid is every internal team inventing a target from their own comfort level, because those numbers do not compose into anything a user experiences.

How do you handle SLOs during a planned migration or a known-risky period?

I make the spending explicit rather than suspending the framework. If a migration is expected to consume budget, we agree in advance how much, we do the work while the budget allows it, and we stop when it is gone — that is precisely what the budget is for and it turns a vague risk conversation into an arithmetic one. I do not silence the SLO, because then you lose the ability to notice that the migration is going worse than planned. What I do adjust is the alerting mode: temporarily route ticket-level burn alerts to the migration channel rather than the on-call rotation, keep the fast-burn page intact, and make the rollback trigger a named budget threshold. If the budget is already exhausted before the migration, the policy answer is that the migration waits or is de-risked further, which is an uncomfortable but healthy conversation to have on the record.

Where should you measure the SLI: client, load balancer, or service?

As close to the user as you can measure reliably, which usually means combining sources. Server-side metrics are precise and cheap but blind to everything that fails before reaching you — DNS, CDN, TLS, network — so a purely server-side SLI can be green during a total outage. Load-balancer metrics catch more and are a good default primary. Real-user monitoring from the client is closest to the truth but noisy, subject to ad-blockers and client-side variance, and includes conditions you do not control. Synthetic probes from outside give you a continuous, controlled signal including on low-traffic paths, at the cost of not reflecting real user distribution. My usual answer is: SLO on load-balancer or server-side ratios for precision, plus synthetic checks and RUM as independent detectors whose disagreement with the SLO is itself an alert-worthy condition.

How do you alert on low-traffic services where ratios are meaningless?

Ratios become statistically unstable at low volumes — one failure out of five requests is a 20% error rate that means nothing — so I do three things. I widen the windows so the denominator is large enough to be meaningful, accepting slower detection as the honest trade. I add synthetic traffic so there is a guaranteed floor of requests to measure, which also gives coverage during genuinely idle periods when a broken service would otherwise look perfect. And I add absolute-count conditions alongside the ratio, so an alert requires both a bad ratio and a minimum number of failures. For genuinely low-traffic, low-criticality services I would also question whether a page is warranted at all, versus a ticket and a daily check, because carrying pager load for something with five users a day is a poor trade.

10The production debugging method

Telemetry is the equipment; this unit is the technique. Under pressure, most people debug by pattern-matching — "this looks like that time the cache broke" — which is fast when it works and catastrophic when it does not, because it produces confident action on an unexamined hypothesis. The alternative is a loop you can run out loud, which is exactly what a good interviewer is listening for: observe → scope → hypothesise → predict → test → narrow, repeated until the search space is one component.

The first question is always "what changed?", because the overwhelming majority of incidents are caused by a change, and changes are enumerable in a way that the space of possible bugs is not. Deploys, config changes, feature-flag flips, infrastructure updates, certificate rotations, dependency releases, data migrations, traffic pattern shifts, and someone else's outage. If you have service.version on your telemetry and deploy annotations on your graphs (unit 08), this is a thirty-second question. If you do not, it is a twenty-minute Slack excavation, which is why that instrumentation work pays for itself in a single incident.

The second question is "what is the scope?", and it is pure differential diagnosis: find the dimension along which the world splits into broken and working. Is it all users or some? All regions or one? All versions or only the canary? All tenants or only the largest? All endpoints or only the ones that write? Started abruptly at 09:14 or ramped over an hour? Each answer eliminates whole classes of cause. An abrupt start with a sharp edge says "a change happened"; a gradual ramp says resource exhaustion, a leak, or growth crossing a threshold; a periodic pattern says a cron job, a cache expiry, or a scheduled batch. This is where high-cardinality telemetry earns its keep, because the discriminating dimension is frequently one nobody dashboarded.

Two pieces of theory make you dramatically better at latency incidents. The first is Little's law: for a stable system, the mean number of requests in flight equals arrival rate times mean latency (L = λ × W). It is trivial arithmetic and it constantly settles arguments — if you serve 500 requests per second at 200 ms, you have 100 requests in flight on average, so a connection pool of 20 is not a tuning detail, it is the bottleneck. The second is the utilisation knee: queueing delay grows non-linearly with utilisation, so a resource at 80% is not "80% as bad as 100%" — it is where latency starts to rise steeply, and past about 90% it goes vertical. This is why saturation is the leading indicator and why "we still had 15% CPU headroom" explains nothing.

The third piece is tail latency amplification. If a request fans out to 20 backends and waits for all of them, then even a 1-in-100 slow backend response makes roughly 18% of requests slow — the tail of the components becomes the median of the whole. That single calculation explains why "our p99 is fine but the page is slow" happens, and it points at the standard mitigations: hedged requests, tied requests, cutting the fan-out, or degrading gracefully rather than waiting.

The discipline that separates leads from strong seniors is mitigate before you diagnose. The instinct of a good engineer is to understand the problem; the responsibility of an incident lead is to stop the bleeding and then understand it. If a rollback restores service, roll back — the root cause investigation is better done on a healthy system with a preserved artefact than on a burning one. The corollary is that you must capture evidence before you destroy it: a restart is a mitigation that deletes the crime scene, so take the heap dump, the thread dump, the profile and the current connection state first, ideally as a one-command script that on-call can run without thinking. "Restart the pod" and "we never found out why" appear together in postmortems with depressing regularity.

Two more rules. Change one thing at a time, and record it: parallel changes during an incident make causality unrecoverable and are the main reason postmortems end with "we think the third change fixed it". And time-box hypotheses — if a line of investigation has not produced evidence in ten minutes, park it, say so out loud, and move to the next one. In a group debugging session, having someone maintain the list of live hypotheses and their status is the single cheapest improvement to incident quality.

Interview trap

Confirmation bias with a deploy. "It started right after the deploy" is powerful evidence and also the single most common wrong turn, because deploys are frequent and correlation is cheap. Two disciplines protect you: check whether the change is even capable of causing the symptom (a front-end CSS release cannot cause database connection exhaustion), and check the version dimension of the SLI — if the errors are equally present on old and new pods, the deploy is a coincidence and you have just saved yourself an hour. The related trap is fixing the alert instead of the problem: raising a threshold or adding a retry makes the symptom disappear while the failure continues, and it is exactly how a metastable failure — where a retry storm keeps a recovered system down — gets built. If your mitigation is "increase the timeout" or "add more retries", say out loud why that will not simply move the queue somewhere less visible.

Solution sketch

The value of (1) is almost never the fix; it is the list of things you discovered you could not see — no per-instance breakdown, no pool saturation metric, no way to tell your latency from a dependency's — and each of those is a concrete ticket. Latency injection is the most instructive failure to inject because it produces the widest range of secondary symptoms: queue growth, pool exhaustion, retry amplification, and eventually errors in services that never touched the injected dependency. In (2) the usual discovery is that the winning hypothesis was tested third or fourth and that the first two were pursued for far too long because nobody had stated what evidence would rule them out — which is the argument for saying predictions out loud before running the query.

Interview Q&A

Walk me through how you debug a production incident you know nothing about.

I start by establishing impact and scope rather than cause: which SLO is burning, since when, how many users, which regions and versions. Then "what changed" — deploys, flags, config, infrastructure, upstream providers — because most incidents are change-induced and the change list is finite. Then I run differential diagnosis: find the dimension that separates broken from working, and use each answer to eliminate classes of cause. I state hypotheses explicitly with the prediction that would confirm or falsify each, test the cheapest first, and time-box anything that is not producing evidence. Throughout, I separate mitigation from diagnosis: if rolling back or shedding load restores service, I do that first and investigate afterwards, having captured a dump or profile so the evidence is not lost.

Latency is up but CPU, memory and error rates all look normal. Where do you go?

Flat CPU with rising latency means waiting rather than computing, so I stop looking at utilisation and go to saturation and waiting: connection pool usage and wait time, thread pool queue depth, lock contention, and the duration of downstream client spans compared with the server span duration. A wall-clock or off-CPU profile tells me directly what the threads are blocked on, which is the fastest path when the metrics are ambiguous. I also check whether the latency is bimodal rather than uniformly shifted, because two humps mean two code paths — cache hit versus miss, or one bad replica — while a uniform shift points at a shared dependency. And I check the request mix, since a change in the shape of traffic, such as more expensive queries from one tenant, moves latency without moving any error signal.

What is Little's law and when has it actually helped you?

For a stable system, the average number of items in the system equals arrival rate times average time in the system. It helps because it turns capacity arguments into arithmetic: at 500 requests per second and 200 ms average latency there are 100 requests in flight, so a pool or thread limit of 20 is provably the constraint, not a tuning preference. It also predicts the feedback loop that makes incidents non-linear — if latency doubles because a dependency slowed down, concurrency doubles at the same arrival rate, and you exhaust pools and threads that were sized for the old latency. That is the mechanism behind most "one slow dependency took down five services" postmortems, and being able to state it converts a war story into an explanation.

Why is 80% utilisation a warning rather than comfortable headroom?

Because queueing delay is non-linear in utilisation: as a resource approaches saturation, the wait time grows steeply, so the difference between 70% and 90% is far more than 20% more latency. Practically that means utilisation is a poor alerting signal on its own, and the useful signals are saturation measures — queue depth, wait time, run-queue length, pool waiters — which move earlier and more sharply. It also means capacity planning should target the knee rather than the ceiling, and that autoscaling on CPU alone reacts too late for latency-sensitive services. When someone says "we had headroom" I want to know headroom in what: a service can be at 50% CPU and completely saturated on a connection pool or a single-threaded event loop.

Explain tail latency amplification and what you do about it.

When one request fans out to many backends and must wait for all of them, the slowest response determines the user's latency, so the probability of hitting a slow component compounds with fan-out — with 20 parallel calls and a 1% chance of a slow response each, roughly 18% of requests are slow. The consequence is that the component p99 becomes the user-facing median, which is why aggregate component dashboards can look healthy while the page is slow. Mitigations, in the order I would consider them: reduce fan-out or make calls optional and degrade gracefully; hedged or tied requests, where a second copy is sent after a short delay and the first response wins; tighter per-call timeouts with fallbacks; and caching to remove calls entirely. The trade-off with hedging is extra load, so it needs a cap and it must never be combined naively with aggressive retries.

What's a metastable failure and how do you get out of one?

It is a state where the original trigger has gone but the system stays down because of a self-sustaining feedback loop — classically retries. A brief dependency blip causes timeouts, clients retry, the retries multiply load beyond capacity, everything times out, and now the retries themselves keep the system saturated even after the dependency recovered. The way out is to break the loop rather than to add capacity: shed load aggressively, disable or drastically reduce retries, open circuit breakers, drain queues, and bring capacity back gradually rather than all at once, because a full restart with a cold cache and a full queue re-enters the same state. The prevention is designed in — retry budgets rather than fixed counts, exponential backoff with jitter, circuit breakers, and load shedding that returns errors quickly instead of queueing.

How do you decide between rolling back and pushing a fix forward?

Default to rollback, because it is the action with the best-understood outcome and the shortest path to a healthy system, and because time-to-mitigate is the metric users experience. I push forward only when rollback is not actually safe or possible — an irreversible data migration, a schema change, a mobile client already in the wild — or when the fix is trivial, well understood and verifiable in a canary. The important discipline is deciding this early and explicitly rather than drifting into a forward fix because someone is already halfway through writing one. I also treat "can we roll back?" as a design requirement, since a system where rollback is unsafe has converted every deploy into a one-way door, and that is a much bigger problem than the incident at hand.

What evidence do you capture before restarting a sick process?

Whatever will be gone forever afterwards, in the order that is cheapest to grab: a thread or stack dump, which is nearly free and answers deadlock and starvation questions; a CPU or wall-clock profile over ten to thirty seconds; a heap dump if the symptom is memory-related and the pause is acceptable; the process's own metrics snapshot; open connection and socket state; and the last portion of logs if they are not already shipped. I want this to be one script that on-call runs without thinking, writing to durable storage with the incident ID in the filename, because during an incident nobody remembers the flags. If the process is unresponsive and customers are down, mitigation wins — but I would then say so explicitly in the postmortem, because "we restarted and never learned why" is a decision, not an accident, and if it happens repeatedly it becomes an action item.

How do you avoid confirmation bias when everything points at the recent deploy?

By demanding a mechanism and a discriminating test rather than accepting correlation. First, is the change even capable of producing this symptom — does the diff touch anything on the path in question? Second, split the SLI by version: if old and new pods fail at the same rate, the deploy is coincidental, and that single query saves an hour. Third, consider the alternatives that a deploy would mask: an upstream provider's incident, a scheduled job, a data threshold crossed, a certificate expiring. I still often roll back first as a mitigation, because it is cheap and reversible, but I keep the investigation open rather than declaring the cause proven — a rollback that does not fix the symptom is itself excellent evidence.

You cannot reproduce a bug that happens in production once an hour. What now?

Stop trying to reproduce it and instrument to catch it in the act. Concretely: make sure the failing requests are always sampled — tail sampling on error or on the specific attribute, or a debug flag propagated through baggage for the affected tenant — so every occurrence produces a full trace with attributes. Add the two or three attributes that would discriminate the failing population, since the whole game is finding what those requests have in common. Turn on continuous profiling so the window is retrospectively inspectable, and if the failure is on a code path where state matters, add a conditional dump or a targeted log at the branch. Once every occurrence produces evidence, an hourly bug is solved within a day; before that, every attempt is a guess.

11Runtime forensics: dumps & eBPF

Sometimes the telemetry narrows the problem to one process and then stops helping, because the answer is inside the runtime: a deadlock, a starved thread pool, a leak, a stuck native call, a container being throttled by a limit nobody remembers setting. This is the layer below observability tooling, and it is where interviews get concrete fast — "the pod is at 100% CPU and unresponsive, what do you actually type?" A lead is expected to have a toolbox and, more importantly, an order of operations.

The cheapest instrument is the thread dump: a snapshot of every thread's stack, taken in milliseconds, with negligible impact. Take three, ten seconds apart. If the same stacks appear in all three, threads are stuck rather than working; if two threads each hold what the other wants, you have a deadlock and most runtimes will detect and name it for you. Thread dumps are how you diagnose pool starvation, the async deadlock pattern where blocking on an asynchronous call consumes every pool thread, and the "the process is alive but serving nothing" class of failure. Next up in cost is the heap dump, which is not a snapshot but a stop-the-world serialisation of the entire live heap: seconds of pause, gigabytes of file, and a full retention graph that answers "what is holding a reference to these ten million strings". Reserve it for confirmed memory problems, take it deliberately, and expect to move the file somewhere with enough RAM to open it.

The container-era failure that catches the most people is CPU throttling. A Kubernetes CPU limit is enforced by the CFS quota: the container gets a slice of CPU time per 100 ms period, and when it exhausts the slice it is stopped until the next period — even if the node is idle. The symptom is latency spikes of tens of milliseconds with CPU utilisation reported well below the limit, because average utilisation over a minute hides being frozen for 40 ms out of every 100. The evidence is nr_throttled and throttled_usec in cpu.stat, or the container_cpu_cfs_throttled_seconds_total metric, and the fix is usually to raise or remove the limit (keeping the request for scheduling) rather than to optimise code that was never slow. Its sibling is OOMKilled: exit code 137, the kernel killing the container for exceeding its memory limit, which is a different event from a runtime's own out-of-memory error and needs a different investigation — cgroup accounting includes page cache and native allocations that the runtime's heap metrics never show.

Interview trap

Trusting host-level numbers inside a container. top, free and nproc classically report the node's CPU count and memory, not the cgroup's limits, which is how a JVM or a thread pool sized from "available processors" ends up creating 64 threads inside a container limited to one core — and then everyone blames the code. Modern runtimes are container-aware, but older ones and hand-rolled sizing logic are not, and this is still one of the most common causes of "it is slow only in Kubernetes". Always read the cgroup files, or a metric derived from them. The second trap in this unit is reaching for strace on a busy production process: ptrace-based tracing can slow a process by 10× or more and has turned a degradation into an outage more than once; the eBPF equivalents exist precisely to avoid that, and saying so is a strong signal.

Try it

1. Deliberately exhaust a connection pool: set the pool to 5, drive 50 concurrent requests, and confirm the diagnosis three ways — pool saturation metric, thread dump showing threads blocked in the pool's wait, and an off-CPU profile. 2. Set a Kubernetes CPU limit well below what a service needs, load it, and correlate the latency spikes with container_cpu_cfs_throttled_seconds_total.

Solution sketch

In (1) the three views should agree, and the point of doing all three is to learn what the same problem looks like in each tool so you recognise it under pressure: the metric shows saturation at 100%, the thread dump shows a wall of identical stacks parked in the pool's acquire method, and the off-CPU profile attributes almost all wall time to that call. Apply Little's law to size the pool properly rather than doubling it and hoping. In (2) you should see latency spikes in the tens of milliseconds while average CPU sits comfortably below the limit — the exact pattern that leads teams to "optimise" code that was never slow — and removing the limit while keeping the request makes them vanish, which is the concrete argument behind the widely-held "set CPU requests, be very careful with CPU limits" position.

Interview Q&A

A pod is at 100% CPU and not responding. What do you do, in order?

Capture before I destroy: three thread dumps ten seconds apart and a 30-second CPU profile, written to durable storage with the incident ID. Then decide mitigation — take the pod out of the load balancer rather than killing it if I can, since that preserves the evidence while stopping user impact. Then read: if the same stacks appear across dumps, threads are stuck; if the profile shows a wide plateau, it is a hot loop or an accidental O(n²); if CPU is high but the profile shows GC frames, it is memory pressure masquerading as CPU. I check the container's throttling counters too, since "100% CPU" from a host tool may be 100% of a very small quota. Only after that do I restart, and I say explicitly in the incident channel that I am about to destroy state.

How do you tell a memory leak from a memory-hungry configuration?

A leak shows live heap growing monotonically across GC cycles and never returning to a baseline; a large working set grows to a plateau and stays there. So the first evidence is the shape of live-heap-after-GC over hours, not the resident set size, which includes caches and native memory. If it is growing, I take in-use heap profiles or gcdumps at two points and diff them to find what survived, then look for retention paths — unbounded caches, un-removed event handlers, thread-locals on pooled threads, static collections, or a client library not being disposed. I also check whether the growth started with a deploy, because a version diff is faster than a heap analysis. And I separate managed from native memory early, because a container OOM-killed while the runtime heap looks healthy points at native allocations, memory-mapped files or a leaking native client.

What is CPU throttling in Kubernetes and how do you spot it?

A CPU limit is enforced by the CFS quota: the container may use a fixed amount of CPU time per 100 ms period, and once it is spent the container is frozen until the next period, regardless of whether the node is idle. The symptom is periodic latency spikes with reported CPU utilisation comfortably below the limit, because averaging hides the freezes. The evidence is nr_throttled and throttled_usec in the cgroup's cpu.stat, or container_cpu_cfs_throttled_seconds_total in Prometheus. The fix is usually to raise or remove the CPU limit while keeping the request, since requests drive scheduling and limits mostly cause this problem — that is a nuanced position, so I would explain the trade-off: without limits, a runaway container can starve its neighbours, so it depends on whether the node has good isolation and whether the workload is latency-sensitive.

Distinguish OOMKilled from a runtime out-of-memory error.

OOMKilled is the kernel terminating the container because the cgroup exceeded its memory limit — exit code 137, visible in the pod's last terminated state — and it counts everything the container uses: runtime heap, native allocations, thread stacks, memory-mapped files and, depending on the accounting, page cache. A runtime out-of-memory error is thrown inside the process when its own managed heap cannot satisfy an allocation, and it usually produces a stack trace and possibly a dump. They need different investigations: the runtime error points at the managed heap and heap profiling; the kernel kill can happen while the managed heap looks perfectly healthy, which points at native memory, off-heap buffers, too many threads, or simply a limit set below the real working set. Confusing them sends people to heap dumps when they should be reading cgroup accounting.

What does eBPF let you do that older tools didn't?

Run verified, bounded programs inside the kernel that aggregate data in kernel space, so you can answer questions continuously in production at a few percent overhead instead of the order-of-magnitude penalty ptrace-based tools impose. Practically that means production-safe answers to questions that used to require a lab: which stacks are blocked and for how long, block-I/O latency distributions, TCP connection lifetimes and retransmits, DNS resolution latency per call, and every process execution on a node. It also underpins zero-code instrumentation — OBI produces OTLP spans from kernel-observed HTTP, gRPC and SQL traffic — and the OpenTelemetry profiling agent. The constraints worth naming are that it needs privileged capabilities and a reasonably modern kernel, it sees the system rather than your application semantics, and encryption inside the process limits what protocol-level tracing can decode.

How do you debug something in a distroless container with no shell?

kubectl debug with an ephemeral container: it attaches a new container with whatever image I choose into the running pod, sharing the process namespace so I can see and inspect the target's processes without changing the pod spec or restarting anything. For node-level problems, kubectl debug node/<name> gives me a privileged container in the host namespaces. If ephemeral containers are not available, the alternatives are copying the pod with a debug image, exec-ing from a privileged sidecar, or using node-level eBPF tooling that does not require entering the container at all. The design lesson I would add is that distroless images are the right default for security and should not be abandoned to make debugging convenient, precisely because these mechanisms exist.

A service intermittently takes five seconds to connect to a dependency. Where do you look?

DNS first, because it usually is: resolver timeouts, a search-domain configuration causing multiple failed lookups per call, an overloaded cluster DNS cache, or conntrack table exhaustion producing dropped packets and a retry after a timeout that is exactly five seconds. The five-second figure is itself a clue, since it matches common resolver timeouts. I confirm with resolver latency measurement — gethostlatency or client-side DNS metrics — and check retransmit counters for packet loss. If DNS is clean, I look at TLS handshakes, connection pool churn creating a new connection per request, and SYN backlog or ephemeral port exhaustion. The design fix, once identified, is nearly always to stop resolving and connecting per request: keep a warm connection pool, cache resolution appropriately, and set connect timeouts far below the user-facing budget.

What is thread pool starvation and how does it happen in async code?

It is the state where every worker in a pool is occupied and work queues without progressing, so the process is alive but serving nothing. The classic async version is blocking on an asynchronous operation — synchronously waiting for a task whose continuation needs a pool thread to run — so each blocked thread consumes the resource its own completion requires, and under load the pool deadlocks itself. The evidence is a growing queue depth with low CPU, and thread dumps showing every worker parked in the same wait. The fixes are structural: async all the way through with no synchronous blocking on async calls, separate pools for blocking work so it cannot starve the async path, and bulkheads so one slow dependency cannot consume every worker. It is worth naming because it is a failure that looks like a hang and is invisible to CPU-based monitoring.

When is it worth taking a heap dump on a live production process?

When I have already confirmed a memory problem from metrics, when lighter tools — allocation profiles, gcdumps, runtime counters — have not identified the retainer, and when I can afford a stop-the-world pause of seconds on that instance. I reduce the impact by taking it from an instance removed from the load balancer, or from a replica reproducing the problem, and I plan where the multi-gigabyte file goes and what machine can open it, because both routinely surprise people. I would not take one reflexively during a customer-facing incident: mitigate first, then reproduce the condition on a spare instance if possible. And I would say plainly that in a container the dump may itself push the cgroup over its memory limit and get the pod killed, which is an embarrassing way to lose both the evidence and the instance.

What do you think of live debugging / dynamic instrumentation in production?

It is valuable for a specific class of problem — you need one more variable from a code path you cannot reproduce, and the alternative is a release cycle — and several vendors now offer non-breaking logpoints and snapshot capture. I would adopt it with guardrails, because it is effectively remote code execution against production: access control and audit on who can place a capture, rate limits and automatic expiry so a capture on a hot path cannot become a performance incident, redaction of captured locals since they can contain personal data, and a review requirement for anything on a critical path. I would also treat heavy reliance on it as a smell: if teams need it weekly, the real problem is that the instrumentation is too thin or the deployment cycle is too slow, and fixing those is more durable than making live capture routine.

12Incident command & postmortems

At lead and principal level, half the observability questions are really questions about how you run an outage with eight people in a channel, a VP asking for updates, and no idea yet what is wrong. The failure mode is not technical: it is six engineers debugging in parallel, nobody tracking what has been tried, two people changing production simultaneously, and the customer-facing update arriving forty minutes late. The industry answer, borrowed almost verbatim from emergency services, is incident command.

Three roles, and the discipline is that they are declared out loud, not assumed:

  • Incident commander. Owns the incident, not the fix. Decides, delegates, keeps the hypothesis list, enforces one-change-at-a-time, and calls when to mitigate. The IC's most important property is that they are not debugging — the moment the IC opens a terminal, coordination stops and everyone converges on their theory.
  • Communications lead. Owns the outside world: status page, stakeholder updates on a fixed cadence, and shielding the responders from "any update?" so they can work.
  • Scribe. Records the timeline as it happens — observations, hypotheses, actions, timestamps. Reconstructing a timeline afterwards from Slack is unreliable and slow, and the scribe's notes are what makes the review honest.

Small incidents collapse all three into one person, and that is fine as long as the collapse is explicit and reversible: the standing rule should be that anyone may say "I think this needs an IC" and that declaring an incident is cheap. Declare early and downgrade freely. The cost of a false alarm is fifteen minutes of a few people's time; the cost of a late declaration is that the first thirty minutes were spent by one person poking around alone while impact grew.

Then comes the review, and the word that matters is blameless — which is widely misunderstood as "be nice". It is an epistemic stance, not a politeness rule: people act rationally given the information, incentives and tooling they had at the time, so if an engineer's action contributed to the outage, the interesting question is what made that action look correct. A deploy button with no canary, a runbook that was out of date, an alert that had cried wolf forty times, a review culture that rewards speed — those are the findings. Blame ends the investigation exactly where it should begin, and it also guarantees that the next person hides information, which is the real long-term cost.

Related, and worth having a considered opinion on: there is rarely a single root cause. Complex systems fail through combinations of contributing factors, each individually survivable — a config change plus an unusual traffic shape plus a retry policy without jitter plus an alert that was routed to a muted channel. "Five whys" produces a single causal chain and therefore systematically under-describes what happened; it is a useful prompt and a poor model. The stronger framing is a list of contributing factors plus the things that went right (which is how you learn what to protect) and an explicit note on how the incident was detected, because "a customer told us" is itself a finding.

Action items are where most postmortem processes quietly fail. Twenty items with no owners is a document; three items with owners, dates and space in the next sprint is a change. Prioritise by what would have reduced impact rather than by what would have prevented this exact bug — better detection, faster rollback, a circuit breaker, a bulkhead — because the specific bug will not recur and the class will. And track completion rate as a metric, reported to leadership: if fewer than half the items land, the process is theatre and the honest fix is fewer items rather than more nagging.

Finally, the proactive side. Game days and chaos engineering are how you find the gaps before an incident does, and the framing that gets them approved is scientific rather than destructive: state a steady-state hypothesis, inject a realistic failure, and see whether the hypothesis holds — starting in staging, with a blast radius you control and an abort switch. In my experience the most valuable output is never the failure itself but the list of things nobody could see while it happened, which converts directly into instrumentation work. The same is true of near misses: an incident that almost happened carries nearly all the learning at none of the cost, and teams that review them are markedly better prepared.

Interview trap

The incident commander who is also the best debugger. It is the most natural mistake for a technical lead, and it is why incidents drift: the moment you start typing, nobody is tracking hypotheses, nobody is deciding, and the group silently converges on whatever you are looking at. If you are the most qualified person to debug, hand over command — explicitly, by name, out loud — and then debug. The second trap is declaring root cause too early and stopping: you rolled back, the graph recovered, everyone goes to bed, and nobody asks why a config default change was able to reach production without a canary catching it. Recovery is the end of the incident, not the end of the investigation. And a third, specific to interviews: describing a postmortem process with no follow-through — if you cannot say what fraction of action items get completed, you are describing a document, not a practice.

Try it

1. Run a game day where the injected failure is observability itself: stop the Collector, or break the metrics backend, and see whether the team can still operate — most organisations have never tested this and discover their runbooks assume dashboards. 2. Take your last three postmortems and count action items, owners, and completion; then rewrite one review to focus on what would have reduced impact rather than what would have prevented that specific bug.

Solution sketch

In (1) expect to find that alerting silently stops — which is worse than alerting failing loudly — and that nobody has a fallback path to raw logs on a node or to a health endpoint. The concrete outcomes are a monitoring-of-the-monitoring alert routed through an independent path, and a runbook page that assumes no dashboards exist. In (2) the usual numbers are sobering: many items, few owners, low completion, and most items phrased as "prevent this bug". Rewriting toward impact reduction typically produces a much shorter and much more valuable list — faster rollback, a circuit breaker, a missing saturation metric — and that shift is exactly the judgment an interviewer is probing for when they ask about postmortems.

Interview Q&A

Describe how you run a severity-1 incident.

Declare it and name an incident commander immediately, because the first cost of an incident is usually coordination, not diagnosis. The IC establishes impact and scope, assigns a communications lead and a scribe, and opens a single channel so there is one source of truth. From there the loop is: state the current hypothesis, name the prediction that would confirm or refute it, assign one person to test it, and enforce one production change at a time with the change announced before it is made. I keep mitigation and diagnosis separate and prefer mitigation early — roll back, shed load, fail over — with evidence captured first. Communication goes out on a fixed cadence even when there is nothing new, because silence is what makes stakeholders interrupt the responders. And I hand over command explicitly if I need to debug myself, or if the incident outlasts my ability to think clearly.

What does the incident commander actually do?

Decides, delegates, and holds the picture: current impact, what has been tried, what is being tried now, who is doing what, and what the next decision point is. The IC does not debug, does not write the fix, and does not talk to executives — those are delegated precisely so the IC can keep the overview. Concretely they enforce the disciplines that groups abandon under stress: one change at a time, time-boxed hypotheses, explicit go/no-go on risky actions, and a periodic "what do we know and what are we assuming?" reset. The role is authority-bearing, so it must be clear that during the incident the IC's decisions stand regardless of seniority, and that anyone can raise a concern but not relitigate a decision mid-flight.

What makes a postmortem blameless, and why does it matter practically?

Blameless means the analysis assumes people acted reasonably given the information, tooling and incentives they had, so when an action contributed to the outage the question becomes what made it look correct at the time. It matters practically for two reasons: blame terminates the investigation exactly where the systemic findings are, and it teaches people to withhold information, which destroys the input the process depends on. The tell for a review that is blameless in name only is a document that says "human error" or that names an individual as a cause. The way I keep it honest is to insist every finding is stated as a property of the system — a missing guardrail, a stale runbook, a misleading alert — and to include what went right, since that is how you learn which defences to protect.

Is there such a thing as a root cause?

Rarely a single one. Complex systems fail through combinations of individually survivable factors — a config change, an unusual traffic shape, a retry policy without jitter, an alert routed to a muted channel — and picking one of them as "the" cause is a narrative choice, not a discovery. That is my main criticism of five whys: it produces exactly one chain and therefore systematically hides the others, though it is a useful prompt for going one level deeper than the obvious. I write reviews as a list of contributing factors with the defences that failed and the defences that held. In an interview I would add the pragmatic caveat that regulators, customers and executives often want a single-cause narrative, so part of the job is producing an honest summary for them without letting it become the internal model.

How do you make sure postmortem action items actually happen?

Fewer of them, each with a named owner and a date, tracked in the normal backlog rather than in a separate document nobody reads. I prioritise by impact reduction over bug prevention — faster detection, faster rollback, a circuit breaker — because the specific bug will not recur and the class will. Completion rate is reported as a metric in the operational review, and if it drops below about half the response is to cut the number of items rather than to nag harder, since a long unfulfilled list corrodes trust in the whole process. I also verify the item in the next review by asking what evidence exists that it works, because "added an alert" is not the same as "the alert would have fired".

How do you keep on-call sustainable?

Treat pager load as a first-class metric with a target, because a rotation that pages people at night regularly loses its best engineers and quietly stops responding well. Concretely: fewer than about two pages per shift, alert precision tracked and reviewed, non-actionable alerts deleted rather than tolerated, and a hard rule that whoever is woken gets time back. I insist on a rotation large enough that the frequency is humane, on documented and tested runbooks so being on call does not require being the expert, and on explicit handovers between shifts. I also make the load visible upward: on-call pain is a symptom of reliability debt, and turning it into a number is what gets the remediation funded rather than endured.

How do you introduce chaos engineering to a nervous organisation?

By framing it as a controlled experiment rather than as breaking things, and by starting where the risk is nearly zero. The sequence I use is: run the first game days in staging with a written hypothesis, a blast radius, an abort condition and a scheduled window; publish what was learned, which is nearly always "we could not see X" rather than "the system failed"; then move to production with the smallest possible scope, business hours, and everyone watching. The argument that lands with sceptics is that the failure will happen anyway, and the choice is whether it happens at 3 a.m. unannounced or at 2 p.m. with the whole team ready. I would also start with dependency latency injection rather than instance termination, because latency produces richer and more realistic secondary failures and is easier to reverse.

What do you do when the same incident happens for the third time?

I stop treating it as an incident and treat it as a systemic finding: three occurrences means the previous reviews produced items that were not done, were the wrong items, or addressed the symptom. I would pull the three timelines together, look for the shared contributing factors rather than the specific triggers, and escalate the remediation as a funded piece of work with a deadline rather than as a backlog item competing with features. It is also a moment to question the architecture — repeated incidents in one area usually indicate a design that requires perfection to stay up, and the durable fix is often a bulkhead, a fallback or a removed dependency rather than another guardrail. And I would say plainly to leadership that the error budget is being spent on the same thing repeatedly, which is exactly the conversation the budget exists to enable.

How much should you tell customers during an outage?

Early, honest, and on a cadence: acknowledge impact in customer terms rather than internal ones, say what is affected and what is not, give the next update time, and keep that promise even when there is nothing new. I avoid speculating about cause while the incident is live, because a retracted cause damages trust more than silence about it, and I avoid minimising language when the impact is real. After recovery, a public writeup for significant incidents — what happened, what you are changing — buys more credibility than it costs, provided the changes are real. Internally I keep the responders shielded from this entirely; that is the communications lead's job, and mixing the two is how updates get late and debugging gets interrupted.

How do you build a culture where people report near misses?

Make it cheap and visibly valuable. Cheap means a lightweight channel and no heavyweight process attached — a near miss should not trigger a full incident review, or nobody will report one. Visibly valuable means acting on some of them and saying so, so people see reports turning into changes rather than into scrutiny. The cultural precondition is the same as for blameless reviews: the person who says "I almost took prod down and here is how" must be thanked in public, every time, including when it is embarrassing. I would also seed it by reporting my own, since senior people modelling the behaviour is what makes it safe, and I would track the report count as a health metric where more is better — a sudden drop usually means fear, not improvement.

13Architecture, cost & rollout

The final technical unit is the one asked of leads and principals almost exclusively: you are handed an estate, a budget and a sceptical set of teams, and you have to decide what to run, what to buy, what to standardise, and how to get there without a two-year programme nobody finishes.

Start with the piece that is no longer a real decision. Instrument with OpenTelemetry, export OTLP, and put a Collector in the middle. My default recommendation, stated as a position rather than a hedge: buy the backend early, because a two-person platform team should be building instrumentation standards and paved roads rather than operating a distributed time-series database; revisit when the bill becomes comparable to the fully-loaded cost of the engineers who would run the alternative, and when the volume is stable enough that self-hosting is an engineering problem rather than a research project. And in every case, keep the Collector so that revisiting is possible.

Cost control deserves an explicit architecture, because "reduce retention" is the only lever most teams ever pull and it is the one that hurts most during an incident. The levers, cheapest-to-most-painful:

  1. Drop what nobody queries. Most backends can tell you which metrics and dashboards were never read; in a mature estate 30–50% of series are unqueried. Delete them at the Collector.
  2. Fix cardinality. One unbounded label typically outweighs every other saving combined.
  3. Sample intelligently. Tail-sample traces to keep all errors and slow requests plus a small baseline; deduplicate and filter logs; aggregate away dimensions nobody slices by.
  4. Tier storage. Hot and searchable for two weeks, cold object storage with slower query for a year, and keep only aggregates beyond that.
  5. Then reduce retention, last, and per-signal rather than globally.

The organisational half of cost is showback: attribute spend per service and per team, publish it, and let teams see their own footprint. This changes behaviour faster than any policy, because engineers do not intend to spend money on unqueried debug logs — they simply cannot see that they are. Full chargeback is heavier and often counterproductive, since it makes teams under-instrument the very services that need it most; the middle path is a published budget with a conversation rather than an automatic cut-off.

On governance, the model that works is a paved road, not a rulebook: the platform team ships base images or Operator injection with instrumentation pre-wired, a golden dashboard template generated per service, a standard alert bundle derived from SLOs, and a documented attribute vocabulary. Teams that take the paved road get everything for free; teams that need to deviate can, and the deviation is visible. The anti-pattern is a standards document with no implementation, which produces compliance theatre and drift.

Two architectural cautions worth raising unprompted. First, do not monitor the monitoring with the monitoring: your alerting path must not depend on the system it is alerting about, so keep an independent, minimal watchdog — a separate Prometheus, a hosted synthetic check, a dead-man's-switch alert that fires when the regular heartbeat stops — because a silent pipeline looks exactly like a quiet system. Second, plan for the vendor outage: if your only view of production is a SaaS that is down, what is the fallback? Usually a node-level log path and a minimal local metrics endpoint, documented in a runbook that assumes no dashboards.

Finally, the emerging area you should be able to speak to: observability for LLM-backed features. The signals are genuinely different — token counts and cost per request, time to first token as well as total latency, prompt and model version, tool-call chains, retrieval hit quality, and output-quality evaluation, which has no analogue in ordinary services. OpenTelemetry has GenAI semantic conventions, and the current state is the thing to get right in an interview: as of mid-2026 every GenAI attribute, span, metric and event is still marked Development, none are stable, and in semconv 1.42.0 (June 2026) they were moved to a dedicated repository. So instrument now, expect renames, keep the mapping in the Collector, and do not build a billing dashboard on an unstable attribute without saying so.

Interview trap

Answering "build or buy" without naming the switching cost. The naive version of both answers is a lock-in trap: proprietary agents in every service make leaving a vendor a fleet-wide redeploy, and a bespoke self-hosted stack makes leaving a migration of storage and of every dashboard and alert. The lead-level answer names the mechanism that preserves optionality — OTLP instrumentation plus a Collector, with dashboards and alerts defined as code — so the decision is reversible in weeks rather than quarters. The second trap is treating the observability platform as infrastructure rather than as a product: if adoption requires reading a wiki, it will not happen, and the estate will fragment into teams with excellent telemetry and teams with none. The measure to quote is adoption of the paved road, not the number of standards published.

Interview Q&A

Self-hosted or SaaS observability — how do you decide?

I compare the vendor bill against the fully-loaded cost of the platform engineers who would run the alternative, plus the opportunity cost of what those engineers would otherwise build. For most organisations below a very large scale, buying wins, because operating a distributed metrics and trace store at scale is a specialist job and the failure modes are subtle. Self-hosting becomes attractive when volume is large and stable, when data residency or regulatory constraints make a vendor awkward, or when the platform capability already exists for other reasons. Whichever way it goes, I keep instrumentation on OpenTelemetry with a Collector in the middle so the decision is reversible, and I define dashboards and alerts as code so migrating does not mean rebuilding them by hand.

Your observability spend is 15% of your infrastructure budget. Too much?

It depends entirely on what it buys, so I would not answer with a benchmark. I would look at whether the spend is proportional to value: what fraction of it is data nobody has queried in ninety days, what the cost per million requests is and whether it is rising, and whether incidents are actually being resolved faster. In most estates a large share is genuinely wasted — unqueried metrics, debug logs left on, retention set globally instead of per-signal — and cutting that costs nothing in capability. If after that cleanup it is still 15% and time-to-mitigate is good and outages are rare, that may be a fair price; if the number is high because one team's cardinality bug is unaddressed, it is not a budget problem at all. The wrong move is a blanket retention cut, which reduces the bill and your ability to debug in the same stroke.

How do you avoid vendor lock-in?

Instrument with OpenTelemetry and export OTLP, so the data-producing side of the estate is vendor-neutral by construction, and put a Collector between applications and any backend so routing, duplication and switching are config changes rather than redeploys. Define dashboards and alerts as code in a portable form where possible, because the hidden cost of migration is usually hundreds of hand-built dashboards, not the data. Avoid depending on proprietary agents and on vendor-specific attribute names in application code; if a vendor feature needs its own naming, add it in the pipeline. And run a periodic exercise — even just exporting a week of data to a second backend — because portability you have never tested is a claim rather than a property.

How would you introduce observability standards to teams that resist them?

By making the standard the easiest path rather than the mandated one. That means shipping instrumentation pre-wired in base images or through Operator injection, generating a golden dashboard and an SLO-derived alert bundle for any service that adopts it, and providing a short attribute vocabulary rather than a long policy document. Then I find a team with real pain, help them personally, and let the result be the argument — internal adoption is driven by demonstrated wins far more than by mandates. I would enforce only the small set of things that genuinely break the commons if violated: resource attributes, semantic-convention names, and cardinality limits, ideally checked automatically in CI or in the pipeline rather than in review. And I would measure adoption of the paved road as the success metric, because a standard nobody follows is worse than none.

How do you make the observability platform itself highly available?

First, decouple the alerting path from the thing being monitored: an independent watchdog — a separate small Prometheus, an external synthetic check, or a hosted uptime service — plus a dead-man's-switch alert that fires when the regular heartbeat stops, so a silent pipeline is loud. Second, make the ingestion path degrade gracefully: agents buffer with bounded persistent queues, applications never block on export, and the gateway sheds load rather than OOMing. Third, replicate what is stateful and test failover, including the query path, since a stack that ingests but cannot be queried during an incident is useless. Fourth, document a no-dashboards fallback: how to read logs on a node, how to hit a health or metrics endpoint directly, how to take a profile by hand. And I would game-day the whole thing, because almost nobody has tested losing their observability during an incident.

What's different about observing LLM-backed features?

The cost model and the failure modes are new. Cost is per token rather than per request, so token counts by model and by feature are first-class metrics and a prompt-length regression is a budget incident. Latency needs time-to-first-token alongside total duration, because the user experience of streaming is different. The call graph is deeper and more dynamic — retrieval, tool calls, chained model calls — which makes tracing more valuable than usual. And quality is a signal with no traditional analogue: you need evaluation results, refusal and failure rates, and a way to sample and inspect actual inputs and outputs, which immediately raises privacy questions. OpenTelemetry has GenAI semantic conventions, but the honest status as of mid-2026 is that all of them are still marked Development and none are stable, and they were moved to a dedicated repository in semconv 1.42.0 — so I instrument now, normalise names in the Collector, and warn stakeholders that dashboards built on them will need maintenance.

How do you handle observability in a regulated or multi-tenant environment?

The controls have to be in the pipeline, because that is the only place you can guarantee them before data leaves your boundary: redaction and deletion rules for known-sensitive fields, pattern matching for identifiers, and an allowlist approach for anything crossing a region or a vendor edge. Data residency usually means regional Collectors exporting to regional backends, with only aggregates crossing borders, which is a topology decision to make early because retrofitting it is painful. Multi-tenancy means tenant labels on data with enforced isolation in the backend, and access control such that a support engineer sees what they need without seeing every customer's payloads. I would also make deletion possible — a subject erasure request must be satisfiable within retention — and treat that as a design constraint rather than a promise, since append-only telemetry stores make it genuinely hard.

You join a company with no observability. What's your ninety-day plan?

Days 1–30: measure the pain and land the pipeline. Interview on-call about the last ten incidents, find the two or three services on the critical user journey, deploy a Collector and a backend, and turn on zero-code instrumentation for those services with correct resource attributes. Days 31–60: define one real SLO for the critical journey, replace whatever noisy alerts exist with burn-rate alerts derived from it, and add manual instrumentation and a canonical event to the highest-pain service — plus exemplars, so metric-to-trace navigation works. Days 61–90: templatise it — golden dashboards, an alert bundle, Operator injection so new services get it by default — and run a game day to find the gaps. Throughout I would publish time-to-detect and time-to-mitigate so the improvement is visible, and I would deliberately not attempt fleet-wide coverage, because the value is concentrated in a handful of services and chasing completeness is how these programmes stall.

What do you flag in a design review from an observability standpoint?

Whether the design states its SLI and SLO, since a service without a definition of "working" cannot be operated. Whether failure is observable at the boundary — is a degraded state distinguishable from a healthy one, or does the fallback silently return empty results forever? Whether the async and fan-out paths carry trace context and whether queue dwell is measured separately from processing. Whether saturation is instrumented for every bounded resource in the design: pools, queues, semaphores, rate limits — because those are what fail first. Whether the identifiers needed to debug a specific customer's problem will exist on the telemetry. And whether the design is rollback-safe, since rollback is the mitigation that makes everything else optional.

How do you measure the maturity of an organisation's observability?

By outcomes and by capabilities, not by tool inventory. Outcomes: what fraction of incidents are detected by alerts before customers report them, time to detect and to mitigate, alert precision, and the proportion of incidents whose cause was identified from telemetry rather than guessed. Capabilities: can you go from an alert to a trace in one click, from a trace to logs and a profile, and can you slice by an attribute nobody dashboarded — those three tests separate real observability from a dashboard collection. I would also look at consistency, since an estate where three services are excellent and forty are dark is a coverage problem masquerading as a maturity problem, and at whether teams own their own telemetry rather than filing tickets against a platform team. Framed that way, the improvement plan writes itself from whichever test fails.

14The big Q&A

Twenty-two questions that do not belong to any single unit: the cross-cutting, architectural, political and scenario questions that fill the back half of a lead or principal interview. Grouped by theme, and deliberately weighted towards judgment rather than recall.

Architecture & ecosystem decisions

Why did OpenTelemetry win, and what does its CNCF graduation actually change?

It won because it removed the thing everybody hated: instrumenting once per vendor. By splitting a stable API from a swappable SDK, it let library authors instrument upstream at no cost to their users, which meant coverage accumulated across the ecosystem rather than inside each vendor's agent — and vendors then joined because competing on agent coverage was a losing game against a standard everyone contributed to. Graduation in May 2026 put it at the same CNCF maturity tier as Kubernetes, which matters less technically than politically: it ends the "is this stable enough to bet on?" objection in procurement and architecture reviews. Practically, what changed is that vendors now compete on backend, analysis and price rather than on lock-in, and that OTLP is a portability guarantee you can actually plan around.

Would you use a service mesh for observability?

A mesh gives you consistent L7 metrics, and often traces, for every service without touching application code, which is genuinely valuable in a polyglot estate and overlaps heavily with what OBI now offers via eBPF at lower cost. But it only sees what crosses the network: it cannot tell you which pricing rule fired, which tenant, or why a request was slow inside a process, and mesh-generated traces are frequently disconnected because the application does not propagate context between the inbound and outbound calls the mesh observes. So I would not adopt a mesh for observability; if one is already there for traffic management, mTLS or routing, I take the telemetry as a useful baseline. And I would name the operational cost — a sidecar per pod, latency added on every hop, an upgrade treadmill — as the reason it should be justified by its primary purpose.

How do you observe serverless and other short-lived compute?

The constraints are that the process may live for 200 ms, cumulative counters are meaningless, there is no local agent to export to, and the platform may freeze the process the instant your handler returns — which kills batched exports. So: delta temporality for metrics, flushing exports before the handler completes or using the platform's extension mechanism to flush out-of-band, and accepting a per-invocation export cost. Context propagation must survive the platform's own event envelope, so the trace context has to be carried in the message or the request attributes, not just in HTTP headers. Cold starts deserve their own attribute and metric, because they dominate tail latency and are otherwise invisible. And I would route through a collector layer the platform provides rather than exporting to a vendor from every invocation, because per-invocation network calls are both slow and expensive.

Front-end and mobile observability — how does it differ?

The data is untrusted, the environment is uncontrolled, and the release cycle is not yours. Untrusted means anything the client sends can be forged, so client telemetry needs its own ingest path with rate limiting and cannot be an authority for billing or security decisions. Uncontrolled means the population is a confound: latency varies by device, network and geography far more than by your code, so aggregates need slicing by those dimensions or they are noise. Not-your-release-cycle means old app versions live for months and will keep emitting whatever they emitted, which makes attribute stability and version dimensions essential. The signals themselves differ too — Core Web Vitals, crash-free session rate, startup time — and the highest-value integration is propagating trace context from the client into the backend so a slow page maps to the requests behind it, with the caveat that this exposes your trace IDs to the public and needs the edge sampling discipline from unit 03.

Security & privacy

What are the security risks of a telemetry pipeline?

Three categories. Data exfiltration: telemetry is a firehose leaving your network, and it will contain whatever people put in it, so it is a plausible path for credentials, tokens, personal data and internal topology to reach a third party. Availability: an unauthenticated OTLP endpoint is an amplification target, and the Collector is a privileged process — the eBPF and host-metrics components especially — with a large supply chain, which is the argument for building a minimal distribution. Integrity: forged telemetry can hide an attack or create a false one, and trusting client-supplied trace context lets an attacker control sampling and pollute traces. The mitigations are correspondingly boring and effective: authenticated ingest, redaction in the pipeline before egress, least-privilege deployment, a minimal component set, and treating Collector configuration as production code under review.

How do you keep secrets and PII out of traces and logs?

Layered controls, because any single one fails. In code: structured fields instead of interpolated strings, pseudonymous identifiers instead of direct ones, and a review rule about request and response bodies. In the pipeline: OTTL rules that delete known-sensitive attribute keys — authorisation headers, cookies, query strings with tokens — and pattern-based redaction for emails, card numbers and keys, applied at the gateway before egress. In storage: access control, retention limits, and a deletion path so an erasure request is satisfiable. Plus a detective control: periodically sample stored telemetry and scan it, and report the result as a compliance metric. The reason the pipeline layer matters most is speed — when someone discovers a leak, a Collector rule stops it in minutes while a code fix takes a release.

Is observability data a compliance liability?

Yes, and treating it as "just telemetry" is how organisations end up with personal data in a vendor's index with no deletion story. Traces and logs routinely contain identifiers, IP addresses, user agents and sometimes payloads, which brings them into the scope of data-protection regimes: purpose limitation, retention limits, subject access and erasure, and cross-border transfer rules. Practically that means a data map for what telemetry contains, regional pipelines where residency is required, contractual review of any vendor that receives it, short retention as a default with justification for anything longer, and a documented redaction and deletion capability. It also means audit logs should be a separate pipeline entirely, because their integrity and retention requirements have nothing to do with debugging and mixing them creates the worst of both.

Performance & debugging

How do you debug a problem that only occurs in production, at scale, for 0.1% of requests?

Make every occurrence produce evidence, then stop guessing. Concretely: ensure the failing population is always sampled — a tail-sampling policy on the error condition or on the discriminating attribute, so 100% of occurrences are captured regardless of the head sampling rate — and add the two or three attributes most likely to distinguish that population. Then do differential analysis: compare the failing set to the succeeding set across every dimension and look for the one that separates them, which is precisely the query a wide event or a richly attributed span makes trivial. Continuous profiling covers the case where the difference is code path rather than data. If it is still opaque, targeted dynamic instrumentation on the specific branch, with an expiry, gets the one extra variable without a release. At 0.1% of a large volume you have plenty of examples; the problem is capture, not rarity.

How do you find a performance regression introduced three releases ago?

A differential profile between then and now is the fastest single tool: if continuous profiling was running, take the flame graph from before and after and let the delta name the function. Failing that, bisect using the version dimension on your latency metrics — if service.version is on your telemetry you can compare percentiles per version directly, which converts a search into a lookup. I also check whether the regression is uniform or restricted to a slice, since a regression that only affects one endpoint or one tenant points at data shape rather than at code. And I would question the premise: gradual degradation over three releases is often data growth crossing a threshold — a table without an index becoming slow at ten million rows — rather than any single commit, and that distinction changes the fix entirely.

What is coordinated omission and why should a lead care?

It is a measurement artefact where a load generator or a client that waits for a response before sending the next request fails to record the requests it should have sent during a stall, so the worst latencies are systematically omitted and your percentiles look far better than reality. A one-second pause in a system doing 1,000 requests per second should show up as roughly a thousand slow requests; a naive closed-loop measurement records one. It matters at lead level because it makes benchmark results and some client-side SLIs quietly optimistic, and because it explains the recurring pattern of "our p99 is 200 ms but customers say the site freezes". The mitigations are open-loop load generation with a fixed arrival rate, tools that correct for it, and — most reliably — measuring latency server-side from request arrival plus real user monitoring at the client, rather than trusting a closed-loop benchmark.

When is the answer "add capacity" and when is it "fix the code"?

Capacity is right when the system is behaving as designed and the workload has simply grown, when the cost of hardware is lower than the engineering time, and when you have headroom in the surrounding constraints — you cannot scale past a database's write capacity or a third party's rate limit by adding application replicas. Fixing the code is right when unit cost is degrading, when the profile shows an obvious pathology such as an N+1 query or a per-request allocation of something expensive, or when scaling would multiply a downstream problem. The test I apply is cost per unit of work over time: if it is flat, growth is the story and capacity is the answer; if it is rising, something is wrong and capacity is a delay tactic that makes the eventual failure larger. I would also add that scaling a metastable system can make it worse, since more replicas can mean more retries against the same struggling dependency.

Tooling & data

How do you evaluate an observability vendor?

With your own data and your own questions, not their demo. I would run a proof of concept sending real production telemetry through a Collector to their endpoint alongside the incumbent, then time a fixed set of tasks drawn from real past incidents — find the slow request behind this metric spike, find which tenant is affected, find what changed since the deploy — and see how many clicks and how many seconds each takes. On the commercial side I model the bill at two and five times current volume, because per-GB and per-host pricing punishes exactly the growth you hope for, and I check what happens on a debug-log accident. On the technical side: native OTLP ingest without translation loss, exemplar and trace-to-log navigation, query language expressiveness, API access to dashboards and alerts as code, and data export on exit. The last one is the negotiating point people forget.

Grafana, Prometheus, Loki, Tempo, Pyroscope, Mimir — how do they fit together?

Grafana is the query and visualisation layer; the rest are stores, each specialised by signal. Prometheus is the single-node metrics store and scraper, Mimir the horizontally scalable, multi-tenant Prometheus-compatible one for long retention — Mimir 3.0 was the 2026 milestone there. Loki stores logs with a small label index and brute-force scanning of compressed chunks, which makes ingestion cheap and demands disciplined labels. Tempo stores traces addressed primarily by ID with object storage behind it, which is why trace search is more limited than a general-purpose index and why exemplars matter so much. Pyroscope does the same for profiles and shares the architecture deliberately, so all four correlate through shared labels. The reason to know the shape is that each store's design decides what queries are cheap: label-based lookup everywhere, arbitrary full-text or attribute search only where you paid for an index.

Synthetic monitoring or real user monitoring?

Both, because they answer different questions. Synthetics give a controlled, continuous signal on a fixed journey from fixed locations, which means they cover paths with no traffic, run during quiet hours, and provide a clean before-and-after for deploys — and they detect the failures that never reach your servers, like DNS or certificate problems. Real user monitoring reflects the actual population with all its device, network and geographic variance, so it is the truth about experience but is noisy, incomplete and easily blocked. My default is synthetics as an independent detector for critical journeys, RUM for understanding and prioritisation, and server-side ratios for the SLO because they are the most precise. When synthetics and server-side metrics disagree, that disagreement is itself a high-value alert, because it usually means the failure is in the path between the user and you.

Legacy & migration reality

How do you instrument a system you cannot change?

From the outside in. eBPF via OBI gives HTTP, gRPC and SQL visibility from the kernel with no redeploy, which covers the common case of a vendor binary or an ancient service. A reverse proxy or gateway in front of it yields request metrics and can inject trace context. Log scraping with a filelog receiver plus parsing turns existing output into structured telemetry, and database-side and network-side telemetry fill in the dependencies. If the runtime supports an agent that attaches without a code change — a JVM agent, a .NET profiler — that is often possible even when "cannot change" means "cannot change the source". What you will not get is business context, so I set expectations explicitly: outside-in instrumentation tells you that the legacy system is slow or failing and which dependency is involved, and that is usually enough to decide whether to invest in it or route around it.

You inherit an estate with three monitoring tools and no traces. What's the sequence?

Do not start by consolidating tools; start by adding the missing capability where the pain is. Deploy a Collector and instrument the two or three services on the critical journey, so within weeks there is trace-based debugging where incidents actually happen — that creates the demand that makes consolidation politically possible. In parallel, fan the Collector out to all three existing backends so nothing breaks and everybody's dashboards keep working while the new path proves itself. Then consolidate by attrition: each tool is retired when the teams using it have an equivalent or better view elsewhere, and the retirement is a project with an owner, not a hope. Throughout, I would resist a big-bang cutover, because migrating dashboards and alerts is always larger than it looks and a failed consolidation poisons the next attempt.

What legacy patterns will you meet, and how do you handle each?

Unstructured text logs parsed by regex at ingestion, which are expensive and brittle — I bridge them through the filelog receiver, extract what I can, and structure new code rather than rewriting everything. Proprietary vendor agents, which I run in parallel with OTel during migration rather than ripping out. OpenTracing and OpenCensus instrumentation, whose compatibility requirements OpenTelemetry formally deprecated in 2026, so I plan migration rather than assume the shims persist. Pre-1.23 semantic-convention attribute names, normalised forward in the Collector. Statsd and Graphite metric feeds, which a Collector receiver can ingest so the migration is transparent. And homegrown correlation IDs, which I keep emitting as an attribute while the trace ID becomes the real join key, because dozens of dashboards and support workflows depend on the old ID and removing it early is how you lose goodwill.

Judgment & scenarios

How do you introduce SLOs to a team that thinks they're bureaucracy?

Start with one service and one SLI, chosen with the team from something they already care about, and make the first artefact useful to them rather than to management — usually replacing a noisy alert with a burn-rate alert, so their pager gets quieter in week one. Do not introduce the error budget policy at the same time; earn the right to it once the measurement is trusted, because the policy is where the politics live and it is unenforceable if people doubt the numbers. Show the dependency arithmetic when someone asks for an unrealistic target, because that conversation converts the framework from bureaucracy into a tool for saying no with evidence. And frame the whole thing as protecting their release velocity: an error budget is permission to ship, and that is the reading that makes engineers care about it.

An engineer wants to add a customer ID label to a metric. Walk me through the conversation.

I start by asking what question they are trying to answer, because the request is almost always a proxy for "I need to find the affected customer" and the answer is a different tool. I explain the arithmetic concretely — customers times routes times status classes times replicas — so the cost is a number rather than a principle, and I mention that the SDK's 2,000-per-metric cardinality limit will fold everything into an overflow bucket anyway, so the label will not even work as intended. Then I offer the alternatives: the identifier as a span or log attribute, where it is free to store and queryable; a top-N recording rule if the aggregate view is genuinely needed; a separate purpose-built metric for a small allowlist of large tenants. I try hard to make this a design conversation rather than a refusal, because a platform team that only says no gets routed around.

Production is broken, and you have no useful telemetry. What now?

Work the change list first, since it needs no instrumentation: what deployed, what flag flipped, what config changed, what expired, whose provider is having an incident. Then get the cheapest possible signal fast — a thread dump, a health endpoint, a tail of logs on one node, a manual timing curl from inside and outside the network — and use the differential method against whatever crude data exists: one instance versus another, one region versus another, one endpoint versus another. Bias hard towards mitigation, because without telemetry the cost of diagnosis is high and rollback is cheap. Then, and this is the part that matters at lead level, capture the gap while it is vivid: write down the three questions you could not answer, and turn them into instrumentation work in the review, because "we could not see it" is the finding, not an excuse.

Your CTO wants a single dashboard showing overall system health. How do you respond?

I would build it, but as an SLO summary rather than a wall of technical metrics: one row per critical user journey showing current SLI, error budget remaining and trend, with drill-down into the detail. That version is genuinely useful because it answers the executive's real question — are customers being served, and are we spending reliability faster than we planned — while a grid of CPU graphs answers nothing and gets ignored within a month. I would push back on any single composite "health score", because it hides the one broken journey behind nine healthy ones and creates false confidence. And I would use the request as leverage: building it requires defining SLOs for the critical journeys, which is work the organisation needs anyway and which now has executive sponsorship.

How do you get instrumentation work prioritised against features?

Attach it to the incidents it would have shortened, in the currency the business uses. If a recent outage cost a quantifiable amount and thirty of its ninety minutes were spent answering a question that a specific attribute would have answered instantly, that is a business case with a number rather than a preference. I also make it cheap to say yes by keeping the units small — one attribute, one SLO, one dashboard template — rather than proposing an observability programme, since large programmes compete with the roadmap while small ones ride alongside it. Where possible I make instrumentation part of the definition of done for new services, so the argument is had once at the platform level rather than per feature. And I use the postmortem process deliberately, because an action item with an owner and executive visibility is the single most reliable path to prioritised reliability work in most organisations.

What would you change about how our industry does observability?

Two things. First, the field over-invests in collecting data and under-invests in the questions: most estates could delete half their telemetry, spend the savings on making the remaining half correlate properly, and be strictly better off — and the reason they do not is that adding a dashboard is easy and deleting one requires someone to take responsibility. Second, instrumentation is still treated as an operational afterthought rather than as part of the design, so it is added by the platform team from outside instead of designed by the people who know what the system is supposed to do. The concrete change I push for is making "how will we know this is working, and how will we debug it at 3 a.m.?" a required section of every design document. It costs nothing, it happens before the code exists, and it is the highest-leverage intervention I know of.

  1. Observability is the property that lets you answer questions you did not anticipate, from the outside, without shipping code — monitoring answers known-unknowns, observability answers unknown-unknowns, and the difference reduces to how much cardinality your telemetry can afford.
  2. OpenTelemetry is the standard and the argument is over: it graduated CNCF in May 2026, the API is a no-op without an SDK so libraries can instrument upstream for free, and OTLP is the wire format everything speaks — including Prometheus 3.x, which ingests it natively.
  3. Metrics answer "how many and how bad", events and traces answer "which ones and why". Bounded dimensions become metric labels; unbounded ones — user, tenant, order, query — go on spans and log records, where storage is per event rather than per label combination.
  4. Cardinality, not volume, is what kills a metrics backend — every label combination is a stored series, which is why OpenTelemetry ships a default limit of 2,000 per metric with an otel.metric.overflow bucket, and why native histograms in Prometheus 3.8+ are a real cost win over classic buckets.
  5. Head sampling is cheap and blind; tail sampling is expensive and forensic. I run both: a parent-based ratio for baseline coverage, plus a gateway that keeps every error and every slow trace — which forces trace-ID-aware routing so all spans of a trace reach one Collector instance.
  6. Profiles are the fourth signal — public alpha since March 2026, collected by an eBPF agent as a Collector receiver, with samples carrying trace and span IDs so a slow span links straight to the flame graph. Remember: width is share of samples, the x-axis is not time.
  7. The Collector is where cost, privacy and portability are actually controlled, because a pipeline change ships in minutes and a code change takes a release. Memory limiter first, batch last, persistent queue on the exporter, and monitor the Collector's own dropped and refused counters — a silent pipeline looks exactly like a quiet system.
  8. An SLI is good events over valid events at a user boundary; an SLO is a target; the error budget is what makes it operational. Latency SLIs are ratios, never percentiles, and pages come from multi-window burn-rate alerts — 14.4× over an hour, 6× over six — not from CPU thresholds.
  9. Debugging is differential diagnosis: what changed, and what separates broken from working. State a hypothesis, name the prediction that would falsify it, test the cheapest first, change one thing at a time — and mitigate before you diagnose, capturing the dump or profile before the restart destroys the evidence.
  10. Incident command is a role, not a title, and the commander does not debug. Reviews are blameless because people act rationally on the information they had; there is rarely one root cause; and three action items that get done beat twenty that do not.
