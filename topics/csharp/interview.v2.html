01Async, await and the Task model

The single most-probed C# area at every level, because nearly every production bug an interviewer has personally fixed was an async one: a deadlock, a starved thread pool, a swallowed exception, a cancellation that never arrived. Screeners check you know what await does; senior questions check you know what the compiler generates and what the thread pool does under load; principal questions ask how you would diagnose a starving service at 3 a.m. and what policy you would set for a codebase. Know the .NET 11 runtime-async change: it is the most current thing you can say here.

screenerWhat actually happens when you await a Task? What does the compiler generate?

Answer

The compiler rewrites an async method into a state machine (a struct in Release builds) with a MoveNext method; each await becomes a state boundary. At runtime await first calls GetAwaiter() and checks IsCompleted: if the task is already done, execution continues synchronously - no thread switch, no scheduling. Otherwise the state machine boxes itself onto the heap (first suspension only), registers its continuation with the awaiter via OnCompleted/UnsafeOnCompleted, and returns to the caller. When the awaited operation completes, the continuation runs on the captured context (SynchronizationContext or TaskScheduler) or, absent one, on a thread-pool thread. The method's own Task is completed by the builder when MoveNext reaches the end or throws.

Example

public async Task<int> LoadAsync(HttpClient http)
{
    var s = await http.GetStringAsync("https://example.test/");  // state 0 -> suspend if not complete
    return s.Length;                                             // state 1 -> SetResult on the builder
}
// Roughly what ships: a struct implementing IAsyncStateMachine with
//   int state; AsyncTaskMethodBuilder<int> builder; TaskAwaiter<string> awaiter;
// MoveNext() switches on state, calls awaiter.GetResult() (which rethrows) on resume.

Follow-ups

  • Why is the state machine a struct in Release and a class in Debug? - A struct avoids a heap allocation when the method never suspends; Debug uses a class so the debugger can inspect locals reliably.
  • When does an async method allocate? - On first suspension (the state machine is boxed) plus the Task object, unless the result is a cached task (completed Task, true/false, small ints) or you return ValueTask.
  • What changes with runtime-async in .NET 11? - The compiler stops emitting the state machine and marks the method; the JIT/runtime implements suspension natively, cutting allocations and giving real stack frames in traces. It was experimental in .NET 10 behind DOTNET_RuntimeAsync and is on in the CoreCLR runtime from .NET 11 Preview 1, with the C# side still gated by the runtime-async feature flag as of RC1 - say "check the RC notes" if pushed on exact defaults.
  • What does GetResult() do with a faulted task? - It unwraps and rethrows the first inner exception with its original stack via ExceptionDispatchInfo, which is why you see the real exception type and not an AggregateException.

Wrong answer

"await spins up a new thread to run the task." No thread is created; for I/O nothing runs on any thread while waiting - the OS completes the operation and a thread-pool thread picks up the continuation. Saying "new thread" signals you would also write Task.Run around I/O, which is the next thing they will ask about.

screenerWhy is async void dangerous, and when is it the only option?

Answer

An async void method has no Task to observe, so the caller cannot await it, cannot compose it and cannot catch its exceptions: a throw after the first await is posted to the captured SynchronizationContext or, absent one, raised on the thread pool and crashes the process. It also makes tests race, because the test finishes before the method does. The only legitimate use is a genuine event handler signature you do not control (void Button_Click(object, EventArgs)), and even there wrap the body in try/catch. Modern code exposes Func<Task> for callbacks instead, and analyzers (VSTHRD100, AsyncFixer01) flag the rest.

Example

// bad: exception escapes to the pool, process dies
async void Fire() { await Task.Delay(10); throw new InvalidOperationException(); }

// event handler: the one legitimate case, fenced
private async void OnClick(object? sender, EventArgs e)
{
    try { await SaveAsync(); }
    catch (Exception ex) { _log.LogError(ex, "save failed"); }
}

Follow-ups

  • How does an unobserved Task exception behave by comparison? - It is held on the task; if the task is finalized unobserved it raises TaskScheduler.UnobservedTaskException but does not crash the process (since .NET 4.5).
  • What about "fire and forget" in a service? - Use a background queue (Channel<T> + hosted service) so the work is tracked, logged and drained on shutdown; naked fire-and-forget loses work on deploy.
  • Can a lambda become async void by accident? - Yes: passing async () => ... to a parameter typed Action compiles to async void. Overloads taking Func<Task> fix it.

Wrong answer

"It is fine as long as you put a try/catch inside." That handles exceptions but not the lifetime problem: nobody can wait for it, so shutdown, tests and retries are all broken. The rejection-grade version is the candidate who uses async void for "fire and forget" in a web service.

midWhat does ConfigureAwait(false) do, and what is your policy for it in 2026?

Answer

ConfigureAwait(false) tells the awaiter not to capture the current SynchronizationContext/TaskScheduler, so the continuation runs on whatever thread completed the task instead of being marshalled back. It matters where a context exists: UI frameworks (WPF, WinForms, MAUI, Blazor Server's renderer) and legacy ASP.NET on .NET Framework. ASP.NET Core has no SynchronizationContext, so in a Core application it changes nothing functionally. Policy: in general-purpose libraries use it everywhere (enforce with CA2007) because you do not know who will host you; in ASP.NET Core applications do not clutter code with it; in UI code omit it where you touch UI after the await. ConfigureAwaitOptions (.NET 8) adds ForceYielding and SuppressThrowing.

Example

// library code
public async Task<byte[]> ReadAllAsync(Stream s, CancellationToken ct)
{
    using var ms = new MemoryStream();
    await s.CopyToAsync(ms, ct).ConfigureAwait(false);
    return ms.ToArray();
}

// .NET 8+: await a task without throwing on cancellation/fault
await task.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);

Follow-ups

  • Does ConfigureAwait(false) on the first await make the whole method context-free? - No. Each await decides independently; after an await that captured the context you are back on it.
  • Why is the classic .Result deadlock impossible in ASP.NET Core? - No single-threaded context to block; but sync-over-async still starves the pool, which is worse at scale (see the starvation question).
  • What does ConfigureAwait(true) mean? - The default: capture and resume on the context. It exists only to make intent explicit next to code that uses false.

Wrong answer

"You must always use ConfigureAwait(false) for performance." In ASP.NET Core it is a no-op, and in UI code it is a bug when the continuation touches the UI. The interviewer wants the distinction between library and application, not a cargo cult.

seniorExplain thread-pool starvation: how does it happen, how do you spot it, and how do you fix it?

Answer

Starvation is when every pool thread is blocked (typically on .Result, .Wait(), GetAwaiter().GetResult(), or a sync lock held across an async boundary) while the work that would unblock them - the continuations - is queued waiting for a pool thread. The pool injects new threads slowly (roughly one or two per second above the minimum, guided by the hill-climbing heuristic), so throughput collapses while CPU sits idle. Symptoms: latency climbs with load, CPU is low, ThreadPool.ThreadCount and the dotnet-counters ThreadPool Queue Length keep rising, and a dotnet-dump/dotnet-stack shows dozens of threads in Monitor.Wait or Task.Wait. Fix: remove the blocking (make the chain async all the way), never "fix" it with ThreadPool.SetMinThreads except as a temporary incident mitigation, and gate outbound concurrency with SemaphoreSlim so a slow dependency cannot pin every thread. .NET 6+ mitigates blocking on Task specifically by detecting it and injecting threads faster, but it does not save you.

Example

// the classic culprit inside a request handler
var user = _repo.GetUserAsync(id).Result;          // blocks a pool thread

// incident triage on Linux
// dotnet-counters monitor -p <pid> System.Runtime   -> watch "ThreadPool Queue Length", "ThreadPool Thread Count"
// dotnet-stack report -p <pid>                      -> many stacks parked in Task.Wait / Monitor.Enter

// the fix: async all the way
var user = await _repo.GetUserAsync(id, ct);

Follow-ups

  • Why not just raise SetMinThreads to 500? - It buys time but each blocked thread costs ~1 MB stack and context switches; the starvation reappears at the next load step. Mitigation, not fix.
  • What is the .NET 6+ "blocking detection" feature? - The pool notices a worker blocked on a Task and injects threads immediately instead of waiting for hill-climbing; it covers Task.Wait, not arbitrary locks or I/O.
  • Where does sync-over-async hide in a modern codebase? - Constructors, property getters, IDisposable.Dispose, ILogger enrichers, static initializers, and legacy IHttpModule-style code; also Task.Run(...).Result "to avoid deadlocks".
  • How does a lead prevent it long-term? - Analyzers (CA1849, VSTHRD002), a code-review rule, no sync APIs on repositories/clients, and a load test that includes a slow dependency.

Wrong answer

"Starvation means we ran out of threads, so add more threads." That mistakes the symptom for the cause and moves the cliff. Candidates who cannot name the blocking call as the root cause, or who propose Task.Run around the blocking call, do not pass this one.

midTask vs ValueTask: when do you return which, and what are the rules for consuming a ValueTask?

Answer

Task<T> is a heap object and a fully general handle: await it many times, store it, WhenAll it. ValueTask<T> is a struct that wraps either a result, a Task<T>, or a pooled IValueTaskSource<T>; it avoids the allocation when the method usually completes synchronously (cache hits, buffered reads). Return ValueTask only on hot paths where the synchronous case is common and measured, and on interfaces designed for it (IAsyncEnumerable, Stream.ReadAsync, PipeReader). Consumer rules: await it exactly once, never await it twice, never call .Result before it completes, and do not hold it across awaits or hand it to WhenAll - call .AsTask() when you need those. The public-API default remains Task.

Example

public ValueTask<Product?> GetAsync(int id, CancellationToken ct)
{
    if (_cache.TryGetValue(id, out var p)) return ValueTask.FromResult<Product?>(p); // no allocation
    return new ValueTask<Product?>(LoadAndCacheAsync(id, ct));                        // wraps a Task
}

// consuming: once, directly
var product = await repo.GetAsync(7, ct);
// need fan-out? convert
await Task.WhenAll(ids.Select(i => repo.GetAsync(i, ct).AsTask()));

Follow-ups

  • Why is awaiting twice undefined? - With a pooled IValueTaskSource the backing object may already be reused for another operation, so the second await reads someone else's state.
  • Does ValueTask (non-generic) make sense? - Yes for hot synchronous-completion paths like DisposeAsync and FlushAsync; the saving is the Task object, though the runtime already caches completed non-generic Tasks.
  • What does IsCompletedSuccessfully buy you? - A fast path: check it and read .Result synchronously to skip the await machinery entirely in the common case.

Wrong answer

"ValueTask is just a faster Task, so use it everywhere." It is a more constrained type with a foot-gun consumption contract, and in the always-asynchronous case it is slower (bigger struct to copy, extra indirection). Blanket adoption is the answer that gets an API designer rejected.

midHow does cancellation work in .NET, and what are the conventions for a well-behaved async API?

Answer

Cancellation is cooperative: a CancellationTokenSource owns the state, hands out CancellationToken structs, and callees either poll (ct.IsCancellationRequested / ct.ThrowIfCancellationRequested()) or register callbacks (ct.Register) that abort the underlying operation. Nothing is interrupted by force. Conventions: the token is the last parameter, defaults to default only on public convenience overloads, is passed down every call, and cancellation surfaces as OperationCanceledException whose CancellationToken matches - callers distinguish "the user cancelled" from "the service timed out" by which token fired. Link tokens with CreateLinkedTokenSource, use CancelAfter for timeouts, dispose the CTS, and prefer WaitAsync(timeout, ct) (.NET 6) to hand-rolled Task.WhenAny races.

Example

public async Task<Report> BuildAsync(int id, CancellationToken ct)
{
    using var timeout = CancellationTokenSource.CreateLinkedTokenSource(ct);
    timeout.CancelAfter(TimeSpan.FromSeconds(5));
    try
    {
        var rows = await _db.QueryAsync(id, timeout.Token);
        return Render(rows);
    }
    catch (OperationCanceledException) when (!ct.IsCancellationRequested)
    {
        throw new TimeoutException("report query exceeded 5s");   // distinguish timeout from user cancel
    }
}

Follow-ups

  • Why must you dispose a linked CTS? - It registers a callback on the parent token; if the parent is long-lived (host shutdown token) each undisposed child leaks a registration.
  • What does ASP.NET Core do with HttpContext.RequestAborted? - It is cancelled when the client disconnects; passing it to the DB call stops wasted work, but do not use it for writes you want to complete.
  • Is TaskCanceledException the same thing? - It derives from OperationCanceledException; catch the base. HttpClient timeouts throw TaskCanceledException too, which is why .NET 5+ adds a TimeoutException inner.
  • How do you cancel a synchronous blocking call? - You mostly cannot; register a callback that closes the socket/stream so the blocking call fails, or move to an async API.

Wrong answer

"Cancelling the token stops the task." It only requests; if the callee ignores the token the work runs to completion. Candidates who think cts.Cancel() is Thread.Abort tend to design retry and shutdown logic that never converges.

seniorHow do exceptions propagate through Task.WhenAll, and how do you make sure none are lost?

Answer

Task.WhenAll waits for every task, then completes as faulted with an AggregateException containing all inner exceptions. But await on that task unwraps and throws only the first one, so the others are silently observed-but-hidden. To see all of them, keep a reference to the WhenAll task and inspect task.Exception.InnerExceptions in the catch, or iterate the input tasks. Cancellation wins ordering: if any task faulted the result is Faulted, otherwise if any was cancelled the result is Canceled. .NET 9's Task.WhenEach yields tasks as they finish so you can handle each outcome as it happens; Task.WhenAny never throws itself - you must await the returned task to observe it.

Example

var tasks = ids.Select(i => ProcessAsync(i, ct)).ToList();
var all = Task.WhenAll(tasks);
try { await all; }
catch when (all.Exception is { } agg)
{
    foreach (var ex in agg.InnerExceptions) _log.LogError(ex, "item failed");
    throw;                         // rethrow the first, already logged the rest
}

// .NET 9: react as each completes
await foreach (var t in Task.WhenEach(tasks).WithCancellation(ct))
    if (t.IsFaulted) _log.LogError(t.Exception, "item failed");

Follow-ups

  • Why is await Task.WhenAll(...) better than awaiting in a loop? - The loop is sequential; also, if the first await throws, later tasks are still running unobserved.
  • What is the classic WhenAny mistake? - Forgetting the losing tasks: their exceptions go unobserved and the work keeps running. Cancel them via a linked token.
  • Does WhenAll allocate for each task? - It allocates one continuation object per task plus the result array; for hundreds of thousands of items use a bounded fan-out (Parallel.ForEachAsync or a semaphore).

Wrong answer

"await Task.WhenAll throws an AggregateException." It is the task that holds an AggregateException; await throws the first inner one. Candidates who write catch (AggregateException) around an await have never actually seen it fire.

midWhen is Task.Run appropriate, and why is it a smell in ASP.NET Core request handling?

Answer

Task.Run queues CPU-bound work to the thread pool. It is right in a UI app (keep the UI thread free), for genuinely CPU-heavy work you want to parallelise, and in a console/worker to overlap CPU with I/O. In an ASP.NET Core handler the request is already on a pool thread, so wrapping work in Task.Run just adds a queue hop and a context switch while consuming the same pool; wrapping I/O in Task.Run is worse because it blocks a thread to fake asynchrony. The exceptions in a web service: offloading a long CPU job to a background queue so the response can return early, or bounding parallelism of CPU work explicitly. Never use Task.Run(() => x.Result) as a "deadlock fix".

Example

// smell in a controller: no benefit, one extra hop
var data = await Task.Run(() => _service.GetDataAsync());

// legitimate: CPU-heavy work off the UI thread in MAUI/WPF
var thumb = await Task.Run(() => Resize(image), ct);

// legitimate in a service: hand CPU work to a bounded background queue
await _queue.Writer.WriteAsync(new ResizeJob(id), ct);   // Channel<ResizeJob> drained by a hosted service

Follow-ups

  • Task.Run vs Task.Factory.StartNew? - StartNew does not unwrap async lambdas (you get Task<Task>) and defaults to the current scheduler; use it only with TaskCreationOptions.LongRunning for a dedicated thread.
  • What about LongRunning? - Creates a dedicated non-pool thread; right for a permanent consumer loop, wrong for anything short.
  • How would you parallelise 10,000 CPU items? - Parallel.ForEach / Parallel.ForEachAsync with MaxDegreeOfParallelism, not 10,000 Task.Run calls.

Wrong answer

"Wrap slow calls in Task.Run so the request is asynchronous." That is "async over sync": it burns two threads per request and hides the blocking. The interviewer is checking whether you know that asynchrony comes from the I/O layer, not from the wrapper.

seniorWhat are SynchronizationContext, TaskScheduler and ExecutionContext, and which one does AsyncLocal<T> ride on?

Answer

SynchronizationContext is the "where continuations run" abstraction for frameworks with a special thread: WPF/WinForms/MAUI post back to the UI thread, Blazor to its renderer, legacy ASP.NET to the request; ASP.NET Core and console apps have null. TaskScheduler is the lower-level equivalent for tasks (default: thread pool); custom schedulers are rare and mostly wrong. ExecutionContext is different in kind: it is ambient data (AsyncLocal<T> values, security/culture on Framework) that is captured at every await, Task.Run, timer and thread-pool hand-off and restored on the other side, so it flows across threads without you doing anything. AsyncLocal<T> lives on ExecutionContext: writes flow down into child async work but never back up to the caller, which is exactly what you want for correlation ids, activity/trace context and ambient tenant info. ThreadLocal<T> does not flow at all.

Example

static readonly AsyncLocal<string?> Tenant = new();

async Task Handle()
{
    Tenant.Value = "acme";
    await Task.Run(() => Console.WriteLine(Tenant.Value)); // "acme": flowed into the pool thread
    await Child();                                          // child sets "beta" ...
    Console.WriteLine(Tenant.Value);                        // ... still "acme" here
}
async Task Child() { Tenant.Value = "beta"; await Task.Yield(); }

Follow-ups

  • When would you suppress flow? - ExecutionContext.SuppressFlow() around a long-lived background loop started from a request, so it does not keep the request's AsyncLocal data alive.
  • How does ILogger.BeginScope or Activity.Current work? - Both are AsyncLocal-backed, so scopes follow the logical call chain, not the thread.
  • What breaks if you write a custom SynchronizationContext in a web app? - Everything that assumes none (ASP.NET Core does), and you re-create the .NET Framework deadlock class.

Wrong answer

"AsyncLocal is a thread-static for async code." It is not tied to threads at all; the mental model of "the thread carries it" leads to bugs when a value set inside a child method is expected to be visible in the parent.

midHow do IAsyncEnumerable<T> and await foreach work, and where does cancellation go?

Answer

An async iterator (async IAsyncEnumerable<T> with yield return, C# 8) produces items lazily; each MoveNextAsync() returns a ValueTask<bool>, so a synchronous stretch costs no allocation. It is the right shape for streaming results from a database, a paged API, a message consumer or a gRPC server stream, and ASP.NET Core serialises it to a chunked JSON array. Cancellation: mark the iterator's token parameter with [EnumeratorCancellation] so WithCancellation(ct) on the consumer side is merged into it; without the attribute the consumer's token is ignored. Iteration is also disposable (IAsyncDisposable) so finally blocks and await using inside the iterator run on early exit.

Example

public async IAsyncEnumerable<Order> ReadOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await using var reader = await _cmd.ExecuteReaderAsync(ct);
    while (await reader.ReadAsync(ct))
        yield return Map(reader);
}

await foreach (var order in repo.ReadOrdersAsync().WithCancellation(ct).ConfigureAwait(false))
    Process(order);

Follow-ups

  • IAsyncEnumerable vs Task<IEnumerable<T>>? - The latter is one batch, materialised; the former streams and lets the consumer stop early, at the cost of one await per item.
  • Is there LINQ for it? - Not in the BCL; System.Linq.Async (now under the dotnet org) provides it. Use it deliberately - each operator adds an async hop.
  • What about Channel<T>.Reader.ReadAllAsync()? - The standard bridge from producer/consumer to await foreach.

Wrong answer

"Pass the token as a normal parameter and also call WithCancellation." Without [EnumeratorCancellation] the WithCancellation token never reaches the iterator; the code compiles, the analyzer warns (CS8425), and the stream keeps running after the client disconnects.

seniorHow do you bridge a callback- or event-based API into a Task, and what are the TaskCompletionSource pitfalls?

Answer

TaskCompletionSource<T> lets you create a task you complete manually from a callback: subscribe, call the API, return tcs.Task, and in the callback call TrySetResult/TrySetException/TrySetCanceled. Pitfall one: by default continuations run synchronously on the thread that calls SetResult, so a callback from a socket or a lock-holding thread ends up running your caller's whole continuation chain inline - always construct with TaskCreationOptions.RunContinuationsAsynchronously. Pitfall two: use the Try* variants because callbacks can fire twice or race with a timeout. Pitfall three: register cancellation (ct.Register(() => tcs.TrySetCanceled(ct))) and unsubscribe from the event, or you leak both the handler and the caller. For the non-generic case use TaskCompletionSource (.NET 5).

Example

public static Task<Reply> SendAsync(this LegacyClient c, Request r, CancellationToken ct)
{
    var tcs = new TaskCompletionSource<Reply>(TaskCreationOptions.RunContinuationsAsynchronously);
    using var reg = ct.Register(() => tcs.TrySetCanceled(ct));
    void OnReply(object? s, ReplyEventArgs e)
    {
        if (e.CorrelationId != r.Id) return;
        c.ReplyReceived -= OnReply;
        if (e.Error is { } err) tcs.TrySetException(err); else tcs.TrySetResult(e.Reply);
    }
    c.ReplyReceived += OnReply;
    c.Send(r);
    return tcs.Task;
}

Follow-ups

  • Why does synchronous continuation matter in practice? - A network library completing a TCS from its I/O thread would run your application code on that I/O thread, stalling all other sockets - the reason the RunContinuationsAsynchronously flag exists.
  • How do you wrap an IAsyncResult (Begin/End) API? - Task.Factory.FromAsync(client.BeginX, client.EndX, state).
  • How do you await a WaitHandle? - ThreadPool.RegisterWaitForSingleObject feeding a TCS; not by Task.Run(() => handle.WaitOne()).

Wrong answer

"new TaskCompletionSource<T>() and call SetResult in the callback." Compiles, works in tests, and in production inlines the continuation onto the producer's thread and throws InvalidOperationException the first time the callback fires twice.

principalYou inherit a 400k-line service mixing sync-over-async, async void and hand-rolled retry loops. What is your migration plan and how do you keep it from regressing?

Answer

Start with measurement, not rewriting: add dotnet-counters/OpenTelemetry metrics for pool queue length, thread count and p99 latency, and find the top blocking sites from dumps under load - usually a handful of shared helpers cause most of the damage. Migrate bottom-up along call chains that touch I/O (data access, HTTP clients, messaging), converting whole vertical slices so you never introduce a new sync-over-async seam mid-chain; where a sync entry point must stay temporarily, isolate it with a clearly named *Blocking wrapper and a tracking issue rather than scattering .Result. Replace hand-rolled retries with Microsoft.Extensions.Resilience/Polly v8 pipelines so cancellation, jitter and circuit breaking are uniform. Lock it in with analyzers as errors (CA2007 for libraries, VSTHRD002/VSTHRD100/VSTHRD103, CA1849), an .editorconfig that new projects inherit, a load test that includes a slow dependency in CI, and a rule that PRs converting a slice must show the counters before/after. Communicate it as a sequence of small, shippable PRs, not a branch.

Example

// .editorconfig: make the regressions impossible to merge
// dotnet_diagnostic.VSTHRD002.severity = error   # avoid .Result / .Wait()
// dotnet_diagnostic.VSTHRD100.severity = error   # avoid async void
// dotnet_diagnostic.VSTHRD103.severity = error   # call async method when in async context
// dotnet_diagnostic.CA1849.severity   = warning  # call async methods when in an async method

// Temporary seam, explicit and searchable
public Result GetBlocking(int id) => GetAsync(id).GetAwaiter().GetResult(); // TODO #4711: remove after v3 cutover

Follow-ups

  • Why bottom-up rather than top-down? - A top-down conversion leaves async callers over sync callees, which still blocks; bottom-up means every converted layer immediately stops blocking.
  • How do you handle constructors and property getters that do I/O? - Factory methods (static async Task<T> CreateAsync) or lazy AsyncLazy; DI composition roots must stay synchronous, so move I/O to a hosted-service warm-up.
  • How do you prove the migration paid off? - Same load test, same hardware: pool queue length flat, thread count near core count, p99 drops; and a chaos test with a 5 s dependency delay no longer collapses throughput.
  • Where does .NET 11 runtime-async change the plan? - It does not change correctness; it may reduce the allocation cost of "async all the way" enough to remove the last performance objection.

Wrong answer

"Freeze features for a quarter and rewrite it async." A big-bang branch never merges cleanly against a moving 400k-line codebase, and it gives the business nothing until the end. The principal-level answer is incremental, measured and enforced by tooling.

02Memory, GC, value and reference types

The second pillar of every C# loop: the stack/heap model, what the garbage collector does and costs, and why structs behave the way they do. Screeners are "value vs reference type"; mid asks about boxing and generations; senior asks about LOH, server vs workstation GC, defensive copies and ref struct; principal asks you to read a memory graph, pick a GC mode for a 64-core service, or explain the .NET 10 escape analysis to a team. Numbers matter here: 85,000 bytes, 16 bytes, gen0 budgets, and dates.

screenerValue types vs reference types: what is the real difference, and where do they live?

Answer

The difference is copy semantics, not location. A value type (struct, enum, primitives, tuples) is copied on assignment and passed by value; a reference type (class, interface, delegate, string, arrays, record class) is a pointer to a heap object, so copies alias the same object. "Structs live on the stack" is only true for locals and parameters that are not captured; a struct field inside a class lives on the heap inside that object, an array of structs is one contiguous heap block, and a struct captured by a lambda or held in an async state machine is heap-allocated with it. Value types have no object header or method-table pointer (16 bytes saved per instance on x64), cannot be null unless wrapped in Nullable<T>, cannot inherit, and are boxed when converted to object or an interface.

Example

struct Point { public int X, Y; }
class Shape  { public Point Origin; }        // Point lives inside the Shape's heap object

var a = new Point { X = 1 };
var b = a; b.X = 2;                          // a.X is still 1: copy
var s1 = new Shape(); var s2 = s1; s2.Origin.X = 9;   // s1.Origin.X is 9: alias

Func<int> f = () => a.X;                     // 'a' is now a field of a heap-allocated closure

Follow-ups

  • Is string a value type? It behaves like one. - Reference type with value-like semantics because it is immutable and overrides Equals/==.
  • When should a struct be preferred? - Small (guideline: 16 bytes or less), immutable, logically a single value, short-lived or stored in bulk arrays; otherwise a class.
  • What does .NET 10's JIT change here? - Escape analysis now stack-allocates small non-escaping objects, arrays and delegates, so "class means heap" is no longer strictly true in hot, inlined code.

Wrong answer

"Value types are on the stack, reference types on the heap." It is the textbook line and it is wrong often enough to cause real bugs (structs in classes, captured structs, async locals). The interviewer is fishing for whether you say "copy semantics" first.

screenerWhat is boxing, when does it happen silently, and why does it matter?

Answer

Boxing allocates a heap object that wraps a copy of a value type so it can be treated as object or an interface; unboxing copies it back out and requires the exact type. It happens silently when you pass a struct to a parameter typed object or an interface, call a non-overridden ToString/Equals/GetHashCode on a struct, use a struct with a non-generic collection, format with string interpolation on older frameworks, or call Enum methods like HasFlag on .NET Framework. It matters because it allocates (GC pressure) and because mutations to the box do not affect the original - the source of "I changed the struct and nothing happened". Generics avoid it: IEquatable<T>, IComparable<T>, List<T>, constrained generic calls (where T : IFoo) dispatch without boxing.

Example

int n = 42;
object o = n;              // box
IComparable c = n;         // box
Console.WriteLine($"{n}"); // no box on modern .NET: DefaultInterpolatedStringHandler has ISpanFormattable path

static void Print<T>(T v) where T : ISpanFormattable { ... }  // no box, constrained call
static void Print(object v) { ... }                            // box for any struct

Follow-ups

  • Does calling an interface method on a struct always box? - Directly on a struct-typed variable, no (the compiler calls the method); through a variable typed as the interface, yes; in a constrained generic, no.
  • How does a struct implementing IEquatable<T> affect Dictionary<TKey,...>? - EqualityComparer<T>.Default uses it and skips the box that object.Equals would incur on every lookup.
  • Why is Nullable<T> boxing special? - Boxing a null int? yields a null reference, not a box; boxing a non-null one boxes the underlying int.

Wrong answer

"Boxing is slow, so avoid structs." Structs used with generics never box; the mistake is using structs through object/interfaces. Candidates who ban structs instead of understanding the dispatch rules get corrected in review.

midDescribe the generational GC: gen0/1/2, LOH, POH, and what makes a collection expensive.

Answer

The GC is generational and mostly-compacting. New objects go to gen0; survivors of a gen0 collection are promoted to gen1, then gen2. Gen0 collections are frequent and cheap because most objects die young and only the live ones are traced and copied; gen2 ("full") collections trace the whole heap and are what you see as pauses. Objects of 85,000 bytes or more go straight to the Large Object Heap, which is logically part of gen2 and not compacted by default (fragmentation risk; GCSettings.LargeObjectHeapCompactionMode can force it once). .NET 5 added the Pinned Object Heap for objects that must never move (buffers pinned for I/O) so pinning stops fragmenting gen0. Since .NET 7 the heap is organised in regions rather than segments, which makes memory return to the OS more predictable. Cost drivers: the number of live objects and references (not garbage), object graphs with many pointers, mid-life crises (objects surviving into gen2 then dying, e.g. cached-then-evicted buffers), and LOH churn (each allocation there triggers gen2 budget accounting).

Example

// LOH churn: a 1 MB buffer per request lands on the LOH and drives gen2 collections
var buffer = new byte[1_048_576];

// fix: rent and return
var rented = ArrayPool<byte>.Shared.Rent(1_048_576);
try { Use(rented.AsSpan(0, 1_048_576)); }
finally { ArrayPool<byte>.Shared.Return(rented); }

// watch it: dotnet-counters monitor System.Runtime  -> gen0/1/2 count, LOH size, % time in GC

Follow-ups

  • Why does the LOH threshold sit at 85,000 bytes? - Empirically chosen: above it copying costs more than the fragmentation it avoids; it has never changed and is tunable with GCLOHThreshold.
  • What is a "mid-life crisis"? - Objects that live just long enough to be promoted to gen2 and then die, so they are collected only by expensive full GCs; typical of caches with short TTLs and per-request pooled objects.
  • What does % Time in GC above ~10% tell you? - Allocation rate or survival rate is too high for the heap configuration; find the allocators with dotnet-trace/PerfView before touching GC settings.
  • Is a double[] of 11,000 elements on the LOH? - Yes: 88,000 bytes. Historically double arrays over 1,000 elements were special-cased on 32-bit for alignment; not on 64-bit.

Wrong answer

"Call GC.Collect() after a big batch to free memory." It forces a full blocking collection, promotes everything still alive, and wrecks the tuning heuristics. The only defensible uses are benchmarks and a one-off after loading a large static dataset at startup, with GCCollectionMode.Optimized.

seniorWorkstation vs server GC, concurrent/background GC, and DATAS: how do you pick for a containerised service?

Answer

Workstation GC uses one heap and collects on the allocating thread (concurrent mode by default: gen2 happens in the background while the app runs). Server GC creates one heap and one dedicated GC thread per core, collecting in parallel for higher throughput at the cost of more memory and longer individual pauses; ASP.NET Core defaults to it. In containers the classic problem was server GC reserving per-core heaps sized for the host, blowing container memory limits; .NET reads cgroup limits and, since .NET 9, enables DATAS (Dynamic Adaptation To Application Sizes) by default for server GC, which starts with one heap and grows/shrinks heap count and gen0 budget based on live data, so memory tracks the workload instead of the core count. Pick: server GC + DATAS for request-serving services with more than a couple of cores; workstation for sidecars, CLI tools and single-core pods; set GCHeapHardLimit/GCHeapHardLimitPercent when the limit must be enforced below the cgroup value. Verify with dotnet-counters and GC.GetGCMemoryInfo(), not folklore.

Example

<!-- .csproj -->
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
  <GarbageCollectionAdaptationMode>1</GarbageCollectionAdaptationMode> <!-- DATAS; default on .NET 9+ server GC -->
</PropertyGroup>
<!-- runtimeconfig / env: DOTNET_GCHeapHardLimitPercent=0x4B (75%) -->

Follow-ups

  • Why would you turn DATAS off? - Latency-critical services with a steady heap where the adaptive gen0 budget causes more frequent gen0s; measure p99 with and without.
  • What is GCSettings.LatencyMode for? - SustainedLowLatency avoids blocking gen2 during a critical window; NoGCRegion pre-allocates and suspends GC for a bounded allocation budget (trading floors, frame rendering).
  • How does .NET see a Kubernetes memory limit? - Via cgroups; the default hard limit is 75% of the container limit. Requests vs limits confusion is the usual OOMKilled root cause.
  • What about GC "conserve memory" mode? - GCConserveMemory (0-9) makes gen2 compact more aggressively to trade CPU for footprint.

Wrong answer

"Always use server GC, it's faster." On a 0.5-CPU pod it is slower and can fail to start under a small limit; and pre-.NET 9 it was the standard cause of "our pods use 4× the memory of the Java ones". The senior answer names the trade-off and DATAS.

seniorWhat are defensive copies with structs, and how do readonly struct, in, and ref readonly avoid them?

Answer

When you call a method or property on a struct through a readonly field, an in parameter or a ref readonly local, the compiler must guarantee the struct is not mutated; since a non-readonly struct's method may mutate this, the compiler silently copies the whole struct first and calls the method on the copy. For a 4-byte struct that is nothing; for a 64-byte matrix in a tight loop it is a hidden copy per call. Declaring the struct readonly struct (or individual members readonly, C# 8) promises no mutation, so the copy disappears. Pass large structs with in (readonly reference) or ref readonly (C# 12, warns if you pass an rvalue) and return them by ref readonly to avoid copies end to end. The same reasoning is why mutable structs in List<T> indexers "don't change": the indexer returns a copy.

Example

public readonly struct Vec3(double x, double y, double z)   // readonly: no defensive copies
{
    public double X { get; } = x; public double Y { get; } = y; public double Z { get; } = z;
    public double Dot(in Vec3 o) => X * o.X + Y * o.Y + Z * o.Z;
}

static double Sum(ReadOnlySpan<Vec3> vs, in Vec3 dir)
{
    double s = 0;
    foreach (ref readonly var v in vs) s += v.Dot(dir);       // no copies in the loop
    return s;
}

var list = new List<MutablePoint> { new() };
list[0].X = 5;                 // CS1612: cannot modify the return value - it is a copy
CollectionsMarshal.AsSpan(list)[0].X = 5;   // ref access when you really need it

Follow-ups

  • How do you see a defensive copy? - Look at the IL/JIT asm (SharpLab, DOTNET_JitDisasm): a ldobj/stack copy before the call; or benchmark in with and without readonly struct.
  • Why is in on a small struct a pessimisation? - It passes a pointer, so every access is an indirection; for structs of 16 bytes or less pass by value.
  • What does ref readonly add over in in C# 12? - It documents that the callee wants a reference to a variable (not a temp) and warns when you pass an rvalue; useful for APIs like ReadOnlySpan constructors.

Wrong answer

"Mark parameters in to make struct passing fast." Without readonly struct every member call on that parameter copies anyway, so the code is slower than before. This is the follow-up interviewers use to distinguish people who have actually measured it.

midWhat is a ref struct (e.g. Span<T>), what can it not do, and what changed in C# 13?

Answer

A ref struct is a value type that may contain a managed pointer (a ref field, C# 11) and is therefore restricted to the stack: it cannot be boxed, cannot be a field of a class or a normal struct, cannot be captured by a lambda, cannot be a generic type argument (pre-C# 13), and cannot live across an await or yield. Span<T> and ReadOnlySpan<T> are the canonical ones: a ref T plus a length, pointing into an array, a string, stackalloc memory or native memory, so the same code handles all four without copying. C# 13 relaxed two things: generics can declare where T : allows ref struct so Span<T> can flow through generic helpers, and ref/unsafe locals are allowed in iterators and async methods as long as they do not cross a suspension point. C# 14 adds first-class implicit span conversions (array to span, span to read-only span) so spans participate naturally in overload resolution and extension receivers.

Example

static int ParseFirstNumber(ReadOnlySpan<char> s)
{
    int end = s.IndexOfAnyExcept("0123456789".AsSpan());
    return int.Parse(end < 0 ? s : s[..end]);
}

ParseFirstNumber("123abc");             // string -> ReadOnlySpan<char> implicit
Span<byte> buf = stackalloc byte[256];  // stack memory, safe: no pointer syntax

// C# 13: generic code that accepts ref structs
static void Fill<T>(T target) where T : allows ref struct, IFillable { target.Fill(); }

// not allowed: async Task F() { Span<int> s = stackalloc int[4]; await Task.Yield(); Use(s); } // CS4012

Follow-ups

  • How do you keep a slice across an await? - Use Memory<T>/ReadOnlyMemory<T> (a heap-safe struct over an array or MemoryManager) and call .Span at the point of use.
  • What does scoped mean? - It tells the compiler a ref/ref struct parameter does not escape the method, relaxing the lifetime rules for callers (e.g. passing a stackalloc'd span).
  • Why does stackalloc in a loop blow the stack? - The memory is released at method exit, not per iteration; hoist it or use ArrayPool above ~1 KB.

Wrong answer

"A ref struct is a struct passed by reference." It is a struct that may hold references to stack memory, which is why the compiler restricts where it can go. Confusing it with ref parameters is a screener fail for anyone claiming span experience.

midFinalizers, IDisposable and SafeHandle: what is the modern guidance for owning an unmanaged resource?

Answer

A finalizer (~T()) runs on the dedicated finalizer thread after the GC finds the object dead, with no ordering guarantees, no guarantee of ever running at process exit on .NET Core, and a cost: finalizable objects survive one extra collection and are promoted. Modern guidance is that application code should almost never write one: wrap the raw handle in a SafeHandle subclass (which has its own critical finalizer and reference counting that prevents handle-recycling races), and implement IDisposable on your type to dispose the SafeHandle and other IDisposable fields. The full "Dispose pattern" with Dispose(bool) and GC.SuppressFinalize exists for unsealed classes that directly own raw handles; for sealed classes owning only managed disposables, a plain Dispose that disposes fields is enough. Add IAsyncDisposable when disposal does I/O (flushing a stream, closing a connection).

Example

sealed class NativeBuffer : IDisposable
{
    private readonly SafeBufferHandle _h;             // SafeHandle subclass: closes via NativeMemory.Free
    public NativeBuffer(nuint size) => _h = SafeBufferHandle.Allocate(size);
    public void Dispose() => _h.Dispose();           // no finalizer needed here
}

sealed class BufferedWriter : IAsyncDisposable
{
    private readonly Stream _s;
    public async ValueTask DisposeAsync() { await _s.FlushAsync(); await _s.DisposeAsync(); }
}

Follow-ups

  • Why is GC.SuppressFinalize(this) called in Dispose? - So an object disposed deterministically does not pay the finalization promotion; it is only meaningful when the type declares a finalizer.
  • What happens to exceptions thrown in a finalizer? - They crash the process. Finalizers must never throw and must not touch other managed objects that may already be finalized.
  • Does using call Dispose if the constructor throws? - No: the object was never assigned. Handle partially-constructed state inside the constructor.
  • Why prefer SafeHandle over IntPtr in P/Invoke? - The marshaller increments its refcount during the call, so another thread cannot close and recycle the handle mid-call.

Wrong answer

"Implement the full Dispose pattern with a finalizer on every disposable class, to be safe." It adds a finalizer that makes every instance survive an extra GC and gains nothing when the class holds only managed resources. Interviewers hear this and ask what the finalizer would actually clean up.

seniorA service's memory grows steadily until the pod is OOM-killed. Walk me through finding the leak in managed code.

Answer

First confirm it is managed heap and not native or fragmentation: dotnet-counters (or the OpenTelemetry runtime metrics) show gen2 size and LOH size climbing after each full GC - if working set climbs but the managed heap is flat, suspect native memory (SkiaSharp, SQLite, HTTP handlers) or the GC not returning regions. Then take two dotnet-gcdump snapshots minutes apart under load and diff by type count and retained size; the growing type is rarely the culprit itself - follow its retention path to the root. The usual roots: a static or singleton-held List/Dictionary/cache without eviction, event handlers subscribed to a long-lived publisher (the subscriber is kept alive by the delegate), IDisposables never disposed (timers, CancellationTokenRegistrations, HttpClient handlers created per call), captured closures in a long-lived lambda, AsyncLocal flowing into a background loop, and MemoryCache with no size limit. For deep dives use dotnet-dump collect and dumpheap -stat, gcroot in the SOS analyzer. Fix, then add a memory-growth assertion to the load test.

Example

dotnet-counters monitor -p 1234 --counters System.Runtime[gc-heap-size,gen-2-size,loh-size,working-set]
dotnet-gcdump collect -p 1234 -o t0.gcdump   # then again 10 minutes later
# open both in Visual Studio / PerfView, diff "Inclusive size by type", walk the root path
dotnet-dump collect -p 1234 && dotnet-dump analyze core_1234
> dumpheap -stat          # types by count/size
> dumpheap -mt <MT>       # instances of the suspicious type
> gcroot <address>        # who keeps it alive

Follow-ups

  • Why do event subscriptions leak in the "wrong" direction? - The publisher holds the delegate, the delegate holds the subscriber's this; a short-lived subscriber to a long-lived publisher lives as long as the publisher.
  • How does WeakReference<T> help a cache? - It lets the GC reclaim entries under pressure; but it makes the cache non-deterministic - prefer explicit size limits and MemoryCache compaction.
  • What does an "OOMKilled with a small managed heap" point to? - Native leaks, too many threads (1 MB stack each), or the GC hard limit set above the cgroup limit.
  • Could it be not a leak at all? - Yes: a gen2 heap that grows until the GC decides to collect is normal; a leak is growth that survives forced full GCs across snapshots.

Wrong answer

"Add GC.Collect() on a timer / raise the memory limit." Neither finds the root. The candidate who cannot name gcroot or a retention path has not actually debugged a .NET leak.

seniorWhat changed in the .NET 10 JIT around allocations (escape analysis, stack allocation) and how should it change your coding guidance?

Answer

.NET 10 (November 2025) extended the JIT's escape analysis so that objects proven not to escape a method - after inlining - can be allocated on the stack instead of the heap; it covers small reference-type objects, small fixed-size arrays, and delegates whose closure does not escape, and it works together with guarded devirtualisation (from Dynamic PGO) so that a lambda passed to an inlined method may never allocate. Practical effect: patterns like a short-lived Tuple, a small array passed to a callee, or a Func passed to a hot helper can become allocation-free in tier-1 code. Guidance change: do not contort code into structs and manual inlining "to avoid allocations" until BenchmarkDotNet on the current runtime says it matters, but keep the guarantees where correctness depends on them (Span, pooling, ValueTask on real hot paths), because escape analysis is best-effort and silently gives up when an object flows into a non-inlined call, a field, or an exception path. .NET 11 continues the work (stack-allocated boxes, more inlining of generic virtual methods).

Example

// .NET 10: after inlining, the delegate and closure may not allocate at all
static int CountMatching(int[] xs, int threshold)
    => Count(xs, x => x > threshold);          // closure captures 'threshold'

static int Count(int[] xs, Func<int, bool> pred)
{
    int n = 0;
    foreach (var x in xs) if (pred(x)) n++;   // GDV + inlining -> direct compare
    return n;
}
// Verify, don't assume: BenchmarkDotNet [MemoryDiagnoser] shows Allocated: 0 B (or not)

Follow-ups

  • What defeats escape analysis? - Storing the object in a field or static, passing it to a non-inlined method, returning it, capturing it in an escaping closure, or throwing it.
  • Does this apply to NativeAOT and ReadyToRun? - Partially: the analysis needs the inlining decisions; without tiered PGO some GDV-dependent cases do not happen in AOT.
  • How do you check what the JIT did? - DOTNET_JitStdOutFile + DOTNET_JitDisasm=Method on a Checked/Release runtime, or the [MemoryDiagnoser] in BenchmarkDotNet as the pragmatic proxy.

Wrong answer

"The JIT now stack-allocates objects, so allocations are no longer a concern." It is best-effort and narrow; a team that stops measuring on that basis ships regressions the first time a helper stops being inlined.

principalDesign the memory strategy for a high-throughput message processor: pooling, struct vs class for messages, GC mode, and how you will prove it works.

Answer

Start from the allocation budget: at, say, 200k messages/s a single 1 KB allocation per message is 200 MB/s of gen0 churn, which is survivable, whereas a 100 KB buffer per message is LOH churn that will dominate. Design so the steady state allocates near zero per message: rent I/O buffers from ArrayPool<byte>.Shared or use System.IO.Pipelines, parse with ReadOnlySpan<byte>/Utf8Parser/Utf8JsonReader straight from the buffer, represent parsed messages as immutable classes only if they live beyond the pipeline stage (otherwise a readonly record struct passed by in), and avoid LINQ, string concatenation and boxing on the hot path. Use server GC with DATAS, verify gen2 count stays flat and % time in GC stays under ~5% under a sustained load test, and set a hard heap limit below the container limit. Prove it with BenchmarkDotNet [MemoryDiagnoser] per stage (target: 0 B allocated), a CI load test that fails on allocation-rate or gen2-count regressions, and production dashboards on the runtime counters. Communicate the rules as a short doc with the numbers, not as "avoid allocations".

Example

// stage boundary: a struct message referencing pooled memory, no per-message heap objects
public readonly record struct Frame(ReadOnlyMemory<byte> Payload, long Offset, IMemoryOwner<byte> Owner) : IDisposable
{
    public void Dispose() => Owner.Dispose();   // returns the buffer to the pool
}

await foreach (var frame in reader.ReadFramesAsync(ct))     // Channel<Frame>, bounded
{
    using (frame)
    {
        var r = new Utf8JsonReader(frame.Payload.Span);
        Handle(ref r);                                       // ref struct reader, zero copies
    }
}

Follow-ups

  • Why not class messages everywhere and let .NET 10 escape analysis handle it? - Messages flow through channels and awaits, so they escape by construction; escape analysis cannot help across stages.
  • How do you keep pooled buffers from being used after return? - Own the lifetime in one type (IMemoryOwner<T>), dispose once at the stage that finishes with it, and run tests with a poisoning pool that scrubs returned buffers.
  • What would make you choose workstation GC here? - Only if the processor runs on one or two cores, or shares the box with something latency-sensitive that server GC's pauses would hurt.
  • What is the first thing to look at when p99 spikes every ~30 s? - Gen2 collections: correlate the spike with gen-2-gc-count, then find what is surviving into gen2 (usually a cache or a batch).

Wrong answer

"Make everything a struct and turn off the GC with NoGCRegion." Structs that escape get copied and boxed, and NoGCRegion is a bounded budget that throws when exceeded - it is a tool for a few milliseconds, not a strategy for a service.

screenerAbstract class vs interface in modern C# - and did default interface methods change the answer?

Answer

An abstract class is an "is-a" base that can carry state (fields), constructors, non-public members and a partial implementation; a type gets exactly one. An interface is a "can-do" contract; a type implements many, and it is the unit of substitution for DI and testing. Default interface methods (C# 8) let an interface ship an implementation so you can add a member without breaking implementers, and static abstract/virtual members (C# 11) let interfaces describe static shape (operators, factories) for generic math. They did not make interfaces into abstract classes: interfaces still have no instance state, default implementations are only reachable through the interface type, and versioning is their main purpose. Rule of thumb: interface for the public contract, abstract class only when there is genuinely shared state or a template-method skeleton, and prefer composition to either.

Example

public interface ILogger
{
    void Log(LogLevel level, string message);
    void Info(string message) => Log(LogLevel.Info, message);   // default: implementers get it for free
}

public abstract class Repository<T>(DbContext db)                 // shared state + template method
{
    protected DbContext Db { get; } = db;
    public async Task<T?> FindAsync(int id, CancellationToken ct) => await Query().FirstOrDefaultAsync(Match(id), ct);
    protected abstract IQueryable<T> Query();
    protected abstract Expression<Func<T, bool>> Match(int id);
}

Follow-ups

  • Can a class call a default interface method on itself? - Only by casting to the interface (((ILogger)this).Info(...)); the member is not part of the class's own surface.
  • What is the diamond problem with DIMs? - Two interfaces provide the same default; the class must override explicitly or it fails to compile - the "most specific override" rule resolves only proper hierarchies.
  • When is an abstract class the wrong tool for reuse? - When subclasses share behaviour but not identity; pull the behaviour into a component and inject it.

Wrong answer

"Interfaces can't have implementations." True until 2019; saying it in 2026 flags stale knowledge. The nuanced answer is that they can, and you should mostly use it for versioning.

screenerWhat do record, record struct and readonly record struct give you, and when is a record the wrong choice?

Answer

A record class (C# 9) is a reference type with compiler-generated value equality (Equals, GetHashCode, ==/!= based on all instance fields and the runtime type), a ToString that prints members, deconstruction for positional records, and non-destructive mutation via with (which calls a copy constructor and then sets init properties). A record struct (C# 10) is the value-type version; positional record structs are mutable unless you write readonly record struct, which is what you almost always want. Records are ideal for DTOs, messages, value objects and immutable snapshots. They are wrong for EF Core entities and anything with identity or mutable lifecycle: value equality on a mutable entity makes it change identity when a field changes, breaks it as a dictionary key, and with silently creates a second instance that the change tracker does not know about. Inheritance between records works but equality includes the exact type, which surprises people comparing a base-typed reference.

Example

public sealed record Money(decimal Amount, string Currency)
{
    public Money Add(Money o) => o.Currency == Currency ? this with { Amount = Amount + o.Amount }
                                                       : throw new InvalidOperationException();
}
public readonly record struct Point(int X, int Y);

var a = new Money(10, "EUR"); var b = new Money(10, "EUR");
Console.WriteLine(a == b);              // True: value equality
Console.WriteLine(a);                   // Money { Amount = 10, Currency = EUR }
var (x, y) = new Point(1, 2);           // deconstruction

Follow-ups

  • What does with do on a record class? - Calls the protected copy constructor (Money(Money original)) then assigns the named init properties; you can customise the copy constructor.
  • How does equality handle a collection property? - Reference equality on the collection; two records with equal-content lists are not equal unless you override Equals.
  • Record vs class with primary constructor? - A record's positional parameters become public init properties; a class's primary-constructor parameters are just captured parameters (see the primary-constructor question).

Wrong answer

"Records are immutable." Positional record classes are init-only, but you can declare mutable properties, and positional record structs are mutable by default. Candidates who put records on EF entities "because they are immutable" get both facts wrong.

midExplain the Equals / GetHashCode / == / IEquatable<T> contract and the classic bug when it is violated.

Answer

The contract: if a.Equals(b) then a.GetHashCode() == b.GetHashCode(); equality is reflexive, symmetric, transitive, and consistent while the object is unchanged. Dictionary/HashSet bucket by hash code first and call Equals only within the bucket, so an object whose hash changes after insertion (a mutable key) is lost - lookups fail while enumeration still shows it. == is a separate static operator: for classes it defaults to reference equality unless overloaded, so overriding Equals without == gives two different answers; records overload it consistently. Implement IEquatable<T> so generic collections avoid the boxing and type test of object.Equals. Use HashCode.Combine (randomised per process - never persist or compare hash codes across processes) and include the same members in both methods. Floating-point NaN and the -0.0/0.0 pair are the famous edge cases.

Example

public sealed class Sku : IEquatable<Sku>
{
    public string Code { get; }
    public Sku(string code) => Code = code;
    public bool Equals(Sku? o) => o is not null && string.Equals(Code, o.Code, StringComparison.OrdinalIgnoreCase);
    public override bool Equals(object? o) => Equals(o as Sku);
    public override int GetHashCode() => StringComparer.OrdinalIgnoreCase.GetHashCode(Code);   // same comparison as Equals!
    public static bool operator ==(Sku? a, Sku? b) => a is null ? b is null : a.Equals(b);
    public static bool operator !=(Sku? a, Sku? b) => !(a == b);
}

Follow-ups

  • Why is a case-insensitive Equals with a case-sensitive hash the classic bug? - "abc" and "ABC" are equal but hash to different buckets; the set contains both.
  • Why are string hash codes randomised? - Hash-flooding DoS mitigation (since .NET Core 1.0 / Framework opt-in); it is also why you cannot store hash codes in a database.
  • How do you compare two objects structurally without owning them? - Pass an IEqualityComparer<T> to the collection; do not override equality on someone else's type.
  • What does ReferenceEquals do for boxed ints? - Two boxes of the same value are different objects: false. Always a fun trap.

Wrong answer

"Override Equals; GetHashCode can stay default because we don't use it as a key." The compiler warns (CS0659) precisely because every LINQ Distinct, GroupBy and Contains on a set uses it; the bug appears the first time someone does.

midvirtual / override / new / sealed: what does method hiding actually do, and why seal classes?

Answer

virtual puts a method in the vtable; override replaces the slot, so a call through the base type dispatches to the derived implementation. new does not touch the slot: it declares an unrelated method with the same name, so the method called depends on the static type of the reference - the classic "why does it call the base version through the interface" surprise; it exists for versioning when a base class later adds a member with your name, and should otherwise be a review flag. sealed on an override stops further overriding; sealed on a class stops derivation, documents intent, and lets the JIT devirtualise and inline calls through that type without a guard - the .NET team seals BCL types by default for that reason, and CA1852 nags you to seal internal classes. Constructors run base-first, so a virtual call from a base constructor hits the derived override before the derived fields are initialised: never call virtuals from constructors.

Example

class Base { public virtual string Who() => "base"; public string Name() => "base"; }
class Derived : Base { public override string Who() => "derived"; public new string Name() => "derived"; }

Base b = new Derived();
b.Who();    // "derived": virtual dispatch
b.Name();   // "base":    hiding, static type wins
((Derived)b).Name();   // "derived"

public sealed class OrderTotal { ... }   // JIT: direct calls, inlinable, no type checks on casts

Follow-ups

  • What is guarded devirtualisation? - With Dynamic PGO the JIT sees which concrete type dominated a virtual/interface call site and emits if (type == Observed) inlined else virtual call.
  • Why is protected internal different from private protected? - OR vs AND of the two accessibilities (C# 7.2 added the AND form).
  • What is a covariant return (C# 9)? - An override may return a more derived type than the base declares: override Derived Clone().

Wrong answer

"new is like override but without the base needing virtual." It is the opposite: it opts out of polymorphism. Someone who uses new to "override" a non-virtual method has a latent bug wherever the object is used through the base type.

seniorPrimary constructors on classes (C# 12) vs on records: what is captured, what is a property, and what are the pitfalls?

Answer

On a record, positional parameters become public init properties that participate in equality and deconstruction. On a class or struct (C# 12), primary-constructor parameters are just parameters in scope for the whole type body: they become compiler-generated private fields only if a member uses them outside an initialiser, otherwise they are consumed by the initialisers and disappear. Pitfalls: they are mutable (there is no readonly), so a method can reassign one and quietly rebind every later use; assigning a parameter to a field and using the parameter elsewhere double-captures it (one field per use); the captured state is invisible to reflection-based tooling expecting fields named by convention; and this()-chained constructors must call the primary one. They shine for DI-heavy services and small immutable helpers; the team rule that works is "parameters are used only in initialisers or are treated as readonly" plus the IDE analyzer that flags reassignment.

Example

public sealed class OrderService(IOrderRepo repo, ILogger<OrderService> log)
{
    private readonly IOrderRepo _repo = repo;    // assigned: 'repo' is not captured ...
    public Task SaveAsync(Order o, CancellationToken ct)
    {
        log.LogInformation("saving {Id}", o.Id);  // ... but 'log' IS captured as a hidden field
        return _repo.SaveAsync(o, ct);
    }
    public void Oops() => log = null!;            // compiles: parameters are mutable
}

public record Customer(string Name);              // Name is a public init property, part of equality

Follow-ups

  • How do you validate a primary-constructor argument? - In a field initialiser: private readonly IRepo _repo = repo ?? throw new ArgumentNullException(nameof(repo));.
  • Are primary constructors on structs safe? - Yes, but a captured parameter becomes a field, which changes the struct's size and default-copy behaviour.
  • What about partial constructors in C# 14? - A defining and an implementing declaration in different partial parts, mainly for source generators; only the implementing part may have a this()/base() initialiser.

Wrong answer

"Primary-constructor parameters on classes are readonly properties, like records." They are neither readonly nor properties; assuming so is why teams hit the "reassigned in a method" bug and why Equals on such a class does not do what people expect.

midImmutability toolkit: init, required, readonly, with, and immutable collections - how do they combine?

Answer

init accessors (C# 9) allow setting a property only during construction or in an object initialiser, so you get object-initialiser ergonomics without a settable API. required (C# 11) makes the compiler refuse an initialiser that omits the member, which replaces long constructors for DTOs and options and works with source-generated JSON. readonly on fields prevents reassignment after construction (for structs, also blocks defensive copies); readonly struct applies it to every field. with expressions clone records (and structs, C# 10) while changing some init members. None of these make contained collections immutable: expose IReadOnlyList<T>, ImmutableArray<T> or FrozenDictionary (.NET 8) rather than List<T> behind a get-only property, because the caller can still Add to the list. The combination for a modern value object is sealed record + required init members + read-only collection types.

Example

public sealed record CreateUserRequest
{
    public required string Email { get; init; }
    public required string DisplayName { get; init; }
    public IReadOnlyList<string> Roles { get; init; } = [];          // collection expression, C# 12
}

var req = new CreateUserRequest { Email = "a@b.c", DisplayName = "A" };   // omit Email -> CS9035
var admin = req with { Roles = ["admin"] };

Follow-ups

  • Can a constructor satisfy required? - Mark it [SetsRequiredMembers] and the compiler stops demanding them in initialisers; it also stops checking, so use sparingly.
  • How does init interact with readonly fields? - An init accessor may assign readonly fields because it runs during construction from the compiler's point of view.
  • Why is ImmutableList<T> often the wrong choice? - It is an AVL tree with O(log n) indexing and heavy allocation; ImmutableArray<T> or FrozenSet is right for read-mostly data.

Wrong answer

"A get-only List<T> property makes the object immutable." The reference is fixed; the list is not. It is the most common immutability bug in DTOs and the interviewer will ask "what stops me calling Add?"

seniorStatic abstract interface members and generic math (C# 11): what problem do they solve and how do they dispatch?

Answer

Before C# 11 you could not write a generic Sum<T> because interfaces could not declare operators or static factories; you needed per-type overloads or a boxing dynamic hack. Static abstract (and static virtual) interface members let an interface require static abstract T operator +(T, T) or static abstract T Parse(string), and the BCL ships a hierarchy (INumber<T>, IAdditionOperators, IParsable<T>, ISpanFormattable, ...) that all numeric primitives implement. Dispatch is compile-time through the type parameter: the call T.Parse(s) is resolved by the JIT for each value-type instantiation (fully specialised, inlined, no boxing) and through a shared generic dictionary for reference types. You cannot call them through an instance or a plain interface reference; they only work in constrained generic code, which is the point - they are for algorithms, not for polymorphic collections.

Example

using System.Numerics;

{
    T acc = T.Zero;
    foreach (var x in xs) acc += x;
    return acc;
}
Sum<int>([1, 2, 3]);            // specialised: plain adds
Sum<decimal>([1.5m, 2.5m]);

public interface IEntity<TSelf> where TSelf : IEntity<TSelf>
{
    static abstract TSelf Create(Guid id);   // generic factory without reflection
}

Follow-ups

  • Why the curiously recurring TSelf pattern? - So the operator signature can mention the implementing type itself (static abstract TSelf operator +(TSelf, TSelf)).
  • Does this work in .NET Framework? - No: it needs runtime support (.NET 7+); it is the clearest "why we can't stay on Framework" example.
  • Static virtual vs static abstract? - Virtual has a default body, letting you add a static member to an interface later without breaking implementers.

Wrong answer

"You use it by calling the method on the interface, like INumber<int>.Zero." Static abstract members have no implementation on the interface; they are reachable only via a type parameter constrained to it.

seniorCovariance and contravariance: why is IEnumerable<out T> safe, why is List<T> invariant, and where does array covariance bite?

Answer

Variance is about substituting type arguments safely. out T (covariance) is allowed when T only appears in output positions: an IEnumerable<Dog> can be used as IEnumerable<Animal> because you only ever pull Dogs out, which are Animals. in T (contravariance) is allowed when T only appears in inputs: an IComparer<Animal> can serve as IComparer<Dog>. List<T> has T in both positions (Add takes one, the indexer returns one), so it must be invariant: a List<Dog> treated as List<Animal> would let you Add(new Cat()). Arrays are covariant for legacy reasons (Dog[] is an object[]), so the runtime must type-check every store into a reference-type array and throws ArrayTypeMismatchException when it fails - a small cost on every write and a real bug source. Variance applies only to interfaces and delegates, only with reference-type conversions (no IEnumerable<int> to IEnumerable<object>), and is why Func<in T, out TResult> is declared the way it is.

Example

IEnumerable<Dog> dogs = new List<Dog>();
IEnumerable<Animal> animals = dogs;            // OK: out T
IList<Animal> bad = (IList<Animal>)dogs;       // runtime InvalidCastException: invariant

Animal[] arr = new Dog[2];                     // compiles: array covariance
arr[0] = new Cat();                            // ArrayTypeMismatchException at runtime

Action<Animal> feed = a => a.Eat();
Action<Dog> feedDog = feed;                    // OK: in T

Follow-ups

  • Why is IReadOnlyList<out T> covariant but IReadOnlyDictionary<TKey,TValue> not? - TKey is used as an input in ContainsKey/indexer, so it cannot be out.
  • Why does the JIT skip the array store check for sealed element types? - If the element type has no subtypes, the stored reference must match exactly; another reason to seal.
  • Can a variant interface have a method with T in a ref parameter? - No; ref is both in and out.

Wrong answer

"List<Dog> should convert to List<Animal>; it's just a compiler limitation." It is a soundness rule; the array covariance hole shows exactly what goes wrong when the rule is skipped.

principalHow do you decide between class, struct, record and interface when modelling a domain, and what do you enforce in code review?

Answer

Decide by semantics first, performance second. Entities (things with identity and lifecycle) are classes with explicit identity-based equality and encapsulated state changes - never records, never public setters on invariants. Value objects (money, ranges, ids, coordinates) are sealed record or readonly record struct: small and hot ones as structs (strongly-typed ids, coordinates), the rest as records; equality is structural by definition. Messages, events, DTOs and options are records with required init members. Interfaces model capabilities and seams you actually substitute (repositories, clocks, gateways) - not one per class. Enumerated closed alternatives are today an abstract record with sealed derived records and an exhaustive switch; note that C# 15 previews union types and the closed modifier for exactly this, so plan the migration. In review I enforce: sealed by default, no mutable structs, Equals/GetHashCode never on mutable state, collections exposed read-only, no records as EF entities, no new hiding, and public types documented with their thread-safety and equality semantics.

Example

public readonly record struct OrderId(Guid Value)          // strongly typed id, 16 bytes
{ public static OrderId New() => new(Guid.CreateVersion7()); }    // .NET 9: time-ordered GUIDs

public sealed class Order                                   // entity: identity + invariants
{

    public IReadOnlyList<OrderLine> Lines => _lines;
    public void AddLine(Sku sku, int qty) { if (qty <= 0) throw new ArgumentOutOfRangeException(nameof(qty)); _lines.Add(new(sku, qty)); }
}

public abstract record PaymentResult                        // closed set today; C# 15 'union' tomorrow
{
    public sealed record Approved(string AuthCode) : PaymentResult;
    public sealed record Declined(string Reason) : PaymentResult;
}

  • How do you keep strongly-typed ids from being painful with EF, JSON and ASP.NET routing? - Value converters, a JsonConverter, and IParsable<T> so minimal APIs bind them; generate the boilerplate with a source generator.
  • When would you allow a mutable struct? - Only as a private implementation detail in a hot loop (an enumerator, an accumulator), never on a public surface.
  • How do you handle a team that wants records everywhere? - Show the EF change-tracker bug and the dictionary-key bug in a 10-line repro; rules land better with a failing test.

"Structs for performance, classes otherwise." Modelling by performance first yields mutable structs in collections and records on entities; the principal answer starts from identity vs value semantics and only then reaches for structs where measurement justifies it.

screenerWhat is deferred execution in LINQ, and what is the multiple-enumeration bug?

Answer

Most LINQ operators (Where, Select, OrderBy, GroupBy, Skip...) build a pipeline and do no work until something enumerates it: foreach, ToList/ToArray, Count(), First(), Any(). Each enumeration re-runs the whole pipeline from the source, so enumerating the same query twice executes the filters twice, hits the database twice, and can yield different results if the source changed. Streaming operators yield as they go; buffering ones (OrderBy, GroupBy, Reverse, ToLookup) must consume the whole input first. Materialise once (ToList()) when you need to iterate more than once, when the source is expensive, or when you hand the result to a caller who may enumerate at any time; return IEnumerable<T> from a method only when laziness is the point. The analyzer CA1851 flags possible multiple enumerations.

Example

var expensive = ids.Select(id => Fetch(id));      // nothing fetched yet
if (expensive.Any())                              // fetch #1 (first item)
    Console.WriteLine(expensive.Count());         // fetch every item again
var list = expensive.ToList();                    // once; reuse 'list'

IEnumerable<int> Seq() { Console.WriteLine("run"); yield return 1; }
var q = Seq().Where(x => x > 0);
foreach (var _ in q) {} foreach (var _ in q) {}   // prints "run" twice

Follow-ups

  • Count() vs Count vs Any()? - Count() enumerates fully unless the source is an ICollection (it checks); Any() stops at one; prefer Any() to Count() > 0, and .Count/.Length when you have them.
  • Does ToList() on an IQueryable matter more? - Yes: it is the moment the SQL executes; enumerating twice is two round-trips.
  • What does .NET's LINQ do to avoid re-enumeration internally? - TryGetNonEnumeratedCount (.NET 6) and the Iterator<T> fast paths that fuse Select/Where and special-case arrays and lists.

Wrong answer

"LINQ executes when you write the query, but lazily fetches items." Candidates who cannot say what triggers execution write if (q.Any()) foreach (var x in q) against a database and wonder why the log shows two queries.

midHow does yield return work, and what are the rules and costs of iterator methods?

Answer

The compiler turns an iterator method into a class implementing IEnumerable<T> and IEnumerator<T> with a state field, locals hoisted to fields, and a MoveNext that resumes at the last yield. The body does not run until the first MoveNext, which is why argument validation in an iterator fires late - split into a validating wrapper and a private iterator. yield break ends the sequence; finally blocks run when the enumerator is disposed (which foreach does), so early exit is safe. Rules: no yield inside try with a catch, no ref/out parameters, no yield in lambdas; C# 13 allows ref locals and unsafe blocks between yields. Costs: one object per enumeration (the same object doubles as enumerator on the first thread that calls GetEnumerator), interface dispatch per item, and no Count fast path. Iterators are the right tool for streaming and for composing lazy pipelines; they are the wrong tool for small, hot collections where an array is cheaper.

Example

public static IEnumerable<T> TakeWhileInclusive<T>(this IEnumerable<T> src, Func<T, bool> pred)
{
    ArgumentNullException.ThrowIfNull(src);          // eager: runs at call time
    return Iterator(src, pred);

    static IEnumerable<T> Iterator(IEnumerable<T> src, Func<T, bool> pred)
    {
        foreach (var x in src)
        {
            yield return x;                           // lazy: runs on MoveNext
            if (!pred(x)) yield break;
        }
    }
}

Follow-ups

  • Why can't you yield inside a try/catch? - A resume point inside a catch-protected region would need the exception state to be preserved across calls; the compiler forbids it (try/finally is fine).
  • Iterator vs returning List<T>? - Iterators are lazy and composable but hide cost; a list is explicit, countable and re-enumerable. Public APIs should be clear which one they are.
  • How does foreach over a List<T> avoid allocation? - List<T>.Enumerator is a struct; iterating through IEnumerable<T> boxes it. Same for Span<T> and Dictionary.

Wrong answer

"yield runs the method on a background thread and hands items over as they are produced." It is a single-threaded state machine. This confusion shows up as thread-safety worries in code that has none, and as missing them where Parallel is actually involved.

midClosures: what does a lambda capture, when does it allocate, and what was the foreach variable change?

Answer

A lambda that references a local, parameter or this captures it by reference to the variable, not by value: the compiler hoists the variable into a compiler-generated closure class (the <>c__DisplayClass) shared by every lambda in that scope, and the delegate points at a method on that object. Consequences: mutations after the lambda is created are visible inside it; the closure keeps everything it captured alive as long as the delegate lives; and creating the delegate allocates both the closure and the delegate (a non-capturing lambda is cached in a static). Loop variables are the classic trap: a for loop's variable is one variable shared by all iterations, so every lambda sees the final value; C# 5 changed foreach to declare a fresh variable per iteration, so foreach lambdas capture each element. Use static lambdas (C# 9) to have the compiler reject accidental captures on hot paths, and pass state through parameters (Func<TState, T, bool>) instead of capturing when it matters.

Example

var actions = new List<Action>();
for (int i = 0; i < 3; i++) actions.Add(() => Console.Write(i));
foreach (var a in actions) a();                   // 333  (one shared 'i')

foreach (var i in Enumerable.Range(0, 3)) actions.Add(() => Console.Write(i));  // 012 since C# 5

int threshold = 10;
var big = items.Where(x => x > threshold);        // closure holds 'threshold' (and it is mutable)
var alsoBig = items.Where(static x => x > 10);    // static: compiler forbids captures

Follow-ups

  • Why does capturing this in a long-lived callback leak? - The delegate holds the closure, the closure holds this; a timer or event holding the delegate keeps your whole object graph alive.
  • How does capture interact with Span<T>? - A ref struct cannot be hoisted to a heap field, so lambdas cannot capture spans (CS8175); use a local function or pass it in.
  • What did .NET 10 change? - Escape analysis can stack-allocate a closure and delegate that do not escape an inlined call; still measure.

Wrong answer

"Lambdas capture a copy of the variable's value at creation." That is how it works in some languages, and believing it in C# produces the 333 bug and "why did my lambda see the updated value" surprises.

seniorIEnumerable<T> vs IQueryable<T>: what are expression trees, and what silently changes when a query switches from one to the other?

Answer

IQueryable<T> LINQ operators take Expression<Func<...>> rather than delegates: the compiler emits an expression tree (a data structure describing the lambda) instead of IL, and a provider (EF Core, OData, Cosmos) translates the tree into SQL or another query language at enumeration time. IEnumerable<T> operators take compiled delegates and run in memory. The moment a query crosses from IQueryable to IEnumerable - a call to AsEnumerable(), a method the provider cannot translate, or simply assigning to a variable typed IEnumerable<T> - everything after it runs client-side on all rows fetched so far. EF Core 3+ throws on untranslatable expressions instead of silently evaluating them client-side, but implicit switches through variable types still fetch the whole table. Expression trees cannot contain statements, async, or most C# 6+ constructs (no ?., no pattern matching, no throw expressions), which is why repository lambdas look old-fashioned.

Example

IQueryable<Order> q = db.Orders.Where(o => o.Total > 100);      // becomes WHERE Total > 100
IEnumerable<Order> e = q;                                          // still not executed ...
var late = e.Where(o => o.Customer.IsVip);                        // ... but this filter runs in memory,
var rows = late.ToList();                                          // after SELECTing every order > 100

Expression<Func<Order, bool>> expr = o => o.Total > 100;          // data: Lambda(GreaterThan(Property(o, Total), Constant(100)))
Func<Order, bool> compiled = expr.Compile();                      // slow (~µs-ms), cache it

Follow-ups

  • How do you build a dynamic filter safely? - Compose expression trees (Expression.AndAlso, a parameter-replacing visitor, or a library like LinqKit) rather than string concatenation; parameters stay parameters in the SQL.
  • Why is Expression.Compile() a hot-path hazard? - It emits IL through DynamicMethod each time; cache compiled delegates per shape. On NativeAOT it falls back to an interpreter.
  • What is a specification pattern for? - Keeping Expression<Func<T,bool>> predicates reusable and testable, so the same rule runs in SQL and in memory.

Wrong answer

"They are the same thing; IQueryable just extends IEnumerable." Structurally true, semantically the whole point is that one is data-about-code and one is code. The candidate who "adds a .ToList() to fix a translation error" has moved the table into memory.

seniorHow does the runtime instantiate generics: code sharing, value-type specialisation, and what that means for performance?

Answer

Generic types and methods are real at runtime (unlike Java's erasure): List<int> and List<string> are distinct types with their own method tables. For value-type arguments the JIT compiles a separate, fully specialised copy per instantiation - T is int, calls on T are direct, and there is no boxing; this is why List<int> beats ArrayList and why struct comparers (where TComparer : struct, IComparer<T>) get inlined. For reference-type arguments the runtime shares one native code body for all instantiations (canonical form __Canon), passing a hidden generic dictionary to look up type-specific data (statics, exact types for new T(), virtual calls on constrained T); this saves code size but costs an indirection on some operations, which the .NET 8+ JIT increasingly removes with Dynamic PGO and (in .NET 11) generic virtual method inlining. Constraints (where T : struct/class/notnull/unmanaged/new()/IFoo/allows ref struct) exist to give the compiler the shape it needs; unmanaged enables pointer and sizeof use, notnull is nullability-only.

Example

// struct-based strategy: specialised, inlined, allocation-free
public readonly struct OrdinalIgnoreCase : IEqualityComparer<string>
{ public bool Equals(string? a, string? b) => string.Equals(a, b, StringComparison.OrdinalIgnoreCase);
  public int GetHashCode(string s) => s.GetHashCode(StringComparison.OrdinalIgnoreCase); }

static int CountDistinct<TComparer>(ReadOnlySpan<string> xs, TComparer cmp)
    where TComparer : struct, IEqualityComparer<string> { ... }     // cmp.Equals is a direct call

// generic dictionary lookup at runtime for reference T:
static T Make<T>() where T : new() => new T();                  // shared code, Activator-like lookup for class T

Follow-ups

  • Why are static fields in a generic class per instantiation? - Each closed type is a distinct type with its own statics; a "generic singleton" is a per-T singleton.
  • What is the cost of typeof(T) checks in shared code? - For value types the JIT folds them to constants (dead branches vanish); for reference types it is a dictionary lookup, so keep if (typeof(T) == typeof(int)) tricks for structs.
  • How does NativeAOT handle generics? - Everything is pre-generated; unknown instantiations at runtime (reflection over generics with value types) fail, so MakeGenericType with dynamic value types is an AOT warning.

Wrong answer

"C# generics are erased like Java's, so List<int> boxes." It is the opposite, and it is the reason generic collections replaced the non-generic ones. Getting this wrong undermines every performance claim that follows.

midDelegates vs events: what does the event keyword actually restrict, and how do you avoid the classic event leak?

Answer

A delegate is a type-safe, multicast, immutable method reference (Func, Action, Predicate, or your own); invoking a multicast delegate calls each target in order and the return value of the last one wins, and an exception in one target stops the rest. A public delegate-typed field lets any caller invoke it, assign it or wipe every subscriber with =. The event keyword wraps the field in add/remove accessors so outsiders can only +=/-=; only the declaring type can raise it. The BCL convention is EventHandler<TArgs> with (object? sender, TArgs e), raised via Handler?.Invoke(this, args) (thread-safe read of a snapshot). The leak: the publisher holds the delegate, the delegate holds the subscriber, so a subscriber that forgets -= lives as long as the publisher - fatal when the publisher is a static or a singleton. Fix with unsubscription in Dispose, weak-event patterns for UI frameworks, or replace long-lived events with IObservable/Channel that own explicit lifetimes.

Example

public sealed class Downloader
{
    public event EventHandler<ProgressEventArgs>? Progress;
    private void OnProgress(int pct) => Progress?.Invoke(this, new(pct));   // snapshot + null-conditional
}

sealed class ProgressBar : IDisposable
{
    private readonly Downloader _d;
    public ProgressBar(Downloader d) { _d = d; _d.Progress += OnProgress; }
    private void OnProgress(object? s, ProgressEventArgs e) { ... }

}

Follow-ups

  • Why Progress?.Invoke and not if (Progress != null) Progress(...)? - The two-step version can NRE if the last subscriber unsubscribes between the check and the call; ?. evaluates the field once.
  • Are delegates equal by value? - Yes: same target and method, which is how -= finds the handler to remove - so lambdas cannot be unsubscribed unless you keep the delegate instance.

"Events are just delegates with different syntax." The accessor encapsulation is the point; a candidate who cannot say why a public delegate field is wrong will also expose List<T> publicly.

seniorWhere does LINQ cost you in a hot path, what did recent runtimes optimise, and what is your team rule?

Answer

Costs: an iterator object per operator, a delegate per lambda (allocated once per query shape if non-capturing, per query if capturing), interface dispatch per element, and buffering operators that allocate arrays and copies (OrderBy, GroupBy, ToArray growing). None of that matters for a request handler filtering 50 items; all of it matters in a per-message loop at 100k/s or a game frame. Recent runtimes have narrowed the gap substantially: .NET 8/9 special-case arrays, lists and ranges inside Select/Where/Sum/Min/Max, vectorise numeric aggregates, fuse Select(...).Where(...) chains, and Dynamic PGO devirtualises and inlines the delegate calls; .NET 9 added CountBy, AggregateBy and Index to avoid GroupBy allocations, .NET 10 added Shuffle, LeftJoin and RightJoin. Team rule that survives contact: LINQ is the default everywhere except code that BenchmarkDotNet has shown to be allocation- or latency-critical; in those files use foreach over spans or arrays, and leave a comment naming the benchmark. Banning LINQ globally costs readability and correctness for no measurable gain.

Example

// request path: fine
var vip = customers.Where(c => c.IsVip).Select(c => c.Email).ToList();

// hot path after measuring: explicit loop over a span, zero allocations
static decimal TotalOver(ReadOnlySpan<Order> orders, decimal min)
{
    decimal sum = 0;
    foreach (ref readonly var o in orders) if (o.Total > min) sum += o.Total;
    return sum;
}

// .NET 9: no GroupBy materialisation
var counts = words.CountBy(w => w.Length);

Follow-ups

  • Is ToList() or ToArray() cheaper? - Roughly equal in modern .NET (both use a segmented builder); ToArray yields a tighter result, ToList lets you append. Use whichever matches the consumer's type.
  • What about PLINQ (AsParallel)? - Good for CPU-heavy, side-effect-free transforms over large in-memory data; ordering costs (AsOrdered), and it is wrong for I/O.
  • How do you catch LINQ regressions in CI? - BenchmarkDotNet with [MemoryDiagnoser] on the named hot methods and a threshold check on allocated bytes, not on wall time (noisy CI).

Wrong answer

"We ban LINQ for performance." Without a benchmark that is superstition, and the hand-written loops are usually worse than the runtime's specialised paths. The senior answer measures first and scopes the rule.

midLocal functions vs lambdas, and Func/Action vs a custom delegate type: how do you choose?

Answer

A local function is a named method nested in another; it can be recursive, generic, an iterator, and - marked static - guaranteed capture-free; when it captures, the compiler uses a struct closure passed by ref (no allocation) unless the function is converted to a delegate. A lambda is an expression producing a delegate (or expression tree) and always allocates when it captures. Choose a local function for helper logic used only inside a method, for recursion, and for iterator splitting; choose a lambda when you need a delegate value to pass around. Func<>/Action<> cover almost every signature and keep APIs interoperable with LINQ; declare a custom delegate when parameter names carry meaning (delegate bool TryParse<T>(string s, out T result)), when you need ref/out/in parameters or Span parameters (variance-free generic delegates cannot take ref structs), or for public events where the type name documents the contract. C# 14 lets simple lambdas carry modifiers ((text, out result) => ...) without spelling the types.

Example

public static int Depth(Node n)
{
    return Walk(n, 0);
    static int Walk(Node n, int d) => n.Children.Count == 0 ? d : n.Children.Max(c => Walk(c, d + 1));
}

public delegate bool SpanPredicate<T>(ReadOnlySpan<T> span);      // Func can't: ref struct parameter
public delegate bool TryParse<T>(string text, out T result);

TryParse<int> p = (text, out result) => int.TryParse(text, out result);   // C# 14 modifiers on simple lambdas

Follow-ups

  • Why does a captured local function not allocate? - The closure is a struct passed by reference; conversion to a delegate forces it onto the heap because a delegate needs an object target.
  • What is the natural type of a lambda (C# 10)? - var f = (int x) => x + 1; infers Func<int,int>; lambdas can also have attributes and explicit return types.
  • Method group vs lambda? - list.Select(Parse) allocates a delegate each call (cached since C# 11 when static and non-generic-dependent); readability usually wins.

Wrong answer

"Local functions are just lambdas with a name." The allocation behaviour, recursion, iterators and static enforcement are the differences the question is testing.

screenerWhat do nullable reference types actually guarantee, and what do they not?

Answer

NRT (C# 8, on by default in new project templates since .NET 6) is a compile-time flow analysis: with <Nullable>enable</Nullable>, string means "not null" and string? means "may be null", and the compiler warns when you dereference a maybe-null value or assign null to a non-nullable target. It guarantees nothing at runtime: there is no check, the IL is identical apart from attributes, and null still arrives from reflection, deserialisers, un-annotated libraries, default(T), arrays (new string[3] is three nulls), EF materialisation and the ! operator. The value is that the annotations become part of the API contract and the warnings catch most bugs before runtime. Public entry points still validate with ArgumentNullException.ThrowIfNull(x) (.NET 6); trust the annotations inside your own code. Turn warnings into errors on new code (<WarningsAsErrors>nullable</WarningsAsErrors>) or the annotations rot.

Example

#nullable enable
string Greet(string name) => $"hi {name.ToUpper()}";     // contract: not null
string? maybe = Find(id);
Greet(maybe);                       // CS8604 warning: possible null
if (maybe is not null) Greet(maybe); // flow analysis: fine
Greet(maybe!);                      // '!' silences the compiler; null still explodes at runtime

public void Save(Order order)
{
    ArgumentNullException.ThrowIfNull(order);           // runtime guard at the public boundary
}

Follow-ups

  • How do you express "returns non-null when true"? - [NotNullWhen(true)] out T? value; also [MaybeNullWhen(false)], [NotNull], [MemberNotNull(nameof(_field))] for init helpers, [DoesNotReturn] for throw helpers.
  • What is the difference between T? for a struct and for a class in generics? - For an unconstrained T, T? means "maybe default" (no Nullable<T> wrapping); with where T : struct it becomes Nullable<T>.
  • Why is the ! operator a review flag? - Each one is an unproven assertion; grep for !. and !; during review and demand a comment or a real check.

Wrong answer

"With nullable enabled, a string parameter can't be null so you can drop null checks." Internally yes; at public boundaries no. Candidates who removed ThrowIfNull from library APIs shipped NREs deep inside their code instead of a clear ArgumentNullException at the call site.

screenerWalk through the pattern-matching forms and explain how switch-expression exhaustiveness works.

Answer

Patterns test a value's shape and optionally bind variables: type patterns (is Circle c), constant and null patterns, property patterns ({ Radius: > 0 }), positional patterns via Deconstruct ((0, var y)), relational (>= 18) and combinator patterns (and, or, not, C# 9), var and discard patterns, list patterns with slices ([first, .., last], C# 11), and extended property patterns ({ Address.City: "Oslo" }, C# 10). A switch expression (C# 8) must produce a value for every input; the compiler warns (CS8509) when it can prove some inputs are unhandled and throws SwitchExpressionException at runtime for them. Exhaustiveness is proven for bools, enums with all values listed (not for undefined enum values, which is why a discard arm is still needed), nullable cases, relational ranges that cover the domain, and - new in C# 15 preview - closed hierarchies and union types, where the compiler knows the full set of cases and no discard arm is required.

Example

static decimal Shipping(Order o) => o switch
{
    { Total: >= 100 }                         => 0m,
    { Destination.Country: "NO" } and { Weight: < 2 } => 49m,
    { Lines: [] }                             => throw new InvalidOperationException("empty"),
    { Lines: [{ Sku.IsBulky: true }, ..] }    => 199m,
    null                                      => throw new ArgumentNullException(nameof(o)),
    _                                         => 99m
};

// C# 15 preview: no discard arm needed, the compiler knows every case
public closed record class Shape;
public sealed record Circle(double R) : Shape;
public sealed record Square(double S) : Shape;
static double Area(Shape s) => s switch { Circle c => Math.PI * c.R * c.R, Square q => q.S * q.S };

Follow-ups

  • Why is an enum switch never exhaustive without _? - Any int casts to the enum; the compiler cannot rule out (Color)42.
  • What does is not null buy over != null? - It ignores user-defined == overloads (which may themselves mishandle null) and reads as a pattern; it is the idiom for null checks since C# 9.
  • Are patterns compiled efficiently? - Yes: the compiler builds a decision DAG, so a switch with many type patterns is a sequence of type checks with shared prefixes, not repeated casts.

Wrong answer

"A switch expression is just shorter syntax for a switch statement." The value-producing, exhaustiveness-checked semantics are the point; someone who does not know about SwitchExpressionException has not seen one in production logs yet.

midCollection expressions (C# 12) and params collections (C# 13): what do they compile to, and when do they beat the old syntax?

Answer

A collection expression [a, b, ..rest] is target-typed: the compiler picks the most efficient construction for the target type - a literal array, a Span<T> over stack or a cached array for ReadOnlySpan<T> of constants, a List<T> with capacity, an ImmutableArray<T> via its builder, or any type annotated with [CollectionBuilder]. Spreads (..) copy elements, using known counts to pre-size. It replaces new List<T> { ... }, new[] { ... }, Array.Empty<T>() ([]) and awkward ImmutableArray.Create calls, and it is the idiomatic default now. params collections (C# 13) let params apply to ReadOnlySpan<T>, IEnumerable<T>, List<T> and any collection-expression-compatible type; the BCL now has params ReadOnlySpan<T> overloads on string.Join, string.Concat, Path.Combine and more, so variadic calls no longer allocate an array. C# 15 previews collection expression arguments ([with(capacity: 100), ..items]) to pass constructor arguments such as capacity or a comparer.

Example

int[] a = [1, 2, 3];
List<int> l = [..a, 4];                       // pre-sized List, then Add
ReadOnlySpan<byte> magic = [0x89, 0x50];      // no allocation: static data
ImmutableArray<string> names = ["a", "b"];    // builder path, no intermediate array
IReadOnlyList<int> empty = [];                // Array.Empty<int>()

static string JoinAll(params ReadOnlySpan<string> parts) => string.Join(",", parts);  // C# 13, no array
JoinAll("x", "y");                            // stack-allocated span

// C# 15 preview
HashSet<string> set = [with(StringComparer.OrdinalIgnoreCase), "Hello", "hello"];   // 1 element

Follow-ups

  • Can you use a collection expression where the target type is var? - No natural type yet; the target must be known (a parameter, field, or explicit type).
  • How do you make your own type accept them? - [CollectionBuilder(typeof(MyType), nameof(Create))] with a static MyType Create(ReadOnlySpan<T>).
  • Does [] for an IEnumerable<T> allocate? - No; it returns the cached empty array.

Wrong answer

"They always create an array first and then convert." The whole design is that they do not; a candidate who avoids them "for performance" has it backwards.

midWhat did C# 14 add and how should each feature be used - or not?

Answer

C# 14 shipped with .NET 10 on 2025-11-11 and is the version any current interview expects you to know. The headline is extension members (extension properties, static extension members and operators; see unit 03). The field keyword gives semi-auto properties a backing field without declaring one - use it for validation and lazy init, beware existing members named field. Null-conditional assignment (customer?.Order = value, also compound +=) evaluates the right side only when the receiver is not null - readable for optional-target updates, but do not hide a null that should be an error. nameof(List<>) now works on unbound generics. First-class span conversions make arrays flow into ReadOnlySpan<T> parameters and extension receivers implicitly, which may change overload resolution in existing code (a potential breaking change to check on upgrade). Simple lambda parameters may carry ref/out/in/scoped without types. Partial constructors and partial events join partial properties (C# 13) for source generators. User-defined compound assignment operators (operator +=) let big-struct math mutate in place instead of allocating a new value. Preprocessor directives for file-based apps (#:package, #:sdk, #:property) support dotnet run app.cs.

// nameof on an unbound generic

// user-defined compound assignment: mutate in place, no temp

    public void operator +=(in Matrix4 other) { /* add into this */ }
}

  • How do you adopt a new LangVersion in a multi-targeting library? - LangVersion follows the SDK, not the TFM; you can use C# 14 syntax targeting net8.0 as long as no BCL support is needed (e.g. field is fine, span conversions are fine, params ReadOnlySpan needs the attribute polyfill).
  • What is the very latest change you can cite? - .NET 11 RC1 with go-live support shipped the week of 2026-09-08 alongside the 10.0.12 servicing release; C# 15 preview features (unions, closed, extension indexers, labeled break/continue, collection expression arguments, the new memory-safety model) are in it, GA in November 2026.

Wrong answer

"C# 14 added primary constructors and collection expressions." Those are C# 12 (2023). Misdating features two versions back is a common tell that the candidate learned the language from an old course, and interviewers do check.

midStrings in modern C#: interpolation handlers, raw string literals, UTF-8 literals and what each costs.

Answer

Since C# 10 an interpolated string is compiled against DefaultInterpolatedStringHandler: the compiler emits AppendLiteral/AppendFormatted<T> calls into a pooled buffer, formatting value types via ISpanFormattable without boxing and producing one final string - so $"..." is now the fastest general way to build a string, faster than string.Format and comparable to StringBuilder for a few pieces. Custom handlers ([InterpolatedStringHandler]) let APIs skip formatting entirely when disabled, which is how ILogger-style and Debug.Assert overloads avoid cost. Constant interpolated strings (C# 10) fold at compile time. Raw string literals (C# 11, """...""") remove escaping for JSON, SQL and regexes and can be interpolated with $$"""{{x}}""". UTF-8 literals ("GET"u8, C# 11) are ReadOnlySpan<byte> over static data - zero allocation, ideal for protocol parsing. Still true: strings are immutable and interned only for literals; concatenation in a loop is O(n²); use StringBuilder or string.Create for large output; and compare with StringComparison.Ordinal unless you mean culture.

Example

var msg = $"order {id} total {total:C} at {when:O}";     // handler: no boxing, one allocation

var sql = """
    SELECT id, total
    FROM   orders
    WHERE  customer_id = @id
    """;                                                  // indentation of the closing quotes is stripped

var json = $$"""{ "id": {{id}}, "tags": ["a"] }""";       // interpolated raw: braces doubled
ReadOnlySpan<byte> method = "GET "u8;                     // static UTF-8 bytes

_log.LogInformation("order {Id} total {Total}", id, total);   // structured logging: NOT interpolation

Follow-ups

  • Why not interpolate into a logger call? - It formats eagerly even when the level is disabled and destroys structured properties; CA2254 flags it. The [LoggerMessage] source generator is the zero-cost form.
  • What is string.Create for? - Writing directly into the final string's buffer via a SpanAction: one allocation, no intermediate StringBuilder.
  • Are strings UTF-16 or UTF-8 in .NET? - UTF-16 in memory; u8 literals and Encoding.UTF8 are for the wire. .NET 10 adds more span-based normalisation APIs to avoid intermediate strings.

Wrong answer

"Interpolation is slow because it calls string.Format; use StringBuilder." True before 2021, false since C# 10 / .NET 6. Repeating it signals the candidate has not looked at what the compiler emits in years.

seniorModelling closed sets: abstract records + sealed subtypes today, closed and union in C# 15 - what changes for exhaustiveness and API design?

Answer

Today the idiom for "one of a fixed set of shapes" is an abstract record with sealed nested records and a switch expression; the compiler cannot know the set is closed, so every switch needs a _ => throw arm, and adding a case is a silent runtime break in every consumer. C# 15 (preview in .NET 11, GA November 2026) adds two tools. The closed modifier on a class fixes its direct descendants to the declaring assembly; the compiler then treats a switch over the direct descendants as exhaustive without a default arm, and adding a descendant becomes a compile error in every incomplete switch - the behaviour you want for domain results and state machines. union types (public union Pet(Cat, Dog, Bird);) go further: a value that is exactly one of the listed case types, with implicit conversions from each case, exhaustive switches, and runtime support through IUnion/UnionAttribute (in .NET 11 from Preview 5); some parts of the proposal (nested unions, some pattern forms) are still landing. API-design consequence: a closed hierarchy is a versioning promise - adding a case is a source-breaking change for consumers, which is exactly the trade-off you must state; keep public unions small and stable, and use them for results and events, not for extensible plugin models.

Example

// C# 15 preview (.NET 11 RC1)
public union PaymentOutcome(Approved, Declined, Pending);
public sealed record Approved(string Auth);
public sealed record Declined(string Reason);
public sealed record Pending(TimeSpan RetryAfter);

static string Describe(PaymentOutcome o) => o switch
{
    Approved a => $"ok {a.Auth}",
    Declined d => $"no: {d.Reason}",
    Pending p  => $"retry in {p.RetryAfter}",
    // no '_' arm: exhaustive; adding a case breaks this switch at compile time
};

PaymentOutcome result = new Approved("A1");   // implicit conversion from a case type

Follow-ups

  • Why is closed not transitive? - A non-closed descendant of a closed class can still be derived elsewhere; to extend exhaustiveness down the tree mark intermediates closed too.
  • How does this interact with sealed? - A closed class is implicitly abstract and cannot be sealed; leaves are typically sealed.
  • What would you do in a library that must still compile on C# 14? - Keep the abstract-record idiom with a [Obsolete]-guarded default arm, and plan the closed migration with the TFM bump; do not multi-target syntax.

Wrong answer

"C# already has discriminated unions via OneOf/records." Records give the shape but not exhaustiveness; libraries give exhaustiveness via delegates with no compiler support. Knowing the gap - and that C# 15 closes it - is what the senior version of the question tests.

midTop-level statements, global usings, file-scoped namespaces, file-based apps: what do they change about project structure?

"Top-level statements are for demos; real projects need a Program class." The ASP.NET Core templates have used them since .NET 6; insisting on a class-based Main reads as unfamiliarity with current templates.

seniorWhat is the practical difference between dynamic, object and generics for late-bound scenarios, and where is dynamic still legitimate?

Answer

object is static typing with the widest type: the compiler only lets you call object's members until you cast. Generics give static typing per instantiation with no runtime cost. dynamic (C# 4) defers binding to runtime via the DLR: each operation becomes a call site with a polymorphic inline cache, so the first call per site pays reflection-like cost (tens of µs) and later calls a few ns; errors surface as RuntimeBinderException, overload resolution happens at runtime with the runtime types, and refactoring tools cannot see through it. It also does not work with NativeAOT trimming warnings and is unsupported with Span. Legitimate uses: COM/Office interop, interacting with dynamic languages, and the "double dispatch by runtime type" trick where the alternative is a visitor - and even there pattern matching is now the better answer. In code review, dynamic in new code needs a justification comment; JSON should be JsonNode/JsonElement or typed models, not dynamic.

Example

dynamic d = JsonSerializer.Deserialize<ExpandoObject>(json)!;   // smells; typos compile
Console.WriteLine(d.totl);                                       // RuntimeBinderException at runtime

var node = JsonNode.Parse(json)!;                                // typed navigation instead
decimal total = node["total"]!.GetValue<decimal>();

// runtime-type dispatch: pattern matching beats dynamic
static string Render(Shape s) => s switch { Circle c => ..., Square q => ..., _ => ... };

Follow-ups

  • Is dynamic the same as var? - No: var is compile-time inference of a static type; dynamic is a real type meaning "bind at runtime".
  • Does dynamic box? - It is object under the hood, so yes for value types on every call site.
  • Why does dynamic break with NativeAOT? - The DLR generates code at runtime via expression trees; AOT has no JIT, so the binder falls back to an interpreter or fails.

Wrong answer

"dynamic is how you handle JSON with unknown schema." JsonNode/JsonElement exist for that and are typed, fast and AOT-safe. Interviewers hear dynamic and JSON together and mark down.

screenerWhat does lock do, what should you lock on, and what is System.Threading.Lock (.NET 9)?

Answer

lock (x) { ... } compiles to Monitor.Enter(x, ref taken) / try ... finally { if (taken) Monitor.Exit(x); }: mutual exclusion plus a full memory barrier on entry and exit, re-entrant on the same thread. Lock on a private, readonly, dedicated object - never on this, a string, a Type, or anything another component could also lock, because that invites deadlocks you cannot see. .NET 9 added System.Threading.Lock, a dedicated class: lock (myLock) on it compiles (C# 13) to EnterScope() with a ref struct scope, which is faster than Monitor (no object-header thin-lock/sync-block dance), cannot be accidentally used with Monitor.Pulse, and the compiler warns if you box it to object and lose the fast path. New code should use Lock; the semantics (exclusive, re-entrant, not async-aware) are unchanged. You cannot await inside a lock - the compiler refuses - because the continuation may run on a different thread.

Example

public sealed class Counter
{
    private readonly Lock _gate = new();          // .NET 9
    private int _n;
    public void Increment() { lock (_gate) { _n++; } }      // EnterScope() + Dispose()
    public int Read() { lock (_gate) return _n; }
}

// legacy still everywhere
private readonly object _sync = new();
lock (_sync) { ... }                                        // Monitor.Enter/Exit

// what lock does NOT do:
lock (_gate) { await SomethingAsync(); }   // CS1996: cannot await in the body of a lock statement

Follow-ups

  • Is Read() above necessary if _n is an int? - The read is atomic, but without the lock (or Volatile.Read) you have no visibility guarantee: the JIT may hoist it out of a loop.
  • What about lock on a struct? - The compiler rejects value types in a lock statement (CS0185); if you box one to object yourself you lock a fresh box each time, i.e. nothing.
  • Why not [MethodImpl(MethodImplOptions.Synchronized)]? - It locks on this (or the Type for statics): exactly the public-lock problem.

Wrong answer

"lock(this) is fine because the object is private to the class." The reference is not private: any holder of the object can lock it, and a deadlock across two classes locking each other's this is a real incident pattern.

midInterlocked, volatile and Volatile.Read/Write: what does each guarantee, and when is a lock unnecessary?

Answer

Interlocked provides atomic read-modify-write operations (Increment, Add, Exchange, CompareExchange, and since .NET 9 on smaller types too) implemented as single CPU instructions with full fences; a counter, a flag, or a lock-free "set once" needs nothing more. volatile on a field makes every read an acquire and every write a release: it prevents the JIT from caching the value in a register or reordering accesses past it, but it does not make compound operations atomic - volatile int x; x++; is still a race. Volatile.Read/Volatile.Write are the explicit, per-access form and the modern preference over the keyword. A lock is unnecessary when the state is a single word updated with Interlocked or a publish-once reference read with acquire semantics; it is necessary as soon as two pieces of state must change together, or when an invariant spans a check and an act. Plain reads/writes of 64-bit values are not atomic on 32-bit processes; on x64 aligned 8-byte accesses are.

Example

private int _requests;
public void Hit() => Interlocked.Increment(ref _requests);         // atomic
public int Snapshot() => Volatile.Read(ref _requests);            // fresh read

private Config? _config;
public Config Get() => Volatile.Read(ref _config) ?? Load();
private Config Load()
{
    var c = ReadFromDisk();
    return Interlocked.CompareExchange(ref _config, c, null) ?? c;  // first writer wins
}

// NOT atomic even if volatile:
if (_map.Count < Max) _map.Add(k, v);                             // check-then-act race: lock it

Follow-ups

  • What does the .NET memory model guarantee for ordinary writes? - Since .NET 5 the documented model: writes are release, reads are acquire only when marked volatile; the JIT may reorder plain accesses. Do not rely on x86 strong ordering - ARM64 servers are common now.
  • When would you use SpinLock or SpinWait? - Extremely short critical sections with no blocking, measured; almost never in application code.
  • Is a bool flag for cancellation safe without volatile? - No: a loop reading a plain field may never see the update after JIT hoisting. Use CancellationToken or Volatile.Read.

Wrong answer

"Mark the field volatile and ++ is thread-safe." It is the single most common concurrency misconception in C#; the counter loses increments under load and the candidate never sees it in unit tests.

midConcurrentDictionary: what is thread-safe about it, why can GetOrAdd run your factory twice, and how do you fix it?

Answer

ConcurrentDictionary<K,V> makes each individual operation atomic and lock-free for reads, with striped locks for writes; enumeration is a snapshot-ish, non-blocking, possibly inconsistent view. GetOrAdd(key, factory) guarantees that exactly one value is stored per key, but not that the factory runs once: two threads can both miss, both run the factory, and one result is discarded - so a factory that opens a connection, starts a task or has side effects misbehaves. The fix is to store a Lazy<V> (or a Task<V> for async work): the dictionary races on cheap Lazy objects and only the winner's .Value executes the expensive work. Other traps: Count and IsEmpty take all locks (avoid in hot paths), AddOrUpdate's update delegate may also run multiple times, and the type does not give you atomic multi-key operations - for those use a lock or an immutable snapshot swap.

Example

private readonly ConcurrentDictionary<string, Lazy<Task<Client>>> _clients = new();

public Task<Client> GetClientAsync(string region)
    => _clients.GetOrAdd(region, r => new Lazy<Task<Client>>(() => ConnectAsync(r))).Value;
// loser's Lazy is dropped unstarted; ConnectAsync runs once per region

// eviction on failure so a faulted Task does not get cached forever
try { return await task; }
catch { _clients.TryRemove(region, out _); throw; }

Follow-ups

  • What LazyThreadSafetyMode do you want? - ExecutionAndPublication (the default): one execution, others block; PublicationOnly allows multiple executions with one winner - the same problem again.
  • When is a plain Dictionary plus lock better? - Write-heavy workloads with multi-key invariants, or when you need consistent enumeration; ConcurrentDictionary shines for read-mostly caches.
  • What about FrozenDictionary? - .NET 8, immutable after creation, optimised for lookups; the right type for a read-only map built at startup.

Wrong answer

"GetOrAdd with a factory is atomic, so the factory runs once." It is the documented behaviour that it may not, and the bug appears as duplicate connections or double-billed side effects on the first traffic spike.

seniorDesign a bounded producer/consumer with Channel<T>: backpressure, multiple consumers, graceful shutdown and error handling.

Answer

System.Threading.Channels is the modern in-process queue: Channel.CreateBounded<T>(capacity) gives backpressure because WriteAsync awaits when full (or you choose BoundedChannelFullMode.DropOldest/DropWrite for telemetry-style data), and ReadAllAsync() feeds await foreach in one or many consumers. Configure SingleReader/SingleWriter when true for faster internals. Shutdown: the producer calls writer.Complete() (or TryComplete(exception) to propagate a failure), consumers drain until ReadAllAsync ends, and the host awaits the consumer tasks with a bounded timeout from IHostApplicationLifetime.ApplicationStopping. Errors inside a consumer must be caught per item (log, dead-letter, continue) so one poison message does not kill the loop; a genuinely fatal error should complete the channel with the exception so producers stop. Sizing: capacity is your latency budget - in-flight items times per-item time - and metrics on queue depth tell you when consumers are the bottleneck. Prefer this to BlockingCollection (blocks threads) and to hand-rolled Queue+lock+SemaphoreSlim.

Example

var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(1_000)
{ SingleWriter = false, SingleReader = false, FullMode = BoundedChannelFullMode.Wait });

// producer (e.g. an API endpoint): awaits when 1,000 jobs are queued -> backpressure
await channel.Writer.WriteAsync(job, ct);

// N consumers
var consumers = Enumerable.Range(0, Environment.ProcessorCount).Select(_ => Task.Run(async () =>
{
    await foreach (var j in channel.Reader.ReadAllAsync(stopping))
    {
        try { await HandleAsync(j, stopping); }
        catch (Exception ex) when (ex is not OperationCanceledException) { await DeadLetterAsync(j, ex); }
    }
})).ToArray();

// shutdown
channel.Writer.Complete();
await Task.WhenAll(consumers).WaitAsync(TimeSpan.FromSeconds(20), CancellationToken.None);

Follow-ups

  • How do you preserve ordering per key with multiple consumers? - Partition: one channel (or one consumer) per hash of the key, like Kafka partitions.
  • What happens to items still in the channel at shutdown with a hard deadline? - They are lost; if that is unacceptable the queue must be durable (a database table, a broker), not in-process.
  • Why Task.Run for consumers here? - The loops are long-lived; starting them from a hosted service's ExecuteAsync is fine too, but do not run them inline in StartAsync, which blocks host startup.

Wrong answer

"Use an unbounded channel so producers never block." Then memory is the bound, and the process falls over at the first consumer slowdown. Backpressure is the feature, not a bug.

midSemaphoreSlim vs Mutex vs ReaderWriterLockSlim vs Monitor.Wait/Pulse: which primitive for which problem?

Answer

SemaphoreSlim is the async-compatible gate: WaitAsync(ct) limits concurrency to N without blocking threads, so it is the tool for "at most 10 concurrent calls to that API" and for an async mutex (N = 1); always release in finally. Mutex is a kernel object, slow, but works across processes (single-instance apps, cross-process file coordination) and is abandonable. ReaderWriterLockSlim allows many readers or one writer; worth it only when reads vastly outnumber writes and hold the lock for a while - otherwise a plain lock is faster, and an immutable-snapshot-swap (readers read a reference, writers build a new collection and Interlocked.Exchange it) is faster still and lock-free for readers. Monitor.Wait/Pulse are condition variables for hand-built queues; today you use Channel<T> instead. Barrier, CountdownEvent and ManualResetEventSlim exist for phased work; TaskCompletionSource covers most async signalling needs.

Example

private readonly SemaphoreSlim _gate = new(10, 10);   // at most 10 concurrent downstream calls

public async Task<Quote> GetQuoteAsync(string sym, CancellationToken ct)
{
    await _gate.WaitAsync(ct);
    try { return await _api.QuoteAsync(sym, ct); }
    finally { _gate.Release(); }
}

// snapshot swap: lock-free readers
private ImmutableDictionary<string, Rate> _rates = ImmutableDictionary<string, Rate>.Empty;
public Rate? Get(string ccy) => Volatile.Read(ref _rates).GetValueOrDefault(ccy);
public void Reload(IEnumerable<Rate> rs) => Interlocked.Exchange(ref _rates, rs.ToImmutableDictionary(r => r.Ccy));

Follow-ups

  • Why not lock around an await? - Not allowed; and even a manual Monitor.Enter would be released on a different thread. SemaphoreSlim(1,1) is the async mutex.
  • Is SemaphoreSlim re-entrant? - No; recursive acquisition deadlocks. Design so the same logical flow never acquires twice.
  • How do you bound concurrency of a batch of async work in one line? - Parallel.ForEachAsync(items, new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct }, async (x, t) => ...) (.NET 6).

Wrong answer

"Use ReaderWriterLockSlim for any read-heavy cache." Its overhead exceeds a plain lock for short critical sections, and it has recursion-policy traps; the immutable snapshot is the senior answer.

seniorParallel loops, PLINQ and the thread pool: how do you parallelise CPU work correctly, and what are the classic mistakes?

Answer

Parallel.For/ForEach partition an in-memory range across pool threads, with MaxDegreeOfParallelism to cap it, a localInit/localFinally overload for per-thread accumulators, and ParallelLoopState for early Break/Stop; PLINQ (AsParallel()) does the same for query shapes and needs AsOrdered() if order matters. Both are for CPU-bound, side-effect-free work over enough items to amortise partitioning (thousands, not tens); for async I/O use Parallel.ForEachAsync (.NET 6) which awaits rather than blocks. Classic mistakes: sharing a List<T> or a non-thread-safe accumulator across iterations (use thread-local + merge, or ConcurrentBag/Interlocked), doing I/O inside Parallel.ForEach (blocks pool threads, starves the app), using it inside an ASP.NET Core request without a cap (one request eats every core), and ignoring that exceptions arrive as an AggregateException after all iterations finish. Measure: parallel code that allocates heavily often loses to a vectorised sequential loop because the GC becomes the bottleneck.

Example

// per-thread partial sums, merged once: no contention, no shared accumulator
long total = 0;
Parallel.ForEach(Partitioner.Create(0, data.Length), new ParallelOptions { MaxDegreeOfParallelism = 8 },
    () => 0L,
    (range, _, local) => { for (int i = range.Item1; i < range.Item2; i++) local += Score(data[i]); return local; },
    local => Interlocked.Add(ref total, local));

// async I/O fan-out with a cap
await Parallel.ForEachAsync(urls, new ParallelOptions { MaxDegreeOfParallelism = 16, CancellationToken = ct },
    async (url, t) => results[url] = await http.GetStringAsync(url, t));

Follow-ups

  • Why Partitioner.Create(0, n) rather than Parallel.For(0, n)? - Range partitioning gives each thread a chunk, avoiding per-iteration delegate overhead and false sharing on adjacent elements.
  • What is false sharing? - Two threads writing different variables on the same 64-byte cache line ping-pong the line between cores; pad or use thread-local accumulators.
  • Should a web service use Parallel.ForEach at all? - Rarely, and always capped; the pool is shared with request processing. Offload heavy CPU batches to a worker service.

Wrong answer

"Parallel.ForEach over the list of URLs to download them faster." It blocks a pool thread per download; the async version exists precisely for this and is the answer interviewers expect since .NET 6.

seniorA production service is hung: no requests complete, CPU is idle. How do you find whether it is a deadlock, and what typically causes one in modern C#?

Answer

Capture state before restarting: dotnet-dump collect (or createdump from the container) and dotnet-stack report for a quick look. In the dump, clrstack -all shows what every thread is doing; a deadlock is a cycle where threads wait on locks held by each other (syncblk lists Monitor owners; dumpasync lists async state machines and what they await, which is essential because async deadlocks have no thread holding anything). Modern causes: a SemaphoreSlim(1,1) acquired twice in the same logical flow (re-entrancy through a callback or event); sync-over-async under a UI/legacy context; two locks taken in opposite orders by two code paths; a Lazy<T> or static constructor whose initialiser waits on something that needs the initialiser to finish (type-initialiser deadlocks); a TaskCompletionSource never completed because an error path skipped it; and awaiting a task that is itself waiting on the caller (e.g. host StartAsync awaiting something that needs the host started). If it is starvation rather than deadlock, the pool queue is huge and threads are in Wait on tasks (see unit 01). Fix the root, then add a watchdog (health check that times out) so the orchestrator restarts a hung pod.

Example

dotnet-stack report -p 4242 | head -100        # quick: what are threads doing?
dotnet-dump collect -p 4242 -o hang.dmp
dotnet-dump analyze hang.dmp
> clrstack -all                                # every managed stack
> syncblk                                      # Monitor owners and waiters
> dumpasync --stats                            # pending async methods (what is everyone awaiting?)
> threadpool                                   # queue length, worker count

Follow-ups

  • How does a lock-ordering deadlock get prevented structurally? - One documented order (e.g. always account before ledger), or a single coarse lock, or lock-free snapshots; and never call out to unknown code (events, callbacks) while holding a lock.
  • What is a type-initialiser deadlock? - Thread A runs static constructor of X which touches Y; thread B runs Y's which touches X; the runtime blocks each waiting for the other's initialiser. Keep static constructors trivial.
  • Can await deadlock in ASP.NET Core? - Not via context capture; but via SemaphoreSlim re-entrancy or a TCS never completed, yes - those look like hangs with no thread involved, hence dumpasync.

Wrong answer

"Restart the pod and add a retry." It clears the symptom, and without a dump you will be back next week. The senior answer captures state first and can name dumpasync.

principalDefine the concurrency guidelines you would put in a team's engineering handbook for a .NET service, and how you would enforce them.

Answer

Keep it to a page with reasons: (1) shared mutable state is the exception - prefer immutable snapshots, message passing (Channel<T>) and per-request objects; (2) when you must share, one clearly named Lock per invariant, never this/types/strings, no callbacks while holding it, and document the lock order if there is more than one; (3) Interlocked/Volatile only for single-word state, with a comment on why a lock is not needed; (4) async all the way: no .Result/.Wait(), SemaphoreSlim for async gating, cancellation tokens on every async signature; (5) concurrency limits are explicit and configurable for every outbound dependency and every parallel loop; (6) every background loop is a hosted service with structured shutdown and per-item error handling; (7) time comes from TimeProvider and randomness from injected sources so concurrency tests are deterministic. Enforce with analyzers as errors (VSTHRD*, CA2002 lock on weak identity, CA1849, CA2016 forward the token), a required review checklist item for any PR touching lock/Interlocked/Parallel, load tests in CI with a slow-dependency chaos step, and dump-collection automation on health-check timeouts so incidents produce evidence. Teach it once with two real incidents from the codebase; rules without the stories do not stick.

Example

// deterministic time makes concurrency tests repeatable (TimeProvider, .NET 8)
public sealed class TokenBucket(TimeProvider clock, int capacity, TimeSpan refill)
{
    private readonly Lock _gate = new();
    private long _lastRefillTicks = clock.GetTimestamp();
    private int _tokens = capacity;

    public bool TryTake()
    {
        lock (_gate)
        {
            var now = clock.GetTimestamp();
            var elapsed = clock.GetElapsedTime(_lastRefillTicks, now);
            if (elapsed >= refill) { _tokens = capacity; _lastRefillTicks = now; }
            if (_tokens == 0) return false;
            _tokens--; return true;
        }
    }
}
// test: var clock = new FakeTimeProvider(); clock.Advance(refill); Assert.True(bucket.TryTake());

Follow-ups

  • How do you test for races at all? - Stress tests with many tasks and invariants asserted after; property-based tests over interleavings for pure logic; and ThreadSanitizer-style tools are weak in .NET, so design for simplicity.
  • What do you do with a library that is not thread-safe (e.g. an old SDK client)? - Wrap it in a single-consumer channel or an object pool; document the constraint on the DI registration.
  • Where do static mutable fields fit? - Nowhere, unless immutable after startup; they are the most common source of "works on one pod, breaks on two" bugs when combined with a cache.

Wrong answer

"Make everything thread-safe by adding locks." Locks everywhere give you deadlocks and contention instead of races; the principal answer reduces shared mutable state first and then chooses the primitive per invariant.

screenerthrow; vs throw ex; vs ExceptionDispatchInfo: what is the difference and why does it matter?

Answer

throw; rethrows the current exception preserving its original stack trace (the point where it was thrown), so logs show the real origin. throw ex; throws the same object again but resets the trace to the current line, destroying the origin - the classic diagnosis-killer, flagged by CA2200. ExceptionDispatchInfo.Capture(ex).Throw() rethrows an exception captured elsewhere (another thread, a stored task fault) with its original trace appended; it is what await uses internally, and .NET 5 added ExceptionDispatchInfo.SetCurrentStackTrace/SetRemoteStackTrace for framework-style helpers. Wrapping in a new exception should pass the original as innerException, which keeps both traces. Also know: the CLR unwinds twice (first pass finds a handler, second runs finallys), exception filters run during the first pass, and .NET 9 replaced the native unwinder with a managed implementation, making throw/catch two to four times faster.

Example

try { Parse(input); }
catch (FormatException ex)
{
    _log.LogWarning(ex, "bad input {Input}", input);
    throw;                                    // original trace intact
    // throw ex;                              // CA2200: trace now starts here
    // throw new InputException("bad", ex);   // wraps, keeps origin as InnerException
}

// rethrow later, elsewhere
var edi = ExceptionDispatchInfo.Capture(ex);
// ... on another thread or after cleanup
edi.Throw();

Follow-ups

  • Why does the stack trace sometimes look wrong in async code? - Each await resumes in MoveNext; the runtime stitches traces across awaits (since .NET Core 2.1 "async stack traces"), but with runtime-async in .NET 11 the frames are real.
  • What does Exception.Data give you? - A dictionary for context that the catcher can log; better than string-concatenating into the message.
  • Are there exceptions you cannot catch? - StackOverflowException kills the process; AccessViolationException is not catchable by default on Core; OutOfMemoryException is catchable but you rarely can do anything.

Wrong answer

"throw ex; and throw; are the same, one is just explicit." The lost stack trace is the first thing a senior reviewer looks for; it is also on every static-analysis ruleset.

midException filters (when): what do they do differently from a catch-and-rethrow, and what are the idioms?

Answer

A filter runs during the first pass of unwinding, before any finally blocks and before the stack is unwound; if it returns false the handler is skipped as if it did not exist. Consequences: the original stack is intact for the debugger and for dumps (the process state is still at the throw point when a non-matching filter runs), no catch/rethrow cost, and you can express conditions on the exception's data, the token, or the retry count. Idioms: catch (HttpRequestException e) when (e.StatusCode == HttpStatusCode.TooManyRequests); catch (OperationCanceledException) when (ct.IsCancellationRequested) to separate user cancellation from timeouts; and the logging filter catch (Exception e) when (Log(e)) where Log returns false - observe every exception passing through without handling it. Filters must not throw (a throwing filter is treated as false) and must be fast and side-effect-light because they may run for exceptions you never catch.

Example

try { await CallAsync(ct); }
catch (HttpRequestException e) when (e.StatusCode is HttpStatusCode.ServiceUnavailable or HttpStatusCode.TooManyRequests)
{ await BackoffAsync(); }
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{ /* caller cancelled: exit quietly */ throw; }
catch (Exception e) when (LogAndFalse(e))
{ throw new UnreachableException(); }          // never entered: the filter observes only

static bool LogAndFalse(Exception e) { Log.Error(e, "unhandled"); return false; }

Follow-ups

  • Why is the observing filter better than catch-log-rethrow? - It leaves the trace and the first-chance state intact and costs nothing when nothing throws; catch-rethrow unwinds and re-throws.
  • Order of filters vs finally? - Filters run before inner finally blocks execute (first pass); this can surprise people who mutate state in finally and read it in a filter.
  • Can a filter see a cancellation token from the outer scope? - Yes, it is just an expression in scope; the cancellation-vs-timeout idiom depends on it.

Wrong answer

"A filter is syntactic sugar for catch { if (!cond) throw; }." The rethrow version unwinds and loses first-chance state; filters are semantically different, which is the whole point of the question.

midHow expensive is throwing an exception in .NET 10, and where is exception-based control flow actually a performance bug?

Answer

A throw/catch costs on the order of a few microseconds on .NET 9/10 (roughly 2-4× faster than .NET 8 after the managed exception-handling rewrite), scaling with stack depth; that is thousands of times more than a branch but irrelevant at tens per second. It becomes a bug when exceptions are on the expected path at high rate: parsing user input with int.Parse in a loop instead of TryParse, using First() where FirstOrDefault() was meant, a validation layer that throws per field, a cache that throws on miss, or Dictionary indexer misses. Then you see high CPU with "% Exceptions Thrown/sec" in the thousands in dotnet-counters, and the first-chance exception rate lights up in dotnet-trace. The rule: exceptions for exceptional conditions - contract violations, infrastructure failures, things the immediate caller cannot handle - and Try*/results for expected outcomes. The static helpers (ArgumentNullException.ThrowIfNull, ThrowIfNegative, ObjectDisposedException.ThrowIf) keep the throw out of the hot method so it stays inlinable.

Example

// expected outcome: no exception
if (!int.TryParse(field, out var qty)) return Result.Invalid("qty");
if (!_cache.TryGetValue(key, out var v)) v = await LoadAsync(key, ct);

// exceptional: contract violation, throw helper keeps the method small
public void Reserve(int qty)
{
    ArgumentOutOfRangeException.ThrowIfNegativeOrZero(qty);      // .NET 8
    ObjectDisposedException.ThrowIf(_disposed, this);            // .NET 7
    ...
}
// watch: dotnet-counters monitor System.Runtime[exception-count]

Follow-ups

  • Why does a throw inside a method prevent inlining? - Methods containing throw are larger and marked cold; pulling the throw into a helper lets the JIT inline the fast path.
  • What did .NET 9 change under the hood? - The unwinder was ported from C++ to managed code (based on NativeAOT's), removing the two-pass native/managed transitions.
  • Is catch (Exception) at the top of a request pipeline a performance problem? - No; catching once per failed request is fine. The problem is throwing per item on success paths.

Wrong answer

"Exceptions are so expensive you should never throw in a library; return error codes." That is the C answer; in .NET, contract violations must throw so bugs are loud. The nuance is expected vs exceptional, not "never".

midThe using forms, IAsyncDisposable, and ownership: who disposes what, and what goes wrong?

Answer

using (var x = ...) { } and the using var x = ...; declaration (C# 8, disposed at end of the enclosing scope, in reverse order) compile to try/finally { x?.Dispose(); }. await using calls DisposeAsync() for IAsyncDisposable types whose disposal does I/O (database connections, streams with buffered writes, ServiceProvider scopes); if a type implements both, prefer the async form in async code. Ownership rule: whoever creates a disposable disposes it, unless the API documents a transfer (e.g. StreamReader owns its stream unless leaveOpen: true); DI containers dispose what they create at scope end, so never dispose an injected dependency, and never register a disposable as a captured instance you also dispose elsewhere. Failure modes: disposing an HttpClient per request (socket exhaustion - use IHttpClientFactory), forgetting to dispose CancellationTokenRegistration/timers (leaks), calling Dispose twice on a non-idempotent type (must be idempotent per the guideline), and using an object after disposal (throw ObjectDisposedException via ThrowIf).

Example

public async Task ExportAsync(Stream destination, CancellationToken ct)
{
    await using var conn = new SqlConnection(_cs);            // async disposal (closes connection)
    await conn.OpenAsync(ct);
    using var cmd = conn.CreateCommand();                     // sync: nothing to flush
    await using var writer = new StreamWriter(destination, leaveOpen: true);   // we do not own 'destination'
    await using var reader = await cmd.ExecuteReaderAsync(ct);
    while (await reader.ReadAsync(ct)) await writer.WriteLineAsync(reader.GetString(0).AsMemory(), ct);
}   // disposal order: reader, writer (flushes), cmd, conn

Follow-ups

  • What if Dispose throws inside a finally during another exception? - The new exception replaces the original; Dispose should not throw. Log and swallow inside it.
  • How do you dispose in a constructor that fails halfway? - Wrap construction in try/catch, dispose what you created, rethrow; or use a static factory that composes already-safe parts.
  • Does IDisposable on a class mean it must be disposed? - Convention says yes; CA2000/CA1001 assume so. If disposal is optional (e.g. Task), document it.

Wrong answer

"Wrap HttpClient in using because it is IDisposable." The textbook socket-exhaustion bug: sockets sit in TIME_WAIT for minutes and the service runs out under load. Interviewers ask it because they have seen the outage.

seniorExceptions vs Result<T> types: how do you decide, and what does each cost in a real codebase?

Answer

Exceptions carry rich context, propagate automatically through every layer including await, and are the only sensible channel for bugs and infrastructure failures; their cost is that expected outcomes (validation failures, not-found, conflicts) become invisible in signatures and expensive at scale. Result types make expected outcomes explicit in the signature and force callers to handle them, at the price of manual propagation, wrapper allocations, a library choice (or your own type), awkward composition with LINQ/async, and the temptation to wrap everything, including bugs, which then get logged and ignored. The workable policy: Result/discriminated outcomes at domain boundaries for outcomes the caller must branch on (validation, business rules), exceptions for contract violations and I/O failures, one translation layer at the edge (ASP.NET Core IExceptionHandler plus ProblemDetails) so neither leaks as a 500 with a stack trace. Do not build a monadic error-handling framework in C#; the language does not have the syntax to make it pleasant, though C# 15 unions will make the "one of these outcomes" shape a first-class type.

Example

public abstract record TransferResult

midHow does the JIT compile code today: tiered compilation, OSR, Dynamic PGO - and what does that mean for benchmarks and startup?

Answer

Methods start at Tier 0 (fast, unoptimised, instrumented) and, after 30 calls plus a backoff timer, get recompiled at Tier 1 with full optimisation on a background thread; hot loops in a method that is still at Tier 0 are handled by On-Stack Replacement (OSR, .NET 7), so long-running loops also get optimised code. Dynamic PGO (default since .NET 8) uses the Tier 0 instrumentation - which classes hit each virtual/interface call, which branches are taken, how hot each block is - to make Tier 1 devirtualise with guards, inline more aggressively, and lay out hot paths; this is why the same code is often 10-20% faster on .NET 8+ without recompiling. ReadyToRun (crossgen) precompiles to skip Tier 0 for startup, and the runtime still re-JITs hot R2R code at Tier 1. Consequences: a micro-benchmark must warm up (BenchmarkDotNet does this), a profile taken in the first seconds shows Tier 0 code, and code that is only executed a few times never reaches Tier 1 - startup-heavy apps benefit from R2R or NativeAOT, not from JIT tweaks. .NET 10 extended the JIT with AVX-512/AVX10 and ARM SVE support, stack allocation of non-escaping objects, and better loop inversion and de-abstraction of generic/interface calls.

Example

//   else return shape.Area();   // slow path

Follow-ups

  • Why can a benchmark of a generic method give different results for int and string? - Value-type instantiations are specialised, reference-type ones share code and pay dictionary lookups; PGO helps the shared case.
  • What is "Tier 1 instrumented"? - For R2R code, which skipped Tier 0, the runtime inserts an instrumented tier before final Tier 1 so PGO still gets data.
  • How do you see what the JIT did? - DOTNET_JitDisasm="Method*" (works on Release runtimes since .NET 7), or the Disassembly Diagnoser in BenchmarkDotNet.

Wrong answer

"The JIT compiles each method once when it is first called." That was true in 2016; today the story is tiering plus PGO, and it explains warm-up curves, benchmark rules and why sealed classes and small interfaces still matter less than they did.

midShow how you would rewrite a string-parsing hot path with Span<T>, stackalloc and SearchValues, and what the allocation profile becomes.

Answer

The old shape (Split, Substring, Trim, ToLower) allocates a string per piece; the span shape slices the original memory with zero allocations and parses numbers directly from the slice with int.TryParse(ReadOnlySpan<char>) or Utf8Parser for bytes. Use IndexOf/Split over spans (MemoryExtensions.Split with a ref struct enumerator, .NET 8), SearchValues<T> (.NET 8) for "any of these characters" searches - it precomputes a vectorised strategy once and is dramatically faster than IndexOfAny with an array - and stackalloc (under ~1 KB, via Span<T>, never raw pointers) for small scratch buffers. For byte input, "key="u8 literals give allocation-free comparisons. Outputs go into a caller-provided Span<char> via TryFormat or into a string.Create callback. The result is a parser whose steady-state allocation is zero, verified with [MemoryDiagnoser], and whose throughput is bound by memory bandwidth, not the GC.

Example

private static readonly SearchValues<char> Separators = SearchValues.Create(",;|");

// "id=42;qty=7" -> (42, 7), zero allocations
public static bool TryParse(ReadOnlySpan<char> line, out int id, out int qty)
{
    id = qty = 0;
    foreach (var range in line.Split(';'))                // .NET 8 span Split: ref struct enumerator
    {
        var kv = line[range];
        int eq = kv.IndexOf('=');
        if (eq < 0) return false;
        var key = kv[..eq]; var val = kv[(eq + 1)..].Trim();
        if (key.SequenceEqual("id"))  { if (!int.TryParse(val, out id))  return false; }
        else if (key.SequenceEqual("qty")) { if (!int.TryParse(val, out qty)) return false; }
    }
    return true;
}

  • What if the input arrives as byte[] chunks? - System.IO.Pipelines + SequenceReader<byte> handle partial frames across buffers; Utf8Parser/Utf8JsonReader parse without decoding to UTF-16.
  • Why not stackalloc a 64 KB buffer? - Default stack is 1 MB per thread and stackalloc is not freed until method exit; use ArrayPool<T>.Shared.Rent above ~1 KB, and a hybrid (stackalloc when small, pool otherwise) in libraries.
  • How much faster is SearchValues? - Several times over IndexOfAny(char[]) for sets larger than 2-5 characters, because the strategy is chosen once (bitmap, vectorised probabilistic map, etc.).

"Use Span everywhere in the domain model." Spans cannot be stored, captured or awaited; they are for the parsing/formatting layer. A candidate who wants Span fields in DTOs has not hit the compiler errors yet.

seniorHow do you benchmark and profile .NET code correctly, and what are the classic ways people fool themselves?

seniorNativeAOT vs ReadyToRun vs plain JIT: what do you gain, what do you lose, and how do you make a codebase AOT-compatible?

Answer

Plain JIT: best steady-state performance (PGO, tiering), slowest startup (~100-300 ms for a web app), largest memory and needs the runtime. ReadyToRun: precompiled IL+native in the assembly, startup cut roughly in half, still re-JITs hot code, still needs the runtime, bigger files; the safe default for services that scale out often. NativeAOT (.NET 7 console, .NET 8 ASP.NET Core minimal APIs/gRPC, broader every release): a single native executable with a trimmed runtime, ~10-30 ms startup, small footprint (tens of MB), no JIT at all - which means no runtime code generation (Reflection.Emit, Expression.Compile falls back to an interpreter, dynamic largely unusable), no Assembly.LoadFrom, and reflection only over what the trimmer kept, plus no Dynamic PGO, so peak throughput is usually a bit lower. Making a codebase AOT-compatible: enable <IsAotCompatible>true</IsAotCompatible> in libraries so the analyzers (IL2xxx/IL3xxx) run; replace reflection-based serialisation with source generators (System.Text.Json context, [LoggerMessage], [GeneratedRegex], [LibraryImport], configuration binding generator); avoid MakeGenericType with value types at runtime; annotate remaining reflection with [DynamicallyAccessedMembers]; and audit dependencies - most ORMs and DI-heavy frameworks need their AOT modes (EF Core compiled models, ASP.NET Core's request-delegate generator). Choose AOT for CLI tools, serverless/functions, sidecars and edge deployments; keep JIT for large monoliths with heavy reflection.

midPooling: ArrayPool<T>, MemoryPool<T>, ObjectPool<T>, StringBuilder caching - when does pooling help and when does it hurt?

Answer

Pooling avoids allocation for objects that are expensive to create or large enough to land on the LOH: byte/char buffers above a few KB, StringBuilders in serialisers, and connection-like objects. ArrayPool<T>.Shared hands out arrays of at least the requested size (check .Length, slice to what you asked for), is thread-safe, and tolerates leaks (unreturned arrays are just garbage); MemoryPool<T> wraps it in IMemoryOwner<T> so ownership is a disposable; ObjectPool<T> (Microsoft.Extensions.ObjectPool) with a policy resets state on return. Pooling hurts when the object is small (gen0 allocation is a pointer bump; pooling adds synchronisation and cache misses), when returned objects are used after return (the worst class of bug - data corruption across requests), when you keep references to pooled memory beyond the operation, and when the pool grows unbounded under bursty load and becomes the leak. Rules: pool only after a profile shows the allocation matters; clear sensitive data on return (clearArray: true); never expose a pooled buffer past the method that rented it; and prefer Span/stackalloc for small scratch space.

Example

public static async Task CopyAsync(Stream src, Stream dst, CancellationToken ct)
{
    byte[] buffer = ArrayPool<byte>.Shared.Rent(81920);      // may be larger than 81920
    try
    {
        int n;
        while ((n = await src.ReadAsync(buffer.AsMemory(0, 81920), ct)) > 0)
            await dst.WriteAsync(buffer.AsMemory(0, n), ct);
    }
    finally { ArrayPool<byte>.Shared.Return(buffer, clearArray: false); }
}

// small scratch: no pool needed
Span<byte> header = stackalloc byte[16];

Follow-ups

  • Why does Rent(100) give you 128? - Buckets are powers of two; the pool keeps a few arrays per bucket per thread, then a shared stack.
  • How do you detect use-after-return in tests? - A test pool that fills returned arrays with a sentinel pattern and asserts on reads; catches most bugs cheaply.
  • Is HttpClient pooling the same idea? - No: IHttpClientFactory pools handlers (connections, DNS refresh); the client object is cheap.

Wrong answer

"Pool everything to reduce GC." Pooling small objects is slower than allocating them, and every pool is a potential use-after-return bug. Measure, then pool the few things that matter.

seniorWhere do hidden allocations come from in ordinary C#, and how do you find and remove them?

seniorSIMD in C#: Vector<T>, Vector128/256/512, TensorPrimitives - when do you write it yourself and when does the BCL already do it?

The BCL is already vectorised for the common cases: Span.IndexOf/SequenceEqual/Contains, SearchValues, string comparison and case conversion, Enumerable.Sum/Min/Max over arrays of primitives (.NET 8), UTF-8 transcoding, Base64, hashing, and System.Numerics.Tensors.TensorPrimitives for numeric kernels (dot product, cosine similarity, softmax - the embedding-math workhorse for AI features). Example

using System.Numerics.Tensors;

static float SumSquares(ReadOnlySpan<float> xs)
{
    var acc = Vector<float>.Zero; int i = 0;
    for (; i <= xs.Length - Vector<float>.Count; i += Vector<float>.Count)
    { var v = new Vector<float>(xs.Slice(i)); acc += v * v; }
    float s = Vector.Sum(acc);
    for (; i < xs.Length; i++) s += xs[i] * xs[i];          // scalar tail
    return s;
}

"Write Vector256 intrinsics for the parsing loop." The BCL search primitives already do it and handle the tails and ISA fallbacks; hand-rolled SIMD is a maintenance burden you take on only when a profile proves the BCL path is the bottleneck.

midStruct layout, [StructLayout], [InlineArray] and cache behaviour: what should a C# engineer know about data layout?

Answer

The runtime lays out class and struct fields with automatic reordering (LayoutKind.Auto for classes, Sequential for structs by default) and pads to natural alignment, so field order affects size: a struct of bool, long, bool is 24 bytes sequential and 16 auto. Use [StructLayout(LayoutKind.Sequential, Pack = 1)] or Explicit with [FieldOffset] only for interop or wire formats. [InlineArray(N)] (C# 12 / .NET 8) turns a struct with one field into a fixed-size inline buffer that you index as a Span<T> - the safe replacement for fixed buffers, used by the BCL for small stack collections. Cache behaviour is what makes layout matter: sequential scans over contiguous arrays of small structs (struct-of-arrays for numeric work) are memory-bandwidth-bound and prefetch-friendly, while linked lists and arrays of references chase pointers and miss cache; a List<Point> of 16-byte structs is one block, a List<PointClass> is a block of pointers to scattered 32-byte objects. Object headers cost 16 bytes on x64 (8 header + 8 method table); arrays add a length. Unsafe.SizeOf<T>() and Marshal.SizeOf differ (managed vs marshalled layout).

public struct Good { public long B; public bool A; public bool C; }   // 16 bytes

[InlineArray(8)]

  • What is false sharing and how do you avoid it in .NET? - Threads writing adjacent fields in one cache line; pad hot per-thread counters (e.g. 128-byte spacing) or use thread-local + merge.

  • Where does Unsafe.As/MemoryMarshal.Cast fit? - Reinterpreting spans of blittable structs as bytes for I/O without copying; only with sequential layout you control.

"Field order doesn't matter in C#, the runtime optimises it." For structs it does not reorder by default; the 24-vs-16 example is the interview classic, and in interop it matters absolutely.

principalA service's p99 latency doubled after upgrading from .NET 8 to .NET 10 while p50 improved. How do you investigate and what are the likely causes?

Answer

Treat it as a regression investigation with a hypothesis list ordered by likelihood and cost to check. First, reproduce in staging with production traffic shape and compare the runtime counters side by side: if gen0/gen1 counts rose sharply, DATAS (default for server GC since .NET 9) is adapting heap count and gen0 budget - the usual cause of "p50 better, tail worse"; test with GarbageCollectionAdaptationMode=0 or a fixed GCgen0size. Second, tiered compilation and PGO: the new JIT's more aggressive devirtualisation can regress a polymorphic hot path (a guarded devirt guard that mispredicts); compare with DOTNET_TieredPGO=0 and look at the tail during the first minutes vs steady state. Third, library behaviour changes: HTTP/3 or HTTP/2 defaults, SocketsHttpHandler connection pooling changes, Kestrel's new defaults, System.Text.Json changes, EF Core query translation changes causing different plans - diff the dependency versions, not just the runtime. Fourth, thread pool: .NET 10's pool tuning and any SetMinThreads hacks that were compensating for something now behave differently. Bisect by running the .NET 10 runtime with .NET 8-era settings (GC knobs, PGO off) to isolate runtime vs library. 09Strings, collections and hashing

Small unit, high hit rate: string comparison and culture, immutability and interning, which collection for which access pattern, and the hashing contract that makes dictionaries work. These are often asked as warm-ups and as "gotcha" follow-ups; the senior versions ask about FrozenDictionary, alternate lookups and comparer choice, and the principal version is a data-structure decision under memory and latency constraints.

screenerWhich string comparison should you use, and what goes wrong with the default?

Answer

== and string.Equals(a, b) are ordinal (byte-wise on UTF-16 code units): fast, culture-independent, correct for identifiers, keys, paths and protocol tokens. string.Compare, StartsWith(string), IndexOf(string), ToUpper()/ToLower() without a StringComparison default to the current culture, which is slower and can change results by machine: the Turkish "I" problem ("file".ToUpper() is "FİLE" in tr-TR), ignorable characters ("\0", soft hyphens) compared equal, and .NET 5+'s switch from NLS to ICU on Windows changed some orderings, which broke code relying on Framework-era culture behaviour. Rules: StringComparison.Ordinal / OrdinalIgnoreCase for anything machine-facing, StringComparer.OrdinalIgnoreCase for dictionaries, ToUpperInvariant for normalisation, and a culture comparison (CurrentCulture) only for sorting text shown to a user. CA1307/CA1309/CA1310 enforce it; <InvariantGlobalization> removes ICU entirely for services that never show localised text.

Example

if (header.StartsWith("Bearer ", StringComparison.Ordinal)) ...
var byName = new Dictionary<string, User>(StringComparer.OrdinalIgnoreCase);
bool same = string.Equals(a, b, StringComparison.OrdinalIgnoreCase);

// culture trap
CultureInfo.CurrentCulture = new CultureInfo("tr-TR");
"file".ToUpper() == "FILE";          // false (dotless I)
"file".ToUpperInvariant() == "FILE"; // true

Follow-ups

  • Why is OrdinalIgnoreCase not the same as comparing ToLower() results? - It uses invariant simple case mapping without allocating; ToLower allocates and uses the current culture.
  • What about string.GetHashCode() across processes? - Randomised per process; use XxHash64/SHA256 for stable hashes.
  • How do you sort user-visible names correctly? - StringComparer.Create(culture, ignoreCase) or CompareInfo, and be explicit about which culture in the requirements.

Wrong answer

"Use InvariantCulture for everything to be safe." Invariant is still a linguistic comparison (ignorable characters, expensive); for keys and protocols the answer is Ordinal.

midPick the collection: List, Dictionary, HashSet, SortedDictionary vs SortedList, LinkedList, PriorityQueue, ImmutableArray, FrozenDictionary, OrderedDictionary.

Answer

List<T>: contiguous, O(1) index and append, O(n) insert/remove in the middle - the default. Dictionary<K,V>/HashSet<T>: O(1) average lookup, unordered (enumeration order is insertion order until removals, but not guaranteed). SortedDictionary: red-black tree, O(log n) everything, good for frequent inserts; SortedList: sorted arrays, O(n) insert but less memory and O(1) indexed access, good for mostly-read data. LinkedList<T>: O(1) insert given a node but pointer-chasing and 48 bytes per node - almost never the right choice; a List with removals or a Queue usually wins. Queue/Stack: ring buffer / array. PriorityQueue<TElement,TPriority> (.NET 6): binary heap, O(log n) enqueue/dequeue, for schedulers and Dijkstra. ImmutableArray<T>: a struct wrapping an array, free to read, rebuild to change - for snapshots. FrozenDictionary/FrozenSet (.NET 8): built once, optimised for reads (specialised strategies for string keys) - for lookup tables built at startup. OrderedDictionary<K,V> (.NET 9): insertion-ordered with index access, for "dictionary that must round-trip in order". Concurrent variants only when actually shared.

Example

// startup-built lookup, read millions of times: FrozenDictionary
private static readonly FrozenDictionary<string, int> Codes =
    new Dictionary<string, int> { ["EUR"] = 978, ["USD"] = 840 }.ToFrozenDictionary(StringComparer.OrdinalIgnoreCase);

// scheduler: next job by due time
var due = new PriorityQueue<Job, DateTimeOffset>();
due.Enqueue(job, job.RunAt);
while (due.TryPeek(out var next, out var at) && at <= clock.GetUtcNow()) Run(due.Dequeue());

// sliding window of last N: Queue, not LinkedList
var window = new Queue<double>(capacity: 100);

Follow-ups

  • Why pre-size a List or Dictionary? - Growth doubles and copies; for known sizes new List<T>(n) avoids log n reallocations, and Dictionary.EnsureCapacity avoids rehashing.
  • Is Dictionary enumeration order guaranteed? - No; it happens to be insertion order without removals. Use OrderedDictionary if you depend on it.
  • What does CollectionsMarshal give you? - AsSpan(list), GetValueRefOrAddDefault(dict, key, out exists) for single-lookup upserts, SetCount; for hot paths only.

Wrong answer

"LinkedList for frequent inserts and removes." The interview classic: in practice the cache misses and per-node allocation make it slower than List for nearly every real size; the strong answer explains why.

midWhy are strings immutable, what is interning, and when should you use StringBuilder, string.Create or spans instead of concatenation?

Answer

Immutability makes strings safe to share across threads, usable as dictionary keys with a cached hash, and lets the runtime intern literals (one instance per distinct literal per process, in the intern pool) so ReferenceEquals("a", "a") is true for literals but false for runtime-built strings unless you call string.Intern - which you almost never should (the pool is never collected). Concatenating in a loop is O(n²) copies; StringBuilder amortises it with a chunked buffer, and for a known final size string.Create(length, state, (span, s) => ...) writes directly into the final string once. Single-expression concatenation (a + b + c, interpolation) is already one allocation via string.Concat/the interpolation handler, so StringBuilder there is noise. When you only need to inspect or compare, do not build strings at all: slice with AsSpan(), compare with SequenceEqual/Equals(span, span, comparison). string.Join and string.Concat have params ReadOnlySpan overloads since .NET 9 that avoid the array.

Example

// O(n^2)
string csv = ""; foreach (var x in xs) csv += x + ",";

// amortised
var sb = new StringBuilder(xs.Count * 8);
foreach (var x in xs) sb.Append(x).Append(',');

// exact single allocation
string hex = string.Create(bytes.Length * 2, bytes, static (span, b) =>
{
    for (int i = 0; i < b.Length; i++) b[i].TryFormat(span.Slice(i * 2, 2), out _, "x2");
});

// no string at all
if (path.AsSpan().EndsWith(".json", StringComparison.OrdinalIgnoreCase)) ...

Follow-ups

  • Is StringBuilder thread-safe? - No. Pool them per thread or per operation; ASP.NET Core provides ObjectPool<StringBuilder> via StringBuilderPooledObjectPolicy.
  • Why is string.IsNullOrWhiteSpace preferred over Trim().Length == 0? - No allocation; Trim creates a new string when there is whitespace.
  • How big is a string in memory? - ~20 bytes overhead + 2 bytes per char on x64; a million 10-char strings is ~40 MB before the array of references.

Wrong answer

"Always use StringBuilder when combining strings." For a single expression it is slower and noisier than +/interpolation; the answer is "in loops or when the size is unknown", with string.Create for the hot case.

seniorCustom comparers, HashCode.Combine, and the .NET 9 alternate lookup: how do you make a dictionary keyed by a compound or span-like key efficient?

Answer

A compound key should be a readonly record struct (value equality, IEquatable<T>, hash via HashCode.Combine generated) so lookups do not box and do not allocate; a tuple key works too but names are better and tuples cannot carry a custom comparer. When equality must differ from the key's own (case-insensitive strings, tolerance on doubles, a subset of fields), pass an IEqualityComparer<TKey> to the dictionary; keep Equals and GetHashCode consistent and cheap, and make the comparer a singleton (static readonly) so it is not allocated per dictionary. For string keys looked up by substring, .NET 9's GetAlternateLookup<ReadOnlySpan<char>>() on Dictionary, HashSet, ConcurrentDictionary and the frozen collections lets you probe with a span - no Substring allocation - provided the comparer implements IAlternateEqualityComparer<ReadOnlySpan<char>, string> (the ordinal StringComparers do). For very large read-only maps, FrozenDictionary picks a strategy (length-bucketed, prefix/suffix hashing) that beats a general hash table.

Example

public readonly record struct RouteKey(string Method, string Path);   // Equals/GetHashCode generated

sealed class RouteKeyComparer : IEqualityComparer<RouteKey>
{
    public static readonly RouteKeyComparer Instance = new();
    public bool Equals(RouteKey a, RouteKey b) =>
        string.Equals(a.Method, b.Method, StringComparison.OrdinalIgnoreCase) && string.Equals(a.Path, b.Path, StringComparison.Ordinal);
    public int GetHashCode(RouteKey k) =>
        HashCode.Combine(StringComparer.OrdinalIgnoreCase.GetHashCode(k.Method), StringComparer.Ordinal.GetHashCode(k.Path));
}
var routes = new Dictionary<RouteKey, Endpoint>(RouteKeyComparer.Instance);

// .NET 9: span lookup on string-keyed collections
var headers = new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase);
var alt = headers.GetAlternateLookup<ReadOnlySpan<char>>();
if (alt.TryGetValue(line.AsSpan(0, colon), out var value)) ...

Follow-ups

  • Why is a mutable class as a key dangerous even with a correct comparer? - If the hashed fields change after insertion the entry becomes unreachable; keys must be effectively immutable.
  • Does a record struct with a string field box when hashed? - No; the generated code calls EqualityComparer<string>.Default without boxing the struct itself.
  • HashCode.Combine vs XOR of hashes? - XOR collides symmetric pairs ((a,b) vs (b,a)) and zeros out equal fields; HashCode mixes with a per-process seed.

Wrong answer

"Concatenate the fields into a string and use that as the key." It allocates on every lookup and invites separator collisions ("a|b" + "c" vs "a" + "b|c"); the record struct key is the idiom.

midWhich interface should a method accept or return: IEnumerable, IReadOnlyList, IList, ICollection, List, arrays, Span?

Answer

Accept the least you need: IEnumerable<T> if you iterate once, IReadOnlyCollection<T> if you need a count, IReadOnlyList<T> if you index, ReadOnlySpan<T> for synchronous hot paths that only read (arrays, lists via CollectionsMarshal, stack memory and strings all convert). Return the most useful concrete guarantee that does not over-promise: IReadOnlyList<T> for materialised results (callers get count and index, cannot mutate, and you may return an array or a list), IEnumerable<T> only when laziness is the contract, IAsyncEnumerable<T> for streams, and avoid returning List<T>/arrays from public APIs unless the caller is meant to mutate or you need the performance (internal code is a different story). Never IList<T>/ICollection<T> for read-only data - they promise Add and throw at runtime for arrays. Fields: concrete types privately, read-only interfaces publicly. A method that takes IEnumerable<T> and calls Count() or enumerates twice has the wrong parameter type.

Example

public IReadOnlyList<Order> Pending { get; }                       // read-only view, count + index
public Task<IReadOnlyList<Order>> LoadAsync(CancellationToken ct); // materialised
public IAsyncEnumerable<Order> StreamAsync(CancellationToken ct);  // streaming

static decimal Total(ReadOnlySpan<decimal> amounts) { ... }        // arrays, lists, stackalloc all work
Total(list_of_decimals.ToArray());          // or CollectionsMarshal.AsSpan(list) internally
Total([1m, 2m]);                            // collection expression -> span, no heap

Follow-ups

  • Is IReadOnlyList<T> actually immutable? - No, it is a read-only view; the underlying list may change. For an immutability guarantee return ImmutableArray<T> or a defensive copy.
  • Why not Span<T> in async or public library APIs? - Cannot cross an await; and in public APIs it forces callers to synchronous code. ReadOnlyMemory<T> is the async-safe alternative.
  • Arrays as return type? - Fine internally and for performance-sensitive APIs; in public APIs they are mutable and their length is fixed, which callers misuse.

Wrong answer

"Always IEnumerable<T> for maximum flexibility." Callers then call Count() and ToList() on it, re-enumerating or re-materialising what you already had; IReadOnlyList is the right default for materialised results.

principalDesign an in-memory index for 50 million records with sub-millisecond lookups and a strict memory budget: which structures and why, and how do you keep the GC out of the way?

Answer

Start with the numbers: 50 M entries in a Dictionary<long, Record> with class values is 50 M objects (each ~40+ bytes plus 24 bytes per entry) - over 3 GB and a gen2 the GC must trace on every full collection. Instead store records in struct-of-arrays or in large arrays of blittable structs (one object per column, allocated once, on the LOH, never traced deeply because they contain no references), keep strings in a single UTF-8 byte arena with offset/length pairs, and index with a Dictionary<long, int> from key to row index (or a custom open-addressing hash over the arrays for even less overhead). Ranges and prefix lookups get sorted key arrays with BinarySearch. Result: a handful of large objects the GC touches once, cache-friendly scans, and lookups that are one hash plus one array read. Build immutably (FrozenDictionary for the key index if it is rebuilt wholesale) and publish snapshots with an Interlocked.Exchange so readers are lock-free; updates go through a small write-side structure merged on a schedule. Keep the GC out of the way by making the steady state allocation-free (span-based query API, no LINQ, ArrayPool for result buffers), using server GC with a hard limit, and verifying with dotnet-gcdump that the heap is a few hundred objects. If the budget is tighter still, memory-map the arrays from disk and use MemoryMarshal.Cast over the mapped spans.

Example

public sealed class RecordIndex
{
    private readonly long[] _keys;          // sorted
    private readonly int[] _cityOffset;     // into _arena
    private readonly short[] _cityLength;
    private readonly decimal[] _balance;
    private readonly byte[] _arena;         // UTF-8 strings, one block
    private readonly FrozenDictionary<long, int> _byKey;

    public bool TryGet(long key, out RecordView r)
    {
        if (_byKey.TryGetValue(key, out var i)) { r = new(this, i); return true; }
        r = default; return false;
    }
    public readonly ref struct RecordView   // no allocation per lookup
    {
        private readonly RecordIndex _ix; private readonly int _i;
        public RecordView(RecordIndex ix, int i) { _ix = ix; _i = i; }
        public ReadOnlySpan<byte> CityUtf8 => _ix._arena.AsSpan(_ix._cityOffset[_i], _ix._cityLength[_i]);
        public decimal Balance => _ix._balance[_i];
    }
}

Follow-ups

  • Why not Dictionary<long, Record> with a struct Record? - Better than classes, but the entries array is still one huge object with structs copied on read, and any string field makes it reference-containing again.
  • How do you handle updates without stopping reads? - Snapshot swap for bulk rebuilds; for point updates, a small overlay dictionary consulted first, merged periodically.
  • Where does .NET 10 help? - Faster FrozenDictionary and span APIs, AVX-512 search; the design is the same, the constants get better.
  • When do you give up and use an external store? - When the data must survive restarts quickly or be shared across nodes; then Redis/RocksDB with the same struct-of-arrays discipline on the client side.

Wrong answer

"A ConcurrentDictionary of record classes, and give the pod more memory." Fifty million objects make every gen2 a multi-second pause and the memory budget is blown three times over; the principal answer changes the data layout, not the pod size.

10Runtime internals, reflection and generators

How C# becomes running code: IL, assemblies and load contexts, reflection and its cost, source generators and analyzers as the modern replacement for runtime metaprogramming, and how DI containers and serialisers actually construct things. Rarely a whole interview, but one or two questions show whether you understand the platform beneath the language. Senior candidates are expected to have written or debugged a source generator by now.

midFrom source to execution: what does the compiler emit, what does the runtime do at load, and what is an assembly really?

Answer

Roslyn compiles C# to IL (a stack-based bytecode) plus metadata (types, members, attributes, references) into a PE file - the assembly - with an identity of name, version, culture and public key; a .deps.json and runtimeconfig.json tell the host which runtime and dependencies to use. At startup the host (dotnet or the apphost) loads CoreCLR, which loads assemblies lazily into an AssemblyLoadContext when a type is first needed, builds method tables from metadata, and JIT-compiles methods on first call (or maps ReadyToRun code). Type loading is where static constructors, beforefieldinit semantics and generic instantiation happen; the runtime verifies nothing by default (no IL verification on Core), which is why unsafe and Unsafe.As can corrupt memory. Multiple versions of an assembly cannot coexist in one load context; version conflicts are resolved at build time by NuGet (highest wins, binding redirects are gone since .NET Core) and at runtime by the default context's probing. Trimming (PublishTrimmed) removes unreferenced IL; NativeAOT compiles it all ahead of time and drops the JIT.

Example

dotnet build -c Release
ls bin/Release/net10.0/       # App.dll (IL + metadata), App.deps.json, App.runtimeconfig.json, App (apphost)
ilspycmd App.dll -t App.Program   # decompile: see the async state machines, closures, records' generated members
# environment probes:
DOTNET_ReadyToRun=0 DOTNET_TieredCompilation=0 dotnet App.dll   # pure JIT, full opts, to compare behaviour

Follow-ups

  • What is beforefieldinit? - A type with no explicit static constructor may have its statics initialised any time before first field access, letting the JIT hoist checks; an explicit static ctor forces precise timing and adds a check per access on some paths.
  • Why are binding redirects gone? - .NET Core resolves the dependency graph at build/publish time into deps.json; there is one version per assembly per context.
  • What is the difference between Assembly.Load, LoadFrom and LoadFile? - Load by identity via the current context; LoadFrom by path into the default context with its probing; LoadFile by exact path with no dependency resolution. Plugins should use a custom AssemblyLoadContext.

Wrong answer

"C# compiles to machine code like C++." It compiles to IL, which is JIT-compiled per method at runtime (or AOT-compiled with NativeAOT); this distinction underlies tiering, PGO, reflection and trimming, so getting it wrong sinks several later questions.

midReflection: what does it cost, how do you make it cheap when you must use it, and what breaks with trimming and AOT?

Answer

GetType().GetProperty(...) walks metadata (cacheable, tens to hundreds of ns), PropertyInfo.GetValue and MethodInfo.Invoke go through a slow dynamic path with argument boxing (.NET 7 rewrote Invoke with emitted IL, making repeated calls several times faster, still far slower than a direct call), and Activator.CreateInstance is acceptable for reference types with a cached factory. To make reflection cheap: do the lookup once and cache MemberInfos in a static; convert to delegates via CreateDelegate or Expression.Lambda(...).Compile() (JIT only); use UnsafeAccessor (.NET 8) to get zero-overhead access to private members without reflection; or, best, move the work to compile time with a source generator. Trimming removes members nothing references statically, so reflection over them fails at runtime; annotate with [DynamicallyAccessedMembers], use [DynamicDependency], or keep the analyzers happy; NativeAOT additionally has no IL emit, so anything that generates code at runtime (Reflection.Emit, expression compilation, older Castle DynamicProxy/AutoMapper versions) does not work. The BCL's own serialisers, logging, regex, configuration binding and P/Invoke all have generator-based modes for this reason.

Example

// .NET 8: direct access to a private field without reflection cost or trimming risk
[UnsafeAccessor(UnsafeAccessorKind.Field, Name = "_items")]
static extern ref T[] Items<T>(List<T> list);

// cached delegate instead of MethodInfo.Invoke
static readonly Func<Order, decimal> GetTotal =
    (Func<Order, decimal>)Delegate.CreateDelegate(typeof(Func<Order, decimal>), typeof(Order).GetProperty("Total")!.GetGetMethod()!);

// trimming annotation: tell the trimmer what you will reflect on
static void Bind([DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicProperties)] Type t, object target) { ... }

Follow-ups

  • Why is typeof(T) cheap but obj.GetType().Name less so? - typeof is a handle load; .Name may allocate the string on first call and goes through metadata.
  • What is RuntimeFeature.IsDynamicCodeSupported for? - Branching at runtime between an emit-based fast path and an interpreter/reflection fallback (AOT), the pattern the BCL uses.
  • How do DI containers construct services fast? - Microsoft.Extensions.DependencyInjection compiles expression trees (or uses IL emit) for resolvers on JIT runtimes and falls back to reflection-based call sites under AOT; registration validation runs at build time.

Wrong answer

"Reflection is fine, we cache the Type." Caching the type is not caching the member lookup or the invocation; the cost is in Invoke/GetValue per call. And it says nothing about trimming, which is where reflection breaks in 2026.

seniorSource generators: how do incremental generators work, what are the rules for a fast one, and where are they the right tool?

Answer

A source generator is a Roslyn component that runs inside the compiler (and the IDE, on every keystroke) and adds generated C# files to the compilation; it cannot modify existing code, only add - which is why partial classes/methods/properties/constructors/events exist. Incremental generators (IIncrementalGenerator, the only kind you should write) build a pipeline of cached steps: a syntax predicate (cheap, runs on every node), a semantic transform (only for matching nodes), and a model that must be equatable so the driver can skip regeneration when nothing changed. Rules: never capture ISymbol or SyntaxNode in the model (they defeat caching and leak the compilation), use ForAttributeWithMetadataName for attribute-driven generators, keep string building in the final step, and test with the Microsoft.CodeAnalysis.Testing harness plus snapshot tests. Right tool for: replacing runtime reflection (JSON, logging [LoggerMessage], [GeneratedRegex], P/Invoke [LibraryImport], options binding, COM), boilerplate from a schema (strongly-typed ids, enums, mappers, minimal-API request delegates), and compile-time validation via diagnostics. Wrong tool for: anything needing runtime data, and for "nice to have" code you could write once by hand. C# 12/13's interceptors (still experimental, [InterceptsLocation]) let generators redirect specific call sites - used by ASP.NET Core and EF Core to make DI and query code AOT-friendly.

Example

[Generator]
public sealed class IdGenerator : IIncrementalGenerator
{
    public void Initialize(IncrementalGeneratorInitializationContext ctx)
    {
        var ids = ctx.SyntaxProvider.ForAttributeWithMetadataName(
            "MyApp.StronglyTypedIdAttribute",
            predicate: static (node, _) => node is RecordDeclarationSyntax,
            transform: static (c, _) => new IdModel(               // equatable record: cacheable
                c.TargetSymbol.ContainingNamespace.ToDisplayString(), c.TargetSymbol.Name));
        ctx.RegisterSourceOutput(ids, static (spc, m) => spc.AddSource($"{m.Name}.g.cs", Emit(m)));
    }
    private readonly record struct IdModel(string Namespace, string Name);
    private static string Emit(IdModel m) => $$"""
        namespace {{m.Namespace}};
        partial record struct {{m.Name}} : System.IParsable<{{m.Name}}> { /* Parse, TryParse, ToString, JsonConverter */ }
        """;
}

Follow-ups

  • Why must the generator target netstandard2.0? - It runs inside the compiler process (Visual Studio is still .NET Framework-hosted in places); the generated code can target anything.
  • How do you debug a slow generator? - dotnet build -bl and the binlog viewer show generator timings; the incremental pipeline's step outputs can be asserted in tests (trackIncrementalGeneratorSteps).
  • Generator vs analyzer vs code fix? - Analyzer reports diagnostics, code fix edits user code in the IDE, generator adds code at build; combine an analyzer with a generator to require the partial keyword and explain why.

Wrong answer

"Use ISourceGenerator and regenerate everything on each build." The old interface re-runs from scratch on every keystroke and makes the IDE crawl; incremental with an equatable model is the only acceptable design since 2022.

seniorHow does System.Text.Json work under the hood, what are its defaults and traps, and when is the source-generated mode mandatory?

Answer

Utf8JsonReader/Utf8JsonWriter are forward-only ref struct tokenisers over UTF-8 bytes - no intermediate strings, no DOM; JsonSerializer sits on top with per-type converters and a metadata cache (JsonTypeInfo) built by reflection on first use or emitted by the source generator (JsonSerializerContext). Traps in .NET 9/10: duplicate property handling (AllowDuplicateProperties, .NET 10 defaults to throwing when disabled), JsonSerializerOptions.Web, and required/init support that respects nullability annotations when RespectNullableAnnotations is on.   • Why is Newtonsoft's TypeNameHandling.All a vulnerability? - The payload names the type to instantiate; gadget types in the BCL lead to remote code execution. STJ never resolves types from the payload.

"We use Newtonsoft because System.Text.Json can't do X." Staying on Newtonsoft is defensible for legacy compatibility, not for missing features.

seniorAssemblyLoadContext: how do you load plugins in isolation, unload them, and what are the failure modes?

Answer

An AssemblyLoadContext (ALC) is a scope for assembly identity: the same assembly name can be loaded into two contexts as two different types, which is how plugins can bring their own versions of dependencies. A plugin host creates new PluginLoadContext(pluginPath, isCollectible: true), resolves dependencies via an AssemblyDependencyResolver over the plugin's .deps.json, and loads the entry assembly; types shared with the host (the plugin interface) must be resolved to the host's context, which the custom Load override does by returning null for those names so probing falls through to the default context. Unloading: Unload() is cooperative - the context is collected only when nothing references any of its types (no live instances, no delegates, no static caches in the host holding plugin objects, no threads running plugin code); verify with a WeakReference to the context and a few GC.Collect() calls. Failure modes: the "same" interface type from two contexts causing InvalidCastException (the plugin compiled against its own copy of the contract), unloads that never complete because a host cache holds a plugin type, native libraries that cannot be unloaded, and JSON/DI caches keyed by Type. In practice, prefer process isolation (a sidecar over gRPC) for untrusted or crash-prone plugins; ALCs are for trusted, versioned, hot-reloadable extensions.

midStatic constructors, Lazy<T>, module initialisers and startup ordering: what runs when, and what are the traps?

Answer

A static constructor runs exactly once per closed type, before the first instance creation or static member access, under a runtime lock; an exception inside it wraps as TypeInitializationException and permanently poisons the type for the process. Without an explicit static constructor (only field initialisers), the type is beforefieldinit and initialisation may happen earlier, at the JIT's convenience, which is faster but means side effects may occur at surprising times. Lazy<T> defers expensive work to first use with a thread-safety mode; LazyInitializer.EnsureInitialized is the allocation-free variant; static readonly fields initialised from a method are the cheapest "init once" when there is no failure mode to retry. Module initialisers ([ModuleInitializer], C# 9) run when the assembly loads - for generators that must register things, not for application logic. Traps: type-initialiser deadlocks when two static constructors touch each other across threads; static constructors doing I/O or DI resolution; a failed static constructor turning into a permanent outage until restart (log inside it and keep it trivial); and static state in libraries used from multiple tenants or test runs (use instance state or AsyncLocal).

Example

{
    // beforefieldinit: initialised lazily at the JIT's convenience, no lock on access after init
    public static readonly FrozenDictionary<string, ICodec> ByName = Build();

    // explicit static ctor: precise timing, but a throw poisons the type forever
    // static Codecs() { ByName = Build(); }
}

{

        new(() => new ExpensiveClient(), LazyThreadSafetyMode.ExecutionAndPublication);
    public static ExpensiveClient Instance => _instance.Value;     // a failure here can be retried: Lazy caches the exception!

  • How do you initialise async state once? - An AsyncLazy (Lazy<Task<T>>) or a hosted service that warms up before the app accepts traffic.
  • Why are generic static fields per instantiation a trap? - Cache<T>.Instance is one per T; a static in a generic type is not shared, which can be a feature (typed caches) or a leak.

Wrong answer

"Put the connection setup in the static constructor so it runs once." It runs once and, if the network is down at that moment, never again until the process restarts. Static constructors must be trivial and infallible.

Where lead and principal interviews spend real time: what makes a public C# API good, what breaks binary versus source compatibility, how to version and deprecate, what you look for when reviewing async, allocation-sensitive or concurrent code, and how you make the rules stick with analyzers rather than nagging. midWhich changes to a public .NET library are binary-breaking, which are source-breaking, and which are safe?

Answer

Binary breaks (compiled callers fail at runtime with MissingMethodException/TypeLoadException): removing or renaming any public member, changing a signature including adding an optional parameter (the default is baked into the caller), changing a return type, changing a field to a property, moving a type to another assembly without a type forward, adding an abstract member to a public class, adding a member to an interface without a default implementation, changing a struct's fields (layout), sealing an unsealed class, and changing a constant's value (also baked into callers). Source breaks (recompile fails or changes meaning): adding an overload that creates ambiguity, adding a member that collides with an extension method callers used, changing parameter names (named arguments), adding a default interface member with the same name as one a class already has, nullability annotation changes when consumers treat warnings as errors. Safe: adding new types, new overloads that do not cause ambiguity, new virtual members on unsealed classes (mostly), new default interface members, widening parameter types via new overloads, and adding optional parameters as a new overload while keeping the old one. Tools: the Microsoft.DotNet.ApiCompat tasks (PackageValidation in the SDK) and the PublicAPI.Shipped.txt/Unshipped.txt analyzer make breaks fail the build.

// safe: keep the old, add the new

"Adding an optional parameter is not a breaking change; existing calls still compile." They compile - and every already-compiled consumer crashes at runtime. This is the single most common library-versioning mistake and interviewers ask it to see if you have shipped a NuGet package.

seniorDesign guidelines for a public async/streaming API surface: Task vs ValueTask, spans, cancellation, overloads, and what you refuse to expose.

Answer

Public async methods return Task/Task<T> by default; ValueTask only where a synchronous completion path is common and measured, and never on interfaces that callers might await twice or fan out; name them *Async, take CancellationToken ct = default as the last parameter, and never offer sync-over-async wrappers - if you must have sync versions, implement them separately. Streaming results are IAsyncEnumerable<T> with [EnumeratorCancellation]; materialised results are IReadOnlyList<T>. Input buffers are ReadOnlySpan<T> for synchronous APIs and ReadOnlyMemory<T> for async ones; provide both when the operation is hot (Write(ReadOnlySpan<byte>) and WriteAsync(ReadOnlyMemory<byte>, CancellationToken)), and Try* variants with caller-provided output spans for allocation-free formatting. Overloads: few, with one full-parameter "canonical" overload the others delegate to; no bool flags (enums), no params object[], no object-typed parameters. Refuse to expose: List<T>/arrays as mutable state, IQueryable, Task-returning properties, dynamic, ref structs across an async boundary, implementation types in signatures (return the interface), and events for things that need back-pressure (use channels or observables). Document thread-safety per type, and mark experimental surface with [Experimental("LIB001")] so callers must opt in.

Example

public interface IBlobStore
{
    ValueTask<bool> ExistsAsync(BlobId id, CancellationToken ct = default);             // hot, often cached: ValueTask
    Task<BlobInfo> PutAsync(BlobId id, ReadOnlyMemory<byte> content, CancellationToken ct = default);
    Task<BlobInfo> PutAsync(BlobId id, Stream content, CancellationToken ct = default);
    IAsyncEnumerable<BlobInfo> ListAsync(string prefix, CancellationToken ct = default);
    Task<IReadOnlyList<BlobInfo>> ListPageAsync(string prefix, int take, CancellationToken ct = default);
}

[Experimental("BLOB001")]                    // callers must suppress to use it: explicit opt-in
public Task<Uri> GetPresignedAsync(BlobId id, TimeSpan ttl, CancellationToken ct = default);

  • Why ct = default on interfaces? - Convenience for callers with no token; the implementation must still forward it. CA2016 flags forgotten forwarding.
  • Should a library call ConfigureAwait(false)? - Yes, everywhere internally (CA2007 as error), because a UI or legacy host may call it.
  • How do you version an interface? - Prefer abstract base classes or default interface members for additive changes; otherwise IBlobStore2 is honest, ugly and safe.

Wrong answer

"Return ValueTask everywhere because it is the modern type." It creates a misuse surface for every consumer; the guideline in the BCL itself is Task by default.

seniorReview this: a PR adds a caching decorator around a repository using a Dictionary, async void refresh and DateTime.Now. What do you write in the review?

Answer

Lead with the defects that will page someone, then design, then style. (1) Correctness under concurrency: a Dictionary shared across requests is a data race that corrupts the table - use ConcurrentDictionary with a Lazy<Task<T>> value or, better, IMemoryCache/HybridCache (.NET 9) which already handles stampedes and eviction. (2) async void refresh: exceptions crash the process, nothing awaits it, tests race - make it a Task tracked by a hosted service or run refresh inline with GetOrCreateAsync. (3) DateTime.Now: local time and untestable - inject TimeProvider and use GetUtcNow(); expiry math on local time breaks at DST. (4) Missing: cancellation token forwarding, a size limit (unbounded cache is a leak), negative caching policy, and metrics (hit ratio). midDeserialisation: why was BinaryFormatter removed, what makes a deserialiser dangerous, and what are the safe defaults?

Answer

BinaryFormatter instantiates whatever types the payload names and runs their deserialisation callbacks, so an attacker who controls the bytes controls which code runs - the BCL contains enough "gadget" types to reach remote code execution. Microsoft obsoleted it in .NET 5, made it throw by default in .NET 7-8, and removed it from the runtime in .NET 9; the compat package exists only for migrating stored data. The same property makes any deserialiser with type-name handling dangerous: Newtonsoft with TypeNameHandling other than None, NetDataContractSerializer, SoapFormatter, ObjectStateFormatter, and XML with XmlResolver enabled (XXE, external entities). Safe defaults: System.Text.Json (never resolves types from the payload; polymorphism only through declared [JsonDerivedType] discriminators; MaxDepth 64), XmlReaderSettings with DtdProcessing.Prohibit, protobuf/MessagePack with fixed schemas, and validation of input sizes before parsing. Treat any "we deserialise object" design as a finding; the security analyzers (CA2300-CA2330, SYSLIB0011) catch the well-known types.

Example

// SYSLIB0011 / removed in .NET 9: throws NotSupportedException at runtime
var obj = new BinaryFormatter().Deserialize(stream);

// Newtonsoft: RCE-enabling setting
var s = new JsonSerializerSettings { TypeNameHandling = TypeNameHandling.All };   // never

// safe polymorphism: the discriminator maps to declared types only
[JsonPolymorphic(TypeDiscriminatorPropertyName = "kind")]
[JsonDerivedType(typeof(EmailNotification), "email")]
[JsonDerivedType(typeof(SmsNotification), "sms")]
public abstract record Notification;

// XML: no DTD, no external entities
var settings = new XmlReaderSettings { DtdProcessing = DtdProcessing.Prohibit, XmlResolver = null };

Follow-ups

  • Is DataContractSerializer safe? - With known types only, yes; NetDataContractSerializer is not, because it embeds type names.
  • What about deserialising into JsonNode/dynamic? - JsonNode is data, not types, so it is safe; the risk is downstream code that acts on it, plus depth/size limits.
  • How do you handle a legacy database full of BinaryFormatter blobs? - Offline one-time migration tool using the compat package on an isolated machine, converting to JSON/protobuf; never at request time.

Wrong answer

"BinaryFormatter is fine for internal data we generate ourselves." The bytes can be swapped by anyone who reaches the storage or the queue; "internal" is the assumption every deserialisation CVE started with.

midInjection in C# code: SQL through interpolation, EF Core's FromSql family, command-line and path traversal - where are the traps?

Answer

String interpolation into a SQL string ($"... WHERE id = {id}") is injection whether via ADO.NET or Dapper; parameters are the fix, and the trap is that EF Core's FromSqlInterpolated/FromSql (EF 7+) accept a FormattableString and turn the holes into parameters, while FromSqlRaw takes a plain string and does not - so assigning the interpolated string to a string variable first silently defeats the protection. Identifiers (table/column names) cannot be parameterised; allow-list them. Process.Start with a shell and concatenated arguments is command injection; pass an argument list (ProcessStartInfo.ArgumentList) and no shell. Path traversal: Path.Combine(root, userInput) returns the user's path if it is rooted, so canonicalise with Path.GetFullPath and check StartsWith(rootWithSeparator, Ordinal). LDAP, XPath, regex (ReDoS: use RegexOptions.NonBacktracking from .NET 7 or a matchTimeout), log injection (structured logging, not interpolation), and HTML (Razor encodes by default; Html.Raw is the trap). The analyzers CA2100 (SQL), CA3xxx (injection review) and the ASP.NET Core template defaults cover most of it if turned on.

// parameterised: FormattableString, the hole becomes @p0
var rows = await db.Users.FromSql($"SELECT * FROM Users WHERE Name = {name}").ToListAsync();
string sql = $"SELECT * FROM Users WHERE Name = {name}";   // now a string: FromSql(sql) would not compile, FromSqlRaw(sql) is injection

// path traversal
var full = Path.GetFullPath(Path.Combine(root, userPath));
if (!full.StartsWith(root + Path.DirectorySeparatorChar, StringComparison.Ordinal)) throw new UnauthorizedAccessException();

// ReDoS-safe
var rx = new Regex(pattern, RegexOptions.NonBacktracking, TimeSpan.FromMilliseconds(100));

"We use EF Core, so SQL injection is impossible." FromSqlRaw and ExecuteSqlRaw with concatenation are injection; the interviewer will ask what the difference between FromSql and FromSqlRaw is.

seniorCryptography in .NET: which APIs for hashing, password storage, symmetric and asymmetric encryption, random numbers, and what changed with post-quantum in .NET 10?

Answer

Use the BCL, never roll your own, and prefer the one-shot static APIs: SHA256.HashData(span) for integrity hashes (not for passwords), Rfc2898DeriveBytes.Pbkdf2 with a high iteration count or Argon2/bcrypt via a vetted package for password storage - and in ASP.NET Core, Identity's PasswordHasher; RandomNumberGenerator.GetBytes/GetInt32/GetHexString for anything security-relevant (Random and Guid.NewGuid are not cryptographic); AesGcm/ChaCha20Poly1305 (authenticated encryption, unique nonce per key) instead of raw Aes-CBC without a MAC; RSA with OAEP/PSS or ECDsa/ECDiffieHellman for asymmetric; CryptographicOperations.FixedTimeEquals for comparing MACs/tokens; the Data Protection API in ASP.NET Core for cookies and tokens with key rotation. .NET 10 shipped post-quantum algorithms - MLKem (key encapsulation), MLDsa and SlhDsa (signatures), with composite ML-DSA support - and .NET 11 RC1 adds experimental caller-driven TLS sessions; the practical guidance is "crypto agility": wrap algorithms behind your own key-management abstraction so you can move to PQC without touching business code. aes.Encrypt(nonce, plaintext, ciphertext, tag, associatedData);

// password hashing
byte[] salt = RandomNumberGenerator.GetBytes(16);

// constant-time compare
if (!CryptographicOperations.FixedTimeEquals(expectedMac, actualMac)) throw new SecurityException();

// .NET 10 post-quantum

  • Why is a nonce reuse with AES-GCM catastrophic? - It leaks the XOR of plaintexts and allows forging tags; use a counter or random 96-bit nonces with key rotation before ~2^32 messages.

"SHA-256 the password with a salt." Fast hashes are brute-forceable at billions per second; password hashing needs a slow, memory-hard KDF. It is the most common crypto answer that fails.

mid[DllImport] vs [LibraryImport]: how does P/Invoke marshalling work, and what makes a call fast and AOT-safe?

Answer

[DllImport] (legacy, still everywhere) makes the runtime generate a marshalling stub at runtime with IL emit: for blittable signatures (primitives, pointers, structs of blittable fields) the stub is trivial and the call is a few ns; for strings, arrays and non-blittable structs it allocates and copies per call and cannot exist under NativeAOT. [LibraryImport] (.NET 7) is a source generator that emits the same marshalling as C# at compile time into a partial method that calls a blittable DllImport underneath - so it is inspectable, debuggable, AOT- and trim-compatible, and lets you customise marshalling with [MarshalUsing] and custom marshallers. Rules for fast and safe calls: keep signatures blittable (pass byte*/ReadOnlySpan<byte> with UTF-8 you encode yourself, int/nint/bool as [MarshalAs(UnmanagedType.I4)] or use byte), return handles as SafeHandle subclasses (refcounted, the marshaller keeps them alive during the call), set SetLastError = true only when you need Marshal.GetLastPInvokeError, avoid SuppressGCTransition unless the call is proven sub-microsecond and never blocks, and resolve libraries with NativeLibrary.SetDllImportResolver for per-platform names. Callback into managed code via [UnmanagedCallersOnly] functions and function pointers rather than delegates, which must be kept alive by you.

Example

internal static partial class Native
{
    [LibraryImport("libsodium", EntryPoint = "crypto_generichash", SetLastError = false)]
    [return: MarshalAs(UnmanagedType.I4)]
    internal static partial int GenericHash(Span<byte> output, nuint outLen, ReadOnlySpan<byte> input, ulong inLen,
                                            ReadOnlySpan<byte> key, nuint keyLen);   // spans pin automatically

    [LibraryImport("mylib", StringMarshalling = StringMarshalling.Utf8)]
    internal static partial SafeMyHandle Open(string path);      // SafeHandle return: ownership + refcount
}

sealed class SafeMyHandle : SafeHandleZeroOrMinusOneIsInvalid
{
    public SafeMyHandle() : base(ownsHandle: true) { }
    protected override bool ReleaseHandle() { Native.Close(handle); return true; }
}

Follow-ups

  • What is blittable? - Same representation in managed and native memory: primitives except bool/char, pointers, and structs of blittable fields with sequential layout; no marshalling needed.
  • Why do delegates passed to native code crash later? - The GC collects the delegate once nothing manages references it; the native side then calls freed memory. Keep a static reference or use [UnmanagedCallersOnly].
  • How do you P/Invoke on Linux and Windows with different library names? - NativeLibrary.SetDllImportResolver or the runtime's probing (libfoo.so/foo.dll variations are tried automatically for a bare name).

Wrong answer

"Pass string and let the marshaller handle it." It works and it costs an allocation and a copy per call, plus it breaks under AOT with the old attribute; the senior answer knows StringMarshalling.Utf8 and when to pre-encode spans.

seniorWhat does unsafe allow today, what are function pointers, and how is C# 15 changing the memory-safety model?

Answer

With <AllowUnsafeBlocks>, an unsafe context permits raw pointers (T*), address-of, pointer arithmetic, fixed to pin managed memory, stackalloc to a pointer, sizeof on non-primitive types, and fixed-size buffers. Function pointers (C# 9, delegate* managed<int, int> / delegate* unmanaged[Cdecl]<...>) are raw calli calls with no delegate allocation - for native callbacks and hot dispatch tables. Most "unsafe" needs are covered without the keyword now: Span<T>, MemoryMarshal, Unsafe.As/Add/AsRef, NativeMemory.Alloc/Free (.NET 6), ref fields, [InlineArray] - these are still memory-unsafe in effect but compile in safe context, which is one reason C# 15 is revisiting the model. The C# 15 preview (in .NET 11 RC1, LangVersion=preview) moves the unsafe requirement from having pointers to accessing memory through them: declaring pointer types, taking addresses, fixed, pointer conversion of stackalloc, and sizeof no longer need an unsafe context; dereference, ->, element access and function-pointer invocation still do; a new unsafe(expr) expression form covers field initialisers and catch filters; unsafe on a member becomes "requires unsafe" so the obligation flows to callers under the updated rules (MemorySafetyRulesAttribute), and a safe modifier marks extern members and explicit-layout fields as audited. It is explicitly multi-release and may change for C# 16 - know it, do not ship on it.

Example

// today (C# 14): function pointer dispatch, no delegate allocation
static unsafe int Apply(delegate*<int, int> f, int x) => f(x);
static int Twice(int x) => x * 2;
unsafe { Console.WriteLine(Apply(&Twice, 21)); }

// native memory without pointers in the API surface
void* p = NativeMemory.Alloc(4096);
Span<byte> s = new(p, 4096);          // safe span over native memory
NativeMemory.Free(p);

// C# 15 preview: declaring and pinning no longer need 'unsafe'; dereferencing still does
int number = 42;
int* pointer = &number;               // allowed in safe context under the new rules
unsafe { Console.WriteLine(*pointer); }

Follow-ups

  • Why is Unsafe.As<T> more dangerous than a cast? - No type check: it reinterprets the reference; wrong use corrupts memory silently. It belongs behind a tested, documented helper.
  • When is fixed vs GCHandle.Alloc(Pinned) vs the POH the right choice? - fixed for the duration of a call; GCHandle for long-lived pins (fragmentation!); GC.AllocateArray<T>(pinned: true) puts it on the Pinned Object Heap for buffers pinned for the process lifetime.
  • Does stackalloc in safe code guard the stack? - The size is not checked against remaining stack; keep it small and constant, or use RuntimeHelpers.TryEnsureSufficientExecutionStack in recursive code.

Wrong answer

"Unsafe code is for performance; we use it in the hot paths." Spans and the Unsafe/MemoryMarshal helpers deliver the performance in safe context; raw pointers in application code are a review finding, and the C# 15 change is about making the remaining risk visible.

midCOM and Windows-specific interop in 2026: ComWrappers, [GeneratedComInterface], CsWin32 and what still requires the old built-in COM support.

principalYour team must integrate a C++ SDK with callbacks and manual memory ownership into a long-running .NET service. How do you structure it so it does not crash the process at 2 a.m.?

Answer

Put the whole native surface in one assembly with a tiny, safe public API, and treat that assembly as the only place unsafe, [LibraryImport] and SafeHandles live. Ownership: every native handle is a SafeHandle subclass with ReleaseHandle calling the SDK's free function - never IntPtrs passed around; buffers the SDK writes into come from NativeMemory or pinned POH arrays with lifetimes tied to the handle. Callbacks: [UnmanagedCallersOnly] static methods with a GCHandle-based context pointer to find the managed object, exceptions caught at the boundary (an exception escaping into native code is undefined behaviour and usually a crash) and translated into an error state the managed side observes; callbacks never block and never call back into the SDK on the same thread unless documented re-entrant. Threading: the SDK's threading model is documented and enforced by a single-consumer channel or a dedicated thread if it is not thread-safe. Isolation decision: if the SDK is known to crash or leak, run it out of process (a sidecar over gRPC/named pipes) so a native fault restarts the sidecar, not the service - the process boundary is the only reliable isolation for native code. Observability: wrap every call with timing and error-code metrics, enable crash dumps (DOTNET_DbgEnableMiniDump) so the 2 a.m. crash leaves a dump with native frames, and run the integration under AddressSanitizer or the SDK's debug build in CI. Governance: the interop assembly has two owners, a review checklist (ownership, threading, exceptions at the boundary, pinning duration), and a soak test that runs for hours looking at native memory via working set minus managed heap.

Example

internal static unsafe partial class Sdk
{
    [LibraryImport("vendor_sdk")] internal static partial SafeSessionHandle session_open(nint userData, delegate* unmanaged[Cdecl]<nint, int, byte*, nuint, void> onEvent);

    [UnmanagedCallersOnly(CallConvs = [typeof(CallConvCdecl)])]
    internal static void OnEvent(nint userData, int kind, byte* data, nuint len)
    {
        try
        {
            var session = (Session)GCHandle.FromIntPtr(userData).Target!;
            session.Enqueue(kind, new ReadOnlySpan<byte>(data, (int)len));   // copy out; native buffer is not ours after return
        }
        catch (Exception ex) { SessionFaults.Record(ex); }                  // never let it escape into native code
    }
}

public sealed class Session : IDisposable
{
    private readonly GCHandle _self;
    private readonly SafeSessionHandle _h;
    private readonly Channel<SdkEvent> _events = Channel.CreateBounded<SdkEvent>(10_000);
    public unsafe Session()
    {
        _self = GCHandle.Alloc(this);
        _h = Sdk.session_open(GCHandle.ToIntPtr(_self), &Sdk.OnEvent);
    }
    public void Dispose() { _h.Dispose(); _self.Free(); }
}

Follow-ups

  • Why copy the callback data out instead of processing inline? - The native buffer is valid only during the callback, and processing inline blocks the SDK's thread; copy into a bounded channel and process on your own terms.
  • How do you detect native memory leaks? - Working set vs managed heap over a soak; the SDK's own stats; on Linux, jemalloc/mimalloc profiling or heaptrack on the sidecar.
  • What if the SDK requires the callback on the calling thread? - Dedicated thread owning the session with a request channel; every call marshalled onto it; no exceptions.

Wrong answer

"Wrap the SDK with DllImports and delegates and call it from the request handlers." Delegates get collected, exceptions cross the boundary, the SDK's threading model is violated by the first concurrent request, and the crash takes the whole service; the principal answer isolates, owns lifetimes explicitly, and leaves evidence.

15Judgment calls

Open-ended questions with no single right answer. The interviewer is grading whether you name the trade-offs unprompted, whether you can state a default and its exceptions, and whether you talk about people and process as fluently as about the compiler. Each block says what a strong answer at the highest level demonstrates.

principalRecords everywhere, or classes with explicit equality? Where do you draw the line in a domain model?

A strong answer demonstrates

A principle before a preference: identity versus value semantics decides, not syntax convenience. Records for value objects, DTOs, messages and immutable snapshots; classes for entities and anything with lifecycle or mutable invariants. Names the specific failure modes unprompted: EF Core change tracking with with, mutable record structs, value equality including collection references, record inheritance and exact-type equality, and hashing of mutable keys. Mentions the upcoming closed/union types as the better tool for closed alternatives and how that changes the record-hierarchy idiom. Then the team angle: a one-line rule in the handbook, an analyzer or a review checklist item, and a 10-line repro of the EF bug to convince rather than decree.

Trade-offs to name

  • Conciseness and correctness of generated equality vs the hidden semantics when identity was meant.
  • Immutability ergonomics (with) vs allocation per change on hot paths.
  • Consistency across a codebase vs letting each bounded context choose.
principalExceptions or result types for a new service platform - and how do you stop the choice from decaying?

A strong answer demonstrates

Refuses the binary: expected outcomes as typed results at domain boundaries, exceptions for contract violations and infrastructure failures, one translation point at the edge (IExceptionHandler/ProblemDetails), one log site per exception. Knows the cost model (microseconds per throw on .NET 9+, so rate matters, not existence) and the cost of results (propagation boilerplate, composition, the temptation to wrap bugs). Names governance: analyzers (CA1031, CA2200), a rule for which exceptions are caught where, and a quarterly look at production's top exceptions as the decay detector. Mentions that C# 15 unions make the result shape first-class and would revisit the design then.

Trade-offs to name

  • Explicit signatures vs ergonomic propagation through async and LINQ.
  • Library choice (OneOf/ErrorOr) vs a small hand-written type: consistency vs dependency.
  • Observability: exceptions come with stack traces for free; results need deliberate logging of failures.
principalNativeAOT for a new microservice fleet: yes, no, or some? How do you decide per service?

A strong answer demonstrates

Decision criteria rather than enthusiasm: cold-start sensitivity (scale-to-zero, functions, CLI), footprint constraints, and dependency compatibility on one side; peak throughput (JIT + Dynamic PGO usually wins), reflection-heavy libraries, plugin loading and dynamic on the other. A staged plan: AOT-compat analyzers everywhere, ReadyToRun + trimming as the fleet default, AOT for the services that benefit, with numbers (startup ms, MB per instance) on a dashboard to justify each step. Knows the source-generator replacements (STJ, logging, regex, config binding, LibraryImport) and that EF Core and ASP.NET Core have AOT modes with limits. Names .NET 11 runtime-async and the .NET 10 JIT gains as reasons JIT remains competitive for steady-state services.

Trade-offs to name

  • Startup and memory vs peak throughput and PGO.
  • Ecosystem compatibility and debugging comfort vs binary size and deployment simplicity.
  • Build time and CI cost (AOT publishes are slow, per-RID) vs runtime savings.
principalShould a team ban LINQ, async state machines or allocations in "hot" code? How do you define hot?

A strong answer demonstrates

"Hot" is defined by a profile, not by intuition: the methods that show up in the top of a production CPU/allocation trace, or a benchmark with a stated budget. Rules are scoped to those files/projects (allocation analyzers on, LINQ replaced with spans, ValueTask where synchronous completion dominates) and explicitly not applied elsewhere, because readability and correctness are the default. Knows the runtime has moved the line: LINQ fast paths and vectorisation, .NET 10 escape analysis, .NET 11 runtime-async - so yesterday's ban may be today's superstition, and the rule set is re-benchmarked at each runtime upgrade. Talks about how to keep the rule alive: a benchmark in CI failing on allocated bytes, a comment naming the benchmark next to the ugly loop.

Trade-offs to name

  • Readability and reviewability vs the last 10% of throughput.
  • Blanket rules (easy to enforce, often wrong) vs measured exceptions (right, need discipline).
  • Micro-optimisations vs architectural wins (batching, caching, fewer round-trips) that dwarf them.
principalMutable structs, ref returns and Span in application code: how much low-level C# do you let into a business codebase?

A strong answer demonstrates

A layering answer: low-level constructs live in a small, well-tested infrastructure layer (parsers, serialisers, buffers) with a safe API on top, and business code never sees a Span, a ref struct or a mutable struct. Knows the specific hazards (defensive copies, ref escaping, use-after-return with pooling, mutable structs in collections) and the tooling that catches them (compiler ref-safety rules, analyzers, a poisoning pool in tests). Distinguishes "safe but subtle" (readonly struct, in parameters) from "unsafe in effect" (Unsafe.As, MemoryMarshal) and reserves the latter for one reviewed assembly. Mentions the hiring/onboarding cost: constructs half the team cannot review are a bus-factor risk, whatever the benchmark says.

Trade-offs to name

  • Performance headroom vs the number of people who can safely change the code.
  • Encapsulating the tricks vs leaking them through public signatures.
  • Staying on the safe side of the compiler vs relying on Unsafe helpers that skip checks.
principalA colleague argues that dependency injection everywhere makes C# code slow and unreadable. What is your position?

A strong answer demonstrates

Separates the container from the principle: constructor injection of real seams is good design; a container is a convenience that costs almost nothing at runtime (compiled resolvers, singletons resolved once) but can hide lifetimes and object graphs. Names the real problems: captive dependencies (a singleton holding a scoped service - caught by ValidateScopes/ValidateOnBuild), service locators, one-interface-per-class noise, and huge constructors signalling a class doing too much. Offers pragmatic defaults: register by convention or explicitly, keep composition roots visible, use keyed services (.NET 8) rather than factories of factories, and measure - resolve cost is nanoseconds after warm-up, and AOT works with the built-in container. Treats readability as a design issue to fix with better boundaries, not by removing DI.

Trade-offs to name

  • Testability and explicit dependencies vs indirection and discoverability.
  • Container features (decorators, keyed services, scopes) vs the temptation to encode business logic in registrations.
  • Startup validation cost vs runtime surprises.
principalHow much of the new language surface (primary constructors, field, extension members, unions) should a team adopt, and how fast?

A strong answer demonstrates

A process, not a taste: each feature gets a short guidance entry within a sprint of GA (use / with care / avoid), examples from the team's own code, and an .editorconfig setting where the IDE can enforce it (e.g. prefer collection expressions). Adopts features that remove bugs or boilerplate immediately (collection expressions, required, field, Lock), adopts semantics-changing ones with a rule (primary constructors as readonly), waits for GA on unions/closed, and never ships LangVersion preview. Mentions the breaking-change list per compiler version as part of the upgrade checklist and that consistency within a file matters more than being current. Sees the tension between "keep the codebase modern so hiring is easier" and "churn for its own sake".

Trade-offs to name

  • Modernity and recruiting appeal vs review churn and mixed idioms in one codebase.
  • Automated bulk rewrites (code fixes) vs incremental adoption as files are touched.
  • Team familiarity vs feature benefit; teaching cost is real.
principalSource generators vs reflection vs hand-written code for mapping, serialisation and validation: what is your default and what changes it?

A strong answer demonstrates

Default to source-generated where a mature generator exists (STJ, logging, regex, options, P/Invoke, mappers like Mapperly) because it is fast, AOT-safe and reviewable; hand-written for the small number of important mappings where explicitness beats magic; reflection only where the shape is genuinely dynamic at runtime, isolated and cached. Knows the costs of generators: compile-time overhead if written badly, debugging generated code, version coupling to the compiler, and the temptation to generate what should be a library. Names the maintenance question: who owns the generator, how it is tested, and what happens when the SDK updates. Ties it to the AOT and cold-start strategy rather than treating it as taste.

Trade-offs to name

  • Build-time complexity vs runtime cost and trimming safety.
  • Convention-based magic (AutoMapper) vs explicit generated code you can read in a diff.
  • Flexibility of reflection vs the class of bugs it hides until runtime.
principalWhere do you stand on ConfigureAwait(false), ValueTask and other "performance hygiene" rules that most application code does not need?

A strong answer demonstrates

Context sensitivity: library code follows the BCL's own rules (ConfigureAwait(false) everywhere, Task by default, ValueTask where measured); ASP.NET Core application code omits ConfigureAwait and uses Task, with ValueTask only on interfaces designed for it. Explains why (no SynchronizationContext in ASP.NET Core; ValueTask's consumption contract), acknowledges the UI/Blazor exceptions, and turns it into analyzer configuration per project type rather than a debate in every review. Knows that .NET 11 runtime-async changes the allocation argument for ValueTask and would re-evaluate the rule then.

Trade-offs to name

  • Uniform rules (easy) vs per-context rules (correct).
  • Micro-savings vs the misuse surface of ValueTask.
  • Portability of library code into unknown hosts vs noise in application code.
principalAn incident: a memory leak in production traced to a static event subscription in a shared library your team owns. What do you do in the first hour, the first week, and the first quarter?

A strong answer demonstrates

First hour: mitigate (restart cadence or rollback of the consuming service), confirm the root with a gcdump retention path, communicate impact and ETA. First week: fix with unsubscription/weak reference/replacing the static event with an injected, scoped mechanism; ship a patch version with [Obsolete] guidance on the old API; add a soak test in the library's CI that asserts heap growth stays flat over N iterations; write the blameless post-mortem with a timeline. First quarter: audit the library for other static/ambient state, add the leak-detection test pattern to the shared template, put a "memory growth over 1 h" check into the platform's load test, and teach the retention-path debugging workflow to the on-call rotation. The senior signal is the balance between fixing the code and fixing the system that let it ship.

Trade-offs to name

  • Fast mitigation (restarts) vs the pressure to skip the root-cause analysis.
  • Breaking the API to remove the trap vs compatibility for 40 consumers.
  • Test cost (soak tests are slow) vs the class of bugs they catch.

16Design exercises

C# connects to system design where the language's execution model shapes the architecture: back-pressure and cancellation in pipelines, memory layout in high-throughput parsing, isolation and versioning in extensibility. Attempt each prompt aloud before opening the solution. Ask the clarifying questions first - interviewers score them.

Exercise 1 - In-process event processing pipeline

Prompt. Design the in-process pipeline for a service that receives 50,000 events/s over HTTP and Kafka, enriches each event with a lookup, and writes batches to a downstream store with a 200 ms p99 budget. Must degrade gracefully when the store slows down and must shut down without losing acknowledged events.

Clarifying questions to ask. Ordering requirements (global, per key, none)? Delivery semantics - at-least-once acceptable, and is the downstream idempotent? What is "acknowledged": HTTP 202 after enqueue, or after write? Event size and burstiness? Enrichment data size and refresh cadence? Single process or scaled out (affects per-key ordering)? Are we allowed to shed load, and which events are droppable?

principalStrong solution outline and the trade-offs to name

Outline

Stages as bounded Channel<T>s: ingest -> enrich -> batch -> write, each with an explicit capacity derived from the latency budget (e.g. 200 ms × 50k/s = 10,000 in flight total, split across stages). HTTP ingestion awaits WriteAsync on the first channel so full channels turn into 503/429 with Retry-After - backpressure to the producer instead of memory growth; Kafka consumption pauses the partition when the channel is full. Enrichment reads from an immutable snapshot (FrozenDictionary swapped by a refresh loop with Interlocked.Exchange), no locks on the hot path. Batching: a consumer that drains up to N items or T milliseconds (PeriodicTimer + TryRead loop), sized so the store's per-batch latency fits the budget. Writers: Parallel.ForEachAsync with a bounded degree, retries via a resilience pipeline with jitter and a circuit breaker; when the breaker opens, the pipeline fills, ingestion sheds load, and a metric fires. Per-key ordering, if required, by partitioning into K enrich/write lanes by key hash. Shutdown: stop ingestion first (return 503), complete channels in order, drain with HostOptions.ShutdownTimeout raised to the drain budget, and only acknowledge (HTTP 202 / Kafka commit) after the write stage confirms - or, if acking on enqueue is required, persist the queue (an outbox table or a local WAL) because in-memory channels lose data on crash. Observability: queue depth per stage, batch size, write latency, breaker state, dropped count.

Trade-offs to name unprompted

  • Ack-on-enqueue (fast, lossy on crash) vs ack-on-write (honest, slower); at-least-once requires idempotent writes or dedup keys.
  • Bounded channels shed load at the edge vs unbounded channels that fail later and harder.
  • Per-key ordering lanes reduce parallelism and create hot partitions; global ordering makes the design a single consumer.
  • Batch size vs tail latency: bigger batches amortise I/O but raise p99 for the first event in a batch.
  • In-process pipeline (simple, fast) vs a broker between stages (durable, restartable, more moving parts).
  • GC: allocation-free enrichment (struct events referencing pooled buffers) vs simpler class events; measure gen2 under load before optimising.

Sketch

var ingest = Channel.CreateBounded<Event>(new BoundedChannelOptions(4_000) { FullMode = BoundedChannelFullMode.Wait });
var toWrite = Channel.CreateBounded<Batch>(64);

app.MapPost("/events", async (Event e, CancellationToken ct) =>
    ingest.Writer.TryWrite(e) ? Results.Accepted()                      // fast path
    : await TryEnqueueWithTimeoutAsync(ingest.Writer, e, TimeSpan.FromMilliseconds(50), ct)
        ? Results.Accepted() : Results.StatusCode(503));                 // shed when full

// batcher
await foreach (var first in ingest.Reader.ReadAllAsync(stopping))
{
    var batch = new List<Event>(500) { Enrich(first) };
    var deadline = clock.GetTimestamp();
    while (batch.Count < 500 && clock.GetElapsedTime(deadline) < TimeSpan.FromMilliseconds(20) && ingest.Reader.TryRead(out var e))
        batch.Add(Enrich(e));
    await toWrite.Writer.WriteAsync(new Batch(batch), stopping);
}

Exercise 2 - High-throughput log/protocol parser

Prompt. Design a component that parses a line-oriented text protocol (think syslog or a custom CSV-ish format) arriving as byte streams at 1 GB/s aggregate across connections, extracting a dozen fields per line into typed records for downstream filtering, with a strict per-core memory budget and no GC pauses above 10 ms.

Clarifying questions to ask. Encoding (UTF-8 guaranteed?) and maximum line length? Are lines guaranteed to be newline-terminated, and can a line span TCP segments? Which fields must be materialised as strings versus compared/filtered in place? Is the filtering predicate known ahead (can we skip parsing fields that are not needed)? Error policy for malformed lines? Single process, how many cores, and are connections long-lived?

principalStrong solution outline and the trade-offs to name

Outline

Per connection, a System.IO.Pipelines PipeReader over the socket (or Stream): it manages buffer pooling and partial-frame handling, so the parser works on ReadOnlySequence<byte> and advances only past complete lines (SequenceReader<byte>.TryReadTo(out span, (byte)'\n')). Parsing is a ref struct tokenizer over ReadOnlySpan<byte> using SearchValues for delimiters and Utf8Parser/Utf8JsonReader-style number parsing straight from bytes; fields that the filter needs are compared in place (SequenceEqual with "level=error"u8), and only fields that survive the filter get materialised - ideally as slices into a per-batch arena (a rented byte[] copied once per line that passes) rather than as .NET strings. The output record is a readonly record struct of offsets/lengths into the arena plus parsed numerics, passed by in to the next stage; the arena's lifetime is owned by an IMemoryOwner disposed when the batch is consumed. Parallelism is per connection (one parser per socket, no shared state) with connections pinned to a bounded set of worker tasks; no LINQ, no closures, no exceptions on the parse path (malformed lines increment a counter and are skipped). Memory budget: pool sizes computed from max line length × in-flight lines; GC configuration server + DATAS with a hard limit, and the steady state verified allocation-free with [MemoryDiagnoser] per stage and a gcdump showing a few hundred objects. Vectorisation comes for free from the BCL primitives; hand-rolled Vector128 only if a profile shows a specific field's scan dominates.

Trade-offs to name unprompted

  • Zero-copy slicing into pooled buffers (fast, lifetime rules the whole team must respect) vs copying to strings (safe, 10× the allocations).
  • Parsing lazily only what the filter needs vs a uniform record - performance vs simplicity of the downstream contract.
  • UTF-8 in-place processing vs decoding to UTF-16 for .NET string APIs; culture/normalisation only where required.
  • Per-connection isolation (no locks, uneven load) vs work-stealing across connections (balanced, shared queues).
  • Strict memory budget via bounded pools means backpressure on the socket (TCP window closes) - acceptable, or must we drop?
  • Testing: property-based tests over random line splits at every byte boundary are mandatory with partial-frame parsing.

Sketch

static async Task ReadLinesAsync(PipeReader reader, LineSink sink, CancellationToken ct)
{
    while (true)
    {
        var result = await reader.ReadAsync(ct);
        var buffer = result.Buffer;
        while (TryReadLine(ref buffer, out var line))        // line: ReadOnlySequence<byte> without '\n'
            ParseLine(line.IsSingleSegment ? line.FirstSpan : line.ToArray(), sink);   // multi-segment lines are rare: copy
        reader.AdvanceTo(buffer.Start, buffer.End);
        if (result.IsCompleted) break;
    }
}

private static readonly SearchValues<byte> Delims = SearchValues.Create("|,"u8);

static void ParseLine(ReadOnlySpan<byte> line, LineSink sink)
{
    int i = line.IndexOfAny(Delims);
    if (i < 0) { sink.Malformed++; return; }
    if (!Utf8Parser.TryParse(line[..i], out long ts, out _)) { sink.Malformed++; return; }
    var rest = line[(i + 1)..];
    if (!rest.StartsWith("error"u8)) return;                  // filter in place, nothing allocated
    sink.Emit(new LineRef(ts, rest));                          // ref struct / offsets, no string
}

Exercise 3 - Plugin/extensibility system for a long-running service

Prompt. Design an extensibility model for a rules engine service where internal teams ship "rule packs" as .NET assemblies that evaluate against domain objects. Packs must be updatable without redeploying the host, must not be able to take the host down, and the host must support two pack versions side by side during a rollout.

Clarifying questions to ask. Are pack authors trusted (same org) or arbitrary? What is the contract surface - a single Evaluate(context) or rich host services? Latency budget per evaluation (in-process nanoseconds, or is a process hop acceptable)? How often do packs change, and how many are loaded concurrently? Do packs need their own NuGet dependencies, possibly conflicting with the host's? Is NativeAOT for the host on the roadmap (it rules out dynamic loading)?

principalStrong solution outline and the trade-offs to name

Outline

Two designs, chosen by trust and latency. (A) In-process with AssemblyLoadContext isolation: a small contracts assembly (IRulePack, RuleContext, a versioned IHostServices) shared from the host's default context, each pack loaded into its own collectible ALC from its own directory with its own .deps.json, so packs bring their own dependency versions without conflicting; side-by-side means two ALCs for two versions of the same pack with routing by version in the host; updates load the new version, drain evaluations from the old one (reference counting per in-flight call), then Unload() and verify collection with a weak reference; failures are contained by a timeout per evaluation (WaitAsync with a cancellation token the pack must honour), catching all exceptions at the boundary, and quarantining a pack after N failures - but a pack that stack-overflows, spins a CPU or leaks native memory can take the host down, which must be said plainly. (B) Out-of-process: packs run in a sidecar per pack (or per version), the host talks gRPC over Unix sockets, and the orchestrator restarts a crashed sidecar; costs ~100 µs per call and serialisation of the context, buys real isolation, per-pack resource limits, independent deployability and AOT compatibility for the host. For internal, trusted packs with sub-millisecond budgets choose (A) with the containment measures and a kill switch; for anything less trusted or if the budget allows, choose (B). In both: contract versioning with default interface members and [Obsolete] diagnostics, a pack manifest (contract version, dependencies, signature), signed packs verified before load, structured metrics per pack (latency, failures, memory delta), and a canary routing rule (1% of evaluations to the new version) before full cutover.

Trade-offs to name unprompted

  • In-process speed and simplicity vs the honest limit of ALC isolation (no CPU/memory/crash isolation).
  • Collectible ALCs enable updates without restarts, but unload only succeeds if the host holds no references - caches keyed by pack types are the classic leak.
  • Sharing the contract assembly (must not be duplicated in pack output) vs letting packs compile against their own copy (type identity breaks).
  • Rich host services in the contract (powerful packs, bigger compatibility surface) vs a minimal contract (safe, limiting).
  • Side-by-side versions double memory and warm-up; routing by version needs an explicit policy and observability.
  • NativeAOT for the host is incompatible with (A); if it is on the roadmap, (B) is the only option.

Sketch

public interface IRulePack                     // contracts assembly, shared with the host context
{
    string Id { get; }  Version ContractVersion { get; }
    ValueTask<Verdict> EvaluateAsync(RuleContext ctx, CancellationToken ct);
}

sealed class LoadedPack : IAsyncDisposable
{
    private readonly PluginLoadContext _alc; private readonly IRulePack _pack; private int _inFlight;
    public async ValueTask<Verdict> EvaluateAsync(RuleContext ctx, CancellationToken ct)
    {
        Interlocked.Increment(ref _inFlight);
        try
        {
            using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct); cts.CancelAfter(TimeSpan.FromMilliseconds(50));
            return await _pack.EvaluateAsync(ctx, cts.Token).AsTask().WaitAsync(cts.Token);
        }
        catch (Exception ex) { Quarantine.Record(_pack.Id, ex); return Verdict.Error; }   // boundary: nothing escapes
        finally { Interlocked.Decrement(ref _inFlight); }
    }
    public async ValueTask DisposeAsync()
    {
        while (Volatile.Read(ref _inFlight) > 0) await Task.Delay(10);   // drain
        _alc.Unload();                                                   // collectible; verify with WeakReference in tests
    }
}

17Night-before cheat sheet

The ten most-asked questions of the whole bank, one sentence each. If you can say these without hesitating, the rest of the loop is about depth, not recall.

  1. What does await do? - Checks IsCompleted, continues synchronously if done, otherwise registers a continuation via a compiler-generated state machine and returns to the caller; no thread is created, and the continuation resumes on the captured context or the thread pool (.NET 11 moves this into the runtime).
  2. Why is async void bad? - Nothing can await or observe it, so exceptions crash the process and lifetimes are untracked; only for event handlers, with a try/catch.
  3. Value vs reference types? - Copy semantics vs shared references; structs live wherever their container lives, not "on the stack"; box when converted to object/interfaces, which generics avoid.
  4. How does the GC work? - Generational (gen0/1/2), LOH at 85,000 bytes, cost proportional to live objects not garbage; server vs workstation, DATAS default for server GC since .NET 9; never call GC.Collect() in production code.
  5. Record vs class? - Records give value equality, with, ToString and deconstruction for value objects and DTOs; entities with identity stay classes; never records for EF entities or mutable dictionary keys.
  6. Deferred execution? - LINQ builds a pipeline executed on enumeration; enumerating twice runs it twice (two DB queries); materialise with ToList() when reusing.
  7. What does lock guarantee, and what is System.Threading.Lock? - Mutual exclusion plus memory barriers on a private object; .NET 9's Lock type is the faster, non-boxing replacement; volatile does not make ++ atomic, Interlocked does.
  8. Task vs ValueTask? - Task by default; ValueTask only for measured hot paths that usually complete synchronously, awaited exactly once, never stored or fanned out.
  9. throw; vs throw ex;? - throw; keeps the original stack trace, throw ex; resets it; use filters (when) to observe without unwinding, and exceptions for exceptional conditions only.
  10. What is current? - C# 14 on .NET 10 LTS (2025-11-11; 10.0.12 servicing on 2026-09-08): extension members, field, null-conditional assignment, first-class spans; .NET 11 RC1 with C# 15 preview (unions, closed, runtime-async) ships GA November 2026; .NET 8 and 9 both end support 2026-11-10.
