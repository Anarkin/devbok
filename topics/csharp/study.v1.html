01 Types, values and identity

Docs: Value types · Records

Everything else in C# is a consequence of one decision the language made in 2000 and has never walked back: a type is either a value type or a reference type, and that choice decides what a variable contains. A variable of a reference type contains a reference — a machine word pointing at an object on the GC heap. A variable of a value type contains the instance itself, wherever the variable happens to live: a stack slot, a field inside another object, a slot in an array. Say that precisely at interview, because the folk version ("structs live on the stack") is wrong and interviewers use it as a filter. A struct field inside a class lives on the heap, inside that object. A struct captured by a lambda lives on the heap, inside the closure. "Stack" is an implementation detail of one common case; "the variable contains the instance" is the actual rule.

The running example

Keep one picture: a Point with X and Y, and an Order with a customer and a list of lines. Point is small, immutable, has no identity — two points with the same coordinates are the same point, and nobody asks "which Point object is this?". Order has identity — order 4711 is order 4711 even after you change its address, and two orders with identical contents are still two orders. That distinction, does this thing have identity?, is the single best predictor of struct-versus-class, and it is a far better answer than "structs if it's under 16 bytes". Size is a performance tiebreaker; identity is the semantic question.

Copying, and where people get hurt

Assignment of a value type copies the whole instance, field by field. Passing it to a method copies it. Returning it copies it. Reading it out of a List<T> via the indexer copies it — which is why list[0].X = 5 does not compile for a struct: you would be mutating a temporary. That compiler error is a gift; the versions of the same mistake that do compile are the dangerous ones.

struct MutablePoint { public int X; public void Bump() => X++; }

var array = new MutablePoint[1];
array[0].Bump();            // works: array indexers give a real reference to the element
Console.WriteLine(array[0].X); // 1

var list = new List<MutablePoint> { default };
list[0].Bump();             // COMPILE ERROR - list[0] is a returned copy, not a variable

readonly MutablePoint _origin;   // a readonly field
void Go() => _origin.Bump();     // COMPILES. Silently mutates a defensive COPY. Nothing happens.

That last line is the classic. Because Bump() is not declared readonly, the compiler cannot prove it does not mutate, so it makes a defensive copy of the readonly field, calls the method on the copy, and throws the copy away. No error, no warning by default, no effect — and a hidden copy on every call. The fix is the discipline the whole ecosystem now follows: make structs readonly struct. Then every member is implicitly readonly, defensive copies disappear, and mutation is a compile error instead of a silent no-op. If you need mutation, mark individual members readonly (C# 8) so the compiler knows which ones are safe.

Boxing: the value type's tax

When a value type has to be treated as object, as a non-generic interface reference, or as anything the runtime needs to look up virtually at a reference-shaped slot, it is boxed: a heap object is allocated, the bits are copied into it, and you now hold a reference. Boxing is invisible in the source, it allocates, and it breaks the mental model people carry ("structs don't allocate"). The four places it happens in real code:

  • object o = 42; and anything that goes through object — old-style collections, string.Format with value arguments before the interpolated-string handler improvements of C# 10, logging APIs that take params object[].
  • Casting a struct to an interface it implements: IComparable c = 42; boxes. But calling CompareTo through a generic constraint where T : IComparable<T> does not — the JIT specializes the method per value type and calls it directly. This is the whole reason generic constraints exist in the form they do.
  • A struct that does not override Equals(object)/GetHashCode falls back to ValueType.Equals, which historically used reflection and boxed. Implement IEquatable<T> and override both, or use a record struct, which generates all of it for you.
  • foreach over an interface-typed collection (IEnumerable<T>) uses the interface enumerator, which boxes struct enumerators; foreach over the concrete List<T> uses its struct enumerator by duck-typing and does not.

Records: the "I only care about the data" type

C# 9 added record (a reference type) and C# 10 record struct. A record is not a new kind of type — it is a class or struct with a pile of generated members: a value-based Equals/GetHashCode/==, a readable ToString, a Deconstruct for positional records, a protected copy constructor, and a Clone that makes with expressions work. That last one is the underrated part: order with { Status = Shipped } is a shallow copy with one field replaced, which is how you get immutable domain objects without writing 40 lines of constructor.

public record class Order(int Id, string Customer, decimal Total)
{
    public OrderStatus Status { get; init; } = OrderStatus.Draft;
}

var a = new Order(4711, "Acme", 99.50m);
var b = a with { Status = OrderStatus.Shipped };   // shallow copy, one property changed
Console.WriteLine(a == b);                          // False - value equality includes Status
Console.WriteLine(a with { Status = OrderStatus.Draft } == a); // True

// record struct: value semantics AND a value type. readonly by choice:
public readonly record struct Money(decimal Amount, string Currency);

Two caveats worth naming out loud, because they are exactly what a senior interviewer probes. First, record equality is shallow: a record holding a List<string> compares the list by reference, so two records with equal-looking contents are unequal. Records are for data that is itself immutable and value-like; the moment you put a mutable collection in one, you have a bug waiting. Second, record equality is exact-type: the generated Equals compares EqualityContract, so a Manager record never equals an Employee record even with identical fields. That is usually what you want, and it is the opposite of what most hand-written Equals implementations do.

Equality: four different questions

Interviewers love this because most candidates conflate them. ReferenceEquals(a, b) asks "same object?". a == b asks whatever the compile-time types' operator says — it is resolved statically, so assigning two strings to object variables changes == from string comparison to reference comparison. a.Equals(b) is virtual, so it uses the runtime type. IEquatable<T>.Equals is the strongly-typed, non-boxing version that generic collections prefer. Collections use EqualityComparer<T>.Default, which picks IEquatable<T> when present and falls back to the virtual Equals(object) otherwise.

object x = new string("abc".ToCharArray());
object y = new string("abc".ToCharArray());
Console.WriteLine(x == y);            // False  - operator == on object: reference comparison
Console.WriteLine(x.Equals(y));       // True   - virtual dispatch reaches String.Equals
Console.WriteLine((string)x == (string)y); // True - static resolution now picks string's ==

The contract you must be able to recite: equal objects must have equal hash codes; hash codes must not change while the object is a key; GetHashCode should be cheap; unequal objects may share a hash code. Use HashCode.Combine(a, b, c) (.NET Core 2.1+) rather than hand-rolled 17 * 31 + … — it is randomised per process, which matters for hash-flooding resistance, and it is why you must never persist a GetHashCode value to disk or across processes.

Default values, and the hole in nullability

Every value type has a zero-bit default: default(int) is 0, default(Point) has all fields zeroed, and there is no way to prevent it. A struct cannot declare a parameterless constructor that the runtime is obliged to call — new T[1000], default(T), and an uninitialized field all produce the zero value without running any code. C# 10 allows you to write a parameterless struct constructor and field initializers, but they run only for explicit new Point(), not for default. This is why "make it a struct so it can't be null" is only half true: it cannot be null, but it can absolutely be a meaningless all-zero instance, and a Money struct whose Currency is null is a nullability hole the compiler will not warn about (unit 02).

Interview trap

"Structs are faster because they don't allocate." Three ways that goes wrong in the same interview. (1) A large struct — anything past roughly 3–4 words — costs more in copying than a class costs in allocation and indirection; System.Numerics aside, the crossover is usually around 16–24 bytes and it is measurable, not theoretical. (2) Any struct that reaches an object, a non-generic interface, or an untyped API is boxed, so it allocates and pays a copy. (3) A struct in a List<T> read through the indexer is copied on every read; the fix is CollectionsMarshal.AsSpan(list) or foreach (ref var item in span), not "use a class". The lead-level answer is: choose by identity and mutability first, then measure. And when someone says "value types are on the stack", correct it gently — a value-type variable holds the value; where the variable lives decides where the value lives.

Gotcha

GetHashCode on a mutable object used as a dictionary key is a silent data-loss bug, not a crash. Insert an Order, mutate its Id, and the entry is still in the bucket it was hashed into — lookups miss, enumeration still finds it, and Remove fails. Records make this easier to hit because they hand you value equality on a type you might later give a mutable property to. Rule for review: a type with value equality should be immutable, full stop.

Try it — prove the defensive copy exists

Exercise 1. Write a struct Counter { public int N; public void Inc() => N++; }, hold one in a readonly field of a class, call Inc() a thousand times in a loop, and print N. Then change the declaration to readonly struct and see what the compiler says. Then remove readonly from the field.

Exercise 2. Put a mutable class into a HashSet<T> with a hash based on a mutable property, mutate the property, then call Contains with the same instance.

Expected outcome

1. With a plain struct in a readonly field, N prints 0 after a thousand increments: every call operated on a fresh defensive copy. Marking the struct readonly struct turns Inc() into a compile error (CS1604-family: cannot assign to N because it is read-only) — the bug becomes impossible instead of invisible. Removing readonly from the field makes it print 1000. The lesson: readonly on a field is a correctness feature and a hidden per-call copy unless the type is readonly struct.

2. Contains returns false for an object that is demonstrably in the set — enumerate it and you will see it. The item is in the bucket for the old hash. This is why every serious codebase bans mutable keys, and why record types used as keys should be readonly/init-only throughout.

Interview Q&A · types and identity

When do you choose a struct over a class?

I start from semantics, not performance: does the thing have identity? A Money, a Point, a DateOnly, a database row's composite key — those are values, two of them with equal fields are interchangeable, and a struct says that in the type system. An Order or a Connection has identity and lifecycle, so it is a class. Then I apply the performance filter: the struct should be small (roughly under 16–24 bytes; past that copying costs more than the allocation it saves), immutable — readonly struct so the compiler eliminates defensive copies — and it must not spend its life being boxed into object or a non-generic interface, because then it allocates anyway and I have paid twice. The one case where I let performance lead is a hot loop over a large array of small values, where struct layout gives me contiguity and cache locality that a class array cannot: an array of classes is an array of pointers to scattered objects.

What actually happens when a value type is boxed, and how do you spot it in a profile?

The runtime allocates a heap object with a normal object header and method table pointer, copies the value's bits into the payload, and hands back a reference. Unboxing copies back out and is checked — an InvalidCastException if the type does not match exactly, including a boxed int unboxed as long. In a profile it shows as unexpectedly high Gen0 allocation in code that "shouldn't allocate", and in an allocation trace you literally see System.Int32 or your struct type as an allocated type. The usual sources are logging and string formatting with object parameters, non-generic collections in old code, Enum.HasFlag before .NET Core 2.1 (which boxed twice), LINQ over structs where a lambda captures, and comparisons through non-generic IComparable. I fix it with generic constraints — where T : IEquatable<T> lets the JIT specialize and call directly — and by giving structs proper IEquatable<T> implementations.

Records are just classes with generated members — so when are they the wrong tool?

Whenever the type is not actually a value. Records hand you value equality, and value equality on something with identity is a landmine: two different customers with the same name compare equal, and if you use the record as a dictionary key and something mutates it, entries go missing. They are also the wrong tool when the payload contains mutable collections, because the generated equality is shallow — record Basket(List<Item> Items) compares the list by reference, so two logically-identical baskets are unequal, which is worse than no equality at all because it looks like it works. And in EF Core, records as entities fight the change tracker, which is built around identity and mutation. Where they are excellent: DTOs, API contracts, domain events, messages, configuration snapshots, and anything you want to with-copy in a pipeline.

Explain the difference between == and Equals in a way a mid-level engineer would remember.

== is chosen by the compiler from the static types; Equals is chosen by the runtime from the actual object. So == can change meaning if you widen a variable to object — the classic demo is two identical strings compared as object, which is false. For reference types with no overload, == means reference identity; string, records and most value types overload it to mean value equality. Equals(object) is virtual and boxes value types, so IEquatable<T> exists as the typed, allocation-free version, and it is what EqualityComparer<T>.Default — and therefore Dictionary, HashSet, Contains, Distinct — actually calls. The practical rule I enforce in review: if you override one, do all four coherently (Equals(object), Equals(T), GetHashCode, and the operators), or use a record and let the compiler do it.

What is the GetHashCode contract, and what breaks if you get it wrong?

Equal objects must produce equal hash codes; the hash must be stable for as long as the object is used as a key; and it should be cheap and well-distributed. Unequal objects sharing a hash is legal — that is just a collision, and the bucket falls back to Equals. Break the first rule and lookups silently miss: the value is in the dictionary but you cannot find it. Break the second — a mutable key — and you get the same silent miss, intermittently, in production, usually under concurrency where it looks like a race. Break "well-distributed" and a dictionary degrades toward a linked list; .NET mitigates this for string keys by switching to a randomised hash after too many collisions in one bucket, which is a defence against algorithmic-complexity denial of service. I use HashCode.Combine, and I never persist a hash code, because it is randomised per process by design.

Why does the compiler reject list[0].X = 5 for a struct but accept array[0].X = 5?

Because List<T>'s indexer is a property whose getter returns a copy — the result is a value, not a variable, so assigning to a field of it would silently do nothing, and the language makes that an error. Array element access is not a method call: the compiler produces a managed reference to the element itself, so the assignment lands in the array. It is a great question because the answer generalises: the same rule explains why mutating a struct through a property, a foreach variable, or a method's return value is either an error or a no-op. If I genuinely need in-place mutation of structs in a list — usually in a hot path — I take a span with CollectionsMarshal.AsSpan(list) and iterate foreach (ref var item in span), which gives me real references and no copies.

What does readonly struct buy you, and what does ref struct mean?

readonly struct declares that no member mutates state, so the compiler stops making defensive copies when the value is behind a readonly field or an in parameter — that alone can be a measurable win in hot code, and it turns silent no-op mutations into compile errors. ref struct is a different axis: it says the value may contain managed references into arbitrary memory, so the runtime forbids it from ever living on the heap. It cannot be boxed, cannot be a field of a class, historically could not be used as a generic argument or captured by a lambda or live across an await. Span<T> is the canonical one. C# 13 relaxed the biggest restriction with where T : allows ref struct, so generic code can finally accept spans, and C# 11 added ref fields so you can build your own span-like types.

Can a struct be immutable in a way the runtime enforces?

Not completely, and that is worth being honest about. readonly struct stops your code from mutating fields, and init accessors stop assignment after construction, but the runtime can still hand you an all-zero instance that never ran a constructor: default(T), new T[n], an uninitialized field, or a deserializer using FormatterServices. So a readonly record struct Money(decimal Amount, string Currency) can exist with a null currency and the nullable analysis will not warn, because it never saw a constructor. The mitigation is to validate at the boundary rather than trust the type, or to accept the zero value as a legitimate "empty" state and design for it — which is exactly what DateTime.MinValue, Guid.Empty and default(TimeSpan) do. I would rather have an explicit Money.None than pretend default is unreachable.

How do you decide between a record, a class with init properties, and a tuple for a small data carrier?

Tuples for something that never leaves the method or one private call — they are structural, so (int Id, string Name) in one file is the same type as in another, which means no shared contract and no place to hang validation or documentation. The moment the shape crosses a public API, a serialisation boundary, or a team boundary, I want a named type, because a tuple's element names are only compiler metadata and they disappear through reflection, dynamic and some serializers. Between the two named options: a record if I want value equality, with-copies and a good ToString for free; a class with init properties if I want reference identity but immutability, which is the right shape for things that are configured once and shared, like an options object. In a public API I lean toward records for messages and classes for services and entities.

Where does the value of a struct actually live? Give me the cases.

The instance lives wherever the variable lives. A local that never escapes is a stack slot or, more often, a register. A field of a class is inside that class's heap object. An element of an array is inline in the array's heap block, which is exactly why an array of structs has better locality than an array of class references. A struct captured by a lambda or an iterator or an async method is hoisted into the compiler-generated closure or state-machine object, so it is on the heap. A boxed struct is a heap object of its own. And a struct in a static field is in the loader heap of its type. The one thing I never claim is "structs are stack-allocated" — the JIT is also free to stack-allocate small non-escaping classes now, in .NET 9 and later, so even the reference-type side of that folk rule is no longer true.

02 Nullability as a contract

Docs: Nullable reference types · Nullable attributes

Nullable reference types (C# 8, 2019; on by default in every template since .NET 6) are the largest behavioural change to the language since generics, and the single most misunderstood. Here is the sentence that unlocks it: NRT is a static analysis over a documentation feature. The runtime does not participate. string and string? are the same type — System.String — and at runtime both can hold null. What you have added is a compiler that tracks, per variable, per branch, whether a value may be null, and warns when the flow says it may be and you dereference it anyway. Nothing throws because a string parameter received null. Nothing is checked at a DLL boundary. It is a type system bolted on with attributes, and it is only as strong as the honesty of the code around it.

That framing matters at lead level because it tells you the failure modes in advance: null still arrives from unannotated third-party libraries, from JSON deserialisation that never runs a constructor, from reflection and ORMs, from default(T) in generic code, from arrays (new string[10] is ten nulls in an array typed non-nullable and the compiler shrugs), and from anywhere someone typed !. Your job is not to reach zero warnings; it is to make the annotations true at the boundaries where data enters.

How the flow analysis actually thinks

The compiler tracks two orthogonal things. The annotation is what you declared — string? versus string. The flow state is what it has proven at this point in the method — "maybe null" or "not null". Assignments, null checks, is not null patterns, and method calls with the right attributes all move the flow state. This is why if (s != null) { s.Length; } compiles with no warning even though s is declared string?: the annotation still says nullable, but the flow state inside the branch says not-null. Conversely a non-nullable string that you assign null! to has flow state "maybe null" and will warn on the next dereference, which surprises people who think ! is permanent. It is not: ! only edits the flow state at that one expression.

#nullable enable

string? Find(int id) => id == 1 ? "one" : null;

void Use(int id)
{
    var name = Find(id);
    // Console.WriteLine(name.Length);      // CS8602: dereference of a possibly null reference

    if (name is not null)
        Console.WriteLine(name.Length);      // fine: flow state is not-null in this branch

    if (string.IsNullOrEmpty(name)) return;
    Console.WriteLine(name.Length);          // fine: IsNullOrEmpty is [NotNullWhen(false)]

    Console.WriteLine(name?.Length ?? 0);    // always fine
}

That third case is the one that shows you understand the mechanism rather than the syntax. string.IsNullOrEmpty is not magic — it is annotated [NotNullWhen(false)] on its parameter, so the compiler knows that a false return proves not-null. Before .NET 5 those annotations were incomplete and everyone had to write !; today the BCL is fully annotated and your own helpers should be too. The set you should be able to name:

The four holes, and what to do about each

  • Deserialisation and ORMs. JsonSerializer.Deserialize<Person>("{}") happily produces a Person whose non-nullable Name is null, because it sets properties by reflection and never ran your validation. System.Text.Json gained RespectNullableAnnotations in .NET 9 to make that throw — turn it on. For EF Core, non-nullable reference properties become NOT NULL columns, which is a real benefit, and the standard idiom for navigation properties is = null!; with a comment saying the ORM fills it.
  • Constructors and object initializers. A non-nullable property with no constructor assignment warns (CS8618), and for years the workaround was = null!. C# 11's required modifier is the real fix: it makes the compiler force the caller to set the property in an object initializer, which is checked at the call site and recorded in metadata so it works across assemblies.
  • Generics. T? on an unconstrained T means "the default-ish nullable form of T", and default(T) for a reference T is null even though T looks non-nullable. This is why Dictionary.TryGetValue needs [MaybeNullWhen(false)] out TValue value and why writing genuinely null-correct generic code needs either where T : class, where T : struct, or where T : notnull.
  • Arrays and collections. new string[10] is ten nulls in a string[]. There is no fix in the language; you either fill it immediately or type it string?[] and be honest.
public class Person
{
    public required string Name { get; init; }        // C# 11: caller MUST set it
    public string? Nickname { get; init; }            // genuinely optional
    public List<string> Tags { get; init; } = [];     // C# 12 collection expression, never null
}

Adopting it on a large existing codebase

This is the question you will actually be asked, and "we turned it on and fixed 9,000 warnings" is the wrong answer. The approach that works: set <Nullable>enable</Nullable> in Directory.Build.props so new projects are correct from birth, and for legacy projects use <Nullable>annotations</Nullable> first — annotations are honoured, warnings suppressed — so you can annotate the public surface of a library without breaking the build. Then move file by file with #nullable enable at the top of files you are already touching, starting at the edges: DTOs, parsers, deserialisation, and the public API of your core assemblies, because annotating a leaf class is worthless while the boundary lies. Treat CS8600-family warnings as errors in the projects that are done, so they cannot regress. And ban ! in review except with an adjacent comment saying why it is provably safe — an unexplained ! is a NullReferenceException with extra steps.

Interview trap

"With nullable reference types on, I don't need argument null checks any more." Wrong, and it is a security-relevant kind of wrong for library authors: nothing stops a caller compiled without NRT, or a caller in F#/VB, or a dynamic/reflection call site, or a JSON payload, from handing you null. On a public API you keep the runtime check — ArgumentNullException.ThrowIfNull(input) (.NET 6, one line, and the JIT inlines it into nothing on the happy path) — because you want a clean ArgumentNullException naming the parameter rather than a NullReferenceException ten frames deeper. On internal code where the whole graph is annotated and warnings are errors, dropping the checks is reasonable. The distinction — public boundary versus internal invariant — is the answer they are listening for.

Gotcha

string? s = null; s!.Length; compiles and throws. ! is not an assertion, not a check, and generates no IL — it edits the compiler's opinion and nothing else. The related surprise: if (x is null) and if (x == null) are not equivalent for a type that overloads operator ==. is null is a pattern and always does a genuine null comparison; == null calls the overload, which for a badly written operator can do anything at all — including recursing or throwing. Prefer is null / is not null.

Try it — find the hole in your own annotations

Exercise 1. In a project with <Nullable>enable</Nullable>, define record Person(string Name, int Age) and run JsonSerializer.Deserialize<Person>("{}"). Print p.Name.Length. Then set JsonSerializerOptions.RespectNullableAnnotations = true and run it again.

Exercise 2. Write a helper static bool TryParseId(string? text, out Guid id) and use it in a caller as if (TryParseId(s, out var id)) { … }, then add [NotNullWhen(true)] string? text and observe what changes at the call site.

Expected outcome

1. The first run prints nothing and throws NullReferenceException — Name is null inside a type that says it never is. (With a positional record you may instead get a constructor-based bind and a null argument; either way the invariant is violated without a warning.) With RespectNullableAnnotations = true (.NET 9+) you get a JsonException at deserialisation time instead, which is where the error belongs. This is the single most convincing demonstration that NRT is compile-time only.

2. Without the attribute the compiler still thinks s may be null after the if, so dereferencing it warns and people add !. With [NotNullWhen(true)] the flow state flips inside the true branch and the warning disappears with no ! anywhere. Annotating your own Try… and validation helpers is the highest-leverage nullability work in a codebase — it removes the ! that would otherwise spread.

Interview Q&A · nullability

Are nullable reference types enforced at runtime?

No. string and string? compile to the same System.String; the difference is recorded in NullableAttribute/NullableContextAttribute metadata purely so other compilations can read your intent. There is no runtime check, no cast failure, no exception on assignment. What you get is a compiler that does per-branch flow analysis and warns. That has two consequences I always spell out: warnings are advice unless you make them errors, and any value that arrives without passing through C# code — deserialisation, reflection, an ORM, interop, or an unannotated dependency — can violate the annotations silently. So annotations are a contract between honest parties, and you still validate at trust boundaries.

How would you roll NRT out across a large legacy solution?

Incrementally, from the outside in, and never as a big-bang branch. First, Directory.Build.props sets Nullable=enable so every new project starts clean. Second, legacy projects get Nullable=annotations: annotations are recorded and consumed by callers, warnings are off, so I can annotate a shared library's public API and every consumer immediately benefits without a single build break. Third, per-file #nullable enable as part of normal work — the rule is "you touch it, you annotate it" — prioritising boundary types: DTOs, request/response models, parsing, configuration. Fourth, once a project is clean, its warnings become errors so it cannot regress. I also add an analyzer rule or a review convention that bans bare !. The metric I track is not "warnings remaining" but "percentage of the public surface annotated", because that is what actually reduces NREs.

What does the null-forgiving operator really do, and when is it acceptable?

It emits no IL at all. It tells the compiler "treat this expression's flow state as not-null here" and nothing else, so it is a way of moving a potential crash from compile time to runtime. It is acceptable in three places: an EF Core navigation property or a framework-populated field where the runtime genuinely guarantees the assignment (= null! with a comment); in tests, where you are deliberately constructing an invalid object; and immediately after a check the compiler cannot see through, such as a custom assertion helper you have not annotated yet — although in that case the right fix is to add [NotNull] or [DoesNotReturnIf] to the helper so nobody needs the operator again. Anywhere else, an unexplained ! is a review comment.

Why is required better than initialising a property to null!?

Because null! lies and required tells the truth. = null! silences CS8618 by asserting the property will be set, but nothing verifies that; you get a null in a non-nullable property and a crash at first use. required (C# 11) makes the compiler reject any construction that does not set the member in an object initializer, and it is recorded in metadata as RequiredMemberAttribute so the enforcement crosses assembly boundaries. It also composes with init, so you keep immutability without writing a constructor whose only job is validation. The one thing it does not do is help with reflection-based construction — a deserializer bypasses it — so for external data I still validate, or configure the serializer to respect required members, which System.Text.Json does by default for required since .NET 8.

How do nullable annotations work with generics?

Badly, until you constrain. For an unconstrained T, the compiler cannot know whether T is a value type or a reference type, so T? means "T with the nullable-ish treatment appropriate to whichever it turns out to be", and default(T) is null for reference types even where the signature reads non-nullable. That is exactly why Dictionary<K,V>.TryGetValue declares [MaybeNullWhen(false)] out TValue value rather than out TValue?. If I am writing an API where nullability matters, I constrain: where T : class gives me real T?, where T : struct gives me Nullable<T>, and where T : notnull forbids callers from instantiating with a nullable type at all, which is what I use for dictionary keys and cache keys.

What is the difference between x is null and x == null?

is null is a constant pattern and always compiles to a genuine reference (or HasValue) comparison. == null performs overload resolution and will call a user-defined operator == if the static type has one. For most types they agree, but for a type with a sloppy operator — one that dereferences the other operand, or that treats an "empty" instance as equal to null, which Unity's UnityEngine.Object famously does — they disagree, and the failure is confusing because the code reads as a null check. It also matters in generic code, where == null on an unconstrained T does not even compile without a constraint, while is null does. I default to is null / is not null and I have an analyzer suggest it.

Give me a case where the compiler says a value is non-null and it is null at runtime, other than !.

Several. new string[10] creates an array typed string[] containing ten nulls — arrays cannot express "not yet initialised". default(T) in generic code, or any struct's zero value whose reference-typed fields are null: default(Money) where Money is a readonly record struct Money(decimal, string Currency) has a null Currency in a non-nullable slot, with no warning, because no constructor ran. A partially-constructed object: a virtual method called from a base constructor sees the derived class's non-nullable fields still null. Deserialisation and ORM materialisation. And any call into a library compiled without an annotation context, where the compiler treats every reference as "oblivious" and simply does not warn either way. Knowing this list is the difference between using NRT and trusting it.

What did C# 14 add here, and does it change how you write null handling?

Null-conditional assignment: ?. and ?[] are now legal on the left-hand side, so customer?.Order = GetCurrentOrder(); replaces an if (customer is not null) block, and the right side is not evaluated at all when the receiver is null — which matters when it has side effects or costs something. Compound assignments (+=, ??= and friends) work too; ++ and -- are deliberately excluded because the read-modify-write semantics on a null receiver would be ambiguous. It is a readability feature rather than a semantic one: it removes a nesting level in mapping and update code. I would not describe it as changing strategy — the strategy is still "make nulls impossible at the boundary" — but it does remove a common source of accidental non-short-circuiting bugs where someone computed the right-hand side before checking the receiver.

How do you keep null out of your domain model entirely?

By making the boundary do the work. External input — HTTP bodies, config, message payloads, database rows — is parsed into a nullable-tolerant DTO, validated once, and mapped into a domain type whose constructor or required members cannot produce an invalid instance. Inside the domain, absence is modelled explicitly rather than with null: an empty collection instead of a null collection (= [] as the initializer, always), a state enum or a closed hierarchy instead of "null means not yet approved", and a Try… method or a result type instead of "returns null on failure". The place I do accept null is genuinely optional data — a middle name — where string? is honest and cheap. The anti-pattern I push back on is a null-object or null-propagating chain (a?.b?.c?.d) deep in business logic, because it converts a missing invariant into a silently wrong result instead of an error.

What is "oblivious" nullability and why does it matter when you consume packages?

A reference type compiled without a nullable context is neither nullable nor non-nullable — the metadata says "unknown", and the compiler deliberately stays silent about it in both directions. So a package compiled for .NET Framework or an older SDK gives you no warnings whether you pass null in or dereference what comes back, which means your beautifully annotated code has an unlit corridor running through it wherever it touches that dependency. Practically: when I pull in a dependency I check whether it is annotated (the package's target framework and whether IntelliSense shows ? on its signatures), and if it is not, I wrap it in a thin adapter that states the real nullability myself, based on its documentation and behaviour. That adapter is also where I put the runtime null checks, so the lie stops at one file instead of spreading.

03 Members and initialization

Docs: Constructors · The field keyword

A type's members are where C#'s "no boilerplate" evolution is most visible. The same class that needed 60 lines in C# 5 is 6 lines in C# 14, and every one of those savings has a rule behind it that interviewers use to check whether you actually know what the compiler generated. This unit is the mechanics of construction and the members that hang off it, and it connects directly to unit 02: most nullability warnings are really initialization-order questions in disguise.

Properties are methods, and that has consequences

public string Name { get; set; } is two methods and a private field named <Name>k__BackingField. Because they are methods, a property is not a variable: you cannot pass it by ref, you cannot take its address, mutating a struct through it silently mutates a copy (unit 01), and reading it in a hot loop is a call the JIT usually — but not always — inlines. Because it is a method, it is also the correct place for a public API: swapping a field for a property is a binary breaking change even though it is source-compatible, which is why every public API guideline says expose properties, never fields.

The accessor story evolved in three steps. init (C# 9) is a setter that may only run during construction or an object initializer, giving you immutability without a constructor. required (C# 11) forces the caller to supply it. And the field keyword (C# 14) removes the last reason to declare a backing field by hand:

// before C# 14
private string _message = "";
public string Message
{
    get => _message;
    set => _message = value ?? throw new ArgumentNullException(nameof(value));
}

// C# 14: the compiler synthesises the backing field; 'field' refers to it
public string Message
{
    get;                                    // auto-implemented getter over the same field
    set => field = value ?? throw new ArgumentNullException(nameof(value));
}

// lazy initialisation without a field declaration
public SqlConnection Connection => field ??= new SqlConnection(_connectionString);

// INotifyPropertyChanged without ceremony
public string DisplayName
{
    get;
    set { if (field == value) return; field = value; OnPropertyChanged(); }
}

The catch to name before they ask: field is a contextual keyword, so a type that already has a member or local called field changes meaning when you move to C# 14. Inside a property accessor, bare field now binds to the synthesised backing field, not to your symbol. Disambiguate with @field or this.field, or — better — rename the offending symbol. This is one of the few genuinely source-breaking changes in the release, and the compiler emits a warning where it can detect the shadowing.

Constructors: the order nobody remembers

Ask a candidate what runs first and you separate the levels immediately. For new Derived() where Derived : Base:

  1. Derived's field initializers, in source order.
  2. The base constructor chain: Base's field initializers, then Base's constructor body — and this repeats all the way up to object.
  3. Derived's constructor body.
  4. Then, and only then, the object initializer's assignments (new Derived { X = 1 } is a constructor call followed by property sets).

Derived field initializers running before the base constructor is the surprise, and it produces the most infamous bug in the language: a virtual method called from a base constructor executes the derived override against a not-yet-initialised derived object. All the derived readonly fields are still null or zero. There is no language protection; the analyzer CA2214 flags it, and the design answer is that a constructor must not call virtual members — do the work in an initialisation method the caller invokes, or use a factory.

abstract class Base
{
    protected Base() => Describe();          // CA2214: virtual call in a constructor
    protected abstract void Describe();
}

sealed class Derived : Base
{
    private readonly string _name = "set";   // runs BEFORE Base's ctor body... no:
    protected override void Describe() => Console.WriteLine(_name.Length); // NullReferenceException
}
// _name's initializer runs first, but only for fields declared in Derived and only
// *before* the base call - which is exactly the code path an explicit `: base(...)`
// argument list can also observe. Any *constructor body* work in Derived has not run.

Primary constructors (C# 12 for classes and structs; C# 9 already had them for records) put the parameter list on the type declaration and make those parameters in scope for the whole body. For a record they generate public properties; for a class or struct they do not — they are captured into private fields only if used, and that difference is a favourite trick question. They are excellent for dependency injection, where the constructor exists only to store services, and they compose with the primary constructor of a base type via : base(x).

// C# 12 primary constructor on a class: no property is generated, no field unless captured
public sealed class OrderService(IOrderRepository repo, ILogger<OrderService> log)
{
    public async Task<Order?> GetAsync(int id, CancellationToken ct)
    {
        log.LogDebug("loading {Id}", id);          // 'log' captured into a private field
        return await repo.FindAsync(id, ct);
    }
}

// records DO generate public properties from their primary constructor
public record class OrderDto(int Id, string Customer);   // Id and Customer are public { get; init; }

const versus static readonly: a versioning question, not a syntax one

This is the highest-value item in this unit for a lead role, because it is about shipping. A const is inlined into every assembly that consumes it at their compile time. Ship version 2 of your library with const int MaxRetries = 5 changed to 10, and every caller that was not recompiled still uses 5 — silently, with no version conflict, no error. A static readonly is a field read at runtime, so callers pick up the new value on the next deploy of your DLL alone. Use const only for things that are true forever (mathematical constants, protocol magic numbers, zero, empty string) and static readonly for everything that is merely true today. The same reasoning applies to default parameter values and enum members, which are also baked into the caller.

Static constructors deserve one line of their own: a type with an explicit static constructor loses the beforefieldinit flag, which forbids the runtime from initialising the type eagerly and forces a check before every static member access. Partial members, and why they keep growing

partial started as a designer-file trick and has become the interface between hand-written code and source generators (unit 12). C# 9 added partial methods with return values and accessibility; C# 13 added partial properties and indexers; C# 14 added partial constructors and events. The pattern is always the same: you write a defining declaration with no body, a generator (or another file) supplies the implementing one. That is how [LoggerMessage], [GeneratedRegex], [JsonSerializable] and the LibraryImport source generator work, and why partial now appears on types you would never have expected.

Interview trap

Changing a public const in a shipped library. The candidate says "it's just a value change, it's not breaking" — and it is one of the nastiest breaking changes there is, because nothing fails. The old value keeps flowing through every un-recompiled consumer, so a timeout, a retry count, or a version string silently disagrees between two assemblies in the same process. The second half of the trap is the enum: adding a member is fine, reordering or renumbering is a silent break for anything persisted or compiled against the old numbering. If you take one rule away: in a public API, const means "this value is part of the contract forever".

Gotcha

Object initializers run after the constructor, so a constructor cannot validate anything an initializer will set. new Person("Ada") { Age = -1 } passes any check the constructor did. That is precisely the hole required plus init plugs — required forces the caller to set it, init stops it changing afterwards — and it is why validation for initializer-set properties belongs in the init accessor, not the constructor.

Try it — watch initialization order

Exercise 1. Write a Base whose constructor calls an abstract Init(), and a Derived that overrides Init() to print the length of a readonly string _name = "hello"; field. Run it. Then move the print into a method called after construction.

Exercise 2. Make a class library with public const int Retries = 3; and a console app referencing it. Build both. Change the library to 7, rebuild only the library, drop the new DLL next to the app, and run the app without rebuilding it. Then repeat with public static readonly int Retries = 3;.

Expected outcome

1. NullReferenceException: the derived field initializer has run but the derived constructor body has not, and more importantly the whole derived object is only partially built while the base constructor is executing. Calling the virtual method after construction prints 5. This is the reason CA2214 exists and the reason initialisation that needs polymorphism belongs in a factory method, not a constructor.

2. The const app still prints 3 — the value was copied into the app's IL at its compile time and the new DLL is irrelevant. The static readonly app prints 7. Nothing warns, nothing versions, nothing fails: it is the cleanest possible demonstration of why const in a public API is a contract, not a value.

Interview Q&A · members and construction

What exactly does a primary constructor generate on a class, and how is it different on a record?

On a record, the primary constructor parameters become public init-only properties, and they participate in the generated equality, ToString and Deconstruct. On a class or struct (C# 12) they generate nothing public at all: the parameters are just in scope for the whole type body, and the compiler creates a private capture field only for the ones you actually use — if a parameter is only used in a field initializer or passed to base(), no field is created. That is a genuine difference people trip on: class Point(int x, int y) does not give you p.X. I use class primary constructors mainly for dependency injection, where the constructor's whole job was assigning services to readonly fields, and I avoid them where I need validation, because there is nowhere to put it except a field initializer or an explicit secondary constructor chaining with this(...).

Walk me through the initialization order for new Derived { X = 1 }.

Derived field initializers run first, in source order. Then control transfers up the base chain — base field initializers, base constructor body — repeating to object. Then the derived constructor body runs. Then the object initializer's property assignments happen, as ordinary setter calls after the object already exists. Two consequences matter in practice. First, a virtual call from a base constructor lands in the derived override while the derived constructor body has not run, so anything it depends on may be uninitialised — this is a real production bug class, not a puzzle. Second, a constructor cannot validate values that an object initializer will assign afterwards, which is why required plus validation inside an init accessor is the modern way to enforce invariants on initializer-built objects.

When would you use const and when static readonly?

const only for values that are conceptually eternal and cheap to inline — Math.PI-style constants, a protocol version byte, an empty string, array index sentinels. Everything else is static readonly. The reason is versioning: a const is copied into the IL of every consuming assembly at their compile time, so changing it in your library has no effect on anyone who does not recompile. In a plugin architecture or a large solution with mixed build times that produces two different values for the same "constant" inside one process, with nothing to diagnose it. static readonly is a field read at runtime, so the new value ships with the DLL. The same trap applies to default parameter values and to enum member numbering, both of which are also baked into callers.

What is beforefieldinit and why should you care?

It is a metadata flag the compiler puts on a type that has static fields with initializers but no explicit static constructor. It tells the runtime "you may initialise this type at any point before the first static field access", which lets the JIT hoist or elide the initialisation check entirely. Writing an explicit static Foo() { } removes the flag and forces a check before every static member access, and while that check is very cheap, in a tight loop it can be measurable. The bigger reason to care is failure behaviour: a static constructor that throws poisons the type for the life of the process — every subsequent access gets TypeInitializationException wrapping the original, and it is famously hard to diagnose because the stack trace points at innocent code. So I keep static constructors trivial, and anything that can fail — configuration, I/O, environment probing — goes behind a Lazy<T> or an explicit init call I control.

What problem does the field keyword solve, and what does it break?

It removes the mechanical backing field. Any time you needed one accessor to do a little work — validate, trim, lazily initialise, raise PropertyChanged — you had to declare a private field, and now the private field is visible to the rest of the type, so nothing stops another method from bypassing your validation by writing to it directly. field (C# 14) gives you a compiler-synthesised field that only the accessors can see, and it lets you write one custom accessor while the other stays auto-implemented. What it breaks: field is contextual, so inside a property accessor it now shadows any member or local you happen to have named field. That is a real source-breaking change on upgrade; the fix is @field, this.field, or renaming. In review I now treat a hand-declared backing field as a smell in new C# 14 code.

Why is turning a public field into a property a breaking change?

Source-compatible, binary-incompatible. A field access compiles to ldfld; a property access compiles to a call. Existing compiled callers still emit ldfld against a member that no longer exists, so they get a MissingFieldException at runtime. There are second-order breaks too: a field can be passed by ref or out and a property cannot, so some call sites will not even recompile; and reflection code, serializers and data binding that look for fields will stop finding it. This is why the very first rule of .NET API design is "never expose public fields" — you are not protecting encapsulation in the abstract, you are protecting your ability to add behaviour later without a major version bump.

What are partial members for now that we have source generators?

They are the handshake. A source generator cannot edit your file, so the pattern is: you declare the shape — partial void, partial property, and since C# 14 partial constructors and events — decorate it with an attribute, and the generator emits the implementing declaration in its own file. That is exactly how [LoggerMessage], [GeneratedRegex], [JsonSerializable] and [LibraryImport] work, and it is why those APIs all require partial. The benefit over reflection-based equivalents is enormous for trimming and native AOT: the code exists at compile time, so the linker can see it, and there is no runtime IL emit. The rule for partial constructors and events specifically is that there is exactly one defining and one implementing declaration, only the implementing one may have a this()/base() initializer, and a partial event's implementing declaration must supply add/remove.

How do you enforce an invariant on a type that is built with object initializers?

Put the check in the init accessor, not the constructor, because initializers run after the constructor has already finished. Combine that with required so the caller cannot omit the member, and the pair gives you compile-time "you must set it" plus runtime "and it must be valid". If the invariant spans multiple properties — a date range where start must precede end — no accessor can validate it in isolation, so I either move to a constructor and drop the initializer style, or add an explicit factory (DateRange.Create(start, end) returning a result) and make the constructor private. The anti-pattern I reject is a public Validate() the caller is supposed to remember to call: an invariant nobody enforces is documentation, not a constraint.

What is a user-defined compound assignment operator and why did C# 14 add it?

Until C# 14, writing operator + was enough to make x += y work, but it worked by expansion: x = x + y, which allocates a whole new instance and throws the old one away. For large mutable values — a big matrix, a builder, an arbitrary-precision number — that is exactly wrong; you want to add in place. C# 14 lets a type declare the compound operator itself (public void operator +=(T other)), so x += y mutates the receiver instead of rebuilding it. It matters most for high-performance numeric and buffer types, and it pairs with generic math (unit 04) where a generic algorithm written with += can now be efficient for both a small int and a large BigInteger-shaped type. In review, the thing to watch is consistency: if += mutates but + returns a new value, a shared instance can be mutated out from under another reference, so this belongs on types you control end to end.

Indexers, operators, conversions — where do you draw the line on operator overloading?

My rule is that an operator must be obvious, total, and cheap. Obvious: + on Money or a vector is clear; + meaning "add to a repository" is a puzzle. Total: it must be defined for all inputs of those types or throw a documented exception — an operator that returns a nonsense value for some inputs is worse than a method, because nobody expects to null-check an addition. Cheap: an operator that does I/O or takes a lock violates every reader's expectation. Implicit conversions get the strictest treatment: they must be lossless and non-throwing, because they fire silently in overload resolution, and a throwing implicit conversion produces exceptions from lines that contain no visible call. When in doubt I write a named method — Money.Add, ToDecimal() — because a name is searchable and an operator is not.

04 Generics and generic math

Docs: Generics · Generic math

C# generics are reified, and that one word is the whole unit. Unlike Java, the type arguments survive into the runtime: typeof(List<int>) != typeof(List<string>), you can ask a List<T> what T is at runtime, and there is no erasure and no hidden casting. The practical payoff is performance. For a value-type argument the JIT compiles a separate native body with T substituted, so List<int> stores raw ints inline and comparing them calls Int32.Equals directly with no boxing. For reference-type arguments all instantiations share one canonical body — a pointer is a pointer — so List<string> and List<Order> reuse the same machine code. Everything else in this unit is a consequence of those two facts.

Constraints are how you get behaviour out of a type parameter

Inside an unconstrained generic method, T is essentially object: you can assign it, compare with EqualityComparer<T>.Default, and little else. Constraints buy back capability, and each one also changes what the JIT can do:

Variance: why IEnumerable<string> is an IEnumerable<object> and List<string> is not

Variance (C# 4) is declared, not inferred, and only on interfaces and delegates. out T (covariant) means T appears only in output positions, so it is safe to widen: an IEnumerable<string> can be read as IEnumerable<object> because everything it hands you is a string, and a string is an object. in T (contravariant) means T appears only in input positions, so it is safe to narrow: an IComparer<object> can be used as an IComparer<string>, because anything that can compare objects can compare strings. List<T> has T in both positions — Add(T) and this[int] — so it is invariant, and must be, or you could Add an int to a List<string> through an List<object> reference.

Which brings up the famous hole: arrays are covariant and it is unsound. string[] is assignable to object[] — a .NET 1.0 decision made before generics existed, to let sort routines work — and the price is a runtime type check on every array store. Write an int into an object[] that is really a string[] and you get ArrayTypeMismatchException at runtime rather than a compile error, and every single array element assignment in your program pays a covariance check unless the JIT can prove the exact type.

object[] objects = new string[2];       // legal: arrays are covariant
// objects[0] = 42;                     // compiles, throws ArrayTypeMismatchException at runtime

IEnumerable<object> items = new List<string>();   // legal: IEnumerable<out T>
// IList<object> list = new List<string>();       // rejected: IList<T> is invariant

IComparer<object> anyComparer = Comparer<object>.Default;
IComparer<string> forStrings = anyComparer;       // legal: IComparer<in T>

// variance is reference-conversion only - never for value types:
// IEnumerable<object> nope = new List<int>();     // rejected: would require boxing each element

That last comment is a favourite follow-up: variance requires an identity-preserving reference conversion, so IEnumerable<int> is never an IEnumerable<object>. If it were, reading an element would have to box, which is not a conversion the CLR can do implicitly through a shared code path.

Static abstract members and generic math (C# 11)

For twenty years you could not write T Sum<T>(T[] xs) because + is a static member and nothing in the constraint system could demand one. The workarounds were awful — dynamic, an IArithmetic<T> strategy object, or expression trees compiled at runtime. C# 11 allowed static abstract (and static virtual) members in interfaces, and the BCL immediately shipped a hierarchy of them: INumber<T>, IAdditionOperators<TSelf, TOther, TResult>, IParsable<T>, ISpanFormattable, and so on, all of which every primitive numeric type implements.

using System.Numerics;

// works for int, long, double, decimal, Half, Int128, BigInteger, and your own types
static T Sum<T>(ReadOnlySpan<T> values) where T : INumber<T>
{
    T total = T.Zero;                          // a static abstract property
    foreach (var v in values) total += v;      // a static abstract operator
    return total;
}

// the same pattern for parsing - no reflection, no dynamic
static T ParseAll<T>(string text) where T : IParsable<T>
    => T.Parse(text, CultureInfo.InvariantCulture);

// and the pattern that makes it work: the type names itself in its own constraint
public interface IShape<TSelf> where TSelf : IShape<TSelf>
{
    static abstract TSelf Empty { get; }
    static abstract TSelf operator +(TSelf a, TSelf b);
}

Two caveats worth having ready. First, static abstract members are resolved through the type argument, so they need a generic context — you cannot call IShape.Empty on an interface reference, only T.Empty inside a generic. Second, this is the mechanism that makes vectorised BCL code possible, and it is why .NET's Enumerable.Sum got dramatically faster in .NET 9: the implementation can now write one algorithm and specialise per numeric type.

Statics, and the thing everyone gets wrong

A static field in a generic type is per closed constructed type. Cache<int>.Instance and Cache<string>.Instance are two different fields with two different lifetimes. This is genuinely useful — it is the standard trick for per-type caches, and it is how EqualityComparer<T>.Default is implemented, with the JIT devirtualising the comparer for sealed and value types — but it also means a generic type with an expensive static initializer pays that cost once per type argument, and a generic type with a static Dictionary keeps one dictionary per instantiation alive for the life of the AppDomain.

Interview trap

"Generics in C# work like Java's." They do not, and the interviewer is checking whether you know why it matters. Java erases: List<Integer> is a List of boxed Integer objects at runtime, you cannot ask for T, and you cannot have new T[]. C# reifies: List<int> stores 4-byte ints contiguously with no boxes, typeof(T) works, new T[n] works, and the JIT generates specialised machine code per value-type argument. The costs of reification are real too — code size grows with the number of distinct value-type instantiations, and generic virtual methods force runtime dictionary lookups that resist inlining and are a known pain point for native AOT. Knowing both sides is the senior answer.

Gotcha

Type inference works on arguments, never on the return type. T Parse<T>(string s) cannot be called as var x = Parse("1"); — you must write Parse<int>("1"). This drives a design idiom: put the inferable thing in the parameters (bool TryParse<T>(string s, out T value)) or accept explicit type arguments. It also explains why so many fluent APIs take a lambda: Select<TSource, TResult> infers TResult from the delegate's return type, which is an argument.

Try it — prove reification and measure it

Exercise 1. Write two methods that sum an array of ints a million times: one taking IComparable[]/object[] and casting, one generic with where T : INumber<T>. Run both under a memory profiler or just print GC.GetAllocatedBytesForCurrentThread() before and after.

Exercise 2. Give a generic class a static int Counter and a static constructor that prints. Instantiate Box<int>, Box<long> and Box<string>, incrementing Counter each time, then print all three.

Expected outcome

1. The object[] version allocates roughly 24 bytes per element per pass — that is the box — and runs several times slower; the generic version allocates zero and the JIT will typically inline the addition entirely. That gap is the single clearest demonstration of why the BCL was rewritten around generics, and why a generic constraint beats an interface parameter for value types.

2. The static constructor prints three times, and each counter reads 1. Static state in a generic type is per closed type, not per generic definition. Useful for per-type caches; a memory leak if you instantiate over many types (for example one per message type in a dispatcher) and keep unbounded state in there.

Interview Q&A · generics

How does the runtime implement generics, and what does that cost?

Reification with selective code sharing. For each distinct value-type argument the JIT produces a specialised native body with the type substituted, so there is no boxing and layouts are exact — List<int> genuinely stores ints inline. All reference-type arguments share one canonical body, because every reference is one machine word; the runtime passes a hidden type handle where the code needs to know the actual type. The costs are code size — many value-type instantiations means many compiled bodies, which matters for startup and for AOT image size — and generic virtual methods, which need a runtime dictionary lookup to resolve, resist inlining, and are the main reason some generic-heavy code is slower under native AOT than you would expect. In exchange you get typeof(T) at runtime, real arrays of T, and no hidden casts.

Why is List<string> not assignable to List<object>, when string[] is assignable to object[]?

Because List<T> uses T in both input and output positions, so widening it would let you Add an int through the object view and corrupt the list — the compiler forbids it, which is correct. Arrays got covariance in .NET 1.0 before generics existed, so that a single Sort(object[]) could handle any array, and the CLR pays for that decision with a type check on every array element store: writing the wrong type throws ArrayTypeMismatchException at runtime instead of failing to compile. It is widely acknowledged as a design mistake, and it is the reason IEnumerable<out T> exists — safe covariance where the type parameter genuinely only comes out.

When would you declare an interface covariant or contravariant in your own code?

Whenever the type parameter genuinely appears in only one direction, because it costs nothing and makes the API compose. A read-only repository or a producer — IProducer<out T> — should be covariant so an IProducer<Order> can satisfy a parameter of IProducer<IEntity>. A handler, validator or comparer that only consumes — IHandler<in TMessage> — should be contravariant so a general handler can be used where a specific one is expected. The constraint is mechanical: out means the parameter may not appear as a method parameter type, and in means it may not appear as a return type, with some subtleties around ref/out parameters (which are neither, so they block both). The one thing to remember is that variance only applies to reference conversions, so it never helps for value-type arguments.

Explain static abstract interface members and what they unlocked.

C# 11 let an interface declare static abstract members — including operators, Parse, and constants like Zero — which a type implements statically, and which generic code can invoke through the type parameter as T.Zero or a + b. That closed a twenty-year hole: you could not write a generic Sum because operator + is static and constraints could only demand instance members. The BCL shipped the whole numeric tower on top of it, INumber<T> and friends, so one algorithm now covers int, double, decimal, Half, Int128 and BigInteger, and the JIT specialises each. Beyond arithmetic, it is the clean way to express factories and parsing — where T : IParsable<T> replaces the reflection-based Activator/TypeConverter dance and is trim- and AOT-friendly. The pattern that makes it work is self-referential: interface IFoo<TSelf> where TSelf : IFoo<TSelf>.

What does where T : allows ref struct mean and why is it unusual?

It is an anti-constraint: instead of narrowing what T may be, it widens it, permitting Span<T> and other ref struct types as generic arguments — which had been forbidden since spans were introduced, because a ref struct must never reach the heap and generic code could not previously promise that. C# 13 added it, and in exchange the compiler applies ref struct safety rules inside the generic body: you cannot box T, cannot store it in a field of a class, cannot use it across an await or yield. In practice it is what finally lets library authors write span-friendly generic helpers — delegates like Func<T, bool> gained the annotation, and Enumerable-shaped utilities can now be written once for both arrays and spans instead of being duplicated.

Static fields in a generic class — what is the scope?

Per closed constructed type. Cache<int> and Cache<string> have entirely separate copies of every static field and each runs its own static constructor. That is the intended design and it is genuinely useful — it is how per-type caches, per-type serializer metadata and EqualityComparer<T>.Default are built, all initialised once and then devirtualised by the JIT. The failure mode is unbounded instantiation: a generic dispatcher with a static dictionary, instantiated over a hundred message types, is a hundred dictionaries that live until process exit, and they are invisible in most memory tooling because nothing "leaks" — the roots are static. In review I look for static mutable state in generic types the same way I look for it anywhere else, but with the extra question "how many closed types will this become?".

Why can't C# infer type arguments from the return type?

Because inference runs over the argument list before the assignment context is known, and allowing return-type inference would make overload resolution circular in the general case — the target type can depend on which overload is chosen, which would depend on the target type. The language does have a narrow form of target-typing (new() target-typed expressions in C# 9, conditional and switch expressions), but not full return-type inference. The practical consequence is a design idiom you see everywhere in the BCL: anything you want inferred must appear in the parameters. That is why TryParse uses an out parameter, why LINQ's Select infers its result from the lambda, and why factory helpers take a sample or a delegate rather than returning a bare T.

What does nameof with unbound generics give you in C# 14?

nameof(List<>) now evaluates to "List". Before C# 14 you had to close the type — nameof(List<int>) — which meant inventing an irrelevant type argument purely to get a name, and that reads as noise and occasionally as a real coupling. It matters most in diagnostics, analyzers, logging and reflection-adjacent code where you want a compile-time-checked name for a generic type definition. It is a small feature, but it removes a category of magic strings, and the general principle is worth stating: every time you can replace a string literal with nameof, you buy rename-safety for free.

Are there cases where you would avoid generics for performance?

Yes, two. First, generic virtual methods and generic interface dispatch on value types require runtime generic dictionary lookups the JIT struggles to inline; in a hot loop, a non-generic specialised method, or a struct-typed strategy passed as a constrained generic parameter (where TComparer : IComparer<T>, passed as a struct so the call is devirtualised), beats a generic virtual call by a large margin. That struct-generic-strategy pattern is used heavily inside the BCL itself. Second, code size: a generic method instantiated over dozens of value types compiles dozens of bodies, which hurts startup, instruction cache behaviour and native AOT image size. In both cases the answer is measurement, not doctrine — but "generics are always free" is not a claim I would make in an interview.

How would you design a generic API so that it stays usable in ten years?

Keep the type parameters few and meaningful — anything past two and callers start needing explicit arguments because inference gives up, which is a usability cliff. Constrain honestly: where T : notnull on keys, where T : class only if you truly need reference semantics, and never add a constraint you do not use, because adding one later is a breaking change while removing one is not. Prefer interfaces over base classes as constraints so implementers are not forced into your hierarchy. Avoid new() where a factory delegate would do, because new() forces a public parameterless constructor onto everyone and historically went through Activator. And think about variance up front: adding out or in to an existing interface is source-compatible but can change overload resolution in callers, so it is safer to get it right the first time.

05 Interfaces and inheritance

Docs: Interfaces · The closed modifier

The interview question is never "what is an interface". It is "when do you reach for an interface, when for an abstract base, and when for neither" — and the tell is whether you talk about versioning. An interface is a contract you promise not to change; a base class is an implementation you promise to keep compatible. Both are commitments, and inheritance is the more expensive one because it exposes your internal structure to people who will depend on it.

Interface versus abstract class, honestly

The textbook answer ("a class can implement many interfaces but inherit one base") is true and boring. The useful framing is: an interface describes a role the type can play — IDisposable, IComparable<T>, IValidator<T> — and a type can play many roles. A base class describes what the type is, and it brings state, constructors, and a fixed initialisation order with it. Since C# 8's default interface members the capability gap narrowed, but three differences remain and they are the ones to name: an interface cannot hold instance state; an interface cannot have a constructor, so it cannot enforce an invariant at construction; and a class can only pick one base, so a base class spends your one inheritance slot forever.

Default interface members: what they are actually for

C# 8 (2019) allowed an interface member to have a body. Everyone read that as "multiple inheritance is here"; it is not. It exists so a library author can add a member to a published interface without breaking every implementer. That is a versioning tool, and the design reflects it: a default implementation is not inherited into the implementing class's member set. If ILogger has a default LogInfo(string) and MyLogger implements ILogger, then new MyLogger().LogInfo(…) does not compile — you must call it through the interface, ((ILogger)logger).LogInfo(…). That surprises people every time, and it is deliberate: the member belongs to the interface, not to the class.

public interface IAuditable
{
    string Describe();

    // added in v2 - existing implementers keep compiling
    string DescribeShort() => Describe().Length <= 40 ? Describe() : Describe()[..40] + "…";
}

public sealed class Payment : IAuditable
{
    public string Describe() => "payment";
}

var p = new Payment();
// p.DescribeShort();                 // does NOT compile: not a member of Payment
((IAuditable)p).DescribeShort();      // fine

Diamond resolution is the second half. If two interfaces both provide a default for the same signature, the compiler requires the implementing type to disambiguate by providing its own implementation — there is no "most derived wins" guessing. And an interface may declare static members, including static abstract (unit 04) and private/protected helpers, so the default body can be non-trivial without leaking helpers into the public surface.

Explicit implementation, and the two reasons to use it

Writing void IDisposable.Dispose() instead of public void Dispose() hides the member from the class's public surface; it is reachable only through the interface. Two legitimate reasons. First, name collisions: implementing both IEnumerable and IEnumerable<T> requires two GetEnumerator methods with the same signature, so the non-generic one is always explicit. Second, deliberately discouraging a member: List<T> implements IList.Add(object) explicitly so the type-unsafe overload does not clutter or tempt. The cost is that explicit implementation on a struct forces boxing when called through the interface, and that it is invisible to anyone reading the class, so use it sparingly and never as a substitute for a good name.

virtual, override, new, and the shadowing trap

C# made overriding opt-in — members are non-virtual by default, unlike Java — precisely because a virtual member is a public extension point you must support forever. new (method hiding) is the escape hatch when a base class later introduces a member with your name, and it is almost always a bug when written deliberately: dispatch then depends on the static type of the reference, so the same object behaves differently through a base-typed variable. That non-polymorphism is the classic interview demo:

class Base   { public virtual string Who() => "Base";  public string Tag() => "base-tag"; }
class Child : Base
{
    public override string Who() => "Child";          // polymorphic
    public new    string Tag() => "child-tag";        // hides - NOT polymorphic
}

Base b = new Child();
Console.WriteLine(b.Who());   // "Child"      - runtime type decides
Console.WriteLine(b.Tag());   // "base-tag"   - compile-time type decides

sealed is the other side. Sealing a class or an override lets the JIT devirtualise calls — turning an indirect call into a direct, often inlinable one — and it removes an extension point you would otherwise owe support for. The BCL seals aggressively. A pragmatic rule for application code: seal classes by default (there is an analyzer, CA1852, that will do it for you), and unseal deliberately when you decide to support derivation.

The fragile base class problem, and closed in C# 15

Inheritance couples you to the base class's internal call graph, not just its signatures. If Base.AddRange is implemented by calling Add in a loop, and you override Add to count items, your count is right — until version 2 of the base class optimises AddRange to bulk-copy, and your counter silently stops working. Nothing broke at compile time; nothing threw. That is the fragile base class problem, and it is the strongest argument for composition: a field you delegate to has an interface contract, not an implementation you are entangled with.

C# 15 adds a genuinely new tool here: the closed modifier. A closed class can only be derived from within its declaring assembly, so the compiler knows the complete set of direct descendants at compile time and a switch over them is exhaustive with no default arm. That is the missing piece for modelling a finite set of states as a type hierarchy — the thing F# has had as discriminated unions forever.

// C# 15 (preview at the time of writing; .NET 11, GA expected November 2026)
public closed record class GateState;                      // implicitly abstract
public record class Closed : GateState;
public record class Open(float Percent) : GateState;

string Describe(GateState state) => state switch
{
    Closed        => "closed",
    Open(var pct) => $"{pct}% open",
    // no default arm needed, and no CS8509 warning: the compiler knows the set is complete
};

Two rules to state precisely: a closed class is implicitly abstract and cannot combine with sealed, static or an explicit abstract; and closure is not transitive — a non-closed descendant of a closed class can still be derived from elsewhere, so to get exhaustiveness all the way down you mark the intermediate levels closed too. Add a new descendant later and every non-exhaustive switch in your assembly lights up as a warning, which is exactly the refactoring safety net the pattern is for.

Interview trap

"Adding a method to an interface is fine, it's just a source change." In a library it is a breaking change for every external implementer — their type no longer satisfies the interface and will not compile, and if they are shipping a compiled assembly it fails at load or on first dispatch. This is why IEnumerable<T> has had two members since 2005 and why every extension to LINQ arrived as an extension method rather than an interface member. Since C# 8 you have one more option, a default implementation, which keeps existing implementers compiling — but it does not make the change free: implementers who wanted to know now silently inherit behaviour they never reviewed. The honest lead answer is: prefer small interfaces, add capability through new interfaces (IAsyncDisposable beside IDisposable) or extension methods, and reserve default members for genuine emergency versioning.

Gotcha

An interface with a default implementation is still not multiple inheritance, because there is no state. The moment your default body needs a field, you are stuck — the workarounds (a static ConditionalWeakTable keyed on this, or an abstract property the implementer must supply) are both worse than an abstract base class. And a default member changes overload resolution: if a class has its own Log(object) and the interface adds a default Log(string), calls through the interface and calls through the class can now pick different methods for the same argument.

Try it — break a subclass without touching it

Exercise 1. Build a CountingList that derives from a SimpleList whose AddRange loops calling the virtual Add. Override Add to increment a counter. Verify the count is right. Now change SimpleList.AddRange to copy directly into its array without calling Add, and re-run the unchanged subclass.

Exercise 2. Write an interface with a default method, implement it in a class, and try calling that method on the class-typed variable. Then add a second interface with the same default signature and implement both.

Expected outcome

1. The count silently drops to zero. Nothing failed to compile, nothing threw, and a test that only checks the list contents still passes. That is the fragile base class problem in nine lines, and it is why "prefer composition over inheritance" is a real engineering rule rather than a slogan: a CountingList that wraps a list and implements the same interface cannot be broken this way.

2. The class-typed call does not compile — a default member is a member of the interface, not of the implementing type — and you must cast. With two interfaces providing the same default, the compiler reports an ambiguity and forces the class to supply its own implementation; there is no silent "closest wins". Both behaviours are deliberate, and both are the reason default members are a versioning tool rather than a mixin mechanism.

Interview Q&A · interfaces and inheritance

Interface or abstract base class — how do you actually decide?

I ask three questions. Does the type need shared state or a constructor that enforces an invariant? Then a base class, because an interface can do neither. Will more than one unrelated hierarchy need to play this role? Then an interface, because inheritance is a single slot and spending it is permanent. Is this a seam for testing, mocking or plugging in an alternative implementation? Then an interface, always, and a small one. In practice most of my abstractions end up as narrow interfaces plus a concrete helper class that implementers may use by composition rather than must inherit — that gives reuse without the coupling. The template-method base class still has a place, but only when I own every subclass in the same assembly, where I can change the base and the subclasses together.

Why were default interface members added, and why can't you call them on the class?

They were added for API versioning: before C# 8, adding a member to a shipped interface broke every implementer, so interfaces effectively froze on release and every extension had to be an extension method. A default body lets you add a member with a sensible fallback, so existing implementers keep compiling. The reason you cannot call it on the class is that the member is not inherited into the class's member set — it stays a member of the interface, reached through an interface reference. If it were inherited, adding a default member could silently change overload resolution inside every implementing class, which would turn a "safe" versioning move into a source break. The same reasoning drives diamond resolution: with two conflicting defaults, the compiler forces the class to choose rather than picking one.

What is the fragile base class problem and how do you avoid it?

Inheritance exposes not just the base class's public contract but its internal call graph, so a subclass can depend on which base method calls which. Refactor the base — make AddRange bulk-copy instead of looping over the virtual Add — and every subclass that overrode Add to observe insertions silently stops working, with no compile error and often no failing test. I avoid it three ways: seal by default and open derivation deliberately; when I do open it, document precisely which members are called by which, because that is now part of my contract; and prefer composition, where the wrapper depends only on the published interface. The one place I accept a deep inheritance chain is a framework I own end to end and version atomically.

What does sealed buy you beyond design intent?

Devirtualisation. A call to a virtual member on a sealed type — or to a sealed override — has exactly one possible target, so the JIT can turn the indirect call into a direct one and then inline it, which in a hot loop is the difference between a few nanoseconds and a fraction of one. .NET's dynamic PGO can often work this out for unsealed types too by profiling the actual types seen and emitting a guarded devirtualised fast path, but sealed makes it unconditional and free. Beyond speed, sealing is a support decision: an unsealed public class is an extension point you have promised to keep working, which constrains every future refactor. My default in application code is sealed, enforced by analyzer CA1852, and I unseal when there is a named reason.

Explain new method hiding and when it is legitimate.

It declares a member that shadows a base member of the same name without overriding it, so dispatch is decided by the compile-time type of the reference: the same object returns different results through a base-typed variable and a derived-typed one. That is almost always a bug when it is intentional, because polymorphism is the reason the hierarchy exists. The legitimate case is defensive and reactive: a base class you do not control adds a member whose name collides with yours, and new lets you keep compiling without renaming your public API. C# requires the keyword rather than allowing silent shadowing precisely so this stays a conscious act — omit it and you get warning CS0108. The other semi-legitimate use is covariant-style narrowing of a return type before C# 9 made covariant returns a real feature, and that is now obsolete.

What does the closed modifier in C# 15 give you that sealed and abstract classes did not?

Compile-time knowledge of the complete set of direct descendants, which turns pattern matching over a hierarchy into an exhaustiveness check. Before it, a switch over an abstract base always needed a default arm or produced CS8509, because someone in another assembly might add a case — so you either wrote a throwing default that only fires in production, or you used an enum plus a cast and lost type safety. With closed, derivation is restricted to the declaring assembly, the compiler can prove the switch covers every case, and adding a new descendant later turns every incomplete switch into a warning at build time. That last part is the real value: it is a refactoring safety net for state machines, result types and domain events. Two rules to remember: a closed class is implicitly abstract and cannot also be sealed or static, and the closure is not transitive, so intermediate descendants need their own closed to keep exhaustiveness going down the tree.

How do you version an interface in a public library?

Ideally I do not — I design them small enough that they do not need to grow, following the interface segregation idea, and I add capability as a new interface that a type can additionally implement. That is exactly what the BCL did with IAsyncDisposable next to IDisposable, and with IAsyncEnumerable<T> next to IEnumerable<T>: consumers test with is and take the better path when available. When a member genuinely must be added to an existing interface, a default implementation is the tool, and I pair it with a clear release note, because implementers who should have reviewed the new behaviour now inherit it silently. What I avoid is the middle ground of adding an abstract member and calling it a minor release — that is a compile break for every external implementer, and there is no way to soften it.

When is explicit interface implementation the right call?

Two cases. When two interfaces demand the same signature and you need different behaviour, or when the same name has to exist twice — implementing both IEnumerable and IEnumerable<T> forces the non-generic GetEnumerator to be explicit. And when a member is required by a contract but is a bad member of the public surface: List<T> implements the non-generic, unsafe IList.Add(object) explicitly so it does not appear on the type and tempt callers. What I do not use it for is fake encapsulation — hiding a method with an explicit implementation does not make it private, it just makes it harder to find, and a one-line cast defeats it. One performance note: calling an explicitly implemented member on a struct through the interface boxes, which matters if the type is meant to be allocation-free.

Access modifiers: what are internal, protected internal, private protected and file?

internal is assembly-scoped — the workhorse for anything you want shared across your own code but not part of the public contract, and it pairs with InternalsVisibleTo for test projects, though I prefer testing through the public surface where I can. protected internal is the union: derived classes anywhere or anything in this assembly. private protected (C# 7.2) is the intersection: derived classes, but only those in this assembly — which is the correct modifier for a member that supports your own subclasses without becoming a public extension point. file (C# 11) restricts a type to the single source file that declares it, and it exists mainly so source generators can emit helper types without any chance of colliding with a user's names. In review, the modifier I question most is public: every public member is a support commitment, and internal is very often the honest answer.

How would you refactor a deep inheritance hierarchy you inherited?

Incrementally and from the leaves. First I introduce interfaces at the seams the rest of the system actually consumes, so callers depend on a role rather than the base type — that alone lets me change the hierarchy without touching consumers. Then I move behaviour out of the base into injected collaborators, one responsibility at a time, replacing protected virtual hooks with composed strategies; each move is mechanical and testable. I seal the leaves as they stop being extended, which surfaces anything that was quietly deriving. Where the hierarchy is really modelling a closed set of states rather than an open set of behaviours — order statuses, result cases — I convert it to a closed hierarchy (C# 15) or a discriminated shape with pattern matching, because that turns "did I handle every case" from a code review question into a compiler warning. The thing I never do is a big-bang rewrite: the value is in each step being separately shippable.

06 Pattern matching and unions

Pattern matching arrived in C# 7 (2017) and has been extended in every release since. It is easy to treat as syntax sugar; it is not. The real shift is that the compiler builds a decision tree from your patterns, checks it for reachability and exhaustiveness, and tells you when a case is dead or missing. That is a type-system feature disguised as syntax, and it is why "can the compiler prove I handled every case?" is now a live design question rather than a wish.

Composition is the point. Each of these is a pattern, and patterns nest inside each other without limit, so a single expression can express a condition that used to be five nested ifs and two local variables:

// one expression: type check, null check, nested property, range, and a capture
static string Classify(object o) => o switch
{
    Order { Total: > 10_000, Customer.Country: "SE" or "NO" } o => $"nordic-large:{o.Id}",
    Order { Lines.Count: 0 }                                   => "empty",
    Order { Total: var t } when t < 0                           => "credit",
    Order                                                       => "standard",
    null                                                        => "none",
    _                                                           => "unknown",
};

// list patterns (C# 11): shape-match a sequence
static string Describe(int[] a) => a switch
{
    []                    => "empty",
    [var only]            => $"single {only}",
    [var first, .., var last] when first == last => "palindromic ends",
    [_, ..var middle, _]  => $"{middle.Length} in the middle",
};

Two details worth knowing precisely. Arms are tested in source order, so a broader pattern above a narrower one makes the narrower one unreachable — and the compiler tells you so (CS8510), which is one of the nicest safety properties of the feature. And when clauses are arbitrary code, so they are not part of the exhaustiveness analysis: a switch whose only non-default arms all carry when is never considered exhaustive, because the compiler cannot reason about your predicate.

Exhaustiveness: the warning that saves refactors

A switch expression must produce a value, so if no arm matches at runtime it throws SwitchExpressionException. The compiler warns (CS8509) when it cannot prove the arms are exhaustive. For an enum that warning is weaker than people assume: any int can be cast to any enum, so the compiler treats every enum switch as potentially incomplete unless you add a discard arm. For a sealed class hierarchy it could not prove anything at all before C# 15 — which is exactly the gap closed (unit 05) and union fill.

Union types (C# 15): the headline language feature of the next release

C# 15, shipping with .NET 11 in November 2026 and available in preview now, introduces union: a type whose value is exactly one of a declared set of case types. The compiler knows the complete set, so a switch over a non-null union is exhaustive without a discard arm, and the case types are ordinary types you already have — no wrapper class, no OneOf package, no object plus casts.

// C# 15 / .NET 11 preview
public record class Cat(string Name);
public record class Dog(string Name);
public record class Bird(string Name);

public union Pet(Cat, Dog, Bird);

Pet pet = new Dog("Rex");                 // implicit conversion from each case type

string name = pet switch
{
    Dog d  => d.Name,
    Cat c  => c.Name,
    Bird b => b.Name,
    // exhaustive: no default, no warning
};

This is the shape .NET has been missing for result-and-error modelling. Instead of a Result<T> class with a nullable Value, a nullable Error and a bool IsSuccess that nothing enforces, you declare the two cases and the compiler makes forgetting one a build error. Two honest caveats for interview: the runtime support types (UnionAttribute, IUnion) landed in .NET 11 Preview 5, some of the proposal is still unimplemented, and until .NET 11 GA this is a preview feature you would not put in production code. And a union is not free — it is a type with a discriminator, so it is not the same as a zero-cost tagged pointer.

Labeled break and continue (C# 15)

The other control-flow addition removes the last honest use of goto. Nested loops that need to abandon the outer one used to need a boolean flag checked at every level, or a jump past the loops. C# 15 lets break and continue name a label placed on an enclosing loop or switch:

outer: for (int row = 0; row < grid.Height; row++)
{
    for (int col = 0; col < grid.Width; col++)
    {
        if (grid[row, col].IsBlocked) continue outer;   // next row
        if (grid[row, col].IsGoal)    break outer;      // done entirely
    }
}

Unlabeled break/continue keep their meaning, and the analyzer IDE0410 flags the flag-variable and goto patterns this replaces. It is small, but it is the kind of detail that signals you are actually tracking the language.

What the compiler emits

Worth knowing because it comes up as "is a switch faster than if/else". For a dense set of integer or enum constants the compiler emits a jump table (switch IL) — O(1). For sparse constants it emits a binary search over ranges. For strings, above a handful of cases it computes a hash, switches on the hash, then does a string comparison to confirm — so a big string switch is close to a dictionary lookup, not a linear scan. For type patterns it emits a chain of type tests, but it hoists shared tests: matching three patterns that all start with Order tests Order once. The practical upshot is that a switch expression is at least as fast as the equivalent hand-written conditionals and usually faster, so readability wins with no trade-off.

Interview trap

Assuming an enum switch is exhaustive. (Status)999 is a perfectly legal Status — enums are just named integers with no runtime validation, and any int can be cast in, including a value that came from a database column or a deserialised payload. So a switch expression over an enum without a discard arm compiles with a warning and throws SwitchExpressionException in production the first time somebody adds a row. Always add the default arm for enums, and make it throw with the value in the message rather than returning a silent fallback. Related: Enum.IsDefined is the validation you actually want at the boundary, and it does not understand [Flags] combinations.

Gotcha

o is Order { Total: > 100 } is null-safe: if o is null the whole pattern is simply false, no exception. But the inverted form is a trap — o is not Order { Total: > 100 } is true for null and for a small order and for a Customer, which is rarely what the author meant. Also: { } on its own is the "not null" pattern, so x is { } means x is not null, which reads badly enough that is not null is always preferred. And a when clause opts the arm out of exhaustiveness analysis entirely.

Interview Q&A · patterns and control flow

What is the difference between a switch statement and a switch expression?

A switch statement is control flow: arms are case labels, each needs break or another jump, cases can share a body by falling through label-to-label, and it produces no value. A switch expression is an expression: it must produce a value, arms are pattern => value, there is no fall-through, and the compiler checks it for exhaustiveness and reachability. The expression form also composes — you can use it as an argument, in an initializer, or as an expression-bodied member — which is why most modern code reads better with it. The two cases I still use a statement for are when each arm does several statements with side effects, and when I need goto case to model an explicit state transition. If the expression form is not exhaustive it throws SwitchExpressionException at runtime, which is a much better failure than falling out the bottom of a statement and silently doing nothing.

Why does the compiler warn about exhaustiveness on some switches and not others?

It warns whenever it cannot prove that some input has no matching arm. For bool it can prove completeness from two arms. For an open class hierarchy it never can, because another assembly could add a subclass. For an enum it deliberately cannot, because enums are unvalidated integers — (Status)42 is legal, so an enum switch listing every declared member is still incomplete. And any arm with a when clause is excluded from the analysis, since the compiler will not evaluate your predicate. What changes this in C# 15 is closed hierarchies and union types, where the set of cases is fixed at compile time within the declaring assembly, so a switch covering them is provably exhaustive and needs no discard arm — and adding a case later turns every incomplete switch into a warning, which is precisely the refactoring signal you want.

How do union types change how you model results and errors?

They make the illegal states unrepresentable, which is the whole game. Today the common shape is a Result<T> class with bool IsSuccess, a nullable Value and a nullable Error, and nothing prevents constructing one with both null or both set — the invariant lives in a comment. With a union you declare union Result(Success, NotFound, Invalid);, the value is exactly one of them, and a switch over it is exhaustive by construction, so forgetting to handle Invalid is a build error rather than a null dereference in production. It also replaces the common hack of returning object or a base class plus casts, and it removes the need for third-party OneOf-style packages. Caveats I would state in an interview: it is C# 15, so preview until .NET 11 GA in November 2026; the runtime support types landed in Preview 5 and parts of the proposal are still unimplemented; and it is a real type with a discriminator, so it is not a zero-cost abstraction.

Is a switch faster than a chain of if/else?

Usually yes, and never slower, because the compiler builds a decision tree rather than testing conditions in order. Dense integer or enum cases become a jump table — one bounds check and an indirect branch, O(1) regardless of case count. Sparse cases become a binary search over ranges. String switches beyond a handful of cases compute a hash, switch on that, then confirm with a single string comparison, so they behave like a dictionary lookup rather than a linear scan of comparisons. Type patterns become a chain of type tests, but shared prefixes are hoisted so a common type is tested once for several arms. The practical conclusion I would give is that you should choose the form that reads best, because the fast one is also the readable one; the only time I hand-tune is when profiling shows a specific hot dispatch, and then the fix is usually a dictionary of delegates or a virtual call, not a rearranged switch.

What are list patterns good for in real code?

Anywhere a sequence has structure: parsing command-line arguments ([var verb, var target, ..var rest]), matching protocol frames or file headers by their first bytes, tokenising, and validating shapes in tests, where Assert.True(result is [_, _, { Status: Ok }]) is far more readable than three separate index assertions. They work on anything countable and indexable — arrays, List<T>, and via the Length/indexer pattern on custom types — and the slice pattern requires a Range indexer or a Slice method. The caveat is performance on non-array types: a slice pattern on a List<T> materialises a sub-list, so in a hot loop I would match over a ReadOnlySpan<T> instead, where slicing is free.

How do when clauses interact with the analysis?

A when clause is arbitrary code, so the compiler excludes that arm from both exhaustiveness and reachability reasoning — it cannot prove your predicate is true for some input, so it must assume the arm might not match. That has two consequences. First, a switch whose arms all carry when always needs a fallback arm, and you will get CS8509 without one. Second, a broader arm below a when-guarded arm is not reported as unreachable even when it obviously is, so you lose a safety check. I use when where the condition genuinely is not a pattern — a range computed from another variable, a call into a policy object — and I push everything expressible as a pattern into the pattern itself, because that is the part the compiler can check. And I never put side effects in a when: arms are evaluated in order, so a side-effecting guard runs for inputs that ultimately match a different arm.

What is the null behaviour of patterns?

Every type pattern implicitly fails for null — o is Order is false when o is null, and so is o is Order { Total: > 0 }, with no dereference and no exception, because the property test only runs after the type test succeeds. The empty property pattern { } therefore means "not null", though is not null reads far better. The trap is negation: is not Order { Total: > 0 } is true for null, for the wrong type, and for a zero-total order all at once, which is almost never the intent. In a switch expression, null must be matched by an explicit null arm or the discard, and if neither is present a null input throws — which is often exactly what you want, and is why I prefer switch expressions over defensive null checks scattered through the method.

When do you still reach for goto?

In C# 15, essentially never, because labeled break and continue cover the one honest case: escaping or continuing an outer loop from inside a nested one. Before that, the alternatives were a boolean flag threaded through every level — which is bookkeeping the reader has to simulate mentally — or goto past the loops, which at least stated the intent directly. The one goto that survives is goto case inside a switch statement, where it expresses a deliberate state transition ("handle this, then fall into that case") that C# otherwise forbids because it banned implicit fall-through. Even there, a small state machine or a loop is usually clearer. The IDE0410 analyzer in .NET 10 and later flags the flag-variable and goto shapes that labeled jumps replace, which is a good rule to turn on when you move a codebase to C# 15.

How would you refactor a long if/else-if chain of type checks?

First I would ask whether it should be polymorphism: if each branch is behaviour that belongs to the type, a virtual method or a strategy keyed by type removes the chain entirely and makes adding a case a local change. If the branching is genuinely the caller's concern — formatting, mapping, serialisation, a translation layer that must not live in the domain — then a switch expression over patterns is the right shape, because it is exhaustiveness-checked and reachability-checked while an if/else chain is neither. If the set of cases is closed and I control it, I would go further and make the hierarchy closed (C# 15) or a union, so the compiler enforces that every future case is handled everywhere. And I would flatten the nesting with property and positional patterns rather than keeping nested ifs inside each branch; the single-expression form usually cuts the code in half and removes the temporaries that made it hard to read.

What does pattern matching cost at runtime compared with a virtual call?

A type pattern is an isinst — a cast test — which is a few instructions and, importantly, is not a virtual dispatch, so no vtable indirection and no branch misprediction on the target. A chain of them is linear in the number of tested types, though the compiler hoists shared tests. A virtual call is one indirect branch that the CPU predicts well when the call site is monomorphic, and .NET's dynamic PGO can devirtualise and inline it entirely when profiling shows one dominant type. So for two or three cases they are comparable, and for a long chain the virtual call wins on raw dispatch cost. That is a performance argument, not the deciding one: I choose polymorphism when the behaviour belongs to the type and pattern matching when it belongs to the consumer, and I only measure if the site is genuinely hot.

07 Delegates, closures, LINQ

Docs: Delegates · LINQ · Expression trees

A delegate is an object with two fields: a target instance and a method pointer. That is the whole idea, and it explains everything downstream — why a delegate keeps its target alive (event leaks), why += creates a new delegate rather than mutating one (thread safety), why a lambda that captures nothing can be cached and a lambda that captures cannot (allocation), and why LINQ-to-objects and LINQ-to-SQL look identical but behave completely differently (delegates versus expression trees).

Closures: what the compiler actually builds

A lambda that references a variable from its enclosing scope does not copy it — it captures it, and the compiler hoists that variable into a generated class ("display class") so both the outer method and the lambda refer to the same field. So captured variables are shared by reference and stay alive as long as the delegate does. Three consequences you must be able to demonstrate:

// 1. Capture is by reference, and one closure object is created PER SCOPE
var actions = new List<Action>();
for (int i = 0; i < 3; i++) actions.Add(() => Console.Write(i));
actions.ForEach(a => a());          // prints "333" - one shared 'i' for the whole loop

for (int i = 0; i < 3; i++) { int copy = i; actions.Add(() => Console.Write(copy)); }
// prints "012" - 'copy' is a new variable each iteration, so a new closure each time

// 2. foreach is different: since C# 5 the iteration variable is per-iteration
foreach (var s in new[] { "a", "b" }) actions.Add(() => Console.Write(s));  // "ab", always

// 3. capturing nothing means the compiler caches a single delegate instance
Func<int, int> pure = static x => x * 2;    // C# 9 'static' lambda: capture is a compile error

The for-versus-foreach difference is the single most asked closure question, and the reason is a deliberate breaking change in C# 5: the foreach variable became a fresh variable per iteration because the old behaviour was, in the language team's words, a bug magnet. The for loop variable was left alone because it is genuinely one variable that the loop mutates — changing it would change the meaning of correct code.

The performance angle matters at lead level. A capturing lambda allocates a display class on every call of the enclosing method, and if you pass it to a hot API — Where, Task.Run, a cache's value factory — you are allocating per call. The fixes, in order of preference: mark the lambda static (C# 9) so capture is a compile error and the delegate is cached; use an overload that takes a state argument (ConcurrentDictionary.GetOrAdd(key, factory, state), Task.Factory.StartNew(action, state)) so nothing needs capturing; or hoist the delegate into a static readonly field.

Events: delegates with an access modifier

The event keyword restricts a delegate field so that outside code can only += and -=, not assign, clear, or invoke it. That is all it does — plus, for field-like events, the compiler generates thread-safe add/remove using a compare-exchange loop. The two things that go wrong:

public event EventHandler<OrderEvent>? OrderPlaced;

protected void Raise(OrderEvent e)
{
    // WRONG on multithreaded code: the handler may be unsubscribed between the check and the call
    // if (OrderPlaced != null) OrderPlaced(this, e);

    OrderPlaced?.Invoke(this, e);   // reads the field once into a temp, then invokes - safe
}

And the leak: publisher.OrderPlaced += subscriber.Handle makes the publisher hold a reference to the subscriber. If the publisher is long-lived (a singleton service, a static cache, a UI window's view model) and the subscriber is short-lived (a page, a request-scoped object), the subscriber is never collected. This is the classic managed memory leak in .NET, it does not show up as a crash, and it is diagnosed by taking two heap snapshots and looking at what roots the supposedly-dead objects. The fixes: unsubscribe in Dispose (and make the subscriber IDisposable if it subscribes to anything it does not own), or use a weak event pattern, or invert the direction so the short-lived object holds the reference.

Expression trees: code as data

Func<Order, bool> is compiled code. Expression<Func<Order, bool>> is a tree describing that code, built by the compiler at the call site, which a library can walk and translate into something else — SQL, a REST query, a validation rule. That single distinction is what separates IEnumerable<T> from IQueryable<T>, and it is the most consequential API-design detail in .NET data access.

Func<Order, bool>             predicate = o => o.Total > 100;   // compiled delegate
Expression<Func<Order, bool>> tree      = o => o.Total > 100;   // a tree, inspectable at runtime

// IQueryable: EF translates the tree to SQL - one filtered query
var big = db.Orders.Where(o => o.Total > 100).ToList();

// IEnumerable: the delegate runs in-process - SELECT * then filter in memory
var oops = db.Orders.AsEnumerable().Where(o => o.Total > 100).ToList();

Those two lines differ by six characters and by an entire table scan pulled across the network. In review, an AsEnumerable(), a ToList() or a foreach in the middle of a query chain is the thing to look for; so is any method call inside a Where that EF cannot translate, which either throws or (in older EF versions, and this is why the silent client-side evaluation was removed in EF Core 3.0) quietly degrades to in-memory filtering.

Expression trees have hard limits worth knowing: no statement bodies before .NET's expression-tree APIs are used manually, no await, no ref/out arguments, no assignment in a lambda expression tree (C# 13 relaxed a few restrictions, allowing ref locals and unsafe code in some positions, but the statement-body ban stands). And they are expensive: compiling one with .Compile() is measured in hundreds of microseconds, so cache the result — a compiled expression in a static field is a normal optimisation, recompiling one per request is a real production problem.

LINQ: deferred execution and the two traps

Almost every LINQ operator returns immediately and does no work; it builds an iterator that runs when you enumerate it. That is deferred execution, and it gives you composability and streaming — Where over a million rows allocates one small object, not a million-element list.

BehaviourOperatorsConsequence
Deferred, streamingWhere, Select, Take, Skip, Concat, SelectMany, Zipconstant memory; re-runs on each enumeration
Deferred, bufferingOrderBy, GroupBy, Reverse, Distinct*, Joinmaterialises the whole source before yielding the first item
ImmediateToList, ToArray, Count, Any, First, Sum, ToDictionaryexecutes now — the place a query actually costs you

Trap one: multiple enumeration. Passing an IEnumerable<T> around and calling .Count() then foreach-ing it runs the query twice — twice the database round trips, twice the side effects, and if the source is a network stream or a yield-based generator, possibly different results. The analyzer will not always catch it; ReSharper's "possible multiple enumeration" warning is worth its licence fee on its own. The rule: a method that takes IEnumerable<T> must enumerate it at most once, or materialise it immediately with ToList(); a method that needs to enumerate several times should take IReadOnlyCollection<T> and say so in the signature.

Trap two: captured state changing before enumeration. Because the query runs later, it sees the variables' values at enumeration time, not at definition time. A query defined inside a loop and enumerated after it sees the final loop values, which is the closure trap wearing a different hat.

On performance: every LINQ operator allocates an iterator, and the delegate call per element defeats inlining, so a hand-written for loop over an array is typically 2–5× faster for trivial bodies. That is almost never the bottleneck in application code and readability should win, but in a hot inner loop it is real. .NET has been closing the gap aggressively — .NET 9 vectorised and specialised many operators (notably Sum, Average, Min/Max, Contains, and Take/Skip fusion), and .NET 10 brought System.Linq.AsyncEnumerable into the box so LINQ over IAsyncEnumerable<T> no longer needs the community System.Linq.Async package.

Interview trap

"IEnumerable and IQueryable are basically the same, one's just for databases." They are opposites in the one way that matters: IEnumerable<T> takes Func and runs your code here; IQueryable<T> takes Expression<Func> and ships a description of your code somewhere else. Returning IQueryable<T> from a repository therefore leaks the database into the caller — they can compose anything onto it, including something untranslatable, and the query executes at an unpredictable point, possibly after the DbContext is disposed. My rule: IQueryable never crosses an architectural boundary; the repository returns materialised results or accepts a specification object. The counter-argument (it prevents over-fetching) is real, and the answer is to expose intent-shaped methods, not a raw queryable.

Gotcha

OrderBy is a stable sort in LINQ-to-objects; List<T>.Sort and Array.Sort are not, because they use introsort. Swapping one for the other "for performance" can silently reorder equal elements, which shows up as flaky UI ordering or non-deterministic output that only reproduces at certain sizes. Also: OrderBy buffers the entire sequence, so .OrderBy(x => x.Date).First() sorts everything to take one item — use MinBy/MaxBy (.NET 6) instead.

Interview Q&A · delegates and LINQ

Explain closures and the classic loop-variable bug.

A lambda that references an enclosing local captures the variable, not its value: the compiler hoists it into a generated class shared by the enclosing scope and the lambda. So in a for loop, every lambda created in the body shares one i, and after the loop that i is 3 — all the lambdas print 3. The fix is to introduce a variable inside the body, because a new closure object is created per scope instance. foreach does not have the problem: C# 5 made the iteration variable a fresh variable per iteration, a deliberate breaking change because the old behaviour caused this bug constantly. The follow-up worth volunteering is the lifetime consequence — a captured variable lives as long as the delegate does, so a lambda stored in a long-lived field can keep an entire object graph alive, which is a common leak in event-driven and caching code.

What is the difference between Func<T,bool> and Expression<Func<T,bool>>?

The first is a compiled delegate — machine code the CLR can invoke. The second is a data structure describing that code, which the compiler builds at the call site from the same lambda syntax, and which a library can walk. That is the entire basis of IQueryable: EF Core inspects the tree and emits SQL, so Where(o => o.Total > 100) becomes a WHERE clause instead of a client-side filter over every row. The costs are real: expression trees cannot contain statement bodies, await, or assignments; not everything you write will be translatable by a given provider, and an untranslatable node throws at execution time rather than compile time; and Compile() is expensive — hundreds of microseconds — so any compiled expression should be cached in a static field rather than rebuilt per request.

What is deferred execution and where does it bite?

Most LINQ operators return an iterator immediately and do no work until you enumerate. That buys streaming and composability, and it costs you predictability in three ways. Multiple enumeration: passing an IEnumerable<T> to code that calls Count() and then iterates runs the whole query twice, which for a database or HTTP source doubles the I/O invisibly. Deferred capture: the query reads its captured variables at enumeration time, so a query built in a loop and run afterwards sees the final values. And lifetime: enumerating after the underlying resource — a DbContext, a file handle — is disposed throws, often far from the code that built the query. My rules are: materialise at the boundary with ToList(), declare IReadOnlyCollection<T> when a method needs to enumerate more than once, and never return an unmaterialised query from a method whose resource scope ends when it returns.

How do event handlers leak memory, and how do you find one?

Subscribing makes the publisher hold a strong reference to the subscriber, through the delegate's target field. If the publisher outlives the subscriber — a singleton service, a static event, a long-lived cache, a parent view model — the subscriber and everything it references stay rooted forever. Nothing crashes; the process just grows. I find it by taking two heap snapshots around a repeated operation, looking for a type whose instance count climbs monotonically, and then asking the tool for the GC root path, which points straight at the event's invocation list. The fixes in order: unsubscribe in Dispose and make subscribing types disposable; prefer the short-lived object holding the reference rather than the long-lived one; use a weak event pattern where you truly cannot control lifetime; and in modern code, prefer an injected callback, a channel, or a mediator over a long-lived event, because those make the lifetime explicit.

Why is ?.Invoke the right way to raise an event?

Because delegates are immutable and +=/-= replace the field rather than mutating it, the pattern if (E != null) E(this, args); has a race: another thread can unsubscribe the last handler between the check and the call, leaving you invoking null. E?.Invoke(this, args) compiles to a single read of the field into a temporary followed by a null-check and invoke on that temporary, so the invocation list you test is the one you call. There is a second-order consequence worth naming: because the list is a snapshot, a handler unsubscribed a microsecond ago can still run, which is inherent to the model — if a handler must not run after disposal, it needs its own guard. Also remember that a multicast delegate invokes handlers sequentially and an exception in one handler prevents the rest from running, so a publisher that must be robust should invoke GetInvocationList() and catch per handler.

When is LINQ the wrong choice?

In genuinely hot inner loops, where the per-element delegate call blocks inlining and each operator allocates an iterator — a hand-written loop over an array or span is typically several times faster for trivial bodies, and in the tightest code I would use spans and avoid the abstraction entirely. Over IQueryable when the provider cannot translate what I wrote, because the failure mode is either an exception at runtime or, historically, silent client-side evaluation of an entire table. And where the query hides an algorithmic problem: a Where inside a Select over the same list is an O(n²) join written to look like O(n), and I have seen that take down a service. Everywhere else, LINQ's readability wins, and .NET has been closing the performance gap directly — .NET 9 vectorised and specialised many operators, so the old "LINQ is slow" reflex is much less true than it was.

What do static lambdas and the C# 14 lambda modifiers give you?

static on a lambda (C# 9) makes capturing a compile error, which is a guarantee rather than a hope: the delegate has no target, the compiler caches a single instance in a static field, and passing it to a hot API allocates nothing. I use it as a default for anything passed into a loop, a cache factory, or a background task, and only drop it when I genuinely need state — at which point I look for an overload taking a state argument instead. C# 14 added parameter modifiers on simple lambda parameters, so you can write (text, out result) => int.TryParse(text, out result) without spelling out every parameter type; previously any modifier forced a fully explicit parameter list, which meant a lot of noise to satisfy a TryParse-shaped delegate. params still needs an explicit type.

Should a repository return IQueryable<T>?

My default is no. Returning IQueryable hands the caller the database: they can compose any predicate onto it, including one the provider cannot translate, they control when it executes, and they can execute it after the DbContext has been disposed — which produces an ObjectDisposedException from a line that contains no database code. It also makes the repository untestable in the way people claim it is testable, because an in-memory IQueryable has different semantics from a SQL one for null handling, string comparison and grouping. What I do instead is expose intent-shaped methods that return materialised results, and where callers genuinely need composability, a specification object or a set of filter parameters that the repository translates itself. The honest counter-argument is over-fetching, and the honest answer to that is that adding a method is cheap and leaking the persistence model is not.

What changed for LINQ recently that you would mention as evidence you're current?

Two things. .NET 9 put serious work into the LINQ-to-objects implementation: vectorisation and specialisation for the numeric aggregates, better fusion of Take/Skip with the preceding operator, and faster paths when the source is already a List or an array, which quietly removed a chunk of the old "rewrite it as a for loop" advice. And .NET 10 shipped System.Linq.AsyncEnumerable in the box, so LINQ over IAsyncEnumerable<T> — WhereAsync-shaped composition over streaming sources — no longer requires the community System.Linq.Async package, which had been the de-facto dependency since C# 8 introduced async streams. If a codebase still references that package, removing it is a small, safe modernisation with a real benefit: one fewer transitive dependency and consistent behaviour with the rest of the BCL.

How do delegates and interfaces compare as an extension point?

A delegate is a single method with no name and no identity — perfect for a callback, a factory, a comparison, anything the caller supplies inline and never needs to reference again. An interface is a named contract that can carry several related members and can be implemented by a type with state and a lifetime. I choose a delegate when there is exactly one operation and the caller will usually write a lambda; I choose an interface when there are two or more related operations, when the implementation needs to be registered in DI, or when I want the implementer to be a testable, nameable thing. There is a performance dimension too: a delegate call is an indirect call that resists inlining, while an interface call on a struct passed as a constrained generic parameter is devirtualised and inlined — which is exactly the trick the BCL uses for comparers in its sort routines. And a delegate captures, so it can silently extend an object's lifetime in a way an injected interface does not.

08 Spans, memory, collections

Docs: Span<T> · Collection expressions

Span<T> (.NET Core 2.1, 2018) is the most important runtime type added to .NET in a decade, and the reason is one sentence: it is a view over contiguous memory — a pointer plus a length — that works uniformly over arrays, strings, stack memory, native memory and slices of any of them, without copying and without leaving safe code. Before spans, "parse this substring without allocating" was impossible in safe C#; Substring copies. After spans, the entire BCL was rewritten around them, and modern high-performance C# is largely the discipline of pushing spans as far up your call stack as they will go.

Why Span<T> must be a ref struct

A span can point into the middle of an array, or at a stackalloc buffer, or at unmanaged memory. If a span pointing at stack memory could be stored on the heap — in a field, a closure, an async state machine — the stack frame it refers to could return and the span would be dangling: memory corruption, in safe C#. So the language declares Span<T> a ref struct and the compiler enforces that it never reaches the heap. Hence the rules people memorise without understanding: cannot be boxed, cannot be a field of a class, cannot be captured by a lambda, cannot live across an await or a yield return. Every one of those is "it would end up on the heap".

ReadOnlySpan<char> line = "id=4711;total=99.50";

// slice with no allocation - Substring would allocate two strings here
int semi = line.IndexOf(';');
ReadOnlySpan<char> idPart = line[..semi];          // "id=4711"
ReadOnlySpan<char> rest   = line[(semi + 1)..];    // "total=99.50"

int id = int.Parse(idPart["id=".Length..]);        // Parse has span overloads throughout the BCL

When the data must outlive the frame or cross an await, you need Memory<T>/ReadOnlyMemory<T>: an ordinary struct that can live on the heap and hands you a Span<T> on demand via .Span. The idiom is "Memory in the async signature, Span inside the synchronous body" — which is exactly why Stream.ReadAsync takes Memory<byte> while Stream.Read takes Span<byte>.

C# 13 and 14 removed the two biggest remaining frictions. where T : allows ref struct (C# 13) lets generic code accept spans at all. First-class span types (C# 14) added implicit conversions between T[], Span<T> and ReadOnlySpan<T> in more positions — as extension-method receivers, composed with other conversions, and in generic inference — so span-based APIs finally feel as natural as array-based ones and overload resolution prefers the span overload where one exists. That last part is a subtle breaking change: code that used to bind to an IEnumerable<T> overload may now bind to a span overload, which is faster but is a different method.

Collection expressions (C# 12), and arguments (C# 15)

C# 12 unified collection creation behind [ … ], target-typed to whatever the destination is, with the spread element .. for inlining another sequence. The compiler picks an efficient construction strategy per target type: for a ReadOnlySpan<T> of constants it can emit a static data blob with zero allocation; for List<T> it presizes; for an array it uses the exact length.

Related, C# 13's params ReadOnlySpan<T> means a params method can now be called with no array allocation at all, and the BCL added those overloads widely — which is why string.Join and friends got faster with no source change on your side.

Pooling and the allocation budget

For buffers above a few hundred bytes, ArrayPool<T>.Shared.Rent/Return replaces an allocation with a rent. Two rules: the returned array is at least the size you asked for (so always slice to your length, and never trust array.Length), and you must return it in a finally or you have converted a GC problem into a leak. Above 85,000 bytes an array goes on the Large Object Heap, which is not compacted by default and is collected only in Gen2 — the classic cause of a service whose memory rises and never comes down. Pooling large buffers is the standard fix; RecyclableMemoryStream is the standard library for the MemoryStream case.

Interview trap

"Strings are immutable, so string concatenation is fine." s += x in a loop is O(n²) in both time and allocation: each iteration copies the whole accumulated string into a new one, so 10,000 concatenations of 10 characters allocates about 500 MB and spends most of its time in the GC. The compiler does not rewrite it into a StringBuilder — it only fuses concatenations within a single expression. Use StringBuilder for loops, string.Join/string.Concat for a known sequence, an interpolated string for a fixed shape (C# 10's interpolated string handler makes those allocate once, and ILogger's handler skips the formatting entirely when the level is disabled), and string.Create when you know the final length and want to write into the buffer directly.

Gotcha

ConcurrentDictionary.GetOrAdd(key, k => Expensive(k)) can call the factory multiple times for the same key under contention — only one result wins, but the others still ran, and if the factory opens a connection or starts a background task you have just leaked one. It is not a locking cache. If the factory must run exactly once, store Lazy<T> values (GetOrAdd(key, k => new Lazy<T>(…))) so the dictionary races on cheap Lazy objects and the expensive work happens once inside. The same applies to AddOrUpdate's update delegate.

Interview Q&A · memory and collections

What is Span<T>, and why can't you put one in a field?

It is a pointer and a length — a view over contiguous memory that can refer to an array, a slice of one, a string, a stackalloc buffer, or native memory, uniformly and without copying. Because it can point at stack memory, storing it on the heap would let it outlive the frame it points into, which is memory corruption in safe code. So the language makes it a ref struct and the compiler enforces stack-only-ness: no boxing, no fields of classes, no capture in lambdas, no living across an await or a yield. When I need those things I use Memory<T>, which is a normal struct that can be stored and awaited around and which yields a Span<T> on demand — that is why async stream APIs take Memory<byte> and the synchronous ones take Span<byte>. C# 13's allows ref struct constraint and C# 14's first-class span conversions have removed most of the remaining friction.

When does span-based code actually pay off?

When the same data is sliced, searched or reinterpreted many times before anything needs to own it — parsers, serializers, protocol handling, formatting, path and URL manipulation, anything reading from a socket or a file in a loop. There the win is large and compounding, because you remove an allocation per slice and the GC pressure that comes with it. Where it does not pay off is ordinary business logic: turning a three-line mapping method into span code makes it harder to read for a saving nobody can measure, and spans constrain you enough — no async, no capture — that they leak awkwardness upward. My rule is that spans belong in the hot path and at the edges of a library, and the boundary where you materialise a string or an array should be a conscious, documented line rather than an accident.

Explain the Large Object Heap and why it causes memory that never comes back.

Any allocation of 85,000 bytes or more goes on the LOH, which by default is not compacted — the GC sweeps it and reuses free blocks, but it does not move objects to close gaps, because copying very large objects is expensive. So a workload that allocates many differently-sized large buffers fragments it: the total free space is large but no single block fits the next request, and the heap grows. It is also only collected during a Gen2 collection, which is the expensive one. The symptom is a service whose working set climbs steadily and drops only on restart, with Gen0 activity that looks perfectly healthy. The fixes are to stop allocating large arrays in the first place — ArrayPool<T>, RecyclableMemoryStream, chunked processing rather than reading a whole file — and, as a last resort, an occasional explicit GCSettings.LargeObjectHeapCompactionMode compaction, which is a stop-the-world pause and not a design.

How do you choose between List, ImmutableArray, and FrozenDictionary?

By the read/write ratio and the sharing story. List<T> for anything being built or mutated, and I presize it when I know the count, because doubling growth copies. ImmutableArray<T> when the collection is shared across threads or handed out from an API and must not change under the recipient — it is a struct wrapping an array, so reads are as fast as an array, but every "modification" copies the whole thing, which makes building one in a loop accidentally quadratic; use the builder and MoveToImmutable. FrozenDictionary/FrozenSet (.NET 8) for lookup tables built once at startup and then read constantly — routing tables, configuration maps, enum-to-handler maps: construction is deliberately slow because it analyses the keys and picks a specialised layout, and lookups are meaningfully faster than Dictionary. The mistake I look for in review is FrozenDictionary being rebuilt per request, which inverts the trade entirely.

What is wrong with ConcurrentDictionary.GetOrAdd and an expensive factory?

The factory is not executed under a lock, so under contention several threads can run it concurrently for the same key; exactly one result is stored and the rest are discarded. If the factory is pure and cheap that is fine — it is a deliberate design choice to avoid holding a lock across user code, which would be a deadlock risk. If the factory opens a connection, starts a timer, registers a handler or costs a second of CPU, you have duplicated work and possibly leaked resources that nobody will ever dispose. The standard fix is to make the value a Lazy<T> with LazyThreadSafetyMode.ExecutionAndPublication: the dictionary then races on cheap wrapper objects, and the expensive initialisation happens exactly once inside the winner. The same caveat applies to AddOrUpdate, and it is worth stating that no method on ConcurrentDictionary makes a multi-step read-modify-write atomic across keys.

What did collection expressions change, and what does with(...) add in C# 15?

C# 12 gave one syntax — [ … ] — that target-types to arrays, List<T>, spans, immutable collections and any type with a builder attribute, with .. for spreading another sequence in. The value is not just brevity: the compiler chooses the construction strategy, so a ReadOnlySpan<int> of constants becomes a static data blob with no allocation at all, and a List<T> is presized rather than grown. What was missing was any way to pass constructor arguments, so "a case-insensitive HashSet" or "a List with capacity" had to fall back to old syntax. C# 15's with(...) element fixes that — [with(StringComparer.OrdinalIgnoreCase), "a", "A"] builds a one-element set — which finally lets a codebase standardise on one collection syntax. Alongside it, C# 13's params ReadOnlySpan<T> means params calls need not allocate an array, and the BCL added those overloads broadly.

How do you make string handling allocation-free?

Work in ReadOnlySpan<char> for as long as possible: AsSpan() instead of Substring, IndexOf/Split-free scanning, and the span overloads of int.Parse, DateTime.TryParse and friends that exist throughout the BCL. For building, string.Create(length, state, static (span, state) => …) lets you write directly into the final string's buffer with one allocation and no intermediate. For formatting into an existing buffer, TryFormat on every primitive writes into a Span<char>. For accumulating unknown-length output, StringBuilder, or a pooled ArrayBufferWriter. And for logging specifically, use structured logging with the source-generated [LoggerMessage] attribute, because the interpolated-string handler pattern means the message is never formatted at all when the level is disabled — which in a hot request path is usually the largest string win available.

What should a public API return: List<T>, IEnumerable<T>, or something else?

IReadOnlyList<T> or IReadOnlyCollection<T> for a materialised result, because they state "this is finished, you may count it and iterate it repeatedly" without promising a mutable List. Returning List<T> hands out a mutable reference to your internal state — the caller can add to it and you will never know. Returning IEnumerable<T> is the subtler mistake: it promises nothing about cost, so callers cannot tell whether Count() is free or a second database round trip, and lazily-evaluated results escape their resource scope. The honesty caveat to volunteer is that IReadOnly* is not a defensive copy — a caller can cast a returned List<T> back and mutate it — so if the immutability is a real invariant rather than documentation, return ImmutableArray<T> or a copy. And IAsyncEnumerable<T> when the result genuinely streams and the caller should be able to stop early.

When would you use stackalloc, and what is the risk?

For a short-lived scratch buffer whose size is small and bounded — formatting a number, building a key, a fixed-size lookup — where the alternative is an array allocation per call in a hot path. Since C# 7.2 you can assign it to a Span<T> without unsafe, which is how it appears in modern code. The risk is stack overflow, which is not a catchable exception in .NET: it terminates the process immediately, with no chance to log. So the size must be a compile-time-bounded constant, not derived from input, and the conventional ceiling is around 256–1024 elements; anything larger or input-dependent uses the hybrid pattern of stackalloc below a threshold and ArrayPool above it, which is exactly what the BCL does internally. The other rule is never to stackalloc inside a loop, because the allocation is only released when the method returns, not when the iteration ends.

How do you find and fix an allocation problem in a running service?

I start with dotnet-counters on the live process to see the shape: Gen0 collection rate, Gen2 rate, LOH size, allocation rate per second, and time in GC. A high Gen0 rate with low Gen2 is churn — usually strings, LINQ in a hot loop, closures, or boxing — and it is cheap to collect but shows up as latency jitter. A climbing Gen2 or LOH is retention or large buffers. Then I capture a trace with dotnet-trace or a dump with dotnet-dump and look at allocation stacks or, for retention, dumpheap -stat plus gcroot on the top type to see who is holding it. The fixes fall in a predictable order: stop allocating (spans, pooling, static lambdas, presized collections), then reduce lifetime (do not cache what you can recompute), then tune the GC last — Server GC and concurrent settings matter, but reaching for GC configuration before fixing the allocation is treating the symptom.

09 Exceptions and lifetime

Docs: Exceptions · Implementing Dispose

Two topics that look unrelated share one mechanism: the CLR's two-pass exception handling. Pass one walks the stack looking for a handler and evaluating when filters — without unwinding. Pass two unwinds, running finally blocks on the way. Everything odd about exceptions and disposal falls out of that: why filters can log with the original stack intact, why finally runs when a handler exists but may not when nothing catches, and why a using is exactly a try/finally.

What an exception costs, and what that implies

Throwing is expensive — on the order of microseconds, thousands of times the cost of a return — because the runtime captures a stack trace, walks frames, and defeats the JIT's optimistic assumptions. A try block itself is nearly free when nothing throws; it is the throw that costs. That gives a clean rule: exceptions are for the exceptional, and any code path where failure is normal and expected should return a value instead. .NET's own APIs model this precisely — int.Parse throws, int.TryParse does not, and there is a TryX beside almost every throwing X. A validation loop over 10,000 user rows that throws for each bad one is not just slow, it is a design error.

// .NET 6/8 guard helpers - one line, and the JIT inlines the happy path to nothing
ArgumentNullException.ThrowIfNull(order);
ArgumentException.ThrowIfNullOrWhiteSpace(order.Reference);
ArgumentOutOfRangeException.ThrowIfNegativeOrZero(quantity);
ObjectDisposedException.ThrowIf(_disposed, this);

// exception filters (C# 6): the filter runs in PASS ONE, before any unwinding
try
{
    await CallDownstreamAsync(ct);
}
catch (HttpRequestException ex) when (ex.StatusCode is HttpStatusCode.TooManyRequests)
{
    await BackOffAsync(ct);          // only retry on 429; anything else propagates untouched
}
catch (Exception ex) when (Log(ex))  // a filter that always returns false: log with the
{                                    // original stack live, then let it propagate
    throw;                           // unreachable
}

The filter idiom deserves the emphasis. catch … when (…) is not sugar for catch { if (…) throw; }: the filter is evaluated before the stack unwinds, so at the moment it runs, the frames below are still live and a debugger or a dump shows the real crash site. Catch-and-rethrow, by contrast, unwinds first, which is why "the stack trace stops at our catch block" is such a common complaint.

throw; versus throw ex;

The most reliably asked exception question, and the answer must be precise. throw; rethrows the current exception preserving the original stack trace. throw ex; throws the same object but resets its stack trace to this line, destroying the evidence of where it actually came from. If you need to rethrow from a different context — you captured an exception, awaited something, and now want to surface it — use ExceptionDispatchInfo.Capture(ex).Throw(), which preserves the original trace and appends the new one. That is exactly what await does internally when it unwraps a faulted task, which is why awaiting gives you a clean trace while task.Result gives you an AggregateException wrapper.

Designing exceptions

  • Throw the most specific existing type. ArgumentNullException, ArgumentOutOfRangeException, InvalidOperationException (wrong state), NotSupportedException (never supported here). Never throw Exception, SystemException or ApplicationException — the caller cannot catch them selectively.
  • Custom exceptions earn their place by being caught. If nobody writes catch (MyDomainException), it did not need to exist. When you do write one, give it the context as properties (the order id, the rule that failed), not just in the message, so handlers and logs can use it structurally.
  • Never catch and swallow. An empty catch block is where production incidents go to hide. If you genuinely must continue, log at warning with the exception object, and say in a comment why continuing is correct.
  • Do not catch Exception except at a boundary — the top of a request pipeline, a background worker's loop, a message handler — where the job is to convert failure into a response or a retry and keep the process alive. And be aware that some failures are not catchable at all: StackOverflowException terminates the process, and OutOfMemoryException is usually unrecoverable in practice.

Deterministic cleanup: IDisposable and using

The GC handles memory; it does not handle file handles, sockets, database connections, locks or unmanaged buffers. IDisposable is the language's answer, and using is exactly a try/finally around Dispose(). C# 8 added the using declaration, which disposes at the end of the enclosing scope and removes a nesting level:

// using declaration (C# 8): disposed at the end of the method, in reverse order
await using var connection = new SqlConnection(cs);        // IAsyncDisposable
await connection.OpenAsync(ct);
using var command = connection.CreateCommand();

// the full dispose pattern is only needed when you own UNMANAGED resources directly
public sealed class Cache : IDisposable                    // sealed: no virtual Dispose(bool) needed
{
    private readonly Timer _timer;
    private bool _disposed;

    public void Dispose()
    {
        if (_disposed) return;                              // Dispose must be idempotent
        _disposed = true;
        _timer.Dispose();
    }
}

The full protected virtual void Dispose(bool disposing) plus finalizer pattern is for one situation only: a class that directly owns an unmanaged resource (a raw handle, a native allocation) and can be derived from. In modern code you should almost never write a finalizer, because SafeHandle already implements a correct, critically-finalized one and composes safely. Finalizers are genuinely costly: an object with a finalizer survives its first collection, gets promoted, and is only reclaimed after the finalizer thread runs it — so a finalizer on a hot type doubles its GC cost and delays reclamation unboundedly, and a finalizer that blocks stalls every other finalizer in the process.

Gotcha

An exception thrown inside a finally block replaces the original one, silently. So a Dispose() that throws during unwinding destroys the exception you actually needed to see — which is why the guidance is that Dispose must never throw, and must be safe to call twice. The async version is nastier: an exception in an await using's DisposeAsync behaves the same way, and a finally containing a blocking .Result can deadlock during unwinding, at the worst possible moment. Related: an unobserved exception in a fire-and-forget Task no longer crashes the process (it did in .NET Framework 4.0), it just vanishes — so _ = DoWorkAsync(); is a silent failure factory, and the fix is to await it or attach a continuation that logs.

Interview Q&A · exceptions and disposal

What is the difference between throw; and throw ex;?

throw; rethrows the in-flight exception and preserves its original stack trace, so the report still points at the line that failed. throw ex; throws the same object but resets the trace to the rethrow site, erasing every frame below it — the exception now appears to originate in your catch block, which turns a five-minute diagnosis into an afternoon. When I need to rethrow outside the original handler — I captured it, awaited something, and now want to surface it — I use ExceptionDispatchInfo.Capture(ex).Throw(), which preserves the original trace and appends the rethrow location. That is the same mechanism await uses when it unwraps a faulted task, which is why awaiting gives you a clean single exception while blocking on .Result gives you an AggregateException wrapper you have to unwrap yourself.

When do you throw and when do you return a result?

Exceptions for genuinely exceptional conditions — a broken invariant, a resource that vanished, a bug in the caller. Return values for outcomes that are part of the normal flow: validation failures, "not found", a parse that may fail on user input. Two reasons. Cost: a throw is microseconds and defeats JIT optimisation, so a validation loop over ten thousand rows that throws per row is measurably slow, while a TryParse-shaped API is free. And honesty: an exception is invisible in the signature, so the caller has no way to know it must be handled, whereas a result type or a bool plus out forces the decision at the call site. The BCL models this explicitly with the Try… pair beside every throwing method. C# 15's union types make the result-returning style much better than it has been, because the compiler can then enforce that every case is handled.

What do exception filters give you that a catch block does not?

They run in the first pass of exception handling, before the stack unwinds. That has two practical consequences. First, you can decide whether to handle without disturbing the exception: catch (SqlException ex) when (ex.Number == 1205) catches only deadlocks and lets everything else propagate with an untouched stack, which catch-and-rethrow cannot do. Second, a filter that logs and returns false gives you a logging hook where the failing frames are still live, so a debugger breaking there or a dump taken there shows the real crash site — this is the standard trick for diagnosing something you cannot reproduce locally. The caveat is that filter code runs at a strange time, potentially on the throwing thread while the stack is still intact, so it must be fast and must not throw; an exception inside a filter is swallowed and the filter is treated as false.

Explain the dispose pattern and when you need the full version.

The full pattern — public Dispose() calling Dispose(true) and GC.SuppressFinalize(this), a protected virtual void Dispose(bool disposing), and a finalizer calling Dispose(false) — exists for exactly one case: an unsealed class that directly owns an unmanaged resource. The disposing flag distinguishes deterministic disposal, where it is safe to touch other managed objects, from finalization, where those objects may already have been collected. In modern code I almost never write it, because SafeHandle wraps unmanaged handles with a correct critical finalizer already, so my class just holds a SafeHandle and disposes it. For the overwhelmingly common case — a sealed class holding some managed disposables — I write a sealed class, a plain Dispose() that is idempotent, and no finalizer at all. Adding a finalizer you do not need is a real cost: the object survives its first GC, gets promoted, and waits on the finalizer thread.

Why should Dispose never throw?

Because it usually runs during unwinding from another exception, and an exception thrown in a finally block replaces the in-flight one — so a throwing Dispose destroys the error you actually needed to diagnose and substitutes a confusing one from cleanup code. It must also be idempotent, because there are several paths that can call it: an explicit call, a using, a DI container, and a caller being defensive. The pattern I use is a _disposed flag with an early return, cleanup that catches and logs rather than propagating for anything genuinely fallible, and ObjectDisposedException.ThrowIf(_disposed, this) on the public methods so use-after-dispose fails clearly rather than corrupting. For cleanup that genuinely needs I/O and can fail — flushing a buffer, sending a final frame — that belongs in an explicit CompleteAsync the caller awaits, with DisposeAsync as the best-effort backstop.

What is IAsyncDisposable for, and what breaks if you implement only one?

It exists because Dispose() is synchronous, so cleanup that involves I/O — flushing a stream, closing a connection gracefully, sending a shutdown frame — either blocks a thread or is skipped. IAsyncDisposable.DisposeAsync plus await using makes that cleanup awaitable. The failure mode is a mismatch: if a type implements only IAsyncDisposable and someone writes a plain using, it compiles only if the type also implements IDisposable, and if it does not, they simply do not dispose it — the resource leaks silently. Conversely a DI container disposing a scope synchronously will not call DisposeAsync. So my rule is: if the type can be consumed from synchronous code or resolved from a container, implement both, with the synchronous one doing the best it can without blocking, and document which one is preferred.

Where should you catch Exception?

Only at boundaries whose job is to keep the system running: the top of a request pipeline, the loop of a background worker or message consumer, a hosted service's entry point, and a UI event handler. There the responsibility is to convert an arbitrary failure into a response, a retry, a dead-letter, or a log entry, and to make sure the process survives. Everywhere else, catching Exception means you are handling failures you have not thought about — including bugs, cancellation, and out-of-memory — and it usually turns a loud failure into a quiet wrong answer. Two refinements I would add: exclude OperationCanceledException explicitly, because cancellation is not an error and logging it as one poisons your dashboards; and remember that some conditions are not catchable at all — a stack overflow terminates the process by design, so "catch everything" is never a completeness guarantee.

What happens to an exception in a fire-and-forget task?

It is stored on the Task and nothing observes it, so nothing happens — the operation silently did not work. In .NET Framework 4.0 an unobserved task exception crashed the process at finalization; that was changed in 4.5 to swallow it and raise TaskScheduler.UnobservedTaskException, which almost nobody subscribes to. So _ = DoWorkAsync(); is a factory for invisible failures, and it is one of the specific things I look for in code review. The correct shapes are: await it; or if it genuinely must outlive the request, hand it to something that owns background work — a hosted service, a channel consumer, a queue — where failures are logged, retried and surfaced as metrics. If I truly must fire and forget, I attach an explicit continuation that logs on fault, and I make that a shared helper so it is consistent and greppable.

How do you decide whether to wrap an exception?

I wrap when the layer boundary means the original exception would leak an implementation detail the caller must not depend on — a repository turning a SqlException into a domain-level failure, so callers do not start catching provider-specific error numbers. I do not wrap merely to add a message; that adds a frame and hides the type without helping anyone. When I do wrap, the original always goes in as the inner exception, and I preserve any structured data the caller might need as properties on the new type. The failure I look for in review is logging ex.Message alone: for a wrapped exception that is the least informative string in the chain, and for something like a SqlException it omits the error number that tells you it was a deadlock and therefore retryable. Log ex.ToString() or let the structured logger capture the exception object, which records the full chain.

What do the .NET 6–8 guard helpers change?

ArgumentNullException.ThrowIfNull, ArgumentException.ThrowIfNullOrWhiteSpace, ArgumentOutOfRangeException.ThrowIfNegativeOrZero, ObjectDisposedException.ThrowIf and their siblings replace three-line guard blocks with one line, and because they use [CallerArgumentExpression] the exception message names the actual argument expression without you passing nameof. They matter for more than brevity: the throwing part is factored into a separate non-inlined method, so the JIT can inline the check itself down to a single test-and-branch on the happy path, which means guards on hot methods are essentially free. Before them, people either skipped guards for performance or wrote a Guard helper class per codebase. My convention now is that every public method starts with these, and internal methods rely on nullable annotations and analyzers instead.

10 Asynchrony in the language

Docs: Task asynchronous programming model · Async streams

One sentence carries this unit: an async method is a method the compiler chops into pieces at every await, and the returned Task is the handle that says when the last piece has run. Notice what is absent — a thread. The most common failure at interview is modelling async as "runs on a background thread". It does not. It is a way of not occupying a thread while a disk, a socket, a timer or another machine is busy. Async does not reduce latency; it reduces the number of threads you need to absorb concurrency.

What the compiler generates

For each async method the compiler emits a state machine — a struct in Release, a class in Debug — hoists every local that lives across an await into a field, and rewrites the body into a MoveNext() with a switch over an integer state. Your original method becomes: create the machine, call builder.Start(ref machine), return builder.Task. Each await x becomes, conceptually:

var awaiter = x.GetAwaiter();               // the awaitable pattern - duck-typed, not an interface
if (!awaiter.IsCompleted)                   // already finished? then never suspend
{
    _state = 0;                             // remember where to resume
    _builder.AwaitUnsafeOnCompleted(ref awaiter, ref this);  // boxes the struct ONCE, creates the Task
    return;                                 // hand the thread back to the caller
}
var result = awaiter.GetResult();           // unwrap, or rethrow preserving the original stack

Three corollaries you can derive almost every other answer from. Awaiting an already-completed task is synchronous and nearly free — no suspension, no boxing, no scheduling, which is why cached results and buffered reads cost almost nothing and why "async everywhere" is not automatically expensive. The first real suspension is where the cost lives: one heap allocation for the boxed state machine plus one for the Task; later awaits in the same method reuse the box. And an async method runs synchronously until its first incomplete await, so a method that parses JSON for 200 ms before its first await blocks its caller for 200 ms, async keyword or not.

ConfigureAwait(false) says "I do not need the captured context". In a library it is still the right default, because you cannot know whether your caller has a UI context — and if they do, and they blocked on your task, you deadlock. In ASP.NET Core application code it is unnecessary: there is no synchronization context, so it changes nothing. .NET 8 added ConfigureAwaitOptions for finer control, including SuppressThrowing (await a task purely for completion, ignoring its exception) and ForceYielding.

The deadlock, and why it happens

// classic sync-over-async deadlock (UI thread or classic ASP.NET, NOT ASP.NET Core)
public string Get()            => GetAsync().Result;             // blocks the context thread
private async Task<string> GetAsync()
{
    var r = await _http.GetStringAsync(url);   // captures the context; wants to resume ON it
    return r.Trim();                           // ... but that thread is blocked in .Result. Deadlock.
}

The rule is not "use ConfigureAwait(false)" — that is a mitigation. The rule is never block on async code: no .Result, no .Wait(), no GetAwaiter().GetResult() outside of Main and a handful of legacy interop points. Async is transitive by design; the correct fix is to make the caller async too, all the way to the entry point.

Task, ValueTask, and cancellation

Task<T> is a class: it allocates, but it is safe — you can await it twice, store it, hand it to WhenAll. ValueTask<T> is a struct that avoids the allocation when the result is already available, which matters for APIs that usually complete synchronously (a cache hit, a buffered read). The price is a strict contract: await it exactly once, never block on it, never store it. Violating that is undefined behaviour, not an exception, because the underlying IValueTaskSource may be pooled and reused. If you need to do any of those things, call .AsTask() first. Use ValueTask when you are writing a hot, frequently-synchronous API; use Task everywhere else.

Cancellation is cooperative and explicit: a CancellationToken is the last parameter of every async API by convention, you pass it down unchanged, and you call ThrowIfCancellationRequested() at loop boundaries so the task ends Canceled rather than Faulted. Two lead-level points: cancellation is not a rollback — a cancelled write may already have hit the database — and CancellationTokenSource.CreateLinkedTokenSource and every Register return something you must dispose, or you leak registrations onto a long-lived token.

Async streams and the newest layer

await foreach (var row in ReadRowsAsync(ct).WithCancellation(ct))
    Process(row);

{
    await using var reader = await OpenAsync(ct);
    while (await reader.ReadAsync(ct))
        yield return Map(reader);            // streams: constant memory, caller can stop early
}

IAsyncEnumerable<T> (C# 8) is the streaming shape — one item at a time, with backpressure, cancellable, and since .NET 10 composable with LINQ operators from the in-box System.Linq.AsyncEnumerable (which supersedes the community System.Linq.Async package). The [EnumeratorCancellation] attribute is the detail people miss: without it, the token passed to WithCancellation at the call site never reaches your method's parameter.

The genuinely new thing is under the surface. .NET 11 (Preview 7, August 2026; GA expected November 2026) ships Runtime Async, moving suspension and resumption out of compiler-generated state machines and into the runtime with a new async calling convention. The BCL is already compiled with it enabled; the visible payoffs are dramatically shorter stack traces and lower per-await overhead, and in Preview 7 async methods finally flow through the tiered-compilation pipeline instead of being stuck at tier 0. Your source does not change — which is exactly why it is a good thing to be able to describe.

Interview trap

async void. It is not "async that returns nothing" — async Task is that. async void has no handle, so nothing can await it, nothing can know when it finished, and an exception inside it is rethrown on the captured SynchronizationContext, which in ASP.NET Core or a console app means the process crashes: it cannot be caught by the caller's try/catch. The only legitimate use is a top-level event handler whose signature you do not control, and even then the body should be a try/catch around a call to an async Task method. The related trap is Task.Run in ASP.NET Core: it does not add capacity, it moves work from one thread-pool thread to another and adds a hop — the reason to use it is offloading genuinely CPU-bound work off a request thread, not "making something async".

Gotcha

Task.WhenAll over an unbounded collection is a load generator: 10,000 items becomes 10,000 concurrent calls, and you will discover your downstream's connection limit the hard way. Bound it with Parallel.ForEachAsync (which takes MaxDegreeOfParallelism and a token), a SemaphoreSlim, or a bounded Channel. Also: WhenAll aggregates every exception but await rethrows only the first — inspect task.Exception if you need them all. And Task.WhenEach (.NET 9) lets you consume results as they complete rather than waiting for the slowest.

Expected outcome

1. The .Result version hangs forever: the UI thread is blocked waiting, and the continuation is queued to that same UI thread, so neither can proceed. ConfigureAwait(false) unblocks it because the continuation no longer needs the UI thread — but note that the fix is a band-aid; the third version, async void handler awaiting properly, is the correct design and also lets exceptions surface. ASP.NET Core does not deadlock here because it has no synchronization context, which is why this bug mostly bites in desktop code and in .NET Framework web apps being migrated.

2. The Task version allocates on the order of 70–100 bytes per call even for cache hits (state machine box plus Task); the ValueTask version allocates essentially nothing on the synchronous path. That is the entire justification for ValueTask — and the reason the contract is strict: the struct may wrap a pooled source that is recycled the moment you await it, so awaiting twice reads someone else's result.

Interview Q&A · asynchrony

Does async create a thread?

No. async/await is a compiler transformation into a state machine; it creates no threads and starts nothing in parallel. For genuinely asynchronous I/O the operating system does the waiting — an I/O completion port signals when the bytes arrive — and no thread is occupied in between. A thread only appears if something explicitly queues work, such as Task.Run, or if a continuation is scheduled onto the pool. The clearest way to say it in an interview is: async decouples thread count from concurrency. Two hundred concurrent requests waiting 40 ms on a database need two hundred threads under blocking I/O and a handful under async I/O, and the latency per request is identical — async did not make the database faster, it made the waiting free.

Why does sync-over-async deadlock, and what is the real fix?

Because await captures the current synchronization context and schedules the continuation back onto it, while .Result blocks the only thread that context owns. The continuation waits for the thread; the thread waits for the continuation. It bites on UI threads and classic ASP.NET, which have single-threaded-ish contexts; ASP.NET Core has none, so the same code does not deadlock there — it just wastes a thread and, at scale, causes pool starvation instead, which is a slower and more confusing failure. ConfigureAwait(false) prevents the deadlock but is a mitigation, not a fix. The fix is to never block: make the call chain async to the entry point. When I inherit a codebase where that is not yet possible, I isolate the blocking call at a single boundary, document it, and treat it as debt with a ticket, rather than sprinkling ConfigureAwait everywhere.

When is ValueTask worth it, and what is the contract?

Worth it when the method usually completes synchronously and is called a great deal: cache lookups, buffered stream reads, pipeline stages that mostly hit fast paths. There it removes the state-machine box and the Task allocation, which at millions of calls per second is real. The contract is strict because the struct may wrap a pooled IValueTaskSource that is recycled as soon as it is consumed: await it exactly once, never await it twice, never block on .Result, never store it in a field or hand it to WhenAll. If you need any of those, call .AsTask() first, which materialises a real Task. Violations do not throw reliably — they read another operation's result — which is why I would not put ValueTask on a public API consumed by people who might not know the rules unless the performance case is genuinely made.

What is wrong with async void?

There is no Task, so there is no handle: nobody can await it, nobody can know when it completed, and nothing composes with it. Worse, its exceptions do not propagate to the caller — they are rethrown on the captured synchronization context, which in a console app, a worker service or ASP.NET Core means an unhandled exception that terminates the process, and a try/catch around the call site does not catch it. The one legitimate use is an event handler whose delegate signature is void, and even there the body should be a try/catch wrapping a call into a proper async Task method so failures are handled. In review it is one of the few things I treat as an automatic change request, and there is an analyzer for it.

Do you still write ConfigureAwait(false)?

In library code, yes, as a default — because I do not know my caller, and if they have a synchronization context and block on me, the omission is a deadlock. In ASP.NET Core application code, no: there is no synchronization context, so it changes nothing and adds noise; the guidance from the ASP.NET team is explicit about that. In desktop application code I want the opposite — I need the continuation back on the UI thread to touch controls — so the default capture is correct and I use ConfigureAwait(false) only in the non-UI layers. .NET 8 broadened the API with ConfigureAwaitOptions, adding SuppressThrowing for awaiting a task purely for completion and ForceYielding for guaranteeing a suspension, which are worth knowing because they replace some awkward older idioms.

How do you bound concurrency correctly?

By deciding a number and enforcing it, rather than letting the collection size decide. Task.WhenAll over an unbounded list issues every call at once, which is a denial-of-service attack on your own downstream — you find the connection pool limit, the API rate limit, or the thread pool at the worst moment. The tools in order of preference: Parallel.ForEachAsync, which takes a MaxDegreeOfParallelism and a cancellation token and is the right default for "do this to every item"; a SemaphoreSlim when I need finer control or per-resource limits; and a bounded Channel<T> with a consumer loop when I want genuine backpressure, so the producer slows down rather than buffering. The number itself should be derived from the downstream's limit — the database connection pool size, the API's documented rate — not guessed. And I use Task.WhenEach (.NET 9) when I want to process results as they land rather than waiting for the slowest.

How does cancellation actually work?

Cooperatively. A CancellationTokenSource owns the state; the CancellationToken is a cheap struct you pass down every call, and the operation itself must check it — via ThrowIfCancellationRequested() at loop boundaries, or by handing it to an API that does. Nothing is aborted; there is no thread abort in modern .NET, deliberately, because it corrupted state. Three things I make sure are right: throw rather than return early, so the task ends Canceled and callers can distinguish it from success; dispose linked sources and registrations, because a Register on a long-lived token is a leak; and remember cancellation is not a rollback — a cancelled HTTP call may have been fully processed by the server, so anything with side effects needs idempotency or compensation. In ASP.NET Core, HttpContext.RequestAborted is the token to plumb through.

What is Runtime Async in .NET 11 and why should you care?

It moves the suspension and resumption mechanics out of compiler-generated state machines and into the runtime itself, using a new async calling convention. Today every async method compiles to a state machine class, which means allocations, extra frames, and stack traces full of MoveNext and AsyncMethodBuilder noise. With runtime async the runtime handles it, so traces get dramatically shorter — Microsoft's own sample went from thirteen frames to five — and per-await overhead drops. The BCL in .NET 11 is already compiled with it on, and Preview 7 (August 2026) added the missing piece of routing async methods through the tiered-compilation pipeline instead of leaving them at tier 0. Nothing changes in your source, which is the point: it is a runtime-level performance and diagnosability win you get by upgrading. .NET 11 is an STS release with GA expected November 2026, so today it is preview-only.

How do you debug an async application that has hung?

Not with a thread dump — that is the key insight. A stalled async service looks healthy in a thread listing, because the suspended operations are not on any stack; they are objects on the heap. So I take a memory dump with dotnet-dump and run dumpasync, which reconstructs the chain of what each pending operation is awaiting and where. That usually points straight at the culprit: a downstream call with no timeout, a semaphore nobody released, a SemaphoreSlim.WaitAsync without a token. Alongside that I check thread-pool starvation with dotnet-counters — a growing work-item queue with high thread count and low CPU is the signature of blocking calls inside async code — and I look for .Result, .Wait() and lock around awaits in the suspect path. The preventative measures are timeouts on every outbound call and a cancellation token that actually reaches the bottom of the stack.

What is System.Threading.Lock and why did it appear?

.NET 9 added a real Lock type instead of locking on an arbitrary object. Locking on object was always a workaround: any object has a header word that can be inflated into a sync block, which is why lock(this) or lock(typeof(T)) was possible and dangerous — external code could take the same lock and deadlock you. Lock is a purpose-built type with EnterScope() returning a disposable, and C# 13 taught the lock statement to recognise it, so lock (_myLock) uses the faster dedicated path rather than monitor-on-object. Practical guidance unchanged: keep the critical section tiny, never await inside a lock (it will not even compile), use SemaphoreSlim.WaitAsync when you need an async-compatible mutual exclusion, and prefer immutable data or a concurrent collection over a lock where you can.

11 The runtime contract

Docs: GC fundamentals · Native AOT

C# does not describe how your code runs; the CLR does. At lead level you are expected to reason about that boundary: what the JIT can and cannot optimise, what the GC's generational assumption buys you, and what you give up when you switch to native AOT. This unit is the model, not the trivia.

Compilation happens twice, and the second time is adaptive

C# compiles to IL. The JIT compiles IL to machine code at runtime, per method, on first call. Since .NET Core 3.0 that happens in tiers: tier 0 compiles fast with almost no optimisation so startup is quick, and any method that runs often enough (a call-count threshold, or an on-stack replacement for long-running loops) is recompiled at tier 1 with full optimisation. Since .NET 8, dynamic PGO is on by default: tier 0 code is instrumented, and tier 1 uses the observed profile — which types actually showed up at a virtual call site, which branches were taken — to devirtualise, inline and lay out code for the path your program really takes. That is why a benchmark's first hundred iterations mean nothing and why BenchmarkDotNet insists on a warm-up.

The corollaries worth stating: the JIT can inline small methods (roughly under 32 bytes of IL, with heuristics), and inlining is what makes properties, guard helpers and small structs free. It cannot inline across a virtual call unless it can devirtualise, which sealed guarantees and PGO often achieves. It eliminates bounds checks when it can prove the index is in range — for (int i = 0; i < array.Length; i++) is the pattern it recognises, and caching array.Length in a local actually defeats it. And ReadyToRun precompilation gives you fast startup by shipping tier-0-quality native code that the JIT can still re-optimise later.

The GC: generations and the assumption behind them

.NET's collector is generational because of one empirical claim: most objects die young. New objects go in Gen0, a small region collected very often and very cheaply — a Gen0 collection is sub-millisecond and only touches surviving objects, so allocating a million short-lived objects costs almost nothing to collect. Survivors are promoted to Gen1, then Gen2, and Gen2 collections are the expensive ones because they walk the whole heap. Large objects (≥ 85,000 bytes) go on the LOH, which is collected with Gen2 and is not compacted by default.

The low-level tools, and when they earn their keep

// pass a large readonly struct without copying it (and without a defensive copy, because it is readonly)

static ref int Slot(int[] data, int i) => ref data[i];
ref int slot = ref Slot(buffer, 3);
slot = 42;                                  // writes into buffer[3]

static void Parse(ReadOnlySpan<char> input) { Span<byte> scratch = stackalloc byte[512]; /* … */ }

All four are real but narrow. in avoids a copy for large readonly structs and does nothing useful (or actively adds a defensive copy) for non-readonly ones. ref returns are how CollectionsMarshal.GetValueRefOrNullRef lets you update a dictionary value without a second lookup. AggressiveInlining on a method that is not tiny makes things worse by bloating the caller. SkipLocalsInit removes the CLR's zeroing of locals, which is a genuine win for big stack buffers and a genuine security risk if you then read uninitialised memory. Reach for them with a benchmark in hand, never on instinct.

Native AOT and trimming: what you give up

Native AOT compiles your app ahead of time to a single self-contained native executable: startup in single-digit milliseconds, no JIT, much smaller memory footprint, and no IL to reverse-engineer easily. The cost is that the whole program must be knowable at build time. That rules out anything the linker cannot see: runtime IL emission (Reflection.Emit, Expression.Compile in its dynamic form), Assembly.LoadFrom of plugins, and reflection over types that trimming removed because nothing referenced them statically. This is exactly why the ecosystem moved to source generators — System.Text.Json's source-generated context, [LoggerMessage], [GeneratedRegex], [LibraryImport], compiled EF Core models — all of which produce visible code at build time instead of emitting it at runtime. In .NET 10, ASP.NET Core minimal APIs, gRPC and much of the BCL are AOT-compatible; MVC, Razor and EF Core's runtime model building are not fully. Turn on <IsAotCompatible>true</IsAotCompatible> in libraries to get the analyzer warnings early even if you never publish AOT.

Interview trap

Micro-benchmarking with Stopwatch in a loop. Almost every number produced that way is wrong, for reasons that are worth being able to list: tiered compilation means the first iterations run unoptimised; the JIT will happily delete a loop whose result you never use; a "constant" input gets folded; the GC may or may not run inside your measurement window; and CPU frequency scaling makes short runs non-comparable. Use BenchmarkDotNet, which handles warm-up, multiple processes, statistics, and — via [MemoryDiagnoser] — allocation counts, which are usually more actionable than the timings. And measure the whole scenario, not the micro-operation: a 40% faster method inside a call that spends 95% of its time on a database round trip is a rounding error.

Gotcha

GC.Collect() in production code is almost always harmful: it forces a Gen2 collection, promotes everything that survives, and destroys the generational assumption the collector is built on — the usual result is worse steady-state memory, not better. The two legitimate uses are a benchmark harness isolating a measurement, and a deliberate one-shot compaction after a known bulk phase (GCSettings.LargeObjectHeapCompactionMode = CompactOnce after loading and discarding a large dataset). Both should have a comment explaining why.

That contrast is the generational hypothesis made visible, and it is why "reduce allocations" is less useful advice than "reduce surviving allocations".

Interview Q&A · runtime and performance

Explain tiered compilation and dynamic PGO.

Methods are first compiled quickly with minimal optimisation (tier 0) so the application starts fast, and methods that prove hot — by call count, or by on-stack replacement for a long-running loop — are recompiled with full optimisation at tier 1. Since .NET 8, dynamic PGO is on by default: tier 0 code carries lightweight instrumentation, and the tier 1 compilation uses that profile. The big wins are guarded devirtualisation — if a virtual call site saw List<T> 99% of the time, the JIT emits a type check plus a direct inlined call with a fallback — plus better branch layout and better inlining decisions. Practically it means three things: startup and steady-state performance are both good without you choosing; measurements before warm-up are meaningless; and interface-heavy code is much cheaper than it used to be, so the old advice to avoid abstraction for speed is largely obsolete.

How does the GC work, and what does "most objects die young" buy you?

It is a generational, mark-and-sweep, compacting collector. Allocation is a pointer bump in Gen0, so it is essentially free. A Gen0 collection only traces from roots into that small region and only copies survivors, so its cost is proportional to what lives, not what was allocated — which is why churning millions of temporary objects is genuinely cheap. Survivors are promoted to Gen1 and then Gen2, and a Gen2 collection walks the whole heap, so it is the expensive one. The large object heap sits alongside, collected with Gen2 and not compacted by default. The engineering conclusion I draw from that model is that the metric to optimise is survival, not allocation: a cache that holds request-scoped data, a static dictionary that grows, or an event subscription that is never removed will hurt far more than a hot loop allocating temporaries.

Server GC or Workstation GC?

Server GC for anything throughput-oriented running on multiple cores — it gives each core its own heap and its own collection thread, so collections parallelise and allocation contention drops. It is the default for ASP.NET Core. Workstation GC for desktop apps and for small containers where a per-core heap would waste memory, since Server GC historically reserved a lot of memory per core regardless of load. That last drawback is much less of an issue now: DATAS, introduced in .NET 8 and on by default since .NET 9, dynamically adapts the number of heaps to actual load, so a container that used to sit at a gigabyte of committed memory idles at a fraction of that. In containers I also make sure the memory limit is visible to the runtime — .NET reads cgroup limits — and I set an explicit heap hard limit when I want headroom for non-GC memory rather than being OOM-killed.

What does native AOT give you and what does it cost?

It gives startup in single-digit milliseconds instead of tens or hundreds, a much smaller and more predictable memory footprint, a single self-contained executable with no runtime to install, and no JIT — which matters for serverless, CLI tools, sidecars and anything that scales from zero. The cost is that the entire program has to be statically knowable: no runtime IL emission, so Reflection.Emit and dynamic Expression.Compile are out; no assembly loading for plugins; and reflection only over what the trimmer can prove is reachable, which means anything driven by reflection needs explicit roots or, better, a source generator. That is precisely why the ecosystem moved to source-generated JSON contexts, [LoggerMessage], [GeneratedRegex] and [LibraryImport]. In .NET 10, minimal APIs and gRPC are AOT-friendly while MVC and EF Core's runtime model building are not fully. Even when I do not publish AOT, I set IsAotCompatible on libraries to get the analyzer warnings, because they also catch trimming hazards.

How do you approach a "the service got slower" report?

Measure before touching anything, and measure the whole path. First I want to know whether it is latency or throughput, which percentile moved, and whether it correlates with deploys, traffic shape or a dependency. Then I look at the cheap signals: dotnet-counters for GC rate, time in GC, thread-pool queue length and lock contention; the tracing system for where the time actually goes across services. Thread-pool starvation — a growing work-item queue with modest CPU — points at blocking inside async code. High Gen2 or LOH growth points at retention. High Gen0 with latency jitter points at churn. Only once the trace names a component do I profile it, and only then do I benchmark a candidate fix with BenchmarkDotNet. The discipline I insist on with a team is that no optimisation merges without a before-and-after number from the real scenario, because the intuitive fix is wrong often enough to matter and the code is always more complex afterwards.

When does in or ref readonly actually help?

When passing a large readonly struct that would otherwise be copied — a snapshot type of several words, a matrix, a big options value — in a hot path. The saving is the copy. The trap is that in on a struct that is not declared readonly makes things worse: the compiler cannot prove that a member call does not mutate, so it inserts a defensive copy at every access, and you have added work rather than removed it. For small structs — anything up to about two machine words — passing by value is faster than passing a reference and dereferencing it, so in is a pessimisation. C# 12's ref readonly parameters made the intent expressible more precisely than in, which had ambiguous rules about accepting rvalues. My rule is: readonly struct always, in only for large ones, and only with a benchmark.

Why is micro-benchmarking with Stopwatch unreliable?

Because several things conspire to measure something other than what you intended. Tiered compilation means early iterations run unoptimised code, so a short loop measures the JIT. The optimiser will delete work whose result is unused and constant-fold inputs it can see, so the "fast" version is often the version that got deleted. A GC pause landing inside the window skews a short measurement badly, and CPU frequency scaling and core migration add noise larger than the effect you are hunting. BenchmarkDotNet exists to handle all of that: separate processes, warm-up, statistically determined iteration counts, outlier analysis, and consumption of results so nothing is optimised away. I also always enable [MemoryDiagnoser], because allocation counts are stable, meaningful and usually more actionable than nanoseconds — and I keep the benchmark at the scenario level, since a faster method inside an I/O-bound call changes nothing.

What is the cost of a virtual call today?

Much lower than the folklore suggests. A monomorphic virtual call site — one where the same type shows up every time — is predicted well by the CPU and, with dynamic PGO on by default since .NET 8, is often devirtualised and inlined entirely: the JIT emits a type check and a direct call with a fallback. So interface-based design does not carry the penalty people assumed a decade ago. Where it still costs is genuinely polymorphic call sites in tight loops, where the branch predictor cannot help and inlining is impossible, and generic virtual methods, which require a runtime dictionary lookup that resists inlining and is a known weak spot under native AOT. The two tools that make a difference are sealed, which makes devirtualisation unconditional, and the struct-generic strategy pattern the BCL uses — passing a struct comparer as a constrained generic argument so the call is resolved statically.

How do you keep memory flat in a long-running service?

By treating retention as the thing to control. I audit the obvious roots: statics and singletons holding per-request or per-user data; caches without a size limit or expiry — MemoryCache with SizeLimit set, not an unbounded ConcurrentDictionary; event subscriptions that are never removed, which is the most common managed leak because the publisher holds the subscriber; and anything captured by a long-lived delegate or timer. Then I look at the LOH, because large buffers fragment a heap that is not compacted by default — the fix is pooling and chunking rather than reading whole files or building giant strings. In operation I watch working set alongside Gen2 and LOH size over days, not minutes, since a leak looks like normal growth for the first hour. And I verify with two heap snapshots around a repeated operation, comparing instance counts and asking the tool for the root path of whatever climbed.

What runtime-level change in the current release would you mention to show you're current?

Two. Dynamic PGO becoming the default in .NET 8 changed the performance advice materially — abstraction is cheaper than it was, and the old habit of avoiding interfaces in hot paths is mostly obsolete. And in .NET 11, currently at Preview 7 from 11 August 2026 with GA expected in November, Runtime Async moves async suspension from compiler-generated state machines into the runtime itself: shorter stack traces, lower per-await overhead, and in Preview 7 async methods finally flow through the tiered-compilation pipeline rather than being pinned at tier 0. Alongside that, .NET 11 brings CoreCLR to WebAssembly with an interpreter-plus-ReadyToRun model, native Zstandard in System.IO.Compression, and BFloat16 for machine-learning workloads. None of it changes your C#, which is the interesting part: the language surface is stable while the execution model keeps improving.

Roslyn is not just a compiler; it is a compiler exposed as an API, and that decision is why C# tooling looks the way it does. Analyzers, code fixes, refactorings, generators and the IDE all run on the same syntax and semantic model the build uses. For a lead, this is the layer where you encode team standards mechanically instead of arguing about them in review.

The project file is the contract

Two things here are load-bearing. That is the mechanism behind the widespread trick of defining IsExternalInit in a .NET Framework project so init and records compile. And TreatWarningsAsErrors is the single highest-leverage line in the file: a warning nobody fixes is a warning nobody reads, and the nullable analysis in particular is worthless as advice and valuable as a gate.

Analyzers: the review comments you only make once

Analyzers ship with the SDK (the CA rules from .NET analyzers, enabled by AnalysisLevel), with packages (StyleCop, SonarAnalyzer, Roslynator, Meziantou), and you can write your own. .editorconfig is where severity lives, and it is per-directory, so you can hold new code to a stricter standard than legacy code without a solution-wide flag day:

# .editorconfig
[*.cs]

dotnet_diagnostic.CA1852.severity = warning     # seal internal types that are never derived from

The judgment call worth being able to defend: which rules are errors. My answer is that correctness and security rules are errors (nullable, disposal, CA2007 in libraries, the crypto and injection rules), performance rules are warnings, and style rules are suggestions enforced by dotnet format in CI rather than by the compiler — because a build that fails on brace placement trains people to disable analyzers.

Source generators: the reflection replacement

An incremental source generator runs during compilation, inspects the syntax and semantic model, and adds source files to the compilation. It cannot modify your code — only add to it — which is why every generator-driven API in .NET requires partial (unit 03). The reason this pattern took over is trimming and AOT: generated code is real code the linker can see, so it survives trimming, works under native AOT, and costs nothing at startup, whereas the reflection and Reflection.Emit it replaced cost both.

The classic mistake is putting a SyntaxNode or an ISymbol into the pipeline's data model — those hold the whole compilation alive, so caching breaks and the IDE crawls. Extract the values you need into a small equatable record early, and everything downstream stays cheap.

Small things that show fluency

  • Global usings and implicit usings (C# 10 / .NET 6): global using in one file replaces a header block in every file; ImplicitUsings adds the SDK's default set. Useful, but a huge global-usings file makes code harder to read out of context — keep it to genuinely universal namespaces.
  • file-scoped types (C# 11) and file-scoped namespaces (C# 10) — the latter removes a whole indentation level and is now the default in templates.
  • Deterministic builds and SourceLink: ContinuousIntegrationBuild plus SourceLink means a stack trace from production can be stepped through against the exact commit, which is worth more than most debugging tools.
  • Central Package Management (Directory.Packages.props): one place for every version in the solution, which turns "which project has the old Newtonsoft" from an investigation into a diff.
  • File-based apps (.NET 10): dotnet run app.cs runs a single C# file with no project, and C# 14 added preprocessor directives — #:package Something@1.2.3, #:sdk Microsoft.NET.Sdk.Web — so a one-file script can declare its own dependencies. It replaces a lot of what people used PowerShell or LINQPad for, and dotnet project convert promotes it to a real project when it outgrows one file.
Interview trap

"We can't upgrade the language version because we're on an old .NET." Half true, and the half matters. LangVersion and TargetFramework are separate: most syntax-only features — pattern matching, expression-bodied members, tuples, switch expressions, file-scoped namespaces, target-typed new, string interpolation improvements — work on older targets, including .NET Framework 4.8, once you set <LangVersion>latest</LangVersion>. What does not work is anything requiring a runtime type or a runtime capability: required, records' init (without an IsExternalInit polyfill), ranges and indices, default interface members, static abstract members, and spans in their modern form. So the honest answer to a team on .NET Framework is: raise LangVersion today for the ergonomics, and plan the framework migration separately for the runtime features and support lifecycle.

Gotcha

Suppressing an analyzer warning solution-wide because one file is noisy is how codebases lose their safety net. Suppress at the narrowest scope that works — an .editorconfig entry scoped to a directory, or #pragma warning disable with a comment and a restore — and treat a global suppression as requiring the same justification as deleting a test. The related habit worth building: [SuppressMessage] with a Justification string, so the reason lives next to the suppression instead of in a pull-request comment nobody will find again.

Interview Q&A · tooling and the compiler

What is the relationship between LangVersion and TargetFramework?

They are separate settings that interact. TargetFramework picks the runtime and the BCL surface; LangVersion picks the compiler's syntax level, and defaults to the newest version the target supports. You can raise LangVersion above the target's default, and every purely syntactic feature will work — pattern matching, tuples, switch expressions, file-scoped namespaces, target-typed new. What fails is any feature that needs a type or capability from the runtime: init needs IsExternalInit, required needs RequiredMemberAttribute, ranges need System.Index and System.Range, and default interface members and static abstract members need runtime support that simply is not in .NET Framework. Several of those can be polyfilled by declaring the attribute yourself, which is exactly what packages like PolySharp automate, and it is a legitimate way to get modern ergonomics on a legacy target while the framework migration is planned separately.

How do you use analyzers to enforce standards without annoying the team?

By tiering severity to purpose and scoping it by directory. Correctness and security rules are errors — nullable warnings, disposal, the crypto and injection rules, ConfigureAwait in libraries — because those are bugs and a warning nobody fixes is noise. Performance rules are warnings, since they need judgment. Style is a suggestion enforced by dotnet format in CI, not by the compiler, because failing a build on brace placement teaches people to switch analyzers off. Then I use per-directory .editorconfig so inherited code is held to a lower bar than new code, which lets me turn the standard on today rather than after a cleanup project that never happens. And every suppression is narrow and carries a justification, because a solution-wide suppression is how a codebase quietly loses its safety net.

What are source generators and why did the ecosystem move to them?

They are compiler plugins that add source files to the compilation based on what they find in your code — they can add, never modify, which is why generator-driven APIs require partial. The move to them was driven by trimming and native AOT: the previous generation of frameworks did their work at runtime with reflection and Reflection.Emit, which the linker cannot see and AOT cannot support, and which costs startup time on every process launch. Generated code is ordinary code the linker can analyse, so it survives trimming and works under AOT, and the work happens once at build time. That is why System.Text.Json has a source-generated context, why logging moved to [LoggerMessage], regex to [GeneratedRegex], interop to [LibraryImport], and EF Core to compiled models. The secondary benefit is debuggability: you can read and step through the generated code instead of guessing what reflection did.

What is the most common bug in a hand-written source generator?

Breaking incrementality by putting Roslyn objects into the pipeline. The IIncrementalGenerator API caches each stage and only re-runs what changed, but caching depends on the stage's output being equatable and small. If you pass a SyntaxNode, an ISymbol or a Compilation through, you have captured a reference to the entire compilation, equality never matches, the cache never hits, and every keystroke in the IDE re-runs the whole generator — which users experience as the IDE freezing. The fix is to project into a small equatable record of plain strings and values in the very first transform. The other frequent mistakes are emitting non-deterministic output such as timestamps, which breaks build caching, and forgetting that your generated file names must be unique or the compiler silently drops one.

What does TreatWarningsAsErrors buy and what does it cost?

It buys the difference between analysis that runs and analysis that matters. Nullable warnings, unawaited tasks, unreachable code, disposal problems — none of them fail anything by default, so in a codebase with a few hundred existing warnings, new ones are invisible. Making them errors means every one is dealt with at the moment it is introduced, when it is cheap. The cost is friction on upgrades: a new SDK adds new analyzers, and a build that was green fails on code nobody touched. I manage that with AnalysisLevel pinned to a specific version rather than latest in CI, so I adopt new rules deliberately, plus WarningsNotAsErrors for a short list of rules I am mid-migration on. The combination gives a hard gate without the upgrade being a surprise.

What are file-based apps in .NET 10?

dotnet run app.cs executes a single C# file with no project file, no obj directory and no ceremony. C# 14 added preprocessor directives so the file can declare what it needs — #:package Newtonsoft.Json@13.0.3 to reference a NuGet package, #:sdk Microsoft.NET.Sdk.Web to make it a web app, #:property for MSBuild properties. It fills the gap that PowerShell, LINQPad and Python scripts have been filling for .NET teams: build scripts, one-off data fixes, quick reproductions of a bug, teaching examples. What makes it more than a toy is dotnet project convert, which promotes the file into a normal project the moment it outgrows one file, so there is no rewrite when a script becomes a tool. I would mention it in an interview as a small but genuinely useful signal of where the platform is going — reducing the activation energy for writing C# at all.

How do you make production stack traces useful?

Three settings and one habit. Deterministic builds with ContinuousIntegrationBuild so the same source always produces the same binary, SourceLink so the PDB records the exact commit and source URL, and publishing symbols — either embedded in the assembly or to a symbol server — so a trace from production can be resolved and stepped through against the right code. The habit is not throwing away the information: log the exception object through structured logging rather than ex.Message, so the inner exception chain and stack survive; never use throw ex;; and prefer exception filters over catch-and-rethrow when the goal is to log. On top of that, in .NET 11 runtime async makes async traces materially shorter by removing the state-machine frames, which is a real diagnosability improvement rather than a cosmetic one.

How do you manage NuGet versions across a large solution?

Central Package Management: a Directory.Packages.props at the root lists every package version once, and project files reference packages without versions. That turns "which project is still on the old serializer" from an investigation into reading one file, and it makes a security update a single-line diff rather than a search-and-replace across forty csproj files. I pair it with Directory.Build.props for the shared compiler settings, lock files for reproducible restores in CI, and a policy that transitive version conflicts are resolved explicitly rather than left to nearest-wins, because nearest-wins is where "it works on my machine" comes from. And I enable the NuGet audit features so known-vulnerable packages fail the build rather than appearing in a report nobody reads.

What would you check in the first hour on an unfamiliar C# codebase?

The build first: target framework and language version, whether nullable is on, whether warnings are errors, and whether there is a Directory.Build.props — that tells me the standard the team actually holds itself to, which is more informative than any documentation. Then the dependency graph and the package versions, looking for unsupported frameworks, abandoned packages, and anything that pins me. Then the test project — how many, how fast, and whether they test behaviour or mocks. Then I run the analyzers with everything enabled and look at the distribution of warnings, which is a very fast map of where the risk is concentrated. Finally I read one vertical slice end to end, from HTTP entry point to database, because architecture documents describe intentions and the slice describes reality.

13 API design and review

Docs: Framework design guidelines · Library change rules

This is the unit that separates a senior from a lead in an interview, because it is where the language stops being about correctness and starts being about commitment. Every public member is a promise you will support for as long as the assembly ships. The question is never "does this compile" but "what does this cost me in two years, and who pays".

What actually breaks a consumer

Source compatibility and binary compatibility are different, and confusing them is how "minor version" releases take down downstream builds:

That is worse than an exception, and it is the strongest practical argument for the rules of thumb — static readonly over const, overloads over new optional parameters, and never renumbering an enum that has ever been persisted or serialised.

Designing for the caller you will never meet

  • Default to internal. Public is a decision, not a default. Use InternalsVisibleTo for the test project sparingly — if a type needs testing badly enough to widen its access, it usually wants to be a separate, genuinely public component.
  • Seal by default (analyzer CA1852). Unsealing later is additive; sealing later is a break.
  • Accept the least specific type you need, return the most specific type you can afford to promise. Take IEnumerable<T>, return IReadOnlyList<T>. Returning List<T> gives away your internal state; returning IEnumerable<T> hides the cost from the caller.
  • Every async method takes a CancellationToken as its last parameter, defaulted, and passes it down. A method that swallows the token is a method nobody can shut down cleanly.
  • Validate at the public boundary with the guard helpers, even with nullable enabled, because annotations are not enforcement (unit 02).
  • Deprecate before you delete. [Obsolete("Use X instead", error: false)] for a release, then error: true, then removal in a major version. Add DiagnosticId and UrlFormat so consumers can suppress it precisely and find the migration note.
  • Track the surface mechanically. Microsoft.CodeAnalysis.PublicApiAnalyzers keeps PublicAPI.Shipped.txt/Unshipped.txt in the repo, so every addition to the public surface shows up as a diff in code review. It turns "we accidentally shipped that" into an explicit decision.

Extension members as an API tool (C# 14)

C# 14's extension blocks are the biggest addition to the API designer's toolkit in years, because they let you add properties, static members and operators to a type you do not own — not just methods. That is how you decorate a BCL or third-party type without a wrapper class, and how a library can offer ergonomic surface without forcing inheritance.

public static class SequenceExtensions
{
    extension<T>(IEnumerable<T> source)          // instance-like members on IEnumerable<T>
    {
        public bool IsEmpty => !source.Any();     // an extension PROPERTY - new in C# 14
        public IEnumerable<T> TakeLast(int n) => source.Skip(Math.Max(0, source.Count() - n));
    }

    extension<T>(IEnumerable<T>)                  // static members ON the type
    {
        public static IEnumerable<T> Empty => [];
        public static IEnumerable<T> operator +(IEnumerable<T> a, IEnumerable<T> b) => a.Concat(b);
    }
}

// C# 15 adds extension indexers too:
extension(IReadOnlyList<int> list) { public int this[Index i] => list[i.GetOffset(list.Count)]; }

The design caution that belongs with it: extension members are resolved at compile time and are not polymorphic, so an extension "property" cannot be overridden and will be shadowed the moment the real type gains a member with the same name — silently changing behaviour on a package upgrade. They are also invisible to reflection-driven code, serializers and data binding. Use them for ergonomics on types you do not own, not to fake inheritance.

What I actually flag in code review

  1. async void, and any fire-and-forget task with no failure handling.
  2. A CancellationToken that is accepted and not passed on.
  3. .Result, .Wait(), or GetAwaiter().GetResult() outside Main.
  4. catch (Exception) that is not at a boundary, and any empty catch.
  5. throw ex; instead of throw;, and wrapping without an inner exception.
  6. IQueryable or IEnumerable escaping a data-access boundary, and any possible double enumeration.
  7. public where internal would do; a new public member with no matching PublicAPI.Unshipped.txt entry.
  8. A mutable type used as a dictionary key, or value equality on something with identity.
  9. DateTime.Now instead of DateTimeOffset.UtcNow or an injected clock — the single most common source of tests that fail twice a year.
  10. An unbounded WhenAll, an unbounded cache, or a HttpClient constructed per call rather than resolved from IHttpClientFactory.
  11. An unexplained !, an unexplained analyzer suppression, or a magic string that nameof would cover.
Interview trap

"We'll make it public now and tighten it later." You will not — nobody has ever tightened a public API on schedule, and the reason is that the cost lands on someone else's roadmap. The same trap wearing different clothes: adding an optional parameter "because it's backwards compatible". It is source-compatible and binary-breaking: the method signature literally changed, so every compiled caller looking for the old one gets a MissingMethodException at runtime, and in a plugin or multi-assembly deployment that is a production incident rather than a build failure. The correct move is an overload. Being able to say why — that default values and consts are baked into the caller's IL, so the caller's compile time is what matters — is what marks the answer as lead-level rather than memorised.

Gotcha

Returning IReadOnlyList<T> is a statement of intent, not a guarantee: if the underlying object is a List<T>, a caller can cast back and mutate your internal state. If the immutability is a real invariant rather than documentation, return ImmutableArray<T>, a copy, or a genuine read-only wrapper. The same applies to arrays returned from properties — public byte[] Key => _key; hands out a mutable reference to your secret, and a ReadOnlySpan<byte> or a defensive copy is the fix.

Try it — break a consumer without breaking the build

Exercise 1. Build a library with public void Send(string message) and a console app that calls it. Build both. Change the library method to public void Send(string message, bool urgent = false), rebuild only the library, drop the DLL next to the app, and run the app.

Exercise 2. Add Microsoft.CodeAnalysis.PublicApiAnalyzers to a library with an existing public surface. Run the build, apply the code fix to populate PublicAPI.Shipped.txt, then add one new public method and build again.

Expected outcome

1. MissingMethodException at runtime. The optional parameter is not a runtime concept — the compiler bakes the default value into the call site, so the app's IL still calls a one-argument overload that no longer exists. The lesson generalises to consts, enum values and default parameter values alike: anything the compiler copies into the caller becomes part of your binary contract, and changing it is invisible until it is not.

2. The new method fails the build with RS0016 until you explicitly add it to PublicAPI.Unshipped.txt. That is the point: every widening of the public surface becomes a line in a diff that a reviewer sees, so "we accidentally made that public" stops being possible. It is one of the cheapest governance mechanisms available for a shared library.

Interview Q&A · design and judgment

What makes a change to a .NET library binary-breaking?

Anything that changes what the caller's compiled IL is looking for. Changing a method signature — including adding an optional parameter — because the call site encodes the exact signature. Turning a field into a property, because a field access is ldfld and a property access is a call. Widening a parameter type, since the old signature no longer exists. Adding a member to an interface without a default implementation. And the silent ones, which are the dangerous category: changing a public const, a default parameter value or an enum member's number, all of which are copied into the consumer's IL at their compile time, so the old value keeps being used with no error at all. The practical policy that falls out is: overloads instead of new optional parameters, static readonly instead of const for anything that might change, never renumber an enum, and run a compatibility checker in CI rather than relying on review.

How do you deprecate something properly?

In stages, with an escape route at every one. First release: [Obsolete("Use NewThing instead.", error: false)] with a DiagnosticId so consumers can suppress that specific warning rather than all obsolescence warnings, and a UrlFormat pointing at a migration note. The replacement must exist and be at least as capable — deprecating without a replacement is just complaining. Second release, after at least one full support cycle: flip to error: true, so it fails builds but the code still exists and can be suppressed in an emergency. Third, in a major version: remove it, documented in the release notes with the migration. In an internal codebase the same shape applies but the timeline can be much shorter, and I would add a static analysis rule or an architecture test so nobody adds new usages while the migration is in flight — otherwise the deprecated surface grows faster than you can remove it.

What is your rule for public versus internal?

Internal until there is a named consumer outside the assembly, and then public deliberately, with a note about why. The reasoning is asymmetry: widening access later is free, narrowing it is a breaking change that lands on someone else's schedule, so the cost of being wrong is entirely on one side. For testing, I prefer testing through the public surface, because a test that needs internals is usually telling me the component boundary is wrong; where InternalsVisibleTo is genuinely warranted I limit it to the test assembly and treat it as a smell to revisit. In a shared library I back this with the public API analyzer, so every addition to the surface shows up as an explicit line in a tracked file and gets reviewed as a design decision rather than sliding in with a feature.

How do C# 14 extension members change API design?

They let you add properties, static members and operators to a type you do not own, not just methods, so you can give a BCL or third-party type ergonomic surface without a wrapper. That removes a whole category of awkward SomethingHelper.IsEmpty(x) static classes and makes fluent APIs read naturally. The design cautions matter as much as the capability. Extension members are resolved at compile time against the static type, so they are not polymorphic and cannot be overridden — and the moment the real type gains a member with the same name, the real one wins silently, changing behaviour on a package upgrade with no warning. They are also invisible to reflection, serializers, data binding and expression-tree translation, so an extension property will not work in an EF Core Where. I use them for consumer-side ergonomics and never as a substitute for a member the type should actually have.

What do you look for first in a code review?

Correctness under failure, before anything stylistic. Concretely: does every async path pass its cancellation token down; is there any blocking on async; are exceptions caught only where something can be done about them, with the stack preserved; are resources deterministically disposed; and is any concurrency bounded rather than "as many as there are items". Then boundaries: is anything public that should be internal, does a data-access type leak IQueryable or an unmaterialised sequence, is there a new dependency direction that was not there before. Then the things that will hurt later: mutable dictionary keys, DateTime.Now, unbounded caches, magic strings. Style I leave to analyzers and dotnet format entirely, because human attention spent on brace placement is attention not spent on the null that arrives from deserialisation.

How would you introduce a language or platform upgrade to a skeptical team?

By making the first step reversible and the benefit measurable. I would not open with "let's move to .NET 10"; I would open with a specific pain the upgrade removes — startup time, a security patch deadline, a support end date, a class of bug the compiler could catch. The support argument is usually the strongest and least arguable: .NET 8 and .NET 9 both leave support in November 2026, and running unsupported means no security fixes, which is a compliance conversation rather than a preference. Then I would do the work in slices: raise LangVersion first, since it is nearly free and gives immediate ergonomics; turn nullable on in annotations mode so nothing breaks; upgrade one low-risk service end to end and publish the before-and-after numbers; and only then propose the fleet-wide plan with those numbers attached. Skepticism is usually about risk and time, not about the technology, so the answer is to make the risk small and visible rather than to argue about the merits.

How do you decide what belongs in a shared library versus duplicated?

I ask whether the two usages will change for the same reason. If they will, sharing is correct and the library encodes a real concept. If they merely look similar today — two mapping methods, two validation routines that happen to have the same shape — sharing couples two roadmaps together, and the first divergent requirement produces a boolean parameter, then two, then a configuration object nobody understands. A shared library also has a cost most teams underestimate: it needs versioning, a compatibility policy, a deprecation process and an owner, and without those it becomes the thing everyone is afraid to change. So my bar is high: shared code should be a genuine domain concept or genuine infrastructure, it should have an owner, and if it is neither, I would rather have the duplication and a comment pointing at its twin.

What does testability look like at the language level?

Seams that do not require a mocking framework to be clever. Constructor injection of dependencies as interfaces, so a test supplies a fake without reflection. No static mutable state, because it makes tests order-dependent and prevents parallel execution. An injected clock rather than DateTime.Now, and an injected randomness source, because both otherwise produce tests that fail on a specific date or one run in a thousand. Async all the way down, so tests do not deadlock on a synchronization context. And methods that return values rather than mutating hidden state, since asserting on a return value is far more robust than asserting that a mock was called with the right arguments — over-specified mock verification is the main reason test suites become the thing preventing refactoring. Sealed classes, incidentally, are not a testability problem: if you need to fake it, it should have been an interface.

Where do you draw the line on "clever" C#?

At the point where the reader has to know a rule they would not have looked up. Pattern matching, records, collection expressions and switch expressions all make code shorter and clearer, and I want those everywhere. Reflection, dynamic, expression-tree manipulation, hand-rolled state machines, unsafe code and clever operator overloading all make code shorter and less clear, and each one needs a written reason and a test. The specific question I ask is: when this fails at three in the morning, can the person on call understand what it does from the code alone? Anything that fails that test needs either a comment explaining the mechanism or a simpler implementation. The one exception I make is genuinely hot code, where the clever version is justified by a benchmark in the pull request — and there the comment is mandatory, because the next person will otherwise "simplify" it back.

How do you plan a migration from .NET Framework to modern .NET?

By separating what must move from what can stay, and by never doing a big bang. First I inventory: which assemblies use APIs that do not exist on modern .NET — remoting, AppDomains, WCF server, WebForms, System.Drawing on Linux — because those need a redesign rather than a retarget, and everything else is mostly mechanical. Then I retarget the leaf libraries to netstandard2.0 so they can be referenced from both worlds, which lets the old and new applications share code during the transition and makes progress visible early. Then I move services one at a time, strangler-style, with the new one behind the same interface and a routing switch so rollback is a configuration change. Along the way I raise LangVersion immediately, since most syntax works on the old target, and turn nullable on in annotations mode. The forcing function I would put in front of leadership is the support timeline rather than the technology: .NET Framework 4.8 is supported indefinitely as a Windows component, but the ecosystem — packages, tooling, hiring — has already moved, and every year of delay makes the same work more expensive.

Everything that matters at lead level but is not one of the language's building blocks: the ecosystem decisions, the security questions, the debugging stories, the legacy reality, and the "how would you…" scenarios. Twenty-two questions, grouped.

Architecture & ecosystem decisions

Which .NET version would you target for a new service today, and why?

.NET 10, because it is the current LTS: it shipped 11 November 2025 and is supported until November 2028, which is three years of security patches without a forced upgrade. The alternative framing matters though — the official guidance is that a service you deploy continuously should take the latest release whether it is LTS or STS, because you are upgrading regularly anyway and STS gives you features a year earlier. I choose LTS when the deployment cadence is slow or the compliance environment makes upgrades expensive, and latest when the team ships weekly. What I would not do today is start on .NET 8 or .NET 9: both leave support in November 2026, so a new project would be planning its first forced migration before it reaches production. And I would set LangVersion to latest regardless, since language ergonomics cost nothing.

How do you choose between C# and something else on the .NET platform?

C# is the default because the ecosystem, the tooling, the hiring pool and the documentation are all built around it, and because the language has absorbed most of what people used to leave for — pattern matching, records, immutability by default in modern style, and now unions in C# 15. F# is a genuinely better fit for a bounded piece of work that is heavily about data transformation, domain modelling with discriminated unions, or computation over immutable structures, and it interoperates fine, so a single F# library inside a C# solution is a reasonable choice when a team member can maintain it. VB.NET I would only meet in maintenance. The consideration that actually decides it in practice is who will support the code in three years: an unusual language choice in one component becomes a bus-factor problem, so I would want more than one advocate before introducing it.

Where do you draw architectural boundaries in a C# solution?

Around things that change for different reasons and are deployed together — which usually means fewer projects than people expect. A separate assembly buys you a compile-time dependency check and nothing else; it does not enforce a boundary at runtime, and a solution with forty projects mostly buys slow builds. So I use projects for genuine reuse and for deployment units, and inside a project I use namespaces plus an architecture test (NetArchTest or ArchUnitNET) to assert the dependency rules, which is faster and more expressive than the project graph. The boundary that really matters is the one where data changes shape: HTTP models, domain types and persistence models should be different types even when they look identical today, because they change for different reasons and coupling them is what turns a small API change into a database migration.

How do you decide whether to take a dependency?

I weigh the cost of writing it against the cost of owning someone else's decisions. A dependency brings its transitive graph, its release cadence, its security posture and its abandonment risk, and every one of those becomes mine at the worst possible moment. So: is it maintained, by whom, and how would I fix a bug in it if I had to? How much of it do I actually use — pulling in a large framework for one helper is usually a bad trade. Does it constrain my runtime, particularly around trimming and native AOT, since reflection-heavy libraries quietly rule those out. And is there a BCL equivalent now — a lot of the classic dependencies have been absorbed: System.Text.Json for Newtonsoft, the built-in DI and logging abstractions, System.Linq.AsyncEnumerable in .NET 10 for the async LINQ package. My bias is toward the platform, because the platform's support timeline is one I already have.

Security

What are the C#-specific security mistakes you look for?

String concatenation into SQL, obviously, but the modern version is subtler: interpolated strings passed to FromSqlRaw in EF Core, where FromSqlInterpolated would have parameterised it correctly. Then deserialisation: BinaryFormatter is removed in .NET 9 for good reason, and any deserializer configured with type-name handling — Newtonsoft's TypeNameHandling.All is the classic — is remote code execution waiting for an attacker. Then secrets: connection strings and keys in appsettings.json, hard-coded IVs, new Random() used for tokens instead of RandomNumberGenerator, and string holding a secret for longer than needed since strings are immutable and stay in memory until collected. Then comparison: == on a token or hash is timing-variable, so CryptographicOperations.FixedTimeEquals is the right call. And culture-sensitive string comparison used for security decisions, which behaves differently under different locales.

How do you handle secrets and configuration in .NET?

Never in source and never in a file that ships. In development, the user-secrets store, which keeps them outside the repository. In production, the platform's secret store — Key Vault, AWS Secrets Manager, Kubernetes secrets — surfaced through a configuration provider so the code just reads IConfiguration or, better, a strongly-typed options object bound at startup with validation via ValidateOnStart, so a missing secret fails the deployment rather than the first request that needs it. I want rotation to be possible without a redeploy, which means the provider must support reload and the consuming code must read through IOptionsMonitor rather than capturing a value at construction. And I would add a secret-scanning check in CI, because the failure mode is not a clever attacker, it is a connection string in a commit from three years ago.

What does unsafe actually risk, and what changes in C# 15?

Today, unsafe is a coarse marker: it is required to declare pointer types at all, so a method that merely takes an address is marked as loudly as one that dereferences arbitrary memory, and reviewers learn to skim past it. The actual risks are the classic memory-safety ones — reading or writing outside a buffer, using a pointer after the underlying object moved because it was not pinned, and type confusion through casts — all of which produce corruption rather than exceptions. C# 15 begins a multi-release effort to make the marker mean something: the pointer relaxations mean declaring a pointer, taking an address with &, using fixed, converting stackalloc to a pointer and applying sizeof no longer need an unsafe context, while the operations that actually touch the pointed-to memory — dereference, ->, element access, function-pointer invocation — still do. The eventual model adds a "requires-unsafe" flow to callers, an assembly-level opt-in recorded by MemorySafetyRulesAttribute, and a safe keyword for extern members. The point is that unsafe becomes an audit signal that correlates with real risk.

How do you keep a .NET application's dependencies secure over time?

Make it automatic, because manual review does not survive contact with a busy quarter. NuGet audit is built into the SDK and reports known vulnerabilities at restore; I turn those into build failures for direct dependencies and warnings for transitive ones, and I use Central Package Management so a version bump is one line in one file. Dependabot or Renovate opens the pull requests, and the test suite decides whether they merge, which means the test suite has to be good enough to trust — that is the real prerequisite. Beyond CVEs I watch for abandonment, since an unmaintained package with no vulnerability today is a vulnerability with no fix tomorrow. And I generate an SBOM as part of the build, so when the next widely-exploited library lands I can answer "are we affected" in minutes rather than days.

Performance & debugging

Walk me through diagnosing a production memory leak in a .NET service.

First I confirm it is a leak rather than a large cache or normal steady-state growth, by watching working set alongside Gen2 heap size and LOH size over hours, not minutes — a genuine leak grows monotonically and does not fall after a Gen2 collection. Then I capture a dump with dotnet-dump from the running container, ideally two dumps separated by a repeated workload. In the analyser, dumpheap -stat shows which types grew, and gcroot on an instance of the top type shows what is keeping it alive. In my experience the answer is almost always one of four things: an event subscription never removed, so the publisher holds the subscriber; a static or singleton collection that only ever grows; a cache with no size limit or expiry; or a captured closure or timer holding an object graph. The fix is usually small once the root path is visible, and the durable improvement is to add a memory ceiling and an alert on Gen2 growth so the next one is caught in staging.

What is thread-pool starvation and how do you recognise it?

The pool has a small number of threads and injects new ones slowly — roughly one or two per second beyond the minimum — because it assumes threads are only blocked briefly. If code blocks pool threads (a .Result, a lock held across I/O, a synchronous database call inside an async handler), the queue of pending work items grows faster than threads are injected, and latency climbs while CPU stays low. That combination — low CPU, high latency, growing thread count, growing work-item queue — is the signature, and dotnet-counters shows all four. The immediate mitigation is raising ThreadPool.SetMinThreads, which buys time and hides the cause; the fix is removing the blocking. I would also mention that ASP.NET Core does not deadlock the way classic ASP.NET did, so the symptom of sync-over-async on a modern stack is starvation rather than a hang, which is why people who "fixed" it by removing the synchronization context still have the problem.

A service's p99 latency doubled after a deploy. How do you find out why?

I start from the diff and from the telemetry simultaneously. Distributed tracing tells me which span grew — if it is a downstream call, the problem may not be mine; if it is our own processing, it is. Then I check the shapes that produce tail latency specifically rather than mean latency: GC pauses (Gen2 count and pause duration), lock contention, thread-pool queue length, and connection-pool exhaustion, all visible in counters. A doubling of p99 with a flat p50 usually means a new pause or a new queue, not slower code. If the diff includes a query change, I would look for an accidental N+1 or a lost index; if it includes a serialisation change, for a switch from a source-generated context back to reflection. And I would make sure I can roll back while investigating — the first job is to restore the service, and the second is to understand it, in that order.

How do you profile CPU in production without taking the service down?

dotnet-trace attaches to a running process and collects an EventPipe trace with modest overhead, and dotnet-counters gives continuous, essentially free counter data that is usually enough to localise a problem before you need a trace. For a container I make sure the diagnostic tools can reach the process — either a sidecar or the dotnet-monitor tool, which exposes dumps, traces and counters over an authenticated endpoint and is designed exactly for this. I would sample rather than trace continuously, and I would take the trace from one instance rather than the fleet. The habit that saves the most time is having done it once before the incident: knowing that the tooling is installed, the permissions work and the symbols resolve is what turns a two-hour investigation into a ten-minute one.

What are the highest-value performance improvements in typical business code?

Almost never the ones people reach for. In order of what I actually find: the database — an N+1, a missing index, a query loading columns nobody uses, or a transaction held across a network call. Then serialisation and logging — reflection-based JSON on a hot path where a source-generated context would halve it, and string interpolation in log calls that are disabled. Then unbounded concurrency and missing timeouts, which turn a slow dependency into an outage. Then allocation in genuinely hot loops, where spans and pooling pay. Micro-optimising C# — struct versus class, LINQ versus loops — is last, and it usually turns out to be a rounding error next to a single network round trip. The lead-level version of this answer is that I would insist on a profile before any of it, because the intuition of a good engineer is wrong often enough that "measure first" is a policy, not a platitude.

Legacy and migration reality

What patterns will you meet in an old C# codebase, and what do you replace them with?

The common list: ArrayList and Hashtable instead of generics, which box everything; the APM (BeginRead/EndRead) and EAP (event-based) async patterns instead of tasks, wrapped now with TaskFactory.FromAsync; manual IDisposable plumbing with hand-written finalizers where a SafeHandle belongs; DataSet and DataTable in place of typed models; service locators and static Singleton.Instance in place of injected dependencies; DateTime.Now everywhere; and string concatenation in loops. The judgment part is that I do not modernise them on sight. Each replacement is a change with risk and no user-visible benefit, so I do it where I am already working, where the old pattern is actually causing a problem, or where it blocks something — for example, replacing reflection-based serialisation because it blocks trimming. The exception is anything with a security dimension, like BinaryFormatter or a deserializer with type-name handling, which I would treat as urgent regardless of where it sits.

How do you handle a codebase where nullable reference types would produce thousands of warnings?

Not by fixing thousands of warnings. I set Nullable=annotations for the legacy projects, which honours annotations and suppresses warnings, so I can start annotating the public surface of shared libraries and every consumer benefits immediately without a single build break. New projects get Nullable=enable from birth via Directory.Build.props. Then existing files get #nullable enable as they are touched, starting deliberately with boundary types — DTOs, parsing, configuration, anything that maps external data — because annotating an internal leaf while the boundary lies is theatre. Once a project is clean, its nullable warnings become errors so it cannot regress. The metric I report is the fraction of the public surface annotated, not the warning count, because that is the number that correlates with fewer null reference exceptions.

When is a rewrite the right answer?

Rarely, and almost never for the reason given. "The code is bad" is not sufficient, because the ugly code encodes years of edge cases that nobody has written down, and a rewrite discards them and rediscovers them in production. The cases where I would genuinely rewrite: the platform is unsupported and cannot be retargeted — WebForms, WCF server-side, something bound to a dead dependency; the architecture makes a required capability impossible rather than merely hard, such as needing horizontal scale from something with per-node state; or the component is small enough that a rewrite is a two-week job with a clean interface on both sides. Otherwise I strangle: put a new implementation behind the existing interface, route a fraction of traffic, compare outputs, and cut over — which keeps the option to stop at every step. The thing I insist on either way is that "we will rewrite it and also add features" is how rewrites fail, so the first version must be behaviour-identical.

How do you deal with a team split across .NET Framework and modern .NET?

By making the shared code target something both can consume and by treating the split as temporary with a dated plan. netstandard2.0 is still the common denominator for libraries that must be referenced from .NET Framework, and it costs you some modern APIs but keeps one copy of the domain logic instead of two — multi-targeting (net48;net10.0) is the better option where the library can benefit from newer APIs on the modern side, with #if for the differences. I would raise LangVersion on the Framework projects immediately, because most syntax works there and it removes the daily friction of writing in two dialects. And I would make the direction of travel explicit and dated — which services move in which quarter — because an indefinite split quietly becomes permanent, and the cost shows up as duplicated fixes, two build pipelines, and engineers who can only work on one half.

Judgment and scenarios

How would you introduce stricter analysis to a team that finds it annoying?

Start with rules that catch bugs the team has actually been bitten by, and show the evidence. If we had a null reference exception in production last month, the nullable analysis is not a style preference, it is that incident's fix. I would enable a small set of high-value correctness rules as errors, everything else as suggestions, and per-directory so legacy code is not held to the new bar — the goal is that the build only fails for reasons people agree with. Then I would automate the mechanical parts so nobody argues about them: dotnet format in CI, an .editorconfig in the repo, and code fixes that apply on save. And I would let the team veto specific rules, because a rule the team resents will be suppressed anyway and the suppression will be global. Trust here is worth more than coverage: three rules everyone respects beat forty everyone disables.

A junior engineer submits a PR that uses dynamic to simplify some mapping code. What do you do?

I would ask what problem it solved, because the answer tells me whether the issue is the tool or the design. dynamic defers binding to runtime, so it throws away every compile-time check, defeats IntelliSense and refactoring, costs a call-site cache and a binder invocation, and does not work under trimming or native AOT. Almost always the underlying need is either "these types have the same shape" — which generics, an interface or a mapping library solves with checking intact — or "I do not know the shape until runtime", which is a JsonElement or a dictionary, not dynamic. I would say that in the review with a concrete alternative rather than a rule citation, because "we don't use dynamic" teaches nothing. The one place I would accept it is genuine COM or IronPython-style interop, where the alternative is reflection and is worse.

How would you guide a team through adopting C# 15's union types when they arrive?

Slowly, and starting where the payoff is unambiguous. C# 15 ships with .NET 11 in November 2026, so the first step is simply not adopting it in production while it is preview — but prototyping now on a preview SDK with LangVersion=preview is worthwhile, because it tells us where the shape fits. The obvious first target is result-and-error modelling, where today we have a class with a bool and two nullable fields whose invariant nothing enforces; converting one bounded area — say, the validation layer of one service — gives a real comparison. I would pair unions with the closed modifier, since they solve adjacent problems, and I would be explicit about what we are not doing: not rewriting existing result types, not adopting it in shared libraries until GA, and not introducing it in code that a third-party analyzer or serializer has to understand until we have checked that they do. The failure mode with an exciting language feature is uneven adoption, so I would want one documented pattern and one reviewer who knows it well before it spreads.

You inherit a service with no tests and a monthly production incident. What do you do first?

Instrument before I refactor. Without tests I cannot change anything safely, and without telemetry I cannot tell whether a change helped, so the first week is structured logging with correlation ids, traces on every outbound call, and metrics on the paths the incidents touch. Then I write characterisation tests at the outermost boundary — HTTP in, database and downstream out, with the real dependencies faked at the edge — which is unglamorous but gives me a safety net without requiring the internals to be testable. Only then do I start changing code, beginning with whatever the incident data says is actually failing rather than whatever is ugliest. Alongside that, I would put in the cheap operational guards that prevent whole categories of incident regardless of the code: timeouts on every outbound call, bounded concurrency, a circuit breaker, and health checks that fail correctly. The goal for the first month is to stop the bleeding and gain the ability to change things, in that order.

What is the most important thing you look for when hiring a senior C# engineer?

Whether they can explain a mechanism rather than recite a rule. Almost anyone can say "use ConfigureAwait(false) in libraries" or "structs go on the stack"; what I want is the reasoning underneath, because that is what transfers to the problem nobody has written a rule for. Concretely I probe two or three things they claim to know deeply and keep asking "why" until either we reach bedrock or the model breaks, and both outcomes are informative — a candidate who says "I don't know, here is how I would find out" scores better with me than one who improvises confidently. The second thing is judgment about cost: do they talk about what a decision commits the team to, how it fails, and who pays for it, or only about whether it works. Technical depth without that is a very productive engineer who leaves a mess behind, and at senior level the mess is the expensive part.

Ten sentences you can say out loud, in this order, and be right. Each one is a hook you can expand into two minutes if they follow up.

  1. "The current language is C# 14, shipped with .NET 10 on 11 November 2025 — an LTS supported to November 2028, at servicing build 10.0.11. C# 15 and .NET 11 are in preview, Preview 7 landed 11 August 2026, and GA is expected this November." Version fluency in one breath, with dates, is the cheapest credibility you can buy.
  2. "C# 14 is about removing boilerplate: extension blocks that give you extension properties, static members and operators; the field keyword so you never hand-write a backing field again; null-conditional assignment; first-class Span<T> conversions; partial constructors and events." Naming field and extension members is the fastest way to show you have actually used the release, not read about it.
  3. "C# 15 is a much bigger language step: union types and the closed modifier give the compiler a complete set of cases, so a switch is exhaustive without a default arm — the thing .NET has been missing for result and state modelling." Add that closure is not transitive and a closed class is implicitly abstract, and you have said more than the blog posts.
  4. "A variable of a value type contains the instance; a variable of a reference type contains a reference. Where the variable lives decides where the value lives — 'structs are on the stack' is a common case, not a rule." Then the design rule: choose by identity first, size second, and make every struct a readonly struct so defensive copies disappear.
  5. "Nullable reference types are a compile-time analysis over a documentation feature — the runtime does not participate, and string and string? are the same type." Follow with the four holes: deserialisation, default(T) and struct zero values, arrays, and unannotated dependencies. That is why public APIs still call ArgumentNullException.ThrowIfNull.
  6. "async creates no threads. It is a compiler transformation into a state machine, and an async method runs synchronously until its first incomplete await." Then the punchline: async does not reduce latency, it reduces the threads you need to absorb concurrency — and never block on it, because on ASP.NET Core the symptom is thread-pool starvation rather than the classic deadlock.
  7. "Generics in C# are reified, not erased: the JIT compiles a specialised body per value type, so List<int> stores raw ints with no boxing, and typeof(T) works." Add the cost — code size and generic virtual dispatch, which is a known weak spot under native AOT — and the C# 11 payoff, static abstract members and generic math.
  8. "Allocation is cheap; survival is expensive. Gen0 collections cost in proportion to what lives, not what was allocated." So the fixes go in order: allocate less with spans and pooling, keep lifetimes short, and tune the GC last. And anything ≥ 85,000 bytes lands on the LOH, which is not compacted by default — that is the service whose memory never comes back down.
  9. "Every public member is a support commitment, and some changes break consumers silently: a const, a default parameter value and an enum's numbering are all baked into the caller's IL at their compile time." Hence static readonly over const, overloads over new optional parameters, seal by default, and internal until there is a named consumer.
  10. "throw; preserves the stack, throw ex; destroys it, and an exception filter — catch (X) when (…) — runs before the stack unwinds, so it can log with the original frames still live." Then the design half: exceptions are for the exceptional; when failure is a normal outcome, return a value, which is exactly what C# 15's unions make pleasant.
