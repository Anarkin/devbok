01Runtime and compilation model

Docs: Managed execution process · Tiered compilation and PGO · C# language versioning

Everything else in this guide is easier to reason about once you hold the pipeline in your head: source → Roslyn → IL + metadata → assembly → CLR loads it → JIT compiles each method on first call → tiered recompilation makes hot methods fast. C# is not "compiled" or "interpreted": it is compiled twice, once ahead of time to a portable intermediate language and once at run time to native code for the exact CPU it lands on. That second compile is why a .NET binary published in 2025 gets AVX-512 or Arm SVE code paths on a 2026 server without a rebuild, and why the JIT can specialise on things a static compiler cannot know (the concrete type behind an interface call, which branches are actually taken).

Tiering, concretely

When a method is first called the JIT produces tier-0 code in microseconds: no inlining, no register allocation heroics, but instrumented. After 30 calls (or when a loop iterates enough, via on-stack replacement) a background thread produces tier-1 code using the profile. The practical consequences are worth stating in an interview: a micro-benchmark that runs a method once measures the wrong thing; a warm-up phase is real; and a virtual or interface call that always sees one implementation is, after tier-1, as cheap as a direct call plus a type check. .NET 10's JIT added escape analysis that can stack-allocate small objects and arrays that provably never escape the method, plus better devirtualisation of delegates and struct arguments; .NET 11 continues with bounds-check elimination and switch-expression folding. Say "the runtime's optimiser learns at run time" and you have explained why the same code got faster across three releases with no edits.

// What a "simple" call becomes at each tier
interface IShape { double Area(); }
sealed class Circle(double r) : IShape { public double Area() => Math.PI * r * r; }

static double Sum(IShape[] shapes)
{
    double total = 0;
    foreach (var s in shapes) total += s.Area();   // tier-0: real interface dispatch
    return total;                                  // tier-1 with PGO: "if (s is Circle c) inline c.Area() else fallback"
}

Interview trap

"C# is compiled to machine code" / "C# is interpreted" / "the JIT compiles the whole program at startup". All three are wrong in ways an interviewer will pull on. The correct sentence: Roslyn compiles to IL once; the CLR JIT-compiles each method on first call and recompiles hot ones with profile data; ReadyToRun and NativeAOT move some or all of that work ahead of time at the cost of run-time specialisation. Follow-up they love: "so why can NativeAOT be slower in steady state?" — because it cannot use dynamic PGO or guarded devirtualisation informed by real traffic, only static PGO if you ship one.

Try it: watch tiering happen

Create a file-based app (dotnet run tiers.cs) with a loop calling a small virtual method 100 000 times, timing the first 100 calls and the last 100 with Stopwatch. Then run it again with the environment variable DOTNET_TieredCompilation=0 and once more with DOTNET_TieredPGO=0.

Expected outcome

With defaults, the last 100 calls are several times faster than the first 100 (tier-1 kicked in after ~30 calls plus a background compile delay). With tiering off every call pays the full-optimisation JIT cost up front but is uniformly fast, and startup is slower. With PGO off the steady state is a little slower because the interface call is no longer devirtualised. Print System.Runtime.JitInfo.GetCompiledMethodCount() at the end to see how many methods were compiled: with tiering on it is higher (tier-0 plus tier-1 versions).

Try it: cross-version language features

Create a project targeting net8.0, set <LangVersion>14</LangVersion>, and write (a) an extension block with an extension property, (b) a field-backed property, (c) a method with a where T : allows ref struct constraint.

Expected outcome

(a) and (b) compile and run on .NET 8: they lower to plain IL. (c) fails with an error about the target runtime, because allows ref struct needs runtime support that shipped with .NET 9. The lesson: "language version" and "runtime support" are two axes, and the interviewer's real question is whether you know which features live on which.

Interview Q&A

Walk me through what happens between dotnet run and my first line of code executing.

MSBuild restores packages and invokes Roslyn, which parses, binds and lowers the C# into IL and metadata inside an assembly, running analyzers and source generators along the way. The host (dotnet or the apphost) resolves the runtime from runtimeconfig.json, CoreCLR starts, loads the assembly and the framework, and the type loader lays out types as they are touched. Main is JIT-compiled at tier-0 on first call, the same for every method after it; a background thread recompiles anything called 30-plus times with dynamic PGO. So the "first line" executes microseconds after JIT of the entry method, and the program keeps getting faster for the first few seconds of life.

Why did Microsoft build tiered compilation instead of just optimising everything?

Because the two goals conflict: full optimisation costs milliseconds per method, which multiplied over thousands of methods dominated startup, while most methods are called once. Tier-0 makes startup cheap and also instruments the code, which gives the optimiser something a static compiler never has: actual observed types and branch frequencies. Tier-1 then uses that profile to devirtualise, inline and lay out hot paths. The trade-off is warm-up: the first requests of a service run slower, which is why ReadyToRun exists for large apps and why load balancers should not send full traffic to a fresh pod immediately.

When would you choose NativeAOT, and what would you have to give up?

I choose it when startup time or memory footprint is the product: serverless functions, CLI tools, sidecars, high-density containers. You give up the JIT, so no dynamic PGO, no Reflection.Emit, no loading assemblies at run time, and trimming must be able to prove what is reachable — meaning source-generated JSON, DI and regex, and no unbounded Type.GetType(string). On ASP.NET Core that means minimal APIs and gRPC yes, MVC with runtime Razor no. The mitigation is analyzers: turn on IsAotCompatible in the libraries early so warnings appear during development, not at publish.

A team is on .NET 8 and asks whether to go to .NET 9 or .NET 10 this quarter. What do you tell them?

.NET 10 without hesitation, and I would state the reason as dates: .NET 8 and .NET 9 both leave support on 2026-11-10, so moving to 9 buys nothing, while 10 is LTS to November 2028. The upgrade from 8 to 10 is usually mechanical — update the TFM, run the upgrade assistant's analyzers, check for the few breaking changes (BinaryFormatter is gone, some default-behaviour flips in ASP.NET Core). I would also set the expectation that .NET 11 in November is STS, so a service that cannot afford yearly upgrades should stay on 10 and skip 11.

Can we use C# 14 features on a project that targets .NET 8?

Partly, and it is worth understanding the split. Set LangVersion to 14 and anything that is purely a Roslyn lowering works — extension members, the field keyword, null-conditional assignment, unbound nameof. Anything that needs a runtime type or JIT support does not: first-class span conversions partially rely on newer BCL overloads, allows ref struct needs .NET 9, and the C# 15 unions need the IUnion types that arrive with .NET 11. My rule for a team is: do not set LangVersion manually in production code; the unsupported combination is a support-policy grey zone and the target framework already tells you the right version.

What is dynamic PGO and what is a "guarded devirtualisation"?

Profile-guided optimisation means the optimiser uses measured behaviour rather than guesses. Dynamic PGO, on by default since .NET 8, gathers that profile in tier-0 code at run time: which branches are taken, which concrete types show up at each virtual or interface call site. Guarded devirtualisation is the JIT emitting "if the object's type is exactly Circle, run the inlined Circle.Area, else fall back to the virtual call". It is why interface-heavy, DI-shaped code is cheap in modern .NET, and why the classic "virtual calls are slow, seal your classes" advice has shrunk to "sealing still helps a bit, and helps AOT more".

How does .NET Framework fit in a modern estate, and what is genuinely stuck there?

.NET Framework 4.8.1 is a Windows component: it gets security fixes with Windows but no new features, its compiler support stops at C# 7.3 officially, and it never gets Span-based APIs, the modern GC or tiered PGO. Genuinely stuck are WCF servers (CoreWCF is the migration path), Web Forms (no path; rewrite), Workflow Foundation, and anything relying on AppDomains or COM+ services. The pragmatic strategy is strangler-fig: put new endpoints in .NET 10, share code through netstandard2.0 libraries during the transition, and treat the Framework host as read-only.

What does ReadyToRun actually give you and when does it not help?

R2R embeds pre-JITted native code alongside the IL so the first call to a method skips tier-0 compilation; the runtime still treats that code as tier-0-equivalent and re-JITs hot methods with PGO, so steady state is unchanged. It helps large applications with long startup and cold-start-sensitive services. It does not help a tight service that is already warm, it grows the binary, and it is platform-specific, so multi-RID publishing costs build time. In containers I usually combine R2R with tiered PGO and let the JIT do the rest.

How would you explain file-based apps and where do they belong in a team?

Since .NET 10, dotnet run script.cs compiles and runs a single file, with #:package Foo@1.2 and #:sdk directives for dependencies and dotnet publish support including NativeAOT; .NET 11 adds #:include so a script can grow to a few files before it graduates. They belong where we used to write PowerShell or Bash for build steps, data fix-ups and one-off migrations: same language, same libraries, same tests, and dotnet project convert turns one into a real project when it gets serious. The judgement call is not to let a 500-line "script" avoid the review and CI a project would get.

What is Roslyn's role beyond being "the compiler", and why does that matter architecturally?

Roslyn is a compiler-as-a-service: the same immutable syntax trees and semantic model the compiler uses are exposed to analyzers, code fixes, source generators and the IDE. That is why an architecture rule (no DateTime.Now, no synchronous I/O in request paths) can be an analyzer shipped as a NuGet package and enforced at build time with TreatWarningsAsErrors, and why serialisation, DI registration, regex and P/Invoke bindings moved from run-time reflection to compile-time generation — which is the enabler for NativeAOT. A principal-level answer connects the three: Roslyn's design made generators possible, generators made trimming feasible, trimming made AOT viable.

02Types: values, references, records

Docs: Value types · Records · ref struct

The single most productive mental model in C# is that a variable of a value type is the bits; a variable of a reference type is a pointer to bits that live on the managed heap. Every rule about copying, mutation, equality, boxing, null, defaults and memory layout falls out of that one sentence. A struct assigned to another variable is copied in full; a class instance assigned shares identity. A struct passed to a method is copied unless you say in, ref or ref readonly; a class passes a copy of the reference, which is why "objects are passed by reference" is a phrase to avoid — the reference is passed by value, and ref on a reference-type parameter means something different (the callee can re-point the caller's variable).

struct Point { public int X, Y; }
class Node  { public int Value; }

var p1 = new Point { X = 1 };  var p2 = p1;  p2.X = 99;   // p1.X is still 1: a copy
var n1 = new Node  { Value = 1 }; var n2 = n1; n2.Value = 99; // n1.Value is 99: shared identity

static void Reset(Node n) => n = new Node();          // caller's n1 unchanged: the reference was copied
static void Reset(ref Node n) => n = new Node();      // caller's variable now points at the new object

Where values live (and the myth to retire)

"Structs live on the stack, classes on the heap" is half true and interviewers know it. A struct lives wherever its container lives: a local struct is on the stack (or in a register), a struct field of a class is inline inside that heap object, a struct in a List<T> is inline in the list's backing array on the heap, and a struct captured by a lambda is hoisted into a heap-allocated closure class. Boxing is the act of copying a struct into a fresh heap object so it can be treated as object or an interface: it costs an allocation, and the box is a copy, so mutating through the box never touches the original. The classic gotchas — calling an interface method on a struct, putting a struct in an ArrayList, string formatting with object parameters, Equals(object) — are all boxing in disguise. Generics exist largely to avoid it: List<int> stores ints inline; IList<int>.Contains through the interface does not box the element, but ((IComparable)5).CompareTo does.

Choosing and designing structs

The official guidance is still good: use a struct when the type is small (the "16 bytes" rule of thumb is about copy cost), logically a single value, immutable, and short-lived or stored in bulk. Modern C# gives you the modifiers to make that intent enforceable:

Records: equality by value, identity by reference

A record class is a reference type whose compiler-generated Equals, GetHashCode, ToString, deconstructor and with-cloning treat it as a value: two records with equal fields are equal even though they are two heap objects. Positional syntax (record Person(string Name, int Age)) generates init-only properties from the primary constructor. Records solve the DTO/message/event problem — you want cheap, correct equality and non-destructive mutation — and they were deliberately not made "value types" because most DTOs are larger than a struct should be and often live in collections that expect reference semantics. The design tension you should be able to articulate: a record's equality includes every field, including collections compared by reference, and inheritance interacts with equality through the synthesised EqualityContract so that a Student : Person never equals a Person with the same name.

public record Person(string Name, int Age)
{
    // Positional records can add validation and extra members
    public string Name { get; init; } = Name ?? throw new ArgumentNullException(nameof(Name));
}

var a = new Person("Ada", 36);
var b = a with { Age = 37 };          // non-destructive mutation: shallow clone + init
Console.WriteLine(a == b);           // False: Age differs
Console.WriteLine(a == a with { });  // True: same values, different object
var (name, age) = b;                 // synthesised Deconstruct

public readonly record struct Money(decimal Amount, string Currency)
{
    public static Money operator +(Money l, Money r) =>
        l.Currency == r.Currency ? l with { Amount = l.Amount + r.Amount }
                                 : throw new InvalidOperationException("currency mismatch");
}

Class design: primary constructors, sealed, and the modern defaults

C# 12 brought primary constructors to classes and structs; unlike records they generate captured parameters, not properties, so class Service(ILogger log) stores log as a private field only if a member uses it — and a common code-review catch is a primary-constructor parameter that is also assigned to a field, creating two copies. Mark classes sealed unless designed for inheritance: it enables devirtualisation, documents intent, and makes is/type checks cheaper. Prefer composition; when you do inherit, follow the virtual/override/abstract rules and never call virtual members from a constructor (the derived object is not yet initialised). Equality: implement IEquatable<T> and override GetHashCode together, or use a record and let the compiler do it correctly.

Interview trap

The mutable struct in a collection. list[0].X = 5 does not compile for a List<Point> (the indexer returns a copy, and the compiler refuses to let you mutate a temporary), but foreach (var p in list) p.X = 5; also fails, and dict["k"].Count++ silently increments a copy that is thrown away. Arrays are the exception: arr[0].X = 5 works because array elements are variables. Candidates who say "make the struct immutable" get the point; candidates who explain why (indexers return values, arrays return references, CollectionsMarshal.AsSpan(list) gives you the array back) get the senior mark.

Gotcha

Record equality is deep for values, shallow for references. record Order(List<Line> Lines) compares Lines by reference, so two orders built from identical data are unequal, and with shares the same list between copies — mutation through one affects the other. Fix with an ImmutableArray<Line>/ImmutableList (which still compare by reference unless you override) or an explicit Equals. The honest sentence: records give you structural equality over the members as they are, nothing recursive.

Try it: break value semantics on purpose

Write a mutable struct Counter { public int N; public void Inc() => N++; }. Store it in a List<Counter>, an array, a Dictionary<string, Counter>, a readonly field of a class, and behind an IIncrement interface reference. Call Inc() once through each and print N.

Expected outcome

Array: 1 (element is a variable). List and dictionary: 0 (indexer returned a copy). Readonly field: 0 in C# 8+ (defensive copy; older compilers gave the same result with no warning). Interface reference: the boxed copy is 1 but the original struct is 0; calling Inc() twice through the same boxed reference gives 2, because you are mutating the box. Now add readonly to the struct: every mutation becomes a compile error, which is the lesson.

Try it: record equality edge cases

Declare record Person(string Name) and record Employee(string Name, string Dept) : Person(Name). Compare new Person("A") == new Employee("A", "X"), then cast the employee to Person and compare again. Then add a List<string> Tags property to Person and compare two persons built with identical tag lists.

Expected outcome

All three comparisons are false. The first two because the synthesised EqualityContract property returns the runtime type, so a derived instance is never equal to a base instance even through a base-typed variable; the third because List<string> is compared by reference. Overriding Equals to use SequenceEqual fixes the third but you must also override GetHashCode consistently, and once you override either on a record the with expression still clones shallowly.

Interview Q&A

Explain value types versus reference types the way you would to a strong junior.

A value-type variable holds the data itself; a reference-type variable holds the address of data on the managed heap. Assigning a value copies the data; assigning a reference copies the address, so two variables now name the same object. Everything downstream follows: structs default to all-zero bits rather than null, structs are copied into method parameters unless you use in/ref, and converting a struct to object or an interface has to allocate a heap copy — boxing. The word I would ask them to retire is "passed by reference" for objects: the reference is passed by value, and ref is a separate concept that lets a callee reassign the caller's variable.

When do you choose a struct over a class, and what modern modifiers change that decision?

A struct when the type is a small (say up to 16–24 bytes), immutable, single logical value that is created in bulk or on hot paths: coordinates, money, IDs, timestamps. readonly record struct is the modern spelling because it gives correct equality and blocks accidental mutation, and in parameters remove the copy cost of passing larger ones. I reach for ref struct only for types that wrap memory that must not escape, like Span<T> or a stack-based builder. The counter-signal is anything that needs identity, inheritance, or gets stored in interface-typed collections: that is a class, and boxing a struct to fit will cost more than the class would.

What is boxing, where does it hide, and how do you find it?

Boxing allocates a heap object to hold a copy of a value type when it is converted to object, ValueType, Enum or an interface it implements. It hides in string formatting with object parameters (interpolated strings avoid it since C# 10 via handlers), in calling non-generic collections, in Equals(object) on structs that do not implement IEquatable<T>, in enum-keyed dictionaries without a comparer on older frameworks, and in LINQ over structs through interfaces. I find it with the allocation view in a profiler (dotTrace, PerfView, dotnet-trace with the GC allocation tick events) or by looking for box instructions in the IL via sharplab; BenchmarkDotNet's [MemoryDiagnoser] makes it a number per operation.

Records versus classes versus structs: give me the decision rule.

Data whose meaning is its contents — messages, DTOs, events, configuration snapshots, value objects — is a record, because equality, hashing, ToString and with come for free and are correct. Data with identity and behaviour — entities, services, anything with a lifecycle — is a class, usually sealed. Small hot values are readonly record struct. The subtle part is the boundary: an EF Core entity should not be a record (identity plus change tracking versus value equality is a mismatch), and a record with a mutable collection has surprising equality, so I keep records shallow and immutable all the way down or override Equals deliberately.

What does a with expression actually do, and what is its trap?

It calls the compiler-generated copy constructor (protected Person(Person original)) which copies every field, then applies the initializers to init properties on the copy. It is a shallow clone: reference-typed members are shared, so order with { Id = 2 } shares the same Lines list, and mutating it mutates both. Second trap: because the copy constructor is a virtual-dispatch pattern (<Clone>$), with on a base-typed variable produces the runtime type, which is what you want, but a hand-written Equals or copy constructor in a derived record must call the base to keep that working.

Why can a ref struct not be used in an async method, and what did C# 13 change?

An async method's locals are hoisted into a state-machine object that lives on the heap and outlives any individual stack frame; a ref struct like Span<T> may hold a pointer into a stack frame, so letting it survive across an await would leave a dangling reference. The compiler forbids it. C# 13 relaxed the rule so a ref struct local is allowed in an async method as long as it does not live across an await (and similar for iterators), and added allows ref struct so generic APIs can accept spans. The pattern in practice is: do the async I/O into a Memory<T>, then slice a Span from it synchronously.

How are strings special, and what is interning?

string is a sealed reference type with value-equality semantics baked into ==, immutable, UTF-16, with a length prefix and a null terminator for interop. Immutability is what makes it safe to share, hashable, and usable as a dictionary key, and why every "modification" allocates — the reason StringBuilder, string.Create, interpolated string handlers and Span<char> parsing exist. Interning is the runtime's table of literal strings: two identical literals in code are the same object, but strings built at run time are not interned unless you call string.Intern, which is why ReferenceEquals on strings is a bug except in the intern-table optimisation of a parser.

What does default mean for a struct, and why is it a design constraint?

Every struct has an implicit all-zero state that the runtime can create without running any constructor: default(Money), an uninitialised array element, a missing dictionary value. Since C# 10 structs may declare parameterless constructors and field initializers, but default still bypasses them. So a struct must be valid when all its bits are zero: Guid.Empty, TimeSpan.Zero, an ImmutableArray whose default is a "not initialised" state that throws on use. In code review I flag structs whose invariant requires a non-null reference field: that field will be null in the default instance and the invariant is a lie.

Primary constructors on classes: what do they generate and what do you flag in review?

On a class or struct they generate captured parameters, not properties: the parameter becomes a compiler-named private field only if some member reads it after construction; otherwise it is just constructor scope. Records are different — positional parameters become public init properties. What I flag: a parameter assigned to a field and used elsewhere, which stores it twice; a parameter that is mutated in a method, which silently makes it a mutable field; and validation that people forget because there is no constructor body — the fix is a field initializer that validates, or a static factory. For DI-heavy services they are a clear win, ten lines of boilerplate gone per class.

How do you implement equality correctly on a class, and what goes wrong when people do it by hand?

Override Equals(object), implement IEquatable<T> with the real logic, override GetHashCode using HashCode.Combine over the same members, and overload ==/!= if callers expect them, handling null on both sides. What goes wrong: hash code inconsistent with equality (dictionary lookups fail after an "equal" object is inserted), equality that includes a mutable member used as a dictionary key (the object moves buckets when it changes), == comparing references while Equals compares values, and derived classes breaking symmetry. That list is exactly why records exist, and my review comment is usually "make it a record, or explain why you need identity".

03Memory, GC and the allocation budget

Docs: GC fundamentals · Memory and spans · GC configuration

The garbage collector is a generational, compacting, mostly-concurrent tracing collector, and the mental model that makes every tuning decision derivable is the generational hypothesis: most objects die young, so collect the young ones often and cheaply, and the old ones rarely. Allocation itself is almost free — bumping a pointer in the thread's allocation context — which is why "allocations are expensive" is the wrong sentence. The right one is allocations are cheap; surviving allocations are expensive, because every object that is still referenced when a collection happens has to be traced, possibly copied, and promoted, and every promotion makes the next collection of the older generation more likely and more costly.

The allocation-avoidance toolkit

Span<T> and ReadOnlySpan<T> are the centre of modern high-performance C#: a ref struct holding a pointer and a length over any contiguous memory — an array, a slice of one, stack memory from stackalloc, native memory, or a string. Because a span cannot escape the stack (unit 02), the runtime can hand out views into the stack safely, which is what lets parsing, formatting and slicing happen with zero allocations. Memory<T> is the heap-safe sibling for async code; ArrayPool<T>.Shared rents buffers instead of allocating LOH arrays; string.Create and interpolated string handlers build strings in one allocation; and C# 14's first-class span conversions mean an array converts implicitly to ReadOnlySpan<T> in more places, including as an extension-method receiver, so span-taking overloads win overload resolution naturally. On top of all this, .NET 10's JIT can stack-allocate small non-escaping objects and arrays outright — so a new int[4] that never leaves a method may not touch the heap at all, but you cannot rely on it across inlining boundaries, so the explicit toolkit still matters.

Deterministic cleanup: IDisposable, using, finalizers

The GC manages memory; it knows nothing about file handles, sockets, database connections or GPU buffers. IDisposable is the contract for releasing those deterministically, and using (statement or C# 8 declaration) is the syntax that guarantees Dispose runs even on exceptions. Finalizers (~Type()) are the last-resort safety net that runs on a dedicated thread after the object is found dead — non-deterministic, costly (finalizable objects survive one extra collection), and never a substitute. The modern rule: wrap native handles in SafeHandle (which has the finalizer for you), implement IDisposable on anything that owns a disposable, implement IAsyncDisposable when disposal does I/O, and write the full "dispose pattern" with Dispose(bool) only when you own unmanaged resources directly. Leaks in managed code are almost always rooted references: static caches, event handlers on long-lived publishers, captured closures in timers, and un-disposed CancellationTokenRegistrations.

public sealed class Session : IAsyncDisposable
{
    private readonly SqlConnection _conn;           // owns it
    private readonly CancellationTokenRegistration _reg;
    private bool _disposed;

    public Session(SqlConnection conn, CancellationToken ct)
    {

    {

        _disposed = true;
        await _reg.DisposeAsync();                  // unregister: otherwise the token roots this object
        await _conn.DisposeAsync();
    }

}

Interview trap

"Call GC.Collect() to fix memory pressure" and "set the reference to null so it can be collected". Forcing a collection promotes everything alive into gen 2 and makes the next real collection worse; the only defensible uses are benchmarks and a known idle point after a huge batch. Nulling a local achieves nothing in optimised code — the JIT already knows a variable's last use and treats it as dead (which is also why a debugger can show "optimised away" locals). The senior answer to memory pressure is: take a dotnet-gcdump, look at what is rooting the largest retained graphs, fix the root. Then, and only then, consider GC settings.

Gotcha

Events are the number one managed leak. publisher.Changed += subscriber.OnChanged stores a delegate holding a strong reference to subscriber inside publisher. If the publisher is long-lived (a static, a singleton service, the application object) every subscriber lives as long as it does. The fix is symmetric unsubscribe in Dispose, a WeakEventManager, or a design that does not need the event (an IObservable with subscription tokens, or a channel).

Interview Q&A

Explain generational garbage collection and why it is designed that way.

The heap is split by object age because empirically most objects die young: temporaries, request-scoped state, iterator objects. Collecting gen 0 only has to trace from the roots into the young region, and its cost scales with how much survived rather than how much was allocated, so a gen-0 GC can be a fraction of a millisecond even after allocating megabytes. Survivors are promoted, and gen 2 is collected rarely and, where possible, concurrently with the application. The design is a bet: it is cheap as long as your allocation pattern respects the hypothesis, and it degrades when mid-lived objects — things that survive a few collections then die, like per-request caches with a minute's TTL — leak into gen 2 and make full collections frequent.

Server GC versus Workstation GC, and what did DATAS change?

Workstation GC uses one heap and prioritises responsiveness; server GC uses one heap and one dedicated GC thread per logical core, collecting in parallel, which maximises throughput at the cost of a larger memory footprint and slightly longer individual pauses. ASP.NET Core defaults to server GC. The historical problem was that server GC sized itself for the whole machine even when the process was idle, which is hostile in containers. DATAS, on by default for server GC since .NET 9, adapts the number of heaps and the gen-0 budget to the live workload, so memory tracks demand. The practical effect: fewer "why is my idle pod using 3 GB" tickets, and a new answer when someone asks whether to switch to workstation GC in containers — measure first, DATAS may already have solved it.

What is the Large Object Heap and how do you keep it from hurting you?

Objects of 85 000 bytes or more — in practice arrays and large strings — are allocated directly into the LOH, which is collected only with gen 2 and, by default, not compacted, so repeated allocate-free cycles fragment it and trigger expensive full collections. You keep it quiet by not allocating large arrays per operation: rent from ArrayPool<T>.Shared, use RecyclableMemoryStream instead of MemoryStream for large payloads, stream instead of buffering whole responses, and size StringBuilders and lists up front when you know the size. GCSettings.LargeObjectHeapCompactionMode lets you compact once at a quiet point, and the threshold is configurable, but both are band-aids over an allocation pattern.

What is Span<T>, why is it a ref struct, and when do you use Memory<T> instead?

A span is a length-checked view over contiguous memory of any origin — array, slice, stackalloc, native, string — with no allocation for the view itself. It is a ref struct because it may point into a stack frame, so it must not outlive the frame: no boxing, no fields in classes, no capture in lambdas, no surviving an await. That restriction is precisely what makes the stack-pointing case safe. Memory<T> is the heap-only version that can be stored and passed to async APIs; you call .Span on it at the point of synchronous work. The rule of thumb: synchronous parsing and formatting take spans, I/O signatures take Memory, and public APIs offer ReadOnlySpan<T> overloads so callers are not forced to allocate arrays.

How do you diagnose a memory leak in a production .NET service?

First confirm it is a leak and not a large working set: dotnet-counters on the GC heap size and gen-2 count over an hour; a leak grows across full collections, pressure does not. Then capture dotnet-gcdump twice, some minutes apart, and diff the object counts by type; the growing type is the symptom, and its retention path to a root is the cause. The roots are nearly always static caches without eviction, event subscriptions on long-lived publishers, timers and CancellationTokenRegistrations never disposed, or a scoped service captured by a singleton through DI. For a hard case I take a full dotnet-dump and use dumpheap -stat and gcroot. The fix is structural; GC settings never fix a leak.

When do you implement a finalizer, and what does implementing one cost?

Almost never in application code: only when the type directly owns an unmanaged resource that no SafeHandle subclass already wraps, and then the finalizer only releases that resource and never touches other managed objects, which may already be finalized. The cost is real: finalizable objects are put on the finalization queue at allocation, survive at least one extra collection, are processed by a single finalizer thread, and delay their memory's reclamation. The modern shape is a SafeHandle for the native part — it has the finalizer, handles reference counting during P/Invoke, and is AOT- and trimming-friendly — and a plain IDisposable on the class that uses it.

What does IDisposable guarantee, and how does DI complicate it?

It is a convention, not a guarantee: calling Dispose releases resources now instead of whenever the GC notices; nothing enforces the call except using and analyzers like CA2000. In DI the container owns disposal: services resolved from a scope are disposed when the scope ends, singletons when the container is disposed, and transient disposables resolved from the root provider are held until shutdown — the classic leak. So my rules are: never resolve disposable transients from the root, do not dispose injected dependencies you did not create, and use IAsyncDisposable plus await using when the cleanup does I/O, because a sync Dispose that blocks on async work is a deadlock waiting for its moment.

Explain stackalloc and when it is dangerous.

stackalloc T[n] reserves n elements on the current stack frame and, since C# 7.2, can be assigned to a Span<T> without unsafe. It is ideal for small, bounded scratch buffers — formatting a number, hashing a key — because there is no allocation and no GC involvement. It is dangerous when n comes from input: stack frames are around 1 MB on the main thread and smaller on thread-pool threads, and a stack overflow cannot be caught. The idiom is n <= 256 ? stackalloc byte[n] : ArrayPool<byte>.Shared.Rent(n), and never in a loop, because the memory is only reclaimed when the method returns.

What did .NET 10's escape analysis change about the "avoid allocations" advice?

The JIT can now prove that certain small objects and arrays never escape the method — not stored in a field, not returned, not passed to something that keeps them — and allocate them on the stack instead of the heap, so some closures, small arrays and boxed values that used to be gen-0 garbage are now free. It changes the advice from "never allocate in hot paths" to "measure": a benchmark on .NET 10 may show zero allocations for code that allocated on .NET 8. What it does not change is anything that escapes — collections, DTOs, strings returned to the caller — and it is fragile under inlining decisions, so the explicit toolkit (spans, pooling, struct enumerators) remains the way to guarantee the numbers.

Your service shows periodic 300 ms latency spikes every few minutes. Where does GC fit in your investigation?

Periodic spikes at that scale smell like blocking gen-2 collections, so I correlate first: dotnet-counters for gen-2 count and "% time in GC", or the GC events in a dotnet-trace against the latency timestamps. If they line up, the question becomes why gen 2 is large or fragmented: LOH churn from per-request large arrays, a cache that promotes everything, or mid-lived objects. Fixes in order of leverage: stop the LOH churn with pooling, bound the cache, and only then consider GCConserveMemory or switching concurrent settings. If they do not line up, GC is exonerated and I look at thread-pool starvation, lock convoys or a downstream dependency — and I say that explicitly, because blaming the GC without the counters is the junior move.

04Nullability and object initialization

Docs: Nullable reference types · required · field keyword (C# 14)

Nullable reference types (C# 8, on by default in every project template since .NET 6) are the most misunderstood feature in day-to-day C#, and the misunderstanding is always the same: people think they changed the runtime. They did not. NRT is a static analysis with annotations, enforced as warnings, that lets the compiler track "could this be null" through your code. string now means "never null here", string? means "maybe null", and the compiler maintains a null-state per variable that flows through checks, assignments, pattern matches and annotated APIs. At run time both are the same System.String; the annotations are metadata attributes. That is why NRT can be adopted incrementally with #nullable directives, why a nullable-oblivious library's return values are treated as "unknown", and why the guarantees stop at the boundary of anything that produces objects without running your code — deserializers, EF Core materialisation, reflection, default(T) — which is exactly where required comes in.

Flow analysis and the annotation vocabulary

The compiler tracks state, not types. After if (s is null) return;, s is not-null in the rest of the method even though its declared type is string?. The vocabulary that lets library authors participate in that analysis is the System.Diagnostics.CodeAnalysis attributes: [NotNullWhen(true)] on TryParse-style out parameters, [MaybeNullWhen(false)] on TryGetValue, [NotNull] on a parameter that a guard method throws for, [MemberNotNull(nameof(_field))] on an initialising helper, [return: NotNullIfNotNull(nameof(input))]. Generics are the sharp edge: an unconstrained T may be a nullable reference or a value type, so T? on an unconstrained type parameter means "default(T) is allowed" rather than Nullable<T>, and [MaybeNull] is how FirstOrDefault is annotated. The null-forgiving ! is a statement to the compiler, not to the runtime; in review, every ! needs a comment or it is a bug that has not happened yet.

Why required exists and how it interacts with everything

Before C# 11, "this property must be set" had exactly one enforceable spelling: a constructor parameter. That fights object initializers, records with many optional members, and serializers. required moves the obligation to the initializer: the compiler refuses new Customer { } without Name, and a constructor that does set everything declares [SetsRequiredMembers] to lift the obligation. System.Text.Json honours it (missing required property → JsonException) since .NET 7, and the C# 14 field keyword completes the picture: you can now validate or normalise inside an auto-property without demoting it to a manual one. The subtle rule is that required is enforced by the compiler at the construction site, so reflection, Activator.CreateInstance and older serializers bypass it, and the property will be null despite the non-nullable annotation — which is the NRT boundary problem again, and why deserialization DTOs deserve required plus a validation pass, not blind trust.

Interview trap

"Nullable reference types make null impossible." They make it visible. A non-nullable string property is null if the object came from a deserializer with a missing field, from EF Core with a NULL column, from default(T) in a generic, from an array (new string[3] is three nulls), or from any assembly compiled without NRT. The interviewer wants to hear "warnings, not runtime checks; guard at the boundary; required for construction; ! only with a reason". Bonus mark for knowing that NRT can be turned into errors with <WarningsAsErrors>nullable</WarningsAsErrors> and that this is the setting to switch on for new code, not TreatWarningsAsErrors for everything.

Gotcha

Nullable<T> and T? on reference types are different things with the same syntax. int? is a real struct with HasValue/Value, boxing to either null or a boxed int, lifted operators (null + 1 is null, null == null is true but null < 1 is false), and it costs an extra byte plus padding. string? is string plus an attribute. In generics, T? with where T : struct is Nullable<T>; without the constraint it is "maybe default". Candidates who mix these up in a generic repository method produce an API that is wrong for value types.

Interview Q&A

What do nullable reference types actually change, and what do they not?

They change the compiler: with #nullable enable, reference types are non-nullable by default, ? marks the ones that may be null, and flow analysis tracks null-state through checks and assignments, warning where you dereference a maybe-null value or assign null to a non-nullable target. They do not change the runtime at all: no checks are inserted, string and string? are the same type, and null can still arrive from deserialization, ORMs, reflection, arrays and oblivious libraries. So the feature's value is proportional to how seriously you treat the warnings and how carefully you guard boundaries; my teams run WarningsAsErrors=nullable on new code and treat ! as needing a justification in review.

How do you introduce NRT into a large legacy codebase without a big-bang?

Enable it project by project, leaf libraries first, and inside a project file by file with #nullable enable at the top, so the warning count stays actionable. Annotate public APIs first because they propagate the most information to callers. Prefer [NotNullWhen], [MaybeNull] and [MemberNotNull] over ! so the fixes are truthful rather than silencing. Keep a metric — warning count per project — on the dashboard so it trends to zero, and flip WarningsAsErrors=nullable when it gets there so it stays. The mistake I have seen is enabling it solution-wide with 4 000 warnings: everyone learns to ignore the warning pane, which is worse than not enabling it.

Explain required versus constructors versus init. When is each the right tool?

init says "settable only during construction" and gives you immutability with initializer syntax. required adds "and the initializer must set it", which is the enforcement constructors used to provide, without a parameter list. A constructor remains the right tool when an invariant spans several members — start must be before end — or when construction needs computation; a static factory when it can fail. My default for DTOs, options and messages is required init properties; for domain entities with invariants, a constructor or factory plus private setters; and I mark constructors that satisfy everything with [SetsRequiredMembers] so the two styles coexist.

What is the C# 14 field keyword and what problem does it solve?

Inside a property accessor, field refers to the compiler-generated backing field, so you can write a validating setter or a lazy getter while keeping the property an auto-property: set => field = value ?? throw ..., get => field ??= Build();. Before, adding any logic forced you to declare the field yourself, which meant a second name, a second place to initialise, and the option for other members to bypass the property and touch the field. It also makes the INotifyPropertyChanged pattern three lines. The breaking-change footnote: a type that already has a member named field must write @field or this.field; the compiler warns.

What is null-conditional assignment and why did it take until C# 14?

customer?.Order = value; assigns only when customer is non-null and, importantly, does not evaluate the right-hand side otherwise — it lowers to if (customer is not null) customer.Order = value;. Compound assignment works too (a?.Count += 1), but ++ and -- are excluded because their result-value semantics become ambiguous. It took this long because the original null-conditional operator was defined as an expression producing a value, and assignments on its left-hand side needed a language change to define what the expression's value is when short-circuited. The review point: it is convenient for optional collaborators, and a smell when it hides a value that should never be null.

How does NRT interact with generics, and what goes wrong in a generic repository?

For an unconstrained T, the compiler cannot know whether T is a reference or value type, so T? means "may be default(T)" rather than Nullable<T>, and where T : struct flips it to the real nullable struct. A typical bug is T? FindById(int id) intended to return null for "not found": for T = int it returns 0, not a nullable int, and for a class it works — the API silently means different things per instantiation. The fixes are where T : class to say what you mean, a bool TryFind(int id, [MaybeNullWhen(false)] out T value) shape, or an explicit result type. Annotations like [MaybeNull] and [NotNullIfNotNull] exist precisely because the type system alone cannot express these.

What is the cost of Nullable<T> and where does it surprise people?

It is a struct of T plus a bool, padded to T's alignment, so int? is 8 bytes and long? is 16 — a real cost in large arrays and in columns of a data structure. Boxing a null nullable gives a null reference, and boxing a value gives a boxed T, not a boxed Nullable<T>, which is why object o = (int?)5; o is int is true. Lifted operators surprise: comparisons with null are false, equality with null is true, and arithmetic propagates null. In EF Core and JSON, int? maps cleanly to NULL, which is why it remains the right representation for optional value data despite the padding.

What do you do about the = null!; initializers all over an EF Core or DTO project?

They are the recognised workaround for "the framework will populate this after construction, trust me", and in EF Core's case Microsoft's own docs suggested it for years. I accept them where the framework genuinely guarantees the value — a required navigation loaded with Include, a non-nullable column — and replace them with required where the object is constructed by our code or by System.Text.Json, because that turns silent nulls into boundary errors. For navigation properties I prefer string?/nullable navigations with an explicit "was it loaded" check, since a non-nullable navigation that was not included is exactly the null the annotation promised could not happen.

How do you design a public API surface so callers get maximum benefit from NRT?

Annotate everything: return types as non-nullable unless null is a meaningful result, parameters as nullable only when null is a valid input, and use the attributes to describe conditional behaviour — [NotNullWhen(true)] on try-methods, [DoesNotReturn] on throw helpers, [MemberNotNull] on initialisers, [NotNullIfNotNull] on pass-throughs. Ship with <Nullable>enable</Nullable> so the metadata is emitted; an oblivious library gives callers nothing. Avoid returning null for "empty" collections — return the empty collection. And treat a change from non-nullable to nullable on a return type as a breaking change, because it is one for every caller compiled with warnings as errors.

When would you still throw ArgumentNullException if the compiler says the argument is non-nullable?

On every public API boundary, because the annotation is a promise made by callers who may be compiled without NRT, using reflection, or passing values from an oblivious source. ArgumentNullException.ThrowIfNull(x) is a one-liner, the throw is out-of-line so it does not hurt inlining, and the failure is at the boundary with the parameter name rather than a NullReferenceException ten frames deeper. Inside a private or internal method of a fully-annotated assembly I skip the guard: the compiler is the guard there, and redundant checks train people to distrust the annotations.

05Generics, interfaces and polymorphism

Docs: Generics · Interfaces · Generic math and static abstract members

C# generics are reified: unlike Java's erasure, List<int> and List<string> are distinct types at run time with distinct native code, and typeof(T) inside a generic method is the real type. The runtime shares one native compilation for all reference-type instantiations (they are all pointer-sized, so List<string> and List<object> share code and use a hidden dictionary for type lookups) and generates a specialised compilation for each value-type instantiation. This one design decision explains the performance folklore: List<int> stores unboxed ints and its Add is specialised; a generic method with a struct type argument constrained to an interface calls interface methods without boxing and with the call devirtualised; and passing a struct comparer (where TComparer : struct, IComparer<T>) rather than an interface reference is the trick the BCL uses to make sorting and hashing inline. The cost is code size and JIT time per value-type instantiation, which NativeAOT has to pay up front.

Variance: why IEnumerable<string> is an IEnumerable<object> and List<string> is not

Covariance (out T) lets an interface that only produces T be treated as producing a base type; contravariance (in T) lets an interface that only consumes T accept a derived type. List<T> both consumes and produces, so it is invariant: if List<string> were a List<object>, you could Add(42) to it. Variance applies to interfaces and delegates only, and only to reference-type arguments — IEnumerable<int> is not an IEnumerable<object> because that conversion would require boxing each element. Arrays are covariant for historical reasons (string[] is an object[]), with a run-time check on every store into a reference-type array to keep it sound — a small cost you can avoid with generics, and a trivia question that reveals whether someone understands why variance has rules.

Interfaces: from pure contracts to traits

Interfaces have quietly gained features that change design options. Default interface members (C# 8) let you add a method with a body to an interface without breaking implementers; the intended use is API evolution and trait-like mix-ins, not "multiple inheritance of state" (interfaces still have no fields). Static abstract and static virtual members (C# 11) let an interface demand static members — operators, Parse, Zero — which makes generic math possible and turns "every type that can be created from a string" into a compile-time contract. Explicit interface implementation hides members from the class's public surface (used to implement IEnumerable non-generically alongside IEnumerable<T>). And the JIT's guarded devirtualisation (unit 01) means the "interfaces are slow" objection is now mostly historical outside of tight numeric loops, where the struct-constraint trick applies.

public interface IEntity<TSelf> where TSelf : IEntity<TSelf>
{
    static abstract TSelf Create(Guid id);       // factory as a contract, no reflection, no new()
    Guid Id { get; }
    string Describe() => $"{typeof(TSelf).Name}:{Id}";   // default interface member
}

public sealed record Order(Guid Id) : IEntity<Order>
{
    public static Order Create(Guid id) => new(id);
}

Interview trap

"Abstract class versus interface" answered as a textbook list. The senior answer is about what changes: an abstract class is a single inheritance slot, can hold state and constructors, and lets you evolve the base with non-breaking virtual additions; an interface is a capability, composable, and — since C# 8 — also evolvable via default members, and — since C# 11 — can require static members. So the decision is: "is this a kind of thing with shared state, or a capability that unrelated things share?" and "will consumers need to mock or compose it?" Then mention that DI, testing and records all pull towards interfaces plus composition, and that sealed classes plus interfaces is the modern default.

Gotcha

Default interface members are not inherited by the class. If IEntity has a default Describe() and Order does not override it, new Order().Describe() does not compile — the member is only reachable through the interface type: ((IEntity)order).Describe(). This is deliberate (adding a default member must not change the class's public surface) and it is the thing that surprises everyone the first time.

Interview Q&A

How are .NET generics implemented, and what are the performance consequences?

They are reified: the runtime creates a distinct type per instantiation, keeps full type information, and the JIT compiles specialised native code per value-type argument while sharing one compilation across all reference-type arguments via a hidden generic dictionary. Consequences: List<int> is unboxed and fast, a struct type argument constrained to an interface gets devirtualised, inlined interface calls, and code size grows with each value-type instantiation — which matters for NativeAOT binaries and JIT warm-up. Reference-type sharing has a small cost for typeof(T)-style lookups through the dictionary. That is the whole reason the BCL passes comparers as struct type parameters in hot paths.

Explain covariance and contravariance with a real bug they prevent.

Covariance (out) lets IEnumerable<Cat> flow into a method taking IEnumerable<Animal>, safe because the interface only hands cats out. Contravariance (in) lets an IComparer<Animal> be used where an IComparer<Cat> is needed, safe because it only takes animals in. The bug variance prevents is the one arrays have: Animal[] a = new Cat[1]; a[0] = new Dog(); compiles and throws ArrayTypeMismatchException at run time, because arrays are covariant unsoundly. List<T> is invariant precisely so that Add cannot be abused that way, and the compiler enforces the in/out positions on interface declarations so a variant interface can never be unsound.

What are static abstract interface members and what did they unlock?

An interface can declare static members — operators, properties, factory methods — that implementing types must provide, and generic code can call them through the type parameter: T.Zero, T.Parse(s), a + b where T : INumber<T>. They unlocked generic math in .NET 7 — one Sum<T> for every numeric type without boxing or delegates — and a class of design patterns that used to need reflection or new(): static factories as contracts, IParsable<T> for "any type that parses", and typed builders. The constraint is that they are only usable through generics; you cannot call INumber<T>.Zero on the interface itself, and they are not virtual dispatch on an instance.

When do default interface members help, and when are they a trap?

They help when you own an interface that is implemented outside your assembly and you need to add a member without breaking every implementer — the classic "add ILogger.BeginScope overload" problem — and for small trait-like helpers expressed in terms of the interface's other members. They are a trap when used as multiple inheritance: no state, class members do not see them without a cast, diamond ambiguities require explicit overrides, and readers do not expect logic in interfaces. In review I accept a default member for evolution or a pure convenience overload, and push logic anywhere else into an extension member or a base class.

Explicit interface implementation: why and when?

It implements a member so it is accessible only through the interface type, not on the class. Uses: satisfying two interfaces with the same member name but different semantics, hiding the non-generic IEnumerable.GetEnumerator behind the generic one, keeping a "framework plumbing" interface off a domain type's public surface, and offering a struct-returning public GetEnumerator while the interface version boxes. The trade-off is discoverability: users must cast to see the member, so it should never hide something users are expected to call.

How do you design a generic API so it does not allocate, and where does it fall apart?

Take ReadOnlySpan<T> for input sequences, constrain behaviour parameters as where TStrategy : struct, IStrategy so the JIT specialises, avoid Func<T> callbacks in tight loops (delegate invocation is not inlined), and offer TryX(out) shapes instead of exceptions or nullable wrappers. It falls apart when the API must also be an interface (interfaces cannot be generic over a struct strategy without boxing at the boundary), when it must cross an await (spans cannot), and under NativeAOT if instantiations are created dynamically. For a public library I ship both the fast generic shape and a simple delegate-based overload, and document which is which.

What is the difference between is, as and a cast, and how expensive are they?

A cast throws InvalidCastException on failure; as returns null for reference and nullable types; is with a pattern (if (o is Circle c)) tests and binds in one step and is the modern idiom. Type checks against a sealed class are a pointer comparison on the method table; against an unsealed class they walk the hierarchy; against an interface they search the interface map — all fast, but the sealed case is why sealed is a free performance win. With PGO the JIT can also guess the likely type. Unboxing is a cast too, and it must be to the exact struct type: (long)(object)5 throws.

Why is new() as a constraint discouraged in modern code?

new T() compiles to Activator.CreateInstance<T>(), which is reflection: slower than a direct call, it wraps constructor exceptions in TargetInvocationException, and it is a trimming/AOT warning surface. It also cannot express parameters. The modern replacements are a Func<T> factory parameter when you need flexibility, or a static abstract factory member on an interface when you need a contract, which is direct, inlineable and AOT-safe. I still see new() in test helpers and DI-less object mothers, and that is fine; in a hot path or a library it gets flagged.

How does generic type inference work, and where do you have to help it?

The compiler infers type arguments from the argument expressions, phase by phase: fixed types first, then lambdas whose parameter types depend on already-inferred parameters, then return types. It never infers from the return type alone, never from constraints, and cannot infer through a user-defined conversion. So Parse<T>(string s) always needs an explicit T, a lambda argument needs at least one typed parameter elsewhere to anchor T, and two arguments of int and long for the same T may infer long via best-common-type or fail. C# 14's first-class span conversions improved inference for span-taking overloads, which is why some older explicit .AsSpan() calls are now redundant.

A colleague wants to add a method to a widely implemented public interface. What are the options and what do you recommend?

Options: add it as a default interface member (binary and source compatible for implementers; consumers calling it through the interface get the default), add a new derived interface (IFooV2 : IFoo) and type-test for it, add an extension member so it is a static helper rather than a contract, or accept the break with a major version bump. My recommendation depends on whether the member is genuinely a new obligation — then it is a new interface or a breaking change, because a default body that throws is a lie — or a convenience expressible via existing members, where a default member or an extension member is fine. And I would remind the team that any of these on a public NuGet package is a semver decision, not a coding one.

06Delegates, lambdas, events and closures

Docs: Lambda expressions · Delegates · Events

A delegate is a type-safe, multicast reference to a method plus, optionally, the object to call it on. Concretely, every delegate instance is a small heap object with a Target (the receiver, or null for static methods), a Method pointer, and an invocation list when combined. Func<>, Action<> and Predicate<> are just generic delegate types the BCL declares so nobody has to. A lambda is syntax that the compiler turns into a method — static if it captures nothing, or an instance method on a compiler-generated closure class if it captures locals, parameters or this — and then wraps in a delegate. That last sentence is the key to every closure question: captured variables are hoisted into fields of a heap object shared by every lambda that captures them. They are captured by reference to the shared object, not by value, which is why a loop variable captured in a lambda sees the value at invocation time, not creation time.

var actions = new List<Action>();
for (int i = 0; i < 3; i++) actions.Add(() => Console.Write(i));   // for: ONE i shared → prints "333"
foreach (var s in new[] { "a", "b", "c" }) actions.Add(() => Console.Write(s)); // foreach since C# 5: fresh s each iteration → "abc"

Events: a delegate with a publisher-controlled surface

An event is a delegate field plus two accessors (add/remove) that outsiders are limited to: subscribers can += and -=, but only the declaring class can invoke or reset it. The EventHandler<TArgs> convention is (object? sender, TArgs e). Two things are always tested: raising safely (Changed?.Invoke(this, args) copies the delegate reference first, so a concurrent unsubscribe cannot produce a null dereference between the check and the call), and lifetime (a subscription is a strong reference from publisher to subscriber, unit 03). Multicast invocation runs subscribers in order; an exception from one stops the rest, so a robust publisher either catches per handler by iterating GetInvocationList() or moves to a design that does not fan out synchronously. C# 14 adds partial events, which matter for source generators: a generator can now provide the add/remove implementation for an event you declare.

public sealed class Downloader
{
    public event EventHandler<ProgressEventArgs>? Progress;

    private void Report(int pct)
    {
        var handlers = Progress;                         // snapshot: safe against concurrent -=
        if (handlers is null) return;
        foreach (EventHandler<ProgressEventArgs> h in handlers.GetInvocationList())
        {
            try { h(this, new ProgressEventArgs(pct)); }
            catch (Exception ex) { /* log; one bad subscriber must not starve the others */ }
        }
    }
}

Expression trees: the lambda that is data

Assign a lambda to Expression<Func<T, bool>> instead of Func<T, bool> and the compiler emits code that builds a syntax tree rather than a method. That is the entire mechanism behind IQueryable and EF Core: the provider walks the tree and translates it to SQL. The consequences follow: only expression-bodied lambdas can become trees (no statements, no async), a method call inside the tree is only meaningful if the provider knows it (hence "could not be translated" errors), and Compile() turns a tree back into a delegate at a cost that is only worth it when cached. Expression trees are also a reflection-free way to build fast accessors — the trick behind many mappers and validators before source generators took over that job.

Interview trap

The captured loop variable — and being asked why for and foreach differ. The answer is scoping: a for loop declares its variable once, outside the body, so every lambda captures the same hoisted field; foreach declares a fresh iteration variable each pass, and since C# 5 the compiler captures each one separately (the C# 4 behaviour was the same bug as for, and the change was one of the very few deliberate breaking changes in the language). The fix for for is a local copy inside the body. The follow-up — "what does this look like after compilation?" — wants the closure-class explanation above.

Gotcha

Async lambdas and Action. button.Click += async (s, e) => await SaveAsync(); compiles to an async void method because the delegate type returns void. Exceptions thrown after the first await cannot be observed by the caller and crash the process (or are swallowed, depending on the synchronization context). Any API taking Action that receives an async lambda has the same problem — Task.Run(async () => ...) is fine because it has a Func<Task> overload, but Parallel.ForEach(items, async i => ...) is a classic bug: it returns before the work is done. Use Parallel.ForEachAsync (.NET 6) or an Func<Task>-taking API.

Interview Q&A

What is a delegate, really, and what does the compiler generate for a lambda?

A delegate instance is an object holding a target reference and a method pointer, plus an invocation list for multicast; the delegate type is a class deriving from MulticastDelegate with a signature-specific Invoke. A lambda becomes a method: static and cached in a static field if it captures nothing, or an instance method on a generated closure class whose fields are the captured variables. this capture makes the enclosing object the target with no closure. Knowing this lets you predict allocations, explain the loop-capture behaviour, and understand why static lambdas exist: the keyword makes the compiler fail if a capture sneaks in.

Explain the loop-variable capture problem and both fixes.

In for (int i...) list.Add(() => i) there is one i for the whole loop, hoisted into one closure object, so every lambda reports the final value. Fix one: copy inside the body, var j = i;, so each iteration has its own variable and therefore its own closure. Fix two: use foreach, which since C# 5 declares a fresh variable per iteration. In review I look for this in any code that queues work items or registers callbacks in a loop, and I also check the inverse: someone who wants shared mutable state across lambdas (a counter) and uses foreach expecting sharing.

When are lambdas expensive, and how do you make a hot path allocation-free?

They allocate a closure object per scope when they capture locals, a delegate per creation unless non-capturing, and invocation through a delegate is an indirect call the JIT will not inline. On a hot path I mark lambdas static so the compiler prevents capture, pass data through a state parameter where the API supports it, and for true inner loops replace the delegate with a generic struct strategy so the JIT specialises and inlines. Since .NET 10, escape analysis can stack-allocate closures that provably do not escape, which removes some of this cost silently, but I do not rely on it in a library: [MemoryDiagnoser] decides.

What is the difference between Func<T, bool> and Expression<Func<T, bool>> and why does it matter for EF Core?

The first is executable code; the second is a data structure describing the code, built by compiler-generated calls to Expression.* factories. EF Core needs the second so it can translate the lambda into SQL by walking the tree. Consequences: Where(x => x.Name.StartsWith(prefix)) becomes LIKE, but Where(x => MyHelper(x)) throws "could not be translated" or, worse in older versions, silently evaluated client-side. A Func passed to IQueryable.Where binds to the IEnumerable overload and pulls the whole table into memory — the most expensive one-character mistake in .NET.

How do you raise an event safely, and what is wrong with the "obvious" code?

The obvious if (Changed != null) Changed(this, e); races: another thread can unsubscribe the last handler between the check and the call and you get a NullReferenceException. Copy the delegate to a local first, or use Changed?.Invoke(this, e), which does exactly that. Beyond null-safety, decide what happens when a handler throws — the default stops later handlers — and whether the publisher should invoke on a captured synchronization context; a robust, reusable publisher iterates GetInvocationList() and isolates failures. And if a handler needs to be async, an event is the wrong tool: use a channel or an observable.

Events versus IObservable<T> versus Channel<T>: how do you choose?

Events are the right thing for in-process, synchronous, UI-style notification where subscribers are few and lifetimes are managed. IObservable<T> (Rx) when you need composition — throttle, buffer, merge, retry — and explicit subscription lifetimes via IDisposable. Channel<T> when the consumer is asynchronous and you need backpressure and a bounded buffer between producer and consumer, which is the shape of most server-side pipelines. The dividing question I ask: "does the consumer need to do async work or apply backpressure?" — if yes, it is not an event.

What are function pointers and when would you reach for them?

delegate* managed<int, int> (C# 9) is a raw pointer to a method: no allocation, no target object, a direct call, and it can be unmanaged for calling into native code with a specified calling convention. They are for interop layers, for the innermost loop of a performance-critical library where even a cached delegate's indirect call shows up, and for building things like vtables without allocation. They cannot capture, they need unsafe today, and the C# 15 memory-safety preview is reshaping which pointer operations require it. In application code I would never expect to see one.

Why does async void exist, and how do lambdas make it a trap?

It exists so async methods can be event handlers, whose delegate type returns void. The cost is that nothing awaits it: exceptions after the first await go to the synchronization context or crash the process, callers cannot know when it finishes, and tests cannot wait for it. Lambdas make it invisible: any async lambda converted to Action is async void, so Parallel.ForEach, List.ForEach and many "callback" APIs quietly produce fire-and-forget code. The review rule: an async lambda must target a Func<Task> overload, and the analyzer VSTHRD100/CA2007-family rules flag the rest.

What is a method group conversion and what does it cost?

Writing list.Select(Transform) instead of x => Transform(x) converts the method group to a delegate. Historically this allocated a new delegate every time for instance methods and, until C# 11, for static methods too; C# 11 caches the static-method conversion just like a non-capturing lambda. For instance methods it still allocates a delegate bound to this each call, and there is a subtle difference when overloads exist: the method group picks the overload at conversion time. Since C# 10, var f = Transform; infers a natural Func<> type, which made method groups first-class values.

How do delegates interact with synchronization contexts and thread affinity in a service versus a UI app?

A delegate has no thread affinity by itself; it runs wherever it is invoked. What gives it affinity is the SynchronizationContext captured by await: in WPF/WinForms/MAUI, continuations after await return to the UI thread, so a lambda registered as a continuation touches UI safely; in ASP.NET Core there is no synchronization context, so continuations run on whichever thread-pool thread completed the I/O. This is why ConfigureAwait(false) is a library concern rather than an application one, why event handlers that hop threads in a service must not assume anything about HttpContext after an await without IHttpContextAccessor, and why capturing a scoped service in a long-lived delegate is a lifetime bug regardless of threading.

07LINQ and collections

Docs: LINQ · Collections · Collection expressions

LINQ is three things wearing one syntax: a set of extension methods over IEnumerable<T> that compose lazily; a parallel set over IQueryable<T> that capture expression trees for a provider to translate; and query syntax that the compiler rewrites into method calls. The mental model that resolves most LINQ questions is that an IEnumerable<T> pipeline is a description: Where returns an object that, when enumerated, pulls from its source and filters. Nothing runs until something enumerates (foreach, ToList, Count, First), and it runs again each time you enumerate. That is deferred execution, and it gives you streaming and composition; it also gives you the two classic bugs — multiple enumeration of an expensive source, and a captured variable that changed between definition and enumeration.

IEnumerable<Order> Big(IEnumerable<Order> orders, decimal min) =>
    orders.Where(o => o.Total > min).OrderByDescending(o => o.Total);   // nothing has run yet

var query = Big(LoadFromApi(), 100);     // still nothing
var count = query.Count();               // runs the whole pipeline (and the API call)
var first = query.First();               // runs it AGAIN, from the source
var snapshot = query.ToList();           // materialise once when you need it more than once

// Iterator methods are the same machinery: a state machine that yields on demand
static IEnumerable<int> Fib()
{
    int a = 0, b = 1;
    while (true) { yield return a; (a, b) = (b, a + b); }
}
var firstTen = Fib().Take(10).ToArray();   // infinite source, finite result: only possible because it is lazy

IEnumerable versus IQueryable: the same method names, a different universe

Both interfaces have Where, Select and friends, but the IQueryable versions take Expression<Func<...>> and add nodes to a tree that the provider (EF Core, a Cosmos or OData client) translates when the query is executed. Overload resolution chooses by static type: as long as the variable is IQueryable<T>, you stay in the translated world; the moment you call AsEnumerable(), ToList(), or pass a Func instead of an expression, everything after runs in memory. The senior-level rules: keep IQueryable inside the data layer and do not return it across a service boundary (it leaks the lifetime of the DbContext and lets any caller generate arbitrary SQL); project with Select into DTOs before materialising; and know that Count() on a queryable is a SELECT COUNT(*) while Count() on the materialised list is O(1) — the same call, opposite costs.

Gotcha

OrderBy is stable and buffers everything; Sort is unstable and in place. LINQ's OrderBy materialises the source into an array, sorts a key array with a stable sort, and yields — O(n) memory and no output until the sort is done. List<T>.Sort uses introsort in place and is not stable, so equal keys may reorder. Choosing the wrong one gives either a memory spike on a large stream or a flaky "sorted by date, then by name" report. Order()/OrderDescending() (.NET 7) are the modern spelling of OrderBy(x => x).

Interview Q&A

What is deferred execution, and name a bug it causes and a feature it enables.

A LINQ-to-objects pipeline is a chain of iterator objects that do no work until enumerated, and do it again on every enumeration. The bug: an expensive or one-shot source enumerated twice, or a variable captured by a Where lambda that changes before the enumeration — the filter uses the value at enumeration time. The feature: streaming through arbitrarily large or infinite sources with constant memory (Fib().Take(10)), and composition — a repository can return a filtered enumerable and the caller can add Take without either side materialising. The discipline is to know where the boundary is and materialise there, once, on purpose.

IEnumerable versus IQueryable: what is the mechanism, and what is the rule you enforce?

IQueryable methods take expression trees and build a query description that a provider translates at execution; IEnumerable methods take delegates and run in memory. Overload resolution by static type decides which you get, so one AsEnumerable() or one Func silently moves the rest of the query client-side. The rule: IQueryable never leaves the data access layer, projection to DTOs happens with Select before materialisation, and any helper that must be reusable inside queries is written as an Expression<Func> or an EF Core-mappable function, not a normal method. And I ask for the generated SQL in review for any non-trivial query.

How does yield return work under the hood, and what are its constraints?

The compiler rewrites the method into a class implementing IEnumerator<T> and IEnumerable<T> with a state field; each yield return becomes "store the value, record the state, return true", and MoveNext resumes at the recorded state. Locals become fields. Constraints follow: no yield inside try with a catch (a finally is allowed and runs on Dispose), no ref/out parameters, no yield in a lambda, and argument validation runs lazily — on first MoveNext, not on call — so the idiom is a non-iterator wrapper that validates and then calls a private iterator. The same machinery, with a task-like return, is how async and IAsyncEnumerable are built.

Choose between List, ImmutableArray, FrozenDictionary and ConcurrentDictionary for a routing table loaded at startup and read on every request.

FrozenDictionary: it is built once, expensive to construct, and optimised for the fastest possible reads with a specialised hashing strategy chosen from the actual keys. ConcurrentDictionary would pay for write-safety nobody needs. ImmutableDictionary is a persistent tree — great for versions and snapshots, but slower lookups. A plain Dictionary behind a readonly field is fine too and thread-safe for concurrent reads as long as nobody writes; the frozen type simply makes that contract impossible to violate and faster. If the table can be reloaded at run time, swap the whole frozen instance atomically through a volatile field rather than mutating.

What do collection expressions compile to, and why prefer them over the older syntax?

The compiler chooses per target type: constant spans point at assembly data with no allocation, arrays are allocated and filled, lists are created with the right capacity when the spread sources have a known count, and any type with a [CollectionBuilder] — ImmutableArray, ReadOnlySpan, your own — gets its builder called with a span. C# 15's with(...) element passes constructor arguments like a comparer or capacity. Prefer them because they are target-typed (one syntax for all collection kinds), because the compiler picks a better construction than most hand-written code, and because the spread operator replaces Concat().ToList() chains with a single pre-sized allocation.

How do you avoid allocations in dictionary-heavy code?

Choose the right comparer once so string keys are not normalised per lookup (OrdinalIgnoreCase rather than ToLower()), use TryGetValue instead of ContainsKey plus indexer, use CollectionsMarshal.GetValueRefOrAddDefault for read-modify-write in one hash, and — since .NET 9 — use GetAlternateLookup<ReadOnlySpan<char>>() to look up by a slice of a larger string without allocating the key. Pre-size the dictionary when the count is known. Avoid Dictionary<Enum, T> without a comparer on .NET Framework, where the default comparer boxes. And profile: often the allocation is the value factory, not the dictionary.

What is IAsyncEnumerable<T>, and how does it differ from returning Task<IEnumerable<T>>?

Task<IEnumerable<T>> completes once, when the whole sequence is available; IAsyncEnumerable<T> is a pull-based stream where each MoveNextAsync may await, so items flow as they arrive and memory stays bounded — the shape for paging an API, reading rows, or streaming a response body. Consumed with await foreach, cancellation via WithCancellation or [EnumeratorCancellation]. Since .NET 10 the full LINQ operator set is in the box for it (System.Linq.AsyncEnumerable), so the old System.Linq.Async package is only needed on older targets. ASP.NET Core streams an IAsyncEnumerable result as NDJSON or a JSON array without buffering.

What is the difference between First, FirstOrDefault, Single and SingleOrDefault, and which do you use for a lookup by primary key?

First returns the first match and throws on none; FirstOrDefault returns default on none; Single throws on none or more than one; SingleOrDefault throws only on more than one. For a primary-key lookup the correct semantic is SingleOrDefault — "there must not be two" is an assertion worth having — but against a database it translates to TOP 2, so it costs nothing extra, while in memory it scans to the end. EF Core's FindAsync is the better tool because it checks the change tracker first. And since .NET 6 the OrDefault variants accept an explicit default value, which removes a lot of ?? fallback noise.

How would you write a LINQ pipeline that must process ten million records without blowing memory?

Keep it streaming end to end: a lazy source (yield, a data reader, IAsyncEnumerable), only per-element operators (Where, Select, Take), and a consumer that writes as it goes. Avoid the buffering operators — OrderBy, GroupBy, Reverse, ToList, Distinct without bounded cardinality — or push them to the database. If aggregation is unavoidable, use CountBy/AggregateBy (.NET 9), which keep one accumulator per key rather than a list of items per key. And for CPU-bound transformation, batch with Chunk and process chunks in parallel while keeping the outer flow sequential so back-pressure still works.

Query syntax or method syntax: what do you mandate in a team?

Method syntax by default, because it covers every operator, composes with extension methods, reads naturally with lambdas, and is what everyone sees in documentation and generated code. Query syntax earns its place for multi-from joins and let clauses, where the method form becomes nested SelectMany with transparent identifiers that nobody can read. They compile to the same thing, so I do not police it beyond "don't mix them in one expression", and I do point out that LeftJoin in .NET 10 removed the last case where query syntax was clearly nicer.

08Pattern matching, unions and closed hierarchies

Docs: Patterns · What's new in C# 15 (unions, closed) · Union types

Pattern matching turned C# from "test the type, then cast, then read" into "describe the shape you want, bind what you need, and let the compiler check you covered everything". That last clause is the whole point and the reason the feature kept growing from C# 7 to C# 15: a switch expression over a well-described set of cases is checked for exhaustiveness, so adding a case to the domain produces a compiler warning at every switch that forgot it. C# 15's union types and closed hierarchies are the missing half of that story — they let you tell the compiler what "everything" means for your own types, which is what functional languages have had as discriminated unions and what C# teams have been emulating with OneOf, sealed-record hierarchies plus a _ => throw arm, and analyzers.

Modelling "one of these": from records to unions

The C# 9–14 idiom for a closed set of alternatives is an abstract record with sealed derived records, matched with a switch expression. Its weakness is exhaustiveness: the compiler cannot know the hierarchy is closed, so every switch needs a _ => throw new UnreachableException() arm, and adding a new case is a run-time failure somewhere, not a compile error. C# 15 fixes this two ways. A closed class can only be derived from within its own assembly, so the compiler knows all direct descendants and a switch over them is exhaustive without a default; closed is implicitly abstract, and exhaustiveness only extends downward if intermediate types are also closed. A union type (public union Pet(Cat, Dog, Bird);) goes further: it composes existing, unrelated types, gives implicit conversions from each case, and switches over it are exhaustive over the case types. The compiler generates a struct with one constructor per case, an object? Value property (so value-type cases box — a known limitation of the first release), and an IUnion implementation; libraries can mark their own OneOf-style types with [Union] to get the same pattern-matching support, and System.Text.Json in .NET 11 serialises them. The runtime scaffolding arrived with .NET 11 Preview 5, so this is a "needs .NET 11" feature, not a lowering trick.

Control flow catching up: labeled break/continue

C# 15 also adds labeled break and continue: outer: for (...) { for (...) { if (found) break outer; } }. It is a small feature, but it retires the two patterns every reviewer has argued about — a boolean flag checked at each level, or a goto — and the IDE0410 style rule now flags both. It is worth naming in an interview as "the most recent citable change" precisely because it is small: it signals you read release notes, not just headlines.

Interview trap

Order matters in a switch expression, and the compiler will tell you when it does not. Arms are tested top to bottom; a more general pattern above a more specific one makes the specific one unreachable, and the compiler errors (CS8510) rather than warning. Candidates also stumble on when guards: an arm with a guard does not contribute to exhaustiveness, so { Total: > 0 } when IsValid(o) => ... followed by no fallback is a "not exhaustive" warning even if you believe the guard is always true. And null: a type pattern never matches null, so a switch over a nullable input needs a null => arm or it throws at run time with a warning at compile time.

Gotcha

Unions box value types and default to null. In the first release, Value is object?, so union Amount(int, decimal) allocates on every conversion from a struct — fine for domain results, wrong for a hot numeric path — and a default(Pet) has a null Value that matches the null pattern and none of the case types. If a union is a field of a class or an element of an array, that default state exists whether you like it or not; design switches over unions with that in mind, or keep them as locals and return values.

Interview Q&A

What does pattern matching give you over if/is/casts beyond brevity?

Three things. Exhaustiveness: a switch expression over a bounded domain — enum, bool, tuple of those, closed hierarchy, union — is checked at compile time, so growth in the domain surfaces as warnings, not runtime failures. Safety: a declaration pattern tests and binds in one step, so the checked type and the used variable cannot drift apart the way a check-then-cast can. Structure: property, positional and list patterns describe shapes declaratively, and the compiler generates a decision DAG that evaluates each component once, which is usually faster than the hand-written chain of ifs. The brevity is a side effect.

Explain switch statement versus switch expression and when you would still use the statement.

The expression form produces a value, requires exhaustiveness (warning otherwise, and a SwitchExpressionException at run time), has no fall-through, and reads as a mapping. The statement form runs blocks, allows multiple statements and side effects per case, and supports goto case. I use the expression for pure mappings and the statement when arms do real work — logging, I/O, mutating state — because cramming that into an expression with a discard arm and throw expressions is worse than the statement. Since C# 8 a statement can also use every pattern form, so the choice is about shape, not power.

How did teams model discriminated unions before C# 15, and what did each approach cost?

Abstract record plus sealed derived records: clean, but no exhaustiveness, so every switch carries a throwing default arm and a new case is a runtime failure. OneOf<T1, T2> and similar libraries: exhaustive via a Match(f1, f2) method, but lambdas per case, allocation, and generic-arity noise. Enum-plus-data structs: fast but unsafe, with invalid combinations representable. Analyzers to enforce closedness: work, but not portable. C# 15's closed modifier fixes the first approach in place, and union replaces the second with language support, implicit conversions, exhaustive switches and [Union] attributes so existing OneOf-style types can participate.

What exactly does closed mean, and where does exhaustiveness stop?

closed on a class restricts derivation to the declaring assembly, so the compiler can enumerate the direct descendants and treat a switch over them as exhaustive without a default. It is implicitly abstract and cannot combine with sealed or static. Exhaustiveness stops at the first non-closed descendant: if Shape is closed and Polygon : Shape is not, then matching Polygon as a whole is enough, but you cannot exhaustively match Polygon's own subtypes unless Polygon is also closed. The design keeps the check local to what the compiler can see, which is why it composes with separate compilation and does not need whole-program analysis.

What does a C# 15 union compile to, and what are the first-release limitations?

A struct with one constructor per case type, implicit conversions from each case, a public object? Value, and an IUnion implementation; patterns on the union are applied to Value, and exhaustiveness is over the declared cases plus a required null arm if any case is nullable. Limitations today: value-type cases are boxed into Value, the default value of the struct has a null Value, and not every feature of the proposal is implemented yet — later previews will add more. The runtime pieces (UnionAttribute, IUnion) shipped in .NET 11 Preview 5, so this is not usable on .NET 10 with a LangVersion override.

Where have you seen pattern matching hurt readability, and what do you do about it?

Deeply nested property patterns that encode business rules — five levels of { A.B.C: ... } with guards — become a rule engine nobody can modify safely, and a switch with 20 arms and when clauses is a decision table pretending to be code. I push those into named predicates or a strategy table, keep patterns to structural shape (which case, which fields), and put the rule in a method with a name. The other smell is matching on types that should have been polymorphic: if every consumer switches over Shape to compute area, Area belongs on Shape; patterns are for operations that live outside the type.

How do list patterns work and what can they match?

They match anything countable and indexable — arrays, lists, strings, spans, anything with a Length or Count and an int indexer — against a sequence of sub-patterns, with one optional slice .. that absorbs the rest and can bind it (.. var tail) if the type supports ranges. [] matches empty, [_] exactly one, [var first, ..] at least one. They are ideal for protocol parsing, argument parsing and tests on small sequences, and they compile to length checks plus indexed access, so they are as fast as the hand-written version.

Give a concrete example where the compiler's exhaustiveness check caught a real bug.

The canonical one is an enum growing: an OrderStatus gains PartiallyShipped, and a switch expression mapping status to a customer-facing string warns in every projection, notification and report that had no default — a code-level list of everything the new status touches, before a single test runs. With records before C# 15 you only got that if you resisted the default arm and accepted the warning; with closed and union you get it for free. My team practice is WarningsAsErrors for CS8509 so the warning is a build break, because a switch that "handles" unknown cases with a throw is exactly the code that pages you.

How do is not null, != null and is { } differ?

!= null calls a user-defined != operator if the type has one — which is how a broken operator overload or an Unity-style "fake null" object makes a null check lie. is not null and is { } are patterns: they compile to a reference check and cannot be overloaded, so they are the safe spelling. is { } additionally binds — if (x is { } value) gives a non-nullable value — and property patterns extend it naturally. Since C# 9 I ask for is null/is not null in review as the default.

What is the newest pattern-related change you can cite, and why does it matter?

Two from the C# 15 preview in .NET 11 RC1 (2026-09-08): union types with exhaustive switches, and the closed modifier that makes record hierarchies exhaustive — plus, on the control-flow side, labeled break and continue. They matter because they finish a ten-year arc: patterns gave C# the syntax of algebraic data types, and these give it the type-system guarantee, so "add a case and the compiler finds every switch" is now a language feature rather than a discipline. For a team, the practical change is retiring OneOf, deleting throwing default arms, and turning CS8509 into a build error.

09async/await and concurrency

Docs: Asynchronous programming · TPL · .NET 11 runtime (Runtime Async)

The sentence to carry into any async discussion: await is a suspension point, not a thread. An async method runs synchronously on the calling thread until it hits an await on something incomplete; at that point it registers a continuation and returns a Task to its caller, freeing the thread. When the awaited thing completes — an I/O completion port fires, a timer elapses, another task finishes — the continuation is scheduled (on the captured SynchronizationContext if there was one, otherwise on the thread pool) and the method resumes from where it left off. No thread is blocked while waiting on I/O; that is the entire point, and it is why a web server with 16 threads can hold 10 000 open requests. The thing that makes this work today is a compiler-generated state machine: the method's locals become fields, each await becomes a state number, and MoveNext is the method body as a big switch. The thing that changes in .NET 11 is that the runtime takes over that job.

Runtime Async: the biggest change to async since C# 5

Since 2012 every async method has been a Roslyn lowering: a struct state machine, an AsyncTaskMethodBuilder, boxing of that struct onto the heap on the first real suspension, and stack traces full of MoveNext frames. Runtime Async, shipping in .NET 11 (no longer behind EnablePreviewFeatures for net11.0 targets as of RC1; the framework libraries themselves are compiled with it on), makes async a first-class concept in the JIT and the runtime: suspension and resumption are handled by the runtime, continuations are lighter, and the JIT can compile a dedicated async version of a method, tail-merge suspension points and skip ExecutionContext capture when there is no ambient state. The observable effects are cleaner stack traces, lower per-await overhead and smaller code; the semantics of async/await, Task and ValueTask do not change. What it means for you: the traditional "avoid async in hot paths because of the state machine" advice weakens on .NET 11, but everything about thread pools, contexts, cancellation and blocking stays exactly as it is.

public async Task<Report> BuildAsync(Guid id, CancellationToken ct)
{
    // 1. Synchronous until the first incomplete await: argument checks run immediately
    ArgumentOutOfRangeException.ThrowIfEqual(id, Guid.Empty);

    // 2. Fan out independent I/O, then await both: total time = max, not sum
    var customerTask = _customers.GetAsync(id, ct);
    var ordersTask   = _orders.ForCustomerAsync(id, ct);
    await Task.WhenAll(customerTask, ordersTask);          // one suspension point for both

    // 3. Results are already complete: these awaits do not suspend
    var customer = await customerTask;
    var orders   = await ordersTask;

    // 4. CPU-bound work in a request path: offload only if it is genuinely heavy
    var summary = orders.Count > 10_000
        ? await Task.Run(() => Summarise(orders), ct)
        : Summarise(orders);

    return new Report(customer, summary);
}

The rules that prevent the incidents

Never block on async: .Result, .Wait(), .GetAwaiter().GetResult() in code that runs on a context (UI, classic ASP.NET) deadlocks, because the continuation needs the thread you are blocking; in ASP.NET Core there is no context, so it "only" burns a thread per blocked call, which under load becomes thread-pool starvation — the number one production incident in .NET services, with the signature of rising latency, a climbing thread count and the pool injecting threads at one or two per second. Async all the way is the fix, and ConfigureAwait(false) is a library discipline (do not capture a context you do not need) rather than an application one. Cancellation is cooperative: pass the CancellationToken through every layer, check it in loops, link tokens with CreateLinkedTokenSource for timeouts, and prefer WaitAsync(timeout, ct) (.NET 6) and TimeProvider (.NET 8) for testable time. Exceptions: an exception inside an async method is stored on the task and rethrown at the await; WhenAll rethrows only the first but keeps the rest in task.Exception.InnerExceptions. And for CPU-bound parallelism use Parallel.ForEachAsync or partition explicitly; Task.Run in a request path does not create capacity, it moves work from one pool thread to another.

Interview trap

"async makes it faster" / "async uses more threads". Neither. A single request is not faster async — it may be marginally slower — but the server handles far more concurrent requests with the same threads because no thread waits on I/O. The classic follow-up is the sync-over-async deadlock: explain it in terms of the captured context needing the blocked thread, then say that ASP.NET Core removed the context so the same code starves the pool instead of deadlocking — and that starvation is worse, because it is gradual and shows up only under load. Mention dotnet-counters' threadpool-thread-count and threadpool-queue-length as how you would prove it.

Gotcha

Awaiting a ValueTask twice, or holding it. The rule set fits on a line: await once, immediately, or convert with AsTask(). Also: an async method that declares ValueTask still allocates when it actually suspends — the saving is only on the synchronous completion path, so it is pointless on a method that always does I/O.

Interview Q&A

Walk me through what happens at an await.

The expression is evaluated to an awaitable; the compiler (or, in .NET 11, the runtime) checks IsCompleted. If it is already complete the method continues synchronously with no suspension at all — which is the fast path ValueTask optimises. If not, the current state is saved, a continuation is registered on the awaiter — capturing the current SynchronizationContext or TaskScheduler unless ConfigureAwait(false) — and the method returns an incomplete Task to its caller. When the awaited operation completes, the continuation is posted to the captured context or queued to the thread pool, and execution resumes after the await, rethrowing if the awaited task faulted. No thread is held between those two points.

Explain sync-over-async deadlocks and why ASP.NET Core "fixed" them into something worse.

In a context that runs continuations on one specific thread — a UI thread or classic ASP.NET's request context — calling .Result blocks that thread, while the awaited task's continuation needs that same thread to complete: a deadlock with no CPU use and no error. ASP.NET Core has no synchronization context, so continuations go to the pool and the block eventually resolves — but every blocked call holds a pool thread for the duration, and under load the pool runs out; new threads are injected only at about one or two per second, so latency climbs steadily and the service looks "slow" rather than "dead". Same root cause, harder diagnosis, which is why "async all the way" is a rule, not a preference, and why Microsoft.VisualStudio.Threading.Analyzers or similar is in my Directory.Build.props.

When should a method return ValueTask instead of Task?

When it is on a measured hot path and completes synchronously most of the time — a cache in front of I/O, a buffered reader that usually has bytes — so the struct return avoids a Task allocation per call. Not as a default: it has stricter consumption rules (await once, do not store, no WhenAll without AsTask()), it is slightly larger to return, and it saves nothing on a method that always suspends. For interfaces used by many implementations, ValueTask gives implementers the option to be allocation-free, which is why the BCL's stream and pipeline APIs use it. I introduce it with a benchmark showing the allocation it removes.

What is ConfigureAwait(false) and where do you require it?

It tells the awaiter not to capture the current SynchronizationContext/TaskScheduler, so the continuation runs on the thread pool. In libraries it is required: the library does not know whether it is called from a UI thread and must not force continuations back onto it, both for performance and to avoid deadlocks when the caller blocks. In an ASP.NET Core application there is no context, so it changes nothing, and in UI applications you usually want the context after an await that precedes UI updates. So: mandatory in library code (enforced with CA2007), noise in ASP.NET Core application code, deliberate in UI code. .NET 8 added ConfigureAwaitOptions for the rarer variants, like suppressing exception rethrow.

How do you design cancellation through a service?

Accept a CancellationToken as the last parameter of every async method and pass it into every awaited call — the request's HttpContext.RequestAborted at the top. Link it with timeouts using CreateLinkedTokenSource so "the caller left" and "we gave up" are distinguishable in the catch filter. Check ct.ThrowIfCancellationRequested() in CPU loops. Never swallow OperationCanceledException silently at a low level; let it propagate to the boundary, where ASP.NET Core maps it to a closed connection. Use TimeProvider so timeouts are testable, and never create a CancellationTokenSource without disposing it, because its timer and registrations are a leak. For long-running background work, the IHostApplicationLifetime token is the root.

What is Runtime Async in .NET 11 and what does it change for a team?

It moves async method execution from a compiler-generated state machine into the runtime and JIT: suspension and resumption are runtime operations, continuations are cheaper, ExecutionContext capture is skipped when there is no ambient state, and stack traces read like synchronous ones. It ships on by default for net11.0 targets as of RC1, and the framework itself is built with it. For a team the semantics do not change, so no code changes; the effects are performance (fewer allocations per await, smaller code) and diagnostics (readable traces, better debugger stepping). What it does not change: thread-pool starvation from blocking, cancellation discipline, or the ValueTask rules. I would plan to re-benchmark async-heavy paths after moving to 11 and delete micro-optimisations that no longer pay for themselves.

How do you run N async operations with bounded concurrency, and what is wrong with the naive approaches?

The naive foreach { await } is sequential; the naive Select(x => DoAsync(x)) plus WhenAll starts everything at once and floods the downstream. The modern answer is Parallel.ForEachAsync with MaxDegreeOfParallelism, or a SemaphoreSlim guarding each call inside a WhenAll, or a bounded Channel with a fixed number of consumers when the producer is separate from the consumers. For rate limiting against an external API use System.Threading.RateLimiting. And the results of WhenAll must be inspected for all failures — it rethrows only the first exception — usually by collecting per-item outcomes rather than throwing.

Explain lock, the .NET 9 Lock type, and when you would avoid locks entirely.

lock (obj) compiles to Monitor.Enter/Exit in a try/finally over any reference type; locking on this, strings or types is a bug because outsiders can lock the same object. .NET 9 added System.Threading.Lock, a dedicated struct-backed type: the lock statement on it uses a faster EnterScope path and the analyzer warns if you box it. You cannot await inside a lock, so async code uses SemaphoreSlim(1,1) with WaitAsync. I avoid locks entirely when the data structure can be immutable (swap a reference atomically), when a Concurrent* collection or Interlocked operation fits, or when the design can be single-writer via a channel — most contention bugs are locks that should have been ownership.

What is the difference between Task.Run, Task.Factory.StartNew, and just calling an async method?

Calling an async method runs it on the current thread until its first suspension — no new thread. Task.Run queues the delegate to the thread pool and, crucially, unwraps Func<Task> so an async lambda returns a task that completes when the inner work completes. Task.Factory.StartNew is the older, lower-level API: it does not unwrap (you get a Task<Task> unless you call Unwrap()), it uses the current scheduler rather than the default, and its LongRunning hint creates a dedicated thread. In modern code StartNew appears only for LongRunning or a custom scheduler; everything else is Task.Run or, better, no offload at all in a server.

A background service processes a queue and occasionally stops silently. What do you look for?

First an unobserved exception: a BackgroundService.ExecuteAsync that throws stops the loop, and by default since .NET 6 that also stops the host (BackgroundServiceExceptionBehavior.StopHost), unless someone changed it to Ignore, in which case the service dies quietly. Second, a swallowed OperationCanceledException or a catch (Exception) without logging inside the loop. Third, an async void or fire-and-forget task whose failure nobody observes. Fourth, a deadlock or starvation inside the loop — a .Result somewhere deep. Fixes: wrap the loop body in try/catch with logging and a backoff, keep the outer loop alive while !stoppingToken.IsCancellationRequested, and emit a heartbeat metric so silence is visible on a dashboard rather than discovered by a customer.

10Extension members, partials and source generators

Docs: extension keyword (C# 14) · Source generators · Partial members

C# has two ways to add behaviour to a type you do not own or do not want to touch: at the language level, extension members; at the compiler level, source generators that write code into your compilation. Both are compile-time and both are why modern .NET can be fast and AOT-friendly: an extension property is a static call; a generated JSON serializer is plain code the JIT sees instead of reflection at run time. The unit is about knowing the mechanisms well enough to reason about what they can and cannot do — and the most-asked recent question, "what are C# 14 extension members and how do they differ from extension methods", is where to start.

Extension members: from this parameters to extension blocks

Since C# 3 an extension method has been a static method whose first parameter is marked this; the compiler resolves x.Foo() to Ext.Foo(x) if no instance Foo exists. That syntax could only express instance methods. C# 14's extension block declares a receiver once and lets you put instance properties, instance methods, static methods, static properties and operators inside it; a block with a receiver type only (no parameter name) declares static extensions that are called as if they were static members of the extended type. Everything still lowers to static methods on the enclosing static class — no runtime support, no virtual dispatch, resolved at compile time against the static type of the receiver — so it works on any target framework with LangVersion 14, and the old this-parameter syntax remains valid and interoperable. C# 15 adds extension indexers to the block. The one breaking change: extension is now a contextual keyword, so a type named extension must be renamed or written as @extension (CS9306).

public static class EnumerableExtensions

Partial everything

partial was invented so designers could generate half a class into a separate file; it is now the interface between your code and generated code. C# 9 partial methods with return values and accessibility, C# 13 partial properties and indexers, and C# 14 partial constructors and partial events complete the set: you write the defining declaration (the signature), a generator supplies the implementing declaration, and the compiler stitches them. That is how [GeneratedRegex], [LoggerMessage], [LibraryImport], [JsonSerializable] contexts and MVVM toolkits work, and why the shape "declare a partial member with an attribute" is the modern face of metaprogramming. Partial constructors let a generator emit the constructor for DI-style property injection; partial events let it implement add/remove for weak or logged events.

Source generators, interceptors and analyzers

A source generator is a Roslyn component that runs during compilation, inspects the syntax and semantic model, and adds C# files to the compilation (it cannot modify existing code). The incremental generator API (IIncrementalGenerator) is the only one you should write today: it is a pipeline of cached transforms over syntax, so IDE typing stays fast; the older ISourceGenerator re-runs everything on every keystroke and is effectively deprecated. Generators exist to replace run-time reflection with compile-time code: they make serialization, logging, P/Invoke, regex and DI wiring inspectable, debuggable, fast at startup and — crucially — trimmable, which is the foundation of NativeAOT. Interceptors (stable in C# 13 via InterceptsLocation, used by ASP.NET Core minimal APIs and EF Core's precompiled queries) go a step further: generated code can replace a specific call site, which is how request delegates and query pipelines become AOT-compatible without changing how you write them. Analyzers are the read-only sibling: same Roslyn model, produce diagnostics and code fixes, and are how architectural rules become build errors.

Interview trap

"Extension members are dynamic dispatch / can override instance members / can access private state." None of that. Resolution is static, on the compile-time type: an instance member always wins, a more specific receiver type wins over a less specific one, and casting to a base type changes which extension is picked. They cannot see private members, cannot be virtual, and an extension property on IEnumerable<T> called on a List<T> variable works because the receiver is an implicit conversion, not because of any run-time lookup. Candidates who explain "it is Ext.IsEmpty(source) with sugar" have it; candidates who reach for dynamic in the explanation do not.

Gotcha

A source generator's output is part of your compilation, with your LangVersion, nullable settings and warnings. A generator that emits C# 12 syntax breaks a project pinned to C# 10; one that emits nullable-unaware code lights up warnings you cannot fix. Turn on EmitCompilerGeneratedFiles to see the output in obj/ when something "impossible" fails, and treat a generator NuGet like a compiler upgrade in your dependency policy.

Interview Q&A

What are C# 14 extension members and how do they differ from extension methods?

Extension methods (C# 3) are static methods with a this first parameter that the compiler lets you call with instance syntax; they can only be instance methods. C# 14's extension block declares the receiver once and allows extension properties, static methods, static properties and operators — and C# 15 adds indexers. They lower to exactly the same static calls, so they need no runtime support, mix with the old syntax and work on older targets with LangVersion 14. The real capability gain is expressiveness: sequence.IsEmpty instead of sequence.IsEmpty(), static factories on interfaces you do not own, and operators on third-party types. The breaking change is the new contextual keyword, CS9306 for any type named extension.

What are the design limits of extension members and when are they the wrong tool?

They are resolved statically on the compile-time type, cannot be virtual or overridden, cannot hold state, cannot access private members, and are only found when their namespace is imported. So they are wrong when behaviour must vary by runtime type (use an interface or a pattern-matching switch), when the operation needs state per instance (a wrapper or a ConditionalWeakTable), and when discoverability matters for a public API's core surface — a property that every user needs should be on the type. They are right for fluent helpers, LINQ-style operators, adapting types you do not own, and keeping domain types free of infrastructure concerns.

What is a source generator and why did the ecosystem move to them?

A Roslyn component that runs inside compilation, reads syntax and semantics, and adds generated source files; it cannot edit existing code, only add. The ecosystem moved because reflection at run time is slow to start, invisible to the trimmer, hard to debug and impossible under NativeAOT, whereas generated code is plain C#: inspectable, steppable, JIT-optimised and trimmable. The concrete wins are System.Text.Json contexts, [LoggerMessage] zero-allocation logging, [GeneratedRegex], [LibraryImport] replacing DllImport marshalling, and the minimal-API and EF Core interceptors that make ASP.NET Core AOT-capable. The cost is build complexity and a dependency on generator quality.

Incremental versus classic source generators — why does it matter?

The classic ISourceGenerator re-executes fully on every compilation, which in the IDE means every keystroke, so a naive generator over a large solution makes typing lag. IIncrementalGenerator models the work as a pipeline of transforms with cached, equatable intermediate values; only stages whose inputs changed re-run. The rules that follow: use ForAttributeWithMetadataName rather than scanning all syntax, extract simple equatable records from symbols early (symbols themselves are not cacheable across compilations), and never hold ISymbol in the pipeline's cached outputs. If a candidate has written one and knows those rules, they have really written one.

What are interceptors and why did minimal APIs need them?

An interceptor is generated code, marked with [InterceptsLocation], that the compiler substitutes for a specific call at a specific source location — the original call remains in your code but binds to the generated method. Minimal APIs' app.MapGet("/x", (Service s, int id) => ...) used to build the request delegate at run time by reflecting over the lambda's parameters; that is untrimmable. With interceptors the request-delegate generator emits a strongly typed binder for that exact call, so the same source becomes AOT-compatible with no API change. EF Core's precompiled queries use the same trick. It is a compile-time-only concept; the runtime never knows a call was intercepted.

How do partial members enable generated code, and what changed in C# 13 and 14?

A partial member has a defining declaration (your signature, usually with an attribute the generator keys on) and an implementing declaration (the generator's body), merged by the compiler. C# 9 made partial methods usable for this by allowing return values and access modifiers; C# 13 added partial properties and indexers, which let generators implement property-backed patterns like MVVM observable properties without the field-plus-property dance; C# 14 added partial constructors and partial events. The practical effect is that "declare the member, add the attribute, let the generator implement it" is now available for every member kind, so generators no longer need to invent naming conventions like OnXChanged hooks.

How do you enforce an architecture rule in a large C# codebase?

As a Roslyn analyzer shipped in a NuGet package referenced from Directory.Build.props, with severity set in .editorconfig and TreatWarningsAsErrors for the rules that matter — "no synchronous I/O in request paths", "no DateTime.Now", "domain assemblies do not reference infrastructure". Analyzers run in the IDE with code fixes, in CI, and on every developer's build; they are not skippable the way a wiki page is. For dependency direction I pair them with architecture tests (NetArchTest-style) in the test suite. And I keep the rule count small: an analyzer nobody understands gets suppressed globally within a month.

What is user-defined compound assignment in C# 14 and when would you implement it?

You can now declare operator += (and the other compound forms, plus ++/--) directly as instance members that mutate in place, instead of the compiler rewriting a += b as a = a + b through the binary operator. It matters for large value types and numeric/tensor libraries where a + b would allocate or copy a temporary and then copy it back. Implement it only when the type is mutable by design and the in-place semantics are the point; for immutable value objects the binary operator remains correct and the compiler's rewrite is fine.

How would you migrate a reflection-heavy library (a mapper or validator) to be AOT-compatible?

Enable IsAotCompatible and IsTrimmable to surface warnings, then classify each reflection use: property enumeration and accessor creation become a source generator emitting typed code per annotated type; Type.GetType(string) becomes a registration or a [DynamicallyAccessedMembers] contract; Expression.Compile becomes generated delegates; MakeGenericType is the hardest, usually replaced by generating the concrete instantiations. Keep the reflection path for non-AOT consumers behind RuntimeFeature.IsDynamicCodeSupported. Ship the generator in the same package, test with a published AOT sample in CI, and expect the generated path to be faster on the JIT too, which is the argument that gets it funded.

What do you flag in a code review of a new extension-method or generator PR?

For extensions: a namespace that is too broad or too narrow (pollution versus discoverability), extensions on object, extensions that duplicate an instance member and will silently lose to it, and helpers that belong on the type because the team owns it. For generators: use of the non-incremental API, symbols held in cached pipeline state, emitted code that ignores the consumer's nullable and language settings, missing EmitCompilerGeneratedFiles in the test project, no snapshot tests of the generated output, and a generator project targeting anything but netstandard2.0 (the compiler host requires it). And for both: is there a benchmark or a diagnostic showing the reflection or boilerplate it replaces.

11Exceptions, diagnostics and production debugging

Docs: Exception best practices · .NET diagnostics · Distributed tracing (Activity)

Exceptions in .NET are two-pass, stack-unwinding, and expensive precisely when thrown: the first pass walks the stack looking for a matching handler (running exception filters as it goes), the second pass unwinds, running finally blocks. Throwing captures a stack trace, allocates, and on .NET 8 and earlier ran through a C++ unwinder; .NET 9 replaced it with a managed implementation that made throw/catch two to four times faster, but the rule is unchanged: exceptions are for exceptional flow. A try block costs nothing on the happy path — the handler tables are static metadata — so guarding is free and throwing is what you budget. That asymmetry is the design principle behind the BCL's TryParse pairs, the ThrowIfNull helpers (the throw is out-of-line so the fast path inlines), and the modern result-type debate.

The mechanics interviewers probe

try
{
    await ProcessAsync(order, ct);
}
catch (HttpRequestException ex) when (ex.StatusCode is HttpStatusCode.TooManyRequests)   // filter: runs in pass 1, no unwind
{
    await RetryLaterAsync(order);
}
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    throw;                                       // rethrow: keeps the original stack trace
}
catch (Exception ex) when (Log(ex))              // logging filter: observe without catching (Log returns false)
{
    throw new UnreachableException();
}
catch (DbUpdateException ex)
{
    throw new OrderPersistenceException(order.Id, ex);   // wrap with context, keep InnerException
    // never: throw ex;  - that resets the stack trace to this line
}
finally
{
    // runs on the unwind pass; do not throw from here, it replaces the in-flight exception
}

Exception filters (when) are underused and the mark of someone who knows the runtime: they run during the first pass, before any unwinding, so the stack is intact for a dump and no finally has run yet; and a filter that returns false is a way to log or capture state without catching. ExceptionDispatchInfo.Capture(ex).Throw() rethrows a stored exception with its original trace, which is how await rethrows a faulted task's exception and why async stack traces are coherent. AggregateException appears only where multiple failures are genuinely aggregated — Task.Wait(), WhenAll's Exception property — and never at an await, which unwraps the first. Custom exceptions: derive from Exception (not ApplicationException), end the name in Exception, add the standard constructors, carry structured context as properties, and do not create a hierarchy for every case — an exception type earns its existence when someone will catch it specifically.

Modern .NET has a unified diagnostics story built on System.Diagnostics: Activity is the tracing span (OpenTelemetry's .NET API is Activity), Meter/Counter<T>/Histogram<T> are metrics, ILogger with structured message templates is logs, and all three flow through the OpenTelemetry SDK to whatever backend. catch (Exception ex) { throw ex; }, catch { }, and "catch and log at every layer". The first resets the stack trace to the rethrow line — use throw;. The second turns failures into silent corruption. The third produces a log with the same exception five times and no signal. The senior position: catch where you can do something (retry, translate, compensate, map to a response); otherwise let it propagate to a single boundary that logs once with correlation and returns a ProblemDetails. Gotcha

A first-chance exception is not a bug — until there are 5 000 per second. Libraries throw internally and catch (Guid.TryParse does not, but plenty of older code does), so a debugger "breaking on all exceptions" or a spike in exception-count in dotnet-counters may be normal. What is not normal is exceptions as the hot path: an int.Parse in a loop over dirty data, an EF Single() used as an existence check, or a cache miss modelled as a KeyNotFoundException. Those show up as CPU in the unwinder and as GC pressure from stack-trace strings, and dotnet-trace with the Exception keyword lists the throwers by type and site.

Try it: measure what an exception costs

With BenchmarkDotNet, compare int.TryParse("x", out _) against try { int.Parse("x"); } catch { }, then the same throw from 10 frames deep, on .NET 8 and .NET 10 (multi-target the benchmark project).

Expected outcome

The ratio is the number to remember — three to four orders of magnitude — and it is why "we use exceptions for validation errors" is a performance answer, not just a style one.

Interview Q&A

How does exception handling work in the CLR, and what does that imply for design?

Two passes: the first walks the stack from the throw site evaluating handler tables and running when filters until it finds a match; the second unwinds to that frame, running finally blocks and fault handlers. Throwing allocates the exception and captures a trace; the try itself costs nothing because handlers are metadata. Implications: guard freely, throw rarely; use filters to observe without unwinding; put throw statements in helper methods so the fast path stays small enough to inline; and never use exceptions for expected outcomes on a hot path, because the cost is microseconds per throw versus nanoseconds for a branch. .NET 9's managed unwinder made throws cheaper but did not change the order of magnitude.

Exceptions or result types for a domain layer — what do you mandate?

Both, by category. Programming errors and invariant violations throw and propagate; expected outcomes that callers must handle — validation failures, not-found, insufficient funds — are values, because they are frequent, part of the contract, and I want the compiler to make callers handle them. Before C# 15 that meant a Result<T, E> type or OneOf; with C# 15 a union with an exhaustive switch is the native spelling. Infrastructure failures throw and are handled at a resilience boundary. The rule I enforce in review is that a method's failure modes are visible in its signature when they are expected, and invisible when they are bugs.

What are exception filters and give two uses beyond "catch a subset".

A when clause evaluated during the first pass, before any unwinding. Use one: log-and-rethrow without catching — catch (Exception e) when (Log(e)) where Log returns false keeps the stack intact for a later dump and does not disturb finally ordering. Use two: distinguishing cancellation origin — catch (OperationCanceledException) when (timeoutCts.IsCancellationRequested) — or matching on a status code inside HttpRequestException without nested ifs. Filters also avoid the "catch then rethrow" pattern that destroys the first-chance stack for the debugger.

Design a global error-handling strategy for an ASP.NET Core API.

Domain and application code throw or return results without knowing HTTP. A single IExceptionHandler (.NET 8) maps known exceptions to ProblemDetails with the right status, adds a correlation ID and the trace ID, logs once at error level with structured properties, and hides internals in production while including them in development. Validation results become 400s with the RFC 9457 errors shape. Unknown exceptions are 500 with the trace ID so support can find the log. Cancellation is not logged as an error. Resilience — retries, circuit breakers, timeouts — lives in HttpClient handlers via Microsoft.Extensions.Http.Resilience, not in catch blocks. Then the dashboards: exception rate by type and endpoint as a metric, not a log search.

A production pod uses 100% CPU with no obvious load. What is your first fifteen minutes?

Attach without restarting: dotnet-counters monitor for GC time, exception rate and thread-pool queue length, to split "GC storm" from "exception storm" from "spinning threads". Then dotnet-trace collect for 30 seconds of CPU samples and open it in PerfView or Visual Studio to see the hot stacks; if the tool cannot be installed, dotnet-stack report or a dotnet-dump plus clrstack -all shows what every thread is doing right now. Common culprits in that order: a regex or JSON parse on a pathological input, a lock convoy or spin-wait, an exception-per-request path, a tight retry loop with no backoff. I say all of this while noting that the pod should already be exporting CPU-profile-on-demand through the OpenTelemetry collector, and if it is not, that is the retrospective item.

How do Activity, Meter and ILogger fit together, and how do you avoid logging costs?

Activity is the span primitive that OpenTelemetry tracing wraps; Meter instruments are metrics with tags; ILogger is structured logging, and since .NET 8 the three correlate automatically through the current Activity's trace and span IDs in log scopes. Cost control: StartActivity returns null when nothing listens, so instrumented code is free in production until sampling turns it on; metrics are pre-aggregated in-process; logs use [LoggerMessage] source-generated methods, which check IsEnabled and avoid boxing and string formatting when the level is off. The anti-pattern is string interpolation in a log call — it formats even when disabled and destroys the structure that makes logs queryable.

What is EventPipe and why does it matter in containers?

A cross-platform, in-process tracing transport that exposes runtime and application events over a Unix domain socket or named pipe; the dotnet-* diagnostic tools speak it, and so does dotnet-monitor, which can run as a sidecar to collect traces, dumps and metrics on demand or on a trigger like "GC heap above 1 GB". It matters in containers because there is no debugger, no Windows event log and no local profiler: EventPipe is how you get a CPU trace or a heap dump from a running pod without rebuilding it. The prerequisites are worth stating — the tools or the sidecar in the image, DOTNET_DiagnosticPorts configured, and a writable volume for dumps.

When would you write a custom exception type, and how?

When a caller will catch it specifically and act differently, or when it needs to carry structured context — an order ID, a rule name, a retry-after — that a message string cannot. Derive from Exception directly or from the closest meaningful BCL type, name it with the Exception suffix, provide the message and inner-exception constructors, expose the context as properties, and keep it serializable only if you actually cross a serialization boundary (the binary-serialization constructor is obsolete since .NET 8). What I reject: one exception per method, exceptions used as return channels, and hierarchies that mirror the domain model — an OrderException : ShopException : Exception tree that nobody catches at any level except the top.

How do you make sure an exception in the wild can be diagnosed?

Preserve the trace (throw;, wrap with inner exceptions, ExceptionDispatchInfo when deferring), add context at the point where it is known (which order, which tenant) via properties or ex.Data, log once at the boundary with structured properties and the trace ID, and ship symbols: portable PDBs published alongside the assembly or to a symbol server so traces have line numbers, and <Deterministic> builds with Source Link so the line maps to a commit. For crashes, enable minidumps on unhandled exceptions in containers and, on .NET 11, the in-process crash report. Then the test: pick a random production stack trace and see whether a new team member can find the line and the commit in under five minutes.

What is the difference between Environment.FailFast, an unhandled exception, and UnhandledException event handlers?

An unhandled exception on any thread terminates the process after raising AppDomain.CurrentDomain.UnhandledException, which can log but not recover — that is the contract since .NET 2, and legacyUnhandledExceptionPolicy is a Framework-only escape hatch. Environment.FailFast skips even that: no finally blocks, no handlers, straight to a crash dump and the event log, for when state is known to be corrupt and running cleanup would make it worse. TaskScheduler.UnobservedTaskException is the async cousin: faulted tasks nobody awaited raise it during finalization and, since .NET 4.5, do not crash the process — which is why fire-and-forget bugs are silent and why I wire that event to a metric.

12Performance engineering

Docs: .NET 10 runtime performance · BenchmarkDotNet · SIMD in .NET

Performance work in C# has a fixed order of operations, and interviewers at lead level test the order more than the tricks: measure in production (counters and traces), reproduce in a benchmark, change one thing, measure again. The runtime does so much on its own — tiered PGO, devirtualisation, escape analysis, vectorised BCL primitives — that most hand-optimisation without a profiler makes code worse and slower. The tricks matter in the 5% of code that the profiler names, and there the mental model is layered: algorithm and I/O shape first (one round trip instead of N, streaming instead of buffering), then allocations (unit 03), then data layout and dispatch (structs, spans, sealed, generics over interfaces), then SIMD.

What the runtime now does for you

Each release moves the line between "your job" and "the JIT's job", and being able to name the moves is how you show currency. .NET 8: dynamic PGO on by default, SearchValues, FrozenDictionary, AVX-512 in the BCL. .NET 9: DATAS server GC default, the managed exception unwinder, Span.Split, AlternateLookup, System.Threading.Lock. .NET 10: escape analysis with stack allocation of objects and small arrays, delegate devirtualisation, better struct argument codegen, AVX10.2, loop inversion improvements — Microsoft's own numbers put many workloads 15–30% faster with no code change. .NET 11: Runtime Async, a faster Math.BigMul, more bounds-check elimination and switch folding, NativeAOT interface dispatch improvements, FP16 hardware paths, and new cross-lane vector APIs. The interview move is: "before I optimise, I check whether the runtime already did — a benchmark across TFMs is fifteen minutes and often the whole answer".

Interview trap

The premature-optimisation trap in reverse: knowing the tricks and not the order. A candidate who answers "how would you speed this endpoint up" with spans and struct enumerators before asking what the profiler said, whether the query is N+1, and whether the JSON is streamed, is optimising the wrong 95%. The winning shape is: production signal (which endpoint, p99 or throughput, CPU or waiting?), trace to find the wait or the hot stack, fix the shape of the I/O, then allocations, then micro-optimisations — each step with a number. Say "I have never seen a span fix a slow endpoint whose problem was 400 database round trips".

Gotcha

Micro-benchmarks lie about GC and about tiering. An allocation-heavy method looks fine in a benchmark with a tiny heap and no other survivors; in production the same allocations promote a large live set and cause gen-2 pauses. And a benchmark without warm-up measures tier-0 code, which BenchmarkDotNet handles but a hand-rolled Stopwatch loop does not. Corollary: a benchmark that claims a win must be followed by the production metric that moved, or it is a hypothesis.

Try it: a runtime upgrade as a benchmark

Take any LINQ-and-dictionary heavy method from a real project, put it in a BenchmarkDotNet project multi-targeting net8.0 and net10.0, and run both jobs with [MemoryDiagnoser]. Then add a lambda that captures a local and passes it to a private generic method and compare again.

Expected outcome

The .NET 10 job is typically 10–30% faster on the same code with no edits, and the closure-passing variant may show zero allocations on .NET 10 where .NET 8 shows the closure and delegate — escape analysis at work — though the effect depends on inlining, which is exactly the lesson. Keep the benchmark project in the repo: it is the cheapest possible argument for the yearly upgrade.

Try it: vectorise, then delete your vectorisation

Write a loop that sums a float[] of 10 million elements, then a Vector256<float> version with a scalar tail, then TensorPrimitives.Sum(span). Benchmark all three, then run with DOTNET_EnableAVX2=0.

Expected outcome

The hand-written SIMD version is 4–8× faster than the scalar loop; TensorPrimitives.Sum matches or beats it, uses AVX-512 where available, and handles the tail and alignment for you. With AVX2 disabled the hand-written version silently falls back to a slower path (or you forgot the IsHardwareAccelerated check and it is now scalar), while the BCL adapts. The lesson to say out loud: write SIMD only for a kernel the BCL does not already provide, and keep the scalar fallback tested.

Interview Q&A

An endpoint's p99 is 800 ms while its median is 40 ms. How do you approach it?

A fat tail with a healthy median points to something intermittent: GC pauses, lock contention, thread-pool starvation, a cold cache, or a downstream dependency's own tail. I correlate first: distributed traces for the slow requests show whether the time is in our process or waiting on a dependency; dotnet-counters shows gen-2 collections and thread-pool queue length at the spike times. If it is GC, I look for LOH churn or a promoted cache; if it is waiting, I look at connection pool exhaustion and missing timeouts; if it is contention, dotnet-trace with the contention keyword names the lock. Only after that do I touch code, and the fix is usually structural — pooling, a bounded cache, a timeout — rather than micro-optimisation.

What is a benchmark you would refuse to merge, and why?

One without [MemoryDiagnoser] when the claim is about allocations; one whose input is unrealistically small, so everything fits in L1 and the "win" vanishes at production size; one comparing against a strawman baseline; one measuring a method that the JIT can constant-fold or dead-code-eliminate because the result is unused; and any hand-rolled Stopwatch loop without warm-up, which measures tier-0 code. I also refuse "it is 30% faster" without the production metric it is supposed to move, because a benchmark is a hypothesis about production, not a result.

How do Span<T>, stackalloc, ArrayPool and string.Create fit together in a parsing hot path?

The input arrives as ReadOnlySpan<byte> or ReadOnlySequence<byte> from a PipeReader; I slice with span methods (IndexOf, Split, SequenceEqual), which are vectorised and allocation-free; small scratch buffers are stackalloc with a size guard, larger ones rented from ArrayPool and returned in a finally; numbers are parsed with Utf8Parser or int.TryParse(span); and the strings I must keep are built once with string.Create or Encoding.UTF8.GetString(span) — the only allocations in the path are the outputs. Since .NET 9, dictionary lookups by span via AlternateLookup mean even key matching does not allocate.

Explain how the JIT's PGO changes the "interfaces are slow" advice.

Dynamic PGO records which concrete type is seen at each interface or virtual call site in tier-0; at tier-1 the JIT emits a guarded direct call for the dominant type — a type check and an inlined body, with the virtual call as fallback. So a monomorphic interface call in a hot loop costs a compare and a branch, not an indirect call, and interface-based design is nearly free. It does not help polymorphic sites with many types, NativeAOT (no runtime profile), or the first few seconds after startup, which is where sealing classes, struct-constrained generics and avoiding interfaces in innermost loops still pay. The honest summary: design with interfaces, and let the profiler tell you the two places where they cost.

When would you reach for SIMD directly, and how do you keep it safe?

Only when profiling names a numeric kernel that the BCL does not already vectorise — Span search and comparison, TensorPrimitives for maths, BitOperations, Vector.Sum-style helpers cover most needs. When I do, I write against Vector128/256/512<T> with IsHardwareAccelerated checks and a scalar tail, keep a scalar reference implementation and a test that compares both over random inputs including the tail sizes, and benchmark on the actual production CPU generation, because AVX-512 downclocking and Arm SVE width make results non-portable. The .NET 10 JIT's AVX10.2 and .NET 11's cross-lane APIs raise the bar for what the BCL does for free.

What are the most common performance mistakes you see in code review?

N+1 queries and unbatched I/O; ToList() in the middle of a query that then filters in memory; string concatenation and interpolation in loops or in log calls; async blocked with .Result; LINQ in hot loops that should be a for over a span; missing dictionary comparers so every lookup normalises a string; new HttpClient() per call; regexes constructed per call instead of [GeneratedRegex]; large arrays allocated per request instead of pooled; and DateTime.Now (a time-zone conversion) where UtcNow was meant. None of them need a profiler to spot; all of them need one to prioritise.

How do you decide between JIT, ReadyToRun and NativeAOT for a new service?

By what the service is measured on. A long-lived API measured on throughput and p99: JIT with tiered PGO, because dynamic profiling beats anything static. A service with strict cold-start requirements — scale-to-zero, serverless, sidecars — NativeAOT, accepting the trimming constraints and the loss of dynamic PGO. A large monolith with slow startup that cannot yet be trimmed: ReadyToRun, which cuts startup JIT time while keeping the JIT for steady state. I decide with a benchmark on the actual app, and I make the AOT-compatibility analyzers part of the build from day one so the door stays open.

Structs of arrays or arrays of structs — when does data layout matter?

When a loop touches one field of many objects, an array of structs pulls whole structs through the cache while the loop uses 8 bytes of each — a struct-of-arrays layout puts the hot field contiguous and can be vectorised. When a loop touches most fields of each object, array-of-structs wins because the data arrives together. Reference-type arrays are the worst of both: an array of pointers to scattered heap objects means a cache miss per element. This matters in numeric code, game loops, and analytics, and does not matter in CRUD services; the tell is a profiler showing time in a loop with a low instructions-per-cycle count.

How do you introduce a performance culture to a team that ships slow code?

Make the numbers visible first: p50/p99 and allocation rate per endpoint on the team dashboard, load tests in CI on the three endpoints that matter, and a benchmark project in the repo. Then set budgets rather than rules — "no endpoint over 200 ms p99, no request over 1 MB allocated" — so the team decides how, and reviews cite the budget. Pair on the first two profiling sessions so people see dotnet-trace find a problem in ten minutes. And celebrate a runtime upgrade as a performance win with the before/after graph, because it teaches that measurement, not cleverness, is the practice.

What is the newest performance-related runtime change you can cite, and what would you do with it?

Two from this year. .NET 10's escape analysis, which stack-allocates non-escaping objects and small arrays, so some closures, boxes and temporaries no longer hit the heap — I would re-run our allocation benchmarks on .NET 10 and delete the hand-written workarounds that no longer pay for themselves. And .NET 11 RC1's Runtime Async, which removes the compiler state machine from async methods and reduces per-await overhead — I would benchmark our async-heavy middleware on 11 and, if it holds, drop the ValueTask micro-optimisations that exist only for the state machine's sake. Both are examples of the same rule: measure before and after a runtime upgrade, because the runtime is the best performance engineer on the team.

13The big Q&A

Everything important that is not a core building block: ecosystem and architecture decisions, security, tooling, legacy reality, and the judgment questions that separate a lead from a senior. Twenty-four questions in six groups.

Architecture and ecosystem decisions

How do you structure a large C# solution so it stays buildable and reviewable at 200 projects?

Fewer, larger projects than people expect — a project is a deployment or a dependency boundary, not a folder — with dependency direction enforced by analyzers or architecture tests rather than by project count. Central package management (Directory.Packages.props) so versions are decided once; Directory.Build.props for shared settings like nullable, warnings-as-errors and analyzers; solution filters (.slnf, editable from the CLI in .NET 11) so nobody opens all 200. Build performance: the MSBuild server and NativeAOT CLI are on by default in .NET 11, and dotnet build --graph plus binary logs find the slow project. When a solution needs more than that, it is usually two solutions with a package boundary between them.

Sealed classes and interfaces everywhere, or inheritance where it fits — what is your default and why?

Default sealed, compose through interfaces, inherit only for genuine is-a with shared state, and then design for it (protected virtuals with documented call order, no virtual calls from constructors). Sealed is a free performance and safety win — devirtualisation, cheaper type checks, no accidental subclassing across an API boundary — and interfaces plus DI are what the test and hosting infrastructure expect. I allow abstract base classes for template-method style frameworks and for record hierarchies that model a closed set, which in C# 15 become closed and get exhaustiveness for free.

When is dynamic acceptable, and what does it cost?

Interop with COM, scripting hosts and genuinely dynamic JSON in throwaway code; almost nowhere else. Every operation on a dynamic value goes through the DLR's call-site cache: a runtime binder that inspects types and generates a delegate, cached per site — roughly reflection speed on the first call and a type check plus delegate call after. It also disables compile-time checking, breaks IntelliSense, and is incompatible with NativeAOT. Modern replacements: JsonNode/JsonElement for loose JSON, generics with static abstract members for "any type with this shape", and source generators where the code used to be written at run time.

How do you evaluate a NuGet package before it enters the codebase?

Maintenance signal: recent releases, responsive issues, more than one maintainer, and a licence the legal team has approved. Technical signal: multi-targeting that includes the current LTS, no unnecessary transitive dependencies, trimming and AOT annotations if we care, and whether it uses reflection or generators. Security: dotnet list package --vulnerable in CI, NuGet audit on by default since .NET 8 SDK, lock files for reproducible restores, and a private feed that mirrors so a deleted package does not break the build. Then the question that matters most: is this 200 lines we could own? A dependency is a permanent maintenance commitment; a small internal utility is not.

Security

What C#-level mistakes turn into security incidents, and how do you prevent them at build time?

SQL built with string concatenation (parameterise, or let EF Core do it; FromSqlInterpolated is safe, FromSqlRaw with interpolation is not); deserialising untrusted input with polymorphic type handling — BinaryFormatter is removed in .NET 9 and TypeNameHandling.All in Newtonsoft is remote code execution; regexes without a timeout on user input (ReDoS; use RegexOptions.NonBacktracking or a matchTimeout); path concatenation without Path.GetFullPath and a root check; Random for secrets instead of RandomNumberGenerator; and comparing secrets with == instead of CryptographicOperations.FixedTimeEquals. Prevention: the security analyzers (CA2100, CA5xxx) as errors, dotnet list package --vulnerable in CI, and a code-review checklist that names these by number.

What do you need to know about cryptography APIs in modern .NET?

Use the platform primitives (Aes.GcmEncrypt-style one-shots, AesGcm, RandomNumberGenerator, SHA256.HashData, Rfc2898DeriveBytes.Pbkdf2, ECDsa) rather than anything hand-rolled, and prefer the static one-shot methods added since .NET 5 because they avoid IDisposable ceremony and mistakes. Data protection for anything app-scoped (IDataProtector). Know that .NET 10 shipped post-quantum algorithms — ML-KEM, ML-DSA and composite ML-DSA — with Windows CNG and OpenSSL backends, and .NET 11 adds X25519 key exchange and unpadded AES key wrap; a lead should know a PQC migration plan is now a concrete engineering task, not a research topic. And never log, serialise or compare keys as strings.

How does trimming and AOT affect security posture?

Positively: a trimmed, AOT-compiled binary has a smaller attack surface (no JIT, no dynamic code, no Reflection.Emit, fewer assemblies loaded), which is why it is attractive for sidecars and edge workloads. The trade-offs are operational: fewer diagnostic hooks, no hot-patching by swapping DLLs, and libraries that used reflection to read configuration may silently see nothing — trim warnings must be treated as errors in CI. It does not change memory safety; C# is memory-safe except in unsafe code, and the C# 15 memory-safety model's point is to make the audit boundary of that unsafe code explicit and caller-visible.

What is the C# 15 memory-safety model and why should a lead care?

C# 15 starts a multi-release effort to tie unsafe to the operations that actually access unmanaged memory rather than to the presence of pointer types. Under the preview rules, declaring pointers, taking addresses, fixed, stackalloc-to-pointer and sizeof no longer need an unsafe context; dereferencing and pointer arithmetic still do; a new unsafe(expr) expression form covers field initialisers and catch filters; and under the updated rules a member marked unsafe becomes "requires-unsafe", pushing the audit obligation to callers, with safe as a modifier for extern members that are known safe. A lead cares because it changes what a security review greps for — the set of things marked unsafe becomes the actual set of dangerous operations — and because it is the language's answer to the memory-safety mandates now appearing in procurement.

Performance and debugging

A memory dump from production is 6 GB. What do you look at first?

dumpheap -stat for the top types by total size, then gcroot on a few instances of the biggest one to find what keeps them alive; eeheap -gc to see the generation sizes and whether the LOH is fragmented; threads and clrstack -all if the question is a hang; syncblk for lock owners; dumpasync to see incomplete async state machines and what they wait on. Before opening anything I check the dump was taken with the right runtime version so SOS resolves symbols, and that the process's memory limit and the GC's view of it agree — a "6 GB dump" with a 4 GB cgroup limit is a finding by itself.

How do you profile CPU in production without a profiler on the box?

dotnet-monitor as a sidecar or dotnet-trace in the image, both over EventPipe, collecting a sampled CPU trace for 30–60 seconds on demand; continuous profiling through the OpenTelemetry collector where the platform supports it. Open the .nettrace in PerfView, Visual Studio, or convert to speedscope. The trace also carries GC, contention, exception and thread-pool events, so one capture usually answers the CPU question and the "why is it waiting" question. What I do not do is attach a debugger to production or guess from logs.

What is thread-pool starvation, how do you detect it, and what is the fix?

All pool threads are blocked (sync-over-async, lock waits, long synchronous I/O), the queue of pending work grows, and the pool injects new threads slowly — historically one or two per second — so latency climbs steadily while CPU stays low. Detection: threadpool-queue-length rising with threadpool-thread-count creeping upward in dotnet-counters, and dumps showing dozens of threads in Monitor.Wait or Task.Wait. The fix is removing the blocking — async all the way — not raising MinThreads, which only delays the symptom. .NET 6+ has starvation mitigations and .NET 9 improved injection heuristics, but none of it makes blocking safe.

How do you debug a bug that only reproduces in Release?

Release means optimised JIT: inlining, dead-store elimination, reordered reads, locals living in registers. Bugs that appear only there are usually a data race that debug timing hid, reliance on a finalizer or a local keeping an object alive (the JIT ends a local's lifetime at last use in Release — GC.KeepAlive exists for that), a struct copy that a debug build made observable, or floating-point differences from fused operations. Approach: reproduce with DOTNET_TieredCompilation and DOTNET_JitDisasm variations to narrow which optimisation matters, add [MethodImpl(NoInlining)] to bisect, and reach for volatile/Interlocked or proper synchronisation rather than "it works in Debug".

Tooling and delivery

What is in your Directory.Build.props for a new service, and why each line?

TargetFramework net10.0 (LTS); Nullable enable and WarningsAsErrors nullable; ImplicitUsings enable; TreatWarningsAsErrors true with a short, deliberate NoWarn list; AnalysisLevel latest-recommended and EnforceCodeStyleInBuild true so style is a build concern; Deterministic, ContinuousIntegrationBuild in CI and Source Link for traceable binaries; IsAotCompatible on libraries that might be published AOT; InvariantGlobalization when the service has no user-facing culture work (smaller images, faster startup); and central package management with NuGet audit on. Every line is a decision the team no longer has to make per project.

How do you test C# code that touches time, randomness and the file system?

Inject the seams the platform now provides: TimeProvider (.NET 8) with FakeTimeProvider from Microsoft.Extensions.TimeProvider.Testing for clocks and timers, Random passed in with a seed, and System.IO.Abstractions or a temp-directory fixture for files. For HTTP, a DelegatingHandler fake or WebApplicationFactory with the real pipeline; for databases, Testcontainers over an in-memory provider that lies about SQL semantics. Test framework: xUnit v3 on Microsoft.Testing.Platform is the .NET 10/11 template default, and dotnet test gained --timeout, --maximum-failed-tests and per-module results in .NET 11. The principle: fake at the boundary the platform designed for faking, not one layer in.

What is your position on TreatWarningsAsErrors and analyzers in a codebase that has 3 000 existing warnings?

Ratchet, don't flip. Turn on warnings-as-errors for new categories immediately (nullable, security, the async rules) and for the whole set per project as each project reaches zero; generate an .editorconfig baseline that silences existing occurrences with a tracked count that must go down, and a CI check that fails when it goes up. Pair analyzers with code fixes so cleanup is dotnet format rather than manual work. The goal is a state where a warning means "something new is wrong", which is only true when the count is zero.

How do you run C# in the cloud today: containers, AOT, Aspire — what is the default?

Containers built by the SDK (dotnet publish /t:PublishContainer, no Dockerfile, chiselled Ubuntu base images, multi-arch in .NET 11 with platform-native runtimes tried before Docker), pushed with reproducible digests; JIT with server GC and DATAS for long-lived APIs, NativeAOT for cold-start-sensitive workloads; Aspire (13.x with .NET 10) for local orchestration, service discovery and OpenTelemetry wiring, with its app-host manifest feeding the deployment tooling. Health checks, IHostApplicationLifetime-aware shutdown with a drain period, and DOTNET_gcServer plus memory limits tuned per pod size. The default is "make the boring path the SDK's path", because that is what gets patched every month.

Legacy and migration reality

How do you migrate a .NET Framework 4.8 application to .NET 10, and what breaks?

Inventory with the upgrade assistant and the API portability analyzer; move shared libraries to netstandard2.0 first so both worlds can consume them; convert to SDK-style projects; then port the host last. What breaks: System.Web (HttpContext, Web Forms, MVC 5 filters) — ASP.NET Core rewrite or the SystemWebAdapters for incremental migration via YARP; WCF services (CoreWCF or gRPC); AppDomains and remoting (gone); BinaryFormatter (removed); System.Drawing on Linux; configuration from web.config; and behavioural changes like culture-sensitive string comparison (ICU on Linux) and the thread-pool defaults. I plan it as a strangler-fig with YARP in front, migrating routes, and I budget for the test suite first — a Framework app without tests is a rewrite, not a migration.

What legacy C# patterns do you still see in codebases, and what do you replace them with?

ArrayList/Hashtable → generics; IEnumerable non-generic → IEnumerable<T>; Thread and BackgroundWorker → Task and hosted services; BeginX/EndX APM and event-based async → Task via TaskFactory.FromAsync or TaskCompletionSource; lock(this) and lock(typeof(X)) → a private Lock; string.Format → interpolation; manual Dispose patterns with finalizers → SafeHandle; DllImport → LibraryImport; reflection-based mappers → generators; DataSet → EF Core or Dapper; Newtonsoft.Json → System.Text.Json where the polymorphism and naming needs allow. The rule: replace on touch, with a test, and never as a standalone "modernisation" PR that changes 400 files.

Newtonsoft.Json or System.Text.Json in 2026?

System.Text.Json for anything new: it is in the box, faster, allocation-conscious, source-generated for AOT, and since .NET 7–10 it covers polymorphism ([JsonDerivedType]), required members, JsonNode for dynamic documents, strict mode and duplicate-property rejection (.NET 10), and in .NET 11 union-type serialisation, per-member naming policies and NDJSON streaming. Newtonsoft stays where its behaviours are load-bearing — TypeNameHandling contracts (which are also a security liability), custom contract resolvers, or third-party SDKs that require it. When both live in one app, I isolate Newtonsoft behind the one integration that needs it, because two serializers with different defaults in one process is a bug factory.

A dependency still targets netstandard2.0. Is that a problem?

Not by itself: netstandard2.0 is the widest-reaching target and is what libraries that support .NET Framework must use; the .NET 10 runtime consumes it fine. The costs are that the library cannot use span-based or modern APIs without polyfills, may carry System.Memory-style shims, and lacks nullable and trimming annotations unless the author added them. The problem signals are different: a library that targets only net48, or one that has not shipped since 2020, or one that uses reflection in ways trimming cannot see. The netstandard2.1 middle ground is mostly dead — it excludes Framework and adds little — so I expect netstandard2.0 plus a modern TFM in a well-maintained package.

Judgment and scenarios

What do you look for first in a C# code review?

Behaviour the tests do not cover, then lifetimes and boundaries: is anything disposable not disposed, does any scoped thing get captured by a singleton, does any async path block, does any exception get swallowed, does any input reach SQL, a path or a regex unvalidated. Then the shape of the I/O (N+1, missing cancellation, unbounded fan-out). Only then style, and style should have been an analyzer. My most frequent comments are "who disposes this", "what happens when this is cancelled", and "this could be a record" — and the meta-rule that a review comment that could have been an analyzer becomes one.

How would you introduce C# 15 unions to a team that has a Result<T> library and strong opinions?

Not by decree. First on .NET 11, since the runtime support is new; then a pilot in one bounded context where the exhaustiveness check would have caught a real bug — every team has the story of the unhandled case that paged them. Show the diff: a union LookupResult(Customer, NotFound, RateLimited) with a switch that fails to compile when a case is added, versus the Match(f1, f2, f3) lambdas. Mark the existing Result types with [Union] so both styles pattern-match the same way and migration is incremental. Keep the library for the things unions do not yet do — value-type cases without boxing, monadic Bind/Map — and be honest about the first-release limitations. The team decides at the pilot retrospective.

Two senior engineers disagree: one wants DDD-style rich entities with private setters, the other wants records and services. How do you settle it?

By asking what varies. Where invariants span fields and change over time — an order that moves through states with rules — a rich entity with a constructor, private setters and behaviour methods protects the invariant at the type; where data is transported, projected or compared — DTOs, events, read models — records with required init properties are simpler and safer. Most systems need both, and the fight is usually about a boundary that has not been drawn. I draw it: entities inside the aggregate, records at every edge, and a mapping step that is boring on purpose. Then I write the decision down as an ADR so the argument does not restart in three months.

An interviewer asks: "what would you change about C# if you could?"

A principal-level answer names real tensions rather than wishes. Null: NRT are annotations, and the language still cannot make non-nullability a runtime guarantee without breaking the ecosystem; I would love a real non-nullable reference type but I understand why it is not coming. Unions: boxing value-type cases in the first release is the wrong default for numeric code, and I expect it to be fixed. Async: Runtime Async finally puts the state machine where it belongs, and the next step is structured concurrency — a scope that guarantees child tasks complete or cancel — which the BCL still leaves to libraries. And the version story: the annual cadence is good, but a year of STS-versus-LTS conversations per release is a cost, and the November 2026 double end-of-support shows how it bites.
