01Type system and value semantics

Every C# loop starts here, because it is the cheapest way to find out whether you understand the runtime or only the syntax. Interviewers use it as a fast filter at screener level ("value versus reference type") and then as a depth probe at senior level, where the real questions are about equality contracts, defensive copies and when a struct is worth its cost. At lead level you are expected to reason about what a type choice does to an API you cannot change later — struct layout, boxing in hot paths, and the equality semantics your callers will assume.

screenerWhat is the difference between a value type and a reference type?

Answer

A value type variable holds the data itself; a reference type variable holds a reference to an object that lives on the managed heap. Copying a value type copies the bits, so two variables are independent; copying a reference copies the pointer, so both names see the same object. The practical consequences are assignment semantics, equality defaults (value types compare field-by-field, reference types compare identity unless overridden), null (only reference types and Nullable<T> can be null), and allocation (value types live inline — in a stack frame, in an array's storage, or inside the containing object — so they do not individually cost a GC allocation). The "stack versus heap" shorthand is wrong often enough to be dangerous: a struct field of a class lives on the heap inside that class, and a captured local can be hoisted into a compiler-generated class.

Example

struct P { public int X; }
class  C { public int X; }

var p1 = new P { X = 1 }; var p2 = p1; p2.X = 9;   // p1.X == 1  (copy)
var c1 = new C { X = 1 }; var c2 = c1; c2.X = 9;   // c1.X == 9  (same object)

var arr = new P[1000];   // ONE allocation, 1000 structs inline
var brr = new C[1000];   // 1001 allocations: the array + 1000 objects

Follow-ups

  • Do value types always live on the stack? — No. They live wherever their container lives: a field of a class is on the heap, a captured local is in a closure object, an async local is in the state machine.
  • Is string a value type because it behaves like one? — No, it is a reference type; it just happens to be immutable and to override == to compare content.
  • What is the size limit that makes a struct a bad idea? — There is no hard rule, but past roughly 16-24 bytes the copy cost usually outweighs the saved allocation; measure rather than guess.

Common wrong answer

"Value types go on the stack, reference types go on the heap." It is the textbook sentence and interviewers use it as a trap: the moment they ask about a struct inside a class, or a local captured by a lambda, the model collapses. Say storage location follows the container instead.

screenerWhat is boxing, and where does it actually hurt?

Answer

Boxing wraps a value type in a heap object so it can be treated as object or as an interface; unboxing copies it back out with a type check. Each box is a heap allocation plus a copy, so it hurts in loops, in logging on hot paths, and in any API that takes object or a non-generic interface. The places it happens silently are what interviewers probe: calling a struct method that comes from object without an override, using a struct through an interface without a generic constraint, string interpolation and string.Format with value arguments, and old non-generic collections such as ArrayList or Hashtable. Modern C# removes most of the accidental ones — generics avoid it entirely, and since C# 10 interpolated string handlers let logging APIs format without boxing — but the check is still "does this value cross an object boundary?".

Example

int i = 42;
object o = i;                     // box: allocation + copy
int j = (int)o;                   // unbox: type check + copy

IComparable c = i;                // box (interface)
void Take<T>(T x) where T : IComparable<T> { }
Take(i);                          // no box: constrained generic call

// The one people miss: a struct's default ToString/Equals/GetHashCode
struct S { }                      // no override -> ValueType.Equals uses reflection AND boxes
Console.WriteLine(default(S).Equals(default(S)));

Follow-ups

  • Does foreach over a List<int> box? — No; List<T> exposes a struct enumerator and foreach binds to it by pattern. Casting the list to IEnumerable<int> first does box the enumerator.
  • How do you find boxing in a real codebase? — Allocation profiling (dotnet-counters, PerfView, or a BenchmarkDotNet MemoryDiagnoser run) and the IL: look for the box opcode.
  • Why is an unoverridden struct Equals so slow? — ValueType.Equals falls back to reflection over the fields when the type is not bitwise-comparable, on top of boxing both operands.

Common wrong answer

"Boxing is when you convert a value type to a reference type, but the JIT optimises it away." The JIT does elide some boxes since .NET 9 in narrow cases, but treating it as free is how a hot loop ends up allocating gigabytes. The right answer names a concrete place it happens in the candidate's own code.

midWhen would you actually declare a struct instead of a class?

Answer

When the type is small, logically a single value, immutable, and allocated in quantity — the classic examples in the BCL are DateTime, Guid, TimeSpan, Span<T> and the System.Numerics vectors. The payoff is that a million of them cost one array allocation instead of a million objects, which removes GC pressure and improves cache locality. The costs are real and permanent: every pass copies, defensive copies appear if the struct is not readonly, it cannot inherit, and putting it in an object-shaped API boxes it. My default is class or record, and I only reach for a struct when a measurement says allocation is the problem — or when the type is genuinely a value, like a strongly-typed id.

Example

// A strongly-typed id: value semantics, 16 bytes, no allocation per row.
public readonly record struct OrderId(Guid Value)
{
    public override string ToString() => Value.ToString("N");
}

// Not a struct: mutable, has behaviour, lives in a graph.
public sealed class Order { public OrderId Id { get; init; } /* ... */ }

Follow-ups

  • Why readonly struct? — It tells the compiler no member mutates this, so passing by in or reading from a readonly field does not create a hidden defensive copy.
  • What breaks if a struct is mutable? — Mutating a struct held in a collection or property mutates a copy; the change silently disappears. Since C# 7.2 the compiler stops the worst cases, but not all.
  • What about ref struct? — Stack-only (Span<T>): it cannot be boxed, stored on the heap, or (before C# 13) used in async methods or iterators.

Common wrong answer

"Use a struct when the object is small and short-lived, it's faster." Repeated without measurement it produces mutable 60-byte structs passed by value through five layers, which is slower than the class it replaced and produces bugs when someone mutates a copy. The credible answer names the measurement that justified it.

midWhat does record give you that a class does not, and when do you not want it?

Answer

A record (C# 9; record struct in C# 10) is a class or struct with compiler-generated value equality, GetHashCode, a ToString that prints the members, a Deconstruct, and a with expression that copies-and-modifies through a synthesised clone. That makes it the right default for DTOs, messages, events and query results — anything where two instances with the same data should be considered the same thing. You do not want it for entities with identity (an EF Core entity is equal to another by primary key, not by every field), for mutable domain objects with invariants, or where the generated ToString would print secrets into a log. Note the equality is field-based including inherited state, and for a record class the runtime types must match, so a derived record is never equal to its base.

Example

public record Money(decimal Amount, string Currency);

var a = new Money(10m, "EUR");
var b = a with { Amount = 12m };
a == new Money(10m, "EUR");   // true  - value equality
a.ToString();                 // "Money { Amount = 10, Currency = EUR }"

// Careful: a record is only shallowly immutable.
public record Basket(List<string> Items);   // the list is still mutable and
                                            // equality compares list REFERENCES

Follow-ups

  • Are records immutable? — Positional parameters become init-only properties, so the record's own references cannot be reassigned; anything they point at can still be mutated.
  • How does with work? — It calls a synthesised copy constructor and then sets the listed init members; it is a shallow copy.
  • Why can a record's equality be a performance problem? — It compares (and hashes) every field, so a record holding a large array is expensive as a dictionary key.
  • record struct vs readonly record struct? — Prefer readonly record struct; a plain record struct has settable properties and reintroduces mutable-struct problems.

Common wrong answer

"Records are immutable classes." Half true and it leads to the real bug: a record with a List or array member is treated as a safe value, shared across threads, and mutated by one of them — while equality quietly compares references and never matches.

midExplain the Equals / GetHashCode contract. What breaks when you get it wrong?

Answer

The contract is: equal objects must return the same hash code, the hash must not change while the object is used as a key, and Equals must be reflexive, symmetric, transitive and consistent. Break the first rule and hash-based lookups miss — the entry is in a different bucket from the one the lookup probes, so Dictionary and HashSet "lose" items that are still there. Break the second by mutating a field that participates in the hash after insertion and you get the same symptom, intermittently, which is one of the nastiest bugs to diagnose. In modern C# I let the compiler do it — a record, or HashCode.Combine(a, b, c) — and I make key types immutable so the second rule cannot be broken.

Example

var key = new MutableKey { Id = 1 };
var set = new HashSet<MutableKey> { key };
key.Id = 2;                    // hash changed while in the set
set.Contains(key);             // false - and Remove(key) also fails: a permanent leak

// Correct: immutable key + compiler-generated equality
public readonly record struct TenantKey(Guid Tenant, string Region);

Follow-ups

  • Must unequal objects have different hash codes? — No; collisions are legal and expected. Only the equal-implies-same-hash direction is required.
  • Is string.GetHashCode() stable across processes? — No. Since .NET Core it is randomised per process, so never persist it or use it as a shard key; use a stable hash such as xxHash or SHA-256 truncated.
  • What about IEquatable<T>? — Implement it on value types to let collections compare without boxing; EqualityComparer<T>.Default picks it up.

Common wrong answer

"Override Equals and return base.GetHashCode()" — or override only Equals and let the analyser warning slide. The class then behaves correctly in a list and incorrectly in a dictionary, which is exactly the bug that survives code review and surfaces in production caching.

midWhy is string immutable, and what does that cost you in practice?

Answer

Immutability makes strings safe to share across threads without locking, allows interning of literals, and lets the runtime cache the length and hash — which is why a string can be a dictionary key at all. The cost is that every "modification" allocates: concatenating in a loop is O(n squared) in bytes, and the classic fix is StringBuilder, or in modern C# string.Create, interpolated string handlers, or working over a ReadOnlySpan<char> with slicing so no intermediate string is allocated. The second practical cost is comparison: == and the default Equals are ordinal, but many BCL methods historically defaulted to culture-sensitive comparison, so the rule is to pass StringComparison explicitly — Ordinal or OrdinalIgnoreCase for identifiers, protocol tokens and file paths, culture-aware only for text shown to a human.

Example

// O(n^2) allocations - the interview classic
var s = ""; foreach (var w in words) s += w + ",";

// Correct
var sb = new StringBuilder(); foreach (var w in words) sb.Append(w).Append(',');

// Zero-allocation parsing over a span
ReadOnlySpan<char> line = "id=42;name=ada";
var id = int.Parse(line.Slice(3, 2));

// Culture bug that reaches production in Turkish locales
"FILE".ToLower() == "file";                          // depends on culture
"FILE".Equals("file", StringComparison.OrdinalIgnoreCase);  // correct

Follow-ups

  • What is string interning? — Literals are pooled per process so identical literals share one instance; string.Intern adds runtime strings to that pool, which is a memory leak risk because the pool is never collected.
  • Is == on strings reference or value comparison? — Value (ordinal) comparison; object.ReferenceEquals is how you ask about identity.
  • When is culture-sensitive comparison right? — Sorting or matching text a user reads. Everything machine-facing is ordinal — the "Turkish I" problem is the standard example.

Common wrong answer

"Strings are immutable so use StringBuilder always." Overcorrecting: for two or three concatenations, interpolation is faster and clearer, and StringBuilder itself allocates. The signal interviewers want is knowing where the quadratic behaviour appears — loops with unknown length — not a blanket rule.

seniorWhat is a defensive copy, and how do readonly struct and in parameters relate to it?

Answer

When you call a member on a struct held in a readonly field, or on an in parameter, the compiler must guarantee the value cannot be mutated. If the struct is not declared readonly and the member is not readonly, the compiler cannot know, so it silently copies the struct before the call — a defensive copy, on every call, in the hot path. Declaring the type readonly struct (C# 7.2) or individual members readonly (C# 8) removes the copy. This is a real measured effect: a 40-byte non-readonly struct in a readonly field can make a property getter several times slower than the same code in a class. in passes by reference to avoid copying large structs at the call site, but it only pays off when the type is readonly, otherwise you trade one copy for many.

Example

struct Big { public long A, B, C, D; public long Sum => A + B + C + D; }

class Holder
{
    private readonly Big _b;          // NOT a readonly struct
    public long Get() => _b.Sum;      // copies all 32 bytes on every call
}

readonly struct BigRo { public readonly long A, B, C, D; public long Sum => A + B + C + D; }
// same field, no copy - and 'in BigRo' at call sites is now a genuine win

Follow-ups

  • How do you spot it? — Look at the IL for an unexpected ldobj/stloc pair before the call, or benchmark the getter; analyser rule CA1067 and the readonly IDE hints catch the common cases.
  • When should you use in? — For readonly structs larger than roughly 16-24 bytes on a hot path; below that the indirection costs more than the copy.
  • What is ref readonly for? — Returning a large struct from an array or buffer without copying, e.g. ref readonly T from a span-like collection.

Common wrong answer

"Adding in everywhere makes struct passing cheaper." Applied to mutable structs it makes things slower — the compiler inserts a defensive copy at each member access — and applied to int-sized values it adds a pointer dereference for nothing.

seniorNullable reference types versus Nullable<T>: what is actually enforced at runtime?

Answer

Nullable<T> is a real runtime type — a struct with a value and a HasValue flag, with compiler and runtime support for lifting, boxing to either null or the underlying value, and pattern matching. Nullable reference types (C# 8, on by default in new project templates since .NET 6) are purely compile-time: they annotate reference types with metadata attributes and produce warnings, and nothing at runtime stops a null arriving from an unannotated library, from reflection, from deserialization, or from another assembly compiled with the feature off. So the design rule is: use the annotations to express intent and let the compiler find the holes, but still validate at trust boundaries — public API entry points, deserialized payloads, and interop — with ArgumentNullException.ThrowIfNull (.NET 6). Treating warnings as errors in new code and leaving legacy files with a per-file #nullable pragma is the standard migration shape.

Example

#nullable enable
string? maybe = GetName();          // compile-time annotation only
int? count = null;                  // Nullable<int>: a real struct

public void Handle(Order order)     // non-nullable by declaration...
{
    ArgumentNullException.ThrowIfNull(order);   // ...but still validated at the boundary
}

// JSON can produce a null in a non-nullable property with no warning at all:
public sealed class Dto { public string Name { get; set; } = ""; }

Follow-ups

  • What does ! (null-forgiving) mean? — "Trust me, compiler." It suppresses the warning and changes nothing at runtime; each use should be justifiable in one sentence.
  • How do you migrate a large legacy codebase? — Enable at the project level, treat the flood as debt, fix per file or per layer with #nullable enable, start at the domain core, and never bulk-insert !.
  • What are the attributes for? — NotNullWhen, MemberNotNull, MaybeNullWhen etc. teach flow analysis about TryParse-shaped APIs and initialisation helpers.

Common wrong answer

"With NRTs enabled you don't need null checks any more." That belief plus a JSON deserializer is a guaranteed NullReferenceException in production; the annotations do not cross assembly, reflection, or serialization boundaries.

seniorCompare is, as, casting and dynamic. What do they cost?

Answer

A cast performs a type check and throws InvalidCastException on failure; as does the same check and yields null, so it is for reference and nullable types only; is tests and, in pattern form, binds in one step, which is the modern idiom and avoids the double check the old is-then-cast pattern produced. All three are cheap — a type handle comparison, or a walk up the hierarchy for interfaces — and the JIT optimises common shapes. dynamic is in a different class entirely: it defers binding to the DLR at runtime, allocates call sites, costs one to two orders of magnitude more per call than a virtual call, breaks refactoring and IntelliSense, and is not supported in Native AOT. I use dynamic only for genuine late-bound interop (COM, ExpandoObject-shaped JSON) and never on a hot path.

Example

// legacy double-check
if (o is Customer) { var c = (Customer)o; Use(c); }

// modern: one check, one bind
if (o is Customer c) Use(c);

// switch on shape (C# 7+, extended by list/property patterns in 8-11)
var label = shape switch
{
    Circle { Radius: > 100 } => "big circle",
    Circle => "circle",
    Rect { W: var w, H: var h } when w == h => "square",
    null => "none",
    _ => "other",
};

Follow-ups

  • Which is faster, as plus null check or is pattern? — They compile to the same thing today; choose for readability.
  • Why avoid casting in a hot loop? — Not the cast itself but what it implies: a heterogeneous collection you could have made generic, which also usually boxes.
  • What replaces dynamic for JSON? — JsonNode/JsonElement in System.Text.Json, or a source-generated contract; both work under AOT.

Common wrong answer

"as is faster than a cast because it doesn't throw." Exceptions cost nothing when not thrown; the two perform identically on success. The real difference is the failure contract — and answering with a performance myth signals cargo cult rather than measurement.

principalA team wants to introduce strongly-typed ids (record struct OrderId) across a large codebase. Do you approve it?

Answer

Usually yes for new code, but scoped, because the benefit is real and the tax is broad. The benefit is that Transfer(OrderId, CustomerId) cannot be called with the arguments swapped — a whole class of bug that testing rarely catches — and it makes primitive obsession visible. The tax is at every boundary: EF Core needs a value converter per id, System.Text.Json needs a converter or a source-generated one, minimal-API route binding needs TryParse or IParsable, Dapper needs type handlers, and logging or Swagger will show a wrapper unless configured. So I would approve it with three conditions: a single shared source generator or a small base pattern so all the converters are written once, an agreed migration boundary (new aggregates only, not a big-bang rewrite), and a measured check that hot paths do not box. If the team cannot commit to the converter infrastructure, the half-done version is worse than primitives.

Example

public readonly record struct OrderId(Guid Value) : IParsable<OrderId>
{
    public static OrderId New() => new(Guid.CreateVersion7());   // .NET 9: sequential GUIDs
    public static OrderId Parse(string s, IFormatProvider? p) => new(Guid.Parse(s));
    public static bool TryParse(string? s, IFormatProvider? p, out OrderId r)
    {
        if (Guid.TryParse(s, out var g)) { r = new OrderId(g); return true; }
        r = default; return false;
    }
    public override string ToString() => Value.ToString("N");
}
// EF Core: builder.HasConversion(id => id.Value, v => new OrderId(v));

Follow-ups

  • What is the cheapest 80% version? — Types only on the aggregate roots that actually get confused (order/customer/tenant), not on every column.
  • Any runtime cost? — A readonly record struct wrapping a Guid is the same 16 bytes; the risk is boxing when it lands in an object-typed dictionary or a non-generic logging call.
  • How do you keep the migration honest? — An analyser or an architecture test that fails when a new public method takes a raw Guid id.

Common wrong answer

"Yes, it's a best practice, let's roll it out everywhere." Approving a cross-cutting type change without naming the serialization, ORM and routing work is exactly what turns into a six-month half-migration where half the code uses Guid and half uses OrderId, with converters at every seam.

02Async, await and the task model

Async is the highest-yield sub-area after the type system, because almost every .NET service is I/O bound and almost every production incident in one has an async cause: thread-pool starvation, a sync-over-async deadlock, an unobserved exception, or an unbounded fan-out. Screener questions check that you know await does not create a thread; senior questions hand you code and ask what happens under load; principal questions are about how you stop a team from reintroducing the same failure. This unit stays at language level — the full internals live in the separate C# async bank.

screenerWhat does await actually do?

Answer

The compiler rewrites the method into a state machine. At each await it asks the awaited thing whether it has already completed: if yes, execution continues synchronously with no suspension at all; if not, it registers a continuation and returns control to the caller, freeing the current thread. When the operation completes, the continuation resumes the state machine — on the captured SynchronizationContext or TaskScheduler if there is one, otherwise on a thread-pool thread. So await is not "wait here"; it is "return now, resume later", and that is exactly why an ASP.NET Core server can hold 10,000 in-flight requests on a few dozen threads. In .NET 10 the compiler-generated state machine is still the default model; .NET 11 moves this into the runtime itself (runtime-async), which changes the mechanics but not this contract.

Example

async Task<int> ReadAsync()
{
    var s = await _http.GetStringAsync(url);   // returns to caller here if not complete
    return s.Length;                           // resumes on a pool thread later
}
// Roughly: MoveNext() { switch (_state) { case -1: ... awaiter.OnCompleted(MoveNext); return;
//                                        case 0: result = awaiter.GetResult(); ... } }

Follow-ups

  • What if the task is already complete? — No suspension, no allocation of a continuation; the method runs straight through, which is why fast-path async is nearly free.
  • Where does the state machine live? — As a struct while the method runs synchronously; it is boxed onto the heap only when the method actually suspends.
  • What is the awaitable pattern? — Anything with GetAwaiter() returning a type with IsCompleted, OnCompleted and GetResult; that is how ValueTask and custom awaitables work.

Common wrong answer

"await runs the method on a background thread so the caller isn't blocked." That describes Task.Run, not await, and the candidate who says it will also propose wrapping every database call in Task.Run — which adds a thread hop and makes throughput worse.

screenerTask versus Thread: does async make my code multithreaded?

Answer

No. A Thread is an OS scheduling unit costing about a megabyte of stack; a Task is a promise of a future result, which may be backed by a thread-pool work item, by an I/O completion with no thread at all, or by nothing (a completed task). For genuine I/O — sockets, files, database calls — the async path uses an OS completion mechanism (IOCP on Windows, epoll/io_uring on Linux) and no thread is held while the operation is in flight; that is the whole point. Threads still matter for CPU-bound work, where Task.Run moves work to the pool, and the pool's growth behaviour (it injects new threads slowly, historically about one or two per second after the minimum is exhausted) is what turns a blocked call into a latency cliff.

Example

// I/O bound: no thread is consumed while waiting
await using var conn = new SqlConnection(cs);
await conn.OpenAsync(ct);

// CPU bound: offload explicitly, and only in a UI or when parallelising
var hash = await Task.Run(() => ComputeExpensiveHash(bytes), ct);

// Wrong on a server: wraps an already-async call in a pool thread for nothing
var s = await Task.Run(() => _http.GetStringAsync(url));

Follow-ups

  • When is Task.Run right on a server? — Rarely: only to parallelise genuinely CPU-bound work, and then with a bounded degree of parallelism.
  • What is thread-pool starvation? — Blocking calls consume pool threads faster than the pool injects them; queued work waits, latency climbs and eventually everything times out. It looks like a hang with low CPU.
  • How do you see it? — dotnet-counters: rising threadpool-queue-length and threadpool-thread-count with flat CPU. A dump shows most threads inside a .Wait() or .Result.

Common wrong answer

"A Task is a lightweight thread." It implies every task consumes a thread, which is the mental model behind wrapping everything in Task.Run and behind the belief that async increases parallelism. Async increases concurrency per thread; it does not add parallelism.

midWhy does .Result deadlock, and how do you fix a codebase full of it?

Answer

In a context with a single-threaded SynchronizationContext — classic ASP.NET, WinForms, WPF — the awaiting continuation is scheduled back onto that context. If the caller is blocking that same context with .Result or .Wait(), the continuation can never run, the task never completes, and the block never ends: a self-deadlock. ASP.NET Core has no synchronization context, so the pure deadlock is gone there, but the pattern is still harmful because it consumes a pool thread per in-flight call and produces thread-pool starvation under load — a slower, more confusing version of the same outage. The fix is async all the way: change the call chain to async Task up to the entry point; where a boundary genuinely cannot be async (a constructor, an interface you do not own, a legacy plug-in), isolate it behind an explicitly named adapter and document why.

Example

// Deadlocks on WPF/WinForms/legacy ASP.NET; starves the pool on ASP.NET Core
public string Get() => GetAsync().Result;

// Fix: propagate async
public Task<string> GetAsync() => _http.GetStringAsync(url);

// Last-resort bridge - visible, named, and rare
private static readonly TaskFactory _bridge = new(CancellationToken.None,
    TaskCreationOptions.None, TaskContinuationOptions.None, TaskScheduler.Default);
public static T RunSync<T>(Func<Task<T>> f) => _bridge.StartNew(f).Unwrap().GetAwaiter().GetResult();

Follow-ups

  • Does ConfigureAwait(false) fix it? — It prevents the deadlock at every await in the callee, but you must own the entire chain; it does not fix the thread starvation, so it is a mitigation, not the fix.
  • What about GetAwaiter().GetResult()? — Same blocking, but it rethrows the original exception instead of an AggregateException. Still blocking.
  • How do you stop it coming back? — Ban it with an analyser (for example the Microsoft.VisualStudio.Threading analysers, or a Roslyn rule set to error) so the build fails rather than the review.

Common wrong answer

"On ASP.NET Core .Result is fine now because there's no synchronization context." True about the deadlock, wrong about production: it converts an I/O wait into a held thread, which is the single most common cause of "the service hangs at peak with 5% CPU".

midDo you still write ConfigureAwait(false)? Where?

Answer

In library code, yes, on every await, because a library does not know whether its caller has a synchronization context, and capturing one it does not need costs a scheduling hop and risks the caller's deadlock. In application code on ASP.NET Core, no: there is no synchronization context, so it is noise. In UI code you want the opposite — the default capture is what puts you back on the UI thread to touch controls. Since .NET 8 there is also ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing) and friends for finer control, and ConfigureAwaitOptions.ForceYielding when you deliberately want to break a synchronous fast path. The lead-level version of the answer is to make it uniform per assembly and enforce it with an analyser rather than argue about it in review.

Example

// library
public async Task<Doc> LoadAsync(Uri u, CancellationToken ct)
{
    var json = await _http.GetStringAsync(u, ct).ConfigureAwait(false);
    return await Parse(json).ConfigureAwait(false);
}

// .NET 8+: await a task purely for completion, ignoring its exception
await task.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);

Follow-ups

  • Does it affect which thread the continuation runs on in ASP.NET Core? — No: with no context, the continuation already goes to the thread pool either way.
  • What is the cost of not using it in a library? — A context hop per await in UI callers, and re-enabling the classic deadlock if any caller blocks.
  • Any way to avoid writing it 500 times? — The ConfigureAwaitAnalyzer/CA2007 rule plus a fixer, or wrapping calls in a helper; some teams accept the noise as the cheaper option.

Common wrong answer

"You should always use ConfigureAwait(false) for performance." It is not a performance idiom, and applying it in UI code produces "cross-thread operation not valid" crashes. The correct framing is about context capture and who owns the calling context.

midWhen is async void acceptable?

Answer

Only for event handlers, and only because the delegate signature forces it. The problem is that async void has no task to observe: the caller cannot await it, cannot know when it finished, and an exception inside it is raised on the synchronization context or thread pool, which in ASP.NET Core or a worker service crashes the process rather than failing a request. The correct alternatives are async Task for anything awaitable, and for fire-and-forget work an explicit background mechanism — a hosted service, a channel plus a consumer, or a queue — with its own error handling. In an event handler I still wrap the body in try/catch so a failure becomes a logged, handled error rather than an unhandled exception.

Example

// unavoidable, but defended
private async void OnClick(object? s, EventArgs e)
{
    try { await SaveAsync(); }
    catch (Exception ex) { _log.LogError(ex, "save failed"); ShowError(ex); }
}

// fire-and-forget done properly: a bounded channel consumed by a hosted service
await _channel.Writer.WriteAsync(new EmailJob(id), ct);

Follow-ups

  • What happens to an exception in async void? — It is posted to the context and rethrown there; with no handler it becomes an unhandled exception and terminates the process.
  • Is _ = DoAsync(); better? — Marginally: the task exists and can be observed, but discarded exceptions become TaskScheduler.UnobservedTaskException at GC time; still not a substitute for a real background mechanism.
  • How do you test an async void method? — You largely cannot; that is another reason to keep the body one line that delegates to an async Task method.

Common wrong answer

"async void is fine for fire-and-forget work you don't care about." Teams that say this ship background emailing that silently dies, and a single unhandled exception takes down a container in production instead of failing one operation.

midWhen do you return ValueTask instead of Task, and what are the rules for consuming one?

Answer

ValueTask<T> exists to avoid allocating a Task when a method usually completes synchronously — a cache hit, a buffered read, Channel.ReadAsync when items are queued. Use it on hot, frequently-called APIs where the synchronous path dominates; use plain Task everywhere else, because Task is cacheable (Task.CompletedTask, cached Task<bool> results), composable with WhenAll, and far harder to misuse. The consumption rules are strict: await it exactly once, never await it twice, never call .Result before it completes, and do not pass it around — if you need any of that, call AsTask() first. Violating them does not always throw; with a pooled IValueTaskSource behind it you can silently read another operation's result, which is the kind of bug that takes a week to find.

Example

public ValueTask<User> GetAsync(int id, CancellationToken ct)
    => _cache.TryGetValue(id, out var u)
        ? new ValueTask<User>(u)                 // no allocation on the hot path
        : new ValueTask<User>(LoadAsync(id, ct));

// WRONG: awaited twice
var vt = GetAsync(1, ct);
var a = await vt;
var b = await vt;        // undefined behaviour
// Right: var t = GetAsync(1, ct).AsTask(); await t; await t;

Follow-ups

  • Can you use Task.WhenAll with ValueTasks? — Not directly; convert with AsTask(), which allocates and therefore removes most of the benefit — a sign the API should have returned Task.
  • What is IValueTaskSource? — The pooling mechanism behind allocation-free async in Socket, Channel and PipeReader; it is what makes double-await genuinely dangerous.
  • Does ValueTask help when the method almost always suspends? — No; you pay a slightly larger struct and get no allocation saving. Return Task.

Common wrong answer

"ValueTask is the faster Task, so use it everywhere." Blanket adoption in a service produces no measurable gain, breaks composition with WhenAll, and eventually produces one double-await bug that returns the wrong user's data.

seniorHow do you do cancellation properly? Show a chain from the request to the database.

Answer

Cancellation in .NET is cooperative: a CancellationToken is a signal, and nothing is cancelled unless someone checks it or an API observes it. The rules are to accept a token as the last parameter of every async method, to pass it down unchanged, to check it in loops with ThrowIfCancellationRequested, and to link tokens with CancellationTokenSource.CreateLinkedTokenSource when you want the shorter of a caller's cancellation and a local timeout. In ASP.NET Core, HttpContext.RequestAborted is the client-disconnect token; wiring it to the database call means an abandoned request stops burning a connection. The senior-level detail is where cancellation should not propagate: after a side effect has been committed, cancelling the surrounding operation must not skip the follow-up work, so cleanup and compensation run with CancellationToken.None or a separate timeout.

Example

public async Task<Order> HandleAsync(Request r, CancellationToken ct)
{
    using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
    cts.CancelAfter(TimeSpan.FromSeconds(5));          // caller's token OR 5s, whichever first

    var order = await _db.Orders.FirstAsync(o => o.Id == r.Id, cts.Token);

    await _payments.ChargeAsync(order, cts.Token);      // cancellable
    await _audit.RecordAsync(order, CancellationToken.None);  // must NOT be skipped
    return order;
}

Follow-ups

  • Should OperationCanceledException be logged as an error? — No, a client disconnect is normal; log it at information/debug and make sure it does not increment your error SLO.
  • How do you cancel work that does not accept a token? — You cannot cancel it; you can only stop waiting (Task.WhenAny with a delay) and let it finish in the background — say so explicitly, because the work continues.
  • What is the difference between a timeout and cancellation? — Mechanically nothing; conceptually a timeout is a cancellation you scheduled, which is why CancelAfter and linked sources cover both.
  • Where do tokens get dropped in practice? — At the repository boundary and inside Parallel/Task.Run lambdas; an analyser rule (CA2016) catches most.

Common wrong answer

"I pass CancellationToken.None because cancelling mid-operation could corrupt data." That is a real concern answered in the wrong place: the fix is to make the write path idempotent or transactional and to exclude only the compensating steps, not to make the whole service uncancellable and let abandoned requests hold connections.

seniorWhere do exceptions go in async code? What does Task.WhenAll do with several failures?

Answer

An exception thrown inside an async method is captured and stored on the returned task; it is rethrown when the task is awaited, with the original stack preserved via ExceptionDispatchInfo. If nobody awaits the task, the exception is never observed — since .NET 4.5 that no longer crashes the process, it just disappears (with a TaskScheduler.UnobservedTaskException event at GC time), which is why fire-and-forget silently swallows failures. Task.WhenAll collects all exceptions into an AggregateException on the task, but await rethrows only the first one; to see them all you inspect task.Exception.InnerExceptions after catching. That distinction matters when a fan-out partially fails: awaiting naively logs one failure and hides four.

Example

var tasks = ids.Select(id => FetchAsync(id, ct)).ToArray();
var all = Task.WhenAll(tasks);
try { await all; }
catch (Exception)
{
    foreach (var ex in all.Exception!.InnerExceptions)   // all failures, not just the first
        _log.LogError(ex, "fetch failed");
    throw;
}
// .NET 9+: Task.WhenEach(tasks) streams results as they complete, so you can
// react to the first failures without waiting for the slowest task.

Follow-ups

  • Does an exception before the first await behave differently? — In an async method, no: it is still captured on the task. In a non-async method returning a task it throws synchronously, which is a real API-design inconsistency for argument validation.
  • How do you validate arguments then? — Split: a synchronous wrapper that validates and throws, delegating to a private async local function.
  • What about Task.WhenAny? — It returns the first completed task; the losers keep running and their exceptions go unobserved unless you attach a continuation.

Common wrong answer

"await Task.WhenAll throws an AggregateException, so I catch that." It does not — await unwraps to the first inner exception, so a catch (AggregateException) block never runs and the failure escapes to a generic handler.

seniorYou need to call a downstream API for 10,000 items. How do you write that?

Answer

Not with Task.WhenAll over 10,000 tasks — that starts every call at once, exhausts sockets or the connection pool, and DDoSes the downstream service. The right shape is bounded concurrency: Parallel.ForEachAsync (.NET 6) with an explicit MaxDegreeOfParallelism, or a SemaphoreSlim gate, or a Channel<T> with N consumers when you also want backpressure. The number itself should come from the downstream limit — its documented rate limit or the connection pool size — not from Environment.ProcessorCount, because this is I/O, not CPU. On top of that I add a per-item timeout, a retry with jittered backoff for transient failures only, and a decision made up front about partial failure: collect results and failures, or stop on first error.

Example

var results = new ConcurrentBag<Result>();
await Parallel.ForEachAsync(items, new ParallelOptions
{
    MaxDegreeOfParallelism = 16,      // sized to the downstream's limit, not the CPU count
    CancellationToken = ct
},
async (item, token) =>
{
    using var timeout = CancellationTokenSource.CreateLinkedTokenSource(token);
    timeout.CancelAfter(TimeSpan.FromSeconds(10));
    results.Add(await _client.SendAsync(item, timeout.Token));
});

Follow-ups

  • Why not Parallel.ForEach? — It is for CPU-bound work over synchronous delegates; calling async code inside it blocks pool threads. ForEachAsync is the async-aware version.
  • How do you pick the degree of parallelism? — Start from the downstream constraint (rate limit, pool size, partitions), then measure end-to-end latency and error rate at 2x and 0.5x.
  • What if one item fails? — Decide explicitly: ForEachAsync cancels the rest on an unhandled exception, so catch per item and collect failures when partial success is acceptable.
  • Where does the HttpClient fit? — One shared HttpClient (or IHttpClientFactory), never one per item; MaxConnectionsPerServer is a second, independent limit.

Common wrong answer

"await Task.WhenAll(items.Select(SendAsync)) — it's async so it scales." It is the single most common async mistake in review: 10,000 simultaneous requests, port exhaustion, a downstream outage that looks like your bug, and no way to cancel or throttle after the fact.

principalWhat is changing in async in .NET 11, and what would you tell your team to do about it today?

Answer

The headline change is runtime-async: instead of Roslyn generating a state machine class per async method, the runtime implements suspension and resumption natively, which produces cleaner stack traces, less allocation and lower overhead — public benchmarks show the no-suspension path collapsing to near-synchronous cost. It was an opt-in experiment in .NET 10; in .NET 11 CoreCLR support is on by default, and as of Preview 7 (2026-08-11) async methods compiled this way go through tiered compilation instead of being stuck in tier-0 code, and projects targeting net11.0 no longer need EnablePreviewFeatures. My advice to a team today is: change nothing in your code, because the programming model is identical and the win is free on upgrade — but stop writing code that depends on state-machine internals (stack-frame scraping, AsyncStateMachineAttribute reflection, some profiler-style instrumentation), and treat .NET 11 as the release where you re-baseline async benchmarks rather than one where you rewrite anything.

Example

Timeline
  .NET 9  (Nov 2024)  compiler state machines; STS - end of support 2026-11-10
  .NET 10 (2025-11-11) LTS; runtime-async experimental, opt-in
  .NET 11 (Nov 2026)   STS; runtime-async on by default in CoreCLR,
                       tiered compilation for async (Preview 7, 2026-08-11),
                       no EnablePreviewFeatures needed for net11.0

What survives unchanged: await semantics, Task/ValueTask, cancellation,
ConfigureAwait, exception propagation. What may not: anything that reads or
patches the generated state machine.

Follow-ups

  • Does this remove the need for ValueTask? — It reduces the allocation gap, so the case for ValueTask on marginal APIs gets weaker; keep it where measurement still justifies it.
  • Any risk for existing libraries? — Diagnostics and instrumentation tooling that assumes generated state machines is the main exposure; validate your APM agent before upgrading.
  • .NET 8 or 9 shops — what is the urgent action? — Both reach end of support on 2026-11-10 (STS was extended from 18 to 24 months, which moved .NET 9 from May to November), so the upgrade to .NET 10 LTS is a deadline, not a preference.

Common wrong answer

"Runtime async means we can drop async/await and the runtime handles concurrency." It changes the implementation of the same language feature; the keywords, the cancellation discipline and the blocking rules are all unchanged. Claiming otherwise reads as having skimmed a blog post.

03Collections, LINQ and iterators

This is where interviewers test whether you know what your code costs. Every candidate can write a LINQ chain; the discriminator is whether you can say what it allocates, when it executes, how many times it enumerates the source, and what happens when the same chain runs against a database instead of a list. At mid level expect deferred execution and collection choice; at senior level expression trees, client-side evaluation and concurrent collections; at lead level the review judgment about where LINQ stops being appropriate.

screenerWhat is deferred execution and when has it bitten you?

Answer

Most LINQ operators build a query object and do nothing until something enumerates it — foreach, ToList, Count, First, or an await foreach. That laziness is what makes composition cheap and lets Where plus First stop at the first match, but it has three classic consequences. Enumerating twice runs the query twice, which against a database means two round trips and against a stream means an exception or an empty second pass; captured variables are read at enumeration time, not at definition time, so a mutated loop variable changes results; and exceptions surface at the point of enumeration, far from the line that looks wrong in a stack trace. The rule I apply is: materialise once with ToList/ToArray at the boundary where the data becomes "a result", and keep it lazy inside a pipeline.

Example

var q = orders.Where(o => o.Total > min);   // nothing runs yet
min = 1000;                                 // the closure sees the NEW value
var a = q.Count();                          // enumerates once
var b = q.ToList();                         // enumerates AGAIN

// Against EF Core this is two SELECTs; against a network stream the second
// enumeration throws or returns nothing.

Follow-ups

  • Which operators are eager? — Anything that must see everything or returns a non-sequence: ToList, ToArray, ToDictionary, Count, Sum, OrderBy (buffers on first enumeration), GroupBy.
  • How do you detect double enumeration in review? — A method that takes IEnumerable<T> and uses it more than once; analysers flag it, and the fix is to materialise on entry or to take IReadOnlyCollection<T>.
  • ToList or ToArray? — ToArray for a fixed result you will only read (slightly smaller, and it can use a pooled buffer internally); ToList when the caller may add. The difference is rarely material.

Common wrong answer

"Deferred execution means LINQ is lazy, so it's always faster." It is not a performance property — it moves the cost, and the same laziness is what produces N+1 query storms in EF Core when a lazy sequence is enumerated inside a loop.

screenerWhich interface do you accept as a parameter and which do you return?

Answer

Accept the least specific thing that supports what you actually do: IEnumerable<T> if you enumerate once, IReadOnlyCollection<T> if you need Count or will enumerate twice, IReadOnlyList<T> if you index. Return the most specific thing you can commit to keeping: a concrete IReadOnlyList<T> or an array signals "this is finished data", while returning IEnumerable<T> tells the caller "this may still be lazy and may hit the database when you touch it". The failure mode of taking IEnumerable<T> is accidental multiple enumeration; the failure mode of returning List<T> is that callers mutate your internal state. And IQueryable<T> is not a collection interface at all — returning it from a repository leaks the persistence model into every caller.

Example

// good: honest about what it needs and what it gives back
public IReadOnlyList<Invoice> Overdue(IReadOnlyCollection<Invoice> invoices, DateOnly today)
    => invoices.Where(i => i.Due < today).ToList();

// leaky: the caller can now write .Where(...).ToList() and control your SQL
public IQueryable<Invoice> Query() => _db.Invoices;

Follow-ups

  • Is exposing IQueryable ever right? — In an internal data layer or a deliberately query-shaped API (OData); as the public surface of a domain repository it is a design smell.
  • What about IReadOnlyList versus ImmutableArray? — IReadOnlyList is a view, and the underlying list can still change; ImmutableArray<T> or FrozenSet is a real guarantee.
  • Why not return IEnumerable everywhere for flexibility? — It defers the cost onto callers who cannot see it, and it prevents Count without enumeration.

Common wrong answer

"Always accept and return IEnumerable<T> — it's the most flexible." It is the most flexible for you and the most dangerous for callers: they cannot tell whether touching the result costs a millisecond or a database round trip, and they will enumerate it twice.

midHow does Dictionary<K,V> work, and when is it the wrong choice?

Answer

It is a hash table with separate chaining implemented over two arrays: a bucket array of indices and an entry array holding hash code, next-index, key and value. Lookup hashes the key, maps it to a bucket, then walks a short chain comparing hash codes first and keys second, so it is O(1) amortised as long as the hash distributes. Growth reallocates both arrays to the next prime and rehashes everything, so pre-sizing with the expected capacity matters on big loads. It is the wrong choice when you need ordering (use a sorted structure or an ordered list), when the collection is tiny — for under about ten items a linear scan over an array is usually faster and allocates nothing — when keys are mutable, or when it is shared across threads, where it will corrupt or spin forever rather than throw.

Example

var d = new Dictionary<string, int>(capacity: 10_000, StringComparer.Ordinal);

// One lookup instead of two (the classic review comment):
if (d.TryGetValue(key, out var v)) Use(v);
// .NET 6+: mutate in place with no second hash
ref var slot = ref CollectionsMarshal.GetValueRefOrAddDefault(d, key, out _);
slot++;

Follow-ups

  • What happens if two threads write concurrently? — Undefined: in the worst case a torn bucket chain makes a reader loop forever at 100% CPU. Use ConcurrentDictionary or a lock.
  • Why pass a comparer explicitly? — StringComparer.Ordinal is faster than the default and, more importantly, states the semantics; the default for string keys is already ordinal but non-obvious.
  • What is FrozenDictionary? — .NET 8: build once, then read-optimised — noticeably faster lookups for tables built at startup and never mutated.
  • Ordering guarantees? — None; enumeration order is an implementation detail that has changed between releases and must never be relied on.

Common wrong answer

"Dictionary lookup is O(1) so it's always the fastest option." For small collections the hashing plus indirection loses to a linear scan over a contiguous array, and for a table read millions of times a FrozenDictionary or a perfect-hash switch is measurably better. The answer interviewers want includes "and I measured it".

midWhat does a LINQ chain cost? When would you rewrite it as a loop?

Answer

Each operator allocates an iterator object and adds one delegate invocation per element, plus a closure allocation if the lambda captures. For a chain of four operators over a million items that is four indirections per element and a handful of allocations — irrelevant in a request handler that runs once, significant in an inner loop that runs a million times a second. .NET has narrowed the gap: LINQ has fast paths that recognise List/array sources, and .NET 9 added SIMD-accelerated implementations for several operators. My rule is to write LINQ by default because it is more readable and reviewable, and to rewrite a chain as a loop only when a profile shows it in the top of the allocation or CPU list — then keep the LINQ version next to it as a comment or a test oracle.

Example

// three iterators + a delegate call per element + a closure over 'threshold'
var top = items.Where(i => i.Score > threshold).OrderByDescending(i => i.Score).Take(10).ToList();

// hot-path rewrite: one pass, no per-element delegate, bounded allocation
var heap = new PriorityQueue<Item, int>();          // .NET 6+
foreach (var i in items)
{
    if (i.Score <= threshold) continue;
    heap.Enqueue(i, i.Score);
    if (heap.Count > 10) heap.Dequeue();
}

Follow-ups

  • Which operators are the expensive ones? — OrderBy (buffers everything and sorts), GroupBy and ToDictionary (build a hash table), and anything after them that re-enumerates.
  • Does Count() enumerate? — Only when the source is not a collection; on ICollection<T> it reads Count directly. On an IQueryable it becomes a SELECT COUNT.
  • What about Any() versus Count() > 0? — Any() stops at the first element; Count() > 0 may enumerate the whole sequence or issue a full count query.

Common wrong answer

"LINQ is slow, we banned it in our codebase." A blanket ban costs readability everywhere to save time in the 1% of code that is hot, and interviewers read it as an inability to measure. The credible version names a specific profiled loop.

midWhat does yield return compile to, and when do you write an iterator?

Answer

The compiler turns the method into a state machine class implementing IEnumerable<T> and IEnumerator<T>, where each yield return becomes a state and MoveNext resumes after it. Nothing in the method body runs until the first MoveNext, which is why argument validation in an iterator method never throws at the call site — the standard fix is a non-iterator wrapper that validates and then calls a private iterator. I write iterators for streaming: reading a large file or a paged API where materialising everything would blow memory, or producing an infinite or expensive sequence the caller may abandon early. I avoid them when the caller will enumerate more than once or needs a count, because each enumeration re-runs the work.

Example

public static IEnumerable<string> ReadLines(string path)
{
    ArgumentException.ThrowIfNullOrEmpty(path);   // throws HERE, at the call
    return Iterate(path);

    static IEnumerable<string> Iterate(string p)
    {
        using var r = new StreamReader(p);        // disposed when enumeration ends OR is abandoned
        while (r.ReadLine() is { } line) yield return line;
    }
}

Follow-ups

  • When does the using inside an iterator dispose? — When the enumerator is disposed: at the end of a foreach, including an early break. If a caller enumerates manually and forgets Dispose, the file handle stays open.
  • Can you yield inside a try/catch? — Not inside a try with a catch; try/finally is allowed.
  • What is the async equivalent? — IAsyncEnumerable<T> with async IAsyncEnumerable<T> plus [EnumeratorCancellation] on the token parameter (C# 8).

Common wrong answer

"yield return is just a shorter way to build a list." That mental model produces methods that validate arguments and then never throw, and callers who enumerate three times and pay for three file reads.

seniorIQueryable versus IEnumerable: what actually differs, and what is client-side evaluation?

Answer

IEnumerable<T> takes delegates and runs them in your process; IQueryable<T> takes expression trees — data structures describing the lambda — which a provider such as EF Core translates into SQL. The practical consequence is that the moment a chain crosses from IQueryable to IEnumerable, everything after that point runs in memory over whatever rows were already fetched. That transition happens silently: calling AsEnumerable(), ToList(), or passing the query to a method typed as IEnumerable. Since EF Core 3.0 the provider throws rather than silently evaluating an untranslatable Where on the client — a deliberate breaking change after too many teams shipped queries that pulled a whole table — so the modern symptom is an exception at development time instead of a slow query in production.

Example

// translated to SQL: WHERE Status = 1 ORDER BY Created DESC LIMIT 10
var a = db.Orders.Where(o => o.Status == Status.Open)
                 .OrderByDescending(o => o.Created).Take(10).ToList();

// pulls the ENTIRE table, then filters in memory
var b = db.Orders.AsEnumerable().Where(o => o.Status == Status.Open).Take(10).ToList();

// untranslatable: EF Core 3.0+ throws instead of silently doing (b)
var c = db.Orders.Where(o => MyBusinessRule(o)).ToList();

Follow-ups

  • How do you make a custom rule translatable? — Express it as an Expression<Func<T,bool>> and compose it into the query, or move it into a computed column or a database function mapping.
  • How do you verify what SQL is produced? — Log with EnableSensitiveDataLogging off in production, or call ToQueryString() on the query in a test.
  • What is the N+1 problem here? — Enumerating a query in a loop and touching a lazy navigation property per row; the fix is Include, a projection, or a single batched query.

Common wrong answer

"They're the same, IQueryable just adds database support." Missing that the lambda becomes an expression tree is what leads to helper methods typed IEnumerable sitting in the middle of a query chain and quietly downloading a table.

seniorWhat is wrong with ConcurrentDictionary.GetOrAdd(key, k => Expensive(k))?

Answer

The value factory is not run under the dictionary's lock, so under concurrency several threads can run it for the same key; only one result is stored, the others are discarded. If the factory is expensive that is wasted work; if it creates something that must be disposed or registered — an HttpClient, a connection, a file handle — you leak the losers; and if it has side effects, they happen more than once. The fixes are: make the factory cheap and idempotent, store a Lazy<T> (or AsyncLazy-style Task<T>) so only the winner's factory is ever executed, or take an explicit lock per key. The same class of surprise applies to AddOrUpdate, whose update delegate can run several times when it loses a race.

Example

// factory may run N times, N-1 results thrown away (and never disposed)
var conn = _map.GetOrAdd(key, k => new Connection(k));

// only one factory ever executes; the losers get the same Lazy instance
var lazy = _map.GetOrAdd(key, k => new Lazy<Connection>(
    () => new Connection(k), LazyThreadSafetyMode.ExecutionAndPublication));
var conn2 = lazy.Value;

Follow-ups

  • Is Count on a ConcurrentDictionary cheap? — No: it takes all internal locks and is a snapshot; avoid it in hot paths and never use it for control flow.
  • Is enumeration safe? — Yes, it yields a moment-in-time snapshot without locking, which also means it can include items added during enumeration.
  • Async factory? — Store Task<T>, not T; and be prepared to remove the entry if the task faults, or you cache a failure forever.

Common wrong answer

"ConcurrentDictionary is thread-safe, so GetOrAdd is atomic." The dictionary operation is atomic; the factory is not, and that distinction is exactly what the question is testing. The visible symptom in production is duplicate expensive objects and leaked handles.

seniorWhen do you use IAsyncEnumerable<T>, and what is the cancellation gotcha?

Answer

Use it when items arrive over time and you want to process them without buffering everything: streaming rows from a database, paging through an API, consuming a channel or an event stream. It gives you back-pressure for free — the producer only advances when the consumer asks for the next item — and it lets an ASP.NET Core endpoint stream a JSON array to the client instead of building it in memory. The cancellation gotcha is that a token passed to the method is captured when the enumerator is created, so a token passed later by the consumer needs [EnumeratorCancellation] on the parameter plus WithCancellation(ct) at the call site; without the attribute the consumer's token is silently ignored. The other trap is doing per-item work with a network round trip each — streaming is not automatically efficient, it just changes where the memory goes.

Example

public async IAsyncEnumerable<Row> StreamAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await using var reader = await _cmd.ExecuteReaderAsync(ct);
    while (await reader.ReadAsync(ct))
        yield return Map(reader);
}

await foreach (var row in StreamAsync().WithCancellation(ct).ConfigureAwait(false))
    Process(row);

Follow-ups

  • Can you use LINQ on it? — With the System.Linq.Async package, or by writing your own await foreach; the BCL does not ship the full operator set.
  • How does ASP.NET Core handle it? — Returning IAsyncEnumerable<T> from a controller or minimal API streams the JSON array without buffering.
  • What about EF Core? — AsAsyncEnumerable() streams rows, but the connection is held for the whole enumeration, so do not interleave slow per-row work with it.

Common wrong answer

"It's the async version of IEnumerable, so I'd use it everywhere I return a collection." For a finished, already-loaded result it adds ceremony and per-item await overhead for nothing; return Task<IReadOnlyList<T>> instead. Streaming is a decision about memory and latency, not a default.

principalA lookup table is read a million times a second and rebuilt hourly. How do you hold it?

Answer

Immutably, and swapped by reference. I build the new table off to the side, then publish it with a single volatile reference assignment (or Interlocked.Exchange) so readers never lock and never see a half-built table; readers just capture the current reference at the start of their work. For the table itself, FrozenDictionary/FrozenSet (.NET 8) is the right shape: construction is deliberately expensive and lookups are optimised, which is precisely the read-heavy, build-once profile. If the keys are small and the set is tiny, an ordered array with a binary search or even a linear scan beats hashing on cache behaviour. What I would not do is lock around a shared mutable dictionary, or use ConcurrentDictionary for what is really a snapshot replacement problem — its per-bucket locking buys write concurrency I do not need and costs read throughput I do.

Example

private volatile FrozenDictionary<string, Rate> _rates = FrozenDictionary<string, Rate>.Empty;

public Rate? Get(string code) => _rates.TryGetValue(code, out var r) ? r : null;   // lock-free

private void Reload(IEnumerable<KeyValuePair<string, Rate>> rows)
    => _rates = rows.ToFrozenDictionary(StringComparer.Ordinal);   // atomic publish

// Reading a hot set of characters/bytes: SearchValues<T> (.NET 8, expanded in 9)
private static readonly SearchValues<char> Delims = SearchValues.Create(",;|");

Follow-ups

  • Why volatile? — It guarantees readers see a fully constructed object and the newest reference; without it a reader could observe a stale reference indefinitely on a weak memory model such as arm64.
  • What about memory during the swap? — Both tables exist briefly; for a large table that doubles the footprint for the duration of the rebuild, which must be budgeted.
  • How would you prove the choice? — BenchmarkDotNet over the real key distribution, comparing Dictionary, FrozenDictionary and a sorted array, plus an allocation check; the ranking depends on size and key type.
  • If readers must see a consistent pair of tables? — Publish one immutable object containing both, so a single reference swap keeps them consistent.

Common wrong answer

"Use ConcurrentDictionary and update the entries in place." It gives a correct-looking answer with two hidden problems: readers observe a partially updated table (old and new values mixed), and the read path is measurably slower than a frozen or plain dictionary because of the concurrency machinery you are not using.

04Memory, garbage collection and Span

Interviewers use this sub-area to separate people who have run a .NET service in production from people who have only written one. Screener depth is "what are generations"; mid depth is the dispose pattern and where leaks come from in a garbage-collected runtime; senior depth is GC mode selection, Span<T> and pooling; and lead depth is the diagnostic story — a symptom, the tool you reach for, and the fix you shipped. Have one real memory incident ready to tell, with numbers.

screenerHow does the .NET garbage collector work?

Answer

It is a generational, mark-and-sweep, compacting collector built on the observation that most objects die young. New objects go into generation 0; anything that survives a collection is promoted to gen 1, then gen 2. Gen 0 collections are frequent and cheap because the collector only walks a small region; gen 2 collections are rare and expensive because they walk everything, which is why the goal of tuning is to avoid promoting garbage. A collection starts from roots — statics, locals on thread stacks, GC handles — marks everything reachable, sweeps the rest, and compacts to remove fragmentation (except for the large object heap, which is not compacted by default). Allocation itself is just a pointer bump, so allocating is fast and collecting is what costs; that is the sentence that reframes most performance discussions.

Example

gen0   small, collected often, cost proportional to SURVIVORS not to garbage
gen1   a buffer between 0 and 2
gen2   long-lived; a full collection is the expensive one
LOH    objects >= 85,000 bytes, collected with gen2, not compacted by default
POH    pinned object heap (.NET 5+), keeps pinned buffers out of the normal heaps

dotnet-counters monitor System.Runtime
  gen-0/1/2-gc-count · gc-heap-size · time-in-gc · alloc-rate

Follow-ups

  • Why is a gen-0 collection cheap even with millions of dead objects? — Dead objects cost nothing; the collector copies survivors and resets the allocation pointer.
  • What is a card table? — The write-barrier bookkeeping that tracks old-to-young references, so a gen-0 collection does not have to scan gen 2.
  • Should you call GC.Collect()? — Essentially never in a service; legitimate uses are benchmarks and a deliberate trim after a known one-off spike, and even then with GCCollectionMode.Aggressive considered carefully.

Common wrong answer

"The GC frees objects when they go out of scope / when the reference count hits zero." .NET has no reference counting; scope is irrelevant, reachability from a root is what matters. That misunderstanding is the root of "why is my object still alive" questions later in the interview.

midWhat is the large object heap and why should you care?

Answer

Allocations of 85,000 bytes or more go on the large object heap, which is collected only with gen 2 and — by default — is not compacted. So a service that repeatedly allocates big arrays or big strings gets two problems: it triggers expensive full collections, and the LOH fragments, so eventually a large allocation fails or the process footprint grows while "free" memory exists. The practical thresholds people forget: a byte[] of 85,000 elements crosses it, but so does an array of about 10,600 longs or 21,250 objects references. The fixes are to stop allocating large arrays per operation — ArrayPool<T>.Shared, chunked processing, streaming instead of buffering whole payloads — and only as a last resort to set GCSettings.LargeObjectHeapCompactionMode for a one-off compaction.

Example

// LOH allocation per request - a classic cause of gen2 pressure
var buffer = new byte[100_000];

// pooled instead
var rented = ArrayPool<byte>.Shared.Rent(100_000);
try { Use(rented.AsSpan(0, 100_000)); }
finally { ArrayPool<byte>.Shared.Return(rented); }   // clearArray: true if it held secrets

Follow-ups

  • How do you see LOH pressure? — gen-2-gc-count climbing with a large gc-heap-size, or a dump showing the LOH dominated by same-sized arrays.
  • Can you change the threshold? — Yes, GCLOHThreshold in runtimeconfig, but raising it moves the problem into gen 2 rather than solving it.
  • Does string hit the LOH? — Yes: about 42,500 characters, which real-world JSON payloads and CSV lines exceed regularly.

Common wrong answer

"The LOH is for big objects and the GC handles it." Missing that it is collected only with gen 2 and never compacted by default is why teams keep buffering whole files into a byte[] and then wonder why the pod restarts on memory limits every few hours.

midExplain IDisposable, using, and when you need a finalizer.

Answer

IDisposable exists because the GC manages memory, not other resources: file handles, sockets, database connections, OS mutexes, unmanaged buffers. using compiles to try/finally, so Dispose runs even on an exception, and C# 8's using var disposes at the end of scope. You need a finalizer only if your type directly owns an unmanaged resource — a raw handle from P/Invoke — and even then the modern answer is to wrap it in a SafeHandle, which already has the finalizer and the critical-execution guarantees. Finalizers are expensive: they put the object on the finalization queue, which promotes it at least one generation and delays its memory by a full extra collection cycle, and they run on a single finalizer thread, so a slow one blocks all of them. For async cleanup, implement IAsyncDisposable and use await using.

Example

public sealed class Reader : IAsyncDisposable
{
    private readonly SafeFileHandle _handle;      // no finalizer needed: SafeHandle has one
    private readonly Stream _stream;

    public async ValueTask DisposeAsync()
    {
        await _stream.DisposeAsync();
        _handle.Dispose();
    }
}

await using var r = new Reader(path);   // disposed asynchronously at end of scope

Follow-ups

  • What is GC.SuppressFinalize for? — In the classic dispose pattern it removes the object from the finalization queue once it has been disposed deterministically; unnecessary if there is no finalizer, and CA1816 will tell you.
  • Who disposes an injected dependency? — The container: with DI you dispose what you created, not what was injected — disposing an injected singleton HttpClient is a classic outage.
  • What if Dispose throws? — It should not; a throwing Dispose in a finally can mask the original exception. Make it idempotent and non-throwing.

Common wrong answer

"I add a finalizer to every disposable class just in case." It roughly doubles the lifetime of every instance, adds finalizer-thread load, and can resurrect objects; the modern guidance is a sealed class, no finalizer, and SafeHandle for anything unmanaged.

midHow do you leak memory in a garbage-collected runtime?

Answer

By keeping things reachable. The recurring five in real codebases are: event handlers, where a long-lived publisher holds a reference to a short-lived subscriber that is never unsubscribed; static collections and caches with no eviction policy; captured closures, where a lambda captures this and is stored somewhere long-lived; timers and background tasks holding a reference to a disposed object; and DI misconfiguration, where something scoped is captured by a singleton and therefore never released. The second family is unmanaged: a missing Dispose means the memory profiler shows a modest heap while the process RSS grows, because the leak is in handles or native allocations. My diagnostic order is: confirm growth with dotnet-counters, take two heap snapshots minutes apart, diff them, and look at the retention path of the biggest growing type — the path names the bug.

Example

// leak: the singleton cache keeps every subscriber alive forever
_bus.MessageReceived += OnMessage;              // never unsubscribed

// fix 1: unsubscribe in Dispose
public void Dispose() => _bus.MessageReceived -= OnMessage;
// fix 2: bounded cache with eviction instead of a static Dictionary
private static readonly MemoryCache _cache = new(new MemoryCacheOptions { SizeLimit = 10_000 });

Follow-ups

  • How do you find the retaining reference? — dotnet-gcdump or a dump in Visual Studio / dotMemory, then "path to root" on the growing type.
  • Do weak references solve event leaks? — They can (weak event pattern), but the simpler answer is deterministic unsubscription tied to the subscriber's lifetime.
  • What does a leak look like in metrics? — Heap size rising monotonically across gen-2 collections, or RSS rising while the managed heap is flat (that one is unmanaged or fragmentation).

Common wrong answer

"You can't leak memory in .NET, the GC handles it." It is the answer that ends the interview early. The GC removes unreachable objects; every leak in .NET is a reachability bug, and naming the five common sources is what the question is for.

seniorServer GC or Workstation GC? What about DATAS?

Answer

Workstation GC uses one collection thread and favours short pauses and low footprint; Server GC allocates a heap and a dedicated GC thread per core, which raises throughput substantially for a multi-core server at the cost of more memory and larger pauses. ASP.NET Core turns Server GC on by default; a console app or a small sidecar defaults to Workstation. The complication in containers is that Server GC sizes itself from the visible core count, so an aggressively over-provisioned heap in a 512 MB pod causes OOM kills — which is exactly the problem DATAS (Dynamic Adaptation To Application Sizes) addresses by adjusting heap count and size to the live workload. DATAS shipped in .NET 7, became available in .NET 8 and is enabled by default with Server GC from .NET 9 onward; the practical guidance is to leave it on, set memory limits so the runtime can see them, and only override ServerGarbageCollection after measuring both settings under a realistic load.

Example

<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
</PropertyGroup>
<!-- runtimeconfig: "System.GC.DynamicAdaptationMode": 1 (default with Server GC since .NET 9)
     Container: set memory limits; the runtime reads cgroup limits for heap sizing. -->

Follow-ups

  • Symptom that says "wrong GC mode"? — High time-in-gc with low allocation rate (too many heaps for the work), or OOM kills in a small container running Server GC without limits configured.
  • What is background GC? — Gen-2 collection running concurrently with the application to shorten pauses; on by default and rarely worth disabling.
  • How do you choose in practice? — Load test both, compare p99 latency and RSS, and record the decision in the repo — this is not a setting to change by intuition during an incident.

Common wrong answer

"Server GC is always better for servers." In a memory-capped container with two cores it can be strictly worse, and this is a live topic because the defaults changed: DATAS is on by default with Server GC from .NET 9, so a team upgrading and seeing different memory behaviour needs to know why.

seniorWhat are Span<T> and Memory<T>, and what are the rules?

Answer

Span<T> is a ref struct holding a reference and a length: a type-safe window over a slice of an array, a stack buffer, a string, or unmanaged memory, with no copying and no allocation. That is what lets you parse and slice without producing intermediate strings or arrays. Because it is a ref struct it is stack-only: it cannot be boxed, stored in a field of a class, used in an async method across an await, or captured in a lambda — the compiler enforces all of that. Memory<T> is the heap-friendly counterpart you can hold in a field and pass through async code; you call .Span to get a span for the synchronous part of the work. C# 14 added first-class span support with new implicit conversions between arrays, Span<T> and ReadOnlySpan<T>, which removed a lot of overload friction.

Example

// parse "key=value" with zero allocations
static (ReadOnlySpan<char> k, ReadOnlySpan<char> v) Split(ReadOnlySpan<char> s)
{
    var i = s.IndexOf('=');
    return (s[..i], s[(i + 1)..]);
}

// async: hold Memory, take the Span only in synchronous stretches
async Task CopyAsync(Memory<byte> buffer, Stream to, CancellationToken ct)
{
    Transform(buffer.Span);                 // ok: no await while the span is alive
    await to.WriteAsync(buffer, ct);
}

Follow-ups

  • Why can't a Span cross an await? — The state machine would have to store it on the heap, and a stack pointer may not outlive its frame; that is the whole safety argument.
  • What does stackalloc give you? — A stack buffer usable as a span, safe since C# 7.2 without unsafe; keep it small (a kilobyte or so) and never in a loop, or you overflow the stack.
  • Can a span point at a string? — Yes, ReadOnlySpan<char> over a string is free and is how modern parsing avoids Substring.
  • What changed in C# 13/14? — C# 13 allows ref structs in more places (including as generic type arguments with allows ref struct); C# 14 added implicit span conversions.

Common wrong answer

"Span is a faster array, I'd use it everywhere." It is a view, not a container: it does not own memory, cannot be stored on the heap, and using it as a general-purpose parameter type in async or interface-heavy code simply will not compile — the candidate who says this has read about it rather than used it.

seniorWhen is object pooling justified, and what goes wrong with it?

Answer

Pooling is justified when an object is expensive to create or large enough to hit the LOH, and it is created and discarded at a high rate: byte buffers for I/O, StringBuilders in a serializer, per-request state objects in a high-throughput pipeline. ArrayPool<T>.Shared and ObjectPool<T> from Microsoft.Extensions.ObjectPool are the standard tools. What goes wrong is predictable: forgetting to return (a leak that also disables the benefit), returning twice (two callers now share a buffer, which is a data-corruption or data-disclosure bug), using a rented array after returning it, and forgetting that Rent can return a larger array than asked for, so you must track the length yourself. For anything holding sensitive data, return with clearing enabled. My rule is to pool only after a profile shows allocation as the bottleneck, and always with the rent/return pair in a try/finally in the same method.

Example

var pool = ArrayPool<byte>.Shared;
var buf = pool.Rent(4096);          // may return 8192 - length is NOT 4096
try
{
    var read = await stream.ReadAsync(buf.AsMemory(0, 4096), ct);
    Process(buf.AsSpan(0, read));
}
finally { pool.Return(buf, clearArray: true); }   // clear: it held user data

Follow-ups

  • Why is double-return so dangerous? — Two consumers rent the same array and overwrite each other; in a web server this shows up as one user seeing another user's bytes.
  • Is RecyclableMemoryStream worth it? — Yes for large or frequent streams; it is the standard answer to MemoryStream churn on the LOH.
  • When is pooling actively harmful? — For cheap, small objects: you replace a pointer-bump allocation and a cheap gen-0 death with synchronisation and lifetime bugs.

Common wrong answer

"Pooling avoids GC so it's always faster." Gen-0 allocation is a pointer bump and gen-0 collection cost is proportional to survivors, so pooling small short-lived objects usually makes things slower and introduces the worst bug class in the list above.

seniorWhat does unsafe buy you in C#, and what is changing about it?

Answer

unsafe enables pointers, fixed pinning, pointer arithmetic and function pointers — used for interop, for zero-copy parsing of native structures, and occasionally for a measured hot loop. In modern C# most of what people used to reach for it is available safely: Span<T>, stackalloc without unsafe, MemoryMarshal, Unsafe.As, and ref locals. The forward-looking part — worth knowing because it shows you are current — is that C# 15 begins a multi-release redefinition of memory safety: the unsafe context is being tied to the operations that actually access unmanaged memory rather than to the mere existence of pointer types. In the first step (preview language version, .NET 11) declaring a pointer, taking an address with &, using fixed, and sizeof no longer require an unsafe context, while dereferencing still does; there is also a new unsafe(expr) expression for places a block cannot go, such as a field initializer.

Example

// C# 15 preview: pointer declaration and 'fixed' outside an unsafe context
int number = 42;
int* pointer = &number;              // allowed
int[] numbers = [10, 20, 30];
fixed (int* first = numbers)
{
    // dereferencing (*first) still requires an unsafe context
}

// modern safe equivalents you should reach for first
Span<byte> scratch = stackalloc byte[256];
ref var head = ref MemoryMarshal.GetReference(scratch);

Follow-ups

  • What does pinning cost? — A pinned object cannot be moved, so it fragments the heap; keep pinning short-lived, or allocate on the pinned object heap (.NET 5+).
  • Are function pointers better than delegates? — delegate* (C# 9) avoids the delegate allocation and an indirection for interop callbacks; it is unsafe and rarely worth it outside interop.
  • Does unsafe work under Native AOT? — Yes; what does not work is dynamic code generation and most reflection-emit.

Common wrong answer

"unsafe makes code faster." It removes bounds checks you often did not need to remove — the JIT already elides many of them — and the measured wins today usually come from Span and SIMD instead. Reaching for pointers first signals a candidate who has not benchmarked the safe version.

principalA service's memory grows from 400 MB to 3 GB over 48 hours and then the pod is killed. Walk me through it.

Answer

First I separate the three possible shapes, because they have different fixes: a managed leak (heap grows across gen-2 collections), unmanaged growth (RSS climbs while the managed heap is flat — handles, native libraries, or missing Dispose), and fragmentation or simply a heap that has been allowed to grow because the limit was never communicated to the runtime. dotnet-counters tells me which within minutes. If it is managed, I take two dotnet-gcdump snapshots several hours apart in the same pod, diff them, and look at the top growing type's path to root — that path is almost always the bug: an event subscription, an unbounded static cache, or a scoped object captured by a singleton. Then I fix the retention and add a guard so it cannot recur silently: a bounded cache with an eviction policy and a size metric, or an assertion in DI validation. Finally I make the failure visible before it kills the pod — an alert on heap growth rate and on gen-2 frequency, not just on the container OOM.

Example

1  dotnet-counters monitor -p PID System.Runtime
     gc-heap-size rising, gen-2 count rising ......... managed leak
     gc-heap-size flat, RSS rising ................... unmanaged/handles
     both flat but pod OOM ........................... limits not seen by the runtime
2  dotnet-gcdump collect -p PID   (x2, hours apart) -> diff in Visual Studio / PerfView
3  top growing type -> "path to root" -> the retaining field IS the bug
4  fix + guard: bounded cache, unsubscribe on dispose, DI scope validation on startup
5  alert on d(heap)/dt and gen2/min, so the next one pages before the OOM kill

Follow-ups

  • How do you capture a dump in Kubernetes without a debugger? — dotnet-dump/dotnet-gcdump in the image or an ephemeral debug container sharing the process namespace; and configure DOTNET_DbgEnableMiniDump so a crash leaves evidence.
  • What if the growth is legitimate caching? — Then the bug is the missing limit: caches need a size or entry bound and an eviction metric, or they are leaks with good intentions.
  • How do you stop this class of bug in the team? — Bounded-by-default cache helpers, an analyser for static mutable collections, DI lifetime validation in CI, and a memory soak test in the nightly pipeline.

Common wrong answer

"I'd increase the memory limit and add a scheduled restart." It is sometimes the right mitigation for tonight, but offering it as the answer signals someone who does not know how to read a heap; interviewers are listening for counters, a snapshot diff and a retention path.

05OOP, generics and API design

Every loop has an object-modelling segment, and at lead level it is the one that reveals taste. Screener questions ("abstract class or interface?") are warm-ups; the real signal comes from how you justify a boundary, what you make virtual, and what you refuse to expose. Generics questions go from "what is a constraint" at mid level to variance and static abstract members at senior level. Expect at least one "here is a class, how would you change it" and treat it as a design conversation, not a checklist recital.

screenerAbstract class or interface — how do you choose in 2026?

Answer

An interface is a contract: it says what a type can do, allows a type to satisfy many of them, and is the right shape for a capability, a port in a hexagonal architecture, or anything you will mock. An abstract class is a partially built implementation: it carries state, constructors and shared behaviour, and it costs the single inheritance slot. Since C# 8, interfaces can have default implementations, which blurs the line — but their purpose is API evolution (adding a member without breaking implementers), not shared state, because interfaces still cannot hold instance fields. My default is: interface for the boundary, and if several implementations share code, a sealed helper or a base class behind that interface, never a base class as the public contract.

Example

public interface IPaymentGateway
{
    Task<Receipt> ChargeAsync(Money amount, CancellationToken ct);

    // C# 8 default member: added later without breaking existing implementers
    Task<Receipt> ChargeAsync(Money amount) => ChargeAsync(amount, CancellationToken.None);
}

internal abstract class HttpGatewayBase : IPaymentGateway   // shared plumbing, not the contract
{
    protected abstract Uri Endpoint { get; }
    public abstract Task<Receipt> ChargeAsync(Money amount, CancellationToken ct);
}

Follow-ups

  • Do default interface methods replace abstract classes? — No: no instance state, no constructor, and resolution is by static type, so a class re-declaring the member wins. They are a versioning tool.
  • When is an interface with one implementation still worth it? — When it is a genuine seam (external dependency, testing boundary); an interface extracted only because "everything needs an interface" is noise.
  • Explicit interface implementation — why? — To keep a member off the public surface of the class, or to implement two interfaces with clashing signatures.

Common wrong answer

"Interface for behaviour, abstract class for 'is-a'." It sounds right and decides nothing. Interviewers want the operational reasons: single inheritance, shared state, mockability, and whether you can add a member later without breaking every implementer.

midExplain generic constraints, and what generics cost at runtime.

Answer

Constraints tell the compiler what a type parameter can do — where T : class, struct, notnull, new(), a base type, an interface, or since C# 11 static abstract members — and they are what lets you call methods on T without boxing or reflection. The runtime cost is the interesting half: .NET generics are reified, not erased like Java's. The JIT shares one native code body across all reference-type arguments (they are all pointer-sized) but produces a specialised body for each value type argument, so List<int> and List<double> get their own code with no boxing and full inlining. That is why a generic method with an IComparable<T> constraint beats a non-generic one taking IComparable: the constrained call on a struct is a direct call, not an interface dispatch through a box.

Example

public static T Max<T>(T a, T b) where T : IComparable<T>
    => a.CompareTo(b) >= 0 ? a : b;             // no boxing for int, decimal, DateTime...

// C# 11 static abstract members: real generic math
public static T Sum<T>(ReadOnlySpan<T> xs) where T : INumber<T>
{
    T total = T.Zero;
    foreach (var x in xs) total += x;
    return total;
}

Follow-ups

  • Why is code sharing for reference types not a problem? — All references are the same size and layout, so one body suffices; type identity is carried in a hidden generic dictionary.
  • Does generic instantiation cost startup time? — Each value-type instantiation is JIT-compiled separately, so very generic-heavy code can raise startup cost; Native AOT must pre-generate them, which is why unbounded generic recursion fails to compile there.
  • What does where T : notnull do? — Nullable-reference-type analysis only; no runtime effect.

Common wrong answer

"Generics are compile-time only, they're erased like in Java." .NET keeps full type information at runtime — typeof(List<int>) is a distinct type, reflection sees the arguments, and value types are specialised. Saying otherwise undermines every performance claim that follows.

midCovariance and contravariance — explain with a case where it bites.

Answer

out T makes an interface covariant: IEnumerable<Derived> is usable as IEnumerable<Base>, safe because T only comes out. in T makes it contravariant: IComparer<Base> is usable as IComparer<Derived>, safe because T only goes in. List<T> is invariant because it does both — allowing List<Derived> as List<Base> would let you insert the wrong type. The place it actually bites is arrays: array covariance predates generics and is unsafe, so object[] a = new string[1]; a[0] = 42; compiles and throws ArrayTypeMismatchException at runtime — and to make that check possible, every store into a reference-typed array pays a covariance check, which is a measurable cost in tight loops.

Example

IEnumerable<string> strings = new List<string>();
IEnumerable<object> objects = strings;            // ok: covariant (out T)

IComparer<object> byHash = Comparer<object>.Default;
IComparer<string> forStrings = byHash;            // ok: contravariant (in T)

object[] arr = new string[1];
arr[0] = 42;                                      // compiles; throws at runtime

Follow-ups

  • Why can't value types participate? — Variance requires reference conversions; IEnumerable<int> is not an IEnumerable<object> because that would require boxing.
  • Where does it show up in the BCL? — IEnumerable<out T>, IReadOnlyList<out T>, Func<in T, out TResult>, Action<in T>, IComparer<in T>.
  • Does variance apply to classes? — No, only to interfaces and delegates.

Common wrong answer

"Covariance means you can use a derived type wherever a base is expected — like arrays." Naming arrays as the model gets it backwards: array covariance is the historical mistake the generic rules were designed to avoid, and knowing that distinction is what the question is checking.

midOverriding versus hiding (virtual/override versus new) — what actually happens?

Answer

override replaces the entry in the virtual method table, so the derived implementation runs no matter which static type the caller holds — that is polymorphism. new declares an unrelated method that merely hides the base name: which one runs depends on the compile-time type of the reference, so the same object behaves differently through a base-typed variable. Hiding is almost always accidental and the compiler warns about it; the legitimate use is versioning, when a base class you do not own adds a member whose name collides with yours. The related rule that matters in review is that C# is non-virtual by default — unlike Java — so a method is only overridable if someone deliberately made it virtual, and that decision is a permanent part of your API contract.

Example

class A { public virtual string V() => "A.V"; public string H() => "A.H"; }
class B : A { public override string V() => "B.V"; public new string H() => "B.H"; }

A x = new B();
x.V();   // "B.V"  - virtual dispatch
x.H();   // "A.H"  - resolved on the STATIC type A

Follow-ups

  • Why is C# non-virtual by default? — Every virtual member is a promise you must keep forever; the default forces the decision to be explicit and helps the JIT devirtualise.
  • What does sealed override mean? — Overrides and then stops further overriding; it also gives the JIT a devirtualisation opportunity.
  • Do interface implementations dispatch differently? — Yes, through an interface dispatch stub, which is slightly more expensive than a vtable call and harder to devirtualise.

Common wrong answer

"new and override do the same thing, new just silences the warning." That is literally how the bug gets introduced: someone adds new to make a warning go away, and the base-typed call path silently keeps the old behaviour — a defect that unit tests using the derived type will never catch.

midWhat are extension methods good for, and what changed in C# 14?

Answer

Extension methods let you add methods to a type you do not own — the mechanism behind all of LINQ — resolved statically at compile time from the using directives in scope. They are right for adding convenience over an interface, for adapting third-party types, and for keeping domain-specific helpers out of a shared class. They are wrong when the behaviour belongs on the type, when they mutate the receiver in surprising ways, or when they extend object and pollute IntelliSense everywhere. C# 14 (November 2025) generalised this into extension members: an extension(Receiver) block can declare extension properties, static members and user-defined operators, not just methods — and C# 15 adds extension indexers. This is worth knowing because it is the most visible C# 14 language change and interviewers who follow the language will ask about it.

Example

// C# 14 extension block: property + static member + operator
public static class SeqExtensions
{
    extension<T>(IEnumerable<T> source)
    {
        public bool IsEmpty => !source.Any();                    // extension PROPERTY
        public IEnumerable<T> TakeLastOrAll(int n) => source.TakeLast(n);
    }

    extension<T>(IEnumerable<T>)
    {
        public static IEnumerable<T> Empty => [];                // static extension property
    }
}

// classic form still works and is still what most codebases contain
public static class Old { public static bool IsEmpty2<T>(this IEnumerable<T> s) => !s.Any(); }

Follow-ups

  • Can an extension method be called on null? — Yes: there is no virtual dispatch, so ((string)null).IsNullOrEmpty()-style extensions work by design.
  • What wins, an instance method or an extension? — The instance method always wins, which is how adding a real member later can silently change behaviour.
  • Are extension members a breaking change? — The new syntax is additive; existing this-parameter extension methods keep working and interoperate with the new blocks.

Common wrong answer

"Extension methods are just syntactic sugar for static helpers, nothing new since C# 3." Since November 2025 that is out of date: extension properties, static extension members and extension operators are the headline C# 14 feature, and not knowing it is the fastest way to look like you stopped reading release notes in 2022.

seniorComposition over inheritance — how do you actually make that call?

Answer

I ask what varies and how many axes it varies on. Inheritance is a good fit when there is exactly one axis of variation, the base genuinely defines the whole lifecycle, and derived types will never need to combine behaviours; the moment you want "retrying and caching and logging" you are in combinatorial explosion territory and composition — decorators, delegates, injected strategies — is the only shape that scales. The second test is the fragile base class problem: with inheritance, every protected member is public API to your subclasses and you can break them by changing your own internals; with composition the surface is the interface you chose. In practice my default is sealed classes and composition, with inheritance reserved for framework extension points that already exist (a base controller, a base BackgroundService) — and I treat "I made it virtual so it could be tested" as a signal that the seam belongs in an interface instead.

Example

// composition: any combination, no new type per pairing
public sealed class RetryingGateway(IPaymentGateway inner, ResiliencePipeline pipeline)
    : IPaymentGateway
{
    public Task<Receipt> ChargeAsync(Money m, CancellationToken ct)
        => pipeline.ExecuteAsync(t => inner.ChargeAsync(m, t), ct).AsTask();
}
// registration: services.AddSingleton<IPaymentGateway>(sp =>
//     new RetryingGateway(new LoggingGateway(new HttpGateway(...)), pipeline));

Follow-ups

  • Isn't a decorator chain harder to read? — Yes, that is its cost; keep the composition in one registration site so the order is visible in a single place.
  • When is inheritance clearly right? — Framework-mandated extension points, and closed hierarchies modelling a fixed set of cases (which C# 15's closed modifier now makes exhaustively checkable).
  • What about default interface methods as mixins? — Workable but easy to abuse; no state, and resolution surprises make them a poor substitute for composition.

Common wrong answer

"Composition over inheritance is a principle, so I never use inheritance." A slogan, not judgment. Interviewers want the discriminating criterion — number of variation axes, and whether the base owns the lifecycle — plus an example where you chose inheritance on purpose.

seniorWhich SOLID principle do you actually enforce in code review, and why that one?

Answer

Dependency inversion and interface segregation, because they are the two whose violation is cheap to spot and expensive to live with. Dependency inversion in practice means a class states its needs as constructor parameters rather than reaching for a static, a new, or a service locator — which is what makes it testable without a container and what stops a domain type from depending on HttpClient. Interface segregation means an interface should be sized to a caller's need, not to an implementation's surface: a 20-member IRepository forces every test double to implement 20 members and makes every consumer look coupled to everything. I am far less dogmatic about the single responsibility principle, because "one reason to change" is unfalsifiable in review and turns into an argument about taste; I use cohesion and the actual change history of the file instead.

Example

// violates DIP and ISP: constructs its dependency, depends on 20 members it does not use
public sealed class OrderService
{
    private readonly SqlRepository _repo = new(Config.ConnectionString);
    private readonly HttpClient _http = new();
}

// inverted and segregated: dependencies stated, interfaces sized to the need
public sealed class OrderService(IOrderStore store, IPaymentGateway payments, TimeProvider clock);
public interface IOrderStore { Task<Order?> FindAsync(OrderId id, CancellationToken ct); }

Follow-ups

  • What about the Liskov substitution principle? — It matters most as a warning against inheritance that strengthens preconditions; in practice it shows up as an override that throws NotSupportedException.
  • Open/closed in modern C#? — Usually achieved by composition and DI registration rather than by inheritance hierarchies; a switch expression over a closed hierarchy is often the honest, readable choice.
  • How do you enforce it without dogma? — Architecture tests (NetArchTest or similar) for dependency direction, and a constructor-parameter count guideline as a smell detector rather than a rule.

Common wrong answer

Reciting all five principles with textbook definitions. The question asks which one you enforce; a recital signals the candidate has never had to arbitrate a real design argument. Pick two, justify them operationally, and say which one you deliberately do not police.

seniorWhat are static abstract interface members for? Show generic math.

Answer

Before C# 11 you could not express "this type has a static Parse" or "this type supports +" in a constraint, so numeric code was written once per type or went through slow, boxing dynamic/reflection paths. Static abstract (and static virtual) interface members let an interface declare static members that implementing types provide, which is what makes INumber<T>, IParsable<T> and ISpanFormattable work — one generic algorithm, JIT-specialised per value type, with no boxing. The practical uses beyond math are factory patterns (T.Create(...) in a generic method), parsing abstractions in minimal APIs, and strongly-typed ids that implement IParsable<T> so routing and configuration bind them automatically.

Example

public static T Mean<T>(ReadOnlySpan<T> xs) where T : INumber<T>
{
    T sum = T.Zero;
    foreach (var x in xs) sum += x;
    return sum / T.CreateChecked(xs.Length);
}
// works for int, double, decimal, Half, Int128 - one implementation, no boxing

public interface IFactory<TSelf> where TSelf : IFactory<TSelf>
{
    static abstract TSelf Create(string raw);
}

Follow-ups

  • What is the curiously recurring pattern here? — where TSelf : IFactory<TSelf> lets the interface refer to the implementing type; it is how INumber<TSelf> is declared.
  • Any runtime cost? — Constrained calls on value types are direct and inlinable; the cost is more JIT instantiations, which matters for startup and AOT size.
  • Does it work with Native AOT? — Yes, as long as the instantiations are statically discoverable, which they are for concrete call sites.

Common wrong answer

"You can already do that with an interface and instance methods." Not for operators, parsing or construction — those are static by nature, and the pre-C#-11 workarounds (a passed-in INumericOperations<T> helper, or dynamic) are exactly the boxing-and-indirection cost the feature removes.

principalYou are designing a NuGet package used by 40 internal teams. What do you decide on day one?

Answer

The decisions that are irreversible: what is public, what is virtual, and what shape the extension points take. My defaults are sealed classes and internal implementations, the smallest possible public surface, no public fields, no public mutable statics, interfaces only where consumers genuinely need a seam, and options supplied through an Options class rather than a constructor overload set that I can never grow. 06Null, exceptions and defensive code

This sub-area is asked constantly because it is where correctness and operability meet: the interviewer can hand you six lines of error handling and learn how you think about failure, logging, retries and blast radius. Mid level is the mechanics — throw versus throw ex, what finally guarantees. Senior and lead level is policy: which layer handles what, what the caller sees, and how you stop a team from writing catch (Exception) { } forever.

screenerHow do you prevent NullReferenceException structurally, not by adding checks?

Answer

By making null unrepresentable where it should not exist and by validating exactly once, at the boundary. Concretely: nullable reference types enabled and warnings as errors, so the compiler tracks intent; constructors that require what the object needs (primary constructors or required members, C# 11) so a half-built object cannot exist; collections returned empty rather than null; and ArgumentNullException.ThrowIfNull at public entry points and after deserialization, where the annotations do not reach. For optional values I prefer an explicit shape — a nullable with pattern matching, or a small option/result type where the absence is a business case rather than a bug. The point is that scattering null checks through the call stack treats the symptom; the fix is that only one layer is allowed to produce a null.

Example

public sealed class Order
{
    public required OrderId Id { get; init; }              // C# 11: cannot forget it
    public IReadOnlyList<Line> Lines { get; init; } = [];  // empty, never null
}

public Order Load(OrderId id)
{
    ArgumentNullException.ThrowIfNull(id);                 // boundary check, once
    return _store.Find(id) ?? throw new OrderNotFoundException(id);
}

Follow-ups

  • Empty collection or null? — Empty, always: it removes a branch from every caller and never changes meaning. Null only when "unknown" genuinely differs from "none".
  • What about ?. chains? — Fine for reading optional data, dangerous as a way to silence a warning: a?.b?.c quietly produces null instead of failing where the invariant broke.
  • Where do nulls still get in with NRTs on? — Deserialization, reflection, unannotated third-party libraries, and interop.

Common wrong answer

"Add null checks at the start of every method." It doubles the code, hides which layer is actually responsible, and still fails at the one place nobody guarded. Interviewers want the structural answer: required members, non-null defaults, and validation at a single boundary.

midWhen do you throw an exception versus returning a result?

Answer

Throw for the exceptional: a broken invariant, a bug, a dependency that failed — anything the immediate caller cannot reasonably be expected to handle. Return a value for outcomes that are part of the business flow and that callers will branch on every time: "not found", "invalid input", "insufficient funds". The test I use is frequency and locality: if the caller would immediately wrap the call in try/catch to make a routine decision, that decision belongs in the return type. The BCL itself models this with the Try pattern — int.Parse throws, int.TryParse returns a bool — and it exists precisely because parse failure is normal for user input and exceptional for internal data. What I avoid is using exceptions for control flow in a loop, where the cost and the noise in logs both become real.

Example

// business outcome: return it
public Result<Receipt> Charge(Money m) => _balance < m
    ? Result.Fail<Receipt>("insufficient funds")
    : Result.Ok(DoCharge(m));

// broken invariant / bug: throw
if (line.Quantity <= 0) throw new InvalidOperationException($"line {line.Id} has quantity {line.Quantity}");

// the BCL's own split
int.Parse(userInput);                      // throws on bad input
int.TryParse(userInput, out var n);        // expected failure, no exception

Follow-ups

  • Where do validation errors belong? — Returned as a collection of failures from a validation step, so the user sees all of them; throwing on the first is a poor API.
  • Is "not found" an exception? — In a repository, usually no (return null or a result); in a handler that already knows the id must exist, yes.
  • Does this change at an HTTP boundary? — Yes: whatever the internal style, the boundary maps outcomes to status codes and ProblemDetails; exceptions must not leak.

Common wrong answer

"Exceptions are slow so never use them." Throwing is expensive (microseconds, stack capture, and it can be far worse under a debugger), but a try/catch that does not throw is essentially free, and refusing to throw for genuine invariant violations produces code that returns error codes nobody checks.

midWhat is the difference between throw;, throw ex; and wrapping?

Answer

throw; rethrows the current exception and preserves the original stack trace — that is what you want in a catch block that only logs or cleans up. throw ex; rethrows the same object but resets its stack trace to the current line, destroying the evidence of where the failure actually happened; it is one of the most damaging one-character-looking mistakes in a codebase because the bug becomes undiagnosable. Wrapping — throw new DomainException("...", ex) — is correct when you are adding context at a layer boundary, as long as you pass the original as innerException. If you need to rethrow an exception captured elsewhere (from a task, or a background thread), use ExceptionDispatchInfo.Capture(ex).Throw(), which preserves the original stack across the boundary.

Example

try { await _gateway.ChargeAsync(m, ct); }
catch (HttpRequestException ex)
{
    _log.LogWarning(ex, "gateway unavailable for {Amount}", m);
    throw;                                        // stack preserved
    // throw ex;                                  // stack destroyed - never
    // throw new PaymentFailedException("gateway unavailable", ex);   // wrap WITH inner
}

ExceptionDispatchInfo.Capture(captured).Throw();   // rethrow across a boundary

Follow-ups

  • Why catch at all if you only rethrow? — To add context to the log, to record a metric, or to convert the type; a catch that does none of those should not exist.
  • What is an exception filter? — catch (Ex e) when (cond): the filter runs before the stack unwinds, so a dump taken inside a filter still shows the original frames — useful for logging without catching.
  • Should you log and rethrow? — Only once per exception; logging at every layer produces the same failure five times in the log and hides the real count.

Common wrong answer

"throw ex is fine, the message is the same." The message is; the stack is not, and after that the exception points at your catch block instead of at the failing line — this is the single most common reason a production stack trace is useless.

midWhich exceptions should you catch, and how do you design a custom exception?

Answer

Catch specific types you can actually do something about — HttpRequestException to retry, DbUpdateConcurrencyException to reload and merge, OperationCanceledException to exit quietly — and let everything else reach a top-level handler that logs it with correlation and returns a safe response. A blanket catch (Exception) belongs at exactly two places: the process-level boundary (middleware, a background service loop) and any place where continuing is genuinely correct, with the exception logged. For a custom exception: derive from Exception, give it the properties a handler needs (ids, codes) rather than only a message string, provide the standard constructors including one taking an inner exception, and make it serializable-agnostic — the legacy SerializationInfo constructor pattern is obsolete since .NET 8, so do not copy it from old code.

Example

public sealed class OrderNotFoundException(OrderId id)
    : Exception($"Order {id} was not found")
{
    public OrderId OrderId { get; } = id;    // structured, not just a message
}

catch (OperationCanceledException) when (ct.IsCancellationRequested) { /* normal shutdown */ }
catch (SqlException ex) when (ex.Number is 1205)  { /* deadlock victim: retry */ }

Follow-ups

  • Do you ever catch Exception? — Yes at the boundary; the anti-pattern is catching it deep inside and swallowing.
  • What about OutOfMemoryException or StackOverflowException? — Do not try to handle them; StackOverflowException cannot be caught at all since .NET Framework 2.0 — the process dies.
  • Should exception messages be user-facing? — No: they are for operators. The user gets a mapped, sanitised message and a correlation id.

Common wrong answer

"I catch Exception, log it, and continue so the service stays up." That is how corrupted state gets committed and how a failing dependency turns into silently wrong data. Availability that produces wrong answers is worse than a failed request.

seniorWhat does finally actually guarantee?

Answer

Less than most people assume. A finally block runs when the try completes normally, on a handled exception, and on an unwinding exception — but not if the process dies: Environment.FailFast, a StackOverflowException, an OS kill, or an unhandled exception on a background thread that terminates the process. It also does not run before an exception filter further up the stack, since filters execute before unwinding. In practice this means finally and using are correct for releasing resources within a running process, and are not a durability mechanism: if the invariant matters across a crash, it needs a transaction, a write-ahead record, or an idempotent retry, not a cleanup block. The related trap is a return inside finally or an exception thrown from finally, both of which discard the original exception.

Example

try { await DoWorkAsync(ct); }
finally { _semaphore.Release(); }        // guaranteed within the process

// NOT a durability guarantee:
try { await _bus.PublishAsync(evt); }
finally { await _db.MarkPublishedAsync(evt.Id); }   // a crash between the two loses it
// use an outbox: write the event and the state change in ONE transaction

Follow-ups

  • Do finalizers run on shutdown? — Not reliably; .NET does not run finalizers on process exit by default, so never put required cleanup there.
  • What about IHostApplicationLifetime and SIGTERM? — Graceful shutdown gives you a bounded window (default 30 seconds in the generic host) to drain; design for being killed mid-way anyway.
  • Async and finally? — await inside finally is allowed (C# 6+) and works, but if the surrounding task is abandoned the continuation may never run.

Common wrong answer

"finally always runs, so cleanup is guaranteed." Said about a distributed side effect it produces systems that lose messages on every pod eviction. The senior answer names the process-crash boundary and reaches for a transaction or an outbox instead.

seniorHow do you structure error handling across an ASP.NET Core service?

Answer

One boundary, one mapping, no try/catch noise in handlers. I register a global exception handler (IExceptionHandler plus AddProblemDetails, the modern replacement for the old exception-handling middleware) that maps exception types to status codes and returns RFC 9457 ProblemDetails with a trace id and no internal details. Domain code throws or returns results; the boundary translates. Every log entry for a failure carries the correlation id from Activity.Current, so an operator can find the whole request across services. Then the operational half: transient failures get a resilience pipeline (Microsoft.Extensions.Http.Resilience / Polly) with timeout, bounded retry with jittered backoff and a circuit breaker; non-transient ones fail fast. And retries only exist because the write path is idempotent — that ordering is the part candidates skip.

Example

builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler<DomainExceptionHandler>();

public sealed class DomainExceptionHandler(IProblemDetailsService problems) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext ctx, Exception ex, CancellationToken ct)
    {
        ctx.Response.StatusCode = ex switch
        {
            OrderNotFoundException => StatusCodes.Status404NotFound,
            ValidationException    => StatusCodes.Status400BadRequest,
            _                      => StatusCodes.Status500InternalServerError,
        };
        return await problems.TryWriteAsync(new() { HttpContext = ctx, Exception = ex });
    }
}

Follow-ups

  • What must never appear in a response? — Stack traces, SQL, connection strings, internal type names; return a trace id and log the detail server-side.
  • Which failures do you retry? — Idempotent operations on transient faults (timeouts, 5xx, 429 with backoff); never a non-idempotent POST without an idempotency key.
  • How do you avoid retry storms? — Jitter, a bounded retry count, a circuit breaker, and never retrying at more than one layer of the stack.

Common wrong answer

"Try/catch in every controller action and return a 500 with the message." It duplicates policy in fifty places, leaks internals to the client, and guarantees the mapping drifts between endpoints. The expected answer names one boundary and ProblemDetails.

seniorWhat do exceptions actually cost?

Answer

Entering a try block is free at runtime — the tables are static metadata, so a try/catch that never throws costs essentially nothing and does not prevent inlining in modern JITs. Throwing costs real time: allocating the exception, capturing the stack trace, and a two-pass search for a handler, which lands in the tens of microseconds for a shallow stack and much worse deep in a call chain, or under a debugger where first-chance notifications dominate. The number that matters operationally is throughput: a path throwing at a few thousand exceptions per second will show up clearly in a profile, and .NET 9's rewritten exception handling improved this substantially but did not make it free. So the rule is not "avoid try/catch", it is "do not use throwing as an expected outcome in a loop" — and if you find a hot exception path, the fix is usually a Try-shaped API.

Example

// hot path with expected failures: an exception per bad row is the wrong design
foreach (var row in rows)
    try { Add(int.Parse(row)); } catch (FormatException) { bad++; }

// same logic without throwing
foreach (var row in rows)
    if (int.TryParse(row, out var v)) Add(v); else bad++;

Follow-ups

  • Does a try block prevent optimisation? — Historically it limited some JIT optimisations inside the protected region; today the practical effect is negligible compared with the cost of the throw.
  • Why are exceptions so slow under a debugger? — Every first-chance exception notifies the debugger, which can turn microseconds into milliseconds — a common cause of "it's only slow when I debug it".
  • How do you measure it? — BenchmarkDotNet for the micro cost, and an exception-rate counter (exception-count in dotnet-counters) in production.

Common wrong answer

"try/catch slows down the method, so I only use it where necessary." The cost is in the throw, not the guard. Getting this backwards leads to code that avoids error handling in the wrong places while happily throwing on the hot path.

principalYour team proposes replacing exceptions with a Result<T> type across the codebase. What do you do?

Answer

I would scope it rather than accept or reject it. Results genuinely improve the code where failure is an expected business outcome and the caller must handle it: validation, parsing, domain rules. They are a poor fit for infrastructure failures — a socket timeout or a broken invariant is not something every intermediate frame should thread through a return type — and a codebase that returns Result everywhere ends up re-implementing exception propagation by hand, badly, with a monadic style that half the team dislikes. So my answer is: results in the domain and application layer where the failure set is closed and enumerable; exceptions across infrastructure and at the process boundary; and one agreed mapping at the edge. The other conditions are practical: pick a library or write fifty lines, do not both; agree how results compose (C# has no do-notation, so the ergonomics are real work); and never mix both styles inside one layer, which is the outcome that makes everyone hate the change.

Example

// domain: closed, enumerable failures - a result is honest
public Result<Order, OrderError> Place(Cart cart, Customer c) =>
    cart.IsEmpty          ? OrderError.EmptyCart
  : c.IsBlocked           ? OrderError.CustomerBlocked
  : !_stock.Reserve(cart) ? OrderError.OutOfStock
  : Result.Ok(new Order(cart, c));

// infrastructure: open-ended failure - exception, handled at the boundary
await _db.SaveChangesAsync(ct);   // may throw; the global handler maps it

Follow-ups

  • How would C# 15 unions change this? — union types with exhaustive switch checking make the closed-failure-set case genuinely first class; that is a reason to design the failure enum now and revisit the representation later.
  • How do you keep it from spreading? — Architecture tests on which layer may return which type, plus code review on the two seams.
  • What about performance? — A struct result avoids the throw cost, which matters only if you were throwing thousands of times a second; do not sell the change on performance.
  • What is the migration cost? — Every call site in the affected layer, plus the team's fluency; scope it to new code and one bounded context first.

Common wrong answer

Either extreme: "exceptions are legacy, results everywhere" or "no, C# is exception-based, drop it". Both skip the actual question, which is where the boundary sits — and a lead who cannot articulate that boundary will get a codebase with two conventions and no rule.

07Modern C# (8 → 15) and migration

Two things are being tested here: whether you have kept up, and whether you can tell a genuine improvement from a fashion. Interviewers who follow the language will open with "what is new in C# 14" and then push on why it exists and what it costs. At lead level the question turns into migration: language version and target framework are fleet-wide decisions with deadlines attached, and .NET 8 and .NET 9 both reach end of support on 2026-11-10 — two months from the date on this page — so an upgrade plan is a live topic, not a hypothetical.

screenerWhat is new in C# 14, and which parts do you actually use?

Answer

C# 14 shipped with .NET 10 on 2025-11-11. The headline is extension members: an extension(Receiver) block that can declare extension properties, static extension members and user-defined operators, generalising the this-parameter extension methods we have had since C# 3. Next is the field keyword, which lets a property accessor use the compiler-generated backing field without declaring one. The rest are smaller but genuinely useful: null-conditional assignment (customer?.Order = x), modifiers on simple lambda parameters ((text, out result) => ...), nameof on unbound generics (nameof(List<>)), partial constructors and events, user-defined compound assignment operators, and first-class span types with new implicit conversions between arrays and spans. In my own code the two I reach for daily are field and the span conversions; extension properties are the ones that change how libraries are shaped.

Example

// field keyword: validation without a hand-written backing field
public string Message
{
    get;
    set => field = value ?? throw new ArgumentNullException(nameof(value));
}

// null-conditional assignment
customer?.Order = GetCurrentOrder();     // RHS not evaluated when customer is null

// lambda parameter modifiers without types
TryParse<int> parse = (text, out result) => int.TryParse(text, out result);

nameof(List<>);                          // "List"

Follow-ups

  • Is field a breaking change? — Potentially, in types that already have a symbol named field; disambiguate with @field or this.field, or rename.
  • Which C# 14 feature needs .NET 10 at runtime? — Extension members and first-class spans lean on the newer BCL; the language version is tied to the target framework by default, and overriding LangVersion upward is not supported for shipping code.
  • What did .NET 10 bring beyond the language? — Broad performance work across JIT, GC and libraries, plus file-based apps (dotnet run app.cs) with the new preprocessor directives.

Common wrong answer

Listing C# 12 features (primary constructors, collection expressions) as "the new ones". It is the clearest sign of someone who upgraded once and stopped reading; the interviewer usually knows the release notes better than the candidate and this is where the level assessment gets revised down.

midWalk me through pattern matching. Where does it genuinely improve code?

Answer

It has grown from a type test in C# 7 into a small sub-language: type and constant patterns (7), switch expressions, property, tuple and positional patterns (8), relational and logical patterns with and/or/not (9), extended property patterns (10) and list patterns with slices (11). Where it earns its place is in flattening branch-heavy code into one expression that the compiler can check for exhaustiveness — mapping a domain state to a decision, parsing a token, or classifying an input by shape. Where it hurts is when a single expression grows past a handful of arms with nested property patterns; that is a domain concept asking to be a method. The exhaustiveness point becomes much stronger in C# 15, where the closed modifier lets the compiler know a hierarchy's complete set of direct descendants, so a switch that handles them all needs no discard arm.

Example

var fee = payment switch
{
    { Method: Card, Amount: < 10m }        => 0.30m,
    { Method: Card, Amount: var a }        => a * 0.014m,
    { Method: Transfer, Sepa: true }       => 0m,
    { Method: Transfer }                   => 4.50m,
    null                                   => throw new ArgumentNullException(nameof(payment)),
    _                                      => throw new NotSupportedException(),
};

// list patterns (C# 11)
if (segments is ["api", "v1", var resource, ..]) Route(resource);

Follow-ups

  • What warning tells you a switch expression is incomplete? — CS8509; it is worth promoting to an error, because the runtime alternative is SwitchExpressionException.
  • Are switch expressions faster? — Sometimes: the compiler can build a jump table or a balanced decision tree; readability is the better justification.
  • What is the is not null idiom for? — It avoids a user-defined == operator being invoked, which is why analysers prefer it over != null.

Common wrong answer

"Pattern matching is just a nicer switch." It misses the compiler-checked exhaustiveness, which is the actual engineering value: adding a case to an enum or a hierarchy makes the build tell you every place that must be updated.

midPrimary constructors on classes (C# 12): would you use them?

Answer

Yes, for dependency-injected services, where they remove the field-plus-assignment ceremony that made up half of every constructor. The semantics differ from records though, and that is what interviewers probe: on a class the parameters are not properties, they are captured into hidden fields only if used, they stay in scope for the whole class body including field initializers, and they are mutable — you can assign to a primary constructor parameter, which silently changes the captured value. There is no generated deconstruction, no equality, and no readonly guarantee, so a team wanting strict immutability still needs explicit readonly fields. My rule is: primary constructors for services and adapters with injected dependencies, explicit constructors for domain types that need validation or overloads.

Example

// concise and idiomatic for DI
public sealed class OrderService(IOrderStore store, ILogger<OrderService> log)
{
    public async Task<Order?> GetAsync(OrderId id, CancellationToken ct)
    {
        log.LogDebug("loading {OrderId}", id);
        return await store.FindAsync(id, ct);
    }
}

// the trap: parameters are not readonly
public sealed class Counter(int start) { public void Reset() => start = 0; }   // compiles

Follow-ups

  • How do you validate a primary constructor parameter? — In a field initializer: private readonly IStore _s = store ?? throw new ArgumentNullException(nameof(store));
  • Does it work with inheritance? — Yes: class B(int x) : A(x); only one constructor may be primary and other constructors must chain to it.
  • Why is a record's primary constructor different? — It generates public init properties, equality members and Deconstruct; a class's does none of that.

Common wrong answer

"Primary constructor parameters become properties, like in records." They do not on a class — nothing is exposed, and assuming otherwise produces code that tries to read other.store and does not compile, or worse, a mental model where the values are immutable when they are not.

midCollection expressions: what do they compile to, and what is new in C# 15?

Answer

C# 12 introduced [...] as one syntax for building any collection, with a spread operator .. for inlining another sequence. The compiler picks an efficient construction strategy per target type: a plain array for T[], CollectionsMarshal-assisted creation for List<T>, a stack buffer for a Span<T> target, and the collection builder method for types that opt in — so it is usually at least as good as what you would write by hand, and better for spans. C# 15 adds collection expression arguments: a leading with(...) element passes arguments to the underlying constructor or factory, which finally makes it possible to specify a capacity or a comparer without abandoning the syntax. That was the main gap — before it, choosing [..values] meant losing control over capacity and equality semantics.

Example

int[] a = [1, 2, 3];
List<int> b = [0, ..a, 4];                  // spread
Span<int> s = [1, 2, 3];                    // may use a stack buffer

// C# 15: arguments to the underlying collection
List<string> names = [with(capacity: values.Length * 2), ..values];
HashSet<string> set = [with(StringComparer.OrdinalIgnoreCase), "Hello", "HELLO"];  // 1 element

Follow-ups

  • Does [] allocate? — For an empty array target it uses the cached Array.Empty<T>(); for List<T> it constructs one.
  • Can your own type participate? — Yes, with [CollectionBuilder] pointing at a static builder method taking a ReadOnlySpan<T>.
  • Is it worth rewriting existing initializers? — Only opportunistically; the value is consistency in new code, not a mass edit that pollutes blame history.

Common wrong answer

"It's just a shorter new List<int> { ... }." It is target-typed and the compiler chooses a different construction strategy per target, including stack allocation for spans — which is exactly why it matters in performance-sensitive code and why the C# 15 argument syntax was needed.

midHow do you express immutability in modern C#? readonly, init, required, records.

Answer

There is a ladder. readonly fields are the strongest for a field; init accessors (C# 9) allow object-initializer syntax and then freeze the property; required members (C# 11) force the caller to set them without needing a constructor parameter, which is what makes large DTOs safe without a twelve-argument constructor; and records combine init properties with value equality and with-expressions. For collections, IReadOnlyList<T> is only a view — ImmutableArray<T> or FrozenSet<T> is the real guarantee. What none of these give you is deep immutability: a record holding a mutable list is a mutable object with a value-equality signature, which is the mistake that gets shipped.

Example

public sealed record Invoice
{
    public required InvoiceId Id { get; init; }                 // caller must set
    public required DateOnly Issued { get; init; }
    public ImmutableArray<Line> Lines { get; init; } = [];      // deep, not just a view
    public decimal Total => Lines.Sum(l => l.Amount);           // computed, never stale
}

var v2 = v1 with { Issued = today };   // shallow copy + set

Follow-ups

  • Does init stop reflection or deserialization from setting it? — No; System.Text.Json and EF Core set init properties deliberately, so treat immutability as a compile-time contract.
  • Is ImmutableArray free? — Reads are; building costs a copy, and ImmutableList is a tree with very different performance from an array — pick deliberately.
  • What about readonly record struct? — The strongest small-value shape: value semantics, no allocation, no defensive copies.

Common wrong answer

"Records are immutable so I use them for thread-safe state." Shallow immutability shared across threads plus a mutable member is a data race with extra confidence. The correct answer names the depth limit explicitly.

seniorWhat is coming in C# 15, and would you adopt any of it early?

Answer

C# 15 ships with .NET 11 in November 2026 and is in preview now. The two that change how you model domains are union types — public union Pet(Cat, Dog, Bird);, with implicit conversions from each case and compiler-checked exhaustive switches — and closed hierarchies, where a closed class can only be derived from within its declaring assembly, so the compiler knows the full set of direct descendants and a switch covering them needs no default arm. Then collection expression arguments (with(...)), extension indexers, labeled break/continue for nested loops, and the first step of a multi-release memory safety redesign that ties unsafe to operations that actually access unmanaged memory. Adoption advice: nothing in production until the release, because previews carry breaking changes and parts of the union proposal are still unimplemented — but design new domain models as closed hierarchies now, because that is the shape unions and closed will formalise.

Example

// C# 15 preview
public record class Cat(string Name);
public record class Dog(string Name);
public union Pet(Cat, Dog);                       // union type

public closed record class GateState;             // closed hierarchy
public record class Closed : GateState;
public record class Open(float Percent) : GateState;

string Describe(GateState s) => s switch
{
    Closed => "closed",
    Open(var p) => $"{p}% open",                  // exhaustive: no default arm needed
};

outer: foreach (var row in rows)                  // labeled break/continue
    foreach (var cell in row) if (cell.IsGoal) break outer;

Follow-ups

  • How mature are unions right now? — The runtime added UnionAttribute and IUnion in .NET 11 Preview 5 and parts of the specification are still landing; treat it as a preview feature.
  • Is closed transitive? — No: a non-closed descendant of a closed class can still be derived from elsewhere; mark intermediate levels closed to keep exhaustiveness.
  • What does this do to the Result-versus-exceptions argument? — It strengthens the result side for closed failure sets, because exhaustiveness becomes a compiler guarantee rather than a convention.

Common wrong answer

"C# 15 has discriminated unions like F#." Close enough to sound informed and wrong in the details that matter: this is a union of named case types with implicit conversions and a closed companion feature, still in preview, not F#-style inline case declarations. If you mention it, mention the preview status.

08Threading, concurrency and synchronisation

Async gets asked more, but concurrency gets asked deeper, because it is where senior candidates separate themselves: anyone can say "use a lock", far fewer can explain what volatile guarantees, why double-checked locking is subtle, or how to make a shared cache correct without serialising every request. Expect at least one "is this code thread-safe?" snippet. The strongest answers reach for a design that removes shared mutable state before reaching for a synchronisation primitive.

screenerWhat does lock do, and what should you lock on?

Answer

Classically, lock (obj) compiles to Monitor.Enter/Monitor.Exit in a try/finally, giving mutual exclusion plus the memory barriers that make writes inside the lock visible to the next thread that takes it. It is re-entrant on the same thread. You lock on a private, readonly, reference-typed object that nothing else can see — never on this, never on a Type, never on a string (interned literals are shared process-wide), because anything public means an unrelated piece of code can deadlock you. In C# 13 / .NET 9 there is a dedicated System.Threading.Lock type: lock on a variable of that type uses its own faster implementation, and the compiler recognises it — that is the modern default for new code. And the async rule is absolute: you cannot await inside a lock, so async mutual exclusion means SemaphoreSlim.

Example

// C# 13 / .NET 9+
private readonly Lock _gate = new();
public void Add(int x) { lock (_gate) { _total += x; } }

// pre-C# 13
private readonly object _legacyGate = new();

// async: a semaphore, not a lock
private readonly SemaphoreSlim _sem = new(1, 1);
public async Task AddAsync(int x, CancellationToken ct)
{
    await _sem.WaitAsync(ct);
    try { _total += x; } finally { _sem.Release(); }
}

Follow-ups

  • Why not lock on this? — Any caller holding your instance can also lock it, so an external lock (myObject) can block or deadlock your internals.
  • Is lock expensive? — An uncontended lock is tens of nanoseconds; contention is what costs, because it means a kernel wait and a context switch.
  • What about Monitor.TryEnter? — Use it with a timeout when you must not block forever; it turns a deadlock into a detectable failure.

Common wrong answer

"Lock on a static object so all instances share it." Sometimes required, usually a bug: it serialises unrelated instances and turns a per-object invariant into a global bottleneck. The interviewer is checking whether you know what the lock protects.

midRace condition versus deadlock — and how do you prevent each?

Answer

A race condition is a correctness bug: two threads interleave and produce a result neither would alone — a lost update, a torn read, a check-then-act that no longer holds by the time you act. A deadlock is a liveness bug: two threads each hold what the other needs and neither proceeds. Races are prevented by removing shared mutable state (immutability, per-thread or per-request state), or by making the operation atomic (Interlocked, a lock, a database constraint). Deadlocks are prevented by a global lock ordering, by holding one lock at a time, by never calling out to unknown code while holding a lock, and by using timeouts so the failure is loud instead of silent. In practice the highest-value rule for a team is the last one in that list — no external call, no event handler and no callback inside a lock, because that is where the unknown second lock comes from.

Example

// race: check-then-act
if (!_cache.ContainsKey(k)) _cache[k] = Load(k);       // two threads both load

// deadlock: opposite lock order
void A() { lock (_x) { lock (_y) { } } }
void B() { lock (_y) { lock (_x) { } } }               // classic ABBA

// atomic instead of locked
Interlocked.Increment(ref _counter);
Interlocked.CompareExchange(ref _head, newNode, oldHead);

Follow-ups

  • How do you find a deadlock in production? — A dump plus dotnet-dump analyze and clrstack/syncblk; threads blocked in Monitor.Wait with a cycle in the ownership graph.
  • Is a database deadlock the same? — Same shape, different resource; the fix is also lock ordering (touch tables in a consistent order) plus retry on the deadlock-victim error.
  • What is a livelock? — Threads keep responding to each other and make no progress; typically a retry loop with no backoff.

Common wrong answer

"Add a lock around the whole method." It removes the race and adds a bottleneck plus a new deadlock surface if that method calls anything else. The expected reasoning is what invariant is being protected and how small the critical section can be.

midWhat does volatile guarantee? When is it the right tool?

Answer

volatile constrains reordering and forces reads and writes to go to memory rather than a register: a volatile read has acquire semantics and a volatile write has release semantics. That is enough for one specific pattern — a flag or a reference published by one thread and observed by others, where the value itself is written atomically. It is not a lock and gives no atomicity for compound operations, so volatile int x; x++; is still a race. The cases where it matters most are weak memory models — arm64 hardware, which is now ordinary in cloud fleets and on Apple silicon — where a non-volatile flag genuinely can be observed stale indefinitely, unlike on x86 where the hardware hides many mistakes. For anything beyond a flag or a published reference, use Interlocked, a lock, or an immutable snapshot swap.

Example

private volatile bool _stopping;              // fine: single write, many reads
public void Stop() => _stopping = true;
private void Loop() { while (!_stopping) { Work(); } }

private volatile Config _config;              // fine: publish an immutable object
public void Reload(Config c) => _config = c;

private volatile int _count;
public void Bad() => _count++;                // STILL a race: read-modify-write
public void Good() => Interlocked.Increment(ref _count);

Follow-ups

  • Why did the code work on x86 and fail on arm64? — x86-64 has a strong memory model that hides missing barriers; arm64 does not, so latent bugs surface after a move to Graviton/Ampere or Apple silicon.
  • What about Volatile.Read/Volatile.Write? — The same semantics applied per-operation, which is preferable when only some accesses need it; also works for types volatile cannot be applied to.
  • Do locks make volatile unnecessary? — Yes for data accessed only inside the lock: entering and leaving a lock includes the required barriers.

Common wrong answer

"volatile makes the variable thread-safe." It makes visibility ordering explicit for single reads and writes, nothing more. That belief is exactly what produces volatile counters that lose increments under load.

midHow do you implement thread-safe lazy initialisation?

Answer

Use Lazy<T> with LazyThreadSafetyMode.ExecutionAndPublication, which is the default for the parameterless constructor: it guarantees the factory runs exactly once and everyone sees the same instance, and it caches an exception if the factory throws (which you must decide is acceptable). Hand-written double-checked locking is the classic interview version — check without a lock, lock, check again, assign — and it is correct in .NET only because the memory model plus a volatile field prevents a reader from seeing a partially constructed object; getting that detail wrong is the point of the question. For async initialisation there is no Lazy in the BCL that awaits, so the idiom is Lazy<Task<T>> — with the caveat that a faulted task is cached forever unless you reset it.

Example

private readonly Lazy<Config> _config = new(() => Load(), isThreadSafe: true);
public Config Config => _config.Value;

// async variant
private readonly Lazy<Task<Config>> _configAsync =
    new(() => LoadAsync(), LazyThreadSafetyMode.ExecutionAndPublication);
public Task<Config> GetAsync() => _configAsync.Value;

// the hand-rolled version the interviewer wants you to critique
private volatile Config? _c;                      // volatile is REQUIRED here
public Config Get()
{
    if (_c is null) lock (_gate) { _c ??= Load(); }
    return _c;
}

Follow-ups

  • What if the factory throws? — ExecutionAndPublication caches the exception; PublicationOnly lets another thread retry but may run the factory several times.
  • Why is a static readonly field often better? — Static initialisation is already thread-safe and lazy per the CLR's beforefieldinit rules, with no Lazy allocation.
  • Is Lazy<T> free? — One extra allocation and an indirection per access; irrelevant except in very hot code.

Common wrong answer

Writing double-checked locking without volatile and calling it correct. On a weak memory model a reader can see the reference before the constructor's writes; this is the canonical example of why "it works on my x86 machine" is not evidence.

seniorIs static state safe? What makes a type thread-safe?

Answer

Static state is shared by every thread in the process, so it is safe only if it is immutable, or if every access is synchronised, or if it is genuinely per-thread ([ThreadStatic], AsyncLocal<T>). The general definition is that a type is thread-safe if concurrent use cannot leave it in an invalid state or produce results impossible under some sequential ordering — which is a property of the whole API, not of individual methods: a type whose methods are each locked can still be misused via check-then-act by a caller. The BCL contract is worth quoting: for most types, public static members are thread-safe and instance members are not. In services this matters most for caches, for Random (use Random.Shared, .NET 6+), for DateTime.Now versus an injected TimeProvider, and for anything holding request state in a static.

Example

// unsafe: shared mutable static
private static readonly Dictionary<string, int> _counts = new();

// safe options, in order of preference
private static readonly FrozenDictionary<string, int> _lookup = Build();   // immutable
private static readonly ConcurrentDictionary<string, int> _live = new();   // synchronised
private static readonly AsyncLocal<RequestContext> _ctx = new();           // per-flow

var n = Random.Shared.Next();      // .NET 6+: thread-safe, no shared-instance bug

Follow-ups

  • Is HttpClient thread-safe? — Yes for the send methods, which is why it is a singleton; the mistake is per-request construction (socket exhaustion) or mutating DefaultRequestHeaders concurrently.
  • Is EF Core's DbContext thread-safe? — No, explicitly not; concurrent use throws or corrupts, which is why it is scoped and never captured by a singleton.
  • What is AsyncLocal for? — Flowing ambient context (correlation ids) across async continuations; it flows to child operations and copies on write, which surprises people.

Common wrong answer

"It's static readonly, so it's thread-safe." readonly freezes the reference, not the object: a static readonly Dictionary mutated at runtime is the most common thread-safety bug in .NET services, and it corrupts silently rather than throwing.

seniorDesign a producer/consumer pipeline. Why Channel<T>?

Answer

System.Threading.Channels is the modern in-process queue: async-native (the consumer awaits instead of blocking a thread), allocation-light, and — the key property — it supports bounded capacity with a defined full-mode behaviour, so producers experience backpressure instead of the queue growing until the process dies. The shape I use is a bounded channel with BoundedChannelFullMode.Wait, one or more consumers reading with await foreach (var item in reader.ReadAllAsync(ct)), and a hosted service owning the lifetime so shutdown completes the writer and drains the reader. BlockingCollection is the older equivalent and blocks threads, which is exactly wrong on a server. The decision that matters more than the type is what happens when the queue is full: block the producer, drop the oldest, drop the newest, or reject — and that must be a deliberate product decision, not a default.

Example

var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(1_000)
{
    FullMode = BoundedChannelFullMode.Wait,   // backpressure, not unbounded growth
    SingleReader = false, SingleWriter = false,
});

// consumer, inside a BackgroundService
await foreach (var job in channel.Reader.ReadAllAsync(ct))
    await HandleAsync(job, ct);

// shutdown: complete then drain
channel.Writer.Complete();
await channel.Reader.Completion;

Follow-ups

  • Why not just Task.Run per item? — No backpressure, no ordering, no bounded concurrency; the pool absorbs the burst until it cannot.
  • What is lost on process restart? — Everything in the channel: it is in-memory. If the work must survive, it belongs in a durable queue, and saying so unprompted is the senior signal.
  • How many consumers? — Sized to the downstream constraint, measured; and if ordering per key matters, partition by key rather than adding consumers.

Common wrong answer

"Use a ConcurrentQueue and a while(true) loop with a Task.Delay." It works, wastes a thread and adds latency, and has no backpressure — the queue grows without bound under load, which turns a downstream slowdown into an out-of-memory kill.

seniorA cache is being stampeded: 500 requests miss the same key at once. Fix it.

Answer

Collapse the duplicate work with a per-key async gate: the first miss starts the load and stores the task in the cache, and the other 499 await that same task. Storing the task rather than the value is what makes it correct, because the entry exists from the moment the load starts, not from when it finishes. On top of that: a short "in-flight" TTL so a failed load is not cached indefinitely, jittered expirations so a thousand keys do not expire in the same second, and optionally serving stale data while refreshing in the background when the domain allows it. HybridCache (.NET 9, in Microsoft.Extensions.Caching.Hybrid) implements exactly this — stampede protection over an L1 in-memory plus L2 distributed cache — so the modern answer is usually "use HybridCache and explain what it does", rather than hand-rolling it.

Example

// .NET 9+: stampede protection built in
public Task<Product> GetAsync(int id, CancellationToken ct) =>
    _hybrid.GetOrCreateAsync($"product:{id}",
        factory: async token => await _db.LoadAsync(id, token),
        options: new HybridCacheEntryOptions { Expiration = TimeSpan.FromMinutes(5) },
        cancellationToken: ct).AsTask();

// hand-rolled equivalent: cache the TASK, not the value
private readonly ConcurrentDictionary<int, Lazy<Task<Product>>> _inflight = new();

Follow-ups

  • Why cache the task and not the value? — The window between "first request starts loading" and "value is stored" is exactly when the other 499 arrive.
  • What if the load fails? — Remove the entry so the failure is not cached; otherwise one transient error poisons the key until expiry.
  • Distributed stampede? — Per-instance collapsing still leaves N instances loading once each; if that matters, add a short distributed lock or accept N as the bound.

Common wrong answer

"Lock around the cache lookup." A single global lock serialises every request for every key — turning a stampede on one key into a queue for the whole cache — and if the lock is held across the async load it either deadlocks or blocks pool threads.

principalA race condition corrupts one order in ten thousand. It is not reproducible. How do you run this?

Answer

First contain, then diagnose, then prevent — and be explicit that the order matters, because a rare corruption is a data-integrity incident, not a bug ticket. Containment means finding the blast radius (how many records, since when, detectable how) and stopping the bleeding: a uniqueness or check constraint in the database, an idempotency key, or serialising the affected path even at a throughput cost, shipped today. Diagnosis is evidence-driven: add a structured log or metric at the suspect interleaving with the identifiers needed to correlate, capture concurrent operations on the same aggregate, and reason about the two writers involved — nearly always a check-then-act across a boundary that is not transactional. The real fix is usually to move the invariant to where atomicity exists: a database constraint, an optimistic concurrency token, or a single-writer partition. Prevention is the part leads are graded on: a test that runs the operation from N threads, an invariant check in the data layer, and a written note about which invariants are enforced where.

Example

Contain   unique index on (CustomerId, IdempotencyKey)  -> duplicates now fail loudly
          alert on the constraint violation so we can count the real rate
Diagnose  log {OrderId, Operation, Version, ThreadId, TraceId} around the write
          look for two writes on the same aggregate within milliseconds
Root      check-then-act: read balance -> decide -> write, no transaction
Fix       optimistic concurrency (rowversion) + retry, or a conditional UPDATE
          ... WHERE Version = @expected   (0 rows affected = someone else won)
Prevent   concurrency test (N threads, same aggregate) in CI; invariant in the DB,
          not only in C#; document which layer owns which invariant

Follow-ups

  • Why put the constraint in the database? — It is the only place that sees all writers, including replays, migrations and the console app somebody wrote last year.
  • How do you test a race? — Deterministically where possible (inject a barrier at the suspect point), plus a stress test; and accept that absence of failure is weak evidence.
  • What do you tell stakeholders? — The rate, the detectable blast radius, the containment already shipped, and the date for the real fix — in that order.
  • What if it is in a third-party library? — Wrap it with your own serialisation, pin the version, file the issue, and record the workaround with an expiry date.

Common wrong answer

"Add a lock around the operation and move on." It hides the symptom on one instance and does nothing across a horizontally scaled service — the second pod races the first exactly as before. Interviewers are listening for "where does atomicity actually exist in this system?".

09Dependency injection and hosting

In a .NET back-end loop this is asked almost as often as async, because every service is built on the generic host and every team has been burned by a lifetime mistake. Mid-level questions are the three lifetimes and the options pattern; senior questions are captive dependencies, IHttpClientFactory and background service failure modes; lead questions are about where the container should stop — how much magic a codebase should contain, and what you enforce at startup so a mistake fails the build instead of production.

screenerSingleton, scoped, transient — how do you choose?

Answer

Singleton: one instance for the process, for stateless services, caches, configuration and expensive-to-create clients — it must be thread-safe. Scoped: one instance per scope, which in ASP.NET Core means per request, for anything carrying request state or a unit of work such as a DbContext. Transient: a new instance per resolution, for cheap stateless helpers where sharing is meaningless. The decision is driven by state and thread safety, not by cost: if it holds per-request data it is scoped, if it holds shared mutable state it is a singleton you must synchronise, and if it holds nothing it can be any of them. The trap is transient IDisposables resolved from the root container, which are held until the container is disposed — that is, until the process ends.

Example

services.AddSingleton<IClock, SystemClock>();          // stateless, thread-safe
services.AddScoped<IUnitOfWork, EfUnitOfWork>();      // per request
services.AddTransient<IEmailFormatter, Formatter>();  // cheap, stateless
services.AddDbContext<AppDb>(o => ...);               // scoped by default - deliberately

// keyed services (.NET 8) when several implementations coexist
services.AddKeyedSingleton<IPaymentGateway, StripeGateway>("stripe");

Follow-ups

  • Who disposes what? — The container disposes what it created, when the owning scope ends; a singleton lives until the host stops.
  • What about a singleton in a console app or a background worker? — There is no request scope, so you create scopes explicitly with IServiceScopeFactory for each unit of work.
  • Is transient ever wrong for a cheap type? — When it is IDisposable and resolved from the root, or when it is resolved thousands of times per request and allocation shows up in a profile.

Common wrong answer

"Use transient by default, it's the safest." It is the least surprising for state, but it hides lifetime bugs (root-scoped disposables leaking) and produces avoidable allocation. The expected answer starts from state and thread safety.

midWhat is a captive dependency, and how do you stop one shipping?

Answer

A captive dependency is a shorter-lived service captured by a longer-lived one: a scoped DbContext injected into a singleton. The singleton is created once, so it holds that first request's DbContext forever — which means stale data, a connection held for the life of the process, and concurrent use of a type that is explicitly not thread-safe, producing corrupted state or "a second operation was started on this context" errors. The fix is to inject IServiceScopeFactory and create a scope per unit of work, or to make the consumer scoped. The way you stop it shipping is validation at startup: the default host in Development already validates scopes, and I turn ValidateScopes and ValidateOnBuild on in every environment so the process fails fast at boot rather than corrupting data at 3 a.m.

Example

// bug: scoped DbContext captured by a singleton
public sealed class Cache(AppDb db) { }        // registered AddSingleton<Cache>()

// correct: a scope per unit of work
public sealed class Cache(IServiceScopeFactory scopes)
{
    public async Task<Product> LoadAsync(int id, CancellationToken ct)
    {
        await using var scope = scopes.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDb>();
        return await db.Products.FindAsync([id], ct);
    }
}

builder.Host.UseDefaultServiceProvider(o => { o.ValidateScopes = true; o.ValidateOnBuild = true; });

Follow-ups

  • Why is ValidateOnBuild worth the startup cost? — It resolves every registration once, so a missing or mis-scoped dependency fails at boot, not at the first request that touches that code path.
  • Does it catch everything? — No: it cannot see dependencies resolved manually from a provider, which is another reason to avoid service location.
  • What about a background service needing scoped work? — BackgroundService is a singleton; create a scope per iteration.

Common wrong answer

"Register the DbContext as transient so the singleton gets a fresh one." A transient resolved once into a singleton constructor is captured just as permanently — the lifetime of the consumer is what matters, not the registration.

midWhy IHttpClientFactory? What are the two failure modes it fixes?

Answer

It fixes the two opposite mistakes people make with HttpClient. Creating one per request exhausts ephemeral ports: each disposed client leaves a socket in TIME_WAIT for a couple of minutes, so a busy service runs out of ports and starts failing with connection errors under load. Keeping one static forever fixes that but pins DNS: the underlying handler caches connections, so a failover that changes an IP address is never picked up. The factory keeps a pool of handlers with a rotation lifetime (two minutes by default), hands out cheap client instances over them, and gives you one place to configure resilience, logging and default headers. In modern code the alternative is a single SocketsHttpHandler with PooledConnectionLifetime set, which achieves the same rotation; either answer is acceptable if you can name both failure modes.

Example

builder.Services.AddHttpClient<PricingClient>(c =>
{
    c.BaseAddress = new Uri("https://pricing.internal/");
    c.Timeout = TimeSpan.FromSeconds(10);
})
.AddStandardResilienceHandler();     // Microsoft.Extensions.Http.Resilience: timeout, retry, breaker

// equivalent without the factory
new HttpClient(new SocketsHttpHandler { PooledConnectionLifetime = TimeSpan.FromMinutes(2) });

Follow-ups

  • Is a typed client scoped or transient? — Transient by default; the expensive handler underneath is pooled, which is what makes that cheap.
  • Where do you set the timeout? — On the client for the whole request, plus per-attempt timeouts in the resilience pipeline; a retry inside a 100-second default timeout is not a policy.
  • What about DNS in Kubernetes? — The same pinning problem, made worse by service IP churn; the handler lifetime is what keeps you honest.

Common wrong answer

"Use a static HttpClient, that's the documented fix." It is half the fix and it is the half that produces a silent outage during a failover, because the client keeps talking to an IP that no longer serves traffic. Naming both failure modes is the point of the question.

midIOptions, IOptionsSnapshot, IOptionsMonitor — which and when?

Answer

IOptions<T> is a singleton computed once at first use: correct for settings that cannot change while the process runs, and the only one you can inject into a singleton safely. IOptionsSnapshot<T> is scoped and recomputed per request, so a configuration reload is visible to the next request — it cannot be injected into a singleton. IOptionsMonitor<T> is a singleton that exposes CurrentValue plus a change callback, which is what a singleton or a background service needs for hot-reloadable settings. On top of that, validation: ValidateDataAnnotations() plus ValidateOnStart() turns a bad configuration into a startup failure instead of a null reference on the first request that reads it — which is the part most teams skip.

Example

builder.Services.AddOptions<PricingOptions>()
    .Bind(builder.Configuration.GetSection("Pricing"))
    .ValidateDataAnnotations()
    .Validate(o => o.Timeout > TimeSpan.Zero, "Timeout must be positive")
    .ValidateOnStart();               // fail at boot, not at first request

public sealed class Worker(IOptionsMonitor<PricingOptions> options)   // singleton-safe, hot reload
{
    private PricingOptions Current => options.CurrentValue;
}

Follow-ups

  • Why does injecting IOptionsSnapshot into a singleton throw? — It is scoped; the scope validator catches it, which is another argument for ValidateScopes.
  • What triggers a reload? — reloadOnChange on the JSON provider, or a provider that pushes changes; the monitor's callback can fire more than once per change, so make handlers idempotent.
  • Where do secrets go? — Not in appsettings.json: user secrets in development, a vault or the platform's secret store in production, bound through the same options types.

Common wrong answer

"Inject IConfiguration and read the key where you need it." It scatters magic strings, loses type safety and validation, and makes the settings a class needs invisible from its constructor — the exact coupling the options pattern exists to remove.

seniorWhat goes wrong with BackgroundService in production?

Answer

Three things, all of which have bitten real services. First, exceptions: an unhandled exception in ExecuteAsync historically stopped that one service silently; since .NET 6 the default BackgroundServiceExceptionBehavior is StopHost, so the whole process goes down — which is better, but only if you know it, and either way the fix is your own try/catch with a restart-with-backoff loop. Second, startup: work in StartAsync blocks host startup, so long initialisation delays readiness and can trip a liveness probe — do the work in ExecuteAsync after the first yield. Third, shutdown: you get a bounded window (30 seconds by default) after the stopping token fires, so long-running iterations must check the token and be safe to kill mid-way, which means idempotent work and a durable queue rather than in-memory state.

Example

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    await Task.Yield();                        // don't block host startup
    while (!stoppingToken.IsCancellationRequested)
    {
        try
        {
            await using var scope = _scopes.CreateAsyncScope();
            await scope.ServiceProvider.GetRequiredService<IJobRunner>().RunAsync(stoppingToken);
        }
        catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested) { break; }
        catch (Exception ex)
        {
            _log.LogError(ex, "iteration failed");
            await Task.Delay(_backoff.Next(), stoppingToken);   // don't hot-loop on failure
        }
    }
}

Follow-ups

  • Multiple instances of the service? — Every replica runs the background service, so anything that must happen once needs a distributed lease or a leader election.
  • How do you make it observable? — A heartbeat metric and a last-success timestamp; a background service that silently stops is otherwise invisible until data goes stale.
  • How do you extend the shutdown window? — HostOptions.ShutdownTimeout, and align it with the platform's termination grace period, or the orchestrator kills you first.

Common wrong answer

"Put the work in ExecuteAsync in a while-true loop with a delay." That is the skeleton, not the answer: without the try/catch, the backoff, the scope per iteration and the token checks it fails on the first transient error and either dies silently or takes the host with it.

seniorWhen is the built-in DI container not enough?

Answer

Microsoft.Extensions.DependencyInjection is deliberately minimal: constructor injection, three lifetimes, and since .NET 8 keyed services. It has no first-class decoration, no convention-based or assembly-scanning registration, no property injection, no interception, and no child containers. Most teams need none of those, and the honest answer is that you should reach for a third-party container (Autofac, Lamar) only when you have a concrete need — usually decoration at scale or interception for cross-cutting concerns — and understand that you are trading away the framework's validation, the ecosystem's assumptions and some AOT friendliness. My own preference is to stay on the built-in container and write decoration explicitly in the registration, because an explicit factory line is more readable than a convention nobody can grep for.

Example

// explicit decoration with the built-in container
services.AddSingleton<HttpGateway>();
services.AddSingleton<IPaymentGateway>(sp =>
    new RetryingGateway(
        new LoggingGateway(sp.GetRequiredService<HttpGateway>(), sp.GetRequiredService<ILogger<LoggingGateway>>()),
        sp.GetRequiredService<ResiliencePipeline>()));

// keyed services, .NET 8
var stripe = sp.GetRequiredKeyedService<IPaymentGateway>("stripe");

Follow-ups

  • Is assembly scanning a good idea? — It saves typing and costs discoverability; in a large codebase "why is this registered?" becomes an archaeology exercise.
  • What about interception/AOP? — Dynamic proxies rely on runtime code generation, which does not work under Native AOT; source generators are the modern alternative.
  • Does the container matter for performance? — Resolution cost is negligible next to any I/O; do not choose a container on benchmarks.

Common wrong answer

"Swap in Autofac, it's more powerful." Power without a stated need is complexity: you inherit different lifetime semantics, a second mental model for the team, and integration friction with every framework feature that assumes the built-in container.

principalA team is using a static ServiceLocator because constructors have too many parameters. What do you do?

Answer

I would treat the constructor size as the real signal and the locator as the wrong remedy. Ten constructor parameters is the class telling you it has ten reasons to change; the fixes are to split it along the cohesive groups, to introduce a facade for a set of collaborators that always travel together, or to move orchestration into a handler per use case. A service locator hides those dependencies instead of reducing them, breaks compile-time and startup validation, makes tests depend on global state, and turns lifetime bugs into runtime surprises. That said, I would not open with a principles lecture: I would take the worst class, split it in a pull request, and show the diff — a 12-parameter constructor becoming three focused classes is a more persuasive argument than any rule. Where a locator is genuinely unavoidable (a framework that constructs objects for you), it stays confined to one adapter with a comment saying why.

Example

// symptom
public OrderService(IOrderStore a, IPaymentGateway b, IEmailSender c, IPdfRenderer d,
    IAuditLog e, IClock f, IFeatureFlags g, IPricing h, ITaxService i, ILogger j) { }

// remedy: use-case handlers with 2-4 dependencies each
public sealed class PlaceOrderHandler(IOrderStore store, IPricing pricing, IPaymentGateway payments);
public sealed class SendInvoiceHandler(IPdfRenderer pdf, IEmailSender email, IAuditLog audit);

Follow-ups

  • How do you measure progress? — Track the distribution of constructor parameter counts over time; it is a cheap, visible proxy for coupling.
  • What if the framework forces static access? — Wrap it once in an adapter registered normally, so the rest of the code stays testable.
  • How do you get buy-in? — Pair on the first split, then let the team do the second; a rule imposed without a worked example gets reverted.

Common wrong answer

"Service locator is an anti-pattern, ban it." Correct conclusion, useless as leadership: it does not address why the team reached for it, and the ban gets worked around with static helpers instead. The question is testing whether you fix causes or symptoms.

10Performance, benchmarking and profiling

Performance questions are where senior candidates either demonstrate method or reveal folklore. Interviewers are not looking for a list of tricks; they are looking for the loop — measure, find the dominant cost, change one thing, measure again — and for the judgment to stop. Expect a "this endpoint takes 2 seconds, what do you do?" scenario, and expect follow-ups on tooling. Numbers you have personally measured are worth more here than any general claim.

midAn endpoint takes 2 seconds. Walk me through what you do.

Answer

I find where the two seconds go before changing anything. First the distribution: is it 2 seconds at p50 or only at p99, and is it all requests or one tenant — because a tail-only problem is usually contention or a cold cache, and a uniform problem is usually a query or a serial chain of calls. Then the breakdown: distributed tracing spans give me database time, downstream time and in-process time in one view; without tracing, a stopwatch around three segments answers it in ten minutes. In .NET services the top causes in my experience are, in order: an unindexed or N+1 query, serial awaits that could be concurrent, an oversized payload being serialized, thread-pool starvation from blocking, and only then actual CPU work. I fix the dominant cost, measure again, and stop when the number meets the requirement — not when the code looks optimal.

Example

p50 120 ms / p99 2,100 ms  -> tail problem, not a slow algorithm
trace: db 1,850 ms (41 spans) -> N+1: one query per line item
fix:   single query with a projection -> p99 210 ms
then:  serial calls to pricing + tax (180 + 160 ms) -> Task.WhenAll -> 190 ms
stop:  requirement was p99 < 500 ms; further work is unjustified

Follow-ups

  • What if there is no tracing? — Add it; but for one incident, a few Stopwatch segments or dotnet-trace on one instance answers it faster than guessing.
  • How do you tell CPU from waiting? — CPU time versus wall time in a profile; high wall and low CPU is I/O or contention, not algorithmic cost.
  • When is the answer "cache it"? — When the data is read far more than written and staleness is acceptable; caching an incorrect query only makes the wrong answer faster.

Common wrong answer

Jumping straight to fixes — "add a cache, use Span, make it parallel" — without a measurement. It is the single most reliable way to fail a senior performance question, because interviewers have all seen a week spent optimising the 3% that was not the problem.

midHow do you benchmark C# code correctly?

Answer

With BenchmarkDotNet, in Release, outside the debugger, with the process pinned to a realistic environment — because a hand-rolled Stopwatch loop measures the JIT warming up, the GC not yet having run, and the dead-code elimination of your unused result. BenchmarkDotNet handles warmup, multiple iterations with statistics, isolation per run, and [MemoryDiagnoser] for allocations, which is often the number that matters more than time. The traps to name are: benchmarking a value the JIT can fold away (return it or use a consumer), forgetting that the first call includes tiered JIT compilation, comparing across machines or cloud instances with noisy neighbours, and micro-benchmarking something that is 1% of the real workload. I treat a micro-benchmark as evidence about one function and a load test as evidence about the system; they answer different questions.

Example

[MemoryDiagnoser]
public class ParseBench
{
    private readonly string _input = "id=42;name=ada";

    [Benchmark(Baseline = true)]
    public int Split() => int.Parse(_input.Split(';')[0].Split('=')[1]);

    [Benchmark]
    public int Span()
    {
        ReadOnlySpan<char> s = _input;
        return int.Parse(s[3..s.IndexOf(';')]);
    }
}
// dotnet run -c Release --  (never 'dotnet run' in Debug, never under the debugger)

Follow-ups

  • Why does the first iteration differ so much? — Tiered compilation: tier-0 code runs first and is replaced by optimised code after the method gets hot; OSR handles long-running loops.
  • How many allocations is "too many"? — Whatever moves gen-0 collection frequency in production; the absolute number is meaningless without the rate.
  • What is a fair baseline? — The code you actually have today, not an idealised version, and with the same inputs including the pathological ones.

Common wrong answer

"I ran it in a loop with a Stopwatch and it was 3x faster." Almost always measuring JIT warm-up, an unrealistic constant-folded input, or a GC that happened to fire in one run. Interviewers ask this question specifically to see whether you know why that number is untrustworthy.

seniorWhat is tiered compilation and dynamic PGO, and why should you care?

Answer

The JIT compiles a method quickly at tier 0 to get the process started, counts invocations, and recompiles hot methods at tier 1 with full optimisation; on-stack replacement lets a long-running loop switch tiers mid-execution rather than staying slow forever. Dynamic PGO adds instrumentation to the tier-0 code — which types actually showed up at a call site, which branches were taken — and feeds that into the tier-1 compile, enabling guarded devirtualisation and better inlining of interface calls. It shipped off by default in .NET 6/7 and is on by default since .NET 8, worth roughly a 10-20% throughput improvement on typical server code with no source change. Why you care: it explains why the first seconds after a deployment are slower (a real effect on canary metrics), why microbenchmarks need warmup, and why ReadyToRun images still get re-jitted for the hot paths.

Example

start -> tier0 (fast to compile, instrumented) -> 30 calls -> tier1 (optimised, PGO-informed)
long loop -> OSR swaps the running frame to optimised code

Consequences you will be asked about:
  first requests after deploy are slower  -> warm up before taking traffic
  ReadyToRun cuts startup, not steady state -> both are still re-jitted when hot
  DOTNET_TieredPGO / TieredCompilation exist, but changing them needs a measurement

Follow-ups

  • Should you disable tiered compilation for a server? — Rarely; it raises startup cost for a small steady-state gain, and PGO makes tier 1 better than a non-tiered compile would be.
  • What is ReadyToRun? — Ahead-of-time precompiled code shipped in the assembly to cut startup; the JIT still re-optimises hot methods later.
  • How does this interact with canary deploys? — Compare warmed instances, or your canary looks worse purely because it is cold.

Common wrong answer

"The JIT compiles each method once, on first call." That was true in .NET Framework and it makes every explanation of warm-up, OSR and PGO impossible. It also leads to bad advice like disabling tiering to "avoid the overhead".

seniorWhere do allocations come from in a typical service, and which ones do you actually remove?

Answer

In a typical ASP.NET Core service the allocation profile is dominated by strings and serialization — JSON buffers, string concatenation and interpolation, Substring, ToLower/ToUpper, and log message formatting — followed by LINQ iterators and closures, and then per-request objects and buffers. The ones worth removing are the ones inside per-request or per-item loops and anything hitting the large object heap; the ones not worth removing are single allocations per request, where the code clarity is worth more than 200 bytes. The techniques, in the order I apply them: stop allocating in logging (use source-generated LoggerMessage so nothing is formatted when the level is disabled), use Span/slicing instead of Substring, pool large buffers, use StringBuilder or string.Create for constructed strings, and only then consider struct enumerators or manual loops.

Example

// allocates a formatted string even when Debug is disabled
_log.LogDebug($"processing {id} for {tenant}");

// source-generated: no allocation, no formatting when the level is off
[LoggerMessage(Level = LogLevel.Debug, Message = "processing {Id} for {Tenant}")]
private static partial void LogProcessing(ILogger logger, int id, string tenant);

// avoid Substring in a parser
var name = line.AsSpan(0, comma);        // no allocation

Follow-ups

  • Why is the interpolated log line so bad? — The string is built before the call, so a disabled log level still pays for it; the structured overload defers, and the source generator removes even the boxing.
  • What tool shows this? — dotnet-counters for allocation rate, then dotnet-trace/PerfView or a memory profiler for allocation call stacks by type.
  • Is zero allocation the goal? — No: the goal is a gen-0 rate that keeps GC pause time out of your latency budget.

Common wrong answer

"Convert everything to structs and spans." It produces unreadable code, defensive copies and ref struct constraints in exchange for allocations that were never on a hot path. The senior answer is the allocation profile first, then the two or three call sites that matter.

seniorWhen would you reach for SIMD or hardware intrinsics?

Answer

When there is a genuinely data-parallel loop over a large contiguous buffer — checksums, encoding and decoding, image or signal processing, bulk numeric aggregation, searching within bytes — and a profile shows it dominating. The first move is not to write intrinsics: much of the BCL is already vectorised, so span.IndexOf, SearchValues<T> (.NET 8), Enumerable.Sum on primitives (vectorised in .NET 9) and the System.Text encoders often beat hand-written code. If you still need it, use Vector<T> or Vector256<T> with a scalar fallback and an IsSupported check per instruction set, and keep the scalar version as the test oracle. The honest caveat to state in an interview: hand-written intrinsics are a maintenance liability, so they belong in a small, well-tested, well-commented function with a benchmark in the repository proving they earn their place.

Example

public static int CountZeros(ReadOnlySpan<byte> data)
{
    if (!Vector256.IsHardwareAccelerated || data.Length < Vector256<byte>.Count)
        return Scalar(data);                       // fallback AND test oracle

    var zero = Vector256<byte>.Zero;
    int count = 0, i = 0;
    for (; i <= data.Length - Vector256<byte>.Count; i += Vector256<byte>.Count)
        count += BitOperations.PopCount(Vector256.Equals(Vector256.Create(data.Slice(i)), zero)
                                        .ExtractMostSignificantBits());
    return count + Scalar(data[i..]);
}

Follow-ups

  • How much faster, realistically? — 2-8x on a genuinely vectorisable loop; nothing at all if the loop is memory-bandwidth bound or branch-heavy.
  • Portability? — Vector<T> adapts to the hardware width; fixed-width types need per-ISA paths, and arm64 has different intrinsics from x64.
  • How do you test it? — Property-based tests against the scalar implementation, including lengths around the vector boundary and the empty case.

Common wrong answer

"I'd use intrinsics to make the hot loop faster" without checking whether the BCL already vectorises it. Rewriting IndexOf by hand and losing to the framework version is a common and embarrassing outcome.

seniorHow do you tell a micro-optimisation from a real win?

Answer

By where the change lands in the end-to-end budget. A 40% improvement in a function that accounts for 2% of request time is a 0.8% win; a 20 ms saving on a 200 ms p99 in a path executed on every request is real money. So I insist on three numbers before accepting an optimisation PR: the share of the total that the target represents, the measured delta at the system level (not the micro-benchmark), and the cost in readability. There is also a cost axis that senior candidates often miss: throughput improvements convert directly into fewer instances, so "15% less CPU" has a number attached in a cloud bill, and that is the argument that gets performance work prioritised. And I actively reject optimisations that trade correctness or clarity for a delta that the load test cannot detect.

Example

Rule of thumb before merging a perf change:
  1  what fraction of the workload is this?        (profile share)
  2  what is the delta at p50 AND p99 end-to-end?  (load test, not micro-bench)
  3  what did it cost in readability/testability?
  4  is there a regression guard?                  (benchmark in CI, or an SLO alert)

Amdahl in one line: optimising a 2% component can never win more than 2%.

Follow-ups

  • How do you stop regressions? — A small benchmark suite in CI with a threshold, plus latency SLOs; without a guard the win erodes within two quarters.
  • When is readability worth losing? — When the code is small, isolated, well-tested and documented with the measurement that justified it.
  • What about premature optimisation in design? — Choosing a scalable shape early is architecture, not micro-optimisation; the distinction is whether the decision is expensive to reverse.

Common wrong answer

"Every optimisation is worth it if it's measurable." Measurable is not the same as material, and a codebase optimised uniformly is one nobody can change safely. The expected framing is the fraction of the total and the cost of the change.

principalLeadership asks for "10x throughput" on a .NET service. How do you run that?

Answer

I would first convert the request into a measurable goal and a budget, because "10x" is usually a proxy for a cost or a capacity deadline. Then establish a baseline nobody disputes: a repeatable load test with production-shaped data, recorded p50/p99, CPU and memory per instance, and cost per million requests. From there the order is architectural before micro: remove work (caching, avoiding recomputation, batching), then remove waiting (concurrency, connection pooling, eliminating blocking), then make the remaining work cheaper (allocation, serialization, query shape) — because in .NET services the first two categories almost always deliver more than the third. I would also set the exit criterion up front and be willing to report that 10x is not achievable within the architecture, with the evidence: at some point the answer is sharding, a different storage engine, or accepting a different consistency model, and saying that early is the job.

Example

Baseline   1,200 rps/instance, p99 480 ms, 3.1 GB RSS, $/1M req recorded
Phase 1    remove work      response cache + batched reads      1,200 -> 3,400 rps
Phase 2    remove waiting   fix 6 blocking calls, pool sizing   3,400 -> 7,900 rps
Phase 3    cheaper work     source-gen JSON, log allocation     7,900 -> 9,800 rps
Wall       single Postgres writer saturates at ~11k rps
           -> beyond this it is sharding or CQRS, i.e. an architecture decision
Report     9,800 rps (8x) at 1/3 the cost per request; 10x needs the write-path change

Follow-ups

  • What if the bottleneck is the database? — Then C# tuning is theatre; say so with the evidence and move the conversation to the data layer.
  • How do you protect the team from a moving target? — Freeze the load profile and the success metric in writing before starting.
  • What do you do about the risk of regressions? — Every phase ships behind a flag with the load test in CI, so a bad change is reverted in minutes.
  • How do you decide when to stop? — When the next phase costs more engineering time than the infrastructure it saves, and say that in cost terms.

Common wrong answer

Accepting the 10x target and starting with code-level optimisation. Two months later there is a faster service, an unhappy sponsor and no baseline to argue from. The lead-level move is to convert the ask into a measurable goal, and to name the architectural ceiling early.

11Testing and code-review judgment

Testing questions look procedural and are actually about design: what you mock reveals how you draw boundaries, and what you block in review reveals what you think matters. At lead level this sub-area often carries more weight than the language questions, because the interviewer is imagining you setting the bar for a team. Have a position on mocking, on flaky tests, and on what you would and would not block a pull request for.

midWhat do you mock, and what do you never mock?

Answer

I mock things I do not own and cannot run cheaply: a payment gateway, an email provider, a third-party HTTP API, the clock. I do not mock things I own and that are cheap to run — my own domain types, value objects, or an in-memory implementation of my own repository — because those tests then assert on my mock setup rather than on behaviour. Databases sit in the middle: mocking a DbContext is famously misleading because LINQ-to-objects behaves differently from LINQ-to-SQL (translation failures, null semantics, string comparison), so I use a real database in a container for repository tests. The heuristic I state in review is: if changing a private implementation detail breaks a test, the test is coupled to structure rather than behaviour, and that is a design signal about the test, not about the code.

Example

// mock the boundary you don't own
var gateway = Substitute.For<IPaymentGateway>();
gateway.ChargeAsync(Arg.Any<Money>(), Arg.Any<CancellationToken>())
       .Returns(new Receipt("r-1"));

// don't mock time - inject it (TimeProvider, .NET 8)
var time = new FakeTimeProvider(new DateTimeOffset(2026, 9, 8, 12, 0, 0, TimeSpan.Zero));
var sut = new SubscriptionService(gateway, time);
time.Advance(TimeSpan.FromDays(31));

Follow-ups

  • Why is TimeProvider better than an IClock interface? — It is the framework abstraction (.NET 8), it also fakes timers and delays, and Microsoft.Extensions.TimeProvider.Testing ships FakeTimeProvider.
  • What about the EF Core in-memory provider? — Microsoft advises against it for testing query behaviour; it does not enforce constraints or translate like a real provider. Use SQLite in-memory or a container.
  • Verify or assert? — Assert on outcomes; verifying that a method was called with exact arguments couples the test to the implementation.

Common wrong answer

"Mock every dependency so the test is a true unit test." It produces tests that pass while the system is broken, because every seam is stubbed to behave the way the author assumed. Interviewers listen for "I don't mock what I own".

midHow do you test async code, timeouts and retries?

Answer

Tests are async Task, never async void (the runner cannot observe it) and never .Result. Time is injected: TimeProvider with FakeTimeProvider lets a test advance an hour instantly, so a retry-with-backoff or a cache expiry can be asserted without a real delay — a Task.Delay in a test is both slow and flaky. Cancellation is tested by passing an already-cancelled token and asserting OperationCanceledException, and by asserting that the side effect did not happen. For concurrency, deterministic tests use a barrier or a TaskCompletionSource to force the interleaving you care about rather than hoping for it; a stress loop is a supplement, not a substitute. And every async test gets a timeout so a hang fails the build instead of stalling CI.

Example

[Fact(Timeout = 5_000)]
public async Task Retries_with_backoff_then_succeeds()
{
    var time = new FakeTimeProvider();
    var gateway = new FlakyGateway(failures: 2);
    var sut = new ResilientClient(gateway, time);

    var task = sut.SendAsync(ct);
    time.Advance(TimeSpan.FromSeconds(30));      // no real waiting
    (await task).Should().BeSuccessful();
    gateway.Attempts.Should().Be(3);
}

Follow-ups

  • How do you force a specific interleaving? — A TaskCompletionSource the test controls, or a SemaphoreSlim held until both threads are in position.
  • Should tests run in parallel? — Yes by default, which immediately exposes shared static state — a useful side effect.
  • How do you test a BackgroundService? — Call StartAsync/StopAsync directly and drive the work through a fake queue and a fake time provider.

Common wrong answer

"Add a Task.Delay(500) so the background work finishes." It is the origin of most flaky suites: it passes on a fast laptop and fails on a loaded CI agent, and the reaction is always to raise the delay rather than to remove it.

midUnit tests or integration tests — where do you spend the budget?

Answer

I want fast unit tests around logic with branches — pricing, validation, state machines — and a smaller number of integration tests that exercise the wiring, because in a typical .NET service most production bugs are in the wiring rather than in a pure function: a wrong lifetime, a mis-mapped column, a serialization setting, a missing index. With WebApplicationFactory and Testcontainers, an integration test against a real Postgres or SQL Server in Docker runs in a couple of seconds and covers the whole request path including DI, model binding, EF mapping and middleware. So my split is closer to a "testing trophy" than a strict pyramid: a broad base of cheap unit tests, a meaningful layer of integration tests at the HTTP boundary, and very few end-to-end tests, because those are slow and flaky and their maintenance cost compounds.

Example

public sealed class ApiFixture : WebApplicationFactory<Program>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _db = new PostgreSqlBuilder().Build();

    protected override void ConfigureWebHost(IWebHostBuilder b) =>
        b.UseSetting("ConnectionStrings:Db", _db.GetConnectionString());

    public Task InitializeAsync() => _db.StartAsync();
    public new Task DisposeAsync() => _db.DisposeAsync().AsTask();
}
// requires: public partial class Program { }   when using top-level statements

Follow-ups

  • How do you keep integration tests fast? — One container per test class or per assembly, a transaction or a truncate per test, and parallelism at the class level.
  • What do you assert at the HTTP boundary? — Status code, the contract shape, and the persisted state — not internal call sequences.
  • Do you test the happy path only? — No: the highest-value integration tests are the failure paths, because that is where mapping and error handling drift.

Common wrong answer

"Follow the test pyramid: 70% unit, 20% integration, 10% E2E." Reciting the ratio without a reason. The interviewer wants to know where your bugs come from and how your split reflects that; in DI-heavy .NET services, wiring bugs dominate.

seniorA test fails once every twenty CI runs. What do you do?

Answer

I treat a flaky test as a defect with a real probability of being a product bug, because a genuine race in the code and a race in the test look identical from the outside. The immediate move is to stop it polluting the signal: quarantine it — run it, record the result, but do not fail the build — with an owner and a deadline, never with a silent [Skip] that lives for two years. Then diagnose: the usual causes are shared state between parallel tests, dependence on wall-clock time or ordering, real network or filesystem access, and an actual concurrency bug in the code under test. What I refuse is the retry-until-green setting applied globally; it converts a signal into noise and guarantees a real race will ship. A single documented retry for a genuinely external dependency is a different decision, made per test.

Example

Flaky test triage
  1  quarantine (still runs, does not block) + owner + date
  2  reproduce: run it 500x locally, and 500x with the suite in parallel
  3  classify: shared state | time/ordering | external I/O | real race in the SUT
  4  fix the cause; if the cause is in the product, that is now a bug ticket
  5  delete the quarantine; a test that stays quarantined past its date is deleted
Metric: flaky rate per suite, tracked - a rising number is a rising ignore-the-build culture

Follow-ups

  • When is deleting the test right? — When it tests nothing that another test does not, and nobody will own it; a permanently red or skipped test is worse than none.
  • How do you find shared state? — Run the suite in a random order and with parallelism forced; order dependence surfaces immediately.
  • What about time-zone and culture flakiness? — Pin the culture and use DateTimeOffset plus an injected time provider; "fails only on the build agent" is usually one of those two.

Common wrong answer

"Add a retry attribute; CI is flaky anyway." It is the decision that teaches a team to ignore red builds, and it hides exactly the class of bug — a race — that is hardest to find in production.

seniorWhat makes code testable, if you cannot rewrite the codebase?

Answer

Seams. The three that unlock most legacy C# are: replace new of an external dependency with a constructor parameter (even without a container, an overloaded constructor keeps the old call sites working), replace static access to ambient state — DateTime.Now, Environment, a static config — with an injected abstraction, and extract the decision from the side effect so the logic can be tested without the I/O. I apply them opportunistically, on the file I am already changing, rather than as a refactoring project, and I write a characterisation test first when the existing behaviour is unclear: capture what it does today, then change it. The honest part of this answer is admitting that some code is best covered from the outside with an integration test until it is genuinely worth restructuring.

Example

// before: untestable - constructs its own dependency, reads the clock statically
public sealed class Expiry
{
    public bool IsExpired(Token t) => t.Issued.AddHours(1) < DateTime.UtcNow;
}

// after: two seams, no call-site churn (the old constructor still works)
public sealed class Expiry(TimeProvider? time = null)
{
    private readonly TimeProvider _time = time ?? TimeProvider.System;
    public bool IsExpired(Token t) => t.Issued.AddHours(1) < _time.GetUtcNow();
}

Follow-ups

  • What is a characterisation test? — A test that asserts current behaviour, right or wrong, so a refactor is provably behaviour-preserving.
  • Do you make members virtual to enable mocking? — Only as a last resort; it makes the member part of your contract. An interface or a delegate parameter is usually a cleaner seam.
  • Where do you start in a large legacy area? — The code that changes most often, from the version history; that is where testability pays back.

Common wrong answer

"It needs a rewrite before it can be tested." Almost never fundable, and it signals someone who cannot make progress inside constraints. Interviewers want the incremental seam technique and the discipline of a characterisation test.

principalWhat do you block a pull request for, and what do you let go?

Answer

I block for things that are expensive to reverse or that endanger production: a correctness bug, a security or data-integrity issue, a public API or database migration that cannot be rolled back, a missing test on new branching logic, blocking calls on an async path, and unbounded resource use — an unlimited fan-out, an unbounded cache, a query with no limit. I comment but do not block on style, naming, structure preferences and micro-optimisations; anything a formatter or an analyser can decide should never consume human review time, so I move that argument into the .editorconfig once. The tone matters as much as the list: I ask questions rather than issue verdicts on design, I approve with comments when the risk is low, and I pair rather than write a twelfth review comment. The metric I care about is time-to-first-review, because a slow review queue causes bigger, riskier pull requests, which is a worse problem than any of the things I would have blocked.

Example

Block                                  Comment only
  correctness / data loss                naming, structure preference
  security, secrets, injection           "I would have done it differently"
  irreversible API or schema change      micro-optimisation
  missing test on new branching logic    formatting (the formatter decides)
  .Result / .Wait() on a hot path        speculative extensibility
  unbounded fan-out, cache, or query     comment wording
Rule: anything an analyser can decide is never a review comment - encode it once.

Follow-ups

  • What if the author disagrees? — One round of discussion, then escalate to a decision (mine or the team's) with the reasoning written down; unresolved reviews rot.
  • How do you review a 2,000-line PR? — You do not: ask for it to be split, and treat the size itself as the finding.
  • How do you review someone more senior than you? — The same way, with questions; the review is about the change, and asymmetry in review is how teams lose their bar.
  • What do you look at first? — The public API and the tests; they tell you what the change means before the implementation does.

Common wrong answer

"I block anything that doesn't meet our standards." Without a distinction between reversible and irreversible, that produces a review queue where a naming preference and a data-loss bug carry the same weight — and a team that stops asking for review early.

12Runtime, JIT, AOT and deployment

These questions check whether you understand what happens after the compiler. They come up in two shapes: the mechanical one ("what happens between your source and the CPU?") and the operational one ("why is startup slow in the container?"). Native AOT and trimming have made this material more relevant, not less, because they change what your code is allowed to do — reflection-heavy patterns that worked for a decade simply stop working.

midWhat happens between your C# source and running machine code?

Answer

Roslyn compiles source to IL plus metadata in a managed assembly — a PE file that is not machine code. At runtime the host loads the assembly into an AssemblyLoadContext, resolves types through metadata, and the JIT compiles each method to native code the first time it is called, in tiers: quick tier-0 code first, then an optimised tier-1 recompile for hot methods informed by profile data. Optionally, ReadyToRun precompiles a native version ahead of time to cut startup, and Native AOT compiles the whole application to a single native binary with no JIT at all. The reason this matters in an interview is that it explains a family of real behaviours: slower first requests, why a stack trace can be inlined away, why reflection is expensive, and why AOT forbids dynamic code generation.

Example

source -> Roslyn -> IL + metadata (.dll)
      -> host + AssemblyLoadContext
      -> JIT tier0 (fast) -> tier1 (optimised, dynamic PGO on by default since .NET 8)
optional: ReadyToRun (precompiled, still re-jitted when hot)
optional: Native AOT (no JIT, no dynamic codegen, single native binary)

Follow-ups

  • What is in the metadata? — Every type, member and signature; it is what reflection, serializers and DI containers read at runtime.
  • Why can a method disappear from a stack trace? — Inlining; [MethodImpl(MethodImplOptions.NoInlining)] is the debugging escape hatch.
  • Is IL portable across platforms? — Yes, that is the point; the JIT targets the local architecture, which is why the same DLL runs on x64 and arm64.

Common wrong answer

"C# compiles to machine code like C++." It makes everything downstream — JIT warm-up, reflection, AOT trade-offs — impossible to explain, and it is a common slip from candidates who have never looked at IL.

midHow expensive is reflection, and what do you use instead?

Answer

Reflection is roughly two to three orders of magnitude slower than a direct call when done naively — GetProperty plus GetValue per item — because it resolves metadata and boxes arguments every time. The classic mitigation is to pay the cost once and cache: resolve members at startup and compile a delegate with an expression tree, or use MethodInfo.CreateDelegate, after which calls are within a small factor of direct. The modern answer is to avoid it entirely with source generators: System.Text.Json's generated context, source-generated logging, generated mappers and validators all produce ordinary compiled code at build time, which is faster, trimmable and AOT-compatible. That last point is the one that matters strategically — reflection-based libraries are what block Native AOT and aggressive trimming, so the ecosystem has been moving away from them since .NET 6.

Example

// naive: metadata lookup + boxing on every call
var value = (string)typeof(User).GetProperty("Name")!.GetValue(user)!;

// cached delegate: resolve once, call fast
private static readonly Func<User, string> GetName =
    (Func<User, string>)typeof(User).GetProperty("Name")!
        .GetGetMethod()!.CreateDelegate(typeof(Func<User, string>));

// best: no reflection at all
[JsonSerializable(typeof(User))]
internal sealed partial class AppJsonContext : JsonSerializerContext;

Follow-ups

  • Where does reflection still belong? — Startup-time work: DI registration, plugin discovery, test frameworks — anywhere the cost is paid once and no AOT constraint applies.
  • What is Reflection.Emit's status? — It works under the JIT, is unavailable under Native AOT, and is what dynamic-proxy and some ORM libraries rely on.
  • How do you find reflection in a hot path? — A CPU profile showing RuntimeType/MethodBase frames, or an allocation profile full of object[] argument arrays.

Common wrong answer

"Reflection is slow, so we never use it." Every DI container, serializer and test framework you use is built on it; the useful distinction is startup-time versus per-request, and cached delegates versus naive lookups.

seniorNative AOT: what do you gain, what do you lose, and would you use it?

Answer

You gain startup time measured in milliseconds instead of hundreds of milliseconds, a much smaller memory footprint, a single self-contained native binary with no runtime install, and no JIT warm-up. You lose dynamic code generation (Reflection.Emit, dynamic proxies, expression-tree compilation), unbounded reflection over types the trimmer cannot see, runtime plugin loading, and some libraries that depend on those — plus cross-compilation is awkward and build times go up. It fits serverless functions, CLI tools, sidecars and short-lived jobs where cold start dominates; it fits a long-running ASP.NET Core service much less, because that service amortises startup over hours and dynamic PGO makes the JIT competitive at steady state. ASP.NET Core supports AOT for minimal APIs (since .NET 8) but not for MVC, so the decision usually decides the programming model too.

Example

<PropertyGroup>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>
  <StripSymbols>true</StripSymbols>
</PropertyGroup>
<!-- Build-time warnings IL2xxx/IL3xxx name every trim- and AOT-unsafe call site;
     treat them as errors, or the failure surfaces at runtime in production. -->

Follow-ups

  • What is trimming and how does it differ? — Trimming removes unreachable IL from a managed deployment; AOT includes trimming plus native compilation. Both break on reflection the analyser cannot follow.
  • How do you make a library AOT-friendly? — Source generators instead of reflection, annotations (DynamicallyAccessedMembers) where reflection is unavoidable, and CI that builds an AOT sample.
  • Does AOT make steady-state throughput better? — Usually slightly worse than tier-1 JIT with dynamic PGO, because the AOT compiler has no runtime profile.

Common wrong answer

"AOT makes .NET faster, we should turn it on everywhere." It makes startup faster and steady state usually a little slower, and it silently breaks reflection-based code. Turning it on for a large MVC application is not even supported.

seniorFramework-dependent, self-contained, ReadyToRun, container image — how do you ship?

Answer

In a container I ship framework-dependent on the official runtime image, because the base layer is shared and patched independently of my application layer: a runtime CVE becomes a base-image bump rather than a rebuild-and-retest of every service. Self-contained is for machines I do not control or where the runtime cannot be installed; the cost is that every security patch is now my rebuild. ReadyToRun is worth adding when cold start matters — it precompiles IL to native ahead of time and typically cuts startup meaningfully, at the price of a larger image. The other decisions that actually matter operationally: non-root user, a distroless or chiselled base, an explicit invariant-globalization choice, correct memory limits so the GC sizes itself, and a health endpoint that reflects readiness rather than liveness.

Example

FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
COPY . .
RUN dotnet publish -c Release -p:PublishReadyToRun=true -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled
USER $APP_UID                       # non-root
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["./Api"]
# set container memory limits; the GC reads cgroup limits for heap sizing

Follow-ups

  • Why chiselled/distroless? — Far smaller attack surface and image size; no shell, which also means no debugging inside the container without an ephemeral sidecar.
  • How do you patch a runtime CVE across 12 services? — Rebuild on the new base tag from a shared pipeline; that is the argument for framework-dependent images.
  • Does dotnet publish build images now? — Yes, the SDK's built-in container support publishes an image without a Dockerfile, which removes a class of Dockerfile mistakes.

Common wrong answer

"Self-contained, so there are no dependencies." In a container the runtime is already a controlled dependency, and self-contained means you own every runtime patch forever — a security liability presented as simplicity.

seniorStartup takes 12 seconds. Where does the time go?

Answer

I measure the phases before guessing: process start to host built, host built to first request served, and first request to warm. The usual culprits in .NET services, in order: synchronous I/O during startup (a configuration provider, a secret store, a schema migration, a warm-up query) blocking the host; assembly loading and JIT of the startup path; DI validation and assembly scanning over many assemblies; and pulling a large image before the process even runs, which is infrastructure rather than code. Fixes follow the cause — move non-essential work behind readiness rather than into StartAsync, cache or parallelise remote configuration calls, enable ReadyToRun to remove startup JIT, and trim assembly scanning. The operational half is to distinguish liveness from readiness so the orchestrator does not kill a process that is legitimately warming up.

Example

phase                             time     fix
image pull + container start      3.1 s    smaller image, prewarm nodes
host build (config + DI)          5.4 s    two secret-store calls serialised -> parallel;
                                           assembly scanning across 40 assemblies -> explicit
first request (JIT of the path)   2.8 s    ReadyToRun; warm-up request before readiness
migrations at startup             0.7 s    move to a deploy job, not the app
readiness probe must allow the warm-up window; liveness must not.

Follow-ups

  • Should migrations run at startup? — Convenient in development, risky in production with multiple replicas racing; a separate migration step is the safer default.
  • How do you measure the phases? — Timestamps around host build and first request, plus dotnet-trace with the startup profile or the Microsoft.Extensions.Hosting event counters.
  • Does Native AOT solve it? — For a small service, dramatically; for a large one it may not be feasible, and ReadyToRun captures much of the gain.

Common wrong answer

"Startup time doesn't matter for a long-running service." It matters for deploy speed, autoscaling responsiveness, and how quickly you can roll back during an incident — a twelve-second start turns a rollback into minutes across a fleet.

principalTwo libraries need different versions of the same dependency. How do you resolve it?

Answer

First understand the failure: .NET Core and later unify to the highest version in the graph, so the usual symptom is not a load failure but a MissingMethodException at runtime when the older consumer calls something the newer version changed — which means the problem surfaces in production, not at build. My order of remedies is: check whether the newer version is genuinely binary-compatible and just pin it centrally (with a test that exercises both consumers); if not, upgrade the lagging library or replace it; if it is unmaintained, isolate it behind a process or service boundary rather than fighting the loader. Loading two versions in one process is possible with a custom AssemblyLoadContext, and I would only do it for a genuine plugin architecture — it complicates diagnostics, type identity and lifetime in ways that are not worth it for an ordinary service. Preventively: central package management, a dependency policy that says how old a transitive dependency may be, and dotnet list package --vulnerable/NuGet audit in CI.

Example

Symptom   MissingMethodException / TypeLoadException at runtime, not at build
Why       .NET unifies to the highest version in the graph; no side-by-side by default
Order     1 pin the higher version centrally + test both consumers
          2 upgrade or replace the lagging library
          3 isolate the offender behind a service or process boundary
          4 (last) a custom AssemblyLoadContext - plugin scenarios only
Prevent   Directory.Packages.props, NuGet audit in CI, a stated dependency-age policy

Follow-ups

  • What about binding redirects? — A .NET Framework mechanism; on modern .NET there are no binding redirects, unification is automatic and the failure mode is different.
  • How do you test for it? — An integration test that exercises both consumers on the unified version; build-time success proves nothing here.
  • When is vendoring the code acceptable? — For a small unmaintained dependency, with the licence checked and an owner named; it is a decision with a maintenance cost, not a shortcut.

Common wrong answer

"Use binding redirects" or "just install both versions". Neither exists on modern .NET, and offering them signals a mental model still anchored in .NET Framework — which is exactly what this question is designed to detect.

13Serialization, interop and data access

These are the seams where C# meets everything else, and they generate a specific kind of interview question: not "what is the API" but "what breaks when the other side changes". Serialization questions are near-universal in service loops; interop appears when the role touches native libraries or legacy systems; data access appears everywhere but is usually kept shallow here, since a dedicated EF Core round would go much deeper.

midSystem.Text.Json versus Newtonsoft.Json: what actually differs?

Answer

System.Text.Json is the built-in, span-based, allocation-conscious serializer and the default in ASP.NET Core since 3.0; Newtonsoft.Json is the older, more permissive, far more feature-rich library. The behavioural differences that actually break migrations are: STJ is case-sensitive by default (Newtonsoft is not), it does not serialize fields unless you ask, it is stricter about comments, trailing commas and number-as-string, it requires an attribute or a converter for polymorphism, and its default settings for nulls and enums differ — enums serialize as numbers unless you add JsonStringEnumConverter. The reason to prefer STJ is performance (roughly 1.5-3x on typical payloads, with far less allocation) and AOT/trimming support through the source generator. The reason teams stay on Newtonsoft is a feature they depend on: JsonPath, custom contract resolvers, or the permissiveness itself.

Example

var options = new JsonSerializerOptions(JsonSerializerDefaults.Web)
{
    PropertyNamingPolicy = JsonNamingPolicy.CamelCase,
    DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull,
    Converters = { new JsonStringEnumConverter() },   // enums as strings, not 3
};

// source-generated context: no reflection, trim- and AOT-safe, faster startup
[JsonSourceGenerationOptions(PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase)]
[JsonSerializable(typeof(OrderDto))]
internal sealed partial class AppJson : JsonSerializerContext;

Follow-ups

  • What is the most dangerous difference in a migration? — Case sensitivity and enum representation: both change the wire format or silently fail to bind, and neither throws in an obvious place.
  • Can you use both? — Yes, ASP.NET Core has a Newtonsoft adapter package; running two serializers in one service is a temporary migration state, not a destination.
  • How do you handle polymorphism? — [JsonDerivedType] with a discriminator (.NET 7+), or a custom converter; never a type name from the payload, which is a deserialization vulnerability.

Common wrong answer

"They're equivalent, STJ is just newer." A drop-in swap in a service with external consumers changes the wire contract — camelCase, enum numbers, missing fields — and the failures show up as null properties in someone else's system rather than as exceptions in yours.

midHow do you version a serialized contract that other teams consume?

Answer

By treating the payload as an API with the same compatibility rules as a method signature. Additive changes are safe if consumers ignore unknown fields, so I add optional properties with defaults and never repurpose an existing field's meaning. Removals and renames are breaking, so they go through a deprecation window where both are populated. For consumers I do not control, the version lives in the transport (a URL path or media type) rather than inside the payload, and I keep an explicit schema — OpenAPI, or a contract test — so a change that breaks a consumer fails my build, not their production. The two failure modes worth naming are "deserialize with strict settings and reject unknown fields" (which makes any additive change breaking for you) and enums, where adding a value breaks consumers that switch exhaustively.

Example

public sealed record OrderDto
{
    public required string Id { get; init; }
    public required decimal Total { get; init; }

    // added in v1.3: optional, defaulted, never repurposed
    public string? Currency { get; init; }

    // deprecated in v1.4: still written for one release, removed in v2
    [Obsolete("Use Currency"), JsonPropertyName("currencyCode")]
    public string? CurrencyCode { get; init; }
}

Follow-ups

  • Unknown fields: ignore or reject? — Ignore for forward compatibility; reject only where an unexpected field indicates a security-relevant mistake, and say so in the contract.
  • How do you catch a breaking change before release? — Consumer-driven contract tests, or at minimum a golden-file test asserting the exact serialized shape.
  • What about messages on a queue? — Harder: old and new messages coexist in flight, so both versions must be readable for at least the retention period.

Common wrong answer

"Add a version number to the payload and switch on it." It sounds disciplined and produces a serializer full of branching that nobody deletes; the important discipline is additive-only changes plus a deprecation window, with transport-level versioning for genuine breaks.

midEF Core: what are the three mistakes you look for in a pull request?

Answer

N+1 queries, missing AsNoTracking on read-only paths, and unbounded results. N+1 comes from enumerating a query and touching a navigation property per row; the fix is a projection or an explicit Include, and the way to see it is to log the generated SQL and count. Change tracking is the second: EF snapshots every entity it returns, which costs memory and time on large read-only queries, so a read path should either project to a DTO (which does not track at all) or use AsNoTracking. Third, any query that can return an unbounded set — no Take, no paging — is a production incident waiting for a data-growth trigger. Beyond those three I look for the query being executed where I cannot see it (a lazy navigation in a view or a serializer) and for a DbContext shared across threads, which is explicitly unsupported.

Example

// N+1: one query per order
foreach (var o in db.Orders.ToList()) Console.WriteLine(o.Customer.Name);

// one query, tracking off implicitly (projection), bounded
var page = await db.Orders
    .Where(o => o.Status == Status.Open)
    .OrderByDescending(o => o.Created)
    .Select(o => new OrderSummary(o.Id, o.Customer.Name, o.Total))
    .Take(50)
    .ToListAsync(ct);

Follow-ups

  • How do you catch N+1 automatically? — Log SQL in tests and assert the query count, or use an interceptor that fails a test exceeding a threshold.
  • When is tracking actually wanted? — When you load, mutate and save in the same unit of work; that is what it is for.
  • Compiled queries? — Worth it on very hot queries: they skip expression-tree translation per call, typically saving tens of microseconds.
  • EF or Dapper? — EF for the write model and rich graphs, hand-written SQL or Dapper for hot read paths and reporting; mixing them deliberately is normal and mature.

Common wrong answer

"EF Core is slow, we use Dapper for everything." It confuses "I never learned to see the generated SQL" with a framework property. The credible answer names the specific EF behaviours (tracking, translation, N+1) and where each tool wins.

seniorHow do you call a native library from C# today?

Answer

With [LibraryImport] and a partial method — the source-generated P/Invoke introduced in .NET 7, which produces the marshalling code at compile time instead of generating it at runtime like [DllImport]. That makes it visible, debuggable, trimmable and AOT-compatible, and it forces you to be explicit about string marshalling, which is where most interop bugs live. The things I check on any interop boundary: the calling convention and struct layout match the native header exactly, strings have an explicit encoding, buffers passed to native code are pinned or fixed for the duration, ownership of allocated memory is stated (who frees it), and every handle is wrapped in a SafeHandle so a leak or a double-free is impossible. And an exception must never cross the boundary in either direction — a callback invoked from native code has to catch everything.

Example

internal static partial class Native
{
    [LibraryImport("crypto", StringMarshalling = StringMarshalling.Utf8)]
    internal static partial int Hash(string input, Span<byte> output, out int written);
}

// handles: never a raw IntPtr
internal sealed class CryptoHandle : SafeHandleZeroOrMinusOneIsInvalid
{
    public CryptoHandle() : base(ownsHandle: true) { }
    protected override bool ReleaseHandle() => Native.Free(handle) == 0;
}

Follow-ups

  • Why is DllImport a problem for AOT? — Its marshalling stubs are generated at runtime; LibraryImport generates them at build time, so nothing dynamic is needed.
  • What is the blittable rule? — Types with identical managed and native representations need no marshalling and can be passed directly; anything else copies.
  • How do you debug a bad marshalling? — Symptoms are corrupted values or a crash in native code; check StructLayout, packing and character encoding first.

Common wrong answer

"[DllImport] with default marshalling, it just works." Defaults differ per platform for strings and booleans, and the code will work on Windows and corrupt data on Linux — plus it blocks trimming and AOT. LibraryImport with explicit marshalling is the current guidance.

seniorWhat deserialization practices do you insist on for untrusted input?

Answer

Never let the payload choose the type. That is the root of the whole vulnerability class: BinaryFormatter, and TypeNameHandling.All in Newtonsoft, allow an attacker to instantiate arbitrary types with attacker-chosen state, which has produced remote code execution repeatedly across the ecosystem. BinaryFormatter was obsoleted, then disabled by default, and removed from the runtime in .NET 9 — if a codebase still uses it, that is a migration item, not a preference. For JSON I use a closed set of types with an explicit discriminator ([JsonDerivedType]), set depth and size limits, validate after deserialization rather than trusting attributes alone, and treat every field as untrusted input for whatever it feeds. The general rule I state in review: deserialization is parsing, and parsing untrusted input into a rich object graph is where you decide how much of your process an attacker controls.

Example

// forbidden on untrusted input
// new BinaryFormatter().Deserialize(stream);       // removed in .NET 9
// JsonConvert.DeserializeObject(json, new JsonSerializerSettings
//     { TypeNameHandling = TypeNameHandling.All });  // arbitrary type instantiation

// closed polymorphism: only these types, chosen by me
[JsonPolymorphic(TypeDiscriminatorPropertyName = "kind")]
[JsonDerivedType(typeof(CardPayment), "card")]
[JsonDerivedType(typeof(TransferPayment), "transfer")]
public abstract record Payment;

var options = new JsonSerializerOptions { MaxDepth = 32 };

Follow-ups

  • What replaced BinaryFormatter? — Explicit, contract-based formats: JSON, protobuf, MessagePack — anything where the schema is yours, not the payload's.
  • Is a size limit enough? — No: a small payload can be a zip bomb or a deeply nested object; limit depth and total elements as well.
  • Where else does this class of bug appear? — XML with DTD processing enabled (XXE), YAML type tags, and any "deserialize to object" convenience API.

Common wrong answer

"We validate the input after deserializing, so it's fine." The exploit happens during deserialization — constructors, setters and callbacks run before your validation line is ever reached.

principalTwo services exchange a large object graph and it is slow. How do you approach it?

Answer

I would question the contract before optimising the serializer, because the usual finding is that the graph is large by accident: the producer is returning its internal model, so every consumer gets every field of every child. The first move is to measure the split between payload size, serialization CPU and network time — they demand different fixes. Then, in order: shrink what is sent (a purpose-built projection per consumer, paging, field selection), then change the encoding if it still matters (source-generated JSON first, then a binary format like protobuf or MessagePack with a schema), then compress, then consider streaming so the consumer starts working before the whole graph arrives. I would also name the organisational trade-off: a shared serialized model between two services is coupling with a nice name, and the fix that pays off longest is usually one contract per consumer, versioned, rather than a faster serializer for a shape nobody should be sending.

Example

Measure    4.2 MB payload · 180 ms serialize · 90 ms network · 260 ms deserialize
Shrink     consumer needs 6 of 40 fields -> projection: 4.2 MB -> 310 KB   (dominant win)
Encode     source-generated STJ: 180 ms -> 65 ms; protobuf if the contract is stable
Compress   gzip/br at the transport, not by hand
Stream     IAsyncEnumerable + chunked JSON so the consumer starts at the first item
Contract   one DTO per consumer, versioned - never the internal domain model on the wire

Follow-ups

  • When is protobuf/gRPC the right answer? — Stable, high-volume, internal service-to-service traffic where schema evolution is disciplined; not for a public API where JSON's tooling wins.
  • Does compression always help? — On big text payloads yes; on small ones the CPU and latency cost exceed the saving, and it hides the real problem.
  • How do you stop the graph regrowing? — A test asserting the serialized shape and a size budget in CI; without a guard, fields creep back within two quarters.

Common wrong answer

"Switch to protobuf, it's faster." It is, and it does not fix sending 40 fields when six are needed — you get a faster transfer of the wrong contract, plus a schema toolchain and a migration for every consumer.

14Production diagnostics and debugging

This is the sub-area that most reliably separates leads from strong seniors, because it cannot be studied — it is the residue of having been on call. Interviewers ask it as a scenario ("the service is at 100% CPU and serving nothing"), and they listen for a method: what you look at first, what you rule out, what you would have needed in place beforehand. Have two incidents ready that you can narrate in three minutes each, with the numbers.

midWhich tools do you reach for on a running .NET process, and in what order?

Answer

Counters first, because they are cheap and answer "what kind of problem is this?" in under a minute: dotnet-counters shows CPU, allocation rate, GC counts and pause time, exception rate, thread-pool queue length and lock contention. If it looks like CPU or a hot path, dotnet-trace gives a sampled profile without stopping the process. If it looks like memory, dotnet-gcdump gives a heap graph small enough to copy out of a container. If the process is hung or dying, dotnet-dump plus dotnet-dump analyze (clrstack, dumpheap -stat, syncblk, threadpool) tells me what every thread is doing. All of these are installable as global tools and can attach in a sidecar container, and the preparation that makes them usable is the part to mention: the diagnostic socket has to be reachable and the image needs the tools or an ephemeral debug container.

Example

dotnet-counters monitor -p 1 System.Runtime Microsoft.AspNetCore.Hosting
  cpu-usage · alloc-rate · gen-2-gc-count · time-in-gc · exception-count
  threadpool-queue-length · monitor-lock-contention-count · requests-per-second

dotnet-trace collect -p 1 --profile cpu-sampling      # hot paths, no stop
dotnet-gcdump collect -p 1                            # heap graph, small
dotnet-dump collect -p 1                              # full dump; analyze offline
  > clrstack -all      what every thread is doing
  > dumpheap -stat     what dominates the heap
  > syncblk            who holds which lock

Follow-ups

  • What is the cost of collecting a dump in production? — The process is frozen for the duration (seconds for a large heap); take it from one instance out of rotation.
  • How do you get a dump from a crash? — DOTNET_DbgEnableMiniDump and a writable path with a volume that survives the container.
  • What if you cannot attach at all? — Then you rely on what you instrumented: logs, metrics and traces. That is why the diagnosability question comes next.

Common wrong answer

"Attach a debugger and step through it." You cannot attach Visual Studio to a production pod, and if you could, breaking a live process during an incident is not a plan. Interviewers want the out-of-process, low-overhead toolchain.

senior100% CPU and almost no throughput. What is it?

Answer

Four candidates, and counters separate them fast. One: GC thrash — time-in-gc high, gen-2 collections frequent; the process is spending its CPU collecting, usually because of a large-object or promotion problem. Two: an infinite or spinning loop, often a corrupted non-concurrent Dictionary being read while another thread writes, which classically spins forever inside a bucket chain. Three: lock convoy or heavy contention — monitor-lock-contention-count climbing, threads busy but making no progress. Four: real work at the wrong scale — an accidental O(n squared) over a collection that grew. A trace with CPU sampling names the method within a minute or two; the important discipline is not to guess, and to take one instance out of rotation for the collection so I do not make the incident worse.

Example

time-in-gc > 30%                      -> GC thrash: allocation rate, LOH, promotions
alloc-rate normal, one method hot     -> spin/infinite loop (check Dictionary misuse)
lock-contention-count climbing        -> convoy: shrink the critical section
CPU spread across the request path    -> genuinely more work per request; check input size

Counter-example worth stating: thread-pool starvation looks like a HANG with LOW CPU,
not high CPU - queue length rises, CPU stays flat. Different problem, different fix.

Follow-ups

  • How does a Dictionary spin forever? — Concurrent writes can create a cycle in the bucket chain; a reader then walks it indefinitely at full CPU. It is the textbook argument for ConcurrentDictionary or immutability.
  • What if the profile points at the framework? — Look at the caller, not the frame: framework methods are usually where your volume shows up.
  • Mitigation before root cause? — Scale out or restart the worst instance to buy time, but capture a trace and a dump first or the evidence is gone.

Common wrong answer

"Restart the pods and add more replicas." It is a legitimate mitigation and a poor answer, because it discards the evidence. The expected sequence is capture, then mitigate, then diagnose.

seniorWhat makes logging useful rather than noisy?

Answer

Structure and correlation. Structured logging means the message template stays constant and the values are named fields (_log.LogInformation("order {OrderId} priced at {Total}", id, total)), so the backend can aggregate and filter rather than regex the text; the source-generated [LoggerMessage] form takes that further by removing allocation and formatting when the level is disabled. Correlation means every entry carries the trace id from Activity.Current, so one request can be followed across services — that is what OpenTelemetry gives for free once configured. Levels have to mean something: warnings that fire routinely train everyone to ignore them, so I audit them. And what never goes in a log: personal data, tokens, connection strings, full request bodies. The test I apply is whether the log line would let a stranger reconstruct what happened without opening the code.

Example

// allocation-free, structured, source-generated
[LoggerMessage(EventId = 42, Level = LogLevel.Warning,
    Message = "payment {PaymentId} retried {Attempt} of {Max} after {Reason}")]
public static partial void PaymentRetried(ILogger logger, string paymentId, int attempt, int max, string reason);

// correlation comes from the ambient Activity; OpenTelemetry wires it end to end
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t.AddAspNetCoreInstrumentation().AddHttpClientInstrumentation())
    .WithMetrics(m => m.AddRuntimeInstrumentation());

Follow-ups

  • Log or metric? — Metrics for anything you want to alert on or graph over time; logs for the detail of one occurrence. Counting by parsing logs is expensive and fragile.
  • What level for an expected failure? — Information or debug: a client disconnect or a validation failure is not an error, and treating it as one destroys your error-rate signal.
  • How do you keep cost down? — Sample high-volume traces, keep debug off in production but switchable per scope, and never log inside a per-item loop.

Common wrong answer

"Log everything at information level so we have it if we need it." It produces a bill, a search that times out, and a signal-to-noise ratio where the one line that mattered is unfindable. The judgment being tested is what you choose not to log.

seniorYou have a stack trace from production and it makes no sense. Now what?

Answer

I check the three things that routinely make a .NET stack trace misleading. Inlining: an optimised build removes frames, so the method you expect may be missing — [MethodImpl(NoInlining)] on a suspect method, or matching the trace against the IL, resolves it. Async: pre-.NET 5 async traces were nearly useless, and even now the frames come from the state machine, so the logical caller may not appear; the fix is correlation through the trace id rather than the stack. And throw ex somewhere in the middle, which resets the trace to that catch block — if the trace begins at a catch block, the real origin has been destroyed. Beyond that, a trace without matching symbols gives offsets rather than lines, so I make sure PDBs are published — ideally embedded or on a symbol server, with SourceLink, so a production trace maps to the exact commit.

Example

Symptom                          Cause                          Fix
frame missing between A and C    inlining                       NoInlining on B; check IL
trace starts at a catch block    'throw ex' reset it            use 'throw;' - fix the code
no async caller visible          state-machine frames only      correlate by TraceId
line numbers absent              no PDBs deployed               DebugType=embedded + SourceLink
frames in a third-party library  their code, your input         log the arguments at the boundary

Follow-ups

  • Are PDBs safe to ship? — Yes; they contain no secrets, and embedded PDBs cost image size but make every production trace readable.
  • What is SourceLink? — Metadata mapping the built assembly to the exact source commit, so a debugger or a viewer can show the code that actually ran.
  • How do you get a stack for a hang? — There is no exception, so a dump and clrstack -all: the stacks are the evidence.

Common wrong answer

"The trace must be wrong, the code can't do that." It is almost always the code plus a missing frame or a reset trace. The senior move is to name the three mechanisms that distort traces rather than to distrust the evidence.

principalHow do you make a service diagnosable before the incident?

Answer

By deciding, at design time, what questions you will need to answer at 3 a.m. and making each of them cheap. Concretely that means: OpenTelemetry traces on every inbound and outbound call so a request can be followed across services; the four service-level signals as metrics (rate, errors, duration, saturation) plus the .NET runtime counters exported continuously, not collected during the incident; structured logs with the trace id, and an ability to raise the log level for one tenant or one route without a deploy; health endpoints that distinguish liveness from readiness; and crash dumps configured to a persistent path. The rule I hold teams to is that every alert has a runbook and every runbook step is executable by someone who did not write the service — and that a new service is not "done" until you can answer "which dependency is slow right now?" from a dashboard rather than from a debugger. The failure to design for this is why so many incidents start with twenty minutes of installing tools.

Example

Design-time diagnosability checklist
  traces     inbound + outbound spans, trace id in every log line, sampling policy set
  metrics    RED per endpoint + runtime counters (GC, threadpool, exceptions) exported
  logs       structured, level switchable per scope at runtime, no PII/secrets
  health     /live (process alive) vs /ready (dependencies usable) - different meanings
  dumps      DOTNET_DbgEnableMiniDump to a persistent volume; tools available in a sidecar
  runbooks   one per alert; each step runnable by someone who did not build the service
  drill      one game day per quarter: kill a dependency and see if the signals show it

Follow-ups

  • What is the cheapest high-value addition to an existing service? — The trace id in every log line; it converts unrelated log soup into a per-request narrative.
  • How much sampling is acceptable? — Head sampling at a few percent for volume, plus tail sampling that always keeps errors and slow requests.
  • How do you know the instrumentation works? — Exercise it: a game day where you break a dependency and confirm the dashboards say which one.
  • How do you fund this work? — With incident time: measure minutes-to-diagnosis before and after; that is the number leadership responds to.

Common wrong answer

"We have logging and Application Insights, so we're covered." Tooling installed is not diagnosability. The question is whether a specific question — which dependency is slow, which tenant is affected, when did it start — can be answered in minutes, and that requires deciding the questions in advance.

15Security in C# code

Security questions in a C# loop are rarely about cryptography theory; they are about whether you write code that fails safely and whether you know which framework defaults protect you. Expect an injection question, a secrets question, and — increasingly — a supply-chain question. At lead level the follow-up is always organisational: how you make the safe path the easy path for a team of twenty.

screenerHow do you prevent SQL injection, and where does it still slip through?

Answer

Parameterise everything: the value travels separately from the statement, so it is never parsed as SQL. ORMs do this by default, which is why injection is rare in EF Core code — until someone reaches for raw SQL. The places it still slips through are worth naming precisely: FromSqlRaw/ExecuteSqlRaw with an interpolated string (the interpolated FromSql overloads parameterise, the Raw ones do not), dynamic ORDER BY or table names, which cannot be parameterised and must be validated against an allow-list, and stored procedures that build dynamic SQL internally. The same shape applies beyond SQL: command injection through Process.Start with a concatenated argument string, LDAP and XPath injection, and path traversal in file APIs — all of which are "untrusted input reaching an interpreter" with a different interpreter each time.

Example

// vulnerable
db.Database.ExecuteSqlRaw($"DELETE FROM Orders WHERE Id = {id}");

// safe: parameterised (the interpolated FromSql/ExecuteSql overloads parameterise)
db.Database.ExecuteSql($"DELETE FROM Orders WHERE Id = {id}");
cmd.CommandText = "DELETE FROM Orders WHERE Id = @id";
cmd.Parameters.Add(new SqlParameter("@id", SqlDbType.Int) { Value = id });

// cannot be parameterised - allow-list it
var column = sort switch { "created" => "Created", "total" => "Total", _ => "Id" };

Follow-ups

  • Do stored procedures prevent injection? — Only if they do not build dynamic SQL internally; a procedure concatenating its parameters is exactly as vulnerable.
  • How do you catch it in review? — Ban the Raw methods with an analyser or a banned-API list; then any use requires a deliberate suppression with a comment.
  • What about the second-order case? — Data read from your own database is still untrusted if a user wrote it; parameterise on the way out too.

Common wrong answer

"We escape the input" or "we use a regex to strip quotes". Escaping by hand fails on encoding tricks and on every dialect edge case; the entire point of parameters is that the value is never parsed as code. Interviewers treat manual escaping as a red flag.

midWhat are the cryptography rules you would enforce in a C# codebase?

Answer

Do not invent anything; use the platform primitives correctly. Randomness for anything security-relevant comes from RandomNumberGenerator, never Random. Passwords are hashed with a memory-hard or iterated KDF — ASP.NET Core Identity's hasher, or Rfc2898DeriveBytes with a current iteration count — never with a raw SHA hash. Symmetric encryption uses an authenticated mode (AesGcm), never raw AES-CBC without a MAC, and a nonce is never reused with the same key. Comparisons of secrets use CryptographicOperations.FixedTimeEquals to avoid timing leaks. Key material lives in a managed store (Key Vault, KMS, the platform secret store) with rotation, not in configuration. And obsolete algorithms — MD5, SHA-1, DES, 3DES — are banned outside of legacy interop, where they get an explicit, documented exception.

Example

// random for security
Span<byte> token = stackalloc byte[32];
RandomNumberGenerator.Fill(token);

// authenticated encryption
using var aes = new AesGcm(key, tagSizeInBytes: 16);
aes.Encrypt(nonce, plaintext, ciphertext, tag);      // nonce MUST be unique per key

// constant-time comparison
if (!CryptographicOperations.FixedTimeEquals(expectedMac, actualMac)) return Unauthorized();

Follow-ups

  • Why not Random for a token? — It is a predictable PRNG seeded from the clock; an attacker who sees a few outputs can predict the rest.
  • Why is a plain SHA-256 password hash wrong? — It is fast, so a GPU tries billions per second; you need work factor and a per-user salt.
  • What is ASP.NET Core Data Protection for? — Protecting local payloads (cookies, tokens) with key management and rotation handled for you; in a multi-instance deployment the key ring must be shared and persisted.

Common wrong answer

"We encrypt passwords with AES." Passwords must be hashed, not encrypted — encryption is reversible, which means a key compromise discloses every password. It is a small wording difference that reveals a fundamental misunderstanding.

midWhere do secrets live, and how do they get into the process?

Answer

Not in source, not in appsettings.json, and not in an environment variable that ends up in a crash dump or a log of the environment. In development, the user-secrets store keeps them off disk in the repository; in production they come from a managed secret store — Key Vault, AWS Secrets Manager, or the orchestrator's secret mechanism — through a configuration provider, so the application code still just binds an options class and never knows where the value came from. The properties I insist on are: rotation without a redeploy (which means the provider reloads and the consumer reads IOptionsMonitor), managed identity or workload identity instead of a bootstrap secret wherever the platform supports it, no secret ever written to a log or an exception message, and detection — a secret scanner in CI and on the repository history, because the real question is not whether one leaks but how fast you find out.

Example

// development
// dotnet user-secrets set "Payments:ApiKey" "..."

// production: managed identity, no bootstrap secret
builder.Configuration.AddAzureKeyVault(
    new Uri("https://kv-prod.vault.azure.net/"), new DefaultAzureCredential());

builder.Services.AddOptions<PaymentOptions>()
    .Bind(builder.Configuration.GetSection("Payments"))
    .ValidateOnStart();     // a missing secret fails the boot, loudly

Follow-ups

  • A secret was committed. What now? — Rotate first, then purge the history; the credential is compromised the moment it is pushed, regardless of whether the commit is removed.
  • Are environment variables acceptable? — Common and workable, with the caveats that child processes inherit them and diagnostic dumps can contain them.
  • How do you keep connection strings out of logs? — Redaction in the logging pipeline plus never logging the whole configuration object — a surprisingly common debug line.

Common wrong answer

"They're in an encrypted config file with the key in the app." That is obfuscation: the process must be able to decrypt, so anyone with the deployment artefact has both halves. Interviewers listen for a store the application authenticates to, not a file it carries.

seniorHow do you manage supply-chain risk in a .NET codebase?

Answer

Treat dependencies as code you did not write but are responsible for. The mechanics: central package management so there is one version per package to reason about, lock files for reproducible restores, NuGet audit — on by default since .NET 8, and extended to transitive packages in .NET 9 — failing the build on known vulnerabilities, and package source mapping so a package name cannot be resolved from an unexpected feed (which is the shape of the dependency-confusion attack). Beyond tooling: a policy on what a new dependency must have (a maintained release history, a licence we accept, an owner on our side), a preference for the BCL over a package for anything small, and a scheduled update cadence so upgrades are routine rather than emergency. The honest lead-level point is that the biggest risk is not a malicious package but an abandoned one that eventually cannot be patched.

Example

<!-- nuget.config: source mapping stops name-confusion attacks -->
<packageSourceMapping>
  <packageSource key="nuget.org"><package pattern="*" /></packageSource>
  <packageSource key="internal"><package pattern="Contoso.*" /></packageSource>
</packageSourceMapping>
<!-- csproj / Directory.Build.props -->
<NuGetAudit>true</NuGetAudit>
<NuGetAuditMode>all</NuGetAuditMode>      <!-- direct + transitive -->
<NuGetAuditLevel>moderate</NuGetAuditLevel>
<RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>

Follow-ups

  • What is dependency confusion? — An attacker publishes a public package with your internal package's name; without source mapping the restore may prefer it.
  • Do you generate an SBOM? — Increasingly required by customers and regulation; the .NET tooling can emit one during publish, and it is cheap to add.
  • What do you do about a vulnerability with no fix? — Assess exploitability in your usage, mitigate at the boundary, and set a date to replace the dependency — recorded, not remembered.

Common wrong answer

"We run Dependabot, so we're covered." Automated PRs address known CVEs in direct dependencies and do nothing about feed confusion, licence risk, abandoned packages or the transitive graph — and unattended update PRs pile up unmerged, which is worse than none.

principalA penetration test finds an IDOR: any user can read any order by changing the id. How do you respond?

Answer

The fix for this instance is a one-liner — filter the query by the authenticated principal's tenant or customer, not by the id alone — but a lead's answer is about the class, not the instance. Insecure direct object reference happens because authorisation lives in the controller while data access lives elsewhere, so anyone writing a new endpoint has to remember. So I would push the check down to where the data is fetched: a query filter that always scopes by tenant, or a repository API that cannot be called without the principal, so the insecure version does not compile. Then I would sweep every endpoint reading by id, add an integration test per resource that asserts another tenant gets 404 (not 403, which confirms existence), and put that test in the template for new endpoints. And I would report it as a data-exposure incident with a blast-radius assessment from access logs, not as a backlog item — because the question of whether it was exploited is separate from whether it is fixed.

Example

// vulnerable: id is the only filter
var order = await db.Orders.FindAsync([id], ct);

// structural fix: scoping is not optional
public sealed class TenantScopedOrders(AppDb db, ICurrentUser user)
{
    public Task<Order?> FindAsync(OrderId id, CancellationToken ct) =>
        db.Orders.SingleOrDefaultAsync(o => o.Id == id && o.TenantId == user.TenantId, ct);
}
// belt and braces: EF Core global query filter on TenantId, applied to every query

Follow-ups

  • 404 or 403? — 404 for a resource in another tenant: 403 tells the attacker the id exists, which is itself a disclosure.
  • Do opaque ids fix it? — GUIDs make guessing harder and are not authorisation; they are a mitigation, never the control.
  • How do you assess exploitation? — Access logs correlating principal and resource owner; if you cannot answer that, that gap is itself a finding.
  • How do you stop the next one? — The default-secure repository plus a test in the endpoint template, so the safe path is also the shortest path.

Common wrong answer

"Add an authorisation check to that controller action." It closes one hole and leaves the other forty endpoints to human memory. The question is testing whether you fix the class of defect and whether you treat a data exposure as an incident.

16Compiler, Roslyn and metaprogramming

Rarely asked, and a strong differentiator when it is — usually by a platform or tooling team, or as the "how deep does this person go" probe at the end of a senior loop. You are not expected to have written a compiler; you are expected to know what Roslyn is, when a source generator is the right tool, and why the ecosystem has been replacing reflection with generated code since .NET 6.

midWhat is Roslyn, and what can you do with it?

Answer

Roslyn is the C# and VB compiler, written in managed code, that exposes its own pipeline as an API: parse to a syntax tree, bind to a semantic model, then emit IL. Because that pipeline is public, everything built on it — the IDE's IntelliSense, refactorings, analysers, code fixes, source generators, and tools like the Roslyn scripting API — is using the same compiler the build uses, which is why an IDE squiggle and a build error agree. Practically, the two things a team uses it for are analysers (rules enforced at compile time with a code fix attached) and source generators (compile-time code generation). Knowing the split between the syntax tree, which is purely lexical, and the semantic model, which knows what a name actually refers to, is the detail that shows you have actually written one.

Example

source text
  -> SyntaxTree      lexical structure; every character preserved (trivia included)
  -> Compilation     references + all trees
  -> SemanticModel   what does this identifier BIND to? types, symbols, nullability
  -> emit            IL + PDB

built on the same API: analysers, code fixes, source generators, IDE refactorings,
dotnet format, and the compiler server itself.

Follow-ups

  • Why do analysers need the semantic model? — Syntax alone cannot tell Console.Write from your own Console class; binding can.
  • What is trivia? — Whitespace, comments and directives attached to tokens; it is why Roslyn can round-trip source exactly and why formatters can be written on it.
  • Is the compiler pluggable? — Only through the defined extension points (analysers, generators); you cannot change code generation itself.

Common wrong answer

"Roslyn is the .NET runtime" or "Roslyn is the JIT". It is the compiler front end that produces IL; the runtime and JIT are separate. Confusing them makes every subsequent answer about generators or AOT incoherent.

seniorWhen is a source generator the right tool, and what are its limits?

Answer

When you would otherwise use reflection at runtime for something knowable at compile time: serialization contracts, logging methods, regular expressions, interop stubs, mappers, DI registration, strongly-typed configuration. The gains are real — no runtime reflection cost, trimming and AOT compatibility, and errors at build time instead of at the first request — which is why the BCL itself now ships generators for JSON, logging, regex and P/Invoke. The limits: generators can only add code, never modify existing code; they run on every keystroke in the IDE, so a slow generator makes the whole editor slow (which is why the incremental generator API exists and why the non-incremental ISourceGenerator is deprecated); debugging them is awkward; and generated code becomes a compile-time dependency the whole team must understand. My rule is to use the ones the platform ships freely, and to write my own only when the alternative is reflection in a hot or AOT-constrained path.

Example

// generated at compile time - no runtime Regex parsing, no reflection
[GeneratedRegex(@"^\d{4}-\d{2}-\d{2}$", RegexOptions.CultureInvariant)]
private static partial Regex IsoDate();

// generated logging: no allocation when the level is disabled
[LoggerMessage(Level = LogLevel.Information, Message = "user {UserId} signed in")]
static partial void SignedIn(ILogger logger, Guid userId);

// generated JSON contract: trim- and AOT-safe
[JsonSerializable(typeof(OrderDto))] internal sealed partial class AppJson : JsonSerializerContext;

Follow-ups

  • Why "incremental"? — The API caches intermediate results so an edit that does not affect the generator's inputs costs nothing; the older model re-ran everything on every keystroke.
  • How do you test a generator? — Snapshot-test the generated source against a golden file, and compile the result to catch errors the generator produces.
  • Can a generator read files? — Yes, via AdditionalFiles (a schema, a resource); reading arbitrary paths breaks determinism and build caching.

Common wrong answer

"Source generators can rewrite my code to add logging or caching." They cannot modify existing code — that is interceptors' and IL-weaving's territory. Assuming otherwise leads to a proposal that cannot be built.

seniorWhat is an expression tree, and where do you actually meet one?

Answer

An Expression<Func<T, TResult>> is a lambda captured as data — a tree of nodes describing the operation instead of compiled IL. That is what lets a LINQ provider translate o => o.Total > 100 into SQL, and what makes IQueryable different from IEnumerable. You meet them in three places: ORM query translation, libraries that read a property path from a lambda (nameof-style APIs, validation rules, mapping configuration), and dynamic query building, where you compose predicates at runtime and then either hand them to a provider or compile them. Compiling one (.Compile()) produces a delegate through runtime code generation, which is fast to call and expensive to build — and unavailable under Native AOT, which is the modern reason to prefer a source generator where you can.

Example

// data, not code: EF Core reads this and writes SQL
Expression<Func<Order, bool>> open = o => o.Status == Status.Open;

// compose at runtime
var byTenant = (Expression<Func<Order, bool>>)(o => o.TenantId == tenant);
var both = Expression.Lambda<Func<Order, bool>>(
    Expression.AndAlso(open.Body, Expression.Invoke(byTenant, open.Parameters)),
    open.Parameters);

var predicate = both.Compile();   // runtime codegen: fast calls, not AOT-safe

Follow-ups

  • Why can EF not translate an arbitrary method? — It only understands nodes it has a mapping for; a call to your own method is opaque, which since EF Core 3.0 throws instead of silently evaluating on the client.
  • Cost of Compile()? — Milliseconds; cache the delegate, never compile per request.
  • Alternatives under AOT? — Pre-generate the code with a source generator, or hand-write the predicate.

Common wrong answer

"It's just a lambda." The distinction between a delegate (compiled code you can only invoke) and an expression tree (data you can inspect and translate) is the entire question, and it is the same distinction that explains IQueryable.

seniorWhat would you use to enforce a team convention the compiler does not know about?

Answer

A Roslyn analyser, preferably with a code fix, shipped as a package that every repository references. The value is that a convention stops being a review comment and becomes feedback in the editor within a second, at the moment the code is written — which is the only intervention that actually changes behaviour at scale. Good candidates are structural rules a human keeps missing: "no DateTime.Now, use the injected TimeProvider", "no raw SQL outside the data layer", "every public API takes a CancellationToken", "domain projects may not reference infrastructure". For dependency direction specifically, an architecture test (NetArchTest and similar) is often cheaper than an analyser. What I avoid is encoding taste — naming preferences and structure opinions — because a wall of style warnings teaches the team to ignore all warnings, including the important ones.

Example

// analyser sketch: flag DateTime.Now / DateTime.UtcNow
context.RegisterOperationAction(ctx =>
{
    var op = (IPropertyReferenceOperation)ctx.Operation;
    if (op.Property.ContainingType.Name == "DateTime" && op.Property.Name is "Now" or "UtcNow")
        ctx.ReportDiagnostic(Diagnostic.Create(Rule, op.Syntax.GetLocation()));
}, OperationKind.PropertyReference);

// cheaper alternative for dependency rules: an architecture test
Types.InAssembly(domain).Should().NotHaveDependencyOn("Contoso.Infrastructure").GetResult();

Follow-ups

  • Warning or error? — Start as a warning with a fix, promote to error once the existing violations are cleared; the reverse order stalls the build.
  • How do you distribute it? — A NuGet package referenced from Directory.Build.props, so a new repository gets the rules automatically.
  • What about the banned-API analyser? — For simple "never call this" rules, BannedSymbols.txt is far cheaper than writing an analyser.

Common wrong answer

"Write it in the wiki and enforce it in code review." Documented conventions decay and review enforcement is inconsistent by construction; the reason this question is asked is to see whether you automate a rule or relitigate it weekly.

principalA team wants to add IL weaving to inject cross-cutting concerns. Your call?

Answer

Almost always no, and the reasons are operational rather than aesthetic. Post-compile IL rewriting means the code that runs is not the code in the repository: stack traces, the debugger, coverage tools and reviewers all see something different from what a developer wrote, and diagnosing an incident becomes an exercise in decompilation. It also creates a build-time dependency on a tool that must keep pace with every C# and .NET release, and it interacts badly with trimming and AOT. The legitimate motivation — removing boilerplate for logging, retries, property-change notification — has better answers now: decorators registered in DI, source generators that add visible partial code, and the framework's own pipelines (middleware, resilience handlers, interceptors). I would ask which concern hurts, solve that one with the least magical mechanism that works, and keep the option open only for a case where nothing else can reach, with an owner and an exit plan.

Example

Concern they want woven      Better mechanism
  logging around methods       a decorator registered in DI, or [LoggerMessage] at the call site
  retry/timeout                Microsoft.Extensions.Http.Resilience / a resilience pipeline
  INotifyPropertyChanged       a source generator (visible, debuggable, steppable)
  null-argument checks         ArgumentNullException.ThrowIfNull + an analyser
  metrics                      the built-in Meter API at the boundary
Cost of weaving: stack traces and the debugger disagree with the source; a build-time

  • What about dynamic proxies at runtime? — Same class of problem plus a Native AOT block; a decorator does the job with code you can read.
  • Is there a case where you would say yes? — A large legacy codebase where inserting a cross-cutting concern by hand is genuinely infeasible, as a time-boxed measure with a plan to remove it.
  • How do you handle the team's frustration? — Take the boilerplate complaint seriously and remove it a different way; rejecting the mechanism without solving the problem just moves the argument.

Common wrong answer

"Sure, it removes boilerplate." Approving it without naming the debugging and diagnostics cost is the failure mode: the team is happy for a quarter, and then an incident arrives where the stack trace points at code that does not exist in the repository.

17Versioning and API stewardship

Asked of leads and principals, almost never of juniors, and it is where an interviewer decides whether you have owned something other people depend on. The questions are about compatibility, deprecation and dependency policy — but what is really being assessed is whether you think in terms of other teams' migration cost. Concrete examples of a breaking change you handled well (or badly) are worth more than any definition here.

seniorWhat counts as a breaking change in a .NET library?

Answer

Three categories, and confusing them is the usual mistake. Source-breaking means existing code no longer compiles — removing or renaming a member, adding an overload that creates ambiguity, adding a required member. Binary-breaking means an already-compiled assembly fails at runtime even though the source would compile — changing a method signature, turning a field into a property, adding a parameter (even with a default, because default values are baked into the call site), changing a struct's layout. Behavioural breaking means everything still compiles and links and does something different — a changed default, a different exception type, a new validation. Behavioural breaks are the most dangerous because no tool catches them and no consumer expects them. Practically: add rather than change, use optional new methods instead of new parameters, and run package validation against the shipped baseline so the build tells you which category you are in.

Example

// binary breaking even though it looks additive
public void Send(string message);
public void Send(string message, bool urgent = false);   // recompiled callers fine,
                                                         // existing binaries: MissingMethodException
// safe alternative: an overload
public void Send(string message);
public void Send(string message, bool urgent);

// behavioural break with no compiler signal at all
// v1: returns null when not found   ->   v2: throws NotFoundException

Follow-ups

  • Is adding an interface member breaking? — Yes for implementers, unless you give it a default implementation (C# 8) — which is what that feature is for.
  • Is making a class sealed breaking? — Yes, source and binary, for anyone deriving from it. Sealing later is much harder than sealing from the start.
  • How do you detect it automatically? — EnablePackageValidation with a baseline version, plus API-surface tracking files reviewed in the pull request.

Common wrong answer

"Adding an optional parameter isn't breaking, callers don't have to change." Source-compatible, binary-breaking: the default is compiled into the caller, so an assembly built against the old signature throws at runtime. It is the single most common accidental break in .NET libraries.

seniorHow do you version a shared library that 40 teams consume?

Answer

Semantic versioning enforced by a tool rather than by intention, plus a support policy that says how long each major is maintained. Patches for fixes, minors for additive changes, majors only for breaks — and majors are rare and scheduled, because 40 teams each paying a migration cost is a real organisational expense. I would publish previews for a major so early adopters can find problems, keep the previous major on security fixes for a stated window, and provide a migration guide with mechanical steps — ideally an analyser or a code fix that performs the rename. The other half is discovery: consumers must be able to find out that a version is deprecated without reading an email, so deprecation goes into the package metadata and into build warnings via [Obsolete]. And I would keep a list of who consumes what, because "we do not know who uses this" makes every version decision guesswork.

Example

1.4.2 -> 1.5.0   additive: new method, new optional behaviour behind a flag
1.5.0 -> 1.5.1   fix: no API change
1.5.x -> 2.0.0   break: scheduled, previewed, migration guide + analyser fixer
Support          N supported; N-1 security fixes for 6 months; N-2 unsupported
Signal           [Obsolete("Use X; removed in 3.0")] -> warning in 2.x, error in 2.9
Inventory        a query over the internal feed: who references which version

Follow-ups

  • What about a security fix in an unsupported version? — Decide the policy in advance; ad-hoc backports become permanent obligations.
  • Should consumers use version ranges? — Floating ranges make builds non-reproducible; pin with central package management and update deliberately.
  • How do you make a major upgrade cheap? — Ship the fixer, do the first three migrations yourself, and publish the diff as the template.

Common wrong answer

"We bump the major version whenever it feels like a big change." Version numbers that do not encode compatibility are worse than none: consumers cannot automate upgrades, so they stop upgrading, and you end up supporting six versions.

seniorWhen do you multi-target, and what does #if cost?

Answer

Multi-target when you genuinely have consumers on different runtimes — the common case is netstandard2.0 for remaining .NET Framework consumers alongside the current .NET — or when you want to use a newer API on newer targets while keeping a fallback. The cost is real: every target multiplies build and test time, #if blocks are code paths that only one CI job compiles, and the conditional code is where bugs hide because it is the least exercised. So the rules I apply are: keep conditional code to the smallest possible surface, ideally one partial class or one file per target rather than #if scattered through logic; run the test suite on every target, not just the newest; and treat each extra target as a support obligation with an end date, because "we still ship netstandard2.0" is a decision that should expire rather than persist by inertia.

Example

<TargetFrameworks>netstandard2.0;net10.0</TargetFrameworks>
public static bool TryParseIso(string s, out DateOnly value)
{
#if NET10_0_OR_GREATER
    return DateOnly.TryParseExact(s, "yyyy-MM-dd", CultureInfo.InvariantCulture,
                                  DateTimeStyles.None, out value);
#else
    // fallback for netstandard2.0 - tested by its own CI job, not assumed
    value = default;
    if (!DateTime.TryParseExact(s, "yyyy-MM-dd", CultureInfo.InvariantCulture,
                                DateTimeStyles.None, out var dt)) return false;
    value = DateOnly.FromDateTime(dt);
    return true;
#endif
}

Follow-ups

  • Is netstandard2.0 still relevant? — Only for .NET Framework consumers; for anything on modern .NET it is a constraint that costs you newer APIs for no benefit.
  • How do you test all targets? — A test project multi-targeting the same set, run per target in CI; otherwise the fallback path is untested by construction.
  • What about [SupportedOSPlatform]? — For platform-specific APIs the analyser enforces guards, which is the same idea applied to operating systems rather than frameworks.

Common wrong answer

"Multi-target everything, it's free." It multiplies the build matrix and creates untested code paths; more subtly, it prevents the library from adopting modern APIs because the lowest target defines the vocabulary of the whole codebase.

principalHow do you deprecate an API that half the company depends on?

Answer

With a plan that treats consumers' time as the scarce resource. First measure: who actually calls it, how often, and which call sites are mechanical versus genuinely hard — usage data beats a survey. Then provide the replacement before announcing the deprecation, with a migration guide, and where possible an automated fixer so most call sites are a one-command change. Then a staged signal: [Obsolete] as a warning with the replacement named and a removal version stated, promoted to an error one release later, removed only after the announced date. Throughout, I would keep an owner for the migration and publish progress — "31 of 40 teams migrated" — because a deprecation with no visible progress silently stalls. And I would be willing to extend the date once with a reason, but never to remove the API without warning, because the trust cost of a surprise break exceeds the maintenance cost of the old path.

Example

T-0    replacement shipped + migration guide + analyser fixer; nothing deprecated yet
T+1    [Obsolete("Use OrderClient.SendAsync. Removed in 4.0.")] as a WARNING
       dashboard: consumers still on the old API, by team
T+2    the three hardest consumers migrated by us, as the reference PRs
T+3    warning -> error (still buildable with an explicit suppression)
T+4    removed in the next major; previous major keeps security fixes for 6 months
Never  a silent removal, or a deprecation with no replacement available yet

Follow-ups

  • What if a team refuses to migrate? — Find out why: usually the replacement is missing a capability, which is your bug, not their obstinacy.
  • How do you handle a security-driven deprecation? — The timeline compresses and the communication changes, but the sequence — replacement first, then signal, then removal — does not.
  • How do you measure success? — Call sites remaining and support requests, not the number of announcements sent.
  • What about internal APIs with no versioning? — Same discipline, cheaper mechanics: an analyser warning and a dashboard beat an email thread.

Common wrong answer

"Mark it [Obsolete] and remove it in the next major." That is the mechanism, not the plan: without a replacement, a fixer, usage data and progress tracking, the deadline arrives with half the company unmigrated and you extend it anyway — having spent the credibility for nothing.

principalHow do you decide whether to take a dependency or write it yourself?

Answer

I weigh the cost of the dependency against the cost of the code, and both are long-lived. A dependency brings maintenance you do not pay for, edge cases you have not thought of, and usually better testing than you would write — but it also brings a version constraint, a security surface, a licence, and an upgrade obligation forever, plus the risk of abandonment. So my heuristics are: prefer the BCL, which is maintained for the life of the platform; take a well-maintained dependency for anything genuinely hard (cryptography, parsing, resilience, serialization) because writing those yourself is how vulnerabilities are born; and write it yourself when it is small, when the library would need heavy configuration to fit, or when it is core to your product's differentiation. The tie-breaker I use in practice is the exit cost: if replacing it later means touching one adapter, take the dependency; if it means touching 300 files, think much harder — and wrap it either way.

Example

Take it            HTTP resilience, cryptography, serialization, date/time parsing,
                   database drivers, OpenTelemetry - hard, well-tested, maintained
Write it           a 40-line helper, anything needing 200 lines of configuration to fit,
                   anything that IS the product
Check before       release cadence · open issues · licence · transitive graph size ·
                   who maintains it · does it work under trimming/AOT
Always             wrap third-party types at the boundary so the exit cost is one adapter
Red flag           a package with one maintainer, last release 3 years ago, 40 dependencies

Follow-ups

  • What about a package that is one method? — Copy the method with attribution and the licence checked; a dependency edge is rarely worth 20 lines.
  • How do you handle an abandoned dependency you already have? — Fork or vendor it as a bridge, with an owner and a date to replace it; both without an owner is how it becomes permanent.
  • Does wrapping always pay off? — Not always; wrap at the boundary where substitution is plausible, not around every type, or you write an abstraction layer nobody wanted.

Common wrong answer

"Don't reinvent the wheel — always use a library." Applied uniformly it produces a service with 200 transitive packages, an unpatchable graph and a build that breaks weekly. The judgment being tested is the exit cost, not a preference.

18Judgment calls

These have no single right answer, and that is why they are asked. They arrive as "what would you do if…", as a challenge to something you just said, or as a staged disagreement to see whether you hold a position under pressure. The hidden part of each block says what a strong answer demonstrates at the top of the IC ladder and which trade-offs a principal candidate names without being prompted. Practise saying each of these out loud in ninety seconds, ending with the condition that would change your mind.

seniorIt is September 2026. Do you move the fleet to .NET 10 now, or wait for .NET 11 in November?

What a strong answer demonstrates

That you know the support calendar and treat it as the constraint rather than chasing the newest release. .NET 8 and .NET 9 both lose support on 2026-11-10, so waiting is not neutral — it means running unsupported for however long the migration takes. .NET 10 is LTS with a three-year window; .NET 11 is STS with 24 months and arrives the same month as the deadline, which means adopting it would put the fleet on a release with no production mileage, in the same weeks as the cutoff. The strong answer moves to .NET 10 now and revisits .NET 11 for services that need a specific feature (runtime-async improvements, C# 15 unions) once it has been out a quarter. It also separates the SDK upgrade from the target-framework upgrade, and names a pilot service with a measured baseline rather than a fleet-wide flag day.

Trade-offs to name unprompted

  • LTS versus STS is a cadence decision for the organisation, not a per-service preference — mixing both doubles the upgrade calendar.
  • The real cost of an upgrade is regression risk in behavioural changes (GC defaults, serialization, analyser promotions), not the version bump.
  • Every quarter of delay compounds: the jump gets bigger and the pool of people who remember the old code shrinks.
  • A team on the newest STS gains features and pays an upgrade every 12 months; say which trade the organisation is choosing.
  • The reversal trigger: a hard dependency that has no .NET 10 build is a reason to sequence differently, not to stay on .NET 8.
seniorWould you enable nullable reference types on a 500,000-line legacy codebase?

What a strong answer demonstrates

That you can convert a large, uncomfortable change into a gradient. Enabling it repository-wide produces tens of thousands of warnings, and the two failure modes are predictable: the team turns it off, or someone bulk-inserts ! and the annotations become lies, which is worse than not having them. The strong answer enables the feature at the project level with warnings not-as-errors, then adopts file by file or project by project, starting where nulls actually cause incidents — the domain core and the boundaries that deserialize external input — and requires new files to be clean. It also names what the feature does not do: nothing at runtime, no protection across assemblies, reflection or JSON, so boundary validation stays. The strongest version ties it to evidence: how many production NREs there were last quarter, and whether that number moves.

Trade-offs to name unprompted

  • Annotation debt versus real safety: an annotated codebase full of ! is more dangerous than an unannotated one, because people trust it.
  • Churn versus blame history — a mass annotation commit destroys git blame for a whole area.
  • The compiler's null analysis is only as good as your dependencies' annotations; unannotated packages are silent holes.
  • Opportunity cost: this competes with feature work, so it needs a defensible size and an incident-based justification.
  • Reversal trigger: if warnings stay flat for two months, the gradient is not working and the scope needs narrowing.
seniorYour codebase uses a convention-based object mapper everywhere. Keep it or remove it?

What a strong answer demonstrates

That you can evaluate a popular tool on its actual costs rather than on taste. Convention-based mapping saves typing and moves errors from compile time to runtime: a renamed property silently stops mapping, the mapping is invisible in the IDE's find-references, profiles get configured in one place and consumed in fifty, and reflection-based implementations complicate trimming and AOT. The counter-argument is real too: hand-written mapping of a 60-property DTO is tedious and gets out of sync in its own way. The strong answer distinguishes cases: keep it for large, stable, flat DTO-to-DTO mapping where the profile is tested; write mapping by hand — or generate it with a source generator — at boundaries where correctness matters, such as domain to persistence. And whichever way it goes, it must be tested: a test asserting that every destination property is populated is what makes either choice safe.

Trade-offs to name unprompted

  • Compile-time errors versus runtime surprises — the single biggest difference between generated/handwritten and reflective mapping.
  • Discoverability: hand-written mapping is greppable and steppable; a convention is neither.
  • Migration cost is proportional to usage; removing it from 400 call sites is a project, so scope it to new code first.
  • AOT and trimming compatibility, if that is on the roadmap at all.
  • Team familiarity is a legitimate factor: a tool everyone knows has lower defect rates than a bespoke replacement nobody has learned.
seniorShould all your services move to Native AOT?

What a strong answer demonstrates

That you match a deployment model to a workload rather than adopting it as a badge. AOT wins where cold start and footprint dominate — serverless functions, CLI tools, sidecars, short-lived jobs, and high-density deployments where memory per instance is the cost driver. It loses where the process runs for hours, because dynamic PGO makes tier-1 JIT competitive or better at steady state, and where the codebase depends on reflection, dynamic proxies, expression compilation or MVC, none of which survive the transition. The strong answer picks one candidate service, measures startup, RSS and throughput before and after, and reports the numbers; it also names the engineering tax — trim warnings become build errors, some libraries have to be replaced, and the build gets slower — so the decision is made with the cost visible.

Trade-offs to name unprompted

  • Startup and memory versus steady-state throughput — they pull in opposite directions and only one of them is usually the constraint.
  • Ecosystem tax: every reflection-based dependency becomes a migration item, and some have no AOT-ready alternative.
  • Diagnostics change: no JIT means some profilers and dynamic instrumentation behave differently.
  • Build and CI time increase, and cross-compilation for another architecture is awkward.
  • Reversal trigger: if the measured cold-start saving does not change a cost or a latency SLO, there is no case.
seniorA team proposes banning LINQ and all allocations in application code "for performance". Your response?

What a strong answer demonstrates

That you separate a real constraint from a cargo-culted rule, and that you can say no without dismissing the concern. In a hot path — a parser, a serializer, a per-item loop running millions of times a second — the rule is defensible and the code that results is worth the readability cost. In ordinary request-handling code the same rule costs clarity everywhere to save microseconds on a path dominated by a database round trip. The strong answer asks for the profile that motivated it, agrees a scope (specific projects or namespaces where the rule applies, enforced by an analyser rather than by review), and asks for a benchmark in CI so the constraint is measured rather than believed. It also names the cultural risk: a blanket ban teaches a team that performance is a style rule, which is exactly the belief that produces optimisation in the wrong places.

Trade-offs to name unprompted

  • Readability and defect rate versus microseconds — most application code is bound by I/O, not by iterators.
  • Scoping a rule to a project or namespace is cheap; applying it globally is a permanent tax.
  • Enforcement mechanism matters: an analyser is a rule, a review comment is an argument.
  • The BCL keeps getting faster (SIMD in LINQ operators since .NET 9), so a rule written in 2021 may already be obsolete.
  • Reversal trigger: no benchmark and no profile means the rule has no evidence, and rules without evidence get relitigated forever.
principalA .NET Framework 4.8 monolith needs to move to modern .NET. Rewrite or strangle?

What a strong answer demonstrates

That you know why rewrites fail and can still name the case where one is right. The default is incremental: run the old and new systems side by side behind a routing layer, move one bounded capability at a time, share the database initially even though that is ugly, and keep shipping features throughout — because a team that cannot ship for a year loses the political capital to finish. The tools that make this concrete matter: the upgrade assistant, multi-targeting shared libraries to netstandard2.0, and moving off the Framework-only dependencies (System.Web, WCF server, WebForms, AppDomains, remoting) one at a time, because those are the actual blockers rather than the language. A rewrite is justifiable only when the old system cannot be decomposed at all and is small enough to rebuild in a quarter or two — and even then with a plan for the data migration, which is usually the harder half.

Trade-offs to name unprompted

  • Two systems in production for a long period: double the operational surface, and a routing layer that must be maintained.
  • Shared database as a transitional coupling — pragmatic, and it must have an end date or it becomes the architecture.
  • Feature freeze is the hidden cost of a rewrite, and it is usually what kills it politically.
  • Framework-only dependencies decide the sequence; find them first, because they set the critical path.
  • Knowledge risk: the people who understand the old behaviour are the scarcest resource, and a rewrite discards their tests.
  • Reversal trigger: if the first strangled capability takes three times the estimate, the decomposition boundary is wrong — stop and re-cut it.
principalWould you adopt C# 15 union types now, in preview, for a new domain model?

What a strong answer demonstrates

Discipline about preview features, plus enough knowledge to say what you would do instead. Unions and the closed modifier are genuinely the right shape for modelling a fixed set of cases with exhaustive matching, and they land with .NET 11 in November 2026 — but parts of the union specification are still unimplemented and previews carry breaking changes, so shipping production code on them means signing up for churn. The strong answer designs the model as a closed hierarchy of records with a switch expression today (which is the same shape, checked by a warning rather than by the compiler's exhaustiveness rule), keeps the pattern-matching code isolated so the migration is mechanical, and revisits after the release. It also distinguishes contexts: a preview feature in an internal tool or a spike is a cheap way to build knowledge; in a service other teams depend on it is a liability.

Trade-offs to name unprompted

  • Preview features change: a breaking change in the language costs a migration on someone else's schedule.
  • Tooling lags — analysers, formatters and IDE support are not complete during preview.
  • Hiring and onboarding: preview syntax in production code is unfamiliar to everyone joining.
  • The design value is available today (closed hierarchy plus exhaustive switch); only the compiler guarantee is missing.
  • Reversal trigger: if the team needs the exhaustiveness guarantee badly enough to accept churn, that is a real reason — but say it out loud.
principalSix teams, six coding styles. How much do you standardise?

What a strong answer demonstrates

That you distinguish decisions that must be uniform from decisions that only need to be consistent locally. Formatting, analyser severities, target framework, package versions, logging and telemetry conventions, and error-response shape should be organisation-wide, because they affect people moving between codebases and they affect operability — and they should be encoded in a shared Directory.Build.props and .editorconfig, not in a wiki. Architecture within a service, library choices that do not leak, and test style can be local, because the cost of divergence is contained and the cost of enforcing uniformity is autonomy. The strong answer also names the mechanism: a shared build package that teams inherit by default with an escape hatch that requires a written reason, plus a small cross-team group that owns changes to it — because standards without an owner drift, and standards without an escape hatch get forked.

Trade-offs to name unprompted

  • Mobility and reviewability versus team autonomy and local optimisation.
  • Enforcement must be automated; anything requiring human vigilance decays within a quarter.
  • An escape hatch with a documented reason keeps the standard alive; no escape hatch produces silent forks.
  • Standardising too much makes the standard the bottleneck for every experiment.
  • Migration cost of a new standard falls on teams who did not choose it — budget it, or it becomes permanent debt.
principalA respected senior engineer submits a PR built on heavy reflection and dynamic. What do you do?

What a strong answer demonstrates

That you separate the technical objection from the social situation, and that you argue with evidence rather than authority. The technical case is concrete: dynamic defers binding to runtime, so refactoring and IntelliSense stop working, errors move from build to production, calls are one to two orders of magnitude slower, and neither dynamic nor unbounded reflection survives trimming or Native AOT — which may already be on the roadmap. The strong answer asks what problem it solves first, because there is often a real one (an unstable external schema, a plugin surface), then offers the modern alternative — a source generator, JsonNode, an interface plus a factory — and if the disagreement persists, prototypes the alternative rather than escalating. The failure mode to avoid is winning the argument by seniority: a decision the author does not believe in produces a codebase they will not maintain.

Trade-offs to name unprompted

  • Flexibility now versus refactorability and compile-time safety for the next five years.
  • Performance is usually the weakest argument; correctness, tooling and AOT compatibility are the strong ones.
  • There are legitimate uses — COM interop, genuinely dynamic external schemas — so the answer is a boundary, not a ban.
  • Team dynamics: how a disagreement with a senior person is handled sets the norm for everyone junior watching.
  • Reversal trigger: if the alternative prototype is materially worse, accept it and record why, contained behind one interface.
principalIs it worth converting a large synchronous codebase to async?

What a strong answer demonstrates

That you can quantify the benefit rather than assume it. Async pays when the workload is I/O-bound and concurrency is limited by threads — a service holding hundreds of concurrent requests, each waiting on a database or an HTTP call — and the symptom that proves it is thread-pool starvation: queue length rising while CPU stays flat. It pays nothing for CPU-bound work, for a batch job with one thread of control, or for a desktop tool where the only benefit is UI responsiveness you may already have. The conversion cost is not small: async is viral through the call stack, half-converted code produces sync-over-async deadlocks and starvation, and every signature change is a breaking change for a library. So the strong answer converts vertically — one complete path from entry point to I/O at a time, never a layer at a time — measures throughput per instance before and after, and bans .Result with an analyser so the boundary cannot leak.

Trade-offs to name unprompted

  • Async is viral: partial conversion is worse than none, because sync-over-async is the failure mode.
  • The benefit is concurrency per instance, which converts into cost — fewer instances — not into lower latency per request.
  • Signature changes break library consumers; a public API conversion needs a versioning plan.
  • Debuggability and stack traces are marginally worse; the team pays a small ongoing tax.
  • Reversal trigger: if the load test shows the bottleneck is the database connection pool, converting the C# changes nothing — fix the pool.

Exercise A — A high-throughput ingestion service in C#

Prompt

"Design a .NET service that accepts 50,000 telemetry events per second over HTTP, validates them, and writes them to a store. Events are small (about 400 bytes of JSON). Bursts reach three times the average for a few minutes. Losing an occasional event is acceptable; stalling the producers is not. Show me the C#: what types, what threading model, what you would measure."

Clarifying questions to ask

  • Durability — May we acknowledge before the write is durable? "Losing an occasional event is acceptable" implies yes; confirm it, because it decides the whole shape.
  • Ordering — Global, per producer, or none? Per-key ordering forces partitioning; none allows free parallelism.
  • Validation — Schema-only, or does it need a lookup? A per-event database call caps throughput long before C# does.
  • Backpressure policy — When the store is slow, do we block producers, shed load, or buffer to disk? This is a product decision.
  • Store — Batch-friendly (columnar, append log) or row-at-a-time? Batch size is the single biggest throughput lever.

Solution outline

Shape: minimal API endpoint -> bounded Channel -> N batching writers -> store

Ingress (must never allocate more than it has to)
  minimal API, source-generated System.Text.Json context (no reflection)
  read the body as a ReadOnlySequence/Span; validate with Utf8JsonReader - no DTO

  reject early with 400 + ProblemDetails; count rejects as a metric, do not log each one

  accumulate into a batch of ~1,000 or 200 ms, whichever first, then one bulk write
  ArrayPool<byte> buffers; no per-event allocation on the write path

  no locks on the hot path: the channel is the synchronisation
  Server GC + DATAS; watch time-in-gc and alloc-rate, keep events out of the LOH
  CancellationToken threaded from the host; shutdown = complete writer, drain, flush

  drop rate, alloc-rate, time-in-gc, threadpool queue length

Trade-offs to name unprompted

  • Acknowledge-before-durable — buys latency and throughput, costs events on a crash; it is only acceptable because the prompt said so, and I would state the loss window in seconds.
  • Bounded channel with a drop policy versus backpressure — dropping protects the producers and the process; blocking protects the data. Choosing silently is the mistake.
  • Batching — the biggest single throughput lever and the biggest latency cost; the batch size and timeout are the two tuning knobs and both belong in configuration.
  • In-memory queue versus a durable broker — a channel is fast and loses everything on restart; if the requirement changes to no-loss, the channel becomes Kafka or a persistent queue, and the code shape barely changes.
  • Parsing without materialising a DTO — measurably cheaper at this rate, harder to read; justified here, not in ordinary handlers.
  • Per-key ordering — if it is required, partition the channel by key hash rather than adding locks, and accept that one hot key limits throughput.

Prompt

"Every team here wraps their HTTP calls in slightly different retry and timeout code. Design the C# API for a shared library that standardises it. You own the package; forty teams will consume it. Show me the types, the configuration surface, and how you would version it."

Clarifying questions to ask

  • Governance — Can we mandate adoption, or must it win on merit? That decides how much migration tooling is needed.

  defaults change ONLY in a major (a changed default is a behavioural break)
  ship 1.0 to three pilot teams, gather usage, then announce
  migration: an analyser that flags hand-rolled retry loops and points at the package
  deprecation: [Obsolete] with the replacement named and a removal version

Trade-offs to name unprompted

  • Opinionated defaults versus flexibility — the value of the library is the defaults; every option added is a decision forty teams now have to make.
  • Retrying non-idempotent requests is off by default — a retried POST without an idempotency key duplicates money; the option exists but the caller has to ask for it.
  • Wrapping the platform rather than reimplementing — less code to own, and you inherit its fixes; the cost is that its breaking changes become yours.
  • Timeout composition — per-attempt versus total timeout is the detail most hand-rolled implementations get wrong, and it must be explicit in the API.
  • Retry storms — retries at two layers multiply; the library should be the only layer, and that has to be documented and observable.
  • Sealed and minimal — a small surface is what lets you keep the promise for five years; every public virtual is permanent.

Exercise C — Model a seat reservation domain in C#

Prompt

"Design the C# domain model and persistence approach for seat reservations: a user holds seats for ten minutes, then either pays or the hold expires. Peak is a few thousand concurrent users fighting over the same popular event. No seat may ever be sold twice. Show me the types and where the concurrency is handled."

Clarifying questions to ask

  • Correctness bar — Is double-selling a hard failure, or acceptable with a compensation flow? Almost always hard here; confirm it.
  • Hold semantics — Does the ten minutes start at selection or at checkout, and can it be extended? It changes the state machine.
  • Scale shape — Contention on one event, or spread over many? One hot event is a different problem from many cold ones.
  • Adjacency — Must seats be contiguous? That turns selection into a search problem, not a lookup.
  • Deployment — Multiple instances? Then in-process locking is not a mechanism, and saying so early scores.

Solution outline

// Types: make illegal states unrepresentable; the state machine is explicit.
public readonly record struct SeatId(int Row, int Number);
public readonly record struct HoldId(Guid Value);

public abstract record SeatState;                       // C# 15: 'closed record' makes
public sealed record Available : SeatState;             // the switch exhaustive
public sealed record Held(HoldId Hold, DateTimeOffset Expires) : SeatState;
public sealed record Sold(OrderId Order) : SeatState;

public sealed class Seat
{
    public SeatId Id { get; }
    public SeatState State { get; private set; }
    public uint Version { get; private set; }           // optimistic concurrency token

    public Result Hold(HoldId hold, DateTimeOffset now, TimeSpan duration) => State switch
    {
        Available                          => Ok(State = new Held(hold, now + duration)),
        Held h when h.Expires <= now       => Ok(State = new Held(hold, now + duration)),
        Held                               => Fail("seat is held"),
        Sold                               => Fail("seat is sold"),
        _                                  => Fail("unknown state"),
    };
}
Where the concurrency actually lives: the DATABASE, not the C# process
  seats table: (EventId, Row, Number) PRIMARY KEY, State, HoldId, ExpiresAt, Version
  hold  = conditional UPDATE:
          UPDATE Seats SET State='Held', HoldId=@h, ExpiresAt=@e, Version=Version+1
          WHERE EventId=@ev AND Row=@r AND Number=@n
            AND (State='Available' OR (State='Held' AND ExpiresAt <= @now))
            AND Version=@expected
          0 rows affected  => someone else won; return "seat taken", do not retry blindly
  sell  = UPDATE ... WHERE State='Held' AND HoldId=@h AND ExpiresAt > @now
  EF Core: [Timestamp]/rowversion + DbUpdateConcurrencyException -> reload and re-decide

Expiry: no background sweeper as the source of truth - expiry is evaluated in the
  predicate above, so a lapsed hold is reclaimed by the next writer. A sweeper only
  tidies up for reporting, and it is idempotent.

Hot event: seats are independent rows, so contention is per seat, not per event.
  Suggest-and-claim UX (offer 3 candidate seats, claim one) reduces collisions.
  TimeProvider injected everywhere so the ten minutes is testable without waiting.

Trade-offs to name unprompted

  • Atomicity belongs where all writers meet — a C# lock protects one process; with two pods it protects nothing. The conditional UPDATE is the real mechanism.
  • Optimistic over pessimistic — row locks held across a user's thinking time would serialise the event; optimistic concurrency with a clear "seat taken" response is the right trade at this contention level.
  • Expiry as a predicate, not a job — a sweeper as the source of truth creates a window where a seat is both expired and not yet reclaimed; evaluating it in the WHERE clause removes the race entirely.
  • Closed state hierarchy plus exhaustive switch — adding a state (Reserved for staff, Blocked) becomes a compile error at every decision point rather than a silent fallthrough.
  • Injected TimeProvider — ten-minute expiry is otherwise untestable except by waiting, which is how flaky suites are born.
  • UX as a concurrency control — suggesting seats rather than showing a map that everyone clicks at once reduces collisions more cheaply than any code change.
  • Idempotency at the payment step — the sell must be safe to retry, because the client will retry it.

20Night-before cheat sheet

The ten questions this bank's map says you are most likely to be asked, each with the one sentence that has to come out first. If you can say these ten cleanly and then go one level deeper on any of them, you will not be caught flat in the opening twenty minutes of a loop.

  1. Value type or reference type — what actually differs? A value variable holds the data and copies on assignment, a reference variable holds a pointer to a heap object; storage location follows the container, so a struct field of a class lives on the heap, and "stack versus heap" is the wrong model.
  2. What does await do? It returns control to the caller and registers a continuation, freeing the thread — no thread is consumed while I/O is in flight — and it runs synchronously with no suspension at all when the awaited task is already complete.
  3. Why is .Result dangerous? It deadlocks wherever a single-threaded synchronization context exists, and on ASP.NET Core it converts an I/O wait into a held pool thread, which is the classic "service hangs at peak with 5% CPU" outage.
  4. How does the GC work? Generational mark-sweep-compact: gen 0 is collected often and cheaply because cost is proportional to survivors, gen 2 is the expensive full collection, and objects of 85,000 bytes or more go on the large object heap, which is not compacted by default.
  5. How do you leak memory in .NET? By keeping things reachable — unsubscribed events, unbounded static caches, closures capturing this, timers, and scoped services captured by a singleton — and you find it by diffing two gcdump snapshots and reading the path to root.
  6. What is deferred execution? A LINQ chain builds a query and runs it only when enumerated, so enumerating twice runs it twice — two database round trips — and the captured variables are read at enumeration time, not at definition time.
  7. Equals and GetHashCode? Equal objects must have equal hash codes and the hash must not change while the object is a key; break either and dictionary lookups silently miss, which is why key types should be immutable and generated by a record.
  8. How do you call a downstream service for 10,000 items? With bounded concurrency — Parallel.ForEachAsync with an explicit degree sized to the downstream limit, or a semaphore — plus a per-item timeout and a decided partial-failure policy; never Task.WhenAll over 10,000 tasks.
  9. What is the difference between throw; and throw ex;? throw; preserves the original stack trace; throw ex; resets it to the current line and is the single most common reason a production stack trace is useless.
  10. What is new in C# 14, and what is the current version story? C# 14 shipped with .NET 10 (LTS) on 2025-11-11 with extension members, the field keyword, null-conditional assignment and first-class spans; C# 15 with unions and closed hierarchies is in preview for .NET 11 (November 2026), and .NET 8 and .NET 9 both lose support on 2026-11-10.

Two habits that score more than any fact. Answer with the mechanism, not the label — "the continuation is registered and the thread is released", not "it's asynchronous" — and volunteer the trade-off before the interviewer asks for it. Almost every rejection at lead level is written up as "knew the APIs, did not reason about consequences".

And one preparation that beats revision. Have three stories ready with numbers: a memory or CPU incident you diagnosed, a migration you led, and a design decision you would now make differently. Half the questions in this bank are a door into one of those three.
