01Thread-pool starvation in the API tier

SeniorProduction incident / outage

(a) Worked example EXAMPLE — replace with your own

The API tier was 14 pods of an ASP.NET Core service on .NET 8, each on 4 vCPUs, doing a boring 2,000 requests per second at p99 around 80 ms. On a Tuesday morning the p99 went from 80 ms to 9 seconds in under three minutes, CPU on every pod sat at 15%, and the load balancer started failing health checks because the /healthz endpoint (which did nothing but return 200) was also timing out. That last detail is the fingerprint: a trivial endpoint that cannot get a thread is not a slow-dependency problem, it is a "no thread is free to run the continuation" problem.

I was incident commander. First thing I did was stop the well-meaning scale-out somebody had started, because adding pods to a starvation incident just gives the same bug more places to happen and hides the signal. Then I attached dotnet-counters monitor -p <pid> --counters System.Runtime to one pod and watched threadpool-thread-count climb by roughly one thread per second: 32, 33, 34, while threadpool-queue-length was in the thousands. That slow ramp is the thread pool's hill-climbing heuristic doing exactly what it is designed to do: beyond the minimum (which defaults to the processor count, so 4 here), it injects new threads cautiously, about one or two per second, because each new thread is expensive and usually wrong. It is the right behaviour for a CPU-bound pool and the worst possible behaviour when every thread is parked in a synchronous wait.

A dotnet-dump collect followed by clrstack -all in dotnet-dump analyze showed 31 of 34 threads sitting in Task.Wait or Task<T>.Result under the same frame: an internal auth library's GetClaims(...), a synchronous method that called _cache.GetOrCreateAsync(...).Result. The library had shipped that way two years earlier, and it had worked because the Redis cache answered in under a millisecond, so the blocked thread was never blocked long enough to matter. That morning Redis had a failover, latencies went to two seconds, and every request thread that entered GetClaims blocked for two seconds, holding a pool thread while the async Redis call's continuation waited in the same pool's queue for a thread that would never be freed. That is the whole mechanism of sync-over-async starvation: the blocked thread is waiting for work that needs the thread it is blocking.

// The offending shape (legacy library, synchronous public API):
public ClaimsPrincipal GetClaims(string token)
{
    // Blocks a pool thread; the continuation of GetOrCreateAsync
    // needs a pool thread to complete. Under latency, deadlock-by-starvation.
    var entry = _cache.GetOrCreateAsync(token, e => FetchAsync(token)).Result;
    return Build(entry);
}

// The fix that shipped: async all the way, with the sync method kept
// only as an [Obsolete] shim that no request path calls.
public async ValueTask<ClaimsPrincipal> GetClaimsAsync(string token, CancellationToken ct)
{
    var entry = await _cache.GetOrCreateAsync(token, e => FetchAsync(token, ct)).ConfigureAwait(false);
    return Build(entry);
}

Mitigation in the incident was ugly and honest: we set DOTNET_ThreadPool_MinThreads=200 on the deployment and restarted, which lets the pool inject up to 200 threads without hill-climbing hesitation. It bought back a p99 of 400 ms within five minutes and made the outage a degradation. Then we fixed Redis. The real fix took a week: make the library async end to end (it was two levels deep), have the middleware await it, and add the CA1849/VSTHRD002-style analyzer rules to that repo as errors so .Result on a Task could not be reintroduced. I also added an alert on threadpool-queue-length > 100 for 30s, because that is the leading indicator: the queue grows before latency does.

What I would do differently: the .NET 6+ thread pool has cooperative blocking detection that injects threads faster when it sees a Task.Wait, and that is why we got one per second instead of worse, but it only sees blocking on Task itself, not on SemaphoreSlim.Wait, lock, or a ManualResetEvent. I should not have relied on the pool to cope. And the min-threads override should have had an expiry attached to a ticket; it stayed in production for four months and masked two smaller regressions.

What the interviewer is really probing. Whether you can run an incident (stop the harmful scale-out, one hypothesis at a time, measure before changing) and whether you understand the mechanism rather than the folklore. The classic failure is narrating "we restarted and it went away" with no root cause, or blaming Redis; the dependency's latency was the trigger, sync-over-async was the cause. Own the fact that the mitigation was a hack and that you left it in too long.

(d) Follow-up drill chain

Why does the thread pool add threads so slowly when it can obviously see a queue building up?

Because it cannot tell a thread that is blocked from one that is doing CPU work, and for CPU work more threads than cores make throughput worse through context switching and cache thrash. Hill-climbing measures completed items per second and adds a thread only if that improved throughput last time, which is a control loop tuned for CPU-bound work. Since .NET 6 there is a second mechanism, cooperative blocking, that detects Task.Wait/.Result on the pool's own threads and injects faster, but it is limited to waits the runtime itself performs on Task. A lead-level answer names both mechanisms and their limits rather than calling the pool "dumb".

What if the blocking call had been a SemaphoreSlim.Wait() or a lock instead of .Result?

Then cooperative blocking would not have seen it at all and injection would have been purely hill-climbing, so the ramp would have been slower and the collapse faster. The dump would look different too: threads in Monitor.Enter or SemaphoreSlim.Wait rather than Task.Wait, so I would use syncblk to find the owner. The fix is the same shape: SemaphoreSlim.WaitAsync, and never await inside a lock (the compiler forbids it, but people restructure around the rule with .Result).

At what scale does "just make it async" stop being enough?

When the downstream is the bottleneck: async frees the thread but not the Redis connection or the DB pool slot, so under a slow dependency you now have thousands of in-flight requests instead of 34 blocked threads, and memory or connection exhaustion takes over. That is where you add bounded concurrency (a semaphore per dependency, or System.Threading.RateLimiting), timeouts with a cancellation token, and load shedding. Async makes the system able to wait cheaply; it does not remove the need to decide how much waiting you accept.

What did you trade away with the min-threads override?

Predictability. Two hundred ready threads mean 200 × 1 MB of reserved stack, more contention on the global queue, and a pool that no longer tells you anything when it grows. It also masked the next two blocking regressions, because they no longer starved, they just cost latency. A temporary override is a fine incident tool; the trade is that it must be temporary, with an owner and a date.

How did you get the library team to accept an API-breaking change?

I did not ask them to break anything: the async method was additive, the sync one stayed with [Obsolete] and an analyzer suppression file listing the remaining callers, and the incident review gave the change a business number (minutes of outage per year of latency risk). I offered to do the two call-site migrations in their busiest consumer myself. The disagreement went away once the cost was visible and the migration was not their work.

Would you do the diagnosis differently on .NET 10?

The counters are metrics now (dotnet.thread_pool.thread.count and dotnet.thread_pool.queue.length on the System.Runtime meter since .NET 9), so I would have them in the dashboard before the incident rather than attaching a tool during it. dotnet-dump plus dumpasync is still the definitive answer for "who is waiting on what". If the app were on .NET 11 with runtime async enabled, live stack traces would show the real async call chain without state-machine frames, which makes the dump faster to read but changes nothing about the starvation itself.

02The hot path that allocated a Task

SeniorPerformance problem diagnosed

(a) Worked example EXAMPLE — replace with your own

The service was a feature-flag evaluation API: every request from a fleet of front ends asked "is flag X on for user Y", and we answered around 40,000 times per second per pod. Almost every answer came from an in-memory cache, so the path was pure CPU and should have been allocation-free. It was not. Gen0 GC count on dotnet-counters was running at roughly 90 collections per second, and a dotnet-trace collect --profile gc-verbose session followed by PerfView's allocation view put 60% of allocations on two types: Task<bool> and the compiler-generated state machine box for EvaluateAsync. The method was async Task<bool>, it awaited a cache lookup that completed synchronously 99.7% of the time, and the 0.3% miss path went to a backing store. Because the signature was Task<bool>, every synchronous completion still had to hand back a Task object, and although the runtime caches Task<bool> for true/false, our method returned a struct result, so a fresh Task<EvalResult> was allocated per call: 40,000 × 72 bytes per second is 2.9 MB/s of garbage from one line.

The change was two-step and I insisted on measuring each. Step one: return ValueTask<EvalResult>. On the synchronous path the ValueTask wraps the result inline and nothing is allocated; on the miss path it wraps the underlying Task and costs the same as before. That alone dropped Gen0 to about 30 per second. Step two was where I was wary: the miss path itself still allocated the state-machine box on every await that did not complete synchronously. Since .NET 6 you can put [AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))] on an async ValueTask<T> method and the runtime pools the state-machine boxes. We tried it, it removed another 20% of the remaining allocations, and it introduced a class of bug we did not have before: a pooled ValueTask must be awaited exactly once, never stored, never awaited concurrently, never .Result-ed before completion, because the box is recycled the moment the first consumer reads it. One integration test that awaited the same ValueTask twice started returning another request's result. The CA2012 analyzer catches the obvious cases; it does not catch a ValueTask stashed in a field.

The final numbers: p99 went from 3.1 ms to 1.4 ms, mostly because Gen0 pauses stopped landing inside requests, and we shed one pod out of six. What I would do differently is scope the pooling builder to the two methods that measured as hot rather than the whole class, which is what a colleague did in a follow-up PR "for consistency" and which I approved too quickly. ValueTask is a contract change for callers; pooling is a sharper one. I would also write down the rule that ValueTask belongs on APIs where the synchronous path is common and measured, not as a default return type: on a method that always goes async it costs a slightly larger struct and buys nothing.

What the interviewer is really probing. Whether you measure before and after and can say which change bought which number, and whether you understand the ValueTask rules well enough to know what you made harder for callers. Candidates fail this by saying "we switched to ValueTask and it got faster" with no allocation profile and no mention of the single-await contract, or by presenting pooling as free.

(d) Follow-up drill chain

Why not just return Task<T> and cache completed tasks yourself?

That works for a small closed set of results, which is exactly what the runtime already does for Task<bool> and small integers, but a struct result per user/flag pair is unbounded. ValueTask<T> generalises the trick: it carries either the result or a Task, so the synchronous path allocates nothing for any T. The trade is that callers lose the freedom to await twice or use Task.WhenAll directly; they call .AsTask() for that, which reintroduces the allocation only where it is needed.

What if the callers need to store the result and await it later, or await it from two places?

Then ValueTask is the wrong public type and I would expose Task<T> or a cached task, because ValueTask's contract is "consume once, promptly". The bug we hit was exactly that: a test awaited the same ValueTask twice and, with pooling on, read another call's box. The honest lead-level rule is that ValueTask optimises the callee at the cost of the caller's freedom, so it belongs on hot internal seams, not on every public method.

At what scale does pooling the state machine stop paying?

When the async path is rare or the method is not hot, the pool's bookkeeping and the contract risk cost more than the box you save; the box is small and Gen0 is cheap when it does not land in a request. Pooling also has a per-core cache with a bounded size, so under a burst you fall back to allocating anyway. It pays on high-frequency streams: socket reads, pipeline frames, the inner loop of a serializer, which is where the BCL itself uses IValueTaskSource.

What did you trade away, and how did you make the contract visible?

Caller flexibility and a class of subtle bugs. We enabled CA2012 (use ValueTask correctly) as an error, added a doc comment on each pooled method saying "await once", and reviewed every consumer of the two hot methods by hand. The analyzer covers the syntactic cases: awaiting twice in one method, calling .Result; it does not see a ValueTask stored in a field, so the review was the real control.

How does .NET 11 runtime async change this calculation?

In preview it targets the same allocations from the other side: the runtime keeps locals on the stack and only spills them to a heap continuation when the method actually suspends, so the state-machine box for the async path shrinks or disappears without a pooling attribute, and the JIT recognises ValueTask.FromResult/Task.FromResult as intrinsics on the sync path. It is opt-in per project (<Features>runtime-async=on</Features>) and still preview, so I would not change a shipped API's return type on the strength of it. The ValueTask-versus-Task caller contract remains what it is either way.

03One library, three hosts: the ConfigureAwait policy

StaffHard architectural trade-off

(a) Worked example EXAMPLE — replace with your own

We had a shared "domain client" library, around 600 async methods, consumed by an ASP.NET Core API, a WPF desktop tool used by support staff, and a Blazor Server admin site. Three hosts, three different SynchronizationContext realities: Kestrel has none, so await continues on whatever pool thread is free; WPF has the dispatcher context, so a continuation without ConfigureAwait(false) is posted back to the UI thread; Blazor Server has its own renderer context per circuit that serialises component work onto one logical thread at a time. The library had grown inconsistently: some authors sprinkled ConfigureAwait(false) everywhere, some nowhere, and two teams had opposing analyzer settings, one with CA2007 as an error and one with it suppressed at the project level.

The forcing incident was a WPF freeze: support staff clicking "resync account" hung the app because a button handler called client.ResyncAsync(id).GetAwaiter().GetResult() (a leftover from a synchronous era), the library's inner await captured the dispatcher context, and the continuation could never run on the UI thread that was blocked waiting for it. Classic deadlock, and the library's missing ConfigureAwait(false) was one of the two hands that clapped. Somebody proposed the "fix" of adding ConfigureAwait(false) to every await in the library by regex. I pushed for a decision instead of a patch, because the regex hides the real question: what is this library's contract about context?

The trade-off I laid out to the three teams: a library that says "we never depend on the caller's context" must use ConfigureAwait(false) consistently on every await, including inside await foreach and await using, and must never touch UI or HttpContext after an await, which is a discipline you have to enforce with an analyzer because one missing call reintroduces the deadlock. The benefit is that the sync-over-async caller does not deadlock (which is not a reason to bless sync-over-async, but it is a reason a library should not be the one that hangs) and that on hosts with a context there is no Post round-trip per await, which measurably matters in Blazor Server where every posted continuation queues behind rendering. The cost is that library code cannot use ambient context-dependent things, and that a few "callback into the host" seams (progress reporting to the UI) need an explicit IProgress<T> or a captured context passed in, not an implicit one.

// Library rule: every await is ConfigureAwait(false); CA2007 is an error in this repo.
public async Task<Account> ResyncAsync(Guid id, IProgress<int>? progress, CancellationToken ct)
{
    await using var conn = await _pool.RentAsync(ct).ConfigureAwait(false);
    await foreach (var step in conn.StepsAsync(id, ct).ConfigureAwait(false))
        progress?.Report(step.Percent);            // IProgress<T> posts to the *caller's* context
    return await conn.LoadAsync(id, ct).ConfigureAwait(false);
}

// .NET 8+: the same policy without the extension-method noise, and the option to
// suppress the throw on a cancelled task when you only want to observe it.
await task.ConfigureAwait(ConfigureAwaitOptions.None);
await task.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);   // Task only, not Task<T>

We chose the strict contract for the library and the opposite for application code: in the API project CA2007 stays off, because there is no context to capture and the calls are noise; in the WPF and Blazor projects app code deliberately does not use ConfigureAwait(false) so that code after an await can touch the UI. Then we wrote the three-line policy into the repo's .editorconfig comments and fixed the GetResult() caller, because a library that survives sync-over-async is not a licence to keep doing it. The thing I would do differently is the order: I spent two weeks getting agreement on the policy before the regex, when I could have shipped the regex for the deadlock the same day with a note that the policy question was still open. Correctness first, then consistency.

What the interviewer is really probing. Whether you can hold a real trade-off (context-free library versus context-dependent app code) without collapsing it into "always use ConfigureAwait(false)", and whether you can drive a cross-team decision to a written contract. The weak answer is the slogan; the mediocre answer is the regex; the strong answer names which hosts have a context, what each choice costs, and how the rule is enforced.

(d) Follow-up drill chain

Why not just make the whole codebase use ConfigureAwait(false) and be done?

Because in a UI host the code after an await usually needs the context: a WPF handler that updates a bound property after ConfigureAwait(false) throws or silently corrupts state from a pool thread, and in Blazor Server touching component state off the renderer context is a race. In ASP.NET Core the calls are pure noise since there is no context to avoid. The right split is by role: libraries are context-agnostic and say so with ConfigureAwait(false) everywhere; app code at the edge captures the context on purpose.

What if a library method genuinely needs to call back into the UI, for progress or prompts?

Then the dependency on context becomes explicit: accept an IProgress<T>, whose default implementation Progress<T> captures the caller's context at construction and posts to it, or accept a callback and document that it runs on an arbitrary thread. What I refuse is the library capturing the context implicitly through a missing ConfigureAwait, because that makes correctness depend on which await someone forgot.

Does ConfigureAwait(false) in the library guarantee the caller cannot deadlock?

No. It guarantees the library's own continuations do not need the caller's context, which removes the most common deadlock. A caller that blocks on the UI thread can still deadlock if anything in the chain, including a third-party dependency, captures context, and it can still starve the thread pool. So the library rule removes one hand; the caller still has to stop blocking, which is why we fixed the GetResult() call rather than declaring victory.

At what scale does the context Post round-trip actually matter?

In Blazor Server it matters per circuit: each posted continuation queues behind render work on that circuit's context, so a method with twenty awaits and no ConfigureAwait(false) costs twenty queue hops, and with hundreds of concurrent circuits that shows up as UI lag. In WPF it is one dispatcher and a human clicking, so it rarely matters. In Kestrel it never matters because there is nothing to post to. That is why the policy is per host, not global.

What changed with ConfigureAwaitOptions in .NET 8, and would you use it?

It turned the boolean into flags: None is the old false, ContinueOnCapturedContext the old true, ForceYielding makes even a completed task yield (a cleaner Task.Yield with context control), and SuppressThrowing lets you await a Task without observing its cancellation or fault, useful in cleanup paths. I use SuppressThrowing sparingly and only on non-generic Task (it throws on Task<T> by design because a suppressed result would be meaningless). For the library policy the plain false is still the idiom because it works on every TFM the library targets.

How would you get three teams with different analyzer settings to agree?

By reframing it from taste to contract: I wrote the one-page "context contract" with the per-host table and the incident that motivated it, proposed the split, and asked each team lead for one objection rather than approval. Two objections were real (progress callbacks; a test host that used a context) and changed the design. Agreement came from the fact that each team's own setting was preserved in its own projects; only the shared library got the strict rule, and that is the one nobody wanted to be paged for.

04The Blazor Server circuit that froze on .Result

MidNasty debugging session

(a) Worked example EXAMPLE — replace with your own

An internal Blazor Server admin app on .NET 8 had a page that froze for exactly one user session at a time: the spinner stayed up, other users' sessions kept working, and reloading the tab fixed it. No exception anywhere. It took me most of two days, and the reason it took two days is that everything I knew about deadlocks came from WPF and legacy ASP.NET, and I had filed Blazor Server under "it's ASP.NET Core, there is no SynchronizationContext". That is wrong, and the wrongness is the whole story.

Blazor Server runs each circuit's component code on a renderer SynchronizationContext that guarantees one piece of component work runs at a time, so you never need locks in components. It is not a dedicated thread; it is a queue that any pool thread can drain, but the guarantee is exclusive. The page's OnInitializedAsync called a helper that had been copied from an old console utility: var cfg = _settings.LoadAsync().Result;. Inside LoadAsync the first await captured the renderer context (no ConfigureAwait(false), and this was app code so that was not wrong in itself). When the HTTP call finished, the continuation was posted to the circuit's context, but the context was busy running the component method that was blocked in .Result waiting for that very continuation. One circuit deadlocked; every other circuit had its own context and was fine, which is why it looked like a per-user bug and not a server bug.

What made it nasty: the freeze only happened when LoadAsync actually went asynchronous. The settings service had a cache, so nine calls out of ten completed synchronously, .Result returned immediately, and the page worked. The tenth call, on cache expiry, went to the network and froze. So it looked like a timing bug and people were reaching for "retry" and "the network is flaky". I finally caught it by taking a dump of the running process (dotnet-dump collect) while one session was frozen and running dumpasync, which lists incomplete async state machines with their continuations: there was the LoadAsync state machine, completed, with a continuation queued to a RendererSynchronizationContext, and there was a thread in Task.Wait inside OnInitializedAsync. Two lines of output, two days of hunting.

// Before: the copied helper. Works while the cache is warm, deadlocks the circuit on a miss.
protected override void OnInitialized()
{
    var cfg = _settings.LoadAsync().Result;   // blocks the renderer context
    _model = Build(cfg);
}

// After: the async lifecycle method exists precisely for this.
protected override async Task OnInitializedAsync()
{
    var cfg = await _settings.LoadAsync();    // no ConfigureAwait(false): we want the renderer context back
    _model = Build(cfg);                       // safe to touch component state here
}

The fix was the obvious one, but the lesson I kept is diagnostic: a deadlock that only reproduces sometimes is almost always a "sometimes synchronous" await plus a blocking caller, and the fastest tool is a dump, not a debugger, because attaching a debugger to a frozen Blazor circuit changes nothing and reading the async state from dumpasync shows you both hands at once. What I would do differently: I spent a day adding logging around the HTTP call, which told me the call completed fine; I should have started from "who is waiting on what" instead of "what is slow".

What the interviewer is really probing. Your debugging method under uncertainty: hypothesis, evidence, tool, and whether you can explain the mechanism you found rather than just the patch. The common failure is telling it as a triumph ("I found the .Result") without owning the wrong turn (a day of logging) or without knowing why it was intermittent. At Mid tier, showing you learned that Blazor Server has a context is the win; at Senior you add how you would stop the class of bug (analyzer for .Result, the rule that lifecycle methods are async).

We upgraded a set of ingestion services from .NET 8 to .NET 10 in the first quarter after the LTS shipped, and the one part of the upgrade that was not "bump the TFM and run the tests" was IAsyncEnumerable<T>. The services streamed events from a queue as IAsyncEnumerable<Event> and shaped them with LINQ from the community System.Linq.Async package (from dotnet/reactive), which we had used since 2020. .NET 10 ships System.Linq.AsyncEnumerable in the box: the same extension surface (Where, Select, ToListAsync, GroupBy, and so on) as first-party code in the System.Linq namespace. Keeping both referenced produced 214 CS0121 "ambiguous call" errors on the first build, because the same method names now existed in the same namespace from two assemblies.

The plan I wrote was small but ordered. Step one: remove the package reference and let the compiler list what breaks. Step two: fix the naming differences. The community package spelled its async-predicate overloads with suffixes, WhereAwait, SelectAwait, WhereAwaitWithCancellation; the in-box version uses plain names with overloads whose lambdas take a CancellationToken and return a ValueTask. So events.WhereAwaitWithCancellation((e, ct) => IsAllowedAsync(e, ct)) becomes events.Where((e, ct) => IsAllowedAsync(e, ct)). Step three: check the cancellation plumbing, because that is where the semantics could differ. In both versions, WithCancellation(ct) on the enumerable flows the token into the source iterator's [EnumeratorCancellation] parameter, and the async-lambda overloads receive the same token, so the behaviour matched; but two of our iterators had the attribute on the wrong parameter, which had silently been a no-op for years and now got a compiler warning we had never seen because the older analyzers did not flag it.

// Source iterator: the token that WithCancellation(ct) supplies lands on this parameter.
public async IAsyncEnumerable<Event> ReadAsync([EnumeratorCancellation] CancellationToken ct = default)
{
    await using var reader = await _queue.OpenAsync(ct);
    while (await reader.WaitToReadAsync(ct))
        while (reader.TryRead(out var evt))
            yield return evt;
}

// Consumer on .NET 10 with in-box System.Linq.AsyncEnumerable:
await foreach (var batch in ReadAsync()
    .WithCancellation(stoppingToken)
    .Where((e, ct) => IsAllowedAsync(e, ct))      // async predicate; was WhereAwaitWithCancellation
    .Select(e => Normalize(e))
    .Chunk(500)
    .ConfigureAwait(false))
{
    await _sink.WriteAsync(batch, stoppingToken);
}

What I would do differently is run the in-box package's analyzer set against the codebase before removing the reference, which would have found the misplaced [EnumeratorCancellation] attributes without the noise of 214 ambiguity errors.

(d) Follow-up drill chain

Why is cancellation of an async stream two-sided, and what goes wrong if you only do one side?

The consumer side is WithCancellation(ct) or passing the token to the iterator; the producer side is the [EnumeratorCancellation] parameter and actually using that token inside the iterator on every await. If the attribute is missing or on the wrong parameter, WithCancellation has nothing to bind to and cancellation only takes effect when control is back in the consumer's loop body, so a producer stuck in a long ReadAsync keeps blocking until the next item arrives. Our misplaced attributes were exactly that: shutdown waited for the next queue message.

What if a consumer breaks out of await foreach early? What happens to the producer?

await foreach calls DisposeAsync on the enumerator, which resumes the iterator's finally blocks and await using disposals, so resources are released without the token ever being cancelled. That is the reason to put cleanup in finally rather than after the loop. What does not happen is that any in-flight await inside the iterator is interrupted; disposal only runs when the iterator is at a yield, which is another reason the producer must honour the token on its awaits.

At what point would you replace LINQ over IAsyncEnumerable with Channels?

When you need a buffer between producer and consumer with a stated capacity and a policy for what happens when it is full, or fan-out to multiple consumers, or time-based batching. IAsyncEnumerable is pull-based and single-consumer with no buffer; every item is requested by the consumer. The reactive operators like Merge and time-windowed Buffer exist because those needs are real, which is why that one service kept the package rather than being rewritten under deadline.

Why keep the community package in one service instead of finishing the job?

Because the job had a scope and that rewrite was not in it. Replacing Merge with a bounded channel and a producer per source is a design change with new failure modes (backpressure, ordering), and doing it inside an upgrade means any regression gets blamed on the upgrade. I isolated it with an alias so the rest of the codebase moved, and I filed the rewrite with a cost estimate. Upgrades should change one variable at a time.

What is the difference between ConfigureAwait(false) on a Task and on an IAsyncEnumerable?

On a task it configures one await; on an async enumerable it wraps the enumerable so that every MoveNextAsync and the final DisposeAsync are awaited with ConfigureAwait(false). It exists as TaskAsyncEnumerableExtensions.ConfigureAwait and returns a ConfiguredCancelableAsyncEnumerable<T>, which is why it composes with WithCancellation. In a library iterator consumer it is the same policy as story 03: context-agnostic code opts out on every await, including the hidden ones.

06"Just wrap it in Task.Run"

SeniorTechnical disagreement with a colleague

(a) Worked example EXAMPLE — replace with your own

A colleague I respected opened a pull request that wrapped every service call in an ASP.NET Core controller in Task.Run: return await Task.Run(() => _orders.GetAsync(id, ct));, twenty-odd endpoints, with the description "make the API more responsive under load". Load tests on their laptop showed p50 improving by a few milliseconds, which made the argument feel data-backed. My position was that this was wrong in principle and would be harmful at scale, and the disagreement got sharp enough that we agreed to settle it with a proper benchmark rather than in review comments.

The mechanism I explained: in a server app every request already runs on a thread-pool thread. Task.Run queues the delegate to the same pool, so the request thread hands the work to a sibling thread and then, because we await it, gives itself back to the pool. Net effect for an already-asynchronous call: one extra queue hop, one extra Task allocation, one extra continuation, and a loss of the locality the runtime works hard for (the pool prefers to run a continuation on the thread that queued it, through its per-thread local queues). On a laptop with idle cores, the extra hop is free and the shuffle can even smooth p50. On a pod with 2 vCPUs at 70% CPU, each hop is contention on the global queue. The load test that mattered was at saturation: at 2 vCPUs and 1,500 rps, the Task.Run variant had 11% lower throughput and a p99 that was 40 ms worse, because the pool was spending its time moving work between threads instead of doing it.

(d) Follow-up drill chain

Why does the thread pool care which thread runs a continuation?

Each pool thread has a local work-stealing queue; work queued from a pool thread goes there first and is preferred by that thread, which keeps caches warm and avoids contention on the global queue. Task.Run from a pool thread also queues locally, so the first hop is cheap, but the awaited continuation then has to be scheduled again, and under saturation other threads steal the work, so you pay the coordination without the benefit. At low load none of this is visible; at saturation it is throughput.

What if the endpoint really did have 200 ms of CPU-bound work?

Then Task.Run still does not help the server: the CPU cost has to be paid on some pool thread either way, and the request thread would just sit awaiting it. What helps is capacity management: a bounded worker (a Channel feeding N dedicated threads) so CPU work cannot consume every pool thread and starve I/O completions, or moving the work out of the request path entirely. The exception is a UI host, where offloading is the whole point.

At what scale does the extra hop stop being noise?

When the pool is near saturation, which in containers happens sooner than people expect: a 2-vCPU pod has a minimum thread count of 2 and every hop competes with real work. Our saturation test at 1,500 rps showed 11% throughput loss; at 200 rps it showed nothing. That is why I insist benchmarks for scheduling changes run at the CPU limit of the production pod size.

Almost only for TaskCreationOptions.LongRunning, which hints the scheduler to use a dedicated thread for a loop that will live for minutes or the process lifetime, so it does not hold a pool thread. Its foot-guns are that it defaults to TaskScheduler.Current rather than the default scheduler, and that an async lambda gives you a Task<Task> you must Unwrap(). In modern code a BackgroundService is the cleaner answer for the long-lived case, and Task.Run for everything short.

// Bounded concurrency for the DB side (.NET 6+): Parallel.ForEachAsync with a degree.
var dbLimit = new ParallelOptions { MaxDegreeOfParallelism = 20, CancellationToken = ct };
await Parallel.ForEachAsync(accountIds, dbLimit, async (id, token) =>
{
    var snapshot = await _repo.LoadAsync(id, token);
    await _outbox.Writer.WriteAsync(snapshot, token);   // hands off to the rate-limited stage
});

// Rate-limited stage for the partner API (System.Threading.RateLimiting, .NET 7+).
var limiter = new TokenBucketRateLimiter(new TokenBucketRateLimiterOptions
{
    TokenLimit = 50, TokensPerPeriod = 50, ReplenishmentPeriod = TimeSpan.FromSeconds(1),
    QueueLimit = 1000, AutoReplenishment = true
});
await foreach (var snapshot in _outbox.Reader.ReadAllAsync(ct))
{
    using var lease = await limiter.AcquireAsync(1, ct);
    if (!lease.IsAcquired) { _metrics.Dropped(); continue; }
    await _partner.PushAsync(snapshot, ct);
}

The pipeline was a bounded Channel<Snapshot> between the two stages, capacity 2,000, with BoundedChannelFullMode.Wait, so if the partner slowed down, backpressure propagated to the database stage and it stopped loading rather than buffering 50,000 snapshots in memory. The old version had used a SemaphoreSlim(100) around ReconcileAsync as a hotfix during the incident; that limited concurrency but still created all 50,000 tasks and their state machines up front, about 40 MB of objects waiting on the semaphore, and made cancellation awkward because you had to drain them. Parallel.ForEachAsync starts only as many iterations as the degree allows and takes a token; that is why it replaced the semaphore.

The job went from a 40-minute run that hurt the API tier to a 25-minute run that nobody noticed, with a dashboard showing the channel's depth so we could see which stage was the bottleneck at a glance. Why is a SemaphoreSlim around each task not enough?

It bounds how many run concurrently but not how many exist: ids.Select(id => DoAsync(id)) eagerly creates every task and its state machine before WhenAll is reached, so memory scales with the input, and cancellation means every waiter has to be woken to observe the token. It also puts the limit at the wrong place: a global semaphore of 100 says nothing about the database wanting 20 or the partner wanting 50 per second. Parallel.ForEachAsync pulls items lazily at the degree you set, which fixes the first problem; per-resource limits fix the second.

What if the two stages need different limits and one is much slower?

Then the bounded channel between them is what keeps the fast stage from running away: when the consumer is slower, the channel fills, the producer's WriteAsync waits, and the fast stage naturally throttles to the slow one's pace. That is backpressure. The trade is that the job's total time is dominated by the slow stage no matter what, so the design question becomes whether the slow stage can be widened (more rate from the partner, batching) rather than whether the fast stage can go faster.

At what scale does this design break?

When the input no longer fits in memory as a list (we loaded 50,000 IDs; at 50 million you stream the IDs too), when a single process's limits are no longer the system's limits (three instances of the job each at 50 rps is 150 rps at the partner, so the rate limit has to move to a shared limiter or a gateway), and when the partner's latency variance makes a token bucket the wrong shape and you need concurrency limiting on their side as well. The principle survives; the placement of the limits moves outward.

What did you trade away with backpressure?

Throughput headroom and simplicity. A pipeline that waits on a full channel will never exceed the slowest stage, so a temporary burst of partner capacity is not exploited. And the code has more moving parts than a WhenAll: two stages, a channel, a completion signal (Writer.Complete() in a finally), and a failure path that has to cancel both stages rather than one. We accepted that because the alternative was an unbounded buffer, which is a memory incident waiting for a slow night.

How does Task.WhenEach (.NET 9) change how you would write this?

It solves a different problem: processing results in completion order as an IAsyncEnumerable<Task> instead of waiting for all or repeatedly calling WhenAny (which was O(n²) over a shrinking list). It still assumes you have started the tasks, so it does not bound concurrency. I would use it inside a bounded batch: start 20, iterate WhenEach to handle them as they finish, refill. For a plain pipeline, ForEachAsync plus a channel remains simpler.

How did you get the DBA and the partner team to give you real numbers?

By asking a narrower question than "how many connections can I have". For the DBA it was "what may this job take between 02:00 and 04:00 without the API tier's p99 moving", which they could answer from their graphs; for the partner it was "which limit do you enforce and what do you return when I hit it", which turned out to be documented. Limits you negotiate with a specific window and a specific consequence get answered; abstract capacity questions get "it depends".

08The request that outlived the client

SeniorSecurity issue found and fixed

(a) Worked example EXAMPLE — replace with your own

A penetration test report flagged a "resource exhaustion via early disconnect" finding against our search API, and the first reaction in the team was to dispute it as theoretical. The finding: a client could open a request for an expensive search (full-text across a large tenant, about four seconds of database time), close the socket after 50 milliseconds, and repeat. Because the server did not notice the disconnect, each abandoned request ran to completion, so an attacker with a single laptop could hold all 100 pooled database connections busy with work nobody would ever read, at a cost of nothing to them. It was not theoretical. I reproduced it with a 20-line script and watched the API's real users time out on connection-pool waits while the attacker's process used 2% CPU.

The root cause was cancellation that stopped one layer deep. ASP.NET Core gives every request HttpContext.RequestAborted, a CancellationToken that Kestrel cancels when the client disconnects, and minimal APIs and MVC will bind a CancellationToken parameter to it automatically. The controller accepted the token. It passed it to the service. The service passed it to the repository. The repository called ExecuteSqlAsync(sql) without it, because the overload with the token had been added to the interface a year after the method was written and nobody went back. Cancellation in .NET is cooperative: a token that is not observed at the point where the work actually happens cancels nothing, and the point where the work happens was the database driver. Once the token reached DbCommand.ExecuteReaderAsync(ct), the driver cancelled the command server-side, which for SQL Server means an attention signal that stops the query, and the connection went back to the pool within milliseconds of the disconnect.

// The repository fix: the token must reach the driver, not stop at the service.
public async Task<IReadOnlyList<Hit>> SearchAsync(Query q, CancellationToken ct)
{
    await using var cmd = _conn.CreateCommand();
    cmd.CommandText = q.ToSql();
    await using var reader = await cmd.ExecuteReaderAsync(ct);          // was: ExecuteReaderAsync()
    var hits = new List<Hit>();
    while (await reader.ReadAsync(ct))                                    // was: ReadAsync()
        hits.Add(Map(reader));
    return hits;
}

// The endpoint: bind the request's token and translate cancellation into a 499-style outcome.
app.MapGet("/search", async (Query q, ISearch search, CancellationToken ct) =>
{
    try { return Results.Ok(await search.SearchAsync(q, ct)); }
    catch (OperationCanceledException) when (ct.IsCancellationRequested)
    { return Results.StatusCode(499); }   // client went away; not a server error, not a 500 in the logs
});

Fixing the plumbing closed the finding but not the class. I then added two controls. First, an analyzer: CA2016 ("forward the CancellationToken parameter to methods that take one") turned to error across the repositories, which found 63 more call sites in a week. Second, a bulkhead: even with cancellation working, an attacker who keeps sockets open instead of closing them still holds connections, so the expensive search got its own concurrency limiter (a ConcurrencyLimiter from System.Threading.RateLimiting via the rate-limiting middleware, partitioned by tenant, capacity 10 per tenant), which caps the damage any one caller can do regardless of whether they disconnect. Cancellation reclaims resources when the client leaves; the limiter bounds them while the client stays.

What I would do differently: I initially treated the finding as a performance bug and fixed it quietly. It was a security bug, with a severity, and it should have gone through the security process so that the analyzer rule became an org-wide baseline rather than one repo's setting. Also, I logged cancelled requests as errors for the first week, which drowned the error dashboard in 499s from mobile clients on flaky networks; the when filter distinguishing the client's cancellation from our own timeouts fixed the noise.

What the interviewer is really probing. Whether you take a security finding seriously without ego, whether you understand that cancellation is cooperative and must reach the leaf, and whether you fix the class (analyzer, bulkhead) rather than the instance. The failure is disputing the finding, or fixing one call site and calling it done, or presenting cancellation as sufficient when a keep-alive attacker defeats it.

(d) Follow-up drill chain

Why does .NET make cancellation cooperative instead of aborting the thread?

Because aborting a thread at an arbitrary point leaves locks held, buffers half-written and invariants broken, which is why Thread.Abort throws PlatformNotSupportedException on .NET Core and later. A token lets the code that owns the resources decide where a safe stopping point is: between awaits, at a loop check, inside a driver that knows how to send an attention signal. The cost is exactly what bit us: every layer must forward it, and one omission silently makes it a no-op.

What if the expensive work is CPU-bound in our own code, not in the database?

Then no driver will cancel it for you: the loop has to call ct.ThrowIfCancellationRequested() at a granularity that matters, or check ct.IsCancellationRequested and unwind cleanly. For a long tight loop I check every N iterations rather than every iteration. And that work should not be on request threads at all if it is seconds long; it belongs on a bounded worker where a limiter caps it per caller, which is the same bulkhead argument.

How do you tell "the client cancelled" from "we timed out" from "someone cancelled the wrong thing"?

By owning the tokens. The request token comes from Kestrel; my own timeout is a linked CancellationTokenSource created with CreateLinkedTokenSource(requestToken) and CancelAfter(…); then in the catch I check which one is signalled: when (requestToken.IsCancellationRequested) is the client, otherwise it is my timeout. Since .NET 5 HttpClient does the same for its own timeout by nesting a TimeoutException inside the TaskCanceledException. And the linked source must be disposed, or its registration on the long-lived request token leaks until the request ends.

At what scale does cancellation alone stop protecting you?

Immediately, against an attacker who keeps the connection open. Cancellation only reclaims what a departed client abandoned; it does nothing about a client who stays and asks for a lot. That is why the second control was a concurrency limiter partitioned per tenant or per API key, and why I would put a request timeout in front of long queries as well. Defence is: cancel what is abandoned, bound what is active, time out what is stuck.

What did you trade away by cancelling database commands?

Some database-side cost and a new class of partial-state bugs. Cancelling a command mid-transaction means the transaction must be rolled back, and any code that did a write followed by a cancelled read has to be examined for whether the write should stand. We audited the search path (read-only, fine) and put explicit "do not cancel after this point" logic on two write paths by passing CancellationToken.None to the commit step, with a comment saying why.

09Retiring 1,900 .Result calls without a big bang

StaffTech-debt paydown / refactor

(a) Worked example EXAMPLE — replace with your own

After two starvation incidents in a year, I got a mandate to "fix sync-over-async" in a codebase of about 400,000 lines that had grown from .NET Framework days. A grep found 1,900 occurrences of .Result, .Wait() and GetAwaiter().GetResult() on tasks, spread across 60 projects, plus about 300 async void methods that were not event handlers. The naive plan, a branch that fixes all of them, was rejected by me before anyone else could: a refactor that changes method signatures across 60 projects cannot be reviewed, cannot be merged without conflicts, and cannot be bisected when it breaks something. This story is about how you pay down debt that is spread thin everywhere.

The mechanism that makes sync-over-async debt special is that it is viral in the opposite direction to async: you cannot make a method async without touching every caller, and every caller's callers, up to an entry point that can await (a controller, a hosted service, an event handler). So the unit of work is not "one call site" but "one path from a blocking site up to an awaitable root". I wrote a small Roslyn-based script that, for each blocking site, computed the call chain to its nearest root and the number of methods on it, and sorted by chain length. Sixty percent of the 1,900 sites had chains of one or two methods; those were a week of mechanical work by three people. The long tail, chains of ten or more through interfaces with many implementations, was where the design decisions lived.

The ratchet was the part that made it stick. Rather than a big-bang analyzer error that would have blocked every build, we enabled the blocking-call rules (the VSTHRD002 family from Microsoft.VisualStudio.Threading.Analyzers, plus a banned-API list for Task.Result) as warnings, generated a baseline suppression file per project with the current count, and made CI fail if any project's count went up. Every PR could lower the number, none could raise it, and a weekly bot posted the total. For the interfaces on the long tail, we added the async method alongside the sync one, marked the sync one [Obsolete] with a message pointing at the async, and migrated implementations one at a time with the sync version delegating to the async one through a deliberately named SyncOverAsyncBridge.Run(...) helper, so that the remaining bridges were greppable and each one had a ticket number in its argument list.

(d) Follow-up drill chain

Why can you not fix sync-over-async one call site at a time?

Because making the callee async changes its return type, and the call site that used .Result now has to await, which makes its own method async, and so on up to a root that is already async. Each blocking site therefore implies a chain of signature changes, and the practical unit of work is the chain. Sorting by chain length is what turns 1,900 sites into a week of easy work plus a manageable long tail.

What if a constructor or a property getter needs the result of an async call?

Then the design is wrong at that seam, not the async: constructors and getters cannot await, and blocking inside them is where the worst deadlocks live. The fix is a static async factory (await Foo.CreateAsync()), lazy initialisation with an AsyncLazy-style helper (a Lazy<Task<T>> works), or moving the work to a hosted service that runs at startup. Each of those is a small refactor that removes a blocking site permanently.

At what scale does the ratchet stop working?

When the number stops moving because the remaining sites are all hard, and nobody owns the hard ones. A ratchet prevents regression; it does not create progress by itself. We paired it with a quarterly "long tail" allocation of one engineer for two weeks, and with the rule that any team touching a file with a bridge in it took the bridge out. Without an owner for the tail, the count plateaus and the suppression file becomes permanent.

What did you trade away with the obsolete-and-bridge approach?

A period where both APIs exist and the sync one is implemented as sync-over-async, which is exactly the pattern we were removing. That was deliberate: the bridge was bounded by a semaphore, named so it could be found, and each use carried a ticket, so the risk was contained and time-boxed. The alternative, a flag day, would have traded a year of measurable progress for a merge nobody could review.

How did you keep 60 project owners on board for a year?

By making it cheap for them and visible to their managers: the ratchet meant no owner ever had to stop feature work, my team did the mechanical 60% ourselves, and the weekly number went to the engineering channel with the projects that moved that week. The two incidents were the reason the mandate existed, so I tied the number back to the incident review's action items each quarter. People support a number they can see going down without paying for it.

10Teaching the state machine, not the rule

SeniorMentoring / levelling someone up

(a) Worked example EXAMPLE — replace with your own

A mid-level engineer on my team was writing async code that compiled and passed tests and was wrong in three recurring ways: async void helpers "because the caller doesn't need the result", calls to async methods without await ("it runs in the background"), and try/catch around an un-awaited call that could never catch anything. Their reviews kept collecting the same comments, and I could see that each comment was being fixed as a local rule ("add await here") without changing the model that generated the bug. Rules do not transfer; a model does. So instead of a fourth round of comments I booked ninety minutes and we read the compiler's output together.

We took one of their methods and looked at what the compiler generates for it: a struct (in Release) implementing IAsyncStateMachine, with a MoveNext method containing their code as a switch over a state field, an AsyncTaskMethodBuilder that creates the Task the caller sees, and, at each await, a check of IsCompleted that either continues inline or stores the state and registers MoveNext as the continuation via AwaitUnsafeOnCompleted. Three things fell out of that reading that no rule had conveyed. First, an async method runs synchronously on the caller's thread until the first await that is not already complete; "it runs in the background" is false, the caller is executing the method's first stretch itself. Second, an exception thrown after the first real await is caught by the state machine and stored on the Task; it surfaces only when someone awaits the task, so a try/catch around an un-awaited call sees nothing, and an unobserved faulted task is just quietly lost (since .NET 4.5 the finalizer no longer crashes the process for it). Third, async void uses AsyncVoidMethodBuilder, which has no task to store the exception on, so it raises it on the captured SynchronizationContext or, where there is none, as an unhandled exception on the thread pool, which terminates the process.

// What they wrote                                 // What actually happens
public async void Save(Order o)                   // no Task: exceptions have nowhere to go
{
    await _repo.SaveAsync(o);                     // throws after the await -> process crash in a server
}

public void Handle(Order o)
{
    try { Save(o); }                              // returns at the first incomplete await; nothing to catch here
    catch (Exception ex) { _log.Error(ex); }      // dead code for anything thrown after the await
}

// What we wrote instead
public Task SaveAsync(Order o, CancellationToken ct) => _repo.SaveAsync(o, ct);

public async Task HandleAsync(Order o, CancellationToken ct)
{
    try { await SaveAsync(o, ct); }               // the await is what rethrows the stored exception
    catch (Exception ex) when (ex is not OperationCanceledException) { _log.Error(ex); throw; }
}

The second session was about the thread hop: I had them log Environment.CurrentManagedThreadId before and after an await in a console app (different thread), in a WPF sandbox (same thread), and in an ASP.NET Core minimal API (different thread). That single exercise made ConfigureAwait and "why do I not need locks in Blazor components" click, because they had seen the context decide. We then turned on CS4014 (call not awaited) as an error and the VSTHRD100 rule for async void in their project so the compiler would say what I had been saying. Over the next quarter their reviews stopped collecting those comments and they started leaving them on other people's PRs, which is the outcome I actually wanted.

What I would do differently: I did this one-to-one, and two other people on the team had the same gaps. A one-hour team session with the decompiled state machine on screen would have been a better use of everyone's time, and I ran it a month later than I should have. I also learned to check for the model gap earlier: if the same comment appears twice on someone's PRs, the third time should be a conversation, not a comment.

What the interviewer is really probing. Whether you develop people by transferring a mental model rather than by correcting output, and whether you can explain async at the level of the state machine yourself. The weak answer is "I explained the best practices"; the strong one shows the concrete artefact you taught from (the generated code, the thread-id experiment), the tooling you installed so the lesson holds without you, and the evidence it worked.

(d) Follow-up drill chain

Why teach the generated code rather than the rules?

Because the rules are consequences of one mechanism, and someone who has the mechanism can derive rules for cases they have never seen. "Don't use async void" is a rule; "there is no Task to hold the exception" is the reason, and it also explains why the exception behaves differently in WPF than in Kestrel, which no rule covers. Rules transfer nothing; a model transfers to the next language feature and the next runtime version.

What if the engineer pushes back that fire-and-forget is what they want?

Then we design fire-and-forget properly rather than accidentally: the work becomes a Task handed to a background queue (a Channel drained by a hosted service) that owns its lifetime, logs its exceptions and participates in shutdown. An un-awaited call in a request is fire-and-forget with no owner: it dies with the request's scope, its exception is lost, and it is not drained on shutdown. Wanting the semantics is legitimate; getting them from a missing await is not.

At what point does async void become acceptable?

Event handlers, where the delegate signature is void and there is no caller to hand a task to, and even then the body should be a try/catch around an awaited Task-returning method so nothing escapes. Everywhere else it is a bug waiting for a host without a synchronization context to become a crash. In the codebase from story 09, every non-handler async void was either an accident or an attempt at fire-and-forget.

How does the state machine explain "the first part runs synchronously"?

The builder's Start calls MoveNext on the caller's thread immediately; code up to the first await executes right there, and if the awaited task is already complete, the code after it executes too, still on the caller's thread, with no continuation ever scheduled. Only at the first incomplete await does the machine save its state, register a continuation and return the Task to the caller. That is why a slow synchronous prefix in an async method blocks the caller, and why a hosted service whose ExecuteAsync never awaits blocks host startup (story 19).

Would you teach this differently now that .NET 11 runtime async exists?

The observable rules stay identical: sync prefix, exceptions on the task, async void semantics, context capture. What changes under runtime async is the implementation, the runtime suspends and resumes methods itself instead of the compiler emitting a state machine, which is why live stack traces lose the MoveNext frames. I would still teach the state machine first, because it is what every shipped .NET version does today and what the runtime-async model is designed to be equivalent to; then show the .NET 11 stack trace as the "same contract, cleaner machinery" coda.

11Graceful shutdown before the Kubernetes deadline

StaffScope / deadline negotiation

(a) Worked example EXAMPLE — replace with your own

Platform gave us six weeks to move a fleet of twelve .NET worker services from VMs to Kubernetes. The workers consumed queues and wrote to databases, and on VMs they had been restarted about once a quarter, by hand, after being drained. On Kubernetes they would be restarted constantly: deploys, node rotations, spot evictions, autoscaling. The product owner's scope was "lift and shift, no behaviour changes". My position was that the behaviour change was already decided by the platform, and that a worker that could be killed mid-message would lose or duplicate work, so shutdown handling had to be in scope or the migration had to slip. That negotiation is the story; the async plumbing is what made the negotiation winnable.

I made the risk concrete with a test rather than an argument: I ran one worker under a SIGTERM with a 30-second grace period, the Kubernetes default, and showed that it died mid-batch 100% of the time. The workers were BackgroundServices, and their ExecuteAsync loops ignored the stoppingToken: they called Task.Delay(1000) without the token and ReceiveAsync() without the token, so when the host cancelled the token on SIGTERM, nothing noticed. The host's StopAsync waits for each service's ExecuteAsync to complete up to HostOptions.ShutdownTimeout (30 seconds by default since .NET 8; it was 5 seconds before, which surprised half the room) and then gives up; Kubernetes sends SIGKILL at its own 30 seconds. So we had two timers with the same length and a loop that respected neither.

public sealed class ReconcileWorker(IQueue queue, IHandler handler, ILogger<ReconcileWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await Task.Yield();                                   // never block host startup (story 19)
        while (!stoppingToken.IsCancellationRequested)
        {
            Message? msg;
            try { msg = await queue.ReceiveAsync(stoppingToken); }             // the token reaches the wait
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested) { break; }

            // In-flight work finishes with a *bounded* token so a slow handler cannot hold shutdown forever,
            // but the ack is never cancelled: half-acked is worse than re-delivered.
            using var work = CancellationTokenSource.CreateLinkedTokenSource(stoppingToken);
            work.CancelAfter(TimeSpan.FromSeconds(20));
            try
            {
                await handler.HandleAsync(msg, work.Token);
                await queue.AckAsync(msg, CancellationToken.None);
            }
            catch (OperationCanceledException) { await queue.NackAsync(msg, CancellationToken.None); }
        }
        log.LogInformation("drained");
    }
}

Given the deadline, I proposed a scope split and got it accepted in one meeting: in scope, every worker's loop honours stoppingToken on its waits, finishes the in-flight message with a bounded timeout, and acks or nacks deterministically; also a preStop hook that sleeps 5 seconds so the load balancer stops sending before shutdown begins, and terminationGracePeriodSeconds raised to 45 so the host's 30-second timeout fires before the kernel's. Out of scope, explicitly, with tickets: idempotent handlers for the three workers whose writes were not idempotent (they got at-least-once semantics and a dedup table later), and IHostedLifecycleService (.NET 8) hooks for ordered stop across services. The trade I asked the product owner to accept was a two-week slip against "a duplicate-payment incident in month one"; the trade I accepted was leaving at-least-once instead of exactly-once for the first release.

The migration shipped one week late instead of two, because the loop fix turned out to be mechanical once the pattern was written, and a chaos test that SIGTERMs a worker every ten minutes ran in staging for the final fortnight without a lost message. What I would do differently: I let "no behaviour change" stand as the framing for two weeks before challenging it. Naming the change the platform had already made ("restarts go from quarterly to hourly") on day one would have made the scope discussion a five-minute one. And the 5-second-to-30-second ShutdownTimeout default change had bitten a sibling team already; I should have known that from their retro.

(d) Follow-up drill chain

Why not just catch the cancellation and let the message be redelivered?

That is the at-least-once fallback and it is what the nack path does, but it only works if the handler is idempotent or the redelivery is deduplicated; three of our workers made non-idempotent writes, so a redelivery after a partial handler run would duplicate a payment. Finishing the in-flight message with a bounded timeout is the cheaper first step because it makes the partial case rare; idempotency makes it harmless, and it was the deferred ticket.

What if a handler genuinely needs longer than the grace period?

Then it must not be a single unit of work inside a pod that can be killed: either checkpoint progress so a restart resumes rather than restarts, or move the long step to a durable workflow. Raising the grace period buys minutes at most; Kubernetes will still evict a node. The honest design says "any single step completes within N seconds or is resumable", and the bounded linked token in the loop is how the code enforces N.

Why must the two timeouts be ordered, and which way?

The host's ShutdownTimeout is the last chance for managed code to log, nack and flush; the orchestrator's grace period is when the process is killed regardless. If the kernel's timer fires first, your finally blocks and your "drained" log never run and you cannot tell from the logs whether shutdown was clean. So the host timeout must be shorter than the grace period, with margin for the preStop sleep, which is why we set 30 seconds inside and 45 outside.

What did you trade away by cancelling in-flight handlers after 20 seconds?

Some work that would have completed at 25 seconds gets redelivered, and any external side effect that happened before the cancel now needs to be safe to repeat. A visible, logged nack at 20 seconds is a better failure than an invisible one at 45.

How did you get the product owner to accept a slip?

By trading a fixed cost for a variable one they could picture: one extra week now, versus a duplicate-payment incident whose cost I estimated from a previous one. The kill test made it concrete: a video of a worker dying mid-batch is more persuasive than a paragraph about cancellation tokens. And I offered the split, so they were choosing between two plans rather than between my plan and theirs.

How does IHostedLifecycleService (.NET 8) change the design?

It adds StartingAsync/StartedAsync and StoppingAsync/StoppedAsync around the existing StartAsync/StopAsync, which lets you order shutdown: stop accepting new messages in StoppingAsync across all workers before any of them begins draining, and flush shared outboxes in StoppedAsync. We deferred it because our workers were independent; for a pipeline of dependent services it would have been in scope, because stopping the consumer before the producer loses messages.

The invoice page's handler did three things: load the tenant's settings, load invoices, load a summary. Somebody had "parallelised" it: var s = LoadSettingsAsync(); var i = LoadInvoicesAsync(); var m = LoadSummaryAsync(); await Task.WhenAll(s, i, m);. All three methods used the same scoped DbContext. But the check is a best-effort guard, not a lock, and there is a window in the change tracker where two concurrent queries can interleave their materialisation, so on rare occasions one query's entities landed in the other query's result set. The tenant filter was in the SQL; the corruption happened in memory after the rows came back.

The reason it had shipped is the thing I teach from this story: await does not make code thread-safe, and Task.WhenAll is a concurrency primitive even if no Task.Run is in sight. Each of the three methods hit its first incomplete await, returned, and the next started; when the database answered, the continuations ran on whichever pool threads were free, at the same time, on the same context. Async code that touches shared state between awaits needs the same discipline as multi-threaded code, and a scoped service in a web request is shared state across every task started in that request.

var invoices = _db.Invoices.Where(x => x.TenantId == tid).ToListAsync(ct);
var summary  = _db.Invoices.Where(x => x.TenantId == tid).SumAsync(x => x.Total, ct);
await Task.WhenAll(settings, invoices, summary);

// After (a): sequential on one context. Simple, correct, 3 round trips.

var i = await _db.Invoices.Where(x => x.TenantId == tid).ToListAsync(ct);
var m = i.Sum(x => x.Total);

(d) Follow-up drill chain

Why does await not protect shared state?

await only sequences the code within one method; it says nothing about what other tasks do while this one is suspended. When three tasks are started before any is awaited, all three progress concurrently, and their continuations run on arbitrary pool threads, possibly at the same instant. Async gives you concurrency by default; whether that concurrency is safe depends on what the tasks share, exactly as with threads.

What if the parallel version was 3× faster? Was killing it the right call?

Why did EF Core's guard not catch it every time?

The guard is a flag checked at operation start, not a lock around the whole operation, because a lock would make the misuse silently serialise and hide the bug. There is a small window between the check and the change-tracker work where two operations can both pass, and under load with variable query latency that window is hit occasionally. It is documented as a detection aid; the contract is that you never do it, and the interceptor we added in test environments makes detection strict where it costs nothing.

At what scale would you have seen this sooner?

At higher load or with slower queries, because the interleaving window is hit more often when continuations pile up. At low load the first query usually completes before the second starts, which is why the guard exception fired only twice a day and the corruption four times in two weeks. Concurrency bugs hide in low traffic; a load test with query latency injected (a delay interceptor) would have surfaced it in staging.

How would you prevent this class in a new codebase?

Two structural choices: make it hard to share, by handing IDbContextFactory to anything that fans out and keeping the scoped context for the linear path; and make misuse loud, with the strict interceptor in every non-production environment and the guard exception routed to an alert rather than a log. Then a review rule: every Task.WhenAll names in a comment what the branches share. That is a habit, not a tool, but it is the habit that catches the semantic case an analyzer cannot.

13Timeouts, retries and hedging: the spec that kept moving

SeniorAmbiguous / shifting requirements

(a) Worked example EXAMPLE — replace with your own

The requirement started as one sentence from a product manager: "the pricing call must never take more than two seconds". Over eight weeks it became "fail fast at two seconds", then "retry once if it fails", then "return a cached price if it fails", then "send a second request to the backup region if the first is slow", and finally "but never double-charge the quote budget", because the pricing provider billed per call. Each version was reasonable; each contradicted the previous one's implementation; and the engineer who had the ticket before me had implemented the first three literally, in sequence, so the code had a hard timeout, a retry inside it, and a cache fallback outside it, and nobody could say what happened at 1.9 seconds on a slow retry. The story is about turning a moving target into a small set of named policies, and the technical core is how timeouts, cancellation and retries compose in .NET.

I wrote a one-page decision table with the PM instead of taking the fifth requirement as given. The columns were the outcomes that could actually happen (fast success, slow success, transient error, hard error, provider down), and for each the question was what the user sees and what it costs us. That surfaced the real constraints: the two seconds was a UI budget, not a provider SLA; the retry was wanted for transient errors only; the hedge to the backup region was worth its double cost only for the checkout page, not for browsing; and a stale cached price was acceptable for browsing but not for checkout. So there were two policies, not one, keyed by call site.

// Composition rules that make the policies predictable:
// 1. One overall deadline per call, as a linked token, so no stage can outlive the UI budget.
// 2. Per-attempt timeouts inside the retry, shorter than the deadline, so a retry can actually happen.
// 3. Distinguish "our deadline", "attempt timeout" and "client left" in the catch, or the metrics lie.
public async Task<Price> GetPriceAsync(Sku sku, CancellationToken clientCt)
{
    using var deadline = CancellationTokenSource.CreateLinkedTokenSource(clientCt);
    deadline.CancelAfter(TimeSpan.FromSeconds(2));
    try
    {
        // Attempt timeout via Task.WaitAsync (.NET 6+); the token cancels the underlying call.
        return await _pipeline.ExecuteAsync(
            async ct => await _provider.QuoteAsync(sku, ct).WaitAsync(TimeSpan.FromMilliseconds(700), ct),
            deadline.Token);
    }
    catch (OperationCanceledException) when (clientCt.IsCancellationRequested) { throw; }            // client left: propagate
    catch (OperationCanceledException) { _metrics.DeadlineExceeded(); return await _cache.StaleAsync(sku); }
    catch (TimeoutException) { _metrics.AttemptTimeout(); return await _cache.StaleAsync(sku); }   // from WaitAsync
}

// Checkout variant: Polly v8 hedging (Microsoft.Extensions.Http.Resilience / Polly.Core), same deadline,
// secondary attempt to the backup region after 500 ms, max 1 hedge so the budget doubles at most once.
var checkoutPipeline = new ResiliencePipelineBuilder<Price>()
    .AddHedging(new HedgingStrategyOptions<Price> { MaxHedgedAttempts = 1, Delay = TimeSpan.FromMilliseconds(500),
        ActionGenerator = args => () => _backup.QuoteAsync(args.PrimaryContext, args.ActionContext.CancellationToken) })
    .Build();

Two .NET specifics carried the design. Task.WaitAsync(timeout, ct) (.NET 6) gives a per-attempt timeout that throws TimeoutException and, crucially, is distinct from cancellation, so the catch blocks can tell them apart; before .NET 6 people used Task.WhenAny(task, Task.Delay(...)), which leaves the original task running and its exception unobserved. And HttpClient's own Timeout since .NET 5 surfaces as a TaskCanceledException whose inner exception is a TimeoutException, which is how you tell it from a client disconnect without guessing. Hedging is not a retry: the second request starts while the first is still running, so the provider's per-call billing doubles, which is why it was limited to the checkout page and to one hedge.

The result was two documented policies, a metrics split (deadline exceeded / attempt timeout / hedge fired / stale served) that let the PM see the trade-offs in numbers, and a p99 for checkout pricing that went from 3.4 seconds to 1.1 with a 9% increase in provider cost, which they signed off on knowingly. What I would do differently: I should have asked for the decision table at requirement two, not five. Each "small addition" to a timeout policy is a new branch in a state space, and the moment there were two interacting timers, the ambiguity was structural, not editorial.

14The vendor SDK with callbacks: bridging to Task

SeniorCross-team / integration dependency

(a) Worked example EXAMPLE — replace with your own

We integrated a hardware vendor's device SDK that had been designed in about 2009 and never revisited: you call BeginRead(handle, callback), the callback fires on the vendor's own internal thread with the result, and errors arrive as a separate OnError event that may fire instead of, or in addition to, the callback. There was also a sync Read(handle) that blocked the calling thread for up to 30 seconds on a slow device. The integration team on the vendor's side was two people in another time zone, changes took a quarter, and we had a month. The dependency was the constraint; the bridge I built was the work.

The right tool for turning a callback into a Task is TaskCompletionSource<T>, and the two decisions that make a bridge production-grade are what happens when the callback never comes and what thread the continuation runs on. For the second: a TaskCompletionSource created with default options runs the awaiting continuation synchronously inside SetResult, on the thread that called it. That thread was the vendor's internal reader thread, so without care our whole request pipeline after the await would have executed on the vendor's thread, blocking their reader loop and, when our code eventually blocked on their next call, deadlocking. TaskCreationOptions.RunContinuationsAsynchronously (.NET 4.6) forces the continuation onto the thread pool, which is the setting every bridge should use unless it has measured a reason not to. For the first: the token registration cancels the TaskCompletionSource (TrySetCanceled), and both the callback and the error event use the Try variants so that whichever arrives second is a no-op rather than an InvalidOperationException.

public Task<Reading> ReadAsync(DeviceHandle h, CancellationToken ct)
{
    var tcs = new TaskCompletionSource<Reading>(TaskCreationOptions.RunContinuationsAsynchronously);

    // Whichever of these fires first wins; the others become no-ops via Try*.
    void OnError(object? s, DeviceErrorEventArgs e) { if (e.Handle == h) tcs.TrySetException(new DeviceException(e)); }
    _sdk.Error += OnError;

    var reg = ct.Register(static state => ((TaskCompletionSource<Reading>)state!).TrySetCanceled(), tcs);

    try
    {
        _sdk.BeginRead(h, r => tcs.TrySetResult(Map(r)));     // callback on the vendor's thread
    }
    catch (Exception ex) { tcs.TrySetException(ex); }        // synchronous failure path

    // Detach everything when the task settles, whatever way it settled.
    return tcs.Task.ContinueWith(t => { reg.Dispose(); _sdk.Error -= OnError; return t; },
        CancellationToken.None, TaskContinuationOptions.ExecuteSynchronously, TaskScheduler.Default).Unwrap();
}

Two more integration facts shaped it. The SDK's callback thread must never be blocked, so the bridge does nothing on it but complete the TCS. And cancellation of a TaskCompletionSource does not cancel the device read; the vendor kept reading for up to 30 seconds and would call our callback into a completed TCS, which is why the Try variants are not optional. For the legacy sync Read we did not build a bridge at all: Task.Run(() => _sdk.Read(h)) would have burned a pool thread for 30 seconds per device; instead reads went through a dedicated thread per device (TaskCreationOptions.LongRunning loop consuming a Channel of requests), so the number of blocked threads was bounded by the number of devices, which was known.

The cross-team part was mostly about making the constraint visible: I wrote up the three behaviours we needed from the SDK (a token-aware async API, a single completion path, a documented callback thread) as a request with a business reason, sent it to the vendor with our bridge attached as evidence of the pain, and then treated their response as a next-year improvement rather than a blocker. What I would do differently: the ContinueWith cleanup is clever and a little ugly; the pattern the BCL itself moved to is a custom awaitable via IValueTaskSource for hot paths, or simply an async wrapper with a try/finally around await tcs.Task, which reads better and is what I would write today. I also should have load-tested with the error event and the callback both firing, which is where the second bug was found in production.

The reasons were all consequences of how async continuations are scheduled, and I should have known most of them in week one. Why does an await ignore TaskScheduler.Current?

Because the awaiter for a Task captures the current SynchronizationContext if there is one, otherwise the current TaskScheduler only if it is not the default; on a server there is no context and the scheduler is the default, so continuations go straight to the thread pool through the fast path. That is deliberate: it makes async code cheap and predictable on servers. A custom scheduler therefore only sees work explicitly started on it, and priority for continuations requires a context, which every well-behaved library escapes with ConfigureAwait(false).

What if you had banned ConfigureAwait(false) in the codebase to keep continuations on your scheduler?

Then our code would have stayed on the scheduler and every dependency (drivers, HTTP client, serializers) still would not, because their internals use it. And we would have made every await a Post to a custom context, with the per-await cost and the deadlock risk that story 03 exists to avoid. Fighting the platform's scheduling model with policy is a sign the lever is wrong.

When interactive and bulk work compete for something admission does not cover, like a shared database or a shared cache, at which point the isolation has to move to those resources (separate pools, separate replicas), or when the interactive path itself is the contention (then you are just under-provisioned). In-process limiters bound what one process does; they do not protect shared infrastructure from many processes, which is why the heaviest jobs went to a separate deployment where cgroup limits are the admission control.

The 30% the scheduler did deliver in the benchmark, temporarily, and a quarter of two engineers' work, permanently. What we got back was a simpler system that beat it and an org that saw a principal kill their own project on evidence, which I think was worth more than the number. I also traded the belief that scheduling is the lever for latency isolation; in async systems admission is.

When is a custom TaskScheduler the right tool?

For CPU-bound parallel work whose degree you need to cap independently of the pool (ConcurrentExclusiveSchedulerPair does this out of the box), for a single-threaded apartment or an actor-style component where everything on it must run one at a time, and for testing (a deterministic scheduler). Not for prioritising async I/O-bound work in a server, which is what we tried.

16Streaming the export: 80% less memory

SeniorCost-optimisation win

(a) Worked example EXAMPLE — replace with your own

The export endpoint let customers download their full transaction history as JSON, and it was the reason the API tier ran on 8 GB pods when everything else would have been happy with 2 GB. The implementation was the natural one: var rows = await _db.Transactions.Where(...).ToListAsync(ct); return Ok(rows);. For a large tenant that was 1.2 million rows, about 900 MB of entity objects, then a second copy as the serialised response buffered by the framework before the first byte went out. Two simultaneous large exports and a pod went into GC death spirals; the platform team's answer had been bigger pods, which cost about 3,000 a month more than the 2 GB size across the fleet. My proposal was to stream, and the numbers made it a cost story rather than a performance one.

The technical core is that IAsyncEnumerable<T> is a pull-based stream and, since .NET 6, ASP.NET Core serialises an IAsyncEnumerable<T> return value incrementally with System.Text.Json instead of buffering it (in .NET Core 3.x and .NET 5, MVC buffered async enumerables into a list first, so this story would not have worked there). EF Core's AsAsyncEnumerable() gives a query result as a stream that materialises one entity at a time as the reader advances, and with AsNoTracking() the change tracker does not hold on to them. So the chain becomes: database reader → one entity → one JSON object on the wire → next row, and the memory in flight is one row plus the response buffer, regardless of the tenant's size.

app.MapGet("/export", (ExportQuery q, AppDbContext db, CancellationToken ct) =>
    db.Transactions
      .AsNoTracking()
      .Where(t => t.TenantId == q.TenantId && t.At >= q.From)
      .OrderBy(t => t.At)
      .Select(t => new ExportRow(t.Id, t.At, t.Amount, t.Currency))   // project early: fewer bytes, no entity
      .AsAsyncEnumerable());                                            // .NET 6+ streams this as JSON

// If shaping is needed, it stays a stream: the token flows via [EnumeratorCancellation].
static async IAsyncEnumerable<ExportRow> WithRunningBalance(
    IAsyncEnumerable<ExportRow> rows, [EnumeratorCancellation] CancellationToken ct = default)
{
    decimal balance = 0;
    await foreach (var r in rows.WithCancellation(ct).ConfigureAwait(false))
    {
        balance += r.Amount;
        yield return r with { Balance = balance };
    }
}

Three things had to be true for this to be safe, and each was a decision. First, the database connection is now held for the duration of the download rather than the duration of the query, so a slow client (mobile on a bad network) pins a connection for minutes; we bounded that with a per-tenant concurrency limit of two exports and a response write timeout, and we watched pool wait time in the dashboard for a month. Second, a failure halfway through can no longer become a 500 because the status line and half the body are already sent; the client gets a truncated JSON document. We documented that, added a trailing record with a row count and a checksum so clients can verify completeness, and made the client SDK retry on truncation. Third, cancellation: when the client disconnects, RequestAborted cancels the token, await foreach disposes the enumerator, and the EF reader is closed, which we verified with the pen-test script from story 08 because an export that keeps reading for a departed client is the same vulnerability.

Peak memory for the largest export went from about 2.1 GB to 180 MB, the pods went back to 2 GB, the fleet's monthly bill dropped by roughly the 3,000 the platform team had been paying for headroom, and the time to first byte went from 40 seconds to under 200 ms, which customers noticed more than the finance team did. What I would do differently: I initially left OrderBy out because "it's an export", and a customer's reconciliation script depended on order; streaming makes ordering the database's job and you have to ask for it. And I should have shipped the trailing checksum record in the first release rather than after the first truncated-download support ticket.

What the interviewer is really probing. Whether you can translate a technical change into money and back, and whether you understand what streaming trades: connection hold time, error semantics after the first byte, and ordering. The failure is "we used IAsyncEnumerable and memory went down" with no mention of the connection pool, truncation, or the version in which streaming actually became real (.NET 6).

(d) Follow-up drill chain

Why is IAsyncEnumerable the right shape here rather than paging?

Paging moves the cost to the client (N requests, consistent snapshots across pages, cursors) and is right for interactive UIs. An export is one logical document and the client wants it in one request; streaming keeps the single-document contract and makes memory constant. They are not exclusive: a paged API for browsing and a streamed one for export is the common pairing. The mechanism that makes streaming cheap is that the enumerator pulls one row per MoveNextAsync and the serializer writes it before pulling the next.

What if the client is slower than the database?

Then the pull model is the backpressure: the serializer only asks for the next row when the response buffer has room, so the database reader waits, which is why the connection is held for the whole download. That is the trade: constant memory for longer connection occupancy. We bounded it per tenant and set a write timeout so a stalled client releases the connection; for very slow consumers a better design writes the export to blob storage in the background and streams from there, which decouples the database from the client entirely.

At what scale does this design break?

When exports are large enough that even a bounded number of them holds too many connections for too long, or when the database's own cursor/snapshot behaviour makes a multi-minute read expensive (long-running transactions, version store growth). At that point the export becomes an asynchronous job: generate to storage with a job status endpoint, and the API streams the finished file. The streaming code is the same; the source moves from the live database to a file.

What did you trade away in error handling?

The ability to return a clean error status after the first byte. A failure at row 800,000 produces a truncated body and a 200 that was already sent, so correctness moved to the client: the trailing count-and-checksum record is how it detects truncation, and the SDK retries. That is a contract change and we versioned the endpoint for it. The alternative, buffering to guarantee all-or-nothing, was the 2.1 GB we were removing.

How does cancellation reach the database when the client disconnects?

Kestrel cancels RequestAborted; the framework's serializer loop is awaiting MoveNextAsync on the enumerable with that token; the EF Core enumerator passes it to the data reader's ReadAsync(ct), which cancels the command. Then await foreach disposes the enumerator, which closes the reader and returns the connection. Every link has to forward the token; the [EnumeratorCancellation] parameter on any shaping iterator in between is what keeps the chain unbroken, as in story 05.

(d) Follow-up drill chain

Why is dumpasync different from a thread dump for async code?

Because a suspended async method has no thread: its state lives in a heap object (the boxed state machine) whose continuation is registered on the task it awaits, so clrstack shows nothing for it. dumpasync walks those heap objects and reconstructs the logical call chain, which is the only way to see that 400 requests are waiting on one semaphore when no thread is doing anything. For blocking code you use clrstack; for awaiting code you use dumpasync; a real hang usually needs both.

What if the process is in a container with no shell or no tools?

Then the tools come from a sidecar sharing the process namespace, or from an ephemeral debug container (Kubernetes supports attaching one), or from dotnet-monitor running as a sidecar that exposes dump collection over an authenticated endpoint and can trigger dumps on counter thresholds automatically. The last is where I would go next: a dump taken when queue length crosses a threshold captures the hang without a human awake.

At what scale does taking a dump become risky?

Dump size scales with the heap: a 12 GB process makes a 12 GB file, takes longer to write, and pauses the process for that write. On a pod serving live traffic that pause is an outage in miniature, so for large heaps you take a dump from one pod that has been pulled from the load balancer, or rely on dotnet-stack and counters first. Memory pressure during the write can also get the pod OOM-killed if limits are tight, which we hit once and fixed with a dedicated volume.

How does .NET 11 runtime async change what a dump looks like?

With runtime async enabled, suspended methods are represented by runtime continuation objects rather than compiler-generated state machines, and live stack traces show the real method chain without MoveNext and builder frames, so clrstack output becomes readable in a way it never was. The diagnostics tooling is being updated to walk the runtime's continuations the way dumpasync walks state machines (the async profiler instruments both models already); until that is verified on a GA runtime I would keep the runbook's expectations on the .NET 10 model.

By making the practice part of on-call onboarding and by giving them a win: each person found a planted hang in the clinic in under fifteen minutes, which turned "scary low-level tool" into "the thing that found it". Then the process rule made it the expected action rather than an optional heroic one, and the first real incident where a junior engineer found the semaphore leak from a dump did more for adoption than the clinic.

18Killing time-based flaky tests with TimeProvider

(a) Worked example EXAMPLE — replace with your own

Our CI had a "retry failed tests once" step, which is the confession that a build has flaky tests, and when I counted, 31 of about 4,000 tests failed at least once a week. All 31 were tests of asynchronous, time-dependent code: a debounce, a token-refresh timer, a retry policy with backoff, a cache with sliding expiry, a PeriodicTimer loop. They all used real time: await Task.Delay(1100) to wait for a 1-second timer, and then asserted. On a loaded CI agent the delay overshot, or the timer under-shot, and the assert raced. The tests also took 90 seconds of wall-clock for what was 20 milliseconds of logic. I took the 31 as a project, and the tool was TimeProvider (.NET 8), which is the abstraction the BCL itself uses for time.

TimeProvider is an abstract class with GetUtcNow(), GetTimestamp(), CreateTimer(...) and TimerQueue semantics, and the important part is that the BCL's async time APIs accept it: Task.Delay(TimeSpan, TimeProvider), CancellationTokenSource(TimeSpan, TimeProvider), PeriodicTimer(TimeSpan, TimeProvider), Task.WaitAsync(TimeSpan, TimeProvider). TimeProvider.System is the real clock; FakeTimeProvider from the Microsoft.Extensions.TimeProvider.Testing package is a controllable one where Advance(TimeSpan) moves time and fires any timers that fall due, synchronously, in order. So the test does not wait for a second to pass; it says a second has passed.

// Production code takes the provider; DI registers TimeProvider.System.
public sealed class TokenRefresher(ITokenSource source, TimeProvider clock)
{
    public async Task RunAsync(CancellationToken ct)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5), clock);
        while (await timer.WaitForNextTickAsync(ct))
            await source.RefreshAsync(ct);
    }
}

// Test: no real waiting, deterministic ordering.
[Fact]
public async Task Refreshes_every_five_minutes()
{
    var clock = new FakeTimeProvider();
    var source = new CountingTokenSource();
    var sut = new TokenRefresher(source, clock);
    using var cts = new CancellationTokenSource();

    var run = sut.RunAsync(cts.Token);
    clock.Advance(TimeSpan.FromMinutes(5));      // tick 1 fires and its continuation is scheduled
    await source.WaitForCallsAsync(1);           // let the async continuation actually run
    clock.Advance(TimeSpan.FromMinutes(5));
    await source.WaitForCallsAsync(2);

    cts.Cancel();
    await run.ContinueWith(_ => { }, TaskScheduler.Default);   // observe completion without rethrowing the cancel
    Assert.Equal(2, source.Calls);
}

The subtle part, and the reason two of the 31 stayed flaky after the first pass, is that advancing the fake clock fires the timer callback, which completes a task, but the continuation of the code awaiting that task runs asynchronously on the thread pool. Asserting immediately after Advance races with that continuation. The test has to wait for an observable effect (a counting stub with a TaskCompletionSource, as above) rather than for time. That is not a limitation of the fake; it is the same fact from story 10: the code after an await runs later, on another thread, and a test must synchronise on the effect, not on the clock. Once the team understood that, the pattern was mechanical: inject TimeProvider, use FakeTimeProvider, advance, await the effect, assert.

All 31 tests became deterministic, the suite's wall-clock dropped by 85 seconds, and the "retry once" step was removed from CI three weeks later, which is the result I actually wanted, because a retry step hides every future flaky test too. The production code got better as a side effect: three classes that had been constructing timers internally now took a TimeProvider, which also made their behaviour on clock changes testable. What I would do differently: I hand-wrote the counting stubs per test; a small shared helper that wraps "advance, then await this effect with a timeout" would have made the pattern harder to get wrong. And I would have used xUnit v3's TestContext.Current.CancellationToken from the start so that a test that hangs on a missed effect is cancelled by the runner rather than by the CI timeout.

Why does advancing the fake clock not make the test deterministic on its own?

Because Advance runs the timer callback, and the callback completes a task, but the code awaiting that task is a continuation that the runtime schedules on the thread pool; it has not run yet when Advance returns. The test must therefore wait for the effect of that continuation, which means the stub exposes a signal (a TaskCompletionSource per expected call). Time is fake; scheduling is still real.

What if the code under test uses DateTime.UtcNow or Stopwatch directly?

Then it is not testable without a seam, and the refactor is to take a TimeProvider and call GetUtcNow()/GetTimestamp() on it, which the BCL's own Stopwatch-style APIs now support (TimeProvider.GetElapsedTime). Before .NET 8 people wrote their own IClock; the value of TimeProvider is that Task.Delay, PeriodicTimer and CancellationTokenSource accept it, so the seam reaches into the runtime's timers rather than stopping at your code.

At what scale does this approach break?

When the test needs to reason about real concurrency between multiple timers and pool threads, a fake clock that fires callbacks synchronously in Advance serialises things that would overlap in production, so the test can pass while the code races. For those cases you want a targeted concurrency test (with a barrier or a deterministic scheduler) or a load test, not a clock. The fake is for logic that depends on when, not on interleaving.

What did you trade away?

A constructor parameter on every time-dependent class and a DI registration, which some people saw as ceremony, and the small risk that a test's fake ordering does not match production's. We accepted both because the alternative was 90 seconds of sleeping tests that still failed weekly, and because the ceremony is the BCL's own convention now. The one place we kept real time is an integration test of the actual PeriodicTimer against the system clock, tagged slow.

How does runner-level cancellation help, and what changed in xUnit v3?

A test that awaits an effect that never comes hangs until the CI job's timeout, which wastes forty minutes and hides which test hung. xUnit v3 exposes TestContext.Current.CancellationToken, which the runner cancels on timeout or when the run is aborted, so the awaiting helper takes that token and the failure is attributed to the right test with a clean OperationCanceledException. It is the same principle as production: every wait takes a token from whoever owns the lifetime.

(a) Worked example EXAMPLE — replace with your own

The page said "notification-worker: readiness probe failing, 0/6 ready" at 03:10, twenty minutes after a routine deploy had rolled out cleanly and then, apparently, done nothing. Nothing in the logs after "Application started" except, on inspection, that line was missing too: the last log line was from a hosted service saying it was "warming cache". The pods were alive, CPU near zero, memory flat. No crash loop, no exceptions. A deploy rollback fixed it, so the firefighting question at 03:15 was "roll back and go to bed" versus "understand it first", and I chose thirty minutes of understanding because a rollback that fixes a symptom you cannot explain will page you again.

The change in the deploy was innocent-looking: a new BackgroundService that pre-warmed a template cache from blob storage before the notification loop started. Its ExecuteAsync began with a synchronous loop over 4,000 templates calling a synchronous parsing method, about 40 seconds of CPU, before its first await. The generic host starts hosted services in registration order, and BackgroundService.StartAsync calls ExecuteAsync and returns only when ExecuteAsync returns or hits its first incomplete await (story 10's "runs synchronously until the first await"). If ExecuteAsync does 40 seconds of synchronous work, StartAsync takes 40 seconds, the next hosted service does not start until then, and the host is not "started" until all of them have, so Kestrel's readiness endpoint was not listening yet. The readiness probe's failure threshold was 30 seconds. Six pods, each taking 40 seconds to start, each killed at 30 and restarted, forever, with no exception because nothing was wrong except timing.

// The 03:10 version: synchronous prefix blocks host startup (StartAsync returns at the first incomplete await).
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    foreach (var t in _store.ListTemplates())        // sync, 40 s of CPU before any await
        _cache[t.Id] = TemplateParser.Parse(t);
    await RunLoopAsync(stoppingToken);
}

// The 03:40 version: yield first so StartAsync returns immediately; then do the work async and cancellable.
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    await Task.Yield();                                  // or: await Task.Delay(0)? No: Delay(0) completes synchronously. Yield does not.
    await foreach (var t in _store.ListTemplatesAsync(stoppingToken))
        _cache[t.Id] = await TemplateParser.ParseAsync(t, stoppingToken);
    _ready.MarkWarm();                                   // readiness reports "warm" separately from "listening"
    await RunLoopAsync(stoppingToken);
}

The mechanism is documented and well known, and it still catches people because the code is "async" and looks fine. await Task.Yield() is the idiomatic first line of an ExecuteAsync that may do real work before its first genuine await: it always suspends and re-queues the continuation, so StartAsync returns at once. The .NET 8 host also added HostOptions.ServicesStartConcurrently, which starts hosted services in parallel and would have hidden this particular ordering problem while leaving the 40-second synchronous block in place, so I did not reach for it. And there is a related trap from the other direction: since .NET 6 an unhandled exception in ExecuteAsync stops the host by default (BackgroundServiceExceptionBehavior.StopHost), which is why a worker that throws on startup crash-loops; this one did not throw, which is exactly why it was confusing.

At 03:45 the fix was three lines and a redeploy; at 09:00 the follow-ups were a startup probe (Kubernetes distinguishes startup from readiness precisely so slow warm-ups do not get killed), a readiness endpoint that reports "listening" and "warm" as separate facts, and an analyzer-free but reviewable rule: an ExecuteAsync starts with await Task.Yield() unless its first statement is an await that will actually suspend. What I would do differently: my first fifteen minutes went to blob storage permissions because the log said "warming cache" and the cache came from blob storage. Reading the code of the thing that had changed in the deploy would have been faster than reading the logs of the thing it talked to. (d) Follow-up drill chain

Why does await Task.Yield() fix it and await Task.Delay(0) not?

Task.Delay(0) returns an already-completed task, so the await continues synchronously without ever suspending; the sync prefix is still there. Task.Yield() returns an awaitable whose IsCompleted is always false, so the state machine always suspends, queues its continuation to the pool (or the current context) and returns to StartAsync. In .NET 8+ ConfigureAwait(ConfigureAwaitOptions.ForceYielding) on a completed task does the same with context control.

What if the warm-up must finish before the service handles any message?

Then the ordering is a readiness concern, not a startup-blocking one: the service starts, warms asynchronously, and reports not-ready until warm; the message loop waits on a warm signal (a TaskCompletionSource or the same readiness object). Kubernetes's startup probe gives the warm-up its own, longer budget so readiness failure during warm-up does not kill the pod. Blocking StartAsync to force the order works only until the warm-up takes longer than any probe.

Why not just enable ServicesStartConcurrently?

It would have let the other hosted services start while this one blocked, so the app might have come up, but the 40 seconds of synchronous CPU would still have happened on a pool thread during startup, and the readiness question would have been hidden rather than answered. Concurrent start is a good option when services are independent and slow for legitimate async reasons; it is not a fix for a synchronous prefix.

How does the .NET 6 exception behaviour interact with this?

If the warm-up had thrown, BackgroundServiceExceptionBehavior.StopHost would have logged a critical error and stopped the host, and the crash loop would have had a stack trace, which is the better failure. Setting it to Ignore to "keep the app up" turns a visible crash into a silent dead worker, which is worse; I leave the default and make the worker's failure loud. The silent case we hit is the one the default cannot help with, because nothing threw.

At what point do you stop diagnosing at 3 a.m. and roll back?

My rule: roll back immediately if there is customer impact and the rollback is safe (no schema change, no queue format change), then spend a bounded window, thirty minutes, on the "why" while the system is stable, because the evidence (pods in that state, the dump you can take) will be gone by morning. If there is no rollback, or the rollback is the risk, the window is for mitigation and the why waits. The thing I refuse is "rolled back, went to bed, no ticket".

(a) Worked example EXAMPLE — replace with your own

After two starvation incidents (story 01 was the first), an engineering director who had read a blog post came to me with a directive: set ThreadPool.SetMinThreads(1000, 1000) across every service as a platform default, and, separately, turn on the .NET 10 runtime-async experiment in production "since Microsoft says it removes the state machine overhead". Both were framed as decisions already made; my job was to implement. I disagreed with both, for different reasons, and the story is about pushing back on someone senior in a way that changed the decision rather than the relationship.

On min threads, the argument was mechanical and I made it with a graph rather than a paragraph. The minimum is the count the pool will inject to without hill-climbing delay; above it, injection is throttled. Raising it to 1000 means any blocking storm gets up to 1000 threads within seconds, which is why it works as an incident mitigation. As a fleet default it does three things I could show: it reserves stack (1000 × 1 MB of virtual, committed lazily, but under a real storm the pages get touched), it turns a starvation that would have been visible in ten seconds into a slow degradation that looks like a latency problem, so the blocking code never gets found, and it lets a single blocking regression consume 1000 database connections or sockets before anything pushes back. I took the dump from incident one, replayed the same blocking library under a load test with min threads at 4 and at 1000, and showed the second run "succeeded" while opening 640 connections to a database whose pool was 100 per pod; the failure had moved from our service to the database, where it would have taken every other service with it. The director's real goal was "no more starvation pages"; the mechanism that serves it is finding blocking code (the ratchet from story 09, the queue-length alert from story 01), with a min-threads override as a documented, expiring incident tool.

It is not something to switch on in a production LTS fleet in response to an incident that runtime async would not have prevented, because starvation is about blocking, and blocking is orthogonal to how the state machine is implemented.

The decision changed in the meeting; the director later used the min-threads graph in their own presentation, which is the outcome you want from a disagreement with someone above you. The failure is either compliance ("I implemented it and it went badly") or a story about being right without the mechanics of how you changed the decision. At principal tier, the answer includes the org-level replacement (alerts, ratchet, canary plan), not just the "no".

(d) Follow-up drill chain

Why is a high min-threads default worse than leaving the pool alone?

Because it removes the pool's only signal that something is blocking, and moves the failure to whatever the extra threads consume: connections, sockets, downstream capacity. The pool's slow injection is a feature in the sense that it makes starvation visible fast; a fleet-wide 1000 turns every blocking regression into a slow bleed that gets blamed on the database. The place for a high minimum is a specific service with a known, bounded blocking dependency, with the number derived from that dependency's concurrency and written down.

What if the director had insisted?

Then I would have asked for the decision to be recorded with the trade-offs I had shown, applied it to one service as a canary with the connection-count graph on a dashboard, and set a review date. Disagree, commit, and make the outcome measurable; not sabotage, not silence. In practice showing the failure moving to the database was enough, because that was a failure the director would own in front of other teams.

At what scale does runtime async matter enough to plan for?

For async-heavy services where state-machine allocation and continuation overhead show up in profiles (high-RPS APIs, streaming pipelines), the .NET 11 preview numbers suggest measurable allocation and throughput wins, and the debugging improvement (real call chains in live stack traces) is valuable everywhere. The plan is to have a canary result before GA so adoption is a known quantity, and to keep the per-project opt-out ready. What it does not change is any behaviour rule in this page: blocking still starves, ValueTask still has its contract, cancellation still has to reach the leaf.

What did you trade away?

Speed of a visible response: the director wanted something done that week, and my alternative delivered its first artefact (the alert) in a week and the ratchet in a month, so I spent political capital on "slower but right". I also conceded the min-threads override as a sanctioned incident tool, which some engineers saw as legitimising the hack; the expiry ticket and the connection-count graph are the guardrails that make that concession safe.

How do you keep this from becoming "the principal says no to everything"?

By always leaving the meeting with a yes to something: the alert, the ratchet, the canary, each with a date and an owner, and by giving the director the evidence to present as their own decision. A pushback that only removes an option is a veto; one that replaces it with a better path to the same goal is engineering leadership. The record of the second kind is what makes the next pushback credible.

22Night-before cheat sheet

delivery
  1. Lead with the situation in one line. "Fourteen pods, p99 from 80 ms to 9 s in three minutes, CPU at 15%." Numbers first; the interviewer can steer from there.
  2. Name the mechanism in one sentence before the fix. "The blocked thread was waiting for a continuation that needed the thread it was blocking." If you can say the mechanism, every follow-up has somewhere to go.
  3. Quantify the result, and say what it cost. Gen0 90 → 30, plus "callers lost the freedom to await twice." A result with a cost is believed; a free win is not.
  4. Own the "what I'd do differently" without being asked. The override left in for four months, the day of logging before the dump. It is the most credible part of the story; volunteer it.
  5. Separate "I" from "we" honestly. "I ran the incident; the library team did the migration; I did the two hard call sites myself." Solo credit for team work is the fastest way to lose a behavioural interview.
  6. Tie every technical decision back to the async trade-off it turned on. Context capture versus context freedom (03), ValueTask speed versus caller contract (02), bounded concurrency versus throughput headroom (07), cancellation reach versus partial-state risk (08).
  7. Be version-precise once per story, not constantly. One "since .NET 6 the serializer streams IAsyncEnumerable" or "ConfigureAwaitOptions is .NET 8" per story signals currency; more sounds like recitation.
  8. Keep .NET 11 in its box. Runtime async is a preview, opt-in, per project, with the environment switch gone; it changes machinery, not the rules. Say exactly that and stop.
  9. Pick the altitude for the level. Mid: I found it and fixed it. Senior: I ran it and fixed the class. Staff/Principal: I changed how the org prevents it, and here is the number a year later.
  10. When a follow-up lands outside your rehearsal, reason from the mechanism aloud. "A custom scheduler only sees work started on it; an await goes to the pool; so..." Thinking visibly from first principles is the point of the drill chains.
  11. Have the "at what scale does this break" answer ready for every story. Async frees threads, not connections; limiters bound one process, not a fleet; streaming trades memory for connection time. If you know where it breaks, you know it works.
  12. End each story with the signal that would tell you if it came back. Queue-length alert, ratchet count, chaos test, the 499/500 split. "Done" includes the detector.
