C# async/await

cheatsheet · .NET 10.0.11 (C# 14) · released 2026-08-11

Everything reached for when writing asynchronous C#: the syntax, the Task and ValueTask surface, cancellation, async streams, ConfigureAwait, thread-pool behaviour and the diagnostic commands, with each row labelled by the version where it became true. It reflects .NET 10 (LTS, GA 2025-11-11; current patch 10.0.11, 2026-08-11) with C# 14. Anything marked .NET 11 is preview today and ships 2026-11-10, so read it as direction, not as something to deploy.

01Syntax essentials

docs: asynchronous programming in C#
Async method
public async Task<Order> GetAsync(int id, CancellationToken ct = default)
Legal return types
Task, Task<T>, ValueTask, ValueTask<T>, IAsyncEnumerable<T>, void (event handlers only), any type with [AsyncMethodBuilder]
Await
var o = await GetAsync(id, ct); — unwraps the result, rethrows the first exception un-aggregated
Entry point
static async Task Main(string[] a) C# 7.1; top-level statements just await directly
Async lambda / local fn
Func<CancellationToken, Task<int>> f = async ct => await GetAsync(ct); · async Task<int> LocalAsync() => ...
Async disposal
await using var conn = new SqlConnection(cs); C# 8 — needs IAsyncDisposable; plain using silently takes the sync path
Async stream, consume
await foreach (var row in src.WithCancellation(ct).ConfigureAwait(false)) { ... }
Async stream, produce
async IAsyncEnumerable<T> ReadAsync([EnumeratorCancellation] CancellationToken ct) + yield return
Awaitable contract
any type exposing GetAwaiter() whose result has bool IsCompleted, GetResult() and INotifyCompletion — that is all await requires
Yield the current thread
await Task.Yield(); — forces an asynchronous continuation; never a substitute for real async I/O
Custom state machine
[AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))] on a method C# 10 or on a type C# 7
ref / unsafe in async
ref locals and unsafe blocks are allowed inside async methods and iterators C# 13 — but never live across an await
await inside lock
compile error, always. With System.Threading.Lock .NET 9 the compiler also rejects await in the block; use SemaphoreSlim(1, 1).WaitAsync(ct)
// The shape 95% of production async methods take.
public async Task<Order> GetOrderAsync(int id, CancellationToken ct = default)
{
    await using var conn = await _factory.OpenAsync(ct);            // IAsyncDisposable
    var dto = await conn.QuerySingleAsync<OrderDto>(Sql, ct)
                        .ConfigureAwait(false);                     // library code
    return Map(dto);
}

// Async iterator: the token must be marked, or WithCancellation(ct) is silently ignored.
public async IAsyncEnumerable<Order> StreamAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await foreach (var dto in _repo.ReadAllAsync(ct))
        yield return Map(dto);
}

02Task API

docs: System.Threading.Tasks.Task
Offload CPU work
await Task.Run(() => Hash(bytes), ct); — never to make sync I/O "async"
Already-finished results
Task.CompletedTask · Task.FromResult(v) · Task.FromException(ex) · Task.FromCanceled(ct)
Fan out, wait for all
var results = await Task.WhenAll(ids.Select(i => GetAsync(i, ct)));
First to finish
var done = await Task.WhenAny(a, b); — the losers keep running; observe or cancel them
Process as they finish
await foreach (var t in Task.WhenEach(tasks)) Handle(await t); .NET 9
Timeout / external cancel
await task.WaitAsync(TimeSpan.FromSeconds(5), ct); .NET 6 — throws TimeoutException on the timeout, OperationCanceledException on the token
Delay
await Task.Delay(delay, timeProvider, ct); .NET 8 — the TimeProvider overload is the testable one
Bridge a callback / event
new TaskCompletionSource<T>(TaskCreationOptions.RunContinuationsAsynchronously) — the flag is not optional; without it the continuation runs on whoever calls SetResult
Non-generic TCS
new TaskCompletionSource(...) .NET 5 — before that, TaskCompletionSource<bool>
Inspect state
t.IsCompletedSuccessfully / IsFaulted / IsCanceled · t.Exception is an AggregateException
Flatten Task<Task>
Task.Factory.StartNew(async () => ...).Unwrap() — the reason Task.Run exists; prefer it
Legacy continuation
t.ContinueWith(x => ..., TaskScheduler.Default) — pre-await; the scheduler argument is mandatory in practice, the default is TaskScheduler.Current
Blocking (avoid)
t.Result, t.Wait(), Task.WaitAll, t.GetAwaiter().GetResult() — last one at least rethrows un-aggregated
// WhenAll surfaces only the FIRST exception on await. Grab the rest from the task.
var all = Task.WhenAll(tasks);
try { await all; }
catch { throw all.Exception!; }                 // AggregateException with every failure

// Streaming completion: react to the fastest replies without waiting for the slowest.
await foreach (var finished in Task.WhenEach(tasks).WithCancellation(ct))   // .NET 9
    await WriteAsync(await finished, ct);

// Timeout without leaking the Task.Delay timer (the pre-.NET 6 WhenAny dance did).
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
var page = await FetchAsync(url, cts.Token).WaitAsync(TimeSpan.FromSeconds(2), ct);

03ValueTask

docs: ValueTask<TResult> · whys, whats and whens
Use it when
the method is hot and usually completes synchronously (cache hit, buffered read) and you measured. Otherwise return Task: it is cacheable, awaitable many times, and cheaper to reason about
The three rules
await it once; never .Result unless IsCompletedSuccessfully; never await the same instance concurrently. Breaking these is undefined behaviour, not an exception you can catch reliably
Store or await twice
Task<T> t = vt.AsTask(); or ValueTask<T> v = vt.Preserve();
Construct
ValueTask.CompletedTask · ValueTask.FromResult(v) · new ValueTask<T>(cached) · new ValueTask<T>(source, token)
Custom backing source
ManualResetValueTaskSourceCore<T> behind IValueTaskSource<T> .NET Core 2.1 — how Socket, Channel and PipeReader allocate zero per operation
Pool the state machine
[AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))] .NET 6, or process-wide DOTNET_SYSTEM_THREADING_POOLASYNCVALUETASKS=1 .NET 5
Sync fast path
if (vt.IsCompletedSuccessfully) return vt.Result; — the whole point: no Task allocation, no state machine box
Analyzer
CA2012: Use ValueTasks correctly catches the double-await and stored-ValueTask mistakes at build time
Interface design
a ValueTask-returning interface method forces every implementer into the contract; public library APIs usually stay on Task
.NET 11
the JIT recognises Task.FromResult, Task.CompletedTask and ValueTask.FromResult as intrinsics and folds them into faster runtime-async paths
// Canonical cache read: synchronous 99% of the time, no allocation on that path.
public ValueTask<Order> GetAsync(int id, CancellationToken ct)
    => _cache.TryGetValue(id, out var o)
        ? new ValueTask<Order>(o)
        : new ValueTask<Order>(LoadAsync(id, ct));   // Task<Order>, wrapped

// WRONG - awaited twice, and stored in a field. Both are undefined behaviour.
var vt = GetAsync(1, ct);
var a = await vt;
var b = await vt;                                    // CA2012

04Cancellation

docs: cancellation in managed threads
Signature convention
CancellationToken ct is the last parameter, = default only on public entry points; CA2016 flags the ones you forgot to forward
Source with a deadline
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30)); · later cts.CancelAfter(delay)
Cancel and drain callbacks
await cts.CancelAsync(); .NET 8 — Cancel() runs registrations synchronously on the caller's thread
Combine tokens
using var linked = CancellationTokenSource.CreateLinkedTokenSource(ct, timeoutCts.Token); — must be disposed or it stays registered on the parents
Check
ct.ThrowIfCancellationRequested(); at loop tops · ct.IsCancellationRequested when you need to clean up first
Callback on cancel
using var reg = ct.Register(static s => ((Socket)s!).Dispose(), socket); — dispose the registration; long-lived tokens leak every un-disposed one
Wait on a task
await task.WaitAsync(ct); .NET 6 — abandons the wait, does not cancel the work
Catch precisely
catch (OperationCanceledException) when (ct.IsCancellationRequested) — separates "the caller gave up" from "my internal timeout fired"
Cooperative only
nothing preempts; a token that nobody polls or passes down does nothing. There is no Thread.Abort
ASP.NET Core sources
HttpContext.RequestAborted (client disconnected) · BackgroundService.ExecuteAsync(stoppingToken) · IHostApplicationLifetime.ApplicationStopping
Never-cancels token
CancellationToken.None — identical to default, but says it on purpose
Testable timeouts
TimeProvider .NET 8 + FakeTimeProvider from Microsoft.Extensions.TimeProvider.Testing; timeProvider.CreateCancellationTokenSource(delay)
Timeouts as policy
HttpClient.Timeout is per-request and surfaces as TaskCanceledException; Microsoft.Extensions.Http.Resilience gives per-attempt timeouts with the token wired through
// Caller's token + our own SLA, distinguished in the catch.
using var timeout = new CancellationTokenSource(TimeSpan.FromSeconds(2));
using var linked  = CancellationTokenSource.CreateLinkedTokenSource(ct, timeout.Token);
try
{
    return await _client.GetAsync(url, linked.Token);
}
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    throw;                                  // caller went away: propagate
}
catch (OperationCanceledException)
{
    return Fallback;                        // our 2s budget blew: degrade
}

05Async streams & channels

docs: async streams · channels
Produce
async IAsyncEnumerable<T> ReadAsync([EnumeratorCancellation] CancellationToken ct) .NET Core 3.0 / C# 8
Consume with a token
await foreach (var x in src.WithCancellation(ct)) ... — no-op unless the producer marked its parameter
Consume in a library
await foreach (var x in src.WithCancellation(ct).ConfigureAwait(false)) ...
LINQ over the stream
await src.Where(x => x.Ok).Select(Map).Take(100).ToListAsync(ct) — in-box System.Linq.AsyncEnumerable .NET 10
Upgrade trap
the in-box operators collide with the System.Linq.Async (Ix) package: drop that reference, or move to Ix 7.0.0; when multi-targeting, reference the System.Linq.AsyncEnumerable NuGet package instead
New joins
AsyncEnumerable.FullJoin plus tuple-returning Join/GroupJoin .NET 11
Bounded queue
Channel.CreateBounded<T>(new BoundedChannelOptions(1000) { FullMode = BoundedChannelFullMode.Wait, SingleReader = true })
Channel read loop
await foreach (var item in ch.Reader.ReadAllAsync(ct)) ... · producer ends with ch.Writer.Complete()
Bounded parallel I/O
await Parallel.ForEachAsync(urls, new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct }, FetchAsync); .NET 6
Periodic work
while (await timer.WaitForNextTickAsync(ct)) ... with new PeriodicTimer(TimeSpan.FromSeconds(5)) .NET 6 — no overlap, no timer captures
Throttle
await _gate.WaitAsync(ct); try { ... } finally { _gate.Release(); } with SemaphoreSlim(8); rate limits via System.Threading.RateLimiting .NET 7
Stream JSON
JsonSerializer.DeserializeAsyncEnumerable<T>(stream, ct); .NET 10 adds PipeReader/PipeWriter overloads, .NET 11 adds NDJSON top-level output
Return from ASP.NET Core
an action returning IAsyncEnumerable<T> streams the response; combine with HttpContext.RequestAborted
// Producer/consumer with backpressure - the default for ingest pipelines.
var ch = Channel.CreateBounded<Event>(new BoundedChannelOptions(1_000)
{
    FullMode = BoundedChannelFullMode.Wait,   // block the producer, do not drop
    SingleReader = true, SingleWriter = false
});

var consumer = Task.Run(async () =>
{
    await foreach (var e in ch.Reader.ReadAllAsync(ct))
        await SinkAsync(e, ct);
}, ct);

await foreach (var e in SourceAsync(ct))
    await ch.Writer.WriteAsync(e, ct);
ch.Writer.Complete();
await consumer;

Ordering gotcha. await foreach is sequential by construction. To overlap, fan out into Task.WhenEach or Parallel.ForEachAsync — an await inside the loop body serialises the whole stream at the slowest item.

06ConfigureAwait & contexts

docs: ConfigureAwait FAQ · API
What await captures
SynchronizationContext.Current, else TaskScheduler.Current. If both are null (console, ASP.NET Core, most services) the continuation goes straight to the thread pool
Library default
.ConfigureAwait(false) on every await in reusable code — it is insurance against the one caller that does have a context
App code
skip it in ASP.NET Core (no context to capture); keep it in WinForms/WPF/MAUI/Blazor Server code only where you do not need the UI thread back
Options overload
await t.ConfigureAwait(ConfigureAwaitOptions.None) .NET 8 — flags: None, ContinueOnCapturedContext, SuppressThrowing, ForceYielding. Task only, not Task<T>
Await without throwing
await t.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing); — marks the exception observed; replaces t.ContinueWith(_ => { })
Always yield
ConfigureAwaitOptions.ForceYielding — continue asynchronously even when the task is already complete; the Task.Yield() semantics, composed
Streams and disposal
await foreach (var x in src.ConfigureAwait(false)) · await using (res.ConfigureAwait(false))
Enforce it
dotnet_diagnostic.CA2007.severity = warning in .editorconfig; the VSTHRD010/VSTHRD110 analyzers go further
What it does not do
it does not stop ExecutionContext flow: AsyncLocal<T>, Activity.Current and the ambient CultureInfo still cross the await
ExecutionContext
flows ambient state and is copy-on-write; suppress deliberately with ExecutionContext.SuppressFlow() or ThreadPool.UnsafeQueueUserWorkItem
Classic deadlock
UI or legacy ASP.NET thread calls .Result → context is occupied → the captured continuation can never run. One ConfigureAwait(false) missing anywhere in the chain is enough
.NET 11
continuations that have nothing to restore skip the ExecutionContext capture/restore cycle entirely — free throughput for code that uses ConfigureAwait(false) and few AsyncLocal<T> values
// Library: no assumptions about the caller's context.
public async Task<byte[]> DownloadAsync(Uri u, CancellationToken ct)
{
    using var rsp = await _http.GetAsync(u, ct).ConfigureAwait(false);
    rsp.EnsureSuccessStatusCode();
    return await rsp.Content.ReadAsByteArrayAsync(ct).ConfigureAwait(false);
}

// Await a task you do not want to throw at you (.NET 8+); the exception counts as observed.
await logTask.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);

07Thread-pool behaviour

docs: the managed thread pool · debug starvation
What await costs
zero threads while suspended. The continuation is a work item queued to the pool (or posted to the captured context) when the I/O completes
Pool sizing
worker threads start at Environment.ProcessorCount; beyond that the hill-climbing injector adds roughly 1 thread per second — so starvation looks like a latency cliff at low CPU
Starvation signature
growing ThreadPool Queue Length, thread count creeping up ~1/s, CPU well under 100%, p99 in seconds. Almost always sync-over-async somewhere
Min threads, config
System.Threading.ThreadPool.MinThreads in runtimeconfig.json, or <ThreadPoolMinThreads> in the csproj
Min threads, code
ThreadPool.SetMinThreads(workers, ioPorts); — a shock absorber for bursts, never a fix for blocking
Windows thread pool
<UseWindowsThreadPool>true</UseWindowsThreadPool> / System.Threading.ThreadPool.UseWindowsThreadPool / DOTNET_ThreadPool_UseWindowsThreadPool — not configurable under NativeAOT
Queue depth at runtime
ThreadPool.PendingWorkItemCount · ThreadPool.ThreadCount · ThreadPool.CompletedWorkItemCount
Long blocking work
Task.Factory.StartNew(Loop, TaskCreationOptions.LongRunning) — a dedicated thread, off the pool. The only defensible use of StartNew left
Allocation-free queueing
ThreadPool.UnsafeQueueUserWorkItem(item, preferLocal: true) where item : IThreadPoolWorkItem — also skips ExecutionContext capture
Local vs global queue
continuations queued from a pool thread land on that thread's local (LIFO) queue and are work-stolen; preferLocal: false forces the global FIFO queue
Do not Task.Run a request
in ASP.NET Core the request already runs on a pool thread; wrapping handler work in Task.Run adds a hop and doubles pool pressure with no extra concurrency
Blocking detection
the pool's blocking-work heuristics (.NET 6+) inject faster when it can tell threads are blocked, but the injection ceiling is still MaxThreads (32767 by default)

Incident playbook. Latency up, CPU flat, queue length climbing: take dotnet-stack report or a dump and look for pool threads parked in Monitor.Wait, Task.Result, Wait(), SemaphoreSlim.Wait or a sync Stream.Read. Bumping MinThreads buys minutes; removing the blocking call is the fix.

08Runtime Async .NET 11 preview

docs: what's new in the .NET 11 runtime
What changes
the compiler stops emitting state-machine classes; the runtime tracks suspension and resumption itself ("Runtime Async V2"). Your source does not change at all
Opt in
<Features>runtime-async=on</Features> in the csproj. A net11.0 project no longer needs <EnablePreviewFeatures>true</EnablePreviewFeatures>
Opt out
<UseRuntimeAsync>false</UseRuntimeAsync>. The DOTNET_RuntimeAsync and UNSUPPORTED_RuntimeAsync environment variables were removed — scripts that set them silently do nothing
Already on
the .NET 11 runtime libraries themselves ship compiled with runtime-async=on and contain no compiler-generated state machines
Headline win
live stack traces: a three-deep async chain drops from 13 frames of AsyncMethodBuilderCore.Start noise to 5 real frames. Exception stack traces were already clean and are unchanged
Debugging
breakpoints bind inside runtime-async methods and stepping crosses await without diving into generated infrastructure
AOT and R2R
NativeAOT and ReadyToRun are supported; crossgen2 can now inline runtime-async methods, including the await-less synchronous fast path
Perf mechanics
tiered compilation for async bodies, cached/reused continuations, tail-merged suspension points, Task/ValueTask factory intrinsics, cheaper await Task.Yield()
Covariant overrides
a derived Task<T> override of a base Task method now works through virtual dispatch via a generated thunk (JIT and NativeAOT)
Profilers
the async profiler instruments runtime-async and classic state machines with one event model, so tooling does not fork
Lead call
preview: do not ship production on it. Do build your libraries against it now and report throughput and size deltas — that is what the team is asking for before GA on 2026-11-10
<!-- opt a project in (preview) -->
<PropertyGroup>
  <TargetFramework>net11.0</TargetFramework>
  <Features>runtime-async=on</Features>
</PropertyGroup>

10Idioms & gotchas

docs: async scenarios · Fowler: async guidance
async void
exceptions go to the SynchronizationContext and usually crash the process; nothing can await it. UI event handlers only
Accidental async void
list.ForEach(async x => await F(x)) binds an async lambda to Action<T>. Any void-returning delegate parameter does this silently
Sync over async
.Result / .Wait() deadlocks under a SynchronizationContext; in ASP.NET Core it "merely" burns a pool thread — at scale that is the outage
Async over sync
Task.Run(() => BlockingCall()) in a library fakes async, doubles the thread cost and hides the blocking. Expose the sync method instead
Eliding async/await
returning the inner task saves a state machine but drops your frame from stack traces, changes when exceptions surface, and is wrong inside using/try. Keep await unless the method is a one-line pass-through
Argument validation
throws from an async method are captured in the task, not raised at the call site. Validate in a sync wrapper that then calls a private async local function
Constructors
no async constructors: use a static async Task<T> CreateAsync(...) factory, or an InitializeAsync called by the composition root
WhenAll exceptions
await rethrows only the first; read whenAllTask.Exception for all of them. Also: one throwing task does not cancel the others
Unbounded fan-out
Task.WhenAll over 10k items exhausts connection pools and sockets long before the CPU. Bound with Parallel.ForEachAsync or a SemaphoreSlim
Serial awaits in a loop
foreach { await ... } is N round trips. Start the tasks first, then await the collection — but only if the dependency really is absent
Fire and forget
_ = FooAsync(); loses exceptions and dies with the request. Queue to a Channel drained by a BackgroundService, or at minimum attach a logging continuation
TaskCompletionSource
without RunContinuationsAsynchronously the whole continuation chain runs inline on the thread that calls SetResult — stack dives and surprise deadlocks
Async mutual exclusion
lock cannot span an await. SemaphoreSlim(1, 1) can, is not reentrant, and must be released in finally
CancellationTokenSource leaks
CancelAfter arms a timer; an undisposed CTS or an undisposed ct.Register on a long-lived token keeps objects alive for the token's lifetime
Missing [EnumeratorCancellation]
WithCancellation(ct) compiles and does nothing. The stream runs to completion after the caller has given up
ValueTask reuse
awaiting twice, storing in a field, or WhenAll-ing them is undefined behaviour — AsTask() first
HttpClient
new instance per request exhausts sockets; a static one misses DNS changes. IHttpClientFactory, or a SocketsHttpHandler with PooledConnectionLifetime
Startup blocking
blocking inside IHostedService.StartAsync stalls the whole host; long work belongs in BackgroundService.ExecuteAsync
AsyncLocal writes
a value set after the await point does not flow back to the caller — ExecutionContext is copy-on-write, one direction only
Disposal ordering
using on an IAsyncDisposable-only type does not compile; on a type with both, it quietly picks the sync path. await using
// Validate eagerly, run lazily.
public Task<Order> GetAsync(int id, CancellationToken ct = default)
{
    ArgumentOutOfRangeException.ThrowIfNegativeOrZero(id);   // throws AT the call site
    return Core(id, ct);

    async Task<Order> Core(int id, CancellationToken ct) => await LoadAsync(id, ct);
}

// Bounded fan-out beats Task.WhenAll over a big collection.
await Parallel.ForEachAsync(ids, new ParallelOptions
{
    MaxDegreeOfParallelism = 16, CancellationToken = ct
}, async (id, ct) => await ProcessAsync(id, ct));
