1. Core mechanics of async/await

asked: oftencritical10 questions

What the compiler and runtime actually do with async/await: the state machine, the synchronous prefix, where continuations run, what allocates. Interviewers test this first because every other sub-area (deadlocks, starvation, ValueTask rules) is a consequence of it; a screener wants "await doesn't block a thread", a senior interviewer wants the state machine, the hot path and the awaitable pattern, and at principal level they want you to turn it into team rules and analyzers.

Docs: Asynchronous programming with async and await · How async/await really works in C# (Stephen Toub)

screenerWhat actually happens when you await a Task — does it block, spawn a thread, or something else?

Answer

Neither. The compiler rewrites the method into a state machine; at an await it calls GetAwaiter(), checks IsCompleted, and if the task is already done it simply continues on the same thread. If not, it registers the rest of the method as a continuation on the awaited task, captures the current SynchronizationContext/TaskScheduler (unless ConfigureAwait(false)) and the ExecutionContext, and returns to its caller — an incomplete Task. No thread waits. When the awaited operation completes, whichever thread completes it (an I/O completion thread, a pool thread, the UI thread via the context) runs the continuation, which re-enters the state machine at the saved state.

Example

async Task<int> GetLengthAsync(HttpClient http)
{
    Console.WriteLine(Environment.CurrentManagedThreadId); // e.g. 1
    var s = await http.GetStringAsync("https://example.org"); // suspends here if not complete
    Console.WriteLine(Environment.CurrentManagedThreadId); // e.g. 7 (pool thread) in a console app
    return s.Length;
}
// The caller receives an incomplete Task<int> at the first real await and can keep working.

Follow-ups

  • What if the awaited task is already complete? The method never suspends: the state machine is not boxed, no continuation is registered, the code after the await runs synchronously on the same thread.
  • Which thread runs the continuation? Without a captured context, usually the thread that completed the antecedent, inline; with a context (UI), it is posted back to that context.
  • So where does the I/O "wait" happen? Nowhere in managed code: the OS notifies completion through an I/O completion port (Windows) or epoll/kqueue (Linux/macOS), and the runtime dispatches the completion onto the pool.

Common wrong answer

"await starts the work on a background thread and blocks until it finishes" — the single most common rejection at screener level. It conflates async with multithreading; the interviewer will immediately ask "then why does async help a web server?" and the candidate cannot answer.

screenerAsync vs multithreading vs parallelism — and does async make my code faster?

Answer

Asynchrony means not holding a thread while waiting for something that is not CPU work (network, disk, a timer, another service). Multithreading means running code on more than one thread; parallelism means doing that to finish CPU work sooner. Async on its own does not make an individual operation faster — the HTTP call takes as long as it takes — it improves throughput and scalability by freeing the thread to serve other work, and it keeps UI threads responsive. Parallelism (Parallel.For, PLINQ, several Task.Run) is what makes CPU-bound work faster, and mixing the two up is where most bad designs start.

Example

// I/O-bound: async frees the thread; no Task.Run needed
var page = await http.GetStringAsync(url, ct);

// CPU-bound in a desktop app: offload to keep the UI responsive
var hash = await Task.Run(() => ComputeExpensiveHash(data), ct);

// CPU-bound data parallelism: use all cores
Parallel.For(0, items.Length, i => items[i] = Transform(items[i]));

Follow-ups

  • Why does async help a web server? A thread released during I/O can serve another request; with blocking I/O, concurrency is capped by thread count and the pool starves under load.
  • When is Task.Run appropriate? Offloading CPU-bound work from a UI thread, or deliberately parallelising CPU work; almost never inside an ASP.NET Core request.
  • Is async I/O "real" on all platforms? Sockets and HTTP yes; file I/O is truly async on Windows and, since .NET 6, uses non-blocking calls where the OS allows on Linux, but some file operations still complete on pool threads.

Common wrong answer

"Async code runs on a background thread, so the request is faster." Interviewers hear this as "does not understand what the thread is doing during I/O", and it predicts the Task.Run-in-a-controller anti-pattern.

screenerWhat is a Task, what states can it be in, and what are the three return types of an async method?

Answer

A Task is a promise: a handle to an operation that may complete later with a result, an exception or cancellation. Its Status moves through WaitingForActivation/Running to one of three terminal states — RanToCompletion, Faulted, Canceled — and IsCompleted is true for all three. Tasks returned by async methods are "hot" (already started); you never call Start() on them. An async method returns Task (no result), Task<T>, or — only for event handlers — void; since C# 7 it can also return ValueTask/ValueTask<T> or any "task-like" type with an AsyncMethodBuilder. Since C# 7.1 Main can be async Task.

Example

Task<int> t = ComputeAsync();
Console.WriteLine(t.Status);        // WaitingForActivation while suspended
int result = await t;               // RanToCompletion → result; Faulted → throws; Canceled → OperationCanceledException

// Pre-built completed tasks avoid allocations and state machines:
Task<int> cached = Task.FromResult(42);
Task done = Task.CompletedTask;
Task failed = Task.FromException(new InvalidOperationException());
Task cancelled = Task.FromCanceled(ct);

Follow-ups

  • Hot vs cold tasks? new Task(...) is cold and needs Start(); nothing in modern code should create one. Everything from async, Task.Run and I/O APIs is hot.
  • What is WaitingForActivation? The state of a promise-style task (from an async method or a TaskCompletionSource) that has not completed yet; it is not "queued to run", there is no delegate.
  • Can a Task be awaited twice? Yes, any number of times, by any number of awaiters; that is the key difference from ValueTask.

Common wrong answer

"A Task is a thread" or "a Task is a unit of work that runs on the thread pool" — true only for delegate tasks from Task.Run; promise tasks from I/O and async methods have no thread at all.

midWhat runs synchronously when you call an async method, and why does it matter?

Answer

The method body runs synchronously on the caller's thread up to the first await whose awaitable is not already complete; only then does control return to the caller with an incomplete task. If every await completes synchronously, the whole method runs synchronously and returns a completed task. Three consequences matter: expensive synchronous prefixes block the caller (e.g. BackgroundService.ExecuteAsync blocking host startup), exceptions thrown before the first await are captured in the returned task rather than thrown at the call site (unlike a non-async method that returns a task), and argument validation that should fail fast needs a non-async wrapper.

Example

// Fail-fast validation: throw synchronously, then run the async core.
public Task<User> GetUserAsync(int id, CancellationToken ct)
{
    ArgumentOutOfRangeException.ThrowIfNegative(id);   // thrown at the call site
    return GetUserCoreAsync(id, ct);
}

private async Task<User> GetUserCoreAsync(int id, CancellationToken ct)
{
    var row = await _db.FindAsync(id, ct);            // exceptions from here go into the Task
    return Map(row);
}

Follow-ups

  • What is "eliding async/await" and when is it safe? Returning the inner task directly instead of awaiting it saves a state machine, but breaks if the method has a using/try around the call (disposal happens before completion) or if you want the method in the exception stack trace. Safe for thin pass-throughs only.
  • Why is the synchronous prefix a problem for hosted services? The host calls StartAsync for each service in order; a long synchronous prefix (or a blocking loop) delays every subsequent service and the "started" signal. await Task.Yield() at the top fixes it.
  • Does the sync prefix run on the caller's context? Yes, it is a normal method call; only continuations after a suspension care about context.

Common wrong answer

"Calling an async method immediately returns and the body runs on another thread." Candidates who believe this write ExecuteAsync bodies that block startup and are surprised when an exception "before the await" is not caught by their try around the call.

midWhat allocations does an async method cost, and where does the state machine live?

Answer

In Release builds the compiler generates a struct state machine that lives on the stack; hoisted locals become its fields. If the method completes synchronously nothing is boxed, and for Task/Task<T> the builder returns Task.CompletedTask or a cached task for common values (both bools, ints from -1 to 8, and defaults for a few primitives), otherwise a new Task<T>. On the first real suspension the struct is boxed to the heap once — and since .NET Core 2.1 that box is the Task object (an IAsyncStateMachineBox that derives from Task<T>), so a suspending async method costs one allocation plus whatever the awaited operation allocates. Awaiting a Task registers the box directly as the continuation, no delegate; awaiting a custom awaiter uses a cached Action stored in the box. Debug builds use a class state machine instead of a struct, so Debug benchmarks lie.

Example

// Zero allocations if the cache hits synchronously; one box + Task if it suspends.
async ValueTask<byte[]> ReadAsync(string key)
{
    if (_cache.TryGetValue(key, out var bytes)) return bytes;   // sync path: no Task, no box
    bytes = await _store.LoadAsync(key);                         // suspends: box allocated once
    _cache[key] = bytes;
    return bytes;
}

Follow-ups

  • Why are locals hoisted to fields? They must survive across a suspension; the compiler hoists any local live across an await. Keeping scopes tight reduces the box size.
  • Does ConfigureAwait(false) change allocations? Not the state machine; it avoids creating a SynchronizationContextAwaitTaskContinuation when a context is present.
  • How does .NET 11 Runtime Async change this? The compiler no longer emits a state machine; the runtime saves live state into continuation objects it can reuse, and avoids saving unchanged locals — see unit 14.

Common wrong answer

"Every async method allocates a Task and a state machine object." The answer misses the synchronous fast path entirely, which is the whole reason ValueTask and the cached-task optimisations exist.

midTask.Run vs Task.Factory.StartNew vs new Task(...).Start(): what is the difference?

Answer

Task.Run (.NET 4.5) is the modern API: it queues to the thread pool via TaskScheduler.Default, uses TaskCreationOptions.DenyChildAttach, and unwraps async lambdas so Task.Run(async () => ...) returns a Task, not a Task<Task>. Task.Factory.StartNew is the older, lower-level API: it defaults to TaskScheduler.Current (which may be a UI or custom scheduler, not the pool), does not unwrap, and exists mostly for TaskCreationOptions.LongRunning or a custom scheduler. new Task(...) creates a cold task that must be started explicitly and has no place in modern code.

Example

Task<Task> wrong = Task.Factory.StartNew(async () => await DoAsync());   // completes when the lambda *returns* its task
Task ok1 = Task.Factory.StartNew(async () => await DoAsync()).Unwrap();  // legacy fix
Task ok2 = Task.Run(async () => await DoAsync());                        // modern: unwrapped, pool scheduler

// Only remaining StartNew use: a dedicated thread for a long blocking loop
Task loop = Task.Factory.StartNew(PumpForever, TaskCreationOptions.LongRunning);

Follow-ups

  • What goes wrong with TaskScheduler.Current? Inside a task running on a custom scheduler, StartNew silently inherits it — code that "worked in tests" runs single-threaded on a UI scheduler in production. Analyzer CA2008 flags it.
  • Does Task.Run capture the SynchronizationContext? No, the delegate runs on the pool; only continuations after awaits inside it capture context (and there is none on a pool thread).
  • What does Unwrap() do? Turns a Task<Task<T>> into a proxy Task<T> that completes when the inner task does.

Common wrong answer

"They are equivalent; Task.Run is just shorthand." The interviewer then shows StartNew with an async lambda that "finishes instantly", and the candidate cannot explain the Task<Task>.

midCan you await something that is not a Task? What makes a type awaitable?

Answer

Yes — await is pattern-based, not type-based. A type is awaitable if it has an accessible GetAwaiter() method (instance, extension, or since C# 14 an extension member) returning an awaiter that exposes bool IsCompleted, GetResult() (void or T) and implements INotifyCompletion (ideally ICriticalNotifyCompletion). That is how Task.Yield() works (a YieldAwaitable), how ValueTask, ConfiguredTaskAwaitable, Task.WhenEach results and Unity's UniTask work, and how you can make TimeSpan, Process or a CancellationToken awaitable with an extension.

Example

public static class TimeSpanAwaiterExtensions
{
    // await TimeSpan.FromSeconds(2);
    public static TaskAwaiter GetAwaiter(this TimeSpan delay) => Task.Delay(delay).GetAwaiter();
}

// C# 14 extension-member form of the same thing:
public static class TimeSpanExtensions
{
    extension(TimeSpan delay)
    {
        public TaskAwaiter GetAwaiter() => Task.Delay(delay).GetAwaiter();
    }
}

Follow-ups

  • Why does ICriticalNotifyCompletion exist? Its UnsafeOnCompleted lets the builder skip flowing ExecutionContext a second time (the builder already handles it), saving work; awaiters without it get the safe path.
  • What does the compiler call in which order? GetAwaiter(), then IsCompleted; if false, AwaitUnsafeOnCompleted/AwaitOnCompleted on the builder, return; on resume GetResult(), which throws on fault/cancel.
  • Is GetAwaiter().GetResult() the same as .Result? Both block; GetResult() throws the original exception, .Result wraps it in AggregateException.

Common wrong answer

"You can only await Task and ValueTask." Shows the candidate has never looked at what Task.Yield() returns or how a library like UniTask can exist.

seniorWhat does await Task.Yield() do, exactly, and when is it the right tool?

Answer

Task.Yield() returns an awaitable whose IsCompleted is always false, so the method always suspends and its continuation is posted to the current SynchronizationContext if there is one, otherwise queued to the thread pool's global queue (not the local queue, so it cannot starve other global work). It is the right tool to break a long synchronous prefix — the classic case is BackgroundService.ExecuteAsync so host startup continues — or to let a UI message loop breathe between chunks of work. It is not a way to run on "another thread" (on a UI context you come back to the same thread), it does not lower priority like Thread.Yield, and it is not a substitute for Task.Run when the work is CPU-heavy.

Example

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    await Task.Yield();                    // return to the host immediately; do not block StartAsync
    while (!stoppingToken.IsCancellationRequested)
    {
        await ProcessBatchAsync(stoppingToken);
    }
}

Follow-ups

  • Why is await Task.Delay(1) a worse way to yield? It costs a timer and 1–15 ms of latency depending on timer resolution; Yield is immediate.
  • Can Task.Yield() deadlock? No — it always completes asynchronously, which is also why it is the standard way to escape "the awaited task completed synchronously, so I never left the caller's stack".
  • What is ConfigureAwaitOptions.ForceYielding? The .NET 8 equivalent applied to an actual task: await task.ConfigureAwait(ConfigureAwaitOptions.ForceYielding) guarantees an asynchronous continuation.

Common wrong answer

"Task.Yield() switches to a background thread so the UI stays responsive" — on a UI context it posts back to the UI thread; heavy work after it still freezes the UI.

senior"Sync over async" and "async over sync": what are they, what breaks, and when is each acceptable?

Answer

Sync-over-async is blocking on a task (.Result, .Wait(), GetAwaiter().GetResult()): it ties up a thread for the duration, deadlocks when a single-threaded context is captured (UI, legacy ASP.NET), and under load on a server it is the number-one cause of thread-pool starvation. Async-over-sync is wrapping a blocking call in Task.Run and calling it "async": it costs a second thread and gains nothing on a server, which is why the BCL deliberately does not expose async wrappers over synchronous work. Sync-over-async is tolerable at true boundaries during a migration (Main before C# 7.1, a legacy interface you cannot change) — ideally with Task.Run(...).GetAwaiter().GetResult() to avoid the context deadlock; async-over-sync is acceptable in a client app to keep the UI responsive, never as a library's public API.

Example

// Boundary hack for a sync interface you cannot change (document it, isolate it):
public Order Load(int id) => Task.Run(() => LoadAsync(id)).GetAwaiter().GetResult();

// Library anti-pattern: fake async that burns a pool thread
public Task<Order> LoadAsync(int id) => Task.Run(() => LoadSync(id));   // do not ship this

Follow-ups

  • Why does Task.Run(...).GetAwaiter().GetResult() avoid the deadlock? The async chain runs on pool threads with no context to capture, so nothing needs the blocked thread; it still burns a thread and still starves under load.
  • Why does the BCL not add Task<T> wrappers around sync methods? Callers assume "Async" means the thread is freed; a wrapper would lie about scalability. Toub's rule: expose async when the underlying operation is truly asynchronous.
  • How do you find sync-over-async in a large codebase? Analyzers (VSTHRD002, CA1849 for the reverse), Ben.BlockingDetector at runtime, and dumps showing pool threads in Task.Wait.

Common wrong answer

"Wrap the synchronous call in Task.Run so it becomes async" as a general strategy — the interviewer will ask what the second thread is doing and why the server is now worse off.

principalHow would you set and enforce async coding standards across a team or a monorepo?

Answer

Make the rules mechanical, not cultural. Turn on the analyzers that already exist and set their severity in a shared .editorconfig: CS4014 (unawaited task) as error, CA2007 (missing ConfigureAwait) as error in library projects and off in app projects, CA2008 (no scheduler on StartNew), CA2012 (misused ValueTask), CA2016 (forward the CancellationToken), CA1849 (call the async version), CA2025 (.NET 9: IDisposable passed to a task that outlives it), plus Microsoft.VisualStudio.Threading.Analyzers (VSTHRD100 async void, VSTHRD002 blocking, VSTHRD110 unobserved) or Meziantou.Analyzer for the gaps. Add the conventions the compiler cannot check to a short written standard: Async suffix, token as last parameter, no Task.Run in request paths, no .Result outside explicitly named boundary adapters, a single approved fire-and-forget helper. Enforce with TreatWarningsAsErrors in CI and a load test that fails on thread-pool queue growth — the only test that catches sync-over-async at scale.

Example

# .editorconfig (shared via Directory.Build.props)
dotnet_diagnostic.CS4014.severity = error
dotnet_diagnostic.CA2007.severity = error      # override to none in app projects
dotnet_diagnostic.CA2008.severity = error
dotnet_diagnostic.CA2012.severity = error
dotnet_diagnostic.CA2016.severity = error
dotnet_diagnostic.CA1849.severity = warning
dotnet_diagnostic.CA2025.severity = warning
dotnet_diagnostic.VSTHRD100.severity = error   # async void
dotnet_diagnostic.VSTHRD002.severity = error   # .Result / .Wait()

Follow-ups

  • Where do you allow exceptions to the rules? In one named place per rule (e.g. *.SyncBoundary.cs files) with #pragma warning disable and a justification, so exceptions are grep-able and reviewable.
  • How do you roll this out on a large legacy codebase? Baseline current violations (severity = suggestion), fail only on new ones via a ratchet, then fix by hotspot using starvation data from production.
  • What can no analyzer catch? Blocking inside a lock, sync I/O hidden in a dependency, scoped services captured by background work — those need runtime detection and load tests.

Common wrong answer

"We cover it in code review and a wiki page." At principal level the interviewer expects the answer to name the analyzers, the CI gate and the rollout strategy; reliance on review alone signals the standard will drift within a quarter.

2. Thread-pool behaviour and starvation

asked: oftencritical9 questions

The thread pool is where continuations run, and its injection algorithm is why sync-over-async turns into an outage. Interviewers use it to separate people who have run async services in production from people who have only written them: what starvation looks like, why the pool adds threads slowly, what the knobs cost. Mid-level candidates should explain the symptoms; senior candidates the algorithm and the diagnosis; principal candidates should partition CPU and I/O work by design.

Docs: The managed thread pool · Debug ThreadPool starvation

screenerWhich threads run async continuations, and where does I/O completion come from?

Answer

Unless a SynchronizationContext or custom TaskScheduler was captured, continuations run on thread-pool worker threads — often inline on the thread that completed the awaited operation. For I/O, that thread is one the runtime dedicates to completion notification: on Windows an I/O completion port is serviced and the completion is dispatched to the pool; on Linux/macOS a small number of epoll/kqueue threads dequeue socket readiness events and hand the work to pool threads. Since .NET 6 the pool itself is fully managed code (the "portable" pool) on every platform, which is why behaviour is now consistent across OSes. Timers (Task.Delay) fire from a timer thread and queue continuations to the pool too.

Example

Console.WriteLine($"{Environment.CurrentManagedThreadId} pool={Thread.CurrentThread.IsThreadPoolThread}"); // 1 pool=False
await Task.Delay(10);
Console.WriteLine($"{Environment.CurrentManagedThreadId} pool={Thread.CurrentThread.IsThreadPoolThread}"); // 4 pool=True
await new HttpClient().GetStringAsync("https://example.org");
Console.WriteLine($"{Environment.CurrentManagedThreadId} pool={Thread.CurrentThread.IsThreadPoolThread}"); // 7 pool=True

Follow-ups

  • Why should you never block an I/O completion path? Blocking inside a continuation that runs inline on a completion thread delays every other completion behind it.
  • What is DOTNET_SYSTEM_NET_SOCKETS_THREAD_COUNT? The knob for the number of socket-engine (epoll) threads on Unix; almost never worth touching.
  • Is the pool the same in .NET Framework? The concepts match, but the Framework pool is native code with separate worker and I/O completion threads and older injection heuristics.

Common wrong answer

"The continuation runs on the thread that called the async method." Only true if a context marshals it there (UI apps); on a server the original thread is long gone serving something else.

screenerWhat is thread-pool starvation, what causes it, and what does it look like in production?

Answer

Starvation is the state where every pool thread is busy — usually blocked — so queued work items, including the continuations that would unblock those very threads, cannot run. The cause is almost always blocking on pool threads: .Result/.Wait() on tasks, synchronous I/O, lock contention, Thread.Sleep. Because the pool only injects threads slowly above its minimum (roughly one to two per second by the classic heuristic), latency climbs in a staircase, requests time out, and — the tell-tale signature — CPU stays low while the thread count creeps up and the work-item queue length grows. Fix the blocking; raising min threads only buys time.

Example

// The classic starvation bomb in a request handler on a 4-core box:
public IActionResult Get() => Ok(_service.LoadAsync().Result);   // blocks a pool thread per request
// Under 100 concurrent requests: 4 threads block, the continuations that would complete
// LoadAsync sit in the queue, the pool adds ~1 thread/second, p99 latency goes to tens of seconds.

Follow-ups

  • Which metrics confirm it? dotnet-counters: threadpool-queue-length rising, threadpool-thread-count climbing by about one per second, low CPU; in ASP.NET Core, current-requests high with low requests-per-second.
  • Why is it worse than simply "slow"? It is self-reinforcing: the blocked threads wait for continuations that need a free thread; only injection or timeouts break the cycle.
  • Can pure async code starve the pool? Yes, with CPU-bound work in continuations (JSON of huge payloads, regex backtracking) or with Parallel.For inside requests — then CPU is high, which distinguishes it from blocking.

Common wrong answer

"Set ThreadPool.SetMaxThreads higher" — max threads is already in the thousands; the limit that matters is how fast threads are injected above min. Also rejected: "it's CPU-bound, add cores" when the dashboard shows 10% CPU.

midHow does the thread pool decide to create threads? Explain min threads, hill climbing and the blocking mitigation.

Answer

The pool keeps a minimum number of worker threads equal to the logical processor count by default (ThreadPool.SetMinThreads, System.Threading.ThreadPool.MinThreads in runtimeconfig.json, or DOTNET_ThreadPool_MinThreads). Up to that minimum, threads are created on demand immediately. Above it, two mechanisms add threads: a hill-climbing algorithm that periodically varies the thread count and keeps changes that improve completed-items throughput, and a starvation detector that adds a thread when the queue has not made progress for a while — historically at most about one thread every 500 ms to 1 s, which is the "staircase" you see in incidents. Since .NET 6 the managed pool also has a cooperative blocking mitigation: when a pool thread blocks on a Task (Wait, Result, GetResult), it notifies the pool, which injects replacement threads without waiting for the heuristic delay, within configurable limits. Threads idle for long enough are retired.

Example

// runtimeconfig.template.json — a stop-gap, not a fix
{
  "configProperties": {
    "System.Threading.ThreadPool.MinThreads": 64
  }
}

Follow-ups

  • Why not set min threads to 1000? Each thread reserves stack (1 MB by default), adds context-switch and cache pressure, and hides the blocking that will resurface at the next scale step; hill climbing also becomes noisier.
  • What does the blocking mitigation not cover? Blocking on locks, Thread.Sleep, synchronous I/O and SemaphoreSlim.Wait — only Task-level waits notify the pool.
  • How do you observe injection? ThreadPoolWorkerThreadAdjustment events via dotnet-trace, or ThreadPool.ThreadCount sampled over time.

Common wrong answer

"The pool creates a thread for each queued work item, up to the max." Reveals no model of why latency climbs in one-second steps; the interviewer will then ask why raising the max did nothing.

midGlobal queue vs local queues vs work stealing — how are work items scheduled, and why does it matter?

Answer

The pool has one global FIFO queue plus a per-thread local queue. Work queued from a non-pool thread (or with preferLocal: false) goes to the global queue; work queued from a pool thread — such as child tasks and most continuations — goes to that thread's local queue, which the thread drains LIFO for cache locality. A thread whose local queue is empty takes from the global queue, then steals from the tail of other threads' local queues. It matters for fairness: local LIFO can delay older items, which is why Task.Yield() queues globally, and why a hot loop that keeps spawning continuations on one thread can starve the global queue until stealing kicks in.

Example

// .NET Core 3.0+: control the queue explicitly and avoid a delegate allocation
sealed class MyWork : IThreadPoolWorkItem
{
    public void Execute() { /* ... */ }
}
ThreadPool.UnsafeQueueUserWorkItem(new MyWork(), preferLocal: true);

Follow-ups

  • Why LIFO locally? The most recently queued item is most likely to have its data in cache; stealing from the tail (oldest) minimises contention with the owner.
  • What is "Unsafe" about UnsafeQueueUserWorkItem? It does not capture/flow ExecutionContext — faster, but AsyncLocal values and the security context do not flow.
  • Does TaskCreationOptions.PreferFairness still exist? Yes: it forces the global queue for that task.

Common wrong answer

"It is a single FIFO queue served by N threads." Acceptable at screener level, but a mid-level candidate should know why Task.Yield() and preferLocal exist.

midWhat does TaskCreationOptions.LongRunning do, and why is it pointless with an async delegate?

Answer

LongRunning hints the default scheduler that the work will occupy a thread for a long time, so it creates a dedicated non-pool thread instead of borrowing a pool thread that hill climbing would otherwise have to compensate for. It is right for a genuinely long blocking loop (a consumer that blocks on a BlockingCollection, a message pump). It is pointless — and misleading — with an async lambda: the dedicated thread is released at the first await, and every continuation afterwards runs on ordinary pool threads anyway. For a long-running async loop, use an async method in a BackgroundService; for a long blocking loop, prefer an explicit Thread with a name, which is clearer.

Example

// Pointless: the thread is given up at the first await
Task.Factory.StartNew(async () => { while (true) await PollAsync(); }, TaskCreationOptions.LongRunning);

// Honest alternatives
var t = new Thread(BlockingPump) { IsBackground = true, Name = "pump" }; t.Start();   // blocking loop
_ = RunAsync(ct);                                                                      // async loop, no thread held

Follow-ups

  • Does Task.Run support LongRunning? No; you need Task.Factory.StartNew(..., TaskCreationOptions.LongRunning, TaskScheduler.Default).
  • What about a hosted service that runs a blocking library loop? Start it on a dedicated thread from StartAsync, complete a TaskCompletionSource when it stops, and await that in StopAsync.
  • When is a raw Thread still correct? Thread affinity (COM STA, native libraries), thread priority, or a name for diagnostics.

Common wrong answer

"Use LongRunning for any task that runs a long time, including async ones." The interviewer will ask where the dedicated thread is after the first await.

seniorA production service is starving. Should you raise min threads? Walk through the trade-offs.

Answer

As a mitigation during an incident, yes: raising MinThreads (environment variable DOTNET_ThreadPool_MinThreads, which needs a restart, or ThreadPool.SetMinThreads at startup) removes the injection delay up to that number and typically restores service within minutes. As a fix, no: it hides blocking that returns at the next traffic step, each extra thread costs stack and scheduler overhead, and a high minimum makes the pool over-subscribe CPU-bound work. The senior answer is a sequence: mitigate (scale out, raise min threads, restart if the queue is already unbounded), capture evidence (counters, a dump with clrstack -all), remove the blocking calls, then set min threads back to default and prove with a load test that queue length stays flat.

Example

# Incident mitigation on Kubernetes: env var + rollout (needs process restart)
kubectl set env deployment/orders DOTNET_ThreadPool_MinThreads=64
# Evidence while it is still happening
dotnet-counters monitor -p <pid> --counters System.Runtime[threadpool-thread-count,threadpool-queue-length,threadpool-completed-items-count]
dotnet-dump collect -p <pid>

Follow-ups

  • Why might raising min threads make it worse? If the blocking is on a downstream with a connection limit (a database pool of 100), more threads just queue on that limit and multiply memory use.
  • What if you cannot change the blocking code (third-party)? Isolate it: a dedicated scheduler or bounded set of threads, or a separate process, so it cannot exhaust the shared pool.
  • Is SetMinThreads also for I/O completion threads? The second parameter historically sized I/O completion threads; with the managed pool it is mostly irrelevant on Unix.

Common wrong answer

Either extreme: "never touch min threads, fix the code" (ignores the incident in progress) or "set it to 500 and move on" (ignores the cost and the recurrence). The interviewer wants the sequence.

seniorWhy is Task.Run inside an ASP.NET Core request an anti-pattern, and is it ever justified?

Answer

Kestrel already runs your handler on a pool thread. Task.Run inside it moves the work to a second pool thread and parks the first one on the await — no gain in throughput, extra queueing, and under load it competes with the very continuations that complete other requests. For CPU-heavy work it makes things worse: the pool is sized for I/O concurrency, not for N parallel CPU jobs, and hill climbing will over-inject. It is justified only when you must offload a long CPU computation off the request thread and bound its concurrency (a SemaphoreSlim or a dedicated scheduler), or when a synchronous third-party API would otherwise block the completion path and you have no alternative.

Example

// Anti-pattern
app.MapGet("/report", async () => await Task.Run(() => BuildReport()));

// Better: bounded CPU work, and queue it if it takes seconds
static readonly SemaphoreSlim CpuGate = new(Environment.ProcessorCount / 2);
app.MapGet("/report", async (CancellationToken ct) =>
{
    await CpuGate.WaitAsync(ct);
    try { return Results.Ok(BuildReport()); }
    finally { CpuGate.Release(); }
});

Follow-ups

  • Why is the "return quickly and process in the background" version also wrong when done with Task.Run? The task captures request-scoped services (DbContext, HttpContext) that are disposed when the response ends; use a hosted service with a Channel.
  • Where does long CPU work belong architecturally? A separate worker process or job system with its own capacity and back-pressure, returning 202 Accepted with a status URL.
  • What about Task.Run in a UI app? Correct there: the goal is freeing the UI thread, not throughput.

Common wrong answer

"Use Task.Run so the request returns faster / the server can handle more requests." The candidate has the client-app mental model and will write starvation-prone servers.

midWhen would you still use ThreadPool.QueueUserWorkItem or a raw Thread instead of Task.Run?

Answer

Task.Run is the default because it gives you a handle for completion, results, exceptions and composition. ThreadPool.QueueUserWorkItem (or UnsafeQueueUserWorkItem with an IThreadPoolWorkItem) is for true fire-and-forget infrastructure where you need zero allocation and no task at all — logging pipelines, event dispatch inside a framework — with the caveat that an unhandled exception there crashes the process. A raw Thread is for work that needs a thread identity: a long-lived blocking loop, thread affinity (COM STA, UI, some native SDKs), a custom stack size, priority, or a stable name for dumps. Everything else is a task.

Example

// Infrastructure fire-and-forget, no Task allocation, no ExecutionContext flow
ThreadPool.UnsafeQueueUserWorkItem(static state => Flush((Buffer)state!), buffer, preferLocal: false);

// Thread identity needed: STA for a COM component
var sta = new Thread(RunComPump) { Name = "com-sta", IsBackground = true };
sta.SetApartmentState(ApartmentState.STA);
sta.Start();

Follow-ups

  • What happens to an exception in QueueUserWorkItem? Process crash (unhandled on a pool thread) — there is no task to hold it.
  • Why is IsBackground = true important? Foreground threads keep the process alive after Main returns; a forgotten pump thread makes shutdown hang.
  • Is a dedicated TaskScheduler an alternative? Yes, e.g. ConcurrentExclusiveSchedulerPair or a custom scheduler over N threads to isolate a subsystem from the shared pool.

Common wrong answer

"Threads are legacy; always use tasks." A mid-level candidate should know the two or three cases where a thread's identity is the requirement.

principalDesign: one service does heavy CPU work (image processing) and high-volume I/O. How do you keep them from starving each other?

Answer

Separate the capacity. The shared pool should stay free for I/O continuations, so CPU work runs with bounded parallelism that is decided by design, not by hill climbing: a dedicated TaskScheduler or a fixed set of worker threads consuming a bounded Channel<Job>, with MaxDegreeOfParallelism around processor count minus a reserve for I/O. Make the queue bounded so back-pressure surfaces as 429/503 or a "queued" status instead of memory growth, and put per-job timeouts and cancellation on it. If the CPU work is bursty or the SLOs differ, move it to a separate process or deployment so the kernel scheduler and autoscaler isolate it — the strongest boundary. Instrument both halves separately: queue depth and processing time for the CPU lane, thread-pool queue length and request latency for the I/O lane, so starvation in one shows up in its own alert.

Example

// In-process isolation: a bounded CPU lane with its own parallelism
var jobs = Channel.CreateBounded<ImageJob>(new BoundedChannelOptions(1_000) { FullMode = BoundedChannelFullMode.Wait });

// Consumers: N dedicated long-running workers, not pool threads
for (int i = 0; i < Environment.ProcessorCount - 2; i++)
    new Thread(() => ConsumeBlocking(jobs.Reader)) { Name = $"img-{i}", IsBackground = true }.Start();

// Request path only enqueues (with cancellation) and returns 202
app.MapPost("/images", async (ImageJob job, CancellationToken ct) =>
{
    if (!jobs.Writer.TryWrite(job)) return Results.StatusCode(503);   // back-pressure surfaces here
    return Results.Accepted($"/images/{job.Id}");
});

Follow-ups

  • Why not Parallel.For inside the request? It uses the shared pool and blocks the calling thread until done; under concurrent requests it over-subscribes the CPU and starves I/O.
  • What about Task.Run with a SemaphoreSlim? Works for small scale, but the waiting continuations still queue on the shared pool; a dedicated lane is explicit.
  • How do you decide in-process vs separate process? Different scaling curves, different SLOs, or a need for crash isolation (native image libraries) push you to a separate process.

Common wrong answer

"Raise min threads and use Task.Run; the pool will balance it." A principal answer must name the isolation boundary and the back-pressure mechanism.

3. ConfigureAwait, SynchronizationContext and deadlocks

asked: oftencritical8 questions

The most-asked follow-up chain in the whole topic: "what does ConfigureAwait(false) do — why does this code deadlock — why doesn't it deadlock in ASP.NET Core?" It tests whether you know what a SynchronizationContext is, which frameworks have one, and what a continuation captures. Mid-level candidates must explain the deadlock; senior ones must know the .NET 8 ConfigureAwaitOptions, the TaskCompletionSource inline-continuation trap and the library rules; principal ones must plan a migration away from .Result.

Docs: ConfigureAwait FAQ · ConfigureAwaitOptions (.NET 8)

screenerWhat does ConfigureAwait(false) do?

Answer

By default, when an await has to suspend, the continuation is scheduled back onto the captured SynchronizationContext (or, if there is none, the current non-default TaskScheduler). ConfigureAwait(false) says "don't do that": run the continuation wherever the task completed, typically a pool thread. Two benefits: it avoids deadlocks when a caller blocks on a single-threaded context, and it skips the marshalling cost. It applies per await, not per method, and it does nothing if the awaited task is already complete — the code just continues synchronously on the current thread. In ASP.NET Core, console apps and worker services there is no SynchronizationContext, so it changes nothing functionally; libraries still use it because they cannot know who calls them.

Example

// Library code: never depend on the caller's context
public async Task<string> ReadAllAsync(Stream s, CancellationToken ct)
{
    using var reader = new StreamReader(s);
    return await reader.ReadToEndAsync(ct).ConfigureAwait(false);
}

// UI code: you *want* the context back to touch controls
private async void OnClick(object sender, EventArgs e)
{
    var text = await _service.ReadAllAsync(stream, ct);   // default: continue on the UI thread
    label.Text = text;
}

Follow-ups

  • Does it make ASP.NET Core faster? Marginally at most: no context to capture, so the only saving is a check; it is not a performance lever there.
  • If the first await uses ConfigureAwait(false), do later awaits need it? Yes, every one — after the first you are on a pool thread with no context, so later awaits capture nothing, but if that first task completed synchronously you are still on the context.
  • What does ConfigureAwait(true) mean? The default; some teams write it to state intent explicitly and silence CA2007.

Common wrong answer

"It makes the continuation run on a background thread" — the continuation runs on whatever thread completes the task, which on a UI app with an already-completed task is still the UI thread. Also wrong: "it is needed everywhere in ASP.NET Core for performance".

screenerExplain the classic .Result deadlock, and why the same code does not deadlock in ASP.NET Core.

Answer

On a UI thread (WinForms, WPF, MAUI) or in legacy ASP.NET, there is a SynchronizationContext that runs continuations on one specific thread. If that thread calls DoAsync().Result, it blocks; inside DoAsync the await captured the context and, when the I/O completes, posts the continuation to that same thread — which is blocked waiting for the continuation. Neither side can proceed: a deadlock. ASP.NET Core has no SynchronizationContext, so the continuation runs on any pool thread and the blocked thread eventually wakes — no deadlock, but the thread was wasted, which under load becomes starvation. The fix is async all the way (never block), not ConfigureAwait(false) at the call site: it only helps if every await in the callee chain uses it.

Example

// WPF: deadlocks
private void Button_Click(object sender, RoutedEventArgs e)
{
    var data = LoadAsync().Result;   // UI thread blocks here...
}
private async Task<string> LoadAsync()
{
    await Task.Delay(100);           // ...continuation is posted to the UI thread, which is blocked
    return "x";
}
// Fix: async void Button_Click(...) { var data = await LoadAsync(); }

Follow-ups

  • Would ConfigureAwait(false) inside LoadAsync fix it? This one, yes, because it is the only await; in real code a single missed await anywhere in the chain (including third-party code) brings the deadlock back.
  • Why does Blazor matter here? Blazor Server has a renderer SynchronizationContext; Blazor WebAssembly runs on a single thread — blocking there deadlocks or throws.
  • What about Task.Run(() => LoadAsync()).Result? Avoids the deadlock because the chain runs without a context; still blocks a thread — a boundary hack only.

Common wrong answer

"Add ConfigureAwait(false) where you call .Result" — the wrong side. The capture happens inside the callee's awaits, not at the blocking call site.

midWhat is a SynchronizationContext, which frameworks install one, and what is captured when there is none?

Answer

SynchronizationContext is an abstraction for "run this delegate in the right place": Post (async) and Send (sync). Frameworks install one where thread affinity or single-threaded access matters: WindowsFormsSynchronizationContext and WPF's DispatcherSynchronizationContext (one UI thread), MAUI and WinUI equivalents, Blazor Server's renderer context (one-at-a-time, not thread-affine), Blazor WebAssembly's single-threaded context, legacy ASP.NET's AspNetSynchronizationContext (one-at-a-time per request, any thread). Console apps, worker services and ASP.NET Core have none — SynchronizationContext.Current is null. When there is no context, the awaiter captures TaskScheduler.Current if it is not the default, which is how a custom scheduler propagates through awaits.

Example

Console.WriteLine(SynchronizationContext.Current is null);   // true in ASP.NET Core / console

// Legacy ASP.NET: one-at-a-time per request (not thread-affine)
// UI: Post(d) == Dispatcher.BeginInvoke(d)
// Custom: a test context that runs everything on one thread to catch deadlocks
SynchronizationContext.SetSynchronizationContext(new SingleThreadedContext());

Follow-ups

  • Why did ASP.NET Core drop the context? The per-request context was a source of deadlocks and overhead; without it the framework is simpler and faster, at the cost of "async all the way" being mandatory.
  • How do you get back to the UI thread without a context? Dispatcher.InvokeAsync / Control.BeginInvoke / MainThread.BeginInvokeOnMainThread; or capture TaskScheduler.FromCurrentSynchronizationContext() for ContinueWith.
  • Does Task.Run inside a UI app capture the context? No; the delegate starts on the pool; only the await of the Task.Run result returns to the UI context.

Common wrong answer

"ASP.NET Core has a per-request context like classic ASP.NET." Leads to wrong deadlock explanations and cargo-cult ConfigureAwait(false) everywhere in controllers.

midWhat did .NET 8 add with ConfigureAwaitOptions, and what is each option for?

Answer

.NET 8 added Task.ConfigureAwait(ConfigureAwaitOptions), a flags enum with four members. None = ConfigureAwait(false); ContinueOnCapturedContext = the default ConfigureAwait(true). SuppressThrowing makes the await not throw when the task faults or is cancelled — for "wait for it to finish, then inspect Status" patterns such as awaiting a cancelled background task during shutdown — and it is only allowed on non-generic Task (analyzer CA2261 fires on Task<T> because there would be no result to return). ForceYielding makes the continuation always run asynchronously even if the task is already complete — the task-based Task.Yield(), useful to escape a lock, a synchronous callback or a TaskCompletionSource completer's stack.

Example

// Graceful shutdown: wait for the worker without a try/catch for OperationCanceledException
await _workerTask.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);
if (_workerTask.IsFaulted) _logger.LogError(_workerTask.Exception, "worker failed");

// Guarantee we are off the completer's thread before doing heavy work
await tcs.Task.ConfigureAwait(ConfigureAwaitOptions.ForceYielding | ConfigureAwaitOptions.ContinueOnCapturedContext);

Follow-ups

  • Does SuppressThrowing mark the exception as observed? Yes — awaiting with it observes the exception, so UnobservedTaskException will not fire.
  • Does ValueTask have these? No; ValueTask.ConfigureAwait(bool) only. Convert with AsTask() if needed.
  • Older equivalent of SuppressThrowing? await Task.WhenAny(task) — a trick that completes without throwing so you can inspect the task.

Common wrong answer

"SuppressThrowing swallows exceptions for Task<T> too and returns default" — it is a compile-time/analyzer error, precisely to avoid that silent default.

seniorState the ConfigureAwait rules for a library versus an application, and justify them.

Answer

Library: use ConfigureAwait(false) on every await, including await using and await foreach (via ConfiguredAsyncDisposable and ConfiguredCancelableAsyncEnumerable), enforce with CA2007, except in the rare code that must call back on the caller's context (a UI toolkit helper, a progress callback contract). Justification: a library cannot know whether its caller blocks on a context, and skipping the marshalling is cheaper. Application: in ASP.NET Core / workers, omit it (no context; CA2007 off) — noise without benefit. In UI apps, use the default in code that touches UI and ConfigureAwait(false) in the app's own service layer, so a stray .Result in a legacy handler cannot deadlock. The senior nuance: ConfigureAwait(false) is not a promise you are off the context (synchronous completion keeps you on it), so UI code must never rely on it to run work "in the background".

Example

// Library: all three forms
await using var conn = await OpenAsync(ct).ConfigureAwait(false);
await using (conn.ConfigureAwait(false)) { }
await foreach (var row in ReadAsync(ct).WithCancellation(ct).ConfigureAwait(false)) { }

// App project: turn the analyzer off
// .editorconfig  → dotnet_diagnostic.CA2007.severity = none

Follow-ups

  • Where does the "except callbacks" case bite? IProgress<T>: Progress<T> captures the context at construction, so it is the app's job, not the library's, to marshal.
  • Does ConfigureAwait(false) in a library affect AsyncLocal / ExecutionContext? No; ExecutionContext always flows regardless of context marshalling.
  • Any performance figure? On a captured UI context each await without ConfigureAwait(false) costs a Post and a message-loop round trip — microseconds each, but thousands per second in a chatty stream parser.

Common wrong answer

"ConfigureAwait(false) everywhere, then Invoke back to the UI when needed" — a rule that ignores the synchronous-completion case and litters UI code with dispatcher calls.

seniorWhere do TaskCompletionSource continuations run, and why is RunContinuationsAsynchronously the default advice?

Answer

When you call SetResult/SetException, the task's continuations run synchronously on the calling thread by default (as long as they were registered as "execute synchronously", which await-based continuations are), before SetResult returns. That means arbitrary awaiting code runs inside whatever the completer was doing: inside a lock it holds, on a native callback thread, on a socket receive loop — causing deadlocks, stack dives and latency for the completer. TaskCreationOptions.RunContinuationsAsynchronously (.NET 4.6+) forces continuations onto the pool instead. Use it whenever the completer is infrastructure (event bridges, I/O loops, timers) or holds a lock; skip it when the completer and the awaiter are the same subsystem and you want the inline speed.

Example

// Bridging an event to a Task: complete from the event thread safely
var tcs = new TaskCompletionSource<Message>(TaskCreationOptions.RunContinuationsAsynchronously);
void Handler(object? s, Message m) { client.Received -= Handler; tcs.TrySetResult(m); }
client.Received += Handler;
using var reg = ct.Register(() => tcs.TrySetCanceled(ct));
var msg = await tcs.Task;   // continuation runs on the pool, not inside the client's dispatch loop

Follow-ups

  • How can it deadlock concretely? Completer calls SetResult while holding lock (_sync); the awaiting continuation runs inline and tries to take _sync — same thread re-enters a Monitor fine, but a SemaphoreSlim or a different lock deadlocks.
  • Why is there a "detrimentally overcorrecting" debate? Always forcing async continuations adds a pool hop to every completion; in hot paths owned end to end by one component, inline is measurably faster.
  • Does the same apply to CancellationToken.Register callbacks? Yes — they run synchronously on the thread that calls Cancel().

Common wrong answer

"SetResult just sets a flag; the awaiter picks it up later." Misses that the entire awaiting method's remaining code runs on the completer's stack.

midYou need to "get off the UI thread": Task.Yield(), ConfigureAwait(false) or Task.Run? Which guarantees what?

Answer

Only Task.Run guarantees the delegate runs on a pool thread. ConfigureAwait(false) only affects what happens after a suspension — if the awaited task is already complete, execution continues synchronously on the UI thread. Task.Yield() on a UI context posts you back to the same UI thread; it lets the message loop process pending messages first, which is useful for responsiveness but does not move work. So: CPU-heavy work goes in Task.Run; I/O-bound work needs neither; Yield is for breaking up long synchronous prefixes on the UI thread.

Example

private async void Compute_Click(object sender, EventArgs e)
{
    await Task.Yield();                                        // still UI thread afterwards
    await cache.GetAsync(key).ConfigureAwait(false);           // if cached (sync completion): still UI thread!
    var r = await Task.Run(() => HeavyCompute(input));         // the only guaranteed hop
    label.Text = r;                                            // back on UI (default ConfigureAwait)
}

Follow-ups

  • How do you assert you are off the UI thread in a test? Check SynchronizationContext.Current is null or Thread.CurrentThread.IsThreadPoolThread.
  • What about ConfigureAwaitOptions.ForceYielding? Guarantees an asynchronous continuation, but on the captured context unless combined with None; with None it does move you to the pool.
  • Which one costs a thread? Task.Run only.

Common wrong answer

"ConfigureAwait(false) guarantees the rest of the method runs on a background thread." The interviewer's next question is "and if the task was cached?".

principalPlan the migration of a large WPF (or legacy ASP.NET) codebase that is full of .Result and .Wait().

Answer

Treat it as a graph problem: the deadlocks happen where a context-bound caller blocks on a chain that captures the context. Step one is containment — an analyzer (VSTHRD002) that forbids new blocking calls and a baseline that ratchets the count down. Step two is to make the leaves honest: replace fake-async or blocking I/O with real async APIs so the chain can become async without Task.Run. Step three is to propagate async upward, one call path at a time, starting from the entry points that are cheapest to make async (event handlers become async void, commands become async Task, legacy ASP.NET pages use RegisterAsyncTask with <httpRuntime targetFramework="4.5"/>). Where a boundary genuinely cannot change yet (a synchronous interface from a framework you do not control), isolate the block behind a named adapter that uses Task.Run(...).GetAwaiter().GetResult() or, in Visual Studio-style hosts, a JoinableTaskFactory, so that it cannot deadlock even if the chain captures the context. Measure with a test SynchronizationContext that runs everything on one thread and fails on deadlock, and remove adapters as paths are completed.

Example

// Transitional adapter: the only place blocking is allowed, and it cannot deadlock
internal static class SyncBoundary
{
    public static T Run<T>(Func<Task<T>> work) => Task.Run(work).GetAwaiter().GetResult();
}
// Legacy interface implementation during migration
public Customer Load(int id) => SyncBoundary.Run(() => _repo.LoadAsync(id));

Follow-ups

  • Bottom-up or top-down? Leaves first (so real async exists), then top-down per path; doing only the top creates async-over-sync, doing only the bottom leaves deadlocks in the middle.
  • Why is ConfigureAwait(false) "everywhere" not the migration? It reduces deadlocks but keeps the blocked threads, and one third-party await without it reintroduces them; it is a mitigation, not the plan.
  • How do you keep the UI safe during the transition? A dev-time watchdog: a DispatcherTimer that logs if the UI thread has not pumped for 500 ms, catching new blocking calls in testing.

Common wrong answer

"Add ConfigureAwait(false) to everything and keep the .Result calls." The interviewer asks what happens under load and with the one NuGet package that does not use it.

4. Cancellation

asked: oftencritical9 questions

Cooperative cancellation is the part of the model most codebases get subtly wrong: tokens not forwarded, linked sources leaked, callbacks running on the wrong thread, writes cancelled halfway. Screeners check that you know cancellation is cooperative and how a task becomes Canceled; senior questions go into registration semantics, timeouts and non-cancellable operations; principal questions ask for a cancellation and shutdown policy across a distributed system.

Docs: Cancellation in managed threads · CancellationTokenSource

screenerHow does cancellation work in .NET? Can you cancel a running task?

Answer

Cancellation is cooperative. A CancellationTokenSource owns the ability to cancel; it hands out a CancellationToken struct that callees observe by polling IsCancellationRequested, calling ThrowIfCancellationRequested(), passing it to APIs that accept one, or registering a callback with Register. Nothing is forcibly stopped: a task that ignores its token keeps running to completion, and Thread.Abort throws PlatformNotSupportedException on .NET Core. So "cancelling a task" means requesting cancellation and having every layer honour it — which is why the token is threaded through every async signature.

Example

using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
try
{
    await foreach (var item in source.ReadAllAsync(cts.Token))
    {
        cts.Token.ThrowIfCancellationRequested();     // cooperative check in CPU-bound loops
        await ProcessAsync(item, cts.Token);          // forwarded to I/O
    }
}
catch (OperationCanceledException) when (cts.IsCancellationRequested) { /* expected */ }

Follow-ups

  • What happens to a cancelled Task.Run that never checks the token? It runs to the end; only if it throws OperationCanceledException with that token does the task end Canceled.
  • Is CancellationToken a class? A readonly struct wrapping a reference to the source; default is a token that can never be cancelled (CancellationToken.None).
  • What about Task.Delay(ms, ct)? Truly cancellable: the timer is disposed and the task completes Canceled immediately.

Common wrong answer

"cts.Cancel() stops the task." At screener level this is the single most common misconception; the follow-up "and if the code never checks the token?" exposes it.

screenerOperationCanceledException vs TaskCanceledException: which do you catch, and how does a task end up Canceled?

Answer

TaskCanceledException derives from OperationCanceledException; the TPL throws the derived one when you await a task that was cancelled (e.g. Task.Delay, HttpClient timeouts), while ThrowIfCancellationRequested() and most BCL/I/O APIs throw the base OperationCanceledException. Catch the base type, and usually filter with when (ct.IsCancellationRequested) to distinguish "my caller cancelled" from "something downstream timed out". An async method whose body throws any OperationCanceledException completes in the Canceled state (not Faulted); awaiting it rethrows that exception, while .Wait() wraps it in an AggregateException.

Example

try { await http.GetAsync(url, ct); }
catch (OperationCanceledException) when (ct.IsCancellationRequested) { /* caller cancelled */ }
catch (TaskCanceledException ex) when (ex.InnerException is TimeoutException) { /* .NET 5+: HttpClient.Timeout */ }
catch (OperationCanceledException) { /* something else cancelled; treat as failure */ }

Follow-ups

  • Why does HttpClient throw TaskCanceledException on timeout? Historical: it uses an internal CTS; since .NET 5 the inner exception is a TimeoutException so you can tell them apart.
  • Should you log cancellations as errors? No — a request cancelled by the client is expected; log at information/debug and count it separately.
  • What does Task.IsCanceled vs IsFaulted tell you? Canceled means an OCE was thrown; Faulted holds any other exception in Task.Exception.

Common wrong answer

"Catch TaskCanceledException" as the general handler — it misses ThrowIfCancellationRequested and every I/O API that throws the base type, so your "expected cancellation" path becomes a 500.

midWhat are the conventions for accepting and forwarding a CancellationToken?

Answer

Accept it as the last parameter, named cancellationToken, with = default on public APIs so callers without a token are not forced to write CancellationToken.None. Forward it to every async call you make (analyzer CA2016 catches misses), including Task.Delay, streams, HttpClient, EF Core, and SemaphoreSlim.WaitAsync. In CPU-bound loops call ThrowIfCancellationRequested() per iteration or per chunk. Do not accept a token you then ignore — the signature is a promise. Prefer ThrowIfCancellationRequested over returning early with partial results, because a Canceled task tells the caller unambiguously what happened; return early only where a partial result is a legitimate outcome and documented as such.

Example

public async Task<Report> BuildAsync(int customerId, CancellationToken cancellationToken = default)
{
    var orders = await _db.Orders.Where(o => o.CustomerId == customerId).ToListAsync(cancellationToken);
    var lines = new List<Line>(orders.Count);
    foreach (var o in orders)
    {
        cancellationToken.ThrowIfCancellationRequested();
        lines.Add(await PriceAsync(o, cancellationToken));
    }
    return new Report(lines);
}

Follow-ups

  • Is polling IsCancellationRequested expensive? A volatile read; negligible. Registering callbacks is the costlier operation.
  • default vs CancellationToken.None? Identical values; default is idiomatic in signatures, None reads better at call sites where you deliberately pass "no cancellation".
  • Should interfaces expose the token? Yes, on every async member; adding it later is a breaking change for implementers.

Common wrong answer

"My method is fast, so it doesn't need a token." The interviewer points out that the method calls something that is not fast, and that the signature is what lets the caller cancel the whole chain.

midOn which thread do CancellationToken.Register callbacks run, and what are the rules for them?

Answer

Callbacks run synchronously on the thread that calls Cancel(), in reverse registration order, before Cancel() returns; if the token is already cancelled at registration, the callback runs immediately on the registering thread. Exceptions from callbacks are aggregated and thrown from Cancel() as an AggregateException (with throwOnFirstException: false by default, all callbacks still run). So callbacks must be short, non-blocking and exception-free — typically tcs.TrySetCanceled(), disposing a socket, or signalling. Dispose the CancellationTokenRegistration when you no longer need it (it also supports await using via DisposeAsync, which waits for an in-flight callback), otherwise long-lived tokens accumulate registrations. UnsafeRegister skips ExecutionContext capture; .NET 8 added CancelAsync() so the canceller can await callback completion without blocking.

Example

// Make a non-cancellable wait cancellable, then always unregister
var tcs = new TaskCompletionSource(TaskCreationOptions.RunContinuationsAsynchronously);
await using (ct.UnsafeRegister(static s => ((TaskCompletionSource)s!).TrySetCanceled(), tcs))
{
    await tcs.Task;
}

// .NET 8: cancel without running callbacks on *this* thread synchronously
await cts.CancelAsync();

Follow-ups

  • Why does the registration disposal matter for RequestAborted? The request token lives for the whole request; a helper that registers per call and never disposes leaks a registration per call.
  • Can a callback deadlock the canceller? Yes: if it takes a lock the canceller holds, or blocks on a task whose continuation needs the cancelling thread.
  • Does Register capture SynchronizationContext? Only with the useSynchronizationContext: true overload; then the callback is posted to that context.

Common wrong answer

"Callbacks are queued to the thread pool." Leads to callbacks that block or throw, which then surface as exceptions from an unrelated Cancel() call — a classic confusing production bug.

midHow do you combine a caller's token with a timeout, and what leaks if you do it wrong?

Answer

Create a linked source: CancellationTokenSource.CreateLinkedTokenSource(ct), then CancelAfter(timeout) (or the constructor overload with a TimeSpan), and dispose it in a using. The linked source registers a callback on the parent token; if you do not dispose, that registration stays alive until the parent is cancelled — for a long-lived parent (application shutdown token, a connection token) that is a per-call leak of the CTS, its timer and everything it references. Disposal also stops the timer. The alternative when you only need "give up waiting" rather than "stop the work" is task.WaitAsync(timeout, ct) (.NET 6), which needs no CTS but leaves the underlying operation running.

Example

public async Task<Quote> GetQuoteAsync(string symbol, CancellationToken ct)
{
    using var linked = CancellationTokenSource.CreateLinkedTokenSource(ct);   // dispose = unregister + stop timer
    linked.CancelAfter(TimeSpan.FromSeconds(2));
    try { return await _client.GetQuoteAsync(symbol, linked.Token); }
    catch (OperationCanceledException) when (!ct.IsCancellationRequested)
    { throw new TimeoutException($"quote for {symbol} timed out"); }   // translate: caller did not cancel
}

Follow-ups

  • Why translate to TimeoutException? Callers (and retry policies) must distinguish "you cancelled" from "downstream is slow"; an OCE with the caller's token not cancelled is ambiguous.
  • What is wrong with Task.WhenAny(work, Task.Delay(timeout))? Without cancelling the delay it leaks a timer for the full timeout per call; and the work keeps running after you gave up.
  • Does CancelAfter use a timer thread? A TimerQueue timer — cheap, but thousands of un-disposed ones add up.

Common wrong answer

Not disposing the linked source ("the GC will collect it") — the interviewer asks what holds a reference to it, and the answer is the parent token's registration list.

seniorHow do you make an operation that does not accept a token cancellable, and what does "cancelled" then mean?

Answer

You cannot make the operation itself stop; you can only stop waiting for it. The idiom is task.WaitAsync(ct) (.NET 6), or before that a TaskCompletionSource cancelled from a token registration and raced with Task.WhenAny. Either way the underlying work keeps running to completion on its own, still holding its connection, buffer or lock — so "cancelled" means the caller has moved on, not that resources were released. That has design consequences: you must decide who observes the eventual result or exception (otherwise it becomes an unobserved exception), whether the abandoned work can corrupt shared state, and whether the resource limit it holds (a DB connection from a pool of 100) can be exhausted by many abandoned waits. Where the resource supports it, prefer disposing the resource in the token callback (closing the socket makes the read fail fast) — that actually stops the work.

Example

// Stop waiting (work continues)
var result = await legacyClient.FetchAsync(id).WaitAsync(TimeSpan.FromSeconds(3), ct);

// Actually stop: tear down the resource on cancel
using var reg = ct.Register(static s => ((Socket)s!).Dispose(), socket);
int n = await socket.ReceiveAsync(buffer);   // fails with ObjectDisposedException/SocketException on cancel

Follow-ups

  • What does the abandoned task's exception do? If it faults and nobody awaits it, it is an unobserved exception — attach a continuation that logs it.
  • Does WaitAsync allocate? Yes, a wrapper task and a timer/registration; fine per request, avoid per byte.
  • Pre-.NET 6 pattern? The Stephen Toub WithCancellation extension: TCS + ct.Register(() => tcs.TrySetResult(true)) + WhenAny.

Common wrong answer

"Wrap it in WaitAsync(ct) and it's cancelled" with no mention that the work continues — the interviewer asks what happens to the connection pool under a retry storm.

seniorWhen must you dispose a CancellationTokenSource, what breaks if you do it too early, and what is TryReset for?

Answer

Dispose a CTS when you own it and it has a timer (CancelAfter/timeout constructor) or is linked to another token — those hold unmanaged timer handles or registrations on a parent. A plain CTS with no timer and no links can be left to the GC, but disposing is harmless and consistent. Dispose too early and outstanding tokens still work for IsCancellationRequested checks, but Register and WaitHandle throw ObjectDisposedException and Cancel() throws — so the rule is "the owner disposes after the last consumer could register". TryReset() (.NET 6) returns a non-cancelled CTS to its initial state, clearing registrations and timers, so infrastructure like Kestrel can pool one CTS per connection instead of allocating per request; it returns false if cancellation has already been requested, in which case you must allocate a new one.

Example

// Pooled CTS for a hot path (framework-style code)
if (!_cts.TryReset()) _cts = new CancellationTokenSource();
_cts.CancelAfter(_timeout);
await HandleAsync(_cts.Token);

Follow-ups

  • Why is Cancel() after Dispose() an error but IsCancellationRequested not? The flag is a plain field; cancel needs the callback list and timer that disposal released.
  • Who disposes a linked source in a fire-and-forget scenario? The task that uses it, in a finally — never the caller who cannot know when it is done.
  • Is disposing a token possible? No; tokens are structs and never own anything.

Common wrong answer

"Always dispose the CTS in the method that created it, immediately after starting the work" — which then throws when the background work registers a callback later.

seniorHow should cancellation be used in an ASP.NET Core request, and which operations must not be cancelled?

Answer

HttpContext.RequestAborted fires when the client disconnects (or the server shuts down); minimal APIs and MVC bind a CancellationToken parameter to it automatically. Forward it into reads: database queries, downstream HTTP, cache lookups — work whose result is useless once the client is gone. Do not forward it blindly into writes that must be atomic from the caller's perspective: cancelling a multi-statement update between statements, or a "charge the card then write the order" sequence after the charge, leaves the system inconsistent. Draw a line at the point of no return: pass CancellationToken.None (with a comment) or a separate shutdown-only token past it, and ensure the operation is idempotent so a client retry after a timeout is safe. Note that EF Core cancellation aborts the command but not a partially applied transaction — the transaction rolls back on dispose, which is usually what you want before the commit and never after it.

Example

app.MapPost("/orders", async (OrderRequest req, OrderService svc, CancellationToken ct) =>
{
    var priced = await svc.PriceAsync(req, ct);             // read: cancellable
    // point of no return: payment + persistence must complete even if the client leaves
    var id = await svc.CommitAsync(priced, CancellationToken.None);
    return Results.Created($"/orders/{id}", id);
});

Follow-ups

  • Why is RequestAborted not triggered on every client timeout? With HTTP/1.1 behind some proxies the server only notices on the next write; test cancellation behaviour rather than assuming it.
  • What about graceful shutdown? IHostApplicationLifetime.ApplicationStopping is a different token; in-flight requests get the shutdown timeout to finish (HostOptions.ShutdownTimeout, 30 s by default on current hosts).
  • How do you test the "must not cancel" path? Cancel the token right after the point of no return in an integration test and assert the record exists.

Common wrong answer

"Always pass the request token to everything, that's the rule." The interviewer asks about the order that was charged but never saved.

principalDefine a cancellation and shutdown policy for a distributed workflow (API → queue → workers → downstream services).

Answer

Tokens do not cross process boundaries, so the policy is about deadlines and idempotency, not tokens. Every hop carries an absolute deadline (gRPC deadlines, an x-deadline header, a message TTL), and each service converts it into a local CTS with CancelAfter(deadline - now); a service that would exceed the deadline fails fast instead of doing useless work. Inside a process, three tokens with distinct meanings: the request/message token (caller gone), ApplicationStopping (drain: stop taking new work, finish current), and a hard-stop token that fires at the shutdown timeout. Workers commit in units that are idempotent and re-deliverable, so cancellation anywhere before the commit is safe and cancellation after the commit is ignored (CancellationToken.None past the point of no return). Kubernetes sends SIGTERM and waits terminationGracePeriodSeconds; align HostOptions.ShutdownTimeout below it and make the readiness probe fail first so the load balancer drains. Compensation (sagas) handles the cases where work cannot be undone by cancellation, and metrics separate "cancelled by caller", "deadline exceeded" and "shutdown" so you can see which one is hurting.

Example

// Worker: three tokens, one linked source per message
protected override async Task ExecuteAsync(CancellationToken stopping)
{
    await foreach (var msg in _queue.ReadAllAsync(stopping))            // stop *taking* work on drain
    {
        using var perMsg = CancellationTokenSource.CreateLinkedTokenSource(_hardStop.Token);
        perMsg.CancelAfter(msg.Deadline - _clock.GetUtcNow());
        try   { await HandleAsync(msg, perMsg.Token); await _queue.AckAsync(msg, CancellationToken.None); }
        catch (OperationCanceledException) { await _queue.NackAsync(msg, requeue: true, CancellationToken.None); }
    }
}

Follow-ups

  • Why absolute deadlines rather than per-hop timeouts? Per-hop timeouts add up beyond what the original caller waits for; a propagated deadline makes downstream work stop when it can no longer matter.
  • How do you avoid duplicate side effects on redelivery? Idempotency keys stored with the commit (or the outbox pattern), so a retried message is a no-op.
  • What breaks if ShutdownTimeout exceeds the grace period? The orchestrator SIGKILLs mid-work; in-flight messages are neither acked nor nacked until the broker's visibility timeout.

Common wrong answer

"Pass the cancellation token along with the message." Tokens are in-process objects; a principal candidate must translate them into deadlines and idempotent commits.

5. Exceptions, async void and fire-and-forget

asked: oftencritical8 questions

Where async errors go is the second most common screener chain after "what does await do": async void, AggregateException, WhenAll losing exceptions, unobserved exceptions, and the fire-and-forget request that captures a disposed DbContext. Mid-level candidates need the mechanics and a safe fire-and-forget pattern; senior candidates the "exception before the first await" subtleties; principal candidates a process-wide error policy.

Docs: Async scenarios and the "async void" guidance · Exception handling (TPL)

screenerWhy is async void dangerous, and when is it the right choice?

Answer

An async void method has no task, so the caller cannot await it, compose it, or observe its exception. When it throws, the exception is raised on the captured SynchronizationContext (a UI app shows an unhandled-exception dialog) or, without a context, directly on a thread-pool thread — which terminates the process. It also breaks testability and makes "did it finish?" unanswerable. It exists for one reason: event handler signatures are void, so UI and framework event handlers are async void by necessity; they should be thin wrappers that try/catch everything and delegate to an async Task method. Everywhere else, return Task, even if the caller discards it through a deliberate fire-and-forget helper.

Example

// Only legitimate use: an event handler, wrapped
private async void Save_Click(object sender, EventArgs e)
{
    try { await SaveAsync(); }
    catch (Exception ex) { ShowError(ex); }     // nothing else can catch it
}

// Everything else returns Task
private async Task SaveAsync() { await _repo.SaveAsync(_doc); }

Follow-ups

  • Does a try/catch around the call catch it? Only the synchronous prefix; anything after the first await escapes the caller's try.
  • Which analyzer flags it? VSTHRD100 (Microsoft.VisualStudio.Threading.Analyzers) and AsyncFixer01; there is no built-in CAxxxx rule.
  • What about async lambdas passed to Action parameters? Same thing in disguise — Parallel.ForEach(items, async x => ...) and list.ForEach(async ...) create async void delegates. VSTHRD101 flags it.

Common wrong answer

"async void is fine for fire-and-forget; I don't need the result." The interviewer asks where the exception goes and gets silence, or "it's swallowed" — which is worse than the truth (process crash).

screenerHow do exceptions surface from a task: await vs .Wait()/.Result vs GetAwaiter().GetResult()?

Answer

A faulted task stores its exceptions in Task.Exception as an AggregateException. await unwraps it: it rethrows the first inner exception with its original stack trace preserved (via ExceptionDispatchInfo), so catch (HttpRequestException) works naturally. .Wait() and .Result throw the AggregateException itself, which is why legacy code has catch (AggregateException ex) { ex.Flatten() ... }. GetAwaiter().GetResult() blocks like .Result but throws the unwrapped exception, which is why the boundary-hack idiom uses it. Cancellation follows the same path: await throws OperationCanceledException, .Wait() wraps it.

Example

Task t = Task.FromException(new InvalidOperationException("boom"));
try { await t; }                       catch (InvalidOperationException) { }   // unwrapped
try { t.Wait(); }                      catch (AggregateException) { }          // wrapped
try { t.GetAwaiter().GetResult(); }    catch (InvalidOperationException) { }   // unwrapped, still blocking

Follow-ups

  • How is the stack trace preserved across the rethrow? ExceptionDispatchInfo.Capture(ex).Throw() appends the new frames to the original trace instead of resetting it.
  • Why only the first exception? await has a single throw site; multiple exceptions exist only for WhenAll and attached child tasks — see the next question.
  • Does the state machine catch everything? Yes, including OperationCanceledException, which it routes to SetException, and the builder decides Canceled vs Faulted.

Common wrong answer

"await throws an AggregateException, so catch that." A candidate who writes catch (AggregateException) around awaits has learned the TPL from .NET 4.0 material and never verified it.

midTask.WhenAll with three failing tasks: what does await throw, and how do you see all three exceptions?

Answer

WhenAll returns a task that faults with an AggregateException containing every inner exception — but await rethrows only the first one. To see them all, keep a reference to the WhenAll task and read whenAll.Exception.InnerExceptions in the catch, or await with ConfigureAwaitOptions.SuppressThrowing (.NET 8) and inspect afterwards, or inspect the individual tasks. Also note that WhenAll only faults after all tasks complete — it does not fail fast — and that if any task is cancelled and none faulted, the result is Canceled.

Example

var all = Task.WhenAll(tasks);
try { await all; }
catch (Exception first)
{
    var every = all.Exception!.InnerExceptions;   // all of them
    _log.LogError(all.Exception, "{Count} of {Total} failed (first: {First})", every.Count, tasks.Count, first.Message);
}

// .NET 8 alternative
await all.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);
foreach (var t in tasks.Where(t => t.IsFaulted)) Handle(t.Exception!);

Follow-ups

  • How do you fail fast on the first failure? Task.WhenAny loop or Task.WhenEach (.NET 9), cancel the rest through a linked CTS when one faults.
  • Is catch (AggregateException) around await WhenAll ever right? No — await unwraps; the catch block never runs.
  • Ordering of results? Task<T[]> preserves input order regardless of completion order.

Common wrong answer

"Wrap await Task.WhenAll in catch (AggregateException) to get all exceptions." Plausible, and wrong: that handler never executes.

midWhat is an unobserved task exception, and what happens to it today?

Answer

A task that faults and whose exception is never observed — never awaited, no .Wait()/.Result/.Exception read — is "unobserved". In .NET 4.0 the finalizer of the task's exception holder rethrew it and crashed the process; since .NET 4.5 (and all of .NET Core) the default is to raise TaskScheduler.UnobservedTaskException when the task is finalized and otherwise ignore it, unless ThrowUnobservedTaskExceptions is enabled in config. Practically: fire-and-forget code that faults fails silently and late (only when the GC runs a finalization), so every service should subscribe to UnobservedTaskException to log and call SetObserved(), and code should never rely on it as its error handling.

Example

TaskScheduler.UnobservedTaskException += (s, e) =>
{
    _logger.LogError(e.Exception, "Unobserved task exception");
    e.SetObserved();
};

_ = DoWorkAsync();   // discarded on purpose? then attach an observer instead (see next question)

Follow-ups

  • When does the event fire? During finalization of the task's exception holder — seconds to minutes later, on the finalizer thread; not useful for correlating with a request.
  • Does ValueTask have this? No; an unobserved faulted ValueTask backed by an IValueTaskSource can simply lose the exception.
  • Does discarding with _ = observe the exception? No; it only silences CS4014.

Common wrong answer

"Unobserved exceptions crash the process, so fire-and-forget is safe because you'd notice." That was .NET 4.0; today they vanish, which is exactly why the question is asked.

midShow a safe fire-and-forget pattern, and explain why "Task.Run from the controller and return 202" is broken.

Answer

Safe fire-and-forget has three properties: exceptions are observed and logged, the work does not capture things that die with the request, and shutdown knows about it. A minimal helper attaches a faulted-only continuation; the robust version hands the work to a hosted service through a Channel, which owns its own DI scope and is stopped gracefully. Starting a task from a controller is broken because it captures request-scoped services: the DbContext and HttpContext are disposed when the response completes, so the background code throws ObjectDisposedException or, worse, reads a recycled HttpContext. It also dies silently on deploy — nothing waits for it.

Example

// Minimal helper (observed exceptions, still dies on shutdown)
public static void Forget(this Task task, ILogger log) =>
    task.ContinueWith(t => log.LogError(t.Exception, "background task failed"),
                      CancellationToken.None, TaskContinuationOptions.OnlyOnFaulted, TaskScheduler.Default);

// Robust: queue to a hosted service that creates its own scope
public sealed class Worker(ChannelReader<Job> jobs, IServiceScopeFactory scopes, ILogger<Worker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        await foreach (var job in jobs.ReadAllAsync(ct))
        {
            await using var scope = scopes.CreateAsyncScope();
            try { await scope.ServiceProvider.GetRequiredService<JobHandler>().RunAsync(job, ct); }
            catch (Exception ex) when (ex is not OperationCanceledException) { log.LogError(ex, "job {Id} failed", job.Id); }
        }
    }
}

Follow-ups

  • Why TaskScheduler.Default in ContinueWith? Without it, ContinueWith uses TaskScheduler.Current (CA2008); in a UI app that could be the UI scheduler.
  • Why swallow only non-cancellation exceptions? An OCE on shutdown is expected and should end the loop, not be logged as an error.
  • What about durability? An in-memory channel loses jobs on crash; if that matters, persist (outbox table or a broker) and let the worker read from there.

Common wrong answer

"Task.Run(() => service.DoWork()) in the action, return Accepted" — plausible, ships, and produces ObjectDisposedException: Cannot access a disposed context instance in production.

seniorExceptions thrown before the first await: how do async and non-async task-returning methods differ, and where does it bite?

Answer

In an async method every exception, including ones thrown synchronously before the first await, is captured into the returned task — the call itself never throws. In a non-async method that returns a task (the "elided" style), code before the inner call runs as a normal method, so an exception there is thrown synchronously at the call site. It bites in three places: Task.WhenAll(items.Select(x => F(x))) — an elided F that throws during enumeration aborts the whole call and abandons the tasks already started; a using/try/finally around a returned-not-awaited task, where disposal happens before the task completes; and stack traces, where the elided method is missing from the async trace. The rule: elide only trivial pass-throughs with no using, no try, no loop.

Example

// BUG: the connection is disposed before the query completes
public Task<int> CountAsync()
{
    using var conn = Open();
    return conn.QuerySingleAsync<int>("select count(*) from t");   // returned, not awaited
}

// Correct: await inside the using
public async Task<int> CountAsync()
{
    using var conn = Open();
    return await conn.QuerySingleAsync<int>("select count(*) from t");
}

Follow-ups

  • Which is the "argument validation" exception to the rule? A non-async wrapper that validates and throws synchronously, then calls the async core — deliberate fail-fast (see 1.4).
  • Does the analyzer help? Yes: CA2025 (.NET 9) flags disposables passed to a task that outlives the using; VSTHRD also has rules for returned-not-awaited inside using.
  • What about ValueTask-returning methods? Same rules; eliding is slightly more tempting there and equally risky.

Common wrong answer

"There's no difference except the state machine overhead, so eliding is a free optimisation." The using case is the one that reaches production.

seniorHow do try/catch/finally, exception filters and rethrow interact with await?

Answer

Since C# 6 you can await inside catch and finally blocks; the compiler hoists the pending exception into the state machine and rethrows it after the awaits complete, preserving the trace through ExceptionDispatchInfo. Exception filters (when) run at throw time, before any unwinding, without an await, which makes them ideal for separating expected cancellation from real failures: catch (Exception ex) when (ex is not OperationCanceledException). For rethrowing: throw; preserves the trace, throw ex; resets it, and ExceptionDispatchInfo.Capture(ex).Throw() rethrows from another location (a later continuation, another thread) with the original trace intact — which is what the awaiter does internally. A finally with an await that itself throws replaces the original exception, as in synchronous code.

Example

ExceptionDispatchInfo? edi = null;
try { await ProcessAsync(ct); }
catch (Exception ex) when (ex is not OperationCanceledException) { edi = ExceptionDispatchInfo.Capture(ex); }
finally { await _conn.CloseAsync(); }                 // await in finally: C# 6+
if (edi is not null)
{
    await _audit.WriteAsync(edi.SourceException);     // async work before rethrow
    edi.Throw();                                      // original stack trace
}

Follow-ups

  • Why prefer a filter over catch-and-rethrow? Filters do not unwind the stack when they return false, so the debugger and crash dumps still see the original throw site.
  • Can you await inside a lock? No (CS1996); the same applies to the C# 13 Lock type. Use SemaphoreSlim or restructure.
  • What does Task.Exception contain for a Canceled task? Null; the OCE is only surfaced on await.

Common wrong answer

"Use throw ex; to rethrow after logging" — resets the stack trace to the catch block, making the production log useless.

principalDefine a process-wide error-handling policy for an async service: what is caught where, what stops the host, what gets retried?

Answer

Three layers with different jobs. At the request edge, one IExceptionHandler (.NET 8) or exception middleware maps exceptions to problem-details responses and logs once — handlers do not catch to log. In hosted services, the default BackgroundServiceExceptionBehavior.StopHost (since .NET 6) means an unhandled exception in ExecuteAsync stops the process: keep it, because a silently dead worker is worse than a restart, but make per-item failures non-fatal inside the loop, distinguishing transient (retry with Polly v8 ResiliencePipeline, then dead-letter) from permanent (log, skip, alert) and cancellation (exit quietly). At process level, subscribe to AppDomain.UnhandledException and TaskScheduler.UnobservedTaskException for last-resort logging, and let the orchestrator restart. Fire-and-forget goes only through the approved queue so nothing is lost on shutdown, and every retry has a budget and an idempotency key. The tests for the policy are: kill a downstream, cancel a request mid-flight, throw inside one job — the service must stay up, the job must land in the dead-letter store, and the log must show exactly one entry per failure.

Example

builder.Services.AddExceptionHandler<ProblemDetailsExceptionHandler>();
builder.Services.AddProblemDetails();
builder.Services.Configure<HostOptions>(o =>
{
    o.BackgroundServiceExceptionBehavior = BackgroundServiceExceptionBehavior.StopHost;   // default, made explicit
    o.ShutdownTimeout = TimeSpan.FromSeconds(20);                                         // below the orchestrator grace period
});
builder.Services.AddResiliencePipeline("job", p => p
    .AddRetry(new() { MaxRetryAttempts = 3, BackoffType = DelayBackoffType.Exponential, UseJitter = true })
    .AddTimeout(TimeSpan.FromSeconds(10)));

Follow-ups

  • Why not Ignore for the background exception behaviour? It is the pre-.NET 6 behaviour: the service dies quietly and the process looks healthy; only choose it with your own supervision loop.
  • How do you avoid double logging? Log where you handle, rethrow where you do not; middleware logs the request-level failure once with the correlation id.
  • What about exceptions in IHostedService.StartAsync? They fail host startup (by design); use ServicesStartConcurrently (.NET 8) carefully as it changes failure ordering.

Common wrong answer

"Catch everything at every layer and log it" — produces triple logs, hides dead workers and retries non-idempotent work. The principal answer assigns each layer one responsibility.

6. Composition and concurrency control

asked: oftencritical9 questions

Running many asynchronous operations at once and keeping them under control: WhenAll/WhenAny/WhenEach, throttling with SemaphoreSlim or Parallel.ForEachAsync, producer/consumer with Channel<T>, bridging callbacks with TaskCompletionSource. This is where coding interviews live ("fetch these 1,000 URLs, at most 10 at a time") and where senior candidates show they know the failure modes (unbounded fan-out, async void lambdas, inline continuations).

Docs: Task.WhenAll · System.Threading.Channels · Parallel.ForEachAsync

screenerWhat is the difference between awaiting in a loop and Task.WhenAll? Is concurrent the same as parallel?

Answer

await inside a foreach is sequential: each operation starts only after the previous one completed, so ten 100 ms calls take a second. Starting all the tasks first (they are hot as soon as the method is called) and then awaiting Task.WhenAll makes them concurrent: the calls overlap in flight and total time is about the slowest one. Concurrency here needs no extra threads — the operations wait on I/O simultaneously — which is different from parallelism, where CPU work runs on several threads at once. The senior addendum: unbounded concurrency is a bug too; a thousand concurrent HTTP calls need a limiter.

Example

// Sequential: ~1 s
foreach (var id in ids) results.Add(await LoadAsync(id, ct));

// Concurrent: ~100 ms, still one thread most of the time
var tasks = ids.Select(id => LoadAsync(id, ct)).ToList();   // ToList: start them all now
var results = await Task.WhenAll(tasks);

Follow-ups

  • Why ToList()? Without materialising, a lazy Select passed to WhenAll still works (WhenAll enumerates it once), but iterating it twice would start the calls twice.
  • When is sequential correct? When each step depends on the previous result, when the target needs ordering, or when the downstream cannot take the load.
  • What does WhenAll return for Task<T>? Task<T[]> in input order.

Common wrong answer

"WhenAll runs the tasks in parallel on multiple threads." It starts nothing and creates no threads; the tasks were already running when they were created.

screenerTask.WhenAll vs Task.WaitAll vs Task.WhenAny vs Task.WaitAny.

Answer

The When* methods return a task you await — non-blocking; the Wait* methods block the calling thread until the condition holds, and belong to pre-async TPL code. WhenAll completes when every task has completed (all results, or an aggregate fault); WhenAny completes as soon as one does and returns that task (not its result), leaving the others running. WaitAll throws an AggregateException; WaitAny returns the index. In modern code WaitAll/WaitAny only appear inside dedicated non-pool threads or legacy console tools.

Example

Task<string> first = await Task.WhenAny(primary, secondary);   // returns the Task, not the string
string value = await first;                                    // observe result/exception

// Race with a timeout without leaking the timer (.NET 6+): prefer WaitAsync
string v = await primary.WaitAsync(TimeSpan.FromSeconds(2), ct);

Follow-ups

  • Why await the returned task again? WhenAny never faults; the inner task's exception is only observed when you await it.
  • What happens to the losers in WhenAny? They keep running; cancel them via a linked CTS if their work is now pointless, and observe their exceptions.
  • Is WaitAll ever fine? In a Main without async or on a dedicated thread; never on a pool thread under load.

Common wrong answer

"WhenAny returns the result of the fastest task." It returns the task; candidates then write var result = await Task.WhenAny(...) and are confused by the type.

midFetch 1,000 URLs with at most 10 in flight. Show the options and their trade-offs.

Answer

Three idioms. Parallel.ForEachAsync (.NET 6) with MaxDegreeOfParallelism is the shortest and handles cancellation and exceptions; its default degree is ProcessorCount, which is wrong for I/O — set it explicitly. A SemaphoreSlim(10) with WaitAsync/Release in try/finally around each task plus WhenAll is the classic and lets you collect results in order. A bounded Channel with ten consumers is the choice when items arrive over time rather than as a list. Do not use Parallel.ForEach with an async lambda (it becomes async void and returns immediately), and do not start all 1,000 tasks and "await in batches of ten" — the batches still start everything at once.

Example

// 1. Parallel.ForEachAsync (.NET 6+)
var results = new ConcurrentBag<(string url, int len)>();
await Parallel.ForEachAsync(urls, new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
    async (url, token) => results.Add((url, (await http.GetStringAsync(url, token)).Length)));

// 2. SemaphoreSlim + WhenAll, results in input order
using var gate = new SemaphoreSlim(10);
var lens = await Task.WhenAll(urls.Select(async url =>
{
    await gate.WaitAsync(ct);
    try { return (await http.GetStringAsync(url, ct)).Length; }
    finally { gate.Release(); }
}));

Follow-ups

  • Which one stops on the first failure? Parallel.ForEachAsync cancels remaining iterations when one throws and rethrows after in-flight ones finish; the semaphore version runs everything and reports via WhenAll.
  • Why is 10 the wrong constant? It should come from the downstream's capacity and HttpClient connection limits (MaxConnectionsPerServer); measure.
  • What about Parallel.ForEachAsync on an IAsyncEnumerable source? Supported; useful for streaming input.

Common wrong answer

Parallel.ForEach(urls, async url => await http.GetStringAsync(url)) — compiles, "works" in a demo, and in production completes before any download finishes while running unbounded.

midWhat does Task.WhenEach (.NET 9) solve, and what did people do before?

Answer

Task.WhenEach(tasks) returns an IAsyncEnumerable<Task> that yields each task as it completes, so you can process results in completion order with await foreach — for example, streaming search results as providers respond. Before .NET 9 the idiom was a WhenAny loop: await WhenAny over the remaining set, remove the winner, repeat. That is O(n²) in registrations (each WhenAny registers continuations on every remaining task) and allocates a new WhenAny task per iteration; the other pre-9 workaround was Stephen Toub's "Interleaved" trick with an array of TaskCompletionSources. WhenEach is O(n) and honours cancellation through WithCancellation.

Example

await foreach (var done in Task.WhenEach(providerTasks).WithCancellation(ct))
{
    try { Render(await done); }                       // completion order
    catch (Exception ex) { RenderError(ex); }         // one failure does not stop the stream
}

Follow-ups

  • Does it start the tasks? No, like WhenAll it only observes already-running tasks.
  • Typed variant? Task.WhenEach<T>(IEnumerable<Task<T>>) yields Task<T>.
  • When is WhenAll still better? When you need all results before doing anything, and failure of one means failure of all.

Common wrong answer

"The WhenAny loop is fine at any scale." Correct for five tasks; at a few thousand the quadratic registrations become visible in profiles.

midWhy can't you await inside a lock, and what do you use for mutual exclusion in async code?

Answer

lock is Monitor.Enter/Exit, which is thread-affine: the thread that entered must exit, and it is re-entrant per thread. An await may resume on a different thread, so the compiler forbids await in a lock body (CS1996) — and the same applies to the C# 13 System.Threading.Lock type, which is a faster lock but still synchronous. For mutual exclusion around asynchronous work use SemaphoreSlim(1, 1) with WaitAsync in try/finally; it is not re-entrant, so design call chains to avoid re-acquiring. Alternatives: an AsyncLock from Nito.AsyncEx, a single-consumer Channel (serialising work instead of locking), or ConcurrentExclusiveSchedulerPair. Keep synchronous lock for short, non-awaiting critical sections — it is still the right tool there.

Example

private readonly SemaphoreSlim _gate = new(1, 1);

public async Task<Token> GetTokenAsync(CancellationToken ct)
{
    if (_cached is { } t && t.Expires > _clock.GetUtcNow()) return t;   // fast path without the lock
    await _gate.WaitAsync(ct);
    try
    {
        if (_cached is { } t2 && t2.Expires > _clock.GetUtcNow()) return t2;  // double-check
        return _cached = await _auth.RefreshAsync(ct);
    }
    finally { _gate.Release(); }
}

Follow-ups

  • What if the awaiting code inside the semaphore calls back into a method that takes it again? Deadlock — SemaphoreSlim has no owner; that is the price of async locks.
  • Manual Monitor.Enter around an await? Throws SynchronizationLockException on exit from another thread, or silently leaves the lock held.
  • Is Interlocked/Volatile enough sometimes? Yes for single-value state (a cached Task<T>, counters) — prefer lock-free where the invariant is one field.

Common wrong answer

"Use Monitor.Enter and Monitor.Exit manually so you can await in between." It compiles and fails at runtime on the first resumption on a different thread.

seniorExplain System.Threading.Channels: bounded vs unbounded, full modes, single-reader/writer options, and completion.

Answer

Channel<T> (.NET Core 3.0) is an async producer/consumer queue with a Writer and Reader. Unbounded channels never block writers, so memory is the limit — acceptable only when producers are naturally bounded. Bounded channels apply back-pressure via BoundedChannelFullMode: Wait (default; WriteAsync awaits space), DropOldest/DropNewest (telemetry-style lossy), DropWrite (reject the new item; TryWrite returns false). SingleReader/SingleWriter options let the implementation skip synchronisation — set them when true. Producers signal the end with Writer.Complete() (optionally with an exception), consumers use ReadAllAsync(ct) or the WaitToReadAsync/TryRead loop, and Reader.Completion is a task that completes when the channel is drained. .NET 9 added CreateUnboundedPrioritized for priority ordering. Compared with TPL Dataflow or Rx it is lower-level and allocation-light — the right primitive for in-process queues.

Example

var ch = Channel.CreateBounded<Event>(new BoundedChannelOptions(10_000)
{
    FullMode = BoundedChannelFullMode.Wait, SingleReader = true, SingleWriter = false
});

// Producer(s): back-pressure when full
await ch.Writer.WriteAsync(evt, ct);
// ...
ch.Writer.Complete();

// Consumer
await foreach (var e in ch.Reader.ReadAllAsync(ct)) await HandleAsync(e, ct);

Follow-ups

  • How do you batch reads? WaitToReadAsync then drain with TryRead in a loop up to a batch size — no allocation per item.
  • Why not BlockingCollection? It blocks threads; channels await. BlockingCollection is for dedicated-thread consumers only.
  • What does ConcurrentQueue + polling cost? Either latency (sleep interval) or CPU (spin); channels give you both zero-latency wakeup and zero idle cost.

Common wrong answer

"An unbounded channel is fine, the consumer is fast." Then the downstream slows down for a minute and the process is OOM-killed; the senior answer starts from the bound.

seniorBridge a callback- or event-based API to a Task with TaskCompletionSource. What are the traps?

Answer

Create a TaskCompletionSource<T> (or the non-generic one, .NET 5) with TaskCreationOptions.RunContinuationsAsynchronously, subscribe the handler, complete it with TrySetResult/TrySetException/TrySetCanceled, and unsubscribe in all paths. The traps: using Set* instead of TrySet* (throws if a timeout and the callback race); forgetting to unsubscribe, which leaks the handler and can complete a stale TCS; completing synchronously inside the event source's dispatch loop without RunContinuationsAsynchronously, so the awaiter's continuation runs on the library's thread; and never completing (a callback that is never called) — add a timeout or a cancellation registration so the awaiter cannot hang forever.

Example

public static Task<int> WaitForExitAsync(Process p, CancellationToken ct)
{
    var tcs = new TaskCompletionSource<int>(TaskCreationOptions.RunContinuationsAsynchronously);
    p.EnableRaisingEvents = true;
    p.Exited += (_, _) => tcs.TrySetResult(p.ExitCode);
    if (p.HasExited) tcs.TrySetResult(p.ExitCode);                   // race: exited before we subscribed
    var reg = ct.Register(() => tcs.TrySetCanceled(ct));
    tcs.Task.ContinueWith(_ => reg.Dispose(), TaskScheduler.Default);   // always unregister
    return tcs.Task;
}
// (.NET 5+ has Process.WaitForExitAsync built in — the same shape.)

Follow-ups

  • Why check HasExited after subscribing? The event may have fired before subscription; checking after closes the race in both orders.
  • What about APIs with a completion callback that passes an error code? Map error codes to exceptions in TrySetException; do not throw inside the callback.
  • How is this different from Task.Factory.FromAsync? FromAsync is the ready-made bridge for the APM Begin/End pattern; TCS is the general tool.

Common wrong answer

"SetResult from the event handler; it's just a flag." Then the whole awaiting method runs inside the library's event dispatch — and the process deadlocks the day the library holds a lock while raising the event.

seniorChoose between Parallel.For/PLINQ, Parallel.ForEachAsync, and N Task.Runs for a workload. What decides?

Answer

The nature of the work decides. CPU-bound over an in-memory collection: Parallel.For/ForEach or PLINQ — they partition the range, keep the degree of parallelism near core count, and block the caller until done (so call them from a dedicated context, not a request thread). I/O-bound over a collection: Parallel.ForEachAsync with an explicit degree — its body is async, it does not hold threads while awaiting, and it handles cancellation. N Task.Run calls is the naive form of the first: fine for a handful of coarse jobs, wrong for ten thousand items (task and scheduling overhead, no partitioning). Mixed work is the interesting case: chunk the CPU part and run the chunks through Parallel.For inside a bounded Parallel.ForEachAsync, or split into stages connected by channels.

Example

// CPU-bound, in-memory: partitioned, no async needed
Parallel.For(0, pixels.Length, new ParallelOptions { MaxDegreeOfParallelism = Environment.ProcessorCount }, i => pixels[i] = Blur(pixels, i));

// I/O-bound: bounded async concurrency
await Parallel.ForEachAsync(files, new ParallelOptions { MaxDegreeOfParallelism = 8 },
    async (f, ct) => await blob.UploadAsync(f, ct));

Follow-ups

  • What is wrong with Parallel.ForEach in ASP.NET Core? It occupies pool threads with CPU work and blocks the request thread; under concurrent requests it starves I/O continuations.
  • PLINQ ordering? Unordered by default; AsOrdered() costs buffering.
  • Does Parallel.ForEachAsync partition? It pulls items one at a time from the enumerator under a lock, so it is fine for I/O but not a substitute for range partitioning on tight CPU loops.

Common wrong answer

"Task.Run per item, then WhenAll" for a CPU-bound list of ten thousand — it works in a demo and thrashes the pool in production.

principalDesign a resilient fan-out: a request must call 20 downstream services and return within 800 ms. Which primitives and policies?

Answer

Structure it as a deadline-driven aggregate with partial results. One linked CTS with CancelAfter(800 ms) for the whole fan-out; each call additionally wrapped in its own shorter timeout and a resilience pipeline (Polly v8 ResiliencePipeline or AddStandardResilienceHandler from Microsoft.Extensions.Http.Resilience in .NET 8+: retry with jitter, circuit breaker, per-attempt timeout, bulkhead). Start all 20 concurrently, consume with Task.WhenEach so fast results are usable immediately, and at the deadline return what you have with per-source status rather than failing everything. Bound total concurrency per downstream (bulkhead) so one slow dependency cannot exhaust connections for the others, cancel the stragglers (do not leave them running against a service that is already struggling), and observe their exceptions. Make the trade-offs explicit: retries inside an 800 ms budget are usually one at most; circuit breakers protect the downstream but need a fallback; hedged requests cut tail latency at the cost of load. Emit metrics per downstream (latency histogram, timeouts, breaker state) so the aggregate SLO can be attributed.

Example

using var budget = CancellationTokenSource.CreateLinkedTokenSource(ct);
budget.CancelAfter(TimeSpan.FromMilliseconds(800));

// task → source name, so results can be attributed; each call: 400 ms timeout, 1 retry, breaker, bulkhead
var calls = sources.ToDictionary(s => CallWithPolicyAsync(s, budget.Token), s => s.Name);
var partial = new Dictionary<string, SourceResult>();
await foreach (var t in Task.WhenEach(calls.Keys))
{
    await ((Task)t).ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);    // never throw here
    partial[calls[t]] = t.IsCompletedSuccessfully ? SourceResult.Ok(t.Result) : SourceResult.Failed(t);
}
return new Aggregate(partial, degraded: partial.Values.Any(v => !v.Ok));

Follow-ups

  • Why cancel stragglers instead of letting them finish? A downstream under load is hurt by abandoned requests; cancelling closes the connection and frees the bulkhead slot.
  • When would you not retry at all? Non-idempotent calls, and any time the retry cannot fit in the remaining budget.
  • Where does caching fit? Serve stale-while-revalidate for sources that are down; the breaker's fallback is the last good value.

Common wrong answer

"WhenAll with a timeout, and retry the whole batch on failure." Loses partial results, multiplies load on the failing dependency, and cannot meet the deadline.

7. ValueTask and allocation

asked: sometimescritical8 questions

ValueTask is the favourite "do you really understand it" probe: cheap to ask, hard to answer well. Interviewers want the when (hot paths that usually complete synchronously, pooled sources), the rules (await once, never concurrently, never block unless completed) and the why (IValueTaskSource reuse). Mid-level answers state the rules; senior answers explain them from the implementation; principal answers make the public-API decision and know that .NET 11's runtime-async narrows the gap.

Docs: ValueTask<TResult> · Understanding the Whys, Whats, and Whens of ValueTask (Toub)

screenerWhat is ValueTask<T> and when should you return it instead of Task<T>?

Answer

ValueTask<T> is a struct that holds either a result T, a Task<T>, or an IValueTaskSource<T> plus a token. Its purpose is to avoid allocating a Task<T> on the path that completes synchronously — a cache hit, a buffered read, a "nothing to do" — and, with a pooled IValueTaskSource, even on asynchronous completions. Return it when you have measured a hot path where synchronous completion is common and the allocation matters (parsers, sockets, pipelines, DisposeAsync/MoveNextAsync contracts). Otherwise return Task: it is simpler, unrestricted (await many times, block, cache) and the default the BCL itself uses for most public APIs. ValueTask<T> arrived with .NET Core 2.0 (C# 7), the non-generic ValueTask and IValueTaskSource with .NET Core 2.1.

Example

public ValueTask<Config> GetAsync(string key, CancellationToken ct)
{
    if (_cache.TryGetValue(key, out var cfg))
        return ValueTask.FromResult(cfg);          // struct only, no heap allocation
    return LoadAndCacheAsync(key, ct);             // async path: wraps a Task<Config>
}
private async ValueTask<Config> LoadAndCacheAsync(string key, CancellationToken ct) { /* ... */ }

Follow-ups

  • How big is the saving? One Task<T> object (~ 64–80 bytes on 64-bit) per synchronous call; meaningful at millions of calls per second, invisible in a request handler.
  • Does ValueTask remove the state machine allocation on the async path? No — that needs PoolingAsyncValueTaskMethodBuilder (7.5).
  • Why do bool and small-int results not need it? Task<bool> and Task<int> for -1..8 are cached by the builder already.

Common wrong answer

"ValueTask is a faster Task, so use it everywhere." It is slower to await in the asynchronous case (bigger struct, extra indirection) and carries usage restrictions; the interviewer will ask for the rules next.

midState the ValueTask consumption rules and what happens if you break them.

Answer

Await a ValueTask exactly once, and then never touch it again. Do not await it twice, do not await it from two places concurrently, do not call .Result or GetAwaiter().GetResult() unless IsCompleted is true, do not store it in a field to await later, do not mix await with AsTask(). If you need any of that, call AsTask() once and use the task, or Preserve() (.NET 5) to get a ValueTask that is safe to await multiple times. Breaking the rules works by accident when the ValueTask wraps a result or a Task, and fails when it wraps a pooled IValueTaskSource: at best an InvalidOperationException from the token check, at worst you read another operation's result. Analyzer CA2012 catches the common shapes.

Example

ValueTask<int> vt = stream.ReadAsync(buffer, ct);
int n = await vt;            // OK
// int again = await vt;     // WRONG: second await
// vt.Result                 // WRONG unless vt.IsCompleted

// Need to hand it around? Convert once.
Task<int> t = stream.ReadAsync(buffer, ct).AsTask();
await Task.WhenAll(t, other);

Follow-ups

  • Is it OK to check IsCompletedSuccessfully and read Result? Yes — that is the sanctioned fast-path pattern for hand-written hot loops.
  • Why does Task.WhenAll not take ValueTasks? Because it would need to observe each one exactly once and hold them; callers convert with AsTask().
  • What does Preserve() cost? It allocates a Task when the source is an IValueTaskSource; free otherwise.

Common wrong answer

"It behaves like Task, just without the allocation." The follow-up "so I can await it twice?" separates people who have read the docs from people who have not.

midWhy do those rules exist? What is IValueTaskSource doing underneath?

Answer

The rules exist because a ValueTask may be backed by a reusable object. IValueTaskSource<T> has three members — GetStatus(token), OnCompleted(continuation, state, token, flags) and GetResult(token) — and the ValueTask carries a short token identifying "this use". After GetResult is called, the source may reset itself and be reused for the next operation with a new token: sockets, PipeReader, Channel readers and ManualResetValueTaskSourceCore all do this. A second await on the old ValueTask presents a stale token — detected if the source checks it, undetected (wrong result) if it has already been recycled with the same token value. Blocking with .Result before completion is undefined because the source is not required to support synchronous waiting.

Example

public interface IValueTaskSource<out TResult>
{
    ValueTaskSourceStatus GetStatus(short token);
    void OnCompleted(Action<object?> continuation, object? state, short token, ValueTaskSourceOnCompletedFlags flags);
    TResult GetResult(short token);   // after this, the source may be reset and reused
}

Follow-ups

  • What do the OnCompletedFlags mean? Whether to capture ExecutionContext and/or the SynchronizationContext for the continuation — the source implements what ConfigureAwait means for it.
  • Who resets the source? The owner (e.g. the Socket's cached SocketAsyncEventArgs-based source) after GetResult returns.
  • Does the compiler know any of this? No; ValueTask is just a struct with an awaiter to the compiler — hence analyzers rather than compiler errors.

Common wrong answer

"The rules are just style guidance to avoid confusion." A mid-level candidate should connect the rules to object reuse.

midHow much does ValueTask actually save, and what does it cost on the asynchronous path?

Answer

On the synchronous path it saves exactly one allocation: the Task<T> the builder would otherwise create (unless the value is one the builder caches). On the asynchronous path it saves nothing by itself — the async method still allocates its boxed state machine (which is the task) and the ValueTask simply wraps it — and it costs a little: a 16-byte struct (24 with the token on some layouts) copied around, an extra type check in the awaiter, and the restrictions. With a pooled IValueTaskSource the asynchronous path becomes allocation-free too, which is how Socket and System.IO.Pipelines achieve zero-allocation reads. So the honest benchmark compares three cases: sync hit, async miss, and pooled async, and only the first and third show a win.

Example

// BenchmarkDotNet shape for an honest comparison
[Benchmark] public async Task<int> TaskHit()      => await GetTask(hit: true);      // allocates Task<int> unless cached value
[Benchmark] public async Task<int> ValueTaskHit() => await GetValueTask(hit: true); // 0 B
[Benchmark] public async Task<int> TaskMiss()     => await GetTask(hit: false);     // 1 box (the Task)
[Benchmark] public async Task<int> ValueTaskMiss()=> await GetValueTask(hit: false);// 1 box, slightly slower

Follow-ups

  • Which BCL APIs return ValueTask? Stream.ReadAsync(Memory), Socket.ReceiveAsync(Memory), ChannelReader.ReadAsync, PipeReader.ReadAsync, IAsyncEnumerator.MoveNextAsync, IAsyncDisposable.DisposeAsync.
  • How does .NET 11 change the picture? Runtime-async allocates continuation objects only on suspension, reuses them, and the JIT folds ValueTask.FromResult/Task.FromResult intrinsics — the synchronous-path gap between the two shrinks, which is why some teams are re-evaluating ValueTask in public APIs.
  • Is ValueTask (non-generic) worth it? Only with pooling; a completed non-generic Task is already the cached Task.CompletedTask.

Common wrong answer

"ValueTask avoids the state machine allocation." It does not; that confusion leads to ValueTask sprinkled over methods that always suspend, for zero benefit.

seniorWhat does [AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))] do, and when is it worth it?

Answer

By default an async ValueTask<T> method that suspends boxes its state machine into a new object that acts as the task. PoolingAsyncValueTaskMethodBuilder<T> (.NET 6, usable per method since C# 10 allowed the attribute on methods) instead rents that box from a pool, implements IValueTaskSource on it, and returns it to the pool after GetResult — so a suspending call can be allocation-free. It is worth it for very hot, short-lived asynchronous operations in infrastructure (custom transports, serializers), after measuring. It is not a default: the pool has its own contention and cache costs, it makes the "await once" rules hard requirements (a second await is now guaranteed to hit a recycled object), and Toub's own guidance is that the benefit rarely justifies the risk outside framework code. In .NET 5 the same behaviour was a runtime-wide environment switch (DOTNET_SYSTEM_THREADING_POOLASYNCVALUETASKS), removed in .NET 6 in favour of the explicit attribute.

Example

[AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))]
private async ValueTask<int> ReadFrameAsync(CancellationToken ct)
{
    var header = await _pipe.ReadAsync(ct);   // suspends often; box is pooled
    return Parse(header);
}

Follow-ups

  • What is the pool size and policy? A small per-core cache plus a shared stack, bounded; overflow simply allocates. Not configurable per method.
  • Does this interact with .NET 11 runtime-async? Methods already using pooling builders opt out of runtime-async ("pooled methods opt out"), so they keep the compiler state machine.
  • How do you prove it helped? Allocation counters in BenchmarkDotNet ([MemoryDiagnoser]) and Gen0 rate in production; if Gen0 did not move, remove it.

Common wrong answer

"Pooling is always a win, so put the attribute on every ValueTask method." A senior candidate should know the pool costs and the guidance that it is rarely justified.

seniorWhy do IAsyncDisposable.DisposeAsync and IAsyncEnumerator.MoveNextAsync return ValueTask, and how do you implement them well?

Answer

Both are called at very high frequency and usually complete synchronously — most MoveNextAsync calls yield an item that is already buffered, most DisposeAsync implementations have nothing asynchronous to do — so a Task return type would allocate on every call for nothing. Implement them by returning default/ValueTask.CompletedTask or ValueTask.FromResult(true) on the synchronous path and delegating to an async ValueTask helper only when real asynchronous work is needed. For DisposeAsync, also implement Dispose for callers that cannot await, and follow the "dispose async core" pattern in inheritable types.

Example

public sealed class BatchReader : IAsyncDisposable
{
    private readonly Stream _s;
    public ValueTask DisposeAsync()
    {
        if (_s is null) return ValueTask.CompletedTask;   // nothing to do: no allocation
        return _s.DisposeAsync();                          // delegate the real work
    }
}

// Enumerator fast path
public ValueTask<bool> MoveNextAsync()
    => _buffer.TryDequeue(out _current) ? ValueTask.FromResult(true) : FetchAndMoveAsync();

Follow-ups

  • Does await using honour ConfigureAwait? Yes: await using (x.ConfigureAwait(false)), via ConfiguredAsyncDisposable.
  • Why not new ValueTask(Task.CompletedTask)? Works, but default/ValueTask.CompletedTask is the idiom and avoids the wrapped-task branch in the awaiter.
  • Should DisposeAsync throw? Avoid it; disposal runs in finally paths, and an exception there masks the original one.

Common wrong answer

"Return Task.CompletedTask" — does not compile; or making every DisposeAsync an async method, which allocates a state machine box on every suspension for objects that never needed one.

seniorSketch a custom IValueTaskSource<T> using ManualResetValueTaskSourceCore<T>. When would you write one?

Answer

You write one when a reusable object represents a repeating asynchronous operation and you want zero allocations per operation — a connection's "wait for next frame", a custom timer, a signal that many producers set and one consumer awaits. ManualResetValueTaskSourceCore<T> (.NET Core 3.0) does the hard part: it stores the continuation, result or exception, handles the token and the completion flags, and gives you Reset(). Your type wraps it, implements the three interface members by forwarding, and exposes a method that returns new ValueTask<T>(this, _core.Version). The reset-after-GetResult discipline is exactly what makes the consumption rules non-negotiable for callers.

Example

sealed class FrameSignal : IValueTaskSource<Frame>
{
    private ManualResetValueTaskSourceCore<Frame> _core = new() { RunContinuationsAsynchronously = true };

    public ValueTask<Frame> WaitAsync() => new(this, _core.Version);
    public void Publish(Frame f) => _core.SetResult(f);
    public void Fail(Exception e) => _core.SetException(e);

    public Frame GetResult(short token)
    {
        try { return _core.GetResult(token); }
        finally { _core.Reset(); }                      // ready for the next WaitAsync
    }
    public ValueTaskSourceStatus GetStatus(short token) => _core.GetStatus(token);
    public void OnCompleted(Action<object?> c, object? s, short token, ValueTaskSourceOnCompletedFlags f) => _core.OnCompleted(c, s, token, f);
}

Follow-ups

  • What breaks if Publish is called twice before a wait? SetResult on an already-completed core throws; your type must serialise producers or queue.
  • Why RunContinuationsAsynchronously = true? Same reason as for TCS: the publisher should not execute the consumer's continuation inline.
  • Is this how Channel<T> works? Yes, its reader uses the same core for ReadAsync/WaitToReadAsync.

Common wrong answer

"Subclass Task or TaskCompletionSource" — Task is not designed for reuse; the whole point is a resettable source.

principalYou own a widely used library. Decide the return type policy (Task vs ValueTask) and its evolution.

Answer

Default to Task on public surface: it is composable, cacheable, unrestricted, and consumers make mistakes with ValueTask that then get filed as your bugs. Use ValueTask where an interface forces it (IAsyncDisposable, IAsyncEnumerator), and on documented hot paths where you have measured synchronous-completion rates above, say, 80% or where you back it with a pooled source — and say so in the XML docs. Changing a return type later is a binary and source breaking change (different types, WhenAll call sites break), so the decision is per major version: add a ValueTask overload rather than swapping, or introduce the new API on a new type. Track the platform: the .NET 11 runtime-async work (folding FromResult intrinsics, reused continuations, cheaper suspension) reduces Task's cost enough that the 2026 conversation in the community is partly about migrating back; a principal engineer keeps the policy tied to measurements on the current runtime, not to 2018 advice.

Example

// Policy in code: Task by default, ValueTask where the contract demands or the hot path is proven
public Task<Order> GetOrderAsync(int id, CancellationToken ct = default);           // public, general
public ValueTask<bool> TryReadAsync(out Frame frame, CancellationToken ct = default); // documented hot path
ValueTask IAsyncDisposable.DisposeAsync();                                            // contract

Follow-ups

  • How do you protect consumers from misuse? Ship the analyzer (CA2012 is built in), document "await once", and avoid returning pooled sources from public APIs unless the type name signals it.
  • How do you measure the real-world sync ratio? A counter on the fast path in a diagnostics build, or an EventCounter that ships with the library.
  • What about ref struct/Span parameters with async? Not possible across awaits; use Memory<T> in async signatures, Span<T> in synchronous ones (see 10.7).

Common wrong answer

"Switch all public methods to ValueTask in the next major for performance." Breaks every consumer for an unmeasured gain and imports their bugs into your issue tracker.

8. IAsyncEnumerable and async streams

asked: sometimescritical7 questions

Async streams (C# 8 / .NET Core 3.0) come up whenever data arrives over time: paging APIs, database cursors, message streams, SSE. Interviewers check the pull model, the two-token cancellation dance ([EnumeratorCancellation] plus WithCancellation), laziness and disposal, and — freshly — the .NET 10 built-in System.Linq.AsyncEnumerable. Senior and principal questions turn to back-pressure and streaming HTTP responses.

Docs: Generate and consume async streams · System.Linq.AsyncEnumerable (.NET 10) · Breaking change: AsyncEnumerable in .NET 10

screenerWhat is IAsyncEnumerable<T>, and how does it differ from Task<IEnumerable<T>> and from IEnumerable<Task<T>>?

Answer

IAsyncEnumerable<T> is a pull-based sequence where each step may be asynchronous: GetAsyncEnumerator() returns an enumerator with ValueTask<bool> MoveNextAsync() and Current, consumed with await foreach and produced with async iterators using yield return. Task<IEnumerable<T>> is one asynchronous wait for the whole batch, then synchronous iteration — fine for small result sets, wrong for large or unbounded ones. IEnumerable<Task<T>> is a synchronous sequence of independent promises — all started eagerly, no ordering by completion. Async streams give you items as they become available, with bounded memory and per-item cancellation.

Example

public async IAsyncEnumerable<Order> GetOrdersAsync([EnumeratorCancellation] CancellationToken ct = default)
{
    string? cursor = null;
    do
    {
        var page = await _api.GetPageAsync(cursor, ct);   // one page at a time
        foreach (var o in page.Items) yield return o;      // hand items out as they arrive
        cursor = page.Next;
    } while (cursor is not null);
}

await foreach (var order in GetOrdersAsync(ct)) Process(order);

Follow-ups

  • What does await foreach expand to? GetAsyncEnumerator(ct), a loop of await MoveNextAsync(), and await DisposeAsync() in a finally.
  • Why is MoveNextAsync a ValueTask? Most steps complete synchronously from a buffer; a Task per item would allocate needlessly.
  • Can it be infinite? Yes — a message stream; the consumer breaks out, which disposes the enumerator.

Common wrong answer

"It's a list of tasks you await one by one." Confuses it with IEnumerable<Task<T>> and misses the pull/back-pressure model entirely.

midHow does cancellation reach an async iterator? Explain [EnumeratorCancellation] and WithCancellation.

Answer

MoveNextAsync() takes no token, so cancellation must be attached when the enumerator is created. GetAsyncEnumerator(CancellationToken) accepts it, and await foreach (... in source.WithCancellation(ct)) is the syntax that passes it. On the producer side, an async iterator declares a CancellationToken parameter marked [EnumeratorCancellation]; the compiler-generated enumerator then uses the token passed to GetAsyncEnumerator, and if the iterator was also called with its own token, the two are linked. A missing attribute triggers warning CS8425; a token parameter without it is simply the one the caller passed at call time. The old System.Linq.Async package had a MoveNextAsync(ct) extension, but it only called ThrowIfCancellationRequested before delegating — it never cancelled the pending step.

Example

// Producer
public async IAsyncEnumerable<Line> ReadLinesAsync(Stream s, [EnumeratorCancellation] CancellationToken ct = default)
{
    using var r = new StreamReader(s);
    while (await r.ReadLineAsync(ct) is { } line) yield return Parse(line);
}

// Consumer: token supplied at enumeration time, plus ConfigureAwait for library code
await foreach (var line in ReadLinesAsync(stream).WithCancellation(ct).ConfigureAwait(false)) { }

Follow-ups

  • Which token wins if both are given? Neither — they are linked; cancelling either cancels the iterator's token.
  • Does the consumer's token cancel an in-flight MoveNextAsync? Only if the iterator body forwards it to the awaited operation — cancellation is still cooperative.
  • What about LINQ operators in .NET 10? Their callbacks receive a CancellationToken so the chain propagates it: Select(async (x, ct) => ...).

Common wrong answer

"Pass the token to MoveNextAsync" — the interface has no such overload; the extension that existed was a check, not a cancellation.

midLINQ over IAsyncEnumerable: what changed in .NET 10, and what breaks when you upgrade?

Answer

.NET 10 ships System.Linq.AsyncEnumerable in the box (and as a NuGet package of the same name for older targets), a from-scratch implementation of LINQ operators for IAsyncEnumerable<T>. It replaces the community System.Linq.Async package (Ix.NET), whose extension methods now collide: a direct reference produces ambiguity errors, so remove it or upgrade to Ix.NET 7.0, which defers to the platform; for transitive references use <ExcludeAssets>compile</ExcludeAssets>. Naming changed: the *Await/*AwaitWithCancellation operators became overloads of the plain names, and their async callbacks now take a CancellationToken: SelectAwait(async x => ...) becomes Select(async (x, ct) => ...). Synchronous-callback operators (Where(x => ...)) are source-compatible.

Example

// .NET 10 built-in LINQ for async streams
var totals = await orders
    .Where(o => o.Status == Status.Paid)
    .Select(async (o, ct) => await _fx.ConvertAsync(o.Total, "EUR", ct))   // was SelectAwaitWithCancellation
    .GroupBy(t => t.Currency)
    .ToListAsync(ct);

// csproj during multi-targeting (net8.0 + net10.0)
// <PackageReference Include="System.Linq.AsyncEnumerable" Version="10.0.*" />

Follow-ups

  • Why did Microsoft rewrite rather than adopt Ix.NET? Naming predated current design guidelines, and the platform should own LINQ for a platform interface; the maintainers petitioned for inclusion.
  • Is ToBlockingEnumerable() part of this? No, that came in .NET 7 for handing async streams to legacy synchronous consumers (it blocks — use on dedicated threads only).
  • Performance difference? The new implementation avoids some allocations and integrates with ValueTask-based MoveNextAsync; measure before assuming.

Common wrong answer

"Add System.Linq.Async from NuGet" as the 2026 answer — shows the candidate has not touched .NET 10; the follow-up about ambiguity errors confirms it.

midWhen does an async iterator's body run, what happens on early exit, and what are the try restrictions?

Answer

Calling the iterator method runs nothing — it returns an object; the body starts on the first MoveNextAsync and runs lazily up to each yield return. If the consumer breaks out of await foreach (or throws), DisposeAsync runs on the enumerator, which executes any pending finally blocks (and using/await using disposals) in the iterator and then stops — code after the current yield never runs. As with synchronous iterators, a yield return cannot sit inside a try that has a catch (only try/finally), and cannot appear in a catch or finally; await is fine in all of them. Since C# 13 the compiler also fixed a long-standing hole: MoveNext on a disposed enumerator now returns false without running more user code.

Example

public async IAsyncEnumerable<Row> QueryAsync([EnumeratorCancellation] CancellationToken ct = default)
{
    await using var conn = await _factory.OpenAsync(ct);   // runs on first MoveNextAsync
    await using var reader = await conn.ExecuteReaderAsync(_sql, ct);
    try
    {
        while (await reader.ReadAsync(ct)) yield return Map(reader);
    }
    finally { _metrics.QueryFinished(); }                  // runs even if the consumer breaks early
}

Follow-ups

  • How do you handle exceptions from the source without a catch around yield? Read the item inside a helper with try/catch, then yield outside it.
  • Can two consumers share one enumerator? No — enumerators are single-consumer; call GetAsyncEnumerator per consumer, or materialise.
  • Does DisposeAsync run if the consumer never calls MoveNextAsync? Yes, and the body simply never started.

Common wrong answer

"The query runs when I call the method; await foreach just reads the results." Leads to "the connection is opened even though nobody enumerated" reasoning and to broken resource accounting.

seniorBack-pressure: how does IAsyncEnumerable compare with Channel<T> and with Rx/IObservable?

Answer

IAsyncEnumerable is pull-based: the producer runs only when the consumer asks for the next item, so back-pressure is intrinsic and buffering is zero unless you add it — but a slow consumer stalls the producer completely, and there is no fan-out. Channel<T> decouples producer and consumer with an explicit buffer; the bound gives you tunable back-pressure and drop policies, multiple producers and consumers, and a natural bridge from push sources (events) to a pull consumer (ReadAllAsync is itself an IAsyncEnumerable). Rx is push-based with rich composition (time windows, merges, retries) but no built-in back-pressure — a fast producer overwhelms a slow observer unless you buffer or sample. Choose pull for sequential processing of one stream, channels for decoupling and multiplicity, Rx for event-time operators.

Example

// Push source → bounded buffer → pull consumer
var ch = Channel.CreateBounded<Tick>(new BoundedChannelOptions(1_000) { FullMode = BoundedChannelFullMode.DropOldest });
feed.OnTick += t => ch.Writer.TryWrite(t);                 // never blocks the feed thread
await foreach (var tick in ch.Reader.ReadAllAsync(ct))     // consumer pulls at its own pace
    await StoreAsync(tick, ct);

Follow-ups

  • How do you add prefetch to an async stream? Wrap it: a producer task fills a bounded channel from the source, the consumer reads the channel — you have just built a buffered operator.
  • Can you merge two IAsyncEnumerables? Not with built-in LINQ in .NET 10; a channel plus two producer loops is the practical merge.
  • What about System.Reactive and ToAsyncEnumerable? Ix.NET provides bridges both ways; the async-enumerable side buffers unboundedly by default, which is the trap.

Common wrong answer

"IAsyncEnumerable is basically an observable." The direction of control is the whole difference; a senior candidate must name pull vs push.

seniorReturning IAsyncEnumerable<T> from an ASP.NET Core endpoint: what happens, and what are the pitfalls?

Answer

MVC and minimal APIs stream it: System.Text.Json serialises the sequence as a JSON array, writing elements as they are produced and flushing in chunks (since .NET 6; in 3.x MVC buffered async enumerables, and Newtonsoft still buffers). The enumeration happens after the action method returns but before the response completes, so request-scoped services (the DbContext behind an EF Core AsAsyncEnumerable()) are still alive — that part works. Pitfalls: any exception after the first element is written arrives mid-body (the client sees a broken JSON array and a 200 status), so validate up front; the client must actually consume as a stream (JsonSerializer.DeserializeAsyncEnumerable) to benefit; buffering proxies defeat the purpose; and you cannot set headers or status after the first flush. Use it for large exports and live feeds; for small results a list is simpler and lets you return a proper error.

Example

app.MapGet("/orders/export", (AppDb db, CancellationToken ct) =>
    db.Orders.AsNoTracking().OrderBy(o => o.Id).AsAsyncEnumerable());   // streamed as a JSON array

// Client side: stream too
await foreach (var o in http.GetFromJsonAsAsyncEnumerable<Order>("/orders/export", ct)) { }

Follow-ups

  • How do you signal errors mid-stream? You cannot change the status; use NDJSON/SSE with per-item envelopes, or gRPC server streaming with proper trailers.
  • Does cancellation on client disconnect stop the query? Yes if the endpoint binds CancellationToken and EF forwards it — the iterator's token comes from RequestAborted.
  • What about Task.WhenAll over items inside the iterator? Not on the same DbContext; it is not thread-safe.

Common wrong answer

"Controllers can't return IAsyncEnumerable, materialise to a list." Wrong since .NET Core 3.0 (and streamed since .NET 6); the interviewer wants the mid-stream error pitfall.

principalDesign a streaming export API for multi-GB datasets: format, cancellation, memory, resumability.

Answer

Pick a framing that survives partial failure: NDJSON or CSV rather than one giant JSON array, so each line is independently parseable and a broken stream is detectable. Produce with an async iterator over a keyset-paginated query (ordered by a stable key, never OFFSET), AsNoTracking, batch size tuned to keep memory flat, and write through HttpResponse.BodyWriter with periodic FlushAsync so proxies and clients see progress. Bind RequestAborted and forward it into the query so a disconnect stops the database work; put a per-request deadline on top. Make it resumable: accept a from=<last key> parameter (or a Range-like header) and emit the key in each line, so a client can restart without re-reading. Bound concurrency of exports per tenant with a semaphore or rate limiter (one export can saturate a database), compress at the transport, and prefer handing very large or slow exports to a background job that writes to blob storage with a signed URL — streaming is for "start now, bounded time", not for hour-long jobs. Server-Sent Events (.NET 10 TypedResults.ServerSentEvents) suit live feeds rather than exports.

Example

app.MapGet("/export", async (long? from, AppDb db, HttpResponse res, CancellationToken ct) =>
{
    res.ContentType = "application/x-ndjson";
    long last = from ?? 0;
    while (!ct.IsCancellationRequested)
    {
        var batch = await db.Rows.AsNoTracking().Where(r => r.Id > last).OrderBy(r => r.Id).Take(5_000).ToListAsync(ct);
        if (batch.Count == 0) break;
        foreach (var r in batch) { await JsonSerializer.SerializeAsync(res.Body, r, cancellationToken: ct); await res.Body.WriteAsync("\n"u8.ToArray(), ct); }
        last = batch[^1].Id;
        await res.Body.FlushAsync(ct);                     // progress visible; memory stays at one batch
    }
});

Follow-ups

  • Why keyset over offset? OFFSET re-scans skipped rows (quadratic), and rows inserted mid-export shift pages; a key cursor is O(batch) and stable.
  • How do you keep the database happy? Read replica, snapshot isolation or a consistent read timestamp, and a concurrency cap per tenant.
  • When is a background job with a file better? When exports exceed proxy timeouts, need retries, or are requested repeatedly — generate once, serve from storage.

Common wrong answer

"Load into a list and return it, the framework streams it anyway" — the list is the memory problem; the interviewer wants keyset pagination and flush behaviour.

9. Async in ASP.NET Core and hosted services

asked: sometimescritical7 questions

The place where the abstract model meets a real host: Kestrel's pool threads, request-scoped lifetimes, BackgroundService semantics, DbContext thread-safety and capacity. Interviewers for backend roles use these to check that you have shipped async services rather than read about them. The senior questions are about queues and shutdown; the principal question is a capacity model.

Docs: ASP.NET Core best practices · Worker services and BackgroundService · David Fowler's async guidance

screenerWhy should ASP.NET Core handlers be async? What do you gain, and what do you not gain?

Answer

Kestrel runs each request on a thread-pool thread. If the handler awaits I/O, that thread is returned to the pool during the wait and can serve another request; if it blocks, it is unavailable and the pool must inject more threads, slowly. So async handlers buy concurrency and resilience under load with a fixed, small thread count, and they keep the server responsive when a downstream is slow. They do not make an individual request faster — the database round trip takes the same time — and they do not help for CPU-bound handlers, where the thread is genuinely busy. The tell: an async server's throughput degrades gracefully when a dependency slows down; a blocking one falls off a cliff.

Example

// One pool thread can interleave thousands of these while the database works
app.MapGet("/users/{id}", async (int id, AppDb db, CancellationToken ct) =>
    await db.Users.FindAsync([id], ct) is { } u ? Results.Ok(u) : Results.NotFound());

Follow-ups

  • How many concurrent requests can N threads serve? With async: limited by memory and downstream capacity, not N. With blocking: at most N in flight, then queueing.
  • Is a synchronous handler ever fine? Pure in-memory work (a health check, a computed value) — no I/O, nothing to await.
  • What about Task<IActionResult> vs IActionResult when nothing is awaited? Return the synchronous type; an async method with no awaits just adds a state machine and a compiler warning.

Common wrong answer

"Async makes each request faster because it runs in the background." The interviewer follows with "then why is p50 unchanged after you made it async?".

midList the ASP.NET Core async anti-patterns you look for in code review.

Answer

The recurring ones: blocking on tasks (.Result, .Wait(), GetAwaiter().GetResult()) anywhere in the request path; Task.Run to "make it faster"; async void or async lambdas passed as Action; starting background work from a request that captures HttpContext, a scoped DbContext or IHttpContextAccessor; not forwarding RequestAborted; synchronous reads of Request.Body or writes to Response.Body (Kestrel throws InvalidOperationException: Synchronous operations are disallowed since 3.0 unless AllowSynchronousIO is enabled — the fix is async I/O, not the flag); System.Threading.Timer callbacks touching scoped services; and Parallel.ForEach or PLINQ inside handlers. Also: returning a Task from inside a using without awaiting it (5.6), and per-request HttpClient instances instead of IHttpClientFactory.

Example

// Three anti-patterns in five lines
public IActionResult Post([FromBody] Dto dto)
{
    var user = _users.GetAsync(dto.Id).Result;                 // blocking
    _ = Task.Run(() => _db.Audit.Add(new Audit(user)));        // captures scoped DbContext
    using var sr = new StreamReader(Request.Body); var raw = sr.ReadToEnd();   // sync body read: throws
    return Ok();
}

Follow-ups

  • Why is AllowSynchronousIO = true wrong? It re-enables thread-blocking I/O for the whole server to paper over one call site; fix the call site.
  • Why is IHttpContextAccessor unsafe off the request thread? It is backed by an AsyncLocal; after the request completes the context is recycled and may belong to another request.
  • Which tool catches these automatically? Analyzers (VSTHRD002/100/101, CA2025), ASP.NET Core's own analyzers for sync I/O, and Ben.BlockingDetector at runtime.

Common wrong answer

"Set AllowSynchronousIO to true, it's a harmless compatibility flag." Reveals the candidate fixes symptoms; the interviewer wants the reason the flag exists.

midWhat are the rules for BackgroundService.ExecuteAsync: startup, exceptions, shutdown?

Answer

ExecuteAsync is called from StartAsync, which returns as soon as ExecuteAsync yields for the first time (or completes). If your implementation runs synchronously for a long time — a blocking loop, a heavy synchronous prefix — host startup stalls behind it, so yield early (await Task.Yield() or an early await). Since .NET 6 an unhandled exception in ExecuteAsync stops the host (BackgroundServiceExceptionBehavior.StopHost, logged as critical) — before that it died silently — so catch per-item failures inside the loop and let only fatal ones escape. On shutdown the stoppingToken is cancelled and StopAsync waits for ExecuteAsync up to HostOptions.ShutdownTimeout (30 s by default on current hosts, 5 s on old ones); treat OperationCanceledException from the token as the normal exit, flush what you must with CancellationToken.None, and finish within the timeout.

Example

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    await Task.Yield();                                             // let the host finish starting
    using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30));
    try
    {
        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            try { await SyncAsync(stoppingToken); }
            catch (Exception ex) when (ex is not OperationCanceledException) { _log.LogError(ex, "sync failed"); }
        }
    }
    catch (OperationCanceledException) { /* shutdown */ }
    finally { await FlushAsync(CancellationToken.None); }          // bounded: must fit in ShutdownTimeout
}

Follow-ups

  • What does ServicesStartConcurrently (.NET 8) change? Hosted services start in parallel instead of in registration order — faster startup, but ordering dependencies must be explicit.
  • Where is StopAsync ordering? Reverse registration order by default; ServicesStopConcurrently parallelises it.
  • How do you run several loops in one service? Start them as tasks and await Task.WhenAll them, each with the same stoppingToken.

Common wrong answer

"ExecuteAsync runs on its own thread, so a blocking while loop is fine." Host startup hangs; the candidate then blames the framework.

midWhy does Task.WhenAll over the same DbContext throw, and how do you use scoped services from background work?

Answer

DbContext is not thread-safe and supports one operation at a time; concurrent queries on the same instance throw InvalidOperationException: A second operation was started on this context instance before a previous operation completed. Concurrency needs separate contexts: an IDbContextFactory<T> per parallel branch, or sequential awaits. For background work, never capture the request's scope; inject IServiceScopeFactory into the hosted service, create a scope per unit of work with CreateAsyncScope(), resolve the DbContext from it and dispose the scope when done. Singletons (hosted services) that inject scoped services directly fail at startup with a validation error in Development, or silently hold a stale context in Production.

Example

// Wrong: same context, concurrent
var a = db.Orders.CountAsync(ct); var b = db.Users.CountAsync(ct);
await Task.WhenAll(a, b);                                       // throws

// Right: a context per branch
await using var db1 = await _factory.CreateDbContextAsync(ct);
await using var db2 = await _factory.CreateDbContextAsync(ct);
var (orders, users) = (await db1.Orders.CountAsync(ct), await db2.Users.CountAsync(ct));   // or WhenAll on the two

Follow-ups

  • Is the concurrency detector always reliable? It catches most cases; some interleavings corrupt the change tracker before it fires — treat it as a safety net, not a guarantee.
  • Does Task.WhenAll with two different repositories help? Only if they resolve different context instances; in one scope they share the same one.
  • Connection cost of a context per branch? Each opens a pooled connection; bound the fan-out or you exhaust the pool.

Common wrong answer

"EF Core handles concurrency; the error is a bug in my query." The candidate has not internalised that the context is a unit of work, not a connection pool.

seniorDesign an in-process background queue for an API: back-pressure, durability, shutdown, observability.

Answer

A bounded Channel<WorkItem> registered as a singleton, written by request handlers with TryWrite (or WriteAsync with a short timeout) and consumed by one BackgroundService with N worker loops, each creating its own DI scope per item. Back-pressure surfaces at the edge: when the channel is full, return 503 with Retry-After or 429, and expose queue depth as a gauge with an alert. Durability: an in-memory channel loses items on crash or deploy, so either accept that (idempotent, re-derivable work like cache warming) or write the work to a table/broker first (outbox) and use the channel only as a wake-up signal. Shutdown: stop accepting (Writer.Complete() on ApplicationStopping), drain within ShutdownTimeout, and requeue or persist what is left. Observability: items enqueued/processed/failed counters, processing-time histogram, queue depth, and correlation ids carried in the item so logs join up with the originating request.

Example

builder.Services.AddSingleton(Channel.CreateBounded<WorkItem>(new BoundedChannelOptions(5_000) { FullMode = BoundedChannelFullMode.Wait }));
builder.Services.AddSingleton(sp => sp.GetRequiredService<Channel<WorkItem>>().Reader);
builder.Services.AddSingleton(sp => sp.GetRequiredService<Channel<WorkItem>>().Writer);
builder.Services.AddHostedService<QueueWorker>();

app.MapPost("/thumbnails", (ThumbnailRequest req, ChannelWriter<WorkItem> q) =>
    q.TryWrite(new WorkItem(req, Activity.Current?.Id)) ? Results.Accepted() : Results.StatusCode(503));

Follow-ups

  • Why not a ConcurrentQueue and a timer? Polling latency vs CPU; channels wake the consumer immediately and idle for free.
  • How many workers? Bound by the downstream (database connections, CPU), not by "as many as possible"; make it configuration.
  • When do you graduate to a broker? When work must survive restarts, be shared across instances, or be retried with visibility timeouts.

Common wrong answer

"An unbounded channel; the worker will catch up." The interviewer asks what happens during a ten-minute database slowdown and the answer is an OOM kill and lost work.

seniorMiddleware and response-writing rules: awaiting next, writing after the response started, and RequestAborted.

Answer

Middleware must await next(context) — never next(context).Wait() — and must not write to the response after calling next if a downstream component already started it (Response.HasStarted): headers and status are frozen after the first flush, so exception-handling middleware checks it and either rethrows or aborts. Use Response.OnStarting to set headers late. Large bodies go through Response.BodyWriter (a PipeWriter) or Body.WriteAsync with cancellation; Response.StartAsync() sends headers early for streaming. Everything I/O-bound in middleware takes context.RequestAborted, and long-running work must observe it because Kestrel does not abort the handler for you — a disconnected client's request keeps running until it finishes or checks the token.

Example

app.Use(async (ctx, next) =>
{
    ctx.Response.OnStarting(() => { ctx.Response.Headers["X-Trace"] = Activity.Current?.Id; return Task.CompletedTask; });
    try { await next(ctx); }
    catch (Exception ex) when (!ctx.Response.HasStarted)
    {
        ctx.Response.StatusCode = 500;
        await ctx.Response.WriteAsJsonAsync(new { error = ex.Message }, ctx.RequestAborted);
    }
});

Follow-ups

  • What does .Wait() on next do under load? Classic sync-over-async in the hottest path of the server; starvation within seconds.
  • Why is writing after HasStarted an error? The status line and headers are already on the wire; you can only append body bytes or abort the connection.
  • Does IExceptionHandler (.NET 8) handle this? Yes — it is invoked only when the response has not started; otherwise the exception propagates and the connection is reset.

Common wrong answer

"Catch the exception after next and set the status code" without checking HasStarted — throws InvalidOperationException in the one case (streaming) where you needed it most.

principalBuild a capacity model: a 4-core pod, handlers that either block 50 ms or await 50 ms per request. What can it serve, and what protects it?

Answer

Use Little's law: concurrency = throughput × latency. With blocking handlers, concurrency is bounded by pool threads: 4 min threads → about 80 requests/s at 50 ms; the pool then injects about one thread per second, so reaching 1,000 req/s needs ~50 threads and takes ~45 s of degraded latency, during which queues build and clients time out — and each retry makes it worse. With async handlers, threads are not the bound: 1,000 req/s × 50 ms = 50 requests in flight, served comfortably by a handful of threads; the real limits become the downstream (database connections, say 100 in the pool → 2,000 req/s at 50 ms), memory per request, and CPU for serialisation. The protective layers: a concurrency limiter (Microsoft.AspNetCore.RateLimiting, .NET 7, with a queue and a 503 on overflow) sized from the downstream's capacity; Kestrel's MaxConcurrentConnections; per-dependency bulkheads; and horizontal scaling triggered by queue length or latency, not CPU. Validate the model with a load test that ramps until the limiter engages, and watch threadpool-queue-length to confirm the pool is not the bottleneck.

Example

builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = 503;
    o.AddConcurrencyLimiter("db", c => { c.PermitLimit = 80; c.QueueLimit = 200; c.QueueProcessingOrder = QueueProcessingOrder.OldestFirst; });
});
app.UseRateLimiter();
app.MapGet("/orders/{id}", GetOrder).RequireRateLimiting("db");   // sized from the connection pool, not from threads

Follow-ups

  • Why not scale on CPU? Starvation and downstream saturation show low CPU; latency and queue depth are the signals.
  • Where does SetMinThreads fit in the model? Nowhere long-term: it changes the ramp time for the blocking case, not the ceiling.
  • How does retry behaviour change the numbers? Client retries multiply arrival rate exactly when capacity is lowest; budget retries and use jitter, or the model collapses.

Common wrong answer

"The thread pool scales automatically, so the pod handles whatever comes." A principal candidate must name the actual bound (downstream capacity), the ramp problem, and a limiter.

10. Internals: awaiters, builders and ExecutionContext

asked: sometimesnice to know7 questions

midWrite out the awaitable/awaiter pattern precisely, and explain each member's role.

Answer

An awaitable exposes GetAwaiter(); the awaiter must have bool IsCompleted { get; }, a GetResult() method (returning void or the value, and throwing on failure), and implement INotifyCompletion.OnCompleted(Action); optionally ICriticalNotifyCompletion.UnsafeOnCompleted(Action). The compiler evaluates GetAwaiter() once, checks IsCompleted to take the synchronous fast path, otherwise hands the awaiter and the state machine to the builder's AwaitUnsafeOnCompleted (or AwaitOnCompleted for non-critical awaiters), which arranges for MoveNext to be called when the awaiter fires the continuation; on resume it calls GetResult(). OnCompleted must flow ExecutionContext; UnsafeOnCompleted may skip it because the builder already captured it — which is why it is faster and why the BCL awaiters implement it.

Example

public readonly struct DelayAwaiter : ICriticalNotifyCompletion
{
    private readonly Task _t;
    public DelayAwaiter(TimeSpan d) => _t = Task.Delay(d);
    public bool IsCompleted => _t.IsCompleted;
    public void GetResult() => _t.GetAwaiter().GetResult();
    public void OnCompleted(Action c) => _t.GetAwaiter().OnCompleted(c);
    public void UnsafeOnCompleted(Action c) => _t.GetAwaiter().UnsafeOnCompleted(c);
}

Follow-ups

  • Why is the awaiter usually a struct? To avoid an allocation per await on the fast path; it lives in the state machine as a field while suspended.
  • What does GetResult() do on a cancelled task? Throws TaskCanceledException; on a faulted one, rethrows the first inner exception via EDI.
  • Where does ConfigureAwait fit? It returns a different awaitable (ConfiguredTaskAwaitable) whose awaiter passes a "don't capture context" flag when registering.

Common wrong answer

"The awaitable must implement an IAwaitable interface." There is none; it is duck-typed, and knowing that is the point of the question.

midWhat is an AsyncMethodBuilder, which members does the compiler call, and where are custom builders used?

Answer

The builder is the object the compiler uses to turn a state machine into a return value. For each async method it calls Create(), stores the builder in the state machine, calls Start(ref stateMachine) (which runs MoveNext synchronously under a captured ExecutionContext), reads .Task to return, and inside MoveNext calls AwaitUnsafeOnCompleted/AwaitOnCompleted on suspension, SetResult on success, SetException on failure, and SetStateMachine (legacy hook). Which builder is used is decided by the return type's [AsyncMethodBuilder] attribute (C# 7) or, since C# 10, an attribute on the method itself. Custom builders power ValueTask (AsyncValueTaskMethodBuilder), pooling (PoolingAsyncValueTaskMethodBuilder), IAsyncEnumerable's iterator builder, Unity's UniTask, and "task-like" types in game engines and actor frameworks that want different scheduling or zero-allocation semantics.

Example

// Sketch of what the compiler emits for: async Task<int> F() { await X(); return 1; }
struct FStateMachine : IAsyncStateMachine
{
    public int state; public AsyncTaskMethodBuilder<int> builder; TaskAwaiter awaiter;
    public void MoveNext()
    {
        try
        {
            if (state != 0) { awaiter = X().GetAwaiter(); if (!awaiter.IsCompleted) { state = 0; builder.AwaitUnsafeOnCompleted(ref awaiter, ref this); return; } }
            awaiter.GetResult();
            builder.SetResult(1);
        }
        catch (Exception e) { builder.SetException(e); }
    }
    public void SetStateMachine(IAsyncStateMachine sm) => builder.SetStateMachine(sm);
}

Follow-ups

  • Why is the state machine passed by ref? It is a struct; passing by reference avoids copies and lets the builder box it exactly once on first suspension.
  • What does Start do with ExecutionContext? Captures it, runs MoveNext, restores it — so the synchronous prefix cannot leak AsyncLocal changes to the caller.
  • Can a method-level builder change the return type? No; it must produce the declared type, but it can change how (pooling, custom scheduling).

Common wrong answer

"async only works with Task/ValueTask; the compiler special-cases them." The attribute-driven extensibility is exactly what the question probes.

midHow do ExecutionContext and AsyncLocal<T> flow across awaits, and what does not flow?

Answer

ExecutionContext is the ambient state the runtime carries with a logical flow of execution: AsyncLocal<T> values (and thus Activity.Current, logging scopes, IHttpContextAccessor) plus the security context. The builder captures it when an await suspends and restores it before running the continuation, on whatever thread that is, so an AsyncLocal set before an await is visible after it. Flow is copy-on-write and downward only: a value set inside a called async method after its first await is not visible to the caller when the call returns, because the callee's continuation ran with a copy. ThreadStatic/ThreadLocal do not flow — they belong to the physical thread. ExecutionContext.SuppressFlow() stops capture for fire-and-forget work so ambient request state does not leak into it. SynchronizationContext is not part of ExecutionContext; it is captured separately by the awaiter. .NET 11 optimises the common case: when nothing needs restoring, the capture/restore cycle is skipped.

Example

static readonly AsyncLocal<string?> Tenant = new();

async Task Outer()
{
    Tenant.Value = "acme";
    await Inner();
    Console.WriteLine(Tenant.Value);   // "acme" — Inner's change did not flow back up
    using (ExecutionContext.SuppressFlow())
        _ = Task.Run(() => Console.WriteLine(Tenant.Value));   // null: not flowed into background work
}
async Task Inner() { await Task.Yield(); Tenant.Value = "other"; }

Follow-ups

  • What is the performance cost of AsyncLocal? Each Value set allocates a new immutable context map; heavy use in hot paths shows up in profiles — set once per request, not per call.
  • Why does Activity.Current disappear in a Task.Run after the request ended? The AsyncLocal flowed, but the activity was stopped/disposed with the request; the flowed reference is stale.
  • Does ConfigureAwait(false) affect flow? No — ExecutionContext flows regardless; only context marshalling is skipped.

Common wrong answer

"Use [ThreadStatic] to carry per-request state through async code." Works until the first await resumes on another thread, and then produces cross-request data leaks.

seniorWhat exactly happens in AwaitUnsafeOnCompleted for a Task, and how do continuations get executed?

Answer

On first suspension the builder boxes the state machine into an IAsyncStateMachineBox object that also is the returned Task<T> (since .NET Core 2.1), storing the captured ExecutionContext in it. If the awaiter is a Task awaiter, the builder short-circuits: it registers the box itself as the task's continuation — no delegate, no closure — via Task.UnsafeSetContinuationForAwait. If a context must be honoured, it wraps in a SynchronizationContextAwaitTaskContinuation or TaskSchedulerAwaitTaskContinuation. For a non-Task awaiter it passes a cached Action (the box's MoveNextAction) to UnsafeOnCompleted. When the antecedent completes, it runs its continuation list: a single box is invoked inline on the completing thread (unless RunContinuationsAsynchronously forces a queue), which is why long chains can run deep on one stack; the runtime guards against stack overflow by checking remaining stack (RuntimeHelpers.TryEnsureSufficientExecutionStack) and queueing to the pool when it runs low. On resume, ExecutionContext.RunInternal restores the captured context and calls MoveNext.

Example

// Observable consequence: continuations of a Task run inline on the completing thread
var tcs = new TaskCompletionSource();
var t = Task.Run(async () => { await tcs.Task; Console.WriteLine(Environment.CurrentManagedThreadId); });
await Task.Delay(50);
Console.WriteLine(Environment.CurrentManagedThreadId);   // e.g. 1
tcs.SetResult();                                          // prints 1: the continuation ran here, inline
await t;

Follow-ups

  • Why "Unsafe"? It skips the awaiter-level ExecutionContext capture because the builder already captured it into the box — one capture instead of two.
  • Multiple awaiters on one task? The continuation field becomes a list; they run in registration order on completion.
  • What changes with .NET 11 runtime-async? No compiler box; the runtime allocates a continuation object with the live locals at the suspension point, and reuses it where it can.

Common wrong answer

"Each await allocates a closure and a delegate for the rest of the method." True of ContinueWith chains, false for await since 2.1 — the whole optimisation story is the box-as-task.

seniorDebug vs Release state machines, hoisted locals, and how async stack traces became readable.

Answer

In Debug the compiler emits the state machine as a class so the debugger can inspect it and Edit-and-Continue works; in Release it is a struct to avoid allocations on the synchronous path. Every local whose lifetime crosses an await is hoisted into a field of the state machine (named like <name>5__2), which is why large locals and long-lived buffers should be scoped tightly. The generated MoveNext lives on a nested type named <MethodName>d__N, and in .NET Framework stack traces showed exactly that, plus builder frames. .NET Core 2.1 cleaned this up: the runtime's stack-trace formatting maps <Foo>d__3.MoveNext() back to Foo(), hides AsyncMethodBuilderCore.Start and friends, and exception traces already looked like the logical call chain. .NET 11 runtime-async does the same for live stacks seen by profilers and debuggers, dropping from ~13 frames to ~5 for a three-deep chain.

Example

// .NET Framework 4.x exception trace (abridged)
at App.Svc.<LoadAsync>d__3.MoveNext()
--- End of stack trace from previous location where exception was thrown ---
at System.Runtime.CompilerServices.TaskAwaiter.ThrowForNonSuccess(Task task)
at App.Svc.<RunAsync>d__2.MoveNext()

// .NET Core 2.1+ / .NET 10
at App.Svc.LoadAsync()
at App.Svc.RunAsync()

Follow-ups

  • Why do Debug benchmarks mislead? Class state machine, no inlining, no tiering: allocation numbers are meaningless; always benchmark Release.
  • What does ILSpy show for hoisted this? A <>4__this field — the state machine keeps the instance alive until completion, which matters for disposal ordering.
  • How do you read an async stack in a dump? dumpasync in SOS walks the boxes and prints the logical chain, including which task each frame is waiting on.

Common wrong answer

"Locals stay on the stack; the continuation captures the stack." Stacks do not survive a return; hoisting into the state machine is the mechanism, and it explains memory behaviour.

seniorMake something awaitable that was never designed for it: a WaitHandle, a legacy event, a timer.

Answer

Never Task.Run(() => handle.WaitOne()) — that burns a pool thread per waiter. For a WaitHandle use ThreadPool.RegisterWaitForSingleObject, which multiplexes many handles onto a small number of wait threads and calls you back; complete a TaskCompletionSource from the callback and unregister. For events, the TCS bridge (6.7). For "wait some time", Task.Delay or a PeriodicTimer, and for "wait until a condition", a TaskCompletionSource the condition-setter completes, or a SemaphoreSlim/Channel as a signal. The general shape is always the same: a lightweight callback registration that completes a promise, plus cancellation and cleanup — never a blocked thread.

Example

public static Task WaitOneAsync(this WaitHandle handle, CancellationToken ct = default)
{
    var tcs = new TaskCompletionSource(TaskCreationOptions.RunContinuationsAsynchronously);
    var rwh = ThreadPool.RegisterWaitForSingleObject(handle,
        static (s, timedOut) => ((TaskCompletionSource)s!).TrySetResult(), tcs, Timeout.Infinite, executeOnlyOnce: true);
    var reg = ct.Register(static s => ((TaskCompletionSource)s!).TrySetCanceled(), tcs);
    tcs.Task.ContinueWith(_ => { rwh.Unregister(null); reg.Dispose(); }, TaskScheduler.Default);
    return tcs.Task;
}

Follow-ups

  • What does RegisterWaitForSingleObject cost? One wait thread per 63 handles (Windows WaitForMultipleObjects limit), shared across the process — cheap.
  • Is SemaphoreSlim.WaitAsync implemented this way? No, it keeps its own queue of TCS-like waiters; but it is the same principle.
  • What about awaiting a CancellationToken? A TCS completed in Register — useful for "wait until shutdown".

Common wrong answer

"await Task.Run(() => handle.WaitOne())" — the interviewer asks how many threads that is for a thousand waiters.

principalWhat can and cannot cross an await today: Span<T>, ref locals, lock, unsafe — and what did C# 13 change?

Answer

Anything that lives on the stack or is thread-affine cannot survive a suspension: ref struct values (Span<T>, ReadOnlySpan<T>), ref locals, pointers, and Monitor locks. Before C# 13 the compiler simply banned ref locals and unsafe blocks anywhere in an async method or iterator; C# 13 relaxed that to "not across an await or yield": you can now declare a Span<T> or a ref local inside an async method as long as it is not live at a suspension point, and you can have unsafe blocks that do not contain awaits. That lets you write a synchronous Span-based parse step inside an async method without splitting it out. Still impossible by design: awaiting inside a lock (CS1996, also for the C# 13 Lock type), holding a Span across an await (use Memory<T> and slice to a span after each resume), and ref parameters on async methods (in/ref/out are all disallowed). At principal level the point is API design: async signatures take Memory<T>/ReadOnlyMemory<T>, synchronous hot loops take Span<T>, and the async method bridges the two.

Example

async ValueTask<int> ParseAsync(Stream s, Memory<byte> buffer, CancellationToken ct)
{
    int n = await s.ReadAsync(buffer, ct);
    ReadOnlySpan<byte> span = buffer.Span[..n];      // C# 13: fine, span is not live across an await
    return Utf8Parser.TryParse(span, out int value, out _) ? value : -1;
}

Follow-ups

  • Why can't the compiler just hoist a Span? A ref struct cannot be a field of a heap object; the state machine gets boxed on suspension.
  • What about stackalloc in async methods? Allowed in C# 13 with the same restriction; the memory must not be used after an await.
  • Does runtime-async change the rules? No; the language rules are unchanged, only the implementation of suspension.

Common wrong answer

"C# 13 lets you use Span<T> across awaits now." It allows spans between awaits, and the difference is the whole safety argument.

midWhich tools diagnose async problems in production, and what does each give you?

midYou open a dump from a starved process. What do you look for, and what does it look like?

Answer

In clrstack -all most pool threads share the same shape: a frame like Task.Wait, Task.Result, TaskAwaiter.GetResult, ManualResetEventSlim.Wait or Monitor.Wait near the top, below it the application method that blocked, below that the middleware/handler frames. Count them: dozens of identical blocked stacks, versus a handful doing real work, is the signature. syncblk shows which monitors are held and by whom if a lock is involved. dumpasync -stacks lists the async state machines that exist and what each awaits — thousands waiting on the same downstream call tells you which dependency stalled. threadpool (SOS) shows worker counts, queue length and whether threads are being injected. Correlate with counters from the same minute: rising thread count, growing queue, low CPU. High CPU with the same blocked shape means the pool is busy with CPU work, not blocked — a different fix.

Example

OS Thread Id: 0x1a2b
  System.Threading.Monitor.Wait(...)
  System.Threading.ManualResetEventSlim.Wait(...)
  System.Threading.Tasks.Task.SpinThenBlockingWait(...)
  System.Threading.Tasks.Task.InternalWaitCore(...)
  System.Threading.Tasks.Task`1.get_Result()
  Orders.Api.PricingClient.GetPrice(...)          ← the blocking call
  Orders.Api.OrdersController.Create(...)
  ... (x 47 threads with the same stack)

Follow-ups

  • Why is the number of blocked threads not the whole story? The queue is what is hurting users; blocked threads explain why it grows.
  • What if the stacks show SemaphoreSlim.Wait (sync) under a cache? A synchronous lock in an async path — same fix: WaitAsync, or remove the lock.
  • Can a GC pause look like this? GC pauses stop all threads briefly; they do not create dozens of identical Task.Wait frames.

Common wrong answer

"High memory, so it's the GC" — without opening the stacks. The interviewer wants the specific frames that prove blocking.

seniorRunbook: p99 latency spiked, timeouts, CPU at 15%. Walk through the first 15 minutes.

Answer

Minute 0–2: confirm the shape — latency up, CPU low, error rate up, one pod or all? If all, suspect a dependency; check its latency dashboards. Minute 2–5: read the runtime counters on one affected pod (queue length, thread count trending up by ~1/s = starvation; a sudden jump in a dependency's latency = the trigger). Minute 5–7: capture evidence before mitigating — dotnet-stack output and one dump — because mitigation destroys the evidence. Minute 7–10: mitigate in order of least risk: shed load at the edge (rate limiter, scale out), restart the worst pods (drains queues immediately), raise DOTNET_ThreadPool_MinThreads if you must survive until a fix; if a dependency is the trigger, open its circuit or fail fast with a shorter timeout. Minute 10–15: communicate status, assign someone to the dump, and decide whether to roll back the last deploy. Afterwards: identify the blocking call from the dump, fix it, add the counters to the standard dashboard with an alert on queue length, and add a load test that reproduces the dependency slowdown.

Example

# evidence first (10 seconds), then mitigate
kubectl exec orders-7f9c -- dotnet-stack report -p 1 > /tmp/stacks.txt
kubectl exec orders-7f9c -- dotnet-dump collect -p 1 -o /tmp/orders.dmp
kubectl scale deployment/orders --replicas=12
kubectl set env deployment/orders DOTNET_ThreadPool_MinThreads=64   # temporary; ticket to remove

Follow-ups

  • Why does scaling out help if the cause is blocking? More pods = more pool threads in aggregate and smaller queues per pod; it buys time, it does not fix anything.
  • Why shorten the timeout on the slow dependency? Blocked threads are freed sooner; failing fast converts a hang into a handled error.
  • What goes into the post-mortem action list? The specific code fix, the analyzer rule that would have caught it, the alert, and the load test.

Common wrong answer

"Restart the pods and see if it comes back." Mitigation without evidence guarantees the next incident is a repeat.

seniorHow do async stack traces, logging scopes and distributed tracing survive across awaits — and where do they leak?

Answer

Exception stack traces are stitched by ExceptionDispatchInfo at each await rethrow and cleaned by the runtime, so a logged exception shows the logical chain. Correlation state — Activity.Current (OpenTelemetry), ILogger.BeginScope scopes, IHttpContextAccessor — lives in AsyncLocals and flows with ExecutionContext to every continuation and to Task.Run work, which is what makes traces join up. The leaks are in the other direction: fire-and-forget work started from a request inherits the request's activity and scopes, then keeps logging under a finished request's trace id (misattributed telemetry), and a background loop that starts an Activity per iteration without stopping it produces ever-growing parent chains. Fix with ExecutionContext.SuppressFlow or explicitly starting a new root activity for background work, and always dispose activities. .NET 11's runtime-async improves the live stack view profilers see; exception traces were already fine.

Example

// Background work: new root, not the request's trace
_ = Task.Run(async () =>
{
    Activity.Current = null;                                     // detach from the request's activity
    using var act = Source.StartActivity("thumbnail.generate", ActivityKind.Internal, parentId: null,
                                         links: [new ActivityLink(requestContext)]);   // keep the relation as a link
    using var scope = _log.BeginScope(new Dictionary<string, object> { ["JobId"] = job.Id });
    await GenerateAsync(job);
});

Follow-ups

  • Why does a scope opened before an await still apply after? The scope stack is an AsyncLocal; it flows with the continuation.
  • Does SuppressFlow also drop the security context? Yes — everything in ExecutionContext; use it deliberately.
  • What does a missing using on an Activity cost? The activity never ends; exporters never see it, and children attach to it forever.

Common wrong answer

"Async loses the stack, so you can't debug it." The exception trace has shown the logical chain since .NET Core 2.1; the interviewer wants the flow mechanism and the leak.

seniorHow do you detect blocking calls before production?

Answer

Three layers. Static: analyzers that flag .Result/.Wait()/GetResult() (VSTHRD002), sync I/O calls with async alternatives (CA1849), and async void (VSTHRD100). For deeper investigation, dotnet-trace with the sample profiler and thread-pool events, and PerfView's Thread Time view, show exactly which frames sit in wait states.

// A load test assertion (k6/NBomber) alongside a counters scrape:
// assert max(threadpool_queue_length) < 10 and max(threadpool_thread_count) <= 2 * cores

Follow-ups

  • Why not run the blocking detector in production? It adds a context to every thread and captures stack traces; acceptable in staging, measurable overhead in prod.

  • Which EventPipe events matter? ThreadPoolWorkerThreadAdjustment/Stats (injection reasons), ThreadPoolWorkerThreadWait, and the sample profiler stacks.

"Only a load test reveals it" or "only code review reveals it" — the senior answer layers static, runtime and load detection.

principalDesign the observability for a fleet of async services so on-call can tell starvation, dependency slowness and CPU saturation apart in one glance.

Answer

Standardise one dashboard per service with four rows. Row 1, RED per endpoint: rate, error rate, latency histogram (p50/p99). Row 2, runtime: thread-pool queue length, thread count, completed items/s, CPU, GC pause time — from the .NET 9+ meters via OpenTelemetry (dotnet.thread_pool.queue.length, dotnet.thread_pool.thread.count) so no agent is needed. midHow do you wrap APM (BeginX/EndX) and EAP (XAsync + XCompleted) APIs as tasks?

Answer

APM: Task.Factory.FromAsync(BeginX, EndX, state) — it calls BeginX with a callback that calls EndX and completes the task, propagating exceptions from EndX; there are overloads for up to three arguments and one that takes an existing IAsyncResult. EAP: subscribe to the XCompleted event, complete a TaskCompletionSource from the handler using e.Error, e.Cancelled and e.Result, unsubscribe, then call XAsync; watch the userState token to match completions to requests when the object supports concurrent operations. In both cases the wrapper is a thin adapter that you keep until the underlying API gains a real TAP method — never Task.Run around the synchronous X, which is not the same thing.

Example

// APM → TAP
Task<int> ReadAsync(Stream s, byte[] buf) =>
    Task.Factory.FromAsync(s.BeginRead, s.EndRead, buf, 0, buf.Length, state: null);

// EAP → TAP
Task<string> DownloadAsync(WebClient wc, Uri uri)
{
    var tcs = new TaskCompletionSource<string>(TaskCreationOptions.RunContinuationsAsynchronously);
    void Handler(object? _, DownloadStringCompletedEventArgs e)
    {
        wc.DownloadStringCompleted -= Handler;
        if (e.Error is not null) tcs.TrySetException(e.Error);
        else if (e.Cancelled) tcs.TrySetCanceled();
        else tcs.TrySetResult(e.Result);
    }
    wc.DownloadStringCompleted += Handler;
    wc.DownloadStringAsync(uri);
    return tcs.Task;
}

Follow-ups

  • Does FromAsync flow cancellation? No — APM has no cancellation; add a token registration that cancels the underlying object if it supports it.
  • Which pattern is TAP? The current one: Task-returning methods named XAsync with an optional CancellationToken.
  • What about IAsyncResult implementations you must expose for old callers? TaskToApm-style helpers (the pattern in the BCL source): implement Begin by starting the task and wrapping it as an IAsyncResult.

Common wrong answer

"Task.Run(() => stream.Read(...))" as the wrapper — it blocks a pool thread; the APM overloads were the truly asynchronous ones.

midCompare ContinueWith chains with await: what do you have to get right by hand?

Answer

ContinueWith is the pre-C# 5 way to run code after a task. Four things await does for you that ContinueWith does not: it unwraps exceptions (a continuation receives the antecedent task and must inspect IsFaulted/Exception, or the exception is silently observed-and-lost); it unwraps nested tasks (an async continuation yields Task<Task> unless you call Unwrap()); it uses the right scheduler (ContinueWith defaults to TaskScheduler.Current, so pass TaskScheduler.Default explicitly — CA2008); and it keeps code linear. TaskContinuationOptions (OnlyOnFaulted, ExecuteSynchronously, NotOnCanceled) let you express things await cannot, which is the one place ContinueWith survives in modern code: cleanup hooks and fire-and-forget observers.

Example

// Legacy chain with the three classic bugs fixed
var t = LoadAsync()
    .ContinueWith(a => ParseAsync(a.Result), TaskContinuationOptions.OnlyOnRanToCompletion, TaskScheduler.Default)   // .Result would wrap exceptions; guarded by OnlyOnRanToCompletion
    .Unwrap();                                                                                                        // Task<Task<Doc>> → Task<Doc>

// Same thing with await
var doc = await ParseAsync(await LoadAsync());

Follow-ups

  • What happens to the chain if the antecedent faults and the continuation has OnlyOnRanToCompletion? The continuation is cancelled — surprising unless you know it.
  • Does ContinueWith flow ExecutionContext? Yes, like Task.Run.
  • Why is ExecuteSynchronously dangerous? Same inline-continuation problem as TCS: your code runs on the completer's thread.

Common wrong answer

"ContinueWith is the same as await, just uglier." The scheduler default and the Task<Task> trap are real production bugs.

midYou inherit code full of Task.Factory.StartNew(...). What do you check before replacing it with Task.Run?

Answer

Three things. Scheduler: if the code passes an explicit scheduler (UI scheduler via FromCurrentSynchronizationContext, a custom limited-concurrency scheduler), keep StartNew — Task.Run always uses the default pool scheduler; if it passes none, it was implicitly using TaskScheduler.Current, which may have been a bug or an accidental dependency. Options: LongRunning has no Task.Run equivalent; AttachedToParent creates parent/child relationships that Task.Run (with DenyChildAttach) forbids — check whether anything relies on the parent waiting for children. Delegates: an async lambda under StartNew returned Task<Task>; if the code awaited the outer task it was silently not waiting for the work, and switching to Task.Run (which unwraps) changes timing — probably fixing a latent bug, possibly exposing one that the premature completion was masking.

Example

// Before: completes when the lambda returns its Task, i.e. immediately
await Task.Factory.StartNew(async () => await SyncCatalogAsync());
// After: actually waits for the sync
await Task.Run(() => SyncCatalogAsync());
// Keep StartNew only for this:
Task.Factory.StartNew(Pump, TaskCreationOptions.LongRunning, TaskScheduler.Default);

Follow-ups

  • What is AttachedToParent used for? Structured parallelism in TPL-era code: a parent task completes when all attached children do; rarely intended with async.
  • Why does Task.Run pass DenyChildAttach? To prevent third-party code from attaching to your task and delaying its completion.
  • Is StartNew deprecated? No, just lower-level; it is fine with explicit scheduler and options.

Common wrong answer

"Find-and-replace StartNew with Task.Run." Changes scheduler and unwrap behaviour silently; the interviewer wants the checklist.

seniorHow did async work in legacy ASP.NET (System.Web), what were the failure modes, and what changes in ASP.NET Core?

Answer

Classic ASP.NET on .NET 4.5+ installs AspNetSynchronizationContext per request: continuations run one at a time (not on a specific thread) with HttpContext.Current restored, provided <httpRuntime targetFramework="4.5"/> (or aspnet:UseTaskFriendlySynchronizationContext=true) is set — without it you get the .NET 4.0 legacy context and hard-to-explain hangs. Failure modes: .Result deadlocks against that context; async void throws InvalidOperationException: An asynchronous module or handler completed while an asynchronous operation was still pending; background work after the request ends is killed on app-domain recycle unless registered with HostingEnvironment.QueueBackgroundWorkItem; Web Forms needs Async="true" and RegisterAsyncTask. ASP.NET Core removes the context entirely (no deadlock, but blocking now starves), replaces HttpContext.Current with DI/IHttpContextAccessor, replaces QueueBackgroundWorkItem with IHostedService, and forbids sync I/O on request bodies by default.

Example

<!-- web.config: without this, .NET 4.5 async controllers run under the legacy context -->
<system.web>
  <httpRuntime targetFramework="4.8" />
</system.web>

Follow-ups

  • Why "one at a time" rather than "same thread"? Requests are not thread-affine; the context guarantees no two continuations of one request overlap, preserving HttpContext semantics.
  • Did legacy ASP.NET have a thread-pool starvation problem? Yes, plus IIS's own request queue limits (maxConcurrentRequestsPerCPU) that masked or magnified it.
  • Is ConfigureAwait(false) still relevant in classic ASP.NET libraries? Very — it is the difference between a deadlock and a working call in a .Result-laden codebase.

Common wrong answer

"ASP.NET Core still has a request context, that's why HttpContext is available." It is an AsyncLocal behind the accessor, not a SynchronizationContext; the two are different mechanisms with different consequences.

seniorReplace BackgroundWorker, System.Timers.Timer and System.Threading.Timer-based code with modern equivalents. What are the semantic differences?

Answer

BackgroundWorker (WinForms-era) marshals progress and completion events to the UI thread; its replacement is await Task.Run(...) with IProgress<T>/Progress<T> (which captures the context at construction) and a CancellationToken instead of CancelAsync/CancellationPending. System.Threading.Timer fires callbacks on pool threads and will overlap them if the previous one is still running, and an exception in the callback crashes the process; System.Timers.Timer silently swallows exceptions and has the same overlap problem unless AutoReset is managed by hand. The modern replacement is PeriodicTimer (.NET 6) in a BackgroundService loop: a single consumer awaits WaitForNextTickAsync, so ticks never overlap, exceptions are yours to handle in the loop, cancellation is a token, and it accepts a TimeProvider (.NET 8) for tests. Where a timer callback used to do I/O with async void, the loop makes it an ordinary await.

Example

// Before: overlapping callbacks, async void, swallowed exceptions
var timer = new System.Timers.Timer(30_000);
timer.Elapsed += async (_, _) => await SyncAsync();     // async void handler
timer.Start();

// After
using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30), _timeProvider);
while (await timer.WaitForNextTickAsync(stoppingToken))
{
    try { await SyncAsync(stoppingToken); }
    catch (Exception ex) when (ex is not OperationCanceledException) { _log.LogError(ex, "sync failed"); }
}

Follow-ups

  • What if a tick takes longer than the period? PeriodicTimer coalesces: the next WaitForNextTickAsync returns immediately once, never overlaps, never queues multiple.
  • Where is System.Threading.Timer still right? Very high-frequency or many timers with cheap synchronous callbacks; or when you need a one-shot from non-async code.
  • What did Progress<T> get wrong for people? It posts to the captured context asynchronously, so reports can arrive after the task completes.

Common wrong answer

"System.Timers.Timer with an async event handler is fine" — it is async void with overlap and swallowed exceptions; three problems in one line.

principalStrategy: a 500k-line synchronous .NET Framework service must become an async ASP.NET Core service. Sequence it.

Answer

Do not do both migrations in one step. Phase 0, measurement: find the I/O leaves (database, HTTP, file, queue) and the entry points; count the synchronous paths between them; baseline latency and throughput. Phase 1, still on Framework: make leaves truly async where APIs exist (ADO.NET, HttpClient), introduce TAP interfaces alongside the sync ones, and propagate async upward along the hottest paths first, with named SyncBoundary adapters where a path cannot be completed yet; enable <httpRuntime targetFramework> and analyzers so new code is async-only. Phase 2, port to ASP.NET Core with the boundaries still in place — the port is easier when most paths are already async, and the missing context removes the deadlock class; keep sync-over-async isolated because on Core it becomes starvation rather than deadlock, and size min threads for the transition. Phase 3, retire adapters path by path, driven by production starvation data, then remove the escape hatches and turn the analyzers to errors. Throughout: strangler-fig the entry points (new endpoints on Core, old ones proxied), integration tests with a single-threaded context to catch deadlocks, and load tests that fail on thread growth. The order matters: leaves before trunks, Framework-async before Core, containment before removal.

Example

Phase 0  inventory + baseline         (2–3 weeks)   output: path map, hot paths, metrics
Phase 1  leaves async + hot paths     (per path)    gate: analyzer baseline ratchets down
Phase 2  port to ASP.NET Core         (one cut)     gate: load test with adapters in place
Phase 3  remove adapters              (per path)    gate: zero VSTHRD002 outside SyncBoundary.cs

Follow-ups

  • Why not leaves-only or trunks-only? Trunks-only creates async-over-sync (fake scalability); leaves-only leaves deadlocks in the middle with no one able to await them.
  • Where does IAsyncEnumerable come in? Late — once paths are async, replace list-returning batch APIs on large data with streams.
  • How do you keep two entry-point stacks consistent during strangler-fig? Shared contracts package, contract tests against both, traffic mirroring before cut-over.

Common wrong answer

"Port to Core first, then make it async" or "wrap everything in Task.Run so it's async immediately". Both create a service that starves on day one of the new platform.

13. Timers, TimeProvider and testing async code

asked: rarelynice to know5 questions

Rarely a whole interview, but a reliable follow-up when you mention retries, periodic jobs or flaky tests: Task.Delay vs Thread.Sleep, PeriodicTimer, the .NET 8 TimeProvider abstraction and FakeTimeProvider, and how to test cancellation and ordering deterministically.

Docs: TimeProvider overview · PeriodicTimer · FakeTimeProvider

midTask.Delay vs Thread.Sleep: what does each cost, and what are the edge cases?

Answer

Thread.Sleep blocks the current thread for the duration — on a pool thread that is exactly the starvation pattern; it is only acceptable on a dedicated thread or in a console tool. Task.Delay creates a timer in the runtime's timer queue and returns a task that completes when it fires: no thread is held, the cost is one timer node plus the task, and it accepts a CancellationToken that disposes the timer immediately. Edge cases: Task.Delay(0) returns a completed task (no yield); Task.Delay(Timeout.Infinite, ct) is the idiom for "wait until cancelled"; timer resolution is coarse (historically ~15 ms on Windows, better on modern runtimes and Linux) so Delay(1) is not 1 ms; and every un-cancelled delay keeps its timer alive, which is how WhenAny(work, Delay(timeout)) leaks.

Example

// Wait for shutdown without polling
try { await Task.Delay(Timeout.Infinite, stoppingToken); }
catch (OperationCanceledException) { }

// Retry backoff: jittered, cancellable, testable via TimeProvider (.NET 8)
await Task.Delay(TimeSpan.FromMilliseconds(200 * Math.Pow(2, attempt) + Random.Shared.Next(50)), _timeProvider, ct);

Follow-ups

  • Is Task.Delay accurate for scheduling? No; it fires no earlier than requested and possibly later; use it for waits, not clocks.
  • What about SpinWait? For microsecond waits in lock-free code only; never for I/O timing.
  • How many timers can the queue hold? Millions; the cost is memory and the timer thread's scan of due timers, which the .NET 6+ implementation partitions to keep cheap.

Common wrong answer

"Thread.Sleep(100) in an async method is fine, it's short." Under load, 100 ms × requests per second = pool threads permanently blocked.

midWhat does PeriodicTimer fix compared with the older timers?

Answer

PeriodicTimer (.NET 6) inverts the model: instead of the timer calling you (on a pool thread, possibly overlapping, with exceptions escaping to the process), you await WaitForNextTickAsync(ct) in a loop. Consequences: ticks never overlap because there is one consumer; a slow iteration simply delays the next tick (one missed tick is coalesced, never queued); exceptions surface in your loop where you can log and continue; cancellation is a token, not a Dispose race; and since .NET 8 the Period is settable at runtime and the constructor takes a TimeProvider, so the loop is unit-testable with FakeTimeProvider. It is single-consumer by design — one WaitForNextTickAsync at a time.

Example

using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1), _timeProvider);
while (await timer.WaitForNextTickAsync(stoppingToken))
{
    var due = await _store.GetDueAsync(_timeProvider.GetUtcNow(), stoppingToken);
    foreach (var job in due) await RunAsync(job, stoppingToken);
    timer.Period = due.Count > 100 ? TimeSpan.FromSeconds(10) : TimeSpan.FromMinutes(1);   // .NET 8: adaptive
}

Follow-ups

  • What does WaitForNextTickAsync return after Dispose? false — the loop exits cleanly.
  • Is the first tick immediate? No, after one period; run the body once before the loop if you need an immediate first run.
  • Drift? Ticks are scheduled relative to the previous tick's due time, so a slow body does not accumulate drift the way Delay-in-a-loop does.

Common wrong answer

"await Task.Delay(period) in a loop is the same thing." It drifts by the body's duration each iteration and is not testable without a TimeProvider overload.

midWhat is TimeProvider (.NET 8), which async APIs accept it, and how does FakeTimeProvider work?

Answer

TimeProvider is the BCL's time abstraction: GetUtcNow(), GetLocalNow(), GetTimestamp()/GetElapsedTime(), LocalTimeZone, and CreateTimer(...). TimeProvider.System is the real clock; inject the abstract type. The async surface takes it as an overload: Task.Delay(TimeSpan, TimeProvider, CancellationToken), Task.WaitAsync(TimeSpan, TimeProvider), new CancellationTokenSource(TimeSpan, TimeProvider) / CancelAfter via the provider, new PeriodicTimer(TimeSpan, TimeProvider). FakeTimeProvider (package Microsoft.Extensions.TimeProvider.Testing) starts at a fixed time and only moves when you call Advance(TimeSpan) or SetUtcNow, firing any timers that became due synchronously inside that call — so a test of a retry-with-backoff or a timeout runs in microseconds and is deterministic. It replaces the old hand-rolled ISystemClock wrappers (ASP.NET Core's own ISystemClock is obsolete since .NET 8).

Example

[Fact]
public async Task Times_out_after_two_seconds()
{
    var time = new FakeTimeProvider();
    var sut = new QuoteClient(_fakeHttp, time);

    var pending = sut.GetQuoteAsync("MSFT", CancellationToken.None);   // internally: linked CTS with CancelAfter(2s, time)
    time.Advance(TimeSpan.FromSeconds(2));                            // fires the timer synchronously

    await Assert.ThrowsAsync<TimeoutException>(() => pending);
}

Follow-ups

  • Why might a test still hang after Advance? The code under test had not yet registered its timer when you advanced (it was still on its synchronous prefix or an earlier await); yield or await a "started" signal first.
  • Does FakeTimeProvider run continuations synchronously? Timer callbacks yes; continuations of tasks they complete run per normal task rules (inline or pool) — hence the occasional need for await Task.Yield().
  • What about DateTime.UtcNow in old code? Wrap it behind the provider progressively; a static ambient TimeProvider is a legitimate transitional step.

Common wrong answer

"Mock DateTime.Now with a custom IClock interface" — the 2026 answer is the BCL abstraction, precisely because the BCL's own timers and delays accept it.

seniorHow do you write deterministic tests for async code: ordering, cancellation, timeouts, deadlocks?

Answer

Tests are async Task, never async void (the runner cannot await it). Control time with FakeTimeProvider, not Task.Delay. Control ordering with TaskCompletionSources handed to fakes: the test decides exactly when a dependency "completes", so races become scripted sequences ("start A, start B, complete B, assert, complete A"). Test cancellation by passing a token, cancelling at the chosen point, and asserting OperationCanceledException plus the state you expect (nothing committed past the point of no return). Test deadlocks with a single-threaded SynchronizationContext (xUnit's AsyncTestSyncContext or Nito's AsyncContext.Run) and a test timeout — a blocked chain hangs and fails instead of passing on the pool. Use xUnit v3's TestContext.Current.CancellationToken so aborted runs stop your loops. Assert on observable outcomes, not on Task.Status transitions, which are timing-dependent.

Example

[Fact]
public async Task First_result_wins_and_loser_is_cancelled()
{
    var a = new TaskCompletionSource<Quote>(TaskCreationOptions.RunContinuationsAsynchronously);
    var b = new TaskCompletionSource<Quote>(TaskCreationOptions.RunContinuationsAsynchronously);
    var loserCancelled = new TaskCompletionSource();
    var sut = new HedgedClient(
        primary:   ct => a.Task,
        secondary: ct => { ct.Register(loserCancelled.SetResult); return b.Task; });

    var pending = sut.GetAsync(TestContext.Current.CancellationToken);
    a.SetResult(new Quote(10));                          // scripted: primary wins
    Assert.Equal(10, (await pending).Price);
    await loserCancelled.Task.WaitAsync(TimeSpan.FromSeconds(1));   // and the loser saw cancellation
}

Follow-ups

  • Why RunContinuationsAsynchronously in test TCSs? So SetResult in the test does not run the SUT's continuation inline on the test thread and reorder your assertions.
  • How do you test "no unobserved exceptions"? Subscribe to TaskScheduler.UnobservedTaskException in a fixture, force GC.Collect(); GC.WaitForPendingFinalizers(), assert none fired.
  • What about testing IAsyncEnumerable producers? Enumerate with a scripted source and assert on the sequence and on disposal (a fake that records DisposeAsync).

Common wrong answer

"await Task.Delay(100) then assert." It passes on the laptop and fails in CI once a month; the interviewer wants scripted completion.

principalYour team's async tests are flaky. Set a policy.

Answer

Flaky async tests almost always come from three sources — real time (Delay, wall-clock timeouts), shared mutable state under test parallelism (static caches, AsyncLocal leaking across tests, a shared HttpClient handler fake), and unscripted completion order. The policy: no Task.Delay or Thread.Sleep in tests (analyzer or a custom rule), time through FakeTimeProvider; every dependency fake exposes completion as a TaskCompletionSource the test controls; test timeouts are a global harness setting (so a hang fails fast) but never an assertion; parallelism stays on, with [Collection] only for tests that touch true shared resources, and per-test DI containers; a test that fails intermittently is quarantined within a day and either fixed or deleted — retries in CI are banned because they hide real races that will ship. Measure: flaky rate per week, time-to-quarantine, and the count of tests using real time trending to zero.

Example

<!-- xunit.runner.json / test project: fail hangs fast, keep parallelism -->
{ "parallelizeTestCollections": true, "maxParallelThreads": -1, "longRunningTestSeconds": 10 }
<!-- Directory.Build.props for test projects -->
<PropertyGroup><TestTimeout>30000</TestTimeout></PropertyGroup>

Follow-ups

  • Why ban retries when other teams use them? A retry converts a race from "fails 1% of the time in CI" into "fails 1% of the time in production"; the flake is the signal.
  • How do you find AsyncLocal leaks between tests? Assert ambient state is null at test start in a base fixture; failures point at the previous test.
  • What about integration tests that need real time (a real database timeout)? Separate suite, run serially, explicitly allowed to be slower; still no Sleep for synchronisation.

Common wrong answer

"Add automatic retries in the pipeline and move on." It is the choice that makes the interviewer stop asking follow-ups.

midWhat is Runtime Async in .NET 11, how do you turn it on, and what does it change for developers?

Answer

Runtime Async moves async/await from a compiler-only feature to a runtime-native one. Instead of emitting a state-machine type per method, the C# compiler marks the method [MethodImpl(MethodImplOptions.Async)] and emits plain IL with calls to AsyncHelpers.Await(...) at suspension points; the runtime (JIT, NativeAOT and ReadyToRun) itself saves live state into a continuation object on suspension and resumes the method later. It is a preview feature in .NET 11: opt in with <Features>runtime-async=on</Features> in the project file (since Preview 7 a net11.0 project no longer needs EnablePreviewFeatures), opt out per project with <UseRuntimeAsync>false</UseRuntimeAsync>; the old DOTNET_RuntimeAsync environment switch has been removed. The runtime libraries themselves are compiled with it, so an app can run entirely on the new model. What changes: live stack traces show the real call chain (a three-deep chain drops from 13 frames to 5), the debugger steps across awaits without builder frames, allocations drop (continuations reused, unchanged locals not saved, await Task.Yield() allocation-free), and hot async methods now go through tiered compilation. What does not change: language semantics, ConfigureAwait, ExecutionContext flow, cancellation, the ValueTask rules, or exception stack traces (already clean).

Example

<PropertyGroup>
  <TargetFramework>net11.0</TargetFramework>
  <Features>$(Features);runtime-async=on</Features>   <!-- preview: measure before shipping -->
</PropertyGroup>
// live StackTrace inside InnerAsync(), three awaits deep
without runtime-async: 13 frames incl. AsyncMethodBuilderCore.Start[...] ×4
with    runtime-async:  5 frames — InnerAsync ← MiddleAsync ← OuterAsync ← Main

Follow-ups

  • Which methods stay on the compiler model? Methods with custom builders (pooling, UniTask-style) and iterators; the runtime handles Task/ValueTask-returning async methods.
  • What about profilers? The async profiler now instruments both models with one event model; older tools may show unfamiliar frames until updated.
  • Where did it start? Experimental in .NET 10 behind an environment variable; Preview 1 of .NET 11 (February 2026) made it the default implementation path on CoreCLR.

Common wrong answer

"Runtime Async changes how await behaves, so you no longer need ConfigureAwait / ValueTask rules." Nothing observable changes except diagnostics and cost; claiming semantic changes is a red flag.

seniorWhat did .NET 11 change about ExecutionContext capture, and what does it imply about AsyncLocal cost?

Answer

Every Task/ValueTask continuation used to capture the current ExecutionContext at suspension and restore it before running, even when the context was the default one and the restore was a no-op. .NET 11 detects that case — no AsyncLocal values set, nothing to restore — and skips the capture/restore cycle for Task, Task<T>, ValueTask, ValueTask<T> and the runtime-async path. The implication is a sharper cost model: code paths that never touch AsyncLocal get cheaper awaits for free, while code that sets AsyncLocal values (logging scopes, Activity, tenant context, IHttpContextAccessor) pays the full capture on every await in that flow, as before. So the senior guidance is unchanged but now measurable: set ambient state once at the boundary, avoid per-call AsyncLocal writes in hot loops, and use ExecutionContext.SuppressFlow for background work that does not need it. It also means benchmarks of "await overhead" now depend on whether the harness itself set any AsyncLocal.

Example

// Cheap on .NET 11: no AsyncLocal in this flow → no EC capture/restore per await
static async Task<int> SumAsync(Stream s) { int n = 0; var buf = new byte[4096]; int r; while ((r = await s.ReadAsync(buf)) > 0) n += r; return n; }

// Pays capture on every await in the flow: the logging scope is an AsyncLocal write
using (_log.BeginScope("job {Id}", id)) { await SumAsync(s); }

Follow-ups

  • Does the optimisation change semantics? No; restoring an empty context is exactly what skipping it produces.
  • How much is the saving? Small per await (a few nanoseconds and a field write or two), significant in tight async loops with millions of awaits per second.
  • Does ConfigureAwait(false) interact? Only in that such code paths tend to be library hot paths where the saving compounds; the docs call out apps that "use ConfigureAwait(false) and AsyncLocal<T> sparingly".

Common wrong answer

"AsyncLocal is free; it's just a field." It allocates a new context map on every set and forces capture/restore on every await downstream.

seniorWhat does Runtime Async mean for custom awaiters, custom builders and ValueTask?

Answer

Custom awaitables keep working: the compiler emits AsyncHelpers.AwaitAwaiter<TAwaiter> (for INotifyCompletion) or UnsafeAwaitAwaiter<TAwaiter> (for ICriticalNotifyCompletion) around any non-Task awaiter, so Task.Yield(), ConfiguredTaskAwaitable, ValueTask awaiters and your own GetAwaiter() extensions all suspend through the runtime path. Methods whose return type or attribute names a custom AsyncMethodBuilder — pooling builders, UniTask, task-like types in frameworks — are not runtime-async: they keep the compiler-generated state machine, because the runtime only knows how to produce Task and ValueTask. That is a design signal: libraries that invented their own task types for performance are now competing with a runtime that reuses continuations, folds Task.FromResult/ValueTask.FromResult as JIT intrinsics and skips empty context restores. For ValueTask specifically, the synchronous-completion advantage remains, the asynchronous path gets the same continuation reuse as Task, and the consumption rules are unchanged.

Example

// What the compiler emits under runtime-async (decompiled shape)
[MethodImpl(MethodImplOptions.Async)]
static Task<string> FetchAsync(HttpClient c, string url)
{
    var resp = AsyncHelpers.Await(c.GetAsync(url));               // Task<T> overload
    resp.EnsureSuccessStatusCode();
    return AsyncHelpers.Await(resp.Content.ReadAsStringAsync());  // no state machine type anywhere
}

Follow-ups

  • Can you mix both models in one process? Yes; a runtime-async method can await a compiler-async method and vice versa — they are all just tasks.
  • Does IAsyncEnumerable use runtime-async? Async iterators keep their compiler-generated machinery in .NET 11.
  • Is MethodImplOptions.Async something you write by hand? No; the compiler emits it under the feature flag. Hand-writing it without the compiler support is unsupported.

Common wrong answer

"All async code, including custom task types, becomes runtime-managed automatically." Only Task/ValueTask-returning methods without custom builders do.

principalShould your organisation enable Runtime Async in production this year? Make the call.

Answer

Not by default, and not on every service. It is a preview feature in .NET 11 (GA 2026-11-10 for the runtime; the feature stays opt-in), which means the runtime team wants throughput and library-size reports, not that it has an SLA. The decision framework: first, get everyone to .NET 10 LTS before .NET 8/9 end of support on 2026-11-10 — that is the non-negotiable migration this year. Second, pick one or two async-heavy, well-instrumented services with a proper canary pipeline and a load test, flip runtime-async=on there, and compare p99 latency, allocation rate, Gen0 GC count, binary size and — importantly — whether your profiler, APM agent and crash-dump tooling still produce usable output (the async profiler was updated; third-party agents may lag). Third, watch the areas the release notes call out: methods with pooling builders (unchanged), covariant Task/Task<T> overrides (fixed in P7), R2R inlining (new). If the canary shows a measurable win and tooling is clean, roll to similar services with UseRuntimeAsync as the per-project kill switch; otherwise wait for .NET 12. Communicate it as an experiment with an owner and an exit date, not as a platform standard.

Example

Canary checklist (per service)
  [ ] net11.0 + runtime-async=on in one deployment slot, same traffic split as any canary
  [ ] compare: p50/p99, alloc/s, Gen0/s, threadpool queue, image size
  [ ] verify: profiler frames, dump `dumpasync`, APM traces, crash-dump symbolication
  [ ] kill switch: <UseRuntimeAsync>false</UseRuntimeAsync> + redeploy, rehearsed
  [ ] exit criteria + owner + review date written down

Follow-ups

  • What would make you say "no" outright? Dependence on a profiler/APM vendor that has not shipped support, or NativeAOT-published services where you cannot easily A/B.
  • What is the upside worth chasing? Cleaner live diagnostics for on-call more than raw throughput; the allocation win is real but modest in typical I/O-bound services.
  • How does this affect library authors? Test under both models; do not rely on state-machine type names in reflection or serialisation.

Common wrong answer

"Turn it on everywhere, it's faster." A principal answer names the preview status, the tooling risk, the canary and the kill switch — and puts the .NET 10 migration first.

15. Judgment calls

asked: often (lead+)critical10 questions

Open-ended questions with no single right answer. Interviewers at lead and principal level use them to see whether you reason from trade-offs, name the ones the interviewer did not mention, and commit to a position. Each hidden part says what a strong answer demonstrates at the highest level and which trade-offs it names unprompted.

principalShould ValueTask or Task be your team's default return type?

Strong answer

Task as the default, ValueTask by exception with a measurement attached — and the answer says why in terms of who bears the cost: ValueTask shifts complexity to every consumer (await-once, no WhenAll, no caching), while Task's allocation is paid once by the producer and is often already avoided by cached results and the box-is-the-task design. Names unprompted: interface contracts that force ValueTask; the difference between sync-path savings and pooled-source savings; CA2012 as the guard rail; the binary-breaking nature of changing the type later; and that .NET 11's runtime-async narrows the gap enough that "we chose ValueTask in 2019" deserves re-measurement rather than inheritance.

principalWhat is your ConfigureAwait policy across a monorepo with libraries, ASP.NET Core services and a WPF client?

Strong answer

Per project type, enforced by analyzer configuration rather than convention: libraries ConfigureAwait(false) everywhere (CA2007 error), services nothing (CA2007 off, because there is no context and the noise hides real review comments), WPF default in view-layer code and false in its service layer. Names unprompted: that ConfigureAwait(false) is not "run in background" and does nothing on synchronous completion; that a single third-party await without it can reintroduce a deadlock, so the client must not block anyway; Blazor's contexts; await using/await foreach forms; and where the policy exceptions live (callback-invoking library code).

principalDuring a migration, when is sync-over-async acceptable, and how do you stop "temporary" from becoming permanent?

Strong answer

Acceptable only at named boundaries where the caller's signature cannot change yet, implemented as Task.Run(...).GetAwaiter().GetResult() to avoid context deadlocks, isolated in files the analyzer suppression is scoped to, and counted. The commitment mechanism: a ratcheting baseline in CI (the count may only go down), a burn-down owned by someone, and starvation metrics from production deciding the order. Names unprompted: that on ASP.NET Core the risk is starvation not deadlock; the thread cost and min-thread sizing during the transition; that async-over-sync is the mirror mistake; and that the boundary list is the migration plan itself.

principalBounded or unbounded queues for in-process background work?

Strong answer

Bounded, always, with the bound derived from how much you are willing to lose or delay — and a decision about what happens at the bound (block the producer, drop, reject with 503/429). Unbounded is a decision to convert back-pressure into memory growth and an eventual OOM kill that loses everything. Names unprompted: the BoundedChannelFullMode options and which fit telemetry versus orders; that an in-memory queue is not durable so the bound is also a statement about acceptable loss; queue depth as the primary alert; and the point at which a broker replaces the channel.

principalHow should cancellation interact with writes — do you honour RequestAborted everywhere?

Strong answer

No: honour it for reads and for work before the point of no return, then deliberately switch to a non-cancellable token for the commit, and make the commit idempotent so a client retry after a timeout is safe. Names unprompted: partial writes across statements or services; EF Core's rollback-on-dispose before commit; that tokens do not cross process boundaries so deadlines and idempotency keys are the distributed equivalent; the three-token model (request, drain, hard stop); and testing the "cancel after commit" path explicitly.

seniorIs Task.Run ever justified inside an ASP.NET Core request?

Strong answer

Almost never for throughput, occasionally for isolation: a long CPU computation that must be bounded (with a semaphore or dedicated scheduler) or a blocking third-party call you cannot replace. A strong answer refuses the "faster response" framing, explains the second-thread cost and hill-climbing interaction, and proposes the alternatives — 202 plus a queue, a separate worker, a limiter. Names unprompted: captured scoped services, the difference for UI apps, and that Parallel.For inside a request is the same mistake with more threads.

principalFire-and-forget: in-process queue, outbox table, or message broker?

Strong answer

Decide by what happens on crash and on scale-out. In-process channel when loss is acceptable and work is per-instance (cache warming, best-effort notifications); outbox when the work must be as durable as the transaction that created it and you want exactly-once semantics without a broker; broker when multiple services or instances must share, retry with visibility timeouts, or absorb bursts. Names unprompted: the ObjectDisposedException class of bugs from capturing request state; shutdown draining; idempotency and poison-message handling; and that all three still need the same in-process discipline (scopes per item, bounded workers, observed exceptions).

seniorSetting ThreadPool.SetMinThreads in production: band-aid, sin, or legitimate configuration?

Strong answer

A legitimate incident mitigation and a sin as a permanent fix — with one nuance: services that must absorb sudden bursts of genuinely blocking work they cannot change (a native SDK) may justify a modest, documented, measured minimum. The strong answer explains the injection ramp, what the .NET 6 blocking mitigation already covers, the memory and scheduling cost of large minimums, and that the number should be reverted once the blocking is gone, with a ticket and a load test proving it.

seniorStreaming responses (IAsyncEnumerable, SSE) or paging for a large read API?

Strong answer

Paging (keyset) for general clients, caches and retries; streaming for exports, live feeds and internal consumers that can handle mid-stream failure. Names unprompted: that a JSON array stream cannot change status after the first byte; NDJSON/SSE framing; resumability via keys; proxies and buffering; memory bounds on the server; cancellation on disconnect; and when a background job plus a file beats both.

principalAdopting preview runtime features (Runtime Async today) — what is your policy?

Strong answer

Experiments, not standards: one owner, one canary service, explicit metrics and exit criteria, a rehearsed kill switch, and a written review date. Names unprompted: preview means no SLA and possible tooling gaps; LTS alignment (get to .NET 10 first, .NET 8/9 EOL 2026-11-10); the difference between "no code changes required" and "no behaviour differences"; and that the diagnostics improvement may be worth more than the throughput.

16. Design exercises

asked: sometimes (lead+)critical3 exercises

Where async connects to system design. Each exercise gives the prompt and the clarifying questions you should ask before designing; the strong solution and the trade-offs you are expected to name unprompted are collapsed so you can attempt it first.

Exercise 1 — Background job subsystem inside an ASP.NET Core service

Prompt. Requests need to trigger work that takes 1–30 seconds (thumbnail generation, PDF rendering, webhook fan-out). Design the subsystem: how work is accepted, executed, bounded, observed, and what happens on deploys and crashes. Assume 6 pods, 200 job requests per second at peak.

Clarifying questions to ask

  • Is losing a job on crash acceptable, or must every accepted job eventually run? (durability)
  • Does the caller need the result, a status, or nothing? (202 + status endpoint vs fire-and-forget)
  • Are jobs idempotent, or do we need exactly-once? (retries, dedup keys)
  • Is the work CPU-bound (rendering) or I/O-bound (webhooks)? (thread isolation vs async concurrency)
  • What is the latency expectation for job completion, and is there a priority scheme?
Strong solution outline and trade-offs

Outline

  • Accept: the request writes a job row to the database in the same transaction as its own state change (outbox), returns 202 with a status URL. No in-memory-only acceptance if durability is required.
  • Dispatch: a BackgroundService per pod polls/claims jobs with SELECT ... FOR UPDATE SKIP LOCKED (or a lease column) in batches, pushing them into a bounded Channel<Job>; the channel is a wake-up buffer, not the source of truth.
  • Execute: two lanes. I/O-bound jobs (webhooks) run under Parallel.ForEachAsync-style bounded async concurrency (say 64 per pod) with per-call timeouts and a resilience pipeline; CPU-bound jobs (rendering) run on a dedicated small set of threads (ProcessorCount − 2) so they cannot starve Kestrel's pool. Each job gets its own DI scope (CreateAsyncScope) and a linked CTS with a deadline.
  • Failure: per-job try/catch; transient failures retried with exponential backoff and a max attempt count stored on the row; permanent failures moved to a dead-letter state with the exception; job exceptions never escape ExecuteAsync.
  • Shutdown: on ApplicationStopping stop claiming, let in-flight jobs finish within ShutdownTimeout (set below the orchestrator grace period), release leases for anything unfinished so another pod picks it up; readiness probe fails first so no new requests arrive.
  • Observability: counters for claimed/completed/failed/dead-lettered, a processing-time histogram per job type, queue depth (rows in "pending") as the scaling and alerting signal, job id and trace link on every log line; new root Activity per job linked to the originating request.

Trade-offs to name unprompted

  • Database-as-queue is simple and transactional but polling adds latency and load; a broker (Service Bus, SQS, RabbitMQ) scales further and adds an operational dependency and the outbox pattern anyway.
  • Bounded channel with Wait vs claiming fewer rows: both are back-pressure; the bound must be small enough that a pod's crash loses little (leases expire and work is reclaimed).
  • Exactly-once is not achievable end to end; at-least-once with idempotent handlers is the honest contract.
  • Running CPU jobs in the API pods vs a separate worker deployment: separate scaling and crash isolation vs simpler ops; at 200 jobs/s with rendering, separate.
  • Priority: prioritized channels (.NET 9) in-process, or separate queues per priority — the latter is easier to reason about under load.

Exercise 2 — Low-latency aggregation over many downstream services

Prompt. A product page calls 12 backend services (pricing, inventory, reviews, recommendations, ...) and must render within 300 ms at p99 with 2,000 requests per second. Some services are slow or flaky. Design the aggregation layer.

Clarifying questions to ask

  • Which of the 12 are required for a valid page and which can degrade (placeholder, cached, omitted)?
  • Per-dependency latency distributions and error rates? Are any of them retry-safe (idempotent GETs)?
  • Is there an existing cache layer, and what staleness is acceptable per field?
  • Do the calls have dependencies on each other (need the SKU list before pricing)?
  • Connection limits and rate limits on each downstream?
Strong solution outline and trade-offs

Outline

  • Budget: one linked CTS per request with CancelAfter(250 ms) (leave headroom for rendering); every downstream call gets the token plus its own tighter per-attempt timeout from a resilience pipeline (AddStandardResilienceHandler or Polly v8), configured per dependency.
  • Fan-out: start all independent calls immediately (hot tasks), model dependencies as a small DAG (await the SKU call, then fan out pricing/inventory), consume with Task.WhenEach so rendering can begin for sections as they arrive; at the deadline, render with what has completed and mark the rest degraded.
  • Isolation: bulkhead per downstream (bounded concurrency, sized from its capacity), circuit breaker with a fallback (last-good cache value or a placeholder), hedged requests for the one or two dependencies with long tails and cheap idempotent reads.
  • Resource hygiene: IHttpClientFactory named clients, HTTP/2 multiplexing where supported, MaxConnectionsPerServer tuned, straggler tasks cancelled (not abandoned) and their exceptions observed.
  • Caching: per-field TTLs, stale-while-revalidate for slow-changing data (reviews, recommendations), request coalescing so a hot SKU does not fan out 2,000 identical calls per second.
  • Observability: per-dependency latency histograms, timeout and breaker-open counters, "degraded sections" counter as the user-facing quality metric; traces with a span per call.

Trade-offs to name unprompted

  • Retries inside a 300 ms budget: usually zero or one, only for idempotent calls, only when the remaining budget allows — otherwise they amplify the outage.
  • Hedging cuts tail latency but doubles load on the hedged dependency; cap it by a percentage and disable it when the breaker is half-open.
  • Partial pages vs errors: product decision; the aggregation layer must expose which sections degraded so the front end and the SLO can account for it.
  • Concurrency limiter at the aggregation edge protects the downstreams from a traffic spike, at the cost of shedding your own requests.
  • All of this is async-native: any blocking call in the 12 clients destroys the model, so the client libraries are the first thing to audit.

Exercise 3 — Streaming ingestion pipeline with back-pressure

Prompt. Ingest a firehose of events (50k/s) from a message broker, enrich each event with a lookup, batch-write to a database, and expose a live-updating dashboard feed. The database can absorb ~5k rows/s per connection in batches. Design the in-process pipeline.

Clarifying questions to ask

  • Is ordering required (per key, global, none)?
  • What is acceptable end-to-end latency, and what is acceptable loss under overload (drop, spill to disk, slow the broker)?
  • Is the enrichment lookup cacheable, and what is its latency?
  • Delivery guarantees from the broker (at-least-once, ack semantics, visibility timeout)?
  • How many instances, and how is partitioning done?
Strong solution outline and trade-offs

Outline

  • Stages connected by bounded channels: consume → enrich → batch → write, each stage a BackgroundService loop (or several) reading one Channel and writing the next; bounds sized so total in-flight memory is known (e.g. 3 × 10k events).
  • Back-pressure: BoundedChannelFullMode.Wait everywhere in the critical path, so when the writer slows, the enrich stage blocks, the consumer blocks, and finally the broker prefetch stops — the broker is the buffer of record. Ack only after the write commits.
  • Enrichment: a bounded Parallel.ForEachAsync over the enrich channel with a cache in front of the lookup (MemoryCache or HybridCache), coalescing concurrent misses for the same key.
  • Batching: a batcher that pulls from its channel with WaitToReadAsync + TryRead up to N items or T milliseconds (via PeriodicTimer/Task.Delay with a TimeProvider), then hands the batch to K writer tasks each owning one connection (10 connections ≈ 50k rows/s); per-key ordering preserved by hashing keys to writers.
  • Dashboard feed: a side tap after the write stage into an unbounded-prioritized or DropOldest channel (lossy by design) exposed as SSE/IAsyncEnumerable per subscriber, each subscriber with its own bounded channel so a slow browser cannot stall ingestion.
  • Failure and shutdown: per-batch retries with backoff, poison events to a dead-letter topic, ApplicationStopping stops the consumer, downstream stages drain, unacked events return to the broker; metrics per stage: channel depth, items/s, batch size, write latency.

Trade-offs to name unprompted

  • Pull-based IAsyncEnumerable alone gives back-pressure but no parallelism; channels give both at the cost of explicit bounds and more moving parts.
  • Larger batches raise throughput and latency; the batcher's N/T are the tuning knobs and should be configuration.
  • Lossy dashboard tap vs exact: DropOldest is correct for a live view, wrong for anything audited.
  • Ack-after-commit gives at-least-once with duplicates on crash; idempotent writes (upsert on event id) make that safe.
  • Any synchronous call in a stage (a blocking lookup client, a sync database driver) caps the whole pipeline at thread count; the design assumes async drivers.

17. Night-before cheat sheet

10 most-asked

The ten questions most likely to come up, with the one-sentence answer that opens the door to the follow-ups above.

  1. What does await do? It registers the rest of the method as a continuation and returns to the caller; no thread blocks, and the continuation runs on whatever thread completes the task (or the captured context).
  2. Why does .Result deadlock in WPF but not in ASP.NET Core? UI apps have a single-threaded SynchronizationContext the continuation needs while the thread is blocked; ASP.NET Core has no context, so it starves instead of deadlocking.
  3. What does ConfigureAwait(false) do? Skips marshalling the continuation back to the captured context; use it in libraries, it is irrelevant in ASP.NET Core, and it does nothing when the task is already complete.
  4. What is thread-pool starvation? Blocked pool threads plus slow injection (about one thread per second above the minimum) so queued continuations cannot run; low CPU, rising queue length, staircase latency.
  5. Why is async void bad? No task to await or observe; exceptions go to the context or crash the process; only event handlers, wrapped in try/catch.
  6. When do you use ValueTask? Measured hot paths that usually complete synchronously or use a pooled source; await it exactly once, never block on it, otherwise use Task.
  7. How does cancellation work? Cooperatively: the callee polls or registers on a CancellationToken; nothing is forcibly stopped, so forward the token everywhere and stop honouring it past the point of no return.
  8. How do you run 1,000 I/O calls with at most 10 in flight? Parallel.ForEachAsync with MaxDegreeOfParallelism = 10, or a SemaphoreSlim(10) around each task plus WhenAll; never Parallel.ForEach with an async lambda.
  9. What does Task.WhenAll throw when several tasks fail? Awaiting it throws only the first exception; read task.Exception.InnerExceptions on the WhenAll task for all of them.
  10. What is new right now? .NET 10 LTS with built-in System.Linq.AsyncEnumerable; .NET 11 (GA 2026-11-10) Runtime Async, opt-in with runtime-async=on, which moves suspension into the runtime for cleaner live stacks and fewer allocations without changing semantics.
