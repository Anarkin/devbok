C# async/await and the Task-based asynchronous pattern

Async/await has been stable since C# 5 (2012) and, for fourteen years, has meant one thing: the compiler rewrites your method into a state machine and a Task is the promise that the state machine completes. Today the current platform is .NET 10 with C# 14, where the shape of the API is settled - ValueTask for hot paths, CancellationToken everywhere, ConfigureAwaitOptions (.NET 8), Task.WhenEach (.NET 9), and, new in .NET 10, LINQ over IAsyncEnumerable<T> in the box. The headline change is architectural: .NET 11 (Preview 7 now, GA in November 2026) ships runtime async, where the runtime itself understands async methods, the BCL is already compiled that way, and compiler-generated state machines become an implementation detail you opt into leaving behind with <Features>runtime-async=on</Features>. What interviewers still probe at lead level has not changed: sync-over-async deadlocks, thread-pool starvation, cancellation plumbing, and whether you can reason about where a continuation runs. Assumption: "modern" means .NET 8+ on ASP.NET Core; .NET Framework behaviour is called out explicitly wherever it differs.

01 · The mental model: what await really does

Docs: Task asynchronous programming model · How async/await really works in C# (Toub)

Everything else in this guide derives from one sentence: an async method is a method the compiler splits at every await, and a Task is the handle that tells callers when the last piece has run. Nothing about that sentence involves a thread. That is the mental model you must be able to reason from, because the majority of async bugs interviewers ask about - deadlocks, starvation, lost exceptions, "it works on my machine" latency - come from people who model async as "run on a background thread" instead of "resume later, wherever the completion arrives".

The problem it solves

Before C# 5 you had two choices for I/O that takes time: block a thread (simple, wastes a 1 MB stack and a scheduler slot per outstanding call, and on a server caps you at "number of threads" concurrent requests), or write callback code (APM BeginRead/EndRead, EAP events) which scales but turns every loop and try/finally into a hand-written state machine. Async/await is the compiler doing the second thing for you while you write the first. The design goal was explicitly scalability of I/O-bound work, not CPU parallelism - that distinction is the first thing a strong candidate says out loud.

What the compiler generates

For each async method the compiler emits a state machine type (a struct in Release, a class in Debug so the debugger can inspect it), moves your locals into fields, and puts your method body into MoveNext() with a switch on an int state. The original method just creates the machine, calls builder.Start(ref machine) and returns builder.Task. Inside MoveNext every await x becomes:

// what `var r = await x;` compiles to, conceptually
var awaiter = x.GetAwaiter();            // 1. the awaitable pattern: any type with GetAwaiter()
if (!awaiter.IsCompleted)                // 2. fast path: already done? then don't suspend at all
{
    state = 1;                           // 3. remember where to resume
    builder.AwaitUnsafeOnCompleted(ref awaiter, ref this); // 4. register continuation, box the struct ONCE
    return;                              // 5. give the thread back to whoever called us
}
// label for state 1 lands here
var r = awaiter.GetResult();             // 6. unwrap value, or rethrow the exception (original stack preserved)

Three consequences that are worth internalising:

  • Awaiting a completed task is synchronous and cheap. If IsCompleted is already true there is no suspension, no allocation, no scheduling; the method just carries on. This is why cached results, ValueTask fast paths and "usually-synchronous" I/O (a buffered Stream read) are nearly free.
  • The first real suspension is the expensive one. On the first return the struct state machine is boxed onto the heap (one allocation, holding all hoisted locals) and the Task object is created. Later awaits reuse that box. This is what runtime async in .NET 11 changes (unit 10).
  • The method returns to its caller at the first suspension, not at the end. Code before the first incomplete await runs synchronously on the caller's thread. This is why an async method that does 200 ms of CPU work before its first await blocks its caller for 200 ms - "async" did not make it concurrent.

Where does the continuation run?

This is the question everything else hangs on. When the awaited operation completes, somebody has to call MoveNext() again. The awaiter decides who, using this order of preference (it is in TaskAwaiter, not in the language):

That makes async cheap, but it also means a long-running continuation can hijack an I/O thread, and it is why TaskCreationOptions.RunContinuationsAsynchronously exists for TaskCompletionSource (unit 8).

The awaitable pattern is duck-typed

The compiler needs only a GetAwaiter() (instance or extension) returning something with bool IsCompleted, void OnCompleted(Action) (via INotifyCompletion, ideally ICriticalNotifyCompletion.UnsafeOnCompleted to skip ExecutionContext capture) and GetResult(). Task, ValueTask, Task.Yield()'s YieldAwaitable, ConfiguredTaskAwaitable and any custom awaitable all fit. That is also why you can write await someCancellationToken with a five-line extension method, and why await foreach and await using are just more sugar over the same pattern.

// A tiny custom awaitable: makes `await token;` mean "wait until cancelled". Useful in tests.
public static class CancellationTokenAwaiterExtensions
{
    public static CancellationTokenAwaiter GetAwaiter(this CancellationToken token) => new(token);

    public readonly struct CancellationTokenAwaiter(CancellationToken token) : ICriticalNotifyCompletion
    {
        public bool IsCompleted => token.IsCancellationRequested;
        public void OnCompleted(Action continuation) => token.Register(continuation);
        public void UnsafeOnCompleted(Action continuation) => token.UnsafeRegister(_ => continuation(), null);
        public void GetResult() { }
    }
}

What changed recently

The language surface has been stable since C# 7.x added generalised async return types (ValueTask, any type with an [AsyncMethodBuilder]) and C# 8 added async streams and await using. The runtime is where the movement is: .NET Core 2.1 rewrote the async machinery to allocate once per method instead of up to four times, .NET 6 added the pooling method builder, and .NET 11 (preview) moves the state machine into the runtime itself (runtime async, unit 10) so that live stack traces show your real call chain instead of AsyncMethodBuilderCore.Start frames. In interviews, being able to explain that await is a compiler feature over a runtime library, and that the library is what has been changing, marks you as someone who reads the release notes.

Interview trap

"Async runs the method on another thread." No: the method starts synchronously on the caller's thread and only yields at the first incomplete await. If you say Task.Run and async are interchangeable, a senior interviewer will follow up with "so where does the code before the first await run?" and you have lost the room. The correct framing: async is about not holding a thread while waiting; parallelism is a separate decision you make with Task.Run, Parallel, or multiple in-flight tasks.

Gotcha

An async method with no await (warning CS1998) still allocates a state machine and returns a completed Task; an exception thrown inside is captured into the task rather than thrown to the caller. A non-async method returning Task throws synchronously instead. That difference is exactly why "argument validation in an async method" is a classic question: validate in a non-async wrapper if you want eager throws, or accept that the exception surfaces at await.

Interview Q&A

Explain what the compiler does with an async method, in enough detail that I believe you have seen the IL.

The method body moves into a MoveNext on a generated state machine struct; locals that survive an await become fields, the method itself just starts the machine and returns builder.Task. Each await becomes: get the awaiter, check IsCompleted, and if not, store the state number, hand the machine to AwaitUnsafeOnCompleted (which boxes the struct on the first suspension and registers MoveNext as the continuation) and return. When the awaiter fires, MoveNext re-enters, jumps to the stored state and calls GetResult(), which either returns the value or rethrows the captured exception with its original stack. Exceptions escaping MoveNext are caught by the machine and placed into the task via SetException, which is why they surface at the caller's await, not at the call site.

What is the difference between an asynchronous operation and a parallel one, and why does the distinction matter on a web server?

Asynchrony is about not occupying a thread while an operation is in flight - the I/O completion, not a thread, drives the continuation. Parallelism is about using multiple threads to make CPU-bound work finish sooner. On a web server the pool has roughly one thread per core, so asynchronous I/O lets thousands of requests be in flight with a handful of threads, while spawning parallel CPU work per request (Task.Run, Parallel.For) competes with other requests for the same cores and often reduces overall throughput. The lead-level framing is: async for scalability, parallelism for latency of CPU-bound work, and never confuse offloading to the pool with "making it asynchronous".

Where does the code after an await run?

Wherever the awaiter decides: on a captured SynchronizationContext if one existed when the await started, on a non-default TaskScheduler if that was current, and otherwise inline on the thread that completed the awaited operation - typically a thread-pool or I/O thread. On ASP.NET Core there is no synchronization context, so continuations run inline on completing threads; in a UI app they are posted back to the UI thread. Two subtle points interviewers like: if the awaited task was already complete there is no hop at all, and a continuation on a TaskCompletionSource runs synchronously inside SetResult unless the source was created with RunContinuationsAsynchronously.

Why does the async method builder use AwaitUnsafeOnCompleted rather than AwaitOnCompleted? What does "unsafe" mean here?

"Unsafe" refers to ExecutionContext flow, not memory. OnCompleted captures the current ExecutionContext (with its AsyncLocal values and, historically, security context) and restores it when the continuation runs; UnsafeOnCompleted skips that capture because the async method builder already captures and flows the context itself at the state-machine level. Using the unsafe variant avoids double capture and is a measurable allocation saving in hot code. This is also the hook .NET 11 uses for its "skip ExecutionContext restore when nothing changed" optimisation for Task and ValueTask continuations.

A colleague marks a CPU-heavy method async and returns Task.FromResult(Compute()). What is your code-review comment?

That method is synchronous in every meaningful sense - it blocks the caller for the full computation and only wraps the answer in a completed task - so the signature lies. Either make it plainly synchronous and let the caller decide whether to offload with Task.Run, or, if it is a library that must honour a Task-returning interface, document that it completes synchronously. On a server I would not wrap it in Task.Run inside the library, because that steals a pool thread for no scalability gain and hides the cost from the caller. The general rule: expose truly asynchronous work as async; do not fake it, and do not use the pool to make a signature look asynchronous.

What is the "awaitable pattern" and why is it duck-typed rather than an interface?

An expression is awaitable if it has a GetAwaiter() method (instance or extension) returning a type with IsCompleted, GetResult() and INotifyCompletion.OnCompleted (optionally ICriticalNotifyCompletion.UnsafeOnCompleted). It is pattern-based, like foreach and LINQ, so that struct awaiters avoid boxing, so that existing types can be made awaitable via extension methods, and so that the compiler can bind statically without virtual calls on the hot path. Practical consequences: Task.Yield() returns a YieldAwaitable rather than a Task to avoid the allocation, ConfigureAwait returns a different awaitable type instead of a task, and you can add awaiters for things like CancellationToken, Process exit or TimeSpan in a few lines.

What happens to an exception thrown before the first await in an async method versus a non-async Task-returning method?

In an async method every exception, including one thrown on the very first line, is caught by the state machine and stored in the returned task; the caller sees it only when awaiting or inspecting the task. In a non-async method that returns a Task, an exception before the task is created propagates synchronously from the call. This matters for argument validation (an ArgumentNullException surfaces later and possibly on another thread), for fire-and-forget calls (the exception is silently stored), and for Task.WhenAll composition (a synchronously thrown exception aborts building the list before any task starts). The idiom is an eager-validation non-async wrapper delegating to a private async core when eager throws matter.

Explain why a struct state machine is boxed and when. Could the compiler avoid it?

The struct lives on the stack of the caller while the method runs synchronously; the moment the method must suspend, its state has to outlive that stack frame, so AwaitUnsafeOnCompleted boxes the struct into a heap object that also doubles as the Task's completion object (.NET Core 2.1 merged these so it is one allocation, not several). It happens only on the first incomplete await; subsequent suspensions reuse the same box. The compiler cannot avoid it in the classic design because the CLR has no way to keep a stack frame alive across a return; that is precisely the limitation runtime async in .NET 11 removes by letting the runtime capture and restore frames itself.

Is await ever free? Give me the cases and the cost model.

If the awaited operation is already complete, the await costs a property check and a GetResult() call - no allocation, no yield - so awaiting cached or synchronously completing operations is effectively free, which is the whole basis for ValueTask. The first incomplete await in a method costs one heap allocation for the boxed machine plus the Task (merged), the registration of the continuation, and an ExecutionContext capture; every later incomplete await costs just the registration. Then the resumption costs a context restore and a possible context hop. A fair summary for a lead: microseconds per suspension and a few hundred bytes, negligible against any real I/O, but material if you suspend millions of times per second on a hot path, which is where ValueTask, pooling and runtime async earn their keep.

How would you explain async/await to a team that is skeptical it is worth the complexity for their internal line-of-business API?

I would not sell it on speed - a single request is not faster, and it can even be marginally slower - but on capacity and resilience under load: with blocking I/O, thread count is the concurrency ceiling, and when a downstream dependency slows down, every waiting request pins a thread until the pool is exhausted and the whole service stalls. With async, slow dependencies cost memory for parked state machines instead of threads, so the service degrades gracefully and the pool stays responsive for health checks and other endpoints. I would pair that with a concrete failure story (thread-pool starvation during a database incident is the classic), an analyzer set so the team cannot accidentally block, and a rule that new code is async end-to-end rather than half-converted, because sync-over-async in the middle is the worst of both worlds.

02 · Task and Task<T>: the promise type

Docs: Task class · Task-based asynchronous pattern (TAP) · Task.WhenEach

A Task is a promise: an object that will, exactly once, transition from not-completed to one of three terminal states - RanToCompletion, Faulted (with an AggregateException holding one or more exceptions), or Canceled. It carries a result (Task<T>), a list of continuations to run on completion, and, since it was designed in .NET 4.0 for the Task Parallel Library, a bunch of baggage from a world before await: Wait(), Result, ContinueWith, Task.Factory.StartNew and child tasks. A good mental model separates the two faces of the type: Task-as-promise (what async I/O returns - nothing is "running", something will "complete") and Task-as-work-item (Task.Run - a delegate queued to the thread pool). Both share the type, which is convenient for composition and the root of most confusion.

Composition

The power of a promise type is that you compose promises without threads. The three combinators every interview touches:

// Fan-out / fan-in: start all, then wait for all. Exceptions: await rethrows the FIRST,
// t.Exception (AggregateException) holds ALL of them.
Task<Product>[] lookups = ids.Select(id => catalog.GetAsync(id, ct)).ToArray();
Product[] products = await Task.WhenAll(lookups);          // .NET 9+: also accepts params ReadOnlySpan<Task>

// First-wins, e.g. a timeout race (prefer WaitAsync, unit 4). WhenAny never throws by itself.
Task finished = await Task.WhenAny(work, Task.Delay(timeout, ct));
if (finished != work) throw new TimeoutException();
await work;                                                 // observe result or exception

// .NET 9: process in completion order without the O(n²) WhenAny-in-a-loop anti-pattern.
await foreach (Task<Product> done in Task.WhenEach(lookups).WithCancellation(ct))
{
    Product p = await done;                                 // already complete: no suspension
    render(p);
}

Note what WhenAll is not: it does not start anything, does not throttle anything, and does not stop the others when one fails. If you call an async method in a Select you have already started all of them; if you need "at most 8 in flight" you need Parallel.ForEachAsync or a SemaphoreSlim (unit 8). And the exception behaviour is deliberately asymmetric: await Task.WhenAll(...) throws only the first exception so that catch (HttpRequestException) works naturally, while whenAllTask.Exception.InnerExceptions has every failure for logging.

The dangerous members: Result, Wait(), GetAwaiter().GetResult()

All three block the calling thread until the task completes. That blocks a thread (defeating the purpose), can deadlock when the task needs the blocked thread to complete (unit 5), and, in the case of Result/Wait(), wraps the failure in an AggregateException. GetAwaiter().GetResult() throws the original exception type, which is why you see it in the few legitimate sync-over-async spots (a Main that cannot be async in old code, a constructor that must not be, a legacy interface). The rule for review is simple: any of these in a request path or on a UI thread is a defect unless justified in a comment.

async void: the one shape you never return

async void exists solely for event handlers, where the signature is fixed. It has no task, so the caller cannot await it, cannot observe completion, and cannot catch its exceptions: a throw inside an async void is posted to the SynchronizationContext if there is one, and otherwise raised on the thread pool and crashes the process. Tests that call async void methods pass before the method finishes. The rule: async Task everywhere, async void only for UI event handlers, with a try/catch around the whole body.

Fire-and-forget, done responsibly

// Wrong: unobserved exception, no cancellation, runs during shutdown, silently dies with the request scope.
_ = SendAuditAsync(evt);

// Right on ASP.NET Core: hand it to a hosted service through a channel; the service owns lifetime, retries, logging.
await _auditQueue.Writer.WriteAsync(evt, ct);

// Acceptable in a desktop app / one-off: observe the exception explicitly.
SendAuditAsync(evt).ContinueWith(
    t => _log.LogError(t.Exception!.InnerException, "audit failed"),
    TaskContinuationOptions.OnlyOnFaulted | TaskContinuationOptions.ExecuteSynchronously);

On a web server "fire and forget" also means "runs outside the request's DI scope and after the HttpContext is disposed", so a DbContext captured from the request will throw ObjectDisposedException. The .NET answer since .NET Core 2.x is the hosted-service + Channel<T> pattern (unit 8), not a bare unawaited task.

What changed recently

.NET 9 added Task.WhenEach and params ReadOnlySpan<Task> overloads for WhenAll/WhenAny (no array allocation for a fixed set); .NET 8 added Task.Delay/WaitAsync overloads taking a TimeProvider (unit 9) and ConfigureAwaitOptions (unit 5); .NET 6 added Task.WaitAsync for timeouts on non-cancellable tasks. Nothing in the Task API is deprecated, but ContinueWith, Task.Factory.StartNew without options, AttachedToParent and cold tasks are legacy shapes you should recognise and replace with await.

Interview trap

Task.Factory.StartNew(async () => ...) returns Task<Task>. Awaiting it waits only for the outer delegate to return the inner task, i.e. until the first await inside; the actual work is still running. Task.Run unwraps automatically. Candidates who have been bitten will say ".Unwrap()"; candidates who have not will confidently claim the two are equivalent. The same trap hides in ContinueWith(async t => ...).

Gotcha

A Task is not a cancellation mechanism and there is no task.Cancel(). Losing a reference to a task does not stop the work, and neither does awaiting WhenAny and walking away from the loser: it keeps running, keeps holding its connection, and completes (or faults, unobserved) later. Anything that starts work must be handed the token that stops it (unit 4).

Interview Q&A

What is the difference between Task.Run and Task.Factory.StartNew, and when would you still use the latter?

Task.Run is a curated wrapper: it always uses the default TaskScheduler, sets DenyChildAttach so a stray AttachedToParent cannot hook into it, and unwraps Task<Task> when you pass an async lambda. Task.Factory.StartNew is the raw API: it takes a scheduler and TaskCreationOptions, honours TaskScheduler.Current by default (which is a subtle bug when called from inside another task on a custom scheduler), and returns Task<Task> for async delegates unless you Unwrap(). The remaining legitimate use is TaskCreationOptions.LongRunning to get a dedicated non-pool thread for a long-lived loop, or to target a specific scheduler such as a UI or a concurrency-limited one. In code review I treat any other StartNew as legacy to be rewritten as Task.Run.

Explain how exceptions propagate from Task.WhenAll and how you would log all failures without losing typed catch blocks.

When you await the combined task it rethrows only the first exception, so that a catch (HttpRequestException) reads naturally, but the combined task's Exception property is an AggregateException containing every faulted task's exception. The idiom is to keep the WhenAll task in a variable, await it inside a try, and in the catch log whenAll.Exception?.InnerExceptions before deciding what to do. Two details show depth: cancellation of any input marks the combined task Canceled only if no task faulted (faults win over cancellation), and if all inputs fail with the same OperationCanceledException the await throws that, not an aggregate. In .NET 9 you can alternatively use Task.WhenEach to handle each outcome as it arrives, which is often the better design for partial failure.

Why is async void dangerous and what is the one place it is acceptable?

An async void method has no task, so nothing can await it, compose it or observe its failure; an exception escaping it is thrown on the SynchronizationContext if one exists, and otherwise on the thread pool, which terminates the process. It also breaks testing (the test returns before the method finishes) and lifetime management (ASP.NET Core cannot know a request is still doing work). It is acceptable only for event handlers whose delegate signature is fixed (EventHandler), and then the entire body should be wrapped in a try/catch that logs. Everywhere else, including "fire and forget", use async Task and either await it or hand it to something that owns its lifetime, such as a hosted service.

What does "fire and forget" look like in a production ASP.NET Core service?

Not an unawaited call: that runs outside the request scope, so scoped services like a DbContext are disposed under it, it dies with the process on shutdown, its exceptions are unobserved and its logging loses the request context. The production shape is a bounded Channel<T> that the request writes to and a BackgroundService that reads from, owning cancellation via the host's stopping token, its own DI scope per item, retries, and metrics on queue depth. If durability matters (payment events, emails) the queue is an external broker or an outbox table, because an in-process channel is lost on a crash. The judgement call I make in review is whether "losing this on restart" is acceptable; if not, in-memory fire-and-forget is the wrong tool regardless of how it is written.

What is the difference between task.Result, task.Wait() and task.GetAwaiter().GetResult()?

All three block the current thread until the task completes and all three can deadlock on a single-threaded context or starve the pool. Result and Wait() wrap any failure in an AggregateException, while GetAwaiter().GetResult() rethrows the original exception exactly as await would, which is why the rare justified blocking sites - an old-style entry point, a constructor, a synchronous interface you cannot change - use that form. None of them should appear in request-handling or UI code; the analyzer set I install (CA1849, VSTHRD002 in VS-SDK contexts, or a custom banned-API list) flags them so the discussion happens at review time rather than in an incident.

Explain Task.WhenAny-based timeouts and why Task.WaitAsync replaced them.

The classic pattern races the work against Task.Delay(timeout), checks which finished first, and throws if it was the delay; it works but leaks: the delay's timer keeps running until it fires unless you cancel it, and the losing work continues regardless. Task.WaitAsync(timeout, ct) (.NET 6) wraps a task so that the await completes with a TimeoutException or OperationCanceledException when the limit is hit, with the timer cleaned up. It still cannot stop the underlying operation, which is the same limitation and the reason to pass a real token whenever the API accepts one; WaitAsync is for operations you cannot cancel, like a third-party callback or a TaskCompletionSource you do not control.

What are the three terminal states of a task and how does an async method end up in each?

RanToCompletion when MoveNext returns normally; Faulted when any exception escapes the body, stored in Exception as an AggregateException; and Canceled when the escaping exception is an OperationCanceledException (or subclass, including TaskCanceledException) - the builder special-cases it and calls TrySetCanceled with the exception's token. So an async method never "returns cancelled"; it throws, and the task state reflects the exception type. This is why ThrowIfCancellationRequested() produces a cancelled task rather than a faulted one, why IsCanceled is true for it, and why Task.WhenAll treats it differently from a fault.

When is ContinueWith still the right tool, and what defaults make it dangerous?

Almost never for application code; await expresses the same thing with correct exception, cancellation and context semantics. Its defaults bite: it schedules on TaskScheduler.Current rather than default (so behaviour changes depending on where it runs), it does not unwrap async delegates, it runs even when the antecedent faulted unless you specify OnlyOnRanToCompletion, and the continuation's own exceptions are easy to leave unobserved. The remaining use is infrastructure: attaching a synchronous, non-throwing observer to a task you do not await (fire-and-forget logging with OnlyOnFaulted | ExecuteSynchronously), or implementing awaiter-like plumbing where await is not available. In review I ask for it to be replaced unless it is one of those.

How do you run N async operations with at most K in flight, and why does Task.WhenAll alone not do it?

Calling the async methods to build the list starts all N immediately, so WhenAll only waits - it never throttles. For bounded concurrency use Parallel.ForEachAsync(items, new ParallelOptions { MaxDegreeOfParallelism = K, CancellationToken = ct }, async (item, token) => ...) (.NET 6), which also propagates cancellation and stops on first failure; or, when you need results in order or custom retry, a SemaphoreSlim(K) with WaitAsync inside each task. At scale I prefer a channel with K consumers so the producer sees backpressure. The lead-level nuance is choosing K from the downstream's capacity (connection-pool size, rate limit), not from core count, because these operations are I/O-bound.

What is a "cold" task and why did the design move away from it?

A cold task is one created with new Task(...) that does nothing until Start() is called; it came from the .NET 4.0 TPL, where tasks were units of parallel work and it was useful to build a graph before running it. With await and I/O-bound promises the model inverted: a task represents an operation already in flight, and TAP guidelines say a method returning a task must return a hot one. Cold tasks break composition (awaiting a task that never started hangs forever), which is the most common bug when people find them in legacy code. Modern equivalents are a Func<Task> for deferred work, or a TaskCompletionSource when you need to control completion.

03 · ValueTask and allocation discipline

Docs: ValueTask<TResult> · Understanding the whys, whats and whens of ValueTask (Toub) · CA2012

Task<T> is a class; every completion of an async method that suspended allocates one, and even one that did not suspend allocates a Task<T> to hold the result unless the runtime has a cached instance (it caches Task<bool>, small ints, Task.CompletedTask and a few others). For an API called millions of times per second that completes synchronously most of the time - Stream.ReadAsync on a buffered stream, PipeReader.ReadAsync, a cache lookup - that allocation is the dominant cost. ValueTask<T> (.NET Core 2.0 / System.Threading.Tasks.Extensions) is a struct that holds either a T (synchronous completion, zero allocation) or a Task<T>, and since .NET Core 2.1 also a third option: an IValueTaskSource<T> plus a version token, which lets a library reuse one pooled object across many asynchronous completions. Non-generic ValueTask arrived with .NET Core 2.1 for the same reason.

The mental model: a ticket, not a promise

A Task is a promise you can share, await repeatedly, store, and query; a ValueTask is a single-use ticket. Because its backing object may be pooled and reused as soon as you have consumed the result, the rules are strict and CA2012 enforces most of them:

  • Await it exactly once, or call .AsTask() once and then treat that task normally.
  • Never await it concurrently from two places, never store it in a field and await later after the callee may have moved on, never call .Result/GetAwaiter().GetResult() unless IsCompleted is true.
  • Do not mix: Task.WhenAll(vt1.AsTask(), vt2.AsTask()) is fine; a ValueTask[] is not a thing you can combine.
  • If you must break the rules (cache it, await twice), call .Preserve() first (.NET 5), which materialises a real task.
public interface ICache
{
    ValueTask<Entry?> GetAsync(string key, CancellationToken ct);   // hot: mostly synchronous hits
}

public sealed class MemoryFirstCache(IDistributedCache l2) : ICache
{
    private readonly ConcurrentDictionary<string, Entry> _l1 = new();

    public ValueTask<Entry?> GetAsync(string key, CancellationToken ct)
    {
        if (_l1.TryGetValue(key, out var hit))
            return new ValueTask<Entry?>(hit);                    // 0 allocations on the hit path
        return GetFromL2Async(key, ct);                            // real async only when needed
    }

    private async ValueTask<Entry?> GetFromL2Async(string key, CancellationToken ct)
    {
        byte[]? bytes = await l2.GetAsync(key, ct).ConfigureAwait(false);
        if (bytes is null) return null;
        var e = Entry.Deserialize(bytes);
        _l1[key] = e;
        return e;
    }
}

// Consumer: the rule is "await once". Fast-path check is optional and only pays in tight loops.
ValueTask<Entry?> vt = cache.GetAsync(key, ct);
Entry? entry = vt.IsCompletedSuccessfully ? vt.Result : await vt;   // never .Result without the check

Pooling the asynchronous path

C# 10 / .NET 6 added [AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))], applicable per method, which makes the state-machine box come from a pool instead of the GC when the method actually suspends. It is opt-in because the pooled object must be returned - which is exactly what the single-await rule guarantees - and because it trades a small allocation for a slightly more expensive rent/return on a cache line other cores may be touching. Measure before using it; Kestrel and System.IO.Pipelines do, most application code should not. Writing your own IValueTaskSource<T> is easy with ManualResetValueTaskSourceCore<T>, which handles the version token, continuation and context capture for you.

What changed recently

The type itself has been stable since .NET 5 (Preserve()). What changed is what surrounds it: .NET 11's runtime async supports ValueTask-returning methods natively, the JIT now recognises ValueTask.FromResult and folds it into the fast path, and the continuation machinery for both Task and ValueTask skips ExecutionContext capture/restore when there is nothing to restore (no AsyncLocal changes) - a .NET 11 change that reduces the per-await overhead ValueTask was invented to avoid. Analyzer CA2012 (ValueTask misuse) has been on by default in the SDK since .NET 5.

Interview trap

"I use ValueTask everywhere because it is faster." It is not faster in the asynchronous case - it is bigger (two words vs one reference) and adds checks; it is faster only when it avoids an allocation because the operation completed synchronously. Returning ValueTask from a method that always awaits a database call gains nothing and imposes the single-consumption rules on every caller. Interviewers want to hear "measured hot path, mostly synchronous completion, I own the callers".

Gotcha

Awaiting a ValueTask twice can return the wrong result, not just throw. With an IValueTaskSource backing object, the second await after the object was recycled may observe another operation's completion, or throw InvalidOperationException from the version check if you are lucky. This is a data-corruption class bug that only appears under load, which is why CA2012 is a warning you never suppress.

Interview Q&A

What problem does ValueTask<T> solve and what does it cost?

It removes the Task<T> heap allocation for operations that complete synchronously - a struct holding either the result or a task/source - and, with IValueTaskSource, allows the asynchronous completion object to be pooled too. The cost is a larger return value (result-or-object plus a token), extra branching in the awaiter, and a consumption contract: await once, never concurrently, no Result before completion, AsTask()/Preserve() when you need task semantics. So it pays only on hot paths that are usually synchronous or where you control pooling; for an ordinary repository method that always hits the database it is pure ceremony. The BCL uses it on Stream, pipes, channels, IAsyncEnumerator and IAsyncDisposable for exactly those reasons.

List the rules of consuming a ValueTask and explain the failure mode behind each.

Await it once, because the backing IValueTaskSource may be recycled the moment the result is read, so a second await can observe a different operation. Do not await it from two places concurrently, because the source supports a single continuation and the second registration throws or is lost. Do not call Result or GetAwaiter().GetResult() unless IsCompleted is true, because unlike Task it may not block and can return garbage or throw. Do not store it across an arbitrary delay, because the version token can be reused. When any of these are needed, convert with AsTask() once or call Preserve(); CA2012 flags most violations at build time.

How does IValueTaskSource<T> make pooling safe, given that a struct copy could outlive the pooled object?

The ValueTask carries a short version token alongside the source reference; every call into the source - GetStatus, OnCompleted, GetResult - passes that token and the source compares it with its current version, throwing if they differ. When an operation completes and the consumer reads the result, the source increments its version and returns itself to the pool; any stale ValueTask copy now has a mismatched token. This is a detection mechanism, not prevention: it makes misuse fail fast instead of silently, most of the time. ManualResetValueTaskSourceCore<T> implements the whole dance - token, status, continuation, ExecutionContext and SynchronizationContext capture - so a custom source is thirty lines.

When should a public library API return Task rather than ValueTask, even if the implementation is usually synchronous?

When consumers are likely to need task semantics - awaiting multiple times, passing to WhenAll, caching the result, awaiting from multiple callers - because forcing AsTask() on them adds the allocation back plus friction and a class of misuse bugs. Also when the method is rarely called or is dwarfed by the work it does; the allocation is noise next to a network round trip. And when you want to keep the option of returning a cached completed task, which is already allocation-free for Task and for common Task<T> values. The BCL's own guidance is Task by default, ValueTask for high-frequency, likely-synchronous, single-consumer members; I apply the same and require a benchmark in the PR that introduces a ValueTask signature.

What does PoolingAsyncValueTaskMethodBuilder do and why is it not the default?

Applied via [AsyncMethodBuilder] on an async ValueTask-returning method (C# 10 / .NET 6), it makes the state machine's heap box come from a per-type pool and return to it when the ValueTask is consumed, so a method that suspends does not allocate per call. It is opt-in because it only works under the single-await contract, because the pool has its own cost (rent/return with cross-core cache traffic, potential memory retention), and because in many workloads the GC handles short-lived boxes so cheaply that pooling is slower. Microsoft measured it as a win in Kestrel-scale request pipelines and a wash elsewhere; the honest answer is "measure, and expect not to need it in application code".

What is the IsCompletedSuccessfully fast-path idiom and when is it worth writing?

Checking vt.IsCompletedSuccessfully and reading vt.Result directly skips the awaiter entirely, avoiding a GetAwaiter() call, the state-machine bookkeeping and, if the surrounding method has no other awaits, potentially the whole async state machine when written as a non-async method that only awaits on the slow path. It is worth it in tight loops over a hot ValueTask API - reading from a PipeReader, iterating a channel - where the compiler-generated overhead is measurable. In ordinary code just await it; the awaiter already takes the synchronous path without suspending, and the idiom trades readability for nanoseconds. Never read Result without the check.

How would you migrate a hot interface from Task<T> to ValueTask<T> across a large codebase?

It is a binary and source breaking change, so I would treat it as a versioned API change: add the ValueTask member alongside (or in a new interface), implement the old one as AsTask() over the new during transition, and drive callers over with an analyzer or obsoletion warning. Before any of that I would prove the win on the actual workload with allocation profiling, because most hot paths turn out to be dominated by something else. I would also audit consumers for patterns that break under ValueTask - stored tasks, WhenAll over collections, double awaits - and enable CA2012 as an error. The goal is that the change lands as "fewer gen0 GCs, lower p99" with numbers attached, not as a stylistic preference.

Why does IAsyncEnumerator<T>.MoveNextAsync return ValueTask<bool> rather than Task<bool>?

Because an async stream typically yields many items and most MoveNextAsync calls complete synchronously - the next item is already buffered, or the iterator's code between yields did not await - so allocating a Task<bool> per element would make streaming allocate linearly in the number of items. With ValueTask<bool>, synchronous steps are free, and the compiler-generated async iterator uses a single reusable IValueTaskSource-style object for the asynchronous ones, so an entire enumeration allocates roughly once. The same reasoning gives IAsyncDisposable.DisposeAsync a ValueTask. It also explains why await foreach consumes each MoveNextAsync exactly once: the pattern is built around the single-consumer contract.

A reviewer says "return Task.FromResult here, it is fine". When are they right?

When the method is not on a hot path, or when the result type is one the runtime caches - Task.CompletedTask, Task<bool> for true/false, small integers, and Task<T> for null/default in some versions - so FromResult allocates nothing anyway. It is also right when the signature is a pre-existing Task-returning interface that you cannot change and the call frequency does not justify the churn. They are wrong when the method is called per byte, per message or per cache lookup and completes synchronously the vast majority of the time; there, FromResult is the allocation ValueTask exists to remove. My review comment would ask which case we are in and for a number.

How do Task caching tricks (returning a stored completed task) relate to ValueTask?

They attack the same allocation from the other side: a Task<T> for a known value can be created once and returned every time, which is allocation-free and safe to await repeatedly - the runtime does this for common values and libraries do it for things like "read returned 0 bytes". It only works for a small, fixed set of results; for arbitrary values you would need a cache keyed by value, which is where ValueTask wins. There is a hybrid: keep a cached Task<T> for the last result and return it when the next result is equal, as Stream implementations did before ValueTask existed. Knowing this history explains why the BCL still has both mechanisms side by side.

04 · Cancellation, done cooperatively

Docs: Cancellation in managed threads · CancellationTokenSource · CA2016 (forward the token)

.NET has no way to kill an asynchronous operation from outside, by design: Thread.Abort was removed in .NET Core because interrupting code at an arbitrary point corrupts state. Instead cancellation is a request carried by a CancellationToken, a readonly struct that is cheap to copy and points at a shared CancellationTokenSource. The source owns the state and the Cancel() method; the token only lets you observe - poll IsCancellationRequested, throw via ThrowIfCancellationRequested(), or register a callback with Register. The split is deliberate: whoever receives a token can never cancel other people's work, which is why you hand out tokens freely and keep sources private.

The mental model: a one-way flag with subscribers

Think of the source as a latch that goes from "not cancelled" to "cancelled" exactly once and never back, and of every awaiting operation as either polling that latch between steps (CPU loops) or subscribing to it (I/O: the socket read registers a callback that closes the handle, the Task.Delay registers one that fires the timer's completion early). Cancellation is only as prompt as the deepest operation that actually looks at the token. That gives you the three rules of plumbing:

  1. Accept a token on every method that can wait, as the last parameter, defaulting to default (CA1068 for ordering, CA2016 for forgetting to forward it).
  2. Forward it to every awaited call that accepts one. A method that takes a token and does not pass it on is the most common cancellation bug in real code.
  3. Check it in CPU-bound loops with ThrowIfCancellationRequested() - I/O does that for you, tight loops do not.
app.MapGet("/report/{id}", async (int id, ReportService svc, CancellationToken ct) =>
{
    // ct here is HttpContext.RequestAborted: fires when the client disconnects or Kestrel shuts down.
    // Composition: request token + our own SLA. Dispose the linked source or its registration leaks.
    using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
    cts.CancelAfter(TimeSpan.FromSeconds(10));
    try
    {
        return Results.Ok(await svc.BuildAsync(id, cts.Token));
    }
    catch (OperationCanceledException) when (ct.IsCancellationRequested)
    {
        return Results.StatusCode(499);          // client went away: nobody is listening, log at debug
    }
    catch (OperationCanceledException)
    {
        return Results.StatusCode(504);          // our own timeout: this one is an incident signal
    }
});

public sealed class ReportService(AppDbContext db, HttpClient http)
{
    public async Task<Report> BuildAsync(int id, CancellationToken ct)
    {
        var rows = await db.Rows.Where(r => r.ReportId == id).ToListAsync(ct);   // EF Core honours ct

        foreach (var row in rows)
        {
            ct.ThrowIfCancellationRequested();                                    // CPU loop: poll
            report.Add(Compute(row, fx));
        }
        return report;
    }
}

Exceptions: OperationCanceledException is the contract

A cancelled operation ends by throwing OperationCanceledException (OCE) carrying the token; TaskCanceledException is a subclass thrown by Task-level APIs such as Task.Delay and HttpClient (which also throws it for timeouts, wrapping a TimeoutException since .NET 5 so you can tell the two apart). Always catch the base type. An async method that lets an OCE escape ends in the Canceled state, not Faulted (unit 2), and the token on the exception tells you whose cancellation it was - the when filter in the example is how you distinguish "client left" (noise) from "we timed out" (signal). Never swallow OCE and return a partial result as if it were success; return nothing, because the caller asked you to stop.

What cancellation does not do

Cancelling a token does not stop work that is not looking at it; a Task.WaitAsync(ct) or WhenAny-race returns control to you while the original operation is still running and still holding its resources. That is fine for a UI (the user pressed Stop) and dangerous on a server (the "abandoned" query still occupies a connection-pool slot; 100 abandoned queries per second exhaust the pool). Also, some operations are deliberately non-cancellable once past a point: the last step of a file write, a payment capture, a SqlTransaction.Commit. The pattern there is to check the token before the point of no return and ignore it after, and to say so in a comment.

What changed recently

CancelAsync (.NET 8) is the notable modern addition; TryReset (.NET 6) and UnsafeRegister (.NET Core 3.0) are the performance ones. ASP.NET Core has passed HttpContext.RequestAborted to handlers since 1.0 and minimal APIs bind a CancellationToken parameter to it automatically; IHostApplicationLifetime.ApplicationStopping and the stoppingToken of BackgroundService.ExecuteAsync are the shutdown tokens, with a default 30 s (.NET 8+; it was 5 s before) HostOptions.ShutdownTimeout before the host gives up on you.

Interview trap

"I passed the token, so cancellation works." Interviewers follow up with "where does it actually take effect?" The honest answer walks the chain: the HTTP request registers the token to abort the connection; EF Core passes it to ADO.NET, which for SQL Server cancels the command over the wire; a foreach over rows polls it only if you added ThrowIfCancellationRequested; a lock or Thread.Sleep ignores it entirely. A candidate who can name the first non-cooperative step in their own stack has debugged this for real.

Gotcha

Cancel() runs callbacks inline. If a registered callback awaits something synchronously or takes a lock, the thread calling Cancel() - often a timer thread, or the Kestrel connection thread noticing a disconnect - blocks. Since .NET 8, prefer await cts.CancelAsync() from async code, and keep callbacks tiny (set a flag, complete a TaskCompletionSource, close a handle). A callback that throws makes Cancel() throw an AggregateException after running the others.

Interview Q&A

Why is cancellation in .NET cooperative, and what are the trade-offs versus forcibly stopping work?

Forcible termination (Thread.Abort, removed in .NET Core) can interrupt code between two writes that must be atomic, leaving locks held, files half-written and shared state corrupt, and it cannot reach into an asynchronous operation at all because nothing is on a thread while it waits. Cooperative cancellation instead passes a token that operations check or subscribe to, so work stops only at points the author declared safe, and resources are released through ordinary finally blocks. The trade-off is that cancellation is only as responsive as the least cooperative step, that the token must be threaded through every layer, and that authors must consciously handle points of no return. In practice the discipline is worth it: the failure mode of forgetting is "stops late", not "corrupts data".

Walk me through what happens, mechanically, when a browser closes the connection mid-request on ASP.NET Core.

Kestrel's transport notices the socket close and cancels the per-request CancellationTokenSource behind HttpContext.RequestAborted; that runs every registered callback synchronously on the transport thread. If my handler passed that token (directly or linked) to SqlCommand.ExecuteReaderAsync, ADO.NET's registration sends an attention packet and the command completes with OperationCanceledException; an HttpClient call's registration aborts its request; a Task.Delay completes early. The exception propagates up my async chain as a cancelled task, the endpoint returns, and ASP.NET Core discards the response since nobody is listening. If instead I forgot to forward the token, the query runs to completion, holding a connection-pool slot for a client that is gone, which under a retry storm is how pools get exhausted.

What is the difference between OperationCanceledException and TaskCanceledException, and which do you catch?

TaskCanceledException derives from OperationCanceledException and is what task-level APIs throw - Task.Delay, Task.WhenAll of cancelled tasks, and notably HttpClient, which throws it both for token cancellation and for its own timeout (with an inner TimeoutException since .NET 5 so you can distinguish). Direct ThrowIfCancellationRequested() and most BCL I/O throw the base OperationCanceledException. So you catch the base type, always, and if you need the cause you inspect the token in an exception filter (when (ct.IsCancellationRequested)) or the inner exception. Catching only TaskCanceledException is a bug I flag in review because it silently misses half the cases.

How do you combine a request's cancellation with a per-operation timeout, and what must you not forget?

CancellationTokenSource.CreateLinkedTokenSource(requestToken) plus CancelAfter(timeout) on the linked source, then pass linked.Token downstream; either trigger cancels it. The thing to not forget is disposing the linked source when the operation completes: it registers a callback on the parent, and if the parent is long-lived (application stopping, a per-connection token) every undisposed link is a leak of the source, its timer and everything the token's registrations capture. Second thing: decide how to distinguish the two causes at the catch site using the parent token's IsCancellationRequested, because the exception carries the linked token. Third, for pure timeouts on tasks you cannot cancel, task.WaitAsync(timeout, ct) is simpler and disposes its own timer.

Explain CancellationTokenSource.CancelAsync (.NET 8). Why was it needed?

Cancel() invokes all registered callbacks synchronously, on the caller's thread, and returns only after the last one has finished; if a callback is slow or blocks, the canceller - a timer thread, a transport thread, an IHostApplicationLifetime shutdown path - stalls. CancelAsync() flips the state immediately and returns a Task that completes when the callbacks are done, so an async caller can await it without holding a thread and without being at the mercy of callback authors. It does not make callbacks asynchronous themselves; they still run inline, but off the caller's critical path. In a host shutdown sequence I use it so that a misbehaving registration cannot eat the shutdown timeout on the main thread.

What does a cancelled operation return, and what is the right behaviour when you are past the point of no return?

It returns nothing: it throws OperationCanceledException and the task ends Canceled, so callers see a clear "did not complete" rather than a partial result masquerading as success. Before an irreversible step - committing a transaction, capturing a payment, sending a message - check the token one last time; after it, ignore the token for the remaining steps that finish the unit of work (writing the outbox record, acknowledging the message) and document that choice. Cancellation must never leave the system inconsistent, and an operation that has already had its side effect must report success, not cancellation, or the caller will retry it. The nuance interviewers look for: cancellation is a request, not a guarantee, and idempotency downstream is what makes retries after cancellation safe.

What are the costs of CancellationToken.Register, and how do you keep them off the hot path?

Each registration allocates a node in the source's callback list, captures the delegate and its closure, and by default captures the ExecutionContext (and, unless you use the overload, the SynchronizationContext) to run the callback on; the source holds all of it until cancellation or until you dispose the registration. On a per-call hot path that is an allocation plus a lock-free list insertion and removal. The mitigations are: check token.CanBeCanceled and skip registration for default tokens, use UnsafeRegister to avoid context capture, pass state through the callback's object parameter instead of a closure, and always dispose the registration in a finally. The BCL itself does exactly this in Task.Delay and socket operations.

How should a BackgroundService handle its stopping token, and what happens if it ignores it?

ExecuteAsync receives the host's stopping token; the loop should await work with that token, catch OperationCanceledException only to exit cleanly, and let the method complete promptly. The host waits HostOptions.ShutdownTimeout (30 s by default since .NET 8, 5 s earlier) for all hosted services to stop; a service that ignores its token is abandoned at that point and in containers the process is then killed, so in-flight work is lost without any finally running. Two practical details: never block on ExecuteAsync synchronously before its first await (it delays startup of every subsequent service), and if the loop does CPU work, poll the token inside it. I also link the stopping token with a per-item timeout so a stuck item cannot extend shutdown indefinitely.

Should a method that receives a cancellation token throw eagerly if it is already cancelled?

Generally yes - ct.ThrowIfCancellationRequested() (or returning Task.FromCanceled from a non-async method) at the start is cheap and avoids starting work nobody wants, and every BCL async method does it. Two caveats: throwing before validating arguments makes the error ordering surprising, so validate arguments first; and inside a ValueTask-returning hot path you may prefer a fast synchronous IsCancellationRequested check that returns a cancelled task without the exception cost. The deeper reason to check early is the retry-storm scenario: when a client gives up and retries, the abandoned requests must exit as close to zero cost as possible, or the retries amplify the load that caused the timeout.

How do you introduce proper cancellation into a large codebase that currently ignores it?

Incrementally, from the edges inward, with the analyzer doing the enforcement: turn on CA2016 (forward the token) and CA1068 (parameter position) as warnings, add an optional CancellationToken ct = default parameter to the leaf I/O methods first so callers compile unchanged, then plumb it up layer by layer with each PR small enough to review. Prioritise by blast radius: request handlers and anything that holds a pooled resource (database, HTTP, message consumer) first, CPU loops last. Add a load test that closes connections mid-request and asserts the connection pool drains, because that is the behaviour that actually changes. Finally, agree a policy on what cancellation means at points of no return, because that is where developers will otherwise make inconsistent choices.

05 · Contexts, ConfigureAwait and deadlocks

Docs: ConfigureAwait FAQ (Toub) · ConfigureAwaitOptions (.NET 8) · SynchronizationContext

Unit 1 said the awaiter decides where a continuation runs and that the first thing it checks is SynchronizationContext.Current. A SynchronizationContext is an abstraction over "a place where code runs": its Post(callback) means "run this there, later". WPF and WinForms install one that posts to the UI message loop; classic ASP.NET installed one that serialised continuations per request and restored HttpContext.Current; Blazor installs one per circuit; console apps, worker services and ASP.NET Core have none. TaskScheduler is the older, TPL-era equivalent for tasks specifically. ConfigureAwait(false) tells the awaiter "do not capture either; resume wherever the completion happens".

The deadlock, mechanically

// WPF button handler, or a classic ASP.NET action, or anything with a single-threaded context:
void Button_Click(object s, EventArgs e)
{
    var text = LoadAsync().Result;      // (1) blocks the UI thread waiting for the task
    label.Text = text;
}

async Task<string> LoadAsync()
{
    var r = await http.GetStringAsync(url);   // (2) captures the UI context, suspends
    return r.Trim();                          // (3) continuation is Post()ed to the UI thread...
}                                             //     ...which is blocked in (1). Forever.

The task cannot complete until its continuation runs; the continuation is queued to the one thread that is blocked waiting for the task to complete. Two independent fixes exist and you should be able to name both: never block (make the caller async all the way up - the right fix), or make the callee not need the context (ConfigureAwait(false) at (2) - a mitigation that works only if every await in the chain uses it, which you cannot guarantee for code you do not own). On ASP.NET Core the same code does not deadlock because there is no context to capture; it "merely" burns a thread, which under load becomes thread-pool starvation (unit 6). So the symptom changed with the platform, the defect did not.

ConfigureAwait(false) is also "viral in the wrong direction": it affects only the method it is written in, so a library must apply it everywhere, and the first await after it that does not use it will happily capture whatever context is now current (usually none, since you are on a pool thread, which is the subtle part: after a ConfigureAwait(false) you are no longer on the context, so SynchronizationContext.Current is null for the rest of the method).

ConfigureAwaitOptions (.NET 8)

// Old: bool. New: flags. ConfigureAwait(false) == ConfigureAwait(ConfigureAwaitOptions.None)
await task.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);  // await never throws; inspect task.Status yourself.
                                                                    // Replaces the try/catch-all around "wait for shutdown".
await task.ConfigureAwait(ConfigureAwaitOptions.ForceYielding);     // always suspend and resume on the pool, even if complete.
                                                                    // Replaces "await Task.Yield()" hacks to get off a caller's thread.
await task.ConfigureAwait(ConfigureAwaitOptions.ContinueOnCapturedContext | ConfigureAwaitOptions.SuppressThrowing);

SuppressThrowing is only allowed on non-generic Task (a Task<T> would have to invent a result), and it is the modern shape for "await this, but a failure here must not abort me" code paths such as draining background work during shutdown. ForceYielding is the tool for "I was called synchronously from something I do not trust and want to guarantee I do not run my expensive work on its thread".

ExecutionContext and AsyncLocal<T> are a different thing

Do not confuse the two contexts. ExecutionContext is ambient state - chiefly AsyncLocal<T> values, which is how Activity.Current (distributed tracing), logging scopes and IHttpContextAccessor work - and it always flows across awaits, regardless of ConfigureAwait. It is captured at the await and restored before the continuation, and flows into child tasks and Task.Run. Writes to an AsyncLocal inside an async method are visible only downstream of that write within the same logical flow, never to the caller after the await returns - a copy-on-write model that surprises people who use it as "thread-local for async". .NET 11 optimises the capture/restore to a no-op when nothing has changed, which is the single largest per-await saving in the runtime-async work.

Interview trap

"ConfigureAwait(false) prevents deadlocks." Half true, and the half that is false is the important half. It prevents the callee from needing the context; it does not stop the caller from blocking, and a single library in the chain without it re-introduces the deadlock. It also does nothing on ASP.NET Core, so a candidate who recommends sprinkling it into a web app "to fix the deadlock" has misdiagnosed the problem (which is blocking). The lead-level answer: eliminate the blocking, use ConfigureAwait(false) in libraries for hygiene and performance, and understand that the two are independent decisions.

Gotcha

ConfigureAwait applies to the await, not to the task, and not to what the method returns: return SomethingAsync().ConfigureAwait(false); does not compile, and await using / await foreach need their own .ConfigureAwait(false) on the disposable or enumerable. Also, Task.Yield().ConfigureAwait(false) does not exist; if you need "get off this thread regardless of context", ConfigureAwaitOptions.ForceYielding on a task or Task.Run are the tools.

Interview Q&A

Explain the classic async deadlock and give both fixes with their trade-offs.

A thread with a single-threaded SynchronizationContext blocks on a task with Result or Wait(); the task's async method awaited something and captured that context, so its continuation is posted to the blocked thread, which never runs it, and the task never completes. Fix one is to stop blocking: make the caller async up to the entry point, which removes the class of bug entirely but can be a large refactor across synchronous interfaces. Fix two is ConfigureAwait(false) in the callee so the continuation runs on a pool thread instead; it is local and cheap but only works if every await beneath the blocking point uses it, including third-party code, so it is a mitigation for libraries rather than a fix for applications. On ASP.NET Core the deadlock disappears because there is no context, but the blocking remains and becomes thread-pool starvation, so I treat the blocking as the defect in both worlds.

Should application code on ASP.NET Core use ConfigureAwait(false)?

It has no behavioural effect there, because ASP.NET Core does not install a SynchronizationContext and the default TaskScheduler is in use, so continuations already run inline on completing threads. Teams decide on readability versus hygiene: omitting it keeps handlers clean, keeping it protects code that later moves into a shared library or is called from a Blazor Server circuit, which does have a context. My policy is: mandatory (CA2007 as error) in library projects, off in ASP.NET Core application projects, and an architectural note explaining why, so nobody cargo-cults it as a deadlock fix. The thing to avoid is a half-applied mix that gives a false sense of safety.

What is the difference between SynchronizationContext and TaskScheduler?

SynchronizationContext is the general, framework-neutral abstraction for "run this delegate in this environment" (Post/Send), used by UI frameworks, classic ASP.NET and Blazor, and it is what await checks first. TaskScheduler is TPL-specific: it schedules Task objects, defaults to the thread pool, and await falls back to it only when it is non-default and no synchronization context exists. TaskScheduler.FromCurrentSynchronizationContext() bridges the two for ContinueWith-era code. In modern code you rarely touch either directly; the exceptions are custom schedulers for concurrency limiting (ConcurrentExclusiveSchedulerPair) and tests that need a deterministic context.

Explain ConfigureAwaitOptions in .NET 8 and a real use for each flag.

It replaces the bool with flags: None is the old false, ContinueOnCapturedContext the old true. SuppressThrowing makes the await complete normally even if the task faulted or was cancelled, so a shutdown routine can await backgroundTask.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing) and then inspect status, instead of a catch-all - it is only valid on non-generic Task. ForceYielding guarantees a suspension even when the task is complete, resuming on the pool, which is how you ensure expensive work does not run on a caller's thread when you are invoked synchronously, replacing the await Task.Yield() idiom that still honours the context. Combining them is allowed, e.g. yield and suppress while draining work in a UI app.

How does ExecutionContext differ from SynchronizationContext, and what does ConfigureAwait(false) do to each?

ExecutionContext is ambient data - AsyncLocal<T> values behind tracing, logging scopes and IHttpContextAccessor - and it flows across every await and into every task and thread-pool work item regardless of ConfigureAwait; it is captured at suspension and restored on resumption. SynchronizationContext is a scheduling target, and ConfigureAwait(false) stops the awaiter from capturing it. So after ConfigureAwait(false) you may be on a different thread but your Activity.Current and logging scope are intact. The way to break ExecutionContext flow deliberately is ExecutionContext.SuppressFlow() or UnsafeQueueUserWorkItem, which is what you want when starting a long-lived background loop that should not inherit a request's trace.

A Blazor Server component calls a service that does not use ConfigureAwait(false). Is that a problem?

Blazor Server installs a per-circuit SynchronizationContext that serialises rendering, so continuations in component code correctly come back onto the circuit's context, and a service without ConfigureAwait(false) will also resume on that context - which costs a hop per await and makes the service's CPU work compete with rendering on the same logical thread, but is not a deadlock unless something blocks. The blocking case is the classic one: a component (or a sync constructor) calling .Result on a service method that awaits without ConfigureAwait(false) deadlocks the circuit. So the guidance is unchanged: services and libraries use ConfigureAwait(false), components never block, and InvokeAsync(StateHasChanged) is the way back onto the context when you deliberately left it.

How would you diagnose a suspected async deadlock in a running process?

Take a dump (dotnet-dump collect) and look at threads with clrstack in dotnet-dump analyze: a blocked thread shows Task.Wait/GetResult frames; then dumpasync lists incomplete async state machines and their continuations, and you look for one whose continuation targets a SynchronizationContext owned by the blocked thread. In Visual Studio the Parallel Stacks window's Tasks view shows the same picture with "waiting on" arrows. Confirm by checking which context type is installed (DispatcherSynchronizationContext, AspNetSynchronizationContext, Blazor's). The fix is always to remove the block; while triaging, note that on ASP.NET Core the same signature presents as starvation, so I check the thread-pool queue counter first to decide which investigation I am in.

Why does await Task.Yield() not reliably move work off a UI thread, and what does?

Task.Yield() forces a suspension but its awaiter honours the current context, so on a UI thread the continuation is posted straight back to the same dispatcher - it yields to other queued messages, which is useful for responsiveness, but the work still runs on the UI thread afterwards. To actually move CPU work off the thread use Task.Run, or in .NET 8 await someTask.ConfigureAwait(ConfigureAwaitOptions.ForceYielding) when you already have a task to await. Note the opposite direction as well: after ConfigureAwait(false) you are on a pool thread and cannot touch UI; you must marshal back with Dispatcher.InvokeAsync or by structuring the method so UI updates precede the un-contexted awaits.

What is the "sync-over-async" pattern, and is there ever a correct way to do it?

Sync-over-async is calling an asynchronous method and blocking on its result to satisfy a synchronous signature; it costs a thread for the duration, risks the context deadlock, wraps exceptions in AggregateException unless you use GetAwaiter().GetResult(), and under load starves the pool. The truly correct way is not to do it: expose an async path, or provide a genuinely synchronous implementation (a sync API over sync I/O), which is what the BCL does rather than blocking on the async version. When forced by a legacy interface you cannot change, isolate it: block with GetAwaiter().GetResult() on a task that was started with Task.Run so the async part runs on a pool thread with no context, document it, and make sure the callee uses ConfigureAwait(false) throughout. The .NET team's own stance is that even that "trick" is a last resort, and .NET 6 added thread-pool blocking detection precisely because it is so common.

What is xUnit's synchronization context and why does it matter for async tests?

xUnit v2 installs an AsyncTestSyncContext/MaxConcurrencySyncContext to limit test parallelism to the configured number of threads and to track async void tests; it means continuations in tests resume on that context, and blocking on a task inside a test can deadlock in exactly the classic way, which is a common "works in the app, hangs in the test" report. xUnit v3 (2025) removed the custom context, running tests on the thread pool, so blocking tests starve rather than deadlock. Either way the guidance is that tests are async Task, never async void, never block, and use TimeProvider (unit 9) rather than real delays. Knowing this explains a whole category of flaky-test tickets.

06 · Thread-pool behaviour and starvation

Docs: The managed thread pool · Debug ThreadPool starvation · Runtime config: threading

Every continuation that is not posted to a UI context runs on the thread pool, so its behaviour is the performance model of an async server. The pool (the managed "portable" thread pool, default on all platforms since .NET 6) keeps a set of worker threads that pull work items from a global FIFO queue and from per-thread local queues (work-stealing: a task queued from a pool thread goes to that thread's local queue, is dequeued LIFO by the owner for cache locality and stolen FIFO by idle threads). Separately there are I/O threads: on Windows, threads bound to an I/O completion port; on Linux, a small number of socket-engine threads doing epoll that hand completions to the worker pool. When an HTTP response arrives, one of those threads runs your continuation - inline, as unit 1 explained - and that is why the async model scales: a handful of threads service thousands of in-flight requests as long as nobody blocks them.

How many threads, and how fast do they grow

The pool starts with MinThreads workers (default: the processor count, which in a container means the CPU limit rounded up) and creates new ones immediately, on demand, up to that number. Above the minimum it becomes deliberately cautious, because more threads than cores usually means more context switching and less throughput: a "gate" thread wakes roughly every 500 ms and, if work items are queued but none have completed since the last check (starvation), injects one more thread; in parallel a hill-climbing controller nudges the count up or down looking for the best measured throughput. The practical consequence: once all your threads are blocked, the pool grows at about one to two threads per second. If 200 requests per second each block a thread for a second, you fall behind by ~198 threads per second and never catch up. That is thread-pool starvation, and the symptoms are unmistakable once you have seen them: latency climbs into seconds while CPU sits near idle, the thread count creeps up linearly on the dashboard, health checks time out, and everything recovers the moment load drops.

// The three ways to starve a pool, in order of how often I find them in code review:

// 1. Sync-over-async in a request path (the thread parks inside Wait/Result until I/O completes).
var user = _users.GetAsync(id).Result;

// 2. Blocking primitives around async work: lock + Wait, Monitor, SemaphoreSlim.Wait(), Thread.Sleep, ManualResetEvent.
lock (_gate) { _cache = _loader.LoadAsync().GetAwaiter().GetResult(); }

// 3. CPU-bound loops or synchronous I/O (File.ReadAllText, HttpClient.Send, Dns.GetHostEntry) on pool threads.
//    Not "blocking" in the OS sense, but each holds a thread for as long as it runs.
var bytes = File.ReadAllBytes(path);   // in an async handler, under load

Blocking detection (.NET 6+)

Because item 1 is so common, the portable pool since .NET 6 recognises blocking calls made by the runtime's own synchronisation paths - Task.Wait, Task.Result, GetAwaiter().GetResult() on an incomplete task - and immediately injects a replacement thread rather than waiting for the gate thread. It softens the cliff for case 1 and does nothing for cases 2 and 3 (a SemaphoreSlim.Wait, a lock or a synchronous file read look like ordinary running code to the pool). It is a safety net, not a licence.

What changed recently

.NET 6 made the managed pool the default and added blocking detection; .NET 7 moved Windows I/O completion handling into the managed pool as well; .NET 8 and 9 improved the injection heuristics and container CPU-limit awareness (the minimum now tracks fractional CPU limits rounded up); .NET 9 exposed pool metrics through the System.Runtime Meter so they arrive in OpenTelemetry without dotnet-counters. .NET 11's runtime async changes what a continuation costs, not where it runs: the pool model is unchanged.

Interview trap

"Just increase MinThreads." As the whole answer it fails the interview; as the first sentence of an incident plan followed by "then find the blocking with a dump and remove it" it passes with distinction. Interviewers want to hear that more threads means more memory (1 MB stack reservation each), more context switching and a later, bigger cliff, and that the fix is to stop holding threads across I/O. Bonus: know that the default is per-core, so a 2-CPU container has a minimum of 2 and starves far faster than your 16-core laptop.

Gotcha

Continuations run inline on I/O threads. A CPU-heavy continuation after await socket.ReceiveAsync(...) runs on the thread that dequeued the completion; on Linux that can be one of the few socket-engine threads, and hogging it delays every other socket's completions. If a continuation does real CPU work, hand it off (Task.Run, a channel consumer) rather than running it in place. This is also why TaskCompletionSource without RunContinuationsAsynchronously can run arbitrary user code inside your SetResult call, on your thread, under your locks.

Interview Q&A

Explain thread-pool starvation: the mechanism, the symptoms and the fix.

The pool creates threads freely up to its minimum (processor count) and then, to protect throughput, adds only about one or two per second when it detects that queued work is not progressing. If request handlers block threads - sync-over-async, locks around I/O, synchronous file or network calls - every thread ends up parked, new continuations queue behind them, and the injection rate cannot keep up with the arrival rate. Symptoms: latency in seconds with CPU nearly idle, thread count rising in a straight line, queue length climbing, health checks failing, full recovery when load drops. The fix is to remove the blocking so threads return to the pool in microseconds; raising MinThreads is a mitigation to buy time during an incident, and load shedding at the edge stops the cliff from becoming an outage.

Why does the thread pool inject threads so slowly above the minimum, rather than creating one per queued item?

Because for CPU-bound work more threads than cores reduces throughput - context switches, cache pollution, and each thread reserving a 1 MB stack - and the pool cannot tell from the outside whether a queued item is CPU work or a blocked caller. So it uses a feedback loop: a hill-climbing controller measures completed items per second and adjusts the thread count toward the maximum, plus a starvation check every ~500 ms that adds a thread when nothing has completed. Since .NET 6 it additionally watches for known blocking calls (Task.Wait, Result) and injects immediately for those. The design bet is that well-written async code rarely needs more threads than cores, which is true, and that misbehaving code should degrade rather than fork-bomb the machine.

What does Task.Run do on an ASP.NET Core server, and when is it justified?

It queues the delegate to the same thread pool that serves requests, so it does not add capacity; it takes a request thread's work and moves it to another pool thread with an extra hop and an extra allocation. Wrapping blocking I/O in it does not make anything asynchronous, and wrapping CPU work in it does not make the request faster unless the request awaits several such tasks in parallel, which competes with other requests for the same cores. It is justified for isolating a truly CPU-heavy step so that the caller's context (a Blazor circuit, a gRPC stream reader) is not held, for bounded parallelism of CPU work via Parallel.ForEachAsync, and for the rare sync-over-async bridge to keep the blocking part off a context thread. In a UI app it is the standard way to keep the UI responsive, which is where the reflex comes from.

How do I/O threads differ from worker threads, and why does it matter where a continuation runs?

Worker threads execute queued work items; I/O threads wait on the OS for completions - an I/O completion port on Windows, epoll via a few socket-engine threads on Linux - and then run or dispatch the completion. Since an awaited I/O operation's continuation runs inline on whichever thread signals completion, a CPU-heavy continuation can occupy an I/O thread and delay completions for every other socket that thread serves; on Linux the engine threads are few, so this is a real head-of-line blocking risk. The BCL mitigates by dispatching socket continuations to the worker pool by default, and on Windows since .NET 7 completion handling lives inside the managed pool. The practical rule: keep continuations short, and offload heavy CPU work explicitly instead of doing it in place after an await.

Describe the work-stealing design of the pool and one bug it explains.

Each worker thread has a local deque; a work item queued from a pool thread (a task started inside another task, a continuation) goes to that thread's local queue and is taken LIFO by its owner, which favours cache-hot, just-created work; other threads steal from the far end when their own queues are empty; items from non-pool threads go to a global FIFO queue that all workers share. The bug it explains is unfairness: a thread that keeps generating local work can starve the global queue for a while, which is why a busy producer loop that never awaits can delay unrelated requests, and why TaskCreationOptions.PreferFairness exists. It also explains why a deeply recursive fan-out completes in a depth-first order, not the order you started it, which surprises people reading logs.

A service running in Kubernetes with a 1-CPU limit starves under load that the same code handles fine on a 16-core VM. Why, and what do you change?

The pool's minimum is the processor count, which the runtime reads from the cgroup CPU limit rounded up, so the container starts with one or two worker threads instead of sixteen; any blocking in the request path exhausts that instantly, and above the minimum the pool grows at the same slow rate everywhere. The same blocking code hid behind sixteen threads on the VM. The right change is to find and remove the blocking (a dump under load shows it in minutes); the operational change while that ships is to raise DOTNET_ThreadPool_MinThreads in the deployment, keep it modest (a few dozen), and add a concurrency limiter so the pod sheds load instead of timing out. I would also revisit the CPU limit itself, since fractional limits combined with per-core minimums are a common source of "works on my machine" capacity surprises.

What is TaskCreationOptions.LongRunning and when is it right?

It is a hint to the default scheduler that the work will run for a long time, and the pool's response is to create a dedicated thread outside the pool instead of borrowing a worker, so a long loop does not consume one of the few pool threads and does not distort the hill-climbing measurements. It is right for a small fixed number of long-lived loops: a queue consumer, a scheduler tick, a connection pump. It is wrong when the delegate is async and awaits quickly, because after the first await the continuation runs on the pool anyway and the dedicated thread simply exits; that misuse is common and harmless but reveals a misunderstanding. For those cases a plain Task.Run or a BackgroundService is correct.

How do you monitor for thread-pool problems before customers notice?

Export the runtime metrics - thread count, queue length, completed items, and the newer System.Runtime meter in .NET 9 so they arrive through OpenTelemetry - and alert on queue length being non-zero for more than a few seconds or on thread count exceeding, say, four times the core count, because both mean work is waiting for threads. Correlate with request latency and CPU: high latency with low CPU is the starvation signature, high latency with high CPU is capacity. Add a synthetic health endpoint that does a trivial await Task.Yield() and measures scheduling delay; it degrades early. And in CI, a load test that closes connections and blocks nothing should show a flat thread count; a rising one is a regression to investigate before release.

What is the relationship between async and the number of concurrent requests a server can handle?

With synchronous handlers, concurrency is bounded by threads: each request holds one for its entire duration including every I/O wait, so capacity is roughly threads divided by request time, and threads are expensive and slow to add. With asynchronous handlers a request holds a thread only while executing CPU work, so capacity is bounded by CPU, memory for the parked state machines (a few hundred bytes each), and downstream limits like connection pools, rather than by thread count. The result is not that a single request is faster - it is not - but that latency stays flat as concurrency rises until you hit a real resource limit, and that a slow dependency costs memory instead of threads. That is the sentence to say in an architecture interview: async converts a thread bottleneck into a memory cost you can measure.

What is the SynchronizationContext-free design of ASP.NET Core buying us, and what did it cost?

Classic ASP.NET's context serialised continuations per request and restored HttpContext.Current, which cost a queue hop per await, made deadlocks trivial to write, and made the framework's own code need ConfigureAwait(false) everywhere. ASP.NET Core dropped the context: continuations run inline on pool threads, HttpContext is passed explicitly or via IHttpContextAccessor (an AsyncLocal, flowing with the ExecutionContext), and the deadlock disappears. The cost is that nothing protects you from parallel access to non-thread-safe per-request objects: two continuations of the same request can run truly in parallel if you start them in parallel, so HttpContext, DbContext and the response stream are not safe to use from concurrent tasks within one request. Interviewers often probe exactly that: "is HttpContext thread-safe?" - no, and the framework tells you so with an InvalidOperationException when it can detect it.

07 · IAsyncEnumerable<T> and streaming

Docs: await foreach · System.Linq.AsyncEnumerable (.NET 10) · Breaking change: System.Linq.AsyncEnumerable in .NET 10

A Task<List<T>> answers "give me everything, when it is all ready"; an IAsyncEnumerable<T> (C# 8 / .NET Core 3.0, 2019) answers "give me the next one, when it is ready". It is the asynchronous twin of IEnumerable<T>: GetAsyncEnumerator(CancellationToken) returns an enumerator with ValueTask<bool> MoveNextAsync(), T Current and ValueTask DisposeAsync(); the compiler consumes it with await foreach and produces it with async iterators (async IAsyncEnumerable<T> plus yield return). Like its synchronous twin it is lazy and pull-based: nothing runs until the consumer asks for the first element, the producer runs only as far as the next yield, and the consumer's speed is the backpressure. That single property is why it fits paging a database, tailing a log, reading messages from a queue, or server-streaming over gRPC and SSE - and why it is the wrong tool when the producer must run ahead of the consumer, which is what Channel<T> (unit 8) is for.

// Producer: page through an API without holding every page in memory. Cancellation flows in via the attribute.
public async IAsyncEnumerable<Order> GetOrdersAsync(
    DateOnly since, [EnumeratorCancellation] CancellationToken ct = default)
{
    string? cursor = null;

Cancellation and disposal, precisely

Two tokens can reach an async iterator: the one the producer was given as an ordinary parameter, and the one the consumer passes via WithCancellation (which becomes the argument to GetAsyncEnumerator). [EnumeratorCancellation] on the parameter tells the compiler to link them: if both are cancellable, the iterator sees a linked token; if only one is, it sees that one. Forgetting the attribute means WithCancellation silently does nothing (analyzer CS8425 warns). Disposal: breaking out of await foreach, or an exception, calls DisposeAsync(), which runs the iterator's finally blocks - so await using resources inside the iterator are released even when the consumer stops early. An exception inside the iterator surfaces from the consumer's MoveNextAsync, i.e. at the await foreach, on the iteration that triggered it.

Interview Q&A

When would you return IAsyncEnumerable<T> instead of Task<IReadOnlyList<T>>, and when not?

Return a stream when the total is large or unbounded, when the consumer benefits from the first items early (a UI list, a log tail, an LLM token stream over SSE), when memory for the whole set is a concern, or when the source is naturally incremental like a paged API, a queue, or a database cursor. Return a materialised list when the consumer needs the count or random access, when the result is small, when it will be cached or serialised as a unit, when the producer holds a scarce resource for the duration of enumeration (a database connection under a slow consumer), or when the API is crossing a lifetime boundary such as a DI scope. The lead-level nuance: a stream makes the consumer's speed and lifetime part of your contract, which is a coupling you should choose deliberately.

Explain how cancellation reaches an async iterator and what [EnumeratorCancellation] does.

The interface method is GetAsyncEnumerator(CancellationToken), and await foreach ... .WithCancellation(ct) passes the token there; but the iterator method's own parameter is bound when the method is called, before enumeration. [EnumeratorCancellation] tells the compiler to generate code that, at enumeration time, combines the parameter's token with the one given to GetAsyncEnumerator - using whichever is cancellable, or a linked source when both are - so the iterator body sees a token that responds to either. Without the attribute the consumer's token is ignored, which is a silent bug the compiler flags with a warning. I also make the parameter optional with = default, so callers can choose either style, which is the BCL convention.

What is the difference between IAsyncEnumerable<T> and IObservable<T> / a channel?

IAsyncEnumerable is pull-based and sequential: the consumer asks, the producer answers, backpressure is inherent, and a slow consumer slows the producer. IObservable is push-based: the producer emits regardless, and you need operators for buffering, throttling and dropping; it fits event sources with fan-out and time-based composition, which is Rx's domain. Channel<T> sits between: a bounded buffer with async write and read sides, so a producer can run ahead up to capacity and multiple consumers can pull, and ReadAllAsync() exposes it as an async stream. My rule of thumb: pull for I/O sources you control, channel to decouple producer and consumer speeds or to fan in and out, observable when the problem is genuinely about events over time.

What does ASP.NET Core do when an endpoint returns IAsyncEnumerable<T>?

With System.Text.Json (the default since .NET 6) it streams: the response starts with [, each item is serialised and flushed as it arrives, and the array closes when the stream ends, so the client sees the first bytes early and the server never buffers the whole set; the trade-off is that once the first byte is sent you cannot change the status code, so an exception mid-stream produces a truncated body rather than a 500. With Newtonsoft.Json it buffers everything first, defeating the purpose. For browsers, .NET 10 adds TypedResults.ServerSentEvents which frames each item as an SSE event with proper content type and flushing. In all cases the request's CancellationToken should be threaded into the source so a disconnect stops the producer.

What is new for async streams in .NET 10 and why was it a breaking change?

.NET 10 ships System.Linq.AsyncEnumerable in the BCL: the full LINQ operator set for IAsyncEnumerable<T>, written from scratch to follow current API guidelines, with async-delegate overloads that carry a CancellationToken and use the plain operator names rather than the community package's SelectAwait/WhereAwaitWithCancellation spelling. Projects that referenced the community System.Linq.Async package hit ambiguous-call errors when they retarget to .NET 10, so the guidance is to remove the reference or upgrade to Ix.NET 7.0, which defers to the BCL. It is a breaking change of the "two libraries define the same extension methods" kind, not a behavioural one. Practically it means streaming pipelines - Where, Select, GroupBy, ToListAsync - are now idiomatic without a dependency, which will make async streams far more common in codebases.

How do exceptions and disposal behave in an async iterator?

An exception thrown in the iterator body propagates out of the consumer's MoveNextAsync, which is the await foreach line, on the iteration that triggered it, and the enumerator is then disposed, so the iterator's finally blocks and await using declarations run. Breaking out of the loop early or an exception in the consumer also triggers DisposeAsync, which resumes the iterator just to run its finalisation code; note that code after the last yield that is not in a finally does not run in that case. Because everything is lazy, none of this happens if the stream is never enumerated, which is why a method that acquires a resource and then returns an iterator should split into an eager part and a private iterator, exactly like synchronous iterators.

How would you consume an async stream with bounded parallelism per item?

await foreach is sequential by design, so for concurrent processing I feed the stream into Parallel.ForEachAsync, which accepts an IAsyncEnumerable<T> directly and pulls items as workers free up with MaxDegreeOfParallelism and a token; that keeps backpressure intact because pulling only happens when there is capacity. If I need to preserve order in the output, I pair it with a channel or write results indexed. What I avoid is Select(item => ProcessAsync(item)) followed by a WhenAll, because that pulls the whole stream into memory and starts unlimited work, which throws away every property the stream gave us. In .NET 10 the in-box LINQ operators are still sequential per element for the same reason.

Why does MoveNextAsync return ValueTask<bool> and what does that imply for consumers?

Streams yield many items and most steps complete synchronously - the next item is already computed or buffered - so a Task<bool> per element would allocate per item; ValueTask<bool> makes synchronous steps free and the compiler's iterator reuses one completion object for the asynchronous ones. The implication is that the enumerator must be consumed by one caller at a time, each MoveNextAsync awaited exactly once before the next call, which await foreach guarantees and hand-written loops must respect. It also means that an async stream of already-available data is cheap enough to use as an abstraction boundary without worrying about per-item overhead, which is why the BCL uses it for ReadAllAsync on channels.

What is the cost of holding a database connection open across a long await foreach, and how do you design around it?

EF Core's AsAsyncEnumerable() keeps the reader, and therefore the pooled connection, open until enumeration completes or is disposed; if each item triggers slow work - an HTTP call, a per-item write on the same context (which is illegal anyway while a reader is open) - one connection is held for the whole batch, and under concurrency the pool (100 connections by default for SQL Server) is exhausted by streams that are mostly idle. Designs around it: page explicitly with keyset pagination and materialise each page, or read into a bounded channel with a dedicated reader task so the connection is busy only while filling the buffer, or use a separate read-only context per stream with an explicit command timeout. The general principle is that a stream whose producer holds a scarce resource should not be handed to a consumer whose speed you do not control.

How does Task.WhenEach relate to async streams, and what problem did it fix?

Task.WhenEach (.NET 9) takes a set of tasks and returns an IAsyncEnumerable<Task<T>> that yields each task as it completes, so await foreach processes results in completion order and awaiting the yielded task never suspends. Before it, the idiom was a loop calling Task.WhenAny on the remaining set and removing the winner, which is O(n²) in continuation registrations and error-prone, or a TaskCompletionSource array trick from Stephen Toub's blog. It is not a throttle - all tasks are already running - and it is not ordered, but it is the right tool for "render each result as it arrives" and for partial-failure handling where each task's exception is observed individually at its own await.

08 · Coordination: throttling, channels, timers, hand-made promises

Docs: System.Threading.Channels · SemaphoreSlim · TaskCompletionSource<T> · PeriodicTimer

Once code is async the classic synchronisation toolbox half-breaks: lock cannot contain an await (CS1996; the same is true of .NET 9's System.Threading.Lock, which is a struct-based, faster Monitor and still thread-affine), Monitor, Mutex and ReaderWriterLockSlim are owned by a thread and a continuation may resume on a different one, and ManualResetEvent.WaitOne() blocks a pool thread. The async-friendly primitives are the ones whose wait returns a task. The mental model: a lock protects a critical section of CPU work; anything that spans an await is not a critical section but a workflow, and workflows are coordinated with semaphores, channels and promises.

Why RunContinuationsAsynchronously matters

By default, TrySetResult runs the awaiting continuations synchronously, inside the call. If the completer is a transport thread holding a lock, every continuation - arbitrary user code - runs on that thread, under that lock, before TrySetResult returns; if a continuation blocks or re-enters the transport, you have a deadlock or a stall that only shows up under load. TaskCreationOptions.RunContinuationsAsynchronously (.NET 4.6) queues continuations to the pool instead. The BCL uses it everywhere it hands out promises across a trust boundary, and so should you. The same applies to SemaphoreSlim.Release() (its async waiters are always woken asynchronously) and to channels.

Single-flight caching

ConcurrentDictionary.GetOrAdd(key, factory) may invoke the factory concurrently for the same key and keep only one result, so with an async factory you get duplicate work; wrapping the value in Lazy<Task<T>> makes creation atomic and the task shared. The catch: a failed task is cached too, so evict on failure. .NET 9's HybridCache does stampede protection for you and is the modern answer for application caches; the Lazy<Task> trick is what you reach for inside a library.

What changed recently

Channel<T> (.NET Core 3.0) and PeriodicTimer (.NET 6) displaced most hand-rolled queues and timers; Parallel.ForEachAsync (.NET 6) displaced semaphore loops for bounded fan-out; RateLimiter (.NET 7) gave a standard token-bucket/sliding-window API; .NET 8 added TimeProvider overloads to PeriodicTimer, Task.Delay and CancellationTokenSource; .NET 9 added System.Threading.Lock (synchronous only) and HybridCache. There is still no BCL AsyncLock or AsyncReaderWriterLock; SemaphoreSlim and Nito.AsyncEx remain the answer.

Interview trap

Parallel.ForEach(items, async item => await ...). The lambda is async void: Parallel.ForEach returns as soon as every lambda has hit its first await, exceptions crash the process, and there is no bound on in-flight operations. The fix is Parallel.ForEachAsync (.NET 6). Its sibling: list.ForEach(async x => ...) and Select(async x => ...) without a WhenAll. Any Action<T>-typed parameter receiving an async lambda is a bug until proven otherwise.

Gotcha

SemaphoreSlim is not re-entrant and has no owner: any code can Release() it, including one too many times (SemaphoreFullException) or, worse, releasing without having waited because an exception happened between WaitAsync and the try. Put WaitAsync immediately before try, and remember that a semaphore-guarded async method that awaits something which calls back into the same method deadlocks silently - the async equivalent of recursive locking, with no runtime detection.

Interview Q&A

Why can you not await inside a lock, and what do you use instead?

lock compiles to Monitor.Enter/Exit, and a Monitor is owned by the thread that entered it; after an await the continuation may run on a different thread, which could not release the lock, while the original thread might re-enter it elsewhere - so the compiler forbids it outright (CS1996). The same applies to .NET 9's System.Threading.Lock. For exclusion across an await use a SemaphoreSlim(1,1) with WaitAsync and Release in a finally, accepting that it is not re-entrant and has no ownership checks; or restructure so the awaited work happens outside the critical section and only the state update is locked, which is usually the better design because holding an async lock across I/O serialises your throughput on that I/O's latency.

Design a background processing queue for an ASP.NET Core service. What do you choose and why?

A bounded Channel<T> registered as a singleton, with requests writing via WriteAsync(item, ct) and a BackgroundService reading with ReadAllAsync(stoppingToken); bounded with FullMode.Wait so that when the consumer falls behind, requests slow down rather than the process eating memory, and with a metric on queue depth so I see it coming. The consumer creates a DI scope per item, catches and logs per-item failures without dying, and on shutdown the writer is completed so the loop drains what it has within the host's shutdown timeout. If losing items on a crash is unacceptable I do not use an in-memory channel at all but an outbox table or a broker, and the channel becomes at most a local buffer in front of it. The judgement I would voice is exactly that durability question, plus how the caller should behave when the channel is full.

What is TaskCompletionSource for, and what is the one option you always set?

It manufactures a Task whose completion you control - TrySetResult, TrySetException, TrySetCanceled - which is how you adapt callbacks, events, message acknowledgements or any "wait for the other side" into something awaitable. I always pass TaskCreationOptions.RunContinuationsAsynchronously, because otherwise the awaiting continuations execute synchronously inside my TrySet* call, on my thread, possibly under my lock, and a slow or re-entrant awaiter stalls or deadlocks the completer; with the option they are queued to the pool. I also use the Try variants so races between completion, cancellation and timeout do not throw, register the cancellation token to cancel the source and dispose that registration when the task completes, and, if many are created per second, use the non-generic TaskCompletionSource (.NET 5) where no result is needed.

How do you implement bounded concurrency with SemaphoreSlim correctly, and what are the failure modes?

Create it with the desired count, and around each operation do await sem.WaitAsync(ct) immediately followed by try { ... } finally { sem.Release(); }, so an exception anywhere in the body still releases; pass the token to WaitAsync so cancellation does not leave callers queued forever. Failure modes: releasing without acquiring (a throw between wait and try, or double release) which either over-admits or throws SemaphoreFullException; re-entrancy where the body awaits something that needs the same semaphore, which deadlocks with no diagnostic; and forgetting that the semaphore does not order waiters strictly, so fairness is not guaranteed. In new code I reach for Parallel.ForEachAsync for the batch case and keep semaphores for long-lived gates like "at most 4 concurrent calls to this vendor".

How do you cache the result of an async operation so that concurrent callers share one in-flight call?

Store the task, not the value: a ConcurrentDictionary<K, Lazy<Task<V>>> with ExecutionAndPublication guarantees a single factory invocation per key, and everyone awaits the same task, which is safe because a Task can be awaited by any number of consumers. Handle the sharp edges: remove the entry if the task faults so the failure is not cached forever, apply an expiry so a stale success is refreshed, and avoid capturing a request-scoped token in the shared task since the first caller's cancellation would fail everyone (use a token linked to application lifetime and let individual callers use WaitAsync(ct)). In application code on .NET 9+ I use HybridCache.GetOrCreateAsync, which implements this stampede protection plus L1/L2 tiers and serialisation.

Compare PeriodicTimer, System.Timers.Timer, System.Threading.Timer and a Task.Delay loop for scheduled async work.

System.Threading.Timer and System.Timers.Timer fire callbacks on the pool regardless of whether the previous one finished, so async work overlaps unless you guard it, and their callbacks are effectively async void with the exception problems that brings. A while loop with Task.Delay(interval) avoids overlap but drifts by the work duration each tick and needs cancellation plumbing. PeriodicTimer (.NET 6) is the modern shape: await WaitForNextTickAsync(ct) in a loop, one consumer, no overlap, ticks measured from the timer start so it does not drift, and it returns false on disposal so the loop ends cleanly. With the .NET 8 TimeProvider overload it is also testable with a fake clock, which decides it for me.

When would you use a Channel<T> over an IAsyncEnumerable<T> producer, and how do you pick the channel options?

A channel when the producer and consumer must be decoupled in time - the producer runs ahead, several producers fan in, several consumers fan out, or the producer is push-based like a socket or an event handler; an async iterator when a single consumer pulling one item at a time is the natural shape. Options: bounded almost always in a server, with capacity sized to smooth bursts you actually expect rather than "large"; FullMode.Wait for backpressure, DropOldest/DropWrite only for telemetry-like data where loss is acceptable and you record the drop count; SingleReader/SingleWriter set truthfully because they unlock faster lock-free implementations. And always complete the writer on shutdown so ReadAllAsync terminates, propagating an exception via Complete(ex) when the producer died.

What is a cache stampede and how do Lazy<Task> and HybridCache prevent it?

A stampede happens when a hot key expires and many concurrent requests miss at once, each running the expensive load and hammering the backing store, sometimes to the point of collapse. Lazy<Task<T>> in a concurrent dictionary makes the first caller create the task and everyone else await that same instance, so the store sees one load; it is the single-flight pattern. HybridCache (.NET 9) does this internally per key with its GetOrCreateAsync, plus in-memory L1 and distributed L2 tiers and serialisation, so applications should prefer it. The nuance to mention: for very hot keys you also want early refresh (recompute before expiry while serving the stale value), which neither pattern gives you for free and which is where a background refresh loop comes in.

Is Interlocked or volatile still relevant in async code?

Yes, for the state that continuations share without any awaits in between: counters, flags, and lock-free publication of a reference. Continuations of different operations can run truly in parallel on the pool, so a plain _count++ across requests is a data race just as it would be across threads, and Interlocked.Increment or a lock around the few nanoseconds of update is correct. What async changes is not the need for memory safety but the granularity: you protect small synchronous regions with locks or interlocked operations and coordinate the async workflow between them with semaphores and channels. Note that await itself establishes the necessary memory barriers, so a value written before an await is visible after it, on whatever thread resumes.

How do you shut down a service that has async work in flight without losing or duplicating it?

Wire everything to the host's stopping token so new work stops being accepted, complete the channel writers so consumers drain rather than wait, and make each consumer finish the item it is on before observing the token, so items are not half-processed; give the host a realistic ShutdownTimeout (30 s default since .NET 8) and make sure the container's grace period exceeds it. For work that must not be lost, acknowledge messages only after the side effect and make the side effect idempotent, because a crash between the two will replay it; for work that must not be duplicated, use an idempotency key. Then test it: a test that starts the host, enqueues items, calls StopAsync mid-flight and asserts that every item was processed exactly once tells you more than any amount of review.

09 · Exceptions, diagnostics and testing of async code

Docs: TimeProvider (.NET 8) · CA2007 · dotnet-dump · TaskScheduler.UnobservedTaskException

Exceptions: where they go

Inside an async method an exception is caught by the state machine and stored in the task; await rethrows it via ExceptionDispatchInfo, which is why the stack trace shows both the original throw site and the await site joined together. Since .NET Core 2.1 the runtime also rewrites async frames in exception stack traces so they read as MyService.LoadAsync() rather than <LoadAsync>d__3.MoveNext(), which is one reason the "async stack traces are unreadable" complaint is mostly historical. The cases that still bite are the ones where nobody awaits:

  • Unobserved faulted tasks (nobody awaited, nobody read Exception): silently collected since .NET 4.5 (they crashed the process in 4.0), but TaskScheduler.UnobservedTaskException fires from the finalizer thread - subscribe and log it; it is your only signal of leaked failures.
  • async void: no task, so the exception goes to the synchronisation context or crashes the process (unit 2).
  • Task.WhenAll: await gives you one exception, .Exception all of them (unit 2).
  • Cancellation: an OperationCanceledException produces a Canceled task, and ASP.NET Core logs request-aborted cancellations at a lower level than failures (unit 4).

Time is a dependency: TimeProvider (.NET 8)

Tests of retry policies, timeouts, debouncing and periodic jobs used to mean real Task.Delays and flaky assertions. TimeProvider is the abstract clock the BCL now understands: Task.Delay(TimeSpan, TimeProvider), PeriodicTimer(TimeSpan, TimeProvider), CancellationTokenSource(TimeSpan, TimeProvider), Task.WaitAsync(TimeSpan, TimeProvider), TimeProvider.System in production, and FakeTimeProvider from Microsoft.Extensions.TimeProvider.Testing in tests, where Advance(TimeSpan) fires every timer that is due, synchronously, in order. Interview Q&A

How do exceptions travel through async code, and where can they get lost?

An exception inside an async method is captured into its task and rethrown at the caller's await with the original stack preserved via ExceptionDispatchInfo, so a properly awaited chain behaves like synchronous code, and since .NET Core 2.1 the trace reads naturally. They get lost in four places: tasks nobody awaits (silent, only visible through TaskScheduler.UnobservedTaskException at finalisation); async void methods (thrown on the context or crashing the process); WhenAll, where await surfaces only the first of several; and ContinueWith chains whose continuation task itself is never observed. My standard mitigations are CS4014 as an error, a global UnobservedTaskException logger, no async void outside UI handlers, and an ownership rule for background work.

What is TimeProvider and how does it change testing async code?

TimeProvider (.NET 8, also available down-level via the Microsoft.Bcl.TimeProvider package) is the BCL's injectable clock: it gives the current time, a timestamp, a time zone, and - crucially - creates timers, and the BCL's own time-based APIs accept it: Task.Delay, PeriodicTimer, CancellationTokenSource timeouts, Task.WaitAsync. In production you inject TimeProvider.System; in tests FakeTimeProvider lets you call Advance and every due delay, timer and timeout fires deterministically and synchronously. That turns retry, backoff, debounce, expiry and scheduling tests from slow and flaky into fast and exact, and it removes a whole category of "sleep and hope" tests. The design note: pass it through constructors like any dependency and never call DateTime.UtcNow or parameterless Task.Delay in code you want to test.

Explain what dumpasync shows and when you would reach for it over a thread dump.

A parked async request is not on any thread, so clrstack shows idle pool threads and nothing about the thousands of in-flight operations; dumpasync in dotnet-dump analyze walks the heap for async state machine objects and prints each with its method, its state field (which await it is suspended at) and, with --stacks, the chain of continuations - effectively the logical call stack of an operation that is waiting. I reach for it when requests hang without CPU or thread-pool symptoms: it tells me whether they are all parked on the same SemaphoreSlim.WaitAsync, the same TaskCompletionSource that nobody completes, or a downstream socket read. It complements the thread dump for starvation, where threads are the story, and the counters, which say which of the two stories I am in.

Which analyzers do you turn on for async code, and which do you deliberately leave off in a web app?

Errors everywhere: CS4014 (unawaited call), CA2012 (ValueTask misuse), CA2016 (forward the token), and the VSTHRD rules against sync-over-async and async void in server projects. Warnings I escalate once the codebase is clean: CA1849 (sync API where async exists), CA2008 (unspecified scheduler), CA2025 (disposing while a task still uses the object), CS1998 (async without await). Deliberately off in ASP.NET Core application projects: CA2007, because ConfigureAwait(false) has no effect there and enforcing it creates noise that trains people to ignore analyzers; it is an error in library projects. The principle is that the analyzer set encodes the team's async rules so that reviews discuss design, not ceremony.

How do you test that a method honours cancellation?

Give it a token, cancel it while the method is parked on a controllable dependency - a TaskCompletionSource-backed fake, or a FakeTimeProvider delay - and assert that the returned task completes as Canceled (await Assert.ThrowsAnyAsync<OperationCanceledException>) promptly, with a WaitAsync deadline on the assertion so a failure is a test failure rather than a hung suite. Then assert the negative: the dependency observed the cancellation (the fake records the token it was given and whether it was cancelled), so you are testing that the token was forwarded, not just that the method eventually threw. For CPU loops, use a pre-cancelled token and assert the method throws before doing work. What I do not do is real-time sleeps and races; every wait in the test is on something the test controls.

What did xUnit v3 change for async tests?

xUnit v2 ran tests under a custom SynchronizationContext that capped parallelism and tracked async void tests, which meant continuations resumed on that context and blocking inside a test could deadlock exactly like a UI app. v3 (2025) dropped that context - tests run on the thread pool - so blocking now starves instead of deadlocking, async void tests are rejected, and each test gets a TestContext.Current.CancellationToken that is cancelled on timeout or abort, which is the token to pass into the code under test and into WaitAsync deadlines. For teams that is mostly good news, but it can change the behaviour of tests that accidentally depended on the old context, which is worth knowing when a migration produces new flakiness.

A production service intermittently logs "A task was canceled" from HttpClient with no cancellation in your code. What is it?

HttpClient's timeout (100 s default) is implemented with a CancellationTokenSource, so a timeout surfaces as TaskCanceledException; since .NET 5 the inner exception is a TimeoutException, which is how you tell it from a real cancellation, and since .NET 8 the message says so. The fix is to treat it as a timeout: catch TaskCanceledException with an inner TimeoutException (or check that your own token is not cancelled in a filter), set a sensible per-request timeout instead of the 100 s default, and look at why the dependency is slow. I would also check whether the request token is HttpContext.RequestAborted, in which case some of those logs are clients disconnecting and should be logged at debug level rather than paged on.

How do you get useful stack traces and profiles from async-heavy services?

Exception traces are already good: the runtime rewrites state-machine frames to method names and ExceptionDispatchInfo stitches the throw site to the await site. Live traces - profilers, dotnet-stack, new StackTrace() - show only the current synchronous segment plus builder frames, which is where .NET 11's runtime async helps by removing the builder layering. For causality across awaits I rely on Activity/OpenTelemetry spans, which flow through AsyncLocal and give a per-request timeline that no stack trace can, and on dotnet-trace with the TPL provider for scheduling delays. For hangs, dumpasync. The habit I coach is to stop expecting a single stack to explain an async request and to instrument the boundaries instead.

When is it acceptable to catch and swallow OperationCanceledException?

At the boundary that owns the cancellation and knows nothing else needs to run: a request pipeline mapping a client disconnect to a 499-style response, a BackgroundService loop exiting on the stopping token, a UI command the user cancelled. Never in the middle of a chain, because swallowing it there turns "stopped early" into "succeeded with partial state" for every caller above; rethrow, or let it propagate. When catching it at the boundary, distinguish the causes with an exception filter on your own token versus the request's, log at debug for client-initiated cancellations and at warning or error for timeouts you imposed, because only the latter is a signal about your system's health.

What would you look at first, second and third if a service's p99 latency doubled after a deploy with no change in traffic?

First, thread-pool counters and CPU: rising queue length with idle CPU means new blocking (a synchronous call added in a hot path, a library update that blocks), and a dump under load names it in minutes. Second, GC and allocation rate: an async change that captures large closures or drops a ValueTask fast path can double gen0 collections, which shows in dotnet-counters as gen-0-gc-count and in dotnet-trace as allocation hot spots. Third, the dependency traces: a missing ConfigureAwait is never the answer on ASP.NET Core, but a missing cancellation forward or a new sequential await where calls used to be concurrent (someone "simplified" a WhenAll into a loop) will show as serialised spans in the trace. The order is deliberate: pool, memory, then call graph, because that is the order of how often each has been the cause in my experience.

10 · Runtime async (.NET 11) and what is next

Docs: What's new in the .NET 11 runtime: Runtime Async · runtime-async design spec (dotnet/runtime) · .NET 11 Preview 7 announcement

Everything in units 1-9 assumed the C# 5 design: the compiler turns an async method into a state machine because the CLR has no way to suspend a method mid-execution. Runtime async, the headline runtime feature of .NET 11 (Preview 7 as of 11 August 2026; two release candidates planned for September and October; GA planned for 10 November 2026 as an STS release), removes that assumption. The compiler now emits the method body almost as you wrote it, flagged with [MethodImpl(MethodImplOptions.Async)], and each await becomes a call to a runtime intrinsic (AsyncHelpers.Await(task) or AwaitAwaiter/UnsafeAwaitAwaiter for custom awaitables). The JIT understands those calls as suspension points: on an incomplete await it captures the live locals into a continuation object, unwinds, and later resumes the method from that point - the "state machine" is now a runtime-managed frame, not a compiler-generated class. Status matters here: it is a preview feature in .NET 11, opt-in per project, but the .NET runtime libraries themselves are already compiled with it, so every application on .NET 11 exercises it through the BCL whether or not it opts in.

How to think about it at lead level

Nothing in the programming model changes: Task is still the promise, cancellation is still cooperative, ConfigureAwait still means the same thing, deadlocks and starvation are still your problem. What changes is the cost model and the observability: fewer and smaller allocations per suspension, no builder frames in profiles, breakpoints and stepping that stay inside your code, and a JIT that can optimise across awaits (tail-merged suspension points, tail-await, factory folding). The migration risk is low precisely because the semantics are pinned to the existing ones and the two modes interoperate through ordinary tasks; the risks that do exist are the edges - custom async method builders and awaitables (pooling builders keep the old path by design), code that reflects over state-machine types (some logging and mocking libraries did), and anything that relied on the exact allocation profile. The honest interview line: "I would enable it in a service with good benchmarks and profiler coverage during the RC window, measure throughput and gen0 rate, and keep the opt-out property ready; I would not enable it in a library I ship to others until GA."

The history, so the timeline is precise

  • .NET 9 (2024): internal experiment (dotnet/runtime #94620) proving the JIT could do it.
  • .NET 10 (Nov 2025): shipped as an experimental feature: <EnablePreviewFeatures> + <Features>runtime-async=on</Features> + DOTNET_RuntimeAsync=1; CoreCLR only; the BCL was not compiled with it, so gains were limited to your own code.
  • .NET 11 Preview 1 (Feb 2026): runtime support enabled by default in CoreCLR; Preview 2 removed the environment variables; later previews compiled the runtime libraries with it, added NativeAOT/R2R support, the covariant Task→Task<T> override thunk, debugger support, and (Preview 7, Aug 2026) tiered compilation and tail-await optimisations.
  • .NET 11 GA (planned 10 Nov 2026): still labelled preview for user code; the expectation set publicly is that it becomes the default in a later release once the ecosystem has validated it.
Interview trap

"Runtime async makes async code faster, so ValueTask and ConfigureAwait are obsolete." No. ValueTask is about avoiding the promise allocation on synchronous completion, which runtime async does not remove (it changes the frame allocation on suspension); ConfigureAwait is about where continuations run, which runtime async does not touch. What runtime async does obsolete is the mental image of "the compiler generates a class with MoveNext" as the definition of async - it is now one of two implementations, and the runtime one is the direction of travel.

Gotcha

Only the four Task/ValueTask return shapes go through the runtime path. An async method returning a custom task-like, or one annotated with [AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))], is still compiled as a state machine even with runtime-async=on, so a codebase can end up mixing both; that is supported, but it means profiles will show builder frames for exactly those methods and you should not be surprised by it.

Interview Q&A

What is runtime async in .NET 11, in one paragraph a principal engineer would sign off on?

It moves the implementation of async/await from the C# compiler into the runtime: instead of Roslyn rewriting each async method into a state-machine type with MoveNext, it emits the method almost verbatim, flagged MethodImplOptions.Async, with awaits lowered to AsyncHelpers.Await calls that the JIT treats as suspension points, capturing live locals into a runtime continuation and resuming later. The language semantics - task types, exception behaviour, context capture, cancellation - are unchanged and the two implementations interoperate through ordinary tasks. The payoff is lower and smaller allocation on suspension, JIT optimisation across awaits, clean live stack traces, and better debugger stepping. Its status is preview in .NET 11 (GA planned November 2026), opt-in per project with <Features>runtime-async=on</Features>, while the runtime libraries themselves already ship compiled that way.

Why could the compiler-generated state machine not simply be optimised further? What does the runtime know that Roslyn does not?

Roslyn must produce IL for a virtual machine that cannot suspend a frame, so it has to reify every local that crosses an await into a heap-visible field, dispatch through MoveNext with a state switch, and go through builder and awaiter abstractions that the JIT sees as opaque calls; it cannot know which locals are actually live at each await after optimisation, cannot reuse continuation storage across methods, and cannot inline across the builder boundary. The JIT, by contrast, sees the real control flow and liveness, can size the continuation to exactly the live set, skip saving unchanged locals, tail-merge suspension points, fold task factories, and, since Preview 7, apply tiered compilation and tail-await optimisations. That is the general argument for moving a language feature down a layer: the layer below has information the layer above must conservatively assume away.

What does adopting runtime async change for an application team, concretely, and what would you check before enabling it?

Source code changes not at all; the build changes by one property, and the binary changes shape: no state-machine types, methods flagged Async, different allocation profile, different live stack traces. Before enabling it I would check three things: dependencies that reflect over or intercept state machines (some mocking, logging-enrichment and AOP libraries), custom awaitables and async method builders (they keep the old path, which is fine but must be understood), and my benchmarks and dashboards so I can see the throughput and gen0 change rather than assume it. I would enable it first in a service with good load tests during the RC window, watch p99 and GC counters, and keep <UseRuntimeAsync>false</UseRuntimeAsync> as the documented rollback. For a shared library I would wait for GA and for the feature to leave preview.

Does runtime async change anything about deadlocks, thread-pool starvation, or ConfigureAwait?

No, and saying so confidently is the point. Deadlocks come from blocking on a task whose continuation needs the blocked thread's context; starvation comes from blocking pool threads; ConfigureAwait controls whether the captured context is used for the continuation. All three are properties of the scheduling model - SynchronizationContext, the thread pool, the awaiter's continuation dispatch - and runtime async preserves that model exactly, including ConfigureAwait overloads on the new helper calls. What it changes is what a suspension costs and what a profiler sees. If anything, cleaner live stacks make starvation and deadlock investigations easier because the blocked frames are no longer buried under builder frames.

Explain the .NET 11 ExecutionContext continuation optimisation and why it matters for both async modes.

Every task continuation historically captured the current ExecutionContext at the await and restored it before running the continuation, even when no AsyncLocal had been touched and the restore was a no-op; that is a small but per-await cost across the whole platform. .NET 11 detects when there is nothing to restore and skips the capture/restore cycle for Task, Task<T>, ValueTask, ValueTask<T> continuations and for the runtime-async path alike. Applications that use AsyncLocal sparingly and libraries that use ConfigureAwait(false) see reduced overhead in hot async paths with no code change. The lead-level point is that it is a platform-wide change to every await, which is why it is worth knowing even if you never opt into runtime async.

What are the restrictions of runtime-async methods, and how do they map to things you already could not do?

Return types are limited to Task, Task<T>, ValueTask, ValueTask<T>; custom task-likes and custom builders stay on the compiler path. Byref locals and byref-like structs cannot be live across a suspension, which is the same rule C# already enforces for ref locals and Span<T> across await, now enforced at the IL level. Suspension inside an exception handler is not allowed at the IL level, so the compiler restructures awaits in catch/finally exactly as it already does today. The method cannot be Synchronized, cannot use localloc or the tail. prefix across suspension for now, and pinning cannot cross a suspension. In practice every restriction corresponds to something that was already a compile error or a nonsense in the old model, which is by design.

What is the migration story between the two modes: can a runtime-async method await a state-machine method and vice versa?

Yes, freely, because the contract between them is the Task/ValueTask object, not the implementation: a state-machine method awaiting a runtime-async method sees an ordinary task returned by a runtime-generated thunk, and a runtime-async method awaiting a state-machine method just calls AsyncHelpers.Await on the returned task. That is what let Microsoft compile the entire BCL with runtime async while every application on .NET 11 still uses state machines by default, and it is why the covariant-override thunk (a derived class returning Task<T> for a base Task method) needed explicit runtime support to keep virtual dispatch working across the calling-convention difference. For a team it means adoption is per project, incremental and reversible, with no flag day.

How would you explain to a skeptical architect why this is not just "another performance knob"?

Because it changes what async is at the runtime level, which unlocks things a knob cannot: the JIT can now reason about suspension as control flow, so future optimisations - continuation reuse, tail-await, inlining across awaits - compound over releases without the language changing; debuggers and profilers get true call stacks; and the CLR gains a primitive that other languages on the platform and future features (structured concurrency, green-thread-like scheduling experiments that were shelved in 2023 in favour of this) can build on. The cost side is also honest: it is a preview, the ecosystem's reflective tooling will need a cycle to adjust, and the gains are per-suspension, so I/O-dominated services will see modest numbers. The recommendation I would make is to treat it like tiered PGO was in .NET 8: adopt during the RC window in one service, measure, then make it the default in the platform template once it leaves preview.

What does C# 15 bring for async, and what does it not?

Nothing directly at the language level: C# 15's features are collection expression arguments, union types, closed hierarchies, extension indexers, labelled break/continue, and the first step of the memory-safety model; the async story in the .NET 11 wave is entirely the runtime's. Roslyn's involvement is the alternate lowering when runtime-async=on is set, which is a compiler feature flag rather than a language version. So the accurate statement in an interview is that async/await syntax has not changed since C# 8's async streams, and that the innovation has moved to the runtime, the libraries (WhenEach, AsyncEnumerable LINQ, TimeProvider) and the analyzers. Knowing that boundary shows you follow the language design process, not just release headlines.

Where do you expect the platform to go after runtime async, and how does that inform decisions you make today?

The likely path is runtime async becoming the default once it leaves preview, with the state-machine lowering kept for custom builders and down-level targets, followed by deeper JIT optimisations that treat await like any other control flow, and possibly runtime-level structured concurrency now that the runtime owns suspension. That informs today's decisions in a conservative direction: write plain Task/ValueTask-returning async methods rather than clever custom builders and awaitables, because those are the shapes that get the new fast path; keep ValueTask for the synchronous-completion case, because that remains a real allocation; avoid libraries that depend on state-machine internals; and invest in benchmarks and profiler-based observability, because the next few releases will change the cost model under your feet and you want to see it rather than guess.

11 · The big Q&A

Everything important that is not a building block: architecture and ecosystem decisions, reliability and security, performance and debugging beyond the pool, tooling, the legacy you will meet in real codebases, and judgement calls. Twenty-two questions, grouped.

Architecture & ecosystem

Should every method in a service be async? Where do you draw the line?

Async belongs on every path that performs or awaits I/O, from the entry point down, because a single blocking call in the middle undoes the scalability of the whole chain and re-introduces the deadlock class in any host with a context. It does not belong on pure computation or in-memory work: an async method that never awaits allocates a state machine, changes exception timing, and lies about its cost. The line I draw is at the boundary of I/O: domain logic is synchronous and testable, application services and repositories are async, and interfaces are designed once as async if any implementation might do I/O, because changing a signature later is the expensive part. The exception I allow is a synchronous fast path on hot interfaces via ValueTask.

How do async and dependency-injection lifetimes interact, and what goes wrong?

Scoped services are tied to the request scope, which is disposed when the request completes, not when every task the request started completes; any task that outlives the request and touches a scoped service (DbContext, a scoped HttpClient handler chain, IHttpContextAccessor) hits ObjectDisposedException or, worse, reads someone else's request. Singleton services must not capture scoped ones, and an async singleton initialisation (a cache warm-up) must be done via a hosted service or a lazy async factory, not in a constructor with .Result. The rule: background work creates its own scope (IServiceScopeFactory.CreateAsyncScope(), .NET 6, so await using works) and receives data, not services, from the request that spawned it.

Where does async fit in a message-driven or event-driven architecture?

The consumer loop is a BackgroundService that awaits the transport (ReceiveAsync, ReadAllAsync), processes each message in its own DI scope with a per-message linked token (shutdown plus a processing timeout), and acknowledges only after the side effect; concurrency is bounded per consumer with Parallel.ForEachAsync or the client's prefetch settings, not unbounded fan-out. Async is what makes a single consumer process handle hundreds of in-flight messages that are mostly waiting on downstream calls. The decisions to make explicitly: ordering (per-key sequential processing needs a partitioned channel, not a global one), idempotency (at-least-once delivery means retries after cancellation), and backpressure (bounded channels between receive and process so a slow downstream slows the receive rather than filling memory).

How does async interact with EF Core's DbContext, and what is the rule you give teams?

DbContext is not thread-safe and does not support concurrent operations: two awaits started in parallel on the same context (Task.WhenAll(db.A.ToListAsync(), db.B.ToListAsync())) throw "a second operation was started on this context", and if the detection misses you get corrupted change tracking. Async on the context is still the right default because query I/O is where a request waits, but the operations must be sequential within one context; for genuine parallelism use separate contexts from a IDbContextFactory. Also pass the token to every EF async call, be aware that streaming with AsAsyncEnumerable holds the connection, and note that some providers (SQLite) make async a thin wrapper over sync, so async there is about API consistency rather than scalability. The one-line rule for teams is: one context, one operation at a time, always with the token.

Reliability & security

How does missing cancellation become a denial-of-service vector?

If a client can start an expensive operation and disconnect, and the server does not observe cancellation, every abandoned request still runs to completion; an attacker - or a retrying client with a short timeout - can generate far more concurrent work than the connection count suggests, exhausting connection pools, CPU or memory while the load balancer sees only fast-failing connections. Cooperative cancellation wired end to end, plus server-side timeouts that are shorter than the client's retry interval, is therefore a security control, not just a nicety. Complement it with rate limiting and concurrency limits at the edge and with per-request cost budgets, and with metrics for "requests cancelled by client" so an anomaly is visible. The point to make in interviews: cancellation is your only mechanism for reclaiming resources from work nobody wants.

What is the right timeout strategy for an async call chain across services?

Deadlines, not per-hop timeouts in isolation: the entry point decides how long the whole operation may take, and each downstream call gets the remaining budget via a linked token with CancelAfter, so a slow first hop does not leave the second hop with a timeout that exceeds what the caller will wait. Every hop's timeout is shorter than its caller's, retries fit inside the budget (and are jittered), and the budget is propagated explicitly in a header when crossing process boundaries (gRPC does this natively with deadlines). Then the cancellation token is what carries the deadline through the code, and OperationCanceledException filters distinguish "budget exceeded" from "client left" for logging. The failure mode this avoids is the retry storm: nested retries with independent timeouts multiply load exactly when the system is slowest.

How do you make async code resilient to partial failure in a fan-out?

Decide per call whether it is required or optional, and structure the fan-out so optional failures are captured rather than propagated: each optional call is wrapped in a method that returns a result-or-error object (or uses ConfigureAwaitOptions.SuppressThrowing in .NET 8 and then inspects status), while required calls are awaited normally so their failure fails the request. Use Task.WhenAll and, in the catch, read whenAll.Exception.InnerExceptions to log every failure, not just the first; or use Task.WhenEach to handle outcomes as they arrive and stop early when a required one fails, cancelling the rest via a linked token. Add a per-call deadline so one slow optional dependency cannot hold the response, and make the degraded response explicit to the client (a flag or missing section) rather than silently partial.

What do AsyncLocal and ExecutionContext mean for security-sensitive ambient state?

Ambient state that flows with the execution context - the current user in IHttpContextAccessor, a tenant id, an Activity - follows the logical async flow correctly, including into Task.Run, which is what makes it usable for authorisation and auditing across awaits. The dangers are the places where flow is suppressed or stale: work queued with UnsafeQueueUserWorkItem or under ExecutionContext.SuppressFlow sees no context, long-lived background loops capture the context of whoever started them (often the first request, so its user or tenant leaks into later work), and pooled objects that cache AsyncLocal values carry them across requests. The mitigation is to pass identity and tenant explicitly into background work and to treat ambient accessors as request-scope only, with a test that asserts background work runs with no ambient identity.

Performance & debugging

Sequential awaits versus concurrent tasks: how do you decide, and what are the hidden costs of concurrency?

Independent I/O calls should be started together and awaited with WhenAll, because sequential awaits add their latencies while concurrent ones take the maximum; a two-call handler that goes from 120 ms to 70 ms is a common easy win. The hidden costs are that concurrent calls multiply load on the downstream and on the connection pool (ten concurrent requests each fanning out to five calls need fifty connections), that they share nothing safely (no shared DbContext, no shared HttpContext writes), that error handling must consider partial completion, and that a fan-out inside a loop becomes unbounded without a throttle. So I make concurrency explicit and bounded, keep the fan-out width small per request, and measure downstream saturation, because the latency win on one request can become a throughput loss under load.

What allocations does a typical async method make, and how do you find out?

On the synchronous path, nothing for Task (cached completed tasks) or ValueTask, and one Task<T> for most result values; on the first suspension, the boxed state machine merged with the task object (one allocation, sized to the hoisted locals), plus any closure the lambda-based awaits capture, plus a cancellation registration if a token was passed to a BCL call, plus an ExecutionContext capture if AsyncLocal values changed. Larger hoisted locals - a big struct, many temporaries across awaits - make the box bigger, which is why splitting a method so the hot path has no awaits helps. To find out: BenchmarkDotNet with [MemoryDiagnoser] for micro, and dotnet-trace or PerfView's allocation sampling (GC/AllocationTick) on the real workload to see whether async boxes even show up, because usually strings and buffers dominate.

A request occasionally takes 30 seconds; most take 50 ms. How do you localise it in an async pipeline?

Distributed tracing first: with Activity flowing through AsyncLocal, each awaited dependency is a span, and the slow trace shows whether the gap is inside a dependency (their problem), between spans (scheduling delay: thread-pool starvation, a semaphore or a lock queue), or in a span that wraps CPU work (a serialisation blow-up, a regex). If the gap is between spans, correlate with thread-pool counters at that timestamp; if the pool was fine, look for a per-key lock or a semaphore with a queue, which dumpasync during the stall will show as many state machines parked on the same WaitAsync. If it is inside a dependency, check whether a timeout should have fired - a 30 s stall often means a missing per-call timeout defaulted to something long, which is a cancellation finding rather than a performance one.

How do you profile CPU in an async service when stacks are fragmented?

Sampling profilers (dotnet-trace, PerfView, dotTrace) still attribute CPU correctly to the method doing the work; what fragments is the caller chain above the last await, which shows as pool infrastructure. So I read profiles bottom-up by method rather than top-down by call tree, and I use the Activity trace to reconstruct which request path led there. .NET 11's runtime async improves the live stacks by removing builder frames, and the async profiler events unify both modes. For allocation profiles the same applies. The habit to build is to instrument boundaries so the profile can be joined with the trace, rather than hoping a single stack will explain a request.

Tooling

What does your ideal async-aware CI and review setup look like?

Analyzers in Directory.Build.props with the async rules as errors (CS4014, CA2012, CA2016, VSTHRD sync-over-async rules) and library-only rules (CA2007) scoped by project type; a banned-API file that forbids .Result, .Wait(), Thread.Sleep and Task.Factory.StartNew in server projects; tests that use TimeProvider and per-test cancellation tokens with a global timeout so a hang fails fast. In CI, a short load test on the main endpoints that asserts flat thread-pool thread counts and no unobserved task exceptions. In review, a checklist: token forwarded, fire-and-forget owned, no async void, concurrency bounded, DbContext not shared across parallel awaits, timeouts explicit. The idea is that humans review design and the tooling catches ceremony.

Which runtime counters and events do you actually watch for async health?

From the System.Runtime counters (or the .NET 9 meter through OpenTelemetry): thread-pool thread count, queue length and completed items per second, gen0 collection rate and allocation rate, and, from ASP.NET Core, current requests and request duration percentiles. Queue length above zero for more than a few seconds and a thread count climbing linearly are the starvation alarms; allocation rate jumps after a deploy point at an async regression; a rising gap between current requests and CPU points at requests parked on something. For deeper cases, the TPL event source shows task scheduling latency, and dumpasync on demand shows what parked requests wait on. I keep it to that handful because dashboards with forty counters do not get looked at.

Legacy & migration

What asynchronous patterns will you meet in older .NET codebases, and how do you bridge each to TAP?

APM (BeginRead/EndRead with IAsyncResult, .NET 1.0) bridges with Task.Factory.FromAsync(BeginX, EndX, state), which is still the correct tool and allocation-light. EAP (DownloadStringAsync plus a Completed event, .NET 2.0) bridges with a TaskCompletionSource whose event handler sets the result and unsubscribes, guarding against the event firing more than once. Callback-style APIs and ContinueWith chains from .NET 4.0 are rewritten as awaits. BackgroundWorker and ThreadPool.QueueUserWorkItem become Task.Run or hosted services. When the whole layer is synchronous, I introduce async at the leaves with new methods rather than blocking wrappers, and I never ship "async over sync" (Task.Run around blocking I/O) as a library API, per the BCL's own guideline.

What is different about async on .NET Framework 4.8 versus modern .NET, for teams still there?

Classic ASP.NET installs AspNetSynchronizationContext, so sync-over-async deadlocks are real and ConfigureAwait(false) in libraries matters; HttpContext.Current depends on that context flowing, so ConfigureAwait(false) in app code loses it. The thread pool is the older native-backed one without blocking detection; ValueTask and IAsyncEnumerable require the System.Threading.Tasks.Extensions and Microsoft.Bcl.AsyncInterfaces packages and C# 8 language support via a newer compiler; IAsyncDisposable likewise. None of WaitAsync, ConfigureAwaitOptions, PeriodicTimer, Parallel.ForEachAsync, TimeProvider (without the Microsoft.Bcl.TimeProvider package), or WhenEach exist. Async stack traces are ugly. The migration advice is to keep async end-to-end discipline identical so the code moves to modern .NET without rework, and to use the polyfill packages so the API shape matches.

A large codebase has .Result in hundreds of places. How do you migrate without a big bang?

Inventory first with an analyzer or a grep, and classify: entry points (controllers, handlers, jobs), library internals, and constructors or property getters. Convert from the top down, one call chain at a time, because making a leaf async and then blocking on it in the middle changes nothing; each PR makes one path async from entry point to leaf and removes the blocks on that path. Keep temporary sync-over-async bridges only at the boundary of not-yet-migrated callers, isolated in one helper so they can be found and removed. Turn the banned-API rule on for new code immediately so the count only goes down, and track it as a metric. Prioritise by traffic and by incident history - the paths that starved the pool go first - and pair the migration with a load test so each PR shows its effect.

Judgement & scenarios

You are incident commander: latency across the service is in seconds, CPU is 20%, and it started after a deploy. Walk me through the first fifteen minutes.

Minute one: confirm the signature with counters - thread-pool queue length and thread count - and if they show starvation, decide whether to roll back immediately (yes, if the deploy is the only change and rollback is cheap) while continuing to diagnose. In parallel, raise DOTNET_ThreadPool_MinThreads on one instance as a mitigation and watch whether latency drops, which both buys time and confirms the diagnosis. Capture a dump from a starving instance before rollback so the evidence survives, and run clrstack -all to find the blocking frames; ninety percent of the time it is a new synchronous call or a .Result in the hot path. Communicate status every five minutes, keep the mitigation until the fix ships, and write the post-mortem action items: the analyzer rule that would have caught it, and the load test that would have shown it.

What do you flag in a code review of async code, in priority order?

First, anything that blocks: .Result, .Wait(), GetAwaiter().GetResult(), Thread.Sleep, synchronous I/O in an async path. Second, lost work or exceptions: unawaited tasks, async void, async lambdas passed to Action parameters, ContinueWith without observation. Third, cancellation: tokens not accepted, not forwarded, or not checked in loops; linked sources not disposed. Fourth, concurrency mistakes: unbounded fan-out, shared DbContext or HttpContext across parallel tasks, lock around awaits. Fifth, cost: ValueTask misuse, unnecessary async on synchronous methods, Task.Run in request paths. I comment on design before ceremony, and I ask for the analyzer rule when the same issue appears twice.

How do you introduce stricter async rules to a team that finds them pedantic?

With an incident, real or reconstructed: the starvation demo from unit 6 in front of the team converts skeptics in ten minutes, because "the service dies at 200 rps with CPU idle" is not pedantry. Then agree a small rule set with reasons attached - block nothing, own every task, forward every token, bound every fan-out - and encode it in analyzers so it is enforced by the build rather than by a reviewer's mood. Roll the rules out as warnings first, fix the existing violations in a couple of focused PRs so nobody inherits a wall of red, then flip to errors. Pair it with a "why" page and with the escape hatch (a suppression with a comment) so the rule is a default, not a dogma, and revisit the set every few months.

A senior engineer proposes wrapping every synchronous legacy call in Task.Run "so the API is async". What do you say?

That it changes the signature without changing the behaviour: the blocking still occupies a pool thread, now a different one, with an extra hop and allocation, and callers will assume scalability that is not there - which is why the .NET team's guidance for libraries is explicitly against async-over-sync. On a server it is strictly worse than an honest synchronous API, which at least tells callers what they are paying for; in a UI app it has a purpose (keeping the UI responsive), which is probably where the intuition comes from. The productive alternative is to make the leaf genuinely asynchronous (most I/O libraries have an async path by now), and where none exists, keep the API synchronous, document it, and have the few callers that need it offload explicitly and with a bounded degree of parallelism.

Design the concurrency of a service that fans out to 20 downstream APIs per request, with a 500 ms SLA.

Start all 20 calls concurrently with one linked token carrying a 450 ms deadline (leaving budget for serialisation), because sequential is impossible under the SLA; bound the per-instance concurrency to each downstream with a semaphore or a rate limiter sized to that downstream's capacity, so a traffic spike degrades gracefully instead of tripping their limits. Classify the calls into required and optional; use Task.WhenEach or per-task wrappers so optional failures and timeouts degrade the response while required ones fail it fast and cancel the rest. Reuse HttpClient through IHttpClientFactory with connection limits raised to match the fan-out, and watch socket and port exhaustion. Cache what is cacheable with stampede protection, and put the whole thing behind a concurrency limiter so the fan-out multiplier (20x) cannot turn a modest request spike into a downstream outage.

Night-before cheat sheet

  1. await is a compiler feature over a runtime library: the method is split at each await, runs synchronously until the first incomplete one, and its continuation runs wherever the completion arrives - captured context if there is one, otherwise inline on the completing thread.
  2. Async is about not holding a thread while waiting; parallelism is a separate decision. Task.Run on a server moves blocking, it does not remove it.
  3. Task is a promise; await rethrows the first exception with its original stack, Task.Exception holds all of them, async void has none and crashes the process. Every task must be awaited or owned.
  4. ValueTask avoids the allocation when an operation completes synchronously; await it exactly once, never concurrently, and use AsTask()/Preserve() when you need more - CA2012 enforces it.
  5. Cancellation is cooperative: accept a token last, forward it always (CA2016), poll it in CPU loops, catch OperationCanceledException (the base type), dispose linked sources, and prefer CancelAsync (.NET 8) from async code.
  6. The deadlock is blocking on a task whose continuation needs the blocked thread's context; the fix is to not block. ConfigureAwait(false) is library hygiene, does nothing on ASP.NET Core, and .NET 8's ConfigureAwaitOptions adds SuppressThrowing and ForceYielding.
  7. The thread pool starts at one thread per core and grows about one to two threads per second after that; blocking in request paths starves it - latency in seconds with idle CPU. Counters first, dump second, remove the blocking third; raising MinThreads only buys time.
  8. IAsyncEnumerable is lazy, sequential and pull-based with inherent backpressure; [EnumeratorCancellation] links the consumer's token; .NET 10 ships LINQ for it in the BCL (System.Linq.AsyncEnumerable) and Server-Sent Events over it; Task.WhenEach (.NET 9) yields tasks in completion order.
  9. Coordinate async workflows with SemaphoreSlim, bounded Channel<T>, Parallel.ForEachAsync, PeriodicTimer and TaskCompletionSource with RunContinuationsAsynchronously; lock and .NET 9's Lock cannot contain an await.
  10. Test time with TimeProvider and FakeTimeProvider (.NET 8), give every awaited assertion a deadline, and diagnose hangs with dumpasync rather than thread stacks.
  11. .NET 11 (Preview 7, GA planned 10 November 2026) ships runtime async: the runtime, not the compiler, suspends and resumes async methods; opt in with <Features>runtime-async=on</Features>, the BCL is already compiled that way, semantics are unchanged, live stack traces and per-suspension cost improve, and ValueTask/ConfigureAwait still mean what they meant.
