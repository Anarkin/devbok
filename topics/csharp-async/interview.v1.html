1Core model: what await really does

asked: oftencritical12 questions · screener → senior

This is the sub-area every interview opens with, at every level: does await block, is a Task a thread, what runs where. Interviewers use it as a fast filter, then push into the details that separate levels: task elision, the synchronous prefix of an async method, and why wrapping I/O in Task.Run is wrong.

At mid level you must explain the "return to caller, resume later" model precisely. At senior level you are expected to reason about which thread resumes, what the cost of an await is, and when to drop the async keyword. At principal level these are verified in one sentence each and the conversation moves on to units 2, 5 and 9.

Official docs: Asynchronous programming with async and await Async in depth TAP specification
screenerWhat does async/await actually do? Does it create a thread?

Answer

No thread is created. async tells the compiler to rewrite the method into a state machine; await marks a point where, if the awaited operation is not yet complete, the method registers a continuation and returns to its caller immediately. When the operation completes, the continuation is scheduled (on the captured context or the thread pool) and the method resumes after the await. For I/O the "waiting" is done by the OS (overlapped I/O / IOCP on Windows, epoll/kqueue on Linux/macOS) with no thread parked. So async is about freeing the current thread while something else finishes, not about parallelism.

Example

public async Task<int> GetLengthAsync(HttpClient http, string url)
{
    Console.WriteLine(Environment.CurrentManagedThreadId); // e.g. 12
    string body = await http.GetStringAsync(url);          // returns Task to caller here if not complete
    Console.WriteLine(Environment.CurrentManagedThreadId); // e.g. 7 (any pool thread in ASP.NET Core)
    return body.Length;
}

Follow-ups

  • What is returned to the caller at the first incomplete await? — An incomplete Task<int> that represents the rest of the method; the caller can await it, compose it, or attach a continuation.
  • Where does the OS-level wait happen for a socket read? — Nowhere in your process' threads: the kernel completes the I/O and signals a completion port / epoll; the runtime then queues the continuation to the thread pool.
  • Is it faster than synchronous code? — A single call is slightly slower (state machine, allocation); throughput under concurrency is much higher because threads are not held during waits.

Common wrong answer

"await starts a background thread that runs the method while the caller continues." This confuses async with Task.Run; it is the answer that makes interviewers go straight to "then why does await Task.Delay not consume a thread?" and ends the interview early.

screenerWhat is the difference between a Task and a Thread?

Answer

A Thread is an OS execution resource: a stack, a scheduler entry, roughly 1 MB of reserved stack on Windows. A Task is a promise: an object that represents an operation that may complete in the future, with a status, a result or exception, and a list of continuations. A Task may be backed by a thread-pool thread (Task.Run), by an I/O completion (Stream.ReadAsync), by a timer (Task.Delay), or by nothing at all (TaskCompletionSource, Task.FromResult). That decoupling is the whole point: many in-flight Tasks can share a handful of threads.

Example

Task cpu   = Task.Run(() => Crunch());            // runs on a pool thread
Task io    = stream.ReadAsync(buffer, ct).AsTask(); // no thread while waiting
Task timer = Task.Delay(1000);                     // timer queue, no thread
var tcs    = new TaskCompletionSource();            // completes when *you* say so
Task manual = tcs.Task;

Follow-ups

  • When would you still create a Thread directly? — Almost never in app code; for a dedicated long-lived loop with a custom stack size, apartment state (STA), or priority. Otherwise Task.Run or TaskCreationOptions.LongRunning.
  • What states can a Task be in? — Created, WaitingForActivation, WaitingToRun, Running, WaitingForChildrenToComplete, RanToCompletion, Canceled, Faulted; the last three are "completed".
  • Is a Task hot or cold? — TAP tasks are hot (already started); new Task(...) creates a cold task and is legacy TPL you should not use.

Common wrong answer

"A Task is a lightweight thread." It is not a unit of execution at all; that misconception leads to sizing "thread pools of tasks" and to Task.Run around I/O.

midWhat happens at an await when the task is already complete versus still running?

Answer

The compiled code first calls GetAwaiter() and checks IsCompleted. If it is already true (a cached result, a synchronous fast path, a buffered read), execution continues synchronously on the same thread with no context switch and, for ValueTask, often no allocation. Only if it is false does the method save its locals into the state machine, register the continuation via OnCompleted/UnsafeOnCompleted, and return. This is why "async all the way" is cheap in the common already-completed case and why the state-machine struct is only boxed on the first real suspension.

Example

// Conceptually what the compiler emits for: int n = await task;
var awaiter = task.GetAwaiter();
if (!awaiter.IsCompleted)
{
    _state = 0; _awaiter = awaiter;
    _builder.AwaitUnsafeOnCompleted(ref awaiter, ref this); // boxes the struct, returns to caller
    return;
}
int n = awaiter.GetResult(); // synchronous continuation, same thread, exceptions rethrown here

Follow-ups

  • Does await on a completed task ever yield? — No; if you need to force a yield use Task.Yield() or ConfigureAwait(ConfigureAwaitOptions.ForceYielding) (.NET 8).
  • Why does this matter for performance? — Hot paths where 90%+ of awaits complete synchronously (buffered streams, caches) pay only a branch; that is the case ValueTask is optimised for.
  • Can a synchronous continuation cause a stack overflow? — In pathological recursion of already-completed awaits, yes; the runtime mitigates with stack-depth checks in Task completion (RunContinuationsAsynchronously is the manual escape hatch).

Common wrong answer

"Every await yields to the caller and resumes on another thread." Candidates who believe this cannot explain why ValueTask exists or why a loop of awaits over cached data allocates nothing.

midWhich thread runs the code after an await?

Answer

By default the awaiter captures SynchronizationContext.Current (or, if null, the current non-default TaskScheduler) and posts the continuation back to it. In a UI app that means the UI thread; in classic ASP.NET the request context; in ASP.NET Core, console apps and worker services there is no SynchronizationContext, so the continuation runs on whichever thread-pool thread the completion arrived on. ConfigureAwait(false) skips the capture, so the continuation runs wherever the task completed. If the task was already complete, the continuation simply runs inline on the current thread.

Example

// WinForms / WPF: continuation marshalled back to the UI thread
private async void Load_Click(object s, EventArgs e)
{
    var data = await _client.GetStringAsync(url);   // captured UI context
    textBox.Text = data;                            // safe: UI thread
}

// Library code: don't care which thread, don't pay for the marshal
public async Task<byte[]> ReadAllAsync(Stream s)
{
    using var ms = new MemoryStream();
    await s.CopyToAsync(ms).ConfigureAwait(false);  // resumes on a pool thread
    return ms.ToArray();
}

Follow-ups

  • What does the ASP.NET Core resume thread have in common with the original? — Nothing guaranteed except the flowed ExecutionContext (AsyncLocal values, security context). [ThreadStatic] state is gone.
  • What about TaskScheduler.Current? — Only captured if it is not the default scheduler, e.g. inside a ConcurrentExclusiveSchedulerPair or a custom scheduler.
  • Does Blazor have a SynchronizationContext? — Blazor Server does (one per circuit, single-threaded like a UI); Blazor WebAssembly runs on a single thread anyway.

Common wrong answer

"It always continues on the same thread it started on." True only when a SynchronizationContext exists; in ASP.NET Core that assumption produces bugs with thread-affine resources (e.g. [ThreadStatic] caches, SQLite connections, COM objects).

screenerI/O-bound versus CPU-bound: when do you use Task.Run, and when is it wrong?

Answer

Use the naturally asynchronous API for I/O (ReadAsync, SendAsync, ExecuteReaderAsync) and never wrap it in Task.Run: that burns a thread-pool thread to block on something the OS could complete without one. Use Task.Run for genuinely CPU-bound work when you must keep a UI thread responsive or want to run several CPU-bound pieces in parallel. In a server (ASP.NET Core) Task.Run for CPU work buys nothing: the request already runs on a pool thread, so you only add a queue hop and a second thread. The rule of thumb is "Task.Run offloads, it does not make anything asynchronous".

Example

// WRONG: fake async, blocks a pool thread for the whole read
public Task<string> ReadAsync(string path) => Task.Run(() => File.ReadAllText(path));

// RIGHT: real async I/O
public Task<string> ReadAsync(string path, CancellationToken ct) => File.ReadAllTextAsync(path, ct);

// RIGHT: CPU-bound offload in a desktop app to keep the UI responsive
var report = await Task.Run(() => BuildReport(rows), ct);

Follow-ups

  • Is there ever a reason to Task.Run in ASP.NET Core? — To parallelise CPU work across cores for one request, or to escape a badly-behaved library that blocks; both are exceptions with a cost you should name (thread-pool pressure, no fairness across requests).
  • How do you expose a sync-only third-party call? — Keep it synchronous and let the caller decide (Task.Run at the UI layer); do not ship "async over sync" wrappers in a library ("do not lie about being async").
  • What about Task.Factory.StartNew with LongRunning? — For a dedicated long loop; it creates a non-pool thread so it does not starve the pool (see unit 5).

Common wrong answer

"Wrap the slow call in Task.Run so it is async." Presenting async-over-sync as a fix is the single most common rejection in this sub-area at mid level and above.

screenerWhy is async void dangerous, and when is it acceptable?

Answer

An async void method has no Task for the caller to observe, so the caller cannot await it, compose it, or catch its exceptions. Exceptions escape to the SynchronizationContext if one exists, or are thrown on the thread pool and crash the process if there is none (ASP.NET Core, console). Tests and callers cannot know when it finished, which produces races and lost work at shutdown. The one legitimate use is event handlers, because event delegates are void by signature, and even there you should wrap the body in try/catch. Analyzers: VSTHRD100, and the compiler-side CS4014 for unobserved calls.

Example

// Acceptable: UI event handler, body guarded
private async void Save_Click(object sender, EventArgs e)
{
    try { await SaveAsync(); }
    catch (Exception ex) { ShowError(ex); }
}

// Not acceptable: a service method
public async void Publish(Message m) { await _bus.SendAsync(m); }   // exception = process crash in a worker

// Fix: return Task
public Task PublishAsync(Message m) => _bus.SendAsync(m);

Follow-ups

  • What happens with Action overloads and async lambdas? — Task.Run(async () => ...) picks the Func<Task> overload, but list.ForEach(async x => ...) or a Parallel.For body becomes async void silently; the loop finishes before the work does.
  • How does an async void exception surface in WPF? — It is posted to the dispatcher and raises Application.DispatcherUnhandledException.
  • How do tests deal with async void? — They cannot await it; xUnit v2 used a custom SynchronizationContext to count outstanding operations, which is a hint of how fragile this is.

Common wrong answer

"async void is fine as long as you catch exceptions inside." Catching solves only the crash; you still cannot await completion, so shutdown, tests and retries are all broken. The answer must include "no handle to observe completion".

seniorShould a method return SomethingAsync() directly or await it? What changes?

Answer

Returning the task directly ("task elision") avoids one state machine and one allocation, and is the right default for thin pass-throughs. Awaiting is required when the method has a using/try/finally/lock-like scope that must stay alive until the operation completes, when it wants to transform the result or catch exceptions, or when argument validation should be thrown lazily into the task. Elision changes three observable things: exceptions thrown synchronously before the call return synchronously (not in the task), the method disappears from async stack traces, and a disposed scope would be released too early. So the rule is: elide for pure delegation, await when you own a scope or the semantics.

Example

// Elision: fine, one less state machine
public Task<User> GetUserAsync(int id) => _repo.FindAsync(id);

// BUG: the connection is disposed before the query finishes
public Task<int> CountAsync()
{
    using var conn = _factory.Open();
    return conn.ExecuteScalarAsync<int>("select count(*) from t"); // returns immediately, using ends
}

// FIX: await keeps the scope alive
public async Task<int> CountAsync()
{
    using var conn = _factory.Open();
    return await conn.ExecuteScalarAsync<int>("select count(*) from t");
}

Follow-ups

  • What about a try/catch that wants to log? — Must await; without it the catch only covers the synchronous prefix.
  • Does elision hurt debugging? — The elided frame is absent from exception stack traces and the debugger's async call stack; acceptable for trivial wrappers, annoying for orchestration methods.
  • Where does the .NET 11 Runtime Async change this? — With runtime-async the per-method overhead shrinks (no compiler state machine, cheaper await), so the performance argument for elision mostly disappears; the scope argument remains.

Common wrong answer

"Always await, it's the same thing" or "always elide, it's faster". Either absolute is rejected; the reviewer wants the using-scope bug named unprompted.

midWhat are the valid return types of an async method, and how do you choose?

Answer

void (event handlers only), Task, Task<T>, ValueTask, ValueTask<T>, IAsyncEnumerable<T> / IAsyncEnumerator<T> for iterators, and since C# 7 any "task-like" type with an [AsyncMethodBuilder]. Default to Task/Task<T>: they are safe to await multiple times, cache, and compose. Use ValueTask<T> only on hot paths where the result is usually available synchronously or where you pool the backing IValueTaskSource. Use IAsyncEnumerable<T> when the natural shape is a lazily produced sequence rather than one value.

  • Why not Task<IEnumerable<T>> instead of IAsyncEnumerable<T>? — The former materialises everything before the first item; the latter streams and can be cancelled per item.
  • Can an interface method return ValueTask and the implementation be async? — Yes; the compiler uses AsyncValueTaskMethodBuilder. The interface choice locks all implementers into ValueTask semantics, so decide deliberately.
  • What is a task-like type? — Any type whose [AsyncMethodBuilder] attribute names a builder with the required shape; used by Unity's UniTask and by PoolingAsyncValueTaskMethodBuilder.

Common wrong answer

"Use ValueTask everywhere because it is faster." It is slower for the truly asynchronous case and unsafe to await twice; that answer signals cargo-culting.

midTask.Run versus Task.Factory.StartNew: what is the difference?

Answer

Task.Run is the modern shortcut: it uses TaskScheduler.Default, TaskCreationOptions.DenyChildAttach, and understands async lambdas, returning an unwrapped Task<T>. Task.Factory.StartNew is the older, more configurable API: it takes a scheduler, creation options and state, but with a Func<Task> lambda it returns Task<Task>, which callers forget to Unwrap(), and by default it uses TaskScheduler.Current, which can silently be a UI or custom scheduler. Use StartNew only when you need LongRunning or a specific scheduler, and always pass the scheduler explicitly (CA2008).

Example

Task<int> a = Task.Run(async () => await ComputeAsync());                 // Task<int>
Task<Task<int>> b = Task.Factory.StartNew(async () => await ComputeAsync()); // wrapped!
Task<int> c = Task.Factory.StartNew(() => ComputeAsync(),
                 CancellationToken.None,
                 TaskCreationOptions.LongRunning,
                 TaskScheduler.Default).Unwrap();

Follow-ups

  • What does DenyChildAttach prevent? — Legacy "attached child tasks" (AttachedToParent) from hooking onto your task and delaying its completion.
  • Why is TaskScheduler.Current a trap? — Inside a task running on a custom scheduler, StartNew without a scheduler inherits it; code that "should" go to the pool runs on the UI or an exclusive scheduler.
  • Is LongRunning honoured for async lambdas? — Only until the first await; after that the continuation runs on the pool, so the dedicated thread is wasted.

Common wrong answer

"They are the same; StartNew is just older." The missing Unwrap and the scheduler default are exactly what the interviewer is checking for.

screenerDoes await block the caller? What does "async all the way" mean?

Answer

await suspends the current method and returns control (and an incomplete Task) to its caller; it never blocks the thread. Whether the caller blocks depends on what the caller does with that Task: if it awaits, it also suspends; if it calls .Result or .Wait(), the thread blocks. "Async all the way" means every layer from the I/O call up to the entry point (controller action, async Main, event handler, BackgroundService.ExecuteAsync) awaits rather than blocks, so no thread is ever parked and no context deadlock can form. Mixing in one blocking call in the middle undoes the benefit for the whole chain below it.

Example

// Entry point awaits: the whole chain is non-blocking
public static async Task Main() => await new App().RunAsync();

// One .Result in the middle: thread held, deadlock risk on a UI/legacy context
public string Load() => LoadAsync().Result;   // don't

Follow-ups

  • Where must the chain terminate? — At a framework that understands Task: ASP.NET Core actions, hosted services, async Main, UI event handlers, test methods returning Task.
  • Does an async method with no await behave asynchronously? — No; it runs entirely synchronously and returns a completed Task (compiler warning CS1998).
  • What is the cost of "async all the way" in call-depth? — One state machine per async frame; negligible next to I/O, and further reduced by Runtime Async in .NET 11.

Common wrong answer

"await blocks the current thread until the task completes, but asynchronously." The word "blocks" here is the red flag; it must be "suspends and returns".

seniorWhat does Task.Yield() do, and when would you use it?

Answer

await Task.Yield() returns an awaiter whose IsCompleted is always false, so the method always suspends and the continuation is posted to the current SynchronizationContext or queued to the thread pool. It is a way to say "let something else run before I continue". Legitimate uses: in UI code, to let the message loop paint before a long synchronous stretch; in a BackgroundService, to make sure ExecuteAsync returns to the host before a CPU-heavy loop begins (otherwise host startup blocks); and in tests to force a real asynchronous path. It is not a way to "give the request thread back" in ASP.NET Core in any meaningful sense: the continuation goes straight back onto the same pool queue.

Example

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    await Task.Yield();                    // return to host before the tight loop
    while (!stoppingToken.IsCancellationRequested)
        ProcessBatchSynchronously();
}

Follow-ups

  • How does it differ from await Task.Delay(0)? — Task.Delay(0) returns a completed task and does not yield; Delay(1) yields but via a timer.
  • What about ConfigureAwait(false) on Task.Yield? — Not available on YieldAwaitable; in .NET 8 use Task.CompletedTask.ConfigureAwait(ConfigureAwaitOptions.ForceYielding) for a yield without context capture.
  • Can Task.Yield fix thread-pool starvation? — No; it re-queues work but does not free any blocked thread.

Common wrong answer

"Task.Yield releases the thread so other requests can be served" as a fix for a CPU-bound loop in a web server. The loop still consumes the pool thread; it only interleaves.

midHow does an async method start executing, and what does that imply for exceptions thrown early?

Answer

An async method runs synchronously on the caller's thread until the first await that is not already complete; only then does it return. Everything before that point, including any exception, happens inside the state machine, so an exception thrown before the first await is not thrown to the caller: it is captured into the returned Task and surfaces when that Task is awaited. A non-async Task-returning method behaves differently: an exception thrown before it creates/returns a Task propagates synchronously. That is the basis of the "eager argument validation" pattern: a non-async public wrapper validates and throws immediately, then calls a private async implementation.

Example

public Task<Order> GetOrderAsync(int id)
{
    if (id <= 0) throw new ArgumentOutOfRangeException(nameof(id)); // thrown at call site
    return GetOrderCoreAsync(id);
}

private async Task<Order> GetOrderCoreAsync(int id)
{
    var row = await _db.FindAsync(id);   // synchronous prefix ends here
    return Map(row);
}

Follow-ups

  • Why does this matter for Task.WhenAll? — With async methods, all tasks are created even if some fail immediately; with a synchronous throw, WhenAll never receives the other tasks and they run unobserved.
  • Does the synchronous prefix block the caller? — Yes; a long synchronous prefix (e.g. building a big request) delays the return of the Task. Hosted services are the classic victim.
  • Is the synchronous prefix run on the captured context? — It runs on the calling thread, whatever that is; context capture only applies to continuations.

Common wrong answer

"An async method starts on a new thread when called." The synchronous prefix is precisely the thing they want you to know exists.

2Deadlocks, ConfigureAwait & SynchronizationContext

asked: oftencritical10 questions · screener → senior

The sync-over-async deadlock is the most-told war story in .NET, and interviewers use it to see whether you can explain a mechanism, not recite a rule. Around it sit the questions about what ConfigureAwait(false) really does, why ASP.NET Core changed the picture, and what the least-bad option is when you truly must block.

Mid level: reproduce the deadlock on a whiteboard and fix it. Senior: explain SynchronizationContext versus TaskScheduler, know the .NET 8 ConfigureAwaitOptions, and argue when blocking is acceptable. Lead/principal: set a codebase policy (library vs app) and defend it.

Official docs: ConfigureAwait FAQ (Stephen Toub) SynchronizationContext ConfigureAwaitOptions (.NET 8)
screenerExplain the classic sync-over-async deadlock step by step.

Answer

On a thread with a single-threaded SynchronizationContext (UI thread, classic ASP.NET request), code calls an async method and blocks on it with .Result or .Wait(). Inside, the async method hits an incomplete await and captures the context, intending to post its continuation back to that same thread. The blocking call now holds that thread. When the I/O completes, the continuation is posted to the context's queue, but the only thread that can run it is blocked waiting for the continuation to finish. Neither side can proceed: a deadlock with no locks involved. Fixes, in order of preference: make the caller async; use ConfigureAwait(false) on every await below the blocking point (only reliable in code you own); or move the blocking call off the context thread.

Example

// WPF button handler
private void Button_Click(object s, RoutedEventArgs e)
{
    var text = LoadAsync().Result;      // 1. UI thread blocks here
    label.Content = text;
}

private async Task<string> LoadAsync()
{
    var r = await _http.GetStringAsync(url); // 2. captures DispatcherSynchronizationContext
    return r.Trim();                          // 3. continuation posted to UI thread -> never runs
}

Follow-ups

  • Why does this not deadlock in a console app? — There is no SynchronizationContext; continuations run on the pool, and the blocked main thread eventually gets its result.
  • Why is ConfigureAwait(false) in the caller alone not enough? — It only affects the await it is attached to; the deadlock is caused by awaits further down the chain that still capture the context.
  • What does xUnit do that surprises people? — xUnit v2 installs its own SynchronizationContext with limited concurrency, so blocking in tests can deadlock where "the same code" works in a console app.

Common wrong answer

"It deadlocks because two threads wait on each other." There is only one thread involved; if you cannot say "the continuation is posted to a thread that is blocked", the interviewer concludes you have memorised the rule, not the mechanism.

screenerWhat does ConfigureAwait(false) do, and when should you use it?

Answer

ConfigureAwait(continueOnCapturedContext: false) tells the awaiter not to capture SynchronizationContext.Current / the current TaskScheduler, so the continuation runs on whatever thread completed the task, typically a pool thread. Benefits: no deadlock when a caller blocks, and no marshalling cost (a Post to the UI queue, or a hop through a context). Use it in library code and any general-purpose code that does not touch context-affine state. Do not use it in UI event handlers, Blazor Server components, or anywhere the code after the await needs the original context. It has no effect on ExecutionContext (AsyncLocal still flows), and it only affects that one await.

Example

public async Task<Document> ParseAsync(Stream s, CancellationToken ct)
{
    var header = await ReadHeaderAsync(s, ct).ConfigureAwait(false);
    var body   = await ReadBodyAsync(s, header, ct).ConfigureAwait(false);
    return new Document(header, body);   // no UI/context state touched: safe to run anywhere
}

Follow-ups

  • Does it help performance in ASP.NET Core? — Marginally: there is no context to capture, so the saving is a null check; the reason libraries still use it is that they may be consumed from UI apps or classic ASP.NET.
  • Does ConfigureAwait(false) guarantee a pool thread? — No; if the task completes synchronously the continuation runs inline on the current thread, context and all.
  • Can you apply it to await foreach / await using? — Yes: await foreach (var x in src.ConfigureAwait(false)) and await using (x.ConfigureAwait(false)) via the extension methods.

Common wrong answer

"ConfigureAwait(false) makes the code run on a background thread" or "makes it faster". Both miss the actual semantics (capture or not capture the context) and lead to the follow-up trap about synchronous completion.

midWhy does ASP.NET Core not need ConfigureAwait(false), and why should libraries still use it?

Answer

ASP.NET Core removed the per-request SynchronizationContext that classic ASP.NET had (AspNetSynchronizationContext), and it runs on the default TaskScheduler, so there is nothing to capture: continuations always go to the thread pool. That is why the framework team stopped using ConfigureAwait(false) in ASP.NET Core app code and why the deadlock cannot occur there. Libraries cannot assume their host, though: the same NuGet package runs inside WPF, MAUI, Blazor Server, classic ASP.NET on .NET Framework, and Unity, so library code keeps ConfigureAwait(false) as a portability and deadlock-safety measure (CA2007 enforces it where you turn it on). The practical policy: app code, off; shared libraries, on.

  • Is it a bug to use ConfigureAwait(false) in an ASP.NET Core controller? — Not a bug, just noise; some teams ban it in app code to keep intent clear.
  • What if the ASP.NET Core app hosts a legacy component that sets a SynchronizationContext? — Then capture matters again; that is why "app code never needs it" is a policy, not a law.
  • Does HttpContext flow across awaits without a context? — Yes, via IHttpContextAccessor backed by AsyncLocal, i.e. ExecutionContext, not SynchronizationContext.

"ASP.NET Core is safe because it uses ConfigureAwait(false) internally." The reason is the absence of a SynchronizationContext, not framework-internal ConfigureAwait calls.

seniorWhat is the difference between SynchronizationContext and TaskScheduler?

Answer

SynchronizationContext is an abstraction over "post this callback to some execution environment" (Post/Send), used by UI frameworks and older ASP.NET to marshal work to their special thread; await captures it first. TaskScheduler is the TPL's abstraction for where Tasks execute; the default schedules onto the thread pool, and you can write custom ones (ConcurrentExclusiveSchedulerPair, a limited-concurrency scheduler) or wrap a context with TaskScheduler.FromCurrentSynchronizationContext(). The awaiter captures the SynchronizationContext if present, else the TaskScheduler if it is not the default. Practically: SynchronizationContext is about the host's thread affinity; TaskScheduler is about Task execution policy, and both are legacy-flavoured compared with plain "run on the pool" in modern services.

Example

// Serialise access to a non-thread-safe resource without locks
var pair = new ConcurrentExclusiveSchedulerPair();
var exclusive = pair.ExclusiveScheduler;
await Task.Factory.StartNew(() => MutateState(), CancellationToken.None,
                            TaskCreationOptions.DenyChildAttach, exclusive);
// Note: continuations inside async work on `exclusive` will capture it (non-default scheduler)

Follow-ups

  • Which one does Task.Run use? — TaskScheduler.Default, always; it ignores the current context.
  • How does ContinueWith pick its scheduler? — TaskScheduler.Current by default, which is a frequent source of "why is my continuation on the UI scheduler" bugs.
  • Is a custom TaskScheduler a good throttling tool? — Rarely; it only limits Task start, not async continuations, so SemaphoreSlim or Parallel.ForEachAsync is usually the right tool.

Common wrong answer

"They are the same thing under different names." The interviewer wants the capture order and the "default scheduler is not captured" detail.

seniorWhat does ConfigureAwaitOptions (.NET 8) add beyond ConfigureAwait(bool)?

Answer

.NET 8 added Task.ConfigureAwait(ConfigureAwaitOptions) with flags: None (like false), ContinueOnCapturedContext (like true), SuppressThrowing, and ForceYielding. SuppressThrowing makes the await complete without throwing even if the task faulted or was cancelled, which is useful for "wait for it, then inspect task.Status" patterns without try/catch; it is only allowed on non-generic Task (a Task<T> would need to invent a result). ForceYielding forces a suspension even if the task is complete, like Task.Yield but with control over context capture. These are mainly framework-author tools, but knowing them shows you follow the platform.

Example

// Wait for a background task to finish during shutdown without exceptions escaping
await _worker.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);
if (_worker.IsFaulted) _log.LogError(_worker.Exception, "worker failed");

// Guarantee we leave the current (e.g. lock-holding) call stack before continuing
await Task.CompletedTask.ConfigureAwait(ConfigureAwaitOptions.ForceYielding);

Follow-ups

  • Does SuppressThrowing mark the exception as observed? — Yes; the exception is considered observed so it will not fire UnobservedTaskException.
  • Is it available on ValueTask? — No, only Task/Task<T> (and SuppressThrowing only on Task).
  • Why not just try { await t; } catch { }? — That works but allocates an exception path and hides the status; the option is cheaper and explicit.

Common wrong answer

"ConfigureAwait only takes a bool." Not disqualifying at mid level, but at senior level it suggests the candidate stopped tracking the platform around .NET 6.

seniorYou genuinely must call async code from a synchronous method. What are the options and their costs?

Answer

Ordered from best to worst. (1) Change the signature: make the caller async; this is almost always possible with some refactoring and is the only real fix. (2) If the sync caller is on a thread with no SynchronizationContext (ASP.NET Core, console) and the async code is short, .GetAwaiter().GetResult() blocks one pool thread without deadlock risk, but costs a thread for the duration and can contribute to starvation. (3) If the caller is on a context thread (UI, legacy ASP.NET), Task.Run(() => WorkAsync()).GetAwaiter().GetResult() pushes the work to the pool so continuations do not need the blocked context: no deadlock, but two threads used and any context-affine state (HttpContext.Current, AsyncLocal ambient scopes) is lost. (4) Microsoft.VisualStudio.Threading's JoinableTaskFactory for UI apps that need re-entrancy. Never .Result on a context thread and never in a library.

Example

// Legacy sync interface you cannot change, called from ASP.NET Core (no context)
public Customer Get(int id) => _svc.GetAsync(id).GetAwaiter().GetResult();

// Same, but the caller might be a UI thread
public Customer Get(int id) => Task.Run(() => _svc.GetAsync(id)).GetAwaiter().GetResult();

Follow-ups

  • What is lost with the Task.Run wrapper? — The ExecutionContext does flow, so AsyncLocal survives; what is lost is the SynchronizationContext-dependent state and the original thread's identity.
  • How would you make this visible in production? — Analyzers (VSTHRD002 / CA2xxx sync waits) plus a counter on the wrapper; treat each remaining call as tech debt with an owner.
  • Why is this worse in ASP.NET Core than it looks? — Under load each blocked pool thread reduces capacity, and the thread pool's injection rate is slow, so a burst turns into a starvation incident (unit 5).

Common wrong answer

"Use .Result, it's fine in .NET Core." Not deadlocking is not the same as fine; missing the starvation cost is the mid/senior discriminator here.

midIs .GetAwaiter().GetResult() better than .Result / .Wait()?

Answer

Both block the thread identically and carry the same deadlock and starvation risks. The difference is exception surfacing: .Result and .Wait() wrap failures in an AggregateException, whereas .GetAwaiter().GetResult() rethrows the original exception with its stack trace preserved, the same way await does. So if you must block, GetAwaiter().GetResult() gives cleaner catch blocks and logs. It is not a fix for anything; it is the least-surprising form of the same bad idea.

Example

try { var x = task.Result; }
catch (AggregateException ae) when (ae.InnerException is HttpRequestException) { }

try { var x = task.GetAwaiter().GetResult(); }
catch (HttpRequestException) { }   // direct

Follow-ups

  • What about Task.WaitAll versus await Task.WhenAll? — WaitAll blocks and throws AggregateException with all faults; await WhenAll suspends and throws the first fault (the rest are on task.Exception).
  • Does GetAwaiter().GetResult() on a ValueTask work? — Only if the ValueTask is already complete; otherwise it is undefined behaviour (CA2012).
  • Does either one spin? — Task.Wait spins briefly before blocking; irrelevant to correctness but shows up in CPU profiles.

Common wrong answer

"GetAwaiter().GetResult() doesn't block / avoids the deadlock." It is exactly as blocking as .Result; only the exception shape differs.

seniorWhy is blocking on a task in ASP.NET Core still dangerous even though it cannot deadlock on a context?

Answer

Because the blocked thread is a thread-pool thread, and the continuation that would unblock it also needs a thread-pool thread. Under load, all pool threads can end up blocked waiting for continuations that are queued behind them; the pool notices starvation and injects new threads only slowly (roughly one or two per second once above the minimum), so latency climbs to seconds and the service appears hung. Since .NET 6 the pool detects blocking on Task.Wait-style calls and injects faster, and .NET 10 moves a blocking worker's local queue items to the global queue to avoid stranding them, but neither makes blocking free. This is the "second deadlock": not a logical deadlock, but a resource one, and it shows up as Kestrel heartbeat warnings and rising threadpool-queue-length.

Example

// 200 concurrent requests, 8 cores: after the first ~8 block, the rest queue.
app.MapGet("/bad", () => _svc.GetAsync().Result);
// Each .Result parks a pool thread until a continuation runs... on a pool thread.
// Symptom: "Heartbeat took longer than 1s ... thread pool starvation" in Kestrel logs.

Follow-ups

  • Why does it work fine in dev? — Concurrency is 1; starvation needs concurrent blocked threads exceeding the pool's ability to inject.
  • How does the .NET 6 blocking detection work? — The pool tracks threads blocked in known Task waits and temporarily raises the injection target; it cannot see blocking in lock, sync I/O or third-party waits.
  • What is the .NET 10 change exactly? — When a worker blocks on a task, its local queue's work items are moved to the global queue so other workers can pick them up at normal priority (dotnet/runtime PR #112796).

Common wrong answer

"No SynchronizationContext means blocking is safe." Safe from one failure mode, exposed to another; the senior answer names thread-pool starvation unprompted.

screenerDoes ConfigureAwait(false) on the first await apply to the whole method?

Answer

No. It applies only to the await it is attached to. After the first await with ConfigureAwait(false) the method is probably on a pool thread with no context, so later awaits have nothing to capture, but that is incidental: if the first await completed synchronously, the method is still on the original context thread and the second, unconfigured await will capture it. Therefore every await in library code needs it, which is exactly what CA2007 checks. The corollary: you cannot "turn it off once at the top".

Example

public async Task WorkAsync()
{
    await _cache.PrimeAsync().ConfigureAwait(false); // may complete synchronously: still on UI thread
    await _http.GetAsync(url);                       // captures UI context after all
}

Follow-ups

  • Is there a method- or assembly-level switch? — No official one; some teams use a source-generated wrapper or ban context-dependent code instead.
  • What about SynchronizationContext.SetSynchronizationContext(null) at the top of a method? — A hack occasionally seen in legacy ASP.NET; it must be restored and is easy to get wrong.

Common wrong answer

"Once you are off the context you stay off, so one is enough." The synchronous-completion case is the trap.

midWhy can't you await inside a lock, and what do you use instead?

Answer

Monitor locks (and the .NET 9 System.Threading.Lock) are thread-affine: the thread that entered must exit. After an await the continuation may run on a different thread, so releasing would throw and the lock would be held indefinitely; the compiler simply forbids it (CS1996). Replace it with SemaphoreSlim(1,1) and await WaitAsync(ct) with release in finally, or restructure so the awaited I/O happens outside the critical section. For read-heavy scenarios there is no built-in async reader-writer lock; use Nito.AsyncEx or design the state to be immutable/atomic.

Example

private readonly SemaphoreSlim _gate = new(1, 1);

public async Task RefreshAsync(CancellationToken ct)
{
    await _gate.WaitAsync(ct);
    try   { _state = await LoadAsync(ct); }
    finally { _gate.Release(); }
}

Follow-ups

  • What if WaitAsync is cancelled? — It throws OperationCanceledException before acquiring, so the finally must not run Release; the pattern above is correct because the try starts after the wait.
  • Is SemaphoreSlim.WaitAsync fair? — Roughly FIFO for async waiters; not guaranteed and not a fairness mechanism across tenants.
  • Can you await inside the new Lock.EnterScope() using block? — The compiler does not stop you with the using form, but it is just as wrong; the lock statement form is the one that errors.

Common wrong answer

"Use Monitor.Enter/Exit manually around the await." That compiles and then throws SynchronizationLockException or leaks the lock when the continuation lands on another thread.

Composition questions (WhenAll, WhenAny, the .NET 9 WhenEach) and exception-propagation questions come up in almost every coding round because they expose whether you understand that a Task stores its exception until observed. screenerHow are exceptions propagated from an async method?

Answer

An exception thrown inside an async method (before or after the first await) is caught by the state machine and stored on the returned Task, whose status becomes Faulted. Nothing is thrown to the caller at call time. When the caller awaits, the awaiter's GetResult rethrows the original exception via ExceptionDispatchInfo, so the stack trace is preserved and you catch the concrete type. If the caller instead uses .Wait()/.Result, the exception is wrapped in AggregateException. If nobody ever observes the task, the exception is "unobserved" and only surfaces through TaskScheduler.UnobservedTaskException when the task is finalised. async void is the exception: it has no Task, so the failure goes to the SynchronizationContext or crashes the process.

Example

async Task<int> ParseAsync(string s) { await Task.Yield(); return int.Parse(s); }

Task<int> t = ParseAsync("x");    // no throw here; t.IsFaulted becomes true later
try { await t; }                   // FormatException, original stack
catch (FormatException) { }
try { _ = t.Result; }              // AggregateException wrapping FormatException
catch (AggregateException) { }

Follow-ups

  • What if the method throws before the first await? — Same: it is captured in the task, because the whole body is inside the state machine's try/catch.
  • How many exceptions can a Task hold? — Several (from attached children or WhenAll); task.Exception is always an AggregateException; await throws the first.
  • Does awaiting a cancelled task throw? — Yes, TaskCanceledException (an OperationCanceledException).

Common wrong answer

"Exceptions from async methods are thrown when the method is called, like normal methods." That misses the whole point of a faulted Task and fails the obvious follow-up about fire-and-forget.

midTask.WhenAll: how do exceptions surface, and how do you get all of them?

Answer

WhenAll returns a task that completes when all inputs complete: it does not fail fast. If one or more inputs fault, the WhenAll task is Faulted and its Exception is an AggregateException containing every input's exception. But awaiting it throws only the first exception, so to see all failures you keep a reference to the WhenAll task and inspect whenAll.Exception.InnerExceptions in the catch, or examine each input task's status afterwards. If no task faulted but some were cancelled, the result is Canceled. Results of Task<T>[] come back as T[] in input order.

Example

var tasks = urls.Select(u => _http.GetStringAsync(u, ct)).ToList();
var all = Task.WhenAll(tasks);
try
{
    string[] bodies = await all;
}
catch (Exception first)
{
    // first == all.Exception.InnerExceptions[0]
    foreach (var ex in all.Exception!.InnerExceptions) _log.LogError(ex, "fetch failed");
    var failedUrls = tasks.Zip(urls).Where(p => p.First.IsFaulted).Select(p => p.Second);
}

Follow-ups

  • How do you get fail-fast behaviour? — Link a CancellationTokenSource, cancel it in each task's catch, or loop WhenAny/WhenEach and cancel the rest on the first failure.
  • What does .NET 9 add to WhenAll? — params ReadOnlySpan<Task> overloads, avoiding the array allocation for small fixed sets.
  • What if the input is a lazily-evaluated LINQ query? — WhenAll materialises it once; but starting tasks inside Select means they start when enumerated, so ToList() first if you need them started before some other step.

Common wrong answer

"Awaiting WhenAll throws an AggregateException with all the errors." It throws the first one; the AggregateException lives on the task. Interviewers hear this daily.

midWhat are the common Task.WhenAny patterns, and what is the classic mistake?

Answer

WhenAny completes when the first input completes (in any state) and returns that task. Patterns: (1) timeout, racing an operation against Task.Delay; (2) hedging, first successful response wins; (3) "process as they complete" by looping WhenAny over a shrinking list. The classic mistakes are forgetting that the losing tasks keep running (and their exceptions go unobserved unless you attach a continuation), and, for the timeout pattern, leaving the Task.Delay timer alive after the operation wins, which is a leak under high volume. Since .NET 6, task.WaitAsync(timeout, ct) replaces the timeout race, and since .NET 9 Task.WhenEach replaces the loop.

Example

// Legacy timeout race (still common in codebases)
using var cts = new CancellationTokenSource();
var delay = Task.Delay(TimeSpan.FromSeconds(5), cts.Token);
var winner = await Task.WhenAny(work, delay);
if (winner == delay) throw new TimeoutException();
cts.Cancel();               // stop the timer; otherwise it lingers for 5s
await work;                 // propagate work's exception properly

// Modern
var result = await work.WaitAsync(TimeSpan.FromSeconds(5), ct);   // .NET 6

Follow-ups

  • Does WaitAsync stop the underlying work? — No; it abandons the wait. The operation continues unless you also cancel its token.
  • Why await work after WhenAny? — WhenAny itself never faults; you must await the winner to surface its exception.
  • What about hedged requests? — Fire the second request after a delay, WhenAny both, cancel the loser; name the cost (double load on the backend, idempotency requirement).

Common wrong answer

"WhenAny cancels the other tasks." Nothing in TAP cancels anything for you; that misconception leaks work and exceptions.

midWhat is Task.WhenEach (.NET 9) and what problem does it solve?

Answer

Task.WhenEach(tasks) returns an IAsyncEnumerable<Task> (or IAsyncEnumerable<Task<T>>) that yields each task as it completes, in completion order. Before it, "process results as they arrive" was written as a loop of WhenAny over a shrinking list, which is O(n²) in continuations registered and easy to get wrong (removing the wrong task, forgetting exceptions). WhenEach registers one continuation per task, is O(n), and composes with await foreach and cancellation via WithCancellation. You still await each yielded task to get its result or exception, so error handling stays per-item.

Example

await foreach (Task<Quote> done in Task.WhenEach(quoteTasks).WithCancellation(ct))
{
    try   { Render(await done); }        // done is already complete: no suspension
    catch (HttpRequestException ex) { RenderError(ex); }
}

Follow-ups

  • What did the pre-.NET 9 O(n) trick look like? — Stephen Toub's "Interleaved" approach: create n TaskCompletionSources and have each input task's continuation complete the next available one.
  • Does WhenEach start the tasks? — No, TAP tasks are already hot; it only observes them.
  • Can you use it for hedging with early exit? — Yes: break out of the loop after the first success and cancel the rest through their token.

Common wrong answer

"WhenEach is just WhenAll that streams results" without mentioning that you await each yielded task; candidates then write code that swallows exceptions.

seniorWhat happens to an exception in a task nobody awaits (unobserved task exceptions)?

Answer

The exception sits on the faulted Task. If the Task is later awaited or its Exception property read, it is "observed". If it is never observed and the Task becomes garbage, its finaliser raises TaskScheduler.UnobservedTaskException on the finaliser thread. Since .NET 4.5 that event no longer crashes the process by default (in .NET 4.0 it did); the failure is silently lost unless you subscribe and log, or set ThrowUnobservedTaskExceptions in config to restore the crash. So fire-and-forget without a continuation means silently lost errors at an unpredictable time. The fix is structural: never drop tasks; route fire-and-forget through a helper that logs, or a queue with a supervised consumer (unit 10).

Example

TaskScheduler.UnobservedTaskException += (s, e) =>
{
    _log.LogError(e.Exception, "unobserved task exception");
    e.SetObserved();            // prevent escalation if ThrowUnobservedTaskExceptions is on
};

// The pattern that produces them:
_ = _svc.SyncAsync();           // discard: exception lost; CS4014 silenced by the discard

Follow-ups

  • When does the event actually fire? — At GC finalisation of the Task object, possibly minutes later, on the finaliser thread; useless for request correlation, which is why you should log with context at the source.
  • Does _ = task; observe the exception? — No; the discard only silences the compiler warning.
  • Is a faulted ValueTask observed the same way? — A ValueTask wrapping a Task behaves like the Task; an IValueTaskSource-backed one has no finaliser and the exception is simply dropped.

Common wrong answer

"Unhandled task exceptions crash the process." They did in .NET 4.0; saying it about modern .NET signals out-of-date knowledge, and it hides the real risk, which is silent loss.

midHow do you implement a timeout for an async operation, and what does the timeout actually do?

Answer

Three layers. (1) Cooperative: CancellationTokenSource.CancelAfter(timeout) and pass the token in; the operation itself stops (best, because resources are released). (2) Abandoning: task.WaitAsync(timeout, ct) (.NET 6) throws TimeoutException to you but the underlying operation keeps running; use it when the API has no token or when you also cancel via a linked token. (3) Built-in: HttpClient.Timeout, database command timeouts; know their exception types (HttpClient throws TaskCanceledException with an inner TimeoutException since .NET 5). Always state which one you are using, because "the request timed out" and "the request was abandoned and is still consuming a connection" are different production behaviours.

Example

public async Task<Report> BuildAsync(CancellationToken ct)
{
    using var timeout = CancellationTokenSource.CreateLinkedTokenSource(ct);
    timeout.CancelAfter(TimeSpan.FromSeconds(10));
    try
    {
        return await _reports.GenerateAsync(timeout.Token);   // cooperative
    }
    catch (OperationCanceledException) when (!ct.IsCancellationRequested)
    {
        throw new TimeoutException("report generation exceeded 10s");
    }
}

Follow-ups

  • How do you tell "timeout" from "caller cancelled" when both are OCE? — Check which token is cancelled (the filter above), or compare ex.CancellationToken.
  • Where does TimeProvider come in? — .NET 8 overloads CancelAfter-style timing, Task.Delay and WaitAsync accept a TimeProvider so tests can fake time.
  • What is the cost of CancelAfter? — One timer per CTS; fine per request, but pool or reuse (TryReset, .NET 6) in tight loops.

Common wrong answer

"Use Task.WhenAny(op, Task.Delay(x))" with no mention that the operation continues and the timer leaks. Acceptable only if the candidate then names both problems.

midCan you await inside catch and finally? How do exception filters help with async code?

Answer

Since C# 6 you can await in catch and finally blocks; the compiler saves the exception, runs the awaited code, and rethrows afterwards (in C# 5 this was a compile error, which is why older code has awkward "capture and await after" patterns). Exception filters (catch (X ex) when (cond)) are the idiomatic way to distinguish cancellation from failure without catching and rethrowing: the filter runs before the stack unwinds, keeps the original stack trace, and avoids the cost of catch/rethrow. The canonical async use is catch (OperationCanceledException) when (ct.IsCancellationRequested) to swallow only expected cancellation.

Example

try
{
    await ProcessAsync(msg, ct);
}
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    // graceful shutdown: expected, don't log as error
}
catch (Exception ex)
{
    await _deadLetter.PublishAsync(msg, ex, CancellationToken.None);   // await in catch
    throw;
}
finally
{
    await _lease.ReleaseAsync();                                       // await in finally
}

Follow-ups

  • Why pass CancellationToken.None in the catch? — The dead-letter publish must complete even during shutdown; using the same token would cancel the cleanup.
  • What happens if the await in finally throws? — The new exception replaces the original, exactly as in synchronous code.
  • Does throw; after an await in catch preserve the stack? — Yes; the compiler uses ExceptionDispatchInfo to rethrow.

Common wrong answer

"You cannot await in a catch block." True in 2012, wrong for a decade; also a hint the candidate has not touched exception filters.

screenerHow do you run two independent async operations concurrently, and what is the pitfall with sequential awaits?

Answer

Start both operations first, then await both: var a = GetAAsync(); var b = GetBAsync(); await Task.WhenAll(a, b);. Writing await GetAAsync(); await GetBAsync(); serialises them, so latency is the sum instead of the max. Starting means calling the method; TAP tasks are hot. The pitfall in the other direction is unbounded concurrency: starting a thousand HTTP calls at once overwhelms connection pools and downstreams, so for collections use Parallel.ForEachAsync with a degree of parallelism or a SemaphoreSlim (unit 8). Use WhenAll rather than awaiting a then b so that a failure in b is observed even if a throws first.

Example

// Sequential: ~400 ms
var user   = await _users.GetAsync(id, ct);      // 200 ms
var orders = await _orders.ListAsync(id, ct);    // 200 ms

// Concurrent: ~200 ms
var userTask   = _users.GetAsync(id, ct);
var ordersTask = _orders.ListAsync(id, ct);
await Task.WhenAll(userTask, ordersTask);
var (u, o) = (userTask.Result, ordersTask.Result);   // safe: both completed

Follow-ups

  • Is .Result acceptable there? — Yes, after WhenAll both tasks are complete, so it does not block; some teams still prefer await for uniformity and to avoid AggregateException on a faulted task.
  • What if both use the same EF Core DbContext? — Not allowed: DbContext is not thread-safe and does not support concurrent operations; you need separate contexts or sequential awaits.
  • How would you cap concurrency over a list? — Parallel.ForEachAsync(items, new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct }, ...).

Common wrong answer

"Wrap each call in Task.Run to make them parallel." They are already concurrent once started; Task.Run adds threads for no benefit.

seniorHow do you add retries and resilience to async calls without making things worse?

Answer

Use a resilience pipeline (Polly v8 via Microsoft.Extensions.Resilience / Microsoft.Extensions.Http.Resilience, .NET 8+) rather than hand-rolled loops, and apply it at the outermost meaningful boundary. The pipeline must be cancellation-aware (propagate the token; a retry loop that ignores cancellation is a shutdown bug), must not retry non-idempotent operations, must use jittered exponential backoff to avoid thundering herds, and should combine retry with a timeout per attempt and a circuit breaker so a dead dependency fails fast instead of holding pool threads. Also decide what to do with OperationCanceledException: never retry it. Measure with the pipeline's built-in metrics so retries are visible as load amplification.

Example

services.AddHttpClient("catalog")
    .AddStandardResilienceHandler(o =>
    {
        o.Retry.MaxRetryAttempts = 3;              // jittered exponential backoff by default
        o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);
        o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(10);
        o.CircuitBreaker.FailureRatio = 0.5;
    });

Follow-ups

  • Which exceptions do you retry? — Transient ones: 5xx, 408, 429 with Retry-After, connection resets; never 4xx business errors or OCE from the caller's token.
  • Where does idempotency come from? — Idempotency keys on writes; retries on POST without them duplicate side effects.
  • How do retries interact with thread-pool health? — Each retry extends the time a request is in flight, raising concurrency; async keeps threads free, but connection pools and memory still grow.

Common wrong answer

"Loop three times with Thread.Sleep or Task.Delay(1000) between attempts." Fixed delay, no jitter, no cancellation, no idempotency: every element the interviewer is fishing for is missing.

seniorWhy are async stack traces readable at all, and what is ExceptionDispatchInfo?

Answer

An exception thrown after an await is thrown on a different thread and stack than the one that started the method, so the physical stack trace would show only MoveNext and thread-pool frames. Two things fix this. ExceptionDispatchInfo.Capture(ex).Throw() is how the awaiter rethrows a stored exception while appending to the original trace instead of resetting it, which is what throw ex; would do. And since .NET Core 2.1 the runtime rewrites async frames in StackTrace.ToString(): it hides the state-machine and builder frames and prints the original method names, so traces read like synchronous call chains. Debuggers reconstruct the logical "async call stack" from continuation links. .NET 11's Runtime Async makes the live stack (profilers, new StackTrace()) cleaner too, dropping from 13 frames to 5 in the docs' three-level example.

Example

// Manual use: rethrow a stored exception with its original trace
ExceptionDispatchInfo edi = null;
try { await op; } catch (Exception e) { edi = ExceptionDispatchInfo.Capture(e); }
await CleanupAsync();
edi?.Throw();   // original stack preserved, cleanup frames appended

Follow-ups

  • Why does throw ex; lose the trace? — It resets the exception's stack trace to the rethrow point; use throw; or EDI.
  • What information is still missing from async traces? — The causality across fire-and-forget boundaries and across ContinueWith; the debugger's Tasks window helps.
  • Does task elision affect traces? — Yes; elided methods are not in the chain because they never had a state machine.

Common wrong answer

"Async stack traces are useless / only show MoveNext." That was .NET Framework-era truth; on modern .NET it signals the candidate has not looked at a trace in years.

4Cancellation

asked: oftencritical9 questions · screener → senior

Cancellation is where "knows the API" and "has run this in production" diverge fastest. Every interviewer asks how it works; the good ones ask what you do when an API does not accept a token, how you distinguish timeout from caller cancellation, and what should happen to a half-finished write when the HTTP client disconnects.

Mid level: cooperative model, CTS lifecycle, the OCE/TCE distinction. Senior: token forwarding discipline, registration callbacks and their threading, request-abort semantics. Principal: cancellation policy across a system (what is cancellable, what is not, how it is observed).

Official docs: Cancellation in managed threads CancellationTokenSource CA2016: Forward the CancellationToken
screenerHow does cancellation work in .NET?

Answer

It is cooperative. A CancellationTokenSource owns the ability to cancel; it hands out a CancellationToken (a struct) that is passed down through every async call. Nothing is ever forcibly stopped: code that receives a token must poll it (IsCancellationRequested / ThrowIfCancellationRequested()), pass it to lower-level APIs that observe it (sockets, timers, database drivers), or register a callback (Register) that aborts the underlying resource. When cancellation is honoured, the operation throws OperationCanceledException and the Task ends in the Canceled state. The design consequences: cancellation is a request, not a guarantee; it can arrive at any time; and an operation that ignores its token is uncancellable no matter what the caller does.

Example

public async Task ExportAsync(Stream output, CancellationToken ct)
{
    await foreach (var row in _repo.StreamRowsAsync(ct).WithCancellation(ct))
    {
        ct.ThrowIfCancellationRequested();            // cheap, cooperative
        await output.WriteAsync(Serialize(row), ct);  // I/O observes the token
    }
}

Follow-ups

  • Why cooperative rather than Thread.Abort? — Abort left shared state corrupt; it is unsupported on .NET Core (throws PlatformNotSupportedException).
  • Is CancellationToken thread-safe? — Yes; it is a readonly struct pointing at the source, and it may be checked from any thread.
  • What does cancelling an already-completed operation do? — Nothing; the token becomes cancelled, but the completed Task keeps its result.

Common wrong answer

"Calling Cancel() stops the task." It requests cancellation; a task that never checks the token runs to completion. Interviewers follow up with "so what does Cancel do to a running CPU loop" and wait.

midWalk through the CancellationTokenSource lifecycle: creation, linking, CancelAfter, disposal.

Answer

Create one CTS per logical operation you might want to cancel. CancelAfter(timeout) arms a timer; CreateLinkedTokenSource(a, b) creates a source that is cancelled when any input is, which is how you combine "caller cancelled" with "my own timeout". Dispose the CTS when the operation ends: it releases the timer and unregisters from linked tokens; forgetting to dispose linked sources on long-lived parent tokens (like ApplicationStopping) is a real memory leak because each linked CTS stays registered on the parent. Cancel() runs registered callbacks synchronously on the calling thread (see q4-5); .NET 8 added CancelAsync() to await callbacks; .NET 6 added TryReset() for pooling.

Example

public async Task<T> RunWithTimeoutAsync<T>(Func<CancellationToken, Task<T>> op,
                                            TimeSpan timeout, CancellationToken caller)
{
    using var cts = CancellationTokenSource.CreateLinkedTokenSource(caller);  // dispose = unlink
    cts.CancelAfter(timeout);
    return await op(cts.Token);
}

Follow-ups

  • What happens if you call Cancel after Dispose? — ObjectDisposedException; tokens obtained earlier keep working for IsCancellationRequested but registering on them throws.
  • Why is a CTS on a hot path expensive? — Each CTS is a class with a timer when CancelAfter is used; per-item CTS in a tight loop shows up in allocation profiles. Pool with TryReset.
  • Does linking flow both ways? — No; cancelling the linked source does not cancel its parents.

Common wrong answer

"You don't need to dispose a CTS." Harmless for a short-lived unlinked CTS without a timer, a leak for linked or timer-armed ones. Reviewers check for using on linked sources.

midOperationCanceledException versus TaskCanceledException: how do you detect cancellation correctly?

Answer

TaskCanceledException derives from OperationCanceledException. ThrowIfCancellationRequested() and most BCL APIs throw OCE; awaiting a Task that ended in the Canceled state throws TCE; HttpClient timeouts throw TCE too. So catch the base type, OperationCanceledException, and then decide why: compare ex.CancellationToken to your token, or use a filter on token.IsCancellationRequested. Treat "cancelled because the caller asked" as normal control flow (log at debug, no alert) and everything else as failure. Do not catch Exception and then test for OCE; put the OCE catch first with a filter.

Example

try
{
    await _client.GetAsync(url, ct);
}
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    return Result.Cancelled;           // caller gave up: not an error
}
catch (OperationCanceledException ex)   // TCE from HttpClient.Timeout, inner TimeoutException in .NET 5+
{
    throw new GatewayTimeoutException(url, ex);
}

Follow-ups

  • How does ASP.NET Core report a cancelled request? — An unhandled OCE from an action becomes a 499-style aborted response in Kestrel logs; there is nobody to send a status to.
  • Should you convert OCE to a custom exception? — Only at boundaries where the meaning changes (timeout → gateway timeout); inside the chain, let OCE propagate so callers can recognise it.
  • What about Task.IsCanceled vs IsFaulted? — A task whose body throws OCE for a token that is cancelled becomes Canceled; OCE for a different token (or unrelated) makes it Faulted. This surprises people.

Common wrong answer

"Catch TaskCanceledException." That misses the OCE thrown by ThrowIfCancellationRequested and most database drivers; cancellation then bubbles up as a 500.

seniorWhat is your token-forwarding discipline, and what do you do when an API does not accept a CancellationToken?

Answer

Discipline: every async method that does I/O or can take noticeable time takes a CancellationToken as its last parameter (default default only on public convenience overloads), forwards it to every awaited call (CA2016 warns when an overload exists and you did not pass it), and never invents CancellationToken.None mid-chain except deliberately for cleanup that must complete. When an API has no token overload, options are: task.WaitAsync(ct) (.NET 6) to stop waiting; a registration that closes or disposes the underlying resource (which usually makes the operation fault); or a documented "this step is not cancellable" with a bounded duration. Be explicit in code review about which of these was chosen; silent abandonment leaks connections.

Example

// Legacy client without token support
public async Task<Data> FetchAsync(CancellationToken ct)
{
    var task = _legacy.FetchAsync();                       // no token
    using var reg = ct.Register(static s => ((LegacyClient)s!).Abort(), _legacy); // best-effort abort
    return await task.WaitAsync(ct);                       // stop waiting even if Abort is ignored
}

Follow-ups

  • Why last parameter and not first? — TAP convention and analyzer expectations; also makes optional-parameter defaults work.
  • Should interface methods declare tokens even if the first implementation ignores them? — Yes; adding it later is a breaking change for implementers.
  • Is WaitAsync without cancelling the work acceptable? — Sometimes (idempotent reads); for writes it can leave a half-done operation you no longer observe, which you must state.

Common wrong answer

"If the API doesn't take a token, there's nothing you can do." Not naming WaitAsync or a registration-based abort is a senior-level miss.

seniorHow do CancellationToken.Register callbacks behave, and what is CancelAsync (.NET 8)?

Answer

Register(callback) returns a CancellationTokenRegistration that must be disposed when the operation finishes, otherwise the delegate (and everything it captures) stays alive as long as the token's source. On Cancel(), callbacks run synchronously on the thread calling Cancel, in reverse registration order, under no lock; if one throws, Cancel throws an AggregateException after running the rest. Because callbacks run inline, a slow or blocking callback stalls the canceller, and a callback that takes a lock can deadlock with the canceller. .NET 8 added CancelAsync(), which returns a Task that completes when all callbacks have finished, so hosts can await cleanup without blocking. Registration flows the ExecutionContext by default; UnsafeRegister does not.

Example

public static Task<T> AsCancellable<T>(this TaskCompletionSource<T> tcs, CancellationToken ct)
{
    if (!ct.CanBeCanceled) return tcs.Task;
    var reg = ct.UnsafeRegister(static (s, token) => ((TaskCompletionSource<T>)s!).TrySetCanceled(token), tcs);
    tcs.Task.ContinueWith(static (_, r) => ((CancellationTokenRegistration)r!).Dispose(), reg,
                          TaskScheduler.Default);   // unregister when done
    return tcs.Task;
}

Follow-ups

  • What if the token is already cancelled when you register? — The callback runs immediately, synchronously, on the registering thread.
  • Why is the registration leak common in servers? — Registering per-request on ApplicationStopping or another process-lifetime token without disposing; memory grows with request count.
  • Does CancellationTokenRegistration.Dispose wait for a running callback? — Yes, it blocks until an in-flight callback finishes (unless called from that callback); DisposeAsync exists for async contexts.

Common wrong answer

"Callbacks run on the thread pool." They run on the cancelling thread; that is why a blocking callback can stall IHostApplicationLifetime.StopApplication.

midIn ASP.NET Core, what is HttpContext.RequestAborted, and what should you link to it?

Answer

RequestAborted is a token that is cancelled when the client disconnects (or Kestrel aborts the connection). Minimal APIs and controllers bind a CancellationToken parameter to it automatically. Link it into reads, queries and outbound calls so abandoned requests stop consuming resources. Do not blindly link it into writes that must be atomic across systems (a payment capture followed by an email): cancelling between steps leaves a partial outcome that the client will never learn about, so either make the operation transactional/idempotent or decouple the commit from the request. Also note that it does not fire for every proxy configuration and that Kestrel only detects disconnects when it tries to read or write.

Example

app.MapGet("/orders/{id}", async (int id, IOrderRepo repo, CancellationToken ct) =>
    await repo.GetAsync(id, ct) is { } o ? Results.Ok(o) : Results.NotFound());   // ct == RequestAborted

app.MapPost("/orders", async (OrderDto dto, IOrderService svc, HttpContext http) =>
{
    // deliberately NOT RequestAborted: the commit must finish once started
    var id = await svc.CreateAsync(dto, CancellationToken.None);
    return Results.Created($"/orders/{id}", null);
});

Follow-ups

  • Which other lifetime tokens exist in a host? — IHostApplicationLifetime.ApplicationStopping / ApplicationStopped and the stoppingToken passed to BackgroundService.ExecuteAsync.
  • Should a background job started from a request use RequestAborted? — No; it outlives the request. Use ApplicationStopping (unit 10).
  • What does EF Core do with a cancelled token mid-transaction? — The command is cancelled at the driver; the transaction is rolled back on dispose. Half-applied multi-transaction workflows are your problem.

Common wrong answer

"Always pass the request token everywhere." The senior answer distinguishes reads (yes) from non-atomic writes (design decision), and says so.

midWhere do you put ThrowIfCancellationRequested in CPU-bound code, and how often?

Answer

CPU-bound loops do not go through the runtime's cancellable I/O paths, so the only way they stop is explicit polling. Check the token at the top of each iteration or each unit of work that takes roughly a millisecond or more; checking per element in a tight inner loop costs a volatile read and a branch, which is usually negligible but measurable in SIMD-style loops, so check per chunk there. Use ThrowIfCancellationRequested() rather than if (IsCancellationRequested) return when you want the Task to end Canceled (so callers can distinguish it); use the early-return form when partial results are the desired outcome. In Parallel.For/Parallel.ForEachAsync, pass the token in ParallelOptions as well.

Example

public static Task<long> ChecksumAsync(byte[] data, CancellationToken ct) => Task.Run(() =>
{
    long sum = 0;
    for (int i = 0; i < data.Length; i += 4096)
    {
        ct.ThrowIfCancellationRequested();                    // once per 4 KB chunk
        var span = data.AsSpan(i, Math.Min(4096, data.Length - i));
        foreach (var b in span) sum += b;
    }
    return sum;
}, ct);

Follow-ups

  • What does the ct passed to Task.Run do? — Only prevents the work from starting if already cancelled; it does not interrupt a running lambda.
  • What is the Task state if the lambda throws OCE with that token? — Canceled, because the token matches; with a different token it would be Faulted.
  • Is there a cost to IsCancellationRequested? — A volatile read of the source's state; if the token has no source (default), it is a null check.

Common wrong answer

"Passing the token to Task.Run cancels the loop." It does not; the loop must poll.

seniorHow do you cancel an operation that is genuinely not cancellable, and what are the risks?

Answer

You cannot cancel it; you can only stop waiting for it or destroy the resource it depends on. The pattern is: register a callback that disposes/closes the resource (socket, connection, process), which makes the pending call fault, and combine with WaitAsync(ct) so the caller returns promptly even if the resource is stubborn. Risks: the resource may be shared (closing a pooled connection affects others), the abandoned operation still consumes memory/threads until it fails, and its eventual exception is unobserved unless you attach a logging continuation. At system level, bound the blast radius: a per-operation resource rather than a shared one, and a metric for "abandoned operations in flight" so a leak is visible.

Example

public async Task<string> RunToolAsync(string exe, CancellationToken ct)
{
    using var p = Process.Start(new ProcessStartInfo(exe) { RedirectStandardOutput = true })!;
    using var reg = ct.Register(static s => { try { ((Process)s!).Kill(entireProcessTree: true); } catch { } }, p);
    var output = await p.StandardOutput.ReadToEndAsync(ct);
    await p.WaitForExitAsync(ct);
    return output;
}

Follow-ups

  • What happens to the abandoned Task's exception? — Unobserved unless you attach ContinueWith(t => log, OnlyOnFaulted) or await it with SuppressThrowing.
  • Can you abort a thread-pool thread stuck in a sync call? — No (no Thread.Abort on .NET Core); the thread is lost until the call returns, which is why sync calls without timeouts are banned in the pool.
  • How do you document the non-cancellable step? — Name it in the method's XML doc and in the runbook: "cancellation returns immediately; the step completes in the background within N seconds".

Common wrong answer

"Just don't await it after cancellation" with no mention of the resource still running or its exception being lost.

screenerCancellationToken.None versus default; what does CanBeCanceled tell you?

Answer

They are the same value: a token with no source that can never be cancelled. Use default in parameter defaults (CancellationToken ct = default) and CancellationToken.None at call sites where you deliberately opt out, because it reads as intent. CanBeCanceled is false for such tokens, which lets library code skip registrations and linked sources entirely: a useful optimisation on hot paths and a signal in code review that a caller "forgot" to pass a token when a cancellable one was available.

Example

public ValueTask<int> ReadAsync(Memory<byte> buffer, CancellationToken ct = default)
{
    if (ct.IsCancellationRequested) return ValueTask.FromCanceled<int>(ct);
    if (!ct.CanBeCanceled) return ReadCoreAsync(buffer);          // no registration cost
    return ReadWithCancellationAsync(buffer, ct);
}

Follow-ups

  • Is it a smell to see CancellationToken.None in app code? — Sometimes it is deliberate (cleanup, commits); require a comment explaining why.
  • Can a token be cancelled without a source? — new CancellationToken(canceled: true) creates a pre-cancelled token; useful for tests.

Common wrong answer

"default is a different token that might get cancelled." They are identical; not knowing that is minor, but it leads to needless linked sources.

5Thread pool behaviour & starvation

asked: oftencritical10 questions · mid → principal

This is the unit that separates people who have run async services in production from people who have written async code. Every senior/lead loop includes a starvation scenario ("latency goes to 10 seconds under load, CPU is at 5%: go"), and many system-design rounds check whether you can reason about threads versus concurrency with numbers.

Mid level: describe queues and work stealing, name starvation and its usual cause. Senior: injection rate, min-threads trade-offs, diagnostics tooling, the .NET 6 blocking detection and .NET 10 local-queue change. Principal: capacity planning with Little's law, container CPU limits, and incident command on a starving fleet.

midHow does the .NET thread pool work internally: queues, work stealing, worker versus I/O threads?

Answer

The pool (fully managed "PortableThreadPool" since .NET 6 on all platforms) has one global FIFO queue plus a per-worker-thread local LIFO queue. Work queued from a pool thread (e.g. a Task continuation) goes to that thread's local queue for cache locality; other threads steal from the tail when they run dry, and the global queue is consulted in between. Worker threads run queued work items; a separate small set of I/O threads (IOCP on Windows; on Unix an epoll/kqueue engine) dequeue completions and then queue the continuation to the workers. Thread count starts at the minimum (by default the logical core count), grows via a hill-climbing heuristic that measures throughput, and shrinks when idle. The pool is a process-wide singleton, so a misbehaving library affects every request.

Example

// Observability from inside the process (all .NET Core 3.0+)
Console.WriteLine(ThreadPool.ThreadCount);            // current worker + I/O threads
Console.WriteLine(ThreadPool.PendingWorkItemCount);   // global + local queue depth
Console.WriteLine(ThreadPool.CompletedWorkItemCount);
ThreadPool.GetMinThreads(out var minWorkers, out var minIo);   // defaults: cores, cores

Follow-ups

  • Why LIFO locally and FIFO globally? — LIFO keeps the hot cache lines; FIFO globally keeps fairness. Stealing takes the oldest local item to reduce contention.
  • What is ThreadPool.UnsafeQueueUserWorkItem(..., preferLocal: true)? — An API to choose the local queue explicitly and skip ExecutionContext capture; used by frameworks.
  • Does a Task continuation always go to the pool? — Only when there is no captured context/scheduler and the completing thread cannot run it inline.

Common wrong answer

"It's a fixed pool of N threads with a queue." Missing local queues and work stealing is forgivable at mid level; missing that the pool grows and shrinks slowly is not, because it is the basis of starvation.

midWhat is thread-pool starvation, what are its symptoms, and what usually causes it?

Answer

Starvation is the state where all pool threads are busy (usually blocked, not computing) and queued work items, including the continuations that would unblock those threads, cannot run. Symptoms: latency climbs into seconds while CPU is low, threadpool-queue-length grows, threadpool-thread-count creeps up by one or two per second, Kestrel logs "heartbeat took longer than 1s ... thread pool starvation", health checks time out, and the service looks hung but recovers slowly when load drops. Causes, in order of frequency: sync-over-async (.Result, .Wait(), GetAwaiter().GetResult()), synchronous I/O or locks in request paths, long CPU-bound work inside requests, and unbounded Task.Run fan-out. Fix the blocking; raising min threads is a stopgap.

Example

// Reproduction on an 8-core box: 100 concurrent hits and this endpoint is dead for ~90 s
app.MapGet("/starve", () =>
{
    Task.Delay(100).Wait();      // holds a pool thread; the continuation needs another
    return "ok";
});
// dotnet-counters monitor --counters System.Runtime -p <pid>
//   threadpool-queue-length rising, threadpool-thread-count +1..2 per second

Follow-ups

  • Why does CPU stay low? — Threads are blocked in waits, not running; the machine is idle while the service is unresponsive.
  • Why does it recover slowly? — Injected threads stay only while needed and the pool retires them; the next burst starts from the minimum again.
  • What is the first command you run on the box? — dotnet-counters for queue length and thread count, then dotnet-stack or a dump to see what the threads are blocked on.

Common wrong answer

"Starvation means too many requests for the server." Load alone causes queueing, not starvation; the discriminating detail is threads blocked while CPU is idle.

seniorHow does the pool decide to add threads: minimum, hill climbing, and blocking detection?

Answer

Up to the minimum (default: logical core count, adjusted for container CPU limits), the pool creates a thread immediately whenever there is queued work and no idle thread. Above the minimum it becomes deliberately slow: the hill-climbing algorithm periodically adjusts the thread count and measures completed-work throughput, adding threads only if throughput improves, roughly one or two per second; plus a starvation rule that adds a thread if no work item has completed in a while. Since .NET 6 the pool also has explicit blocking detection: when a worker blocks in a known Task wait (Task.Wait, Result, GetResult on an incomplete task) the pool temporarily raises its target and injects threads faster. It cannot see blocking on Monitor, SemaphoreSlim.Wait, synchronous I/O or native calls, so those still rely on the slow path. Idle threads above the minimum are retired after a timeout.

Example

// Rough capacity maths for an 8-core container:
// min threads = 8 → 8 requests can block "for free".
// Request 9..N each wait for injection at ~1–2 threads/s.
// 100 blocked requests → ~60–90 s until the pool catches up.
// Same endpoint written async: 0 threads blocked, 100 requests in flight on ~8 threads.

Follow-ups

  • Why is hill climbing slow on purpose? — More threads than cores usually lowers throughput (context switches, cache); the algorithm optimises throughput, not latency.
  • What does the .NET 6 detection change in practice? — Sync-over-async bursts recover in seconds instead of a minute; it is a safety net, not a licence.
  • How do container CPU limits affect the minimum? — Environment.ProcessorCount honours cgroup quotas (rounded up); a 0.5-CPU pod has a min of 1 thread, which makes starvation trivially easy.

Common wrong answer

"The pool spins up threads as needed." The senior discriminator is knowing that above the minimum it is throttled to about one or two per second.

seniorIs raising ThreadPool.SetMinThreads a fix? What does it cost?

Answer

It is a legitimate mitigation and a poor fix. Raising the minimum lets the pool create threads immediately up to that number, which hides sync-over-async and buys time during an incident. Costs: each thread reserves stack (1 MB by default) and has scheduling overhead, so a minimum of 500 on an 8-core box means heavy context switching and worse throughput for the code that is actually asynchronous; the setting is process-wide and masks the root cause so it never gets fixed; and it does not help when the blocked count exceeds the new minimum. Set it via System.Threading.ThreadPool.MinThreads in runtimeconfig.json or DOTNET_ThreadPool_MinThreads, with a ticket to remove it, and pair it with analyzers that fail the build on new blocking calls.

Example

// runtimeconfig.template.json (temporary mitigation, tracked in INC-1234)
{
  "configProperties": {
    "System.Threading.ThreadPool.MinThreads": 64
  }
}

Follow-ups

  • How would you pick the number? — From the dump: count of blocked pool threads at peak plus headroom; not "a big number".
  • Is SetMaxThreads ever useful? — Rarely; lowering it caps concurrency crudely and can deadlock; the default max is very large.
  • What about using the Windows thread pool (.NET 8 UseWindowsThreadPool)? — A different injection policy that can behave better with blocking on Windows; still not a fix.

Common wrong answer

"Set min threads to 1000 and it's solved." The interviewer wants the cost list and the "temporary, tracked" framing; presenting it as the fix reads as junior.

midWhen do you use TaskCreationOptions.LongRunning?

Answer

LongRunning is a hint to the default scheduler that the work will occupy a thread for a long time; the scheduler responds by creating a dedicated non-pool thread instead of taking one from the pool, so a long loop does not count against pool capacity or trigger hill climbing. Use it for a handful of dedicated loops per process: a consumer draining a channel synchronously, a socket accept loop written synchronously, a scheduler tick. Do not use it for async lambdas (the dedicated thread is abandoned at the first await) or for many short tasks (thread creation is expensive). Long-running async loops do not need it at all: they hold no thread while awaiting.

Example

// Dedicated thread for a blocking consumer of a legacy queue
_consumer = Task.Factory.StartNew(() =>
{
    foreach (var msg in _legacyQueue.GetConsumingEnumerable(ct))   // blocks
        Handle(msg);
}, ct, TaskCreationOptions.LongRunning, TaskScheduler.Default);

Follow-ups

  • How is it different from new Thread? — Same thread-wise; you get a Task for completion and exceptions, and the scheduler may decide otherwise in principle.
  • What if you pass an async lambda with LongRunning? — The dedicated thread runs the synchronous prefix and exits at the first await; continuations run on the pool.
  • Does Task.Run have a LongRunning overload? — No; that is the main reason Task.Factory.StartNew is still used.

Common wrong answer

"Use LongRunning for any task that takes more than a few seconds, including async ones." It only matters for work that blocks a thread.

seniorProduction is starving right now. How do you confirm it and find the culprit?

Answer

Confirm with counters: dotnet-counters monitor -p <pid> --counters System.Runtime shows threadpool-queue-length climbing and threadpool-thread-count rising slowly while CPU is low (in .NET 9+ the same data is in the System.Runtime meter: dotnet.thread_pool.queue.length, dotnet.thread_pool.thread.count). Then find what threads are doing: dotnet-stack report -p <pid> for a quick look, or dotnet-dump collect and dotnet-dump analyze with clrstack -all to see dozens of threads sitting in Task.Wait/Monitor.Enter/sync socket reads, and dumpasync to see the async state machines waiting on them. The stack that appears fifty times is the culprit. Mitigate (scale out, raise min threads, shed load), then fix the blocking call and add the analyzer that would have caught it. Keep the dump for the post-mortem.

Example

dotnet-counters monitor -p 4242 --counters System.Runtime[threadpool-thread-count,threadpool-queue-length,threadpool-completed-items-count]
dotnet-stack report -p 4242 | grep -c "System.Threading.Tasks.Task.Wait"    # how many blocked
dotnet-dump collect -p 4242
dotnet-dump analyze core_20260907 -c "clrstack -all" -c "dumpasync -stats"

Follow-ups

  • Why is a dump safer than attaching a debugger? — Collection pauses the process for a second; a debugger attach can hang a starving process indefinitely.
  • What if the blocking is in native code? — clrstack shows the P/Invoke frame; correlate with the OS view (strace/ProcMon) to see what it waits on.
  • What alert do you add afterwards? — Queue length above a small threshold for more than N seconds, plus the Kestrel heartbeat warning as a log-based alert.

Common wrong answer

"Restart the pods." It recovers the symptom, destroys the evidence, and the incident repeats at the next peak; the interviewer is looking for "collect a dump first".

seniorWhat changed in the .NET 10 thread pool for blocked workers, and why does it matter?

Answer

In .NET 10, when a worker thread blocks on a task (the Task.Wait/Result family), the pool moves that thread's local-queue work items to the global queue before blocking (dotnet/runtime PR #112796, on by default; it had been introduced as an opt-in earlier). Previously those items were stranded: local queues are stolen at the lowest priority, so under starvation a blocked worker could hold the very continuation that would unblock it, a priority inversion that turned a slow pool into a deadlock-like hang. The change does not make blocking free, but it removes the worst failure mode and makes recovery depend only on injection speed. It is a good example of a "recent, citable" detail: it demonstrates you understand local queues and priority inversion, not just "blocking is bad".

Example

// Pre-.NET 10 pathological case (8 workers, all doing this):
var inner = Task.Run(() => Compute());     // continuation queued to *this* worker's local queue
inner.Wait();                              // this worker blocks; other workers steal local items last
// .NET 10: local items are handed to the global queue first, so another worker runs Compute().

Follow-ups

  • Does it cover SemaphoreSlim.Wait or lock? — No, only waits the pool can see (task waits); those remain fully on the slow path.
  • What other thread-pool knobs arrived recently? — .NET 8: UseWindowsThreadPool (opt-in Windows-native pool); .NET 6: managed pool everywhere and blocking detection.
  • How would you verify the behaviour on your build? — Reproduce the inner-Wait scenario under load on .NET 9 and .NET 10 and compare queue length and recovery time.

Common wrong answer

Presenting the .NET 10 change as "the thread pool now handles blocking, so sync-over-async is fine". It addresses stranded work items, not the thread cost of blocking.

seniorWhere does an I/O completion actually run, and how does the continuation get to your code?

Answer

On Windows, sockets and files use overlapped I/O; the kernel posts a completion packet to an I/O completion port, an I/O-pool thread dequeues it, and the runtime queues the continuation (the Task completion) to the worker pool, or runs a small amount inline for socket completions. On Linux/macOS, .NET's SocketAsyncEngine runs one or more epoll/kqueue threads that receive readiness, perform the read, and hand the continuation to the worker pool. File I/O on Unix is not truly asynchronous at the OS level for regular files, so FileStream uses a small dedicated path; since .NET 6 FileStream was rewritten and honours useAsync correctly on Windows. Net effect: no thread waits for I/O, one thread briefly dispatches, and your continuation runs on a worker, which is why your code must not assume any thread identity.

Example

// The awaiter chain for a socket read (simplified):
// kernel completes → IOCP/epoll thread → SocketAsyncEventArgs completion
//   → ValueTask<int> source signals → continuation queued (ThreadPool) → your MoveNext()
var n = await socket.ReceiveAsync(buffer, SocketFlags.None, ct); // ValueTask<int>, pooled source

Follow-ups

  • How many I/O threads exist? — Few (min = cores on Windows; one to a handful of epoll threads on Unix, scaled with core count); they must never run user code that blocks.
  • Why does Console.ReadLine or a synchronous FileStream.Read not benefit? — They are blocking syscalls: the calling thread waits.
  • What is RunContinuationsAsynchronously's role here? — Frameworks use it on internal completion sources so user continuations never run inline on the I/O thread.

Common wrong answer

"A thread-pool thread waits on the socket." That is exactly what does not happen; it is the whole reason async scales.

midExplain with numbers why async improves throughput even though each call is slightly slower.

Answer

Little's law: concurrent operations in flight = throughput × latency. A service doing 1,000 requests/s where each request waits 100 ms on a database has 100 requests in flight at all times. Synchronous code needs 100 threads parked in waits (100 MB of reserved stack, context switches, and a pool that takes a minute to grow to that size); async code has 100 outstanding I/O operations and needs only as many threads as there is CPU work, typically the 8 cores' worth. Per call, async adds a state machine and a few allocations (microseconds), which is invisible next to a 100 ms wait. The gain is not speed per request; it is not tying capacity to thread count, and not having latency spikes from thread injection.

Example

throughput 1,000 rps × latency 0.1 s = 100 in flight
sync : 100 threads blocked  → pool must grow to 100 (≈1–2/s above min) → 60–90 s of degraded latency per burst
async: 100 pending I/O ops   → ~8 worker threads busy with CPU work → steady latency
downstream slows to 1 s     : sync needs 1,000 threads (unreachable); async needs 1,000 pending ops (memory only)

Follow-ups

  • What becomes the new bottleneck with async? — Downstream capacity and connection pools (e.g. SQL pool default 100); async makes it easy to overload dependencies, so add bounded concurrency.
  • Is async faster for CPU-bound work? — No; it only helps when there is a wait to hide.
  • How does this change autoscaling signals? — CPU stops being a proxy for saturation; use queue length, in-flight count and latency.

Common wrong answer

"Async makes each request faster because it runs in parallel." Per-request latency is unchanged or slightly worse; the answer must be about threads per unit of concurrency.

principalHow do containers, CPU limits and the choice of thread pool affect an async service's behaviour?

Answer

The pool sizes itself from Environment.ProcessorCount, which honours cgroup CPU quotas (a 1.5-CPU limit reports 2 cores): minimum threads, GC heap count and Parallel.ForEachAsync's default degree of parallelism all shrink with it. Small limits make any blocking catastrophic (min 1–2 threads) and make CPU throttling visible as latency spikes when a burst of continuations runs. Practical policy: set requests and limits so the pod has at least 2 CPUs if it runs request workloads; prefer CPU requests without hard limits where the platform allows; use DOTNET_PROCESSOR_COUNT only when you understand the GC implications; and keep the managed pool (default) unless a Windows-specific blocking workload measurably benefits from UseWindowsThreadPool. Watch dotnet.process.cpu.time against throttling metrics from the orchestrator to tell "we are starved of threads" from "we are throttled by the kernel".

Example

# k8s: give the pool something to work with
resources:
  requests: { cpu: "2", memory: "1Gi" }
  limits:   { memory: "1Gi" }        # no CPU limit: avoids CFS throttling latency spikes
env:
  - { name: DOTNET_gcServer, value: "0" }        # workstation GC on small pods
  # - { name: DOTNET_ThreadPool_MinThreads, value: "16" }  # only as a tracked mitigation

Follow-ups

  • Why is server GC relevant? — Server GC creates a heap and GC thread per core; on tiny pods it wastes memory and its GC threads compete with the pool.
  • What about horizontal scale as the fix for starvation? — Scales the symptom: N pods each starving; use it to buy time while fixing the blocking.
  • How does Parallel.ForEachAsync misbehave on a 1-CPU pod? — Default parallelism 1; explicit MaxDegreeOfParallelism for I/O-bound fan-out is required.

Common wrong answer

Treating the pool as independent of the container: "it starts with a default of 8 threads" on a pod limited to 0.5 CPU.

6ValueTask, allocation & hot paths

asked: sometimescritical at senior+8 questions · mid → principal

ValueTask is the favourite "do you actually understand the machinery" probe. It is asked less often than the units above, but when it is asked the bar is high: interviewers want the rules (await once, never concurrently, never block), the allocation story behind them, and a sober view of when the optimisation is worth its API cost.

Mid level: what ValueTask is and the one-await rule. Senior: IValueTaskSource, allocation profile of an async method, task caching. Principal: API design policy for a shared library and how you measure before adopting it.

Official docs: Understanding the whys, whats and whens of ValueTask ValueTask<TResult> CA2012: Use ValueTasks correctly
midWhat is ValueTask<T> and when should you use it instead of Task<T>?

Answer

ValueTask<T> is a struct that holds either a result, a Task<T>, or an IValueTaskSource<T> plus a token. When a method can often complete synchronously (a cache hit, a buffered read), returning ValueTask avoids allocating a Task<T> for that result; when the work is truly asynchronous it wraps a Task or a pooled source. Use it for hot-path APIs where profiling shows Task allocation matters and the synchronous case is common, or where you control an IValueTaskSource pool (sockets, channels, pipelines). Do not use it as a default: it is larger (two words plus a token), has strict usage rules, and callers who need Task semantics must call AsTask(), which allocates anyway.

Example

private readonly ConcurrentDictionary<string, Config> _cache = new();

public ValueTask<Config> GetAsync(string key, CancellationToken ct)
{
    if (_cache.TryGetValue(key, out var cfg))
        return new ValueTask<Config>(cfg);            // no allocation on the hit path
    return new ValueTask<Config>(LoadAndCacheAsync(key, ct));   // real async: wraps a Task
}

Follow-ups

  • Which BCL APIs return ValueTask? — Stream.ReadAsync(Memory<byte>), Socket.ReceiveAsync, ChannelReader.ReadAsync, PipeReader.ReadAsync, IAsyncEnumerator.MoveNextAsync, IAsyncDisposable.DisposeAsync.
  • Does async ValueTask<T> allocate? — Not if it completes synchronously; if it suspends, the builder allocates a state-machine box (a Task-like object) the same as Task would.
  • What is the non-generic ValueTask for? — Same idea for operations without a result, e.g. DisposeAsync; it appeared in .NET Core 2.1 with IValueTaskSource.

Common wrong answer

"ValueTask is just a faster Task." It is a different contract; saying that invites the "can you await it twice?" follow-up, which then fails.

seniorWhat are the rules for consuming a ValueTask, and why do they exist?

Answer

Await it exactly once, and do nothing else with it. Specifically: do not await it twice; do not await it concurrently from two places; do not call .Result/GetAwaiter().GetResult() unless IsCompleted is true; do not store it and use it later; do not mix AsTask() with awaiting. The reason is IValueTaskSource pooling: once the consumer has retrieved the result, the source may be reset and reused for a different operation, so a second await could observe someone else's result or corrupt the pool. If you need Task semantics (multiple awaiters, WhenAll, caching), call AsTask() once and use the Task, or .Preserve() (.NET 5) to get a ValueTask that is safe to await repeatedly. CA2012 flags most violations.

Example

ValueTask<int> vt = reader.ReadAsync(buffer, ct);

// OK: single await
int n = await vt;

// OK: fast-path check then await
if (vt.IsCompletedSuccessfully) n = vt.Result; else n = await vt;

// WRONG: second await may hit a recycled source
int again = await vt;                 // CA2012

// OK when you need a Task
Task<int> t = reader.ReadAsync(buffer, ct).AsTask();
await Task.WhenAll(t, other);

Follow-ups

  • Is IsCompletedSuccessfully then .Result safe? — Yes; reading the result of a completed ValueTask is the intended fast path.
  • What does .Preserve() do? — If the ValueTask wraps a pooled source it converts it into a Task-backed ValueTask; otherwise returns itself.
  • Can you pass a ValueTask to Task.WhenAny? — Not directly; AsTask() first, which allocates the Task you were trying to avoid.

Common wrong answer

"It behaves like Task, you can await it as many times as you like as long as it's a struct copy." The pooled-source reuse is the point of the question.

principalHow does IValueTaskSource<T> work, and when would you implement one?

Answer

IValueTaskSource<T> is the interface a ValueTask delegates to: GetStatus(token), OnCompleted(continuation, state, token, flags), and GetResult(token). The token guards against reuse: each new operation increments it, and a stale ValueTask calling with an old token throws. ManualResetValueTaskSourceCore<T> (.NET Core 3.0) implements the state machine for you (result/exception storage, continuation capture with ExecutionContext/SynchronizationContext, Reset()), so a typical implementation wraps it in a pooled object. You implement one when you own a high-frequency asynchronous primitive: a custom socket layer, an async queue, a timer-like primitive, an object pool with async rent; in application code it is almost never justified. The runtime uses it for sockets, Channel<T>, pipelines and Task.Delay-style internals.

Example

sealed class ReusableSignal : IValueTaskSource<bool>
{
    private ManualResetValueTaskSourceCore<bool> _core = new() { RunContinuationsAsynchronously = true };

    public ValueTask<bool> WaitAsync() => new(this, _core.Version);
    public void Set(bool value) => _core.SetResult(value);
    public void Reset() => _core.Reset();                       // bumps Version: old ValueTasks become invalid

    bool IValueTaskSource<bool>.GetResult(short token) { var r = _core.GetResult(token); _core.Reset(); return r; }
    ValueTaskSourceStatus IValueTaskSource<bool>.GetStatus(short token) => _core.GetStatus(token);
    void IValueTaskSource<bool>.OnCompleted(Action<object?> c, object? s, short token, ValueTaskSourceOnCompletedFlags f)
        => _core.OnCompleted(c, s, token, f);
}

Follow-ups

  • Why RunContinuationsAsynchronously = true? — So the caller of Set does not run arbitrary consumer code inline (stack depth, lock scope, I/O thread).
  • Where does the reset happen safely? — After GetResult has been called by the single consumer; resetting before that is the bug the token protects against.
  • What flags does OnCompleted receive? — Whether to capture ExecutionContext and/or the current SynchronizationContext/scheduler; ConfigureAwait(false) clears the latter.

Common wrong answer

Describing a TaskCompletionSource instead. TCS allocates a Task per operation; the whole point of IValueTaskSource is reuse.

seniorWhat does an async method allocate, and when?

Answer

In Release builds the compiler generates a struct state machine that lives on the stack while the method runs synchronously. If the method completes without suspending, the only allocation is the returned Task (and even that is avoided for Task, cached Task<bool>/small ints, or any ValueTask result). On the first real suspension the builder boxes the struct into a single heap object that is the returned Task (since .NET Core 2.1 the box derives from Task<T>), plus one continuation delegate cached inside it; subsequent suspensions reuse both. Extra allocations come from closures captured by lambdas, from ConfigureAwait wrappers (none: they are structs), from Task.WhenAll arrays, from CTS/registrations, and from awaiting non-Task awaitables that box. So: zero allocations on the synchronous path is achievable; one object per suspended async frame is the floor with compiler-generated async, and Runtime Async in .NET 11 reduces even that by allocating continuations lazily and reusing them.

Example

// BenchmarkDotNet, [MemoryDiagnoser]: typical numbers on .NET 10
// Method                       Mean      Allocated
// SyncPath_Task_bool           ~15 ns    0 B      (cached Task<bool>)
// SyncPath_Task_int_1000       ~20 ns    24 B     (Task<int> for non-cached value)
// SyncPath_ValueTask_int       ~12 ns    0 B
// Suspending_once              ~150 ns   ~100 B   (state machine box)
public async ValueTask<int> ReadIntAsync()
{
    if (_buffered >= 4) return ReadBuffered();      // 0 B
    await FillAsync();                                // box on suspension only
    return ReadBuffered();
}

Follow-ups

  • Why is the state machine a class in Debug? — So the debugger can inspect it after being moved to the heap; it changes allocation numbers, so never benchmark Debug builds.
  • Which Task<T> results are cached by the runtime? — bool, small ints (-1..8), null/default reference results, and Task.CompletedTask.
  • What about async lambdas? — Each invocation allocates a delegate and possibly a closure in addition to the state machine; hoist static lambdas where possible (static lambdas, C# 9).

Common wrong answer

"Every async method allocates several objects per call." That was .NET Framework (Task + boxed state machine + MoveNextRunner + delegate); modern .NET is one box on suspension, zero if synchronous.

principalWhat is PoolingAsyncValueTaskMethodBuilder, and when is it worth using?

Answer

.NET 6 added a builder that pools the state-machine boxes of async ValueTask/ValueTask<T> methods so a suspending call reuses an object from a per-core cache instead of allocating. You opt in per method with [AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))] (C# 10 allows the attribute on methods) or per assembly with the DOTNET_SYSTEM_THREADING_POOLASYNCVALUETASKS switch. It is worth it only for very hot async methods whose callers obey the ValueTask rules strictly, since pooling makes violations (double await) into real bugs, and only when measured: the pool has its own overhead and the gain is typically single-digit percent in allocation-heavy servers. Runtime Async in .NET 11 aims to make this largely unnecessary by reusing continuations natively.

Example

[AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))]
public async ValueTask<int> ReadFrameAsync(CancellationToken ct)
{
    var len = await ReadIntAsync(ct);
    await FillAsync(len, ct);
    return len;
}

Follow-ups

  • Does it work with async Task? — No; Task objects must stay valid forever, which is incompatible with pooling.
  • How do you prove it helps? — BenchmarkDotNet with MemoryDiagnoser and an allocation-rate counter under load; if allocation rate does not move, remove it.
  • What breaks if a caller awaits twice? — They may read another operation's result; the failure is silent, which is why this is a "with analyzers only" feature.

Common wrong answer

Applying it broadly "because it is free". It moves risk from the callee to every caller.

seniorShould a public API or interface return ValueTask? What are the design implications?

Answer

Default to Task in public surface; use ValueTask only where the API is a hot primitive and the framework precedent applies (streams, channels, enumerators, disposables). Implications of ValueTask in an interface: every implementer inherits the ability to pool, and every consumer inherits the consumption rules; mocking is more awkward; combinators (WhenAll, caching, retries) need AsTask(), which erases the benefit and adds a copy; and changing your mind later is a binary-breaking change either way. A reasonable policy for a shared library: Task on service-level interfaces, ValueTask on byte-level or per-item interfaces, and never ValueTask in a method that callers will commonly compose.

Example

public interface IOrderRepository            // service-level: Task
{
    Task<Order?> FindAsync(OrderId id, CancellationToken ct);
}

public interface IFrameReader                 // per-item primitive: ValueTask
{
    ValueTask<Frame?> ReadAsync(CancellationToken ct);
}

Follow-ups

  • How does this interact with DI decorators (logging, caching)? — A decorator that awaits a ValueTask and returns a new one keeps the contract; one that stores it in a cache violates it.
  • Is ValueTask for DisposeAsync a good precedent? — Yes: usually synchronous, single consumer, rarely composed.
  • What about source-generated or gRPC clients? — They return Task; matching them avoids conversions at boundaries.

Common wrong answer

"Use ValueTask on all interfaces for consistency." Consistency in the wrong direction; the reviewer wants the composition and mocking costs named.

midHow do you avoid allocating Tasks for common results (task caching)?

Answer

Return pre-completed tasks: Task.CompletedTask for Task; Task.FromResult(x) allocates a new Task<T> each time, so cache the ones you return often in static readonly fields (e.g. Task<bool> true/false, an empty array). The runtime already caches Task<bool> and small integer results from async methods. For truly hot paths return ValueTask instead. In non-async Task-returning methods, avoid async just to return a constant; Task.FromException/FromCanceled exist for the error paths so the method's contract stays "exceptions are in the Task".

Example

private static readonly Task<IReadOnlyList<Item>> s_empty = Task.FromResult<IReadOnlyList<Item>>(Array.Empty<Item>());

public Task<IReadOnlyList<Item>> ListAsync(Filter f, CancellationToken ct)
{
    if (f.IsEmpty) return s_empty;                              // no allocation
    if (ct.IsCancellationRequested) return Task.FromCanceled<IReadOnlyList<Item>>(ct);
    return ListCoreAsync(f, ct);
}

Follow-ups

  • Is a cached Task<T> safe to share across callers? — Yes; completed Tasks are immutable and can be awaited any number of times.
  • Why not cache a ValueTask? — A result-holding ValueTask is a struct, so "caching" is just constructing it; a source-backed one must never be shared.
  • Does async Task returning nothing allocate? — Not on the synchronous path: the builder returns the cached Task.CompletedTask.

Common wrong answer

"Task.FromResult is free." It allocates unless you cache the result; the interviewer expects the static field pattern.

midHow do you measure whether an async hot path is worth optimising?

Answer

Start with production signals: allocation rate (gc-heap-size, alloc-rate in dotnet-counters, or the System.Runtime meter), Gen0 GC frequency, and CPU time attributed to MoveNext/builder frames in a sampled profile (dotnet-trace, PerfView). If async overhead is not visible there, do nothing. If it is, isolate the method in BenchmarkDotNet with [MemoryDiagnoser] and compare Task vs ValueTask vs elision on both the synchronous and suspending paths, in Release, on the target runtime. Decide on numbers with a stated threshold (e.g. "adopt only if allocations per request drop by 10% and p99 does not regress"). Interviewers care less about which tool and more that you measure before and after, and that you know async overhead is rarely the bottleneck compared with I/O and serialization.

Example

[MemoryDiagnoser]
public class ReadBench
{
    [Benchmark(Baseline = true)] public async Task<int> TaskPath()      => await _reader.ReadTaskAsync();
    [Benchmark]                  public async ValueTask<int> ValueTaskPath() => await _reader.ReadValueTaskAsync();
}
// dotnet run -c Release -- --filter *ReadBench*

Follow-ups

  • What does a high Gen0 count with low latency impact tell you? — Allocation is cheap when objects die young; optimise only if GC pauses or CPU show up.
  • How do you profile allocations in production safely? — dotnet-trace collect --profile gc-verbose for a short window, or the EventPipe allocation sampling in .NET 8+ (--clrevents gc --clreventlevel verbose); keep sessions short.
  • What is a typical win from ValueTask on a real API? — Often nothing measurable at the service level; large for byte-level loops like framing or parsing.

Common wrong answer

"Use ValueTask everywhere and remove async where possible; it's always faster." No measurement, no threshold: the reviewer marks it as premature optimisation.

screenerWhat is IAsyncEnumerable<T>, and how does it differ from Task<IEnumerable<T>> and IObservable<T>?

Answer

IAsyncEnumerable<T> (C# 8 / .NET Core 3.0) is a pull-based sequence where each MoveNextAsync() may await: items are produced lazily and consumed with await foreach. Task<IEnumerable<T>> is one asynchronous step that yields a fully materialised collection, so memory and time-to-first-item scale with the whole result. IObservable<T> is push-based: the producer decides the pace and the consumer must keep up or buffer, which is why Rx has explicit back-pressure operators. Choose async streams when the consumer should control pacing (paging over a database, reading a socket, streaming an HTTP response), Task-of-collection when the whole set is small and needed at once, and observables for event-style fan-out.

Example

public async IAsyncEnumerable<Order> StreamOrdersAsync(
    DateOnly since, [EnumeratorCancellation] CancellationToken ct = default)
{
    string? cursor = null;
    do
    {
        var page = await _api.GetOrdersPageAsync(since, cursor, ct);   // one page at a time
        foreach (var o in page.Items) yield return o;
        cursor = page.NextCursor;
    } while (cursor is not null);
}

await foreach (var o in StreamOrdersAsync(since).WithCancellation(ct)) Process(o);

Follow-ups

  • What does MoveNextAsync return? — ValueTask<bool>, so a buffered page is consumed with no allocation per item.
  • Can the consumer stop early? — Yes: breaking out of await foreach calls DisposeAsync, which runs the iterator's finally blocks.
  • Is IAsyncEnumerable re-enumerable? — Like IEnumerable, each GetAsyncEnumerator starts a fresh enumeration if the implementation allows it.

Common wrong answer

"It's a list you can iterate asynchronously." Missing laziness and consumer-driven pacing means the candidate will also miss why it is the right shape for large exports.

midHow does cancellation work with async streams: WithCancellation and [EnumeratorCancellation]?

Answer

GetAsyncEnumerator(CancellationToken) is where the token enters an async stream; await foreach passes default unless you call .WithCancellation(ct) on the source. Inside an async iterator method, mark a CancellationToken parameter with [EnumeratorCancellation]: the compiler then wires the token passed to GetAsyncEnumerator into that parameter, and if the caller supplied one at call time as well, it links both. Without the attribute, the token the consumer passes via WithCancellation is silently ignored (the compiler warns, CS8425). The idiomatic signature is [EnumeratorCancellation] CancellationToken ct = default as the last parameter, so both call-time and enumeration-time cancellation work.

Example

public async IAsyncEnumerable<string> LinesAsync(Stream s,
    [EnumeratorCancellation] CancellationToken ct = default)
{
    using var reader = new StreamReader(s);
    while (await reader.ReadLineAsync(ct) is { } line)   // ct comes from WithCancellation or the call
        yield return line;
}

await foreach (var line in LinesAsync(stream).WithCancellation(requestAborted)) { }

Follow-ups

  • What if both a call-site token and WithCancellation token are given? — The generated code creates a linked source; cancelling either cancels the enumeration.
  • Does cancelling mid-enumeration run finally blocks? — The OCE propagates out of MoveNextAsync, the loop exits, and DisposeAsync runs the finally blocks.
  • Why does the attribute exist instead of a language rule? — Because the iterator's parameter and the enumerator's token are two different injection points; the attribute names which parameter to bind.

Common wrong answer

"Just pass the token to the iterator method." That covers call-time cancellation only; without the attribute, WithCancellation does nothing.

midHow do async iterators execute: laziness, exceptions, and disposal?

Answer

An async IAsyncEnumerable<T> method with yield return compiles to a state machine that is both the enumerable and (for the first enumeration) the enumerator. Nothing in the body runs until the first MoveNextAsync; each call runs until the next yield return or the end. Exceptions thrown in the body surface from MoveNextAsync (i.e. inside the consumer's await foreach), not from the initial call, so argument validation needs the same wrapper trick as async methods. yield break ends the sequence; finally blocks and using scopes run when enumeration completes or when the consumer disposes early. Because the body can await between yields, one enumerator must not be advanced concurrently; guard shared producers with a Channel instead.

Example

public IAsyncEnumerable<Row> QueryAsync(string sql, CancellationToken ct = default)
{
    ArgumentException.ThrowIfNullOrEmpty(sql);        // eager: thrown at call time
    return QueryCoreAsync(sql, ct);
}

private async IAsyncEnumerable<Row> QueryCoreAsync(string sql, [EnumeratorCancellation] CancellationToken ct)
{
    await using var conn = await _factory.OpenAsync(ct);
    await using var reader = await conn.ExecuteReaderAsync(sql, ct);
    while (await reader.ReadAsync(ct))
        yield return Map(reader);                      // connection stays open between yields
}

Follow-ups

  • What happens if the consumer holds the enumerator for a long time between items? — Resources in the iterator (the connection above) stay open; document it or copy pages into memory.
  • Can you yield return inside a try with catch? — No (same rule as sync iterators); only inside try/finally.
  • Does the enumerator capture the SynchronizationContext? — Each internal await does unless configured; consumers use ConfigureAwait(false) on the stream when appropriate.

Common wrong answer

"The iterator runs eagerly to fill a buffer, then hands items out." It is lazy; that misunderstanding leads to wrong reasoning about when the DB connection opens.

seniorWhat changed for LINQ over IAsyncEnumerable<T> in .NET 10, and how do you migrate?

Answer

.NET 10 ships System.Linq.AsyncEnumerable in the base library: the full set of LINQ operators (Where, Select, ToListAsync, ToArrayAsync, and async-delegate variants) for IAsyncEnumerable<T>, replacing the community System.Linq.Async package (Ix.NET). Projects that reference the old package on .NET 10 get ambiguity errors because both define the same extension methods; the fix is to remove the package or upgrade to System.Linq.Async 7.0, which defers to the built-in implementation. For multi-targeting older TFMs reference the System.Linq.AsyncEnumerable NuGet package instead. .NET 11 previews add join operators (FullJoin, tuple-returning Join/GroupJoin) to AsyncEnumerable alongside Enumerable. EF Core's ToListAsync etc. live in EF's own namespace and are unaffected, but watch for name clashes when both are in scope.

Example

// .NET 10, no package needed
var bigOrders = await _repo.StreamOrdersAsync(since, ct)
    .Where(o => o.Total > 1000)
    .Select(o => new OrderSummary(o.Id, o.Total))
    .Take(100)
    .ToListAsync(ct);

// csproj migration: remove <PackageReference Include="System.Linq.Async" />
//                   or bump it to 7.0.0 when multi-targeting net8.0/net10.0

Follow-ups

  • Why did the BCL take this over? — With Task.WhenEach, channels and streaming APIs all returning async streams, a standard operator set became necessary, and the Ix maintainers agreed.
  • Are the operators identical in behaviour? — Mostly; some naming differs (SelectAwait-style names were dropped in favour of overloads taking async delegates), so a compile pass is needed.
  • How does ToListAsync interact with cancellation? — Takes a token that is passed to GetAsyncEnumerator.

Common wrong answer

"You need System.Linq.Async for LINQ on async streams." True before November 2025; today it signals not having built on .NET 10.

seniorHow do ASP.NET Core and EF Core handle IAsyncEnumerable<T>, and where does buffering still happen?

Answer

ASP.NET Core (6+) streams an IAsyncEnumerable<T> returned from a minimal API or controller: System.Text.Json writes items into the response as they arrive, flushing in chunks, so memory stays flat. Newtonsoft.Json formatters buffer instead (they do not understand async streams). The response is chunked and the client sees a JSON array whose closing bracket arrives at the end; an exception mid-stream cannot change the status code because headers are already sent, so the client gets a truncated body. EF Core exposes AsAsyncEnumerable() and await foreach over a query, keeping one open DbDataReader, which pins a connection and a DbContext for the whole stream; you cannot run another query on that context until it completes. Also, some providers still buffer the entire result set client-side depending on the reader options (e.g. MARS off, or when the query has an Include of a collection that requires ordering across rows).

Example

app.MapGet("/export", (AppDb db, CancellationToken ct) =>
    db.Orders.AsNoTracking()
             .Where(o => o.Created > DateTime.UtcNow.AddDays(-30))
             .OrderBy(o => o.Id)
             .AsAsyncEnumerable()          // streamed: DbContext + connection stay busy until done
             .WithCancellation(ct));       // client disconnect stops the query

Follow-ups

  • What if the export takes 10 minutes? — Connection pinned for 10 minutes; consider a background job writing to blob storage plus a download link, or NDJSON with periodic flushes.
  • How do you report a mid-stream error to a client? — Use NDJSON and a terminal error record, or a trailer; with a plain JSON array you cannot.
  • What does .NET 11 add here? — SerializeAsyncEnumerable overloads targeting PipeWriter and top-level NDJSON output in System.Text.Json (preview).

Common wrong answer

"Returning IAsyncEnumerable from a controller buffers everything anyway." True on ASP.NET Core 3.x/5 with MVC in some configurations; not since 6.

seniorHow do you get back-pressure with async streams, and when is a Channel<T> the better shape?

Answer

Async streams have back-pressure built in because they are pull-based: the producer cannot run ahead of the consumer, since the next item is only produced when MoveNextAsync is called. That is ideal for one producer and one consumer in the same call chain. When you need decoupling (a producer running on its own, several consumers, buffering to smooth bursts, or a boundary between a request and a background worker) use a bounded Channel<T>: the writer awaits WriteAsync when the buffer is full (or drops per BoundedChannelFullMode), and consumers read with ReadAllAsync(), which is itself an IAsyncEnumerable<T>. Unbounded channels or Task.Run-per-item fan-out remove back-pressure and turn a slow consumer into an out-of-memory.

Example

var channel = Channel.CreateBounded<Event>(new BoundedChannelOptions(1_000)
{
    SingleWriter = true, SingleReader = false,
    FullMode = BoundedChannelFullMode.Wait          // producer slows down when the buffer is full
});

// producer
await foreach (var e in source.WithCancellation(ct)) await channel.Writer.WriteAsync(e, ct);
channel.Writer.Complete();

// consumers (N of them)
await foreach (var e in channel.Reader.ReadAllAsync(ct)) await HandleAsync(e, ct);

Follow-ups

  • How do you propagate a producer failure to consumers? — Writer.Complete(exception); readers observe it from ReadAllAsync/Completion.
  • Which FullMode for metrics/telemetry? — DropOldest/DropWrite with a dropped-count metric; never Wait on a request path that must stay fast.
  • Why prefer channels over BlockingCollection? — BlockingCollection blocks threads; channels await and integrate with cancellation.

Common wrong answer

"Use an unbounded channel or a ConcurrentQueue with Task.Run consumers." Removing the bound removes the back-pressure that was the whole question.

midWhat are IAsyncDisposable and await using, and how do they interact with ConfigureAwait?

Answer

IAsyncDisposable.DisposeAsync() (returning ValueTask) lets a type flush or close asynchronously (a stream with a buffer, a database connection, a gRPC call). await using calls it at scope exit, including on exceptions. Types that implement both interfaces should make Dispose() synchronous and not block on DisposeAsync, and DisposeAsync should be idempotent. For library code that must not capture the context, use await using (x.ConfigureAwait(false)) or the extension ConfigureAwait(false) on the stream in await foreach; these return ConfiguredAsyncDisposable/ConfiguredCancelableAsyncEnumerable wrappers. Forgetting to await disposal (using plain using on an async-only resource) is a compile error; using sync using on a type that has both silently loses the async flush behaviour.

Example

await using var conn = new SqlConnection(cs);
await conn.OpenAsync(ct);
await using (var tx = await conn.BeginTransactionAsync(ct).ConfigureAwait(false))
{
    await WriteAsync(conn, tx, ct).ConfigureAwait(false);
    await tx.CommitAsync(ct).ConfigureAwait(false);
}   // DisposeAsync awaited, without context capture

Follow-ups

  • Can DisposeAsync take a CancellationToken? — No; disposal should complete; cancel earlier operations instead.
  • Should DisposeAsync throw? — Avoid it; it masks the original exception in await using.
  • How does DI handle IAsyncDisposable? — The container disposes scopes with DisposeAsync if you use await using var scope = ...CreateAsyncScope(); a sync scope dispose on an async-only service throws.

Common wrong answer

"using works for everything; DisposeAsync is optional." A type implementing only IAsyncDisposable does not compile with sync using, and for dual types the sync path may block or skip a flush.

seniorWhen is IAsyncEnumerable<T> the wrong choice?

Answer

When the items are cheap and numerous and the source is already in memory: per-item MoveNextAsync is a virtual call plus a ValueTask<bool> check, far more than a synchronous enumerator, so summing a million cached numbers through an async stream is measurably slower than IEnumerable. When the consumer needs random access, counting or re-enumeration, a materialised collection is simpler. When you need push semantics, multiple consumers, or a buffer between stages, a Channel or Rx fits better. Across service boundaries, an async stream maps naturally to gRPC server streaming or NDJSON, but not to a request/response REST call, where paging is the honest shape. A good rule: async streams where each item involves I/O or where memory matters; otherwise a Task of a collection.

Example

// Overkill: everything is already in memory
public async IAsyncEnumerable<int> NumbersAsync() { foreach (var n in _cached) yield return n; }

// Better: one await for the load, then a plain collection
public async Task<IReadOnlyList<int>> NumbersAsync(CancellationToken ct) => await LoadAsync(ct);

Follow-ups

  • How big is the per-item cost? — Roughly tens of nanoseconds per item versus a few for a sync enumerator; irrelevant if the item involves I/O, dominant if not.
  • Is it OK for a public API to return IAsyncEnumerable from a paged REST call? — As a client-side convenience over paging, yes, if the doc says one request per page.
  • How does gRPC map it? — Server streaming methods return IAsyncStreamReader, easily wrapped as an async stream with ReadAllAsync.

Common wrong answer

"Always return IAsyncEnumerable for collections; it's more scalable." Blanket answers get the per-item overhead follow-up.

Once the basics are verified, coding rounds turn into "limit this to 10 at a time", "make this initialise once", "bridge this callback API": the coordination primitives. midLimit N concurrent async operations over a collection: SemaphoreSlim or Parallel.ForEachAsync?

Answer

For "process every item with at most N in flight", Parallel.ForEachAsync (.NET 6) is the modern answer: it takes MaxDegreeOfParallelism and a CancellationToken in ParallelOptions, pulls items lazily from an IEnumerable or IAsyncEnumerable, and stops on the first exception (cancelling the rest and aggregating). Use SemaphoreSlim when the limit must span multiple call sites or the lifetime of a service (e.g. "at most 20 concurrent calls to the pricing API from anywhere in the process"), or when you need results as they finish. Never use Parallel.ForEach (sync) with async lambdas: that is async void. Pick the number from downstream capacity, not from core count, because this is I/O-bound.

Example

await Parallel.ForEachAsync(urls,
    new ParallelOptions { MaxDegreeOfParallelism = 16, CancellationToken = ct },
    async (url, token) => results[url] = await _http.GetStringAsync(url, token));

// Process-wide limit shared by many callers
private static readonly SemaphoreSlim s_pricing = new(20, 20);
public async Task<Price> GetPriceAsync(Sku sku, CancellationToken ct)
{
    await s_pricing.WaitAsync(ct);
    try { return await _pricing.GetAsync(sku, ct); }
    finally { s_pricing.Release(); }
}

Follow-ups

  • What is the default MaxDegreeOfParallelism? — Environment.ProcessorCount, which is wrong for I/O-bound work; set it explicitly.
  • How does ForEachAsync handle one failure? — It cancels the loop's token, waits for in-flight bodies, and throws (an AggregateException when multiple failed).
  • Where does the throttle belong architecturally? — At the client wrapper for the dependency, so every caller shares it; not in each feature.

Common wrong answer

"Select(...).ToList() and WhenAll" with no limit, or Parallel.ForEach with an async lambda. Both are unbounded in different ways.

seniorExplain Channel<T>: bounded versus unbounded, options, completion and error propagation.

Answer

System.Threading.Channels (.NET Core 3.0) is the async producer/consumer primitive. Channel.CreateBounded<T>(capacity) gives back-pressure via WriteAsync awaiting when full, with FullMode alternatives (Wait, DropNewest, DropOldest, DropWrite) and an optional callback for dropped items; CreateUnbounded never blocks the writer and so never applies back-pressure. SingleReader/SingleWriter enable faster lock-free implementations. The writer signals end-of-stream with Complete() or Complete(exception); readers see the end from WaitToReadAsync returning false, from ReadAllAsync finishing, or from Reader.Completion, which faults with the exception. Channels are in-process only; the moment you need durability or cross-process fan-out, that is a queue.

Example

public sealed class WorkQueue<T>
{
    private readonly Channel<T> _ch = Channel.CreateBounded<T>(new BoundedChannelOptions(500)
        { FullMode = BoundedChannelFullMode.Wait, SingleReader = true });

    public ValueTask EnqueueAsync(T item, CancellationToken ct) => _ch.Writer.WriteAsync(item, ct);
    public IAsyncEnumerable<T> DequeueAllAsync(CancellationToken ct) => _ch.Reader.ReadAllAsync(ct);
    public void Shutdown(Exception? error = null) => _ch.Writer.TryComplete(error);
}

Follow-ups

  • What does TryWrite do on a full bounded channel? — Returns false (or drops per FullMode); use it on paths that must never wait, with a metric.
  • Why not BufferBlock from TPL Dataflow? — Dataflow is heavier and older; channels are the recommended primitive, Dataflow is for pipelines with transforms and linking.
  • How do you drain on shutdown? — Complete the writer, let the consumer finish ReadAllAsync, bounded by the host's shutdown timeout (unit 10).

Common wrong answer

Reaching for ConcurrentQueue + a polling loop with Task.Delay. It works, wastes CPU, has no completion semantics and no back-pressure.

seniorWhat is TaskCompletionSource for, and why does RunContinuationsAsynchronously matter?

Answer

TaskCompletionSource<T> creates a Task whose completion you control: SetResult/SetException/SetCanceled (or the Try* variants when several parties may race). It bridges callback-, event- or message-based APIs into TAP: a request/response correlation table over a socket, a "wait until the service is ready" signal, a test fixture. By default, completing the TCS runs the awaiting continuations synchronously on the completing thread; if that thread is an I/O thread, holds a lock, or is inside a loop, arbitrary user code now runs there, causing deadlocks and stack growth. TaskCreationOptions.RunContinuationsAsynchronously (.NET 4.6) forces continuations onto the thread pool; almost every production TCS should use it. Since .NET 5 there is a non-generic TaskCompletionSource, and .NET 9 added SetFromTask/TrySetFromTask to copy another task's outcome.

Example

private readonly ConcurrentDictionary<int, TaskCompletionSource<Response>> _pending = new();

public Task<Response> SendAsync(Request r, CancellationToken ct)
{
    var tcs = new TaskCompletionSource<Response>(TaskCreationOptions.RunContinuationsAsynchronously);
    _pending[r.Id] = tcs;
    ct.Register(() => { if (_pending.TryRemove(r.Id, out var t)) t.TrySetCanceled(ct); });
    _socket.Send(r);
    return tcs.Task;
}

// on the receive loop (an I/O thread): user continuations must not run here
void OnMessage(Response resp) { if (_pending.TryRemove(resp.Id, out var tcs)) tcs.TrySetResult(resp); }

Follow-ups

  • Why TrySet* instead of Set*? — Set* throws if already completed; with cancellation racing a response, both sides may try.
  • What happens if nobody completes the TCS? — The Task never completes and everything awaiting it leaks; always pair with a timeout or cancellation.
  • How does this differ from IValueTaskSource? — TCS allocates a Task per operation and is safe to await many times; IValueTaskSource is pooled and single-consumer.

Common wrong answer

Creating the TCS without RunContinuationsAsynchronously "because it's the default". The interviewer is waiting for that flag.

seniorHow do AsyncLocal<T> and ExecutionContext flow through async code?

Answer

ExecutionContext is the ambient state the runtime carries across asynchronous boundaries: AsyncLocal<T> values, plus security/impersonation context on Windows. At every await, Task.Run, ThreadPool.QueueUserWorkItem and CancellationToken.Register, the current ExecutionContext is captured and restored when the continuation runs, regardless of thread or of ConfigureAwait. Flow is copy-on-write and one-directional: a value set inside an async method after an await is visible in that method and its callees, but not in the caller after it returns, because the caller's context was captured earlier. That makes AsyncLocal right for read-mostly ambient data (correlation ids, logging scopes, current tenant) and wrong for "return values via ambient state". ExecutionContext.SuppressFlow() stops flow for fire-and-forget work that must not inherit request state; the Unsafe* APIs skip capture for performance. .NET 11's runtime avoids the capture/restore cost entirely when no AsyncLocal state is present.

Example

static readonly AsyncLocal<string?> CorrelationId = new();

async Task HandleAsync()
{
    CorrelationId.Value = "req-42";
    await Task.Delay(10);              // still "req-42" on whatever thread resumes
    await ChildAsync();                // sees "req-42"; its own writes don't come back
    Console.WriteLine(CorrelationId.Value);   // "req-42", not "child"
}
async Task ChildAsync() { CorrelationId.Value = "child"; await Task.Yield(); }

Follow-ups

  • How do logging scopes use this? — ILogger.BeginScope in Microsoft.Extensions.Logging stores the scope stack in an AsyncLocal; scopes therefore follow the async flow, not the thread.
  • Does ConfigureAwait(false) stop AsyncLocal flow? — No; that is SynchronizationContext, a different mechanism.
  • What is the performance cost? — A capture per await when any AsyncLocal has been set in the flow; mutation of an AsyncLocal copies the context map, so avoid setting them in tight loops.

Common wrong answer

"AsyncLocal is like ThreadStatic but for tasks; changes are visible to the caller afterwards." The one-way flow is the whole point of the question.

midHow do you initialise something asynchronously exactly once (async lazy)?

Answer

Wrap the initialisation Task in Lazy<Task<T>>: the first access starts the task, later accesses await the same Task, and Task's multi-await semantics make it thread-safe. Pitfalls: with the default LazyThreadSafetyMode.ExecutionAndPublication a failed initialisation is cached forever, so for retryable failures either use a factory that replaces the Lazy on fault or an "AsyncLazy" that resets on failure; the init lambda starts on the accessing thread (wrap in Task.Run only if it has a long synchronous prefix on a UI thread); and cancellation of one caller must not cancel the shared init, so the shared Task should not take a per-caller token (await it via WaitAsync(ct) instead). The same pattern solves cache stampedes: a per-key Lazy<Task<T>> inside a ConcurrentDictionary ensures single-flight loading.

Example

private Lazy<Task<Schema>> _schema = NewLazy();
private Lazy<Task<Schema>> NewLazy() => new(() => LoadSchemaAsync(), LazyThreadSafetyMode.ExecutionAndPublication);

public async Task<Schema> GetSchemaAsync(CancellationToken ct)
{
    var lazy = _schema;
    try { return await lazy.Value.WaitAsync(ct); }        // per-caller cancellation only stops waiting
    catch (Exception) when (lazy.Value.IsFaulted)
    {
        Interlocked.CompareExchange(ref _schema, NewLazy(), lazy);   // allow retry next time
        throw;
    }
}

Follow-ups

  • Why not ConcurrentDictionary.GetOrAdd(key, k => LoadAsync(k)) directly? — The factory may run more than once concurrently; wrapping the value in Lazy makes the async load single-flight.
  • Is there a BCL AsyncLazy? — No; Lazy<Task<T>> is the idiom, and libraries such as Nito.AsyncEx or VS Threading provide richer ones.
  • What about ValueTask here? — Unsafe: multiple callers await the same value, so it must be a Task.

Common wrong answer

A double-checked if (_value == null) _value = await LoadAsync(); under a semaphore, which is fine, or without one, which races; the interviewer wants the "failure is cached" nuance too.

midHow do you run periodic work: PeriodicTimer, System.Threading.Timer, or a Task.Delay loop?

Answer

PeriodicTimer (.NET 6) is the modern choice for async periodic work: await timer.WaitForNextTickAsync(ct) in a loop gives one tick at a time, never overlaps executions (ticks are coalesced if the body is slow), is cancellable, and disposes cleanly. System.Threading.Timer fires a callback on the pool at fixed intervals regardless of whether the previous one finished, so slow work overlaps and callbacks become async void; it also needs the timer kept alive and disposed. A while (true) { await DoAsync(); await Task.Delay(period, ct); } loop is fine and drifts by the work duration, which is sometimes what you want. .NET 8 made PeriodicTimer.Period settable and added a TimeProvider overload for testability.

Example

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30), _timeProvider);
    while (await timer.WaitForNextTickAsync(stoppingToken))     // returns false on dispose; throws OCE on cancel
    {
        try { await SyncAsync(stoppingToken); }
        catch (Exception ex) when (ex is not OperationCanceledException) { _log.LogError(ex, "sync failed"); }
    }
}

Follow-ups

  • What if the body takes longer than the period? — The next tick is delivered immediately after; intermediate ticks are dropped, so there is never more than one execution in flight.
  • How do you test it? — Inject TimeProvider and use FakeTimeProvider.Advance() instead of waiting real seconds.
  • Why the try/catch inside the loop? — An unhandled exception ends ExecuteAsync, which stops the host by default since .NET 6.

Common wrong answer

"Use System.Threading.Timer with an async callback." That is async void with overlapping executions; a classic production bug.

midHow do you handle async work in constructors, properties and Dispose?

Answer

Constructors cannot be async, and blocking inside one is the deadlock/starvation pattern in disguise. Use a static async factory (public static async Task<Client> CreateAsync(...)) with a private constructor, or lazy initialisation on first use (Lazy<Task<T>>, previous question), or an explicit InitializeAsync that a hosted service calls at startup. Properties should not be async either (a property that returns a Task is a method in disguise); expose GetXAsync(). For disposal, implement IAsyncDisposable when cleanup awaits (flush, graceful close) and keep Dispose synchronous and non-blocking; in DI, register types with async cleanup and dispose scopes with CreateAsyncScope. For DI-created services that need async init, resolve them lazily or initialise in an IHostedService.StartAsync.

Example

public sealed class SearchClient : IAsyncDisposable
{
    private readonly Connection _conn;
    private SearchClient(Connection c) => _conn = c;

    public static async Task<SearchClient> CreateAsync(Uri endpoint, CancellationToken ct)
        => new(await Connection.OpenAsync(endpoint, ct));

    public ValueTask DisposeAsync() => _conn.CloseAsync();
}

Follow-ups

  • How does that fit DI's synchronous factories? — Register the factory result as a singleton created in StartAsync, or register Func<Task<T>>; DI containers are synchronous by design.
  • What about EF Core DbContext in a constructor? — Never query in a constructor; it runs during resolution on whatever thread asked.
  • Should Dispose call DisposeAsync().GetAwaiter().GetResult()? — Avoid; prefer a sync path that does not flush, or document that async disposal is required.

Common wrong answer

"Call .Result in the constructor; it only runs once." Once per instance, on DI resolution, possibly on a UI thread: exactly where it deadlocks.

seniorHow do you avoid races on shared state in async code without blocking?

Answer

Prefer designs where there is no shared mutable state: immutable snapshots swapped atomically with Interlocked.Exchange/Volatile.Write, per-request objects, or a single owner (a Channel consumer) that serialises mutations. For counters and flags use Interlocked. For collections use ConcurrentDictionary with the knowledge that GetOrAdd factories can run concurrently and AddOrUpdate delegates may be retried. When a critical section must span an await, use SemaphoreSlim(1,1) with WaitAsync; keep the awaited section short and never call out to unknown code under it. Remember that async makes interleaving points explicit (only at awaits), which is easier to reason about than preemptive threads, but a callback from an I/O thread still runs truly in parallel with your continuation.

Example

private Snapshot _current = Snapshot.Empty;      // immutable

public async Task RefreshAsync(CancellationToken ct)
{
    var next = await BuildSnapshotAsync(ct);      // no lock while loading
    Interlocked.Exchange(ref _current, next);     // atomic publish
}

public Snapshot Current => Volatile.Read(ref _current);

Follow-ups

  • Is lock still fine for short non-awaiting sections in async methods? — Yes; a lock that does not span an await is the cheapest option.
  • When do you need a memory barrier? — When publishing a reference read on another thread without a lock; Volatile/Interlocked provide it.
  • How does Blazor Server change this? — Its per-circuit SynchronizationContext serialises component code, so you mostly avoid locks there but must not touch component state from unrelated threads.

Common wrong answer

"Async code is single-threaded, so no synchronisation is needed." True only under a single-threaded SynchronizationContext, not in ASP.NET Core.

seniorDesign a producer/consumer that drains gracefully on cancellation.

Answer

Separate "stop accepting" from "stop processing". On shutdown, complete the channel writer so producers stop, then let the consumer keep reading until the channel is empty, using a token that only fires after a grace period; anything still unprocessed when that token fires is either persisted for later or reported as lost with a count. Consumers process each item with its own bounded timeout; an item that fails is dead-lettered, not retried forever. Expose metrics for queue depth, in-flight count and drained-on-shutdown count. The host's ShutdownTimeout must exceed the grace period, and the orchestrator's termination grace period must exceed the host's, or the drain is cut off by SIGKILL.

Example

public async Task StopAsync(CancellationToken hardStop)   // hardStop = host shutdown token
{
    _queue.Writer.TryComplete();                                     // 1. stop accepting
    using var grace = CancellationTokenSource.CreateLinkedTokenSource(hardStop);
    grace.CancelAfter(TimeSpan.FromSeconds(20));                     // 2. bounded drain
    try { await _consumerTask.WaitAsync(grace.Token); }              // consumer exits when the queue is empty
    catch (OperationCanceledException)
    {
        _log.LogWarning("drain aborted with {Count} items pending", _queue.Reader.Count);
    }
}

Follow-ups

  • Why not pass the host token straight to the consumer loop? — It would abort in-flight items at the first signal instead of draining.
  • How do you make drained items durable? — Do not keep them only in memory: use an outbox table or a broker; the in-memory channel is a buffer, not a queue.
  • How does this interact with Kubernetes? — SIGTERM → ApplicationStopping; set terminationGracePeriodSeconds above HostOptions.ShutdownTimeout (default 30 s).

Common wrong answer

Cancelling everything with one token and calling it graceful. The two-phase stop is the discriminator.

9Internals: state machines to Runtime Async

asked: sometimesnice to know · senior+ differentiator8 questions · senior → principal

Internals questions are how interviewers find the top of the ladder. Nobody is rejected for not knowing the builder's method names, but a candidate who can sketch the state machine, explain the awaiter pattern, and describe what .NET 11's Runtime Async changes (and does not change) is remembered.

Senior: state machine shape, awaiter pattern, what is boxed when, ExecutionContext versus SynchronizationContext capture. Principal: Runtime Async status and its consequences for library and platform strategy, custom awaitables, continuation scheduling.

Official docs: How async/await really works in C# (Stephen Toub) What's new in the .NET 11 runtime: Runtime Async Task-like types (C# 7 proposal)
seniorHow does the C# compiler transform an async method?

Answer

The compiler generates a struct (class in Debug) implementing IAsyncStateMachine with fields for the method's parameters, hoisted locals, a state integer, the builder (AsyncTaskMethodBuilder<T>, AsyncValueTaskMethodBuilder<T>, or a custom one), and one field per distinct awaiter type. The method body becomes MoveNext(): a switch on the state that jumps to the right resume point, with each await turned into "get awaiter; if not completed, store state and awaiter, call builder.AwaitUnsafeOnCompleted(ref awaiter, ref this), return; else fall through to GetResult()". The whole body is wrapped in a try/catch that routes exceptions to builder.SetException. The original method just creates the struct, calls builder.Start(ref sm) (which runs MoveNext synchronously) and returns builder.Task. The awaiter's continuation is a delegate that calls MoveNext again.

Example

// Source
async Task<int> F() { var x = await A(); return x + 1; }

// Generated (abridged)
struct FStateMachine : IAsyncStateMachine {
    public int state; public AsyncTaskMethodBuilder<int> builder; TaskAwaiter<int> aw; int x;
    public void MoveNext() {
        try {
            if (state != 0) { aw = A().GetAwaiter(); if (!aw.IsCompleted) { state = 0; builder.AwaitUnsafeOnCompleted(ref aw, ref this); return; } }
            else state = -1;
            x = aw.GetResult(); aw = default;
            builder.SetResult(x + 1);
        } catch (Exception e) { state = -2; builder.SetException(e); }
    }
    public void SetStateMachine(IAsyncStateMachine sm) => builder.SetStateMachine(sm);
}

Follow-ups

  • Why is state -1 while running and -2 when done? — Conventions: non-negative values index resume points; -1 running; -2 completed.
  • What does SetStateMachine do? — Lets the builder store a reference to the boxed copy so later MoveNext calls hit the heap instance, not a stale stack copy.
  • How do local variables survive? — Locals live across awaits are hoisted into fields; ones that do not are left as real locals in MoveNext.

Common wrong answer

"The compiler wraps the rest of the method in a callback closure." That describes JavaScript promises pre-async; C# generates a resumable state machine with an explicit state field.

seniorWhat is the awaiter pattern, and what can you await?

Answer

await x is pattern-based, not type-based: x needs a GetAwaiter() method (instance or extension) returning a type with a bool IsCompleted property, a GetResult() method (void or T), and implementing INotifyCompletion (OnCompleted(Action)); optionally ICriticalNotifyCompletion (UnsafeOnCompleted, which skips ExecutionContext capture because the builder handles it). That is why Task, ValueTask, YieldAwaitable, ConfiguredTaskAwaitable and third-party types are all awaitable, and why you can add an extension GetAwaiter to make anything awaitable: a TimeSpan, a CancellationToken, a Process. The builder always prefers UnsafeOnCompleted when available, so custom awaiters should implement both interfaces.

Example

public static class AwaitExtensions
{
    // await TimeSpan.FromSeconds(1);
    public static TaskAwaiter GetAwaiter(this TimeSpan t) => Task.Delay(t).GetAwaiter();

    // await cancellationToken;  (completes when cancelled)
    public static TaskAwaiter GetAwaiter(this CancellationToken ct)
    {
        var tcs = new TaskCompletionSource(TaskCreationOptions.RunContinuationsAsynchronously);
        ct.Register(static s => ((TaskCompletionSource)s!).TrySetResult(), tcs);
        return tcs.Task.GetAwaiter();
    }
}

Follow-ups

  • Why does ConfigureAwait return a different type? — ConfiguredTaskAwaitable's awaiter carries the "don't capture context" flag; the pattern lets the same await syntax work.
  • Where is the SynchronizationContext captured in this pattern? — Inside the awaiter's OnCompleted/UnsafeOnCompleted, not by the compiler.
  • What must GetResult do on failure? — Rethrow the stored exception (typically via ExceptionDispatchInfo) and on cancellation throw OCE/TCE.

Common wrong answer

"You can only await Task and ValueTask." The extension GetAwaiter trick is the expected senior-level detail.

seniorWhy is the state machine a struct, and what exactly gets boxed on first suspension?

Answer

A struct lets the synchronous fast path run entirely on the stack: if the method never suspends, no heap object is created for the state machine. On the first incomplete await, AwaitUnsafeOnCompleted boxes the struct into an AsyncStateMachineBox<TStateMachine>, a class that, since .NET Core 2.1, derives from Task<TResult>: the box is the returned Task, holds the state machine by value, caches the MoveNext delegate, and stores the captured ExecutionContext. So a suspended async method costs exactly one allocation for the state machine/task pair, and later suspensions reuse it. In Debug builds the compiler emits a class instead, which allocates on every call but makes locals inspectable; that is why allocation measurements must be taken in Release. Runtime Async in .NET 11 removes the compiler struct altogether and allocates a continuation object only at suspension, reusing it where possible.

Example

// .NET Framework 4.x (4+ allocations on suspension):
//   Task<T> + boxed state machine + MoveNextRunner + Action delegate (+ ExecutionContext copy)
// .NET Core 2.1 → .NET 10 (1 allocation):
//   AsyncStateMachineBox<TStateMachine> : Task<T>  { TStateMachine StateMachine; Action MoveNextAction; ExecutionContext Context; }
// .NET 11 runtime-async (preview): no compiler state machine; runtime continuation objects, cached/reused

Follow-ups

  • What does SetStateMachine have to do with boxing? — After boxing, the builder must point at the heap copy; older runtimes used it, modern ones mostly do not need it because the box owns the builder.
  • Can the box be pooled? — For ValueTask-returning methods via PoolingAsyncValueTaskMethodBuilder; not for Task, which must remain valid indefinitely.
  • Does async void allocate a Task? — No Task is returned, but the state machine is still boxed on suspension.

Common wrong answer

"The state machine is always heap-allocated at method entry." Only in Debug; the struct-on-stack fast path is the design.

seniorWhat is captured at an await: ExecutionContext versus SynchronizationContext?

Answer

Two independent things. ExecutionContext (AsyncLocal values, Windows security context) is captured by the async method builder when it hands the continuation to the awaiter and restored around MoveNext; it cannot be turned off by ConfigureAwait, only by ExecutionContext.SuppressFlow or the Unsafe* APIs. SynchronizationContext/TaskScheduler are captured by the Task awaiter's OnCompleted and determine where the continuation runs; ConfigureAwait(false) disables exactly this. The confusion is common because both are "context"; the test question is "does ConfigureAwait(false) lose my AsyncLocal correlation id?" and the answer is no. .NET 11 adds a runtime optimisation that skips ExecutionContext capture/restore when no AsyncLocal state has been set in the current flow, which is why apps that use AsyncLocal sparingly get cheaper awaits.

Example

static readonly AsyncLocal<int> Tenant = new();
Tenant.Value = 7;
await _http.GetAsync(url).ConfigureAwait(false);
Console.WriteLine(Tenant.Value);        // 7: ExecutionContext flowed
Console.WriteLine(SynchronizationContext.Current is null);   // true on a pool thread: SC not restored

Follow-ups

  • What is the cost of ExecutionContext capture? — A reference copy when the context is the default; a small object when AsyncLocals are set, plus restore on each continuation.
  • Does Task.Run flow ExecutionContext? — Yes; UnsafeQueueUserWorkItem does not.
  • What does a security-context capture mean on Linux? — Nothing; impersonation is Windows-only, so ExecutionContext there is effectively the AsyncLocal map.

Common wrong answer

"ConfigureAwait(false) drops all context, including AsyncLocal/logging scopes." It drops only the SynchronizationContext.

principalWhat is Runtime Async (.NET 10 experiment, .NET 11 preview), what changes, and what does not?

Answer

Runtime Async moves async-method implementation from the C# compiler into the runtime and JIT. Instead of a state-machine struct and builder, the compiler emits a normal-looking method flagged [MethodImpl(MethodImplOptions.Async)] whose awaits become calls to System.Runtime.CompilerServices.AsyncHelpers.Await(...); the JIT generates suspension and resumption code, saving only the live locals into a continuation object at actual suspension points and reusing continuations aggressively. Benefits documented for .NET 11 Preview 7: live stack traces show the real call chain (13 frames down to 5 in the docs' three-level example), breakpoints and stepping work through awaits, async methods now go through tiered compilation, tail-merged suspension points shrink code, factory intrinsics fold Task.FromResult/CompletedTask, and ExecutionContext capture is skipped when there is nothing to restore. In .NET 10 it was an experiment (EnablePreviewFeatures, Features=runtime-async=on, DOTNET_RuntimeAsync=1). In .NET 11 previews the runtime support is on by default, the runtime libraries themselves are compiled with it, a net11.0 project opts in with just <Features>runtime-async=on</Features> (no EnablePreviewFeatures), the environment variables were removed, and <UseRuntimeAsync>false</UseRuntimeAsync> opts out. What does not change: source code, Task/ValueTask semantics, awaiter contracts, cancellation, ConfigureAwait, or the thread-pool model; compiler-generated and runtime-async methods interoperate freely.

Example

<!-- .NET 11 Preview 7 project opting in -->
<PropertyGroup>
  <TargetFramework>net11.0</TargetFramework>
  <Features>$(Features);runtime-async=on</Features>
  <!-- <UseRuntimeAsync>false</UseRuntimeAsync>  opt a project out -->
</PropertyGroup>
// What the compiler emits under runtime-async (conceptually)
[MethodImpl(MethodImplOptions.Async)]
static Task<int> GetLengthAsync(HttpClient c, string url)
{
    HttpResponseMessage r = AsyncHelpers.Await(c.GetAsync(url));   // JIT-managed suspension point
    return Task.FromResult((int)r.Content.Headers.ContentLength.GetValueOrDefault());
}

Follow-ups

  • Does it help exception stack traces? — Not visibly: those were already cleaned up via ExceptionDispatchInfo; the gain is in live stacks seen by profilers, debuggers and new StackTrace().
  • What should a team do today? — Nothing in source; on .NET 11 previews, test with the feature on in a canary, compare allocation and p99, and watch for library issues; keep the opt-out handy.
  • Does NativeAOT support it? — .NET 11 previews added NativeAOT and ReadyToRun support; Mono/WebAssembly are not covered by the CoreCLR implementation.
  • What happens to PoolingAsyncValueTaskMethodBuilder and custom builders? — Methods that are already pooled opt out of runtime-async; custom task-like types keep using the compiler path.

Common wrong answer

"Runtime async makes async free / removes the need for ValueTask / is on by default for my app in .NET 10." It is opt-in per project in .NET 11 previews, experimental in .NET 10, and it reduces overhead rather than eliminating it.

principalHow and why would you build a custom awaitable or a custom async method builder?

Answer

Custom awaitables (a type or extension exposing GetAwaiter) are cheap and useful for readability or for adapting primitives: awaiting a SemaphoreSlim lease that releases on dispose, awaiting a Process exit, or a SwitchTo(scheduler) awaitable that moves execution to a specific context (the JoinableTaskFactory idea). Custom async method builders (via [AsyncMethodBuilder] on a task-like type or on a method since C# 10) are rare and heavier: they let you change how the state machine is hosted and completed, which is how UniTask avoids allocations in Unity, how PoolingAsyncValueTaskMethodBuilder pools boxes, and how some frameworks inject tracing around every async method. The bar for writing one in application code is very high: the builder contract is subtle (ExecutionContext handling, exception routing, SetStateMachine), and Runtime Async will make compiler builders a legacy path over time.

Example

// A small custom awaitable: switch the rest of the method to a dedicated scheduler
public readonly struct SwitchTo(TaskScheduler scheduler) : ICriticalNotifyCompletion
{
    public SwitchTo GetAwaiter() => this;
    public bool IsCompleted => TaskScheduler.Current == scheduler;
    public void GetResult() { }
    public void OnCompleted(Action c) => Task.Factory.StartNew(c, CancellationToken.None, TaskCreationOptions.DenyChildAttach, scheduler);
    public void UnsafeOnCompleted(Action c) => OnCompleted(c);
}

// usage
await new SwitchTo(_exclusiveScheduler);
MutateState();   // now running on the exclusive scheduler

Follow-ups

  • What must a builder expose? — Create(), Start, SetStateMachine, SetResult, SetException, AwaitOnCompleted, AwaitUnsafeOnCompleted, and a Task property.
  • Why is the awaitable a readonly struct? — To avoid allocations; the builder handles boxing only if it needs to store the awaiter.
  • Could a builder implement structured concurrency? — Partly (tracking child tasks), but without language support it leaks; teams usually do it with explicit scopes instead.

Common wrong answer

"Custom builders are how you make async faster in general." They are a niche tool; the principal answer explains why you almost never write one.

principalHow does a Task complete and run its continuations, inline or queued?

Answer

A Task stores its continuation(s) in a single field that is either null, one continuation object, or a list. When the Task transitions to a final state (on whatever thread called SetResult, or the I/O thread that observed completion), it walks that list. Each continuation may run inline on the completing thread if it was registered with ExecuteSynchronously semantics (which await-based continuations are, subject to a stack-depth check and the current scheduler matching) or queued to the pool/scheduler otherwise. TaskCreationOptions.RunContinuationsAsynchronously on a TCS forces queuing for all continuations of that Task, and TaskContinuationOptions.RunContinuationsAsynchronously does the same per continuation. The trade-off: inline is faster (no queue hop) but runs unknown code on the completer's thread, holding its locks and consuming its stack; frameworks therefore force asynchronous continuations at boundaries and let ordinary awaits inline.

Example

// Inline: fast, but runs on the thread that calls SetResult
var tcs1 = new TaskCompletionSource<int>();
_ = Consume(tcs1.Task);       // its continuation will run inside tcs1.SetResult(...)
tcs1.SetResult(1);            // if Consume's continuation blocks, this caller is stuck

// Queued: the continuation is dispatched to the thread pool
var tcs2 = new TaskCompletionSource<int>(TaskCreationOptions.RunContinuationsAsynchronously);

Follow-ups

  • How does the runtime avoid stack overflows from chained inline continuations? — It checks remaining stack (RuntimeHelpers.EnsureSufficientExecutionStack-style) and falls back to queuing.
  • Why does Task.Delay's continuation not run on the timer thread? — The timer's completion queues to the pool precisely to keep the shared timer thread free.
  • What is the ordering guarantee for multiple continuations? — None documented; do not rely on registration order.

Common wrong answer

"Continuations always run on the thread pool." Inline execution is the default for awaits and the source of several classic deadlocks.

seniorHow do debuggers and diagnostics reconstruct the "async call stack"?

Answer

There is no physical async call stack: once a method suspends, its caller has returned. Tools rebuild a logical one by walking continuation links: each state-machine box holds the awaiter, the awaiter holds the Task being awaited, and that Task's continuation list points to the next box. Visual Studio's Tasks window, Parallel Stacks (async view), and dotnet-dump's dumpasync command traverse those links from live objects in the heap, which is why they work from a memory dump and show what each async method is waiting on. Exception stack traces use a different mechanism (ExceptionDispatchInfo appending and frame cleanup). Runtime Async in .NET 11 makes the live stack itself meaningful (real methods as frames) and the runtime's async profiler emits one event model for both implementations, which improves profiler causality without dumps.

Example

dotnet-dump analyze core.dmp
> dumpasync -stats                 # counts of state machines by type: what is everything waiting on?
> dumpasync -tasks -completed:false # each incomplete async method with its awaited task and continuation chain

Follow-ups

  • Why is a chain broken at ContinueWith or fire-and-forget? — No state-machine box links the two sides; correlation ids in logs are the fallback.
  • What does "Activity" (System.Diagnostics) add? — Distributed-tracing spans flow via AsyncLocal, giving causality across services, not just within a process.
  • How do you find a leaked async operation? — dumpasync across two dumps: state machines that persist between them and are never completed.

Common wrong answer

"The debugger shows the real stack, which includes the caller." The caller returned long ago; the logical stack is reconstructed from heap links.

asked: sometimescritical6 questions · mid → senior

Most async bugs that reach production are lifetime bugs: work that outlives its request, a hosted service that silently died, a shutdown that lost messages. Interviewers who run services ask these to see if you have been paged for them.

Mid level: why Task.Run in a request is wrong and what to do instead. Senior: BackgroundService exception behaviour, graceful shutdown timing, scoped services in background work, captured HttpContext. Principal: the policy (what is allowed to be fire-and-forget at all) and the supervision design.

Official docs: Background tasks with hosted services Worker services HostOptions
midHow do you do fire-and-forget safely in ASP.NET Core, and why not Task.Run in the request?

Answer

Task.Run (or an un-awaited call) inside a request has no owner: exceptions are unobserved, the DI scope and HttpContext it captured are disposed when the response ends (so DbContext throws ObjectDisposedException), and on shutdown the host does not know to wait for it, so work is lost. The safe pattern is a queue plus a supervised consumer: the request enqueues a message into a bounded Channel<T> (or a durable broker for anything that must survive a restart), and a BackgroundService dequeues, creates its own scope, does the work with the host's stopping token, and logs failures. That gives back-pressure, a shutdown story, and observability. If the work must be durable, the in-memory channel is the wrong tool: write an outbox row in the same transaction as the request and let a worker process it.

Example

app.MapPost("/signup", async (Signup s, IUserService users, Channel<WelcomeEmail> queue, CancellationToken ct) =>
{
    var id = await users.CreateAsync(s, ct);
    await queue.Writer.WriteAsync(new WelcomeEmail(id), ct);   // bounded: applies back-pressure
    return Results.Accepted();
});

sealed class EmailWorker(Channel<WelcomeEmail> queue, IServiceScopeFactory scopes, ILogger<EmailWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stop)
    {
        await foreach (var job in queue.Reader.ReadAllAsync(stop))
        {
            await using var scope = scopes.CreateAsyncScope();
            try { await scope.ServiceProvider.GetRequiredService<IMailer>().SendAsync(job, stop); }
            catch (Exception ex) when (ex is not OperationCanceledException) { log.LogError(ex, "email {Id} failed", job.UserId); }
        }
    }
}

Follow-ups

  • What if the process dies with 500 items in the channel? — They are gone; that is the durability boundary, so decide per use case whether an outbox/broker is needed.
  • Is IHostApplicationLifetime.ApplicationStopping the right token for the consumer? — ExecuteAsync's stoppingToken is derived from it; use the two-phase drain from unit 8 if you must finish in-flight items.
  • Where do libraries like Hangfire fit? — They are the durable, scheduled version of this pattern; use them when you need persistence, retries and dashboards.

Common wrong answer

"_ = Task.Run(() => SendEmailAsync(...)) with a try/catch inside." It solves the crash and nothing else: scope disposal, shutdown loss and back-pressure remain.

seniorWhat happens when BackgroundService.ExecuteAsync throws, or completes synchronously?

Answer

Since .NET 6 an unhandled exception in ExecuteAsync is logged and, by default (HostOptions.BackgroundServiceExceptionBehavior.StopHost), stops the host, which is the safe default: before .NET 6 the service died silently and the process kept running with a dead worker. You can switch to Ignore, but then you own the monitoring. A second trap is the synchronous prefix: the host calls StartAsync on hosted services sequentially, and BackgroundService.StartAsync simply calls ExecuteAsync and stores the Task; if ExecuteAsync runs a long synchronous loop before its first await, host startup blocks (Kestrel never starts listening). Yield early (await Task.Yield() or an initial await). .NET 8 added HostOptions.ServicesStartConcurrently/ServicesStopConcurrently for parallel start/stop.

Example

builder.Services.Configure<HostOptions>(o =>
{
    o.BackgroundServiceExceptionBehavior = BackgroundServiceExceptionBehavior.StopHost; // default since .NET 6
    o.ShutdownTimeout = TimeSpan.FromSeconds(30);
    o.ServicesStartConcurrently = true;    // .NET 8
});

protected override async Task ExecuteAsync(CancellationToken stop)
{
    await Task.Yield();                    // return to the host before doing anything heavy
    while (!stop.IsCancellationRequested)
    {
        try { await ProcessOnceAsync(stop); }
        catch (Exception ex) when (ex is not OperationCanceledException) { _log.LogError(ex, "iteration failed"); }
    }
}

Follow-ups

  • Should the loop catch everything? — Catch and log per iteration so one poison message does not stop the host; let truly fatal states (config missing) propagate and stop it.
  • What does StopAsync do in BackgroundService? — Cancels the stopping token and awaits ExecuteAsync's Task until the host's shutdown timeout elapses.
  • How do you health-check a background service? — Have it publish a heartbeat timestamp and add an IHealthCheck that fails when it is stale.

Common wrong answer

"An exception in ExecuteAsync just kills that background task; the app keeps running." True before .NET 6; the default since then is to stop the host, and the senior answer states which behaviour they want and why.

seniorWalk through graceful shutdown of an ASP.NET Core / worker host and where async work gets cut off.

Answer

SIGTERM (or Ctrl+C) triggers IHostApplicationLifetime.ApplicationStopping. Kestrel stops accepting new connections and lets in-flight requests finish (they see RequestAborted only if the client drops). Hosted services' StopAsync are called (in reverse registration order, or concurrently with the .NET 8 option) with a token that fires when HostOptions.ShutdownTimeout (default 30 s) elapses; BackgroundService.StopAsync cancels its stopping token and awaits ExecuteAsync. Then ApplicationStopped fires and the DI container disposes singletons. Anything still running when the timeout expires is abandoned, and once the process exits, killed. Under Kubernetes the pod's terminationGracePeriodSeconds (default 30 s) must exceed the host timeout plus pre-stop hooks, or SIGKILL arrives mid-drain. Design consequence: every long async operation needs a bounded drain and a durable fallback.

Example

SIGTERM
 └─ ApplicationStopping (CTS cancelled; callbacks run synchronously here)
     ├─ Kestrel: stop accepting, drain in-flight requests
     ├─ IHostedService.StopAsync(...) for each service (ShutdownTimeout token, default 30 s)
     │    └─ BackgroundService: cancel stoppingToken → await ExecuteAsync task
     └─ ApplicationStopped → dispose container → process exit
Kubernetes: terminationGracePeriodSeconds must be > ShutdownTimeout (+ preStop sleep)

Follow-ups

  • Why add a preStop sleep in Kubernetes? — Endpoint removal is asynchronous; a few seconds' sleep lets load balancers stop routing before the app stops accepting.
  • What if a StopAsync blocks? — It delays everything after it until the timeout; keep StopAsync cooperative and bounded.
  • How do you test shutdown? — Integration test that starts the host, enqueues work, calls StopAsync, and asserts the drain completed within the timeout.

Common wrong answer

"The host waits for all tasks to finish before exiting." It waits for hosted services up to a timeout; unowned tasks are never waited for.

midHow do you use scoped services (e.g. DbContext) from background async work?

Answer

Scoped services are tied to a DI scope; in a request that scope is the request. Background work runs outside any request, so a singleton BackgroundService cannot take a scoped service in its constructor (the container throws in validation, or you get a captive dependency). Inject IServiceScopeFactory and create a scope per unit of work with await using var scope = _scopes.CreateAsyncScope(), resolve the scoped services from scope.ServiceProvider, and dispose the scope when the unit finishes. Never capture a request's scoped service into background work: the request's scope is disposed when the response completes, so the captured DbContext is dead by the time the work runs. One scope per message also keeps DbContext change tracking bounded.

Example

sealed class Reconciler(IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stop)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));
        while (await timer.WaitForNextTickAsync(stop))
        {
            await using var scope = scopes.CreateAsyncScope();        // new DbContext per run
            var db = scope.ServiceProvider.GetRequiredService<AppDb>();
            await ReconcileAsync(db, stop);
        }
    }
}

Follow-ups

  • Why CreateAsyncScope rather than CreateScope? — It disposes IAsyncDisposable services asynchronously; a sync scope dispose on an async-only service throws.
  • Can two concurrent jobs share one scope? — Not if they share a DbContext; it is not thread-safe. One scope per concurrent unit.
  • What about IHttpContextAccessor in background work? — It returns null (or a disposed context); pass the data you need explicitly.

Common wrong answer

"Inject the DbContext into the hosted service and use it in the loop." Captive dependency: one DbContext for the process lifetime, growing change tracker, no concurrency safety.

seniorHow should async work at startup be handled (warm-up, migrations, cache priming)?

Answer

Options, each with a trade-off. Run it in Program.cs before app.RunAsync(): simple, blocks readiness until done (good for migrations you must not serve without). Run it in an IHostedService.StartAsync: sequential with other services by default, blocks the host's start; use when readiness depends on it and you want DI. Run it in a BackgroundService and gate readiness with a health check: the app starts listening immediately, the readiness probe fails until the warm-up completes, and a slow warm-up does not fail the deployment. Never block (.Wait()) in Program.cs or in a constructor; Main is async since C# 7.1. For migrations at scale, prefer a separate job rather than every replica racing at startup.

Example

var app = builder.Build();
await using (var scope = app.Services.CreateAsyncScope())
    await scope.ServiceProvider.GetRequiredService<AppDb>().Database.MigrateAsync();   // before serving

app.MapHealthChecks("/ready", new() { Predicate = c => c.Tags.Contains("ready") });
await app.RunAsync();

Follow-ups

  • What does a hosted service's StartAsync token mean? — Since .NET 6 it is cancelled if startup is aborted; honour it.
  • How do you avoid all replicas running migrations? — A single init job or leader election; the app checks the schema version and refuses to serve if behind.
  • Why is the readiness gate better than blocking start for cache priming? — Kubernetes can roll the deployment; a 60-second warm-up does not trip the liveness probe.

Common wrong answer

"Do it in the constructor of a singleton so it runs once." Constructors run during resolution, cannot await, and block whoever resolves first.

seniorWhat goes wrong when a continuation captures HttpContext or a request-scoped object beyond the request?

Answer

HttpContext is a per-request object that is reset and pooled after the response completes; reading it later returns garbage or another request's data, and writing to the response throws. IHttpContextAccessor relies on AsyncLocal, so the value flows into any continuation started during the request, including background work you fired off, which makes the bug look intermittent. Request-scoped services (DbContext, unit-of-work) are disposed with the scope. The rule: extract the primitive data you need (user id, correlation id, tenant) into an immutable message before leaving the request pipeline, and hand only that to background work. Also note HttpContext is not thread-safe: two concurrent continuations touching it in one request is a bug even inside the request.

Example

// BUG: captured accessor, used later on a pool thread after the request ended
_ = Task.Run(async () => await Audit(_accessor.HttpContext!.User.Identity!.Name));

// FIX: capture data, not context
var userName = http.User.Identity?.Name ?? "anonymous";
await queue.Writer.WriteAsync(new AuditEvent(userName, DateTimeOffset.UtcNow), ct);

Follow-ups

  • Why does it sometimes work? — The pooled context may not have been reused yet; it fails under load, which is the worst kind of bug.
  • Does ExecutionContext.SuppressFlow help? — It stops the accessor's AsyncLocal from flowing into the background task, so the bug becomes a clean null instead of stale data.
  • What about logging scopes? — Also AsyncLocal-based; a scope opened in the request will annotate background logs with the wrong request unless you start a fresh scope.

Common wrong answer

"Pass HttpContext to the background job; it's just an object." The pooling and disposal are the point.

seniorA service is hung with low CPU. How do you find what every thread and every async method is waiting on?

Answer

Capture first, hypothesise second. dotnet-counters confirms the thread-pool picture; dotnet-dump collect takes a full dump (seconds of pause). In dotnet-dump analyze, threads lists managed threads, clrstack -all prints each thread's stack (look for dozens of identical Monitor.Enter, Task.Wait, SemaphoreSlim.Wait, sync Socket.Receive frames), syncblk shows which thread owns a contended monitor, and dumpasync lists incomplete async state machines with what they await, which finds "everything is waiting on one TCS that never completed" and "10,000 requests awaiting a semaphore". dotnet-stack gives the thread view without a dump when you only need a glance. Correlate with logs (Kestrel heartbeat warnings, timeouts) and with the deploy timeline; the fix is usually one blocking call or one never-completed Task.

> clrstack -all | grep -E "Wait|Monitor|Receive" | sort | uniq -c | sort -rn | head
> syncblk                      # who owns the lock everyone is waiting for?

midWhat are the top async issues you flag in code review?

Answer

In rough order of frequency and severity: (1) sync-over-async (.Result, .Wait(), GetAwaiter().GetResult()) anywhere but a documented bridge; (2) un-awaited calls and fire-and-forget without an owner; (3) async void outside event handlers, including async lambdas passed to Action parameters; (4) missing or invented cancellation tokens (CancellationToken.None mid-chain); (5) Task.Run around I/O, or in a web request for CPU work; (6) sequential awaits that could be concurrent, and unbounded concurrency where they are; (7) using/try scopes with an elided Task; (8) ContinueWith instead of await; (9) ValueTask awaited twice or stored; (10) blocking primitives (lock spanning awaits, Thread.Sleep, SemaphoreSlim.Wait) in async methods; (11) Timer with async callbacks; (12) captured HttpContext/scoped services in background work. Each gets a one-line reason and the fix, not a lecture.

Example

// One PR, five findings
public async void Handle(Msg m)                                  // 3: async void
{
    var cfg = _config.LoadAsync().Result;                        // 1: sync-over-async
    _ = _audit.WriteAsync(m);                                    // 2: unowned fire-and-forget
    await Task.Run(() => File.ReadAllText(m.Path));              // 5: Task.Run around I/O
    foreach (var t in m.Targets) await _client.SendAsync(t);     // 6: sequential, no token (4)
}

Follow-ups

  • Which of these block a merge? — 1, 2, 3 and lock-across-await; the rest are "fix before merge unless justified".
  • How do you keep reviews from being religious about ConfigureAwait? — Decide the policy once per repo (library vs app) and let the analyzer enforce it.
  • What do you ask for in the PR description? — Where the concurrency is bounded and what the cancellation behaviour is.

Common wrong answer

Listing style points (naming with Async suffix, ConfigureAwait everywhere) ahead of blocking calls and unowned tasks. Severity ordering is the point of the question.

seniorHow do you test time-dependent async code deterministically (TimeProvider, .NET 8)?

Answer

Inject TimeProvider (abstract class in System, .NET 8; available down-level via the Microsoft.Bcl.TimeProvider package) instead of calling DateTime.UtcNow, Task.Delay, PeriodicTimer or CancellationTokenSource.CancelAfter directly: all of these have overloads taking a TimeProvider. In production register TimeProvider.System; in tests use FakeTimeProvider from Microsoft.Extensions.TimeProvider.Testing and call Advance(TimeSpan) to fire timers and delays instantly. The result: a retry-with-backoff or a 30-second periodic job is tested in milliseconds, with no flaky sleeps. Other rules for deterministic async tests: return Task from tests, never async void; use pre-cancelled tokens to test cancellation paths; assert on Task.Status after Advance rather than sleeping; and keep real-time tests (if any) to one integration suite.

Example

[Fact]
public async Task Retries_three_times_with_backoff()
{
    var time = new FakeTimeProvider();
    var sut = new Retrier(time, attempts: 3, baseDelay: TimeSpan.FromSeconds(1));
    var calls = 0;
    var task = sut.RunAsync(ct => { calls++; throw new IOException(); }, CancellationToken.None);

    time.Advance(TimeSpan.FromSeconds(1));   // fires the first delay
    time.Advance(TimeSpan.FromSeconds(2));   // second
    await Assert.ThrowsAsync<IOException>(() => task);
    Assert.Equal(3, calls);
}

Follow-ups

  • How do you handle Task.Delay in code you don't own? — Wrap the dependency behind an interface, or accept a slow test in the integration suite.
  • Does FakeTimeProvider.Advance run continuations synchronously? — Timer callbacks run inline during Advance; continuations may still need a yield (await Task.Yield()) before asserting.
  • What about Stopwatch-based code? — TimeProvider.GetTimestamp()/GetElapsedTime() replace it.

Common wrong answer

"Use Task.Delay(1100) in the test and assert afterwards." Flaky, slow, and it signals the candidate has not seen TimeProvider.

midHow do you debug async code in an IDE: stepping, the Tasks window, Parallel Stacks?

seniorHow do traces, logging scopes and correlation flow across awaits, and what breaks them?

Answer

System.Diagnostics.Activity (the OpenTelemetry span in .NET) and ILogger.BeginScope both use AsyncLocal, so they flow through awaits, Task.Run and thread switches automatically, and they propagate into HttpClient headers via DiagnosticsHandler. What breaks flow: ExecutionContext.SuppressFlow, UnsafeQueueUserWorkItem/UnsafeRegister, background work started from a request (the Activity flows but ends when the request's Activity is stopped, producing orphaned children), and queues: a Channel consumer runs in its own flow, so you must carry the trace context in the message and restore it (ActivityContext.Parse + new Activity with that parent). Batch consumers should start one Activity per message linked to the producer's, not a child (the producer span is long finished).

Example

// producer (request)
await queue.Writer.WriteAsync(new Job(payload, Activity.Current?.Id), ct);

// consumer (background)

    parentId: job.TraceParent);                     // link to the originating request
using var scope = _log.BeginScope(new Dictionary<string, object> { ["JobId"] = job.Id });
await HandleAsync(job, stop);

Follow-ups

  • Why do logs from background work show a stale request id? — The AsyncLocal-based scope flowed into it; start a fresh scope in the consumer.
  • What does .NET 11 change here? — The ExecutionContext capture optimisation is transparent: when an Activity is set, the context is captured as before.
  • How does this interact with ConfigureAwait(false)? — Not at all; ExecutionContext flows regardless.

Common wrong answer

"Pass the correlation id as a parameter everywhere." Workable but ignores that the platform already flows it; the senior answer knows both the mechanism and where it stops.

seniorWhat async-specific memory leaks have you seen, and how do you find them?

midHow do you wrap APM (Begin/End) and EAP (event-based) APIs into Tasks?

Answer

APM (the .NET 1.x BeginRead/EndRead pairs with IAsyncResult) converts with Task.Factory.FromAsync(BeginX, EndX, state), which handles the callback and exception marshalling for you. EAP (.NET 2.0 XxxAsync methods paired with XxxCompleted events, e.g. WebClient, BackgroundWorker) converts with a TaskCompletionSource: subscribe to the event, start the operation, complete the TCS in the handler (result, Error, or Cancelled), and unsubscribe. In both cases give the wrapper a cancellation token via registration and prefer a modern replacement API when one exists (HttpClient over WebClient, Stream.ReadAsync over BeginRead).

Example

// APM → TAP
Task<int> read = Task.Factory.FromAsync(stream.BeginRead, stream.EndRead, buffer, 0, buffer.Length, null);

// EAP → TAP
public static Task<string> DownloadAsync(this WebClient wc, Uri uri, CancellationToken ct)
{
    var tcs = new TaskCompletionSource<string>(TaskCreationOptions.RunContinuationsAsynchronously);
    DownloadStringCompletedEventHandler handler = null!;
    handler = (s, e) =>
    {
        wc.DownloadStringCompleted -= handler;
        if (e.Cancelled) tcs.TrySetCanceled(ct);
        else if (e.Error is not null) tcs.TrySetException(e.Error);
        else tcs.TrySetResult(e.Result);
    };
    wc.DownloadStringCompleted += handler;
    using var reg = ct.Register(wc.CancelAsync);
    wc.DownloadStringAsync(uri);
    return tcs.Task;
}

Follow-ups

  • How do you recognise EAP? — A void XxxAsync(...) method plus an XxxCompleted event and often CancelAsync.
  • Does FromAsync use a thread? — No; it registers the APM callback, so it is real async if the underlying API is.
  • Why unsubscribe in the handler? — To avoid leaking the closure through the long-lived WebClient and to prevent double completion.

Common wrong answer

"Wrap EndRead in Task.Run." That blocks a thread on a callback-based API; FromAsync exists precisely to avoid it.

seniorWhat are the important async behavioural differences between .NET Framework 4.x and modern .NET?

Answer

(1) SynchronizationContext: classic ASP.NET has one per request (deadlocks with .Result, one continuation at a time); ASP.NET Core has none. (2) HttpContext.Current flows via that context on Framework and does not exist on Core; use IHttpContextAccessor. (3) Allocation: Framework async methods allocate several objects per suspension; Core 2.1+ allocates one. (4) Stack traces: Framework shows MoveNext soup; Core cleans them. (5) APIs missing on Framework: ValueTask needs a package, no IAsyncEnumerable without C# 8 and a package, no Task.WaitAsync, Parallel.ForEachAsync, PeriodicTimer, Channel<T> only as a package. (6) Thread pool: Framework uses the native Windows pool with its own injection; Core 6+ uses the managed pool with blocking detection. (7) Sync I/O: many Framework APIs that look async (FileStream without useAsync) fake it with pool threads. Migrations must re-check every blocking bridge, because the deadlock that "worked" through the ASP.NET context becomes starvation on Core.

midWhy is ContinueWith considered legacy, and what are its traps?

Answer

ContinueWith predates await and exposes everything the compiler now handles: it does not unwrap nested tasks (a Func<Task> continuation gives Task<Task>), it does not propagate exceptions naturally (the continuation runs even if the antecedent faulted unless you use TaskContinuationOptions.OnlyOnRanToCompletion, which then cancels the continuation on fault), it defaults to TaskScheduler.Current (context-dependent), and it does not participate in the cleaned-up async stack traces or the debugger's async chain. It survives for two uses: attaching a logging continuation to a task you deliberately do not await (OnlyOnFaulted, explicit scheduler), and low-level library code that needs a continuation without a state machine. Everything else should be await.

Example

// Legacy
client.GetAsync(url).ContinueWith(t =>
{
    if (t.IsFaulted) Log(t.Exception);
    else Process(t.Result);
});   // scheduler = TaskScheduler.Current; exceptions inside Process are lost

// Modern
try { Process(await client.GetAsync(url)); } catch (Exception ex) { Log(ex); }

// Acceptable use: observe a deliberately un-awaited task
_ = task.ContinueWith(static t => Log(t.Exception!), CancellationToken.None,
                      TaskContinuationOptions.OnlyOnFaulted | TaskContinuationOptions.ExecuteSynchronously,
                      TaskScheduler.Default);

Follow-ups

  • What does ExecuteSynchronously do? — Runs the continuation on the completing thread; fine for a log call, dangerous for real work.
  • Why is the t.Result inside safe? — The antecedent is complete, so it does not block, but it wraps exceptions in AggregateException.
  • How does Unwrap() fit? — Converts Task<Task<T>> to Task<T> for continuations returning tasks.

Common wrong answer

"ContinueWith is just await for people who prefer callbacks." The scheduler default and the exception handling are functionally different.

principalHow would you migrate a large synchronous .NET codebase to async without a big-bang rewrite?

Answer

Sequence it by risk, not by module. First, instrument: find where threads block (dumps under load, analyzers in report mode) and prioritise the hot paths. Second, go bottom-up from I/O leaves (data access, HTTP clients) adding parallel async methods (GetAsync next to Get) rather than replacing signatures, so callers migrate independently. Third, go top-down from entry points (controllers, handlers, hosted services) to consume the async versions, converting one vertical slice at a time and removing the sync path when a slice is complete. Keep sync-over-async bridges only at the seams between converted and unconverted code, isolated in one helper with a counter, and never in libraries. Interfaces are the hard part: introduce async variants, mark sync ones [Obsolete] with a date. On .NET Framework, watch for the SynchronizationContext deadlock during the transition; on modern .NET, watch thread-pool counters as the number of blocking seams changes. Ship with load tests per slice, and define done as "no blocking calls on request paths, verified by analyzer and dumps".

Example

Phase 0  Measure: dumps + VSTHRD002/CA1849 in report-only mode → list of blocking sites by request volume
Phase 1  Leaves: add *Async overloads to repositories/clients; sync overloads delegate nothing (keep both real)
Phase 2  Slices: pick the highest-volume endpoint; convert its whole call chain; remove its sync path
Phase 3  Seams: one AsyncBridge.RunSync helper with a metric; budget: N calls, decreasing each sprint
Phase 4  Enforce: analyzers to error; delete the bridge; document the policy in the repo

Follow-ups

  • Why parallel methods instead of changing signatures? — Changing a signature forces every caller to change at once; parallel methods let each team move on its own schedule.
  • Where do you allow Task.Run during migration? — At UI or entry points to keep them responsive; never in the shared layers.
  • How do you handle a third-party sync-only SDK? — Isolate it behind an interface, bound its concurrency, and treat it as a known blocking site with a replacement ticket.

Common wrong answer

"Add async to every method and await everywhere in one PR." No sequencing, no measurement, no seams: it is the answer that produces months of deadlocks.

screenerasync Main, Task.WaitAll versus await Task.WhenAll, and what you still see in console apps.

Answer

Since C# 7.1 Main can be async Task/async Task<int>, so console apps should await rather than call .Wait() or .Result on their root task; the compiler generates the blocking call for you in a place where it is safe (no SynchronizationContext, no starvation concern at process start). Task.WaitAll blocks the calling thread and throws AggregateException with all faults; await Task.WhenAll suspends and throws the first fault. In modern code WaitAll appears only in synchronous test harnesses or console tools, and even there await WhenAll is cleaner. Generic hosting (Host.CreateApplicationBuilder) makes the question moot: await host.RunAsync().

Example

// Legacy console
static void Main() { RunAsync().GetAwaiter().GetResult(); }

// Modern
static async Task<int> Main(string[] args)
{
    await Task.WhenAll(Migrate(), Seed());
    return 0;
}

Follow-ups

  • What does the compiler generate for async Main? — A synthetic Main that calls your method and blocks with GetAwaiter().GetResult().
  • Is Task.WaitAll ever right? — In a sync context that cannot be async and has no SynchronizationContext, e.g. a legacy scheduler job; document it.

Common wrong answer

"Use .Result in Main because there is nothing to deadlock with." Works, but the interviewer expects async Main to be the reflex.

principalWhat is still missing or awkward in .NET's async story, and how do you work around it?

Answer

Structured concurrency: there is no language-level scope that guarantees child tasks complete or are cancelled before a method returns; teams emulate it with explicit WhenAll plus linked tokens and discipline. No built-in async lazy, async lock or async reader-writer lock: Lazy<Task<T>>, SemaphoreSlim, and community libraries fill in. No async constructors or async properties. Cancellation is cooperative and therefore only as good as the least careful library. async void still exists for event handlers, and analyzers rather than the language prevent misuse. Interfaces cannot easily offer both sync and async without duplication. Runtime Async addresses overhead and diagnostics, not these design gaps. A principal answer names these calmly, explains the workaround policy in place, and does not pretend the platform is either perfect or broken.

Example

// Poor man's structured concurrency: children cannot outlive the scope
public async Task ProcessAllAsync(IEnumerable<Job> jobs, CancellationToken ct)
{
    using var scope = CancellationTokenSource.CreateLinkedTokenSource(ct);
    var children = jobs.Select(j => RunChildAsync(j, scope.Token)).ToList();
    try { await Task.WhenAll(children); }
    catch { scope.Cancel(); await Task.WhenAll(children).ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing); throw; }
}

Follow-ups

  • How do other ecosystems solve structured concurrency? — Kotlin coroutine scopes, Swift task groups, Python's TaskGroup; .NET has design discussions but no shipped feature.
  • Would you write your own async lock? — No; use a maintained library or SemaphoreSlim; hand-written ones get fairness and cancellation wrong.

Common wrong answer

Either "nothing is missing" or a list of complaints with no workaround; the interviewer wants judgment, not sentiment.

seniorShould RequestAborted cancel database writes when the client disconnects?

What a strong answer demonstrates

Splits the answer by operation type: idempotent reads and single-statement writes inside one transaction, yes (resources are released, the transaction rolls back cleanly); multi-step or cross-system writes, no, because a partial outcome the client never sees is worse than finishing work nobody waits for. Proposes the design that makes the question easy: keep request handlers thin, commit atomically, and push multi-step work behind an outbox. Mentions that RequestAborted is not reliable behind every proxy, so the design must not depend on it.

Trade-offs named unprompted

  • Resource release on abandoned requests vs. partial side effects.
  • Simplicity of one policy vs. correctness of two.
  • Client retry behaviour (they will retry the POST) vs. idempotency keys.
principalBig-bang or incremental when removing sync-over-async from a legacy service?

What a strong answer demonstrates

Incremental, with a plan (unit 12, q12-4): measure, leaves first with parallel methods, vertical slices, one isolated bridge with a shrinking budget, analyzers to error at the end. Explains why big-bang fails (every seam changes at once, deadlocks appear in untested paths, no way to attribute regressions). Acknowledges when a big-bang is right: a small service with full test coverage and a maintenance window.

Trade-offs named unprompted

  • Duration of the transition (living with seams) vs. risk concentration of a single cutover.
  • API duplication during the transition vs. forced simultaneous caller changes.
  • Where the remaining bridges may live and how their count is made visible.
seniorStream results across a service boundary with IAsyncEnumerable, or page them?

What a strong answer demonstrates

Matches transport to shape: gRPC server streaming or NDJSON/chunked HTTP for long, unbounded or latency-sensitive streams where the consumer needs early items; cursor-based paging for REST clients, caching, retries and resumability. Names the mid-stream error problem (status already sent), the connection-pinning cost on the server (DbContext, connection), and the client-side back-pressure story. Suggests the hybrid: a paged API plus a client helper exposing it as an async stream.

Trade-offs named unprompted

  • Time-to-first-item and memory vs. resumability and cacheability.
  • Server resources pinned per stream vs. per-page overhead.
  • Error semantics (truncated body) vs. explicit per-page status codes.
seniorHow do you set the degree of parallelism for I/O-bound fan-out in a shared service?

What a strong answer demonstrates

Rejects core count as the basis for I/O-bound work and derives the number from the downstream's capacity and the service's fair share of it (per-dependency semaphore, not per-request), with Little's law to connect concurrency, latency and throughput. Puts the limit in the dependency's client wrapper so it is global, makes it configurable, and pairs it with timeouts and a circuit breaker so a slow dependency degrades gracefully. Mentions connection-pool limits (HttpClient handler, SQL pool) as hard ceilings.

Trade-offs named unprompted

  • Throughput vs. protecting the downstream (and other tenants of it).
  • Per-request fairness vs. global efficiency.
  • Static limits vs. adaptive ones (more complexity, better behaviour under change).

§Design exercises

Where this topic meets system design. Each exercise gives the prompt and the clarifying questions you should ask; the strong solution outline and the trade-offs you are expected to name are collapsed so you can attempt it first.

1. Outbound webhook dispatcher

Prompt. Design the component that delivers webhooks to customer endpoints for a multi-tenant SaaS: 5,000 events/s peak, 20,000 distinct endpoints with wildly different latency (50 ms to 30 s), at-least-once delivery, retries with backoff, and no tenant may starve another. It runs on .NET 10 across several replicas.

Clarifying questions to ask

  • Delivery guarantee and ordering: per-endpoint ordering required, or only at-least-once?
  • Durability boundary: is there an existing broker/outbox, or must this component own persistence?
  • Retry policy limits: maximum attempts and age, dead-letter expectations, customer-visible status?
  • Per-tenant limits: contractual rate limits, or just fairness?
  • Timeouts per attempt and what "the endpoint is down" should trigger (circuit breaker per endpoint?).
  • Observability requirements: per-tenant delivery latency, backlog, failure reasons.
Strong solution outline and trade-offs (attempt it first)

Outline

  • Durability first. Events land in an outbox table or broker (partitioned by tenant/endpoint) written in the producing transaction; the dispatcher is a stateless consumer. In-memory channels are only buffers inside a replica.
  • Per-endpoint pipelines. A bounded Channel<Delivery> per active endpoint (created lazily, evicted when idle) with one consumer loop each gives per-endpoint ordering and isolates a slow endpoint. A global SemaphoreSlim (or Parallel.ForEachAsync over endpoints) caps total in-flight HTTP calls at what the replica's connection pool and CPU can handle (e.g. 2,000), sized by Little's law from target throughput × typical latency.
  • Fairness. Round-robin or weighted scheduling across tenants when acquiring the global permit; per-tenant token buckets for contractual limits; a slow endpoint holds only its own permit, never the queue.
  • HTTP layer. One HttpClient via IHttpClientFactory with a standard resilience handler: 10 s attempt timeout, jittered exponential backoff on 5xx/408/429, circuit breaker per endpoint (keyed pipelines) so a dead endpoint fails fast and is re-probed slowly. Idempotency key header on every attempt.
  • Cancellation and shutdown. All I/O takes the host's stopping token via a two-phase drain: stop pulling from the outbox, finish in-flight attempts within the shutdown timeout, release leases on anything not finished so another replica picks it up. Never cancel an attempt mid-request just because the pod is stopping unless the grace period is expiring.
  • Retries. Failed deliveries return to durable storage with a next-attempt time, not to memory; a scheduler pulls due retries. Dead-letter after N attempts or T age, with a customer-visible status.
  • Observability. Metrics: backlog per tenant, in-flight count, permit wait time, attempt latency histogram per endpoint, circuit state; thread-pool queue length and Kestrel-style heartbeat as health. Activity linked (not parented) to the originating event.

Trade-offs to name unprompted

  • Per-endpoint ordering (one consumer per endpoint) vs. throughput for endpoints with bursts; offer ordering as an opt-in.
  • Global concurrency limit: too low wastes capacity, too high exhausts sockets and downstream; adaptive limits add complexity.
  • Retrying in memory (fast, lost on crash) vs. persisting every retry (durable, more DB load).
  • Per-endpoint circuit breakers protect the fleet but delay recovery for flapping endpoints; choose probe intervals deliberately.
  • At-least-once means duplicates; idempotency keys shift the burden to customers and must be documented.

2. Streaming export endpoint for 10 million rows

Prompt. Design GET /exports/orders that streams up to 10 million rows from a relational database as NDJSON or CSV to an HTTP client, with flat memory, client-disconnect handling, a bounded impact on the database, and the ability for the client to resume.

Clarifying questions to ask

  • Consistency: snapshot at request start, or is a live cursor acceptable?
  • Client types: browsers (download), scripts (curl), or other services? Do they need resume?
  • Latency to first byte required, or is an async job with a download link acceptable?
  • Database limits: max connection duration, read replica availability, pagination-friendly keys?
  • Auth and size limits: per-tenant caps, rate limits on exports?
Strong solution outline and trade-offs (attempt it first)

Outline

  • Two shapes. Interactive streaming for moderate sizes (say under 1 M rows or 2 minutes), and an asynchronous export job that writes to blob storage with a signed download URL for anything larger. The endpoint decides by estimated size and returns 202 with a job id when it picks the job path.
  • Streaming path. An IAsyncEnumerable<Row> from EF Core AsNoTracking().AsAsyncEnumerable() or a raw DbDataReader, ordered by a keyset (WHERE id > @last ORDER BY id) in pages of a few thousand so no single reader is open for the whole export; write with a PipeWriter/Utf8JsonWriter into the response body, flushing every N KB; RequestAborted linked into every read so a disconnect stops the query within one page. Chunked transfer, Content-Disposition, and no Content-Length.
  • Resume. Emit the last key in a trailer or as part of each NDJSON line, and accept ?after=<key>; keyset paging makes resume exact and cheap, offset paging does not.
  • Database impact. Read replica; statement timeout per page; a per-tenant semaphore limiting concurrent exports; page size tuned so a page is one round-trip of roughly 100 ms.
  • Errors. A mid-stream failure cannot change the status code: end with an explicit error record (NDJSON) and a trailer; document that clients must validate the terminal record.
  • Back-pressure. Awaiting FlushAsync naturally slows the DB reads when the client is slow; no unbounded buffering between DB and socket.

Trade-offs to name unprompted

  • Snapshot consistency (long transaction, replica lag) vs. keyset pages that may see rows inserted during the export.
  • Streaming (low latency, pinned resources, no retry) vs. job + blob (higher latency, durable, cacheable, resumable).
  • Row-by-row serialization simplicity vs. per-page batching efficiency.
  • Client-disconnect cancellation of reads is a pure win; cancelling a snapshot transaction may be more expensive than finishing the page.
  • NDJSON (resumable, error record possible) vs. a JSON array (easier for naive clients, no error semantics).

3. Async-safe cache with stampede protection

Prompt. Design an in-process read-through cache for expensive lookups (100 ms to 2 s each) used by hot request paths: single-flight loading per key, a fast path with no allocation on hits, correct behaviour when callers are cancelled while a load is in progress, failure handling so a transient error does not poison the cache, and bounded memory.

Clarifying questions to ask

  • Hit ratio and key cardinality (does bounded memory mean LRU, TTL, or both)?
  • Staleness tolerance: can we serve stale while refreshing (stale-while-revalidate)?
  • Is a distributed cache also involved (two-level), and who is the source of truth?
  • What does cancellation mean for the caller: stop waiting, or abort the shared load?
  • Failure policy: negative caching, backoff per key, or plain retry?
Strong solution outline and trade-offs (attempt it first)

Outline

  • API. ValueTask<T> GetAsync(TKey key, CancellationToken ct): hit path returns new ValueTask<T>(value) with zero allocation; miss path returns a Task-backed ValueTask. Document the single-await rule or return Task if callers compose.
  • Single-flight. ConcurrentDictionary<TKey, Lazy<Task<Entry>>> (or GetOrAdd with a TCS) so exactly one loader runs per key; concurrent callers await the same Task. The shared load uses a cache-owned token (linked to the host lifetime), not any caller's token; callers use WaitAsync(ct) so their cancellation only stops their wait.
  • Failure handling. On fault, remove the entry immediately (so the next caller retries) and optionally store a short negative-cache entry with per-key backoff to avoid hammering a broken dependency; never cache OCE.
  • Expiry and memory. TTL per entry plus an LRU bound (size-aware); background refresh for hot keys before expiry (stale-while-revalidate) using a PeriodicTimer-driven worker with bounded concurrency, so request paths rarely see a miss.
  • Two-level option. Local cache in front of a distributed one; local single-flight still applies; distributed stampede protection via a short lock key or probabilistic early expiration.
  • Observability. Hit/miss/stale-hit counters, in-flight loads, load latency, eviction counts.

Trade-offs to name unprompted

  • ValueTask fast path vs. Task simplicity for callers who compose or retry.
  • Caller cancellation semantics: abort shared load (wastes the work others wait for) vs. detach (a load may run for nobody).
  • Negative caching reduces load on a failing dependency but delays recovery; pick a short TTL with jitter.
  • Stale-while-revalidate trades correctness window for latency; must be per-key configurable.
  • Lazy<Task> caches a faulted Task unless replaced; the replace-on-fault logic is the part people get wrong.

§Night-before cheat sheet

The ten most-asked questions in the whole bank, one sentence each.

  1. Does await create or block a thread? Neither: the method suspends and returns an incomplete Task to its caller, and the continuation is scheduled when the awaited operation completes, with no thread parked for I/O.
  2. Explain the sync-over-async deadlock. Blocking with .Result on a single-threaded SynchronizationContext holds the only thread the awaited method's continuation was posted to, so neither side can proceed; fix by going async all the way (or ConfigureAwait(false) below the block).
  3. What does ConfigureAwait(false) do? Skips capturing the SynchronizationContext/scheduler for that one await so the continuation runs on the completing (pool) thread; it does not affect ExecutionContext/AsyncLocal, and it is needed on every await in library code.
  4. How do exceptions flow from async methods? They are stored in the returned Task and rethrown (original type, preserved stack) when awaited; .Wait()/.Result wrap them in AggregateException, and async void crashes the process because there is no Task.
  5. Task.WhenAll and exceptions? Awaiting throws only the first exception; all of them are on the WhenAll task's Exception.InnerExceptions, and nothing fails fast unless you add cancellation.
  6. How does cancellation work? Cooperatively: a CTS issues a token that is passed down and polled or registered; cancelling requests, never forces, and the operation ends with an OperationCanceledException (TaskCanceledException is its subtype).
  7. What is thread-pool starvation and its cause? All pool threads blocked (usually by sync-over-async or sync I/O) while the continuations that would free them queue behind them; the pool injects only about one or two threads per second above the minimum, so latency explodes while CPU is idle.
  8. When do you use Task.Run? To offload CPU-bound work off a UI thread or to parallelise CPU work; never to wrap I/O, and rarely in ASP.NET Core where the request is already on a pool thread.
  9. Task versus ValueTask? Task is a heap object safe to await many times and compose; ValueTask is a struct for hot paths that often complete synchronously or use pooled sources, and it must be awaited exactly once.
  10. What is IAsyncEnumerable<T> and how do you cancel it? A pull-based lazily produced async sequence consumed with await foreach; pass the token with WithCancellation(ct) and bind it in the iterator with [EnumeratorCancellation].
