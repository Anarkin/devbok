01 What await really does

Docs: Task asynchronous programming model

Everything in this guide derives from one sentence: an async method is a method the compiler chops into pieces at every await, and the returned Task is the handle that tells the caller when the last piece has run. Notice what is missing from that sentence: a thread. The single most common failure at interview is a candidate who models async as "runs on a background thread". It does not. It is a way of not occupying a thread while something else — a disk, a socket, a timer, another core — is busy.

The problem it was designed to solve

Before C# 5 (2012) you had two options for an operation that takes time. Block a thread: simple to read, but each blocked thread costs a stack (1 MB reserved on Windows by default), a scheduler slot and context switches, so a server's concurrency ceiling becomes "how many threads can I afford". Or write callbacks: the APM pattern (BeginRead/EndRead/IAsyncResult) and EAP (DownloadStringCompleted events) scale fine but turn every loop, every try/finally and every using into a hand-rolled state machine, and exception flow becomes something you maintain by hand. Async/await is the compiler writing the callback version for you while you keep the shape of the blocking version. The explicit design goal was scalability of I/O-bound work, not CPU parallelism — say that out loud early, because everything else follows from it.

The running example: a request that waits

Keep one picture in your head for the whole guide. An ASP.NET Core handler calls a database; the round trip takes 40 ms. Under blocking I/O one thread sits in a kernel wait for 40 ms doing nothing, so 200 concurrent requests need 200 threads. Under async I/O the thread issues the read, registers a completion and returns to the pool; when the bytes arrive, an I/O completion port hands them to some pool thread, which resumes the method at the line after the await. Same latency per request — async does not make the database faster — but thread count decouples from concurrency. "Async does not reduce latency, it reduces the threads you need to absorb concurrency" is a sentence interviewers reward.

What the compiler generates

For each async method the compiler emits a state machine type — a struct in Release, a class in Debug so the debugger can inspect it — hoists the locals that live across an await into fields, and moves the body into MoveNext() with a switch over an int state. Your original method shrinks to: create the machine, call builder.Start(ref machine), return builder.Task. Every await x inside MoveNext becomes roughly this:

// what `var r = await x;` compiles to, conceptually
var awaiter = x.GetAwaiter();               // 1. the awaitable pattern - duck-typed, not an interface
if (!awaiter.IsCompleted)                   // 2. fast path: already finished? then never suspend
{
    _state = 0;                             // 3. remember where to resume
    _awaiter = awaiter;                     // 4. hoist the awaiter into a field
    _builder.AwaitUnsafeOnCompleted(ref awaiter, ref this); // boxes the struct ONCE, creates the Task
    return;                                 // 5. hand the thread back to the caller
}
// the resume label for state 0 lands here
var r = awaiter.GetResult();                // 6. unwrap the value, or rethrow with the original stack

Three consequences are worth memorising, because most interview answers are corollaries of them.

  • Awaiting an already-completed task is synchronous and nearly free. If IsCompleted is true there is no suspension, no boxing, no scheduling — control falls through. This is why cached results, ValueTask fast paths and buffered stream reads cost almost nothing, and why "async everywhere" is not automatically expensive.
  • The first real suspension is where the cost lives. At the first incomplete await the struct is boxed onto the heap (one allocation carrying every hoisted local) and the Task is created. Later awaits in the same method reuse that box. Two allocations per async call that actually suspends is the number to quote.
  • An async method runs synchronously until its first incomplete await. Code before that point executes on the caller's thread. A method that spends 200 ms parsing JSON before its first await blocks its caller for 200 ms; the async keyword changed nothing about it.

Where does the continuation run?

Somebody has to call MoveNext() when the operation completes. Who, is decided by the awaiter — not by the language and not by Task. TaskAwaiter captures a context at the moment of the await and uses this order of preference:

Captured at the awaitWho runs the continuationWhere you meet it

No sync context, but TaskScheduler.Current is not TaskScheduler.DefaultQueued to that schedulerCode inside Task.Factory.StartNew with a custom scheduler (rare, usually a smell)

The highlighted row is the one people get wrong. With no context the continuation is not "queued to the thread pool"; it runs synchronously on whichever thread called TrySetResult, right at that point. That is what makes await cheap — and it is also why a slow continuation can hijack an I/O completion thread, and why TaskCreationOptions.RunContinuationsAsynchronously exists on TaskCompletionSource (unit 02).

The awaitable pattern is duck-typed

There is no IAwaitable. The compiler needs a GetAwaiter() — instance or extension method — returning a type with bool IsCompleted, GetResult(), and OnCompleted(Action) via INotifyCompletion (ideally also UnsafeOnCompleted via ICriticalNotifyCompletion, which skips a second ExecutionContext capture the builder already did). Task, ValueTask, YieldAwaitable from Task.Yield(), ConfiguredTaskAwaitable and every custom awaitable satisfy it. This is why await someToken can be made to compile with a small extension, and why await foreach and await using are just more sugar over the same shape.

// A custom awaitable: `await token` means "wait until this token is cancelled".
// Useful in shutdown coordination - and the cheapest way to show an interviewer
// that "awaitable" is a pattern, not an interface.
public readonly struct TokenAwaiter : ICriticalNotifyCompletion
{
    private readonly CancellationToken _token;
    public TokenAwaiter(CancellationToken token) => _token = token;

    public bool IsCompleted => _token.IsCancellationRequested;
    public void GetResult() { }
    public void OnCompleted(Action continuation) => _token.Register(continuation, useSynchronizationContext: true);
    public void UnsafeOnCompleted(Action continuation) =>
        _token.UnsafeRegister(static (s, _) => ((Action)s!)(), continuation);
}

public static class TokenAwaitExtensions
{
    public static TokenAwaiter GetAwaiter(this CancellationToken token) => new(token);
}

Async is not concurrency, and neither is a thread

Four ideas get conflated constantly. Pin them apart once and half the "what is the difference between" questions answer themselves.

AsynchronyNot holding a thread while waiting for something else to finishawait on an I/O Task
ConcurrencySeveral operations in flight at once, possibly on one threadTask.WhenAll, a Channel, an event loop
ParallelismSeveral operations executing on several cores at the same instantParallel.For, Task.Run per CPU chunk, PLINQ

Interview trap

"Does await create a thread?" No — and the follow-up is the real question: which thread resumes you. Pure I/O (HttpClient, SqlConnection, a FileStream opened with useAsync: true) has no thread at all during the wait; the continuation runs on whichever thread the completion arrives on, or on the captured context. But await Task.Run(...) does occupy a pool thread for the duration of the delegate, and wrapping a synchronous method in Task.Run inside a server does not make it async — it moves the blocking from one pool thread to another and adds a scheduling hop. The lead-level version of the answer names the exceptions: a FileStream without useAsync: true, and ...Async methods over drivers with no true async support, will block a pool thread behind an async-looking API.

Try it — prove the state machine to yourself

1. Paste a small async Task<int> method with two awaits and a for loop into sharplab.io, switch the output to C# decompilation, and read the generated state machine struct: find the state field, the hoisted locals and the two resume labels.

2. Write a method that does Thread.Sleep(2000) before its first await, call it without awaiting it, and time how long the calling line takes.

Expected outcome

1. A loop variable that lives across an await becomes a field of the state machine; one that does not survive an await usually stays a local. In Release you see a struct, in Debug a class. Under .NET 11 with <Features>runtime-async=on</Features> the state machine is gone entirely and you see IL using the async calling convention instead (unit 12).

2. The calling line takes about 2000 ms. The body up to the first incomplete await is your caller's code on your caller's thread. This is the mechanism behind "my async endpoint blocks under load even though everything is async": some synchronous work — config parsing, deserialising a 5 MB payload, a lazy singleton initialisation — sits before the first await.

Interview Q&A

Walk me through what happens, mechanically, when I call an async method.

The caller invokes an ordinary method. That method allocates a state machine — a struct on the caller's stack in Release — copies the parameters into it, and calls AsyncTaskMethodBuilder.Start, which invokes MoveNext synchronously on the calling thread. Your code runs on the caller's thread until it hits an await whose awaiter reports IsCompleted == false. At that point the builder boxes the state machine onto the heap, creates the Task the caller will receive, registers MoveNext as the continuation on the awaiter, and returns. The caller now holds an incomplete task and carries on. Later, whatever completes the underlying operation invokes the continuation, which calls MoveNext again, jumps via the state field to the resume label, and runs to the next await or to the end, where the builder calls SetResult and the caller's await is satisfied.

Why is async not part of the method signature's contract?

Because it is an implementation detail, not part of the type. Callers bind to "returns Task<T>", and whether you produce that task with a state machine, by returning another method's task directly, or with a TaskCompletionSource, is your business. That is why you cannot write async in an interface declaration, why an override need not be async, and why removing async/await from a pass-through wrapper is source-compatible. The code-review corollary: adding async to a method that only forwards a task costs a state machine and an allocation for no behavioural gain — unless you need the try/finally, using or exception-wrapping semantics that awaiting gives you.

What is the awaitable pattern, and why is it a pattern rather than an interface?

The compiler requires a GetAwaiter(), instance or extension, returning a type with bool IsCompleted, GetResult() and INotifyCompletion.OnCompleted(Action), optionally ICriticalNotifyCompletion.UnsafeOnCompleted. It is structural rather than nominal for performance and reach. Structural matching lets awaiters be structs that never box and whose members inline, whereas an interface would force a virtual call and, for value types, a box on every await. It also lets types that predate async, or that live in libraries you do not own, become awaitable through an extension method. The practical payoff is ValueTask, ConfiguredValueTaskAwaitable and IValueTaskSource: none of them would be viable if awaiting went through an interface.

Someone says "we made the endpoint async and throughput didn't change". How do you diagnose that?

First I check whether anything is actually asynchronous end to end: an async method whose awaits all complete synchronously is just a slower synchronous method. The usual causes are a synchronous driver behind an async-looking API, a FileStream without useAsync: true, a .Result buried in a helper, or CPU work before the first await. Second, I ask whether thread count was ever the constraint: if the connection pool caps at 100 or the downstream rate-limits you, freeing pool threads buys nothing except burst tolerance. Third, I look at the thread-pool counters — if queue length sits near zero and thread count is flat, threads were not the bottleneck, and the honest answer is "async was the wrong lever for this problem, though it remains the right default for I/O". I would rather say that than let a team believe async is a performance feature.

Concurrency versus parallelism here — and why does the distinction change a design?

Concurrency is having multiple operations in flight; parallelism is executing them at the same instant on different cores. Async/await gives concurrency without parallelism: one thread can hold a thousand outstanding HTTP calls. It matters because the two have different scarce resources. Concurrency is limited by the remote system, connection pools and memory for in-flight state, so you throttle it with a SemaphoreSlim or a bounded channel. Parallelism is limited by cores, so you throttle it with MaxDegreeOfParallelism and you start worrying about cache contention. Conflating them produces the two classic incidents: firing 10,000 concurrent calls and taking down a partner, and using Task.Run per item for I/O on a four-core box and starving the pool.

Why a struct state machine in Release but a class in Debug?

Release optimises for allocation: if the method completes without ever suspending — the common case for cached or buffered operations — the struct never leaves the stack and there is no heap cost. It is boxed only at the first genuine suspension. Debug uses a class so the debugger can hold a stable reference and show locals across awaits; a struct copied on boxing would make that view wrong. Two consequences: allocation benchmarks in Debug are meaningless, and "async allocates" is only true of methods that actually suspend. That is precisely the cost Runtime Async in .NET 11 attacks by keeping locals on the stack unless they really cross a suspension point.

What does await give you that a callback does not?

Control flow, exception semantics and resource lifetime. A callback cannot sit naturally inside a using, a try/finally or a loop, so all of those have to be re-encoded by hand. await keeps them lexical: the finally runs after resumption, the using disposes at the right moment, and exceptions propagate to the enclosing catch with the original stack preserved via ExceptionDispatchInfo. It also flows the ambient context — ExecutionContext and, unless you opt out, SynchronizationContext — so AsyncLocal values, logging scopes and UI-thread affinity survive suspension. Those properties are what make async code reviewable; the scheduling part is almost incidental.

Is there a cost to marking a method async when it has no awaits?

Yes, and the compiler warns you with CS1998. You still get a state machine and a builder, the body runs entirely synchronously, and any exception it throws is captured into a faulted task rather than thrown at the call site — which changes error handling for the caller in a way people do not expect. For a method that must satisfy an async interface but has nothing to await, return Task.CompletedTask or Task.FromResult(x) from a non-async method, or ValueTask.FromResult. The one time I keep async without awaits deliberately is when I want argument-validation errors to become faulted tasks for consistency — and then I comment it, because the next reader will otherwise "fix" it.

Explain "async all the way down", and when you may break it.

The rule exists because the only safe boundary between async and synchronous code is the top of the call stack. Anywhere else, converting async to sync means blocking a thread on a task, which risks deadlock when a context is captured and always costs you the thread you were trying to save. So async should propagate from the I/O call up to the framework entry point: controller action, hosted service, message handler, Main. You may break it exactly at entry points that are genuinely synchronous and that you control — Main (which C# 7.1 lets you make async anyway), a legacy plug-in interface you cannot change, a module initialiser, a one-shot startup path where blocking one thread once is irrelevant. When I do it, I isolate it in one clearly named method, use GetAwaiter().GetResult() so I get the unwrapped exception rather than an AggregateException, and comment why the boundary exists.

How would you introduce async to a team that has never used it, without a wave of incidents?

I would teach the mental model before the syntax, because the incidents come from the model: no thread while waiting, the continuation runs somewhere specific, and blocking on a task is the one forbidden move. Then I would make the rules mechanical rather than cultural — turn on the analyzers that catch the mistakes (CA2007 for missing ConfigureAwait in libraries, CA1849 for synchronous calls inside async methods, and the Microsoft.VisualStudio.Threading analyzers where the codebase warrants it) and make .Result/.Wait() a build error rather than a wiki page. Third, I would convert one vertical slice end to end and load-test it against the synchronous version, so the team sees the thread-count difference instead of trusting me. Finally I would put thread-pool queue length and thread count on the dashboard before the rollout, because the failure mode of a half-converted codebase is starvation and you want to meet it in staging.

02 Task and the TAP contract

Docs: Task-based Asynchronous Pattern (TAP) · TaskCompletionSource<T>

If unit 01 was the language, this unit is the library. Task is a promise: a reference-typed object with a state (created, waiting, running, ran-to-completion, faulted, canceled), an optional result, an optional exception, and a list of continuations. TAP — the Task-based Asynchronous Pattern — is the set of conventions that make those promises interoperable across the whole ecosystem, and the interview questions here are conventions questions as much as mechanics questions.

The TAP conventions, and why each exists

A TAP method is named with an Async suffix, returns Task, Task<T> or ValueTask<T>, takes an optional CancellationToken as its last parameter (before an optional IProgress<T>), and — this is the load-bearing one — returns a task that is already started. Tasks in TAP are "hot": by the time you have the object, the work is in flight. Cold tasks, where you must call Start(), exist only via the Task constructor, which is effectively deprecated for application code; the moment you see new Task(...) in a review, ask why. The convention matters because it makes composition safe: Task.WhenAll(a, b) is only meaningful if a and b are already running, and awaiting the same task twice must return the same answer rather than run the work twice.

A second convention is that a TAP method should throw synchronously only for usage errors (a null argument), and report everything else — including cancellation — through the returned task. That is what lets a caller write one try around an await and catch everything. It is also the reason argument validation in async methods is often split into a non-async wrapper that validates and a private async core that does the work.

Producing a task without a state machine

Not every task comes from an async method. Four factories cover most cases, and a fifth — TaskCompletionSource — bridges the entire callback world into TAP.

Task done   = Task.CompletedTask;             // cached singleton, zero allocation
Task<int> r = Task.FromResult(42);            // allocates, but small ints/bools are cached internally
Task bad    = Task.FromException(new IOException());
Task gone   = Task.FromCanceled(token);       // token must already be cancelled

// The bridge: turn any callback-based API into a Task.
public static Task<string> ReadLineAsync(this ILegacyPort port, CancellationToken ct)
{
    // RunContinuationsAsynchronously is almost always what you want - see the trap below.
    var tcs = new TaskCompletionSource<string>(TaskCreationOptions.RunContinuationsAsynchronously);

    void OnLine(string line) => tcs.TrySetResult(line);
    void OnError(Exception e) => tcs.TrySetException(e);

    port.LineReceived += OnLine;
    port.Failed += OnError;

    // Cancellation must also complete the task, or the caller waits forever.
    CancellationTokenRegistration reg = ct.Register(static s =>
        ((TaskCompletionSource<string>)s!).TrySetCanceled(), tcs);

    return tcs.Task.ContinueWith(static (t, s) =>
    {
        var (p, onLine, onError, r) = ((ILegacyPort, Action<string>, Action<Exception>, CancellationTokenRegistration))s!;
        p.LineReceived -= onLine; p.Failed -= onError; r.Dispose();
        return t.GetAwaiter().GetResult();     // rethrows unwrapped, preserves cancellation
    }, (port, (Action<string>)OnLine, (Action<Exception>)OnError, reg), TaskContinuationOptions.ExecuteSynchronously);
}

Note the Try* methods rather than SetResult: a task can only be completed once, and in a race — result arrives at the same moment as cancellation — SetResult throws InvalidOperationException on the loser. Using TrySetResult everywhere is the difference between a robust bridge and a 3 a.m. page. Since .NET 5 there is also a non-generic TaskCompletionSource, so you no longer have to write TaskCompletionSource<object?> for a void-shaped promise.

Task.Run versus Task.Factory.StartNew

This comparison comes up constantly, because StartNew is what you meet in ten-year-old code and it has three sharp edges Task.Run was created to blunt.

TaskCreationOptions.AttachedToParent deserves a sentence of its own: it creates a parent/child relationship in which the parent task does not complete until its children do, and children's exceptions aggregate into the parent. It is a TPL-era feature that interacts badly with async/await, and its presence in modern code is almost always accidental — Task.Run refuses it for that reason.

How exceptions are surfaced

A faulted task stores an AggregateException, because a task can represent many failures (WhenAll, child tasks). How you observe the task decides what you see:

Async return types, and why async void is different

An async method may return void, Task, Task<T>, ValueTask, ValueTask<T>, IAsyncEnumerable<T>, or any type carrying an [AsyncMethodBuilder] attribute — and since C# 10 you can put that attribute on an individual method, which is how PoolingAsyncValueTaskMethodBuilder is opted into per method (unit 05). async void is the odd one out: there is no task, so there is nothing to await, nothing to observe, and an exception escaping it is raised on the SynchronizationContext — meaning it usually crashes the process. It exists for one reason, event handlers, and that is the only place it belongs.

Interview trap

The TaskCompletionSource stack dive. Without TaskCreationOptions.RunContinuationsAsynchronously, calling tcs.TrySetResult(...) runs every awaiting continuation synchronously, on your thread, inside your call. If you complete a TCS while holding a lock, the continuation — arbitrary user code — runs under your lock and can deadlock or reenter. If you complete a thousand TCS objects in a loop, you run a thousand continuations before the loop's next iteration, and the stack can grow until it overflows. This is the classic "our message pump froze and the dump shows a 4,000-frame stack" incident. The fix is one flag, and the reason it is not the default is backwards compatibility: it was added in .NET Framework 4.6, long after the type shipped. In a code review, a new TaskCompletionSource<T>() with no options is a finding.

Try it — make a stack dive happen, then fix it

1. Create a TaskCompletionSource<int> with no options. Start a task that awaits it and, in the continuation, prints new StackTrace().FrameCount. From the main thread, complete it inside a lock and print the current thread id before and after TrySetResult.

2. Write a loop that creates 10,000 TCS objects, each awaited by a continuation that completes the next one, then completes the first. Compare with and without RunContinuationsAsynchronously.

Expected outcome

1. Without the flag, the continuation prints the same thread id as the completer and runs before TrySetResult returns — inside your lock. With the flag, the id differs (a pool thread) and TrySetResult returns immediately.

2. Without the flag you get a single enormous stack and usually a StackOverflowException, which is unrecoverable and kills the process without an exception you can catch. With the flag each continuation is queued to the pool and the loop finishes flat. This is exactly why libraries such as Channel, SemaphoreSlim and Kestrel's internals are careful about how they complete promises.

Interview Q&A

What does it mean that TAP tasks are "hot", and what breaks if they are not?

Hot means the operation has already started by the time the caller receives the task; the caller's only job is to observe completion. Everything composes on that assumption: Task.WhenAll would run things sequentially rather than concurrently if tasks were cold, and awaiting a task twice would either re-run the work or throw. Cold tasks are only creatable through the Task constructor plus Start(), which modern code should never use. If you genuinely need deferred work, the correct shape is a Func<CancellationToken, Task> — a factory you invoke when you want it — not a cold task, because a delegate makes the deferral explicit at the type level and can be invoked more than once.

When would you reach for TaskCompletionSource?

Whenever the completion signal comes from somewhere the compiler cannot see: an event, a callback from unmanaged code, a message arriving on a socket that must be correlated to a request by id, a test double that I want to release at a precise moment. It is the universal adapter from any completion model into TAP. The three rules I apply every time: create it with RunContinuationsAsynchronously so completing it does not run arbitrary code on my thread; use TrySet* rather than Set* because races between result, error and cancellation are normal; and make sure every path completes it, including cancellation and disposal, or you leak a caller that waits forever. For request/response correlation over a socket I also keep the pending TCS objects in a dictionary keyed by correlation id and fail all of them when the connection drops.

Why does await throw the first inner exception while .Wait() throws AggregateException?

Because they were designed at different times for different purposes. Wait() and .Result come from the TPL, where a task might be a tree of parallel child tasks and reporting all failures was the priority, so they wrap. await came later with the goal of making asynchronous code read like synchronous code, and that requires catch (IOException) to work, so the awaiter unwraps the first exception and rethrows it with ExceptionDispatchInfo so the original stack survives. The practical consequences: never write catch (AggregateException) around an await; if you must block, use GetAwaiter().GetResult() to get the unwrapped behaviour; and when you need all failures from a WhenAll, inspect task.Exception.InnerExceptions rather than relying on what the await threw.

Task.Run or Task.Factory.StartNew?

Task.Run unless you need something only StartNew offers. StartNew schedules on TaskScheduler.Current, so inside another task with a custom scheduler it silently inherits it; it does not unwrap async delegates, so StartNew(async () => ...) gives you a Task<Task> that completes when the lambda reaches its first await — which is the bug where "the work seemed to finish instantly and exceptions vanished"; and it accepts AttachedToParent, which creates parent/child semantics that interact badly with async. The legitimate reasons to keep StartNew are TaskCreationOptions.LongRunning, which asks for a dedicated thread instead of a pool thread for a long blocking loop, and a genuine custom TaskScheduler such as a single-threaded one for a legacy COM component.

What is TaskCreationOptions.LongRunning actually for, and would you use it today?

It is a hint that the delegate will occupy its thread for a long time, so the scheduler should create a dedicated thread rather than consume a pool thread and confuse the pool's injection heuristics. I still use it for one shape: a blocking consumer loop over an API with no async support — a legacy driver, a native queue client — that must run for the process lifetime. For anything else in modern code the answer is no. If the loop is async, a plain Task.Run is right because the thread is released at every await; if you truly need a thread for its whole life, being explicit with new Thread { IsBackground = true } communicates intent better than a scheduling hint. In a hosted service, the cleanest modern equivalent is a BackgroundService whose ExecuteAsync does the loop asynchronously.

What is task "unwrapping" and where does it bite?

Unwrapping converts a Task<Task<T>> into a Task<T> that completes when the inner task completes. It bites wherever a lambda returning a task is passed to something that treats the return value as a plain result: Task.Factory.StartNew(async ...), ContinueWith(async ...), and any custom helper taking Func<Task> but storing the result as object. The symptom is characteristic and nasty: the outer task completes at the inner method's first await, so the work appears to finish immediately, the results are missing, and any exception is stored on a task nobody observes, so it disappears. Task.Run and await both unwrap automatically; .Unwrap() is the manual fix. In review, any ContinueWith with an async lambda is a defect until proven otherwise.

Is ContinueWith ever the right tool now?

Rarely, and always with explicit arguments. await is better in almost every case because it preserves exception semantics, cancellation and control flow, whereas ContinueWith silently defaults to TaskScheduler.Current and gives you a task whose result you must unwrap by hand. Where I still reach for it is in low-level plumbing that must not allocate a state machine, or where I need a continuation that runs regardless of outcome and must not capture context — for example, cleaning up a registration in the TaskCompletionSource bridge, where I pass TaskContinuationOptions.ExecuteSynchronously and TaskScheduler.Default deliberately. If I write it, I write out every argument, because the defaults are the trap.

Can you await the same task twice? What about awaiting it from two threads?

Yes to both, for Task and Task<T>. A task is a completed-or-not-yet promise, so awaiting it again after it has completed simply returns the stored result or rethrows the stored exception — no work re-runs. It is thread-safe: multiple awaiters register multiple continuations and all are released on completion. This is exactly what makes caching a Task<T> a valid pattern for expensive one-time initialisation, and it is a deliberate contrast with ValueTask, which may be backed by a pooled source and must be consumed exactly once. If an interviewer asks the question, they are usually setting up the ValueTask follow-up.

What does Task.Yield() do, and when have you needed it?

It returns an awaitable that is never completed synchronously, so awaiting it always forces a suspension and reschedules the rest of the method — to the captured context if there is one, otherwise to the thread pool. I have used it in three situations. To break up a long synchronous loop inside an async method on a UI thread so the message pump can run. To defend against a caller that would otherwise run my whole method synchronously and blow the stack — a recursive protocol handler, for example. And to guarantee that a method returns to its caller before doing anything expensive, which matters when a constructor-ish path calls an async initialiser. What it is not is a way to "make something async": the work still runs on a thread, just a different one, and one iteration later.

How do you decide whether a new API in your codebase should be async at all?

My rule is that the signature should tell the truth about the implementation, so a method is async when a realistic implementation performs I/O or waits on something external — even if today's implementation is an in-memory stub. Adding async later is a breaking change for every caller, and abstractions such as repositories and gateways almost always acquire real I/O eventually, so I make those async from day one. Conversely I resist making CPU-only helpers async and wrapping them in Task.Run inside the library: that hides a scheduling decision from the caller, and the caller is the one who knows whether offloading is appropriate. For hot in-memory paths where the answer is usually cached, I use ValueTask<T> so the synchronous case does not allocate — which is exactly the trade-off unit 05 is about.

03 Context, ConfigureAwait and deadlock

Docs: Async scenarios · ConfigureAwaitOptions (.NET 8+) · ConfigureAwait FAQ

SynchronizationContext is an abstraction with one method that matters: Post(callback, state), meaning "run this somewhere appropriate". What "appropriate" means is the whole story. On a WPF or WinForms UI thread it means "queue to the message pump so this runs on the UI thread", because touching a control from another thread throws. In classic ASP.NET it meant "restore HttpContext.Current, and hold the request's one-at-a-time lock". In ASP.NET Core, Kestrel, worker services and console apps it means nothing at all, because there is no context — SynchronizationContext.Current is null.

The capture

When TaskAwaiter.OnCompleted runs, it captures SynchronizationContext.Current (or, if that is null, a non-default TaskScheduler.Current) and arranges for the continuation to be posted back there. ConfigureAwait(false) returns a different awaiter — ConfiguredTaskAwaitable — that skips the capture, so the continuation runs wherever the completion happened. That is the entire mechanism. Two clarifications that separate good answers from great ones: the capture happens per await, not per method, so ConfigureAwait(false) on one await says nothing about the next one; and ConfigureAwait(false) never affects where the method starts — the code before the first suspension always runs on the calling thread.

The deadlock, precisely

Say it as a three-step story, not as a rule.

// Classic ASP.NET or a WPF button handler
public ActionResult Get()
{
    var data = GetDataAsync().Result;   // (1) UI/request thread blocks, still holding the context
    return View(data);
}

private async Task<string> GetDataAsync()
{
    var s = await _http.GetStringAsync(_url);   // (2) captures the context; continuation must run ON it
    return s.Trim();                            // (3) never reached: the one thread that could run it is blocked at (1)
}

One thread, two things that need it, and neither yields: a textbook deadlock. Three separate fixes exist, and knowing which one is real is the interview point. Do not block — make the caller async, which removes the cause. Use ConfigureAwait(false) on every await inside the library, which removes the requirement to come back to the context — but only if you get every await, in your code and in every library you call, which is why it is a mitigation and not a fix. Running the call on the pool with Task.Run(() => GetDataAsync()).Result also "works" and is the worst of the three: it burns a pool thread, hides the design error, and still blocks.

That is a feature when you deliberately abandon a pipeline, and a hazard when you use it to paper over failures you should be logging.

Should libraries still use ConfigureAwait(false) everywhere?

Yes — with an honest justification. On ASP.NET Core it changes no behaviour, so the argument is not "it prevents deadlocks in my app"; it is that a general-purpose library does not know whether its caller is a WPF app, a Blazor circuit, a legacy ASP.NET app or an add-in host with a custom context, and continuing on a captured context in library code is both slower (a Post per await) and a correctness hazard for those callers. Application code — controllers, hosted services, your own endpoints — does not need it, because you know your environment. Enforce it mechanically with the CA2007 analyzer scoped to library projects rather than by review discipline, and turn it off in application projects so the noise does not train people to ignore warnings. For await foreach and await using, the equivalents are .ConfigureAwait(false) on the IAsyncEnumerable<T> and on the IAsyncDisposable, which is easy to forget because the loop syntax hides the await.

Interview trap

"We added ConfigureAwait(false) and the deadlock came back." Of course it did — it only removes the context capture at the awaits you changed. One missed await, deep in a transitive dependency or in a finally block, is enough to re-create the requirement to return to the blocked context. The other half of the trap is the reverse: candidates who claim ConfigureAwait(false) "improves performance" on ASP.NET Core. There is no context there, so the only saving is a tiny amount of work in the awaiter — real in a hot loop measured in millions of iterations, invisible anywhere else. The credible answer is: it is a correctness convention for libraries, a micro-optimisation at best in apps, and never a substitute for not blocking.

Expected outcome

ConfigureAwait(false) works but stops working the moment you add a second await without it — try that too, so you feel how fragile the mitigation is. Task.Run(...).Result works while consuming two threads to do one thread's work; under load that is the shape that turns a deadlock into a starvation incident.

Interview Q&A

Explain the .Result deadlock as if to a mid-level engineer.

There is one thread that is allowed to run this code — the UI thread, or in classic ASP.NET the thread holding the request context. You block that thread on .Result. Meanwhile the async method you called captured that same context at its await, so when the HTTP call comes back the continuation is posted to the context and queues behind... the thread you blocked. The continuation cannot run until the thread is free, the thread cannot be freed until the task completes, the task cannot complete until the continuation runs. The fix is to not block: make the caller async so the thread is returned to the pump while waiting. Everything else — ConfigureAwait(false), offloading to Task.Run — treats the symptom.

Why does the same code not deadlock on ASP.NET Core?

Because ASP.NET Core has no SynchronizationContext: it was removed deliberately in the 1.0 redesign. With no context to capture, the continuation runs on whichever thread completed the I/O rather than needing the blocked one, so .Result completes. That is why teams migrating from classic ASP.NET find their sync-over-async code "suddenly works" — and it is exactly the trap, because the failure mode simply changed shape. Instead of a deadlock on a single request you get thread-pool starvation under load: every blocked request holds a pool thread, the pool injects new threads slowly, latency climbs, and eventually requests time out. A deadlock at least fails loudly in development; starvation only shows up at peak traffic.

Does ConfigureAwait(false) mean "run this on a background thread"?

No. It means "when this await resumes, do not bother marshalling back to the captured context". The continuation runs wherever the completion arrived — often an I/O completion thread, sometimes a pool thread, and sometimes, if the awaited task was already complete, no suspension happens at all and execution simply continues on the current thread. It also has zero effect on where the method begins: the code before the first incomplete await always runs on the caller's thread, so it cannot be used to offload synchronous work. If a candidate says it moves work to the background, they have the model wrong, and the follow-up question is usually "then how do you offload CPU work?" — the answer being Task.Run, at the call site, chosen by the application rather than the library.

What does ConfigureAwaitOptions.SuppressThrowing give you that a try/catch does not?

Intent and precision. try { await t; } catch { } swallows everything, including exceptions from code you did not mean to cover, and an empty catch is a review smell that hides real bugs. SuppressThrowing applies to exactly one await, says in the type system "I am waiting for this to finish and I do not care how it ended", and marks the task's exception observed so it does not later surface through TaskScheduler.UnobservedTaskException. I use it in shutdown paths — waiting for a consumer loop to drain after cancelling it, where the expected outcome is an OperationCanceledException that carries no information. What I do not do is use it on a task whose failure would be news; suppressing that is how you get a silently degraded service.

How does ConfigureAwait apply to await foreach and await using?

Both hide awaits, so both need it explicitly. For an async stream you call .ConfigureAwait(false) on the IAsyncEnumerable<T>, which returns a ConfiguredCancelableAsyncEnumerable<T> that the await foreach then consumes — this also gives you .WithCancellation(token), and the two are chained together. For await using, the disposable itself has a ConfigureAwait(false) extension. The reason people miss both is that there is no visible await keyword on the line, and the CA2007 analyzer does flag them, which is another argument for turning the analyzer on rather than relying on reading. In a library that streams results, forgetting it means every element resumes on the caller's UI context — a per-item Post, which is measurable and, in a Blazor circuit, visible as jank.

When is capturing the context essential rather than optional?

Whenever the code after the await has thread affinity. UI frameworks are the obvious case: WPF, WinForms and MAUI throw if you touch a control from the wrong thread, so a view model that updates bound properties must resume on the dispatcher. Blazor Server's renderer is the same idea over a circuit. Beyond UI there is anything with thread-local or context-local requirements — a legacy COM component with apartment affinity, code that reads HttpContext.Current on .NET Framework, or a testing framework that requires assertions on its own context. My rule of thumb in review: application-level code that touches presentation state keeps the default; everything below it — services, repositories, HTTP clients, serializers — uses ConfigureAwait(false).

You inherit a .NET Framework app full of .Result. What is your migration plan?

I do not start by deleting .Result calls at random, because a half-converted call chain is how you turn a working app into an intermittent deadlock. First I inventory the blocking sites with an analyzer or a Roslyn script and classify them by whether the callee is genuinely async underneath. Then I convert whole vertical slices from the entry point down — controller to service to data access — so each slice is async end to end and there is no boundary left in the middle. For slices I cannot convert yet, I leave the blocking call in place, isolated behind a single named method, and I add ConfigureAwait(false) in the library layers to reduce the blast radius. Where the app runs on classic ASP.NET, I check Task.Run workarounds carefully, because they are the ones that break silently when the app moves to ASP.NET Core and the context disappears. Throughout, I keep thread-pool metrics on a dashboard, since starvation is the failure mode of a partial migration.

What is ForceYielding for, and how is it different from Task.Yield()?

Functionally they are close: both guarantee the continuation does not run synchronously. ForceYielding fuses that guarantee into an existing await rather than adding a separate one, so you get one suspension instead of two, and you can combine it with SuppressThrowing. I reach for it in two places. In a protocol handler where completions can arrive synchronously in a long chain, forcing a yield breaks the stack dive that would otherwise overflow. And in an API where I want to guarantee that control returns to the caller before any expensive work starts — a "start this and give me back control now" contract — which is otherwise surprisingly hard to express, because an await that completes synchronously simply keeps running on the caller's thread.

Why did ASP.NET Core remove the synchronization context, and what did that cost?

It was removed for throughput and simplicity: a per-request context means a Post for every await in the request pipeline, plus the machinery to restore ambient state, and both cost measurably at Kestrel's target request rates. Removing it also removed the single-threaded-per-request model that made classic ASP.NET deadlock-prone. What it cost is the guarantee that request-scoped ambient state is restored for you: anything you need across awaits must ride on ExecutionContext instead, which is why IHttpContextAccessor is implemented over AsyncLocal<T> and why capturing HttpContext in a background task is now explicitly unsafe — the context object is pooled and reused once the response completes. It also means "it works locally" tells you nothing about ordering: continuations can run on any pool thread, so latent thread-safety bugs in per-request services surface under load.

How would you decide whether to enable CA2007 across a repository?

Per project, not per repository. I enable it as an error in projects that are libraries consumed by unknown hosts — NuGet packages, shared SDKs, anything a desktop or Blazor app might reference — because there the missing ConfigureAwait(false) is a genuine correctness risk for a caller I cannot see. I leave it off in application projects: on ASP.NET Core it produces hundreds of warnings for zero behavioural change, and a wall of ignorable warnings is worse than no analyzer at all because it teaches the team that warnings do not matter. If a solution mixes both, I put the setting in a Directory.Build.props for the library folder rather than repeating it, and I pair it with a one-paragraph note in the contributing guide explaining why the rule differs between folders — otherwise someone will "helpfully" unify the settings six months later.

04 Thread pool and starvation

Docs: The managed thread pool · Runtime config: threading · ASP.NET Core diagnostic tools

Async removes the need for threads; the thread pool decides how many you actually get. Every question about latency spikes, "it is fine until 200 rps", and "adding a retry made it worse" resolves in this unit, so it is worth knowing the pool's actual behaviour rather than the folklore.

What the pool is

Since .NET 6 the portable thread pool — written in C#, shared across platforms — is the default everywhere, replacing the old native Windows implementation. It holds a global queue plus per-thread local queues (work queued from inside a pool thread goes to that thread's local queue and is taken LIFO, which keeps caches warm; other threads steal from the tail). On Windows, I/O completions still arrive via completion ports and are dispatched onto pool threads; on Linux and macOS an epoll/kqueue-based poller does the same job. The pool's key parameters are:

  • Minimum threads, default Environment.ProcessorCount. Up to this count, a new thread is created immediately when work arrives and no thread is free.
  • Above the minimum, the pool switches to a hill-climbing algorithm: it adds roughly one thread per 500 ms while work is queued and throughput is improving. That rate is the single most important number in this unit.
  • Maximum threads, a large number (thousands) you should never rely on reaching, since you will have exhausted memory or the CPU long before.

Starvation, and why it looks like a network problem

Starvation is what happens when pool threads are blocked instead of working. Each blocked thread removes capacity; the pool responds at one thread per 500 ms; if requests arrive faster than that, the queue grows without bound. The characteristic signature — worth memorising as a set, because it is how you win the diagnosis question:

SymptomWhy it happens

// 3. Task.Run wrapping blocking work on a server: moves the block, adds a hop.

// 4. A sync-only dependency behind an async-looking facade.

// 5. Fire-and-forget CPU work stealing request threads.
_ = Task.Run(() => RebuildIndex());              // unbounded, unobserved, competes with requests

Where continuations run, revisited

Unit 01 said the continuation runs inline on the completing thread when there is no context. On a server that thread is usually an I/O thread, and that has a practical consequence: the work you do immediately after an await is charged to whoever completed your task. Deserialising a 20 MB response, or running a synchronous crypto operation, right after await httpClient.GetStreamAsync(...), runs on the completion thread and delays every other completion queued behind it. If you have genuinely CPU-heavy post-processing, that is one of the few legitimate uses of Task.Run in a server: get off the completion path deliberately, at a place you have chosen.

The second half of the trap is the opposite mistake: assuming starvation must mean sync-over-async. Interview Q&A

Describe thread-pool starvation and how you would confirm it in production.

Starvation is when pool threads are blocked rather than working, so queued work waits for the pool's injection rate — about one thread per 500 ms above the minimum — instead of for a free thread. I confirm it with three signals together. Thread count climbing well past core count while CPU stays low: that combination means waiting, not computing. A sustained non-zero ThreadPool.PendingWorkItemCount or the equivalent counter from dotnet-counters. And a dump or dotnet-stack capture taken during the incident, where I expect many threads parked in ManualResetEventSlim.Wait, Monitor.Wait or a socket read under a Task.Wait frame. The dump is what turns a hypothesis into an answer, because it names the exact call site that is blocking.

Why does starvation produce stepped latency rather than a smooth curve?

Because relief arrives in discrete units. Above the minimum, the pool adds one thread roughly every half second while work is queued. Each new thread picks up a queued item and shortens the queue briefly, so latency dips, then climbs again as arrivals outpace the single new worker. Plotted over a minute you get a sawtooth on a rising trend. Recognising that shape is genuinely useful on call, because it distinguishes starvation from a slow dependency — a slow dependency raises latency smoothly and raises it for the calls that touch it, whereas starvation raises latency for everything in the process, including endpoints that touch nothing.

Is Task.Run ever appropriate in ASP.NET Core?

Rarely, and never as a way to make blocking code "async". The pool threads it uses are the same threads serving requests, so offloading blocking work to it does not create capacity; it moves the block and adds a queueing hop. Three cases where I do use it. Genuinely CPU-bound work that would otherwise run on an I/O completion thread and delay other completions — image resizing, a large deserialise — where I am deliberately choosing to get off the completion path. Breaking a stack dive when a completion chain would otherwise run synchronously and deeply. And fitting a synchronous third-party callback into an async pipeline where I have already bounded the concurrency. Outside of those, seeing Task.Run in a request path is a review conversation.

What actually happens on the machine when you await an HTTP call?

The socket write is issued and an overlapped/epoll-style completion is registered with the OS; no managed thread is waiting. Your method returns to its caller, and if that caller is the request pipeline, the thread goes back to the pool and serves someone else. When the response arrives, the OS signals completion, a pool thread picks it up from the completion queue, and the continuation runs on it — inline, since ASP.NET Core has no synchronization context. So during a 40 ms call there is no thread charged to your request; there is a socket, a registration, and a heap-allocated state machine holding your locals. That last part is why in-flight state, not threads, becomes the memory story at high concurrency, and why you should care about how much you capture in a long-lived async method.

When would you legitimately call SetMinThreads?

When I have a known, bounded source of blocking that I cannot remove yet, and a burst profile where the 500 ms injection rate is the binding constraint. The two real cases in my experience are a vendor SDK with only synchronous APIs, and process startup, where a cold pool at the size of the core count meets a thundering herd of readiness checks and cache warms. I treat it as a documented mitigation with an owner and a removal condition, not a setting. I also set it to a number derived from something — expected concurrent blocking calls plus headroom — rather than a round number someone liked, and I watch memory afterwards, because each thread costs its stack. What I never do is raise it and consider the problem solved; if I do not also file the work to remove the blocking, I have converted an outage into a slow leak.

Your CPU is at 15%, requests time out, and the dependency dashboards are green. What next?

That pattern says the process, not the dependencies. I would grab a dump or a dotnet-stack report while it is happening, because the evidence disappears when load drops. Then I count threads by stack shape: if hundreds sit under Task.Wait, .Result, Monitor.Enter or SemaphoreSlim.Wait, that is starvation and the stacks name the culprit. If instead they sit in GC frames I am looking at allocation pressure; if they sit in a lock convoy on one object, it is contention rather than starvation. Meanwhile I would check ThreadPool.PendingWorkItemCount and thread count over time, and confirm whether the incident correlates with a deploy. The immediate mitigation might be raising min threads or shedding load; the fix is whatever the stacks named.

How do async and the connection pool interact — can async make things worse?

Yes, and this is a good senior answer because it shows async is not free. Async raises the number of operations you can have in flight, so it moves the bottleneck outward to whatever is next: the ADO.NET connection pool (100 by default for SQL Server), HTTP connection limits, or the downstream service itself. A synchronous app naturally throttled itself at the thread count; an async one will happily queue 5,000 requests against a 100-connection pool, and you get timeouts inside the pool with stacks that point at OpenAsync, not at your code. The lesson is that removing one queue exposes the next, so when I make something async I also make its concurrency explicit — a bounded channel, a semaphore, or the pool's own limits configured and monitored — rather than letting the new headroom become unbounded pressure downstream.

What is the local-queue/work-stealing design, and when does it matter to you?

Work queued from inside a pool thread goes into that thread's local queue and is taken last-in-first-out, which keeps the freshly touched data in cache; idle threads steal from the tails of other threads' queues. It matters in two ways. It makes fine-grained continuations cheap, which is part of why awaiting a completed task and chaining continuations is fast. And it makes execution order deliberately non-FIFO, so any code that assumes queued work items run in submission order is wrong — I have seen that assumption baked into a "sequential" background processor that only worked under light load. If you need ordering, get it from a Channel with a single reader, not from the pool.

How do you keep a starvation regression from coming back after you fix it?

Three layers. Prevention at build time: analyzers that make .Result, .Wait() and synchronous SemaphoreSlim.Wait in async contexts build errors, so the pattern cannot re-enter the codebase. Detection in test: a load test in CI, even a modest one, that asserts p99 latency and thread count under a fixed rate — starvation shows up as a thread-count assertion failure long before it shows as a latency one. Observability in production: thread count, queue length and a starvation alert on the combination of low CPU with high queue depth, plus a runbook that says "take a dump first, then mitigate", because the evidence is ephemeral. I would also add the incident's exact call site as a named test if it can be reproduced deterministically.

Does async help a CPU-bound service at all?

Not directly — if every request burns CPU, the throughput ceiling is cores, and async adds state machines and scheduling to a system that has nothing to wait for. Where it still earns its place is at the edges: a CPU-bound service usually still reads a request body, writes a response, logs, and talks to a cache, and keeping those asynchronous means the cores spend their time on the actual work rather than on blocked threads. The design that matters more for CPU-bound work is admission control — a bounded queue with a fast rejection path so you fail quickly at capacity rather than accumulating latency — and, if the work is long, moving it out of the request path entirely onto a queue with a job id. I would say plainly in an interview that async is the wrong lever here; naming when a technique does not apply usually scores better than advocating it everywhere.

05 ValueTask and allocation

Docs: ValueTask<TResult> · Understanding the whys, whats, and whens of ValueTask

ValueTask<T> exists for one shape of problem: an operation that is asynchronous in principle but synchronous most of the time, called often enough that the Task<T> allocation shows up in a profile. The canonical example is a buffered stream read. Stream.ReadAsync returns from an in-memory buffer 99 times out of 100 and only actually hits the disk on the hundredth call — but with Task<T>, all hundred calls allocate a task object, and at a million reads per second that is real garbage.

What it actually is

ValueTask<T> is a struct that is a discriminated union of three things: a raw T (the operation completed synchronously — no allocation at all), a Task<T> (it did not, so fall back to the normal machinery), or an IValueTaskSource<T> plus a token (a reusable, poolable completion source). The non-generic ValueTask and IValueTaskSource arrived in .NET Core 2.1; ValueTask<T> itself in 2.0. That third case is the interesting one: it is what lets Socket, Channel and Kestrel perform millions of asynchronous operations while allocating essentially nothing, because a single pooled source object is reused for every operation on that connection, distinguished by a version token.

And that pooling is exactly where the restrictions come from. Once you have awaited a ValueTask backed by a pooled source, the source may immediately be recycled for the next operation, so the token you hold is stale. Hence the rules:

Producing one

// The everyday case: a cache that is usually warm. No allocation on the hot path.
public ValueTask<User> GetUserAsync(int id, CancellationToken ct)
{
    if (_cache.TryGetValue(id, out User? cached))
        return new ValueTask<User>(cached);        // synchronous: zero allocation

    return new ValueTask<User>(LoadAsync(id, ct)); // slow path: wraps a Task, one allocation

    async Task<User> LoadAsync(int id, CancellationToken ct)
    {
        var u = await _db.FindAsync(id, ct).ConfigureAwait(false);
        _cache.Set(id, u);
        return u;
    }
}

// The advanced case: opt one method into a pooled state machine (C# 10 allows the
// attribute on a method, not just a type). Reuses the boxed state machine from a pool
// instead of allocating one per suspension.

public async ValueTask<int> ReadChunkAsync(CancellationToken ct) { /* ... */ }

The local-function trick in the first example matters: writing the method as async ValueTask<User> with an if would allocate a state machine box on the slow path and still create the async plumbing, whereas the split version keeps the fast path free of both. This is the standard shape in the BCL — you will see it in Stream, Channel and PipeReader.

Interview trap

"Is ValueTask just a faster Task?" No, and answering yes is a strong negative signal — it says you have adopted a type without reading its contract. The right answer names the constraint before the benefit: it is a struct with a single-consumption contract, and violating that contract produces non-deterministic corruption rather than a clean exception, which makes it far more dangerous than the allocation it saves. The related trap is the interviewer asking you to review this line:

ValueTask<int> v = reader.ReadAsync(ct);
if (v.IsCompleted) log.Debug("fast path");
int a = await v;
int b = await v;                      // BUG: second await on a possibly pooled source

Reading IsCompleted is fine. The second await is the defect, and the reason it is dangerous is that in a unit test with an unpooled source it will pass, and in production against a pooled socket source it will hand you another connection's bytes.

Try it — measure the thing everyone assumes

1. With BenchmarkDotNet and [MemoryDiagnoser], benchmark a cache lookup that hits 95% of the time, implemented three ways: async Task<T>, ValueTask<T> with the split fast path shown above, and async ValueTask<T> written naively with an if.

2. Repeat with a 5% hit rate.

Expected outcome

1. The split ValueTask version allocates nothing on the 95% path and wins clearly. The naive async ValueTask version allocates on the slow path anyway and gains far less than people expect — the state machine box, not the task object, is often the bigger cost.

2. At a 5% hit rate the gap collapses and ValueTask may lose, because you now pay struct copying on every call plus the allocation you were trying to avoid. That inversion is the point of the exercise: the type is a bet on the synchronous-completion rate, and you should know that rate before you take the bet. Pair it with PoolingAsyncValueTaskMethodBuilder and measure again — pooling helps the asynchronous path but adds its own bookkeeping, and it is not a free win either.

Interview Q&A

When would you choose ValueTask<T> over Task<T>?

When three things are true together: the operation usually completes synchronously, it is called at a rate where allocation matters, and the consumer is disciplined code I control or an API whose contract I can state clearly. Buffered reads, cache lookups, channel reads and object-pool rentals fit. If any of the three fails I use Task<T>, because the single-consumption contract is a real burden on every caller forever, and the failure mode when someone violates it is non-deterministic wrong data rather than an exception. I would also say that I want a benchmark, not an intuition: the struct is larger than a reference and gets copied at every call boundary, so on paths that are usually asynchronous it can be a net loss.

What exactly goes wrong if you await a ValueTask twice?

It depends on what backs it, which is precisely the problem. If it wraps a raw value or a Task, nothing happens and your tests pass. If it wraps an IValueTaskSource — a socket, a channel, a pooled builder — that source is versioned and is recycled once the first await completes, so the second await either observes a completely different operation's result, or throws InvalidOperationException about a stale token, or hangs waiting for something that already completed. It is a data-corruption bug that only appears under the conditions where the type is actually worth using. That asymmetry is why I treat "await once" as a hard rule rather than advice, and why Preserve() exists for the rare case where you genuinely need to observe twice.

How does IValueTaskSource achieve zero-allocation async, and where have you seen it?

The object implementing it is the operation's completion machinery, and it is reused. It exposes GetStatus(token), OnCompleted(...) and GetResult(token), with the token identifying which operation the caller thinks it is observing, so a stale caller is detected instead of silently served. ManualResetValueTaskSourceCore<T> in the BCL implements the fiddly parts for you. You see it in Socket's SocketAsyncEventArgs-based operations, in System.Threading.Channels, in PipeReader, and inside Kestrel — anywhere a long-lived object performs an unbounded sequence of asynchronous operations. I would write one myself only for a similar shape: a connection object doing millions of reads. For everything else the complexity is not repaid.

What does PoolingAsyncValueTaskMethodBuilder do?

It replaces the per-suspension allocation of the boxed state machine with a rented object from a pool. You opt in per method with [AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))] — C# 10 allowed the attribute on methods rather than only on types, which is what made it practical. It targets the cost most people forget: when an async method suspends you allocate the state machine box and the result object, and pooling addresses the first. It is not free — renting, returning and the associated bookkeeping cost something, and pooled objects survive to gen 2 in a way short-lived boxes do not — so it is a "measure it on the specific method" tool. It also only applies to ValueTask-returning methods, and it inherits every single-consumption rule.

Would you expose ValueTask<T> from a public library API?

Only with a strong reason, documented at the API. The problem is that the contract binds every caller I will never meet, and the common conveniences — awaiting twice, storing the result in a list and calling WhenAll, passing it to a Polly-style retry wrapper, mocking it in a test framework that replays the value — all quietly break. If I do expose it, the API is one where the synchronous case dominates and performance is the reason people chose the library; I document "await exactly once" in the XML docs, and I make sure the framework-facing entry points still take and return Task. In an internal hot path within one assembly, where I can see every caller, my bar is much lower.

Why can a ValueTask-based API be slower than a Task-based one?

Because you traded an allocation for copying and indirection. ValueTask<T> is a multi-word struct — a result, an object reference and a token — so it gets copied at every call boundary, does not fit in a return register, and forces a branch on every consumption to discover which of the three states it is in. If the operation usually completes asynchronously you pay all of that and then allocate a Task anyway. The generational GC also makes the comparison less lopsided than it looks: a short-lived task object dies in gen 0, which is close to free, whereas a pooled source survives collections. That is why the guidance is "default to Task, switch when a benchmark on your workload says so", and why I would be suspicious of a codebase that had converted every signature.

How do you compose several ValueTasks?

Convert each to a Task exactly once with .AsTask() and compose those, or — better where the shape allows — await them sequentially, which is what you want anyway when they usually complete synchronously, because there is nothing to overlap. There is no ValueTask.WhenAll in the BCL, and the reason is instructive: any general implementation would have to observe each source, which conflicts with single consumption and with pooling. If I find myself needing WhenAll over ValueTasks regularly, I take it as a signal that the API should have returned Task in the first place, since the caller's usage pattern is fan-out rather than a tight sequential hot loop.

A junior engineer has changed 300 method signatures from Task to ValueTask "for performance". How do you handle it in review?

I would not argue from authority; I would ask for the benchmark and the synchronous-completion rate for a representative sample of those methods. Then I would name the risk concretely — the single-consumption contract now applies to 300 call sites, including tests and any future caller, and violating it fails non-deterministically rather than loudly — and point at the ones where the API crosses a boundary the team does not control. Usually the outcome is to keep the change on the handful of genuinely hot, usually-synchronous methods and revert the rest, plus an analyzer or a convention so the exception is visible. I would also use it as a teaching moment about the real distribution of async cost: for most services, allocation from state machines is dwarfed by serialisation, logging and the response body.

How does ValueTask interact with ConfigureAwait and cancellation?

ValueTask has ConfigureAwait(bool) returning a ConfiguredValueTaskAwaitable, so context suppression works the same way. What it does not have, as of .NET 10, is the ConfigureAwaitOptions overload — that was added to Task in .NET 8 only, so SuppressThrowing and ForceYielding are unavailable and you have to call .AsTask() first, which defeats the point. Cancellation is unchanged: the token goes in as a parameter and a cancelled operation surfaces as an OperationCanceledException from the await, exactly as with Task. The one wrinkle is WaitAsync(timeout), which lives on Task, so timing out a ValueTask also means converting it first.

Where does the allocation actually go in a modern async method, and what would you optimise first?

For a method that suspends, the two costs are the boxed state machine holding the hoisted locals and the returned task object; for one that never suspends, in Release, neither. So the first thing I optimise is not the return type at all — it is how many methods suspend and how much they capture. Splitting a method so the common path returns before any await, avoiding closures that capture more than they need, and using static lambdas with explicit state arguments usually beat a type change. After that I look at the real allocation in a typical service, which is almost never the async machinery: it is the JSON buffers, the logging string interpolation, the LINQ over collections in the request path. I would say that plainly in an interview, because knowing where async cost genuinely sits — and where it does not — is more valuable than reciting the ValueTask rules.

06 Cancellation, cooperatively

Docs: Cancellation in managed threads · CancellationTokenSource · TimeProvider (.NET 8+)

.NET has no way to abort an operation from outside. Thread.Abort was removed in .NET Core precisely because injecting an exception at an arbitrary instruction leaves locks half-held and invariants broken. So cancellation is cooperative: a CancellationToken is a request, and code that wants to be cancellable must check it or register a callback. Everything else in this unit follows from that one design decision — including why cancellation is unreliable in exactly the places people forget to plumb it.

The two halves

CancellationTokenSource is the producer half: it owns the state, is IDisposable, and has Cancel(), CancelAfter(TimeSpan) and, since .NET 8, CancelAsync(). CancellationToken is the consumer half: a struct, freely copyable, with IsCancellationRequested, ThrowIfCancellationRequested(), Register(...) and WaitHandle. Never hand a source to a consumer — that gives them the ability to cancel work they do not own, which is a real bug I have found in production more than once.

// Producing: a per-operation timeout linked to the caller's token.
public async Task<Report> BuildAsync(CancellationToken ct)
{
    using var timeout = CancellationTokenSource.CreateLinkedTokenSource(ct);
    timeout.CancelAfter(TimeSpan.FromSeconds(30));

    try
    {
        return await _slow.RunAsync(timeout.Token).ConfigureAwait(false);
    }
    catch (OperationCanceledException) when (!ct.IsCancellationRequested)
    {
        // Distinguish MY timeout from the CALLER's cancellation. Without this filter,
        // a 30 s timeout is reported to the client as "you cancelled", which is a lie
        // that costs an hour in the next incident review.
        throw new TimeoutException("Report generation exceeded 30 s.");
    }
}

// Consuming: check at the top of each iteration and pass the token onward. Both matter.
await foreach (var batch in _source.ReadAllAsync(ct).ConfigureAwait(false))
{
    ct.ThrowIfCancellationRequested();               // covers the synchronous work below
    await _sink.WriteAsync(batch, ct).ConfigureAwait(false); // propagate, never pass CancellationToken.None
}

Two details in that snippet are worth stating explicitly, because they are common review findings. The linked source is using-scoped: a linked source registers a callback on its parent, and if you forget to dispose it, the registration keeps it — and everything it closes over — alive for as long as the parent token lives. With a long-lived parent such as IHostApplicationLifetime.ApplicationStopping, that is a textbook leak that shows as steadily growing memory in a long-running service. And the exception filter distinguishes whose cancellation fired; a bare catch (OperationCanceledException) cannot tell a client disconnect from your own timeout.

A task also has a state, and cancellation is not the same as faulting. A task ends Canceled only when the OperationCanceledException that escaped carries the token the operation was given; if it carries a different token — or none — the task ends Faulted instead. This is why passing the token to ThrowIfCancellationRequested() rather than throwing new OperationCanceledException() by hand actually matters, and it is a favourite deep-dive question.

Timeouts, and the testability problem

Timeouts implemented with CancelAfter or Task.Delay are hard to test, because a unit test that waits 30 seconds is a unit test nobody runs. TimeProvider, added in .NET 8, is the fix: an abstraction over "what time is it" and "wake me later" that both CancellationTokenSource and Task.Delay accept, with a FakeTimeProvider in Microsoft.Extensions.TimeProvider.Testing that lets a test advance the clock instantly.

// Injectable clock: the constructor takes TimeProvider.System in production.
public sealed class Poller(TimeProvider time)
{
    public async Task<Result> PollAsync(CancellationToken ct)
    {
        using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
        cts.CancelAfter(TimeSpan.FromSeconds(30), time);            // .NET 8+ overload
        await Task.Delay(TimeSpan.FromSeconds(1), time, cts.Token); // .NET 8+ overload
        // ...
    }
}

// In the test: no real waiting at all.
var fake = new FakeTimeProvider();
var task = new Poller(fake).PollAsync(CancellationToken.None);
fake.Advance(TimeSpan.FromSeconds(31));
await Assert.ThrowsAsync<OperationCanceledException>(() => task);

The other modern timeout tool is Task.WaitAsync(TimeSpan), added in .NET 6, which gives you "this task, but fail after N" without building a source or a WhenAny race — and unlike the old WhenAny(task, Task.Delay(n)) idiom it does not leave a timer running and does not leave the loser unobserved.

Interview trap

Swallowing cancellation, and mistaking it for success. Three failures stack up here and interviewers probe all of them. First, catch (OperationCanceledException) { /* log and continue */ } inside a loop turns shutdown into an infinite loop that ignores the stop signal — the host then kills the process at the shutdown timeout and you lose in-flight work. Second, treating a cancelled operation as a completed one: a write that was cancelled halfway leaves partial state, so cancellation must be handled with the same care as an error. Third — the subtle one — cancelling after the side effect: an HTTP POST that was cancelled while awaiting the response may well have been processed by the server, so "cancelled" never means "did not happen". At lead level, say that out loud: cancellation is a request to stop waiting, not a rollback, and anything that needs exactly-once behaviour needs idempotency keys, not a token.

Try it — leak a token registration, then find it

1. In a loop of 100,000 iterations, create CancellationTokenSource.CreateLinkedTokenSource(appStopping) without disposing it, each closing over a large byte array. Take a heap snapshot with dotnet-gcdump and look at what roots the arrays.

2. Add using and repeat. Then do the same experiment with token.Register(...) whose returned CancellationTokenRegistration you never dispose.

Expected outcome

Without disposal, the objects are rooted through the parent token's registration list — the gcdump shows a chain from the long-lived CancellationTokenSource to your arrays — and memory grows monotonically until the app stops. With using, the registration is removed on dispose and the graph is clean. The Register variant behaves identically, which is the general lesson: any registration on a long-lived token is a subscription, and subscriptions to long-lived publishers must be unsubscribed. This is the most common real-world cancellation bug I see, well ahead of anything involving exceptions.

Interview Q&A

Why is cancellation cooperative rather than pre-emptive?

Because pre-emption cannot be made safe. Thread.Abort injected an exception at an arbitrary point, which could land between acquiring a lock and entering the try, or in the middle of updating a data structure, leaving the process in a state no code was written to handle; it was removed from .NET Core for that reason and throws PlatformNotSupportedException. The cooperative model instead puts the decision at points the author chose, so invariants hold and finally blocks run. The cost is that cancellation is only as good as the plumbing: an operation that never checks the token, or a library that ignores it, simply is not cancellable, which is why "pass the token everywhere" is a real discipline and not ceremony.

What is the difference between OperationCanceledException and TaskCanceledException?

TaskCanceledException derives from OperationCanceledException; you get the derived one when awaiting a task that finished in the Canceled state, and the base one from ThrowIfCancellationRequested and most BCL APIs. Always catch the base type — catching the derived one silently misses half the cases. The other half of the answer is that a task ends up Canceled rather than Faulted only when the escaping exception's token matches the token the operation was handed, so throwing new OperationCanceledException() without the token produces a faulted task, which then shows up in your error rate and pages someone. Use ThrowIfCancellationRequested() and let the framework get it right.

How do you distinguish "the caller cancelled" from "my own timeout fired"?

By checking the caller's token in an exception filter: catch (OperationCanceledException) when (!callerToken.IsCancellationRequested) means the cancellation came from my linked timeout source, so I translate it into a TimeoutException. The distinction matters operationally, because the two have opposite meanings on a dashboard — client cancellations are usually normal traffic (a user navigated away) and should not count against your error budget, while timeouts against a dependency are a signal about that dependency. I also check OperationCanceledException.CancellationToken when there are several linked sources, and in ASP.NET Core I separate RequestAborted from internal timeouts in logging so the two are never aggregated into one meaningless "cancelled" metric.

What are the leak risks with CancellationTokenSource?

Two, both from registrations on long-lived tokens. A linked source created with CreateLinkedTokenSource registers a callback on each parent, so if the parent is application-lifetime scoped and you never dispose the child, the child and everything it references stays alive — per request, that is an unbounded leak. The same applies to a raw token.Register(...) whose CancellationTokenRegistration you never dispose. There is also a timer to consider: CancelAfter schedules one, and disposing the source cancels it, so a source that is never disposed keeps a timer entry alive as well. My rule is that every CreateLinkedTokenSource and every Register is written with a using or an explicitly stored registration disposed in a finally, with no exceptions.

Should every async method take a CancellationToken?

Every one that can wait, yes, as the last parameter, and it should be passed to everything it calls. The exceptions are methods that genuinely cannot be interrupted — a final flush that must complete for correctness, or a cleanup path in a finally, where accepting a token and then ignoring it would be a lie. For those I either omit the parameter or take one and document that it applies only to part of the operation. I resist defaulting the parameter to default in internal code, because a defaulted token is how cancellation quietly stops propagating: someone adds a call, forgets the argument, and there is no compiler error. In public APIs the default is usually necessary for source compatibility, so there I rely on an analyzer instead — CA2016, which flags a token that is not forwarded.

What does Task.WaitAsync(TimeSpan) give you over the old WhenAny plus Task.Delay idiom?

Correctness and cleanliness. The classic idiom races your task against a delay, and it has three defects: the timer keeps running after the winner is decided unless you cancel it, the losing task remains unobserved so its eventual failure can surface as an unobserved exception, and you must remember to re-await the winner to get its result or exception. WaitAsync, added in .NET 6, handles all three and throws TimeoutException, which is also more honest than a cancellation exception. It also has an overload taking a CancellationToken and, since .NET 8, a TimeProvider, so it composes with the testable-clock story. The one thing it does not do — and cannot — is stop the underlying work; the task keeps running, so if the work holds a scarce resource you still need real cancellation underneath.

How do you make a genuinely non-cancellable operation cancellable?

You cannot make the operation itself stop, so you have to be honest about which of two things you want. If you only need to stop waiting, race it: await work.WaitAsync(timeout, ct) or a WhenAny against a token-driven task, and accept that the work continues in the background, which means you must ensure it cannot corrupt state or leak — usually by giving it its own lifetime and observing its eventual outcome for logging. If you need the work to actually stop, the only options are inside it: check the token in its loop, or use an API that supports interruption, such as closing the underlying socket or connection to force the pending call to fail. For a synchronous third-party call with neither, I isolate it behind a bulkhead — a bounded set of threads, or a separate process — so a stuck call degrades one slice rather than the service.

How should a BackgroundService handle its stopping token?

It should treat it as the only shutdown signal, and it must return promptly when it fires, because the host waits only HostOptions.ShutdownTimeout — 30 seconds by default — before killing the process. In practice that means the outer loop awaits with the token, the OperationCanceledException is allowed to escape the loop (or caught deliberately at the very top just to log a clean-shutdown message), and any in-flight unit of work is either finished quickly or checkpointed so it can resume. Two traps: catching cancellation inside the loop and continuing turns the service into one that cannot be stopped; and doing long synchronous work in ExecuteAsync before the first await blocks host startup, since the host awaits your method up to its first suspension. For anything with a real drain requirement I stop accepting new work on the token and use a separate, longer-lived path to finish what is in flight, with the timeout raised deliberately.

A cancelled HTTP POST — did the server process it?

You do not know, and that is the correct answer. Cancelling means you stopped waiting for the response; the request may already have been received and applied. So cancellation cannot be treated as a rollback. In design terms this pushes you to idempotency: an idempotency key on the request so a retry is safe, or a state machine where the operation is recorded as "attempted" before the call and reconciled afterwards. It is also why I am careful about cancelling writes on RequestAborted in a service that mutates state — the user disconnecting is not a reason to abandon a half-applied transaction, and the right behaviour is often to finish the unit of work and skip only the response. Interviewers like this question because it separates people who have plumbed tokens from people who have operated a system that had partial failures.

What would you look for in a code review specifically about cancellation?

Six things, in order. Tokens accepted but not forwarded — that is CA2016 and I would rather the analyzer caught it. CancellationToken.None or default passed explicitly, which usually means someone silenced a compiler error rather than thought about it. Bare catch (OperationCanceledException) without a filter, which conflates the caller's cancellation with my own timeouts. Linked sources or registrations without using, which leak. Loops that check IsCancellationRequested but never call ThrowIfCancellationRequested, so cancellation silently produces a partial result reported as success. And finally blocks that perform async cleanup using the same token that was just cancelled, so the cleanup itself is cancelled — the fix there is a fresh token with a short timeout for the cleanup path.

07 Composition and throttling

Docs: Task.WhenAll · Task.WhenEach (.NET 9+) · Parallel.ForEachAsync · System.Threading.Channels

One await is easy. The interview lives in what happens when you have five hundred of them: how they overlap, how errors combine, how you keep from flooding the thing you are calling, and how you get partial results out before the slowest one finishes.

The three combinators, and what each really promises

Task.WhenAll returns a task that completes when every input has completed. Crucially it always waits for all of them, even after one fails — there is no fail-fast. If several fail, the returned task holds an AggregateException with all of them, but await rethrows only the first, so the others are visible solely through task.Exception.InnerExceptions. That asymmetry is the number-one WhenAll interview question.

Task.WhenAny completes as soon as one input does, and hands you the winning task — which you must then await to get its result or exception. The losers keep running, and their failures become unobserved exceptions unless you deal with them. Historically it was also the standard timeout idiom, a role now better filled by WaitAsync.

Task.WhenEach, added in .NET 9, is the one that removes a whole class of hand-rolled code: it returns an IAsyncEnumerable<Task> that yields each task as it completes, so you can process results in completion order without a WhenAny-and-remove loop that is O(n²) and easy to get wrong.

// .NET 9+: stream results as they arrive, in completion order.
List<Task<Quote>> quotes = suppliers.Select(s => s.GetQuoteAsync(sku, ct)).ToList();

await foreach (Task<Quote> finished in Task.WhenEach(quotes).WithCancellation(ct))
{
    try   { Render(await finished); }              // already complete: the await is free
    catch (HttpRequestException ex) { LogSupplierFailure(ex); }   // one failure does not stop the rest
}

// Before .NET 9 this was the loop everyone wrote - and often got wrong:
var pending = new HashSet<Task<Quote>>(quotes);
while (pending.Count > 0)
{
    Task<Quote> done = await Task.WhenAny(pending);
    pending.Remove(done);
    // ... and if you forget the Remove, you spin forever on the same completed task
}

    async (sku, token) => await _pricing.RefreshAsync(sku, token));

// When you need the results: semaphore + WhenAll.
using var gate = new SemaphoreSlim(8);
Task<Price>[] tasks = skus.Select(async sku =>
{
    await gate.WaitAsync(ct).ConfigureAwait(false);   // WaitAsync, not Wait
    try { return await _pricing.GetAsync(sku, ct).ConfigureAwait(false); }
    finally { gate.Release(); }                       // release in finally, always
}).ToArray();                                         // ToArray: start them now, not on enumeration

Price[] prices = await Task.WhenAll(tasks).ConfigureAwait(false);

Getting every error out of a WhenAll

Task all = Task.WhenAll(tasks);
try
{
    await all.ConfigureAwait(false);
}
catch (Exception)
{
    // `all.Exception` holds every failure; the await gave you only the first.
    foreach (var e in all.Exception!.InnerExceptions) _log.LogError(e, "leg failed");

Note that WhenAll also has no built-in "cancel the siblings when one fails" behaviour. If that is what you want — and for a fan-out where any failure dooms the result, it usually is — create a linked CancellationTokenSource, hand its token to every leg, and cancel it in the catch. Otherwise the remaining nine legs finish their work for a result nobody will use, which at scale is a meaningful waste and, for writes, an actual correctness problem.

Backpressure with channels

A bounded Channel<T> is the async equivalent of a fixed-size queue: when it is full, WriteAsync suspends the producer instead of buffering without limit. That is the whole point — an unbounded queue converts a throughput mismatch into a memory leak, and the crash arrives hours after the cause. Bounded channels make the mismatch visible immediately, as a slow producer.

var channel = Channel.CreateBounded<WorkItem>(new BoundedChannelOptions(1_000)
{
    FullMode = BoundedChannelFullMode.Wait,   // Wait = backpressure; DropOldest/DropWrite = shed load
    SingleReader = false, SingleWriter = true // these enable real optimisations - set them honestly
});

// N consumers, each an ordinary async loop:
var consumers = Enumerable.Range(0, 4).Select(_ => Task.Run(async () =>
{
    await foreach (var item in channel.Reader.ReadAllAsync(ct).ConfigureAwait(false))
        await HandleAsync(item, ct).ConfigureAwait(false);
})).ToArray();

// The producer must complete the writer, or consumers wait forever.
try     { await ProduceAsync(channel.Writer, ct).ConfigureAwait(false); }
finally { channel.Writer.Complete(); }
await Task.WhenAll(consumers).ConfigureAwait(false);
Interview trap

The LINQ fan-out that is not what it looks like. var tasks = items.Select(i => FooAsync(i)); gives you a lazy IEnumerable<Task>: nothing has started. If you then foreach over it and await each one, you get a sequential loop, because each task is created only when the enumerator reaches it. If you pass it to WhenAll, everything starts at once — unbounded. Both behaviours are surprises, and both appear in production code. Materialise deliberately with .ToArray() when you mean "start them all now", write a plain foreach with an await inside when you mean sequential, and use Parallel.ForEachAsync when you mean bounded. The second half of the trap is Parallel.ForEach (no Async) with an async lambda: the lambda is async void, so ForEach returns when every lambda reaches its first await, exceptions are lost, and the work continues invisibly.

Try it — feel unbounded concurrency

1. Point Task.WhenAll at 5,000 HttpClient calls to a local test server that sleeps 100 ms. Record wall time, socket count, and any exceptions. Then do the same with Parallel.ForEachAsync at a degree of 16.

2. Build a producer that writes 100,000 items into an unbounded channel with a consumer that is 10× slower, and watch working set. Switch to CreateBounded(1_000) and watch again.

Expected outcome

1. The unbounded version is usually slower, not faster: you exceed the server's capacity, connections queue, some time out, and retries make it worse. You may also hit SocketException from ephemeral-port exhaustion on the client. The bounded version has predictable latency and finishes in a time you can compute. The lesson interviewers want: concurrency has an optimum, and more is not better past the point where the bottleneck saturates.

2. The unbounded channel grows memory linearly until the process dies — and the failure looks like a memory leak, hours from the actual cause. The bounded one holds a flat, small footprint and the producer slows to the consumer's rate. That is backpressure, and being able to say why an unbounded queue is a latent outage is one of the higher-signal things you can say about pipeline design.

Interview Q&A

What are the exception semantics of Task.WhenAll?

It waits for every task regardless of failures — there is no fail-fast — and the returned task ends faulted if any input faulted. Awaiting it throws only the first exception, because the awaiter unwraps for readability, so if three legs failed you see one. To get them all you look at the Exception.InnerExceptions of the WhenAll task itself, which means you have to hold onto that task rather than awaiting an expression inline. Cancellation is folded in the same way: if some tasks cancelled and others faulted, the aggregate is faulted, and the rethrown exception may be either. In practice I capture the combined task, catch, log every inner exception with its context, and then decide whether to rethrow a summary or the first one.

How do you cancel the remaining work when one leg of a fan-out fails?

WhenAll will not do it for you, so I create a linked CancellationTokenSource from the caller's token, pass its token to every leg, and cancel it as soon as a failure is observed — either in each leg's own catch or after the WhenAll throws, depending on whether I want the other legs stopped mid-flight or merely not retried. If I need the very first failure to stop everything immediately, I do not use WhenAll at all: I use WhenEach (or WhenAny in a loop before .NET 9), react to the first faulted task, cancel the source, and then still await the rest with SuppressThrowing so their exceptions are observed rather than left dangling. The important part is that abandoning tasks is never free — you must observe them somewhere, or an eventual failure becomes an unobserved exception.

Explain Task.WhenEach and what it replaced.

Introduced in .NET 9, it returns an IAsyncEnumerable<Task> that yields each task as it completes, so you write a plain await foreach and process results in completion order. It replaces the WhenAny-in-a-loop idiom, where you kept a list, awaited WhenAny, removed the winner and repeated. That idiom had three recurring bugs: forgetting the remove, which spins on an already-completed task; O(n²) behaviour because each WhenAny attaches continuations to every remaining task; and losing exceptions from tasks you never got around to awaiting. WhenEach is the streaming counterpart to WhenAll's batch semantics, and it is the natural fit for anything with a progressive UI — search results from several providers, or a fan-out where an early answer lets you respond sooner.

How do you bound concurrency, and how do you choose the bound?

Mechanically: Parallel.ForEachAsync with MaxDegreeOfParallelism when I do not need results back, a SemaphoreSlim around each item when I do, or a bounded channel with a fixed number of consumer loops for a long-lived pipeline. Choosing the number is the interesting half. It is not core count — this is I/O — it comes from the constraint downstream: the connection pool size, the partner's documented rate limit, the database's healthy concurrent-query count. I start from that limit, divide by the number of instances of my service, and leave headroom for retries, because a retry storm multiplies concurrency exactly when the dependency is least able to take it. Then I make the number configurable and put the in-flight count on a dashboard, because the right value changes when either side is redeployed.

Why is Parallel.ForEach with an async lambda a bug?

Because Parallel.ForEach takes an Action<T>, so an async lambda passed to it becomes async void. Each invocation returns at its first await, ForEach concludes that the body finished, and the method returns while the work is still running. Exceptions in those bodies do not aggregate into ForEach; they are raised on the synchronization context and typically crash the process. The correct tool is Parallel.ForEachAsync, added in .NET 6, which takes a Func<T, CancellationToken, ValueTask>, awaits each body properly, respects MaxDegreeOfParallelism, and threads cancellation through. This is a favourite code-review question precisely because the broken version compiles cleanly and appears to work under light load.

When would you choose a channel over a plain WhenAll?

When the work is a continuous stream rather than a batch, or when producers and consumers run at different rates and I need backpressure. WhenAll assumes a finite, known collection and gives me no way to limit how much is in flight or in memory. A bounded channel gives me both: the queue depth is capped, so a slow consumer slows the producer instead of growing the heap, and the number of consumer loops is my concurrency knob. I also reach for it when I need decoupling — several producers, several consumers, or a consumer that batches — and when ordering matters, since a single-reader channel preserves FIFO order in a way that the thread pool never promises. The cost is lifecycle management: completing the writer, draining on shutdown, and observing the consumer tasks.

Is WhenAll over 10,000 tasks a problem in itself?

The combinator handles it, but the design usually does not. Memory is the first cost: 10,000 in-flight state machines, their captured locals, buffers and connections. The second is the downstream: unbounded concurrency turns your service into a load generator, and the classic outcome is that you overwhelm a dependency, everything times out, retries double the load, and the incident spreads. The third is diagnostic — when something fails you get one exception out of ten thousand possible ones and no idea of the distribution. So I treat "collection of unknown size" plus "unbounded fan-out" as a design defect regardless of whether it works today. For a small, fixed set — three dependencies for a page — WhenAll is exactly right and I would not add ceremony.

How do you retry inside a fan-out without making things worse?

Very carefully, because retries and concurrency multiply. The retry budget has to be part of the concurrency budget: if I allow eight concurrent calls and three attempts each, the dependency can see 24 in flight at the worst possible moment. So I use exponential backoff with jitter, cap total attempts, and put a circuit breaker in front so a dependency that is down stops receiving traffic entirely rather than receiving a retry storm. I also make sure the retry lives at one layer only — the classic incident is retry at the HTTP handler, retry in the client wrapper and retry in the job scheduler, giving 27 attempts nobody designed. And I only retry idempotent operations, or ones carrying an idempotency key, because a cancelled or timed-out write may already have been applied.

What does SingleReader/SingleWriter on a bounded channel actually buy you?

They are promises you make to the implementation, and it uses them to pick cheaper internals — fewer interlocked operations and a simpler queue when it knows there is only one side. The payoff is real in high-throughput pipelines, but so is the penalty for lying: if you declare SingleWriter and then write from two tasks, you get corruption rather than an exception, because the checks you would need are exactly the ones you asked it to skip. So I set them only when the topology is structurally guaranteed — one producer loop, one consumer loop — and I leave them false when the number of producers is configuration-driven. It is a nice example of a general API pattern: options that trade safety checks for speed should be set from the shape of the code, never from the shape of today's configuration.

Design an aggregation endpoint that calls five services with different SLAs.

I would start from the response contract: is this all-or-nothing, or can it degrade? Almost always it can, so I would fan out with a linked token per leg, each with its own timeout derived from that service's SLA, and use WhenEach so fast legs render immediately. Each leg's failure or timeout maps to a documented degraded state in the response rather than a 500 — a missing panel, a cached value, or a null with a reason — and every leg is instrumented separately so the dashboard shows which one degrades. I would put an overall budget on the endpoint, say 800 ms, so that the slowest leg cannot hold the response past it, and a circuit breaker per dependency so a sustained failure short-circuits instantly rather than burning the budget each time. Finally I would cache aggressively where staleness is acceptable, because the cheapest call is the one you do not make, and I would make sure the cache is populated asynchronously rather than on the request path.

08 IAsyncEnumerable and streaming

Docs: Generate and consume async streams · System.Linq.AsyncEnumerable (.NET 10) · Breaking change: AsyncEnumerable in .NET 10

Task<T> is one value, later. IEnumerable<T> is many values, now. IAsyncEnumerable<T>, added in C# 8 with .NET Core 3.0, is the missing fourth quadrant: many values, each of them later. It is a pull model — the consumer asks for the next item and awaits it — which is what gives it natural backpressure and makes it the right shape for paged APIs, database cursors, log tails and streaming responses.

The shape

The interface is IAsyncEnumerable<T>.GetAsyncEnumerator(CancellationToken) returning an IAsyncEnumerator<T> with ValueTask<bool> MoveNextAsync(), T Current and ValueTask DisposeAsync(). Note the ValueTask: an enumerator performs a long sequence of operations, most of which are satisfied from a buffer, which is exactly the case ValueTask was designed for. Note also that the token is a parameter of GetAsyncEnumerator, not of the interface — that detail is the source of the unit's main gotcha.

// Producing: an async iterator over a paged API. Note [EnumeratorCancellation].
public async IAsyncEnumerable<Order> StreamOrdersAsync(
    DateOnly since,
    [EnumeratorCancellation] CancellationToken ct = default)
{
    string? cursor = null;
    do
    {
        Page<Order> page = await _api.GetPageAsync(since, cursor, ct).ConfigureAwait(false);
        foreach (var order in page.Items)
            yield return order;              // suspends here until the consumer asks for the next one
        cursor = page.NextCursor;
    }
    while (cursor is not null && !ct.IsCancellationRequested);
}

// Consuming: WithCancellation feeds the token into GetAsyncEnumerator; ConfigureAwait
// applies to the hidden MoveNextAsync/DisposeAsync awaits inside the foreach.
await foreach (var order in StreamOrdersAsync(since)
                   .WithCancellation(ct)
                   .ConfigureAwait(false))
{
    await _sink.WriteAsync(order, ct).ConfigureAwait(false);
    if (order.IsTerminal) break;             // break still calls DisposeAsync - the finally runs
}

[EnumeratorCancellation] is what connects the two halves. Without it, the token you pass to WithCancellation goes into GetAsyncEnumerator and is dropped on the floor, while the ct parameter of your iterator keeps whatever the caller passed at construction time — usually default, because the enumerable is typically created and enumerated in different places. The attribute tells the compiler to overwrite that parameter with the token given to GetAsyncEnumerator, combining the two if both are present. It is easy to miss, produces no warning by default, and the symptom is "cancellation just does not work in our streaming endpoint".

LINQ over async streams — new in .NET 10

Until .NET 9 you needed the community System.Linq.Async package (part of Ix.NET) to write Where or Select over an IAsyncEnumerable<T>. .NET 10 ships System.Linq.AsyncEnumerable in the box, with a re-designed operator set that matches current library conventions. It is also a genuine breaking change worth knowing about, because it is the kind of concrete, recent detail that shows you are current: if a project references the old package and targets .NET 10, the two sets of extension methods are ambiguous and the build fails with CS0121. The fix is to drop the package where you can, or use the System.Linq.AsyncEnumerable NuGet package for down-level targets so one implementation serves both.

// .NET 10, no NuGet package required.
using System.Linq;

IAsyncEnumerable<Order> large = StreamOrdersAsync(since, ct)
    .Where(o => o.Total > 10_000m)
    .Select(o => o with { Currency = "EUR" })
    .Take(100);

decimal sum = await large.SumAsync(o => o.Total, ct);
List<Order> list = await large.ToListAsync(ct);

// Also useful: a synchronous escape hatch, deliberately named to look uncomfortable.
foreach (var o in large.ToBlockingEnumerable(ct)) { /* blocks a thread per item */ }

Streaming out of an ASP.NET Core endpoint

Returning IAsyncEnumerable<T> from a controller action or minimal API makes the framework serialise items to the response as they are produced, rather than buffering the whole collection — a memory win that turns an O(n) heap cost into O(1). .NET 10 added the other streaming shape as a first-class result: TypedResults.ServerSentEvents, which takes an IAsyncEnumerable<T> and handles the text/event-stream content type, the wire format, JSON serialisation, keep-alive and cancellation, so a browser can consume it with plain EventSource and no client library.

// .NET 10 minimal API: server-sent events straight from an async stream.
app.MapGet("/prices/stream", (string sku, IPriceFeed feed, CancellationToken ct) =>
    TypedResults.ServerSentEvents(feed.WatchAsync(sku, ct), eventType: "price"));

// Streaming JSON: one array, written as items are produced.
app.MapGet("/orders", (DateOnly since, IOrders o, CancellationToken ct) =>
    o.StreamOrdersAsync(since, ct));

The CancellationToken parameter there is HttpContext.RequestAborted, bound by the framework — which is what makes the stream stop when the browser closes the tab, and is the difference between a feature and a resource leak.

IAsyncDisposable and await using

Async iterators need asynchronous cleanup — the finally after your last yield return may itself await — which is why IAsyncDisposable exists and why await foreach always calls DisposeAsync, including when you break or throw. For your own types: implement IAsyncDisposable when disposal genuinely performs I/O (flushing a buffer, sending a close frame, committing), implement both interfaces when the type may be used from synchronous code, and never implement IDisposable by blocking on the async version. In DI, note that a scope must be disposed with await scope.DisposeAsync() for async-disposable services to be cleaned up properly.

Interview trap

Three that catch people. First, the missing [EnumeratorCancellation] above: cancellation silently does nothing, and there is no warning unless you enable the analyzer. Second, assuming an IAsyncEnumerable<T> is a snapshot — it is a recipe, so enumerating it twice runs the query twice, hitting the API twice and possibly producing different data; if you need it twice, materialise once with ToListAsync. Third, ToBlockingEnumerable(): it exists so you can bridge into synchronous code, and it blocks a thread per MoveNext — using it inside a request handler is sync-over-async wearing a LINQ hat and will starve the pool exactly like .Result does. A fourth, for EF Core specifically: an await foreach over a query holds the reader — and the connection — open for the whole loop, so doing slow work per item can exhaust the connection pool while nothing looks wrong in your code.

Try it — make cancellation work, then make it not work

1. Write an infinite async iterator that yields a counter every 100 ms. Consume it with await foreach (... .WithCancellation(cts.Token)) and cancel after a second — first without [EnumeratorCancellation], then with it.

2. Add a try/finally around the yield return that logs "disposed". Break out of the loop early and confirm when it prints.

Expected outcome

1. Without the attribute the loop runs forever: the token reached GetAsyncEnumerator and was discarded, and the iterator's own parameter still holds default. With it, the token is injected and ThrowIfCancellationRequested — or the awaited Task.Delay(100, ct) — throws promptly. Enable the analyzer that flags this once you have felt it.

2. "Disposed" prints when you break, because await foreach compiles to a try/finally that calls DisposeAsync, which resumes your iterator at the suspended yield return and runs its finally. This is the mechanism that makes streaming a database cursor safe to abandon — and the reason a manually driven enumerator that you never dispose leaks the reader.

Interview Q&A

What problem does IAsyncEnumerable<T> solve that Task<IEnumerable<T>> does not?

Task<IEnumerable<T>> means "one await, then all the items", so the producer must materialise everything before the consumer sees anything: peak memory is the whole result and time-to-first-item is the time to the last. IAsyncEnumerable<T> interleaves them — each item can be awaited separately, so memory is O(1) in the number of items and the first item arrives immediately. It is also the only shape that expresses an unbounded sequence, such as tailing a log or watching a price feed. The trade is that the connection or cursor stays open for the whole enumeration, and that the consumer's speed now controls the producer, which is usually what you want but does mean slow consumers hold resources.

What does [EnumeratorCancellation] do?

It bridges the two places a token can enter an async stream. The token given to WithCancellation is passed to GetAsyncEnumerator(CancellationToken); the token your iterator method declares as a parameter is bound when the enumerable is created. Those are different moments, and without the attribute the first is discarded. Marking the parameter tells the compiler to substitute the enumerator's token — combining the two into a linked token when both are non-default — so the token the consumer supplies actually reaches your awaits. Practically, I write iterator methods with the attribute always, defaulted to default, so both calling styles work; and I turn on the analyzer that flags a token parameter without it, because the failure is silent.

How do ConfigureAwait and WithCancellation combine on an await foreach?

They chain: source.WithCancellation(ct).ConfigureAwait(false), both producing a ConfiguredCancelableAsyncEnumerable<T> that the loop consumes. The order does not matter, and calling either returns a struct so there is no allocation. This matters more than it looks in a library, because a single await foreach hides two kinds of await — one per MoveNextAsync and one for DisposeAsync — and without ConfigureAwait(false) each of them posts back to the caller's context. Streaming ten thousand items to a WPF or Blazor caller then means ten thousand context posts, which is visible as UI jank. It is also the case CA2007 catches that reviewers do not, because there is no visible await keyword on the line.

Async streams or a channel?

I choose by who sets the pace and how many consumers there are. If a single consumer drives a source that can be paused — a paged API, a cursor, a file — the async stream is simpler, needs no lifecycle management, and gets backpressure for free because nothing happens until MoveNextAsync is called. If the producer runs independently, or several consumers compete for items, or I need buffering between stages, a channel is right: it decouples the two sides and lets me choose the buffer policy explicitly. The two also compose nicely — ChannelReader<T>.ReadAllAsync() hands you an IAsyncEnumerable<T> — so a common shape is a channel internally for the pipeline and an async stream as the public API.

What changed for LINQ over async streams in .NET 10?

System.Linq.AsyncEnumerable is now built in, so Where, Select, Take, ToListAsync, SumAsync and the rest work on any IAsyncEnumerable<T> with no package reference. It was reimplemented rather than absorbed, because the community System.Linq.Async package predates current API-design guidelines and made naming choices the team did not want to bake into the platform. The practical consequences are two: existing projects that reference the old package and move to .NET 10 hit ambiguous-method build errors and need to drop the package; and libraries targeting older frameworks can use the System.Linq.AsyncEnumerable NuGet package to get the same surface, which is the migration path I would take for a multi-targeted library.

Is returning IAsyncEnumerable<T> from a Web API endpoint a good idea?

For genuinely large or open-ended results, yes: ASP.NET Core serialises items as they are produced, so the response starts immediately and the server never holds the whole set in memory. The caveats are what an interviewer is after. Error handling changes shape — once the first bytes are on the wire you cannot change the status code, so a failure mid-stream produces a truncated 200, and you need a protocol-level marker or SSE-style events to signal it. The database connection or upstream call stays open for the life of the response, so a slow client holds server resources; pair it with a timeout and with RequestAborted plumbed through. And buffering proxies may negate the streaming entirely. For a bounded page of results, plain pagination is simpler and I would prefer it.

When is ToBlockingEnumerable() acceptable?

At a genuine synchronous boundary that I control and that is not on a request path: a console tool, a migration script, a test, or an adapter into a legacy interface that cannot be made async. It blocks a thread for every MoveNext, so inside a server it is sync-over-async with all the starvation consequences — the fact that it is spelled as a LINQ-ish method makes it much easier to smuggle past review than a bare .Result, which is precisely why I call it out by name. If I find it in a service, the fix is almost always to make the consumer async rather than to make the producer synchronous, because the producer is usually the thing doing I/O.

What is the relationship between async streams and IAsyncDisposable?

An async iterator can hold resources whose release needs I/O — an open reader, a socket, a buffer to flush — so its enumerator implements IAsyncDisposable, and await foreach guarantees DisposeAsync runs whether the loop ends normally, breaks or throws. That resumes the suspended iterator so its finally blocks execute. For your own types, I implement IAsyncDisposable when disposal really performs I/O, implement both interfaces when synchronous consumers exist, and never implement the synchronous one by blocking on the asynchronous one — that reintroduces sync-over-async at the least convenient moment, during cleanup. One DI detail worth knowing: service scopes must be disposed with await scope.DisposeAsync(), or async-disposable scoped services are disposed synchronously or not at all.

How would you stream results to a browser today?

For one-directional server-to-client updates I would use server-sent events, which .NET 10 made first-class: TypedResults.ServerSentEvents takes an IAsyncEnumerable<T> and the framework handles the content type, framing, serialisation, keep-alive and cancellation, while the browser consumes it with the built-in EventSource and reconnects automatically. I would assign an event id per item so a reconnecting client sends Last-Event-ID and I can resume rather than replay from the start. I would choose WebSockets or SignalR instead only when I need client-to-server messages on the same connection or a fallback matrix for old clients. And I would still bound it: a per-connection timeout, a cap on concurrent streams, and a heartbeat, because a streaming endpoint's failure mode is thousands of half-open connections rather than a spike in error rate.

What goes wrong when you enumerate an async stream twice?

You run it twice. An IAsyncEnumerable<T> is a factory for enumerators, not a materialised sequence, so a second await foreach calls the API again, re-executes the query and may see different data — with the corresponding cost and side effects. The bug appears when someone passes a stream to two helpers, or writes if (await s.AnyAsync()) await foreach (var x in s), which now performs two enumerations and, on a live feed, may consume the item that AnyAsync peeked. The fix is to materialise once with ToListAsync when the set is bounded, or to restructure so there is one enumeration. It is the same mental model as IEnumerable<T> deferred execution, but the consequences are larger because each enumeration is I/O.

09 Exceptions and async void

Docs: Asynchronous programming in C# · TaskScheduler.UnobservedTaskException · ExceptionDispatchInfo

The core rule is short: an exception thrown inside an async method does not propagate at the call site — it is captured and stored in the returned task, and it is re-thrown when someone awaits that task. Everything difficult about async error handling follows: if nobody awaits, nobody sees it; if the method returns void, there is no task to store it in; and by the time it is re-thrown, the original stack has to be reconstructed.

Capture, storage, and rethrow

When your method throws, the builder calls SetException, which faults the task. On await, the awaiter uses ExceptionDispatchInfo.Throw to re-raise it with its original stack trace intact rather than resetting it at the rethrow point — which is why an async stack trace shows the frame that actually failed, and why you should never write throw ex; to rethrow (that does reset the stack). Two timing consequences are worth stating because interviewers use them as probes: exceptions thrown before the first await are also captured, not thrown synchronously, so a caller who does not await gets no error at all; and the exception surfaces at the await, not at the call, so the try must wrap the await.

// Argument validation: throw synchronously, do the work asynchronously.
public Task<Order> PlaceAsync(Order order, CancellationToken ct)
{
    ArgumentNullException.ThrowIfNull(order);                 // throws AT THE CALL SITE
    if (order.Lines.Count == 0) throw new ArgumentException("empty order", nameof(order));
    return PlaceCoreAsync(order, ct);                          // no async/await here: no state machine

    async Task<Order> PlaceCoreAsync(Order o, CancellationToken t) { /* ... */ }
}

Without the split, a caller that stores the task and awaits it much later gets the argument error at a place that has nothing to do with the mistake. With it, misuse fails fast and everything else flows through the task. The BCL uses this shape throughout, and recognising it is a good signal in review.

The unobserved case deserves a footnote, because the folklore is out of date. In .NET Framework 4.0 an unobserved task exception killed the process at finalisation. Since 4.5 it does not: the UnobservedTaskException event fires and, if nobody marks it observed, execution continues. That default is what makes silently-swallowed failures possible, and it is why subscribing to the event and logging loudly is standard practice — the log line is often the only trace of a fire-and-forget bug.

async void: the one legitimate use, and the safe alternative

async void exists so that event handlers, whose delegate type returns void, can await. That is the whole justification. Everywhere else it is a defect: you cannot await it, so you cannot know when it finished; you cannot catch its exceptions, because they are raised on the context rather than returned; and it does not participate in WhenAll, cancellation or testing. Even in an event handler, wrap the body so nothing escapes.

// The only place async void belongs - and even here, catch everything.
private async void OnSaveClicked(object sender, EventArgs e)
{
    try { await _vm.SaveAsync(_cts.Token); }
    catch (OperationCanceledException) { /* expected */ }
    catch (Exception ex) { _log.LogError(ex, "save failed"); ShowError(ex); }
}

// Deliberate fire-and-forget, made observable. The point is not that it is safe -
// it is that the failure is logged and the intent is visible in the call site.
public static void FireAndForget(this Task task, ILogger log, [CallerMemberName] string? from = null)
{
    _ = task.ContinueWith(
        static (t, s) =>
        {
            var (logger, caller) = ((ILogger, string?))s!;
            logger.LogError(t.Exception!, "unobserved failure in background work started by {Caller}", caller);
        },
        (log, from),
        CancellationToken.None,
        TaskContinuationOptions.OnlyOnFaulted | TaskContinuationOptions.ExecuteSynchronously,
        TaskScheduler.Default);
}

In a hosted app, the better answer than any fire-and-forget helper is usually not to fire and forget at all: put the work on a channel that a BackgroundService drains, so it has a lifetime, a concurrency bound, cancellation on shutdown, and somewhere for its errors to go. "Fire and forget" in a request handler also means the work dies when the process recycles, which is fine for a metric and not fine for a payment.

Async stack traces

Because each resumption starts a fresh call stack, an async exception's trace is stitched together from the state machines rather than being a real stack. That has improved steadily — [StackTraceHidden] on infrastructure frames, and the runtime's async-aware trace assembly — but under the classic model a live stack (what a profiler or new StackTrace() sees mid-execution) is still full of AsyncMethodBuilderCore.Start noise. This is one of the concrete things Runtime Async fixes in .NET 11: Microsoft's own sample goes from 13 frames to 5, with the real call chain visible, because the runtime knows about async instead of inferring it (unit 12). Exception traces from catch blocks already looked much the same either way, so the improvement is about debugging and profiling live execution rather than about post-mortem error logs.

Interview trap

"Why didn't my try/catch catch it?" Three distinct causes, and a strong candidate names all three. The method was async void, so the exception went to the context and there was never a task to observe. Or the call was not awaited — _ = DoAsync(); or a forgotten await — so the fault sat on a task nobody looked at; note that the compiler warns (CS4014) only when the result is discarded implicitly, and assigning to a discard silences it. Or the try wrapped the call but the await happened outside it, which is common when a task is created in one method and awaited in another. The fourth variant, for extra credit: the exception was thrown inside a WhenAll and there were three of them, so the one you caught was not the one you were looking for.

Try it — lose an exception, then find it

1. Write a console app with a method that throws after await Task.Delay(50). Call it three ways: awaited inside try/catch; assigned to a discard and never awaited; and as async void. Force a GC and GC.WaitForPendingFinalizers() at the end.

2. Subscribe to TaskScheduler.UnobservedTaskException and to AppDomain.CurrentDomain.UnhandledException and re-run.

Expected outcome

1. The awaited call behaves normally. The discarded one prints nothing at all — the program exits successfully with a bug it never mentioned. The async void one crashes the process, and no try at the call site helps.

2. The unobserved handler fires for the discarded task, but only after the GC collects it, which can be seconds or minutes later and in a completely unrelated part of the log — that delay is exactly why these bugs are hard to attribute. The async void case goes to the unhandled-exception handler and still terminates. Wire the unobserved handler into your logging in every service you own; it costs nothing and is occasionally the only evidence you get.

Interview Q&A

Why is async void dangerous?

Because it breaks the three things the task gives you. There is no handle, so you cannot await completion, compose it, or test it deterministically. There is nowhere to store a failure, so the exception is re-thrown on the captured synchronization context — or on a pool thread when there is none — and becomes an unhandled exception that terminates the process; a try/catch around the call cannot see it. And cancellation and timeouts have nothing to attach to. The only justified use is an event handler whose delegate signature requires void, and even there the body should be wrapped in a catch-all that logs. In review I treat any other async void as a defect, and I would enforce it with an analyzer rather than by reading.

When does an exception from an async method actually get thrown?

At the await, not at the call. The method captures it into the returned task via the builder's SetException, and the awaiter re-throws it using ExceptionDispatchInfo so the original stack survives. This includes exceptions thrown before the first await — argument validation, for instance — which is why the split-method pattern exists: a non-async outer method that validates and throws synchronously, plus a private async core. The practical consequence for callers is that try { var t = FooAsync(); } catch { } catches nothing useful, and the try has to be around the await. It also means a method that returns a faulted task has already "returned" successfully as far as the call site is concerned.

What is TaskScheduler.UnobservedTaskException and what is its history?

It is the event raised when a faulted task is garbage-collected without anyone having observed its exception. In .NET Framework 4.0 an unobserved exception escalated at finalisation and killed the process; that was reversed in 4.5, and since then the default is to fire the event and carry on, with the old behaviour available via a runtime configuration switch. The current default is the pragmatic one — a forgotten task should not kill a healthy server — but it is what allows fire-and-forget failures to vanish. I subscribe to the event in every service and log at error level with as much context as I can get, because the alternative is that a whole class of bug produces no signal. The catch is timing: the event fires at collection, so the log entry can be minutes after the fact and far from the cause.

How do you do fire-and-forget properly?

My first move is to question the premise, because in a hosted service the usual right answer is a queue: write the work to a bounded channel and let a BackgroundService drain it, so the work has a lifetime, a concurrency limit, cancellation on shutdown, retries and a place for errors. If it really must be fire-and-forget — a metric, an audit ping, a cache warm — then I make it explicit and observable: a named helper rather than a bare discard, so the intent is greppable; a mandatory logging continuation so failures are recorded; no capture of request-scoped state such as HttpContext or a scoped DbContext, which are disposed or recycled the moment the response completes; and a check that the work is idempotent, since it will be abandoned mid-flight when the process recycles. If losing the work would matter, it is not fire-and-forget, it is a durable job.

Why does await throw one exception when a WhenAll had five failures?

Because the awaiter unwraps the stored AggregateException and rethrows its first inner exception, so that catch (IOException) behaves the way it does in synchronous code. That readability choice loses the other four unless you go and get them. The technique is to hold the combined task in a variable, catch, and then read task.Exception.InnerExceptions — logging each with which leg it came from, which requires you to have kept that association, typically by using an index or a dictionary from task to input. When failures need to be reported to a caller as a set, I construct my own AggregateException or a domain-specific result type; when I only need the first, I let the natural behaviour stand. What I never do is catch (AggregateException) around an await, because that catches nothing.

What makes async stack traces hard, and what has improved?

Each resumption begins a new physical stack, so the logical chain of "who awaited whom" is not present in the machine stack; it must be reconstructed from the state machine objects. Historically this produced traces cluttered with builder frames and missing the caller chain. It has improved through [StackTraceHidden] on infrastructure methods, better stitching in the runtime, and tooling such as the parallel-stacks window and the SOS commands that walk async state machines in a dump. The most recent change is Runtime Async in .NET 11: because the runtime owns suspension, the real methods appear on the live stack — 5 frames instead of 13 in Microsoft's example — which fixes profilers, debuggers and any diagnostics that call new StackTrace() during execution. Exception traces from a catch block were already reasonable, so it is live inspection that gets better.

What should a BackgroundService do when its ExecuteAsync throws?

Know the default and choose deliberately. Since .NET 6 the default BackgroundServiceExceptionBehavior is StopHost: an unhandled exception in ExecuteAsync stops the whole application, which is usually correct in a container, because a crash-looping pod is visible while a silently dead worker inside a healthy-looking process is not. The older behaviour, Ignore, leaves the host running with that service dead — the worst of both worlds unless you have your own supervision. So I keep StopHost, and inside the service I handle the errors I actually expect: a per-item try/catch that logs and continues, backoff for transient dependency failures, and cancellation allowed to propagate cleanly on shutdown. What escapes to the host is then genuinely fatal, which is the contract I want.

How do you test that an async method fails the way you intend?

By asserting on the awaited call, not on the call: await Assert.ThrowsAsync<T>(() => sut.DoAsync()), since a synchronous assertion around the invocation would only catch the argument-validation case. I test both halves deliberately — that misuse throws synchronously, and that operational failures come back through the task — because that difference is a design decision I made and it should be pinned. For cancellation I use a FakeTimeProvider to advance a timeout rather than sleeping, and I assert on OperationCanceledException plus, where it matters, that the task's status is Canceled rather than Faulted. For fire-and-forget paths I make the helper injectable so the test can await the background work; if I cannot observe it, I treat that as a design problem rather than writing a test that sleeps.

A service logs "unobserved task exception" once an hour with no other symptom. How do you chase it?

I start by making the log entry useful, because by default it tells you almost nothing: log the full exception including inner exceptions, and enrich the handler with anything ambient I can capture. Then I look for the shape rather than the line — an hourly cadence suggests a timer or a scheduled job, so I would inventory every Timer, PeriodicTimer, hosted service and cache refresh, since those are the classic places a task is started and never awaited. Turning on first-chance exception logging in a staging instance under the same schedule usually names it in one cycle. Structurally, the fix is not to catch it better but to remove the unobserved task: give the background work an owner that awaits it. I would also treat the frequency as data — once an hour with no user impact still means something is failing every hour, and that something is often the health of a dependency I have not been watching.

What do you look for about error handling when reviewing async code?

Discards and missing awaits first, since those are the ones that lose failures silently; then async void outside event handlers. Then try blocks that wrap the call but not the await, and empty catches that were added to make a test pass. I check that cancellation is distinguished from failure — a bare catch (Exception) that logs at error level will turn every client disconnect into an alert, which trains people to ignore alerts. I check finally blocks for async cleanup that uses an already-cancelled token, and for anything that can itself throw and mask the original exception. Finally, I look for exception filters used to distinguish my timeout from the caller's cancellation, and for whether the failures that matter reach a log with enough context to identify which of fifty concurrent operations failed — that last one is usually the difference between a two-minute and a two-hour incident.

10 Ambient state and mutual exclusion

Docs: AsyncLocal<T> · ExecutionContext · SemaphoreSlim · The lock statement and System.Threading.Lock

Two problems live in this unit, and they are mirror images. Ambient state is data that must follow a logical operation across threads — a correlation id, a tenant, a logging scope. Mutual exclusion is code that must not run concurrently. Both were designed for a world where "logical operation" meant "thread", and both had to be rebuilt when a logical operation became a chain of continuations on arbitrary threads.

ExecutionContext: the thing that flows

ExecutionContext is the runtime's carrier for ambient state across asynchronous points. When you await, the builder captures it and restores it before running the continuation, so anything stored in it appears to follow your logical call chain even though the thread changed. AsyncLocal<T> is the public way to put values in it. Two properties define its behaviour and both are asked about:

  • It flows downward, not upward. The context is captured (conceptually copied) when work is started, so a value set inside an async method is visible to everything that method calls afterwards — but assigning a new value inside a called method does not propagate back to the caller. If you need upward mutation, the ambient value must be a mutable object you set fields on, not a value you assign.
  • It is copy-on-write. Setting an AsyncLocal allocates a new context rather than mutating the shared one, which is why setting them frequently in a hot loop is a real, measurable cost, and why libraries treat them as scarce.

This is the machinery behind IHttpContextAccessor, behind ILogger scopes, behind Activity.Current for distributed tracing, and behind TransactionScope when you enable async flow. It is also, in .NET 11, the target of a specific optimisation: continuations now detect when there is nothing to restore and skip the capture/restore cycle entirely, which pays off precisely in the code that uses ConfigureAwait(false) and does not use AsyncLocal — the common server path.

private static readonly AsyncLocal<string?> Correlation = new();

async Task HandleAsync()
{
    Correlation.Value = "abc-123";        // flows into everything awaited from here
    await Task.WhenAll(A(), B());          // both see "abc-123"
    Console.WriteLine(Correlation.Value);  // still "abc-123" - A/B could not change it
}

async Task A()
{
    Console.WriteLine(Correlation.Value);  // "abc-123"
    Correlation.Value = "changed";         // visible only inside A and its callees
    await Task.Yield();
}

// Deliberately NOT flowing context - e.g. starting a long-lived background loop
// that must not pin the current request's ambient state alive.
using (ExecutionContext.SuppressFlow())
{
    _ = Task.Run(BackgroundLoopAsync);
}

Why you cannot lock across an await

It is a compile error, and the reason is that Monitor — and, since .NET 9, System.Threading.Lock — is thread-affine: the thread that entered must be the thread that exits. An await can resume on a different thread, so releasing would either fail or corrupt the lock's ownership. The compiler stops you rather than letting you find out at run time. What it cannot stop is the workaround people reach for: calling .Result inside the lock, which blocks a pool thread while holding a lock and combines starvation with a convoy — the worst pattern in this entire guide.

The concurrency bug that is not about locks at all

By far the most common concurrency failure in async .NET code is using a stateful, non-thread-safe service from several tasks at once. DbContext is the canonical case: it is explicitly documented as supporting one operation at a time, so Task.WhenAll(ctx.SaveChangesAsync(), ctx.Users.ToListAsync()) — or, much more commonly, a Select(async id => await ctx.FindAsync(id)) fan-out — throws InvalidOperationException: A second operation was started on this context, and sometimes corrupts the change tracker before it does. The fix is not a lock; it is a context per unit of work, resolved from its own DI scope inside each parallel branch. The same reasoning applies to HttpContext, to any scoped service captured by a background task, and to shared StringBuilders and dictionaries in per-request singletons.

Interview trap

"Just use a lock." Two failures hide behind that answer. The first is the sync-over-async escape hatch — a lock around a .Result — which holds a lock while blocking a pool thread, so under load every request queues on both. The second is scope: a SemaphoreSlim in a singleton serialises the whole process, which is right for "refresh this cache once" and catastrophic for "one at a time per customer", where you need a keyed gate — a ConcurrentDictionary<string, SemaphoreSlim> — with a cleanup story so it does not grow forever. And none of it survives a second instance of your service: process-local exclusion is not distributed exclusion, so if the invariant is real, you need a database constraint, an optimistic-concurrency token or a distributed lease. Naming that boundary unprompted is a strong senior signal.

Try it — flow, and fail to flow

1. Set an AsyncLocal<int> to 1, start two tasks that each set it to their own value and print it after an await, then print it in the parent. Then wrap the task starts in ExecutionContext.SuppressFlow() and compare.

2. Take a SemaphoreSlim(1,1) and call, inside the guarded body, another method that takes the same semaphore. Then do the same with lock.

Expected outcome

1. Each task sees the parent's value, changes it locally, and the parent still sees its own — downward flow, no upward propagation. Under SuppressFlow, the tasks see the default value instead, which is exactly what you want for a long-lived background loop that must not keep a request's ambient objects alive.

2. The semaphore version deadlocks instantly and permanently: it counts permits, it does not track owners, so your own second acquisition waits for a release that only you could issue. lock succeeds, because Monitor is reentrant per thread. That asymmetry is the single most surprising thing about migrating a lock to an async mutex, and it is why "make it async" is never a mechanical transformation.

Interview Q&A

What is ExecutionContext and what flows across an await?

It is the runtime's container for ambient state that should follow a logical operation rather than a thread: AsyncLocal<T> values, the security context, and anything the runtime pins to it. The async builder captures it at a suspension and restores it before running the continuation, so a correlation id set at the start of a request is visible in code running twenty continuations later on a different thread. What does not flow is ThreadLocal<T> and anything else tied to the physical thread, which is why thread-local storage is essentially unusable in async code. SynchronizationContext is a separate capture with a separate opt-out — ConfigureAwait(false) suppresses the synchronization context, not the execution context, and there is no way to opt out of the latter at an await; you suppress it around the start of work with ExecutionContext.SuppressFlow.

AsyncLocal<T> versus ThreadLocal<T>?

ThreadLocal<T> is keyed on the physical thread, so in async code it is wrong by construction: your continuation may run on a different pool thread, and a pool thread is shared between unrelated operations, so a leftover value is a cross-request data leak. AsyncLocal<T> is keyed on the execution context, which follows the logical operation. The gotchas with AsyncLocal are its copy-on-write cost — every assignment allocates a new context, so it is not for hot loops — and its one-way flow, since a value assigned in a callee is invisible to the caller. When I need mutation visible upward, I flow an immutable reference to a mutable holder object instead of reassigning the ambient value.

Why can't you await inside a lock, and what do you use instead?

Monitor — and the newer System.Threading.Lock in .NET 9 — is thread-affine: the entering thread must be the exiting thread, and it tracks reentrancy per thread. An await can resume anywhere, so releasing on a different thread would be invalid; the compiler makes it an error rather than a run-time surprise. The async substitute is SemaphoreSlim(1,1) with WaitAsync and a finally release. The three things to say next, because they are what the follow-up is about: it is not reentrant, so a recursive path deadlocks; it has no ownership concept, so any code can release it, and a stray release raises the permit count and silently breaks exclusion; and often the better design is not a mutex at all but a single-reader channel, which serialises by construction and gives you a queue you can observe.

How do you implement one-time async initialisation safely?

Lazy<Task<T>> with thread safety enabled is the simplest correct answer: the factory runs once, every caller awaits the same task, and there is no lock held across an await because the lock only guards creating the task, not awaiting it. The subtlety is failure caching — if the factory's task faults, every future caller gets the same faulted task, which is right for genuinely one-time setup and wrong for something you want retried, in which case I detect the faulted state and replace the Lazy with a new one under a small lock or an Interlocked.CompareExchange. I would also mention what I avoid: double-checked locking with a bool flag around an async call, which is where people accidentally block, and initialising in a constructor, which cannot await and pushes people toward .Result.

A team reports "A second operation was started on this context". What is happening and how do you fix it?

They are using one DbContext from two operations concurrently — almost always a fan-out where a Select(async ...) or WhenAll shares the captured context, sometimes a background task holding a scoped context after the request ended. DbContext is documented as supporting a single operation at a time; it is not a thread-safety bug you can lock your way out of, because the change tracker's state would still be shared. The fix is one context per unit of work: inside each parallel branch, create a scope from IServiceScopeFactory and resolve a fresh context, or use IDbContextFactory<T>, which exists for exactly this. I would also ask whether the fan-out is worth it at all — often the parallel version issues N queries where one query with a join would do, and removing the concurrency is both faster and simpler.

What is ExecutionContext.SuppressFlow for?

It stops the current ambient context from being captured by work started inside its scope. The case where I need it is long-lived background work started from a request or from a scope: without suppression, the background task captures the request's execution context, which keeps its AsyncLocal values — and anything they reference, including possibly a whole object graph — alive for the life of the task, and it also means the background work's logs are tagged with a request that finished long ago. Suppressing gives the background loop a clean context. It is a niche tool and I would not scatter it around: the more common correct answer is not to start unbounded background work from a request at all, but to hand it to a hosted service that has its own lifetime and its own context from the start.

How do you serialise access per key rather than globally?

A ConcurrentDictionary<TKey, SemaphoreSlim> with GetOrAdd, taking the per-key semaphore around the critical section. The part that separates a working implementation from a leaking one is cleanup: entries accumulate for every key ever seen, so I either bound it with a size-limited cache and eviction, or reference-count each entry and remove it when the count returns to zero — which needs its own small lock to avoid a race between the last release and a new acquisition. Because that is fiddly, I often prefer to sidestep it: partition the work by key across a fixed number of single-reader channels, so keys map to a queue and ordering per key comes for free with no dictionary to clean. And whichever I choose, I state the boundary explicitly — this is process-local, so with more than one instance the real guarantee has to come from the database or a distributed lease.

How does TransactionScope behave with async, and what is the trap?

The trap is that TransactionScope predates async and, by default, the ambient transaction does not flow across awaits — so a using var scope = new TransactionScope(); followed by awaited work leaves that work outside the transaction, and the dispose may then throw about a different thread. The fix is the constructor overload with TransactionScopeAsyncFlowOption.Enabled, which makes the ambient transaction ride on the execution context. Even with that, I am cautious: distributed transactions across resource managers have limited support in .NET Core and up, and the ambient nature makes it very easy for a method to be enlisted in a transaction it knows nothing about. Where I can, I prefer explicit transactions on the connection or context passed as a parameter, so the scope is visible in the signature rather than in the environment.

Where does Interlocked still belong in async code?

Wherever the critical section is a single variable, because it is the only synchronisation with no waiting at all and therefore no interaction with the thread pool. Counters for in-flight operations, a one-time initialisation flag with CompareExchange, a "has this been completed" guard for a bridge over a callback API, a cheap sequence number: all of those are better as an interlocked operation than as any kind of lock. It is also the right primitive for the "only the first result wins" pattern in a fan-out race. What it does not solve is a multi-field invariant — anything where two variables must change together needs a real critical section, and reaching for interlocked operations there produces code that is subtly wrong and very hard to review, which is a reasonable thing to say out loud when someone proposes a lock-free design.

Your service must not process two messages for the same customer at once. How do you design it?

I would first establish whether the requirement is really mutual exclusion or really ordering, because they have different solutions and people conflate them. If it is ordering, the answer is partitioning: key messages by customer id onto partitions — Kafka partitions, Service Bus sessions, or my own consistent-hash mapping onto N single-reader channels — so each customer's messages are handled sequentially by construction, with no lock and no cross-instance coordination. If it is genuinely exclusion, I would put the guarantee where it survives multiple instances: an optimistic-concurrency token on the customer row so a conflicting write fails and can be retried, or a lease in the database or Redis with a TTL, understanding that leases are not safe by themselves without fencing tokens. A process-local keyed semaphore is a useful optimisation on top of either — it stops the common case from ever reaching the durable check — but I would not present it as the guarantee, and saying why is usually the point of the question.

The metrics I put on every dashboard

  • Thread-pool thread count and queue length (ThreadPool.ThreadCount, ThreadPool.PendingWorkItemCount). An alert on "queue length sustained above zero while CPU is low" catches starvation before customers do.

  • Connection-pool usage for the database and HTTP handlers, because that is the queue async pushes the pressure into.
  • Cancellation rate, separated from the error rate. Client disconnects are normal; a jump in them means something upstream changed.
  • Unobserved task exceptions, from the TaskScheduler event, as an explicit counter — a non-zero value is always a bug.

Three rules that decide whether the numbers mean anything. Benchmark in Release, because the Debug state machine is a class and every allocation number is wrong. Benchmark the real synchronous-completion rate — a ValueTask benchmark with a 100% cache hit rate proves nothing about a 40% one. And prefer a load test over a microbenchmark for anything involving the thread pool, because starvation is an emergent property of arrival rate and blocking, and no microbenchmark will show it.

Testing async code deterministically

The tests that catch async bugs are the ones with no sleeps in them. Three techniques cover most of it:

// 1. Control time instead of waiting for it (.NET 8+ TimeProvider, FakeTimeProvider from
//    Microsoft.Extensions.TimeProvider.Testing).
var time = new FakeTimeProvider();
var sut  = new Poller(time);
Task<Result> run = sut.PollAsync(ct);
time.Advance(TimeSpan.FromMinutes(5));      // instant, deterministic
await run;

// 2. Control completion instead of racing it: a TaskCompletionSource in a fake lets the
//    test decide the exact interleaving.
var gate = new TaskCompletionSource(TaskCreationOptions.RunContinuationsAsynchronously);
fakeRepo.Setup(r => r.LoadAsync(It.IsAny<CancellationToken>())).Returns(gate.Task);

Task first  = sut.RefreshAsync(ct);          // now suspended inside the semaphore
Task second = sut.RefreshAsync(ct);          // proves the second caller waits
gate.SetResult();                            // release both, in a known order
await Task.WhenAll(first, second);

// 3. Assert on the awaited call, not the invocation.
await Assert.ThrowsAsync<TimeoutException>(() => sut.BuildAsync(ct));

What I avoid: Task.Delay as a synchronisation device, which produces tests that are slow when they pass and flaky when the machine is busy; .Result in test bodies, which reintroduces the deadlock you are testing for on frameworks with a test synchronization context; and asserting on thread ids, which are an implementation detail the pool is free to change.

Interview trap

"The app is hung. Take a dump and look at the threads." That is the .NET Framework reflex and it will mislead you. In an async app the interesting operations are not on any stack — they are suspended state machines on the heap, waiting for a completion that never came. A thread dump of a hung async service often shows a handful of idle pool threads and nothing else, which reads as "the app is fine". The correct move is dumpasync (or the Tasks window), which reconstructs the await chains from the heap. The related trap is the opposite: a dump full of threads blocked in Task.Wait is not an async problem at all, it is sync-over-async, and the fix is in the code that blocks, not in the pool settings.

Try it — diagnose a hang you built

1. Write a service that awaits a TaskCompletionSource which is never completed, behind two layers of async methods. Run it, then use dotnet-dump collect and dumpasync to find the chain. Compare with what clrstack on each thread tells you.

2. Add a SemaphoreSlim(1,1) that is acquired and never released on one path, drive it with concurrent calls, and repeat the exercise.

Expected outcome

1. Thread stacks show almost nothing — the threads are back in the pool. dumpasync shows the full await chain down to the pending state machine, with the type and method names, which is normally enough to identify the bug from the dump alone. Practise this once when nothing is on fire; it is a completely different workflow from synchronous debugging and you do not want to learn it during an incident.

2. You see many state machines all suspended at the same SemaphoreSlim.WaitAsync, which is the signature of a leaked permit. Note that thread count stays low and CPU stays at zero — from the outside this looks identical to "the dependency is slow", which is exactly why the dump is worth taking before the mitigation restarts the process and destroys the evidence.

Interview Q&A

An async service is hung. Walk me through your first ten minutes.

I preserve evidence before I mitigate, because a restart destroys it: capture a dump, or at minimum dotnet-stack report and a dotnet-counters sample. Then I read the counters first, because they classify the problem in seconds — high thread count with low CPU means blocking; a large queue with normal thread count means the pool is behind; high GC time means allocation; all flat means we are waiting on something external. Next I run dumpasync on the dump to see what the pending operations are actually awaiting, which usually names the dependency or the primitive. In parallel I check whether this correlates with a deploy or a dependency incident, since the fastest fix is often a rollback. Only then do I mitigate — restart, shed load, raise a limit — and I write down what I saw first, because in an hour nobody will remember.

Which counters matter for async health, and what thresholds?

Thread-pool thread count relative to ProcessorCount: steady state should be close to it, and sustained growth past a few times that means threads are blocking. Pending work item count: healthy services sit at zero almost always, so any sustained non-zero value is a signal, and I alert on it rather than on a magic number. Completed work items per second gives you throughput to compare against arrival rate. Beyond the runtime counters I add my own in-flight gauge per dependency and the connection-pool usage, because those are where async moves the pressure. I deliberately avoid alerting on CPU alone for these services — the defining feature of starvation is that CPU looks fine.

What is dumpasync and why does a normal thread dump not work?

A suspended async operation has no thread and no stack; it is a state machine object on the heap holding its locals and a continuation. So a thread dump of a stalled async app shows idle pool threads and tells you nothing. dumpasync, an SOS command available through dotnet-dump analyze, scans the heap for those state machines and reconstructs the logical await chains — which method is awaiting which, and what the innermost one is waiting on. That is the async equivalent of a stack trace, and it is usually sufficient to name the bug. I would also mention the Visual Studio Tasks and Parallel Stacks windows for the same job during development, and that under .NET 11's Runtime Async the live stacks themselves become meaningful again, which makes profilers and any new StackTrace()-based diagnostics considerably more useful.

How do you write a deterministic test for a timeout?

By injecting TimeProvider — added in .NET 8 — and using FakeTimeProvider in the test. The production code takes TimeProvider.System, uses the Task.Delay, CancelAfter and WaitAsync overloads that accept one, and the test advances the clock instantly, so a 30-second timeout is verified in microseconds with no flakiness. Before TimeProvider, the equivalent was a hand-rolled IClock plus an injectable delay function, which most codebases still have somewhere; migrating them is a small, high-value cleanup. What I would not accept is a test that actually waits, because it makes the suite slow and, worse, it makes the assertion probabilistic on a loaded CI agent — and a flaky test is eventually a disabled test.

How do you test that two callers are correctly serialised by an async mutex?

I control completion rather than timing. I make the dependency return a task from a TaskCompletionSource I hold, start two calls, and assert that the second one has not progressed — for example by checking a counter of how many times the dependency was invoked, which should be one. Then I complete the source and await both, asserting the final state. That gives an exact interleaving with no sleeps. The one detail that matters is creating the source with RunContinuationsAsynchronously, so completing it in the test does not run the continuation inline on the test thread and produce an ordering the production code will never see. If a test needs several such gates I give them names, because the failure message from an interleaving assertion is otherwise unreadable.

How do you benchmark async code without fooling yourself?

Release configuration always, since the Debug state machine is a class and allocation numbers are meaningless otherwise. Use BenchmarkDotNet, return the task from the benchmark method rather than blocking inside it, and turn on MemoryDiagnoser, because for async the allocation profile is usually more decision-relevant than the nanoseconds. Model the real synchronous-completion rate, since anything comparing Task and ValueTask is entirely determined by it. And be clear about what a microbenchmark cannot show: thread-pool starvation, connection-pool contention and GC behaviour under sustained load are emergent, so the decisions that matter most get made with a load test against a realistic dependency, not with a benchmark of a single method.

How does distributed tracing survive across awaits?

Through ExecutionContext: Activity.Current is an AsyncLocal, so it flows into continuations and into work you start, which is why an OpenTelemetry trace stays coherent across a chain of awaits without you passing anything. The places it breaks are the places context does not flow: work started under ExecutionContext.SuppressFlow, a message handed to a queue and picked up in another process — where you must propagate the trace context explicitly in the message headers — and any custom thread that was created outside the operation. Two practical notes: starting an Activity per item in a very hot loop is expensive, both for the allocation and the copy-on-write context, so sample; and when using fire-and-forget, the background work will otherwise attach itself to the request's trace and make one request look pathologically slow.

What would you put in a load test to catch async regressions before production?

A fixed arrival rate, held long enough for the pool to reach steady state, with assertions on more than latency. I assert on p99, but also on thread count — because starvation shows up there first and much more clearly — and on the in-flight gauge, so a change that removes a throttle fails the build rather than the customer. I include a scenario where a dependency is deliberately slow, since that is when blocking code reveals itself, and one where clients disconnect mid-request, which exercises the cancellation paths that are otherwise never tested. Making it a gate takes discipline: the test must be stable enough not to be routinely overridden, so I keep the rate modest and the assertions on shapes rather than absolute numbers.

How do you find blocking calls hiding in a large codebase?

Statically first: analyzers for .Result, .Wait(), GetAwaiter().GetResult(), synchronous SemaphoreSlim.Wait, and CA1849 for sync calls with async alternatives — set as errors so nothing new lands. That misses the interesting ones, which are inside dependencies, so dynamically I run a representative load and take a few dotnet-stack samples: a thread parked in a kernel wait under a call chain that includes your code is a blocking call, whoever wrote it. dotnet-trace with the thread-pool and task providers shows the same thing over time. The category people forget is the third-party client that looks async but is a synchronous implementation behind a Task.FromResult; the only way to find those is to look at the stacks, or to notice that its "async" calls never yield.

Your p99 doubled after a release with no obvious code change. What is your hypothesis list?

For an async service, in the order I would check: something new is blocking — a synchronous call added to a hot path, or a dependency upgraded to a version whose async path is a wrapper; concurrency limits changed, so either a throttle was removed and the dependency is now saturated, or a limit was tightened and requests queue; a new AsyncLocal or logging scope in a hot loop, which is a surprisingly common cause because the copy-on-write cost is invisible in review; the connection pool is exhausted because a context or client is no longer being disposed; and GC pressure from a serialisation change, which shows as latency but not as thread growth. I would confirm with counters before touching anything, because those hypotheses have different fixes and the first two look identical from a latency graph alone.

12 Runtime Async (.NET 11)

Docs: What's new in the .NET 11 runtime · What's new in .NET 11

This is the one genuinely new thing in this topic, and the one detail that shows an interviewer you are current in September 2026. .NET 11 is in preview — Preview 7 as of August 2026, with GA expected in November 2026 — and its headline runtime feature is Runtime Async: moving suspension and resumption out of compiler-generated state machines and into the runtime itself.

What actually changes

Under the classic model the C# compiler rewrites every async method into a state machine type before the runtime ever sees it, and the JIT compiles that rewritten shape with no idea that it was ever asynchronous. Under Runtime Async the compiler preserves the original asynchronous control flow in IL, and the JIT compiles it directly using a new async calling convention. Alongside the normal arguments, that convention passes a continuation object holding the state needed to resume. The first call passes null: there is nothing to restore, so the method starts at the top like an ordinary synchronous method, and if it never suspends it returns its result with a null continuation — which is how the caller knows it completed synchronously. That null-continuation fast path is the design's central trick, and it is why the synchronous case can be nearly as cheap as a plain call.

The performance work behind the headline

  • Dedicated JIT async versions. The JIT compiles a runtime-async version of a synchronous task-returning method instead of routing through a thunk, and turns tail calls into runtime-async calls, removing a layer of indirection.
  • Continuations without ExecutionContext. Every task continuation previously captured and restored the execution context even when no AsyncLocal value existed and the restore was a no-op. The runtime now detects that and skips the whole cycle — for Task, Task<T>, ValueTask and ValueTask<T> alike. Code that uses ConfigureAwait(false) and few AsyncLocals — the standard server profile — benefits most.
  • Tiered compilation for async. Async versions now flow through tiered compilation, so hot async methods reach tier 1 after warm-up like everything else.
  • Cached continuations, tail-merged suspension points, factory intrinsics. The JIT recognises Task.FromResult, Task.CompletedTask and ValueTask.FromResult and folds them into faster paths; suspension points are tail-merged to shrink generated code; await Task.Yield() avoids extra allocations.
  • AOT and R2R support. Runtime Async works with NativeAOT and ReadyToRun; the crossgen2 restrictions that blocked inlining of runtime-async methods were removed, so the await-less synchronous fast path inlines end to end.

What it does not change

Be precise here, because overclaiming is how candidates lose the point. It does not change the semantics of async/await, the meaning of ConfigureAwait, where continuations run, or anything about cancellation. It does not fix sync-over-async: blocking on a task still blocks a thread, and a service that deadlocks on .Result will deadlock identically. It does not remove the need for ValueTask discipline, and it does not make exception stack traces from a catch block noticeably better — those already looked much the same, because ExceptionDispatchInfo cleanup handled them. The improvement is in live stacks: what a profiler, a debugger's call-stack window or a new StackTrace() sees during execution.

Interview Q&A

What is Runtime Async and why is Microsoft doing it?

It moves async suspension and resumption from Roslyn-generated state machines into the runtime, using a new async calling convention in which methods receive a continuation object and return one when they suspend. The motivation is that the compiler transformation throws away information the JIT could use: because every local that might cross an await is hoisted into a heap object before the JIT ever sees the method, the JIT cannot decide what really needs to be on the heap, cannot inline through the boundary well, and produces stacks full of infrastructure. Doing the split in the runtime restores that information, so locals stay on the stack unless they truly cross a suspension, continuations can be reused, chains of async calls can avoid allocating tasks at all, and live stack traces show the methods you wrote. Better debugging and profiling arguably matter more day to day than the allocation numbers.

Is it on by default in .NET 11?

Not for your code — it is a preview feature you opt into with <Features>runtime-async=on</Features>, though on a net11.0 target it no longer needs EnablePreviewFeatures. But it is on for the framework: the .NET 11 runtime libraries are compiled with it and no longer contain compiler-generated state machines, so every BCL async method you call runs the new model regardless. The environment variables that previously toggled it, DOTNET_RuntimeAsync and UNSUPPORTED_RuntimeAsync, have been removed; the per-project opt-out is <UseRuntimeAsync>false</UseRuntimeAsync>. That combination is why I would test an app on .NET 11 well before adopting the flag: you inherit the change in the libraries either way.

Would you turn it on in production today?

No, not in September 2026, and I would say why rather than just declining. It is preview, .NET 11 itself is preview until November, and the failure modes of a change at this level — JIT codegen for every async method in the process — are the kind you find with time and traffic rather than with a test suite. What I would do now is run our test suite and a load test on .NET 11 preview with the flag on in a non-production environment, because the feedback is genuinely wanted and because our own benchmarks are the only ones that matter. I would also check anything that reads stack traces at run time — APM agents, error grouping, custom diagnostics — since the frames change. Then I would revisit adoption a servicing release or two after GA, which is my normal policy for anything that changes codegen.

What is the async calling convention, concretely?

In addition to the normal arguments, an async method receives a continuation object and can return one. The first call passes null, meaning "no state to restore", so the method runs from the top like a synchronous method; if it completes without suspending it returns its result together with a null continuation, and the caller uses that null to detect synchronous completion cheaply. If it does suspend, it builds a continuation capturing what is needed to resume and returns that instead. The JIT can then optimise the handoff between two runtime-async methods directly, which is where "chains of async calls can avoid task allocations entirely" comes from. It also means the physical stack during execution contains the real methods rather than builder frames, which is the mechanism behind the cleaner traces.

What does the ExecutionContext optimisation actually save?

Previously every task continuation captured a snapshot of the execution context and restored it before running, so that AsyncLocal values and other ambient state would be correct — even when nothing was stored in it and the restore was a pure no-op. .NET 11 detects that case and skips the capture and restore entirely, for Task, Task<T>, ValueTask, ValueTask<T> and the runtime-async path. The saving per await is small but it is on the hottest path in the platform, and it lands exactly on the standard server profile: library code using ConfigureAwait(false) with few or no AsyncLocals. The flip side is a design consequence worth naming: a codebase that sprinkles AsyncLocal values everywhere opts itself out of the optimisation, which is one more reason to treat ambient state as scarce.

Does Runtime Async change how you write code?

No, and that is deliberate — it is a compilation and runtime change, not a language change. async, await, Task, ValueTask, ConfigureAwait, cancellation and exception semantics are all identical, which is what makes it adoptable at all. What it does change is the cost model, and that shifts some advice at the margins: some of the hand-optimisation people do today — avoiding an async wrapper to save a state machine, or reaching for PoolingAsyncValueTaskMethodBuilder — gets less valuable when the runtime keeps locals on the stack and reuses continuations. I would not preemptively undo those optimisations, but I would stop adding new ones on faith and re-measure once we are on .NET 11.

What are the compatibility risks of moving to it?

Three that I would actually check. Anything that reads stack traces at run time sees different frames: APM agents, error-grouping heuristics that hash a stack, and home-grown diagnostics calling new StackTrace(). Anything that reflects over compiler-generated state machine types — some serialisers, some test frameworks, some profilers, and any code keying off the AsyncStateMachineAttribute — will find they are no longer there in runtime-async assemblies. And the change interacts with AOT and ReadyToRun, which .NET 11 supports but which is where I would look first if something odd happens in a published app. Beyond those, the risk is the generic risk of new JIT codegen, which is why I would want it under load in staging for a meaningful period before production.

A stakeholder wants to ship .NET 11 with Runtime Async now, for the performance. How do you respond?

I would separate the two decisions, because they are different risks. Moving to .NET 11 at GA is a normal, scheduled upgrade with a real forcing function: .NET 8 and .NET 9 both go out of support on 10 November 2026, so we have to be on 10 or 11 regardless, and I would be planning that migration now. Enabling Runtime Async in our own assemblies is a separate, optional flag whose benefit for us is unmeasured, and I would ask what problem we are solving — if async allocation is genuinely in our profile, I would want the benchmark before the flag, and if it is not, the flag buys us risk for nothing. I would offer a concrete plan instead of a flat no: upgrade to .NET 10 LTS now if we are not there, evaluate .NET 11 in staging during preview, adopt after GA, and treat the flag as a measured experiment afterwards. That reframes it from "are you blocking performance work" to "here is the sequence", which is usually what the stakeholder actually wants.

What else in the recent releases is worth knowing for this topic?

Going backwards: .NET 10 put LINQ over IAsyncEnumerable in the box as System.Linq.AsyncEnumerable, superseding the community package and creating an ambiguity break for projects that reference both; it also added first-class server-sent events in ASP.NET Core and a set of async ZIP APIs. .NET 9 added Task.WhenEach, which removes the awkward WhenAny-in-a-loop idiom, and System.Threading.Lock as a faster, type-safe lock — still not awaitable. .NET 8 added ConfigureAwaitOptions with SuppressThrowing and ForceYielding, and TimeProvider, which is the thing that finally made timeouts testable. .NET 6 gave us Parallel.ForEachAsync and Task.WaitAsync. Being able to attach features to versions like that is most of what "be precise about versions" means in an interview.

If Runtime Async is the future, what happens to everything in units 01 to 11?

Almost all of it survives, because it is about semantics rather than implementation. Where continuations run, what ConfigureAwait does, why sync-over-async starves the pool, how cancellation flows, the ValueTask contract, backpressure — none of that is affected by who generates the suspension code. What ages is the mechanical detail: "the compiler emits a state machine struct that gets boxed at the first await" becomes a description of how it used to work, and some allocation-avoidance micro-patterns become unnecessary. That is a good thing to say in an interview because it demonstrates the distinction between a model and an implementation. The mental model I would keep is the one from unit 01 — an async method is chopped into pieces at each await, and something has to run the next piece — and Runtime Async just changes who does the chopping.

13 The big Q&A

Everything that is not a core building block: the architecture, security, tooling, migration and judgment questions that decide a lead/principal interview.

Architecture and ecosystem decisions
How do you decide between async I/O, a background job and a message queue for a piece of work?

I ask how long it takes, whether the caller needs the result, and what happens if the process dies mid-way. If it is short and the caller needs the answer, it belongs in the request as an awaited call. If the caller does not need the result but losing the work is acceptable — a cache warm, a metric — an in-process background worker fed by a bounded channel is enough, and I still give it a lifetime and a concurrency bound. If losing the work is not acceptable, or it takes longer than a request should live, or it must survive a deployment, it goes to a durable queue with an idempotent handler, and the API returns an id the client can poll. The mistake I watch for is the middle case dressed as the last: fire-and-forget work in a request handler that someone assumes is durable, which is fine until the first rolling deploy at peak.

Where do you put concurrency limits in a layered system?

As close as possible to the resource being protected, and expressed once. A limit inside the HTTP client wrapper protects the downstream service regardless of how many call sites there are; a limit in each call site protects nothing, because they add up. So per-dependency bulkheads at the client, connection-pool sizing at the data layer, and, at the edge, admission control that rejects quickly when the system is at capacity rather than accepting work it cannot do. I want each limit to be observable — an in-flight gauge and a rejection counter — because an invisible limit is indistinguishable from a slow dependency on a dashboard. And I want them chosen from the downstream's stated capacity divided by my instance count, not from a number that felt safe.

Async everywhere — is there a case against it?

There is, and being able to make it is worth more than advocacy. Async has costs: state machines and their allocations, harder stack traces (until .NET 11 improves live ones), a steeper debugging story, and the loss of the natural backpressure that a thread-per-request model gave you for free. In a low-concurrency internal tool, a console utility or a CPU-bound service, those costs buy very little. What tips it the other way in almost every server is that the boundary between async and sync code is where deadlocks and starvation live, so a partially async codebase is riskier than either extreme. My position is: async everywhere within a service that does I/O, synchronous where there is no I/O and no framework requirement, and no mixed call chains.

How does async change your capacity model?

It moves the constraint. Synchronously, capacity is threads, and the model is simple: concurrency equals thread count, and everything queues at the front door where you can see it. Asynchronously, threads are no longer the limit, so capacity is set by whatever is next — connection pools, downstream rate limits, memory for in-flight state, or the CPU needed to process responses. The practical consequences are that you must model those explicitly, that memory becomes a first-class capacity dimension because every in-flight operation holds a state machine and its buffers, and that queues move to places without a natural bound. So when I make a service async, I add explicit limits and in-flight metrics at the same time; otherwise I have removed the safety valve and kept none of the visibility.

Would you build a public library API on Task, ValueTask or IAsyncEnumerable?

Task or Task<T> by default, because it composes with everything, can be awaited more than once, and imposes no contract on the caller beyond the obvious. ValueTask<T> only where the operation usually completes synchronously and is called at a rate where allocation matters, with the single-consumption rule documented at the API. IAsyncEnumerable<T> where the result is a sequence that is genuinely produced over time — a stream, a cursor, a paged fetch — because it gives the consumer backpressure and O(1) memory. I also always take a CancellationToken as the last parameter and forward it, since a library that ignores cancellation cannot be used well by anyone; and I keep synchronous overloads out entirely rather than implementing them by blocking.

Security and correctness
What are the security implications of ambient state flowing across awaits?

The upside is that identity travels with the logical operation: ExecutionContext carries the security context, so a continuation runs with the same principal as the code that started it, and that is what makes authorisation checks meaningful across awaits. The risks come from the edges. Work started with ExecutionContext.SuppressFlow, or on a raw thread, does not inherit that context, so a background task can run with different — often more or less — privilege than the request that spawned it. Pool threads are shared, so anything you stash in thread-local storage rather than AsyncLocal can leak between unrelated requests, which is a genuine cross-tenant data exposure and one I have seen in real code. And capturing HttpContext or a scoped identity in a fire-and-forget task means acting on state that has been recycled by the time the work runs.

How does cancellation interact with correctness in a system that writes data?

Cancellation is a request to stop waiting; it says nothing about whether the effect happened. A cancelled HTTP POST may have been processed, a cancelled database command may have committed, and a token that fires between two writes leaves you half-applied. So anything that mutates state needs the same treatment as a failure: idempotency keys so a retry is safe, a durable record of intent before the effect, and reconciliation afterwards. I am also deliberate about which token I pass to writes — cancelling a half-finished unit of work because the browser tab closed is usually the wrong behaviour, and I would rather finish the transaction and skip the response. And cleanup paths get a fresh token with a short timeout, because doing compensating work with the token that was just cancelled means the compensation is cancelled too.

Can async introduce a denial-of-service risk in your own service?

Yes, in two directions. Outbound, because unbounded fan-out turns your service into a load generator against a dependency, and retries multiply it at exactly the wrong moment — the classic self-inflicted outage. Inbound, because async removes the thread-count ceiling that used to shed load implicitly: a synchronous service naturally rejected work when threads ran out, whereas an async one accepts everything and converts the overload into unbounded memory for in-flight state and unbounded queue depth downstream. Both are solved the same way: explicit limits with fast rejection. Bounded channels rather than unbounded, admission control at the edge that returns 429 rather than queueing, per-dependency bulkheads and circuit breakers, and timeouts on everything so a stuck call cannot accumulate.

Performance and debugging
Where does the time actually go in a typical async request?

Almost always in the waiting, not in the async machinery. A request that makes three dependency calls at 20 ms each spends 60 ms waiting and microseconds in state machines, so optimising the async plumbing before removing a round trip is backwards. The order I actually work in: reduce round trips (batch, cache, or join instead of N+1), then overlap the independent ones with WhenAll, then reduce payload and serialisation cost, and only then look at allocation and the async machinery itself. The exception is code called millions of times a second — a framework, a parser, a proxy hot path — where the machinery genuinely is the cost, and that is where ValueTask, pooling builders and now Runtime Async earn their complexity.

How do you profile an async application without drowning in noise?

I start with counters rather than a profiler, because they classify the problem in seconds and cost nothing: thread count, queue length, GC time, allocation rate, and my own in-flight gauges. If it is a latency question I use a trace with a targeted provider list — dotnet-trace with the task, HTTP and GC providers rather than everything — and look at the distribution rather than the mean, because async systems fail at the tail. If it is a hang or a leak, I take a dump and use dumpasync or a gcdump, since the state lives on the heap and not on the stacks. What I try to avoid is sampling CPU profilers as the first tool, because a starved or waiting async app has no CPU to sample and the profile looks empty, which is the classic wrong turn.

Give me the shortest possible summary of async allocation costs.

A method that never suspends allocates nothing in Release, because the state machine stays a stack-allocated struct. A method that suspends allocates two things: the boxed state machine holding its hoisted locals, and the returned task — and later awaits in the same method reuse that box. ValueTask removes the second when the result is available synchronously, and PoolingAsyncValueTaskMethodBuilder can remove the first. Closures captured by lambdas inside the method add more, which is why static lambdas with an explicit state argument are worth the small ugliness in hot code. And in .NET 11 Runtime Async attacks the first cost structurally, by keeping locals on the stack unless they genuinely cross a suspension and by reusing continuations.

Your latency is fine at p50 and terrible at p99. What does that suggest in an async service?

Queueing somewhere, since a uniform slowdown moves the median too. The candidates I check, roughly in order: thread-pool queueing from occasional blocking calls, which shows as thread growth with low CPU; connection-pool contention, where most requests get a connection immediately and the unlucky ones wait; GC pauses, visible as correlated spikes across unrelated endpoints; a dependency whose own tail is bad, which shows up isolated to the calls that touch it; and lock or semaphore contention, where a shared gate serialises a small fraction of traffic. The distinguishing evidence is different for each — counters for the first three, per-dependency histograms for the fourth, a dump for the last — which is why I would resist changing anything before I know which one it is.

Tooling and team practice
Which analyzers would you make errors in a .NET codebase for async correctness?

The ones whose violations are always bugs. CA2012 (do not store a ValueTask for later consumption), CA2016 (forward the CancellationToken), CA1849 (do not call synchronous methods when an async alternative exists inside an async method), and the compiler's own CS4014 for unawaited calls, promoted from warning to error. CA2007 (ConfigureAwait) as an error in library projects only, off in application projects, so the signal stays meaningful. Beyond the built-ins, I ban .Result, .Wait() and Thread.Sleep in async contexts with a custom rule or a banned-API list, because those are the ones that cause incidents rather than untidiness. The principle is that anything I would block a pull request for should be enforced by the build, not by whoever reviews it that day.

How do you review async code efficiently?

I read for a short list of shapes rather than line by line, because the defects are structural. Blocking calls anywhere. Unawaited tasks and async void. Tokens accepted but not forwarded, and bare catches of OperationCanceledException. Unbounded fan-out over a collection whose size is not fixed by the code. Shared non-thread-safe state — a DbContext, an HttpContext, a scoped service — used from concurrent branches. Missing disposal of linked token sources and registrations. And, at the design level, whether the concurrency of this change is bounded and observable. If I find more than a couple, I stop enumerating and have a conversation instead, because a review comment thread is a poor place to teach the model.

What does good observability for async work look like?

It answers "what is in flight and what is it waiting for" without a debugger. Concretely: an in-flight gauge per dependency and per background pipeline, queue depth for every channel, thread-pool thread count and pending work items, a rejection counter for every limit so throttling is visible rather than looking like latency, cancellation separated from errors, and a counter for unobserved task exceptions. On top of that, distributed tracing with spans around each awaited call, which is nearly free because Activity.Current flows on the execution context. The test I apply is whether an on-call engineer who has never seen the code can tell, from the dashboard alone, whether the service is waiting, working, or refusing work — and if not, what is missing is usually a limit that has no metric.

Legacy and migration reality
What are the async differences you must remember on .NET Framework?

The synchronization context is the big one: classic ASP.NET has a per-request context, so .Result deadlocks where the same code runs fine on ASP.NET Core. ConfigureAwait(false) therefore matters far more there. You do not have the modern conveniences — no ConfigureAwaitOptions, no TimeProvider, no Task.WaitAsync, no Parallel.ForEachAsync, no WhenEach, and IAsyncEnumerable only through Microsoft.Bcl.AsyncInterfaces. The thread pool is the older implementation with different injection behaviour. And TransactionScope needs TransactionScopeAsyncFlowOption.Enabled or the ambient transaction does not flow. When I work on such a codebase I keep a written list of these, because the muscle memory from modern .NET is actively wrong in a couple of places.

How would you migrate a synchronous WCF-era service layer to async?

From the outside in, one vertical slice at a time. I start at an entry point — one endpoint or one message handler — and convert the whole chain down to the driver, so the slice is async end to end and no sync/async boundary remains in the middle of it. Each converted slice gets a load test against the old behaviour before it ships, because the failure mode of a partial migration is starvation rather than a compile error. Where a dependency has no async API, I leave the blocking call, isolate it behind one named method, bound its concurrency with a semaphore so it cannot consume the whole pool, and record it as debt with an owner. I resist the two tempting shortcuts: a big-bang rewrite, and mechanically wrapping everything in Task.Run, which produces something that compiles, looks async and behaves worse than the original.

You find Task.Run(() => Foo()).Result in production code. What do you do?

First I understand why it is there, because it is usually a scar from a real deadlock rather than ignorance: someone hit the classic sync-context deadlock and this made it stop. Then I trace who calls it. If the caller can be async, the fix is to make it async and delete the whole construct. If the caller genuinely cannot — a legacy interface, a constructor, a plug-in contract — I keep a single blocking boundary but simplify it to GetAwaiter().GetResult(), since the extra Task.Run burns a second thread to no benefit once the context question is settled, and I add a comment naming the constraint. I would also check for a bigger pattern: one of these is a smell, thirty of them means the codebase has an async/sync boundary in the wrong place and the fix is architectural.

How do you handle a third-party library with no async support?

I accept that I cannot make it asynchronous and design around the fact that each call costs a thread. That means bounding it: a semaphore or a dedicated bounded worker pool so those calls can never consume the shared thread pool, which turns a potential outage into a slow subsystem. I make the boundary explicit in the code — a small adapter whose name says it blocks — so nobody mistakes it for real async. If the calls are long and central, I consider isolating them in a separate process or service so their failure mode is contained. And I set the expectation up front with the team and with monitoring, since the honest position is "this dependency limits us to N concurrent operations", which is a capacity fact to publish rather than a bug to hide.

Judgment and scenario
You are on call. Latency is climbing, CPU is 20%, thread count is 400 and rising. What do you do, in order?

Capture evidence first — a dump if I can afford the pause, otherwise dotnet-stack report and a counters sample — because the mitigation destroys it. Then mitigate: shed load or restart the worst instances to buy time, and if I know a blocking dependency is involved, raise min threads as a stopgap. Then diagnose from the captured stacks: hundreds of threads under Task.Wait or SemaphoreSlim.Wait names the call site directly. In parallel, check whether this correlates with a deploy or a dependency incident, since a rollback is often the fastest real fix. Afterwards I want the incident to produce three things: the code fix, a metric that would have caught it earlier, and an analyzer or test that stops the pattern returning — otherwise it comes back next quarter with a different call site.

A senior engineer insists ConfigureAwait(false) everywhere is pointless because you are on ASP.NET Core. How do you respond?

By agreeing with the part that is right, which is most of it. On ASP.NET Core there is no synchronization context, so it changes no behaviour in application code, and adding it there is noise. Where I disagree is scope: in library code — anything a WPF app, a Blazor circuit or a plug-in host might reference — capturing a context you do not control is both slower and a correctness hazard for that caller, and the library cannot know its host. So the resolution is not a global policy either way; it is CA2007 as an error in library projects and off in application projects, encoded in Directory.Build.props with a comment explaining the split. That converts an opinion argument into a build setting, which is usually the outcome worth aiming for.

A team wants to use ValueTask everywhere for performance. Talk them out of it — or into it.

I would ask for two numbers: the fraction of calls that complete synchronously on the paths they care about, and the share of total allocation that async machinery represents in a profile. If synchronous completion is high and the methods are genuinely hot, they are right and I would help them do it properly, with the split fast-path shape rather than a naive async ValueTask. If they cannot produce the numbers, the answer is no, because they are proposing to bind every current and future caller to a single-consumption contract whose violation fails non-deterministically, in exchange for an unmeasured gain. The framing I use is that ValueTask is not an optimisation, it is a trade of safety for allocation, and trades need a price on both sides.

How would you design an ingestion pipeline that must never lose messages and must not overwhelm a downstream API?

Durability first: messages land in a durable queue before I acknowledge anything, and handlers are idempotent, because at-least-once delivery plus retries makes duplicates certain. Then flow control: a bounded channel between the consumer and the workers so backpressure reaches the broker's prefetch rather than my heap, and a fixed number of worker loops sized from the downstream's published rate limit divided by my instance count. Then failure handling: per-message try/catch with classification — transient failures retried with exponential backoff and jitter, poison messages dead-lettered with the full context after a bounded number of attempts, and a circuit breaker so a downstream outage stops traffic instead of grinding through retries. Shutdown gets explicit attention, since the stopping token must stop intake while in-flight messages are finished or abandoned cleanly within the host's shutdown timeout. Finally, metrics on queue depth, in-flight count, retry rate and dead-letter rate, because those four tell you the pipeline's health without reading any logs.

What is the most valuable async lesson you would teach a team, if you could only teach one?

That await is about giving the thread back, not about going faster — and that everything painful follows from breaking that contract. Blocking on a task is the one forbidden move, and it explains deadlocks, starvation, and most of the incidents teams attribute to "the framework". The second-order lesson, if I get to add one, is that async removes a natural limit, so every place you make something async is a place you must decide, explicitly, how much of it may happen at once. Those two ideas — do not block, bound your concurrency — cover more real production failures than the entire API surface does, and they are also the two things that hold true whether the state machine is generated by the compiler or, from .NET 11, by the runtime.

14 Night-before cheat sheet

Ten sentences to say out loud until they are yours. Each one is a claim you can defend from the units above.

  1. Await is about giving the thread back, not about going faster. An async method is chopped into pieces at each await; the returned Task says when the last piece ran. Nothing in that involves a thread, and I/O has none while it waits.
  2. The current platform is .NET 10 with C# 14, an LTS released 11 November 2025 and supported to November 2028, with 10.0.11 the August 2026 servicing build. .NET 8 and .NET 9 both go out of support on 10 November 2026, so the migration is not optional.
  3. .NET 11, in preview now and GA expected November 2026, brings Runtime Async: suspension moves from compiler-generated state machines into the runtime's async calling convention, locals stay on the stack unless they cross a suspension, live stack traces drop from 13 frames to 5, and the BCL already ships compiled with runtime-async=on — but for my own code it is still an opt-in preview flag.
  4. The continuation runs on the captured SynchronizationContext if there is one; otherwise inline on the thread that completed the task. ASP.NET Core has no context, which is why the classic .Result deadlock does not reproduce there — and why the failure mode becomes thread-pool starvation instead.
  5. Blocking on a task is the one forbidden move. Above the minimum, the pool injects about one thread every 500 ms, so blocked threads produce stepped latency, low CPU and a climbing thread count. Raising min threads is a painkiller, not a fix.
  6. ConfigureAwait(false) is a library convention, not an app-level optimisation — a library does not know whether its caller is WPF, Blazor or a plug-in host. Since .NET 8, ConfigureAwaitOptions adds SuppressThrowing for shutdown paths and ForceYielding for breaking stack dives.
  7. Task is the default; ValueTask is a trade, not an upgrade. Await it exactly once, never block on it, never hand it to WhenAll — because it may be backed by a pooled IValueTaskSource, and violating that contract corrupts non-deterministically rather than throwing.
  8. Cancellation is cooperative and it is not a rollback. Pass the token everywhere, throw with ThrowIfCancellationRequested so the task ends Canceled rather than Faulted, dispose linked sources and registrations or you leak, and remember that a cancelled write may already have been applied.
  9. Unbounded concurrency is a design defect. WhenAll over an unknown-sized collection is a load generator; the defaults are Parallel.ForEachAsync with a degree derived from the downstream's limit, a bounded channel for real backpressure, and Task.WhenEach (.NET 9) to consume results as they land.
  10. When an async app hangs, the evidence is on the heap, not on the stacks. Take a dump and run dumpasync to see what each suspended operation is awaiting; a thread dump of a stalled async service looks deceptively healthy.
One more, if you only get one sentence

"Async does not reduce latency — it reduces the threads you need to absorb concurrency, and every place you make something async is a place you must decide, explicitly, how much of it may happen at once."
