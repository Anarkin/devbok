C# async/await & the Task-based asynchronous pattern

Task · ValueTask · cancellation · IAsyncEnumerable · ConfigureAwait · thread-pool behaviour — reference card

Syntax, the daily Task/ValueTask and cancellation APIs, async streams and channels, context and scheduling rules, thread-pool behaviour with its runtime knobs, concurrency patterns with their legacy shapes, analyzers and diagnostic commands, a modern-versus-legacy table and a version timeline — one line per item, verified against Microsoft Learn on 2026-09-07. Everything is stated for the current stable platform, .NET 10 (LTS, servicing release 10.0.11 of 2026-08-11) with C# 14; items that became true earlier or later carry their version. 1Syntax essentials docs ↗

Async method
async Task<int> LoadAsync(CancellationToken ct = default) { var s = await ReadAsync(ct); return s.Length; }
Return types
Task / Task<T> default · ValueTask / ValueTask<T> for hot paths that usually complete synchronouslyC# 7 · void event handlers only · any type carrying [AsyncMethodBuilder]C# 7
What is awaitable
anything exposing GetAwaiter() → IsCompleted, OnCompleted, GetResult(): Task, ValueTask, Task.Yield(), ConfiguredTaskAwaitable, your own
Async lambda
Func<int, Task<string>> f = async x => await GetAsync(x); · await Task.Run(async () => { … });an async lambda converted to Action becomes async void — its exceptions crash the process
Async local function
async Task<int> CountAsync() { … } inside a method — keeps argument validation eager: check args, then return CountAsync();
Entry point
static async Task Main(string[] args) or Task<int>C# 7.1 · top-level statements may await directlyC# 9
await in catch / finally
catch (Exception ex) { await LogAsync(ex); throw; }C# 6
Async dispose
await using var conn = new SqlConnection(cs); → IAsyncDisposable.DisposeAsync()C# 8 · await using (x.ConfigureAwait(false))
Async stream
await foreach (var item in source.WithCancellation(ct)) { … }C# 8
Async iterator
async IAsyncEnumerable<T> ReadAsync([EnumeratorCancellation] CancellationToken ct = default) { … yield return item; }
Yield the thread
await Task.Yield(); — re-queues the continuation (captured context if any, else the pool's global queue); it is not a background thread
Elide async/await
Task<User> GetAsync(int id) => _cache.GetAsync(id); — only when no using/try/loop wraps the call; you lose a frame in exception traces
Locks
await inside lock is error CS1996 — use SemaphoreSlim.WaitAsync; lock (_gate) on a System.Threading.Lock field for await-free sections.NET 9 · C# 13
ref / span in async
ref locals, ref struct locals (Span<T>) and unsafe blocks are allowed in async methods and iterators as long as none lives across an awaitC# 13
Exceptions
an async method never throws at the call site — even before its first await the exception lands on the returned Task; a non-async Task-returning method throws synchronously
Status flags
IsCompleted (any final state) · IsCompletedSuccessfully · IsFaulted · IsCanceled · Status == TaskStatus.WaitingForActivation = async method still running
public async Task<IReadOnlyList<Order>> LoadAsync(int customerId, CancellationToken ct = default)
{
    await using var conn = await _db.OpenAsync(ct).ConfigureAwait(false);   // async dispose + cancellation
    var orders = new List<Order>();
    await foreach (var row in conn.QueryAsync(customerId).WithCancellation(ct).ConfigureAwait(false))
        orders.Add(Map(row));
    return orders;                                                          // completes the Task<T>
}

2Task & ValueTask APIs docs ↗

Offload CPU work
await Task.Run(() => Compute(data), ct); · Task.Run(async () => await IoAsync()) unwraps to a plain Task
Dedicated thread
Task.Factory.StartNew(Loop, ct, TaskCreationOptions.LongRunning, TaskScheduler.Default) — an async delegate yields Task<Task>: add .Unwrap()
Pre-completed
Task.CompletedTask · Task.FromResult(v) · Task.FromException<T>(ex) · Task.FromCanceled<T>(ct).NET 4.6 · ValueTask.CompletedTask · ValueTask.FromResult(v).NET 5
All of them
T[] r = await Task.WhenAll(t1, t2, t3); — awaiting rethrows only the first fault; all are in whenAll.Exception.InnerExceptions · params ReadOnlySpan<Task> overloads.NET 9
First of them
var done = await Task.WhenAny(tasks); var r = await done; — the second await surfaces its exception
As they complete
await foreach (var t in Task.WhenEach(tasks)) Use(await t);.NET 9 — replaces the WhenAny-in-a-loop O(n²) idiom
Delay
await Task.Delay(TimeSpan.FromSeconds(1), ct); · Task.Delay(Timeout.Infinite, ct) = "until cancelled"
Timeout on any task
await task.WaitAsync(TimeSpan.FromSeconds(5), ct);.NET 6 → TimeoutException; the inner operation keeps running — give it a token too
Continuation (legacy)
t.ContinueWith(x => …, ct, TaskContinuationOptions.OnlyOnRanToCompletion, TaskScheduler.Default) — prefer await; CA2008 wants the scheduler explicit
Manual completion
var tcs = new TaskCompletionSource<int>(TaskCreationOptions.RunContinuationsAsynchronously); tcs.TrySetResult(42); · non-generic TaskCompletionSource.NET 5
Wrap old patterns
APM: Task.Factory.FromAsync(s.BeginRead, s.EndRead, buf, 0, n, null) · EAP / events: complete a TCS inside the Completed handler
Block (last resort)
task.GetAwaiter().GetResult() rethrows the real exception; task.Result / task.Wait() wrap it in AggregateException
ValueTask fast path
var vt = ReadAsync(); return vt.IsCompletedSuccessfully ? vt.Result : await vt; — .Result is legal only once completed
ValueTask rules
await it once · never block on it · no WhenAll — convert with vt.AsTask() · must consume twice? vt.Preserve().NET 5 · CA2012 enforces all of this
Pooled state machine
[AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))] async ValueTask<int> HotAsync()C# 10 · .NET 6 — per-method opt-in that amortizes the box on the asynchronous path
Custom awaitable source
implement IValueTaskSource<T> over ManualResetValueTaskSourceCore<T>.NET Core 3.0 — reusable, allocation-free awaits (Sockets, Pipelines and Channels do this)
Public API guidance
return Task/Task<T> by default; ValueTask<T> when profiling shows synchronous completion is common or the awaitable is pooled; non-generic ValueTask rarely beats Task (its CompletedTask is cached)

3Cancellation & timeouts docs ↗

Accept a token
Task DoAsync(…, CancellationToken ct = default) — last parameter, optional, forwarded to every call below (CA2016)
Create / cancel
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30)); · cts.CancelAfter(5_000); · cts.Cancel(); runs callbacks inline · await cts.CancelAsync();.NET 8 keeps the caller off the callback path
Link tokens
using var linked = CancellationTokenSource.CreateLinkedTokenSource(ct, timeoutCts.Token); — dispose it, or the registration on a long-lived parent leaks
Check in loops
ct.ThrowIfCancellationRequested(); (CA2250 prefers it to a manual throw) · if (ct.IsCancellationRequested) return; for a graceful exit
Callback
using CancellationTokenRegistration r = ct.Register(() => conn.Close()); · ct.UnsafeRegister(cb, state) without ExecutionContext.NET Core 3.0 · await r.DisposeAsync() waits for an in-flight callback
Token → Task
var tcs = new TaskCompletionSource(); using var _ = ct.Register(() => tcs.TrySetResult()); await tcs.Task; · or Task.Delay(Timeout.Infinite, ct) when throwing is acceptable
Throw correctly
throw new OperationCanceledException(ct); — pass the token so task.IsCanceled is true; TaskCanceledException : OperationCanceledException, so catch (OperationCanceledException) covers both
Who cancelled?
catch (OperationCanceledException) when (ct.IsCancellationRequested) = the caller · when (!ct.IsCancellationRequested) = a timeout or an internal source
HttpClient timeout
throws TaskCanceledException whose InnerException is TimeoutException.NET 5 — that is how you tell it from user cancellation
Task status on OCE
async method: any OperationCanceledException → Canceled · Task.Run(action, ct): Canceled only if the OCE's token equals ct, otherwise Faulted
Reuse a source
if (!cts.TryReset()) cts = new();.NET 6 — pooling for per-request sources
Abstract time
await Task.Delay(TimeSpan.FromSeconds(1), timeProvider, ct); · task.WaitAsync(TimeSpan, timeProvider) · new CancellationTokenSource(delay, timeProvider).NET 8 · tests: FakeTimeProvider.Advance(…) from Microsoft.Extensions.TimeProvider.Testing
Already cancelled
ct.Register(cb) on a cancelled token runs cb synchronously, right there · Task.FromCanceled(ct) requires ct.IsCancellationRequested
Sentinels
CancellationToken.None == default — never null · ct.CanBeCanceled to skip registrations cheaply
Hosting tokens
ASP.NET Core: HttpContext.RequestAborted (bound automatically to a CancellationToken parameter) · IHostApplicationLifetime.ApplicationStopping · BackgroundService.ExecuteAsync(stoppingToken)
using var timeout = new CancellationTokenSource(TimeSpan.FromSeconds(3));
using var linked  = CancellationTokenSource.CreateLinkedTokenSource(ct, timeout.Token);
try   { return await client.GetStringAsync(url, linked.Token); }
catch (OperationCanceledException) when (timeout.IsCancellationRequested && !ct.IsCancellationRequested)
      { throw new TimeoutException($"{url} exceeded 3 s"); }            // caller cancellation propagates as OCE

4IAsyncEnumerable & channels docs ↗

Produce
async IAsyncEnumerable<Row> RowsAsync([EnumeratorCancellation] CancellationToken ct = default) { while (await r.ReadAsync(ct)) yield return Map(r); }
Consume
await foreach (var row in RowsAsync().WithCancellation(ct).ConfigureAwait(false)) …
Cancellation plumbing
WithCancellation(ct) is merged into the [EnumeratorCancellation] parameter (both given → linked source); without the attribute CS8425 warns and the token is ignored
Laziness
the body runs on the first MoveNextAsync(), not at the call; every await foreach re-runs it — ToListAsync(ct) once if you enumerate twice
LINQ in-box
using System.Linq; → await rows.Where(r => r.Ok).Select(r => r.Id).Take(10).ToListAsync(ct).NET 10 · async predicates are overloads: .Where(async (r, ct) => await CheckAsync(r, ct)) — no WhereAwait any more · LeftJoin/RightJoin/FullJoin.NET 11 preview
Old package
System.Linq.Async (Ix) → remove the reference, or take 7.0 which forwards to the BCLsuperseded .NET 10
Adapters
list.ToAsyncEnumerable() · AsyncEnumerable.Empty<T>() · AsyncEnumerable.Range(0, n) · ToArrayAsync · CountAsync · FirstOrDefaultAsync · AggregateAsync
Manual enumeration
await using var e = src.GetAsyncEnumerator(ct); while (await e.MoveNextAsync()) Use(e.Current);
Bounded channel
var ch = Channel.CreateBounded<Job>(new BoundedChannelOptions(1_000) { FullMode = BoundedChannelFullMode.Wait, SingleReader = true });
Write
await ch.Writer.WriteAsync(job, ct); · ch.Writer.TryWrite(job) · ch.Writer.Complete(error) / TryComplete()
Read
await foreach (var job in ch.Reader.ReadAllAsync(ct)) … · while (await ch.Reader.WaitToReadAsync(ct)) while (ch.Reader.TryRead(out var j)) … · await ch.Reader.Completion
Other channels
Channel.CreateUnbounded<T>(new UnboundedChannelOptions { SingleWriter = true }) · Channel.CreateUnboundedPrioritized<T>(new() { Comparer = … }).NET 9
Backpressure
Wait = the producer awaits (lossless) · DropOldest / DropNewest / DropWrite for telemetry-style lossy queues, with an itemDropped callback
Stream JSON
JsonSerializer.SerializeAsync(stream, asyncEnumerable, ct) streams items · JsonSerializer.DeserializeAsyncEnumerable<T>(stream, ct).NET 6 · ASP.NET Core writes a returned IAsyncEnumerable<T> as streamed JSON
Implement IAsyncDisposable
public async ValueTask DisposeAsync() { await _conn.DisposeAsync().ConfigureAwait(false); GC.SuppressFinalize(this); } — also implement IDisposable when wrapping sync resources; Dispose() must never block on async work
var ch = Channel.CreateBounded<Job>(new BoundedChannelOptions(500) { FullMode = BoundedChannelFullMode.Wait });
var consumers = Enumerable.Range(0, Environment.ProcessorCount).Select(_ => Task.Run(async () =>
{
    await foreach (var job in ch.Reader.ReadAllAsync(ct)) await HandleAsync(job, ct);
}, ct)).ToArray();
await foreach (var job in SourceAsync(ct)) await ch.Writer.WriteAsync(job, ct);   // awaits while full
ch.Writer.Complete();
await Task.WhenAll(consumers);

5Context, ConfigureAwait & scheduling docs ↗

What await captures
SynchronizationContext.Current, else a non-default TaskScheduler.Current, else nothing → the continuation runs on the pool or inline on the completing thread
Where a context exists
WPF, WinForms, MAUI, Blazor Server (the UI thread) · none in ASP.NET Core, console apps and Worker Services — ConfigureAwait(false) is a no-op there
Library rule
await x.ConfigureAwait(false); on every await in library / general-purpose code (CA2007); app code that needs the UI thread afterwards keeps the default
Options
ConfigureAwait(ConfigureAwaitOptions.None) = false · ContinueOnCapturedContext = true · SuppressThrowing awaits a faulted or cancelled Task without throwing (not Task<T>) · ForceYielding never continues synchronously.NET 8
Back to the UI
stay on the captured context by not using ConfigureAwait(false); from elsewhere: await dispatcher.InvokeAsync(…) / syncCtx.Post(…) / TaskScheduler.FromCurrentSynchronizationContext() for ContinueWith
The deadlock
the context thread blocks in .Result/.Wait() while the awaited method's continuation needs that same context → hang. Fix: await all the way up; ConfigureAwait(false) in the callee helps only if every await in the chain has it
Continuation inlining
an await continuation runs synchronously on whichever thread completes the task (no context) — completing a TCS while holding a lock or on an I/O thread runs consumer code right there; use TaskCreationOptions.RunContinuationsAsynchronously
ExecutionContext / AsyncLocal
AsyncLocal<T> flows across await, Task.Run, QueueUserWorkItem and timers; not across the Unsafe* APIs · a child's writes never propagate up · using (ExecutionContext.SuppressFlow()) before starting background loops from a request
EC fast path
continuations skip ExecutionContext capture/restore when there is nothing to restore — Task, ValueTask and runtime-async paths alike.NET 11 P6
Schedulers
TaskScheduler.Default = pool · TaskScheduler.Current = the running task's scheduler (why CA2008 wants it explicit) · new ConcurrentExclusiveSchedulerPair(TaskScheduler.Default, maxConcurrencyLevel: 4) for bounded concurrency without locks
Creation options
DenyChildAttach (what Task.Run uses) vs AttachedToParentlegacy · PreferFairness → global queue · LongRunning → own thread · HideScheduler
Task.Yield semantics
posts to the captured context if any, else to the pool's global queue (fair) — use it to let a UI paint, or so a long synchronous prefix in ExecuteAsync stops delaying host start-up
Blazor WebAssembly
single-threaded: everything continues on the same thread; ConfigureAwait(false) changes nothing and any blocking wait deadlocks instantly
Old hack
SynchronizationContext.SetSynchronizationContext(null) around callsdon't — use ConfigureAwait(false) or Task.Run to leave the context

6Thread pool behaviour & knobs docs ↗

Two thread kinds
worker threads run Task.Run, continuations and timer callbacks; I/O completion threads drain IOCP (Windows) or the epoll/kqueue engines (Unix) and hand continuations to workers
Defaults
min workers = Environment.ProcessorCount (cgroup/quota-aware; override with DOTNET_PROCESSOR_COUNT.NET 6) · max = 32,767 · idle threads retire after ~20 s
Injection
up to the minimum: a thread per queued item, immediately · above it: hill-climbing adds or removes ≈1–2 threads/s while measuring throughput — that ramp is the latency cliff during starvation
Blocking-aware injection
a pool thread blocking in Task.Wait/.Result/GetResult() triggers immediate extra threads (up to ThreadsToAddWithoutDelay_ProcCountFactor × cores), then delayed ones.NET 6 — Monitor, semaphore and Thread.Sleep blocking is not detected
Queues
global FIFO queue + per-worker local LIFO deque with work stealing; a Task.Run issued from a pool thread lands in that thread's local queue (hot cache, weaker fairness) — PreferFairness / preferLocal: false → global
Starvation signature
dotnet.thread_pool.queue.length climbs, thread count rises ~1/s, p99 latency explodes while CPU stays low → sync-over-async or blocking I/O on pool threads
Mitigate in an incident
ThreadPool.SetMinThreads(workerThreads: Environment.ProcessorCount * 4, completionPortThreads: …) or the env var below — buys minutes; then find the blocking call with dotnet-stack
Long / blocking work
Task.Factory.StartNew(Loop, TaskCreationOptions.LongRunning) → a dedicated thread outside the pool · new Thread(Loop) { IsBackground = true }.Start() for permanent loops
Raw enqueue
ThreadPool.QueueUserWorkItem(static s => Work(s), state, preferLocal: false) (flows ExecutionContext) · ThreadPool.UnsafeQueueUserWorkItem(IThreadPoolWorkItem, preferLocal).NET Core 3.0 zero-alloc, no EC
Inspect from code
ThreadPool.ThreadCount · ThreadPool.PendingWorkItemCount · ThreadPool.CompletedWorkItemCount.NET Core 3.0 · ThreadPool.GetAvailableThreads(out w, out io)
Min / max config
runtimeconfig System.Threading.ThreadPool.MinThreads / .MaxThreads · MSBuild <ThreadPoolMinThreads> / <ThreadPoolMaxThreads> · env DOTNET_ThreadPool_ForceMinWorkerThreads=0x40 (hex).NET 10
Windows thread pool
<UseWindowsThreadPool>true</UseWindowsThreadPool> / DOTNET_ThreadPool_UseWindowsThreadPool=1.NET 8 — default only for NativeAOT on Windows; SetMinThreads/SetMaxThreads are ignored there
Blocking knobs
runtimeconfig System.Threading.ThreadPool.Blocking.ThreadsToAddWithoutDelay_ProcCountFactor, …ThreadsPerDelayStep_ProcCountFactor, …DelayStepMs, …MaxDelayMs.NET 6, …IgnoreMemoryUsage.NET 7
Stack size
System.Threading.DefaultStackSize / DOTNET_Thread_DefaultStackSize (hex).NET 10 — default 1.5 MB on Windows/macOS, 8 MB on Linux
Implementation
the managed "portable" pool is the default on every OS since.NET 6; the opt-out to the native Windows pool was removed in .NET 7
Timers
System.Threading.Timer callbacks run on pool threads and overlap when slow · PeriodicTimer.NET 6 never overlaps: while (await timer.WaitForNextTickAsync(ct)) …
Metrics
System.Runtime meter.NET 9: dotnet.thread_pool.thread.count, dotnet.thread_pool.queue.length, dotnet.thread_pool.work_item.count, dotnet.monitor.lock_contentions, dotnet.timer.count · EventCounters: threadpool-thread-count, threadpool-queue-length, threadpool-completed-items-count

7Concurrency patterns — modern, with the legacy shape docs ↗

Fan-out / fan-in
var results = await Task.WhenAll(ids.Select(id => FetchAsync(id, ct))); — start all, await oncelegacy: foreach (var id in ids) results.Add(await FetchAsync(id)); — serial by accident
Throttled async loop
await Parallel.ForEachAsync(items, new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct }, async (item, ct) => await ProcessAsync(item, ct));.NET 6 default DOP = ProcessorCountlegacy: SemaphoreSlim(8) + WaitAsync/Release in try/finally around each task
Indexed async loop
await Parallel.ForAsync(0, n, ct, async (i, ct) => …);.NET 8
CPU-bound parallel
Parallel.For / Parallel.ForEach with sync lambdas, or PLINQ .AsParallel() — never Parallel.ForEach(items, async x => …) (async void, returns immediately)
First wins
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct); var winner = await Task.WhenAny(a, b); cts.Cancel(); then observe the losers: await Task.WhenAll(a, b).ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);
Results as they land
await foreach (var t in Task.WhenEach(tasks)) Render(await t);.NET 9legacy: repeated WhenAny + Remove, or the "sort by completion" TCS-array trick
Producer / consumer
bounded Channel<T> + N consumer Task.Run loops over ReadAllAsync (unit 4)legacy: BlockingCollection<T> (blocks pool threads), TPL Dataflow ActionBlock<T> (fine, heavier)
Periodic work
using var timer = new PeriodicTimer(TimeSpan.FromSeconds(10)); while (await timer.WaitForNextTickAsync(ct)) await TickAsync(ct);.NET 6legacy: while (true) { await Task.Delay(…); } (drifts) · System.Threading.Timer (overlaps)
Hosted loop
sealed class Worker : BackgroundService { protected override async Task ExecuteAsync(CancellationToken st) { await Task.Yield(); while (!st.IsCancellationRequested) { … } } } — an unhandled exception stops the host.NET 6 (HostOptions.BackgroundServiceExceptionBehavior)
Async mutual exclusion
readonly SemaphoreSlim _gate = new(1, 1); await _gate.WaitAsync(ct); try { … } finally { _gate.Release(); } — the async replacement for lock; Lock/Monitor only for sections with no await
Async lazy init
readonly Lazy<Task<Config>> _cfg = new(() => LoadAsync(), LazyThreadSafetyMode.ExecutionAndPublication); → await _cfg.Value — caches failures forever; reset on fault, or use AsyncLazy<T> (Microsoft.VisualStudio.Threading)
Fire-and-forget
_ = Task.Run(async () => { try { await WorkAsync(ct); } catch (Exception ex) { _log.LogError(ex, "bg"); } }, ct); — better: enqueue to a channel drained by a hosted service; unobserved faults are silent, async void faults kill the process
Timeout
await op.WaitAsync(TimeSpan.FromSeconds(3), ct);.NET 6legacy: if (await Task.WhenAny(op, Task.Delay(3000)) != op) throw new TimeoutException(); — the Delay timer lives on unless cancelled
Retry with backoff
for (var i = 0; ; i++) try { return await CallAsync(ct); } catch (HttpRequestException) when (i < 3) { await Task.Delay(TimeSpan.FromMilliseconds(200 * (1 << i)), ct); } — production: Microsoft.Extensions.Resilience / Polly v8 ResiliencePipeline
Async event handler
btn.Click += async (s, e) => { try { await SaveAsync(); } catch (Exception ex) { Show(ex); } }; — the one legitimate async void; catch everything inside it
Async construction
public static async Task<Svc> CreateAsync(…) { var s = new Svc(…); await s.InitAsync(); return s; } — constructors cannot await; with DI register a factory, or initialize in IHostedService.StartAsync
Interfaces
declare Task<T> GetAsync(…, CancellationToken ct); use ValueTask<T> when most implementations complete synchronously (caches); default interface members may be async

8Runtime async — .NET 11 preview docs ↗

What it is
the runtime, not the compiler, suspends and resumes async methods: no IAsyncStateMachine struct, no MoveNext; the compiler emits [MethodImpl(MethodImplOptions.Async)] IL that calls AsyncHelpers.Await(…) (System.Runtime.CompilerServices)
Semantics
unchanged by design — await, ConfigureAwait, SynchronizationContext, ExecutionContext and exceptions behave as before; only codegen, allocations and stack shape differ
Enable (net11.0)
<Features>runtime-async=on</Features> in the project — <EnablePreviewFeatures> is no longer required for net11.0P7 · 2026-08
Disable per project
<UseRuntimeAsync>false</UseRuntimeAsync> — the DOTNET_RuntimeAsync / UNSUPPORTED_RuntimeAsync env vars are goneremoved .NET 11 P1
.NET 10 (stable) status
experimental only: DOTNET_RuntimeAsync=1 at run time + <EnablePreviewFeatures>true</EnablePreviewFeatures> + <Features>runtime-async=on</Features>; the .NET 10 BCL is not compiled with it
BCL built with it
the .NET 11 runtime libraries ship compiled runtime-async=on — no compiler state machines left in the BCLP7; an app with only library dependencies can run entirely on the new model
Live stack traces
three nested awaits: 13 frames of AsyncMethodBuilderCore.Start noise → 5 real frames; exception traces already looked clean, this fixes profilers, new StackTrace() and the debugger call-stack window
Debugging
breakpoints bind inside runtime-async methods; stepping crosses await without landing in generated code
Performance work
tiered compilation of async bodies · JIT folds Task.FromResult, Task.CompletedTask, ValueTask.FromResult · tail-merged suspension points · cached continuations · allocation-free await Task.Yield() · a dedicated async version of sync Task-returning methods instead of a thunkP6–P7
Deployment
works with NativeAOT and ReadyToRun; crossgen2 inlines await-less async calls; covariant Task→Task<T> overrides get a bridging thunk
Profilers
the async profiler instruments runtime-async and state-machine methods with one event model — tooling should not care which model an assembly used
What to tell a team
preview until GA (Nov 2026, STS); keep code portable — nothing may depend on <>c__DisplayClass / state-machine type names in logs or reflection; benchmark before flipping runtime-async=on on hot services and report regressions upstream

10Gotchas & pitfalls — one line each docs ↗

  • async void — exceptions go to the SynchronizationContext or crash the process; callers cannot await or observe. Event handlers only.
  • Sync-over-async — .Result/.Wait()/GetResult() on pool threads eats threads (starvation); on UI or legacy ASP.NET threads it deadlocks.
  • AggregateException — .Result/.Wait() wrap; await and GetAwaiter().GetResult() unwrap the first exception.
  • WhenAll hides faults — awaiting throws one exception; loop tasks.Where(t => t.IsFaulted) or read whenAllTask.Exception to log them all.
  • Unobserved faults — a discarded faulted task only fires TaskScheduler.UnobservedTaskException at finalization and never crashes (since .NET 4.5); log there.
  • ValueTask twice — awaiting or reading a ValueTask after it was consumed returns garbage or throws once its source is recycled.
  • Token not forwarded — one missing ct makes cancellation "work" only up to that call; make CA2016 an error.
  • Lost cancellation in iterators — WithCancellation(ct) without [EnumeratorCancellation] silently ignores the token.
  • lock + await — CS1996; and Monitor is thread-affine while continuations may resume elsewhere. Use SemaphoreSlim.
  • using returns an un-awaited task — using var conn = …; return conn.QueryAsync(); disposes before the query runs; await inside the scope (CA2025 catches the Task.Run variant).
  • Parallel.ForEach with an async lambda — it is Action<T> → async void; the loop returns before the work finishes. Use Parallel.ForEachAsync.
  • StartNew with an async delegate — returns Task<Task>; awaiting the outer task waits only until the first await. .Unwrap() or Task.Run.
  • Task.Run in ASP.NET Core — there is no context to leave; wrapping I/O in Task.Run burns a second pool thread per request for nothing.
  • TCS inline continuations — SetResult runs awaiters synchronously on the caller's thread unless RunContinuationsAsynchronously; stack dives and lock-held callbacks follow.
  • ConfigureAwait(false) too late — it must be on every await in the callee chain, is per-await not per-method, and does nothing for the synchronous prefix.
  • Dispose vs DisposeAsync — using on an IAsyncDisposable-only type does not compile; on a type with both, plain using silently picks the sync one.
  • Timer overlap — System.Threading.Timer fires again while the previous callback still runs; PeriodicTimer waits.
  • Task.Delay + WhenAny timeout — the timer keeps running after the race; cancel it, or use WaitAsync.
  • WaitAsync does not cancel — the wrapped operation continues after the timeout; give it the token as well.
  • HttpClient timeout is a TaskCanceledException — with an inner TimeoutException (.NET 5+); not every TCE is user cancellation.
  • BackgroundService crash stops the host — since .NET 6; wrap ExecuteAsync loops in try/catch and log; a long synchronous prefix delays the other services' start.
  • AsyncLocal surprises — set inside an awaited child, invisible to the parent; flows into fire-and-forget work unless SuppressFlow.
  • Exception before the first await — in an async method it is still a faulted Task, not a synchronous throw; validate arguments in a non-async wrapper for eager throws.
  • IAsyncEnumerable enumerated twice — runs the query twice; ToListAsync once or fan out through a channel.
