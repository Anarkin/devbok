Task, ValueTask, cancellation, async streams, ConfigureAwait and thread-pool behaviour on one card: the daily syntax and APIs, the modern form next to the legacy form still found in real code, config knobs and diagnostic commands, and a dated timeline. 01Syntax essentials

docs: asynchronous programming
async method
async Task<Order> LoadAsync(int id, CancellationToken ct = default) { var row = await db.FindAsync(id, ct); return Map(row); }token last, optional, forwarded to every call; suffix Async
return types
Task · Task<T> · ValueTask · ValueTask<T> · IAsyncEnumerable<T> · voidany type with [AsyncMethodBuilder] works (C# 7); void only for event handlers
what is awaitable
x.GetAwaiter() → { bool IsCompleted; void OnCompleted(Action); T GetResult(); }Task, ValueTask, Task.Yield(), ConfiguredTaskAwaitable, custom awaiters, extension GetAwaiter
elide async/await
Task<int> F() => Compute(); // ok: nothing wraps the call async Task<int> G() { using var s = Open(); return await Compute(s); }keep await inside try/using/loops, else the resource is disposed before the work runs
async lambda
Func<Task> work = async () => await SaveAsync(); button.Click += async (s, e) => { try { await RunAsync(); } catch (Exception ex) { Log(ex); } };an Action overload turns it into async void: check overload resolution (Task.Run, Parallel.ForEach)
async local function
async Task<int> CoreAsync() { … } // inside a method; can be staticidiom: validate args synchronously, then return CoreAsync()
async Main C# 7.1
static async Task<int> Main(string[] args)top-level statements: just use await
await in catch/finally C# 6
try { … } catch (HttpRequestException) { await RetryAsync(); } finally { await CleanupAsync(); }
async iterator C# 8
async IAsyncEnumerable<T> ReadAsync([EnumeratorCancellation] CancellationToken ct = default) { while (await reader.ReadAsync(ct)) yield return Map(reader); }yield inside try/finally ok, inside try/catch not
await foreach C# 8
await foreach (var x in src.WithCancellation(ct).ConfigureAwait(false)) { … }
await using C# 8
await using var conn = new SqlConnection(cs); // IAsyncDisposable.DisposeAsync() : ValueTask await using (stream.ConfigureAwait(false)) { … }implement both IDisposable and IAsyncDisposable on your own types
async void
async void OnClick(object s, EventArgs e) { try { await X(); } catch (Exception ex) { … } }exceptions escape to the SynchronizationContext or crash the process; not awaitable, not testable: handlers only
not allowed
ref/out/in parameters · await inside lock (CS1996) · yield in try/catch · await in unsafe/fixed bodyC# 13 allows ref locals and ref struct (Span) in async methods as long as they are not live across an await
pooled builder .NET 6 · C# 10
[AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))] async ValueTask<int> HotAsync() { … }per method or assembly-wide via [module: …]; pools the state-machine box
state machine facts
struct in Release, class in Debug · boxed once, on the first real suspension · synchronous completion allocates nothingruntime async (unit 08) removes the compiler state machine altogether

02Task API

docs: System.Threading.Tasks.Task
offload CPU work
await Task.Run(() => Crunch(data), ct); await Task.Run(async () => await IoAsync()); // Func<Task> overload unwrapsthe token only prevents the start; running work must observe it itself
completed tasks
Task.CompletedTask · Task.FromResult(v) · Task.FromException<T>(ex) · Task.FromCanceled<T>(ct)cache Task.FromResult for hot constants (true/false/0 are cached by the runtime)
all
Order[] orders = await Task.WhenAll(tasks); // params ReadOnlySpan<Task> since .NET 9 try { await Task.WhenAll(a, b); } catch { var all = new[] { a, b }.Where(t => t.IsFaulted).Select(t => t.Exception!); }await rethrows only the first exception; the rest sit in each task's Exception
first
var done = await Task.WhenAny(a, b); var result = await done;await the winner to unwrap its result/exception; losers keep running
as they complete .NET 9
await foreach (var t in Task.WhenEach(tasks)) Handle(await t);replaces the WhenAny-remove-loop (O(n²)) idiom
timeout / cancel a foreign task .NET 6
var v = await task.WaitAsync(TimeSpan.FromSeconds(5), ct); // TimeoutException / OperationCanceledExceptionabandons, does not stop the underlying work; TimeProvider overload .NET 8
delay / yield
await Task.Delay(TimeSpan.FromMilliseconds(200), ct); await Task.Delay(Timeout.Infinite, ct); // wait for cancellation await Task.Yield(); // requeue on the current context/schedulerTask.Delay(0) completes synchronously; Yield always suspends
TaskCompletionSource
var tcs = new TaskCompletionSource<Reply>(TaskCreationOptions.RunContinuationsAsynchronously); tcs.TrySetResult(r); tcs.TrySetException(ex); tcs.TrySetCanceled(ct); using var reg = ct.Register(() => tcs.TrySetCanceled(ct));non-generic TaskCompletionSource since .NET 5; without RunContinuationsAsynchronously continuations run inline on the completer's thread
status
t.IsCompleted · IsCompletedSuccessfully · IsFaulted · IsCanceled · Status · Exception (AggregateException)
blocking (avoid)
t.GetAwaiter().GetResult() // rethrows the original exception t.Result · t.Wait() // wrap in AggregateExceptionboth block a thread; deadlock under a SynchronizationContext, starvation on the pool
exceptions
await t; // throws the first inner exception t.Exception.Flatten().InnerExceptions TaskScheduler.UnobservedTaskException += (s, e) => { Log(e.Exception); e.SetObserved(); };unobserved faults no longer crash the process (since .NET 4.5); they surface at GC time
throttle
using var gate = new SemaphoreSlim(8); await gate.WaitAsync(ct); try { await WorkAsync(); } finally { gate.Release(); }
bounded fan-out .NET 6
await Parallel.ForEachAsync(items, new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct }, async (item, ct) => await ProcessAsync(item, ct));accepts IEnumerable or IAsyncEnumerable; default DOP = ProcessorCount
legacy: ContinueWith
t.ContinueWith(x => Use(x.Result), ct, TaskContinuationOptions.OnlyOnRanToCompletion, TaskScheduler.Default);always pass a scheduler (CA2008); prefer await
legacy: StartNew
Task.Factory.StartNew(() => Loop(), ct, TaskCreationOptions.LongRunning, TaskScheduler.Default); Task.Factory.StartNew(async () => …).Unwrap(); // returns Task<Task> otherwiseLongRunning = dedicated thread; useless with an async delegate (thread is released at the first await)
legacy: APM / EAP
Task<int> t = Task.Factory.FromAsync(s.BeginRead, s.EndRead, buf, 0, n, null); // Begin/End pairs client.DownloadCompleted += (_, e) => tcs.TrySetResult(e.Result); client.DownloadAsync(uri); // event pairs → TCS

03ValueTask

docs: ValueTask<TResult>
when
hot path that usually completes synchronously (cache hit, buffered read) and you measured the allocationdefault stays Task: it is cached, composable, safe to misuse
create
return ValueTask.FromResult(42); ValueTask.CompletedTask; ValueTask.FromException<T>(ex); ValueTask.FromCanceled<T>(ct) new ValueTask<T>(task) // wrap a Task new ValueTask<T>(source, token) // IValueTaskSource<T>
consume rules
await vt; // exactly once, no second await, no .Result unless IsCompleted Task<T> t = vt.AsTask(); // to store, WhenAll, or await twice vt.Preserve() // makes repeated awaits legalCA2012 flags misuse; violations read garbage or throw InvalidOperationException with pooled sources

non-generic .NET Core 2.1

reusable source .NET Core 3.0
sealed class Op : IValueTaskSource<int> { ManualResetValueTaskSourceCore<int> core; // Reset(), SetResult(), GetStatus(), OnCompleted(), GetResult() public ValueTask<int> Task => new(this, core.Version); … }zero-alloc awaitable objects (sockets, pipelines, channels); the version token catches double-await
pooled async methods .NET 6
[AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))] async ValueTask<int> …only the state-machine box is pooled, and only when the method actually suspends

IAsyncDisposable.DisposeAsync · IAsyncEnumerator.MoveNextAsync · Stream.ReadAsync(Memory<byte>) · ChannelReader.ReadAsync · PipeReader.ReadAsync

04Cancellation

docs: cancellation in managed threads
source & token
using var cts = new CancellationTokenSource(); CancellationToken ct = cts.Token;dispose sources with timers or registrations; a token is a struct wrapper, pass by value
timeout
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30)); cts.CancelAfter(TimeSpan.FromSeconds(5)); // re-arm any time before it fires.NET 8: new CancellationTokenSource(delay, timeProvider) for testable timeouts
combine
using var linked = CancellationTokenSource.CreateLinkedTokenSource(ct, appLifetime.ApplicationStopping); linked.CancelAfter(timeout); var token = linked.Token;dispose the linked source or it stays registered on both parents
cancel
cts.Cancel(); // runs callbacks synchronously on this thread; throws AggregateException if one throws await cts.CancelAsync(); // .NET 8: same, but awaits callbacks off-thread instead of blocking cts.Cancel(throwOnFirstException: true)
reuse .NET 6
if (!cts.TryReset()) cts = new(); // only succeeds if never cancelled; used by pooled per-request sources
observe
ct.ThrowIfCancellationRequested(); // in loops / between chunks if (ct.IsCancellationRequested) return partial; // graceful exit ct.CanBeCanceled · CancellationToken.None == default
register
using CancellationTokenRegistration reg = ct.Register(static s => ((Connection)s!).Abort(), this); ct.UnsafeRegister(cb, state); // .NET 6: no ExecutionContext capture ct.Register((state, token) => …, state); // .NET 6: callback receives the tokendispose the registration to unhook; reg.DisposeAsync() waits for a running callback
throw & catch
throw new OperationCanceledException(ct); catch (OperationCanceledException) when (ct.IsCancellationRequested) { /* caller cancelled */ } catch (OperationCanceledException) { /* timeout token */ }a cancelled Task throws TaskCanceledException : OperationCanceledException; catch the base
forward
Task<T> GetAsync(int id, CancellationToken ct = default) => http.GetFromJsonAsync<T>(url, ct);CA2016 warns when a token is available but not passed
uncancellable callee .NET 6
await legacy.DoAsync().WaitAsync(ct); // stops waiting, not the work
wait for cancel
await Task.Delay(Timeout.Infinite, ct); // async ct.WaitHandle.WaitOne(); // blocking, allocates the handle
hosting tokens
HttpContext.RequestAborted · IHostApplicationLifetime.ApplicationStopping/ApplicationStopped · BackgroundService.ExecuteAsync(stoppingToken)ASP.NET Core also binds a CancellationToken parameter on endpoints to RequestAborted
async streams
await foreach (var x in Read(ct1).WithCancellation(ct2)) // [EnumeratorCancellation] links both
TCS
tcs.TrySetCanceled(ct); // keeps the token in the TaskCanceledException
pitfalls
catch (Exception) swallows OperationCanceledException → rethrow or filter · Task.Run(f, ct) only skips the start · Task.Delay cancel = TaskCanceledException · never dispose a CTS from its own callback

06ConfigureAwait & contexts

docs: ConfigureAwait FAQ · API
what await captures
SynchronizationContext.Current ?? (TaskScheduler.Current != Default ? TaskScheduler.Current : null)the continuation is posted back to it; with nothing captured it runs on the completing thread (usually a pool thread)
library code
await stream.ReadAsync(buf, ct).ConfigureAwait(false); // every await, every method (CA2007)protects callers that block, avoids a hop back to a UI thread; one missed await in the chain re-introduces the deadlock
app code
ASP.NET Core · console · workers · gRPC: no SynchronizationContext → ConfigureAwait(false) is a no-op WPF · WinForms · MAUI · Blazor Server: default (true) keeps you on the UI/renderer contexttest frameworks may install a context: never block in tests either
options .NET 8
await t.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing | ConfigureAwaitOptions.ForceYielding); // None · ContinueOnCapturedContext · SuppressThrowing (Task only; swallows fault/cancel) · ForceYielding (never continue inline)SuppressThrowing on Task<T> throws ArgumentOutOfRangeException; inspect t.Exception after
async streams / disposables
await foreach (var x in src.ConfigureAwait(false)) … await using (conn.ConfigureAwait(false)) …
the deadlock
// UI thread or legacy ASP.NET: LoadAsync().Result ⇄ LoadAsync awaits with context → continuation needs the blocked threadfix: async all the way; second best ConfigureAwait(false) inside; last resort Task.Run(() => LoadAsync()).GetAwaiter().GetResult()
ExecutionContext
static readonly AsyncLocal<string?> Tenant = new(); // flows into awaited callees and Task.Run, never back up using (ExecutionContext.SuppressFlow()) { _ = Task.Run(...); } // detachConfigureAwait(false) does NOT stop ExecutionContext flow; Activity.Current, IHttpContextAccessor ride on it. .NET 11 skips capture/restore when nothing is set
ThreadLocal vs AsyncLocal
ThreadLocal<T> / [ThreadStatic]: per OS thread, wrong after an await · AsyncLocal<T>: per logical flow
schedulers
TaskScheduler.Default (pool) · TaskScheduler.FromCurrentSynchronizationContext() · new ConcurrentExclusiveSchedulerPair().ExclusiveSchedulerawait only honours a scheduler when the awaiting code itself runs under it (via StartNew/ContinueWith)
back to the UI
await Dispatcher.InvokeAsync(() => label.Text = s); // WPF await MainThread.InvokeOnMainThreadAsync(...); // MAUI await InvokeAsync(StateHasChanged); // Blazor component
Progress<T>
IProgress<int> p = new Progress<int>(v => bar.Value = v); // captures the context at construction, posts callbacks to it

07Thread pool behaviour

docs: managed thread pool · starvation tutorial
who runs what
await I/O → no thread while pending → completion via I/O pool / epoll thread → continuation queued to a worker (or the captured context)Kestrel requests, hosted services, timers, Task.Run: all worker-pool work items
defaults
min workers = Environment.ProcessorCount · max workers = 32,767 · min I/O = ProcessorCount · max I/O = 1,000ProcessorCount honours cgroup CPU limits in containers; override with DOTNET_PROCESSOR_COUNT
injection
≤ min: threads start immediately · > min: hill-climbing adds/removes ~1 thread per 0.5–1 s by measured throughput · blocked-on-Task work (.NET 6+): fast injection without the delayso starvation shows as thread count creeping 1–2/s, not as a hard error
queues
global FIFO queue + per-worker LIFO local queues with work stealing ThreadPool.UnsafeQueueUserWorkItem(item, preferLocal: true) // IThreadPoolWorkItem, no ExecutionContexta Task.Run issued from a pool thread lands in that thread's local queue
starvation signature
latency ↑, CPU well below 100 %, dotnet.thread_pool.thread.count climbing then flat > 3 × cores, dotnet.thread_pool.queue.length > 0causes: .Result/.Wait()/GetAwaiter().GetResult(), Thread.Sleep, blocking locks, sync I/O inside pool work
inspect .NET Core 3.0
ThreadPool.ThreadCount · PendingWorkItemCount · CompletedWorkItemCount · GetAvailableThreads(out w, out io) · GetMinThreads(out w, out io)
tune
ThreadPool.SetMinThreads(workers: 64, completionPortThreads: 64); // band-aid for bursty blocking; prefer config (unit 09)ignored under the Windows thread pool; more threads = more memory and context switches, never a fix for sync-over-async
dedicated thread
new Thread(Loop) { IsBackground = true, Name = "outbox-pump" }.Start(); Task.Factory.StartNew(Loop, TaskCreationOptions.LongRunning); // same, sync delegate onlyfor long-lived loops that block (consumers of blocking APIs, message pumps)
Task.Run in web apps
don't: the request is already on the pool; it only adds a hop and hides the CPU cost. Do it in UI apps to keep the UI thread free
timers
using var timer = new PeriodicTimer(TimeSpan.FromSeconds(10)); while (await timer.WaitForNextTickAsync(ct)) await TickAsync(ct); // no overlapping ticks (.NET 6) new System.Threading.Timer(cb, null, 0, 10_000); // callbacks on the pool, re-entrant if slow
implementations
PortableThreadPool (managed, default on every OS since .NET 6) · Windows thread pool opt-in (.NET 8; default for NativeAOT on Windows)
events & metrics
WaitHandleWait runtime event (.NET 9) on every blocking wait · System.Runtime meter: dotnet.thread_pool.* (OpenTelemetry-ready since .NET 9)
legacy
ThreadPool.QueueUserWorkItem(_ => Work()); // → Task.Run BackgroundWorker · Thread + ManualResetEvent // → async/await + CancellationToken

08Runtime Async .NET 11 preview

docs: what's new in .NET 11 runtime
what it is
the JIT/runtime suspends and resumes async methods; no compiler-generated state machine; same async/await source, same Task/ValueTask typesan ABI and codegen change, not a semantics change: awaits, contexts and exceptions behave the same
.NET 10 (experiment)
DOTNET_RuntimeAsync=1 + <EnablePreviewFeatures>true</EnablePreviewFeatures> + <Features>runtime-async=on</Features>BCL not compiled with it, so gains were limited to your own code
.NET 11 (preview 7)
<Features>runtime-async=on</Features> // opt in per project; no EnablePreviewFeatures on net11.0 <UseRuntimeAsync>false</UseRuntimeAsync> // opt the runtime side outruntime support on by default and the BCL itself ships compiled runtime-async=on; the DOTNET_RuntimeAsync / UNSUPPORTED_RuntimeAsync env vars were removed
wins
live stack traces show the real call chain (docs sample: 13 frames → 5) · fewer allocations: continuations reused, unchanged locals not saved, ExecutionContext capture skipped when empty · cheaper await Task.Yield() · async bodies go through tiered compilation · JIT folds Task.FromResult / Task.CompletedTask / ValueTask.FromResult
also covered
NativeAOT + ReadyToRun (crossgen2 inlining of await-less async calls) · covariant Task→Task<T> overrides bridged by a thunk · debugger breakpoints/stepping across await · async profiler sees one event model for both paths (P7)
not changed
custom [AsyncMethodBuilder] methods and pooled ValueTask methods stay on the compiler path · exception stack traces already looked the same (ExceptionDispatchInfo cleanup)
interview line
"it changes who owns the state machine, not what await means; the payoff is allocations, stack traces and debuggability, and it lands as preview in .NET 11 GA (2026-11-10)"

10Idioms & gotchas

docs: async scenarios · Fowler: async guidance

Idioms — modern | legacy still seen

offload CPU work
await Task.Run(() => Crunch(data), ct);
new Thread(…).Start(); ThreadPool.QueueUserWorkItem; BackgroundWorker
compose
var (a, b) = (await ta, await tb); // after starting both await Task.WhenAll(ta, tb);
Task.WaitAll(ta, tb); ta.ContinueWith(_ => tb.ContinueWith(…))
timeout
await t.WaitAsync(TimeSpan.FromSeconds(5), ct);
if (await Task.WhenAny(t, Task.Delay(5000)) != t) throw new TimeoutException();
cancel + timeout
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct); cts.CancelAfter(timeout);
manual Timer + volatile bool flag
periodic loop
using var timer = new PeriodicTimer(period); while (await timer.WaitForNextTickAsync(ct)) await TickAsync(ct);
System.Timers.Timer.Elapsed += async (…) => … // async void, overlaps, swallowed exceptions while (true) { await Task.Delay(period); … } // drifts
wrap callback API
var tcs = new TaskCompletionSource<Reply>(TaskCreationOptions.RunContinuationsAsynchronously); client.Replied += (_, e) => tcs.TrySetResult(e.Reply); return await tcs.Task.WaitAsync(ct);
Task.Factory.FromAsync(Begin, End, state) // still right for APM pairs ManualResetEvent + WaitOne
async mutual exclusion
await sem.WaitAsync(ct); try { … } finally { sem.Release(); } // SemaphoreSlim(1, 1)
lock (o) { x.Wait(); } // CS1996 if you await; deadlock/starvation if you block
async lazy init
readonly Lazy<Task<Config>> cfg = new(() => LoadAsync(), LazyThreadSafetyMode.ExecutionAndPublication); await cfg.Value; // or AsyncLazy<T> from Microsoft.VisualStudio.Threading
double-checked lock + .Result; static ctor calling Wait()
async construction
public static async Task<Client> CreateAsync(...) { var c = new Client(); await c.InitAsync(); return c; }
ctor calling InitAsync().Wait() // deadlock under a context
async cleanup
public async ValueTask DisposeAsync() { await FlushAsync(); } + await using
Dispose() { FlushAsync().Wait(); }
background work in ASP.NET Core
Channel<Job> singleton + BackgroundService consumer; enqueue from the request
_ = Task.Run(() => DoAsync(scopedDb)); // scope disposed under it, exceptions lost HostingEnvironment.QueueBackgroundWorkItem // classic ASP.NET
forced sync-over-async
Task.Run(() => DoAsync()).GetAwaiter().GetResult(); // avoids the context deadlock, still burns a thread
DoAsync().Result; // AggregateException + deadlock

Gotchas — one line each

  • async void anywhere but an event handler: the exception has no Task to land in and takes the process down.
  • Missing await (CS4014): the call runs, its exception vanishes, and using scopes close underneath it.
  • return SomethingAsync(); inside try/using: the catch never sees the fault and the resource is disposed early. Use return await.
  • .Result/.Wait() under a SynchronizationContext (UI, classic ASP.NET, some test runners) deadlocks; on ASP.NET Core it starves the pool instead.
  • Parallel.ForEach(items, async x => …) compiles to async void per item and returns immediately: use Parallel.ForEachAsync.
  • Task.Factory.StartNew(async () => …) returns Task<Task>; awaiting it waits only for the outer task. Task.Run unwraps.
  • TaskCompletionSource without RunContinuationsAsynchronously runs awaiting code inline on whoever calls SetResult, often while holding a lock.
  • Unbounded Task.WhenAll(items.Select(DoAsync)) on 10k items opens 10k connections: throttle with Parallel.ForEachAsync or a semaphore.
  • Select(async …) starts every task eagerly; re-enumerating an IEnumerable<Task> starts them again. Materialise with ToList().
  • catch (Exception) swallows OperationCanceledException; retry policies then retry cancelled work. Filter with when (ex is not OperationCanceledException).
  • Timeouts via WaitAsync/WhenAny abandon the work; only a token the callee honours stops it.
  • A CTS registration callback that throws makes Cancel() throw AggregateException at the caller; keep callbacks trivial.
  • Cancelling Task.Delay throws TaskCanceledException: expected, catch OperationCanceledException, do not log it as an error.
  • ValueTask awaited twice, stored, or .Result-ed before completion: undefined result or InvalidOperationException. AsTask() when in doubt.
  • ConfigureAwait(false) only on the first await does nothing for the later ones; it must be on every await in the library call chain.
  • ConfigureAwait(false) does not stop AsyncLocal/ExecutionContext flow; ExecutionContext.SuppressFlow() does.
  • An AsyncLocal set inside an awaited callee is not visible to the caller afterwards; set it before the call, at the top of the flow.
  • Async methods on a struct operate on a copy of this; mutations are lost. Make it a class.
  • HttpClient.GetAsync buffers the whole body unless HttpCompletionOption.ResponseHeadersRead, then await using the stream.
  • IAsyncEnumerable returned from an ASP.NET Core endpoint has already sent 200 by the time a mid-stream exception fires.
  • Passing a disposable into an un-awaited task and disposing it right after (CA2025): the task reads a disposed object.
  • Task.Run(…, ct): the token only prevents the start; Task.Delay(0) completes synchronously; Task.Yield() always suspends.
  • ThreadPool.SetMinThreads hides starvation until the burst exceeds the new floor; it is a mitigation while you remove the blocking call.
  • Blocking inside a lock (or C# 13 Lock) on a pool thread while other pool work waits for that lock is the second most common starvation cause after sync-over-async.
