01Core mechanics of async/await

This is the compulsory sub-area: nearly every loop opens here, and a shaky answer ends the interview regardless of what you know about distributed systems. What is tested is whether you understand that await is a suspension, not a thread, and that the compiler rewrites your method into a state machine whose continuation gets scheduled somewhere. At mid level you should describe that rewrite in words; at senior you should describe context capture and what it costs; at principal you should be able to explain to a team why "make it async" is a scalability decision and never a latency one.

screenerWhat does await actually do — does it start a new thread?

Answer

No thread is created. await asks the awaited thing whether it is already complete; if it is, execution continues synchronously on the same thread. If it is not, the method returns to its caller, and the compiler-generated state machine registers a continuation with the awaited task. When the underlying operation finishes — an I/O completion callback, a timer, another task completing — that continuation is scheduled, normally onto the thread pool, and the method resumes from the line after the await with its locals restored. So await costs a suspension and possibly a context switch, not a thread.

Example

async Task<int> GetLengthAsync(HttpClient http)
{
    // runs synchronously on the calling thread up to here
    var body = await http.GetStringAsync("https://example.com");
    // may resume on a DIFFERENT thread-pool thread
    return body.Length;
}

Follow-ups

  • Which thread resumes the method? — Whatever the captured SynchronizationContext or TaskScheduler says; in ASP.NET Core and console apps there is none, so a thread-pool thread.
  • What if the task is already complete? — IsCompleted is true on the awaiter, no suspension happens, and the code runs straight through on the same thread: the synchronous fast path.
  • So what is waiting during a 200 ms HTTP call? — Nothing. No thread is blocked; the OS holds a pending I/O request and signals a completion port when the bytes arrive.

Common wrong answer — this rejects candidates

"await runs the method on a background thread so the UI or request thread is free." That is what Task.Run does, not await. Saying it reveals you think async is threading, and every later question about starvation and deadlocks will go badly.

screenerAsynchrony vs parallelism vs concurrency — which one does async/await give you?

Answer

Parallelism is doing several things at the same instant on several cores — Parallel.For, PLINQ, threads doing CPU work. Asynchrony is not occupying a thread while you wait for something else to finish — async/await over I/O. Concurrency is the general property of having several operations in flight. async/await gives you asynchrony and, through composition like Task.WhenAll, concurrency; it gives you parallelism only if the tasks you compose actually do CPU work on separate threads. The practical consequence: async improves throughput and scalability under I/O-bound load, and does nothing for a CPU-bound hot loop except add overhead.

Example

// concurrency over I/O — no extra threads needed
var results = await Task.WhenAll(ids.Select(id => repo.LoadAsync(id, ct)));

// parallelism over CPU — threads are the point
Parallel.ForEach(images, img => img.Resize(1024));

Follow-ups

  • Is Task.Run parallelism or asynchrony? — Parallelism dressed as a Task: it queues real work onto a pool thread.
  • Which one helps a web API serve more requests per second? — Asynchrony; the cores are already busy with other requests, what you are freeing is threads.
  • When is async actively harmful? — Tight CPU loops and very hot short paths, where state-machine allocation and scheduling exceed the work itself.

Common wrong answer

"Async makes the code run faster / in parallel." A single async call is marginally slower than its sync equivalent. It buys thread-count scalability, not wall-clock speed — unless you are deliberately overlapping independent operations, which is a separate decision.

midWalk me through what the compiler generates for an async Task<T> method.

Answer

Roslyn rewrites the body into a state machine type implementing IAsyncStateMachine — a struct in release builds, a class in debug so the debugger can inspect it. The original method becomes a stub that creates an AsyncTaskMethodBuilder<T>, stores parameters and this as fields, and calls builder.Start(ref stateMachine), which runs MoveNext synchronously until the first incomplete await. At each await the generated code fetches an awaiter, checks IsCompleted, and on false hoists the state machine to the heap (boxing the struct), records the resume state in an int field, and calls AwaitUnsafeOnCompleted, which registers MoveNext as the continuation. Locals that live across an await become fields; the returned Task<T> comes from the builder and is completed by SetResult or SetException.

Example

// what you write
async Task<int> F() { var s = await GetAsync(); return s.Length; }

// what it becomes, in outline
// struct FSM : IAsyncStateMachine {
//   int _state; AsyncTaskMethodBuilder<int> _builder; TaskAwaiter<string> _awaiter;
//   void MoveNext() {
//     switch (_state) {
//       case -1:
//         _awaiter = GetAsync().GetAwaiter();
//         if (!_awaiter.IsCompleted) {
//           _state = 0;
//           _builder.AwaitUnsafeOnCompleted(ref _awaiter, ref this);  // boxes, returns
//           return;
//         }
//         goto case 0;
//       case 0:
//         var s = _awaiter.GetResult();
//         _builder.SetResult(s.Length);
//         return;
//     }
//   }
// }

Follow-ups

  • Why a struct? — So a method that completes synchronously never heap-allocates the state machine; it is boxed only on the first real suspension.
  • What allocates on the slow path? — The boxed state machine, the Task (unless a cached one is returned), the continuation delegate and the ExecutionContext copy.
  • Where do exceptions go? — The whole MoveNext body is wrapped in try/catch; a caught exception becomes SetException, which faults the returned Task instead of throwing on the current stack.

Common wrong answer

"The compiler wraps the body in Task.Run." No — the state machine runs on the calling thread until the first suspension and never queues work to the pool by itself.

midWhen does the body of an async method start running — at the call, or at the first await of the returned task?

Answer

At the call. Calling an async method invokes it immediately and synchronously on the current thread; it runs until it hits an await on something not yet complete, and only then returns a task. That is why argument validation inside an async method throws late — the exception is captured into the returned task rather than thrown at the call site — and why "start it now, await it later" works for overlapping two independent calls. It also means an async method that never awaits anything incomplete runs entirely synchronously and hands back an already-completed task.

Example

var a = FetchAsync("a");                  // starts NOW
var b = FetchAsync("b");                  // starts NOW, overlapping a
var results = await Task.WhenAll(a, b);   // ~max(a,b), not a+b

Follow-ups

  • How do you get eager argument validation then? — Split it: a non-async outer method validates and returns the inner async local function's task.
  • Does that apply to async iterators too? — No. An async IAsyncEnumerable<T> method is lazy: nothing runs until the first MoveNextAsync.
  • What is the risk of "start now, await later"? — If the first task faults before you await it and you return early, you get an unobserved exception; use try/finally or always await both.

Common wrong answer

"Nothing happens until you await the Task." That is promise/lazy-sequence thinking. Tasks returned by async methods are hot: already started.

midWhat happens when you await a task that is already completed, and what does it cost?

Answer

The awaiter reports IsCompleted true, so there is no suspension, no continuation, no context capture and no thread hop — GetResult() runs inline and execution continues on the same thread. The cost is a few nanoseconds plus whatever the method already paid: if it completed entirely synchronously the struct state machine never boxed, though a Task-returning method still allocates a Task unless it returns a cached one such as Task.CompletedTask. This fast path is exactly why ValueTask exists — for methods that usually hit a cache and complete synchronously.

Example

async ValueTask<User> GetUserAsync(int id, CancellationToken ct)
{
    if (_cache.TryGetValue(id, out var u)) return u;   // no await: fully synchronous, 0 B
    return await _db.LoadAsync(id, ct);                // only this path suspends
}

Follow-ups

  • Does the synchronous path still capture the SynchronizationContext? — No, because there is no continuation to post.
  • Is there a stack-overflow risk from always-synchronous completion? — Yes, in recursive or looping pipelines; break the chain with await Task.Yield() or ConfigureAwait(ConfigureAwaitOptions.ForceYielding) (.NET 8+).
  • How would you measure the difference? — BenchmarkDotNet with [MemoryDiagnoser]: the sync path shows 0 B allocated, the suspending path shows the boxed state machine plus the Task.

Common wrong answer

"Awaiting always yields, so it always costs a thread switch." Wrong: the fast path is the common case in caching and buffered-stream code, and the entire ValueTask design rests on it.

seniorIs async part of a method public contract? Can an interface member be async?

Answer

No and no. async is an implementation detail of the body — it tells the compiler to build a state machine — and it is not part of the signature; it cannot appear on an interface member or an abstract method. What is part of the contract is the return type: Task, Task<T>, ValueTask<T> or IAsyncEnumerable<T>, plus by convention the Async suffix and a trailing CancellationToken. An implementation may satisfy a Task-returning member with or without async, and switching between the two is not a breaking change for callers.

Example

interface IUserRepo { Task<User> GetAsync(int id, CancellationToken ct = default); }

// both are legal implementations of the same contract
class Db   : IUserRepo { public async Task<User> GetAsync(int id, CancellationToken ct) => await Query(id, ct); }
class Fake : IUserRepo { public Task<User> GetAsync(int id, CancellationToken ct) => Task.FromResult(_u); }

Follow-ups

  • Where does async show up in metadata at all? — As [AsyncStateMachine] on the method, which is how stack traces and analyzers can tell.
  • Can you override a sync method with an async one? — Only if the return type matches; you cannot turn void into Task in an override, which is why making a legacy interface async is a breaking change.
  • Should the token parameter be optional? — In application code yes for ergonomics; in library code many teams require it explicitly so nobody silently drops it.

Common wrong answer

"You mark the interface method async Task so implementors must be async." It does not compile — and even if it did it would be the wrong idea, because the caller cares about the task, not the state machine.

seniorWhen should a method return the inner task directly instead of async ... await-ing it? What do you lose?

Answer

Eliding async/await removes one state machine, one Task allocation on the suspending path and a frame of overhead, so it is worth it for thin pass-through wrappers on measured hot paths. You lose three things: exceptions thrown before the inner call now surface at the call site rather than on the returned task; the wrapper disappears from async stack traces, making diagnosis harder; and — the dangerous one — you can no longer wrap the call in using, try/finally or any scope, because the scope exits while the task is still running. My default is to keep await everywhere except trivial one-line forwards with no resource scope.

Example

// SAFE elision: nothing to scope
Task<User> GetAsync(int id, CancellationToken ct) => _inner.GetAsync(id, ct);

// BUG: the connection is disposed before the query completes
Task<User> Broken(int id) { using var conn = Open(); return conn.QueryAsync(id); }

// correct
async Task<User> Fixed(int id) { using var conn = Open(); return await conn.QueryAsync(id); }

Follow-ups

  • Does elision change how cancellation behaves? — No; the token flows identically. Only exception timing and stack traces change.
  • Can you elide when returning ValueTask? — Yes for a direct forward, but the single-consumption rule still applies to whoever awaits it.
  • Is there an analyzer? — Microsoft.VisualStudio.Threading.Analyzers flags both elision hazards and missing ConfigureAwait; CA2007 covers the latter in the built-in rule set.

Common wrong answer

"Always elide, await is pure overhead." The using-plus-elision bug is one of the most common production defects in .NET, and it fails intermittently — only when the inner call actually suspends.

seniorWhat is the "async all the way" rule, and what exactly goes wrong when you break it?

Answer

It means that once anything in a call chain is asynchronous, every caller up to the entry point should be asynchronous too, rather than bridging with .Result, .Wait() or .GetAwaiter().GetResult(). Breaking it costs you one of two things. On any framework with a SynchronizationContext — WinForms, WPF, legacy ASP.NET, some test runners — you deadlock, because the continuation needs the very thread you have blocked. On ASP.NET Core, where no such context exists, you do not deadlock; you burn a thread-pool thread per in-flight request, turning a healthy service into a starved one under load, with latency going superlinear rather than the service failing cleanly. The second failure mode is worse in practice because it only appears at peak traffic.

Example

// the bridge that starves the pool (or deadlocks on a UI thread)
public IActionResult Get(int id) => Ok(_repo.GetAsync(id).Result);

// async all the way
public async Task<IActionResult> Get(int id, CancellationToken ct) => Ok(await _repo.GetAsync(id, ct));

Follow-ups

  • What if a third-party interface is sync-only? — Push the boundary outward: do the async work before entering the sync API, or run the sync API on the pool and keep the bridge at the top of your own stack.
  • Is GetAwaiter().GetResult() ever acceptable? — At true entry points that cannot be async (module initializers, a few DI factories, some legacy Mains) and when you know the task is already complete.
  • How do you enforce it across a team? — Analyzer VSTHRD002 at error severity plus a documented migration path, so the ban is actionable rather than a nag.

Common wrong answer

"On ASP.NET Core there is no SynchronizationContext, so .Result is fine." It is not fine — it trades a deterministic deadlock for a load-dependent starvation incident, which is far harder to diagnose at 3 a.m.

seniorWhat happens to AsyncLocal<T> and ExecutionContext across an await?

Answer

ExecutionContext — which carries AsyncLocal<T> values and the security context — is captured when a continuation is registered and restored before that continuation runs, so ambient values flow down the async call graph. It does not flow back up: setting an AsyncLocal inside an awaited method is invisible to the caller, because the context is copy-on-write per logical thread of execution. This is the mechanism behind scoped logging, Activity.Current in OpenTelemetry and ambient transaction scopes. It is also a real cost — every suspension pays a capture and restore — which is why .NET 11 added an optimisation that skips capture/restore entirely when there is nothing to restore.

Example

static readonly AsyncLocal<string> Correlation = new();

async Task Handle()
{
    Correlation.Value = "req-42";
    await Inner();
    Console.WriteLine(Correlation.Value);  // still "req-42"
}

async Task Inner()
{
    Console.WriteLine(Correlation.Value);  // "req-42" — flows down
    Correlation.Value = "changed";         // NOT visible to Handle
    await Task.Yield();
}

Follow-ups

  • Does ConfigureAwait(false) stop ExecutionContext flow? — No. It suppresses only the SynchronizationContext/TaskScheduler capture; ExecutionContext always flows.
  • How do you deliberately suppress the flow? — ExecutionContext.SuppressFlow(), typically around long-lived background work so it does not pin a request scope.
  • Why is AsyncLocal a memory-leak suspect? — A value captured into a long-lived fire-and-forget task keeps the whole graph — request, DI scope, DbContext — alive for that task lifetime.

Common wrong answer

"AsyncLocal is like ThreadStatic, so it breaks across awaits." The opposite: ThreadStatic breaks across awaits; AsyncLocal is precisely the thing that survives them.

principalA team lead says "we made everything async and it is not faster". What do you tell them, and how do you prove it?

Answer

They are measuring the wrong thing. Async does not reduce the latency of any single operation — per call it is marginally slower because of state-machine allocation, scheduling and context capture. What it changes is how many concurrent operations a fixed number of threads can hold open, so the payoff appears only as a shift in the throughput/latency curve under concurrency: the knee moves right and the tail flattens. I would prove it with a load test at increasing concurrency, plotting p50/p99 latency and RPS for the sync and async builds side by side, plus thread-pool thread count and queue length as counters. If the workload is genuinely CPU-bound, or concurrency never exceeds the thread count, the honest answer is that async was the wrong investment there and the code should stay simple.

Example

// the counters that make the argument, not opinions
// dotnet-counters monitor -p PID System.Runtime Microsoft.AspNetCore.Hosting
//   System.Runtime               : threadpool-thread-count, threadpool-queue-length,
//                                  threadpool-completed-items-count
//   Microsoft.AspNetCore.Hosting : current-requests, requests-per-second

Follow-ups

  • What single number would you show an exec? — RPS at a fixed p99 SLO, before and after; or cost per million requests, since it is really a machine-count argument.
  • When would you revert async code to sync? — Hot in-memory paths, CPU-bound transforms and internal helpers that never touch I/O, where the state machine is pure overhead.
  • What is the hidden benefit besides throughput? — Graceful degradation: an async server queues in its own request pipeline where you can shed load, instead of silently blocking threads.

Common wrong answer

"Async is faster because it uses more threads" — or the equally bad inverse, "async is always the right default". A principal-level answer names the workload and shows the measurement.

02Task, the TAP contract and completion

Task is the currency of the whole model, and interviewers use it to check whether you understand that a Task is a promise of a result, not a unit of work. Expect questions on Task vs Thread, on hot vs cold tasks, and — at senior level — on TaskCompletionSource, which is where you prove you can bridge a callback API into TAP correctly. Library-shaped roles will also probe the TAP contract itself: naming, token placement, and what a well-behaved async API promises its callers.

screenerWhat is the difference between a Task and a Thread?

Answer

A Thread is an OS scheduling entity with roughly 1 MB of reserved stack; creating one costs on the order of hundreds of microseconds and it is yours until it exits. A Task is a promise object representing an operation that will complete in the future, with a result or an exception, and a list of continuations. Some tasks are backed by a thread — the ones from Task.Run, which borrow a thread-pool thread — but most tasks in a well-written service are backed by nothing at all: an outstanding I/O request whose completion callback will complete the Task. Confusing them is the root of nearly every async mistake.

Example

var t1 = new Thread(Work);  t1.Start();      // one dedicated OS thread, ~1 MB stack
var t2 = Task.Run(Work);                     // queued onto a pool thread
var t3 = File.ReadAllTextAsync(path);        // NO thread at all while it waits

Follow-ups

  • When do you still create a raw Thread in 2026? — Long-running dedicated loops that must not occupy a pool thread, when you need a specific stack size, COM apartment state, or a custom priority.
  • What is TaskCreationOptions.LongRunning? — A hint that makes the default scheduler spin up a dedicated thread instead of queueing to the pool; use it for blocking loops, not for I/O.
  • Is a completed Task cheap to hold? — Yes, it is a small object, but a faulted one holds an exception with its stack trace, and a Task with continuations holds them too.

Common wrong answer

"A Task is a lightweight thread." That framing makes every I/O-bound Task sound like it costs a thread, and it is the reason people then "optimise" by raising ThreadPool.SetMinThreads.

midWhat states can a Task be in, and what is the difference between IsCompleted, IsCompletedSuccessfully and Status?

Answer

A Task ends in exactly one of three terminal states: RanToCompletion, Faulted or Canceled. IsCompleted is true for all three — it means "no longer running", not "succeeded", which is the trap in the question. IsCompletedSuccessfully (.NET Core 2.0+) is the one that means success; IsFaulted and IsCanceled cover the rest. Status exposes the full enum including the pre-terminal states (Created, WaitingForActivation, Running). In code you rarely poll any of these: you await, and let the exception or result come back.

Example

if (task.IsCompleted) { /* WRONG check for success — includes faulted and canceled */ }

if (task.IsCompletedSuccessfully) Use(task.Result);
else if (task.IsCanceled)         Log("canceled");
else if (task.IsFaulted)          Log(task.Exception!.InnerException);

Follow-ups

  • Why does Task.Exception return an AggregateException? — Because a Task can represent several operations (WhenAll); await unwraps it to the first inner exception.
  • Is a canceled Task faulted? — No; cancellation is its own terminal state, and awaiting it throws TaskCanceledException (an OperationCanceledException).
  • Can a Task go from Faulted to RanToCompletion? — No, terminal states are final; that is why TaskCompletionSource has both SetResult (throws if already set) and TrySetResult.

Common wrong answer

"IsCompleted means it succeeded." Code built on that assumption silently swallows failures — it reads Result on a faulted task and throws an unhelpful AggregateException somewhere else entirely.

midHot vs cold tasks: what is the difference, and why is new Task(...) almost always wrong?

Answer

A hot task is already running or already completed; a cold task has not been started. In TAP every task you get back from a well-behaved API is hot — that is part of the contract, so callers never have to ask whether they need to start it. new Task(action) creates a cold task that does nothing until Start() is called, which is a legacy of the .NET 4.0 TPL and has no place in modern code: it invites the bug where someone awaits a task nobody started, and the call hangs forever. Use Task.Run for CPU work, an async method for I/O, and TaskCompletionSource when you need a task you complete yourself.

Example

var cold = new Task(() => Work());   // legacy, never started
await cold;                           // hangs forever

var hot = Task.Run(Work);             // modern: already queued
await hot;

Follow-ups

  • Is there any legitimate use of cold tasks? — Custom schedulers and a few TPL-era pipelines; in application code, effectively none.
  • How do you model "start later" then? — A Func<CancellationToken, Task> factory: the delegate is the deferred thing, not the task.
  • What about Task.Factory.StartNew? — Still available, but it does not unwrap async delegates (you get Task<Task>) and defaults to TaskScheduler.Current; prefer Task.Run unless you need its options.

Common wrong answer

"You have to call Start() on tasks returned by async methods." That reveals the candidate has never actually read the TAP contract, and predicts they will also write Task.Run(async () => await X()) reflexively.

seniorWhat is TaskCompletionSource for, and what is the trap with it?

Answer

It is how you produce a Task that you complete manually — the standard way to wrap a callback-, event- or message-based API into TAP, and to build async coordination primitives. The trap is continuation scheduling: by default the continuations attached to that Task run synchronously on the thread that calls SetResult. If that thread is your I/O reader loop or a lock holder, arbitrary user code now runs inside it, which produces stalls, reentrancy and deadlocks that are very hard to trace. The fix is to always construct it with TaskCreationOptions.RunContinuationsAsynchronously, which has been the recommended default since .NET Framework 4.6. Second trap: use TrySet* rather than Set* if more than one path can complete it, or you get an InvalidOperationException in a race.

Example

var tcs = new TaskCompletionSource<Response>(TaskCreationOptions.RunContinuationsAsynchronously);

_pending[correlationId] = tcs;                 // callback thread will complete it
using var reg = ct.Register(() => tcs.TrySetCanceled(ct));
return await tcs.Task;                          // caller awaits normally

// in the transport callback:
void OnMessage(Message m) => _pending[m.CorrelationId].TrySetResult(m.Body);

Follow-ups

  • What breaks without RunContinuationsAsynchronously? — The completing thread runs the awaiting code inline; a socket read loop can end up executing business logic, and throughput collapses.
  • How do you make it cancellable? — Register on the token to TrySetCanceled(ct), and dispose the registration so the token does not keep the TCS alive.
  • The non-generic TaskCompletionSource? — Added in .NET 5; before that people used TaskCompletionSource<object?> or <bool>.

Common wrong answer

"It is just a way to return a Task from a sync method" — with new TaskCompletionSource<T>() and no options. It works in a unit test and stalls in production, which is exactly the kind of bug interviewers are probing for.

seniorYou are reviewing a new async library API. What does the TAP contract require?

Answer

Six things I check every time. The method is named with an Async suffix and returns Task, Task<T>, ValueTask<T> or IAsyncEnumerable<T>. The returned task is hot and never null. A CancellationToken is the last parameter and is actually passed down, not accepted and ignored. Failures come back through the task, not as synchronous throws — except for argument validation, which is allowed and preferred to be eager. Progress, if any, comes through IProgress<T> rather than events. And internally it does not call ConfigureAwait(true) semantics by accident: library code awaits with ConfigureAwait(false) so it never captures a caller context.

Example

public Task<Report> BuildAsync(ReportSpec spec, IProgress<int>? progress = null,
                               CancellationToken ct = default)
{
    ArgumentNullException.ThrowIfNull(spec);      // eager, synchronous
    return Core(spec, progress, ct);

    async Task<Report> Core(ReportSpec s, IProgress<int>? p, CancellationToken c)
    {
        var rows = await _db.QueryAsync(s, c).ConfigureAwait(false);
        p?.Report(50);
        return await Render(rows, c).ConfigureAwait(false);
    }
}

Follow-ups

  • Should you offer sync and async versions of the same method? — Prefer one. If you must offer both, implement them separately; never wrap one in the other (no sync-over-async, no Task.Run facades).
  • Why is a fake-async wrapper worse than a sync method? — It lies to the caller about cost, hides a blocked thread behind an async signature, and prevents callers from making a correct scheduling decision.
  • Where is this written down? — The "Task-based asynchronous pattern" docs on Microsoft Learn, plus the .NET Framework Design Guidelines async section.

Common wrong answer

"Add an async wrapper with Task.Run so the API is async too." That is the classic fake async anti-pattern: it consumes a thread per call and gives callers no benefit whatsoever, while making the API look scalable.

midWhen do you use Task.CompletedTask, Task.FromResult, Task.FromException and Task.FromCanceled?

Answer

They are the way to satisfy a Task-returning contract without paying for a state machine. Task.CompletedTask is a cached singleton, so returning it is free. Task.FromResult allocates, except for values the runtime caches (small ints, booleans, null references), which is one reason ValueTask is preferred on hot cache paths. Task.FromException and Task.FromCanceled matter because they give the caller a faulted or canceled task rather than throwing synchronously — important when you are eliding async and want the failure to behave exactly as if the method had been async.

Example

public Task PublishAsync(Event e, CancellationToken ct)
{
    if (ct.IsCancellationRequested) return Task.FromCanceled(ct);
    if (!_enabled) return Task.CompletedTask;                 // no allocation
    if (e is null) return Task.FromException(new ArgumentNullException(nameof(e)));
    return _bus.SendAsync(e, ct);
}

Follow-ups

  • Is Task.FromResult(true) allocation-free? — Yes for bool and small int values, thanks to the runtime cache; not in general for reference types.
  • What about ValueTask.CompletedTask? — Also free, and the right choice when the surrounding API already returns ValueTask.
  • Why not just async Task M() { } with no awaits? — It still builds a state machine and produces a compiler warning (CS1998); returning Task.CompletedTask is clearer and cheaper.

Common wrong answer

"Task.FromResult is free, so use it everywhere." On a path called millions of times per second, returning Task<byte[]> from a cache via FromResult is a measurable allocation — this is the exact scenario ValueTask was designed for.

screenerTask.Delay vs Thread.Sleep — what actually differs?

Answer

Thread.Sleep blocks the current thread for the duration: it stays alive, holds its stack, and is unavailable to anyone else. Task.Delay returns a Task backed by a timer; awaiting it releases the thread, and a continuation is scheduled when the timer fires. In a server, a thousand concurrent Thread.Sleep(1000) calls occupy a thousand threads; a thousand await Task.Delay(1000) calls occupy one timer queue and no threads. Task.Delay also takes a CancellationToken, so a shutdown can interrupt it, which Thread.Sleep cannot.

Example

await Task.Delay(TimeSpan.FromSeconds(1), ct);   // no thread held, cancellable

// for repeating work, prefer a PeriodicTimer (.NET 6+) over a delay loop:
using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30));
while (await timer.WaitForNextTickAsync(ct)) await PollAsync(ct);

Follow-ups

  • How accurate is Task.Delay? — It guarantees "at least" the delay; expect roughly 15 ms of scheduling granularity on Windows, more under load. Never build timing-critical logic on it.
  • How do you make it testable? — Inject TimeProvider (.NET 8+) and call Task.Delay(delay, timeProvider, ct); tests use FakeTimeProvider to advance time instantly.
  • What does Task.Delay(0) do? — Returns an already-completed task, so awaiting it does not yield — use Task.Yield() if you actually want to yield.

Common wrong answer

"Task.Delay sleeps on a background thread." There is no thread; it is a timer callback. The distinction is the whole point of the question.

seniorWhat does await Task.Yield() do, and when have you needed it?

Answer

It forces the method to return to its caller and re-schedule the rest of the method as a continuation — an unconditional yield, even though nothing is being waited on. Three places it earns its keep: breaking out of a deep synchronous chain that would otherwise stack-overflow (a pipeline where every stage completes synchronously); giving a UI message pump or a request thread a chance to run before you continue a long CPU stretch; and making a method that is otherwise fully synchronous behave asynchronously so the caller is not surprised by inline execution. In .NET 8+ the more expressive form is ConfigureAwait(ConfigureAwaitOptions.ForceYielding) applied to a task you were awaiting anyway.

Example

async Task PumpAsync(ChannelReader<Item> reader, CancellationToken ct)
{
    var n = 0;
    while (await reader.WaitToReadAsync(ct))
        while (reader.TryRead(out var item))
        {
            Process(item);                        // fully synchronous
            if (++n % 1000 == 0) await Task.Yield();   // do not monopolise the thread
        }
}

Follow-ups

  • Where does the continuation go? — To the captured context if there is one, otherwise the thread pool. Task.Yield() on a UI thread returns to the UI thread.
  • Is it a fix for thread-pool starvation? — No; it re-queues work, it does not stop you blocking. It only helps fairness within a thread.
  • Cheaper alternative in a tight loop? — Check ct.IsCancellationRequested and yield only every N items, as above; every yield costs a scheduling round trip.

Common wrong answer

"It moves the work to a background thread." It does not move work anywhere new — it re-queues the continuation to the same context or the pool. Candidates who confuse it with Task.Run usually also misdiagnose UI freezes.

03Thread-pool behaviour and starvation

This is where senior candidates are separated from mid ones, because it is the sub-area that shows up in real incidents. Interviewers want to hear that you know the pool grows slowly and deliberately, that blocking a pool thread is the cardinal sin, and that the symptom of starvation is rising latency with idle CPU. At principal level the question becomes an incident-command one: what you would look at first, what you would change in the next five minutes, and what you would change in the next sprint.

midHow does the .NET thread pool decide how many threads to run?

Answer

The pool starts with a minimum equal to Environment.ProcessorCount worker threads (plus a separate I/O completion pool on Windows). Up to that minimum, a queued work item that finds no free thread gets one immediately. Beyond it, the pool injects threads slowly — historically about one or two per second — governed by a hill-climbing algorithm that watches completed-work-item throughput and adds or removes threads to maximise it. The maximum is very large (thousands) and is effectively never the binding constraint. The consequence you must state: if you block threads faster than roughly one or two per second, the pool cannot catch up, and the queue grows without bound while CPU sits idle.

Example

// the two numbers to know
Console.WriteLine(Environment.ProcessorCount);                 // e.g. 8
ThreadPool.GetMinThreads(out var w, out var io);               // 8, 8 by default
ThreadPool.GetAvailableThreads(out var aw, out var aio);       // how many are free right now

Follow-ups

  • Does SetMinThreads fix starvation? — It buys a burst of headroom and can rescue a startup spike, but it treats the symptom; the cause is blocking, and a bigger pool just means more blocked threads.
  • What changed recently? — Since .NET 6 the pool is implemented in managed code (the portable thread pool) on all platforms, which made injection behaviour consistent and easier to instrument.
  • Where do await continuations go? — Onto the same worker queues; each thread has a local queue plus a global queue with work stealing, so continuations are usually cheap.

Common wrong answer

"The pool creates threads as fast as needed, so blocking is fine as long as you have RAM." The injection rate — not the maximum — is what kills you, and it is why starvation manifests as a latency cliff rather than a gradual slowdown.

seniorDescribe thread-pool starvation: cause, symptom, and how you confirm it in production.

Answer

Cause: work items block pool threads — .Result, .Wait(), lock held across a slow call, a synchronous DB or file call, Thread.Sleep — so threads are consumed faster than the pool injects replacements. Symptom: request latency climbs steeply and non-linearly while CPU utilisation stays low, queued work grows, and health checks or timers start firing late; restarts "fix" it for a while. Confirmation: watch threadpool-thread-count climbing in one-per-second steps while threadpool-queue-length grows and CPU is under 30%; then take a dump and look at the stacks — dozens of threads parked in Monitor.Wait, Task.Wait or ManualResetEventSlim.Wait under your own code is the signature.

Example

// live triage
// dotnet-counters monitor -p PID System.Runtime
//   threadpool-thread-count   : 8 -> 9 -> 10 ...  (one per second = injection, not health)
//   threadpool-queue-length   : rising
//   cpu-usage                 : 15%          <-- the tell

// then, from a dump:
// dotnet-dump analyze core.dmp
//   > clrthreads
//   > parallelstacks         (look for many identical blocked stacks)

Follow-ups

  • How do you distinguish starvation from a slow dependency? — A slow dependency shows high current-requests with normal thread counts; starvation shows a growing queue and steadily injected threads.
  • What is the five-minute mitigation? — Raise MinThreads or scale out to stop the bleeding, then find and remove the blocking call — never stop at the first step.
  • Does async everywhere guarantee immunity? — No: a synchronous CPU-heavy handler, a lock under contention, or a blocking third-party SDK will starve an otherwise async service.

Common wrong answer

"CPU was low so it was not a compute problem — must have been the database." Starvation looks exactly like a slow dependency from the outside; the difference is visible only in thread count and queue length, and candidates who never check those keep restarting pods.

midWhen is Task.Run the right tool, and when is it a mistake?

Answer

Task.Run is correct when you have genuinely CPU-bound work that you want off the current thread — most importantly in a UI app, to keep the message pump responsive. It is a mistake in server code used to "make something async": on a server there is no thread to protect, so you have simply moved the work from one pool thread to another and added a queueing hop. It is also a mistake as a wrapper around blocking I/O in a library, because it hides a blocked thread behind an async signature. The rule I give teams: Task.Run at the call site when the caller needs the thread back; never inside a library to fake asynchrony.

Example

// GOOD (desktop): keep the UI responsive during CPU work
private async void OnCalcClick(object s, EventArgs e)
    => Result.Text = (await Task.Run(() => Simulate(_input))).ToString();

// BAD (server): no benefit, one extra hop, still one blocked thread
public Task<byte[]> ReadAsync(string p) => Task.Run(() => File.ReadAllBytes(p));

Follow-ups

  • Is Task.Run ever right on a server? — Yes: to parallelise a genuinely CPU-bound chunk across cores, or to offload a blocking third-party call at the boundary so it does not sit on the request path unbounded — with a concurrency limit around it.
  • What about Task.Run with an async lambda? — Task.Run(async () => await X()) unwraps correctly (unlike StartNew) but adds a pointless hop unless you specifically want to leave the current context.
  • Long-running blocking loop? — Use a dedicated thread or TaskCreationOptions.LongRunning via Task.Factory.StartNew, so you do not hold a pool thread for hours.

Common wrong answer

"Wrap the sync method in Task.Run so the controller can await it and scale." Throughput is identical or slightly worse; you have added a queue hop and made the thread cost invisible to whoever reads the signature later.

seniorShould you call ThreadPool.SetMinThreads? What are you actually trading?

Answer

Sometimes, as a deliberate and documented mitigation — not as a default. Raising the minimum removes the injection delay for the first N threads, which genuinely helps two cases: a startup or deployment burst where a lot of work arrives before hill climbing has adapted, and a service that unavoidably calls a blocking dependency. What you trade is memory (about 1 MB of reserved stack per thread), more context switching, worse cache locality, and — most importantly — the loss of the signal: with a large minimum, starvation no longer shows up as an obvious slow climb in thread count. I set it only with a comment pointing at the blocking call it compensates for, and a ticket to remove both.

Example

// Program.cs — mitigation, not a fix. Ticket PLAT-4471 removes the blocking SDK call.
ThreadPool.GetMinThreads(out _, out var io);
ThreadPool.SetMinThreads(workerThreads: Environment.ProcessorCount * 4, completionPortThreads: io);

Follow-ups

  • Is there a config-file way? — Yes: System.Threading.ThreadPool.MinThreads in runtimeconfig.json, which is preferable because it is visible in ops tooling rather than buried in startup code.
  • What is a sane ceiling? — There is no universal number; derive it from concurrency times blocking duration (Little law) and validate under load, rather than picking 200 because a blog said so.
  • Does it help a fully async service? — Almost never; if you need it there, you have an unidentified blocking call.

Common wrong answer

"Set MinThreads to 200 at startup, it is a best practice." It is a known incident-shaped anti-pattern: it masks the blocking bug, costs hundreds of megabytes of stack reservation, and removes the diagnostic you would have used to find the real cause.

seniorWhat are I/O completion port threads, and does that distinction still matter?

Answer

On Windows the CLR historically maintained two pools: worker threads for queued work items and a separate set of I/O completion port threads that service overlapped I/O completions, each with its own minimum. That is why SetMinThreads takes two arguments and why old guidance told you to raise both. Since .NET 6, with the portable thread pool as the default on all platforms, completions are dispatched onto the same managed worker pool, so the practical distinction has largely gone — but the API and the counters remain, and .NET Framework services still very much have two pools. In an interview, saying "two pools historically, unified in the portable pool since .NET 6" is the answer that lands.

Example

ThreadPool.GetMinThreads(out var worker, out var completionPort);
// On modern .NET the second number matters far less than it did on .NET Framework,
// but SetMinThreads still requires you to pass something sane for it.

Follow-ups

  • How can you tell which pool is starved? — threadpool-thread-count plus stacks; on .NET Framework, comparing GetAvailableThreads for both numbers.
  • Does this apply on Linux? — There were never IOCP threads there; epoll completions were always dispatched through the managed pool.
  • Can you go back to the old pool? — There was a System.Threading.ThreadPool.UseWindowsThreadPool switch in .NET 8 for opting into the OS pool; treat it as a niche performance experiment, not a default.

Common wrong answer

"I/O threads are what run your await continuations, so raise those." Continuations run on worker threads; conflating the two leads people to tune the wrong number and conclude tuning does not work.

seniorA service has slow p99 latency and 20% CPU. Walk me through your diagnosis.

Answer

Low CPU with bad tail latency means we are waiting on something, so I split it into three hypotheses and test each cheaply. First, thread-pool starvation: dotnet-counters for thread count, queue length and completed items — a queue that grows while threads climb one per second confirms it. Second, a slow or contended dependency: dependency duration histograms and connection-pool exhaustion counters (an SQL pool of 100 with 300 concurrent requests behaves exactly like starvation). Third, lock contention or GC pauses: lock-contention-count and gen2/pause metrics. Then I take a dump and read parallel stacks: many identical blocked frames name the culprit in seconds. Only after the class of problem is identified do I touch configuration.

Example

// counters that separate the three hypotheses
// System.Runtime            : threadpool-queue-length, threadpool-thread-count,
//                             monitor-lock-contention-count, gc-pause-time-percent
// Microsoft.Data.SqlClient  : active-hard-connections, number-of-pooled-connections
// Microsoft.AspNetCore.Hosting : current-requests, failed-requests

Follow-ups

  • What if all three look normal? — Look outward: DNS, TLS handshakes, a proxy, or a downstream with its own queue; distributed traces will show where the time actually sits.
  • How do you make this repeatable for the team? — Ship the counters to the dashboard permanently and write the runbook while the incident is fresh, so the next person does not rediscover it.
  • What is your first mitigation while diagnosing? — Shed load or scale out to protect the SLO; diagnosis and mitigation run in parallel, not in sequence.

Common wrong answer

Jumping straight to "scale out" or "increase MinThreads" without a hypothesis. Interviewers score the diagnostic sequence, not the fix; a candidate who names counters and dumps beats one who names remedies.

midWhy is holding a lock across an await impossible, and what do you do instead?

Answer

You cannot await inside a lock block — the compiler rejects it — because Monitor is thread-affine: the thread that entered must be the one that exits, and after an await the continuation may run on a different thread. The correct tool is SemaphoreSlim(1,1) with WaitAsync, which is not thread-affine, released in a finally. Two caveats: it is not reentrant, so a nested acquire self-deadlocks; and holding it across a slow I/O call serialises your whole service, so scope it as narrowly as possible or key it per entity.

Example

private readonly SemaphoreSlim _gate = new(1, 1);

async Task<Config> GetAsync(CancellationToken ct)
{
    await _gate.WaitAsync(ct);
    try
    {
        return _cached ??= await LoadAsync(ct);
    }
    finally { _gate.Release(); }   // MUST be in finally, including on cancellation
}

Follow-ups

  • What about System.Threading.Lock? — Added in .NET 9 and used by the lock statement for better performance, but it is still synchronous and thread-affine; it does not enable awaiting inside a lock.
  • What if you forget the finally? — One thrown exception permanently leaks a permit and every later caller hangs — a slow, total outage.
  • Alternative to a lock entirely? — Lazy<Task<T>> or AsyncLazy for one-time init, or a single-writer channel/actor so no shared state needs a lock at all.

Common wrong answer

"Use Monitor.Enter/Monitor.Exit manually to get around the compiler." That compiles and then corrupts: exit from a different thread throws SynchronizationLockException, or worse, the lock is silently never released.

principalYou inherit a service that blocks on async calls everywhere. How do you get it to async without a big-bang rewrite?

Answer

I would not start with code. First put the measurement in — thread-pool counters and dependency histograms on the dashboard — so the migration has a scoreboard and the team can see the win. Then work outside-in, one vertical slice at a time: make the entry point (controller, consumer, job) async, then the layer beneath it, keeping the bridge at exactly one place per slice and moving it down as you go. Take the highest-traffic slice first, ship it, and show the p99 change. In parallel, land the analyzer (VSTHRD002) as a warning, then error on new code only, so the ratchet holds. If a dependency truly has no async API, isolate it behind a bulkhead with a bounded concurrency limit rather than letting it consume the pool. And I would explicitly not convert code paths that are CPU-bound or never contended — those are cost without benefit.

Example

// bulkhead for a blocking legacy SDK: bounded threads, explicit queueing, visible cost
private static readonly SemaphoreSlim _legacyGate = new(8);

async Task<Result> CallLegacyAsync(Req r, CancellationToken ct)
{
    await _legacyGate.WaitAsync(ct);
    try { return await Task.Run(() => _sdk.Call(r), ct); }
    finally { _legacyGate.Release(); }
}

Follow-ups

  • How do you sequence it against feature work? — Tie each slice to a feature already touching that code; a standalone "async migration" epic gets deprioritised in month two.
  • How do you prevent regressions? — Analyzer as error on changed files, plus a load test in CI that fails on queue-length regression.
  • What would make you stop the migration? — If the counters show no starvation and latency is dominated by a downstream, the migration is not the highest-value work — say so and move on.

Common wrong answer

"Rewrite it all async in one branch." Long-lived branches on cross-cutting changes never merge cleanly, and without a scoreboard nobody can tell whether it helped — which is how these efforts get cancelled halfway.

principalHow do you size the concurrency limit for an outbound dependency?

Answer

Start from Little law: the in-flight count you need is arrival rate times service time. If you take 500 requests per second and the dependency answers in 40 ms, you need about 20 concurrent calls to keep up, so a limit of 20–30 is right and anything much larger just moves queueing into the dependency where you cannot see or control it. Then cross-check against the dependency published limit and its own connection pool — an SQL connection pool of 100 is a hard ceiling regardless of what your semaphore says. Finally, decide the behaviour at the limit: fail fast with a clear error is usually better than an unbounded queue, and it should be paired with a timeout so a slow dependency cannot pin permits forever.

Example

// .NET 8+ rate limiting, with fail-fast rather than an unbounded queue
builder.Services.AddRateLimiter(o => o.AddConcurrencyLimiter("search", opt =>
{
    opt.PermitLimit = 24;                                  // ~ 500 rps * 40 ms + headroom
    opt.QueueLimit = 16;
    opt.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
}));

Follow-ups

  • What happens if you set it too low? — You throttle yourself and the queue backs up into request latency; the counters will show wait time at the limiter, which is exactly why you instrument it.
  • Static or adaptive? — Start static because it is predictable; move to adaptive (gradient/AIMD) only when you have the telemetry to trust it.
  • Where else does an implicit limit already exist? — HttpClient connections per server, the SQL pool, Kestrel max concurrent connections — find them before adding another.

Common wrong answer

"Do not limit it, async scales." Unbounded concurrency turns a slow dependency into an out-of-memory crash and destroys the dependency in the process — the limit is what converts a partial failure into a bounded one.

04ConfigureAwait, contexts and deadlocks

The single most-asked "do you really understand this" topic, and the one where confident wrong answers are most common. Interviewers are checking three things: that you know what a SynchronizationContext is, that you can explain the classic deadlock mechanically rather than by ritual, and that you know the modern guidance differs between library code and application code. At principal level the question becomes a policy one — what rule you would set for a codebase, and how you would enforce it.

midWhat does ConfigureAwait(false) do?

Answer

It tells the awaiter not to capture the current SynchronizationContext (or, failing that, the current TaskScheduler) for the continuation, so the rest of the method resumes on whatever thread completed the operation — normally a thread-pool thread — rather than being posted back to the original context. It has two effects: it avoids the deadlock that occurs when the original context is a single-thread pump you have blocked, and it removes a scheduling hop, which is a measurable win in hot library code. It does not affect ExecutionContext, so AsyncLocal values and Activity.Current still flow.

Example

// library code: never assume anything about the caller context
public async Task<string> ReadAsync(Stream s, CancellationToken ct)
{
    using var reader = new StreamReader(s);
    return await reader.ReadToEndAsync(ct).ConfigureAwait(false);
}

Follow-ups

  • Does it apply to the whole method? — No, only to that one await. Each await decides for itself, which is why libraries apply it consistently on every await.
  • What if there is no SynchronizationContext? — It is a near no-op: a flag check, no behaviour change. That is why it is harmless but also pointless in ASP.NET Core app code.
  • What about ConfigureAwait(true)? — The default; writing it explicitly is only useful as documentation that the capture is intentional.

Common wrong answer

"It makes the continuation run on a background thread." It does not schedule anything anywhere new — it just declines to post back to a captured context. And "it prevents deadlocks" is only half true: it prevents that deadlock, in the callee, and only if applied everywhere down the chain.

seniorExplain the classic .Result deadlock mechanically.

Answer

On a framework with a single-threaded SynchronizationContext — a WPF/WinForms UI thread, or legacy ASP.NET request context — the UI thread calls an async method and then blocks on .Result. Inside, the async method awaits; because a context was present, the awaiter captured it and will Post the continuation back to that context when the operation completes. The operation completes, the continuation is posted to the context queue — and nobody is draining that queue, because the one thread that services it is sitting inside .Result waiting for the very task that continuation would complete. Deadlock, permanently. Two independent fixes: do not block (await all the way up), or do not capture (ConfigureAwait(false) on every await in the callee). Only the first is reliable, because the second requires every layer to comply.

Example

// WPF button handler — hangs the app
private void OnClick(object s, RoutedEventArgs e)
{
    var data = LoadAsync().Result;    // UI thread blocked here
    Text.Text = data;
}

async Task<string> LoadAsync()
{
    var r = await _http.GetStringAsync(Url);  // captured UI context; Post never runs
    return r.Trim();
}

// fix: async void event handler, await all the way
private async void OnClick(object s, RoutedEventArgs e) => Text.Text = await LoadAsync();

Follow-ups

  • Why does the same code not deadlock in a console app? — No SynchronizationContext, so the continuation goes to the pool and completes; you get starvation risk instead of a hang.
  • Does Task.Run(() => LoadAsync()).Result fix it? — It usually unblocks, because the inner method runs with no captured context — but you have burned a thread and kept the blocking bug. It is a workaround, not a fix.
  • Where else does a context appear unexpectedly? — Some test frameworks (older xUnit/NUnit sync contexts), Blazor WebAssembly, Xamarin/MAUI UI threads, and Office/COM add-ins.

Common wrong answer

"You need ConfigureAwait(false) on the .Result call site." ConfigureAwait applies to awaits, not to blocking calls; and putting it in the caller does nothing for the callee awaits that actually captured the context.

midDo you need ConfigureAwait(false) in an ASP.NET Core application? Why is the answer different for a library?

Answer

In ASP.NET Core application code, no: there has been no SynchronizationContext since ASP.NET Core 1.0, so the call is a no-op and it costs readability. In library code, yes on every await — a library does not know who calls it, and a WPF app, a MAUI app, a Blazor WebAssembly page or a legacy ASP.NET service might. That single asymmetry is the whole modern guidance, and it is what interviewers are checking: not the ritual, but whether you know why the answer depends on who owns the code.

Example

// application code (ASP.NET Core) — plain awaits, readable
public async Task<IActionResult> Get(int id, CancellationToken ct)
    => Ok(await _repo.GetAsync(id, ct));

// library code — defensive on every await
internal async Task<Row> QueryAsync(CancellationToken ct)
{
    await using var conn = await OpenAsync(ct).ConfigureAwait(false);
    return await conn.ReadAsync(ct).ConfigureAwait(false);
}

Follow-ups

  • Any perf argument in app code? — Marginal: it skips one flag check and one potential post. Not worth the noise unless a benchmark says otherwise on a very hot path.
  • How do you enforce it in a library? — Enable CA2007 for library projects only, so app projects stay clean.
  • What about Blazor Server vs WebAssembly? — Blazor Server has a renderer SynchronizationContext, and Blazor WebAssembly historically has a single-threaded context; library code shared with either must not capture.

Common wrong answer

"You must always write ConfigureAwait(false), it is a best practice." Applied blindly in a UI app, it moves your continuation off the UI thread and the next line throws a cross-thread access exception. Context is the point.

seniorWhat is ConfigureAwaitOptions and what does each option do?

Answer

Added in .NET 8, it replaces the boolean with a flags enum on Task (not yet on ValueTask). None is the old false: do not capture the context. ContinueOnCapturedContext is the old true. SuppressThrowing makes the await complete without throwing when the task faults or is canceled — the modern way to say "wait for this to finish, I do not care how it ended", which is exactly what you want when awaiting a background task during shutdown. ForceYielding makes the await always suspend even if the task is already complete, which is the expressive replacement for a bare Task.Yield() in the middle of a method.

Example

// shutdown: wait for the pump to drain, ignore how it ended
await _pumpTask.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);

// guarantee a yield even on the synchronous fast path
await cachedTask.ConfigureAwait(ConfigureAwaitOptions.ForceYielding
                              | ConfigureAwaitOptions.None);

Follow-ups

  • Does SuppressThrowing mark the exception observed? — Yes, so it will not resurface as an unobserved task exception — which also means you must log it yourself if you care.
  • Why is it not on ValueTask? — ValueTask keeps its simpler ConfigureAwait(bool); the flags overload was added to Task only.
  • What did people write before .NET 8? — try { await t; } catch { } for suppression and await Task.Yield() for forced yielding — both still perfectly valid.

Common wrong answer

"SuppressThrowing swallows exceptions, so it is dangerous and should never be used." It is the deliberate, self-documenting version of an empty catch — the danger is using it without logging, not the option itself.

seniorWhat exactly is a SynchronizationContext, and which ones will you meet?

Answer

It is an abstraction over "where should this callback run", with a Post (asynchronous) and Send (synchronous) method. The awaiter captures SynchronizationContext.Current at the point of suspension and posts the continuation to it on completion. The ones that matter in practice: WindowsFormsSynchronizationContext and DispatcherSynchronizationContext post to a single UI thread message pump; AspNetSynchronizationContext in legacy ASP.NET (System.Web) serialises request continuations onto the request context; Blazor has a renderer context; and modern ASP.NET Core and console apps have null, meaning the pool. If the context is null, the awaiter falls back to TaskScheduler.Current when it is not the default scheduler — which is how nested TPL work sometimes ends up on an unexpected scheduler.

Example

// bridge back onto the UI thread from non-UI code, explicitly
var ui = SynchronizationContext.Current;   // capture on the UI thread
await Task.Run(HeavyWork);
ui!.Post(_ => Status.Text = "done", null);

Follow-ups

  • How do you remove a context deliberately? — SynchronizationContext.SetSynchronizationContext(null) around the call, which is what some test harnesses and console hosts do.
  • Post vs Send? — Post queues and returns; Send blocks until it runs, and calling Send from the context own thread or under a lock is a classic deadlock.
  • Does it matter for a Worker Service? — No, there is none — which is why library code shared between a Worker and a WPF app still needs ConfigureAwait(false).

Common wrong answer

"SynchronizationContext is a legacy concept that no longer exists in .NET." It is gone from ASP.NET Core, not from .NET: every desktop, MAUI and Blazor app has one, and libraries must still behave correctly under it.

midWhy can awaiting the same async code resume on a different thread each time — and when does that matter?

Answer

Because with no captured context the continuation is queued to the thread pool, and which pool thread picks it up is arbitrary. It matters in three places. Thread-affine state breaks: ThreadStatic fields, Thread.CurrentPrincipal in some hosts, thread-affine COM objects, and UI controls. Thread-affine locks break: a Monitor or ReaderWriterLockSlim acquired before an await cannot be released after it. And thread-id-based logging or correlation silently becomes meaningless — which is why you correlate with AsyncLocal/Activity rather than Thread.CurrentThread.ManagedThreadId.

Example

[ThreadStatic] static string? _tenant;

async Task Handle()
{
    _tenant = "acme";
    await Task.Delay(10);
    Console.WriteLine(_tenant);   // very likely null: different thread
}
// use AsyncLocal<string> instead — it flows with the logical call, not the thread

Follow-ups

  • Is resumption ever guaranteed on the same thread? — Only under a context that says so (a UI thread), or on the synchronous fast path where no suspension happened.
  • What about [ThreadStatic] caches for performance? — Still fine for pure per-thread scratch buffers, since correctness does not depend on continuity — but never for logical state.
  • How do you log a correlation id correctly? — ILogger scopes backed by AsyncLocal, or Activity.Current.TraceId from the OpenTelemetry pipeline.

Common wrong answer

"It resumes on the same thread unless you use ConfigureAwait(false)." Backwards: with no context — the ASP.NET Core and console default — it resumes on any pool thread whether or not you wrote ConfigureAwait.

seniorA library you depend on deadlocks a WPF app. You cannot change it. What are your options?

Answer

Three, in order of preference. First, stop blocking on the UI thread at all — make the call site async void at the event handler and await down, which removes the trigger entirely. Second, if some intermediate code must block, run the library call on a context-free thread so its awaits have nothing to capture: await Task.Run(() => lib.DoAsync()). Third, if you are stuck with a synchronous entry point that must block, use a nested pump such as JoinableTaskFactory.Run from Microsoft.VisualStudio.Threading, which drains the context while blocking — the only correct way to block on a UI thread. And I would open an issue upstream, because a library that captures context is a library bug.

Example

// option 2: strip the context by hopping to the pool
var result = await Task.Run(() => badLibrary.LoadAsync(id));

// option 3: correct blocking on a UI thread, when you truly have no choice
var jtf = new JoinableTaskFactory(new JoinableTaskContext());
var result2 = jtf.Run(() => badLibrary.LoadAsync(id));

Follow-ups

  • Why not SetSynchronizationContext(null) around the call? — It works but is fragile and global-ish; anything the library posts back after you restore the context is now on the wrong thread.
  • Cost of the Task.Run workaround? — One pool thread for the duration plus a scheduling hop; acceptable on a click handler, not in a loop.
  • How do you catch this in CI? — A UI-context test that runs the library call under a single-threaded SynchronizationContext with a timeout; it fails fast on regression.

Common wrong answer

"Add .ConfigureAwait(false) where I call it." Your await is not the one capturing — the library internal awaits are, and you cannot reach them from outside.

principalWhat ConfigureAwait policy would you set for a codebase with libraries, a WPF client and an ASP.NET Core API?

Answer

Split the rule by project type and let tooling carry it. Shared library projects: ConfigureAwait(false) on every await, enforced with CA2007 as an error via a Directory.Build.props that targets library projects only. Application projects (API and WPF): CA2007 disabled, plain awaits, because the API has no context and the WPF app wants the context. Everywhere: VSTHRD002 as an error to ban .Result/.Wait(), with a documented escape hatch requiring a comment. I would write this in one page of the engineering handbook with the WPF deadlock as the worked example, because a rule people can derive is a rule they will follow when they meet a new case.

Example

// Directory.Build.props for src/Libraries/**
// <PropertyGroup>
//   <AnalysisMode>Recommended</AnalysisMode>
//   <WarningsAsErrors>$(WarningsAsErrors);CA2007;VSTHRD002;VSTHRD103</WarningsAsErrors>
// </PropertyGroup>

Follow-ups

  • What if a shared project is used only by the API today? — Treat it as a library anyway; "only used by X today" is exactly the assumption that breaks two years later.
  • How do you handle the existing violations? — Baseline them (analyzer suppression file or #pragma with a ticket) and enforce on new code, so the ratchet turns without a stop-the-world cleanup.
  • What is the one exception you would allow? — Test projects, where a deliberate context is sometimes part of the test.

Common wrong answer

"One rule everywhere — always ConfigureAwait(false)." It is wrong in the WPF app and it teaches the team a ritual instead of the model, so the first novel situation gets handled badly.

principalIs ConfigureAwait(false) still worth the noise in 2026?

Answer

In libraries yes, in applications no, and the trend is toward less of it, not more. The ecosystem has moved: ASP.NET Core has had no context for a decade, most new .NET code is server or console, and the per-await cost when no context exists is a flag check. What has genuinely changed the calculus is .NET 11 runtime async, which reduces async overhead broadly and — with the continuation change that skips ExecutionContext capture and restore when there is nothing to restore — removes some of the cost that motivated micro-optimising awaits in the first place. So my position is: keep it as a mechanical rule in shared libraries because the deadlock risk is real and asymmetric; drop it from application code because readability is worth more than a no-op; and revisit if you ever measure it mattering.

Example

// .NET 11 (preview 7 at time of writing): the runtime libraries themselves are built
// with runtime-async=on, and continuations skip ExecutionContext capture/restore when
// there is nothing to restore. Opt in per project:
// <PropertyGroup><Features>runtime-async=on</Features></PropertyGroup>

Follow-ups

  • Would you retro-fit it into an existing app codebase? — No; a mass edit adds churn and risk for a no-op, and reviewers stop reading diffs that big.
  • Any case where you would add it to app code? — A shared handler used by both the WPF client and the API, which is really library code wearing an app project name.
  • Does runtime async change the deadlock story? — No. Context capture semantics are unchanged; runtime async changes how suspension is implemented, not where continuations go.

Common wrong answer

"It is obsolete, nobody needs it any more." Say that in a shop that ships a WPF or MAUI client on top of shared libraries and you have just described a future incident.

05Cancellation

Cancellation is asked in almost every loop because it is where sloppy code shows immediately: a token accepted and never passed on, a catch that swallows OperationCanceledException, a timeout that leaks a timer. Mid-level candidates should know the source/token split and cooperative cancellation; senior candidates should know linked sources, registration lifetime and how cancellation interacts with disposal; principal candidates should be able to design a cancellation and timeout policy for a whole request path, including what must not be cancelled.

screenerHow does cancellation work in .NET? What are the roles of CancellationTokenSource and CancellationToken?

Answer

It is cooperative: nothing is forcibly aborted. The CancellationTokenSource owns the signal and is the only thing that can trigger it; it hands out lightweight CancellationToken structs to consumers, who either poll IsCancellationRequested, call ThrowIfCancellationRequested(), register a callback, or pass the token to an API that does one of those. When cancellation fires, cooperating code throws OperationCanceledException, which propagates as a canceled task. The split exists so that the ability to cancel (the source) is not accidentally handed to the code being cancelled (the token).

Example

using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
try
{
    await DoWorkAsync(cts.Token);
}
catch (OperationCanceledException) when (cts.IsCancellationRequested)
{
    // our timeout fired
}

async Task DoWorkAsync(CancellationToken ct)
{
    foreach (var item in items)
    {
        ct.ThrowIfCancellationRequested();       // cooperative check
        await ProcessAsync(item, ct);            // and flow it down
    }
}

Follow-ups

  • Why not Thread.Abort? — It never worked reliably and throws PlatformNotSupportedException on .NET Core and later; there is no safe way to interrupt arbitrary code.
  • Is CancellationToken expensive to pass? — No, it is a small struct wrapping a reference; passing it everywhere is free and expected.
  • Must you dispose the source? — Yes, especially timed ones: it holds a timer and the registration list.

Common wrong answer

"Cancelling the token kills the running task." Nothing is killed. If the callee never checks the token or never passes it down, the work runs to completion and your timeout is a lie.

midOperationCanceledException vs TaskCanceledException — which do you catch?

Answer

Catch OperationCanceledException. TaskCanceledException derives from it, and different APIs throw one or the other, so catching the derived type alone means you will miss some cancellations. The more important discipline is deciding whether you should catch at all: a cancellation that is expected (client disconnected, shutdown requested) should usually propagate so the framework can record it correctly, and only be caught where you are converting it into a domain outcome. Use an exception filter to distinguish "my timeout fired" from "my caller cancelled me", because those deserve different responses — a timeout is usually a 504 and a caller cancellation is usually nothing at all.

Example

try
{
    await CallDependencyAsync(linked.Token);
}
catch (OperationCanceledException) when (requestAborted.IsCancellationRequested)
{
    return;                                  // client went away: log at debug, do not alert
}
catch (OperationCanceledException)
{
    throw new TimeoutException("dependency exceeded 3s budget");   // our timeout
}

Follow-ups

  • Why does Task.Delay throw TaskCanceledException but ThrowIfCancellationRequested throw the base type? — Historical API choice; treat them as the same category and always catch the base.
  • What is OperationCanceledException.CancellationToken for? — It tells you which token caused it, which is how you attribute a cancellation when several are linked.
  • How should cancellation be logged? — At debug/information, not error; alerting on client disconnects is a classic source of alert fatigue.

Common wrong answer

"Catch TaskCanceledException, that is the one async throws." You will miss every ThrowIfCancellationRequested and every stream API that throws the base type, and the bug only appears under real cancellation.

midHow do you implement a timeout on an operation whose API takes a token?

Answer

Create a linked source that combines the caller token with a timeout, and pass its token down. CancellationTokenSource.CreateLinkedTokenSource plus CancelAfter — or the constructor that takes a TimeSpan — gives you a single token that fires on either. Dispose it, because it owns a timer and registrations on the parent. The important second half of the answer is attribution: after the await, check which token actually fired so you can report a timeout differently from a caller cancellation.

Example

using var linked = CancellationTokenSource.CreateLinkedTokenSource(ct);
linked.CancelAfter(TimeSpan.FromSeconds(3));

try
{
    return await _client.GetAsync(url, linked.Token);
}
catch (OperationCanceledException) when (!ct.IsCancellationRequested)
{
    throw new TimeoutException("GET exceeded 3s");    // ours, not the caller
}

Follow-ups

  • What about Task.WaitAsync(TimeSpan) (.NET 6+)? — It gives you a TimeoutException without a linked source, but it only stops waiting; the underlying work keeps running, so use it when abandoning is acceptable.
  • What if the API has no token parameter? — You cannot truly cancel it; wrap with WaitAsync to stop waiting, and understand you are leaking the operation until it finishes.
  • How do you test a timeout deterministically? — TimeProvider (.NET 8+) with FakeTimeProvider, or pass the delay in as configuration.

Common wrong answer

"Use Task.WhenAny(work, Task.Delay(3000))." It works but leaks: the delay task and its timer stay alive, the work continues unobserved, and exceptions from it are never seen. It is the pre-.NET 6 pattern people still copy.

seniorWhat is the lifetime trap with CancellationToken.Register?

Answer

The registration is held by the token source, so it keeps your callback — and everything the callback closure captures — alive for as long as the source lives. With a long-lived source (an application-lifetime token, a hosted service stopping token) and short-lived subscribers, that is a textbook memory leak: thousands of dead request objects rooted by one token. Always dispose the registration, normally with using, and be aware that Dispose on a registration whose callback is currently running blocks until it finishes — so callbacks must be short and must never take a lock the disposing thread holds.

Example

async Task<Response> SendAsync(Request r, CancellationToken ct)
{
    var tcs = new TaskCompletionSource<Response>(TaskCreationOptions.RunContinuationsAsynchronously);
    using var reg = ct.Register(static s => ((TaskCompletionSource<Response>)s!).TrySetCanceled(), tcs);
    _transport.Send(r, tcs);
    return await tcs.Task;      // reg disposed here, unrooting the callback
}

Follow-ups

  • What does the state-object overload buy you? — It avoids a closure allocation, which matters on hot paths; the static lambda plus state argument is the allocation-free form.
  • What happens if the token is already cancelled at registration? — The callback runs synchronously on the registering thread, so it must be safe to run inline.
  • Is there an async dispose? — Yes, DisposeAsync on CancellationTokenRegistration, which avoids blocking while a callback completes.

Common wrong answer

"Registrations clean themselves up when the token is cancelled." Only then — if the token is never cancelled, and application-lifetime tokens usually are not until shutdown, the callbacks accumulate for the whole process lifetime.

seniorWhat is CancellationTokenSource.CancelAsync and why was it added?

Answer

Added in .NET 8. Cancel() runs every registered callback synchronously on the calling thread, in order, and does not return until they are all done — so a slow or blocking callback stalls whoever called Cancel, and a callback that takes a lock the canceller holds deadlocks. CancelAsync() queues the callback invocation instead and returns a task you can await, which keeps the cancelling thread free. Use it wherever you cancel while holding a lock, from a UI thread, or when you do not control what the callbacks do — which in a large system is most of the time.

Example

// shutting down a component that may have arbitrary registrations
public async ValueTask DisposeAsync()
{
    await _cts.CancelAsync();          // .NET 8+: callbacks do not run on this thread
    await _pump.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);
    _cts.Dispose();
}

Follow-ups

  • Does CancelAfter have the same problem? — The timer callback path effectively calls Cancel, so callbacks run on a timer thread; keep them short regardless.
  • What order do callbacks run in? — Reverse order of registration, and an exception in one is collected into an AggregateException after the others run (with Cancel(false)).
  • Should library code prefer it? — Yes, as the default, since a library cannot know what callers registered.

Common wrong answer

"Cancel() just sets a flag." It sets a flag and synchronously invokes every registration — a fact that surfaces as a mysterious stall or deadlock during shutdown, which is exactly when nobody wants to debug.

midWhere does CancellationToken come from in an ASP.NET Core request, and what does it mean when it fires?

Answer

Model binding injects HttpContext.RequestAborted into any action or minimal-API handler parameter of type CancellationToken. It fires when the client disconnects — the browser tab closed, the load balancer gave up, the mobile app went to background — and, during shutdown, when the host stops accepting. Firing means "nobody is waiting for this response any more", so the right reaction is to stop doing expensive work and return; it does not mean an error occurred, and it should not page anyone. What it must never do is abort a write that has already partially committed something: cancellation belongs on reads and on the request path, not in the middle of a non-idempotent write.

Example

app.MapGet("/search", async (string q, ISearch s, CancellationToken ct) =>
    Results.Ok(await s.QueryAsync(q, ct)));       // ct == HttpContext.RequestAborted

// deliberately NOT cancellable: the payment must finish or compensate
app.MapPost("/pay", async (PayCmd c, IPayments p) => Results.Ok(await p.ChargeAsync(c, CancellationToken.None)));

Follow-ups

  • Does a canceled request still run middleware? — Unwinding continues, so logging and diagnostics middleware still see it; the status code recorded is typically 499-style or a client-abort marker depending on your host.
  • How do you combine it with your own timeout? — A linked source, as above; ASP.NET Core 8+ also ships a request timeouts middleware that does it for you per endpoint.
  • What about background work started from a request? — Never give it RequestAborted; give it the application lifetime token, or it dies as soon as the response is sent.

Common wrong answer

"Pass RequestAborted to everything, including the database write." Then a client that disconnects mid-write leaves you with a half-applied transaction and a support ticket. Deciding what is not cancellable is part of the answer.

seniorHow do you cancel work that is already in progress and not cooperative?

Answer

You cannot, in-process, safely. The honest options are: stop waiting for it (WaitAsync with a timeout) and accept that a thread or connection stays busy; give the work a hard external boundary such as a socket or command timeout that the driver enforces (SQL CommandTimeout, HttpClient.Timeout, a gRPC deadline); or move it out of process so you can kill a child process or let the remote side enforce its own deadline. At design level, the real answer is to make long operations chunked and checkpointed so there is always a safe cancellation point, rather than trying to interrupt a monolithic call.

Example

// stop waiting; the work continues but is no longer on our critical path
var task = _legacy.LongCallAsync();
try { return await task.WaitAsync(TimeSpan.FromSeconds(10), ct); }
catch (TimeoutException)
{
    _ = task.ContinueWith(t => _log.LogWarning(t.Exception, "abandoned legacy call"),
                          TaskContinuationOptions.OnlyOnFaulted);   // observe, do not leak
    throw;
}

Follow-ups

  • What is the risk of abandoning? — Resource exhaustion: abandoned calls still hold connections and memory, so an abandonment policy needs its own concurrency limit.
  • Does HttpClient cancellation actually abort the request? — Yes, it aborts the underlying connection/stream — one of the few places cancellation is genuinely enforced.
  • And a SQL query? — SqlCommand.ExecuteReaderAsync(ct) sends an attention signal to the server, so it does cancel server-side — a good example to name.

Common wrong answer

"Run it on a thread and abort the thread." Thread.Abort throws PlatformNotSupportedException on modern .NET, and even on .NET Framework it corrupted state — this answer marks a candidate as living in 2012.

seniorWhy does a CancellationToken parameter that you accept but never use fail code review?

Answer

Because the signature is a promise. A caller who sees a token parameter reasonably assumes that cancelling it stops the work; if you drop it, every timeout built on top of your method silently does nothing, and the failure appears far away — a request timeout that does not free the connection, a shutdown that hangs for two minutes. It is worse than not accepting a token at all, because it makes the wrong behaviour invisible. The mechanical rule I enforce: a token accepted must be flowed to every awaited call and checked in every loop; if the method genuinely cannot be cancelled, document that and do not accept one.

Example

// FAILS review: token accepted, promise broken
async Task<Rows> QueryAsync(string sql, CancellationToken ct) => await _db.QueryAsync(sql);

// correct
async Task<Rows> QueryAsync(string sql, CancellationToken ct) => await _db.QueryAsync(sql, ct);

Follow-ups

  • Can this be caught automatically? — Yes: CA2016 (forward the CancellationToken) plus VSTHRD103-family rules catch the common shapes.
  • What if the inner API has no token overload? — Check the token before and after, and say so in an XML comment; do not pretend.
  • Is CancellationToken.None ever right? — Yes, explicitly, for work that must not be interrupted — and writing None deliberately reads far better than dropping the parameter.

Common wrong answer

"It is harmless, the token is just ignored." It is the opposite of harmless: it converts a loud failure (no cancellation support) into a silent one (cancellation that appears to work).

principalDesign a timeout and cancellation policy for a request that fans out to five services.

Answer

I start from a single request budget — say 800 ms at the edge — and treat it as a deadline that is passed down, not a per-hop timeout that is re-set at each hop. Each call gets a linked token combining the caller token with the remaining budget, so a slow first hop shrinks what later hops may use, and nothing downstream can outlive the client. Per-dependency I set a limit below the remaining budget and classify each as required or optional: optional fan-out legs get a shorter deadline and degrade to a cached or empty result rather than failing the request. Retries come out of the same budget — a retry that exceeds it is pointless work — and I pair them with a circuit breaker so a dead dependency stops consuming budget at all. Finally, non-idempotent writes are excluded from cancellation and given a compensation path, because abandoning them is what turns a timeout into a data-integrity incident.

Example

var deadline = DateTimeOffset.UtcNow.AddMilliseconds(800);

async Task<T> CallAsync<T>(Func<CancellationToken, Task<T>> op, TimeSpan max, CancellationToken ct)
{
    var remaining = deadline - DateTimeOffset.UtcNow;
    if (remaining <= TimeSpan.Zero) throw new TimeoutException("budget exhausted");
    using var linked = CancellationTokenSource.CreateLinkedTokenSource(ct);
    linked.CancelAfter(remaining < max ? remaining : max);
    return await op(linked.Token);
}

Follow-ups

  • How do you propagate the deadline across the wire? — gRPC has real deadlines; over HTTP use a header (grpc-timeout-style or your own) and have each service honour it.
  • What do you do when the budget is exhausted before a required call? — Fail immediately with a clear timeout; starting a call you cannot afford wastes capacity on both sides.
  • How do you observe this? — Emit remaining-budget-at-hop as a span attribute; the histogram tells you which leg eats the budget long before customers do.

Common wrong answer

"Give every call a 5-second timeout." Per-hop timeouts multiply: five hops at five seconds is a 25-second worst case that no client waits for, and the retries on top make it worse. Budgets compose; timeouts do not.

06Exceptions, async void and fire-and-forget

Every loop has at least one question here, because error handling is where async code silently loses information. Interviewers want to see that you know exceptions travel on the task rather than the stack, that async void is a landmine with exactly one legitimate use, and that "fire and forget" is a design decision with a required checklist rather than a discard operator. Senior and principal candidates get the aggregation and observability variants: what WhenAll does with three failures, and how you make background failures visible.

midHow do exceptions propagate out of an async method?

Answer

They do not propagate on the calling stack. The generated state machine catches everything and calls builder.SetException, which puts the exception on the returned Task and faults it. The exception is re-thrown at the point where somebody awaits that task, with its original stack trace preserved via ExceptionDispatchInfo. Two consequences: an async method that is never awaited never reports its failure, and code that reads .Result or .Wait() instead of awaiting gets an AggregateException wrapper rather than the original exception type — which is why catch (SqlException) around .Result silently fails to catch.

Example

var t = FailAsync();          // does NOT throw here
try { await t; }              // throws InvalidOperationException here, original stack
catch (InvalidOperationException) { }

try { t.Wait(); }             // throws AggregateException wrapping it
catch (InvalidOperationException) { }   // NEVER hit

Follow-ups

  • What does await do with an AggregateException? — It unwraps and rethrows the first inner exception, which is why WhenAll awaits show only one of several failures.
  • Does the stack trace survive? — Yes, ExceptionDispatchInfo.Capture/Throw preserves it and appends the rethrow location; async frames appear thanks to [AsyncStateMachine] metadata.
  • Where do exceptions before the first await go? — Still onto the task, not the call site — which is why eager argument validation needs the non-async wrapper pattern.

Common wrong answer

"try/catch around the call catches it." Around the call it catches nothing; around the await it does. Candidates who get this wrong usually also write catch blocks that never fire in production.

midWhy is async void dangerous, and when is it correct?

Answer

An async void method returns nothing, so there is no task to await, no way to know when it finished, and — critically — nowhere for an exception to go. The state machine rethrows it on the captured SynchronizationContext, or on a thread-pool thread if there is none, where it becomes an unhandled exception that crashes the process. It also cannot be composed, tested by awaiting, or cancelled through its result. The one legitimate use is a top-level event handler whose signature is fixed by a framework — a WinForms/WPF click handler — and even there you wrap the body in try/catch. Everything else returns Task.

Example

// the only acceptable async void: fixed signature, body fully guarded
private async void OnSaveClick(object sender, RoutedEventArgs e)
{
    try { await _vm.SaveAsync(); }
    catch (Exception ex) { _log.LogError(ex, "save failed"); ShowError(ex); }
}

Follow-ups

  • What about async void in a test? — Never; xUnit and NUnit cannot await it, so the test passes before the assertions run. Use async Task.
  • Why does it crash rather than fault something? — There is no Task to fault, so the builder (AsyncVoidMethodBuilder) rethrows on the context, which reaches the unhandled-exception handler.
  • Can an analyzer find them? — Yes, VSTHRD100 flags async void outside event-handler signatures.

Common wrong answer

"Use async void for fire-and-forget work." It is the worst possible choice: a single unhandled exception takes the process down, and you have no handle to await during shutdown.

seniorWhat happens to exceptions when several tasks in a Task.WhenAll fail?

Answer

WhenAll waits for all of them regardless of failures, then returns a task faulted with an AggregateException containing every exception. But await unwraps that and rethrows only the first one, so a naive catch sees one failure and loses the rest — a real problem when three of five dependencies are broken and you only ever see the first. To get them all, catch and then inspect the task Exception property, whose InnerExceptions holds the full set. Also note that cancellation counts: if some tasks were cancelled and others faulted, the resulting task is faulted, and cancellation appears as OperationCanceledException among the inner exceptions.

Example

var all = Task.WhenAll(tasks);
try
{
    await all;
}
catch (Exception)
{
    foreach (var ex in all.Exception!.InnerExceptions)     // ALL of them
        _log.LogError(ex, "leg failed");
    throw;
}

Follow-ups

  • Does WhenAll stop early on the first failure? — No. If you want that, use a linked CancellationTokenSource that you cancel from the first failure, or WhenEach and abandon.
  • What about the results array when one fails? — You get no results at all; the task is faulted. Wrap each leg in its own try/catch if you want partial success.
  • How do you model partial success cleanly? — Have each leg return a result type (Result<T> / discriminated union) instead of throwing, so WhenAll always succeeds and you inspect the outcomes.

Common wrong answer

"await WhenAll throws an AggregateException." It throws the first inner exception — which is why the "we only ever see one dependency failing" bug is so common in fan-out code.

seniorWhat is an unobserved task exception, and does it still crash the process?

Answer

An unobserved exception is one on a faulted Task that nobody ever awaited or inspected before the Task was garbage collected. On .NET Framework 4.0 that terminated the process at finalization; since 4.5 the default changed and the exception is raised on TaskScheduler.UnobservedTaskException and otherwise swallowed — same on modern .NET. So it does not crash you, which is worse: failures vanish silently. The practical response is to subscribe to that event and log it at startup, treat any occurrence as a bug to fix rather than a condition to handle, and stop producing unawaited tasks in the first place.

Example

TaskScheduler.UnobservedTaskException += (_, e) =>
{
    _log.LogError(e.Exception, "unobserved task exception — find the unawaited task");
    e.SetObserved();     // keeps legacy ThrowUnobservedTaskExceptions configs from killing us
};

Follow-ups

  • When exactly does the event fire? — At finalization of the Task, so it can be seconds or minutes after the failure and with no useful context — another reason to prevent rather than monitor.
  • Can you re-enable the crash behaviour? — <ThrowUnobservedTaskExceptions>true</ThrowUnobservedTaskExceptions> in runtimeconfig; some teams do this in test environments to make the bug loud.
  • Does ConfigureAwaitOptions.SuppressThrowing observe it? — Yes, it marks the exception observed, which is why you must log deliberately when using it.

Common wrong answer

"Unobserved exceptions crash the app, so we would have noticed." That has been false since .NET Framework 4.5; assuming it is true is exactly how a fire-and-forget failure runs unnoticed for months.

seniorYou need genuine fire-and-forget work. What is your checklist?

Answer

Five items, and if I cannot satisfy them I do not fire and forget — I use a queue. One: never async void; keep the Task. Two: catch everything inside the work and log it, because nobody will await it. Three: hold the task somewhere so shutdown can await it, otherwise the host stops mid-write. Four: bound it — a concurrency limit or a channel, so a traffic spike does not create ten thousand in-flight operations. Five: do not capture request-scoped state (a scoped DbContext, an HttpContext, a request-scoped token), because it is disposed the moment the response is sent. In a service of any size the honest answer is usually "put it on a durable queue and let a consumer do it", because in-process fire-and-forget dies with the process.

Example

// minimum viable in-process background work
private readonly ConcurrentDictionary<Task, byte> _inFlight = new();

void FireAndForget(Func<CancellationToken, Task> work)
{
    var t = Task.Run(async () =>
    {
        try { await work(_appStopping.Token); }
        catch (OperationCanceledException) { }
        catch (Exception ex) { _log.LogError(ex, "background work failed"); }
    });
    _inFlight[t] = 0;
    _ = t.ContinueWith(x => _inFlight.TryRemove(x, out _), TaskScheduler.Default);
}

public Task StopAsync() => Task.WhenAll(_inFlight.Keys);   // drain on shutdown

Follow-ups

  • What does the discard _ = actually buy? — Only silence from the compiler warning; it does not observe exceptions or manage lifetime, so it is a documentation marker at best.
  • Is IHostedService a better home? — Yes for anything recurring: it gets lifetime, DI scope creation and graceful shutdown for free.
  • What about Channel<T> plus one consumer? — The standard in-process pattern: bounded, observable, one place to handle errors, and it applies natural backpressure.

Common wrong answer

"_ = DoWorkAsync(); and move on." It loses exceptions, loses shutdown, keeps request scope alive, and is unbounded — four production bugs in one line, and it is the single most common one in real codebases.

midWhat does try/finally around an await guarantee, and what does it not?

Answer

The finally runs whenever the method resumes and leaves the block — after success, after an exception, and after cancellation — because the compiler preserves the exception-handling structure across the state machine. What it does not guarantee is running at all: if the method suspends at the await and the continuation is never scheduled (the process is killed, or the awaited task never completes), the finally never executes. That is why cleanup that must happen — releasing a semaphore, returning a pooled buffer — is safe under normal flow but must not be your only defence against process death; that is what idempotency and external timeouts are for.

Example

await _gate.WaitAsync(ct);
try
{
    await WorkAsync(ct);      // throws, cancels, or completes
}
finally
{
    _gate.Release();          // runs in all three cases — but not if the process dies
}

Follow-ups

  • Can you await inside a finally? — Yes since C# 6, which is what makes await using and async disposal work.
  • What about await inside catch? — Also allowed since C# 6; before that people used flags and rethrows.
  • Does cancellation skip finally? — No: cancellation is an exception, so the normal unwinding rules apply.

Common wrong answer

"finally may not run after an await because the thread changed." The thread is irrelevant; the state machine carries the handler structure. The real risk is never resuming, which is a different failure.

seniorHow do you preserve a useful stack trace through async code?

Answer

Mostly the runtime does it for you: ExceptionDispatchInfo preserves the original trace across the await boundary, and async frames are reconstructed from [AsyncStateMachine] metadata. What ruins it is your own code: throw ex; instead of throw; resets the trace, catching and wrapping without an inner exception loses it, and eliding await in wrappers removes those frames entirely. In release builds inlining and the state-machine rewrite can still make traces confusing, which is why DOTNET_TieredPDB-style symbol availability and structured logging with correlation ids matter more than trace archaeology. Worth naming: .NET 11 runtime async makes live stacks dramatically cleaner — a three-deep async chain drops from about 13 frames to 5 — which helps profilers and debuggers, though caught-exception traces were already fine.

Example

catch (SqlException ex)
{
    throw new DataAccessException($"order {id} lookup failed", ex);   // keeps the inner trace
}
// never: catch (Exception ex) { throw ex; }   — resets the stack trace to here

Follow-ups

  • Why do async stacks look shallow? — Each suspension breaks the physical stack; what you see is reconstructed from continuation chains, which is exactly what runtime async improves.
  • Anything to add in production? — Structured logging with a correlation id and OpenTelemetry spans; a trace id beats a stack trace across service boundaries.
  • Does ContinueWith hurt traces? — Yes, it introduces scheduler frames and loses the logical chain — another reason to prefer await.

Common wrong answer

"Async loses stack traces, nothing you can do." Untrue since .NET Framework 4.5, and it usually signals someone who has been writing throw ex; for years.

midWhat does Task.WhenAny do with the tasks you did not observe?

Answer

Nothing — and that is the problem. WhenAny completes as soon as the first task completes and returns it; the others keep running, keep holding their resources, and if one of them faults later, nobody observes that exception. The two safe patterns are: keep the losers and await them (or at least attach a logging continuation) so failures are seen, and cancel them through a linked token if the work is abandonable. For the specific case of timeouts, prefer WaitAsync(TimeSpan) (.NET 6+) over the WhenAny-plus-Delay idiom, because it does not leave a timer task behind.

Example

using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
var tasks = mirrors.Select(m => m.FetchAsync(cts.Token)).ToList();

var winner = await Task.WhenAny(tasks);
await cts.CancelAsync();                       // stop the losers
foreach (var t in tasks.Where(t => t != winner))
    _ = t.ContinueWith(x => _log.LogDebug(x.Exception, "loser"), TaskScheduler.Default);

return await winner;                            // rethrows if the winner failed

Follow-ups

  • What if the first task to complete is the one that failed? — WhenAny returns it; you must decide whether to fail or to await the next one, which is why hedging logic usually loops rather than taking the first completion blindly.
  • Is WhenAny O(n) per call? — Yes, it registers continuations on all tasks each time; in a loop over many tasks prefer Task.WhenEach (.NET 9+).
  • Does it observe exceptions of the winner? — Only when you await the returned task; WhenAny itself never faults.

Common wrong answer

"WhenAny cancels the others." It has no idea they exist beyond waiting on them; the abandoned work is still consuming a connection and a thread-pool slot, and its exception is unobserved.

principalHow do you make background and async failures visible across a whole service?

Answer

I treat invisibility as the defect and design three layers. Prevention: analyzers ban async void and unawaited tasks, and any background work goes through one shared helper or a hosted service, so there is exactly one place errors can escape. Detection: subscribe TaskScheduler.UnobservedTaskException and AppDomain.UnhandledException to structured logging, and alert on their rate — any nonzero rate is a bug, not a condition. Attribution: every background operation runs inside its own Activity with the parent trace id, so a failure lands in the same trace as the request that scheduled it. Then a single dashboard panel: background operations started, completed, failed, and in-flight. The design principle is that a background operation with no metric is an operation that does not exist to operations.

Example

// one helper, one place for the telemetry
async Task RunBackgroundAsync(string name, Func<CancellationToken, Task> work, CancellationToken ct)
{
    using var activity = ActivitySource.StartActivity(name, ActivityKind.Internal);
    _started.Add(1, new KeyValuePair<string, object?>("op", name));
    try { await work(ct); }
    catch (OperationCanceledException) when (ct.IsCancellationRequested) { }
    catch (Exception ex)
    {
        activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
        _failed.Add(1, new KeyValuePair<string, object?>("op", name));
        _log.LogError(ex, "background {Op} failed", name);
    }
}

Follow-ups

  • What is the leading indicator before failures? — In-flight count and age of the oldest in-flight operation; a rising oldest-age catches stuck work that never fails.
  • How do you stop alert fatigue from cancellations? — Classify expected cancellation separately from failure, as in the catch filter above.
  • What would you require in a design review? — Every background operation names its failure mode, its bound, and its shutdown behaviour, in one sentence each.

Common wrong answer

"We log exceptions, so we would see it." Logging without a metric means nobody sees it until a customer complains; the answer that scores names the alertable signal, not the log line.

07Composition and concurrency control

Once you can write one async call, interviewers check whether you can orchestrate many: sequential versus concurrent, bounded versus unbounded, and how you fail. This is also where a lot of real performance work lives — the difference between an N+1 await loop and a bounded fan-out is often an order of magnitude. Expect a whiteboard exercise: "here is a list of 10,000 ids, call this API for each" is close to universal at senior level, and the grading is entirely about the bound.

midSequential awaits in a loop vs Task.WhenAll — when do you use which?

Answer

Sequential when the operations depend on each other, when order matters, when the target cannot take concurrent load, or when a shared resource (an EF Core DbContext, a single connection) forbids it. WhenAll when the operations are independent and the target can absorb the concurrency — then wall-clock time drops from the sum to roughly the maximum. The unstated third option, which is the one senior candidates are expected to reach for, is bounded concurrency: WhenAll over 10,000 items is not "fast", it is a denial-of-service attack on your own dependency and a memory spike on your own heap.

Example

// sequential: ~N * latency
foreach (var id in ids) results.Add(await GetAsync(id, ct));

// unbounded concurrent: ~max latency, but N in-flight calls
var results = await Task.WhenAll(ids.Select(id => GetAsync(id, ct)));

// bounded: the answer they want for large N
await Parallel.ForEachAsync(ids, new ParallelOptions
{
    MaxDegreeOfParallelism = 16,
    CancellationToken = ct
}, async (id, token) => bag.Add(await GetAsync(id, token)));

Follow-ups

  • What breaks with EF Core? — A DbContext is not thread-safe; concurrent queries on one context throw InvalidOperationException. Use a context per operation from a factory.
  • How do you pick the bound? — Little law against the dependency capacity, cross-checked with its connection pool — the same reasoning as sizing any concurrency limit.
  • Does WhenAll preserve order? — Yes, the results array matches the input task order, regardless of completion order.

Common wrong answer

"Always use WhenAll, it is faster." With 10,000 items you open 10,000 concurrent calls, exhaust the connection pool, get throttled or time out, and allocate 10,000 state machines at once. The bound is the answer, not the parallelism.

seniorHow do you throttle async work? Compare the main options.

Answer

Three tools, chosen by shape. Parallel.ForEachAsync (.NET 6+) is the default for "process this collection with at most N in flight": it handles the token, the degree of parallelism and the aggregation for you. A SemaphoreSlim around each task is the manual equivalent, and is right when the work is not a simple collection or when you need the permit held across a scope you control — it is easy to get wrong by acquiring outside the try. Channel<T> with N consumer loops is the right shape for a continuous stream rather than a batch, and gives you backpressure through a bounded channel. Above these, ASP.NET Core rate limiting (.NET 7+) is the right place for a limit that belongs to the endpoint rather than the algorithm.

Example

// manual throttling — note the acquire OUTSIDE try, release INSIDE finally
var gate = new SemaphoreSlim(16);
var tasks = ids.Select(async id =>
{
    await gate.WaitAsync(ct);
    try { return await GetAsync(id, ct); }
    finally { gate.Release(); }
});
var results = await Task.WhenAll(tasks);

Follow-ups

  • What is still unbounded in that snippet? — Memory: ids.Select(...) materialises N state machines and N tasks even though only 16 run. For very large N stream it with Parallel.ForEachAsync or a channel.
  • Does Parallel.ForEachAsync work over IAsyncEnumerable? — Yes, which makes it the natural fit for paged sources.
  • How does failure behave? — Parallel.ForEachAsync cancels the remaining work on the first exception and surfaces an AggregateException; WhenAll runs everything to completion.

Common wrong answer

"Use Parallel.ForEach with an async lambda." Parallel.ForEach takes an Action, so the async lambda becomes async void: it returns immediately, the loop "finishes" instantly, exceptions crash the process, and nothing is actually awaited.

seniorWhat is Task.WhenEach and what problem does it solve?

Answer

Added in .NET 9, it returns an IAsyncEnumerable<Task> that yields each task as it completes, so you can process results in completion order with a plain await foreach. Before it, the idiom was a list plus repeated Task.WhenAny and Remove, which is O(n²) in continuations and easy to get wrong. It matters whenever early results are useful — streaming partial results to a client, starting downstream work as soon as any leg lands, or logging progress on a long fan-out. Note it yields the task, not the result, so you still await each one to observe its outcome.

Example

await foreach (var completed in Task.WhenEach(tasks).WithCancellation(ct))
{
    try { yield return await completed; }        // stream results as they land
    catch (Exception ex) { _log.LogWarning(ex, "one leg failed, continuing"); }
}

Follow-ups

  • How did you do this before .NET 9? — var pending = tasks.ToList(); while (pending.Count > 0) { var t = await Task.WhenAny(pending); pending.Remove(t); ... } — correct but quadratic.
  • Does it stop on the first failure? — No; every task is yielded and you decide per task, which is what makes partial-success handling easy.
  • Can you combine it with a bound? — Yes, but it does not bound anything itself; start the tasks under a semaphore or a channel first.

Common wrong answer

"It is the same as WhenAll but faster." It changes the shape of the result — streaming versus batch — not the speed; the point is latency to first result, not total time.

midTwo independent calls: how do you overlap them, and what is the pitfall?

Answer

Start both, then await both — either by capturing the tasks and awaiting each, or with Task.WhenAll. The pitfall is that if you capture and then await a; await b; and a throws, you never await b, so its eventual failure is unobserved and its resources are abandoned. Task.WhenAll avoids that because it always waits for both. The second pitfall is thinking this overlaps work that shares a non-thread-safe resource — two queries on one DbContext will throw rather than overlap.

Example

var userTask  = _users.GetAsync(id, ct);
var ordersTask = _orders.GetAsync(id, ct);

// safe: both are awaited even if one fails
await Task.WhenAll(userTask, ordersTask);
return new Dto(await userTask, await ordersTask);   // already complete, just unwrapping

Follow-ups

  • Why await each task again after WhenAll? — To get typed results without indexing into an object[]; the tasks are already complete so it costs nothing.
  • What if one leg is optional? — Give it its own try/catch or a shorter deadline so a failure degrades rather than fails the request.
  • Does this help if both hit the same database? — Only if the connection pool has headroom; otherwise you have moved the queue rather than removed it.

Common wrong answer

"var a = await X(); var b = await Y(); runs them in parallel." It does not — that is strictly sequential, and it is the most common accidental latency bug in service code.

seniorHow would you implement a retry with backoff around an async call?

Answer

I would not implement it; I would configure it. In .NET 8+ the standard answer is Polly v8 through Microsoft.Extensions.Http.Resilience, wired into the HttpClient pipeline, giving retry with exponential backoff and jitter, a timeout, a circuit breaker and a bulkhead in one place with telemetry. If asked to hand-roll it, the essentials are: only retry idempotent operations, only on transient classifications (timeouts, 5xx, 429 with Retry-After) and never on 4xx; exponential backoff with jitter to avoid synchronised retry storms; a hard cap on attempts and on total elapsed time drawn from the request budget; and cancellation honoured during the delay. The failure mode to name unprompted is retry amplification: three layers each retrying three times is 27 calls to a dependency that is already struggling.

Example

builder.Services.AddHttpClient<IPricing, PricingClient>()
    .AddStandardResilienceHandler(o =>
    {
        o.Retry.MaxRetryAttempts = 3;
        o.Retry.BackoffType = DelayBackoffType.Exponential;
        o.Retry.UseJitter = true;
        o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);
        o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(8);
    });

Follow-ups

  • Where do you put the circuit breaker relative to the retry? — Breaker outside the retry, so a broken dependency stops the retries entirely instead of each attempt re-testing it.
  • How do you make a non-idempotent call retryable? — An idempotency key the server deduplicates on; without that, retrying a POST is a correctness bug.
  • What do you do with 429? — Honour Retry-After rather than your own backoff, and count it against the budget.

Common wrong answer

"Retry three times with Task.Delay(1000) on any exception." It retries validation errors, ignores cancellation during the delay, synchronises every client onto the same retry instant, and multiplies load exactly when the dependency is failing.

midWhat is wrong with ContinueWith, and what replaced it?

Answer

await replaced it. ContinueWith defaults to TaskScheduler.Current, not Default, so in a nested TPL or UI context the continuation can run somewhere you did not intend — a classic source of "works on my machine". It also does not unwrap nested tasks (you get Task<Task<T>> without .Unwrap()), it does not flow exceptions the way await does (you must inspect t.Exception yourself or leave it unobserved), and it makes the code read backwards. The only remaining uses are attaching a fire-and-forget observation to a task you are deliberately abandoning, and building library-level plumbing where you want explicit scheduler control — and even then pass TaskScheduler.Default explicitly.

Example

// legacy shape you will meet in old code
DownloadAsync(url).ContinueWith(t => Save(t.Result));   // scheduler? exceptions? nesting?

// modern
var data = await DownloadAsync(url);
Save(data);

Follow-ups

  • What does Unwrap() do? — Flattens Task<Task<T>> to Task<T>; needed with ContinueWith and Task.Factory.StartNew over async delegates.
  • Is TaskContinuationOptions.OnlyOnFaulted useful? — Yes, for the abandon-and-log pattern, and it is one of the few places ContinueWith still reads well.
  • Performance difference? — Marginal; the argument is correctness and readability, not speed.

Common wrong answer

"ContinueWith is the same as await but more explicit." The default scheduler difference alone makes it not the same, and the difference only shows up in a UI or nested-TPL context — that is, in production, not in your test.

seniorDesign an async producer/consumer pipeline. What do you reach for?

Answer

System.Threading.Channels, bounded. A bounded channel gives you backpressure for free: when the buffer is full, WriteAsync suspends the producer instead of growing the heap, which is the single most important property of a pipeline. I pick the bound from acceptable in-flight memory and latency, run N consumer loops reading with await foreach (var x in channel.Reader.ReadAllAsync(ct)), complete the writer on shutdown so consumers drain naturally, and make each consumer error-handle per item so one poison message does not stop the pipeline. TPL Dataflow is the older alternative and still fine for multi-stage graphs with per-block parallelism, but Channels is the modern default because it is simpler, faster and allocation-light.

Example

var channel = Channel.CreateBounded<WorkItem>(new BoundedChannelOptions(1_000)
{
    FullMode = BoundedChannelFullMode.Wait,       // backpressure, not drop
    SingleReader = false, SingleWriter = false
});

var consumers = Enumerable.Range(0, 8).Select(_ => Task.Run(async () =>
{
    await foreach (var item in channel.Reader.ReadAllAsync(ct))
        try { await HandleAsync(item, ct); }
        catch (Exception ex) { _log.LogError(ex, "item {Id} failed", item.Id); }
})).ToArray();

// shutdown
channel.Writer.Complete();
await Task.WhenAll(consumers);

Follow-ups

  • What are the FullMode options? — Wait (backpressure), DropOldest/DropNewest/DropWrite for load shedding — a deliberate choice, not a default.
  • How do you preserve ordering per key? — Partition by key hash into per-key channels or consumers, since a shared channel with N consumers has no ordering guarantee.
  • When would you use Dataflow instead? — Multi-stage graphs with different parallelism and buffering per stage, where the block model expresses it more directly.

Common wrong answer

"Use a ConcurrentQueue and a consumer loop with a delay." That is a polling loop with no backpressure and no completion signal: it burns CPU when idle, grows unboundedly under load, and cannot drain cleanly on shutdown.

principalA batch job calls an API for 1,000,000 records. Design it.

Answer

Three properties decide the design: it must be bounded in memory, bounded in concurrency, and resumable. Streaming from the source with IAsyncEnumerable keeps memory flat and independent of the record count. A bounded concurrency limit — derived from the dependency capacity, not from the record count — keeps the API alive, with the rate-limit response feeding an adaptive backoff. Resumability means checkpointing progress durably, so a crash at record 800,000 does not restart from zero, and processing must be idempotent because a checkpoint plus a retry inevitably reprocesses some records. On top of that: a dead-letter path for permanently bad records so one poison row does not stop the job, a progress metric with a rate so operators can see the ETA, and a kill switch. If the job needs to be fast rather than polite, the correct conversation is with the API owner about a bulk endpoint — a million single calls is usually the wrong shape regardless of how well you throttle.

Example

await Parallel.ForEachAsync(StreamRecordsAsync(from: checkpoint, ct),
    new ParallelOptions { MaxDegreeOfParallelism = 24, CancellationToken = ct },
    async (rec, token) =>
    {
        try
        {
            await _api.UpsertAsync(rec, token);           // idempotent by design
            await _checkpoint.AdvanceAsync(rec.Id, token); // durable, monotonic
        }
        catch (Exception ex) when (IsPermanent(ex))
        {
            await _deadLetter.WriteAsync(rec, ex, token);
        }
    });

Follow-ups

  • How do you checkpoint without a write per record? — Checkpoint per batch or per interval and accept replaying the window; that is exactly why idempotency is a prerequisite.
  • What if the API rate-limits you? — Honour Retry-After, reduce the degree of parallelism adaptively, and expose the current effective concurrency as a metric.
  • How would you run it at scale? — Shard by key range across workers with a lease per shard, so throughput scales and no two workers touch the same record.

Common wrong answer

"Load the ids into a list and Task.WhenAll in chunks of 10,000." Memory scales with the input, a crash loses everything, and chunked WhenAll stalls on the slowest item in every chunk — you get the worst of both bounded and unbounded.

principalWhen is unbounded concurrency actually acceptable?

Answer

When the fan-out is small and structurally fixed — three dependencies for a page render, two lookups for a DTO — because the bound is the code shape itself and adding a limiter is noise. The test I apply: can the number of concurrent operations grow with input, traffic or data? If yes, it needs a bound. There is also a legitimate case for deliberately unbounded fan-out behind an existing limit — if the endpoint already has a rate limiter and the per-request fan-out is fixed, the total is already bounded by concurrency times fan-out, and a second limiter just adds latency. What I would never accept is unbounded concurrency driven by user-supplied input size, which is a self-inflicted denial of service with a clean-looking one-liner.

Example

// fine: fan-out is fixed by the code
var u = GetUserAsync(id, ct); var p = GetPrefsAsync(id, ct); var f = GetFlagsAsync(id, ct);
await Task.WhenAll(u, p, f);

// not fine: fan-out is chosen by the caller
var all = await Task.WhenAll(request.Ids.Select(i => GetAsync(i, ct)));   // request.Ids: 50,000?

Follow-ups

  • How do you defend the second case without a limiter? — Validate and cap the input size at the edge; rejecting 50,000 ids with a 400 is better than serving it slowly.
  • Does the thread pool protect you? — Not for I/O-bound fan-out: 50,000 in-flight HTTP calls need no threads, so nothing pushes back until memory or the dependency gives out.
  • What is the review heuristic you would teach? — "Point at the number that bounds this." If nobody can, the code is unbounded.

Common wrong answer

"Always add a semaphore, unbounded is never OK." Blanket rules produce ceremony around three-way fan-outs and dull the team sense of when it actually matters — the judgment is what is being tested.

08ValueTask and allocation

Asked whenever the role involves libraries, high-throughput services or performance work. The signal interviewers look for is restraint: ValueTask is a specialised optimisation with a consumption contract, not a better Task. You should be able to state when it wins, state its three rules, and say honestly that you would default to Task and reach for ValueTask only with a benchmark. At principal level the question shifts to API design: what you would put on a public interface that others must implement.

midWhat is ValueTask<T> and why does it exist?

Answer

It is a struct that holds either an already-computed result, a Task<T>, or an IValueTaskSource<T>. It exists because Task<T> is a class: every call allocates one, even when the method completed synchronously from a cache. For a method called millions of times per second that hits a cache 95% of the time, that is a large amount of garbage for no benefit. ValueTask<T> makes the synchronous path allocation-free while still supporting the asynchronous path by wrapping a Task. Introduced in .NET Core 2.0 and used throughout the BCL — Stream.ReadAsync, Channel, Socket — precisely because those are hot paths with frequent synchronous completion.

Example

public ValueTask<byte[]> ReadAsync(string key, CancellationToken ct)
{
    if (_cache.TryGetValue(key, out var hit)) return new ValueTask<byte[]>(hit);  // 0 allocations
    return new ValueTask<byte[]>(LoadFromDiskAsync(key, ct));                    // wraps a Task
}

Follow-ups

  • Is it always cheaper? — No: on the asynchronous path it wraps a Task and is a larger struct to copy, so a method that almost always suspends is better off returning Task.
  • Where is it in the BCL? — Stream.ReadAsync(Memory<byte>), ChannelReader.ReadAsync, IAsyncEnumerator.MoveNextAsync, ValueTask-based socket APIs.
  • Does it help with ValueTask non-generic? — Yes, same idea for methods with no result, e.g. DisposeAsync.

Common wrong answer

"It is a struct so it never allocates." On the async path it still wraps a heap object; the win is confined to synchronous completion, and claiming otherwise shows you have not measured it.

seniorWhat are the consumption rules for ValueTask, and what happens if you break them?

Answer

Three rules: await it exactly once; do not await it concurrently from two places; and do not read .Result before it completes. The reason is that a ValueTask may be backed by a pooled IValueTaskSource that is recycled after its result is read, with a token to detect misuse. Breaking the rules yields either an InvalidOperationException or — much worse — a result belonging to a completely different operation, because the backing object has already been handed to someone else. If you need to await something twice, store it, or call AsTask() once and use the resulting Task freely.

Example

// WRONG: two awaits of one ValueTask
ValueTask<int> vt = source.ReadAsync(ct);
var a = await vt;
var b = await vt;                 // undefined: may throw, may return another operation result

// right, if you must reuse it
Task<int> t = source.ReadAsync(ct).AsTask();
var a2 = await t;
var b2 = await t;                 // Tasks are freely re-awaitable

Follow-ups

  • Can you store a ValueTask in a field? — Do not; it is meant to be awaited immediately at the call site. Convert with AsTask() if it must outlive the expression.
  • Can you use it with WhenAll? — Not directly; Task.WhenAll takes Tasks, so you call AsTask() — which allocates and undoes the benefit, a good reason not to use ValueTask for fan-out APIs.
  • Is ValueTask.CompletedTask safe to reuse? — Yes, the default-constructed and completed forms carry no pooled source.

Common wrong answer

"It behaves like a Task, you can await it as many times as you want." That is the bug that produces cross-request data leakage in a pooled-source implementation — one of the nastiest classes of bug you can ship.

seniorWhen would you choose Task over ValueTask in a new API?

Answer

By default, always — and I would switch only with a benchmark showing the allocation matters. Task is the right choice when the method almost always completes asynchronously, when callers will want to store, cache, combine or await the result more than once, when the API is used with WhenAll/WhenAny, and when the API is public and used by people who will not read the consumption rules. ValueTask earns its place on very hot paths with a high synchronous-completion rate, typically inside a library. There is also an asymmetry that matters for public interfaces: going from ValueTask to Task is a breaking change, so choosing ValueTask speculatively locks in a constraint on every implementor.

Example

// Task: composed, stored, awaited by many callers
public Task<Order> GetOrderAsync(int id, CancellationToken ct);

// ValueTask: hot, usually cache-hit, awaited immediately at one call site
internal ValueTask<Segment> ReadSegmentAsync(int index, CancellationToken ct);

Follow-ups

  • What is the measurable threshold? — There is no universal one; run BenchmarkDotNet with [MemoryDiagnoser] at your real hit rate and look at allocated bytes per operation and gen0 rate.
  • Does ValueTask help with GC pauses specifically? — It reduces gen0 pressure; whether that shows up as a latency improvement depends on how close you already were to a collection budget.
  • What about IAsyncEnumerable? — MoveNextAsync already returns ValueTask<bool>, so async streams get the benefit without you choosing.

Common wrong answer

"Use ValueTask everywhere, it is strictly better." It is strictly more constrained, marginally larger to copy, awkward with combinators, and a trap for callers — the "everywhere" answer signals cargo-culting rather than measurement.

seniorWhat is IValueTaskSource and when would you implement it?

Answer

It is the interface that lets a ValueTask be backed by a reusable object rather than a Task, so a component can serve many operations with zero allocations by pooling one source per in-flight operation. Implementing it by hand is genuinely hard — you must get the token/version protocol, continuation scheduling and ExecutionContext flow right — which is why the runtime provides ManualResetValueTaskSourceCore<T> to embed in your type. I would implement it only in genuinely hot infrastructure — a custom transport, a pooled connection, a high-frequency channel — where profiling shows Task allocation dominating, and never in application code. Naming it correctly in an interview is usually enough; being able to say why you would avoid it is the better signal.

Example

sealed class Op : IValueTaskSource<int>
{
    private ManualResetValueTaskSourceCore<int> _core;    // struct, mutable: never copy it

    public ValueTask<int> Task => new(this, _core.Version);
    public void Complete(int result) => _core.SetResult(result);

    int IValueTaskSource<int>.GetResult(short token)
    {
        var r = _core.GetResult(token);
        _core.Reset();                                     // recycle for the next operation
        return r;
    }
    ValueTaskSourceStatus IValueTaskSource<int>.GetStatus(short token) => _core.GetStatus(token);
    void IValueTaskSource<int>.OnCompleted(Action<object?> c, object? s, short t,
        ValueTaskSourceOnCompletedFlags f) => _core.OnCompleted(c, s, t, f);
}

Follow-ups

  • What is the token for? — Version stamping: if a caller awaits a stale ValueTask after the source was recycled, the mismatched token is detected instead of returning someone else result.
  • Where does the BCL use it? — Sockets, Channel, pipelines and Stream implementations — anywhere per-operation allocation would dominate.
  • Cheaper alternative? — AsyncOperation-style pooling in your own code, or simply accepting the Task allocation until a profile says otherwise.

Common wrong answer

"You implement it whenever you want a ValueTask." You do not — new ValueTask<T>(result) and wrapping a Task cover 99% of cases; reaching for the interface without a profile is how subtle cross-operation bugs get shipped.

midWhat allocates in a typical async call, and how do you find out?

Answer

On the synchronous fast path, ideally nothing: the state machine struct stays on the stack and a cached completed task is returned. On the suspending path you pay for the boxed state machine, the Task object, the continuation delegate (plus a closure if the lambda captures), the ExecutionContext copy, and any CancellationTokenRegistration. Closures are the sneaky one — a lambda capturing a local inside a loop allocates per iteration. You find all of this with BenchmarkDotNet plus [MemoryDiagnoser] for microbenchmarks, and with dotnet-counters gen0 rate plus a dotnet-trace allocation profile in a running service.

Example

// allocates a closure per call (captures 'id')
ct.Register(() => _log.LogInformation("cancelled {Id}", id));

// allocation-free: static lambda + state object
ct.Register(static s => ((State)s!).Log(), state);

Follow-ups

  • Does async allocate if the method never awaits? — It still builds a state machine and, for Task, returns a Task; the compiler warns (CS1998) precisely because you should drop async.
  • How much does a boxed state machine cost? — Tens of bytes depending on hoisted locals; the number matters only relative to your throughput, which is why you measure rather than guess.
  • What is changing here? — .NET 11 runtime async reuses continuation objects more aggressively and avoids saving unchanged locals, reducing allocation in async-heavy code.

Common wrong answer

"Async allocates one object per await, so avoid awaits." The fix is to avoid unnecessary async on hot synchronous paths, not to avoid await — and closures usually cost more than the state machine anyway.

seniorWhat is [AsyncMethodBuilder] and PoolingAsyncValueTaskMethodBuilder?

Answer

[AsyncMethodBuilder] lets you tell the compiler which builder type to use for an async method or for a custom awaitable return type — the extensibility point behind custom task-like types. The one that matters in practice is PoolingAsyncValueTaskMethodBuilder, which pools the state machine objects for async ValueTask methods so even the suspending path avoids per-call allocation. You opt in per method with the attribute, or process-wide with the DOTNET_TieredPGO-style runtime config switch System.Threading.Tasks.ValueTaskPoolingEnabled. It is a real win in high-frequency infrastructure and a pointless complication elsewhere; pooling also means the object is reused, so the ValueTask consumption rules become even more important.

Example

[AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))]
async ValueTask<int> ReadHotAsync(CancellationToken ct)
{
    return await _pipe.ReadAsync(ct);      // state machine object comes from a pool
}

Follow-ups

  • What is the risk? — Pooled objects amplify any misuse of the ValueTask; a double-await now reads a recycled object rather than a dead one.
  • Does it help for async Task? — No, the pooling builders are for ValueTask; Task results are observable and re-awaitable, which prevents recycling.
  • Is C# 10 AsyncMethodBuilder on methods the same feature? — Yes, C# 10 extended the attribute from types to individual methods, which is what makes the per-method opt-in above possible.

Common wrong answer

"Turn on ValueTask pooling globally, it is free performance." It changes lifetime semantics for every async ValueTask method in the process, including third-party code that may await sloppily; that is an opt-in-per-hot-path decision.

midHow do you benchmark async code properly?

Answer

BenchmarkDotNet, with the benchmark method returning Task or ValueTask so the harness awaits it rather than you blocking inside. Turn on [MemoryDiagnoser] because allocation is usually the story, and be explicit about whether you are measuring the synchronous fast path or the suspending path — mixing them produces a meaningless average. Avoid real I/O in a microbenchmark: the variance swamps the difference you are looking for, so stub the dependency and measure the async machinery. And separate the microbenchmark question ("is this method cheaper") from the system question ("does the service get faster"), because they routinely disagree and only the second one pays.

Example

[MemoryDiagnoser]
public class Bench
{
    [Benchmark(Baseline = true)]
    public Task<int> WithTask() => _svc.TaskVersionAsync(42);

    [Benchmark]
    public ValueTask<int> WithValueTask() => _svc.ValueTaskVersionAsync(42);
}

Follow-ups

  • Why not measure with a Stopwatch in a loop? — Tiered JIT, no warm-up, no statistical treatment: the numbers are noise, and typically wrong by more than the effect size.
  • How do you benchmark under concurrency? — You do not, in BenchmarkDotNet; use a load generator against the real service and read latency percentiles.
  • What confounds async benchmarks most? — Hit rate. Reporting one number for a method that is 95% synchronous hides the entire effect you were trying to show.

Common wrong answer

"Call .Result inside the benchmark method to keep it simple." That measures blocking, adds thread-pool interaction to every iteration, and can deadlock under a harness sync context — the result tells you nothing about the async path.

principalYour service spends 30% of CPU in GC and the heap is dominated by async machinery. What do you do?

Answer

First I would confirm the attribution, because "async machinery" is often a proxy for closures, boxed tokens and logging allocations that sit next to the state machines in a profile. A dotnet-trace allocation profile or a dump with allocation stacks tells you the actual top types. Then I would work in order of leverage: remove async from methods that never suspend (the CS1998 candidates and thin wrappers), switch the hottest cache-hit paths to ValueTask, remove closure allocations in registrations and lambdas, and only then consider pooled builders. In parallel I would check the non-async suspects — string formatting in hot logs, LINQ in loops, large short-lived buffers that belong in ArrayPool — since those frequently outweigh everything async. Finally, the configuration lever: server GC and, where appropriate, DATAS, which changed heap behaviour meaningfully in recent releases. The principle is that I want a measurement between every two steps, because allocation work is exactly where intuition is least reliable.

Example

// dotnet-trace collect -p PID --providers Microsoft-DotNETCore-SampleProfiler
// dotnet-counters monitor -p PID System.Runtime
//   alloc-rate, gen-0-gc-count, gc-heap-size, time-in-gc
// then: is the top allocating type a state machine, a closure, or a string?

Follow-ups

  • What is the fastest big win in practice? — Usually removing async from hot methods that never actually suspend, and eliminating per-call closures — both are cheap and low-risk.
  • When would you say "do not optimise this"? — When GC time is high but latency meets SLO and headroom is adequate; 30% of an underused CPU may cost nothing worth engineering time.
  • How would you protect the win? — An allocation regression test in CI on the hot path, so the next refactor does not quietly undo it.

Common wrong answer

"Convert everything to ValueTask." It is a broad change with a consumption contract attached, it will not touch the closure and string allocations that usually dominate, and it makes the API harder for every caller — for a win you have not yet located.

09IAsyncEnumerable and async streams

Async streams come up whenever the role touches data pipelines, paged APIs, gRPC streaming or server-sent events. Interviewers test two things: whether you understand that the sequence is lazy and pull-based, and whether you know how cancellation flows into an iterator, which is the one genuinely fiddly part of the API. At senior level expect a design question about streaming versus buffering, and at principal level a question about where streaming stops being worth its complexity.

midWhat is IAsyncEnumerable<T> and when do you reach for it?

Answer

It is the asynchronous counterpart of IEnumerable<T>, introduced with C# 8: a pull-based sequence where advancing is itself awaitable, consumed with await foreach and produced with an async iterator that yield returns. You reach for it when items arrive over time or in pages and you do not want to buffer the whole set: reading a large query result row by row, following a paged HTTP API, consuming a message stream, or producing a response the client can start rendering immediately. The alternative — Task<List<T>> — is simpler and correct when the set is small and bounded; streaming buys flat memory and time-to-first-item, at the cost of holding a connection or cursor open for longer.

Example

async IAsyncEnumerable<Order> StreamOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    var page = 0;
    while (true)
    {
        var batch = await _api.GetPageAsync(page++, ct);
        foreach (var o in batch.Items) yield return o;
        if (!batch.HasMore) yield break;
    }
}

await foreach (var order in StreamOrdersAsync(ct)) Handle(order);

Follow-ups

  • When does the method body first run? — At the first MoveNextAsync, not at the call: async iterators are lazy, unlike ordinary async methods.
  • Can you use LINQ on it? — Yes: System.Linq.AsyncEnumerable shipped in the BCL with .NET 10, replacing the third-party System.Linq.Async package for most uses.
  • What does MoveNextAsync return? — ValueTask<bool>, so per-item enumeration is allocation-free on synchronous items.

Common wrong answer

"It is a push stream like an observable." It is pull-based: the consumer controls the pace, which is exactly why it gives you natural backpressure and why it is not a replacement for IObservable/Rx.

seniorHow does cancellation flow into an async iterator, and what is [EnumeratorCancellation]?

Answer

There are two places a token can enter: the iterator method parameter, captured when the method is called, and GetAsyncEnumerator(CancellationToken), which the consumer supplies via WithCancellation(ct) at enumeration time. They are different moments, and by default the second one is not visible inside your iterator body. [EnumeratorCancellation] on the parameter tells the compiler to wire them together: the token passed to GetAsyncEnumerator is combined with the one passed at call time, and the parameter inside the body sees the combination. Without the attribute, a consumer calling WithCancellation gets no cancellation at all — the classic silent bug in this area.

Example

// producer: attribute is what makes WithCancellation work
async IAsyncEnumerable<Row> ReadAsync([EnumeratorCancellation] CancellationToken ct = default)
{
    await using var reader = await _db.OpenReaderAsync(ct);
    while (await reader.ReadAsync(ct)) yield return reader.Map();
}

// consumer
await foreach (var row in ReadAsync().WithCancellation(ct)) Use(row);

Follow-ups

  • What if the caller passes a token both ways? — The compiler-generated code creates a linked source, so either firing cancels the enumeration.
  • Is WithCancellation the same as ConfigureAwait? — No; both return configurable wrappers, and you can chain .WithCancellation(ct).ConfigureAwait(false).
  • What happens on cancellation mid-enumeration? — MoveNextAsync throws OperationCanceledException and DisposeAsync still runs, so await using inside the iterator cleans up.

Common wrong answer

"Just take a CancellationToken parameter, that is enough." Without the attribute, WithCancellation silently does nothing — the consumer believes it can cancel and cannot, which is the worst kind of bug because it looks correct.

midWhat does await using do, and when do you implement IAsyncDisposable?

Answer

await using calls DisposeAsync() and awaits it, so cleanup that involves I/O — flushing a buffer, sending a close frame, committing or rolling back a transaction, draining a consumer loop — does not block a thread and does not get skipped. You implement IAsyncDisposable when disposal genuinely needs to await something; if it does not, plain IDisposable is simpler and cheaper. A type that owns async resources usually implements both, with the synchronous path either doing a best-effort cleanup or being unsupported, and DI containers cooperate: the Microsoft container disposes IAsyncDisposable services asynchronously when the scope is disposed asynchronously.

Example

public sealed class Pump : IAsyncDisposable
{
    private readonly CancellationTokenSource _cts = new();
    private readonly Task _loop;

    public async ValueTask DisposeAsync()
    {
        await _cts.CancelAsync();
        await _loop.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);  // drain
        _cts.Dispose();
    }
}

Follow-ups

  • Why does DisposeAsync return ValueTask? — Disposal is frequently synchronous in practice, so the fast path should not allocate.
  • What if a caller uses using instead of await using? — Your synchronous Dispose runs, which may block or skip cleanup; analyzer CA2213/CA1816-adjacent rules and code review are the defence.
  • Does await foreach dispose the enumerator? — Yes, it calls DisposeAsync on the enumerator, including when you break out early.

Common wrong answer

"DisposeAsync is just Dispose with async in the name." The difference is whether cleanup that awaits actually completes; a synchronous Dispose that fires an async flush and returns loses data at shutdown.

seniorStreaming vs buffering a large result set: how do you decide?

Answer

The trade is memory and time-to-first-byte against resource hold time and error semantics. Streaming keeps memory flat regardless of size and lets the client start work immediately, which is why it is right for large or unbounded results. But it holds a database cursor, connection or HTTP response open for the whole duration, it makes transactions long-lived, and — importantly — it means you have already sent a 200 and part of the body when a failure occurs halfway, so you cannot cleanly signal an error. Buffering is correct when the set is small and bounded, when you need to transform or validate the whole set before responding, or when a clean failure mode matters more than memory. My rule: stream when size is driven by data, buffer when size is driven by design, and always cap either way.

Example

// streams: response starts immediately, memory flat, connection held
app.MapGet("/orders", (IOrders o, CancellationToken ct) => o.StreamAsync(ct));

// ASP.NET Core 10: Server-Sent Events, for a live feed rather than a JSON array
app.MapGet("/metrics", (IMetrics m, CancellationToken ct) =>
    TypedResults.ServerSentEvents(m.StreamAsync(ct), eventType: "metric"));

Follow-ups

  • How do you report an error mid-stream? — An in-band error item or a trailer; over gRPC, a status trailer. Decide the contract before you stream, not during an incident.
  • What about EF Core? — AsAsyncEnumerable() streams and holds the connection; ToListAsync() buffers and releases it. Streaming inside a long transaction is a lock-duration problem.
  • Does streaming help p99? — It improves time-to-first-byte; total time is usually unchanged or slightly worse.

Common wrong answer

"Stream everything, it is always more scalable." Streaming trades memory for held connections; a thousand concurrent streamed queries can exhaust a connection pool that a thousand buffered ones would not.

seniorWhat are the gotchas of async iterators?

Answer

Four in practice. Laziness: nothing runs until the first MoveNextAsync, so eager validation needs a non-iterator wrapper, exactly as with sync iterators. You cannot yield return inside a try that has a catch — only try/finally — so per-item error handling has to be structured around the yield. Disposal is real work: if the consumer breaks early, DisposeAsync runs the finally blocks, and a consumer that abandons the enumerator without disposing leaks the cursor. And the cancellation wiring needs [EnumeratorCancellation]. A fifth, more subtle one: an iterator that awaits inside a lock-like scope cannot exist, and one that holds a transaction across yields makes the transaction as long as the consumer is slow.

Example

async IAsyncEnumerable<Row> ReadAsync([EnumeratorCancellation] CancellationToken ct)
{
    await using var reader = await OpenAsync(ct);
    try
    {
        while (await reader.ReadAsync(ct))
            yield return Map(reader);          // legal: try/finally only
    }
    finally
    {
        _metrics.RecordStreamClosed();         // runs on break, cancel or completion
    }
}

Follow-ups

  • How do you handle a per-item failure then? — Wrap the mapping in a method with its own try/catch and yield a result object, or filter and log outside the iterator.
  • Does await foreach with break dispose properly? — Yes; the compiler emits the async dispose in a finally.
  • What about testing them? — Enumerate with a cancellation token and assert the finally ran; a test that only reads the first item will not exercise disposal.

Common wrong answer

"You can try/catch around a yield return like normal code." It does not compile with a catch, and candidates who have never hit it usually have not written a real streaming producer.

midHow do you convert between IAsyncEnumerable<T>, Task<List<T>> and channels?

Answer

ToListAsync() from System.Linq.AsyncEnumerable (in the BCL since .NET 10; previously the System.Linq.Async package) materialises a stream — with the obvious caveat that you have just reintroduced unbounded memory unless you also apply Take. Going the other way, a channel reader exposes ReadAllAsync(ct) which is already an IAsyncEnumerable<T>, so a channel is the natural bridge from push-shaped producers (events, callbacks) to pull-shaped consumption. To go from a stream to a channel — usually to decouple a slow consumer from a producer that must not be blocked — write a pump into a bounded channel and accept the buffering that implies.

Example

// stream -> list, with an explicit cap so it stays bounded
var first1000 = await source.Take(1000).ToListAsync(ct);

// push -> pull: event source into an async stream
var ch = Channel.CreateBounded<Tick>(256);
feed.OnTick += t => ch.Writer.TryWrite(t);              // drops when full: a choice
await foreach (var tick in ch.Reader.ReadAllAsync(ct)) Handle(tick);

Follow-ups

  • What is lost bridging push to pull? — Either backpressure (if you drop) or producer independence (if you block); a bounded channel forces you to state which.
  • Is System.Linq.AsyncEnumerable a full LINQ? — It covers the common operators and, in .NET 11, gains join improvements alongside the sync ones; niche operators may still need Rx or hand-written code.
  • How do you test an async stream? — Produce from an array with ToAsyncEnumerable(), or hand-write a small iterator with controlled delays.

Common wrong answer

"ToListAsync the stream and work with the list." That discards the reason you streamed; if the source is unbounded it is also how you turn a memory-safe design into an out-of-memory crash.

principalWhen is streaming the wrong abstraction for an API you own?

Answer

When the consumer cannot act on partial results, when errors must be signalled cleanly, or when the operational cost of long-lived connections exceeds the memory it saves. A REST endpoint that streams 50 items has bought nothing and made retries, caching and error codes harder: a partially delivered 200 cannot become a 500. Streaming also fights with proxies, gateways and client libraries that buffer anyway, so the benefit sometimes does not survive the network path. My default for public APIs is pagination — bounded, cacheable, resumable, trivially retryable — and I reserve streaming for genuinely continuous data (events, logs, metrics, model output) or for internal high-volume paths where I control both ends. The senior-level nuance is that pagination and streaming solve the same memory problem, but only pagination composes with HTTP caching and idempotent retries.

Example

// public: paginate — cacheable, retryable, resumable
GET /orders?cursor=eyJpZCI6MTAwfQ&limit=100   -> { items: [...], nextCursor: "..." }

// internal or continuous: stream
GET /events (SSE)  or  rpc Subscribe(Filter) returns (stream Event)

Follow-ups

  • Cursor or offset pagination? — Cursor: stable under concurrent inserts and cheap for the database; offset degrades badly at depth.
  • What breaks with SSE behind a proxy? — Response buffering and idle timeouts; you need explicit flushing and periodic keep-alive comments.
  • How do you let a client resume a stream? — A resume token in each item (SSE Last-Event-ID, or your own cursor), which effectively makes it pagination with a long poll.

Common wrong answer

"Streaming is strictly better than pagination, it is more modern." Pagination is what makes an API cacheable and retryable; choosing streaming for a small bounded result set is complexity with no payoff.

10Async in ASP.NET Core

If the role is server-side .NET, this sub-area is where the abstract async knowledge is cashed out against a real host. Interviewers probe the request lifecycle, scoped service lifetime across awaits, what happens on client disconnect, and how the server behaves when it runs out of threads. Lead and principal candidates get the capacity version: how many concurrent requests this instance can hold, and what limits it.

midWhat happens to a request while it awaits in ASP.NET Core?

Answer

The thread is returned to the pool and the request stays alive as state: the HttpContext, the DI scope, the response object and the open connection remain, but no thread is associated with them. When the awaited operation completes, a pool thread picks up the continuation and finishes the request — possibly a different thread each time. That is the whole scalability argument: an instance can hold tens of thousands of in-flight requests with a few dozen threads, because in-flight cost is memory and sockets, not threads. It is also why blocking is so damaging here: one blocked request now costs a scarce thread instead of cheap memory.

Example

app.MapGet("/order/{id}", async (int id, IOrders orders, CancellationToken ct) =>
{
    var o = await orders.GetAsync(id, ct);   // no thread held during the DB round trip
    return o is null ? Results.NotFound() : Results.Ok(o);
});

Follow-ups

  • Is HttpContext safe to use after an await? — Yes within the request, because it is not thread-affine; but never after the response completes, and never captured into background work.
  • What limits in-flight requests then? — Memory, sockets, Kestrel limits (MaxConcurrentConnections) and the capacity of whatever you call downstream.
  • Does IHttpContextAccessor still work after an await? — Yes, it is backed by AsyncLocal, so it flows with the logical call.

Common wrong answer

"The request thread waits for the database." That is the sync model. If a candidate says this, everything they subsequently say about scaling the service will be wrong in the same direction.

seniorWhat is the scoped-service lifetime trap with background work started from a controller?

Answer

A scoped service — DbContext, a unit of work, anything registered AddScoped — is disposed when the request scope ends, which is when the response completes. If you start background work that captures one, that work continues after disposal and throws ObjectDisposedException, usually intermittently and usually in production, because whether you win the race depends on timing. The fix is to create your own scope for the background work from IServiceScopeFactory and resolve fresh instances inside it, or better, hand the work to a hosted service or queue rather than starting it from a request at all.

Example

// BUG: _db is scoped and disposed when the response completes
_ = Task.Run(async () => await _db.Audit.AddAsync(entry));

// correct: own scope, own instances, app lifetime token
_ = Task.Run(async () =>
{
    using var scope = _scopeFactory.CreateScope();
    var db = scope.ServiceProvider.GetRequiredService<AppDb>();
    await db.Audit.AddAsync(entry, _appStopping.Token);
    await db.SaveChangesAsync(_appStopping.Token);
});

Follow-ups

  • Why does it sometimes work in dev? — Low latency means the background work often finishes before the response does; the race only loses under load.
  • Is IServiceScopeFactory a singleton? — Yes, so it is safe to capture from any lifetime, unlike a scoped provider.
  • What is the better structural answer? — IHostedService with a Channel<T>: the request enqueues, the hosted service owns scope, lifetime and error handling.

Common wrong answer

"Register the DbContext as a singleton to avoid disposal." Now you have a shared, non-thread-safe context across concurrent requests — you traded an intermittent disposal error for data corruption and hard-to-reproduce concurrency exceptions.

midWhere does the CancellationToken in an action method come from, and what should you do when it fires?

Answer

It is HttpContext.RequestAborted, bound automatically by model binding for any CancellationToken parameter. It fires on client disconnect and during host shutdown. The right reaction is to stop doing work and unwind: pass it to reads and to expensive computation, let the OperationCanceledException propagate, and log at debug rather than error. The judgment part is deciding what should ignore it — writes that must complete or be compensated, audit records, and any operation where a partially applied change is worse than a wasted one. Those get CancellationToken.None explicitly, with a comment saying why.

Example

// ASP.NET Core 8+: per-endpoint request timeout middleware, on top of RequestAborted
builder.Services.AddRequestTimeouts(o =>
    o.AddPolicy("fast", new RequestTimeoutPolicy { Timeout = TimeSpan.FromSeconds(2) }));

app.MapGet("/search", async (string q, ISearch s, CancellationToken ct) =>
    Results.Ok(await s.QueryAsync(q, ct))).WithRequestTimeout("fast");

Follow-ups

  • How do you tell disconnect from your own timeout? — Compare against the specific source with an exception filter, as in unit 05.
  • Should cancellations count against your error SLO? — No; classify them separately or your availability metric will track client behaviour rather than your service health.
  • Does cancellation roll back a database transaction? — The command is cancelled and the transaction is rolled back on dispose — which is precisely why cancelling mid-write needs deliberate thought.

Common wrong answer

"Catch the cancellation and return a 500." You have turned a client hanging up into a paged alert and an error-budget burn; the client is not there to read your 500.

seniorHow do you run recurring or queued background work in ASP.NET Core?

Answer

BackgroundService (an IHostedService) for anything that owns its own loop, with a PeriodicTimer for recurring work and a bounded Channel<T> for queued work handed over from requests. The three details that separate a working implementation from a broken one: create a DI scope per work item rather than resolving scoped services in the constructor; honour the stoppingToken so shutdown does not hang for the host timeout; and catch per item, because an exception escaping ExecuteAsync stops the service silently (and, since .NET 6, can bring down the host depending on BackgroundServiceExceptionBehavior). For anything that must survive a restart, the honest answer is that in-process is the wrong home — use a durable queue or a scheduler.

Example

public sealed class Worker(IServiceScopeFactory scopes, ChannelReader<Job> jobs, ILogger<Worker> log)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in jobs.ReadAllAsync(stoppingToken))
        {
            using var scope = scopes.CreateScope();
            try { await scope.ServiceProvider.GetRequiredService<IHandler>().RunAsync(job, stoppingToken); }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested) { throw; }
            catch (Exception ex) { log.LogError(ex, "job {Id} failed", job.Id); }   // do not kill the loop
        }
    }
}

Follow-ups

  • What is the default shutdown timeout? — 30 seconds for the host (HostOptions.ShutdownTimeout); work that cannot finish in it is killed, so long jobs need checkpointing.
  • Why does ExecuteAsync need an await before any long loop? — Because the host awaits it synchronously until the first yield; a fully synchronous prologue delays startup of everything after it.
  • Multiple instances behind a load balancer? — Recurring work needs a lease or a distributed lock, or every instance runs the job.

Common wrong answer

"Fire a Task.Run from the controller and forget it." It dies with the request scope, dies with a deployment, has no retry and no visibility — and in a rolling deploy you lose whatever was in flight on every pod.

seniorWhere does connection-pool exhaustion look exactly like thread-pool starvation, and how do you tell them apart?

Answer

Both present as rising latency with low CPU and a growing backlog, because in both cases requests are queueing for a scarce resource. The difference is which counter moves. Starvation shows thread count climbing steadily and thread-pool queue length rising. Pool exhaustion shows thread count flat and healthy, but a spike in the driver own counters — active connections at the pool maximum, and timeouts phrased as "Timeout expired. The timeout period elapsed prior to obtaining a connection from the pool", which is a distinctive message worth memorising. The usual root causes are also different: starvation comes from blocking, exhaustion comes from leaked connections, long transactions, or a concurrency limit above the pool size.

Example

// SqlClient counters that separate the two
// dotnet-counters monitor -p PID Microsoft.Data.SqlClient.EventSource
//   active-hard-connections, number-of-active-connections, number-of-free-connections
// Default Max Pool Size is 100 per distinct connection string.

Follow-ups

  • How does a connection leak happen in async code? — A DbConnection or DbDataReader not disposed on an exception path, or a streamed query the consumer abandons without disposing the enumerator.
  • Should you just raise Max Pool Size? — Only after checking the database can take the extra concurrency; otherwise you move the queue onto the server and make everyone slower.
  • Does async make exhaustion more likely? — It can: async lets you have far more requests in flight, so a pool that was implicitly bounded by thread count is now the binding limit.

Common wrong answer

"Low CPU and slow requests means thread-pool starvation." It is one of at least three explanations, and fixing the wrong one wastes the incident; the counters are what distinguish them.

midIs it worth making every controller action async?

Answer

Async is right for any action that does I/O, which in a real service is nearly all of them. It is not automatically right for an action that only reads from memory, returns a constant, or does pure CPU work — there the state machine is overhead and adds nothing, and an async method with no awaits produces CS1998 for exactly that reason. The nuance interviewers like: the benefit is not per-action but per-instance, so a single blocking action in an otherwise async service can starve the pool for everything else. So the practical policy is "async wherever there is I/O, and no blocking anywhere", rather than "async everywhere" as a style rule.

Example

// no I/O: keep it synchronous, no state machine
app.MapGet("/health", () => Results.Ok(new { status = "ok" }));

// I/O: async
app.MapGet("/orders/{id}", async (int id, IOrders o, CancellationToken ct) => Results.Ok(await o.GetAsync(id, ct)));

Follow-ups

  • What about an action that is CPU-heavy? — Keep it synchronous but bound its concurrency, or move it out of the request path entirely; wrapping it in Task.Run changes nothing on a server.
  • Does an async action cost measurable throughput on a trivial endpoint? — Slightly, and it is visible in a synthetic benchmark of a no-op endpoint; it is irrelevant next to any real I/O.
  • Does the framework care? — No; MVC and minimal APIs handle both, and returning Task<IResult> or IResult are equally supported.

Common wrong answer

"Make it async so it does not block the thread" — said about an in-memory lookup. Nothing was going to block; the answer reveals a rule applied without a model.

principalHow many concurrent requests can one instance of your service handle, and what limits it?

Answer

I would answer with a model rather than a number. In-flight requests cost memory (the HttpContext, DI scope, buffers, and whatever the handler holds), a socket, and a slot in whatever downstream resource they are waiting on — but not a thread while they are awaiting. So the ceiling is usually the smallest of: memory divided by per-request footprint, the downstream concurrency limit (connection pool, dependency rate limit), Kestrel connection limits, and the file-descriptor limit on the host. Threads only become the constraint if something blocks. I would derive the estimate from measurement — run a load test and read per-request memory and the first counter to saturate — and then set an explicit admission limit slightly below it, so that exceeding capacity produces fast 503s rather than a slow collapse. That last part is the point: the number matters less than making the failure mode bounded.

Example

// admission control: fail fast above the modelled ceiling
builder.Services.AddRateLimiter(o =>
{
    o.GlobalLimiter = PartitionedRateLimiter.CreateChained(
        PartitionedRateLimiter.Create<HttpContext, string>(_ =>
            RateLimitPartition.GetConcurrencyLimiter("global",
                _ => new ConcurrencyLimiterOptions { PermitLimit = 2_000, QueueLimit = 200 })));
    o.RejectionStatusCode = StatusCodes.Status503ServiceUnavailable;
});

Follow-ups

  • How do you find per-request memory? — Load test at two concurrency levels and take the slope of working set against in-flight requests; the intercept is your baseline.
  • Why 503 rather than queueing? — A queue longer than the client timeout produces work nobody will read; rejecting keeps latency honest and lets the load balancer route elsewhere.
  • What changes with HTTP/2 or HTTP/3? — Many streams multiplex over one connection, so connection counts stop being a proxy for concurrency and stream limits become the thing to tune.

Common wrong answer

"It is limited by the thread pool, so around 32 concurrent requests." That is the sync-era model. In an async service threads are not the constraint, and this answer usually accompanies a proposal to raise MinThreads.

11Async synchronization primitives

Asked when the role involves shared state, caches or coordination. The core test is whether you know that classic thread-affine primitives cannot be used across an await, and whether you can pick the right async-compatible replacement without inventing one. Senior candidates should be able to talk about reentrancy, fairness and the cache-stampede problem; principal candidates should be able to argue for designs where the lock is not needed at all.

midWhich synchronization primitives work with async code, and which do not?

Answer

Work with async: SemaphoreSlim.WaitAsync (the general-purpose async mutex when constructed with count 1), Channel<T> for handing work between producers and consumers, Interlocked and Volatile for lock-free atomics, and the concurrent collections for simple shared state. Do not work: lock/Monitor, Mutex, ReaderWriterLockSlim, and anything else that is thread-affine, because the continuation may run on a different thread than the one that acquired. ManualResetEventSlim and CountdownEvent block, so they are wrong in async code even though nothing prevents you from calling them; their async equivalents are a TaskCompletionSource and Task.WhenAll respectively.

Example

// async mutex
private readonly SemaphoreSlim _mutex = new(1, 1);

// async manual-reset event, built from a TCS
private volatile TaskCompletionSource _ready = new(TaskCreationOptions.RunContinuationsAsynchronously);
public Task WaitUntilReadyAsync() => _ready.Task;
public void SignalReady() => _ready.TrySetResult();

Follow-ups

  • What about System.Threading.Lock (.NET 9)? — A faster dedicated lock type that the lock statement now targets, but still synchronous and thread-affine; it does not help async code.
  • Is Interlocked safe across awaits? — Yes, it operates on memory, not on thread identity — which makes it ideal for counters in async code.
  • Is there an async reader/writer lock in the BCL? — No; Nito.AsyncEx and Microsoft.VisualStudio.Threading provide one, or you build it on semaphores — but first check whether you actually need it.

Common wrong answer

"Use lock and just do not await inside it." Fine until someone adds an await two refactors later, or calls a method that blocks on async internally. The primitive should make the mistake impossible, not rely on discipline.

seniorWhat are the pitfalls of SemaphoreSlim as an async lock?

Answer

Four. It is not reentrant, so a method that acquires and then calls another method that acquires the same semaphore deadlocks itself — and unlike Monitor, there is no thread identity to detect it. The release must be in a finally, or a single exception permanently loses a permit and the service degrades to a total hang. It is not fair by default in the sense that waiters are released in FIFO order but a synchronous Wait and an async WaitAsync mix badly, so pick one. And it must be disposed, though the common bug is the opposite — disposing it while waiters are pending, which throws for them.

Example

// the shape that survives review
await _gate.WaitAsync(ct);          // acquire OUTSIDE the try
try
{
    return await CriticalAsync(ct);
}
finally
{
    _gate.Release();                // exactly one release per acquire
}

Follow-ups

  • Why acquire outside the try? — If WaitAsync throws (cancellation), you never acquired, so releasing in finally would over-release and corrupt the count.
  • How do you make per-key locking? — A ConcurrentDictionary<TKey, SemaphoreSlim> with careful cleanup, or a striped array of semaphores indexed by hash — simpler and leak-free.
  • What is the alternative to locking a cache? — Lazy<Task<T>> stored in a ConcurrentDictionary, so concurrent callers await the same in-flight task rather than serialising.

Common wrong answer

"Wrap the whole thing in try including the WaitAsync, and release in finally." Under cancellation that releases a permit you never took; the semaphore count drifts upward and the limit silently stops limiting.

seniorHow do you prevent a cache stampede in async code?

Answer

Store the task, not the value. When the first caller misses, it puts a Lazy<Task<T>> (or the task itself) into the cache immediately, so every concurrent caller finds it and awaits the same in-flight operation instead of launching its own. Without that, a popular key expiring under load produces hundreds of simultaneous identical database calls — the stampede. The details that matter: use GetOrAdd with a Lazy so the factory runs once even though GetOrAdd may invoke it more than once; remove the entry if the task faults, or you cache a failure forever; and consider serving stale data while refreshing in the background, which converts a latency spike into a slightly stale answer. HybridCache in .NET 9+ provides exactly this stampede protection out of the box, and naming it is a good signal.

Example

private readonly ConcurrentDictionary<string, Lazy<Task<Value>>> _inflight = new();

Task<Value> GetAsync(string key, CancellationToken ct)
{
    var lazy = _inflight.GetOrAdd(key,
        k => new Lazy<Task<Value>>(() => LoadAsync(k, ct), LazyThreadSafetyMode.ExecutionAndPublication));

    var task = lazy.Value;
    _ = task.ContinueWith(t =>                          // never cache a failure
    {
        if (t.IsFaulted || t.IsCanceled) _inflight.TryRemove(key, out _);
    }, TaskScheduler.Default);
    return task;
}

Follow-ups

  • What is the cancellation subtlety? — A shared task must not be cancelled by one caller token; use CancellationToken.None for the shared load and let individual callers give up with WaitAsync.
  • Why Lazy rather than the task directly? — GetOrAdd can call the factory concurrently and discard losers; Lazy guarantees the expensive call happens once.
  • What does HybridCache add? — Stampede protection plus a two-level (in-memory and distributed) cache with serialization and tag-based invalidation, so you stop hand-rolling this.

Common wrong answer

"Lock around the cache miss." A global lock serialises every miss across all keys, converting a stampede into a queue — and if the load call is slow, the queue is now your latency for unrelated keys too.

midHow do you implement thread-safe lazy async initialisation?

Answer

Lazy<Task<T>> with LazyThreadSafetyMode.ExecutionAndPublication: the factory that starts the async operation runs once, and every caller awaits the same task. That composes correctly because a Task can be awaited any number of times. The alternatives to know: AsyncLazy<T> from Nito.AsyncEx or Microsoft.VisualStudio.Threading is the same idea packaged; a SemaphoreSlim plus double-checked field works but is more code and easier to get wrong. The failure case to mention unprompted is a faulted initialisation being cached permanently — with Lazy you keep the failed task forever, so if retry matters you need to reset it explicitly.

Example

private readonly Lazy<Task<Config>> _config =
    new(() => LoadConfigAsync(CancellationToken.None), LazyThreadSafetyMode.ExecutionAndPublication);

public Task<Config> GetConfigAsync() => _config.Value;   // one load, many awaiters

Follow-ups

  • Why not AsyncLazy from the BCL? — There is none; the pattern is Lazy<Task<T>>, and the named types come from community or Microsoft threading libraries.
  • What about async initialisation in a constructor? — Not possible; use a static async factory method, or an InitializeAsync called by the host at startup.
  • How do you allow retry after failure? — Store the Lazy in a field you can replace with Interlocked.CompareExchange, or use the in-flight dictionary pattern that evicts faulted entries.

Common wrong answer

"Lazy<T> with an async factory that blocks on .Result." The factory runs under a lock, so a blocked async call inside it is a deadlock waiting for a context or a starvation source under load.

seniorWhat is Interlocked good for in async code, and where does it stop being enough?

Answer

It gives you atomic read-modify-write on a single memory location with no thread affinity, so it is perfect for counters, flags and single-reference swaps in async code — in-flight counts, one-shot initialisation with CompareExchange, cheap metrics. It stops being enough the moment an invariant spans more than one location: two counters that must agree, a value plus a version, a collection plus its count. At that point you need either a lock (and therefore no awaits inside), an immutable snapshot swapped atomically with CompareExchange, or a single-owner design such as a channel consumer where only one logical thread mutates the state at all. The third option is the one I would push for in a design review, because it removes the concurrency problem instead of managing it.

Example

// atomic one-shot initialisation, no lock, safe across awaits
private Config? _config;
void Publish(Config c) => Interlocked.CompareExchange(ref _config, c, null);

// immutable snapshot swap: readers never lock, writers replace the whole graph
private ImmutableDictionary<string, Rule> _rules = ImmutableDictionary<string, Rule>.Empty;
void Replace(ImmutableDictionary<string, Rule> next) => Volatile.Write(ref _rules, next);

Follow-ups

  • Do you need volatile as well? — Interlocked operations already imply the necessary barriers; Volatile.Read/Write is for plain field access you want ordered.
  • Is Interlocked.Increment cheap? — Cheap but not free, and it becomes a contention point under high concurrency; per-core or striped counters help at extreme rates.
  • What about ConcurrentDictionary? — Thread-safe per operation, but composite operations still need care — GetOrAdd may run your factory more than once.

Common wrong answer

"Interlocked makes the whole method thread-safe." It makes one operation atomic. Multi-field invariants built out of individual atomics are a classic source of races that only appear under load.

principalWhen would you design shared state away instead of protecting it?

Answer

Whenever the contention is on the critical path or the invariant spans several fields, because locks are correct but they do not scale and they do not compose. The usual moves: partition by key so each partition has a single owner and no cross-talk; funnel mutations through one consumer (a channel or actor) so the state is single-threaded by construction and readers get immutable snapshots; make the state immutable and swap it atomically; or push the state out to a system built for concurrency — a database with the right isolation level, or a distributed cache with compare-and-swap. The trade is real: single-owner designs add a queue and therefore latency and a backpressure decision, and immutable snapshots add allocation. I would take that trade when the state is hot, and keep a simple lock when it is not — the mistake is applying either universally.

Example

// single-owner: no lock exists because only one consumer mutates
var commands = Channel.CreateBounded<Command>(1024);

_ = Task.Run(async () =>
{
    var state = State.Empty;                                   // owned by this loop alone
    await foreach (var cmd in commands.Reader.ReadAllAsync(ct))
    {
        state = Apply(state, cmd);                             // no synchronisation needed
        Volatile.Write(ref _snapshot, state);                  // readers see an immutable snapshot
    }
});

Follow-ups

  • What is the cost of the single-owner pattern? — Throughput is capped by one consumer, and you must decide what happens when the queue fills; partition by key when one owner is not enough.
  • How do you keep read-your-writes semantics? — Return a completion task from the command, so the caller can await the effect of its own mutation.
  • When is a plain lock still the right call? — Cold paths, small critical sections, and code where the extra machinery would cost more in comprehension than it saves in contention.

Common wrong answer

"Lock-free is always better." Lock-free code is harder to prove correct, and a naive lock-free rewrite of a multi-field invariant is worse than the lock it replaced. The judgment is about where contention actually is.

Docs: SemaphoreSlim · HybridCache

12Diagnosing async in production

This sub-area is what senior and principal interviews use to separate people who have operated a service from people who have only written one. Nobody expects command-line perfection; they expect a sequence — hypothesis, signal, tool, conclusion — and familiarity with the specific counters and stack shapes that async problems produce. Answers that name tools and what they would show score far above answers that describe the problem again in more words.

seniorWhat tools do you reach for when an async service misbehaves in production?

Answer

dotnet-counters first, because it is live, cheap and answers the "which resource is saturated" question in seconds. dotnet-dump plus dotnet-dump analyze when I need stacks — clrthreads and parallel stacks show blocked threads immediately, and dumpasync reconstructs pending async state machines, which is the async-specific superpower. dotnet-trace when I need timing or allocation attribution rather than a snapshot. dotnet-stack for a quick look without a full dump. And underneath all of it, structured logs plus OpenTelemetry traces, because in a distributed system the answer is often "the time is somewhere else" and only a trace will show that.

Example

// dotnet-counters monitor -p PID System.Runtime Microsoft.AspNetCore.Hosting
// dotnet-dump collect -p PID
// dotnet-dump analyze core_dump
//    > clrthreads          how many, and what are they doing
//    > dumpasync -stacks   pending async operations, with their continuations
//    > syncblk             contended monitors

Follow-ups

  • What does dumpasync give you that clrthreads does not? — Async work that is pending with no thread attached: exactly the operations that are invisible in a thread-based view.
  • Can you do this in a container? — Yes; ship the diagnostic tools in the image or use the sidecar/ephemeral-container pattern, and make sure the process is not PID 1 without a signal handler.
  • What is the cheapest always-on signal? — Counters exported to your metrics backend; a dump is a last resort because it pauses the process.

Common wrong answer

"Add more logging and redeploy." In an ongoing incident that is a 20-minute round trip for information a 5-second counter check would have given you — and it changes the system you are debugging.

seniorWhat does a starved thread pool look like in a memory dump?

Answer

A large number of threads — far more than ProcessorCount — with nearly identical stacks parked in a waiting primitive: Monitor.Wait, Task.Wait/GetAwaiter().GetResult(), SemaphoreSlim.Wait, ManualResetEventSlim.Wait or a native blocking call. The frames above the wait tell you the culprit, and in a starvation case they are usually the same method repeated dozens of times, because every request took the same bad path. Two supporting signals: the thread-pool work queue holds a large backlog, and dumpasync shows many pending async operations whose continuations cannot be scheduled. If instead the threads are few and idle, you are not starved — look at the connection pool or a downstream.

Example

// dotnet-dump analyze
//   > clrthreads
//     ... 187 threads
//   > parallelstacks
//     150 threads:
//        System.Threading.Monitor.Wait
//        System.Threading.Tasks.Task.SpinThenBlockingWait
//        MyApp.Repos.OrderRepo.Get(Int32)          <-- the blocking call
//        MyApp.Controllers.OrderController.Get(Int32)

Follow-ups

  • How do you get a dump without killing the pod? — dotnet-dump collect pauses briefly rather than terminating; schedule it during the incident and copy it out before the pod is recycled.
  • What if the blocking is inside a third-party library? — The stack still names it; the mitigation is a bulkhead around that library until it can be replaced.
  • Is high thread count alone conclusive? — No; a legitimately high-concurrency blocking workload also has many threads. The identical stacks plus the queue backlog are what make it conclusive.

Common wrong answer

"Look at CPU in the dump." A dump is a snapshot with no time dimension; CPU comes from counters or a trace, and expecting it from a dump signals unfamiliarity with the tool.

midWhich counters do you watch for async health, and what does each tell you?

Answer

Five from System.Runtime: threadpool-thread-count (steady growth means injection, i.e. starvation), threadpool-queue-length (backlog waiting for a thread), threadpool-completed-items-count (throughput — flat with a growing queue is the clearest starvation signature), monitor-lock-contention-count (lock contention), and alloc-rate plus time-in-gc for allocation pressure. From the host, current-requests and requests-per-second. Plus whatever your dependencies expose — the SQL connection-pool counters especially. The interpretation matters more than the list: rising queue with flat completions is starvation, rising in-flight with flat queue is a slow dependency.

Example

// export them permanently rather than only in an incident
builder.Services.AddOpenTelemetry().WithMetrics(m => m
    .AddRuntimeInstrumentation()          // thread pool, GC, exceptions
    .AddAspNetCoreInstrumentation()
    .AddHttpClientInstrumentation());

Follow-ups

  • What would you alert on? — Queue length sustained above a threshold, and thread count above a multiple of ProcessorCount; both are leading indicators of latency, not lagging.
  • Is threadpool-thread-count alone enough? — No; a spike during a burst is normal. It is the sustained climb with a growing queue that matters.
  • What about async-specific traces? — .NET 11 unified the async profiler event model across runtime-async and compiler-generated state machines, so tools get one consistent view.

Common wrong answer

"CPU and memory." They are the two counters that tell you least about an async problem — starvation shows low CPU and normal memory right up until the service falls over.

seniorHow do you find where an async operation is hanging?

Answer

A hang with no thread is invisible to thread-based tools, which is exactly why dumpasync exists: it walks the async state machines on the heap and reconstructs pending continuation chains, showing you which method is suspended and what it is waiting on. Before reaching for a dump, though, the cheap answer is usually timeouts: an operation with no timeout can hang forever, so instrument every external call with a deadline and the hang becomes a timeout with a stack. In distributed systems the fastest path is a trace with a span that never closes — it names the hop immediately. The systemic fix is that nothing should be able to hang indefinitely: every external call gets a timeout, every loop gets a cancellation check.

Example

// dotnet-dump analyze core_dump
//   > dumpasync -stacks
//     Pending async: MyApp.Sync.PushAsync
//       awaiting: System.Threading.SemaphoreSlim.WaitAsync   <-- permit never released
//       continuation: MyApp.Sync.RunBatchAsync

Follow-ups

  • Common causes of a permanent async hang? — A TaskCompletionSource never completed (a message that never arrives, a callback that fires on an error path you did not handle), a semaphore permit leaked by a missing finally, and a captured-context deadlock.
  • How do you catch it in testing? — Timeouts on every test and on every external call, plus a chaos test that drops responses.
  • What if the hang is in a third-party client? — Wrap it with WaitAsync and a deadline so it becomes a bounded failure you can retry or fail over.

Common wrong answer

"Attach a debugger and look at the threads." The hanging operation has no thread; the threads look perfectly healthy, which is why people conclude "nothing is wrong" while requests pile up.

midHow do you write reliable tests for async code?

Answer

Return Task from every async test — never async void, which the runner cannot await, so the test passes before its assertions run. Give every test a timeout so a hang fails fast instead of blocking the suite. Do not use real delays for timing: inject TimeProvider (.NET 8+) and drive it with FakeTimeProvider, so a test for a 30-second retry runs in milliseconds and deterministically. Control concurrency explicitly with a TaskCompletionSource you complete from the test, rather than sleeping and hoping. And test cancellation as a first-class case — pass an already-cancelled token and assert the exception — because that path is almost never exercised otherwise.

Example

[Fact(Timeout = 5_000)]
public async Task Retries_with_backoff_without_real_delays()
{
    var time = new FakeTimeProvider();
    var sut = new Client(_transport, time);

    var call = sut.SendAsync(_req, CancellationToken.None);   // suspends on the backoff delay
    time.Advance(TimeSpan.FromSeconds(30));                   // deterministic, instant

    Assert.Equal(3, _transport.Attempts);
    await call;
}

Follow-ups

  • How do you test a race deterministically? — Gate the participants on a TaskCompletionSource so the test decides the interleaving; do not Task.Delay and hope.
  • Should tests use ConfigureAwait(false)? — Irrelevant for modern xUnit, which has no sync context; older runners with one are exactly where blocking tests deadlocked.
  • What about testing for deadlocks? — Run the code under a single-threaded SynchronizationContext with a timeout; that is the environment where a capture-and-block bug fails.

Common wrong answer

"Use Task.Delay(100) to let the background work finish." That is the definition of a flaky test: it passes on your laptop, fails in CI under load, and gets marked as a known flake instead of fixed.

seniorHow do you correlate logs across async boundaries?

Answer

Never with thread ids — they change across awaits and are meaningless in async code. Use Activity and the W3C trace context: Activity.Current flows via ExecutionContext, so trace and span ids follow the logical operation across awaits, thread hops and even HTTP calls if you propagate the traceparent header. In practice that means OpenTelemetry instrumentation plus a logging provider that emits TraceId/SpanId on every entry, and ILogger.BeginScope for domain-level identifiers like tenant or order id. The one thing to watch is background work: if you start it without linking to the parent activity, its logs land in no trace at all, which is why the background helper should create a child activity explicitly.

Example

using var scope = _log.BeginScope(new Dictionary<string, object>
{
    ["OrderId"] = order.Id,
    ["TraceId"] = Activity.Current?.TraceId.ToString() ?? "none"
});

await ProcessAsync(order, ct);   // every log line inside carries both, on any thread

Follow-ups

  • Does the scope survive an await? — Yes, logger scopes are backed by AsyncLocal, which is exactly why they work where ThreadStatic would not.
  • What breaks correlation? — ExecutionContext.SuppressFlow, manual thread creation, and queue hops where you forget to carry the trace context in the message.
  • How do you correlate across a queue? — Put traceparent in the message headers and restore it in the consumer; most brokers and libraries have built-in propagators.

Common wrong answer

"Log the managed thread id." It changes at every await, so the same logical operation appears as several unrelated threads and two operations appear to be one — worse than no correlation at all.

principalWrite the runbook entry for "service is slow, CPU is low".

Answer

Three sections: triage, diagnose, mitigate. Triage in 60 seconds: is it one instance or all, did it start at a deploy, is a dependency also degraded — that alone resolves most incidents. Diagnose with the counters in a fixed order: thread-pool queue and thread count (starvation), dependency connection-pool counters and latency (exhaustion or a slow downstream), lock contention and GC. If none is conclusive, take a dump and run clrthreads, parallel stacks and dumpasync. Mitigate in parallel with diagnosis: roll back if it started at a deploy, shed load or scale out to protect the SLO, and raise MinThreads only as an explicitly temporary stopgap that must be reverted. Then the parts people forget: every step names the expected output so a tired on-call engineer can compare, and every incident ends with a specific follow-up ticket — the runbook is a living document, not an archive.

Example

// RUNBOOK: slow responses, low CPU
// 1. scope     one pod or all? recent deploy? dependency dashboards red?
// 2. counters  dotnet-counters monitor -p PID System.Runtime
//                queue-length rising + completed flat            -> starvation      -> step 4
//                thread-count flat + dependency latency high     -> downstream      -> step 5
//                lock-contention-count high                      -> contention      -> step 6
// 3. dump      dotnet-dump collect; analyze: clrthreads, parallelstacks, dumpasync
// 4. mitigate  roll back if deploy-correlated; scale out; MinThreads ONLY with a revert ticket
// 5. escalate  page the dependency owner with the trace id and the latency percentile
// 6. follow-up open a ticket naming the blocking call; link this incident

Follow-ups

  • How do you keep a runbook from rotting? — Reference it in the alert itself and require the on-call engineer to update it during the incident review; unreferenced runbooks are always stale.
  • What do you automate first? — The counter capture, so the data exists before a human logs in.
  • What is the most common actual cause in your experience? — A blocking call introduced in an otherwise async path, or a concurrency limit set above the downstream capacity.

Common wrong answer

A runbook that says "investigate the issue". If it does not name the command, the expected output and the branch, it is a title, not a runbook — and at 3 a.m. the difference is an hour.

13Lifetime, disposal and background work

Async work outlives the code that started it, and this sub-area is about owning that. Interviewers ask it when the role involves hosted services, message consumers or desktop apps with long-running operations. The signals they want: you know who owns a task, you know graceful shutdown is a design property rather than a framework feature, and you know that "it worked in dev" usually means the process never actually stopped under load.

midWhat does graceful shutdown mean for an async service, and how do you implement it?

Answer

It means: stop accepting new work, let in-flight work finish within a bounded time, flush anything buffered, and exit — without losing acknowledged work or leaving half-applied state. In .NET the host gives you the hooks: IHostApplicationLifetime exposes ApplicationStopping, and BackgroundService receives a stoppingToken that fires at the start of shutdown. Your part is to honour the token everywhere, to await your in-flight tasks rather than abandoning them, and to keep the total within HostOptions.ShutdownTimeout (30 seconds by default) because past that the host stops waiting. In Kubernetes the additional piece is the preStop hook and terminationGracePeriodSeconds: the pod must stop receiving traffic before it stops accepting work, or you drop live requests during every deploy.

Example

builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(45));   // must exceed the longest drainable unit

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    try
    {
        await foreach (var msg in _queue.ReadAllAsync(stoppingToken))
            await HandleAsync(msg, stoppingToken);
    }
    catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested) { }
    finally
    {
        await _sink.FlushAsync(CancellationToken.None);   // flush must NOT be cancellable
    }
}

Follow-ups

  • Why CancellationToken.None for the flush? — Shutdown already cancelled the work token; using it for cleanup means cleanup never runs, which is the classic shutdown data-loss bug.
  • What if shutdown exceeds the timeout? — The host stops waiting and the process exits; work in flight is lost, which is why long units need checkpointing.
  • How do you test it? — Send SIGTERM under load and assert no request errors and no lost messages; most teams discover their shutdown is broken only in production.

Common wrong answer

"The framework handles shutdown." It cancels a token and waits 30 seconds; whether that loses data is entirely determined by code you wrote.

seniorWho owns a Task, and why does the question matter?

Answer

Whoever is responsible for awaiting it, observing its exception, and ensuring it finishes before the process exits. An unowned task is a bug with three symptoms: exceptions vanish unobserved, shutdown does not wait for it, and nothing bounds how many exist. The design rule I apply is that every task has exactly one owner, and ownership is explicit in the code — a field, a collection the component drains on dispose, or a hosted service that owns its loop. When a component starts work, it also owns stopping it; when it hands work to a queue, ownership transfers to the consumer. The moment you cannot point at the owner, you have fire-and-forget with extra steps.

Example

sealed class Uploader : IAsyncDisposable
{
    private readonly CancellationTokenSource _cts = new();
    private readonly Task _loop;                      // owned: awaited on dispose

    public Uploader() => _loop = RunAsync(_cts.Token);

    public async ValueTask DisposeAsync()
    {
        await _cts.CancelAsync();
        await _loop.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);
        _cts.Dispose();
    }
}

Follow-ups

  • What about a task started in a static constructor? — Owned by nobody and unstoppable; move it to a hosted service so the host owns its lifetime.
  • Does the DI container help? — Yes: register the component and let scope disposal drive DisposeAsync, so ownership follows the container graph.
  • How do you review for this? — Look for every Task.Run and discard, and ask "who awaits this?" If nobody, it needs an owner or a queue.

Common wrong answer

"The garbage collector handles it." The GC will happily collect a faulted Task and swallow its exception; it has no concept of work that should have completed.

seniorWhat are the async pitfalls of IDisposable and DisposeAsync?

Answer

Three that bite. Blocking in Dispose to wait for async cleanup — _task.Wait() — reintroduces every deadlock and starvation problem at the worst possible time, during shutdown. Implementing only IDisposable on a type with async cleanup means the cleanup either blocks or silently does not happen, so a type with async resources should implement IAsyncDisposable and, if it must support both, make the synchronous path a documented best-effort. And disposal must be idempotent and race-safe, because a component can be disposed while an operation is in flight; the usual shape is cancel, then await the loop, then dispose the resources, in that order.

Example

// WRONG: blocks a pool thread during shutdown, can deadlock under a context
public void Dispose() { _cts.Cancel(); _loop.Wait(); _cts.Dispose(); }

// right
public async ValueTask DisposeAsync()
{
    if (Interlocked.Exchange(ref _disposed, 1) == 1) return;   // idempotent
    await _cts.CancelAsync();
    await _loop.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);
    _cts.Dispose();
}

Follow-ups

  • What if a consumer only calls Dispose? — Document it, and if the type cannot clean up synchronously, do not implement IDisposable at all so the mistake is a compile error rather than data loss.
  • Does the DI container call DisposeAsync? — Yes, when the scope or provider is disposed asynchronously; a synchronous disposal of a provider holding IAsyncDisposable services throws.
  • What about finalizers? — Never async, never useful here; they run on the finalizer thread with no ordering guarantees.

Common wrong answer

"Call DisposeAsync().GetAwaiter().GetResult() from Dispose for compatibility." It is sync-over-async in the one place where the thread pool is already draining — a reliable way to turn a clean shutdown into a hung pod.

midHow do you run periodic async work correctly?

Answer

PeriodicTimer (.NET 6+) inside a BackgroundService: WaitForNextTickAsync(ct) returns false on cancellation, so the loop is a plain while, there is no timer callback reentrancy, and the work runs sequentially by construction. The older System.Threading.Timer fires callbacks concurrently if the previous one has not finished, which is how a nightly job ends up running four copies of itself when the database is slow — and it takes an async void-shaped callback, so exceptions crash the process. Two details for real systems: each tick should catch its own exceptions so one failure does not stop the schedule, and multi-instance deployments need a lease so the job runs once globally rather than once per pod.

Example

using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));
while (await timer.WaitForNextTickAsync(stoppingToken))
{
    try { await ReconcileAsync(stoppingToken); }
    catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested) { throw; }
    catch (Exception ex) { _log.LogError(ex, "reconcile failed; will retry next tick"); }
}

Follow-ups

  • What if a tick takes longer than the period? — PeriodicTimer does not queue ticks; you simply get the next one late, which is usually what you want. If not, you need a scheduler with catch-up semantics.
  • How do you test the schedule? — .NET 8+ PeriodicTimer accepts a TimeProvider, so FakeTimeProvider makes it deterministic.
  • What about cron-shaped schedules? — Use a scheduler (Quartz, Hangfire) or an external trigger; hand-rolled cron in a loop is where time zones and DST bugs live.

Common wrong answer

"new Timer(async _ => await Work(), ...)." That is async void in a callback: overlapping executions, unobservable exceptions that crash the process, and no way to await it at shutdown.

seniorWhat happens to in-flight async work when the process is killed, and how do you design for it?

Answer

On SIGKILL, nothing runs: no finally, no DisposeAsync, no flush. On SIGTERM you get the graceful path, but only within the shutdown timeout. So any correctness that depends on code running after a failure point is not correctness — it is a hope. The design answers are the standard distributed-systems ones: make operations idempotent so a retry after a crash is safe; use at-least-once delivery with deduplication rather than pretending in-memory state survives; checkpoint long work so a restart resumes rather than restarts; and use the outbox pattern when a database write and a message must both happen. The interview-worthy framing is that graceful shutdown reduces the frequency of the problem, and idempotency is what actually solves it.

Example

// outbox: one transaction, so a crash cannot split the write from the message
await using var tx = await _db.Database.BeginTransactionAsync(ct);
_db.Orders.Add(order);
_db.Outbox.Add(new OutboxMessage(order.Id, "OrderCreated", payload));
await _db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
// a separate relay publishes outbox rows at-least-once and marks them sent

Follow-ups

  • How do you make a handler idempotent? — A dedupe key persisted with the effect, checked in the same transaction; without persistence it is not deduplication, it is a cache.
  • Where does the ack belong in a queue consumer? — After the effect is durable, never before — acking first converts a crash into silent data loss.
  • How do you verify any of this? — Kill pods under load deliberately (chaos testing) and assert the invariants; nothing else finds these bugs.

Common wrong answer

"We handle it in finally." finally does not run on SIGKILL, on an OOM kill, or when the node dies — and those are exactly the cases the question is about.

principalA team wants to run long jobs inside the API process. How do you respond?

Answer

I would ask what "long" means and what happens when the pod dies mid-job, because those two answers decide everything. In-process is fine for short, best-effort, idempotent work — sending a notification, warming a cache — where losing it on a deploy is acceptable and the code stays simple. It is the wrong home as soon as the job must survive a restart, must not run twice concurrently across replicas, needs retry with backoff, or takes longer than the shutdown grace period, because you would end up rebuilding a job system inside a web app: durability, leasing, retries, visibility. At that point the honest recommendation is a queue plus a worker, or a managed scheduler. I would also name the operational coupling that people forget: long jobs in the API process make deploys slow (you must drain them), make autoscaling wrong (CPU from jobs triggers scaling of the request tier), and make one bad job a latency incident for every user.

Example

// the boundary I would draw, written down in the design doc
// in-process  : < 5 s, idempotent, loss-tolerant, no cross-replica coordination
// queue+worker: everything else — durability, retries, leases, its own scaling and dashboard

Follow-ups

  • What if they say "we do not have a queue"? — A database-backed outbox or job table with a lease is a legitimate first step; the point is durability, not a specific broker.
  • How do you handle the migration pragmatically? — Keep the API endpoint, make it enqueue, and move the handler as-is into a worker; the change is small if the handler was already a service.
  • What is the cost of the queue approach? — Another deployable, another failure mode, and eventual consistency the API contract must express — real costs worth naming rather than hiding.

Common wrong answer

"Never run background work in the API." Absolutism loses credibility: plenty of short, loss-tolerant work belongs exactly there, and a rule with no boundary condition gets ignored the first time it is inconvenient.

14Internals: state machines, awaitables and schedulers

These are the ceiling questions — asked rarely, and usually only after you have answered everything else well, to find out where your understanding stops. Nobody is expected to recite IL. What is being checked is whether you know the extensibility points exist and can reason from them, which is what lets you debug something the documentation does not cover.

seniorWhat makes a type awaitable? Could you await something that is not a Task?

Answer

Awaitability is a compile-time pattern, not an interface. The compiler needs a GetAwaiter() method — instance or extension — returning a type that implements INotifyCompletion (or ICriticalNotifyCompletion) and exposes bool IsCompleted and T GetResult(). That is it. Which is why Task, ValueTask, Task.Yield() (which returns a YieldAwaitable), ConfiguredTaskAwaitable, WinRT operations and third-party types are all awaitable without sharing a base type. You can make your own — an extension method giving GetAwaiter() to TimeSpan so await TimeSpan.FromSeconds(1) compiles is the classic party trick — and you should almost never do it, because it hides what the code costs.

Example

public static TaskAwaiter GetAwaiter(this TimeSpan delay) => Task.Delay(delay).GetAwaiter();

await TimeSpan.FromSeconds(1);   // compiles — clever, and a bad idea in a real codebase

Follow-ups

  • Why ICriticalNotifyCompletion? — Its UnsafeOnCompleted skips ExecutionContext capture, because the async method builder has already captured it — an allocation and time saving on every await.
  • What does [AsyncMethodBuilder] add? — It lets a custom awaitable also be a valid async method return type, by naming the builder the compiler should use.
  • Where is this used legitimately? — IAsyncEnumerable, ValueTask, pooled builders, and framework types like SocketAsyncEventArgs-based awaitables.

Common wrong answer

"You can only await Task and ValueTask." True in practice, false in principle — and the follow-up about Task.Yield(), which returns neither, usually exposes it.

seniorWhat is a TaskScheduler and when would you use a custom one?

Answer

A TaskScheduler decides where and when queued tasks run. TaskScheduler.Default is the thread pool; FromCurrentSynchronizationContext() wraps a UI context so continuations return to the UI thread. Custom schedulers exist for things the pool cannot express: strict ordering (a limited-concurrency scheduler with degree 1), a dedicated thread with COM apartment state, or priority scheduling. In modern code they are largely obsolete — a Channel with one consumer expresses ordering better, and SemaphoreSlim or Parallel.ForEachAsync expresses limited concurrency better — so the useful part of this answer is knowing why TaskScheduler.Current matters: ContinueWith and StartNew default to it, so nested TPL work can inherit a scheduler you did not intend.

Example

// the practical reason to know schedulers exist
task.ContinueWith(t => Log(t), TaskScheduler.Default);   // NOT Current — be explicit

// the WPF/WinForms use that is still legitimate
var ui = TaskScheduler.FromCurrentSynchronizationContext();
work.ContinueWith(t => Bar.Value = t.Result, ui);

Follow-ups

  • Default vs Current — what is the difference? — Default is always the pool; Current is the scheduler of the task you are inside, which may be a custom or UI scheduler.
  • Does await use TaskScheduler? — Only as a fallback: it prefers SynchronizationContext.Current, and uses TaskScheduler.Current when there is no context and it is not the default.
  • Modern replacement for a limited-concurrency scheduler? — Parallel.ForEachAsync with MaxDegreeOfParallelism, or a channel with N consumers.

Common wrong answer

"TaskScheduler is how you control which thread async code runs on." For await-based code the SynchronizationContext is what matters; schedulers govern the TPL surface, and confusing the two leads to fixes that do nothing.

principalWhy is the async state machine a struct, and when does it box?

Answer

In release builds the compiler emits it as a struct so that a method completing synchronously never touches the heap: the struct lives on the caller stack frame, runs to completion, and dies. It boxes exactly once, on the first suspension, when AwaitUnsafeOnCompleted must hand a reference to the continuation registration that will outlive the stack frame. That is why the synchronous fast path is genuinely allocation-free and why ValueTask plus a high cache-hit rate can give you zero-allocation async. In debug builds it is a class instead, so the debugger can display it — which is one reason allocation numbers from a debug build are meaningless.

Example

// 95% of calls: struct on the stack, cached Task, 0 bytes allocated
// 5% of calls: box the state machine + allocate Task + delegate + ExecutionContext copy
async ValueTask<int> GetAsync(string key)
    => _cache.TryGetValue(key, out var v) ? v : await LoadAsync(key);

Follow-ups

  • What else does the box carry? — Every local that lives across an await, plus this, which is why large captured state makes the box large.
  • Can you avoid the box entirely on the async path? — With pooled builders (PoolingAsyncValueTaskMethodBuilder) the object is reused rather than freshly allocated — pooling rather than elimination.
  • What changes with runtime async? — The state machine class disappears from the generated code; the runtime tracks suspension itself, and .NET 11 also avoids saving unchanged locals and reuses continuations.

Common wrong answer

"Async always allocates a state machine object." Only when it actually suspends — and this misconception is exactly what leads people to avoid async on cache-hit paths where it is free.

seniorHow does the runtime resume a continuation after I/O completes?

Answer

The asynchronous I/O is issued to the OS with a completion mechanism — an I/O completion port on Windows, epoll/kqueue on Linux and macOS — and no thread waits on it. When the operation finishes, the OS signals the completion, a runtime thread dequeues it, and the runtime completes the corresponding Task. Completing the task runs its continuations: either inline on that thread, or queued to the thread pool, or posted to a captured SynchronizationContext, depending on how the await was configured and on RunContinuationsAsynchronously. Your MoveNext then resumes at the recorded state. The part worth saying out loud is that the "waiting" is entirely in the OS and costs no managed thread — which is the mechanical justification for everything async gives you.

Example

// no thread exists between these two lines while the socket is in flight
var bytes = await socket.ReceiveAsync(buffer, SocketFlags.None, ct);
Process(buffer.Span[..bytes]);   // resumed by an I/O completion, on a pool thread

Follow-ups

  • Why can inline continuations be dangerous? — They run your code on the I/O completion thread; a slow continuation stalls other completions, which is why RunContinuationsAsynchronously exists.
  • Is this different on Linux? — The mechanism differs (epoll rather than IOCP) but the model is identical from managed code.
  • What about file I/O? — Genuinely asynchronous only when the handle is opened for overlapped/async I/O (FileOptions.Asynchronous); otherwise the runtime may fall back to a thread.

Common wrong answer

"A background thread polls until the I/O finishes." That is what async exists to avoid, and it is the mental model behind most "async does not help" claims.

principalHow would you explain async to a strong engineer coming from Node.js or Go?

Answer

To a Node developer: the model is the same event-loop-shaped idea, but .NET has no single loop — continuations go to a multi-threaded pool, so your continuation can run on a different thread than the one that started, and shared state genuinely needs synchronisation. The upside is that CPU work does not block everything; the cost is that data races are possible, which they are not in single-threaded JavaScript. To a Go developer: Task is not a goroutine. Go multiplexes cheap stackful goroutines onto OS threads and lets you write blocking code; .NET makes suspension explicit in the type system with stackless state machines, so blocking is a real cost and await is not free syntax sugar over a scheduler. Channels are the concept that translates almost exactly, and I would use that as the bridge. In both directions the thing to over-communicate is that blocking a .NET thread pool thread is a capacity decision, not a style choice.

Example

// Go: go doWork(ch)      — cheap stackful goroutine, blocking reads are fine
// .NET:
_ = Task.Run(() => DoWorkAsync(channel.Writer, ct));   // pool thread; blocking is NOT fine
// the channel part translates directly:
await foreach (var item in channel.Reader.ReadAllAsync(ct)) Handle(item);

Follow-ups

  • What surprises Node developers most? — That two continuations can run concurrently, so a shared dictionary needs a concurrent type or a lock.
  • What surprises Go developers most? — That "just block, the runtime handles it" is wrong here, and that there is no preemption of a CPU-bound task.
  • What is the single sentence you would give both? — "await means give the thread back; blocking means keep it, and threads are the scarce resource."

Common wrong answer

"It is basically the same as promises / goroutines." Both analogies mislead in ways that produce real bugs — races for the Node developer, blocking for the Go developer — and a principal-level answer names the difference rather than the similarity.

15Runtime async and the 2026 landscape

Rarely asked, but it is the sub-area that shows you follow the platform rather than just use it. Interviewers who ask are usually testing currency: do you know what is stable today, what is in preview, and what will change how async performs. Keep answers factual about status — .NET 10 is the current LTS, .NET 11 is in preview with GA expected November 2026 — and be explicit that preview features are not things you would ship on today.

seniorWhat is runtime async, and what changes for the code you write?

Answer

Runtime async moves suspension and resumption from compiler-generated state machines into the runtime itself: the compiler marks a method as async and the runtime handles saving and restoring execution. The visible wins are cleaner live stack traces — a three-deep async chain drops from about 13 frames to 5, since the AsyncMethodBuilderCore.Start infrastructure frames disappear — better debugging with breakpoints binding correctly inside async methods, and lower overhead through reused continuations and locals that are not saved when unchanged. For the code you write, nothing changes: async/await is identical, and the semantics of context capture and cancellation are unchanged. It landed for experimentation in .NET 10 and became far more real in .NET 11 preview, where the runtime libraries themselves are compiled with runtime-async=on — but it is still a preview feature you opt into per project, so on a .NET 10 LTS service today it is something you follow, not something you ship.

Example

// .NET 11 preview: opt in per project
// <PropertyGroup>
//   <Features>runtime-async=on</Features>
// </PropertyGroup>
//
// The DOTNET_RuntimeAsync / UNSUPPORTED_RuntimeAsync environment switches are gone;
// to opt out per project set <UseRuntimeAsync>false</UseRuntimeAsync>.

Follow-ups

  • Does it change exception stack traces? — Barely: caught-exception traces were already cleaned up by ExceptionDispatchInfo. The improvement is in live stacks that profilers, debuggers and new StackTrace() see.
  • Does it work with NativeAOT and ReadyToRun? — Yes, and .NET 11 removed the restrictions that prevented runtime-async methods being inlined during crossgen2 R2R compilation.
  • Would you enable it in production today? — No. It is preview; I would benchmark it on a branch and wait for GA.

Common wrong answer

"Runtime async means async is free now." It reduces overhead; it does not remove suspension, scheduling or context capture, and it does nothing about a blocking call.

midWhat is the current .NET release and support picture, and why does it matter for async code?

Answer

.NET 10 is the current release, shipped 11 November 2025, and it is LTS with support to November 2028, carrying C# 14. .NET 11 is in preview with GA expected November 2026 and will be an STS release. The reason it matters for async specifically is version-gating: several things you will want to name in an interview have concrete floors — ConfigureAwaitOptions and CancellationTokenSource.CancelAsync in .NET 8, Task.WhenEach and HybridCache in .NET 9, System.Linq.AsyncEnumerable in the BCL in .NET 10, runtime async as preview through .NET 10 and 11. If the team is on .NET 8, half of those are not available to you, and proposing them without checking is a credibility problem.

  • What is the upgrade risk for async code specifically? — Low; the async model has been stable for a decade. The risk is in the surrounding platform, not in await.

seniorWhich recent async-adjacent APIs have actually changed how you write code?

Answer

Four, in order of how often I use them. TimeProvider (.NET 8) made time injectable, so retry and timeout logic is finally testable without Thread.Sleep in tests — it is the one I reach for most. Task.WhenEach (.NET 9) replaced the quadratic WhenAny-and-remove loop for streaming completions. ConfigureAwaitOptions (.NET 8) gave SuppressThrowing, which made shutdown drain code honest instead of an empty catch. HybridCache (.NET 9) removed the hand-rolled stampede protection that every team writes slightly wrong. Worth naming as a fifth: System.Linq.AsyncEnumerable moved into the BCL in .NET 10, so streaming pipelines no longer need a third-party package.

Example

// TimeProvider: the change that pays off every week
public sealed class Retrier(TimeProvider time)
{
    public async Task<T> RunAsync<T>(Func<CancellationToken, Task<T>> op, CancellationToken ct)
    {
        for (var attempt = 0; ; attempt++)
        {
            try { return await op(ct); }
            catch (Exception ex) when (attempt < 3 && IsTransient(ex))
            {
                await Task.Delay(Backoff(attempt), time, ct);   // fake it in tests
            }
        }
    }
}

Follow-ups

  • What did TimeProvider replace? — Hand-rolled IClock interfaces in every codebase, none of which covered Task.Delay or timers.
  • Anything you deliberately do not use? — Pooled ValueTask builders outside genuine hot paths; the consumption constraints are not worth it for ordinary code.
  • What is on your watch list? — Runtime async at GA, and whether the ExecutionContext capture elision measurably changes hot-path guidance.

Common wrong answer

Listing features you have not used. Interviewers follow up with "how did that change your code", and a memorised release-notes answer collapses in one question.

principalHow do you decide whether to adopt a preview runtime feature like runtime async?

Answer

I would treat it as a bet with an explicit cost, expected value and exit. Cost: preview features can change shape or be pulled, tooling and profilers may lag, and you take on an upgrade obligation. Expected value: for runtime async specifically, cleaner live stacks and lower async overhead — real, but neither is likely to be the top constraint on a typical service, so the honest answer is often "not yet". Exit: it must be a project-level flag I can turn off, which runtime async is. So my process is: prototype on a branch, benchmark the actual service rather than a microbenchmark, and adopt only if it moves a metric we already track. For a preview runtime feature in a production service on an LTS, my default is no, with a scheduled re-evaluation at GA — and I would say that plainly rather than dressing conservatism up as caution.

Example

//   <!-- <UseRuntimeAsync>false</UseRuntimeAsync>   opt out again, per project -->
// </PropertyGroup>

Follow-ups

  • What would make you adopt early? — A metric it directly improves that we are actually failing, plus a service where the blast radius is small and rollback is a config change.
  • How do you keep the team from adopting it informally? — A short written policy on preview features and a build check on the flags, so it is a decision rather than a drive-by commit.
  • What is the cost of always waiting? — You lose the feedback window where your report can still change the feature; contributing a benchmark to the issue tracker is a cheap way to have both.

"Preview features are fine, we are on the latest anyway." Preview means the contract can change; adopting one without a documented exit is how a team ends up pinned to a broken preview SDK during an incident.

16Legacy patterns and interop

Rarely a primary topic, but it appears in two forms: a code-reading exercise using an older pattern, and "we have a .NET Framework service, how would you modernise it". Both are really testing whether you can work in a codebase you did not write. Recognising APM and EAP on sight, and knowing that legacy ASP.NET behaves differently from ASP.NET Core, is enough depth.

midWhat are APM and EAP, and how do you bring them into modern async code?

Answer

APM is the .NET 1.x Begin/End pattern with an IAsyncResult; EAP is the .NET 2.0 event pattern with a ...Async method plus a ...Completed event and a cancel method. Both predate Task. You bridge APM with Task.Factory.FromAsync, which wraps a Begin/End pair in a Task, and EAP with a TaskCompletionSource completed from the event handler — remembering to unsubscribe, or you leak. You will meet them in old SQL, socket and WCF code. The judgment part is when to bridge versus replace: if the underlying library has a modern async API, use it; bridging is for code you cannot change.

Example

// APM -> Task
var read = Task.Factory.FromAsync(stream.BeginRead, stream.EndRead, buffer, 0, buffer.Length, null);

// EAP -> Task
Task<string> DownloadAsync(WebClient c, Uri uri)
{
    var tcs = new TaskCompletionSource<string>(TaskCreationOptions.RunContinuationsAsynchronously);
    void Handler(object? s, DownloadStringCompletedEventArgs e)
    {
        c.DownloadStringCompleted -= Handler;                    // unsubscribe or leak
        if (e.Error is not null) tcs.TrySetException(e.Error);
        else if (e.Cancelled) tcs.TrySetCanceled();
        else tcs.TrySetResult(e.Result);
    }
    c.DownloadStringCompleted += Handler;
    c.DownloadStringAsync(uri);
    return tcs.Task;
}

Follow-ups

  • What is the leak risk with EAP bridging? — Forgetting to unsubscribe roots the handler and its closure on a long-lived component.
  • Is WebClient still acceptable? — No; it is obsolete in favour of HttpClient, and in .NET 6+ it carries an obsoletion warning.
  • How do you go the other way, Task to APM? — ToApm-style helpers exist for implementing a legacy interface over modern code; rare, but it comes up in plugin hosts.

Common wrong answer

"Wrap the Begin/End call in Task.Run." That blocks a thread inside End... and throws away the asynchrony the APM API was already providing.

seniorHow does async differ on .NET Framework and legacy ASP.NET?

Answer

The big one is the AspNetSynchronizationContext: legacy ASP.NET (System.Web) installs a context that serialises continuations onto the request, so .Result deadlocks exactly like a UI thread, and ConfigureAwait(false) genuinely matters throughout. It also requires <httpRuntime targetFramework="4.5"/> for correct async behaviour, and it needs AsyncTimeout and page-level Async="true" for WebForms. Beyond that: two separate thread pools (worker and IOCP) with independent minimums, no ValueTask, no IAsyncEnumerable, and a much older thread-pool injection implementation. So code that behaves fine on ASP.NET Core can deadlock on .NET Framework, and vice versa the starvation profile is different.

Example

// legacy ASP.NET: this deadlocks; the same code on ASP.NET Core does not
public ActionResult Index()
{
    var data = _service.GetAsync().Result;   // continuation needs the request context
    return View(data);
}

Follow-ups

  • Why does ConfigureAwait(false) matter more there? — Because a context exists on every request, so every await without it posts back and serialises.
  • What breaks when you port to ASP.NET Core? — Code relying on HttpContext.Current, which is AsyncLocal-backed there and absent in Core.
  • Is .NET Framework still supported? — 4.8/4.8.1 are supported as a Windows component with no new features; new work should target modern .NET.

Common wrong answer

"Async works the same everywhere." The presence or absence of a SynchronizationContext changes whether a given piece of code deadlocks — it is the single biggest behavioural difference between the two platforms.

midWhat async patterns in an old codebase would you flag immediately in review?

Answer

Six, in the order I look for them: .Result and .Wait() anywhere below an entry point; async void outside an event handler; Task.Run wrapping synchronous I/O to fake async; ContinueWith without an explicit TaskScheduler; a CancellationToken parameter that is not passed down; and Task.Factory.StartNew with an async delegate (which yields Task<Task> and completes immediately unless unwrapped). Each is a one-line grep, which is why I would land an analyzer rather than rely on eyes — but knowing the list is what lets you triage a codebase in an afternoon and say which problems are cosmetic and which are outage-shaped.

Example

// the grep list
//   \.Result\b            \.Wait\(\)            async void
//   Task\.Run\(.*File\.   ContinueWith\(        StartNew\(async
//   GetAwaiter\(\)\.GetResult\(\)

Follow-ups

  • Which of those is most urgent? — Blocking calls on the request path, because they are the ones that cause incidents rather than merely being untidy.
  • Which is most often a false positive? — GetAwaiter().GetResult() at a genuine entry point, and .Result on a task you have already awaited.
  • How do you prioritise the fixes? — By traffic through the code path, not by count; ten violations in a nightly job matter less than one in the hot endpoint.

Common wrong answer

"Fix all of them." Without prioritisation you spend the budget on cold paths and never reach the one blocking call that is actually starving the pool.

seniorA WinForms/WPF app freezes during a long operation. Walk me through the fix.

Answer

First establish which kind of freeze it is, because the fixes differ. If the UI thread is doing CPU work, move it off with await Task.Run(...) and marshal the result back — the await returns to the UI thread automatically because the context is captured. If the UI thread is blocked on async work with .Result or .Wait(), that is the deadlock, and the fix is to make the handler async void and await down the chain. If it is a third-party library capturing the context, hop to the pool around the call. Then the things that make it a good answer: disable the control or show progress so the user knows, support cancellation with a token wired to a Cancel button, and add an analyzer so it does not come back. Do not move UI updates off the UI thread — that trades a freeze for a cross-thread exception.

Example

private CancellationTokenSource? _cts;

private async void OnRunClick(object sender, EventArgs e)
{
    _cts = new CancellationTokenSource();
    RunButton.Enabled = false;
    try
    {
        var result = await Task.Run(() => Compute(_input, _cts.Token), _cts.Token);
        ResultLabel.Text = result;                 // back on the UI thread automatically
    }
    catch (OperationCanceledException) { ResultLabel.Text = "cancelled"; }
    catch (Exception ex) { _log.LogError(ex, "compute failed"); ShowError(ex); }
    finally { RunButton.Enabled = true; }
}

Follow-ups

  • Why is async void acceptable here? — The event signature requires it; the body is fully guarded, which is the condition that makes it safe.
  • How do you report progress? — IProgress<T>; its Progress<T> implementation captures the UI context on construction and posts callbacks there.
  • What if the work is I/O rather than CPU? — No Task.Run at all — just await the async API; wrapping I/O in Task.Run is the classic over-correction.

Common wrong answer

"Use BackgroundWorker." It still works but it is the EAP-era answer; async/await with Task.Run and IProgress<T> does the same job with cancellation, exceptions and composition handled properly.

17Judgment calls

These have no single right answer, which is the point: they are asked to see whether you reason from constraints or from rules. A strong answer states the trade explicitly, names the condition that would flip your decision, and mentions the cost of your own choice unprompted. Each block below tells you what a top answer demonstrates rather than giving you a script — practise saying yours out loud, then compare.

principalShould everything in a new service be async by default?

What a strong answer demonstrates

That you separate the default from the rule. A strong answer says yes for anything touching I/O — which is nearly everything in a service — but explicitly excludes pure in-memory and CPU paths where the state machine is cost without benefit, and it points out that the real invariant is "nothing blocks", not "everything is async". It names the enforcement mechanism (analyzers) rather than relying on culture, and it acknowledges the readability cost of async plumbing in code that will never suspend.

Trade-offs a top candidate names unprompted

  • Async is per-call slower and only pays off under concurrency — so on a low-traffic internal tool it is ceremony.
  • Mixed sync and async in one codebase is where bridges appear; a consistent default reduces the chance of an accidental .Result.
  • Making a public API async later is a breaking change, which argues for async in library signatures even when the current implementation is synchronous.
  • The enforcement question is cultural: a rule nobody can derive from a model gets applied wrongly at the first novel case.
principalWhen is it acceptable to block on async code?

What a strong answer demonstrates

That you can name the small set of genuine entry points — a Main that cannot be async, a module initializer, some DI factories, a legacy plugin interface you do not own — and that you distinguish them from convenience blocking in the middle of a call chain. It also shows you know the failure modes differ by host: deadlock under a SynchronizationContext, thread-pool starvation without one. The best answers add that blocking on an already-completed task is harmless, which is why GetAwaiter().GetResult() on a known-complete task is a legitimate micro-optimisation rather than a sin.

Trade-offs a top candidate names unprompted

  • Blocking at the outermost frame costs one thread; blocking per request costs one thread per request — the same construct, wildly different consequences.
  • GetAwaiter().GetResult() is preferable to .Result when you must block, because it does not wrap in AggregateException.
  • A documented, commented exception is better than a rule everyone quietly breaks; the analyzer suppression should carry the reason.
  • The bridge should be pushed as far out as possible, so the blocked thread count does not scale with traffic.
principalTask or ValueTask on a new public interface that many teams will implement?

What a strong answer demonstrates

Awareness that the choice constrains implementors and callers, not just you. Task is forgiving: re-awaitable, composable with WhenAll, familiar. ValueTask imposes a consumption contract that many callers will violate, and cannot be combined without AsTask(), which erases the benefit. A strong answer defaults to Task for a public cross-team interface and reserves ValueTask for internal hot paths with measured synchronous completion — and notes the asymmetry that widening from ValueTask to Task later is a breaking change.

Trade-offs a top candidate names unprompted

  • Interface choices propagate: every implementor and every caller inherits the constraint, so the blast radius is much larger than a single method.
  • The performance win only exists at a high synchronous-completion rate; on an interface used many ways, that rate varies per implementation.
  • Documentation does not prevent misuse at scale; if the contract can be broken silently, it will be.
  • You can always add a ValueTask overload internally later; you cannot easily take the constraint back.
principalA dependency has no async API. What do you do?

What a strong answer demonstrates

That you can weigh isolation against replacement and be honest that no option is free. The realistic answers are: bulkhead it behind a bounded concurrency limit with Task.Run, so the blocking cost is capped and visible; move it out of process so blocking happens somewhere that is allowed to block; push the vendor or fork the client; or accept it and size the thread pool deliberately for it. A strong answer picks based on traffic and criticality and names the monitoring that makes the choice reversible.

Trade-offs a top candidate names unprompted

  • A bulkhead converts starvation into queueing — better, but it means requests now wait, so the limit needs a timeout too.
  • Moving out of process adds latency, a deployable and a failure mode; it is worth it only if the blocking is heavy or the dependency is unstable.
  • Forking a client is a maintenance commitment that outlives the person who made it.
  • "Just raise MinThreads" is a legitimate temporary answer, but only with a revert ticket and a comment naming this dependency.
principalRetry aggressively, or fail fast?

What a strong answer demonstrates

That you treat retries as a load-multiplier decision rather than a reliability feature. The reasoning should cover idempotency (non-idempotent retries are correctness bugs without an idempotency key), the failure class (a transient blip deserves a retry; a dependency that is down deserves a circuit breaker), and the budget (a retry that exceeds the client deadline is pure waste). A top answer names retry amplification explicitly — three layers of three retries is 27 calls into something already failing — and pairs any retry policy with a breaker and jitter.

Trade-offs a top candidate names unprompted

  • Retries help most exactly when they hurt most: during partial failure, when the dependency has least capacity.
  • Retry at one layer only, ideally the outermost that knows the deadline; nested retries are how a blip becomes an outage.
  • Failing fast gives the client the choice, which is often better than deciding for them at 400 ms into an 800 ms budget.
  • Jitter is not optional; synchronised retries from a thousand clients are a self-inflicted thundering herd.
principalStreaming or pagination for a large result set?

What a strong answer demonstrates

That you know both solve the memory problem and differ everywhere else. Streaming wins on time-to-first-byte and flat memory; pagination wins on cacheability, retryability, resumability and clean error semantics, and it does not hold a connection or cursor open. A strong answer picks pagination for public APIs and streaming for continuous data or internal high-volume paths where both ends are yours, and it raises the mid-stream error problem: once you have sent a 200 and half the body, you cannot turn it into a 500.

Trade-offs a top candidate names unprompted

  • Streaming trades memory for held connections and cursors — a resource that is often scarcer.
  • Proxies, gateways and client libraries may buffer anyway, silently erasing the benefit.
  • Cursor pagination is stable under concurrent writes; offset pagination degrades badly at depth.
  • Streaming needs an in-band error contract designed up front, not improvised during an incident.
principalShould CancellationToken be a required parameter in your codebase standard?

What a strong answer demonstrates

That you see both the ergonomics and the failure mode. Required tokens make it impossible to silently drop cancellation and force the caller to think, at the cost of noise on every signature — including methods that can never be cancelled. Optional tokens read better and are the .NET convention, but they make dropping one invisible. A strong answer usually lands on: required in libraries and any method that does I/O, optional or absent elsewhere, with an analyzer (CA2016) enforcing forwarding — and it names CancellationToken.None as the explicit way to say "deliberately not cancellable".

Trade-offs a top candidate names unprompted

  • An accepted-but-ignored token is worse than no token: it makes a broken promise look like a working feature.
  • Required parameters break existing callers, so the migration path matters as much as the rule.
  • Not everything should be cancellable — writes, audits and compensations often must complete.
  • Tooling beats convention: an analyzer catches the case a reviewer skims past at the end of a long diff.
principalIn-process background work, or a queue and a worker?

What a strong answer demonstrates

That you decide from durability requirements rather than from convenience. In-process is right for short, idempotent, loss-tolerant work; a queue is right the moment the work must survive a restart, must not run twice across replicas, needs retry and visibility, or takes longer than the shutdown grace period. The strongest answers name the operational coupling: long in-process jobs make deploys slow, distort autoscaling signals, and turn one bad job into a latency incident for every user of the API.

Trade-offs a top candidate names unprompted

  • A queue adds a deployable, a failure mode and eventual consistency the API contract must express.
  • Starting with a database-backed job table is a legitimate middle step — durability without a new broker.
  • In-process work competes with request handling for the same thread pool and the same memory.
  • The migration is cheap if the handler is already a service: the endpoint enqueues, the handler moves.
principalHow much async complexity is worth it for performance?

What a strong answer demonstrates

Calibration. A strong answer starts from whether the code is on a path that matters at all, insists on a measurement before and after, and weighs the ongoing cost — every future reader and every future change pays for cleverness once. Pooled ValueTask builders, hand-rolled IValueTaskSource and custom schedulers are justified in a library used by thousands of services and almost never in an application. The best answers also name the reversal condition: if the benchmark does not survive the next refactor, the complexity should not either.

Trade-offs a top candidate names unprompted

  • Complexity is paid continuously in comprehension and bugs; performance is paid once and measured.
  • Optimisations without a regression test silently erode — protect them in CI or expect to lose them.
  • The biggest wins are usually removing work (an unnecessary await, a redundant call), not making work faster.
  • Library and application code sit at different points on this curve, and applying library standards to app code wastes budget.
principalHow do you teach async correctly to a team that has been getting it wrong?

What a strong answer demonstrates

That you change the system, not just the people. Tooling first, because an analyzer catches every case forever and a talk catches the people who attended: analyzers at error severity on new code, baselined for existing. Then the mental model, taught once with the specific incident from your own service as the worked example, because a real 3 a.m. story is what makes it stick. Then a small set of blessed patterns — the background-work helper, the throttling helper, the timeout helper — so the correct thing is also the easy thing. A strong answer explicitly rejects the "write a wiki page" approach as insufficient, and names how you would know it worked: fewer analyzer suppressions over time, and no new blocking calls in the hot path.

Trade-offs a top candidate names unprompted

  • Turning analyzers on globally at error severity blocks everyone on day one; baseline plus new-code enforcement is what actually ships.
  • Blessed helpers become their own liability if nobody owns them — assign an owner or expect drift.
  • Teaching the model beats teaching rules, because the team will meet cases your rules do not cover.
  • You need a measurable outcome, or "we improved async knowledge" is unfalsifiable and gets deprioritised.

18Design exercises

These are the whiteboard-length versions, where async knowledge meets system design. Attempt each one before opening the solution: write down the clarifying questions first, then a rough design, then compare. The grading in a real interview is mostly about whether you bound things, whether you name failure modes before you are asked, and whether you can say what you would measure.

Exercise 1 — Fan-out API gateway

Prompt. Design an endpoint that assembles a product page by calling five backend services: catalog, pricing, inventory, reviews and recommendations. It must respond in under 300 ms at p99 and must not fall over when one backend degrades.

Clarifying questions you should ask

  • Which of the five are required for a useful page, and which can degrade to a placeholder or cached value?
  • What is the latency profile of each backend today, and what are their concurrency limits?
  • Is the page cacheable, per user or shared, and for how long?
  • What is the traffic shape — steady, spiky, or driven by campaigns?
  • Is a stale price acceptable, or is pricing a correctness requirement?
principalSolution outline and expected trade-offs

Design

Start all five calls concurrently under one request deadline of 300 ms, propagated as a shrinking budget rather than five independent timeouts. Split them into required (catalog, pricing) and optional (inventory, reviews, recommendations): required legs fail the request, optional legs get a shorter deadline — say 120 ms — and degrade to cached or empty content. Each backend gets its own HttpClient with a resilience pipeline: attempt timeout, bounded retry on transient failures only, and a circuit breaker so a dead backend stops consuming budget immediately. Cache aggressively per backend with stampede protection, since the same product is requested by many users. Emit a span per leg with the remaining budget as an attribute, so you can see which leg eats the deadline.

Sketch

using var linked = CancellationTokenSource.CreateLinkedTokenSource(ct);
linked.CancelAfter(TimeSpan.FromMilliseconds(300));

var catalog   = _catalog.GetAsync(id, linked.Token);          // required
var pricing   = _pricing.GetAsync(id, linked.Token);          // required
var inventory = Optional(_inventory.GetAsync(id, linked.Token), fallback: Inventory.Unknown);
var reviews   = Optional(_reviews.GetAsync(id, linked.Token),   fallback: Reviews.Empty);
var recs      = Optional(_recs.GetAsync(id, linked.Token),      fallback: Recs.Empty);

await Task.WhenAll(catalog, pricing, inventory, reviews, recs);
return Page.From(await catalog, await pricing, await inventory, await reviews, await recs);

static async Task<T> Optional<T>(Task<T> t, T fallback)
{
    try { return await t; } catch { return fallback; }         // degrade, never fail the page
}

Trade-offs you are expected to name unprompted

  • Degrading silently hides backend failures from users but also from you — the fallback path needs its own metric or the page quietly gets worse.
  • Fan-out multiplies load: one page request is five backend requests, so the gateway concurrency limit must be sized against the weakest backend.
  • Caching improves p99 dramatically but introduces staleness; pricing is usually where the business draws the line.
  • A circuit breaker makes failure fast and predictable, at the cost of rejecting requests a struggling backend might have served.
  • The 300 ms budget is only real if it is propagated; per-hop timeouts would allow a worst case far above it.

Exercise 2 — High-throughput ingestion pipeline

Prompt. Design a service that ingests 50,000 events per second from a message broker, enriches each event with a lookup, and writes to a database. It must not lose acknowledged events and must survive a restart.

Clarifying questions you should ask

  • Delivery guarantee: at-least-once with deduplication, or is exactly-once being assumed?
  • Does ordering matter, globally or per key?
  • What is the enrichment lookup — cacheable, and what is the hit rate?
  • What write throughput can the database actually take, and does it support batching?
  • What is the acceptable end-to-end latency: seconds, or minutes?
principalSolution outline and expected trade-offs

Design

Partition by key so ordering is per key and the pipeline scales horizontally — one consumer per partition, no cross-partition coordination. Within a consumer, a bounded Channel between the broker reader and the processing stage gives backpressure: when the database is slow, the channel fills, the reader stops pulling, and the broker holds the backlog, which is exactly where a backlog belongs. Enrichment goes through a cache with stampede protection, because at 50k/s a cache miss storm is the failure mode. Writes are batched — say up to 500 rows or 50 ms, whichever comes first — since per-event round trips will not reach the throughput. Acknowledge to the broker only after the batch is durably written, which gives at-least-once, and make the write idempotent on an event id so replay after a restart is safe. On shutdown, stop reading, drain the channel, flush the final batch with a non-cancellable token, then ack.

Sketch

var buffer = Channel.CreateBounded<Event>(new BoundedChannelOptions(10_000)
{
    FullMode = BoundedChannelFullMode.Wait          // backpressure to the broker
});

// writer stage: batch by size or time, ack after durability
var batch = new List<Enriched>(500);
using var flushTimer = new PeriodicTimer(TimeSpan.FromMilliseconds(50));

await foreach (var e in buffer.Reader.ReadAllAsync(ct))
{
    batch.Add(await _enrich.GetAsync(e, ct));       // cached, stampede-protected
    if (batch.Count >= 500) await FlushAsync(batch, ct);
}

async Task FlushAsync(List<Enriched> rows, CancellationToken token)
{
    await _db.BulkUpsertAsync(rows, token);          // idempotent on event id
    await _broker.AckAsync(rows[^1].Offset, token);  // ack AFTER durability
    rows.Clear();
}

Trade-offs you are expected to name unprompted

  • At-least-once plus idempotency is the pragmatic choice; exactly-once across a broker and a database needs distributed transactions or an outbox, and usually is not worth it.
  • Batching trades latency for throughput; the time-based flush is what keeps tail latency bounded when the rate drops.
  • Backpressure means the backlog moves to the broker, which is durable and observable — but you need alerting on consumer lag, or the queue silently grows.
  • Partitioning gives ordering per key, not globally; if the business needs global ordering, throughput is capped by one consumer.
  • Restart safety depends entirely on the ack-after-durability ordering — acking first is the single change that turns this into data loss.

Exercise 3 — Long-running job API

Prompt. Users submit a report that takes 2–30 minutes to generate. Design the API and the execution model. HTTP requests must not stay open, users must see progress, and a deployment mid-job must not lose work.

Clarifying questions you should ask

  • How many concurrent jobs, and how bursty is submission?
  • Is a job resumable, or must it restart from scratch after a failure?
  • How do users learn the job finished — polling, webhook, SSE, email?
  • How long must results be retained, and are they large?
  • Can two identical submissions be deduplicated into one job?
principalSolution outline and expected trade-offs

Design

Asynchronous request-reply. POST /reports validates, persists a job row with status Queued, enqueues it, and returns 202 Accepted with a Location header pointing at GET /reports/{id}, which returns status and progress until the result is ready. Workers are a separate deployable so they scale independently of the API and a long job never blocks a request thread. Each worker leases a job with a visibility timeout and heartbeats while working, so a crashed worker releases its job automatically rather than leaving it stuck in Running. Progress is written as checkpoints, which serves two purposes at once: the user sees a percentage, and a restart resumes from the last checkpoint instead of from zero. Idempotency on submission — a client-supplied key — deduplicates retries. Notification is polling by default, with an optional webhook, because polling is trivial to make reliable and webhooks are not.

Sketch

app.MapPost("/reports", async (ReportSpec spec, IJobs jobs, CancellationToken ct) =>
{
    var id = await jobs.EnqueueAsync(spec, spec.IdempotencyKey, ct);
    return Results.Accepted($"/reports/{id}", new { id, status = "Queued" });
});

app.MapGet("/reports/{id}", async (Guid id, IJobs jobs, CancellationToken ct) =>
    await jobs.GetAsync(id, ct) switch
    {
        null                              => Results.NotFound(),
        { Status: "Succeeded" } j         => Results.Ok(new { j.Status, url = j.ResultUrl }),
        { Status: "Failed" } j            => Results.Ok(new { j.Status, j.Error }),
        var j                             => Results.Ok(new { j.Status, j.PercentComplete })
    });

Trade-offs you are expected to name unprompted

  • 202-plus-polling is more moving parts than a synchronous call, but a 30-minute HTTP request is not survivable through any proxy or load balancer.
  • Checkpointing costs write amplification and forces the job to be idempotent per checkpoint; the payoff is that deployments stop being destructive.
  • Leases with heartbeats add complexity but are the only way a crashed worker releases work automatically; without them you need manual intervention.
  • Polling wastes requests but is far more reliable than webhooks, which need retries, signing and an endpoint the user actually operates.
  • Separate worker scaling is the main operational win — and the main new cost, since it is another deployable to monitor and page on.

19Night-before cheat sheet

The ten questions most likely to be asked, with the one-sentence answer to have ready. If you only have twenty minutes, read these and the wrong answers in units 01, 03 and 04.

  1. Does await create a thread? No — it suspends the method, returns to the caller, and resumes on a continuation when the operation completes; no thread waits.
  2. Why does .Result deadlock? The continuation is posted back to a captured single-threaded context whose only thread is the one you just blocked, so it can never run.
  3. What does ConfigureAwait(false) do? It declines to capture the SynchronizationContext for that one await — essential in libraries, a no-op in ASP.NET Core app code.
  4. What is thread-pool starvation? Blocking pool threads faster than the pool injects new ones (roughly one or two per second), producing rising latency with low CPU and a growing work queue.
  5. Why is async void dangerous? There is no task to await, so nothing can observe its completion and an unhandled exception is rethrown on the context and crashes the process.
  6. Task vs ValueTask? Task by default; ValueTask only on hot paths that usually complete synchronously, and it must be awaited exactly once.
  7. How does cancellation work? Cooperatively: the source signals, the token is checked or passed down, and cooperating code throws OperationCanceledException — nothing is forcibly aborted.
  8. WhenAll vs WhenAny vs WhenEach? All (waits for everything, first exception rethrown), Any (first completion, losers keep running unobserved), Each (.NET 9+, yields each task as it completes).
  9. How do you bound concurrency? Parallel.ForEachAsync with MaxDegreeOfParallelism, a SemaphoreSlim, or a bounded Channel — sized from arrival rate times service time.
  10. Async in ASP.NET Core: what is freed while awaiting? The thread — the request itself stays alive as memory, a socket and a DI scope, which is why in-flight requests are cheap and blocking is expensive.
