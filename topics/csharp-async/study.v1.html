C# async/await & the Task-based asynchronous pattern

.NET 10 (LTS) — released 11 Nov 2025, supported to 10 Nov 2028 · C# 14 .NET 11 Preview 7 — 11 Aug 2026 · GA expected 10 Nov 2026 (STS) · C# 15

Async/await in C# is mature and stable: the language surface has barely moved since C# 8 (async streams), C# 10 ([AsyncMethodBuilder] on methods) and C# 13 (params ReadOnlySpan overloads for Task.WhenAll), so the action has shifted into the runtime and libraries. .NET 8 added ConfigureAwaitOptions, CancellationTokenSource.CancelAsync and TimeProvider; .NET 9 added Task.WhenEach, prioritized channels and the WaitHandleWait diagnostic event; .NET 10 shipped in-box LINQ for IAsyncEnumerable<T> (System.Linq.AsyncEnumerable) plus async ZIP and WebSocketStream APIs. The headline change you should be able to discuss today is Runtime Async in the .NET 11 previews: async methods compiled as [MethodImpl(MethodImplOptions.Async)] IL that the runtime suspends and resumes itself, instead of compiler-generated state machines — opt-in with <Features>runtime-async=on</Features>, no longer needing EnablePreviewFeatures on net11.0, and as of Preview 7 the runtime libraries themselves are compiled that way. Semantics are unchanged; what improves is live stack traces, allocations, NativeAOT/R2R support and diagnostics. Assumption: "C#" here means modern .NET (8/9/10 and the 11 previews); .NET Framework 4.x and classic ASP.NET are covered only where legacy codebases force the conversation.

01

How await really works: the mental model

Official: Asynchronous programming (C# guide) How Async/Await Really Works in C# (Stephen Toub, 2023) Task-based Asynchronous Pattern

Everything in this topic derives from one sentence: await is a continuation registration, not a thread. The problem async/await solves is composition. Before C# 5 (2012) you had the APM (BeginRead/EndRead) and EAP (DownloadAsync + Completed event) patterns: non-blocking, but every try/catch, loop and using had to be re-implemented by hand across callbacks. The compiler transform lets you write sequential-looking code while the machine underneath is still "register a callback and return".

What the compiler emits

An async method is rewritten into a state machine type implementing IAsyncStateMachine: a struct in Release builds, a class in Debug builds (so Edit & Continue and the debugger can inspect it). Its MoveNext() method contains your method body, chopped at each await into states. Locals that live across an await are hoisted into fields; the rest stay real locals. A builder chosen from the return type (AsyncTaskMethodBuilder, AsyncTaskMethodBuilder<T>, AsyncValueTaskMethodBuilder<T>, AsyncVoidMethodBuilder, or whatever [AsyncMethodBuilder] names, on the type or since C# 10 on the method) creates the returned task and drives the machine. The method body you wrote becomes roughly: create the machine, builder.Start(ref sm), return builder.Task.

Start calls MoveNext() synchronously on the caller's thread. Your code runs until the first await whose awaitable reports IsCompleted == false. Only then does the method "go async": the builder boxes the struct (once — that box is reused for all later suspensions and, since .NET Core 2.1, the box is the Task object the caller sees), captures the ExecutionContext, hands a continuation to the awaiter via UnsafeOnCompleted, and returns the incomplete Task to the caller. When the awaited operation finishes, whichever thread completes it (typically a thread-pool thread that picked up an I/O completion from IOCP on Windows or epoll on Linux) runs the continuation, which calls MoveNext() again; a switch on the state field jumps to the right place, calls awaiter.GetResult() to fetch the value or rethrow, and carries on. Nothing waits in between. That is why a Kestrel server can hold 10,000 in-flight requests on 16 threads: an in-flight request costs a heap object, not a thread.

The awaitable pattern

await is duck-typed. Anything with an accessible GetAwaiter() (instance or extension) returning a type that has bool IsCompleted, GetResult(), and implements INotifyCompletion (ideally ICriticalNotifyCompletion) can be awaited. That is how Task, ValueTask, Task.Yield() (a YieldAwaitable), ConfigureAwait(...) (a ConfiguredTaskAwaitable) and custom awaitables all plug into one language feature. The "Unsafe" variant exists because the builder already handles ExecutionContext flow, so the awaiter is told not to capture it again — one of several places where the design avoids duplicate work per await.

// Running example for the whole guide: an order summary that fans out to two services.
public sealed class OrderSummaryService(HttpClient http)
{
    public async Task<OrderSummary> GetOrderSummaryAsync(int orderId, CancellationToken ct)
    {
        Console.WriteLine($"[{Environment.CurrentManagedThreadId}] start (caller's thread)");

        // Both requests are *started* here; neither blocks a thread while in flight.
        Task<Inventory> inventory = http.GetFromJsonAsync<Inventory>($"/inventory/{orderId}", ct)!;
        Task<Pricing>   pricing   = http.GetFromJsonAsync<Pricing>($"/pricing/{orderId}", ct)!;

        await Task.WhenAll(inventory, pricing);          // first incomplete await: method returns to caller here

        Console.WriteLine($"[{Environment.CurrentManagedThreadId}] resumed (whatever thread completed the I/O)");
        return new OrderSummary(inventory.Result, pricing.Result); // .Result is safe: both are known complete
    }
}

A simplified sketch of what the compiler produces for that method (names are illustrative; the real ones are unspeakable like <GetOrderSummaryAsync>d__0):

// Release build: a struct. One box allocation happens on the FIRST incomplete await, never again.
struct GetOrderSummaryAsync_StateMachine : IAsyncStateMachine
{
    public int state;                                   // -1 = not started, 0.. = suspended at await N, -2 = done
    public AsyncTaskMethodBuilder<OrderSummary> builder;
    public OrderSummaryService self; public int orderId; public CancellationToken ct;   // parameters, hoisted
    private Task<Inventory> inventory; private Task<Pricing> pricing;                  // locals that live across an await
    private TaskAwaiter awaiter;                                                          // the in-flight awaiter

    public void MoveNext()
    {
        OrderSummary result;
        try
        {
            if (state == 0) goto Resume0;                                    // jump table on resume
            inventory = self.http.GetFromJsonAsync<Inventory>(...);
            pricing   = self.http.GetFromJsonAsync<Pricing>(...);
            awaiter = Task.WhenAll(inventory, pricing).GetAwaiter();
            if (!awaiter.IsCompleted)
            {
                state = 0;
                builder.AwaitUnsafeOnCompleted(ref awaiter, ref this);         // boxes 'this' (once), registers continuation
                return;                                                        // <-- caller gets an incomplete Task
            }
        Resume0:
            state = -1;
            awaiter.GetResult();                                               // rethrows if faulted/cancelled
            result = new OrderSummary(inventory.Result, pricing.Result);
        }
        catch (Exception ex) { state = -2; builder.SetException(ex); return; } // exception goes INTO the task
        state = -2;
        builder.SetResult(result);                                             // completes the task, runs ITS continuations
    }
    public void SetStateMachine(IAsyncStateMachine sm) => builder.SetStateMachine(sm);
}

Cost model and what changed recently

An async method that completes synchronously allocates nothing beyond its result task, and even that is often cached (Task.CompletedTask, Task<bool>, small Task<int> values; ValueTask removes the rest, Unit 7). One that suspends allocates the box once. .NET Core 2.1 (2018) collapsed what used to be ~4 allocations per suspending method into that single box; .NET 6 added a pooling builder for ValueTask methods; .NET 11 skips capturing/restoring ExecutionContext when there is nothing to restore (no AsyncLocal<T> in play), for both Task and ValueTask continuations. The biggest change is Runtime Async in the .NET 11 previews (Unit 10): the compiler stops emitting the state machine and marks the method [MethodImpl(MethodImplOptions.Async)], and the runtime suspends/resumes it directly. The observable semantics described above are deliberately unchanged, which is exactly why this mental model is worth internalizing: it survives the implementation swap.

Interview trap

"When the method hits await, it returns." No: it returns at the first await whose awaitable is not already complete. Everything before that — including a CPU-heavy loop or a synchronous File.ReadAllText — runs on the caller's thread. That is why an async button handler can still freeze a UI, why async does not make a method "run in the background", and why "make it async" is not a fix for CPU-bound work (use Task.Run for that, from UI code — not from ASP.NET Core request code, Unit 3). Corollary: marking a method async with no await (CS1998) makes it run fully synchronously, just with exceptions redirected into the task.

Interview Q&A

Q1. What does the C# compiler actually do with an async method?

It rewrites the body into a state machine type with a MoveNext method, hoists locals that live across awaits into fields, and picks a builder from the return type. The public method just creates the machine, calls builder.Start, which runs MoveNext synchronously on the caller's thread, and returns builder.Task. At each await it checks IsCompleted; if the operation is already done it continues inline, otherwise it records the state, registers a continuation with the awaiter and returns. The async keyword itself is only a compiler instruction — it is not part of the method signature or the IL, which is why interfaces cannot require it and why callers cannot tell the difference between an async method and a hand-written Task-returning one.

Q2. Does await create or use a new thread? Then what runs the continuation?

No thread is created and none waits. For true I/O the operation is owned by the OS and the hardware; when it completes, a completion is posted to the thread pool (via IOCP on Windows, epoll on Linux) and a pool thread runs the continuation, which resumes the state machine. If a SynchronizationContext or non-default TaskScheduler was captured, the continuation is posted there instead. The thread that resumes is therefore "whichever thread completed the awaited task", and code after an await must not assume thread identity. The only thing that sits around while the operation is in flight is a heap object holding the hoisted state — which is why async scales to far more concurrent operations than threads.

Q3. What happens at an await when the task is already complete?

The fast path: the awaiter reports IsCompleted, the compiler-generated code calls GetResult() immediately and execution continues on the same thread with no suspension, no boxing, and no context switch. This matters for performance because many awaits in real code hit completed tasks — cached results, buffered stream reads, already-completed Task.CompletedTask — and the design makes those nearly free. It also matters for correctness reasoning: ConfigureAwait(false) has no effect on a completed task, so you cannot rely on an await to "move off the UI thread" unless you force a yield with Task.Yield() or, since .NET 8, ConfigureAwaitOptions.ForceYielding.

Q4. Where does the synchronous prefix of an async method run, and why do leads care?

On the caller's thread, up to the first incomplete await. In a UI app that means argument validation, synchronous parsing, or an accidental blocking call all happen on the dispatcher thread; in a library it means a synchronous exception thrown before the first await is still captured into the task rather than thrown at the call site. I care because it shapes API design: expensive synchronous preambles should be moved after a yield or into Task.Run on the client side, argument validation should be deliberately synchronous (the "async elision" wrapper pattern) if you want eager exceptions, and in server code it explains why an "async" endpoint with a synchronous hash computation still monopolizes a pool thread.

Q5. How many allocations does an async method cost, and when are they paid?

If the method never suspends: zero beyond the result task, and even that is cached for Task, Task<bool> and small integers; with ValueTask it is zero. If it suspends: one allocation for the state-machine box, which since .NET Core 2.1 is also the returned Task object, and it is reused for every later suspension in that call. Older .NET Framework paid about four allocations per suspending method (box, task, continuation delegate, context wrapper). .NET 6's PoolingAsyncValueTaskMethodBuilder can recycle even the box, and .NET 11's Runtime Async reuses continuation objects and skips ExecutionContext capture when there is nothing to flow. So the honest performance answer is "async is cheap per call; the cost is per suspension, and you tune it only on hot paths."

Q6. What is the awaitable pattern? Can you await something that is not a Task?

await is pattern-based, like foreach. The compiler needs GetAwaiter() — instance or extension — returning a type with IsCompleted, GetResult() and INotifyCompletion, preferably ICriticalNotifyCompletion so the builder can use the "unsafe" path that does not double-capture ExecutionContext. That is how ValueTask, Task.Yield(), ConfigureAwait results and custom awaitables all work, and you can add GetAwaiter to your own types — people have done it for TimeSpan, Process and CancellationToken. My guidance for teams is to be conservative: custom awaitables are great inside frameworks and hot paths, but in application code they surprise readers and confuse analyzers, so I want a design review before one appears in a shared library.

Q7. Why does an exception inside an async method not throw at the call site?

Because MoveNext wraps the whole body in a try/catch and routes any exception into builder.SetException, which faults the task; the exception then surfaces when someone awaits (or calls .Result/.Wait()). This holds even for exceptions thrown before the first await, which differs from a non-async method that returns a Task and throws synchronously. The rethrow uses ExceptionDispatchInfo so the original stack is preserved, and await unwraps the first exception rather than handing you an AggregateException. The design decision was consistency: from the caller's perspective every failure of an async operation arrives through the task, whether it happened synchronously or later.

Q8. Why is the state machine a struct in Release but a class in Debug?

In Release the struct avoids any allocation for methods that complete synchronously and lets the builder box it exactly once on the first suspension. In Debug the compiler emits a class so that the debugger and Edit & Continue can hold a stable reference to the machine and inspect hoisted locals; allocation cost is irrelevant there. This is why benchmarks of async code must run in Release, and why "we saw lots of state-machine allocations in the profiler" is a question I answer with "which configuration?" before anything else.

Q9. How does the resumed method know where to continue, and what state is preserved?

The machine has an integer state field; before suspending, the compiler stores the index of the await, and MoveNext begins with a jump table on that field. Only values needed after the await are hoisted into fields: parameters, this, locals that span the await, and the in-flight awaiter. Everything else is recomputed or dead. Structures like try/finally are re-entered by the jump, which is how using and lock-free cleanup keep working across suspensions. Two consequences worth knowing: ref locals and Span<T> cannot live across an await because they cannot be hoisted to the heap, and the same restriction reappears in Runtime Async's spec as "byref-like locals default after a suspension point".

Q10. Explain async/await to a junior in two minutes without lying to them.

"An async method runs like any other method until it needs to wait for something slow, such as a network reply. Instead of blocking the thread, await tells the operation 'call me back here when you are done', packs up the method's local variables into an object, and returns to the caller so the thread can do other work. When the reply arrives, the runtime picks a thread, unpacks the object, and continues from the line after the await. The Task you get back is a promise that this will eventually finish and either produce a result or an exception. Two rules follow: never block on a task with .Result, because you would waste the thread you just freed, and never assume you are on the same thread after an await." That is accurate, and every detail in this unit is a refinement of it, not a correction.

02

Task anatomy and composition

Official: Consuming the TAP Task.WhenEach Task.WaitAsync TaskCompletionSource<T>

A Task is a promise: an object that will eventually be in one of three final states — RanToCompletion, Faulted (with an AggregateException inside) or Canceled. There are two families and interviewers like candidates who separate them. Delegate tasks wrap code to run somewhere, created by Task.Run or Task.Factory.StartNew and executed by a TaskScheduler (the thread pool by default). Promise tasks represent the completion of something that is not code on a scheduler at all — an I/O completion, a timer, a TaskCompletionSource, or an async method's state machine. Most tasks you await in modern code are promise tasks, which is why "which thread is the task running on?" is usually a category error: an in-flight HttpClient request is running on no thread.

TAP tasks are always hot: the operation is started by the method that returns the task. The pre-2012 new Task(...) + .Start() pair is a legacy smell (the "cold task" model), as are most uses of ContinueWith, which predates await, ignores SynchronizationContext unless you pass a scheduler, and hands you the antecedent task rather than its result so exceptions are easy to swallow. The one modern niche for ContinueWith is attaching an OnlyOnFaulted logger to a fire-and-forget task (Unit 5).

Task.Run versus Task.Factory.StartNew

Task.Run(work) is Task.Factory.StartNew(work, CancellationToken.None, TaskCreationOptions.DenyChildAttach, TaskScheduler.Default) plus an automatic Unwrap() when the delegate is async. StartNew still exists for two reasons: TaskCreationOptions.LongRunning, which on the default scheduler creates a dedicated thread outside the pool (right for a long-lived blocking loop such as a legacy queue consumer; wrong for an async loop, because the dedicated thread is abandoned at the first await), and passing a custom TaskScheduler. Its traps are that it defaults to TaskScheduler.Current, which may be a custom scheduler if you are already inside one, and that StartNew(async () => ...) returns Task<Task> — awaiting it observes only the start of the inner work.

TaskCompletionSource: the bridge

TaskCompletionSource<T> (non-generic since .NET 5) is how you manufacture a promise task for anything callback- or event-shaped: a legacy EAP API, a message correlation id, a "wait until the connection is ready" signal. The rule that separates seniors from juniors: construct it with TaskCreationOptions.RunContinuationsAsynchronously. Without it, SetResult runs every awaiting continuation synchronously on the calling thread, inline, before SetResult returns. That thread might be a socket-receive loop, a timer callback, or code holding a lock; a slow continuation then stalls the producer, and deep chains can even overflow the stack. Use TrySet* when several parties may race to complete it.

// Wrapping an event-based (EAP-style) client in a promise task.
public Task<Reply> SendAsync(Request request, CancellationToken ct)
{
    var tcs = new TaskCompletionSource<Reply>(TaskCreationOptions.RunContinuationsAsynchronously);

    void OnReply(object? s, ReplyEventArgs e)
    {
        if (e.CorrelationId != request.Id) return;
        _client.ReplyReceived -= OnReply;
        if (e.Error is not null) tcs.TrySetException(e.Error);
        else                     tcs.TrySetResult(e.Reply);
    }

    _client.ReplyReceived += OnReply;
    // Make it cancellable: a registration that fails the promise. Dispose the registration when done (Unit 6).
    CancellationTokenRegistration reg = ct.Register(static state =>
        ((TaskCompletionSource<Reply>)state!).TrySetCanceled(), tcs);
    tcs.Task.ContinueWith(static (_, r) => ((CancellationTokenRegistration)r!).Dispose(), reg,
        CancellationToken.None, TaskContinuationOptions.ExecuteSynchronously, TaskScheduler.Default);

    _client.Send(request);          // fire the actual operation LAST, after all hooks are in place
    return tcs.Task;
}

Combinators

Task.WhenAll returns a task that completes when all inputs complete, with results in input order for Task<T>. If several fault, awaiting it throws only the first exception; the full set is on whenAllTask.Exception.InnerExceptions. Task.WhenAny completes with the first completed task (faulted or cancelled counts as completed) and returns that task, so you await it twice: once for the winner, once to observe its result; the losers keep running and must be cancelled or at least observed. Task.WhenEach .NET 9 yields an IAsyncEnumerable<Task<T>> in completion order, replacing the O(n²) "WhenAny-and-remove in a loop" idiom. task.WaitAsync(timeout, ct) .NET 6 lets you stop waiting for a task you cannot cancel — it does not stop the underlying work, and the abandoned task should still be observed. .NET 9 added params ReadOnlySpan<Task> overloads (C# 13 params spans) so WhenAll(a, b, c) no longer allocates an array; .NET 8 added TimeProvider overloads to Task.Delay and WaitAsync for testability.

// Fan-out with complete failure reporting.
var tasks = orderIds.Select(id => svc.GetOrderSummaryAsync(id, ct)).ToArray();
Task<OrderSummary[]> all = Task.WhenAll(tasks);
try
{
    OrderSummary[] summaries = await all;
}
catch (Exception first) when (all.Exception is { } agg)     // 'first' is only the first failure
{
    foreach (var ex in agg.Flatten().InnerExceptions) log.Error(ex, "order summary failed");
    throw;
}

// Completion-order processing (.NET 9): report each result as soon as it lands.
await foreach (Task<OrderSummary> t in Task.WhenEach(tasks).WithCancellation(ct))
{
    if (t.IsCompletedSuccessfully) Render(t.Result);
    else                           log.Warn(t.Exception?.GetBaseException(), "one order failed");
}

// A timeout on something you cannot cancel (.NET 6). The underlying work keeps running.
try { await legacyTask.WaitAsync(TimeSpan.FromSeconds(2), ct); }
catch (TimeoutException) { _ = legacyTask.ContinueWith(t => log.Warn(t.Exception), TaskContinuationOptions.OnlyOnFaulted); }

Interview trap

"We used Task.WhenAny with a Task.Delay to implement a timeout." It works, but candidates forget three things: the timed-out task keeps running and holds resources, its eventual exception is unobserved, and the Delay timer keeps ticking after the real task wins unless you cancel it. Interview Q&A

Q1. What is the difference between a delegate task and a promise task, and why are TAP tasks "hot"?

A delegate task wraps code and is executed by a scheduler — that is what Task.Run creates. A promise task represents the eventual completion of something external: I/O, a timer, a TaskCompletionSource, an async method. Nearly everything you await in modern code is a promise task, which means it does not "run on" any thread while in flight. TAP mandates hot tasks — the operation starts inside the method that returns the task — so callers can compose them immediately with WhenAll and never need Start(). Cold tasks (new Task) are a pre-async relic; if I see one in review, I ask what problem it solves, and the answer is almost always "none".

Q2. Task.Run versus Task.Factory.StartNew: when would you still use StartNew?

Task.Run is a safe default: default scheduler, DenyChildAttach, and it unwraps async delegates. StartNew is for two things — TaskCreationOptions.LongRunning to get a dedicated thread for a genuinely long blocking loop, and running on a custom TaskScheduler. Its traps are that it picks up TaskScheduler.Current, so inside another scheduled task you may land somewhere unexpected, and that with an async lambda it returns Task<Task>, which completes as soon as the inner method hits its first await unless you Unwrap(). In codebases from the .NET 4.0 era I see StartNew everywhere because Task.Run arrived with .NET 4.5; converting is mechanical but I add a test around anything using AttachedToParent first.

Q3. Why do you insist on RunContinuationsAsynchronously for TaskCompletionSource?

Because by default SetResult runs the awaiting continuations synchronously, inline, on the thread that called it. That thread is usually something precious — a socket receive loop, a timer callback, a lock holder — and a slow or blocking continuation stalls it; in pathological cases it deadlocks (continuation needs the lock the setter holds) or overflows the stack in long chains. The option queues continuations to the pool instead, decoupling producer from consumers at the cost of one extra hop. Stephen Toub's guidance is to use it by default and only remove it after measuring; I make it a code-review rule and an analyzer suggestion in shared repos.

Q4. What are Task.WhenAll's exception semantics and how do you surface every failure?

The combined task faults with an AggregateException holding every inner exception, but await unwraps and throws only the first one, in input order. To see all of them, keep a reference to the WhenAll task and read .Exception.InnerExceptions in the catch, or inspect each input task's status afterwards. A common bug is awaiting the inputs one by one in a loop instead, which stops at the first failure and leaves the others unobserved. For batch jobs I typically wrap this into a helper that returns a result-per-item structure so callers never re-invent the aggregation.

Q5. How do you use Task.WhenAny correctly?

WhenAny returns the first task to complete in any state, so you await the returned task to observe its result or exception. The losers keep running, so a correct pattern cancels them with a token and observes their eventual completion, or at least attaches a fault handler so exceptions are not silently unobserved. Using it in a loop to process tasks in completion order is O(n²) and is exactly what Task.WhenEach in .NET 9 replaces. For timeouts, WaitAsync is now the idiomatic shape rather than racing against Task.Delay.

Q6. What problem does Task.WhenEach solve?

Processing results as they arrive rather than waiting for the slowest — think rendering search results from several providers, or streaming progress for a batch. Before .NET 9 you either wrote the WhenAny-remove loop, which is quadratic and error-prone, or built a Channel and fed it. WhenEach returns an IAsyncEnumerable<Task<T>> that yields each task exactly once as it completes, and because you get the task rather than the value you can inspect fault or cancellation per item. It composes with WithCancellation and the new System.Linq.AsyncEnumerable operators in .NET 10.

Q7. What does Task.WaitAsync do, and what does it not do?

It returns a new task that completes when the original completes, when the timeout elapses (TimeoutException), or when the token is cancelled (OperationCanceledException). It does not cancel or stop the original operation — that is still running, holding its connection or buffer, and if it later faults that exception is unobserved unless you attach a handler. So it is the right tool for "stop waiting for a legacy API I cannot cancel" and the wrong tool as a substitute for passing a real cancellation token. The .NET 8 overloads taking a TimeProvider let tests drive the timeout with a fake clock instead of real time.

Q8. How do you adapt legacy APM/EAP APIs to TAP, and the reverse?

For APM (BeginX/EndX with IAsyncResult) use Task.Factory.FromAsync(BeginX, EndX, state), which handles the callback plumbing and exception marshalling. For EAP (XAsync plus a XCompleted event) use a TaskCompletionSource: subscribe, start, complete the source from the event, unsubscribe, and wire cancellation through ct.Register — always with RunContinuationsAsynchronously. The reverse direction, exposing a Task-based method through IAsyncResult for an old interface, got an official helper in .NET 8: TaskToAsyncResult.Begin/End. In a migration I isolate these adapters in one place so the rest of the codebase only ever sees tasks.

Q9. What does TaskCreationOptions.LongRunning actually do, and when is it wrong?

On the default scheduler it creates a dedicated non-pool thread for the delegate instead of queuing it, so a long-running blocking loop does not occupy a pool thread and does not trigger hill-climbing. It is right for a legacy consumer that blocks on a queue or a COM/STA affinity requirement. It is wrong for async delegates: the dedicated thread is abandoned at the first incomplete await and all continuations run on the pool anyway, so you paid for a thread that did nothing. It is also not a priority or a scheduling guarantee, which is what people sometimes assume.

Q10. Task.Delay versus Thread.Sleep, and what does Task.Yield really do?

Thread.Sleep blocks the current thread; on a pool thread that is starvation fuel. Task.Delay creates a timer-backed promise task and returns; no thread is held, and it accepts a cancellation token and, since .NET 8, a TimeProvider. Task.Yield returns an awaitable that always reports not-completed, so the method suspends and the continuation is posted to the captured SynchronizationContext if there is one, otherwise queued to the pool; it is how you let a UI thread pump messages or split a long method into pieces. Note it has no ConfigureAwait; if you want "yield to the thread pool regardless of context" the .NET 8 way is Task.CompletedTask.ConfigureAwait(ConfigureAwaitOptions.ForceYielding).

The thread pool: injection, starvation and sync-over-async

Official: The managed thread pool Debug ThreadPool starvation Threading config settings

Async code is only as healthy as the pool that runs its continuations, and most production async incidents are thread-pool incidents. The pool has worker threads that execute queued work items and task continuations, plus I/O completion handling (IOCP on Windows, epoll/kqueue engines on Unix) that turns OS completions into queued continuations. Since .NET 6 the pool is the fully managed portable thread pool on every OS, with the Windows I/O completion processing moving into managed code as well in .NET 7; .NET 8 added an opt-in to delegate to the native Windows thread pool (UseWindowsThreadPool), which is the default only for NativeAOT apps on Windows and disables SetMinThreads/SetMaxThreads.

Work is queued into a global FIFO queue plus a per-thread local queue for each worker. A worker takes from its own local queue LIFO (the most recently queued item is hot in cache) and, when empty, steals from other workers' queues FIFO — the classic work-stealing design. Continuations of tasks completed on a pool thread prefer the local queue, which is why a chain of awaits often stays on the same thread: not a guarantee, a cache-friendliness heuristic.

Sizing and injection

The minimum worker count defaults to Environment.ProcessorCount (cgroup-aware: a container limited to 0.5 CPU reports 1), the maximum to 32,767. Up to the minimum, threads are created on demand without delay. Beyond it the gate thread runs hill-climbing: it samples throughput and adds or removes threads to maximize completed work items per second, with a cap of roughly one new thread per 500 ms while the queue is not draining. That slow ramp is deliberate — threads are expensive and usually the existing ones free up first — and it is also why starvation feels like a slow-motion outage rather than a crash.

.NET 6 added blocking-aware injection: when a pool thread blocks inside a Task wait (Task.Wait, .Result, GetAwaiter().GetResult(), Task.WaitAll) the pool is notified and may immediately add threads, bypassing hill-climbing. The runtime defaults (all configurable under System.Threading.ThreadPool.Blocking.*) add about 1.25 × processor-count threads with no delay, then slow down in 25 ms steps up to 250 ms, and back off further when physical memory is tight (IgnoreMemoryUsage disables that, .NET 7). The crucial limitation: only Task-style waits notify the pool. Thread.Sleep, lock/Monitor.Wait, SemaphoreSlim.Wait, ManualResetEventSlim.Wait, synchronous socket/file I/O and HttpClient.Send get only the slow ramp. Microsoft's own starvation tutorial shows the difference: an endpoint doing .Result on a 500 ms task degrades to ~3.5 s p50 under 125 connections, the one doing Thread.Sleep inside a task to ~15 s.

Starvation: what it looks like

Starvation is the state where every worker is busy or blocked, queued items wait for a thread, and the pool adds threads too slowly to catch up. The signature in production: latency climbing while CPU stays well under 100%, dotnet.thread_pool.thread.count rising steadily (2–3× cores fast, then 1–2 per second), dotnet.thread_pool.queue.length large, dotnet.thread_pool.work_item.count low. When the count finally stabilizes the pool is no longer starving, but if it stabilizes above ~3× cores, code is blocking pool threads and the pool is compensating. The nasty second-order effect: health checks are also queued work items, so the orchestrator kills the "unhealthy" pod, the replacement starts with a cold pool, and the ramp starts over — a restart loop caused by a .Result.

Fixing it for real

The only cure is async all the way down: the request path must not block a pool thread. If a dependency is synchronous by nature (a legacy SDK, a driver), you have three honest options: bound its concurrency with a SemaphoreSlim so it can consume at most N pool threads, move it onto dedicated threads (TaskCreationOptions.LongRunning consumer loop, or a small ConcurrentExclusiveSchedulerPair-style scheduler) fed by a Channel, or raise the minimum thread count as a temporary mitigation while you fix the code — and write that "temporary" into the ticket, because the extra threads cost memory, context switches, and hide the next regression. Task.Run(() => sync.Call()) is not a fix in a server: it moves the block to another pool thread and adds a hop. One more nuance interviewers enjoy: on Unix, asynchronous file reads are performed by pool threads calling blocking pread under the hood (there is no io_uring path yet), so "async" file-heavy workloads still consume workers, whereas sockets are truly asynchronous via epoll.

Interview trap

Say instead: "we raised min threads as a same-day mitigation and used dotnet-stack / the WaitHandleWait trace to find the .Result". A second trap: "Task.Run makes the sync call async". It makes the caller non-blocking at the cost of a different pool thread — fine in a UI app to keep the dispatcher free, pointless in ASP.NET Core where the caller already is a pool thread.

Interview Q&A

Q1. Describe the modern .NET thread pool architecture.

Since .NET 6 it is a managed, portable pool on every platform: a set of worker threads, a global FIFO queue, and per-worker local queues that are consumed LIFO by their owner and stolen FIFO by others, which gives cache locality and load balancing. I/O completions come from IOCP or epoll engines and are turned into queued continuations, so I/O-bound code never holds a worker while waiting. A gate thread watches the queue and runs hill-climbing to size the pool beyond the minimum, and since .NET 6 the pool also reacts immediately to Task-style blocking. .NET 8 lets Windows apps delegate to the native Windows pool, which is the default only under NativeAOT, and .NET 10 added environment-variable overrides for min and max threads for containers where you cannot touch runtimeconfig.

Q2. What are the default sizes, and how does the pool decide to add a thread?

Minimum workers equal the processor count as the runtime sees it — cgroup-aware, so a 0.5-CPU pod starts with one — and the maximum is 32,767. Up to the minimum, threads are created immediately on demand. Above it, hill-climbing measures throughput and injects roughly one thread per half second while work is queued and not draining, and it removes threads when they stop improving throughput. Separately, since .NET 6, a worker that blocks in a Task wait notifies the pool, which may add threads at once, about 1.25× cores without delay before backing off. Knowing those two rates lets you read a thread-count graph and say whether you are looking at Task blocking or something invisible like Thread.Sleep or a sync socket call.

Q3. What is thread-pool starvation, and how do you detect it in production without a debugger?

Starvation is when queued work waits because all workers are busy or blocked and the pool cannot add threads fast enough. The production signature is rising latency with low CPU, thread count climbing slowly and steadily, queue length growing and completed items per second flat. I look at dotnet.thread_pool.thread.count, queue.length and work_item.count on the dashboard — those are the .NET 9 counter names; older runtimes expose threadpool-thread-count and friends. To find the culprit I use dotnet-stack for a persistent problem, or a dotnet-trace capture of the .NET 9 WaitHandleWait events for an intermittent one, and look for pool threads whose top frames are GetResultCore, ManualResetEventSlim.Wait or a sync I/O call. A dump with clrstack -all and dumpasync is the post-mortem route.

Q4. What changed about blocking in .NET 6, and what does it still not catch?

.NET 6's portable pool added blocking-aware injection: Task.Wait, .Result and GetAwaiter().GetResult() tell the pool that a worker is parked, and the pool injects replacements immediately rather than waiting for hill-climbing. That shortened sync-over-async starvation episodes from minutes to seconds, but it did not make the pattern acceptable — the threads still exist and the memory is still spent. It catches nothing that does not go through Task's wait path: Thread.Sleep, monitors, semaphores, sync sockets and file I/O, or the sync HttpClient.Send added in .NET 5. In .NET 9 the WaitHandleWait event made those other waits at least observable in traces.

Q5. Why is .Result in a request path so damaging, and how do .Result, .Wait() and GetAwaiter().GetResult() differ?

All three block the current thread until the task completes, so in a server they turn a request that should cost a heap object into one that costs a thread for its whole duration; under load that is starvation, and in a UI or classic ASP.NET app with a SynchronizationContext it is a deadlock. The differences are cosmetic: .Result and .Wait() wrap failures in an AggregateException, while GetAwaiter().GetResult() rethrows the original exception the way await does — which is why it is the least-bad choice at a genuine sync boundary such as Main in old frameworks or a synchronous interface you cannot change. In review I treat all three as a design smell that needs a comment explaining the boundary; the CA1849 and VSTHRD002 analyzers flag them automatically.

Q6. Incident: p99 spikes for two minutes after every deploy, CPU sits at 20%. Walk me through it.

Low CPU with high latency right after a start says "cold thread pool plus blocking", not compute. I would confirm with the thread-count counter: if it climbs steadily from the core count for those two minutes and then plateaus high, something in the hot path blocks and the pool is ramping to compensate; the plateau height tells me how many concurrent blocks there are. Then dotnet-stack during the spike, or a WaitHandleWait trace, to find which call blocks — often a cache warm-up or a synchronous config/secrets fetch inside a request path, or a middleware calling .Result. Mitigation for tonight might be raising min threads or moving the warm-up to a hosted service before the readiness probe reports healthy; the fix is removing the block. I would also add the counter to the deploy dashboard so the next regression is caught in canary.

Q7. Is raising the minimum thread count ever the right call?

Yes, as a bounded mitigation or when the workload genuinely needs parked threads by design: a service that must call a synchronous third-party SDK under bursty load, or a gRPC/Kafka client library that blocks internally and that you cannot change this quarter. In those cases I set it via configuration rather than code — ThreadPoolMinThreads in the project or the runtimeconfig knob — size it from observed plateau plus headroom, and document the cost: each thread reserves stack, adds scheduler pressure and, more importantly, hides new blocking regressions because the pool no longer struggles visibly. What I refuse is the "set it to 500 and forget it" cargo cult, because it turns the pool's early-warning signal off.

Q8. How do containers change thread-pool behaviour?

The runtime derives Environment.ProcessorCount from the cgroup CPU quota, rounded up, so a pod limited to 500m CPU sees one processor and starts with one worker thread and one GC heap. That makes any blocking call catastrophic — a single .Result stalls the whole service — and it makes the hill-climb ramp painfully visible. It also affects Parallel.ForEachAsync's default degree of parallelism. When a team insists on a tiny CPU limit for a request-serving pod I ask them to justify it against the thread-pool math, and if they need it I document DOTNET_PROCESSOR_COUNT or the .NET 10 DOTNET_ThreadPool_ForceMinWorkerThreads override as explicit, reviewed configuration rather than a surprise.

Q9. When is a custom TaskScheduler or a dedicated thread justified?

Rarely, and each case has a name. Thread affinity — STA/COM objects, some native SDKs, UI toolkits — needs a dedicated thread, usually via LongRunning or a hand-rolled single-thread scheduler. Isolating a synchronous, blocking dependency so it cannot starve the shared pool justifies a small dedicated scheduler or ConcurrentExclusiveSchedulerPair with a limited concurrency level. Priority or fairness requirements might justify one, though prioritized channels in .NET 9 cover many of those. What I push back on is a custom scheduler used to "limit concurrency" of async work — that is what SemaphoreSlim, Parallel.ForEachAsync and bounded channels are for, and they do not fragment the pool.

Q10. When is Task.Run acceptable inside an ASP.NET Core request?

Almost never for parallelism: the request is already on a pool thread, so Task.Run just adds a hop and, under load, competes with other requests for the same workers. Short CPU-bound work should simply run inline; long CPU-bound work should not live in a request at all — accept the job, hand it to a background service through a bounded channel, and let the client poll or receive a callback. The narrow legitimate cases are running a few independent CPU-heavy computations in parallel when the machine is otherwise idle, and isolating a synchronous library call that you also bound with a semaphore. The question I ask in review is "which thread were you trying to free, and who is going to use it?"

SynchronizationContext, ConfigureAwait and ExecutionContext

Official: ConfigureAwait FAQ (Stephen Toub) ConfigureAwaitOptions SynchronizationContext AsyncLocal<T>

Two unrelated things called "context" flow across an await, and conflating them is the single most common conceptual error in this topic. The first decides where the continuation runs: the SynchronizationContext (or, failing that, the non-default TaskScheduler) that was current at the await. It is captured by default and opted out of with ConfigureAwait(false). The second decides what ambient state the continuation sees: the ExecutionContext, which carries every AsyncLocal<T> value — and therefore logging scopes, Activity.Current for distributed tracing, culture, impersonation. It always flows, regardless of ConfigureAwait, unless you explicitly ExecutionContext.SuppressFlow().

SynchronizationContext: "run this here"

A SynchronizationContext is an abstraction over "post this delegate to run in my world". WPF installs a DispatcherSynchronizationContext, WinForms a WindowsFormsSynchronizationContext, MAUI its platform dispatcher; each marshals to the one UI thread. Blazor Server installs a RendererSynchronizationContext that serializes all work for a circuit onto one logical thread, so component code never races with rendering even though physical threads vary; Blazor WebAssembly is single-threaded. Classic ASP.NET (System.Web) had the AspNetSynchronizationContext, which allowed one thread at a time per request and is the origin of the famous deadlock. ASP.NET Core has none: continuations go straight to the thread pool, which removed the deadlock class and made ConfigureAwait(false) in application code a matter of taste. Console apps have none either; xUnit v2 installs its own to limit test parallelism.

When the awaiter suspends, it captures SynchronizationContext.Current if it is non-null and not the default one, else TaskScheduler.Current if not the default — and later posts the continuation there. ConfigureAwait(false) skips the capture, so the continuation runs on whatever thread completed the task, typically a pool thread. Three properties follow that interviewers probe: it applies to that one await only; it does nothing if the task was already complete; and it is a per-await decision, so a single unconfigured await anywhere up the chain re-introduces the capture.

// The classic deadlock: UI (or classic ASP.NET) thread blocks on a task whose continuation needs that same thread.
private void OnClick(object sender, EventArgs e)
{
    string json = LoadAsync().Result;      // UI thread parks here, waiting for LoadAsync's task...
    textBox.Text = json;
}
private async Task<string> LoadAsync()
{
    using var http = new HttpClient();
    var s = await http.GetStringAsync(url); // ...but the continuation was posted to the UI context, which is blocked. Forever.
    return s.Trim();
}

// Fix hierarchy: (1) async all the way — make OnClick 'async void' (the one legitimate use) and await;
// (2) in *library* code, ConfigureAwait(false) on every await so the library never needs the caller's context;
// (3) last resort at a genuine sync boundary: Task.Run(() => LoadAsync()).GetAwaiter().GetResult() — costs a pool thread.
private async void OnClickFixed(object sender, EventArgs e)
{
    try { textBox.Text = await LoadAsync(); }   // continuation returns to the UI thread: touching controls is safe
    catch (HttpRequestException ex) { ShowError(ex); }
}

ConfigureAwaitOptions .NET 8

Task.ConfigureAwait(ConfigureAwaitOptions) takes a flags enum: None (0, same as false), ContinueOnCapturedContext (1, same as true), SuppressThrowing (2) and ForceYielding (4). SuppressThrowing makes the await complete quietly for a faulted or cancelled task and marks the exception observed — ideal for "await this WhenAll, then inspect each task" or for shutdown code that must not throw; it is only permitted on the non-generic Task, because a Task<T> would have no result to return, and the Task<T> overload throws ArgumentOutOfRangeException if you try (upcast to Task first). ForceYielding makes an already-completed task behave as incomplete, so the method suspends; Task.CompletedTask.ConfigureAwait(ConfigureAwaitOptions.ForceYielding) is the context-free replacement for Task.Yield(), which cannot be configured. ValueTask only has the boolean overload.

// Library code: never depend on the caller's context (CA2007 / VSTHRD111 enforce this).
public async Task<Config> LoadConfigAsync(CancellationToken ct)
{
    await using var stream = File.OpenRead(path);
    var cfg = await JsonSerializer.DeserializeAsync<Config>(stream, options, ct).ConfigureAwait(false);
    return cfg ?? throw new InvalidDataException(path);
}

// .NET 8: wait for everything, throw for nothing, then decide.
Task all = Task.WhenAll(tasks);
await all.ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing);
foreach (var t in tasks) if (t.IsFaulted) log.Error(t.Exception!.GetBaseException(), "worker failed");

// .NET 8: guarantee we leave the caller's thread even if everything below completes synchronously.
public async Task RunInBackgroundAsync()
{
    await Task.CompletedTask.ConfigureAwait(ConfigureAwaitOptions.ForceYielding); // now on a pool thread, no captured context
    DoCpuWork();
}

ExecutionContext and AsyncLocal<T>

ExecutionContext is an immutable, copy-on-write snapshot of ambient state. It is captured wherever work is forked — at an await suspension, Task.Run, ThreadPool.QueueUserWorkItem, timers, CancellationToken.Register — and restored around the continuation, so AsyncLocal<T> reads the same value after an await even on a different thread. That is what makes ILogger.BeginScope and Activity.Current "just work" across awaits, and it is why [ThreadStatic] and ThreadLocal<T> are wrong in async code — after an await you may be on another thread with somebody else's value. The subtle rule: the flow is a copy, so a value set inside an async callee is not visible to the awaiting caller once control returns, and values set after a fork are invisible to the already-forked flow. ExecutionContext.SuppressFlow() exists for fire-and-forget work that must not inherit request state. .NET 11 makes all of this cheaper: continuations skip the capture/restore entirely when there is nothing to restore, which benefits both compiler-generated and runtime-async methods and rewards code that uses ConfigureAwait(false) and AsyncLocal sparingly.

static readonly AsyncLocal<string?> Tenant = new();

    await Callee();
    Console.WriteLine(Tenant.Value);   // "acme" — the callee's change did not flow back
    _ = Task.Run(() => Console.WriteLine(Tenant.Value)); // "acme" — captured at the fork
    using (ExecutionContext.SuppressFlow())
        _ = Task.Run(() => Console.WriteLine(Tenant.Value)); // null — nothing flowed
}
static async Task Callee()
{
    Tenant.Value = "changed-in-callee";

Interview Q&A

Q1. What are the two contexts that flow across an await, and how do they differ?

SynchronizationContext (or a non-default TaskScheduler) determines where the continuation executes: the UI thread, a Blazor circuit, or nowhere special. It is captured by default and disabled per-await with ConfigureAwait(false). ExecutionContext determines what ambient state the continuation observes — every AsyncLocal<T>, hence logging scopes, Activity.Current, culture. It flows always, through awaits, Task.Run, timers and token registrations, and is suppressed only with ExecutionContext.SuppressFlow. The interview-grade point is that ConfigureAwait(false) has zero effect on ExecutionContext: your trace IDs still flow, your continuation just may run on a different thread.

Q2. Explain the classic async deadlock and rank the fixes.

A thread that owns a single-threaded context — the UI thread, or a classic ASP.NET request — blocks on .Result; the awaited method's continuation was captured to that context and is posted to a thread that is busy blocking, so neither side can proceed. Fix one, always preferred: go async all the way and await, using async void only for the event handler itself. Fix two, for libraries: ConfigureAwait(false) on every internal await so the library never needs the caller's context — which removes the deadlock only if the whole chain complies. Fix three, at a genuine sync boundary you cannot remove: Task.Run(...).GetAwaiter().GetResult(), which trades the deadlock for a parked pool thread and a frozen UI. Note that ASP.NET Core cannot deadlock this way because it has no context, but the same code still causes starvation.

Q3. Does ASP.NET Core code need ConfigureAwait(false)?

No. There is no SynchronizationContext, so there is nothing to capture and the continuation goes to the pool either way. The call is harmless and saves a tiny check, and libraries used from ASP.NET Core should still have it because they may be consumed from WPF, MAUI or Blazor Server. In application code I let teams choose a convention and enforce it with an analyzer setting rather than argue; what I do insist on is that nobody believes ConfigureAwait(false) "moves work to another thread" or protects against blocking, because those beliefs lead to real bugs.

Q4. What does ConfigureAwaitOptions add, and when would you use SuppressThrowing or ForceYielding?

.NET 8 replaced the boolean with a flags enum: None, ContinueOnCapturedContext, SuppressThrowing and ForceYielding. SuppressThrowing completes the await silently for faulted or cancelled tasks and marks the exception observed, which is exactly what you want after Task.WhenAll when you intend to inspect each task, or in shutdown and cleanup paths that must not throw; it is only valid on the non-generic Task, and using it on Task<T> throws an ArgumentOutOfRangeException at the ConfigureAwait call. ForceYielding forces a suspension even on a completed task; combined with None it is the clean way to guarantee "the rest of this method runs on the pool, not on the caller's thread", replacing the unconfigurable Task.Yield(). I use both sparingly and comment why, because they change control flow in ways that surprise readers.

Q5. Why doesn't an AsyncLocal value set inside an awaited method show up in the caller?

Because ExecutionContext is copy-on-write: at the point the callee's continuation is scheduled, it gets its own snapshot, and writes to an AsyncLocal replace that snapshot, not the caller's. When control returns to the caller, its own context is restored, so the value it sees is the one it had before the call. The mental model is "values flow down into forked work, never back up". Practically, request-scoped values like tenant or correlation IDs must be set in the outermost frame — middleware — before any forking, and code that needs a mutable shared bag across the flow should store a reference type once and mutate its fields.

Q6. What is special about Blazor Server's context?

Blazor Server installs a RendererSynchronizationContext per circuit that serializes all component work — event handlers, lifecycle methods, rendering — so a circuit behaves like one logical thread even though continuations run on varying pool threads. Awaits in component code capture it, so after an await you can safely touch component state and call StateHasChanged. Code arriving from outside the circuit — a timer, a background service, a SignalR hub, a ConfigureAwait(false) continuation — must marshal in with InvokeAsync, or you get races and "the current thread is not associated with the Dispatcher" errors. It is the one server-side model where the desktop-style context rules still apply, which surprises people coming from ASP.NET Core APIs.

Q7. What rules do you set for a shared library's async code, and how do you enforce them?

ConfigureAwait(false) on every await, enforced by CA2007 (or VSTHRD111 if the team uses Microsoft.VisualStudio.Threading.Analyzers) as an error in the library projects and disabled in app projects. No sync-over-async: CA1849 and VSTHRD002 catch .Result/.Wait(). Cancellation tokens forwarded everywhere: CA2016. No async void outside event handlers: VSTHRD100. ValueTask consumed correctly: CA2012. And CA2025, off by default in .NET 10, for disposables passed into unawaited tasks. The enforcement lives in a shared .editorconfig package so new repos inherit it, and I keep the rule set boring on purpose: the point is that reviewers never have to argue about these again.

Q8. How does Task.Yield interact with contexts, and what replaces it?

Task.Yield() returns a YieldAwaitable whose IsCompleted is always false, so the method suspends and the continuation is posted to the current SynchronizationContext if one exists, else to the current non-default scheduler, else to the pool. It cannot be configured, so in a UI app it always comes back to the UI thread — useful to let the message loop run, useless to get off it. In .NET 8+ Task.CompletedTask.ConfigureAwait(ConfigureAwaitOptions.ForceYielding) gives the same forced suspension with control over the context, which is the idiom I recommend when the goal is "get off the caller's thread".

Q9. You are migrating a classic ASP.NET app full of .Result to ASP.NET Core. What changes?

The deadlocks disappear overnight because there is no AspNetSynchronizationContext, which tempts teams to declare victory — but every .Result is now a starvation risk under load instead of a hang in development. My plan is to inventory blocking calls with an analyzer before the cutover, convert the request path top-down (controllers first, then services) so partial conversions do not create new sync-over-async boundaries in the middle, and keep HttpContext access out of code that runs after the request completes. I also remove HttpContext.Current-style statics in favour of IHttpContextAccessor, which is AsyncLocal-based and therefore flows correctly across awaits.

Q10. What does ConfigureAwait(false) actually save, and why doesn't it "run on another thread"?

It saves the capture and the Post back to the context: the continuation runs inline on whatever thread completed the task, avoiding a queue hop and, in UI apps, a trip through the message loop. It does not move anything anywhere — if the task was already complete the method continues synchronously on the same thread, and if it was not, the continuation runs where completion happened, which is a pool thread only because that is where I/O completions land. So the accurate phrasing is "don't care where I resume", not "resume elsewhere". In ASP.NET Core it is a micro-optimization; in libraries it is a correctness guarantee for callers you cannot see.

Exceptions, async void and fire-and-forget

Official: Exception handling (TPL) Async/Await best practices (Stephen Cleary) CA2025 Worker services / BackgroundService

In an async Task method an exception is data: MoveNext catches it and faults the task, whether it was thrown before or after the first await. It becomes a thrown exception again only when someone observes the task — await unwraps the first exception and rethrows it with the original stack via ExceptionDispatchInfo; .Result/.Wait() wrap it in an AggregateException; task.Exception exposes the aggregate directly. If nobody ever observes it, the exception is unobserved: TaskScheduler.UnobservedTaskException fires when the task is finalized (late and non-deterministic), and since .NET 4.5 the process no longer crashes for it. That silence is the root cause of most "the job just stopped and nobody noticed" incidents in async code.

Three ways to return a Task

Async elision — a non-async method that returns a task it got from elsewhere (return _http.GetStringAsync(url);) — saves a state machine and a stack frame, and TAP guidelines even allow it to throw argument exceptions synchronously. But it changes semantics: exceptions from the synchronous prefix escape at the call site rather than at the await, a using or try/finally around the returned task runs before the task completes (disposing the stream the task is still reading — that is what CA2025 flags), and the frame vanishes from stack traces. The rule I teach: elide only trivial pass-through methods with no using, try, loop or lock around the call; when in doubt, return await.

async void exists for one reason: event handler signatures are void. Its builder captures the SynchronizationContext at the start and, on an exception, posts a throw onto that context — in WPF/WinForms that surfaces as DispatcherUnhandledException/ThreadException; with no context it is raised on a thread-pool thread and crashes the process. Callers cannot await it, so tests finish early, disposal races the running method, and classic ASP.NET detected the pattern via SynchronizationContext.OperationStarted and threw "an asynchronous module or handler completed while an asynchronous operation was still pending". The hidden form is worse than the explicit one: an async lambda passed where an Action is expected becomes async void — list.ForEach(async x => ...), Parallel.ForEach(items, async i => ...), timer callbacks. Overload resolution prefers Func<Task> when one exists, which is why Task.Run(async () => ...) is safe.

await Parallel.ForEachAsync(orderIds, ct, (id, token) => new ValueTask(svc.ProcessAsync(id, token))); // bounded parallel fix

// 2) Elision + using: the stream is disposed before the read finishes.
public Task<int> ReadHeaderAsync(string path)
{

    return fs.ReadAsync(_buffer, 0, 16);          // BUG: returns immediately, 'using' disposes fs → ObjectDisposedException later
}

{

Fire-and-forget without losing the failure

The discard _ = DoAsync(); silences CS4014 but not the problem: the exception is still unobserved and the work still races app shutdown. In ASP.NET Core, fire-and-forget from a request is almost always wrong for a second reason — request-scoped services such as the DbContext are disposed when the response ends, so the background continuation finds a disposed context. The correct shape is a BackgroundService consuming a bounded Channel (Unit 9): the request enqueues, the service processes with its own scope, its own cancellation on shutdown, and its own error handling. When a true fire-and-forget is unavoidable (telemetry, cache refresh), route it through one helper that logs faults, and consider ExecutionContext.SuppressFlow() so it does not drag request-scoped AsyncLocal state along. Also know the .NET 6 change: an unhandled exception in BackgroundService.ExecuteAsync now logs and stops the host (HostOptions.BackgroundServiceExceptionBehavior = StopHost by default) instead of being swallowed silently as in .NET 5 — a deliberate "fail loudly" decision that catches teams whose workers used to die quietly.

Interview Q&A

Q1. Where does an exception thrown inside an async Task method go, and inside an async void method?

In an async Task method the compiler-generated MoveNext catches it and faults the task, so it surfaces when the task is awaited, unwrapped and with the original stack, or wrapped in an AggregateException if someone blocks with .Result. In async void there is no task, so the builder posts the exception onto the captured SynchronizationContext — in a UI app that becomes the app-level unhandled-exception event, elsewhere it is thrown on a pool thread and terminates the process. That asymmetry is the whole argument against async void: it converts a recoverable failure into a crash and removes the caller's ability to know when the work finished.

Q2. When is async void acceptable, and how do hidden ones appear?

Only for event handlers, whose delegate type forces void, and then the handler owns a try/catch of its own because nothing above it can catch. The dangerous cases are implicit: an async lambda converted to Action or Action<T> — List.ForEach, Parallel.ForEach, Dispatcher.Invoke, System.Threading.Timer callbacks — silently becomes async void, so exceptions escape and the loop finishes before the work does. C# prefers a Func<Task> overload when one exists, which is why Task.Run and most modern APIs are safe. I enable VSTHRD100 and teach people to look for "await inside a lambda passed to something that returns void" in reviews.

Q3. return await task versus return task — what are the trade-offs?

Returning the task directly avoids the state machine, one potential allocation and a stack frame, so it is attractive on hot, trivial pass-through methods. The costs are semantic: any using, try/finally, lock or loop around the call now completes before the operation does, exceptions from the synchronous prefix throw at the call site, and the method disappears from stack traces. Stephen Toub's guidance, which I follow, is to elide only when the method is a pure forwarder; the moment there is a scope, use async and return await. CA2025 catches the disposable case, and Runtime Async in .NET 11 shrinks the cost difference, which removes most of the performance argument.

Q4. What is an unobserved task exception, and how would you detect them in production?

A faulted task whose exception nobody read before the task was garbage collected. Since .NET 4.5 that no longer crashes the process; instead TaskScheduler.UnobservedTaskException fires from the finalizer thread, non-deterministically and possibly minutes later. I hook that event at startup to log with a distinct marker and a metric, because a non-zero rate means some code path is dropping tasks — usually a discarded fire-and-forget, a WhenAny loser, or an elided task inside a using. The fix is never "handle the event better"; it is finding the drop and routing it through an explicit fault-observing helper.

Q5. How do you run background work triggered by a web request?

Not with Task.Run or a discarded task: the request scope and its services are disposed when the response ends, shutdown does not wait for the work, exceptions are unobserved, and there is no back-pressure. The pattern is a bounded Channel<T> registered as a singleton, a request that TryWrites or WriteAsyncs a message, and a BackgroundService that reads from it, creates its own IServiceScope per item, honours the stopping token and handles failures per item. For anything that must survive a restart you go one step further to a durable queue. Since .NET 6 an unhandled exception in the service stops the host, which is the right default — a dead worker should be visible.

Q6. How should OperationCanceledException be handled in a request pipeline?

As a non-error outcome. When the client disconnects, HttpContext.RequestAborted fires, EF Core and HttpClient throw OperationCanceledException, and logging that at error level produces alert noise and misleading dashboards. I filter with catch (OperationCanceledException) when (ct.IsCancellationRequested) at the boundary, count it as a 499-style metric, and let true failures fall through. The subtlety is telling cancellations apart — a timeout token versus the client's token versus shutdown — which you do by comparing ex.CancellationToken or by structuring linked sources so each layer knows which token fired.

Q7. What did .NET 6 change about exceptions in BackgroundService?

Before .NET 6 an exception escaping ExecuteAsync was swallowed: the service silently stopped and the host kept running, which produced workers that "just stopped processing" for days. .NET 6 introduced HostOptions.BackgroundServiceExceptionBehavior with a default of StopHost: the exception is logged as critical and the host shuts down, so orchestration restarts the process. You can set Ignore for the old behaviour, but the better response is to catch per work item inside the loop so one poison message does not take the service down, while letting genuinely fatal startup errors propagate.

Q8. Why are exception filters especially useful in async code?

A when clause runs before the stack unwinds, so you can log, count or classify an exception without catching and rethrowing, which keeps the original stack and avoids the throw; versus throw ex; mistake. In async code the stack is already assembled from pieces, so every rethrow point matters for diagnosability. Filters also express intent precisely: when (ct.IsCancellationRequested) separates expected cancellation from failure, and when (ex is not OperationCanceledException) makes a catch-all safe. A side benefit is that a filter that returns false leaves the exception first-chance for debuggers and dump tools.

Q9. Where does AggregateException still appear, and how do you deal with nested ones?

It is the task's native fault container: task.Exception, .Result, .Wait(), Task.WaitAll, and the exception an UnobservedTaskException handler receives. await hides it by rethrowing the first inner exception, which is convenient but loses the others after a WhenAll, so for batch operations I read whenAll.Exception.InnerExceptions. Nested WhenAlls produce aggregates inside aggregates; Flatten() collapses them and GetBaseException() gives the root cause of a single chain. In code review I flag any catch (AggregateException) in async code as a sign of blocking somewhere.

Q10. What do you flag in code review for async exception handling?

Discarded tasks (_ = X()) without a fault-observing helper; hidden async void lambdas; a using or try around a returned, unawaited task; catch blocks that log OperationCanceledException as errors; throw ex;; catch (AggregateException) indicating hidden blocking; and background work started from a request scope. Positively, I look for exception filters that classify cancellation, per-item error handling inside worker loops, and SuppressThrowing or explicit inspection after WhenAll when partial failure is acceptable. Most of these are mechanical enough to become analyzer rules — VSTHRD100, VSTHRD110, CA2025, CS4014 as error — so review time goes to the design questions.

Cancellation: cooperative by design

Official: Cancellation in managed threads CancellationTokenSource.CancelAsync CA2016 ASP.NET Core request timeouts

.NET has no way to abort running code, and that is a feature: Thread.Abort was removed from .NET Core precisely because interrupting arbitrary code leaves locks, files and invariants in unknown states. Cancellation is therefore cooperative: a CancellationTokenSource owns the state, a CancellationToken is a cheap struct handle to it, and the code doing the work decides how to honour a request — by polling IsCancellationRequested in a CPU loop, by passing the token down to I/O APIs that will close the socket or abort the overlapped operation, or by registering a callback that tears something down. The consumer's promise is only "I will stop as soon as I reasonably can, and I will leave things consistent".

Sources, tokens and callbacks

Cancel() flips the state and then runs every registered callback synchronously on the calling thread, in reverse registration order; if any callback throws, the rest still run and Cancel() throws an AggregateException afterwards. That is why callbacks must be tiny, non-blocking and non-throwing, and why calling Cancel() while holding a lock that a callback might need is a deadlock. CancelAsync() .NET 8 runs the callbacks on the thread pool and returns a Task you can await to know they finished — the right choice when the cancelling thread must not pay for them. CancelAfter(timeout) and the CancellationTokenSource(TimeSpan) constructor add a timer; the callbacks then run on the timer thread. CreateLinkedTokenSource(a, b) makes a source that cancels when any parent does by registering on each parent — which means a linked source you never dispose leaks a registration on the parent for the parent's lifetime. Against a long-lived parent such as ApplicationStopping that is a textbook memory leak, so linked sources live in a using. TryReset() .NET 6 lets frameworks like Kestrel pool sources per connection.

Two exception types matter: OperationCanceledException is the base, thrown by ThrowIfCancellationRequested() and by most APIs; TaskCanceledException derives from it and is what you get from awaiting a task that ended in the Canceled state. Catch the base type. To know whose cancellation fired — the caller's, a timeout, shutdown — compare ex.CancellationToken against the tokens you hold, or structure linked sources so each layer catches only its own.

// Timeout + caller cancellation, correctly composed and disposed.
public async Task<Quote> GetQuoteAsync(string symbol, CancellationToken ct)
{
    using var timeout = CancellationTokenSource.CreateLinkedTokenSource(ct);   // dispose = unregister from 'ct'
    timeout.CancelAfter(TimeSpan.FromSeconds(3));
    try
    {
        return await _http.GetFromJsonAsync<Quote>($"/quote/{symbol}", timeout.Token) ?? throw new InvalidDataException(symbol);
    }
    catch (OperationCanceledException) when (!ct.IsCancellationRequested)   // the caller did NOT cancel → it was our timeout
    {
        throw new TimeoutException($"quote for {symbol} timed out after 3s");
    }
}

{

    {

    }

}

static Task<T> WithCancellation<T>(Task<T> task, CancellationToken ct)
{
    if (task.IsCompleted || !ct.CanBeCanceled) return task;
    var tcs = new TaskCompletionSource<T>(TaskCreationOptions.RunContinuationsAsynchronously);
    var reg = ct.UnsafeRegister(static (s, token) => ((TaskCompletionSource<T>)s!).TrySetCanceled(token), tcs);
    task.ContinueWith(static (t, s) =>
    {
        var (source, registration) = ((TaskCompletionSource<T>, CancellationTokenRegistration))s!;
        registration.Dispose();
        if (t.IsCanceled) source.TrySetCanceled();
        else if (t.IsFaulted) source.TrySetException(t.Exception!.InnerExceptions);
        else source.TrySetResult(t.Result);
    }, (tcs, reg), CancellationToken.None, TaskContinuationOptions.ExecuteSynchronously, TaskScheduler.Default);
    return tcs.Task;
}

ASP.NET Core exposes the client's disconnect as HttpContext.RequestAborted, and both MVC and minimal APIs bind a CancellationToken parameter to it automatically; the .NET 8 request-timeouts middleware (AddRequestTimeouts, [RequestTimeout]) triggers the same token when a policy elapses, so one parameter covers both. Forward it into EF Core, HttpClient, gRPC and your own services — CA2016 warns when you drop it. On the hosting side, IHostApplicationLifetime.ApplicationStopping and the stoppingToken handed to BackgroundService.ExecuteAsync signal shutdown; the host then waits HostOptions.ShutdownTimeout — 30 seconds by default since .NET 8, up from 5, to line up with Kubernetes' terminationGracePeriodSeconds — for services to drain before it gives up. Design rules that follow: cancellation is not rollback (use try/finally to leave state consistent), never return a partial result silently after noticing cancellation, and never store a token in a constructor — pass it per operation, as the last parameter.

Interview Q&A

Q1. Why is .NET cancellation cooperative, and what does Cancel() actually do?

Because forcibly interrupting code cannot know which locks, buffers or invariants are mid-update; Thread.Abort proved that and was removed from .NET Core. So Cancel() only sets a flag and runs registered callbacks — synchronously, on the calling thread, in reverse registration order, collecting any exceptions into an AggregateException at the end. Everything else is the callee's job: polling in CPU loops, forwarding to I/O APIs that close the underlying handle, or registering a callback that aborts a native operation. The consequence for design is that a cancellation request is a request; the caller must still await the operation to learn how it actually ended.

Q2. Why did .NET 8 add CancelAsync, and when do you choose it over Cancel?

Cancel executes every callback inline on the cancelling thread, so a UI thread, a socket loop or a request thread pays for whatever those callbacks do — including callbacks registered by libraries you do not control that might block or take a lock. CancelAsync queues the callback execution to the thread pool and returns a task that completes when they are all done, which both protects the caller and gives you something to await if you need "cancellation has taken effect" semantics before proceeding, for example before disposing resources the callbacks touch. I reach for it in shutdown paths and anywhere the cancelling thread is precious, and keep Cancel for simple sources with callbacks I own.

Q3. How do linked token sources work, and why must you dispose them?

CreateLinkedTokenSource creates a new source and registers a callback on each parent that cancels the child, so cancelling any parent cancels the child. Those registrations live in the parents' registration lists until the child is disposed; if the parent is long-lived — ApplicationStopping, a connection-level token — each undisposed child is a permanent leak of a few hundred bytes plus whatever the child references. The rule is using var linked = CreateLinkedTokenSource(...) scoped to the operation. In one incident this pattern produced a slow multi-day memory climb in a service that linked per request to the host lifetime; the fix was one using.

Q4. OperationCanceledException versus TaskCanceledException, and how do you tell timeout from client cancel from shutdown?

TaskCanceledException derives from OperationCanceledException; you get the derived one from awaiting a task that ended in the Canceled state and the base one from ThrowIfCancellationRequested and many APIs, so catch the base. To distinguish causes, compare ex.CancellationToken against the tokens you hold, or use an exception filter like when (!callerToken.IsCancellationRequested) to conclude it was your own timeout and translate it into a TimeoutException. Structuring linked sources per layer — request token, then a per-call timeout source linked to it — keeps that reasoning local. The payoff is correct HTTP status codes and clean dashboards: 499 for client disconnect, 504 for upstream timeout, nothing logged as error for shutdown.

Q5. What does passing a token to Task.Run or StartNew do?

Two things only: if the token is already cancelled when the task would start, the delegate never runs and the task is Canceled; and if the delegate throws an OperationCanceledException carrying that same token, the task transitions to Canceled rather than Faulted. It does not interrupt a running delegate. So the body must observe the token itself — ThrowIfCancellationRequested at amortized intervals in CPU loops, forwarding to any async call inside. I still pass it, because the Canceled state versus Faulted matters for callers filtering cancellation, but I never let a reviewer believe it provides abort semantics.

Q6. How does cancellation reach a request handler in ASP.NET Core, and what changed in .NET 8?

Kestrel signals HttpContext.RequestAborted when the client connection drops, and both MVC and minimal APIs bind a CancellationToken parameter to it. .NET 8 added the request-timeouts middleware, where a global or per-endpoint policy cancels the same token after a deadline and lets you return a 504 or custom response. The handler forwards that token into EF Core queries, outbound HttpClient calls and downstream services, so a disconnected client stops consuming database and upstream capacity — which is a real cost saver under retry storms. Two cautions: for HTTP/1.1 the disconnect is only detected when the transport notices, and work that must complete regardless — a payment confirmation — should deliberately use CancellationToken.None with a comment explaining why.

Q7. Design graceful shutdown for a message-processing BackgroundService.

ExecuteAsync gets a stopping token that fires on SIGTERM or StopApplication; the host then waits up to HostOptions.ShutdownTimeout, 30 seconds since .NET 8. My loop stops pulling new messages when the token fires, lets the in-flight item finish or checkpoint, and catches the expected OperationCanceledException at the top so shutdown is logged as information, not error. Per-message failures are caught inside the loop and retried or dead-lettered so a poison message does not stop the host, which since .NET 6 is what an escaping exception does. I size the timeout against the orchestrator's grace period and the longest single message, and I test it by sending SIGTERM under load and asserting nothing is lost or double-processed.

Q8. What rules apply to Register callbacks, and how can Cancel deadlock?

Callbacks run synchronously on whichever thread cancels — the caller of Cancel, or a timer thread for CancelAfter — so they must be quick, must not block, must not throw, and should not acquire locks. The deadlock: thread A holds a lock and calls Cancel; a callback registered by thread B's operation needs that lock; A waits forever inside Cancel. Related: disposing a registration waits for a currently running callback to finish unless called from inside it, so disposing under a lock is also risky. UnsafeRegister skips the ExecutionContext capture for allocation-sensitive paths, and CancelAsync in .NET 8 sidesteps the inline execution entirely.

Q9. What are your API-design rules for cancellation tokens?

Every async method that does I/O or meaningful work takes a CancellationToken as its last parameter; public leaf APIs may default it to default, internal ones should not, so callers are forced to think. Tokens are per operation, never stored in constructors or fields, because an object outlives many operations. Forward, never swallow — CA2016 enforces the forwarding. Compose timeouts with a linked source inside a using. Async iterators use [EnumeratorCancellation] so WithCancellation works. And document what cancellation means for each operation: abandonment of a read is safe, cancelling a two-phase commit halfway is not, so those methods either ignore the token past the point of no return or explicitly say so.

Q10. How do you make a non-cancellable operation cancellable, and what is the honest limitation?

You cannot make it abortable; you can make it abandonable. task.WaitAsync(ct) in .NET 6 does it in one call, and the classic implementation is a TaskCompletionSource that the token's registration cancels while the original task's continuation completes it normally — being careful to dispose the registration and use RunContinuationsAsynchronously. The limitation is that the original operation still runs to completion, still holds its connection or buffer, and its eventual result or exception must be observed so it is not unobserved. For anything that owns a native resource the right fix is upstream: find or add an overload that takes a token so the socket or handle is actually closed.

ValueTask and allocation-aware async

Official: ValueTask<TResult> Understanding the Whys, Whats, and Whens of ValueTask (Toub) CA2012 ManualResetValueTaskSourceCore<T>

Task<T> is a class, so an async method that returns one allocates it on every call unless the result is cached — and on hot paths that usually complete synchronously that allocation is pure waste. A buffered Stream.ReadAsync returns from the buffer 99 times out of 100; a ChannelReader.ReadAsync usually finds an item; a socket receive often has bytes waiting. ValueTask<T> (in-box since .NET Core 2.0, non-generic ValueTask since 2.1) is a struct that holds either a completed result, or a Task<T>, or — the important third case added in .NET Core 2.1 — an IValueTaskSource<T>: a reusable, poolable object that the library controls. With the first case the synchronous path allocates nothing; with the third case even the asynchronous path can be allocation-free, because the backing object is recycled. That is why the interfaces designed for implementers use it: IAsyncDisposable.DisposeAsync, IAsyncEnumerator<T>.MoveNextAsync, PipeReader.ReadAsync, the Memory<byte> overloads of Stream.ReadAsync/WriteAsync.

The consumption contract

The flexibility is paid for by the consumer. Because the backing object may be recycled the moment the result is read, a ValueTask must be consumed exactly once: await it once, or call AsTask() once, or check IsCompletedSuccessfully and read .Result once. Never await it twice, never await it concurrently, never block on .Result or GetAwaiter().GetResult() before it is complete, never hand the same instance to two consumers. Violating this with a pooled source means reading another operation's result — silently — or an InvalidOperationException from the version token check if you are lucky. If you genuinely need multi-await semantics call Preserve() (returns a copy backed by a real task when needed) and if you need WhenAll, convert with AsTask(). CA2012 flags the common misuses at compile time. Stephen Toub's guidance is still the policy I use: default to Task; return ValueTask from an API only when profiling shows it is hot and either synchronous completion is common or you can back it with a pooled source.

This is how Socket's awaitable event args, Channels, System.IO.Pipelines and the compiler's async iterators (Unit 8) achieve near-zero allocations per operation. For ordinary async ValueTask methods there is a middle ground: .NET 6 [AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))], applied per method since C# 10, pools the state-machine box itself. It is worth measuring, not assuming: pooling adds synchronization and the .NET 5 global switch for it was removed because the win was workload-dependent.

Interview Q&A

Q1. What is ValueTask, and what problem does it solve?

It is a struct that can represent an async result in three ways: an already-available value, a wrapped Task, or an IValueTaskSource that a library owns and can recycle. It exists because Task is a heap object and hot APIs that usually complete synchronously — buffered reads, channel reads, socket receives — were allocating on every call for nothing. With the value case the synchronous path is allocation-free; with the source case even the asynchronous path can be, which is how Pipelines and Sockets reach near-zero per-operation garbage. The trade is a stricter consumption contract for callers, which is why it is a targeted optimization and not a replacement for Task.

Q2. What are the rules for consuming a ValueTask, and why are they so strict?

Consume it once: a single await, or a single AsTask(), or one IsCompletedSuccessfully check followed by one read of Result. Do not await it twice, concurrently, store it for later, or block on it before completion. The reason is the pooled case: once the consumer reads the result the backing object may be reset and handed to the next operation, so a second read might observe someone else's data or hit a version-token exception. Preserve() gives you a copy that is safe to await repeatedly, and AsTask() bridges to WhenAll. I make CA2012 an error in every project because these bugs are silent and intermittent.

Q3. When do you return ValueTask from an API you design?

When the method is on a measured hot path and either completes synchronously most of the time or is backed by a pooled source — and, for public APIs, when the consumers are sophisticated enough to follow the contract. Interfaces meant for implementers, like a stream, an enumerator or a disposable, are good candidates because implementations vary and some will be allocation-free. Anything that gets stored, composed with WhenAll, or exposed to application developers returns Task. The bar is evidence: a benchmark showing the allocation matters, because ValueTask also costs diagnosability and reviewer attention.

Q4. What does an async ValueTask method allocate, and what does the pooling builder change?

If it completes synchronously, nothing. If it suspends, the same state-machine box an async Task method would allocate — the box implements IValueTaskSource and becomes the backing object. .NET 6 added PoolingAsyncValueTaskMethodBuilder, applied per method with the C# 10 method-level [AsyncMethodBuilder] attribute, which rents and returns those boxes through a per-thread and global cache instead of allocating. It removes allocations but adds pooling overhead and makes lifetime bugs possible, and the runtime team turned the .NET 5 experiment's global switch into an opt-in attribute precisely because the benefit is workload-specific. Runtime Async in .NET 11 attacks the same cost from the other side by reusing continuation objects in the runtime.

Q5. What is IValueTaskSource and ManualResetValueTaskSourceCore, and who uses them?

IValueTaskSource<T> is the three-method interface — status, completion registration, result — that lets any object back a ValueTask, with a version token so stale consumers are detected. ManualResetValueTaskSourceCore<T> is the struct that implements the tricky parts: storing the continuation, capturing and restoring contexts, optional asynchronous continuation execution, and the version counter behind Reset(). You embed it, forward the interface, and reuse the object per operation. It powers Socket's awaitable event args, Channels, Pipelines, and the compiler's own async iterators, which reuse the iterator object as the source for every MoveNextAsync. In application code I have used it for reusable signals and for request-response correlation in custom protocol clients.

Q6. Why do IAsyncDisposable and IAsyncEnumerator return ValueTask?

Because they are implemented by thousands of types and called in tight loops, and most implementations complete synchronously: disposing something that has nothing to flush, or moving to the next element already in a buffer. Returning Task would force an allocation on every element and every disposal for the majority case. The interface contract pushes the consumption rules onto await foreach and await using, which the compiler generates correctly, so ordinary application code never sees the sharp edges. It is a good example of the guidance: use ValueTask where the implementer side benefits and the consumer side is mostly compiler-generated.

Q7. What does CA2012 catch?

It flags ValueTask instances that are consumed incorrectly: awaited or accessed more than once, stored in a field or local and used later, passed to multiple consumers, or having Result read without a completion check. It also flags calling GetAwaiter().GetResult() on one. It cannot see through every indirection, so it is a safety net, not a proof; the complement is the team rule that ValueTask-returning members are awaited immediately or converted with AsTask() at the point of receipt. I keep it at error severity because every violation is a latent data-corruption bug with pooled sources.

Q8. Preserve() versus AsTask() — when do you use which?

AsTask() converts to a real Task<T> exactly once — allocation-free if the ValueTask already wraps a task, one allocation otherwise — and you use it when you need Task semantics: WhenAll, storing the operation, returning it from a Task-typed API. Preserve() returns a ValueTask that is safe to await multiple times, which is useful when you must hand the same in-flight operation to several awaiters but want to keep the ValueTask type at the boundary. Both must be called before any other consumption of the original. In practice I see AsTask() far more often; Preserve() is for framework-style code that caches an operation.

Q9. Describe a real failure caused by misusing ValueTask.

The pattern I have seen: a helper stored the ValueTask from a pipe or socket read in a field to "retry if it times out", then awaited it again after the timeout fired. With a pooled source the second await read the next request's bytes, so under load users occasionally received fragments of each other's responses — intermittent, load-dependent, invisible in unit tests where nothing was pooled. The fix was AsTask() at the boundary and CA2012 as an error. The lesson I give teams is that ValueTask failures look like data corruption and race conditions, not like exceptions, so the contract must be enforced by tooling rather than by review vigilance.

Q10. As a lead, what Task/ValueTask policy do you set?

Application and service code returns Task by default; ValueTask is allowed in a short allow-list of hot interfaces and requires a benchmark in the PR showing the allocation reduction matters at our request rates. CA2012 is an error everywhere, and public library packages document the consumption rules on every ValueTask member. Consumers convert at the boundary with AsTask() when they need composition. I also make sure the team knows the .NET 11 direction: Runtime Async and continuation reuse are reducing the per-suspension cost inside the runtime, so most of the historical motivation for sprinkling ValueTask is fading, and the remaining cases are the sync-fast-path ones.

IAsyncEnumerable<T> and async streams

Official: Generate and consume async streams System.Linq.AsyncEnumerable (.NET 10) Breaking change: AsyncEnumerable in .NET 10 EnumeratorCancellationAttribute

C# 8 and .NET Core 3.0 (2019) added IAsyncEnumerable<T>: a pull-based sequence in which each pull may be asynchronous. GetAsyncEnumerator(CancellationToken) returns an IAsyncEnumerator<T> with ValueTask<bool> MoveNextAsync(), T Current and ValueTask DisposeAsync(); await foreach consumes it, async iterator methods with yield return produce it, and await using/IAsyncDisposable completes the picture. The mental model: it has the laziness and natural back-pressure of IEnumerable<T> — the consumer sets the pace and nothing is produced until asked — combined with the non-blocking waits of Task. Contrast with Task<IEnumerable<T>> (all or nothing, fully buffered), IObservable<T> (push; the producer sets the pace) and ChannelReader<T> (a buffer that decouples the two; Unit 9). Unlike a Task, a stream is cold: every enumeration re-executes the iterator from the top.

What the compiler generates

An async iterator becomes a state machine that is simultaneously an IAsyncEnumerable<T>, an IAsyncEnumerator<T>, an IAsyncStateMachine and an IValueTaskSource<bool>: each MoveNextAsync() returns a ValueTask<bool> backed by the iterator object itself through an embedded ManualResetValueTaskSourceCore, so iterating allocates essentially nothing per element, and the enumerable reuses itself as the enumerator for the first enumeration on the same thread (the same trick synchronous iterators use). Because it is both an iterator and a coroutine it has two kinds of suspension points — yield return hands a value to the consumer, await waits for a producer. Restrictions follow from that: no yield return inside a try that has a catch (only try/finally), no yield in catch or finally, no ref locals or spans across either kind of suspension, and an async method returning IAsyncEnumerable<T> must contain a yield. Note for Unit 10: Runtime Async's spec covers only Task/ValueTask-returning methods, so async iterators keep their compiler-generated machine in .NET 11.

Cancellation and configuration

The consumer passes a token with source.WithCancellation(ct), which flows into GetAsyncEnumerator(ct). The iterator only receives it if one of its parameters is marked [EnumeratorCancellation]; otherwise the token is silently ignored, and the compiler warns (CS8425) when an iterator has a CancellationToken parameter without the attribute. If the iterator was invoked with a token and the consumer supplies another, the generated code links them. .ConfigureAwait(false) on the enumerable configures the consumer's awaits of MoveNextAsync/DisposeAsync; awaits inside the iterator are configured individually as usual. Breaking out of await foreach calls DisposeAsync, which runs the iterator's pending finally blocks — so await using resources inside an iterator are cleaned up even on early exit. Exceptions thrown by the producer surface at the consumer's next MoveNextAsync await.

Interview Q&A

Q1. What is IAsyncEnumerable<T>, and how does it differ from Task<IEnumerable<T>> and IObservable<T>?

It is a lazily evaluated, pull-based sequence where each MoveNextAsync may complete asynchronously, consumed with await foreach and produced with async iterators. Task<IEnumerable<T>> is a single asynchronous result: nothing is available until everything is, and memory is proportional to the result size. IObservable<T> is push-based: the producer decides when items arrive and the consumer needs Rx operators to buffer or throttle. The async stream sits in between with consumer-driven pacing and O(1) memory, which makes it the natural type for paged APIs, database readers and streaming HTTP responses. It is also cold — each enumeration re-runs the producer — which is the source of several lifetime bugs.

Q2. How does cancellation flow through an async stream?

The consumer attaches a token with WithCancellation(ct), which the compiler passes to GetAsyncEnumerator(ct). Inside an async iterator that token is delivered only to a parameter marked [EnumeratorCancellation]; if the iterator was also called with its own token, the generated code links both into one. Without the attribute the consumer's token is silently dropped — the compiler warns when an iterator has a token parameter without it — and the producer keeps fetching pages after the client is gone. Inside the iterator you then forward that token into every await, the same as anywhere else. In review I check that every public async iterator has exactly one [EnumeratorCancellation] parameter.

Q3. What does the compiler generate for an async iterator, and what does it cost per element?

One object that plays four roles: the enumerable, the enumerator, the async state machine, and an IValueTaskSource<bool> that backs each MoveNextAsync through an embedded ManualResetValueTaskSourceCore. Because the iterator itself is the value-task source, a MoveNextAsync that completes synchronously allocates nothing and even an asynchronous one only reuses the same object, so the steady-state cost per element is close to zero. The enumerable reuses itself as the first enumerator, mirroring synchronous iterators. Two consequences worth knowing: the object is both a coroutine and a generator, which is why yield inside try/catch is forbidden, and Runtime Async in .NET 11 does not replace this machinery, since its spec only covers Task and ValueTask returning methods.

Q4. What changed for LINQ over async streams in .NET 10, and how do you migrate?

.NET 10 ships System.Linq.AsyncEnumerable in the box: a from-scratch implementation of the standard operators for IAsyncEnumerable<T>, with ToListAsync, ToArrayAsync, CountAsync and friends, and async-selector overloads that keep the sync names and accept (T, CancellationToken) callbacks. The community System.Linq.Async package predated the design guidelines and used SelectAwait-style suffixes, so having both referenced produces ambiguity errors. Migration is: drop the old package or move to Ix.NET 7.0, which defers to the platform; reference the System.Linq.AsyncEnumerable NuGet for older target frameworks; use ExcludeAssets=compile if a transitive dependency still pulls the old one; and upgrade EF Core if you hit CS0121 on ToListAsync because DbSet implements both interfaces. .NET 11 keeps extending it with FullJoin and tuple-returning joins.

Q5. How does ASP.NET Core stream an IAsyncEnumerable<T> response, and what is new in .NET 11?

Since .NET 6, returning an IAsyncEnumerable<T> from a minimal API or MVC action makes System.Text.Json write the opening bracket immediately and each element as it is produced, flushing through the response body with chunked encoding, so time-to-first-byte is independent of result size and memory stays flat. MVC configured with Newtonsoft.Json buffers the whole sequence into a list first, which surprises people. On the consuming side JsonSerializer.DeserializeAsyncEnumerable reads such a stream incrementally, and .NET 10 added PipeReader/PipeWriter overloads. .NET 11 adds SerializeAsyncEnumerable overloads for top-level values — newline-delimited JSON — which is the format most log and event pipelines actually want.

Q6. How do async streams provide back-pressure, and how does that compare with channels?

An async stream is pull-based: the producer cannot run ahead of the consumer, because it only executes when MoveNextAsync is called and suspends at each yield. That is back-pressure by construction, with no buffer and no configuration. A channel decouples the two sides with a buffer, and back-pressure appears only when the channel is bounded and the writer awaits WriteAsync on a full buffer. So a stream is right when one consumer drives one producer and latency per item is acceptable; a channel is right when producers and consumers run at different rates or in different numbers, or when the producer is a callback you cannot suspend. Streams compose on top of channels through ReadAllAsync().

Q7. A method creates a DbContext in a using and returns AsAsyncEnumerable(). What happens, and what is the fix?

It throws ObjectDisposedException when the caller enumerates, because the stream is lazy: the method returned, the using disposed the context, and only then did the consumer pull the first row. The fix is to give the resource the same lifetime as the enumeration by making the method an async iterator: await using the context inside, await foreach the query and yield return each row, so disposal runs when the consumer finishes or breaks. The same lifetime rule applies to HttpResponseMessage, readers and scopes; and it is why I treat "return a stream from inside a using" as a review blocker rather than a style issue.

Q8. When do you choose a channel, an async stream, or an observable?

Async stream: one logical consumer pulling from a lazy, possibly paged source, with cancellation and early exit — API pagination, DB readers, streaming responses. Channel: producer/consumer with different cardinalities or rates, needing a bounded buffer, drop policies, or a producer that is a callback — background job queues, batching, fan-in from many sockets. Observable: event-shaped data with time-based operators — UI input, market ticks, telemetry with windowing — where Rx's operator library pays for itself. They compose: a channel's reader exposes ReadAllAsync() as a stream, and in .NET 10 LINQ operators work directly on streams, which removed most reasons to reach for Rx just to filter and project.

Q9. What happens on break inside await foreach, and how do exceptions behave?

await foreach expands to an enumerator with a try/finally that awaits DisposeAsync, so break, return or an exception in the loop body disposes the iterator, which runs the iterator's pending finally blocks and await using disposals — connections are released even on early exit. An exception thrown inside the iterator surfaces from the consumer's next MoveNextAsync await, after which the iterator is finished; you cannot resume it. Because yield inside a try with catch is forbidden, error handling in producers is done with finally for cleanup plus explicit try/catch around the awaits that can fail, yielding an error item or rethrowing deliberately.

Q10. Design an export endpoint that streams ten million rows as JSON.

Return an IAsyncEnumerable<Row> from an async iterator that opens its own DbContext with AsNoTracking and AsAsyncEnumerable(), forwards HttpContext.RequestAborted through [EnumeratorCancellation], and never materializes. Let System.Text.Json stream it, or use the .NET 11 NDJSON output so consumers can process line by line; set a request timeout policy long enough for the export and disable response buffering in any proxy. Watch the two costs of streaming: the database reader and connection stay open for the whole response, so I would page through a keyset query rather than one giant reader, and slow clients hold server resources, so I would bound concurrent exports with a semaphore. For anything larger or repeatable I would push the export to blob storage from a background job and return a link instead.

Coordination and concurrency patterns

Official: System.Threading.Channels Parallel.ForEachAsync PeriodicTimer TimeProvider System.Threading.Lock

This is the unit where lead-level interviews actually happen: not "what is a Task" but "design the ingestion pipeline", "why did the export job exhaust the connection pool", "how do we stop the batch from hammering the partner API". The recurring principle is everything bounded — concurrency, queues, time — and the recurring trap is that the obvious async idiom, Task.WhenAll(items.Select(x => DoAsync(x))), is unbounded: it starts every operation at once. With 10,000 items that means 10,000 concurrent HTTP requests (socket exhaustion, partner rate limits), 10,000 EF Core queries against a pool of 100 connections (pool timeout exceptions), and memory proportional to the batch.

Bounded fan-out

Parallel.ForEachAsync .NET 6 is the default answer: a source (IEnumerable<T> or IAsyncEnumerable<T>), a ParallelOptions with MaxDegreeOfParallelism (defaults to the processor count, which is often too low for I/O — set it explicitly) and a cancellation token, and a body of Func<T, CancellationToken, ValueTask>. On a failure it stops dispatching new items, cancels the body token so in-flight iterations can bail, waits for them, then throws. Its limitation is that it returns nothing, so when you need results in order or per-item failure tracking, the classic SemaphoreSlim + WhenAll shape is still right. For rate rather than concurrency limits — "at most 50 calls per second" — System.Threading.RateLimiting .NET 7 provides token-bucket, sliding-window and concurrency limiters with an awaitable AcquireAsync.

// Concurrency-bounded, cancellation-aware fan-out. 32 in flight, not 10,000.
await Parallel.ForEachAsync(orderIds,
    new ParallelOptions { MaxDegreeOfParallelism = 32, CancellationToken = ct },
    async (id, token) => { await svc.ReprocessAsync(id, token); });

// When you need results and per-item outcomes: semaphore + WhenAll.
using var gate = new SemaphoreSlim(32, 32);
var results = await Task.WhenAll(orderIds.Select(async id =>
{
    await gate.WaitAsync(ct);                       // WaitAsync, never Wait, inside async code
    try   { return (id, Result: await svc.ReprocessAsync(id, ct), Error: (Exception?)null); }
    catch (Exception ex) when (ex is not OperationCanceledException) { return (id, Result: default, Error: ex); }
    finally { gate.Release(); }
}));

// Rate-limited outbound calls (.NET 7): 50 per second with a burst of 100.
var limiter = new TokenBucketRateLimiter(new() { TokenLimit = 100, TokensPerPeriod = 50, ReplenishmentPeriod = TimeSpan.FromSeconds(1), QueueLimit = 1000 });
using RateLimitLease lease = await limiter.AcquireAsync(1, ct);
if (lease.IsAcquired) await partner.NotifyAsync(evt, ct);

Mutual exclusion and single-flight

lock — and the .NET 9 System.Threading.Lock type it targets in C# 13 — cannot contain an await (CS1996), and it should not: Monitor, Mutex and ReaderWriterLockSlim are thread-affine, and after an await you may be on another thread, which is how you get SynchronizationLockException or a lock that is never released. The async-compatible mutex is SemaphoreSlim(1, 1) with WaitAsync in a try/finally — not reentrant, so structure code so a holder never calls back into the guarded section. For the classic cache stampede — a hundred requests miss the cache simultaneously and all hit the database — the single-flight idiom is ConcurrentDictionary<TKey, Lazy<Task<TValue>>>: GetOrAdd may create several Lazy instances but publishes exactly one, and only the winner's factory runs; evict on failure so a faulted task is not cached forever. HybridCache (Microsoft.Extensions.Caching.Hybrid, GA in 2025) bakes stampede protection in and is what I reach for in new code.

// Async mutex (not reentrant) and single-flight cache.
private readonly SemaphoreSlim _mutex = new(1, 1);
public async Task RotateAsync(CancellationToken ct)
{
    await _mutex.WaitAsync(ct);
    try { await DoRotationAsync(ct); }              // holding an async lock across I/O: keep the section short
    finally { _mutex.Release(); }
}

private readonly ConcurrentDictionary<string, Lazy<Task<Profile>>> _inflight = new();
public Task<Profile> GetProfileAsync(string id, CancellationToken ct)
{
    var lazy = _inflight.GetOrAdd(id, key => new Lazy<Task<Profile>>(() => LoadAndCacheAsync(key)));
    var task = lazy.Value;                             // exactly one LoadAndCacheAsync per key at a time
    if (task.IsFaulted || task.IsCanceled) _inflight.TryRemove(id, out _);   // do not pin a failure
    return task.WaitAsync(ct);                         // the caller may stop waiting; the shared load continues
}

Producer/consumer with channels

System.Threading.Channels is the modern queue primitive: Channel.CreateBounded<T>(new BoundedChannelOptions(capacity) { FullMode = Wait | DropOldest | DropNewest | DropWrite, SingleReader, SingleWriter }), CreateUnbounded, and since .NET 9 CreateUnboundedPrioritized, which dequeues by IComparer<T> order instead of FIFO. Writers WriteAsync (awaits when a bounded channel is full — that is back-pressure) or TryWrite (returns false, useful for shedding load); the producer calls Complete() to signal the end; consumers await foreach (var x in reader.ReadAllAsync(ct)), and several consumers can share one reader. Compared with the legacy BlockingCollection<T> it never blocks a thread; compared with TPL Dataflow it is a single lightweight primitive rather than a block graph. The canonical ASP.NET Core shape is a singleton bounded channel written by request handlers and read by a BackgroundService that creates a DI scope per item, honours the stopping token, and drains on shutdown.

// Registration: the channel is the seam between request handling and background processing.
builder.Services.AddSingleton(Channel.CreateBounded<EmailJob>(new BoundedChannelOptions(1_000)
    { FullMode = BoundedChannelFullMode.Wait, SingleReader = false, SingleWriter = false }));
builder.Services.AddSingleton(sp => sp.GetRequiredService<Channel<EmailJob>>().Reader);
builder.Services.AddSingleton(sp => sp.GetRequiredService<Channel<EmailJob>>().Writer);
builder.Services.AddHostedService<EmailWorker>();

// Producer (request path): shed load instead of blocking a request forever.
app.MapPost("/signup", async (SignupDto dto, ChannelWriter<EmailJob> jobs, CancellationToken ct) =>
    jobs.TryWrite(new EmailJob(dto.Email)) ? Results.Accepted() : Results.StatusCode(503));

// Consumer: N concurrent workers over one reader, scope per item, graceful stop.
public sealed class EmailWorker(ChannelReader<EmailJob> jobs, IServiceScopeFactory scopes, ILogger<EmailWorker> log) : BackgroundService
{
    protected override Task ExecuteAsync(CancellationToken stoppingToken) =>
        Task.WhenAll(Enumerable.Range(0, 4).Select(_ => WorkerLoopAsync(stoppingToken)));

    private async Task WorkerLoopAsync(CancellationToken stoppingToken)
    {
        await foreach (var job in jobs.ReadAllAsync(stoppingToken))
        {
            using var scope = scopes.CreateScope();
            try { await scope.ServiceProvider.GetRequiredService<IMailer>().SendAsync(job, stoppingToken); }
            catch (Exception ex) when (ex is not OperationCanceledException) { log.LogError(ex, "email job {Email} failed", job.Email); }
        }
    }
}

// Periodic work without overlapping ticks or async void: PeriodicTimer (.NET 6) + TimeProvider (.NET 8) for tests.
public sealed class CleanupWorker(TimeProvider clock, ICleanup cleanup) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5), clock);
        while (await timer.WaitForNextTickAsync(stoppingToken))       // returns false when disposed; throws on cancellation
            await cleanup.RunAsync(stoppingToken);                     // a slow run simply delays the next tick — no overlap
    }
}

Interview trap

"We parallelized it with Parallel.ForEach and an async lambda." Parallel.ForEach takes Action<T>, so the lambda is async void: the loop finishes instantly, nothing is awaited, exceptions crash the process, and the "parallelism" is unbounded. Try it

1. Unbounded versus bounded. Fire 2,000 requests at a local echo endpoint with Task.WhenAll(Select), then with Parallel.ForEachAsync at 16 and at 128. Watch netstat/ss for socket counts, and time each run.

Expected outcome

Interview Q&A

Q1. How do you bound the concurrency of an async fan-out, and how do the options compare?

Parallel.ForEachAsync is the default: source, explicit MaxDegreeOfParallelism, token, async body, and it stops dispatching and cancels in-flight work on failure. When I need results in input order or a per-item success/failure record, I use a SemaphoreSlim gate inside the selector of a WhenAll, catching per item so one failure does not hide the rest. For "N per second" rather than "N at once", System.Threading.RateLimiting gives token-bucket and sliding-window limiters that compose with the same code. The number itself comes from the downstream's limits — connection pool size, partner rate limit — and I make it configuration, because the right value in staging is wrong in production.

Q2. Why can't you await inside a lock, and what do you use instead?

The compiler rejects it (CS1996) because Monitor is thread-affine: the lock must be released by the thread that took it, and after an await you may resume on a different thread — so either the release throws SynchronizationLockException or the lock is held forever. The same applies to Mutex and ReaderWriterLockSlim, and to the new System.Threading.Lock in .NET 9, whose EnterScope returns a ref struct that cannot survive an await. The async replacement is SemaphoreSlim(1,1) with WaitAsync in a try/finally, keeping the guarded region short and never re-entering it. If the design needs a lock held across long I/O, I question the design first — usually a queue or single-flight cache is the real answer.

Q3. Channels versus BlockingCollection versus TPL Dataflow — how do you choose?

BlockingCollection is the pre-async producer/consumer queue: its Take blocks a thread, which is fine on dedicated threads and terrible on the pool, so it is legacy in async code. Channel<T> is the modern primitive: awaitable reads and writes, bounded modes with explicit full-buffer policies, single-reader/writer optimizations, and since .NET 9 a prioritized variant; it is what I use for job queues, batching, and fan-in. TPL Dataflow is a graph of linked blocks with their own bounded capacities and degrees of parallelism — heavier, but genuinely useful when the pipeline has several stages with different parallelism and you want the wiring declarative. My rule: one stage or two, channels; a real multi-stage pipeline with transforms and batching, consider Dataflow, or channels plus Parallel.ForEachAsync per stage.

Q4. Design a background job system inside an ASP.NET Core service.

A singleton bounded channel as the seam: request handlers TryWrite and return 202, or 503 when the buffer is full, so the request path never blocks on the backlog. A BackgroundService runs N worker loops over the reader, each creating its own DI scope per job, forwarding the stopping token, and catching per job so a poison item is logged and dead-lettered rather than stopping the host. Shutdown completes the writer, drains within HostOptions.ShutdownTimeout, and reports whatever could not be processed. Observability is queue length, oldest-item age and per-job latency as metrics. And I say out loud that this loses jobs on a crash: if that matters, the channel becomes an outbox table or a broker, and the in-process worker becomes the consumer of that durable queue.

Q5. PeriodicTimer versus the classic timers, and how does TimeProvider help testing?

System.Threading.Timer and System.Timers.Timer invoke a callback on a pool thread on schedule regardless of whether the previous callback finished, and an async callback becomes async void — so you get overlapping runs and uncatchable exceptions. PeriodicTimer in .NET 6 inverts that: one consumer awaits WaitForNextTickAsync in a loop, ticks never overlap and are coalesced if the body runs long, cancellation is honoured, and exceptions stay in your loop. .NET 8's TimeProvider abstracts the clock and timers — PeriodicTimer, Task.Delay and WaitAsync accept one — so tests use FakeTimeProvider from Microsoft.Extensions.TimeProvider.Testing and advance time instantly instead of sleeping. It turned our slowest test suite from minutes to seconds.

Q6. How do you prevent a cache stampede in async code?

Single-flight: ensure exactly one load per key is in flight and every concurrent caller awaits the same task. The idiom is ConcurrentDictionary<TKey, Lazy<Task<T>>> with GetOrAdd, because Lazy guarantees a single factory execution even if several values are created and discarded during the race; evict the entry when the task faults so a transient failure is not cached forever, and let callers apply their own cancellation with WaitAsync rather than cancelling the shared load. In new code HybridCache provides this out of the box together with L1/L2 tiering. The subtle point is that the cached item is a task, so the storage is a promise of the value rather than the value, which is what makes it race-free.

Q7. Parallel.ForEach, Parallel.ForEachAsync or Task.WhenAll — which for what?

Parallel.ForEach and PLINQ are for CPU-bound work with synchronous bodies: they partition the data and use pool threads efficiently, and they must never be given async lambdas. Parallel.ForEachAsync is for I/O-bound async work with a concurrency cap. Task.WhenAll is for a small, known set of independent async operations — two or three service calls per request — where starting all of them is the point. The mistake in each direction is predictable: CPU work under ForEachAsync wastes the cap on compute that could have used partitioning, and I/O fan-out under WhenAll over a large collection is unbounded. I ask "how many, and is it CPU or I/O?" before picking.

Q8. What are prioritized channels in .NET 9 good for?

Channel.CreateUnboundedPrioritized<T> dequeues the smallest element according to a comparer instead of FIFO, which covers cases that used to need a hand-rolled heap plus a semaphore: retry queues ordered by next-attempt time, work items with a priority field, or scheduling the nearest deadline first. It is unbounded only, so producers must shed load themselves, and priority means starvation of low-priority items is possible under sustained load — I usually age priorities or cap the high-priority share. It composes with the same ReadAllAsync consumer loops, so adopting it inside an existing worker is a one-line change.

Q9. Describe graceful shutdown for a pipeline with several stages.

Stop intake first — the readiness probe fails, the HTTP endpoint returns 503, the broker subscription pauses — so no new work enters. Then complete the first channel's writer and let each stage drain into the next in order; completion propagates because ReadAllAsync ends when the channel is completed and empty. Each stage bounds its own drain with the stopping token so a stuck item cannot exceed the host's 30-second budget, and anything still in flight at the deadline is checkpointed or acknowledged as not done so a broker redelivers it. I test it by sending SIGTERM under load and asserting counts in equals counts out plus redelivered, and I make sure health probes and shutdown hooks run before the thread pool is saturated, because a starved pool cannot even run the shutdown code.

Q10. How do you keep outbound calls from overwhelming a partner API?

Two independent limits: concurrency and rate. Concurrency is Parallel.ForEachAsync or a semaphore; rate is a TokenBucketRateLimiter from System.Threading.RateLimiting, sized from the partner's documented quota with a small burst, applied through a DelegatingHandler so every HttpClient call to that host acquires a lease. Combine with retry-after-aware retries and jitter — Polly or the .NET 8 resilience pipeline — so a 429 slows us down rather than doubling the load. Then observe: leases queued, wait time per lease, and 429 rate are the metrics that tell you whether the limit is set right. The failure I am avoiding is the one where each of forty service instances is individually polite and collectively still forty times over the quota, so for hard quotas the limiter has to live in a shared gateway.

Runtime Async (.NET 11) and staying current

Official: What's new in the .NET 11 runtime — Runtime Async runtime-async spec (dotnet/runtime) .NET 11 Preview 7 announcement C# version history

For thirteen years every C# async method has been a compiler-generated state machine; the runtime knew nothing about suspension. Runtime Async — sometimes called "async2" from the experiment days — moves that knowledge into the runtime. The compiler emits a method marked [MethodImpl(MethodImplOptions.Async)] whose body still contains your straight-line code, with each await compiled to a call such as AsyncHelpers.Await<T>(task). The JIT generates code that, when the awaited operation is not complete, saves only the live locals into a runtime-managed continuation object and returns; when the operation completes, the runtime resumes the method at the suspension point. No IAsyncStateMachine, no MoveNext, no builder, no boxing of a struct that hoisted every variable. The observable semantics — where continuations run, ConfigureAwait, ExecutionContext flow, exception behaviour, ValueTask rules — are deliberately unchanged; what changes is cost and visibility.

Where it stands today (September 2026)

It was an experiment in .NET 9 and available for experimentation in .NET 10 behind an environment variable plus preview flags. In the .NET 11 previews it became real: Preview 1 (Feb 2026) enabled the CoreCLR support by default and added foundational NativeAOT support; by Preview 7 (11 Aug 2026) a net11.0 project needs only <Features>runtime-async=on</Features> — no EnablePreviewFeatures — the old DOTNET_RuntimeAsync/UNSUPPORTED_RuntimeAsync variables were removed in favour of a per-project <UseRuntimeAsync>false</UseRuntimeAsync> opt-out, and, the headline, the runtime libraries themselves are compiled with runtime-async=on: the BCL no longer contains compiler-generated state machines. Microsoft explicitly asks for reports on throughput and library size. It is still labelled a preview feature and opt-in; .NET 11 GA is expected 10 November 2026 as an STS release, and whether the switch flips to default is something to check in the GA notes.

What improves, what is restricted, what is unaffected

Improves: live stack traces (13 frames → 5 in the docs' three-level example) for profilers, the debugger call-stack window and diagnostic logging; breakpoints and stepping across await; allocations, via reused continuation objects, not saving unchanged locals, and the ExecutionContext capture elision that .NET 11 applies to all continuations; code size through tail-merged suspension points; NativeAOT and ReadyToRun support including inlining of await-less async calls in crossgen2; and JIT-level wins such as recognizing Task.FromResult/ValueTask.FromResult/Task.CompletedTask as intrinsics, tiering async methods, and cheaper await Task.Yield(). Restricted: only Task, Task<T>, ValueTask and ValueTask<T> returns, so async iterators and async void keep the compiler machinery; methods using a custom or pooling [AsyncMethodBuilder] opt out; suspension points cannot sit inside catch/filter/finally handler blocks at the IL level (the C# compiler keeps lowering await in catch/finally as it always has, so your source is unaffected); byref-like locals default after a suspension; no localloc in the method. Custom awaiters work through AsyncHelpers.AwaitAwaiter/UnsafeAwaitAwaiter. Unaffected: blocking is still blocking, ConfigureAwait still means what it meant, AsyncLocal still flows, and a ValueTask may still be consumed once. It is also not green threads: the .NET team ran a green-threads experiment in 2023 and shelved it because of interop, performance and ecosystem costs; Runtime Async is the chosen direction precisely because it keeps the existing async model.

Interview Q&A

Q1. What is Runtime Async, in one paragraph?

It is the .NET 11 preview feature that moves async method suspension from the C# compiler into the runtime. Instead of generating a state machine with MoveNext, the compiler emits a method marked MethodImplOptions.Async whose awaits are calls to AsyncHelpers.Await; the JIT produces code that saves live locals into a runtime-managed continuation when the awaited operation is incomplete and resumes the method later. Semantics are unchanged, so existing code keeps working, but live stack traces become the real call chain, allocations drop, NativeAOT and ReadyToRun are supported, and the JIT can optimize across awaits. As of Preview 7 it is opt-in per project and the runtime libraries themselves are built with it.

Q2. How do you enable or disable it today, and what did the previews change?

On a net11.0 project you add <Features>runtime-async=on</Features>; since Preview 7 you no longer need EnablePreviewFeatures, and the environment variables that used to gate the runtime side were removed — the runtime support is simply on, and you opt a project out with <UseRuntimeAsync>false</UseRuntimeAsync>. In .NET 10 it was experimental and needed DOTNET_RuntimeAsync=1 plus the preview flag. The other preview milestones were NativeAOT support in Preview 1, ReadyToRun inlining and tiered compilation of async methods later, and the BCL being compiled with the feature by Preview 7. I would phrase the status as "preview, opt-in, production-validated by the framework itself, default status to be confirmed at GA in November".

Q3. What changes for a developer, and what explicitly does not?

Nothing in the source: async, await, ConfigureAwait, cancellation and exception handling are written and behave the same, including where continuations run and how AsyncLocal flows. What changes is what the tools show and what the runtime spends: the debugger steps cleanly across awaits and binds breakpoints reliably, profilers and new StackTrace() see real frames, and hot async paths allocate less. What does not change is every performance rule that was about blocking or unbounded concurrency — starvation, sync-over-async and WhenAll over 10,000 items are exactly as bad as before — and the ValueTask consumption contract still holds.

Q4. What evidence is there that it is worth adopting?

The strongest evidence is that Microsoft compiled the entire runtime library set with it in Preview 7 and is running its own validation on that, which no private benchmark can match. The documented, reproducible gains are the stack-trace reduction — 13 frames to 5 in a three-level example — NativeAOT and R2R support, and a list of JIT optimizations such as continuation reuse, not saving unchanged locals, factory intrinsics and tiered async compilation. What is missing in the public material as of now is a headline throughput number, so my honest position is "adopt in a canary, measure allocations and p99 on your workload, and report", which is what the team is asking for.

Q5. Is this green threads? Why did .NET go this way?

No. Green threads would have made blocking calls cheap by multiplexing user-mode threads, and the .NET team prototyped that in 2023 and shelved it: it clashed with native interop and existing thread-affinity assumptions, complicated the runtime and debugger, and the ecosystem already had a working async model with a huge API surface. Runtime Async keeps the explicit Task-based model — every existing library, analyzer and diagnostic tool continues to apply — and attacks the actual complaints: state-machine cost, ugly stacks, AOT friction. It is an implementation upgrade of the model rather than a replacement of it, which is why it can be rolled out as an opt-in with no semantic migration.

Q6. What does Runtime Async not cover, and what are its restrictions?

It applies only to methods returning Task, Task<T>, ValueTask or ValueTask<T>, so async iterators, async void and methods with custom or pooling [AsyncMethodBuilder] attributes stay on the compiler path. At the IL level, suspension points cannot sit inside catch, filter or finally handlers, byref-like locals cannot survive a suspension, and stackalloc is disallowed in such methods — constraints the C# compiler already deals with, so source code is not affected. Custom awaiters are supported through AwaitAwaiter and UnsafeAwaitAwaiter. And it requires a runtime that has the feature, so a library that must run on .NET 10 cannot ship runtime-async IL for that target.

Q7. How would you roll it out across forty services?

Start with the services already on net11.0 previews and pick one canary with good telemetry and a representative async profile — a gateway or a high-RPS API. Flip the feature in that project, run the full test suite, then compare allocation rate, GC pauses, p50/p99 and CPU against a control deployment under production traffic for a week. In parallel, check anything that parses stack traces — APM agents, log sanitizers, exception grouping keyed on MoveNext frame names — because those are what actually change. Then roll out by risk tier with UseRuntimeAsync=false as the documented one-line rollback, and file findings upstream. I would not do this in .NET 10, and I would wait for the GA notes before making it a default in the shared build props.

Q8. What could break?

Not the semantics — the design goal is zero behavioural change — but the periphery. Tooling that pattern-matches compiler-generated names (<Foo>d__3.MoveNext) in stack traces, exception fingerprinting that depended on those frames, custom stack-walking code, and profilers or APM agents that have not updated to the new async profiler events are the realistic risks. Libraries with custom async method builders opt out automatically, so they are safe but gain nothing. Because it is a preview feature, a genuine runtime bug is possible, which is why the canary approach and Microsoft's request for reports matter. What I would not expect are subtle ordering or context differences, and if I saw one I would treat it as a bug to report, not a new rule to learn.

Q9. How does it interact with ValueTask, pooling and ConfigureAwait?

ValueTask is fully supported — AsyncHelpers.Await has overloads for it and for ConfiguredValueTaskAwaitable — and the JIT treats ValueTask.FromResult as an intrinsic, so the synchronous fast path stays allocation-free. Methods that use PoolingAsyncValueTaskMethodBuilder opt out of runtime async because they are already pooled; the runtime's own continuation reuse is the generic replacement, which over time reduces the reasons to hand-pool. ConfigureAwait is honoured identically, through the configured-awaitable overloads. The ExecutionContext capture elision in .NET 11 is separate and benefits both models, and it rewards code that does not touch AsyncLocal on hot paths. So none of the existing guidance is reversed; some of the performance motivations for it become weaker.

Q10. How do you keep a team current on async without chasing every preview?

Anchor on LTS: today that is .NET 10, so the team standard is System.Linq.AsyncEnumerable, Task.WhenEach, ConfigureAwaitOptions, CancelAsync, TimeProvider, channels and Parallel.ForEachAsync, all enforced with the analyzer set. Assign one person to read the preview notes for the next major and demo anything that changes our rules — for .NET 11 that is Runtime Async and the NDJSON streaming overloads — in a short session, with a canary if it is cheap. Keep a one-page "modern versus legacy" table in the repo so reviewers can point at it instead of arguing, and retire legacy patterns (StartNew, ContinueWith, BlockingCollection, System.Linq.Async) on a schedule tied to framework upgrades. The goal is that people can explain why a rule exists, because that is what transfers to the next feature.

Architecture & API design
Q1. What does "async all the way" mean at system scale, and where are synchronous boundaries legitimate?

It means that from the entry point — the request delegate, the message handler, Main — down to the I/O call, no frame blocks on a task; every layer returns a task and every caller awaits it. The reason is scale: a blocked thread is a resource you have very few of, while a suspended state machine costs a heap object, so the design only pays off if the chain is unbroken. Legitimate boundaries are entry points that are synchronous by contract and cannot be changed today — an old plugin interface, a COM callback, a console Main on .NET Framework — and there the rule is one explicit GetAwaiter().GetResult() with a comment, at the very top, never in the middle. In a migration I count the boundaries and drive the number down release by release, top-down, because a boundary in the middle of the stack creates sync-over-async underneath it.

Q2. Should a library expose synchronous wrappers over async methods, or async wrappers over synchronous ones?

Neither, as a rule — Stephen Toub's two classic posts still stand. A sync wrapper (Foo() => FooAsync().GetAwaiter().GetResult()) hides blocking and sync-over-async inside your library where the caller cannot see it, and it deadlocks under a SynchronizationContext. An async wrapper (FooAsync() => Task.Run(Foo)) is "async over sync": it lies about scalability, burns a pool thread, and prevents the caller from making the offloading decision themselves. If the underlying operation is truly asynchronous, expose only the async version; if it is truly synchronous — CPU work, in-memory — expose only the sync version and let callers use Task.Run where it suits their app model. The exception is a genuinely dual implementation, like Stream, where both paths are native.

Q3. How do you design an async interface for a service abstraction?

Methods return Task or Task<T>, with the Async suffix, and take a CancellationToken last; ValueTask only on a documented hot member where implementations commonly complete synchronously. Anything naturally streaming — rows, pages, events — returns IAsyncEnumerable<T> rather than Task<List<T>>, so implementations can stream and callers can stop early. Resource-owning abstractions implement IAsyncDisposable, and I keep IDisposable too when synchronous cleanup is cheap. I never put a token in the constructor or a property, never expose Task.Result-shaped members, and I document per method what cancellation and partial failure mean. Finally, the interface must be implementable without blocking, which is a good test: if a reasonable implementation would need .Result, the interface is wrong.

Q4. How do dependency-injection scopes interact with async work?

A scope is a lifetime boundary, not a thread boundary: scoped services are safe to use across awaits within the request, but they are disposed when the scope ends, which in ASP.NET Core is when the response completes — so any work that outlives the request must create its own scope from IServiceScopeFactory. Since .NET 6 scopes are async-aware: CreateAsyncScope() returns an AsyncServiceScope whose DisposeAsync calls IAsyncDisposable on services, and disposing a scope synchronously that holds an async-only disposable throws. Scoped services are also not thread-safe, so parallel work inside one request must not share the DbContext — that is the "a second operation was started on this context" exception. In workers, the rule is one scope per message.

Performance & debugging
Q5. An async operation is hung in production and nothing is being logged. How do you find out what it is waiting on?

Take a dump with dotnet-dump collect and open it in dotnet-dump analyze or Visual Studio. clrstack -all shows what threads are doing, but a hung async operation is usually on no thread, so the key command is dumpasync, which lists the async state machines and tasks still alive with their state and, with -stacks, the chain of continuations — effectively the logical async stack. From there you find the awaiter that never completed: a TaskCompletionSource nobody set, a semaphore never released, a Channel read with no writer. Visual Studio's Tasks and Parallel Stacks windows show the same in a UI. If it recurs, I add dotnet-trace collection of the WaitHandleWait and thread-pool events so the next occurrence is captured in flight.

Q6. What HttpClient practices matter specifically for async code?

Use IHttpClientFactory or a long-lived HttpClient over a SocketsHttpHandler with PooledConnectionLifetime, so you neither exhaust sockets by creating clients per request nor pin stale DNS. Pass the cancellation token to every call and set a per-request timeout via the token or Timeout — the default is 100 seconds, which is far too long for a hop inside a request. For large responses use HttpCompletionOption.ResponseHeadersRead and stream the body, and dispose the response so the connection returns to the pool. Bound concurrency per host with a semaphore or a rate limiter, because .NET Core imposes no per-host connection limit by default. And use the .NET 8 resilience handler or Polly for retries with jitter, capped, so an outage does not become a retry storm.

Q7. How do you measure async overhead, and what do you look for?

With BenchmarkDotNet in Release and [MemoryDiagnoser], benchmarking the real code path with both the synchronous-completion and suspending cases, because they have completely different costs. In allocation profiles I look for AsyncStateMachineBox instances per operation — more than one per logical operation means unnecessary suspension or non-elided wrappers — for ExecutionContext churn from AsyncLocal writes on hot paths, and for Task instances that could be ValueTask or cached. In traces I look at thread-pool queue length and the time between a completion and its continuation running, which is where SynchronizationContext hops and starvation show up. The trap is optimizing async plumbing when the actual cost is the I/O; I always compare against wall-clock per operation before touching ValueTask.

Q8. What techniques do high-throughput .NET servers use to keep async cheap?

ValueTask backed by pooled IValueTaskSources for I/O, System.IO.Pipelines to avoid copying, ArrayPool buffers with strict ownership across awaits, IThreadPoolWorkItem implementations to queue work without delegate allocations, ConfigureAwait(false) everywhere, no AsyncLocal writes on hot paths, and cached completed tasks for common results. Kestrel and SocketsHttpHandler are the reference implementations of all of these. Most application code should not do this — the complexity cost is real — but a lead should recognize these patterns when reading framework code and know that .NET 11's Runtime Async and ExecutionContext elision are pushing several of them down into the runtime so fewer people need to hand-roll them.

Legacy & migration reality
Q9. What is different about async on .NET Framework 4.8, and how do you sequence a migration?

On Framework every suspending async method costs about four allocations instead of one, there is no pooling builder, IAsyncEnumerable and IAsyncDisposable need the Microsoft.Bcl.AsyncInterfaces package, the thread pool lacks blocking-aware injection, and classic ASP.NET's AspNetSynchronizationContext makes any .Result a deadlock. The migration order that works: first make the code correct on Framework — remove sync-over-async top-down, add ConfigureAwait(false) in libraries, replace ContinueWith — because those changes are safe on both runtimes; then retarget shared libraries to netstandard2.0 or multi-target; then move the host to ASP.NET Core, at which point the deadlocks are gone and the remaining blocking calls show up as starvation under load tests. Doing the host move first tends to hide problems that reappear in production.

Q10. How do you remove ContinueWith and Task.Factory.StartNew from a large codebase safely?

Mechanically most ContinueWith(t => ...) chains become await plus straight-line code, but each one needs a look at three things: whether it relied on TaskContinuationOptions like OnlyOnFaulted or ExecuteSynchronously, whether it silently swallowed the antecedent's exception by never touching t.Result, and whether it captured a scheduler explicitly. StartNew becomes Task.Run unless it used LongRunning or AttachedToParent, which need an explicit decision. I do it with an analyzer flagging the calls, a rule that every converted site keeps or improves its exception handling, and tests around anything with a custom scheduler. The payoff is not style: it is that exceptions stop disappearing and that SynchronizationContext behaviour becomes predictable.

Q11. How do you adopt IAsyncEnumerable and the new LINQ across a solution with mixed target frameworks?

Standardize the operator source first: on net10.0 the in-box System.Linq.AsyncEnumerable, and for net8.0/netstandard2.0 projects the System.Linq.AsyncEnumerable NuGet package, which has the same API — never a mix with the old System.Linq.Async, or you get ambiguity errors. Remove System.Linq.Async or upgrade it to 7.0, rename SelectAwait-style calls, and upgrade EF Core so ToListAsync on DbSet stops being ambiguous. Then convert APIs that return large lists to streams from the data layer outward, keeping Task<List<T>> where consumers really need the whole set. Add the [EnumeratorCancellation] rule to reviews and the disposed-context trap to the team wiki, because those two bugs account for most of the early incidents.

Testing & tooling
Q12. How do you test async code deterministically?

Tests are async Task, never async void, and never contain Task.Delay or Thread.Sleep to "wait for things". Control ordering with TaskCompletionSource: the fake dependency returns a task you complete from the test at the exact moment you want, which lets you assert behaviour while an operation is in flight — cancellation, timeouts, concurrent calls. Time goes through TimeProvider with FakeTimeProvider, so a five-minute retry schedule is tested in milliseconds by advancing the clock. Cancellation is tested by cancelling a real token and asserting OperationCanceledException and the cleanup side effects. For concurrency limits I count concurrent in-flight fakes with Interlocked and assert the maximum. What I avoid is testing thread identity, because nothing in the model guarantees it.

Q13. Which analyzers do you turn on for async, and how do you introduce them into a noisy codebase?

From the built-in set: CA2007 for libraries, CA1849 and CA2012, CA2016, CA2025 in .NET 10, plus CS4014 and CS1998 raised to errors. From Microsoft.VisualStudio.Threading.Analyzers: VSTHRD002 (sync-over-async), VSTHRD100 (async void), VSTHRD103 (sync call in async method), VSTHRD110 (unobserved result), VSTHRD111 (ConfigureAwait). Introduction is incremental: enable as warnings, generate a baseline with dotnet format or a suppression file so existing violations do not block builds, make new violations errors on changed files via .editorconfig and CI, and burn down the baseline with a fixed weekly budget. The rules that find real bugs — async void, unobserved tasks, disposed-before-awaited — go to error first; the style ones can wait.

Q14. How do you read an async stack trace, and what tooling helps?

An exception trace from async code is stitched from segments: the frames up to the throw, then "End of stack trace from previous location", then the frames of each awaiting caller as the exception propagated through awaits — so read it as a logical call chain, and note that frames of elided (non-async) methods are missing. Compiler-generated names like <LoadAsync>d__12.MoveNext map to LoadAsync; modern .NET already tidies exception traces, and .NET 11's Runtime Async tidies live traces for profilers and debuggers too. In Visual Studio the Tasks window and Parallel Stacks with "Tasks" view show the logical chain; dotnet-dump's dumpasync does it offline; dotnet-trace with the thread-pool and .NET 9 wait events shows scheduling delays. The recurring mistake is grouping errors by the top frame, which for async is often framework plumbing — group by the first application frame instead.

Reliability & security
Q15. How can async code become a denial-of-service vector, and what are the defences?

Async makes it cheap to accept work, so the failure mode shifts from "out of threads" to "out of everything else": memory from a million buffered request bodies, sockets from unbounded fan-out, database connections from unbounded queries, and starvation from a single blocking call that a malicious slow client can trigger repeatedly. Defences are bounds at every layer: Kestrel's request body and concurrent connection limits, the .NET 7 rate-limiting middleware and .NET 8 request timeouts, bounded channels and Parallel.ForEachAsync internally, per-host outbound limits, and forwarding RequestAborted so a disconnected attacker stops consuming capacity. Then load-test the limits, because a limit you have never hit is a guess.

Q16. Design the timeout strategy for a request that crosses four services.

A deadline budget that shrinks as it goes down: the edge sets the total, say 5 seconds, and each hop passes a token with a shorter remaining time so a downstream call never outlives its caller's interest. In .NET that is CreateLinkedTokenSource(ct) plus CancelAfter per hop, forwarded into HttpClient, EF Core and gRPC, which supports deadlines natively. Timeouts are shorter than retries: retries fit inside the remaining budget or do not happen, with jitter, so a slow dependency degrades into fast failures instead of a queue of doomed work. HttpClient's 100-second default and unbounded database command timeouts are replaced with explicit values, and each layer maps its own timeout to a distinct error so the dashboards show where time went. The organizing principle is that timing out early and cheaply is what keeps the thread pool and connection pools alive for the requests that can still succeed.

Q17. The client cancels in the middle of a multi-step write. What should happen?

Cancellation must never leave the system half-written, so I distinguish the point of no return. Before it, cancellation aborts and the work is rolled back or was never committed — a transaction that is disposed without commit. After it, the operation ignores the client's token deliberately: the write completes, the outbox record is committed with it, and the client's disconnect only means it will not see the response. In code that is a linked token for the preparatory phase and CancellationToken.None with an explanatory comment for the commit phase, plus idempotency keys so a retrying client does not duplicate the effect. The anti-pattern is catching OperationCanceledException around the whole thing and returning a partial success, which is how you get a debited account and no order.

Judgment & scenarios
Q18. A PR adds .Result in a constructor because "constructors can't be async". What do you say?

Correct premise, wrong conclusion. Constructors cannot await, so the async initialization moves out of the constructor: a static factory method CreateAsync that awaits and then calls a private constructor, or an explicit InitializeAsync called by the composition root, or lazy initialization with an AsyncLazy-style cached task on first use. In DI I register the type and have a hosted service or a startup filter await the initialization before the app reports ready, so nothing blocks inside container resolution — which would otherwise deadlock in some hosts and starve the pool in others. I frame the review comment as "we need the object constructed synchronously and its data loaded asynchronously; here is the factory shape", because the author's constraint is real and the fix is a pattern, not a rejection.

Q19. How do you move a skeptical team off .Result and Task.Run habits?

With evidence from their own system rather than doctrine: I reproduce starvation on a staging copy with a load tool and show the thread-count graph and p99 climbing while CPU idles, then show the same endpoint with await. That converts the discussion from taste to physics. Next I make the right thing easy — analyzers that flag the patterns, a wiki page with the three or four idioms that replace them, a helper for the one fire-and-forget case, and a shared Directory.Build.props — and I pair on the first few conversions in the ugliest code so people see it is mechanical. I explicitly allow one documented sync boundary per entry point so the change is not "rewrite everything", and I track the number of boundaries on a dashboard so progress is visible. Skepticism usually comes from a bad past experience with a deadlock; naming that and explaining why ASP.NET Core removed it goes a long way.

Q20. Incident: a downstream API slows from 50 ms to 5 s and your service's error rate climbs to 40% within minutes. First fifteen minutes?

First, confirm the mechanism: latency on the dependency, then our thread-pool counters and connection-pool waits — if thread count is climbing, something is blocking on that dependency; if it is flat but queue length and outbound in-flight counts are high, we are simply holding too many concurrent requests open and hitting our own limits. Second, stop making it worse: cut retries to the slow dependency, tighten its timeout so requests fail fast, and if we have a circuit breaker, verify it opened; if we have a rate limiter, lower the concurrency to what the dependency can currently sustain. Third, shed or degrade: serve cached or default responses for the affected feature if the product allows. Only then do I care about root cause on their side. Afterwards the postmortem asks why a single slow dependency could take 40% of our capacity — usually a missing timeout budget, unbounded concurrency or a hidden blocking call — and fixes that structurally.

Q21. Leadership asks whether to enable Runtime Async when .NET 11 ships in November. What is your recommendation?

Adopt deliberately, not by default. The technical case is strong — the whole BCL is compiled with it, the diagnostics improvements are real, and the semantics are unchanged — but it is labelled preview and the throughput evidence is workload-dependent. So: upgrade to .NET 11 on its normal STS schedule, enable the feature on one or two well-instrumented canary services, measure allocations and tail latency for a couple of weeks, verify our APM and log tooling handle the new stack shapes, and keep UseRuntimeAsync=false as the rollback. If the canaries are clean, flip it in the shared build props for services on .NET 11, and wait for Microsoft to make it the default before removing the opt-in. What I would push back on is either extreme: enabling it everywhere on day one, or ignoring it until it is forced, because the teams that understand it early will write better async code regardless.

Q22. What do you listen for when a candidate explains async, and what is the one rule you would put on the wall?

I listen for the mechanism rather than the vocabulary: whether they know that an await is a continuation registration, that the synchronous prefix runs on the caller's thread, that the pool ramps slowly and why blocking hurts, that ConfigureAwait and ExecutionContext are different things, and that cancellation is cooperative. A senior adds trade-offs — when ValueTask is wrong, when a stream beats a list — and a principal adds system consequences: bounded concurrency, timeout budgets, graceful shutdown, what to do in an incident, and what is changing in the platform. The wall rule is "never block on a task, never leave a task unobserved, and bound everything"; nearly every async incident I have seen violated one of those three.

Night-before cheat sheet

  1. await is a continuation registration, not a thread: the method runs synchronously to the first incomplete await, then returns an incomplete Task; whoever completes the awaited operation runs the rest.
  2. A suspending async method costs one allocation (the state-machine box, which is the Task); a synchronously completing one costs nothing — which is the whole case for ValueTask on hot paths, and only there.
  3. The thread pool starts at the processor count and grows about one thread per half second; since .NET 6 it reacts faster to Task-style blocking but not to Thread.Sleep, locks or sync I/O — so .Result in a request path is starvation, and in a UI or classic ASP.NET app it is a deadlock.
  4. Two contexts flow across an await: SynchronizationContext (where; skipped by ConfigureAwait(false)) and ExecutionContext (what — AsyncLocal, logging scopes, tracing; always flows). ASP.NET Core has no SynchronizationContext; libraries still use ConfigureAwait(false).
  5. .NET 8's ConfigureAwaitOptions adds SuppressThrowing (non-generic Task only) and ForceYielding; .NET 8 also added CancelAsync, TimeProvider and request timeouts.
  6. Exceptions live in the task and surface at the await; WhenAll throws the first and keeps the rest in .Exception; async void crashes; unobserved tasks are silent — so every fire-and-forget goes through one fault-observing helper, and background work from requests goes through a channel and a hosted service.
  7. Cancellation is cooperative: Cancel runs callbacks inline, linked sources must be disposed, Task.Run's token only prevents starting, WaitAsync abandons rather than aborts, and you catch OperationCanceledException, not just TaskCanceledException.
  8. ValueTask is consumed exactly once — CA2012 as an error — and IValueTaskSource with ManualResetValueTaskSourceCore is how the framework gets to zero allocations; default to Task everywhere else.
  9. IAsyncEnumerable<T> is a cold, pull-based, back-pressured stream: [EnumeratorCancellation] or WithCancellation is ignored, never return one from inside a using, and since .NET 10 the LINQ operators are in the box (System.Linq.AsyncEnumerable, replacing System.Linq.Async).
  10. Bound everything: Parallel.ForEachAsync with an explicit degree, SemaphoreSlim as the async lock, bounded Channel<T> for producer/consumer (prioritized in .NET 9), PeriodicTimer for loops, RateLimiter for quotas, and a shrinking timeout budget per hop.
  11. .NET 9 added Task.WhenEach, System.Threading.Lock and the WaitHandleWait trace event; .NET 10 LTS (Nov 2025) is the anchor release; .NET 11 (GA expected 10 Nov 2026) brings Runtime Async — opt-in via <Features>runtime-async=on</Features>, BCL already compiled with it since Preview 7, same semantics, cleaner live stacks, fewer allocations, NativeAOT-ready, and it is not green threads.
  12. Diagnose with dotnet-counters (thread count, queue length), dotnet-stack, dotnet-trace --clrevents waithandle, and dotnet-dump's dumpasync; enforce with CA2007/CA1849/CA2012/CA2016/CA2025 and the VSTHRD rules.
