1.The 2 a.m. thread-pool starvation

SeniorProduction incident / outageTeaches: hill-climbing injection, sync-over-async, dotnet-counters / dotnet-stack, .NET 9 WaitHandleWait event

Altitude ladder: Mid — you found the .Result and replaced it with await. Senior — you ran the incident: rollback first, diagnosis second, permanent fix and alerting third. Staff — you explain the injection algorithm and why SetMinThreads is a bandage, and you changed the review process. Principal — you turned it into a platform guardrail (blocking detection in staging, thread-count SLO) across teams.

aWorked example Example — replace with your own

The page went at 02:07. An order API that normally ran at a p99 of 180 ms was answering in 12 seconds, and the Kubernetes readiness probe — a trivial /healthz endpoint — was timing out, so the orchestrator was killing pods and replacing them with fresh ones that came up cold and fell over within a minute. CPU across the fleet sat at 35%, which was the first real clue: a saturated service is hot, a starved service is idle and slow. On the dashboards dotnet.thread_pool.thread.count had climbed from 16 (one per core) to about 48 within seconds of the deploy and was then creeping up by one or two threads every second toward 240, while dotnet.thread_pool.queue.length was sitting in the thousands. That signature — thread count growing roughly linearly while CPU stays low — is the thread pool's hill-climbing and blocking-aware injection telling you that its worker threads are blocked, not busy.

I declared the incident and made the first decision: roll back before understanding, because the deploy was the only change and a rolling restart of the previous image takes four minutes. The p99 was back under 200 ms six minutes later. Then, on one pod I had kept alive with the bad build, I ran dotnet-stack report -p <pid> and got 180 near-identical stacks: WorkerThreadStart → … → FeatureFlagClient.IsEnabled → Task.SpinThenBlockingWait → ManualResetEventSlim.Wait. The new feature-flag SDK exposed a synchronous IsEnabled(string); on a cache miss it refreshed flags over HTTP and blocked on .GetAwaiter().GetResult(). The refresh interval was 60 seconds, so every minute a burst of requests hit the miss simultaneously, each one parking a pool thread while waiting for an HTTP continuation that itself needed a pool thread to run. The pool injects new threads only slowly once above the minimum (the runtime's own docs describe the pattern as 2–3× cores quickly, then one or two per second), so the backlog compounded faster than threads arrived.

// The pattern that took the service down (inside an IAuthorizationHandler that was sync by signature)
public bool IsEnabled(string flag)
{
    if (_cache.TryGetValue(flag, out var on)) return on;
    RefreshAsync().GetAwaiter().GetResult();      // sync-over-async on a ThreadPool thread
    return _cache[flag];
}

// The fix: no network on the request path, ever.
public sealed class FlagRefresher(FlagClient client, FlagCache cache) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(60));   // .NET 6+
        do { await cache.ReplaceAsync(await client.FetchAsync(stoppingToken)); }
        while (await timer.WaitForNextTickAsync(stoppingToken));
    }
}
// Request path becomes a dictionary lookup; the handler stays sync and never blocks.

What I did differently after: the permanent fix moved the refresh off the request path entirely (a BackgroundService on a PeriodicTimer, request path reads a snapshot), the authorization handler became async anyway so the next SDK could not reintroduce the trap, and we added dotnet.thread_pool.thread.count > 3 × cores for 2 min as an alert. In staging we enabled a blocking detector (the WaitHandleWait runtime event, new in .NET 9, collected with dotnet-trace collect --clrevents waithandle --clreventlevel verbose) so a sync-over-async call fails a load test before it reaches production. The thing I would change about the night itself: I spent eight minutes reading logs before looking at thread counts. Starvation has a two-counter signature; I should have checked it first.

cRecall prompts

When did you last watch a .NET service behave differently under load than in dev because a thread pool thread was blocked?

Look for: latency spikes with low CPU, "it only happens in prod", readiness probes failing, a thread count that keeps growing. Common culprits: .Result in a middleware, lock around an I/O call, an IMemoryCache.GetOrCreate factory that blocks, a sync logging sink flushing over the network, a sync-only vendor SDK.

Which tool actually confirmed the cause — counters, dumps, traces, a profiler, or a guess that happened to be right?

Be honest if it was a guess. A strong answer names the tool and the exact evidence: 180 stacks in SpinThenBlockingWait, a WaitHandleWait event tree in PerfView, a Parallel Stacks view in Visual Studio. If you did guess, say what you would use now.

What was your first action, and would you still make that call with hindsight?

Rollback versus roll-forward, scaling out as a bandage, bumping min threads. Explain the trade-off you took (e.g. rollback lost a feature for 3 hours but restored SLO in 6 min).

What guardrail exists now that did not exist before, and who else adopted it?

Alerts on thread count, analyzers (VSTHRD002 for .Result/.Wait), blocking detection in load tests, a written "no network on the sync path" rule. Cross-team adoption is your Staff/Principal signal.

dFollow-up drill chain

Why does one blocking call cause a cascade instead of a single slow request?

Because the thing the blocked thread waits for — the HTTP completion — needs a pool thread to run its continuation, and the pool is the shared resource being consumed. Once every worker is parked, no continuation can run, so no blocked thread ever unblocks; it is a self-sustaining wait. The pool does inject threads, and since .NET 6 it reacts faster to Task.Wait/.Result specifically, but above the minimum it still adds roughly a thread or two per second, which is far slower than a load spike creates blocked requests. Cheap capacity to lose, expensive capacity to add: that asymmetry is the cascade.

Why not just call ThreadPool.SetMinThreads(500, 500) and move on?

Because it changes how fast the pool injects, not whether threads block. It removes the injection throttle up to 500, so a burst of 500 blockers gets absorbed, but the 501st still queues; meanwhile you pay memory (each thread reserves stack — 1 MB on Windows, up to 8 MB on Linux by default, committed lazily) and context-switch cost, and you hide the defect that will resurface at the next scale step. I use it as a documented, alerted stopgap with an expiry date when a fix cannot ship today, never as the fix. The actual fix is to stop blocking or to isolate known-blocking work on dedicated threads.

At what scale does the "make it async" fix itself break?

Async removes thread blocking, not work. Once nothing blocks, the next ceiling is whatever the awaited resource can sustain: connection-pool limits, downstream rate limits, socket counts, and GC pressure from state machines and continuations. A fully async service can happily open 50,000 concurrent DB calls and fall over differently. So after making it async I bound concurrency explicitly — SemaphoreSlim, Parallel.ForEachAsync with a max degree, or a bounded Channel<T> — and I watch allocation rate, because at high RPS the state-machine boxes and Task objects become the profile.

How did you get the team to accept a rollback that removed a feature customers were waiting for?

I framed it as reversible versus irreversible: a rollback costs three hours of a feature, an extended outage costs order data and trust we cannot roll back. I stated the decision, the reason, and the re-deploy criteria — root cause identified, fix reviewed, load-tested against the dependency's cold path — in the incident channel so product could see the path back rather than just the loss. The disagreement resolved because the criteria were concrete and dated.

What would you change in the review process so this class of bug does not merge?

Two things. Mechanically: Microsoft.VisualStudio.Threading.Analyzers with VSTHRD002 (synchronous waits) and CA1849 (call async when available) as errors in service projects, and a load test that fails on any WaitHandleWait event on a pool thread. Culturally: every new SDK or dependency gets a "what does it do on its slow path" question in the design review, because the bug was in a vendor library's cache miss, not in code we wrote. The analyzers would not have seen inside the SDK; the review question would.

What did you trade away with the BackgroundService refresh design?

Freshness and a failure mode. Flags are now up to 60 seconds stale by design, and if the refresh loop dies the request path silently serves the last snapshot — safer than blocking, but invisible. So the loop catches and logs per-iteration, exposes a "last successful refresh" gauge with an alert at 5 minutes, and the snapshot swap is an atomic reference replace so readers never see a partial update. I took staleness in exchange for never putting network latency on a request thread.

2.ConfigureAwait(false) everywhere? The library/app line

StaffTechnical disagreement with a colleagueTeaches: SynchronizationContext, TaskScheduler capture, ConfigureAwaitOptions (.NET 8), CA2007 scoping

Staff — you settled the disagreement with evidence and turned it into a scoped, enforced policy. Principal — you explain why the platform never made ConfigureAwait(false) the default and what that implies for API design across the organisation.

aWorked example Example — replace with your own

A principal-level colleague opened a pull request that turned analyzer rule CA2007 ("consider calling ConfigureAwait on the awaited task") into a build error across all forty projects in the monorepo and added .ConfigureAwait(false) to roughly 3,000 awaits, including every ASP.NET Core minimal-API handler and every BackgroundService. The stated reason was defensive: "we had a deadlock once, this makes it impossible." I disagreed with the blanket, not with the goal, and the disagreement was worth having because both positions were half right.

What ConfigureAwait(false) actually configures is one thing: whether the continuation after the await is posted back to the captured SynchronizationContext.Current (or, if there is none, to a non-default TaskScheduler.Current) or is allowed to run wherever the task completed. ASP.NET Core has never installed a SynchronizationContext; in a Kestrel request SynchronizationContext.Current is null and TaskScheduler.Current is the default, so the default await and the ConfigureAwait(false) await take the exact same branch in TaskAwaiter.OnCompleted and the continuation goes to the thread pool either way. In the application projects the change was 2,400 lines of pure noise that would train reviewers to stop reading it. But our three shared NuGet packages target netstandard2.0 and are consumed by a WPF desktop client and by a legacy ASP.NET 4.8 site, both of which do have a context — DispatcherSynchronizationContext and AspNetSynchronizationContext respectively — and there a library that awaits without ConfigureAwait(false) both pays a marshal per await (in a UI-context microbenchmark the default await is roughly three times slower than the configured one) and hands the caller the classic .Result deadlock. The deadlock he remembered had been exactly that: library code, WPF caller.

We resolved it with data and scope rather than opinion. I wrote a ten-line endpoint that printed SynchronizationContext.Current?.GetType().Name ?? "null" from inside a request — it printed null on .NET 10 — and a table of every runtime we ship into and whether it installs a context. Then we scoped the rule in .editorconfig: CA2007 is an error under src/libraries/**, none under src/services/** and src/workers/**, with a comment explaining why. For the library DisposeAsync paths we used .NET 8's ConfigureAwaitOptions.SuppressThrowing so a failing flush during cleanup is observed without a try/catch wrapper. The one thing I conceded fully: the WPF client itself keeps ConfigureAwait(false) in its non-UI layers, because a view-model that touches the dispatcher after a configured await is a bug we want the analyzer to force us to think about.

// .editorconfig — the rule is a library rule, not a style preference
// [src/libraries/**.cs]
// dotnet_diagnostic.CA2007.severity = error
// [src/services/**.cs]
// dotnet_diagnostic.CA2007.severity = none

// Library code: never assume the caller's context.
public async ValueTask DisposeAsync()
{
    await _stream.FlushAsync().ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing); // .NET 8+
    await _stream.DisposeAsync().ConfigureAwait(false);
}

// Diagnostic endpoint that ended the argument (prints "null" on ASP.NET Core)
app.MapGet("/ctx", () => SynchronizationContext.Current?.GetType().Name ?? "null");

Two things I would do differently: I would have led with the table and the endpoint instead of the first-round comment thread, which cost a day of both of us being right at each other; and I would have added the .NET 11 note up front — Runtime Async changes how suspension is implemented, not the captured-context semantics, so the rule survives the next runtime and nobody needs to relitigate it.

dFollow-up drill chain

Why did the .NET team never make ConfigureAwait(false) the default?

Because the default optimises for correctness in the environments where the context matters. If the default were "don't capture", every UI developer would have to remember to marshal back before touching a control, and the failure would be a cross-thread exception or silent corruption rather than a deadlock you notice immediately. Capturing by default makes app code correct and pushes the burden onto library authors, who are fewer and better placed to carry it. The cost is the folklore: a rule that is mandatory in libraries and noise in Kestrel gets cargo-culted into both.

What exactly is captured — only the SynchronizationContext?

Two things, in order. The awaiter first checks SynchronizationContext.Current; if it is non-null and not the base type, the continuation is posted to it. Otherwise it checks TaskScheduler.Current; if that is not the default scheduler, the continuation is scheduled there. Only if both are default does the continuation run inline on the completing thread or the pool. ConfigureAwait(false) skips both checks. Separately and regardless of the flag, the ExecutionContext — AsyncLocal values — always flows across the await; people conflate the two and that is a different story (see story 10).

What does .NET 8's ConfigureAwaitOptions add, and when would you use each option?

ContinueOnCapturedContext is the old true; None is the old false. SuppressThrowing makes the await complete without rethrowing a faulted or cancelled task's exception — useful in DisposeAsync and best-effort cleanup where you want the exception marked observed but not propagated; it only applies to the non-generic Task so you cannot accidentally read a result from a faulted task. ForceYielding forces the continuation to be scheduled even if the task is already complete, which is a targeted way to break out of a deep synchronous chain or a lock without Task.Yield(). I use the last two sparingly and always with a comment.

At what scale does the "it's a no-op in ASP.NET Core" argument stop being true?

It stops being true the moment code moves. The same class copied into a Blazor Server component, a MAUI app, or a test project with a context suddenly behaves differently, and the extreme case is a shared package consumed by a host you do not control. So the scale question is really an ownership question: code that will only ever run inside your service can drop it; code that crosses a package boundary cannot. That is why the rule is scoped by directory rather than by taste.

Does .NET 11's Runtime Async change any of this?

No, and I checked rather than assumed. Runtime Async replaces the compiler-generated state machine with runtime-managed suspension — you get five real frames in a live stack trace instead of thirteen and lower overhead — but the docs and the team's guidance are explicit that captured-context semantics are unchanged. ConfigureAwait, SynchronizationContext and TaskScheduler behave identically. The one adjacent improvement is that continuations can now skip ExecutionContext capture when there is nothing to restore, which reduces per-await cost in high-throughput paths but changes no observable behaviour.

3.The ValueTask that was awaited twice

StaffNasty debugging sessionTeaches: ValueTask contract, IValueTaskSource pooling, Preserve()/AsTask(), CA2012

Altitude ladder: Senior — you found the double await and know the three ValueTask rules. Staff — you explain why pooling makes the bug non-deterministic, you built the stress repro, and you decided where ValueTask is and is not worth it. Principal — you set the API-surface policy that prevents the class of bug (story 18).

aWorked example Example — replace with your own

The bug report said "about once a day a consumer receives a message that belongs to a different subscription", which is the kind of sentence that makes you cancel your afternoon. The system was an in-process message router: producers wrote frames into per-subscription pipes and consumers read them through ValueTask<Frame> ReadAsync(CancellationToken). Three weeks earlier a colleague had optimised that hot path. Instead of allocating a Task<Frame> per read — two million reads a minute — the reader now returned a ValueTask<Frame> backed by a pooled IValueTaskSource<Frame> built on ManualResetValueTaskSourceCore<Frame>. Allocation rate dropped by a third and everyone was pleased. The optimisation was correct. The caller was not.

The contract of ValueTask is short and unforgiving: await it exactly once, never call .Result or .GetAwaiter().GetResult() before it has completed, never await it concurrently from two places, and once you have consumed it treat it as gone. Those rules exist because the struct may wrap a pooled source that is reset and reused for the next operation the moment the first consumer reads the result; a second await asks the same token-versioned source for a result that now belongs to someone else. A Task is an immutable, cached result holder, so it tolerates all of that; a pooled ValueTask is a one-shot ticket. And the bug only shows when the pool actually recycles the object under a different call, which is why it was daily rather than constant.

The caller was a timeout wrapper written before the change. It stored the ValueTask in a local, raced it against a delay with Task.WhenAny(vt.AsTask(), Task.Delay(timeout)), and then — this was the line — in the timeout branch it logged "slow read" and awaited vt a second time to "get the eventual value". Both awaits were fine when vt wrapped a Task; AsTask() on a pooled source consumes it, so the later await vt fetched whatever the recycled source held, occasionally a frame from a different subscription. I found it not by reading logs but by turning on the CA2012 analyzer ("use ValueTasks correctly"), which flagged three call sites in ninety seconds, and then by writing a stress test that ran the wrapper with a two-slot pool and a 1 ms timeout: it reproduced in under a second where production took a day.

// BUG: a ValueTask consumed twice (AsTask() consumes it; the later await re-reads a recycled source)
ValueTask<Frame> vt = reader.ReadAsync(ct);
var winner = await Task.WhenAny(vt.AsTask(), Task.Delay(timeout, ct));
if (winner is not Task<Frame>) { log.Slow(); }
return await vt;                             // second consumption — undefined with a pooled source

// FIX 1: consume once, and only via a Task if you really need multi-await/WhenAny
Task<Frame> task = reader.ReadAsync(ct).AsTask();
await Task.WhenAny(task, Task.Delay(timeout, ct));
return await task;                           // Task is safe to await any number of times

// FIX 2 (what we shipped): no WhenAny at all — let the read own the deadline
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
cts.CancelAfter(timeout);
return await reader.ReadAsync(cts.Token);    // single await, no AsTask, no extra Task allocation

// If a ValueTask genuinely must be awaited more than once: vt.Preserve() returns a safe copy backed by a Task.

What I would do differently is about sequencing, not code. The optimisation PR changed a return type on a widely used interface without an audit of the callers, and a return-type change from Task to ValueTask is a semantic change dressed as a performance change. I now treat that migration as: enable CA2012 first, fix its findings, then change the type. And I keep ValueTask to where it earns its keep — hot methods that complete synchronously most of the time or that can use a pooled source — because for a method that always suspends, a ValueTask wrapping a Task saves nothing and costs a larger struct and a foot-gun.

Why does a pooled source make the bug non-deterministic rather than always wrong?

Because the second await is only wrong if the source has been reset and reassigned in between. ManualResetValueTaskSourceCore uses a version token: if the second await presents the old token it throws, which is loud; if the pool has recycled the source and the token happens to match a new operation, you get another caller's result, which is silent. Under low load the source often sits idle between the two awaits and everything looks fine; under bursts the recycle happens in the gap. Making the pool tiny in the test collapses the gap and makes the recycle certain — that is the trick that turned a day into a second.

When is ValueTask actually worth it? Give me the decision rule you use.

Three conditions, all measured rather than assumed. The method is hot enough that a Task allocation per call shows in the allocation profile; it completes synchronously a large fraction of the time (a buffered read, a cache hit) so the zero-allocation path is the common one; and the callers are under my control or the contract is documented, because I am moving a burden onto them. If it always suspends, ValueTask over a Task saves nothing unless I also pool the source — with IValueTaskSource or the PoolingAsyncValueTaskMethodBuilder attribute — and pooling is where the sharp edges live. Public library surface defaults to Task.

What does Preserve() do and why not just always call it?

Preserve() returns a ValueTask that is safe to await multiple times; if the original is backed by a pooled source it does so by materialising a Task underneath, which is precisely the allocation you tried to avoid. So it is the correct escape hatch for the rare multi-consumer case and the wrong default, because using it everywhere silently reintroduces the cost while keeping the awkward type. If you need multi-await semantics as the norm, return a Task and be honest about it.

At what scale does the ValueTask optimisation stop mattering — or start hurting?

It stops mattering when the per-call cost is dominated by something else: a 2 ms database round trip does not care about a 72-byte Task. It starts hurting in two ways. The struct is two words plus a token, so returning it through many layers copies more than a reference; and pooling adds a synchronisation point per rent/return, which under extreme contention can cost more than the allocation it saves — the .NET team saw exactly that when they experimented with pooling by default in .NET 5 and left it opt-in. So I profile before and after at production concurrency, not in a single-threaded microbenchmark.

We were paying for work nobody would ever read.

Cancellation in .NET is cooperative: nothing stops unless it periodically looks at a CancellationToken and chooses to stop. ASP.NET Core hands you the right token for free — HttpContext.RequestAborted, and in minimal APIs and MVC any CancellationToken parameter is bound to it — but the token only helps if it flows all the way down to the thing doing the work. Ours stopped at the controller. Every handler accepted CancellationToken ct and then called _repo.GetOrdersAsync(id) without it; the repository called EF Core's ToListAsync() without it; the HTTP client calls to the pricing service used GetAsync(url) without it. Enabling analyzer CA2016 ("forward the CancellationToken parameter") counted 212 call sites in one afternoon, which was both embarrassing and the reason this was cheap to fix.

The change was mechanical at the call sites and careful at the edges. At the top I linked the request token with a hard budget so a slow client could not hold a query open for a minute: CreateLinkedTokenSource(ct) plus CancelAfter(5s), disposed with using because an undisposed linked source leaves a registration hanging off the parent token for the parent's lifetime. In the exception middleware I mapped OperationCanceledException to a 499-style response only when ct.IsCancellationRequested was true, so a genuine timeout from a dependency still logged as a failure rather than being hidden as "client went away". And I deliberately did not forward the token into the payment-capture path: once the money call has started, a cancelled request must still finish and record its result, because the alternative is a charge with no order. The token stops reads; it must not orphan writes.

app.MapGet("/orders/{id}", async (int id, OrderRepo repo, CancellationToken ct) =>
{
    // Hard budget linked to client disconnect; dispose so the registration on ct is released.
    using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
    cts.CancelAfter(TimeSpan.FromSeconds(5));

    var orders = await repo.GetOrdersAsync(id, cts.Token);   // flows to EF Core / SqlCommand
    return Results.Ok(orders);
});

// Exception mapping: distinguish "client left" from "dependency timed out"
catch (OperationCanceledException) when (ct.IsCancellationRequested) { return Results.StatusCode(499); }
catch (OperationCanceledException ex) { log.Timeout(ex); return Results.StatusCode(504); }

// CPU-bound loop that must be cancellable
foreach (var row in rows) { ct.ThrowIfCancellationRequested(); Process(row); }

// .NET 8+: cancel without blocking on callbacks; await their completion instead
await cts.CancelAsync();

Database CPU dropped from 70% to 41% over the following week with no change in traffic, which let us step down one instance tier and take roughly two thousand a month off the bill; p99 improved as a side effect because the queue of zombie queries was gone. dFollow-up drill chain

Why is cancellation cooperative rather than preemptive — wouldn't killing the thread be simpler?

Preemptive abort was tried: Thread.Abort existed in .NET Framework and was removed from .NET Core because a thread interrupted at an arbitrary instruction can leave locks held, buffers half-written and invariants broken, and no library can be made safe against it. Cooperative cancellation moves the decision to the code that knows where it is safe to stop, at the cost that code has to opt in. The consequence for design is that a token is a request, not a command: the work may finish anyway, so the caller must be prepared for both outcomes, which is exactly why Task.WaitAsync(ct) in .NET 6 exists — it lets you stop waiting without pretending the work stopped.

What does a token cost, and when would you avoid registering callbacks?

Checking IsCancellationRequested is a volatile read, effectively free. Registering a callback allocates a registration node and, on a linked source, adds a link to each parent, so a per-request linked source is cheap but a per-item linked source inside a tight loop is not, and every await on a cancellable operation typically registers and unregisters once. The mistake I watch for is registrations that are never disposed on long-lived tokens — a server-lifetime token that accumulates one registration per request is a memory leak with a slow fuse. Rule: one linked source per unit of work, always disposed.

What changed with CancellationTokenSource.CancelAsync in .NET 8, and when do you use it?

Cancel() runs registered callbacks synchronously on the calling thread and blocks until they finish, which is a problem if a callback is slow or if a callback on another thread is mid-execution and you end up waiting on it. CancelAsync() returns a task that completes when all callbacks have run, so an async shutdown path can await it instead of blocking. I use it in host shutdown and in orchestrators that cancel many children; in ordinary request code where callbacks are trivial, Cancel() is fine and the difference is unobservable.

At what scale does forwarding the token stop helping — or start hurting?

It stops helping when the expensive part is already committed: a query plan that has scanned the table before the first row is returned has spent its cost, and cancellation only saves the transfer. It starts hurting when cancellation is frequent enough that the cost of aborting — SQL attention packets, connection resets, retries triggered by the abort — exceeds the work saved, which we saw when a bug made the client cancel at 200 ms and the pool spent its time reopening connections. So the token is one lever; the bigger ones are client retry policy and idempotency keys, which is why I said I would fix the client next.

How would you convince a sceptical DBA that this was the API's fault and not the database's?

With their own view: the active-query snapshot joined to request logs by correlation id showed queries still running for request ids that had already logged a client disconnect. That makes the waste visible in the DBA's tool rather than in mine, which is what wins the argument. Then I proposed a shared metric — "queries for aborted requests per minute" — that both teams watch, so the fix is verified where the cost was felt.

What changed was a refactor two days earlier that had "made the handler async".

The handler was a broker client's Received event. Events want void delegates, so the refactor produced async void OnReceived(object? s, MessageArgs e), and that is the whole bug. An async Task method captures any exception into its Task, where it sits harmlessly until someone awaits or observes it. An async void method has no task; when it throws after its first await, the runtime has nowhere to put the exception except the SynchronizationContext that was current when the method started — and in a worker with no context, "raise it on the context" degrades to "throw it on a pool thread", which kills the process. Before the refactor the handler was synchronous and wrapped in a try/catch; after it, the try/catch still existed inside the method, but the exception came from a using block's DisposeAsync in a finally, outside it. The nightly outage of a dependency turned into a nightly outage of us.

At 03:20 I did the boring thing first: scaled the worker to zero so the retries stopped hammering a service under maintenance and the queue simply buffered, which it was designed to do. Then I set DOTNET_DbgEnableMiniDump=1 and DOTNET_DbgMiniDumpType=4 on one replica so the next crash left a dump, and dotnet-dump analyze with clrstack -all showed the async void state machine's MoveNext at the top of the dying thread. The fix in the morning was three parts. The event subscription became a thin void that hands off to an async Task HandleAsync and observes it through a single SafeFireAndForget helper that logs and never throws. The worker's main loop moved into a BackgroundService, whose ExecuteAsync failures are handled by the host — since .NET 6 the default BackgroundServiceExceptionBehavior.StopHost logs the exception and stops the host, which in an orchestrator is the same restart but with a logged reason rather than a mystery crash — and I made that behaviour explicit in configuration so nobody would be surprised by it later. And we subscribed TaskScheduler.UnobservedTaskException to log, because the audit that followed found four other places where a Task was dropped on the floor and its exception had been silently collected for months.

// FIX: events stay void; the async work is a Task that is always observed.
_client.Received += (s, e) => HandleAsync(e).SafeFireAndForget(_log, "Received");

dFollow-up drill chain

Why can't the compiler just forbid async void?

Because event handlers in the BCL and every UI framework have void delegate signatures, and the language team chose to make those handlers awaitable inside rather than force a wrapper everywhere. So async void is a deliberate accommodation with a specific semantics: exceptions go to the SynchronizationContext so a UI framework can surface them as it would any handler exception. The trap is that the same accommodation runs in hosts with no context, where it degrades to a process crash. The pragmatic answer is an analyzer that allows it only on event-handler signatures.

What happens to an exception in a Task nobody awaits — is it really silent?

It is stored in the task and marked unobserved. When the task is finalised the runtime raises TaskScheduler.UnobservedTaskException; since .NET 4.5 that no longer crashes the process by default, so unless something subscribes to the event you get nothing at all — no log, no crash, and only when a GC happens to finalise the task. That is worse than a crash in one respect: a crash gets noticed. Hence the helper that observes every fire-and-forget task explicitly, plus the event subscription as a safety net that tells you where the helper was not used.

What does BackgroundServiceExceptionBehavior change, and which do you pick?

Before .NET 6, an unhandled exception in ExecuteAsync was swallowed and the service silently stopped while the host kept running — the "worker that died in March" problem. .NET 6 made StopHost the default: the exception is logged and the host shuts down, so an orchestrator restarts it with a reason attached. Ignore restores the old behaviour. I pick StopHost for single-purpose workers because a dead loop should be visible, and I only use Ignore when one host runs several independent services and I have my own per-loop supervision with alerts.

At what scale does the "log and continue" fire-and-forget helper become the problem?

When the fire-and-forget work has no bound. A handler that spawns unobserved tasks faster than they complete has no backpressure: memory grows, the pool fills with continuations, and "log and continue" hides it until the container is OOM-killed. Above a modest rate I stop using fire-and-forget entirely and push the work into a bounded Channel<T> consumed by a BackgroundService, so the producer awaits WriteAsync and slows down when the consumer cannot keep up, and the failure of any single item is handled in one place with retry policy rather than in a catch-all logger.

How did you handle the dependency team whose 03:00 maintenance triggered this?

I did not ask them to change anything, because a dependency being unavailable for maintenance is a normal condition our worker was supposed to tolerate — the bug was ours. What I did ask for was a published maintenance window in the shared calendar and a status endpoint we could poll, so our retry policy could back off deliberately instead of hammering them for an hour. Framing it as "help us be a better client" got a yes in one message.

The gateway was twelve years old, ran on .NET Framework 4.8, and spoke a binary protocol to a few thousand field devices over raw TCP. The business case for touching it was end-of-support risk and the fact that nobody left on the team could safely change it. My job was to get it onto .NET 10 (the current LTS) without changing the wire protocol or the operational behaviour.

The Task-based Asynchronous Pattern (TAP) has a wrapper for each legacy shape, and knowing which is which is the whole skill. APM pairs map mechanically through Task.Factory.FromAsync(BeginX, EndX, …), which adapts the callback into a Task without a thread; I did that first, behind an IDeviceChannel interface, so the callers could switch to await while the socket code stayed put. EAP events need a TaskCompletionSource<T>: subscribe, start, and complete the source from the event with SetResult/SetException/SetCanceled — but in .NET Core-era code that whole WebClient dance simply became HttpClient.GetStringAsync(url, ct), so I deleted rather than wrapped. The StartNew(async …) calls were the subtle ones: StartNew does not understand async delegates, so it returns a Task<Task> whose outer task completes as soon as the inner method hits its first await; every caller that awaited it believed the dispatch had finished when it had barely started, which explained a "lost message on shutdown" bug that had been open for six years. Task.Run unwraps automatically, so that was the replacement, with TaskCreationOptions.LongRunning reserved for the one genuinely long-lived listener loop that should not consume a pool thread.

Then, once on .NET 10, I replaced the FromAsync layer with the modern socket API — Socket.ReceiveAsync(Memory<byte>, SocketFlags, CancellationToken) returns a ValueTask<int> and completes on the I/O completion machinery without a callback object per read — and dropped the thread-per-connection handshake for a bounded Parallel.ForEachAsync. Memory per connection fell from about 1.3 MB (a dedicated thread's stack plus buffers) to under 20 KB, and the gateway that used to top out around 3,000 connections held 40,000 in a soak test.

What broke was instructive. The TaskCompletionSource I used for the EAP-style device-acknowledgement flow completed inline: SetResult ran the awaiting continuation synchronously on the I/O thread that called it, and a heavy continuation stalled every other socket serviced by that thread — we saw p99 spikes on unrelated devices. The fix is one flag, TaskCreationOptions.RunContinuationsAsynchronously, which forces continuations onto the pool, and I now consider it the default for any source that is completed from a thread you do not own.

Task<int> ReceiveAsync(byte[] buf) =>
    Task.Factory.FromAsync(
        (cb, state) => _socket.BeginReceive(buf, 0, buf.Length, SocketFlags.None, cb, state),
        _socket.EndReceive, state: null);

// EAP → TAP: TaskCompletionSource, completed from the event — off-thread continuations on purpose
Task<Ack> WaitForAckAsync(int id, CancellationToken ct)
{
    var tcs = new TaskCompletionSource<Ack>(TaskCreationOptions.RunContinuationsAsynchronously);
    _pending[id] = tcs;
    ct.Register(() => tcs.TrySetCanceled(ct));     // registration disposed when the entry is removed
    return tcs.Task;
}

dFollow-up drill chain

Why is Task.Run almost always preferred over Task.Factory.StartNew today?

Task.Run is StartNew with the right defaults baked in: the default scheduler rather than TaskScheduler.Current, DenyChildAttach so parent-child task nesting cannot surprise you, and automatic unwrapping of Task<Task> for async delegates. StartNew still has two legitimate uses — passing TaskCreationOptions.LongRunning to get a dedicated thread for a loop that would otherwise pin a pool thread, and targeting a specific scheduler — and analyzer CA2008 exists precisely to make you pass a scheduler when you use it. Everything else is a footgun in a legacy-shaped API.

What does RunContinuationsAsynchronously trade away?

Latency and one scheduling hop. With inline continuations, SetResult runs the awaiter immediately on the completing thread, which is the fastest possible hand-off; with the flag, the continuation is queued to the pool and runs a little later on another thread. The trade is worth it whenever the completing thread is shared and precious — an I/O completion thread, a lock holder, a UI thread — because a slow continuation there stalls everyone. It is not worth it in a tight producer-consumer pair where inline execution is the point. Note that await's own continuations are already scheduled that way when the awaiter's context demands it; the flag is about TaskCompletionSource and ContinueWith.

At what scale does the thread-per-connection model actually break, and how did you know async would fix it?

A dedicated thread costs stack reservation (1 MB on Windows, commonly 8 MB on Linux, committed lazily), a kernel object and scheduler overhead, so a few thousand mostly idle connections are already wasteful and tens of thousands hit memory and context-switch limits well before CPU. Async I/O parks the connection in the OS (I/O completion ports, epoll) with no thread until data arrives, so the cost per idle connection is buffers, not threads. I knew rather than hoped because the soak test measured resident memory and p99 at 3k, 10k and 40k connections on both builds; the old one degraded past 3k and failed at 6k.

Why keep FromAsync as an intermediate step instead of going straight to the modern socket API?

Risk isolation. FromAsync changes the calling convention without changing the I/O implementation, so if behaviour changed I knew it was the callers; then swapping the I/O layer underneath a stable async interface isolated the second change. Two small, separately verifiable moves beat one large one with two suspects. The cost was a temporary allocation per read for the APM callback object and a few weeks of an extra layer — cheap against the cost of debugging a combined change in a protocol nobody fully understood.

The first step alone — replacing StartNew and closing the lost-message bug — took two weeks and bought the credibility for the rest.

aWorked example Example — replace with your own

The export endpoint was killing pods. A customer with four million transaction rows asked for a full extract; the handler did what handlers do — await query.ToListAsync(), serialise, return — and a List<TransactionRow> of 1.8 GB does not fit in a 2 GB container. Even smaller exports hurt: every list over 85 KB lands on the large object heap, the resulting Gen2 collections paused everything else on the node for hundreds of milliseconds, and time-to-first-byte was 40 seconds because nothing left the process until everything had arrived. Scaling the container to 8 GB would have moved the cliff, not removed it.

IAsyncEnumerable<T> (C# 8, .NET Core 3.0) is the right shape for this because it is pull-based: the consumer asks for the next item with MoveNextAsync, the producer suspends when there is no item, and only one element needs to be alive at a time. EF Core's AsAsyncEnumerable() keeps a data reader open and yields rows as they arrive; ASP.NET Core will serialise an IAsyncEnumerable<T> result as a JSON array incrementally, flushing as it goes; and on the client side JsonSerializer.DeserializeAsyncEnumerable<T> reads the array element by element without buffering the document. The rewrite was three methods and the results were not subtle: peak memory for the four-million-row export went from 1.8 GB to a flat 60 MB, time-to-first-byte from 40 seconds to about 200 milliseconds, and the Gen2 pauses disappeared from the node.

What broke was the lifetime, twice. First, cancellation: an async IAsyncEnumerable method receives the consumer's token only if a parameter is decorated with [EnumeratorCancellation] and the consumer passes it through WithCancellation(ct) — without the attribute, a client that disconnects halfway leaves the data reader streaming into a closed response until the query finishes, which for four million rows was several minutes of a pinned connection. Second, the connection itself: streaming holds a database connection for the duration of the response, so a slow client (a mobile network reading at 200 KB/s) held a pooled connection for twenty minutes and under a few concurrent exports the pool ran dry for everyone else. I bounded that by paging inside the enumerable — a keyset-paginated query per 10,000 rows, each with its own short connection — so the stream is continuous to the client but the database sees short queries.

// Producer: pull-based, one page per short connection, cancellation flows in from the consumer
public async IAsyncEnumerable<TransactionRow> ExportAsync(
    int customerId, [EnumeratorCancellation] CancellationToken ct = default)
{
    long lastId = 0;
    while (true)
    {
        await using var db = await _factory.CreateDbContextAsync(ct);          // short-lived connection per page
        var page = await db.Transactions.AsNoTracking()
            .Where(t => t.CustomerId == customerId && t.Id > lastId)
            .OrderBy(t => t.Id).Take(10_000).ToListAsync(ct);                  // 10k rows ≈ 4 MB, gone after the page
        if (page.Count == 0) yield break;
        foreach (var row in page) { yield return row; lastId = row.Id; }
    }
}

dFollow-up drill chain

Why IAsyncEnumerable rather than IEnumerable<Task<T>> or Task<IEnumerable<T>>?

Task<IEnumerable<T>> is a single asynchronous wait followed by synchronous iteration — it forces the producer to have everything before the consumer sees anything, which is the buffering problem in a different coat. IEnumerable<Task<T>> makes each element an independent asynchronous operation, which is a fan-out shape, not a stream: elements are not produced in sequence and there is no shared reader to keep open. IAsyncEnumerable<T> is the only one of the three where both the "is there another item" question and the item itself are asynchronous, in order, with one live element — which is exactly what a database cursor or a network stream is.

What is the difference between this and a Channel<T>, and when do you pick each?

IAsyncEnumerable is pull-based and single-consumer: the producer runs only when the consumer asks, so backpressure is implicit and there is no buffer to size. A Channel<T> is a buffered hand-off between independently running producers and consumers, possibly many of each, with explicit bounded capacity and a FullMode policy. I reach for a channel when producer and consumer must be decoupled in time or count — an ingest loop feeding several workers, or a producer that cannot pause — and for a plain sequential transformation of a source I stay with the enumerable. A channel's reader exposes ReadAllAsync() as an IAsyncEnumerable, so the two compose.

At what scale does streaming over HTTP break?

At the infrastructure's idea of a request lifetime. Load balancers and gateways have idle and total timeouts — often 60 to 300 seconds — and a slow client reading a large stream will trip them; proxies may buffer the whole response anyway, defeating the point; and each in-flight stream pins server resources (a connection, a reader) for its duration, so concurrency is bounded by the slowest client. Past a few minutes of transfer I switch to an asynchronous job: produce to object storage with the same streaming code, then hand out a URL. The streaming primitive stays; the transport changes.

What did you trade away with the paging-per-connection design?

Snapshot consistency and a little latency. Ten thousand-row pages on separate connections mean rows inserted or updated during the export may or may not appear, depending on where the cursor was; a single long-running read under a snapshot isolation level would have seen a consistent point in time. For an export that customers treat as "everything up to roughly now", that was acceptable, and I documented it. The latency cost is a connection open per page and a round trip between pages, around 2–3 ms each, invisible against the transfer time. If consistency had mattered, I would have used a snapshot and a dedicated connection pool sized for exports.

Why does ConfigureAwait(false) on await foreach exist, and does it apply to each iteration?

Because every MoveNextAsync is an await, and so is DisposeAsync at the end, and each one would capture the context like any other await. ConfigureAwait(false) on the enumerable configures all of them, and it matters in exactly the same places it matters for a single await — library code and UI contexts — and is a no-op in ASP.NET Core. The one subtlety is ordering: WithCancellation and ConfigureAwait both return configured wrappers and can be chained in either order.

8.Teaching the deadlock: a junior's .Result on the UI thread

SeniorMentoring / levelling someone upTeaches: SynchronizationContext deadlock, why ConfigureAwait(false) is a fragile fix, legitimate async void, VSTHRD002

Altitude ladder: Senior — you explained the mechanism so it stuck and let them fix it. aWorked example Example — replace with your own

A junior on the team — three months in, sharp, fast — pushed a change to the desktop client that froze the window when you clicked "Refresh". It worked on her machine, which is the sentence that started the conversation. The handler was private void Refresh_Click(object s, RoutedEventArgs e) { var data = _api.LoadAsync().Result; Bind(data); }. On her machine the API returned from a local cache synchronously, so LoadAsync never actually suspended and .Result was instant; against the real service it suspended, and the app hung forever. My goal was not to fix the line. It was that she would never write it again and would be able to explain to the next person why.

I drew it as two parties who each need the other to go first. The UI thread calls .Result, which blocks that thread until the task completes. Inside LoadAsync, the await httpClient.GetAsync(…) captured SynchronizationContext.Current — the WPF DispatcherSynchronizationContext — and when the HTTP call finishes, the continuation (the rest of LoadAsync, including the line that would complete the task) is posted to the UI thread. The UI thread is blocked in .Result waiting for that very task. Nothing can proceed. Then I asked her why it worked locally, and she got there herself: no suspension, no continuation, no post, no deadlock. That question — "why did it work on your machine" — is the one that makes the model stick, because it shows the bug is in timing, not in syntax.

Then we looked at three "fixes" and ranked them. Adding .ConfigureAwait(false) inside LoadAsync makes this call work because the continuation no longer needs the UI thread, and it is the right thing for library code anyway — but it is fragile as a deadlock fix because it depends on every await in the call chain being configured, including in third-party code, and the moment one is not, the hang is back. Wrapping in Task.Run(() => _api.LoadAsync()).Result also works, by moving the await onto a pool thread with no context, and is an honest escape hatch when you are trapped in a sync signature you do not own; it still blocks the UI thread, so the window is unresponsive for the duration. The real fix is to make the handler async void — the one signature where async void is correct, because event handlers must return void — and await the call, with a try/catch around the body because an exception from an async void handler goes to the dispatcher's unhandled-exception path rather than to the caller. She wrote that version; I did not.

// The deadlock: UI thread blocks on .Result; LoadAsync's continuation needs the UI thread.
private void Refresh_Click(object s, RoutedEventArgs e)
{
    var data = _api.LoadAsync().Result;     // blocks the dispatcher thread
    Bind(data);
}

// The fix she wrote: async void is correct for event handlers, and only there.
private async void Refresh_Click(object s, RoutedEventArgs e)
{
    try
    {
        RefreshButton.IsEnabled = false;
        var data = await _api.LoadAsync();  // continuation returns to the UI thread; that's what we want here
        Bind(data);
    }
    catch (Exception ex) { ShowError(ex); }
    finally { RefreshButton.IsEnabled = true; }
}

// Library side (netstandard2.0 shared package): never assume the caller's context
public async Task<Data> LoadAsync(CancellationToken ct = default)
{
    using var resp = await _http.GetAsync("/data", ct).ConfigureAwait(false);
    return await resp.Content.ReadFromJsonAsync<Data>(ct).ConfigureAwait(false);
}

Why isn't ConfigureAwait(false) a sufficient fix for the deadlock?

Because it only prevents the capture at the awaits you control. The deadlock needs just one continuation in the whole chain to require the blocked context — an await in a third-party library, a Task.Yield somewhere, an await added next month by someone who did not know the rule — and the hang returns with no compile-time warning. It is the correct default for library code for performance and independence reasons, but "we are safe to block because everything below is configured" is a claim no one can verify. The fix is to not block: make the caller async or, if trapped in a sync signature you do not own, hop to a pool thread with Task.Run and accept the blocked UI.

What if the sync signature is imposed on you — an interface, a framework callback, a constructor?

Then I choose the least bad of three. If the operation can be made lazy, I start it and await it later where I am async — a Lazy<Task<T>> or an async factory instead of a constructor. If I must block, Task.Run(() => Op()).GetAwaiter().GetResult() avoids the context deadlock at the cost of a blocked thread and a pool hop, and I isolate it and comment it. If this is in a UI app with many such calls, a joinable-task pattern — the kind Visual Studio's threading library implements — lets the blocked UI thread run the continuations itself while it waits, which is the only way to block on the UI thread without deadlock. None of them is good; the honest answer is that the interface should change.

When the work is not uniform or the stages have different limits. It also runs the source enumeration lazily but starts items eagerly up to the degree, so with a very slow producer you get idle workers; and above a few million items the per-item async state machine allocation becomes the profile, at which point batching — a hundred SKUs per task — matters more than the primitive.

Atomicity. The old behaviour — abort on first failure — at least guaranteed the catalogue was either fully priced or untouched (in practice it was neither, because half the writes had already happened, but the intent was there). A partial result with visible gaps beat an all-or-nothing that was really a nothing-or-half.

dFollow-up drill chain

Explain precisely what await does with the ExecutionContext, and how that differs from ConfigureAwait.

When an async method suspends, the builder captures the current ExecutionContext — the container for all AsyncLocal values — and stores it with the state machine; when the continuation runs, the runtime restores that context around MoveNext, so AsyncLocal reads see the same values regardless of thread. That capture is unconditional; ConfigureAwait(false) affects only the SynchronizationContext/TaskScheduler decision, never the ExecutionContext. Setting an AsyncLocal triggers a copy-on-write of the context, which is why writes are more expensive than reads and why a child's write does not affect the parent. In .NET 11 the runtime skips the capture/restore entirely when there is nothing to restore, which is a performance change with no semantic change.

Why not make the tenant id an explicit parameter everywhere and abolish ambient context?

That is where we ended up for new code, and it is the right default for a security boundary because it is checkable by the compiler. The cost is plumbing: threading a parameter through every layer, including third-party callbacks and logging, and the reality that some cross-cutting concerns — correlation ids, logging scopes, IHttpContextAccessor — are ambient by nature. The compromise that held was explicit for anything that scopes data access, ambient only for observability, and an AsyncLocal guard that throws if the explicit and ambient values disagree, which turns a silent leak into a loud exception.

At what scale does AsyncLocal itself become a performance problem?

When it is written often. Each write copies the context, and each await of a method that has a non-default context captures and restores it; with a handful of values set once per request this is nanoseconds and invisible. With a logging library that pushes and pops a scope around every operation, or a value mutated in a loop, it shows up as allocation and time in ExecutionContext.RunInternal in profiles. The mitigations are to set once at the boundary, to keep a single mutable holder object in the AsyncLocal rather than replacing the value, and — since .NET 11 — to benefit from continuations skipping capture when no AsyncLocal state is in use, which is another reason not to sprinkle them.

Exposure is irreversible and availability is not, so I took the availability hit, said so to product in the same message as the security lead, and gave a review checkpoint at thirty minutes. The decision was easy once framed as reversible versus irreversible; the discipline is making that framing explicit under pressure.

What would you say to a team that wants to add a new AsyncLocal-based context today?

If they can answer all three in the design doc, fine; the pattern is not banned, it is just no longer allowed to be implicit.

This is the oldest race there is — check-then-act — and async makes it easier to write, because the gap between the check and the act is now a suspension point rather than a couple of instructions, and the compiler will not let you close it with lock: an await inside a lock statement is a compile error (CS1996), and rightly so, because a Monitor is owned by a thread and the continuation may resume on a different one. The C# 13 System.Threading.Lock type has the same restriction. So the tools are different. Lazy<Task<T>> — the pattern usually called AsyncLazy — makes the start of the operation happen exactly once, with the Lazy doing the thread-safe publication and every caller awaiting the same Task; that was the right fit here because the initialisation is a one-shot. SemaphoreSlim(1,1) with WaitAsync is the general async mutex when you need to serialise repeated critical sections; and ConcurrentDictionary.GetOrAdd with a Lazy<Task> value is the per-key version of the same idea for caches.

The incident response came before the fix. I stopped the bleeding by scaling the deployment so no new cold pods would start, then wrote the reconciliation query — orders with the same idempotency key created within 5 seconds of each other — which found the seventeen, and the refunds went out with a personal apology before the customers noticed. The fix was the AsyncLazy, with one refinement people forget: a Lazy<Task> caches a faulted task forever, so if the first load fails on a transient database blip, every subsequent request fails until the pod restarts. I used a small wrapper that resets on failure so the next caller retries. And the real fix was not in memory at all: a unique index on the idempotency key in the orders table, so a duplicate insert is rejected by the database regardless of what the cache believes. The cache is an optimisation; the constraint is the guarantee.

private Lazy<Task<KeySet>> _keys = new(() => LoadKeysAsync(), LazyThreadSafetyMode.ExecutionAndPublication);
private async Task<KeySet> GetKeysAsync()
{
    var lazy = _keys;
    try { return await lazy.Value; }
    catch { Interlocked.CompareExchange(ref _keys, new(() => LoadKeysAsync(), LazyThreadSafetyMode.ExecutionAndPublication), lazy); throw; }
}

try { if (_keys is null) _keys = await LoadKeysAsync(ct); }
finally { _gate.Release(); }

dFollow-up drill chain

Why can't you await inside a lock, and what would go wrong if the compiler allowed it?

lock compiles to Monitor.Enter/Exit, and a monitor is owned by the thread that entered it. After an await the continuation can resume on a different pool thread, which would then try to Exit a monitor it does not own — an exception at best — while the original thread walks away still holding it, blocking everyone else forever. Even if ownership were transferable, holding a thread-affine lock across a suspension would block a thread for the duration of an I/O wait, which is exactly what async exists to avoid. So the compiler refuses, and the async-safe alternatives — SemaphoreSlim, AsyncLazy, channels — are all owner-less by design.

What memory-model guarantee were you relying on when other callers read the Lazy's task?

Lazy<T> in ExecutionAndPublication mode publishes the value under a lock, which gives a release/acquire pair, so any thread that observes the created value also observes the fully constructed Task object. And a Task's completion is itself a synchronisation point: everything the initialiser wrote before completing the task is visible to any continuation that runs after awaiting it. That second guarantee is why "await the same task from many callers" is safe without any further synchronisation on the loaded data — provided the data is not mutated after publication, which I enforced by making KeySet immutable.

At what scale does the single-process AsyncLazy stop being enough?

The moment there is more than one process. Twenty pods each warm their own cache once, which is fine, but twenty pods each believing they own "exactly once" is the same race at a larger scale — pod A and pod B both miss in their local cache and both insert. That is why the database constraint is the actual guarantee and the in-memory check is a latency optimisation. If the constraint cannot live in the database — say the write goes to a third-party API — the equivalent is an idempotency key the third party honours, or a distributed lock with a lease, and both of those have their own failure modes I would rather not take on for a problem a unique index solves.

Why not just make the warm-up eager at startup and avoid the lazy path entirely?

We did both in the end, and the reason to keep the lazy path is honesty about startup. An eager load in a hosted service delays readiness by two seconds, which is fine, but if the database is slow on a cold start the pod is not ready for twenty seconds, and an orchestrator that restarts slow pods can turn that into a loop. So the eager load happens in StartAsync with a timeout, readiness reports "warming" rather than "unready", and the lazy path is the fallback if the eager load did not complete — with the constraint underneath as the guarantee either way. The trade-off is a little complexity against a startup failure mode we had actually seen.

Why is Task.Run in a request handler usually wrong on a server, and when is it right?

Because the handler is already on a pool thread that Kestrel dispatched, so offloading to the pool is offloading from the pool to the pool: an extra queue hop and context switch for nothing, and for I/O-bound work the thread is released at the first await anyway. It is right when the work is genuinely CPU-bound for long enough to hurt — tens of milliseconds and up — and you want to keep the request thread's continuation cheap, or in a UI app where you must leave the UI thread. Even then it is a scheduling choice, not a throughput one: the same cores do the same work, so it must be bounded or it starves the very request threads it was trying to protect.

What does SetMinThreads actually control, and what is the default?

The default minimum is the processor count (for worker threads; the I/O completion minimum is the same on modern .NET). Below the minimum the pool creates threads on demand without delay; above it, new threads are injected by the hill-climbing algorithm, which adds roughly a thread or two per second while it measures whether throughput improves, plus the .NET 6+ fast path that injects faster when it sees threads blocked in Task.Wait-style calls. Raising the minimum therefore only changes how quickly you can absorb blocking; it does not make blocked threads productive. It is a legitimate emergency lever with an expiry date, and a wrong permanent setting because every blocked thread still costs memory and scheduling.

The channel made the trade-off explicit and measurable; it did not make the network share faster.

The mechanism matters for the decision. Since C# 5 the compiler has rewritten every async method into a state machine: a struct with a MoveNext and an AsyncTaskMethodBuilder, which on the first real suspension gets boxed into an AsyncStateMachineBox on the heap along with the captured ExecutionContext; every await that suspends goes through the builder's AwaitUnsafeOnCompleted, and a live stack trace shows the builder and MoveNext frames for every level of the chain. Runtime Async moves the concept into the runtime: the compiler emits plain IL annotated with [MethodImpl(MethodImplOptions.Async)] and calls into AsyncHelpers.Await; the JIT understands suspension and resumption natively, generates continuation objects only when a method actually suspends, and can optimise across the await — tiered compilation now applies to async methods, common factories like Task.FromResult and ValueTask.CompletedTask are intrinsics, and continuations skip ExecutionContext capture when there is nothing to restore. Your source does not change; Task, ValueTask, ConfigureAwait, cancellation and custom awaiters all keep their semantics.

The evaluation harness was one service with about 2,000 async methods, built twice from the same commit — once with <Features>runtime-async=on</Features> in the csproj, once without — and run through the same load profile on the same hardware. Why did the .NET team move async into the runtime instead of continuing to optimise the compiler's state machines?

Because the compiler model hit a ceiling: the runtime saw async methods as ordinary methods with an opaque struct, so it could not optimise across an await, could not avoid the box-plus-builder shape, and could not give diagnostics tools a truthful stack. They had first tried the other big idea — green threads, a runtime-managed stack-switching model — in a 2023 experiment and rejected it because it would have fractured the ecosystem's Task-based APIs and interop. Runtime Async keeps every existing API and source line and changes only the implementation, which is the least disruptive way to get JIT-level optimisation, real stack traces and lower overhead. That history is why I trust the semantics to stay stable even while the performance moves.

Nine days before a regulatory deadline, we discovered that the vendor SDK for the mandatory e-signature step was synchronous all the way down: SignDocument(bytes) made a network call of roughly 300 milliseconds and there was no async overload, no callback, nothing to await. The vendor's async API was six weeks out. The feature had to ship; the call would run on every submission, up to 40 per second at peak; and a 300 ms blocking call at that rate would pin twelve pool threads continuously — fine on a quiet day, a starvation cascade the first time something else slowed down. The product owner heard "known thread-pool risk" and wanted to know whether we could just ship anyway. The right answer was yes, with conditions, and the conditions were the whole negotiation.

There are four ways to run known-blocking work in an async service and they are not equivalent. Wrapping it in Task.Run just moves the block onto a different pool thread — it looks async to the caller and changes nothing about starvation. Raising SetMinThreads lets the pool absorb the blocking faster but caps nothing and hides the problem. Task.Factory.StartNew with TaskCreationOptions.LongRunning gives a dedicated thread per call, which protects the pool but at 40 calls per second means creating and destroying a thread every 25 milliseconds. The option that actually contains the risk is a small pool of dedicated threads that the blocking call cannot escape: a bounded Channel<SignRequest> feeding eight new Thread(…) workers, each looping on a blocking Read and completing a TaskCompletionSource — with RunContinuationsAsynchronously, so the awaiting request resumes on the pool, not on the signing thread. Callers await the completion source, the pool stays untouched, and the maximum damage is bounded by design: eight in flight, the rest queued, and a queue depth we can alert on.

Then the negotiation. I wrote a one-page risk note: what the risk is, what bounds it, what we monitor (channel depth, signing latency, pool thread count), what the alert thresholds are, what the fallback is if the vendor is slow (a 5-second timeout via Task.WaitAsync that abandons the wait and returns "signing pending" to the user while the worker finishes or fails on its own), and a dated ticket to remove the whole thing when the vendor's async API arrived. The product owner accepted the risk in writing, which changed the conversation from "the engineers are worried" to "the business has chosen this trade-off and knows its shape". We shipped on day eight. The channel depth alert fired once, during the vendor's own incident three weeks later — the queue backed up to 400, users saw "signing pending", and nothing else in the service was affected, which was the point. The async SDK arrived in week seven; the removal PR was 190 lines of deletion.

// Contain the blocking call on threads the pool does not own; callers still await.
public sealed class SigningGate : IAsyncDisposable
{
    private readonly Channel<(byte[] Doc, TaskCompletionSource<byte[]> Tcs)> _queue =
        Channel.CreateBounded<(byte[], TaskCompletionSource<byte[]>)>(new BoundedChannelOptions(500) { FullMode = BoundedChannelFullMode.Wait });
    private readonly Thread[] _workers;

    public SigningGate(ISigner signer, int workers = 8)
    {
        _workers = Enumerable.Range(0, workers).Select(i => new Thread(() => Loop(signer)) { IsBackground = true, Name = $"sign-{i}" }).ToArray();
        foreach (var t in _workers) t.Start();
    }

    private void Loop(ISigner signer)
    {
        while (_queue.Reader.WaitToReadAsync().AsTask().GetAwaiter().GetResult())   // blocking here is fine: dedicated thread
            while (_queue.Reader.TryRead(out var item))
            {
                try { item.Tcs.SetResult(signer.SignDocument(item.Doc)); }          // the 300 ms blocking call
                catch (Exception ex) { item.Tcs.SetException(ex); }
            }
    }

    public async Task<byte[]> SignAsync(byte[] doc, CancellationToken ct)
    {
        var tcs = new TaskCompletionSource<byte[]>(TaskCreationOptions.RunContinuationsAsynchronously); // resume on the pool
        await _queue.Writer.WriteAsync((doc, tcs), ct);                              // backpressure when 500 are queued
        return await tcs.Task.WaitAsync(TimeSpan.FromSeconds(5), ct);               // .NET 6: stop waiting; work continues or fails alone
    }

    public ValueTask DisposeAsync() { _queue.Writer.Complete(); return ValueTask.CompletedTask; }
}

dFollow-up drill chain

Why dedicated threads rather than Task.Run with a SemaphoreSlim(8)? Both bound it to eight.

The semaphore bounds how many callers proceed, but each one that proceeds still blocks a pool thread for 300 ms, so under sustained load eight pool threads are permanently unavailable and, if anything else in the process also blocks, the pool's injection logic is now reasoning about our blocks plus theirs. Dedicated threads take the blocking out of the pool's accounting entirely: eight threads that belong to the signing gate, whose blocking is expected and invisible to hill climbing. The cost is eight mostly idle threads, which is nothing. The principle is that the pool should only ever see work that yields.

What does Task.WaitAsync actually do to the underlying work when the timeout fires?

Nothing — and that is the point to be honest about. WaitAsync (.NET 6) returns a new task that completes when either the original completes or the timeout/cancellation fires; on timeout it throws TimeoutException and the original task keeps running to whatever end it reaches. So the request stops waiting, the user sees "pending", and the signing thread still finishes the call and completes the TaskCompletionSource, whose result nobody reads. It is the correct tool when the underlying operation cannot be cancelled; the design must then account for the abandoned work — here, a worker slot occupied until the vendor responds, bounded by the vendor's own timeout.

At what scale would the eight-thread gate have broken?

Eight workers at 300 ms each sustain roughly 26 signings per second; our peak was 40, so the queue absorbs bursts but under a sustained peak it grows at about 14 per second and hits the 500 bound in half a minute, after which callers await the writer and request latency rises. We knew that and sized the alert at a queue depth of 100. Beyond that the options are more workers — sixteen would clear 50/s — which is cheap, or shedding load with a "try later" response, which is a product decision. The gate did not make the vendor faster; it made the failure mode a queue we could see instead of a starvation we could not.

How did you keep the product owner from hearing "the engineers are being difficult"?

By making the ask small and the choice theirs. I did not ask for more time; I asked for a signature on a one-page note that said what could happen and what we would see if it did. What is your general rule for shipping known-bad code?

// Production: inject the clock; every delay, timer and timeout flows through it
public sealed class RetryPolicy(TimeProvider clock)
{
    public async Task<T> RunAsync<T>(Func<CancellationToken, Task<T>> op, CancellationToken ct)
    {
        for (var attempt = 0; ; attempt++)
        {
            try { return await op(ct); }
            catch (TransientException) when (attempt < 3)
            {
                await Task.Delay(TimeSpan.FromSeconds(Math.Pow(2, attempt)), clock, ct);   // .NET 8 overload

        }
    }
}

Advance fires the timers due up to the new instant on the calling thread, which completes the corresponding delay tasks; the continuations of code awaiting those delays are then scheduled — on the pool, since there is no context in a test unless the runner installs one. The goal was fairness. A multi-tenant API had a recurring problem where one tenant's batch import — thousands of requests in a minute — degraded latency for everyone else, and the proposal I sponsored was elegant on the whiteboard: a custom TaskScheduler per tenant implementing weighted fair queuing, so a noisy tenant's continuations would be scheduled behind everyone else's, plus a custom SynchronizationContext installed per request so that await would keep each request's continuations on its tenant's scheduler. Six weeks and two engineers later I cancelled it, and the reason is a precise fact about how await chooses where to run.

An await continuation goes to the captured SynchronizationContext if there is one, otherwise to TaskScheduler.Current if it is not the default, otherwise inline or to the pool. We had covered the first case by installing our context, but every path that bypasses the context bypassed our fairness: any ConfigureAwait(false) in our own code or in any library, every Task.Run (which targets the default scheduler by design), every TaskCreationOptions.HideScheduler, every Timer callback, and — the killer — every I/O completion, because the socket layer completes on the pool and the continuation only comes back to our context via a post that is itself an extra hop. Instrumenting it showed about 40% of a request's CPU time actually ran on the tenant scheduler; the rest ran wherever the platform put it, so the fairness was 40% real, and the 60% included the expensive parts. Worse, the double hop — completion on the pool, post to our context, dequeue by our scheduler — added roughly 30 µs per await and blew the p50 up by 15%. We had built a slower system that was partly fair.

The decision meeting was short because I brought the number rather than the argument. I said the design was mine, the 40% figure was the evidence, and the fix was not more engineering on the scheduler but a different place to solve the problem: admission control at the entry, not scheduling in the middle. We replaced it in nine days with a PartitionedRateLimiter (System.Threading.RateLimiting, .NET 7) keyed by tenant in the middleware — each tenant gets a concurrency limit and a queue, and a noisy tenant's excess requests wait or get a 429 before they consume any pool time — plus a bounded Channel<T> per tenant for the import path so its work is throttled as it enters. The noisy-neighbour p99 impact on other tenants dropped from 800 ms to under 40 ms, and the p50 went down because we had removed the double hop. The custom scheduler code was deleted except for its test harness, which became the load test for the limiter.

Fairness, priority and isolation belong at the boundary, where work is admitted, not in the middle, where it is already running.

When is a custom TaskScheduler the right tool?

When you control every task that runs on it and none of them await across a boundary you do not own. The legitimate cases are narrow: ConcurrentExclusiveSchedulerPair to get reader/writer-style exclusivity for CPU-bound work you start with Task.Factory.StartNew; a limited-concurrency scheduler for a pool of synchronous jobs; a scheduler that pins work to a single thread for a COM or legacy component that requires thread affinity. In each of those the work is explicitly started on the scheduler and does not rely on await capture to stay there. The moment the design says "and awaits will keep it on our scheduler", it is the design I cancelled.

Why does Task.Run ignore TaskScheduler.Current?

Deliberately, as a correction to Task.Factory.StartNew, which uses TaskScheduler.Current by default and caused a generation of bugs where work started inside a task on a special scheduler silently inherited it — code that meant "run this on the pool" ran on a UI scheduler or a limited one. Task.Run always targets TaskScheduler.Default so its meaning is stable regardless of where it is called from. Analyzer CA2008 exists for the StartNew case for the same reason. It is a good rule for the platform and a fatal one for a design that wanted inheritance.

At what scale does the rate-limiter replacement itself break?

Per instance it is cheap — a partition per tenant with a semaphore and a queue — so tens of thousands of tenants are fine, and idle partitions are reclaimed. The real limits are semantic: it is per process, so with twenty replicas a tenant gets twenty times the limit unless the load balancer is tenant-aware or the limit is coordinated through a shared store, which adds latency and a dependency; and a concurrency limit protects the pool but not a downstream shared resource like the database, which needs its own budget. We accepted per-instance limits with sticky routing for the import path and put a separate limiter in front of the database client. Fairness at one layer is not fairness everywhere.

How did you avoid this becoming a story about wasted money?

I put those in the cancellation note next to the cost. What principle did you write down, and has it been challenged since?

The principle held; I expect it to hold until the platform itself offers something different.

The requirement arrived as one sentence in a ticket: "the checkout API must never hang." Everyone agreed with it and nobody could say what it meant. Hang for whom — the user, the load balancer, the retrying client? For how long is "not hanging" — 2 seconds, 30? And what happens to the payment that is half-way through when we decide it has hung? My first job was not code; it was to turn a feeling into numbers people could sign off, because an unspecified timeout is a bug you have not chosen yet.

I proposed a deadline budget and walked the product owner through it. The user-facing SLO was 2 seconds end to end. That budget is propagated, not repeated: middleware creates a CancellationTokenSource linked to HttpContext.RequestAborted with CancelAfter(2s), and the token flows down. Each dependency gets a slice — inventory 400 ms, pricing 300 ms, payment 1,200 ms — expressed as its own linked source with a shorter CancelAfter, so a slow inventory call cannot eat the payment's time. HttpClient.Timeout was set to infinite on the typed clients because its built-in timeout is a per-request wall clock that knows nothing about the remaining budget, and on .NET 5+ it surfaces as a TaskCanceledException with an inner TimeoutException, which is easy to misread as user cancellation; the per-request token is the only timeout. The resilience layer used the .NET 8 Microsoft.Extensions.Http.Resilience standard pipeline — total timeout, retry, circuit breaker, per-attempt timeout — tuned so its total never exceeded the slice, and for the read-only inventory call I enabled hedging, which fires a second request after 150 ms and takes whichever answers first.

Then the requirement shifted, twice. First "and retry the payment if it times out", which I refused as stated: a payment call that timed out may have succeeded on the provider's side, and a retry without an idempotency key is how you charge someone twice. We shipped idempotency keys on the payment request first — the provider supported them — and only then enabled a single retry. Second, "the 2 seconds should include the queue time at the gateway", which meant our budget had to start from a header the gateway stamped rather than from Kestrel's first byte; that was a two-line change to read X-Request-Start and subtract elapsed, but it changed the semantics of every slice, and I re-ran the load test rather than assume. The exception mapping did the rest: OperationCanceledException where the request token was cancelled maps to a 499-style abort and no alert; where a dependency slice expired it maps to a 504 with the dependency named, and those are the alerts we actually want.

// Budget at the edge: one deadline, propagated. Not "a 2 s timeout on every call".
app.Use(async (ctx, next) =>
{
    var started = ctx.Request.Headers.TryGetValue("X-Request-Start", out var s) ? ParseUnixMs(s) : now();
    var remaining = TimeSpan.FromSeconds(2) - (now() - started);
    using var budget = CancellationTokenSource.CreateLinkedTokenSource(ctx.RequestAborted);
    budget.CancelAfter(remaining > TimeSpan.Zero ? remaining : TimeSpan.Zero);
    ctx.Features.Set<IDeadline>(new Deadline(budget.Token, started + TimeSpan.FromSeconds(2)));
    await next(ctx);
});

// A slice: shorter linked timeout; the parent still wins if it expires first
async Task<Stock> GetStockAsync(Sku sku, CancellationToken budget)
{
    using var slice = CancellationTokenSource.CreateLinkedTokenSource(budget);
    slice.CancelAfter(TimeSpan.FromMilliseconds(400));
    try { return await _inventory.GetAsync(sku, slice.Token); }
    catch (OperationCanceledException) when (!budget.IsCancellationRequested)
    { throw new DependencyTimeoutException("inventory", 400); }        // slice expired → 504, alertable
    // budget expired or client left → OperationCanceledException propagates → 499, no alert
}

dFollow-up drill chain

Why a propagated budget rather than a timeout on each call?

Because per-call timeouts do not compose into an end-to-end promise. Five calls with 2-second timeouts can legally take 10 seconds, and any retry layer multiplies that. A single deadline propagated as a token means the whole request stops at the SLO regardless of where it is, and slices inside it prevent one dependency from consuming everyone's time. The cost is that every layer must accept and honour a token — which we wanted anyway (story 4) — and that "remaining time" must be computed from an absolute instant, not restarted at each hop.

What is wrong with relying on HttpClient.Timeout?

Three things. It is a fixed wall clock per request that knows nothing about the remaining budget, so it is either too long for a request that has already used most of its time or too short for a fresh one. It surfaces as TaskCanceledException — since .NET 5 with an inner TimeoutException — which is easily conflated with real cancellation unless you check the inner exception or the token. And it interacts badly with resilience pipelines, which have their own timeouts, so you end up with three numbers and no one knows which fired. Setting it to infinite and using the per-request token makes the deadline the single source of truth.

At what scale does hedging stop being a good idea?

When the dependency is near capacity or the operation is not idempotent. Hedging trades extra load for tail latency: at 150 ms delay with a 200 ms p90, it sends a second request for roughly 10–15% of calls, which is fine for a read-only inventory service with headroom and catastrophic for a dependency at 90% utilisation, where the hedges push it over and make every request slow. And hedging a write is a double write. So hedging is only for idempotent reads, with a metric on hedge rate and a circuit that disables it when the dependency's latency rises across the board rather than in the tail.

What did you trade away by refusing the payment retry until idempotency keys existed?

About two weeks of a modest conversion improvement — timed-out payments that would have succeeded on retry were instead shown as "please try again" to the user, which some did not. I judged that against double charges, which are refunds, support tickets and a compliance conversation. The trade was easy to explain because the downside of the shortcut was a specific customer harm rather than an engineering preference; I put the two-week cost and the double-charge scenario side by side in the ticket and the product owner chose the delay. Refusals land better when they come with the price of both options.

How do you keep the budget convention alive across many teams?

By making the right thing the default thing: a shared middleware package that stamps the deadline feature, a typed-client registration helper that sets Timeout to infinite and wires the standard resilience handler with the slice, an analyzer rule (CA2016) that fails builds where a token is not forwarded, and a dashboard that splits 499s from 504s by dependency. Then a one-page convention that says "the deadline is absolute, propagated, and the only timeout". Teams adopt conventions that cost them nothing and catch their bugs; they ignore documents.

aWorked example Example — replace with your own

We were designing the client SDK for an internal data platform that sixty services would depend on for years, which is the kind of API where every decision is a decision you cannot easily reverse. The async surface raised four questions with real trade-offs: should hot methods return ValueTask<T> or Task<T>; should we ship synchronous overloads; should listing return IAsyncEnumerable<T> or Task<Page<T>>; and how far back in target frameworks did we owe support. I ran it as a written design review with the three consuming teams who would be loudest, because an SDK designed by its authors alone is designed for its authors.

On ValueTask, I followed what the BCL does rather than what benchmarks tempt you to do. The BCL uses ValueTask on the byte-level surfaces — Stream.ReadAsync(Memory<byte>), PipeReader.ReadAsync, Socket.ReceiveAsync — where calls are frequent, often complete synchronously, and callers are expected to be sophisticated; everywhere else it returns Task, because Task composes (WhenAll, caching, multiple awaiters) and cannot be misused. We had exactly two byte-level methods, the streaming read and write on a record channel, and those got ValueTask with the single-await rule in their XML docs and CA2012 recommended for consumers. Everything else — GetAsync, PutAsync, QueryAsync — returns Task<T>, takes a CancellationToken as its last, optional parameter (CA1068), and uses ConfigureAwait(false) internally because we do not know the caller's context. No sync overloads: a sync method over an async transport is sync-over-async with our name on it, and the one legitimately synchronous operation — reading already-fetched configuration — is a property, not a method with an Async twin.

Listing became IAsyncEnumerable<Record> with [EnumeratorCancellation], plus a lower-level Task<Page<Record>> GetPageAsync(continuationToken) for consumers who need to checkpoint — the enumerable is built on the page method, so both stay consistent. That decision drove the reach decision: IAsyncEnumerable and IAsyncDisposable exist in netstandard2.1 and on .NET Framework only through the Microsoft.Bcl.AsyncInterfaces package, so we multi-targeted netstandard2.0 plus net8.0 and net10.0, took the package dependency on the 2.0 target, and used System.Linq.AsyncEnumerable internally on .NET 10 where it is in the box. What broke after release was predictable in hindsight: one consumer wrapped our ValueTask reads with .AsTask() into a WhenAll over a thousand calls, which negated the zero-allocation path and, on a pooled source, would have been unsafe if they had awaited twice — they had not, but the pattern was one line from it. We added a ReadManyAsync batch method so the fan-out lived inside the SDK where we control it, and we wrote a "when to use which" section that is now the most-read page in the docs.

dFollow-up drill chain

Why does the BCL offer sync overloads on Stream if sync-over-async is bad?

Because Stream has genuinely synchronous implementations — a MemoryStream or a FileStream doing a blocking read is a real, efficient synchronous operation, not an async one wrapped in a wait. The rule is not "never sync", it is "never fake sync over an async transport". Our SDK's only transport is a network call that is asynchronous at the OS level, so a sync overload could only be implemented by blocking on the async one, which would block the caller's thread and, in a UI or legacy ASP.NET context, deadlock. When there is a native synchronous implementation, offer both; when there is not, offer neither.

What is the argument for ValueTask everywhere, and why did you reject it?

The argument is uniformity and future-proofing: a ValueTask can always be backed by a Task today and a pooled source tomorrow without changing the signature, so you never have to break consumers to optimise. It is a real argument and some libraries follow it. I rejected it because the cost is paid by every caller on every method — no direct WhenAll, no caching the result, one-await discipline, a larger return struct — to buy an optimisation that only two methods could ever use. The BCL made the same call. If the SDK had been a low-level I/O library where every method is a hot path, I would have chosen differently.

At what scale does the IAsyncEnumerable listing API become a liability?

When consumers need to parallelise or checkpoint. A pull-based stream is sequential by construction, so a consumer wanting to process pages in parallel has to break out of it; that is why the page API exists underneath and is public. And a long-lived enumeration holds a connection and a server-side cursor for its duration, so a consumer that enumerates slowly — writing each record to a slow sink — pins resources on our side; we bound that with a server-side cursor timeout and document that slow consumers should page. The enumerable is the convenient path; the page API is the one that scales.

How did you handle the consumer that wrapped your ValueTask reads in a thousand-way WhenAll?

As a design signal, not a support ticket. They had a legitimate need — read many records fast — and our API only offered a per-item method, so they built the fan-out the only way they could, and it was one line from a serious bug. I paired with them on a ReadManyAsync in the SDK that does the fan-out with bounded concurrency and a single Task result, shipped it in the next minor, and credited their use case in the release notes. The API grew a method it should have had; they got a faster, safer path; nobody was told they were holding it wrong.

What would change in this design if you were starting it on .NET 11 with Runtime Async?

Almost nothing on the surface, and that is the point of Runtime Async: Task, ValueTask, IAsyncEnumerable and cancellation keep their semantics. The economics shift slightly — the per-await overhead of the compiler state machine shrinks and continuations avoid ExecutionContext capture when unused, so the marginal gain of ValueTask on a method that always suspends gets even smaller, which strengthens the "Task by default" rule. The one design input I would add is diagnostics: with real frames in live stack traces, I would drop the internal frame-filtering our logging did to hide MoveNext noise, because it would hide real frames instead.

The message router was allocating 400 MB per second at 60,000 messages per second, running a Gen0 collection every 40 milliseconds, and the p99 had a sawtooth on it that lined up with the GC. CPU was only 55%, so the cheap fixes — bigger instances, more replicas — would have been paying for garbage. I took a dotnet-trace with the GC allocation-tick events (--providers Microsoft-DotNETCore-SampleProfiler,Microsoft-Windows-DotNETRuntime:0x1:5) and opened the allocation stacks in PerfView. The top three types were AsyncStateMachineBox<…> instances from a six-deep chain of async Task methods per message, Task<bool> and Task<int> results from methods that mostly completed synchronously, and closure classes (<>c__DisplayClass) from lambdas that captured the message in middleware delegates. None of it was a bug. All of it was the async machinery doing what it does, six times per message, sixty thousand times a second.

The lifecycle is the lesson. In a Release build the compiler emits the state machine as a struct on the stack; if every await in the method finds an already-completed awaitable, the method runs to completion synchronously and nothing is boxed — the only allocation is the returned Task, and even that is avoided when the builder can hand back a cached one (Task.CompletedTask for non-generic, and cached Task<T> for bool, small integers and default reference results). The first time an await actually suspends, the builder boxes the struct into an AsyncStateMachineBox on the heap, captures the ExecutionContext, and that box is what the awaiter's continuation points at; subsequent suspensions in the same call reuse it. So a six-deep chain where each level suspends once costs six boxes plus five intermediate Tasks per message, and a chain where only the innermost level suspends costs one box and five tasks. Our chain suspended at the innermost level 5% of the time — a socket write — and at the outer levels never, so the boxes were rare; the Task<T> results and the closures were the bulk.

The fixes were targeted and I measured each in isolation. The three hottest intermediate methods returned ValueTask<int> instead of Task<int>, which removed the per-call result allocation on the 95% synchronous path — 140 MB/s gone. Two pass-through methods that did nothing but return await inner(…) lost their async and returned the inner task directly, which eliminates the state machine entirely, with the caveat I always spell out: a non-async method that returns a task will not catch exceptions thrown synchronously by the callee into the task, and a using in such a method disposes before the returned task completes, so it is only safe when the method has no try/catch, no using, and no work after the call. The closures became static lambdas (C# 9 static modifier makes capture a compile error) with the message passed as state through the delegate's parameter — 90 MB/s gone. I also tried the [AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder<>))] attribute (C# 10 / .NET 6) on the one method that did suspend, which pools its state-machine boxes; it saved 4 MB/s and added a synchronisation point per call, and I reverted it as not worth its complexity. Final: 400 MB/s down to 90, Gen0 every 180 ms, the sawtooth gone, p99 down 30%.

dFollow-up drill chain

Why does an async method that never suspends still allocate, and when does it not?

It allocates the Task it returns, because the caller needs an object to await even if it is already complete — the state machine itself stayed on the stack. It does not allocate when the builder can return a cached task: Task.CompletedTask for non-generic methods, and for Task<T> a small cache covering bool, integers from −1 to 8, and null/default for reference and other types. Anything else — a string, an int of 42, a struct — is a fresh Task<T> per call, which is exactly the case ValueTask<T> exists for.

What is the difference between Debug and Release builds here, and why does it matter for benchmarks?

In Debug the compiler emits the state machine as a class, so every async call allocates it up front even if it never suspends, which makes the debugger's job easier (it can hold a reference to the machine) and makes allocation numbers roughly meaningless; in Release it is a struct that is boxed only on suspension. A benchmark or an allocation profile taken from a Debug build will show the state machines as the dominant allocation regardless of behaviour, and people have "optimised" production code based on that. Rule: allocation profiles from Release builds only, ideally from the production binary.

At what scale do these micro-optimisations stop being worth their complexity?

Below a few thousand operations per second they are invisible; a 72-byte Task at 1,000 per second is 72 KB/s, which the GC clears without noticing. They matter when the async machinery is itself in the top ten of the allocation profile, which in practice means tens of thousands of operations per second through several async layers — routers, proxies, serialisers, database drivers. Even then I apply them to the three hottest methods, not the codebase, and I keep the rest written for clarity. The pooling attribute is the clearest example: real, measurable, and not worth it at our scale.

What did you trade away with the ValueTask change on those three methods?

The composability and safety of Task for every caller of those methods: they cannot cache the result, cannot pass it to WhenAll without AsTask(), and must await exactly once (story 3). The methods were internal with four call sites I controlled, so the cost was a review and CA2012 in the build, and the benefit was 140 MB/s. If they had been a public SDK surface, the same change would have been a contract change with documentation and consumer support attached, and I would have weighed it very differently (story 18).

How does Runtime Async in .NET 11 change this analysis?

It removes the compiler-generated state machine and its box; the runtime allocates a continuation only when a method actually suspends, reuses them more aggressively, skips ExecutionContext capture when there is nothing to restore, and — as of Preview 7 — inlines the hot "await an already-completed task" path down to a status check, which is why the team's microbenchmark of 100 million completed awaits went from about 191 ms to 32 ms. So the pass-through and layering costs shrink toward zero. What does not change: a Task<T> result is still an allocation unless cached, and closures are still closures, so the ValueTask and static-lambda fixes stand. The lesson is to optimise the parts that are semantic, not the parts the runtime is busy fixing.
