Domain-Driven Design (.NET)

study · .NET 10 / EF Core 10 (LTS) · released 2025-11-11

Domain-Driven Design has no version number of its own — Eric Evans' 2003 book still anchors the vocabulary — so this guide pins "latest" to the .NET 10 / EF Core 10 LTS release (November 2025) that today's DDD code actually runs on. Two changes from the last year matter for interviews: EF Core 10 now recommends complex types over owned entity types for value objects, because owned entities carry hidden identity that breaks the copy-by-value semantics DDD expects; and MediatR, the de-facto in-process mediator for CQRS-flavoured .NET codebases, moved to a commercial license in 2025, pushing teams toward Wolverine or a short hand-rolled mediator. The rest of the field is stable: bounded contexts, aggregates and ubiquitous language remain the strategic core, while the industry's pendulum has swung back from microservices-by-default toward modular monoliths that keep bounded contexts as in-process modules until a real scaling or team reason forces a split. Pitched for a lead/principal engineer: expect trade-off and system-design conversations more than definitional recall, with the fundamentals covered fast, as verification rather than first exposure.

01 · Foundations & Ubiquitous Language

DDD starts from a diagnosis, not a technique: in any system big enough to matter, most of the difficulty is essential complexity — the actual tangle of rules the business runs on — not the accidental complexity of frameworks and wiring. Eric Evans' 2003 book bet that the highest-leverage move is to make the code's structure mirror the business's structure so closely that a domain expert and a developer can point at the same class and mean the same thing. The mechanism for that is the ubiquitous language: a vocabulary, forged in conversation with domain experts, that is used identically in speech, in requirements, in tests and in the code itself — not a glossary bolted on afterward, but the language the model is built out of. When the language drifts (the business says "hold", the code says "Suspended", the database column says "status = 3"), that drift is the bug: it means two mental models are diverging and every future change has to translate between them.

Evans' classification splits a domain model into a small vocabulary of building-block roles: entities (things distinguished by identity, which persists through change — a specific Order), value objects (things distinguished by their attributes, with no identity of their own — an Address or a Money amount), domain services (an operation that doesn't naturally belong to any one entity or value, e.g. "transfer funds between two accounts"), and domain events (something that happened, that other parts of the model may care about). Getting fluent at spotting which role a concept plays is the single most testable "fundamentals" skill in a DDD interview, because every later topic — aggregates, bounded contexts, CQRS — is built as a composition of these four roles.

The second half of Evans' insight, easy to forget at senior level, is that not every part of a system deserves this investment. He proposes a core domain — the part that is genuinely the reason the business wins or loses (for an e-commerce company, plausibly pricing and fulfillment logistics, not user authentication) — surrounded by supporting subdomains (specific to this business but not differentiating) and generic subdomains (solved problems: auth, payments processing, email). A lead engineer's real job is triage: pour modelling effort and your best people into the core domain, buy or commodity-build the generic ones, and resist the urge to DDD everything uniformly — that uniformity is the most common way teams burn budget on ceremony with no payoff.

Anemic vs. rich: where the language actually lives

The language is falsified the moment behaviour moves off the model and into a "service" that pokes at public setters — the anemic domain model anti-pattern (unit 11 covers it as a named trap). Compare the same rule expressed both ways:

// Anemic: Order is a bag of properties; the rule lives in a service, in technical vocabulary
public class Order
{
    public OrderStatus Status { get; set; }
    public DateTime? ShippedAt { get; set; }
}

public class OrderService
{
    public void Cancel(Order order)
    {
        if (order.Status == OrderStatus.Shipped)
            throw new InvalidOperationException("bad state");
        order.Status = OrderStatus.Cancelled;
    }
}
// Rich: the rule is the model. "Cancel" and the exception speak the language a domain expert uses.
public class Order
{
    public OrderStatus Status { get; private set; }

    public void Cancel()
    {
        if (Status == OrderStatus.Shipped)
            throw new DomainException("A shipped order can no longer be cancelled — issue a return instead.");
        Status = OrderStatus.Cancelled;
    }
}

Interview trap

Candidates recite "ubiquitous language means using business words in code" and stop there. The real claim is stronger and easier to probe: the language is the same language spoken by the business, actively maintained in conversation — when a domain expert's phrasing changes, the model changes, not the other way around. A second, related trap: treating the domain model as a description of the database schema. Schema-first thinking imports relational concerns (nullability, normalization, foreign keys) into a model that should instead be organized around behaviour and invariants; the persistence shape is a downstream concern, not the model.

Interview Q&A

What problem is DDD actually trying to solve?

It's aimed at systems whose difficulty is dominated by the business domain itself — the rules, exceptions and vocabulary an expert has in their head — rather than by technical scale. The claim is that most of that difficulty is essential, not accidental, so the fix isn't a better framework; it's making the code's structure and language mirror the business's structure and language closely enough that both sides can reason about it together. For domains that are genuinely simple — a CRUD admin panel — DDD's ceremony buys you very little, which is itself a DDD-flavoured judgment call.

What is the ubiquitous language, precisely, and how do you keep it alive?

It's the vocabulary shared by domain experts and the team, used identically in conversation, requirements, tests and code — not a glossary, a living agreement enforced by refusing translation layers between "what the business says" and "what the code says." You keep it alive by having developers sit in on domain conversations, by renaming code the moment a term shifts, and by writing acceptance tests in that vocabulary so a stale name breaks a test, not just a diagram.

How do you tell an entity from a value object when a concept is ambiguous — say, an email address?

Ask whether two instances with identical attributes are interchangeable. If you don't care which "123 Main St" object you hold, only that it says 123 Main St, it's a value object; if you need to track a specific one through changes — this particular Order even after its total changes — it's an entity. Email address is usually a value object in a Contact context, but could become entity-like (needs its own identity and history) inside an email-deliverability system that tracks bounce history per address.

Why does Evans separate core, supporting and generic subdomains, and why does it matter at your level?

Because modelling rigor is expensive, and applying it uniformly is a common way senior teams waste a quarter. The core domain is where the business actually differentiates — that's where you invest your best engineers and deepest modelling; supporting subdomains get "good enough" custom code; generic subdomains (auth, payments, email delivery) should usually be bought or wrapped, not modelled at all. As a lead, this framing is your answer to "why are we spending three sprints on the pricing engine's aggregate design but not on the newsletter signup."

What's the difference between a domain service and an application service?

A domain service holds domain logic that doesn't fit naturally on one entity or value object — think "TransferFunds(fromAccount, toAccount, amount)," which touches two aggregates and enforces a domain rule. An application service (unit 05) is a thin orchestrator one layer up: it starts a transaction, loads aggregates via repositories, calls domain methods, and coordinates side effects like publishing events — it should contain no business rules of its own, only plumbing.

Give a concrete example of ubiquitous-language drift causing a real bug.

A logistics team called something "Delivered" the moment a carrier scan fired, while finance's "Delivered" meant the customer had signed for it — same word, two different truths. Revenue was recognized on carrier-scan "Delivered," overstating recognized revenue by the transit window, until an audit traced it to the single overloaded enum value shared across two bounded contexts that should never have shared it.

Is Evans' Blue Book still the right first reference in 2026, or has it been superseded?

The strategic-design half (bounded contexts, context mapping, ubiquitous language) has aged extremely well and is still the reference. The tactical half is usefully supplemented, not replaced, by Vaughn Vernon's "Implementing Domain-Driven Design" (2013) for aggregate design rules, and by more recent community work on Context Mapping (Michael Plöd) and Team Topologies for how bounded contexts map onto teams and deployables — the vocabulary is Evans', the operational playbook has grown around it.

How would you introduce ubiquitous language to a team that's never done DDD, without it feeling like a rename exercise?

Start from the next feature conversation with a domain expert rather than a code audit — capture the words they actually use, including the awkward and inconsistent ones, and let disagreements surface early since they usually mean two contexts are being conflated. Land it in code incrementally as you touch files for other reasons, and anchor it in a living glossary the team edits together rather than a one-time document; treating it as a rename sprint is exactly the anti-pattern that makes teams give up on DDD after one project.

What's a "knowledge-crunching" session, and why does Evans treat modelling as continuous rather than up-front?

It's a collaborative session — closely related to what the industry now calls Event Storming — where developers and domain experts work through concrete scenarios together until a shared model emerges, then refine it as new scenarios expose gaps. Evans rejects big-design-up-front because a domain model is a hypothesis about how experts think, and that hypothesis is only validated by continuously testing it against real scenarios and revising — the model is expected to change shape many times before it's good.

How do you defend the ubiquitous language against dilution from product, sales or a new hire who reintroduces old terms?

Treat the glossary as a contract with a visible owner, and enforce it the same way you'd enforce a linting rule — in code review, flag a reintroduced term and ask which of the two meanings is intended, forcing the disambiguation to happen once rather than silently. Long term, the strongest defense is making the correct term the path of least resistance: if the type, the exception message and the test names all use it, drifting away from it takes active effort.

When is DDD's investment not worth it?

When the domain is genuinely simple (thin CRUD over a handful of entities with no real invariants), when the system is short-lived or a throwaway prototype, or when the team lacks access to domain experts, making the "ubiquitous" half of ubiquitous language impossible to build. The tell in an interview is a candidate who can name these limits unprompted — it signals judgment rather than dogma.

02 · Bounded Contexts & Context Mapping

The single most important strategic idea in DDD, and the one most likely to actually come up in a principal-level interview, is that you should stop trying to build one model for the whole business. A "Customer" means something different to Sales (a lead with a pipeline stage), Billing (an entity with payment terms and a credit limit), and Support (a person with a ticket history) — and forcing one class to serve all three produces a God object riddled with nullable fields nobody fully understands. A bounded context is the explicit boundary — usually along team or subsystem lines — inside which a model is internally consistent and a term has exactly one meaning; outside it, the same term is allowed to mean something else, on purpose. Getting this right is what makes ubiquitous language actually work at scale: the language isn't ubiquitous across the whole company, it's ubiquitous within a context, and contexts talk to each other through explicit translation, not shared types.

Once you accept multiple models exist, you need a map of how they relate — that's context mapping, DDD's most under-taught tool and the one that most directly answers "how would you decompose this system." The canonical patterns, from Evans and refined by the DDD Europe community (Michael Plöd's Context Mapper work is the modern reference), describe the relationship between two contexts, which is as much organisational as technical:

The anticorruption layer is the pattern worth being able to sketch from memory, because "how do you integrate with the legacy system without your new domain rotting alongside it" is a near-universal senior-interview question. It's a translation boundary: adapters and a small set of DTOs that convert the legacy system's shapes and vocabulary into your bounded context's ubiquitous language, so corruption stops at the wall instead of leaking through your whole model.

// Anticorruption layer: the legacy "LegacyCustomerRecord" never crosses into our domain
public interface ICustomerAcl { Customer Translate(LegacyCustomerRecord legacy); }

public class CustomerAcl : ICustomerAcl
{
    public Customer Translate(LegacyCustomerRecord legacy) =>
        Customer.Reconstitute(
            new CustomerId(legacy.CUST_ID),
            new PersonName(legacy.FNAME, legacy.LNAME),
            legacy.STATUS_CD == "A" ? CustomerStatus.Active : CustomerStatus.Inactive);
}
Interview trap

Candidates equate "bounded context" with "microservice" 1:1. That's a deployment decision layered on top of a modelling decision — a bounded context is a boundary in the model, and can perfectly well be a module inside a modular monolith (unit 09), one microservice, or in rare cases span a couple of tightly-related small services. Presenting it as always meaning "separate deployable" reads as cargo-culting the 2015-era microservices wave rather than understanding what the boundary is actually for.

Interview Q&A

Define bounded context in one breath, then defend it against "isn't that just a module?"

A bounded context is the boundary within which a specific model, and the ubiquitous language it's expressed in, is internally consistent and unambiguous — outside it, the same term can validly mean something else. It's more than "a module" because a module boundary is usually about code organization, while a bounded context boundary is about semantic ownership: crossing it always requires translation, even if the module boundary would let you import the type directly.

How do you actually find bounded-context boundaries in an existing tangled system?

Look for words that are overloaded — the same field or class name used with subtly different meaning in different parts of the code, which is exactly the smell from unit 01 — and for places where a change in one "area" keeps forcing unrelated changes elsewhere, a sign the areas are actually one undifferentiated context. Event Storming workshops with domain experts are the standard technique: pivotal business events cluster naturally around future context boundaries once you lay them out on a timeline.

When would you deliberately choose Conformist over building an anticorruption layer?

When the upstream model is good enough, unlikely to actively corrupt your domain, and the cost of a translation layer exceeds its benefit — e.g. consuming a well-designed platform API where you have no real disagreement with its vocabulary. Choosing Conformist should be an active decision recorded somewhere, not the default outcome of "we didn't get around to writing an ACL."

What's the difference between Shared Kernel and Open Host Service?

Shared Kernel is a small, jointly-owned piece of model shared by a small number of tightly-collaborating teams — changes require mutual agreement, which only scales to a couple of teams. Open Host Service is the opposite shape: one team designs a stable, documented protocol precisely so that many consumers can integrate without needing to coordinate changes with the owning team at all.

How would you use context mapping to plan a decomposition of a monolith?

Map the current model's implicit contexts first — where the vocabulary already splits, even inside one codebase — before touching deployment topology; extraction order should follow business volatility and team ownership, not technical convenience. Contexts with a Conformist or ACL relationship to the rest of the system are natural first candidates to extract, because the translation boundary already exists in the model and just needs a network hop added.

What's a "context map" used for in a real architecture review, beyond documentation?

It surfaces where organisational and technical coupling actually is, which is usually not where the org chart says it is — a Conformist relationship your team never agreed to is a governance risk worth escalating before it becomes an incident. It's also the tool for spotting a Shared Kernel that's quietly become a bottleneck because too many teams now depend on it.

How do bounded contexts relate to Conway's Law?

Conway's Law says system structure mirrors communication structure; DDD's strategic design turns that from an observation into a design lever — deliberately drawing bounded-context boundaries along the lines you want teams to communicate (or not communicate) across. Team Topologies builds directly on this, treating a bounded context as the natural unit a "stream-aligned team" should own end to end.

What goes wrong when a Shared Kernel grows too large?

Every change requires cross-team agreement, so the kernel becomes a coordination bottleneck and teams start avoiding necessary refactors rather than negotiate them — velocity drops precisely in the shared code that was meant to save duplication. The usual fix is to shrink the kernel back to genuinely stable concepts (e.g. a Money value object) and move the volatile parts behind an explicit API with one clear owner, i.e. convert it into a Customer–Supplier or Open Host relationship.

Can two bounded contexts legitimately have entities with the same name and different shapes? Isn't that duplication?

Yes, and it's not duplication in the harmful sense — it's the correct outcome of two contexts genuinely modelling different concerns under one English word. A billing "Order" caring about invoicing terms and a fulfillment "Order" caring about pick-pack-ship states aren't the same concept wearing different clothes; forcing them into one shared type is what actually causes the coupling and God-object problems DDD is trying to avoid.

How do you communicate context boundaries to non-technical stakeholders who just see "the Customer table"?

Frame it in terms they already feel: "Sales' definition of a customer and Billing's definition of a customer already disagree today — this makes that disagreement explicit and safe instead of an accidental bug," using a concrete example of a field that already means different things. A context map with plain-language boxes (not UML) usually lands better than the DDD vocabulary itself.

What's the risk of getting bounded-context boundaries wrong early in a project, and how do you course-correct?

Drawing them too fine-grained too early creates chatty, tightly-coupled "distributed monolith" contexts that all change together anyway, paying integration overhead for none of the isolation benefit; too coarse, and you're back to a tangled single model. The practical course-correction is to keep contexts as in-process modules with enforced boundaries (unit 09) until real evidence — team ownership friction, independent scaling needs — justifies physically splitting one out; a module boundary is far cheaper to redraw than a network boundary.

03 · Entities & Value Objects

With the strategic boundaries in place, the tactical building blocks are how you actually write the model inside one. The entity/value-object split from unit 01 has sharp practical consequences once you write real .NET code: an entity needs a stable identity (usually a strongly-typed id, not a bare int or Guid, so the compiler stops you from passing a CustomerId where an OrderId is expected) and equality by that identity alone; a value object should be immutable, compared by all its fields, and — critically — self-validating, so it is impossible to construct an invalid one. That last property is what makes value objects worth their ceremony: a Money type that guards against negative amounts and mismatched currencies at construction turns a whole category of "how did this get into an invalid state" bugs into a compile-time or constructor-time impossibility instead of a runtime hunt.

// A value object: immutable, self-validating, equality by value (records give you this almost for free)
public sealed record Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        if (amount < 0) throw new ArgumentException("Money cannot be negative.");
        if (string.IsNullOrWhiteSpace(currency)) throw new ArgumentException("Currency is required.");
        Amount = amount; Currency = currency;
    }

    public static Money operator +(Money a, Money b)
    {
        if (a.Currency != b.Currency) throw new InvalidOperationException($"Cannot add {a.Currency} to {b.Currency}.");
        return new Money(a.Amount + b.Amount, a.Currency);
    }
}

Mapping value objects in EF Core 10: the switch from owned entities to complex types

This is the sharpest recent .NET-specific change relevant to DDD. EF Core has long offered owned entity types to persist a value object like Address or Money inside its owner's table — but an owned entity type is, under the hood, still an entity type, with hidden identity and reference semantics. That mismatch causes real bugs: assigning customer.BillingAddress = customer.ShippingAddress throws, because EF won't let the same tracked entity instance be referenced twice, and bulk operations like ExecuteUpdateAsync don't support owned types at all. EF Core 10 (shipped with .NET 10, November 2025, LTS until November 2028) promotes complex types — introduced in EF 8 for simple cases — to the recommended way to map value objects: complex types have true value semantics (copy-assignment just copies fields, equality compares content), now support optional (nullable) complex properties, mapping to a single JSON column, and structs as well as classes. The EF team's own release notes explicitly advise projects still using owned types for value objects to migrate to complex types.

// EF Core 10: map Address as a complex type — value semantics all the way through
public class Customer
{
    public int Id { get; set; }
    public Address ShippingAddress { get; set; } = default!;
    public Address? BillingAddress { get; set; }   // optional complex types: new in EF Core 10
}

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity(b =>
    {
        b.ComplexProperty(c => c.ShippingAddress);
        b.ComplexProperty(c => c.BillingAddress);
    });
}

Interview Q&A

Why should a value object be immutable — what specifically breaks if it isn't?

If a value object is mutable, two references that were equal a moment ago can silently diverge, which breaks the "equal by content" contract every consumer relies on — a Money handed to a discount calculator could change underneath it. Immutability also makes value objects trivially safe to share and cache across aggregates and threads, since there's no mutation to synchronize.

What is "primitive obsession," and how do strongly-typed ids fix it?

It's the smell of representing domain concepts as bare primitives — a raw Guid for both CustomerId and OrderId — so the compiler can't stop you from passing one where the other belongs, and every validation rule has to be re-asserted by hand at each call site. A small wrapper type (a record struct in modern C#) makes the concept a real citizen of the type system: the mistake becomes a compile error instead of a runtime data-corruption incident.

Explain the EF Core 10 change from owned entity types to complex types for value objects, and why it matters for DDD specifically.

Owned entity types are, underneath, still entities with hidden identity, which gives them reference semantics that actively fight the value semantics DDD expects — you can't assign the same address to two properties, and bulk updates don't work. EF Core 10 (with .NET 10, released November 2025) makes complex types — which compare and copy by content — the recommended mapping, closing that semantic gap; if you're doing an EF Core review of a DDD-flavoured codebase today, owned types used for value objects are now a flagged legacy pattern, not a neutral choice.

How do you handle a value object that needs to be looked up or filtered on efficiently in the database?

Complex types mapped via table splitting still produce ordinary columns, so ordinary indexes and query translation work exactly as they would on flattened properties — the value-object abstraction is a code-level concern, not a storage-format tax you have to pay in query performance. If you map to a single JSON column instead, EF Core 10's JSON-aware LINQ translation (JSON_VALUE(...) on SQL Server) still lets you filter by an inner property, though a dedicated column is usually still faster for a hot filter path.

Can an entity's identity ever change?

No — that's the defining property. If the identifier can legitimately change (a customer's loyalty number gets reissued, say), what you actually have is either a new entity with a link to the old one, or the identifier was never truly the entity's identity in the first place and something more stable (a surrogate key) should be.

Give an example where the same concept is a value object in one bounded context and an entity in another.

A "SKU" is typically a value object inside an Ordering context — two order lines referencing "SKU-123" are interchangeable, nothing about the SKU itself is tracked. Inside an Inventory context that needs to track a specific physical unit's serial number, location history and condition, that same product identity becomes (or grows into) an entity — the correct classification depends on what the context actually needs to do with it, not on some universal truth about SKUs.

What's a common mistake when implementing equality for a value object in C#?

Overriding Equals without also overriding GetHashCode (or using a plain class with reference equality and forgetting both) — breaks dictionary/set usage and any code that hashes the value object, and produces confusing bugs where two "equal" objects behave differently in a HashSet. Using C# record or record struct for value objects sidesteps this entirely, since value-based equality and hashing are generated for you.

Should a value object ever hold a reference to an entity?

Generally no — that would give it an implicit identity dependency and complicate its copy-by-value semantics; value objects should be self-contained data. If you find yourself wanting a value object to "know about" a specific entity, that's usually a sign the concept actually needs identity and should be modelled as an entity, or that the relationship belongs one level up, in the aggregate that holds both.

How would you migrate an existing EF Core codebase from owned types to complex types, and what's the risk?

It's a model-only change for table-split mappings — swap OwnsOne/OwnsMany for ComplexProperty, add a migration, and verify column names haven't shifted — but any code that relied on owned types' reference semantics (tracking a specific owned instance, or comparing by reference) needs auditing, since that behaviour silently changes. Collections of complex value types have some remaining limitations (no struct collections yet as of EF 10), so an owned collection of a class-based value object migrates more cleanly than one using a struct.

Why does DDD care about self-validating value objects instead of validating in a separate validation layer?

A separate validation layer only protects the paths that call it — anyone constructing the object another way (a test, a mapper, a deserializer) can bypass it and produce an invalid value that then propagates. Making invalidity unrepresentable at construction — throw or refuse to compile — means every consumer of the type can trust its invariants without re-checking, which is the whole point of a rich domain model over an anemic one.

What's the trade-off of making every small concept (name, email, percentage) its own value-object type versus keeping primitives?

Each wrapper buys compile-time safety and a single place for validation and behaviour, but adds ceremony — more types to map, more constructors, more places EF configuration and serializers need attention — so it pays off fastest for concepts with real validation rules or a real risk of mix-up (money, ids, percentages) and pays off least for a field that's genuinely just a display string. The judgment call is proportional to the blast radius of getting it wrong, not a blanket rule either way.

04 · Aggregates & Invariants

An aggregate is a cluster of entities and value objects treated as one consistency unit, with a single aggregate root — an entity through which the entire cluster is loaded, mutated and saved. The reason aggregates exist at all is invariant enforcement: a rule that must always hold ("an order's line-item total must equal its recorded total," "you cannot ship more than was ordered") can only be guaranteed if every mutation that could violate it happens inside one transactional and conceptual boundary. Anything reachable only through the root, and anything that must always be consistent with something else, belongs inside the same aggregate; anything that can tolerate being briefly stale relative to the rest of the system belongs in a different aggregate, updated via eventual consistency (unit 06).

Vaughn Vernon's "Effective Aggregate Design" (2011) is the standard operational playbook, and it corrects a common misreading of the original Blue Book: Evans' examples are often larger than they should be, and Vernon's central rule is design small aggregates. A large aggregate — say, an Order that holds every historical status change, every note, every attachment as child entities inside one root — means every concurrent edit to any part of it contends for the same lock or the same optimistic-concurrency token, and every load pulls in data most operations don't need. The rule of thumb: reference other aggregates by identity only (an Id, never a live object reference), enforce true invariants inside the aggregate boundary, and treat everything else as eventually consistent through domain events.

public class Order   // aggregate root
{
    public OrderId Id { get; }
    private readonly List<OrderLine> _lines = new();
    public IReadOnlyCollection<OrderLine> Lines => _lines.AsReadOnly();
    public OrderStatus Status { get; private set; }

    public void AddLine(ProductId product, int quantity, Money unitPrice)
    {

Interview trap

The most common aggregate-design mistake in real .NET codebases is modelling a one-to-many relationship as an aggregate boundary just because EF Core's navigation properties make it easy — e.g. Order owning a Customer as a child collection because "an order belongs to a customer." Ownership in the data-modelling sense is not the same question as "must these be transactionally consistent." A second trap, common among strong engineers overcorrecting: designing one giant aggregate to "guarantee consistency everywhere," which kills write throughput and creates lock contention across unrelated concerns that never needed to be atomic together.

Try it
  1. Take an aggregate in your codebase and list every invariant it actually enforces. For each one, ask: does violating this really break the business, or would a slightly-stale value be tolerable for a few seconds? Any "tolerable" answer is a candidate for moving out of the aggregate.
  2. Deliberately break an aggregate's invariant by mutating a child collection directly instead of through a root method (e.g. exposing a public List<OrderLine> setter) and observe what goes wrong under a concurrent write.
    Expected outcomeTwo concurrent requests can both pass a validation check based on stale in-memory state and then both commit, producing a state the invariant was supposed to forbid — the fix is making the collection only mutable through root methods that re-check the invariant against current state.

Interview Q&A

What is an aggregate root, and why must all mutation go through it?

It's the single entity that acts as the entry point to the whole cluster — every load, every mutation, every save happens through it, and nothing outside the aggregate holds a live reference to its internal entities. Routing everything through the root is what makes invariant enforcement possible at all: if code elsewhere could reach in and mutate a child entity directly, the root could never guarantee the rule held after the fact.

What's the correct size for an aggregate — how do you decide what's inside versus outside the boundary?

Small, and decided by true invariants, not by data-modelling convenience: something belongs inside the aggregate only if it must be transactionally consistent with the root right now, not eventually. Vernon's guidance is to design the smallest aggregate that can still enforce its invariants, and to reference everything else — even things that look "owned" in an ER diagram — by id, coordinating consistency between aggregates via domain events instead.

Why does referencing other aggregates by id instead of by object reference matter so much in practice?

A live object reference lets code accidentally reach across an aggregate boundary and mutate something it has no business mutating, silently defeating the invariant guarantee the boundary exists for. It also usually means loading far more data than the operation needs (pulling in a whole Customer graph to check a discount an Order applies), and it makes each aggregate's persistence unit unclear, which complicates both performance and testing.

How do you enforce a rule that spans two aggregates, like "the sum of a customer's open orders can't exceed their credit limit"?

You don't try to make it a hard, always-consistent invariant across two aggregate boundaries — you either accept eventual consistency (a domain event updates a running total on the Customer aggregate after each Order is submitted, with compensating action if it's later found to be over limit) or you pull the check into a domain service that reads both aggregates and makes the decision at the point of the state-changing command, accepting a small race window. Forcing it into one aggregate to get true atomicity usually costs more in contention than the rare race condition would ever cost in correctness.

Optimistic vs. pessimistic concurrency for aggregates — which do you default to and why?

Optimistic, by default: a version token that fails a concurrent write at commit time scales far better than holding a database lock across a whole business transaction, especially under real .NET/EF Core web workloads where a request might involve I/O (external calls) between load and save. Pessimistic locking earns its place only for aggregates with very high write contention and cheap, fast transactions, where retry storms under optimistic concurrency would be worse than a short lock wait.

What goes wrong with an aggregate that's too large, concretely?

Every unrelated field change contends for the same concurrency token, so two edits that have nothing to do with each other (updating a shipping note vs. adding a line item) can conflict and force a retry; loading the aggregate for a small operation pulls in data — and often related entity graphs — the operation never touches, hurting latency; and the object becomes hard to reason about because "what does this really guarantee" stops having a clean answer.

Should a repository ever expose a method that loads part of an aggregate?

No — the aggregate is the unit of consistency and the unit of loading; a repository should load and save whole aggregates by their root id, never a fragment, because a partially-loaded aggregate can't safely re-validate its own invariants. If a read pattern genuinely only needs a projection of the data, that's a query concern (unit 07's read side), not a reason to weaken the write-side aggregate's loading contract.

How does aggregate design interact with EF Core's change tracking?

EF Core's change tracker naturally maps well to "load the whole aggregate graph, mutate it via root methods, call SaveChanges once" — as long as child collections are exposed as read-only and mutated only through root methods, so nothing outside the aggregate can add or remove tracked entities behind its back. A common misconfiguration is exposing a public setter on a navigation collection, which lets calling code bypass the root entirely and corrupt the invariant the aggregate exists to protect.

Give an example of a rule that looks like an aggregate invariant but isn't.

"A product's stock count must never go negative across all warehouses" sounds like an invariant on a Product aggregate, but if warehouses are modelled as separate aggregates for independent scaling and ownership reasons, this becomes a cross-aggregate policy enforced via events and reconciliation, not a single-aggregate invariant — treating it as one forces an unnaturally large aggregate spanning every warehouse. The tell: does violating it for a few seconds actually cause business harm, or just look untidy? Untidy-but-tolerable belongs outside the boundary.

How would you explain aggregate boundaries to a team that keeps modelling them as EF Core navigation properties?

Reframe the question from "what's related to what" (a data-modelling question EF Core answers for free) to "what must never be observed in an inconsistent state, even for a moment" (a business-rules question EF Core can't answer for you) — most navigation properties turn out to describe legitimate relationships that don't need transactional consistency. Walking through one or two real invariants together, and asking "what actually breaks if this update lands one second late relative to that one," usually converts the team faster than the abstract definition does.

05 · Layering: Domain, Application & Repositories

DDD's tactical patterns need somewhere to live that keeps the domain model free of infrastructure concerns — that's the job of layering. Evans' original four layers were User Interface, Application, Domain, and Infrastructure; the modern .NET incarnation is almost always some variant of Clean Architecture, Onion Architecture or Hexagonal (Ports & Adapters) Architecture — different names for the same core rule: the Dependency Rule, where dependencies point inward, toward the domain, and the domain itself depends on nothing. The domain layer defines interfaces (ports) it needs — IOrderRepository, IPaymentGateway — and the infrastructure layer implements them (adapters); the domain never references EF Core, HTTP clients, or any concrete infrastructure type. This is what makes a domain model unit-testable without a database and swappable without a rewrite.

The repository pattern is the domain's port to persistence: one repository per aggregate root, returning and accepting whole aggregates (unit 04), never fragments. A repository is not a generic data-access wrapper around every table — a GetOrderLinesByProductAsync method on an order repository is a smell, because it exposes internals of the aggregate that should only ever be reached through the root.

// Domain layer: the interface, with zero EF Core knowledge
public interface IOrderRepository
{
    Task<Order?> GetByIdAsync(OrderId id);
    void Add(Order order);
}

// Infrastructure layer: the implementation, isolated behind the interface
public class EfOrderRepository : IOrderRepository
{
    private readonly AppDbContext _db;
    public EfOrderRepository(AppDbContext db) => _db = db;

    public Task<Order?> GetByIdAsync(OrderId id) =>
        _db.Orders.Include(o => o.Lines).SingleOrDefaultAsync(o => o.Id == id);

    public void Add(Order order) => _db.Orders.Add(order);
}

// Application layer: orchestration only — no business rule lives here
public class SubmitOrderHandler
{
    private readonly IOrderRepository _orders;
    public SubmitOrderHandler(IOrderRepository orders) => _orders = orders;

    public async Task Handle(SubmitOrderCommand cmd)
    {

        order.Submit();                 // the rule lives on the aggregate, not here
        // SaveChangesAsync via a unit-of-work / DbContext scope commits the transaction
    }
}
Interview trap

The most common layering violation in real .NET codebases is an EF Core entity that is the domain entity, decorated with data annotations and navigation properties designed for the ORM's convenience rather than the domain's invariants — which quietly makes the "domain" layer depend on EF Core after all. A second trap: application services that contain actual business rules ("if the customer's total this month exceeds X, apply a discount") instead of delegating to the aggregate — this is the anemic-model problem from unit 01 wearing a "Clean Architecture" folder structure as camouflage. Folder structure that matches the layer names is not the same thing as respecting the dependency rule.

Try it

  2. Find an application service method over ~15 lines and highlight every line that is a business decision (an if based on domain state) versus orchestration (loading, saving, mapping).
    Expected outcomeAny highlighted "decision" line is a candidate to move onto the aggregate as a method; a healthy application service should be almost entirely orchestration lines.

Interview Q&A

State the Dependency Rule and explain why the domain layer can't reference infrastructure, even "just for a small helper."

Dependencies point inward: outer layers (infrastructure, presentation) may depend on inner layers (domain, application), but never the reverse — the domain defines the interfaces it needs and infrastructure implements them. The moment the domain references a concrete infrastructure type, even for something small, the domain can no longer be tested or reasoned about in isolation, and a change to that infrastructure detail can now force a change to business logic that has nothing to do with it.

What's the difference between a domain service and an application service, precisely, and where does a "SubmitOrder" use case's transaction boundary live?

A domain service holds business logic that spans multiple domain objects but doesn't belong to any one of them (unit 01); an application service orchestrates a use case — load, call the domain, save, publish events — and should contain no business rules itself. The transaction boundary belongs in the application layer, typically one transaction per use case / per aggregate save, started and committed around the orchestration, never inside the domain layer which has no concept of "database transaction."

Why "one repository per aggregate root" rather than one repository per table or one generic repository?

The aggregate, not the table, is the actual unit of consistency and loading (unit 04) — a repository that exposes methods reaching into an aggregate's internals (fetching a child collection directly) breaks the invariant guarantee the aggregate exists to provide. A single generic IRepository<T> for every entity tends to leak persistence concerns (arbitrary IQueryable exposure, generic filtering) into the domain and erases the very aggregate boundaries you're trying to enforce.

Should an EF Core entity and a domain entity be the same class?

They can be, pragmatically, in many real .NET codebases — EF Core's mapping is flexible enough (private setters, backing fields, owned/complex types) that the domain class doesn't have to look like an anemic DTO just because EF Core maps it. The line not to cross is letting EF Core's convenience (public setters for convenient seeding, exposed navigation collections) leak into the public API of the entity in a way that lets code outside the aggregate mutate it directly — the mapping detail must stay a detail.

How do you unit-test a domain model that's properly isolated per the Dependency Rule?

Directly, with no database, no HTTP, and no mocks for the domain's own logic — construct an aggregate, call its methods, assert on its state or the domain events it raised. Repository interfaces get faked only at the application-service test boundary, where you're testing orchestration, not domain rules; a domain model that needs a database or a mock framework to test is a sign the Dependency Rule has already been violated somewhere.

What's the "Unit of Work" pattern, and does EF Core's DbContext already give it to you?

Unit of Work tracks a set of changes across possibly multiple repositories and commits them atomically in one transaction — EF Core's DbContext already behaves this way natively (its change tracker accumulates changes from multiple DbSets, and one SaveChangesAsync commits them together), so hand-rolling a separate Unit-of-Work abstraction on top of EF Core is usually redundant ceremony rather than a needed pattern.

How would you review a pull request to check it respects the layering, in under two minutes?

Check the using statements in any file under the domain folder for framework or infrastructure namespaces, and skim the application service methods for any if that's evaluating business state rather than orchestrating a call — those two checks catch the two most common violations (infrastructure leaking in, business rules leaking out) fast. It's not exhaustive, but it's the highest-signal two-minute check for this class of problem.

Is Clean/Onion/Hexagonal Architecture required to do DDD? Could you do tactical DDD in a simpler layering?

No — the Dependency Rule is a means to protect the domain model's independence, not a DDD requirement in itself; you can absolutely do tactical DDD (rich aggregates, value objects, domain events) inside a simpler three-tier layering as long as business rules genuinely live in the domain classes and not in controllers or services. What DDD actually requires is that the model be rich and language-driven — the specific layering diagram is an implementation choice, and over-formalizing it (extra projects, extra interfaces "for testability" nobody uses) is itself a smell worth flagging in review.

What's a "specification" and where does it sit in this layering?

A specification is an object that encapsulates a reusable query or business-rule predicate ("orders overdue by more than 30 days") so it can be shared between a repository query, an in-memory check, and a validation rule without duplicating the logic — it's a domain-layer concept (the rule) with an infrastructure-layer translation (to SQL/LINQ) behind the repository interface. Unit 10 covers it as a testing tool as well.

How would you introduce this layering into a legacy codebase where controllers call EF Core directly, without a rewrite?

Start with the highest-value aggregate — usually the core domain from unit 01 — extract its rules into rich methods on the existing entity classes, introduce a repository interface for just that aggregate, and route new features through it, leaving the rest of the codebase as-is until it's touched for other reasons. Trying to erect the full four-layer structure everywhere on day one, before any real domain logic has moved into it, produces empty ceremony layers with nothing in them — a very common and very visible sign of cargo-culted DDD.

06 · Domain Events & Integration

A domain event captures something that happened in the domain that other parts of the model, or other systems, might care about — OrderSubmitted, PaymentCaptured, InventoryReserved. Evans introduced them as a first-class Building Block because "the order was submitted" is a fact the ubiquitous language already talks about in the past tense, and modeling it explicitly (rather than inferring it from a row's Status column changing) makes side effects — sending an email, updating a read model, notifying another bounded context — explicit and testable instead of buried in a cascade of method calls. The critical distinction, and a frequent interview probe, is between an in-process domain event (raised by an aggregate, handled synchronously in the same transaction, same process, same request — e.g., recalculating an order's total when a line is added) and an integration event (published after the transaction commits, consumed by other services or bounded contexts, asynchronous, and must survive process crashes).

Conflating the two is the single most common event-related production bug: raising a domain event that triggers a call to another microservice inside the same database transaction couples your consistency boundary to a network call, and if that transaction rolls back after the external call already fired, you've told another system about something that never actually happened. The fix is the outbox pattern: when the aggregate's transaction commits, an "outbox" row (the eventual integration event) is written atomically in the same transaction as the domain state, and a separate, independent process (a background poller or a change-data-capture pipeline like Debezium) reads unpublished outbox rows and publishes them to the message broker, retrying until it succeeds — this gives you exactly the reliability guarantee ("the event is published if and only if the transaction committed") that a direct in-transaction publish cannot.

"We publish the event directly to the message bus right after SaveChangesAsync" sounds fine until the process crashes between the two calls — the transaction committed, the event never went out, and downstream systems silently drift out of sync with no error anywhere. The outbox pattern exists specifically to close this gap; if a candidate proposes direct publish-after-commit without mentioning this failure window, that's the follow-up question to ask. The opposite trap is over-modeling: not every state change needs a domain event — raising one for every property setter turns the event stream into noise nobody can operate on.

Interview Q&A

Why does the transactional outbox pattern exist — what specific failure does it prevent that a direct publish doesn't?

It prevents the "dual write" problem: writing to the database and publishing to a message broker are two separate systems with no shared transaction, so a crash between them (or a broker outage) leaves the two permanently out of sync with no automatic recovery. The outbox writes the event as a row in the same database transaction as the domain change, making the event's existence atomic with the state change; a separate publisher then delivers it with retries, so worst case the event is delayed, never lost or falsely sent.

What does "at-least-once delivery" mean for integration events, and what does it require of consumers?

Because the outbox publisher retries until it gets a delivery acknowledgment, a broker or network blip can cause the same event to be delivered twice — consumers must be idempotent, typically by tracking processed event ids and skipping duplicates, or by designing the handler so applying it twice has the same effect as applying it once (e.g., an upsert rather than an increment).

Should an in-process domain event handler be allowed to call another aggregate's repository and save it, in the same request?

Generally no if it crosses aggregate boundaries within the same transaction — that reintroduces the multi-aggregate transaction unit 04 warns against, just hidden behind an event handler instead of an explicit call. The common resolution is: update the other aggregate eventually, via its own transaction, triggered by the same domain event but running after the first commit (in-process, later in the request, or via the outbox) — eventual consistency between aggregates, strong consistency within one.

How would you version an integration event's schema without breaking existing consumers?

Treat it like the Published Language from context mapping (unit 02): add fields as optional/additive rather than removing or renaming existing ones, and if a genuinely breaking change is needed, publish a new event type/version alongside the old one for a transition window rather than mutating the existing contract in place. Consumers should also tolerate unknown fields rather than failing deserialization on them.

What's the difference between a domain event and a "notification" in something like MediatR's terms?

They're the same underlying concept — MediatR's INotification/IRequest split (unit 07 covers MediatR's current status) is a mechanism for in-process dispatch of domain events to handlers within the same request; the DDD term "domain event" is about what it represents (a business-meaningful fact), while "notification" is about how a particular library delivers it in-process. Nothing stops you from raising a domain event and dispatching it with a hand-rolled dispatcher instead.

Why store the event as JSON payload rather than a strongly-typed column per event type in the outbox table?

A single generic outbox table (id, event type discriminator, JSON payload, timestamps) scales to any number of event types without a schema migration per new event, and matches how most brokers serialize messages anyway; the cost is losing compile-time/DB-level type safety on the payload, which is an acceptable trade because the payload's shape is validated at serialization/deserialization time in code, not by the database schema.

Can you use EF Core's SaveChanges interceptors to implement the outbox pattern, and is that a good idea?

Yes — an ISaveChangesInterceptor can inspect the tracked aggregates' raised events before SaveChangesAsync commits and add corresponding outbox rows to the same DbContext, so they're written in the same transaction with no extra plumbing in every application service. It's a good idea specifically because it centralizes the "collect events → write outbox rows" step once, instead of repeating it in every command handler and risking someone forgetting it.

A downstream team asks you to add a field to an integration event for their new feature. What do you push back on, and what do you ask?

Push back on adding anything that exposes your internal model rather than a genuinely public fact (per Open Host Service from unit 02) — if the field only makes sense in terms of your internal aggregate's implementation, that's a sign the event shouldn't carry it, or that they need a different integration point (a query API) rather than piggybacking on your event. Ask whether the field is additive/optional so existing consumers are unaffected, and whether they actually need it pushed proactively or could pull it via a query when the event tells them "something changed."

How do you test an outbox-based flow end-to-end without a real message broker?

Split the test into layers: unit-test the aggregate raising the correct events (no infrastructure at all, per the try-it above), integration-test that a saved aggregate produces the right outbox rows (using a real or in-memory database, no broker), and separately test the poller's publish-and-mark-sent logic against a broker test container or a fake — you rarely need all three layers wired together in one test to have confidence in the whole pipeline.

What's "eventual consistency" in this context, and how do you explain the acceptable staleness window to a stakeholder who's worried about it?

It means data derived from an event (a read model, another bounded context's copy of the data) may lag the source of truth by a small, typically sub-second-to-seconds window while the event travels through the outbox and broker — the stakeholder conversation should focus on what actually breaks if a user sees slightly stale data for that window (usually nothing, since most UX is already tolerant of a page not being millisecond-fresh) versus the availability and coupling cost of forcing synchronous consistency instead.

Where do domain events fit if you're not doing full event sourcing (unit 08) — are they only useful with an event store?

No — domain events are useful independently of event sourcing; here they're a side-effect and integration mechanism layered on top of a conventional state-stored aggregate (EF Core mapping current state), not the system of record itself. Event sourcing is the more radical step of making the event stream itself the source of truth and deriving current state by replaying it — a separate decision covered next.

07 · CQRS & the Application Layer

Command Query Responsibility Segregation (CQRS) splits the model used to change state (commands, routed through the rich domain model — aggregates, invariants, the works) from the model used to read state (queries, which can bypass the domain entirely and read a shape optimized for the screen or report that needs it). This is a direct consequence of a tension DDD surfaces early: an aggregate designed around consistency and invariants is usually a terrible shape for a UI grid or a dashboard that needs to join and flatten data from several aggregates. Greg Young coined the term generalizing Bertrand Meyer's Command-Query Separation principle to the architectural level; the key thing CQRS does not require, despite common conflation, is separate databases or event sourcing — those are optional escalations (a separate read-optimized store, materialized via the domain events from unit 06) you reach for only when a single shared database's read performance or query complexity actually demands it. Most .NET teams practicing CQRS today still read and write the same database — commands go through EF Core and the aggregate, queries run a lean, purpose-built LINQ projection (or raw SQL/Dapper) straight to a DTO, skipping the aggregate's Include graph entirely.

The application layer (unit 05) is where commands and queries live as discrete objects with their own handler — this is what a mediator library gives you: SubmitOrderCommand in, handled by exactly one SubmitOrderCommandHandler, decoupling the caller (a controller) from the handler and letting cross-cutting concerns (logging, validation, transactions) wrap every command/query uniformly via a pipeline. In .NET, this has meant one library so dominant its name became shorthand for the pattern: MediatR. That changed materially in 2025 — MediatR's author moved the project to a commercial license: as of MediatR v13 (2025), production use requires a paid license key purchased through mediatr.io, while the message contracts (IRequest, INotification) were split out into the still-free, MIT-licensed MediatR.Contracts package so consuming libraries that only reference the interfaces aren't forced into the paid tier. This is exactly the kind of very recent, citable change worth walking into an interview with: teams now face a real build vs. buy decision that didn't exist before, and the two live alternatives are Wolverine (Jeremy Miller's open-source mediator/messaging framework, which also unifies in-process and out-of-process messaging under one API) and a hand-rolled mediator — often just a few dozen lines using DI's IEnumerable<IHandler<T>> resolution — since the pattern itself is simple enough that many teams conclude they don't need a library-shaped dependency for it at all.

Interview trap

Candidates often describe CQRS as "always means event sourcing and two databases" — that's the maximalist, high-end version, not the definition. The core idea is simply "don't force one model to serve both reads and writes," and it's entirely legitimate — and far more common in practice — to apply it against a single shared database. The second trap: treating "we use MediatR" as synonymous with "we do CQRS" — a mediator library is dispatch plumbing for commands/queries, not the architectural decision itself; you can do CQRS with no mediator at all, and you can use MediatR for something that isn't CQRS.

Interview Q&A

Define CQRS precisely, and correct the common misconception that it requires event sourcing or two databases.

CQRS is the principle of using separate models for reads and writes — commands mutate state through the domain model with full invariant enforcement, queries return data shaped for their consumer without going through that same model. It requires neither event sourcing nor a separate physical database; both are optional escalations for when a single shared database's read side becomes a genuine bottleneck or the query shape diverges too far from the write model to share it economically.

What changed with MediatR in 2025, and what are the concrete options for a .NET team affected by it?

As of v13, MediatR requires a paid license key for production use via mediatr.io, while the request/notification interfaces were split into the still-free MediatR.Contracts package. Teams can pay for the license, pin to the last free v12.x release (accepting no further updates), migrate to Wolverine (a broader, free, open-source alternative that also handles out-of-process messaging), or hand-roll a minimal in-process mediator over DI, which is realistic precisely because the core pattern is simple.

When would you actually stand up a separate read database for the query side, rather than querying the same database as the writes?

When read query complexity or volume genuinely can't be served well by the write-optimized schema — heavy reporting/aggregation workloads competing with transactional load, or a read shape that requires joining across many aggregates or even bounded contexts in ways that would be expensive to compute on demand. The trigger is a measured pain point (slow queries, lock contention, unacceptable latency), not a default architectural starting position.

How do pipeline behaviors (in MediatR or Wolverine) relate to cross-cutting concerns like validation, logging, and transactions?

A pipeline behavior wraps every command/query handler with middleware-style logic — validate the request before it reaches the handler, log timing/outcome, open and commit a transaction around the handler — without each handler repeating that plumbing itself. This is the main reason teams reach for a mediator library rather than calling handlers directly: it's not the dispatch itself that's hard, it's getting consistent cross-cutting behavior without duplicating it everywhere.

Should a query handler ever call into the domain model (aggregates)?

Generally no — the point of the read side is to skip the ceremony (loading a whole aggregate graph, enforcing invariants that don't apply to a read-only view) and project directly to the shape the consumer needs, typically via a lean LINQ projection or raw SQL. An occasional exception is a query that needs to reuse a genuinely complex piece of domain logic for a computed field, but even then, prefer duplicating the read-only calculation in the query projection over pulling the whole aggregate into a read path.

What's the risk of hand-rolling a mediator instead of using a library, and when is it the right call?

The risk is quietly reinventing the pipeline-behavior ecosystem (validation, logging, transaction wrapping, retry) one ad-hoc mechanism at a time as needs arise, ending up with something less consistent than what a mature library gives for free. It's the right call when the team's needs are simple and stable — a handful of cross-cutting concerns, no need for out-of-process messaging — and the cost of a paid or larger dependency outweighs a genuinely small amount of code to write and own.

How does CQRS interact with the aggregate boundaries from unit 04 — does every command target exactly one aggregate?

In the healthy case, yes — one command should load, mutate, and save exactly one aggregate instance, which is precisely why aggregates should be sized around true transactional consistency needs (unit 04); a command that needs to touch two aggregates in the same transaction is usually a sign either the aggregate boundary is wrong or the operation should be split into two commands coordinated via a domain event (eventual consistency, unit 06) instead of a single cross-aggregate transaction.

What's the difference between a "command" that returns nothing and one that returns an id or a result — is that a CQRS violation?

Strict Command-Query Separation (Meyer's original principle) says commands shouldn't return domain data, only success/failure — but pragmatic CQRS in most real systems relaxes this slightly, letting a command return the minimum needed for the caller to proceed (a new id, a version stamp for later requests), while still not returning a full query-shaped payload. This is a judgment call to name explicitly in review rather than a hard rule to enforce dogmatically.

A junior developer wants to add event sourcing "because we're doing CQRS anyway." What do you ask them?

Ask what specific problem event sourcing solves that the current state-stored model plus domain events (unit 06) doesn't — usually the honest answer is "none yet," since event sourcing is a much bigger commitment (unit 08) that should be justified by a real need for full audit history, temporal queries, or true CQRS with independently-scaled read models, not adopted as a default extension of "we already split reads and writes."

How would you introduce CQRS-style read/write separation into a codebase currently doing everything through one repository-and-service layer, incrementally?

Start with the read side on the highest-traffic or most awkward screen: replace its current aggregate-hydrating query with a direct, flat projection DTO query, measure the improvement, and repeat opportunistically where it pays off — no need to introduce a mediator library, a command/query naming convention, or a separate database on day one. The write side usually needs no change at all if it already goes through the domain model correctly.

What do you tell a team that's anxious about MediatR's licensing change affecting a large existing codebase with hundreds of handlers?

First, the free v12.x line keeps working indefinitely — there's no forced runtime shutoff, so there's no emergency; the decision (pay, migrate, or hand-roll) can be made on the team's own timeline. Second, because the actual message contracts (IRequest/INotification) stayed free and the handler-calling code is thin, a migration to Wolverine or an in-house dispatcher is mostly mechanical rather than a rewrite of business logic, since none of the domain or handler bodies need to change — only the dispatch registration and pipeline wiring.

08 · Event Sourcing

Event sourcing takes the domain events from unit 06 and makes them the system of record: instead of storing an aggregate's current state (a row that gets overwritten on every update), you store the full, ordered sequence of events that produced it — OrderCreated, LineAdded, LineAdded, Submitted — and derive current state by replaying them, typically by folding each event over the aggregate's state through the same methods that raised them. This is a genuinely different persistence model, not a variant of "just add an events table" — the event stream is the data; the current-state snapshot, if you keep one at all, is a cache you can always regenerate. The payoff is real: a complete, tamper-evident audit trail of everything that ever happened for free, the ability to answer "what did this order look like at 3pm yesterday" by replaying up to that point, and natural support for the CQRS read-model story from unit 07 — project the same event stream into as many differently-shaped read models as you need, and rebuild them from scratch whenever their shape changes.

The cost is equally real and is why event sourcing remains a deliberate, narrow choice rather than a default: every query against current state now requires either replaying the whole stream (slow for long-lived aggregates, mitigated with periodic snapshots) or maintaining projections that can themselves drift or need rebuilding; schema evolution of the events themselves is harder than evolving a table, because old events already committed to the store must still deserialize correctly forever (versioned event types, upcasting old shapes to new ones); and the team now needs real competence in a genuinely less familiar model — most .NET line-of-business systems, even those enthusiastic about DDD, do not use event sourcing, and using it as a badge of "we do real DDD" rather than a response to an actual audit/temporal/CQRS-scale requirement is a well-known trap. Marten (built on PostgreSQL, from the same author as Wolverine) and EventStoreDB are the two most common concrete choices in the .NET ecosystem for teams that do have the requirement.

    public static Order FromHistory(IEnumerable<IDomainEvent> history)
    {
        var order = new Order();
        foreach (var e in history) order.Apply(e);
        return order;
    }

    private void Apply(IDomainEvent e)
    {
        switch (e)
        {
            case OrderCreated c: Id = c.Id; Status = OrderStatus.Draft; break;
            case LineAdded l: _lines.Add(new OrderLine(l.ProductId, l.Quantity)); break;
            case OrderSubmitted: Status = OrderStatus.Submitted; break;
        }
    }
}

The deeper trap is proposing event sourcing to solve a problem (usually "we need an audit log") that a much smaller, well-understood tool already solves — audit tables, temporal tables (SQL Server's built-in SYSTEM_VERSIONING), or CreatedBy/ModifiedBy columns — without the replay complexity, snapshotting, and event-schema-versioning burden that full event sourcing brings.

Interview Q&A

Define event sourcing precisely, and distinguish it from "just raising domain events."

Event sourcing means the append-only stream of events is the actual system of record — current state is always a derived, rebuildable projection of that stream, never stored as the primary truth. Raising domain events (unit 06) for side effects and integration is orthogonal — you can do that with a conventional state-stored aggregate that never persists its event history at all; the two are frequently confused because they use the same event types conceptually.

How do you handle querying "current state" efficiently in an event-sourced system, given replaying the whole stream every time would be slow?

Two standard techniques, often combined: periodic snapshots (store the folded state every N events so replay only needs to start from the last snapshot forward) and CQRS-style projections (a separate, denormalized read model kept up to date as events arrive, queried directly instead of ever replaying). Most production event-sourced systems use projections for anything read-heavy and only fall back to full replay for the aggregate's own write-side consistency check.

What happens when you need to change the shape of an event type that's already been persisted thousands of times?

You version the event type and write an "upcaster" — a small transform that reads the old shape and produces the new one on the fly during deserialization — so old events keep working without a destructive migration of the event store itself; the event store is append-only by design, so you add new event versions going forward rather than rewriting history. This is genuinely harder than an EF Core migration and is one of the real, ongoing costs of the model.

What's the difference between Marten and EventStoreDB, at a decision-making level?

Marten builds event sourcing (and general document storage) on top of PostgreSQL, which means a team already running Postgres gets event sourcing without adding a new database technology to operate; EventStoreDB is a purpose-built event store database with its own operational footprint and stream-native features. The practical decision driver is usually "do we want one more infrastructure component to run and monitor" versus "do we want the more event-native tooling" rather than a large functional gap for typical use cases.

Can you mix event-sourced and conventional state-stored aggregates in the same bounded context?

Yes, and it's common — event sourcing is applied per-aggregate-type based on whether that specific aggregate actually needs the audit/temporal/projection benefits, not as an all-or-nothing decision for a whole bounded context. A core aggregate with real audit or replay requirements might be event-sourced while supporting aggregates in the same context stay conventional.

How would you test business logic in an event-sourced aggregate — what does a typical test look like?

The canonical shape is "given these prior events, when this command is handled, then these new events are produced" — you build the aggregate via FromHistory with a fixture list of past events, invoke the method under test, and assert on the newly raised events (and optionally the resulting state), never touching a real event store. This maps directly to Given-When-Then and is one of event sourcing's genuine testing advantages.

What's a concurrency conflict in an event-sourced system, and how is it detected without a [Timestamp]-style column?

Each stream tracks its own version (the number of events appended so far); a command is loaded against a known version, and appending new events includes an expected-version check — if another process appended events in between, the append is rejected and the command must be retried against the now-current stream, which is the event-sourcing equivalent of the optimistic-concurrency token from unit 04.

Why is event sourcing often paired with CQRS, even though the two are independently optional?

The event stream is naturally a great source to build multiple independent read projections from — since it's already the full history of what happened, projecting it into several different shapes for different read needs is close to free once the pipeline exists — which is exactly the read-side flexibility CQRS wants. They're commonly adopted together, but neither requires the other: you can do CQRS with a conventional database (unit 07), and you can event-source without maintaining more than one read model.

What's the single biggest reason a team should NOT adopt event sourcing for a given aggregate?

If there's no real requirement for full history, temporal queries, or multiple independently rebuildable projections, event sourcing adds meaningful complexity (snapshotting, event versioning, a less familiar query story) with no corresponding payoff — a conventional state-stored aggregate, optionally with an audit table, delivers the same business value with far less operational and cognitive overhead. The decision should be justified by a concrete requirement, not general architectural enthusiasm.

How does GDPR-style "right to erasure" interact with an append-only event store that's supposed to be immutable history?

Genuine tension: you typically can't delete or rewrite historical events without undermining the audit guarantee that's often the whole reason for event sourcing, so the common resolution is crypto-shredding — store personal data encrypted with a per-subject key, and "erase" by discarding the key, leaving the event structurally intact but the personal payload permanently unreadable. This needs to be designed in from the start; retrofitting it onto an existing event store is painful.

A team wants event sourcing purely to get "time travel debugging" in production. Is that alone a good justification?

It's a real and sometimes valuable benefit, but weigh it against cheaper alternatives first — structured logging, distributed tracing, and periodic state snapshots often answer "what led to this bad state" well enough without committing the whole aggregate to event-sourced persistence. It's a good supporting reason once other requirements (audit, projections) already justify the move, but a thin justification on its own given the ongoing cost of event schema evolution.

09 · Modular Monoliths & Team Boundaries

The industry's default architectural instinct swung hard toward microservices in the 2015-2020 period, largely on the strength of DDD's own bounded-context concept — "each bounded context should be its own deployable service" felt like the natural conclusion. By the mid-2020s the pendulum swung back, not because bounded contexts stopped being useful but because teams learned the hard way that a service boundary is an operational commitment (network calls, independent deployment, distributed tracing, data consistency across service boundaries) layered on top of the modeling commitment a bounded context already is — and paying the operational cost before you actually need independent scaling or independent deployment cadence is usually a net loss. The modular monolith is the resulting synthesis: keep the bounded contexts DDD asks for as genuinely separate modules — separate namespaces/projects, no direct references to another module's internal types, communication only through each module's public contracts or in-process events — but deploy them all as one process, one database (with schema-per-module or at least logically separated tables), one deployment pipeline. You get the modeling discipline of bounded contexts without paying for distributed systems until a real, measured need (a module that genuinely needs independent scaling, a team that genuinely needs to deploy independently) appears.

This is also where DDD stops being purely a software-design discipline and meets Conway's Law — "organizations design systems that mirror their own communication structure" — and its prescriptive counterpart, Team Topologies (Skelton & Pais): a bounded context is most successful when it's owned end-to-end by one team, because the ubiquitous language (unit 01) only stays coherent when the people who use it in conversation are the people who write the code that embodies it. A context split across two teams' code ownership tends to develop two dialects of the same language and a constant negotiation overhead; a context that's too large for one team to hold in their heads collectively tends to develop the internal inconsistency of "several sub-languages wearing one name." Team Topologies' four team types (stream-aligned, platform, enabling, complicated-subsystem) give a vocabulary for deciding who should own which bounded context and where the collaboration/interface friction is deliberate versus accidental — the "team-first" reading of bounded contexts (design the team, and let the context boundary follow) is now at least as common in practice as the "model-first" reading DDD originally emphasized.

Interview Q&A

Does DDD require microservices? Correct the common misreading.

No — DDD's bounded context is a modeling boundary about where a ubiquitous language stays consistent, and says nothing about deployment topology; the idea that "each bounded context = one microservice" was an industry inference from the mid-2010s, not something Evans' book asserts. A bounded context can be a module inside a monolith just as validly as a standalone service, and the choice between them is an operational decision made independently of the modeling decision.

What specifically makes a modular monolith different from just "a monolith with folders," and how do you keep it from decaying into the latter?

The difference is enforcement: a modular monolith has module boundaries that are checked, not just organized — no direct references to another module's internal namespaces, communication only through published contracts or in-process events, ideally verified by an automated architecture test that fails the build on violation. Without that enforcement mechanism, folder-level organization erodes within a few quarters as deadline pressure makes "just reach across and call that internal method" the path of least resistance.

State Conway's Law and explain its practical implication for how you'd draw bounded context boundaries in a new project.

Conway's Law says a system's structure ends up mirroring the communication structure of the organization that builds it — in practice, this means you should draw bounded context boundaries with an eye to what team topology you actually have or intend to build, because a context boundary that cuts across a team's natural communication pattern will be fought by that structure regardless of how clean the model is on a whiteboard. It's a reason to design org structure and context boundaries together, not sequentially.

What are Team Topologies' four team types, and how does a "complicated-subsystem team" relate to a bounded context?

Stream-aligned (owns a slice of business value end-to-end), platform (provides self-service capabilities other teams consume), enabling (temporarily helps a team build a capability, then steps back), and complicated-subsystem (owns a piece of genuine deep technical complexity, like a pricing engine, that needs specialist knowledge). A complicated-subsystem team often maps naturally onto a bounded context that's a core domain (unit 01) requiring deep specialist modeling that a general stream-aligned team shouldn't be expected to hold.

How would you decide whether a module in your modular monolith is ready to be extracted into its own service?

Look for a concrete, already-felt pain: the module needs to scale independently of the rest (different load profile), a separate team needs to deploy it on its own cadence without coordinating releases with everyone else, or it needs a genuinely different technology stack — extracting before any of these pains exist just adds distributed-systems cost for no offsetting benefit. The module boundary you already enforced in code (the try-it above) is exactly what makes the eventual extraction mechanical rather than a rewrite.

Can two modules in a modular monolith share the same database tables directly?

They shouldn't reach into each other's tables directly — the same "no reaching into another context's internals" rule applies to data as to code, so each module should own its own tables (or schema) and expose data to other modules only through its own code's contracts, even though all the tables physically live in one database. Direct cross-module table access is exactly the kind of boundary violation that's invisible until it blocks an eventual service extraction.

What's the "distributed monolith" anti-pattern, and how does it relate to this unit?

It's what you get when you extract services along the wrong boundaries — usually technical layers (a "data service," a "business logic service") rather than bounded contexts — so the services must be deployed together anyway because they're too tightly coupled to release independently, but you now pay full network/distributed-systems cost for no autonomy benefit. It's the worst-of-both-worlds outcome the modular-monolith-first approach is specifically trying to avoid.

A skeptical team lead says "modular monoliths are just an excuse to avoid doing microservices properly." How do you respond?

Reframe it around evidence: microservices are a valid answer to specific operational needs (independent scaling, independent deploy cadence, polyglot requirements), and a modular monolith is the right default until those needs are actually measured and present — starting monolith-first with enforced module boundaries doesn't preclude extracting services later, and in fact makes a well-justified extraction easier because the seams are already clean. It's not avoidance, it's sequencing the investment to match actual need.

How do domain events (unit 06) work differently across modules in a monolith versus across services?

Within a modular monolith, cross-module domain events can often be dispatched in-process (still going through published contracts, not internal types) and can even participate in the same database transaction if strong consistency is genuinely needed — a choice unavailable across real service boundaries, which are forced into eventual consistency via the outbox pattern. Choosing in-process synchronous dispatch versus deferred/eventual dispatch, even within one monolith, should still be a deliberate decision based on whether the two modules' consistency truly needs to be atomic.

What's a practical first step to introduce module boundaries into an existing "big ball of mud" .NET monolith without a rewrite?

Pick the clearest, highest-value candidate bounded context (often the core domain), identify its current entry points, and start routing new work through explicit interfaces while leaving legacy call paths alone until they're touched anyway — add an architecture test that only checks the new boundary, so it can't regress, without attempting to retrofit the whole codebase's boundaries at once. This mirrors the incremental Anticorruption Layer approach from unit 02.

10 · Testing the Domain Model

A well-layered domain model (unit 05) pays for itself most visibly in testing: because the domain has no dependency on EF Core, HTTP, or any infrastructure, testing an aggregate's business rules is pure object construction and method calls — no database, no mocks, no test containers, no WebApplicationFactory. This is the fastest, cheapest, most valuable layer of the test pyramid for a DDD codebase, and it should be the largest by count: construct the aggregate (or use a small builder/factory to keep tests readable), call the method under test, assert on the resulting state or the domain events it raised (unit 06). A common and effective style is Given-When-Then, expressed directly as test structure rather than a BDD framework requirement: given this aggregate state, when this method is called, then this happens — the same shape unit 08 showed for event-sourced aggregate tests, but it applies equally to conventional state-stored aggregates.

The Specification pattern earns its place here as a testing and reuse tool, not just an application-layer concern: a specification is an object encapsulating a business predicate — "is this order eligible for free shipping," "is this customer in good standing" — that can be evaluated in-memory against a domain object directly in a unit test, translated to a LINQ/SQL query for a repository, and reused across both without duplicating the rule. This solves a real pain point: without it, the "is eligible" logic tends to get written once as a LINQ expression in a repository query (fast, but only testable through the database) and once again as a hand-written if in a validation method (testable, but a second place the rule can drift out of sync with the first). One well-tested specification object, used both ways, closes that gap. Where the domain model does need infrastructure (a repository, a payment gateway) inside a use case, that's the application-service test's job (unit 05) — fake or in-memory implementations of those interfaces, testing orchestration rather than business rules a second time.

Interview Q&A

Why should domain unit tests be the largest layer of the test pyramid in a DDD codebase, by count?

Because they're the cheapest to write and run — no infrastructure, no async waiting on a database or network — and because a properly layered domain model (unit 05) has genuinely no dependency that would force a test to reach outside pure objects. A large base of fast domain tests gives the fastest feedback on the logic that changes most often (business rules), leaving the slower, more expensive layers to cover what only they can: real persistence mapping, real HTTP wiring, real end-to-end flows.

What's the Specification pattern, precisely, and what specific duplication problem does it solve?

It's an object that encapsulates a business predicate in a form that can be evaluated in-memory (as a Func<T,bool> or similar) and also translated into a query expression (LINQ Expression<Func<T,bool>>, then SQL) — solving the specific problem where the same rule would otherwise be written twice: once as an in-memory if for validation, once as a database query filter, with no guarantee the two stay in sync as the rule evolves.

What's the "ice-cream cone" anti-pattern, and how would you diagnose it's happening on a team you've just joined?

It's an inverted test pyramid — few or no fast unit tests, most coverage carried by slow integration/E2E tests — usually caused by business logic living somewhere (controllers, an anemic domain, application services) that can't be tested without infrastructure. Diagnose it by checking the CI run time and the ratio of test types: if the suite takes many minutes and almost every test spins up a database or an HTTP server, that's the signature, and the root cause is almost always in unit 05's layering, not in testing tool choice.

How do you unit test a domain service (unit 01) that coordinates two aggregates, without hitting a repository?

Construct both aggregate instances directly in the test (no repository involved at all), pass them into the domain service's method, and assert on the resulting state or events — a domain service's dependencies, if it has any beyond the aggregates themselves, should be other domain-layer abstractions, not infrastructure, so the same "no mocks needed" property from aggregate testing carries over.

What should an application-service (use-case) test fake, and what should it NOT re-test?

It should fake the repository interfaces (an in-memory implementation is usually enough — no mocking framework needed for something this simple) so the test can verify the orchestration sequence — load, call the domain, save — without a real database; it should not re-assert the business rule's correctness in detail, since that's already covered by the domain unit tests, or the application test becomes redundant and brittle to any change in the rule's exact behavior.

How would you approach testing a value object like Money (from unit 03)?

Directly and thoroughly, since it's pure logic with no dependencies at all: construction validation (rejecting a negative amount or mismatched currency), equality (two Money instances with the same amount and currency are equal, per value-object semantics), and any operators/methods it exposes (addition across matching currencies, rejecting addition across mismatched ones) — this is the cheapest, highest-value test surface in the whole model, and skipping it because "it's just a value object" is a missed opportunity.

Should you unit test private methods on an aggregate directly?

No — test through the aggregate's public API (the methods that represent real behavior, like Submit() or AddLine()) and let the assertions on resulting state or raised events cover what the private methods do internally; testing private methods directly (via reflection or by making them internal "for testability") couples the test suite to implementation details that should be free to change as long as the public behavior stays correct.

How do integration tests for a repository differ in purpose from the domain unit tests for the aggregate it persists?

The repository integration test verifies persistence mechanics — does saving and reloading an aggregate produce an equivalent object graph, are optimistic-concurrency tokens (unit 04) enforced correctly, does the EF Core mapping round-trip value objects correctly (unit 03) — while the domain unit test verifies business rules with no persistence involved at all; a repository test that also re-asserts business logic is testing the same thing twice, slower, in the wrong layer.

What test-first approach works well for a new aggregate's invariants, and why does DDD's explicit invariant language make TDD easier here?

Because DDD pushes you to name invariants explicitly (unit 04) — "an order cannot be submitted with no lines," "a shipment cannot exceed the carrier's weight limit" — each invariant translates directly into a test-first assertion (write the failing test asserting the exception, then implement the guard) before any persistence or UI exists at all; this is a natural fit for outside-in or classic TDD specifically because the domain layer has no dependencies to stub out first.

A code reviewer asks why a PR added an integration test for something that's "just a getter." What's the right response?

If it's a genuine pass-through getter, the integration test is likely unnecessary ceremony and the reviewer's instinct is right — push back on tests that don't exercise a decision or a boundary; the useful question to ask instead is whether there's a real invariant or persistence-mapping concern hiding behind what looks like a plain getter, and if not, cut the test rather than defend it out of habit.

11 · Anti-Patterns & Legacy Adoption

The single most-cited DDD anti-pattern, and the one most worth being able to name and diagnose fluently, is the anemic domain model — entities that are just property bags (public getters and setters, no behavior) with all the actual business logic living in "service" classes that operate on them from the outside. Fowler called this out explicitly as an anti-pattern, not a neutral style choice: it looks object-oriented (you have classes called Order and Customer) but behaves procedurally (the logic is organized around functions, not around the objects the ubiquitous language actually talks about), and it directly defeats DDD's core value — the model stops being a place where business rules are discoverable and enforced, because nothing stops any code anywhere from setting an Order's Status to Submitted without ever validating it has lines. This is usually not a one-time design mistake but a slow drift: a model starts rich, then a deadline pressures someone into adding a public setter "just this once," and the invariant it was protecting quietly stops being enforced everywhere except the one call site the original author remembered to guard.

The second major anti-pattern is over-engineering CRUD — applying the full weight of aggregates, domain events, repositories, and a dedicated bounded context to a genuinely simple lookup-table-style feature ("manage a list of shipping carriers") that has no real invariants, no real domain logic, and would be better served by a straightforward CRUD endpoint over a simple data model. DDD's own vocabulary anticipates this: the whole point of separating core, supporting, and generic subdomains (unit 01) is permission to apply full tactical DDD only where the complexity is real, and to be unapologetically simple everywhere else. A team that applies aggregates-and-repositories ceremony uniformly across an entire codebase, core domain and admin screens alike, has usually skipped the strategic step (subdomain classification) and jumped straight to tactical patterns as a checklist. Both anti-patterns, despite looking opposite, come from the same root cause: not matching the modeling investment to where the actual business complexity lives.

Interview Q&A

Define the anemic domain model anti-pattern and explain precisely why Fowler considers it an anti-pattern rather than a legitimate style choice.

It's a model where entities carry only data (public getters/setters) with all behavior extracted into external "service" classes — Fowler's objection is that this defeats the purpose of object orientation and domain modeling both: the objects look domain-shaped but no invariant is actually enforced by them, since any code anywhere can mutate their state directly without going through a method that could validate the change. It's not "simpler OO," it's OO's behavioral encapsulation benefit discarded while keeping its structural cost.

How do you spot an anemic domain model in a code review, quickly?

Scan the entity classes for public setters on anything that represents a business-meaningful state transition (an order's status, a shipment's tracking state) — if setting it is a one-liner assignment from anywhere in the codebase with no accompanying validation, that's the signature; then check whether a "manager" or "service" class contains the actual conditional logic that decides when that state should change, which confirms the diagnosis.

What's "over-engineered CRUD," and how does DDD's own vocabulary give you the tool to avoid it?

It's applying full tactical DDD ceremony — aggregates, repositories, domain events, a dedicated bounded context — to a feature with no real business complexity or invariants, adding cost with no corresponding benefit. DDD's strategic step (classifying core, supporting, and generic subdomains, unit 01) exists precisely to license simplicity: generic and most supporting subdomains should stay as plain CRUD, and only the core domain (and the supporting subdomains with genuine complexity) earn the full tactical toolkit.

What's the "God aggregate" anti-pattern and how do you fix one that already exists in production?

It's an aggregate that's grown to reference most of the object graph, usually because its boundary was drawn from what was convenient to load via EF Core navigation properties rather than from actual transactional consistency needs (unit 04) — the fix is identifying the true invariants that must be atomic, keeping only those inside the aggregate, and moving everything else to be referenced by id and loaded/updated separately, migrated incrementally rather than in one big rewrite given the risk of touching a heavily-used aggregate all at once.

What's "Smart UI" as an anti-pattern, and why does Evans list it as a legitimate anti-pattern rather than always condemning it outright?

Smart UI puts all logic directly in the UI/controller layer with no separate domain or application layer at all — Evans actually lists it as a legitimate, deliberate choice for genuinely simple, short-lived, or low-complexity applications where the overhead of proper layering wouldn't pay for itself; it becomes an anti-pattern specifically when applied to a system with real, growing business complexity that needs the discoverability and reuse a real domain model provides.

How would you introduce tactical DDD into a legacy .NET codebase that's a Big Ball of Mud, without a rewrite?

Start with subdomain classification (unit 01) to find the actual core domain buried in the mud, then apply an Anticorruption Layer (unit 02) around just that piece so new work can build a clean model behind it while the rest of the legacy code continues unchanged — extract behavior from the surrounding "service" classes onto rich entities incrementally, one invariant at a time, verified by the fast domain unit tests from unit 10, rather than attempting a big-bang rewrite that risks the business logic hidden in the mud along the way.

A team lead says "our domain model is anemic, but our test coverage is high, so it's fine." How do you respond?

High test coverage over an anemic model usually means the tests are asserting against the "service" classes' orchestration logic, not against invariants enforced by the entities themselves — coverage numbers don't distinguish "we tested that this scenario currently produces this output" from "the model makes the invalid state impossible to reach at all"; the latter is what a rich domain model buys you, and no amount of external test coverage substitutes for state that simply cannot become invalid because the object's own API doesn't allow it.

What's the risk of over-applying DDD's strategic patterns (bounded contexts, context maps) to a small team or a small system?

Strategic DDD's ceremony (formal context maps, dedicated Anticorruption Layers, multiple bounded contexts each with its own model) pays off when a system is big enough or has enough independent teams that language and model actually do diverge across parts of it; for a system one small team can hold entirely in their heads, a single shared model with no formal context boundaries is often correct, and imposing the full strategic toolkit anyway is ceremony without a matching problem to solve.

How do you distinguish "this feature genuinely needs an aggregate" from "this feature is being over-engineered," in a design review?

Ask what invariant would be violated if the naive CRUD version were built instead — if there's a genuine, nameable rule (an order can't be submitted empty, a shipment can't exceed a weight limit) that a plain property-bag model would let slip through, that's the aggregate's justification; if the honest answer is "nothing bad would happen, it's just good practice," that's a sign the ceremony isn't earning its cost for this particular feature.

What's the most common way a rich domain model degrades back into an anemic one over time, and how do you guard against it?

Incrementally: a deadline pressures someone into adding a public setter "just this once" to unblock a feature, bypassing the method that enforces an invariant, and the pattern repeats until most invariants have at least one unguarded back door. Guarding against it is mostly a code-review discipline (flag any new public setter on state that has a corresponding business rule) plus, where the tooling allows, encoding the rule so it genuinely can't be bypassed — private setters with EF Core backing-field mapping, immutable value objects, factory methods that are the only way to construct valid instances.

Architecture & ecosystem decisions

How do you decide whether a new system warrants DDD's tactical patterns at all, versus a simpler CRUD architecture?

Start with the strategic question, not the tactical one: does this system have a core domain with genuine, non-obvious business rules that will change over time and need to be discoverable in code, or is it mostly data entry and display? If it's the latter, DDD's tactical ceremony (unit 11) is a cost without a matching benefit; the decision should follow from the subdomain classification (unit 01), not be applied as a default posture to every new project regardless of its actual complexity.

How would you explain the relationship between DDD, Clean Architecture, and microservices to someone who thinks they're the same thing?

DDD is a modeling discipline (how to structure the domain's concepts and language); Clean/Onion/Hexagonal Architecture is a layering discipline (how to keep that model isolated from infrastructure, unit 05); microservices is a deployment/operational topology decision. They compose well together but are independently adoptable — you can do rich DDD tactical modeling inside a single-layer script, and you can deploy microservices with anemic models in every one of them; conflating the three is one of the most common sources of cargo-culted architecture.

What's your position on using DDD tactical patterns with a NoSQL document database instead of a relational one?

It often fits naturally — an aggregate's consistency boundary maps closely onto "what should live in one document," since most document databases only guarantee atomic writes within a single document, which is exactly the granularity DDD already asks you to reason about (unit 04); the friction point is querying across aggregates, which needs the same CQRS-style projection thinking (unit 07) regardless of database technology.

How do you keep a bounded context's model from silently drifting as the team rotates or grows over a couple of years?

The ubiquitous language has to be actively maintained, not just documented once — glossaries go stale, but a living glossary tied to actual code (a domain project whose class and method names are the glossary) stays honest because a mismatch is a compile error or a failing test, not a documentation review; pairing that with regular model-review conversations involving actual domain experts is what keeps the language and the code from diverging as people rotate through the team.

When would you deliberately choose NOT to use an Anticorruption Layer when integrating with a legacy system?

When the legacy system's model is genuinely simple, stable, and unlikely to conflict with your own — or when the integration is small enough and short-lived enough that the translation-layer cost isn't worth paying; an ACL is a defensive investment against a growing, evolving core domain being corrupted by a messy upstream model, and applying it to every integration regardless of scale is itself a form of over-engineering (unit 11).

Security

How does putting invariant enforcement inside the aggregate improve your system's security posture, not just its correctness?

Every invariant enforced only outside the entity (in a controller, a service) is a security control that depends on every caller remembering to invoke it — a new endpoint, an admin script, a data-fix task can all bypass it; enforcing the rule inside the aggregate's own methods means it's structurally impossible to violate through any code path, which is a much stronger guarantee than "we validate on every controller action" and closes an entire class of authorization/business-rule bypass bugs.

Where should authorization checks (can this user submit this order) live relative to the domain model?

Authorization ("is this actor allowed to do this") is usually an application-layer concern, evaluated before invoking the domain method, since it depends on identity and permissions that aren't part of the ubiquitous language's business rules; business invariants ("can this order, regardless of who's asking, be submitted in its current state") belong on the aggregate. Conflating the two by embedding role checks into aggregate methods couples the domain model to an authorization model that will change for reasons unrelated to the business rules themselves.

What's the security risk of an integration event carrying more data than the consumer strictly needs?

Over-sharing in a published event silently widens the blast radius of a data exposure — every current and future consumer of that event topic now has access to fields they never asked for, and revoking that later means a breaking contract change (unit 06); the Open Host Service discipline of publishing a deliberately minimal, purpose-built contract is as much a security practice as an integration-design one.

Performance & debugging

An aggregate load is slow because EF Core is eagerly including a large object graph. How do you diagnose and fix it without breaking invariant enforcement?

First confirm whether the whole graph is actually needed to enforce the invariants for the operation being performed — if a command only needs a subset of the aggregate's data, that's a signal the aggregate boundary might be too large (unit 04), not just a query-tuning problem; if the boundary is genuinely correct, the fix is selective loading (splitting the aggregate's read path for commands that need the full graph versus queries that don't, via the CQRS read-side from unit 07) rather than loosening the write-side's own loading, which would risk enforcing invariants against incomplete state.

How would you profile whether a domain event dispatch pipeline is a bottleneck in a high-throughput system?

Separate the measurement into the three stages that can each independently bottleneck: raising the event (in-memory, should be near-free), the outbox write (adds one row to the same transaction, measure its overhead directly), and the background publisher's throughput to the broker (often the actual bottleneck under load, tunable via batching and poller concurrency) — treating "events are slow" as one undifferentiated problem usually leads to optimizing the wrong stage.

You're seeing intermittent DbUpdateConcurrencyException spikes in production. How do you distinguish a real design problem from expected contention?

Check whether the spikes correlate with genuine concurrent business activity on the same aggregate instance (multiple users editing the same order at once — expected, and the retry-with-reload strategy from unit 04 is the correct response) versus a single logical operation that's internally racing itself (a background job and a user action both touching the same aggregate without coordination, or a retry loop retrying the wrong unit of work) — the latter is a design bug to fix, not contention to absorb.

How do you debug a read model that's drifted out of sync with the write side in an eventually-consistent (CQRS + events) system?

Trace the specific event that should have updated the read model and check each stage it passed through — was it raised, did it reach the outbox, did the publisher deliver it, did the projection handler process it without error and without silently swallowing an exception — eventual consistency bugs are almost always a break in one link of that chain, and structured logging with a correlation id carried through every stage is what makes this traceable rather than guesswork.

Tooling

What tools would you introduce to keep architecture/layering rules (unit 05, unit 09) enforced automatically rather than relying on code review discipline alone?

Architecture testing libraries (NetArchTest, ArchUnitNET) that assert dependency-direction rules as part of the normal test suite and CI gate, so a violation fails the build rather than slipping through review; for module boundaries specifically, some teams also use separate assemblies/NuGet packages per module so the compiler itself enforces the boundary, which is stronger than a runtime test but has more ceremony to set up.

What's EF Core's role versus a hand-rolled data mapper in a DDD-styled codebase, and when would you choose the latter?

EF Core's flexibility (private setters, backing fields, owned/complex types, value converters) is usually enough to map a rich domain model without compromising it, which is why it remains the default choice for most .NET teams doing DDD; a hand-rolled mapper (or Dapper for the read side) earns its place when the mapping needs are unusual enough that fighting the ORM's conventions costs more than writing explicit mapping code, or when the read/write split from CQRS (unit 07) already has Dapper on the query side for performance reasons.

Would you recommend a dedicated event-sourcing framework (Marten, EventStoreDB) versus hand-rolling an event store on top of a regular database?

Reach for the framework once the team has confirmed event sourcing is genuinely justified (unit 08) — the hard parts (snapshotting, projections, optimistic concurrency on streams, event upcasting) are exactly the parts a mature framework has already solved and battle-tested; hand-rolling makes sense mainly for a narrow, well-understood use case where pulling in a new piece of infrastructure isn't worth it, but it's easy to underestimate the edge cases a framework already handles.

Legacy & migration reality

You've inherited a 10-year-old .NET codebase with no discernible domain model, entity classes are just EF Core mapping classes, and "business logic" is scattered across 40 controller actions. Where do you start?

Resist the urge to redesign everything at once — pick the single highest-value core-domain behavior, trace every place its rule currently lives (likely duplicated across several controllers), consolidate it onto a method on the entity, add domain unit tests for it (unit 10), and route the controllers through that method instead of reimplementing the check; repeat for the next-highest-value rule. This is deliberately slow and incremental because the codebase's existing behavior, bugs included, is often load-bearing in ways nobody has fully documented.

How do you get buy-in from a team that sees DDD as "academic" or "too much ceremony for our deadlines"?

Lead with a concrete, recent bug that a richer model would have prevented structurally rather than with terminology — "this invalid state got into production because nothing stopped it" lands better than a lecture on ubiquitous language; then propose the smallest possible pilot (one aggregate, one bounded context) with a clear, measurable before/after rather than asking for a wholesale architecture change up front. Ceremony objections are usually really about scope and risk, not about the ideas themselves.

How do you handle a bounded context boundary that turns out to be wrong after the system's already in production with real data?

Treat it like any other significant migration: identify the data and behavior that need to move to the corrected boundary, build the new model behind an Anticorruption Layer or a feature flag so both old and new can coexist during the transition, migrate data and traffic incrementally with the ability to roll back, and only remove the old boundary once the new one has run correctly under real load for a meaningful period. Discovering a wrong boundary is normal — Evans himself describes context boundaries as something you refine as understanding deepens, not something you're expected to get perfectly right up front.

What's your approach to reviewing a vendor's or contractor's code that claims to "follow DDD" but you suspect doesn't?

Check for the concrete signals from unit 11 rather than taking the label at face value: are there public setters on state that clearly has business rules attached, is there a "service" layer doing what should be aggregate behavior, do bounded context boundaries (if claimed) actually correspond to anywhere the language or team ownership genuinely diverges. The label "DDD" in a deliverable description is not evidence; the code's actual invariant enforcement is.

Judgment & scenario questions

A product manager wants a new feature that would require two aggregates to be updated atomically in one transaction. How do you handle the conversation?

Don't just say no — first check whether the aggregate boundaries are actually correct for the business's real consistency needs (maybe they should be one aggregate) or whether the "atomic" requirement is actually a UX assumption that eventual consistency (a brief, sub-second lag) would satisfy just as well from the user's perspective; most of these conversations resolve once the PM understands the actual user-facing consequence of eventual consistency, which is usually much smaller than "atomic" sounds.

You're asked to estimate how long it would take to introduce a bounded context split into a monolith ahead of a planned team split. What do you actually need to know before answering?

Whether the module boundary already exists in any enforced form (unit 09) or is purely conventional today, how tangled the data model is across the proposed split (shared tables, foreign keys crossing the boundary), and whether the split needs to happen before or can lag behind the team split — a team split ahead of a clean code boundary is workable short-term (one team temporarily owns code it doesn't have full boundary isolation over) but the estimate should be honest that "clean split" and "teams reorganized" are two different milestones, often on different timelines.

How do you decide, as the most senior engineer on a team, when to overrule a junior developer's DDD-purist objection to a pragmatic shortcut?

Distinguish shortcuts that violate a real invariant (never take these, regardless of deadline — that's exactly the anemic-model drift from unit 11) from shortcuts that just look "impure" relative to a textbook pattern (a slightly pragmatic aggregate size, an EF Core entity that's also the domain entity) — the latter are legitimate trade-offs a lead should be comfortable making explicitly, ideally with the junior developer walked through the actual reasoning so the exception doesn't read as "the rules don't matter."

What would you look for in the first 30 days after joining a team to assess whether their DDD is real or cargo-culted?

Sit in on a conversation between a domain expert and an engineer and check whether the vocabulary used matches the class and method names in the actual code; read the most business-critical aggregate's code and check whether its invariants are enforced in methods or just implied by convention; and check whether bounded context boundaries (if claimed) correspond to any real divergence in language, team ownership, or deployment, or are just folder names.

How would you mentor a mid-level engineer who writes technically correct code but keeps missing where business logic should live?

Have them narrate, for a piece of logic they just wrote, which object in the ubiquitous language "owns" the concept the code is expressing — most misplacement comes from defaulting to "put it in the nearest service class" without asking that question first; pairing on a few real PRs specifically to ask "whose responsibility is this rule, in the business's own terms" builds the habit faster than a general lecture on layering.

13 · Night-Before Cheat Sheet

Read this once before you walk in. Every sentence is something you can say out loud with confidence, and every one connects back to a unit above if you need to go deeper.

  • DDD is a modeling discipline built on a shared ubiquitous language between engineers and domain experts, made concrete through Evans' Building Blocks (entities, value objects, aggregates, domain services, domain events) and made scalable through Strategic Design (subdomain classification, bounded contexts, context mapping) — it says nothing about deployment topology, and never required microservices.
  • Spend your strategic-design budget deliberately: classify subdomains into core (differentiating, worth deep modeling), supporting, and generic (buy or keep simple) before applying any tactical pattern — the single biggest anti-pattern is applying full aggregate/repository ceremony uniformly, core domain and admin CRUD alike.
  • An aggregate's boundary is drawn from true transactional invariants, never from EF Core navigation-property convenience; per Vernon, favor small aggregates referencing others by id, and treat cross-aggregate consistency as eventual, coordinated through domain events, not a shared transaction.
  • In .NET 10 / EF Core 10 (LTS since 2025-11-11), model value objects as C# record/record struct types mapped with complex types (ComplexProperty) for pure value semantics, reserving owned entity types for cases that genuinely need per-instance identity or independent querying — this is the current, version-precise answer, not owned types by default.
  • Enforce optimistic concurrency on every mutable aggregate with a [Timestamp]/rowversion column, catch DbUpdateConcurrencyException, and reload-and-retry — this is the default correct answer for concurrent edits, with pessimistic locking reserved for the rare case that genuinely can't tolerate a retry.
  • Keep the domain layer free of every infrastructure dependency (the Dependency Rule) — it defines the repository interfaces it needs, infrastructure implements them — and put transaction boundaries and orchestration, never business rules, in the application layer.
  • Separate in-process domain events (synchronous, same transaction) from integration events (asynchronous, published after commit via the transactional outbox pattern) — publishing directly to a broker inside the same transaction as the domain change is the classic dual-write bug.
  • MediatR went commercial in 2025 (v13+, license key via mediatr.io, contracts split into the free MediatR.Contracts) — know Wolverine and a hand-rolled mediator as the two live alternatives, and know that CQRS itself needs neither MediatR nor event sourcing nor a second database to be legitimate.
  • Event sourcing makes the event stream the system of record instead of an add-on — a deliberate, narrow choice for real audit/temporal/multi-projection needs, not a default extension of "we already raise domain events," because of the real cost in replay performance, snapshotting, and event-schema versioning it brings.
  • Modular monoliths are now at least as common a default as microservices for new .NET systems — keep bounded contexts as enforced (architecture-tested) code modules, one deployment, one database, and extract a service only once independent scaling or deploy cadence is a measured, not speculative, need; draw the boundaries with Conway's Law and team ownership in mind, not model purity alone.
  • Domain unit tests — pure object construction, no database, no mocks — should be your largest test layer by count; if most of your coverage lives in slow integration tests, that's a layering smell (an anemic model), not a testing-strategy choice.
