Domain-Driven Design (.NET)

cheatsheet · .NET 10.0.12 (LTS) · released 2026-09-08

This card maps DDD's tactical building blocks and strategic tools onto the current .NET stack; since DDD itself carries no version, the version facts here pin to today's .NET 10 LTS and its ecosystem rather than to the pattern language. It favors the C# 14 / EF Core 10 idioms a lead engineer should reach for over the legacy patterns still common in existing codebases, including the recent move of MediatR and MassTransit to commercial licensing. Every claim below is dated to the release that made it true.

01Building blocks

C# 14 field keyword
Entity
Identity-based equality; mutable over its lifetime; compare by Id, never by value. Behaviour lives on it, not in a service.
Value object
Structural equality, immutable, no identity. Use a C# record/record struct, or a source-generated wrapper (unit 02) instead of a bare primitive.
Aggregate root
The one entity a repository loads and saves; every invariant that must hold *right now* lives inside its boundary. Reference other aggregates by Id, never by object reference.
Aggregate boundary rule
One aggregate = one transaction = one lock. If two "invariants" never need to be consistent in the same instant, they belong to different aggregates.
Validated setter, C# 14
The field keyword lets a property validate without a hand-declared backing field.
// Value object: immutable record, structural equality for free
public sealed record Money(decimal Amount, string Currency)
{
    public static Money Zero(string currency) => new(0m, currency);
}

// Entity / aggregate root with a C# 14 validated auto-property
public sealed class Order
{
    public OrderId Id { get; }
    public Money Total
    {
        get;
        private set => field = value.Amount >= 0
            ? value
            : throw new ArgumentOutOfRangeException(nameof(value), "Total cannot be negative.");
    } = Money.Zero("USD");

    private readonly List<OrderLine> _lines = new();
    public IReadOnlyList<OrderLine> Lines => _lines;
}

02Invariants & strong IDs

Ardalis.GuardClauses · Vogen
Guard clauses
Ardalis.GuardClauses (v5.0.0, 2024-09-30) — fluent precondition checks at the top of constructors/methods instead of scattered if blocks.
Strongly-typed IDs
Vogen source-generates value objects (CustomerId, Money) from primitives, blocking default, bare new, and reflection bypass at compile time. Kills primitive obsession without hand-rolled wrapper boilerplate.
Construction
Private constructor + a Create/Reconstitute factory that returns a Result or throws — never a public parameterless constructor on a domain type.
Setter visibility
Public getters, private setters mutated only through named methods (Ship(), Cancel()) that enforce invariants and raise domain events (unit 03).
using Ardalis.GuardClauses;

public sealed class Customer
{
    public CustomerId Id { get; }
    public string Email { get; private set; }

    private Customer(CustomerId id, string email)
    {
        Id = id;
        Email = Guard.Against.NullOrWhiteSpace(email);
    }

    public static Customer Create(CustomerId id, string email) => new(id, email);
}

// Vogen: source-generated strongly-typed id, no runtime allocation cost
[ValueObject<Guid>]
public readonly partial struct CustomerId { }

03Domain events

EF Core SaveChanges events
Raise
An aggregate method appends to its own _domainEvents list; it never calls a bus, mediator or dispatcher directly — that would couple the domain model to infrastructure.
Collect
A shared Entity/AggregateRoot base class exposes DomainEvents read-only and a protected Raise(...)/ClearDomainEvents() pair.
Dispatch
An EF Core SaveChangesInterceptor (or a mediator pipeline step) walks tracked aggregates after SaveChangesAsync and publishes what they collected, inside the same transaction where possible.
Cross-process delivery
The outbox pattern: write the event row in the same DB transaction as the state change, then a separate relay publishes it — avoids the dual-write problem between DB commit and bus publish.
Library support
Wolverine ships a transactional inbox/outbox out of the box; MediatR needs a hand-built dispatcher; MassTransit's outbox needs the (now commercial, unit 05) package.
public abstract class AggregateRoot
{
    private readonly List<IDomainEvent> _events = new();
    public IReadOnlyList<IDomainEvent> DomainEvents => _events;
    protected void Raise(IDomainEvent e) => _events.Add(e);
    public void ClearDomainEvents() => _events.Clear();
}

// Dispatch after commit, from a SaveChangesInterceptor.SavedChangesAsync override
foreach (var agg in ChangeTracker.Entries<AggregateRoot>().Select(e => e.Entity))
{
    foreach (var evt in agg.DomainEvents) await _publisher.Publish(evt);
    agg.ClearDomainEvents();
}

04Repositories & specifications

Ardalis.Specification
Repository granularity
One repository per aggregate root, never per table and never one generic IRepository<T> for every entity — a fixed generic surface forces every aggregate through the same query shape.
Specification pattern
Encapsulate a reusable query (filter + include + sort + paging) as an object implementing ISpecification<T>; the repository takes the spec instead of exposing IQueryable<T> to callers.
Leaking IQueryable
Returning IQueryable<T> from a repository leaks the ORM (and, eventually, the schema) past the domain boundary — return materialized lists or apply a spec.
Read models
Queries for UI/reporting bypass the aggregate/repository entirely and hit the DB (or a projection) directly — CQRS's query side, unit 05.
public sealed class ActiveOrdersForCustomerSpec : Specification<Order>
{
    public ActiveOrdersForCustomerSpec(CustomerId id)
    {
        Query.Where(o => o.CustomerId == id && o.Status != OrderStatus.Cancelled)
             .Include(o => o.Lines)
             .OrderByDescending(o => o.PlacedAtUtc);
    }
}

// repository.ListAsync(new ActiveOrdersForCustomerSpec(customerId));

05CQRS & mediator

Wolverine · MediatR licensing
CQRS
Separate the write side (commands mutate one aggregate, return little or nothing) from the read side (queries return DTOs, skip the domain model entirely).
Mediator pipeline
A command/query handler wrapped by cross-cutting behaviours — validation, logging, transaction, outbox — resolved and invoked by a mediator instead of chained by hand in each handler.
MediatR licensing
Commercial since v13.0.0 (2025-07-02); current is 14.2.0 (2026-07-02). Tiers via mediatr.io: Standard $799/yr (≤10 devs), Professional $1,499/yr (≤50), Enterprise $6,399/yr (unlimited). Free "Community License" for orgs under $5M revenue and $10M raised (bundles AutoMapper).
Wolverine
MIT-licensed in-process command bus and out-of-process messaging from Jeremy Miller/JasperFx — the drop-in-shaped replacement teams are migrating to; adds built-in transactional inbox/outbox.
MassTransit licensing
Also went commercial: current 9.2.1 (2026-08-26) "must be licensed"; versions before the change remain under the old permissive OSS license.

06EF Core 10 mapping

EF Core 10 what's new
Value objects: complex types
EF Core 10 recommends complex types over owned entity types for value objects — they have real value semantics: copy on assign, compared by content, no shadow key.
Owned entity types (legacy)
Reference/identity semantics: customer.Billing = customer.Shipping silently does the wrong thing, and owned types never supported ExecuteUpdateAsync.
JSON-backed complex types
ComplexProperty(...).ToJson() maps a complex type straight to a JSON column — no manual converter.
Struct complex types
Complex types can now be readonly record struct, avoiding a heap allocation per value object per row.
ExecuteUpdateAsync
Now works against JSON columns and complex-type properties — bulk-update a Money/Address field without loading the aggregate.
Named query filters
Multiple, independently toggleable filters per entity (HasQueryFilter("softDelete", ...), HasQueryFilter("tenant", ...)) — combine soft-delete with multi-tenancy without one giant AND'd predicate.
modelBuilder.Entity<Order>(b =>
{
    b.ComplexProperty(o => o.Total);                 // value semantics, no owned-type identity
    b.ComplexProperty(o => o.ShippingAddress).ToJson(); // one JSON column, still strongly typed

    b.HasQueryFilter("softDelete", o => !o.IsDeleted);
    b.HasQueryFilter("tenant", o => o.TenantId == _tenant.Current);
});

07Context mapping

Fowler: Bounded Context
Bounded context
A boundary of linguistic and model consistency — "Order" means one specific thing inside it. It is a modelling boundary, not automatically a deployment boundary (unit 09).
Anti-corruption layer (ACL)
A translation adapter at the edge of your context that converts a legacy or upstream model into your ubiquitous language, so foreign concepts never leak inward.
Skipping the ACL
The most common context-mapping mistake: "just reuse their DTO for now" — the legacy model's shape becomes permanent because nothing forces the translation later.
Context mapping patterns
PatternUse when
Shared kernelTwo teams truly co-own one small, stable model (rare — creates coupling).
Customer / supplierDownstream team has influence over upstream's roadmap and priorities.
ConformistDownstream has no influence; it accepts the upstream model as-is.
Anti-corruption layerDownstream wants its own model and will pay to translate at the boundary.
Open host service / published languageOne upstream serves many consumers through a stable, documented contract.
Separate waysNo meaningful integration benefit — duplicate the small overlap instead.

08Ubiquitous language

Fowler: Ubiquitous Language
Ubiquitous language
A model-derived vocabulary shared by domain experts and code inside one bounded context — the class/method names in the code are the words the business uses.
Event storming
A workshop technique (orange stickies = domain events, in timeline order) used to discover bounded contexts and aggregate boundaries before writing a line of code.
Same word, two meanings
The classic smell that reveals a missing context boundary: "Customer" in Sales and "Customer" in Support silently mean different things, and one shared class is quietly wrong for one of them.
Glossary drift
A language that isn't reinforced in code review decays back into implementation jargon within a few sprints — treat the glossary as a living artifact, not a one-time deliverable.

09Monolith vs microservices

.NET microservices architecture guide
Bounded context = natural seam
Whether you ship one deployable or many, the bounded context is the unit that should never be split mid-boundary — splitting it creates a distributed monolith, not a service.
Modular monolith
Each bounded context is a separate project/assembly with internal types at its edges and an architecture test (e.g. a dependency-direction unit test) enforcing that other modules only reach it through its public contract.
When to extract a service
Split out only when a context needs its own scaling profile, its own deploy cadence, or its own team boundary (Conway's law) — not by default, and not speculatively.
Team topology
A service boundary that doesn't match a team boundary tends to need cross-team coordination for every change — the org chart leaks into the architecture either way.

10Gotchas & pitfalls

  • Anemic domain model — public setters everywhere, all logic in "services": a smell that behaviour has leaked off the aggregate.
  • Fat aggregate — loading unrelated data through one root to save a join kills performance; split by invariant, not by "everything sort of related."
  • Repository returning IQueryable<T> — leaks the ORM past the domain boundary; return materialized results or a specification instead.
  • Domain events raised but never dispatched — forgetting to wire the interceptor/pipeline step silently drops behaviour, with no exception to notice.
  • Upgrading MediatR blind — pulling v13+ without reading the license terms bills the team; pin to the last OSS 12.x or move to Wolverine first.
  • Owned entity types for money/address — EF tracks them by reference, so a.Address = b.Address doesn't behave like a value copy; use complex types (EF Core 10+) instead.
  • Anti-corruption layer skipped "to save time" — the legacy model's shape leaks in and never leaves.
  • Generic IRepository<T> for every entity — forces one query shape on every aggregate and defeats the specification pattern.
  • Value object with a public parameterless constructor — an EF materialization backdoor that bypasses every invariant you wrote.
  • Publishing the whole aggregate as an integration event — couples every consumer to your internal shape; publish a projected DTO in the published language instead.
