interview · .NET 10 (LTS) · released 2025-11-11

DDD interviews at lead/principal level rarely test whether you can define "aggregate" — they test whether you can draw a context map for a real system, defend an aggregate's boundary under concurrent load, and explain why a domain event delivered twice didn't corrupt anything. Work the map top to bottom: bounded contexts and aggregates come up in almost every architecture round and are exactly where a strong senior and a strong principal give the same vocabulary but a different depth of trade-off, while event sourcing and formal domain-model testing are reached only by some loops. Every implementation example targets .NET 10 (LTS), C# 14 and EF Core 10, and leans on two changes worth knowing cold: EF Core 10 now recommends complex types over owned entity types for value objects, because complex types finally have copy-by-value semantics instead of the hidden identity owned entities carry underneath; and MediatR — the de facto in-process mediator for CQRS in .NET — moved to a paid commercial license at v13 (mid-2025), which turned "do you still reach for MediatR" into a live judgment question. Assume Evans' and Vernon's vocabulary throughout; nothing here assumes a specific industry, employer or existing codebase.

01 Bounded contexts & context mapping

A bounded context is the boundary inside which a model and its language are internally consistent; context mapping is how you describe and negotiate the relationships between contexts that disagree. Interviewers open here because it is the one DDD idea that shows up whether or not the rest of the pattern language is used, and because getting it wrong — either one model for everything, or a context per table — predicts almost every other modeling mistake in the interview. At mid level you name the patterns; at senior you use them to negotiate a real integration; at principal you use them to carve services out of a monolith without a rewrite.

martinfowler.com: Bounded Context · docs: Identify domain-model boundaries for each microservice

What is a bounded context, and why does DDD insist on explicit boundaries? screener

A bounded context is the boundary within which a specific model and its ubiquitous language stay internally consistent — the same word can and often should mean something different once you cross it. DDD insists on the boundary because a single unified model for an entire enterprise is either too generic to be useful anywhere or too specific to be correct everywhere; splitting the model lets each team optimise its own language for its own problem instead of negotiating a compromise nobody needs. The boundary is conceptual and linguistic first — it usually becomes a module, a schema or a service, but that's a consequence, not the definition.

Example 
// Billing context: Customer means a payer.
public record Customer(CustomerId Id, string LegalName, PaymentMethod DefaultMethod, CreditLimit Limit);

// Support context: same real person, a different model entirely.
public record Customer(CustomerId Id, string DisplayName, SlaTier Tier, IReadOnlyList<TicketId> OpenTickets);

Follow-ups

  • How do you know a boundary is wrong? — You're constantly translating between two "versions" of the same concept for routine operations, or one team must ask another before making an everyday change.
  • Can one service contain more than one bounded context? — Yes, especially early on — the boundary is conceptual, not deployable; a service should never straddle two contexts, but a context can outgrow a service later.
  • Is a bounded context the same as a subdomain? — No — a subdomain is a problem-space concept (what the business does), a bounded context is a solution-space concept (how you modeled it); they often but don't have to line up one-to-one.

Wrong answer: "A bounded context is just a microservice." Conflating the modeling boundary with the deployment boundary leads either to fragmenting services down to single aggregates chasing "purity," or refusing to split a monolith because "there's only one service" — both wrong, for opposite reasons.

How do you decide where one bounded context ends and another begins? mid

You look for a seam in the language, not in the data: a place where the same noun starts carrying different attributes, different invariants, or a different rate of change, or where two groups of stakeholders use the word differently in the same meeting. A practical signal is team ownership — Conway's Law says the boundary that isn't reinforced by a team boundary tends to erode — and another is the lifecycle: things that are created, changed and retired together belong together. You don't get this right on paper; event storming or just walking the process end-to-end with domain experts surfaces the seams faster than staring at an ER diagram.

Example

In an e-commerce platform, "Product" in Catalog is a rich, marketing-owned description (title, images, category, SEO fields) that changes daily; "Product" in Inventory is a SKU with a quantity and a warehouse location that changes by the second. Modeling one "Product" class for both forces either the catalog team to wait on inventory's concurrency-heavy schema, or the inventory team to carry fields it never touches.

Follow-ups

  • What if the org doesn't have separate teams yet? — Model the seams anyway as module boundaries; the org will eventually organise around them, or the seams tell you it should.
  • Is data duplication across contexts a smell? — No, it's usually the point — each context keeps a local, denormalised copy of what it needs and stays loosely coupled to the source of truth.
  • How fine-grained can this get before it's silly? — When you're translating a term back and forth more than you're using it — the cost of the seam should be less than the cost of the ambiguity it removes.

Wrong answer: "Draw the boundary around each database table." Tables are an implementation detail; a boundary chosen by schema instead of language reliably cuts through the middle of a concept that should have stayed together (or fuses two that shouldn't).

Name the core context-mapping patterns and when each applies. mid

Context mapping patterns describe the political and technical relationship between two contexts, not just the technical one. Shared Kernel — two teams jointly own a small shared model, only viable with tight coordination. Customer/Supplier — a downstream team's needs are planned into the upstream team's backlog. Conformist — downstream just accepts the upstream model as-is, no negotiating power. Anticorruption Layer (ACL) — downstream translates the upstream model at the boundary and keeps its own model pure. Open Host Service / Published Language — upstream exposes a stable, documented protocol many consumers conform to. Separate Ways — no integration is cheaper than integration. Big Ball of Mud — the honest label for a legacy area with no discernible boundary at all.

Example

Integrating with a third-party payment gateway: you don't get a say in their model, so it's Conformist at best, and in practice you wrap their SDK behind an ACL so a gateway migration never touches your domain layer.

Follow-ups

  • When is Shared Kernel a bad idea? — Across more than two teams, or when either team ships independently — the coordination cost scales faster than the code it saves.
  • Difference between Conformist and ACL? — Conformist lets the upstream model leak in untranslated; an ACL pays the translation cost to keep it out. Same power imbalance, different amount of protection.
  • What's Open Host Service in .NET terms? — A versioned public API (REST/gRPC) plus a schema (OpenAPI/protobuf) that is the contract — consumers integrate against the contract, not your internals.

Wrong answer: Treating context mapping as purely a diagramming exercise. The patterns describe a power relationship between teams — picking the wrong one (agreeing to Shared Kernel when you have no influence over the other team's roadmap) is an organisational mistake that no amount of good code fixes.

What's the difference between a bounded context and a subdomain (core / supporting / generic)? mid

Subdomains classify the problem space: core is where your competitive advantage lives and deserves your best modeling effort and best people; supporting is necessary but not differentiating, worth a solid but unglamorous model; generic is solved-problem territory (auth, payments, email) you should buy or borrow rather than build. Bounded contexts classify the solution space — the models you actually built. They frequently align (one context per subdomain) but don't have to: a core subdomain might be split across two contexts as it grows, or a generic subdomain might be satisfied by a vendor SaaS with no bespoke context at all.

Example

For a logistics company: route optimisation is core (get it exactly right, invest heavily); billing is supporting (needed, not a differentiator); identity and access management is generic (buy Auth0/Entra ID rather than model it).

Follow-ups

  • Why does this classification matter for staffing? — It tells you where to put your best domain modelers and where a competent generalist (or a vendor) is perfectly adequate.
  • Can a generic subdomain still need a bounded context? — Yes, a thin one — even a bought identity provider needs an ACL translating its model into your own User/Actor concept.
  • Does "core" ever change? — Yes — what was a differentiator two years ago can commoditise; the classification is a snapshot, not a permanent label.

Wrong answer: "Subdomain and bounded context are basically the same word for the same thing." Using them interchangeably is exactly what leads teams to over-invest modeling effort in a generic subdomain because "it needs a bounded context too."

When is a Shared Kernel appropriate, and what does it cost? senior

A shared kernel is appropriate when two teams' domains genuinely overlap in a small, stable, low-change area — a common example is a shared Money or Address value object library — and both teams are willing to treat any change to it as a cross-team change with joint review. It's not a shortcut to avoid duplicating a few classes; it's a standing coordination cost that both teams pay forever. The moment one team needs to evolve the shared piece in a way the other doesn't want, the kernel is actively harmful, because now nobody can move without the other's sign-off.

Example 
// Shared.Kernel package, versioned and owned jointly, referenced by both services.
public readonly record struct Money(decimal Amount, string CurrencyCode)
{
    public static Money operator +(Money a, Money b) =>
        a.CurrencyCode == b.CurrencyCode
            ? a with { Amount = a.Amount + b.Amount }
            : throw new InvalidOperationException("currency mismatch");
}

Follow-ups

  • What's the alternative if two teams keep diverging? — Fork it: each team keeps its own copy and accepts the duplication — cheaper than perpetual negotiation once the models genuinely diverge.
  • How do you keep a shared kernel small? — Only true value objects with no business behaviour opinions attached — Money, not Order.
  • Who owns the shared kernel's CI? — Ideally both teams' changes to it run both teams' test suites before merge — if that's not feasible, it's a sign the kernel is already too coupled.

Wrong answer: Reaching for a shared kernel to avoid "duplicating" a few DTOs between services. A handful of near-identical value types costs almost nothing to duplicate; a shared assembly that now gates two teams' release trains costs a great deal — duplication is usually the cheaper failure mode.

An upstream team won't change their model to suit you. How do you use context mapping to respond? senior

First name the relationship honestly: if you have no influence over their roadmap, you are a Conformist by default, and the only real decision left is whether to conform directly or interpose an Anticorruption Layer. I'd choose an ACL whenever the upstream model would otherwise leak concepts, naming or invariants into my own domain that don't belong there — a translation layer at the boundary that converts their DTOs into my domain's own vocabulary, so a change on their side is a change to one adapter, not a change scattered through my model. I'd also try to become a Customer/Supplier relationship by getting our needs onto their backlog, even informally, since that's strictly better than pure conformism if it's achievable.

Example 
public interface IShippingProviderAcl { ShipmentQuote GetQuote(ShippingRequest request); }

internal sealed class LegacyCarrierAcl(LegacyCarrierClient client) : IShippingProviderAcl
{
    public ShipmentQuote GetQuote(ShippingRequest request)
    {
        var raw = client.Quote(new { wt = request.WeightKg, dst = request.Destination.PostalCode });
        // Translate their flat, stringly-typed reply into our domain's own type.
        return new ShipmentQuote(Money.FromMinorUnits(raw.PriceCents, "USD"), TimeSpan.FromDays(raw.EtaDays));
    }
}

Follow-ups

  • Does an ACL cost performance? — A translation step, yes, usually negligible next to the network call it wraps; the cost that matters is the code you write and maintain, not CPU.
  • Where does the ACL live physically? — At the edge of your own bounded context, as an adapter implementing a port your domain defines — the domain never imports the upstream's types.
  • What if the upstream model changes underneath you? — Only the adapter breaks; that's the entire point of paying for the translation layer up front.

Wrong answer: Quietly threading the upstream team's DTOs and enum values through your own service "just for now" to save time. It's never just for now — those types end up in your domain logic, your persistence model and your tests, and untangling them later costs far more than writing the adapter would have.

How does a bounded context map to team boundaries, and why does that matter at scale? senior

Conway's Law says a system's structure mirrors the communication structure of the organisation that built it — so a bounded context that spans two teams will, over time, either force those teams to communicate constantly (slow) or drift into two accidental sub-models anyway (the boundary you didn't design). The practical consequence is that healthy DDD at scale puts one team in clear ownership of each context's model and its ubiquitous language, with context maps documenting every place two teams' models touch. This is the origin of the "Inverse Conway Maneuver": deliberately shaping team boundaries to match the bounded contexts you want, rather than discovering your contexts after the fact from how the org already happens to be split.

Example

A platform team and a checkout team both "own" pricing logic because it was never assigned — every promotion rule needs both teams in the room, releases are coupled, and nobody can explain who's authoritative when the two disagree. Splitting pricing into its own bounded context with one clear owning team, and making the checkout team a documented consumer via a published API, removes the coupling at its source.

Follow-ups

  • What if the org can't be restructured? — Model the boundary in code and process anyway (module ownership, a documented interface, a shared backlog item for cross-cutting changes) — it recovers most of the benefit without an org chart change.
  • Does this mean one team per microservice? — Usually the reverse causality: one team should own each bounded context, and a context may contain several services that team runs.
  • How do you spot a Conway violation in an org chart? — Look for a single feature that reliably needs sign-off from more than two teams to ship — that's a bounded context nobody owns.

Wrong answer: "Team topology is an engineering-management concern, not something I model." At principal level, refusing to touch org structure when it's the actual root cause of a modeling problem is a bigger miss than any code-level mistake — the two are inseparable in DDD's own strategic design chapter.

You inherit a Big Ball of Mud monolith. How do you discover bounded contexts inside it without a rewrite? principal

Start from behaviour, not code structure: run event storming with domain experts and engineers together to lay out the business process as domain events on a timeline, and let the natural clusters — places where events pile up around the same actors and the same nouns — suggest candidate contexts, entirely independently of how the code is currently organised. Cross-check against the codebase with a dependency and change-coupling analysis (which classes change together in the same commits) to find where the existing structure already agrees or disagrees with the storming output. Then don't extract anything yet — first draw module boundaries inside the monolith that match the candidate contexts, enforce them with architecture tests (no cross-module references except through an explicit interface), and let the modular monolith run for a while before any physical extraction.

Example

Event storming an order-fulfilment monolith surfaces three clusters: events about pricing and promotions, events about payment capture and refunds, and events about picking and shipping — three candidate contexts, none of which correspond to the existing OrderService/OrderRepository/OrderController layering the code is currently organised around.

Follow-ups

  • Why modularise before extracting a service? — Because a poorly-bounded module extracted into a service just becomes a distributed Big Ball of Mud with network calls — the boundary has to be right first.
  • How do you enforce a module boundary in a .NET monolith? — Separate project references with `InternalsVisibleTo` avoided, architecture tests (e.g. NetArchTest) asserting no namespace reaches into another module except through its public contracts.
  • What's the actual signal that it's time to extract a service? — A real forcing function: a differing scaling profile, an independent deployment cadence the team is blocked on, or a compliance boundary — not "it feels cleaner as a service."

Wrong answer: Reorganising the folder structure by technical layer (Controllers, Services, Repositories) and calling the result "bounded contexts." That's a rename, not a boundary — the coupling that made it a ball of mud lives in the business logic, and a folder move doesn't touch it.

What information should go on a context map, and who is it for? mid

A context map names every bounded context in play, the relationship pattern between each pair that integrates (Shared Kernel, Customer/Supplier, Conformist, ACL, Open Host Service, Separate Ways), the direction of the dependency, and — critically — which team owns each context. It's a living artifact for engineers making integration decisions and for managers making staffing and roadmap decisions; it is deliberately not a data-flow diagram or a deployment diagram, because those describe mechanics the context map doesn't care about.

Example

A one-page map for a retailer: Catalog (Open Host Service, owned by Merchandising) → conformed to by Search and Recommendations; Pricing (Customer/Supplier, owned by Commercial) supplies Checkout (owned by Checkout team); Checkout talks to the third-party Payments gateway through an ACL.

Follow-ups

  • How often should it be updated? — Whenever an integration relationship changes — treat drift the same way you'd treat stale architecture documentation, because a wrong map is worse than none.
  • Should it show every service, down to infrastructure? — No — infrastructure and deployment topology belong on a different diagram; the context map is strictly about model boundaries and team relationships.
  • Who draws it — architects or the teams themselves? — The teams, ideally together in one room; an architect drawing it alone tends to produce a map nobody on the ground recognises.

Wrong answer: Producing a context map once, during a kickoff workshop, and never revisiting it. A stale context map actively misleads new hires and gives false confidence in an integration pattern (say, Customer/Supplier) that quietly degraded into Conformist once the upstream team stopped listening.

What's an Open Host Service, and how do you keep it from becoming an accidental Shared Kernel? senior

An Open Host Service exposes a deliberately designed, versioned protocol — the Published Language — that any number of consumers can integrate against without individual negotiation, which is what makes it scale past two teams where a Shared Kernel can't. It stays a real Open Host Service, rather than sliding into a de facto Shared Kernel, only if the contract is genuinely stable and versioned (breaking changes go through deprecation, not a Slack message), and if consumers are integrating against that published contract rather than against the provider's internal types leaking through a thin wrapper.

Example 
// Published Language: a versioned, documented contract — not the internal Catalog aggregate.
public sealed record CatalogProductV2(string Sku, string Title, decimal Price, string CurrencyCode, string[] CategoryPath);

app.MapGet("/api/v2/products/{sku}", (string sku, ICatalogQuery q) => q.GetV2(sku));
// v1 stays live under its own route until every known consumer has migrated.

Follow-ups

  • REST, gRPC or events for the Published Language? — Whatever fits the consumption pattern — request/response favours REST or gRPC with an OpenAPI/protobuf schema; broadcast-to-many favours a versioned event contract instead.
  • How do you version without breaking every consumer at once? — Additive changes only on the current version; a genuine breaking change ships as a new version published alongside the old, with a deprecation window.
  • What turns an OHS into an accidental Shared Kernel? — Consumers reaching past the published contract into internal fields "just this once," which re-creates the coupling the pattern exists to avoid.

Wrong answer: Publishing your internal domain model's DTOs directly as the API contract because "it's less work." Every internal refactor now risks breaking every consumer, which is precisely the coupling an Open Host Service's Published Language is supposed to prevent.

02 Aggregates & aggregate roots

An aggregate is a cluster of entities and value objects treated as one consistency boundary; the aggregate root is the single entity through which everything outside the cluster must interact with it. This is the pattern interviewers use to check whether you can turn "the invariants" into an actual transaction and concurrency design, not just a class diagram. Screeners want the definition and the rule ("never reach inside"); mid and senior candidates are expected to draw a boundary and defend its size; principal candidates are expected to redesign a boundary that's already wrong in production without a rewrite.

docs: Implementing domain entities and aggregates · martinfowler.com: DDD_Aggregate

What is an aggregate, and what does the aggregate root control? screener

An aggregate is a group of related objects — entities and value objects — that must be treated as a single unit for the purpose of enforcing business invariants and data changes; the aggregate root is the one entity in that group that external code is allowed to reference and call directly. Everything else inside the aggregate is reachable only by navigating from the root, and the root is responsible for keeping the whole cluster in a valid state after every operation. This is what makes an aggregate a transaction boundary: one aggregate, one unit of work, saved atomically.

Example 
public sealed class Order // aggregate root
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyList<OrderLine> Lines => _lines;
    public OrderStatus Status { get; private set; }

    public void AddLine(ProductId product, int quantity, Money unitPrice)
    {
        if (Status != OrderStatus.Draft) throw new InvalidOperationException("order already placed");
        _lines.Add(new OrderLine(product, quantity, unitPrice)); // no public OrderLine constructor outside the aggregate
    }
}

Follow-ups

  • Can code outside the aggregate hold a reference to an inner entity? — No — only IDs or read-only projections; holding a live reference lets external code mutate it and bypass the root's invariants.
  • Is every entity an aggregate root? — No — most entities are inner members of some aggregate; only the entity that owns the consistency boundary is a root.
  • Can an aggregate be a single entity with no children? — Yes, and that's common — a one-entity aggregate is still an aggregate, just a trivial one.

Wrong answer: "An aggregate is just a fancy word for a class with some child objects in it." Without the "external code only touches the root, root enforces invariants, one transaction per aggregate" rules, it's just composition — the DDD content is entirely in those rules, not the shape.

What decides where you draw an aggregate's boundary? mid

The boundary is drawn around the invariant that must be true at the end of every transaction, not around "things that are related." Ask: which pieces of data must change together, atomically, for the business rule to hold? Everything the rule needs to check goes inside the boundary; everything else — even if conceptually related — stays out and is referenced by ID. This usually produces boundaries that are much smaller than a naive "everything an Order touches" grouping would suggest.

Example

An Order aggregate must enforce "line item quantities can't be changed after the order is placed" and "the total must equal the sum of the lines" — both are checked inside one Order instance. It does not need to include the full Customer or Product records inside its boundary; it references them by CustomerId and ProductId because no invariant requires them to change atomically with the order.

Follow-ups

  • What if two invariants seem to require different boundaries? — That's a signal you actually have two aggregates; don't force one boundary to serve two unrelated rules.
  • Does "the UI shows it together" justify one aggregate? — No — display composition is a query-side concern (read model, DTO projection), never a reason to widen a transactional boundary.
  • How do you validate a boundary is right? — Ask what happens under concurrent edits from two users — if the answer requires locking two aggregates together, the boundary is probably wrong.

Wrong answer: "Group everything that's shown on the same screen into one aggregate." That's a UI-driven boundary, not an invariant-driven one, and it reliably produces aggregates that are too large and lock too much.

Why do experienced DDD practitioners push for small aggregates, and what actually breaks with a "God aggregate"? mid

A large aggregate means every write to any part of it takes a lock (optimistic or pessimistic) on the whole thing, so unrelated changes made by different users start contending with each other even though their business rules never overlap. It also means loading the aggregate for a single small change pulls the entire graph into memory, and every invariant check on save has to walk more state than the specific change warranted. Vernon's guidance ("Effective Aggregate Design") is to keep aggregates small — reference other aggregates by identity, model true invariants only, and let anything eventually-consistent happen through domain events instead of being folded into the same transaction.

Example

An Order aggregate that embeds the entire ShippingHistory (every tracking event ever recorded) means adding a new tracking event takes the same lock as changing the order's line items — two operations that have zero business reason to conflict now contend on every write.

Follow-ups

  • What's the practical symptom in production? — Frequent optimistic-concurrency exceptions ("row was modified by another user") on an aggregate that's actually being edited by unrelated features.
  • Is there a size where you know it's too big? — No fixed number — the tell is unrelated invariants sharing one root, not a line count.
  • How do you fix a God aggregate already in production? — Identify the sub-clusters with independent invariants, extract each as its own aggregate, and connect them by ID plus domain events instead of direct references.

Wrong answer: "Bigger aggregates are safer because everything is consistent together." Strong consistency inside an oversized aggregate buys you nothing the business actually needs and costs you throughput and contention on every unrelated change — most of that "consistency" is unused.

How should one aggregate refer to another? mid

By identity only — store the other aggregate's ID (a strongly-typed id value object, not a raw Guid, ideally), never a live object reference or a navigation property that an ORM could eagerly load into the same graph. This keeps each aggregate loadable and saveable independently, keeps the transaction boundary honest, and stops a change deep in one aggregate from cascading into another's save.

Example 
public sealed class Order
{
    public CustomerId CustomerId { get; private set; } // reference by id
    // not: public Customer Customer { get; private set; }
}

Follow-ups

  • Doesn't that make reads awkward — I need the customer's name on the order? — Yes, slightly; solve it in the query/read side with a join or a denormalised projection, not by pulling the reference into the write-side aggregate.
  • What about EF Core navigation properties between aggregate roots? — Avoid them across aggregate boundaries; EF happily lets you add one, but it invites accidentally modifying two aggregates in the same SaveChanges call, breaking the "one transaction per aggregate" rule.
  • Is it ever OK to load a related aggregate in the same use case? — Yes, as two separate loads and (if both must change) two separate saves — or better, one changes now and the other reacts later via a domain event.

Wrong answer: Modeling a full object reference (`Customer Customer { get; set; }`) between two aggregate roots because EF Core makes it easy. It's technically effortless and semantically wrong — it re-creates a single giant consistency boundary across aggregates that were supposed to be independent.

How do aggregates relate to transactions, and what's the rule of thumb for "one transaction, one aggregate"? senior

The rule of thumb is: a single database transaction should modify exactly one aggregate instance. The aggregate is the unit that guarantees its own invariants are true when the transaction commits, and if you need two aggregates to change atomically together, that's usually evidence the boundary is drawn wrong, or the two changes should be decoupled via a domain event and processed eventually consistently rather than atomically. This rule is a design constraint, not an artifact of any one persistence technology — it holds whether you're using a relational database, a document store, or event sourcing.

Example 
await using var tx = await db.Database.BeginTransactionAsync();
order.Place(); // mutates only the Order aggregate
db.Orders.Update(order);
await db.SaveChangesAsync();
await tx.CommitAsync();
// Inventory reservation happens later, via a handler reacting to OrderPlaced — a separate transaction.

Follow-ups

  • What if the business genuinely needs two aggregates updated atomically? — That's a strong signal to re-examine the boundary — either merge them (if the invariant is truly indivisible) or accept eventual consistency and design for the intermediate state.
  • Does this rule apply to reads too? — No — reads can and should span multiple aggregates freely (that's what read models are for); the rule is about the write/transaction boundary only.
  • What about a batch job that touches thousands of Orders? — Each order still gets its own transaction (or a well-understood batching strategy); "one transaction per aggregate instance," not "one transaction total."

Wrong answer: Wrapping a multi-aggregate update in one big database transaction "to be safe." It works until scale or lock contention makes it painful, and it hides a boundary problem that eventual consistency (via domain events) would have surfaced and solved properly.

An invariant genuinely spans two aggregates — e.g. "total reserved inventory across all orders must not exceed stock." How do you handle it? senior

You almost never enforce a true cross-aggregate invariant with a synchronous, strongly-consistent check across both aggregates in the same transaction — that reintroduces the coupling aggregates exist to avoid, and it doesn't scale. Instead: either move the invariant fully inside one aggregate if it can be reformulated that way (e.g. give Inventory sole ownership of "available quantity" and have it reject a reservation attempt), or accept eventual consistency — the order is placed optimistically, an OrderPlaced event triggers an inventory reservation, and if it fails, a compensating action (cancel or backorder the line) runs. Which one you pick depends on whether the business can tolerate a brief window where the invariant is provisionally violated.

Example 
public sealed class Inventory // sole owner of the "don't oversell" invariant
{
    public Result Reserve(ProductId product, int qty)
        => _available >= qty
            ? Result.Success(() => _available -= qty)
            : Result.Failure("insufficient stock");
}
// OrderPlaced handler calls Inventory.Reserve; on failure, publishes OrderReservationFailed.

Follow-ups

  • Isn't there a race between two orders reserving the last unit? — Yes, which is exactly why Inventory itself must serialize reservations (optimistic concurrency retry or a queue) — it's a within-aggregate concern once ownership is centralised there.
  • What if the business truly cannot tolerate overselling even briefly? — Then reservation has to happen synchronously as part of placing the order, inside a single transaction that spans both — an explicit, rare exception to the rule, justified by a real business constraint, not convenience.
  • How do you communicate the interim state to the customer? — Show the order as "pending confirmation" until the reservation succeeds, rather than implying a guarantee you haven't yet secured.

Wrong answer: Loading both the Order and Inventory aggregates in the same use case and checking the invariant across both before saving both in one transaction. It looks correct in a single-instance demo and falls over under real concurrency and scale — the two-phase check-then-commit isn't actually atomic unless the database serialises the whole thing, which defeats the purpose of having two aggregates at all.

What concurrency strategy do you use for aggregates, and why is optimistic concurrency usually preferred? senior

Optimistic concurrency — a version number or rowversion column checked on update, with the write failing and the caller retrying if it's stale — is preferred because aggregate boundaries are supposed to be small and short-lived: you load, mutate, save, all within one request, so contention is rare and a retry is cheap. Pessimistic locking (holding a row/table lock for the duration of the operation) trades that cheap-retry model for held locks that block other transactions even when they'd never actually conflict, and doesn't compose well with a stateless web request model where "how long is the lock held" depends on network latency to the caller. EF Core supports optimistic concurrency natively via a concurrency token (`[ConcurrencyCheck]`/`IsRowVersion()`), throwing `DbUpdateConcurrencyException` on a stale write.

Example 
public class Order
{
    [Timestamp] public byte[] RowVersion { get; private set; } = default!;
}

try { await db.SaveChangesAsync(); }
catch (DbUpdateConcurrencyException)
{
    // reload, reapply the intended change, retry — or surface a conflict to the caller
}

Follow-ups

  • When would you reach for pessimistic locking instead? — High-contention hot rows where retries would themselves become the bottleneck (e.g. a single shared counter under heavy concurrent load) — rare, and usually a sign to redesign the aggregate rather than lock harder.
  • How many retries is reasonable on a concurrency conflict? — Usually one or two with fresh data reloaded; beyond that, surface the conflict to the caller rather than retrying blindly, since the business context may have changed.
  • Does event sourcing change this? — The mechanism shifts to checking the expected version of the event stream before appending, but the optimistic principle is identical.

Wrong answer: Reaching for `SELECT ... FOR UPDATE` / `TransactionScope` with serializable isolation by default "to avoid race conditions." That's pessimistic locking applied everywhere, and it turns every aggregate save into lock contention the aggregate's own small boundary was designed to avoid.

How do you make an invariant change to an aggregate that's already live in production, without a big-bang data migration? senior

Introduce the new rule so it's enforced going forward for new state transitions while tolerating existing data that predates it, rather than trying to retroactively validate every historical row against the new invariant before deploy. Concretely: add the new check to the aggregate's mutating methods (so nothing new can violate it), backfill or reconcile existing data out-of-band on its own schedule, and — if the invariant genuinely can't coexist with legacy shapes — version the aggregate's schema and migrate incrementally with a compatibility shim in the repository, not a single flag-day cutover.

Example

Adding "an order line's quantity must be positive" to an aggregate that already has legacy rows with zero-quantity lines: the new invariant blocks any new attempt to create or edit a zero-quantity line; a background job flags and reconciles the pre-existing rows; nothing breaks for orders nobody is actively editing.

Follow-ups

  • What if the invariant must hold immediately for correctness reasons (e.g. financial)? — Then it's worth the bigger migration, but do it as an explicit, reviewed, reversible data migration — not silently inside application code that assumes it already holds.
  • How do you test this kind of rollout? — Load real (anonymised) production aggregates into a staging invariant-check pass before deploying the new rule, to see how much existing data would fail it.
  • Does event sourcing make this easier or harder? — Harder in one sense (you can't rewrite history) but it gives you an explicit tool: an upcaster/migration event that transforms old event shapes into the new invariant's expectations as they're replayed.

Wrong answer: Shipping the new invariant check unconditionally and letting it throw for every pre-existing row that violates it. It turns a design improvement into a production incident the moment any legacy aggregate is loaded and saved.

A code review flags an aggregate that has grown to own half the domain — orders, line items, payments, shipments, and a full audit log, all inside one root, all locked together. How do you split it under production pressure without a rewrite? principal

Start by mapping which pieces of state are actually load-bearing for which invariant — usually you'll find the audit log and shipment history have no invariant that requires atomicity with the order at all; they're append-only records that were folded in for convenience. Extract those first: they're the lowest-risk, highest-value cut, because nothing about them needs to change synchronously with the order. Payments are next: they almost certainly deserve their own aggregate with its own lifecycle (authorised, captured, refunded) connected to the order by ID and coordinated through domain events, since "the order changed" and "the payment changed" are rarely the same invariant. Do each extraction as a separate, independently-shippable change behind the existing repository interface, migrating data and dual-writing if needed, and only remove the old embedded fields once the new aggregate is proven in production. The key discipline under pressure is: one extraction at a time, each one individually safe to roll back, never a single flag-day cutover of the whole thing.

Example

Order 1 (this sprint): extract ShipmentHistory into its own append-only table/aggregate written via a domain event handler, read via its own query — zero coupling to Order's invariants. Order 2: extract Payment as its own aggregate with `OrderId` reference, migrating existing embedded payment records in a background job. Order's own invariants (line items, totals, status transitions) are what's left, and it's now small enough that the next reviewer wouldn't flag it.

Follow-ups

  • How do you avoid breaking existing queries during the extraction? — Keep a read-side compatibility view/projection that reassembles the old shape from the new aggregates until every consumer has migrated to the new query surface.
  • What's the risk of extracting too many pieces at once? — You lose the ability to roll back a single change independently, and you multiply the number of places a bug can hide during the transition — exactly the "big bang" risk this approach exists to avoid.
  • How do you know when to stop splitting? — When every remaining piece inside the aggregate shares an invariant that genuinely requires atomicity with the root — splitting further would just fragment a single true invariant.

Wrong answer: Proposing a full domain-model rewrite as the fix. A God aggregate in production got that way over months or years of real feature work sitting on top of it; a rewrite freezes feature delivery and re-introduces every subtle behaviour the legacy code accumulated — incremental extraction behind a stable interface is almost always the responsible answer at this level.

03 Entities vs. value objects

Entities have identity and a lifecycle; value objects are defined entirely by their attributes and are interchangeable if those attributes match. This distinction sounds academic until it drives real decisions — mutability, equality, how you persist something, and whether "the same address twice" is one thing or two. It's tested constantly because it's cheap to ask and expensive to get wrong: an anemic domain full of mutable DTOs almost always traces back to never having drawn this line.

docs: Implement value objects · martinfowler.com: ValueObject

What distinguishes an entity from a value object? screener

An entity is defined by its identity — two entities with identical attributes are still different things if their IDs differ, and the same entity remains "the same" even as its attributes change over time (a Customer who changes their name is still that customer). A value object is defined entirely by its attributes — two value objects with the same attribute values are interchangeable and considered equal, and a value object never "changes"; you replace one instance with another. The practical test: does this thing need a stable ID that survives attribute changes, or does "same values" already mean "same thing"?

Example 
public sealed class Customer // entity — has identity
{
    public CustomerId Id { get; }
    public string Name { get; private set; } // can change; still the same Customer
}

public sealed record Address(string Street, string City, string PostalCode); // value object — no identity

Follow-ups

  • Can a value object contain an entity's ID? — Yes — a value object can reference an entity by ID (e.g. a `ShippingDetails` value object holding a `CarrierId`) without becoming an entity itself.
  • Is a DTO a value object? — Not automatically — a DTO is a data-transfer shape; it becomes a domain value object only once it carries behaviour and enforces its own invariants.
  • What about a `Money` type — entity or value object? — Value object: two `Money(10, "USD")` instances are simply equal and interchangeable; neither has or needs an identity.

Wrong answer: "Entities are things with a database primary key, value objects aren't stored." Persistence is a consequence of this distinction, not the definition — plenty of value objects are stored (as owned rows or JSON columns) without ever having their own identity or key.

Why should value objects be immutable? screener

Immutability follows directly from having no identity: if two value objects with the same attributes are supposed to be interchangeable, then mutating one in place would silently change every reference to "that value" elsewhere, which contradicts the whole point of comparing by value rather than by reference. Immutability also makes value objects trivially safe to share across aggregates, cache, and reason about in concurrent code — there's no defensive copying needed because nothing can change out from under you.

Example 
public sealed record Money(decimal Amount, string CurrencyCode)
{
    public Money Add(Money other) =>
        CurrencyCode == other.CurrencyCode
            ? this with { Amount = Amount + other.Amount } // returns a new instance
            : throw new InvalidOperationException("currency mismatch");
}

Follow-ups

  • What's the "change" operation on an immutable value object called? — A "with" or "replace" operation that returns a new instance — C# records' `with` expression is built for exactly this.
  • Does immutability hurt performance? — Rarely meaningfully — value objects are typically small, and the cost of a new allocation is far smaller than the bugs aliasable mutable state causes.
  • Can a value object have a setter for anything? — No — any setter reintroduces the aliasing problem immutability exists to prevent; expose only a constructor/factory and transformation methods that return new instances.

Wrong answer: Giving a value object public setters "for convenience" (e.g. an EF Core-friendly `Address` with a settable `City`). It works until two aggregates share a reference to the same `Address` instance and one mutates it, silently corrupting the other's state.

How do you implement value-object equality correctly in C#? mid

A C# `record` (or `record struct`) gives you structural equality for free — `Equals`, `GetHashCode` and `==` are all generated to compare every declared member's value, which is exactly the semantics a value object needs. Before records (or for cases needing a `class`), you'd override `Equals`/`GetHashCode` by hand, comparing every field, and overload `==`/`!=` to match — easy to get subtly wrong (forgetting a field, using reference equality by accident) which is precisely why records exist.

Example 
public sealed record Address(string Street, string City, string PostalCode);

var a = new Address("1 Main St", "Springfield", "00000");
var b = new Address("1 Main St", "Springfield", "00000");
Console.WriteLine(a == b); // True — structural equality, not reference equality

Follow-ups

  • Record class or record struct for a value object? — `record struct` avoids a heap allocation for small, frequently-created value objects, but watch for accidental boxing when used through interfaces; `record class` is the safer default for anything with several fields or nested value objects.
  • Do collections inside a record get structural equality? — No — a `List<T>` member still compares by reference; use an immutable collection and override equality, or compare via a computed key, if a value object needs a collection member.
  • What about EF Core and record-based value objects? — EF Core 8+ maps records like any other CLR type via owned entities or (from EF Core 10) complex types; the equality semantics are a C# concern, independent of how EF persists it.

Wrong answer: Modeling a value object as a plain class and relying on the default `Equals` (reference equality) "because it's simpler." Two value objects with identical data will then compare unequal, breaking every place the domain logic assumes value semantics — a subtle bug that surfaces far from where it was introduced.

Something looks like it has "identity" — e.g. an email address, or a shipping address on file. When is it still a value object? mid

The question isn't whether the thing has a real-world identifier (an email address is unique to a person; an address is a real place) — it's whether your domain needs to track that identity across changes. If nothing in the business logic cares whether "this is the same address instance as last time" versus "an address with the same values," it's a value object regardless of how identifiable it feels in the real world. The moment you need to track an address's history (this specific shipping address was used on these specific orders, and if it's edited, old orders still show the original) it might need to become an entity with its own ID and lifecycle.

Example

A Customer's current shipping address is a value object — replacing it is just assigning a new `Address` value. But a SavedAddress in an address book, which the user names ("Home", "Office"), edits in place, and expects to persist as a distinct row they can update or delete, has become an entity — it has a lifecycle and identity the domain now needs to track.

Follow-ups

  • Does having a database row automatically make something an entity? — No — a value object can absolutely have its own row (owned entity or complex type); the entity/value distinction is about domain semantics, not schema shape.
  • What's the risk of over-promoting things to entities? — Unnecessary identity tracking, equality-by-reference bugs, and repositories/queries for things that never needed a lifecycle — extra ceremony with no domain payoff.
  • What's the risk of under-promoting an entity to a value object? — You lose the ability to track history or react to "this specific one changed," which the business may actually need (e.g. audit trail on a specific saved address).

Wrong answer: "If it has a real-world unique identifier (email, SSN, VIN), it's an entity." Real-world uniqueness and domain identity are different questions — an email address is almost always a value object even though it's globally unique, because the domain rarely needs to track "this specific email object" across changes.

What's a "self-validating" value object, and why is it worth the extra ceremony? mid

A self-validating value object enforces its own invariants in its constructor or factory method, so it is genuinely impossible to construct an instance that violates the rule — an EmailAddress that always contains an "@" once constructed, an OrderQuantity that's always positive. This moves validation from "scattered checks before every use" to "checked exactly once, at the one place a value can come into existence," which eliminates an entire class of bugs where a validated value is passed around and re-validated inconsistently (or not at all) downstream.

Example 
public sealed record EmailAddress
{
    public string Value { get; }
    public EmailAddress(string value)
    {
        if (!value.Contains('@')) throw new ArgumentException("invalid email", nameof(value));
        Value = value;
    }
}
// or, avoiding exceptions in the domain: a static Create returning Result<EmailAddress>

Follow-ups

  • Exceptions or a Result type for validation failures? — Either is defensible — exceptions are simpler and fine for "this should never happen given upstream validation"; a `Result`/`Maybe` factory is better when invalid input is an expected, user-facing case you want to handle without try/catch.
  • Does this replace input validation at the API boundary? — No — API-level validation (model binding, FluentValidation) gives fast, user-friendly feedback; the value object's own validation is the last line of defense that holds regardless of entry point.
  • What if the same primitive (e.g. `string`) is used for ten different concepts? — That's primitive obsession — each concept deserves its own self-validating value object so the compiler stops you from passing a `CustomerName` where an `EmailAddress` was expected.

Wrong answer: Validating a value with a static helper method (`Validators.IsValidEmail(str)`) called at each usage site, while the value itself is stored as a plain `string`. Every call site that forgets to call the validator — and there's always one — creates a hole; a self-validating type has no such hole because invalid instances simply cannot exist.

Can a value object hold a reference to an entity, or must it be pure data? senior

A value object can reference an entity — typically by that entity's ID, which is itself just data and keeps the value object's own equality and immutability intact. What it must not do is hold a live, mutable reference to the entity object itself, because then two "equal" value objects could observe different entity state depending on when they were constructed, breaking the "defined entirely by its attributes" contract. The pattern that comes up constantly: a value object like `ShippingSelection(CarrierId Carrier, ServiceLevel Level)` — data plus an ID — versus a temptation to embed the actual `Carrier` entity, which would leak a mutable, identity-bearing object into a supposedly-immutable value.

Example 
public sealed record DiscountApplication(CouponId CouponId, Money AmountOff); // fine: ID reference
// not: public sealed record DiscountApplication(Coupon Coupon, Money AmountOff); // leaks a mutable entity in

Follow-ups

  • Why does embedding the entity break equality? — Two `DiscountApplication`s with the same `CouponId` but pointing at two different in-memory `Coupon` instances (or a `Coupon` that's since changed) would no longer reliably compare equal by value.
  • Is it OK for a value object to hold another value object? — Yes, freely — nested value objects are common and keep everything immutable and structurally comparable.
  • What about a snapshot of entity data inside a value object, not a live reference? — That's fine and common — it's just more data (e.g. capturing the coupon's discount percentage at the time it was applied), not a reference to the mutable entity.

Wrong answer: Embedding a live entity reference in a value object "so I don't have to look it up again." It quietly turns the value object into something whose equality and immutability guarantees no longer hold, for a convenience that a proper lookup or a snapshot value would have given you safely.

A price needs to be captured with the exchange rate and date it was quoted, and must never change even if the live rate does later. How do you model that? senior

This is exactly what value objects are for: model a `QuotedPrice` (or similar) value object that captures the amount, currency, the exchange rate used, and the timestamp, all together, at the moment the quote is created — once constructed, it never changes, regardless of what the live rate does afterward. The key modeling move is recognising that "price right now" and "price as quoted on this order" are two different concepts entirely, and conflating them (storing only the base amount and re-deriving the rate later) silently changes historical data whenever the live rate updates.

Example 
public sealed record QuotedPrice(Money BaseAmount, decimal ExchangeRate, string TargetCurrency, DateTimeOffset QuotedAt)
{
    public Money ConvertedAmount => BaseAmount with { Amount = BaseAmount.Amount * ExchangeRate, CurrencyCode = TargetCurrency };
}
// Order stores the QuotedPrice at placement time — it is never recomputed from a "current" rate.

Follow-ups

  • Where does the live/current rate live, then? — In its own service or value (e.g. an `ExchangeRateProvider`) that's consulted only at the moment a new quote needs to be created — never referenced by an existing, already-quoted price.
  • Isn't this just an audit log entry, not a value object? — It's both — an immutable value object is exactly the right shape for a fact that needs to be captured once and never mutated, which is also what makes it audit-friendly.
  • How would you catch a bug where someone "helpfully" recomputes it? — Make the value object's constructor the only way to create one, and never expose a way to update `ExchangeRate` in place — a compile error, not a runtime check, is the goal.

Wrong answer: Storing only the base amount and looking up "the exchange rate for that currency" whenever the converted price is displayed. Every historical order's displayed price then silently drifts as rates change, which is a real, embarrassing, and hard-to-trace class of bug in any system dealing with money over time.

What's the trade-off of pervasive strongly-typed value objects (avoiding "primitive obsession") at large scale? principal

Strongly-typed value objects (a distinct `CustomerId`, `Sku`, `EmailAddress` instead of raw `string`/`Guid` everywhere) pay off by making illegal states unrepresentable at compile time — you cannot accidentally pass a `ProductId` where an `OrderId` was expected — and by centralising validation and formatting logic in one place per concept. At scale, the cost shows up as ceremony: every layer (API contracts, serialization, EF Core mapping, logging, caching keys) needs conversions at its boundary, value-object proliferation can genuinely slow onboarding for a large team, and naive JSON (de)serialization or EF Core value comparers need explicit setup for every new type or you get subtle bugs. The judgment call is where to draw the line: strongly type identifiers and any concept with real business rules (money, quantities, anything validated); leave genuinely inert, single-use primitives (a one-off internal counter) as primitives.

Example

A payments platform strongly types `Money`, every entity ID, and `Iban`/`RoutingNumber` — real invariants, real bugs prevented (a `CustomerId` passed where a `MerchantId` was expected would have shipped a real production incident twice before). It deliberately leaves an internal `RetryCount` as a plain `int` — no business rule attaches to it, and a value-object wrapper would be pure ceremony.

Follow-ups

  • How do you keep serialization/EF Core mapping from becoming a maintenance burden? — Source generators (e.g. strongly-typed-id generators) or EF Core value converters written once per "kind" of value object (e.g. a generic single-value-wrapper converter), not hand-rolled per type.
  • Does this slow down a large team? — Initially, yes — the payoff is fewer whole categories of bugs and self-documenting signatures; teams that skip it tend to reach for it retroactively once they've been burned by an ID mix-up in production.
  • How do you decide the line for a new concept? — Ask whether a wrong value would compile silently and fail at runtime, and whether the concept has any validation or behaviour of its own — if both are "no," a primitive is fine.

Wrong answer: Wrapping every single primitive in the codebase in a value object "for consistency," including things with no business meaning of their own (a UI page-size parameter, a generic retry counter). Blanket rules produce blanket ceremony; the payoff of a value object comes from the invariant or the type-safety it buys, and some primitives genuinely don't need either.

You're modeling a value object that needs to be persisted with EF Core. What are the options, and which is current? senior

Historically the only option was an owned entity type (`OwnsOne`/`OwnsMany`) — EF Core creates a shadow "owned" record that's stored inline (or in a separate table for collections) but underneath still carries its own hidden identity/key, which means assigning the same owned instance to two different owner properties, or bulk-updating with `ExecuteUpdateAsync`, could behave unexpectedly because EF still tracks it with reference semantics. EF Core 10 (Nov 2025) adds Complex Types as the modern alternative specifically for this case: true value/copy semantics (no hidden identity, compared by content, safe to share an instance across properties), with support for JSON-column mapping and complex types on `readonly record struct`. Microsoft's own EF Core 10 guidance now recommends switching value-object mapping from owned entity types to complex types where the type has no independent identity — which is precisely the value-object case.

Example 
// EF Core 10+
public class Order
{
    public required Address ShippingAddress { get; set; } // complex type — true value semantics
}
modelBuilder.Entity<Order>().ComplexProperty(o => o.ShippingAddress);
// vs. the legacy pattern still seen in existing codebases:
// modelBuilder.Entity<Order>().OwnsOne(o => o.ShippingAddress);

Follow-ups

  • Why did owned entity types cause bugs with shared instances? — Because EF's change tracker still gave the owned instance an identity under the hood, so assigning the same `Address` object to two different `Order.ShippingAddress` properties could throw or misbehave — a value object should never have had that restriction.
  • Do complex types support collections? — As of EF Core 10, complex type collections are more limited than owned-type collections in some scenarios; a value object that's genuinely a collection member may still need an owned type until parity closes further — check current docs per EF Core minor version.
  • Is this a breaking change for existing code? — No — owned entity types remain fully supported; complex types are additive and recommended for new value-object mappings going forward.

Wrong answer: "EF Core has no way to persist value objects that isn't a full extra table with its own primary key." That was the practical experience with early owned-type collections, but a single owned reference has been inline-mappable for years, and EF Core 10's complex types now remove even the hidden-identity caveat for the common single-instance case.

04 Domain events

A domain event records something that happened in the domain that other parts of the system might care about — "OrderPlaced," not "SaveOrder." Interviewers use this sub-area to check whether you can decouple side effects from the aggregate that caused them, and whether you understand the sharp line between an in-process domain event and an integration event that crosses a service boundary — conflating the two is one of the most common mid-level mistakes. Expect questions on naming, delivery guarantees, and — at senior/principal level — what happens when delivery fails.

docs: Domain events design and implementation · martinfowler.com: DomainEvent

What is a domain event, and how does it differ from just calling another method directly? screener

A domain event is an immutable record of something significant that already happened inside the domain, named in the past tense (`OrderPlaced`, not `PlaceOrder`), raised by the aggregate that caused it and handled by one or more listeners that react to it. The difference from a direct method call is decoupling: the aggregate that raises `OrderPlaced` has no idea who's listening or what they'll do — reserve inventory, send an email, update a read model — so new reactions can be added without ever touching the aggregate again. A direct call couples the caller to every side effect it triggers; an event inverts that dependency.

Example 
public sealed record OrderPlaced(OrderId OrderId, CustomerId CustomerId, Money Total) : IDomainEvent;

public sealed class Order
{
    private readonly List<IDomainEvent> _events = [];
    public void Place() { Status = OrderStatus.Placed; _events.Add(new OrderPlaced(Id, CustomerId, Total)); }
    public IReadOnlyList<IDomainEvent> DequeueEvents() { var e = _events.ToList(); _events.Clear(); return e; }
}

Follow-ups

  • Should the aggregate publish the event itself? — No — it should only record/collect it; the application layer (or unit-of-work) dispatches events after the transaction commits, so a handler never sees an event for a change that got rolled back.
  • Past tense naming — why does it matter? — It reinforces that the event is a fact about something that already happened, not a command asking for something to happen — `OrderPlaced` vs. `PlaceOrder` is a meaningful semantic difference, not style.
  • Can an aggregate raise more than one event per operation? — Yes — a single `Place()` call might raise `OrderPlaced` and, if it's the customer's first order, `FirstOrderMilestoneReached`.

Wrong answer: "A domain event is just an event handler pattern — same as a C# `event` field or a UI click handler." The mechanics can look similar, but a domain event's purpose is decoupling business side effects at the aggregate boundary, with explicit dispatch timing tied to the transaction — a raw C# `event` fired synchronously mid-method doesn't give you either.

What's the difference between a domain event and an integration event? mid

A domain event lives and dies inside one bounded context (often inside one process), is usually delivered in-process and synchronously (or synchronously-enough) within the same transaction's aftermath, and its shape is free to change whenever the internal model changes since nothing outside the context depends on it. An integration event is the subset of "things that happened" that other bounded contexts or services need to know about — it crosses a process/service boundary, typically over a message broker, needs a stable versioned contract because external consumers depend on its shape, and must be designed for at-least-once delivery and idempotent handling. Publishing every domain event directly as an integration event tightly couples your internal model to every external consumer's expectations.

Example

OrderLineDiscountRecalculated is a domain event — useful inside the Order context for updating totals, meaningless to anyone outside it. OrderPlaced (a much coarser, stable fact) is worth publishing as an integration event to Shipping and Billing — but as its own versioned message contract, not the internal domain-event type verbatim.

Follow-ups

  • Can the same event type serve both purposes? — In simple systems, yes, pragmatically; at any real scale, translate at the boundary so internal refactors don't become breaking changes for external consumers.
  • What transport is typical for integration events in .NET? — A broker (Azure Service Bus, RabbitMQ, Kafka) with a documented, versioned message schema — not a direct in-process call.
  • Do integration events need to be domain events first? — No — sometimes an integration event is deliberately coarser or different in shape, purpose-built for external consumers rather than derived one-to-one from an internal event.

Wrong answer: Serializing the internal domain event class straight onto the message bus. It works until the domain event's shape changes for an unrelated internal reason and silently breaks every external consumer who was deserializing it — the exact coupling integration events are supposed to prevent.

When should domain events be dispatched — during the transaction, or after it commits? mid

After the transaction that raised them has committed successfully — never before, and ideally not interleaved with it. If a handler runs mid-transaction and something later in the same transaction fails and rolls back, you've already told the world about something that, from the database's point of view, never happened. The common .NET pattern is: aggregates only collect events during the operation; the application/infrastructure layer dispatches them in a post-`SaveChanges` step (or via an outbox pattern for anything crossing a process boundary), so a handler only ever fires for a change that's durably persisted.

Example 
await db.SaveChangesAsync(); // commit the aggregate's state first
foreach (var evt in order.DequeueEvents())
    await mediator.Publish(evt); // dispatch only after the transaction succeeded

Follow-ups

  • What if dispatch itself fails after a successful commit? — That's exactly what the outbox pattern solves — persist the event in the same transaction as the aggregate change, then a separate dispatcher reliably delivers it, retrying independently of the original request.
  • Can a handler run in the same transaction, deliberately? — Sometimes, for a handler that must maintain strict consistency within the same bounded context — but that's an explicit, narrow exception, not the default.
  • What if you dispatch before commit and the commit then fails? — You've sent an email, called a webhook, or updated another aggregate for an order that doesn't actually exist — a real, recurring production bug class.

Wrong answer: Publishing the event synchronously from inside the aggregate's method, before `SaveChanges` runs. It's the most tempting place to put it and the most common source of "we sent a confirmation email for an order that failed to save" bugs.

How do you guarantee a domain/integration event is eventually delivered even if the process crashes right after committing the aggregate? senior

The Outbox pattern: write the event to an "outbox" table in the same database transaction as the aggregate's own change, so either both commit or neither does — no window where the state changed but the event was lost. A separate background process (or a change-data-capture feed) then reads unpublished outbox rows and delivers them to the broker or in-process dispatcher, retrying on failure, and marks them delivered once acknowledged. This trades a small amount of latency and infrastructure for a real at-least-once delivery guarantee that a bare "commit then publish" can't provide.

Example 
await using var tx = await db.Database.BeginTransactionAsync();
db.Orders.Update(order);
db.OutboxMessages.Add(new OutboxMessage(Guid.NewGuid(), nameof(OrderPlaced), JsonSerializer.Serialize(evt)));
await db.SaveChangesAsync();
await tx.CommitAsync();
// A separate OutboxProcessor polls OutboxMessages and publishes, marking rows as sent.

Follow-ups

  • Doesn't the outbox processor risk publishing the same event twice? — Yes, by design (at-least-once) — every handler downstream must be idempotent (dedupe by event ID) rather than relying on exactly-once delivery.
  • What's the alternative to a polling processor? — Change-data-capture (e.g. Debezium) tailing the outbox table's transaction log, which reduces latency and polling load at the cost of extra infrastructure.
  • Does this apply to in-process domain events too? — Usually not needed there — in-process dispatch after a successful `SaveChanges` in the same request is durable enough; the outbox earns its cost specifically for anything crossing a process boundary asynchronously.

Wrong answer: "Just publish to the message broker right after `SaveChangesAsync` returns, in a try/catch, and log if it fails." A crash between the commit and the publish call — or a broker outage — silently drops the event with no automatic recovery; logging a failure isn't the same as guaranteeing eventual delivery.

What belongs in a domain event's payload, and what's the risk of putting too much in it? mid

Enough data for a handler to act without needing to reload the aggregate for the common case — typically the aggregate's ID plus the specific facts that changed (not the entire aggregate state). Putting too much in — the full aggregate graph, every field regardless of relevance — couples every consumer to the aggregate's internal shape, makes the event awkward to version, and bloats messages that may be persisted or transmitted at volume. The right size is "what a typical handler needs," with handlers that need more free to reload the aggregate by the ID the event carries.

Example 
// Right-sized:
public sealed record OrderPlaced(OrderId OrderId, CustomerId CustomerId, Money Total, DateTimeOffset PlacedAt);
// Over-sized — leaks the whole aggregate and everything it might ever contain:
// public sealed record OrderPlaced(Order FullOrderSnapshot);

Follow-ups

  • Should the event carry the "why," not just the "what"? — Often useful — a `causationId`/`correlationId` and, for state-transition events, the previous state, if a handler plausibly needs to distinguish causes.
  • What if a handler genuinely needs the whole aggregate? — Let it load the aggregate via the ID in the event — that's a normal, explicit dependency, cheaper to reason about than a bloated event payload everyone else has to carry too.
  • Does this differ for integration events? — Integration events often carry slightly more (a denormalised subset useful to external consumers who can't easily "reload" your aggregate), but the same discipline against dumping the whole internal model applies.

Wrong answer: Attaching the entire aggregate as the event payload "so handlers have everything they might need." It maximises coupling to the aggregate's internal shape for every consumer, forever, in exchange for saving the rare handler an extra lookup.

How do domain events relate to CQRS read models — should the read model be updated directly, or only via events? senior

In a CQRS setup, the read model is a projection built and kept in sync by reacting to domain (or integration) events, not written to directly by the same code path that changes the write model — that's what makes the read side independently scalable, independently shaped for queries, and eventually consistent by design rather than by accident. A handler subscribed to `OrderPlaced` updates an `OrderSummary` read table with exactly the shape a specific screen or query needs; if a new query need appears, you add a new projection or a new handler, never a new write path into the read store from the command side.

Example 
public sealed class OrderSummaryProjector : INotificationHandler<OrderPlaced>
{
    public async Task Handle(OrderPlaced e, CancellationToken ct)
        => await readDb.OrderSummaries.UpsertAsync(new OrderSummaryRow(e.OrderId, e.CustomerId, e.Total, "Placed"), ct);
}

Follow-ups

  • What if the UI needs strong consistency right after a write? — Return the confirmation from the command's own result (the aggregate you just saved), not from re-querying a possibly-lagging read model — read your write from the write path, not the projection.
  • How do you rebuild a read model from scratch? — Replay the full event history (if event-sourced) or re-run a backfill query against the write-side data, then resume live projection from events going forward.
  • Does every CQRS system need a separate physical read database? — No — plenty run read models as separate tables or views in the same database; the separation is architectural (different write path vs. read path) before it's physical.

Wrong answer: Writing to both the write model and the read model synchronously, in the same command handler, "to avoid eventual consistency." It reintroduces tight coupling between the two sides and typically the two writes aren't even atomic together, so you get the downsides of eventual consistency without admitting to it or designing for it.

Two services process the same integration event twice — a duplicate delivery. How do you design handlers to be safe under that? senior

Design every handler to be idempotent: processing the same event twice must produce the same end state as processing it once. Concretely, that means keying off the event's unique ID (not just its content) and checking — atomically, usually via a unique constraint or an "already processed" dedupe table — whether this specific event has already been handled before applying its effect, or designing the effect itself to be naturally idempotent (an "upsert to this exact state" rather than an "increment by one"). At-least-once delivery is the honest default for almost any message broker; exactly-once delivery either doesn't exist or is expensive and narrow, so idempotency at the consumer is the standard, portable answer.

Example 
public async Task Handle(OrderPlaced e, CancellationToken ct)
{
    if (await db.ProcessedEvents.AnyAsync(x => x.EventId == e.EventId, ct)) return; // dedupe
    await inventory.Reserve(e.OrderId, e.Lines, ct);
    db.ProcessedEvents.Add(new ProcessedEvent(e.EventId, DateTimeOffset.UtcNow));
    await db.SaveChangesAsync(ct);
}

Follow-ups

  • Isn't checking-then-acting itself a race under concurrent delivery? — Yes if not careful — back it with a unique constraint on `EventId` in the same transaction as the effect, so a concurrent duplicate fails the insert rather than double-applying.
  • Does message ordering matter here too? — Often yes — most brokers guarantee ordering only within a partition/session key, so handlers that care about order (e.g. status transitions) need to key their partitioning by aggregate ID.
  • Is "at-least-once + idempotent consumer" the same as exactly-once? — Functionally, close enough for almost every business case — true exactly-once delivery across a network is famously not achievable without cooperation from both ends, which idempotency provides more cheaply.

Wrong answer: Assuming the message broker's "exactly-once" marketing claim removes the need for idempotent handlers. Nearly every real broker's exactly-once guarantee is scoped narrowly (e.g. exactly-once processing within its own transactional log, not end-to-end to your handler's side effects) — building on that assumption without idempotency is a recurring source of duplicate-charge and duplicate-email incidents.

What in-process dispatch mechanism do .NET codebases typically use for domain events, and what changed recently with the most common choice? senior

MediatR has long been the de facto standard for in-process domain-event dispatch and CQRS-style command/query handling in .NET, via its `INotification`/`INotificationHandler` pair for events and `IRequest`/`IRequestHandler` for commands and queries — lightweight, no infrastructure, just DI-resolved handlers. What changed: starting with v13.0.0 (mid-2025), MediatR moved from an Apache-licensed OSS project to a dual commercial/OSS model under RPL 1.5, requiring a license key (`MEDIATR_LICENSE_KEY` or `cfg.LicenseKey`) for continued use beyond the free tier — v12.5.0 was the last fully free release. That turned "just use MediatR" from a default into a real decision: pay for a license, pin to v12.5.0 and accept no further updates, or roll a minimal in-process mediator yourself (a handful of interfaces and a DI-based dispatcher cover 90% of what most codebases actually use MediatR for).

Example 
// The MediatR-free alternative many teams now roll for the simple in-process case:
public interface IDomainEventHandler<in TEvent> { Task Handle(TEvent e, CancellationToken ct); }

public sealed class DomainEventDispatcher(IServiceProvider sp)
{
    public async Task DispatchAsync<TEvent>(TEvent e, CancellationToken ct)
    {
        foreach (var handler in sp.GetServices<IDomainEventHandler<TEvent>>())
            await handler.Handle(e, ct);
    }
}

Follow-ups

  • Is MediatR's free tier gone entirely? — No — v13+ still ships a free tier for smaller usage; the license requirement targets larger/commercial usage, but the exact terms are worth checking against the current license page before committing either way.
  • What do teams that stay on MediatR do? — Either pay for the license (straightforward for a commercial product) or pin to the last free release (12.5.0) and accept they're on an unmaintained version going forward.
  • Does this affect CQRS itself as a pattern? — No — CQRS and the mediator pattern are independent of any specific library; this is a build-vs-buy decision about one popular implementation, not a change to the pattern.

Wrong answer: Not knowing MediatR's licensing changed at all, and citing outdated "it's free and Apache-licensed" advice. At principal/senior level this is a live build-vs-buy conversation interviewers will specifically probe to see if your knowledge is current — this is exactly the kind of thing this bank flags as a very recent, citable change.

05 Repositories & the persistence boundary

A repository provides the illusion of an in-memory collection of aggregates, hiding how they're actually persisted. It's the seam between the domain model and infrastructure, and interviewers use it to check whether you understand what a repository is for — one per aggregate root, no leaking query concerns into the domain — versus treating it as a generic data-access wrapper around an ORM. Expect a code-review-flavoured question at senior level about a repository that's grown query methods it shouldn't have.

docs: Infrastructure persistence layer design · martinfowler.com: Repository

What is a repository, and why one per aggregate root? screener

A repository gives the domain and application layers a collection-like interface — `Add`, `GetById`, `Remove` — for loading and saving aggregates, hiding the actual persistence mechanism (SQL, an ORM, a document store) behind that interface. It's one per aggregate root, not per entity or per table, because the aggregate is the transactional/consistency unit — a repository for an inner entity would let callers load and save part of an aggregate independently of the root, which breaks the invariant-enforcement the aggregate exists to guarantee.

Example 
public interface IOrderRepository
{
    Task<Order?> GetByIdAsync(OrderId id, CancellationToken ct);
    Task AddAsync(Order order, CancellationToken ct);
    // no IOrderLineRepository — OrderLine is only reachable through Order
}

Follow-ups

  • Does every aggregate need an explicit `Remove`/`Delete`? — Only if the domain actually deletes aggregates; many domains prefer a status transition (e.g. `Cancelled`) over physical deletion, in which case there's no delete method at all.
  • Where does the repository interface live, and where's it implemented? — The interface lives in the domain (or application) layer, defined by what the domain needs; the implementation lives in infrastructure, depending on the domain's interface — never the other way round.
  • Is a repository the same as a `DbSet<T>`? — No — `DbSet<T>` is a generic, query-capable ORM abstraction; a repository is a narrower, domain-shaped interface, sometimes implemented using a `DbSet<T>` underneath.

Wrong answer: "A repository is just a wrapper around `DbContext`/`DbSet` so you can unit test without a database." Testability is a nice side effect, not the reason it exists — the real reason is enforcing that aggregates are only ever loaded and saved as complete, invariant-respecting wholes.

Should a repository interface expose generic query methods like `IQueryable<T>` or a general `Find(predicate)`? mid

No — a task-oriented (or "intention-revealing") repository exposes exactly the lookups the domain actually needs, named for what they mean (`GetActiveOrdersForCustomer`, `GetByReference`), rather than leaking `IQueryable<T>` or a generic predicate through the abstraction. Exposing `IQueryable<T>` defeats the point of the abstraction — it lets any caller compose arbitrary queries against what's supposed to be a persistence-hiding seam, coupling application code to the ORM's query capabilities and making it much harder to swap the implementation or reason about what queries actually run against the aggregate.

Example 
public interface IOrderRepository
{
    Task<Order?> GetByIdAsync(OrderId id, CancellationToken ct);
    Task<IReadOnlyList<Order>> GetPendingForCustomerAsync(CustomerId id, CancellationToken ct); // intention-revealing
    // not: IQueryable<Order> Query();
}

Follow-ups

  • What about complex reporting queries that don't fit any single named method? — Those belong on the query/read side (a dedicated query object or a read-model query service), not on the aggregate repository at all — CQRS's separation applies here.
  • Isn't a task-oriented repository more methods to write and maintain? — Yes, marginally — the payoff is a much clearer picture of every actual access pattern against the aggregate, and an implementation free to be optimised per method.
  • Does this rule apply to the read side too? — No — read-side query objects are expected to be flexible and query-shaped; the "task-oriented, no leaky IQueryable" rule is specifically about the write-side aggregate repository.

Wrong answer: Exposing `IQueryable<Order>` from the repository "so I don't have to add a new method every time I need a different filter." It's the most common way a repository quietly becomes a thin ORM proxy, losing the encapsulation it was introduced to provide.

How do you implement a repository with EF Core without it becoming a leaky wrapper around `DbContext`? mid

Implement the domain-defined interface concretely against `DbContext`, keeping EF Core-specific concerns (`Include`, tracking behaviour, `AsNoTracking`) entirely inside the repository implementation, never surfaced through its interface. `SaveChangesAsync` is typically called once, at the unit-of-work boundary (often the same `DbContext` instance wrapped as a unit of work) rather than inside every repository method, so multiple repository calls within one use case still commit as a single transaction.

Example 
public sealed class OrderRepository(AppDbContext db) : IOrderRepository
{
    public async Task<Order?> GetByIdAsync(OrderId id, CancellationToken ct)
        => await db.Orders.Include(o => o.Lines).FirstOrDefaultAsync(o => o.Id == id, ct); // EF specifics stay in here

    public Task AddAsync(Order order, CancellationToken ct) { db.Orders.Add(order); return Task.CompletedTask; }
    // SaveChangesAsync is called once by the caller's unit of work, not per repository method
}

Follow-ups

  • Where does `SaveChangesAsync` get called? — Once per use case, typically in the application service or a unit-of-work abstraction wrapping the `DbContext` — not inside `AddAsync`/`GetByIdAsync` themselves.
  • Should `GetByIdAsync` use `AsNoTracking`? — No — if the caller intends to mutate and save the aggregate, it needs tracking; `AsNoTracking` is for read-only queries, which belong on the query side, not the write-side repository.
  • Is a generic `Repository<T>` base class a good idea? — Often a trap — it pushes every aggregate toward the same shape of access, re-introducing the generic-query problem; a thin, hand-written repository per aggregate is usually clearer.

Wrong answer: Injecting `DbContext` directly into application services and skipping the repository interface entirely "because EF Core is already an abstraction." It works for small apps, but it means every use case now depends directly on EF Core's API surface, and you've lost the seam that would let you enforce aggregate-shaped, intention-revealing access — or swap persistence technology at all.

How should a repository handle loading a very large aggregate — always eager-load the whole graph? mid

Load exactly what the aggregate needs to enforce its invariants for the operation at hand — which, if the aggregate is well-bounded, is usually its full graph anyway, since a well-sized aggregate doesn't have a "large, rarely-needed" portion in the first place. If a genuinely large sub-collection inside the aggregate only matters for specific operations, that's often a sign the aggregate boundary itself is too big (see Unit 02) rather than a problem to solve with lazy loading — lazy-loading proxies inside an aggregate are a common source of "N+1 query" and "DbContext disposed" bugs, and reintroduce exactly the kind of partial, inconsistent load the aggregate is supposed to prevent.

Example

An Order with 5 line items loads all 5 every time — that's fine, because every invariant (total, status transitions) needs all of them. If an Order instead had a 10,000-row embedded "full event history," that's not a lazy-loading problem to solve — it's a sign the history belongs in its own read-only projection, outside the aggregate.

Follow-ups

  • Is EF Core lazy loading ever appropriate inside a repository? — Rarely for aggregate loads — it's more defensible for read-only query-side projections where partial loading is explicitly fine.
  • What about paging an aggregate's own child collection? — If a collection is large enough to need paging, it very likely doesn't belong inside the aggregate boundary at all — split it out.
  • How do you diagnose a repository doing too much eager loading? — Profile the actual SQL — a repository generating a huge join for a simple status check is a symptom of an oversized aggregate, not an EF Core tuning problem.

Wrong answer: "Use lazy loading proxies so large aggregates only pull in what's actually accessed." Lazy loading masks an aggregate-boundary problem with an infrastructure workaround, and introduces its own class of bugs (accessing a lazy property after the `DbContext` is disposed) that a correctly-sized aggregate never needed to face.

How do you unit test domain logic without hitting a real database, given a repository interface? mid

Because the repository is an interface owned by the domain/application layer, you can substitute an in-memory fake (a simple `Dictionary`-backed implementation) or a mock in unit tests, letting you test the aggregate's behaviour and the use case's orchestration logic without any database at all — the point of the seam. The aggregate's own invariant logic ideally needs no repository at all in its tests: construct it, call its methods, assert on its state and raised events, entirely in memory.

Example 
public sealed class InMemoryOrderRepository : IOrderRepository
{
    private readonly Dictionary<OrderId, Order> _orders = [];
    public Task<Order?> GetByIdAsync(OrderId id, CancellationToken ct) => Task.FromResult(_orders.GetValueOrDefault(id));
    public Task AddAsync(Order order, CancellationToken ct) { _orders[order.Id] = order; return Task.CompletedTask; }
}
// Application-service tests use this fake; aggregate tests use no repository at all.

Follow-ups

  • Should you also test against the real database (EF Core + a test container)? — Yes, at the integration level — to catch mapping issues, real query behaviour and concurrency-token handling the in-memory fake can't exercise, but not for the domain logic itself.
  • What's the downside of over-mocking repositories in tests? — Tests that assert on "was `AddAsync` called" rather than on actual domain state or outcome, which pass even when the domain logic is subtly wrong — assert behaviour, not interaction, wherever you can.
  • Does EF Core's in-memory provider replace the need for a fake repository? — It's a poor substitute — EF Core's in-memory provider doesn't enforce real relational/constraint behaviour and Microsoft explicitly discourages relying on it for meaningful tests; prefer a hand-written fake repository or a real database in a test container.

Wrong answer: Testing domain logic exclusively through integration tests against a real (or in-memory-provider) database, with no pure unit tests of the aggregate itself. It makes the test suite slow and brittle for logic that has nothing to do with persistence, and hides which failures are actually domain bugs versus infrastructure quirks.

A repository method has grown a dozen optional filter parameters over time, used inconsistently across the codebase. How do you fix it in review? senior

That's the generic-repository anti-pattern manifesting gradually: every new screen's filtering need got bolted onto one method instead of being asked "does this belong on the write-side aggregate repository at all?" The fix is to split by responsibility — genuine aggregate-loading needs (a handful of well-named, task-oriented methods) stay on the repository; everything that's actually about querying and filtering for display moves to the read/query side as its own query object or specification, which is allowed to be as flexible as the UI needs since it's not gating write-side consistency. Do the split incrementally, method by method, redirecting callers as you go, rather than as one big-bang repository rewrite.

Example

Before: `GetOrders(customerId?, status?, fromDate?, toDate?, minTotal?, sortBy?, ...)` used differently by six call sites. After: `IOrderRepository.GetByIdAsync` (the one write-side load), plus an `OrderSearchQuery` on the read side taking a small, purpose-built filter object, backed by whatever query technology fits (LINQ, Dapper, a stored proc) without any pretense of being an aggregate-consistency boundary.

Follow-ups

  • Is the Specification pattern a good middle ground? — Yes, for composable write-side lookups that still need to stay aggregate-shaped (e.g. "orders eligible for a specific loyalty rule") — but display-driven filtering still belongs on the read side, not as ever-more specifications on the aggregate repository.
  • How do you avoid this recurring? — A review habit: any new repository parameter that exists purely to shape a UI's filtering/sorting is a signal it belongs on the query side, not the aggregate repository.
  • What's the migration risk? — Low if done incrementally — each call site moves to the new query object independently; the aggregate repository's actual contract (loading and saving whole aggregates) never has to change.

Wrong answer: Adding a thirteenth optional parameter to fix the immediate need "since the pattern's already established." Every additional parameter increases the combinatorial surface of untested filter combinations and further blurs write-side and read-side responsibilities — the immediate fix makes the underlying problem strictly worse.

Does every bounded context or every aggregate strictly need the repository pattern, or are there cases where it's overkill? senior

The repository pattern earns its cost when there's real domain logic and invariants worth protecting behind a persistence-hiding seam, and when you actually benefit from swappable or testable persistence. For a simple CRUD-shaped subdomain with no meaningful invariants beyond "the fields are valid" — a generic supporting subdomain, say — a direct, thin data-access layer (even calling EF Core's `DbContext` straight from the application service) is often perfectly adequate, and adding a repository abstraction there is ceremony without payoff. The judgment call is matching the pattern's cost to the subdomain's actual complexity, not applying it uniformly because "that's how we do persistence here."

Example

A rich Order aggregate with placement invariants, concurrency handling, and domain events deserves a proper repository. A "notification preferences" feature that's just a settings row with no business rules beyond field validation doesn't need one — a direct EF Core query in the application service is simpler and just as correct.

Follow-ups

  • Doesn't skipping the repository hurt testability for that simple case? — Marginally, but a CRUD-shaped feature usually has little domain logic worth unit-testing in isolation anyway — integration tests against a real database cover it adequately.
  • What's the risk of mixing styles in one codebase? — Confusion if the line isn't explicit — document (or enforce via architecture tests) which subdomains get the full pattern and why, so it reads as a deliberate choice, not inconsistency.
  • Should this decision ever be revisited? — Yes — if a "simple" subdomain accumulates real business rules over time, that's the signal to introduce the aggregate/repository structure then, not before it's earned.

Wrong answer: Mandating the repository pattern uniformly across every part of the system "for consistency," including parts with no real domain logic. Applying a pattern uniformly regardless of whether the underlying complexity justifies it is the same mistake as skipping it where it's actually needed — DDD's whole premise is matching modeling effort to where it pays off (see subdomain classification, Unit 01).

06 Application services, CQRS & the mediator pattern

Application services orchestrate use cases — load an aggregate, call its behaviour, save it, dispatch its events — without containing business logic themselves; CQRS separates the write model (commands, aggregates) from the read model (queries, projections); the mediator pattern is the plumbing that dispatches commands/queries/events to their handlers without callers depending on concrete handler classes. This trio is where "the domain model" meets "the actual application," and interviewers use it to check you keep business logic out of controllers and orchestration out of aggregates.

docs: Microservice application layer and Web API design · martinfowler.com: CQRS

What does an application service do, and what must it never contain? screener

An application service orchestrates a single use case: load the relevant aggregate(s) via a repository, call behaviour methods on them, persist the result, and dispatch any raised domain events — coordination, not decision-making. It must never contain business rules or invariant checks itself; those live inside the aggregate. If you find an `if` statement in an application service deciding whether an operation is allowed based on domain state, that logic almost always belongs inside the aggregate instead.

Example 
public sealed class PlaceOrderHandler(IOrderRepository repo, IUnitOfWork uow)
{
    public async Task Handle(PlaceOrderCommand cmd, CancellationToken ct)
    {
        var order = await repo.GetByIdAsync(cmd.OrderId, ct) ?? throw new NotFoundException();
        order.Place(); // the actual rule lives here, inside the aggregate
        await uow.SaveChangesAsync(ct);
    }
}

Follow-ups

  • Can an application service call more than one aggregate? — Yes, for reads or for coordinating multiple independent saves within the same use case — but each aggregate's own invariants are still enforced by the aggregate, not the service.
  • Should application services be unit tested? — Lightly — mostly to verify orchestration (repository calls, event dispatch happen), since the actual logic under test lives in the aggregate.
  • Is "application service" the same as a MediatR command handler? — Functionally, yes in most .NET codebases — a `IRequestHandler<PlaceOrderCommand>` is just an application service dispatched via the mediator instead of injected directly.

Wrong answer: Putting a validation check like `if (order.Status != OrderStatus.Draft) throw ...` in the application service instead of the aggregate. It duplicates (or worse, diverges from) the rule the aggregate should own, and the moment a second use case calls `Place()` without going through this exact service, the invariant is unprotected.

What problem does CQRS actually solve, and when is it overkill? mid

CQRS (Command Query Responsibility Segregation) separates the model used to change state (commands, going through the aggregate and its invariants) from the model used to read state (queries, which can be shaped however the query needs — denormalised, joined, cached — with no obligation to match the write model's structure). It earns its cost when the read and write shapes genuinely diverge (a complex domain model that would make for a terrible, over-joined read API) or when read and write loads need to scale independently. For a simple CRUD-shaped feature where the read shape is basically the write shape, full CQRS (separate models, maybe separate databases) is ceremony without payoff — the same judgment call as the repository pattern in Unit 05.

Example

An Order write model with normalized aggregates and enforced invariants; a read model that's a single flat `OrderListItemDto` table, pre-joined and denormalised specifically for the orders-list screen — built and kept current by a projector reacting to domain events (Unit 04), never by querying the write-side aggregates directly.

Follow-ups

  • Does CQRS require separate databases? — No — "logical CQRS" (separate models/code paths, same database) is common and often sufficient; separate physical stores are an additional, optional step taken for independent scaling.
  • Does CQRS require event sourcing? — No — they're independent and often paired, but plenty of CQRS systems have a conventional, current-state write model and just build read projections from its changes.
  • What's the simplest form of CQRS in a .NET app? — Splitting `Commands`/`Queries` namespaces and handler types even against the same `DbContext` and the same tables — the segregation is architectural before it's physical.

Wrong answer: Adopting full CQRS with separate read/write databases and event-driven projections for every feature "because it's the modern DDD way." CQRS is a targeted answer to a specific mismatch between write and read shapes or scaling needs — applying it uniformly adds real operational complexity (eventual consistency, more moving parts) to features that never needed it.

What is the mediator pattern doing for you in a CQRS/DDD codebase, concretely? mid

A mediator decouples the sender of a command/query/event from the handler that processes it — the caller depends only on the mediator and the message type (`PlaceOrderCommand`), never on a concrete `PlaceOrderHandler` class, and the mediator resolves and invokes the right handler (often via DI) at runtime. This buys you a uniform, cross-cutting place to add pipeline behaviours — logging, validation, transactions, authorization — that wrap every handler without each one repeating that plumbing, and it keeps controllers/API endpoints thin: build a message, send it, return the result.

Example 
app.MapPost("/orders/{id}/place", async (Guid id, IMediator mediator, CancellationToken ct)
    => await mediator.Send(new PlaceOrderCommand(new OrderId(id)), ct) is var _ ? Results.Ok() : Results.Problem());
// The endpoint has no idea PlaceOrderHandler exists.

Follow-ups

  • What's a "pipeline behaviour"? — Cross-cutting middleware around every handler invocation — e.g. a `LoggingBehavior<TReq,TRes>` or `ValidationBehavior<TReq,TRes>` that wraps the actual handler transparently.
  • Is a mediator required for CQRS? — No — CQRS just needs separate command/query models; a mediator is one convenient way to dispatch them, not a requirement.
  • What's the downside of a mediator? — An extra layer of indirection that can make "where does this actually run" harder to trace by just reading the code, especially for newcomers, and (see next question) a licensing/dependency decision if using a specific library.

Wrong answer: "A mediator is just for events, not commands and queries." Most .NET mediator implementations (MediatR chief among them) dispatch commands and queries via request/handler pairs (`IRequest`/`IRequestHandler`) just as much as events via notifications — it's a general in-process message dispatcher, not an event-only mechanism.

Given MediatR's licensing change, how would you decide whether to keep using it, pay for it, or replace it on an existing project? senior

Frame it as a build-vs-buy decision, not a knee-jerk migration. First check actual usage scale and whether the project is commercial in a way that triggers the license requirement, and get a real quote — for many teams, the license cost is trivial next to engineering time. If cost or procurement friction makes paying unattractive, the realistic alternative isn't "write your own MediatR clone" but recognising that most codebases use a small fraction of MediatR's surface (basic command/query/notification dispatch, maybe one or two pipeline behaviours) which a 100-150 line custom dispatcher covers, with DI-based handler resolution doing most of the work. Pin to the last free version (12.5.0) only as a stopgap, since an unmaintained dependency is its own long-term risk. The decision should be made deliberately and documented, not inherited silently from whatever the last project used.

Example

A small internal tool with light command/query dispatch and no pipeline behaviours: replace MediatR with a ~100-line custom dispatcher over a weekend, remove the dependency and the licensing question entirely. A large commercial SaaS platform already deeply invested in MediatR's request/notification pipeline and third-party libraries built on top of it: paying for the license is almost certainly cheaper than the migration risk.

Follow-ups

  • What are the free/OSS alternatives if you don't want to write your own? — Options exist (e.g. Wolverine's messaging model, or lighter mediator libraries under permissive licenses) but any it: evaluate whichever has current maintenance, not just current license terms.
  • What's the risk of writing a custom dispatcher? — Undertesting edge cases MediatR already solved (multiple handlers per notification, generic handler resolution, pipeline ordering) — budget real time for it, it's not a trivial afternoon for a nontrivial usage pattern.
  • Does this decision affect the domain model itself? — No — it's purely an infrastructure/dispatch-mechanism decision; the aggregates, commands, and handlers' actual logic are unaffected either way.

Wrong answer: Treating "MediatR went commercial" as a reason to abandon the mediator pattern and CQRS entirely. The licensing change is about one library, not the architectural pattern — conflating the two throws away a working architecture over a solvable dependency-management question.

Where should input validation happen — the API/mediator pipeline, the application service, or the domain model? mid

Layered by kind, not duplicated by accident: structural/format validation (is this field present, is it the right shape, is the string a valid email format) belongs at the boundary — API model binding or a pipeline validation behaviour — so bad requests are rejected cheaply and with good error messages before any domain code runs. Business-rule validation (is this quantity allowed given the order's current state, is this discount still valid) belongs inside the aggregate, because that's the only place with the full context and the only place that can guarantee the rule holds regardless of entry point. The two are not redundant — the boundary check protects against garbage input; the domain check protects the invariant regardless of who's calling.

Example 
// Boundary: FluentValidation or a MediatR ValidationBehavior — "is the shape right?"
public class PlaceOrderCommandValidator : AbstractValidator<PlaceOrderCommand>
{ public PlaceOrderCommandValidator() => RuleFor(x => x.OrderId).NotEmpty(); }

// Domain: the aggregate — "is this allowed given the current state?"
public void Place() { if (Lines.Count == 0) throw new DomainException("cannot place an empty order"); Status = OrderStatus.Placed; }

Follow-ups

  • Isn't checking the same thing twice wasteful? — They're rarely actually the same check — format/presence validation and business-invariant validation usually differ; where they do coincide, the small redundancy buys defense in depth.
  • Should the domain model ever trust that boundary validation already ran? — No — the domain model must be safe to call from any code path (a background job, a test, a future entry point), so it validates its own invariants unconditionally.
  • Where does authorization fit? — Usually its own pipeline concern (a MediatR behaviour or middleware) separate from both — "can this user do this" is neither a format check nor a domain invariant.

Wrong answer: Relying entirely on API-level validation (FluentValidation/data annotations) and skipping invariant checks inside the aggregate "since the request already passed validation." It leaves the domain model unsafe against any other caller — a background job, a test, an internal admin tool — that bypasses that specific API endpoint.

How do you keep an application service's transaction boundary correct when a use case touches multiple aggregates? senior

Default to the Unit 02 rule — one aggregate per transaction — and design the use case so only one aggregate is actually mutated synchronously; any other aggregate that needs to react gets a domain event handled afterward, in its own transaction. If a use case genuinely requires two aggregates to change together for correctness (rare, and worth questioning), wrap both in one database transaction deliberately and explicitly, understanding you've accepted the coupling and contention cost that comes with it — don't let it happen by accident because the application service called `SaveChangesAsync` on a shared `DbContext` touching two aggregates without thinking about it.

Example 
public async Task Handle(TransferFundsCommand cmd, CancellationToken ct)
{
    var from = await accounts.GetByIdAsync(cmd.FromAccountId, ct);
    from.Withdraw(cmd.Amount); // one aggregate, one transaction
    await uow.SaveChangesAsync(ct);
    await mediator.Publish(new FundsWithdrawn(cmd.FromAccountId, cmd.ToAccountId, cmd.Amount), ct);
    // A handler reacting to FundsWithdrawn credits the destination account in its own transaction.
}

Follow-ups

  • What if the second aggregate's update fails after the first succeeded? — That's the eventual-consistency trade-off — design a compensating action (e.g. reverse the withdrawal, or retry the credit) rather than assuming it can't happen.
  • Is a distributed transaction (two-phase commit) ever the right answer here? — Almost never in modern .NET systems — it doesn't scale well and most databases/brokers you'd want to span don't support it cleanly; sagas/compensation are the standard alternative (Unit 10).
  • How do you test this kind of use case? — Test the first aggregate's transaction in isolation, and test the event handler's reaction in isolation — the seam between them is exactly where integration tests earn their keep.

Wrong answer: Loading and mutating two aggregates in the same application-service method and calling `SaveChangesAsync` once on a shared `DbContext`, assuming EF Core's single transaction makes it "fine." It technically commits atomically today, but it silently couples two aggregates' persistence together, defeating the purpose of having drawn separate boundaries and making it much harder to later scale or move one of them independently.

What's a "command" versus a "query" in this model, and can a command ever return data? mid

A command expresses intent to change state ("place this order") and, per the strict CQS principle, shouldn't return domain data — at most an acknowledgment or an ID. A query asks for data and must never change state. In practice, most real systems relax the strict rule slightly: a command handler commonly returns the new aggregate's ID, or a lightweight result indicating success/failure/validation errors, because forcing every command to be immediately followed by a separate query for the ID it just generated is often pure friction for no real benefit.

Example 
public sealed record PlaceOrderCommand(OrderId OrderId) : IRequest<Result>; // returns success/failure, not domain data
public sealed record GetOrderQuery(OrderId OrderId) : IRequest<OrderDto>; // returns data, never mutates

Follow-ups

  • Is returning a generated ID from a `CreateOrder` command a CQS violation? — Technically yes by the strictest definition, but it's a pragmatic, widely-accepted exception — the alternative (client-generated IDs, or a mandatory follow-up query) is often worse ergonomics for no real safety gain.
  • Should a query ever trigger a side effect (like a cache warm-up)? — Avoid it — a query silently mutating anything observable breaks the caller's ability to reason about "did this change state," which is the entire point of the separation.
  • Do commands and queries need different handler interfaces? — Not necessarily mechanically (MediatR uses `IRequest<TResponse>` for both) but keeping them in separate namespaces/folders (`Commands/`, `Queries/`) keeps the intent visible even when the plumbing is shared.

Wrong answer: "CQRS means commands can never return anything, full stop — that's what makes it CQRS." Conflating the strict academic CQS principle with practical CQRS ignores that essentially every production .NET CQRS implementation returns at least an ID or a result object from commands — dogmatic purity here isn't what interviewers are checking for.

How do cross-cutting concerns (logging, retries, authorization, transactions) get applied consistently across many command/query handlers without duplicating code in each one? senior

Pipeline behaviours (MediatR's term) or middleware wrapping every handler invocation: each behaviour runs before/after the actual handler, composed in a defined order (e.g. logging outermost, then validation, then transaction, then the handler itself), registered once in DI rather than called explicitly inside every handler. This keeps handlers focused purely on orchestration logic and makes cross-cutting policy changes (add a new retry policy, tighten authorization) a one-place change instead of a sweep across every handler class.

Example 
public sealed class TransactionBehavior<TReq, TRes>(AppDbContext db) : IPipelineBehavior<TReq, TRes>
    where TReq : IRequest<TRes>
{
    public async Task<TRes> Handle(TReq req, RequestHandlerDelegate<TRes> next, CancellationToken ct)
    {
        await using var tx = await db.Database.BeginTransactionAsync(ct);
        var result = await next();
        await tx.CommitAsync(ct);
        return result;
    }
}
// Registered once: services.AddTransient(typeof(IPipelineBehavior<,>), typeof(TransactionBehavior<,>));

Follow-ups

  • Does behaviour ordering matter? — Yes, significantly — logging should usually wrap everything (including validation failures); a transaction behaviour should wrap the handler but typically run after validation, so invalid requests never open a transaction at all.
  • What if only some handlers need a particular behaviour? — Marker interfaces (e.g. `ITransactional`) let a behaviour opt specific request types in or out, rather than applying globally to every handler regardless of need.
  • Is this pattern specific to MediatR? — No — ASP.NET Core middleware is the same idea at the HTTP layer; the mediator pipeline is the equivalent one layer down, around in-process message handling.

Wrong answer: Calling a shared `Logger.Log(...)`/`Authorize(...)` helper explicitly at the top of every handler method. It works, but every new handler has to remember to call it, every policy change requires touching every handler, and it's trivially easy for one handler to be missed — exactly the duplication pipeline behaviours exist to eliminate.

07 Layered, onion, hexagonal & clean architecture

DDD doesn't mandate a specific architecture, but it needs one where the domain model has no outward dependencies — layered (with the dependency rule enforced), onion, hexagonal (ports and adapters) and Clean Architecture are the common .NET shapes that all express the same underlying idea in slightly different vocabulary. Interviewers use this to check you understand why the domain sits at the centre, not just that you can draw the concentric-circles diagram, and whether you can tell when the ceremony of strict layering is worth it.

docs: Common web application architectures · alistair.cockburn.us: Hexagonal Architecture

What's the one dependency rule that all of layered, onion, hexagonal and Clean Architecture are really expressing? screener

Dependencies point inward, toward the domain model, and never the other way — the domain layer knows nothing about the database, the UI, or any framework; infrastructure and presentation depend on the domain (often through interfaces the domain defines), not vice versa. Every named architecture style is a different diagram for the same rule: onion draws concentric rings with domain at the centre, hexagonal calls the domain's interfaces "ports" and their implementations "adapters," Clean Architecture adds an explicit use-case/application ring — but "can the domain model compile and be tested with zero references to EF Core, ASP.NET Core, or any specific database" is the actual test that matters, regardless of which diagram you drew.

Example 
// Domain project: references nothing but the BCL.
public sealed class Order { /* no [Table], no DbContext, no HttpContext anywhere */ }

// Infrastructure project: references Domain, implements its interfaces.
public sealed class OrderRepository(AppDbContext db) : IOrderRepository { /* ... */ }
// Domain never references Infrastructure — the reference arrow only ever points inward.

Follow-ups

  • How do you verify the rule holds, beyond code review? — Architecture tests (e.g. NetArchTest or a simple reflection-based check in the test suite) asserting the domain assembly has no dependency on infrastructure assemblies — turns a convention into something CI enforces.
  • Does "no framework references" mean no NuGet packages at all in the domain project? — Not quite absolute — small, dependency-free packages (e.g. a value-object base library) are usually fine; the line is "no framework that ties the domain to a specific technology choice."
  • Is this the same idea as the Dependency Inversion Principle? — Yes — these architecture styles are essentially DIP applied consistently at the level of whole layers/projects, not just individual classes.

Wrong answer: "They're basically the same thing, the names don't matter." The names don't matter for the underlying rule, but claiming that in an interview without being able to say what the rule actually is (dependencies point inward) reads as having memorised diagram labels rather than understanding what they protect.

What's the practical difference between onion architecture and hexagonal (ports and adapters)? mid

They're close enough in intent that many teams use the terms interchangeably, but the emphasis differs slightly: onion architecture's mental model is concentric layers (domain → domain services → application services → infrastructure/UI), foregrounding the layering itself; hexagonal's mental model is a domain core surrounded by symmetric "ports" (interfaces the domain/application defines for anything it needs — persistence, messaging, external APIs) and "adapters" (concrete implementations plugged into those ports), foregrounding the idea that any adapter is swappable and the domain is equally isolated from every direction (not just "the database" but also "the UI," "the message broker," "the external API client") via the same mechanism. In practice, a well-built .NET onion-architecture solution and a well-built hexagonal one look almost identical in code.

Example

Onion framing: "Infrastructure is an outer layer that depends inward." Hexagonal framing: "`IPaymentGateway` is a port; `StripePaymentGateway` and `FakePaymentGateway` are interchangeable adapters plugged into the same port" — same isolation, described from the "swap the adapter" angle rather than the "layer" angle.

Follow-ups

  • Does it matter which term I use in an interview? — Not much — what matters is demonstrating you understand the isolation goal; using either term correctly and being able to explain a port/adapter or a layer boundary concretely is what's being checked.
  • Where does Clean Architecture (Robert Martin's) fit relative to these? — It's essentially the same idea with an explicit extra ring for use cases/application logic between the domain and everything else — see the next question.
  • Is CQRS a fifth architecture style in this family? — No — CQRS is orthogonal, about splitting read/write responsibility; it composes with any of layered/onion/hexagonal/Clean rather than replacing them.

Wrong answer: Insisting there's a rigorous, important distinction between onion and hexagonal that changes how you'd structure a .NET solution. In real .NET codebases the practical folder/project structure ends up nearly identical either way — over-indexing on naming precision here misses what the interviewer is actually probing.

How does Robert Martin's Clean Architecture add to the onion/hexagonal picture, and how would you lay it out as .NET projects? mid

Clean Architecture makes explicit a ring that onion/hexagonal sometimes leave implicit: use cases (application logic/orchestration — Unit 06's application services) as their own layer, distinct from both the innermost entities/domain model and the outer infrastructure/UI. The typical .NET mapping is one project per ring: a `Domain` project (entities, value objects, aggregates, domain events, repository interfaces — no dependencies), an `Application` project (use cases/command-query handlers, depends only on `Domain`), and one or more outer projects (`Infrastructure` implementing the interfaces, `Api`/`Web` wiring everything via DI) that depend inward but are never depended on.

Example 
// Solution structure:
// MyApp.Domain          -> no project references
// MyApp.Application     -> references MyApp.Domain only
// MyApp.Infrastructure  -> references MyApp.Domain, MyApp.Application (implements their interfaces)
// MyApp.Api             -> references MyApp.Application, MyApp.Infrastructure (composition root, DI wiring)

Follow-ups

  • Does the API project reference the Domain project directly? — Often yes, for things like returning domain IDs in routes, but ideally through DTOs defined in or near the Application layer rather than leaking domain entities straight into HTTP responses.
  • Where do DTOs/view models live? — Usually in the Application layer, since they're shaped by use cases, not by the domain model directly or by a specific UI technology.
  • Is a separate physical project per layer required, or can it be folders in one project? — Folders work for small projects; separate projects make the dependency rule mechanically enforceable by the compiler (you can't accidentally reference what you haven't added a project reference to) — the C# convention scales the discipline as the codebase grows.

Wrong answer: Putting EF Core entity configuration attributes (`[Table]`, `[Column]`) directly on domain entities "for convenience since it's less code." It's a small crack that, over time, widens into the domain project needing an EF Core reference at all — exactly the coupling the whole architecture exists to prevent; use `Fluent API`/separate configuration classes in the Infrastructure layer instead.

Is strict layered/onion/hexagonal architecture always worth the ceremony, or when is it overkill? senior

It earns its cost when the domain model has real, evolving business logic worth protecting from framework churn, and when the team is large or long-lived enough that the enforced boundaries prevent accidental coupling that would otherwise accumulate. For a small CRUD-shaped service, greenfield prototype, or short-lived internal tool, the multi-project ceremony (four projects, DI wiring, interfaces for things that will only ever have one implementation) is often pure overhead — a well-organized single project with folders and a light separation of concerns delivers most of the same clarity without the friction. The judgment call mirrors Units 02 and 05: match structural investment to how much the domain logic actually needs isolating, not to what "good architecture" is supposed to look like on a diagram.

Example

A core-subdomain pricing engine with intricate, frequently-changing business rules and a multi-year roadmap: full layered separation, enforced by architecture tests, pays for itself many times over. A three-endpoint internal admin tool that reads and writes a couple of tables with no real invariants: one ASP.NET Core project with a few folders, direct EF Core usage, done — retrofitting the same rigor there is effort spent on abstraction the tool will never grow into using.

Follow-ups

  • Isn't it safer to always use the strict version "just in case it grows"? — Not free — every interface with exactly one real implementation, every extra project, is a tax paid by every future reader and every build; "just in case" isn't free insurance, it's a bet, and a lot of small tools never grow into needing it.
  • What's a middle ground? — A single project with clear internal namespace boundaries (`Domain/`, `Application/`, `Infrastructure/`) and a lighter version of the dependency rule enforced by convention/code review rather than separate assemblies — cheap to relax or tighten later.
  • How do you retrofit strict layering onto a project that's outgrown "simple"? — Incrementally — extract the domain model into its own project first (the highest-value, lowest-risk step), then split infrastructure out once real coupling pain shows up, rather than a big-bang restructure.

Wrong answer: Scaffolding every new service with the full four-project Clean Architecture template regardless of its actual complexity, "because that's our standard." Treating an architecture style as a mandatory checkbox rather than a response to actual domain complexity produces exactly the kind of cargo-cult ceremony DDD's own subdomain-classification principle (Unit 01) warns against.

Where does the application's composition root (DI container wiring) live, and why does that matter for the dependency rule? mid

At the outermost layer — typically the API/Web/Host project — because wiring concrete implementations to their interfaces (`services.AddScoped<IOrderRepository, OrderRepository>()`) necessarily requires knowing about both the interface (inner) and the concrete class (outer), and only the outermost layer is allowed to depend on everything. If the composition root lived in the Domain or Application layer, those layers would need a reference to Infrastructure to register its types — which breaks the entire dependency rule. This is also why the Domain and Application layers should generally not reference a DI container package at all; they just define interfaces and expect them to be satisfied by whoever wires up the app.

Example 
// In MyApp.Api's Program.cs — the one place allowed to know about everything:
builder.Services.AddScoped<IOrderRepository, OrderRepository>(); // Infrastructure
builder.Services.AddScoped<IClock, SystemClock>();               // Infrastructure
builder.Services.AddMediatR(cfg => cfg.RegisterServicesFromAssembly(typeof(PlaceOrderHandler).Assembly)); // Application

Follow-ups

  • Can Infrastructure register its own services via an extension method? — Yes, commonly — `services.AddInfrastructure(config)` defined inside the Infrastructure project, called from the composition root — keeps the root tidy while still only depending outward-in for the actual registration call.
  • What if a domain service genuinely needs something like `DateTime.Now`? — Abstract it behind a domain-owned interface (`IClock`) implemented in Infrastructure and injected — never call static framework/system APIs directly from domain code, for testability as much as for layering.
  • Does this rule apply to background workers/console apps the same way? — Yes — whatever hosts the app (worker service, console app, API) is the composition root regardless of hosting model; the rule is about "outermost," not about a specific project type.

Wrong answer: Having the Application layer directly reference and configure a DI container (calling `AddScoped` for its own handlers) rather than just registering itself via an extension method called from the outer host. It's a subtle crack, but it starts the Application layer depending on hosting/composition concerns that belong exclusively to the outermost layer.

A junior developer adds a NuGet package for a third-party payment SDK directly to the Domain project, since "the aggregate needs to charge the card." How do you redirect this in review? mid

The domain model shouldn't know a specific payment SDK exists at all — it should express the need abstractly ("this order requires payment to be captured") via an interface it defines (`IPaymentGateway`) and depend on nothing but that interface; the actual SDK reference belongs in Infrastructure, in a concrete adapter class implementing that interface. This isn't pedantry — the moment the payment provider changes (a real, common event), a domain-coupled SDK reference means changing domain code and re-testing business rules that have nothing to do with the switch, whereas an interface-based design means swapping one Infrastructure class.

Example 
// Domain: defines the need, references nothing external.
public interface IPaymentGateway { Task<PaymentResult> ChargeAsync(Money amount, PaymentMethod method, CancellationToken ct); }

// Infrastructure: the only place that knows Stripe (or whatever) exists.
public sealed class StripePaymentGateway(StripeClient client) : IPaymentGateway { /* SDK-specific code lives here, only here */ }

Follow-ups

  • Should the aggregate call `IPaymentGateway` directly, or should an application service? — Usually the application service — calling an external, potentially slow/failing gateway from inside the aggregate mixes an I/O-bound external call into what should be a fast, synchronous domain operation; the aggregate records intent (e.g. "awaiting payment"), the application service orchestrates the actual call.
  • What if the SDK types are needed for a value object (e.g. a currency code type)? — Judge case by case — a tiny, stable, dependency-free type might be fine to reference even from Domain; a full SDK with its own dependency tree, versioning cadence, and unrelated surface area should not be.
  • How do you catch this kind of drift before code review, systematically? — An architecture test asserting the Domain project has zero third-party package references beyond an approved allowlist, run in CI — turns "please don't do this" into a build failure.

Wrong answer: Allowing the SDK reference in Domain "just this once, we'll clean it up later, and it does need to charge the card after all." Exceptions to the dependency rule compound quickly — once one aggregate directly references a payment SDK, the next reviewer has a precedent to point to, and the isolation the architecture exists to provide erodes one "just this once" at a time.

08 Mapping the domain model with EF Core

A rich domain model — private setters, enforced invariants, value objects, aggregates that don't expose their internals for direct mutation — has to be persisted by an ORM that wants public setters and simple, flat shapes. EF Core's Fluent API is how you reconcile the two without compromising the domain model to make the mapper happy. Interviewers use this sub-area to check you can actually make DDD's modeling ideas work against a real, current EF Core version, not just describe them in the abstract.

docs: EF Core — Modeling · docs: What's new in EF Core 10

How do you map an aggregate's private/protected setters and backing collection fields so EF Core can still materialize it? mid

EF Core doesn't require public setters — it can bind to private setters (including init-only or fully private, via backing-field access configured in `OnModelCreating`) and can populate a private backing `List<T>` field exposed publicly only as `IReadOnlyList<T>`, so the aggregate's public API stays invariant-safe while EF Core still has a materialization path. This is exactly what lets an aggregate look the same whether it's freshly constructed in a unit test or reconstituted from the database — no special "ORM-friendly" public surface required.

Example 
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyList<OrderLine> Lines => _lines; // no public setter, no public Add
    public void AddLine(OrderLine line) { /* invariant checks here */ _lines.Add(line); }
}

// OnModelCreating:
modelBuilder.Entity<Order>().Property<OrderStatus>("Status").HasField("_status"); // private field
modelBuilder.Entity<Order>().Metadata.FindNavigation(nameof(Order.Lines))!
    .SetPropertyAccessMode(PropertyAccessMode.Field); // materialize via the backing field, not a setter

Follow-ups

  • Does this require a parameterless constructor? — EF Core can use a private parameterless constructor (or even a parameterized one matching property names) specifically so the public API never needs one just to satisfy the ORM.
  • What if a property genuinely has no setter at all, computed from other fields? — Don't map it — mark it `[NotMapped]` and let EF Core skip it; only backing state needs a materialization path.
  • Does this differ for records vs. classes? — Records work too, though a mutable aggregate root is more commonly a class with private setters; immutable value objects (Unit 03) are where records shine, mapped as owned types/complex types rather than as separate entities.

Wrong answer: Adding public setters and a public `List<OrderLine>` property purely so EF Core can populate them, abandoning the aggregate's encapsulation. It solves the mapping problem by giving up the exact protection the aggregate pattern exists to provide — any code anywhere can now mutate `Lines` directly, bypassing every invariant check in `AddLine`.

Owned Entity Types vs. EF Core 10's Complex Types for a value object like Money — walk through the difference and which you'd pick today. senior

Owned Entity Types (available since EF Core 2.0) let a value object be mapped without its own table, typically inlined into the owner's table — but under the hood they still have hidden entity-like identity and reference semantics: EF Core tracks them as dependent entities of the owner, which means two aggregates can't cleanly share one assigned `Money` instance, and operations like `ExecuteUpdateAsync` (bulk, no-tracking updates) don't work cleanly against them. EF Core 10 (Nov 2025) added Complex Types as a first-class alternative built specifically for value objects: true value/copy semantics, no hidden identity, support for being `null` as a whole, mapping to JSON columns, and — critically — working correctly with `ExecuteUpdateAsync`. For any new value-object mapping on EF Core 10+, Complex Types are now the recommended default; Owned Entity Types remain for backward compatibility and for the narrower cases that still need entity-like semantics (e.g. an owned type with its own identity-like key for polymorphic collections).

Example 
public readonly record struct Money(decimal Amount, string Currency);

// EF Core 10 Complex Type — the modern default for a value object:
modelBuilder.Entity<Order>().ComplexProperty(o => o.Total, cp =>
{
    cp.Property(m => m.Amount).HasColumnName("TotalAmount");
    cp.Property(m => m.Currency).HasColumnName("TotalCurrency");
});
// vs. the legacy Owned Entity Type equivalent:
// modelBuilder.Entity<Order>().OwnsOne(o => o.Total);

Follow-ups

  • Can Complex Types be nullable? — Yes — EF Core 10 supports a Complex Type being null as a whole, which Owned Entity Types historically struggled to represent cleanly.
  • What about collections of value objects (e.g. a list of `Address`)? — EF Core 10 supports complex type collections too, though check current documentation for the exact maturity/limitations at the version you're on — this area is actively evolving.
  • Do Complex Types support inheritance/polymorphism like owned entities can? — No — that's specifically a case where Owned Entity Types' entity-like semantics are still the right (or only) tool; Complex Types are deliberately simpler.

Wrong answer: "Owned Entity Types and Complex Types are basically the same feature with a new name." They solve overlapping problems but have materially different semantics — the hidden identity/reference-sharing issue with owned types is a real, documented pain point Complex Types were specifically built to fix, not a rename.

How do you map an aggregate's identity (e.g. a strongly-typed OrderId value object wrapping a Guid) as the primary key? mid

EF Core supports value converters that translate a strongly-typed ID to and from its underlying primitive at the database boundary, so the domain model keeps its strong typing (`OrderId`, not a bare `Guid`, preventing accidental mix-ups between different entities' IDs) while the database column stays a plain `Guid`/`uniqueidentifier`. Since EF Core 8, "strongly typed keys" have first-class, less-boilerplate support in some scenarios, but the value-converter approach remains the general, always-works mechanism across versions.

Example 
public readonly record struct OrderId(Guid Value);

modelBuilder.Entity<Order>().Property(o => o.Id)
    .HasConversion(id => id.Value, value => new OrderId(value));

Follow-ups

  • Why bother with a strongly-typed ID instead of a bare `Guid`? — Compile-time protection against passing a `CustomerId` where an `OrderId` is expected — a real, recurring class of bug in codebases with many Guid-keyed entities.
  • Does this add meaningful overhead? — Negligible at runtime; the main cost is the small amount of ceremony (the wrapper type, the conversion) per entity, which most teams find well worth it once the codebase has more than a handful of entity types.
  • Can value converters be reused across many ID types? — Yes — a generic converter factory or source-generated ID types (via a small library or your own `[GenerateStronglyTypedId]`-style approach) avoid repeating the conversion boilerplate per type.

Wrong answer: Using bare `Guid` properties for every entity's ID "to keep EF Core mapping simple." It's simpler to map, but it silently permits `GetOrder(customerId)`-shaped bugs that the type system would otherwise catch — the mapping convenience isn't worth giving up that safety, and the converter-based fix is only a few lines.

How do you configure optimistic concurrency (a concurrency token) for an aggregate root in EF Core? mid

Add a version/row-version property to the aggregate root and mark it as a concurrency token — `[Timestamp]`/`.IsRowVersion()` for a database-generated `rowversion` column (SQL Server), or `.IsConcurrencyToken()` on an application-managed version number for providers without a native rowversion type. EF Core includes the token's original value in the `UPDATE`'s `WHERE` clause and throws `DbUpdateConcurrencyException` if zero rows were affected — meaning someone else changed the row since you loaded it — which the application layer then has to handle (reload and retry, or surface a conflict to the user), tying back to Unit 02's aggregate-consistency discussion.

Example 
public sealed class Order
{
    public byte[] RowVersion { get; private set; } = [];
}
modelBuilder.Entity<Order>().Property(o => o.RowVersion).IsRowVersion();

// Handling the conflict:
try { await db.SaveChangesAsync(ct); }
catch (DbUpdateConcurrencyException) { /* reload, reapply, retry — or surface a conflict to the caller */ }

Follow-ups

  • Does every aggregate need a concurrency token? — Any aggregate that can plausibly be edited concurrently by more than one actor — which is most of them at real scale; it's cheap insurance even when contention is rare.
  • What's the alternative to optimistic concurrency here? — Pessimistic locking (`SELECT ... FOR UPDATE`-equivalent) — rarely the default choice in .NET/EF Core systems because it holds locks for the duration of a use case, hurting throughput; reserved for narrow, high-contention operations.
  • How do you unit test concurrency-conflict handling without a real database race? — Simulate it — load two separate `DbContext` instances of the same row, save one, then attempt to save the other and assert the exception/handling path, without needing actual concurrent threads.

Wrong answer: Skipping a concurrency token entirely and relying on "the last write wins" for aggregates that multiple users or processes can edit. It silently drops one party's change with no error and no signal to either party — a correctness bug that's easy to miss in testing because it needs genuine concurrent access to surface.

Should you use `ExecuteUpdateAsync`/`ExecuteDeleteAsync` (EF Core's bulk update/delete APIs) against aggregate roots? senior

Be deliberate — these APIs bypass change tracking and the normal `SaveChanges` pipeline entirely, updating rows directly in the database without loading entities, which means they also bypass domain events, invariant checks, and concurrency tokens on the affected aggregate. They're a great fit for genuinely bulk, invariant-free operations (e.g. "mark all orders older than 2 years as archived" as a housekeeping job) where going through individual aggregates would be needlessly slow, and a poor fit for anything that's supposed to go through the aggregate's actual business logic — using them there is a backdoor around the exact protection the aggregate exists to provide.

Example 
// Appropriate: a bulk housekeeping operation with no domain invariant at stake.
await db.Orders.Where(o => o.PlacedAt < cutoff).ExecuteUpdateAsync(s => s.SetProperty(o => o.Archived, true));
// Inappropriate: bypassing Order.Cancel()'s invariant checks and event-raising to "just update the status column."
// await db.Orders.Where(o => o.Id == id).ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Cancelled));

Follow-ups

  • Does this interact with Complex Types well, as the earlier question implied? — Yes — that's precisely one of the documented improvements EF Core 10's Complex Types bring over Owned Entity Types, which historically had friction with these bulk APIs.
  • What about domain events for a bulk operation like the archiving example? — If downstream systems need to know, either raise one coarse integration event for the whole batch, or reconsider whether this operation is really invariant-free enough to skip the aggregate — don't assume "bulk" always means "no one needs to know."
  • Is this the same trade-off as choosing raw SQL/Dapper for a query? — A related one — both are ways of stepping outside the tracked-aggregate path for performance; the same judgment (is domain logic actually at stake here) applies to both.

Wrong answer: Reaching for `ExecuteUpdateAsync` on individual aggregate updates purely because it's faster than load-mutate-save. Speed is real, but the moment the "update" you're bypassing actually enforces a business rule or needs to raise an event, you've built a second, unprotected write path into the same aggregate — exactly the crack Unit 05's repository discussion warns against.

How do you keep EF Core mapping configuration (Fluent API, `IEntityTypeConfiguration<T>`) from leaking domain concerns, at scale across many aggregates? mid

One `IEntityTypeConfiguration<TEntity>` class per aggregate/entity, living entirely in the Infrastructure layer, applied via `modelBuilder.ApplyConfigurationsFromAssembly(...)` — never inline attributes on the domain entities themselves (Unit 07's point about `[Table]`/`[Column]`), and never scattered ad hoc across a growing `OnModelCreating` method. This keeps each aggregate's persistence mapping in one discoverable place, keeps the domain assembly free of EF Core references, and scales cleanly as the number of aggregates grows — a new aggregate means one new configuration file, not a bigger shared method.

Example 
public sealed class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> b)
    {
        b.HasKey(o => o.Id);
        b.ComplexProperty(o => o.Total);
        b.HasMany(o => o.Lines).WithOne();
    }
}
// AppDbContext.OnModelCreating: modelBuilder.ApplyConfigurationsFromAssembly(typeof(OrderConfiguration).Assembly);

Follow-ups

  • Should configuration classes live next to the aggregate, or in a separate `Mapping/` folder? — Either is defensible — the key requirement is that they live in Infrastructure, not that they're physically near the domain class; team convention decides the folder.
  • How do you test that mappings are correct without a real database? — A lightweight integration test against a real (or containerized) database exercising `SaveChanges`/`FirstOrDefault` for each aggregate is more trustworthy here than trying to unit test `OnModelCreating` output directly.
  • Does this scale to hundreds of aggregates? — Yes — that's exactly the scenario `ApplyConfigurationsFromAssembly` is for; each configuration is independently discoverable and testable, unlike one large `OnModelCreating` method.

Wrong answer: Writing all entity mapping directly inside one large `OnModelCreating` override as the number of aggregates grows. It's fine at three entities and unmanageable at thirty — a method that long is itself a code-review smell, independent of DDD, but especially painful when it's the one place mapping every aggregate's persistence shape.

09 Domain services, factories & anti-corruption layers

Not every operation belongs on an entity or value object — some domain logic genuinely spans multiple aggregates, or needs external context an aggregate shouldn't hold. Domain services, factories, and anti-corruption layers are the three escape valves DDD gives you for that, each with a narrow, specific job. Interviewers use this sub-area to check you reach for the narrowest tool, and don't turn a domain service into a dumping ground for logic that actually belongs on an aggregate.

docs: Microservice domain model design · martinfowler.com: AnemicDomainModel

When does an operation belong on a domain service instead of on an entity or aggregate? screener

When the operation is a genuine domain concept but doesn't naturally belong to any single entity — it either spans multiple aggregates, needs a stateless calculation that isn't "owned" by one thing, or needs external context (like current exchange rates) that would pollute an aggregate's own state if stored there. The test is: does this operation have exactly one clear owning aggregate? If yes, put it there. If the honest answer is "it involves two aggregates" or "it's a pure function of several inputs with no natural home," it's a domain service — stateless, named for the domain concept it represents, not a generic "OrderHelper."

Example 
// Spans two aggregates — a domain service, not a method on either:
public sealed class OrderPricingService(IExchangeRateProvider rates)
{
    public Money ConvertAndApplyDiscount(Order order, Customer customer, Currency target)
    { /* needs both Order and Customer, plus external rate data — no single aggregate owns this */ }
}

Follow-ups

  • Is a domain service the same thing as an application service (Unit 06)? — No — a domain service expresses actual business logic/domain concepts and lives in the Domain layer; an application service orchestrates use cases and contains no business logic of its own, living in the Application layer.
  • Should a domain service be stateless? — Yes, essentially always — it takes its inputs as parameters and returns a result, holding no per-call state between invocations, which keeps it trivially thread-safe and easy to test.
  • Can a domain service call a repository? — Generally avoid it — that starts to blur into application-service territory; a domain service usually takes the aggregates it needs as parameters, already loaded by the caller.

Wrong answer: Creating a domain service for logic that clearly belongs to one aggregate, just because "services feel more testable/flexible." Moving an aggregate's own invariant logic out into a service produces the anemic-domain-model anti-pattern (Unit 11) — entities become bags of properties, and business rules scatter into services that have no natural home for enforcing them consistently.

What is a factory in DDD, and when does aggregate construction need one instead of a plain constructor? mid

A factory encapsulates the logic for creating a valid aggregate (or complex value object) when that creation involves enough decision-making, validation, or coordination that a plain constructor would be overloaded or would need to expose intermediate, potentially-invalid state. A plain constructor is enough when creation is simple and can enforce its invariants directly; reach for a factory (a static factory method, a dedicated factory class, or a domain service that creates aggregates) when creation needs to choose between several valid initial states, needs external input to decide validity, or when you want to name the creation intent clearly (`Order.PlaceForCustomer(...)` vs. a generic constructor).

Example 
public sealed class Order
{
    private Order(OrderId id, CustomerId customerId) { Id = id; CustomerId = customerId; Status = OrderStatus.Draft; }

    public static Order StartFor(CustomerId customerId, ICustomerEligibilityChecker checker)
    {
        if (!checker.IsEligibleToOrder(customerId)) throw new DomainException("customer is not eligible to place orders");
        return new Order(new OrderId(Guid.NewGuid()), customerId);
    }
}

Follow-ups

  • Is a static factory method on the aggregate itself still "a factory," or does it need its own class? — A static named factory method on the aggregate is the most common, lightweight form and is entirely sufficient for most cases; a separate factory class earns its keep only when creation logic is substantial enough to deserve its own tested unit, or needs dependencies the aggregate itself shouldn't hold.
  • Does a factory bypass the aggregate's own invariants? — No — it should only ever produce a fully valid aggregate; if it can't satisfy the invariants given the inputs, it throws rather than returning a partially-valid instance.
  • How does this relate to EF Core's private-constructor materialization (Unit 08)? — They're separate concerns using a similar mechanism — the EF Core materialization constructor exists purely for the ORM to reconstitute from the database; the factory method is the domain-facing way to create a genuinely new aggregate, and the two constructors/paths don't need to be the same one.

Wrong answer: Exposing a public parameterless constructor plus public setters and telling callers to "just set the fields you need after construction." That's the exact anti-pattern the aggregate/factory combination exists to prevent — it permits constructing an aggregate in an invalid intermediate state that no invariant check ever runs against.

What is an Anti-Corruption Layer, concretely, and how would you implement one against a legacy or third-party system in .NET? mid

An ACL is a translation layer that sits between your bounded context and an external system whose model you don't control (a legacy system, a third-party API, an upstream team's incompatible model), converting its concepts into your own domain's ubiquitous language and shielding your model from the external system's quirks, inconsistencies, or future changes. Concretely in .NET, it's usually a small set of adapter classes implementing an interface your domain defines, with mapping code (and often a lot of defensive handling of the external system's oddities) isolated entirely inside the adapter — nothing about the external system's shape leaks past it.

Example 
// Your domain's clean interface:
public interface IShippingRateProvider { Task<Money> GetRateAsync(Address from, Address to, Weight weight, CancellationToken ct); }

// The ACL: absorbs the legacy carrier API's weird units, string-typed statuses, and inconsistent error codes.
public sealed class LegacyCarrierRateAdapter(LegacyCarrierClient client) : IShippingRateProvider
{
    public async Task<Money> GetRateAsync(Address from, Address to, Weight weight, CancellationToken ct)
    {
        var raw = await client.GetRateInCentsAndOunces(from.ToLegacyFormat(), to.ToLegacyFormat(), weight.ToOunces(), ct);
        return new Money(raw.Cents / 100m, "USD"); // translate at the boundary, once
    }
}

Follow-ups

  • How is this different from the port/adapter idea in Unit 07? — It's the same mechanical pattern (an interface plus an adapter), specifically applied to protect against a model mismatch rather than just swappable infrastructure — the ACL's explicit purpose is translation between two different ubiquitous languages.
  • Where did this term come from originally? — Context Mapping in Eric Evans' original DDD book (Unit 01) — ACL is one of the context-mapping patterns, specifically the one for a downstream context protecting itself from an upstream (or external) model it doesn't control.
  • Does an ACL always mean a lot of code? — Not necessarily — sometimes it's a thin mapping function; the amount of code should be proportional to how different (and how untrustworthy) the external model actually is.

Wrong answer: Passing the third-party API's response DTOs directly into domain logic "since mapping them would just be extra code." It works until the third-party API changes its schema (or you switch providers) and that change now ripples directly into domain logic — the ACL's entire purpose is containing that blast radius to one translation layer.

A domain service you're reviewing takes seven different repository and provider dependencies and has grown to do "everything related to pricing." Is that a problem, and how would you fix it? senior

Yes — a domain service accumulating many unrelated dependencies and responsibilities over time is the same "God object" failure mode as an oversized aggregate (Unit 02), just manifesting on the service side. The fix is the same instinct: identify the distinct responsibilities actually being served (base-price calculation, discount eligibility, currency conversion, tax calculation) and split into focused services named for each, each with only the dependencies it actually needs — not because "smaller is always better," but because a seven-dependency service is nearly impossible to unit test meaningfully and signals that several genuinely separate concerns got merged by convenience rather than by design.

Example

Before: one `PricingService(IOrderRepo, ICustomerRepo, IExchangeRateProvider, ITaxRateProvider, IDiscountRepo, IPromotionRepo, IClock)` doing everything pricing-related. After: `DiscountEligibilityService`, `CurrencyConversionService`, `TaxCalculationService`, each independently testable with two or three dependencies, composed by whichever application service actually needs the full pricing pipeline for a given use case.

Follow-ups

  • Doesn't splitting into smaller services just move the complexity to whoever composes them? — It moves the coordination responsibility to the application layer (Unit 06), which is exactly where orchestration belongs — the domain services themselves get simpler and more testable, which is the actual win.
  • Is seven dependencies always too many? — Not a hard rule — the smell is "unrelated responsibilities," not dependency count per se; a service with seven dependencies all genuinely in service of one narrow, cohesive responsibility is a different (better) situation than seven dependencies serving five different responsibilities.
  • How do you catch this drift earlier, before it reaches seven? — Review discipline — when a new, unrelated dependency gets added to an existing service "since it's already here," ask whether it belongs to the service's actual name/responsibility or is being added for convenience.

Wrong answer: Leaving the service as one class but splitting its methods into partial classes across multiple files "to make it more manageable." That addresses file-length discomfort, not the actual problem — a class with unrelated responsibilities is still one class with unrelated responsibilities regardless of how many files its methods are spread across.

Should validation that requires checking against external state (e.g. "is this promo code still valid today") live in the aggregate, a domain service, or the application layer? senior

Split by what the check actually needs: if the aggregate already has everything required to decide (its own current state plus values passed in as parameters), keep the check inside the aggregate's method. If deciding genuinely requires querying something external at the moment of the call (today's date/time from a clock abstraction, another aggregate's current state, or a third-party system) that the aggregate shouldn't be responsible for reaching out to itself, resolve that externally first (in a domain service or the application layer) and pass the already-resolved fact into the aggregate as a parameter — the aggregate then still enforces the actual invariant, but never performs I/O or reaches outside itself to do so.

Example 
// Application/domain-service layer resolves the external fact:
var promoIsValid = await promoValidator.IsValidNow(code, clock.UtcNow);
// The aggregate enforces the invariant using the already-resolved fact, no I/O of its own:
order.ApplyPromoCode(code, promoIsValid);
public void ApplyPromoCode(PromoCode code, bool isValid)
{ if (!isValid) throw new DomainException("promo code is not currently valid"); /* ... */ }

Follow-ups

  • Why not just inject the external checker into the aggregate directly? — Aggregates should stay free of I/O and external dependencies entirely — injecting services into entities makes them hard to construct, hard to test in isolation, and blurs the "aggregates are plain in-memory objects" model that makes them easy to reason about.
  • Isn't there a race between resolving the fact and applying it? — Potentially, for time-sensitive checks — usually acceptable given the granularity involved (a promo's validity window is rarely contested at millisecond precision), but worth naming explicitly if the domain genuinely needs stronger guarantees.
  • Does this pattern have a name? — Sometimes called "pushing I/O to the edges" or keeping aggregates as pure, side-effect-free decision-makers — a specific application of the general dependency-rule discussion from Unit 07.

Wrong answer: Injecting `IPromoCodeValidator` directly into the `Order` aggregate's constructor so it can check validity itself whenever needed. It turns the aggregate into something that performs I/O and requires DI-style construction, which breaks the simple "aggregates are plain objects, easy to construct in a unit test" property that makes aggregate testing (Unit 05, Unit 14) straightforward.

How would you decide whether a new integration with an external partner API needs its own Anti-Corruption Layer, versus just calling it directly from an application service? senior

Weigh how much the external system's model actually differs from — and how much you trust the stability of — your own domain's concepts. A well-designed, stable API whose model already closely matches your ubiquitous language (or that you control, e.g. another team's well-maintained service in the same organization) may not need much beyond a straightforward client wrapper. A legacy system, a third-party API with a genuinely different conceptual model, inconsistent semantics, or one you expect to change or be replaced, justifies a real ACL — the translation cost pays for itself the first time the external system's model shifts and your domain doesn't need to change alongside it.

Example

Calling a modern, well-documented, stable internal "Customers" microservice whose model already speaks your ubiquitous language: a thin typed HTTP client is enough — full ACL ceremony would be solving a problem you don't have. Integrating a 20-year-old mainframe inventory system with inconsistent status codes and no concept of your "Reserved" state: build a proper ACL, because the translation burden and the risk of that system's quirks leaking into your domain model are both real and ongoing.

Follow-ups

  • Can you add an ACL later if you skip it initially? — Yes, and it's a common, low-risk refactor — introduce the interface first, wrap the existing direct-call code as its first adapter, no behavior change, then harden the translation as pain points surface.
  • Does trusting an internal team's API reduce the need for an ACL entirely? — Reduces it, but internal APIs still evolve and can still differ conceptually — the Customer-Supplier and Conformist context-mapping patterns from Unit 01 describe exactly this spectrum of how much protection you need even from friendly upstream teams.
  • Should the decision be revisited over time? — Yes — an integration that started simple can accumulate enough special-case handling that introducing a proper ACL retroactively is the right call, the same "revisit as complexity grows" judgment from Unit 05's repository discussion.

Wrong answer: Mandating a full Anti-Corruption Layer for every external integration regardless of how well-aligned or stable it is, "for consistency and future-proofing." Uniformly applying the heaviest translation pattern to every integration — including ones that don't need it — is the same misjudged-effort mistake DDD's subdomain classification (Unit 01) warns against, just applied to integrations instead of subdomains.

10 DDD in microservices: contexts, sagas & consistency

Bounded contexts (Unit 01) map naturally onto microservice boundaries, which is exactly why DDD and microservices are so often discussed together — but that mapping introduces distributed-systems problems (network failure, partial success, no cross-service transactions) that a single-process modular monolith doesn't have to face. This sub-area is where architecture judgment gets tested hardest: sagas, eventual consistency across services, and knowing when microservices are the wrong answer entirely.

docs: Designing a DDD-oriented microservice · microservices.io: Saga pattern

Why does "one bounded context per microservice" work well as a starting heuristic, and when does it break down? mid

A bounded context already defines a coherent model with its own ubiquitous language and its own consistency boundary, which is exactly what a well-designed service boundary should be — so aligning them means each service owns a model that makes sense on its own, without needing to coordinate schema or terminology with any other service. It breaks down when a bounded context is too large to be one deployable/scalable unit (in which case it may need splitting into several services that still share the same context/language, coordinating internally), or when teams draw service boundaries around technical layers or organizational convenience instead of actual domain boundaries — producing distributed systems with none of a bounded context's actual cohesion.

Example

A "Fulfillment" bounded context might be one service if its scale is modest, or split into "Inventory" and "Shipping" services if the load profiles diverge — but both pieces still share the same ubiquitous language and conceptual model; that's different from a service boundary drawn along technical lines like "the API layer" and "the database layer" as separate deployables, which isn't a bounded-context split at all.

Follow-ups

  • Can two bounded contexts share one microservice? — It happens, especially early on, but it reintroduces exactly the coupling bounded contexts exist to avoid — worth treating as a temporary state, not a stable design.
  • Does every bounded context need to become a microservice eventually? — No — plenty of well-modeled systems keep multiple bounded contexts inside one deployable (a "modular monolith") indefinitely; the context/language separation is the valuable part, physical service separation is optional and situational.
  • How do you recognize a service boundary drawn for the wrong reasons? — It tends to require frequent, synchronous, cross-service calls just to complete ordinary operations — a sign the boundary cuts across what should have been one cohesive model.

Wrong answer: Drawing microservice boundaries by technical layer (a "database service," a "business logic service," a "UI service") instead of by bounded context. That's the exact anti-pattern that turns a distributed system into a distributed monolith — every meaningful operation now requires multiple synchronous cross-service calls, with none of a bounded context's actual cohesion or independence.

A use case needs to update state across three microservices (e.g. place an order, reserve inventory, and charge payment). How do you keep this consistent without a distributed transaction? senior

A saga: a sequence of local transactions, each in its own service, where each step publishes an event/message that triggers the next step, and every step has a corresponding compensating action to undo its effect if a later step fails. This trades strict atomicity for eventual consistency plus explicit, designed-for failure handling — instead of "all three succeed or none do," you get "each step commits locally, and if step three fails, steps one and two are explicitly compensated (e.g. release the inventory reservation, refund/void the payment)."

Example 
// Orchestrated saga, one common style:
// 1. OrderService: creates order (status: Pending) -> publishes OrderCreated
// 2. InventoryService: reserves stock -> publishes StockReserved (or StockReservationFailed)
// 3. PaymentService: charges payment -> publishes PaymentCaptured (or PaymentFailed)
// On PaymentFailed: a compensating action releases the stock reservation and marks the order Failed.

Follow-ups

  • What's the difference between an orchestrated and a choreographed saga? — Orchestrated has a central coordinator explicitly directing each step and handling failures; choreographed has each service reacting to the previous service's event with no central coordinator — orchestration is easier to reason about and debug as the number of steps grows, choreography has less central coupling but gets hard to trace past a few steps.
  • Are saga steps required to be idempotent? — Yes — the same at-least-once delivery and idempotency discipline from Unit 04 applies to every saga step, since retries and duplicate delivery are expected, not exceptional.
  • What if a compensating action itself fails? — A real operational concern — needs retry with backoff, alerting, and often a manual-intervention/dead-letter path for cases that can't self-heal; sagas make failure handling explicit rather than eliminating the possibility of failure.

Wrong answer: Reaching for a distributed transaction protocol (two-phase commit) across the three services' databases. It's rarely supported cleanly by modern databases/brokers at this scale, doesn't handle partial network failure gracefully, and creates tight temporal coupling (all three services must be up and responsive simultaneously) that defeats much of the purpose of having separate services in the first place — sagas are the standard, better-suited answer.

How does a service in one bounded context safely reference an entity that "belongs" to another bounded context/service? mid

By ID only, never by a shared reference to the other context's actual entity or a shared database — the same principle as cross-aggregate references within one context (Unit 02), just enforced harder because there's a network and a deployment boundary in the way too. If richer data about that entity is needed locally, either query the owning service's API for it, or maintain a local, deliberately partial read-model copy (kept current via that context's published integration events) shaped for exactly what this context needs — never assume you can reach into another bounded context's database or internal model directly.

Example 
// Inside the Shipping context, referencing a Customer that belongs to the Customer context:
public sealed class ShippingProfile
{
    public CustomerId CustomerId { get; } // reference by ID only
    public Address DeliveryAddress { get; } // Shipping's own concept, not borrowed from Customer's model
}
// If Shipping needs the customer's name for a label, it keeps its own small, denormalized copy,
// updated by reacting to a CustomerRenamed integration event — not by querying Customer's database directly.

Follow-ups

  • Isn't querying the owning service's API synchronously simpler than maintaining a local copy? — Simpler, and fine for low-volume/latency-tolerant reads — but it couples your context's availability to the other service's uptime and adds latency; a local, event-kept-current copy trades storage/consistency-lag for independence.
  • Does sharing a database between two services violate this? — Yes, directly — a shared database is the most common way bounded-context isolation quietly erodes in microservice systems; each service should own its own data store.
  • What if the other context's model genuinely changes shape? — Only the small mapping/translation code reacting to its integration events needs to change — this is the direct microservices analogue of the Anti-Corruption Layer discussion in Unit 09.

Wrong answer: Giving the Shipping service direct read access to the Customer service's database "just for this one read-heavy report." It's the single most common way microservice boundaries erode in practice — the moment one service depends on another's internal schema, that schema can no longer change independently, which defeats the entire point of having drawn separate services.

How do you handle a query that needs data spanning multiple bounded contexts/services, without collapsing them back into one? senior

Build a dedicated read-side aggregator — either an API composition layer (a backend-for-frontend or API gateway that calls multiple services' APIs and combines results per request) for read-after-write-tolerant, moderate-volume cases, or a materialized cross-context read model (a service or table that subscribes to integration events from each relevant context and maintains its own denormalized, query-optimized copy) for high-volume or latency-sensitive queries. Either way, the composition/aggregation logic lives outside any single bounded context — it's explicitly a read-side, cross-context concern, not something any one context's model should be twisted to support directly.

Example

A "customer order history with current shipping status" screen needs Order data and Shipping data. Rather than having the Order service reach into Shipping's database, a small "Order History" read service subscribes to both contexts' relevant events (`OrderPlaced`, `ShipmentDelivered`) and maintains its own combined, denormalized view purpose-built for that screen.

Follow-ups

  • Doesn't this multiply the number of moving parts in the system? — Yes, meaningfully — this is exactly why the decision to physically split services (rather than keep contexts together in a modular monolith) should be made deliberately, weighing that operational cost against the scaling/team-autonomy benefit.
  • Is API composition or event-driven materialization the "right" default? — Neither universally — API composition is simpler to build and reason about for low-to-moderate query volume; materialized views pay off once composition's per-request fan-out latency or the called services' load becomes a problem.
  • Who owns the cross-context read model? — Usually a dedicated team/service boundary of its own (sometimes informally "the reporting/BFF team"), explicitly not owned by either of the source contexts, to avoid it becoming a backdoor coupling point.

Wrong answer: Merging the two bounded contexts back into one service "since they're queried together so often." Query co-occurrence doesn't imply the underlying domain concepts should share a model or a consistency boundary — it's a read-side composition problem, and solving it by collapsing the write-side boundaries throws away the isolation those boundaries were drawn to provide.

What are the specific new risks Bounded Contexts + microservices introduce that a modular monolith with the same context boundaries doesn't have? senior

Network partial failure (a call can fail, time out, or succeed-but-the-response-is-lost, none of which happen with an in-process method call), the loss of any cross-context transaction (forcing eventual consistency and sagas for anything that used to be a simple multi-aggregate transaction), independent deployability creating version-compatibility concerns between services evolving at different rates, and genuinely harder debugging/observability (a single user-visible failure can originate in any of several services, requiring distributed tracing to even locate). None of these are DDD problems specifically — they're the standard microservices tax — but choosing to physically split bounded contexts into separate services means accepting all of them, on top of whatever the actual domain complexity already required.

Example

In a modular monolith, "place order, reserve inventory" is one in-process call sequence inside one transaction, trivially rolled back together on failure. Split into two services, the same operation needs a saga, idempotent handlers, distributed tracing to debug a failure, and careful thought about what "in-flight, partially reserved" state looks like to a user checking order status mid-saga.

Follow-ups

  • Does this mean microservices are usually the wrong choice? — Not universally, but it means the decision should be justified by an actual need (independent scaling, independent team ownership/deployment cadence, genuinely different technology needs) rather than assumed as a default "modern" architecture.
  • What's the cheapest way to get some of the benefit without full physical separation? — A modular monolith: enforce bounded-context isolation (separate modules/projects, no shared database tables across contexts, communication via well-defined in-process interfaces or events) without the network/deployment overhead — a genuinely common and often underrated middle ground.
  • How do observability requirements change? — Distributed tracing (correlation IDs propagated across service calls, structured logging tied to a trace ID) becomes close to mandatory rather than a nice-to-have, since a single failure now spans process boundaries.

Wrong answer: "DDD basically requires microservices, so drawing bounded contexts means you should split into services." DDD says nothing about deployment topology — Eric Evans' original work predates microservices as a term; bounded contexts are a modeling and team-boundary concept that can be realized as modules in one deployable just as validly as separate services, and the choice should be driven by operational needs, not by having drawn context boundaries.

You're advising a team that split a well-modeled monolith into microservices along its existing bounded contexts, and the result is slower delivery and more incidents. How do you diagnose whether the split itself was premature? senior

Look for the specific symptoms of a split that outran its justification: frequent synchronous cross-service calls for routine operations (suggesting the contexts weren't as independent as assumed, or were split too finely), a small team now maintaining many services' worth of deployment/observability/on-call overhead disproportionate to actual scaling or ownership needs, and incidents whose root cause is cross-service consistency/timing rather than actual domain-logic bugs. If most incidents trace back to distributed-systems mechanics (a saga step's timing, a stale read model, a service being briefly unavailable) rather than the domain model itself, that's a strong signal the split's operational cost is currently exceeding its benefit for this team's actual scale.

Example

A five-person team running twelve microservices for what's genuinely one product with modest traffic, where every deploy requires coordinating three services and every incident retro ends in "the saga didn't handle this failure mode" — the diagnosis here usually isn't "write better sagas," it's "this team doesn't yet have the scale or organizational shape that justified the split in the first place."

Follow-ups

  • Is the fix always "merge back into a monolith"? — Not necessarily full reversal — sometimes it's merging a subset of overly-fine-grained services back together while keeping others split, matching granularity to where independent scaling/ownership genuinely pays off.
  • How do you present this without it reading as blaming the original decision? — Frame it as new information — the split was a reasonable bet given what was known then; the incident/delivery data since is exactly the feedback that should inform revisiting it, the same iterative judgment DDD applies to subdomain classification (Unit 01) over time.
  • What's a lower-risk first step than a full re-merge? — Identify the specific services with the highest cross-service chatter and merge just those, observing whether delivery speed and incident rate improve before deciding on any further consolidation.

Wrong answer: Concluding the team just needs better tooling (more distributed tracing, a better service mesh, more resilience patterns) without questioning whether the service boundaries themselves matched the team's actual scale and organizational shape. Tooling can genuinely help, but if the underlying problem is that the split doesn't match the team's size or the domain's actual coupling, better tooling treats the symptom while the mismatch keeps generating new incidents.

How do integration events (Unit 04) and sagas relate — is a saga just "a bunch of event handlers"? mid

They're closely related but not identical: integration events are the messages that flow between services; a saga is the pattern that gives those messages a coherent, stateful sequence with explicit success and compensation paths for a specific multi-step business process. A choreographed saga is indeed implemented as a chain of event handlers, each publishing the next event — but what makes it a saga rather than just "some services react to some events" is that someone has explicitly designed the full sequence, including every failure branch and its compensating action; ad hoc event reactions without that designed-for-failure completeness are not a saga, they're just an event chain that happens to work in the happy path.

Example

Reacting to `OrderPlaced` by sending a confirmation email is a simple event handler, not a saga — nothing needs compensating if it fails, you just retry sending the email. `OrderPlaced` → reserve inventory → charge payment → confirm, with an explicit "release inventory and cancel order" path if payment fails, is a saga — it's the compensation design, not the event-driven mechanics alone, that makes it one.

Follow-ups

  • Does a saga need a persisted "saga state" record? — For an orchestrated saga, usually yes — the orchestrator needs to track which step a given process instance is at, to know what to do on timeout or failure; a choreographed saga's state is implicit and spread across each service's own local state instead.
  • Is there tooling in .NET specifically for sagas? — Yes — several service-bus/messaging libraries (e.g. MassTransit's saga state machines, NServiceBus sagas) provide first-class saga orchestration support rather than hand-rolling one from raw event handlers.
  • Can a saga span more than one bounded context conceptually, or is it always cross-service? — It's specifically the pattern for cross-transaction-boundary processes — usually cross-service in a microservices context, but the same idea applies to any process spanning multiple aggregates/consistency boundaries, even within one service, if a distributed-transaction-shaped problem exists there too.

Wrong answer: "A saga is just marketing for event-driven architecture — if you're using events, you already have sagas." Plenty of legitimate event-driven systems have no sagas at all because no process genuinely needs multi-step compensation — calling every event reaction a saga blurs a specific, deliberately-designed pattern with the general (and much more common) case of simple, independent event handling.

11 Anti-patterns & code-review judgment

Most senior/principal DDD interviewing is really code-review judgment in disguise — recognizing a specific anti-pattern in a snippet or a description, naming why it's a problem, and knowing what to do about it without over-correcting. This unit gathers the anti-patterns not already covered in depth elsewhere (anemic models, transaction scripts masquerading as DDD, and the general "DDD applied where it doesn't pay off") into direct, spot-the-problem questions.

martinfowler.com: AnemicDomainModel · docs: DDD-oriented microservice patterns

What is an anemic domain model, and why is it specifically called out as an anti-pattern rather than just "a simple design"? screener

An anemic domain model is a set of classes named after domain concepts but containing only data — public getters and setters, no behavior — with all actual business logic living elsewhere, typically in a sprawl of "service" classes that operate on those data bags. Martin Fowler calls it out specifically because it looks like object-oriented / domain-driven design (there are classes named `Order`, `Customer`) while providing none of the actual benefits — invariants aren't enforced at the point of change because there's no behavior to enforce them, so the same validation logic tends to get duplicated (or, worse, inconsistently reimplemented) across every service that touches the data.

Example 
// Anemic: pure data, no behavior, no protection.
public class Order { public OrderStatus Status { get; set; } public List<OrderLine> Lines { get; set; } = []; }
public class OrderService
{
    public void Place(Order order) { if (order.Lines.Count == 0) throw new Exception(); order.Status = OrderStatus.Placed; }
    // Every other service touching Order.Status has to remember (or forget) this same check.
}

Follow-ups

  • Is every DTO an anemic domain model? — No — a DTO is explicitly meant to be a plain data carrier for transport/display, not a stand-in for domain behavior; the anti-pattern is specifically about entities/aggregates that should own behavior but don't.
  • Can an anemic model still technically work? — Yes, often for a long time — that's exactly why it's insidious; the cost shows up gradually as validation logic drifts out of sync across services, not as an immediate failure.
  • What's the one-line fix philosophy? — Move behavior onto the object that owns the data — `order.Place()` enforcing its own invariant, rather than `OrderService.Place(order)` reaching in and mutating public setters.

Wrong answer: "It's fine as long as the service layer is well-tested — the logic is correct, it's just organized differently." Correctness today doesn't prevent the drift problem — the moment a second service needs to change an `Order`'s status and doesn't know about (or forgets) the first service's validation, the invariant silently breaks somewhere the tests for the first service will never catch.

What's a "transaction script" and how do you tell it apart from a legitimately thin, CRUD-appropriate application service? mid

A transaction script is a procedural method that does everything a use case needs — validation, business logic, database calls — as one linear sequence of steps, with no domain model in between; it's a legitimate, simpler alternative to DDD for genuinely simple domains (Unit 05/09's recurring "when is the heavier pattern overkill" theme), but becomes an anti-pattern when the underlying domain actually has real invariants and behavior that deserve to live in a model, and instead got flattened into procedural steps scattered across many such scripts. The tell is whether the same business rule appears, slightly differently worded, inside multiple transaction scripts — that's a sign of real domain logic being manually re-implemented per use case instead of being centralized in a model.

Example

A "deactivate stale user accounts" script that queries, checks a date, and updates a flag — appropriate as a transaction script if that's genuinely the entire rule. If three other scripts elsewhere in the codebase also each contain their own slightly different version of "what makes an order eligible for cancellation," that's transaction-script proliferation hiding domain logic that should have been `Order.Cancel()`.

Follow-ups

  • Is transaction script always wrong for DDD-flavored codebases? — No — Martin Fowler explicitly presents it as a legitimate pattern for simple domains; it's only an anti-pattern relative to a domain that's complex enough to need a real model and doesn't have one.
  • How do you spot this in review without reading every script? — Grep for the same validation phrase/condition appearing in multiple handler classes — near-duplicate business-rule checks across files is the concrete signal.
  • What's the incremental fix? — Extract the duplicated rule into the entity/aggregate it actually concerns, one rule at a time, redirecting each script to call it — the same incremental-extraction approach used throughout this bank (Units 02, 05, 08) rather than a big-bang rewrite.

Wrong answer: Treating every transaction script anywhere in the codebase as automatically wrong and something to eliminate. Plenty of genuinely simple operations are correctly implemented as transaction scripts — the anti-pattern is specifically duplicated/scattered domain logic, not the existence of any procedural code at all.

Code review: a public setter has been added to an aggregate's previously read-only property "just so a script can bulk-fix some bad data." What do you say? mid

Push back on the setter and solve the actual need differently — a public setter added for a one-off fix doesn't go away after the fix; it stays as a permanent, invariant-bypassing door for every future caller, including ones with no idea it was meant to be a one-time escape hatch. Prefer a purpose-built, narrowly-scoped method that expresses the actual intent (`Order.CorrectMisRecordedTotal(Money correctTotal)`, ideally still enforcing whatever invariants still apply) or, for a genuine one-off data fix, a direct, reviewed SQL/migration script run once outside the domain model entirely rather than permanently weakening the aggregate's public API.

Example

Instead of adding `public Money Total { get; set; }` to fix a handful of bad rows, either add `internal` visibility scoped to a dedicated one-time fixer type in the same assembly, or just run a one-off SQL `UPDATE` as a reviewed, logged migration — the aggregate's public contract for every other caller stays exactly as protected as it was before the bad data existed.

Follow-ups

  • Isn't a one-off SQL fix "outside the domain model" itself risky? — Yes, and that's the honest trade-off — it's risky in a contained, reviewed, one-time way, versus a public setter which is risky in an ongoing, uncontained way for the rest of the aggregate's life.
  • What if bad data like this keeps recurring? — That's a signal the aggregate's invariants have a gap somewhere upstream (a missing validation on creation, a bug in a specific code path) — worth root-causing rather than building permanent bulk-fix tooling around a public setter.
  • Is there a case where the setter really is the right call? — Rare, and worth naming explicitly as "we are deliberately weakening this invariant permanently for this reason" rather than smuggling it in as a quiet side effect of one bug fix.

Wrong answer: Approving the setter "temporarily" with a `// TODO: remove after data fix` comment. TODO comments asking future readers to remove a capability are reliably never acted on — the setter becomes permanent, and the aggregate is now weaker forever for the sake of a fix that took an afternoon.

You see a "God service" — a single class injected into nearly every handler in the codebase, with dozens of unrelated methods. How do you approach breaking it apart without a risky big-bang rewrite? senior

Same incremental-extraction discipline used throughout this bank: don't attempt one large refactor; instead, group the God service's methods by actual responsibility (they usually cluster naturally once you list them out), extract one cohesive group into its own focused service, redirect its callers, verify, and repeat. Prioritize extracting the highest-churn or highest-risk cluster first (the one causing the most review friction or bugs), since that's where the payoff is immediate; leave lower-risk clusters for later passes rather than blocking the whole effort on doing it all at once.

Example

A `CustomerService` with forty methods spanning authentication, address validation, loyalty-points calculation, and email preferences: list every method, notice the four natural clusters, extract `LoyaltyPointsService` first (say it's the one under active, error-prone development), redirect its three callers, ship, then repeat for the next cluster next sprint — never touching all forty methods in one PR.

Follow-ups

  • How do you avoid breaking the extraction into something that's just as tangled? — Name the new service for the responsibility, not for a technical grouping — a service earns the name "LoyaltyPointsService" only if every method in it is actually about loyalty points; if that's not obviously true, the clustering step needs more thought first.
  • Should this be done alongside a broader push toward aggregates/bounded contexts? — Often, yes — a God service is frequently a symptom of the same underlying issue as a missing bounded-context boundary (Unit 01); breaking it up is a good opportunity to notice where those boundaries actually are.
  • What tests give you confidence during the extraction? — Characterization tests around the God service's existing behavior before touching anything, so each extraction step can be verified as behavior-preserving rather than trusted on inspection alone.

Wrong answer: Scheduling a dedicated multi-week "big refactor" sprint to split the God service into its final target architecture all at once. Big-bang refactors of widely-depended-on code carry high regression risk and tend to stall or get abandoned partway through when priorities shift — the incremental, one-cluster-at-a-time approach delivers value continuously and is far easier to stop safely partway through if needed.

What's the difference between rich, expressive domain logic and simply over-engineering a simple problem with unnecessary DDD ceremony — how do you tell the two apart in review? senior

Ask whether the ceremony (a value object, a domain event, a separate aggregate, a repository) is actually protecting an invariant or expressing a distinction that matters to the business, versus simply mirroring a pattern because "that's how we do DDD here." Rich modeling that pays for itself reads as clarifying — a `Money` value object stops a currency-mismatch bug that plain decimals would allow; a domain event decouples two things that genuinely need to vary independently. Ceremony without payoff reads as friction — a value object wrapping a string with no validation or behavior beyond what the primitive already gave you, a domain event with exactly one hardcoded handler that will never have a second, a repository interface with exactly one implementation and no test ever substituting a fake for it.

Example

A `Money` value object preventing a `decimal` amount from silently being compared or added across different currencies: rich modeling with a real, demonstrable payoff. An `OrderNumber` value object that's just a `string` with no validation, no formatting logic, and no behavior beyond `.Value`, introduced "for consistency with the other value objects": ceremony with no payoff — a plain string typed via `readonly record struct OrderNumber(string Value)` for type-safety is fine, but if it's being sold as "rich domain modeling" it's overstating what it actually does.

Follow-ups

  • Is "ceremony without payoff today" always wrong, even if it might pay off later? — Judge against actual, foreseeable need rather than hypothetical future complexity — this is the same "premature abstraction" trade-off as everywhere else in software, not something unique to DDD.
  • How do you raise this in review without sounding like you're against DDD generally? — Frame it around the specific invariant or behavior in question — "what does this value object protect that a plain string/decimal wouldn't?" is a concrete, answerable question, not an ideological objection.
  • Does this same judgment apply to bounded contexts and microservices? — Yes — Unit 10's discussion of over-early microservice splitting is exactly this same anti-pattern at the architecture-topology level rather than the code level.

Wrong answer: Treating "more DDD patterns applied" as inherently better craftsmanship, independent of whether they solve an actual problem in this specific codebase. DDD's own founding premise — concentrate modeling effort where the domain is actually complex, don't uniformly apply it everywhere — makes "we used all the patterns" the wrong metric; the right metric is whether the patterns used are earning their complexity cost where they were applied.

A pull request introduces a new aggregate that has getters and setters for every field, plus a repository, plus a domain event on every property change. What's actually wrong here, beyond "this seems like a lot"? mid

Public setters for every field mean it's an anemic model wearing DDD's clothing — the aggregate/repository/event scaffolding is present, but nothing is actually protected, since any caller can still set any field directly and bypass whatever behavior methods exist alongside the setters. A domain event per property change, meanwhile, usually signals events are being used as a generic "something changed" notification mechanism rather than to represent meaningful business facts — most property-level changes aren't independently significant to anything else in the system, and firing an event for each one creates event-handling noise without matching how the business actually thinks about what happened.

Example

`Order` with `public OrderStatus Status { get; set; }` plus a `StatusChanged` event fired from the setter, rather than `Status` being privately set only inside meaningful methods like `Place()`/`Cancel()`/`Ship()`, each raising the specific, meaningful event (`OrderPlaced`, `OrderCancelled`) that matches how the business actually describes what happened — not a generic `StatusChanged(oldValue, newValue)` for every transition indiscriminately.

Follow-ups

  • Is a generic `PropertyChanged`-style event ever appropriate on an aggregate? — Rarely for domain events specifically — it's a UI/data-binding pattern (INotifyPropertyChanged), not a domain-modeling one; domain events should represent meaningful business occurrences, not generic mutation notifications.
  • What's the fix, concretely, in review? — Remove the setters, add named methods for each meaningful state transition, and replace the generic property-change event with specific, meaningfully-named events raised only from those methods.
  • How do you avoid this pattern being introduced in the first place? — A team convention/architecture test flagging public setters on aggregate roots — turning "don't do this" into something caught mechanically before review even starts.

Wrong answer: Approving the PR because "it has all the DDD building blocks — aggregate, repository, events — so it follows the pattern." Counting the presence of pattern names rather than checking whether they're actually doing their job is exactly how an anemic model with DDD-shaped scaffolding gets through review.

12 Event sourcing & CQRS read models

Event sourcing takes the domain-events idea from Unit 04 one step further: instead of storing an aggregate's current state, you store the full sequence of events that produced it, and derive current state by replaying them. It's a genuinely different persistence model with real benefits (a complete audit trail, the ability to build new read models from history) and real costs, and interviewers use it to check you know it's optional — not a required part of DDD — and can reason about when it's worth the cost.

docs: Event Sourcing pattern · martinfowler.com: Event Sourcing

What is event sourcing, and how does it differ from "just" using domain events (Unit 04) alongside conventional current-state persistence? mid

With conventional persistence, domain events are dispatched as a side effect after saving current state — the events themselves aren't the system of record, the current-state table is. With event sourcing, the events are the system of record — an aggregate's current state is never stored directly; it's derived by loading every event ever raised for that aggregate and replaying them, in order, against the aggregate's logic. This is a fundamentally different persistence strategy, not an extension of "publish events after saving" — an event-sourced aggregate has no "current row" to update at all, only an ever-growing, append-only event stream.

Example 
// Conventional: current state is the source of truth; events are a side effect of change.
// Order table: { Id, Status, Total } — events published, but not the thing you reload from.

// Event-sourced: the event stream IS the source of truth.
// EventStream for OrderId=42: [ OrderCreated, LineAdded, LineAdded, OrderPlaced ]
// Current state = fold(events) — replay each event's effect in order to arrive at "now."

Follow-ups

  • Does event sourcing require CQRS? — Not strictly, but they're almost always paired in practice — replaying a full event stream to answer every query is usually too slow, so a separate, continuously-updated read model (see below) is the practical answer, which is CQRS.
  • Is event sourcing part of "core" DDD? — No — Eric Evans' original DDD book doesn't require or even emphasize it; it's a persistence-strategy choice that composes well with aggregates and domain events but is entirely optional.
  • What happens to an aggregate's invariant checks in an event-sourced model? — They still run the same way — a command still loads (replays) the aggregate to its current state, calls a behavior method that validates and, if valid, produces a new event; only the persistence mechanism changed, not the domain logic.

Wrong answer: "Event sourcing just means you also keep an audit log/event table alongside your normal current-state tables." That's a useful, much simpler pattern (sometimes called an "event log" or the audit-trail-only approach) but it isn't event sourcing — the defining property of event sourcing is that the event stream is the only source of truth, with no independently-persisted current-state row to fall back on.

How do you reconstruct an aggregate's current state from its event stream, and how do you avoid replaying thousands of events on every load? senior

Reconstruction is a fold: start from the aggregate's initial/empty state and apply each event's effect in order, typically via an `Apply(SomeEvent e)` method per event type that mutates internal state (no validation here — validation already happened when the event was originally raised; replay is purely mechanical state reconstruction). To avoid replaying a long history every time, use snapshotting: periodically persist a snapshot of the aggregate's current state alongside the event stream position it represents, and on load, start from the latest snapshot and replay only the events after it, rather than from the beginning of time.

Example 
public sealed class Order
{
    public static Order LoadFromHistory(IEnumerable<IDomainEvent> events)
    {
        var order = new Order();
        foreach (var e in events) order.Apply(e); // pure state reconstruction, no invariant checks here
        return order;
    }
    private void Apply(OrderPlaced e) { Status = OrderStatus.Placed; }
    private void Apply(LineAdded e) { _lines.Add(new OrderLine(e.ProductId, e.Quantity)); }
}
// Snapshotting: LoadFromHistory(snapshot, eventsSinceSnapshot) instead of the full history each time.

Follow-ups

  • Does replay logic ever need to change after events have already been stored? — The `Apply` methods can evolve (bug fixes, refactoring) as long as they still interpret old event shapes correctly — this is exactly why event versioning (below) matters so much for event-sourced systems specifically.
  • Should invariant validation ever run during replay? — No — replaying history reconstructs a state that was already validated when originally produced; re-validating during replay risks rejecting legitimate history if a rule has since tightened.
  • How often should snapshots be taken? — A judgment call based on stream length and load frequency — e.g. every N events, or on a schedule — balancing snapshot storage/maintenance cost against replay cost.

Wrong answer: Loading and replaying an aggregate's entire event history on every single command, with no snapshotting strategy at all, regardless of stream length. It works fine for short streams and becomes a real, worsening performance problem for long-lived, frequently-modified aggregates — worth addressing before it's a production incident, not after.

An event's shape needs to change (a field renamed, a new required field added) but old events in the store still have the old shape. How do you handle this? senior

Event versioning: never mutate the meaning of an already-stored event type; instead, either make the change backward-compatible (a new field with a sensible default when absent from old events, so old and new events both deserialize into the same current shape) or introduce an explicit new version of the event type (`OrderPlacedV2`) with an upcaster/migration step that transforms old-shaped events into the new shape at read time, keeping the `Apply` logic simple and only ever dealing with the current shape. The event store's append-only nature makes this unavoidable — you can never simply "run a migration" to change historical events the way you might with a conventional current-state table, because the events themselves are permanent history.

Example 
// Old event, already persisted, can never be changed in place:
public sealed record OrderPlaced(OrderId OrderId, Money Total);
// New requirement: need a PlacedBy field. Don't mutate the old record — version it, or default it:
public sealed record OrderPlacedV2(OrderId OrderId, Money Total, UserId? PlacedBy) : IUpcastFrom<OrderPlaced>
{
    public static OrderPlacedV2 Upcast(OrderPlaced old) => new(old.OrderId, old.Total, PlacedBy: null); // old events: unknown
}

Follow-ups

  • Is this harder than schema migration in a conventional relational model? — Genuinely, yes — it's one of event sourcing's real, ongoing costs, not a one-time setup cost; every event shape change from here on needs this same care, indefinitely.
  • Can you ever delete old event types once nothing reads them anymore? — Only once you're certain no aggregate's replay path (including from the very beginning of any stream) still needs to interpret that shape — often "never, in practice," which is part of the cost calculus.
  • Does snapshotting reduce this burden? — Somewhat — a snapshot taken after an upcast is applied means older raw event shapes matter less going forward, but you still need the upcast logic to exist for full replays and audits.

Wrong answer: Writing a one-off script to rewrite historical events in the event store to the new shape "to keep things simple going forward." Mutating the append-only event log defeats the core guarantee event sourcing is chosen for — an immutable, trustworthy history — and if anything downstream (an audit requirement, a rebuilt read model) depended on the original recorded shape, that history is now permanently altered and unrecoverable.

How do you build and rebuild a CQRS read model from an event-sourced write side? mid

A projector subscribes to the event stream (either the aggregate-level event stream directly, or a global/category stream depending on the event store's capabilities) and, for each event, updates a denormalized read-model table shaped for a specific query need — the same idea as Unit 04's projection discussion, just now backed by the full, replayable event history rather than just live dispatch. Rebuilding from scratch is a genuine strength of event sourcing: replay the entire event history from the beginning through the projector's logic to regenerate the read model — useful after a bug in projection logic, or when introducing a brand-new read model for a query need that didn't exist before but whose data was always implicitly present in history.

Example 
public sealed class OrderSummaryProjector
{
    public void Project(IDomainEvent e, OrderSummaryReadDb db)
    {
        switch (e)
        {
            case OrderPlaced p: db.Upsert(new OrderSummaryRow(p.OrderId, "Placed", p.Total)); break;
            case OrderCancelled c: db.UpdateStatus(c.OrderId, "Cancelled"); break;
        }
    }
}
// Rebuild: db.Clear(); foreach (var e in eventStore.ReadAllEventsFromBeginning()) projector.Project(e, db);

Follow-ups

  • Is rebuilding a read model from scratch expensive? — Proportional to total history length — for very large, long-lived systems this can be substantial, sometimes mitigated by periodic read-model snapshots of its own, or by rebuilding incrementally rather than always from the absolute beginning.
  • Can a projector fail partway through and leave the read model inconsistent? — Yes — projectors need the same idempotent, resumable design as any event handler (Unit 04); track the last successfully-processed event position so a restart resumes rather than reprocessing or skipping.
  • Does the read model need to live in the same database as the event store? — No, and usually shouldn't — the read model is free to live wherever best serves its query shape (a different database technology entirely, if that fits the query pattern better).

Wrong answer: Treating "we can rebuild any read model from history" as a reason to skip careful read-model design up front, since "we can always fix it later by replaying." Rebuilding is genuinely valuable, but it doesn't make read-model shape decisions free — a poorly-shaped read model still causes real query performance and correctness problems in the meantime, and large rebuilds still cost real time and resources when they're needed.

When is event sourcing worth its cost, and when would you actively steer a team away from it? senior

It earns its cost when the business genuinely needs a full, trustworthy audit trail of everything that happened (regulated domains, financial ledgers), when "what was the state at any point in the past, and why did it get there" is a real, recurring question the business asks, or when the domain naturally thinks in terms of a sequence of occurrences rather than current state (e.g. a ledger, a workflow with many valid paths). Steer away from it for domains where current state is really all that matters, where the team has no existing operational experience with event-sourced systems (the learning curve and operational tooling gap are real), or where the event-versioning burden described above would land on a team not prepared to carry it indefinitely — event sourcing is one of the highest-commitment architectural choices in this entire bank, harder to walk back from than almost anything else covered.

Example

A financial ledger or an insurance-claims workflow where "show me exactly what happened and in what order, and let us reconstruct state as of any past date" is a real, recurring business requirement: event sourcing earns its cost directly. A typical CRUD-shaped internal tool, or even a moderately complex e-commerce order flow where a normal audit log (Unit 04-style domain events fired alongside conventional persistence) already satisfies the actual business need: event sourcing would be a large, hard-to-reverse commitment for a benefit the business never asked for.

Follow-ups

  • Can you event-source just one aggregate/bounded context and not others? — Yes, and this is common — event sourcing is a per-aggregate or per-context persistence decision, not an all-or-nothing choice for the whole system.
  • What's a lower-commitment way to get some of the audit-trail benefit? — Keep conventional current-state persistence but also durably log every domain/integration event (Unit 04) to an append-only audit table — gets you a trustworthy history without committing to event sourcing as the actual persistence mechanism.
  • How do you know a team is "not ready" operationally? — No existing experience running/debugging an event store in production, no established event-versioning discipline, and no clear owner for the read-model rebuild tooling — these gaps should be closed (or explicitly staffed for) before adopting event sourcing, not discovered after.

Wrong answer: Recommending event sourcing broadly "because it gives you a complete audit trail for free, which is always valuable." The audit trail isn't free — it comes with permanent event-versioning discipline, materially harder debugging and tooling requirements, and a real team-capability bar — recommending it without weighing those costs against a business's actual need for full history is exactly the kind of unqualified pattern-application this whole unit warns against.

13 Ubiquitous language, event storming & team practice

DDD is as much a set of collaborative practices for discovering a model as it is a set of coding patterns — this is where "lead/principal" questions probe whether you can actually run the modeling process with a team and domain experts, not just implement the patterns once someone else has drawn the boundaries. Ubiquitous language and event storming are the two practices interviewers ask about most; expect this to come up as "how would you run the first two weeks on a new domain," not as trivia.

docs: The ubiquitous language · eventstorming.com

What is the ubiquitous language, and what specifically breaks when a team doesn't have one? screener

The ubiquitous language is the shared vocabulary — precise, agreed, and used consistently by domain experts and developers alike — for the concepts inside a specific bounded context, used identically in conversation, in code (class/method names), and in documentation, so there's never a translation step between how the business talks about something and how the code expresses it. Without it, developers build an internal vocabulary that drifts from what domain experts actually mean (a "cancelled" order in code might mean something subtly different from what an ops person means by "cancelled"), and every conversation between business and engineering pays a translation tax — worse, translation errors introduce real bugs when a developer's private mental model of a term doesn't match the business rule that term is supposed to represent.

Example

If domain experts distinguish "Cancelled" (the customer backed out before shipping) from "Returned" (the customer sent it back after delivery) as clearly different outcomes with different financial handling, and the code only has one `IsCancelled` boolean covering both, that's not a naming nitpick — it's a sign the code's model doesn't actually match the business's model, and financial reporting built on top of it will eventually be wrong.

Follow-ups

  • Is the ubiquitous language the same across the whole system? — No — it's scoped per bounded context, deliberately; the same word ("Customer," "Account") can and often does mean something different in different contexts, which is fine as long as each context is internally consistent.
  • Who owns keeping it up to date? — Shared between domain experts and developers continuously, not written once in a glossary document and left to go stale — the real test is whether the code's naming keeps pace as the team's shared understanding evolves.
  • Does this apply to database column names too? — Yes, ideally — a column named `flag1` or a status code `3` that requires a lookup table to explain is exactly the translation-tax problem the ubiquitous language exists to eliminate, at the persistence layer too.

Wrong answer: "It's just about using good, clear variable names." Good naming is a symptom of having a ubiquitous language, not the practice itself — the actual practice is the ongoing, collaborative process of aligning the team's and the domain experts' understanding of what each term means, which naming then reflects.

What is event storming, and what does a session concretely produce that a whiteboard architecture discussion wouldn't? mid

Event storming is a workshop format (developed by Alberto Brandolini) where domain experts and developers collaboratively map out a business process by writing domain events (orange sticky notes, past tense — "Order Placed," "Payment Captured") in chronological sequence on a long wall/board, then layering on commands (what triggers each event), actors, and eventually bounded-context boundaries and aggregates once the event flow is visible. What it produces that a typical architecture discussion doesn't: a shared, chronologically-ordered picture of the actual business process built by the people who understand the business alongside the people who'll build it, surfacing gaps, disagreements, and hidden complexity (a step everyone assumed was simple turns out to have three different exception paths domain experts know about but developers didn't) before a single line of code or a single aggregate boundary gets committed to.

Example

A session for "how does an order get fulfilled" surfaces the full event sequence — `OrderPlaced → PaymentAuthorized → InventoryReserved → ... → ShipmentDelivered` — with domain experts flagging in real time "actually, sometimes inventory isn't available and we do a partial shipment, that's a whole separate flow nobody's mentioned yet," which is exactly the kind of gap a purely technical whiteboard session (without domain experts in the room) would never surface.

Follow-ups

  • Who should be in the room? — Domain experts (the people who actually do or deeply understand the business process) and developers together — a session with only developers defeats the purpose, since the whole value is surfacing what only domain experts know.
  • How does event storming lead to bounded contexts? — Once the full event timeline is visible, natural clusters/pivot points emerge — places where language or ownership shifts — which is where you draw bounded-context boundaries (Unit 01), grounded in the actual observed process rather than guessed up front.
  • How long does a session typically take? — Anywhere from a few hours (a "lightweight" storming for one process) to a full day or two for a "big picture" session covering an entire domain — scoped to the size of what's being explored.

Wrong answer: Running an event storming session with only the engineering team, "to move faster since we already understand the requirements." Without domain experts actually in the room, it's just developers writing sticky notes for what they already believed — the entire value of the exercise (surfacing what developers don't yet know) is lost.

As the lead on a new domain with no existing model, how would you run the first two weeks to arrive at initial bounded contexts and aggregates? senior

Start with discovery before any code: get time with actual domain experts, run one or more event storming sessions to map the real business processes (not the org chart, not the existing legacy system's table structure — the actual flow of what happens), and pay close attention to where vocabulary shifts or where different people give visibly different answers to the same question — those are the seams that usually become bounded-context boundaries. From that map, identify candidate aggregates by looking for genuine invariants that need atomic protection, provisionally size them, and treat the first cut as exactly that — provisional, expected to be revised once actual code and real edge cases start testing it — rather than a final design to defend. Resist the pressure to skip straight to class diagrams before the process-level picture and the language are actually shared.

Example

Week one: schedule 3-4 event storming sessions with different domain experts/stakeholders covering the core processes; note every place two people used the same word differently or looked confused by the same question. Week two: draft a first bounded-context map and a handful of candidate aggregates from those sessions, socialize it back with the domain experts for correction before writing a single class, and explicitly flag it as "version 0.1, expect this to move."

Follow-ups

  • What if domain experts aren't available for that much time up front? — Push for it anyway, even in smaller increments — this is one of the areas where the lead's job is protecting the process, since skipping it doesn't remove the discovery work, it just defers it to be done badly, later, through expensive rework.
  • How do you avoid analysis paralysis during this discovery phase? — Time-box it, and treat the output as a starting hypothesis rather than a spec to perfect — the real validation comes from building against it and seeing where it resists reality, not from more upfront discussion.
  • Should any code get written during these two weeks? — Often a small, throwaway spike against the provisional model is useful to stress-test it early, as long as everyone understands it's disposable and not the foundation being committed to.

Wrong answer: Starting by reverse-engineering the domain model from the existing legacy system's database schema, since "that's what actually exists today." A legacy schema usually encodes years of technical shortcuts and past misunderstandings of the domain, not the domain itself — modeling from it directly tends to import those same misunderstandings into the new system rather than actually improving on them.

A domain expert and a developer are using the same word to mean two different things, and it's been causing bugs. How do you resolve this at the team level, not just for the one bug? mid

Surface the disagreement explicitly and resolve it as a team, not privately between the two people involved — get everyone who uses the term in the same room, name both meanings concretely with examples, and either agree on one meaning and rename whichever concept in code was using the term incorrectly, or recognize that there are genuinely two distinct concepts hiding under one overloaded word and give each its own explicit name. Then propagate the resolution everywhere the term appears — code, documentation, any glossary the team maintains — rather than fixing just the one bug's immediate cause and letting the underlying ambiguity persist to cause the next one.

Example

Ops calls a shipment "Delivered" once the carrier's tracking says so; the code's `Delivered` flag was actually set on "carrier scan at local depot," a step earlier than what ops means. Resolution: rename the code's concept to `ArrivedAtLocalDepot`, introduce an actual `Delivered` concept matching ops' real meaning, and update every place in the codebase (and any customer-facing status text) using the old, ambiguous flag.

Follow-ups

  • Should this trigger a broader review of similar terms? — Often worth a quick pass — if one term was silently overloaded, it's a reasonable prompt to check a handful of other frequently-used terms for the same issue while everyone's attention is already on language precision.
  • How do you prevent this recurring as the team grows? — A living glossary tied to the ubiquitous language, reviewed periodically, plus a team norm that "wait, what do you mean by X" is a welcome question in any domain discussion, not a sign of not having done homework.
  • What if renaming the code concept is a large, disruptive change? — Rename incrementally behind the scenes (introduce the correctly-named concept alongside the old one, migrate callers, remove the old one) rather than either a risky big-bang rename or leaving the ambiguity in place indefinitely.

Wrong answer: Adding a code comment clarifying which meaning is intended at the one call site where the bug occurred. It fixes nothing for the next developer who touches a different call site with the same ambiguous name and no comment nearby — the ambiguity itself, not this one instance of it, is the actual problem.

How do you keep the ubiquitous language and the code from drifting apart as a team scales and domain experts rotate off the project? senior

Treat language alignment as an ongoing practice, not a one-time artifact from the initial modeling sessions — build it into regular rituals (new-feature kickoffs that start by naming the concepts involved before any design, periodic glossary reviews, code review comments that specifically flag naming drift from agreed terms) rather than relying on it having been "figured out" once at project start. When domain experts rotate, actively onboard their replacements into the existing language rather than letting a new expert's different phrasing quietly diverge from what's already encoded in the code — reconcile explicitly, the same way you'd reconcile the earlier "two meanings of one word" scenario.

Example

A team practice where any pull request introducing a new domain concept or renaming an existing one requires a one-line note on why, visible in review — cheap, and it keeps language decisions traceable and discussable rather than silently accumulating drift across dozens of individually-reasonable-seeming PRs.

Follow-ups

  • Is a formal glossary document worth maintaining? — Useful as a reference, but it's not a substitute for the code itself using the language correctly — a glossary that says one thing while the code says another is worse than no glossary, since it actively misleads.
  • How do you handle a new domain expert who insists on different terminology than what's already in the code? — Investigate whether it's a genuine terminology evolution (the business's own language changed) worth propagating into the code, or a personal-preference difference that doesn't need to trigger a rename — not every disagreement is a signal to change the code.
  • Does this practice cost meaningful time? — Some, but it's cheap relative to the alternative — the translation-tax and bug-risk cost of language drift (this question's opening problem) compounds silently and is far more expensive to unwind later than to prevent continuously.

Wrong answer: Relying on the original modeling documentation from the project's early event-storming sessions as the permanent source of truth for terminology. A domain's real language evolves as the business evolves — treating an early artifact as permanently authoritative guarantees it eventually diverges from how the team and the business actually talk, which is the exact drift this practice exists to prevent.

14 Testing the domain model

A well-modeled domain — aggregates enforcing their own invariants, no infrastructure dependencies at the core (Unit 07) — should be some of the easiest, fastest code in the entire system to test. This unit checks whether you actually exploit that, or whether testing habits from a more infrastructure-coupled codebase (mocking everything, testing through the database) leak in and undermine what the modeling effort bought you.

docs: .NET testing overview · martinfowler.com: TestPyramid

What should a unit test of an aggregate look like, and why shouldn't it need any mocks? screener

Construct the aggregate (directly, or via its factory), call a behavior method, and assert on its resulting state and/or the domain events it raised — no repository, no database, no DI container involved at all, because a well-isolated aggregate (Unit 07's dependency rule applied at the unit level) has no dependencies on anything external to mock in the first place. If a test of "does placing an order work" needs to mock three infrastructure interfaces, that's a strong signal the aggregate has taken on dependencies it shouldn't have — the fix is usually pushing that I/O out to the application layer (Unit 09's "resolve externally, pass in the fact" pattern), not adding more mocking infrastructure to the test.

Example 
[Fact]
public void Place_WithNoLines_ThrowsDomainException()
{
    var order = Order.StartFor(new CustomerId(Guid.NewGuid()));
    Assert.Throws<DomainException>(() => order.Place()); // no mocks, no database, milliseconds to run
}

[Fact]
public void Place_WithLines_RaisesOrderPlaced()
{
    var order = Order.StartFor(new CustomerId(Guid.NewGuid()));
    order.AddLine(new OrderLine(new ProductId(Guid.NewGuid()), 1));
    order.Place();
    Assert.Contains(order.DequeueEvents(), e => e is OrderPlaced);
}

Follow-ups

  • Should you test private methods directly? — No — test through the aggregate's public behavior methods, the same surface any real caller uses; private implementation details should be free to change without breaking tests.
  • How many of these tests should exist relative to integration tests? — Many more — this is the base of the testing pyramid; fast, dependency-free aggregate tests should vastly outnumber slower integration tests, precisely because they're cheap to write and run.
  • What if the aggregate genuinely needs a `Guid.NewGuid()` or `DateTime.Now`? — Inject an abstraction (`IIdGenerator`, `IClock`) as a factory-time input rather than a live dependency the aggregate holds, or pass the value in as a parameter — keeps tests deterministic without needing to mock anything at call time.

Wrong answer: Testing every aggregate behavior exclusively through integration tests that go through a real (or in-memory-provider) database and the full application-service/repository stack. It works, but it's slow, makes failures harder to localize (is this a domain bug or a mapping bug?), and throws away the fast-feedback benefit that a well-isolated domain model is specifically designed to provide.

How do you test a domain event's effects without turning the test into an integration test of the whole dispatch pipeline? mid

Split the concern in two, testing each in isolation: (1) does the aggregate raise the correct event, with the correct data, for a given action — a pure aggregate unit test, no dispatcher involved at all; (2) does the handler for that event produce the correct effect, given the event — a unit test of the handler alone, constructed directly with a fake/in-memory dependency (Unit 05's fake-repository pattern) rather than going through the real mediator/dispatch pipeline. The dispatch mechanism itself (does MediatR/your custom dispatcher actually route `OrderPlaced` to the right handler) is a separate, much smaller concern, usually covered by a handful of thin integration tests rather than duplicated across every event/handler pair.

Example 
// (1) Aggregate raises the right event — no handler involved:
Assert.Contains(order.DequeueEvents(), e => e is OrderPlaced { Total: var t } && t == expectedTotal);

// (2) Handler reacts correctly to the event — no real dispatch pipeline involved:
var handler = new ReserveInventoryHandler(new FakeInventoryRepository());
await handler.Handle(new OrderPlaced(orderId, customerId, total), CancellationToken.None);
Assert.True(fakeInventory.WasReservedFor(orderId));

Follow-ups

  • Do you need any test that exercises the full pipeline end-to-end? — Yes, a small number — a few integration/end-to-end tests confirming the wiring actually connects correctly, but these should be few relative to the many fast unit tests covering the actual logic on both sides.
  • How do you test the Outbox pattern (Unit 04) specifically? — At the integration level — it's inherently about the interaction between the database transaction and a separate dispatch process, which isn't meaningfully testable as a pure unit.
  • Should event-handler tests assert on side effects or on interactions (mock verification)? — Prefer asserting observable outcomes (state changed, a record exists) over asserting "method X was called" — the latter tends to couple tests to implementation details rather than actual behavior.

Wrong answer: Writing one large test that raises a command through the full mediator pipeline, waits for the aggregate to save, waits for the event to dispatch, and waits for the handler's side effect to land — all in one test, for every scenario. Each such test is slow and, when it fails, doesn't tell you which of the three stages actually broke — splitting into the two focused unit tests above gives faster feedback and clearer failure localization.

How do you test invariants that span multiple aggregates enforced eventually (Unit 02's cross-aggregate consistency), given there's no single object to assert against synchronously? senior

Test each side of the eventual-consistency boundary independently, plus the reconciling mechanism as its own explicit test subject: does the first aggregate correctly raise the event that signals the cross-cutting condition; does the handler/second aggregate correctly react to that event and reach the expected end state; and — importantly — does the system correctly handle the case where the second side's reaction fails or is delayed (the compensating/retry path). There's rarely a single test that spans both aggregates in one assertion, because that's not how the system actually behaves at runtime either — the tests should mirror the actual eventually-consistent design, not pretend it's synchronous for convenience.

Example

For "total reserved inventory across all orders must never exceed stock on hand," don't try to write one test asserting both `Order` and `InventoryItem` state together as if atomic. Instead: test that `Order.Place()` raises `OrderPlaced` correctly; test that the inventory-reservation handler correctly reserves stock given that event, including the case where insufficient stock triggers the correct compensating `ReservationFailed`/order-cancellation path; test each independently, and add one narrow integration test confirming the wiring between them actually works.

Follow-ups

  • Should you test the "window of inconsistency" itself? — Where it matters to the business (e.g. "can a user briefly see an order as placed before inventory is confirmed reserved, and is that acceptable"), yes — as an explicit scenario, not an oversight.
  • Does this need a real message broker in tests? — Rarely for the logic itself — an in-memory fake dispatcher is usually enough; a real broker matters more for infrastructure-level integration tests of serialization/delivery guarantees specifically.
  • How do you catch a regression where the compensating action silently stops firing? — An explicit test asserting the compensating path specifically — it's exactly the kind of thing that's easy to have coverage of the happy path but not the failure/compensation path, and that gap is where real incidents happen.

Wrong answer: Not testing the compensation/failure path at all, since "the happy path already covers the normal event flow." The entire reason eventual consistency needs careful design is the failure/delay case — a test suite that only exercises the happy path gives no actual confidence about the property (bounded inconsistency, eventual correctness) the design is supposed to guarantee.

A test suite has hundreds of tests but they're all written against the repository/persistence layer rather than the domain model directly — what's the risk, and how would you rebalance it? senior

The risk is an inverted testing pyramid: slow test runs, brittle tests that break on unrelated persistence changes (an EF Core mapping tweak breaking dozens of "domain logic" tests that never should have depended on it), and — most importantly — weaker actual coverage of domain logic edge cases, since writing a persistence-layer test for every invariant branch is enough friction that people tend to test only the happy paths. Rebalancing means adding the missing layer of fast, dependency-free aggregate unit tests (this unit's opening pattern) for the actual business-rule branches, and demoting the existing persistence-heavy tests to cover what they're actually suited for — confirming mapping and querying behavior — rather than re-verifying business rules that are now covered faster and more thoroughly elsewhere. Don't necessarily delete the existing tests outright; some earn their keep as genuine integration coverage once their purpose is reconsidered.

Example

Before: `OrderRepositoryTests` with forty test methods, each spinning up a test database, creating an order through the repository, saving, reloading, and asserting business rules like "cannot place an empty order." After: those forty become perhaps ten integration tests confirming mapping/persistence round-trips correctly, plus forty fast aggregate unit tests (no database) actually covering the business-rule branches — same or better coverage, a fraction of the runtime.

Follow-ups

  • How do you introduce this change without a disruptive rewrite? — Incrementally, the same pattern as everywhere else in this bank — add fast aggregate tests for new features going forward, and backfill/rebalance existing persistence-heavy tests opportunistically as they're touched, rather than a dedicated rewrite sprint.
  • Isn't this just "more tests to write and maintain" overall? — Initially yes, but the fast unit tests are cheaper per-test to write and run going forward, and the net long-term cost (test suite runtime, flakiness, time-to-feedback) usually drops significantly.
  • What's the root cause that produces this pattern in the first place? — Usually an anemic-model-adjacent habit (Unit 11) — if business rules were never confidently isolated in the aggregate to begin with, testing through the full persistence stack can feel like the only way to be sure the whole thing actually works together.

Wrong answer: Leaving the test suite as-is because "it has good coverage numbers and it's all passing." Coverage percentage says nothing about test speed, brittleness, or how well edge-case branches are actually exercised — a green, slow, persistence-heavy suite can coexist with genuinely under-tested domain logic if most of those tests only exercise the happy path due to the friction of setting up a database-backed test per scenario.

15 Judgment calls

Open-ended, no single right answer — these are the questions a principal-level interview actually hinges on. Each hidden panel names what a strong answer demonstrates and the trade-offs it names without being prompted; use them to rehearse structuring an answer, not to memorize a "correct" one.

A new core-subdomain project is starting from scratch. How much upfront modeling do you do before writing the first line of production code, and how do you decide when discovery is "enough"?

What a strong answer demonstrates

  • Ties the amount of upfront modeling to the subdomain's classification (Unit 01) — heavy investment for a genuine core subdomain, deliberately light for supporting/generic ones — rather than applying a fixed process length everywhere.
  • Describes concrete discovery mechanics (event storming with actual domain experts, not just developers) and names what signal tells them discovery is converging (vocabulary stabilizing, fewer new edge cases surfacing per session) rather than a fixed calendar duration.
  • Treats the first model as provisional and names how they plan to validate it against real code and edge cases quickly, rather than polishing it indefinitely before writing anything.

Trade-offs named unprompted

  • Analysis paralysis / opportunity cost of delaying working software vs. the cost of building on a wrong model and having to rework it later.
  • Domain-expert time is scarce and expensive — over-scheduling discovery sessions has a real organizational cost, not just a schedule cost.
  • A model that looks "finished" after discovery is not validated — only contact with real code and real edge cases validates it, so some rework should be budgeted for regardless of how much upfront time was spent.
You've inherited a monolith with no bounded contexts at all — one shared database, one giant set of services touching everything. How do you introduce boundaries without a rewrite?

What a strong answer demonstrates

  • Reaches for event storming or a similar discovery pass to find natural seams in the existing behavior, rather than guessing boundaries from the code's current (possibly accidental) structure.
  • Describes an incremental strangler-fig-style approach — carve out one bounded context at a time behind an explicit interface, starting with the highest-pain or clearest-boundary area first, while the rest of the system stays as-is.
  • Names how they'd keep the system shippable throughout — no long-lived "big rewrite" branch, continuous small, reviewable, revertible steps.

Trade-offs named unprompted

  • Speed of extraction vs. risk of extracting the wrong boundary and having to redo it — early boundaries should be treated as provisional, same as greenfield discovery.
  • The shared-database problem is usually the hardest part to unwind — separating data ownership lags behind separating code, and that gap is a real, ongoing risk window that needs explicit management (dual-writes, sync jobs) rather than being ignored.
  • Organizational cost — carving out a context often implies carving out team ownership too, which is a people change, not just a code change, and needs to be sequenced deliberately.
How do you decide, for a specific aggregate, whether a business rule change should be enforced with a "big bang" migration (rewrite all existing data to comply) or allowed to apply only going forward, with old data grandfathered?

What a strong answer demonstrates

  • Asks what the actual business risk of non-compliant historical data is — some invariants matter retroactively (financial correctness), others genuinely don't (a new validation rule for future orders only).
  • Weighs migration risk (touching large amounts of production data) against the ongoing cost of code having to handle two valid shapes indefinitely if grandfathering is chosen.
  • Proposes a concrete mechanism either way — a bounded, tested migration script with rollback capability, or an explicit versioning/tagging scheme distinguishing old-shape from new-shape records — rather than leaving the decision unimplemented.

Trade-offs named unprompted

  • Migration risk (data loss, downtime, an incorrect transform at scale) vs. permanent code complexity from supporting two shapes indefinitely.
  • Grandfathering can silently accumulate — "just this once" old-shape exceptions tend to multiply across multiple rule changes over a system's life if not tracked deliberately.
  • Whoever inherits the codebase later needs to understand why two shapes coexist — undocumented grandfathering is a specific, recurring source of "why does this code have two paths" confusion.
Your team is about to adopt event sourcing for a new core subdomain because "it's what a well-architected system should have." How do you respond?

What a strong answer demonstrates

  • Separates the decision from the stated justification — "well-architected" isn't a reason; asks what specific business need (audit trail, point-in-time reconstruction, an inherently event-shaped domain) is actually driving it.
  • Names the concrete, ongoing costs (event versioning discipline, operational unfamiliarity, harder debugging) from Unit 12 and asks whether the team is realistically staffed and experienced enough to carry them indefinitely.
  • Offers a genuine lower-commitment alternative (conventional persistence plus a durable audit log of domain events) that might satisfy the actual need without the full commitment, and proposes validating the real need before committing.

Trade-offs named unprompted

  • Event sourcing is one of the hardest architectural decisions to reverse in this entire topic — the cost of getting it wrong compounds specifically because historical events can't be cleanly rewritten.
  • Team capability and operational maturity matter as much as the domain's theoretical fit — a domain that "would benefit" from event sourcing but a team unprepared to run it is still a bad bet.
  • Saying no to a popular pattern has a social cost within the team that needs managing alongside the technical argument.
Two teams own adjacent bounded contexts and disagree about where a specific piece of behavior belongs. How do you help resolve it as the lead, without just picking a side by authority?

What a strong answer demonstrates

  • Goes back to first principles — which context's ubiquitous language and invariants actually govern this behavior, rather than which team wants it or which codebase is more convenient to change.
  • Facilitates a joint session (event-storming-style) with both teams to make the disagreement concrete and visible, rather than mediating an abstract argument secondhand.
  • Recognizes that some disagreements are genuinely about context-mapping choice (Customer-Supplier vs. Separate Ways, Unit 01) rather than a factual question with one right answer, and names the relationship pattern being effectively chosen either way.

Trade-offs named unprompted

  • A "fair" process takes longer than an authority-based decision — worth it for a decision with lasting architectural consequences, overkill for a small one.
  • Whichever team doesn't own the behavior going forward loses some autonomy over a concept they may have cared about — that ownership cost is real and worth naming explicitly, not glossed over.
  • Revisiting the decision later if it proves wrong should be explicitly cheaper than the original decision process, or the team will avoid revisiting a decision that no longer fits.
How do you decide the right granularity for aggregates in a domain you're still learning — err toward larger, more inclusive aggregates, or smaller, more numerous ones?

What a strong answer demonstrates

  • Names the asymmetry in the two mistakes: an oversized aggregate causes contention/performance problems that are usually visible and fixable later by splitting; an undersized aggregate can allow an actual invariant violation to happen unnoticed, which is a correctness bug, not just a performance one.
  • Given that asymmetry, argues for erring slightly toward drawing the boundary around what's needed to protect a genuine invariant, even if that means a somewhat larger aggregate than feels comfortable, rather than optimizing for smallest-possible size upfront.
  • Names how they'd validate the choice quickly — real usage patterns and contention data, not more upfront analysis — and treats early aggregate boundaries as provisional.

Trade-offs named unprompted

  • Splitting an oversized aggregate later is a well-understood, incremental refactor (Unit 02); catching a silently-violated invariant after the fact often means a data-integrity cleanup, which is a much worse problem to have shipped.
  • Larger aggregates cost real throughput/contention even when no invariant is at risk — the "err larger" bias isn't free, it's a deliberate bet that correctness risk outweighs performance risk while the model is still being learned.
  • How much this matters at all depends heavily on actual concurrent-write volume for that aggregate — the judgment call changes for a low-contention aggregate versus a hot one.
A senior engineer on your team wants to introduce full CQRS with separate physical read/write databases for a moderately complex, but not yet high-scale, subdomain. How do you evaluate the proposal?

What a strong answer demonstrates

  • Separates the architectural pattern (logical CQRS — separate models/code paths) from the physical decision (separate databases), and probes whether the actual justification supports the physical split specifically, not just "CQRS is a good idea here."
  • Asks for concrete evidence of the mismatch or scaling need the physical split is meant to solve, and what the operational cost (two data stores, replication lag, more failure modes) buys in return at current scale.
  • Proposes a middle path — adopt logical CQRS now, defer physical separation until a concrete scaling trigger is hit — as a way to capture most of the benefit without the premature cost.

Trade-offs named unprompted

  • Premature physical separation adds operational complexity (replication lag, more infrastructure to monitor, more failure modes) that has to be paid for immediately, while the benefit it targets may be years away.
  • Deferring the physical split isn't free either — logical CQRS done well should make the later physical split easy, but only if the boundary is drawn cleanly from the start, which itself takes some care.
  • Saying no to an engineer's proposal has a morale/trust cost that needs managing alongside the technical merits — framing it as "not yet, here's the trigger that changes the answer" preserves both.
You're brought in to review a system where every service anemically wraps a shared database, with all logic in a scattering of "manager" classes. Leadership wants an estimate for "fixing it to be proper DDD." How do you respond?

What a strong answer demonstrates

  • Pushes back on "fixing it to be proper DDD" as the framing — the actual goal should be named business/engineering outcomes (fewer production incidents from inconsistent validation, faster feature delivery in specific hot areas) that DDD patterns are a means to, not an end in themselves.
  • Proposes identifying the highest-pain areas first (via incident history, change frequency) and scoping an incremental, aggregate-by-aggregate extraction there, rather than committing to a full-system estimate upfront that's unlikely to be accurate.
  • Is honest that a full estimate for the whole system is not credibly knowable yet, and explains why, rather than producing a confident number to satisfy the request.

Trade-offs named unprompted

  • Leadership wants a number; giving an honest "we can't know that yet, here's what we can commit to for the first slice" carries real communication risk that needs managing deliberately.
  • Incremental extraction delivers value continuously but delays the point at which the whole system can be called "done," which may or may not match what leadership actually needs to hear.
  • Not every part of the anemic system needs fixing — some of it may be legitimately fine as simple CRUD (Unit 05's judgment call) and effort spent there is effort not spent where it matters.
How do you balance "modern-first" technology adoption (e.g. EF Core 10 Complex Types, the latest .NET LTS) against the real cost of migrating a large, stable codebase that isn't broken?

What a strong answer demonstrates

  • Distinguishes "worth adopting for new code going forward" from "worth migrating existing, working code" — these are different questions with different cost/benefit calculus, and a strong answer doesn't conflate them.
  • Names concrete triggers that would justify migrating existing code (a real bug the old approach causes, an LTS support deadline approaching, a new feature that's much harder to build on the old pattern) rather than migrating purely for modernity's sake.
  • Proposes new code adopting the modern approach immediately while existing code migrates opportunistically (when it's already being touched for another reason) rather than as a dedicated migration project, unless a concrete trigger justifies dedicating time to it.

Trade-offs named unprompted

  • Staying on an old pattern accrues technical debt and eventual unsupported-version risk (the .NET/EF Core LTS timeline is a real, dated constraint) — "not broken" doesn't mean "no growing risk."
  • Migrating for its own sake spends engineering time that produces no immediate user-facing value and carries real regression risk in code that was working.
  • Running two patterns side by side (old code on the old approach, new code on the new one) has its own ongoing cost — inconsistency across the codebase, onboarding confusion — that should be weighed against the alternative of a dedicated migration.
A principal engineer on another team argues DDD's ceremony (aggregates, repositories, bounded contexts) is never worth it for their team's product, which has always shipped fast without it. How do you engage with that view?

What a strong answer demonstrates

  • Takes the claim seriously rather than dismissing it — genuinely simple, low-invariant products can be entirely well-served without DDD's heavier patterns, and this bank's own recurring theme (Units 05, 07, 09, 11) is exactly "match effort to actual complexity."
  • Probes for specific evidence either way — has their product actually stayed simple, or has complexity crept in (scattered validation, duplicated business rules across handlers) without being named as such — rather than accepting or rejecting the claim on faith.
  • Frames the real disagreement precisely: not "DDD vs. no DDD" as a binary, but where on the complexity spectrum their actual domain sits today, and that this can be reassessed later without it being an admission that the original choice was wrong.

Trade-offs named unprompted

  • Pushing unwanted process onto a team that's shipping successfully has a real morale and trust cost — this needs to be a genuine inquiry, not a thinly veiled argument for adopting DDD everywhere.
  • If their domain has quietly grown more complex than their current approach handles well, the cost of that mismatch is often invisible until an incident makes it visible — but that risk has to be demonstrated with evidence from their system, not asserted from principle.
  • Being wrong in either direction has a cost — recommending unneeded ceremony wastes their team's time; failing to flag a real, growing mismatch risks a future incident that traces back to this conversation.

16 Design exercises

Full exercises where DDD meets system design — the format a principal-level onsite actually uses. Read the prompt, think about what you'd ask before designing anything, then open the collapsed panel for a strong solution outline and the trade-offs it names unprompted.

Exercise 1 — Design the domain model for a ride-hailing dispatch system: riders request rides, drivers accept or are assigned, a ride goes through a lifecycle from requested to completed or cancelled, and pricing may change (surge) between request and acceptance.

Clarifying questions to ask

  • Is pricing locked at request time, or can it legitimately change before the rider confirms — does the domain need to model a price quote as distinct from the final charged price?
  • Can a ride be reassigned to a different driver after acceptance (driver cancels, goes offline), and if so, how many times, and does that count against the driver?
  • Is driver-availability/matching itself in scope, or is "a driver has been assigned" an input this model receives from elsewhere (a separate matching/dispatch bounded context)?
  • What are the actual consistency requirements — must "driver accepted" and "rider notified" happen atomically, or is a brief window of one-sided knowledge acceptable?

Strong solution outline

  • Treat Ride Lifecycle as its own bounded context, separate from Driver Matching/Dispatch and Pricing — matching is a different concern with different scaling/algorithmic needs (Unit 01's context-mapping judgment), and pricing/surge calculation is a genuinely separate subdomain that the ride context consumes as a fact, not computes itself.
  • Ride is the aggregate root: RideId, RiderId, DriverId?, Status (Requested → Accepted → InProgress → Completed / Cancelled), QuotedPrice (a Money value object captured at request time), FinalPrice?. Behavior methods: Accept(DriverId), Start(), Complete(Money finalPrice), Cancel(CancelledBy, Reason) — each enforcing valid state transitions only (can't Complete a ride that was never Started).
  • Pricing is resolved via an anti-corruption layer (Unit 09) — the Ride context asks a IPricingQuote port for a quote at request time and stores the result as a value object on the aggregate; it never reaches into the Pricing subdomain's own logic directly.
  • Driver assignment arrives as a fact from the Matching context, e.g. a DriverAssigned integration event the Ride aggregate reacts to by calling its own Accept/reassignment logic — the Ride context doesn't run the matching algorithm itself.
  • Domain events: RideRequested, RideAccepted, RideCompleted, RideCancelled — used to trigger rider/driver notifications, billing, and analytics without coupling the aggregate to any of those concerns directly.

Trade-offs expected unprompted

  • Separating Matching from Ride Lifecycle adds an integration boundary (an event/API call) where a single-context design would have direct in-process access — worth it because matching's scaling and algorithmic profile is genuinely different, but it's a real cost, not a free win.
  • Storing QuotedPrice and FinalPrice separately (rather than one mutable price field) protects the invariant that surge changes don't silently rewrite what the rider was shown — at the cost of a slightly larger aggregate and more fields to reconcile in reporting.
  • Reassignment-after-acceptance is exactly the kind of edge case that's easy to underspecify — naming a concrete limit (e.g. max N reassignments, or an explicit "driver cancelled after acceptance" event distinct from rider cancellation) unprompted signals real production experience with this domain shape.
Exercise 2 — A single, large e-commerce monolith's "Order" concept has grown to touch inventory reservation, payment, shipping, promotions, and customer loyalty points, all in one 3000-line Order class. Propose how you'd decompose it into bounded contexts and aggregates.

Clarifying questions to ask

  • Is there evidence (incident history, review friction, team-ownership conflicts) pointing to specific pain areas, or is this purely "it's grown too large" with no concrete failure yet?
  • Are inventory, payment, shipping, promotions, and loyalty already owned by different teams organizationally, or is it genuinely one team today?
  • What's the actual consistency requirement between Order and each of these — must inventory be reserved atomically with order placement, or is eventual consistency (Unit 02/10) acceptable for some of them?
  • Is this decomposition expected to land as one large migration, or incrementally alongside ongoing feature work?

Strong solution outline

  • Run (or simulate, in the interview, by reasoning through) an event-storming pass first: Order itself is almost certainly the core subdomain; Inventory, Payment, Shipping are each their own bounded contexts with their own ubiquitous language ("reservation" means something specific to Inventory that Order shouldn't need to understand); Promotions and Loyalty are good candidates for supporting or even generic subdomains depending on how bespoke the rules are.
  • Keep a lean Order aggregate: identity, lines, status, totals, and the invariants that are genuinely about the order itself (can't place an empty order, can't ship a cancelled order) — nothing about how inventory is reserved, how payment is captured, or how loyalty points are calculated.
  • Each of Inventory, Payment, Shipping becomes its own aggregate in its own bounded context, reacting to integration events from Order (OrderPlaced) and raising their own events back (InventoryReserved, PaymentCaptured, ReservationFailed) that Order's own handlers react to by advancing its own status — the sagas-and-cross-context pattern from Unit 10.
  • Promotions/Loyalty are modeled as domain services or their own small contexts that Order consults (or that react to OrderCompleted to award points) — kept out of the Order aggregate itself since a discount/points calculation changing shouldn't require touching Order's own invariant-protecting code.
  • Sequence the actual extraction incrementally (Unit 11's God-object playbook): identify which cluster of the 3000 lines is causing the most current pain, extract it first behind an explicit interface while Order keeps calling through that interface, verify, then repeat — never a single big-bang rewrite.

Trade-offs expected unprompted

  • Splitting into contexts trades a single, easy-to-read (if bloated) class for several smaller ones connected by asynchronous events — genuinely better long-term but harder to trace end-to-end in the short term, especially for engineers new to the system.
  • Whichever context reacts to OrderPlaced and can fail (inventory unavailable, payment declined) needs an explicit compensating path back to Order — this is real, ongoing design work, not a one-time detail, and skipping it is exactly Unit 14's "untested compensation path" risk.
  • Team-ownership boundaries should track context boundaries where possible — if Inventory stays owned by the same team as Order after the split, most of the coordination benefit of separating them is lost even though the code now looks decomposed.
Exercise 3 — Design a domain model for a hotel-booking system that must prevent double-booking a room for overlapping date ranges, support cancellations with a refund policy that depends on how close to check-in the cancellation happens, and handle a multi-night stay as a single booking.

Clarifying questions to ask

  • Is availability/inventory checked and reserved per-room or per-room-type (e.g. "a Deluxe King," not a specific numbered room) — this changes what the aggregate actually needs to protect.
  • Is there ever a legitimate reason to overbook intentionally (airline-style overbooking against no-show rates), or is "never double-book" an absolute invariant?
  • Does the refund-policy calculation belong inside the Booking aggregate, or is it a separate policy the aggregate consults — is the policy itself likely to vary by hotel/rate plan?
  • What's the concurrency profile — is this a single popular property where many users might try to book the same room concurrently, materially affecting the aggregate-boundary decision?

Strong solution outline

  • Booking as the aggregate root for the guest-facing lifecycle: BookingId, RoomTypeId, DateRange (a value object with its own overlap-checking behavior), Status (Confirmed/Cancelled/CheckedIn/CompletedStay), RatePlanId. Behavior: Cancel(DateTime now) computing the refund via the consulted policy, CheckIn(), CheckOut().
  • Double-booking prevention is not an invariant the Booking aggregate alone can enforce — it's an invariant across the set of all bookings for a given room/room-type, which is exactly the "aggregate boundary needs to include everything that must be atomically consistent" test from Unit 02. Model a separate RoomInventory (or RoomTypeAvailability) aggregate keyed by room and date, whose job is specifically to accept or reject a reservation request for a date range — this is the thing that actually enforces "no overlap," with Booking created only after inventory grants the hold.
  • Refund policy is a domain service/strategy (Unit 09) taking the booking's date range, cancellation time, and rate plan, and returning a refund amount — kept separate from Booking itself since refund rules vary by hotel/rate plan and change independently of the booking lifecycle's core invariants.
  • Flow: RoomInventory.TryReserve(dateRange) → on success, create Booking (Confirmed) and raise BookingConfirmed; on failure, the request fails fast with no booking created — avoiding the classic bug of creating a Confirmed booking before availability is actually locked.

Trade-offs expected unprompted

  • Splitting Booking from RoomInventory means two aggregates must agree — a two-phase-feeling flow (reserve, then confirm) that's more moving parts than one aggregate doing everything, but it's the only way to actually protect the overlap invariant correctly under concurrent requests for the same room/dates.
  • Per-room-type inventory tracking (many nights × many rooms) can become a hot aggregate under high concurrent demand for a popular date range — worth naming as a scaling concern with a concrete mitigation (e.g. sharding by date range, or a dedicated high-throughput availability service) rather than left unaddressed.
  • Keeping refund policy external means an inconsistent policy change doesn't require touching Booking's code at all — good for changeability, but means Booking's own tests can't fully verify refund correctness in isolation and need the policy tested as its own unit alongside it (Unit 14's testing-boundary discipline).

17 Night-before cheat sheet

The 10 most-asked questions across the whole bank, one sentence each. Read this last.

#QuestionOne-sentence answer
1What is a bounded context?An explicit boundary around a model and its ubiquitous language, inside which every term means exactly one thing, and outside of which the same term may legitimately mean something else.
2What is an aggregate, and what does the aggregate root do?A cluster of objects treated as one consistency unit for a transaction, with the root as the only entry point that enforces the invariants spanning the whole cluster.
3Entity vs. value object — what's the actual difference?An entity is defined by a stable identity that persists through change; a value object is defined entirely by its attributes, is immutable, and is compared by value, not identity.
4What is a domain event, and why raise it instead of calling the dependent logic directly?A domain event is an immutable record of something significant that already happened, raised so that reactions to it can be added, removed, or changed without touching the aggregate that caused it.
5Why does the repository interface live in the domain layer, not the infrastructure layer?Because the domain defines what persistence operations it needs in its own vocabulary, and infrastructure implements that contract — the dependency points inward, per the dependency rule.
6What is CQRS, and is it required by DDD?CQRS separates the model used to write state from the model used to read it, optimizing each independently; it's a genuinely optional pattern that pairs well with DDD but isn't part of its core definition.
7What is the dependency rule in layered/onion/clean architecture?Dependencies point inward only — the domain model has zero dependencies on infrastructure, application, or UI, so those outer layers can change without ever forcing a change to the domain.
8EF Core: Owned Entity Types vs. Complex Types for value objects — which do you use now?Complex Types (EF Core 8+, matured in EF Core 10) are now the recommended default for value objects — true value/copy semantics and no hidden identity — with Owned Entity Types reserved for cases needing their own table or collection navigation.
9What's wrong with an anemic domain model?Classes named after domain concepts hold only data with no behavior, so invariants aren't enforced at the point of change and the same validation logic gets duplicated or inconsistently reimplemented across every service that touches the data.
10What is event sourcing, and is it required by DDD?Event sourcing persists the full sequence of events as the only source of truth and derives current state by replaying them; it's a powerful but optional, high-commitment persistence strategy, not a required part of DDD.
