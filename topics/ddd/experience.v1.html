01The Order aggregate that loaded its whole history to flip one flag

Senior performance problem diagnosed

(a) Worked example EXAMPLE — replace with your own

Cancelling an order should be one of the cheapest writes in the system: set a status, stamp a timestamp, raise a domain event. Ours took 1.8 seconds at the 99th percentile, and the support tool that triggered it timed out often enough to be a running joke. The Order aggregate had grown, over two years of "just add it to the repository call", into a graph that included every StatusHistory row ever written, every ShipmentEvent, and the full OrderLine collection — all pulled back by one OrderRepository.GetByIdAsync with four Includes, because that was the one method every command handler already called and nobody wanted to write a second one.

The invariant that looked like it needed all that data was inside Order.Cancel(): it refused to cancel an order that had already shipped, and "already shipped" was computed by scanning ShipmentEvents for a terminal state. For a young order that's two or three rows. For a three-year-old order that had been split, re-shipped and partially returned, it was thousands — and none of that history mattered to the invariant, which only ever needed the current shipment status, not how it got there.

// The aggregate as it had grown: a viewing convenience masquerading as a consistency boundary.
public class Order
{
    public IReadOnlyCollection<OrderLine> Lines => _lines;
    public IReadOnlyCollection<StatusHistoryEntry> StatusHistory => _statusHistory; // years of audit trail
    public IReadOnlyCollection<ShipmentEvent> ShipmentEvents => _shipmentEvents;   // every carrier webhook, ever

    public void Cancel(string reason)
    {
        if (_shipmentEvents.Any(e => e.Status == ShipmentStatus.Delivered))
            throw new DomainException("Cannot cancel a delivered order.");
        Status = OrderStatus.Cancelled;
        _statusHistory.Add(new StatusHistoryEntry(OrderStatus.Cancelled, reason, DateTimeOffset.UtcNow));
        Raise(new OrderCancelled(Id, reason));
    }
}

The fix split what had quietly become one aggregate into a small write-side Order (root + OrderLines + a single LatestShipmentStatus value object) and a separate OrderTimeline read model, populated by a subscriber to ShipmentStatusChanged and OrderStatusChanged domain events. Cancel() now checks one enum on the aggregate itself, never touches history, and the audit trail lives where an audit trail belongs: in a projection nobody has to load to change anything.

What I'd do differently: I'd have asked, the day ShipmentEvents was first added to the aggregate, "does Cancel need the history, or just the current fact?" That one question is the whole rule for aggregate design — model the transactional invariant, not the viewing convenience — and I let two years of habit answer it for me instead.

What the interviewer is really probing. Whether you treat "aggregate" as a consistency boundary with a specific invariant to protect, or as "everything related to an Order" — the tell for the latter is a candidate who can't say what would actually break if a piece of data were pulled out of the aggregate. The other failure mode is proposing caching or AsNoTracking as the fix: that hides the query cost without addressing why a status check depends on unbounded history, so the bug — and the temptation to keep growing the aggregate — comes back.

(b) STAR/CARL scaffold

Situation
A write that should be trivial (a status flip) is instead slow or timing out for a subset of records, and the aggregate behind it has grown for a long time without anyone questioning its shape.
Task
Make the write fast and keep the invariant correct, without breaking every other command that already depends on the same repository method.
Action
Find which invariant genuinely needs which data (read the guard clauses, not the schema); separate "what must be consistent in this transaction" from "what is nice to have loaded alongside it"; move the latter to a projection fed by domain events.
Result
A latency number, a row-count number, and — the one people forget — the size of the new eventual-consistency window and why it's safe.
Differently
The moment the aggregate should have been questioned, before it grew for two years by accretion.

(c) Recall prompts

When has "just add another Include" quietly become your aggregate boundary?

Sketch: look for a repository method every handler calls, with more eager-loaded navigations than any single command actually needs. That's usually where the boundary drifted.

Have you found an invariant that depends on history or audit data it didn't actually need?

Sketch: a guard clause that scans "every X ever" when it only cares about the latest X is the classic version of this bug — it's cheap to spot once you know to look for the word "any" or "all" next to an unbounded collection.

Where does one of your aggregates carry another aggregate's data for convenience?

Sketch: a denormalized copy is fine if it's a value object kept in sync by an event; it's a smell if it's a live navigation property crossing what should be a separate consistency boundary.

What's the largest object graph you've had to load to make what should have been a one-field change?

Sketch: put a number on it — rows, megabytes, milliseconds — because "it was really big" doesn't survive a follow-up and a measured number does.

(d) Follow-up drill chain

Why not just cache the repository call or add AsNoTracking instead of restructuring the aggregate?

Because that treats the symptom, not the coupling. The aggregate would still let the next feature reach into ShipmentEvents to answer some other question, and the invariant would still be entangled with unbounded history. Caching also risks serving a stale "not yet delivered" answer right through the one invariant that most needs to be correct at the moment of cancellation. The structural fix — moving history out of the write-side aggregate entirely — makes the coupling impossible to reintroduce by accident, which a cache never does.

What if two other aggregates needed the same "latest shipment status" fact?

That's precisely why it's a value object populated from a domain event rather than a join: any number of read sides — the timeline projection, a customer-facing tracker, a returns aggregate — can subscribe to the same ShipmentStatusChanged event and keep their own denormalized copy, with no coupling between the aggregates themselves and no risk that adding a fourth subscriber changes the transaction cost of cancelling an order.

At what scale does even the slimmed-down aggregate break?

Once OrderLines itself is unbounded — a B2B order with several thousand SKUs — the same rule applies again one level down: don't load every line to add one. I'd model "add a line" as a small, targeted operation (an ExecuteUpdate-style append, or a paginated aggregate load scoped to the lines actually being touched) rather than materialising the whole collection through the aggregate root every time.

What did you trade away?

Strong consistency between the cached shipment status and shipment reality — there's now a real, measured window (p99 ~340 ms) where Order could think a shipment is in transit moments after it was delivered. I accepted that because the business already tolerated a slower manual-reversal path for exactly that race, and because the endpoint that most needed speed — cancellation — is inherently a "did we act before the physical world changed" problem regardless of consistency model.

How did you validate the eventual-consistency window was actually acceptable?

I measured the real event-dispatch latency in production before shipping the change, compared it against the support team's existing manual process (which already assumed several minutes of lag), and put an alert on the subscriber's queue depth so a growing backlog — which would widen the window silently — pages someone before a customer notices.

Would you do it the same way on today's stack?

Yes, and I'd go one step further on EF Core 10: model the OrderTimeline projection's entries as a JSON-mapped complex type rather than a normalised table, since it's read-only, document-shaped, and never needs to be queried as individual rows in the write path — EF 10's JSON complex-type mapping and ExecuteUpdateAsync support make that a clean fit that didn't exist when I first built this.

02Where the Subscription ends and the Invoice begins

Staff hard architectural trade-off

(a) Worked example EXAMPLE — replace with your own

Billing and subscription management started as one module because one team wrote both, and for a year the shared Subscription aggregate held plan, seats, proration state, invoice line items and payment retries all in one place. The trade-off surfaced when Finance needed a second, independent billing cadence (annual pre-pay with monthly usage true-up) that had nothing to do with how seats were provisioned, and the team discovered that touching proration logic risked breaking seat assignment because both lived inside the same Cancel() and ChangePlan() methods.

The real question wasn't "should we split the code" — everyone agreed the class was too big — it was where the seam goes. Three options were on the table: split by technical layer (still one bounded context, just smaller classes); split by aggregate only (two aggregates, one bounded context, one team); or split into two bounded contexts entirely, each with its own ubiquitous language, each owned by a different team, talking only through events.

// The seam we chose: Subscription (owned by Provisioning) publishes facts.
// Billing owns Invoice and never reaches into Subscription's internals.
public sealed record SubscriptionRenewed(SubscriptionId SubscriptionId, PlanId PlanId, int SeatCount, DateOnly PeriodStart, DateOnly PeriodEnd);

public sealed class Invoice // Billing's own aggregate root — its own ubiquitous language, "billing period" not "subscription cycle"
{
    public static Invoice OpenFor(BillingPeriod period, IReadOnlyCollection<LineItem> usageLines) { /* ... */ return null!; }
    // Invoice has never heard of "seats" or "plans" — it knows LineItems and BillingPeriods.
}

We drew the boundary at the subdomain, not the class: Provisioning (core domain — plan changes, seat assignment, entitlements) stayed one bounded context; Billing (supporting domain — invoicing, proration math, payment retries) became a second, subscribed to SubscriptionRenewed/SubscriptionCancelled/PlanChanged events and translated them into its own Invoice vocabulary via an anti-corruption layer at the subscription boundary.

The trade-off we accepted going in: Billing's view of a subscription is now always slightly behind reality, and reconciliation (what happens when a plan change and a renewal race) became a real design problem instead of an implicit database transaction. We built an explicit reconciliation job for exactly that race, because pretending eventual consistency has no edge cases is how you get a quiet, expensive support queue.

What the interviewer is really probing. Whether you can articulate a bounded-context boundary in terms of subdomain type and team ownership, not just "the code got big." A candidate who says "we just extracted a service" without naming what changed about the language, the consistency guarantee, and who owns the model on each side hasn't actually drawn a bounded context — they've done a deployment topology change and called it DDD.

(b) STAR/CARL scaffold

Situation
Two genuinely different subdomains have been sharing one aggregate/module because one team originally wrote both, and a new requirement on one side keeps risking breakage on the other.
Task
Decide where the bounded-context seam actually goes, not just which classes to split.
Action
Identify the two ubiquitous languages already fighting each other in the code; check which side is core vs. supporting; choose the integration pattern (published event + ACL, in this case) that matches the actual team-ownership boundary.
Result
Independent deploys, an explicit and monitored consistency window, and a named reconciliation process for the race the split created.
Differently
I'd draw the seam a year earlier, at the point the second team was staffed, rather than waiting for a feature collision to force the conversation.

(c) Recall prompts

Where in your codebase do two different teams' vocabularies collide inside one class or module?

Sketch: look for a class with two sets of naming conventions, or a comment like "this field is really for the other team's use case."

Have you ever had to decide between splitting an aggregate and splitting a bounded context?

Sketch: the tell is whether the split needs a new ubiquitous language and a new team boundary, or just a smaller class — those are different-sized decisions.

What's a time an eventual-consistency window you introduced created a real race condition?

Sketch: name the two events that could arrive out of order, and what you built to reconcile them.

Have you used an anti-corruption layer to keep one side's model pure?

Sketch: a translation layer at the boundary that turns the other side's events/DTOs into your own model's vocabulary, so your domain never imports their types.

(d) Follow-up drill chain

Why not a shared kernel instead of two fully separate contexts?

A shared kernel would have meant Billing and Provisioning agreeing on and versioning a common model together — viable when the overlap is small and stable, but our overlap (proration math touching seat counts) was exactly the part that kept changing on both sides independently. A shared kernel under active, divergent change becomes a permanent negotiation; the event-based seam let each side evolve its own invariants without a cross-team change-approval step on every release.

What if Billing needed strongly consistent seat counts at invoice time?

Then I'd reconsider whether Billing is really a separate bounded context or whether seat-count-at-invoice-time is actually a Provisioning invariant leaking into Billing's language. If the business genuinely requires strong consistency, that's a signal the two are more tightly coupled than "core vs. supporting" and might warrant a synchronous query (not a shared database) at invoice-generation time, accepting the availability coupling that comes with it — a customer-supplier relationship rather than a pure event subscriber.

At what team scale does this split stop paying for itself?

Below roughly one team per context, the ceremony of published events, versioned contracts and an ACL is pure overhead — a single team maintaining both sides can just refactor the shared aggregate directly and skip the integration pattern entirely. We only justified the split because two separately-staffed teams already existed and were already stepping on each other.

What did you trade away?

Query simplicity — "give me a subscription with its current invoice" is now two calls and a join in application code instead of one EF navigation — and immediate consistency, in exchange for independent deployability and a much smaller blast radius per change.

How did you handle versioning the published event contract itself?

Treated SubscriptionRenewed as a published language with the same care as a public API: additive changes only, a deprecation window before removing a field, and a contract test in Provisioning's pipeline that fails the build if a change would break Billing's known consumers.

Would you do it the same way today?

Yes — and today I'd also write the contract test using EF Core 10's ability to project events straight into a JSON complex type snapshot for the contract fixture, rather than the hand-rolled serializer we built at the time.

03Two clerks, one seat, no lock

Senior production incident / outage

(a) Worked example EXAMPLE — replace with your own

A venue-booking feature let two support agents assign the same last seat in a section within the same second, because the Booking aggregate's "is this seat still free" check and the write that claimed it were two separate round-trips with no concurrency control between them — a textbook lost-update problem. It only showed up under real concurrent load (Friday afternoon, agents racing to fulfil the same waitlist), so it slipped through every manual test and most of the automated ones too.

// Before: check-then-act with no protection against another writer in between.
var section = await _repo.GetByIdAsync(sectionId);
if (section.AvailableSeats.Contains(seatNumber))
{
    section.AssignSeat(seatNumber, customerId); // both agents get past the check
    await _repo.SaveAsync(section);              // second save silently overwrites the first
}

The fix used EF Core's built-in optimistic concurrency: a RowVersion token on the Section aggregate's row, mapped as a concurrency token, so the second save throws DbUpdateConcurrencyException instead of silently clobbering the first agent's assignment. The aggregate itself also got a proper invariant — AssignSeat re-checks AvailableSeats against its own in-memory state right before mutating, so the failure mode is "reload and retry", not "double-booked, discover it downstream."

public class Section
{
    public byte[] RowVersion { get; private set; } = default!; // EF concurrency token
    public void AssignSeat(SeatNumber seat, CustomerId customer)
    {
        if (!_availableSeats.Remove(seat))
            throw new DomainException($"Seat {seat} is not available."); // invariant, not a caller's job to re-check
        _assignments.Add(new SeatAssignment(seat, customer));
        Raise(new SeatAssigned(Id, seat, customer));
    }
}
// modelBuilder.Entity<Section>().Property(s => s.RowVersion).IsRowVersion();

The application layer now catches DbUpdateConcurrencyException, reloads the aggregate, and retries the command once before surfacing a "seat just taken, pick another" response to the losing agent — a much better outcome than a double-booked seat discovered at the venue door.

What the interviewer is really probing. Whether you distinguish this from a locking problem that needs a mutex, and instead recognise it as a consistency-boundary problem the aggregate itself should own. The strong answer names the mechanism (optimistic concurrency token, retry-on-conflict) and explains why the invariant belongs inside AssignSeat rather than as a check the caller is trusted to perform first — an aggregate that trusts its caller to check invariants isn't really protecting them.

(b) STAR/CARL scaffold

Situation
Two concurrent writers can both pass a stale "is this still available" check and one write silently overwrites the other.
Task
Prevent the double-assignment without serialising every read through a database lock.
Action
Add an optimistic concurrency token to the aggregate's persistence mapping; move the invariant check inside the aggregate's own mutating method so it re-validates against current state; add a reload-and-retry path in the application layer for the losing writer.
Result
Zero double-assignments since the fix, one clean retry for the losing agent instead of a silent conflict discovered later.
Differently
I'd have written a concurrent-writers test for this aggregate from day one — it's a five-line xUnit test with Task.WhenAll that would have caught it before Friday afternoon did.

(c) Recall prompts

Where have you seen a check-then-act race on an aggregate that only showed up under real concurrent load?

Sketch: the giveaway is a bug that never reproduces in a debugger step-through but shows up reliably under load — that's your signal to look for a gap between a read and the write that acts on it.

Have you added an optimistic concurrency token to fix a lost-update bug?

Sketch: name the column/property (row version, timestamp, ETag) and what the retry path looked like for the caller that lost the race.

What invariant did you move from "caller's responsibility" into the aggregate itself?

Sketch: a validation that used to live in a service or controller, moved into the entity/aggregate's own method so it can't be bypassed by a second caller.

Have you written a test specifically designed to provoke a race condition?

Sketch: concurrent Task.WhenAll calls against the same aggregate ID is the simplest version; note what you asserted on the losing call.

(d) Follow-up drill chain

Why optimistic concurrency and not a distributed lock or SELECT ... FOR UPDATE?

Because the contention here is rare (two agents hitting the exact same seat in the exact same second) relative to total traffic, so paying the cost of a lock — held connections, reduced throughput, and a new failure mode if the lock isn't released — on every single assignment would be strictly worse than occasionally retrying the rare loser. Pessimistic locking is the right call when contention is the common case, not the exception.

What if the retry also lost, and kept losing?

After one retry we surface "seat no longer available" rather than looping — an aggregate under genuine sustained contention (a flash-sale seat) needs a different design entirely (e.g. a reservation queue or a dedicated allocator service), and silently retrying forever just hides that the aggregate boundary is wrong for that specific hot spot.

At what request volume does optimistic concurrency itself become the bottleneck?

When the conflict rate climbs high enough that a large fraction of writes are retries, the aggregate is effectively a single point of serialisation regardless of locking strategy — at that point I'd split the hot aggregate (e.g. one row per seat rather than one row per section) so unrelated seats stop contending on the same concurrency token at all.

What did you trade away?

A slightly worse user experience for the rare loser (an extra round-trip and a "pick another seat" message) in exchange for never silently corrupting the booking state — an acceptable trade for anything where the alternative is two people showing up for one seat.

How did you make sure this class of bug doesn't recur elsewhere?

Added a lint-style code-review checklist item — any aggregate mutator that removes from a finite collection (seats, inventory, coupon redemptions) must have both a concurrency token on the entity and an in-method invariant check — and retrofitted the same pattern onto two other aggregates that had the identical shape.

Would you do it the same way on today's stack?

Yes, unchanged — IsRowVersion() and catching DbUpdateConcurrencyException are unaffected by the EF Core 10 owned-entity-to-complex-type migration, since Section here is an entity with identity, not a value object; that change matters more for stories like the ones about value objects, not this one.

04Fixing the value object that wasn't one

Senior migration / version upgrade

(a) Worked example EXAMPLE — replace with your own

We modelled Address as a value object on Customer years ago, using EF Core's owned entity types because that was the documented way to map value objects at the time. It worked, mostly — until a bug report: updating a customer's billing address sometimes also silently changed their shipping address. Two owned instances that should have been independent values turned out to be the same tracked entity instance after a particular load pattern, because owned entity types have reference semantics in EF's change tracker, not value semantics — assigning one owned instance's reference to two navigation properties aliases them, and EF Core's own documentation for EF Core 10 explicitly calls this out as a reason to migrate to complex types instead.

// Before: Address as an owned entity type — looks like a value object, behaves like an aliasable reference.
modelBuilder.Entity<Customer>().OwnsOne(c => c.BillingAddress);
modelBuilder.Entity<Customer>().OwnsOne(c => c.ShippingAddress);

// The bug: a "copy billing to shipping" helper did this —
customer.ShippingAddress = customer.BillingAddress; // now BOTH properties reference the same tracked instance
customer.ShippingAddress.Line1 = "Suite 400";        // mutates BillingAddress too — surprise
// After: Address as a complex type (EF Core 10) — genuine value semantics, no shared tracked identity.
modelBuilder.Entity<Customer>().ComplexProperty(c => c.BillingAddress);
modelBuilder.Entity<Customer>().ComplexProperty(c => c.ShippingAddress);

public readonly record struct Address(string Line1, string City, string PostalCode, string Country); // struct: copy semantics for free
customer.ShippingAddress = customer.BillingAddress; // a genuine copy now — mutating one never touches the other

The migration wasn't purely mechanical: complex types (unlike owned entity types) have no independent identity or table by default, don't support collections of complex types in every provider yet, and — the part that actually took the most care — every LINQ query that had relied on Address comparing by identity (context.Customers.Where(c => c.BillingAddress == someTrackedInstance)) had to be rewritten to compare by value, which is what a value object should have meant all along.

Owned entity type (before)Complex type (after, EF10)
EqualityIdentity-based (reference/PK)Value-based, as expected of a VO
Assignment aliasing riskYes — the bug we hitNo, struct-backed copy semantics
Bulk update via ExecuteUpdateAsyncNot supportedSupported (EF Core 10)
Optional (nullable) instanceAwkwardSupported (EF Core 10)

What I'd do differently: model value objects as complex types (or, pre-EF10, at minimum as immutable classes with value equality overridden) from day one, and treat "does this concept have its own identity and lifecycle" as the actual test for entity-vs-value-object — not "does it have more than one property," which was the intuition that led us to reach for OwnsOne without questioning it.

What the interviewer is really probing. Whether you know the difference between a value object's conceptual definition (no identity, immutable, compared by value) and how a specific ORM has historically mapped it — and whether you can name a concrete, current (EF Core 10) reason the mapping technique itself changed. A candidate who says "value objects are just DTOs" or can't explain why aliasing was even possible hasn't internalised the concept, only the vocabulary.

(b) STAR/CARL scaffold

Situation
A "value object" mapped via ORM owned-entity conventions exhibited reference-sharing behaviour that a real value object never should.
Task
Fix the aliasing bug and migrate the mapping to something that actually enforces value semantics, without breaking existing queries.
Action
Diagnosed the root cause as owned-entity reference semantics; migrated to EF Core 10 complex types backed by a record struct; found and rewrote every identity-based comparison in the codebase.
Result
The aliasing class of bug became structurally impossible, and several LINQ queries got simpler once they compared by value instead of joining through a synthetic owned-entity key.
Differently
Modelled the type as immutable with value equality from the very first line, rather than trusting the ORM's default mapping to imply the right semantics.

(c) Recall prompts

Have you found a "value object" in your codebase that was actually mutable or shared by reference?

Sketch: look for a setter on a type that conceptually shouldn't have identity, or a bug where mutating one instance affected an unrelated one.

What's a migration you did purely to fix a semantic mismatch, not to add a feature?

Sketch: name the before/after mapping and the specific bug class it eliminated, not just "we cleaned up the code."

Where has an ORM's default mapping convention led your team to model something incorrectly?

Sketch: this doesn't have to be EF Core — any ORM's "convention over configuration" can quietly encode the wrong domain concept if nobody questions it.

Have you had to rewrite queries after changing how equality worked on a type?

Sketch: identity-based to value-based (or vice versa) comparisons are a common source of silent behaviour change during this kind of migration.

(d) Follow-up drill chain

Why not just override Equals and GetHashCode on the owned entity type instead of migrating to complex types?

Because the aliasing bug wasn't about equality comparison at all — it was about two navigation properties sharing one tracked instance in the change tracker. Overriding equality would have made two different instances compare equal by value, which is correct, but it does nothing to stop an assignment from aliasing the same instance across two properties. The reference-semantics problem needed a representation with copy semantics (a struct-backed complex type), not a smarter comparer.

What if a provider doesn't yet support every complex-type feature you need — collections of complex types, say?

Then I'd keep the specific collection case as an owned entity type (or a normalised child table) while moving every non-collection value object to complex types — the migration doesn't have to be all-or-nothing, and mixing mapping strategies per-property is explicitly supported. I'd document which properties are the exception and why, so the next person doesn't "fix" it back to owned inconsistently.

At what schema scale does this migration get risky?

Once dozens of entities own the same value-object type across a large schema, the query-rewrite surface (every identity-based comparison, every raw SQL that assumed an owned-entity shadow key) grows fast enough that I'd do it type-by-type behind a feature flag, with a query-level regression suite run against a copy of production data, rather than one big-bang migration.

What did you trade away?

A short migration window of dual-write risk (had to keep both mappings compiling during the transition) and the loss of the owned entity's implicit shadow primary key, which two reporting queries had started depending on without anyone noticing — those queries needed an explicit rewrite, not just a recompile.

How did you catch other places relying on owned-entity identity semantics before shipping?

Grepped for every navigation property of the value-object type, then specifically searched for assignment expressions (x.Address = y.Address) and any .Where clause comparing the property directly rather than its fields — both are the two shapes that behave differently under the old vs. new mapping.

Would you do it the same way today?

Yes, and today I'd start there directly — EF Core 10 complex types are the documented, recommended approach for value objects from the outset, so a new project has no reason to reach for owned entity types for a true value object at all.

06The refund that emailed the customer twice

Mid nasty debugging session

(a) Worked example EXAMPLE — replace with your own

Customers processing a refund sometimes got two "your refund is on its way" emails for the same refund. It wasn't a duplicate-message-queue problem — the queue had exactly-once delivery to the handler. The actual cause took a full afternoon to find: the domain event RefundIssued was being raised twice from inside one call to Refund.Issue(), because a retry wrapper around the repository's save call re-executed the whole application-service method (including the domain call that raised the event) after a transient database timeout — and the event had already been dispatched to the notification handler on the first, apparently-failed attempt, before the timeout was even reported.

// The trap: retrying the whole use case re-runs domain logic that already had a side effect.
[Retry(Attempts = 3)]
public async Task IssueRefundAsync(RefundRequest request)
{
    var refund = await _repo.GetByIdAsync(request.RefundId);
    refund.Issue(request.Amount);              // raises RefundIssued and dispatches immediately — side effect #1
    await _repo.SaveAsync(refund);              // times out here — retry re-runs the whole method
} // second attempt: refund.Issue() runs again, dispatches RefundIssued a second time

The domain event itself wasn't the bug — dispatching it eagerly, from inside the domain method, before the transaction that made the state change durable had actually committed, was. The fix collected domain events on the aggregate without dispatching them, and had the application layer dispatch them only after SaveChangesAsync succeeded — so a retry after a save failure re-runs the domain logic (which is idempotent on already-issued refunds, since Issue() now checks status first) but never re-dispatches an event for a save that already, in fact, went through.

public abstract class AggregateRoot
{
    private readonly List<IDomainEvent> _events = new();
    protected void Raise(IDomainEvent e) => _events.Add(e); // collected, not dispatched
    public IReadOnlyList<IDomainEvent> PullEvents() { var e = _events.ToList(); _events.Clear(); return e; }
}
// Application layer: dispatch only after the transaction that persisted the state change actually commits.
await _db.SaveChangesAsync();
foreach (var e in refund.PullEvents()) await _publisher.PublishAsync(e);

What made this a nasty debugging session specifically: the retry attribute lived in a cross-cutting infrastructure module nobody on the feature team had touched in months, so the first three hours went into the notification pipeline and the message broker — the places that looked like they owned "sending things twice" — before anyone thought to ask whether the domain call itself could have run more than once.

What the interviewer is really probing. Whether you understand that domain events must be collected and dispatched after the transaction commits, not raised-and-dispatched inline — this is one of the most common real bugs in DDD implementations that use in-process domain events, and a candidate who's actually shipped this pattern will have a story like this one, because almost everyone hits it once.

(d) Follow-up drill chain

Why not just make the notification handler deduplicate by refund ID instead of fixing the dispatch timing?

Deduplication at the handler is a reasonable belt-and-suspenders addition, but it doesn't fix the underlying problem: any other consumer of RefundIssued — a future analytics subscriber, an audit log — would hit the same double-dispatch, and I'd need to remember to add dedup logic to every single one forever. Fixing the dispatch timing at the source removes the entire class of bug for every current and future subscriber at once.

What if the transaction commits but the event dispatch itself then fails?

That's the mirror-image problem — the state change is durable but the notification never went out — and it's why I'd rather have an outbox-style approach for anything where a lost event is unacceptable: persist the events to be dispatched in the same transaction as the state change, then have a separate dispatcher read and publish them with its own retry, so dispatch failure is retryable independent of whether the aggregate's own method runs again.

At what scale does the in-process collect-and-dispatch pattern stop being sufficient?

Once dispatch needs to survive the process crashing between commit and publish, or needs to reach consumers in a separate service, in-process dispatch isn't enough regardless of timing — that's the point at which I'd introduce the transactional outbox pattern this story only gestures toward, backed by a proper message broker for delivery to other services.

What did you trade away?

A small amount of complexity — the aggregate now needs a "pull events" step that every application-service method must remember to call after save — in exchange for correctness that doesn't depend on the retry policy of unrelated infrastructure code staying exactly as it was when the aggregate was written.

How did you make sure every other aggregate got the same fix, not just Refund?

Wrote a unit test template that any aggregate's test suite could reuse — "call the mutating method, assert events are queued but not dispatched, call PullEvents, assert they drain" — and added a code-review checklist line for any new aggregate root.

Would you do it the same way today?

Yes, and today I'd pair it with a source-generated marker interface for domain events so the "did you remember to call PullEvents" step can be enforced by an analyzer rather than a checklist, catching the mistake at compile time instead of in production.

08The script that balanced itself

Senior security issue found and fixed

(a) Worked example EXAMPLE — replace with your own

A wallet top-up feature had a security review finding that turned out to be a domain-modelling problem in disguise: the "add funds" and "spend funds" operations were two separate application-service methods, each independently loading a customer's WalletBalance row, mutating it, and saving — with no aggregate enforcing that balance could never go negative and no single place that owned the invariant "balance changes must be attributable to exactly one recorded transaction." An attacker who fired concurrent spend requests at an endpoint with a race in the balance check could push the balance negative before either write committed — a lost-update bug with a security consequence, not just a data-integrity one.

// Before: balance is a bare decimal column, mutated directly by two unrelated code paths.
public async Task SpendAsync(Guid customerId, decimal amount)
{
    var balance = await _db.WalletBalances.FirstAsync(w => w.CustomerId == customerId);
    if (balance.Amount >= amount) // check
    {
        balance.Amount -= amount; // act — no protection against a concurrent spend between check and act
        await _db.SaveChangesAsync();
    }
}

The fix modelled Wallet as a proper aggregate root whose only way to change balance is through Debit/Credit methods that append an immutable LedgerEntry and enforce the non-negative invariant inside the same method — plus the row-version concurrency token from a similar earlier incident, so a race is rejected rather than silently corrupting the balance. The balance itself became a derived value (sum of ledger entries), not a mutable field that any caller could decrement directly.

public class Wallet
{
    private readonly List<LedgerEntry> _entries = new();
    public Money Balance => _entries.Aggregate(Money.Zero, (sum, e) => sum + e.SignedAmount);
    public void Debit(Money amount, string reason)
    {
        if (Balance - amount < Money.Zero)
            throw new InsufficientFundsException(Id, Balance, amount); // invariant enforced here, nowhere else
        _entries.Add(LedgerEntry.Debit(amount, reason));
        Raise(new WalletDebited(Id, amount, reason));
    }
}

Security signed off once we could show: no code path could mutate balance except through the two methods, both methods were covered by the concurrency token, and the ledger gave us a tamper-evident audit trail (every balance is provably the sum of its recorded entries) that the original bare-decimal column never could.

What the interviewer is really probing. Whether you connect security and domain modelling — a lot of "security bugs" in financial-flavoured domains are actually missing aggregate invariants, and the fix that satisfies a security reviewer (an auditable, tamper-evident trail; an invariant that can't be bypassed) is often exactly the fix a DDD-minded engineer would reach for anyway. The weak answer treats this as purely "add a lock"; the strong one treats it as "the aggregate wasn't protecting its own invariant."

public class Order // after: the rules live once, inside the type they govern
{
    public OrderStatus Status { get; private set; }
    public void Ship()
    {
        if (Status != OrderStatus.Paid) throw new DomainException("Cannot ship an unpaid order.");
        Status = OrderStatus.Shipped;
        Raise(new OrderShipped(Id));
    }
    public Money Cancel()
    {
        var refundable = _lines.Where(l => !l.IsShipped).Sum(l => l.Total); // the bug is now structurally impossible
        Status = OrderStatus.Cancelled;
        Raise(new OrderCancelled(Id, refundable));
        return refundable;

12The cascade delete that reached across a boundary

(a) Worked example EXAMPLE — replace with your own

Deleting a product category in the catalog admin tool cascaded, through an EF Core foreign key relationship, all the way down to deleting order line items in a completely different bounded context — because a "temporary" convenience navigation property from Category to OrderLine (added months earlier so a report could avoid a join) had a cascade-delete convention nobody had turned off. // The convenience navigation that should never have existed across a bounded-context boundary.

{

}
// modelBuilder had no explicit .OnDelete(DeleteBehavior.Restrict) — EF's default FK convention cascaded.

public class Category
{
    // Reporting now queries OrderLine by CategoryId (a plain value), never through a shared EF navigation —
    // there's no relationship for a cascade convention to ever attach to.

14Translating a mainframe into a domain

(a) Worked example EXAMPLE — replace with your own

A new claims-processing bounded context had to integrate with a decades-old mainframe policy system that spoke in coded field abbreviations ("PLCYSTA", values like "A", "L", "P", "T" with meanings that existed only in a retired analyst's memory and a scanned PDF from 1994) and had no appetite, budget, or business case for replacement. Modelling the new domain directly against those codes would have meant every developer touching claims logic needing to know that "PLCYSTA=L" means "lapsed," forever, and every mainframe quirk (a known bug where "T" sometimes appears for terminated policies instead of the documented code) leaking straight into our domain model's vocabulary.

We built a dedicated anti-corruption layer — a translation service sitting at the integration boundary, owned by our team, whose entire job is converting the mainframe's coded, quirky representation into our own clean PolicyStatus domain concept, and nothing on our side of the line ever sees a raw mainframe code.

public enum PolicyStatus { Active, Lapsed, PendingRenewal, Terminated } // our domain's own vocabulary

public class MainframePolicyTranslator // the anti-corruption layer — the only place that knows "PLCYSTA" exists
{
    public PolicyStatus Translate(MainframePolicyRecord raw) => raw.PlcySta switch
    {
        "A" => PolicyStatus.Active,
        "L" => PolicyStatus.Lapsed,
        "P" => PolicyStatus.PendingRenewal,
        "T" => PolicyStatus.Terminated,
        _ when raw.PlcySta == "T" && raw.LastModifiedByBatchJob == "EOD_TERM" => PolicyStatus.Terminated, // the known quirk, isolated here
        _ => throw new UntranslatableMainframeCodeException(raw.PlcySta) // fail loudly, never guess silently
    };
}

The UntranslatableMainframeCodeException branch turned out to matter more than the happy path: it fired twice in the first month on genuinely new codes the mainframe team had added without telling anyone, and because our domain model failed loudly at the translation boundary instead of silently mis-mapping an unknown code to some default, both incidents were caught before a single claim was processed incorrectly — exactly the containment an anti-corruption layer is supposed to provide.

What the interviewer is really probing. Whether you understand the anti-corruption layer as an active translation boundary with its own tests and failure modes, not just a thin DTO-mapping layer. The strongest signal is the "fail loudly on unknown input" design choice and a real story of it catching an actual integration surprise — a candidate who says "we just wrote a mapper" without that safety property has built a thinner, riskier version of the pattern.

An order-fulfilment saga — reserve inventory, charge payment, schedule shipment, notify customer, close order — was implemented as choreography: each step's aggregate raised a domain event, and the next step's handler subscribed to it, with no single place coordinating the whole flow. The root cause: the shipment-scheduling service had deployed a change that silently swallowed a specific exception type instead of letting it propagate, so failures weren't being retried or dead-lettered — they were disappearing, with no compensating action ever triggered to refund the now-orphaned charge. In choreography, with no central saga state, there was no single place that even knew a specific order had stalled at step three specifically — each service only knew its own step, and nothing was watching for "an order that should have moved to step four hours ago and hasn't."

// Immediate mitigation: manual compensating action, driven by a query no one had needed to write before.
var stuckOrders = await _db.Orders.Where(o => o.PaymentChargedAt != null && o.ShipmentScheduledAt == null
    && o.PaymentChargedAt < DateTimeOffset.UtcNow.AddHours(-1)).ToListAsync();
foreach (var order in stuckOrders) { await _refundService.RefundAsync(order.Id); await _notify.SendStalledOrderApologyAsync(order.CustomerId); }

The longer-term fix moved this specific saga from pure choreography to orchestration: a dedicated OrderFulfillmentSaga process manager holding explicit state for every order in flight, with an explicit timeout on every step and a defined compensating action if that timeout fires — so "stuck after payment, before shipment" becomes a state the saga itself detects and reacts to automatically, not a fact only discoverable by an ad hoc query at 2am.

public class OrderFulfillmentSaga // orchestrator — the single place that knows the whole flow's current state
{
    public SagaStep CurrentStep { get; private set; }
    public void OnShipmentSchedulingTimedOut() // explicit timeout handling, per step
    {
        _compensations.Enqueue(new RefundPayment(OrderId));   // compensating transaction for the pivot already crossed
        _compensations.Enqueue(new ReleaseInventoryReservation(OrderId));
        CurrentStep = SagaStep.Failed;
    }
}

What the interviewer is really probing. Whether you understand the real operational trade-off between saga choreography and orchestration — not just that they're "two ways to do sagas," but that choreography's decoupling comes at the direct cost of losing a single place to observe and react to a stuck multi-step process. (d) Follow-up drill chain

Why not just fix the swallowed exception and keep the choreography design?

Fixing the swallowed exception addressed that one root cause, but the structural gap — no place that knows an order is stuck, regardless of why it's stuck — would still be there for the next unrelated failure mode. The orchestrator redesign is about detecting and compensating for any stall at any step, not just the specific bug that caused this one; choreography would need the same "is anything overdue" watchdog logic re-invented and duplicated per service to get equivalent coverage.

What if moving to full orchestration was too large a change to make quickly — what would you have done as an intermediate step?

Exactly what we actually did first: keep choreography, but add a lightweight saga-state tracking table (updated by each step's event handler) purely for observability, plus a scheduled job that alerts on any order overdue at any step. That gets you the detection benefit without the larger redesign, and is a reasonable place to stop if full orchestration's added coupling isn't justified for a given saga's risk profile.

At what saga complexity does orchestration's central coordinator become a bottleneck or single point of failure itself?

Once the orchestrator needs to coordinate a very large number of steps or very high-volume sagas, its own state store and its own availability become the new critical path — at that scale I'd shard the orchestrator by saga instance (each in-flight order's saga state is independent) rather than accept one global coordinator, keeping the "one place to see this order's state" benefit without a single global bottleneck.

What did you trade away?

Some of choreography's service independence — the orchestrator now has to know about all five steps, so a new step type requires changing the orchestrator, not just adding an independent subscriber — in exchange for the single, queryable source of truth about any order's saga state that made this incident possible to prevent from recurring.

How did you make sure the compensating actions themselves were safe to run automatically, unattended?

Made every compensating action idempotent (refunding an already-refunded order is a safe no-op, releasing an already-released inventory reservation is a safe no-op) and added a dry-run mode that logged what it would have compensated for a full week before enabling live automatic compensation, specifically because an automated system taking money-affecting action unattended needed more scrutiny than the manual version had.

Would you do it the same way today?

Yes — and if we were choosing the messaging/mediation layer for the orchestrator fresh today, the MediatR licensing change from story 17 would be part of that specific tooling decision, alongside the architectural choice of orchestration itself.

Staff CI / test reliability improvement

(a) Worked example EXAMPLE — replace with your own

Our CI pipeline for the pricing domain took eleven minutes and failed intermittently roughly one run in eight, for reasons that had nothing to do with pricing logic — a shared test database under contention from parallel test runs, container startup flakiness, migration ordering races. (d) Follow-up drill chain

Isn't it risky to lose end-to-end coverage by testing the domain in isolation from real persistence?

We didn't lose end-to-end coverage — we kept a smaller, deliberately-scoped set of integration tests specifically for the persistence mapping (owned-entity/complex-type configuration, cascade behaviour, query translation) that can only be verified against a real database, plus a handful of true end-to-end smoke tests. What we removed was redundant coverage: the same domain rule being re-verified, at database speed, by dozens of tests that all exercised persistence in an identical, already-covered way.

What if a domain rule's correctness genuinely depended on database behaviour — a computed column, a stored procedure?

Then that rule doesn't belong purely in the in-memory unit-test bucket — it's a case where domain logic and persistence are legitimately coupled, and I'd test it as an integration test deliberately, not force it into the fast suite for the sake of a clean split. The split is a guideline based on where the actual dependency lies, not a rule to satisfy at the cost of a real gap in coverage.

At what team/codebase size does maintaining two separate test tiers (fast unit, slower integration) stop being worth the extra structure?

Even a small codebase benefits from this split once CI time starts to matter to velocity — the real cost isn't the two-tier structure, which is cheap to set up, it's remembering to keep new tests in the right tier as the team grows, which is why we added a lightweight naming/folder convention and a CI runtime budget per tier that fails the build if a "unit" test takes longer than a configured threshold, catching drift back toward database-backed unit tests automatically.

What did you trade away?

A small amount of test realism — the in-memory unit tests can't catch a mismatch between the aggregate's in-memory behaviour and how EF actually materialises or persists it, which is exactly why the smaller integration-test tier still exists rather than being eliminated entirely.

How did you migrate the existing ~140 tests without a huge, risky one-time rewrite?

Migrated incrementally, by aggregate, starting with the highest-flakiness offenders first (measured from CI history, not guessed), verifying each migrated test still failed on the same bug scenarios via mutation testing before deleting its database-backed predecessor — the same "prove parity before cutting over" discipline as the strangler-fig story earlier in this bank.

Would you do it the same way today?

Yes — and I'd specifically watch, on EF Core 10, that any complex-type value objects used as test-builder arguments stay plain, equality-comparable structs, since that's precisely the property that keeps them constructible and assertable without touching the change tracker at all.

Modelling judgment

22Night-before cheat sheet

All tiers last-minute recall

  1. An aggregate is a consistency boundary, not a convenience boundary — model exactly what one transaction's invariant needs, nothing more; story 01 is the load-bearing example if asked to elaborate.
  2. Reference other aggregates by ID only, never by navigation property — cascade deletes, deploy coupling, and God-object growth (stories 07, 12) all trace back to violating this one rule.
  3. A value object has no identity and is compared by value — on EF Core 10, that means complex types, not owned entity types, because owned entities alias by reference (story 04).
  4. Domain events are collected on the aggregate and dispatched only after the transaction commits — dispatching inline, before commit, causes duplicate side effects under any retry (story 06).
  5. Bounded context boundaries follow subdomain type and team ownership, not code size — "the class got big" is not the same decision as "these are two different ubiquitous languages" (story 02).
  6. Ubiquitous language lives in the code, not just in a glossary doc — if two teams' rename conversation doesn't touch actual type and method names, the ambiguity will drift back (story 13).
  7. Anti-corruption layers should fail loudly on unrecognised input, never guess silently — a silent default at a translation boundary is how a legacy system's drift becomes your domain's corruption (story 14).
  8. Event sourcing earns its cost only when you actually need history or temporal queries — check the real read pattern first; both over-adopting it (story 15) and belatedly retiring it (story 16) are common, credible stories.
  9. Saga orchestration trades some coupling for a single place to observe and compensate a stuck multi-step process — choreography's independence is exactly what makes "which step is this stuck at" unanswerable without it (story 18).
  10. Domain logic that depends only on plain values and value objects — not injected infrastructure — is what makes fast, database-free unit testing possible (story 19); if you can't unit-test an invariant without a database, the aggregate's dependencies are probably wrong, not just the tests.
  11. Two current, citable 2025/2026 facts worth having ready: EF Core 10 (LTS, November 2025) recommends complex types over owned entity types for value objects; MediatR v13+ requires a paid commercial licence above a revenue/funding threshold, with a free Community tier below it.
