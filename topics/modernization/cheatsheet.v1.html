Modernization (.NET full-stack)

cheatsheet · .NET 10 LTS · released 2025-11-11

The commands, project switches, migration idioms and cutover mechanics for moving a live .NET + JS/TS + SQL + Azure system off its legacy: assessment queries, strangler-fig and expand–contract patterns, System.Web adapters and YARP, upgrade tooling, ESM and TypeScript 7, schema evolution, Azure platform choice and the flags that make a cutover reversible. It reflects .NET 10 LTS (2025-11-11, supported to 2028-11-14) with .NET 11 in RC for 2026-11-10, C# 14/EF Core 10, Aspire 13.5, TypeScript 7.0 (native Go compiler, GA 2026-07-08), Node.js 24 LTS, ESLint 10, Angular 22, React 19.2 and SQL Server 2025. Assumption: “modernization” here means evolving a system that is already in production — runtime and framework upgrades, decomposition, data and platform moves — not greenfield architecture and not datacentre-exit rehosting, which appears only as the option you compare against.

01Assess before you touch code

docs: Port from .NET Framework

Every modernization argument you will have is won or lost on inventory. Produce four numbers first: what is out of support, what is vulnerable, what actually gets traffic, and where the code churns.

.NET inventory

Installed SDKs/runtimes, EOL flags
dotnet sdk check — prints “out of support” per band; dotnet --info for the raw list
Which projects are still legacy
grep -rl "<TargetFrameworkVersion>" --include=*.csproj . — non-SDK-style; SDK-style uses <TargetFramework>
Effective TFM per project
dotnet msbuild App.csproj -getProperty:TargetFramework SDK 8+
Outdated / vulnerable / deprecated
dotnet list package --outdated --include-transitive, then --vulnerable, then --deprecated — transitive is where the CVEs hide
Why is this package here at all
dotnet nuget why ./src Newtonsoft.Json SDK 8.0.2+ — prints the dependency chain, ends “we can't drop it” arguments
Restore-time CVE gate
<NuGetAudit>true</NuGetAudit> + <NuGetAuditMode>all</NuGetAuditMode> — on by default since NuGet 6.8; all (direct+transitive) is the default from SDK 9
Windows-only API use
analyzer CA1416 with <SupportedOSPlatform> — the old .NET Portability Analyzer is archived; use analyzers, not the retired tool
Binary-level API surface
apicompat / Microsoft.DotNet.ApiCompat.Tool — proves a rewritten library is drop-in for its callers

JS/TS inventory

Outdated + advisories
npm outdated; npm audit --omit=dev; npm audit fix --dry-run
Who pulls in the bad version
npm ls lodash --all; npm query "#lodash" — the npm answer to nuget why
Dead files, exports, deps
npx knip — deletes more of a legacy SPA than any refactor; npx depcheck for deps only
Bundle truth
npx vite-bundle-visualizer / npx source-map-explorer dist/**/*.js
Node floor the repo assumes
engines in package.json + .nvmrc — CI and dev must agree or “works on my machine” is structural

Data and traffic inventory

-- compat level per database: 160 = SQL 2022, 170 = SQL 2025
SELECT name, compatibility_level, is_read_committed_snapshot_on FROM sys.databases;

-- deprecated T-SQL still being executed (counter resets on restart)
SELECT instance_name, cntr_value FROM sys.dm_os_performance_counters
WHERE object_name LIKE '%Deprecated Features%' AND cntr_value > 0;

-- the 20 queries that actually cost money (Query Store, on by default since SQL 2022)
SELECT TOP 20 q.query_id, SUM(rs.count_executions * rs.avg_duration) / 1000.0 AS total_ms
FROM sys.query_store_runtime_stats rs
JOIN sys.query_store_plan p ON p.plan_id = rs.plan_id
JOIN sys.query_store_query q ON q.query_id = p.query_id
GROUP BY q.query_id ORDER BY total_ms DESC;
Azure estate in one query
az graph query -q "Resources | summarize count() by type, location" — Resource Graph, not az resource list, once you pass a few hundred resources
Runtime versions in App Service
az webapp list --query "[].{n:name,stack:siteConfig.netFrameworkVersion,tls:siteConfig.minTlsVersion}" -o table
Which endpoints are alive
App Insights / OTel: requests by route over 30 days — retire the zero-traffic 30% instead of porting it
Where the code churns
git log --format=format: --name-only --since=2.years | sort | uniq -c | sort -rg | head -30 — churn × complexity picks the first strangler slice

Assessment output, not a report: one table of components × {runs on, supported until, CVEs, traffic, churn, owner}. If a component has no owner, that is the finding.

02Strategy patterns & the 7 Rs

docs: CAF Modernize

Pick the R per component, never per system. Most real programmes are a mix, and the two cheapest Rs — retire and retain — are the ones nobody proposes.

RMeansPick it whenCost / risk
Retiredelete itzero or near-zero traffic; a report nobody openslowest; only political
Retainleave it, ring-fence itstable, low-change, regulated, or vendor-ownedlow; needs an explicit re-review date
Rehostlift & shift to IaaS/containersdatacentre exit deadline drives the clockfast, keeps every existing problem
Replatformsame code, managed platformIIS → App Service, SQL VM → Azure SQL MIthe usual 80/20 — config change, not rewrite
Refactorsame shape, new runtime/APIs.NET Framework → .NET 10; jQuery → TSmedium; behaviour must be provably unchanged
Rearchitectsplit or re-shape the systemone deploy unit blocks four teamshigh; only with a real scaling/ownership pain
Rebuild / Replacerewrite, or buy SaaSdomain has moved on; commodity capabilityhighest; the rewrite everyone underestimates

The patterns you will actually name in a design review

Strangler fig
route slice-by-slice through a facade (YARP, App Gateway, Front Door) until the legacy has no traffic, then delete it. Needs a routing seam and per-route rollback; the “then delete it” is the step teams skip.
Branch by abstraction
introduce an interface over the old implementation, add the new one behind it, flip per call site, remove the abstraction. Trunk-based alternative to a long-lived migration branch.
Expand – migrate – contract
the only safe schema/API change under zero downtime: add the new shape, dual-write and backfill, move readers, drop the old. Also called parallel change; each phase is its own deploy.
Anti-corruption layer
translate at the boundary so legacy models never leak into the new service. One ACL per legacy system, owned by the new side.
Dark launch / shadow traffic
send real traffic to the new path, discard its response, compare. The cheapest correctness evidence you will ever get.
Verification by diff
call both, return old, log mismatches (the “scientist” pattern). Budget for non-determinism: clocks, GUIDs, ordering, culture.
Fitness function + ratchet
an automated check that the property you are fixing only improves: warning count, TFM count, nullable-clean project count. Baseline it in CI; the number may fall, never rise.
Seam
the place you can change behaviour without editing the legacy: HTTP route, DI registration, message topic, DB view. No seam ⇒ no incremental plan ⇒ you are proposing a rewrite; say so out loud.

Sequencing rule: runtime upgrade first (same shape, new .NET), then architecture. Rearchitecting on a dead runtime means debugging two problems at once, and the runtime one has a support deadline attached.

03.NET SDK, TFMs & repo hygiene

docs: .NET CLI

Before any porting, make the repo boring: one SDK band, one place for versions, warnings that mean something. Multi-targeting is what lets old and new hosts share the same library during the migration.

// global.json - pin the SDK band, allow patches, keep CI and dev identical
{ "sdk": { "version": "10.0.100", "rollForward": "latestFeature", "allowPrerelease": false } }
<!-- Directory.Build.props at repo root: applies to every project below it -->
<Project>
  <PropertyGroup>
    <LangVersion>latest</LangVersion>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <!-- the ratchet: everything is an error except the debt you have not paid yet -->
    <WarningsNotAsErrors>CS8600;CS8602;CS8618</WarningsNotAsErrors>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
    <AnalysisLevel>latest-recommended</AnalysisLevel>
    <NuGetAuditMode>all</NuGetAuditMode>
    <InvariantGlobalization>true</InvariantGlobalization>  <!-- only if you never format per-culture -->
  </PropertyGroup>
</Project>

<!-- Directory.Packages.props: Central Package Management, one version per package for the repo -->
<Project>
  <PropertyGroup><ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally></PropertyGroup>
  <ItemGroup>
    <PackageVersion Include="Microsoft.EntityFrameworkCore.SqlServer" Version="10.0.0" />
    <PackageVersion Include="Azure.Identity" Version="1.17.0" />
  </ItemGroup>
</Project>
Bridge library for both hosts
<TargetFrameworks>net48;net10.0</TargetFrameworks> + #if NETFRAMEWORK — the domain assembly compiles for the old web app and the new one at once
packages.config → PackageReference
VS: right-click Migrate packages.config…; then SDK-style csproj by hand or via the Copilot upgrade agent — do this before retargeting; a 600-line csproj becomes ~15 lines
Add / list / search packages
dotnet package add Serilog, dotnet package list --outdated SDK 10 — new noun-first verbs; dotnet add package still works
Reproducible restore
dotnet restore --locked-mode with <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
Format / style ratchet
dotnet format --verify-no-changes in CI; severities live in .editorconfig, raised one rule at a time
Test platform
dotnet test runs on Microsoft.Testing.Platform by default SDK 10; dotnet test --coverage --coverage-output-format cobertura — no more coverlet package for the common case
Throwaway spike, no project
dotnet run probe.cs .NET 10 — file-based app with #:package Dapper@2.* directives; ideal for migration probes and data checks
Container without a Dockerfile
dotnet publish -p:PublishProfile=DefaultContainer -p:ContainerRegistry=acme.azurecr.io .NET 7+
Trim / AOT viability check
<PublishTrimmed>true</PublishTrimmed>, <PublishAot>true</PublishAot> — warnings here tell you which reflection-heavy libraries block the modern hosting model
Which .NET is supported
10 LTS → 2028-11-14 · 9 STS and 8 LTS both end 2026-11-10 · 11 STS GA 2026-11-10 — landing on 8 today buys you two months

Framework is not dead, it is frozen: .NET Framework 4.8/4.8.1 is a Windows component and stays serviced with the OS — no forced deadline, but no new APIs, no ASP.NET Core, no modern perf, and a shrinking library ecosystem. “It is supported” is a true statement and a bad argument.

04ASP.NET → Core, incrementally

docs: Incremental migration

The supported strangler for ASP.NET on .NET Framework: a new ASP.NET Core app in front, YARP forwarding what it cannot serve, System.Web adapters sharing session and identity across the two. Ship route by route.

// New .NET 10 app (the "shim"): handles migrated routes, proxies the rest to the .NET 4.8 app
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSystemWebAdapters()
    .AddJsonSessionSerializer(o => o.RegisterKey<int>("VisitCount"))
    .AddRemoteAppClient(o =>
    {
        o.RemoteAppUrl = new Uri(builder.Configuration["LegacyApp:Url"]!);
        o.ApiKey = builder.Configuration["LegacyApp:ApiKey"]!;   // shared secret, from Key Vault
    })
    .AddAuthenticationClient(isDefaultScheme: true)   // identity comes from the legacy app
    .AddSessionClient();                              // and so does Session

builder.Services.AddReverseProxy()
    .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"));

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.UseSystemWebAdapters();
app.MapDefaultControllerRoute().RequireSystemWebAdapterSession();
app.MapForwarder("/{**catch-all}", builder.Configuration["LegacyApp:Url"]!);  // fallback = legacy
app.Run();
// Legacy .NET Framework app: expose the session/auth endpoints the shim calls
// Global.asax.cs -> Application_Start
SystemWebAdapterConfiguration.AddSystemWebAdapters(this)
    .AddJsonSessionSerializer(o => o.RegisterKey<int>("VisitCount"))
    .AddProxySupport(o => o.UseForwardedHeaders = true)   // so the legacy app sees the real host/scheme
    .AddRemoteAppServer(o => o.ApiKey = ConfigurationManager.AppSettings["RemoteAppApiKey"])
    .AddAuthenticationServer()
    .AddSessionServer();

The mechanical replacements

HttpContext.CurrentIHttpContextAccessoradapters provide HttpContext.Current as a bridge — a crutch, not a destination; it forces sync request buffering
Session["k"] (in-proc)distributed cache / explicit stateadapters can share it; sticky sessions block scale-out
Web API 2 ApiControllerControllerBase / minimal APIsIHttpActionResult → IResult/ActionResult<T>
MVC5 System.Web.MvcMicrosoft.AspNetCore.MvcRazor syntax mostly ports; @Html helpers shrink, tag helpers replace them
WebForms .aspxRazor Pages / Blazorno automated path — ViewState has no equivalent; rebuild page by page behind YARP

Cost of the bridge: remote session is an HTTP round trip and locks the legacy session for the request; auth is another. Fine for a migration window, wrong as an architecture. Track “routes still proxied” as a burn-down and delete the adapters at zero.

05Upgrade tooling & Copilot agents

docs: Copilot upgrade for .NET

The tooling story changed under everyone in November 2025: the free .NET Upgrade Assistant was deprecated in favour of an AI agent behind a paid Copilot licence. Know both, and know why the agent output still needs a characterization-test net.

Current path (retarget)
GitHub Copilot app modernization — upgrade for .NET: VS 2026, or VS 2022 17.14.16+; assess → plan → execute, each stage writing Markdown artifacts you review and edit before it runs 2025-11
Licence
paid Copilot SKU (Pro / Pro+ / Business / Enterprise) — the agent will not run on Copilot Free; budget it, it is now a line item in a migration plan
Current path (to Azure)
app modernization — migrate to Azure: predefined tasks (SQL/Service Bus/Storage auth → managed identity, on-disk files → Blob, MSMQ → Service Bus), then generates azd + Bicep and fixes the code to match
Interactive run
the upgrade canvas in the GitHub Copilot app shows the live plan, per-project status and diffs instead of scattered chat + Markdown 2026
Legacy path, still there
the classic Upgrade Assistant ships in VS 2026 but is off by default — enable it under Tools > Options; the standalone CLI (dotnet tool install -g upgrade-assistant, upgrade-assistant upgrade ./App.sln) is deprecated and unmaintained
Still useful, non-AI
dotnet format, dotnet list package, dotnet nuget why, Roslynator, and repo-wide Roslyn analyzers with dotnet build /warnaserror — deterministic, free, CI-able
Retired, do not cite
try-convert (archived), .NET Portability Analyzer (archived), Data Migration Assistant retired 2025-07-16, Azure Data Studio retired

JS/TS and framework codemods

Angular version step
ng update @angular/core@22 @angular/cli@22 — one major at a time, never two; schematics rewrite the code for you
React API churn
npx codemod react/19/migration-recipe; npx types-react-codemod@latest preset-19 ./src
ESLint config
npx @eslint/migrate-config .eslintrc.json — mandatory for ESLint 10, which removed eslintrc
Anything bespoke
npx jscodeshift -t transform.js src/ --parser=tsx — write the codemod once for 400 call sites; reviewable as one mechanical diff

Rule for agent-driven upgrades: characterization tests first (record real inputs/outputs of the legacy path), agent second. An LLM upgrade produces a plausible diff; only the pinned behaviour tells you it is the same program. Review agent commits per project, not per solution, and never let it bump a major version and refactor in the same commit.

06JS/TS: ESM, TS 7, tooling

docs: TS modules reference

Three separate migrations that get conflated: CommonJS→ESM, JS→TS, and the toolchain (webpack/Babel/ts-node → Vite/esbuild/native). Do them one at a time; each has its own rollback.

Node runtime ladder

Where the LTS line is

// package.json - the modern shape
{
  "type": "module",
  "engines": { "node": ">=24" },
  "exports": {                       // replaces "main"; blocks deep imports into your internals
    ".":         { "types": "./dist/index.d.ts", "import": "./dist/index.js" },
    "./testing": { "types": "./dist/testing.d.ts", "import": "./dist/testing.js" }
  },
  "imports": { "#config": "./src/config.js" },   // internal alias, no tsconfig paths needed at runtime
  "workspaces": ["packages/*"]
}
// tsconfig.json - TypeScript 7 baseline for a Node service
{
  "compilerOptions": {
    "module": "nodenext", "moduleResolution": "nodenext", "target": "es2023", "lib": ["es2023"],
    "strict": true, "noUncheckedIndexedAccess": true, "exactOptionalPropertyTypes": true,
    "verbatimModuleSyntax": true,     // `import type` means erased; no accidental runtime import
    "isolatedModules": true,          // required by every esbuild/swc-based bundler
    "erasableSyntaxOnly": true,       // keeps the code runnable by node's type stripping
    "noEmit": true, "skipLibCheck": true
  }
}
TypeScript 7.0
native Go compiler, GA 2026-07-08; same tsc binary, same typescript package, 8–12× faster check — no stable programmatic API until 7.1, so custom transformers, some ESLint type-aware rules and API-consuming plugins are the migration blockers, not your code
Staged adoption
keep TS 6.x (the JS compiler line) for the build, run tsgo --noEmit in a parallel CI job until it is green, then swap — both read the same tsconfig
__dirname in ESM
import.meta.dirname / import.meta.filename Node 20.11 — not fileURLToPath(import.meta.url) boilerplate any more
JS → TS, file by file
allowJs + checkJs + JSDoc types first; rename .js→.ts per file; ban new any with @typescript-eslint/no-explicit-any on new files only
Strictness ratchet
baseline the error count from tsc --noEmit; CI fails if it rises — same fitness-function trick as the C# warning ratchet
ESLint 10
2026-02 flat config only (eslint.config.mjs), eslintrc removed, Node ^20.19+ required; v9 went EOL 2026-08-06
Build tool
webpack → Vite (Rolldown/esbuild under it) — port dev server first, keep the webpack production build until bundle diffing is clean
Lockfile discipline
npm ci in CI, never npm install; force a transitive fix with "overrides" (npm) / "resolutions" (yarn) / "pnpm.overrides"

Order that works: Node LTS bump → ESM ("type": "module" + exports) → TS strictness → TS 7 → bundler. Doing ESM and the bundler swap together makes every failure ambiguous, and both fail loudly at runtime rather than at build time.

08Database & schema evolution

docs: Applying EF migrations · Azure DB migration

The database is the part of the system that cannot be rolled back by redeploying. Every schema change ships as expand → migrate → contract, and every one of those phases is compatible with both the old and the new code.

-- 1. EXPAND (deploy alone; old code unaffected)
ALTER TABLE dbo.Orders ADD CustomerRef uniqueidentifier NULL;          -- metadata-only, NULLable
CREATE INDEX IX_Orders_CustomerRef ON dbo.Orders(CustomerRef)
    WITH (ONLINE = ON, RESUMABLE = ON, MAXDOP = 4);                    -- pause/resume under load

-- 2. MIGRATE: app dual-writes both columns; backfill in bounded batches, never one UPDATE
DECLARE @rows int = 1;
WHILE @rows > 0
BEGIN
    UPDATE TOP (5000) o SET o.CustomerRef = c.ExternalId
    FROM dbo.Orders o JOIN dbo.Customers c ON c.Id = o.CustomerId
    WHERE o.CustomerRef IS NULL;
    SET @rows = @@ROWCOUNT;
    WAITFOR DELAY '00:00:00.200';                                      -- give the log shipper air
END

-- 3. CONTRACT (only after every reader is on the new column, and you can prove it)
ALTER TABLE dbo.Orders ALTER COLUMN CustomerRef uniqueidentifier NOT NULL;
ALTER TABLE dbo.Orders DROP COLUMN CustomerId;
Migration style
migration-based (EF Core, DbUp, Flyway) vs state-based (SSDT/DACPAC + sqlpackage) — pick one per database and write it down; mixing them is how “drift” becomes an outage
Deploy EF migrations properly
dotnet ef migrations bundle --self-contained -o migrate — a single executable for the pipeline; no SDK on the box; or dotnet ef migrations script --idempotent for DBA review
Never
db.Database.Migrate() in Program.cs — N replicas race, and rollback means a code deploy. Schema is a pipeline step, not a startup step.
EF Core 10 wins
LeftJoin()/RightJoin() as first-class operators · JSON columns translate to JSON_VALUE(... RETURNING ...) · SQL parameter values redacted in logs by default · vector search — requires .NET 10
Bulk without a loop
ExecuteUpdateAsync / ExecuteDeleteAsync EF 7 — replaces load-modify-SaveChanges for backfills
Compat-level bump
ALTER DATABASE X SET COMPATIBILITY_LEVEL = 170; (SQL 2025; 160 = 2022) after SET QUERY_STORE = ON and SET AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = ON) — upgrade the engine and the CE separately so a regression has one cause
Pin a plan, no code change
sys.sp_query_store_set_hints SQL 2022 — the modern replacement for plan guides and OPTION (RECOMPILE) sprinkling
Blocking-free reads
ALTER DATABASE X SET READ_COMMITTED_SNAPSHOT ON; — usually the single highest-value legacy fix; needs tempdb headroom and a NOLOCK hunt afterwards
SQL Server 2025
native vector type + VECTOR_DISTANCE (GA; DiskANN vector indexes still preview), native json type, regex functions, Entra managed identity for outbound calls

10Cutover, flags & verification

docs: .NET feature management

A migration is not a release, it is a sequence of reversible releases. Every step needs a flag, a metric that says it is working, and a documented way back that is not “restore the backup”.

// Flag + percentage rollout, config-driven from Azure App Configuration
builder.Configuration.AddAzureAppConfiguration(o => o
    .Connect(new Uri(endpoint), cred)
    .UseFeatureFlags(f => f.SetRefreshInterval(TimeSpan.FromSeconds(30))));
builder.Services.AddFeatureManagement().WithTargeting();

app.MapGet("/orders/{id}", async (int id, IVariantFeatureManager flags, HttpContext ctx) =>
    await flags.IsEnabledAsync("NewOrderPipeline", ctx.RequestAborted)
        ? await modern.GetAsync(id)
        : await legacy.GetAsync(id));
// Shadow + diff: legacy answers the user, modern is measured against it
var legacyTask = legacy.GetAsync(id);
if (await flags.IsEnabledAsync("ShadowOrderPipeline"))
{
    _ = Task.Run(async () =>
    {
        try
        {
            var (a, b) = (await legacyTask, await modern.GetAsync(id));
            if (!Compare.Equivalent(a, b))                       // ignore clocks, GUIDs, ordering
                _mismatch.Add(1, new KeyValuePair<string, object?>("route", "orders.get"));
        }
        catch (Exception ex) { _log.LogWarning(ex, "shadow failed"); }   // never affects the user
    });
}
return await legacyTask;
Route-level traffic split
az webapp traffic-routing set --distribution staging=10 -g rg -n app · az containerapp ingress traffic set -n app -g rg --revision-weight blue=90 green=10
Blue/green swap and back
az webapp deployment slot swap -g rg -n app --slot staging — swap back is the rollback; mark environment-specific settings as slot settings or they travel with the swap
Data cutover
dual-write behind the flag, or CDC/change tracking → outbox → new store; reconcile with a scheduled count/checksum job until the diff is zero for N days
Proof the port is faithful
characterization tests from recorded production inputs · contract tests at the seam · shadow diff rate · p95 latency and error rate per route, old vs new on one dashboard
Rollback ladder
flag off (seconds) → revision weight to 0 (a minute) → slot swap back (minutes) → redeploy previous (10s of minutes). Database changes are forward-only — that is why contract is a separate deploy.
Decommission is a task
legacy stays warm and monitored for an agreed window, then: DNS off → traffic zero for N days → stop → snapshot → delete. Unfinished migrations cost double forever; put the delete date in the plan.
Progress metric that is not a story point
% of requests served by the new path · routes still proxied · projects still on the old TFM · shadow mismatch rate — publish them weekly; they end the “are we nearly there” meeting

Flag hygiene: every migration flag gets an owner and an expiry date at creation. A flag that outlives its migration is a permanent untested branch — the second system you now maintain.

11Gotchas & review one-liners

docs: .NET breaking changes

Runtime and .NET

  • Sync-over-async ported straight from Framework (.Result, .Wait()) — harmless under ASP.NET's sync context, thread-pool starvation under Kestrel.
  • HttpContext.Current via the adapters forces request buffering and kills streaming; every remaining use is a migration to-do, not a solution.
  • Default culture changed: .NET Core is invariant-first on Linux — ToString(), Parse and string sorting drift. Set InvariantGlobalization deliberately, and never rely on string.Compare ordinal-by-accident.
  • new HttpClient() per call exhausts sockets; per-app singleton never sees DNS changes. Use IHttpClientFactory.
  • BinaryFormatter is removed in .NET 9+ — any legacy cache, session or on-disk blob using it needs a new serializer and a data migration.
  • MachineKey-encrypted cookies do not decrypt under Data Protection — without the compat shim, every user is logged out at cutover.
  • Windows-only leftovers that fail only in production on Linux: registry reads, System.Drawing, drive letters, \ paths, case-insensitive file names, WMI, COM.
  • Multi-targeting hides bugs: a net48+net10.0 library ships two behaviours. Run the test suite for both TFMs or the bridge is untested.
  • Landing on .NET 8 “because it is LTS” in 2026: support ends 2026-11-10. Target 10.

JS/TS

  • Flipping "type": "module" breaks require, __dirname, and every tool config that was CommonJS — convert configs in the same PR.
  • enum, namespace and constructor parameter properties block Node's type stripping; erasableSyntaxOnly catches them before the runtime does.
  • TS 7's missing stable API breaks plugins, not your code — audit custom transformers and type-aware lint rules before scheduling the swap.
  • skipLibCheck: false plus one badly typed dependency stalls the whole upgrade; keep it true during migration.
  • Two React copies (module federation, a stale nested node_modules) produce “invalid hook call” — check npm ls react before debugging hooks.
  • A supply-chain fix that only bumps direct deps fixes nothing: the CVE is usually transitive. Verify with npm ls, not the changelog.

Database

  • An unbounded backfill UPDATE takes a lock escalation, blows the log and blocks the app; batch it and watch log reuse.
  • ALTER COLUMN ... NOT NULL and dropping a column are size-of-data or blocking operations — they belong in the contract phase, never with the expand.
  • Bumping the compat level changes the cardinality estimator: plans regress. Query Store + FORCE_LAST_GOOD_PLAN before, not after.
  • NOLOCK everywhere is a symptom of missing RCSI, not a performance strategy; it returns rows twice or not at all.
  • EF Core generates different SQL across majors — a version bump is a query-plan change. Diff the generated SQL for the top-20 queries.
  • Azure SQL Database has no SQL Agent, no cross-database queries, no CLR; discovering that after the code freeze is the classic Managed-Instance-shaped surprise.

Azure and process

  • App settings that are not marked slot settings follow the swap and point production at the staging database.
  • DefaultAzureCredential silently walks its chain: it can work locally with your account and fail in Azure with the wrong identity. Pin ManagedIdentityClientId and log which credential won.
  • Connection strings in app settings are not secrets management; a Key Vault reference costs one line and removes the rotation project.
  • Lift-and-shift to containers without externalizing session, local file writes and the local scheduler gives you a container that cannot scale past one replica.
  • Rewrite before instrumentation: without baseline latency, error and usage data you cannot prove the new system is better, and you will be asked.
  • A migration with no delete date is not a migration — it is a second system, funded forever.
