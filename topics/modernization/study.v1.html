Modernization (.NET full-stack)

study · anchor stack: .NET 10 LTS · released 2025-11-11 · supported to 2028-11-14

Modernization in 2026 is dominated by two hard calendar dates and one new tool class. .NET 8 and .NET 9 both leave support on 10 November 2026 — nine weeks from today — which means every "we're on .NET 8, we're fine" estate is about to be unsupported, and .NET 10 LTS (11 November 2025, supported to 14 November 2028) is the only sane target; on the data side SQL Server 2016 hit end of extended support on 14 July 2026, Data Migration Assistant retired in July 2025 and the Azure Data Studio SQL migration extension retired on 28 February 2026, so the tooling you rehearsed two years ago no longer exists. The new tool class is agentic: GitHub Copilot app modernization went GA for .NET on 22 September 2025 and now runs in Visual Studio 2026, VS Code, the Copilot CLI and on GitHub.com, doing assessment, upgrade, dependency patching and containerization as an agent loop rather than a wizard — which changes what a lead is expected to do from "run the upgrade" to "design the verification that makes an agent's diff safe to merge". The rest of the stack moved too: TypeScript 7.0 shipped its Go-native compiler on 8 July 2026 (8–12× faster, but no stable programmatic API until 7.1, so typescript-eslint and the Vue/Svelte/Astro type-checkers cannot run on it yet), Node.js 24 is Active LTS with the release model changing in October 2026, and the architectural fashion has reversed — roughly 42% of organisations that went microservices have consolidated services back, making the modular monolith the default landing zone rather than a fleet of services. One assumption, stated once because the phrase is overloaded: this guide treats "software modernization" as moving existing, revenue-carrying .NET + JS/TS + SQL systems onto a currently supported runtime, data platform and cloud without stopping the business — not greenfield architecture, not a general cloud-adoption course, and not a specific vendor's migration-factory methodology.

01 Why modernize, and the 7 Rs

Docs: Cloud Adoption Framework · Modernize · Port from .NET Framework to .NET · .NET support policy · Rationalize workloads

Modernization is not "rewrite the old thing in the new thing". It is a controlled, reversible sequence of changes to a system that is currently earning money, chosen so that the business keeps running through every intermediate state. That definition is the whole discipline. Everything else in this guide — strangler fig, expand–contract, characterization tests, YARP, blue/green — exists to make one of those intermediate states survivable. If you take one mental model into an interview, take this one: the hard part is never the target architecture, it is the twelve months during which both architectures are live at once.

The second mental model, which separates lead-level answers from senior ones: modernization is a portfolio decision, not an engineering decision. You do not modernize "the system". You classify each workload, and for most of them the correct answer is "not now, and here is what would change my mind". A candidate who wants to move everything to Kubernetes has told the interviewer they have never had to defend a budget.

The running example: Meridian

Keep one system in your head for the whole guide. Meridian is a freight-and-customs brokerage platform, first shipped in 2011, that clears roughly 40,000 shipments a day and is the only way the company invoices. It is:

  • an ASP.NET Web Forms operator UI (~600 .aspx pages) and an ASP.NET MVC 5 customer portal, both on .NET Framework 4.8;
  • a WCF service layer (netTcpBinding internally, basicHttpBinding for two customs authorities) with EF6 and a lot of hand-written SqlCommand;
  • a SQL Server 2016 database, 4 TB, ~900 tables, 1,200 stored procedures, compatibility level 110, plus overnight SSIS packages;
  • a front end of jQuery 1.9, Knockout and a bundle of ScriptManager partial postbacks, with one team already shipping a React 19 island;
  • running on Windows Server 2016 VMs in a colocation facility, deployed by a Friday-night MSI and a runbook in Confluence.

Every unit below moves one piece of Meridian. Every deadline in the hero applies to it: SQL Server 2016 lost support on 14 July 2026, Windows Server 2016 loses it on 12 January 2027, and .NET Framework 4.8 will get security patches "for decades" but caps you at C# 7.3 and Windows-only hosting.

Three honest reasons, and one dishonest one

Interviewers probe your why because it predicts everything downstream: what you sequence first, what you are willing to leave alone, and how you talk to a CFO. There are three defensible drivers and one that gets projects cancelled halfway.

  1. Risk you cannot insure against. An unsupported runtime, OS or database means unpatchable CVEs, failed audits, and — increasingly — contractual and regulatory exposure. This is the driver that gets funded, because it is the one where doing nothing has a price.
  2. Cost of change. The metric that matters is not infrastructure spend, it is how long a routine change takes to reach production. If a one-line pricing fix takes six weeks because it needs a Friday-night MSI and a full regression, the business is paying for that every week.
  3. A capability you cannot build. Something concrete and dated: the customer wants real-time shipment tracking, the regulator wants an audit event stream, the board wants vector search over customs rulings. .NET Framework and a 2016 database physically cannot deliver it.

The dishonest one is "the code is bad". Every legacy system's code is bad, that has never once been sufficient justification, and saying it out loud marks you as the engineer who will run out of political capital in month four. Translate it: bad code becomes "cost of change", which is measurable, and measurable is fundable.

The business case, in numbers a CFO recognises

Two framings, and you need both. The risk framing prices doing nothing: unsupported SQL Server 2016 means paid Extended Security Updates (available to 17 July 2029) or an unpatched database in a PCI/ISO audit; unsupported Windows Server 2016 after 12 January 2027 means the same for the OS. ESU is deliberately priced to be more expensive than migrating — that is its purpose, and naming it shows you understand Microsoft's incentive design.

The flow framing prices the status quo. Take the four DORA metrics and convert them to money: if lead time for a pricing change is 30 days and each day of delay costs the business a quantifiable margin, that is your number. Do not promise "50% cost savings" from cloud — that claim ages badly, and the 2026 evidence runs the other way: microservice estates commonly run 3.75–6× the infrastructure cost of the monolith they replaced, which is exactly why the modular monolith is the current default (unit 13).

Interview trap

Proposing a rewrite. "We'd rebuild it properly on .NET 10 and cut over" is the single most common way to fail a lead-level modernization interview, because the interviewer has lived through one. The failure mode is structural, not motivational: the legacy system keeps changing while you rebuild, so you are chasing a moving target with a team half the size of the one maintaining the original; you have no revenue until cutover day, so the project is politically defenceless the moment budgets tighten; and the requirements are not in the specification, they are in fifteen years of bug fixes that nobody wrote down. The answer that lands is: "big-bang rewrite only when the old system is genuinely unportable and small enough to rebuild in under two quarters — otherwise strangler fig, so every month produces something shippable and the project can be paused at any point without losing what it has delivered."

Gotcha

"Lift and shift then optimise later" is a real strategy and also the most common place modernization dies. Rehosting removes the deadline pressure that funded the work, so the optimisation phase competes with feature work and loses. If you rehost, write the replatform commitment into the same funding decision with a date, or accept honestly that rehost is the end state and you have bought three years of runway at a higher run-rate.

Try it — 45 minutes, two exercises

1. Rationalize a real portfolio. List every deployable unit in a system you know — including the scheduled jobs and the "temporary" console app. For each, write the R, one sentence of rationale, and the evidence you would need to defend it. Time-box it to 45 minutes; the point is not accuracy, it is discovering how many units you cannot name an owner for.

2. Price doing nothing. Pick the oldest component in your stack, find its official end-of-support date, and work out the two costs: the ESU/extended-support price if one exists, and the lead-time cost of the change process it forces.

Expected outcome

Exercise 1 almost always turns up two things: a handful of units that should simply be retired (the cheapest modernization there is, and the one nobody proposes because it earns no architecture points), and at least one component with no owner — which is your real risk, because unowned components are the ones that block a cutover at 3am.

Exercise 2 gives you the sentence that unlocks funding. "Staying on SQL Server 2016 costs us ESU from July 2026 and fails the next ISO 27001 surveillance audit" moves budget; "the code is hard to work with" does not.

Interview Q&A · why modernize

How do you decide whether to modernize a system at all?

I start from the workload, not the system, and I ask what would change if we did nothing for two years. Three things justify action: unsupported components that create unpatchable risk or audit failures, a cost of change high enough that the business is visibly paying for it in lead time, and a capability the current platform physically cannot deliver. If none of those is true, the honest answer is "retain, with a review date" — and I write the review date down so the decision does not quietly rot. I also try to get the driver named explicitly by the sponsor, because the driver decides the sequence: risk-driven work goes runtime and OS first, cost-of-change-driven work goes deployment pipeline and test coverage first, and capability-driven work goes to the specific slice that unlocks the capability. Projects that cannot state their driver are the ones that get cancelled at the halfway mark.

Walk me through the 7 Rs and how you choose between them.

Retire, retain, rehost, replatform, refactor, rebuild, replace — ordered roughly by cost and disruption. I treat it as a ladder and force a justification for each rung I climb: you only rehost if retain is untenable, only replatform if rehost does not remove the risk, and so on. In practice replatform is the sweet spot for most .NET estates, because moving from IIS on a VM to App Service or Container Apps, and from SQL Server on a VM to Azure SQL Managed Instance, removes the OS and patching risk without touching business logic. Rebuild I reserve for things with no supported migration path — ASP.NET Web Forms is the canonical example, since it never came to modern .NET and never will. And I always look for retire candidates first, because deleting a workload is the only option with negative cost, and in every estate I have seen there were at least a few.

The business wants a full rewrite. How do you respond?

I do not refuse it, I price it and expose the risk profile, because "no" without an alternative loses the room. A rewrite has three structural problems: the legacy system keeps changing so you are chasing a moving target, there is no value delivered until cutover so the project is defenceless when budgets tighten, and the real requirements live in fifteen years of undocumented bug fixes rather than in any specification. Then I offer the alternative in their language: a strangler-fig sequence where every six to eight weeks something real ships and the old system shrinks, with the option to stop at any point and keep what has been delivered. I will concede a rewrite when the component is genuinely unportable and small enough to finish inside two quarters — a Web Forms screen group, a Silverlight applet — because at that size the rewrite is a strangler step. What I will not agree to is a rewrite whose first release date is more than two quarters out.

How do you build the business case for modernization?

Two framings, presented together. The risk framing prices doing nothing with dates and invoices: SQL Server 2016 left extended support on 14 July 2026, so we are either buying Extended Security Updates or running an unpatched database through the next audit, and Windows Server 2016 hits the same wall on 12 January 2027. The flow framing prices the status quo using DORA metrics translated into money — a 34-day median lead time on a pricing change is a number the commercial side can multiply by something. What I deliberately avoid is promising infrastructure cost savings from moving to cloud, because that claim is frequently false and it will be audited; the 2026 data on microservice estates running several times the cost of the monolith they replaced is a good reminder. I also present the portfolio distribution rather than a single number, so the sponsor sees that most workloads are cheap replatforms and only two are expensive.

What is the cost of doing nothing, concretely?

Four buckets. Direct: extended-support fees, which Microsoft prices deliberately above the cost of migrating, plus the rising cost of hardware and hosting for platforms nobody else runs. Risk: unpatchable CVEs in unsupported components, and the audit and insurance consequences — many cyber-insurance renewals now ask directly about unsupported software. Opportunity: features you cannot ship, which is the bucket the business feels but rarely attributes correctly. And people: hiring for .NET Framework 4.8 and Web Forms is measurably harder every year, and the engineers who know the system are the ones most likely to leave because of it. The fourth bucket is the one leaders underweight, and it is the one that turns a manageable migration into an emergency, because you lose the knowledge exactly when you need it.

Which R would you pick for an ASP.NET Web Forms application, and why?

Rebuild the UI, but only after replatforming everything underneath it, and only for the pages that matter. Web Forms depends on System.Web, the page lifecycle and ViewState, none of which came to modern .NET and none of which ever will — so there is no port, only a rewrite of the presentation layer. But the business logic behind it usually does port, so the sequence is: extract the logic out of code-behind into libraries that target net10.0 or netstandard2.0, get those onto modern .NET with tests, then rebuild the screens incrementally behind a reverse proxy so old and new pages coexist on one hostname and one session. I also insist on usage data before scoping: in the systems I have seen, a small minority of screens carry the overwhelming majority of sessions, and the tail is a retire candidate rather than a rebuild candidate. Blazor Server is a legitimate target if the team's skills are C#-heavy and the component model fits, but it is a choice to argue for, not a default.

How do you know when modernization is "done"?

I define done as a set of testable properties, not a milestone, and I write them at the start so the answer is not negotiated at the end. Typically: zero components past end of support, the old runtime removed from every build and the CI images that could build it deleted, deployment frequency and lead time inside agreed thresholds, and the legacy shim layers — the reverse proxy routes, the dual-write paths, the compatibility adapters — deleted rather than merely unused. That last one is the honest test, because a strangler fig that never removes the scaffolding has produced two systems instead of one. I also expect an explicit list of what we chose not to modernize with review dates, because a mature programme ends with a documented residual, not with a claim of completeness.

What is the single biggest predictor of a modernization programme failing?

No verification story. Teams that fail are usually not short of engineering skill; they are unable to answer "how do we know the new path behaves like the old one?" other than by manual regression. Without characterization tests, a parallel run or production traffic shadowing, every cutover becomes a leap of faith, so cutovers get postponed, batched, and eventually become the big-bang the team swore they would avoid. The second predictor is funding shape: programmes funded as a project with an end date get cancelled at the halfway point where cost is maximal and value is minimal, whereas programmes funded as a percentage of ongoing capacity survive leadership changes. The third is not having a named owner for the legacy system during the transition, because "everyone owns it" means the production incidents land on whoever is closest and the migration team gets consumed by them.

How do you handle a workload where the only person who understands it has left?

I stop treating it as a migration problem and treat it as an archaeology problem with a hard rule: nothing is rewritten until its observable behaviour is captured. Concretely, I put the system under observation first — request/response logging at the boundary, query capture at the database, scheduled-job inventories — and build characterization tests from real traffic rather than from anyone's understanding of intent. Where the behaviour is genuinely unknowable, I use a parallel run and compare outputs on live traffic instead of trying to reason it out. I would also be explicit with the sponsor that this workload is now the most expensive item in the plan and possibly a retire candidate, because a component nobody understands, that nobody can safely change, may already be delivering less value than its risk. That conversation is uncomfortable and it is exactly what a lead is being hired to have.

Which .NET version would you target today, and why not the newest?

.NET 10, which is the LTS released on 11 November 2025 and supported to 14 November 2028. The important detail as of today is that .NET 8 and .NET 9 both go out of support on 10 November 2026 — the same day — so any estate that landed on .NET 8 as "the safe LTS" has about nine weeks left, and any plan that targets .NET 8 today is planning a second migration immediately. I would not target the newest STS release for a migration because migrating a legacy estate is already a multi-quarter commitment and pinning it to a runtime with a 24-month window converts a one-off cost into an annual one. The counter-argument I would accept is a team already on a fast upgrade cadence, where moving between majors is a week of work — for them the STS/LTS distinction barely matters, and that fluency is itself the real modernization outcome.

02 Assessing the legacy estate

Docs: Azure Migrate application and code assessment for .NET (AppCAT) · .NET Upgrade Assistant · Assess third-party dependencies · Database migration assessment

Assessment answers one question: what will actually break, and in what order do we find out? Not "what does the system do" — nobody has that, and pursuing it is how six months disappear into a documentation exercise. The output of a good assessment is a ranked list of blockers with an owner and a spike attached to each, plus an honest confidence level. The output of a bad assessment is a 90-page current-state document that is stale before it is signed off.

The mental model: your estate has three layers of unknowns, and each needs a different instrument. Static unknowns (what APIs and packages do we depend on) are answered by scanners. Dynamic unknowns (what is actually used, by whom, how often) are answered by telemetry — and only by telemetry, because every code path looks used when you read it. Behavioural unknowns (what is this stored procedure supposed to do) are answered by capture and comparison, never by reading. Candidates who only bring the first instrument produce plans that are wrong in exactly the expensive places.

Instrument one: static scanners

AppCAT — Azure Migrate application and code assessment for .NET — is the tool to name. It scans source, binaries and configuration, and reports both portability blockers and Azure-readiness issues (hard-coded connection strings, local file-system writes, machine-key session state, System.Web usage, Windows-only APIs) against a chosen target: App Service, Container Apps or AKS. It ships as a .NET global tool and a Visual Studio extension, and needs only a .NET SDK to run.

# Azure Migrate application and code assessment for .NET

  --target AppServiceWindows \

Two things a lead adds on top of the tool output. First, de-duplicate by root cause: 400 AppCAT findings are usually a dozen causes, and "every page writes to Server.MapPath("~/temp")" is one decision (move to blob storage or a temp abstraction), not 380 tickets. Second, separate blockers from smells: a blocker stops the build or the runtime, a smell costs you later. Only blockers belong in the critical path.

Instrument two: telemetry, because usage beats intuition

Scope is decided by usage data, and it is the single highest-leverage hour in the whole programme. Before scoping the Web Forms rebuild in Meridian, we counted page hits for 30 days: 180 of 600 pages carried 95% of sessions, 240 pages had fewer than ten hits in a month, and 90 had zero. That converted a 600-page rebuild into a 180-page rebuild plus a retire list — and the retire list was defensible because it had numbers.

The database has the same trick, and almost nobody runs it:

-- Which stored procedures has anyone actually executed since the last restart?
-- (Cached-plan stats: a floor, not a census - plans get evicted, so treat
--  "absent" as "needs a longer window", never as proof of disuse.)
SELECT  OBJECT_SCHEMA_NAME(ps.object_id) AS [schema],
        OBJECT_NAME(ps.object_id)        AS [proc],
        ps.execution_count,
        ps.last_execution_time,
        ps.total_worker_time / NULLIF(ps.execution_count, 0) AS avg_cpu_us
FROM    sys.dm_exec_procedure_stats AS ps
ORDER BY ps.execution_count DESC;

-- Procedures with NO cached plan at all, cross-checked against a 90-day
-- Extended Events capture before anyone is allowed to say "unused".
SELECT  s.name + '.' + p.name AS candidate_for_retirement, p.create_date, p.modify_date
FROM    sys.procedures AS p
JOIN    sys.schemas    AS s ON s.schema_id = p.schema_id
LEFT JOIN sys.dm_exec_procedure_stats AS ps ON ps.object_id = p.object_id
WHERE   ps.object_id IS NULL
ORDER BY p.modify_date;

-- What still talks to this database, and from where? The answer is always
-- "more things than the architecture diagram shows".
SELECT  DISTINCT program_name, host_name, login_name, COUNT(*) OVER (PARTITION BY host_name) AS conns
FROM    sys.dm_exec_sessions
WHERE   is_user_process = 1;

That last query is the one that finds the Access database on the finance manager's laptop, the SSRS instance nobody documented, and the integration a partner built in 2017 against a table you were about to drop. Every legacy database has at least one. Finding it during assessment costs an afternoon; finding it during cutover costs a weekend and a customer apology.

Instrument three: seams and coupling

Michael Feathers' term seam — a place where you can change behaviour without editing the code around it — is the vocabulary interviewers listen for, because the whole strangler strategy depends on finding them. In a .NET estate the natural seams are, in descending order of usefulness: HTTP boundaries (a reverse proxy can redirect a route with no code change at all), message queues, interfaces already registered in a container, database views and synonyms, and — the miserable last resort — static method calls, which have no seam at all and must be given one first.

Where there is no seam, the first modernization commit is not a migration, it is creating the seam: extract an interface, introduce a façade, put a view in front of a table. This is Feathers' "sprout and wrap" applied at architecture scale, and it is why assessment must produce a seam map, not just a blocker list.

// Before: no seam. Static call into a Framework-only, Windows-only component.
public sealed class ShipmentService
{
    public byte[] Manifest(int shipmentId)
        => LegacyPdfEngine.Render(BuildHtml(shipmentId));   // static, unmockable, Win-only
}

// First commit of the migration: create the seam. No behaviour change,
// no new project, fully testable, ships on its own.
public interface IManifestRenderer { byte[] Render(string html); }

internal sealed class LegacyManifestRenderer : IManifestRenderer
{
    public byte[] Render(string html) => LegacyPdfEngine.Render(html);
}

public sealed class ShipmentService(IManifestRenderer renderer)
{
    public byte[] Manifest(int shipmentId) => renderer.Render(BuildHtml(shipmentId));
}

What changed recently

Assessment is the part of modernization that agents genuinely changed in the last year. GitHub Copilot app modernization reached general availability for .NET on 22 September 2025, and it merges assessment and remediation into one loop: it inventories the solution, proposes an upgrade plan, applies transformations, fixes the build errors it causes, and can containerize the result. It runs in Visual Studio 2026 (and VS 2022 17.14.17+), VS Code, the Copilot CLI and on GitHub.com. On the data side the tools you may have rehearsed are gone: Data Migration Assistant retired on 16 July 2025 and the Azure SQL migration extension for Azure Data Studio retired on 28 February 2026; the current path is Azure Database Migration Service, the Azure Arc SQL migration experience, and — for Managed Instance — the Managed Instance link built on distributed availability groups for near-zero-downtime cutover (unit 08).

Interview trap

Confusing "the scanner found no blockers" with "this will port". AppCAT and the Upgrade Assistant see code, not behaviour. They cannot see that your DateTime.Now semantics depend on the server's Central European time zone and the new Linux container runs UTC; that string.Compare changed from the legacy NLS ordering to ICU on .NET 5+, so your sort order and your StartsWith results move; that your text processing assumed Windows-1252 because .NET Framework's default encoding differed; that your file paths are case-insensitive today and will not be on Linux; or that a stored procedure has been silently swallowing a deadlock for nine years. The honest answer is: scanners size the known work, and the schedule risk lives entirely in the unknown work — which is why the same assessment must produce a behavioural capture plan, not just a findings report. Naming globalization/ICU and case sensitivity specifically is a strong signal you have actually done a Framework-to-Core port.

Gotcha

Do not trust sys.dm_exec_procedure_stats as a census. It reads the plan cache, which is emptied by restarts, failovers, memory pressure and DBCC FREEPROCCACHE, so a procedure that runs once a quarter for year-end will look dead every time you check. Anything you intend to delete needs a capture window that spans the business's longest cycle — usually a full fiscal year — or an Extended Events session logging module starts to a durable target. "Unused" and "not in the cache" are different claims, and the difference is a year-end incident.

2. Find the undocumented consumer. On any database you have read access to, run the sys.dm_exec_sessions query above and list the distinct program_name/host_name pairs. Compare that list with the architecture diagram.

Expected outcome

In exercise 1 the ratio is usually between 20:1 and 40:1 — a few hundred findings collapsing to well under twenty decisions. That ratio is the number to quote when a sponsor sees a scary finding count: the report measures instances, the plan measures decisions.

In exercise 2 you will find at least one consumer that is not on the diagram: an SSRS server, a reporting tool with a shared read-only login, a scheduled Access or Excel refresh, or a partner integration. That discovery is the single most valuable artifact of assessment, because it is precisely the thing that turns a rehearsed cutover into an unrehearsed one.

Interview Q&A · assessment

How do you assess a legacy .NET estate you have never seen?

Three instruments in parallel, because they answer different questions. Static scanning with AppCAT and the .NET Upgrade Assistant tells me what will not compile or will not run on the target — System.Web, WCF server bindings, Windows-only APIs, packages with no modern target. Telemetry tells me what is actually used: page hits, endpoint call counts, procedure execution counts, job schedules, and crucially who connects to the database. Behavioural capture — request/response logging at the edge, Extended Events on the database — tells me what the system does, which no amount of reading will. I run all three in the first two weeks and deliberately do not attempt a comprehensive current-state document, because it will be stale before it is signed off. The deliverable I aim for is a ranked blocker list with an owner and a time-boxed spike per item, plus a stated confidence level so the plan's uncertainty is visible rather than implied.

What is AppCAT and what does it not tell you?

Azure Migrate application and code assessment for .NET, available as a global tool and a Visual Studio extension, scans source, binaries and configuration and reports portability and Azure-readiness issues against a chosen target such as App Service, Container Apps or AKS. It is genuinely useful for sizing the mechanical work — it will find your System.Web dependencies, local file-system writes, in-process session state and hard-coded connection strings. What it cannot see is behaviour: time-zone assumptions that break when the container runs UTC, string comparison and sorting changing because modern .NET uses ICU rather than the legacy NLS tables, case-sensitive file paths on Linux, and any semantic difference in a stored procedure. So I use it to size known work and to build the ticket list, and I explicitly budget separate time for the unknown work, which is where schedule risk actually lives. Quoting a finding count as a project estimate is the mistake it enables.

How do you find out what a legacy system actually does?

By observation, not by reading, because reading gives you intent and intent is what changed. I put logging or a proxy at the boundary and capture real request/response pairs, turn on database capture — Extended Events or Query Store — to see the actual query mix, and inventory scheduled jobs and integrations from the operating system and the scheduler rather than from documentation. Then I convert the captured traffic into characterization tests that assert current behaviour including its bugs, which gives me a regression net before I touch anything. Where behaviour is genuinely unknowable and critical, I plan a parallel run so the new implementation is compared against the old on live traffic. The mindset shift I would want an interviewer to hear is that legacy behaviour is an empirical question, and treating it as a comprehension exercise is how teams ship subtly wrong systems very confidently.

How do you identify which parts of the system to migrate first?

I score candidates on four axes and look for a specific shape rather than a maximum. Business value and change frequency tell me where modernization pays back; coupling tells me how hard it is to extract; risk tells me what a failure costs; and the presence of a seam tells me whether the extraction is even mechanically possible without a preparatory refactor. The first slice should be low risk, high learning and end-to-end — it should traverse every layer, from browser through API to database to deployment pipeline, because the point is to prove the pipeline and the coexistence mechanism, not to deliver the most value. I explicitly avoid starting with the crown-jewel workflow, since the team's first attempt at a new architecture is its worst attempt, and I avoid starting with something nobody uses, because nobody will care whether it works. Something like a read-only lookup or a reporting endpoint on the revenue path is usually the right first slice.

A stored procedure has not been called in six months. Can you delete it?

Not on that evidence. Procedure statistics come from the plan cache, which is cleared by restarts, failovers, memory pressure and manual cache flushes, so absence from the cache is not absence of execution. For anything I intend to delete I want a capture that spans the business's longest cycle — a full fiscal year for anything that could be year-end or annual regulatory reporting — collected by an Extended Events session writing to a durable target rather than by sampling the cache. Even then I do not drop it: I rename it or move it to a quarantine schema so it fails loudly and is trivially restorable, wait a cycle, and only then drop. That "deprecate before delete" step costs nothing and converts an irreversible mistake into a recoverable one, which is the whole game in a system you cannot fully test.

What is a seam, and why does it matter in modernization?

A seam, in Michael Feathers' sense, is a place where you can change behaviour without editing the surrounding code. It matters because every incremental migration strategy needs a point at which traffic or calls can be redirected to a new implementation, and that point has to exist before you can strangle anything. In a .NET estate the best seams are HTTP boundaries, because a reverse proxy can move a route with no code change at all; then message queues, then interfaces already resolved through the container, then database views and synonyms. Static calls and new expressions buried in code-behind have no seam, so the first migration commit for those components is not a migration at all — it is extracting an interface or introducing a façade so a seam exists. Being explicit about this reframes early, unglamorous refactoring work as a prerequisite the plan depends on rather than as gold-plating.

How long should an assessment take?

Two to four weeks for a substantial estate, and I would defend that boundary hard. The scanners run in hours; the rest is the telemetry window and the interviews with the people who operate the system. Beyond about a month you have stopped reducing uncertainty and started producing documentation, and the system keeps changing underneath you, so the marginal accuracy is negative. I prefer to end assessment deliberately incomplete: a ranked blocker list, a seam map, a usage-based scope decision, and an explicit list of the questions we could not answer with a spike attached to each. Then the first migration slice answers the biggest remaining questions in practice — one shipped slice reduces more uncertainty than another four weeks of analysis, and it produces something the sponsor can see.

How do you assess third-party dependencies?

Three questions per package: does a version targeting modern .NET exist, is the project alive, and how deeply is it woven into our code. dotnet list package --outdated --deprecated --vulnerable --include-transitive gives the mechanical picture, and NuGet's target frameworks tell me whether a net8.0/net10.0 or at minimum a netstandard2.0 asset exists. Packages with a modern target are a version bump; packages with only a Framework target and a live vendor are a support ticket; packages with only a Framework target and a dead vendor are a replacement project, and those are the ones that set the schedule. For the last group I look at how many files reference them — a library used behind one interface is a week, a library whose types appear in 400 files is a quarter, and that difference should show up in the plan rather than in a surprise. I also check licence and support terms at this point, because a modernization is the cheapest moment to exit a dependency you were always going to have to exit.

The estate has no documentation and no tests. Where do you start?

With observability, because it is the only thing that makes every subsequent step safer and it can be added without changing behaviour. Structured logging and distributed tracing at the boundaries, request/response capture on a sample of live traffic, and database query capture give me an empirical description of the system within days. From that capture I build characterization tests — golden-master assertions that encode what the system currently does, bugs included — and I put them in CI so the safety net exists before the first migration commit. In parallel I inventory deployables, scheduled jobs and database consumers, since undocumented consumers are the usual cause of a failed cutover. What I do not do is start by writing unit tests for the legacy code, because unit tests on untestable code require refactoring, refactoring without a net is exactly the risk I am trying to avoid, and the boundary-level tests give a far better coverage-to-effort ratio.

How has AI changed assessment in the last year?

It collapsed assessment and remediation into one loop. GitHub Copilot app modernization went GA for .NET in September 2025 and now runs in Visual Studio 2026, VS Code, the Copilot CLI and on GitHub.com; it inventories the solution, proposes an upgrade plan, applies transformations, fixes the build errors those transformations cause, and can containerize the result — so the output of assessment can now be a pull request rather than a report. That genuinely compresses the mechanical work, particularly retargeting projects, moving packages.config to PackageReference, and replacing well-known API patterns. What it does not change is verification: an agent's diff is only as safe as the tests it has to run against, and on a system with no tests the agent's confidence is indistinguishable from a guess. So the lead-level shift is that less of my time goes into producing the change and more goes into building the evidence that makes a change reviewable — characterization tests, parallel runs and traffic shadowing become the bottleneck and therefore the thing worth investing in first.

03 Migration patterns that work

Docs: Strangler Fig pattern · Anti-corruption Layer · YARP reverse proxy · Branch by Abstraction · Parallel Change (expand–contract)

There are only about five migration patterns, and every real programme is a composition of them. They all solve the same problem from different angles: how do you replace a live component when you are not allowed to have a moment where neither the old nor the new one works? The answer is always the same shape — introduce an indirection, run both sides behind it, shift traffic gradually, then delete the indirection. What differs is where the indirection sits: at the network edge (strangler fig), inside the process (branch by abstraction), at the data contract (expand–contract), or at the model boundary (anti-corruption layer).

Strangler fig: the network-edge indirection

The name is Martin Fowler's, after the Australian fig that germinates in a host tree's canopy, sends roots down around the trunk, and eventually stands as a hollow cylinder where the host used to be. The engineering content is precise: put a façade in front of the legacy system, route one capability at a time to a new implementation behind that same façade, and shrink the legacy system until it can be deleted.

In a .NET estate the façade is almost always YARP (Yet Another Reverse Proxy), which is a library you host in an ASP.NET Core app rather than an appliance — so routing rules live in your config and can be changed per deployment, per header, or per user. Azure Front Door, Application Gateway or nginx work equally well when the routing rules are static; YARP wins when you want route decisions in code, which you will.

// appsettings.json in the YARP facade. Meridian, month 5:
// the customer portal's tracking pages are new, everything else is still Web Forms.
{
  "ReverseProxy": {
    "Routes": {
      "tracking-new": {
        "ClusterId": "modern",
        "Match": { "Path": "/portal/tracking/{**catch-all}" },
        "Order": 1
      },
      "tracking-canary": {                       // 5% of traffic, by header set upstream
        "ClusterId": "modern",
        "Match": { "Path": "/portal/quotes/{**catch-all}", "Headers": [
          { "Name": "X-Canary", "Values": [ "on" ], "Mode": "ExactHeader" } ] },
        "Order": 0                               // lower Order wins - evaluated first
      },
      "everything-else": {
        "ClusterId": "legacy",
        "Match": { "Path": "{**catch-all}" },
        "Order": 100
      }
    },
    "Clusters": {
      "modern": { "Destinations": { "d1": { "Address": "https://meridian-portal.internal/" } },
                  "HealthCheck": { "Active": { "Enabled": true, "Path": "/health/ready" } } },
      "legacy": { "Destinations": { "d1": { "Address": "http://legacy-iis.internal/" } } }
    }
  }
}
// Program.cs - the facade. Note what it is NOT: it holds no business logic.
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddReverseProxy()
       .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"));
builder.Services.AddSingleton<IFeatureGate, ConfigFeatureGate>();

var app = builder.Build();

// Route decisions that need more than config: percentage rollout, per-tenant,
// per-user opt-in. This is why YARP-as-a-library beats an appliance.
app.MapReverseProxy(pipeline =>
{
    pipeline.Use(async (context, next) =>
    {
        var gate = context.RequestServices.GetRequiredService<IFeatureGate>();
        var tenant = context.User.FindFirst("tenant_id")?.Value;
        if (context.Request.Path.StartsWithSegments("/portal/quotes")
            && gate.IsEnabled("quotes.modern", tenant))
        {
            context.Request.Headers["X-Canary"] = "on";   // steers the route above
        }
        await next();
    });
});
app.Run();

The three things that make or break a strangler fig, and the ones interviewers actually probe:

  1. Shared session and auth. Old and new must be one logical application to the user. In practice that means a shared cookie domain, and — for ASP.NET Core reading a .NET Framework forms-auth or OWIN cookie, or vice versa — the Microsoft.Owin.Security.Interop package plus a shared Data Protection key ring stored somewhere both sides can read (a file share, blob storage, or the registry). Get this wrong and every route switch logs the user out.
  2. Shared state. In-process session state is fatal. Move to a distributed cache (Redis / Azure Cache for Redis, or SQL Server session state) before the first route moves, not after.
  3. A deletion plan. Every route you move gets a ticket to delete the legacy handler. A strangler fig that never deletes has produced two systems and doubled your maintenance surface — the single most common way this pattern is done badly.

Branch by abstraction: the in-process indirection

When the seam is inside the process — a data access layer, a pricing engine, a PDF renderer — you cannot route at the edge. Branch by abstraction introduces an interface over the existing implementation, adds the new implementation behind the same interface, and switches with a flag. The essential property is that every intermediate commit is shippable on trunk, which is why this beats a long-lived migration branch that has to be rebased against six months of production fixes.

// Step 2 of 5. Step 1 was extracting IRatingEngine over the legacy implementation.
public sealed class RatingEngineRouter(
    LegacyRatingEngine legacy,
    ModernRatingEngine modern,
    IFeatureGate gate,
    ILogger<RatingEngineRouter> log) : IRatingEngine
{
    public async Task<Rate> RateAsync(Shipment s, CancellationToken ct)
    {
        var authoritative = await legacy.RateAsync(s, ct);

        if (gate.IsEnabled("rating.shadow", s.TenantId))
        {
            // Shadow mode: run the new path, compare, never return it.
            // Failures here must never affect the customer - hence the catch.
            try
            {
                var candidate = await modern.RateAsync(s, ct);
                if (candidate.Total != authoritative.Total)
                {
                    log.LogWarning("rating divergence {Lane} legacy={Legacy} modern={Modern} delta={Delta}",
                        s.Lane, authoritative.Total, candidate.Total, candidate.Total - authoritative.Total);
                }
            }
            catch (Exception ex) { log.LogError(ex, "shadow rating failed for {Lane}", s.Lane); }
        }

        return gate.IsEnabled("rating.modern", s.TenantId)
            ? await modern.RateAsync(s, ct)     // step 4: modern becomes authoritative
            : authoritative;
    }
}

The five steps, which is the answer to "how would you replace a component with no downtime": (1) extract the abstraction over the old implementation and ship it; (2) add the new implementation in shadow mode and measure divergence; (3) drive divergence to zero, or explain every remaining difference as a legacy bug you are deliberately fixing; (4) flip the flag per tenant, then broadly; (5) delete the old implementation, the flag and the router. Step 5 is not optional and it is the step teams skip.

Expand–contract: the contract-level indirection

Also called parallel change. Any breaking change to a shared contract — a database column, an API field, a queue message shape — becomes three deployments instead of one: expand (add the new thing, keep the old, write both), migrate (move readers over, backfill the data), contract (delete the old thing). It is the only technique that lets a database schema change while multiple application versions are live, which is exactly the situation a rolling deployment creates. Anti-corruption layer: the model-level indirection

From Evans' Domain-Driven Design. When the new system talks to the old one, the old model will leak: nullable-everything DTOs, sentinel values like 'X' for "unknown", a Status column with fourteen meanings, dates stored as varchar(8). An ACL is a translation layer at the boundary whose only job is to stop that leaking inwards — it maps the legacy shape onto the model you actually want, and it is the thing you delete last.

// The legacy contract, faithfully typed. Ugly on purpose - this is what IS.
internal sealed record LegacyShipmentRow(
    string SHP_NUM, string STAT_CD, string? CUST_REF,
    string ETA_DT,          // "20260908", or "        ", or "00000000"
    decimal? DECL_VAL, string CURR_CD);

// The anti-corruption layer: the ONLY place these rules exist.
internal static class ShipmentTranslator
{
    public static Shipment ToDomain(LegacyShipmentRow r) => new(
        Number:   ShipmentNumber.Parse(r.SHP_NUM.TrimEnd()),
        Status:   r.STAT_CD switch
        {
            "01" or "1 " => ShipmentStatus.Booked,
            "05"         => ShipmentStatus.InTransit,
            "07"         => ShipmentStatus.Held,        // customs hold, 2019 onward
            "9"  or "09" => ShipmentStatus.Cleared,     // both forms exist in the data
            "X"          => ShipmentStatus.Unknown,     // sentinel, ~0.3% of rows
            _            => throw new UnmappedLegacyValueException(nameof(r.STAT_CD), r.STAT_CD)
        },
        CustomerRef: string.IsNullOrWhiteSpace(r.CUST_REF) ? null : r.CUST_REF.Trim(),
        Eta: DateOnly.TryParseExact(r.ETA_DT, "yyyyMMdd", CultureInfo.InvariantCulture,
                                    DateTimeStyles.None, out var d) ? d : null,
        DeclaredValue: r.DECL_VAL is { } v && !string.IsNullOrWhiteSpace(r.CURR_CD)
            ? new Money(v, Currency.Parse(r.CURR_CD)) : null);
}

Note the throw on an unmapped status. An ACL that silently maps unknown legacy values to a default is worse than no ACL, because it converts a loud data-quality discovery into a quiet wrong answer. Throw, alert, and add the mapping — you will find codes nobody remembered existed, and finding them in a log is far cheaper than finding them in an invoice.

Interview trap

Saying "strangler fig" and stopping there. Interviewers hear the term constantly; it is now table stakes. What distinguishes a lead answer is naming the three hard parts nobody mentions: shared authentication (the Data Protection key ring shared between the ASP.NET Core app and the .NET Framework app, via Microsoft.Owin.Security.Interop, so a route switch does not log the user out); shared session and state (in-process session must move to a distributed store before the first route moves); and the shared database, which is the real reason strangler figs stall — you can move the code in a weekend and still be sharing one 900-table schema three years later. A strangler fig over a shared database is a UI refactor with extra proxies unless the data migration is planned as its own track with its own expand–contract sequence.

Gotcha

Long-lived migration branches. "We'll rewrite on the modernize branch and merge when it's done" collapses under the weight of production fixes that must be applied twice, and the merge is unreviewable. Every pattern in this unit exists specifically so migration work can live on trunk behind a flag: the new implementation is deployed to production, dormant, from week one. If your migration cannot be expressed as commits that are individually safe to deploy, the design is wrong, not the process.

Try it — 90 minutes, two exercises

1. Build a two-line strangler. Create an ASP.NET Core app with YARP, point {**catch-all} at any existing site, and add one route that serves a different response from a local endpoint. Then add a middleware that flips that route on only when a header or claim is present.

2. Shadow a function. Take any pure-ish function you have, wrap it in an interface, add a second implementation, and write a router that calls both, returns the old one and logs divergences with the inputs. Feed it a few thousand rows of real-shaped data.

Expected outcome

Exercise 1 takes about twenty minutes and permanently changes how you answer "how would you migrate incrementally?", because you will have felt that the edge indirection is trivially cheap — and that everything expensive (auth, session, database) lives elsewhere.

Exercise 2 will find divergences you did not expect, and they will cluster: rounding on a half-cent boundary, a culture-dependent parse, a null treated as zero in one implementation and as missing in the other. That clustering is the point — divergence logs give you a defect taxonomy, and each cluster is one fix rather than a thousand mismatches.

Interview Q&A · migration patterns

Explain the strangler fig pattern and how you would implement it on a .NET estate.

You put a façade in front of the legacy application, route one capability at a time to a new implementation behind that façade, and shrink the legacy system until you can delete it. On a .NET estate I would use YARP hosted in an ASP.NET Core app rather than an appliance, because routing decisions then live in code and I can gate them per tenant, per user or by percentage rather than only by path. The mechanical part is easy; the three hard parts are shared authentication, shared session state and the shared database. For auth, the .NET Framework and ASP.NET Core sides need a shared Data Protection key ring and the OWIN interop cookie format so a route switch does not sign the user out. For session, anything in-process has to move to a distributed cache before the first route moves. And the database usually cannot be split at the same time, so I plan it as a separate track with its own expand–contract sequence, otherwise the fig never actually strangles anything.

What is branch by abstraction, and when is it better than a feature branch?

It is the in-process equivalent of a strangler fig: extract an interface over the existing implementation, add the new implementation behind the same interface, switch with a flag, then delete the old one and the flag. It is better than a feature branch essentially always for migration work, because every intermediate state is deployable to production, so the new code is exercised — at least in shadow mode — from week one instead of on merge day. A long-lived branch has to absorb every production fix twice and produces a merge nobody can review, and the risk is concentrated at exactly the moment when you have the least information. The cost of branch by abstraction is that you carry both implementations for a while and the flag creates real branching in production, so I treat flag removal as a scheduled, ticketed step rather than a hope. If a team tells me they have thirty long-lived migration flags, that is the same failure mode as a long-lived branch wearing a different hat.

How do you change a database column that a live application depends on?

Expand–contract, across three deployments. Expand: add the new column as nullable, deploy code that writes both old and new, and leave every reader on the old column — this deployment is trivially reversible. Migrate: backfill in bounded batches so no single transaction takes a long lock, create the index, add any constraint as NOT TRUSTED then validate it, and switch readers to the new column with a fallback to the old. Contract: once no live version reads the old column, drop it. The rule that makes it work is that the schema must be compatible with both the currently deployed application version and the next one at every point, because a rolling deployment means both are live simultaneously. The contract step is the only irreversible one, so I put deliberate distance between migrate and contract — often a full release cycle — and I verify with query capture that nothing still reads the old column before dropping it.

What is an anti-corruption layer and where do you put it?

It is a translation boundary whose only job is to stop the legacy model leaking into the new one. Legacy schemas carry sentinel values, overloaded status codes, dates in varchar, and nullable-everything shapes that encode fifteen years of workarounds; without a deliberate boundary those concepts spread through the new code and you have rebuilt the legacy model with better syntax. I put it at the edge of the new component — as close to the legacy call as possible, with the legacy shape typed faithfully and ugly on one side and the domain model on the other. One rule I insist on: unmapped legacy values throw and alert rather than falling back to a default, because a silent default converts a data-quality discovery into a wrong answer in an invoice. It is also usually the last thing you delete, since it survives until the legacy store itself is gone.

What is a parallel run and when is it worth the cost?

You run old and new implementations on the same live input, treat the old one as authoritative, return its result, and log every divergence. It is worth the cost when behaviour is both critical and not reliably knowable — pricing, tax, billing, rating, regulatory calculations — which is precisely where reading the code is least trustworthy because the behaviour is fifteen years of accumulated exceptions. It costs you double compute on that path, the discipline to make the shadow call non-blocking and failure-isolated so it can never affect the customer, and somewhere to store comparisons at volume. What you get is the ability to make a cutover a non-event: when the divergence rate has been zero for a month across real traffic, flipping the flag is boring. I would also insist on classifying every remaining divergence rather than tolerating a small percentage, because in my experience the residual is where the genuinely interesting legacy bug lives.

How do you keep a user logged in while routes move between a Framework app and an ASP.NET Core app?

Both sides must produce and accept the same authentication cookie, which means three things line up. First the cookie itself: same name, same domain and path, and a cookie domain that covers both hosts. Second the format: ASP.NET Core's cookie authentication and Katana/OWIN cookie middleware use different serializers, so you use Microsoft.Owin.Security.Interop to teach one side the other's format. Third and most often missed, the keys: ASP.NET Core's Data Protection key ring must be shared with the Framework side and persisted somewhere durable — a UNC share, blob storage, or a database — with the same application name, or the two sides simply cannot decrypt each other's tickets. The failure mode when you get this wrong is nasty precisely because it is intermittent: it works until the key ring rotates or a new instance generates its own keys, and then a subset of users is randomly signed out. The alternative, which I would prefer for a longer programme, is to move both sides to token-based auth against Entra ID and stop sharing cookies at all.

When is a big-bang cutover actually the right answer?

When the coexistence cost genuinely exceeds the cutover risk, and that is rarer than people claim but not never. The conditions I look for: the system is small enough that a full rehearsal is affordable, there is a natural business quiet period, the data can be migrated and verified inside the window, and — the decisive one — there is a tested, time-boxed rollback that does not depend on the migration having gone well. Regulated data migrations and some database platform moves fall here, because dual-write to two engines is more dangerous than a short outage. What I would insist on is rehearsing the cutover against a production-sized copy at least twice with the clock running, and defining a go/no-go checkpoint partway through with a named decision maker. A big bang without a rehearsed rollback is not a plan, it is a wager, and the tell is when someone says "we can't roll back, we'll fix forward" before anything has happened.

How do you avoid ending up with two systems forever?

By making deletion a tracked deliverable rather than a hope. Every route moved behind the proxy creates a ticket to delete the legacy handler, every flag has a removal date and an owner, and I report on the shrinking legacy surface — lines of code, endpoints, database objects still referenced — as the primary programme metric rather than on features shipped. It helps enormously to make the legacy side visibly unattractive to extend: freeze it to defect fixes only, require an explicit exception to add anything, and make the modern path the path of least resistance in the templates and the pipeline. The organisational half matters more than the technical half; if the team that owns the legacy system is measured on its uptime and nothing else, nobody is paid to delete it. I would also put a hard stop in the plan: if the last 10% of routes has not moved within a defined window, we escalate that as a decision to be made rather than letting it become the permanent state.

Your strangler fig has stalled at 70%. What is going on and what do you do?

Nearly always one of three causes. The remaining routes are the hard ones — the ones with the deepest database coupling or the least understood behaviour — and the team has been picking the easy wins, so the difficulty curve has caught up. Or the shared database was never split, so the last routes cannot move without a data migration nobody scoped. Or the funding narrative was "modernization" and the visible wins are gone, so attention moved on. My response is to name which one it is publicly, because the responses are different: for the first, invest in the safety net so the hard routes become tractable — parallel runs on the unknown behaviour; for the second, stop route migration entirely and run the data track, because more route moves add coupling without reducing it; for the third, re-cut the plan into outcomes the business cares about and be honest that the remaining 30% carries most of the remaining risk. What I would not do is keep going route by route and hope, because the 70% state has the maintenance cost of two systems and the benefits of neither.

Legacy and new both need to write the same data. How do you handle it?

My strong preference is to avoid dual-write entirely, because two writers to two stores with no shared transaction is a distributed consistency problem that will produce divergence under partial failure, and reconciling it later is far more expensive than it looks. The order of preference is: keep a single writer and let the other side call it; if that is impossible, keep a single source of truth and replicate one way — change data capture, the transactional outbox pattern, or SQL Server 2025's change event streaming — accepting eventual consistency explicitly and designing the UI for it; only then consider dual-write, and if you must, make one store authoritative, write to it first, and treat the second write as a replayable, idempotent projection rather than as a peer. Whatever the choice, I would build the reconciliation job before the first dual write, not after the first incident, because you need to know your divergence rate to have any idea whether the design is holding. And I would put a date on it: dual-write is a transitional state, and transitional states without end dates become architecture.

04 The safety net

Docs: Testing in .NET · ASP.NET Core integration tests · Testcontainers for .NET · Feature flags in Azure App Configuration · OpenTelemetry for .NET

The safety net is what makes everything else in this guide affordable. Without it, every migration step is a bet; with it, every migration step is an experiment you can run and reverse. This is the unit that most distinguishes lead-level answers, because it is where the honest constraint lives: you cannot write good unit tests for legacy code, because legacy code is untestable by construction — and making it testable requires the refactoring you were trying to make safe. That circularity is real, and the way out of it is to test at a level the legacy code cannot resist: the boundary.

Invert the pyramid, deliberately and temporarily

For greenfield code the test pyramid is right: many unit tests, fewer integration tests, a handful of end-to-end. For a legacy migration it is upside down, and that is a correct trade rather than a compromise. What you want is a thick band of characterization tests at the outermost boundary you can reach — HTTP in, HTTP out; message in, message and side effects out — because those are the only tests that survive the code being replaced underneath them. A unit test of a Web Forms code-behind is worthless the day you delete the page; an HTTP-level golden-master test of POST /quotes keeps working across a rewrite, a runtime change and a re-platform.

Characterization tests: assert what is, not what should be

A characterization test encodes current behaviour including its bugs. That is the discipline, and it feels wrong the first time: if the legacy system rounds VAT down on a half-cent, the test asserts rounding down. You are not certifying correctness, you are building a tripwire that fires when the new implementation behaves differently — and then a human decides whether that difference is a fix or a regression. A test suite that asserts what the system ought to do will fail on day one and get switched off.

Approval (golden-master) testing is the cheapest way to write hundreds of these: run the input, serialize the whole output, and diff it against a checked-in snapshot. Verify is the standard .NET library.

// Characterization tests generated from 30 days of captured production traffic.
// Cases live as JSON files; the snapshot is the legacy system's own answer.
public class QuoteCharacterizationTests(LegacyFixture fx) : IClassFixture<LegacyFixture>
{
    public static TheoryData<string> Cases => CaptureCorpus.Load("captures/quotes"); // 4,182 cases

    [Theory, MemberData(nameof(Cases))]
    public async Task Quote_response_is_unchanged(string caseId)
    {
        var request  = CaptureCorpus.Request(caseId);
        var response = await fx.Client.PostAsJsonAsync("/api/quotes", request);
        var body     = await response.Content.ReadFromJsonAsync<JsonNode>();

        await Verify(new { status = (int)response.StatusCode, body })
            .UseDirectory("snapshots/quotes")
            .UseFileName(caseId)
            // Scrub only what is genuinely non-deterministic. Every scrubber is a
            // hole in the net, so each one needs a comment justifying it.
            .ScrubMember("quoteId")          // new GUID per call
            .ScrubMember("generatedAtUtc")   // clock
            .DontScrubDateTimes();           // business dates MUST be compared
    }
}

Two rules that decide whether this works. Scrub as little as possible — every scrubbed field is a place a regression can hide, and the temptation is to scrub whatever is failing. And generate cases from real traffic, not from imagination: capture a representative window (include a month-end and a quarter-end), redact PII, and keep the corpus in the repository or in blob storage next to it. A corpus of four thousand real requests finds things a hundred hand-written cases never will, because production input distributions are far weirder than anyone's intuition.

Legacy .NET systems keep a large share of their behaviour in T-SQL. In-memory providers cannot express it — EF Core's in-memory provider does not enforce constraints, does not translate SQL, and will happily pass tests that fail in production; the EF team's own guidance is to use a real database or at least SQLite. Testcontainers makes a real SQL Server per test class cheap enough to be the default.

Interview trap

Promising to "add unit tests first". It sounds responsible and it is the wrong answer, because legacy code is untestable by construction — static state, new in constructors, HttpContext.Current, database calls in the UI layer — so unit-testing it requires exactly the refactoring the tests were supposed to protect. The lead answer names the circularity and escapes it: start at the outermost boundary the legacy code cannot resist (HTTP, message, batch file), build characterization tests from captured production traffic, and only write unit tests for logic as you extract it through a seam. A related trap is asserting intended rather than actual behaviour: if the legacy system truncates instead of rounding, the characterization test asserts truncation. You are building a tripwire, not a specification — and a suite that fails on day one because it encodes someone's opinion of correctness will be disabled by day three.

Gotcha

Non-determinism silently destroys golden-master suites. GUIDs, DateTime.Now, dictionary ordering, culture-dependent formatting, floating-point accumulation order and parallelism all produce diffs that have nothing to do with your change, and the reflex — scrub the field, or re-approve the snapshot — quietly hollows out the net until it catches nothing. Fix causes rather than symptoms: inject TimeProvider (built into .NET 8+) instead of scrubbing timestamps, seed identifier generation in tests, force CultureInfo.InvariantCulture, sort collections before serializing. Every scrubber that remains should carry a comment explaining why it cannot be fixed, and a bulk re-approval should require the same review scrutiny as a production change.

Try it — 2 hours, two exercises

1. Golden-master an endpoint you did not write. Pick any HTTP endpoint in a codebase you know poorly. Capture 50 real or realistic requests, write one Verify-based theory over them, and commit the snapshots. Then make a deliberately subtle change — swap a decimal for a double in one calculation, or change a rounding mode — and watch which cases fail.

2. Break the net on purpose. Add a DateTime.Now to a response and observe your suite fail everywhere. Now fix it properly with TimeProvider and a fake clock rather than by scrubbing.

Expected outcome

In exercise 1, the decimal-to-double swap typically fails a small, specific subset — the cases with many summed line items or values near a rounding boundary. That is the argument for capturing production traffic rather than writing cases by hand: the failures live in the tail of the input distribution, and nobody imagines the tail.

In exercise 2 you will feel the pull towards scrubbing, because it is one line and it makes the build green. Resisting it once is the habit that keeps a golden-master suite alive for a two-year migration; giving in once is how suites end up with fourteen scrubbers and no ability to detect a regression.

Interview Q&A · the safety net

There are no tests. How do you make changes safely?

I test at the outermost boundary the legacy code cannot resist, because that is the only level that survives the code being replaced. Concretely: capture a representative window of production traffic at the HTTP or message boundary, redact it, and turn it into characterization tests using an approval-testing library so I get hundreds of assertions for the price of one test method. Those tests assert what the system currently does, bugs included, so any behaviour change shows up as a diff a human then classifies as fix or regression. Underneath that I add a real-database integration layer using Testcontainers rather than in-memory fakes, because a large share of legacy behaviour is in T-SQL and a fake provider will pass tests that fail in production. Unit tests come later and only for logic I have actually extracted through a seam — writing them against untouched legacy internals costs enormously and buys almost nothing, since those tests are deleted along with the code they cover.

What is a characterization test and how does it differ from a unit test?

A characterization test documents observed behaviour rather than intended behaviour. You feed the system an input, record whatever comes out, and assert that it keeps coming out — even if it is wrong. A unit test encodes a specification and fails when the code does not meet it; a characterization test encodes reality and fails when reality changes, which during a migration is exactly the signal you want. The practical consequence is that you write them without understanding the code, which is the whole point when nobody understands the code. They also make an excellent discovery tool: when a characterization test fails on a change you believed was behaviour-preserving, you have just learned something about the system that no document contained. The discipline that keeps them useful is refusing to "fix" a failing case by editing the expectation without a decision recorded somewhere.

How do you decide what to scrub in a golden-master test?

As little as possible, and every scrubber has to justify itself in a comment. Genuine non-determinism is a short list: newly generated identifiers, wall-clock timestamps, and anything reflecting machine or process identity. Everything else that looks non-deterministic usually is not — culture-dependent formatting, dictionary or set ordering, and parallel accumulation order are all fixable at the source with invariant culture, explicit sorting, and deterministic iteration. For clocks specifically, .NET 8 shipped TimeProvider, so injecting a fake clock is now first-class and there is no excuse for scrubbing timestamps in new code. The reason I am strict about this is that scrubbing is the failure mode of the whole technique: each scrubber is a blind spot, the pressure to add one always arrives when the build is red and you are in a hurry, and a suite with a dozen scrubbers has quietly stopped protecting anything.

How do you manage feature flags on a long migration?

As a debt account with an owner. Every migration flag is created together with a removal ticket, an owner and a date, and the flag count is a metric I report on alongside progress, because two interacting flags are four code paths and five are thirty-two — nobody tests thirty-two. I keep flags in a system that can be flipped without a deployment, typically Azure App Configuration with Microsoft.FeatureManagement and targeting filters so I can go per-tenant then per-percentage, and I make sure the flag state is emitted on the telemetry span so an incident can be correlated with what was on. I also distinguish release toggles, which are short-lived and must die, from operational toggles like a kill switch, which are permanent and legitimately live in configuration forever. The failure mode I am guarding against is a codebase where nobody can reason about production behaviour because the combination of flags in effect is unknown, and that arrives sooner than people expect.

Should you use EF Core's in-memory provider for tests?

No, and the EF team says so themselves. The in-memory provider does not enforce referential integrity or unique constraints, does not translate LINQ to SQL so it silently accepts queries the real provider cannot translate, and has different null and ordering semantics — so it passes tests that fail in production and fails to catch the class of bug you most need to catch during a migration. If the goal is a fast, isolated database for logic tests, SQLite in-memory is a better compromise because it is a real relational engine, though it still differs from SQL Server on types, collations and date handling. For anything that touches SQL Server-specific behaviour — stored procedures, computed columns, temporal tables, collation-sensitive comparison, JSON or vector types in SQL Server 2025 — I run a real SQL Server via Testcontainers, applying exactly the schema artifact production uses. It is slower per test class and it is the only version of the test that is actually evidence.

How do you compare old and new implementations on live traffic?

Shadow mode behind a seam: the router calls the legacy implementation and returns its result, and when a flag is on it also calls the new one, compares the results and logs the divergence with enough input context to reproduce it. Three rules make it safe. The shadow call must be failure-isolated — wrapped so that an exception or timeout in the new path can never affect the response — and it must be bounded, so it cannot consume the request's own budget. Side effects must be suppressed or redirected: the shadow path writes to a separate store, sends no emails, charges no cards, and this is the part that bites people. And divergences must be classified rather than counted, because the useful output is a taxonomy — rounding, null handling, culture, a genuine legacy bug — where each cluster is one fix. I would run it for at least a full business cycle including a month-end before treating a zero divergence rate as meaningful.

What observability do you put in place before starting?

Enough to answer "is the new path behaving like the old one" quantitatively, and it has to exist before the first migration commit because otherwise there is no before. That means OpenTelemetry tracing across the proxy, the legacy app and the new app with a single trace id propagated through all three — modern .NET propagates W3C traceparent by default and there is instrumentation for .NET Framework so the legacy side can participate. Then RED metrics per endpoint split by which implementation served it, so I can compare latency percentiles and error rates for exactly the same route across old and new. Then business-level metrics — quotes issued, shipments cleared, invoices raised per hour — because those are the ones that catch a silent correctness failure that no technical metric shows. And structured logs with the tenant, the trace id and the flag state, since correlating an incident to a rollout is the single most common question during a migration.

What is an architectural fitness function and would you actually use one?

Yes, and they are cheap enough that not using them is hard to defend. A fitness function is an automated test of a structural property rather than a behavioural one: the domain project must not reference the legacy contracts namespace, no project may target net48 after a given date, no controller may call DbContext directly, the allowlist of remaining Framework projects must only shrink. In .NET you can write them with NetArchTest, a Roslyn analyzer, or plain reflection over assembly references in an xUnit test — the mechanism matters far less than having them run in CI. What they buy on a long migration is protection against drift, because the pressure during a two-year programme is always to take the shortcut "just this once" at 4pm on a Friday, and a failing build is the only reviewer that is awake. I especially like the shrinking-allowlist form, because it makes progress a build-enforced ratchet rather than a status report.

How much test coverage is enough before you start migrating?

Coverage percentage is the wrong instrument, because a legacy codebase can have 70% line coverage of code you are about to delete. I ask a different question: for each capability I intend to move in the next quarter, can I detect a behaviour change automatically? If yes, that capability is ready; if no, building that detection is the first task of that slice. That makes the safety net incremental and just-in-time rather than a six-month prelude, which matters politically because a programme that spends two quarters writing tests with nothing shipped loses its sponsor. I do insist on two things being in place globally before the first move: end-to-end telemetry so we can compare, and a smoke suite over the handful of journeys that must never break — login, quote, book, invoice. Everything else is bought slice by slice, paid for by the slice that needs it.

How do you test a migration that changes the database schema?

Three layers. First, the migration script itself is tested by running it against a restored, production-sized copy — timing it, watching the locks it takes, and verifying the rollback path — because a script that works on a 500-row developer database and blocks for forty minutes on four terabytes has not been tested. Second, application compatibility is tested at both ends of the expand–contract sequence: the currently deployed version must pass its full suite against the new schema, and the new version must pass against the pre-migration schema, since a rolling deployment has both live at once. Third, data correctness is verified by reconciliation rather than by inspection: row counts, checksums per partition, and business aggregates like total declared value per day compared before and after. I run the whole thing in a rehearsal environment created from a recent restore, at least twice, with the clock running, because the number that matters at the go/no-go meeting is how long it took the last time somebody actually did it.

Interview trap

Treating the port as "it compiles, ship it". The dangerous changes are the ones that compile cleanly and return different answers: ICU replacing NLS changes string comparison and sort order, so a persisted sort, a binary-searched lookup or a StartsWith-based routing rule can silently change; UTF-8 default encoding corrupts fixed-format export files; Linux case sensitivity turns a working template path into a 500 in the container only; and the disappearance of ASP.NET's SynchronizationContext means old sync-over-async code stops deadlocking, which looks like a fix and is actually a thread-pool starvation bug that now waits for load to reveal itself. Gotcha

BinaryFormatter is not merely obsolete — it was removed from .NET in version 9 and throws at runtime even when the compatibility switch is set. If your legacy system persists BinaryFormatter blobs in a database column, a session store or a cache, the port is not a code change but a data migration: you need the old runtime alive long enough to read every blob, convert it to a portable format, and write it back. Discover this during assessment. Discovering it during cutover means either an unplanned dual-runtime period or a lost session store, and it is a common cause of a rollback.

Try it — 2 hours, two exercises

1. Port something small, end to end. Take a .NET Framework class library with packages.config. Convert it to SDK-style targeting net48 only, commit. Then multi-target net48;net10.0 and fix what breaks, commit. Notice how much of the difficulty is package targets rather than your code.

2. Reproduce the ICU break. Write a program that sorts a list containing hyphenated and apostrophised strings ("co-op", "coop", "O'Brien", "OBrien") with StringComparison.CurrentCulture, run it on modern .NET, then set System.Globalization.UseNls to true on Windows and run it again.

Expected outcome

Exercise 1: the majority of your fixes will be dependencies without a modern target, not your own code. That ratio is the honest estimate for a real port and the reason unit 02 spends so much time on the dependency inventory.

Exercise 2: the orderings differ. Now imagine that ordering was used to build a paged list with a keyset cursor, or to decide equality in a de-duplication job. This is the concrete story to tell when an interviewer asks what surprised you — it compiles, it runs, it is wrong, and no scanner will tell you.

Interview Q&A · runtime migration

Walk me through porting a .NET Framework application to .NET 10.

Four phases, each shippable. First, inventory and dependencies: run AppCAT and the Upgrade Assistant in analyse mode, and classify every NuGet package as has-a-modern-target, needs-an-upgrade, or needs-replacing — that last group sets the schedule. Second, prepare without changing behaviour: convert projects to SDK-style and packages.config to PackageReference while still targeting net48, and deploy that; it is a no-op release that makes the retarget a one-line diff. Third, work bottom-up through the dependency graph, multi-targeting shared libraries as net48;net10.0 so the same assembly serves the old host and the new one during coexistence. Fourth, move the host itself, which for a web application is the real project and belongs in its own plan. Throughout, I keep the characterization suite green, and I budget explicitly for the silent behaviour changes — globalization, encoding, case sensitivity, time zones — because the compiler will not find them.

What in .NET Framework simply has no path forward?

Web Forms is the headline: it depends on System.Web, the page lifecycle and ViewState, and it was never ported, so it is a rebuild rather than a port. WCF server-side hosting is not in the box, though CoreWCF under the .NET Foundation gives you a compatible server if you need to preserve the contract for callers you do not control; WCF clients are supported through the System.ServiceModel packages, which trips people up because the two halves have very different stories. .NET Remoting and AppDomains are gone, so cross-domain isolation becomes separate processes or AssemblyLoadContext. Workflow Foundation was not ported, leaving CoreWF, Durable Functions or an explicit state machine. And BinaryFormatter was removed outright in .NET 9, which is a data-migration problem rather than a code problem if you persisted anything with it. System.Drawing.Common is a subtler one: it still exists but is Windows-only from .NET 6, so a Linux container needs ImageSharp or SkiaSharp.

What is the role of .NET Standard 2.0 today?

It is a coexistence bridge, not a destination. During the period where a legacy .NET Framework host and a new modern .NET host both need to load the same business logic, a library targeting netstandard2.0 loads into both — which lets you extract logic out of Web Forms code-behind and WCF services and start unit-testing it long before the host moves. Once nothing on .NET Framework consumes a library any more, I retarget it to net10.0 and get the newer APIs, span-based overloads, nullable annotations and performance work that .NET Standard denies you. In practice I prefer multi-targeting net48;net10.0 over netstandard2.0 when I control both consumers, because it lets each target use its best APIs with a small amount of #if, rather than reducing both to a 2018-era surface area. What I would not do is start a new library at netstandard2.0 in 2026 unless it genuinely has a Framework consumer.

What is the globalization change and why does it matter?

From .NET 5, modern .NET uses ICU for globalization on every platform, where .NET Framework used Windows NLS. That changes culture-sensitive string comparison, sorting and casing — the textbook example is that NLS treated certain punctuation as ignorable, so "co-op" and "coop" compared equal under the current culture while ICU says they differ. It matters because legacy .NET code defaults to culture-sensitive comparison almost everywhere, since string.Compare and StartsWith(string) use the current culture unless told otherwise, so a port can silently change sort order, equality checks, deduplication and any lookup built on a sorted structure. The fix is to make the intent explicit: ordinal for identifiers, paths, protocol strings and anything persisted or indexed, culture-sensitive only for text a human reads. There is a compatibility switch to fall back to NLS on Windows, and I would use it only as a dated, tracked stopgap, because it does not exist on Linux and will strand you the moment you containerize.

How do you handle configuration when moving off web.config?

I replace it rather than shim it, because the shim keeps the string-keyed, untyped access pattern that makes configuration errors runtime failures. The target is IConfiguration with layered providers — appsettings, environment-specific files, environment variables, and Azure App Configuration — bound into strongly typed options classes registered with IOptions, plus validation at startup with ValidateOnStart so a missing or malformed setting fails the deployment rather than the first request that needs it. Secrets leave configuration entirely: Key Vault referenced through App Configuration, accessed with managed identity, so nothing sensitive is in a file or a pipeline variable. During coexistence I keep a single source of truth — usually App Configuration — and have the legacy Framework app read from it too, because two divergent configuration stores during a strangler migration is a reliable source of incidents where old and new disagree about, say, a VAT rate. And I bring feature flags into the same store, since they are configuration with a rollout policy attached.

Your ported service works on Windows and fails in a Linux container. What do you check?

Five things, in order of how often they are the cause. Path case sensitivity — templates, content files and embedded resource names that worked case-insensitively on Windows; this is by far the most common, and it appears only in the container. Path separators and any hard-coded backslash or rooted Windows path. Time zone identifiers, because Windows IDs like "W. Europe Standard Time" and IANA IDs like "Europe/Vienna" are different vocabularies, and if the container has no tzdata installed everything silently falls back to UTC. Windows-only APIs — the registry, WMI, Windows authentication, System.Drawing.Common, performance counters — which throw PlatformNotSupportedException at runtime rather than at build. And file permissions and the non-root user, since containers commonly run as a non-root identity that cannot write where the code assumes. I would also check that the culture data package is present, because a minimal or invariant-globalization base image changes formatting and comparison behaviour in ways that look like application bugs.

What happens to sync-over-async code when you move to ASP.NET Core?

It stops deadlocking, which is the trap. Classic ASP.NET installed a SynchronizationContext that marshalled continuations back to the request context, so .Result or .Wait() on an async call could deadlock with a single request. ASP.NET Core has no SynchronizationContext, so that specific deadlock disappears and the code appears fixed. It is not: every blocking call still occupies a thread-pool thread while waiting, so under load you get thread-pool starvation, which manifests as latency that grows non-linearly with concurrency and as request timeouts that look like a downstream problem. Because it only appears at load, it usually reaches production. So I treat the disappearance of the deadlock as a reason to prioritise the async cleanup, not to defer it, and I would drive it with a load test and thread-pool queue-length metrics rather than with a code review. The related detail worth mentioning is that ConfigureAwait(false), which was mandatory hygiene in library code on Framework, is a no-op in an ASP.NET Core app — still correct in libraries, no longer load-bearing in the host.

How do you migrate a WCF service?

It depends entirely on who the callers are, and that is the first question I ask. If I control every client, the best outcome is deleting WCF: expose the same operations as HTTP APIs or gRPC and migrate clients one at a time behind the proxy, which is a strangler fig at the service layer. If I do not control the clients — a customs authority, a partner integration, a fleet of devices — then CoreWCF is the answer: it is a .NET Foundation project that hosts WCF service contracts on ASP.NET Core, so the SOAP contract and the WSDL stay stable while the host modernizes underneath. The caveats worth naming are binding support, since CoreWCF covers the common HTTP and NetTcp bindings but not every exotic one, and WS-* security and transaction flow, which is where MSDTC-based distributed transactions become a genuine blocker rather than an inconvenience. Client-side WCF is comparatively easy: the System.ServiceModel client packages are supported on modern .NET, so calling a legacy SOAP service from new code is a package reference and a generated proxy.

Would you use Native AOT in a modernized .NET application?

Selectively, and rarely as part of the migration itself. Native AOT gives near-instant startup and a much smaller memory footprint, which is genuinely valuable for functions, CLI tools, sidecars and services that scale to zero or scale out aggressively. The costs are real: no runtime code generation, so reflection-heavy libraries, dynamic proxies and some serializers do not work; you need source-generated JSON and, for data access, EF Core 10's AOT-compatible path — EF Core 10 added Native AOT support with compiled models, which is new and worth knowing about. For a system coming off .NET Framework, that library ecosystem constraint usually rules it out for the main application, because legacy code leans on reflection heavily. So my answer is that AOT is a later optimisation for specific services, not a migration goal, and I would deliberately not put it on the critical path of a port — you would be debugging trimming warnings during the highest-risk phase of the programme.

How do you keep a large solution buildable while half of it is ported?

Multi-targeting plus strict dependency direction. Shared libraries target net48;net10.0 so a single project serves both hosts, with a small amount of #if for the genuinely divergent bits; I keep that conditional code isolated behind an interface rather than sprinkled through business logic. I enforce direction with fitness functions in CI: modern projects may not reference Framework-only projects, and the allowlist of remaining net48 projects may only shrink, which turns progress into a build-enforced ratchet. Central package management with Directory.Packages.props keeps versions consistent so the two graphs cannot drift, and warnings-as-errors keeps compatibility warnings from accumulating into background noise. Practically, I also work bottom-up — leaf libraries first, hosts last — because a leaf can be ported and shipped without coordination, whereas porting a host first forces everything underneath it to move at once, which is precisely the big bang I am trying to avoid.

The web tier is where modernization stops being a refactor and becomes an operational problem, because the user must not notice. Old pages and new pages have to live on one hostname, one session, one login, for months. Microsoft's supported answer to this is the incremental ASP.NET migration toolkit — the Microsoft.AspNetCore.SystemWebAdapters packages — and being able to describe it precisely is a strong differentiator, because most candidates only know "put a proxy in front".

The architecture: new app in front, old app behind

The counter-intuitive part, and the reason the toolkit exists: the new ASP.NET Core app is the front door, not the legacy app. It hosts YARP, serves the routes it has already implemented, and proxies everything else back to the legacy IIS application. That ordering is what makes each migrated route a config change instead of a deployment dance, and it means the new app owns the request from day one — headers, TLS, logging, tracing, rate limiting — while still serving 100% legacy content.

System.Web adapters: making Framework code compile on modern .NET

The adapters supply System.Web.HttpContext, HttpRequest, HttpResponse, HttpContext.Current and friends on top of ASP.NET Core's own HttpContext. That means a class library full of HttpContext.Current.Session["cart"] can be multi-targeted and used from both hosts without being rewritten first — you get to move the code before you get to fix it, which is the correct order when the alternative is a stalled migration.

// New ASP.NET Core 10 app - Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddSystemWebAdapters()
    .AddJsonSessionSerializer(o =>
    {
        // Every session key crossing the boundary must be declared and serializable.
        o.RegisterKey<string>("user-locale");
        o.RegisterKey<ShoppingCart>("cart");        // must be [Serializable]-free, JSON-able
    })
    // Pull session and identity from the legacy app over an authenticated channel.
    .AddRemoteAppClient(o =>
    {
        o.RemoteAppUrl = new Uri(builder.Configuration["Legacy:Url"]!);
        o.ApiKey       = builder.Configuration["Legacy:ApiKey"]!;   // from Key Vault
    })
    .AddAuthenticationClient(isDefaultScheme: true)   // legacy forms auth = our identity
    .AddSessionClient();

builder.Services.AddReverseProxy()
       .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"));

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.UseSystemWebAdapters();

app.MapRazorPages().RequireSystemWebAdapterSession();   // opt in per endpoint
app.MapReverseProxy();                                  // fallback: everything else
app.Run();
// Legacy .NET Framework 4.8 app - Global.asax.cs. Three lines, no restructuring.
protected void Application_Start()
{
    SystemWebAdapterConfiguration.AddSystemWebAdapters(this)
        .AddProxySupport(o => o.UseForwardedHeaders = true)   // so Request.Url is right
        .AddJsonSessionSerializer(o => { o.RegisterKey<string>("user-locale");
                                         o.RegisterKey<ShoppingCart>("cart"); })
        .AddRemoteAppServer(o => o.ApiKey = ConfigurationManager.AppSettings["RemoteAppApiKey"])
        .AddAuthenticationServer()
        .AddSessionServer();
}

Two costs to name, because interviewers ask: remote session is a network round trip per request that touches session, and ASP.NET session is exclusive-locked, so a page holding a writeable session lock serializes concurrent requests from that user. The adapters give you SessionAttribute(IsReadOnly = true) for read-only endpoints, and the strategic answer is to shrink session usage as part of the migration rather than to make the shim faster.

Web Forms: the honest plan

There is no port, so the question is only how you slice the rebuild. The sequence that works on Meridian's 600 pages:

  1. Measure. 30 days of page-hit telemetry. 180 pages carry 95% of sessions; 90 pages have zero hits. The zero-hit pages are a retire list, not a rebuild list — and that conversation is only winnable with data.
  2. Extract logic out of code-behind into net48;net10.0 libraries with tests. This is a Framework-side refactor, ships to the legacy app, and is the largest single de-risking step. Nothing about the UI changes.
  3. Rebuild by page group, not by page — a whole workflow (quote → book → confirm) at a time, so a user never bounces between old and new inside one task. Bouncing mid-workflow is what generates the "the new system is broken" perception even when it works.
  4. Route the group at the proxy, canary by tenant, then delete the .aspx files and their code-behind in the same sprint.

On the target: Razor Pages is the closest mental model to Web Forms (page-centric, a file per screen, a model class beside it) and is the low-friction default for a team of Web Forms developers. Blazor Server is attractive because the stateful component model resembles server controls and keeps C# skills relevant, but it trades an HTTP request model for a persistent WebSocket circuit — which changes your scaling, reconnection and load-balancer story, and is a decision to argue for explicitly rather than to slip in.

Shared authentication, precisely

The mechanism that has to work before any route moves. Three things must align: cookie name and domain, ticket format, and keys.

// ASP.NET Core side: same cookie, same protection keys, same application name.
builder.Services.AddDataProtection()
    .PersistKeysToAzureBlobStorage(new Uri(cfg["DataProtection:BlobUri"]!), new DefaultAzureCredential())
    .ProtectKeysWithAzureKeyVault(new Uri(cfg["DataProtection:KeyUri"]!), new DefaultAzureCredential())
    .SetApplicationName("Meridian");          // MUST match the legacy app's name

builder.Services.AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(o =>
    {
        o.Cookie.Name   = ".AspNet.SharedCookie";
        o.Cookie.Domain = ".meridian.example";
        // Katana/OWIN and ASP.NET Core serialize tickets differently: interop bridges it.
        o.TicketDataFormat = new AspNetTicketDataFormat(
            new DataProtectorShim(DataProtectionProvider
                .Create(new DirectoryInfo(cfg["DataProtection:KeyPath"]!))
                .CreateProtector("Microsoft.AspNetCore.Authentication.Cookies."
                                 + "CookieAuthenticationMiddleware",
                                 "Cookies", "v2")));
    });

If the programme is long, the better answer is to stop sharing cookies at all: move both applications to OIDC against Microsoft Entra ID, so identity is a token issued by a third party and neither app has to understand the other's crypto. That is more work up front and removes an entire class of intermittent, key-rotation-triggered logout incidents.

Interview trap

Forgetting that the reverse proxy changes what the legacy app sees. Behind a proxy, Request.Url, Request.IsSecureConnection and Request.UserHostAddress report the proxy, not the client — so absolute URLs generated by the legacy app point at the internal host, redirect loops appear when the app decides it must upgrade to HTTPS, and every IP-based rule (rate limiting, geo-blocking, audit logging) records the proxy's address. The fix is forwarded headers handled correctly on both sides: UseForwardedHeaders with a restricted list of known proxies on the ASP.NET Core side, and AddProxySupport from the System.Web adapters on the Framework side. A second, subtler version of the same trap: WebSockets, Server-Sent Events, long-polling SignalR and large file uploads all need explicit proxy configuration for timeouts and buffering, and they fail only under real usage — which is why the first strangler slice should deliberately include one of them.

Gotcha

ASP.NET session state is exclusively locked per session: two concurrent requests from the same user serialize, and with remote session over the adapters you have added a network hop to that lock. A page that opens three parallel AJAX calls behind a writeable session becomes three sequential calls plus three round trips. Mark read-only endpoints as read-only, and treat "how much of this actually needs session?" as a migration task in its own right — most legacy session usage turns out to be a cache that would be better as a claim on the identity, a query parameter, or a row in the database.

Expected outcome

Exercise 2 produces either a redirect loop or a link to the internal hostname, which is precisely the failure that turns up at 9am on the first day of a canary. Having seen it makes "what breaks when you put a proxy in front of a legacy app?" a story instead of a list.

Interview Q&A · web tier

How do you migrate an ASP.NET application to ASP.NET Core incrementally?

I put the new ASP.NET Core app in front as the entry point, with YARP proxying everything not yet migrated back to the legacy IIS application, and I use Microsoft's System.Web adapters so identity and session flow across the boundary. The adapters give the new app a System.Web.HttpContext shim, which means Framework-era class libraries can be multi-targeted and consumed by the new host without being rewritten first — that lets me move code before fixing it, which is the right order. Session and authentication cross the boundary via the remote app feature, where the new app calls back into the legacy app over an API-key-authenticated channel to fetch the session and the user. Then I migrate route by route, and crucially delete the legacy handler in the same sprint the route moves. The reason the new app goes in front rather than behind is that it makes each migration a routing config change and lets the modern host own cross-cutting concerns — TLS, tracing, rate limiting — from day one.

What are the System.Web adapters and what do they cost?

They are the Microsoft.AspNetCore.SystemWebAdapters packages, which implement System.Web.HttpContext and its object model on top of ASP.NET Core's HttpContext, plus a remote-app channel that shares session and authentication between a .NET Framework app and an ASP.NET Core app. The benefit is that you can move library code and even some page logic across without first purging HttpContext.Current. The costs are real and worth naming: session keys must be explicitly registered and JSON-serializable, so anything storing arbitrary object graphs in session needs work; each request that touches remote session makes a network round trip to the legacy app; and ASP.NET's session lock is exclusive, so concurrent requests from one user serialize across that hop. I treat them explicitly as scaffolding with a removal plan rather than as an architecture, and I use the migration as the occasion to shrink session usage, because most of what is in session is not really session state.

How do you migrate ASP.NET Web Forms?

You do not migrate it, you rebuild it, because Web Forms depends on System.Web, ViewState and the page lifecycle and was never ported to modern .NET. The plan I would run has four steps. Measure usage first, because in every large Web Forms application a minority of pages carry the overwhelming majority of sessions and a meaningful tail has effectively zero traffic — that converts part of the rebuild into a retirement, and it is only winnable with numbers. Then extract logic out of code-behind into libraries targeting both frameworks, with tests; that ships to the legacy app, changes nothing visible, and is the largest de-risking step. Then rebuild by workflow rather than by page, so a user never bounces between old and new inside a single task. Then route the group at the proxy, canary it, and delete the .aspx files in the same sprint. On the target, Razor Pages is the closest model and the lowest-friction choice for a Web Forms team; Blazor Server is defensible but trades the request model for a persistent circuit, which changes scaling and reconnection, so it needs an explicit argument.

How do old and new applications share a logged-in user?

Three things have to line up, and missing any one produces intermittent logouts. The cookie itself — same name, same domain, path covering both — so the browser sends it to whichever app serves the request. The ticket format, because OWIN/Katana cookie middleware and ASP.NET Core cookie authentication serialize tickets differently; Microsoft.Owin.Security.Interop bridges that. And the keys: ASP.NET Core's Data Protection key ring must be persisted somewhere both apps can read, protected consistently, with the same application name set on both sides — otherwise it works until keys rotate or a new instance generates its own, and then a random subset of users is signed out, which is a miserable bug to diagnose. For anything longer than a few months I would rather move both applications to OIDC against Entra ID so identity is a token from a third party and neither app needs to understand the other's cryptography. The System.Web adapters' remote authentication is a third option, and it is the pragmatic one when the legacy app must remain the source of identity.

What breaks when you put a reverse proxy in front of a legacy web app?

The app's view of the request changes. Scheme, host and client IP now describe the proxy, so absolute URLs the app generates point at the internal host, HTTPS-required redirects can loop because the app sees HTTP on the inside, and every IP-based rule — rate limits, geo-blocks, audit logs — records the proxy address. The fix is forwarded headers processed on both sides, restricted to known proxies so the headers cannot be spoofed by clients. Beyond that, the things that break under real usage rather than in a smoke test: WebSockets and SignalR need explicit upgrade support and generous idle timeouts, large uploads and downloads need buffering and body-size limits configured, client certificates need forwarding if the app uses them, and sticky sessions may be required if the legacy app still holds in-process state. I make a point of putting one long-lived connection and one large upload into the first strangler slice, because those are the failures that otherwise wait until the canary widens.

Razor Pages, MVC, or Blazor for a rebuilt Web Forms screen?

Razor Pages by default, for a page-centric application built by a Web Forms team: one file per screen with a model class beside it maps almost directly onto the .aspx/code-behind mental model, and the handlers map onto postbacks, so the team's intuitions transfer. MVC when the screens are genuinely resource-oriented and shared across many views, or when the team already thinks in controllers. Blazor when interactivity is high and you want to keep the logic in C# — Blazor Server is seductive for a Web Forms shop because the stateful component model resembles server controls, but it replaces the stateless request model with a persistent circuit, which changes load balancing, reconnection behaviour, memory per user and how a deployment interrupts users. Blazor WebAssembly or the .NET 8+ auto render modes are a different trade again, moving you toward a client-side app with the payload and API design that implies. My rule is that the rendering model should be chosen per workflow rather than for the whole application, and that whichever we choose, the business logic sits in libraries that none of these frameworks touch — so the choice is reversible.

What do you do with a WCF service that a customs authority calls?

Keep the contract and change the host, which means CoreWCF. It is a .NET Foundation project that hosts WCF service contracts on ASP.NET Core, so the SOAP endpoint, the WSDL and the message shapes stay stable for a caller I cannot ask to change, while the runtime underneath moves to modern .NET. I would verify binding support early, because CoreWCF covers the common HTTP and NetTcp bindings well but not every exotic configuration, and I would look hard at WS-* security and any transaction flow, since MSDTC-style distributed transactions are the genuine blocker rather than the plumbing. I would also treat the WSDL as a contract under test: generate a client from the old service and the new one and compare, and run the real caller against the new endpoint in a parallel environment before cutting over. And I would use the opportunity to put a proper anti-corruption layer behind the SOAP surface, so the external contract's shape stops dictating the internal model — the external ugliness stays external.

How do you handle session state during a web-tier migration?

First, get it out of process, before any route moves: in-process session makes the legacy app impossible to scale, impossible to deploy without disrupting users, and impossible to share. SQL Server session state or a Redis-backed store both work on .NET Framework, and that change alone is worth shipping on its own. Second, share it deliberately rather than accidentally — the System.Web adapters' remote session feature is the supported route, with keys explicitly registered and JSON-serializable, and I keep the shared surface as small as possible because every key crossing the boundary is coupling. Third, and most valuable, shrink it: I audit what is actually in session and find that most of it is either derivable from the identity, better as a query parameter, or genuinely persistent data that belongs in the database. The strategic point is that session state is the main thing preventing the two applications from being independent, so reducing it is not cleanup, it is the migration.

How do you migrate bundling and minification from System.Web.Optimization?

It does not come across, and I would not look for an equivalent — the replacement is a real front-end build. In practice that means Vite (or esbuild/Rollup) producing hashed asset bundles, with the ASP.NET Core app referencing them through a manifest so cache-busting is content-based rather than query-string based. Modern .NET also gives you static asset fingerprinting and compression in the framework itself, which covers simpler cases without a bundler. The migration is usually staged: keep the legacy bundles serving the legacy pages, add a Vite build for the new pages, and let the two coexist behind the proxy rather than trying to unify the asset pipeline on day one. The trap is the shared global CSS and jQuery plugin soup that both sides depend on, which is unit 09's problem — trying to solve the asset pipeline and the framework migration in the same change is how the front-end work stalls.

How do you decide the order in which routes move?

By risk-adjusted learning value, and I want the first slice to be end-to-end rather than important. The first route should traverse every layer — browser, proxy, new app, database, deployment pipeline, telemetry — so it proves the mechanism, and it should be something with real but recoverable traffic, like a read-only lookup or a tracking page on the revenue path. After that I sequence by coupling rather than by value: routes that share session state or database tables with unmigrated routes are expensive, so I look for workflows that can move as a whole. I also deliberately front-load one route with an awkward technical property — a file upload, a long-lived connection, an integration with client certificates — because those reveal proxy and hosting problems while the blast radius is still small. What I avoid is starting with the crown jewels, since the team's first attempt at the new architecture is its worst, and avoiding the noisiest screens early, since the migration will be judged on perception as much as on metrics.

EF Core is not EF6 with a new version number; it is a different ORM with a familiar API surface, and that mismatch is exactly where migrations go wrong. Code that compiles after a mechanical port can throw at runtime, silently issue different SQL, or — the expensive one — work correctly in development and fall over at production data volumes. The mental model to carry: EF6 was permissive and would quietly do the wrong thing in memory; EF Core is strict and would rather fail loudly. Almost every difference below is an instance of that.

The hard prerequisite, worth saying first because it drives sequencing: EF Core does not run on .NET Framework in any version you would choose today, so the data-access migration is downstream of unit 05. During coexistence, EF6 and EF Core can run side by side in the same modern .NET process against the same database — different DbContext types, separate connections — which is how you strangle a data layer without a big-bang switch.

The strangler pattern for a data layer

You do not convert 900 tables at once. EF6 and EF Core coexist in one process, so you migrate by aggregate: pick a bounded set of tables with a clear owner, build an EF Core context for just those, route the repositories that touch them, and leave the rest on EF6. The two contexts share a database and can share a transaction if they share a connection.

// Coexistence: one connection, one transaction, two ORMs. Ugly, temporary, works.
await using var conn = new SqlConnection(cs);
await conn.OpenAsync(ct);
await using var tx = await conn.BeginTransactionAsync(ct);

// EF Core context enlisted on the shared connection
await using var modern = new ShipmentContext(
    new DbContextOptionsBuilder<ShipmentContext>().UseSqlServer(conn).Options);
await modern.Database.UseTransactionAsync(tx as DbTransaction, ct);

// EF6 context on the same connection + transaction
using var legacy = new MeridianEntities(conn, contextOwnsConnection: false);
legacy.Database.UseTransaction(tx as DbTransaction);

await modern.SaveChangesAsync(ct);
legacy.SaveChanges();
await tx.CommitAsync(ct);

And the honest option interviewers respect: not every query belongs in an ORM. Reporting queries, bulk loads and the twenty hot paths that carry 80% of your database load are often better as Dapper over hand-written SQL, or as a call to a stored procedure you keep. EF Core for the aggregate write model, Dapper for the read model, is a completely defensible modernized shape and avoids a common failure: rewriting a tuned 200-line query as LINQ, producing worse SQL, and blaming EF Core.

What EF Core 10 adds

Shipped with .NET 10 on 11 November 2025. Interview trap

"EF Core is faster, so the port will improve performance." It usually does per-query, and it routinely makes the application slower after a mechanical port, for three reasons candidates rarely name. First, EF6's silent client evaluation was hiding queries that were always terrible; when EF Core refuses them, people "fix" them by calling .ToList() earlier — which keeps the table scan and adds materialization. Second, lazy loading is off by default, and the reflex fix is to enable proxies, which reproduces the N+1 pattern rather than removing it. Third, multiple Includes produce cartesian explosions that a 500-row dev database never shows and a production tenant does immediately. The answer that lands: "I port with query logging on and a performance test against production-shaped data, I review the generated SQL for the top twenty queries by volume, and I expect to rewrite some of them as projections, split queries or Dapper rather than to get a free win."

Gotcha

System.Data.SqlClient is legacy and receives no new features; the supported driver is Microsoft.Data.SqlClient. Switching is usually a namespace change plus one very sharp edge: from version 4.0 the default is Encrypt=true, so a connection to a SQL Server with a self-signed or internal-CA certificate fails with a certificate-chain error that reads like a network fault. The correct fix is to give the server a trusted certificate; the expedient one is TrustServerCertificate=true, which is a documented, dated exception, not a default. This breaks on-premises SQL Server connections far more often than Azure SQL ones, so it typically appears in the least-tested environment.

Try it — 2 hours, two exercises

1. Make client evaluation bite. Build a small EF Core model with 100,000 rows and write a Where that calls a local C# method. Observe the exception. Then rewrite it three ways — translatable predicate, server-narrowed then client-filtered, and a mapped SQL function — and compare the generated SQL and timings.

2. Explode the cartesian product. Take a parent with two collection navigations and Include both. Log the SQL and count the rows returned versus the rows you needed. Then add AsSplitQuery() and compare.

Expected outcome

Exercise 1: the server-narrowed version is usually within a few percent of the fully translated one and far more readable, which is the practical answer for most business rules. The mapped-function version wins only when the predicate is genuinely selective in the database — and that nuance is a much better interview answer than "always translate everything".

Exercise 2: the row-count ratio is typically one to two orders of magnitude. Once you have seen the number, "why is the new version slower than the old one?" stops being a mystery, and you will reach for AsSplitQuery or an explicit projection before anyone files a performance ticket.

Interview Q&A · data access

What actually breaks when you port EF6 code to EF Core?

The headline is client evaluation. EF6 would silently pull rows into memory and evaluate an untranslatable predicate in C#, so queries that were always table scans appeared to work; EF Core throws instead, which is safer but means a mechanical port surfaces years of hidden bad queries all at once. Then lazy loading, which is on by default in EF6 and off in EF Core, so navigations come back null and the reflexive fix — enabling proxies — reintroduces the N+1 problem. Then EDMX, which EF Core does not support at all, so a Database First model has to be regenerated by scaffolding and then hand-tuned. Then transactions: TransactionScope works but ambient distributed transactions need explicit opt-in and are constrained on Linux, so anything relying on MSDTC needs a design conversation. And model conventions differ — cascade delete behaviour, key discovery, table naming — so I always diff the model EF Core infers against the real schema rather than trusting the scaffold.

How do you migrate data access incrementally rather than all at once?

By aggregate, with both ORMs live in the same process. EF6 and EF Core can run side by side against the same database in a modern .NET application, so I pick a bounded set of tables with a clear owner, build an EF Core context covering only those, and route the repositories that touch them while everything else stays on EF6. Where a single operation must span both, they can share a connection and an explicit transaction, which is ugly but works and is temporary by design. I do this behind repository or handler interfaces so the switch is a DI registration and a feature flag rather than a code change at every call site. And I sequence by risk: start with a read-heavy aggregate where a wrong answer is visible and recoverable, not with the billing write path. The alternative — converting nine hundred tables in one branch — is the same big-bang failure mode as a rewrite, wearing an ORM costume.

Would you keep stored procedures during a modernization?

Often yes, and I would resist the reflex to move all logic into C# as a matter of principle. Three cases where a procedure earns its place: it is genuinely set-based and moving it to the application means shipping large result sets over the network; it is tuned in ways an ORM cannot express, with hints, indexed views or plan guides that took real work; or it is called by consumers I do not control, in which case it is a public contract, not an implementation detail. Where I do want them gone is when they encode business rules that also exist in the application, because the duplication guarantees divergence, and when they make the deployment story worse by coupling schema releases to application releases. The pragmatic modernized shape I would defend is EF Core for the transactional write model, Dapper or procedures for reporting and hot read paths, and an explicit inventory of which rules live where. Rewriting a tuned two-hundred-line query as LINQ, getting worse SQL and blaming the ORM is a very common self-inflicted wound.

How do you find performance regressions after an EF Core migration?

I make the SQL visible and test against production-shaped data, because neither happens by default. Concretely: enable EF Core's query logging with parameter values in non-production, capture the generated SQL for the top twenty queries by call volume, and review them by eye — that alone finds the cartesian explosions and the accidental full-table projections. Then run a load test against a database restored from production, or at least generated at production cardinality, because the failures here are cardinality-dependent and a 500-row development database shows none of them. Alongside that, Query Store on SQL Server gives me a before-and-after comparison of plans and regressed queries, which is the most direct evidence available. And I tag telemetry with the implementation that served the request, so I can compare percentile latency for the same endpoint on the old and new data layer rather than arguing from averages.

Explain split queries and when you would use them.

When you Include more than one collection navigation, EF Core produces a single query with joins, so the result set is the cartesian product of the collections — a thousand parents with twenty lines and fifteen documents each returns three hundred thousand rows to materialise a few thousand objects. AsSplitQuery() issues one query per collection instead, so you trade extra round trips for a dramatically smaller payload, and for two or more collection includes it is almost always the right trade. The caveat that matters and that candidates miss: split queries are not a consistent snapshot, because the separate queries can interleave with concurrent writes, so if consistency matters you need an explicit transaction or an appropriate isolation level. I would also say that reaching for split queries is often a sign the query wants to be a projection instead — selecting exactly the fields the caller needs into a DTO usually beats both forms, and it is the change I would make first on a hot path.

What is new in EF Core 10 that changes your design choices?

Three things. Native AOT support with precompiled queries means EF Core can finally be used in AOT-published services, which changes the calculus for small, scale-to-zero APIs where startup time dominated. Vector similarity search is production-ready, with SqlVector<float> mapping to SQL Server 2025's and Azure SQL's native vector type, so semantic search over your own data no longer requires standing up and synchronising a separate vector database — that is a real architectural simplification and a good answer when someone asks how you would add AI features to a legacy system without a new datastore. And better JSON column support lines up with SQL Server 2025's native JSON type, which is genuinely useful for legacy schemas full of semi-structured blobs. Smaller but pleasant: full LeftJoin and RightJoin operators replace the old GroupJoin/SelectMany/DefaultIfEmpty pattern, which removes a class of subtly wrong hand-written joins.

Should you scaffold the EF Core model from the database or write it by hand?

Scaffold to start, then own it. Reverse engineering a nine-hundred-table schema by hand is a waste, and dotnet ef dbcontext scaffold gets the shape right in minutes. But the generated model is a starting point in two respects: it reflects the schema's accidents — every column nullable because someone was cautious in 2012, string keys, no navigation where there is no foreign key — and it uses EF Core's conventions, which differ from EF6's, so the model EF Core infers may not match the schema you actually have. So I scaffold, then diff the inferred model against the real database using a migration or a schema comparison and reconcile the differences deliberately, and then I hand-tune: correct nullability, add the navigations the schema forgot to declare, and split the giant context into smaller ones per aggregate. I would also scaffold into a separate folder and treat re-scaffolding as a one-off rather than a repeated build step, because a model you regenerate is a model you cannot improve.

How do you manage schema migrations when a legacy database already exists?

The first migration is a baseline, not a creation script: I scaffold the model, generate the initial migration, and then empty its Up method and mark it as applied on existing databases, so EF Core's history table starts in sync with reality without trying to recreate nine hundred tables. From there, everything goes through migrations, generated as idempotent SQL scripts or a migration bundle rather than Database.Migrate() at application startup — startup migrations race across instances during a rolling deployment and give the application's identity permission to alter schema, both of which are bad. The deployment sequence follows expand–contract from unit 03, so every migration is compatible with both the currently deployed application version and the next one. And where the database also has objects EF Core does not model — procedures, views, jobs, permissions — I keep those in the same versioned artifact, either as raw SQL in the migration or as a DACPAC, so there is exactly one story for how schema reaches an environment.

What is the difference between System.Data.SqlClient and Microsoft.Data.SqlClient?

System.Data.SqlClient is the legacy driver, effectively frozen and receiving only critical fixes; Microsoft.Data.SqlClient is the actively developed one and the only one that gets new features — Always Encrypted with secure enclaves, modern authentication against Entra ID, and support for new SQL Server 2025 types like vector and native JSON. Switching is mostly a namespace change, with one edge that causes real incidents: from version 4.0 the default connection encryption setting flipped to Encrypt=true, so connections to servers with self-signed or internal-CA certificates start failing with a certificate chain error that reads like a network problem. The right fix is a properly trusted certificate on the server; TrustServerCertificate=true is an expedient with a date on it. Because Azure SQL always presented a trusted certificate, this breaks on-premises and test environments rather than the cloud ones, which means it typically surfaces in the environment nobody rehearsed in.

When would you not use an ORM at all in a modernized system?

For read models and reporting, for bulk operations, and for the small number of hot paths where the SQL is the design rather than an implementation detail. An ORM's value is in the write side — change tracking, unit of work, mapping an aggregate to rows — and that value largely evaporates when you are projecting a shaped result set for a screen or a report, where a hand-written query plus Dapper is simpler, faster and easier to tune. Bulk work is similar: even with EF Core's ExecuteUpdate and ExecuteDelete, genuinely large loads belong in SqlBulkCopy or a set-based statement. I would frame it as picking per use case rather than per system, and I would be explicit that mixing is normal rather than a compromise — the trap is the team that adopts EF Core as a standard and then contorts reporting queries into LINQ to comply. What I do insist on is that both paths share the same connection, transaction, retry and telemetry configuration, so the mixture is a deliberate design rather than two unrelated data layers.

08 The database and its data

The database is where modernization programmes actually stall. Code can be strangled route by route in weeks; a 4 TB schema with 900 tables, 1,200 procedures and eleven undocumented consumers cannot. Two consequences follow, and both are lead-level judgments. First, the data track must start at the same time as the code track, not after it — a strangler fig over a shared database is a UI project. Second, the database usually moves before it is split: get onto a supported, managed platform first, decompose later or never.

The calendar, because it is driving everyone right now

SQL Server 2016 reached end of extended support on 14 July 2026 — eight weeks ago. Microsoft's three options are the ones to name: migrate to Azure SQL, upgrade in place to SQL Server 2025, or buy Extended Security Updates, which are available for up to three further years through July 2029 and can be managed via SQL Server enabled by Azure Arc or on Azure VMs. Databases running on Azure VMs or Azure Arc-enrolled hosts can receive ESUs at no extra charge in some configurations — that asymmetry is deliberate, and it is a real lever in a budget conversation. SQL Server 2025 went GA on 15 November 2025 (build 17.0), bringing a native vector type, a native json type, regular expressions, change event streaming, and a REST API surface — plus Standard edition limits raised to 32 cores and 256 GB, with Web edition discontinued after 2022.

Upgrading the engine without a plan-regression incident

The most common self-inflicted database-migration incident is a query-plan regression from the cardinality estimator, and the mitigation is a documented, boring workflow that far too few candidates can describe: upgrade the engine, keep the old compatibility level, enable Query Store, establish a baseline, then raise the compatibility level and use Query Store to find and fix regressions.

-- 1. Engine is now SQL Server 2025 (17.0). Compatibility level stays where it was.
ALTER DATABASE Meridian SET COMPATIBILITY_LEVEL = 130;   -- as on SQL Server 2016

-- 2. Query Store on, sized for a full business cycle, capturing everything that matters.
ALTER DATABASE Meridian SET QUERY_STORE = ON
  (OPERATION_MODE = READ_WRITE,
   MAX_STORAGE_SIZE_MB = 10000,
   QUERY_CAPTURE_MODE = AUTO,
   DATA_FLUSH_INTERVAL_SECONDS = 900,
   INTERVAL_LENGTH_MINUTES = 30,
   SIZE_BASED_CLEANUP_MODE = AUTO);
-- ... now run a full workload cycle. Weeks, not hours: month-end plans matter.

-- 3. Raise the compatibility level. This is the change that moves plans.
ALTER DATABASE Meridian SET COMPATIBILITY_LEVEL = 170;   -- SQL Server 2025

-- 4. Find regressions: same query, new plan, worse duration.
SELECT TOP 25 q.query_id, qt.query_sql_text,
       MIN(rs.avg_duration) AS avg_us, rs.plan_id, MIN(rs.first_execution_time) AS seen
FROM sys.query_store_query AS q
JOIN sys.query_store_query_text AS qt ON qt.query_text_id = q.query_text_id
JOIN sys.query_store_plan  AS p  ON p.query_id = q.query_id
JOIN sys.query_store_runtime_stats AS rs ON rs.plan_id = p.plan_id
GROUP BY q.query_id, qt.query_sql_text, rs.plan_id
ORDER BY MIN(rs.avg_duration) DESC;

-- 5. Pin the good plan while you fix the query properly. Reversible, per query.
EXEC sp_query_store_force_plan @query_id = 41287, @plan_id = 90114;

Forcing a plan is a tourniquet, not a treatment: it keeps the business running while the query is rewritten or indexed properly, and every forced plan should carry a ticket. Query hints applied through Query Store (sp_query_store_set_hints) are the less blunt version — they let you apply a hint to a query you cannot edit, which is exactly the situation with a vendor application or a procedure called from a system you do not own.

Zero-downtime schema change, mechanically

Unit 03 gave the expand–contract shape; here is what actually goes wrong at 4 TB. Three rules:

  1. Never let a migration take a long lock. Adding a nullable column with no default is metadata-only and instant. Adding NOT NULL WITH DEFAULT is metadata-only from SQL Server 2012 Enterprise onward for most types but not for all of them — verify, do not assume. Adding a CHECK or foreign key constraint scans the table unless you add it WITH NOCHECK and validate afterwards.
  2. Backfill in bounded batches with a lock timeout, never as one statement. One UPDATE over 200 million rows escalates to a table lock, fills the log, blocks everything and cannot be stopped without an equally long rollback.
  3. Build indexes online where the edition supports it, and expect the resumable option to be the difference between a maintenance window and a normal Tuesday.
-- EXPAND: metadata-only, instant, safe to deploy at any time.
ALTER TABLE dbo.Shipment ADD customer_ref VARCHAR(40) NULL;

-- MIGRATE: batched backfill. Bounded work, bounded locks, restartable, observable.
DECLARE @batch INT = 5000, @rows INT = 1;
SET LOCK_TIMEOUT 5000;                       -- fail fast rather than block the app
WHILE @rows > 0
BEGIN
    UPDATE TOP (@batch) s
       SET s.customer_ref = c.ExternalRef
    FROM dbo.Shipment AS s
    JOIN dbo.Customer AS c ON c.CustomerCode = s.CustomerCode
    WHERE s.customer_ref IS NULL AND s.CustomerCode IS NOT NULL;

    SET @rows = @@ROWCOUNT;
    WAITFOR DELAY '00:00:00.100';            -- let the log ship and other work in
END

-- Index online and resumable: survives a failover, can be paused during peak.
CREATE INDEX IX_Shipment_customer_ref ON dbo.Shipment (customer_ref)
  WITH (ONLINE = ON, RESUMABLE = ON, MAX_DURATION = 60 MINUTES);

-- Constraint without a blocking scan, then validate as a separate, killable step.
ALTER TABLE dbo.Shipment WITH NOCHECK
  ADD CONSTRAINT CK_Shipment_customer_ref CHECK (customer_ref IS NOT NULL);
ALTER TABLE dbo.Shipment WITH CHECK CHECK CONSTRAINT CK_Shipment_customer_ref;

-- CONTRACT: only after query capture proves nothing reads the old column.
-- Deprecate first - rename so failures are loud and the change is reversible.
EXEC sp_rename 'dbo.Shipment.CustomerCode', 'CustomerCode_deprecated_20261115', 'COLUMN';
-- ... one full release cycle later ...
-- ALTER TABLE dbo.Shipment DROP COLUMN CustomerCode_deprecated_20261115;

Moving the data, and proving you moved it

The cutover mechanism depends on the downtime you can buy. Backup/restore is simplest and costs hours. Log shipping or the MI link gets you to minutes. Transactional replication or CDC gets you to seconds at the cost of real complexity. Whatever you choose, reconciliation is not optional and it is the thing juniors omit: counts per table, checksums per partition, and — the one that catches real problems — business aggregates.

-- Reconciliation the business can sign off on. Technical checksums prove bytes moved;
-- business aggregates prove MEANING moved.
SELECT CAST(ClearedOn AS date)      AS day,
       COUNT(*)                     AS shipments,
       SUM(DeclaredValue)           AS declared_value,
       COUNT(DISTINCT CustomerCode) AS customers,
       CHECKSUM_AGG(BINARY_CHECKSUM(ShipmentId, DeclaredValue, StatusCode)) AS chk
FROM   dbo.Shipment
WHERE  ClearedOn >= DATEADD(day, -90, SYSUTCDATETIME())
GROUP BY CAST(ClearedOn AS date)
ORDER BY day;
-- Run on source and target, diff the result sets, and require a human sign-off
-- on any day that differs - including the days you expect to differ.

Two more pieces of a real .NET estate: SSIS packages lift to Azure Data Factory's SSIS Integration Runtime with little change, which buys time, or get rewritten as ADF/Synapse pipelines when someone is willing to fund it. And SQL Agent jobs survive on Managed Instance but not on Azure SQL Database, which is frequently the single fact that decides between those two targets.

Interview trap

Upgrading the engine and the compatibility level in the same change. It is the most common cause of a "the migration made everything slow" incident, and the fix is a documented workflow candidates rarely know: upgrade the engine, hold the compatibility level at its old value, turn on Query Store and capture a full business cycle including month-end, then raise the compatibility level and use Query Store's regressed-query view to find and force the plans that got worse. It is Microsoft's own recommended upgrade workflow. The related trap is over-trusting sp_query_store_force_plan: forcing a plan is a tourniquet with a ticket attached, not a fix, and an estate with forty forced plans has a permanent, invisible dependency on an old optimiser's choices.

Gotcha

Collation. A restore keeps the database collation, but a new Azure SQL database defaults to SQL_Latin1_General_CP1_CI_AS, and the instance-level collation on Managed Instance is fixed at creation and cannot be changed afterwards. If your legacy database used a different collation, comparisons, sorting and tempdb joins can behave differently — and cross-collation joins against tempdb throw errors that appear only under specific queries, typically in reports nobody ran during testing. Check the source collation before you create the target, because on MI the remedy is recreating the instance.

Try it — 2 hours, two exercises

1. Run the compatibility-level workflow. Take any SQL Server database (a container is fine), set the compatibility level low, enable Query Store, run a workload, then raise the level and use the Query Store regressed-queries view to find what changed. Force a plan and confirm the change.

2. Break a backfill on purpose. Create a table with a few million rows and run an unbatched UPDATE across all of them while another session reads it. Watch the blocking and the log growth. Then do it batched with a lock timeout and compare.

Expected outcome

Exercise 1 gives you the sentence "I upgrade the engine and the compatibility level as two separate changes with Query Store in between", backed by having watched a plan actually change. That is a distinguishing answer, because most candidates treat compatibility level as a version number rather than as the optimiser switch it is.

Exercise 2 makes the lock escalation visceral: the unbatched update takes a table lock at around five thousand row locks and blocks every reader, and the rollback takes as long as the update did. That is why "restartable, bounded, observable" is the design rule for anything touching a big table, and why the migration script needs a kill switch.

Interview Q&A · database and data

How do you migrate a large SQL Server database to Azure with minimal downtime?

I pick the mechanism from the downtime budget backwards. If hours are acceptable, backup and restore is simplest and least risky. If minutes are the target and the destination is Managed Instance, the Managed Instance link is the answer: it uses distributed availability group technology to keep the target continuously replicated from the source, so cutover is a controlled failover rather than a restore. If seconds are required, transactional replication or change data capture into the target gets you there at a real cost in complexity and operational risk. Whatever the mechanism, the parts that decide success are the same: rehearse the cutover at production scale at least twice with the clock running, prepare reconciliation queries that compare row counts, checksums and business aggregates on both sides, and have a rollback that does not depend on the migration having gone well — usually meaning the source stays writable-capable and untouched until sign-off. I would also note the tooling changed recently: Data Migration Assistant retired in July 2025 and the Azure Data Studio migration extension in February 2026, so the current path is Azure Database Migration Service and the Arc-based experience.

Azure SQL Database or Managed Instance?

Managed Instance is the default for a legacy .NET estate, because it preserves the instance-level surface that legacy applications assume: SQL Agent jobs, cross-database queries, CLR, Service Broker, linked servers, and instance-scoped logins. Azure SQL Database is a better product in several ways — serverless, Hyperscale, simpler networking, faster feature delivery — but it is a single-database model, so cross-database queries and Agent jobs have to be redesigned into elastic jobs, Functions or Data Factory, and that redesign can be larger than the migration itself. The specific question I ask first is whether anything does a three-part-name query across databases, because that single fact usually decides it. My preference is to land on MI to get supported and managed quickly, then move individual databases to SQL DB later where the dependency is gone. And I check collation before creating anything, because the MI instance collation is fixed at creation and cannot be changed afterwards.

How do you change a schema without downtime?

Expand–contract across three deployments, with the rule that the schema must be compatible with both the currently deployed application version and the next one at every moment, since a rolling deployment has both live. Expand adds the new structure as nullable and deploys code that writes both old and new; this is instantly reversible. Migrate backfills in bounded batches with a lock timeout so no single statement escalates to a table lock or fills the log, creates indexes online and resumable, and adds constraints with NOCHECK followed by a separate validation step that can be killed. Contract drops the old structure, and I put a full release cycle between migrate and contract, verify with query capture that nothing still reads the old column, and rename before dropping so the failure mode is a loud error rather than data loss. The contract step is the only irreversible one, and treating it with more ceremony than the others is the whole discipline.

You raised the compatibility level and everything slowed down. What do you do?

First, stop the bleeding using the evidence I should already have: Query Store's regressed-queries view shows which queries changed plan and by how much, and sp_query_store_force_plan pins the previously good plan per query, which is reversible and surgical. That buys time without reverting the whole database. Then I decide whether to fall back — setting the compatibility level down is a legitimate, fast rollback — or to fix forward query by query, which depends on how many queries regressed and how business-critical they are. Then the real fix: each forced plan gets a ticket, and the query is rewritten, re-indexed or given a Query Store hint so it performs under the new cardinality estimator on its own merits, because a forced plan is a permanent invisible dependency on an old optimiser. And I would say plainly that this situation is avoidable: the reason Microsoft documents upgrading the engine and raising the compatibility level as two separate steps with a Query Store baseline in between is precisely to make this a measured change rather than a surprise.

How do you verify that a data migration was correct?

Three layers, and I insist on the third. Structural: object counts by type, schema comparison, and permissions and logins, since orphaned users are the classic post-restore surprise. Technical: row counts per table and checksums per partition or date range, which prove the bytes moved. Business: aggregates the business itself recognises — shipments cleared per day, total declared value per month, open invoices by customer — compared between source and target and signed off by someone who would notice if they were wrong. The third layer is the one that catches the failures that matter, because a truncated varchar, a collation difference, a time-zone shift or a decimal-scale change can preserve row counts perfectly while changing meaning. I also compare a sample of individual records end to end rather than only aggregates, and I keep the source available and unmodified until the business signs off, because the reconciliation is only useful if you can still act on what it tells you.

What do you do with 1,200 stored procedures?

Not rewrite them, at least not as part of the migration. First I find out which are actually used, with a capture window that spans the business's longest cycle rather than the plan cache, because year-end procedures look dead for eleven months. That typically retires a large fraction outright. Of what remains, I keep the set-based ones and the tuned ones, because moving them into C# usually means moving large result sets over the network for no benefit, and I keep anything called by a consumer I do not control, because that is a public contract. What I do want out are the ones encoding business rules also implemented in the application, since duplication guarantees divergence. The important reframing is that stored procedures are not inherently legacy — they are a deployment and ownership problem, so I bring them into source control and the same versioned deployment artifact as the schema, and then I stop treating their existence as a defect. Migrating a database and rewriting its logic at the same time is two migrations, and one of them will fail.

How do you handle SSIS packages and SQL Agent jobs?

Pragmatically, because they are rarely the point of the programme. SSIS lifts to Azure Data Factory's SSIS Integration Runtime with little or no change, which gets the packages onto a managed platform quickly and buys time; rewriting them as ADF or Synapse pipelines is a separate, later, separately funded piece of work that needs its own justification. SQL Agent jobs run on Managed Instance essentially as they do on-premises, which is frequently the deciding factor for choosing MI over Azure SQL Database, since on SQL DB they have to become elastic jobs, Azure Functions, Container Apps jobs or Data Factory triggers. Either way I insist on two things during the migration: inventory every job and every package with an owner and a schedule, because these are the workloads most likely to be forgotten and then to fail silently at month-end, and get them into source control, since a job whose only definition lives in msdb cannot be reviewed, tested or restored. Scheduled work is also where undocumented consumers hide, so the inventory pays for itself in unit 02 terms.

Would you move from SQL Server to PostgreSQL as part of a modernization?

Almost never during the modernization itself, and I would push back hard if it were proposed as part of the same programme. The engine change is not the ORM's dialect; it is T-SQL procedures, collation and sorting semantics, identity and sequence behaviour, date and time types, isolation-level defaults — SQL Server defaults to read committed with locking and PostgreSQL to MVCC snapshot semantics, which changes concurrency behaviour in ways that surface as rare, hard-to-reproduce bugs — plus the entire operational toolchain and your team's accumulated expertise. Doing it at the same time as a runtime and hosting migration means that when something breaks you cannot tell which change caused it, and that ambiguity is what kills programmes. If there is a genuine driver — licensing cost at scale, a multi-cloud requirement, a managed-service preference — I would sequence it strictly after the estate is on modern .NET and supported infrastructure, treat it as its own funded programme with its own parallel-run verification, and pilot it on one bounded service first. The exception I would accept is a small, well-isolated database whose migration is genuinely a week of work and can act as the pilot.

What is new in SQL Server 2025 that matters for a modernization?

Four things I would actually use. The native vector type with vector indexes and distance functions, which means semantic search over your own operational data without standing up and synchronising a separate vector database — and EF Core 10 maps it, so it is reachable from application code rather than only from SQL. The native json type with JSON indexes, which is a real improvement for the semi-structured columns every legacy schema accumulates and which were previously nvarchar(max) with string functions over them. Regular expression support, which removes a common reason for CLR assemblies — and CLR is exactly the kind of dependency that complicates a move to a managed platform. And change event streaming, which gives you an outbox-like change feed from the engine, useful for keeping a read model or a downstream service in sync during a strangler migration without dual-write. Beyond features, the edition change matters commercially: Standard now allows up to 32 cores and 256 GB with Resource Governor included, and Web edition is discontinued, so the licensing conversation during an upgrade is different from last time.

How do you decompose a shared database that four applications write to?

Slowly, and by ownership before physical separation. The first step is to establish which application owns which tables, which is a political exercise as much as a technical one, and to stop the non-owners writing directly — they call the owner's API, or they consume a change feed. That alone removes most of the coupling, and it can be done while everything still lives in one database, which makes it far cheaper and reversible. I enforce it with schemas and permissions so the constraint is real rather than a convention, and I use views or synonyms as an interim seam where a consumer must keep reading a table it no longer owns. Physical separation comes last, and only where it buys something specific — independent scaling, independent release cadence, a compliance boundary — because the moment the data is in two databases you have lost transactional integrity across the boundary and bought eventual consistency, reconciliation jobs and a new class of incident. I would also be honest in an interview that many estates should stop after the ownership step, and that a single database with enforced ownership boundaries is a perfectly respectable end state — which is the data-layer version of the modular-monolith argument.

JavaScript to TypeScript: a ratchet, not a rewrite

The only migration strategy that finishes is the incremental one: turn on allowJs, rename files one at a time, and tighten compiler options as a ratchet that can only go one way. Renaming 900 files to .ts in one branch produces 40,000 errors and a branch nobody merges.

// tsconfig.json - phase 1. Compiles the existing JS, checks nothing yet.
{
  "compilerOptions": {
    "target": "ES2022", "module": "ESNext", "moduleResolution": "bundler",
    "allowJs": true,          // .js files participate
    "checkJs": false,         // ... but are not type-checked yet
    "strict": false,
    "noEmit": true,           // Vite/esbuild transpiles; tsc only type-checks
    "skipLibCheck": true
  },
  "include": ["src/**/*"]
}

// tsconfig.strict.json - phase 2. A SECOND config over an explicit, growing
// allowlist. CI runs both: the loose one over everything, the strict one over
// the migrated set. The list only ever grows - that is the ratchet.
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "erasableSyntaxOnly": true       // no enums/namespaces: keeps files
  },                                 // runnable by Node's own type stripping
  "include": ["src/domain/**/*", "src/islands/**/*", "src/api/**/*"]
}

Two details worth knowing in 2026. erasableSyntaxOnly forbids TypeScript syntax that cannot simply be erased — enum, namespace, parameter properties — which keeps files compatible with Node's built-in type stripping and with the fastest transpile-only paths. And verbatimModuleSyntax plus import type is what makes a CommonJS-to-ESM move survivable, because it stops the compiler from silently eliding imports that had side effects.

Interview trap

Claiming TypeScript 7 as a simple win. It is genuinely 8–12× faster and it shipped on 8 July 2026, but the follow-up question is the real test: what does it break? TypeScript 7.0 has no stable programmatic compiler API, so anything that consumes the API — typescript-eslint, ts-jest, ts-morph, and the template type-checkers behind Vue, Svelte and Astro — cannot run on it; that API is targeted for 7.1. The workable 2026 answer is to run both compilers: the native one for fast local and CI type-checking, the JS-based 5.9/6.x line for the tools that need the API, with a single source of truth for tsconfig. Saying "we'd just upgrade to TS 7" without naming the API gap tells an interviewer you read a headline; naming it tells them you have looked at your own lockfile.

Gotcha

The npm supply chain is now the most likely way a front-end modernization introduces a security incident, and a migration is exactly when you touch every dependency at once. Self-replicating credential-stealing worms have hit the registry repeatedly since September 2025, propagating through post-install scripts and stolen publish tokens. Non-negotiables during a dependency sweep: commit the lockfile and install with npm ci, disable lifecycle scripts by default (--ignore-scripts, with an explicit allowlist), pin exact versions rather than ranges for the migration window, enable provenance/attestation checks where publishers support them, and keep a cooling-off period before adopting brand-new releases. "We upgraded 400 packages in one PR" is how a compromised transitive dependency reaches production unnoticed.

Try it — 3 hours, two exercises

1. Mount an island in a legacy page. Take any server-rendered page and replace one region with a React or Vue component built by Vite, reading its props from data- attributes and its script URL from the Vite manifest. Confirm the rest of the page — session, navigation, styling — is untouched.

2. Ratchet a JS codebase. Point a tsconfig with allowJs: true, checkJs: false at an existing JavaScript project. Then flip checkJs: true and count the errors. Then create a second strict config over a three-file allowlist and wire both into CI.

Expected outcome

Exercise 1 usually takes under an hour and is the thing that makes front-end modernization fundable, because it produces a visible improvement inside the existing application in one sprint rather than a parallel SPA in one year.

Exercise 2 produces a large error count on checkJs and a small one on the allowlist. That contrast is the strategy: the global number is a reason never to start, the allowlist number is a Tuesday. The two-config ratchet is also the most portable idea in this unit — it works identically for nullable reference types in C#, for warnings-as-errors, and for the Framework-project allowlist in unit 05.

Interview Q&A · front end

How would you modernize a jQuery front end without a rewrite?

Keep the server-rendered pages and replace regions rather than pages. I add a modern build — Vite with one entry point per island — that emits hashed bundles into the existing application's static folder, and the server reads the manifest so cache-busting is content-based. Each island is mounted into a div in an existing page with its props passed through data- attributes, so the surrounding page, its session, its navigation and its authorization are untouched. That means a user never bounces between two applications, and each island ships in a sprint rather than a year. I would sequence islands by interaction complexity: grids, filters and multi-step forms first, because that is where jQuery hurts most and where a component model pays for itself. And I would deliberately leave the simple pages alone — a form that posts and redirects does not become better as a client-rendered component, and pretending otherwise is how front-end migrations lose their sponsor.

What is the state of TypeScript right now and how does it affect a migration?

TypeScript 7.0 went GA on 8 July 2026 and replaced the compiler with the Go-native port, roughly 8 to 12 times faster on full builds, which is transformative for a large legacy codebase where tsc took minutes. The catch that decides your plan is that 7.0 has no stable programmatic API, so tooling that consumes the compiler API — typescript-eslint, ts-jest, ts-morph, and the template type-checkers behind Vue, Svelte and Astro — cannot run on it; that API is expected in 7.1. So the pragmatic setup today is dual: use the native compiler for fast type-checking locally and in CI where speed matters, and keep the JavaScript-based 5.9 or 6.x line for the tools that need the API, sharing one tsconfig. For migration planning that means I would not block adoption of TS 7 on the lint story, but I would not rip out the old compiler either, and I would check my own lockfile for API consumers before promising anything.

How do you migrate a JavaScript codebase to TypeScript?

As a ratchet with two configs, never as a big rename. Phase one turns on allowJs with checkJs off, so TypeScript compiles the existing JavaScript and nothing fails; that ships immediately. Phase two adds a second, strict tsconfig over an explicit allowlist of directories, and CI runs both — the loose config over everything and the strict one over the migrated set. Files move into the strict set as they are touched, and the allowlist only ever grows, which is what makes it a ratchet rather than an aspiration. I convert by value rather than by directory order: shared domain logic and API clients first, because typing the boundary catches the most bugs per file, and leave the leaf UI glue for last. I also ban any in the strict set from the start and allow unknown plus narrowing instead, because a codebase that migrates to TypeScript with any everywhere has paid the cost and bought nothing.

Should a legacy internal application become a single-page app?

Usually not, and being able to say so is the point of the question. A SPA buys you rich client-side interactivity, offline capability and a decoupled front end; a dense internal forms application over an authenticated intranet needs almost none of that, and in exchange you take on a second authorization model, token handling, client-side state management, a bundle-size budget, a separate deployment and often a backend-for-frontend. The alternative — server-rendered Razor Pages or MVC with islands of interactivity where it is genuinely warranted — keeps one session, one authorization story and one deployment, and is a legitimate modern architecture rather than a compromise. I would choose a SPA when the interaction model is genuinely application-like, when the same API serves mobile clients, or when the front-end team is separate and needs an independent release cadence. What I would not do is adopt one because the current stack is old, since the age of jQuery is an argument about jQuery, not about rendering strategy.

How do you handle an AngularJS 1.x application?

It is a rewrite; there is no upgrade path, and AngularJS reached end of life in January 2022 so it has been unsupported for over four years, which is also the argument that funds the work. The ngUpgrade hybrid mode, which lets AngularJS and modern Angular run side by side, still exists and can be useful for a large application, but it is itself unsupported ground and adds a bootstrapping complexity that many teams underestimate. My preferred approach is the same island strategy as anywhere else: pick a route or a component region, rebuild it in the target framework, mount it in place, and let the two coexist at the DOM level rather than through a framework bridge — this works whether the target is Angular 22 or React, and it does not couple you to a deprecated interop layer. I would also treat this as the moment to question the SPA decision itself, because many AngularJS applications were built when server-rendered pages could not do what was needed, and that constraint no longer holds. Whatever the target, I would want usage data first, since a portion of the routes are invariably retire candidates.

What replaces System.Web.Optimization bundling?

A real front-end build, normally Vite, producing content-hashed bundles that the server references through a manifest. The framework itself now covers the simple cases — modern ASP.NET Core does static asset fingerprinting and compression at build time — but anything with TypeScript, JSX or a component framework wants a proper bundler. The migration is staged rather than atomic: the legacy bundles keep serving legacy pages, the Vite build serves the new islands, and both are referenced from the same layout until the last legacy bundle is gone. The genuinely awkward part is not the bundler, it is the shared global CSS and the jQuery plugin soup both sides depend on, because those have no module boundaries and cannot simply be split; my approach there is to leave the global stylesheet in place, scope new component styles so they cannot be affected by it, and treat de-globalising the CSS as a separate, later project. Trying to unify the asset pipeline and migrate the framework in one change is how front-end modernization stalls.

How do you manage npm dependency risk during a modernization?

Carefully, because a migration touches every dependency at once and that is exactly the window an attacker needs. The concrete controls I insist on: a committed lockfile with npm ci in CI so installs are reproducible, lifecycle scripts disabled by default with an explicit allowlist, since post-install scripts are the standard propagation mechanism for the self-replicating credential-stealing worms that have hit the registry repeatedly since September 2025, exact version pinning during the migration window rather than ranges, and a cooling-off period before adopting a brand-new release. Beyond that, provenance and attestation checks where publishers support them, an SBOM produced per build so I can answer "do we ship this package?" in minutes rather than days, and dependency updates in small reviewable batches rather than one four-hundred-package pull request. The organisational half matters too: publish tokens should be short-lived and scoped, and CI should not hold a token that can publish to a registry unless it genuinely publishes.

Which Node.js version should a project target today, and what is changing?

Node 24, which is the current Active LTS and supported until 30 April 2028. Node 26 was released on 5 May 2026 and enters LTS in October 2026, so it becomes the target shortly. The change worth knowing is structural: from October 2026 Node moves from two major releases a year to one, version numbers align to the calendar year, and every release becomes an LTS, with a new alpha channel for early testing — Node 26 is the last release under the old model and Node 27 the first under the new one. For a modernization that is good news, because it turns the runtime upgrade from a twice-yearly decision into an annual one and removes the "current versus LTS" confusion that led teams to sit on unsupported versions. Practically I pin the version in .nvmrc or engines, use the same version in CI and in the container base image, and treat the annual bump as a scheduled maintenance item rather than an event.

How do you keep two front ends from looking like two products?

By making the design system, not the framework, the unit of consistency. Before any island ships, I extract the existing look into shared CSS custom properties and a small set of primitives — buttons, inputs, tables, spacing scale — and make both the legacy pages and the new components consume the same tokens, so a colour or spacing change lands in both. Then I mount new components inside existing page shells rather than replacing whole pages, so the header, navigation and layout stay identical throughout, and the user experiences one application even mid-migration. I also migrate by workflow rather than by page, so a user never crosses the boundary inside a single task, since that is where the perception of a broken system comes from. And I would keep one team accountable for the visual result across both stacks rather than splitting ownership by technology, because two teams optimising their own half is exactly how you get two products.

How do you decide what the API between the new front end and the back end looks like?

By resisting the reflex to expose the legacy model over HTTP. If the new front end calls an API whose shapes are the legacy tables, you have rebuilt the legacy model in JSON and locked yourself into it for the next decade. So the API is designed from the screens backwards — a shape per use case rather than per entity — with an anti-corruption layer behind it translating from whatever the legacy store actually looks like. I would keep it boring: REST or a backend-for-frontend over HTTP with OpenAPI generated from the code, typed clients generated for the front end so the contract is compile-checked on both sides, and versioning from day one because during a migration you will need two versions live at once. I would avoid introducing GraphQL as part of a modernization unless there is a specific client-shape problem it solves, because it adds an authorization surface, a caching story and a performance failure mode that a team already absorbing a runtime, data and hosting migration does not need. And I would put the contract tests in unit 04's safety net, since the API boundary is the seam that both sides are strangling across.

The things that surprise a lifted application in PaaS

  • Transient faults are normal. Azure SQL and Service Bus disconnect routinely — failovers, throttling, maintenance. Retry with exponential backoff and jitter is not defensive programming, it is a functional requirement. EnableRetryOnFailure for EF Core, and Microsoft.Extensions.Http.Resilience (the standard resilience handler) for HTTP.
  • Latency is different, not worse. A chatty data access layer that did 40 round trips per page over a 0.2 ms LAN does the same 40 over a 2 ms PaaS link. Nothing is broken; the design was always wrong and the LAN was hiding it.
  • Networking is the schedule risk. Private endpoints, VNet integration, DNS zones and firewall rules are where migrations lose weeks — not because they are hard, but because they usually belong to a different team. Start the networking conversation in week one.
  • Scale-to-zero is a trap for user-facing APIs. It is excellent for jobs and internal tools; on a customer-facing endpoint the cold start is a latency SLO violation with a nice invoice attached.
Interview trap

Reaching for AKS. Kubernetes is the answer that sounds most senior and is most often wrong for a modernization, because you are proposing to add a platform-engineering obligation — cluster upgrades, node pools, CNI, ingress controllers, CVE response, RBAC, cost governance — to an organisation that has just proved it could not keep a runtime patched. Container Apps gives you containers, KEDA-based autoscaling including scale-to-zero, revisions and traffic splitting, and jobs, with none of that obligation; App Service gives you even less to run. The credible answer names the specific requirement that would force the descent — custom CNI or node-level networking, operators, a service mesh, GPU scheduling, many teams needing genuine multi-tenant isolation, or an existing platform team who already run clusters well — and otherwise picks the managed option and says why. The corollary interviewers like: "if we do choose AKS, that is a decision to hire or assign a platform team, and I would put that in the same paper."

Gotcha

The Data Protection key ring. On .NET, cookies, antiforgery tokens and any IDataProtector payload are encrypted with a key ring that, by default, is generated per instance and stored on the local file system — which in a container is ephemeral and per-replica. The symptoms are maddening and are misdiagnosed as load-balancer or session problems: users randomly signed out, antiforgery validation failures that vanish on refresh, and everything breaking after a deployment or a scale-out. Persist the key ring to blob storage, protect it with Key Vault, and set the same SetApplicationName on every application that must share it. Do this before the first container reaches production, because in a strangler-fig migration the legacy app must share that ring too.

Try it — 3 hours, two exercises

1. Containerize and break it. Containerize an ASP.NET Core app with cookie authentication, run two replicas behind a load balancer, and log in. Restart one replica. Observe the sign-outs. Then persist Data Protection to blob storage with a shared application name and repeat.

2. Delete a secret. Take an application with a SQL connection string containing a password, create a managed identity, grant it database access, switch to Authentication=Active Directory Default, and remove the password from every configuration file and pipeline variable.

Expected outcome

Exercise 1 reproduces one of the most commonly misdiagnosed production incidents in containerized .NET. Having caused it deliberately means you will recognise "users get randomly logged out after we scaled up" in seconds rather than after two days of blaming the load balancer.

Exercise 2 usually takes longer than expected — not the code, but finding every place the password was copied: appsettings, a pipeline variable group, a runbook, someone's local file, a Terraform state. That search is the argument for managed identity, and the story to tell when an interviewer asks what security improvement you got from the migration.

Interview Q&A · Azure

How do you choose between App Service, Container Apps, AKS and VMs?

I start at the top of the abstraction ladder and only descend when a specific, named requirement forces it, because every step down adds a permanent operational obligation rather than a one-off cost. App Service if the workload is an HTTP application and needs nothing unusual from the operating system. Container Apps as the default for a containerized estate, because it gives scale-to-zero, KEDA-based autoscaling on things like queue depth, revisions with traffic splitting and a jobs model, without a cluster to run. AKS only when there is a real cluster-level requirement — custom networking, operators, service mesh, GPUs — or an existing platform team who already operate Kubernetes well; otherwise it is a liability an organisation that just failed to patch a runtime should not take on. VMs for the rehost step and for genuinely unportable Windows components, with a date attached. And I would say the choice is per workload, not per estate: a modernized system quite reasonably has an App Service front end, Container Apps jobs replacing SQL Agent, and one VM still running the thing nobody has ported.

What breaks when you containerize a legacy .NET web application?

Five things, in roughly that order of frequency. Local file-system writes, because the container file system is ephemeral and often read-only, so temp files, uploads and generated PDFs have to move to blob storage. In-process session and cache, because there are now multiple replicas, so anything in memory has to move to a distributed store. The Data Protection key ring, which is generated per instance by default, so cookies and antiforgery tokens stop validating across replicas and after every restart — this is the one that gets misdiagnosed as a load-balancer problem. Missing operating-system data in a minimal base image, most often time-zone data, so time-zone lookups throw or silently fall back to UTC. And the absence of graceful shutdown handling, so a scale-in or a deployment kills in-flight requests and half-finished background work. All five are things a scanner will not tell you and a single-instance test will not reveal, which is why the first containerized workload should run with at least two replicas from day one.

How do you handle secrets and configuration in a modernized Azure application?

The goal is that there are no secrets to handle. Managed identity for every Azure resource — SQL, Storage, Service Bus, Key Vault — so the connection strings name an identity rather than carrying a password, and DefaultAzureCredential lets the same code use the developer's identity locally and the assigned identity in Azure. Configuration lives in Azure App Configuration with environment labels, secrets that genuinely must exist live in Key Vault and are referenced from App Configuration rather than copied, and everything binds into strongly typed options validated at startup so a missing value fails the deployment rather than the first request. During coexistence I keep one source of truth and have the legacy application read from it too, because two configuration stores drifting is a reliable source of incidents where old and new disagree. And I would treat removing the last password from a pipeline variable as a deliverable with a date, because it is the security improvement the migration can actually point at.

What is the difference between liveness and readiness probes, and why does it matter?

Liveness answers "is this process broken and in need of a restart"; readiness answers "should this instance receive traffic right now". They must check different things, and conflating them causes outages. If the liveness probe checks the database, then a brief database failover makes every replica report unhealthy simultaneously, the platform restarts all of them, and you have converted a thirty-second blip into a full outage plus a cold start. So liveness checks only the process itself, readiness checks the dependencies it needs to serve, and a startup probe covers slow initialisation so a long warm-up is not mistaken for a hang. The related thing I would add for a migration is that readiness has to become false before shutdown begins, so the load balancer stops sending requests while in-flight work drains — that plus a shutdown timeout is what makes rolling deployments invisible to users, and its absence is why legacy applications need a maintenance window.

How do you make a lifted application resilient in PaaS?

By treating transient failure as normal rather than exceptional, because in a managed platform it is: failovers, throttling and planned maintenance all disconnect you. Concretely, EF Core gets EnableRetryOnFailure with a bounded retry count, HTTP clients get the standard resilience handler from Microsoft.Extensions.Http.Resilience with retry, timeout and circuit breaker, and message handlers are made idempotent so a retry cannot double-charge or double-ship. Timeouts have to be explicit everywhere, because the default of infinite is what turns a slow dependency into thread exhaustion. Beyond retries, the design points are bulkheads so one slow dependency cannot consume the whole thread pool, and graceful degradation so a non-essential dependency being down produces a reduced feature rather than a 500. What I would warn against is retrying non-idempotent operations blindly, since a retried payment is worse than a failed one — which is why idempotency keys and an outbox belong in the same conversation.

Is a modernized application slower in the cloud?

Some things are, and it is almost always the same thing: network round trips. A data access layer doing forty queries per page over a sub-millisecond LAN feels fine and does the same forty over a two-millisecond managed link, so the latency multiplies visibly. The correct response is not to blame the platform but to observe that the design was always wrong and the LAN was subsidising it, then fix the chattiness — batching, projections, caching, or moving the logic to where the data is. The other common surprise is throughput limits: managed services have quotas and throttle rather than degrade gracefully, so an unbounded parallel load that a dedicated server absorbed now returns errors. On the other side, PaaS usually improves the things people did not measure: patching, failover, backup and the ability to scale out at all. I would set the expectation explicitly before migration — median latency may rise slightly, tail latency and availability should improve — and I would have the before-and-after telemetry from unit 04 to prove which of those actually happened.

When would you use Windows containers?

When the application genuinely cannot leave .NET Framework yet and I still want it on a modern deployment pipeline. That is a real situation — a Web Forms application with a rebuild scheduled for next year, or a component depending on a Windows-only COM or imaging library — and Windows containers let it be built, versioned, deployed and rolled back like everything else instead of by MSI. The costs are substantial and worth stating: images are several gigabytes rather than a couple of hundred megabytes, start-up is much slower, the host OS version and the container OS version are coupled in ways Linux containers are not, and it is more expensive to run. So I treat it as a bridge with a date in the plan, not a destination, and I would rather use it than let an unportable component justify keeping a hand-managed VM. The alternative worth comparing is leaving that component on an Azure VM and proxying to it, which is sometimes simpler and honest about what it is.

How does infrastructure as code fit into a modernization?

It is not optional, because the migration is the moment when environments multiply and drift becomes permanent. Bicep or Terraform — the choice matters far less than the rule that no human clicks in the portal — so environments are reproducible, reviewable and diffable, and so the rehearsal environment for a cutover can be created from the same definition as production. The specific value during a migration is that you will build the target environment several times: a pilot, a rehearsal, then production, plus whatever gets thrown away, and doing that by hand guarantees the rehearsal is not the thing you rehearsed. I would also put the platform baseline — networking, private endpoints, DNS, policy, diagnostic settings — into a landing zone owned by whoever owns the subscription, and let workload teams deploy into it, because networking is consistently the item that costs weeks and it usually belongs to a different team. Starting that conversation in week one rather than week twelve is one of the more reliable schedule savings available.

What does .NET Aspire add during a migration?

Mainly a coherent local development story for a mixed estate, which is exactly what a strangler-fig migration lacks. The AppHost describes the whole system — the legacy container, the new API, SQL Server, Redis, a queue — and starts it with one command, wiring connection strings and service discovery between them, so a new engineer is productive on day one instead of working through a nine-step README. It also gives a dashboard with traces, logs and metrics locally, which lowers the barrier to instrumenting the new services properly, and it produces deployment manifests for Container Apps and Kubernetes. Aspire 13.5, released 18 August 2026, added interactive AppHosts with terminal sessions and took TypeScript AppHosts to general availability, which matters for a full-stack estate where the front-end build is part of the system. What I would be careful about is treating it as an architecture: it is an orchestration and developer-experience layer, adopting it does not modernize anything by itself, and I would introduce it because onboarding and local parity are painful rather than because it is new.

How do you avoid the cloud bill becoming the story?

By making cost a design constraint with a named owner from the start, rather than a surprise at the first invoice. Practically: tag every resource with workload and owner so the bill can be attributed, set budgets and alerts before the first production workload lands, and right-size from measured usage rather than from the on-premises specification, since lifted VMs are almost always provisioned for a five-year-old peak. Then use the platform's elasticity deliberately — scale to zero for jobs and internal tools, scale in at night, serverless or Hyperscale tiers where the load is spiky — and buy reservations or savings plans once the shape is stable rather than on day one. I would also be honest in the business case that modernization is not primarily a cost-reduction exercise; the 2026 evidence on microservice estates running several times the infrastructure cost of the monolith they replaced is a useful corrective, and it is the same argument that makes the modular monolith the sensible default. Promising savings you cannot deliver is how a technically successful migration gets remembered as a failure.

Modernization is judged on cutover day, and cutover day is decided months earlier by whether the delivery pipeline can put a change in production and take it back out again in minutes. That is the actual deliverable of this unit: a system whose cost of a wrong decision is small enough that decisions can be made quickly. Every technique below — slots, revisions, canaries, expand–contract, rehearsal — is a way of buying reversibility.

The frame that reorganises everything: deploy and release are different events. Deploying is putting the bits on the platform; releasing is letting a user reach them. Legacy systems fuse the two, which is why they need Friday nights and change freezes. Separating them — with slots or revisions for the infrastructure half and feature flags for the logical half — is what makes a modernization survivable, and it is usually the first thing worth building.

Ordering: schema, code, flag

The invariant that makes zero-downtime possible: the database must be compatible with both the currently running application version and the next one, at every instant. That forces a fixed order and a fixed rule.

  1. Schema change first, and only ever backward-compatible (the expand phase from unit 03). It deploys on its own, days before the code that needs it, and it is reversible.
  2. Code second, dark: deployed to a zero-traffic revision or a staging slot, so the bits are in production before anyone can reach them.
  3. Release third, by shifting traffic and flipping flags — cheap, fast, reversible without a deployment.
  4. Contract last, a release cycle later, once query capture proves nothing reads the old shape. This is the one-way door and it gets its own change record.

Two anti-patterns to name explicitly. Database.Migrate() at application startup races between replicas during a rolling deployment, requires the application's identity to hold schema-alter permission, and turns a failed migration into a crash loop; ship an idempotent script or a migration bundle applied by the pipeline instead. And a "rollback" that requires restoring a database is not a rollback — it is an incident with a recovery-point objective.

Rollback versus roll-forward

The honest position: roll back when the previous version still works and the change is reversible; roll forward when the change touched data. Once a deployment has written data in a new shape, going back means the old code meets data it does not understand — which is exactly why expand–contract keeps the old shape readable for a full cycle. A team that has genuinely thought about this can say, per change, which category it is in, and that classification belongs in the change record rather than in someone's head at 2am.

Cutover day

For the irreversible moments — a database platform switch, a DNS move, the final proxy flip — the plan is operational, not technical, and interviewers at lead level are testing whether you have run one.

  • Rehearse at least twice against a production-sized copy, with the clock running. The number that matters at go/no-go is how long it took the last time somebody actually did it, not an estimate.
  • A written runbook with a step number, an owner and an expected duration per step — executable by someone who is not the architect, because the architect will be on the bridge call answering questions.
  • A go/no-go checkpoint partway through, with named criteria and a named decision maker. Without it, sunk cost decides, and sunk cost always says continue.
  • A rollback that is rehearsed too, time-boxed ("if we are not green by 04:00 we roll back"), and that does not depend on the migration having gone well.
  • Reconciliation before you open the doors: the counts, checksums and business aggregates from unit 08, signed off by someone from the business.
  • Hypercare: elevated monitoring, a staffed bridge, and — the detail that matters — a deliberately slower change cadence for a week, so any new incident is attributable.
Interview trap

Having no answer for "what if it goes wrong halfway through?" Candidates describe a beautiful cutover and stop at the happy path. The follow-ups an interviewer has ready: what is the last reversible moment; who decides, by what criteria, and by what time; what happens to the transactions that landed on the new system before you rolled back; how do you tell the difference between "it is slow because caches are cold" and "it is slow because it is broken"; and what does the business do for the two hours you are deciding? The credible answer names a rehearsed, time-boxed rollback, a point of no return marked in the runbook, a plan for reconciling in-flight work in both directions, and a named decision maker who is not the person executing the steps. Saying "we would fix forward" without having earned it is the wrong answer — fix-forward is a legitimate strategy only when you have deployment lead times measured in minutes to back it up.

Gotcha

Change freezes during a migration are counter-productive and very popular. The instinct — "stop deploying while we cut over" — batches changes into a bigger, riskier release immediately afterwards, and it removes the very capability you need during hypercare, which is the ability to ship a small fix in twenty minutes. What you actually want is the opposite: smaller changes, more often, with an explicit list of what is temporarily out of scope (schema contractions, anything touching the migrated boundary) rather than a blanket ban. If your organisation genuinely cannot deploy safely during a cutover window, that is the finding — the pipeline is the risk, and it needs fixing before the cutover, not a freeze wrapped around it.

Try it — 2 hours, two exercises

1. Deploy without releasing. On any app, create a second Container Apps revision (or an App Service slot) with zero traffic, verify it is healthy through its direct endpoint, then shift 5% of traffic, then roll it back to zero. Time each step.

2. Practise a rollback with data. Deploy a change that writes a new column, write some rows, then roll back to the previous version. Observe what the old code does with the new rows. Then redo it with dual-write and observe the difference.

Expected outcome

Exercise 1 shows that the traffic shift is seconds while the deployment is minutes — which is precisely why release should be a traffic and flag operation, never a deployment. That timing is the concrete backing for "deploy and release are different events".

Exercise 2 is the one that changes how you plan. Without dual-write the old code either crashes or silently drops the new field, and you will feel the difference between a reversible change and an irreversible one in your hands. That distinction — per change, written down — is the thing that lets a team roll back confidently at 2am.

Interview Q&A · delivery and cutover

How do you deploy a schema change and a code change together with zero downtime?

You do not deploy them together — you deploy them in a fixed order with a rule that makes each step reversible. The rule is that the database must be compatible with both the currently running version and the next one at every instant, because a rolling deployment has both live. So the backward-compatible schema change goes first, on its own, often days earlier: add nullable columns, add indexes online, add constraints unvalidated. Then the code deploys dark, to a zero-traffic revision or a staging slot. Then the release is a traffic shift and a flag flip, which is fast and reversible without redeploying. Then, a full release cycle later and only after query capture proves nothing reads the old shape, the contraction drops the old structure — and that step gets its own change record because it is the only irreversible one. I would also insist that migrations are applied by the pipeline as an idempotent script, not by the application at startup, because startup migrations race between replicas and require the app identity to hold schema-alter rights.

Rollback or roll forward?

It depends on whether the change touched data, and I want that classification written on the change before it ships rather than decided at 2am. If the previous version still works and nothing has been written in a shape it cannot read, rolling back is the right answer because it is fast, well-understood and does not require anyone to write code under pressure. Once new-shaped data exists, rolling back means the old code meets data it does not understand, so you either roll forward or you accept data loss — which is precisely why expand–contract keeps the old shape written and readable for a full cycle, to preserve the rollback option deliberately. Fix-forward is legitimate when your deployment lead time is genuinely minutes, because then shipping a corrected version is faster than reverting; it is not legitimate as a substitute for having a rollback path. And I would say plainly that a rollback which requires restoring a database backup is not a rollback, it is an incident with a recovery-point objective attached.

How do you run a canary deployment and know whether it is working?

Shift a small percentage of traffic to the new revision, soak, and compare the two revisions on the same metrics before widening — and the second half is the part people skip. That means telemetry tagged with the revision or version so I can compare error rate, latency percentiles and, crucially, business outcomes for the canary against the stable version rather than against yesterday. Business outcomes matter because the failure mode a canary is uniquely good at catching is the one where the service is technically healthy and quietly doing the wrong thing — quotes still returned, but 3% lower. I automate the gate so a breach shifts traffic back to zero without a human, and I soak long enough for the slow signals to appear, which for anything with caching or a scheduled component means longer than the ten minutes people default to. I also make sure the canary is a representative slice — routing by tenant rather than randomly can be better, because it produces coherent user experiences and a nameable blast radius.

Walk me through a cutover plan for a database platform migration.

Rehearsal first: at least two full runs against a production-sized copy with the clock running, because the only number worth quoting at go/no-go is how long it took the last time someone actually did it. The plan itself is a numbered runbook with an owner and an expected duration per step, executable by someone who is not the architect, since the architect will be on the bridge answering questions. It contains an explicit point of no return, a go/no-go checkpoint before it with named criteria and a named decision maker, and a rollback that is itself rehearsed and time-boxed — if we are not green by a stated time, we roll back regardless of how close we feel. Before traffic is admitted, reconciliation runs: object counts, row counts, checksums and business aggregates compared on both sides and signed off by someone from the business who would notice if they were wrong. Afterwards, hypercare — elevated monitoring, a staffed bridge and a deliberately reduced change cadence for a week so any new incident is attributable to something specific.

Should you freeze changes during a migration?

No, and I would push back on it firmly, because a freeze produces exactly the risk it is trying to avoid. Stopping deployments batches changes into a larger, riskier release immediately afterwards, and it removes the capability you most need during hypercare, which is shipping a small fix in twenty minutes. What I want during a cutover window is the opposite: smaller changes more often, with a specific, short list of what is temporarily out of scope — schema contractions, anything touching the boundary being migrated — rather than a blanket ban. If the organisation genuinely cannot deploy safely during a cutover, that is the real finding, and the pipeline is the risk that needs addressing before the cutover rather than a freeze wrapped around it. I would also note that a freeze is often a proxy for a missing capability — no canary, no revision-tagged telemetry, no fast rollback — so the productive conversation is about building those, not about the calendar.

What do you do about in-flight work at the moment of cutover?

Enumerate it explicitly before the day, because it is the category that produces the worst surprises. Typically there are four kinds: HTTP requests in flight, which drain if readiness goes false before shutdown and the shutdown timeout is generous enough; queued messages, which are safe if handlers are idempotent and the queue is the source of truth, and dangerous if the old and new consumers both read it; scheduled and batch jobs, which need to be paused explicitly before the window and resumed deliberately, since a nightly job firing mid-cutover is a classic incident; and long-running business workflows that span the boundary, like a multi-step booking a user started on the old system. The last group needs a decision per workflow: drain them by pausing new starts and waiting, migrate their state, or accept and communicate that they restart. I write that decision into the runbook per workflow type, because "we'll deal with it" reliably becomes an incident at 03:00 when someone finds three hundred half-finished bookings.

How do you keep deployments safe when two systems share a database?

By treating the schema as a published contract with multiple consumers rather than as an implementation detail of either application. Practically that means every schema change is backward compatible by default and expand–contract is not optional, since the old application will still be reading and writing while the new one deploys. It also means the schema needs a single owner and a single deployment path — one versioned artifact, applied by one pipeline — rather than each application running its own migrations, because two migration histories against one database is a reliable source of conflict. I would add contract tests that run the currently deployed version's test suite against the new schema in CI, so incompatibility is caught before deployment rather than during. And I would keep an inventory of every consumer, including the ones outside both applications — reporting tools, integrations, scheduled jobs — because those are the readers that no test suite covers and they are exactly who breaks when a column is dropped.

What metrics tell you the migration is going well?

Two groups, and I would report both to different audiences. Delivery health, for the team and the sponsor: deployment frequency, lead time for change, change failure rate and time to restore — the DORA four — plus the size of the legacy surface, measured concretely as endpoints still proxied, projects still targeting the old framework, and database objects only the legacy app uses. That last one is the honest progress metric, because it goes down only when something is actually deleted. Service health, for comparing old against new: error rate and latency percentiles per endpoint split by which implementation served it, plus business rates — quotes per hour, shipments cleared, invoices raised — because those catch the silent correctness failures that no technical metric shows. What I would not report as progress is story points, percentage complete or number of services migrated, since none of them survive contact with a stalled last 30%. If I could keep only one number it would be lead time for change, because it predicts your ability to recover from everything else.

The new system is live and something is wrong, but you are not sure what. What do you do?

Reduce the blast radius first and diagnose second, in that order. If there is a traffic weight or a flag, I take it back — shifting the canary to zero or turning the flag off is seconds, costs almost nothing if I am wrong, and buys the room to think; deciding whether it is really broken while it is broken is the classic mistake. Then I compare rather than investigate: the same endpoint on the old implementation versus the new one, on error rate, latency percentiles and business rate, using revision-tagged telemetry — that comparison usually localises the problem faster than reading logs. If the symptom is correctness rather than availability, I check whether the shadow or reconciliation data shows divergence, since that tells me whether it started with this release or existed before. Then I establish blast radius — which tenants, which routes, how many records — and communicate that before I have a root cause, because the business needs a scope far more urgently than an explanation. Root cause comes afterwards, in a blameless review, along with the question of why the canary gate did not catch it.

How do you build confidence in a cutover with a business that has been burned before?

By making the risk visible and the rehearsals real rather than by making promises. Concretely, I invite the sceptics to the rehearsal and share the timings, including what went wrong and how long the rollback took, because a rehearsal that reports only success is not believed and should not be. I sequence the programme so there are small, reversible cutovers long before the big one — a route, a job, a read-only endpoint — so the organisation accumulates evidence that we can do this and undo this. I state the rollback criteria and the decision maker in writing before the day, so nobody is asking who decides while the clock runs. And I am explicit about what could go wrong and what the impact would be, in their language: which customers, which transactions, for how long. The counterintuitive part is that naming the failure modes builds more confidence than minimising them, because a team that has enumerated the ways it could fail is visibly a team that has thought about it — and everyone in the room has previously been told "it will be fine" by someone who had not.

The mental model that matters: agents change the cost curve of the mechanical work, not the cost curve of the verification. Retargeting projects, converting packages.config to PackageReference, replacing well-known API patterns, generating Dockerfiles and Bicep, fixing hundreds of near-identical compile errors — all of that gets dramatically cheaper. Deciding whether the resulting diff preserves behaviour does not, because that requires evidence the agent cannot manufacture. So the bottleneck moves, and a lead's job moves with it: less time producing the change, more time building the evidence that makes a change reviewable. Where AI helps most on a legacy estate: comprehension, not production

The counter-intuitive finding from real programmes is that the biggest win is not code generation. It is collapsing the time to understand: what does this 900-line procedure do, what calls this assembly, what are the ten distinct behaviours of this Web Forms page, what would break if this column were nullable. On Meridian that turned a two-week archaeology exercise into two days — with the essential caveat that every answer was a hypothesis to be confirmed against a characterization test or a query capture before anyone acted on it.

The corresponding trap is that a fluent explanation feels like knowledge. When an agent says "this status code appears to represent a customs hold introduced for the 2019 regulation change", that is a plausible story generated from patterns, not a fact recovered from history. The discipline is unchanged from unit 02: behaviour is an empirical question, and the agent has made forming hypotheses cheap, not made verification unnecessary.

Governance a lead is expected to have thought about

  • Provenance. Agent-authored commits should be identifiable, so a later incident can be correlated with how the code was produced. This is a data question, not a blame question.
  • Review load. An agent can produce diffs faster than humans can review them, and unreviewed volume is the actual new risk. Cap PR size, and treat "we merged it because the build was green" as an incident waiting to happen on a codebase whose test suite you do not fully trust.
  • Data boundaries. Legacy code contains connection strings, embedded credentials, customer names in test fixtures and sometimes regulated data. Know what leaves your tenancy, and use enterprise controls rather than personal accounts.
  • Skill erosion. If the agent does the whole port, nobody on the team has learned the codebase — and you still have to operate it at 3am. I deliberately assign the highest-risk slice to a human pair.
  • Measurement. Report the same metrics as before: lead time, change failure rate, escaped defects. If change failure rate rises after adopting agents, the verification is not keeping up, and that is the signal to slow down.
Interview trap

Both extremes are wrong answers, and interviewers are listening for which one you fall into. "AI will do the migration for us" ignores that the constraint was never typing — it was verification, coordination and the coexistence period, none of which an agent removes. "I don't trust AI for legacy code" ignores a tool that Microsoft has shipped to GA specifically for this problem and that genuinely collapses the mechanical work, and it reads as incuriosity. The calibrated answer is a division of labour: agents own the mechanical, compiler-verifiable work and the comprehension pass; humans own sequencing, the definition of done, the acceptance of behaviour changes, and the cutover decision. Then add the sentence that shows you have actually run this: "the binding constraint becomes review capacity and test coverage, so I invest in characterization tests first — an agent's diff is only as safe as the oracle it can be checked against, and on an untested codebase its confidence is indistinguishable from a guess."

Gotcha

Agents will happily "fix" a failing test by editing the test. On a characterization suite that is catastrophic and almost invisible in a large diff: the snapshot is updated, the build goes green, and the tripwire you built in unit 04 has been quietly disarmed. Defend it mechanically rather than by instruction — put snapshots and test expectations behind a CODEOWNERS rule requiring human approval, add a CI check that fails when a migration PR modifies both source and snapshot files, and state the rule in AGENTS.md as well. The same applies to warnings-as-errors and analyzer suppressions: an agent under pressure to make the build pass will add #pragma warning disable, and that too should require explicit sign-off.

Try it — 2 hours, two exercises

1. Run an agent-assisted upgrade with an oracle. Take a small .NET Framework project, write three or four characterization tests at its outermost boundary first, then let the modernization agent upgrade it. Note which of your tests broke and whether the agent's fixes were behaviour-preserving.

2. Test the comprehension claim. Ask an agent to explain a piece of legacy code you already understand deeply. Grade the answer: what did it get right, what did it get plausibly wrong, and how would you have detected the wrong part if you had not already known?

Expected outcome

Exercise 1 usually shows the agent handling the mechanical work well and producing one or two subtle behaviour changes — commonly around string comparison, nullability or exception types. The point is not that it erred; it is that you could tell, because you built the oracle first. Without the tests, that same run would have looked like a complete success.

Exercise 2 is the one that calibrates you. The answer is typically 80% right, fluent, and wrong in a specific way that reads exactly like the correct parts — usually an invented rationale for a historical quirk. Being able to describe that failure mode concretely in an interview is far more convincing than a general statement about hallucination.

Interview Q&A · AI-assisted modernization

How would you use AI tooling on a .NET modernization?

For the mechanical work and the comprehension pass, with humans owning judgment and verification. GitHub Copilot app modernization has been GA for .NET since September 2025 and runs in Visual Studio 2026, VS Code, the Copilot CLI and on GitHub.com; it assesses a solution, proposes an upgrade plan, applies transformations, then builds and fixes the errors it caused in a loop. That is genuinely good at retargeting projects, moving packages.config to PackageReference, replacing known API patterns, and generating containerization and infrastructure scaffolding — anything where a compiler is the oracle. It is also very good at the archaeology: summarising a long stored procedure or an unfamiliar page lifecycle, which collapses a two-week comprehension exercise into days. What I keep with humans is sequencing, the acceptance of any behaviour change, and the cutover decision. And I would sequence the investment deliberately: build the characterization suite first, because an agent's diff is only as safe as the oracle it can be checked against.

What are the risks of agent-driven migration and how do you control them?

Three, and they are all about verification rather than about the model. First, plausible wrongness: an agent will produce a fluent explanation of an undocumented business rule that is simply invented, so I treat every explanation as a hypothesis to be confirmed against captured behaviour rather than as documentation. Second, review capacity: agents produce diffs faster than humans can read them, and unreviewed volume is the actual new risk, so I cap PR size, require the characterization suite to be green with zero snapshot changes, and refuse "the build was green" as a review. Third, silent disarming of the safety net — an agent asked to make a build pass will edit a test, update a snapshot or suppress a warning — so I protect snapshots and analyzer configuration with CODEOWNERS and a CI rule that fails any PR touching both source and expectations. I would add a governance point: agent-authored commits should be identifiable so an incident can be correlated with how the code was produced, and the highest-risk slice should still be done by a human pair, because someone has to understand the system at 3am.

Does AI change the modernization strategy itself?

It changes the economics of some steps enough to shift decisions, but not the shape of the plan. The mechanical port gets cheap, which makes previously marginal work worth doing — upgrading the long tail of small services, converting a large JavaScript codebase to TypeScript, writing the hundreds of adapters an anti-corruption layer needs. It also makes the comprehension phase far cheaper, which improves the quality of the assessment. What it does not touch is everything that made modernization hard in the first place: the coexistence period, the shared database, the undocumented consumers, the cutover, the organisational sequencing and the funding. So the strategy is unchanged — strangler fig, expand–contract, safety net first — but the ratio shifts, and more of the programme's cost and calendar sits in verification and coordination than in writing code. If anything, that strengthens the argument for investing early in characterization tests and telemetry, because those are now the bottleneck rather than the overhead.

An agent produced a 3,000-line migration PR. What do you do?

Do not review it, and do not merge it. A diff that size cannot be meaningfully reviewed, so approving it means the build is the only reviewer, and on a legacy codebase the build is not a sufficient oracle. I would send it back with instructions to split it along the boundaries that make each piece independently verifiable — one project, one pattern, one mechanical transformation per PR — and I would fix the process rather than just this instance, by putting the size limit and the split rule into the repository's standing agent instructions and, ideally, into a CI check. I would also look at what the PR mixes: the common failure is a diff that retargets a project and refactors it at the same time, so behaviour changes hide among mechanical ones. Separating "change structure" from "change behaviour" into different commits is an old rule that matters far more now that producing both at once is free.

How do you stop an agent from breaking your characterization tests by editing them?

Mechanically, because instructions alone will not hold. The snapshots and expected-output files go behind a CODEOWNERS rule that requires a specific human approval, and CI has a check that fails any pull request touching both production source and snapshot files in the same change — legitimate snapshot updates are their own PR with a written justification. The same protection covers analyzer configuration, warning suppressions and the architecture fitness tests, since those are the other things an agent will edit to make a build pass. I also state the rule in the repository's agent instructions file, not because that is sufficient but because it makes the intent explicit and reduces the number of times the guard actually fires. And I would treat a bulk re-approval of snapshots with the same scrutiny as a production change, because it is one — it is a statement that the system's behaviour changed and somebody accepted it.

Where does AI help most on a legacy estate?

Comprehension, ahead of code generation, and that surprises people. The single most expensive thing about a legacy system is that nobody knows what it does, and the time to get an initial map — what this procedure does, what calls this assembly, what the distinct behaviours of this page are, what would break if this column became nullable — drops from weeks to days. That improves the assessment, which improves the sequencing, which is where the money actually is. Second most valuable is the tedious, highly patterned work that surrounds a migration rather than being the migration: turning a corpus of captured request/response pairs into characterization tests, writing hundreds of small mapping functions for an anti-corruption layer, generating the boilerplate for infrastructure as code. Third is the mechanical port itself. What I would not use it for is deciding what to migrate and in what order, because that depends on organisational facts it cannot see, and it will produce a confident, plausible plan regardless — which is more dangerous than producing nothing.

How do you measure whether AI tooling is actually helping?

With the same delivery metrics I would use anyway, because the failure mode is throughput going up while quality goes down. Lead time for change and the rate at which the legacy surface shrinks tell me whether we are moving faster; change failure rate, escaped defects and rework tell me whether the speed is real. If throughput rises and change failure rate rises with it, the verification is not keeping up and the correct response is to slow down and invest in tests, not to attribute the failures to the tool. I would also watch review latency and PR size, since the first thing to break is the human bottleneck, and I would track how much of the diff volume is agent-authored so the correlation is visible rather than anecdotal. What I would avoid is measuring acceptance rate or lines generated, which measure activity rather than outcome, and which reliably go up while nothing improves.

Should the team learn the legacy system, or let the agent handle it?

Learn it, deliberately, because you still have to operate it. If an agent performs the whole port, the organisation ends up with a modern codebase nobody understands, which is the same problem it started with in a newer syntax — and the moment that matters is the 3am incident, when there is no time to ask an agent to explain a subsystem and verify the answer. So I use agents to accelerate learning rather than to replace it: the comprehension pass produces hypotheses that a human confirms against captured behaviour, which is a much faster way to learn a system than reading it cold. And I deliberately assign the highest-risk slices — the rating engine, the billing path — to a human pair, so that at least two people carry a real mental model of the parts that will hurt most. There is also a retention argument: engineers who learn nothing on a two-year programme leave, and they take the little context that exists with them.

What would you put in a repository's agent instructions for a migration?

The things that are cheap to state and expensive to discover. The target framework and an explicit prohibition on introducing versions that are already end-of-life, since a model's training data will happily suggest .NET 8. The rule that structural and behavioural changes never share a commit. The protected paths — snapshots, analyzer configuration, architecture tests — that must not be modified. The project-specific pitfalls that a general model has no reason to know: ordinal string comparison because ICU is not NLS, TimeProvider instead of DateTime.Now, IANA time-zone identifiers, no new NuGet packages outside central package management. And a definition of done that is machine-checkable: build clean with warnings as errors, characterization suite green with zero snapshot changes, fitness tests green, diff under a few hundred lines. I would treat that file as a living artifact reviewed like code, because every incident it prevents twice pays for the time spent writing it — and it doubles as onboarding documentation for humans.

How do you handle a stakeholder who thinks AI makes the migration a three-month job?

By agreeing about the part that got faster and being precise about the part that did not. I would say plainly that the mechanical work — retargeting, package upgrades, API replacement, boilerplate — genuinely has collapsed, and I would demonstrate it on a real project rather than argue about it. Then I would show where the calendar actually goes: the coexistence period during which both systems are live, the data migration and its reconciliation, the undocumented consumers, the cutover rehearsals, and the verification needed to make any of it safe — none of which an agent removes, and all of which are constrained by the business's tolerance for risk rather than by engineering throughput. The persuasive move is to offer evidence instead of an argument: take one representative slice, do it end to end with agent assistance, and measure it, then multiply. That converts the disagreement into a number both sides can inspect, and if I am wrong about the multiplier, I would rather find out on one slice than in a committed three-month plan.

Team shape: Conway's law is not optional

The system you get will mirror the communication structure you have. So the organisational anti-pattern is the obvious one: a separate "modernization team" alongside a "legacy team". It fails predictably in three ways — the modernization team lacks the domain knowledge that only the legacy team has; the legacy team is measured on uptime and therefore rationally resists change; and the interface between them becomes a queue. Worse, the people who understand the system are the ones you have told, implicitly, that their expertise belongs to the past. They leave, and they take the requirements with them.

What works: the team that owns the system owns its modernization, with a small platform or enabling group supplying the paved road — pipeline, telemetry, templates, the proxy, the migration patterns — so each product team does not solve the same problems eight times. That is the Team Topologies shape (stream-aligned teams plus an enabling team), and naming it signals you have thought about the org, not just the code.

The architecture the organisation can actually operate

The 2026 correction is worth stating plainly because it inverts the advice of five years ago: roughly 42% of organisations that adopted microservices have consolidated at least some services back into larger deployable units, and infrastructure costs for microservice estates commonly run several times those of the monolith they replaced. Cost, not scalability, has become the binding constraint, and the modular monolith is now the default landing zone — one deployable unit with enforced internal boundaries, from which you extract a service only when a specific pressure justifies it.

For modernization that is liberating, because it removes the most expensive false requirement in the field. The migration target for Meridian is not forty services; it is a modular monolith on .NET 10 with clear module boundaries, one database with enforced ownership per module, and two or three genuinely independent services where there is a real reason — the PDF renderer because it is CPU-spiky and isolatable, the customs integration because it has a different availability profile and a different release cadence. Extraction stays available as a later option, which is the whole point of enforcing the boundaries in the first place.

Knowing when to stop

A mature programme ends with a documented residual, not a claim of completeness. Stop modernizing a workload when it is supported, deployable, observable and understood — those four properties, not "modern". Chasing architectural purity past that point is where modernization becomes a hobby, and the tell is a backlog item nobody outside the team can explain the value of. Write down explicitly what you are not modernizing and when it will be reviewed; that list is a sign of judgment, not of failure.

Interview trap

Answering the "how do you get buy-in?" question with technical arguments. Candidates reach for maintainability, code quality and developer experience, and every one of those is an internal concern that a CFO has no way to price. The answers that move budget are risk with a date and an invoice ("SQL Server 2016 left support on 14 July 2026; we either buy Extended Security Updates or fail the next audit"), flow translated into money ("a pricing change takes 34 days; here is what a week of that is worth"), and capability with a customer attached ("we cannot ship real-time tracking, and two deals cited it"). The second half of the answer matters just as much: land the first visible win inside one quarter, because credibility is the currency that funds the unglamorous middle. And name the anti-pattern — a separate modernization team — since interviewers use this question to find out whether you have run a programme or only designed one.

Gotcha

The morale curve. Modernization has a long, unglamorous middle where both systems are live, the work is adapters and shims, and nothing looks impressive in a demo. That is when your best engineers — the ones with options — leave, and they are precisely the ones holding the undocumented context. Manage it deliberately: rotate people between migration work and feature work rather than assigning anyone to shims for a year, celebrate deletions as loudly as launches (a "lines removed" number in the sprint review is surprisingly effective), make sure modernization work is visible in promotion cases, and give the hardest slices to people who want to grow rather than to whoever is available. A programme that burns out the people who understand the system has converted a technical problem into an unsolvable one.

2. Draw Conway. Sketch your current team boundaries and your current system boundaries side by side. Then sketch the target architecture and ask which team boundaries it implies. If nobody is planning to change the org chart, the target architecture will not happen.

Expected outcome

Exercise 1 is hard in a way that is diagnostic: if you cannot fill the risk section with dates and the flow section with numbers, you do not yet have a fundable case, and the next task is measurement rather than planning. The page also becomes the artifact you reuse every time the sponsor changes, which on a two-year programme is at least once.

Exercise 2 usually reveals that the proposed architecture requires a team structure nobody has agreed to — most commonly a target of independently deployable services with a single shared team, or a shared database with teams who want autonomy. Spotting that before the plan is committed is exactly the kind of judgment a lead interview is probing for.

Interview Q&A · sequencing, funding, people

How do you get buy-in for modernization from a business that sees no benefit?

By translating it out of engineering language into risk, flow and capability, each with a date or a number attached. Risk: name the unsupported components and their end-of-support dates and the cost of the alternative — Extended Security Updates are deliberately priced above the cost of migrating, and audits and cyber-insurance renewals now ask directly about unsupported software. Flow: measure the current lead time for a routine change and let the business price a week of it; a 34-day median on a pricing change is a number a commercial director can act on. Capability: name a specific thing the business wants and cannot have, ideally with a lost deal attached. Then the tactical half, which matters as much: deliver a visible win inside the first quarter, because credibility is what funds the unglamorous middle, and pick something users can see rather than something only the team appreciates. What I would avoid is arguing from code quality or developer experience, because those are real and unpriceable, and using them signals that I have not done the translation work.

How should a modernization be funded?

As a standing allocation of capacity rather than a project with an end date, because that determines whether it survives a leadership change. A project budget creates a line item that can be cancelled, and it will be cancelled at the halfway point where cost is maximal and delivered value is minimal — leaving you running two systems, which is the worst outcome available. A standing allocation, typically 20 to 30% of every team's capacity, has no line item to cut, only a policy to change, and it tells the truth: modernization is the ongoing cost of owning software, not a one-off. The failure mode I watch for is silent erosion under delivery pressure, so I make the allocation visible and report on it, and I attach a metric — the shrinking legacy surface — so a quarter where it did not move is a conversation rather than a discovery. I would accept a fixed programme budget only where the driver is genuinely bounded and dated, like a data-centre exit or an end-of-support cliff, and even then I would ask what happens to the residual afterwards.

How do you structure teams for a modernization?

The team that owns the system owns its modernization, supported by a small enabling or platform group. The anti-pattern I would argue hard against is a separate modernization team working alongside a legacy team, because it fails in three predictable ways: the modernization team lacks the domain knowledge that only the incumbents have, the legacy team is measured on stability and therefore rationally resists change, and the interface between them becomes a queue. It also sends the message that the people who understand the system are the past, which is how you lose them and their undocumented context at the worst possible moment. What the enabling group provides is the paved road — pipeline, telemetry, templates, the proxy, the migration patterns, the characterization test harness — so eight product teams do not each solve the same problems differently. And I would take Conway's law seriously in the other direction: if the target architecture implies team boundaries nobody intends to create, the target architecture is not going to happen, and it is better to find that out while it is still a diagram.

Would you break the monolith into microservices as part of the modernization?

Almost certainly not, and this is one place where the industry advice has genuinely reversed. Around 42% of organisations that adopted microservices have consolidated at least some services back into larger deployable units, and microservice estates commonly cost several times what the monolith they replaced cost to run — cost, rather than scalability, has become the binding constraint. So my default target is a modular monolith: one deployable unit with module boundaries enforced by the build and by database permissions, from which a service is extracted only when there is a specific pressure that justifies it, such as a different scaling profile, a different availability requirement, a genuine compliance boundary or an independent release cadence a separate team needs. That preserves the option to extract later at low cost, which is the actual value of the boundary work, while avoiding a distributed system's operational burden during the period when the organisation is already absorbing a runtime, data and hosting migration. Doing a decomposition and a modernization simultaneously means that when something breaks you cannot tell which change caused it — and that ambiguity is what kills programmes.

How do you keep a two-year programme from losing momentum?

By making progress visible in the terms other people care about, and by protecting the people doing it. Visibility means a metric that only moves when something is actually finished — the shrinking legacy surface, counted as endpoints still proxied, projects still on the old framework, database objects only the legacy app uses — rather than percentage complete, which can sit at 80% for a year. It also means alternating risk work with value work so there is something for the sponsor to see every quarter, not just something for the auditors. Protecting people means rotating them between migration and feature work rather than assigning anyone to write shims for twelve months, celebrating deletions as loudly as launches, and making sure this work is visible in promotion cases, because otherwise the ambitious engineers route around it. And I would re-tell the story regularly, because sponsors change and the new one did not attend the original meeting — the one-page case is a living artifact, not a one-off deck.

The legacy team resists the migration. What do you do?

Assume they are behaving rationally and find out what they are optimising for, because they usually are. Most often they are measured on the stability of a system they know intimately and are being asked to help replace it with something they will be blamed for when it breaks and will not own afterwards. Sometimes it is more personal: their expertise is being framed as obsolete, and nobody has told them what their role is on the other side. Both are fixable, and both are fixed by changing incentives rather than by persuasion — give them ownership of the modernization of their own system, make their knowledge visibly central to it, invest in their skills on the new stack early and publicly, and change what they are measured on so that shrinking the legacy surface counts. Where the resistance turns out to be about protecting job security through indispensability, that is a management conversation and I would not pretend it is a technical one. What I would not do is route around them, because the requirements are in their heads, and a programme that treats them as an obstacle will discover that at the worst possible moment.

How do you handle the skills gap on the team?

By treating it as a deliverable of the programme rather than a precondition, since waiting for everyone to be ready means never starting. Concretely: pair a small group with strong modern .NET experience alongside the people who know the domain, and rotate rather than concentrate, so knowledge spreads instead of forming a new bottleneck; use the first end-to-end slice as the teaching vehicle, since one real slice teaches more than any course; and invest in a paved road so the number of new things any individual must learn is bounded — templates, a working pipeline and a reference implementation do more for adoption than training does. I would also be explicit that this cuts both ways: modern .NET engineers do not know the domain, and the domain is the harder half. Where there is a genuine specialist gap — Kubernetes, a database platform move — I would rather buy that expertise temporarily and pair it with permanent staff than have the team learn it under deadline. And I would say plainly that a modernization which leaves the team unable to operate the result has not succeeded, whoever wrote the code.

How do you know when to stop modernizing?

When each workload is supported, deployable, observable and understood — those four properties, not "modern". Supported means nothing is past end of support. Deployable means a change can reach production in hours without a maintenance window. Observable means you can tell what it is doing without attaching a debugger. Understood means at least two people can explain it and its behaviour is captured in tests. Past that point, further work needs its own justification like any feature, and continuing on architectural taste alone is where modernization becomes a hobby — the tell is a backlog item nobody outside the team can explain the value of. I would also end the programme with an explicit written residual: what we chose not to modernize, why, and when it gets reviewed. That list is evidence of judgment rather than of incompleteness, and it is the artifact that stops the same discussion restarting from zero in eighteen months.

Halfway through, the business asks you to stop and ship features instead. What do you say?

First I find out whether it is a pause or a cancellation, because the responses are different and people rarely say which they mean. Then I make the halfway position explicit, since it is the worst place to stop: two systems, two deployment paths, two sets of on-call knowledge, and the coexistence scaffolding still costing money. I would present the options with honest costs — finish the current slice and pause at a clean boundary, which is usually weeks; pause indefinitely and accept the carrying cost of the intermediate state, with a number attached; or stop permanently and delete the new path, which is legitimate but should be a decision rather than a drift. I would also point out that a well-run strangler fig is designed to be pausable at slice boundaries, so if we are mid-slice the cheapest answer is to finish it. And I would not treat the request as an attack: if the business genuinely needs features now, the right answer may well be to slow to a lower standing allocation rather than to argue, provided the risk items with hard dates are carved out and protected.

What is the most common non-technical reason these programmes fail?

No single owner with both the authority and the endurance to see it through. Modernization spans teams, budgets and quarters, so it needs someone who can make trade-offs across all of them and who is still there in eighteen months; when it is owned by a committee, every hard decision — which workloads to retire, which team absorbs the coexistence pain, when to accept a behaviour change — is deferred, and deferred decisions are what turn a two-year plan into a five-year one. Closely related is the funding shape, since a project budget guarantees a cancellation review at the point of maximum cost, and the separate-modernization-team structure, which guarantees that the people with the knowledge are not the people with the mandate. If I had to name one leading indicator, it would be whether anyone can tell me, without checking, what we decided not to modernize and why. A programme that can answer that has an owner; one that cannot is being run by momentum, and momentum runs out.

Architecture & ecosystem decisions

When should modernization stop at "supported" rather than continue to "modern"?

Whenever the workload's cost of change is not actually constraining the business. A stable component that changes twice a year, has an owner, is on a supported runtime and is understood by two people does not need an architecture; it needs a review date. The mistake is treating architectural consistency as an end in itself — spending a quarter making a rarely-touched batch job match the reference architecture buys nothing that anyone outside the team can name. My test is the four properties: supported, deployable, observable, understood. If a workload has all four, further work competes with features on equal terms and usually loses, correctly. Being able to say that in an interview is a differentiator, because it signals you allocate effort by value rather than by discomfort.

How do you decide between fixing the architecture and fixing the delivery pipeline first?

Pipeline first, almost always, and I would defend that even when the architecture is visibly worse. The pipeline is what makes every subsequent change cheap and reversible: without fast, safe deployment and the ability to roll back, every architectural improvement is a high-stakes event, so the team makes fewer, bigger, riskier changes — which is the same dynamic that produced the legacy system. With a good pipeline plus telemetry and a test net, even a bad architecture becomes tractable, because you can change it in small steps and observe the effect. There is also an organisational argument: pipeline improvements produce a visible result in weeks, which buys the credibility that funds the slower architectural work. The exception is when a specific architectural defect is actively preventing safe deployment — in-process session state, a shared mutable singleton, a single deployable everyone must coordinate on — in which case fixing that defect is the pipeline work.

Event-driven architecture as part of a modernization: yes or no?

Selectively and late, never as the headline. Messaging genuinely solves specific problems — decoupling a slow or unreliable integration, smoothing spiky load, fanning out to consumers you do not want to know about — and where one of those problems exists, introducing a queue is a good change with a clear before and after. What I resist is adopting event-driven architecture as a target state, because it converts synchronous, debuggable, transactionally consistent flows into asynchronous ones with eventual consistency, ordering concerns, poison messages, idempotency requirements and a much harder debugging story, on a team that is already absorbing a runtime and hosting migration. If we do introduce it, I want the transactional outbox pattern from day one so a message and its database change cannot diverge, idempotent handlers because at-least-once delivery is the norm, and a dead-letter strategy with an owner. And I would introduce it on one flow with a named problem rather than as a platform decision.

Do you modernize the API contract at the same time as the implementation?

No — separate them, because they have different consumers and different risk profiles. Changing the implementation behind a stable contract is verifiable: a parallel run tells you whether behaviour is preserved. Changing the contract requires every consumer to move, which is a coordination problem measured in quarters and often involving people outside your organisation. Doing both at once means that when a consumer breaks, you cannot tell whether it is the new implementation or the new contract, and the blast radius is everyone. So the sequence is: keep the contract, replace the implementation, prove equivalence, then version the contract deliberately with a deprecation period and a measured migration of consumers. The exception is when the old contract is itself the obstacle — if it leaks the legacy model so badly that the new implementation cannot be sane behind it, then an anti-corruption layer at the boundary lets the new internals be clean while the old contract survives outside.

Security & compliance

What security improvements does a modernization make available almost for free?

Four, and I would put them in the plan explicitly because they are the easiest wins the programme will ever have. Managed identity everywhere, which removes passwords and connection-string secrets entirely along with their rotation and their appearances in pipeline variables and screenshots. A supported runtime and OS, which is the difference between patchable and unpatchable and is usually the audit finding that funded the work. TLS and transport defaults that are modern by construction — Microsoft.Data.SqlClient defaults to encrypted connections, and modern base images ship sane cipher configuration. And a real software bill of materials, because an SDK-style project with central package management and a lockfile can answer "do we ship this vulnerable package?" in minutes, which is now a regulatory question in several jurisdictions rather than a hygiene one. I would also add secret scanning and dependency scanning to the pipeline while it is being built, since retrofitting them later means triaging years of accumulated findings at once.

How do you handle a legacy authentication system during a migration?

In two stages, because trying to change identity and everything else simultaneously is a common way to break the whole programme. Stage one preserves it: whatever the legacy app uses — forms authentication, Windows authentication, a home-grown cookie — is shared with the new application, via a shared Data Protection key ring and the OWIN interop format, or via the System.Web adapters' remote authentication where the legacy app remains the source of identity. That is scaffolding, and it has all the fragility scaffolding has, particularly around key rotation. Stage two replaces it: move both sides to OIDC against Entra ID or another identity provider, so identity becomes a token issued by a third party and neither application needs to understand the other's cryptography. I would sequence stage two once the coexistence mechanism is proven but before the migration is finished, because it removes a whole class of intermittent incidents. And I would treat password storage as its own migration: if the legacy store uses a weak hash, you rehash on next successful login rather than forcing a global reset.

What compliance obligations should shape a modernization plan?

The ones with dates and the ones with data-location constraints, because those change the architecture rather than the paperwork. Support status is the first: unsupported components are increasingly a direct finding in ISO 27001 and PCI audits and a question on cyber-insurance renewals, which is precisely why end-of-support dates make such effective funding arguments. Data residency and sovereignty decide Azure regions and sometimes rule out managed services, so that question belongs in week one, not at deployment. Audit and retention requirements decide whether you can retire data as part of the migration and whether the new system must preserve an audit trail the old one produced as a side effect — which is a requirement people discover after the old system is gone. Where products are sold into the EU, the Cyber Resilience Act's vulnerability handling and reporting duties push you toward a queryable release inventory and a real SBOM, both of which are much cheaper to build during the modernization than after. And the general principle: migrating data is the cheapest moment to delete data you should not be keeping.

Performance & debugging

The new implementation is slower than the legacy one. How do you find out why?

Compare rather than profile first, because the comparison localises the problem far faster. I look at the same endpoint on both implementations with revision-tagged telemetry — latency percentiles, not averages, since the interesting failure is usually in the tail — and I check whether the difference is in the application, in the database or in the network between them, which distributed tracing answers directly. In a .NET migration the usual suspects are specific: a chattier data access layer whose round trips were hidden by a LAN and are now visible over a managed link, an Include-driven cartesian explosion that a small development dataset never showed, thread-pool starvation from sync-over-async code that stopped deadlocking when the SynchronizationContext disappeared, missing connection resilience causing retries, or a plan regression after a compatibility-level change. If nothing shows, then I profile properly — dotnet-counters and dotnet-trace in production, or a continuous profiler — rather than guessing. And I would say explicitly that "it's slower" needs a percentile and a comparison before it is a problem statement at all.

How do you debug a problem that spans the legacy and the new system?

With one trace id that survives the boundary, which is a thing you have to build before you need it. Modern .NET propagates W3C traceparent by default, the reverse proxy forwards it, and there is OpenTelemetry instrumentation for .NET Framework, so a request through the proxy into the legacy application and back can appear as a single trace — that alone answers most cross-boundary questions in minutes rather than hours. Beyond tracing, I want the same correlation id on structured logs from both sides, the flag and revision state emitted on the span so I can tell which code path served the request, and clocks synchronised, since comparing timestamps between systems with a few seconds of drift produces confidently wrong conclusions about causality. When it is a correctness problem rather than an availability one, the shadow-run comparison data from unit 04 is usually the fastest route, because it tells me whether the divergence is new or pre-existing. And I would make sure the legacy side is instrumented before the first route moves, because retrofitting it during an incident is not possible.

How do you performance-test a migration when you cannot replicate production?

By replicating the parts that determine performance rather than the whole environment, and by being explicit about what the test does not cover. Data cardinality matters most, so I test against a restored or generated database at production scale, because almost every failure in this space is cardinality-dependent and a small dataset shows none of them. Traffic shape matters next: I replay captured production traffic rather than synthesising a uniform load, since real traffic is bursty and skewed and the tail is where the failures are. Where a full-scale environment is genuinely unaffordable, I would rather test one representative slice at full scale than everything at 10%, and I would supplement it with production techniques — shadow traffic to the new implementation, and a canary that compares percentiles between revisions on real load. I would also state the residual risk honestly rather than implying the test was conclusive, because a load test that nobody believes is worse than none: it produces false confidence at exactly the go/no-go moment.

Tooling & versions

What are the version facts you would want at your fingertips today?

.NET 10 is the current LTS, released 11 November 2025 and supported to 14 November 2028, and — the fact that matters most this quarter — .NET 8 and .NET 9 both leave support on 10 November 2026, so .NET 8 is no longer the conservative choice. SQL Server 2025 went GA on 15 November 2025 with native vector and JSON types, regex and change event streaming, while SQL Server 2016 left extended support on 14 July 2026 with ESUs available to July 2029. Windows Server 2016 goes end of support on 12 January 2027. TypeScript 7.0 shipped on 8 July 2026 with the Go-native compiler, 8–12× faster, but no stable programmatic API until 7.1. Node.js 24 is Active LTS and the release model changes in October 2026 to one calendar-aligned major a year, all LTS. GitHub Copilot app modernization has been GA for .NET since 22 September 2025. And on the tooling that disappeared: Data Migration Assistant retired 16 July 2025, and the Azure Data Studio SQL migration extension retired 28 February 2026.

Which tools would you actually run in the first week of a modernization?

Five, and they take about a day between them. AppCAT — Azure Migrate application and code assessment for .NET — against the whole solution with a chosen Azure target, for portability and cloud-readiness findings. The .NET Upgrade Assistant in analyse mode per project, for the retargeting picture. dotnet list package with --outdated, --deprecated, --vulnerable and --include-transitive, because the dependency graph usually sets the schedule. Query Store enabled on the database with a capture window started, since you cannot get that time back and every later decision wants it. And whatever telemetry gets page-level and endpoint-level usage counts, because usage data is what converts a rebuild into a partial retirement. I would deliberately not run anything that produces a document — the output of week one is a ranked blocker list with owners and a set of running captures, not a report.

How do you keep dependencies current after the migration, so this never happens again?

By making the upgrade a routine rather than an event, which is the only durable answer. Automated dependency update pull requests on a schedule, small and frequent, with CI trusted enough that a green build is meaningful — that last clause is the load-bearing one, and it is why the test investment from unit 04 keeps paying. Central package management so versions are declared in one place and drift is impossible, a lockfile so builds are reproducible, and an annual runtime bump treated as a scheduled maintenance item with a date in the roadmap rather than as a project. Then a fitness function that fails the build when anything targets an out-of-support framework, so the ratchet is enforced by the machine rather than by memory. And the organisational half: the standing capacity allocation from unit 13 does not end when the migration does, because the reason this system became legacy was that nobody was paid to keep it current. A team that can upgrade a major version in a week has genuinely modernized; a team on the newest runtime that would need six months to move again has not.

Legacy reality

What do you do about the component that nobody can modernize?

Isolate it, wrap it, and give it a review date rather than pretending it will be dealt with. Concretely: put an interface in front of it so nothing else depends on its shape, run it in the smallest possible container of its own — a Windows container, a dedicated VM, an out-of-process service behind a queue — so its constraints do not dictate the rest of the architecture, and make sure the boundary is well tested so it can be replaced later without archaeology. Then be explicit in the plan that this is a retained item with a named owner and a date, because unowned exceptions are how a modernized estate quietly becomes legacy again. I would also ask the question people avoid: what would it take to retire it entirely, and what is the business actually getting from it? Surprisingly often the answer is that it serves one report for one team, and the cheapest modernization available is a conversation rather than an engineering project.

How do you deal with business logic that only exists in stored procedures or, worse, in an Excel file?

Treat it as a source of truth to be captured, not as an embarrassment to be eliminated on sight. The first task is characterization: capture inputs and outputs from real usage so I have an executable description of what it does before anyone touches it, and use a parallel run if the calculation is financially material. Then decide deliberately where the rule should live, and be honest that "in the database" is sometimes the right answer for genuinely set-based rules. The Excel case is more common than people admit and needs a different move: find out who maintains it and why, because a spreadsheet in the finance team usually exists because the system could not express something they needed, and reimplementing it without solving that will simply produce a second spreadsheet. What I would insist on either way is that the rule ends up in exactly one place with a test, since the truly dangerous state is the same rule implemented in the procedure, the application and the spreadsheet, all slightly differently — which is what you almost always find.

What surprises people most about a real modernization?

How much of it is not code. The engineering is bounded and mostly known; the calendar goes into finding undocumented consumers, negotiating with teams who own the network or the database, waiting for a business cycle to complete so a capture window is valid, coordinating with external partners who integrate against you, and getting decisions made about behaviour changes nobody wants to own. The second surprise is that the last 20% takes as long as the first 80%, because the easy routes move first and what remains is everything with deep coupling or unknown behaviour. The third is how much of the risk is in the data rather than the code — schemas, collations, encodings, time zones, and the rows that violate constraints nobody enforced. If I could give one piece of advice to a team starting, it would be to begin the data track and the undocumented-consumer hunt in week one, in parallel with everything else, because those are the two things that cannot be compressed later.

Judgment & scenarios

How would you guide a team through their first strangler-fig migration?

By making the first slice deliberately small, end-to-end and unglamorous, and by treating it as a teaching exercise rather than as delivery. It should traverse every layer — browser, proxy, new service, database, pipeline, telemetry — so the team builds the whole mechanism once on something recoverable, and it should be something users can actually see, so the organisation gets evidence early. I would pair the people who know the domain with the people who know the modern stack rather than splitting the work by expertise, and I would write down the patterns we used as we went, because the second slice should be done by a different pair using that write-up. I would also set the expectation explicitly that the first slice takes disproportionately long and that this is correct, since we are building the road as well as travelling it. And I would insist on the deletion step actually happening in the same sprint, because the habit that makes strangler figs work is finishing, and a team that skips it once will skip it every time.

What do you flag in a code review during a modernization?

Three categories, and I weight them differently from a normal review. First, anything that mixes structural and behavioural change in one commit, because that is what makes a diff unreviewable and a rollback ambiguous — retarget and refactor belong in separate changes. Second, anything that weakens the safety net: an edited snapshot, a suppressed analyzer warning, a disabled test, a scrubbed field in a golden-master assertion, a broadened fitness-function allowlist. Those are more important than most logic defects, because they remove the mechanism that would catch the next logic defect. Third, the migration-specific correctness traps that are invisible to the compiler: culture-sensitive string comparison where ordinal is meant, DateTime.Now instead of an injected clock, blocking calls on async code, missing CancellationToken propagation, and a new dependency on the legacy model outside the anti-corruption layer. What I deliberately do not spend review capital on is style and architectural taste on code that is scheduled for deletion, because the goal is throughput on a long programme, not perfection on a temporary artifact.

You inherit a modernization that is two years in and 60% done. What do you do first?

Establish the true state before changing anything, because the reported percentage is almost certainly measuring the wrong thing. I would count the legacy surface directly — endpoints still proxied, projects still on the old framework, database objects only the legacy application uses, flags still live — since those numbers cannot be argued with and usually tell a different story than the status report. Then I would find out what is blocking the remaining work, and it will be one of three things: the shared database was never split, the hardest routes were deferred and have no safety net, or the sponsor's attention moved and nobody has said so. Then I would talk to the team about what they think is true, because after two years they know and have usually stopped saying it. My first change would be to make progress visible in terms of deletion rather than delivery, and to get an explicit decision on the residual — what we will finish, what we will retain deliberately, and by when — because the failure mode at 60% is drifting into a permanent two-system state that nobody ever chose.

How do you introduce modernization practices to a skeptical team?

By demonstrating rather than mandating, on something they already find painful. I would pick the thing that hurts them most — usually the deployment process or a component everyone is afraid to touch — and fix it with them, so the first experience of the new way is relief rather than overhead. Characterization tests are a particularly good opening move, because they require no refactoring, they immediately make a scary component safer to change, and the team sees the value within days. I would avoid arriving with a target architecture, because a target architecture from a newcomer is an argument, whereas a working pipeline is evidence. I would also take their objections seriously and write them down, since experienced skepticism in a legacy team is usually accurate: they have watched previous initiatives fail and they know exactly why. Addressing those specific reasons publicly does more for adoption than any amount of advocacy, and if I cannot address them, that is important information about whether this programme is going to work.

Design a two-year plan for the system in this guide: Web Forms, WCF, EF6, SQL Server 2016, jQuery, on Windows Server 2016 VMs.

Quarter one is foundation and evidence: telemetry across the estate, characterization tests on the revenue path, a working CI/CD pipeline, AppCAT and dependency assessment, usage capture on pages and stored procedures, and the Azure landing zone with networking started immediately because it always takes longer than expected. Quarter two takes the hard deadlines off the table — the database moves to Azure SQL Managed Instance using the MI link for a minutes-long cutover, which also removes the Windows Server 2016 exposure for that tier, with the engine upgraded first and the compatibility level raised separately behind Query Store. Quarters three and four build the coexistence mechanism and prove it: the ASP.NET Core front door with YARP and the System.Web adapters, shared identity, distributed session, and the first end-to-end slice migrated including one awkward route with an upload or a long-lived connection. Year two is the grind: page groups and services move by workflow, prioritised by the usage data, with the WCF endpoints going to CoreWCF where external callers exist and being replaced where they do not; EF6 gives way to EF Core aggregate by aggregate; the jQuery UI is replaced region by region with islands. Throughout, deletion is tracked as the primary metric, the target is a modular monolith on .NET 10 rather than a service fleet, and I would state plainly that a portion of the estate will still be retained at the end — deliberately, with review dates — because a plan that claims to finish everything is a plan nobody should believe.

Night-before cheat sheet

  1. Modernization is a controlled, reversible sequence of changes to a system that is currently earning money — the hard part is never the target architecture, it is the twelve months when both architectures are live at once.
  2. Target .NET 10 LTS, released 11 November 2025 and supported to 14 November 2028. .NET 8 and .NET 9 both leave support on 10 November 2026, so .NET 8 is no longer the safe choice — it is a second migration you have already scheduled.
  3. The database sets the calendar: SQL Server 2016 left extended support on 14 July 2026 with ESUs available to July 2029, SQL Server 2025 went GA on 15 November 2025, and Windows Server 2016 goes end of support on 12 January 2027.
  4. Classify the portfolio with the 7 Rs, look for retire candidates first because deleting a workload is the only option with negative cost, and expect replatform to be the right answer for most of it.
  5. Never propose a big-bang rewrite: the legacy system keeps moving, no value ships until cutover so the project is politically defenceless, and the requirements live in fifteen years of undocumented bug fixes.
  6. Compose the same five patterns — strangler fig at the network edge with YARP, branch by abstraction inside the process, expand–contract at every shared contract, an anti-corruption layer at the model boundary, and a parallel run where behaviour is unknowable.
  7. You cannot unit-test legacy code, so build characterization tests at the outermost boundary from captured production traffic, run them against a real database with Testcontainers, and treat every scrubbed field as a hole in the net.
  8. The compiler errors are the cheap half of a Framework port. The expensive half compiles and returns different answers: ICU instead of NLS changes string comparison and sort order, UTF-8 replaces the ANSI default, Linux paths are case-sensitive, time zones use IANA ids, and BinaryFormatter was removed outright in .NET 9.
  9. Coexistence has three hard parts and everything else is easy: shared authentication via a shared Data Protection key ring, session moved out of process before the first route migrates, and the shared database — which is why a strangler fig without a data track is a UI refactor with extra proxies.
  10. Deploy and release are different events. Backward-compatible schema first, code deployed dark to a zero-traffic revision, release by traffic weight and feature flag, contraction a full cycle later — and know, per change, whether it can be rolled back or must be rolled forward.
  11. Pick the highest-level Azure service that will run the workload: App Service, then Container Apps, and AKS only when you can name the cluster-level requirement and the team who will own upgrades for five years.
  12. Agents changed the cost of the mechanical work, not the cost of verification — Copilot app modernization has been GA for .NET since 22 September 2025 — so the bottleneck moves to review capacity and test coverage, and that is where a lead invests first.
  13. The 2026 default landing zone is a modular monolith, not a service fleet: around 42% of organisations that went microservices have consolidated services back, and cost rather than scalability is now the binding constraint.
  14. Fund it as a standing 20–30% of capacity rather than as a project with an end date, let the team that owns the system own its modernization, and never create a separate modernization team alongside a legacy team.
  15. Finish by deleting. Track the shrinking legacy surface as the primary metric, stop at supported-deployable-observable-understood, and end with a written list of what you deliberately did not modernize and when it will be reviewed.
