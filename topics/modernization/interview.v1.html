Modernization (.NET full-stack)

interview · .NET 10 LTS (10.0.x) · released 2025-11-11 · .NET 8/9 out of support 2026-11-10

Modernization interviews are not upgrade-command trivia: they test whether you can move a system that is earning money right now onto a supported, changeable platform without a freeze, a rewrite, or an outage. Three things get probed relentlessly — the incremental strategy (strangler fig, branch by abstraction, expand/contract) and why big-bang is a career-limiting choice; the safety net (characterization tests, parallel run, feature flags, reversible cutover) that makes the strategy honest; and the business framing, because modernization is the one area where an engineer is expected to argue in money, risk and dates rather than elegance. Assumption stated up front: this bank reads "modernization" as the full-stack .NET case — legacy .NET Framework / ASP.NET services, JavaScript-era front ends moving to TypeScript, SQL Server databases, and Azure as the destination — not mainframe/COBOL modernization, which is a different practice with different tooling. Work the map in order: sub-areas 01–09 produce roughly three quarters of what you will actually be asked, and 01–03 show up in almost every loop. Everything is current to 2026-09-08 and version-labelled: .NET 10 LTS is the migration target because .NET 8 and .NET 9 both lose support on 2026-11-10 — 63 days from today — the same day the Azure Functions in-process .NET model retires and .NET 11 (STS) ships; SQL Server 2016 left extended support on 2026-07-14; TypeScript 7.0, the Go-native compiler, went GA on 2026-07-08; Node.js 20 hit EOL on 2026-04-30 and the Node release schedule changes in October 2026.

01Strategy & the modernization business case

Every modernization loop opens here, because it is the fastest way to separate an engineer who upgrades frameworks from one who can be trusted with a two-year programme and someone else's revenue. Screener depth is "name the options"; senior depth is choosing between them with reasons tied to a specific system; principal depth is sequencing a multi-year programme so value lands quarterly, arguing it in money and risk to people who do not care about C# versions, and being willing to say "not this one" out loud. Expect at least one question where the correct answer is don't modernize this.

What are your options for a legacy system, and how do you choose between them? screener

Answer. The usual frame is the seven Rs: retire, retain, rehost (lift-and-shift), replatform (lift-and-reshape — same code, managed runtime), repurchase (buy a SaaS product instead), refactor (change the code, keep the architecture), and rearchitect/rebuild (change the architecture). They are not a ladder you climb; they are a per-workload decision, and a real portfolio ends up with several of them at once. I choose on two axes: business value of the workload (is it differentiating, or is it commodity someone else does better?) and change rate (does anyone touch this code, and how often?). High value plus high change earns refactor or rearchitect; high value but frozen earns rehost or replatform so it stops being an operational risk without spending engineering time; commodity earns repurchase; low value and low change earns retire — and the first genuine win of most programmes is discovering how much of the estate is in that last box.

Example

WorkloadValueChange rateCall
Pricing engine (.NET 4.8, edited weekly)highhighrefactor to .NET 10, strangle by module
Warehouse label printer servicemediumnone in 4 yearsrehost on a supported VM/container, freeze
In-house expenses toollowlowrepurchase (SaaS) and retire
Reporting web app nobody logs into——retire after 90-day usage log

Follow-ups

  • Who decides value? — Not engineering alone. I bring usage data and cost; the product/business owner sets value, and their signature is what makes "retire" survivable.
  • Rehost is often called a waste of money. Is it? — Only if you stop there. As a step that buys a supported OS and a rollback-able deployment before refactoring, it is cheap risk reduction; as a destination, it is your data centre with a worse bill.
  • How do you find out what nobody uses? — Instrument first: request logs per endpoint, sign-in logs, and database query capture for 30–90 days including a month-end and a quarter-end.

Wrong answer: "We'd rearchitect it into microservices on Kubernetes." Reaching for the most expensive R by default, for the whole estate, with no per-workload analysis, tells the interviewer you would spend two years and deliver a distributed version of the same problems. The senior answer sorts the estate first and applies the cheapest R that removes the actual risk.

Why is a big-bang rewrite almost always the wrong call — and when is it actually right? mid

Answer. A rewrite freezes the old system's evolution while the business keeps moving, so you are chasing a target that never stops: by the time v2 reaches feature parity, parity has moved, and the switchover is a single enormous, untested, all-or-nothing event. It also discards knowledge — the odd-looking branches in the legacy code are usually paid-for bug fixes and regulatory edge cases nobody documented — and it defers all value to the end, which is exactly when budgets get cut. Incremental replacement inverts every one of those properties: value each sprint, small reversible cutovers, and the legacy code available as the executable specification. A rewrite is genuinely right in a narrow band: the system is small enough to rebuild in about a quarter; or the platform is truly dead (a runtime with no supported host, an abandoned commercial framework); or the requirements themselves changed so much that you would be transplanting a solution to a problem you no longer have. Even then, I would run the rewrite behind a facade so the cutover is per-user or per-tenant rather than per-universe.

Example

Rewrite:      [------------ 18 months, zero value ------------] BIG BANG  -> hope
Strangler:    [3wk facade][mod A][mod B][mod C][mod D]... each live, each reversible
              ^ value from week 3, every cutover independently rollback-able

Follow-ups

  • The business is already sold on a rewrite. What do you do? — Agree with the goal, change the delivery shape: propose the same end state via strangling, with a first cutover in 6–8 weeks as proof. Argue schedule risk, not aesthetics.
  • How do you keep two systems in sync during a long coexistence? — Prefer one system of record per capability, with an anti-corruption layer over it; where you cannot, use CDC or an outbox for one-way propagation and never a bidirectional dual write.
  • What is the cost of coexistence? — Two deployment paths, two on-call surfaces, and a routing layer. It is real, and it is the price of reversibility — but you must budget its removal, or you will run it for years.

Wrong answer: "Rewrites are always wrong." Absolutism reads as dogma. Interviewers at this level want the boundary conditions — small scope, dead platform, changed requirements — and a plan to de-risk even the justified rewrite with a per-tenant cutover.

Sell modernization to a CFO who sees no new features in it. What is your case? senior

Answer. I never lead with technology; I lead with three numbers and a date. First, the forced date: .NET 8 and 9 leave support on 2026-11-10 and SQL Server 2016 left extended support on 2026-07-14, so "do nothing" means running unpatched software or buying Extended Security Updates — that is a line item, not an opinion. Second, cost of delay: the share of engineering capacity currently spent on toil the modernization removes — incident hours, manual releases, environments that only one person can build — expressed as a percentage of the team's salary cost. Third, opportunity: the specific roadmap items that are currently expensive or impossible, priced as "this feature costs 8 weeks today and 2 weeks after" — the CFO buys throughput, not architecture. Then I frame the ask as a portfolio of small bets with checkpoints, not a single large one, and I offer to stop: any programme you cannot cancel at the end of a quarter is an unfunded risk.

Example

Do nothing (12 mo):  ESU + unsupported risk  ~ £180k
                     + 31% of 9 FTE on toil  ~ £430k
                     + 2 roadmap items unbuildable
Modernize (12 mo):   4 FTE for 3 quarters    ~ £320k
                     toil falls 31% -> 12% by Q3 (measured monthly)
                     ESU avoided from month 7
Checkpoint: cancellable at each quarter; first cutover live in week 8

Follow-ups

  • Where do those toil numbers come from? — Incident and change records, deployment lead time, and a two-week engineering time survey. Estimated is fine if the method is stated; invented is not.
  • What if the CFO funds half? — Then I re-scope to the half with the forced date and the biggest toil, and say plainly which risks stay open. Half a budget with the full scope is how programmes die quietly.
  • How do you report progress to that audience? — Percentage of traffic served by the new path, endpoints/tenants migrated, toil and lead-time trend — never "80% of the refactor done".

Wrong answer: "We need to modernize because the code is a mess and we're on old tech." Technical debt as an aesthetic complaint has no budget owner. Every clause of the case has to end in money, risk, or a date someone else already set.

You join as lead on a system you have never seen. What are your first 30 days? senior

Answer. Weeks one and two are pure discovery, and the first artefact is not a plan — it is a build. I get the system building and running locally or in a disposable environment from a clean clone, because the time that takes is the single best proxy for how bad the rest is. In parallel I map reality: dependency graph of projects and packages, target frameworks, deployment path, the actual runtime topology (what is on which server), the data stores and their sizes, and the integration edges nobody remembers. Then I instrument before I judge: request volumes per endpoint, error rates, slow queries, release frequency and change failure rate. I interview the people who carry the pager and the person who has been there longest, and I read the last 20 incidents — the estate's real risk map is in the incident history, not in the architecture diagram. By day 30 I deliver a one-page current-state, a ranked risk list, the two or three forced dates, and one small, visible improvement already shipped to prove the pipeline works end to end.

Example

Get-ChildItem -Recurse -Filter *.csproj |
  Select-String -Pattern 'TargetFramework(s)?>([^<]+)' |

Churn crossed with complexity is where modernization pays; a gnarly file nobody has touched in six years is not urgent.

Follow-ups

  • What is the one small improvement you ship in month one? — Usually the build: a reproducible CI build and a one-command local run. It buys credibility and every later step depends on it.
  • Nobody can tell you what the system does. Now what? — Traffic tells you. Log every endpoint, queue and job for a full business cycle; unused code is discovered, not remembered.
  • How do you avoid alienating the incumbent team? — Attribute the state to constraints, not people, and make your first change something that removes their pain. The person who wrote the "bad" code usually knows why.

Wrong answer: "I'd do an architecture review and produce a target-state diagram in the first month." A target state with no measured current state is a wish. Interviewers listen for evidence-gathering — builds, telemetry, incidents, churn — before opinions.

How do you decide what not to modernize? mid

Answer. I exclude anything that is stable, low-change, not a security or support risk, and not blocking a roadmap item — those systems are already delivering value at zero marginal cost, and touching them converts a working asset into a project. The three things that override "leave it alone" are: an unsupported runtime or OS with real exposure, a component sitting on the critical path of work we actually plan to do, and a single point of knowledge failure (one person can deploy it). I also freeze rather than modernize where the business intends to retire or replace a capability within about 18 months — modernizing something that is scheduled to die is the purest form of waste. Making this list explicit matters as much as the migration list: "not now, and here is what would change my mind" is a decision, and it protects the programme's scope.

  • Something is out of support but air-gapped and frozen. Modernize? — Usually no: compensating controls (network isolation, no new data, documented exception with an owner and a review date) are cheaper than a migration nobody needs.
  • How do you keep "not now" from becoming "never"? — Every exclusion gets a review date and a named owner, and the list is re-read each quarter alongside the forced-date calendar.

Wrong answer: "Everything on an old framework has to move." That is a scope you cannot fund and a plan the business will cancel halfway. Uniform urgency is the fastest way to run out of money before the risky parts are done.

The system works and the business is happy. Why modernize at all? mid

Answer. Because "works" is a snapshot and the costs are cumulative and mostly invisible on a dashboard. Four forces make the case concrete: support and compliance deadlines set by someone else (.NET 8/9 end of support on 2026-11-10; SQL Server 2016 gone since 2026-07-14; Windows Server 2016 ends 2027-01-12) — after those dates a CVE is an incident with no patch; delivery speed, where change lead time and change failure rate degrade until a one-line change costs a fortnight; the security surface of dependencies you can no longer upgrade because the framework holds you back; and hiring and retention, since the market for engineers who will maintain a 2013 stack shrinks every year and the people who can are the ones you least want to lose. I would add one honest caveat: none of that is an argument for modernizing everything — it is an argument for modernizing what the four forces actually touch.

Example

"Works" today            Same system, 18 months on
------------------------ -------------------------------------------
patched monthly          unpatched: runtime past EOL, no security fix
2 devs know the build    1 dev; the other left for a modern stack
release: 2 weeks         release: 4 weeks (fear + manual steps)
1 dependency CVE open    9 open, blocked by the framework version

Follow-ups

  • What if there is genuinely no roadmap for the system? — Then rehost/replatform to remove the support risk and stop. Do not refactor a system that will never be changed.
  • Which force convinces executives fastest? — The one with an externally set date. "Unsupported on 10 November" needs no persuasion; "the code is hard to change" needs a spreadsheet.
  • How do you quantify the hiring argument without sounding like a preference? — Time-to-hire and offer-decline reasons for the last few roles, plus attrition of the people who own the legacy components.

Wrong answer: "Because it's using old technology and modern platforms are better." That is a taste argument, and a good interviewer will push until you produce either a date, a cost or a blocked business outcome. If you cannot, the correct answer was "don't".

Sequence a three-year modernization so value lands early and the programme survives a budget review. principal

Answer. I sequence by risk retired per pound and by reversibility, not by architecture layer, and I make the first slice end-to-end rather than foundational. Quarter one buys the ability to change anything at all: reproducible build, automated deploy, telemetry, characterization tests around the highest-churn module, plus one visible user-facing improvement so the programme has a story. Quarters two and three take the highest-churn, highest-value module through the full path — new service, routed via the facade, live, old code deleted — because the first complete cutover is what proves the pattern and calibrates all later estimates. After that I parallelize across teams using the same pattern, taking forced-date work (runtime EOL, database EOL) at the point in the calendar where it must land, not last. Deletion of the old path is part of each slice's definition of done, and each quarter ends with an explicit go/no-go where the honest answer may be "stop, the remaining risk is not worth it".

Example

Q1  build+deploy+telemetry, char tests, facade (YARP) in front of the monolith
Q2  module A end-to-end: new .NET 10 service, 1% -> 100% traffic, old code deleted
Q3  runtime EOL work (must land before 2026-11-10) + module B
Q4  database platform move (rehearsed 3x), modules C/D in parallel by two teams
Y2  remaining modules; front end to TypeScript strict in the same slices
Y3  decommission legacy hosts, remove facade routes, close the ESU line item
Every quarter: go/no-go, and "delete the old path" in the DoD of every slice

Follow-ups

  • Why not build all the platform foundations first? — Because a foundation with nothing on it cannot be validated and is the first thing cut in a budget review. One thin end-to-end slice validates the foundation and buys credibility.
  • How do you estimate years two and three? — From the measured cost of the first complete cutover, in units of "modules like this one", with an explicit spread. Not from a WBS built before you have migrated anything.
  • What is your leading indicator that the programme is failing? — Old paths not being deleted. Coexistence that only grows means cutovers are not really finishing.

Wrong answer: "Year one is platform and foundations, year two is services, year three is the front end." A layered plan defers all value past the first budget cycle and hides the fact that nothing has actually been proven. Slice vertically, prove early, and price the rest from evidence.

What do you target today — .NET 10, .NET 8, or wait for .NET 11 — and why? mid

Answer. .NET 10, the LTS released 2025-11-11 and supported to November 2028. Targeting .NET 8 today is the trap: it is an LTS, so it feels safe, but it reaches end of support on 2026-11-10 along with .NET 9 — you would finish a migration into a runtime that leaves support the same month, buying yourself a second upgrade before the first has settled. .NET 11 RTMs on that same date as an STS with an 18-month window, which is right for a team that upgrades continuously and wrong as the destination for a multi-year migration off .NET Framework. The nuance that earns the point: the framework choice and the migration are separable — get code onto .NET 10 first, and adopt LTS-to-LTS cadence afterwards, since the whole reason the estate is stuck is that someone treated a runtime upgrade as an event rather than as routine maintenance.

  • A key third-party library only supports .NET 8. — .NET 8-targeting libraries load fine on .NET 10; the question is whether the vendor will patch them. Target .NET 10 for the app, track the dependency, and have a replacement or a wrapper ready.
  • Is there ever a case for STS? — Yes, for a team already upgrading every 6–12 months and wanting a feature early. The cost is a mandatory move within 18 months, which must be someone's actual plan.
  • What about .NET Framework 4.8 — is it not "supported forever"? — It follows the Windows lifecycle, so it is patched but frozen: no new APIs, no perf work, no cross-platform, and a shrinking package ecosystem. Supported is not the same as viable.

Wrong answer: "We'd go to .NET 8 because it's the LTS everyone is on." That was true two years ago and is now the answer that ends the conversation — it shows you are quoting remembered advice instead of checking the support calendar, on a topic whose entire premise is support calendars.

The roadmap does not stop for your migration. How do you split capacity? principal

Answer. I refuse the two structures that fail predictably: a separate "modernization team" working alongside a feature team on the same code (they collide, and the feature team keeps growing the legacy path), and "we'll do it in the slack time" (there is none). What works is one team, one backlog, with a standing, negotiated allocation — commonly 20–30% of capacity — and an explicit rule that new work is built on the new path only. That rule is the real lever: the migration finishes because the legacy side stops growing, not because of the percentage. For the forced-date items I get a dated commitment instead of a percentage, since a support deadline is not something you burn down at 20%. And I insist that every feature that touches a legacy module carries the migration of that module as part of its cost — modernization as a tax on change, not as a separate budget that can be cut in isolation.

Example

Rule 1  new endpoints/screens land on the new path; adding to the legacy one needs my sign-off
Rule 2  20-30% standing allocation, visible in the same board, reviewed monthly
Rule 3  forced-date work (EOL 2026-11-10) is dated, not percentaged
Rule 4  "you touch it, you move it": a feature in module C funds module C's migration
Rule 5  no parallel modernization team on the same code base

Follow-ups

  • An urgent feature is far cheaper on the legacy path. Do you allow it? — Sometimes yes, with a dated, tracked exception and the cleanup in the same quarter. Never silently, and never twice for the same module.
  • How do you protect the allocation when a big customer escalates? — By having agreed in advance what gets paused and what does not: forced-date work and the safety net never pause; module order can.
  • Would you ever pause modernization entirely? — Yes, for a genuine company-level event, with a written restart date and an explicit statement of the risk being carried meanwhile.

Wrong answer: "We'd get the business to agree to a feature freeze while we migrate." Freezes are almost never granted, and when granted they get revoked mid-flight — leaving you with a half-migrated system and no protection. Design for coexistence with ongoing feature work; that is the whole skill.

02Strangler fig & incremental migration

This is the pattern vocabulary of the discipline, and interviewers use it as a fast competence check: name it, draw it, then defend it under pressure with shared state, shared databases and a business that will not wait. Screener depth is defining strangler fig; senior depth is the routing layer, the anti-corruption boundary and how coexistence actually behaves in production; principal depth is why real strangler programmes stall at 60% and what you do about it. Expect the interviewer to attack the seams — sessions, transactions, the shared database — because that is where the pattern is hard.

What is the strangler fig pattern? screener

Answer. You put a facade — usually a reverse proxy or gateway — in front of the existing system so that every request flows through a point you control, then migrate functionality behind it one slice at a time, redirecting each slice's routes to the new implementation as it becomes ready. The old system keeps serving everything not yet migrated, so the system is always live and each cutover is small and reversible. The name comes from Fowler's strangler fig: the new growth wraps the old trunk and eventually replaces it, at which point the old trunk is removed — and removal is part of the pattern, not an afterthought. The properties that matter in an interview are: no big-bang date, per-slice rollback, and continuous delivery of value while the migration runs.

Example

// YARP as the facade: new routes first, everything else falls through to legacy
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddReverseProxy()
       .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"));
var app = builder.Build();
app.MapControllers();          // migrated slices, served here
app.MapReverseProxy();         // catch-all -> the .NET Framework app
app.Run();
{ "ReverseProxy": {
  "Routes": {
    "orders-new": { "ClusterId": "new",    "Match": { "Path": "/api/orders/{**c}" }, "Order": 1 },
    "catch-all":  { "ClusterId": "legacy", "Match": { "Path": "{**catch-all}" },     "Order": 100 } },
  "Clusters": {
    "new":    { "Destinations": { "d1": { "Address": "https://orders.internal/" } } },
    "legacy": { "Destinations": { "d1": { "Address": "https://legacy.internal/" } } } } } }

Follow-ups

  • Where does the facade live? — Anywhere you already terminate traffic: Azure Front Door or Application Gateway, an APIM instance, an nginx tier, or a YARP app you own. Owning it in code is the most flexible and the easiest to test.
  • How long should coexistence last? — As short as the plan allows, and with a stated end date per slice. Coexistence is a cost you are paying to hold an option.
  • When is the migration done? — When the last legacy route is removed and the legacy host is decommissioned. If the old code is still deployed, it is still an on-call surface.

Wrong answer: "It's when you rewrite the system module by module." That describes any incremental rewrite and misses the load-bearing part — the interception point that lets you move traffic per route, per tenant or per percentage, and roll it back in seconds without a deploy.

How do you actually route traffic during a strangle, and how do you shift it safely? mid

Answer. Routing is layered: the edge (Front Door / Application Gateway / APIM) decides which stack a request reaches, and inside the new stack a feature flag or routing rule decides whether the request is handled or proxied onward. I always want a dimension finer than "route", because path-based cutover is all-or-nothing for that endpoint: percentage of traffic for idempotent reads, and a stable key — tenant, user id hash — for anything with state, so a given user does not flip between implementations mid-session. The shift is a ramp with a defined bake at each step (1% → 5% → 25% → 50% → 100%, at least one full business cycle at 25%), with automatic rollback on error-rate or latency regression against a pre-agreed threshold. And the rollback path must not require a deploy: a configuration change or a flag flip, one control, one place, rehearsed.

Example

// deterministic per-tenant assignment: same tenant, same path, every request
static bool UseNewPath(string tenantId, int percent)
{
    var bytes = System.Security.Cryptography.SHA256.HashData(
        System.Text.Encoding.UTF8.GetBytes("orders-cutover:" + tenantId));
    return (BitConverter.ToUInt32(bytes, 0) % 100) < (uint)percent;
}

The salt in the hash matters: reuse the same key across two cutovers and you get the same tenants in both experiments, which quietly ruins your comparison.

Follow-ups

  • Why not just do it per-route in one step? — Because the first real traffic is where you discover the difference. A ramp gives you a small blast radius and a signal before it is everyone's problem.
  • What breaks when a user flips between old and new mid-session? — Session state, in-flight multi-step workflows, and caches keyed differently. Sticky assignment on a stable key avoids all three.
  • What do you monitor during the ramp? — Error rate, latency percentiles, and a business metric per cohort (orders placed, payments settled). Technical health can look perfect while the new path silently returns wrong results.

Wrong answer: "We'd flip DNS to the new service and watch." DNS is slow to propagate and slower to revert because of client-side caching, and it is all-or-nothing. If your rollback story is a DNS change, you do not have a rollback story.

Branch by abstraction versus strangler fig — when do you use which? mid

Answer. Strangler fig operates at the deployment boundary: it intercepts traffic outside the process, so it fits replacing whole endpoints, screens or services. Branch by abstraction operates inside the code base: you introduce an abstraction over the thing you want to replace, put the old implementation behind it, build the new implementation behind the same abstraction, switch by configuration, then delete the old one and often the abstraction as well. Use branch by abstraction when the seam is internal — swapping a data-access layer, an ORM, a payment provider, a caching strategy — where there is no request boundary to intercept. They compose: a typical programme strangles at the edge and branches by abstraction inside whatever remains, and both exist to keep trunk releasable while a large change is half-done, which is the real point of either.

Example

public interface IOrderStore { Task<Order?> GetAsync(int id); }

sealed class Ef6OrderStore    : IOrderStore { /* legacy EF6 path   */ }
sealed class EfCoreOrderStore : IOrderStore { /* new EF Core 10    */ }

// toggled implementation + shadow comparison during the bake
sealed class SwitchingOrderStore(IOrderStore legacy, IOrderStore modern,
                                 IFeatureManager flags, ILogger<SwitchingOrderStore> log) : IOrderStore
{
    public async Task<Order?> GetAsync(int id)
    {
        var a = await legacy.GetAsync(id);
        if (!await flags.IsEnabledAsync("OrderStore.Modern")) return a;
        var b = await modern.GetAsync(id);
        if (!OrderComparer.Equal(a, b)) log.LogWarning("divergence on order {Id}", id);
        return b;
    }
}

Follow-ups

  • What is the failure mode of branch by abstraction? — The abstraction outlives the migration and becomes permanent indirection. Deleting the old implementation and collapsing the abstraction is in the definition of done.
  • How do you keep the abstraction from leaking the legacy model? — Design it from the new implementation's needs, then adapt the legacy one to fit. Extracting an interface from the legacy class gives you the legacy design with extra steps.
  • Can you branch by abstraction across a database change? — Yes, paired with expand/contract: the abstraction hides which schema shape is authoritative while both exist.

Wrong answer: "They're the same thing at different scales." Close enough to sound right, but it misses that strangler fig needs a network interception point and gives you per-request routing and rollback without deploying, while branch by abstraction is a compile-time seam switched by configuration. The distinction decides which one you can actually use on a given seam.

What is an anti-corruption layer, and where exactly do you put one? senior

Answer. An anti-corruption layer is a translation boundary that stops one system's model from leaking into another's: the new service speaks its own domain language internally and converts at the edge to whatever the legacy system exposes — its stored procedures, SOAP contracts, magic status codes and 40-column tables. Without one, the legacy model propagates into the new code and you end up with the same design in nicer syntax, which is the most common way modernization produces no benefit. I put it on the new side, owned by the new team, so the legacy system needs no changes; it is the place where all the ugliness is concentrated, named honestly, and covered by tests. That concentration is also what makes the layer deletable: when the legacy system dies, one clearly-marked component dies with it instead of a diffuse smear across the code base.

Example

// new domain: explicit, total, no legacy vocabulary
public sealed record Shipment(ShipmentId Id, ShipmentStatus Status, Address To);
public enum ShipmentStatus { Draft, Booked, InTransit, Delivered, Cancelled }

// ACL: the only place that knows legacy status codes exist
internal static class LegacyShipmentMapper
{
    public static ShipmentStatus ToStatus(string code) => code switch
    {
        "N" or "NEW"      => ShipmentStatus.Draft,
        "B"               => ShipmentStatus.Booked,
        "T" or "TRN"      => ShipmentStatus.InTransit,
        "D"               => ShipmentStatus.Delivered,
        "X" or "C" or "9" => ShipmentStatus.Cancelled,
        _ => throw new LegacyContractException($"unknown status '{code}'")
    };
}

Throwing on the unknown code is deliberate: silent defaults in an ACL turn a data problem into a wrong-behaviour problem you discover a quarter later.

Follow-ups

  • Is an ACL not just a mapper? — A mapper converts shapes; an ACL also converts semantics — units, time zones, null-as-zero, statuses that mean two things — and holds the legacy quirks so the domain stays clean.
  • Two-way ACL? — Yes when the legacy system calls you back; keep both directions in the same component so the translation stays consistent and reviewable.
  • Performance cost? — Real but usually trivial next to the I/O it wraps. If it is not trivial, cache at the ACL boundary rather than leaking the legacy model to avoid a mapping.

Wrong answer: "We'd reuse the legacy DTOs in the new service to avoid duplicating models." That is precisely the corruption the pattern exists to prevent: the legacy model then constrains every design decision in the new service, and when the legacy system is retired its shape is still in your code — the migration bought nothing.

Old and new run side by side. How do users stay logged in across both? senior

Answer. The rule is one issuer, two validators: a single identity provider (usually Microsoft Entra ID) issues the session, and both stacks validate it rather than each minting its own. In the ASP.NET → ASP.NET Core case there are two established routes. Remote app authentication in the System.Web Adapters lets the ASP.NET Core app delegate authentication to the still-running .NET Framework app during the transition, so users are not asked to sign in twice while you migrate. Alternatively both apps share a cookie by using ASP.NET Core Data Protection with a shared key ring (Azure Blob Storage plus Key Vault) and a common cookie name, domain and purpose string — this is the classic answer, and the classic failure is forgetting that the key ring must be shared and persisted or every app restart signs everybody out. For APIs the answer is simpler: both sides validate the same JWT with the same issuer, audience and clock skew rules. Whatever the mechanism, sign-out must invalidate on both sides, and that is the part candidates forget.

Example

// shared key ring so the auth cookie survives restarts and is readable by both apps
builder.Services.AddDataProtection()
    .PersistKeysToAzureBlobStorage(blobUri, credential)
    .ProtectKeysWithAzureKeyVault(keyIdUri, credential)
    .SetApplicationName("contoso-portal");   // must match on both apps

builder.Services.AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(o => { o.Cookie.Name = ".Contoso.Auth"; o.Cookie.Domain = ".contoso.com"; });

Follow-ups

  • Legacy uses ASP.NET Forms Authentication tickets. Now what? — Either keep the legacy app as the authentication authority via remote app authentication, or move sign-in to the new stack and have the legacy app accept the new cookie via a shim. Do not reimplement the MachineKey ticket format in new code.
  • Session state (in-proc Session)? — Externalize it first (Redis / SQL) or use the adapters' remote app session feature; in-process session is the single most common reason a strangle cannot ramp traffic.
  • What about anti-forgery tokens across stacks? — They are per-stack; keep each form's POST on the stack that rendered it, or migrate page and handler together.

Wrong answer: "Each app authenticates independently and we sync the session in the database." Two issuers means two sign-in flows, two expiry policies and two sign-out semantics, and the "sync" is a distributed-state bug generator. One issuer, two validators, shared key ring — that is the answer interviewers are listening for.

How do you prove the new implementation behaves like the old one before you trust it? senior

Answer. Parallel run, also called shadow traffic or dark launch: real production requests go to both implementations, only the legacy result is returned to the user, and a comparator records where the two differ. It finds what tests cannot — the undocumented behaviour in real data — and it is the only technique that gives you a divergence rate to argue about rather than an opinion. Three details make it work: compare semantically, not byte-for-byte (normalize ids, timestamps, ordering, floating point) or you will drown in noise; never let the shadow path write, send email, or charge cards — route it to a sandbox or make writes no-ops; and cap the cost, because shadowing 100% of traffic doubles load on shared dependencies. I run it until the divergence rate is stable and every remaining class of difference has been triaged as "new is right", "legacy is right" or "does not matter", and only then start the traffic ramp.

Example

app.MapPost("/api/quote", async (QuoteRequest req, Legacy legacy, Modern modern, IShadow shadow) =>
{
    var authoritative = await legacy.QuoteAsync(req);
    _ = Task.Run(async () =>                       // fire-and-forget, never blocks the user
    {
        try
        {
            using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(2));
            var candidate = await modern.QuoteAsync(req, cts.Token);
            shadow.Record(req, authoritative, candidate);   // normalizes then diffs
        }
        catch (Exception ex) { shadow.RecordError(req, ex); }
    });
    return Results.Ok(authoritative);
});

Follow-ups

  • What divergence rate is acceptable before cutover? — There is no universal number; what matters is that every class of divergence is explained. A 2% difference that is entirely "legacy rounds wrong" can be safer than 0.01% of unexplained ones.
  • Shadow traffic doubles database load. What do you do? — Sample (5–10%), shadow off a read replica, or restrict to a representative slice. Sampling with good coverage beats full traffic that you have to turn off.
  • What if the new implementation is deliberately different? — Encode the intended differences as rules in the comparator so they are documented and reviewed, and alert only on the unintended ones.

Wrong answer: "We'd write a comprehensive test suite against the new service and cut over when it's green." Tests encode the behaviour you know about; the legacy system's value is in the behaviour nobody remembers. Parallel run against production traffic is what surfaces that, and skipping it is how the "successful" cutover produces a week of customer-reported edge cases.

How do you use feature flags in a migration without drowning in flag debt? mid

Answer. I distinguish flag kinds and treat them differently. Release/migration flags are short-lived operational switches that exist to make a cutover reversible without a deploy; they get an owner, a removal date, and a ticket created at the same commit that introduces them. Experiment and permission flags are a different lifecycle and should not be mixed into migration switches. Practically: one flag per cutover slice, evaluated at exactly one place (the routing seam or the abstraction), never sprinkled through business logic, and always with a defined default for when the flag service is unavailable — that fail-open/fail-closed decision is a design choice, not an accident. In Azure the usual home is App Configuration feature management with IFeatureManager, and I keep flag state visible in telemetry so a graph of an incident shows which cohort was on which path.

Example

builder.Configuration.AddAzureAppConfiguration(o => o.Connect(uri, cred)
       .UseFeatureFlags(f => f.SetRefreshInterval(TimeSpan.FromSeconds(30))));
builder.Services.AddFeatureManagement();

// one evaluation point, tagged onto telemetry so incidents are attributable
var useModern = await features.IsEnabledAsync("Orders.ModernPath", new TargetingContext { UserId = tenant });
activity?.SetTag("migration.orders.path", useModern ? "modern" : "legacy");

Follow-ups

  • How do you stop flags accumulating? — A recurring audit that fails the build (or files a ticket) for any migration flag past its removal date, and "flag removed" in the slice's definition of done.
  • What happens if the flag store is unreachable? — Cached last-known value, then an explicit default per flag. During a cutover the default is usually the legacy path, because that is the known-good one.
  • Flags versus config versus branch? — Long-lived environment differences are config; incomplete work behind a switch on trunk is a flag; long-lived branches are the thing both exist to avoid.

Wrong answer: "We put the new code behind an if on an app setting and remove it later." "Later" is the whole problem: without an owner and a date, migration flags become permanent, untested branches, and two years on nobody knows which combination is even exercised in production. Interviewers are testing lifecycle discipline, not the mechanism.

The new service and the legacy app must share one database for a while. How do you keep that sane? senior

Answer. A shared database during coexistence is normal and acceptable — as an explicitly time-boxed transitional state with rules, not as an architecture. My rules: exactly one writer per table (the other side reads, or goes through the writer's API), a stable read contract via views or synonyms instead of direct table access from the new side, all schema change through expand/contract so both versions of the code work against both versions of the schema, and one migration tool owning the schema — never EF Core migrations and a DBA's change scripts fighting each other. I also mark ownership explicitly (a table-per-owner map in the repo) and enforce it with permissions where possible, because "one writer" that is only a convention lasts about six weeks. Then I schedule the split: which tables move with which slice, and how the last cross-boundary join is removed, because otherwise the shared database silently becomes the permanent integration point and you have built a distributed monolith.

Example

-- new service reads through a contract view, not the physical table
CREATE VIEW app_orders.v_order_summary
AS
SELECT o.OrderId, o.CustomerId, o.PlacedUtc, o.TotalMinor, o.CurrencyCode
FROM   dbo.ORDERS_TBL o WITH (NOLOCK IS NOT USED)  -- read committed snapshot, not NOLOCK
WHERE  o.DELETED_FLG = 0;
GO
GRANT SELECT ON app_orders.v_order_summary TO [svc-orders-api];
DENY  SELECT, INSERT, UPDATE, DELETE ON dbo.ORDERS_TBL TO [svc-orders-api];

Follow-ups

  • Both sides need to write the same table during a transition. — Then pick one as the writer and give the other a narrow API or a queue. If that is truly impossible, use optimistic concurrency with a row version and be explicit that you have accepted a race.
  • How do you handle transactions spanning old and new? — You do not: no distributed transactions (MSDTC is not a modern .NET/Linux option anyway). Use the outbox pattern and idempotent consumers, and make the operation eventually consistent by design.
  • How do you eventually split the data? — Copy with CDC, run both stores in parallel with comparison, switch reads, then switch writes, then drop the old tables. The join you cannot remove tells you the boundary is in the wrong place.

Wrong answer: "Sharing a database is an anti-pattern, so we'd split the data first." Splitting the data before you understand the boundaries is the highest-risk ordering available: you get distributed consistency problems while you still do not know where the seams are. Share deliberately, with rules and an end date, then split along boundaries the migration has proven.

Most strangler programmes stall around 60–70% done. Why, and what do you do about it? principal

Answer. They stall because the easy 60% is genuinely easy and the remaining 40% is the part with no owner: the batch jobs, the report nobody can identify a user for, the integration with a partner who has not answered email since 2019, the one screen finance uses at year end. Meanwhile the urgency evaporates — the painful parts have been fixed, the new stack is delivering, and the residual legacy is quiet — so the programme loses its sponsor while the organisation pays for two of everything forever. My counters: publish a full inventory of remaining legacy surface from day one so the tail is visible and finite; make decommissioning the unit of progress rather than migration, since a migrated-but-not-deleted path counts for nothing; put a dated end-of-life on the legacy host and let that date drive the remaining work (a shutdown date does what a backlog cannot); and route the tail explicitly — some items get migrated, some get retired after a usage check, some get repurchased, and a few get a written exception with an owner. And I keep one named engineer accountable for the endgame, because the tail dies from diffuse ownership, not from difficulty.

Example

Endgame board (the only chart the sponsor sees after 60%):
  legacy endpoints live      41  -> target 0 by 2027-03-31
  legacy scheduled jobs      12  -> 5 migrate, 4 retire, 3 repurchase
  legacy DB objects in use  208  -> tracked via sys.dm_exec_procedure_stats
  legacy hosts running        6  -> shutdown dates: 2 in Nov, 2 in Jan, 2 in Mar
  cost of coexistence   £14k/mo  -> the number that keeps the sponsor engaged

Follow-ups

  • How do you find whether a legacy endpoint or proc is still used? — Access logs at the facade, plus sys.dm_exec_procedure_stats and Extended Events on the database, over a full business cycle including month-end and year-end.
  • Nobody will own a tail item. — Then it is a candidate for retirement: announce a shutdown date, and let the absence of an owner be the decision. Someone always appears if it matters — that is the cheapest discovery mechanism there is.
  • How do you keep momentum when the pain is gone? — Report the monthly cost of coexistence and the open risks, not the percentage complete. Money and dated risk survive attention shifts.

Wrong answer: "We'd add more engineers to finish the tail faster." The tail is a decision problem, not a capacity problem — unknown ownership, unknown usage, unclear value. More people without decisions produces more half-migrated components and a longer coexistence bill.

When is strangler fig the wrong pattern? principal

Answer. Four cases. When there is no interception point — a thick desktop client talking straight to the database, or a batch system with no request boundary — the facade has nowhere to live, and you need branch by abstraction or a data-level strategy instead. When the system is small enough that the facade, dual running and coexistence cost more than a three-month rebuild, the pattern is ceremony. When the legacy behaviour is not worth preserving — a compliance regime that changed, a business process being replaced anyway — strangling faithfully reproduces requirements you are meant to be dropping. And when the coupling is so pervasive that no slice can be cut without dragging in everything (one shared mutable session object, a database where every query joins every table), you must first do a preparatory refactor to create a seam; strangling without a seam turns into a rewrite with extra infrastructure. The senior signal is naming a case where you would not use your favourite pattern.

Example

SituationBetter move
WinForms client → direct SQL, no server tierintroduce an API seam first, or branch by abstraction in the client
12k-LOC internal tool, one team, 3 monthsrebuild behind a per-user cutover switch
Process being replaced by a bought packagerepurchase; migrate data, not behaviour
Everything joins everything, no module edgesseam-creating refactor first (module boundaries, then strangle)

Follow-ups

  • How do you create a seam where there is none? — Introduce an API in front of the data for one capability, move clients to it, then strangle behind it. That first API is the facade you were missing.
  • How small is "small enough to rebuild"? — My rule of thumb: one team can rebuild and validate it inside a quarter, with the legacy behaviour fully understood. Beyond that, incremental wins.

Wrong answer: "Strangler fig always works, it's just a matter of how you slice it." Technically defensible, practically a red flag: applied without a seam it degenerates into a rewrite carrying the cost of a routing tier, dual deployments and dual on-call, and the interviewer is specifically checking whether you know the limits of the pattern you just advocated.

The mechanical core of the topic, and the sub-area where vagueness is most obvious: either you have moved a real .NET Framework code base or you have read about it. Screener depth is "what blocks the port"; mid depth is the tooling and the project-file work; senior depth is the incremental ASP.NET → ASP.NET Core route with System.Web Adapters and YARP, plus the behaviour changes that bite after the code compiles; principal depth is orchestrating a 200-project solution across teams without a branch that lives for a year. What actually stops .NET Framework code from running on .NET 10? screener

Answer. Not the language and mostly not the BCL — it is the Windows-and-hosting-shaped technologies that were never ported. The list you should be able to produce cold: System.Web and everything on it (Web Forms, the ASP.NET pipeline, HttpContext.Current), WCF server hosting (the client is available via System.ServiceModel packages; the server needs CoreWCF), Windows Workflow Foundation, .NET Remoting, AppDomains, Code Access Security and transparency attributes, the System.Configuration XML model as the primary configuration system, the GAC and machine-wide install semantics, distributed transactions across resource managers via MSDTC, and a long tail of Windows-only APIs that now throw PlatformNotSupportedException or require the Microsoft.Windows.Compatibility package. Everything else is usually a package upgrade and a project-file change. The practical framing for an interview: classify the code base into "compiles as-is", "needs a package", and "has no port and needs a design decision" — the third bucket is the actual project.

  • What is .NET Standard 2.0 for now? — A bridge TFM so a library can be consumed by both .NET Framework and modern .NET during coexistence. It is not a destination — target net10.0 once no Framework consumer remains.
  • Does the C# language version change anything? — .NET Framework projects are effectively capped at C# 7.3 for supported use; moving the TFM unlocks a decade of language features, which is a genuine productivity argument.

Wrong answer: "It's mostly a recompile — .NET Core is just .NET Framework cross-platform." True for a leaf library, catastrophically false for a web app or anything using System.Web, WCF hosting or AppDomains. Interviewers use this question to check whether you have hit the wall personally.

In what order do you migrate a multi-project solution, and why that order? mid

Answer. Bottom-up, leaf-first, in dependency order: build the project graph, start with the libraries that depend on nothing but the BCL, and work up towards the entry points, migrating the executable host last. The reason is that a library can be multi-targeted (net481;net10.0 or netstandard2.0) so the old host keeps consuming it while the new host consumes the same code — meaning you migrate on trunk, in small merges, without a long-lived branch. Before touching TFMs I do the mechanical prep everywhere: convert to SDK-style project files, move packages.config to PackageReference, and delete the accumulated MSBuild archaeology (per-project NuGet targets, hint paths, custom build steps). Test projects come along with each library. Two things get pulled out of order deliberately: shared "utility" assemblies that everything references (they gate everything else) and anything with a hopeless dependency, which is decided early because it may change the plan.

Example

<!-- during coexistence: one source, both hosts -->
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFrameworks>net481;net10.0</TargetFrameworks>
    <LangVersion>latest</LangVersion>
    <Nullable>enable</Nullable>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>
  <ItemGroup Condition="'$(TargetFramework)' == 'net481'">
    <Reference Include="System.Web" />
  </ItemGroup>
</Project>
#if NET481
    // legacy-only shim; every one of these is a tracked debt item with a removal ticket
#endif

Follow-ups

  • Why not migrate the web app first — it is where the value is? — Because it sits on top of everything; you would migrate the whole graph in one branch. Leaf-first keeps each merge days-sized, and the incremental ASP.NET route gives you web-tier value without needing the whole graph anyway.
  • Multi-targeting doubles build time and adds #if. Worth it? — For the coexistence window, yes: it is the price of not branching. Drop the old TFM the moment the last Framework consumer goes.
  • How do you keep 200 projects consistent? — Directory.Build.props plus central package management (Directory.Packages.props) so TFMs, analyzers and versions live in one file rather than 200.

Wrong answer: "We'd branch, migrate everything, and merge when it's done." That branch will live for months against a moving trunk, and the merge is the big-bang you were avoiding — with the added insult that all the risk lands on one day, in code nobody has run. Multi-targeting exists precisely so this branch is unnecessary.

What tooling do you use, and what does it genuinely do for you? mid

Answer. The .NET Upgrade Assistant is the workhorse: it analyses a solution, reports incompatible APIs and packages, converts project files to SDK style, moves packages.config to PackageReference, and retargets — with an AI-assisted mode in recent versions. Alongside it, the platform-compatibility and API analyzers flag what will throw at runtime on the target, and dotnet list package --outdated --vulnerable --deprecated and the dotnet-outdated-style workflows cover the dependency side. Since 2025 there is also GitHub Copilot modernization for .NET (GA, in Visual Studio 2026 / VS 2022 17.14.17+, VS Code, the Copilot CLI and github.com), which does assessment, produces a migration plan, applies known code fixes for Azure-target patterns, and iterates until the build passes. My honest framing in an interview: tooling reliably handles the mechanical 60–70% — project files, package references, obvious API swaps — and none of it decides your architecture, resolves a dependency with no port, or tells you whether behaviour changed. Every tool run is a pull request that must be reviewed and covered by tests, not a migration.

Example

dotnet tool install -g upgrade-assistant
upgrade-assistant analyze ./src/Contoso.sln          # inventory + incompatibility report
upgrade-assistant upgrade  ./src/Contoso.Domain/Contoso.Domain.csproj

dotnet list package --outdated --include-transitive
dotnet list package --vulnerable --include-transitive
dotnet build -warnaserror -p:TargetFramework=net10.0

Follow-ups

  • How do you review a large tool-generated diff? — Split it: project-file changes separately from code changes, one project per PR, with the test suite and a binary-behaviour check (public API diff) on each.
  • What does the assistant get wrong most often? — Custom MSBuild logic, content/None item globbing (SDK-style includes files implicitly), strong-naming and signing, and anything with a hand-rolled build step.
  • Would you trust AI to do the whole migration? — For mechanical, verifiable steps behind a strong test suite, yes with review. For behaviour-preserving decisions, no: the model cannot know which legacy quirk is a bug and which is a paid-for requirement.

Wrong answer: "We'd run the Upgrade Assistant and fix the compile errors." Compiling is the low bar; the expensive failures — culture handling, serialization, transaction semantics, sync-over-async under a different threading model — all compile perfectly. The senior answer pairs tooling with a behavioural safety net.

Walk me through migrating a big ASP.NET MVC app to ASP.NET Core incrementally. senior

Answer. The supported route is Microsoft's incremental migration: stand up a new ASP.NET Core app, put YARP inside it as a catch-all proxy to the existing .NET Framework app, and add Microsoft.AspNetCore.SystemWebAdapters to both sides so code that depends on System.Web types (HttpContext.Current, Request, Response, Session) can compile and run on the new stack while it is being cleaned up. Traffic then moves route by route: the new app handles what it has implemented and proxies everything else, so at every moment the site is fully functional. The adapters also provide remote app authentication and remote app session state, which are what make the middle of the migration survivable — the new app can borrow the old app's identity and session instead of you having to solve both problems on day one. The order I use: shared libraries first, then read-only pages, then simple forms, then the complex stateful flows, with session externalized as early as possible because it constrains everything.

Example

// new ASP.NET Core host, coexisting with the .NET Framework app
builder.Services.AddSystemWebAdapters()
    .AddJsonSessionSerializer(o => o.RegisterKey<int>("cart-count"))
    .AddRemoteAppClient(o => { o.RemoteAppUrl = new Uri(legacyUrl); o.ApiKey = apiKey; })
    .AddAuthenticationClient(isDefaultScheme: true)
    .AddSessionClient();

builder.Services.AddHttpForwarder();
var app = builder.Build();
app.UseSystemWebAdapters();
app.MapDefaultControllerRoute().RequireSystemWebAdapterSession();
app.MapForwarder("/{**catch-all}", legacyUrl).Add(b => ((RouteEndpointBuilder)b).Order = int.MaxValue);
app.Run();

Follow-ups

  • What is the cost of remote app session? — A network hop to the legacy app per request that touches session, and exclusive locking semantics that can serialize requests. It is a transition crutch: externalize session properly (Redis/SQL) before you ramp real traffic.
  • Do the adapters mean you can keep writing HttpContext.Current? — They let it work, they do not make it right; treat every adapter usage as a tracked debt item removed when its page migrates.
  • Web Forms instead of MVC? — Same shape at the traffic layer, but there is no Web Forms on ASP.NET Core: each page is rebuilt as Razor Pages/MVC/Blazor while the proxy serves the rest.
  • Where does the proxy live in production? — Front the new ASP.NET Core app with your existing edge; the legacy app stops being publicly routable, which also shrinks its attack surface.

Wrong answer: "You can't migrate ASP.NET incrementally — you have to rewrite the web tier in one go." This was arguably true years ago and is now demonstrably wrong: System.Web Adapters plus YARP are the documented, supported path, and not knowing it signals your knowledge of the platform stopped several versions back.

How does configuration change, and what breaks in the move off web.config? senior

Answer. You go from a single XML file read through a static ConfigurationManager, with build-time XDT transforms per environment, to a layered IConfiguration composed at startup from appsettings files, environment variables, Key Vault or App Configuration and command line, surfaced to code through the options pattern with validation. Three things reliably break. First, the static access pattern: ConfigurationManager.AppSettings["X"] is scattered everywhere, so I introduce a typed options class and change call sites incrementally (a shim that reads IConfiguration keeps the old signature alive during the transition). Second, environment handling: transforms happen at build time, which means one artefact per environment — the modern model is one artefact, configured at run time, and that change is often the more valuable half of the work. Third, secrets: connection strings and keys were in web.config and are now expected in Key Vault or App Configuration behind managed identity, which is a security upgrade the migration should not waste. Also remember the parts of web.config that are not configuration at all — IIS handlers, modules, request limits — which become middleware, host options or web.config for the ANCM only.

Example

builder.Configuration
    .AddJsonFile("appsettings.json", optional: false, reloadOnChange: true)
    .AddJsonFile($"appsettings.{builder.Environment.EnvironmentName}.json", optional: true)
    .AddAzureAppConfiguration(o => o.Connect(appConfigUri, cred).ConfigureKeyVault(kv => kv.SetCredential(cred)))
    .AddEnvironmentVariables();

builder.Services.AddOptions<OrderingOptions>()
    .Bind(builder.Configuration.GetSection("Ordering"))
    .ValidateDataAnnotations()
    .ValidateOnStart();      // fail at startup, not on the first request at 2am

Follow-ups

  • Why ValidateOnStart? — Configuration errors should crash the deployment, where a health check catches them and the rollout stops — not surface as a null reference during the first customer request.
  • How do you handle hundreds of app settings? — Group into option classes by feature, put them under prefixed sections, and use double-underscore environment variables (Ordering__RetryCount) so container platforms can override anything.
  • Anything left in web.config? — Only IIS/ANCM hosting concerns when hosting on IIS; application configuration should not live there any more.

Wrong answer: "We'd keep using ConfigurationManager — the System.Configuration.ConfigurationManager package works on .NET 10." It does compile and read an app.config, which makes it a legitimate short-lived crutch, but presenting it as the destination gives up reloadable, layered, secret-store-backed, validated configuration and keeps a static global that fights testing and DI.

HttpContext.Current is everywhere in the code base. What do you do? senior

Answer. HttpContext.Current is ambient per-request state implemented on the legacy SynchronizationContext; on ASP.NET Core it does not exist, and the closest equivalent — IHttpContextAccessor, backed by AsyncLocal — is deliberately opt-in and has a real cost. The structural fix is to stop depending on ambient state: pass what the code actually needs (user id, tenant, correlation id, culture) as explicit parameters or as a scoped, injected context object. Practically I do it in three passes: introduce a scoped IRequestContext abstraction populated by middleware; replace call sites file by file, which is mostly mechanical and highly parallelizable across a team; and only where a deep call chain cannot be reworked cheaply do I fall back to IHttpContextAccessor — or, during coexistence, the System.Web Adapters' HttpContext shim — with each usage tracked for removal. The important senior point: the reason HttpContext.Current hurts is not that it was removed, but that it silently makes every consumer untestable and background-work-hostile, which is why re-implementing it is the wrong instinct.

Example

public interface IRequestContext { string TenantId { get; } string? UserId { get; } string CorrelationId { get; } }

sealed class RequestContextMiddleware(RequestDelegate next)
{
    public Task InvokeAsync(HttpContext ctx, RequestContextAccessor acc)
    {
        acc.Current = new RequestContext(
            ctx.User.FindFirst("tid")?.Value ?? throw new InvalidOperationException("no tenant"),
            ctx.User.FindFirst(ClaimTypes.NameIdentifier)?.Value,
            ctx.TraceIdentifier);
        return next(ctx);
    }
}
// background work gets an explicit context, not a null HttpContext at 3am
await _jobs.EnqueueAsync(new RebuildIndex(ctx.TenantId, ctx.CorrelationId));

Follow-ups

  • Why is IHttpContextAccessor discouraged in library code? — It reintroduces ambient state, ties the library to a web host, and is null in background threads, hosted services and tests — the exact places where the legacy pattern failed.
  • Is AsyncLocal expensive? — Enough to matter on hot paths (it adds allocation and context flow work), but the real cost is design: implicit dependencies you cannot see in a signature.
  • How do you parallelize the cleanup? — It is a per-file mechanical change with a compiler-verified end state, so it is ideal work to split across the team, or to hand to an AI-assisted pass with review.

Wrong answer: "We'd write a static HttpContext.Current-style helper backed by AsyncLocal so the code doesn't change." It compiles, it demos, and it preserves the exact coupling that makes the code untestable — plus it silently returns null in every non-request code path, so the bugs appear in background jobs weeks later. The whole point of the migration is to remove the ambient dependency.

What behaviour changes — not compile errors — do you deliberately test for after the port? senior

Answer. The dangerous class is code that compiles and behaves differently. My standing checklist: globalization, because modern .NET uses ICU rather than Windows NLS, so culture-sensitive string comparison, sorting and casing can differ (and StringComparison.Ordinal versus culture-sensitive defaults is now a real bug source); serialization, if you swap Newtonsoft.Json for System.Text.Json, where defaults differ on case sensitivity, nulls, dictionary keys, polymorphism and DateTime/TimeZoneInfo handling; DateTime parsing and time zone id differences on Linux; cryptography and TLS defaults; the threading model, since ASP.NET Core has no SynchronizationContext, so old sync-over-async deadlocks disappear while thread-pool starvation remains; and file-system semantics if you also move to Linux — case sensitivity, path separators, and the fact that Path.Combine was hiding it. I would also mention that the breaking-changes documentation is versioned per release and is a required read, not a fallback: for each release between source and target, not just the target.

Example

// ICU vs NLS: this changed meaning between Framework and modern .NET on some cultures
bool same = string.Equals(a, b, StringComparison.OrdinalIgnoreCase);   // deterministic; use for ids/keys

// System.Text.Json defaults are strict where Newtonsoft was lenient
var opts = new JsonSerializerOptions
{
    PropertyNameCaseInsensitive = true,                       // Newtonsoft was case-insensitive
    DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull,
    NumberHandling = JsonNumberHandling.AllowReadingFromString // legacy clients send "42"
};

Follow-ups

  • How do you catch these systematically? — Golden-file/approval tests over serialized payloads and formatted output, run on both runtimes; plus parallel run in production for the behaviour no test knows about.
  • Keep Newtonsoft or switch? — Keep it initially to remove a variable from the migration, then switch as its own change with its own tests. Two behavioural changes at once make attribution impossible.
  • Anything that bites specifically when moving to Linux containers? — Case-sensitive paths, missing Windows fonts/GDI, time zone ids (Europe/London versus GMT Standard Time), and file permissions. TimeZoneInfo now accepts both forms on modern .NET, but stored ids in the database may not.

Wrong answer: "If it compiles and the unit tests pass, it's the same code — the runtime is just faster." Every experienced migrator has a scar here: a culture-sensitive sort, a serialized payload shape, a rounding change. The interviewer is checking whether you have a checklist, and whether "breaking changes" means the documented, versioned list rather than a vague fear.

A critical third-party library has no modern .NET version. What are your options? mid

Answer. Five options, in the order I would evaluate them. Check whether it actually needs replacing — a library targeting net48/netstandard2.0 often runs fine, and a package's target framework is a support statement, not always a technical barrier. Replace it, if there is a maintained equivalent; this is the most common outcome for logging, DI, mapping and scheduling libraries. Wrap and isolate it: keep the component on .NET Framework as a small Windows-hosted service behind an HTTP or queue contract, so one deployable stays legacy instead of the whole app — the pragmatic move for a licensed component with no port (reporting engines, document generation, hardware SDKs). Reimplement the slice you actually use, which is frequently a fraction of the library's surface. Or buy the vendor's modern SKU, which is often a commercial rather than technical decision. What matters in the answer is that I decide this early, in the assessment phase, because a single unportable dependency can dictate the hosting model for the whole system.

Example

[ .NET 10 app on Linux containers ]
        |  HTTPS / queue, narrow contract, versioned
        v
[ net481 "legacy adapter" service on Windows ]  -> licensed PDF engine, COM component
   * one deployable stays legacy, with a dated retirement plan
   * the contract is the ACL: the new side never sees the vendor's types

Follow-ups

  • How do you stop the adapter service becoming permanent? — It has an owner, a cost line and a review date, and its retirement is a named item on the endgame board.
  • Any risk in "it targets netstandard2.0, so it works"? — Yes: it may P/Invoke Windows APIs or use unsupported types at runtime. Verify with the platform-compatibility analyzer and an integration test on the target OS, not with the TFM alone.
  • COM interop? — Supported on Windows in modern .NET, but not on Linux; if the component is COM-based you are choosing between staying on Windows hosting and isolating it behind a service.

Wrong answer: "We'd have to stay on .NET Framework until the vendor ships a version." One dependency should never hold the whole estate hostage — isolating it behind a contract is a standard, well-understood move, and failing to reach for it suggests you would let a single blocker stall an entire programme.

How do you migrate a 200-project, 2M-line solution across several teams without a year-long branch? principal

Answer. Three mechanisms. First, trunk-based migration through multi-targeting: every library carries both TFMs during the transition so each change is a small, mergeable PR and both hosts keep working — there is never a "migration branch". Second, centralized build configuration: Directory.Build.props, Directory.Packages.props and shared analyzer rules mean a policy change is one file, not 200 diffs, and CI builds both TFMs so a regression on either fails immediately. Third, a scoreboard and clear ownership: the dependency graph is topologically sorted, each layer assigned to the team that owns those projects, and the tracked metric is projects retargeted, adapter usages remaining, and legacy hosts still running. I run a small enabling team that owns the build system, the shims and the patterns, and does the first two or three projects of each category as worked examples — the teams then follow the example rather than each inventing an approach. Finally I sequence around the calendar: the forced date (2026-11-10) determines which hosts must be off .NET 8/9 first, and everything else negotiates around that.

  • What is the role of the enabling team? — Build system, shims, patterns, first examples, and unblocking — not migrating everything themselves, which recreates the two-team failure mode.
  • How do you prevent regressions from new code? — An analyzer or CI rule that fails a PR adding new net481-only references or new adapter usages, so the legacy surface can only shrink.

Wrong answer: "We'd freeze the code base for a sprint and do a coordinated big-bang retarget of all projects." At this size the freeze never holds, the retarget uncovers hundreds of unrelated issues at once, and there is no way to attribute a regression to a change. The graders are listening for trunk-based, incremental, centrally-configured, with a scoreboard.

You are already on .NET 8. What does the upgrade to .NET 10 actually involve? mid

Answer. Far less than the Framework port, and it should be routine: bump TargetFramework to net10.0, update the SDK in global.json and in every CI image and base container image, update Microsoft package versions to the matching major (ASP.NET Core, EF Core, extensions), then read the breaking-changes list for .NET 9 and .NET 10 — both, because you are skipping a release — and run the full test suite plus a performance comparison. The realistic risk areas are EF Core (query translation and default changes between majors can change generated SQL and, occasionally, results), any source generator or analyzer packages that must match the SDK, and container base images (tag, and whether you are on the right distro/chiselled variant). I would run it as its own change with its own bake, not bundled with feature work, and I would do it now rather than in October: .NET 8 and 9 leave support on 2026-11-10, and a rushed runtime upgrade in the last fortnight is how a routine change becomes an incident.

  • Do you have to go through .NET 9? — No, jump straight to 10; just read both releases' breaking changes and both EF Core majors' behaviour notes.
  • How do you catch a performance regression? — A benchmark of the top few endpoints before and after, plus latency percentiles in the bake. Major upgrades are usually faster, but "usually" is not a deployment plan.
  • What about the runtime on Azure App Service? — Verify the platform has the target runtime available (or deploy self-contained/containerized), and remember to change the stack setting; a missing runtime shows up as a failed start, not a build error.

Wrong answer: "We'll go to .NET 10 when we next have time — .NET 8 is LTS, so we're fine." That answer expires on 2026-11-10, which is nine weeks from now. On this topic in particular, not tracking the support calendar is the disqualifying error.

04Safety nets: testing legacy code

This sub-area separates people who have modernized something from people who have planned it: legacy code by definition lacks the tests you need, and every credible strategy above depends on a safety net that has to be built before the interesting work starts. Mid depth is characterization tests and seams; senior depth is choosing the cheapest net that covers the risk — approval tests, contract tests, parallel run — and knowing when not to bother; principal depth is arguing about how much verification a given cutover deserves. Interviewers listen for "I made the change testable before I made the change".

Docs: Testing in .NET · EF Core testing · Characterization tests

There are no tests. Where do you start? mid

Answer. Not with unit tests — legacy code usually has no seams to unit-test, and creating them requires exactly the refactoring the tests were meant to protect. I start at the outside: characterization tests at the highest boundary I can reach cheaply, typically HTTP request in, response and database side effects out, run against a known data set in a container. They assert what the system does, not what it should do — including the bugs — because during a migration behaviour preservation is the requirement. Then I add coverage where risk is: I use churn and incident history to pick the modules worth investing in, not a uniform coverage target. Once the outer net exists, I refactor for seams and add fast unit tests as I go, so the pyramid gets built inside out. The one thing I insist on before touching anything: the tests must run in CI, from a clean checkout, in minutes — a safety net that only runs on one person's machine is not a net.

Example

// characterization test with Testcontainers: real SQL Server, real app, no mocks
public sealed class OrderApiCharacterization : IAsyncLifetime
{
    private readonly MsSqlContainer _db = new MsSqlBuilder().Build();

    [Fact]
    public async Task Quote_for_known_basket_is_unchanged()
    {
        var res = await _client.PostAsJsonAsync("/api/quote", KnownBaskets.Basket17);
        var body = await res.Content.ReadAsStringAsync();
        await Verify(body).UseDirectory("__approved__");   // approval/snapshot: locks current behaviour
    }
}

Follow-ups

  • What if current behaviour is wrong? — Lock it anyway, then fix it as a separate, visible change. Fixing a bug inside a migration destroys your ability to tell a regression from an intended change.
  • Where do the test inputs come from? — Anonymized production traffic and real data shapes. Hand-invented inputs miss the edge cases that make legacy systems legacy.
  • How much is enough? — Enough to cover the paths the first cutover touches, plus the money paths. Chasing a global percentage on code you are about to delete is a waste.

Wrong answer: "First we'd get unit test coverage above 80%, then migrate." You would spend months writing tests against code you are about to delete, and you would have to refactor to make it unit-testable — the very act the tests were supposed to protect. High-level characterization tests first, unit tests as seams appear.

What is a characterization test, and how is it different from a unit test? mid

Answer. A characterization test (Feathers' term) documents what the code currently does, produced by running the code and recording the output, rather than asserting what a specification says it should do. It is a change detector: its value is not correctness but the alarm it raises when behaviour moves. Practically it is often an approval/snapshot test — serialize the output, review it once by hand, commit it as the approved file, and the test fails on any diff. That makes it perfect for migrations, where the acceptance criterion is genuinely "identical to before", and poor for greenfield development, where it freezes arbitrary implementation details. The discipline that keeps it useful: normalize volatile fields (ids, timestamps, ordering) before approving, keep the approved files reviewable in a diff, and require a human to explain any change to an approved file in the PR — the moment approvals are re-baselined automatically, the net is gone.

Example

[Fact]
public async Task Invoice_pdf_model_is_stable()
{
    var model = await _svc.BuildInvoiceModelAsync(invoiceId: 4711);
    await Verify(model)
        .ScrubMember("GeneratedUtc")           // volatile: normalize or the test is a flake
        .ScrubMember("CorrelationId");
}
__approved__/Invoice_pdf_model_is_stable.verified.txt   <- reviewed once, committed, diffed forever

Follow-ups

  • Is it a problem that they are brittle? — Brittleness is the feature: they fire on any change. Keep them at boundaries where change should be deliberate, not around internals you expect to churn.
  • How do they interact with parallel run? — Same idea at two scopes: characterization compares old-vs-new offline in CI, parallel run compares them on live traffic. Use both; the second finds what the first's inputs never covered.
  • When do you delete them? — When the migrated component has proper specification-based tests. Keeping both forever means every intentional change breaks two suites.

Wrong answer: "It's basically an integration test." It is about intent, not scope: it asserts observed behaviour rather than specified behaviour, and it can be written at any scope. Missing that distinction usually goes with missing why you would deliberately lock in a bug.

How do you create a seam in code with no dependency injection and static everything? senior

Answer. Cheapest seam first, and always with the outer characterization test already green. The ladder I use: extract the logic into a new method or class and call it from the old site (pure move, no behaviour change); introduce a parameter to pass in what was previously fetched from a static; wrap the static in an instance-based adapter interface and inject that where you can; and where none of it is possible, use a settable static factory hook — ugly, but it is a two-line change and it lets you get a test around the code so you can then do the real refactoring safely. On the modern side, once the class is constructed by the DI container, all of that disappears. The principle I want to articulate in an interview is the ordering: you do not refactor to make code nice and then test it; you make the smallest possible change that lets you observe the behaviour, lock it, then refactor freely.

Example

// before: untestable - time, config and data access are all ambient statics
public decimal CalculateFee(Order o)
    => o.Total * decimal.Parse(ConfigurationManager.AppSettings["FeeRate"])
       * (DateTime.Now.DayOfWeek == DayOfWeek.Sunday ? 1.5m : 1m);

// step 1: parameterize (no behaviour change, callers pass the same values)
public decimal CalculateFee(Order o, decimal feeRate, DateTime now)
    => o.Total * feeRate * (now.DayOfWeek == DayOfWeek.Sunday ? 1.5m : 1m);

// step 2: the old signature stays as a thin shim while call sites move
public decimal CalculateFee(Order o)
    => CalculateFee(o, decimal.Parse(ConfigurationManager.AppSettings["FeeRate"]), DateTime.Now);

Follow-ups

  • Why not just use a mocking framework that can fake statics? — Tools that intercept statics (profiler-based mockers) work, but they hide the coupling and often need special runners in CI. Fine as a temporary crutch, bad as a strategy.
  • What about DateTime.Now specifically? — Inject TimeProvider (built into modern .NET since .NET 8); it is the standard abstraction and makes time-dependent tests deterministic without a custom interface.
  • How do you keep these mechanical refactors safe? — Use the IDE's refactorings rather than hand edits, commit each step separately, and keep the characterization test green after every step.

Wrong answer: "You can't test it, so we rewrite that class properly first." Rewriting untested legacy code is exactly the unverifiable change the whole discipline exists to avoid. The seam-first ladder — parameterize, extract, wrap — is the answer, and knowing it signals real experience with this work.

How do you test that a migrated service still honours its contract with callers you do not own? senior

Answer. Consumer-driven contract tests plus a recorded corpus. Each consumer publishes the interactions it relies on (Pact or an equivalent), the provider's CI verifies every published contract on each build, and the provider cannot deploy a change that breaks a consumer's expectations — which is precisely the risk when you reimplement a service. Where consumers cannot or will not participate (external partners, internal teams with no capacity), I substitute a recorded corpus: capture real requests and responses at the edge over a full business cycle, replay them against the new implementation, and diff semantically. I also freeze the wire contract during the migration on principle — reimplementation and redesign at the same time makes every difference ambiguous — and version the API explicitly so that the contract change, when it comes, is a separate, announced event with a deprecation window.

Example

1. capture at the facade:  method, path, headers (allow-listed), body, status, response body
2. anonymize + dedupe -> corpus of ~5k distinct request shapes for one business cycle
3. replay against new impl in CI; semantic diff (ignore ordering, ids, timestamps)
4. gate: 100% of the corpus matches, or every mismatch class is signed off as intended

Follow-ups

  • Contract tests versus recorded replay — which is better? — Contract tests express intent and catch the consumer's real needs; replay covers what actually happens including undocumented usage. Migrations want both, and replay is the one you can build unilaterally.
  • What about the payloads' schema itself? — Diff the OpenAPI/JSON schema between old and new as a build step; an added optional field is fine, a renamed one is a break, and a tightened validation rule is the sneaky break people miss.
  • Do you tell consumers you are reimplementing? — Yes, with dates and a test window. Silent reimplementation is how you find out about a consumer's dependency on a quirk during an incident.

Wrong answer: "We'd publish an OpenAPI spec and tell consumers to code against it." The spec documents what you meant; consumers depend on what you did — field ordering, lenient parsing, an undocumented field, a 200 with an error body. On a migration, observed behaviour is the contract.

How do you get realistic test data without copying production personal data? senior

Answer. Three tiers, chosen by what the test must prove. Synthetic generated data for functional tests, where shape matters more than realism. A masked/anonymized production subset for behavioural and performance work — referentially consistent (the same customer id maps to the same fake identity everywhere), format-preserving so validation still fires, and with the distributions intact, because performance behaviour comes from cardinality and skew, not from row count. And for the queries that only misbehave at real scale, statistics-only or read-only access in a controlled environment with logging and time limits. The governance answer matters as much as the technique: masking runs as part of a restore pipeline so no unmasked copy ever lands in a lower environment, the mapping table is kept in the secure zone, and the whole thing is documented for GDPR/DPIA purposes. I would also say plainly that "we take a production backup and restore it into test" — the most common real practice — is a data breach waiting for a subject access request.

Example

-- deterministic, referentially consistent masking during the restore pipeline
UPDATE c
SET    c.Email     = CONCAT('user', c.CustomerId, '@example.invalid'),
       c.FullName  = CONCAT('Customer ', c.CustomerId),
       c.Postcode  = LEFT(c.Postcode, 3) + ' 0AA'     -- format preserved, area kept for skew
FROM   dbo.Customers AS c;
-- keep row counts, key distributions and NULL ratios untouched: they drive plan choice

Follow-ups

  • Why keep distributions? — Query plans depend on cardinality and skew; a uniformly random data set makes a query that scans 4M rows in production look instant in test.
  • SQL Server features that help? — Dynamic Data Masking for display-level masking (not a security boundary), plus a scripted post-restore mask job for real anonymization; Always Encrypted for the columns that should never be readable at all.
  • How do you test month-end/year-end paths? — Time-shifted data sets and an injectable clock (TimeProvider), so the calendar behaviour is testable in March.

Wrong answer: "We restore a production backup into the test environment — it's the only realistic data." It is realistic and it is a personal-data breach the moment a developer laptop or a lower-tier environment holds it. Say masked subset, referentially consistent, in a restore pipeline; volunteering the privacy dimension is a senior signal.

How do you know performance did not regress after a migration? senior

Answer. By measuring the same thing before and after with the same load and the same data, at percentiles rather than averages. Concretely: baseline the top endpoints and jobs on the legacy system (p50/p95/p99 latency, throughput at a fixed concurrency, CPU and memory per request, database reads per request), then run the identical scenario against the new implementation on production-like data. Two migration-specific traps to name: the database, where an ORM change can turn one query into N and the plan cache is cold on a new server, so I compare query counts and logical reads per request, not just wall-clock; and the environment, where "new is slower" often means a smaller SKU, a different region, or a missing warm-up rather than worse code. In production the real check is a canary at low traffic percentage with per-cohort dashboards, because synthetic load never reproduces the tail. And I set the acceptance threshold in advance — "p99 within 10% at the same cost" — so the go/no-go is not an argument at 11pm.

Example

// per-request DB round trips: the metric that catches ORM regressions before users do
optionsBuilder.LogTo(msg => queryCount++, new[] { DbLoggerCategory.Database.Command.Name },
                     LogLevel.Information);
// assert in an integration test - N+1 regressions are caught in CI, not in production
Assert.InRange(queryCount, 1, 3);

Follow-ups

  • Why percentiles? — Averages hide the tail that users feel and that timeouts trigger on. A migration that improves p50 and doubles p99 is a worse system.
  • What about cold start? — Modern .NET on containers/serverless has real cold-start characteristics; measure it explicitly, and consider ReadyToRun/AOT or always-on instances rather than discovering it at 8am Monday.
  • Legacy is faster and nobody can explain why. — Do not cut over. Usually it is a cached plan, a missing index on the new store, chattier ORM access, or an in-process call that is now a network hop.

Wrong answer: "Modern .NET is much faster than .NET Framework, so performance improves for free." Often true for CPU-bound code, and irrelevant if you added a network hop, changed the data-access pattern, or moved to a smaller instance. Claiming the improvement without a measurement is the answer that ends the topic badly.

How much verification is enough? Argue the trade-off. principal

Answer. I size the net to blast radius and reversibility, not to a policy number. Two questions decide it: what happens if this is wrong (money moved incorrectly, data corrupted, a report slightly off, a page styled badly), and how fast can we undo it? A cutover that is flag-reversible in 30 seconds, on a read path, with a small cohort, needs a canary and good alerts — not a six-week parallel run. A one-way data migration that mutates historical financial records needs reconciliation, a rehearsal on a full copy, a reversible plan and sign-off, because "roll back" is not available. That gives a simple grid I can defend to a sponsor: high impact plus irreversible earns everything; low impact plus reversible earns monitoring and a fast undo. The failure I actively guard against is uniform rigour — spending the same verification effort everywhere means the cheap paths are over-tested and the dangerous ones are under-tested, and it is also the fastest way to make the programme too slow to survive.

  • Who decides "high impact"? — The business owner, in writing, before the cutover. Engineering estimating regulatory impact alone is how a "minor" rounding change becomes a restatement.
  • How do you resist pressure to skip the net on the risky one? — Convert it into a decision with a name on it: state the risk, the cost of the net, and ask for the decision explicitly. Most pressure evaporates when the trade-off is written down.
  • Does the answer change late in a programme? — Yes: as the team's cutover track record accumulates, you can justify lighter verification for the same class of change. Evidence, not fatigue.

Wrong answer: "You can never have too much testing — we'd parallel-run everything for a month." Verification has a cost in calendar time and in shared-dependency load, and a programme that verifies everything to the same depth ships too slowly to reach the risky parts before the budget runs out. The principal signal is a defensible, differentiated rule.

05Zero-downtime schema change

Almost every modernization eventually hits the database, and this is where a plausible-sounding plan meets locks, 500-million-row tables and a rollback that cannot happen. Mid depth is expand/contract and why you never rename a column; senior depth is deployment ordering (schema and code are two releases, not one), batched backfills and online DDL specifics on SQL Server; principal depth is splitting a store while both systems run. Interviewers probe here because it is the least reversible part of a migration, and because "we take a two-hour maintenance window" is an answer many organisations no longer accept.

Docs: Online index operations · Applying EF Core migrations · Change data capture

Explain expand/contract (parallel change) for schema evolution. screener

Answer. You never change a schema element in place while code depends on it; you go through three phases. Expand: add the new element (column, table, index) in a way that is backwards compatible — nullable, with a default handled in code, no destructive change — and deploy it while the old code is still running. Migrate: deploy code that writes both old and new, backfill existing rows in batches, then move reads to the new element once the data is verified. Contract: after a bake period long enough that you would not need to roll back, remove the old element and the dual-write code. The property this buys you is that at every moment, the currently deployed application version and the currently deployed schema version are compatible in both directions — which is what makes a rolling deployment and a code rollback possible without a database rollback, since restoring a database loses the transactions written since.

Example

-- 1. expand (safe, metadata-only, deployed before any code change)
ALTER TABLE dbo.Customers ADD EmailAddress nvarchar(256) NULL;

-- 2. migrate: code writes both; backfill in batches
UPDATE TOP (5000) c SET c.EmailAddress = c.Email
FROM dbo.Customers c WHERE c.EmailAddress IS NULL AND c.Email IS NOT NULL;

-- 3. contract (only after the new column has been authoritative through a full bake)
ALTER TABLE dbo.Customers DROP COLUMN Email;

Follow-ups

  • How long is the bake? — At least as long as your rollback horizon and one full business cycle; if month-end batch jobs touch the table, it includes a month-end.
  • What is the cost? — Three deployments instead of one, dual-write code, and a window where both columns exist. That is the price of never needing a maintenance window or a database restore.
  • What if the contract step never happens? — The usual outcome, and the reason to schedule it as a ticket at expand time. A schema full of abandoned "_old" columns is the fossil record of migrations nobody finished.

Wrong answer: "We deploy the schema change and the code change together in one release." That only works if you can stop all traffic and if you never need to roll back — because rolling back the code leaves the new schema, and rolling back the schema loses data written in the meantime. Interviewers ask this precisely to hear whether you separate the two.

Add a NOT NULL column with a default to a 500-million-row table, online. How? mid

Answer. On modern SQL Server (2012+, Enterprise) adding a NOT NULL column with a constant default is a metadata-only operation — it does not rewrite the table — so the naive statement is actually fine if the default is a runtime constant and the edition supports it. The trap is that it still takes a schema-modification lock, so on a busy table it will queue behind long-running readers and then block everything behind it; the mitigation is a short lock timeout and WAIT_AT_LOW_PRIORITY, executed in a quiet window, with the statement abandoned and retried rather than left blocking. Where the default is non-deterministic (NEWID(), a computed value) or the edition does not support the online path, the safe route is expand/contract: add the column nullable, backfill in batches with a resumable driver, add a NOT NULL constraint with WITH VALUES/NOCHECK semantics as appropriate, and only then make application code depend on it. I would also check the table's real shape first — a heap versus a clustered index, LOB columns, and existing partitioning all change the answer.

Example

-- metadata-only on SQL Server 2012+ Enterprise, but still needs a Sch-M lock:
SET LOCK_TIMEOUT 3000;
ALTER TABLE dbo.Orders ADD Channel tinyint NOT NULL CONSTRAINT DF_Orders_Channel DEFAULT (0)
WITH (ONLINE = ON);     -- and retry on 1222 rather than blocking the queue behind you

-- resumable batched backfill for the non-constant case
DECLARE @rows int = 1;
WHILE @rows > 0
BEGIN
    UPDATE TOP (5000) o SET o.Channel = dbo.fn_DeriveChannel(o.SourceRef)
    FROM dbo.Orders o WHERE o.Channel IS NULL;
    SET @rows = @@ROWCOUNT;
    WAITFOR DELAY '00:00:00.200';   -- give the log and replicas room to breathe
END

Follow-ups

  • How do you size the batch? — Small enough to stay under lock escalation (~5,000 row locks) and to keep each transaction short; tune against log growth and replica lag, not against a guess.
  • What about Always On availability groups? — Batching also protects synchronous replicas from log flooding; watch redo queue and send rate during the backfill and throttle on them.
  • Is a NOT NULL column with a default always metadata-only? — No: it depends on version, edition and the default being a runtime constant. Verify with a test on a restored copy before claiming it, because the failure mode is a full table rewrite.

Wrong answer: "We'd take a maintenance window and run the ALTER." It is the honest fallback, but as a first answer it skips the entire craft — metadata-only paths, lock priority, batching, resumability — and organisations doing modernization are usually trying to escape exactly that habit.

The team wants to rename a column to something sensible. Talk me through it. mid

Answer. A rename is a drop plus an add from the application's point of view, so it goes through expand/contract like anything else: add the new column, write to both, backfill, switch reads, bake, drop the old one. sp_rename is atomic and instant but breaks every deployed code path referencing the old name at the same instant, which means downtime and no rolling deploy. The subtlety worth raising: the rename usually is not worth doing at all. If the goal is a nicer name in application code, the ORM can map it ([Column("OLD_NAME")] or a fluent mapping) at zero risk, and the physical name stays until the table is retired. So my actual answer in a review is: map it in code now, and rename physically only if you are already rewriting that table's access path — plus check the dependency surface first, because views, stored procedures, synonyms, reports, ETL jobs and index definitions reference it too, and sys.sql_expression_dependencies does not see dynamic SQL.

Example

// zero-risk alternative to a physical rename
public sealed class Customer
{
    [Column("CUST_EMAIL_ADDR_1")]         // legacy physical name stays
    public string? EmailAddress { get; set; }
}
-- if you do rename, find the blast radius first (and grep for dynamic SQL separately)
SELECT OBJECT_NAME(referencing_id) AS referencing_object, referenced_entity_name, referenced_minor_name
FROM   sys.sql_expression_dependencies
WHERE  referenced_entity_name = 'Customers' AND referenced_minor_name = 'Email';

Follow-ups

  • What about a computed column or a view as the bridge? — A view or a persisted computed column can expose both names during the transition and is a good bridge for report and ETL consumers you do not control.
  • Does sp_rename update dependent objects? — No, and it leaves stale definitions in modules; SQL Server even raises a warning about it. That is the trap the question is set up to catch.
  • Same answer for renaming a table? — Same shape, larger blast radius; a synonym pointing at the new name gives legacy consumers time.

Wrong answer: "sp_rename and update the code in the same deployment." It is instant and it is the classic outage: any instance still running old code, any stored procedure, report or job referencing the old name breaks immediately, and there is no rolling window. The fact that it looks atomic is what makes it dangerous.

How do migrations actually run in your pipeline — and who applies them? senior

Answer. Migrations are their own pipeline stage, run once, before the application deployment, by a principal that has DDL rights the application itself does not have. Concretely with EF Core I generate a migration bundle (a self-contained executable) or an idempotent SQL script in CI, review the SQL as part of the PR, and apply it in a dedicated stage with its own approval and rollback plan; the application's runtime identity keeps only DML permissions. What I do not do is call Database.Migrate() at startup: with more than one instance you get concurrent DDL and a race, it makes startup fail in ways health checks handle badly, and it means the app identity must be able to alter the schema — the largest privilege in the system granted to the most exposed component. For teams with heavy stored-procedure estates I am equally happy with a script-based tool (DbUp, Flyway, SSDT/DACPAC) — the requirement is one owner of the schema, versioned in the same repo, applied by the pipeline, and reviewable as SQL before it runs.

Example

# CI: produce artefacts a human can review and a pipeline can run once
dotnet ef migrations bundle --self-contained -r linux-x64 -o ./artifacts/migrate
dotnet ef migrations script --idempotent --output ./artifacts/migrate.sql

# CD, migration stage (separate identity, separate approval)
./artifacts/migrate --connection "$MIGRATION_CONNECTION"

Follow-ups

  • How do you roll back a migration? — Preferably you do not: forward-only, expand/contract, so a code rollback needs no schema rollback. Destructive steps get a tested down-path or a pre-change backup/snapshot with a documented restore point.
  • Where do stored procedures live? — In the repo as idempotent CREATE OR ALTER scripts applied by the same stage, so the database is fully described by source control.
  • How do you keep EF's model in sync with a DBA-owned schema? — Scaffold and baseline: a compare step in CI that fails when the model and the database drift is worth more than any convention.

Wrong answer: "We call Database.Migrate() on startup so the schema is always current." Convenient in a single-instance dev environment, and in production it is concurrent DDL from N instances, a schema-altering privilege on the app identity, and a change nobody reviewed as SQL. Interviewers treat this as a fast senior/mid separator.

Design a backfill for 800 million rows that must not disturb production. senior

Answer. A backfill is a long-running background job, not a script someone runs in SSMS at midnight. Properties I insist on: batched by primary key range so each transaction is short and lock escalation never triggers; resumable, with the last processed key persisted so a restart continues instead of starting over; throttled by a feedback signal — replica lag, log usage, or measured p95 latency on the live workload — rather than a fixed sleep; idempotent, so re-running a batch is harmless; and observable, publishing progress, rate and estimated completion so it is visible without someone querying it. I run it off-peak with an explicit stop switch, and I reconcile at the end (counts and checksums between source and target) rather than trusting that it finished. On very large tables I would also consider partition-based processing or a shadow table populated in bulk and switched in, but only when the simple batched update genuinely cannot keep up.

Example

while (!ct.IsCancellationRequested)
{
    var lag = await _sql.GetReplicaLagSecondsAsync(ct);
    if (lag > 5) { await Task.Delay(TimeSpan.FromSeconds(30), ct); continue; }  // throttle on a real signal

    var (moved, lastKey) = await _sql.BackfillBatchAsync(_cursor, batchSize: 5_000, ct);
    if (moved == 0) break;

    _cursor = lastKey;
    await _state.SaveCursorAsync(_cursor, ct);          // resumable across restarts
    _metrics.Add(moved);                                 // rate + ETA on a dashboard
    await Task.Delay(TimeSpan.FromMilliseconds(200), ct);
}

Follow-ups

  • How do you handle rows changing while you backfill? — Dual write from the application handles new and updated rows; the backfill only fills historical ones, and the "still NULL" predicate makes it naturally idempotent.
  • How long is acceptable? — Days is fine. A backfill that takes a week and never disturbs anyone beats a four-hour one that causes an incident.
  • How do you prove it is complete? — Zero remaining rows matching the predicate, plus a count/checksum reconciliation and a spot comparison of a random sample.

Wrong answer: "One UPDATE statement over the whole table, run overnight." It escalates to a table lock, generates an enormous transaction log, floods replicas, and if it fails at 90% you have no idea where it stopped — and its rollback can take longer than the update did.

What SQL Server features let you change schema without blocking, and what are their limits? senior

Answer. The main ones: ONLINE = ON index rebuilds and creates (Enterprise; Standard is limited), which still require a brief Sch-M lock at start and end; RESUMABLE = ON for index operations, so a long rebuild can be paused and resumed rather than rolled back — invaluable when your window is shorter than the operation; WAIT_AT_LOW_PRIORITY with an abort action, so your DDL waits politely instead of blocking the queue behind it; partition switching, which moves data in and out of a table as a metadata operation and is the standard trick for archiving and for shadow-table swaps; and READ_COMMITTED_SNAPSHOT at the database level so readers do not block writers in the first place (a change with its own tempdb cost, which is why it is a decision rather than a default). Adding a nullable column and most constraint additions WITH NOCHECK are metadata-only. The limits worth naming: several are Enterprise-only, LOB columns and some data-type changes force a rewrite, and "online" never means "lock-free" — it means "short lock at the boundaries", which on a hot table is still where an outage comes from.

Example

-- polite, resumable, online: the three options that make big DDL survivable
ALTER INDEX IX_Orders_Customer ON dbo.Orders
REBUILD WITH (ONLINE = ON (WAIT_AT_LOW_PRIORITY (MAX_DURATION = 2 MINUTES, ABORT_AFTER_WAIT = SELF)),
              RESUMABLE = ON, MAX_DURATION = 30);

-- pause when the business day starts, resume tonight
ALTER INDEX IX_Orders_Customer ON dbo.Orders PAUSE;
ALTER INDEX IX_Orders_Customer ON dbo.Orders RESUME;

Follow-ups

  • Standard edition, no online rebuilds. What then? — Shadow table plus partition switch, or create a new index under a different name during a quiet window, or accept a short window. Say the edition constraint out loud; it changes the plan.
  • What does ABORT_AFTER_WAIT = SELF mean? — Your DDL gives up rather than the blocking user sessions being killed. BLOCKERS kills theirs — powerful and rarely the right default.
  • Cost of READ_COMMITTED_SNAPSHOT? — Row versioning in tempdb and different behaviour for code that relies on blocking reads; it usually helps, but it is a behaviour change to test, not a switch to flip on Friday.

Wrong answer: "ONLINE = ON means there is no locking, so we can do it any time." The short Sch-M locks at the start and end of an online operation are exactly what blocks a busy table, and on a system with long-running readers they queue behind them and block everything else. That is a real, common outage.

How do you order deployments so that code and schema are never incompatible? senior

Answer. The rule is N-1 compatibility in both directions: any deployed schema version must work with the previous and the next application version, because during a rolling deployment both application versions are live simultaneously. That yields a fixed ordering — additive schema change first, then the code that can use it, then (a release later) the code that stops using the old shape, then the destructive schema change. It also yields a constraint on what a single migration may contain: nothing that the currently-deployed code cannot tolerate. I enforce this with a test matrix in CI — old code against new schema and new code against old schema — which sounds fussy until the first time it catches a dropped column in a release that would otherwise have gone out on a Friday. The reason this is non-negotiable is rollback: application rollback is cheap and frequent, database rollback is expensive and lossy, so the schema must never be the thing that has to move backwards.

Example

Release 1   schema: ADD new column (nullable)          app: unchanged            [old app OK]
Release 2   schema: -                                  app: writes both, reads old
Release 3   schema: backfill complete                  app: reads new, writes both
Release 4   schema: -                                  app: writes new only      [rollback to R3 still OK]
Release 5   schema: DROP old column                    app: unchanged            [R4 still OK, R3 is not]
                                                    ^ the rollback horizon closes here, deliberately

Follow-ups

  • What if a hotfix must skip a step? — It must still satisfy N-1. If it cannot, it needs a window and a written decision — the exception exists, it just is not free.
  • How do you test both directions? — Run the previous release's integration tests against the new schema in CI. It is one extra job and it is the cheapest insurance in the pipeline.
  • Does blue-green deployment remove the need? — No: both slots usually share one database, so N-1 compatibility is exactly what makes blue-green safe.

Wrong answer: "We deploy schema and code together and roll both back together if there's a problem." Rolling a database back means restoring, which discards every transaction since the change — customer data. The asymmetry between cheap code rollback and lossy schema rollback is the whole reason for the ordering.

You are introducing EF Core over a 15-year-old database you cannot restructure. How? senior

Answer. Database-first, with the database as the authority: scaffold the model (dotnet ef dbcontext scaffold), then curate it rather than living with the generated output — real names in code mapped to physical names, no navigation properties you do not want, and value conversions for the legacy encodings (char(1) flags, "0001-01-01" as null, money as scaled integers). Then create a baseline migration representing the existing schema so future changes are versioned without EF attempting to create the world. Practical rules I would state: keep the mapping in a configuration class per entity rather than attributes on shared models; use keyless entity types or raw SQL for the reporting queries that were never going to map cleanly; keep existing stored procedures where they encode real logic and call them from EF rather than reimplementing them mid-migration; and add a CI check that fails when the scaffolded model and the live schema drift, because in a shared database somebody will change a column without telling you. And I would not turn on lazy loading — in a legacy schema with wide navigation graphs it is an N+1 factory.

Example

dotnet ef dbcontext scaffold "Name=Legacy" Microsoft.EntityFrameworkCore.SqlServer \
  --context LegacyContext --output-dir Models --context-dir Data --no-onconfiguring --use-database-names
public sealed class OrderConfig : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> b)
    {
        b.ToTable("ORD_HDR", "dbo");
        b.HasKey(o => o.Id);
        b.Property(o => o.Id).HasColumnName("ORD_ID");
        b.Property(o => o.IsCancelled).HasColumnName("CNCL_FLG")
         .HasConversion(v => v ? "Y" : "N", v => v == "Y");          // legacy char flag
        b.Property(o => o.TotalMinor).HasColumnName("ORD_TOT_PENCE");
    }
}

Follow-ups

  • EF Core or Dapper for a legacy schema? — Often both: Dapper for the gnarly report and bulk paths, EF Core for the transactional aggregate work. Insisting on one tool for a 15-year-old schema is dogma.
  • How do you avoid a performance regression versus hand-written SQL? — Assert query counts in tests, log generated SQL in CI for the hot paths, and keep AsNoTracking for reads. Watch for client-side evaluation surprises across EF majors.
  • Do you migrate the stored procedures into C#? — Only where they are being replaced by a new implementation anyway. Rewriting working SQL for aesthetic reasons is unpaid risk.

Wrong answer: "We'd redesign the schema properly and use code-first migrations." That converts an incremental adoption into a full data migration, with backfills and cutovers, before you have delivered anything. Adopt the ORM over the schema you have; change the schema later, with expand/contract, where there is a reason.

Extract one service's data out of a shared database with no downtime. Design it. principal

Answer. Five phases, each independently reversible. First, encapsulate: all access to those tables goes through the owning service's API, so you know every reader and writer — usually the longest phase, and the one that delivers value even if you stop there. Second, replicate: stand up the new store and populate it with an initial copy plus ongoing change data capture, so it converges without the application knowing. Third, verify: continuous reconciliation of counts, checksums and business totals, plus a read-comparison in shadow mode until divergence is explained and stable. Fourth, switch reads with a flag and a ramp, watching per-cohort business metrics rather than just error rates. Fifth, switch writes — the only genuinely dangerous step — with a short write-freeze on that entity (seconds, via a queue or a lock), a final CDC drain, then writes to the new store while the old one is kept in sync for the rollback horizon. Then, and only then, contract: stop the sync, drop the old tables, and remove the last cross-boundary joins. I would explicitly reject bidirectional dual writes: they have no consistent ordering story, and the reconciliation problem they create is worse than the freeze they avoid.

Example

P1 encapsulate  all readers/writers -> Orders API              (reversible, valuable alone)
P2 replicate    snapshot + CDC -> new store                    (invisible to users)
P3 verify       counts/checksums/business totals + shadow reads
P4 read switch  flag ramp 1% -> 100% by tenant, per-cohort dashboards
P5 write switch brief per-entity freeze -> drain CDC -> new store authoritative
                old store kept in sync (reverse CDC) for the rollback horizon
P6 contract     stop sync, drop tables, delete cross-boundary joins

Follow-ups

  • How long is the write freeze? — Seconds, scoped per entity or per tenant, not global: queue writes at the API, let CDC catch up, flip the authority, drain the queue.
  • What if a report joins across the boundary? — Move reporting to a replicated read model or a warehouse. A cross-service join in the transactional path is the boundary telling you it is wrong.
  • What is your rollback after the write switch? — The reverse sync you set up in P5, plus the flag. If you have not built the reverse path, you have a one-way door and should say so before the cutover, not during it.

Wrong answer: "Dual-write to both databases from the application until they're in sync, then switch." Dual writes fail partially (one succeeds, one fails), have no ordering guarantee under concurrency, and leave you reconciling divergence by hand at exactly the wrong moment. CDC or an outbox gives you a single source of truth and ordered propagation; that distinction is the point of the question.

06Database platform migration & cutover

Moving the database itself — version upgrade, or SQL Server to Azure SQL — is the highest-stakes single event in most modernization programmes, and the calendar makes it current: SQL Server 2016 left extended support on 2026-07-14, so a large number of estates are being forced through this right now. Mid depth is naming the destinations and the assessment tools; senior depth is a rehearsed cutover plan with reconciliation and a rollback; principal depth is a near-zero-downtime move and the honest trade-offs between managed instance, single database and a VM.

Docs: Azure Database Migration Guides · Managed Instance link · Compatibility level · SQL Server end of support

SQL Server 2016 is out of support since July. What are the options and how do you choose? mid

Answer. Four destinations and one stopgap. In-place or side-by-side upgrade to a supported SQL Server (2019, 2022, or 2025, which went GA on 2025-11-18) — cheapest change, keeps everything, keeps the operational burden. SQL Server on an Azure VM — same surface again, plus Azure Hybrid Benefit and free ESUs for out-of-support versions running there, which is why it is such a common landing spot for the truly frozen systems. Azure SQL Managed Instance — near-full instance compatibility (SQL Agent, cross-database queries, Service Broker, CLR), managed patching and backups, and the usual destination for a lift of an existing estate. Azure SQL Database — the most managed and the most constrained (no SQL Agent, no cross-database queries, database-scoped), best for applications you are modernizing anyway. The stopgap is Extended Security Updates, which buys time at a price and buys nothing else. I choose by counting instance-level dependencies: if the application uses Agent jobs, linked servers, cross-database joins and CLR, Managed Instance or a VM; if it is a self-contained database, Azure SQL Database and take the operational win.

  • How do you find the instance-level dependencies? — An assessment run (Azure Migrate / Data Migration Assistant lineage tooling) plus your own inventory of Agent jobs, linked servers, cross-database references, CLR assemblies, and anything reading the file system.
  • Would you migrate to PostgreSQL to save licence cost? — Only as a deliberate, separately funded project: T-SQL, stored procedures, ORM behaviour and operational tooling all change at once. Doing it inside a modernization already in flight doubles the risk for a cost saving that is rarely the binding constraint.
  • Where does SQL Server 2025 matter? — It is the current release (GA 2025-11-18) and the target if you are staying on-prem; note it also brings built-in vector/AI features that occasionally change the buy-versus-build conversation.

Wrong answer: "Move it to Azure SQL Database — it's the most modern option." It is the most managed, not the most compatible, and a legacy estate usually depends on instance-level features it simply does not have. Choosing the destination before inventorying the dependencies is how a migration discovers in week six that 40 Agent jobs have nowhere to run.

What is the compatibility level, and what breaks when you raise it? mid

Answer. The compatibility level controls which query-optimizer and language behaviours a database uses, independently of the engine version — so you can run a database on SQL Server 2025 at level 130 (2016 behaviour) and change it later. That decoupling is the standard upgrade technique: move the engine first, keep the old level, then raise the level as a separate, reversible change under Query Store. What breaks when you raise it is almost always plan-related: the cardinality estimator changed in 2014 (level 120), and a query tuned against the legacy estimator can regress badly — the classic upgrade horror story is a report that ran in 8 seconds taking 40 minutes. The modern mitigation is Query Store plus automatic plan correction: capture baselines before the change, raise the level, and let forced plans or your own sp_query_store_force_plan handle regressions while you fix the queries. Other things to check: deprecated syntax finally removed, changed default behaviours (string truncation messages, STRING_AGG and function behaviour), and hints that no longer do what they did.

Example

-- upgrade sequence that keeps the plan risk separate from the engine risk
ALTER DATABASE Sales SET COMPATIBILITY_LEVEL = 130;    -- keep 2016 behaviour after the engine move
ALTER DATABASE Sales SET QUERY_STORE = ON (OPERATION_MODE = READ_WRITE);
-- collect a baseline for a full business cycle, then:
ALTER DATABASE Sales SET COMPATIBILITY_LEVEL = 160;    -- SQL Server 2022 behaviour
ALTER DATABASE Sales SET AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = ON);

-- targeted escape hatch for a single regressed query, without going back a level
SELECT ... OPTION (USE HINT ('FORCE_LEGACY_CARDINALITY_ESTIMATION'));

Follow-ups

  • How do you find regressions before users do? — Query Store's regressed-queries view, or replay a captured workload (Distributed Replay / a captured trace) against both levels and compare durations and reads.
  • Is staying on an old compatibility level forever acceptable? — It is supported, and it forgoes years of optimizer improvements while accumulating a cliff you will eventually have to jump. Treat it as a dated exception.
  • Does Azure SQL let you control this? — Yes, the compatibility level is per database there too, which is what makes a staged Azure migration feasible.

Wrong answer: "Upgrade the engine and set the latest compatibility level so we get the newest optimizer." Doing both at once means that when performance falls over, you cannot tell whether it is the engine, the hardware, the statistics or the estimator — and you have no baseline to compare with. Separate the changes; that is the whole point of the setting existing.

How do you get a 2 TB SQL Server database into Azure SQL Managed Instance? senior

Answer. Assess, then replicate, then cut over. Assessment first: run the Azure Migrate/Data Migration Assistant-style assessment to find blocking features (unsupported instance features, filestream, cross-instance dependencies, unsupported collations) and size the target — vCores, storage tier and, critically, the IO characteristics, since the General Purpose tier's remote storage latency is the most common cause of "it's slower in the cloud". For the move itself the modern route is the Managed Instance link: it uses distributed availability groups to replicate continuously from your SQL Server to MI, so the target stays current for as long as you need to test, and failover is a short, controlled event rather than a restore. The alternatives are Azure Database Migration Service in online mode (log-shipping-based) or, if a window is acceptable, native backup to URL and restore. Whichever route, I rehearse the full cutover at least twice on a copy — including the application-side connection string, permissions, Agent jobs and linked-server replacements — and I measure the actual failover duration rather than quoting the documentation.

Example

T-14  assessment fixed; MI sized; link established; target continuously replicating
T-7   rehearsal #1: failover on a copy, run app smoke + reconciliation, measure duration
T-2   rehearsal #2 with the real runbook, including rollback
T-0   freeze writes (app read-only mode) -> final log drain -> failover -> repoint apps
      -> reconcile (row counts, checksums, business totals) -> open writes
      rollback: keep the source available and re-point back; decision point at T+30 min

Follow-ups

  • What is usually slower after the move, and why? — IO latency on General Purpose, and anything chatty over a new network path. Fix with tier choice (Business Critical), indexing, or reducing round trips — not by blaming the platform.
  • What about the things MI does not have? — Instance-level items you must re-home: some linked servers, filestream, cross-instance jobs, and anything touching the local file system. Each needs an owner before cutover day.
  • How do you handle SQL Agent jobs? — MI has Agent, so most come across; check job steps that shell out (xp_cmdshell, CmdExec, SSIS packages) — those need Azure alternatives such as Azure Data Factory / SSIS Integration Runtime.

Wrong answer: "Back up and restore into MI over the weekend." At 2 TB the restore alone can consume the window, you have no rehearsal, no continuous replication and no fast rollback — and you discover the unsupported feature on Saturday night. The link/DMS routes exist so the cutover is a short failover rather than a race against a backup file.

Write me the cutover runbook. What is in it? senior

Answer. A runbook is a rehearsed, timed, step-by-step document with named owners, and its most important sections are the ones people skip: the go/no-go criteria agreed in advance, the rollback procedure with its own steps and its own decision deadline, and the verification that decides success. Structure: pre-cutover checks (replication lag zero, backups verified, target smoke-tested, support and business stakeholders on the call), the freeze (put the application into a read-only mode rather than "ask people not to use it"), the switch itself with each step timed from the rehearsal, verification (technical smoke tests plus a business reconciliation someone from the business signs), then the ramp back to full traffic and an explicit "we are past the rollback point" announcement. I also insist on a comms plan and a scribe, because the difference between a controlled cutover and an incident is often just whether anyone recorded what happened at 02:14. And every step has an expected duration from rehearsal — a runbook nobody has timed is a wish list.

Example

GO/NO-GO (T-60m)   lag=0 | backup verified < 2h old | rehearsal signed off | on-call staffed
                   business rep present | rollback owner named | no open Sev1/Sev2
T-15  app -> read-only mode (banner + 503 on writes), queue depth watched
T-00  final drain; failover; repoint connection strings (config, not deploy)
T+05  smoke: login, place order, run report, background job heartbeat
T+15  reconcile: row counts, 5 business totals vs pre-cutover snapshot, sign-off by Finance
T+30  DECISION: proceed (open writes) or roll back (documented, rehearsed, 12 min)
T+60  monitoring watch: error rate, p95, queue depth, deadlocks for 2 hours
T+1d  retrospective; delete the old path from the runbook, not from memory

Follow-ups

  • What makes a rollback impossible? — Writes landing only in the new store with no reverse sync. Know your point of no return, put a time on it, and announce when it passes.
  • How many rehearsals? — At least two, the second on the real runbook with the real people. The first rehearsal is always the one that finds the missing firewall rule.
  • Who calls the abort? — One named person, agreed beforehand, using the pre-agreed criteria — not a committee at 3am with sunk-cost bias.

Wrong answer: "We take a backup before we start, so we can always restore." A restore is not a rollback plan once users have written to the new system, it takes an unknown amount of time you have never measured, and it says nothing about the application tier, the queues or the caches. Rollback must be rehearsed and timed like everything else.

How do you prove the data arrived correctly? senior

Answer. Three layers, cheapest first. Structural: row counts per table, plus object counts (indexes, constraints, procedures, users and permissions) — permissions are the ones people forget and they surface as a broken job on Monday. Content: checksums or hash aggregates over each table's key columns, and full comparison on the tables that matter most; tablediff, a hash-based comparison query, or a data-compare tool all work — what matters is that it is automated and repeatable, because you will run it several times. Business: a handful of totals the business already trusts — today's order count, month-to-date revenue, open balances, the number of active users — computed on both sides and signed off by someone from the business, since these catch semantic problems (a time zone shift, a collation change, a truncated decimal) that row counts cannot. I run all three in every rehearsal so the comparison scripts themselves are proven before the night it matters, and I keep a pre-cutover snapshot of the business figures so the comparison is against a fixed point rather than a moving system.

Example

-- content check that is cheap to run repeatedly and catches value-level drift
SELECT CHECKSUM_AGG(BINARY_CHECKSUM(OrderId, CustomerId, TotalMinor, StatusCode)) AS chk,
       COUNT_BIG(*) AS rows_
FROM   dbo.Orders WITH (NOLOCK IS NOT USED);

-- collation and unicode traps show up here, not in COUNT(*)
SELECT TOP 100 CustomerId, FullName FROM dbo.Customers ORDER BY FullName;   -- compare ordering both sides

Follow-ups

  • What do you do when counts match and a total does not? — Suspect collation, decimal scale, time zone or a filtered index. Binary-search by narrowing the aggregate to a date range and then to rows.
  • Is CHECKSUM_AGG reliable? — Good enough as a fast detector; it can collide, so use it as a screen and a stronger hash or a full compare on the critical tables.
  • What about the things outside the database? — Blobs, file shares, search indexes and caches migrate too and are frequently forgotten. Count and sample them the same way.

Wrong answer: "The migration tool reports success and row counts match, so the data is correct." Row counts survive truncated strings, shifted times, changed collation ordering, lost precision and dropped permissions. Business totals verified by a business person are the check that actually finds those, and volunteering it is what separates a senior answer here.

Azure SQL Database, Managed Instance, or SQL on a VM — argue the choice. senior

Answer. Argue it as a trade of compatibility against operational burden, with cost as an output rather than an input. SQL on a VM is full compatibility and full responsibility — you patch, you back up, you configure HA — and it is the right choice for a frozen application, for instance-level features nothing else supports, and as a short lift-and-shift step that stops the clock on an unsupported OS. Managed Instance gives near-full instance compatibility (Agent, cross-database queries, Service Broker, CLR, linked servers within limits) with managed patching, backups and HA, and it is the default landing zone for an existing estate; the costs are a VNet requirement, a bigger price floor and less elasticity. Azure SQL Database is the most managed and the most elastic — serverless, elastic pools, hyperscale for very large data — but is database-scoped: no Agent, no cross-database joins, and applications must handle transient faults and connection resilience properly. My rule: if the application is being modernized anyway, aim for Azure SQL Database and design out the instance-level dependencies; if the application is not changing, Managed Instance; if it cannot change at all, a VM with a dated review.

Example

// non-negotiable on any Azure SQL target: retry on transient faults, and managed identity
builder.Services.AddDbContextPool<OrdersContext>(o => o.UseSqlServer(cs, sql =>
{
    sql.EnableRetryOnFailure(maxRetryCount: 6, maxRetryDelay: TimeSpan.FromSeconds(30), null);
    sql.CommandTimeout(30);
}));
// connection string: "Server=...;Authentication=Active Directory Default;Encrypt=True;" - no password

Follow-ups

  • Why do transient faults matter so much more in the cloud? — Managed platforms move your database (patching, failover, scaling), so short disconnects are normal operation rather than incidents. Code that never retried on-prem will look broken.
  • When is Hyperscale the answer? — Multi-terabyte databases needing fast backups/restores and rapid read-scale; it changes the backup and restore story more than the query story.
  • Does the choice affect the application code? — Yes: cross-database queries, Agent jobs, xp_cmdshell, and distributed transactions all need alternatives on Azure SQL Database. That is the real cost line.

Wrong answer: "PaaS is always better, so Azure SQL Database." "Always" is the tell. The correct answer names the dependency inventory as the deciding input and accepts that a VM is sometimes the right, boring choice — particularly as a first step that removes an unsupported OS without touching the application.

The business will not accept any downtime at all. How do you move the database? principal

Answer. I start by negotiating the requirement, because "zero downtime" and "zero downtime for writes on this one entity" have wildly different price tags: a few seconds of queued writes is usually acceptable once the alternative is priced, and getting that agreed is often the highest-value five minutes of the project. Assuming a genuinely near-zero requirement, the shape is: continuous replication to the target (MI link / distributed AG / DMS online / log shipping) so the target is always current; application changes first so it can talk to either target through configuration; a read cutover ahead of the write cutover, with reads served from the target while writes still go to the source; then a brief, per-entity write pause implemented in the application — queue or reject-and-retry — while the final log drains and the roles swap; then reverse replication so rollback remains possible for a defined window. The parts that make it real are rehearsal (three times, timed), idempotent and retry-safe clients so a few seconds of failures are invisible to users, and monitoring that watches business metrics, not just uptime. And I would say plainly what the residual risk is: there is always a moment where authority moves, and engineering it down to seconds is achievable while engineering it to zero is marketing.

Example

// the write pause users never see: queue + retry-after, seconds long, per entity
if (_cutover.State == CutoverState.WritesPaused)
{
    await _queue.EnqueueAsync(command, ct);          // durable, idempotent, ordered per key
    return Results.Accepted($"/operations/{command.Id}");
}
// clients already poll the operation endpoint, so a 3-second pause is a slightly slower save

Follow-ups

  • What is the residual risk you would state to the sponsor? — The authority switch itself, the possibility of a longer-than-rehearsed drain under peak load, and the rollback window closing once new writes exist only on the target.
  • How do you keep rollback available afterwards? — Reverse replication for a defined window, plus a documented decision point at which you stop it and accept one-way.
  • Does an async, queue-based write model help? — Enormously: if writes are already commands processed asynchronously, a pause is a queue depth spike rather than an outage. That property is worth building before the migration, not during it.

Wrong answer: "We'd dual-write to both databases from the application so there is never a switchover." Dual writes across two systems have no atomicity and no ordering guarantee; under concurrency you get divergence you must reconcile manually, and the failure is silent. Replicate with CDC/log shipping, keep one authority, and make the authority switch short.

07Monolith decomposition & boundaries

Modernization interviews use decomposition to test judgment rather than knowledge: the microservices question is a trap with a right answer that starts "it depends what problem you are solving". Mid depth is knowing that a modular monolith is usually the correct first step; senior depth is finding boundaries from real evidence, handling the shared-kernel assembly and the consistency consequences of splitting; principal depth is recognising a distributed monolith early and being willing to merge services back. Expect follow-ups aimed at whether you would create a distributed system for an organisational problem.

How do you find service boundaries in a monolith you did not write? screener

Answer. From evidence, in this order. Language and process: the capabilities the business names and owns separately ("ordering", "billing", "fulfilment") are the strongest candidates, because a boundary that matches how the organisation actually works stays stable. Data: which tables are written by which code paths — a cluster of tables written by one area and read-only elsewhere is a boundary announcing itself, and a table written by six areas is a warning. Change: files that change together, from the commit history, belong together; teams that always have to coordinate a release are inside one boundary, not two. Runtime: call graphs and traces show the chatty paths that must not be split, because a boundary drawn across a hot, synchronous, high-cardinality path buys latency and coupling with no benefit. Then I sanity-check each candidate with two questions: can it own its data, and can it be deployed and rolled back independently? If the answer is no, it is a module, not a service — yet.

Example

# cheap coupling signal: which files keep changing in the same commit?
git log --since=2.years --name-only --pretty=format:"%H" |
awk 'NF' | ... # group by commit, count co-occurring pairs, rank
# the top pairs across "module" folders are the boundaries your code does not really have
-- which code paths write which tables (Extended Events / Query Store, over a full cycle)
SELECT t.name AS table_name, COUNT(DISTINCT qt.query_sql_text) AS writers
FROM   sys.tables t JOIN /* query store texts filtered to INSERT/UPDATE/DELETE */ qt ON ...
GROUP  BY t.name ORDER BY writers DESC;   -- 6 writers = not a boundary yet

Follow-ups

  • What if the business language does not match the code at all? — That mismatch is itself the finding; run an event-storming session with the business and use the resulting process model as the target, then measure how far the code is from it.
  • How do you validate a proposed boundary before committing? — Enforce it as a module first (compile-time, no shared internals) and see whether normal feature work keeps violating it. Cheap to reverse, and it produces evidence.
  • Which boundary is always wrong? — Layer boundaries: a "data service", "business service" and "UI service" split gives you a distributed system where every feature still touches all three.

Wrong answer: "We'd split it along the existing project or layer structure — that's already the modularization." The existing structure is the artefact of the problem you are fixing, and layer-shaped services are the canonical distributed monolith: every change spans all of them, so you pay network cost and deployment coordination for zero independence.

Does modernization mean microservices? mid

Answer. No, and treating them as synonyms is the most expensive confusion in the field. Microservices solve organisational and operational problems — independent deployment for independent teams, independent scaling of genuinely different load profiles, fault isolation — at the price of network failure, distributed data, distributed debugging and a serious operations investment. Most legacy systems' problems are lack of modularity, no tests, an unsupported runtime and a fear of deploying; a distributed architecture fixes none of those and makes each one harder. The route I recommend is a modular monolith first: enforce module boundaries in one deployable, with each module owning its tables and talking through explicit contracts. That gets the design benefit immediately, and it makes extraction a mechanical step later if and when the organisational need is real. The framing that lands well in an interview: extract a service when you can name the specific problem — this team's release is blocked by that team's, or this component needs to scale 20x independently — and can pay for the operational consequence.

Example

Problem                               Right tool
"our releases block each other"       independent deployables (services) - if teams are also independent
"this one job needs 40 machines"      extract that job, or scale it out separately
"a bug in reports takes down orders"  process isolation - service or separate worker
"the code is a mess"                  modules, tests, boundaries - NOT services
"we can't deploy safely"              CI/CD, tests, flags - NOT services

Follow-ups

  • What makes a modular monolith real rather than aspirational? — Compile-time enforcement: separate projects, internal types, an architecture test that fails the build on a cross-module reference, and one module owning each table.
  • Does a modular monolith scale? — Vertically and by running multiple instances, which is enough for the vast majority of systems. Independent scaling of one component is a specific need, not a general one.
  • What do you say to a team that wants microservices for their CV? — Name it kindly, then redirect: agree the target design, deliver it as modules first, and make extraction the second step with a stated trigger.

Wrong answer: "Yes — modern architecture means microservices, so we'd decompose into services as we migrate." Doing the runtime migration and a distributed rearchitecture simultaneously multiplies risk: two sets of unknowns, no ability to attribute a regression, and an operations bill your team is not yet equipped to pay. Migrate first, decompose when the need is demonstrated.

Everything depends on a giant Common assembly. How do you break it up? senior

Answer. First I stop it growing — a build rule that fails a PR adding new public types to it — because the shared-kernel assembly is a ratchet, and any plan that does not stop the ratchet fails. Then I classify its contents rather than treating it as one thing: genuinely generic infrastructure (result types, guard clauses, retry helpers) can become a small, versioned package; domain concepts that leaked in (a Customer class used by five modules with different meanings) must be split per module, even at the cost of "duplication", because that duplication is the boundary reasserting itself; and cross-cutting integrations (a mail sender, a PDF wrapper) become owned components with explicit contracts. Practically I move types out leaf-first, using the compiler as the guide, and I accept that two modules having their own slightly different Address type is not a defect — the shared type is what forced every consumer to change together in the first place. Cyclic dependencies get broken by inverting one direction (an interface owned by the consumer, implemented by the provider) or by publishing an event instead of calling.

Example

// NetArchTest / ArchUnitNET as a unit test - the boundary that fails the build
[Fact]
public void Ordering_does_not_reference_Billing_internals()
{
    var result = Types.InAssembly(typeof(OrderService).Assembly)
        .That().ResideInNamespace("Contoso.Ordering")
        .ShouldNot().HaveDependencyOn("Contoso.Billing.Internal")
        .GetResult();
    Assert.True(result.IsSuccessful, string.Join(", ", result.FailingTypeNames ?? []));
}

Follow-ups

  • Is duplicating a model not a violation of DRY? — DRY is about knowledge, not about text. Two modules with different reasons to change should not share a type; coupling them to avoid duplication is the more expensive mistake.
  • How do you version the extracted infrastructure package? — Semantically, with a short support window for the previous version, published to an internal feed. If every consumer must upgrade in lockstep, you rebuilt Common.
  • What about the utility class nobody understands? — Check usage; the majority of a legacy Common assembly is usually dead. Delete first, then split what remains.

Wrong answer: "We'd turn Common into a NuGet package so it's properly shared." That formalises the coupling and adds version skew on top: now every module must agree on a version, and a change to a shared domain type becomes a coordinated multi-repo release. Package the genuinely generic 10%; split the rest.

Which component do you extract first, and why that one? senior

Answer. I want the first extraction to teach the team the pattern at the lowest possible risk, so I look for a component with a clean data boundary (few tables, ideally written only by itself), a clear owner, low transactional coupling with the rest, and enough real traffic that the exercise proves something. Notification/email sending, document generation, search, and read-only reporting endpoints are classic first extractions for exactly those reasons. What I avoid first is the core transactional aggregate (orders, payments) — highest coupling, highest consistency stakes, worst place to learn — and anything with no traffic, which teaches you nothing. After the first one, the ordering shifts to value: the components blocking releases or needing independent scale. I would also say the first extraction should be treated as an experiment with a written hypothesis — "this will let team B deploy without team A, and cost us one extra service to operate" — so that at the end you can say whether it worked before repeating it nine times.

  • What if the painful component is the core one? — Then strangle it in place (modularize, add tests, split reads from writes) rather than extracting it first. Extraction is not the only way to reduce pain.
  • How do you know the extraction succeeded? — Deploy independence actually used, no increase in incident rate, and no new synchronous dependency in the hot path. If the extracted service must be up for orders to work, you moved a dependency, not removed one.
  • How long should the first one take? — Weeks, not quarters. If your smallest, cleanest extraction takes a quarter, that is the signal about the rest.

Wrong answer: "Start with the most business-critical component, since that's where the value is." Highest value, highest coupling, highest consistency risk, and the team has never done this before — that is how a decomposition programme gets cancelled after its first incident. Prove the pattern on something safe, then aim it at the valuable target.

After splitting, an operation spans two services. How do you keep it consistent? senior

Answer. You give up the ambient database transaction and design the consistency explicitly. Within one service, keep the local transaction and use the transactional outbox: the state change and the outbox row commit together, and a relay publishes the message afterwards, which gives at-least-once delivery without a distributed transaction. Across services, model the flow as a saga — a sequence of local transactions with compensating actions for the steps that need undoing — and choose orchestration (a coordinator holding the state machine) when the flow is complex or needs visibility, choreography (services reacting to events) when it is simple and you want low coupling. The consequences you must state unprompted: consumers must be idempotent because messages will be redelivered; ordering is only guaranteed per key at best; compensation is a business decision, not a rollback (a refund is not the inverse of a charge); and the user experience has to accommodate "in progress" states. And the honest senior point: if a flow genuinely needs atomicity across two services, that is evidence the boundary is wrong, and merging them is a legitimate answer.

Example

// outbox: state + message commit in ONE local transaction
using var tx = await db.Database.BeginTransactionAsync(ct);
db.Orders.Add(order);
db.Outbox.Add(new OutboxMessage(
    Id: Guid.CreateVersion7(),                       // time-ordered id, .NET 9+
    Type: nameof(OrderPlaced),
    Payload: JsonSerializer.Serialize(new OrderPlaced(order.Id, order.TotalMinor)),
    OccurredUtc: TimeProvider.System.GetUtcNow()));
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
// a relay publishes and marks sent; consumers dedupe on message id (at-least-once)

Follow-ups

  • Why not two-phase commit? — MSDTC-style distributed transactions are not available across modern .NET services and cloud data stores, they couple availability (any participant down blocks all), and they scale badly. The outbox plus idempotency is the accepted replacement.
  • How do consumers become idempotent? — A processed-message table keyed by message id inside the same transaction as the effect, or naturally idempotent operations (set to a value rather than increment).
  • What does the user see mid-saga? — An explicit pending state with a real status endpoint. Pretending the operation is synchronous when it is not is how you get double submissions.

Wrong answer: "We'd wrap both calls in a TransactionScope so it's atomic." Across service boundaries and cloud databases there is no distributed transaction manager to enlist, and even where something appears to work it is fragile and blocking. This is a fast credibility check: the expected words are outbox, idempotency, saga, compensation.

How do you spot a distributed monolith, and what do you do about it? senior

Answer. The signals are all about coupling that survived the split. Services that must be deployed together or in a specific order; a change to one service's contract requiring a coordinated release of three others; shared database tables written by several services; synchronous call chains three or four deep on the request path, so availability multiplies down; a shared library that every service must upgrade in lockstep; and the human tell — the team says "we can't release until service X ships". The fix is not more services, it is removing the coupling: give each service its own data, replace synchronous chains with events or with data replicated into a local read model, version contracts so old and new coexist, and merge services that genuinely cannot be decoupled. I would also point out the availability arithmetic to make it concrete: four services at 99.9% in a synchronous chain give roughly 99.6% — worse than the monolith they replaced, with more moving parts to debug.

Example

Symptom                                  Cure
release trains / ordered deploys         contract versioning; consumer-driven contract tests
shared tables between services           one owner per table; replicate a read model
sync chain A -> B -> C -> D              events, or cache/replicate what A needs from D
lockstep shared NuGet upgrade            shrink the shared package to genuinely stable primitives
"blocked on team X" every sprint         the boundary is wrong: merge, or move the capability

Follow-ups

  • How do you measure it rather than argue about it? — Count co-deployments, cross-service change coupling in the commit history, and the depth of synchronous call chains in traces. All three are objective and trend over time.
  • Is a synchronous call between services always bad? — No — a shallow, well-bounded call with a timeout, a fallback and a circuit breaker is fine. Chains and fan-out on the request path are what kill you.
  • What is the cheapest fix that usually helps most? — Removing the shared database write path. It unlocks independent deployment more than anything else.

Wrong answer: "We'd add an API gateway and a service mesh to manage the coupling." Infrastructure makes the coupling observable and slightly more survivable; it does not remove it. The coupling is in the data ownership and the contracts, and no mesh will fix a table written by four services.

How do you enforce module boundaries in a .NET solution so they do not erode? senior

Answer. Make violations a build failure, because anything else erodes under deadline pressure. The layers I use: one project per module with only the intended project references (the reference graph is the first boundary and it is compiler-enforced); internal as the default accessibility with a small public contract surface per module, so a neighbouring module physically cannot reach the internals; architecture tests (NetArchTest, ArchUnitNET) asserting the allowed dependency directions, including "no module references another module's Internal namespace" and "domain does not reference EF Core"; and analyzers or banned-API rules for the specific things that keep creeping back (DbContext outside the owning module, HttpContextAccessor in the domain). Data boundaries are enforced separately, with a schema per module and permissions per identity, so a module cannot quietly query someone else's tables. For local development .NET Aspire is a genuinely useful addition — it orchestrates the modules and their dependencies as a runnable app graph, which keeps a modular design from becoming painful to run.

Example

src/
  Ordering/ Contoso.Ordering.Contracts   (public: DTOs + interfaces other modules may use)
            Contoso.Ordering             (internal: domain, EF model, schema "ordering")
  Billing/  Contoso.Billing.Contracts
            Contoso.Billing              (may reference Ordering.Contracts, never Ordering)
  Host/     Contoso.Api                  (references every module; the only composition root)
tests/      Contoso.ArchitectureTests    (fails the build on a forbidden reference)

Follow-ups

  • Someone needs data from another module's tables for a report. — Either a contract query on the owning module, or a reporting read model fed by events. Not a join — a join is the boundary dissolving.
  • Does this slow the team down? — Slightly, at exactly the moments where slowing down is the point. The alternative is the coupling you are paying to remove.
  • How does this help later extraction? — A module with its own contracts, schema and no inbound internal references becomes a service by changing the transport. That is the payoff for the discipline.

Wrong answer: "We agree on the boundaries as a team and enforce them in code review." Code review catches it on a good week; on a bad week, under a deadline, with a new joiner, it does not — and one accepted violation legitimises the next. Boundaries that are not machine-checked are aspirations.

When would you merge services back together? principal

Answer. When the evidence says the boundary is not real: two services that always change together, that must be deployed in order, that share data, or whose combined on-call burden exceeds any independence benefit. Also when the operational overhead is not being paid for — a five-person team running fifteen services is spending its capacity on deployment pipelines and distributed debugging rather than on the product. And when a synchronous chain has made the composite less available than the monolith it replaced. Merging is a legitimate, senior move, and being willing to say so is what the question is testing: architecture decisions are hypotheses, and reversing one on evidence is a strength, not an admission of failure. Practically I merge the same way I split — with characterization tests, a facade preserving the external contract so callers do not notice, and one behaviour change at a time — and I write down what the original hypothesis was and which observation falsified it, so the organisation learns rather than just oscillating.

Example

Evidence gathered over 2 quarters:
  co-deployment rate  Orders + Pricing   87% of releases      -> not independent
  cross-service calls per request        6 (p95 adds 140 ms)  -> chatty
  incidents attributed to the boundary   4 of 9               -> negative value
  shared tables                          2                    -> not autonomous
Decision: merge Pricing into Orders; keep the public contract; revisit if pricing
          gains its own team and its own release cadence.

Follow-ups

  • How do you present this without it looking like failure? — As designed learning: the split was a hypothesis, here is the data, here is the cheaper design. Teams that cannot reverse decisions accumulate them.
  • What do you keep from the split? — The module boundary, the contracts and the tests. You are removing the network, not the design.
  • Does this argue against ever splitting? — No: it argues for splitting on evidence and with a stated hypothesis, so you can tell later whether it paid.

Wrong answer: "You wouldn't — going back to a monolith is a regression." That treats architecture as a ratchet and ideology as evidence. The strongest answers in this sub-area are the ones willing to undo their own earlier decision when the measurements say so.

Where the code ends up, and the sub-area where a candidate's real cloud experience shows fastest. Interviewers listen for whether you would replatform pragmatically or insist on a full cloud-native rebuild.

App Service, Container Apps, AKS, Functions or VMs — how do you choose? screener

Answer. Cheapest abstraction that meets the requirement, and requirements here means networking, runtime control and operating model rather than fashion. App Service for a standard web application or API — least to operate, deployment slots, autoscale, and it hosts Windows workloads including .NET Framework, which is exactly why it is such a common first landing zone. Container Apps for containerized services and background workers when you want serverless scale (including scale to zero and KEDA-driven scaling) without owning a cluster. AKS when you genuinely need Kubernetes: complex networking, custom operators, an existing Kubernetes operating model, or a platform team that already runs it. Functions for event-driven and scheduled work with a natural trigger, where the unit of deployment is small. VMs when the software demands a machine — legacy installers, COM components, third-party services, or a lift-and-shift step to stop the clock on an unsupported OS. My default sequence in a modernization: VM or App Service to get out of the data centre, then Container Apps or App Service as the steady state, and AKS only where the need is demonstrated and staffed.

  • Windows containers — worth it? — Sometimes, for a .NET Framework app you want in a container pipeline, but the images are large, cold starts are slow, and platform support is narrower. App Service on Windows is usually the easier answer.
  • How do you decide between App Service and Container Apps for a new API? — Whether you want to own the container. If the team is already building images, Container Apps; if not, App Service and skip the complexity.

Wrong answer: "AKS, because it's the most flexible and everything can run there." Flexibility is the cost, not the benefit: you take on upgrades, node pools, networking, RBAC and a much larger failure surface. Choosing Kubernetes without an operating model to run it is the most expensive default in Azure modernization.

What is the minimum viable change to get a .NET Framework web app into Azure? mid

Answer. App Service on Windows, because it runs .NET Framework applications on IIS without a port. The realistic work is not the code: externalize session state (in-process session breaks the moment you have more than one instance, and App Service will restart instances underneath you), move machine keys and Data Protection to a shared store so cookies and forms authentication survive restarts and scale-out, move connection strings and secrets to App Service configuration or Key Vault, remove dependencies on the local file system (writeable paths, uploaded files, log files) in favour of Blob Storage, and re-home anything that was a Windows scheduled task or a Windows service into WebJobs, Functions or Container Apps jobs. Microsoft's App Service Migration Assistant will do the assessment and much of the mechanical move. This is a replatform, not a modernization, and I would frame it that way to a stakeholder: it removes the data centre and the unsupported OS from the risk register, and it buys the time to do the .NET 10 work properly.

  • What breaks first if you skip session externalization? — Users get logged out or lose their basket at random as requests land on different instances, and it looks like an intermittent bug rather than a configuration issue.
  • Is lift-and-shift not just deferring the work? — It defers the code work and immediately retires the infrastructure risk. As a step with a dated follow-on, it is good sequencing; as a destination, it is a more expensive data centre.
  • What about the local file system in App Service? — There is a writable path, it is shared across instances and it is not durable in the way apps assume. Anything that must persist goes to Blob Storage.

Wrong answer: "You can't run .NET Framework in Azure PaaS — it has to go on a VM." App Service on Windows has hosted .NET Framework applications for years, and assuming otherwise costs the organisation a managed platform and pushes patching back onto the team. It is a common and consequential misconception.

What actually breaks when you containerize a legacy application? senior

Answer. Everything that assumed a long-lived, single, writable machine. Local disk: uploads, caches, generated files and log files vanish when the container is replaced, so they move to Blob Storage or a mounted share. In-process state: session, in-memory caches and static counters break the moment there is more than one replica, and containers make replica count fluid. Logging: file and Event Log sinks become invisible — logs go to stdout/stderr as structured events. Configuration: file-based configuration becomes environment variables and mounted secrets. Scheduled work: Windows scheduled tasks and Windows services have no home inside a web container. Identity: Windows integrated authentication and gMSA are hard, so plan for Entra ID and managed identities. Lifecycle: containers get SIGTERM and a grace period, so the app must shut down gracefully and drain, and it needs readiness and liveness probes that mean something. Plus the Windows-container specifics — multi-gigabyte images, slow cold starts, and host/container OS version matching. My rule is to fix state and logging first, because those two produce the confusing production behaviour that makes people distrust the whole migration.

Example

// graceful shutdown and health endpoints: what the platform needs from your app
builder.Services.Configure<HostOptions>(o => o.ShutdownTimeout = TimeSpan.FromSeconds(30));
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddSqlServer(cs, name: "sql", tags: ["ready"]);

app.MapHealthChecks("/health/live",  new() { Predicate = h => h.Tags.Contains("live") });
app.MapHealthChecks("/health/ready", new() { Predicate = h => h.Tags.Contains("ready") });

Follow-ups

  • Why must liveness and readiness differ? — Liveness restarts the container; readiness only removes it from rotation. A liveness probe that checks the database restarts every instance during a database blip and turns a partial outage into a full one.
  • Is a container image of a legacy app worth building at all? — If it unlocks a consistent build/deploy pipeline and a modern host, yes. If it is a Windows image nobody can shrink and the app is going to be rewritten in a year, App Service or a VM is cheaper.
  • How do you handle scheduled tasks? — Container Apps jobs, Functions timer triggers, or a scheduler service — with the important addition that they must now be safe to run concurrently or singleton-protected.

Wrong answer: "We containerize it as-is and it behaves the same — that's the point of containers." Containers give you a consistent runtime, not a machine. Local disk, in-process session, file logging and scheduled tasks all behave differently, and finding that out in production is a standard and avoidable modernization scar.

Your Functions run on the in-process .NET model. What do you do about it? senior

Answer. Migrate to the isolated worker model now, because the in-process model retires on 2026-11-10 — the same day .NET 8 and .NET 9 leave support — and after that it is unsupported. The mechanical change: the function class stops deriving from the host's runtime assemblies and runs in its own process, so you get your own Program.cs with a host builder, full control of DI, configuration, middleware and the .NET version, at the cost of a serialization boundary between host and worker. Practically the work is: new project templates and package references (Microsoft.Azure.Functions.Worker.*), attribute and binding changes, logging via injected ILogger<T> rather than the passed-in one, HttpRequestData/HttpResponseData instead of HttpRequest, and updating the host configuration. It is a day or two per small function app and a couple of weeks for a large one — very much not a crisis, and very much something that becomes a crisis if it is discovered in the first week of November. I would do it as its own change, with the existing tests, before touching anything else in the app.

Example

// isolated worker: your own host, your own DI, your own .NET version
var host = new HostBuilder()
    .ConfigureFunctionsWebApplication()
    .ConfigureServices(s =>
    {
        s.AddApplicationInsightsTelemetryWorkerService();
        s.ConfigureFunctionsApplicationInsights();
        s.AddSingleton<IPricing, Pricing>();
    })
    .Build();
await host.RunAsync();

public sealed class QuoteFunction(IPricing pricing, ILogger<QuoteFunction> log)
{
    [Function("quote")]
    public async Task<HttpResponseData> RunAsync(
        [HttpTrigger(AuthorizationLevel.Function, "post")] HttpRequestData req)
    { /* ... */ }
}

Follow-ups

  • What do you gain besides support? — Your own process and .NET version (decoupled from the host), clean DI and middleware, and fewer assembly-version conflicts with the host — a long-standing in-process annoyance.
  • What is the catch? — A serialization hop between host and worker, so bindings behave slightly differently and cold start can be marginally higher; measure if you are latency-sensitive.
  • Durable Functions? — Supported in the isolated model; check the specific patterns and package versions you use, and re-run your orchestration tests, since the serialization boundary is where surprises live.

Wrong answer: "We'll move when we upgrade .NET — in-process still works fine." It works until 2026-11-10, which is nine weeks away, and after that you are running an unsupported hosting model with no security servicing. On a modernization topic, missing a retirement date this close is the failure the question is designed to find.

What is your security and networking baseline for the migrated workloads? senior

Answer. Four non-negotiables. Managed identity everywhere: no connection strings with passwords, no client secrets in configuration — the app authenticates to SQL, Storage, Key Vault and Service Bus as itself, which removes the single largest class of legacy credential incidents. Secrets that remain (third-party API keys) live in Key Vault, referenced rather than copied, with rotation. Private networking for data: databases, storage and caches reachable over private endpoints, public network access disabled, and the app on a VNet — a public SQL endpoint with a firewall rule for the office IP is the legacy pattern to remove. And least privilege in the control plane: separate identities per environment, RBAC over ownership by individuals, and infrastructure changes through pipelines rather than the portal. On top of that, TLS everywhere with modern minimum versions, WAF at the edge for public applications, and diagnostic logging to a central workspace so there is an audit trail. I would phase it: managed identity and secrets first (biggest risk reduction per effort), private networking with the platform move, and control-plane tidy-up as part of the IaC work.

Example

// no secret anywhere in configuration or code
var cred = new DefaultAzureCredential();                    // managed identity in Azure, dev creds locally
builder.Configuration.AddAzureKeyVault(new Uri(kvUri), cred);
builder.Services.AddSingleton(new BlobServiceClient(new Uri(blobUri), cred));
// SQL: "Server=sql-x.database.windows.net;Database=orders;Authentication=Active Directory Default;Encrypt=True"

Follow-ups

  • The legacy app cannot use managed identity. — Then a Key Vault-stored credential with rotation and a dated plan, not a secret in configuration. Name the exception rather than pretending it is fine.
  • What breaks when you turn off public network access? — Developer tooling, build agents and third-party integrations. Solve with private endpoints plus a bastion/self-hosted agent, and expect this to be the fiddly part of the migration.
  • How do you prove the baseline holds? — Azure Policy denying non-compliant resources, plus a compliance view per subscription. Standards that are not enforced by policy decay in months.

Wrong answer: "We'd move the connection strings into App Service configuration — they're encrypted at rest, so that's secure enough." It is better than web.config and it is still a long-lived shared credential that can be read by anyone with configuration access and is never rotated. Managed identity removes the credential entirely, and not reaching for it in 2026 reads as dated.

The infrastructure was created by clicking in the portal. How do you get to infrastructure as code? senior

Answer. Not by trying to codify everything at once. I start by exporting what exists (Bicep decompile from ARM templates, or Terraform import) to get an accurate inventory, and then treat the export as documentation rather than as the target — generated templates are unreadable and encode every accidental setting. From there I write clean, parameterized modules for the resources the new workloads need, stand up a fresh non-production environment entirely from code, and prove parity; that new environment is the proof the code is complete. Then production is brought under management resource group by resource group, with a policy that new resources must come from the pipeline, so the manual surface only shrinks. Tool choice matters less than discipline — Bicep if the estate is Azure-only and the team is Microsoft-centric, Terraform if there is multi-cloud or an existing Terraform practice — but state management, environment parameterization and a plan/what-if step in the pipeline are non-negotiable in either. And I would call out drift explicitly: a scheduled what-if that reports manual changes, because the first undetected drift is the moment the code stops being the truth.

Example

az bicep decompile --file exported.json          # inventory, not the target
az deployment group what-if -g rg-orders-prod -f main.bicep -p @prod.bicepparam   # drift + review gate
Order of work
1. new environments from code (dev/test) -> proves completeness
2. new resources only via pipeline (policy: deny portal writes on the rg)
3. existing production adopted rg by rg, lowest-risk first
4. scheduled what-if in CI; drift is a ticket, not a surprise

Follow-ups

  • Bicep or Terraform? — Azure-only and Microsoft-centric: Bicep, no state to manage. Multi-cloud or existing practice: Terraform. Choosing based on team familiarity is a legitimate reason; choosing based on a blog post is not.
  • What about the resources nobody can identify? — Tag everything with owner and system as a first pass; whatever remains untagged after a deadline is a candidate for shutdown with notice.
  • How do you handle secrets in IaC? — They are not in IaC: the template creates the Key Vault and the access, and the values are set out of band or generated.

Wrong answer: "We'd export ARM templates for everything and commit them." Exported templates are enormous, full of read-only and defaulted properties, and are not redeployable in practice — so you get the appearance of IaC with none of the benefit. Export to inventory; author clean modules; prove them by building a new environment.

How do you keep the system available while half of it is on-prem and half in Azure? senior

Answer. Accept that the hybrid period is a distinct architecture with its own failure modes, and design for it rather than treating it as a temporary inconvenience. Connectivity first: ExpressRoute or a site-to-site VPN with realistic bandwidth and latency expectations, plus DNS that resolves consistently from both sides — hybrid DNS is the single most common cause of "it works from Azure but not from the office". Then minimize the chat across the link: put the components that talk most to each other on the same side, and where a cross-link call is unavoidable, make it asynchronous (queue) or cache-tolerant, with timeouts, retries and circuit breakers tuned to a link that will occasionally be slow rather than down. Keep the data on one side at a time — a database in Azure with the application on-prem, or vice versa, is where latency compounds per query, so migration order should keep chatty pairs together. And monitor the link itself as a first-class dependency with its own alerts and its own runbook, because during a phased migration it is a single point of failure that did not exist before.

Example

Migration order that respects the link
  1. move the chatty pair together (app + its database), never one without the other
  2. keep cross-link traffic asynchronous: Service Bus / Storage queues, not sync RPC
  3. read replicas on the far side for reporting, so reports never cross the link live
  4. alerting on the link: latency, packet loss, BGP state - with a named owner

Follow-ups

  • What is the classic hybrid mistake? — Moving the application to Azure and leaving the database on-prem "for now": every query pays 10–40 ms, and a chatty ORM turns a 200 ms page into 4 seconds.
  • How do you handle Active Directory during the transition? — Entra ID with Entra Connect sync, and Entra Domain Services or line-of-sight to a domain controller for the workloads that genuinely need Kerberos. Plan it early; it gates more than people expect.
  • Does the hybrid period change your DR plan? — Yes, and it must be rewritten for the interim state, because failing over half a system is a scenario nobody has rehearsed.

Wrong answer: "We'd set up a VPN and treat both sides as one network — the applications don't need to know." They absolutely notice: latency per call, occasional link failures, and DNS that resolves differently. A design that ignores the link produces a system that is slower and less reliable than either half was alone.

What does resilience and DR look like after the migration, and how do you get there? principal

Answer. It starts with the business setting RTO and RPO per capability, in writing — without those two numbers every architecture discussion is preference. Then I design to the cheapest thing that meets them: zone-redundant deployment within a region covers the overwhelming majority of real failures and is close to free compared with multi-region; multi-region active-passive with a documented, rehearsed failover is the next step for genuinely critical capabilities; active-active is expensive, changes the data architecture (conflict handling, latency, global routing), and should be reserved for cases whose RTO genuinely cannot be met otherwise. I make the migration itself an opportunity: legacy DR is usually a tape restore nobody has tested, so define the targets during the migration and build the capability while you are rebuilding the deployment anyway. And the part that decides whether any of it is real: rehearsal on a schedule, with the failover exercised in production or in an identical environment, plus a check that the dependencies (DNS, identity, secrets, the deployment pipeline itself) also fail over — the classic discovery is that the failover procedure requires the CI system that is in the failed region.

Example

Checkout15 min / 1 minzone-redundant + secondary region warm, geo-replicated DB~1.7x
Back office8 h / 1 hzone-redundant, restore from geo-backup~1.05x

Follow-ups

  • How do you get RTO/RPO out of a business that says "zero"? — Price each level. "Zero" becomes "four hours" the moment the second column has numbers in it.
  • What breaks in most failover tests? — DNS TTLs, secrets and certificates that exist only in the primary, identity dependencies, and a deployment pipeline in the failed region. All findable only by rehearsing.
  • Is multi-region worth it for the migration period itself? — Rarely; during migration your biggest risk is the change you are making, not a regional outage. Spend on rehearsed rollback first.

Wrong answer: "We'd deploy active-active across two regions so we're always available." It is the most expensive answer, it changes your data consistency model, and it is usually solving a failure mode far rarer than the deployment mistakes that actually cause your outages. Zone redundancy plus a rehearsed regional failover meets almost every stated RTO at a fraction of the cost.

The half of full-stack modernization that .NET-centric candidates most often under-prepare, and interviewers know it. How do you move a large JavaScript code base to TypeScript without stopping delivery? screener

Answer. Incrementally, file by file, with the compiler configured to accept the mixed state. Turn on allowJs so TypeScript compiles the existing JavaScript, add checkJs (or per-file // @ts-check) to get type feedback from JSDoc without renaming anything, and start with strict: false so the build is green from day one. Then convert file by file, leaf-first — types and utilities before the modules that use them — and turn on strictness flags one at a time (noImplicitAny, then strictNullChecks, which is the one that finds real bugs and takes real effort) once the bulk is converted. Two rules keep it honest: no any without a comment and a ticket, and a ratchet in CI so the counts of any, @ts-ignore and unconverted files can only go down. Types for third-party libraries come from DefinitelyTyped or a local declaration file; a missing type is not a reason to give up on a module. In 2026 the compiler itself is a reason to do this: TypeScript 7.0 (GA 2026-07-08) is the Go-native rewrite with roughly 10x faster builds, so the check step that used to be the cost of adoption is much cheaper.

Example

{ "compilerOptions": {
    "allowJs": true, "checkJs": true, "strict": false,
    "noImplicitAny": true, "strictNullChecks": false,   // flip these on one at a time
    "target": "ES2022", "module": "ESNext", "moduleResolution": "bundler",
    "isolatedModules": true, "skipLibCheck": true } }
# the ratchet: the migration cannot go backwards
test "$(grep -rc ': any' src | awk -F: '{s+=$2} END {print s}')" -le "$(cat .any-budget)" || exit 1

Follow-ups

  • Which files first? — Shared utilities and data models, because their types propagate outward and immediately improve every consumer's editor experience.
  • Is strictNullChecks worth the pain? — It is where most of the value is; it is also the flag that produces thousands of errors on a large code base, so it is enabled per-directory or after the bulk conversion, not on day one.
  • What about TypeScript 7 specifically? — The native compiler is roughly an order of magnitude faster on type-checking and editor responsiveness; check plugin/transform compatibility before switching, since the rewrite changed the extension surface.

Wrong answer: "We'd rewrite the front end in TypeScript with strict mode on from the start." That is a rewrite disguised as a language migration: thousands of errors on day one, a branch that cannot merge, and no delivery meanwhile. The whole design of allowJs/checkJs and incremental strictness exists to avoid exactly that.

The UI is Razor/Web Forms views with jQuery. What is the modernization path? mid

Answer. Page by page, not framework-first. The cheapest credible route is islands: keep the server-rendered pages, and replace individual widgets with modern components mounted into a container element, so each conversion is independently deployable and reversible. That works with React, Vue or Web Components, and it lets the shared shell (navigation, authentication, layout) stay where it is until the end. If the target is a full SPA, the route is the same shape with a bigger unit: the new SPA takes ownership of whole routes behind the same reverse proxy used for the back-end strangle, and the two coexist until the last page moves. What I avoid is the intermediate state nobody plans for — jQuery and a framework fighting over the same DOM nodes — so each page belongs entirely to one world, with the boundary at the page or the widget container. And I would question the SPA assumption out loud: for a forms-and-tables line-of-business application, server-rendered pages with modern interactivity are often the cheaper end state, and choosing an SPA by default is how a UI modernization triples in size.

Example

<!-- island: one widget, mounted into a server-rendered page, independently shippable -->
<div id="order-grid" data-customer-id="@Model.CustomerId"></div>
<script type="module" src="/dist/order-grid.js"></script>
const el = document.getElementById("order-grid")!;
createRoot(el).render(<OrderGrid customerId={Number(el.dataset.customerId)} />);
// the rest of the page stays Razor + jQuery; the boundary is this element

Follow-ups

  • How do the island and the page share state? — Through data attributes and a small event contract, or by fetching from the API. Not by reaching into each other's DOM.
  • What about the design system? — Build the shared component library early; without it, each converted page invents its own look and the application ends up visibly patchwork, which is what stakeholders notice.
  • Web Forms specifically? — Same approach, with the caveat that postback and ViewState-heavy pages are usually rebuilt rather than islanded; those pages are the argument for Razor Pages or Blazor rather than an SPA.

Wrong answer: "We'd build a new SPA and switch the front end over once it reaches parity." That is the big-bang rewrite again, in the layer where parity is hardest to define because it includes every screen, validation message and keyboard habit users have. Islands and per-route cutover keep the same end state and remove the cliff.

You are on AngularJS 1.x / an old Angular / React classes. How do you get current? mid

Answer. Distinguish "unsupported and unmigratable in place" from "behind but on a ladder". AngularJS 1.x has been end-of-life since 2022 and there is no upgrade path to modern Angular — it is a rewrite, either page-by-page behind a proxy or with a hybrid bootstrap during a transition. Angular 2+ is a ladder: one major at a time using ng update and the official update guide, never skipping, with each step deployed before the next; the schematics do most of the mechanical work, and the recent steps are substantial in their own right — v21 (2025-11-20) made zoneless the default and swapped Karma for Vitest, and v22 (2026-06-03) made Signal Forms stable. React is the gentlest: classes and hooks coexist indefinitely, so you upgrade the library first and convert components opportunistically as you touch them; React 19.2.x is the current line, and the migration effort there is mostly removing deprecated patterns and legacy context. In all three the ordering is the same: get onto a supported version first (security), then modernize idioms, then adopt new capabilities — and never combine a framework major with a feature release.

Example

# Angular: one major at a time, each one deployed before the next
npx @angular/cli@21 update @angular/core@21 @angular/cli@21
npm test && npm run e2e && git commit -am "chore(fe): angular 21"
npx @angular/cli@22 update @angular/core@22 @angular/cli@22   # v22 released 2026-06-03

Follow-ups

  • How do you handle abandoned third-party components? — Inventory them before starting; each one is replace, fork, or wrap. A single unmaintained grid component can dominate the schedule of an Angular ladder.
  • Hybrid AngularJS/Angular — worth it? — Only for a large application where a rewrite cannot be funded in one go; it carries both frameworks' weight and is a transitional state that needs an end date.
  • How do you avoid falling behind again? — Scheduled upgrade work every quarter and a policy of staying within one major of current. The reason these migrations are expensive is that the ladder was skipped for years.

Wrong answer: "We'd jump straight to the latest Angular major and fix whatever breaks." Skipping majors means the schematics cannot help you, several breaking changes arrive at once, and you lose the ability to attribute a regression to a specific step. The supported path is one major at a time, deployed in between.

The build is webpack 4 with CommonJS and a 12-minute CI. What do you change? senior

Answer. I treat the build as a product with a measurable outcome (feedback time), and I change one variable at a time. Usually the highest-value moves in order: get onto a supported Node LTS first, because everything else depends on it; move to ESM, since the modern tooling ecosystem assumes it and CommonJS interop is the main source of build weirdness; then replace the bundler with Vite (or Rspack if the webpack configuration is too bespoke to abandon), which typically takes a multi-minute dev build to sub-second HMR; and adopt the fast type-checker — TypeScript 7's native compiler since 2026-07-08 — so type-checking stops being the long pole. Alongside that, cache aggressively in CI, split type-checking and linting into parallel jobs, and only build what changed if the repository is a monorepo (Nx/Turborepo). What I would resist is doing all of it in one pull request: each of these changes can break the output subtly, and bundling them means you cannot bisect. Verify with a bundle-size and output diff, not just a green build.

Example

{ "type": "module",
  "engines": { "node": ">=24" },
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "typecheck": "tsc --noEmit",     // TypeScript 7: ~10x faster than the JS compiler
    "test": "vitest run" } }

Follow-ups

  • How do you prove the migration did not change the output? — Compare bundle contents and sizes, run the e2e suite against both builds, and check the runtime behaviour of anything relying on module side-effect ordering — the classic CommonJS-to-ESM breakage.
  • What if the webpack config has bespoke loaders nobody understands? — Inventory what each one produces; most are replaceable by first-class Vite features. The one or two genuinely custom ones decide whether you migrate or move to Rspack.
  • Is a monorepo worth introducing during modernization? — Only if there are already several front-end packages fighting over versions. It is a large operating-model change, not a build tweak.

Wrong answer: "We'd migrate to Vite, ESM, TypeScript 7 and a monorepo in one go — it's all the same modernization." Four simultaneous changes to the build means any breakage has four candidate causes, and front-end build breakage is often subtle (module ordering, tree-shaking, polyfills) rather than a failed build. Sequence them, and keep a diffable output.

How do you manage Node.js runtime upgrades and npm supply-chain risk? senior

Answer. Runtime: stay on an Active LTS and treat the upgrade as scheduled maintenance rather than an event. Right now that is Node 24 (Active LTS, supported to 2028-04-30); Node 20 went end-of-life on 2026-04-30, so anything still on it is unpatched. There is a structural change worth knowing: from October 2026 Node moves to one major per year with calendar-aligned version numbers and every release becoming LTS, which makes planning easier and removes the "is this an even-numbered release?" folklore. Pin the version in .nvmrc, in the CI image and in the container base image so all three agree, and upgrade in a PR that runs the full suite. Supply chain: lockfiles committed and enforced (npm ci, never npm install in CI), npm audit or Dependabot/Renovate with an actual triage process, and provenance checks where available. The higher-leverage controls are reducing the dependency count, avoiding packages with one maintainer and no releases for years, and pinning transitive versions where you have been bitten — plus scripts disabled by default (--ignore-scripts) for a real reduction in install-time attack surface.

Example

.nvmrc          24
Dockerfile       FROM node:24-alpine
CI               uses: actions/setup-node with node-version-file: .nvmrc
install          npm ci --ignore-scripts        # lockfile-exact, no install-time scripts
audit gate       npm audit --audit-level=high   # fails the build; triage weekly, not never

Follow-ups

  • How do you handle a vulnerability with no fix available? — Assess exploitability in your usage (many are dev-only or unreachable), document the decision with a review date, and add a compensating control. Blanket "fix all highs" burns credibility on non-issues.
  • Renovate or Dependabot? — Either, with grouping and a schedule; the tool matters far less than whether someone reviews and merges the PRs. Unmerged update PRs are worse than none, because they look like coverage.
  • Does the Node schedule change affect planning? — Yes: with one calendar-aligned major per year and every release LTS, the annual upgrade becomes a predictable slot rather than a negotiation.

Wrong answer: "We run npm audit fix and keep everything on latest." audit fix happily applies breaking major upgrades, and "always latest" makes the build non-reproducible and imports every fresh supply-chain compromise on day zero. Pinned lockfiles plus reviewed, scheduled updates is the answer.

How do you keep a long front-end migration from becoming a visibly patchwork product? senior

Answer. By migrating the shared shell and the design system first, so old and new pages look and behave the same even though they are built differently. Concretely: extract the header, navigation, authentication state and notification patterns into a shared, framework-agnostic layer (CSS custom properties and web components work well for this because both worlds can consume them), and version it so both stacks pull from the same source. Then set a rule that a converted page must not visibly differ from the one it replaced except where the change is intentional and communicated. I also watch the transitions — the moment where a user moves from an old page to a new one is where a full page reload, a lost scroll position or a second authentication check becomes visible — and I keep the URL structure stable so bookmarks, deep links and any SEO surface survive. And I plan for the migration's own visual debt: a screenshot-diff suite over key pages, so drift is caught rather than reported by a customer.

Example

/* one token source consumed by Razor views, the SPA and the component library */
:root { --brand-500: #c2410c; --space-3: 12px; --radius-2: 4px; --font-ui: system-ui, sans-serif; }
// framework-agnostic shell component: usable from a Razor page and from the SPA
class AppHeader extends HTMLElement { connectedCallback() { /* renders identical markup */ } }
customElements.define("app-header", AppHeader);

Follow-ups

  • How do you handle authentication across the two front ends? — One session cookie and one sign-in flow, with both front ends reading the same state. Two sign-in experiences is what makes users notice the migration.
  • What is the cost of a shared shell? — Up-front work before any page is converted, which is exactly why it is often skipped and exactly why the patchwork happens.
  • How do you keep old pages from drifting? — Freeze cosmetic work on pages scheduled for conversion; spending design effort twice is pure waste.

Wrong answer: "We'd let the new pages use the new design system and eventually the old ones catch up." Then users see two products, support tickets rise, and stakeholders lose confidence in the migration on aesthetic grounds — which is a genuinely common way front-end modernization gets paused, regardless of engineering progress.

What is your testing strategy for a front end being migrated? senior

Answer. The stable layer during a rewrite is the user journey, not the component, so end-to-end tests carry the weight: a Playwright suite over the top journeys, written against user-visible semantics (roles, labels, text) rather than CSS selectors or component internals, so the same test passes before and after a page is converted. That gives you a characterization test at the UI level, which is exactly the safety net the migration needs. Underneath, component tests come with the new components (Vitest plus Testing Library, and note that Angular's default moved from Karma to Vitest in v21), and I do not invest in unit tests for code that is about to be deleted. I add visual regression on the key pages, because layout breakage is invisible to functional tests, and I run the suite against both the old and new implementations during the coexistence window. Two practical points: keep the e2e suite small enough to run on every PR (tens of tests, minutes) or it will be disabled within a month, and put test ids on the elements where semantic queries genuinely cannot express the intent rather than pretending the problem does not exist.

Example

// survives the rewrite: no framework, no CSS selectors, no component internals
test("customer can place an order", async ({ page }) => {
  await page.goto("/catalogue");
  await page.getByRole("button", { name: "Add to basket" }).first().click();
  await page.getByRole("link", { name: "Basket" }).click();
  await page.getByRole("button", { name: "Checkout" }).click();

Follow-ups

  • How do you stop the e2e suite becoming flaky? — Deterministic test data, no arbitrary waits (auto-waiting assertions only), API-level setup for preconditions, and quarantining plus fixing flakes rather than retrying them into silence.
  • Do you keep the old framework's tests? — Only until their code is deleted. Porting old unit tests to the new framework is usually wasted effort; the e2e layer is what carries the behaviour across.
  • Visual regression: worth the maintenance? — On a handful of key pages, yes; across everything, no — the noise makes teams approve diffs blindly, which is worse than not having it.

Wrong answer: "We'd write unit tests for the new components as we build them and rely on those." Component unit tests verify the new implementation against itself; they cannot tell you the migrated page still does what the old one did. The migration-specific safety net is the journey-level test that is agnostic to the implementation on either side.

Server-rendered .NET, an SPA, or Blazor — how do you choose during a modernization? principal

Answer. I choose on the interaction model, the team, and the operational cost, and I say plainly that all three are viable end states in 2026. Server-rendered Razor Pages/MVC with light interactivity is the cheapest to build and operate for forms-and-tables line-of-business software, and it is often the correct destination for an internal application whose users want speed and keyboard flow rather than app-like transitions. An SPA (React or Angular) earns its cost when the interaction is genuinely rich, when there are multiple clients including mobile consuming the same API, or when the front-end team is separate and wants an independent release cadence — and its price is a second runtime, a second dependency ecosystem, and a build pipeline someone must own. Blazor is the option worth naming explicitly for a .NET shop: it lets one team work in one language, with server-side rendering plus interactive islands via the unified model, and it is a strong fit when the team's JavaScript depth is genuinely thin — with the honest caveats of the WebAssembly download size, the connection sensitivity of server interactivity, and a smaller component ecosystem. What I would not do is choose by fashion or by what the strongest engineer prefers; I would prototype the two most demanding screens in the two leading candidates and decide on evidence.

10Build, CI/CD & dependency upgrades

Modernization is rate-limited by how safely you can deploy, so the pipeline is usually the first thing that has to change and the last thing candidates mention. Mid depth is the mechanical work — SDK-style projects, PackageReference, a real pipeline; senior depth is build-once-deploy-many, deployment strategies coupled to schema change, and keeping dependencies current as a habit rather than a project; principal depth is moving an organisation from six-week releases to daily without losing its nerve.

Docs: PackageReference · Central package management · Deployment slots · DORA metrics

Releases are manual, from a build server nobody understands. What do you fix first? mid

Answer. Reproducibility before automation: a build that only works on one machine cannot be automated, only relocated. So the first step is a clean-clone build that produces the artefact with a documented command and pinned tool versions (SDK in global.json, Node in .nvmrc, an agent image or container). Second, one-command deploy to a lower environment, even if it is a script — the point is that the sequence is written down and identical everywhere. Third, tests in the pipeline as a gate, starting with whatever exists plus a smoke test. Fourth, build once and promote the same artefact through environments, configuring at deploy time rather than rebuilding per environment. Only then do the deployment strategy improvements — slots, canaries — because they are meaningless while the artefact differs per environment. I would also delete rather than migrate: legacy build definitions accumulate steps nobody can justify, and porting them faithfully carries the archaeology forward into the new pipeline.

Example

# the whole build, runnable on a laptop and in CI, identically
dotnet restore --locked-mode           # packages.lock.json committed: reproducible restores
dotnet build -c Release --no-restore
dotnet test  -c Release --no-build --logger trx
dotnet publish src/Contoso.Api -c Release -o ./out --no-build

Follow-ups

  • What if the build needs a manual step (a licence, a signing key, an installed SDK)? — Move it into the agent image or into a secret in the pipeline. A manual step is a single point of failure with a name attached to it.
  • How do you handle the deployment nobody dares automate? — Automate it in a lower environment first and run it dozens of times; confidence comes from repetition, not from review.
  • Old pipeline in parallel or cut over? — In parallel briefly, then delete. Two pipelines for long means neither is trusted and drift is guaranteed.

Wrong answer: "We'd migrate the existing build definitions to the new CI system first." That moves the problem, keeps every unexplained step, and does not give you a build anyone can run locally. Start from a clean, reproducible build and port only what is justified.

What changes when you move from packages.config to PackageReference? mid

Answer. Dependencies become transitive and version-resolved rather than a flat, per-project list of exactly-installed packages. Practically: no more packages folder in the repository, restore is per-build, and NuGet resolves one version per package across the graph — which means the binding-redirect archaeology in app.config/web.config mostly disappears (on modern .NET entirely, since assembly unification works differently). The friction you hit is version conflicts that were previously hidden: two libraries wanting incompatible versions of a third now surface as NU1605-style errors, and that is a real finding rather than a nuisance. On top of that I add central package management (Directory.Packages.props) so a version is declared once for the whole solution, and lock files (packages.lock.json) with --locked-mode in CI so builds are reproducible and a transitive version cannot change under you. The migration itself is one of the things the Upgrade Assistant does reliably; the review effort goes into the conflicts it surfaces.

Example

<!-- Directory.Packages.props: one version per package for the whole solution -->
<Project>
  <PropertyGroup><ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally></PropertyGroup>
  <ItemGroup>
    <PackageVersion Include="Serilog.AspNetCore" Version="9.0.0" />
    <PackageVersion Include="Microsoft.EntityFrameworkCore.SqlServer" Version="10.0.0" />
  </ItemGroup>
</Project>

Follow-ups

  • What do you do about a genuine diamond conflict? — Upgrade the consumer, or isolate the offender behind a service. Suppressing the warning and hoping is how you get a MethodNotFoundException in production.
  • Are lock files worth it? — Yes for applications, where reproducibility matters; less so for libraries, which should float within their supported range.
  • What about the packages folder in source control? — Delete it; with restore and a lock file it is dead weight, and it hides which versions are actually resolved.

Wrong answer: "It's just a different file format for the same list." The resolution model changes from flat and pinned to transitive and unified, which is exactly why previously-invisible conflicts appear during the migration — and being surprised by that mid-migration costs days.

How do you stop dependencies falling behind again after the migration? senior

Answer. Make it continuous and boring. Automated update PRs (Renovate or Dependabot) with sensible grouping — patch and minor batched weekly and auto-merged when the suite is green, majors raised individually with a human — plus a standing slot in the team's week so the PRs are actually reviewed rather than accumulating. The framework and runtime get a scheduled slot too: a calendar entry for each LTS with the upgrade planned before the previous one expires, which is the discipline that would have prevented the estate's current state. I pair it with policy: CI fails on known high-severity vulnerabilities, and a dependency with no release in two years gets flagged for review. The cultural half matters more than the tooling — the reason estates fall behind is that upgrades are treated as projects requiring justification, so I frame them as maintenance that happens by default and requires justification to skip. And I measure it: mean dependency age and the count of majors behind are two numbers that make regression visible before it becomes a migration.

Example

// renovate.json - patch/minor batched and auto-merged, majors reviewed
{ "extends": ["config:recommended"],
  "schedule": ["before 6am on monday"],
  "packageRules": [
    { "matchUpdateTypes": ["patch", "minor"], "groupName": "weekly deps", "automerge": true },
    { "matchUpdateTypes": ["major"], "automerge": false, "dependencyDashboardApproval": true },
    { "matchPackagePatterns": ["^Microsoft\\.EntityFrameworkCore"], "groupName": "ef core" } ] }

Follow-ups

  • Auto-merge feels risky. Is it? — It is only as risky as your test suite, which is the point: it makes test quality a visible, funded concern instead of a preference.
  • What about a dependency that always breaks? — Wrap it behind your own interface so upgrades touch one file, or replace it. Repeated upgrade pain is a design signal.
  • How do you handle the framework upgrade itself? — Same cadence, bigger slot: plan the LTS move within three months of release, not three months before end of support.

Wrong answer: "We'll do a dependency upgrade project each year." Annual upgrade projects are exactly how a code base reaches the state that needed modernizing: twelve months of drift makes each upgrade a multi-major jump with no ability to bisect a regression. Continuous small updates are cheaper in total and far less risky.

Blue-green, canary or slots — what do you use, and how does the database constrain it? senior

Answer. Canary where you can, blue-green where you must, slots as the App Service implementation of either. Canary — a small percentage of traffic on the new version with automated rollback on error-rate or latency regression — has the smallest blast radius and is my default for stateless web tiers. Blue-green is better where a version must be validated as a whole before any real traffic arrives, and slot swaps give you that with a warm-up. But whichever you choose, the database is the constraint: both versions share one database in almost every real deployment, so the schema must be compatible with both — which is the expand/contract discipline again. That means the deployment strategy is not an infrastructure choice you can make independently; it is a property of how you evolve your schema. The second constraint is state: sticky sessions, in-memory caches and background jobs all need thought, and background workers in particular need singleton protection so two versions do not process the same queue with different logic.

Example

Deploy sequence with a shared database
  1. migration stage: additive schema only (safe for old + new)
  2. deploy new version to green/slot; warm up; health checks pass
  3. shift 5% -> 25% -> 100% with automatic rollback on SLO burn
  4. next release removes the old code path; the one after drops the old column

Follow-ups

  • What breaks in a slot swap most often? — Configuration that is not slot-specific, warm-up not actually warming the paths that matter, and background jobs starting in both slots.
  • How long should a canary bake? — Long enough to cover a representative traffic mix — at least one business-hours peak, and a full day for anything touching batch or scheduled work.
  • What automates the rollback decision? — SLO-based rules on error rate and latency, evaluated per cohort. A human watching a dashboard at 2am is not a rollback mechanism.

Wrong answer: "Blue-green gives us instant rollback, so we can deploy anything safely." Only the application rolls back instantly. If the release included a destructive schema change, green wrote data blue cannot read, and the swap back is broken — which is why the schema discipline is inseparable from the deployment strategy.

Why "build once, deploy many", and what breaks when you do not? senior

Answer. Because the artefact you tested must be the artefact you ship; rebuilding per environment means production runs a binary nobody tested, differing by whatever changed in the meantime — a package version resolved differently, a build machine's SDK patch, a transform applied differently. Legacy .NET pipelines are especially prone to this because web.config transforms are build-time by design, so "build for production" was the normal idiom. The modern shape is one build producing one artefact (or container image), stamped with a version and a commit, promoted through environments, with all environment differences supplied at deploy time via configuration and secrets. The practical benefits beyond correctness: you can roll back to a specific known artefact, you can trace exactly what is running from the version stamp, and your build time is paid once rather than per environment. The change is usually small mechanically and significant culturally, because it forces environment differences out of the build and into configuration where they are visible.

Example

- stage: Build           # once
  jobs: [ { steps: [ dotnet publish, docker build -t app:$(Build.BuildId), push ] } ]
- stage: Test            # same image
  jobs: [ { steps: [ deploy app:$(Build.BuildId) to test, run smoke ] } ]
- stage: Prod            # same image, different configuration + secrets
  jobs: [ { steps: [ deploy app:$(Build.BuildId) to prod, canary, verify ] } ]

Follow-ups

  • What about compile-time environment differences that genuinely exist? — They should become runtime configuration or feature flags. If something truly must differ at compile time, it is a separate product, and saying so usually kills the requirement.
  • How do you know what is deployed? — Version and commit stamped into the artefact and exposed on a health/info endpoint, and emitted with every log event.
  • Does this apply to database scripts too? — Yes: the same idempotent script artefact is applied to each environment in turn, not regenerated per environment.

Wrong answer: "We build per environment so each one gets the right configuration baked in." That is the legacy transform habit, and it means the production binary has never been tested anywhere. It also makes "roll back to what was running last Tuesday" a rebuild rather than a redeploy.

Take a team from six-week releases to daily. How, without breaking things? principal

Answer. Attack the reason releases are big before attacking their frequency, because frequency is a symptom. The sequence I use: make the release boring (automated, repeatable, one command, rehearsed in lower environments); shrink the batch (trunk-based development with short-lived branches, feature flags so incomplete work can ship dark); make failure cheap (canary, automatic rollback, feature-flag kill switches, and an SLO that says what "bad" means); then increase frequency and let the pain surface the next bottleneck — usually a manual test phase or a change-approval board. For the approval board specifically, the productive move is to show that small, automated, reversible changes have a lower change failure rate than the big batched ones being approved, and to propose a standard-change category with evidence rather than to argue against governance. I track the four DORA metrics because they make the argument for me, and I expect the transition to take two to four quarters — the technical work is weeks, the trust is quarters.

Example

Quarter 1  automated deploy, smoke tests, one-command rollback; release every 2 weeks
Quarter 2  trunk-based + flags; branches < 2 days; release weekly; canary on the web tier
Quarter 3  daily; standard-change category agreed with evidence (CFR, MTTR trend)
Quarter 4  on-demand; DB changes expand/contract by default; batch size is the metric watched
Watched throughout: deployment frequency, lead time, change failure rate, MTTR

Follow-ups

  • The team believes big releases are safer. How do you shift that? — Data from your own system: plot incident severity against release size. The correlation is usually stark and it is more persuasive than any industry report.
  • What if a regulator requires change approval? — Keep the approval and change what is approved: pre-approved standard changes with automated evidence. Compliance wants evidence and traceability, which automation provides better than a meeting.
  • Which metric do you watch first? — Lead time, because it exposes queues and handoffs; deployment frequency follows once the queues are gone.

Wrong answer: "We'd mandate daily deployments and the team will adapt." Frequency without the safety net converts one big failure into many small ones and destroys the credibility of the whole programme. Make it boring, make it small, make failure cheap — then the frequency arrives on its own.

11Identity & security modernization

Legacy systems carry legacy identity, and this sub-area is asked because it is where modernization most often collides with something that cannot be changed unilaterally — an ADFS estate, a partner using a deprecated flow, twenty years of password hashes. Mid depth is the target model and the retired libraries; senior depth is remediation ordering, credential migration without a mass reset, and how the threat model changes when you introduce a gateway and tokens.

Docs: Migrate to MSAL · OIDC on the Microsoft identity platform · Managed identities · ASP.NET Core Data Protection

The app uses Forms authentication against a users table. How do you get to Entra ID? mid

Answer. In stages, with the application's authorization decoupled from its authentication first. Step one: replace the sign-in mechanism with OpenID Connect against Entra ID while keeping the application's own user records, matched on a stable identifier (object id, not email, because emails change) — users sign in with the identity provider and the application still knows who they are locally. Step two: move authorization to claims and policies rather than to the roles table, so the application stops depending on its own user store for decisions. Step three: retire local credentials — password fields, reset flows, lockout logic — which is where most of the security benefit lands, since MFA, conditional access and credential policy all become the identity provider's job. For a period both paths coexist behind a flag, and the migration of users is per cohort. Two details that matter in practice: keep a break-glass local admin path until the new flow is proven, and plan the mapping carefully for accounts with no matching directory entry — service accounts, shared logins and long-departed users are always more numerous than expected.

Example

builder.Services.AddAuthentication(OpenIdConnectDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApp(builder.Configuration.GetSection("AzureAd"));

builder.Services.AddAuthorization(o => o.AddPolicy("CanApproveInvoice", p =>
    p.RequireAuthenticatedUser().RequireClaim("roles", "invoice.approver")));

// map the external identity to the local user on a stable id, not on email
var oid = principal.FindFirst("http://schemas.microsoft.com/identity/claims/objectidentifier")!.Value;

Follow-ups

  • What about external/customer users? — External ID (the successor to Azure AD B2C for new tenants) or a separate consumer identity provider; do not put customers in your workforce directory.
  • Service accounts? — Managed identities or workload identity federation, never a user account with a password in configuration.
  • Can you migrate users gradually? — Yes, per cohort behind a flag, with both flows live. A single big-bang identity cutover locks everyone out simultaneously when something is wrong.

Wrong answer: "We'd export the users and import them into Entra ID with their password hashes." Password hashes are not portable into a modern identity provider, and the attempt distracts from the actual win: stop owning credentials entirely. Map identities, keep both flows briefly, and retire the local password store.

The code uses ADAL and Azure AD Graph. What is the problem and what is the fix? mid

Answer. Both are retired: ADAL reached end of support in mid-2023 and Azure AD Graph has been retired as well, so anything still on them is running unsupported authentication code against an endpoint that has already been shut down or is on borrowed time. The fixes are MSAL (or, in ASP.NET Core, Microsoft.Identity.Web which wraps it) and Microsoft Graph. The migration is more than a package swap: MSAL's token cache model is explicit, so distributed applications need a shared, encrypted cache rather than the implicit per-process behaviour; the v1 endpoint's resource-based token requests become v2 scope-based requests; and Graph's permission model and response shapes differ from Azure AD Graph, so every call site needs checking rather than a find-and-replace. Practically I inventory every ADAL usage, group them by flow (interactive, client credentials, on-behalf-of), migrate one flow at a time behind tests, and take the opportunity to replace client secrets with certificate credentials or federated/managed identity — since the migration is touching the credential code anyway.

Example

// ADAL (retired)                            -> MSAL / Microsoft.Identity.Web
// new AuthenticationContext(authority)          builder.Services.AddMicrosoftIdentityWebApiAuthentication(config)
//   .AcquireTokenAsync(resource, credential)      .EnableTokenAcquisitionToCallDownstreamApi(["User.Read"])
//                                                 .AddDistributedTokenCaches();   // shared cache: required at scale
var token = await _tokenAcquisition.GetAccessTokenForAppAsync("https://graph.microsoft.com/.default");

Follow-ups

  • Why does the token cache matter so much? — Without a shared cache, every instance acquires its own tokens: throttling, latency and, in extreme cases, service-principal rate limiting. It is the classic post-migration incident.
  • How do you find every usage? — Package references plus a code search for the ADAL types, and a check for direct HTTP calls to the v1 endpoints, which no package scan finds.
  • Secrets or certificates? — Certificates or federated credentials; a client secret in configuration is the thing you are supposed to be removing during this work.

Wrong answer: "We'd swap the NuGet package and update the namespaces." The token cache model, the endpoint version and the Graph API surface all change; a mechanical swap compiles and then fails at runtime under load or against permissions that no longer exist. This is a "have you done it?" question.

There are secrets in web.config, in source control history, and in a shared spreadsheet. Remediation plan? senior

Answer. Rotate first, then remove, then prevent — in that order, because removing a secret from a file does nothing if it is already compromised, and history rewriting is slow. Concretely: inventory (secret scanning across repositories including history, plus configuration in every environment), then rotate every credential that has been exposed, prioritizing production and anything with wide blast radius; then move the surviving secrets into Key Vault with references rather than copies, and replace as many as possible with managed identity so there is no secret at all; then add prevention — pre-commit and server-side secret scanning that blocks the push, plus a policy that configuration files may not contain credentials. History rewriting is the last step and often not worth it for a large repository: treat exposed secrets as burned, rotate them, and spend the effort on prevention instead. The framing that matters at senior level: this is an incident-shaped piece of work with a prioritized queue, not a tidy-up task, and it should be sequenced early in a modernization because everything else you do touches those files.

Example

1. scan       repo history + all env configs + pipeline variables + the spreadsheet
2. classify   prod/non-prod, blast radius, rotation cost, who else uses it
3. rotate     prod first; coordinate with third parties; verify the old value fails
4. remove     Key Vault references; managed identity wherever the platform supports it
5. prevent    push protection + CI secret scan + policy; the spreadsheet is deleted, not archived
6. verify     re-scan monthly; a metric on the dashboard, not a one-off project

Follow-ups

  • A third-party key cannot be rotated without their change window. — Book it, and meanwhile restrict by IP/network and monitor its use. Document the accepted risk with an owner and a date.
  • Is rewriting git history worth it? — Rarely: it breaks every clone and fork, and the secret is already out. Rotate, then prevent. Exception: a repository about to be made public.
  • How do you handle developers needing secrets locally? — They should not: local development uses their own identity (DefaultAzureCredential picks up developer credentials) against a dev resource, or user-secrets for non-production values.

Wrong answer: "We'd move everything to Key Vault and clean up the config files." That is the middle step presented as the whole plan, and it leaves live credentials in git history and in a spreadsheet. Rotation comes first; anything exposed is compromised until it is changed.

The system uses SHA-1 password hashes, custom crypto and TLS 1.0. How do you fix that safely? senior

Answer. Each has a different migration shape. Password hashes cannot be recomputed, so you upgrade on next successful sign-in: verify against the old algorithm, and on success re-hash with a modern one (Argon2id, or ASP.NET Core Identity's PBKDF2-based hasher with a current iteration count) and store the new format with a version marker; after a cutoff, force a reset for the accounts that never signed in. Better still, this is the moment to remove local passwords entirely by moving to an identity provider. Custom crypto is replaced with platform primitives — and the risk is that data encrypted with the old scheme must remain readable, so you decrypt-and-re-encrypt in a background migration with both implementations live, versioning every ciphertext so you know which is which. TLS is the easiest technically and the hardest politically: enable modern versions, measure who is still negotiating old ones (the clients are usually a handful of partners and one embedded device), give them a deadline, then disable. In all three cases the pattern is the same: support both, migrate on use or in the background, version the stored artefact, and have a dated end to the old path.

Example

// upgrade-on-login: no mass reset, no downtime, and it converges on its own
if (stored.StartsWith("v1$"))                       // legacy SHA-1 + salt
{
    if (!LegacyHasher.Verify(password, stored)) return SignInResult.Failed;
    user.PasswordHash = _modern.HashPassword(user, password);   // "v3$..." going forward
    await _users.UpdateAsync(user);
    return SignInResult.Success;
}
return _modern.VerifyHashedPassword(user, stored, password) == PasswordVerificationResult.Success
     ? SignInResult.Success : SignInResult.Failed;

Follow-ups

  • How do you find who still uses TLS 1.0? — Connection logs at the load balancer or gateway with the negotiated version and client identity, over a full business cycle. Guessing produces an outage for a partner nobody remembered.
  • What about data encrypted with a key nobody can find? — Then it is unreadable and that is a data-loss finding, not a migration task. Discover it early, before it becomes an incident during a cutover.
  • Does the Data Protection API help? — Yes, for cookies and tokens: it handles key rotation and algorithm versioning for you, which is exactly what the hand-rolled implementations were doing badly.

Wrong answer: "We'd force a password reset for all users and switch the algorithm in one release." A mass reset is a support-desk incident, a phishing opportunity (users are primed to click a "reset your password" email) and unnecessary — upgrade-on-login converges without any user noticing, with a targeted reset only for the accounts that never come back.

Authorization is hard-coded role checks against a roles table. What does modern look like? senior

Answer. Separate the decision from the enforcement and stop encoding roles in the code. In ASP.NET Core that means policy-based authorization: the code asks for a permission ("CanApproveInvoice"), a policy defines what satisfies it, and the mapping from users to permissions lives in data or in the identity provider — so adding a role becomes configuration rather than a release. Where the rules are relational ("can approve invoices for their own cost centre up to £10k"), the resource-based authorization handlers give you the resource in the decision, and for large multi-tenant systems a relationship-based model (Zanzibar-style) answers the "which items can this user see?" query that policy engines answer badly. The migration is incremental: introduce the permission abstraction, map existing role checks onto permissions mechanically (each [Authorize(Roles = "X")] becomes a policy), then change the underlying model without touching call sites again — which is the whole payoff. And enforce at one chokepoint so a new endpoint is denied by default rather than accidentally public.

Example

// before: the rule is spread through the code and requires a release to change
if (user.IsInRole("Manager") || user.IsInRole("Finance")) { ... }

// after: the code asks for a permission; the mapping is data
[Authorize(Policy = "Invoice.Approve")]
public async Task<IResult> Approve(int id) => ...

builder.Services.AddAuthorization(o =>
{
    o.FallbackPolicy = new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build(); // deny by default
    o.AddPolicy("Invoice.Approve", p => p.Requirements.Add(new PermissionRequirement("invoice:approve")));
});

Follow-ups

  • How do you migrate without a big bang? — Map each existing role check to a policy with identical semantics first (pure refactor, no behaviour change), then evolve the policies. Two changes at once here is how you accidentally grant access.
  • How do you test authorization? — Explicit negative tests per endpoint and per role, generated from the policy table. The dangerous defect is the endpoint nobody wrote a test for.
  • Where do you cache decisions? — Short-TTL caching of permissions per user is fine; the hazard is that a revoke takes effect late, so keep the TTL small and support explicit invalidation.

Wrong answer: "We'd put the roles in the JWT as claims and check them in the controllers." Roles in a token are a snapshot that goes stale on revoke, tokens have size limits that a real role model exceeds, and checking roles in controllers keeps the rule in the code. Ask for permissions, decide centrally, keep the mapping in data.

How does modernization change the threat model? senior

Answer. It moves risk rather than removing it, and naming the new risks unprompted is the senior signal. You gain: patched runtimes, dependency upgrades that were previously blocked, managed identity instead of stored credentials, private networking, and central logging. You also gain new surface: a gateway or reverse proxy that must correctly propagate and not spoof identity (header injection through the proxy is a real class of bug); tokens instead of server-side sessions, so revocation becomes a design question; service-to-service calls that need their own authentication rather than being in-process; a much larger dependency graph and therefore supply-chain exposure; a control plane where an over-privileged pipeline identity can do more damage than any application bug; and, during coexistence, two systems with two authorization implementations that can disagree — the most commonly exploited seam. My practice is to threat-model the transitional architecture, not only the target, because the coexistence period is where the mismatch lives and it is often the longest-lived state of the whole programme.

  • What is the most common coexistence vulnerability? — An endpoint reachable on the legacy path that the new path protects, or vice versa. Enumerate both surfaces and test the negative cases on each.
  • How do you prevent proxy header spoofing? — Strip and re-set identity headers at the trust boundary, restrict the legacy app to accept traffic only from the proxy, and prefer a signed token over a trusted header.
  • Does the pipeline need its own threat model? — Yes: it deploys to production, holds credentials, and is often the least-monitored component in the estate.

Wrong answer: "Modernizing improves security because we're on supported versions with managed identities." True as far as it goes, and it skips the whole question. An answer that only lists benefits reads as someone who has not run a coexistence period, where the interesting vulnerabilities actually live.

12Observability during migration

Modernization is a series of comparisons — is the new path as good as the old one? — and you cannot compare what you cannot measure, so telemetry is the prerequisite that legacy systems least often have. Mid depth is knowing what to instrument before starting; senior depth is OpenTelemetry adoption, correlating a request across old and new stacks, and comparing cohorts on business metrics rather than technical ones; principal depth is running the programme against SLOs.

Docs: OpenTelemetry .NET · Azure Monitor OpenTelemetry · .NET diagnostics

What do you instrument before you change anything? mid

Answer. Enough to answer "is it working as well as before?" for both technical and business meanings of working. Technically: request rate, error rate and latency percentiles per endpoint; the same for background jobs and queues (depth, age of oldest message, processing rate); database query volume and slow queries; and dependency call rates. In business terms, a small set of metrics the organisation already trusts — orders placed per hour, payments settled, logins, documents produced — because those are what tell you a cutover silently broke something the error rate cannot see. I also want a usage inventory (which endpoints, jobs and stored procedures are actually exercised) because it drives the migration plan and the retirement decisions. The important discipline is baselining: capture a period long enough to include a peak and a month-end, and store it, so later comparisons are against recorded numbers rather than memory. Getting this in place is usually the first sprint of a modernization, and it pays for itself before any code moves.

Example

// business metrics alongside the technical ones - the pair is what makes a cutover decidable
static readonly Meter Meter = new("Contoso.Ordering");
static readonly Counter<long> OrdersPlaced = Meter.CreateCounter<long>("orders.placed");
static readonly Histogram<double> QuoteLatency = Meter.CreateHistogram<double>("quote.duration", "ms");

OrdersPlaced.Add(1, new KeyValuePair<string, object?>("path", useModern ? "modern" : "legacy"));

Follow-ups

  • The legacy app cannot be instrumented easily. — Instrument at the edge (proxy/gateway logs) and in the database; you get per-endpoint rates and latencies without touching the application.
  • How long a baseline? — At least one full business cycle. A migration validated against a quiet Tuesday fails on the first month-end.
  • What is the single most valuable signal? — A business metric tagged with the code path, because it is the only one that catches "technically healthy, semantically wrong".

Wrong answer: "We'd add Application Insights to the new services as we build them." Then you have no basis for comparison: the legacy system's behaviour is unmeasured, so "is the new one better?" is opinion. Instrument the old system first — that is the baseline the whole programme is judged against.

How do you trace one request that crosses the legacy app and the new services? senior

Answer. One correlation standard, injected at the edge, propagated by everything. Modern .NET emits and honours W3C traceparent automatically through Activity/System.Diagnostics, so the new stack is nearly free; the work is the legacy side. Options in order of preference: add the OpenTelemetry or Application Insights SDK for .NET Framework, which supports both and will propagate headers; if that is not possible, generate the id at the proxy and have the legacy app log it (even a manual read of the header into log4net's context is enough to join the traces); and at minimum, log it in the access logs so you can correlate by id even without spans. On the query side, tag every span and log event with the migration cohort (legacy or modern) so a trace explorer can filter, and make sure the id flows through queues and background jobs too — asynchronous boundaries are where correlation usually dies. The goal is that one identifier from a user's support ticket finds every log line, span and database call in both systems.

Example

// legacy .NET Framework app: read the incoming id and put it into every log line
protected void Application_BeginRequest()
{
    var traceparent = Request.Headers["traceparent"];
    var traceId = ParseTraceId(traceparent) ?? Guid.NewGuid().ToString("n");
    log4net.LogicalThreadContext.Properties["TraceId"] = traceId;    // pattern: %property{TraceId}
    Response.Headers["x-trace-id"] = traceId;                        // support tickets quote this
}

Follow-ups

  • What about sampling? — Use tail-based or higher sampling during a cutover: sampled-away traces are exactly the ones you want when comparing implementations. Turn the rate back down after the bake.
  • Does OpenTelemetry work on .NET Framework? — The .NET Framework support is more limited than on modern .NET, but sufficient for HTTP and SQL instrumentation and header propagation, which is what correlation needs.
  • Where does correlation break most often? — Queues and scheduled jobs. Carry the trace context in the message envelope explicitly.

Wrong answer: "Each system has its own logging, so we'd search both by timestamp and user id." At any real traffic level that is guesswork, and during an incident it costs the minutes that matter. One propagated id is a day of work and it changes what debugging a coexistence period feels like.

How do you actually compare old and new in production? senior

Answer. By making the cohort a dimension on every relevant signal, so old and new are the same chart rather than two dashboards. Every metric — request duration, error rate, database calls per request, and the business metrics — carries a tag for the path, and the comparison view shows them side by side over the same window with the same traffic. Then I compare four things explicitly: correctness (business metric rates per cohort — orders per session, not orders total, since cohorts differ in size), latency (percentiles, not means), cost (CPU/memory/database load per request), and error taxonomy (not just the rate but the kinds, since a new implementation often trades one failure mode for another). I set the pass criteria before the ramp and write them down. And I keep the comparison running through the bake rather than checking once at cutover, because the failures that matter often appear at the next peak, the next month-end or the next partner batch rather than in the first hour.

Example

Cutover dashboard (one chart per row, cohort as the series)
  orders per 1000 sessions      legacy 41.2   modern 41.0    within noise    PASS
  p95 quote latency             legacy 380ms  modern 240ms                   PASS
  db calls / request            legacy 7      modern 19      REGRESSION - N+1 introduced

Follow-ups

  • Why per-session rather than absolute? — Cohorts have different sizes and often different composition; absolute counts make a 5% cohort look catastrophically worse than the 95% one.
  • How do you avoid cohort bias? — Assign deterministically by a hashed stable key and check the cohorts are comparable on the dimensions you care about (tenant size, geography, plan) before trusting the comparison.
  • What if the metrics disagree — technical better, business worse? — Business wins, every time. A faster path that produces fewer orders is a broken path.

Wrong answer: "We'd watch the error rate and latency on the new service after the cutover." That catches crashes and slowness and misses silently wrong results, which is the characteristic failure of a reimplementation. Business metrics per cohort are the check that finds them.

The legacy app logs unstructured text to files. What do you change, and what do you watch for? senior

Answer. Move to structured events shipped to a central store: keep log4net or NLog if replacing the logging framework is not worth a change (both have structured layouts and modern sinks), or move to ILogger with Serilog in the new stack, and standardise the fields — timestamp, level, message template, trace id, tenant, user, cohort. Ship to one place (Log Analytics / Application Insights) so a query spans both systems. Two things to watch. First, personal data: legacy logs are full of it — full request bodies, email addresses, sometimes card fragments and passwords in exception dumps — and centralizing them turns a local problem into a governance one, so redaction goes in with the shipping, not afterwards. Second, volume and cost: naive shipping of debug-level file logs produces an eye-watering ingestion bill and drowns the signal, so set levels deliberately, sample high-volume events, and use structured fields instead of long strings. I would also seize the opportunity to make the log messages queryable — a message template with named properties instead of interpolated text is the difference between grep and analysis.

Example

// structured: queryable fields, no PII, cohort tagged
_log.LogInformation("Quote produced for {TenantId} in {ElapsedMs} ms on {Path}",
    tenantId, sw.ElapsedMilliseconds, "modern");

// NOT: _log.LogInformation($"Quote for {customerEmail} took {sw.ElapsedMilliseconds}ms");
//      interpolated (unqueryable) and it puts an email address in the log store

Follow-ups

  • How do you find PII already in the logs? — Pattern scans over a sample (emails, card patterns, national ids) plus a review of exception logging, which is where request bodies leak.
  • How do you control cost? — Level discipline, sampling for high-volume success events, retention tiers, and keeping metrics as metrics rather than as parsed log lines.
  • Do you migrate old log files? — Almost never; keep them accessible for their retention period and start clean centrally.

Wrong answer: "We'd ship the existing log files to Log Analytics so everything's in one place." You get unparseable text, a large bill, and every piece of personal data that was in those files now in a central, widely-readable store. Structure and redact at the source; shipping raw legacy logs is a governance incident with an invoice attached.

How do you use SLOs to run a migration? principal

Answer. The SLO becomes the contract that lets the team move fast without asking permission each time. I define an SLO per user-facing journey (availability and latency) before the migration, measured on the legacy system so the target is grounded in reality rather than aspiration, and I set an error budget from it. Then the rule is explicit: while the budget is healthy, cutovers proceed on the team's judgment; when the budget is being consumed faster than planned, migration work pauses and reliability work takes priority. That converts "should we do this cutover this week?" from a debate into a measurement, which is worth an enormous amount of organisational energy. I also add a migration-specific guardrail — an automatic rollback rule tied to the same signals, so a bad ramp reverses without a human decision — and I report budget consumption to the sponsor alongside progress, because it is the honest answer to "are you going too fast?". The nuance worth stating: an error budget deliberately permits some failure, and a programme that never consumes any of it is probably moving too slowly to finish.

Example

SLO  checkout availability 99.9% / 28 days   -> budget 40 min
     checkout p95 < 800 ms  (measured legacy baseline: 740 ms)
Rules
  budget > 50% remaining   cutovers proceed, ramp at team discretion
  budget < 50%             ramps pause at current percentage; fix first
  budget exhausted         freeze migration work; reliability only; sponsor informed
  auto-rollback            5xx > 1% or p95 > 1200 ms over 5 min on the modern cohort

Follow-ups

  • What if the legacy baseline is already below the SLO? — Then say so: you cannot hold the new system to a standard the old one never met. Set the SLO at the current reality plus an improvement target, and make the gap visible.
  • Who owns the freeze decision? — Agreed in advance and automatic on the budget; a decision that requires a meeting during an incident will not be made in time.
  • Do SLOs slow the migration? — They speed it up, because they replace per-change approval with a standing rule. The slowness comes from committees, not from measurement.

Wrong answer: "We'd set a target of zero incidents during the migration and stop if we cause one." Zero-failure targets produce risk aversion, hidden failures and a programme that stalls at the first setback. An error budget names an acceptable amount of failure in advance, which is what makes reversible experimentation possible at all.

13Risk, rollback & migration incidents

Asked as scenarios rather than as definitions: what do you do when it goes wrong at 2am, a week later, or six months into a programme that is over budget. Senior depth is a rehearsed reversal and a calm incident structure; principal depth is designing the blast radius before the change and being the person who says stop. Answers here are judged on decision-making under uncertainty and on honesty — invented certainty reads badly.

Docs: Well-Architected: Reliability · Testing for resiliency

What makes a cutover genuinely reversible? mid

Answer. Four properties. The switch is configuration, not deployment, so reversing takes seconds and does not need a build. The old path is still running and still correct — not decommissioned, not starved of updates, not left with a stale schema it can no longer read. Data written by the new path is either compatible with the old path or can be reconciled, which is the property that expand/contract exists to guarantee. And the reversal has been rehearsed and timed, so "we can roll back" is a measured statement rather than a hope. To that I add: the decision to reverse must be pre-delegated to whoever is on the call, with criteria written down, because a rollback that requires waking an executive is not available at 2am. I would also name the point of no return explicitly for each cutover — the moment new writes exist only in the new system — and treat crossing it as a scheduled event with its own go/no-go rather than something that happens by drift.

Example

Reversibility checklist (part of every cutover's definition of ready)
  [ ] switch is a flag/config change, no deploy, verified in staging today
  [ ] legacy path still deployed, still receiving schema changes, smoke-tested this week
  [ ] new writes readable by the legacy path (expand/contract) or reconcilable
  [ ] rollback rehearsed end to end; measured duration: ____ minutes
  [ ] criteria + named decision-maker on the call
  [ ] point of no return identified and scheduled separately

Follow-ups

  • What if reversal is genuinely impossible? — Then it is a one-way door: it needs more verification up front, a rehearsal on a full copy, explicit sign-off, and everyone should know before it starts that there is no undo.
  • How long do you keep the old path? — Through at least one full business cycle after 100% traffic, then delete it deliberately. Keeping it "just in case" forever is how the endgame stalls.
  • Does a flag flip risk its own incident? — Yes if the flag service is a dependency; cache the value and define the fail-safe default so a flag outage does not become an application outage.

Wrong answer: "We keep the previous deployment available so we can redeploy it if needed." A redeploy is minutes to tens of minutes, needs a working pipeline at the worst possible moment, and says nothing about the data. Reversibility is a config switch plus data compatibility, rehearsed.

Two hours into a cutover, errors are climbing but not catastrophic. Walk me through it. senior

Answer. Stop the ramp immediately — that is free and reversible — and separate the roles: someone owns the incident, someone investigates, someone communicates. Then check the pre-agreed criteria rather than debating: if the error rate is above the abort threshold, roll back and investigate afterwards, because the cheap reversal is the whole reason it was built. If it is below, hold at the current percentage and diagnose with a time box — typically 15–30 minutes — after which the default is to roll back rather than to keep looking. What I am watching is the shape: errors concentrated in one cohort, one endpoint or one tenant is a bug I might fix forward; errors spread evenly and rising is systemic and I reverse. I keep a running written timeline throughout, because the retrospective and the next rehearsal both depend on it. And I would say explicitly that rolling back is not a failure of the cutover — an unused rollback capability is the actual waste.

Example

02:10  ramp 25% -> hold. IC: me. Investigator: A. Comms: B. Scribe: C.
02:12  5xx 0.9% (threshold 1.0%); concentrated on /api/quote, modern cohort only
02:15  hypothesis: pricing timeout under concurrency; check pool + p99 dependency latency
02:26  confirmed: connection pool exhaustion (pool 20, legacy used 100)
02:28  DECISION: roll back to 0% (config, 40 s). Fix + rehearse; re-ramp Thursday.
02:35  verified: error rate at baseline; comms sent; timeline saved to the incident doc

Follow-ups

  • When would you fix forward instead? — When the cause is identified, the fix is small and tested, and rolling back is itself risky (for example, data has already diverged). Otherwise reverse first.
  • Who decides? — The incident commander, using the pre-agreed criteria. During an incident, decision latency is the thing that turns a hold into an outage.
  • What goes in the retrospective? — Why the rehearsal did not catch it — almost always because the rehearsal lacked production concurrency or production data shape.

Wrong answer: "We'd push through — it's probably teething problems and rolling back wastes the work." Sunk cost during an incident, and "probably" is doing all the work in that sentence. The ramp exists to make reversal cheap; refusing to use it means you paid for the mechanism and took the risk anyway.

A week after cutover you discover the new path has been writing subtly wrong data. Now what? senior

Answer. Contain, quantify, correct, communicate — and start the clock on the ones with legal or regulatory dimensions. Contain first: stop the bad writes, which usually means reverting to the legacy path or disabling the affected operation, even if that costs the migration a fortnight. Quantify second: determine exactly which records, over exactly which window, are affected, and be precise — an over-broad estimate destroys trust and an under-broad one leaves corruption in place; this is where the audit trail, event log or CDC history earns its keep. Correct third: a scripted, tested, idempotent remediation run on a restored copy first, with before/after reconciliation, and rehearsal proportional to the number of rows and their sensitivity. Communicate throughout: the business owner needs to know immediately, not when the fix is ready, because downstream consumers may have already acted on the bad data — invoices sent, reports filed, payments made — and correcting the database does not correct those. Then the retrospective question that matters: what verification would have caught this in the first day, and why was it not there? Almost always the answer is that business-metric comparison per cohort was missing.

Example

-- quantify before correcting: exact scope, from the audit trail
SELECT COUNT(*) AS affected, MIN(ModifiedUtc) AS first_, MAX(ModifiedUtc) AS last_,
       SUM(CASE WHEN ExportedToLedger = 1 THEN 1 ELSE 0 END) AS already_downstream
FROM   dbo.Invoices
WHERE  ModifiedUtc >= '2026-09-01T02:00Z' AND WrittenBy = 'orders-api-modern'
AND    TaxMinor <> dbo.fn_ExpectedTax(NetMinor, TaxCode);
-- "already_downstream" is the number that decides whether this is an engineering fix
-- or a business incident with external notifications

Follow-ups

  • What if the correct value cannot be reconstructed? — Then it is data loss: say so plainly, recover what you can from backups and upstream sources, and involve the business in deciding the treatment of the rest.
  • Do you keep the migration paused? — Yes until the class of defect is addressed — not just this instance — and the verification that would have caught it is in place.
  • What if it is a regulated data set? — Legal and compliance are informed immediately; notification deadlines start from discovery, and engineering does not get to decide that timeline.

Wrong answer: "We'd write a script to fix the affected rows and carry on." That treats a trust and process failure as a data-cleanup task. It skips containment, skips quantification, skips the downstream consumers who already acted on the bad data, and skips the question of why a week of wrong writes was invisible.

What is on the risk register for a modernization programme? senior

Answer. The technical risks people expect, plus the organisational ones that actually kill programmes. Technical: undiscovered behaviour in the legacy system (mitigated by parallel run), data migration correctness, performance regression, an unportable dependency, and the coexistence period lasting longer than planned. Organisational, and usually higher probability: loss of sponsorship at a budget review or a reorganisation; the one person who understands the legacy system leaving; a competing initiative taking the team; scope creep from "while we're in there"; and the tail never being finished so coexistence becomes permanent. External: vendor or partner dependencies, and hard dates set elsewhere — right now .NET 8/9 end of support on 2026-11-10, the Functions in-process retirement on the same day, and Windows Server 2016 on 2027-01-12. Each entry gets an owner, an early-warning indicator and a mitigation; what makes a register useful rather than decorative is the indicator, because it converts "sponsor loses interest" from a vague worry into something with a trigger — for example, two consecutive steering meetings cancelled.

  • Which risk materialises most often? — Loss of sponsorship or attention, by a distance. Everything technical is manageable; a defunded programme is not.
  • How do you keep the register alive? — Review it at the quarterly go/no-go with the indicators, and close risks explicitly. A register nobody closes items on is a document, not a tool.
  • Do you share it with the sponsor? — Yes, in full. Surfacing risk early is what buys you credibility when one of them lands.

Wrong answer: "The main risks are technical: data loss, downtime and performance." Those are the manageable ones, with known mitigations. Naming only technical risk suggests you have not run a programme long enough to watch one die of a reorganisation, a budget cycle or a departure.

You inherit a modernization that is 18 months in, over budget, and has delivered nothing. What do you do? senior

Answer. Assess before deciding, and be genuinely open to stopping. Two weeks of discovery: what actually exists (running in production versus written but not shipped), what the original goals were, why nothing has landed, and what the current cost of coexistence and of continuing is. Then present three costed options — stop and stabilise what exists, re-scope to the smallest slice that delivers real value in 90 days, or continue with a changed approach — with the cost and risk of each, including the cost of stopping, which people rarely quantify. My default recommendation in this situation is the middle one: find something shippable inside a quarter and ship it, because the programme's real problem is usually the absence of proof, and one delivered slice changes the conversation more than any plan. I would also fix the structural cause: almost always a plan with no end-to-end slice, foundational work with nothing on top of it, or an architecture that cannot be delivered incrementally. And I would be honest about sunk cost: the 18 months are gone regardless of the decision, and the only question is what the next six are worth.

Example

Option A  STOP        stabilise what exists, retire the half-built path      cost X, risk: original problem remains
Option B  RE-SCOPE    one vertical slice live in 90 days, then reassess      cost Y, risk: needs a sponsor decision now
Option C  CONTINUE    same plan, revised estimate                            cost Z (>2X), risk: same failure mode
Recommend B. Structural fix: every slice ends in production; nothing is "done" until traffic uses it.

Follow-ups

  • How do you tell a sponsor their investment has produced nothing? — Factually, without blame, with options and a recommendation. People forgive bad news delivered early with a plan; they do not forgive discovering it later.
  • What if the team is demoralised? — Ship something small quickly. Nothing restores a team faster than a change that reaches users, and it is also the evidence you need.
  • When would you genuinely recommend stopping? — When the original driver has gone (the system is being replaced by a purchased product, the business line is closing) or when the remaining cost exceeds the risk being removed.

Wrong answer: "We've come this far, so I'd get it over the line — restarting would waste the investment." Textbook sunk-cost reasoning, and it is the reason such programmes reach 18 months. The money is spent either way; the only live question is the value of the next increment.

How do you design the blast radius of a change before you make it? principal

Answer. By deciding, in advance, who can be hurt and for how long, and then building the change so the answer is enforced rather than hoped for. The levers: cohort (internal users first, then a friendly tenant, then a percentage, then everyone), scope (one endpoint, one entity type, one region), duration (an automatic expiry on the experiment so a forgotten ramp does not become the default), and reversibility (config-switchable, data-compatible). I also run a pre-mortem before significant cutovers — the team assumes it is six weeks later and the change failed badly, and writes down why — which surfaces different risks than a forward-looking risk assessment, particularly the organisational ones nobody wants to raise in a planning meeting. The output is not a document; it is changes to the plan: an added rehearsal, a narrowed first cohort, a metric that was not being collected. And I make blast radius explicit in the go/no-go: "worst case, N tenants see degraded quotes for up to M minutes, and here is how they are made whole" — a sponsor can approve that, whereas they cannot approve "we're pretty confident".

Example

Pre-mortem output for the pricing cutover
  "It failed because..."
   - the pricing service throttled at real concurrency        -> load test at 3x peak first
   - a month-end batch hit a path nobody ramped               -> shift the cutover away from month-end
   - the flag was left at 50% and nobody noticed              -> auto-expiry on the ramp state
   - the only person who understood it was on leave           -> two people run the rehearsal
Blast radius as approved: max 40 tenants, max 15 minutes, quotes re-issued automatically.

Follow-ups

  • Why a pre-mortem rather than a risk assessment? — Assuming failure has already happened removes the social cost of pessimism, so people say the things they would otherwise keep quiet.
  • How do you choose the first cohort? — Internal users, then tenants who have agreed to be early, then the smallest representative slice. Never your largest customer, and never a cohort so unrepresentative that success proves nothing.
  • Can blast radius be too small? — Yes: a cohort with no real traffic gives false confidence. It must be small and representative, which is a design decision.

Wrong answer: "We test thoroughly in staging so the blast radius doesn't matter." Staging never has production's data, concurrency, integrations or user behaviour, which is precisely why blast-radius design exists. Thorough testing and a small first cohort are complements, not alternatives.

14Leading people through modernization

Modernization is disproportionately a people problem, and lead/principal loops always contain at least one question here — usually disguised as a technical scenario. What is being tested is whether you can move an organisation, not just a code base: the team that built the legacy system, the sponsor whose attention wanders, the knowledge held by one person, and the morale cost of a two-year programme with no launch party. Answers that treat resistance as irrationality score badly; answers that find the legitimate concern inside it score well.

Docs: Cloud Adoption Framework — organize · DORA capabilities

The team that built the legacy system will maintain the new one. How do you bring them with you? mid

Answer. By treating them as the source of the requirements rather than as an obstacle, because they are: the "weird" code is their accumulated knowledge of edge cases, and nobody else can tell you which of it still matters. Practically: they own the migration of their own components rather than watching someone else do it; my first change addresses a pain they nominated, not one I diagnosed; and I never characterise the existing system as bad — it was built under constraints, most of which I was not there for. Then I invest in capability early, because the real resistance is usually fear of becoming less valuable in the new stack: training, pairing, and giving them the first meaningful pieces of new work rather than only cleanup. And I am explicit about what does not change — their domain knowledge is the scarce asset and it transfers completely. Where resistance persists after that, it is usually a legitimate concern I have not heard yet.

Example

Week 1   ask each engineer: "what wastes your time every week?" -> ranked list
Week 2   fix the top item, ship it, credit them publicly
Week 3-4 pair on the first migrated module; they drive, I navigate
Ongoing  each engineer migrates their own components; training budget agreed up front
Never    "the old code is bad" - it is "the constraints changed"

Follow-ups

  • What if their concern is that they will be made redundant? — Address it directly with whatever truth you have, including "I don't decide that, and here is what I do control". Evasion confirms the fear.
  • How do you handle the person who wrote the worst part? — Ask them what they would change and why it is that way; the answer is usually a constraint you did not know about, and it recruits them.
  • How long does buy-in take? — Weeks if you deliver something they wanted; indefinitely if the first move is a plan they were not consulted on.

Wrong answer: "I'd bring in a modernization team with the right skills and have them lead it, with the legacy team supporting." That structure creates an in-group and an out-group, and the people holding the knowledge you need most are placed in the losing one. It is also the structure that produces the parallel-team failure mode where the legacy path keeps growing.

A senior engineer insists the whole thing should be rewritten from scratch. How do you handle it? senior

Answer. Take the position seriously and interrogate it, because there is usually a real problem underneath — most often that the current architecture makes a specific class of change impossible, and they are tired of paying for it. So I ask for specifics: what would the rewrite make possible that incremental change cannot, how long, and what happens to feature delivery meanwhile. Frequently the honest answer converges on "one subsystem is beyond repair", which is a proposal I can support, scoped and funded. If they hold to a full rewrite, I make the comparison explicit and shared — cost, timeline, risk of both paths, in writing — and if the decision goes against them, I ask for their commitment to make the chosen path work, and I give them a meaningful role in it (often designing the target architecture that the strangler converges on). What I do not do is win by authority and leave the disagreement unresolved: an unconvinced senior engineer will find the incremental path's every weakness, which is corrosive if they are opposed and extremely valuable if they are not.

Example

Question set for the rewrite advocate
  1. what specifically becomes possible?            (if "cleaner code" - keep digging)
  2. what is the parity list, and who validates it?
  3. what happens to the roadmap for N months?
  4. what is the cutover, and what is the rollback?
  5. which subsystem is genuinely beyond repair?    (this is usually the real answer)
Outcome: scoped rewrite of one subsystem behind the facade; they own the target architecture.

Follow-ups

  • What if they are right? — Then say so and change the plan. Being persuadable by evidence is the behaviour you want the team to copy.
  • What if they will not commit after the decision? — A direct conversation about disagree-and-commit, and if that fails it becomes a management issue. One unresolved dissenter at senior level can stall a programme.
  • How do you keep the debate from consuming weeks? — Time-box it: one written comparison, one decision meeting, a date.

Wrong answer: "I'd explain that rewrites always fail and point them at the literature." Correct-sounding, dismissive, and it wastes the information in their objection. It also loses the strongest engineer's engagement on the exact work where you need it most.

One person understands the legacy system. How do you fix that? senior

Answer. By making the knowledge transfer a by-product of the work rather than a documentation project, because documentation written to order goes stale and gets skipped. The mechanisms that work: pair or ensemble on every migration slice touching their area, so the knowledge transfers while the work happens; make them the reviewer rather than the implementer, which forces the knowledge into someone else's hands and their head into the review; capture what surfaces as tests, because a characterization test is executable knowledge that cannot go stale silently; and rotate who carries the pager for that component, which is the fastest way to discover what is actually undocumented. I would also record short walkthroughs — 15 minutes of narrated code, kept with the repository — since they cost almost nothing and are what new joiners actually watch. And I would state the risk explicitly to management with the mitigation cost, because "the bus factor is one on the billing engine" is a business risk, not an engineering preference.

Example

Bus-factor plan for the billing engine (owner: A, currently sole)
  every slice paired with B or C; A reviews rather than implements after week 3
  each pairing session ends with 1 characterization test + 1 note in the repo
  A takes a two-week holiday in month 2 - deliberately, as the test
  metric: PRs touching billing authored by someone other than A (target > 50%)

Follow-ups

  • What if they resist sharing? — Usually it is workload or fear of losing status, not hoarding. Recognise the expertise publicly, reduce their delivery load to make room, and make mentoring part of how their contribution is measured.
  • Is documentation worthless? — No, but architecture decisions and rationale age far better than mechanics; write the "why", let tests and code carry the "how".
  • What if they leave mid-programme? — Slow down deliberately and rebuild understanding with parallel run and characterization tests. Pretending you still have the knowledge is how you cut over something nobody understands.

Wrong answer: "I'd have them write comprehensive documentation of the system before we start." It takes months, it blocks the migration, it is written from memory rather than from the code, and it will be wrong in the places that matter. Knowledge transfers through shared work, not through a document.

What does your progress report to a non-technical steering group look like? senior

Answer. One page, four sections, and no engineering vocabulary. Value delivered since last time, in their terms: which capabilities are now on the new path, what got faster, what risk is retired. Risk position: forced dates and their status, the top three live risks with owners and indicators. Cost: spend against plan, plus the cost of coexistence — the monthly bill for running two of everything, which is the number that keeps the endgame funded. And decisions needed, with options and a recommendation, because a steering group's function is to decide rather than to be briefed. What I explicitly do not report is percentage complete, because it is unfalsifiable and it hides the tail; instead I report countable things — endpoints migrated, legacy hosts remaining with their shutdown dates, tenants on the new path. The tone matters too: surface bad news early and with a plan. A report that is always green is a report nobody believes when it finally turns amber.

Follow-ups

  • They ask "when will it be done?" — Give a date for the next named outcome and a range for the endgame, with the assumptions that would change it. A false precise date buys one meeting of comfort and a year of distrust.
  • How often? — Monthly written, quarterly go/no-go. More often produces theatre; less often loses the sponsor.
  • What if a month has no visible value? — Say so and explain what it bought. Two consecutive such months is a signal that the slicing is wrong.

Wrong answer: "We report on the burndown and the percentage of the migration complete." Percentage complete is the metric that lets a programme sit at 80% for a year; it is also meaningless to a steering group. Countable outcomes, forced dates, cost of coexistence and decisions needed are what they can act on.

Two years is a long time. How do you keep a team motivated? senior

Answer. By making sure the work reaches users often, because the demotivating thing is not difficulty, it is invisibility. Every slice ends in production and every cutover is announced with what it improved, so there is a stream of small completions instead of one distant finish. I mix the work deliberately — nobody spends six months only deleting legacy code — and I make sure the interesting new-stack work is shared rather than monopolised by whoever is fastest. I also protect the team from the two things that grind people down: endless coexistence with no deletions (so "delete the old path" is in every definition of done, and it is genuinely satisfying), and being blamed for legacy incidents they inherited. Recognition should go to progress that is not user-visible too — the test net, the pipeline, the deleted subsystem — because that is most of the work. And I keep an eye on the specific fatigue of migration work: it is relentless, low-glory and detail-heavy, so rotation and honest acknowledgement matter more than in feature work.

Example

Rituals that keep a long programme alive
  demo every 2 weeks, always something running in production
  a "deleted" channel: lines removed, hosts shut down, flags retired - celebrated
  rotation: nobody does only migration or only features for more than a sprint
  a visible countdown of legacy hosts remaining, with their shutdown dates
  retro after every cutover, including the ones that went fine

Follow-ups

  • Someone wants to leave because the work is unglamorous. — Find them something with visible ownership — the new architecture, the platform work, the first extraction — and be honest that some of the work is grind. Pretending otherwise loses them anyway.
  • How do you celebrate deletion? — Make it countable and public: lines removed, hosts decommissioned, the monthly bill going down. Deletion is the most under-recognised achievement in this work.
  • What is the biggest morale risk? — A cancelled or indefinitely paused programme. Which is why quarterly value delivery is a morale strategy as much as a governance one.

Wrong answer: "We'd keep the team focused on the end goal and the benefits of the new architecture." A goal two years away motivates nobody by month four. Frequent completion, visible deletion and rotation are what sustain a long programme; the vision is necessary and nowhere near sufficient.

How do you structure teams for a large modernization? principal

Answer. Stream-aligned teams owning capabilities end to end — including their migration — plus one small enabling team that builds the paved road: the pipeline, the shims, the patterns, the reference implementation, and hands-on help. The enabling team's success measure is the other teams' throughput, not its own output, and it must be explicitly forbidden from becoming the team that does all the migrations. I resist two structures: a central migration team working on other teams' code (they lack context, they collide with feature work, and ownership evaporates at handover), and a component-shaped organisation, because Conway's law means the architecture will end up matching the org chart — so if the target is capability-aligned services, the teams should be capability-aligned before the code is. Cross-cutting concerns get a working group rather than a team. And I would name the inverse Conway manoeuvre explicitly: reorganise towards the target architecture, then let the code follow, because trying to build a capability-aligned architecture with a layer-aligned organisation loses every time.

                                                  pairing; measured on others' lead time

Follow-ups

  • What if a legacy component has no owning team? — Assign one before starting; unowned components are where migrations stall and where the tail lives.
  • How big should the enabling team be? — Small, 3–5, and time-boxed in its current form. If it grows, it is doing the work instead of enabling it.
  • Does this need a reorganisation? — Often a light one. Given Conway's law, changing team boundaries is one of the highest-leverage architectural moves available, and it is usually cheaper than the code work it enables.

Wrong answer: "A dedicated modernization team with the strongest engineers, so the product teams keep delivering features." It is the most common structure and the most reliable failure: the product teams keep adding to the legacy path faster than the migration team removes from it, and nobody owns the result at handover.

15Measuring modernization

A smaller sub-area, asked mostly at senior and above and usually as a follow-up to the business-case question: how would you know this worked? The trap is vanity metrics — percentage migrated, lines of code, projects retargeted — which measure activity rather than outcome. Good answers pair delivery metrics with cost and risk, and are honest that some benefits are only visible as an absence.

Docs: DORA · Well-Architected: Operational Excellence

What metrics tell you the modernization is working? mid

Answer. Three families. Delivery: the four DORA metrics — deployment frequency, change lead time, change failure rate, time to restore — because the point of modernization is usually to make change cheap and safe, and these measure exactly that. Risk retired: components off unsupported runtimes, open vulnerabilities that were previously unpatchable, forced dates met, legacy hosts decommissioned. Cost: the coexistence bill, infrastructure spend, and the share of engineering time spent on toil rather than on product. On top of those I keep one or two outcome measures the business already cares about — time to deliver a specific class of feature, or the cost per transaction — because they are the ones that survive a change of sponsor. I would also be honest that some benefits are counterfactual: the incident that did not happen and the CVE that was patched in a day rather than never are real value that no chart displays well, and pretending otherwise leads to over-claiming that damages credibility later.

Follow-ups

  • Can DORA metrics be gamed? — Easily: deploy trivial changes often. Which is why change failure rate and time to restore are reported alongside, and why they are trends for the team rather than targets imposed on it.
  • What if delivery metrics get worse during the migration? — Expected during coexistence; say so in advance with the expected shape, so a dip is a forecast rather than a surprise.
  • Which single metric would you pick? — Change lead time. It captures the pipeline, the test net, the architecture and the approval process in one number.

Wrong answer: "Percentage of the code base migrated, and test coverage." Both measure effort, neither measures value: you can be 80% migrated with worse delivery performance and the same risk profile, and coverage can rise while nothing gets safer. Outcome metrics only.

How do you measure technical debt without it becoming a vanity number? senior

Answer. I measure the effects rather than trying to price the debt, because the effects are the reason anyone cares. Concretely: the cost of change in the affected areas (lead time and effort for comparable work in module A versus module B), the failure rate of changes there, the toil (manual steps, recurring incidents, time spent on environment problems), and the constraint list — the things that are currently impossible or absurdly expensive. Where a single number is demanded, I use a small set of countable risk facts instead: components on unsupported runtimes, unpatchable vulnerabilities, bus-factor-one components, undeployable-without-manual-steps systems. What I avoid is the composite "debt score" from a static analysis tool: it is precise, unfalsifiable, and correlates poorly with what actually makes change expensive — and once it is on a dashboard, teams optimise the score rather than the system. The honest framing to a sponsor is that debt is not a quantity, it is an interest payment, and I can show what we are paying.

Example

Instead of "debt: 412 days"
  comparable feature, legacy module      18 days, 2 of 5 releases required a fix
  comparable feature, migrated module     4 days, 0 fixes
  toil                                    31% of team time (survey + incident hours)
  currently impossible                    per-tenant configuration; regional deployment
  unpatchable CVEs                        9 (framework-blocked)

Follow-ups

  • Is static analysis useless then? — No — it is useful for finding specific issues and for trend within a team. It is the aggregate money-valued score that misleads.
  • How do you compare modules fairly? — Same class of work, same team, enough samples. Anecdote is fine as illustration and not as evidence.
  • What about a debt register? — Useful if entries are specific, owned and dated. A list of vague complaints is noise.

Wrong answer: "We'd use SonarQube's technical debt ratio to track it over time." It gives a confident number derived from rule violations that mostly do not predict the cost of change, and it invites optimising the metric. Measure the pain — lead time, failure rate, toil, impossibility — not a synthetic score.

How do you avoid vanity metrics in modernization reporting? senior

Answer. Apply one test to every metric: if this number improves and nothing else does, has anything actually got better? "Projects retargeted", "lines migrated", "services created", "percentage complete" all fail it. Then prefer metrics that can go down as well as up and that someone could use to argue with you — cost of coexistence, lead time, change failure rate, legacy hosts remaining with dates. I also insist that the countable things be countable in the world rather than in a plan: an endpoint serving production traffic on the new path is a fact; a story marked done is an assertion. The specific failure mode to name is percentage complete: it is the metric that lets a programme sit at 80% for a year, because the denominator is unknown and the remaining tail is the expensive part. And I would rather report a smaller set of honest metrics than a dashboard, because a dashboard with thirty tiles is where the important number goes to hide.

  • Stakeholders want a percentage anyway. — Give a countable proxy with a denominator you can defend — "31 of 47 endpoints, 4 of 6 hosts" — which is a percentage that can be checked.
  • Is velocity useful here? — Only inside the team for planning. As a reported metric it is pure vanity and actively harmful.
  • How many metrics should the report carry? — Five or six. More and nobody reads them; fewer and you are hiding something.

Wrong answer: "We track percentage complete, story points and test coverage — they show steady progress." All three can improve while delivery gets slower, risk stays flat and the coexistence bill grows. A year later, the CFO asks whether the modernization paid off. How do you answer? senior

Answer. With the same frame I used to ask for the money, populated with actuals, and with the parts I cannot prove labelled as such. Costs avoided: ESU and support contracts no longer needed, infrastructure retired, licences dropped — hard numbers from invoices. Capacity released: the change in toil percentage times the team's cost, with the measurement method stated. Delivery: lead time and change failure rate before and after, and the specific roadmap items that were previously blocked and have now shipped. Risk retired: components off unsupported runtimes, vulnerabilities now patchable, DR now rehearsed rather than theoretical. And the honest caveats: attribution is imperfect because other things changed too, and the counterfactual — the incident that did not happen — cannot be measured. That honesty is what makes the rest credible; a report claiming a precise multi-million return from a modernization is the sort of thing that gets audited and then disbelieved. If the answer is "partly", I say partly, and I say which part did not pay and what I would do differently.

Example

Costs avoided (invoiced)     ESU £180k/yr; 6 hosts retired £64k/yr; 2 licences £22k/yr
Capacity released (measured) toil 31% -> 12% of 9 FTE  ~ £260k/yr, method: time survey + incident hours
Delivery (measured)          lead time 31d -> 4d; CFR 22% -> 9%; 3 blocked roadmap items shipped
Risk retired (countable)     14 -> 0 unsupported components; 9 -> 0 unpatchable CVEs; DR rehearsed twice
Spent                        £780k over 5 quarters
Not claimed                  incidents avoided (counterfactual); attribution shared with other changes

Follow-ups

  • What if it did not pay off? — Say so, with the reason and the learning. Overstating a return is a one-time gain and a permanent credibility cost.
  • How do you handle attribution? — State it plainly: other changes happened; here is why the direction is nonetheless attributable, and here is what would falsify it.
  • What about the benefits that arrive later? — Name them with an expected date and revisit. Some value (hiring, optionality) only shows up over years.

Wrong answer: "Developer productivity is up 40%, so it paid for itself." Productivity is not measurable to that precision, the number will not survive scrutiny, and offering it invites exactly the scrutiny that destroys the rest of the case. Invoiced savings, measured delivery metrics, countable risk — and explicit humility about the rest.

16Cost, licensing & FinOps

Asked when the role has a budget attached, and often as a sanity check: does this person know that lift-and-shift usually costs more, and why? Mid depth is the cost model change and the main Azure levers; senior depth is diagnosing a bill that came in higher than the business case and building an honest TCO comparison. Licensing detail is genuinely useful here because it is where the largest single savings usually sit.

Docs: Azure Hybrid Benefit · FinOps on Azure · Cost Management

What actually changes about cost when you move to Azure? mid

Answer. The shape changes more than the total. You move from capital expenditure with a three-to-five-year refresh cycle and mostly fixed cost, to operating expenditure that varies with usage and is visible monthly — which is a finance change as much as a technology one, and it is why the first cloud bill is often a shock even when the migration was a success. The controllable levers, roughly in order of size: right-sizing (on-premises servers are provisioned for peak plus headroom and typically run at 10–20% utilisation, so a like-for-like move buys idle capacity at retail price), reserved instances and savings plans for steady workloads (substantial discounts for a one- or three-year commitment), Azure Hybrid Benefit for Windows Server and SQL Server licences you already own — including free Extended Security Updates for out-of-support SQL Server and Windows Server running in Azure, which is often the single biggest line — non-production environments shut down outside working hours, and autoscale so variable workloads actually vary. The cost items people forget are egress, cross-region traffic, log ingestion and backup storage, all of which are usage-based and none of which appeared on the old bill.

  • When are reservations a mistake? — On anything you plan to re-architect within the term; you commit to a shape you are about to change. Reserve the stable core, not the parts in flight.
  • What surprises teams most? — Log and telemetry ingestion, egress, and non-production environments left running. All three are invisible on-premises.
  • Does PaaS cost more than VMs? — Higher unit price, usually lower total once you count the operational hours and the licences it absorbs. Compare total cost of ownership, not sticker price.

Wrong answer: "Moving to the cloud reduces cost because you only pay for what you use." You pay for what you provision, and a lift-and-shift provisions the same idle capacity at retail. Cloud enables cost control; it does not deliver it, and saying otherwise is how a business case fails at the first invoice.

Six months after the lift-and-shift the bill is 40% over the business case. What do you do? senior

Answer. Diagnose before cutting, because the usual causes are specific and fixable. I break the bill down by resource, environment and owner — untagged resources first, since an estate without tags cannot be managed and the untagged portion is where the surprises hide. The usual findings, in the order I encounter them: non-production environments running 24/7; VMs sized from the old hardware specification rather than measured utilisation; storage tiers and snapshots nobody cleaned up; log ingestion at debug level; orphaned resources (disks, IPs, load balancers) from failed deployments; and no reservations on genuinely steady workloads. Then I fix in order of effort against saving — schedules and orphan cleanup first (days, immediate), right-sizing next (weeks, needs measurement), reservations once the shape is stable — and I put a guardrail in place: budgets with alerts, cost anomaly detection, and a monthly review where each team sees its own spend. The cultural fix matters most: cost has to be visible to the people who create it, or it stays somebody else's problem.

Example

  untagged spend            34%  -> enforce tags via Azure Policy; assign owners
  non-prod running 24/7           -> auto-shutdown schedules: ~65% of non-prod cost
  VMs sized from old spec         -> right-size on 30-day p95 CPU/memory, not on the spec sheet
  orphaned disks/IPs/snapshots    -> cleanup + a policy to prevent recurrence
  Log Analytics at debug          -> levels, sampling, retention tiers
  steady core, no reservations    -> reserve once the architecture stops moving

Follow-ups

  • How do you stop it recurring? — Budgets and anomaly alerts per team, tags enforced by policy, and cost as a standing item in the team's monthly review. Central cost policing does not work.
  • Is it worth re-architecting to save money? — Sometimes — serverless or scale-to-zero for spiky workloads can be dramatic — but only after the cheap fixes, and only with the engineering cost in the comparison.
  • How do you handle the conversation with the sponsor? — Own the variance, show the diagnosis and the plan with dated savings. Cost overruns are survivable; unexplained ones are not.

Wrong answer: "We'd negotiate a bigger discount with Microsoft and buy reservations." Reservations on an unoptimised, wrongly-sized estate lock in the waste for one to three years. Right-size and clean up first; commit to the shape only once it is the shape you actually want.

How does licensing affect your modernization choices? senior

Answer. More than most engineers expect, and it is often where the biggest single saving or cost sits. Windows Server and SQL Server licences you already own can be applied to Azure through Azure Hybrid Benefit rather than paying the pay-as-you-go rate, and out-of-support SQL Server and Windows Server get Extended Security Updates free while running in Azure — which is why "move it to an Azure VM" is frequently the cheapest way to deal with an end-of-support server that cannot be upgraded yet. SQL Server edition matters architecturally, not just financially: several of the online-DDL and HA features are Enterprise-only, so an edition decision constrains your zero-downtime options. Moving from Windows to Linux hosting removes Windows licensing entirely and is often free money once the application runs on modern .NET, which is a genuine, quantifiable modernization benefit worth putting in the business case. And on the database side, the choice between Managed Instance, single database and a VM has a licensing dimension (vCore versus licence-included pricing) that should be modelled, not assumed. My practice is to get a licensing specialist into the design conversation early — the rules are detailed, they change, and an engineer guessing at them can be wrong by six figures.

Example

Same workload, four shapes
  on-prem SQL Std VM         hardware refresh + SA + hosting + your ops hours
  Azure VM + Hybrid Benefit  bring your licence; free ESU for out-of-support versions

  .NET 10 on Linux containers no Windows licence at all - a modernization dividend

Follow-ups

  • Does moving to Linux always save money? — It removes Windows licensing; it adds a skills and tooling change. Net positive for a team already comfortable with containers, less obvious for a Windows-only operations group.
  • How does edition constrain design? — Enterprise-only features (online index rebuilds, some HA options, partitioning capabilities) are exactly what your zero-downtime plans rely on; confirm the edition before designing around them.
  • Who should own this? — Not you alone. Get licensing expertise into the room; the rules are specific and mistakes are expensive in both directions.

Wrong answer: "Licensing is a procurement problem, not an architecture one." It determines which SQL features you can design with, whether an out-of-support server can stay alive legally, and whether Linux hosting is a saving or a wash. Treating it as somebody else's problem is how an architecture arrives that finance cannot fund.

Build the TCO comparison for staying versus migrating. What goes in it? senior

Answer. Both columns must be complete, and the "stay" column is the one people under-fill. Staying costs: hardware refresh amortised, data centre or hosting, licences and support contracts, extended security updates, the operations hours (patching, backups, DR tests) at loaded rates, the incident cost at the current rate, and the opportunity cost of the roadmap items that cannot be built. Migrating costs: the engineering effort with a realistic range, the cloud run-rate after right-sizing, the coexistence period where you pay for both, training, and the temporary productivity dip. Then compare over a horizon long enough to include a hardware refresh — typically five years — with a stated discount rate if finance wants one, and with a sensitivity analysis on the two or three assumptions that dominate, usually engineering effort and post-migration run-rate. What makes the comparison credible is the ranges and the assumptions being visible: a single number invites disbelief, whereas "here is the range, here is what would change it, here is the break-even" invites a decision.

  • What if migrating never breaks even? — Then say so, and make the case on risk and optionality instead — or recommend not migrating. A modernization justified on a manipulated TCO fails at the first review.
  • How do you estimate engineering effort credibly? — From your own first completed slice, in units of "modules like that one", with a range. Anything before that is a guess and should be labelled one.
  • Should the incident cost be included? — Yes, at the historical rate, and clearly labelled as an estimate. It is usually the largest hidden cost of staying.

Wrong answer: "Compare current hosting cost against the Azure pricing calculator estimate." That omits the operations hours, licences, ESU, hardware refresh, migration effort and coexistence — the majority of both columns — and produces a comparison that a CFO will dismantle in one meeting, taking your credibility with it.

17AI-assisted modernization

New, current and increasingly asked, because tooling shipped in 2025–2026 changed what is realistic: GitHub Copilot modernization for .NET is generally available across Visual Studio 2026, VS Code, the Copilot CLI and github.com, and the .NET Upgrade Assistant has an AI-assisted mode. Interviewers are checking two things at once: that you know the tools exist, and that you have a sober view of what they can and cannot decide. Over-claiming and dismissing both score badly; the good answer is "mechanical work with a strong verification net".

Docs: GitHub Copilot modernization for .NET · .NET Upgrade Assistant

Where does AI genuinely help in a modernization today? mid

Answer. Four places, all characterised by high volume, mechanical transformation and cheap verification. Assessment: inventorying a solution, finding incompatible APIs, and producing a first-pass migration plan — Copilot modernization for .NET does exactly this and iterates on build errors until the project compiles. Mechanical code transformation: project files, package references, API swaps, HttpContext.Current removal, converting a file to TypeScript — repetitive edits with a compiler as the oracle. Comprehension: explaining an unfamiliar 4,000-line stored procedure or a class nobody understands, which is genuinely valuable when the author left in 2015 — with the caveat that the explanation is a hypothesis to verify, not documentation. And test generation: characterization tests over existing behaviour, where the model writes the scaffolding and the assertions are captured from actual runs. What all four share is that a human or a compiler can check the output cheaply. Where verification is expensive — deciding whether a quirk is a bug or a requirement, choosing a boundary, judging a trade-off — the tool has no advantage and considerable confidence.

Example

High value (cheap to verify)          Low value (expensive to verify)
  retarget 200 project files            is this rounding a bug or a regulatory rule?
  packages.config -> PackageReference   where should the service boundary be?
  remove HttpContext.Current            is this cutover safe to run tonight?
  JS -> TS file conversion              which of these 40 quirks must be preserved?
  first-pass characterization tests     what should we not migrate at all?

Follow-ups

  • What is the realistic productivity effect? — Large on the mechanical bulk, near zero on the decisions — and since the decisions are usually the critical path, the honest claim is weeks saved on a multi-quarter programme, not a halving.
  • Does it change the plan? — It moves the cost balance: mechanical migration gets cheaper, so strategies that were rejected for grind (converting every call site rather than shimming) become viable.
  • What is the prerequisite? — A test net. Without verification, faster code changes are just faster unreviewed changes.

Wrong answer: "AI can migrate the code base automatically — you point it at the repository and review the PRs." The tools genuinely produce a compiling, plausible result; the failure is behavioural, and reviewing a 40,000-line generated diff for behaviour change is not a thing humans do well. The compiling result is the beginning of the work.

How do you use an LLM to understand a legacy code base without being misled? senior

Answer. Treat every output as a hypothesis with a cheap verification attached. I ask for explanations of specific units — this procedure, this class, this configuration file — rather than "explain the system", because narrow questions with the code in context are where the accuracy is. Then I verify: the explanation says this branch fires when the status is 'X', so I query production data for status 'X' and see whether it occurs, or add a log line and watch. I use it to generate candidate questions rather than answers — "what edge cases might this code handle?" produces a checklist worth testing — and to draft characterization tests whose assertions come from real runs rather than from the model's expectation. The risk to name is confident fabrication of behaviour that is not in the code, which is especially dangerous in legacy work because there is nobody left to contradict it. So: never let a model's explanation become the basis for deleting code, and never treat generated documentation as authoritative — the authority is the code, the data and the traffic.

Example

Prompt shape that works
  [paste the 300-line procedure]
  "List every branch and the condition that reaches it. For each, say what data would
   prove it is still exercised in production. Do not speculate about intent."
Then verify each claim with a query or a log line before it enters the plan.

Follow-ups

  • How do you handle a very large code base? — Work bottom-up on units, and use the tooling's repository-wide indexing for navigation rather than for conclusions.
  • Can you trust generated documentation? — As a draft that a human who verified it signs. Unverified generated documentation is worse than none, because it is trusted.
  • Where has it been most valuable in practice? — Explaining dense stored procedures and gnarly regular expressions, and drafting the first version of tests for both.

Wrong answer: "We'd have it generate documentation for the legacy system as the starting point." Generated documentation reads authoritatively and is confidently wrong in exactly the places nobody can check, and it then gets cited for months. Verify claim by claim against data and traffic, or do not record it.

What guardrails do you put around AI-generated migration changes? senior

Answer. The same as for any change, applied more strictly because volume is the point. Small, reviewable PRs — one project or one concern per PR, never a repository-wide sweep — so review is genuinely possible. Mechanical changes separated from behavioural ones, so a project-file retarget never shares a diff with a logic edit. The full test suite plus characterization tests as the gate, and for a public library an API-surface diff so signature changes cannot slip through. A human owner per PR who is accountable for it, because "the tool did it" is not a review. And a stated rule about what the tool may not decide: whether a legacy behaviour is preserved, where a boundary goes, whether a cutover proceeds. I would also watch for the specific failure mode of generated code — plausible-looking handling of the edge case that quietly differs, particularly around nulls, culture, rounding and time zones — and I would put those explicitly on the review checklist rather than trusting a general read-through.

Example

PR policy for tool-assisted migration
  scope        one project OR one mechanical concern; < ~800 lines of real change
  separation   project/package changes and code changes never in the same PR
  gates        full suite + characterization approvals + public API diff + build on both TFMs
  review       named human owner; checklist: nulls, culture, rounding, time zones, async
  forbidden    behaviour decisions, boundary decisions, cutover decisions

Follow-ups

  • How do you review a large generated diff? — You do not: you reject it and ask for smaller ones. Reviewability is a property of the change, and it is your job to require it.
  • Do you allow generated tests? — Yes as scaffolding, with assertions captured from real behaviour and a human confirming they assert something meaningful. A generated test asserting the generated behaviour is circular.
  • Does this slow it down enough to remove the benefit? — No: the generation was never the bottleneck. Verification was, and it still is.

Wrong answer: "We'd review the generated changes carefully before merging." Everyone says this and nobody does it at 40,000 lines. The guardrail that works is structural — small scoped PRs, mechanical and behavioural changes separated, automated gates — not an intention to be careful.

Where would you refuse to use AI assistance in a migration? senior

Answer. Anywhere the cost of a plausible-but-wrong answer is high and verification is expensive. Concretely: deciding whether a legacy behaviour is a bug or a requirement, because that needs business context no model has and being wrong is silent; data migration and transformation logic for financial or regulated data, where I want code a human wrote and a reconciliation that proves it; security-sensitive code — authorization rules, cryptographic choices, token validation — where plausible and wrong is the definition of a vulnerability; architectural boundaries, which depend on the organisation as much as the code; and anything where the model would need to see data it should not (production personal data pasted into a prompt is a governance incident, and I would state that explicitly). I would also avoid it as the primary explanation for a system nobody understands when a decision to delete rests on the answer. The framing I would give: use it where the compiler or a test is the oracle; avoid it where a human's judgment is the oracle and the feedback loop is a quarter long.

Example

Refuse                                        Because
  "is this rounding rule a bug?"                needs business/regulatory context; wrong = silent
  financial data transformation logic           reconciliation must prove a human's intent
  authorization rules, crypto, token checks     plausible-but-wrong = vulnerability
  service boundaries                            depends on teams and ownership, not code
  anything requiring production PII in context  governance incident, independent of quality

Follow-ups

  • Not even as a first draft for security code? — As a draft to critique, with a security review that would happen anyway. What I will not do is let it be the reason nobody thought hard.
  • How do you handle the data governance issue? — Explicit policy on what may be pasted, tooling configured for the enterprise boundary, and masked samples for anything involving real data.
  • Does this stance age badly as the tools improve? — The line moves with verification cost, not with model quality: as verification gets cheaper or the tools get better at proving their work, more moves into the "use it" column.

Wrong answer: "Nowhere — with proper review it's safe everywhere." That collapses the distinction the question is probing. Review quality is not uniform: reviewing a retarget diff is easy and reviewing whether a generated financial transformation preserves twenty years of tacit rules is not, and pretending otherwise is how a subtle data defect ships.

A vendor offers automated legacy modernization. How do you evaluate the claim? senior

Answer. With a paid pilot on your own hard code and pre-agreed acceptance criteria, not on their demo repository. I would pick a representative module — one with real gnarliness, not a leaf library — and define success in advance: it compiles, the characterization tests pass, performance is within a stated band, and the output is code my team judges maintainable, which is the criterion vendors most often fail. Questions I would ask: what does the output look like (idiomatic modern code, or transpiled legacy structure with modern syntax?), who owns and can maintain it afterwards, what happens to the parts it cannot handle, is there lock-in to their runtime or their tooling, and what is the reference customer's experience two years on rather than at go-live. The specific failure to watch for is a faithful mechanical translation that preserves every legacy design decision — you get a .NET 10 code base with a .NET Framework architecture, having spent the budget and gained the maintainability of the original. And I would insist that the verification net is mine: their tests proving their output is circular.

Example

Pilot contract
  module        the ugly one (real dependencies, real quirks), chosen by us
  criteria      builds | our characterization tests pass | p95 within 10% | our team rates
                the output maintainable (blind review by 3 engineers)
  artefacts     the code is ours, no runtime lock-in, no per-seat dependency to run it
  references    two customers, 18+ months post-delivery, spoken to without the vendor present

Follow-ups

  • What if the pilot succeeds but the team dislikes the output? — That is a failure: they maintain it for the next decade. Maintainability is an acceptance criterion, not a preference.
  • Is there a legitimate use for such vendors? — Yes, for genuinely mechanical bulk on a large estate, with your architecture decisions made by you and their output reviewed by you.
  • What is the biggest commercial risk? — Dependency on a proprietary runtime or framework: you replaced a legacy platform with someone else's proprietary one and a licence.

Wrong answer: "If they can demonstrate a successful migration of a similar system, that's good enough evidence." Every vendor can demonstrate a successful migration — of a system they chose. The evidence that matters is your hardest module, your tests, your team's judgment of the output, and a reference customer two years down the line.

18Legacy integration: WCF, SOAP, MSMQ

Rarely the focus of a loop, but it appears as a follow-up whenever an estate is genuinely old, and a blank look here is costly because these technologies are the reason many systems cannot move. Mid depth is knowing what replaces what; senior depth is preserving a contract that external partners depend on while the implementation moves underneath, and knowing which messaging semantics change.

Docs: Unavailable technologies · CoreWCF · Azure Service Bus

You have WCF services on .NET Framework. What replaces them? mid

Answer. It depends on who calls them. If external partners consume the SOAP contract and cannot change, CoreWCF is the answer: it is the community port of the WCF server stack, now with Microsoft support behind it, and it lets you keep the WSDL, the bindings and the message contract while running on modern .NET — the lowest-risk path, and it preserves the contract exactly, which is the point. If the callers are internal and can change, replace it: gRPC for high-throughput internal service-to-service calls where the contract-first, code-generated model maps well onto what WCF was doing, or plain HTTP/JSON where the consumers are varied or browser-based. The migration order I use is: move the service to CoreWCF first so the platform is modern and the contract is untouched, then introduce the new contract alongside it and migrate consumers one at a time, then retire the SOAP endpoint when the last consumer leaves. That separates the platform move from the contract change, which is the same discipline as everywhere else in this topic.

Example

// CoreWCF: same contract, same bindings, modern .NET host
builder.Services.AddServiceModelServices().AddServiceModelMetadata();
var app = builder.Build();
app.UseServiceModel(b =>
{
    b.AddService<OrderService>()
     .AddServiceEndpoint<OrderService, IOrderService>(new BasicHttpBinding(), "/OrderService.svc");
});
// partners' generated proxies keep working; the platform underneath is .NET 10

Follow-ups

  • What does CoreWCF not support? — The exotic bindings and features (MSMQ transport specifics, some WS-* stacks, distributed transactions). Inventory your bindings before committing; the common HTTP and NetTcp cases are well covered.
  • WCF clients on modern .NET? — Supported through the System.ServiceModel.* client packages, so calling an old SOAP service from new code is not a blocker.
  • gRPC or REST for the replacement? — gRPC for internal, high-volume, strongly-contracted calls; REST/JSON for broad or browser consumers. Do not force gRPC on partners with unknown tooling.

Wrong answer: "WCF is dead, so all the services have to be rewritten as REST APIs." That forces every external consumer to change on your schedule — commercially and often contractually impossible — and it changes the contract at the same time as the platform. CoreWCF exists precisely to decouple those two moves.

MSMQ is the backbone of the integration. How do you modernize it? senior

Answer. Replace it with a managed broker — Azure Service Bus for enterprise messaging (topics, sessions, dead-lettering, scheduled delivery), or Storage Queues for simple, cheap work queues — but do it through an abstraction so producers and consumers move independently, and be explicit about the semantics that change. MSMQ gave you local, transactional, ordered delivery with a queue that lived on the machine; the replacement is remote, so you lose the local transaction with the database (replaced by the outbox pattern) and you must handle transient network failure. Ordering becomes per-session rather than global, so anything that relied on strict order needs a session key. Poison-message handling becomes explicit through max delivery count and a dead-letter queue, which is an improvement over the MSMQ habit of a message spinning forever. And message size limits are real, so large payloads move to the claim-check pattern with the body in blob storage. Migration shape: dual-publish to both transports behind an abstraction, move consumers one at a time, then drain and retire the MSMQ queues — with the drain being an explicit, verified step, since a forgotten queue with 12,000 messages in it is a classic discovery.

Example

// per-key ordering + explicit poison handling: the two semantics that change
await sender.SendMessageAsync(new ServiceBusMessage(payload)
{
    SessionId = order.CustomerId.ToString(),   // ordering guarantee is per session, not global
    MessageId = command.Id.ToString(),         // dedupe window; consumers must be idempotent anyway
});
// receiver: MaxDeliveryCount = 5 -> dead-letter queue, monitored and alerted on

Follow-ups

  • What replaces the local transaction between the queue and the database? — The outbox: write the message to the database in the same transaction, then relay it. That is the standard answer and it is what this question is really probing.
  • How do you handle the migration cutover? — Dual-publish, migrate consumers, then stop publishing to MSMQ and verify the queues drain to zero before decommissioning.
  • What about ordering-dependent processes? — Session-based consumption with a partition key, or redesign so ordering does not matter — usually the more durable fix.

Wrong answer: "We'd swap MSMQ for Service Bus — it's the same queueing model with a different client library." Transactional local delivery, global ordering and poison handling all differ, and code written against MSMQ's guarantees breaks subtly rather than loudly. Name the outbox, per-session ordering and dead-lettering, or this answer sounds unlived.

Integration is FTP file drops, flat files and a BizTalk-era orchestration. Where do you start? senior

Answer. With an inventory and the partners, because the constraint is external. For each interface: who sends it, what format, what schedule, what happens when it is late or malformed, and who notices. Then modernize the plumbing before the contract: keep the file-based interface the partner knows, and move the transport and processing to managed services — SFTP into Blob Storage with an event-driven trigger, Azure Data Factory or Logic Apps for scheduled movement and mapping, and a .NET worker for the business processing. That gives you retries, dead-lettering, observability and an audit trail without asking any partner to change anything. The orchestration itself is the harder half: BizTalk-style pipelines encode years of routing and transformation rules, so I would replatform them a flow at a time — Logic Apps where the flow is genuinely integration-shaped, explicit code plus a durable orchestration where the logic is real business logic that deserves tests. Only then would I approach the willing partners about a modern API. And I would add idempotency and duplicate detection early, because file-based integration's characteristic failure is the same file processed twice.

Example

Partner (unchanged)  SFTP drop -> landing container
                     |
Event Grid trigger -> validate (schema + checksum) -> quarantine on failure, alert with the file
                     -> idempotency check (hash + business key) -> skip duplicates
                     -> transform -> enqueue business commands -> process with retries
                     -> archive the original for the retention period (audit)

Follow-ups

  • What is the most common defect in file integrations? — Duplicate processing, followed by silent partial failure — the file half-processed with no alert. Idempotency and per-file completion tracking fix both.
  • Logic Apps or code? — Logic Apps for connector-heavy movement and mapping; code for anything with real business rules that deserves unit tests and a review history.
  • How do you handle a partner who cannot change? — You keep their interface indefinitely. Modernize your side of it and stop treating their constraint as a blocker.

Wrong answer: "We'd replace the file interfaces with REST APIs and ask partners to integrate against them." Partner change is the one thing you do not control: their schedules, budgets and contracts decide it, and some will never move. Modernize your side under a stable contract, then negotiate the contract separately with those who are willing.

A partner depends on an exact SOAP contract you must not break. How do you migrate under it? senior

Answer. Freeze the contract and treat it as an external API with a compatibility test suite. Practically: capture the current WSDL and a corpus of real request/response pairs, build a replay harness that asserts byte-level-equivalent responses (modulo genuinely volatile fields), then move the implementation underneath — CoreWCF on modern .NET, or a facade that speaks SOAP and delegates to a new internal service. The facade approach is usually right when the new internal design differs, because it concentrates all the contract fidelity in one small, well-tested component. Details that bite: namespace and prefix changes in generated XML, element ordering, nil versus absent elements, date-time formats and time zone offsets, and fault contract shapes — all invisible to a functional test and all capable of breaking a partner's generated proxy. So the replay corpus is not optional; it is the specification. And I would tell the partner what is happening with a test window, even though the contract is unchanged, because goodwill costs nothing and their test run is a free extra verification.

Example

[Theory, MemberData(nameof(CapturedRequests))]   // 3,200 real partner requests, anonymized
public async Task Soap_response_is_byte_equivalent(string requestXml, string expectedXml)
{
    var actual = await _client.PostSoapAsync(requestXml);
    Assert.Equal(Normalize(expectedXml), Normalize(actual));   // normalize only timestamps + ids
}

Follow-ups

  • What if the new implementation cannot reproduce a quirk? — Fix it in the facade's serialization layer, not in the domain. Quirk preservation belongs at the boundary, where it can be deleted when the contract is finally retired.
  • How do you eventually change the contract? — Version it, run both, migrate consumers with a deprecation window, and retire the old one on a date the partners agreed.
  • Is byte-equivalence too strict? — For generated SOAP proxies it is the safe default; relax it deliberately per field once you know the consumer tolerates it.

Wrong answer: "As long as the schema is the same, the responses will be compatible." Generated clients are notoriously sensitive to namespace prefixes, element ordering, empty-versus-absent elements and date formats — none of which the schema pins down. Schema equality is necessary and nowhere near sufficient.

19Desktop & other legacy clients

The smallest sub-area, and only asked when the estate has one — but when it does, it is often the hardest part of the programme, because the client is installed on machines you do not control and it frequently talks straight to the database. Depth expected is modest: know the supported paths, know why a thick client with a database connection is an architectural problem before it is a migration problem, and know when the answer is "rebuild as a web application".

Docs: Migrate WinForms apps to .NET · Migrate WPF apps to .NET · Upgrade Assistant

WinForms and WPF on .NET Framework — what is the migration? mid

Answer. Both are supported on modern .NET (Windows only), so this is a real port rather than a rewrite: retarget to net10.0-windows with UseWindowsForms or UseWPF, convert the project to SDK style, and let the Upgrade Assistant do the mechanical work. What actually consumes the time is the surrounding estate: third-party UI control suites that need a modern-.NET licence or have no port, COM interop and ActiveX controls, custom designers, ClickOnce or MSI deployment, and app.config-based configuration. Deployment deserves specific thought — self-contained deployment removes the machine-wide runtime dependency, which is often the reason these applications were stuck, at the cost of a much larger installer. My usual sequencing is: port the shared libraries first (they are frequently the same libraries the server side uses), then the client, then modernize the client's data access if it is talking straight to the database. And I would ask the strategic question out loud: is this application worth porting at all, or is it a candidate for a web rebuild — because desktop deployment is often the real pain and the port does not fix it.

Example

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net10.0-windows</TargetFramework>
    <UseWindowsForms>true</UseWindowsForms>
    <SelfContained>true</SelfContained>      <!-- no machine-wide runtime dependency -->
    <PublishSingleFile>true</PublishSingleFile>
  </PropertyGroup>
</Project>

Follow-ups

  • What about a third-party control suite with no modern version? — Replace it, buy the current version, or keep that screen on .NET Framework behind a launcher. Inventory the controls before estimating anything.
  • Is self-contained always right? — It trades installer size and patching responsibility for independence from machine state. For a fleet you do not control, usually yes.
  • WinUI/MAUI instead? — Only if you want a UI rewrite; the WinForms/WPF port keeps the UI code, which is the whole point of it being cheap.

Wrong answer: "Desktop technologies aren't supported on modern .NET, so it has to be rebuilt as a web app." Both WinForms and WPF run on modern .NET on Windows, and a port is typically weeks where a rebuild is quarters. Recommending a rewrite because you did not know the port exists is an expensive error.

The desktop client connects directly to the database. How do you modernize that? senior

Answer. The direct connection is the architectural problem: every installed client is a database user, business rules live on machines you do not control, upgrades require a coordinated rollout, and the database must be reachable from wherever the client runs — which usually means a VPN and a broad firewall exposure. The move is to introduce an API tier and migrate the client onto it capability by capability. Because there is no request boundary to intercept, this is branch by abstraction rather than strangler fig: introduce a data-access abstraction in the client, implement it first over the existing SQL calls, then over HTTP, and switch per capability with a client-side flag. Two hard constraints shape the plan: client versions in the wild, so the API must support the old and new client simultaneously and be versioned properly; and update mechanics, so ClickOnce/auto-update should be working before you start, or you cannot ship the client changes the migration needs. The order I use is reads first (safe, immediately reduces the connection's privileges), then writes, then revoke direct database access entirely — which is the moment the benefit lands.

Example

// branch by abstraction in the client: same interface, two implementations, per-capability switch
public interface IOrderGateway { Task<Order> GetAsync(int id); Task SaveAsync(Order o); }

sealed class SqlOrderGateway  : IOrderGateway { /* existing direct ADO.NET */ }
sealed class HttpOrderGateway : IOrderGateway { /* new API                 */ }

services.AddSingleton<IOrderGateway>(sp =>
    sp.GetRequiredService<IClientFlags>().UseApiForOrders
        ? sp.GetRequiredService<HttpOrderGateway>()
        : sp.GetRequiredService<SqlOrderGateway>());

Follow-ups

  • How do you handle clients that never update? — A minimum supported version enforced by the API with a clear message, plus telemetry on version distribution. Without an enforcement point you will support every version forever.
  • What about the business logic that lives in the client? — It moves to the server with the capability; do not port it to the API and leave a copy behind, or they diverge within a release.
  • Does this let you remove the VPN? — Eventually, and that is often the business benefit that funds the work: a client that talks HTTPS to an API can work anywhere.

Wrong answer: "We'd build the API and switch the client over in one release." A single release means every installed client must update simultaneously — which you cannot enforce on machines you do not control — and you have no per-capability rollback. Per-capability switching with version negotiation is what makes this survivable.

Silverlight, ActiveX, VB6, an Access front end. What are the options? senior

Answer. These are dead-platform cases: Silverlight's browser support ended years ago, ActiveX requires a browser nobody ships, VB6 tooling is long unsupported, and an Access front end over a shared database is a data-integrity incident waiting for a concurrent user. There is no port, so the options are rebuild, repurchase or retire — and the first question is which, decided on usage and value rather than on sentiment. Where a rebuild is chosen, the risk is that the requirements exist only in the artefact, so I treat the old application as the specification: record the workflows on video with the actual users, capture the data model, and rebuild capability by capability with per-user cutover, keeping the old one available in a controlled environment for reference. For the interim, isolation is the containment strategy — a locked-down VM or a published application for the handful of users who still need it, on a network segment that limits the damage. And I would set a hard shutdown date, because these systems only end when someone puts a date on them.

Example

Access front end over the shared database
  now      isolate: read-only where possible; revoke write access from the Access user;
           log every query; identify the actual users (usually 3, not 30)
  next     rebuild the 2-3 workflows that matter as web pages, per-user cutover
  then     shutdown date announced, enforced; the .accdb is archived, not maintained
  never    "modernize" it in place - there is no supported path and no test net

Follow-ups

  • How do you capture requirements that exist nowhere? — Record real users doing real work, and instrument the database to see which operations actually occur. Both beat interviews, which produce the idealised process rather than the real one.
  • What if a handful of users refuse to move? — Escalate as a business decision with the risk stated, and set the shutdown date anyway. Indefinite support of a dead platform is a decision someone is making by default.
  • Is a rebuild always the answer? — No: for these, repurchase or retire is very often cheaper, and the usage data usually supports it.

Wrong answer: "We'd find a migration tool that converts VB6/Silverlight to a modern equivalent." Such tools exist and typically produce unmaintainable generated code that preserves every original design decision — you get a modern-syntax version of a dead architecture with no test net. For dead platforms, rebuild the capability from observed behaviour, or retire it.

20Judgment calls

Open-ended questions with no single right answer, used at lead and principal level to see how you reason rather than what you know. The hidden part of each block says what a strong answer demonstrates and which trade-offs you are expected to name without being asked. The pattern that scores: state the decision, name the two or three factors that would flip it, say what you would measure to find out, and be willing to recommend not doing the work.

A 12-year-old system has a core module nobody can safely change. Rewrite the module, or keep patching? principal

What a strong answer demonstrates. That you separate the module from the system: a scoped rewrite of one component behind a stable interface is a very different proposition from rewriting the application, and the strong answer reaches for that distinction immediately. It sizes the module (can one team rebuild and validate it in a quarter?), asks whether the behaviour is knowable (is there traffic to parallel-run against, or is it a batch process that runs twice a year?), and insists on a facade so the rewrite is switchable per cohort. It also questions the premise — "nobody can safely change it" usually means "there are no tests and one person understands it", both of which are addressable for far less than a rewrite, and the strongest answers try that first and use the result as evidence.

Trade-offs to name unprompted

  • Knowledge loss versus code quality — the odd branches encode paid-for edge cases; a rewrite discards them unless you parallel-run.
  • Scoped rewrite versus creeping scope — the interface is what stops it spreading; without a hard boundary this becomes the system rewrite you rejected.
  • Opportunity cost — a quarter on this module is a quarter not spent on the forced dates or the roadmap.
  • Verification cost — if the module has no live traffic to compare against, the rewrite's risk goes up sharply and that should change the answer.
  • Who maintains it after — a rewrite by a contractor or a single enthusiast recreates the original problem in a newer language.
Move to Azure first, or modernize the code first? senior

What a strong answer demonstrates. That the order follows the binding constraint, not a preference. If the forcing function is infrastructure — a data centre contract ending, an unsupported OS, hardware failing — move first, accept a lift-and-shift, and take the free Extended Security Updates that come with running out-of-support Windows/SQL Server in Azure. If the forcing function is delivery speed or a runtime end-of-support date, modernize the code first, because a lifted legacy application on cloud infrastructure is more expensive and no easier to change. The strong answer also notes that the two interleave: code changes that make the application cloud-viable (externalize session, remove local disk assumptions, configuration and logging) are worth doing regardless and are cheap, so they come first in either ordering.

Trade-offs to name unprompted

  • Lift-and-shift cost — you pay retail for idle capacity and gain no agility; justified as risk reduction with a dated follow-on, not as a destination.
  • Doing both at once — no attribution when something regresses; almost always the wrong choice.
  • Team capability — a team with no cloud experience learning it while also porting a runtime is two learning curves at once.
  • Licensing and ESU — a genuine, quantifiable reason to move infrastructure first for an out-of-support estate.
  • Reversibility — an infrastructure move is usually reversible; a code migration less so. Sequence the reversible one first when uncertain.
You find a bug during a migration. Do you fix it or reproduce it faithfully? senior

What a strong answer demonstrates. The default is reproduce, and the reason is attribution: if the new system behaves differently, you cannot tell a regression from an intended change, and your parallel-run comparison fills with noise. So the sequence is preserve, ship the migration, then fix as a separate visible change. But the strong answer names the exceptions cleanly: a security vulnerability is fixed immediately regardless; a bug actively corrupting data is fixed immediately with the business informed; and a bug someone is deliberately relying on is not a bug — it is an undocumented feature, and changing it is a business decision. It also mentions telling the business what you found, because "we knew and shipped it anyway" is much worse than the bug when it surfaces later.

Trade-offs to name unprompted

  • Attribution versus doing the right thing now — the whole argument for preserving behaviour is diagnostic clarity during the cutover.
  • Users depending on the bug — workarounds get built on wrong behaviour; changing it silently breaks a process nobody documented.
  • Regulatory exposure — a miscalculation may need disclosure and correction of historical records, which is not an engineering decision.
  • Test suite honesty — a characterization test that encodes a bug should say so in its name, or someone will "fix" the test later.
The runtime deadline is nine weeks away and the team cannot make it. What do you do? senior

What a strong answer demonstrates. Triage rather than heroics. Split the estate by exposure — internet-facing and data-handling components first, internal and isolated ones later — and get the exposed set onto the supported runtime even if that means the minimum viable retarget with no other improvements. For the remainder, buy time deliberately and visibly: compensating controls (network isolation, WAF, restricted access), a documented risk acceptance with an owner and a date, and where the platform offers it, a paid extension. The strong answer is explicit that being unsupported is a risk to be managed with evidence, not a binary catastrophe, and equally explicit that "we'll get to it" without a date is not management. It also asks the uncomfortable question: why was this discovered in September when the date has been known for two years, and what changes so the next one is not?

Trade-offs to name unprompted

  • Minimum retarget versus doing it properly — a bare retarget leaves the improvements undone but removes the support cliff; that is a legitimate trade under a hard date.
  • Risk acceptance needs a name and a date — otherwise it is avoidance with paperwork.
  • Cost of extension versus cost of rushing — a rushed migration causing an outage can cost more than the ESU.
  • Team sustainability — a nine-week crunch has a cost you pay in Q1 attrition.
  • Process failure — the real finding is the absence of a support-calendar review, and fixing that is worth more than this deadline.
The business will fund modernization only if it comes with new features. Do you accept? principal

What a strong answer demonstrates. Pragmatism with a boundary. Bundling is often good: a feature delivered on the new path is the best possible proof of value, and "you touch it, you move it" turns modernization into a tax on change rather than a separate budget that can be cut. So the answer is usually yes — with conditions: the forced-date work is funded separately because it cannot be hostage to a feature's fate; the migration part of each item is estimated honestly rather than hidden inside the feature estimate (hiding it is how you end up unable to explain a slipped date); and the technical approach is not compromised to fit the feature's schedule. The strong answer also names the failure mode: if every migration must be justified by a feature, the components nobody is building features on — usually the riskiest — never get touched.

Trade-offs to name unprompted

  • Visible value versus honest estimates — bundling buys funding and blurs accounting; keep the split visible in the estimate.
  • Coverage gaps — feature-driven modernization follows the roadmap, not the risk; the untouched components need their own funding line.
  • Schedule pressure on migration quality — a cutover rushed to hit a feature launch is where the safety net gets skipped.
  • Sponsor trust — hidden migration cost inside feature estimates is discovered eventually and reads as dishonesty.
Business logic lives in 400 stored procedures the DBA owns. Move it to code, or leave it? senior

What a strong answer demonstrates. That the decision is per-procedure and driven by change rate and testability, not by an ideology about where logic belongs. Procedures that are set-based data operations — bulk updates, reporting aggregations, anything moving a lot of rows — belong in SQL, and moving them to C# usually makes them slower and no clearer. Procedures encoding branching business rules that change with the business, especially those nobody can test, are the ones to move. The strong answer also addresses the organisational half: the DBA's ownership exists for reasons (production stability, performance, a review gate), and the modern answer keeps the review while putting the procedures in source control, in the same pipeline, with tests — which is usually a bigger win than relocating the logic. And it starts with the procedures the migration actually touches, not with a 400-item project.

Trade-offs to name unprompted

  • Performance versus testability — set-based work in the database is often orders of magnitude faster; moving it for purity is a real cost.
  • Deployment coupling — logic in the database means schema and code releases are coupled, which conflicts with expand/contract.
  • Skills and ownership — moving logic to C# moves the on-call and the expertise; make sure the receiving team wants it.
  • Vendor lock-in — T-SQL logic is the largest obstacle to any future database change, which matters if that is on the roadmap.
  • Incrementality — do it with the migration that touches each procedure, never as a standalone 400-item programme.
When is "wrap it and leave it" the right answer for a component you know is bad? senior

What a strong answer demonstrates. Willingness to leave something ugly alone, with conditions. Wrapping is right when the component works, is not changing, and is not a security or support risk — but is blocking the modernization of things around it. You put a clean contract in front of it, isolate it (its own process or host, restricted permissions, monitored), and treat it as an external dependency with a dated review. The strong answer names what makes wrapping legitimate rather than lazy: the wrapper is genuinely narrow, the component's blast radius is contained, and there is a written decision with an owner and a date rather than a silent decision to ignore it. It also names when wrapping is wrong: when the component is where the change actually needs to happen, when it is unsupported and exposed, or when the wrapper would be as complex as a rewrite.

Trade-offs to name unprompted

  • Isolation cost versus rewrite cost — an extra deployable and an extra on-call surface against a quarter of engineering time.
  • The wrapper becoming permanent — nearly always does; budget for that rather than pretending it is temporary.
  • Hidden coupling — if the component shares a database with the rest, wrapping it is cosmetic.
  • Security posture — an unsupported wrapped component still needs network isolation and monitoring; wrapping is not a control.
How much of a team's capacity should go to modernization and maintenance — permanently? principal

What a strong answer demonstrates. That this is a steady-state question, not a project one. A common answer is 15–25% permanently for dependency updates, runtime upgrades, refactoring alongside features and paying down the debt created by delivery — with the number varying by system age, regulatory load and how much of the estate is on a supported cadence. The strong answer resists both extremes: zero produces the estate you were hired to fix, and 50% suggests something structurally wrong that should be addressed as a project rather than as a permanent tax. It also argues for the mechanism rather than the number — upgrades happening by default and requiring justification to skip, framework moves scheduled against the support calendar, and "leave it better" as part of feature work — because a percentage without a mechanism is a wish.

Trade-offs to name unprompted

  • Fixed allocation versus opportunistic — fixed is easier to defend and can become box-ticking; opportunistic is efficient and gets squeezed to zero under pressure.
  • System age and criticality — a regulated 15-year-old system needs a bigger share than a two-year-old service.
  • Who decides — if the product owner controls it, it goes to zero in a crunch; a standing agreement with the sponsor survives.
  • Measurement — without lead time and change failure rate, you cannot tell whether the allocation is working or just being spent.
Would you ever recommend stopping a modernization programme? principal

What a strong answer demonstrates. That you can recommend against your own work. Legitimate stop conditions: the driver disappeared (the business line is closing, a package purchase replaces the capability, the regulation changed); the remaining cost exceeds the remaining risk being removed; the organisation cannot sustain it and half-finished coexistence is worse than either end state; or repeated evidence that the chosen approach cannot work and no better one is fundable. The strong answer distinguishes stopping from pausing, and insists that stopping is an active piece of work — consolidate on one path, delete or finish the half-migrated components, document the accepted risks with owners — because an abandoned migration left mid-flight is the worst of all outcomes. It also acknowledges the personal dimension honestly: recommending a stop is career-risky and is exactly why it is a principal-level signal.

Trade-offs to name unprompted

  • Sunk cost — the spend is gone either way; only the next increment's value is decidable.
  • Stopping is not free — consolidation, deletion and documented risk acceptance all cost real time.
  • Residual risk — the unsupported runtime does not go away because the programme did; someone must own it explicitly.
  • Team morale and credibility — how the stop is communicated determines whether the next initiative is trusted.
Two teams disagree: one wants .NET 10 everywhere now, the other wants to stay put and ship features. You decide. principal

What a strong answer demonstrates. That you resolve it with facts and a partial commitment rather than by picking a side. The facts that decide it: which components are on runtimes with a support date (.NET 8 and 9 expire on 2026-11-10, which converts that portion from preference to obligation), which are exposed, and what the feature roadmap genuinely requires in the same window. The likely outcome is both: dated commitments for the components with a support cliff, continued feature delivery elsewhere, and a standing allocation so the rest moves without a separate negotiation each time. The strong answer also handles the human half — both teams have a legitimate point, and framing it as "obligation versus preference" lets both keep face — and it sets a review date so the decision is revisited with evidence rather than re-argued weekly.

Trade-offs to name unprompted

  • Obligation versus preference — support dates are not negotiable; "everywhere now" is.
  • Uniformity versus pace — a mixed-version estate is more complex to support but lets you sequence by risk.
  • Cost of deferral — the longer the gap, the bigger the eventual jump and the less bisectable any regression.
  • Credibility — a decision without a review date will simply be re-litigated; put the date in writing.

21Design exercises

Modernization connects to system design constantly, and at lead/principal level these appear as whiteboard rounds. Each exercise gives the prompt and the clarifying questions you should ask before designing — the clarifying questions are scored — with the solution outline collapsed so you can attempt it first. Budget roughly 5 minutes on clarifications, 25 on design, 5 on trade-offs and what you would do first.

Exercise 1 — Retail platform: on-premises ASP.NET 4.8 + SQL Server 2016 to Azure, no downtime

Prompt. A retailer runs an ASP.NET MVC 5 application on .NET Framework 4.8 across four IIS servers on-premises, against a 1.8 TB SQL Server 2016 database that left extended support in July. There is a Windows service running nightly batch, an MSMQ-based order pipeline, and a jQuery front end. Peak trading is November–December, when downtime is unacceptable. The roadmap has two funded initiatives this year. Design the modernization.

Clarifying questions to ask. What is forcing this — the SQL Server support date, a data centre contract, delivery speed, or an incident? What is the actual peak load, and what is the current utilisation? What is the deployment process and frequency today, and is there any test coverage? What integrations exist with third parties, and can any of them change? Who owns the database schema, and are there stored procedures with business logic? What is the required RTO/RPO, and what does "no downtime" mean precisely — including for order placement specifically? What is the team's cloud and modern .NET experience? Is there a code freeze during peak trading, and when does it start?

Strong solution outline and expected trade-offs principal

Outline. Sequence around two hard dates: SQL Server 2016 is already out of support, and the trading peak forbids risky change from roughly late October. So: Phase 0 (weeks 1–4) — reproducible build, automated deploy to a lower environment, telemetry on the legacy app (edge logs plus Application Insights for .NET Framework), characterization tests over checkout and pricing, and a usage inventory of endpoints, procedures and MSMQ queues. Phase 1 (weeks 4–12) — database first, because it carries the support risk: assess with the Azure migration tooling, size Azure SQL Managed Instance (Business Critical if IO-sensitive), establish the MI link for continuous replication, rehearse the failover three times, and cut over with a short write-freeze implemented in the application. Keep the application on-premises briefly only if the link latency is acceptable; otherwise move the web tier in the same window. Phase 2 (weeks 8–20, overlapping) — web tier to App Service on Windows as a replatform: externalize session to Redis, fix machine keys, remove local-disk assumptions, move configuration to App Service/Key Vault with managed identity, and put the batch service into Container Apps jobs or WebJobs. This is deliberately not a .NET 10 port yet. Phase 3 (from week 16) — stand up an ASP.NET Core host on .NET 10 with System.Web Adapters and YARP in front, and start moving routes: read-only pages first, then forms, then checkout last. MSMQ moves to Service Bus behind an abstraction with dual publishing, and the outbox pattern replaces the local transactional enqueue. Front end gets a shared design-system shell and island-by-island replacement, with TypeScript adopted incrementally (allowJs, ratchet). Freeze from late October to early January: no cutovers, monitoring only, with the two roadmap initiatives delivered on whichever path is live at the time. Phase 4 (January onward) — remaining routes, then delete legacy paths, shut down the IIS servers on dated commitments, and remove the adapters. Everything runs behind flags with per-cohort ramps and rehearsed rollback; every slice ends with the old path deleted.

Trade-offs you are expected to name unprompted

  • Database first versus application first — the database carries the support risk and the longest lead time, but moving it while the app is on-premises adds link latency; if that is unacceptable, both move in one window, which raises cutover risk. Name the choice and the measurement that decides it.
  • Replatform before port — App Service on Windows buys a managed platform in weeks without a runtime port; the cost is an interim state and a second migration of the same component.
  • Managed Instance versus Azure SQL Database — MI for instance-level features (Agent jobs, cross-database queries) with a higher floor cost; Azure SQL Database only if you are willing to re-home those dependencies now.
  • Peak freeze — the freeze is non-negotiable and compresses the calendar; it also means anything not done by late October waits until January, which must be in the plan rather than discovered.
  • Coexistence cost — YARP, dual hosting, remote app session and two deployment paths for several months; budget it and delete it deliberately.
  • MSMQ semantics — losing local transactional enqueue means the outbox pattern and idempotent consumers; ordering becomes per-session.
  • Team capability — if cloud experience is thin, the replatform is also the training exercise; plan for a slower first phase rather than pretending otherwise.

What I would do in week one

Get the build reproducible and the telemetry on. Everything else is opinion until you can see the traffic and deploy on demand.

Exercise 2 — Extract billing from a shared database with zero downtime

Prompt. A monolith's billing capability shares a 900 GB SQL Server database with everything else: 40 tables, of which 12 are written by billing and 8 are written by both billing and ordering. Invoicing runs nightly and must be exactly correct; the finance team reconciles daily. Billing needs its own release cadence because a new tax regime lands in six months. Design the extraction.

Clarifying questions to ask. Which tables are genuinely written by two areas, and can one writer be eliminated? What is the transactional boundary today — does a single transaction span billing and ordering tables? What reads cross the boundary, including reports and ETL? What is the finance reconciliation exactly, and can it be automated as a comparison? What are the retention and audit requirements for invoices? Is there an outbox or event mechanism already? Who owns the nightly job and what happens when it fails today? What is the deadline for the tax regime, and is it hard?

Strong solution outline and expected trade-offs principal

Outline. Stage 1 — encapsulate (no data movement). Route every read and write of the 12 billing-owned tables through a billing module with an explicit contract; enforce with schema separation and database permissions, so ordering physically cannot write them. For the 8 shared tables, decide a single writer per table: usually ordering owns the order-side data and billing consumes it, with billing's writes replaced by a command on the ordering API or an event. This stage delivers value alone — clear ownership, testable boundary — and is reversible. Stage 2 — decouple reads. Billing needs order data; replicate what it needs into a billing-owned read model, fed by events (outbox from ordering) or CDC, rather than joining. Reconcile the read model continuously against the source. Stage 3 — replicate. Stand up the billing database, seed it, keep it current with CDC, and run continuous verification: row counts, checksums, and the finance totals themselves computed on both sides nightly and compared automatically — that automated comparison is the deliverable that makes the cutover decidable. Stage 4 — read cutover. Flag-controlled, ramped, with the nightly invoicing job run in shadow mode against the new store and its output diffed against production invoices for at least one full monthly cycle including month-end. Stage 5 — write cutover. Per-entity brief write pause (queue at the API, drain CDC, swap authority), then reverse replication maintained for a defined rollback window. Stage 6 — contract. Stop the sync, drop the old tables, remove the last cross-boundary joins and the reporting queries that used them. The tax-regime work then happens in the extracted service on its own cadence, which was the point.

Trade-offs you are expected to name unprompted

  • Loss of transactional consistency — a single transaction across ordering and billing becomes a saga with compensations; invoices must be idempotent and the "in progress" state must be visible to finance.
  • Eventual consistency versus finance's expectations — a reconciliation that runs while data is in flight will show differences; agree the reconciliation point (end-of-day boundary) with finance before cutting over.
  • CDC versus dual write — CDC has one authority and ordered propagation; dual write has neither, and this is the decision most likely to be probed.
  • Read model staleness — billing acting on stale order data has real consequences; define the acceptable lag and alert on it.
  • Reporting and ETL — the cross-boundary joins that exist today have to go somewhere: a warehouse or a replicated read model, not a live join.
  • The six-month deadline — if the extraction cannot be safely complete by then, do the tax work in the monolith behind the module boundary and extract afterwards. Say this out loud: forcing an extraction to meet a regulatory date is how you get both late.
  • Audit and retention — invoices are regulated records; the migration must preserve immutability and history, and deleting the old tables may not be permitted for years.

Exercise 3 — Multi-tenant SaaS: full-stack modernization with 5,000 tenants

Prompt. A B2B SaaS product serves 5,000 tenants from a single ASP.NET Web Forms application with a jQuery front end, on .NET Framework 4.8, backed by one large SQL Server database with a TenantId column on most tables. Tenants range from 2 to 4,000 users. Some enterprise tenants require SSO and have contractual uptime commitments. The company wants a modern API, a modern front end, and the ability to onboard tenants faster. Design the modernization.

Clarifying questions to ask. What is the tenant size distribution and the load profile — a few huge tenants or a long tail? What are the contractual uptime and change-notification obligations for the enterprise tenants? Is there per-tenant customization (custom fields, custom pages, custom code) — this changes everything? What does onboarding involve today and where is the actual bottleneck? Do tenants have their own identity providers already? What is the data residency situation? Is there an existing API, and who consumes it? What is the release cadence and is it per-tenant or global? What happens today when one tenant runs an expensive report?

Strong solution outline and expected trade-offs principal

Outline. The multi-tenancy is the lever: it gives a natural cutover cohort, so every change ramps tenant by tenant, starting with internal test tenants and friendly small ones and finishing with the contractual enterprises. Foundation. Reproducible build, per-tenant telemetry (every metric and log tagged with tenant), a shared design-system shell consumable by both Web Forms and the new front end, and an ASP.NET Core host on .NET 10 with YARP and System.Web Adapters in front of the existing application. Identity moves first for the enterprise tenants who want SSO: OIDC against their identity providers, with the local credential store retired per tenant — this is both a modernization step and a sellable feature, which is how it gets funded. API-first. Build the modern API as the new path for each capability, with the Web Forms pages calling it before they are replaced, so the API is proven by the legacy UI before any front-end work depends on it. Front end. Islands inside the Web Forms pages first (grids, editors), then whole routes on the new stack, with TypeScript adopted incrementally and a per-tenant flag for the new experience so enterprise tenants can opt in on their own schedule — a contractual necessity as much as a technical one. Data. Keep the shared database with TenantId, but enforce isolation properly: query filters plus row-level security so an unscoped query cannot leak, and per-tenant quotas and a separate read replica for reporting to stop noisy-neighbour effects. Introduce a tenant-tier concept: the long tail stays on the shared database, and the largest tenants become candidates for a dedicated database later — designed for, not built yet. Onboarding. Automate provisioning (schema seeding, configuration, identity setup) as code; the bottleneck is usually manual steps, and fixing it is early, cheap, visible value. Endgame. Delete legacy pages as they are replaced, decommission the Web Forms host on a dated commitment, and remove the adapters.

Trade-offs you are expected to name unprompted

  • Per-tenant cutover versus operational complexity — the safest possible ramp, at the cost of running many combinations of old and new simultaneously; cap the number of live combinations deliberately.
  • Shared database versus per-tenant isolation — 5,000 databases is an operations problem, one database is a blast-radius and noisy-neighbour problem; tiering is the compromise and the migration path between tiers must exist.
  • Contractual obligations — enterprise tenants may require notice, test windows or explicit approval for changes; that constrains the ramp order and must be in the plan, not discovered.
  • Per-tenant customization — if tenants have custom pages or code, the migration is many small migrations; this is the question whose answer most changes the estimate, which is why it is a clarifying question.
  • Two front ends — a per-tenant new experience means supporting both for a long time; the shared design system is what keeps it from looking like two products.
  • Identity migration risk — a botched identity cutover locks out an entire tenant; per-tenant, with a fallback path and a rehearsal, and never on a Friday.
  • Row-level security cost — enforcement at the database is the strongest isolation control and has a performance and complexity cost; measure it rather than assuming either way.

22Night-before cheat sheet

The ten questions most likely to appear in any modernization loop, with a one-sentence answer each. If you can say these cleanly and then go one level deeper on each, you are prepared for the majority of the conversation.

  1. Rewrite or incremental? — Incremental by default: a rewrite freezes the old system while the business keeps moving, defers all value to a single untested cutover, and discards the edge cases the legacy code encodes; rewrite only when the scope is a quarter, the platform is dead, or the requirements themselves changed.
  2. What is the strangler fig pattern? — Put a facade (YARP, gateway) in front of the legacy system, migrate one slice at a time behind it with per-route, per-tenant or per-percentage routing, and delete the old path as part of each slice's definition of done.
  3. What target framework, and why? — .NET 10 LTS (shipped 2025-11-11, supported to November 2028), because .NET 8 and .NET 9 both reach end of support on 2026-11-10 — migrating onto .NET 8 today buys a second upgrade project before the first has settled.
  4. How do you migrate ASP.NET to ASP.NET Core incrementally? — A new ASP.NET Core host with YARP proxying everything to the .NET Framework app, plus Microsoft.AspNetCore.SystemWebAdapters (including remote app authentication and session) so routes move one at a time with the site live throughout.
  5. How do you change a schema with no downtime? — Expand/contract: add the new shape, deploy code that writes both, backfill in throttled batches, switch reads, bake, then drop the old shape — so any deployed code version works with any deployed schema version and a code rollback never needs a database rollback.
  6. How do you know the new implementation is correct? — Characterization tests to lock current behaviour plus a parallel run on live traffic where only the legacy result is returned and a comparator triages every class of divergence before the ramp starts.
  7. What replaces a distributed transaction after you split a service? — The transactional outbox (state and message committed together, relayed afterwards) with idempotent consumers, and a saga with compensating actions across services; MSDTC-style two-phase commit is not available and not the answer.
  8. What makes a cutover reversible? — A config-switchable flag (not a deploy), the legacy path still running and still correct, data written by the new path readable or reconcilable by the old one, and a rollback that has been rehearsed and timed.
  9. What is the deadline nobody should miss right now? — 2026-11-10: .NET 8 and .NET 9 end of support, the Azure Functions in-process .NET model retires, and .NET 11 RTMs — with SQL Server 2016 already out of support since 2026-07-14 and Windows Server 2016 ending 2027-01-12.
  10. How do you justify modernization to the business? — Three numbers and a date: the externally-set support deadline, the engineering capacity currently lost to toil, and the roadmap items that are expensive or impossible today — presented as cancellable quarterly bets, with progress reported as endpoints migrated and cost of coexistence rather than percentage complete.
