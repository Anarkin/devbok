01 The failure model

Docs: Retry pattern · SRE Book: cascading failures

Everything in this guide is a consequence of a single fact: in a distributed system a request has three outcomes, not two. It succeeded, it failed, or — the one that generates every hard bug you will ever debug — you do not know. The response may have been lost on the way back. The server may have committed and then crashed before replying. The packet may still be sitting in a switch buffer and will arrive in forty seconds. A local method call has two outcomes; a remote call has three, and the third is not rare, it is the normal case under load.

The classic framing is the eight fallacies of distributed computing (Deutsch and Gosling, Sun, 1994–97): the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology doesn't change, there is one administrator, transport cost is zero, the network is homogeneous. Quoting them is table stakes. What a lead is actually asked is the operational version — which fallacy is this outage? A retry storm is "latency is zero" plus "bandwidth is infinite". A cross-region call that works in staging and melts in production is "topology doesn't change". A service that goes down because its dependency's TLS certificate expired is "the network is secure" wearing a different hat.

The running example: charge the card, ship the order

Keep one picture for the whole guide. An OrderService receives "place order", calls PaymentService to charge a card, writes an Order row, and emits an OrderPlaced event that ShippingService and EmailService consume. Every concept below appears in that one flow: the payment call has the unknown outcome (did we charge them twice?), the row write and the event publish are a dual write (unit 09), the two consumers need different delivery guarantees (unit 07), and refunding a charge when shipping fails is a saga (unit 10). If you can narrate that flow end to end with its failure modes, you can derive most distributed-systems answers without having rehearsed them.

Timeouts are your only failure detector

In an asynchronous network — no upper bound on message delay, no bound on process pause — it is provably impossible to distinguish a crashed node from a slow one. That is the practical content of the FLP impossibility result and of every "is it down or is it slow?" argument in an incident channel. So you pick a timeout, and the timeout is your definition of failure. Too low and you declare healthy nodes dead, retry, and add load to a system that was merely slow — the classic self-inflicted outage. Too high and a dead dependency holds your threads hostage until you run out of them.

Two rules separate seniors from leads here. First, every timeout must be shorter than the timeout of the caller above it, or the caller gives up while you are still working and your work is wasted; propagate a deadline (an absolute instant) rather than a per-hop duration, so each hop spends the remaining budget instead of restarting the clock. gRPC does this natively with the grpc-timeout header; over plain HTTP you carry it yourself. Second, a pause is not always the network: a stop-the-world GC, hypervisor steal, a container throttled by its CPU quota, or an fsync stalled behind a disk flush all look exactly like a partition from outside. A process paused for 12 seconds by a full GC has been, for those 12 seconds, a partitioned node that still believes it holds the lock.

// The three outcomes, made explicit. Anything that hides them is lying to you.
public enum CallResult { Committed, DefinitelyNotCommitted, Unknown }

async Task<CallResult> ChargeAsync(ChargeRequest req, CancellationToken ct)
{
    // The deadline travels with the request: each hop spends what is left, it does not restart the clock.
    using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
    cts.CancelAfter(_deadline.Remaining());          // e.g. 800 ms out of a 2 s end-to-end budget

    try
    {
        var res = await _http.PostAsJsonAsync("/charges", req, cts.Token);
        if (res.IsSuccessStatusCode) return CallResult.Committed;
        if ((int)res.StatusCode == 422) return CallResult.DefinitelyNotCommitted;  // business rejection
        return CallResult.Unknown;                    // 5xx: the server may well have committed
    }
    catch (TaskCanceledException) { return CallResult.Unknown; }   // timeout: no information at all
    catch (HttpRequestException)  { return CallResult.Unknown; }   // connection reset mid-flight
}

Notice what the code refuses to do: it never maps a timeout to "failed". A timeout on POST /charges means the charge may exist. The only safe responses are to make the call retryable without duplication — which is why every serious remote mutation carries an idempotency key (unit 07) — or to make the operation queryable ("did the charge with key K happen?"). "Retry on timeout" without one of those two is how customers get charged twice.

Gray failure and the health-check lie

Modern outages are rarely "the node is down". They are gray failures: the node answers /health in 1 ms because that endpoint touches nothing, while every real request times out on a saturated connection pool. Load balancers and Kubernetes readiness probes keep sending it traffic; the node keeps failing it. Two mitigations to have ready: make readiness probes exercise the critical dependency path (a real query through the real pool), and complement server-side health with client-side outlier ejection — the caller notices that this one instance returns 3% errors while its peers return 0.01% and takes it out of rotation. Envoy and most service meshes do this out of the box; it is one of the few genuine mesh advantages worth arguing for in an interview.

Interview trap · "we retry on failure"

The most common candidate answer, and the most common cause of the outages you will be asked about. Three follow-ups are waiting. (1) Retry on what? A 503 with Retry-After, yes. A 400, never — it will fail identically forever. A timeout, only if the operation is idempotent. (2) With what backoff? Fixed-interval retries synchronise across every caller and produce a thundering herd exactly when the dependency is trying to recover; you need exponential backoff with jitter and a retry budget (say "retries may be at most 10% of traffic") so retries cannot become the majority of load. (3) Retries at how many layers? Three at the SDK, three at the gateway and three in the client is 27 requests for one user action — retry amplification is what turns a 10% degradation into a full outage. "Retries at exactly one layer, the one that knows the operation is idempotent" is a better answer than most principals give.

Try it · make the unknown outcome visible

1. Run any HTTP service locally behind a fault-injecting proxy (Toxiproxy, or a twenty-line reverse proxy you write). Add a toxic that accepts the request, forwards it, and then drops the response. Watch the client report failure while the server log shows a committed transaction. Then add an idempotency key and re-run the same request; confirm the second call returns the first result instead of doing the work twice.

2. Take a service with a 30 s client timeout and a dependency you can freeze (docker pause). Freeze it and watch the thread or connection pool drain. Measure how long until your service starts failing requests that never touch the frozen dependency.

Expected outcome

1. The client sees a timeout or a reset and, if it retries naively, the server executes twice — two charges, two rows, two emails. With an idempotency key stored in the same transaction as the effect, the retry becomes a lookup that returns the original response. That is the whole game: the network gives you at-least-once; your storage has to give you at-most-once.

2. With 200 pool slots, a 30 s timeout and 20 rps to the frozen dependency you exhaust the pool in about 10 seconds, and then every unrelated request queues behind it. This is why bulkheads (a separate, small pool per dependency) matter more than the timeout value itself: the timeout limits how long one request suffers, the bulkhead limits how much of the system one sick dependency can take with it.

Interview Q&A · failure and the network

What actually makes a system "distributed", and why is that hard?

A system is distributed when its parts fail independently and communicate over a network they do not control. The hardness is not concurrency — you get that on one machine too — it is partial failure plus the impossibility of distinguishing a slow node from a dead one. On one machine, if the process dies everything dies together and you restart from a known state. Across machines, half your operation can have happened, on a node you cannot reach, and you must design so that both "it happened" and "it did not" lead to a correct outcome. Everything else — consensus, quorums, idempotency, sagas — is machinery for coping with that one problem.

What are the fallacies of distributed computing and which one bites you most?

The eight are: the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology doesn't change, there is one administrator, transport cost is zero, the network is homogeneous. In practice the most expensive is "latency is zero", because it hides in code review: someone puts a remote call inside a loop and a 2 ms method becomes 200 calls at 3 ms each, which only surfaces at production data volumes. Second is "topology doesn't change" — everything works until a deployment moves a service to another availability zone and a 0.3 ms hop becomes 1.5 ms with 50 ms tails.

Your call to a payment provider times out. What do you do?

Nothing destructive, because a timeout carries zero information — the charge may exist. Concretely: I mark local state Pending rather than Failed, and I never retry a payment without an idempotency key the provider honours, so a retry is a lookup rather than a second charge. If they expose query-by-key I reconcile asynchronously; if not, I reconcile against their settlement file. The user-facing decision is separate: I would rather say "your payment is processing" and confirm within seconds than either lie about failure or hold the request thread for 30 seconds.

How do you choose a timeout value?

From the dependency's latency distribution and from the budget above me, never from a round number. I start near the observed p99.5 plus headroom, then check two things: that it is comfortably below my caller's deadline so my work is never wasted, and that timeout × concurrency limit is a load the dependency can survive. I strongly prefer propagating an absolute deadline over per-hop durations, because per-hop timeouts multiply down a chain — three hops of 2 s each is a 6 s worst case that the user's 3 s budget never agreed to. And I treat the timeout as a tunable with an alert on its firing rate, not a constant nobody revisits.

What is a gray failure, and why do health checks miss it?

A gray failure is a node that is degraded rather than dead — high latency, 5% errors, one disk failing writes — while still passing a shallow health check that only proves the process is running. Health checks miss it because they are deliberately cheap and dependency-free, which is exactly what makes them uncorrelated with request success. The fix is layered: readiness probes that touch the real critical path, client-side outlier ejection so callers can evict an instance their peers are happy with, and alerting on the differential — one instance's error rate against the fleet median — rather than on absolute thresholds.

Why can a garbage-collection pause cause data corruption in a distributed system?

Because a paused process is indistinguishable from a partitioned one, but it wakes up still believing what it believed before. The canonical case: node A holds a lease, pauses for 15 seconds, the lease expires, node B acquires it and starts writing; A wakes up, has no idea time passed, and writes with a stale lease. A wall-clock check inside A does not save you because A checked before the pause. The real fix is a fencing token: the lock service hands out a monotonically increasing number and the storage layer rejects any write carrying a token lower than the highest it has seen. That is unit 04, and it is the answer interviewers are fishing for.

Crash-stop versus Byzantine failure models — which do you design for?

Crash-stop assumes a failed node simply stops and never sends wrong messages; crash-recovery adds that it may return with its durable state. Byzantine allows arbitrary behaviour — lying, corrupting, replaying — which blockchains and some avionics defend against at roughly 3f+1 replicas instead of 2f+1. Inside one trust domain I design for crash-recovery: it is what Raft, Kafka's KRaft and etcd assume, and it is the right cost/benefit. What I take from the Byzantine world is checksums on the wire and on disk, because silent corruption from bad hardware or a buggy proxy is a real, non-adversarial version of the same problem — Kafka's per-record CRC has caught exactly that.

What is retry amplification and how do you prevent it?

It is the multiplication of retries down a call chain: four layers retrying three times each turns one user request into up to 81 backend calls, and it happens precisely when the backend is already struggling. Prevention has three parts. Retry at one layer only — the one that knows the call is safe to repeat — and make the others fail fast. Use a retry budget: a token bucket capping retries at, say, 10% of successful traffic, so retries collapse to zero when everything is failing. And propagate deadlines so a hop with no remaining budget does not start a retry it cannot finish. Jitter is necessary but not sufficient: it spreads the herd, it does not shrink it.

Your service depends on five others, each 99.9% available. What is your availability?

If I need all five synchronously on every request, roughly 99.5% — about 3.6 hours of downtime a month instead of 43 minutes. That arithmetic is why the answer is almost never "make the dependencies more reliable"; it is to remove them from the critical path. Which can be asynchronous (publish an event and let them consume it)? Which can be cached with a stale-if-error policy? Which can be degraded — render the page without the recommendations block? A system that composes five 99.9% dependencies into 99.95% availability does it by depending on fewer of them per request, not by everyone trying harder.

How do you introduce failure testing to a team that thinks it is reckless?

I never start with production and I never start with the word "chaos". I start with a specific hypothesis in a test environment: "we believe order placement survives the recommendation service being down; here is a fifteen-minute experiment that proves it". The first experiments should find something embarrassing but harmless — usually a missing timeout or a retry loop — which converts the argument from philosophy to evidence. Then I formalise it: an experiment needs a hypothesis, a blast-radius limit, an abort condition and an owner watching. Production comes later, in business hours, on one instance, with a big red button. The framing that lands is "we will find this failure either way; the only choice is whether we find it on Tuesday at 11 or Saturday at 3".

02 Time, order and causality

Docs: Spanner TrueTime · RFC 9562 — UUID formats

There is no "now" in a distributed system. Each machine has its own clock, disciplined by NTP to a few milliseconds if you are lucky and tens of milliseconds if you are normal, and those clocks step backwards during corrections, leap-second smearing and VM migrations. So you cannot order two events on two machines by comparing their timestamps, and any design that does — "last write wins by timestamp", "expire the lock when now > expiry", "sort the audit log by created_at" — has a correctness bug whose frequency is proportional to your clock skew.

Two clocks, two jobs

Every runtime gives you two clocks, and conflating them is the single-machine version of this bug. The wall clock (DateTime.UtcNow, System.currentTimeMillis(), time.Now()) tells you what a human calls the time; it jumps when NTP corrects it and it can move backwards. The monotonic clock (Stopwatch, System.nanoTime(), time.Since()) only ever moves forward and is meaningless across machines. The rule: wall clock for "when did this happen for a human", monotonic for "how long did this take" and for every timeout. Measuring a timeout with a wall clock means an NTP step can make your 5-second timeout fire in 5 milliseconds — or never.

// Wrong: elapsed time can go negative when NTP steps the clock backwards.
var t0 = DateTime.UtcNow;
DoWork();
var elapsed = DateTime.UtcNow - t0;              // may be negative, may be minutes

// Right: monotonic, immune to clock adjustments.
var sw = Stopwatch.StartNew();
DoWork();
var elapsed2 = sw.Elapsed;                        // always forward, always sane

// Wrong: comparing timestamps from two machines to decide who wrote last.
if (incoming.UpdatedAtUtc > current.UpdatedAtUtc) Apply(incoming);   // silently loses writes

// Right: a version the system controls, not a clock.
if (incoming.Version == current.Version + 1) Apply(incoming);
else Reconcile(incoming, current);

Happens-before: the only ordering you actually have

Lamport's happens-before relation (1978) is the mental model to carry. Event a happens-before b if they are on the same node and a came first, or a is a send and b is the matching receive, or by transitivity. Anything not related by happens-before is concurrent — and concurrent events genuinely have no order, whatever their timestamps claim. That is not a limitation to work around, it is a truth to design with: concurrency means either the operations commute (increments, set-adds) or a human decision is required, because last-write-wins loses data while a merge function preserves it.

The tools that make happens-before machine-readable, in increasing cost:

  • Lamport clocks — one counter per node, sent with every message, max(local, received) + 1 on receipt. Gives a total order consistent with causality, but two Lamport timestamps cannot tell you whether the events were causally related or concurrent.
  • Vector clocks — one counter per node, all of them sent. Now you can detect concurrency (neither vector dominates), which is exactly how Dynamo-style stores surface sibling versions for the application to merge. The vector grows with the number of writers, so they are scoped per key and pruned.
  • Hybrid logical clocks (HLC) — a wall-clock component plus a logical counter, so timestamps are causally correct and close to real time. CockroachDB, MongoDB and YugabyteDB use HLC; it is the pragmatic default when you want causality plus a timestamp humans can read.
  • Bounded-uncertainty clocks — Spanner's TrueTime returns an interval [earliest, latest] with a hardware-backed bound (GPS plus atomic clocks) and commits wait out the uncertainty, historically a few milliseconds, so external consistency holds. You are buying linearizability with latency and with hardware most people do not have.

Identifiers carry time too

A detail that shows up constantly in real designs: your ID scheme is a time decision. Random UUIDv4 keys destroy insert locality in a B-tree — every insert lands on a random page, so an index that fit in cache stops fitting. UUIDv7, standardised in RFC 9562 (May 2024, superseding RFC 4122), puts a 48-bit Unix-millisecond timestamp in the high bits, so IDs sort roughly by creation time and inserts stay at the right edge of the index; PostgreSQL 18 (September 2025) ships uuidv7() in core, which is what turned it from a library trick into the default. Snowflake-style IDs (timestamp | machine id | sequence) give the same locality plus a guaranteed per-node sequence, at the cost of assigning machine ids. The trade-off to name out loud: time-ordered IDs leak creation time and sometimes volume, which is why public-facing identifiers are often a separate opaque value.

Interview trap · "last write wins"

LWW sounds like a policy. It is a data-loss policy with a clock-skew-sized window, and interviewers probe it because most candidates have shipped it without noticing. If two replicas accept concurrent writes and you resolve by wall-clock timestamp, the winner is the write whose node had the faster clock, not the one that happened later — and the loser is gone with no trace. Cassandra's LWW is the textbook example, and the operational consequence is real: a node whose clock is five minutes ahead can silently suppress every subsequent write to those keys for five minutes. Acceptable answers: make writes commutative (CRDT counters, set-adds), keep siblings and merge in the application (Dynamo/Riak style), or route all writes for a key through a single leader so there is no concurrency to resolve. If you do keep LWW, say so deliberately and say what you are willing to lose.

Try it · watch concurrency become invisible

1. Simulate two replicas in a few dozen lines: each holds {value, timestamp}, you can write to either, and they gossip. Give replica B's clock a +2000 ms offset. Write "alice" to A, wait 100 ms, write "bob" to B, then write "carol" to A. Gossip, and observe which value survives.

2. Repeat with vector clocks, returning siblings when neither vector dominates, then implement a merge (keep both names) and observe that nothing is lost.

Expected outcome

1. "bob" wins permanently, even though "carol" was written a second later in real time, because B's clock is ahead. Worse, every later write to A is also discarded until A's clock passes B's timestamp — a silent write blackhole that no error log records. That is exactly the incident behind most "our updates sometimes don't stick" tickets.

2. With vector clocks the third write is a descendant of the first and concurrent with the second, so you get a sibling pair and a deliberate merge. The sentence to keep: the timestamp did not make the conflict go away, it made it invisible.

Interview Q&A · time and ordering

Why can't you order events across machines by timestamp?

Because the timestamps come from different clocks with independent error. NTP typically holds machines within a few milliseconds inside a datacentre and tens of milliseconds across the internet, but it also steps clocks during correction, so a clock can move backwards, and virtualised clocks jump on migration. Two events 5 ms apart on two machines can carry timestamps in the wrong order, and nothing in the data reveals it. If I need order I use something the system controls: a per-key version, a sequence from a single leader, a log offset, or a logical/hybrid clock. Wall-clock timestamps are for humans and coarse retention policies, not for correctness.

Explain happens-before, and why "concurrent" is a real answer.

Happens-before is the partial order generated by two rules: within a process, program order; and a send happens-before its receive. Transitivity does the rest. If neither a happens-before b nor b happens-before a, they are concurrent — and that is a fact about the execution, not a gap in instrumentation. It matters because it tells you exactly where a design decision is required: for concurrent updates you need commutativity, a merge function, or a coordination point that removes the concurrency. Pretending you can order concurrent events with timestamps is how you get silent data loss.

Lamport clocks versus vector clocks — when do you pay for vectors?

Lamport clocks give a total order consistent with causality, which is enough when you only need a deterministic tie-break and do not care whether a conflict existed. Vector clocks additionally tell you whether two versions are causally related or genuinely concurrent, which is what you need when multiple replicas accept writes and you must merge rather than discard. I pay for vectors when the data model has real multi-master writes — offline-capable clients, active-active regions, shopping carts — and I keep them bounded by scoping to actors that actually write the key, plus pruning. If a single leader owns each key, vectors are cost with no benefit.

What is a hybrid logical clock and why do databases like it?

An HLC is a pair: a physical component tracking wall-clock time and a logical counter that increments when events happen faster than clock resolution or when a received timestamp is ahead. It preserves happens-before like a Lamport clock but stays within clock skew of real time, so timestamps are causally correct and still meaningful to a human or a TTL. CockroachDB and MongoDB use it because it delivers causal consistency and readable versions without Spanner's atomic-clock hardware. The trade-off worth naming: HLC bounds the error, TrueTime's commit-wait eliminates it — HLC alone is not linearizable.

How does Spanner get global external consistency, and what does it cost?

TrueTime exposes time as an interval with a bounded error, backed by GPS receivers and atomic clocks in every datacentre. A transaction picks a commit timestamp and then waits out the uncertainty — it does not acknowledge until that timestamp is certainly in the past everywhere — so any transaction starting after it commits sees a strictly greater timestamp. The cost is a commit-wait of a few milliseconds on every write, plus real hardware and a global deployment. The generalisable lesson: you can buy strong ordering with latency, and every system claiming strong global consistency is paying for it somewhere.

You need monotonically increasing ids across a fleet. Options?

A database sequence is simplest and correct but is a coordination point and a failure domain; batching (hand out 1000 at a time) removes most round trips at the cost of gaps. Snowflake-style ids need no coordination per id but need machine-id assignment and are sensitive to clock rollback, so a good implementation refuses to issue ids while the clock is behind its last issued timestamp. UUIDv7 gives time-ordered ids with no coordination at all and is my default now that RFC 9562 standardised it and Postgres 18 ships uuidv7(). The question I ask back is whether the requirement is truly monotonic or merely time-sortable and unique — the second is far cheaper and is usually what people need.

What is causal consistency and when is it enough?

Causal consistency guarantees that if A happens-before B, every replica that sees B has already seen A, while concurrent operations may be observed in different orders on different replicas. It is the strongest model achievable while remaining available under partition, which makes it a sweet spot for user-facing systems: a reply never appears before the comment it replies to, and you never fail to read your own write. It is enough whenever the invariants are per-entity and per-session. It is not enough when a global invariant is at stake — uniqueness of an email address, a balance that may not go negative — because those need a single point of serialisation.

Why are random UUIDs a performance problem, and is that still true?

UUIDv4 keys are uniformly random, so inserts hit random pages of a B-tree; once the index exceeds memory each insert becomes a read plus a write of a cold page, and page splits fragment the index. On a clustered primary key — SQL Server's default, InnoDB always — the whole row moves with it, so it is worse. It is still true, and the fix is now standard rather than folklore: UUIDv7 puts a millisecond timestamp in the leading bits so inserts are near-sequential and hot pages stay hot. Stuck on v4 in an existing schema, the usual mitigations are a separate monotonic clustered key with the UUID as a secondary unique index, or SQL Server's NEWSEQUENTIALID().

A colleague proposes ordering an event stream by the producer's event timestamp. What do you say?

That it is right for analytics and wrong for correctness. Event time is what you want for windowing and reporting — which is exactly why stream processors distinguish event time from processing time and use watermarks to decide when a window is complete. But it is not a total order you can drive a state machine from, because producers' clocks disagree and late events arrive after you have already acted. For correctness I order by something the system owns: partition plus offset in Kafka, a per-aggregate version, or a sequence assigned by the single writer of that entity. I would also ask what happens to an event that arrives an hour late, because the honest answer usually redesigns the feature.

How do you handle clock skew operationally?

Monitor it explicitly: every node exports its offset from its time source and I alert when the offset exceeds a threshold that matters to the design (say 100 ms) or when a node is unsynchronised at all. I prefer chrony over legacy ntpd, and where correctness depends on bounded skew I use the cloud provider's local time service rather than a public pool. Then I design so skew is a performance problem rather than a correctness one: no wall-clock ordering, monotonic clocks for timeouts, fencing tokens instead of time-based lock expiry, and leases that are renewed rather than trusted. The one place I accept a hard time dependency is certificate and token expiry, and there I make the allowed tolerance explicit.

03 Replication and consistency

Docs: Jepsen: consistency models · Kafka replication · RabbitMQ quorum queues

You replicate for two different reasons and they pull in opposite directions: durability (survive losing a machine) and availability (keep serving while a machine is gone). The moment there is more than one copy, you owe an answer to "what does a reader see?" — and that answer is the consistency model. Almost every argument about CAP is really an argument about which consistency model a product needs, so start there rather than at the theorem.

The ladder of consistency models

Think of it as a ladder from expensive to cheap, and pick the lowest rung that satisfies the invariant:

  • Linearizable (a.k.a. atomic, "strong") — the system behaves as if there were a single copy and every operation took effect at one instant between its call and its return. If a write completes at 10:00:00.000, no later read anywhere may return the old value. Costs a round trip to a quorum on reads too, which is the part people forget.
  • Sequential — all nodes see the same order, but that order need not match real time. Rarely offered by name in products.
  • Causal — happens-before is respected, concurrent operations may be ordered differently by different replicas. The strongest model that survives a partition without losing availability.
  • Read-your-writes / monotonic reads / monotonic writes — session guarantees. Weak globally, but they are what makes an eventually consistent system feel non-broken to a single user, and they are cheap: sticky routing plus a version token.
  • Eventual — replicas converge if writes stop. Says nothing about what you read in the meantime, which is why it is a floor, not a design.

Two distinctions that separate people who have read about this from people who have operated it. First, linearizability is about single objects, serializability is about transactions — they are orthogonal, and "strict serializability" is the combination. A database can be serializable and still let you read stale data (snapshot-isolated reads from a follower); a register can be linearizable with no transactions at all. Second, "strong consistency" in a vendor's marketing usually means "linearizable reads if you ask for them", and the default is often a follower read. Always ask what the default read path does.

CAP, and then PACELC because CAP is not enough

CAP says that when a network Partition occurs, you must choose between Consistency (linearizability) and Availability (every non-failing node answers). That is a real theorem and a narrow one: it says nothing about the 99.9% of the time when there is no partition, and "CA systems" do not exist because you do not get to opt out of partitions. The useful extension is PACELC (Abadi, 2012): if Partition then A or C; Else, Latency or Consistency. That second clause is the one you actually trade every day — a synchronous cross-region quorum costs you 60–150 ms per write even when nothing is broken.

Quorums, and why R + W > N is only half the story

In a leaderless (Dynamo-style) system with N replicas, a write goes to W and a read to R; if R + W > N the sets must intersect, so a read sees at least one copy of the latest write. With N=3, the usual choice is R=W=2: you tolerate one node down for both reads and writes. The half that gets missed in interviews: quorum overlap gives you the value, it does not give you an order. If two writers concurrently write the same key at W=2, both succeed and you have siblings — the intersection guarantees you see the conflict, and you still have to resolve it (unit 02). Quorums also fail to make writes atomic across keys, and a write that reaches only one node before the coordinator crashes may or may not survive read repair. That is why Dynamo-style stores add hinted handoff, read repair and anti-entropy (Merkle-tree) sync on top of quorums, and why a "consistent" answer there is a probabilistic one.

Set min.insync.replicas=1 and you have chosen availability: writes keep succeeding into one replica, and if that broker dies before the others catch up, those messages never existed. unclean.leader.election.enable=true is the same choice at the extreme — it promotes a replica that is missing data, truncating the log and silently losing committed messages, in exchange for the partition coming back online.

Synchronous, asynchronous, and the semi-synchronous middle

Synchronous replication acknowledges only after a replica has durably received the write: zero RPO, but the writer's latency includes the slowest replica and the writer stalls when a replica is down. Asynchronous acknowledges immediately: fast, survives replica outages, and loses the tail on failover — the RPO equals the replication lag at the moment of the crash, which is why you must monitor lag as a data-loss metric, not a performance one. The practical middle is what most systems actually run: quorum replication (wait for k of n, not all), which bounds latency at the k-th fastest replica rather than the slowest, plus asynchronous fan-out to the rest. Postgres calls it synchronous_standby_names = 'ANY 1 (a, b)'; Kafka's ISR is the same idea with a dynamic membership.

Interview trap · "we're eventually consistent, so it's fine"

Eventual consistency is a statement about what happens when writes stop, which they never do. The trap is answering "eventually consistent" without saying how the user experiences the window. Three specific follow-ups you should pre-empt: (1) How long is eventually? If you cannot state a p99 replication lag with an alert on it, you do not have eventual consistency, you have hope. (2) Does a user read their own write? Posting a comment and not seeing it is the bug that generates support tickets; the fix is a session guarantee — sticky routing to the replica that took the write, or passing a version token the read waits for. (3) Which invariants can't tolerate it? Uniqueness, non-negative balances and "only one of these may be active" all need a single serialisation point, so they either sit in one strongly consistent store or become a compensating workflow with a business rule for the overdraft. Answering "eventual consistency plus read-your-writes on the session, with a 200 ms p99 lag alert, and uniqueness enforced in one Postgres table" is a lead answer; "eventually consistent" alone is a junior one.

Interview Q&A · replication and consistency

State CAP precisely, and then tell me why it is over-quoted.

CAP says that a system which may be partitioned cannot simultaneously guarantee linearizability and availability for every non-failing node. It is over-quoted because it is a statement about a rare condition, phrased as if it were a taxonomy of databases. Two corrections I would make in a design review: "CA" is not an option, because partitions are chosen for you; and CAP says nothing about the normal case, where the real trade-off is latency versus consistency. PACELC captures that — if partitioned, A or C; else, L or C — and it is the one I actually use, because the cost of a cross-region quorum on every write shows up in the p99 every day, not once a year.

Difference between linearizability and serializability?

Linearizability is a recency guarantee about single objects: once a write returns, every later read sees it, and operations appear to take effect at a single point in real time. Serializability is an isolation guarantee about transactions: the outcome equals some serial order of the transactions — but that order need not match real time, so a serializable database may serve you a transaction that appears to have run in the past. Together they give strict serializability, which is what Spanner and CockroachDB advertise. The practical consequence is that "we use a serializable database" does not mean a read after a write sees it if you read from a follower or a snapshot.

What do R + W > N and quorum reads actually guarantee?

That the read set and the write set intersect on at least one replica, so a read observes at least one copy of the most recent successful write. That is weaker than it sounds. It does not order concurrent writes — both can succeed at W and produce siblings — and it does not make multi-key operations atomic. It also degrades quietly: with sloppy quorums and hinted handoff, W can be satisfied by nodes that are not the key's real replicas, so the intersection argument no longer holds until handoff completes. I use quorums for availability and durability, and I put the actual ordering guarantee somewhere else: a single leader per key, or a conflict-free data type.

Walk me through Kafka's ISR and what acks=all really promises.

Each partition has a leader and followers; the in-sync replica set is the leader plus the followers that are caught up within replica.lag.time.max.ms (30 s by default). With acks=all the producer's write is acknowledged once every member of the current ISR has it. The subtlety candidates miss: the ISR is dynamic, so with RF=3 the ISR can shrink to just the leader, and then acks=all means "one replica has it". That is precisely what min.insync.replicas=2 guards: if the ISR falls below two, the leader rejects the produce with NOT_ENOUGH_REPLICAS instead of accepting a write it cannot protect. RF=3 with min.insync.replicas=2 and acks=all is the standard durable configuration, and unclean.leader.election.enable must stay false or you can lose acknowledged data on failover.

What is read-your-writes, and how do you implement it cheaply?

It is the session guarantee that a user always sees at least their own most recent write, even if the global system is eventually consistent. Three cheap implementations, in rising order of robustness: route the session's reads to the replica that accepted the write for a few seconds (sticky routing); have the write return a version or LSN and have reads wait for a replica that has caught up to it (a "consistent prefix token", which is what Cosmos DB and MySQL's MASTER_POS_WAIT expose); or read from the leader for the small subset of pages where staleness is visible. I usually start with the third, because it costs nothing to implement and applies to a handful of endpoints, and move to the token when leader read load becomes a problem.

Synchronous or asynchronous replication for a payments database?

Synchronous to at least one replica in a different failure domain, because the acceptable RPO for money is zero. I would use quorum-style semi-synchronous — ANY 1 (standby_a, standby_b) in Postgres — so a single slow standby does not stall commits, and I would place the synchronous standbys in a second availability zone rather than a second region, because cross-region synchronous replication puts 60–150 ms on every commit and that is usually unacceptable for the transaction rate. Cross-region then gets asynchronous replication with an explicit, monitored RPO, and the disaster-recovery runbook states plainly how many seconds of transactions a region failover can lose and who signs off on it.

How do you monitor replication so you find out before your users do?

Three signals, not one. Replication lag in bytes or LSN distance tells you how much data you would lose on failover — that is the RPO metric and it belongs on the durability dashboard. Lag in time (how old is the newest record the replica has applied) is what correlates with user-visible staleness. And replica apply rate versus primary write rate tells you whether the lag is shrinking or diverging, which is the difference between a blip and an incident. I alert on time lag for user impact and on byte lag for data-loss risk, and I make one dashboard panel show them together, because a replica that is 2 seconds behind on a quiet night and 2 seconds behind during peak are very different amounts of data.

When would you deliberately choose availability over consistency?

When the cost of rejecting a write exceeds the cost of reconciling later. Shopping-cart adds, telemetry, "like" counts, session state, audit-style append logs — for all of these, refusing a write during a partition loses real value while a merge afterwards is cheap or even trivially correct if the operation commutes. I would not make that choice for anything with a global invariant: seat inventory, account balances, unique usernames. And I would make the choice per operation rather than per system, which is what tunable-consistency stores are for: quorum writes for the balance, ONE for the activity feed, in the same database.

What is a split brain and how do you prevent it in a replicated database?

Split brain is two nodes each believing they are the primary, both accepting writes, producing histories that cannot be merged. Prevention needs a majority-based decision — only the side holding a quorum may act — plus something that stops the deposed primary from writing after it has been deposed. That second part is where systems fail: majority election alone does not stop a paused old primary from waking up and writing. You need fencing at the resource: STONITH at the machine level, a fencing token the storage rejects if it is stale, or (in Kafka's case) an epoch number attached to every produce so a stale leader's writes are refused. If someone proposes an even number of voters or a two-node cluster with a heartbeat, that is the moment to raise it: two nodes cannot form a majority when they cannot see each other.

How would you introduce a consistency model discussion to a product team?

By translating each model into a sentence about user experience and a sentence about cost. "Strong" becomes "if you refresh, you always see what you just did, everywhere, and each write costs an extra 40 ms plus we stop accepting writes when a zone is unreachable." "Causal with read-your-writes" becomes "you always see your own actions immediately, and other people's may take up to two seconds; we stay up when a zone fails." Then I ask for the invariants in business language — can we ever sell the same seat twice, can a balance go negative, is a duplicate email address an outage or a cleanup task — and let those answers pick the model. Product people make good decisions about consistency when it is framed as "what may a customer see" rather than as a theorem.

04 Consensus, leases and fencing

Docs: Raft · etcd API · RabbitMQ metadata store (Khepri)

Consensus is the primitive that makes "there is exactly one leader", "this value is decided", and "these nodes are the members" true in a system where messages are lost and nodes pause. Everything else in the reliability toolbox is either built on it or deliberately avoiding it. It is worth knowing well because the industry has converged: ZooKeeper's ZAB, etcd/Consul's Raft, Kafka's KRaft (Raft), RabbitMQ's Ra/Khepri (Raft) and CockroachDB's per-range Raft are all the same shape. Learn Raft and you can reason about all of them.

Raft in one paragraph you can say out loud

Time is divided into terms, each with at most one leader. A node with no heartbeat from a leader becomes a candidate, increments the term and asks for votes; a node grants at most one vote per term and only to a candidate whose log is at least as up to date as its own. A candidate with a majority becomes leader. The leader appends client commands to its log and replicates them; once a majority has persisted an entry it is committed and can be applied to the state machine. Two properties do all the work: quorum intersection (any two majorities share a node, so a new leader has seen every committed entry) and the up-to-date vote restriction (a node with a stale log can never win). Randomised election timeouts (typically 150–300 ms) break the symmetry that would otherwise cause repeated split votes.

The consequences worth stating in an interview: a Raft cluster of 2f+1 nodes tolerates f failures, so 3 nodes tolerate 1 and 5 tolerate 2. Even sizes are strictly worse — four nodes still tolerate only one failure but need three votes, so you have added cost and latency for nothing. Every write costs a round trip to a majority, so a 5-node cluster spread across three regions has write latency equal to the second-slowest region. And a read is only linearizable if it also confirms leadership: either through the log, or via a lease, or with a "read index" heartbeat round — which is why etcd offers serializable (local, fast, possibly stale) and linearizable (default, quorum-confirmed) reads as separate options.

What changed recently, and why it matters

Two of the biggest messaging systems finished replacing bespoke coordination with Raft, and both changes are recent enough to be worth quoting. Kafka 4.0 (18 March 2025) removed ZooKeeper entirely — not deprecated, removed — so the controller quorum is KRaft, metadata is an internal Kafka log replicated by Raft, and the practical wins are faster failover and cluster metadata that scales to millions of partitions because a broker replays a log instead of loading a ZooKeeper tree. RabbitMQ 4.3 (23 April 2026) made Khepri the only supported metadata store, deleting Mnesia; with it went the old partition-handling strategies pause_minority, autoheal and pause_if_all_down, because a Raft store does not need policies for what to do about split brain — the minority side simply cannot make progress. If you have operated RabbitMQ, this is the migration question of 2026: an upgraded cluster keeps its existing store until an administrator explicitly enables Khepri (that was the 4.2 behaviour, October 2025), so anyone still on Mnesia must convert before 4.3.

// A lease is a lock with an expiry the grantor controls. etcd's version, with the trap made visible.
lease, _ := cli.Grant(ctx, 10)                       // 10-second TTL
sess, _ := concurrency.NewSession(cli, concurrency.WithLease(lease.ID))
mu := concurrency.NewMutex(sess, "/locks/rebalance")
if err := mu.Lock(ctx); err != nil { return err }
defer mu.Unlock(ctx)

// mu.Header().Revision is a monotonically increasing FENCING TOKEN.
// Everything the critical section writes must carry it, and the store must reject stale ones:
token := mu.Header().Revision
if err := store.WriteIfTokenAtLeast(ctx, "shard-7", token, payload); err != nil {
    // Someone with a newer token already wrote. We were paused and lost the lease; abort quietly.
    return err
}

That last block is the entire point of this unit. A distributed lock cannot stop a process that has been paused for longer than the lease from waking up and acting; the lock service has already given the lease away. Only the resource can stop it, by rejecting writes carrying a token lower than the highest it has seen. Kafka does exactly this with producer epochs and leader epochs; Postgres-backed workers do it with an WHERE token >= $1 guard; object stores do it with conditional writes on an ETag. If your answer to "how do you protect the critical section?" ends at "we take a lock in Redis", you have not answered it.

When not to use consensus

Consensus is a coordination bottleneck by design: every decision costs a majority round trip and the cluster's write throughput does not grow when you add nodes — it shrinks. So use it for metadata, not for data. Kafka does not run Raft over your messages; it runs Raft over the controller metadata and uses a much cheaper leader-and-ISR scheme per partition. CockroachDB runs Raft per range so the coordination is sharded. The design smell to name in a review is a single consensus group on the hot path of every request — one etcd cluster that every service reads on every call is a latency floor and a blast radius, and the fix is caching with watches, not a bigger etcd.

Interview trap · "we use a distributed lock"

Interviewers ask about distributed locks because the honest answer is uncomfortable. A lock with a TTL gives you mutual exclusion only if no participant can pause longer than the TTL — and a GC pause, a page fault storm, a throttled container or a stalled fsync can all exceed it. The Redlock debate (Kleppmann vs Antirez, 2016) is the canonical reference: the algorithm's safety argument depends on bounded clock drift and bounded pauses, which an asynchronous system does not provide. What you should say: locks are a performance optimisation that keeps two workers from doing the same expensive work; they are not a correctness mechanism. Correctness comes from the resource refusing stale writers — a fencing token, an optimistic-concurrency version, a unique constraint, or a conditional write. And the best answer of all is often to remove the need: partition the work so exactly one owner exists by construction (unit 05).

Try it · break a lock on purpose

1. Run a 3-node etcd (or a single node for the experiment). Write a worker that acquires a 5-second lease-backed lock, then SIGSTOPs itself for 8 seconds (simulating a GC pause), then writes to a file. Run two of them. Observe both writing.

2. Now make the target reject stale writers: store the highest revision seen alongside the data and refuse writes with a lower one. Re-run the same experiment.

Expected outcome

1. Both workers write, in the wrong order, with no error anywhere. The lock service behaved perfectly — it expired a lease and granted it to someone else — and your invariant is still broken. This is the experiment that changes how people talk about locks.

2. The paused worker's write is rejected because its token is older, and it can detect that it lost the lease and abandon the work instead of corrupting it. Note the shape: the check and the write must be atomic at the resource. Reading the token, comparing it in your code and then writing reintroduces the race.

Interview Q&A · consensus and coordination

Explain Raft to someone who knows what a leader is.

Raft splits the problem into leader election, log replication and safety. Time is divided into terms with at most one leader each; a follower that stops hearing heartbeats becomes a candidate, bumps the term and requests votes, and wins with a majority — but a node only votes for a candidate whose log is at least as current as its own. The leader appends commands to its log, replicates to followers, and once a majority has persisted an entry it is committed and applied. Safety comes from quorum intersection: any two majorities overlap, so a new leader necessarily has every committed entry. The parts people forget are randomised election timeouts to avoid split votes, and that reads need leadership confirmation to be linearizable.

Why should a Raft or ZooKeeper ensemble have an odd number of nodes?

Because fault tolerance is floor((n-1)/2), so 3 and 4 nodes both tolerate exactly one failure — the fourth node adds cost, adds a replica to replicate to, and raises the quorum size from 2 to 3, which makes writes slower and makes a two-node failure fatal in both cases. Five nodes tolerate two failures and are the usual choice for something like etcd behind a large Kubernetes cluster; beyond seven the write latency and the replication fan-out stop paying for themselves. The related trap is a two-node "cluster": two nodes cannot form a majority when they cannot see each other, so it is strictly worse than one node plus good backups.

What is a fencing token, and why does a lock without one not give you mutual exclusion?

A fencing token is a monotonically increasing number issued with the lock — etcd's mod revision, ZooKeeper's zxid, Kafka's leader epoch — that the client must present on every write, and that the resource uses to reject anyone holding an older token. It matters because a lock's TTL cannot bound a process pause: a client can be stopped for longer than the lease, wake up believing it still holds the lock, and write. The lock service did nothing wrong; the only place that can reject the stale writer is the resource itself. So the lock gives you "usually only one worker", which is a performance property, and the token gives you "never two writers", which is the correctness property.

Is Redis a valid place for distributed locks?

For coordination that is an optimisation, yes — a single-instance SET key value NX PX ttl with a random value and a compare-and-delete release is simple and fast, and it is honest about being best-effort. For correctness, no, and Redlock across five instances does not fix that: its safety argument assumes bounded clock drift and bounded pauses, and it still hands you no fencing token to give the resource. My position in a design review is that if a duplicate execution is merely wasteful, Redis is fine; if a duplicate execution is a bug, the resource must enforce it with a version check or a unique constraint, and then the lock is optional.

What did Kafka's move to KRaft actually change?

Kafka 4.0, in March 2025, removed ZooKeeper completely — it is not an option any more — so cluster metadata lives in an internal Kafka log replicated by a Raft quorum of controllers. Operationally it removes an entire system to run, secure and upgrade, and it removes the class of incidents where ZooKeeper and Kafka disagreed. Functionally, controller failover went from seconds of loading state to near-instant, because a new controller is already following the metadata log, and the supported partition count went up by an order of magnitude because metadata propagates as incremental log records rather than full-state watches. The migration consequence that still matters in 2026 is that there is no direct path from an old ZooKeeper cluster to 4.x: you migrate to KRaft on 3.9 first, then upgrade.

Same question for RabbitMQ and Khepri.

RabbitMQ replaced Mnesia — the Erlang-native store it used for all metadata — with Khepri, a Raft-based store built on the Ra library. Khepri became the default for new clusters in 4.2 (October 2025) and in 4.3 (April 2026) it became the only store, with Mnesia removed. The reason is that Mnesia's network-partition recovery was a set of policies you had to choose between — pause_minority, autoheal, pause_if_all_down — all of which are gone in 4.3, because with Raft the minority side simply cannot commit metadata changes and there is nothing to heal. Practically: metadata operations become quorum operations (slightly slower, dramatically more predictable), and cluster formation and recovery stop requiring the operator to reason about split brain by hand.

When is gossip the right answer instead of consensus?

When the information is large, changes constantly and does not need a single agreed value — membership, failure suspicion, load metrics, routing hints. SWIM-style gossip scales to thousands of nodes with constant per-node cost and no leader, and it degrades gracefully because the worst case is a stale view rather than a stall. Consensus is the right answer when a decision must be unique and durable: who is the leader, what is the current configuration, was this transaction committed. The common architecture uses both, and that is worth saying: Cassandra gossips membership but uses Paxos for lightweight transactions; Consul gossips health across the fleet and runs Raft in each server cluster.

How do you do a leader election without a consensus system available?

By making the database the arbiter, since it already provides atomicity. A leader table with a single row, a lease expiry and a version column: candidates run one conditional update — take the row if it is expired, and bump the version — and only one can win because the database serialises it. The version doubles as the fencing token. I renew at a third of the lease so a slow renewal does not cause an unnecessary handover, and I make sure the leader checks the token on every consequential write rather than trusting a boolean in memory. It is a perfectly respectable answer for a system that already depends on a strongly consistent database and does not want to run etcd for one job — and I would say plainly that it inherits the database's availability, which is the trade-off.

Your etcd cluster loses quorum. What happens and what do you do?

Writes stop and linearizable reads stop; serializable reads keep working from whatever each node has, stale. That is by design: the cluster prefers to be unavailable rather than to split. The response is to restore quorum, not to work around it — bring back a failed member, or if the machines are truly gone, recover from a snapshot and force a new single-member cluster, then re-add members. The thing to say next, because it is the lead-level part: the real fix is upstream, in making sure clients degrade sanely when the coordination store is unavailable. Services that cache their configuration with watches keep serving; services that read etcd on every request are down the instant etcd is, and that dependency should have been flagged in design review.

How do you explain to a team that they should not build their own consensus?

By being specific rather than dismissive. I would point out that the properties they need — a unique leader across pauses, no lost committed writes, safe reconfiguration when membership changes — are exactly the parts that are hard to get right, and that the published record is unkind: real implementations of Raft have shipped bugs in membership change and log truncation, found by Jepsen, years after being in production. Then I would offer the cheap path: for one leader, use the database you already have with a lease and a fencing token; for anything richer, use etcd or the coordination the platform gives you. I would also concede where they are right — reading the Raft paper and building a toy implementation is genuinely worth a week of someone's learning time, just not in the production path.

05 Partitioning and placement

Docs: DynamoDB partition key design · Kafka topics and partitions

Replication makes copies; partitioning makes pieces. You partition when one machine can no longer hold the data or absorb the writes, and the whole discipline reduces to one question: what is the key? Get it right and the system scales linearly and nothing coordinates. Get it wrong and you have a hot shard you cannot fix without a migration, because the partition key is the hardest decision in the system to change later — it is baked into every stored record, every consumer's ordering assumption and every client's routing.

Three ways to map keys to partitions

Range partitioning keeps keys sorted and assigns contiguous ranges (HBase, Bigtable, CockroachDB, Postgres declarative partitioning). Range scans are efficient — "all orders in March" reads one partition — but sequential keys create a write hotspot on the last partition, which is why timestamp-prefixed keys are an anti-pattern unless you salt them. Hash partitioning hashes the key and takes the modulus (Kafka's default partitioner, DynamoDB, Cassandra): writes spread evenly, but range scans must fan out to every partition, and hash(key) % N makes N almost immovable, since changing N remaps nearly every key. Consistent hashing places nodes and keys on a ring so adding a node moves only 1/n of the keys, with virtual nodes (100–256 tokens per physical node) to smooth the distribution; rendezvous hashing (highest random weight) achieves the same with simpler code and is what a lot of newer systems use.

// Consistent hashing with virtual nodes: adding a node moves ~1/n of keys, not all of them.
public sealed class HashRing
{
    private readonly SortedDictionary<uint, string> _ring = new();
    private const int VirtualNodes = 200;   // fewer than ~100 and the load spread gets visibly uneven

    public void Add(string node)
    {
        for (var i = 0; i < VirtualNodes; i++)
            _ring[Hash($"{node}#{i}")] = node;
    }

    public string NodeFor(string key)
    {
        var h = Hash(key);
        foreach (var (position, node) in _ring)      // first node clockwise from the key
            if (position >= h) return node;
        return _ring.First().Value;                   // wrap around the ring
    }

    private static uint Hash(string s) =>
        BitConverter.ToUInt32(SHA1.HashData(Encoding.UTF8.GetBytes(s)), 0);
}

Skew is the default, not the exception

Real key distributions are Zipfian. One celebrity account, one enterprise tenant, one product on the front page — and that single key's partition receives a disproportionate share of traffic while the rest idle. Because a partition is the unit of ownership, you cannot scale past a single hot key by adding machines; that is the constraint to state before proposing fixes. The fixes, in order of preference: (1) pick a compound key that splits the hot entity naturally (tenantId + regionId rather than tenantId); (2) salt the hot key into k sub-keys and fan out reads, accepting the read amplification; (3) put the hot key behind a cache or an aggregation buffer so the partition sees one write per interval instead of ten thousand; (4) give the biggest tenants their own dedicated partitions or their own cell. Note what none of these do: they do not preserve per-key ordering across the split, which is why salting a Kafka partition key is a correctness decision, not a tuning knob.

Partition count is a one-way door (mostly)

In Kafka the partition count of a topic determines the maximum consumer parallelism in a classic consumer group — one partition is consumed by at most one member — and it determines key ordering, because partition = hash(key) % partitions. Increasing the count is allowed but it rehashes future records, so a key that lived in partition 3 may start landing in partition 7 while its history stays in 3: ordering per key is broken across the change and any stateful consumer keyed by that value now has state in the wrong place. That is why the standard advice is to over-provision partitions modestly at creation (enough for 2–3× your expected peak consumer count) and never to decrease, which Kafka does not support at all. The 2026 nuance worth knowing: share groups (KIP-932, production-ready in Kafka 4.2, February 2026) let many consumers read the same partition cooperatively, so partition count no longer caps consumer parallelism for workloads that do not need per-key ordering — the first real relaxation of this constraint in Kafka's history.

Placement: cells, blast radius and co-location

Above partitioning sits placement, which is where lead-level answers live. Two ideas to have ready. Co-location: put data that is read together in the same partition — orders keyed by customerId means one customer's whole history is one partition read, which is why DynamoDB single-table design exists and why "join across shards" is a smell. Cell-based architecture: rather than one large partitioned system serving everyone, run many independent, identical cells, each with its own full stack and a fixed set of tenants, plus a thin routing layer. Each cell is a blast radius: a poison-pill message, a bad deploy or a runaway tenant takes down 1/N of customers instead of all of them, and you get a natural deployment canary. The cost is real — more infrastructure, cross-cell operations become migrations, and the routing layer is now your most critical component — so it earns its place when you have many tenants and a strong isolation requirement, not by default.

Interview trap · choosing the partition key for ordering you do not need

Candidates routinely key a Kafka topic by something coarse — tenantId, or worse a constant — to "keep everything in order". Two things go wrong. First, a single key means a single partition means a single consumer: you have capped throughput at one consumer's speed and no amount of scaling helps, and the symptom appears months later as unbounded lag on the biggest tenant. Second, you have bought ordering you do not actually need. Ordering is almost never required globally; it is required per entity, and the right key is the finest-grained identity whose events must be sequential — usually the aggregate id (orderId, accountId), not the tenant. The senior version of the answer names both directions: too coarse and you lose parallelism, too fine and you lose the ordering the consumer's state machine depends on, so the key is the aggregate boundary — and if you genuinely need no ordering, say so and use share groups or a queue instead of pretending.

Try it · manufacture and then fix a hot partition

1. Create a Kafka topic with 6 partitions and produce 100k messages where 90% carry the key "tenant-1". Run kafka-consumer-groups --describe and look at per-partition lag while a 6-member group consumes.

2. Change the key to tenant-1#{0..9} (salted) and re-run. Then ask yourself what broke, and write down which consumer logic is no longer safe.

Expected outcome

1. One partition holds ~90k messages and five hold ~2k each. Five consumers are idle while one is saturated, and total throughput equals one consumer's throughput — adding members changes nothing, because a partition has exactly one owner in a classic consumer group. This is the single most common Kafka scaling incident.

2. Lag spreads evenly and throughput rises roughly 6×. What broke: events for tenant-1 are no longer ordered relative to each other, so any consumer that maintains per-tenant state (running balances, state machines, "last write wins" upserts) is now racing. The honest fix is either to salt only for genuinely order-independent event types, or to move to share groups (Kafka 4.2+) where ordering is explicitly not offered and delivery is per-record.

Interview Q&A · partitioning

How do you choose a partition key?

I start from two requirements and let them intersect. The first is the ordering requirement: what is the smallest scope within which events must be sequential? That is almost always an aggregate — an order, an account, a device — and it sets the maximum granularity. The second is the distribution requirement: the key must produce enough distinct, evenly-loaded values to spread across partitions, which rules out tenant ids in a system with one dominant tenant. Then I check the read path: keys that are read together should land together. If the two requirements conflict — you need per-tenant ordering and one tenant is 80% of traffic — that is a design conversation about whether ordering is really needed, not a tuning exercise.

Why not just use hash(key) % N?

Because N becomes unchangeable. Increasing from 6 to 8 partitions remaps roughly 75% of keys, so every key's history is in one place and its future is in another, which breaks per-key ordering and every stateful consumer keyed on it. Consistent hashing exists precisely to bound that: adding a node moves about 1/n of the keys and leaves the rest alone. Kafka does use modulo, which is why partition count is treated as near-permanent there and why you over-provision at creation rather than growing later. Where I control the mapping myself — a sharded cache, a custom router — I use consistent or rendezvous hashing with virtual nodes.

What is a hot partition and what are your options?

A partition receiving disproportionate traffic because one key or a small set of keys dominates. The framing that matters: a partition is the unit of ownership, so no amount of horizontal scaling helps a single hot key. Options in order: refine the key so the hot entity splits naturally; salt the key into k buckets and fan out on read, accepting read amplification and the loss of per-key ordering; absorb the writes before they reach the partition with a cache, a batch or a pre-aggregation window; or isolate the whale onto dedicated capacity. Which one I pick depends entirely on whether ordering for that key is load-bearing, so that is my first question back.

How many partitions should a Kafka topic have?

Enough for peak consumer parallelism with headroom, and not more. I size from target throughput divided by what one consumer instance can sustain, then multiply by two or three so a future scale-up does not require a repartition. Against that I weigh the costs, which are real: every partition is open file handles and memory on brokers, a unit of replication traffic, and a contributor to end-to-end latency on rebalance and on failover. KRaft raised the practical ceiling substantially — clusters with hundreds of thousands of partitions are now workable where ZooKeeper-era guidance capped around 200k per cluster — but "we can" is not "we should". And since Kafka 4.2 I would also ask whether the workload needs partition-level ordering at all; if it does not, share groups let me scale consumers past the partition count and the sizing question softens.

Local versus global secondary indexes on a partitioned store?

A local secondary index lives inside each partition and is updated in the same write, so it is consistent and cheap, but a query on it must fan out to every partition and gather — fine for a small number of partitions, terrible at a thousand. A global secondary index is itself partitioned by the index key, so a query hits exactly one partition, but maintaining it is a cross-partition write, which means it is either asynchronous and eventually consistent (DynamoDB's GSIs) or it costs a distributed transaction. My rule: local index when the query always carries the partition key, global when the query is genuinely by another dimension — and if a global index would need to be strongly consistent, that is usually a signal to model a second table maintained by the same event stream rather than to fight the store.

What is a cell-based architecture and when is it worth it?

Instead of one large system partitioned internally, you run N complete, independent copies — each with its own database, brokers and compute — and route each tenant to exactly one cell. The point is blast radius: a poison message, a bad migration, a runaway tenant or an overload event affects one cell's customers, not all of them, and cells double as a deployment canary since you can roll a change to cell 1 first. It is worth it when you have many independent tenants, a hard isolation or compliance requirement, and enough scale that the duplicated infrastructure is a small fraction of the total. It is not worth it for a handful of large tenants or when the product needs cross-tenant queries, because those become cross-cell operations and you have re-created the coordination you were avoiding.

How do you rebalance a partitioned system without downtime?

By making ownership transfer explicit and incremental. The standard shape is: mark the partition as moving, replicate its data to the new owner while the old owner still serves, catch up the delta from a change log, then flip routing atomically with a short write pause on that partition only, and finally clean up the source. Two details matter more than the algorithm. First, routing must have a single source of truth that both sides read, or you get double ownership — this is where a fencing token or an epoch belongs. Second, the move must be throttled and resumable, because a rebalance that saturates the network during peak is a self-inflicted outage; every mature system exposes a rate limit and I would insist on it being set before the first move, not after.

What is the relationship between partitioning and multi-tenancy?

Tenancy is usually the first partitioning dimension people reach for and often the wrong one alone, because tenant sizes follow a power law: your largest tenant may be a thousand times your median, so tenant-keyed partitions are guaranteed to be skewed. What works is a hybrid — partition by tenant for isolation and locality, but allow large tenants to be split across multiple partitions or promoted to dedicated capacity, with the routing layer holding the exceptions. The operational payoff of tenant-aware partitioning is worth naming: per-tenant quotas, per-tenant lag metrics, and the ability to pause or replay one tenant's traffic during an incident without touching anyone else.

Your consumer group has 12 members and the topic has 6 partitions. What happens?

Six members are assigned a partition each and six sit idle as hot standbys — they consume nothing and cost you money, though they do reduce failover time since a rebalance can hand them work immediately. Nothing is broken, but the deploy that scaled to 12 achieved nothing for throughput, which is exactly the surprise this question is testing. The remedies are to increase partitions (with the rehash caveat), to reduce members, or — since Kafka 4.2 — to use a share group, where all 12 members can consume the same 6 partitions cooperatively with per-record acknowledgement, at the cost of giving up partition-order guarantees.

How would you migrate a system from one partition key to another?

As a dual-write-and-backfill migration with an explicit cutover, never as a big-bang. Concretely: stand up the new partitioning as a second destination; start writing to both, with the new one keyed correctly; backfill history into the new layout in the background, throttled; run a comparison job that samples both and reports divergence; move reads over per tenant or per cell behind a flag, watching error and latency; then stop writing the old one and, only after a retention period, delete it. The parts people underestimate are the comparison job — without it you cut over on faith — and the ordering discontinuity during backfill, which for event data usually means the new stream must be rebuilt from a source of truth rather than copied record by record.

06 Brokers: queues and logs

Docs: Kafka documentation · RabbitMQ documentation · NATS JetStream

Two data structures have historically defined the broker landscape, and the interview question "Kafka or RabbitMQ?" is really "queue or log?". A queue is a shared work list: the broker tracks per-message state, a message is delivered to one consumer, acknowledged, and deleted. A log is an append-only file: the broker tracks nothing per message, consumers track their own position (offset), messages are retained by policy and any number of independent readers can read the same record at their own pace.

Why that one difference explains everything else

Because the broker in a queue owns per-message state, it can do things a log cannot: per-message acknowledgement and redelivery, per-message TTL, priorities, and dead-lettering an individual poison message while everything else flows. Because a log owns nothing per message, it gets what a queue cannot: replay from any point, multiple independent consumer groups over the same data, sequential disk I/O with zero-copy transfer (which is why a single Kafka broker sustains hundreds of MB/s), and retention as a first-class feature — the stream is the source of truth for a while. Nearly every other difference you can name follows from those two facts, and saying it that way is far stronger than reciting a feature matrix.

RabbitMQ's model: exchanges do the routing

Producers publish to an exchange with a routing key; bindings decide which queues receive a copy. direct matches the routing key exactly, topic matches patterns (order.*.eu), fanout copies to everything bound, headers matches on attributes. That indirection is RabbitMQ's real strength: the producer knows nothing about consumers, and adding a new consumer is a binding, not a code change. In 2026 the queue-type story has settled: quorum queues (Raft-replicated, the durable default since 4.0 removed classic mirrored queues in September 2024), streams (an append-only log type for replay and fan-out — RabbitMQ's answer to Kafka-shaped workloads), and classic queues for transient, non-replicated work. RabbitMQ 4.3 (April 2026) closed the biggest remaining gaps in quorum queues: 32 strict priority levels, a native delayed-retry mechanism that sets a message aside instead of rewriting it, and roughly 50% less memory per message up to 32 KiB — which together retire the old rabbitmq-delayed-message-exchange plugin, now deprecated and archived.

The line is blurring, in both directions

The most current thing you can say about this topic in 2026: the queue/log distinction is eroding from both sides. Kafka added share groups — KIP-932, preview in 4.0/4.1, production-ready in 4.2 (17 February 2026) — which give a Kafka topic genuine queue semantics: consumers in a share group cooperatively read the same partitions, acknowledge individual records (ACCEPT, RELEASE, REJECT, and since 4.2 RENEW for long processing), and the broker counts delivery attempts, archiving a record after the limit (default 5) so a poison message cannot be redelivered forever. Meanwhile RabbitMQ added streams with offset-based, replayable consumption and, in 4.2 (October 2025), SQL-like server-side stream filtering. NATS JetStream sits in the middle by design — a stream plus consumers with either an explicit ack workqueue policy or a replayable cursor — and in 2.12 and 2.14 (30 April 2026) it added atomic batch publishing, a server-side message scheduler for delayed and cron-style delivery, and counter CRDT streams.

The consequence for a design discussion is that "which broker" is now less about capability and more about operational fit: retention and replay requirements, the ordering scope, whether you need per-message dead-lettering, the team's operational experience, and — increasingly the decisive factor — whether you run it or a cloud runs it for you.

Interview trap · "Kafka because it's fast"

Throughput is almost never the reason to choose Kafka, and saying so signals that you have not run either system. RabbitMQ moves tens of thousands of messages a second per node, which is more than most systems will ever need; Kafka's advantage is that it moves millions and keeps them. The real selection criteria, in the order I would ask them: do you need replay? (a new consumer reading two years of history, rebuilding a projection, reprocessing after a bug — this is the honest reason to choose a log). What is the ordering scope? (per-entity ordering is nearly free in a log and expensive in a queue). Do you need per-message dead-lettering and priorities? (historically a queue's home turf, now available in Kafka via share groups). How many independent consumers will this data have in three years? (fan-out is free in a log, a new binding-plus-queue in RabbitMQ). And the practical one: what does your team already operate at 3 a.m.? A well-run RabbitMQ beats a badly-run Kafka every night of the week.

Try it · feel the difference

1. Publish 10,000 messages to a RabbitMQ queue and consume them. Then start a second consumer application that also wants all 10,000. Now do the same in Kafka with a second consumer group. Time how long each takes to set up and what data the newcomer can see.

2. In Kafka, make one record poison (throw on a specific value) with a classic consumer group and watch the partition. Then repeat with a share group (kafka-console-share-consumer, Kafka 4.2+) and watch the delivery count.

Expected outcome

1. In RabbitMQ the messages are gone — consumed and deleted — so the second application can only receive future messages, and you must add a binding and a queue before the traffic arrives. In Kafka the second group sets auto.offset.reset=earliest and reads all 10,000 immediately, with no change on the producer side and no coordination. That asymmetry is the single most important practical difference, and it is why event-carried architectures gravitate to logs.

2. With a classic consumer group the poison record blocks its partition: the consumer retries forever or you skip it manually by seeking past the offset, and everything behind it waits. With a share group the record is redelivered, its broker-side delivery count increments, and after the configured limit (default 5) it moves to the Archived state while the rest of the partition keeps flowing — queue-style poison handling inside a log.

Interview Q&A · brokers

Kafka or RabbitMQ — how do you actually decide?

I decide on replay, ordering scope and fan-out, not on throughput. If the data has multiple independent consumers now or plausibly later, if anyone will need to reprocess history after a bug or to build a new projection, or if the ordering requirement is per-entity and strict, that is a log and I reach for Kafka. If the work is a task queue — one consumer does the job, the message is then meaningless, individual messages can poison and must be dead-lettered, and I want priorities and per-message TTL — that is a queue and RabbitMQ is simpler to run and reason about. In 2026 I would add the caveat that both have moved toward the middle: Kafka 4.2 made share groups production-ready and RabbitMQ has streams, so the capability argument is weaker than it was and operational familiarity carries more weight.

Explain the RabbitMQ exchange model and why the indirection exists.

Producers publish to an exchange with a routing key and never name a queue; bindings from exchanges to queues decide who gets a copy. Direct matches the key exactly, topic matches wildcard patterns, fanout copies to all bound queues, headers matches on attributes. The indirection means producers and consumers are genuinely decoupled: a new consumer is a new queue and binding, added at runtime with no producer change and no redeploy. It also means the routing topology is operational state you must manage deliberately — I treat exchanges, queues and bindings as declarative infrastructure defined in code or in the definitions file, because a topology that exists only because someone once clicked in the management UI is an outage waiting for a rebuild.

What are quorum queues and why did classic mirrored queues go away?

Quorum queues replicate via Raft: a leader and followers, writes committed by a majority, deterministic failover, and no way for a minority to accept writes. Classic mirrored queues used a leader-plus-mirrors scheme whose failure semantics were genuinely unsafe — under partition and requeue they could lose or duplicate confirmed messages, and recovery required the operator to choose a partition-handling policy. They were deprecated in 3.x and removed in RabbitMQ 4.0 (September 2024), and 4.3 (April 2026) finished the job by removing Mnesia entirely in favour of Khepri, so the whole system is now Raft-backed. The practical trade-off with quorum queues is that they are memory- and disk-hungrier per message and were historically weaker on priorities and delays — which is exactly what 4.3 addressed with 32 priority levels, native delayed retry and about half the memory per message up to 32 KiB.

What are Kafka share groups and what problem do they solve?

Share groups, introduced by KIP-932 and production-ready in Kafka 4.2 as of February 2026, let multiple consumers read the same partitions cooperatively rather than each partition having exactly one owner. Records are acknowledged individually — accept, release, reject, or renew if processing takes longer — and the broker keeps a delivery count per record, archiving it after a limit (default 5) so a poison message cannot loop forever. The two problems it solves are the ones that used to force a queue into a Kafka shop: consumer parallelism capped by partition count, and one bad record blocking a whole partition. The cost is explicit and worth stating: share groups give up partition ordering. You use them for genuinely independent work items, not for per-entity state machines.

How does a consumer group rebalance work, and what changed with KIP-848?

Classically, a group coordinator on a broker tracked membership, and every membership change triggered a stop-the-world rebalance: all members revoked their partitions, one member (the leader) computed the assignment, and everyone rejoined — so one rolling deploy of a 30-instance service caused repeated global pauses. KIP-848, GA in Kafka 4.0, moves assignment to the broker and makes it incremental: a joining member is granted partitions as they are released, so members that are not affected keep consuming. It is enabled server-side by default but clients must opt in with group.protocol=consumer, which is the detail people miss — upgrading the broker alone changes nothing. The observable win is that deploys and scale-ups stop producing lag spikes, which used to be the top source of "why did latency triple for 40 seconds" tickets.

When would you use NATS instead of Kafka or RabbitMQ?

When the latency budget is tight, the operational footprint must be small, or the topology is edge-to-cloud. Core NATS is fire-and-forget pub/sub with microsecond-scale latency and a single small binary; JetStream adds persistence, replay and work queues on top when you need them, so you can start cheap and add durability per stream rather than per cluster. It is also the strongest of the three for many-to-many request/reply and for hierarchical deployments with leaf nodes. What you give up is ecosystem: Kafka's connector, stream-processing and schema-registry ecosystem is far deeper, and in a shop that already runs Kafka the marginal cost of one more topic is much lower than the cost of a second messaging system. NATS 2.14 (April 2026) narrowed the gap on scheduling — server-side delayed and cron-style delivery — which used to be a reason to keep RabbitMQ around.

Push or pull: which model do you want and why?

Pull, for anything with variable processing cost, because the consumer decides when it is ready and backpressure is automatic — Kafka's poll() cannot overwhelm you. Push has lower latency and is simpler for the consumer, but it needs an explicit flow-control mechanism or the broker will bury a slow consumer; that is precisely what RabbitMQ's basic.qos prefetch is, and leaving prefetch unbounded is the classic RabbitMQ mistake, because one consumer grabs the whole queue into memory and the others starve. In practice most modern systems are pull with long polling, which gets pull's backpressure with most of push's latency, and that is what I would design toward.

Do you still need a broker if you have gRPC and a service mesh?

They solve different problems. Synchronous RPC is right when the caller needs the answer to continue and the callee's availability is genuinely part of the operation. A broker is right when you want temporal decoupling — the consumer can be down for an hour and nothing is lost — buffering against load spikes, fan-out to consumers the producer does not know about, and replay. The mistake I see in both directions: teams doing RPC where an event would remove a hard dependency and improve availability arithmetic, and teams putting a broker in the middle of a request/response interaction, which adds latency and creates a correlation-id state machine nobody wanted. My rule of thumb is that a broker belongs where the producer does not need an answer, and RPC belongs where it does.

How do you handle a message larger than the broker's limit?

By not putting it in the broker. Kafka's default max.message.bytes is 1 MB, and raising it is a whole-cluster performance decision because it affects replication, page cache and consumer memory. The standard pattern is claim check: write the payload to object storage, publish a message containing the key, a checksum and enough metadata to route and to decide relevance, and have the consumer fetch on demand. The details that make it work in practice are lifecycle (the blob must outlive the topic's retention or the replay is broken), access control on the bucket matching the topic's, and idempotent uploads so a producer retry does not orphan objects. If the payloads are large because the event is carrying entire entities, that is also worth challenging — often the right fix is a thinner event plus a query.

Your team wants to run its own Kafka instead of using a managed service. How do you evaluate that?

I make the operational cost explicit rather than arguing about principle. Running Kafka means owning broker upgrades and the KRaft migration path, partition rebalancing and disk pressure, quota management, certificate rotation, and a 3 a.m. runbook for under-replicated partitions — and doing that well is roughly a part-time engineer forever, plus a lumpy amount of learning in the first year. Managed costs more per byte and gives up some tuning and some version agility. So the decision comes down to scale, regulatory constraints and headcount: at low volume, managed is cheaper than the engineer; at high volume with an existing platform team, self-hosting can be dramatically cheaper. What I insist on either way is that the choice is revisited with numbers, and that self-hosting comes with named owners and a tested disaster-recovery drill, not just enthusiasm.

07 Delivery guarantees and idempotency

Docs: Kafka message delivery semantics · Idempotent requests (Stripe)

Three guarantees are on offer and only two of them are real. At-most-once: acknowledge before processing, so a crash loses the message. At-least-once: process, then acknowledge, so a crash between the two redelivers it. Exactly-once: the thing everyone wants, which cannot exist across an arbitrary network — the Two Generals problem says a sender and receiver cannot both become certain about a single message with a lossy channel. What does exist is effectively-once: at-least-once delivery plus an idempotent or transactional consumer, so the observable effect happens once even though the message arrives more than once.

Say that clearly and the rest of this unit is mechanics. Say "we use exactly-once" without qualification and you will be asked to explain how the acknowledgement of the acknowledgement is acknowledged.

Where the duplicate comes from

Walk the round trip in the running example. The producer sends OrderPlaced and the broker persists it, but the ack is lost; the producer retries and there are now two copies. The consumer reads it, ships the order, and crashes before committing the offset; on restart it reads the same record and ships again. A rebalance revokes a partition mid-batch and another member re-processes the uncommitted tail. Every one of those is normal operation, not a bug. Duplicates are a property of the transport; uniqueness is a property of your storage.

-- The consumer-side dedup that makes at-least-once safe. One transaction, two effects.
BEGIN;

INSERT INTO processed_messages (message_id, consumer, processed_at)
VALUES ($1, 'shipping', now())
ON CONFLICT (message_id, consumer) DO NOTHING;

-- 0 rows means we have already handled it: commit and acknowledge without doing the work again.
-- 1 row means we own it, so the effect goes in the SAME transaction:
INSERT INTO shipments (order_id, address, status)
VALUES ($2, $3, 'pending')
ON CONFLICT (order_id) DO NOTHING;

COMMIT;

Two details make this correct rather than merely plausible. The dedup record and the effect must be in one transaction — write the dedup row first and crash, and you have swallowed a message you never processed. And the dedup table needs a retention policy with an index on processed_at, because it grows forever otherwise; the window must exceed the maximum plausible redelivery delay, which for a topic you might replay from is far longer than people assume.

Natural idempotency beats bookkeeping

The best consumers need no dedup table because the operation is naturally idempotent. SET status = 'shipped' is idempotent; UPDATE balance = balance - 10 is not. An upsert keyed by the entity is idempotent; an insert into an append-only table is not. Sending an email is not idempotent, which is why the email service should key on (orderId, templateId) and refuse a second send. When you can express the handler as "make the world look like this" rather than "apply this delta", duplicates stop mattering — and that reframing is worth more in a design discussion than any broker feature. Where deltas are unavoidable (money, counters), carry a version and make the write conditional: UPDATE ... WHERE version = $expected, which converts a duplicate into a no-op with zero extra tables.

What Kafka's "exactly-once" actually gives you

Kafka has two distinct features and candidates routinely conflate them. The idempotent producer (enable.idempotence=true, the default since Kafka 3.0) attaches a producer id and a per-partition sequence number so the broker discards a duplicate caused by a producer retry: it removes duplicates from the network, per partition, for the lifetime of that producer session. Transactions (transactional.id, initTransaction/beginTransaction/commitTransaction) let you atomically write to several partitions and commit consumer offsets, which makes a read-process-write pipeline atomic — the basis of Kafka Streams' processing.guarantee=exactly_once_v2. Consumers must set isolation.level=read_committed to hide aborted records.

The boundary is the point. Kafka's exactly-once holds within Kafka. The moment your handler calls a payment API, writes to Postgres or sends an email, the transaction cannot cover it and you are back to at-least-once with an idempotent consumer. So the honest framing for an interview is: "exactly-once is available inside a Kafka-to-Kafka pipeline and nowhere else; everywhere else I make the consumer idempotent."

Where the acknowledgement goes matters more than the mode

Almost every "we lost messages" incident is an acknowledgement in the wrong place. Auto-commit in Kafka (enable.auto.commit=true) commits on a timer, during poll(), for records you may not have finished — a crash then skips them, silently, which is at-most-once wearing an at-least-once costume. Acknowledging a RabbitMQ delivery before the handler returns does the same. The rule is simple and worth stating as a rule: acknowledge after the effect is durable, never before, and accept the duplicates that follow. If a duplicate is more expensive than a loss — a rare but real case, such as a low-value notification — choose at-most-once deliberately, write it in the code comment, and make sure everyone knows.

Interview trap · "we use exactly-once, Kafka supports it"

This is the highest-frequency trap in messaging interviews and it has a specific follow-up waiting: "your consumer charges a credit card — walk me through how the transaction covers that." It does not. Kafka's transactional guarantee spans Kafka partitions and Kafka's own offset topic; it cannot enrol an external HTTP call or another database. There are three acceptable answers and they are all worth having. (1) Make the external effect idempotent with a key you derive deterministically from the message — idempotency-key: order-4711-charge — so the provider dedups for you. (2) Use the outbox pattern so the only thing your transaction must cover is your own database (unit 09). (3) If the external system offers nothing, record intent before the call and reconcile after — the Pending state from unit 01. A candidate who says "exactly-once end to end is not achievable, so I design for effectively-once and here is where the dedup lives" is immediately reading as senior.

Try it · earn a duplicate, then defeat it

1. Write a Kafka consumer that processes a record by appending to a file, then commits offsets. Kill it (SIGKILL) between the append and the commit — a sleep in between makes this easy. Restart and count the lines.

2. Now make the effect idempotent: write to a keyed store using the record's topic-partition-offset as the key, or a business id if you have one. Repeat the kill. Then run the same experiment with auto-commit enabled and kill it just after a commit but before processing.

Expected outcome

1. You get the record twice. This is at-least-once behaving exactly as documented, and being able to say "I have reproduced this in ten lines" is a much better interview answer than quoting the guarantee.

2. With the keyed write, the second delivery overwrites identically and the observable state is unchanged: effectively-once. With auto-commit you get the opposite failure — a record that was committed but never processed, gone with no error anywhere. Seeing both failure directions in one afternoon is the fastest way to internalise why acknowledgement placement is the decision, not the delivery mode.

Interview Q&A · delivery and idempotency

Explain at-most-once, at-least-once and exactly-once.

At-most-once acknowledges before doing the work, so a crash loses the message and you never duplicate. At-least-once does the work first and acknowledges after, so a crash between them redelivers and you may duplicate. Exactly-once, in the sense of "the message crosses the network precisely once", is impossible with a lossy channel — that is the Two Generals result. What is achievable is effectively-once: at-least-once transport plus a consumer whose effect is idempotent or transactional, so the observable outcome happens once. In practice I pick at-least-once for everything that matters and spend the effort on making the handler idempotent, because that is a property I control and the network is not.

How do you make a consumer idempotent?

In order of preference: make the operation naturally idempotent — an upsert keyed by the entity, a state assignment rather than a delta; make it conditional on a version so a repeat is a no-op; or, if neither is possible, keep a dedup table keyed by message id and consumer name and write it in the same transaction as the effect. The last one has two traps worth naming: the dedup row must not be committed separately from the effect, or a crash between them swallows the message forever; and the table needs a retention policy sized to the longest redelivery window you can experience, which includes any replay you might do, not just the broker's redelivery timer.

What exactly does Kafka's exactly-once semantics cover?

Two features. The idempotent producer, on by default since 3.0, attaches a producer id and per-partition sequence numbers so the broker drops duplicates caused by producer retries within a session. Transactions let a producer write to multiple partitions and commit consumer offsets atomically, so a read-process-write loop is all-or-nothing, and consumers set isolation.level=read_committed to skip aborted records. Together they give exactly-once within Kafka — which is what Kafka Streams' exactly_once_v2 uses. What they cannot cover is any side effect outside Kafka: an HTTP call, an email, a write to another database. So my answer in a design review is always "exactly-once inside the pipeline, idempotent handlers at every edge".

What makes a good idempotency key?

Deterministic, unique per logical operation, and derived from something stable — not generated at retry time. For an inbound API I let the client supply it and reject requests without one on any mutating endpoint. For a message handler I derive it from the business identity plus the action (order-4711-charge) rather than from the delivery, because topic-partition-offset changes if the message is republished or the topic is rebuilt, and then a genuine duplicate slips through. I also store the response alongside the key, so a retry returns the original result rather than a 409 the caller has to interpret — that is what makes the pattern pleasant for clients, and it is what Stripe does.

A duplicate is worse than a loss for one of your message types. What do you do?

I say so explicitly and design for at-most-once on that path — acknowledge first, process after — and I document the choice in the handler, because the next engineer will otherwise "fix" it. But I would push back first, because the case is rarer than people think: usually the real requirement is "the user must not see two notifications", which is a dedup at the point of delivery rather than a delivery-mode change. Suppressing a second push notification with a five-minute key is cheap and keeps the durability of at-least-once. I reserve genuine at-most-once for things where the value is low and the volume is high — telemetry samples, cache invalidations that will be repeated anyway.

Where should the offset commit happen relative to the work?

After the work is durable, always, and never on a timer that is unaware of the work. Kafka's auto-commit fires during poll() on an interval, so it can commit records still in flight, which turns at-least-once into silent at-most-once. I disable it and commit explicitly after the batch is persisted, usually with commitSync at batch boundaries and a final commit on shutdown and on partition revocation. The subtle part is the rebalance listener: on revocation I must finish or abandon in-flight work and commit what is done, otherwise the new owner reprocesses a tail that my instance is still writing, and two consumers race on the same records.

How do SQS FIFO and Azure Service Bus handle duplicates?

Both offer producer-side deduplication over a window rather than true exactly-once. SQS FIFO deduplicates on a message deduplication id within a five-minute window, and orders within a message group id; the trade-off is throughput limits relative to standard queues. Service Bus offers duplicate detection over a configurable window keyed on the message id, plus sessions for ordered processing. In both cases the guarantee is bounded by the window: a redelivery or a producer retry outside it produces a duplicate. So I treat them as a useful first line that removes most duplicates cheaply, and still make the consumer idempotent for the long tail — particularly for anything that can be replayed or reprocessed hours later.

Your handler is idempotent but the message is processed twice concurrently. Is that safe?

Not automatically — idempotency and concurrency are different properties. Two concurrent executions of an upsert can interleave into a lost update, and two dedup-table inserts can both see zero rows if the read and write are not atomic. The fix is to rely on the database's atomicity rather than on application logic: a unique constraint with ON CONFLICT DO NOTHING, a conditional update on a version, or a row lock taken by the first statement in the transaction. Where the handler touches multiple resources I would also serialise per key — process each entity's messages on a single lane (unit 08) — so concurrent duplicates cannot arise in the first place. This is a good question to answer with "idempotent and serialised per key", because most candidates only cover one half.

What is the poison message problem and how does the guarantee interact with it?

A poison message is one that always fails: bad schema, a reference to a deleted entity, a bug for that specific shape. Under at-least-once the broker keeps redelivering it, so with a classic Kafka consumer group it blocks its partition forever and lag grows behind it, while with a queue it consumes redelivery attempts and eventually hits the delivery limit. The controls are a delivery limit plus a dead-letter destination, which RabbitMQ gives you with x-delivery-limit and a DLX, and which Kafka historically did not — hence retry topics and hand-rolled skip logic. Kafka 4.2's share groups changed that: the broker counts deliveries and archives a record after the limit, defaulting to 5, so a poison record no longer blocks the partition. Whatever the mechanism, the operational rule is the same: a DLQ with no alert and no owner is a data-loss bucket, not a safety net.

How do you convince a team to add idempotency when "we've never seen a duplicate"?

I show them one. It usually takes an hour: reproduce a redelivery by killing a consumer between the effect and the commit, or by forcing a rebalance mid-batch during a deploy, and point at the two rows. If that is not available I go to the data — a query for duplicate business effects (two shipments for one order, two identical charges within a minute) almost always finds a handful, and the reason nobody noticed is that support silently refunded them. Then I make the fix small: idempotency is usually one unique index and one ON CONFLICT DO NOTHING, not an architecture. Framing it as "a one-line constraint that makes deploys safe" wins where "the network is unreliable" does not.

08 Ordering, consumer groups and backpressure

Docs: Kafka consumer configuration · KEDA Kafka scaler

Throughput and ordering are in direct tension, and every consumer design is a position on that trade-off. Strict ordering means one thing happens at a time; parallelism means several do. The reason messaging systems feel complicated is that they let you choose the scope of ordering — global, per partition, per key, or none — and each scope has a different maximum parallelism.

The scopes, from most to least expensive

  • Global order — one partition, one consumer, no parallelism. Almost never a real requirement; when someone asks for it, they usually mean per-entity order.
  • Per-partition order — what Kafka guarantees. Parallelism equals partition count.
  • Per-key order — what you actually want. Achieved by keying the partition, and, within a consumer, by striping work onto lanes by key so a slow message for key A does not delay key A's successor but does not block key B either.
  • No order — a work queue. Maximum parallelism, and the model RabbitMQ's competing consumers and Kafka's share groups give you.

The pattern worth having ready is per-key parallelism inside one partition: read a batch, group it by key, process groups concurrently, and commit only the contiguous prefix that is complete. It multiplies throughput without breaking the ordering the domain actually needs, and it is the answer to "your partition is the bottleneck but you cannot add partitions".

// Per-key lanes: parallel across keys, strictly sequential within a key, then a safe commit.
var batch = consumer.Consume(TimeSpan.FromMilliseconds(500));
var lanes = batch.GroupBy(r => r.Message.Key);

await Parallel.ForEachAsync(lanes, new ParallelOptions { MaxDegreeOfParallelism = 16 },
    async (lane, ct) =>
    {
        foreach (var record in lane)          // sequential within the key - this is the guarantee
            await HandleAsync(record, ct);
    });

// Commit only the contiguous prefix of completed offsets. Committing the max offset would
// silently skip a gap if one lane failed - the classic parallel-consumer data-loss bug.
var safe = HighestContiguousCompleted(batch);
consumer.Commit(safe);

Head-of-line blocking, and why a DLQ is a throughput feature

In a strictly ordered stream, one slow or failing message stops everything behind it. That is head-of-line blocking, and it is the reason a partition with a poison message accumulates millions of records of lag while five other partitions are idle. There are exactly three ways out and you should be able to name all three: skip the message (seek past it — fast, and you have now lost it unless you captured it), park it (move it to a retry topic or a dead-letter queue and continue — the standard answer, and why DLQs are as much about throughput as about error handling), or relax the ordering (share groups, or per-key lanes if the blockage is on one key). Retrying in place with backoff is a fourth option that is only correct when the failure is genuinely transient and short; otherwise it is head-of-line blocking with extra steps.

Backpressure: the knob is prefetch

Backpressure means a fast producer cannot bury a slow consumer, and in messaging it is usually a single setting. In RabbitMQ it is basic.qos(prefetch_count): the maximum unacknowledged deliveries per consumer. Leave it unbounded and the broker pushes the entire queue at the first consumer that connects, which blows up its memory and starves its peers; set it to 1 and you pay a network round trip per message. A workable starting point is the number of concurrent handlers times two, tuned by watching consumer utilisation. In Kafka the equivalents are max.poll.records and max.partition.fetch.bytes, plus the constraint that binds them: max.poll.interval.ms (5 minutes by default). If processing a batch takes longer than that, the coordinator declares the member dead and rebalances, your commit fails, and the batch is reprocessed — a feedback loop that looks like "the consumer keeps restarting" and is really "the batch is too big for the work".

Scaling on lag, and the trap inside it

Consumer lag — records behind the log end — is the right autoscaling signal, and KEDA's Kafka and RabbitMQ scalers exist for exactly this. Two cautions to voice. First, lag is a stock, not a rate: a large but shrinking lag needs patience, a small but growing lag needs capacity, and scaling on the absolute number produces oscillation. Prefer the derivative, or better, the projected drain time. Second, in a classic consumer group scaling past the partition count achieves nothing (unit 05), so the scaler's maximum must be pinned to the partition count or you pay for idle pods — and every scale event triggers a rebalance, so an aggressive scaler can spend more time rebalancing than consuming. Static membership (group.instance.id) plus the KIP-848 protocol removes most of that pain, and is the single highest-value consumer configuration change most teams have not made.

Interview trap · "we just add more consumers"

The reflex answer to lag, and it is wrong three different ways. (1) In a classic Kafka consumer group, members beyond the partition count get nothing — throughput is unchanged and you have added rebalance churn. (2) If the consumer is slow because it calls a downstream service, more consumers means more concurrent load on the thing that was already the bottleneck; you have converted your lag into their outage. That is the moment to talk about rate limits and bulkheads rather than replicas. (3) If ordering matters, more consumers per partition breaks it, silently, and the corruption shows up much later as inconsistent state. The strong answer walks the diagnosis instead: is the lag on all partitions or one (skew), is the handler CPU-bound or waiting (profile it), is the arrival rate genuinely up (then it is capacity), and only then decide between more partitions, per-key lanes inside the consumer, share groups, or fixing the downstream.

Try it · induce a rebalance loop

1. Set max.poll.records=500 and make your handler sleep 2 seconds per record. Watch what happens to group membership and to the offsets you thought you committed.

2. Fix it two ways and compare: lower max.poll.records so a batch finishes inside max.poll.interval.ms, versus keeping the batch and processing it on a background thread while calling poll() with pause()/resume() to hold the assignment.

Expected outcome

1. The member misses max.poll.interval.ms, the coordinator removes it, a rebalance reassigns the partition, and the commit fails with CommitFailedException because the member no longer owns it — so the whole batch is reprocessed by someone else, forever. It looks like a crash loop and it is a configuration mismatch.

2. Both work; they trade differently. Smaller batches are simpler and give lower per-record latency but more round trips. The pause/resume approach keeps large fetches and decouples processing from polling, which is what parallel-consumer libraries do — at the cost of you owning the offset bookkeeping, including the contiguous-prefix rule from the code above.

Interview Q&A · ordering and flow

What ordering guarantee does Kafka give, exactly?

Strict order within a partition, and nothing across partitions. Records with the same key go to the same partition under the default partitioner, so you get per-key order as a consequence — provided the partition count does not change and the producer preserves it. That last part is the detail: with retries and multiple in-flight requests, a failed batch could historically be reordered behind a later one, which is why max.in.flight.requests.per.connection mattered. With enable.idempotence=true — the default since 3.0 — the broker enforces sequence numbers, so up to five in-flight requests remain ordered. So the accurate sentence is: per-partition order, per-key order by construction, and no global order at all.

How do you get parallelism without losing per-entity ordering?

Partition by the entity id so all of an entity's events land in one partition, then, inside the consumer, stripe the batch into lanes by key and process lanes concurrently while keeping each lane sequential. That gives you parallelism bounded by the number of distinct keys in flight rather than by the partition count. The part that must be right is the commit: you can only commit the highest contiguous completed offset, because committing the maximum would skip any record still in flight behind it. If I do not want to own that bookkeeping I use a parallel-consumer library that implements the same idea, or — when ordering genuinely does not matter — a share group, which hands the problem to the broker.

What is head-of-line blocking and how do you handle it?

One message that cannot complete stops every message behind it in the same ordered stream. It is the dominant cause of runaway Kafka lag, because a classic consumer group cannot move past a failing offset. The three responses are skip, park or relax ordering: seek past it and accept the loss, move it to a retry topic or dead-letter queue and continue, or use a model with per-record acknowledgement so the rest keeps flowing. I default to parking with a DLQ that has an owner and an alert, because it preserves the message for investigation and unblocks throughput in the same move. Retrying in place is fine only for failures I know are short and transient — a 429 from a downstream, say — with a bounded number of attempts before parking.

How do you size prefetch in RabbitMQ?

Start with the number of concurrent handlers times two, then tune against consumer utilisation and message processing time. The failure modes bound the range: unbounded prefetch means the broker pushes the entire queue at the first consumer, which starves the others and can exhaust its memory — the classic "why is one pod at 100% and four idle" report. A prefetch of one gives perfect load balancing and a network round trip per message, which is fine for slow, expensive work (a 30-second job) and terrible for 2 ms messages. Large messages push it down; fast, uniform messages push it up. I also set it per consumer rather than globally on the channel, because global QoS across a shared channel is rarely what people mean.

Your consumer group's lag is growing. Walk me through the diagnosis.

First, is it all partitions or one? One partition means skew or a stuck record — I look at the record at the committed offset. All partitions means arrival exceeds service rate, so I ask which. Second, is the consumer saturated or waiting? CPU near the limit means scale out or make the handler cheaper; low CPU with high latency means it is blocked on a downstream, and adding consumers would make that worse rather than better. Third, did something change — a deploy, a schema change, a new producer, a batch job upstream? Lag that starts at a deploy is usually a slower handler or a rebalance loop. Only after those do I decide between more consumers, more partitions, per-key lanes, or fixing the downstream, and I say the number I am aiming at: drain time, not lag count.

What is static membership and why does it matter?

Static membership gives each consumer instance a stable group.instance.id, so when it disconnects briefly — a rolling restart, a pod reschedule — the coordinator holds its assignment until the session times out rather than immediately rebalancing the whole group. It turns a deploy of thirty instances from thirty stop-the-world rebalances into none, provided the restarts finish inside the session timeout. Combined with the KIP-848 consumer protocol, which makes rebalances incremental and broker-driven, it removes the great majority of deploy-time lag spikes. It is the change I would make first in a shop complaining about latency during releases, and it costs a configuration line plus a stable identity, which a StatefulSet or an ordinal-aware deployment already provides.

Should you autoscale on lag? What are the pitfalls?

Yes, lag is the right signal — it is the closest thing to "how far behind the business is" — and KEDA makes it straightforward. The pitfalls are three. Lag is a stock rather than a rate, so scaling on the absolute value oscillates; I scale on the projected drain time or on the growth rate. Scaling past the partition count does nothing in a classic consumer group, so the maximum must be pinned to it. And every scale event causes a rebalance, so an aggressive scaler with a short cooldown can spend more time rebalancing than working — I use generous stabilisation windows and static membership. I also make sure the scaler cannot amplify a downstream outage: if the consumer is slow because a database is struggling, more replicas is the wrong reflex, so there is a concurrency limit downstream regardless.

Producer-side batching: what are you trading?

Latency for throughput and cost. Kafka's linger.ms makes the producer wait briefly to fill a batch; a value of 5–20 ms typically multiplies throughput several times over the default of 0 because compression works better on a larger batch and there are far fewer requests, and it adds that many milliseconds to end-to-end latency. Compression type matters alongside it: lz4 or zstd for a good ratio at reasonable CPU, and it is worth remembering that the batch is compressed once by the producer and stored compressed, so the saving is in network, disk and page cache too. The failure mode to mention is that a larger batch.size plus a bounded buffer.memory means the producer blocks when it cannot flush — which is backpressure on your application, and it should be surfaced as a metric rather than as a mysterious latency spike.

How do you apply backpressure end to end, not just at one hop?

By making sure every stage has a bounded queue and that a full queue is visible upstream. Unbounded buffers are the enemy: they convert an overload into unbounded latency and eventual memory failure, which is far worse than a fast rejection. Concretely, that means bounded in-memory channels between stages with a blocking or rejecting policy, bounded prefetch at the broker, a concurrency limit on every outbound dependency, and load shedding at the edge that returns 429 with Retry-After rather than queueing indefinitely. The broker itself is a legitimate buffer — that is its job — but the depth of that buffer is a business decision, so I put an explicit limit and an alert on queue depth and treat exceeding it as an incident, not as normal operation.

What do you look for in code review of a message handler?

Six things, quickly. Is it idempotent, and where exactly is the uniqueness enforced? Is the acknowledgement after the durable effect rather than before? Are failures classified — transient retry, permanent to the DLQ — rather than one catch that retries everything, including the malformed message that will never parse? Is there a timeout and a concurrency limit on every outbound call? Does it assume ordering that the partitioning does not actually provide, particularly if someone has added parallelism inside the handler? And does it log the message id, key and offset so that when it does fail at 3 a.m. the on-call engineer can find the record without a full-text search? Those six catch most of the incidents I have seen in production messaging.

09 Dual writes: outbox and CDC

Docs: Debezium outbox event router · Transactional outbox

Here is the bug at the centre of nearly every event-driven system, and it is worth being able to draw on a whiteboard in ten seconds. Your handler saves the order and then publishes OrderPlaced:

await _db.SaveChangesAsync();          // committed
await _bus.PublishAsync(evt);          // ...and now the process dies, or the broker is down

That is a dual write: two independent systems, no shared transaction, and a window between them. Crash in the window and the order exists but nothing downstream knows — no shipment, no email, no analytics row, and no error anywhere, because the transaction committed. Swap the order of the two lines and you get the mirror bug: the event is published for an order that was never saved. There is no ordering of the two statements that is correct, which is the point. You cannot atomically write to two systems without a protocol, so stop trying and write to one.

The outbox: make the event part of the transaction

The transactional outbox turns the dual write into a single write. In the same database transaction that changes your state, insert a row into an outbox table describing the event. The transaction commits both or neither. A separate process then reads the outbox and publishes to the broker, marking or deleting rows as it goes. Publication is now at-least-once — the relay can crash after publishing and before marking — which is fine, because unit 07 already made consumers idempotent.

CREATE TABLE outbox (
  id            uuid PRIMARY KEY,          -- becomes the message id; consumers dedup on it
  aggregate_id  text        NOT NULL,      -- becomes the partition key: per-entity ordering
  type          text        NOT NULL,      -- 'OrderPlaced'
  payload       jsonb       NOT NULL,
  headers       jsonb       NOT NULL,      -- traceparent, tenant, schema version
  created_at    timestamptz NOT NULL DEFAULT now(),
  published_at  timestamptz                -- NULL = not yet relayed
);
CREATE INDEX outbox_unpublished ON outbox (created_at) WHERE published_at IS NULL;
// One transaction. Two rows. No broker involved on the request path.
using var tx = await _db.Database.BeginTransactionAsync();
_db.Orders.Add(order);
_db.Outbox.Add(new OutboxRow {
    Id = Guid.CreateVersion7(),                  // time-ordered id, .NET 9+; also the message id
    AggregateId = order.Id.ToString(),
    Type = nameof(OrderPlaced),
    Payload = JsonSerializer.SerializeToDocument(new OrderPlaced(order.Id, order.Total)),
    Headers = TraceContext.Capture()             // propagate the trace across the async boundary
});
await _db.SaveChangesAsync();
await tx.CommitAsync();                          // both or neither. That is the whole trick.

Two ways to drain the outbox

Polling publisher. A background worker runs SELECT ... WHERE published_at IS NULL ORDER BY created_at LIMIT n FOR UPDATE SKIP LOCKED, publishes, and marks rows. Simple, no extra infrastructure, works with any database, and the code fits on a page. Costs: polling latency (usually 100 ms–1 s, tunable), a constant query load, and the need to handle the relay's own concurrency — SKIP LOCKED is what makes multiple relay instances safe. It is what most teams should start with.

Change data capture. A connector tails the database's replication log — Postgres logical decoding, MySQL binlog, SQL Server CDC — and turns committed changes into messages with no polling and no load on the primary. Debezium is the standard (3.6.1, August 2026; the 3.x line has been the current one since Debezium 3.0 in October 2024) and its outbox event router SMT is purpose-built for this: it reads the outbox table's change events, routes each to a topic based on the aggregate type, uses aggregate_id as the message key, and unwraps the payload so consumers see a clean event rather than a database row. Costs: another distributed system to run (Kafka Connect or Debezium Server), replication-slot management — an unconsumed Postgres slot will fill your disk and take the primary down, which is the operational failure everyone hits once — and schema changes in the source table becoming a deployment concern.

The inbox, and why "log-tailing the real tables" is a trap

The mirror image on the consumer side is the inbox: record the incoming message id in the same transaction as its effect, which is exactly the dedup table from unit 07. Outbox plus inbox gives you at-least-once transmission with effectively-once processing, using nothing but your database's transactions — no distributed transaction anywhere. That combination is the honest answer to "how do you get exactly-once across services".

A tempting shortcut is to skip the outbox table and have CDC stream your business tables directly. It works and it is genuinely right for some cases (replicating to a search index or a warehouse), but it publishes your schema as your public contract: every column rename becomes a breaking change for consumers, every internal-only column leaks, and the event vocabulary becomes "row changed" rather than "the customer did something". The outbox table exists precisely to be a deliberate contract that you version independently of the schema behind it. Say that distinction in an interview and you have answered a question most candidates do not know is there.

Interview trap · "we'll use a distributed transaction"

Someone always suggests two-phase commit, and dismissing it with "2PC is slow" is a weak answer. The precise objections: 2PC is a blocking protocol — if the coordinator fails after prepare and before commit, participants hold locks and cannot decide unilaterally, so the resource stays locked until an operator intervenes; it requires every participant to support XA, which brokers like Kafka and most HTTP APIs simply do not; and it couples the availability of all participants on every write, so five 99.9% services give you a 99.5% transaction. It is not universally wrong — inside one database, or between a legacy MSMQ and SQL Server on the same box, XA is fine and was standard practice for a decade. The lead answer names the modern alternative in one sentence: make the atomic unit local (outbox), make the cross-service consistency eventual (saga), and make every step idempotent.

Try it · lose an event, then stop losing it

1. Write the naive version — save, then publish — and kill the process between the two with a sleep in the middle. Query the database and the topic and count the divergence. Then break the broker instead (stop it) and see what your error handling does with an order that is already committed.

2. Add an outbox table and a polling relay with FOR UPDATE SKIP LOCKED. Run two relay instances at once, kill one mid-publish, and verify no event is lost and duplicates are only ever duplicates.

Expected outcome

1. Orders exist with no events, and — worse — your retry logic probably rolled back nothing, because the transaction was already committed. The second experiment is more instructive: with the broker down, either the request fails after the data was saved (a lie to the user) or you swallow the publish error (silent data divergence). Neither is acceptable, and that is the argument for the outbox in one screen.

2. With the outbox, both failures become harmless: the row is committed with the order and the relay publishes it whenever the broker returns, minutes later if necessary. Killing a relay mid-publish produces a duplicate, which the consumer's inbox absorbs. The metric to watch from now on is outbox age — the age of the oldest unpublished row — because a stalled relay is now silent, and that single gauge is the thing that tells you.

Interview Q&A · outbox and CDC

What is the dual-write problem?

Writing to two systems that do not share a transaction — typically a database and a message broker — so a failure between them leaves them inconsistent with no error raised. Save-then-publish loses the event when the process dies or the broker is unreachable; publish-then-save announces something that never happened. There is no correct ordering, because the problem is the absence of atomicity, not the sequence. The fix is to make the write single: put the event in the same database transaction as the state change (the outbox) and let a separate relay move it to the broker at-least-once, with idempotent consumers absorbing the duplicates that follow.

Walk me through implementing the outbox pattern.

An outbox table with the message id, an aggregate id that becomes the partition key, a type, the payload, headers including the trace context, and a published timestamp. The command handler inserts the domain change and the outbox row in one transaction. A relay — either a poller using FOR UPDATE SKIP LOCKED so several instances are safe, or Debezium tailing the table — publishes each row, then marks or deletes it. Consumers dedup on the message id. The three details that decide whether it works in production: the partition key must come from the row so ordering per entity is preserved, published rows need a cleanup job or the table becomes the biggest one in the database, and you need a metric for the age of the oldest unpublished row, because a stalled relay is otherwise completely silent.

Polling or CDC for the relay?

Polling first, unless there is a reason not to. It needs no extra infrastructure, is trivial to reason about and to test, and a 200 ms poll interval is imperceptible for most workloads. I move to CDC when the latency budget is genuinely tight, when the poll load starts mattering, or when a platform team already runs Kafka Connect and adding a connector is cheaper than another background service in every application. What I would say about the trade: CDC gives you strict commit ordering and no primary load, and charges you an operational tax — replication slots that must be consumed or they fill the disk, connector restarts and snapshot behaviour, and schema evolution in the source table becoming a coordinated deployment.

Why not just have CDC publish your business tables directly?

Because it makes your database schema the public contract. Every rename, every column type change and every internal flag becomes visible to consumers and potentially breaking, and the events you emit are "a row changed" rather than "a customer placed an order" — so consumers reimplement your domain logic to work out what happened. It is right for some purposes: feeding a search index, a cache or a warehouse, where you genuinely want the data rather than the meaning. For inter-service events I want a deliberate, versioned contract, which is exactly what an outbox table is: a small, stable schema I control, decoupled from whatever refactoring happens behind it.

How do you preserve ordering with an outbox?

By carrying the aggregate id on the row and using it as the message key, so all of an entity's events land on the same partition and stay in order. Within a single relay instance, publishing in created_at or id order preserves the sequence; with multiple relay instances, SKIP LOCKED means two rows for the same aggregate could be published out of order, so either partition the relay by aggregate hash, or lock per aggregate, or accept it if the consumer is order-insensitive. This is exactly why time-ordered ids matter: with UUIDv7 the primary key sorts by creation and the ordering query needs no extra index. With CDC the problem disappears, since the replication log is already in commit order.

What is the inbox pattern?

The consumer-side mirror of the outbox: record the incoming message id in the same transaction as the effect it produces, so a redelivery finds the row and skips the work. It converts at-least-once delivery into effectively-once processing using only local transactions. The requirements are that the message id is stable across redeliveries — so it comes from the producer, not from the broker's offset — and that the inbox has a retention policy longer than any plausible redelivery, including a deliberate replay. Outbox plus inbox is the pair I would draw for "exactly-once between two services", because it needs no distributed transaction and degrades to duplicates rather than to loss.

What operational problems does Debezium bring?

Three that I have seen bite. Replication slots: if the connector stops and the slot is not consumed, Postgres retains WAL indefinitely and eventually fills the disk, which takes down the primary — so slot lag needs an alert with real urgency, not a dashboard. Initial snapshots: the first run reads whole tables, which can be hours and heavy, and understanding incremental snapshots is what makes adding a table to an existing connector safe. And schema changes: a DDL change flows through as a schema change event, so consumers and the registry have to be ready, which makes migrations a cross-team sequence rather than one team's deploy. None of these is a reason to avoid it — it is a mature project, 3.6.1 as of August 2026 — but they are the reasons it deserves an owner rather than being someone's side project.

When is two-phase commit actually the right answer?

When all participants are resource managers under one administrative domain that already speak XA, the transactions are short, and the coordinator is highly available — a couple of databases in the same datacentre, or the classic MSMQ-plus-SQL-Server pattern that a lot of .NET systems still run on. In that setting 2PC is well understood, and reimplementing it as a saga would be more code and more risk. It stops being right the moment a participant is an HTTP API, a modern broker or another team's service, because they do not support it and because you would be coupling availability across an organisational boundary. So my answer is: local atomicity where the transaction manager reaches, sagas where it does not, and never a distributed transaction across a network I do not control.

How do you migrate an existing save-then-publish codebase to the outbox?

Incrementally and behind the existing abstraction. Almost always the publish goes through some IEventPublisher; I add an implementation that writes to the outbox table and enlists in the ambient transaction, and swap it in one service at a time. Because the message contract does not change, consumers do not notice. Then I add the relay, the cleanup job and the outbox-age metric, and only after those are stable do I remove the direct-publish path. If there is no abstraction, adding one is the first commit and it is worth doing on its own. The measurement that justifies the work is usually available beforehand: a reconciliation query counting entities without their corresponding events almost always finds the divergence that has been quietly accumulating.

What do you monitor for an outbox?

The age of the oldest unpublished row, above everything else — it is the direct measure of "how stale is the outside world's view", and it catches a stalled relay, a broker outage and a poison row equally. Alongside it: outbox depth (rows awaiting publication) to distinguish a backlog from a stall, publish error rate by type, and relay throughput against insert rate so you can see divergence early. I also alert on the table's absolute size, because a failed cleanup job is the second most common outbox incident after a stalled relay. And I make the age metric a service-level objective rather than a dashboard curiosity, since it is the number that tells you whether the eventual in eventual consistency is seconds or hours.

10 Sagas and durable execution

Docs: Saga pattern · Temporal workflows

Once you have accepted that there is no distributed transaction, you need something else to keep a multi-step business process correct when step three fails. That something is a saga: a sequence of local transactions where each step has a compensating action that semantically undoes it. Not a rollback — the effect already happened and other people may have seen it — but a business-level reversal: refund the charge, release the seat, cancel the shipment, send an apology.

Choreography or orchestration

Choreography: each service reacts to events and emits its own. OrderPlaced → payment charges and emits PaymentCaptured → inventory reserves and emits StockReserved → shipping ships. Nobody is in charge. It is beautifully decoupled at two steps, and by step six nobody in the company can tell you what the process does, because the flow exists only as the sum of the subscriptions. Debugging becomes archaeology across five services' logs.

Orchestration: a coordinator owns the process, calls each step and decides what happens on failure. The flow is one readable piece of code, the state is one queryable row, and you can answer "where is order 4711?" instantly. The cost is a component that knows about all the others — a coupling that is real but is usually worth it, because the alternative is that the knowledge exists in nobody's head.

The lead-level position: choreography for reactions, orchestration for processes. If the steps must happen in a defined order, if failure of a later step must undo an earlier one, or if a human will ever ask "where is this?", it is a process and it needs an owner. If a service simply wants to know that something happened — analytics, notifications, cache invalidation — that is a reaction and an event subscription is exactly right. Most mature systems have both, and being able to say which is which is the answer interviewers are looking for.

// An orchestrated saga as an explicit state machine. The state is a row; every step is idempotent.
public async Task<SagaState> StepAsync(SagaState s, CancellationToken ct) => s.Step switch
{
    Step.Started        => await Try(s, Step.Charged,   () => _payments.ChargeAsync(s.OrderId, s.Total, key: $"{s.OrderId}:charge", ct)),
    Step.Charged        => await Try(s, Step.Reserved,  () => _inventory.ReserveAsync(s.OrderId, s.Lines, key: $"{s.OrderId}:reserve", ct)),
    Step.Reserved       => await Try(s, Step.Shipped,   () => _shipping.CreateAsync(s.OrderId, s.Address, key: $"{s.OrderId}:ship", ct)),

    // Compensation runs backwards, and each compensation is idempotent too.
    Step.CompensateShip => await Try(s, Step.CompensateReserve, () => _shipping.CancelAsync(s.OrderId, ct)),
    Step.CompensateReserve => await Try(s, Step.CompensateCharge, () => _inventory.ReleaseAsync(s.OrderId, ct)),
    Step.CompensateCharge  => await Try(s, Step.Failed,          () => _payments.RefundAsync(s.OrderId, ct)),

    _ => s
};

Three properties make that code correct and they are the ones to name. Every forward step carries a deterministic idempotency key, so a retry after an unknown outcome does not double-charge. Every compensation is itself idempotent, because compensations get retried too, and a "refund" that runs twice is a worse bug than the one it was fixing. And the state transition is persisted before the next call, so a crash resumes rather than restarts — which means the state row and the effect need the same transactional care as everything else in unit 09.

Durable execution: the 2020s answer

Hand-writing that state machine is legitimate and a lot of systems do it. The alternative that has become mainstream is durable execution — Temporal, Azure Durable Functions, AWS Step Functions, Restate, DBOS — where you write the process as ordinary sequential code and the platform persists every step's result to an event history. When the worker crashes, the workflow is replayed from that history: completed steps return their recorded results without re-executing, and execution resumes at the line where it stopped. A workflow can sleep for thirty days, await a human approval, and survive every deploy in between. Temporal has become the default reference in this space, and 2026 is the year it pushed into serverless workers and agentic workflows, which is the visible edge of durable execution becoming infrastructure rather than a specialism.

The constraint that comes with it, and that interviews probe: workflow code must be deterministic, because it is re-executed during replay. No DateTime.Now, no Guid.NewGuid(), no direct I/O, no iterating an unordered map — all of that goes through the SDK's deterministic equivalents or into an activity, which is the non-deterministic, retryable unit. And changing workflow code while instances are in flight requires versioning, because replaying old history against new code diverges. Those two constraints are the entire price, and they are worth it the moment your process has a timeout longer than a request.

Interview trap · compensations that cannot compensate

The saga literature makes it sound as though every step has a neat inverse. In practice some do not, and the interviewer is waiting to see whether you have met that. You cannot un-send an email; you send a correction, which is a different, visible business event. You cannot un-ship a parcel; you initiate a return, which costs money and takes a week. You cannot un-publish a fact someone already acted on. Three techniques to have ready. Reorder so that irreversible steps come last, after everything reversible has succeeded — send the email after the payment is captured, not before. Use a semantic lock: mark the entity Pending so other actors know it is mid-process and do not act on it, and only make it Confirmed at the end. Escalate: when compensation genuinely cannot restore the invariant, route to a human queue with all the context, because a workflow that silently gives up is worse than one that asks. The bad answer here is "we'd roll back"; there is no rollback.

Try it · fail in the middle

1. Build the three-step saga above against three fake services. Make step 3 fail permanently and verify that compensation runs backwards and leaves no charge. Then make step 3 fail with a timeout and see whether your compensation is safe when the step may in fact have succeeded.

2. Rebuild the same process in Temporal (or Durable Functions) with a 24-hour timer between steps 2 and 3. Deploy new code while an instance is waiting, then let the timer fire.

Expected outcome

1. The permanent failure is the easy case. The timeout is the interesting one: if step 3 actually succeeded, cancelling a shipment that "does not exist" must be a no-op rather than an error, and your compensation must tolerate both worlds. That is why compensations are written as "ensure this is not in effect" rather than "undo the last call" — a subtle wording difference with large consequences.

2. The waiting instance survives the deploy — that is the whole selling point — but if you changed the workflow's step sequence rather than only an activity's body, replay diverges and you get a non-determinism error. That failure is the fastest way to learn what workflow versioning is for, and having hit it makes the interview answer concrete instead of theoretical.

Interview Q&A · sagas and processes

What is a saga and when do you need one?

A saga is a business process spanning several services, implemented as a sequence of local transactions where each step has a compensating action that semantically undoes it. You need one whenever an operation must change state in more than one service and you cannot use a distributed transaction — which is essentially always across service boundaries. The mental shift is from atomicity to eventual correctness with explicit compensation: the intermediate states are visible to other actors, so the design has to say what those actors are allowed to see and do. That is why sagas usually come with a semantic lock — a Pending or Reserved state — rather than pretending the intermediate state does not exist.

Choreography or orchestration — how do you choose?

By asking whether the thing is a process or a reaction. If steps must happen in a defined order, if a later failure must undo an earlier step, or if anyone will ever need to ask "where is this order right now", it is a process and it needs an orchestrator that owns the state and the flow. If a service just wants to know something happened and its response affects nobody else — analytics, notification, cache invalidation — that is a reaction, and choreography via an event subscription is right. My practical rule is that choreography stops paying at about three steps, because the flow becomes undiscoverable and debugging turns into correlating logs across services that each know only their own fragment.

What is durable execution and what does it change?

You write the process as ordinary sequential code, and the platform records every step's result to an event history; on crash or redeploy the workflow is replayed, completed steps return recorded results instead of re-executing, and execution resumes where it stopped. What changes is that timers, retries, waits and compensations stop being infrastructure you build and become language constructs — a workflow can sleep 30 days awaiting an approval and survive every deploy in between. The price is determinism: workflow code cannot call the clock, generate random values or do I/O directly, because replay would diverge; all of that lives in activities. And changing an in-flight workflow's shape needs explicit versioning. I reach for it when there are several long-running processes with human steps or long timers; for one three-step saga, a hand-rolled state machine is honest and cheaper.

Some steps cannot be compensated. How do you design around that?

By ordering, by locking semantically, and by escalating. Ordering: put irreversible steps last, so everything that can fail has already succeeded before you send the email or hand the parcel to the courier. Semantic locks: keep the entity in a Pending state that other actors respect, so the intermediate state is not treated as final — that is what stops someone else from acting on a half-finished process. Escalation: when the invariant genuinely cannot be restored, put the case in a human queue with full context rather than logging and moving on. And I would say out loud that compensation is a business decision, not a technical one: whether a failed shipment becomes a refund, a credit or a re-send is a product question, and asking it is part of designing the saga.

How do you handle a saga step whose outcome is unknown?

I never treat unknown as failure. The step is written with a deterministic idempotency key, so a retry is safe and returns the original outcome; if the downstream also offers a query-by-key, I ask it before deciding. If neither is available, the saga records "attempted" with the key and moves into a reconcile state, where a slower process settles it — checking a settlement file, a report, or a periodic sync. Compensations are written as "ensure this is not in effect" rather than "undo the previous call", so they are correct whether or not the step happened. This is the same three-outcome discipline from unit 01, applied at the process level.

Where does the saga state live?

In a durable store the orchestrator owns, updated in the same transaction as any local effect and any outgoing message (via the outbox). Practically that is a row per instance with the current step, a version for optimistic concurrency, the correlation id, the idempotency keys already used, and a timeout timestamp. The version matters because two messages can arrive concurrently for one instance — a step completion and a timeout, say — and without optimistic concurrency they interleave into a corrupted state machine. If I use a framework, this is what it is doing for me, and I still want to know where the row is, because that is the table on-call will be querying at 3 a.m.

How do you handle timeouts in a long-running process?

As first-class scheduled events, not as background sleeps in application memory. Every step that waits for an external response gets a deadline persisted with the saga state, and a scheduler — a durable timer, a delayed message, or a polling sweeper over expired rows — delivers a timeout event when it passes. That event is just another input to the state machine, so the process decides whether to retry, compensate or escalate. Two details: the timeout handler must be idempotent and must tolerate the response arriving after it fired, which is the race that produces double-compensation; and timeouts must be visible in the same monitoring as everything else, because a process that quietly times out for every instance is an outage nobody has noticed.

What frameworks would you consider in the .NET or JVM world, and what has changed recently?

On .NET the historical default was MassTransit, whose saga state machine is genuinely good, but the licensing changed: version 9 was announced in 2025 and shipped in January 2026 as commercial, source-available software requiring a runtime licence key, with a discount tier for small organisations and a paid minimum otherwise, while version 8 stays Apache-2.0 but is unsupported with no end date. That has pushed teams toward Wolverine and Rebus, both MIT, or toward NServiceBus if they were already paying. On the JVM, Axon and Camunda cover the orchestration space, and Temporal spans both ecosystems with first-class SDKs. The point I would make in an interview is that this is a live architectural risk to track, not trivia: a licence change in a framework that sits in the middle of every message path is exactly the kind of dependency decision a lead is expected to have an opinion about.

How do you test a saga?

At three levels. Unit-test the state machine as a pure function — given state and event, assert the next state and the commands emitted — which is why keeping the transition logic free of I/O pays off immediately. Integration-test each step's idempotency by invoking it twice with the same key and asserting a single effect. Then test the failure matrix explicitly: for every step, a permanent failure, a timeout, and a duplicate delivery, asserting that compensation leaves the system in a defined state. Durable-execution platforms make the last part much easier, because you can advance time and inject activity failures deterministically in a test harness. The check I insist on is that every compensation path is exercised by a test, since those are the paths that only run in production incidents.

A team wants to model everything as choreography because it is "more decoupled". Your response?

I would agree that it is more decoupled and then ask them to draw the current order flow on a whiteboard from memory. Usually nobody can, which makes the point better than I could. Then I would frame the trade honestly: choreography moves coupling from a visible place — an orchestrator whose code names the steps — to an invisible one, the implicit contract that this event triggers that behaviour, which no test asserts and no diagram shows. I would propose the split I actually believe in: orchestrate processes, choreograph reactions, and require that any flow with compensation has a named owner and a queryable state. And I would offer a concrete acceptance test for the decision: if support cannot answer "where is this order and why" from one place, the design has failed regardless of how decoupled it is.

11 Events, schemas and contracts

Docs: Schema Registry compatibility · CloudEvents · Fowler: what do you mean by event-driven?

A message is one of three things and conflating them causes most event-driven design arguments. A command tells a specific service to do something (ShipOrder) — one recipient, may be rejected, the sender expects it to happen. An event states that something already happened (OrderPlaced) — past tense, any number of recipients, cannot be rejected because it is a fact. A document just carries data with no intent. The naming test is reliable: if you cannot phrase it in the past tense without it sounding wrong, it is a command wearing an event's clothes, and OrderShippingRequested published to a topic that exactly one service consumes is a command with extra latency.

How much state does an event carry?

Three shapes, and the choice is a coupling decision. An event notification is thin — { orderId, occurredAt } — and the consumer calls back to fetch what it needs. Minimal payload coupling, but it creates a runtime dependency on the producer (your availability arithmetic just got worse), and callbacks during a replay can stampede the producer. Event-carried state transfer puts everything the consumer plausibly needs in the event, so the consumer never calls back and can work while the producer is down. That is the pattern that actually delivers the decoupling people want from events, and its costs are payload size, more schema surface to version, and the fact that consumers now hold a copy of your data that is stale by construction. Event sourcing goes further: the events are the state, and current state is a fold over them.

The lead answer is that these are not a hierarchy but a per-topic choice, and that event-carried state transfer is the sensible default for cross-service events, with notifications reserved for high-volume, low-value signals. And it is worth separating event sourcing from event-driven architecture explicitly, because interviewers ask that on purpose: event-driven is how services communicate; event sourcing is how one service persists its own state. You can do either without the other, and a team that adopts event sourcing because they wanted event-driven integration is about to have a bad year.

Schemas: the contract you will change while people are using it

Every event you publish is a contract with consumers you do not control and cannot redeploy. That makes schema evolution the single most important operational discipline in an event-driven system, and a schema registry — Confluent's, Apicurio, AWS Glue, Azure's — is the mechanism: schemas are registered per subject, each version is checked against a compatibility rule, and the producer's serializer refuses to publish something that would break the rule.

Plain BACKWARD only checks the immediately previous version, so a consumer reading a topic from offset zero — a new projection, a rebuild after a bug — can meet a version from eighteen months ago that no longer parses. If a topic is replayable, its compatibility must be transitive.   "name": "OrderPlaced",

    { "name": "channel", "type": ["null", "string"], "default": null },

The rules that make evolution boring

  • Never change a field's meaning. Reusing status for a new set of values is not detectable by any compatibility check and will silently corrupt every consumer. Add a new field instead.
  • Never remove a required field without a deprecation window measured against your longest retention, not your sprint.
  • Be a tolerant reader. Consumers ignore unknown fields rather than failing — which JSON and Protobuf give you by default and strict validation takes away, so watch for a well-meaning additionalProperties: false.
  • Version in the namespace, not the field. When a change is genuinely breaking, publish orders.v2 alongside v1, dual-publish for a migration window, and delete v1 when telemetry says nobody reads it — which requires per-consumer metrics you must have added in advance.
  • Envelope your events. A consistent wrapper — id, type, source, time, subject, trace context, schema version — makes routing, tracing and dead-lettering generic instead of per-topic. CloudEvents is a CNCF standard for exactly this and is worth adopting rather than inventing, particularly if you cross cloud services.
Interview trap · "we use JSON, so it's flexible"

JSON without a registry is not flexible, it is unenforced — the difference shows up the day someone changes total from a number to a string and three consumers break in production instead of in CI. The pushback to have ready has three parts. Enforcement: the check must happen at publish time, not at review time, or it happens at incident time. Efficiency: Avro and Protobuf carry a schema id instead of repeating every field name, which on a high-volume topic is a large fraction of the bytes, the network and the retained disk. Explicitness: a registry gives you a documented, discoverable list of what your system emits, which is the single artefact new engineers ask for and no codebase provides. That said, JSON Schema in a registry is a perfectly good answer — the argument is about enforcement, not about the format. Pick binary when volume matters, JSON Schema when debuggability and human readability matter more, and never "no schema" on a topic more than one team consumes.

Try it · break a consumer with a schema change

1. Stand up a registry-backed Avro topic with one producer and one consumer. Add a required field with no default to the schema and try to register it under BACKWARD. Then set the subject to NONE, publish it anyway, and watch the consumer.

2. Set the subject to BACKWARD (not transitive), evolve the schema three times, and then start a brand-new consumer reading from offset zero.

Expected outcome

1. Under BACKWARD the registration is rejected before a single message is produced — the failure has moved from runtime to deploy time, which is the entire value proposition. Under NONE the consumer fails to deserialize and, depending on your error handling, either dies in a loop or dead-letters every message; either way the incident is now in production.

2. The new consumer breaks on the oldest records, because each version was only checked against its immediate predecessor and the chain has drifted. This is the argument for BACKWARD_TRANSITIVE on any topic you intend to replay, and having seen it makes it a much more convincing point in a design review.

Interview Q&A · events and contracts

What is the difference between an event and a command?

A command is an instruction to a known recipient to do something; it can be rejected, it is named in the imperative, and the sender cares that it happens. An event is a statement that something already happened; it is past tense, it goes to anyone interested, and it cannot be rejected because you cannot un-happen a fact. The practical consequence is coupling direction: with commands the sender knows the receiver, with events the receiver knows the sender's contract. The failure I look for in review is a command dressed as an event — a past-tense name published to a topic with exactly one consumer that must act — because it gets the decoupling benefits of neither and the debuggability of a queue with none of the delivery guarantees people assume.

Thin events or fat events?

Fat by default for cross-service events — event-carried state transfer — because it removes the runtime callback to the producer, which is the dependency that ruins your availability arithmetic and makes replay a stampede. Thin events are right when the payload is large or sensitive, when consumers need very different subsets, or when the volume makes the bytes matter. The cost of fat events is real and I would name it: consumers hold a stale copy of your data, so you need to say how stale is acceptable and make the event include enough versioning that a consumer can detect out-of-order or duplicate application. A middle path I use often is a moderately fat event plus a documented query endpoint for the rare consumer that needs more.

Event sourcing versus event-driven architecture?

Event-driven architecture is about how services communicate — they publish and react to events instead of calling each other. Event sourcing is about how a single service persists state: it stores the sequence of events as the source of truth and derives current state by folding them. They are independent choices. You can have a fully event-driven system where every service uses ordinary relational tables, and you can event-source one aggregate inside a service that talks to everyone over HTTP. Conflating them is expensive, because event sourcing brings a real cost — projections, snapshots, schema upcasting, and a team that must think in events — which is worth paying where audit and temporal queries are the product, and not worth paying just to publish messages.

How do you evolve a schema without breaking consumers?

Additively, with defaults, enforced by a registry. Adding an optional field with a default is safe; removing a field or making it required is not. The compatibility mode determines the upgrade order — BACKWARD means consumers upgrade first, FORWARD means producers do — and I default to BACKWARD_TRANSITIVE on anything replayable so a consumer reading history does not meet an ancient version it cannot parse. For genuinely breaking changes I publish a new versioned subject or topic, dual-publish through a migration window, and use per-consumer metrics to know when the old one is truly unread. And the rule no tool enforces: never repurpose an existing field, because no compatibility check can detect a change of meaning.

Avro, Protobuf or JSON Schema?

Avro when the data is high-volume and lives in the Kafka/Hadoop ecosystem: compact, schema-id-based, and its evolution rules with defaults are the best specified of the three. Protobuf when the same contracts are also used for gRPC — one definition for synchronous and asynchronous paths is a genuine simplification, and field numbering makes its evolution rules easy to hold in your head. JSON Schema when human readability and debuggability outweigh bytes, or when consumers are outside your ecosystem. What matters more than the choice is that the schema is registered and enforced at publish time; I have seen teams succeed with all three and fail with all three when nothing checked the contract.

What is CloudEvents and why would you use it?

It is a CNCF specification for a common event envelope — id, source, type, specversion, subject, time, plus extensions like distributed-tracing context — with defined bindings for HTTP, Kafka, AMQP and MQTT. The value is that generic machinery stops being per-topic code: routing, deduplication on id, tracing, dead-lettering and audit all read the same fields regardless of payload. It is particularly worth it when you cross platforms, because managed services increasingly emit or accept it natively. It does not replace a schema for the payload — it standardises the metadata around it — and I would still register the data schema separately.

How do you name topics and events so the system stays navigable?

Consistently and boringly: a topic name that encodes the owning domain, the aggregate and the version — orders.order.v1 — and event types in past tense with the same domain prefix. The rules I enforce are that the owning team is derivable from the name, that the version is in the name rather than only inside the payload so a breaking change is visible in the topic list, and that nothing environment-specific appears in the name. I would also insist on a discoverable catalogue — even a generated page listing every topic, its schema, its owner and its consumers — because in a system with a hundred topics the most expensive question is "does an event for this already exist?", and without an answer people publish a fifth variant of the same fact.

Who owns an event schema, and how do you handle a change that a consumer objects to?

The producing team owns the schema, because they own the fact; but ownership is not unilateral authority, since the value of the event is entirely in its consumers. In practice I run it like a public API: additive changes go through the registry's compatibility check and need no negotiation, breaking changes require a new version, a published migration window and consumer sign-off. When a consumer objects, the useful question is which of the three cases it is — they need time (give them the window), they need a different shape (that may be a second event rather than a change to this one), or the change is wrong (they are the domain check that caught it). Contract tests help here: a consumer-driven contract suite turns "we think this breaks us" into a failing build, which is a far better conversation than an argument in a channel.

What are the failure modes of event-carried state transfer at scale?

Three. Payload growth: the event accretes fields because adding one is easier than negotiating a query, and eventually you are replicating a whole aggregate on every change — which shows up as broker cost and consumer memory. Staleness with no version: consumers apply events out of order or apply a duplicate over newer data, so every event needs an aggregate version and consumers must ignore older ones. And the fan-out amplification of a bulk operation: an admin updates 200,000 customers and every consumer receives 200,000 fat events at once, which is a self-inflicted denial of service. The mitigations are a size budget with an alert, a version on every event with a monotonic check in the consumer, and rate-limiting bulk operations at the source rather than hoping consumers cope.

How do you introduce schema governance without slowing everyone down?

By automating enforcement and keeping the human process small. The registry check runs in CI, so an incompatible change fails a build in minutes with a clear message, and nobody needs to attend a review board for an additive field. The human part is limited to breaking changes and new topics, and even there I would rather have a template — name, owner, schema, retention, expected consumers, compatibility mode — than a meeting. The framing that gets buy-in is that governance here is protecting them: the alternative to a failed build is a 2 a.m. page from a consumer they have never met. And I would measure it: if the median schema change takes more than a day of wall-clock time, the process is too heavy and people will start smuggling changes through a nullable string field, which is worse than no governance at all.

12 Retries, DLQs and overload

Docs: Timeouts, retries and backoff with jitter · Circuit breaker

Unit 01 established that retries are how you turn an unknown outcome into a known one, and that badly done they are how you turn a degradation into an outage. This unit is the discipline around them: classify the failure, bound the retries, park what cannot succeed, and shed load before you collapse.

Classify first — most retry bugs are classification bugs

Before any policy, every failure must be sorted into one of three buckets, and a catch (Exception) that retries everything is the anti-pattern.

  • Transient — a timeout, a 503, a connection reset, a broker leader election, a deadlock victim, a 429. Retry with backoff and jitter; it will probably work.
  • Permanent for this message — a malformed payload, a schema violation, a reference to an entity that will never exist, a business rule rejection. Retrying is pure waste and, in an ordered stream, it is head-of-line blocking. Park it immediately.
  • Permanent for the system — a bad deploy, an expired credential, a dependency that is fully down. Retrying makes it worse; this is where the circuit breaker belongs, and the right move is to stop, alert and let the messages accumulate in the broker, which is what the broker is for.

The third bucket is the one people miss, and it is where the expensive mistake lives: when a downstream is down and every message fails, a naive retry policy sends every message to a dead-letter queue within minutes. Now you have a million messages in a DLQ, no ordering, and a replay job that is far riskier than the incident was. A circuit breaker prevents that by failing fast and not consuming — the consumer pauses, lag grows, and when the dependency returns the backlog drains in order.

// Classify, then decide. The shape matters more than the library.
try
{
    await _downstream.SendAsync(msg, ct);
    await consumer.AckAsync(msg);
}
catch (Exception ex) when (IsTransient(ex))          // timeouts, 5xx, 429, connection resets
{
    if (msg.Attempt >= MaxAttempts) { await DeadLetterAsync(msg, ex, "retries exhausted"); return; }
    // Full jitter: sleep = rand(0, min(cap, base * 2^attempt)). Never a fixed interval.
    var window = Math.Min(30_000, 200 * Math.Pow(2, msg.Attempt));
    await Task.Delay(TimeSpan.FromMilliseconds(Random.Shared.Next((int)window)), ct);
    await RetryLaterAsync(msg with { Attempt = msg.Attempt + 1 });
}
catch (Exception ex) when (IsPermanentForMessage(ex)) // bad schema, unknown entity, business reject
{
    await DeadLetterAsync(msg, ex, "permanent");      // no retries at all: they cannot help
}
catch (Exception ex)                                   // unknown, or the dependency is simply down
{
    _breaker.RecordFailure();                          // when it opens, stop consuming entirely
    throw;                                             // do NOT ack; let redelivery handle it
}

Backoff, jitter and the retry budget

Exponential backoff spreads retries in time; jitter spreads them across callers, and without it a thousand clients that failed together retry together, forever, in synchronised waves. Full jitter — sleep a random duration between zero and the exponential cap — is the version AWS recommends and it measurably outperforms both fixed and "exponential plus a little noise". Above the per-call policy sits the retry budget: a token bucket that permits retries only while they are a small fraction (typically 10%) of successful traffic, so a total outage produces zero retries instead of tripling the load on a system trying to recover. And retries should live at exactly one layer, chosen as the one that knows the operation is idempotent.

Dead letters are an operational surface, not a bin

Every messaging system gives you somewhere to park a message that cannot be processed: RabbitMQ's dead-letter exchange with x-delivery-limit, SQS and Service Bus dead-letter queues, and — for Kafka, which historically had nothing — retry topics, Connect's errors.deadletterqueue.topic.name, or, since Kafka 4.2, share groups' broker-side delivery counter that archives a record after the limit (default 5). Whatever the mechanism, a DLQ without three things is a data-loss bucket with good branding: an alert when anything lands in it, a named owner, and a tested replay path that can filter and re-publish after the fix. The replay tool is the part teams skip and then hand-write during an incident at 2 a.m., which is the worst possible time to discover it must preserve ordering, avoid re-triggering side effects, and let you exclude the twelve messages that are genuinely garbage.

A useful refinement for ordered streams is the retry-topic ladder: on transient failure, publish the message to orders.retry.5s, then orders.retry.1m, then orders.retry.10m, then the DLQ, with a consumer per tier that waits before processing. The main stream never blocks, the delays are real, and the tier a message reaches tells you how sick the dependency is. The cost you must name: ordering is lost for retried messages, so this is only correct where per-key ordering is not load-bearing — the same trade-off as everywhere else in this guide.

Interview trap · retrying a non-idempotent operation, politely

The trap is subtler than "don't retry non-idempotent calls", because the interviewer will construct a case where you must. Suppose the downstream has no idempotency keys and you time out on a charge. Retrying may double-charge; not retrying may lose the sale. There is no clean answer, and saying so is the point — then you show the options and their costs. Query before retry, if the downstream can be asked whether the operation happened (often it can, via a search by your reference). Record intent first, so a reconciliation job can settle it later against a report or a settlement file. Push the key upstream: negotiate with the provider, because most serious APIs added idempotency keys after exactly this conversation. And choose the cheaper error deliberately — for a payment, a duplicate you can refund usually beats a lost order you never knew about; for an outbound email, the opposite. What loses the interview is treating a timeout as a definite failure and retrying silently, which is the behaviour that produces the double-charge in the first place.

Try it · build a retry storm, then survive it

1. Run 200 clients against a service with a fixed 1-second retry and no budget. Make the service return 503 for 30 seconds, then recover. Plot request rate. Then swap in full jitter and a 10% retry budget and repeat.

2. Add a circuit breaker to a consumer whose downstream you stop entirely. Compare two runs: one where the breaker pauses consumption, one where the consumer keeps consuming and dead-letters on exhaustion.

Expected outcome

1. With fixed retries you get synchronised waves that persist after recovery — the recovering service is hit by the full backlog at once and often fails again, which is the retry-induced second outage. Full jitter smooths the curve, and the budget collapses retry traffic to nearly zero during the outage, so the service recovers into normal load rather than into a spike.

2. Without the breaker you dead-letter tens of thousands of perfectly good messages in minutes, and recovery becomes a replay project with ordering problems. With the breaker the consumer stops, lag grows visibly, alerting fires on lag rather than on DLQ depth, and when the dependency returns the backlog drains in order with nothing lost. This experiment is the clearest demonstration that lag is a better failure signal than a DLQ.

Interview Q&A · resilience

How do you decide what to retry?

By classifying the failure first. Transient — timeouts, 5xx, 429, connection resets, leader elections, deadlock victims — gets exponential backoff with full jitter and a bounded attempt count. Permanent for this message — bad schema, unknown entity, a rejected business rule — gets no retries at all and goes straight to a dead-letter destination, because retrying is waste and, in an ordered stream, it blocks everything behind it. Permanent for the system — a dependency that is entirely down — trips a circuit breaker and stops consumption, so messages stay in the broker rather than filling a DLQ. A single catch-all that retries everything is the most common bug in this area, and it usually shows up as a DLQ full of messages that were never broken.

Why is jitter necessary?

Because clients that fail together retry together. A dependency that blips for two seconds causes every caller to back off by the same schedule, so they all return at the same instant, producing synchronised waves that keep the dependency down long after the original fault cleared. Jitter randomises the wait so the load spreads smoothly. Full jitter — a random wait between zero and the exponential cap — is the variant I use, because it both spreads and reduces total attempts compared with adding small noise to a fixed exponential. And jitter alone is not enough at scale: it spreads the herd but does not shrink it, so it has to be paired with a retry budget that stops retries entirely when nearly everything is failing.

How does a circuit breaker work and how do you tune it?

It counts failures in a rolling window; above a threshold it opens and fails fast without calling the dependency; after a cooldown it goes half-open and lets a small number of trial requests through, closing again if they succeed. Tuning is mostly about avoiding two opposite mistakes. Too sensitive and it flaps, taking out a dependency that was merely slow for a second; I use a minimum request volume so a couple of failures on a quiet endpoint cannot trip it, and a failure rate rather than a count. Too slow and it provides no protection during the seconds that matter. I also scope breakers per dependency and often per endpoint, because one failing endpoint should not stop calls to a healthy one on the same host, and I make the open/closed state a metric, since a silently open breaker looks exactly like a dependency outage from the outside.

What belongs in a dead-letter queue and what happens next?

Messages that cannot be processed after a bounded number of attempts, with enough context attached to diagnose them: the original payload and headers, the exception, the attempt count, the consumer, and the trace id. What happens next is the part that matters — a DLQ needs an alert on arrival, a named owner and a tested replay path. Replay is not "publish them back"; it needs filtering (some messages are genuinely garbage), a check that the underlying bug is fixed, awareness of side effects already applied, and a rate limit so the replay does not become a second incident. I also review DLQ contents periodically even when the alert is quiet, because a slow trickle of dead letters is a bug report nobody has read.

What is a bulkhead and how does it differ from a circuit breaker?

A bulkhead limits how much of a shared resource one dependency may consume — a separate connection pool or a concurrency limit per downstream — so a slow dependency cannot exhaust the threads that unrelated requests need. A circuit breaker decides whether to call at all based on recent failures. They compose: the bulkhead caps the damage while the breaker is still deciding, and the breaker stops the calls once the pattern is clear. The framing I use in review is that the bulkhead protects the caller's other work, the breaker protects the callee and shortens the caller's failure. A system with retries and a breaker but no bulkhead still goes down when a dependency gets slow rather than failing, which is the more common outage shape.

How do you shed load, and how do you choose what to shed?

By rejecting work at the edge before it enters a queue, based on a signal that leads rather than lags — queue depth or measured latency, not CPU, which saturates too late. The response should be an explicit 429 or 503 with Retry-After, because a fast rejection lets the caller react while a slow timeout wastes both sides' resources. What to shed is a product decision made in advance: I want a priority classification so that checkout survives while recommendations and bulk exports are shed first, and per-tenant quotas so one customer's batch job cannot consume the capacity of everyone else. The principle I would state is that a system without load shedding does not degrade, it collapses — unbounded queues convert overload into unbounded latency and then into memory exhaustion.

Retry topics or in-place retries in Kafka?

In-place with a short bounded backoff for failures I expect to clear in seconds — a brief downstream blip — because it preserves ordering and needs no extra topics. A retry-topic ladder (5 s, 1 m, 10 m, then DLQ) for anything longer, because in-place waiting blocks the partition and the lag it creates is indistinguishable from an outage. The trade-off to state is that the ladder reorders: a retried message is now behind messages produced later, so it is only safe where per-key ordering is not load-bearing, or where the handler is written to detect and ignore stale updates via a version. And I would mention the 2026 alternative: for genuinely order-independent work, a share group gives per-record delivery counting and broker-side archiving, which is the ladder's benefit without the topic sprawl.

A downstream service is rate-limiting you with 429s. What do you change?

First, honour the signal: respect Retry-After, back off with jitter, and stop treating 429 as an error to alert on — it is flow control working. Second, apply the limit on my side with a client-side rate limiter or a concurrency cap, so I stop generating requests that will be rejected; a token bucket sized just under their published limit is both politer and faster than discovering the limit by hitting it. Third, look for structural fixes: batch endpoints, caching, or removing the call from the hot path entirely by pre-fetching or by consuming an event instead. And I would open the conversation with the owning team, because sustained 429s usually mean my usage pattern and their quota were designed by different people who have not spoken.

How do you prevent a cascading failure across services?

By bounding everything that can grow. Every call has a timeout tied to a propagated deadline; every dependency has a concurrency limit so it cannot consume the whole thread pool; retries are budgeted and single-layer; queues are bounded and overflow sheds rather than grows; and circuit breakers stop calls into a known-dead dependency. Then I remove synchronous dependencies wherever the answer is not needed immediately, because the cheapest way to avoid a cascade is not to have the edge. Finally I make degradation explicit and tested: the page renders without recommendations, checkout works without the loyalty service, and there is a test that proves it — otherwise "graceful degradation" is an aspiration rather than a behaviour.

How do you decide the maximum number of retry attempts?

From the total time budget rather than from a habit. If the operation has, say, 30 seconds before the caller or the business gives up, and my backoff caps at 5 seconds, then five or six attempts is the arithmetic — I would rather compute it than pick three. For asynchronous work with no caller waiting, the bound is different: how long is it worth blocking this queue, and after what point is a human better placed to decide? That usually produces a small number of fast attempts, then a ladder of slower ones over minutes, then a dead letter. I also make attempts observable: a histogram of attempt counts tells you whether retries are actually rescuing anything, and if 95% of successes happen on the first attempt and the rest never succeed, the retry policy is costing more than it earns.

13 Running it in production

Docs: OTel messaging semantic conventions · Kafka monitoring · Kafka tiered storage

Everything above is design. This unit is the part that decides whether the design survives contact with a Tuesday: how you see inside an asynchronous system, what you measure, how you replay, how you upgrade, and how you keep it secure. At lead level this is usually where the interview goes deepest, because it is the part you cannot learn from a book.

Tracing across an asynchronous boundary

A request trace is easy when calls are synchronous — the context rides along the wire. With a broker in the middle, producer and consumer are separated in time, and the naive result is two disconnected traces and no way to answer "what happened to this order?". The fix is to propagate the trace context in message headers: traceparent and tracestate from W3C Trace Context, put in the headers by the producer and extracted by the consumer, which then starts a span linked to the producing span rather than nested inside it — because the consumer may run an hour later and a child span that long distorts every latency chart you own.

// Producer: inject the current context so the consumer can link back to it.
using var send = Activity.Current?.Source.StartActivity("orders publish", ActivityKind.Producer);
Propagators.DefaultTextMapPropagator.Inject(
    new PropagationContext(send?.Context ?? default, Baggage.Current),
    message.Headers,
    static (headers, key, value) => headers[key] = Encoding.UTF8.GetBytes(value));

// Consumer: extract, then LINK rather than nest. The two sides may be an hour apart.
var parent = Propagators.DefaultTextMapPropagator.Extract(default, message.Headers,
    static (headers, key) => headers.TryGetValue(key, out var v) ? [Encoding.UTF8.GetString(v)] : []);

using var receive = Source.StartActivity(
    "orders process", ActivityKind.Consumer,
    parentContext: default,                                 // a NEW trace root...
    links: [new ActivityLink(parent.ActivityContext)]);     // ...linked to the producer's span

receive?.SetTag("messaging.system", "kafka");
receive?.SetTag("messaging.destination.name", "orders");
receive?.SetTag("messaging.message.id", message.Id);

A currency note worth having: OpenTelemetry's messaging semantic conventions are still in Development status as of 2026 — not stable — which is why instrumentation libraries gate the new attribute names behind OTEL_SEMCONV_STABILITY_OPT_IN=messaging and can emit both old and new during a transition. The practical consequence for a platform team is that dashboards and alerts built on messaging attribute names need a migration plan, and that pinning instrumentation versions matters more here than for HTTP, whose conventions stabilised years ago.

The five numbers

Dashboards proliferate; the signals that actually page someone are few. For any messaging system I want these, and I want them per topic and per consumer group rather than as a cluster aggregate:

  • Consumer lag — records behind the end of the log. The primary business-impact signal. Alert on projected drain time, not the raw count.
  • Message age at processing — now minus the event's produced-at timestamp, which is the number that answers "how stale is the downstream world?" and is the one to build an SLO on. Lag in records is meaningless when throughput varies; age in seconds never is.
  • Outbox age (unit 09) — the oldest unpublished row, because a stalled relay is otherwise silent.
  • Dead-letter arrival rate — with an owner attached. Zero should be the normal value.
  • Under-replicated partitions / unavailable quorum members — the durability signal. It is not user-visible until it is catastrophic, which is precisely why it needs an alert.

Two anti-patterns to name: alerting on absolute lag (a batch job legitimately creates a million-record lag every night) and alerting on broker CPU (which correlates with nothing your users experience). Rebalance rate and consumer restarts are worth a dashboard panel too, since a rebalance loop is invisible in lag until it is enormous.

Replay is a capability you build before you need it

The reason to choose a log is replay, and replay is a procedure, not a button. It has four parts, and rehearsing them is the difference between a controlled recovery and a second incident. Scope: which topic, which partitions, what offset or timestamp range, which consumer group. Isolation: replay into a new consumer group writing to a shadow destination if the effects are not idempotent, because replaying into the live group re-triggers every side effect — the emails, the charges, the webhooks. Rate: throttle, because a topic that took a week to fill will replay in an hour and flatten every downstream. Verification: a reconciliation query that says the result is right before you switch traffic to it. Kafka's kafka-consumer-groups --reset-offsets --to-datetime does the mechanical part; everything else is yours.

Retention, tiered storage and what it costs

Retention is a product decision disguised as a broker setting. Seven days is a common default and it is also the maximum age of any bug you can fix by replay. Longer retention used to mean expensive broker disks; tiered storage (KIP-405, generally available since Kafka 3.9 and extended in 4.3 with follower fetch from the tiered offset) changed the arithmetic by moving closed segments to object storage while the broker keeps only the hot tail — so months of retention costs object-storage prices and a new broker replicates in minutes instead of hours, because it does not have to copy the cold data. The trade-off is latency on historical reads and a hard dependency on the object store for replay. For queue-shaped systems, the equivalent conversation is TTL and queue-depth limits: RabbitMQ's x-message-ttl and x-max-length with an overflow policy, which forces you to decide in advance whether an overloaded queue drops the oldest messages or rejects new ones.

Security, briefly but concretely

Four things get asked. Transport: TLS everywhere, and mutual TLS where the broker must authenticate the client — Kafka's SSL and SASL_SSL listeners, RabbitMQ's TLS listeners with peer verification. Authentication: SASL/SCRAM for password-based, OAuth bearer tokens for federated identity — and Kafka 4.3 (May 2026) added client-assertion support to the OAuth client_credentials grant (KIP-1258), which removes shared client secrets from broker configuration in favour of signed assertions. Authorisation: per-topic, per-group ACLs with least privilege, which in practice means a service account per application rather than one shared superuser, and it means ALLOW READ on a topic does not imply ALLOW WRITE. Data: encryption at rest is table stakes; the harder question is PII in payloads, because a topic with seven days of retention is a seven-day copy of personal data that a deletion request must reach. The two answers worth knowing are field-level encryption with a key per subject (delete the key, the data is unreadable — "crypto-shredding") and tokenisation, keeping the sensitive value in one system and a reference in the event.

Interview trap · "we'll just replay from Kafka"

Offered confidently, and it collapses under three questions. Is the data still there? Default retention is seven days; the bug you are fixing may be three weeks old, and unless someone set infinite retention or tiered storage, the answer is no. Are the side effects idempotent? Replaying OrderPlaced through the live consumer group means re-sending emails, re-charging cards and re-firing webhooks, so replay into the production group is only safe when every consumer is idempotent — which is a claim you should be able to substantiate per consumer, not assume. Can the downstream absorb it? Three weeks of traffic in one hour is a 500× spike, and the replay becomes the outage. The strong answer names all three and adds the operational one: replay into a new consumer group with a throttle, verify against a reconciliation query, then cut over — and say plainly that if the effects are not idempotent, you replay into a shadow destination and diff.

Try it · trace and replay

1. Instrument a producer and a consumer with OpenTelemetry and view a trace in Jaeger or Zipkin. First nest the consumer span under the producer's, then switch to a link. Compare what each does to the trace duration when you delay consumption by 60 seconds.

2. Produce 100k records, consume them with group g1, then replay from a timestamp into a new group g2 that writes to a shadow table, throttled. Diff the shadow table against the live one.

Expected outcome

1. Nesting produces a trace that appears to take 60 seconds, which pollutes every latency percentile and makes the producer look catastrophically slow. Linking keeps the producer's trace honest and still lets you navigate from one to the other — which is exactly why the messaging conventions specify links for this case rather than parent-child.

2. The diff should be empty, and if it is not you have found either a non-deterministic handler or a dependency on state that has since changed — both of which are things you very much want to learn on a Wednesday afternoon rather than during an incident. Time the replay too: the ratio of replay time to original elapsed time is the multiplier your downstream will experience, and it is the number to put in the runbook.

Interview Q&A · operations

How do you trace a request across a message broker?

By propagating W3C Trace Context in the message headers — traceparent and tracestate — injected by the producer and extracted by the consumer, which starts a new span with a link to the producing span rather than as its child. The link matters because producer and consumer can be minutes or hours apart, and a child span of that duration corrupts latency analysis. I also put the message id, destination and consumer group on the span as attributes so a support question can be answered by search. One currency note: OpenTelemetry's messaging semantic conventions are still in development status, so attribute names can move and instrumentation gates the new ones behind an opt-in environment variable — which means version pinning and a dashboard migration plan.

What do you alert on for a messaging system?

Consumer lag expressed as projected drain time, message age at processing against an SLO, dead-letter arrivals, outbox age if there is an outbox, and durability signals like under-replicated partitions or a quorum missing members. I deliberately do not alert on raw lag counts, because a nightly batch legitimately creates a huge lag, nor on broker CPU, which correlates with nothing users feel. I would also have a panel — not a page — for rebalance rate and consumer restarts, since a rebalance loop is invisible in lag until it becomes enormous. The framing I use is that the alert should describe a user-visible or data-loss condition, and everything else is a dashboard.

Walk me through replaying a topic to fix a bug.

Scope it first: which topic, which partitions, what time range, and which consumers actually need the reprocessing. Then decide isolation — if every affected consumer is idempotent I can reset that group's offsets; if not, I replay into a new consumer group writing to a shadow destination. Throttle it, because a week of data replays in an hour and that is a 150× spike on every downstream. Verify with a reconciliation query before switching anything, then cut over and keep the old data until I am confident. The two things I check before starting are retention (is the data even still there?) and schema compatibility, because a consumer reading a year-old record needs transitive compatibility or it will fail on the oldest messages.

How do you decide retention?

By asking what replay I want to be possible. Retention is the maximum age of a bug I can fix by reprocessing, and the maximum history a new consumer can bootstrap from — so it is a product question, not a storage one. Seven days is the common default and it is usually too short for the second use. Tiered storage changed this materially: since KIP-405 went GA, cold segments live in object storage, so months of retention cost object-storage prices, and broker recovery is faster because a new replica does not copy the cold data. Against that I weigh the compliance side, since retained events are retained personal data, which is why long retention usually comes with field-level encryption or tokenisation rather than raw PII.

How do you handle PII in events?

By not putting raw PII in a long-retained topic if I can avoid it. The two techniques I would name are tokenisation — the event carries a reference and the sensitive value lives in one system with its own access controls and deletion path — and field-level encryption with a key per data subject, so honouring a deletion request means destroying the key and every copy of the event everywhere becomes unreadable. That "crypto-shredding" approach is what makes retention and the right to erasure compatible, and it is the answer that shows you have actually met the problem. Alongside that: least-privilege ACLs per topic, encryption in transit and at rest, and a discipline that log lines and DLQ payloads are copies of the data too, which is where PII most often leaks unnoticed.

How do you run a multi-region messaging setup?

I start by asking what the requirement really is, because the three answers are very different. For disaster recovery, asynchronous replication of topics to a standby region — MirrorMaker 2 or a vendor's cluster linking for Kafka, federation or shovel for RabbitMQ — with an explicit, measured RPO and a rehearsed failover, including the offset translation problem that makes consumers resume in the right place. For latency, regional clusters with only the genuinely global topics replicated. For active-active writes, I push back hard, because that is multi-master with conflict resolution, and unless the data is commutative it needs a per-key home region. Whatever the shape, the thing I insist on is a tested failover: an untested DR plan is a document, not a capability.

What is tiered storage and when does it pay for itself?

Kafka stores closed log segments in object storage while keeping the recent tail on broker disks, so retention and broker capacity are decoupled. It became generally available in Kafka 3.9 and has kept improving — 4.3 added follower fetch from the tiered offset so a new replica bootstraps from remote storage instead of streaming everything through the leader. It pays for itself when retention is long relative to throughput, and it has a second benefit people undersell: rebalancing and broker replacement get dramatically faster and cheaper because only the hot data moves. The costs are latency on historical reads and a hard dependency on the object store, so a replay is now also an availability question about S3 or its equivalent.

How do you test a distributed messaging system?

In layers. Handlers are pure functions where possible and unit-tested including their idempotency, by invoking twice and asserting a single effect. Integration tests run against a real broker in Testcontainers rather than an in-memory fake, because the behaviours that matter — redelivery, rebalance, ordering, acknowledgement semantics — are exactly the ones a fake does not reproduce. Contract tests, consumer-driven, guard the schemas so a producer change fails a build rather than a consumer. Then failure-injection tests for the paths that only run during incidents: broker unavailable, duplicate delivery, out-of-order arrival, poison message. And for anything with strong claims about consistency, I look for published Jepsen results rather than trusting the marketing page.

Your Kafka cluster shows under-replicated partitions. What do you do?

First I establish whether it is a broker problem or a network problem: are the under-replicated partitions concentrated on one broker (likely a disk, a GC pause or an overloaded node) or spread across many (likely network or a cluster-wide event such as a rolling restart)? I check whether the ISR is shrinking and expanding repeatedly, which points at a follower that cannot keep up, and I look at request latency and disk I/O on the affected broker. The immediate risk is durability, not availability, so I would stop anything that reduces redundancy further — pause a rolling restart, delay a rebalance — and I would check that min.insync.replicas is protecting writes. Then the fix follows the cause: replace a failing disk, throttle a rebalance that is saturating the network, or add capacity if the node is simply overloaded.

How do you plan a major broker upgrade?

As a rehearsed sequence with a rollback, not as a maintenance window. Read the release notes for removals rather than features — that is where the surprises are — and check client compatibility in both directions, since brokers and clients upgrade at different times. Rehearse on a staging cluster with production-shaped topics and a replayed traffic sample. Then roll one broker at a time, watching under-replicated partitions return to zero between each, and keep the protocol version pinned until every broker is upgraded so you can roll back. The two 2026 examples I would cite as evidence that this matters: Kafka 4.0 removed ZooKeeper entirely, so there is no direct upgrade path from a ZooKeeper cluster — you migrate to KRaft on 3.9 first — and RabbitMQ 4.3 removed Mnesia, so a cluster still on the old metadata store must convert to Khepri before upgrading. Both are the kind of removal that turns an ordinary upgrade into a project if nobody read the notes.

14 The big Q&A

Docs: Kafka release blog · RabbitMQ release information · Jepsen analyses

Twenty-two questions that do not belong to a single building block: the architecture calls, the security questions, the debugging stories, the migration reality, and the judgment scenarios that a lead or principal interview spends most of its time on.

Architecture & ecosystem decisions

Synchronous or asynchronous — how do you decide for a given interaction?

By asking whether the caller needs the answer to proceed and whether the callee's availability should be part of the caller's availability. If a user is waiting for a decision — is this card valid, is this seat free — that is synchronous, and I keep the chain short because each hop multiplies latency and divides availability. If the caller only needs the work to happen eventually, that is a message, and it buys temporal decoupling, buffering and fan-out. The two mistakes I look for are opposite: an RPC chain five deep where three of the calls are really "and also tell these people", and a request/response conversation forced through a broker with correlation ids, which is synchronous coupling with worse ergonomics and no timeout semantics. A useful test: if the producer would ever say "and I don't care who listens", it is an event.

How do you decide whether something should be a new service at all?

By whether it has an independent reason to change, an independent scaling profile, and an owner. Distribution is a cost you pay in latency, partial failure, deployment coordination and cognitive load, so it should buy something specific. The failure mode I have seen most is services split along technical layers rather than domain boundaries, which produces a distributed monolith: every feature touches four services, they must deploy together, and you now have the drawbacks of both architectures. My practical filter is the transaction boundary — if two things must change atomically and constantly, they belong in one service, because splitting them converts a database transaction into a saga, and that is a large permanent tax to pay for an org-chart preference.

Managed cloud messaging or self-hosted — how do you frame that decision?

As total cost of ownership against control, with numbers rather than principle. Managed removes upgrades, capacity, patching and most 3 a.m. pages, and it costs more per byte plus some version and tuning agility; self-hosting is cheaper at volume if you already have a platform team, and it is a standing commitment of roughly a part-time engineer forever plus a lumpy learning cost in the first year. The factors that usually decide it are scale (below a few hundred GB a month, the engineer costs more than the service), regulatory constraints, latency requirements that a shared service cannot meet, and whether the team has genuinely operated the thing before. Whichever way it goes, I insist on the same two artefacts: a named owner and a rehearsed disaster-recovery drill.

What is your view on service meshes for a message-heavy system?

A mesh solves service-to-service synchronous problems — mTLS, retries, outlier ejection, traffic shifting, uniform telemetry — and does almost nothing for the broker path, since the interesting semantics there are consumer groups, offsets, acknowledgement and ordering, which live above the transport. So I evaluate a mesh on the RPC share of the system, and I would not adopt one to improve messaging. The parts I would actually want are usually available more cheaply: mutual TLS the broker already supports, client-side outlier ejection in a resilience library, and tracing through OpenTelemetry SDKs. Where a mesh earns its keep is a large fleet with heterogeneous languages where consistent identity and encryption would otherwise be reimplemented ten times — and even then the honest framing is that it is a platform investment with an ongoing operational cost, not a free upgrade.

Where do you draw the line between a stream processor and application code?

I use a stream processor — Kafka Streams, Flink — when the work is genuinely stream-shaped: windowed aggregation, stream-to-stream joins, or stateful computation over large key spaces where the framework's state store, changelog and exactly-once integration would otherwise have to be rebuilt badly. I keep it in application code when the handler is "read a message, apply a business rule, write to a database", because a framework adds a large operational surface — state directories, rebalance semantics, versioned topologies — for no benefit. The line I watch for is a team building windowing and out-of-order handling by hand inside a consumer, which is the point at which they have started writing a stream processor and should use one instead.

Security

How do you secure a broker properly?

Four layers, none optional. Transport encryption with TLS on every listener, including inter-broker traffic. Authentication with per-application identities — SASL/SCRAM or mutual TLS, or OAuth where there is a central identity provider, and Kafka 4.3's client-assertion support for the OAuth client-credentials grant is worth knowing because it removes shared client secrets from configuration. Authorisation with least-privilege ACLs per topic and per consumer group, which in practice means one service account per application and no shared superuser, because a shared credential makes both audit and rotation impossible. And data protection: encryption at rest, plus a deliberate answer for personal data in payloads, since a topic with long retention is a long-lived copy of that data.

A regulator asks you to delete a customer's data. It is in a Kafka topic with 90-day retention. What now?

You cannot delete a record from the middle of a log, so the answer has to have been designed in advance. The mechanism I would have chosen is crypto-shredding: personal fields are encrypted with a per-subject key held in a key store, so deleting the key makes every copy — in the log, in backups, in downstream caches — permanently unreadable, and the deletion is a single, auditable operation. The alternatives are worse: tokenisation works similarly if the sensitive value never entered the event; compacted topics with a tombstone can remove a key's latest value but not its history; and shortening retention is a blunt instrument that loses everyone's data. If none of that exists yet, the honest answer in the room is that this is now a project, and the immediate step is to enumerate every downstream copy, because the topic is rarely the only one.

What are the security risks specific to asynchronous systems?

Three that do not exist in a synchronous call. First, the message is a stored copy: retention, DLQs and logs all hold payloads long after processing, so a topic's access control is a data-protection boundary and a DLQ full of raw payloads is a quiet exfiltration risk. Second, the authorisation context is detached — the user's token has usually expired by the time the message is processed — so you must decide deliberately whether the consumer acts as the system or re-derives the user's permissions, and both choices need to be explicit rather than accidental. Third, replay is an attack surface: an attacker who can publish, or who can cause a replay, may be able to repeat an effect, which is one more reason for consumer-side idempotency and for signed or authenticated message provenance where the stakes justify it.

Performance & debugging

A message takes 40 seconds end to end and it should take 200 ms. How do you find where it went?

I break the journey into its four measurable segments and find which one holds the time: produce (application to broker acknowledgement), wait (in the log or queue until consumption starts), process (handler duration), and downstream (what the handler waits on). Trace context in the headers gives me this directly if it is instrumented; if not, the broker's own metrics give me the wait time as lag or queue depth, and that alone usually settles it. A long wait means consumer capacity or a stuck partition. A long process time means the handler or its dependencies. A long produce time points at broker throttling, batching configuration, or the producer's buffer being full. The mistake I avoid is starting with the code: in an asynchronous system, most missing time is queueing, and queueing is measured, not read.

Your p50 latency is fine and your p99 is terrible. What do you look at?

Tail latency almost always has a small number of causes and I would work through them: queueing behind a slow batch (head-of-line blocking, so look at batch sizes and per-key lanes), garbage collection or runtime pauses that correlate with the spikes, a single slow instance or partition dragging the aggregate — which is why per-instance and per-partition percentiles matter more than the fleet number — connection pool contention, and retries adding whole extra round trips to a small fraction of requests. The structural fixes are usually hedged requests for read paths, bounded queues so waiting is visible rather than absorbed, and removing a synchronous dependency from the path. I would also check whether the p99 is dominated by one tenant or one key, because a single hot entity produces exactly this signature.

How do you debug a problem that only happens under production load?

By making production observable rather than by reproducing it. Structured logs with correlation ids across every hop, tracing with sampling that is biased toward slow and failed requests rather than uniform, and metrics with enough dimensions to segment by tenant, endpoint and instance. Then I look for the correlation: does it track deploys, time of day, a particular partition, a specific customer? Continuous profiling has repaid its cost every time I have used it, because "the handler is slow" and "the handler spends 60% of its time in JSON serialisation" are very different tickets. Where the effect is rare I add targeted instrumentation and ship it, which is faster than a week of local reproduction. And where a load test is genuinely needed, it has to replay real traffic shapes, because synthetic uniform load does not produce the skew that causes the problem.

Consumer lag was zero, then jumped to millions in minutes. What is your first hypothesis?

A producer-side event, not a consumer-side one: a backfill, a bulk update, a migration job, or an upstream retry storm that multiplied the volume. That covers most cases and the check is a single graph — produce rate against consume rate. If produce rate is flat, my next hypotheses are that consumers stopped (a rebalance loop, a crash loop, a deployment that failed readiness), that they are blocked on a downstream that just got slow, or that one partition is stuck on a poison record while the aggregate makes it look uniform. The reason I ask "did production change?" first is that the expensive mistake here is scaling consumers to absorb a bulk job, which converts a temporary lag into a downstream outage.

How do you performance-test a message-driven system?

By testing the shape, not just the volume. That means production-like key distribution — including the skew, because a uniform key space hides every hot-partition problem — realistic message sizes, and the same consumer concurrency and downstream latencies. I test at least three scenarios: steady state at the target rate, a burst several times larger to see whether backpressure works or something unbounded grows, and a recovery test where consumers are stopped for a period and then must drain a backlog, since drain rate is a different number from steady-state throughput and it is the one that matters during an incident. The metrics I care about are end-to-end age at the p99, drain rate, and where the first bottleneck appears, because a test that only reports throughput has told me almost nothing about how the system fails.

Tooling & testing

What does your local development setup look like for a message-driven system?

Real infrastructure in containers, orchestrated by the test framework rather than by a README. Testcontainers for Kafka, RabbitMQ or whatever the system uses, so integration tests start a real broker and exercise real redelivery and rebalance semantics; in-memory fakes are fine for handler unit tests but they do not reproduce the behaviours that actually break. Alongside that, a way to see what is happening — a UI or CLI to browse topics, inspect messages and reset offsets — because debugging blind is what makes people afraid of asynchronous systems. And a seed script that produces representative traffic, because a system that only ever sees three hand-written messages during development will meet its first realistic key distribution in production.

How do you make contract testing work across teams?

Consumer-driven contracts, automated in both pipelines. Consumers declare what they need from an event; those expectations are published to a broker like Pact's, and the producer's build verifies against every registered consumer contract, so a breaking change fails the producer's build with the name of the team it would break. For schema-registry ecosystems, much of this is already handled by compatibility checks at publish time, and I would use that as the first line, with contract tests covering semantics the schema cannot express — that this field is always present for this event type, that this enum only takes these values in practice. The organisational half matters as much as the tooling: contracts need to be cheap to add and the failure message needs to say exactly what to do, or people route around them.

What tooling do you insist on before a messaging system goes to production?

Four things. A way to inspect and search messages, so support questions do not become engineering escalations. A tested replay tool with scoping, throttling and a dry-run, because it will be written eventually and writing it during an incident is the worst option. Dead-letter tooling that shows why each message failed and can selectively re-publish. And per-topic, per-consumer-group dashboards with lag, age and error rates. I would also want the topology to be declarative — topics, queues, bindings, ACLs and retention defined in code and applied by a pipeline — because manually created infrastructure cannot be rebuilt in a disaster and nobody can answer "who owns this topic?" about it.

Legacy and migration reality

You inherit a system using MSMQ or a classic ESB. How do you modernise it?

Incrementally, with a bridge, and never as a big-bang rewrite. The first step is to understand and document the existing flows, because an ESB usually contains business logic in its routing and transformation rules that exists nowhere else. Then I put a bridge in place — a small adapter that forwards messages between the legacy transport and the new broker in both directions — so new services can be written against the modern system while old ones keep working. Then I migrate flow by flow, starting with something low-risk and well understood, and I keep both paths live with reconciliation until confidence is earned. The two things that decide success are that the bridge is boring and well-tested, and that there is an agreed end state with a date, because a permanent bridge is the worst of both worlds and that is the default outcome without one.

What legacy patterns will you meet in an older message-driven codebase, and what do you do about them?

Several, and I would fix them in order of danger. Dual writes — save then publish — is the one that is silently losing data, and the outbox is the fix. Distributed transactions over MSMQ and SQL Server: they work, and I would leave them alone unless the components are being moved anyway, because replacing a working XA transaction with a saga is a real risk for no immediate benefit. Auto-acknowledgement or acknowledge-before-process, which is silent message loss. Shared broker credentials with full privileges. And RPC-over-queue — request and reply through a broker with correlation ids — which I would migrate to HTTP or gRPC where the caller genuinely needs an answer, because it is synchronous coupling with none of the timeout, retry or tracing ergonomics.

What are the biggest recent version changes a team could be caught out by?

Three that are live in 2026. Kafka 4.0, in March 2025, removed ZooKeeper entirely — so an old cluster cannot upgrade directly; it must migrate to KRaft on 3.9 first — and the KIP-848 consumer protocol, GA in the same release, is enabled server-side but requires clients to opt in with group.protocol=consumer, so brokers alone change nothing. RabbitMQ removed classic mirrored queues in 4.0 and then removed Mnesia in 4.3 (April 2026), making Khepri the only metadata store and retiring the pause_minority family of partition strategies, so anyone who has not converted must do so before upgrading. And outside the brokers, MassTransit v9 shipped in January 2026 as commercial software with a runtime licence key while v8 remains Apache-2.0 but unsupported, which is a dependency decision sitting in the middle of a lot of .NET message paths.

Judgment and scenarios

How would you introduce event-driven architecture to a team that has only built synchronous services?

With one flow, chosen because it is genuinely a good fit, and with the hard parts solved before anyone else copies it. I would pick something where the producer plainly does not need an answer — notifications, or an audit trail — and build it properly: outbox on the producer, idempotent consumer, schema in a registry, DLQ with an alert and an owner, tracing across the boundary. Then I would make that a template, because the second and third flows will copy whatever the first one did, including its mistakes. What I would resist is a broad "we are now event-driven" mandate, because the failure mode is teams publishing events with no schema discipline and no idempotency, and then concluding that events are unreliable. And I would be explicit about the costs up front — debugging is harder, eventual consistency is now visible to users — so the team is choosing them rather than discovering them.

What do you look for when reviewing a distributed system design?

I read it for failure first. Where are the dual writes? What happens when each remote call times out — not fails, times out? Which operations are not idempotent and what protects them? Where is ordering assumed, and does the partitioning actually provide it? What is unbounded — a queue, a retry, a payload, a fan-out? Then the operational questions: how do we know it is broken, what does the on-call engineer do at 3 a.m., how do we replay, and what happens to a poison message. Finally the change questions: how does this schema evolve, and how do we upgrade this with instances of the old version still running. If a design answers those, the happy path takes care of itself; if it only describes the happy path, the review has not started.

A junior engineer asks why the system cannot just be consistent everywhere. What do you say?

That it can, and here is the bill. I would make it concrete rather than theoretical: consistency across services means either a distributed transaction, which blocks and couples availability, or a single database, which couples deployment and scaling. Then I would show the arithmetic they can check themselves — five dependencies at 99.9% is 99.5% if you need them all synchronously — and the latency of a cross-region quorum on every write. The point I want them to take away is not that consistency is bad but that it has a price, that the price is paid in availability and latency, and that the skill is deciding which invariants are worth it. Usually one or two are: money must not be created, a seat must not be sold twice. Everything else can be eventual with a good user experience around it.

It is 3 a.m., consumer lag is 40 million and growing. Walk me through the first ten minutes.

First, is it getting worse or draining, and what is the projected drain time — that decides whether this is an incident or a wait. Second, produce rate versus consume rate: if produce spiked, find who and consider throttling them at the source; if consume collapsed, look at consumer health, restarts and rebalances. Third, is it all partitions or one, because one means a stuck record or a hot key and the fix is completely different. Fourth, what changed in the last few hours — a deploy, a migration, a schema change, a downstream release. While diagnosing, I would communicate what is user-visible, because lag is not automatically an outage and stakeholders need the difference. The actions I hold back are the tempting ones: scaling consumers before knowing whether the downstream can take it, and resetting offsets to skip the backlog, which is data loss dressed up as a fix.

15 Night-before cheat sheet

Docs: Kafka 4.2 announcement · RabbitMQ 4.3 highlights · Transactional outbox

Ten sentences you can say out loud, in this order, and be right. Each is a hook you can expand into two minutes if they follow up.

  1. "A remote call has three outcomes — succeeded, failed, and unknown — and every hard bug in a distributed system lives in the third one." Then the consequence in one breath: a timeout carries no information, so you never treat it as failure, you make the operation idempotent and retry, or you make it queryable and reconcile.
  2. "There is no 'now'. You cannot order events on two machines by their timestamps, so ordering comes from something the system owns — a log offset, an aggregate version, or a logical clock." Add that last-write-wins by wall clock is a data-loss policy with a clock-skew-sized window, and that hybrid logical clocks are what CockroachDB and MongoDB use to get causality with readable time.
  3. "CAP is about the partition; PACELC is about every other day — else, latency or consistency — and that is the trade I actually make." Ground it in a config: Kafka RF=3 with acks=all and min.insync.replicas=2 is choosing C and will return NOT_ENOUGH_REPLICAS rather than accept a write it cannot protect; min.insync.replicas=1 is choosing A and will lose the tail on failover.
  4. "A lock cannot give you mutual exclusion, because a process can pause longer than its lease. Only the resource can, by rejecting a stale fencing token." Then name the real implementations: etcd's mod revision, Kafka's producer and leader epochs, a version column in a conditional update. And note that the industry has converged on Raft — etcd, KRaft since Kafka 4.0, and Khepri, which became RabbitMQ's only metadata store in 4.3.
  5. "The partition key is the hardest decision to change later: too coarse and one consumer is your ceiling, too fine and you lose the ordering the domain needs. Key by the aggregate." Follow with the 2026 relaxation: Kafka 4.2 made share groups production-ready, so consumer parallelism is no longer capped at the partition count — for work that does not need ordering, which is the price.
  6. "Queue versus log is one difference with many consequences: a queue tracks state per message and deletes it, a log tracks one offset per consumer and keeps everything." Everything else — replay, fan-out, per-message dead-lettering, priorities — follows from that. And add that the line is blurring in both directions: Kafka got share groups, RabbitMQ got streams and, in 4.3, quorum queues with 32 priority levels, native delayed retry and about half the memory per message up to 32 KiB.
  7. "Exactly-once delivery does not exist; effectively-once processing does. Kafka's transactions are exactly-once within Kafka and cover nothing outside it." So the design rule is at-least-once transport plus an idempotent consumer — a natural upsert, a conditional update on a version, or an inbox row written in the same transaction as the effect.
  8. "Never dual-write. Put the event in the same transaction as the state change and let a relay publish it." Outbox with a poller and FOR UPDATE SKIP LOCKED, or CDC with Debezium; the metric that matters afterwards is the age of the oldest unpublished row, because a stalled relay is otherwise completely silent.
  9. "There is no rollback across services — there are compensations, and some steps cannot be compensated, so irreversible work goes last and the entity carries a semantic lock while the process runs." Then the modern shape: orchestrate processes, choreograph reactions, and use durable execution when there are long timers or humans in the loop — at the cost of deterministic workflow code and explicit versioning.
  10. "Retries are how a degradation becomes an outage: classify the failure first, retry at one layer with full jitter and a budget, and park what cannot succeed." Add the operational half: a DLQ without an alert, an owner and a tested replay path is a data-loss bucket, and when a dependency is fully down the right move is a circuit breaker that stops consumption so the backlog stays in the broker in order.
If you only get one sentence

"Distributed systems are the discipline of making partial failure survivable: you cannot make the network reliable, so you make every operation idempotent, every boundary explicit about what it guarantees, and every failure visible in a number somebody is paged on."
