01Delivery semantics & idempotency

docs: Kafka message delivery semantics
At-most-once
ack/commit before handling. Loses on crash. Only for metrics, traces, telemetry sampling.
At-least-once
ack/commit after handling. The default everywhere; duplicates are guaranteed, so the handler must be idempotent.
Effectively-once
at-least-once delivery + idempotent consumer (dedupe store). The only "exactly-once" that survives an external side effect.
Exactly-once (real)
only inside one transactional system: Kafka read-process-write (processing.guarantee=exactly_once_v2), Flink checkpoint + two-phase-commit sink. Never end-to-end into a third-party HTTP API.
Idempotency key
producer-chosen, stable across retries: {aggregateId}:{eventType}:{version}, not a random GUID per attempt. Put it in the message id / header, not the body.
Inbox dedupe
INSERT INTO inbox(message_id) ... ON CONFLICT DO NOTHING in the same transaction as the side effect; row count 0 means "already handled, ack and drop".
Dedupe window
size it as max retry horizon + broker retention + replay budget. 7 days is the common default; a 5-minute window is a bug waiting for a DLQ replay.
Poison message
bounded attempts, then park in a DLQ with the failure reason, headers and original topic — never nack(requeue: true) forever.
Ordering scope
ordering is per partition key / message group, never global. Key by the aggregate that must serialize (orderId), not by tenant, or one hot tenant serializes the topic.
Commutative > idempotent
prefer SET balance = 100 (absolute) over balance += 10 (relative); an absolute state message is naturally replayable.
// Idempotent consumer: dedupe and side effect in ONE local transaction.
await using var tx = await db.BeginTransactionAsync(ct);
var fresh = await db.ExecuteAsync(
    "INSERT INTO inbox (message_id, handler, seen_at) VALUES (@id, @h, now()) ON CONFLICT DO NOTHING",
    new { id = msg.Headers["idempotency-key"], h = nameof(OrderPlacedHandler) });
if (fresh == 0) { await tx.CommitAsync(ct); return Ack.Ok; }   // duplicate: ack, do nothing
await Handle(msg, ct);                                          // must write through the same tx
await tx.CommitAsync(ct);

Interview line. "Exactly-once delivery is impossible over an unreliable network (two-generals); exactly-once processing is achievable by pairing at-least-once delivery with an idempotent, transactional consumer." Say which of the two the question means before answering.

Share groups vs consumer groups
4.2 share groups give per-record acks and delivery counts with more consumers than partitions — a real work queue on Kafka. Consumer groups still own ordered, offset-based streaming.
Ack types (share groups)
ACCEPT / RELEASE / REJECT, plus RENEW 4.2, KIP-1222 to extend the lock for a long handler.
Streams DLQ
4.2, KIP-1034 built-in dead-letter queue for Kafka Streams — no more hand-rolled DeserializationExceptionHandler plumbing.
ZooKeeper
gone. KRaft is the only mode 4.0; an upgrade from a ZK cluster must land on 3.9 first.
Partition sizing
partitions = max(target throughput / per-consumer throughput, peak consumer count). Over-partitioning costs memory, open files and recovery time; under-partitioning caps parallelism forever.

03RabbitMQ & AMQP 1.0

docs: RabbitMQ 4.3
Queue type: quorum
the default choice 4.0. Raft-replicated, durable, poison-message handling via x-delivery-count. Classic mirrored queues were removed in 4.0.
Queue type: stream
append-only log, non-destructive reads, replayable by offset — Kafka-shaped workloads inside RabbitMQ. 4.2 AMQP 1.0 clients can push SQL-like filter expressions server-side.
Declare a quorum queue
x-queue-type=quorum, x-dead-letter-strategy=at-least-once, x-delivery-limit=5, x-max-in-memory-length
Exchange types
direct (exact key) · topic (order.*.eu) · fanout (broadcast) · headers (rare) · x-delayed-message (plugin, for scheduling)
Publisher confirms
mandatory for durability: channel.confirm_select(), then wait for basic.ack. Without it a publish is fire-and-forget even to a durable queue.
Prefetch
basic_qos(prefetch_count=N). Unset means unlimited: one consumer grabs the whole queue and nothing else scales. Start at N = ceil(target_rate × handler_p99), often 10–50.
Dead lettering
x-dead-letter-exchange + x-dead-letter-routing-key. Reason lands in the x-death header (rejected, expired, maxlen, delivery_limit).
Delayed retry
classic trick: a per-delay queue with x-message-ttl + DLX pointing back at the work exchange. Retry ladder 5s / 30s / 2m / 10m, then park.
Khepri
default metadata store 4.2, the only one 4.3. Cluster availability now needs a node majority — a two-node cluster is no longer a cluster.
Native AMQP 1.0
4.0 first-class alongside AMQP 0-9-1; over WebSocket and with filter expressions 4.1; rejection reasons carry the queue name 4.3.
Single Active Consumer
x-single-active-consumer=true gives per-queue ordering with hot standby; 4.3 AMQP 1.0 consumers are told when they become active.
Upgrade rule
4.3 is only supported from 4.2.x, and khepri_db should be enabled before the upgrade or the boot migrates Mnesia in place.
# Ops commands worth memorising
rabbitmqctl list_queues name type messages messages_unacknowledged consumers memory
rabbitmqctl list_consumers | grep -c ''            # consumer count sanity check
rabbitmq-diagnostics check_running check_local_alarms   # readiness, and flow-control alarms
rabbitmq-diagnostics memory_breakdown               # who is holding the memory
rabbitmqctl enable_feature_flag khepri_db           # required before upgrading to 4.3
rabbitmqctl set_policy DLX ".*" '{"dead-letter-exchange":"dlx"}' --apply-to queues

Gotcha. A RabbitMQ memory or disk alarm does not fail publishes — it blocks the TCP connection. Symptom is a producer that hangs with no error. Watch rabbitmq_alarms_*, not just queue depth.

04NATS, Pulsar & cloud brokers

docs: NATS · Pulsar · SQS · Service Bus

NATS / JetStream 2.14, 2026-04-30

Core vs JetStream
core NATS is at-most-once, no persistence, microsecond fan-out; JetStream adds streams, consumers, persistence and replay. Pick per subject, not per cluster.
Stream / consumer
nats stream add ORDERS --subjects 'orders.>' --retention limits --replicas 3; nats consumer add ORDERS billing --ack explicit --max-deliver 5
Retention policies
limits (log) · interest (drop once all consumers ack) · workqueue (drop on first ack — a real queue)
Delayed delivery
built-in message scheduler 2.12, extended 2.14: publish now with a future timestamp header, no external scheduler.
Atomic batch publish
2.12 N messages staged and committed or rejected as one unit — the closest thing to a transaction in NATS.
Strict mode
2.12 invalid JetStream requests are now rejected, not just logged. A silent 2.10-era bug becomes a hard error on upgrade.
Key-value / object store
nats kv add CONFIG --history 5 — KV is a compacted stream; watchers give you a change feed for free.

Pulsar 4.2.0, 2026-03-31

Subscription types
Exclusive · Failover (ordered with standby) · Shared (round-robin queue) · Key_Shared (per-key ordering and more consumers than partitions)
Why reach for it
tiered storage, geo-replication and multi-tenancy built in; broker/storage split (BookKeeper) lets you scale them independently. Cost: two systems to run.
Roadmap
5.0.0-M1 milestones are out; 5.0 GA expected later in 2026 — do not plan a migration on it yet.

05Outbox, inbox & CDC

docs: Debezium outbox event router
The problem
dual write: db.Save() then bus.Publish() can crash between the two. No amount of retry logic fixes it; only a shared transaction does.
Transactional outbox
write the event into an outbox table in the same transaction as the state change; a relay publishes it after commit. At-least-once by construction.
Outbox table shape
id uuid, aggregate_type, aggregate_id, type, payload jsonb, headers jsonb, created_at, processed_at null — index on (processed_at, created_at).
Relay: polling
SELECT ... WHERE processed_at IS NULL ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 100. Simple, no extra infra, adds poll-interval latency.
Relay: CDC (preferred at scale)
Debezium tails the WAL/binlog; zero query load on the primary, sub-second latency, survives app restarts.
Debezium
3.5.1.Final (2026-05-14) current; 3.6 in alpha. The Quarkus outbox extension needs Hibernate 7+ 3.3.
Postgres replication
wal_level=logical, publication + slot per consumer. Unconsumed slots pin WAL and fill the disk — alert on pg_replication_slots.confirmed_flush_lsn lag.
Failover slots
PG 17 CREATE SUBSCRIPTION ... WITH (failover = true) + sync_replication_slots=on on the standby, so a promotion does not lose the slot. Before 17, a failover meant a full re-snapshot.
Listen-to-yourself
alternative shape: publish first, and let your own consumer apply the state change. Removes the outbox but makes the write path async and the read-your-writes story harder.
Inbox
the consumer mirror of the outbox: dedupe table keyed by message_id, written in the handler transaction (see 01). Prune with a retention job, not by hand.
Ordering through CDC
route by aggregate id so all events for one aggregate land on one partition — Debezium's outbox.event.router with route.by.field=aggregate_id.
Snapshot cost
an initial Debezium snapshot locks/reads the whole table; use incremental snapshots (signal table) on anything over a few million rows.
-- Outbox write and relay claim, Postgres.
BEGIN;
UPDATE orders SET status = 'placed' WHERE id = $1;
INSERT INTO outbox (id, aggregate_type, aggregate_id, type, payload, headers)
VALUES (gen_random_uuid(), 'order', $1, 'com.acme.order.placed.v1', $2,
        jsonb_build_object('idempotency-key', $1 || ':placed:1', 'traceparent', $3));
COMMIT;

-- Relay: many workers, no contention, no double-send.
UPDATE outbox SET processed_at = now()
WHERE id IN (SELECT id FROM outbox WHERE processed_at IS NULL
             ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 100)
RETURNING id, type, payload, headers;

Gotcha. An outbox relay that marks rows processed before the broker confirms turns at-least-once into at-most-once. Mark after the publisher confirm/delivery report, and accept the duplicate.

06Sagas & durable execution

docs: Temporal · saga pattern
Choreography
each service reacts to events, no coordinator. Cheap to start, no single point of failure; the flow exists only in everyone's heads and no one can answer "where is order 42 stuck?".
Orchestration
one workflow owns the steps and compensations. Visible state, easy timeouts and queries; the orchestrator is a component you now operate. Default to this past ~4 steps.
Compensation
semantic undo, not rollback: RefundPayment, not DELETE. Compensations must themselves be idempotent and retriable, and must tolerate "the thing was never done".
Pivot step
the first irreversible action (email sent, card captured). Order the saga so every retryable/compensatable step comes first and the pivot is last.
Durable execution
Temporal / Restate / Azure Durable Functions: workflow code is deterministic and replayed from an event history, so a process crash resumes mid-function. Replaces hand-written state machines.
Determinism rule
inside workflow code: no DateTime.Now, no Guid.NewGuid(), no I/O, no unordered iteration. Use workflow.Now(), side effects, and activities.
Activity vs workflow
activities do I/O and may run at-least-once (make them idempotent); workflows only decide. Activity timeouts: StartToClose is the one you must always set.
Worker versioning
Temporal pins running workflows to the worker build that started them, so a deploy cannot break in-flight executions — the modern replacement for patched() branches in workflow code.
Serverless workers
2026: Temporal Cloud can run workers on AWS Lambda, scaling and shutting them down from workload metrics. New enough to be a good "what have you read lately" answer.
Timeouts as first-class
every saga step needs a deadline and a timeout branch; an un-timed-out step is a stuck order that only a human ever finds.
Process manager
the older .NET name for the same thing (NServiceBus/MassTransit sagas) — correlated by a saga id, persisted per step. Still everywhere in existing code.
// Temporal-style workflow: compensations pushed on a stack, run in reverse.
var comp = new Stack<Func<Task>>();
try {
    var res = await Workflow.ExecuteActivityAsync((Acts a) => a.ReserveStock(order), Opts);
    comp.Push(() => Workflow.ExecuteActivityAsync((Acts a) => a.ReleaseStock(res.Id), Opts));
    await Workflow.ExecuteActivityAsync((Acts a) => a.CapturePayment(order), Opts);  // pivot: last
} catch (ActivityFailureException) {
    while (comp.Count > 0) await comp.Pop()();   // compensate in reverse order
    throw;
}

.NET note, 2026. MassTransit v9 ships under a commercial licence (v8 stays open source with security patches through 2026). MIT alternatives in active use: Wolverine and Rebus; NServiceBus if you are buying support anyway. This is now a real architecture decision, not trivia.

07Consistency, consensus & clocks

docs: Raft · Jepsen consistency models
CAP, stated properly
during a partition, choose consistency or availability. It says nothing about the non-partitioned case — that is PACELC's "else latency or consistency", the trade-off you actually make daily.
Linearizable
single-object, real-time order. Cost: a quorum round trip per read unless you use leases. Raft/Paxos give you this.
Serializable
multi-object, some serial order — not necessarily real-time. Serializable + linearizable = strict serializable (Spanner, CockroachDB).
Read-your-writes
the session guarantee users actually notice. Cheapest fix: route a user's reads to the leader (or the replica past their write LSN) for a few seconds after a write.
Quorum arithmetic
R + W > N for overlap; W > N/2 to avoid split writes. N=3,W=2,R=2 is the workhorse; RF3 + min.insync=2 is the same idea in Kafka.
Raft in one line
leader election by randomised timeout, append-entries replication, commit once a majority persists. Used by etcd, Kafka KRaft, RabbitMQ quorum queues and Khepri, NATS JetStream, CockroachDB.
Even node counts
never. 3 tolerates 1 failure, 4 also tolerates only 1 — you paid for latency and got no extra fault tolerance. 5 tolerates 2.
Split brain
prevented by majority quorum + fencing tokens (monotonic epoch numbers checked by the storage layer). A lease alone is not a lock: a GC pause outlives it.
Logical clocks
Lamport = happens-before only; vector clocks detect concurrency at O(nodes) size; hybrid logical clocks (HLC) bound the skew and are what modern databases actually use.
Wall-clock rule
never order events, compute timeouts or generate ids from DateTime.Now across machines. NTP skew is 10–100 ms and can go backwards; use monotonic clocks for durations.
CRDTs
merge without coordination (G-counter, OR-set, LWW-register). Buy AP availability at the price of "last write wins" surprises; great for presence, carts, collaborative text.
Idempotent id generation
ULID/UUIDv7 (time-ordered, index-friendly) beat UUIDv4 for keys; Snowflake ids need a coordinated worker id.
Failure detection
phi-accrual / SWIM gossip beat fixed timeouts. Anything below ~2× the network p99 turns a GC pause into a topology change.

Design-review question that pays. "What is the consistency requirement of this specific read?" Most reads in a system tolerate seconds of staleness; paying linearizable cost everywhere is the most common self-inflicted latency wound.

08Retries, timeouts & backpressure

docs: Polly resilience strategies · AWS: backoff with jitter
Retry only what is safe
retry on connect/timeout/5xx/429 with an idempotency key. Never blind-retry a non-idempotent POST — that is how you double-charge.
Backoff formula
full jitter: sleep = random(0, min(cap, base × 2^attempt)). Base 100–200 ms, cap 20–30 s, 3–5 attempts. Without jitter you rebuild the thundering herd you were avoiding.
Retry budget
cap retries at ~10% of request volume (client-side token bucket). Per-call limits still let a whole fleet retry a dying dependency to death.
Retry amplification
3 retries × 3 layers = 27 calls. Retry at one layer — usually the outermost that owns the idempotency key — and pass a deadline down so inner layers stop.
Timeouts
every network call gets one. Set it from the dependency's p99, not a round number; total budget = sum of downstream timeouts, so propagate a deadline (grpc-timeout, CancellationToken).
Circuit breaker
open on failure ratio over a sampled window (e.g. >50% of ≥20 calls in 30 s), half-open probe after 15–30 s. Count-based breakers trip on low-traffic noise.
Bulkhead
separate connection pools / concurrency limits per dependency so one slow downstream cannot consume every thread.
Load shedding
reject early with 429/503 + Retry-After when the queue is over its latency SLO. Shedding 5% keeps p99 for 95%; queueing everything keeps p99 for nobody.
Backpressure, pull
consumer-paced brokers (Kafka poll, SQS receive, JetStream pull) are naturally back-pressured; concurrency is the knob, prefetch is the trap.
Backpressure, push
bounded channels + BoundedChannelFullMode.Wait in .NET, Flow frames in AMQP 1.0, gRPC/HTTP-2 stream windows. Unbounded queues turn a latency problem into an OOM.
Little's Law
L = λ × W: concurrency = arrival rate × latency. 500 rps × 200 ms ⇒ 100 in-flight. Size pools, prefetch and consumer counts from it instead of guessing.
Hedged requests
fire a second attempt at p95 latency; cuts tail latency for read-only, idempotent calls at ~5% extra load. Never hedge writes.
Retry ladder + DLQ
fast in-process retries (2–3, ms) → delayed topic/queue retries (s to min) → DLQ with reason. Alarm on DLQ depth > 0, not on rate.
// Polly v8 pipeline: order matters — timeout inside retry, breaker outside.
var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddRetry(new RetryStrategyOptions<HttpResponseMessage> {
        MaxRetryAttempts = 4, BackoffType = DelayBackoffType.Exponential,
        UseJitter = true, Delay = TimeSpan.FromMilliseconds(200) })
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions<HttpResponseMessage> {
        FailureRatio = 0.5, MinimumThroughput = 20,
        SamplingDuration = TimeSpan.FromSeconds(30), BreakDuration = TimeSpan.FromSeconds(20) })
    .AddTimeout(TimeSpan.FromSeconds(2))          // per-attempt
    .Build();

Autoscaling. Scale consumers on queue depth or consumer lag, never CPU — a blocked consumer is idle. KEDA (CNCF graduated, 60+ scalers) does this on Kubernetes and scales to zero; pair it with a maxReplicaCount below the partition count for Kafka, since extra pods above it just idle.

09Schemas, envelopes & contracts

docs: schema evolution & compatibility · CloudEvents · AsyncAPI 3.1.0
Format choice
Protobuf for RPC and high-volume topics · Avro where schema registry + big-data tooling dominates · JSON Schema when humans and heterogeneous consumers must read it.
Compatibility modes
BACKWARD (default: new schema reads old data — upgrade consumers first) · FORWARD (old schema reads new data — upgrade producers first) · FULL · *_TRANSITIVE against all versions, not just the last.
Always-safe changes
add an optional field with a default; add an enum value only if consumers have an unknown-value branch; never rename, never change a type, never reuse a Protobuf field number.
Protobuf hygiene
reserved 4, 7; reserved "old_name"; after deleting a field. Field numbers 1–15 cost one byte — spend them on the hot fields.
Registry wire format
Confluent framing: magic byte 0x00 + 4-byte big-endian schema id + payload. A "corrupt Avro" bug is usually someone deserializing without stripping those 5 bytes.
Schema Registry 8.x
adds guid, subject, ts, deleted to JSON responses; clients older than 6.2 throw UnrecognizedPropertyException on GET /schemas/ids/{id}. Pin client versions when upgrading.
Envelope: CloudEvents 1.0
required id, source, specversion, type; useful optional subject, time, datacontenttype, dataschema. Binary mode maps them to ce-* headers — keeps the payload clean and lets brokers filter on them.
Versioning in the type
com.acme.order.placed.v1. Bump to v2 for a breaking change and publish both for one deprecation window; never mutate v1's meaning.
AsyncAPI
3.1.0 (2026-01-31). 3.x separates channels from operations, so one channel can be sent to and received from. Generate docs and code from it; treat it as the event-side OpenAPI.
Event shape
event-carried state transfer (fat event, no callback, may be stale) vs notification (thin, forces a read, chattier). Pick per topic and write it down; mixing silently is what makes consumers fragile.
Consumer-driven contracts
Pact for message contracts, or registry compatibility checks in CI. A schema check that runs only at deploy is a schema check that fires in production.
PII
topics are replayable and long-retained. Crypto-shredding (per-subject key, delete the key) is the practical GDPR answer; compaction with tombstones alone does not delete history from every consumer.

10Observability & ops numbers

docs: OpenTelemetry messaging semantic conventions
Trace propagation
put traceparent (and tracestate, baggage) in message headers, never the body. Producer span send links to consumer span process — a link, not a child, for batched consumption.
Span attributes
messaging.system, messaging.destination.name, messaging.operation.name (send/receive/process/settle), messaging.message.id, server.address.
Semconv status
messaging conventions are still development, not stable. Opt in with OTEL_SEMCONV_STABILITY_OPT_IN=messaging, or messaging/dup to emit old and new during a migration.
Kafka-specific
messaging.kafka.offset, ...message.key, ...consumer.group, and messaging.kafka.cluster.id (recent addition) — the last one saves you in multi-cluster estates.
The four signals to alert on
consumer lag (and lag trend), age of the oldest unprocessed message, DLQ depth, handler error ratio. Throughput alone hides a stopped consumer.
Lag vs latency
lag in records is meaningless across topics; alert on estimated time-to-drain = lag / consume_rate, or on record timestamp age.
Kafka broker metrics
UnderReplicatedPartitions (must be 0), OfflinePartitionsCount (must be 0), ActiveControllerCount (exactly 1 cluster-wide), request queue time p99.
RabbitMQ metrics
rabbitmq_queue_messages_unacked (stuck consumers), rabbitmq_alarms_memory_used_watermark, per-queue consumer count = 0 on a live queue.
Replay drill
practise it: reset the group to a timestamp, run in a shadow consumer group, compare outputs. A replay path first exercised during an incident is not a replay path.
Kill-switch
a per-consumer feature flag that pauses consumption without a deploy; the fastest safe action during a bad-message storm.
Capacity rules of thumb
Kafka: keep partitions per broker in the low thousands and a partition's retained data under ~50 GB to keep recovery fast. RabbitMQ: keep quorum queues in the thousands, and watch segment file counts (Prometheus endpoint 4.2).
Latency budget
same-AZ RTT ~0.5 ms, cross-AZ ~1–2 ms, cross-region 60–150 ms. A cross-region synchronous quorum write is a design decision, not a config value.

Gotchas, one line each

  • Adding Kafka partitions rehashes keys: ordering per key is only preserved from that moment forward.
  • acks=all with min.insync.replicas=1 is acks=1 wearing a costume.
  • A consumer that is slower than max.poll.interval.ms gets evicted and replays — every time, forever, until you cut the batch size.
  • RabbitMQ quorum queues keep the whole message index in memory: millions of tiny messages OOM a node long before disk fills.
  • Unlimited prefetch turns a fleet of consumers into one consumer with an audience.
  • SQS Standard can deliver a message twice even without a failure — dedupe is not optional.
  • An unread Postgres replication slot will fill the disk and take the primary down; alert on slot lag, not just disk.
  • A DLQ nobody has a replay tool for is a delete queue with extra storage cost.
  • Retrying a timeout on a non-idempotent endpoint is how a double payment is born; the timeout never told you the write failed.
  • Compacted topics never delete a key without an explicit null tombstone — and the tombstone itself expires after delete.retention.ms.
  • Two-node clusters (RabbitMQ 4.3, etcd, any Raft system) have worse availability than one node: either failure loses quorum.
  • Consumer lag of zero on a topic with no producers proves nothing; alert on message age too.
  • Scaling Kafka consumers above the partition count adds cost and no throughput — use share groups if you need more workers than partitions.

Freshest thing to say out loud. Kafka 4.2 (2026-02-17) made share groups GA, so "use Kafka for streams and RabbitMQ/SQS for work queues" is no longer automatically true — and RabbitMQ 4.3 (2026-04-23) removed Mnesia, so RabbitMQ clusters now need an odd node count and a majority quorum just like Kafka's KRaft controllers. Both are recent enough that many teams' mental models are still on the old shape.
