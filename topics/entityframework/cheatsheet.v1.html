01 Packages, DbContext, registration

EF Core 10 needs .NET 10; there is no .NET Framework target. Provider version tracks the EF version.

Core + provider (SQL Server)
dotnet add package Microsoft.EntityFrameworkCore.SqlServer -v 10.0.11
Other providers
Npgsql.EntityFrameworkCore.PostgreSQL · Pomelo.EntityFrameworkCore.MySql · Microsoft.EntityFrameworkCore.Sqlite · Microsoft.EntityFrameworkCore.Cosmos · Oracle.EntityFrameworkCore
Design-time (migrations, scaffold)
Microsoft.EntityFrameworkCore.Design — PrivateAssets="all"; only the startup project needs it
CLI tool
dotnet tool install --global dotnet-ef --version 10.*
Register a context
builder.Services.AddDbContext<AppDb>(o => o.UseSqlServer(cs)) — scoped lifetime; one context per request/unit of work
Pooled context (hot path)
AddDbContextPool<AppDb>(...) — reuses instances; no injected scoped state in the ctor
Factory (Blazor, background work)
AddDbContextFactory<AppDb>(...) → await using var db = await f.CreateDbContextAsync()
Retry on transient failure
o.UseSqlServer(cs, s => s.EnableRetryOnFailure()) — then you must own transactions via an execution strategy, see 06
Diagnostics for dev only
o.EnableSensitiveDataLogging().EnableDetailedErrors() — EF 10 redacts inlined constants from logs by default; this switch turns them back on
public sealed class AppDb(DbContextOptions<AppDb> options) : DbContext(options)
{
    public DbSet<Blog> Blogs => Set<Blog>();
    public DbSet<Post> Posts => Set<Post>();

    protected override void OnModelCreating(ModelBuilder b)
        => b.ApplyConfigurationsFromAssembly(typeof(AppDb).Assembly);

    protected override void ConfigureConventions(ModelConfigurationBuilder c)
        => c.Properties<decimal>().HavePrecision(18, 2);   // EF6+: model-wide defaults
}

Lifetime rule. DbContext is not thread-safe: one concurrent operation per instance. Parallel work needs one context each (use the factory), or you get InvalidOperationException: A second operation was started on this context instance.

02 Modelling: conventions & fluent API

Conventions first, fluent API for anything the convention gets wrong. Data annotations only for the trivial cases.

Key
Id / <Type>Id by convention · b.HasKey(x => x.Id) · composite b.HasKey(x => new { x.A, x.B })
Required / optional
nullability decides it under NRTs; b.Property(x => x.Name).IsRequired().HasMaxLength(200)
One-to-many
b.HasOne(p => p.Blog).WithMany(x => x.Posts).HasForeignKey(p => p.BlogId).OnDelete(DeleteBehavior.Cascade)
Many-to-many
b.HasMany(x => x.Tags).WithMany(t => t.Posts).UsingEntity<PostTag>() — skip navigations, EF Core 5+; no join entity needed unless it carries payload
Owned value object
b.OwnsOne(x => x.Address) — has identity, one instance per owner
Complex type (preferred value object)
b.ComplexProperty(x => x.Address) — EF Core 8+; no identity, no tracking, struct or class; EF 10 adds optional complex properties
Value conversion
b.Property(x => x.Status).HasConversion<string>() · strongly typed ids: HasConversion(v => v.Value, v => new OrderId(v))
Global convention
c.Properties<string>().AreUnicode(false) in ConfigureConventions (EF Core 6+); custom IModelFinalizingConvention (EF Core 7+)
Index / unique
b.HasIndex(x => x.Slug).IsUnique().HasFilter("[Slug] IS NOT NULL")
Inheritance
TPH default (HasDiscriminator) · UseTptMappingStrategy() · UseTpcMappingStrategy() (EF Core 7+, usually the fastest of the three)
Query filter
b.HasQueryFilter(x => !x.IsDeleted); EF 10 names them: b.HasQueryFilter("SoftDelete", x => !x.IsDeleted) + IgnoreQueryFilters(["SoftDelete"])
Concurrency token
b.Property(x => x.RowVersion).IsRowVersion() · [Timestamp]
Keyless (views, raw projections)
b.HasNoKey().ToView("vw_Sales")
Named default constraint
.HasDefaultValueSql("GETUTCDATE()", "DF_Post_Created") · model-wide modelBuilder.UseNamedDefaultConstraints() — EF Core 10
public sealed class PostConfig : IEntityTypeConfiguration<Post>
{
    public void Configure(EntityTypeBuilder<Post> b)
    {
        b.ToTable("Posts", t => t.HasCheckConstraint("CK_Post_Rating", "[Rating] BETWEEN 0 AND 5"));
        b.Property(p => p.Title).IsRequired().HasMaxLength(200);
        b.ComplexProperty(p => p.Seo);                       // EF8+ value object, no identity
        b.HasQueryFilter("SoftDelete", p => !p.IsDeleted);   // EF10 named filter
        b.HasIndex(p => new { p.BlogId, p.PublishedOn });
    }
}

03 Querying: LINQ that translates

Everything before the first ToList/AsEnumerable is SQL. Anything EF cannot translate throws since EF Core 3.0 — it no longer silently evaluates on the client.

Read-only read
await db.Blogs.AsNoTracking().Where(b => b.Rating > 3).ToListAsync(ct)
Project, don't load entities
.Select(b => new BlogDto(b.Id, b.Name, b.Posts.Count)) — one SQL statement, no tracking cost, no lazy loading
Single row
FirstOrDefaultAsync (TOP 1) · SingleOrDefaultAsync (TOP 2, throws on 2) · FindAsync(id) (identity-map hit first, no round trip)
Paging
.OrderBy(b => b.Id).Skip(n).Take(20) — unordered Skip/Take is undefined; keyset paging (Where(b => b.Id > last)) beats OFFSET on deep pages
IN over a collection
.Where(b => ids.Contains(b.Id)) — EF 10 sends @ids1, @ids2, … with parameter padding instead of inlined constants or a JSON array
Left / right join
.LeftJoin(db.Depts, s => s.DeptId, d => d.Id, (s, d) => new { s, d }) — EF Core 10 + .NET 10; replaces the GroupJoin/SelectMany/DefaultIfEmpty dance. FullJoin lands in EF 11
Grouping
.GroupBy(p => p.BlogId).Select(g => new { g.Key, Count = g.Count(), Max = g.Max(p => p.Rating) }) — group-then-materialize-entities does not translate; aggregate in the Select
Set-based existence
await db.Posts.AnyAsync(p => p.BlogId == id, ct) — never Count() > 0
Streaming
await foreach (var b in db.Blogs.AsAsyncEnumerable().WithCancellation(ct)) — EF 11 analyzer flags ToAsyncEnumerable as the wrong one
Provider functions
EF.Functions.Like(b.Name, "%ef%") · EF.Functions.DateDiffDay(a, b) · EF.Functions.Contains(...) (full-text)
Force server evaluation of a constant
EF.Constant(x) (inline literal) vs EF.Parameter(x) (force a parameter) — EF Core 8/9, for plan-cache tuning
Split a cartesian explosion
.AsSplitQuery() · default it with o.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery)
Compose a filter
IQueryable<Blog> q = db.Blogs; if (r != null) q = q.Where(b => b.Rating >= r);
See the SQL
query.ToQueryString() — EF Core 5+; prints the SQL plus parameter declarations

Async everywhere, or nowhere. Sync ToList() on a web request burns a thread-pool thread per query; mixing the two is how thread-pool starvation shows up under load. Pass the CancellationToken — EF ships it to the provider.

04 Loading related data

Three ways in, one to avoid. Projection is a fourth and usually the right answer.

Eager
db.Blogs.Include(b => b.Posts).ThenInclude(p => p.Author)
Filtered include
.Include(b => b.Posts.Where(p => !p.IsDeleted).OrderByDescending(p => p.Date).Take(5)) — EF Core 5+
Include everything one level
.Include(b => b.Posts).AsSplitQuery() — two Includes of collections in one query = row multiplication
Explicit
await db.Entry(blog).Collection(b => b.Posts).LoadAsync() · .Reference(p => p.Blog).LoadAsync()
Explicit with a filter
await db.Entry(blog).Collection(b => b.Posts).Query().Where(p => p.Rating > 3).ToListAsync()
Lazy (opt-in, usually a mistake)
o.UseLazyLoadingProxies() + public virtual ICollection<Post> Posts — the classic N+1 generator; disabled by default in EF Core, was on by default in EF6
Projection instead of Include
.Select(b => new { b.Name, Recent = b.Posts.OrderByDescending(p => p.Date).Take(3).Select(p => p.Title) })
Auto-include a navigation
b.Navigation(x => x.Owner).AutoInclude() (EF Core 6+); opt out per query with .IgnoreAutoIncludes()
Load the FK only
keep the shadow/explicit FK property and read post.BlogId — no join at all

Cartesian explosion. Include of two sibling collections multiplies rows (10 posts × 20 tags = 200 rows of duplicated blog columns). Symptom: a query that returns a handful of entities but transfers megabytes. Fix: AsSplitQuery(), or project.

05 Change tracking & SaveChanges

One SaveChanges = one transaction, ordered and batched by EF. Tracking is what makes it work and what makes it slow.

Insert
db.Blogs.Add(blog); await db.SaveChangesAsync(ct); — graph is added too; AddRange for many
Update (tracked)
load, mutate, SaveChangesAsync — EF writes only changed columns
Update (disconnected)
db.Attach(e).Property(x => x.Name).IsModified = true; — prefer this to db.Update(e), which marks every column dirty
Delete
db.Remove(new Blog { Id = id }); — no SELECT needed when you have the key
Entry state
db.Entry(e).State ∈ Detached | Unchanged | Added | Modified | Deleted
Original vs current values
db.Entry(e).OriginalValues["Name"] · .CurrentValues.SetValues(dto)
Audit hook
override SaveChangesAsync and walk ChangeTracker.Entries<IAuditable>(); call ChangeTracker.DetectChanges() first if you disabled it
Interceptor (cleaner hook)
o.AddInterceptors(new AuditInterceptor()) : SaveChangesInterceptor / DbCommandInterceptor / IMaterializationInterceptor
Turn off tracking globally for reads
o.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking), opt back in with .AsTracking()
Identity resolution without tracking
.AsNoTrackingWithIdentityResolution() — EF Core 5+; dedupes repeated rows in the graph
Clear the tracker
db.ChangeTracker.Clear() — EF Core 5+; cheaper than a new context in a long loop
Debug the graph
db.ChangeTracker.DebugView.LongView
Optimistic concurrency
catch DbUpdateConcurrencyException, inspect ex.Entries, refresh with GetDatabaseValuesAsync(), retry
try { await db.SaveChangesAsync(ct); }
catch (DbUpdateConcurrencyException ex)
{
    foreach (var entry in ex.Entries)
    {
        var db_ = await entry.GetDatabaseValuesAsync(ct);
        if (db_ is null) { /* deleted by someone else */ continue; }
        entry.OriginalValues.SetValues(db_);          // client wins, retry once
    }
    await db.SaveChangesAsync(ct);
}

Cost model. DetectChanges is O(tracked entities × properties) and runs on every SaveChanges, Find and most queries. 10 000 tracked entities in one context is a design smell — batch in chunks, or use ExecuteUpdate (06).

06 Bulk ops, raw SQL, transactions

Set-based work bypasses the change tracker entirely: no entities loaded, no SaveChanges, no interceptor on SaveChanges.

Bulk update
await db.Posts.Where(p => p.Old).ExecuteUpdateAsync(s => s.SetProperty(p => p.Archived, true), ct) — EF Core 7+
Conditional bulk update
EF Core 10 allows a statement-bodied lambda: s => { s.SetProperty(...); if (x) s.SetProperty(...); }
Bulk delete
await db.Logs.Where(l => l.At < cutoff).ExecuteDeleteAsync(ct) — ignores cascade config: the database's FK rules apply
Raw SQL returning entities
db.Blogs.FromSql($"SELECT * FROM Blogs WHERE Rating > {min}") — EF Core 8+; interpolation becomes parameters. Composable: .Where(...).ToListAsync()
Raw SQL, unmapped type
db.Database.SqlQuery<int>($"SELECT Id FROM Blogs") — EF Core 8+
Non-query SQL
await db.Database.ExecuteSqlAsync($"EXEC Rebuild {id}", ct)
The unsafe one
FromSqlRaw / ExecuteSqlRaw — EF Core 10 ships an analyzer that warns on string concatenation into these (SQL injection)
Explicit transaction
await using var tx = await db.Database.BeginTransactionAsync(ct); … await tx.CommitAsync(ct);
Transaction + retrying strategy
wrap the whole unit: await db.Database.CreateExecutionStrategy().ExecuteAsync(async () => { … }) — mandatory once EnableRetryOnFailure is on
Share a transaction (Dapper etc.)
db.Database.UseTransaction(dbTransaction) · db.Database.GetDbConnection()
Isolation level
BeginTransactionAsync(IsolationLevel.Serializable, ct)
Third-party bulk copy
EFCore.BulkExtensions / SqlBulkCopy for 10k+ row inserts — EF batches, but it still sends parameterised INSERTs

ExecuteUpdate is not SaveChanges. It runs immediately, outside any tracked state, and leaves already-tracked entities stale. Run it first, or ChangeTracker.Clear() after. It also skips soft-delete query filters unless you keep the Where yourself.

Install / update the tool

Add a migration
dotnet ef migrations add AddPostRating -p src/Infra -s src/Api -o Migrations
Apply
dotnet ef database update · to a point dotnet ef database update AddPostRating · undo all dotnet ef database update 0
Drop the last (unapplied) migration
dotnet ef migrations remove
List / inspect
dotnet ef migrations list · dotnet ef dbcontext info · dotnet ef dbcontext list
CI drift gate
dotnet ef migrations has-pending-model-changes — EF Core 9+; non-zero exit if the model moved without a migration
Deployment SQL
dotnet ef migrations script --idempotent -o migrate.sql · range script From To
Self-contained bundle
dotnet ef migrations bundle --self-contained -r linux-x64 -o efbundle — EF Core 6+; the one artefact to ship to a locked-down environment
Reverse-engineer a database
dotnet ef dbcontext scaffold "$CS" Microsoft.EntityFrameworkCore.SqlServer -o Models -t Orders --use-database-names --no-onconfiguring
Compiled model (large models)
dotnet ef dbcontext optimize --output-dir Generated — EF Core 6+; EF Core 9+ can regenerate it on build via MSBuild
NativeAOT / precompiled queries
dotnet ef dbcontext optimize --precompile-queries --nativeaot — experimental in EF Core 9 and still experimental in EF Core 10; not production-ready
Common flags
-c AppDb (context) · -p project · -s startup project · --no-build · --connection · --verbose · --json
Apply at startup (dev only)
await db.Database.MigrateAsync() — never EnsureCreated() alongside migrations; the two are mutually exclusive
Coming in EF 11
.config/dotnet-ef.json for per-repo defaults · dotnet ef database update Init --add (create + apply in one step) · --offline · --context "*"
public partial class AddPostRating : Migration
{
    protected override void Up(MigrationBuilder b)
    {
        b.AddColumn<int>("Rating", "Posts", nullable: false, defaultValue: 0);
        b.Sql("UPDATE Posts SET Rating = 3 WHERE Legacy = 1;");   // data moves here, not in code
        b.CreateIndex("IX_Posts_Rating", "Posts", "Rating");
    }
    protected override void Down(MigrationBuilder b) => b.DropColumn("Rating", "Posts");
}

EF Core 10 breaking change. database update no longer wraps all migrations in one transaction — each migration gets its own. A failure part-way now leaves earlier migrations applied. Expand/contract your schema changes and make them re-runnable.

08 JSON, complex types, vectors

Where EF Core 8–11 actually moved: document-shaped columns as first-class model members, and AI workloads on relational stores.

Owned entity as a JSON column
b.OwnsOne(x => x.Metadata, o => o.ToJson()); — EF Core 7+
Complex type as a JSON column
b.ComplexProperty(x => x.Details, o => o.ToJson()); — EF Core 10; on SQL Server 2025 it uses the native json type
Query into JSON
db.Blogs.Where(b => b.Details.Views > 100) — translates to OPENJSON/JSON_VALUE
Update inside JSON
ExecuteUpdateAsync(s => s.SetProperty(b => b.Details.Views, b => b.Details.Views + 1)) — EF Core 10; partial update, no full-document rewrite
Primitive collection
public List<int> Scores { get; set; } maps to a JSON column by convention — EF Core 8+; Contains translates
Vector column (SQL Server 2025 / Azure SQL)
[Column(TypeName = "vector(1536)")] public SqlVector<float> Embedding { get; set; } — EF Core 10
Vector distance search
.OrderBy(b => EF.Functions.VectorDistance("cosine", b.Embedding, query)).Take(5)

EF.Functions.FullTextContains(b.Body, "ef core") · FullTextScore · hybrid via EF.Functions.Rrf(...) — EF Core 10

Index a JSON path

// EF10: value object in a native json column, queried and patched server-side
modelBuilder.Entity<Blog>().ComplexProperty(b => b.Details, d => d.ToJson());

09 Performance & diagnostics

The order that pays: fewer round trips → less tracking → narrower projections → better SQL → caching.

Biggest wins, in order
1. kill N+1 (project or Include) · 2. AsNoTracking on reads · 3. Select only needed columns · 4. AsSplitQuery on wide graphs · 5. index the predicate
Pooling
AddDbContextPool — removes context construction + model resolution per request
Compiled model
dotnet ef dbcontext optimize then o.UseModel(AppDbModel.Instance) — pays off past ~100 entity types
Compiled query
EF.CompileAsyncQuery((AppDb d, int id) => d.Blogs.FirstOrDefault(b => b.Id == id)) — skips LINQ→SQL each call; EF already auto-caches, so measure first
Plan-cache control
EF.Parameter(x) to force parameterisation, EF.Constant(x) to inline — EF 10 parameterises collections and pads counts to keep plans reusable
Batching
o.UseSqlServer(cs, s => s.MaxBatchSize(100)) — EF batches inserts/updates into one round trip by default
See the SQL for one query
query.ToQueryString()
Log all SQL in dev
o.LogTo(Console.WriteLine, [DbLoggerCategory.Database.Command.Name], LogLevel.Information)
Metrics / traces
OpenTelemetry sources Microsoft.EntityFrameworkCore and Microsoft.Data.SqlClient; EventCounters Microsoft.EntityFrameworkCore
Find the N+1 in prod
a DbCommandInterceptor that counts commands per request and logs when the count exceeds a threshold
Warn on bad patterns
o.ConfigureWarnings(w => w.Throw(RelationalEventId.MultipleCollectionIncludeWarning))
Don't
second-level cache libraries before fixing queries; ToList() mid-pipeline; Count() where Any() works; entity graphs as API DTOs

10 Testing & concurrency

Test against the real provider; the in-memory provider does not enforce constraints and is not maintained for new work.

Preferred test database
Testcontainers (Testcontainers.MsSql / .PostgreSql) + MigrateAsync() per fixture
Fast local alternative
SQLite in-memory: var c = new SqliteConnection("Filename=:memory:"); c.Open(); o.UseSqlite(c); — keep the connection open for the DB's lifetime
Avoid
UseInMemoryDatabase — no FK/unique enforcement, no relational SQL semantics; Microsoft explicitly recommends against it for testing
Fresh state per test
transaction per test + rollback, or Respawn to reset tables
Assert the SQL, not the DB
Assert.Contains("LEFT JOIN", query.ToQueryString())
Concurrency: rowversion
b.Property(x => x.RowVersion).IsRowVersion() — SQL Server; on PostgreSQL use UseXminAsConcurrencyToken()
Concurrency: any column
b.Property(x => x.Price).IsConcurrencyToken()
Pessimistic lock
raw SQL: FromSql($"SELECT * FROM Orders WITH (UPDLOCK, ROWLOCK) WHERE Id = {id}") inside a transaction
Transient-fault retries
EnableRetryOnFailure(maxRetryCount: 6, maxRetryDelay: TimeSpan.FromSeconds(30), null) + execution strategy around explicit transactions
Idempotent writes
unique index + catch DbUpdateException with the provider's duplicate-key number (SQL Server 2601/2627)

11 Gotchas & pitfalls

One line each; every one of these has cost somebody a production incident.

  • N+1 by lazy loading — proxies turn a foreach into one query per row; if you must keep them, log command counts per request.
  • Cartesian explosion — two collection Includes multiply rows; use AsSplitQuery() and accept the extra round trips.
  • Split query without OrderBy — pages can interleave inconsistently between the split statements; always order.
  • Client evaluation throws — since EF Core 3.0 an untranslatable Where is an exception, not a silent full-table scan; the fix is AsEnumerable() at the boundary you chose.
  • db.Update(entity) marks every property modified — a full-column UPDATE and lost concurrency granularity.
  • ExecuteUpdate/ExecuteDelete bypass the tracker — interceptors on SaveChanges, soft-delete filters and audit hooks do not run.
  • Query filters + required navigation — an Include over a required nav becomes an INNER JOIN and silently drops parents whose child was filtered out.
  • Async captured wrong — mixing ToList() and ToListAsync() under load starves the thread pool; one style per codebase.
  • DbContext shared across threads — A second operation was started on this context instance; use IDbContextFactory.
  • EnableRetryOnFailure without an execution strategy — explicit transactions throw InvalidOperationException at runtime, not at startup.
  • EnsureCreated() and migrations together — EnsureCreated skips the __EFMigrationsHistory table, so the first Migrate() fails on existing objects.
  • Migrating on startup in multi-instance deployments — concurrent Migrate() calls race; ship an idempotent script or a bundle from the pipeline instead.
  • EF Core 10: migrations are no longer one transaction — a mid-run failure leaves a partially migrated database.
  • Skip/Take without OrderBy — non-deterministic paging; the database may return the same row twice across pages.
  • Deep OFFSET paging — Skip(100000) scans everything skipped; switch to keyset paging.
  • DateTime.Now in a query — evaluated once, parameterised, and in server-local time; use DateTime.UtcNow captured explicitly.
  • Decimal without precision — silently truncates to decimal(18,2) on SQL Server; set it in ConfigureConventions.
  • string.Contains as search — becomes LIKE '%x%', unindexable; use full-text search past a few thousand rows.
  • Enum stored as int by convention — reordering the enum silently corrupts data; convert to string or pin the values.
  • Owned types are not entities — you cannot query them independently or track them separately; complex types (EF Core 8+) say that out loud.
  • Scaffolding overwrites — dbcontext scaffold regenerates the whole context; keep customisations in partial classes or -f will eat them.
  • EF Core 8/9 leave support on 2026-11-10 — anything still on .NET 8 needs an upgrade plan now.
