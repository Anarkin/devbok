01The N+1 that only existed in production

Senior performance problem diagnosed

(a) Worked example EXAMPLE — replace with your own

An order-history screen took 90 ms in dev and 4.5 seconds for our largest customer. Nobody believed it was the ORM, because the code looked like one query. It was one query in the C# and 1,400 queries in the database, and the reason is the single most useful thing I know about EF Core: the query pipeline decides what SQL to send at the point you enumerate, and anything you touch afterwards is either already loaded, lazily loaded, or a bug.

I found it with the tooling rather than by reading. Turning on EnableSensitiveDataLogging in a staging pod and filtering the logs to the Microsoft.EntityFrameworkCore.Database.Command category showed the pattern immediately: one SELECT against Orders, then the same SELECT … FROM OrderLines WHERE OrderId = @p repeated once per row. The application had lazy-loading proxies enabled — UseLazyLoadingProxies(), added years earlier by someone porting from EF6 where lazy loading was the default — and the Razor view iterated order.Lines inside the loop. In dev the seed data had 12 orders. In production that customer had 1,400.

// The shape that hides the N+1: nothing in this method mentions Lines.
var orders = await _db.Orders
    .Where(o => o.CustomerId == customerId && o.PlacedAt >= from)
    .OrderByDescending(o => o.PlacedAt)
    .ToListAsync();
// ... and then, in the view: @foreach (var l in order.Lines) { ... }  // one round trip per order

The naive fix is Include(o => o.Lines), and it is the fix I did not ship first, because it trades one problem for another. A single query with Include on two collection navigations produces a cartesian explosion: EF joins Orders × Lines × Payments, and every order row is duplicated lines × payments times on the wire. With 1,400 orders averaging 6 lines and 2 payments that is roughly 16,800 rows carrying every order column, and the network and materialisation cost is worse than the round trips it saved. EF warns about this — MultipleCollectionIncludeWarning — and I now configure it as an error in new services.

What actually shipped was a projection. The screen needed six columns, not entities, so the query became a Select into a DTO, which means EF composes exactly those columns into one SELECT, materialises no entities, tracks nothing, and never lazy-loads because there is nothing to lazy-load from. Where a screen genuinely needs the graph, the tool is AsSplitQuery(): EF issues one query per collection navigation and stitches the results in memory, which trades round trips for row volume — and, importantly, gives up cross-query consistency unless you wrap it in a transaction.

// What shipped: one SQL statement, six columns, no entities, no proxies involved.
var rows = await _db.Orders
    .Where(o => o.CustomerId == customerId && o.PlacedAt >= from)
    .OrderByDescending(o => o.PlacedAt)
    .Select(o => new OrderRow(
        o.Id, o.PlacedAt, o.Status,
        o.Lines.Count,
        o.Lines.Sum(l => l.Net),
        o.Payments.Any(p => p.State == PaymentState.Failed)))
    .ToListAsync();

Result: 4.5 s to 140 ms for that customer, and — the number I actually led with in the write-up — database round trips per page load from 1,401 to 1. We also removed UseLazyLoadingProxies() from the service entirely, which broke four other screens in a good way: each one turned into a compile-time-visible decision about what to load. On EF Core 10 I would add ConfigureWarnings(w => w.Throw(CoreEventId.LazyLoadOnDisposedContextWarning)) and treat any surviving lazy load as a defect.

What I would do differently: I would have caught it before production. Dev data that is uniform in shape but not in cardinality is a trap, and the cheap fix is a seed script with one deliberately pathological tenant. I also should have looked at the SQL log on day one instead of reading C# for an afternoon — with an ORM, the code you wrote and the work the database did are two different artefacts, and only one of them is the truth.

What the interviewer is really probing. Whether you understand that an ORM is a SQL generator, and whether you can read what it generated. The signal: you name the diagnostic (SQL logging, a profiler, ToQueryString()), you quote a before/after number, and you can explain why each candidate fix behaves the way it does — not just that Include "fixes N+1". The classic failure is the candidate who says "we added Include" and cannot describe cartesian explosion, or who blames the ORM in general terms without ever having looked at a single generated statement. The second failure is claiming the whole investigation when a DBA handed you the query trace: say who found what.

(c) Recall prompts

When did you last read the SQL your ORM actually generated, and what surprised you?

Sketch: everyone has one. Common answers — an OPENJSON you did not expect from an ids.Contains(...) filter, a LEFT JOIN tower from nested Include, an ORDER BY you never wrote that EF added to keep an Include stable. Name the tool: command logging, ToQueryString(), SQL Server Extended Events, pg_stat_statements.

Have you ever had a performance bug that only appeared with one customer's data?

Sketch: cardinality skew is the classic ORM trap — one tenant with 50× the rows, one product with 4,000 variants. If you have one, the strong version of the answer includes what you changed about your test data afterwards, not just the code.

Where in your systems is lazy loading still enabled, and do you know why?

Sketch: it is usually a fossil from EF6, where lazy loading was on by default with virtual navigations. If your codebase has UseLazyLoadingProxies() or ILazyLoader injection, the interesting answer is whether that was a decision or an inheritance.

What is the biggest reduction in round trips you have personally achieved, and how did you prove it?

Sketch: proof beats claim. A count from the SQL log, a metric from Application Insights dependency tracking, or a SET STATISTICS IO comparison all make the number defensible.

(d) Follow-up drill chain

Why did you project instead of just adding Include?

Because the screen needed six values, not the object graph, and the moment you materialise entities you also pay for change tracking, identity resolution and the fixup pass that wires navigations together. With Include on two collections I would also have paid the cartesian product — roughly 16,800 rows for 1,400 orders — and every one of those rows carries the full order payload. Projection sends the join to the database, which is the machine that is good at joins, and returns exactly the tuple I need. I would use Include when the caller genuinely needs the aggregate to mutate it, because then the tracking is the point rather than the tax.

What if the screen had needed the full graph, not a DTO?

Then it becomes a choice between one wide query and several narrow ones, and I would decide on measured row counts. AsSplitQuery() issues one statement per collection navigation and eliminates duplication, so it wins as soon as the product of collection sizes gets large; the cost is that the queries run at different points in time, so without an explicit transaction you can read a parent from before a write and children from after it. I would also check the ordering: EF Core 10 fixed a real bug where the subquery feeding a split query omitted the key from its ORDER BY, which could silently return the wrong children for a Take-limited parent set. Before EF 10 that is a reason to be careful with split queries plus paging.

At what scale does the projection stop being enough?

It scales with columns, not with rows, so it stops helping when the row count itself is the problem. At around 50,000 orders for one customer the single SELECT is still one round trip but it is now a sort and an aggregate over a large set, and the answer moves to the database: a covering index on (CustomerId, PlacedAt) INCLUDE (Status), keyset paging instead of Skip/Take, and possibly a summary table maintained on write. That is the point where I would stop optimising the ORM call and start changing the data model, and I would say so explicitly rather than pretending EF has another trick.

What did you trade away?

Reuse and a little cohesion. A projection is written for one screen, so the next screen writes its own, and you end up with several near-identical Select blocks that all have to change when a column changes. I bounded that by putting the projection in a static Expression<Func<Order, OrderRow>> next to the DTO so it is composable and testable, rather than hiding it behind a repository method that returns IEnumerable. I also gave up the ability for a caller to mutate what they read, which for this screen was a feature.

How did you stop the team from reintroducing it?

Three things, in increasing order of teeth. I removed the proxies package so lazy loading cannot happen by accident; I turned MultipleCollectionIncludeWarning into a thrown exception via ConfigureWarnings, so a cartesian-explosion query fails in CI instead of in production; and I added a seeded "pathological tenant" to the integration test database with 2,000 orders, plus a test that asserts a maximum number of executed commands using a DbCommandInterceptor as a counter. The last one is the one that keeps working after everyone forgets the incident.

Would you do it the same way on EF Core 10 today?

The diagnosis identically. The fix mostly, with two additions. First, I would check whether the filter is a parameterised collection — EF 10 changed the default translation of ids.Contains(x) from a single JSON-array parameter back to one parameter per element with padding, because the JSON form denied the planner any cardinality information; if my query has a big IN list, that default now matters and is tunable per query with EF.Constant/EF.Parameter or globally with UseParameterizedCollectionMode. Second, if the shape is genuinely document-like I would consider mapping the child data as a complex type in a JSON column, which in EF 10 gets first-class querying and ExecuteUpdateAsync support — but that is a modelling change, not a query fix, and I would not smuggle it into a latency ticket.

02The repository on top of a repository

Staff hard architectural trade-off

(a) Worked example EXAMPLE — replace with your own

I inherited a service with 41 repository classes, a IUnitOfWork interface with a single SaveChangesAsync method, and a generic base class exposing GetAll(), Find(Expression<Func<T,bool>>) and Update(T). It had been built that way "so we can swap the ORM". Six years in, nobody had swapped the ORM, and the abstraction was costing us three concrete things a week. The argument I had to make — and lose part of — is the one worth rehearsing, because it is the most common architecture question in .NET interviews.

The technical core is that DbContext already is a unit of work and DbSet<T> already is a repository. The change tracker is the unit of work: it accumulates the state of every tracked entity and SaveChangesAsync writes them in one transaction, in dependency order, batched. Wrapping that in a second unit of work does not add a boundary, it adds a synonym. The real damage was in the query surface. GetAll() returned IEnumerable<T>, which forces enumeration in the repository, which meant a filter written in a service method ran in memory over the whole table. One method was pulling 180,000 rows to return 30.

// The costly abstraction: the return type decides where the WHERE runs.
public IEnumerable<Order> GetAll() => _db.Set<Order>().ToList();          // 180k rows, always
public IQueryable<Order> Query() => _db.Set<Order>().AsNoTracking();      // composable, but leaks EF

// Caller, unchanged in both worlds:
var recent = repo.GetAll().Where(o => o.PlacedAt > cutoff).Take(30);

The trade-off is genuinely two-sided and I want to state both sides honestly, because an interviewer will push on whichever one you skip. Returning IQueryable<T> keeps composition and lets EF do the work, but it leaks the persistence model into callers: they can write a query that cannot be translated, they can accidentally hold the context open, and your "swap the ORM" story is dead because IQueryable semantics are provider-specific. Returning materialised collections gives you a real boundary and testability, but you must then provide a query method for every access pattern, and you will have 41 classes with 300 methods, most of them one caller deep.

What I proposed was not "delete the repositories". It was: delete the generic base and the second unit of work; keep a small number of hand-written, aggregate-shaped repositories for the write side; inject DbContext directly for reads and project. The write side is where invariants live and where a boundary pays for itself; the read side is where an abstraction only gets in the way. We cut 41 classes to 9, deleted about 2,600 lines, and the client-evaluation bug class went away because no method returned IEnumerable from a query any more.

I lost one part of the argument, and I think correctly. A senior engineer insisted that SaveChangesAsync should not be callable from a controller. He was right — with the context injected directly, anyone can save at any time, and the transaction boundary becomes implicit. We settled on a thin ITransactionScope owned by the application layer that wraps SaveChangesAsync and the domain-event dispatch, so the boundary is explicit without pretending to be a persistence abstraction. What I would do differently: I would have run the deletion as three PRs over three sprints instead of one 2,600-line PR that sat in review for eleven days.

What the interviewer is really probing. Whether you have opinions grounded in consequences rather than in books. The signal: you know why DbContext is a unit of work, you can name the concrete cost of the abstraction you are criticising, and you can argue the other side convincingly. The classic failure is dogma in either direction — "repositories are always an anti-pattern" or "you must never depend on EF" — with no story about what it actually broke. The second failure is telling this as a story where you were right and everyone else was wrong; interviewers at staff level are listening for how you moved a team, and for the part of the argument you conceded.

(c) Recall prompts

What persistence abstraction have you argued for or against, and what did it cost either way?

Sketch: generic repositories, a mediator around every query, a hand-rolled specification pattern, a "database gateway" service. The strong version names a specific defect the abstraction caused or prevented.

Have you ever had a query evaluate on the client without meaning to?

Sketch: EF Core 3.0 made client evaluation of the top-level Where throw rather than silently work, so on EF Core the modern form of this bug is a repository that returns IEnumerable, or a .AsEnumerable() someone added to make a compile error go away. On EF6 it was silent and everywhere.

Where do you draw the transaction boundary in your services, and who is allowed to commit?

Sketch: if the answer is "anyone with the context", that is worth admitting — it is the honest cost of injecting DbContext directly, and the interesting part is what you did about it.

When did you last delete an abstraction, and how did you get sign-off?

Sketch: numbers move architects. Lines deleted, classes removed, a defect count, a benchmark. "It felt cleaner" is the answer that loses the argument.

(d) Follow-up drill chain

Why is DbContext already a unit of work? Be specific.

Because it owns a change tracker that records the original values and state of every tracked entity, and SaveChanges turns that accumulated state into a single, ordered, batched set of statements inside one transaction, rolling the whole thing back on failure. That is the definition of the pattern: track changes across a business transaction, then commit them atomically. It also gives you the identity map — the same primary key resolves to the same instance within a context — which is the other half of what Fowler's repository/unit-of-work pair provides. Adding an IUnitOfWork with a Commit() that calls SaveChanges does not add a boundary; it renames one.

What if a future team really does want to swap EF for Dapper or a document store?

Then the repository will not save them, and I would say that plainly. IQueryable is not portable — its translation is provider-specific and every real codebase has queries that only one provider supports — so a repository that returns IQueryable leaks anyway, and one that returns materialised collections has to be rewritten method by method regardless. What genuinely helps is keeping the domain model free of persistence attributes, keeping queries in named, testable places so you can find all of them, and having integration tests that assert behaviour rather than SQL. In practice the swap that actually happens is partial — a few hot read paths move to Dapper — and that needs a seam per query, not a framework.

At what scale does injecting DbContext directly break down?

It breaks down when the number of people exceeds the number of people who understand the change tracker. On a team of six with code review it is fine; at forty engineers across four teams sharing a context, you get untracked saves from controllers, contexts held across await boundaries into background work, and someone calling SaveChanges mid-way through a domain operation leaving a half-applied aggregate. That is when I would add the explicit application-layer transaction boundary and, if the domain has real invariants, aggregate-shaped repositories that only hand back valid roots. The trigger is organisational, not technical, and I would say that out loud.

What did you trade away by deleting the generic base?

Cheap unit tests. With IRepository<T> you can fake persistence with a list; without it, testing a service that queries needs a database, and that means Testcontainers, slower runs and CI infrastructure. I decided that trade was worth it because the fakes were lying: they tested LINQ-to-Objects semantics, not the translation, so a test could pass while the query threw at runtime. But it is a real cost — our test suite went from 9 seconds to 90 — and I paid for it with a shared, snapshot-restored container and parallel test collections.

How did you get the person who built the old design to support the change?

By making his objection part of the outcome rather than an obstacle to it. He cared about the transaction boundary, which was a legitimate concern I had not solved, so the final design includes the explicit application-layer boundary he asked for, and he wrote it. I also framed the change around evidence he could check himself: the 180,000-row query, the count of repository methods with exactly one caller, the two production defects traced to client evaluation. The thing I avoided was arguing from authority or from a blog post — at staff level the job is to convert a disagreement into a shared design, not to win it.

Would you build it the same way today on EF Core 10?

Yes, with one modernisation. Complex types mapped to JSON columns, which became genuinely usable in EF 10, remove a lot of the pressure that used to push people toward owned entities and child tables purely for value objects — so more of my aggregates now fit in one table and one round trip, which makes aggregate-shaped repositories cheaper to write. I would also use DbContext pooling with a scoped factory from the start, because that pushes you toward short, explicit context lifetimes, which is most of what the ceremonial unit of work was trying to enforce in the first place.

03The migration that locked the orders table

Staff production incident / outage

(a) Worked example EXAMPLE — replace with your own

We shipped a release at 09:40 on a Tuesday. At 09:42 every write to the orders API was timing out, and it stayed that way for 22 minutes. The cause was three lines in a generated migration that nobody had read: adding a non-nullable decimal column with a default to a 34-million-row table, in the same migration as a rename, applied by the app at startup via Database.Migrate().

The mechanics are worth being precise about, because "adding a column is instant" is a half-truth that has caused a lot of outages. On SQL Server, adding a nullable column is a metadata-only operation. Adding a NOT NULL column with a constant default has been metadata-only since SQL Server 2012 Enterprise — but only for a constant default; ours was HasDefaultValueSql("dbo.CalcFee(Total)"), a non-deterministic expression, which forces a full table rewrite under a schema-modification lock. Every read and write queued behind it. And because the migration ran from Database.Migrate() in Program.cs, all six replicas started it simultaneously; five blocked on the migration history lock while the sixth rewrote the table, and the health checks failed, so the orchestrator killed and restarted pods that were waiting.

// The generated migration nobody reviewed
migrationBuilder.AddColumn<decimal>(
    name: "ServiceFee", table: "Orders", type: "decimal(18,2)",
    nullable: false, defaultValueSql: "dbo.CalcFee(Total)");   // full rewrite, Sch-M lock

migrationBuilder.RenameColumn(                                  // and a rename in the same transaction
    name: "Total", table: "Orders", newName: "GrossTotal");     // every prior build now broken

Recovery was ugly and instructive: we could not simply kill the session, because rolling back a half-completed rewrite takes as long as the rewrite. We let it finish, then discovered the second half of the problem — the rename meant the previous application version could no longer read the table, so rolling back the deployment was not an option either. We had painted ourselves into a forward-only corner during an incident.

What changed afterwards is the part I would actually talk about. First, migrations no longer run from the application. We generate an idempotent SQL script or a migration bundle in CI and apply it as a separate, gated pipeline step before the new pods roll:

# CI: a self-contained executable that applies exactly the migrations in this build
dotnet ef migrations bundle --self-contained -r linux-x64 -o ./efbundle
# CD, as its own gated stage, before the app rollout:
./efbundle --connection "$MIGRATION_CONNECTION"
# Or, for a DBA-reviewed change window:
dotnet ef migrations script --idempotent --output ./migrate.sql

Second, every schema change follows expand / migrate / contract: add the nullable column, backfill in batches outside the deployment, make it non-nullable in a later release, and never rename — add the new name, dual-write, drop the old one two releases later. Third, we made "will this rewrite the table?" a checklist item on migration review, with the generated SQL attached to the PR, because dotnet ef migrations script costs ten seconds and reading it is the only way to know.

Result: 22 minutes of write downtime, roughly 4,100 failed orders, and a postmortem I wrote and presented. Since the change, 300-odd migrations have shipped with zero schema-related incidents, and the median migration now applies in under two seconds because the expensive part — backfill — happens in a batched background job, not in a lock.

What I would do differently: I would have caught it in review. The pull request was titled "add service fee" and had 40 lines of C# and one generated migration file; I approved it in ninety seconds. Now the generated SQL goes in the PR description, and a migration touching a table over a million rows needs a second reviewer.

What the interviewer is really probing. Incident command and blameless ownership, plus whether you understand that migrations are production changes, not code. The signal: a timeline with real times, what you did to stop the bleeding versus what you did to fix the cause, and a systemic change that would have prevented it. The classic failure is a story where the fix is "we were more careful afterwards" — that is not a control. The second failure is throwing the author under the bus; if you approved the PR, say so, because the interviewer is listening for exactly that.

(c) Recall prompts

How do your migrations actually reach production — from the app, a pipeline, or a DBA?

Sketch: Database.Migrate() in Program.cs is extremely common and is the honest answer for many teams. If that is yours, the good story is whether you know the risks (concurrent replicas, no gate, no review of generated SQL) and what you would change.

Have you ever been unable to roll back a deployment? Why not?

(d) Follow-up drill chain

Why didn't you just kill the blocking session?

Because the rewrite was already several minutes in, and killing it starts a rollback that has to undo the same work — in practice at least as long as the operation itself, sometimes longer, and during that rollback the lock is still held. Killing it would have converted a 22-minute outage into a 40-minute one with less predictability. What I did instead was measure: I checked the session's percent_complete in sys.dm_exec_requests, saw it moving steadily, told the incident channel a projected finish time, and spent the wait preparing the forward fix and drafting comms. The judgment call I would defend is that in an incident, an ugly known duration beats an unknown one.

What if the rewrite had been going to take four hours instead of twenty minutes?

Then the calculus flips and I would kill it and take the rollback, because at that horizon you are past any reasonable RTO and you need a decision point sooner. The plan I would then run is the expand path from scratch: restore write availability, add the column as nullable, backfill in 5,000-row batches with a short delay so the log can truncate and other work can interleave, and only then apply the NOT NULL constraint with WITH CHECK during a quiet window. I would also want a copy of the table's row count and index list before deciding, because "four hours" has to come from a measurement or a comparable operation, not a feeling.

At what table size does your expand/contract rule kick in?

I set the threshold at a million rows for a hard rule, but the honest answer is that the row count is a proxy for two things that matter more: how long the lock is held and how many concurrent writers are queued behind it. A 200,000-row table in a system doing four writes a second can absorb a five-second lock; a 34-million-row table under 900 writes a second cannot absorb one second. So the rule is written as row count because that is checkable in review, and the escape hatch is that anyone can invoke expand/contract on a smaller table if the write rate justifies it. I would rather have a slightly over-cautious mechanical rule than a judgment call at 09:40 on a Tuesday.

What did you trade away by moving migrations out of the application?

Simplicity, and a bit of developer velocity. Database.Migrate() at startup is one line and it means a developer's local database is always current; the pipeline approach needs a bundle artifact, a gated stage, a connection string with elevated permissions stored separately from the app's, and a story for what happens when the migration stage succeeds and the app rollout fails. We kept Database.Migrate() for local development and integration tests only, gated behind an environment check, which preserves most of the convenience. The other cost is that the app and schema can now be out of step, which is exactly why expand/contract stopped being optional.

How did you get the team and the DBAs to adopt the new process?

The postmortem did most of the work, but the thing that made it stick was making the safe path the easy path. I wrote the pipeline stage, the bundle build, and a PR template that auto-attaches the generated script, so following the process is less effort than not following it. With the DBAs, the win was that they now see every schema change as reviewable SQL before it runs, which is what they had been asking for for two years; in exchange they agreed to a same-day review SLA so we did not lose release velocity. The negotiation was the real work — the technical change was an afternoon.

Would anything about this be different on EF Core 10?

Two things, and both are small but worth knowing. EF Core 9 wrapped all pending migrations in a single transaction; EF 10 reverted that, because one big transaction caused problems for operations that cannot run inside one and made partial recovery harder — so on EF 10 you are back to per-migration transactions, which is the behaviour my batching assumed. And EF 10 added named default constraints via HasDefaultValueSql("…", "DF_Orders_ServiceFee") plus UseNamedDefaultConstraints(); useful, but note that turning that on renames every default constraint in your model in the next migration, which is exactly the kind of "small" migration that needs the generated SQL read before it ships.

Why strangle instead of a big-bang rewrite?

Because a big-bang has one integration point at the end, and that integration point is the whole system on the day of a deadline. What if a query genuinely could not be translated by EF Core?

Third, drop to FromSql with a parameterised statement, or map a keyless entity type onto a view. The moment two of them write the same table, and the failure is not a crash, it is drift. EF6 and EF Core can disagree about DateTime precision, about default constraints, about how they treat concurrency tokens, and about whether a value converter round-trips identically — so the same logical write can produce different bytes. It also breaks when the schema needs to change on a shared table, because both models must be updated in lockstep across two deployment pipelines. Our rule was one writer per table, enforced by database permissions rather than by convention, and the incident in month nine was exactly what happens when a hotfix bypasses that.

A colleague opened a pull request adding .AsNoTracking() to every query in the codebase — 214 call sites — with the description "perf". I blocked it, and the conversation that followed was one of the more useful technical disagreements I have had, because we were both partly right and the resolution needed a rule rather than a verdict.

His evidence was real: a benchmark showing a 30% improvement materialising 10,000 rows. My objection was that the benchmark measured the one case where tracking is pure overhead, and the change applied to 214 cases where it might not be. Change tracking is not a tax, it is a feature with a cost, and the cost is concentrated in two places: creating an EntityEntry with a snapshot of original values per entity, and running identity resolution so the same key maps to the same instance. For a 20-row query feeding a screen, that cost is invisible. For a 100,000-row export it dominates.

The part that decided the argument was correctness, not speed. Without tracking, identity resolution is off by default, so a query that returns the same underlying row through two paths materialises two separate objects. Code that compared references, or that mutated one and expected the other to see it, broke.

// No-tracking: a fresh Blog per Post. Cheaper, and a different object graph.
var posts2 = await db.Posts.AsNoTracking().Include(p => p.Blog).ToListAsync();
// same == false

// The middle option, when you want one instance but no change tracking:
var posts3 = await db.Posts.AsNoTrackingWithIdentityResolution().Include(p => p.Blog).ToListAsync();

(d) Follow-up drill chain

Why does tracking cost anything at all? Be concrete.

For each entity that the materialiser produces, EF creates an EntityEntry and, with the default change-tracking strategy, a snapshot of every mapped property's original value, so it can compute a diff at SaveChanges time. That is an allocation and a copy per entity, plus insertion into the identity map keyed on the primary key, plus the fixup pass that wires navigations between tracked instances. Then DetectChanges walks all of it on save. For 20 entities this is microseconds; for 100,000 it is a measurable fraction of the request and a real chunk of gen-0 pressure. Notably, none of that happens for a projection to a non-entity type — EF does not track what is not an entity — which is why "project it" usually beats "untrack it".

What if someone needs to update a small number of entities from a no-tracking read?

Then they attach, and this is where people go wrong. Update(entity) marks every property modified, so it writes all columns and will happily overwrite fields changed by someone else since the read. The safer pattern is Attach plus marking the specific properties modified, or re-reading the entity tracked and applying the changes — and, if the data can be concurrently edited, a concurrency token (rowversion on SQL Server, xmin on PostgreSQL) so a stale write fails with a DbUpdateConcurrencyException rather than silently winning. On EF 10 there is a fourth option for simple cases: ExecuteUpdateAsync, which now takes a plain lambda instead of an expression tree, so you can build the setters conditionally without hand-constructing expressions.

At what row count does the tracking overhead actually start to matter?

In the systems I have measured, it becomes visible somewhere around a few thousand entities per query and dominates past tens of thousands — but the number is much less interesting than the shape. A query returning 5,000 entities with 40 properties each and three navigations costs far more than one returning 20,000 with four properties and none, because the snapshot is per property and fixup is per relationship. So my rule is: if a query returns enough rows for the flag to matter, it is almost certainly a query that should have been a projection, and the tracking decision becomes moot. I would rather teach that heuristic than a threshold, because thresholds get cargo-culted.

What did you trade away by setting NoTracking as a host-level default?

Discoverability at the call site. A developer reading a query in the read host cannot tell from the code that it is untracked; they have to know the host's configuration. That is a real cost and it bit us once, when someone moved a handler between hosts and its SaveChanges silently did nothing. We mitigated it by making the read host's context type distinct — ReadContext with no SaveChanges exposed at all, so a write attempt is a compile error rather than a no-op. If I could not split the context, I would prefer the explicit per-query flag over the global default, precisely because the global default is invisible.

How did you keep the relationship intact after blocking his PR?

That was deliberate: the fastest way to turn a blocked PR into a lasting grudge is to block it and then solve the problem yourself. I also apologised specifically for the way I opened — not for the objection, which I still think was right, but for stating it as a verdict rather than a question. At senior level, the thing being assessed is whether disagreement makes your team stronger or quieter.

Does anything about this change on EF Core 10?

The mechanics are unchanged, and I would flag that as a feature: tracking behaviour is stable, well-documented, and worth learning once. What EF 10 changes around the edges is how often you need entities at all. Complex types mapped to JSON columns are queryable and now bulk-updatable through ExecuteUpdateAsync, so a class of "load the aggregate, mutate one field, save" code becomes a single statement with no tracking involved. And parameter names in logs are now readable (@city rather than @__city_0), which sounds cosmetic but made our SQL-log-based diagnosis of these problems noticeably faster.

A support ticket said "invoice 4471 appears on page 2 and page 3". One ticket, one customer, not reproducible. It took me two days, and the bug turned out to be a single missing clause in an ORDER BY — mine, not EF's. It is the best debugging story I have because the wrong answer was available at every step.

The endpoint was ordinary keyset-less paging: OrderBy(i => i.IssuedOn).Skip(page * 50).Take(50). IssuedOn is a date, not a timestamp, and that customer imports invoices in bulk, so 380 of them share the same IssuedOn value. SQL has no stable sort. An ORDER BY on a non-unique key leaves rows with equal keys in an unspecified order, and the engine is free to return them differently between executions — different plans, different parallelism, a different buffer-pool state. Page 2 and page 3 are two separate queries; between them the tie-break shifted, so one row appeared twice and another vanished.

// The bug: a non-deterministic sort key with Skip/Take on top.
var page = await db.Invoices
    .Where(i => i.CustomerId == id)
    .OrderBy(i => i.IssuedOn)          // 380 ties
    .Skip(pageIndex * 50).Take(50)
    .ToListAsync();

// The fix: make the ordering total by appending a unique tiebreaker.
    .OrderBy(i => i.IssuedOn).ThenBy(i => i.Id)

// The better fix for deep pages: keyset (seek) pagination — no OFFSET at all.
var page2 = await db.Invoices
    .Where(i => i.CustomerId == id)
    .Where(i => i.IssuedOn > lastOn || (i.IssuedOn == lastOn && i.Id > lastId))
    .OrderBy(i => i.IssuedOn).ThenBy(i => i.Id)
    .Take(50)
    .ToListAsync();

What made it take two days was the false leads, and they are worth listing because each one teaches something. I first suspected the change tracker's identity map producing duplicate references — it does not, that is the opposite of what it does. Then I suspected an Include duplicating rows, which is a real EF behaviour (cartesian explosion), but this query had no Include. Then I suspected caching. What finally cracked it was dumping query.ToQueryString() and running the two page queries by hand against a restored snapshot in a loop: about one run in fifteen returned a different set for page 2. That reproduction — a loop, not a single run — is the technique I took away.

The wider lesson I now teach: EF gives you exactly the ordering you asked for, and no more. There is one place where EF adds ordering on your behalf — it appends key columns to keep Included collections grouped — and people generalise from that into believing the ORM guarantees stability. It does not, and neither does the database.

Result: fixed with a two-word ThenBy, plus a code review rule that any Skip/Take must be preceded by an ordering that ends in a unique column. I also converted the three deepest-paged endpoints to keyset pagination, which took the p95 of page 400 from 900 ms to 20 ms because the database stopped scanning and discarding 20,000 rows per request.

What I would do differently: I would have reached for ToQueryString() and a repeat-execution loop on hour one rather than hour ten. Non-reproducible means "I have not found the variable yet", not "intermittent".

(d) Follow-up drill chain

Why is the ordering unstable if the data has not changed?

Because ORDER BY only constrains the columns you name; rows that tie on those columns may come back in any order, and nothing in the SQL standard or in SQL Server promises otherwise. In practice the order that emerges depends on the access path — whether the optimiser chose a clustered scan, an index seek plus lookup, or a parallel plan whose threads finish in a different sequence — and those can change between two executions seconds apart because of statistics, memory pressure or plan cache eviction. So identical data with an incomplete ORDER BY genuinely can produce different pages. The fix is to make the sort total, which is a one-column change and costs nothing when the tiebreaker is the clustered key.

What if the tiebreaker column were not unique either — say a natural key?

Then paging is unsound and I would say so rather than patching it. The requirement for correct OFFSET paging is a total order, which means the ordering columns together must be unique; if no combination is, you have to add a surrogate — a sequence, an identity, a rowversion — or accept that the page boundaries are approximate and design the UI around that, for example by paging over a snapshot captured once and stored. For an audit or export scenario where correctness is non-negotiable, the answer is usually a stable snapshot: capture the ordered key set once into a temp table or a cursor, then page over that.

At what page depth does OFFSET paging stop being viable?

It degrades linearly with offset, because OFFSET n makes the engine produce and discard n rows before returning anything, so the cost of page 400 is 400 pages of work. In our system it was fine to about page 20 and visibly bad past page 100; at page 400 it was 900 ms for 50 rows. Keyset pagination replaces that with a seek on the ordering columns, so every page costs the same and the p95 stops depending on how far the user has scrolled. The trade is that keyset cannot jump to an arbitrary page number and does not give you a total count for free — which is exactly why I converted three endpoints and not all of them.

What did you trade away by moving to keyset pagination?

Random access and, in one place, product behaviour. The UI had a page-number control, and keyset paging only supports next/previous plus a jump to a known anchor, so we replaced the numbered pager with infinite scroll on the two internal screens and kept OFFSET paging — with the fixed tiebreaker — on the customer-facing one where the page numbers were a documented part of an export workflow. I also gave up the cheap total count, which we replaced with an approximate count from statistics on the screens where an exact number was decoration. Being able to say which endpoints you did not convert, and why, is usually the more convincing half.

How did you stop this happening in other queries?

A Roslyn analyser would have been the ideal control but was more than the problem justified, so I did two cheaper things. First, a code-review rule with a grep-able signature: any .Skip( in the codebase must have an OrderBy chain ending in Id or another unique column, and I fixed the eleven existing violations in one PR so the rule started from zero. Second, an integration test per paged endpoint that requests every page twice, in a different order, and asserts the union has no duplicates and no gaps — it runs against seeded data with deliberate ties, and it fails loudly if someone drops the tiebreaker. The test is the control; the rule is a reminder.

Is there anything version-specific here worth knowing?

Yes, and it is a nice one to have in your pocket. EF Core 10 fixed a genuine ordering bug in split queries: when a query used AsSplitQuery() together with Take, the subquery that fed the collection queries omitted the key column from its ORDER BY, so the parent set could differ between the two statements and you could get children attached to the wrong parents. That is the same class of bug as mine — an incomplete ordering under a limit — except that one was EF's rather than the developer's. If you are on EF 9 or earlier and you combine split queries with paging, it is worth knowing about.

A checkout API that was comfortable at 200 requests per second fell over at 700, and the errors were not slow queries — they were InvalidOperationException: Timeout expired. The timeout period elapsed prior to obtaining a connection from the pool. The database was at 12% CPU. The bottleneck was entirely on our side of the wire, and understanding why is a good tour of how EF actually uses connections.

Three things compounded. First, the ADO.NET connection pool is per connection string and defaults to 100 connections; EF opens a connection when it needs one and returns it when the query completes, but a context inside an explicit transaction holds its connection for the whole transaction. We had a handler that started a transaction, called an HTTP service, then saved — so a connection was pinned for the duration of a network call to something we did not control. When that dependency slowed to 400 ms, 100 connections were consumed at 250 concurrent requests.

Second, context construction was not free at that rate. Each DbContext builds internal services and resolves the model; the model itself is cached across instances, but the per-instance setup still allocates. At 900 rps that was measurable — around 8% of CPU in a trace — and it is exactly what AddDbContextPool exists to remove: the pool reuses context instances, resetting their state between uses.

Third, we had a genuine concurrency bug hiding in the noise: a handler doing Task.WhenAll over two queries on the same context. DbContext is not thread-safe and does not support concurrent operations; the symptom is A second operation was started on this context instance before a previous operation completed, which we were seeing at a rate of about 30 a day and had dismissed as a transient.

(d) Follow-up drill chain

Why not just raise Max Pool Size to 500?

Because the pool was not the constraint, it was the symptom, and raising it moves the queue from your process to the database. Five hundred connections per pod across six pods is three thousand sessions against a database whose worker threads, memory grants and lock manager are sized for far fewer, so you convert fast client-side failures into slow server-side contention and lose the backpressure that was protecting you. It also would not have fixed the actual defect: a connection pinned across a 400 ms external call is a design error at any pool size, and at 900 rps you would exhaust 500 connections at 1,250 concurrent requests instead of 250. Raising the limit is a legitimate step once you have proven the holding time is already minimal — not before.

What if the external call genuinely had to be inside the transaction?

Then the transaction is distributed in everything but name, and I would stop trying to make it atomic and make it reliable instead. The pattern is the transactional outbox: inside the database transaction, write the intent to an outbox table alongside the state change, commit, and let a separate dispatcher perform the external call at least once with idempotency on the receiving side. That converts "two systems change together" into "one system changes, the other converges", which is what you can actually guarantee. If the external system supports a two-phase reservation — authorise then capture — I would use that instead, reserving before the transaction and capturing after. What I would not do is reach for a distributed transaction coordinator in a cloud environment.

At what point does DbContext pooling stop helping?

Pooling removes construction cost, so it helps exactly as long as construction is a meaningful share of the work — at 900 rps with short queries it was worth about 8% CPU; at 50 rps it is noise, and at very high rates the remaining cost is materialisation and change tracking, which pooling does not touch. It also has a real constraint: a pooled context must not carry per-request state, because it is reused. If your context injects a tenant ID or a user in its constructor, pooling either breaks or requires the pooling-aware pattern where state is reset explicitly. That caught us on the multi-tenant context, which we deliberately left unpooled — knowing which of your contexts cannot be pooled, and why, is the answer that shows you have actually done it.

What did you trade away?

Atomicity, in one place, deliberately. Moving the payment authorisation outside the transaction means there is a window where the order is committed and the authorisation has not happened, so we needed a reconciliation job and an idempotency key, and the business had to accept a small number of orders per day sitting in "awaiting authorisation" for a few seconds. That was a product conversation, not just a technical one, and I would present it that way: I traded a guarantee we could not actually keep — because the transaction could still fail after the external call succeeded — for a weaker guarantee we could verify. We also gave up some simplicity: two extra tables, a dispatcher, and monitoring for it.

How did you convince the team that more pods was the wrong answer?

With a graph, not an argument. We ran the load test at the current pod count and at double, and the failure point moved by almost nothing — because each pod has its own pool and each pod was pinning connections for the same 400 ms, so doubling the pods doubled the pressure on the same database while doubling the cost. That single chart ended the debate in about four minutes. I have since made "show the scaling curve before you scale" a standard step, because the intuition that more instances help is strong and only evidence dislodges it.

Would you configure this the same way on EF Core 10?

Broadly yes — pooling, retry-on-failure with an explicit execution strategy around user transactions, factories for background work, and short transactions are all still the shape. Two EF 10 details would change what I look at during the investigation. Parameter names in logs are now simplified to @city instead of @__city_0, which makes correlating a slow statement in the database's query store with a line of C# noticeably easier. And the new default translation of parameterised collections — one padded scalar parameter per element instead of a single OPENJSON array — changes plan-cache behaviour for Contains queries, so if I were tuning a high-rate service today I would explicitly choose the mode per query rather than accept whatever the default gives me.

The WHERE clause was parameterised properly, so it looked safe to a skim. It was not, and the reason is the thing worth teaching: parameters can only appear where the database expects a value, never where it expects an identifier or a keyword.

var rows = await db.Customers.FromSqlRaw(sql, region).ToListAsync();
// sortColumn came from a query string. "Name; DROP TABLE Audit--" is a valid string.

    .FromSql($"SELECT * FROM Customers WHERE Region = {region}")
    .ToListAsync();

    "region" => safe.OrderBy(c => c.Region),
    _        => safe.OrderBy(c => c.Id)

The distinction people get wrong in interviews is between FromSql and FromSqlRaw. FromSql (and ExecuteSql, and the older FromSqlInterpolated) takes a FormattableString: it looks like string interpolation but the compiler hands EF the holes separately and EF binds each one as a DbParameter. FromSqlRaw takes a plain string and does exactly what you tell it. The trap is that the two overloads look nearly identical at the call site, and an interpolated string passed to FromSqlRaw is concatenated by the compiler before EF ever sees it — the single most dangerous accidental keystroke in EF Core.

The good news, and the very recent detail worth carrying into an interview: EF Core 10 ships a Roslyn analyser that warns when string concatenation happens inside a raw SQL method call. That would have caught this exact line at build time. We turned the analyser's diagnostic into an error in the shared build props, which found two more instances in other services within a week.

The audit I ran afterwards found the second-order problems, which is where the real work was. LINQ is inherently safe against injection because every captured variable becomes a parameter — but three of our queries used EF.Functions.Like(c.Name, "%" + term + "%"), which is parameterised and therefore not injectable, but is vulnerable to something else: a user supplying % or _ or [ turns the pattern into a table scan. That is a denial-of-service vector rather than an injection one, and it needed an escape clause, which we added with ESCAPE and a sanitising helper.

(d) Follow-up drill chain

Why is LINQ safe from injection, mechanically?

Because the query is an expression tree, not a string. When EF translates it, every node that came from a captured variable or a method argument becomes a DbParameter on the command, and the value never touches the SQL text — so a value containing a semicolon and a DROP is just a string being compared. The corollary is the part people miss: this holds for values, not for structure. You cannot parameterise a table name, a column name, a sort direction or an operator, so any feature that lets a user choose those has to map user input to a fixed set in C#. That is the rule I would state in an interview, because it explains both why LINQ is safe and exactly where raw SQL becomes dangerous.

What if a user-driven dynamic query genuinely needs a variable column list?

Then the safety comes from an allowlist, and the allowlist should be derived from the model rather than hand-maintained, so it cannot drift. In EF you can ask the model itself — db.Model.FindEntityType(typeof(Customer)).GetProperties() gives you the mapped properties and their column names — and validate the user's choice against that set before it goes anywhere near SQL. For a genuinely arbitrary filter builder I would build an expression tree instead of a string: construct Expression.Property against the validated property and let EF parameterise the value, which keeps the whole thing in the safe path. Quoting and escaping identifiers by hand is the approach I would argue against, because it is one missed edge case from being exploitable.

At what point does the LIKE denial-of-service actually matter?

It matters when the table is large enough that a full scan is expensive and the endpoint is reachable by an untrusted user. On a 40,000-row table nobody notices; on our 12-million-row customer table a single % query took 9 seconds and a handful of concurrent ones saturated the database's worker threads, so it is a real availability issue rather than a theoretical one. The fixes are layered: escape the wildcard characters so a literal % searches for a percent sign, require a minimum term length, put a command timeout on the query so a pathological one fails fast rather than holding a connection, and for real search workloads move to full-text indexing rather than LIKE. EF Core 11 previews add managing SQL Server full-text catalogs from the model, which would make that last step cheaper than it is today.

What did you trade away by banning interpolated identifiers?

Some genuinely useful flexibility, and I had to give something back to make the rule stick. Two teams had generic export endpoints where the column list is data-driven, and the switch-expression pattern does not scale to sixty columns. For those we built a small helper that takes the requested column names, validates them against the EF model's property list, and produces the expression tree — about eighty lines, shared, tested, and the only sanctioned path. The cost is a shared component that now needs an owner, and a slightly slower path for those endpoints because the expression is built per request rather than compiled. That was worth it; a blanket ban with no alternative would have been routed around within a month.

How did you handle it with the developer who wrote the vulnerable line?

I fixed nothing before talking to him. I raised it in a direct message with the line and the exploit string, asked him to confirm my reading, and let him write the fix and the write-up — partly because he understood the screen better, mostly because the alternative teaches everyone that finding a bug in your code means being publicly corrected. In the team write-up the framing was "our review process let this through", which is accurate: two people approved that PR and I was almost the third. The security team graded it low because the endpoint was behind admin authentication, and I made sure that call was documented as theirs.

Three things I would turn on in the first week. The raw-SQL concatenation analyser as a build error, because it catches this bug class at compile time rather than at review. The default constant redaction, which is now on by default but is worth verifying, because the failure mode — PII in logs — is a compliance problem rather than a bug. And a deliberate decision about EnableSensitiveDataLogging per environment, wired to configuration rather than to a compile constant, so nobody can leave it on in staging. I would also revisit whether any of our raw SQL still needs to be raw: EF 10's LeftJoin/RightJoin operators and JSON querying removed the reason for two of ours.

(d) Follow-up drill chain

Why did owned entity types cause the assignment to fail at all?

Because owned types are entity types under the hood: EF gives them a key, usually a shadow key made of the owner's key, and tracks them in the identity map like anything else. When you assign the shipping address instance to the billing property, both navigations point at one tracked entity with one identity, and EF cannot decide which owner it belongs to — hence the exception. Complex types have no identity at all; they are stored as part of the owner's entry, so an assignment copies the property values and there is nothing to conflict. This is also why comparison behaves differently in LINQ: entity comparison compiles to a key comparison, complex-type comparison to a member-by-member comparison.

What if you had needed a collection of value objects?

Then the choice narrows, because complex types only support collections when mapped to JSON — table splitting cannot hold a collection, and collections of structs are not supported at all yet. So a list of addresses per customer means either a JSON column, which gives you one round trip, atomic updates with the parent, and queryability through JSON_VALUE-based translation on SQL Server 2025 or Azure SQL, or a genuine child table, which gives you indexing, foreign keys and the ability to query the children independently. My rule is the access pattern: if the children are only ever read and written with the parent and you never need to index or join on them, JSON; if anything queries them on their own, a table. Getting that wrong is expensive to undo, so it deserves a deliberate decision.

At what data volume does mapping to a JSON column become a bad idea?

Two limits bite before raw size does. First, updates: a change to any property in a JSON document historically rewrote the whole column value, so a 200 KB document updated per request is a lot of write amplification — EF 10 improves this materially on SQL Server 2025 by translating ExecuteUpdateAsync into the JSON type's modify function, which updates in place, but that requires the new json data type rather than nvarchar(max). Second, queryability: filtering on a JSON property means a computed column plus an index, or a scan, so a predicate used on every request is a reason to promote that property to a real column. I would keep JSON documents small and read-mostly, and I would measure the update path specifically, because that is where it goes wrong quietly.

What did you trade away in the three table-to-JSON conversions?

Referential integrity and independent queryability, knowingly. Those child rows had foreign keys and indexes, and after the move they are properties inside a document that the database will not police — so an invariant that used to be enforced by a constraint is now enforced only by our code. I compensated with a check constraint on the JSON shape where the provider allowed it, and with tests, but it is genuinely weaker. I also gave up the ability for the reporting team to join against those tables, which meant publishing a view that shreds the JSON back into rows for them — an extra artefact to maintain that I did not budget for and would call out explicitly next time.

How did you get two weeks of dual-read approved?

By pricing the alternative. A one-shot cutover on the three real migrations meant a window where a bug in the backfill would be discovered by users against data we had already dropped, and the recovery would be a restore. Dual-read behind a flag cost two weeks of a slightly slower read path and a bit of extra code, and gave us a comparison job that asserted the JSON and the table agreed for every row every night — which found 340 rows where the backfill had mishandled nulls in an optional field. I presented that number afterwards as the justification, and it is now the default shape for data migrations on that team.

Would this refactor even be necessary if you started fresh on EF Core 10?

No, and that is the honest framing: complex types are now the recommended way to model both table splitting and JSON, and the docs say plainly that users on owned entity types for those purposes should switch. Starting fresh I would use complex types for every value object from day one, use structs where the type is genuinely small and immutable, and reserve owned entity types for the case they are still right for — a genuinely dependent child entity with its own lifecycle inside an aggregate. The reason the refactor existed at all is that the primitive we needed did not exist when the model was written, which is worth saying out loud, because it distinguishes debt from carelessness.

(a) Worked example EXAMPLE — replace with your own

A strong mid-level engineer joined the team and kept producing the same defect in different disguises: an update that overwrote a colleague's concurrent edit, a delete that took a child row with it, a save that did nothing. Every one of them came from the same gap — she was treating DbContext as a data-access API rather than as a stateful graph of tracked objects. Coaching her through it was the most useful mentoring I have done, mostly because I had to first work out what she actually believed.

The belief was reasonable and wrong: that db.Update(entity) means "save this entity". What it means is attach this graph and mark every scalar property as modified, which produces an UPDATE touching every column — including the ones the user did not edit, and including whatever stale values arrived from the client. That is how the lost-update bug happened: the API took a DTO from the browser, mapped it onto a new entity, called Update, and wrote all twenty columns over the top of a change another user had made two seconds earlier.

// What she wrote: every column written, stale values included.
var entity = _mapper.Map<Customer>(dto);
db.Update(entity);
await db.SaveChangesAsync();

// What we moved to: fetch tracked, apply, let the tracker compute the diff.
var customer = await db.Customers.FindAsync(dto.Id)
    ?? throw new NotFoundException(dto.Id);
customer.Apply(dto);                       // domain method; sets only what changed
await db.SaveChangesAsync();               // UPDATE touches only modified columns

// And, where the data is concurrently edited, an actual concurrency token:
modelBuilder.Entity<Customer>().Property<byte[]>("RowVersion").IsRowVersion();

The teaching device that worked — after two failed attempts at explaining it in prose — was making the tracker visible. I had her print db.ChangeTracker.DebugView.LongView before and after each operation in a scratch console app, and work through six scenarios: add, modify one property, attach an untracked graph, delete a parent with children, re-attach an entity with the same key as a tracked one, and save twice. Seeing Modified: {Name, Email, CreditLimit, …} when she had only meant to change one field ended the argument in ninety seconds.

(d) Follow-up drill chain

Why is fetch-then-mutate better than Update, mechanically?

Because the tracker keeps an original-values snapshot of the entity it loaded, so at save time it compares current against original and marks only genuinely changed properties as modified — the resulting UPDATE touches a subset of columns and leaves everything else alone. Update has no snapshot to compare against, because the entity arrived from outside, so EF conservatively marks everything modified. The practical consequence is the lost update: with Update, a field the user never saw gets written back with whatever the client sent, overwriting a concurrent change. The cost of fetch-then-mutate is one extra round trip, which is usually the right price and is exactly the trade I would name.

What if the extra read is too expensive — a high-rate write path?

Then I would use Attach and mark only the properties the caller actually supplied, which produces the same narrow UPDATE without the read, or drop to ExecuteUpdateAsync for a purely set-based change. Both give up something: Attach means you are trusting the client's values for the columns you mark, and ExecuteUpdateAsync bypasses the change tracker entirely, so any SaveChanges interceptor, audit-stamping override or domain-event dispatch you rely on simply does not run. That last point is the one I would emphasise, because it is the trap: teams adopt ExecuteUpdate for speed and quietly lose their audit trail. Either way, a concurrency token is what makes the no-read path safe rather than merely fast.

At what team size does mentoring one person stop being the right investment?

Roughly the point where the same gap appears in more than two people, because then you are treating a symptom of missing shared knowledge. At that point the leverage moves to artefacts: a written explanation with runnable examples, an analyser or review checklist that catches the pattern mechanically, and a design that makes the wrong thing harder — for us, that meant handlers receiving a loaded aggregate rather than a raw context, so Update was not the obvious call any more. I would still do the one-to-one work, because it is how you find out what the gap actually is, but I would treat the first person as research and the doc as the deliverable.

What did you trade away by having her write the doc rather than writing it yourself?

Speed and polish. I could have written it in ninety minutes and it would have been more precise; hers took a week of her time and needed two rounds of correction, and the first version had a genuinely wrong statement about cascade behaviour that I had to catch. What I bought was that she now owns the concept — the person who writes the explanation is the person who has to resolve every ambiguity — and that new joiners get a document written by someone who recently did not understand it, which is usually better pedagogy than one written by someone who never struggled. I would make the same trade again, but I would review it earlier.

How did you avoid making her feel singled out?

By framing it as a gap in the codebase rather than in her. The first conversation opened with the observation that Update was used in fourteen places by six different people and that most of them were probably wrong — which was true — so the investigation was into our conventions, not into her PRs. She found eleven of the fourteen. It also helped that I said plainly that I had made the same mistake and could show her the commit where I did. At senior level, the interviewer is often listening for whether your mentoring creates safety or compliance, and the concrete evidence is what the person did next.

Would you teach it differently on EF Core 10?

The core concepts are unchanged, which is a point in EF's favour: change tracking, the identity map and the original-values snapshot have been stable for years. What I would add today is the set-based path, because it is now genuinely good: ExecuteUpdateAsync takes a plain lambda since EF 10, so building setters conditionally no longer requires hand-constructed expression trees, and it works against complex types in JSON columns. That makes it a legitimate first choice for bulk operations rather than an escape hatch. But I would teach it second, after the tracker, precisely because it bypasses everything the tracker does — you cannot judge when to skip a mechanism you do not understand.

11Ship the report, not the model

Mid scope / deadline negotiation

(a) Worked example EXAMPLE — replace with your own

Nine working days before a contractual deadline, a customer needed a reconciliation report: eleven joins, three aggregates, a pivot by month, over about 40 million rows. The plan of record was to extend the domain model with the entities the report needed. I argued for not touching the model at all, and the negotiation — not the SQL — is the story.

The technical fork was real. Modelling it properly meant four new entity types, their configuration, migrations, and a set of LINQ queries that EF would have to translate — and two of the aggregates involved a GroupBy with a projection shape that EF Core does not translate, so they would have become client evaluation or raw SQL anyway. Estimated: fifteen to eighteen days. The alternative was to write the report as SQL and map it onto a keyless entity type, which EF supports precisely for this: a type with no primary key, no change tracking, read-only, mapped to a view or a query.

// Keyless entity type mapped to a view: no key, no tracking, no migrations for it.
modelBuilder.Entity<ReconciliationRow>(b =>
{
    b.HasNoKey();
    b.ToView("vw_Reconciliation");     // the view is owned by a versioned .sql file
});

var rows = await db.Set<ReconciliationRow>()
    .Where(r => r.Month >= from && r.Month < to)
    .ToListAsync();

// The lighter alternative when there is no view: SqlQuery for an arbitrary result shape (EF Core 7+)
var totals = await db.Database
    .SqlQuery<MonthTotal>($"EXEC dbo.Reconciliation @from = {from}, @to = {to}")
    .ToListAsync();

What made the negotiation work was giving the product owner a choice with costs rather than a recommendation. I wrote three options on one page: full modelling at 15–18 days and a missed deadline; the view-plus-keyless-type at 4 days with a named limitation (the report is read-only, cannot be filtered on arbitrary columns without changing the view, and adds a SQL artefact the team must maintain); and a manual export at 1 day that would need repeating monthly by a human. He picked the middle one in about four minutes, which is what usually happens when the options are concrete.

The part I insisted on, and would insist on again, was writing the limitation into the ticket. "This report is a view, not a model. Adding a column means changing SQL. If we need to filter or sort by a column not in the view, that is a new change." That sentence is what stops a tactical decision from silently becoming an architectural one, and it is what I would point at if an interviewer asked how I avoid accumulating debt under deadline pressure.

Result: shipped in four days with two days of slack, the deadline was met, and the view is still in production three years later — which is either a success or a warning, depending on how you frame it. It has been extended twice, both times by the same process.

What I would do differently: I did not put an expiry review on it. A tactical artefact with no scheduled reconsideration becomes permanent by default, and a six-month "is this still the right shape?" ticket costs nothing to create.

Why a keyless entity type rather than just a DTO from raw SQL?

Because a keyless type is still part of the EF model, which buys three things: the query is composable, so callers can add Where and OrderBy in LINQ and EF pushes them into SQL against the view; the mapping is configured and validated at model-building time, so a column rename in the view fails fast rather than at first execution; and it participates in the same context, connection and transaction as everything else. A raw SqlQuery<T> is fine and I use it, but composition is what mattered here — the screen needed filtering by month and by account, and I did not want three views. The cost is that the type must be explicitly keyless and read-only, which is a good constraint to have to declare.

What if the customer had then asked for the report to be editable?

Then the decision has to be reopened rather than patched, and I would say so before writing any code. A keyless type cannot be tracked or saved, so "editable" means real entities with keys, which is exactly the 15–18 days I deferred — and that is the point of having written the limitation into the ticket: the conversation starts from a documented trade-off rather than from an argument about why the existing thing cannot be extended. In practice I would look for a narrower answer first, because "editable" usually means one field on one row, and that can be a small properly-modelled entity alongside the view rather than a full remodelling of the report.

When the view's cost per execution stops fitting the request budget, which for us was around 40 million rows and 2.5 seconds — acceptable for a report, unacceptable if it ever moved into a page load. The next steps in order are: indexed views if the aggregates qualify and the write cost is tolerable; a materialised summary table refreshed on a schedule, which trades freshness for speed; and finally a separate read store fed by change events if the reporting load starts affecting the transactional workload. I would move at the point where the report's queries show up in the database's top-ten waits, not before, and I would say that the trigger is a measurement rather than a row count.

Testability and locality. The business rules for the reconciliation now live in SQL, which our unit tests cannot reach, so they are covered only by integration tests against a real database — slower, and easier to skip. The logic also lives in a different file, in a different language, reviewed by different people, so a change to a business rule can be made in C# and missed in the view. I mitigated it by versioning the view as a checked-in .sql file applied by a migration, so it is reviewed like code and cannot drift between environments, and by writing five integration tests that assert the totals against hand-computed fixtures. 12The soft delete that deleted for real

Staff data-loss / corruption scare

(a) Worked example EXAMPLE — replace with your own

A cleanup job removed 61,000 rows that should have been retained, and we did not notice for eleven hours. Nothing was lost permanently — point-in-time restore saved us — but the eleven hours is the part I still think about, and the cause was two EF features interacting in a way neither of them documents as dangerous.

The system used the standard soft-delete pattern: an IsDeleted flag, a global query filter so every query excludes deleted rows, and a SaveChanges override that converts EntityState.Deleted into a modification of the flag. That is a good pattern and it worked for years.

// The pattern: a filter, and a SaveChanges override that turns Delete into Update.
modelBuilder.Entity<Document>().HasQueryFilter(d => !d.IsDeleted);

public override Task<int> SaveChangesAsync(CancellationToken ct = default)
{
    foreach (var e in ChangeTracker.Entries<ISoftDelete>().Where(e => e.State == EntityState.Deleted))
    {
        e.State = EntityState.Modified;
        e.Entity.IsDeleted = true;
    }
    return base.SaveChangesAsync(ct);
}

// The line that bypassed all of it:
await db.Documents.Where(d => d.ArchivedOn < cutoff).ExecuteDeleteAsync();

The mechanism is simple once you see it: ExecuteDeleteAsync and ExecuteUpdateAsync do not go through the change tracker or SaveChanges. They translate the LINQ into a single DELETE/UPDATE statement and send it. Global query filters are applied — so the statement did respect !d.IsDeleted — but the SaveChanges override that implements soft delete never ran, so the rows were physically removed. Every audit interceptor, domain-event dispatch and UpdatedBy stamp was skipped too. The engineer who wrote it had done exactly the right thing for performance and had no way of knowing it turned a soft delete into a hard one.

The eleven hours were a monitoring failure, not an EF one. The job logged "removed 61,000 documents", which looked like a successful run. Nothing compared expected to actual, and nothing alerted on a row-count delta.

SaveChanges pathExecuteUpdate / ExecuteDelete
Change trackerUsed; entities loaded and diffedBypassed; no entities loaded

The controls we put in afterwards, in order of how much they were worth. First, an interceptor that refuses ExecuteDelete against soft-deletable types: a SaveChangesInterceptor cannot see these, so we used a DbCommandInterceptor that inspects the command tree and throws for a DELETE against a table on a known list, with an explicit opt-out attribute for the two legitimate cases. Crude, effective, and it has fired twice since. Second, every destructive job now computes an expected row count first and aborts if the actual differs by more than 10%. Third, the job's own log line became a metric with an alert on anomalous values.

The EF 10 feature that would have helped with the adjacent risk is named query filters. Before EF 10 an entity could have only one query filter, so teams combined soft delete and tenancy into a single predicate, and IgnoreQueryFilters() — needed to see deleted rows in an admin screen — disabled tenancy at the same time. That is a data-leak waiting to happen, and it nearly was ours: an admin restore screen used IgnoreQueryFilters() and would have shown other tenants' deleted documents if the tenancy filter had not also been applied at the repository level by luck. EF 10 lets you name each filter and disable them individually.

// EF Core 10: filters have names, and you disable them one at a time.
modelBuilder.Entity<Document>()
    .HasQueryFilter("SoftDelete", d => !d.IsDeleted)
    .HasQueryFilter("Tenant",     d => d.TenantId == _tenant.Id);

var deleted = await db.Documents
    .IgnoreQueryFilters(["SoftDelete"])   // tenancy still enforced
    .ToListAsync();

Result: full recovery via point-in-time restore to a staging copy and a targeted reinsert of 61,000 rows, roughly six hours of engineering, zero customer-visible data loss, and three controls that have since caught two more attempts. I ran the postmortem and the action item I insisted on was the anomaly alert, because that is what turns eleven hours into eleven minutes.

What I would do differently: the code review. Two of us approved that PR and both of us read ExecuteDeleteAsync as a performance improvement, which it was — we just did not ask what it bypassed. I now treat any first use of a bulk API in a codebase as a design change requiring a written note, not a routine optimisation.

The signal: you can state the mechanism precisely, you separate the data-loss cause from the detection failure (they are different problems with different fixes), and your action items are automated. The classic failure is a story with no detection lesson — "we restored from backup" is table stakes. The second is blaming the author of the line; the interviewer will note whether you approved it.

(d) Follow-up drill chain

Why did the global query filter apply but the SaveChanges override not?

Because they hook into two different pipelines. A global query filter is part of the model and is injected into the query expression tree during translation, so it affects any LINQ query — including the one that ExecuteDeleteAsync compiles into a DELETE … WHERE. The SaveChanges override, and interceptors of the same kind, sit in the update pipeline, which runs over the change tracker's entries — and ExecuteDelete never touches the change tracker, because its whole purpose is not to load entities. So the query half of your cross-cutting behaviour survives and the write half does not. That asymmetry is the thing I would want a candidate to be able to state, because it generalises to auditing, domain events and concurrency tokens.

What if you had needed the bulk delete's performance and the soft-delete semantics?

Then it becomes ExecuteUpdateAsync setting the flag, not ExecuteDeleteAsync — one statement, same performance, correct semantics — and on EF 10 that is nicer than it used to be because the setters are a plain lambda rather than an expression tree, so you can add the UpdatedBy and UpdatedOn stamps conditionally. What you still lose is anything your SaveChanges override did beyond the flag, most importantly domain events, so if a soft delete is supposed to publish a DocumentArchived event you have to publish it explicitly. I would encapsulate the whole thing in one extension method — SoftDeleteAsync — so there is exactly one correct implementation and the raw API is not the obvious call.

At what scale does the load-and-track soft delete stop being viable?

It degrades with row count in a very ordinary way: loading 61,000 entities to flip one boolean means 61,000 entity instances, 61,000 snapshots, a DetectChanges pass over all of them, and a batched set of updates — in our case about 40 seconds and 900 MB of allocation, versus 300 ms for the single statement. Below a few thousand rows the difference is not worth a special path. Above it, the answer is ExecuteUpdateAsync plus explicit handling of whatever the tracker would have done for you. That threshold is also roughly where the transaction duration starts to matter, because a long-running batch of updates holds locks that a single statement does not.

What did you trade away with the command interceptor guard?

Performance and elegance, both a little. Inspecting the command text on every execution costs a few microseconds per command, which is negligible for us but would not be for a very high-rate service, and it is string-shaped matching against a table list rather than a first-class model check, so it is fragile: a schema-qualified name or an alias could slip past it. I accepted that because it is defence in depth rather than the primary control — the primary control is the encapsulated SoftDeleteAsync method plus review — and a guard that catches most mistakes immediately beats a perfect one that we would still be designing. I documented the fragility in the class comment so nobody mistakes it for a guarantee.

How did you run the postmortem given that you had approved the change?

I said it in the first two minutes, before anyone else had to. The write-up opens with the review as a contributing factor, names both approvers including me, and frames the finding as "our review process has no concept of a semantics-changing API", which is the accurate systemic version. That mattered because the engineer who wrote the line was fairly new and was visibly braced for it; the fastest way to lose a good engineer is to let a blameless postmortem be blameless for everyone except the person whose name is on the commit. The action items were all systemic — the guard, the anomaly alert, the review rule — and none of them was "be more careful".

Would named query filters have prevented any of this?

Not the delete itself, but they would have removed the second, quieter risk in the same system. Before EF 10 one entity type could carry only one query filter, so soft delete and tenancy had to be combined into a single predicate, and any screen needing to see deleted rows had to call IgnoreQueryFilters(), which switched off tenancy at the same time. That is a cross-tenant data-leak pattern that exists in a lot of multi-tenant EF codebases and is usually saved only by a second filter somewhere else. EF 10's named filters let you declare them separately and disable exactly one — IgnoreQueryFilters(["SoftDelete"]) — which turns a latent leak into a non-issue. It is the EF 10 feature I would adopt first in any multi-tenant system.

Two hard problems came out of this and both are good interview material. The first is migrations across N databases. (d) Follow-up drill chain

Why not move everyone to database-per-tenant for consistency?

Because it would multiply the operational surface by 900 to satisfy four customers. Each database is a thing to migrate, back up, monitor, patch, size and pay for, and at 900 databases the migration runner stops being a script and becomes a platform with its own failure modes, staged rollouts and reconciliation. It also costs real money: on managed cloud SQL you pay per database or per pool, and a thousand mostly-idle databases is dramatically more expensive than one shared one, elastic pools notwithstanding. The hybrid keeps the expensive model scoped to the customers who are paying for it, which is also the honest commercial framing — isolation became a priced feature rather than a platform-wide cost.

What if a shared-database tenant grows large enough to need moving?

That is a designed-for case rather than an exception, and it is the reason the two models share one schema. Moving a tenant is: provision a database, run the migrations to the current version, copy that tenant's rows with the filter applied, verify counts and checksums, switch the placement record, and keep the source rows for a retention window before deleting them. The hard part is the cutover window, because writes have to stop or be queued for the duration — we do it with a short read-only period, typically under two minutes for a mid-sized tenant. I would not attempt zero-downtime tenant moves until a customer asks, because change-data-capture-based migration is a lot of machinery for a rare operation.

At what number of databases does your approach break?

Two things break at different points. The connection pooling breaks first: each distinct connection string gets its own ADO.NET pool, so at a few hundred tenants per process you have hundreds of pools each holding idle connections, and memory and connection counts get ugly — somewhere around 200 to 400 in our sizing. The migration runner breaks second, at low thousands, when a sequential fleet run no longer fits a deploy window and you need parallelism, batching and partial-rollout logic. If we were heading past a few hundred dedicated tenants I would move to a sharded model with tenants grouped into a small number of physical databases, which keeps isolation groups without a database per customer. I wrote that limit down rather than discovering it.

What did you trade away by supporting both models?

Simplicity, permanently. Every piece of infrastructure now has a tenant dimension — caches keyed by tenant, background jobs iterating placements, logs and metrics tagged, integration tests that must run in both modes — and a new engineer has to learn the concept before they can safely write a query. There is also a whole class of bug that only exists in the hybrid: code that works on the shared database because the filter saves it, and would be wrong on a dedicated one, or vice versa. We pay for that with a test suite that runs the critical paths against both configurations, which doubles those tests' runtime. If we had only four tenants total I would have picked one model and lived with it.

How did you handle the sales pressure while the design was still open?

By separating the commitment from the design. I gave the commercial team a date I could defend for the capability, and a written list of what "isolation" would and would not mean — separate database and credentials and backups, yes; separate region, yes; separate application instance, no — so the contract language could be drafted against something real rather than against a word. That prevented the classic failure where sales sells "fully isolated" and engineering discovers in month three that it was read as "dedicated infrastructure end to end". I also said explicitly what would slip if this was pulled forward, and let the sponsor choose. The negotiation took two meetings and saved a quarter.

What would you use from EF Core 10 here?

Named query filters, without hesitation. The single biggest latent risk in a shared-database multi-tenant model is that soft delete and tenancy share one filter, so any screen that calls IgnoreQueryFilters() to show archived rows also switches tenancy off — a cross-tenant leak one line away at all times. EF 10 lets each filter carry a name and be disabled individually, which turns that from a discipline problem into a mechanical one. Beyond that, I would keep watching EF 11's Cosmos work if any tenant ever asks for a document-shaped store, but for a relational fleet the named filters are the feature that changes the design rather than the code.

14Two teams, one schema, one migrations folder

(a) Worked example EXAMPLE — replace with your own

Two teams shared a database and a single DbContext in a shared library. Every fortnight, two migrations generated on two branches would merge into a folder with a snapshot file that could only represent one truth, and someone would spend a day untangling it. That is the surface problem. The real problem was that schema ownership was undefined, and the migrations conflict was just where it became visible.

The EF mechanic that makes this painful is worth stating precisely: migrations are ordered by timestamped identifiers, and the model snapshot (ModelSnapshot.cs) is a single generated file representing the model as of the last migration. Two people generating migrations in parallel produce two snapshots that both claim to be the latest, and git merges them into something that compiles and is wrong — so the next migration is generated against a corrupted baseline and proposes to drop columns nobody touched.

# The mechanical resolution when it happens anyway (documented, so it stops being folklore):
git checkout --theirs Migrations/AppContextModelSnapshot.cs   # take the mainline snapshot
dotnet ef migrations remove                                    # unwind your local migration
git rebase main                                                # take their migration
dotnet ef migrations add AddShipmentTracking                   # regenerate against the true baseline
dotnet ef migrations script --idempotent --from <prev> --output ./verify.sql   # read it

The structural fix was to stop sharing the context. We split it into two DbContext types over the same physical database, one per bounded context, each with its own migrations assembly, its own migrations history table (__EFMigrationsHistory_Orders, __EFMigrationsHistory_Shipping) and its own schema. Tables owned by the other team are mapped where needed but marked ExcludeFromMigrations(), so each team's differ only ever proposes changes to tables it owns.

// Each context declares what it owns; foreign tables are read-only citizens.
protected override void OnModelCreating(ModelBuilder b)
{
    b.HasDefaultSchema("shipping");
    b.Entity<Shipment>().ToTable("Shipments", "shipping");
    b.Entity<Order>().ToTable("Orders", "orders", t => t.ExcludeFromMigrations());  // owned by Orders
}

// And the history table is per-context, so the two migration streams never collide.
o.UseSqlServer(cs, x => x.MigrationsHistoryTable("__EFMigrationsHistory", "shipping"));

The organisational half took longer than the technical half and is the part interviewers care about. We wrote a one-page contract: every table has exactly one owning team; cross-schema reads go through a view published by the owner, which is the versioned interface; cross-schema writes are not allowed, they become an API call or a message; a breaking change to a published view needs two weeks' notice and a deprecation period. Getting that agreed took four meetings across two engineering managers and one architect who initially wanted a full database split.

I argued against the full split, and this is the trade-off I would defend. Splitting the database physically would have removed all coupling and cost us cross-schema joins that both teams relied on for reporting, plus transactional consistency on the one workflow that genuinely spans both. The middle position — one database, two schemas, two contexts, ownership by convention enforced by tooling — kept the joins and killed the conflicts. It is less pure and it worked.

Result: migration conflicts went from roughly two per sprint to zero over the following year; the day-per-fortnight of untangling disappeared; and the ownership document became the template for three later team splits. The cost was two weeks of setup and a permanent rule that nobody may write to another team's tables.

What I would do differently: I let it run for five months before acting, because each individual conflict was only a day and nobody escalated. Recurring small costs do not escalate themselves — I now total them up explicitly before deciding they are tolerable.

(d) Follow-up drill chain

Why does the model snapshot make parallel migrations so painful?

Because it is a single generated file that encodes the entire model as of the most recent migration, and it is the baseline the differ uses to compute the next migration. Two branches each add a migration and each regenerate the snapshot from their own model, so git sees two rewrites of the same large file and merges them line by line into a state that matches neither branch. Nothing fails at that moment — it compiles — and the damage shows up in the next migration, which is generated against the corrupted baseline and proposes to add or drop things nobody changed. That delayed feedback is what makes it expensive; the resolution is mechanical once you know it, which is why we documented it rather than relying on whoever had seen it before.

What if the two teams genuinely need a transaction spanning both schemas?

They can have it, and that is one of the reasons I kept a single physical database: a transaction across two schemas in one database is an ordinary local transaction, and both contexts can share a connection and a DbTransaction via UseTransaction. What I did not want was that becoming routine, because a workflow that transactionally spans two teams' tables is a workflow that couples their deployment schedules. So the rule is that there is exactly one such flow, it is documented, both teams know about it, and any proposal for a second one is an architecture discussion rather than a pull request. If the count ever went past two or three I would take that as evidence the boundary is in the wrong place.

At what team count does schema-per-team stop working?

It scales further than people expect on the technical side — a dozen schemas in one database is unremarkable — but it stops working socially at the point where a single database's operational limits become a shared fate: one team's runaway query, one team's index maintenance window, one team's need to restore. That is usually around four or five teams for us, and the symptom is scheduling conflicts rather than merge conflicts. Past that I would split databases along the lines the ownership document already draws, which is the real payoff of writing it: the boundaries are already agreed, so the physical split becomes a migration rather than a negotiation. I would also expect to give up the cross-schema reporting joins at that point and stand up a proper analytics copy.

What did you trade away by keeping one physical database?

Blast-radius isolation and independent scaling. Both teams share a connection limit, a CPU budget, a backup schedule and a maintenance window, so a bad query on one side is a shared incident, and neither team can size their storage independently. We also kept a form of coupling that is easy to abuse: nothing physically prevents a developer writing to another schema's table, so the ownership rule is enforced by review and by database permissions rather than by architecture. I made the permissions real — each context's login has write access only to its own schema — which converts the convention into a runtime failure, and that is what I would point at if challenged on whether "by convention" is good enough.

How did you get two managers and an architect to agree?

By writing the options down and letting the costs argue. The architect wanted a full database split, which was defensible; I priced it — six to eight weeks, loss of three reporting joins, a new integration for the one cross-team workflow — against a two-week middle option, and put both in the same document with the same criteria. Then I asked for a decision rather than agreement, which is a distinction that matters: I did not need everyone to prefer my option, I needed a decision they would all support. The architect's concern went into the document as a written trigger — "if the cross-schema workflow count exceeds three, revisit the physical split" — so his position was preserved rather than defeated, and he supported the outcome.

Is there anything in recent EF versions that helps with this?

Nothing that changes the shape, and I would say that honestly — the multiple-context, per-context history table, ExcludeFromMigrations toolkit has been stable since EF Core 5 and is still the right answer. The relevant recent change is operational rather than modelling: migration bundles, which give you a self-contained executable per context that CI produces and CD applies, so each team's migrations reach production through its own gated pipeline stage instead of at application startup. That removes the last place where the two teams' schema changes were implicitly coupled — the shared deploy. It is a small feature that solves a real coordination problem, which is often what these questions are actually about.

The premise was sound in the abstract. Our read queries were joining eight tables, and CQRS with a separate read model is a well-understood answer. (d) Follow-up drill chain

When would a read model have been the right answer?

When the read shape is genuinely different from the write shape, not merely slower — for example when a screen needs data from five services that no single database can join, when the read volume is orders of magnitude above what the write store can serve even with correct indexing, or when the query language itself is wrong for the job, such as full-text or graph traversal over relational tables. The tell is that no amount of indexing or projection on the transactional model gets you there, because the model is a poor fit rather than a poorly tuned one. Our second attempt met that bar: it aggregated across five services and had no single-database alternative. That is the criterion I now apply before proposing one.

What if the sponsor had refused to cancel?

Then my job would have been to give them the smallest viable version and an explicit checkpoint, not to keep arguing. I would have proposed scoping the read model to the three screens with genuine query-shaped problems, delivering that in four weeks, and setting a measurable exit criterion — if those three screens are not materially better than the index-and-projection alternative, we stop. At what read volume does index tuning stop being enough?

It stops when the write cost of the indexes you need starts to hurt, or when the read volume saturates the instance regardless of plan quality. Practically: every index is a write amplification, so a table with twelve indexes on a high-insert path is already paying, and adding a thirteenth covering index for one screen can slow the ingest path more than it speeds the read. In our system the writes were modest, which is exactly why indexing won — and I would say that explicitly, because it is the condition that makes the answer generalisable. If the same twelve screens sat on a table taking 5,000 inserts a second, the trade would flip and a separate read store, or read replicas, would be back on the table.

I do not dress that up, and I have found that stating it plainly is what makes the rest of the story credible — a failure story with no number in it reads as a rehearsed humility exercise. The bigger cost was opportunity: two engineers spent a quarter on something that shipped nothing, and I was the one who chose that for them.

The first was SELECT * by default. Projection to DTOs cut the bytes read per request by 96% on those endpoints, and because the database's data-page reads dropped, so did the IO component of the bill.

The second was chatty saves. A nightly import created 180,000 rows one SaveChanges at a time inside a loop — 180,000 round trips, each with its own transaction. EF batches statements within a single SaveChanges up to MaxBatchSize (42 by default on SQL Server), so moving the save outside the loop, in chunks of 2,000, took the import from 71 minutes to 4.

// Before: one round trip and one transaction per row.
foreach (var row in rows) { db.Add(Map(row)); await db.SaveChangesAsync(); }

// After: batched, chunked, untracked between chunks so the tracker does not grow unbounded.
foreach (var chunk in rows.Chunk(2_000))
{
    db.AddRange(chunk.Select(Map));
    await db.SaveChangesAsync();
    db.ChangeTracker.Clear();       // otherwise DetectChanges cost grows with every chunk
}

Our Contains-style filters produced a different SQL string for every distinct list length, so a filter called with 3, 7 and 12 ids compiled three plans. Sketch: unused reports, a dead index, a job nobody read the output of, a duplicated cache. These are the cheapest wins and they are always available.

Sketch: fewer columns, fewer round trips, better plans. Being able to hold both framings at once is a principal-level signal.

(d) Follow-up drill chain

Why not just move to a cheaper tier first?

Because a cheaper tier under the same load turns a cost problem into an availability problem, and you find that out in production. The load was genuinely there — 61% of it was waste, but the database did not know that — so downsizing before removing the waste would have produced timeouts and a rollback, after which nobody would fund the real work. Sequencing matters for a second reason: once the load is 58% lower, the right-sizing decision is easy and low-risk, and you can prove the headroom with a load test rather than argue about it. I would move tier first only if the measurements said we were genuinely over-provisioned relative to real demand, which is a different finding.

What if the workload had been write-heavy rather than read-heavy?

Then the levers change substantially and I would say so rather than reciting the same list. On a write-heavy system the costs are log throughput, index maintenance and lock contention, so the wins come from reducing the number of indexes rather than adding them, batching writes to amortise log flushes, moving to set-based operations with ExecuteUpdateAsync instead of load-modify-save, and shortening transactions so locks are held briefly. Table design matters more too — a clustered index that causes page splits on every insert is a large, invisible cost. The one thing that transfers is the method: measure what the resource is spent on before choosing a lever.

At what point does plan-cache thrash actually matter?

It matters when compilation CPU is a visible share of total CPU and when cache eviction starts pushing out plans you need. Our tell was 900 compilations per second and 4.2 GB of single-use plans, which is unambiguous; at 20 compilations per second nobody should care. The subtlety is that the fix is not free in either direction — a single parameterised shape gives you one plan but denies the optimiser cardinality information, so a query that is fast for three ids and needs a different plan for three thousand gets one compromise plan. That is precisely why EF 10 defaults to padded scalar parameters and exposes the mode per query: it is a genuine trade with no universal right answer, and being able to say that is better than quoting a default.

What did you trade away with the projections?

Reuse and a bit of maintainability, the same trade as any DTO layer. Fifteen endpoints now have fifteen projection shapes, and a column rename touches all the ones that use it; there is also a real risk of a projection drifting from what the screen needs and quietly selecting a column nobody displays any more. I bounded it by putting each projection as a static expression next to its DTO so it is testable and greppable, and by adding a monthly check that compares columns selected against fields rendered — which is crude and has found two stale columns in a year. The alternative, a single fat entity query reused everywhere, is what got us here, so I would take this trade every time.

How did you get engineering time for this against a feature roadmap?

By making the ask small and the payback explicit. I asked for two weeks of measurement only, with no commitment to the fixes, which is an easy yes; the measurement produced the 61% number, and that number made the rest of the case by itself. I also brought the finance partner into the review, so the saving was quantified by someone whose numbers the sponsor already trusted rather than by an engineer with an estimate. The part I would repeat is separating the investigation from the work — asking for sixteen days to fix an unproven problem is a hard sell, asking for ten to measure it is not.

What would you do differently on EF Core 10 specifically?

I would make the parameterised-collection mode an explicit, reviewed decision from the start rather than a discovery. EF 10's default — one padded scalar parameter per element — is a better default than either predecessor, but it is still a default, and on a system with hundreds of Contains call sites of wildly different cardinality the right answer varies per query. I would also look harder at ExecuteUpdateAsync for the import path now that it accepts a plain lambda, and at whether the two nvarchar(max) HTML columns should be a JSON complex type instead, which on SQL Server 2025 would let us update them in place with the modify function rather than rewriting the whole value.

(d) Follow-up drill chain

Why does the model drift from migrations in the first place?

Because the two are only connected when someone runs a command. The model is C# — conventions plus OnModelCreating — and migrations are a snapshot-plus-delta record of what has been applied; adding a property changes the model instantly and changes nothing else. Locally you can get away with it for a long time, especially if you use EnsureCreated or recreate the database, because the schema is generated from the current model rather than from the migration history. It only fails when the model meets a database built from migrations, which is production. has-pending-model-changes closes that gap by asking EF the direct question — does the differ produce anything against the last migration — which is exactly the check a human review cannot reliably perform.

What if a check is right but a team needs to ship past it?

Then they use the documented opt-out and the exception is visible, which is the whole point of having one. Our convention tests take an attribute with a required reason string, so an unbounded string column is allowed if someone writes down why, and the list of exceptions is reviewable in one place — I look at it quarterly and about a third of them turn out to be stale. The alternative, no escape hatch, produces one of two outcomes: the check gets deleted in a hurry during an incident, or people restructure code to evade it, which is worse because the evasion is invisible. A rule you can break loudly is more durable than one you cannot break at all.

At what point do these checks stop scaling?

The per-build time is the first limit — 80 seconds is invisible, 8 minutes is not, and the apply-from-empty check is the one that grows, because it replays every migration in the project's history against a fresh container. At around 300 migrations ours takes a minute; at a thousand it will not be acceptable, and the answer then is to squash the migration history into a baseline, which EF supports and which teams put off for far too long. The convention tests scale fine because they inspect the model in memory. The command-count assertions are the ones that scale worst socially rather than technically — every new endpoint is a decision about whether to assert on it, and without a default that decision gets skipped.

What did the checks cost beyond CI time?

A maintenance owner, which I under-budgeted. The convention tests need updating whenever a legitimate new pattern appears, the opt-out list needs periodic review, and the bundle build needs to track SDK and runtime-identifier changes — that is a few hours a quarter, and when I moved teams it briefly became nobody's job and two of the checks were disabled during a release crunch. I would now name an owner explicitly and put the review in a recurring team ritual rather than relying on the person who built them. The other cost is a subtle one: mechanical checks make people slightly less attentive in review, because the machine is watching, so I would not let the check list grow into a substitute for reading migrations.

How did you handle the engineer whose PR was the first to be blocked?

I paired with him on it within the hour, and then I used his case as the worked example in the documentation, with his agreement. The blocked PR was a legitimate change that needed a migration he had not realised was required, so it took eleven minutes to resolve — and making that visible was worth more than any amount of advance explanation, because the fear with a new blocking check is that it will cost you a day. I also asked him afterwards whether the error message had told him what to do, and it had not, so we changed the CI failure output to print the exact command to run. Error messages that end with a runnable command are the cheapest adoption tool there is.

Which of these checks did not exist in older EF versions?

has-pending-model-changes is the recent one — it arrived in EF Core 9, and before that teams approximated it by generating a migration in CI and asserting the output was empty, which worked but was fiddly and slow. Migration bundles came in EF Core 6 and are still under-used; a lot of teams are on modern EF and still calling Database.Migrate() at startup. The convention tests have always been possible because the model metadata API has been stable for years, which is worth pointing out: the most valuable check in that list is the one anyone could have written at any time, and nobody does until an incident makes it obvious.

18The 3 a.m. deadlock storm

(a) Worked example EXAMPLE — replace with your own

The page fired at 03:12: error rate above 5% on the inventory service, with SqlException 1205 — "transaction was deadlocked on lock resources and has been chosen as the deadlock victim" — at about 40 per minute. I was on call, alone, and it is the incident I use when asked how I operate under pressure, because most of what I did was decide what not to do.

The immediate mitigation came before the diagnosis, which is the right order. The service had EnableRetryOnFailure configured, but SQL Server error 1205 is not in the default transient-error list for the SQL Server provider — deadlocks are not treated as automatically retryable, because a retried transaction may not be idempotent. So the errors were reaching users. I did not change the retry policy at 3 a.m.; I scaled the nightly reindex job down to one worker, which cut the error rate by two thirds within four minutes, and then I stopped touching things and started reading.

The deadlock graph, pulled from the system_health extended-events session, showed the classic shape: two transactions taking the same two resources in opposite orders. One was our stock-adjustment handler updating StockItems then StockLedger; the other was the reindex job's batch, which EF was writing in a different order because SaveChanges orders its statements by dependency, not by a stable order across entity types, and within a type by the order entities were tracked. Two batches touching overlapping rows in different sequences deadlock reliably once concurrency is high enough.

// The durable fix: impose a deterministic order before saving, so two batches
// can never take the same rows in opposite sequences.
foreach (var item in adjustments.OrderBy(a => a.StockItemId))
    ApplyAdjustment(item);
await db.SaveChangesAsync();

// And make the retry real for deadlocks, since our handler is idempotent by design.
o.UseSqlServer(cs, sql => sql.EnableRetryOnFailure(
    maxRetryCount: 5,
    maxRetryDelay: TimeSpan.FromSeconds(5),
    errorNumbersToAdd: new[] { 1205 }));   // deadlock victim — only safe because we are idempotent

// Explicit transactions must run inside the strategy, or the retry silently does not apply.
var strategy = db.Database.CreateExecutionStrategy();
await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync();
    await DoWorkAsync();
    await tx.CommitAsync();
});

(d) Follow-up drill chain

Why is a deadlock not automatically retryable?

Because the framework cannot know whether repeating your transaction is safe. A deadlock victim is rolled back entirely, so retrying is correct if the unit of work is idempotent and self-contained — but if the transaction had side effects outside the database, or if it was part of a longer conversation where the caller has already acted on partial results, a retry duplicates work. That is why the SQL Server provider's default transient list covers connection-level and throttling errors but not 1205, and why adding it via errorNumbersToAdd is a decision you make per application, having reasoned about idempotency. It is also why user-initiated transactions are excluded from the execution strategy unless you wrap them yourself: EF refuses to guess.

What if the ordering fix had not been possible — say the two writers were different services?

Then the cycle has to be broken somewhere else, and there are three places. You can serialise access to the contended resource with an application-level lock or a queue, which trades throughput for determinism and is often the honest answer for a low-volume hot resource. You can change the locking behaviour — read-committed snapshot isolation stops readers blocking writers, which eliminates a large family of deadlocks at the cost of version-store growth in tempdb, and it is a database-wide change I would only make with a DBA and a load test. Or you can restructure so the two services do not write the same rows, typically by making one of them publish an event and the other own the write. I would try them in that order, because the first is reversible and the last is a redesign.

At what concurrency does this class of problem appear?

Deadlocks are a function of overlap probability, so they scale with concurrency times lock duration times how much of the key space each transaction touches. Ours was invisible at four concurrent workers and constant at sixteen, which is typical — the curve is steep once the overlap probability crosses a threshold, so a system can look completely healthy right up until a job's parallelism is increased. That is why the mitigation was to reduce concurrency: it moves you back down the curve immediately without changing correctness. It also means load testing at production concurrency is the only way to find these before users do, and a test at half the concurrency proves almost nothing.

What did you trade away by adding 1205 to the retryable list?

A safety default, deliberately. Every unit of work in that service now retries on deadlock, which is correct for the stock-adjustment handler because it is idempotent by design — it computes an absolute target rather than applying a delta — but I had to check every other handler in the service before enabling it, and one of them was not idempotent and had to be changed first. There is also a latency cost: a retried transaction with a back-off adds up to several seconds to the tail, which for an interactive endpoint might be worse than a clean failure the client can handle. I documented the idempotency requirement in the context's configuration file with a comment, because the next person to add a handler will not know that the retry policy imposes an obligation on their code.

How did you communicate during the incident?

Short updates on a fixed cadence, in the incident channel, in a format anyone could read: what is broken, what I have changed, what I am doing next, when I will update again. Three updates in the first fifteen minutes, then every fifteen. I woke one other person at 03:40 — not to help fix it, but because I had been alone for half an hour and wanted a second opinion before making any further change, which I now think is the single most useful on-call habit I have. I also wrote the timeline as I went rather than reconstructing it afterwards, which made the postmortem a thirty-minute job and made it accurate.

Does anything in current EF Core make this easier to diagnose?

Two things help, and both are diagnostic rather than preventive. EF Core 10 simplified generated parameter names — @city rather than @__city_0 — which sounds trivial until you are correlating a deadlock graph's statement text with a piece of C# at four in the morning; it genuinely shortened that step for us. And EF's interceptor and diagnostic-listener surface has been stable for long enough that capturing the failing command, its parameters and the entity types involved when a DbUpdateException occurs is a small amount of code with a large payoff — that is what I would build next, so the alert carries the deadlock graph and the EF-side context together.

(d) Follow-up drill chain

Why is the in-memory provider actively misleading rather than merely limited?

Because it does not translate anything: it executes your LINQ against object collections with LINQ-to-Objects semantics, so every query "works", including ones no relational provider can translate. It also has no schema, so it cannot enforce nullability, lengths, unique constraints, foreign keys or precision, and it has no transactions in any meaningful sense — which means a test can assert behaviour that the real database would reject outright. The EF team's own documentation says it is not designed for testing that a query works against a relational database and recommends against using it that way. It is legitimately useful for testing code paths that merely happen to hold a context, but calling that a data-access test is the error.

What if the team could not run containers in CI?

Then I would take the layered fallback rather than give up on truth. SQLite in-memory as the default gate catches every translation failure, which is the largest defect class, and it runs anywhere; you then need a smaller nightly or pre-merge suite against a real engine — a shared, per-branch database provisioned by the pipeline, or an ephemeral cloud database — to catch the semantic differences SQLite hides. I would be explicit about what the fast gate does not cover, in a comment at the top of the test project, so nobody mistakes green for safe. The one option I would refuse is going back to mocking DbSet, because that tests the mock.

At what suite size does a container per assembly stop working?

Container startup is a fixed cost of roughly twenty to forty seconds for SQL Server, so it amortises well over a few hundred tests and badly over ten. Our limit showed up differently: at around 900 database tests, the Respawn reset between tests became the dominant cost, and the answer was to move more tests to a shared-fixture model where a read-only test class seeds once and does not reset. Past a few thousand, I would shard by assembly across parallel CI agents rather than trying to make one agent faster. The signal that you have gone too far is when developers stop running the suite locally, because at that point the tests have become a CI gate rather than a development tool.

What did you trade away for the four-minute suite?

Local iteration speed, which is the cost that actually matters. Nobody minds four minutes in CI; people mind waiting four minutes before knowing whether a change compiles conceptually, and the risk is that they stop running tests locally and start pushing to find out. I mitigated it three ways: the domain suite stays under twenty seconds and is what you run constantly, the database suite has filters so you can run one class, and the container is reused between local runs rather than torn down. I also accepted a real infrastructure dependency — Docker on every developer machine and every CI agent — which caused two onboarding problems in the first quarter and needed a documented fallback.

How did you handle the objection that this was gold-plating?

I stopped arguing the principle and started counting. For the three months before the change I logged every defect that reached staging or production and marked whether a real-database test would have caught it; the answer was six out of nineteen, including the one that caused an incident. That list, on one slide, ended the discussion — and it was more honest than my original argument, because it also showed that thirteen of the nineteen would not have been caught, which kept my credibility for the next proposal. The general lesson I took is that testing arguments are unwinnable in the abstract and trivially winnable with a defect log.

Anything about this that is specific to current EF Core?

The guidance has firmed up rather than changed: the EF docs now explicitly steer people away from the in-memory provider for query testing and toward a real engine, and the Testcontainers-plus-migrations pattern has become the mainstream answer. One current detail worth knowing is that running your real migrations in the fixture also exercises EF 10's changed migration transaction behaviour — EF 9 wrapped all pending migrations in one transaction and EF 10 reverted that — so a migration that only worked under the EF 9 semantics will now fail in your test fixture rather than in production. That is a good example of why building the schema from migrations, not from EnsureCreated, is worth the extra seconds.

Principal pushing back on a stakeholder

(a) Worked example EXAMPLE — replace with your own

A senior executive came back from a conference and asked for semantic search over our document corpus in six weeks, with a specific justification: "EF Core 10 supports vector search natively now, so this is just a column." That last clause is technically true and operationally false, and unpicking it without dismissing the request is the story.

What is true: EF Core 10 has first-class support for the SQL Server vector data type and VECTOR_DISTANCE(). You map a property as SqlVector<float>, populate it from an embedding generator, and order by EF.Functions.VectorDistance("cosine", b.Embedding, query). That part genuinely is close to "just a column".

// EF Core 10, and this really is the easy part.
public class Document
{
    [Column(TypeName = "vector(1536)")]
    public SqlVector<float> Embedding { get; set; }
}

var similar = await db.Documents
    .OrderBy(d => EF.Functions.VectorDistance("cosine", d.Embedding, queryVector))
    .Take(10)
    .ToListAsync();

What is not true, and what I laid out in a one-page note. First, the vector data type requires Azure SQL Database or SQL Server 2025; our production instance was SQL Server 2019, and upgrading a 4 TB production database across two major versions is a quarter of work with its own risk profile, not a line in a sprint. Second, EF Core 10 requires .NET 10, and two of the three services that would need this were on .NET 8. Third — and this is the part nobody costs — an embedding pipeline is the actual project: choosing a model, generating embeddings for 2.3 million existing documents, keeping them current as documents change, handling the re-embedding cost when the model version changes, and evaluating whether the results are any good. The database column is maybe 5% of the work.

The pushback that worked was not "no". It was a two-week spike with a defined output: semantic search over a 50,000-document subset, running on a managed Azure SQL instance provisioned for the spike, with a relevance evaluation against twenty real user queries. That gave the executive something to show, gave us real numbers instead of estimates, and — crucially — surfaced the finding that mattered: on our corpus, hybrid search combining full-text and vector scores beat pure vector search substantially, which changed the design before we had built anything.

The spike also produced the honest answer on timing: a production rollout was two quarters, gated on the SQL Server 2025 upgrade that was already on the roadmap for other reasons. Attaching the feature to an existing platform project rather than proposing a new one is what got it funded.

Result: spike delivered in two weeks; the feature shipped seven months later alongside the database upgrade; the executive got a demo for his board meeting five weeks earlier than the original ask would have allowed, because a spike on a subset is faster than a production build. Nobody was told no.

What I would do differently: my first response in the meeting was to list the blockers. That was accurate and it made the room defensive. The version I would run now opens with "here is how we find out in two weeks", and puts the constraints in the written note where they can be read rather than argued with.

What the interviewer is really probing. Whether you can disagree upward without either capitulating or blocking, and whether you can separate a genuine capability from its operational prerequisites. The signal: you converted a bad plan into a cheap experiment, you were precise about what is actually easy versus hard, and the stakeholder got something. The classic failure is a story where you were right and the executive was foolish. The second is capitulation dressed as pragmatism — "we made it work" — with the cost paid quietly by the team.

(d) Follow-up drill chain

Why was the database version the hard blocker rather than something you could work around?

Because the vector data type and VECTOR_DISTANCE() are server-side features — they exist in Azure SQL Database and SQL Server 2025 and simply are not present in 2019, so there is no client-side compatibility shim EF could provide. The workarounds are all architectural rather than incremental: a separate vector store alongside the relational database, which means a second system to operate and a consistency problem between them; or computing distances in the application, which is untenable at 2.3 million documents. So the choice was a platform upgrade or a new piece of infrastructure, and the upgrade was already on the roadmap. That is the distinction I would draw in an interview: some constraints are cost, and some are capability, and treating the second as the first is how six-week estimates happen.

What if the executive had insisted on the six weeks anyway?

Then I would have delivered the honest six-week version and named it as such: semantic search over a subset, on a spike instance, not production, clearly labelled as a prototype, with the production path costed separately. What I would not do is attempt the full scope and let quality absorb the difference, because the failure lands on the team and on the customers rather than on the decision. I would also put the risk in writing to my own manager, briefly, so the commitment and its conditions are on record — not as defensiveness, but because a verbal caveat in a meeting has a half-life of about a week. If it were genuinely non-negotiable I would ask what to stop doing, since capacity is the constraint being ignored.

At what corpus size does the naive vector approach stop working?

The straightforward ORDER BY VECTOR_DISTANCE(...) is an exact search, so it scans every candidate row and the cost grows linearly — fine for tens of thousands of documents, slow at a few hundred thousand, unusable at millions unless you pre-filter hard. That is exactly what approximate nearest-neighbour indexes exist for, and it is where the roadmap matters: SQL Server 2025 DiskANN vector indexes with a VectorSearch() translation are in the EF Core 11 previews rather than in EF 10, so on EF 10 today the honest answer is that large corpora need either aggressive pre-filtering on a relational predicate or a dedicated vector index. I would design the pre-filter in from the start — tenant, document type, date range — because it is both a relevance improvement and the thing that keeps the scan bounded.

What did the two-week spike cost you?

Two engineers for two weeks, a provisioned Azure SQL instance for the duration, and embedding-generation spend on 50,000 documents — small, but not nothing, and it came out of a team that had committed work in that sprint, so something slipped by a week and I had to own that with a different stakeholder. The subtler cost is that a good demo creates expectation: once the executive had seen it working, "seven months" was a harder sell than it would have been before, and I spent two further conversations re-explaining the difference between a subset on a spike instance and a production rollout. I would still spike, but I would put the production caveat in the demo itself, on the screen, rather than saying it out loud.

How did you avoid making him look wrong in front of his peers?

By giving him the true part of his claim, loudly and first. The premise that EF Core 10 makes the query side trivial is correct, and I said so in the meeting and in the note — the disagreement was about everything around it, which is a much easier position for someone to accept than "your understanding is wrong". I also framed the constraints as the platform's rather than the request's: we are on SQL Server 2019, and that is a fact about us, not a judgment about him. And the spike gave him a demo to show his board, which meant the outcome of the disagreement was that he got something earlier. At principal level, the skill being assessed is whether disagreement costs you access to the person, and it did not.

What EF Core 11 features would change this answer?

The vector story is the area moving fastest. The EF Core 11 previews add SQL Server DiskANN vector index support with an approximate nearest-neighbour VectorSearch() translation, and full-text catalog and index management from the EF model — which together turn my "pre-filter hard or use a dedicated store" answer into "EF can express the whole hybrid search". Cosmos gets transactional batches by default and bulk execution, which matters if the corpus lived there instead. EF Core 11 is due November 2026 as an STS release, so for a system that just landed on EF 10 LTS I would treat those as a planned second step rather than a reason to wait — and I would say that explicitly, because "wait for the next version" is how features never ship.

21The big behavioural Q&A

21 prompts cross-cutting deploy a prepared story

These are the prompts that are not tied to one story. Each answer names which of the twenty stories to deploy and what the interviewer is listening for. The discipline is to answer the question asked and then land on a story, not to recite a story and hope it fits — and never to use the same story twice in one interview, because the second use tells the panel your history is thin.

Failure & ownership

Tell me about a time you broke production.

Deploy story 03 (the migration lock) or 12 (the soft delete). Lead with the timeline: what time, what broke, how long, how many users. The interviewer wants incident behaviour, not the bug — so weight it towards what you did in the first ten minutes, why you chose a reversible action, and how you communicated. Land on a systemic control, not a promise: migrations out of app startup, an anomaly alert on row-count deltas. If you approved the pull request, say so before they ask; volunteering that is worth more than any amount of technical detail.

Tell me about your biggest professional failure.

Deploy story 15 (the cancelled read model). The structure that works: what you believed, what it cost in real numbers, what evidence changed your mind, what you did about it, and what you would need to have seen to be right. Name the sunk cost — 340 engineer-days — because a failure story with no number reads as a rehearsed humility exercise. Do not choose a failure that is secretly a strength ("I cared too much about quality"); interviewers at lead level have heard it and it wastes the one question where honesty is genuinely rewarded.

Tell me about a time you were wrong about a technical decision.

Deploy story 05 (the tracking argument, where the colleague was partly right) or 15. The strongest form has a measurement changing your mind, not a person's authority. Say what you predicted, what the number was, and what you shipped. Follow it with the durable change — a rule in CONTRIBUTING.md, a benchmark in the repo — because "I learned to be humble" is not an outcome.

Tell me about a time you missed a deadline.

Deploy story 04 (the migration programme's month-nine incident) or an honest slip from your own history. Do not use 11 — that is a story about making a deadline by trading scope, and using it here reads as dodging. What the interviewer wants: when you knew, who you told, how early, and what you offered instead. The failure mode they are screening for is the engineer who reports green until the week before.

Conflict & influence

Tell me about a technical disagreement with a peer.

Deploy story 05 (AsNoTracking) or 02 (the repository debate). State their position first and state it fairly — an interviewer's main filter here is whether the other person sounds like a real engineer or a strawman. Land on what you conceded: the transaction boundary in story 02, the export benchmark in story 05. Ending with "and they came round" is weaker than ending with a design that contains both positions.

Tell me about a time you disagreed with your manager or an executive.

Deploy story 20 (vector search in six weeks). The pattern that lands: acknowledge the true part of their premise loudly and first, put the constraints in writing rather than in the room, and replace the yes/no with a cheap way to find out. Have the ending ready: they got a demo five weeks earlier than the original plan would have allowed. If they push, be ready to say what you would have done had he insisted — deliver the honest six-week version, labelled, with the risk on record.

How do you handle a code review where you and the author cannot agree?

Draw on stories 05 and 12. The answer they want is a decision procedure, not a personality: try to make the disagreement empirical (a benchmark, a query plan, a defect count); if it stays a matter of judgment, name the cost of each option and let the person who owns the consequence decide; escalate on principle only for correctness, security or data loss. Say plainly that you have approved things you disagreed with, and what your bar for blocking is — mine is data loss, security, or an irreversible decision.

Tell me about a time you influenced people you had no authority over.

Deploy story 14 (two teams, one schema) or 17 (CI checks). The mechanism matters more than the outcome: in 14 it was writing options with costs and asking for a decision rather than agreement, and preserving the dissenting position as a written trigger; in 17 it was fixing every existing violation before making the check blocking. Both are transferable techniques, which is what an interviewer can actually use to predict your behaviour.

Leadership, mentoring & team

Tell me about someone you helped grow.

Deploy story 10 (the change tracker). Lead with the diagnosis — the wrong belief, not the wrong code — then the teaching method you chose and why, then what they went on to own without you. The transfer test is the whole answer: she wrote the document new joiners still use and led the concurrency-token rollout. Avoid describing pull-request review as mentoring.

How do you onboard someone onto a codebase with heavy ORM usage?

Draw on stories 10, 17 and 19. A concrete answer beats a philosophy: give them the change-tracker debug view exercise on day two; have them read the generated SQL for the three busiest endpoints; point them at the model convention tests as the written-down rules; make their first task a real migration so they meet the pipeline early. Name the one concept you insist they understand before merging anything — for me, that saving is a diff against a snapshot, not a command.

Tell me about a time you had to raise the bar on a team's engineering practice.

Deploy story 17 (CI checks) or 19 (real databases in tests). The rollout is the story: warn, publish counts, fix the backlog yourself, then block — plus an escape hatch with a required reason. Have the failure ready too: the assertions you introduced too tightly and the credibility it cost. Interviewers discount improvement stories that contain no friction.

How do you decide what your team should work on when everything is urgent?

Draw on stories 16 and 15. The answer is a method: measure before choosing (the 61% of database CPU spent on data nobody displayed), prefer the cheapest experiment that would falsify your assumption, and be willing to stop your own project. Give a concrete example of something you deprioritised and were later shown to be right or wrong about — the willingness to name the miss is what makes the method credible.

Ambiguity & prioritisation

Tell me about a time requirements changed late.

Deploy story 13 (database per tenant). What they are listening for is whether you over-engineered in advance or panicked afterwards — the good answer is neither: you kept optionality cheap and paid for it when someone asked. Land on the reflective point: record decisions with their reopening conditions, not just their conclusions. That single sentence is often the thing an interviewer writes down.

Tell me about a time you had to ship with incomplete information.

Deploy story 11 (the report) or 20 (the spike). The shape: what you did not know, the cheapest thing you could do to reduce the uncertainty, the decision you made anyway, and the reversibility you preserved. Naming what would have made you change course — an expiry review, a spike result — is what distinguishes a decision from a guess.

How do you balance technical debt against feature delivery?

Deploy story 09 (owned entities to complex types) and reference 14. Argue in defects and delivery time, never in aesthetics: four production bugs in a year traced to one modelling decision, 900 lines of workaround deleted, a batch job from 40 minutes to 11 seconds. Then the honest scoping lesson — bundling low-risk and high-risk work into one approval makes the whole thing look as risky as its worst part.

Tell me about a trade-off you made that you would make differently now.

Deploy story 11 (the view that is still in production) or 07 (moving the payment call outside the transaction). Both are genuinely two-sided, which is what makes them good answers. The mark of seniority is being able to state the conditions under which the other choice becomes correct — for the view, the moment anyone needs to filter on a column it does not expose.

Craft & technical judgment

How do you approach a performance problem you have never seen before?

Deploy story 01 (N+1) or 16 (the SQL bill). The method is the answer: measure the system before the method before the line; with an ORM, always read the generated SQL before reading the C#, because they are two different artefacts and only one of them is what the database did. Quote the tools by name — command logging, ToQueryString(), Query Store, wait statistics — and give one before/after pair.

What is the hardest bug you have debugged?

Deploy story 06 (the duplicated row) or 18 (deadlocks). Include the wrong hypotheses; they are the substance. Finish with the technique that made it reproducible — running the query in a loop against restored data — because that generalises and a root cause does not.

How do you decide when to drop out of the ORM into SQL?

Deploy story 11 and reference 08. The criteria: the query does not translate; the shape is set-based and loading entities is the cost; a DBA owns the object; or you need a database feature EF does not express. The discipline that goes with it: every raw call carries a comment saying why LINQ was insufficient, values are always parameters, and identifiers are never interpolated. Mentioning EF Core 10's concatenation analyser here shows you keep current.

Values & motivation

Why do you enjoy working on data-access and persistence problems?

No single story — but ground it in one. The honest version for most people: this is the layer where correctness, performance and cost all meet, where a small decision has a measurable effect in three dimensions, and where the failure modes are visible and diagnosable. Pick the story that best shows what you actually enjoy — 16 if it is the systems-thinking, 06 if it is the puzzle, 10 if it is the teaching — and be specific about the moment, not the category.

What would you change about how your last team worked with the database?

Draw on 17, 19 and 03. Answer with one thing, not five: for most teams it is that migrations are production changes and are treated as code. Say what you would do in the first month — generated SQL attached to every migration PR, has-pending-model-changes in CI, migrations out of application startup — and what you would leave alone, because a lead who changes everything in month one is a risk the interviewer is explicitly screening for.

22Night-before cheat sheet

10 sentences say them out loud

Ten speakable sentences. Read them aloud once tonight and once in the car. They are about delivery, which is the half most technically strong candidates lose points on.

  1. Lead with the situation in one line, then stop. "An order-history screen took 90 milliseconds in dev and four and a half seconds for our biggest customer." One sentence of context buys you sixty seconds of undivided attention; three sentences of preamble spends it.
  2. Quantify the result before you explain the method. Round trips from 1,401 to 1. Twenty-two minutes of write downtime. Fifty-eight per cent less database CPU. If you have no number, say what changed for a person — the support queue emptied, the DBA stopped paging you.
  3. With an ORM, always say what the database actually did. The code you wrote and the SQL that ran are two different artefacts; naming the generated statement, the plan or the lock is what separates a candidate who uses EF from one who understands it.
  4. Separate "I" from "we" without being told to. "The DBA found the deadlock graph; I traced it to our save ordering and wrote the fix." Interviewers are trained to probe this, and volunteering it converts a suspicion into a point in your favour.
  5. Own the "what I'd do differently" as a decision, not a personality trait. "I read C# for an afternoon before I read SQL" is useful. "I'm too much of a perfectionist" is a red flag with a bow on it.
  6. Name the trade-off out loud before they ask. Every choice cost something: projections cost reuse, split queries cost consistency, JSON columns cost referential integrity, moving a call outside a transaction costs atomicity. Saying it first signals judgment; being caught by it signals luck.
  7. Label the version. "That was on EF Core 6, and I would do it differently on 10 because complex types now support JSON and ExecuteUpdate." Version-aware answers are the cheapest available proof that you are current rather than remembering.
  8. Have one very recent fact ready and deploy it once. EF Core 10 changed the default translation of Contains back to padded scalar parameters so the optimiser can see cardinality; EF Core 10 is LTS to November 2028; EF6 is security-fix-only. One is impressive, three in a row is a recital.
  9. Answer the question asked, then land on the story. Do not open with "that reminds me of a time" — open with the direct answer in one sentence, then say "the clearest example was…". And never use the same story twice in one loop.
  10. When you do not know, say the boundary and then reason. "I have not run EF against Cosmos in production, so let me reason from the relational case and tell you where I would expect it to differ." Interviewers grade calibration, and a confident wrong answer costs more than an honest "I would have to measure that".
