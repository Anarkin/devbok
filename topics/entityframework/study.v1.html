Entity Framework

study · EF Core 10.0.11 · released 2026-08-11

"Entity Framework" today means two things and this guide covers both, weighted towards the living one: EF Core, the cross-platform O/RM that all new work uses, and EF6.x, the .NET Framework-era original that is in maintenance mode and still runs a large amount of production code. EF Core 10 (EF10) shipped on 11 November 2025 alongside .NET 10 as an LTS release, supported to 10 November 2028; 10.0.11 (11 August 2026) is the current patch, and EF Core 11 is at RC1 — published 8 September 2026 — for a November 2026 GA on .NET 11. EF10's headline changes are the ones that show up in interviews now: LeftJoin/RightJoin as first-class LINQ, a new default translation for parameterized collections (multiple scalar parameters instead of an OPENJSON array), complex types mapped to JSON as the recommended replacement for owned entity types, named query filters, SQL Server 2025's native json and vector types, and log redaction of inlined constants. The centre of gravity has moved: EF is no longer just "LINQ to tables" but a document-and-vector-capable mapper, while the hard parts of the job — change tracking, loading strategy, migrations in a team, and knowing when to drop to SQL — have not changed at all. EF6.5.2 (April 2026) added .NET 10 compatibility and is security-fix-only; there is no migration path that is just a package upgrade.

01 The landscape: EF Core vs EF6

Docs: EF Core and EF6 — choosing and comparing · EF Core releases and planning

An O/RM exists to solve one problem: the impedance mismatch between a relational store (sets, rows, foreign keys, no identity beyond the key) and an object graph (references, inheritance, encapsulated behaviour, reference identity). Every design decision in EF falls out of how it chose to solve that. EF's answer has three moving parts, and if you can name them you can reason about almost any EF question without having memorised it: a model (metadata describing how CLR types map to database objects), a query pipeline (LINQ expression trees translated to SQL), and a change tracker (an in-memory unit of work that turns object mutations into INSERT/UPDATE/DELETE at SaveChanges time). Units 02–05 are those three parts; everything after is what happens when you take them to production.

The name is overloaded and interviewers do use it loosely, so be explicit about which line you mean. EF6.x (originally shipped 2008 as "Entity Framework" on .NET Framework, open-sourced 2014) is the original: it has an EDMX designer, Database-First and Model-First workflows, an ObjectContext underneath, and System.Data.Entity namespaces. EF Core is a from-scratch rewrite first released in 2016, in Microsoft.EntityFrameworkCore, code-first only, provider-pluggable, and the only line receiving features. They share concepts and almost no code. "Migrating" from EF6 to EF Core is a port, not an upgrade: Microsoft's own guidance says to expect real work, and the EDMX designer has no EF Core equivalent at all.

The provider model, and why it leaks

EF Core is a framework, not a database library. The core (Microsoft.EntityFrameworkCore) owns the model, change tracker and LINQ pipeline; a provider owns SQL generation, type mapping and migration operations. First-party providers: SQL Server / Azure SQL, SQLite, Azure Cosmos DB for NoSQL, and the in-memory provider (for internal testing — the docs explicitly discourage it, see unit 12). The most important third-party provider by a distance is Npgsql for PostgreSQL, which is community-maintained, feature-rich, and typically ships a matching major within weeks of EF's GA; Pomelo for MySQL and Oracle's own provider round out the common set.

The provider boundary leaks in exactly the way you would expect: capabilities differ. ExecuteUpdate maps to UPDATE ... FROM on SQL Server but not everywhere; SQL Server 2025's json and vector types exist only there; Cosmos has no joins and no transactions across partitions; SQLite has no real decimal and only recently learned ordered group_concat. A senior answer to "is EF database-agnostic?" is: the model and the LINQ are portable, the performance characteristics and the last 10% of features are not, and the migrations are definitively not.

Interview trap — "EF Core is just EF6 for .NET Core"

It is the wrong mental model and it produces wrong answers all through the interview. EF Core dropped EDMX, ObjectContext, the metadata workspace, automatic migrations, entity SQL, and — the one that bites hardest — silent client evaluation. It also has different defaults: no lazy loading, no Include of everything, explicit transactions behave differently under retrying execution strategies. Conversely EF Core added things EF6 never had: ExecuteUpdate/ExecuteDelete, split queries, owned and complex types, JSON columns, compiled models, query filters, interceptors. The useful framing to say out loud: EF6 is a supported legacy asset; EF Core is the product.

Gotcha — the "which version am I on" tell

Read the generated SQL, not the csproj. If parameters look like @__city_0 you are on EF Core 9 or earlier; EF10 simplified them to @city. If an ids.Contains(...) query produces OPENJSON(@__ids_0) you are on EF Core 8–9; EF10's default emits IN (@ids1, @ids2, ...) with padding. That parameter-name change is not cosmetic — because parameter names are part of the SQL text, upgrading to EF10 invalidates essentially every cached plan on the server, so a large system should expect a compilation spike right after the deploy. That is exactly the kind of detail a principal is expected to have thought about before the change window.

Try it — see all three parts in one run

1. Create a console app on .NET 10 with the model above and SQLite. Turn on optionsBuilder.LogTo(Console.WriteLine, LogLevel.Information).EnableSensitiveDataLogging(), add a blog with two posts, save, then query it back with ids.Contains over three ids. Read every line of the log.

What you should see, and why it matters

Three distinct phases in the log: a model-building message the first time the context is used (this is what compiled models eliminate — unit 09), INSERT statements batched into one round trip with the generated keys read back, and a SELECT whose WHERE ... IN uses several scalar parameters. Add EF.Parameter(ids) and re-run to see the EF8/EF9-style single-parameter translation instead. You have now seen the model, the tracker and the query pipeline do their jobs, and you have a REPL for every later unit.

2. Break it on purpose: delete the BlogId property from Post and re-run. EF still works — it creates a shadow FK property. Now query Where(p => p.BlogId == 1) and watch it fail to compile, forcing EF.Property<int>(p, "BlogId"). That is the concrete cost of implicit shadow FKs, and it is why explicit FK properties are the house style in most teams.

What problem does an O/RM solve, and when would you not use one?

It solves the impedance mismatch — mapping rows and foreign keys onto an object graph with reference identity and behaviour — and it removes an enormous amount of boilerplate: parameterisation, materialisation, change detection, batching, transaction and connection lifetime. What it costs you is a translation layer between the code you write and the SQL that runs, which is fine until it is not. I would not use EF for a reporting or analytics path with hand-tuned SQL, for very high-throughput write paths where a bulk-copy or a stored procedure is the right tool, or for a service whose whole job is a handful of fixed queries — Dapper or raw ADO.NET is honest there. In practice the decision is not either/or: I run EF for the transactional domain model and drop to FromSql, a mapped view, or Dapper on the same connection for the queries that need it, and I say so explicitly in the design so nobody thinks the escape hatch is a defeat.

EF6 or EF Core for a new service in 2026 — and what if it has to run on .NET Framework?

EF Core, without hesitation, for anything on .NET 8 or later; EF6 is maintenance-mode and gets security fixes only. If a component genuinely must remain on .NET Framework 4.8, EF6.5 is the supported answer, and 6.5.2 from April 2026 is the patch to be on — but I would treat that as a containment decision and write down what would have to be true to move it. The interesting sub-case is a .NET Framework app that has already been ported to .NET 6+: EF6 does run there, so you can port the host without porting the data access, then move to EF Core as a second step. That two-phase approach is usually the right call because it keeps one risky change per release.

How do you decide when to move a large EF6 codebase to EF Core?

I start by asking what the move buys, because "it's newer" does not survive a budget conversation. The real drivers are: the host has to move to .NET 8+ for support or performance and the data layer is the last blocker; the app needs something EF Core has and EF6 cannot get, like bulk ExecuteUpdate, JSON columns, or a non-SQL-Server provider; or the team is paying a recurring tax on EF6's silent client evaluation. Then I scope honestly: EDMX has no equivalent and must be reverse-engineered to code-first; ObjectContext, entity SQL and automatic migrations are gone; the migration history table format differs, so you baseline rather than replay. I would do it strangler-style — new bounded contexts on EF Core against the same database, old ones untouched — rather than a big-bang rewrite, and I would insist on characterisation tests over the generated SQL for the hot queries before touching anything.

Is EF Core database-agnostic? Where does that break down?

The model and most LINQ are portable; the rest is not, and pretending otherwise is how teams get hurt. Migrations are provider-specific — the generated DDL, column types and even operation set differ, so a single migrations assembly targeting two providers requires separate migrations per provider. Type mappings differ: SQLite has no native decimal or DateTimeOffset, Cosmos has no joins or cross-partition transactions, PostgreSQL has arrays and jsonb that SQL Server models differently. Provider-specific translations like EF.Functions.VectorDistance or SQL Server temporal tables simply do not exist elsewhere. So my rule is: agnostic enough to swap SQLite in for a fast test suite only if you have proved the behaviours you rely on are shared, and otherwise pick one production database and use it properly, including its non-portable features.

What actually changed in EF Core 10 that you would call out to your team?

Five things. LeftJoin/RightJoin are first-class LINQ operators now, so the GroupJoin+SelectMany+DefaultIfEmpty incantation can be deleted. Parameterized collections default to multiple scalar parameters instead of a JSON array, which changes plans on existing queries — that is the upgrade risk, and it is tunable per query or globally. Complex types can be mapped to JSON and are now the recommended way to model value objects, replacing owned entity types. Named query filters make multi-tenancy plus soft delete finally composable. And logging redacts inlined constants by default, which is a quiet but real security improvement. I would add the parameter-name simplification to the release notes for ops, because it invalidates cached plans.

How would you plan an EF Core 8 to EF Core 10 upgrade for a system you cannot take down?

Read the breaking-changes page first and classify: the medium-impact one is that EF tooling now needs --framework on multi-targeted projects, which breaks CI silently and is a five-minute fix. Then the behavioural ones: the parameterized-collection default change, the JSON column type switch if you use UseAzureSql or compatibility level 170 (which will generate a migration altering every nvarchar(max) JSON column to json), the Application Name injection into the connection string that can split SqlClient connection pools and escalate a TransactionScope, and — for SQLite users — three high-impact DateTimeOffset/UTC changes in Microsoft.Data.Sqlite 10. I would capture the generated SQL for the top queries as a baseline, upgrade in a branch, diff the SQL, load-test the paths that use Contains over big collections, and stage the deploy knowing plan caches will be cold.

What is coming in EF Core 11, and does it change what you would build today?

EF11 is at RC1 as of today, 8 September 2026, GA in November on .NET 11 as an STS release. The parts I would actually plan around: complex types and JSON columns finally work with TPT and TPC inheritance, which removes the main reason people still use owned entities in a hierarchy; to-one join SQL got materially better — Microsoft benchmarked around 29% on a split-query scenario and 22% on a single query from pruning unnecessary joins and redundant ORDER BY columns; SqlVector columns are no longer selected into entity materialisation by default, which was worth roughly 9× locally and 22× against a remote Azure SQL in their benchmark; and migrations record the latest migration id in the model snapshot so divergent branches produce a merge conflict instead of a silent mess. Does it change today's design? Only in that I would model value objects as complex types now rather than owned types, because that is the direction the whole feature set is moving.

Why did EF Core 3.0 make untranslatable LINQ throw instead of evaluating on the client?

Because silent client evaluation is a production incident waiting to happen. In EF6 a predicate the translator did not understand was quietly executed in memory, which meant EF pulled the entire table across the wire and filtered it in the app. It works in dev with 50 rows and takes the site down with 50 million. EF Core 1.x kept the behaviour with a warning; nobody read the warning. EF Core 3.0 made it an exception for everything except the top-level projection — the final Select, where client evaluation is both intentional and safe, because the rows have already been reduced. The lesson generalises: for a framework, the right default for an operation with a catastrophic and invisible failure mode is to fail loudly at the boundary.

How does EF Core's release cadence interact with your dependency policy?

EF ships in lockstep with .NET: a major every November, LTS on even-numbered releases with three years of support, STS on odd with two. That makes the decision mechanical rather than a matter of taste. Products on a slow release train sit on LTS and skip the STS entirely — .NET 8 to .NET 10, EF Core 8 to EF Core 10. Products that ship weekly can ride STS to get features a year earlier, provided they accept an annual forced upgrade. What I insist on either way is that we never sit on an out-of-support version: EF Core 6 and 7 are already expired, and EF Core 8 and 9 both go out on 10 November 2026, which is a date that belongs on a roadmap, not in someone's head. Patches are non-negotiable: always the latest 10.0.x.

Someone proposes replacing EF with Dapper across the board for performance. How do you respond?

I ask what the measurement is. Dapper wins on raw materialisation of a known query and on cognitive simplicity, and it loses everything EF gives you for free on the write path: change tracking, batching, relationship fix-up, concurrency tokens, transactional consistency across an object graph, migrations. If the profile shows a read-heavy service dominated by a few queries, moving those reads to Dapper is a good, small, reversible change — and EF makes it easy because they can share a connection and transaction. If it is a domain-heavy write path, replacing EF means hand-writing the unit of work, which teams consistently underestimate. The response I would give in an interview is that this is a per-query decision, not an architecture-wide one, and that I would first check whether the EF slowness is actually N+1, tracking, or a missing index — because in my experience it usually is, and those are unit 09 problems, not framework problems.

02 DbContext and the model

Docs: Creating and configuring a model · DbContext lifetime, configuration and initialization

DbContext is doing four jobs at once, and most EF confusion comes from not separating them. It is (1) the model holder — the metadata built from your types, conventions and OnModelCreating; (2) a unit of work — the change tracker plus a SaveChanges that wraps everything in a transaction; (3) an identity map — at most one tracked instance per entity type and key value; and (4) a query root and connection owner. Jobs 2–4 are per-operation and cheap; job 1 is expensive and shared.

That split explains the single most important operational fact about EF: the model is built once per DbContext type and cached in the internal service provider, but a context instance is meant to be short-lived. Model building for a large model (hundreds of entity types) can cost hundreds of milliseconds to seconds on first use — that is the first-request latency spike people blame on "EF being slow" — but it happens once per process, not once per request. Everything else about a context is designed to be created and thrown away: it is not thread-safe, it accumulates tracked entities forever, and a long-lived context is a memory leak plus a stale-data machine.

"DbContext is not thread-safe" is worth being precise about, because it is the most common production bug in EF code. If you want parallel queries, you want parallel contexts, which is exactly what IDbContextFactory<T> is for.

Configuring the model: conventions, then fluent API, then annotations

public sealed class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> b)
    {
        b.ToTable("Orders", "sales");
        b.HasKey(o => o.Id);

        b.Property(o => o.Reference)
            .HasMaxLength(32)
            .IsRequired()
            .IsUnicode(false);                         // varchar(32), not nvarchar(32)

        b.Property(o => o.Status)
            .HasConversion<string>()                    // enum stored as text, not int
            .HasMaxLength(24);

        b.Property(o => o.Total)
            .HasPrecision(18, 2);                      // never leave money on the default

        b.HasIndex(o => o.Reference).IsUnique();
        b.HasIndex(o => new { o.CustomerId, o.PlacedAt })
            .HasDatabaseName("IX_Orders_Customer_PlacedAt");

        b.Property(o => o.RowVersion).IsRowVersion();   // optimistic concurrency, unit 08

        // EF10: name the default constraint instead of letting SQL Server invent DF__Orders__...
        b.Property(o => o.PlacedAt).HasDefaultValueSql("SYSUTCDATETIME()", "DF_Orders_PlacedAt");
    }
}

protected override void OnModelCreating(ModelBuilder modelBuilder)
    => modelBuilder.ApplyConfigurationsFromAssembly(typeof(BloggingContext).Assembly);

Three layers decide the final model, in increasing precedence: conventions (a property called Id or <Type>Id is the key; a reference navigation plus a matching FK property builds a relationship; string becomes nvarchar(max)), data annotations ([Required], [MaxLength], [Table]), and the fluent API in OnModelCreating, which wins. The house style that scales is: fluent API in IEntityTypeConfiguration<T> classes, one per aggregate, discovered with ApplyConfigurationsFromAssembly. It keeps persistence concerns out of domain types — which matters if the domain assembly is meant to be persistence-ignorant — and it keeps OnModelCreating from becoming a 2000-line file. Annotations are fine for a small app and for things that genuinely are domain invariants ([MaxLength] on a name), but they cannot express relationships, indexes with filters, or conversions with comparers.

Since EF Core 6 you can also write your own model-building conventions (and since EF Core 9 they are considerably more extensible), which is the right answer when you find yourself repeating configuration for every entity — "all decimal properties are (18,2)", "all string properties default to 256 unless told otherwise", "every entity implementing IAuditable gets these four columns".

// Bulk configuration that beats copy-paste: applied to the whole model, once.
protected override void ConfigureConventions(ModelConfigurationBuilder builder)
{
    builder.Properties<decimal>().HavePrecision(18, 2);
    builder.Properties<string>().HaveMaxLength(256);
    builder.Properties<DateOnly>().HaveConversion<DateOnlyConverter>();   // only if the provider needs it
}

Interview trap — "make DbContext a singleton, it's faster"

It is the fastest way to break a service. Three failure modes, and you should be able to name all three: thread safety (concurrent operations throw, and worse, sometimes corrupt the tracker instead of throwing), unbounded growth (every entity ever loaded stays tracked; memory climbs until the process dies), and staleness (the identity map returns the instance you loaded an hour ago, so another process's update is invisible and you write over it). The performance intuition behind the suggestion is not crazy — context creation used to be blamed for the model build — but the correct fix is the model cache (which already exists), AddDbContextPool, or a compiled model. Scoped per request, or explicitly created and disposed per unit of work.

Gotcha — DbContext pooling and captured state

AddDbContextPool reuses the context instance, resetting only EF's own state. Any field you added to your context class survives into the next request. The classic incident: a context with a private readonly Guid _tenantId set from an injected ITenantAccessor in the constructor — with pooling, the constructor does not run again, so request two silently inherits request one's tenant and a global query filter happily serves the wrong customer's data. If you need per-request state in a pooled context, the supported route is to inject it through the pooled factory's DbContextOptions or to read it lazily through a scoped service resolved per call, never to capture it in a field. This is a data-isolation bug, so treat it as a security review item, not a style one.

Try it — prove the identity map and the pooling trap

1. In one context, load an entity, then load it again with a different query that returns the same row but different columns via a tracked query. Compare with ReferenceEquals. Then change a property on the first reference and re-query — observe that the tracked instance wins and the database value is discarded on materialisation.

Expected outcome

ReferenceEquals is true: the identity map returned the same object, and EF did not overwrite your local modifications with the freshly-read row (default QueryTrackingBehavior plus ChangeTrackerBehavior keep client values). This is the mechanism behind "my query returns stale data" bug reports. The cures are a fresh context, AsNoTracking(), or an explicit entry.Reload().

2. Register a context with AddDbContextPool, add a public Guid InstanceId { get; } = Guid.NewGuid(); field to it, and log it per request. Hit the endpoint repeatedly.

Solution sketch

Ids repeat across requests once the pool warms up — that is the whole hazard in one line. Now imagine that field held a tenant id. Fix by moving the value out of a field: resolve it per operation, or pass it via DbContextOptions from a pooled factory, and add a test that asserts two sequential requests with different tenants see different data.

What is the correct DbContext lifetime, and why?

Scoped to a unit of work — in ASP.NET Core, per request, which is what AddDbContext gives you. The reasons are that a context is not thread-safe, it accumulates tracked state without bound, and its identity map makes long-lived instances serve stale data. The counter-pressure is that creating one has a cost, but that cost is small: the expensive part, model building, is cached per context type for the life of the process. Where a request is not the right boundary — Blazor Server, where the circuit lives for minutes, or a background worker processing a queue — I use IDbContextFactory<T> and create a context per message or per operation. And if throughput genuinely warrants it, AddDbContextPool reuses instances, with the caveat that any state I put in my own context fields survives between users.

Fluent API or data annotations? Defend your choice.

Fluent API in IEntityTypeConfiguration<T> classes, applied with ApplyConfigurationsFromAssembly, for anything that is a persistence concern; annotations only where the constraint is genuinely a property of the domain type. Three reasons. It is strictly more expressive — relationships, composite keys, filtered and included indexes, value converters with comparers, query filters, table splitting all have no annotation form. It keeps the domain assembly free of an EF dependency, which matters if you care about testability or a clean architecture boundary. And it scales organisationally: one file per aggregate is reviewable and merges cleanly, whereas a monolithic OnModelCreating is a permanent merge conflict. Where I do accept annotations is [MaxLength], [Required] and [ComplexType] on types that are already EF-aware, and in small services where a second file per entity is real overhead for no benefit.

What is a shadow property and when would you use one?

A property that exists in the EF model and the database but not on the CLR type; you read and write it with EF.Property<T>(entity, "Name") or through the EntityEntry. EF creates them implicitly for foreign keys you did not declare, and for the discriminator in a TPH hierarchy. I use them deliberately for infrastructure columns the domain has no business knowing about — CreatedAt, LastModifiedBy, a tenant id — set in a SaveChanges interceptor. The trade-off is real: shadow properties cannot be used in a compiled LINQ predicate naturally, they are invisible to anyone reading the class, and querying on them is stringly-typed. So my rule is that anything the application logic branches on should be a real property; anything only infrastructure touches can be a shadow property.

A value object stored via a value converter isn't detecting changes. Diagnose it.

Almost certainly a missing ValueComparer on a mutable type. EF detects changes by comparing the current value with a snapshot taken at materialisation. For value-converted properties EF cannot infer how to compare or how to snapshot, so for reference types it defaults to reference equality and a shallow copy. If your property is a List<string> or a mutable class, mutating it in place leaves the snapshot pointing at the same object, so old and new compare equal and no UPDATE is generated. The fix is to supply a ValueComparer with an equality function, a hash function, and — crucially — a deep-copy snapshot function. The better fix is to make the value object immutable, ideally a readonly record struct, so structural equality is free and the whole class of bug disappears. This is also a good moment to say that EF10's complex types are the modern way to model this, since they have value semantics by design.

What is a compiled model and when is it worth it?

A compiled model is a code-generated version of your model metadata produced by dotnet ef dbcontext optimize, so EF skips discovering and building the model at startup. It matters at scale: with hundreds or thousands of entity types, model building can cost seconds on first use, and that lands on the first user or on a cold-started serverless instance. Since EF Core 9 it is discovered automatically if it lives in the same assembly as the context — no UseModel line — and the Microsoft.EntityFrameworkCore.Tasks MSBuild package can regenerate it on every build so it cannot go stale. The catch is exactly that staleness: a hand-run compiled model that lags the real model produces confusing failures, so if I adopt it I automate it. For a model with 20 entity types it is not worth the machinery; the honest threshold is roughly "startup time is a metric someone complains about".

How do you keep a large model's configuration maintainable across a big team?

Three moves. One configuration class per aggregate root implementing IEntityTypeConfiguration<T>, discovered by assembly scan, so files map to owners and merges are local. Cross-cutting rules expressed once as bulk configuration in ConfigureConventions or a custom convention — decimal precision, string lengths, enum-to-string, UTC DateTime conversion — because those are exactly what gets forgotten on the twentieth entity and shows up as a silent decimal(18,0) truncating money. And a test that walks context.Model asserting the invariants: every decimal has explicit precision, every string has a max length, every entity has a concurrency token if it is user-editable. That last one is unglamorous and catches more real bugs than any amount of review.

Why is DbContext not thread-safe, and what does that mean in async code?

Because the change tracker, the identity map and the underlying connection are mutable state with no synchronisation, and adding locks would cost every single-threaded user. Concretely, EF detects re-entrancy and throws InvalidOperationException: A second operation was started on this context instance before a previous operation completed. In async code the bug is almost always a missing await — a fire-and-forget query — or a Task.WhenAll over several queries that all close over the same scoped context. It is worth stressing that "async" does not mean "parallel": awaiting queries sequentially on one context is completely fine and is the normal pattern. When I genuinely want parallelism, I inject IDbContextFactory<T> and give each task its own context and connection, and then I think about whether N parallel connections is actually what I want to do to the database.

Where should DbContext live in a layered or clean architecture?

In the infrastructure layer, behind whatever abstraction the team has actually agreed on — and I would push back on wrapping it in a generic repository. DbSet<T> is already a repository and DbContext is already a unit of work; a generic IRepository<T> over it usually leaks IQueryable anyway, so it buys an abstraction that does not abstract. What I do find worth it is a per-aggregate repository with intention-revealing methods — GetOrderForFulfilment(id) that knows which navigations to include — because that puts the loading strategy where it can be reviewed, which is unit 04's whole problem. If the domain assembly must be persistence-ignorant, keep the entities there without attributes and put all the mapping in configuration classes in infrastructure. And be honest in the interview that this is a trade-off with a cost: an extra layer that most teams get wrong is worse than a well-used DbContext.

How do you configure EF differently per environment without duplicating code?

Configuration goes through DbContextOptions at registration, never inside the context, so the composition root is the only place environments diverge. In practice: connection string from configuration and a secret store; EnableRetryOnFailure on for cloud SQL, with the caveat that it changes how user-initiated transactions must be written; EnableSensitiveDataLogging and EnableDetailedErrors in development only, because they put parameter values in logs; command timeout tuned per environment; and UseQuerySplittingBehavior set globally if that is the house default. I avoid OnConfiguring in application code entirely — it hides the connection string in the assembly and makes testing awkward — except in the design-time factory that the EF tools use. And I keep the design-time configuration explicit with an IDesignTimeDbContextFactory<T> so dotnet ef never accidentally boots the whole application host to find a connection string.

A team reports the first request after deploy takes 4 seconds and the rest take 20ms. What is happening and what do you do?

That is the classic EF cold-start profile, and it is usually three costs stacked: model building on first use of the context type, query compilation for each distinct LINQ query the first time it runs, and the connection pool being empty so the first connection pays the full handshake. I would confirm rather than assume, by turning on EF's model-building log message and looking at where the time actually goes. Then: generate a compiled model with dotnet ef dbcontext optimize and wire the MSBuild task so it stays current; warm the app after deploy by hitting the handful of endpoints that cover the hot queries, which compiles those queries and fills the pool; and if the app is genuinely startup-sensitive — serverless, scale-to-zero, or short-lived jobs — look at precompiled queries via dotnet ef dbcontext optimize --precompile-queries, remembering that NativeAOT and query precompilation are still flagged experimental as of EF10 and are not something I would ship to production on that basis alone.

03 Change tracking and SaveChanges

Docs: Change tracking in EF Core · Saving data

The change tracker is EF's implementation of the Unit of Work pattern, and it is the thing that separates EF from a query mapper. The contract is: load or attach objects, mutate them like normal objects, call SaveChanges once, and EF works out the minimal set of statements, orders them so foreign keys are satisfied, batches them, and wraps them in a transaction. Understanding it means understanding one data structure and one algorithm.

The data structure is the EntityEntry: for every tracked entity, EF holds the instance, its EntityState, and a snapshot of the original property values taken at materialisation or attach time. The algorithm is DetectChanges: walk every tracked entity, compare current values to the snapshot property by property, mark the differences as modified, and also discover newly-reachable entities in navigations so they get inserted too. DetectChanges runs automatically before SaveChanges and before most tracker queries — and it is O(tracked entities × properties), which is why tracking ten thousand entities to update one is a performance bug rather than merely wasteful.

The disconnected problem

Inside one context, tracking is invisible and delightful. The hard case — the one interviews are actually about — is disconnected: a web request loads an entity in request A, sends a DTO to the browser, and receives it back in request B on a brand-new context with no snapshot and no idea what changed. You have three options and each is a different trade.

// (a) Load-then-map. One extra SELECT; UPDATEs only the columns that really changed;
//     concurrency tokens work naturally; deleted-in-the-meantime is detected.
var order = await db.Orders.FindAsync(dto.Id);        // Find hits the identity map first
if (order is null) return NotFound();
order.ShippingAddress = dto.ShippingAddress;          // only touch what the DTO owns
order.Notes = dto.Notes;
await db.SaveChangesAsync();

// (b) Attach + mark modified. No SELECT; UPDATEs EVERY mapped column, which means
//     any property missing from the DTO is written as its default. Last-write-wins.
db.Update(order);                                      // == Attach + State = Modified (whole graph)
await db.SaveChangesAsync();

// (c) Attach + mark specific properties. No SELECT, surgical UPDATE, but you must
//     supply the original concurrency token yourself or you have no optimistic locking.
db.Attach(order);
db.Entry(order).Property(o => o.Notes).IsModified = true;
db.Entry(order).Property(o => o.RowVersion).OriginalValue = dto.RowVersion;
await db.SaveChangesAsync();

Option (a) is the right default in almost every web application: the extra round trip is cheap compared with getting concurrency and partial updates wrong, and it is the only one where a malicious or careless client cannot null out fields it never saw. Option (b) is what db.Update(entity) does, and it is the source of the classic bug report "saving the profile wiped the user's password hash" — because the DTO did not carry it. Option (c) is for hot paths where you have measured that the read matters.

What SaveChanges actually does

// 1. DetectChanges (unless AutoDetectChangesEnabled == false)
// 2. Validate the graph, resolve dependencies, TOPOLOGICALLY SORT the operations
//    so principals are inserted before dependents and dependents deleted first
// 3. Open a transaction if there is more than one statement and no ambient one
// 4. Batch statements into round trips (SQL Server: MERGE/multi-statement batches;
//    default MaxBatchSize is provider-chosen, tunable via UseSqlServer(o => o.MaxBatchSize(42)))
// 5. Read back store-generated values (IDENTITY, rowversion, computed columns)
// 6. Commit, then mark everything Unchanged and re-snapshot ("accept changes")

Step 6 is important and often missed: if SaveChanges throws, the tracker is left as it was — states are not reset — so a naive retry loop re-sends the same work, and a caught-and-swallowed exception leaves a context whose state no longer matches the database. That is why the standard advice after a failed SaveChanges is to discard the context, or to handle the specific exception deliberately (unit 08 covers DbUpdateConcurrencyException).

Turning tracking off, and when not to

// Read-only query: no snapshots, no identity map, no DetectChanges cost.
var rows = await db.Orders.AsNoTracking()
    .Where(o => o.PlacedAt >= from)
    .Select(o => new OrderRow(o.Id, o.Reference, o.Total))   // projection: even better
    .ToListAsync();

// Same, but keep reference identity within the result (duplicate rows -> same object).
var graph = await db.Orders.AsNoTrackingWithIdentityResolution()
    .Include(o => o.Lines).ThenInclude(l => l.Product)
    .ToListAsync();

// Global default, if your app is read-dominated:
options.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);

A projection to a DTO is automatically non-tracked for the projected shape — EF has nothing to track because the result is not an entity — so AsNoTracking() on a query that already projects to an anonymous type or record is harmless but redundant. Where AsNoTracking() earns its keep is queries that materialise entities: it removes the snapshot allocation per entity and takes those entities out of every subsequent DetectChanges sweep.

Interview trap — "AsNoTracking makes queries faster"

It makes materialisation and later tracking work cheaper; it does not change the SQL by a single character. If the query is slow because it lacks an index, joins six tables, or returns 200,000 rows, AsNoTracking will not save you — and a candidate who reaches for it first is telling you they have not profiled. The measurable win is real but bounded: fewer allocations (no snapshot per entity), no identity-map lookups, and — the one that actually shows up in flame graphs — DetectChanges no longer walking those entities on every subsequent operation on that context. Say it as: "it reduces the CPU and memory EF spends per row, not the work the database does." The second half of the trap: AsNoTracking without identity resolution returns duplicate object instances for the same row when it appears more than once in a join, which breaks code that compares by reference or mutates and expects sharing.

Gotcha — Update() is not "save my changes"

DbContext.Update(entity) attaches the whole graph and marks every entity in it Modified, which means UPDATE statements setting every mapped column, including ones the caller never populated. On an entity loaded and mutated in the same context it is pure waste — the tracker already knows. On a disconnected entity it is a data-loss weapon. It also defeats a rowversion concurrency check unless you set the original value explicitly, because the attached entity's original values are its current values. The related trap: Attach on a graph decides Added vs Unchanged per entity by whether the key is set — an entity with a zero/empty key becomes Added. That is how you get a duplicate customer inserted because a DTO round-tripped without its id.

Try it — make the tracker visible

1. Load an order with three lines in a tracking query, mutate one line's quantity, and print db.ChangeTracker.DebugView.LongView before calling SaveChanges. Then repeat with db.ChangeTracker.DetectChanges() called manually first, and with db.ChangeTracker.AutoDetectChangesEnabled = false.

Expected outcome

DebugView shows each entity, its state, and which properties are modified with original vs current values — it is the single most useful debugging tool in EF and most candidates have never used it. With auto-detect disabled and no manual DetectChanges, your mutation produces no UPDATE at all: the tracker never noticed. That is the trade you make when you disable auto-detect for a bulk loop, and why the safe version of that optimisation is to call DetectChanges once at the end.

2. Break the disconnected case on purpose: build a DTO that omits one property, map it to a fresh entity instance, call db.Update(entity), save, and inspect the row.

Solution sketch

The omitted property is now null or 0 in the database, because Update wrote every column from an object where that property was never set. Now do it the load-then-map way and confirm the UPDATE statement in the log touches only the columns you assigned. Then argue in your own words why "the API contract is a DTO, so the update must be a merge, not a replace" — that sentence is a good thing to have ready for a code-review question.

Explain what happens between mutating a property and the UPDATE hitting the database.

Nothing happens at the moment of mutation — EF has no property interception by default, it uses snapshot change tracking. When you call SaveChanges, EF first runs DetectChanges, which walks every tracked entity and compares each property's current value against the snapshot taken when the entity was materialised, marking differing properties as modified and discovering new entities reachable through navigations. Then it builds a dependency graph of the pending operations and topologically sorts them so principals are inserted before dependents and dependents deleted before principals. It opens a transaction if more than one statement is needed and there is no ambient one, batches the statements into as few round trips as the provider allows, executes them, reads back store-generated values like identity keys and rowversions, commits, and finally marks everything Unchanged and re-snapshots. The two details worth volunteering are that only changed columns appear in the UPDATE, and that if the save throws, the tracker is not reset — so a blind retry re-sends the same work.

When exactly do you use AsNoTracking, and what does it cost you?

Every read that will not be written back in the same unit of work — which in a typical web app is most of them. It removes the per-entity snapshot allocation, keeps those entities out of the identity map, and takes them out of every subsequent DetectChanges sweep, so it is a CPU and memory win that grows with result size. It costs you two things. First, the identity map: the same row appearing twice in a join materialises as two separate objects, so reference comparisons and shared mutations break — AsNoTrackingWithIdentityResolution, added in EF Core 5, gets identity back at the cost of a lookup dictionary. Second, you cannot then mutate and save without attaching, which puts you back in the disconnected problem. The nuance I would add: if the query already projects to a DTO, tracking never happened, so adding AsNoTracking there is cargo cult. And if a service is read-dominated I would rather set QueryTrackingBehavior.NoTracking globally and opt in to tracking on the write paths, because the default-safe direction is the one where forgetting has the smaller blast radius.

How do you correctly update an entity that came back from a browser as JSON?

Load it, then map onto the loaded instance, then save. That gives you three things the alternatives do not: the UPDATE contains only the columns that actually changed; the concurrency token's original value is the one from the database, so an optimistic check is meaningful when I also carry the client's token; and a row that was deleted in the meantime is detected as a missing entity rather than a silent no-op update. The cost is one extra SELECT, which is almost never the bottleneck. I explicitly avoid db.Update(dto-mapped-entity), because it marks every property modified and writes defaults over any column the DTO did not carry — that is the "saving the profile cleared the phone number" class of bug. If profiling proves the read matters, the surgical version is Attach plus setting IsModified on the specific properties and setting the concurrency token's OriginalValue from the client, but I would only reach for it with a measurement in hand.

What is DetectChanges and when is it a performance problem?

It is the sweep that makes snapshot change tracking work: for each tracked entity, compare every property to its snapshot and walk navigations to find newly-reachable entities. It runs automatically before SaveChanges and before tracker-dependent APIs like ChangeTracker.Entries() and Find. It is O(entities × properties), so it becomes a problem in exactly one shape: a loop that adds or modifies many entities on one context, where each Add triggers a full sweep and you get quadratic behaviour. The fixes in order of preference are to not track that many entities at all — use ExecuteUpdate/ExecuteDelete, or a bulk-copy library — then to batch into several contexts, and only then to set AutoDetectChangesEnabled = false around the loop and call DetectChanges() once before saving. The last one is a sharp tool: if you forget the manual call, changes are silently not saved, so I would wrap it in a small disposable helper rather than leave a bare flag toggle in business code.

Why does SaveChanges succeed but the database is unchanged?

Handful of usual suspects, in the order I would check them. The entity is not tracked at all — it came from an AsNoTracking query, or from a different context instance, so mutating it does nothing. Auto-detect changes was disabled and nobody called DetectChanges. The property is value-converted and mutable with no ValueComparer, so EF compares the snapshot reference to itself and sees no difference. The mutation happened on a copy — an AutoMapper projection or a record with expression producing a new object that is not the tracked one. Or there is an ambient TransactionScope or an explicit transaction that never got committed, in which case the write happened and was rolled back. The diagnostic that answers it in one step is db.ChangeTracker.DebugView.LongView just before the save — it shows exactly which entities are in which state and which properties EF thinks are modified.

How does EF decide the order of INSERTs, and can it fail?

It builds a graph of the pending operations from the model's foreign keys and topologically sorts it, so a principal is inserted before its dependents and dependents are deleted before their principals, with store-generated keys propagated between the statements in a batch. It fails on genuine cycles — two entities each holding a required FK to the other — and EF will tell you it cannot determine an order and suggest breaking the cycle. The practical resolutions are to make one side optional so it can be inserted null and updated in a second statement, to save in two explicit steps inside one transaction, or to reconsider the model, because a mandatory cycle is usually a modelling smell. The related surprise is that self-referencing hierarchies work fine as long as the FK is nullable, and that EF does not reorder across a batch boundary in a way that would violate a deferred constraint, which matters if you have added constraints outside EF's knowledge.

Should you call SaveChanges once per operation or several times?

Once per unit of work, because that is what gives you atomicity for free — EF wraps a multi-statement save in a transaction, so either the whole graph lands or none of it does. Calling it in a loop turns one transaction into N and turns one round trip into N, and it also loses you the guarantee that the aggregate is consistent. The cases where I deliberately call it more than once are when I need a store-generated key before I can build the next part of the graph and the relationship is not something EF can propagate, or when a very large operation would otherwise hold locks too long and I have consciously chosen chunking with idempotent retry semantics. In both cases I take an explicit transaction with BeginTransaction so the several saves are still atomic — and if a retrying execution strategy is enabled I do that inside strategy.ExecuteAsync, which is unit 08's trap.

What is the identity map and when does it bite you?

Within one context, EF guarantees at most one tracked instance per entity type and key, so two queries returning the same row give you the same object and relationship fix-up can wire navigations automatically. It bites in three ways. Stale data: once an entity is tracked, a later query that reads the same row does not overwrite your in-memory changes with the database values, so a long-lived context serves increasingly stale objects — the cure is a fresh context or an explicit entry.Reload(). Surprising results: a query with a Where that the tracked entity no longer satisfies still returns the tracked instance if the database row still matches, so filtering feels inconsistent. And memory: everything ever loaded stays reachable. It also has a pleasant side: Find/FindAsync checks the identity map first and can return without touching the database, which is a genuine optimisation on hot lookup paths.

How does batching work in SaveChanges, and how would you tune it?

EF groups the statements it needs into as few round trips as the provider supports — on SQL Server that means multi-statement batches with output clauses to read back generated values, and there is a threshold below which batching is not worth the parameter overhead. You can tune the ceiling with UseSqlServer(o => o.MaxBatchSize(n)), and the reasons to lower it are real: SQL Server has a 2100-parameter limit per command, very large batches can produce plan-cache pressure and long-running implicit transactions, and some proxies and connection poolers behave badly with huge commands. The reasons to raise it are round-trip-dominated workloads over high-latency links. I would tune it only with a measurement, because the default is sensible and the failure mode of a too-large batch — parameter limit errors under a specific data shape — shows up in production and not in tests. If I find myself wanting a batch size in the thousands, that is the signal that SaveChanges is the wrong tool and I should be using ExecuteUpdate, a bulk copy, or a set-based statement.

What is your rule for entity design so change tracking behaves?

Entities that EF can construct and mutate, with the mutability confined to the aggregate. Concretely: a parameterless or EF-usable constructor and settable properties for anything mapped — EF supports constructor binding and backing fields, but fighting it costs more than it saves; explicit foreign key properties alongside navigations, so I can set a relationship without loading the principal and can query on it in a compiled predicate; collections exposed as IReadOnlyCollection over a private backing field so callers go through domain methods rather than mutating the list EF is tracking; no lazy-loading virtual keywords unless we have deliberately enabled proxies. Value objects as immutable types mapped as complex types, which is EF10's answer and avoids the mutable-value-converter comparer trap entirely. And a concurrency token on anything a user can edit, because retrofitting one after the first lost update is much more expensive than adding it on day one.

04 Relationships and loading

Docs: Loading related data · Single vs. split queries

A relationship in EF is four things that must agree: a principal and a dependent, a foreign key on the dependent, one or two navigations, and a delete behaviour. Conventions will infer all of it from a Blog Blog navigation plus a BlogId property, and that is fine for simple models; the fluent API exists for the cases conventions cannot see — composite keys, alternate-key relationships, two relationships between the same pair of types, or navigations named nothing like the type.

b.HasOne(p => p.Blog)                  // dependent -> principal
 .WithMany(bl => bl.Posts)             // principal -> dependents
 .HasForeignKey(p => p.BlogId)
 .HasPrincipalKey(bl => bl.Id)         // only needed for an alternate key
 .OnDelete(DeleteBehavior.Restrict);   // see the table below

// Many-to-many with no join entity in your model (EF Core 5+):
b.HasMany(p => p.Tags).WithMany(t => t.Posts)
 .UsingEntity<PostTag>(                // ...unless you need payload on the join
    j => j.HasOne(pt => pt.Tag).WithMany().HasForeignKey(pt => pt.TagId),
    j => j.HasOne(pt => pt.Post).WithMany().HasForeignKey(pt => pt.PostId),
    j => j.Property(pt => pt.TaggedAt).HasDefaultValueSql("SYSUTCDATETIME()"));

Required vs optional is decided by the nullability of the foreign key, not by the navigation. int BlogId is required; int? BlogId is optional. This is the single most common source of "EF generated a nullable column I didn't want" and, with nullable reference types enabled, of the opposite surprise: Blog Blog (non-nullable reference) makes the relationship required, so removing a post from a blog's collection tries to delete the post rather than null out the FK.

The three loading strategies

// EAGER — one query (or one per Include with AsSplitQuery), decided at the call site.
var orders = await db.Orders
    .Include(o => o.Lines).ThenInclude(l => l.Product)
    .Include(o => o.Customer)
    .Where(o => o.PlacedAt >= from)
    .ToListAsync();

// FILTERED INCLUDE (EF Core 5+): the only operators allowed are
// Where / OrderBy / OrderByDescending / ThenBy / Skip / Take.
.Include(o => o.Lines.Where(l => !l.Cancelled).OrderBy(l => l.LineNumber).Take(20))

// EXPLICIT — you decide, per entity, after the fact. Costs one query each.
await db.Entry(order).Collection(o => o.Lines).LoadAsync();
await db.Entry(order).Reference(o => o.Customer).LoadAsync();
var openLines = await db.Entry(order).Collection(o => o.Lines)
    .Query().Where(l => !l.Cancelled).ToListAsync();   // compose before loading

// LAZY — opt-in, and the reason most N+1 bugs exist.
// dotnet add package Microsoft.EntityFrameworkCore.Proxies
options.UseLazyLoadingProxies();                        // + every navigation must be `virtual`

Cartesian explosion and split queries

Eager loading two collection navigations in one query means a join whose row count is the product of the collection sizes: an order with 50 lines and 20 shipments produces 1000 rows, each repeating the order's own columns. EF materialises it correctly, but you have moved megabytes to move kilobytes. This is cartesian explosion, and it is the most common cause of "EF is slow" in reviewable code.

// One query per collection instead of one exploded join (EF Core 5+).
var orders = await db.Orders
    .Include(o => o.Lines)
    .Include(o => o.Shipments)
    .AsSplitQuery()                       // or globally: UseQuerySplittingBehavior(SplitQuery)
    .ToListAsync();

The trade-off is precise and you should be able to state it: split queries fix the row explosion at the cost of N+1 round trips and no cross-query consistency unless you wrap them in a serializable/snapshot transaction — between the two SELECTs another transaction can commit. EF Core 10 fixed a long-standing correctness wrinkle here: the subquery that limits the parent rows now carries the same complete ORDER BY as the outer query, so a Take plus a non-unique sort no longer risks the two queries disagreeing about which parents they mean.

Interview trap — lazy loading is not a convenience, it's an N+1 generator

EF Core made it opt-in for a reason. With proxies enabled, foreach (var o in orders) Console.WriteLine(o.Customer.Name); issues one query per order, silently, from inside a template or a mapper where nobody is looking for database access. Worse, it is synchronous only — there is no async lazy load — so on a web server every lazy load blocks a thread-pool thread, and under load that becomes thread starvation rather than merely slow queries. Worse still, it does not work at all on a disposed context, so the same code that works in a controller throws ObjectDisposedException when the serializer touches the navigation after the response has started. My position in a review: lazy loading is acceptable in a desktop app or a script; in a server application it is a defect, and the fix is an explicit Include or a projection.

Gotcha — Include is not a filter, and Select beats both

Two mistakes live here. First, Include(o => o.Lines).Where(o => o.Lines.Any(l => l.Cancelled)) filters the orders, not the loaded lines: you get matching orders with all their lines. Filtering inside the navigation requires a filtered Include. Second — and this is the one that separates levels — Include pulls every mapped column of every included entity. If the endpoint returns five fields, a projection with Select is strictly better: it emits exactly the needed columns, needs no Include at all (EF infers the joins from the navigations you touch in the projection), produces no tracking, and cannot explode cartesianly on to-one navigations. The rule I give teams: Include for write paths where you need the real entities, Select for read paths.

Try it — watch the explosion and the N+1

1. Seed 10 orders, each with 30 lines and 10 shipments. Query with two Includes and log the SQL plus ToList().Count of the raw reader (use a DbCommandInterceptor, or just count rows in SSMS with the captured SQL). Then add AsSplitQuery() and compare.

Expected outcome

Single query: 10 × 30 × 10 = 3000 rows returned to materialise 10 orders, 300 lines and 100 shipments — order columns repeated 300 times each. Split: three queries returning 10, 300 and 100 rows. The bytes-on-the-wire difference is the whole lesson, and it grows multiplicatively with each added collection Include. Now measure with the collections at size 2 and see split queries lose, because three round trips cost more than a small join — which is why this is a per-query decision and not a global setting you set and forget.

Solution sketch

N+1 queries, all synchronous, and after disposal an ObjectDisposedException from inside what looks like plain property access. Then rewrite the loop as a projection selecting o.Customer.Name directly and confirm one query with a single LEFT JOIN. Keep this example — "one query, correct columns, no proxies" is the answer to a lot of interview questions.

Compare eager, explicit and lazy loading. Which do you default to?

Eager, expressed as a projection wherever the path is read-only. Eager loading with Include makes the data requirement visible at the call site, which is what makes it reviewable — you can look at a method and know how many round trips it costs. Explicit loading is for the cases where you genuinely do not know until runtime whether you need the navigation, and it lets you compose a filtered query with .Query() before loading. Lazy loading I treat as a defect in server code: it hides database access inside property getters, it has no async form so it blocks threads, it produces N+1 by construction, and it fails after the context is disposed. The nuance I would add is that eager loading has its own failure mode — cartesian explosion when you include two collections — so "always eager" is not the whole answer either; the whole answer is Select for reads, Include plus a considered split/single choice for writes.

What is cartesian explosion and how do you fix it?

Including two or more collection navigations in a single query produces a join whose row count is the product of the collection sizes, with the parent's columns repeated in every row. Ten orders with 30 lines and 10 shipments is 3000 rows to carry 410 entities. EF materialises it correctly, so it is never a wrong answer — it is a bandwidth and memory problem that scales multiplicatively and therefore looks fine in test data and falls over in production. The direct fix is AsSplitQuery(), which issues one query per collection; the trade is more round trips and no consistency between them unless you are inside a snapshot or serializable transaction. The better fix for read paths is usually to project: select exactly the fields you need, optionally as nested collections in the projection, and EF generates the same split behaviour without materialising entities at all. I would not set split queries globally without thinking, because for small collections the extra round trips lose.

How do you spot and fix an N+1 in an EF codebase?

Symptomatically it is a request whose duration scales with the size of a list and whose database time is many small identical queries. I find them three ways: EF's own logging with a query counter per request, an APM trace that shows the fan-out, or — best — a test-time interceptor that fails a test if a single request issues more than N commands, which turns regressions into build failures instead of incidents. The causes are almost always one of three: lazy loading enabled and a loop touching navigations; a loop that calls await db.Something.FirstAsync(...) per item; or client-side foreach over a collection calling a method that queries. The fixes correspondingly: turn lazy loading off and add explicit Includes or a projection; replace the per-item query with one query using Where(x => ids.Contains(x.Id)) and a dictionary lookup; or push the work into the projection. I would also add that in EF10 the Contains rewrite is worth a look after this fix, because the default translation changed and large id lists behave differently than they did on EF8.

Single query or split query — how do you decide?

Per query, based on the shape. Single query is right when there is at most one collection navigation, when the collections are small, or when you need a consistent snapshot without an explicit transaction. Split query is right when you are including two or more collections, or one collection whose size multiplied by the parent's row width is large — that is the cartesian explosion case. The two costs of split are extra round trips, which matter on a high-latency link, and the loss of atomicity: between the parent query and the child query another transaction can commit, so you can observe a parent whose children have changed. If that matters, wrap both in a transaction with snapshot or serializable isolation. One EF10 detail worth knowing: split queries now emit the same complete ORDER BY in the parent subquery as in the outer query, fixing a case where a Take with a non-unique sort could silently pair the wrong children with the wrong parents.

How do you model and query many-to-many?

Since EF Core 5, if the join table has no extra data, I model it as two collection navigations and let EF create and manage the join entity implicitly — HasMany().WithMany(), and adding to the collection is enough. The moment the relationship carries payload — when it was added, by whom, an ordering, a soft-delete flag — I model the join entity explicitly, because a relationship with attributes is an entity and pretending otherwise leads to awkward workarounds later. The configuration form is UsingEntity<PostTag>(...), which lets you keep the pleasant post.Tags navigation and still configure the payload. In EF6 and EF Core 2–3 you had no choice: the implicit join was either EDMX magic or absent, so codebases from that era have explicit join entities everywhere and part of a modernisation is deciding whether to simplify them. Querying is the same either way; the thing to watch is that Include(p => p.Tags) on a many-to-many is a two-hop join and a strong candidate for a projection instead.

Explain delete behaviours and when you would change the default.

EF's default is Cascade for required relationships and ClientSetNull for optional ones, and the behaviour has two halves that people conflate: what EF does to tracked entities, and what DDL it generates for the database. Cascade both deletes loaded dependents and emits ON DELETE CASCADE. ClientSetNull nulls the FK on loaded dependents but generates NO ACTION, so an unloaded dependent produces a constraint violation at the database — which is the surprise people hit. I change the default in two situations. For anything auditable or financial I use Restrict, because a cascading delete that silently removes rows nobody intended to remove is far worse than an error; deletes there should be explicit or soft. And on SQL Server, diamond-shaped relationships trip the "multiple cascade paths" restriction, where ClientCascade lets EF do the cascade in the application while the database stays NO ACTION. Whatever I choose, I want it stated in configuration rather than inherited from a convention, because it is a data-loss decision.

What are relationship fix-up and orphan deletion?

Fix-up is EF wiring navigations automatically from the identity map: if you load a blog and then separately load its posts on the same context, blog.Posts is populated and each post.Blog points at the blog, even though neither query used Include. It is why a tracked graph feels coherent, and it is also why an AsNoTracking query without identity resolution produces a graph that looks half-wired. Orphan deletion is the flip side: for a required relationship, removing a dependent from the principal's collection — or setting its navigation to null — marks the dependent Deleted, because a required FK means it cannot exist unowned. For an optional relationship it just nulls the FK. This catches people converting a nullable navigation to non-nullable when they turn on nullable reference types: the relationship silently becomes required, and code that used to detach a child now deletes it.

When would you use a projection instead of Include, and what do you lose?

For every read path that feeds a DTO, an API response or a view — which is most of them. The projection emits exactly the columns you named, so no cartesian explosion on to-one navigations, no wasted bandwidth on nvarchar(max) columns nobody rendered, no tracking, and no need for Include at all because EF infers the joins from the navigations the projection touches. What you lose is the entity: you cannot mutate and save the result, and you cannot pass it to domain logic that expects the real type. You also lose global query filters' automatic application to manually constructed joins, and you have to be careful that the projection is translatable — calling a constructor with logic in it, or a method the translator does not know, throws or forces the client-evaluation boundary later than you expect. The practical rule: Select for reads, Include for the write path where you are going to mutate the graph.

Should navigations be virtual? What about nullable reference types?

virtual is only meaningful if you have enabled lazy-loading proxies, and since I do not enable them on servers, my navigations are not virtual — leaving them virtual is a latent trap, because someone adding the proxies package later silently turns on N+1 everywhere. For nullable reference types, the important thing is that EF uses the annotation: a non-nullable reference navigation or a non-nullable scalar makes the property required in the model, which changes the generated DDL and the delete behaviour. So public Blog Blog { get; set; } = null!; declares a required relationship, and public Blog? Blog { get; set; } declares an optional one; getting that wrong silently changes whether removing a child deletes it. On collections I initialise to an empty list and expose it read-only where the domain has invariants. And I would flag in review that required members and constructor binding both work in modern EF, so there is no need for the old = null!; ceremony everywhere if the type is designed for it.

A query with three Includes has become the slowest endpoint in the system. Walk me through your response.

First I look at the generated SQL and the actual row count returned, not the entity count — that immediately tells me whether this is cartesian explosion, in which case the row count is a product rather than a sum. Then I check what the endpoint actually returns: if it is a DTO with eight fields, the whole Include chain is wrong and I replace it with a projection, which usually ends the conversation. If the entities are genuinely needed, I try AsSplitQuery and measure, keeping in mind it trades bytes for round trips and consistency. Then the database side: is there an index supporting the join and the filter, is the plan doing a scan because a parameterized-collection translation changed under EF10, is the query returning far more rows than the page the UI shows. And I would look for the structural fix — pagination, a denormalised read model, or caching — because an endpoint that legitimately needs 3000 rows to answer one question is often a design problem rather than an EF problem. Throughout, I would keep the before-and-after SQL, because "we made it faster" without the SQL diff is not a reviewable claim.

05 LINQ translation

Docs: Querying data · Client vs. server evaluation

The mental model that makes every translation question answerable: IQueryable<T> is not a collection, it is an expression tree. Each operator you chain does no work; it builds a node. When you enumerate — ToListAsync, FirstAsync, foreach, CountAsync — EF takes the finished tree and runs it through a pipeline: expand navigations into joins, apply query filters, translate the tree into a provider-agnostic SqlExpression, optimise it, and let the provider render SQL. The result is cached against a key derived from the tree's shape, so the second execution of the same query with different parameter values skips compilation.

That caching detail is the source of a real production hazard: anything that changes the shape creates a new cache entry. Constants inlined into the tree are shape; parameters are not. EF parameterises captured variables precisely to keep the shape stable, and the EF.Constant/EF.Parameter/EF.MultipleParameters family exists to let you override that decision when you know better.

Client evaluation: where the line is

// Throws (EF Core 3.0+): the predicate can't be translated, and silently pulling
// the whole table to filter in memory is a production incident, not a convenience.
db.Users.Where(u => MyHelper.IsEligible(u)).ToList();

// Legal: the FINAL projection may evaluate on the client — rows are already reduced.
db.Users
  .Where(u => u.IsActive)                       // server
  .Select(u => new { u.Id, Label = Format(u.Name) })   // client, and that's fine
  .ToList();

// Explicit boundary when you really do need client logic in a filter:
db.Users.Where(u => u.IsActive)
        .AsEnumerable()                          // "everything after this is LINQ to Objects"
        .Where(u => MyHelper.IsEligible(u))
        .ToList();

EF6 evaluated anything it could not translate on the client, silently. EF Core 1.x kept that with a warning nobody read. EF Core 3.0 made it throw, restricting client evaluation to the top-level projection. The design principle is worth stating in an interview: when an operation's failure mode is catastrophic and invisible, the framework should fail loudly at the boundary rather than degrade quietly.

Interview trap — the query cache and accidental shape explosion

EF caches the compiled plan against the expression tree's shape. Two things silently blow that cache up. First, inlined constants: Where(o => o.Status == "Shipped") uses a literal, which is deliberate and fine because there are few statuses — but building a predicate string-concatenation-style, or interpolating a value into a constant expression, produces one cache entry per value, and the cache is bounded, so you thrash it and pay compilation on every request. Second, dynamically composed queries: conditionally chaining Where clauses produces a distinct shape per combination, which is fine for three flags and pathological for ten. Symptoms are high CPU inside EF with fast database times, and a flat profile full of expression-tree work. The fix is to keep predicates parameterised, cap the combinations, and use EF.Constant only where you have decided the plan benefit outweighs the cache cost.

Gotcha — First vs Single, and where the filter goes

SingleAsync emits TOP(2) and throws if two rows come back; FirstAsync emits TOP(1) and does not. That is not a style preference: Single is an assertion that the predicate is unique, and using it on a non-unique predicate turns a data problem into a runtime exception at exactly the moment you want to know. Conversely First without an OrderBy is non-deterministic and will eventually return different rows on different plans. The related trap is putting the filter in the wrong place: db.Orders.ToList().First(o => o.Id == id) reads the whole table and filters in memory — it compiles, it passes tests with ten rows, and it is a table scan in production. Any ToList(), AsEnumerable() or ToListAsync() in the middle of a chain is a boundary marker worth a comment.

How does a LINQ query become SQL?

IQueryable operators build an expression tree rather than executing anything; the tree is only processed when you enumerate. EF then runs it through a pipeline: a preprocessing pass that expands navigation properties into joins and applies global query filters, a translation pass that turns the tree into EF's provider-agnostic SQL expression model, an optimisation pass that prunes unused projections and simplifies predicates, and finally provider-specific SQL generation. The result — the SQL plus a materialisation delegate — is cached against a key derived from the expression tree's shape, so repeated executions with different parameter values reuse it. Two consequences fall out of that and are worth volunteering: anything that changes the shape of the tree, like inlining a constant, creates a new cache entry; and anything the translator does not recognise causes a translation failure rather than silent client evaluation, since EF Core 3.0.

Why did client evaluation become an error, and how do you opt back in safely?

Because the failure mode was invisible and catastrophic. In EF6 an untranslatable predicate meant EF fetched the whole table and filtered in memory; that works in development with fifty rows and takes the system down with fifty million, and nothing in the code says so. EF Core 3.0 restricted client evaluation to the top-level projection — where it is deliberate and the rows are already reduced — and made everything else throw. To opt in intentionally I insert an explicit boundary with AsEnumerable() or AsAsyncEnumerable(), which reads as "server-side work ends here" to anyone reviewing the code, and I only do it after the Where clauses that reduce the set. The general lesson I would draw is about API design rather than EF: if an operation can silently become thousands of times more expensive, the right default is a compile-time or startup-time error, not a log warning.

What changed about parameterized collections in EF Core 10 and why should you care?

The default translation of collection.Contains(x) changed for the second time in three releases. Up to EF7 the values were inlined as constants, which gave the optimiser perfect information and polluted the plan cache with a distinct plan per distinct list. EF8 switched to a single JSON array parameter unpacked with OPENJSON, which fixed plan-cache bloat but hid the collection's cardinality from the planner, so plans tuned for three values ran for three thousand. EF10 defaults to one scalar parameter per value, padded up to the next bucket so similar lengths share a plan — the optimiser sees cardinality and the cache stays bounded. Why care: this changes the plans of existing queries on upgrade, so it is the single most likely source of a post-upgrade performance regression. It is also fully controllable, globally with UseParameterizedCollectionMode and per query with EF.Constant, EF.Parameter and EF.MultipleParameters, and for genuinely large lists none of the three is really right — a temp table or a table-valued parameter is.

When is a compiled query worth it, and what is the difference from the automatic cache?

EF already caches the translation, keyed by the expression tree's shape, so the second and subsequent executions skip compilation. What they do not skip is building and hashing the tree and looking it up — a genuine but small cost, on the order of microseconds, which only matters when the query runs at very high frequency and the database part is already trivial. EF.CompileQuery/EF.CompileAsyncQuery hands you a delegate that has that work done once, at the cost of a static field, no composability, and a fixed set of parameters. So the honest answer is: measure first, and expect it to matter on hot lookup paths in a high-throughput service and nowhere else. The related and more impactful lever is precompiled queries via dotnet ef dbcontext optimize --precompile-queries, which moves the compilation of all statically-analysable queries to build time and helps startup — though I would note it is still marked experimental as of EF Core 10, alongside NativeAOT support.

How do you build a query dynamically without wrecking the plan cache?

Conditional chaining of Where clauses is fine and idiomatic — if (filter.Status is not null) q = q.Where(...) — as long as the number of distinct combinations is bounded and small, because each combination is a distinct expression-tree shape and therefore a distinct cache entry. It goes wrong in two ways. Ten independent optional filters is 1024 shapes, which thrashes a bounded cache and puts query compilation on the hot path; the fix there is usually to accept a couple of canonical query shapes with parameters that mean "not filtered", or to accept the cost knowingly for a rarely-used admin search. The other way it goes wrong is building predicates by string concatenation or by baking values into constants, which produces a shape per value. If I genuinely need arbitrary user-driven querying, I would rather generate SQL explicitly with parameters, or use a proper search index, than pretend it is a LINQ problem. Note also that dynamically-composed queries are exactly what query precompilation cannot handle, so this choice interacts with startup optimisation.

A query works in test and throws "could not be translated" in production. How is that possible?

Most often the code path differs: a nullable value, a different overload, or a branch that only executes with production data pulls an untranslatable call into the tree — a helper method, a ToString() on a type the provider has no mapping for, a culture-sensitive string.Compare, a custom equality. It can also be a provider difference: a translation that exists for SQL Server does not exist for the SQLite you used in tests, which is one of the strongest arguments against testing on a different provider than you ship on. Occasionally it is a version difference — a translation added in a later EF version, or removed as part of a correctness fix. My response is to reproduce with the same provider, use ToQueryString() to see how far the translation gets, and then either push the logic into something translatable, precompute the value outside the tree so it becomes a parameter, or draw an explicit AsEnumerable() boundary after the filters have reduced the set.

How do nullable semantics differ between C# and SQL, and what does EF do about it?

C# uses two-valued logic and SQL uses three-valued logic, so a != b in C# is true when one side is null, while a <> b in SQL is unknown and the row is filtered out. EF's job is to preserve C# semantics, so it expands comparisons involving nullable columns into forms with explicit null handling — which is why a simple-looking Where(x => x.A != x.B) can generate a surprisingly baroque predicate with IS NULL checks and CASE expressions. EF Core 9 did significant work to simplify those expansions and to translate logical negation better, and EF Core 11 strips no-op CASTs that were preventing index usage. The practical consequences are two: the generated SQL for null-heavy predicates can be much harder for the optimiser than you expect, so it is worth looking at, and if you genuinely want SQL's semantics you should write the null check yourself rather than fight the expansion. If you want the opposite — treat null as a value — EF.Functions and explicit ?? handling are clearer than hoping.

What is EF.Functions and when do you reach for it?

It is the extension point for SQL constructs that have no LINQ equivalent, exposed as fake methods the translator recognises: EF.Functions.Like for LIKE with explicit wildcards, Collate for a per-query collation, DateDiffDay and friends, Contains/FreeText for SQL Server full-text search, VectorDistance for SQL Server 2025 and Cosmos vector search, FullTextContains and Rrf for Cosmos. They only exist inside a query — calling one in ordinary code throws — because they are translation markers, not implementations. I reach for them when the alternative is dropping to raw SQL for one predicate, and it is worth noting they are provider-specific: EF.Functions.Like lives in the relational package, but VectorDistance is SQL Server and Cosmos only, so using them is a deliberate decision to stop being portable. You can also add your own with HasDbFunction, mapping a static method to a database function, which is the clean way to expose a UDF the database team owns.

How would you enforce query quality in a large team's code review?

Mostly by not relying on review. Three mechanisms. A test-time DbCommandInterceptor that records every command a test issues, so tests can assert query counts and catch N+1 as a build failure, and so a golden-file test can pin the SQL of the ten queries that matter — then an unintended change to translation, including one caused by an EF upgrade, shows up as a diff instead of an incident. An analyzer or a convention test asserting things like "no ToList() in the middle of a chain in this assembly". And EF's own signals turned into errors in development: ConfigureWarnings can promote specific EF events to exceptions, so for example the multiple-collection-include warning or a lazy-loading event fails fast rather than being logged. On top of that I would review for the two judgment calls that tooling cannot make: whether a read path should be a projection, and whether an Include chain is a hidden cartesian explosion. That combination is far more effective than asking reviewers to imagine SQL.

What is the most valuable EF debugging technique you know?

Reading the SQL, and having a way to read it without a debugger. Concretely: ToQueryString() to see the SQL of any IQueryable without executing it, LogTo(Console.WriteLine, LogLevel.Information) to see everything that actually ran including timings, and ChangeTracker.DebugView for save-side problems. In production the equivalent is EF's DiagnosticSource and metrics feeding an APM, plus the database's own query store. The habit I try to instil is that "EF is slow" is never an acceptable diagnosis — either the SQL is wrong, in which case fix the LINQ, or the SQL is right and the database is slow, in which case it is an indexing or plan problem and EF is a bystander. A note that lands well in interviews: since EF10, logs redact constants that EF inlines into SQL, replacing them with ? unless sensitive data logging is on, so the log and the executed SQL are no longer character-identical — worth knowing before you go hunting for a discrepancy that is by design.

Composition: owned types, then complex types

An Address inside a Customer is not an entity — it has no identity of its own, two identical addresses are the same address, and it should be replaceable wholesale. EF's original answer was owned entity types (EF Core 2): entities under the hood, with an implicit key and reference semantics, mapped either into the parent's table (table splitting) or, since EF Core 7, into a JSON column. That "entities under the hood" part is exactly where they hurt.

db.Customers.Where(c => c.BillingAddress == c.ShippingAddress)   // not what you meant

Interview trap — "TPT is the clean design, so use TPT"

It is the normalised design and it is usually the wrong one. Every query against the base type joins every table in the hierarchy; a five-type hierarchy means a five-way join for db.Payments.ToList(), and inserts touch two tables per row. Microsoft's own guidance and every benchmark that has been published put TPH ahead for most workloads, and the price — nullable columns for subtype-specific data — is a data-integrity concern you can address with check constraints rather than with joins. The lead-level answer names the actual decision criteria: how wide the subtype-specific columns are, whether you query the base or the leaves, whether the schema is yours to choose, and whether integrity must be enforced by the database or can be enforced by the aggregate. And if you are on EF Core 11, add that complex types and JSON columns finally work with TPT and TPC, which removes one of the last reasons those strategies forced you into owned entities.

Gotcha — JSON columns are not free schema flexibility

Mapping to JSON avoids joins and models documents naturally, and on SQL Server 2025 the native json type makes it genuinely efficient. What it costs: you cannot put a foreign key into a JSON document, indexing requires explicit support (SQL Server 2025 JSON indexes, which EF Core 11 can create and scaffold), and querying inside JSON is only as good as the provider's translation — DISTINCT over a JSON array is not supported on SQL Server at all. There is also a live migration hazard in EF10: if you configure with UseAzureSql or compatibility level 170, existing nvarchar(max) JSON columns are automatically altered to the json type by the next migration you add. That is a supported operation but a non-trivial one on a large table, and it will appear in a migration nobody deliberately wrote. Opt out with a lower compatibility level or explicit HasColumnType("nvarchar(max)") if you want to schedule it yourself.

2. Map a complex type with ToJson() against SQLite, then against SQL Server with compatibility level 150 and again with 170. Add a migration each time and read the DDL.

Solution sketch

Compatibility level 150 gives nvarchar(max); 170 gives the native json type, and if you switch an existing model from 150 to 170 the generated migration alters every JSON column. That is the "surprise migration" this unit warns about — seeing it once in a sandbox is worth more than reading about it. Finish by running ExecuteUpdate on a property inside the JSON document and confirm SQL Server emits a .modify() call rather than rewriting the whole document.

Compare TPH, TPT and TPC and pick one for a payments hierarchy.

TPH puts the whole hierarchy in one table with a discriminator, so base-type queries are a single scan and leaf queries are a scan with a predicate; the cost is that subtype-specific columns must be nullable. TPT normalises: a base table plus one table per subtype joined on a shared key, giving real NOT NULL constraints at the cost of a join per level on every read and multiple inserts per row. TPC gives each concrete type its own complete table, so leaf reads are single-table and fast, base reads are a UNION ALL, and there is no shared identity column, so keys must come from a sequence or be GUIDs. For payments I would default to TPH: the hierarchy is shallow, the subtype columns are few, and reads are dominated by "all payments for this order". I would pin the discriminator values explicitly rather than accept type names, add check constraints so the nullable subtype columns cannot hold nonsense, and index the discriminator. If a subtype turned out to carry twenty of its own columns I would revisit — that is when the nullable-column cost becomes real — and on EF Core 11 the fact that complex types and JSON now work with TPT/TPC widens that option.

Owned entity types or complex types — what changed and what do you use?

Complex types, for new work, and I would plan a migration for existing owned types used as value objects. The distinction is semantic: owned types are entities with a hidden identity, so they have reference semantics, cannot be assigned to two navigations, compare by identity in LINQ, and cannot participate in ExecuteUpdate. Complex types are true value objects — assignment copies, equality is structural, structs are supported. EF Core 8 introduced them for table splitting only; EF Core 10 completed the picture with optional complex types, ToJson() mapping, struct support and ExecuteUpdate over properties inside a JSON-mapped complex type, and the docs now explicitly advise switching. EF Core 11 adds them to TPT/TPC hierarchies, lambda chaining for configuration, and keys and indexes on nested paths. The practical migration is mostly a configuration change from OwnsOne to ComplexProperty, but the column names can shift — EF10 also changed nested complex type column naming to use the full path and started uniquifying clashes — so it needs a migration reviewed by hand, not a blind dotnet ef migrations add.

When would you map to a JSON column instead of a related table?

When the data is genuinely part of the aggregate, is always read and written with its parent, and nothing else needs a foreign key to it — configuration blobs, an address, an audit payload, a set of options, a snapshot of an external document. The wins are real: no join, no separate table to migrate, natural modelling of nested and variable structures, and on SQL Server 2025 or Azure SQL the native json type gives efficient storage and JSON_VALUE(... RETURNING int) predicates that EF generates for you. The costs are equally real: no foreign keys into the document, indexing needs explicit support, some operations simply are not translatable — DISTINCT over a JSON array is unsupported on SQL Server — and reporting tools hate it. My rule is that JSON is for data the relational model does not need to reason about. The moment somebody wants to join to it or aggregate across it, it should have been a table.

How do you handle a discriminator when class names change?

By never letting the class name be the stored value. The default TPH discriminator is the CLR type name, so a rename or a namespace move changes what EF writes and, worse, what it matches on read — existing rows stop materialising and you get an exception about an unmapped discriminator value, usually in production after a refactor that passed every test because the tests were seeded fresh. So I pin values explicitly with HasDiscriminator<string>("Kind").HasValue<CardPayment>("card"), using short stable strings that are part of the data contract. If I inherit a model where this was not done, the fix is a data migration that rewrites the column plus the explicit configuration, done in one release. I would also mention that you can map the discriminator to a real property, index it, and constrain it — all of which turn an implicit EF detail into something the database and the DBA can see.

Can you use EF's inheritance mapping with a schema you do not control?

Usually yes, because the three strategies cover the shapes legacy schemas actually have: one wide table with a type column is TPH, a base table with satellite tables is TPT, and parallel similar tables are TPC. The work is in the configuration rather than the model — mapping the existing discriminator column and its existing values, pointing each type at its real table and columns, and reconciling nullability. Where it breaks down is when the legacy schema does something no strategy expresses, like a discriminator that is a bitmask, or subtype tables keyed differently from the base. Then I stop trying to make inheritance work and map the types independently, using views or a mapped ToView/ToSqlQuery for the read shape and keeping the inheritance in the domain rather than in the mapping. The general principle I would state: EF's model should describe the schema honestly; if the mapping is fighting, the mapping is the wrong tool and a view or a read model is the right one.

What is table splitting and when is it useful?

Mapping two or more entity types to the same table, sharing the primary key. The classic use is separating a rarely-needed heavy column set from the hot one — an Order and an OrderBlob sharing the Orders table, so ordinary queries never read the big nvarchar(max) column but you can load it on demand through a navigation. It is also what complex types do implicitly when they are not mapped to JSON: the nested type's properties become extra columns on the parent's table with prefixed names. The trade-offs: the split entities have the same lifetime and the same key, EF requires a relationship between them, and it is easy to confuse with entity splitting (one entity across two tables, added in EF Core 7), which solves the opposite problem. I would reach for a projection first — selecting only the columns I need is simpler than modelling a split — and use table splitting when the heavy column has to be part of an entity that domain code mutates.

How do you model a value object that must be queryable and indexable?

As a complex type mapped by table splitting, not as JSON, so each component is a real column that can be indexed and constrained. Money as amount plus currency, an address as its parts, a date range as two columns — these want to be columns. If the value object is a single scalar with a wrapper type, a value converter is enough, and if it is mutable I supply a ValueComparer with a deep-copy snapshot, or better, make it immutable so I never need one. If it must live in JSON and still be queryable, EF Core 11 adds keys and indexes on complex type paths and SQL Server JSON indexes generated from the model, which is new and worth knowing about, but on EF10 the honest answer is that indexing inside JSON is manual. The design instinct I would express: choose the mapping from the query requirements, not from the object model's aesthetics — the object model is the same either way.

What is the migration risk when adopting EF Core 10's JSON improvements on an existing system?

Three specific things. First, if you configure with UseAzureSql or set compatibility level 170 or higher, EF10 defaults JSON storage to SQL Server's native json type, so the first migration you generate after upgrading will alter every existing nvarchar(max) JSON column — supported, but a large table rewrite that appears in a migration nobody wrote deliberately. Second, complex type column names changed: nested complex properties now use the full path, and clashing names are uniquified with a numeric suffix, so a model that previously produced NestedComplex_Property now produces Complex_NestedComplex_Property and generates rename operations. Third, if you switch owned types to complex types as the docs recommend, that is a model change with its own column-name consequences. My approach is to upgrade the package first with no model changes, generate a migration, and read it — if it is empty, good; if it is not, that migration is the actual upgrade plan and it gets scheduled, reviewed and tested against a production-sized copy.

How do vector columns fit into all this, and would you use EF for a RAG store?

EF Core 10 added first-class support for SQL Server 2025 and Azure SQL's vector data type: a property of type SqlVector<float> with a column type like vector(1536), populated from any IEmbeddingGenerator, and queried with EF.Functions.VectorDistance("cosine", b.Embedding, query) in an OrderBy. Cosmos got vector similarity search out of preview in EF10, plus full-text search and Rrf for hybrid ranking. EF Core 11 goes further with real approximate nearest-neighbour: HasVectorIndex in the model, VectorSearch(...).Take(k).WithApproximate() translating to SQL Server's VECTOR_SEARCH(), and — the change with the biggest practical impact — vector columns are no longer selected when materialising entities, which their benchmark put at roughly 9× locally and 22× against a remote database. Would I use it? For a system that already has SQL Server and needs semantic search over data it already owns, yes, and the argument is operational: one database, one transaction, one backup, no synchronisation job between a relational store and a vector store. For a large dedicated vector workload with heavy index tuning, a purpose-built store still wins.

A team wants "schemaless" columns so they can stop writing migrations. What do you say?

That the migrations are not the cost they think they are, and that the cost they are avoiding will reappear as unversioned data. JSON columns do not remove schema; they move it into the application, undocumented, where three versions of the shape coexist in the same column and every reader needs defensive parsing. I would ask what is actually painful — usually it is the deployment process for migrations, or the review latency, and both are fixable. Then I would offer the genuine use cases for JSON: data that is truly variable per row, a payload from an external system stored as received, user-defined fields nobody queries. And I would put a boundary around it: anything queried, joined, aggregated or reported on is a column; anything JSON gets an explicit version field and a mapped complex type so at least the shape is declared in one place. Framing it as "we will use JSON deliberately for these three things" turns an argument about tooling into a design decision, which is the outcome you want.

07 Migrations and schema lifecycle

Docs: Migrations overview · Applying migrations · Migrations in team environments

A migration is a diff. When you run dotnet ef migrations add, EF builds the model from your code, compares it to the model snapshot (ModelSnapshot.cs, a generated C# description of the schema as of the last migration), and emits a class with Up and Down methods expressed as provider-agnostic operations plus a new snapshot. At apply time EF reads the __EFMigrationsHistory table, works out which migrations are missing, and runs their Up in order, recording each.

Three consequences follow directly and answer most migration questions. The snapshot is the source of truth for the next diff, so anything that desynchronises it — hand-editing a migration without editing the snapshot, deleting a migration file, merging two branches that each added one — produces a wrong next migration. The history table is keyed by migration id, so migrations are identified by name and timestamp, not by content. And Down is generated but almost never tested, which is why rollback-by-migration is a much weaker guarantee than teams assume.

The commands you actually use

dotnet ef migrations add AddOrderReference --project src/App.Infrastructure --startup-project src/App.Api
dotnet ef migrations list
dotnet ef migrations remove                       # only if not applied anywhere
dotnet ef database update                         # dev only
dotnet ef migrations script --idempotent -o migrate.sql    # what production gets
dotnet ef migrations bundle --self-contained -r linux-x64  # a single executable (EF Core 6+)
dotnet ef dbcontext script                        # full schema from the model, no migrations

# EF Core 10 breaking change: multi-targeted projects must say which TFM.
dotnet ef migrations add AddOrderReference --framework net10.0

The idempotent script is the production workhorse: it wraps every migration in IF NOT EXISTS (SELECT ... FROM __EFMigrationsHistory WHERE MigrationId = ...), so it can be applied to a database at any version, re-run safely, reviewed by a DBA, and executed by a deployment tool that has no .NET on it. Migration bundles (EF Core 6+) are the middle ground — a self-contained executable that applies migrations without the SDK — and they are the right answer for containerised deployments that cannot ship a script through a DBA process.

Zero-downtime schema change

The rule that makes this tractable: during a rollout, the old code and the new code both run against the same schema. So every change must be decomposed into steps that are each backward-compatible — the expand/contract (or parallel-change) pattern.

// Renaming Customer.Name to Customer.FullName, safely, across three releases.

// R1 — EXPAND: add the new column, nullable. Old code ignores it.
migrationBuilder.AddColumn<string>("FullName", "Customers", nullable: true);

// R1 (app) — dual-write: set both. Backfill existing rows in a batched job,
// NOT in the migration, so the deploy is not blocked by a 40-minute UPDATE.
// R2 — read from FullName, keep writing both. Verify no readers of Name remain.
// R3 — CONTRACT: stop writing Name; drop it.
migrationBuilder.DropColumn("Name", "Customers");

The same shape covers making a column non-nullable (add nullable, backfill, add the constraint), splitting a table, changing a type, and adding a foreign key to existing data. What it never covers is a RenameColumn in one release, which EF will happily generate and which breaks the old instances still serving traffic.

modelBuilder.Entity<Country>().HasData(

Interview trap — "we roll back by running Down"

Down methods are generated, rarely executed, and never tested; the first time most teams run one is during an incident, which is the worst possible time to discover that DropColumn is not a rollback — the data is gone. And a rollback of a deployment is not a rollback of a migration: the old code must run against the new schema, because the data written since the deploy lives there. The professional answer is that schema changes roll forward, not back: keep every migration backward-compatible (expand/contract), so rolling back the application binary is always safe and no schema action is needed. Reserve Down for local development, where it genuinely is convenient. If a destructive change must be reversible, the reversal mechanism is a backup or a shadow table, not a generated method.

Gotcha — merge conflicts in the model snapshot

Two developers branch, each adds a migration, both regenerate ModelSnapshot.cs. Git merges the migrations cleanly (different files) and produces a snapshot that reflects one branch, or a mangled union of both — and the next migration anyone generates will contain the difference, silently trying to drop the other branch's column. The manual fix is to keep one branch's migration, delete and regenerate the other's after merging, and never resolve a snapshot conflict by hand-picking hunks. EF Core 11 finally addresses this at the tooling level: the snapshot now records the id of the latest migration, so two divergent branches both modify that value and Git raises a conflict instead of merging quietly. Until you are on EF11, the practical mitigations are a team convention of one open migration at a time, and a CI check that runs dotnet ef migrations add --dry-run-style verification and fails if the model and the snapshot disagree.

Try it — desynchronise the snapshot on purpose

1. Add a property, generate a migration, apply it. Now delete the migration file by hand (leave the snapshot), add another property, and generate a second migration. Read what it contains.

Expected outcome

The second migration only contains the second property, because the snapshot — not the migration files, and not the database — is what EF diffs against. Your first change is now unrepresented anywhere in the migration history, so a fresh database built from migrations will be missing that column while your dev database has it. This is exactly the failure mode of a bad merge, and doing it deliberately once makes the rule "never hand-delete an applied migration; use dotnet ef migrations remove" stop being a rule and start being obvious.

2. Practise expand/contract: rename a column across three migrations with a dual-writing application in between, and verify at each step that the previous version of the code still runs.

Solution sketch

Add nullable column → deploy code writing both and reading old → backfill in batches → deploy code reading new and writing both → deploy code writing only new → drop old column. Six steps, three deploys, and at no point is there a moment where a running instance sees a schema it does not understand. Time yourself doing it; the point of the exercise is to feel how much cheaper it is to design changes this way from the start than to retrofit the pattern during an incident.

How do migrations work under the hood?

EF builds the model from your code and diffs it against the model snapshot — a generated C# file describing the schema as of the last migration — producing a migration class with Up and Down expressed as provider-agnostic operations like AddColumn and CreateIndex, plus an updated snapshot. At apply time EF queries __EFMigrationsHistory, determines which migration ids are missing, and executes their Up in order inside transactions where the provider supports transactional DDL, recording each as it goes. Three implications matter in practice: the snapshot, not the database, is the baseline for the next diff, so anything that desynchronises it produces a wrong migration; migrations are identified by id, so the same schema change under two names applies twice; and the operations are translated to SQL by the provider at apply time, which is why a migrations assembly is provider-specific and why you need separate migrations if you genuinely ship on two databases.

How do you apply migrations in production?

An idempotent SQL script generated at build time, applied by the deployment pipeline as a distinct step before the application rollout — or a migration bundle where a script cannot be used. The reasons are permissions, review and control: the application's runtime identity should not hold DDL rights, a DBA or a reviewer can read a script, and the pipeline can fail the deploy if the schema step fails rather than half-rolling-out. I specifically avoid Database.Migrate() at startup in production. Even though EF Core 9 added a migration lock so concurrent instances no longer corrupt the database, startup migration still means every instance contends on rollout, a long DDL statement delays readiness and can trip health checks, and the app needs elevated rights permanently to cover a rare event. The exception I would accept is a single-instance internal tool, or an Aspire-style setup where a dedicated migration project runs once — and even then I would keep it out of the serving application.

Two developers merged branches and the next migration is nonsense. What happened and how do you fix it?

Both branches regenerated the model snapshot, and Git merged the migration files cleanly because they are separate files while producing a snapshot that reflects only one branch or a mangled mix. Since EF diffs against the snapshot, the next migration generated after the merge contains the delta between the wrong baseline and the real model — typically trying to drop the other branch's column. The fix is to keep whichever migration is already applied somewhere, revert the snapshot to that migration's version, delete the other migration and regenerate it on top, then verify by generating one more migration and confirming it is empty. That last check — "generate a migration and assert it is empty" — is worth wiring into CI, because it catches every kind of model/snapshot drift. EF Core 11 improves the ergonomics by recording the latest migration id in the snapshot so divergent branches produce a real Git conflict rather than a silent bad merge, but the team convention of one open migration at a time is still the cheapest prevention.

How do you make a breaking schema change with zero downtime?

By never making one. Every change gets decomposed into steps that are individually backward-compatible, because during a rollout the old and new code both run against one schema. Renaming a column becomes: add the new one nullable; deploy code that writes both and reads the old; backfill in a batched background job rather than in the migration; deploy code that reads the new and still writes both; deploy code that writes only the new; drop the old. Making a column non-nullable becomes add-nullable, backfill, then add the constraint. Adding a foreign key to existing data means cleaning the data first, then adding the constraint NOT FOR REPLICATION-style or with validation deferred if the database supports it. The things I explicitly refuse in a single release are RenameColumn, DropColumn on a column the previous version still writes, and any long-running UPDATE inside a migration that blocks the deployment. The cost is more releases; the benefit is that a rollback of the binary is always safe, which is worth far more.

How do you seed reference data?

It depends on whether the data is part of the schema or part of the environment. Genuine reference data that the code depends on — currency codes, statuses, feature definitions — I put in HasData, because it becomes part of the model, is diffed into insert/update/delete operations by migrations, and therefore versions with the schema and gets applied exactly once per environment. The constraint is that HasData requires fixed primary keys and it will delete rows you remove from the seed, which is a sharp edge worth stating. Environment-specific or bulk data — demo data, a test tenant, a large lookup import — I keep out of migrations entirely and run as an idempotent application-level job, which since EF Core 9 has a supported hook in UseSeeding/UseAsyncSeeding. What I never do is a big data migration inside migrationBuilder.Sql: it blocks the deployment, it is not resumable, and it will eventually time out on the largest customer's database.

What is EnsureCreated and why is it dangerous?

EnsureCreated builds the schema directly from the model, without consulting or writing the migrations history table. It is fast and convenient, and it is a trap because the database it produces can never be migrated: EF has no record of which migrations are "already applied", so the first database update tries to run the initial migration against a database that already has the tables. Its legitimate uses are throwaway databases — a SQLite file in a test run, an in-memory provider, a scratch container — where the whole database is created and dropped per run. Anything with a lifetime longer than a test gets migrations from day one, including local development databases, because the day someone needs to add a column to a shared dev database is the day EnsureCreated costs an afternoon. The related caution is EnsureDeleted in tests pointed at a connection string that is not what you think it is.

How do you handle a database you do not own — DBA-controlled schema?

Reverse the direction: the schema is the source of truth and EF follows it. dotnet ef dbcontext scaffold reverse-engineers a model, and the practical approach is to scaffold into a separate partial-class-friendly location, keep hand-written configuration alongside it, and re-scaffold when the schema changes. Migrations are then either not used at all, or used only to generate scripts the DBA reviews and owns — dotnet ef migrations script as a proposal, not as an executed artifact. Two things make this work in practice: a CI check that scaffolds the current database and fails if the model has drifted, so you find out about a schema change before your users do; and mapping views or table-valued functions with ToView/ToSqlQuery for read shapes so you are not tempted to reshape the tables. EF Core 11's ExcludeForeignKeyFromMigrations is a relevant new tool here, letting you model a relationship EF knows about while suppressing the constraint EF would otherwise want to create.

Should migration files ever be hand-edited?

Yes, deliberately and often — with the discipline that the snapshot must stay consistent. The generated migration is a starting point, not a contract. I edit them to add CREATE INDEX ... WITH (ONLINE = ON) on SQL Server so an index build does not lock a hot table, to split one generated migration into two so an operation that cannot run inside a transaction is isolated (EF Core 9 warns when a migration mixes those), to replace a generated RenameColumn with an add/backfill/drop sequence, to add explicit Sql() for a view or a stored procedure the model does not describe, and to write a real Down for something I actually intend to be able to reverse. What I do not do is edit a migration that has already been applied anywhere — that changes history that other environments have already recorded — and I do not touch the snapshot by hand; if the model changed, regenerate.

How do you verify a migration before it touches production?

Four gates. A CI step that generates a migration and fails if it is non-empty, which proves the model and the snapshot agree. A restore of a production-sized copy — not a fresh database — with the idempotent script applied against it, timed, because the thing that hurts is not correctness but a table rewrite that takes forty minutes and holds a lock. A review of the generated SQL by someone who reads execution plans, looking specifically for implicit rebuilds: changing a column type, adding a non-nullable column with a default, adding an index on a large table. And an integration test suite that runs against the migrated schema, ideally in a Testcontainers-backed database, so behavioural regressions from a type or collation change show up. For anything I judge risky, the deployment plan also names how we abandon: usually "roll forward with a compensating migration", occasionally "restore from the pre-deploy snapshot", and I want that written down before the change window, not improvised during it.

What migration tooling improvements are coming in EF Core 11 and do they change your process?

Several, and two of them do. The model snapshot recording the latest migration id turns silent branch divergence into a Git merge conflict, which removes the single most common team-scale migration failure — that changes my process by making the "one open migration at a time" convention less critical. dotnet ef database update <name> --add creates and applies a migration in one step, compiling it at runtime with Roslyn, aimed at Aspire and container scenarios where recompiling is impossible; useful, but I would keep it out of production paths. The rest are ergonomics I would adopt immediately: a .config/dotnet-ef.json file so nobody types --project and --startup-project again, --offline and --connection for migrations remove and database drop, a wildcard --context "*" for multi-context projects, -NoBuild in the Package Manager Console, and the tool writing logs to stderr so migrations script output can be piped cleanly. ExcludeForeignKeyFromMigrations is the one modelling addition that matters for legacy databases without constraints.

08 Concurrency and transactions

Docs: Handling concurrency conflicts · Transactions · Connection resiliency

EF's default is optimistic concurrency, and it is off unless you configure it. That sentence surprises people: without a concurrency token, two users who load the same order and save produce last-write-wins, silently. Nothing throws. The lost update is invisible in logs and shows up as a support ticket weeks later.

Turning it on means giving EF a token to compare. On SQL Server the idiomatic choice is a rowversion/timestamp column, which the database bumps automatically on every update; portably you can mark any property as a concurrency token and take responsibility for changing it yourself.

public byte[] RowVersion { get; set; } = [];
b.Property(o => o.RowVersion).IsRowVersion();          // SQL Server: rowversion column

// Portable alternative: an incrementing token you own.
b.Property(o => o.Version).IsConcurrencyToken();

// PostgreSQL system column, via Npgsql:
// b.UseXminAsConcurrencyToken();

With a token in place, EF adds it to the WHERE clause of every UPDATE and DELETE and checks the affected row count:

UPDATE [Orders] SET [Total] = @p0
OUTPUT INSERTED.[RowVersion]
WHERE [Id] = @p1 AND [RowVersion] = @p2;   -- 0 rows affected => someone else won
// Handling the conflict: the only interesting part is the merge policy.
while (true)
{
    try { await db.SaveChangesAsync(); break; }
    catch (DbUpdateConcurrencyException ex)
    {
        foreach (var entry in ex.Entries)
        {
            var databaseValues = await entry.GetDatabaseValuesAsync();
            if (databaseValues is null) throw new OrderDeletedException(entry);   // deleted by someone else

            // "database wins" for fields we did not touch, "client wins" for ours:
            var current = entry.CurrentValues.Clone();
            entry.OriginalValues.SetValues(databaseValues);   // accept their version as the new base
            entry.CurrentValues.SetValues(databaseValues);
            entry.CurrentValues.SetValues(current.ToObject() is Order o ? PickMine(o) : current);
        }
    }
}

Interview trap — retry policies and non-idempotent work

EnableRetryOnFailure is close to mandatory against Azure SQL, because transient failures are normal there. But a retry replays the operation, and EF cannot know whether the first attempt committed before the connection dropped — the classic case is a SaveChanges that succeeded on the server and whose acknowledgement was lost. Retrying then inserts the row twice. The mitigations are the ones you should name: make the write idempotent with a natural or client-generated key so the duplicate insert violates a unique constraint instead of succeeding; use an outbox with a deduplication key for anything that has effects outside the database; and never wrap an operation with external side effects (send an email, call a payment API) in a retried block. The second half of the trap is the one people hit first: with retries enabled, a user-initiated BeginTransaction throws unless it is created inside strategy.ExecuteAsync, and the error message is not obvious if you have not seen it.

Gotcha — ExecuteUpdate/ExecuteDelete bypass everything

ExecuteUpdateAsync and ExecuteDeleteAsync issue SQL immediately. They do not participate in SaveChanges, so they are not in its transaction unless you opened one explicitly; they do not update the change tracker, so tracked entities become stale and a subsequent SaveChanges can write the old values back over them; they do not run SaveChanges interceptors, so audit columns, soft-delete conversion and domain-event dispatch silently do not happen; and they ignore concurrency tokens entirely. None of that is a bug — they are set-based operations by design, and that is exactly why they are fast — but "we replaced the loop with ExecuteUpdate and now the audit trail has holes" is a real incident shape. Use them where set semantics are what you want, in their own transaction, and know that anything relying on the tracker will not see them.

Expected outcome

It throws, telling you the configured execution strategy does not support user-initiated transactions. Wrap the whole block in db.Database.CreateExecutionStrategy().ExecuteAsync(...) and it works. Then reason about the consequence: your delegate can now run more than once, so anything inside it — including code that appends to a list, increments a counter or calls a service — must be safe to repeat. Writing that sentence in a comment above the block is a habit worth keeping.

How does optimistic concurrency work in EF Core, and what is the default?

The default is no concurrency control at all: without a configured token, EF's UPDATE matches on the primary key only, so the last writer wins silently and the first user's change disappears with no exception anywhere. Once you mark a property as a concurrency token — on SQL Server usually a rowversion column via IsRowVersion, which the database increments automatically — EF includes its original value in the WHERE clause of every UPDATE and DELETE for that entity, and checks the rows-affected count. Zero rows means someone else changed or deleted the row since you read it, and EF throws DbUpdateConcurrencyException with the offending entries. The critical design point is that the framework only detects; it cannot resolve. Choosing between client-wins, store-wins and a field-level merge is a product decision, and for anything a human edits I strongly prefer surfacing the conflict to the user with both versions rather than silently picking, because silently picking is how you get a lost-update bug that nobody can reproduce.

Optimistic or pessimistic locking — when would you use each?

Optimistic by default, because it costs nothing when there is no contention, it works across HTTP requests where a lock cannot be held, and it scales. Pessimistic when the contention is high enough that optimistic retries dominate, or when the work between read and write is expensive enough that redoing it is worse than blocking — a batch allocator handing out sequence numbers, a stock-reservation path where every request touches the same row, a job queue. EF has no first-class pessimistic locking, so the implementations are raw SQL with UPDLOCK, ROWLOCK hints on SQL Server or SELECT ... FOR UPDATE elsewhere, inside an explicit transaction, or an application-level lock row that everybody takes in a defined order to avoid deadlock. The point I would make is that "high contention on one row" is usually a design smell worth attacking directly: partition the counter, move to an append-only log with periodic aggregation, or let the database do the arithmetic with ExecuteUpdate so the read never happens in the application at all.

When do you need an explicit transaction rather than relying on SaveChanges?

SaveChanges already wraps its own statements in a transaction, so a single save of an entire object graph is atomic without any code. I open an explicit transaction when the unit of work spans more than one SaveChanges — usually because I need a store-generated key before building the next part — or when it mixes EF with raw SQL or Dapper on the same connection, or when I need a specific isolation level for the whole block, such as snapshot isolation to make a split query consistent. The mechanics matter: BeginTransactionAsync returns something you dispose, EF enlists subsequent operations automatically, and if I am sharing with ADO.NET I get the underlying DbTransaction with GetDbTransaction() and pass it explicitly. The one thing I avoid is holding a transaction open across a network call or user interaction, because locks held for hundreds of milliseconds are how a system that works at ten users falls over at a thousand.

What does EnableRetryOnFailure actually do, and what breaks when you turn it on?

It installs an execution strategy that catches provider-classified transient errors — network blips, Azure SQL throttling, failovers — and retries the operation with exponential backoff up to a limit. Against Azure SQL it is close to mandatory. Two things break. First, user-initiated transactions: because the strategy retries a whole operation and cannot retry a block it does not own, calling BeginTransaction directly throws, and the fix is to run the whole transactional block inside db.Database.CreateExecutionStrategy().ExecuteAsync(...). Second, and more subtly, idempotency: a retried SaveChanges may be re-executing work that actually committed before the connection dropped, so an insert can happen twice. That is why anything with external side effects must not sit inside the retried block, and why writes should be made naturally idempotent — a client-supplied key with a unique index turns a duplicate into a catchable constraint violation rather than a duplicate row. I would also point out that retries hide latency, so the retry count and delays belong in metrics, not just in configuration.

You get a DbUpdateConcurrencyException. Walk me through handling it properly.

First, distinguish the two causes: the row changed, or the row is gone. entry.GetDatabaseValuesAsync() returning null means deleted, and that is usually a different user-facing outcome. For the changed case I fetch the database values and decide per the domain. Client wins means copying database values into OriginalValues so the token matches and re-saving — that deliberately discards the other user's change, and I would only do it where the domain says my write is authoritative. Store wins means refreshing the entity and telling the caller their edit was rejected. The interesting one is a field-level merge: take the database values as the new baseline, re-apply only the properties this user actually edited, and re-save — that is what most collaborative editing wants, and it needs the UI to send which fields changed. I loop, because a merge can itself conflict, but with a bounded retry count and a metric, because unbounded retry on a hot row is a livelock. And whatever I choose, I make the policy explicit in code with a name, because a silent choice here is a data-loss decision made by accident.

How do you keep EF writes atomic with a message publish?

You cannot make a database transaction and a broker publish atomic without distributed transactions, which I would not reach for, so I use the transactional outbox. In the same SaveChanges that writes the domain change, insert a row into an outbox table describing the message; a separate dispatcher reads unsent rows and publishes them, marking them sent. Because it is one transaction, the domain change and the intent to publish either both happen or neither does. The properties I want the team to understand are that this gives at-least-once delivery, not exactly-once, so consumers must be idempotent; that the dispatcher needs a claim mechanism so two instances do not publish the same row; and that ordering is only guaranteed if you enforce it, typically per aggregate. Implementing the outbox write is a natural fit for a SaveChanges interceptor, which turns "remember to write the outbox row" from a code-review item into a structural guarantee — and it is also exactly why ExecuteUpdate paths bypassing interceptors are dangerous in a system that relies on this.

What isolation level does EF use, and when would you change it?

EF does not set one; it uses the connection's default, which on SQL Server is READ COMMITTED — and, importantly, non-snapshot read committed unless the database has READ_COMMITTED_SNAPSHOT on, meaning readers can block writers. I change it deliberately in a few cases. Snapshot isolation for a read that spans several queries and needs to be consistent, which is exactly the split-query consistency problem from unit 04. Serializable for a check-then-act invariant that cannot be expressed as a unique constraint, accepting the deadlock risk and retrying. Read uncommitted essentially never — the "just add NOLOCK" reflex trades correctness for a symptom fix and I would push back on it in review, because it can return rows twice or not at all during a page split. The broader point is that isolation is a database-level design decision that EF happens to expose; if a team is arguing about isolation levels in application code, the underlying question is usually whether the transaction boundaries are right.

Two instances of a background job both process the same record. How do you fix it in EF?

Make the claim atomic and set-based rather than read-then-write. The cheapest correct version is a single UPDATE that both selects and claims: ExecuteUpdateAsync over a filtered query setting ClaimedBy and ClaimedAt where the row is unclaimed, then read back what you claimed — or on SQL Server, raw SQL with UPDATE ... WITH (READPAST, UPDLOCK) ... OUTPUT INSERTED.*, which claims and returns in one statement and skips locked rows so instances do not queue behind each other. If I have to do it with tracked entities, then a concurrency token on the claim column turns the race into a DbUpdateConcurrencyException that the loser handles by moving to the next record. What I would avoid is a distributed lock as the first answer: it works, but it adds a dependency and a liveness problem, and the database already has the primitive. I would also add a lease timeout so a crashed worker's claim expires, because "claimed forever by a dead process" is the failure this design has instead of double-processing.

Why might ExecuteUpdate be the wrong tool even though it is faster?

Because it is a different operation with different guarantees. It runs immediately, outside SaveChanges, so it is not in that transaction unless you opened one explicitly; it does not touch the change tracker, so tracked entities silently hold stale values and a later SaveChanges can write them back over your update; it does not fire SaveChanges interceptors, so audit columns, soft-delete handling, outbox writes and domain-event dispatch do not happen; and it ignores concurrency tokens completely. On a system that relies on any of those for correctness, replacing a tracked loop with ExecuteUpdate is a behavioural change, not an optimisation. The right usage is where the set semantics are what you actually mean — mark 40,000 notifications read, increment a counter, purge expired rows — and where you have thought about the transaction and the interceptors. I would also mention the EF10 ergonomics improvement, that the setters argument is now a plain lambda rather than an expression tree, so building the update conditionally no longer requires hand-constructing expression trees.

How would you design a system so concurrency conflicts are rare rather than handled well?

By reducing shared mutable state and shortening the window between read and write. Concretely: model the aggregate so that the unit people edit concurrently is small — if two users editing different lines of an order conflict, the order is too coarse an aggregate. Push arithmetic into the database with ExecuteUpdate or a computed statement so an increment never round-trips as read-modify-write. Prefer append-only writes with periodic aggregation for hot counters, so writers never contend on one row. Give clients idempotency keys so retries are safe and a conflict is detectable rather than duplicative. And use the token to make conflicts visible even where they are rare, because a system that has no concurrency control does not have fewer conflicts, it just has invisible ones. In an interview I would finish by naming the trade-off honestly: every one of those moves adds complexity, so I would apply them where the contention is measured, not everywhere on principle.

Interview trap — reaching for micro-optimisations first

Candidates who answer "how would you speed up EF?" with "compiled queries and AsNoTracking" are answering the wrong question. Those are single-digit-percent wins on the CPU EF spends per row. The wins that matter are structural and measured in multiples: eliminating N+1 (100× fewer round trips), replacing an Include chain with a projection (10× fewer bytes), adding the index the plan is scanning without (1000× fewer reads), replacing a tracked loop with one ExecuteUpdate. The credible answer starts with "I would measure where the time goes — EF CPU, network round trips, or the database — because the fix is completely different for each," and only then names the tools. The corollary is that if the database is the bottleneck, EF is irrelevant: no EF setting fixes a missing index.

Gotcha — async is not faster, and Count() is not free

Two adjacent misconceptions. Async EF calls do not make a query complete sooner; they release the thread while waiting, which raises throughput under load and does nothing for a single request's latency — and getting it wrong (sync-over-async, or blocking on .Result) causes thread-pool starvation that looks exactly like database slowness. Separately, list.Count on a materialised list is free, but query.Count() is a second round trip and a second aggregate query; a paged endpoint that returns both a page and a total does two queries, and on a large filtered set the count is often the expensive one. Options are to cache or approximate the count, to fetch Take(pageSize + 1) and report "there is more" instead of a total, or to move to keyset pagination which does not need a count at all. EF Core 9 did optimise Count() != 0 into EXISTS, but the general point stands: every terminal operator is a round trip.

1. Write the counting DbCommandInterceptor above, register it in your integration test fixture, and add an assertion helper: AssertMaxCommands(3, () => ...). Wrap your three busiest endpoints' tests in it.

Expected outcome

At least one of them fails, and the failure names a number rather than a feeling. Now you have a regression gate: a future change that reintroduces lazy loading or moves a query into a loop breaks the build instead of the site. This single test pattern catches more real EF performance bugs than any amount of profiling, because it catches them before they ship.

2. Take a paged list endpoint and measure three versions: Include + entity mapping, Select into a DTO, and Select plus keyset pagination at page 500. Capture bytes returned and duration.

Solution sketch

The projection typically cuts bytes several-fold immediately. The keyset version is indistinguishable from the offset version at page 1 and dramatically better at page 500, because OFFSET 10000 makes the database read and discard 10,000 rows. Write down both numbers — the ability to say "offset pagination is O(skip) and here is the measurement" is the difference between an opinion and an engineering argument.

"The app is slow and we think it is EF." How do you investigate?

I refuse to guess and split the time three ways: time in EF's own code, time waiting on round trips, and time the database spends executing. EF's logging with timings and a command counter per request separates the first two — many small fast queries is N+1, one slow query is a database problem, and fast SQL with a slow request points at EF CPU or materialisation. Then I look at rows returned versus entities materialised, which exposes cartesian explosion, and at the columns being selected, which exposes over-fetching. If the SQL looks right and is slow, it stops being an EF question and becomes an indexing and plan question — I take the SQL to the query store or an execution plan. Only after all that do I consider tracking behaviour, compiled queries or model compilation, because those are percentage-level wins. The habit I would emphasise is capturing a before-and-after SQL diff for any change, because "we made it faster" without evidence is how teams accumulate cargo-cult optimisations.

What are the highest-leverage EF performance fixes, in order?

Eliminate N+1 first — that is usually two orders of magnitude of round trips and it is almost always present in an untuned codebase. Then reduce rows: pagination, filtering server-side, and killing cartesian explosion with split queries or a projection. Then reduce columns by projecting to DTOs instead of loading entities, which also removes tracking cost for free. Then fix the database: the indexes the plans want, and any plan regressions — with EF10 specifically I would look at queries using Contains over a collection, because the default translation changed and the new plan may not suit the data. Then EF's own CPU: AsNoTracking on reads, fewer tracked entities in write loops, ExecuteUpdate/ExecuteDelete instead of load-modify-save for set operations. Startup cost — compiled models and precompiled queries — comes last unless the workload is serverless or the process is short-lived, in which case it jumps to the top.

When should you drop out of LINQ entirely for performance?

When the SQL you want is not the SQL EF will generate and the gap is material. Concretely: window functions and recursive CTEs that have no LINQ expression; a bulk insert of hundreds of thousands of rows, where SqlBulkCopy is a different algorithm rather than a faster version of the same one; a query needing hints or a specific plan guide; a set-based upsert like MERGE; hierarchical or full-text queries; anything where you have a hand-tuned statement from a DBA. The way I do it keeps the seams clean — FromSql so the result still materialises as entities and stays composable, or a mapped view or table-valued function so the query looks like LINQ to callers, or Dapper on EF's own connection and transaction so it is still one unit of work. And I put it behind a named method with a comment explaining the measurement that justified it, because otherwise the next person "cleans it up" back into LINQ.

Explain offset versus keyset pagination and when the difference matters.

Skip/Take becomes OFFSET/FETCH, and the database must produce and discard every skipped row, so cost grows linearly with the page number — page 5000 of a 20-row page reads 100,000 rows to return 20. It also gives inconsistent results under concurrent inserts, because a row inserted before your position shifts everything and the user sees a duplicate or misses an item. Keyset (seek) pagination filters on the last row's sort key instead — WHERE (SortKey, Id) > (lastSortKey, lastId) expanded into the equivalent boolean form — so each page is an index seek at constant cost and unaffected by inserts before your position. The costs are that you cannot jump to an arbitrary page number and the sort key must be unique, which is why you almost always append the primary key as a tiebreaker. My rule: offset is fine for admin screens with a few hundred rows and a page-number UI; anything infinite-scroll, API-driven, or over a large table is keyset.

What does DbContext pooling actually save, and what is the risk?

It saves the allocation and initialisation of the context object and its internal service scope — not the model build, which is already cached per context type. That is a real but modest win, most visible in high-throughput services with small, fast queries where per-request overhead is a measurable fraction. The risk is state: pooling resets EF's own state but not fields you added to your context class, so a per-request value captured in a constructor survives into the next request. Injecting a tenant accessor and storing the tenant id in a field is the canonical incident, because a global query filter then serves the wrong customer's data — a security bug, not a performance one. So my adoption rule is: pool only if I have measured a benefit, only with a context class that has no mutable state of its own, and with a test that runs two requests with different tenants through the pool and asserts isolation.

How do you deal with a query whose plan is good for some parameters and terrible for others?

That is parameter sniffing, and it is a database problem that EF exposes rather than causes. The diagnosis is a query that is fast most of the time and pathologically slow for particular inputs — typically a skewed column where a plan built for a selective value is reused for a value matching a third of the table. The remedies are mostly SQL Server-side: OPTIMIZE FOR UNKNOWN or RECOMPILE hints, a plan guide, or Query Store forcing a plan; splitting the query so the skewed case takes a different code path; or making the value a constant instead of a parameter so each value gets its own plan, which EF supports with EF.Constant. That last one is a legitimate EF-side lever and it is exactly the trade-off from unit 05: a plan per value at the cost of cache entries. Related and topical: EF10's switch to multiple scalar parameters for collections was motivated by this exact tension — it restores cardinality information to the planner, and it is the first thing I would examine if a Contains query regressed after upgrading.

What is the cost of tracking, quantitatively, and when is it the bottleneck?

Roughly: an extra allocation per entity for the snapshot, an identity-map insertion, and participation in every subsequent DetectChanges sweep on that context, which is O(tracked entities × properties). For a query returning 20 entities it is noise. It becomes the bottleneck in two shapes. First, large read queries — materialising 50,000 tracked entities to render a report doubles the allocations and pressures gen-0 and gen-1 collection; AsNoTracking, or better a projection, removes it. Second, write loops: adding entities one at a time triggers a full sweep per Add, which is quadratic and is the reason an import of 10,000 rows can take minutes. Microsoft's own benchmarks put no-tracking queries meaningfully ahead on large result sets, but I would frame it honestly in an interview: it is a real, measurable, bounded win, and it is nowhere near the win from not fetching the rows in the first place.

How do you bulk-insert a million rows with EF?

Mostly, I do not use SaveChanges for it. EF batches, but it still generates parameterised statements, tracks every entity and runs change detection, so a million rows is minutes and a lot of memory. The right tool is the database's bulk path: SqlBulkCopy on SQL Server, COPY via Npgsql's binary importer on PostgreSQL, both of which can share EF's connection and transaction so the operation is still atomic with the rest of the unit of work. Third-party libraries wrap this over the EF model if you want to keep entity types. If it must be EF, the mitigations are batching into chunks with a fresh context per chunk, disabling auto-detect changes, tuning MaxBatchSize, and accepting a much worse number. The deeper question I would raise is whether the million rows need to be entities at all — a staging table plus a set-based MERGE is often both simpler and faster, and it keeps the transaction short.

What EF-level caching would you use, and what would you avoid?

EF has first-level caching by construction — the identity map within one context — and no second-level cache, which I consider correct. I would avoid bolting on a second-level cache library as a general solution, because invalidation across instances is a genuinely hard problem and the failure mode is serving stale data silently, which is worse than being slow. What I do use: caching at a higher, explicit layer, where the cache key and the invalidation event are visible — a memory or distributed cache of a DTO with a TTL chosen from the business tolerance for staleness, or a cache keyed by a version column that a write bumps. For reference data that changes rarely, loading it once into a dictionary at startup with a refresh signal is simple and reliable. And I would separate the two questions being conflated: caching to reduce database load is an architectural decision; the query plan cache and EF's compiled-query cache are internal mechanisms I tune by keeping query shapes stable, not by adding a component.

Your service is serverless and cold starts hurt. What EF-specific options do you have?

Three levers, in order. A compiled model via dotnet ef dbcontext optimize, wired into the build with the Microsoft.EntityFrameworkCore.Tasks MSBuild package so it cannot go stale — EF Core 9 made it auto-discovered, so no UseModel call is needed when it lives beside the context. Then precompiled queries with dotnet ef dbcontext optimize --precompile-queries, which generates C# interceptors carrying the final SQL and a materialiser per query, so query translation moves from startup to build time; the caveat is that only statically analysable queries qualify, so conditionally composed IQueryables must be rewritten as separate whole queries. Then NativeAOT publishing, which combines with precompilation for the biggest startup win. The important honesty is that NativeAOT and query precompilation are still flagged experimental in the EF Core 10 documentation, with known limitations around dynamic queries, query syntax, captured-state value converters and provider support — so I would prototype and measure rather than commit a production service to them, and I would get most of the benefit from the compiled model alone plus a post-deploy warm-up that exercises the hot endpoints.

10 Raw SQL and escape hatches

Docs: SQL queries · User-defined function mapping

A mature EF codebase uses raw SQL deliberately, in a few named places, and says why. The escape hatches are a designed part of the framework, not an admission of defeat — the skill is choosing the one that keeps the most of EF's guarantees.

// 1. FromSql — returns ENTITIES, stays composable, parameterises via FormattableString.
var orders = await db.Orders
    .FromSql($"SELECT * FROM dbo.RecentOrders WHERE CustomerId = {customerId}")
    .Where(o => o.Total > 100)        // composed as a subquery — still server-side
    .OrderBy(o => o.PlacedAt)
    .ToListAsync();

// 2. SqlQuery<T> — scalars and unmapped types (EF Core 8+).
var totals = await db.Database
    .SqlQuery<decimal>($"SELECT SUM(Total) FROM Orders WHERE PlacedAt >= {from}")
    .ToListAsync();

// 3. ExecuteSql — non-query DDL/DML. Returns rows affected. Bypasses the tracker.
await db.Database.ExecuteSqlAsync($"EXEC dbo.RebuildOrderSummary @Year = {year}");

// 4. FromSqlRaw / ExecuteSqlRaw — string SQL, YOU own parameterisation.
//    EF Core 10 ships an analyzer that WARNS on concatenation inside these calls.
await db.Database.ExecuteSqlRawAsync(
    "UPDATE Orders SET Status = {0} WHERE Id = {1}", status, id);   // positional params

FromSql takes a FormattableString: every interpolated value becomes a DbParameter, so the interpolated form is the safe form and the "Raw" variants are the ones that need care. That is deliberately the opposite of intuition, and it is worth saying explicitly in an interview because a lot of people assume interpolation means injection.

Constraints on FromSql

  • The SQL must return all columns the entity maps (or all columns of the projected type), with matching names.
  • It cannot contain multiple statements, and on SQL Server the composed form wraps it as a subquery — so no trailing semicolons, no ORDER BY without TOP, and stored procedures are not composable (call them terminally with ToList(), or not through FromSql at all).
  • Results are tracked by default if the type is an entity — add AsNoTracking() for reads.
  • Global query filters are applied when you compose over FromSql, which surprises people both ways.

WHERE Id = {id}" produces WHERE Id = @p0, and injection is impossible. FromSqlRaw takes a plain string, so "... WHERE Id = " + id is concatenated straight into the command text and is a textbook injection. The trap catches people because C# interpolation normally means "build a string". EF Core 10 added an analyzer that warns when you concatenate inside a raw SQL call, which is the kind of thing worth naming: it turns a review-time concern into a compile-time one. The residual risk raw SQL cannot solve for you is identifiers — table and column names cannot be parameters, so dynamic ordering or dynamic column selection must be validated against an allow-list, never interpolated.

Gotcha — stored procedures and composition

FromSql composes by wrapping your SQL in a subquery, and you cannot wrap EXEC. So db.Orders.FromSql($"EXEC GetOrders {id}").Where(...) fails at execution with an opaque SQL error, while the same call without composition works. The workarounds are to terminate immediately with ToListAsync() and compose in memory (accepting the cost), to convert the procedure into a table-valued function or a view, or to use ExecuteSql if you only need the side effect. The wider point for a lead: a codebase where procedures are the interface and EF is the caller is a legitimate architecture — but then map them as functions or views so the composition story is honest, rather than sprinkling FromSql("EXEC ...") and discovering the limits one endpoint at a time.

Expected outcome

The interpolated form sends WHERE Id = @p0 with the whole malicious string as a parameter value, which simply does not match anything. The concatenated form sends the injection verbatim. Solution sketch

The terminal call works; the composed call fails, because EF tries to wrap EXEC in a subquery. Then wrap the procedure's body in a table-valued function, map it with HasDbFunction, and compose against that — full LINQ composition against database-owned SQL. That combination — the database team owns the query, the application composes over it — is a genuinely good architecture for organisations where the DBA owns the SQL, and it is a strong thing to be able to propose.

What are your options for raw SQL in EF Core and when do you use each?

FromSql when I want entities back and want to keep composing — it materialises into the model's types, supports tracking, and further LINQ operators are applied server-side as a subquery. SqlQuery<T>, added in EF Core 8, when the result is a scalar or a type that is not in the model, which used to require a keyless entity type. ExecuteSql for non-queries: calling a procedure for its side effect, a set-based statement, occasional DDL. The "Raw" variants only when the SQL text genuinely has to be assembled at runtime, and then with explicit parameters. Cross-cutting the choice: I keep raw SQL behind named methods on a repository or a query class rather than inline in a handler, so it is discoverable, testable and reviewable, and I comment the reason — a plan, a database feature EF cannot express, or a measured win — because the next reader's default assumption will be that it is legacy.

How does EF protect against SQL injection, and where does it stop?

Everything EF generates from LINQ is parameterised, and the interpolated raw-SQL APIs take a FormattableString so each hole becomes a DbParameter — which means the natural-looking FromSql($"... WHERE Id = {id}") is safe and the intuition that interpolation is dangerous is wrong here. Protection stops in three places. FromSqlRaw/ExecuteSqlRaw with concatenation, which is the real hole; EF Core 10 added an analyzer that warns on concatenation inside those calls, which is a genuine improvement because it moves the check from review to build. Identifiers — table names, column names, sort directions — cannot be parameters in SQL at all, so dynamic ordering or dynamic column lists must be validated against an allow-list. And anything constructed in a stored procedure with dynamic SQL, which EF cannot see into. I would also mention the adjacent EF10 change: inlined constants are now redacted from logs by default, so a value EF chose to inline no longer leaks into log aggregation.

How do you map a database view or a stored procedure result?

A view maps cleanly as a keyless entity type with HasNoKey().ToView("...") — it is fully queryable and composable, never tracked, and migrations do not try to create it, which is exactly right when the DBA owns it. A query that is not a view can be mapped the same way with ToSqlQuery, so callers write LINQ over what is really a fixed SELECT. Stored procedures are the awkward case: they are not composable, so I either call them terminally with SqlQuery<T> or FromSql plus ToListAsync, or — much better where the database team is willing — I ask for the logic as a table-valued function, map it with HasDbFunction, and get full LINQ composition over database-owned SQL. That last pattern is worth proposing explicitly in organisations with a strong DBA function, because it satisfies both sides: the SQL is owned and reviewed centrally, and the application can still filter and page without a round trip per variation.

Would you use EF and Dapper in the same application?

Yes, and I would present it as a deliberate design rather than an inconsistency. EF owns the write model — change tracking, graph consistency, concurrency tokens, migrations — and Dapper owns read paths where the query is hand-written for a reason: a reporting query with window functions, a wide denormalised list, anything where materialising entities is pure overhead. The mechanics keep it honest: Dapper can execute on db.Database.GetDbConnection() with tx.GetDbTransaction(), so both participate in one transaction and one connection, and there is no second connection string or second pool. What I would guard against is drift — two ways to express the same query, or Dapper creeping into the write path where it loses all of EF's guarantees. So I would put a rule around it: Dapper for reads that are explicitly outside the domain model, EF for everything that mutates, and the migration story stays with EF regardless.

What are the composition rules for FromSql, and why do they exist?

When you add LINQ operators after FromSql, EF wraps your SQL as a subquery and applies the operators around it. That imposes the rules: the SQL must be a single statement that is legal as a subquery, so no trailing semicolon, no multiple statements, no EXEC, and no bare ORDER BY without TOP on SQL Server. It must also return every column the target type maps, with matching names, because EF materialises by name. And global query filters are applied on top of your SQL, which is a genuine gotcha in both directions — a soft-delete filter still applies to a hand-written query, which is usually what you want, and occasionally exactly what you do not. If I need something the composition rules forbid, I stop composing: terminate the query and shape the rest in memory, or move the SQL into a view or a table-valued function where composition is native.

How do you expose a database function to LINQ?

With HasDbFunction, or the [DbFunction] attribute, mapping a static .NET method to a database function so the translator emits a call instead of trying to translate the body. Scalar functions map to a method returning a scalar; table-valued functions map to a method returning IQueryable<T> defined with FromExpression, and those are composable — you can filter and page over them like a DbSet. It is the cleanest way to use a database capability EF does not know about without leaving LINQ, and it makes the dependency explicit in the model rather than hidden in a string. Two practical notes: the .NET method body is never executed, so it should throw if called outside a query, which makes accidental client-side use fail loudly; and if the function is not created by EF migrations, someone has to own its DDL — I would create it in a migration with migrationBuilder.Sql so it is versioned alongside the schema.

Under what circumstances is EF the wrong abstraction entirely for a component?

When the component's work is not object-graph-shaped. A reporting or analytics service whose job is aggregation over millions of rows should be writing SQL or using a query engine — materialising entities is pure loss. A high-throughput ingestion path is a bulk-copy problem. An ETL job is a set-based problem. A service that reads and writes a handful of documents by key might be better off with a document store or with Dapper over JSON columns. And anything where the SQL must be reviewed and controlled by a separate team, and cannot vary, is better expressed as procedures or functions with a thin caller. What I would not do is generalise from one of those components to "we should not use EF" — the value EF delivers on the transactional domain model, migrations included, is real, and a system can happily contain both. The framing I would use is that the O/RM is a tool for the part of the system where the object model is the point.

How do you keep raw SQL maintainable as the schema evolves?

Raw SQL does not participate in the model, so nothing tells you when a rename breaks it — that is the actual maintenance cost, and it has to be paid with tests. Every raw-SQL query gets an integration test that runs it against a migrated database, so a schema change that breaks it fails CI rather than production. I keep the SQL in one place per bounded context, not scattered in handlers, and I prefer views and table-valued functions to inline strings, because those are created by migrations and therefore versioned with the schema and validated when they are created. Where the SQL exists to work around an EF limitation, I write down which limitation and which EF version, so it can be revisited — several of my old workarounds became unnecessary at EF Core 7's ExecuteUpdate, EF Core 8's SqlQuery<T> and EF Core 10's LeftJoin. And I would add golden-file tests over the generated SQL of the important LINQ queries too, for the same reason: it turns an invisible translation change into a reviewable diff.

What is the risk of using EF's connection directly?

You are stepping around EF's assumptions, so the failure modes are about lifetime and state. If you open or close the connection yourself, EF's own management gets confused — EF opens and closes around operations unless the connection was already open, in which case it leaves it alone and you own closing it. If you run a command outside EF's transaction, it is not atomic with the save even though it looks adjacent in the code. If you leave a data reader open and then issue an EF query on the same connection, you get a "there is already an open data reader" error unless MARS is enabled, and enabling MARS has its own consequences. And nothing you do that way is visible to the change tracker, so tracked entities can be stale afterwards. None of this makes it wrong — sharing the connection with Dapper is a good pattern — but the discipline is to always pass the transaction explicitly, to not change the connection's open state, and to treat any tracked entities touched by the raw command as suspect.

A DBA insists all data access goes through stored procedures. Can you still use EF, and would you?

Yes, and often it is a reasonable constraint rather than an obstruction — it usually comes from a genuine need for reviewable, permission-controlled SQL. EF can call procedures for reads with FromSql or SqlQuery<T>, and EF Core 7 added mapping of insert, update and delete to stored procedures with InsertUsingStoredProcedure and its siblings so even SaveChanges can go through them. But I would negotiate the shape: composability is the thing you lose, so I would ask for table-valued functions or views for read paths, which give the DBA the same ownership and review while letting the application filter and page without a procedure per variation. And I would be honest about what the constraint costs — every new query needs a database change, which slows delivery — so the conversation should be about the underlying goal, usually security or plan stability, and whether there is a cheaper way to get it. If the answer is no, EF still earns its place for the model, the migrations and the change tracking.

11 Filters, interceptors, cross-cutting

Docs: Global query filters · Interceptors

Soft delete, multi-tenancy, auditing and domain events are the four cross-cutting concerns almost every EF codebase grows. Doing them by convention — "remember to add .Where(x => !x.IsDeleted)" — fails, because the failure is silent and the blast radius is a data leak. EF gives you two structural mechanisms instead: global query filters for reads and interceptors for writes.

Global query filters, and what EF Core 10 fixed

// Before EF10: ONE filter per entity type. Combining soft delete and tenancy meant
// an && expression you could only disable as a unit.
b.Entity<Blog>().HasQueryFilter(x => !x.IsDeleted && x.TenantId == _tenantId);
db.Blogs.IgnoreQueryFilters();      // disables BOTH — including the tenant boundary

// EF Core 10: NAMED filters, disabled individually.
b.Entity<Blog>()
    .HasQueryFilter("SoftDelete", x => !x.IsDeleted)
    .HasQueryFilter("Tenant",     x => x.TenantId == _tenantId);

var withDeleted = await db.Blogs
    .IgnoreQueryFilters(["SoftDelete"])     // tenancy still enforced
    .ToListAsync();

That change is more than ergonomics. Under EF9 and earlier, the admin screen that needed to see deleted rows had to call IgnoreQueryFilters(), which also switched off the tenant predicate — so the "show deleted" toggle became a cross-tenant data leak unless someone remembered to re-add the tenant filter by hand. Named filters make the security-relevant predicate non-optional while the convenience one is optional. If you are on EF Core 10, this is a change worth making on day one.

Interceptors: the write-side hook

public sealed class AuditAndSoftDeleteInterceptor(TimeProvider clock, IUserContext user)
    : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData e, InterceptionResult<int> result, CancellationToken ct = default)
    {
        var ctx = e.Context!;
        foreach (var entry in ctx.ChangeTracker.Entries<IAuditable>())
        {
            if (entry.State is EntityState.Added)
            {
                entry.Entity.CreatedAt = clock.GetUtcNow();
                entry.Entity.CreatedBy = user.Id;
            }
            if (entry.State is EntityState.Added or EntityState.Modified)
            {
                entry.Entity.ModifiedAt = clock.GetUtcNow();
                entry.Entity.ModifiedBy = user.Id;
            }
        }

        // Turn a hard delete into a soft delete, structurally.
        foreach (var entry in ctx.ChangeTracker.Entries<ISoftDeletable>()
                                 .Where(x => x.State == EntityState.Deleted))
        {
            entry.State = EntityState.Modified;
            entry.Entity.IsDeleted = true;
            entry.Entity.DeletedAt = clock.GetUtcNow();
        }
        return base.SavingChangesAsync(e, result, ct);
    }
}

Interview trap — soft delete looks simple and is not

Adding IsDeleted plus a query filter takes ten minutes; the consequences last years. Unique indexes stop working the way you expect, because a deleted row still occupies the unique value — the fix is a filtered unique index (WHERE IsDeleted = 0), which EF supports with HasFilter. Foreign keys still point at soft-deleted parents, so a child can reference something the application considers gone. Aggregates and counts must all remember the filter — the query filter handles LINQ but not raw SQL or reporting tools. Cascade delete no longer cascades, so children must be soft-deleted explicitly. And the data grows forever unless you have a purge story, which interacts with GDPR-style deletion requirements where "soft deleted" is not deleted at all. The lead-level answer names an alternative: for many domains an explicit status field with real business meaning, or an archive table, is a better model than a boolean that pretends rows do not exist.

Gotcha — filters, ExecuteUpdate and the model cache key

Three sharp edges. First, a tenant id captured directly in the filter lambda is evaluated when the model is built; if the model is cached per context type, tenant two gets tenant one's filter. The supported shape is to reference an instance field or property on the context so the expression re-reads it, and if the model itself genuinely differs per tenant you must implement IModelCacheKeyFactory so EF caches one model per tenant. Second, ExecuteUpdate/ExecuteDelete respect query filters (good) but bypass SaveChanges interceptors (bad), so a bulk delete on a soft-deletable entity performs a hard delete — the interceptor that would have converted it never runs. Third, IgnoreQueryFilters() without arguments removes every filter including the tenant boundary; on EF Core 10 always name the filter you mean to disable.

Try it — leak a tenant, then close the hole

1. Build a two-tenant model with a single combined filter (!IsDeleted && TenantId == current) and an admin endpoint that calls IgnoreQueryFilters() to show deleted records. Log in as tenant A and hit it.

Expected outcome

You see tenant B's deleted rows. Now split into two named filters and change the call to IgnoreQueryFilters(["SoftDelete"]); the leak closes and the admin feature still works. Then add SQL Server row-level security driven by SESSION_CONTEXT from a connection interceptor and try to leak it again with raw SQL — the database refuses, which is the point of defence in depth.

2. Add a soft-delete interceptor, then delete a set of rows two ways: tracked Remove + SaveChanges, and ExecuteDeleteAsync.

Solution sketch

The tracked path soft-deletes; the bulk path hard-deletes, because interceptors do not run for set-based operations. That asymmetry is the single most common way a soft-delete design gets violated. The fixes are to expose a domain-level SoftDeleteAsync helper that uses ExecuteUpdateAsync to set the flag, and to add an architecture test that forbids ExecuteDeleteAsync on types implementing ISoftDeletable.

How do you implement soft delete properly, and would you?

Mechanically: a flag or a deleted-timestamp, a global query filter so reads exclude them, a SaveChanges interceptor converting Deleted entries into modifications so nothing has to remember, filtered unique indexes so a deleted row does not block reuse of a unique value, and an explicit decision about children since cascade delete no longer applies. Then the operational parts people forget: a purge job, because the table grows forever; a story for raw SQL and reporting tools, which do not see the filter; and an answer for regulatory deletion, where soft delete is not deletion. Would I? Often not. In many domains the honest model is a status with business meaning — cancelled, archived, superseded — which reads better, indexes better, and does not pretend rows are absent. I would ask what the requirement actually is: undo, audit history, or referential safety. Undo argues for a short-lived flag; audit history argues for a separate history table or temporal tables; referential safety argues for restricting the delete instead.

Design multi-tenancy for a SaaS on EF Core.

I start from the isolation requirement, not the technology. If tenants are few, large and contractually isolated, database-per-tenant is the strongest and simplest to reason about — the cost is migrating N databases and managing connection pooling, and EF handles it with a connection string resolved per request. For many small tenants, a shared database with a TenantId discriminator is the only economical option, and then the design is defence in depth: a named query filter on every tenant-owned entity so reads are scoped by default, a SaveChanges interceptor that stamps TenantId on inserts so writes cannot land in the wrong tenant, and — the part that actually makes it safe — row-level security in the database driven by SESSION_CONTEXT set from a connection interceptor, so even raw SQL and a forgotten filter cannot cross the boundary. On EF Core 10 I would use named filters specifically so that disabling soft delete does not disable tenancy. And I would write tests that assert cross-tenant access fails, because this is the one area where a silent bug is a breach.

How do global query filters interact with Include, ExecuteDelete and raw SQL?

They apply to every query root of the filtered entity type, and that includes navigations pulled in by Include — so including posts on a blog will not surface soft-deleted posts. They also apply when you compose LINQ over FromSql, which surprises people in both directions. ExecuteUpdate and ExecuteDelete do respect filters, since they are built from an IQueryable. What filters never touch is the write path: SaveChanges will happily update an entity that the filter would hide, and Find returns a tracked entity regardless. Raw SQL executed with ExecuteSql, or anything running outside EF such as a reporting tool, sees everything — which is the argument for enforcing the important predicate in the database with row-level security rather than only in the model. There is also a modelling wrinkle worth naming: filtering a principal makes a required navigation look optional, and EF warns about it; the resolution is to filter both ends consistently.

When do you use an interceptor rather than overriding SaveChanges?

Overriding SaveChanges on the context is fine for one concern in one application and it is easy to read. I move to interceptors when there is more than one concern, when the concerns need dependencies the context should not have, or when I want the behaviour to apply to several contexts. Interceptors compose — audit, soft delete, outbox, event dispatch as separate registered classes — get their dependencies from DI at registration time, and can be added or removed per environment, which an override cannot. They also cover surfaces an override does not: command interception for tagging or counting, connection interception for tokens and session context, materialisation interception for post-load work. The one thing I insist on either way is that this logic is structural rather than advisory — if audit columns depend on every developer remembering, they will be wrong within a month.

How do you dispatch domain events with EF?

Collect events on the aggregate as it is mutated, then dispatch them around SaveChanges — and the interesting question is which side. Dispatching before the save, inside SavingChanges, lets handlers make further changes that join the same transaction, which is right for events that must be atomic with the aggregate. Dispatching after a successful save, in SavedChanges, is right for effects that should only happen if the write committed, but those effects are then outside the transaction and can be lost if the process dies — which is exactly why anything leaving the process should go through a transactional outbox written in the same save rather than being dispatched directly. I also clear the events from the aggregates as I collect them so a retry does not double-dispatch, and I keep handlers off the hot path where I can. The failure I have seen most is dispatching after commit and sending an email for an operation that later gets compensated; the outbox plus idempotent consumers is the answer that survives contact with production.

Your audit columns are missing for some rows. How do you find out why?

I would enumerate the paths that write to the database and check which ones bypass the mechanism. If audit is done in a SaveChanges interceptor, then ExecuteUpdate and ExecuteDelete skip it entirely, as does any raw SQL, any Dapper write, any stored procedure, and anything done by a migration or by a DBA. That is almost always the answer, and the giveaway is that the missing rows correlate with one feature — usually a bulk operation somebody optimised. The fixes are layered: expose helpers so the bulk path sets the audit columns explicitly, add an architecture test forbidding raw bulk operations on auditable types, and — the durable fix — put a default constraint or a trigger in the database for the columns that must never be null, so the guarantee does not depend on the application. If the audit trail is a compliance artefact rather than a convenience, I would push for temporal tables or change data capture instead, because application-level auditing is only as good as the least careful write path.

What is IModelCacheKeyFactory and when do you need it?

EF caches one model per DbContext type, keyed by that type. IModelCacheKeyFactory lets you widen the key so several models can coexist for the same context type. You need it when the model genuinely differs per instance — schema-per-tenant, where table names include the tenant; a design where entity configuration varies by feature flag; or a filter that cannot be expressed as a re-read of context state. What you should not use it for is a tenant id in a query filter, because that does not need a different model: referencing a context property inside the filter lambda makes EF read the current value per query, and one cached model serves every tenant. Getting that wrong in the other direction is the bug — a captured local variable is baked in at model-build time, so the first tenant's id is used for everyone. And if you do implement a per-tenant key, remember the memory consequence: one compiled model and one query cache per tenant, which for thousands of tenants is not viable.

How do you tag EF queries so you can trace them back to code?

TagWith("...") puts a comment in the generated SQL, and TagWithCallSite() adds the file and line — so the query text in Query Store, in an extended events trace or in a DBA's slow-query report identifies the source. That is one of the highest value-per-effort things you can do in a large system, because the usual failure is a DBA arriving with a slow query nobody can locate in the codebase. Beyond that I add correlation via a DbCommandInterceptor that appends the request or trace id as a comment, so a slow statement links to a distributed trace. On the observability side, EF emits events through DiagnosticSource and metrics that dotnet-counters and most APM agents pick up automatically, giving command duration, failures and connection stats. The caution: tags change the SQL text, so a tag that varies per request creates a distinct plan-cache entry — keep tags static and put the varying part in a comment only where the plan-cache cost is acceptable.

How would you enforce a data-isolation invariant so it cannot be bypassed?

By making it true in more than one layer and by testing the boundary rather than the implementation. Layer one is the model — a named query filter so ordinary LINQ is scoped by default and an interceptor that stamps the tenant on insert. Layer two is the database — row-level security, or separate databases, so a forgotten filter, a raw SQL query, an ad-hoc report or a bug cannot cross the line. Layer three is the tests — an integration test that authenticates as tenant A and asserts that every endpoint returns nothing for tenant B's ids, generated from the route table so new endpoints are covered automatically. Then I remove the footguns: ban parameterless IgnoreQueryFilters() with an analyzer or a code-review rule, and prohibit context fields holding per-request state when pooling is on. The principle I would state is that an invariant enforced only by developer discipline is not an invariant, and for tenancy the cost of being wrong is a breach notification, so it deserves the belt-and-braces treatment.

What are the risks of putting business logic in interceptors?

Invisibility and ordering. Logic in an interceptor does not appear at the call site, so a developer reading a handler cannot see that saving also writes an outbox row and rewrites deletes — which is exactly why it is reliable, and exactly why it is confusing when it goes wrong. Multiple interceptors run in registration order and can interfere: one converting deletes to updates changes what a later one sees in the change tracker. They run inside the save, so anything slow or failure-prone there fails the whole transaction, and an exception in an interceptor surfaces as a save failure with a confusing stack. And they are easy to bypass, since set-based operations and raw SQL never reach them. My rules: interceptors do infrastructural, idempotent, fast work — stamping columns, converting states, writing an outbox row — and never make business decisions or call external services. Anything that a reader would be surprised by gets documented in the context class, and the behaviour gets its own tests.

Interview trap — the in-memory provider

It is the single most common wrong answer to "how do you test EF?", and the reasons are specific rather than aesthetic. The in-memory provider is a LINQ-to-Objects store: it does not enforce foreign keys, unique indexes, required columns, string lengths or decimal precision, so a test suite passes on data the real database would reject. Its query translation is different, so queries that throw in production ("could not be translated") succeed in tests, and queries that work in production can behave differently — most notably around null semantics and ordering. Transactions are a no-op, so anything testing rollback proves nothing. It cannot run raw SQL, migrations, concurrency tokens or provider functions. Microsoft's own testing documentation recommends against it and points to SQLite or a real database. The credible answer is: unit-test logic without a database at all, and integration-test everything data-shaped against the real engine in a container — it costs seconds and it actually tests the thing most likely to be wrong.

Gotcha — logging that leaks, and logging that lies

EnableSensitiveDataLogging puts parameter values in the log. On a users table that is names, emails and anything else you query by, sprayed into log aggregation and retained for a year. It is a development switch, and I would enforce that with configuration that cannot turn it on outside development, not with a code review. The mirror-image issue: EF Core 10 now redacts constants that EF inlines into SQL, replacing them with ? — a genuine security improvement, and also a reason the logged SQL is no longer byte-identical to what executed, so do not spend an afternoon hunting a discrepancy that is by design. Third: the SQL EF logs is the SQL EF sent, not the plan the database chose, so a query that looks fine in the log and is slow in production is a plan problem and the next stop is Query Store, not the EF log.

Try it — build the fixture you will reuse for years

1. Stand up a Testcontainers-backed SQL Server fixture, run MigrateAsync() once per collection, and isolate tests by wrapping each in a transaction that is rolled back (or by resetting with Respawn). Port three existing tests to it.

Expected outcome

Startup costs a few seconds once; each test then runs in tens of milliseconds. You immediately get things the in-memory provider never gave you: constraint violations surface as real exceptions, migrations are exercised on every run, and provider-specific SQL is actually executed. Note the trade-off honestly — the suite now needs Docker in CI, which is a real constraint in some environments and the main legitimate reason teams reach for SQLite instead.

2. Add a snapshot test over ToQueryString() for your five most important queries, and a CI step that generates a migration and fails if it is non-empty.

Solution sketch

The snapshot test turns an EF upgrade from a gamble into a code review: when EF Core 10 changed collection parameterisation and parameter naming, those diffs would have appeared as a reviewable change instead of a production plan regression. The empty-migration check catches model/snapshot drift and unmerged migrations before they reach anyone else. Two small tests, both of which pay for themselves the first time somebody upgrades a package.

How do you test code that uses EF Core?

I split by what is being proven. Pure domain logic gets unit tests with no database, which usually means the logic should not be inside a query in the first place. Anything whose correctness depends on SQL — queries, filters, migrations, concurrency, constraints — gets an integration test against the real engine in a container, because the provider is the component most likely to surprise me and swapping it out removes exactly the risk I am trying to cover. Isolation between tests is either a transaction rolled back per test or a fast reset with a tool like Respawn; both are much faster than recreating the database. I explicitly avoid mocking DbSet, which is brittle and tests nothing, and I avoid the in-memory provider, which Microsoft's own documentation advises against because it does not enforce relational constraints and translates queries differently. Where Docker is genuinely unavailable, SQLite is the pragmatic compromise, and I would list what it cannot cover so nobody mistakes a green suite for coverage of SQL Server behaviour.

Why is the in-memory provider a bad testing strategy?

Because it is not a database. It does not enforce foreign keys, unique indexes, required columns, maximum lengths or numeric precision, so tests pass on data production would reject. Its LINQ translation is different — it is LINQ to Objects — so a query that throws "could not be translated" in production passes in tests, and null-ordering and comparison semantics differ. Transactions do nothing, so rollback tests are theatre. It cannot execute raw SQL, run migrations, honour concurrency tokens or evaluate provider functions. The net effect is a suite that is green for reasons unrelated to whether the software works, which is worse than no suite because it creates confidence. Microsoft's testing guidance says as much and points at SQLite or a real database. The only use I would defend is a fast smoke test of wiring in a project that has real integration tests elsewhere, and even then SQLite is barely slower and much more honest.

How do you catch performance regressions in EF before production?

Three gates, all cheap. A command-counting interceptor in integration tests with per-test assertions, so an accidental N+1 or a reintroduced lazy load fails the build with a number. Snapshot tests over ToQueryString() for the queries that matter, so a translation change — including one caused by an EF upgrade — appears as a reviewable diff; that would have caught EF Core 10's change of collection parameterisation before it changed a plan in production. And a benchmark or load test on the two or three endpoints that carry the traffic, run against a database with production-like volume, because most EF performance bugs are invisible at a thousand rows and obvious at ten million. Beyond the gates, in production I want per-query metrics and tagged SQL so a slow statement maps back to code, and Query Store or its equivalent so plan regressions are visible as plan regressions rather than as "the site is slow".

What do you monitor in production for an EF-based service?

At the application level: query duration distributions per endpoint, commands per request (a rising count is the N+1 tripwire), save-changes duration and failure rate, connection-pool exhaustion and wait times, and the compiled-query cache hit rate, which drops when query shapes are exploding. EF publishes these through DiagnosticSource and event counters that most APM agents collect automatically. At the database level: the top queries by total duration, plan regressions, blocking and deadlock counts, and index usage. The joining piece is tagging — TagWith or TagWithCallSite so a slow query in the database's own tooling names the code that issued it — plus a correlation id in the command comment so a slow statement links back to a trace. I also alert on things that only EF can tell me: a spike in DbUpdateConcurrencyException, which usually means a hot row and a design problem, and retry counts from the execution strategy, which are a leading indicator of database trouble.

How do you test migrations?

Three levels. Every integration test run applies migrations to a fresh container database, which proves they are internally consistent and that the final schema matches the model — and a CI step generates a migration and fails if it is non-empty, which proves the snapshot and model agree and catches unmerged branches. Then, separately, a restore of a production-sized copy with the idempotent script applied and timed, because correctness is rarely the risk and duration usually is; a column-type change that rewrites a 200-million-row table is not a bug, it is a maintenance window. Then a compatibility check for zero-downtime: run the previous version's integration tests against the new schema, which is what proves the expand step is genuinely backward-compatible. What I do not do is test Down methods extensively, because I do not intend to use them — the rollback strategy is roll-forward with a compensating migration, and pretending otherwise gives false confidence.

How do you handle EF logging so it is useful and safe?

Structured logs at information level for commands in development, and in production either sampled or restricted to slow commands and failures, because logging every SQL statement at volume is both expensive and noisy. EnableSensitiveDataLogging never leaves development, and I would enforce that in configuration rather than trusting review, because parameter values are exactly the personal data you do not want in log aggregation. I use ConfigureWarnings to promote specific EF events to exceptions in development and CI — the multiple-collection-include warning, lazy-loading events if lazy loading is meant to be off — so the framework's own advice becomes a build failure rather than a line nobody reads. In production the log is a starting point rather than the whole picture: EF logs what it sent, so a query that looks fine and runs slowly is a plan question. And on EF Core 10 there is one behavioural detail worth knowing before it confuses somebody: constants EF inlines are redacted to ? in logs by default, so the logged text is deliberately not identical to what executed.

Something is deadlocking in production and EF is in the stack. How do you approach it?

Deadlocks are a database phenomenon, so I start with the deadlock graph, not the C# — it names the resources and the two statements, and that usually identifies the pattern immediately. The common EF-adjacent shapes are: two transactions touching the same rows in different orders, which is a code-ordering fix; a long-running transaction holding locks while doing application work or a network call, which is a transaction-scope fix; lock escalation from a large ExecuteUpdate or a big SaveChanges batch, which argues for chunking; and missing indexes causing scans that take far more locks than necessary, which is an indexing fix and is more often the cause than people expect. On the EF side I check whether a retrying execution strategy is configured, since deadlock victims are retryable and a bounded retry with jitter converts an error into latency — but I would treat that as a mitigation, not a fix, and I would alert on the retry rate so it does not quietly mask a worsening problem. Then I would reduce the transaction's footprint: shorter transactions, smaller aggregates, and set-based statements instead of read-modify-write where the semantics allow.

How do you introduce EF Core to a team that is sceptical of ORMs?

By agreeing with their objection and scoping the tool. The scepticism is almost always earned — someone has been burned by lazy loading, invisible N+1 or generated SQL nobody could read — so I would not argue that those things do not happen. I would show the SQL: turn on logging, put ToQueryString() in front of them, and demonstrate that EF's output is inspectable and testable, which is what they actually care about. Then I would draw explicit boundaries — EF for the transactional domain model and migrations, hand-written SQL for reporting and the two queries that need tuning — so nobody feels forced into an all-or-nothing choice. Then I would put in the guardrails that make the failure modes impossible rather than discouraged: lazy loading off, command-count assertions in tests, snapshot tests over generated SQL, no Include chains on read paths. And I would pick one bounded context, ship it, and let the migration story and the change tracking sell themselves — the write path is where EF is unambiguously better than the alternative, and that is the argument that lands.

What would you put in a code-review checklist for EF changes?

Short and specific, because a long checklist is not used. Does this read path project to a DTO rather than Include entities? Does any query run inside a loop? Are there two collection Includes without a considered split-query decision? Is the entity being updated loaded first, rather than Update() on a mapped DTO? Does anything user-editable have a concurrency token? Does a new ExecuteUpdate/ExecuteDelete bypass an interceptor that matters — audit, soft delete, outbox — and is it inside the right transaction? Does a new migration contain a rename, a drop, or a long-running data change that breaks zero-downtime? Is any IgnoreQueryFilters() call naming the filter it means to disable? Is raw SQL parameterised, and does the analyzer pass? Most of these should eventually become tests or analyzers rather than checklist items — the checklist is the staging area for automation, not the destination.

How do you keep an EF codebase current across annual major releases?

Treat the upgrade as a scheduled, small, boring event rather than an epic. Concretely: sit on LTS unless there is a reason not to, and put the support end dates on the roadmap — EF Core 8 and 9 both end on 10 November 2026, which is a fact that should be in a planning document rather than in someone's memory. Always take the latest patch of the current major. Before each major, read the breaking-changes page as a team and classify each item as "does not apply", "mechanical fix" or "needs testing"; the mechanical ones are usually an afternoon. Have the safety net in place beforehand: snapshot tests over generated SQL, command-count assertions, and a load test on the two endpoints that matter, because the risky changes are behavioural rather than compile-time — EF Core 10's collection parameterisation and parameter naming are the current example, and both are invisible to the compiler. Then upgrade in its own release, not bundled with features, so if something regresses the bisect is trivial.

13 The big Q&A

Everything important that is not one of the twelve building blocks: the decisions, the security surface, the operational reality, and the questions that are really about judgment.

Architecture & ecosystem decisions

How does EF fit into a CQRS design?

Naturally, and usually with two different shapes on the two sides. The command side is exactly what EF is best at: load an aggregate, mutate it, SaveChanges once, with change tracking, concurrency tokens and a transactional outbox doing the heavy lifting. The query side does not want entities at all — it wants projections straight to read DTOs, which means Select against the same DbContext, or a second read-only context registered with NoTracking as the default, or hand-written SQL and Dapper where the query is genuinely a report. I would not automatically add a separate read store: separate read models in the same database, as views or projections, buy most of the benefit without eventual consistency. The mistake I would call out is treating CQRS as a mandate for two databases and a message bus; the pattern is about separating the models, and EF supports that inside one database perfectly well. Where I do split stores, the projector becomes another consumer of the outbox, and the consistency story has to be explicit in the UI, not hidden.

Would you use EF Core with Cosmos DB or another non-relational store?

Yes, when the team's centre of gravity is EF and the workload fits the document model, because the provider is genuinely good now — EF Core 9 overhauled its LINQ translation, partition-key handling and pagination, and EF Core 10 brought vector similarity search out of preview, added full-text search and Rrf hybrid ranking, and stopped throwing when a document lacks a value for a newly-required property. EF Core 11 goes further with complex types, transactional batches by default, bulk execution and a System.Text.Json-based serialiser replacing Newtonsoft. What I would set expectations about is that the abstraction leaks by design: no joins, no cross-partition transactions, request units rather than query cost, and partition-key design mattering more than anything EF does. So the honest framing is that EF makes Cosmos familiar, not relational — if the team designs Cosmos containers as if they were tables, the provider will not save them, and the failure will look like a cost problem rather than a modelling problem.

Database-per-service in microservices — how does that change your EF choices?

It mostly simplifies them, because the hardest EF problems are cross-aggregate ones and a service-owned database makes the aggregate boundary and the schema boundary the same line. Each service owns its context, its migrations and its deployment of them, and nobody queries anybody else's tables. The consequences to plan for: joins across services become API calls or replicated read models, so I expect an outbox and projections rather than a join; transactions across services become sagas with compensating actions, which is a design commitment, not a library choice; and reference data gets duplicated deliberately with a refresh mechanism. On the EF side specifically, I would keep each service's model small enough that model building is cheap, use a single provider per service so migrations stay simple, and resist a shared "common entities" package, because that reintroduces the coupling the boundary was meant to remove. The thing I would flag as underestimated is operational: N services means N migration pipelines and N sets of database credentials to manage.

How do you decide the aggregate boundary, and what does EF have to do with it?

The boundary is the consistency boundary: what must be transactionally correct together, and what can be eventually consistent. EF then makes that concrete in ways that give useful feedback. If saving one aggregate requires loading thousands of children, the aggregate is too big and you will feel it as slow saves and lock contention. If two users routinely conflict on the same aggregate root's concurrency token while editing unrelated parts, it is too coarse and the token is telling you so. If you find yourself needing a transaction across two aggregates for an invariant, either the boundary is wrong or the invariant should become eventually consistent with a compensating action. I use those symptoms as design signals rather than tuning them away — a concurrency conflict rate is data about the model. And I keep the mapping honest: value objects as complex types, children owned by the root with cascade behaviour that matches the domain, and references to other aggregates as plain id properties rather than navigations, which stops a query from silently walking outside the boundary.

What is your position on the repository pattern over EF?

A generic IRepository<T> over EF is usually a net negative: DbSet is already a repository, DbContext is already a unit of work, and the generic wrapper ends up exposing IQueryable anyway, so it abstracts nothing while adding indirection and a place for bugs. What I do find valuable is a per-aggregate repository with intention-revealing methods — GetForFulfilment(orderId) that knows which navigations to include and whether to track — because it puts the loading strategy in one reviewable place, which is exactly the decision that goes wrong. The strongest genuine argument for a repository is testability, and I would answer it with a container-backed integration test instead, which tests more and mocks less. The argument that it lets you swap the ORM I do not accept: nobody swaps, and if they did the queries would need rewriting anyway. So: no generic repository, yes to named query methods, and be ready to defend that with the trade-off rather than as a rule.

Security

What does the security review of an EF data layer look like?

Six things, in order of how often they are wrong. Connection identity: the application should authenticate with a managed identity or a workload identity rather than a password in configuration, and its database principal should have DML but not DDL rights — which is the real reason migrations do not run at startup in production. Injection surface: every FromSqlRaw/ExecuteSqlRaw call reviewed, EF Core 10's concatenation analyzer enabled and its warnings treated as errors, and any dynamic identifier validated against an allow-list because identifiers cannot be parameters. Logging: EnableSensitiveDataLogging off outside development, enforced by configuration. Isolation: tenant filters named so IgnoreQueryFilters cannot switch tenancy off, and row-level security in the database as a second layer. Over-posting: entities never bound directly from request bodies. And data at rest: which columns are encrypted, and whether the encryption is compatible with the queries we run.

How do you prevent over-posting / mass assignment with EF?

By never letting a request body become a tracked entity. Model binding directly onto entity types means any property the attacker names is set, and if the code then calls Update() or saves a tracked instance, they have written to columns the UI never exposed — role, tenant id, price, status. So: request models are separate types containing exactly the fields the endpoint accepts; mapping to the entity is explicit and assigns named properties; and the update path loads the entity first and applies only those fields, which is the same load-then-map discipline that gives correct partial updates and concurrency. For belt and braces I mark infrastructure fields as shadow properties or set them exclusively in an interceptor, so they are not settable from application code at all. And I would put it in the review checklist as a security item rather than a style one, because the failure is privilege escalation and it looks like ordinary code.

How do you handle encrypted or sensitive columns?

The first question is whether the column needs to be queryable, because that decides the mechanism. Transparent Data Encryption protects the files and nothing else — it is table stakes, not a control against application-level compromise. SQL Server Always Encrypted encrypts in the client driver, so the database never sees plaintext; deterministic encryption allows equality searches and randomised allows none, and EF works with it because the encryption happens below EF in Microsoft.Data.SqlClient — the constraint is that you lose ranges, LIKE and sorting on those columns, which is a schema design decision, not an EF one. Application-level encryption via a value converter is possible and I would use it only for columns that are never filtered on, with keys in a managed key store, because a converter cannot help the database index ciphertext. For anything that must be searchable and secret, the usual answer is a separate deterministic hash or blind index column. And I would keep the key management out of the application and be explicit about who can decrypt, since that is the control auditors actually ask about.

Where do connection strings and credentials belong?

Not in the application, ideally not anywhere as a secret at all. The modern shape is a connection string with no password, authenticating with a managed identity or workload identity, so there is nothing to rotate or leak; where that is not possible, the secret lives in a secret store and reaches the process through configuration, never in source control or an appsettings file, and it is rotated on a schedule the application tolerates because it reconnects. Two EF-specific notes. The application's principal should not have DDL rights, which is why the migration step runs with a different, elevated identity in the pipeline — that is a security argument for not calling Migrate() at startup, independent of the concurrency one. And EF Core 10 now injects an Application Name into the connection string if you have not set one; that is benign but it changes the string SqlClient uses to key its connection pool, which can split pools and, inside a TransactionScope, escalate to a distributed transaction — so setting Application Name explicitly is now good practice as well as good diagnostics.

Performance & debugging in the real world

Requests are timing out and the database looks idle. What do you check?

That pattern points away from the database and at the connection pool or the thread pool. Connection-pool exhaustion produces exactly this: requests waiting for a free connection while the server has capacity, and the tell is a timeout message about obtaining a connection from the pool rather than about a command. Causes are contexts or connections not being disposed, a streaming query holding a connection open across slow work, too small a Max Pool Size for the concurrency, or a long-running transaction pinning connections. The other half is thread-pool starvation from sync-over-async — a .Result or a .Wait() somewhere on the request path, or synchronous lazy loading, which has no async form at all — and the tell there is high queue length with low CPU. I would look at EF's own counters for active contexts, at connection-pool metrics, and at a dump or a thread-pool starvation detector before touching a single query, because if this is the problem then tuning SQL will change nothing.

A query got 10× slower after a deploy and the SQL is unchanged. What happened?

If the SQL text is genuinely identical, the plan changed, and the usual causes are parameter sniffing after a plan cache eviction or a statistics update, data volume crossing a threshold where the optimiser prefers a different join, or an index change. Query Store makes this a five-minute investigation: it shows the plan history for the query and lets you force the previous plan as an immediate mitigation while you fix the cause. But I would check the "unchanged" claim carefully, because EF can change SQL without any code change — an EF upgrade is the classic case, and EF Core 10 in particular changed both parameter naming and the default translation of collection Contains, either of which alters the text and therefore the plan cache entry even when the query's meaning is identical. That is precisely why I want snapshot tests over generated SQL: they turn "the SQL is unchanged" from an assumption into a fact.

How do you find the actual bottleneck when everything is "a bit slow"?

By refusing to optimise anything until the time is attributed. I want a distributed trace of a representative request broken into application CPU, EF processing, network wait, and database execution, because the four have entirely different fixes and teams routinely guess wrong between them. Commands per request tells me about round trips; rows returned versus entities materialised tells me about explosion and over-fetching; database-side top-queries-by-total-duration tells me where the aggregate cost lives, which is often a fast query executed a hundred thousand times rather than a slow one. Then I fix the largest attributed cost, measure again, and stop when it is good enough rather than when I run out of ideas. The cultural part matters as much as the technical one: I would publish the numbers, because the alternative is a team applying AsNoTracking everywhere and believing they have done performance work.

How do you handle a table that has grown beyond what EF queries comfortably?

The table size is rarely the problem; the access pattern is. So first I check that queries are seeking on indexed predicates and returning bounded result sets — pagination that is keyset rather than offset, filters that are sargable, and no accidental scans from a value conversion or a CAST the translator inserted, which EF Core 11 got better at stripping. Then the structural options in order of disruption: an appropriate index or a covering index; partitioning or a filtered index if the queries are naturally time-bounded; archiving cold rows to a separate table with a view or a mapped read model over the union; and only then splitting the table or moving the workload. EF-specific contributions are modest but real: project instead of loading entities, use ExecuteUpdate/ExecuteDelete for maintenance operations so you never materialise millions of rows, and chunk any bulk work so transactions stay short. And I would ask whether the queries hitting the big table are actually reporting queries that belong somewhere else entirely.

Tooling and ecosystem

How do you set up EF tooling so it is not a source of friction?

Pin the tool version to the EF version and install it as a local tool in the repository with a dotnet-tools.json manifest, so everyone and CI use the same one and nobody has a global install from two majors ago. Keep a design-time factory (IDesignTimeDbContextFactory<T>) so dotnet ef does not have to boot the whole application host to find a connection string, which is the usual cause of "it works on my machine". Document the exact command with the right --project and --startup-project, and on EF Core 11 replace that with a .config/dotnet-ef.json file so the options are checked in rather than remembered. On EF Core 10 specifically, remember that multi-targeted projects now require --framework, which is a breaking change that presents as a confusing CI failure. And add the CI gate that generates a migration and fails if it is non-empty, because that single check catches most of the drift the tooling would otherwise let through.

When do you scaffold from an existing database, and how do you keep it sane?

When the database is the source of truth and someone else owns it — a legacy system, a DBA-controlled schema, or a database shared with applications you do not control. dotnet ef dbcontext scaffold generates the model, and the discipline is to treat the generated files as generated: regenerate rather than edit, put hand-written configuration and any domain behaviour in separate partial classes or configuration classes, and keep the generation command in a script so it is reproducible. The check that makes it trustworthy is a CI job that re-scaffolds against a current schema and fails on drift, so you learn about a column change from the build rather than from a customer. Two practical notes: scaffolding produces a model that mirrors the schema faithfully, including things you would not have designed, so expect to add configuration for enums, value objects and naming; and if you later want to take ownership of the schema, the transition is to baseline — generate an initial migration that matches the current database and mark it applied — rather than to let EF try to create everything.

How do migrations fit into a modern deployment pipeline, including Aspire and containers?

As an explicit, ordered step with its own identity. The build produces the artifact — an idempotent SQL script or a migration bundle — and the release applies it before the application rollout, using a database principal that has DDL rights the application does not. In containerised environments where a script cannot be handed to a DBA, a bundle or a short-lived migration job or init container does the same job, and the important property is that it runs exactly once and the rollout waits for it. Aspire is the case where startup migration is most tempting, and the pattern I prefer even there is a dedicated migration project or worker that Aspire orchestrates, rather than the serving application migrating itself. EF Core 9's migration lock makes concurrent startup migration survivable, and EF Core 11's database update --add makes runtime-compiled migrations possible for those environments, but neither changes my default, because the permissions argument stands regardless of the concurrency one.

Which third-party parts of the EF ecosystem are worth knowing?

Npgsql is the one that matters most — the PostgreSQL provider is community-maintained, ships close behind EF's own releases, and supports things the SQL Server provider does not, like native arrays and jsonb; if you are on PostgreSQL, its documentation is as important as EF's. For bulk operations, the various EF bulk-extension libraries wrap SqlBulkCopy and MERGE over the EF model, and they are worth it when you need bulk semantics with entity types rather than hand-rolling; I would evaluate licensing and maintenance carefully, since some are commercial and they sit on the write path. Testcontainers and Respawn are effectively standard for integration testing. Beyond that I am deliberately conservative: an ORM sits on the critical path of everything, and each additional library that hooks into it is something you must upgrade in lockstep every November. The question I ask before adopting is what happens if it stalls for a release — if the answer is "we cannot upgrade EF", that is usually a no.

Legacy and migration reality

You inherit a codebase with EDMX, ObjectContext and stored procedures everywhere. What now?

First, stabilise and understand: get it building, get characterisation tests around the behaviour that matters, and confirm EF6.5.2 is the version in use since only the latest patch is supported. Then decide whether moving is worth it, in business terms — usually the driver is that the host must move to .NET 8 or later, and the useful fact is that EF6 runs on modern .NET, so the host port and the ORM port can be separate projects. For the ORM port, EDMX has no EF Core equivalent, so the model is reverse-engineered to code-first with scaffolding and then reconciled by hand. Stored procedures mostly survive: EF Core can call them, and EF Core 7 added mapping insert, update and delete to procedures with InsertUsingStoredProcedure and friends, so a procedure-centric design is portable. I would go strangler-style, one bounded context at a time against the same database, with both ORMs coexisting during the transition, and I would insist on SQL-level characterisation tests first, because the silent differences — client evaluation, lazy loading, delete behaviours — are the ones that hurt.

How do you upgrade a system that is four EF majors behind?

One major at a time, each in its own release, with the test suite green in between — skipping intermediate versions means debugging four releases' worth of behavioural changes at once with no way to bisect. Before starting I put the safety net in place: integration tests against a real database, snapshot tests over the generated SQL of the important queries, and a load test on the two endpoints that carry the traffic, because the dangerous changes are behavioural and invisible to the compiler. For each hop I read the breaking-changes page and classify every item. The ones I expect to matter across that range: EF Core 3.0's end of silent client evaluation, which surfaces as runtime exceptions in code paths nobody exercised; EF Core 8's switch of primitive collections to JSON parameters; and EF Core 10's switch again to multiple scalar parameters plus the parameter-name simplification, which invalidates cached plans and can regress Contains-heavy queries. Also worth planning around: EF Core 10 requires .NET 10, so the runtime upgrade is coupled, and the EF tooling now needs --framework on multi-targeted projects.

Half the team writes EF and half writes stored procedures. How do you resolve that?

By separating the technical question from the ownership question, because it is usually the latter. If the procedures exist because a DBA function owns and reviews SQL, that is a legitimate constraint and the resolution is a shape that satisfies it — views and table-valued functions for reads, which the database team owns and the application composes over, and EF for the write model and migrations. If they exist because of a belief that procedures are faster, that is testable and generally false for the kinds of queries EF generates; plan stability is the real historical argument and Query Store addresses it better than procedures do. If they exist because of history, then I would agree a boundary going forward rather than rewriting: new work uses EF, existing procedures stay until there is a reason to touch them. What I would not do is let both patterns cover the same operations, because two ways to update an order is how invariants get violated. And I would write the decision down with its rationale, since the cost of this disagreement is mostly re-litigation.

Judgment and scenarios

You are on call. Database CPU is at 100% and it started an hour ago. Go.

Stabilise before diagnosing. I look at the top queries by CPU in Query Store or the equivalent, which almost always names the culprit in a minute, and I check what changed an hour ago — a deploy, a migration, a batch job, a traffic shift, a statistics update. The fastest mitigations, in order: force a known-good plan if it is a plan regression; disable or throttle the offending feature or job if it is new; add the obviously missing index if the plan shows a scan and the write cost is acceptable; scale up if the platform allows and nothing else is available. Then the EF-side questions: did we just deploy an EF version change that altered a translation, is a bulk operation running as a tracked loop, is something issuing N+1 at a rate proportional to a list that just got bigger. Afterwards, the follow-up that matters is the guard — a command-count assertion, a snapshot test, an alert on query duration — because an incident that produces only a fix will recur with a different query.

What do you look for when reviewing a pull request that touches data access?

I read the generated SQL in my head and ask what happens at 100× the test data. Concretely: is a read path loading entities when it should project; is there a query inside a loop; are two collection Includes going to explode; is an update loading the entity first or blindly calling Update() on a mapped DTO; does anything user-editable have a concurrency token; does a new ExecuteUpdate or ExecuteDelete skip an interceptor that provides audit, soft delete or an outbox row, and is it in the right transaction; does the migration contain a rename, a drop, or a long data change that breaks the rollout; is IgnoreQueryFilters naming the filter it disables; is raw SQL parameterised. Beyond the checklist I look for the decision that was not made explicit — a loading strategy chosen by accident, a transaction boundary that drifted — and I ask for a comment rather than a change, because the value is in the next reader knowing it was deliberate.

A senior engineer wants to adopt complex types and JSON columns across the domain model. How do you respond?

I would agree with the direction and disagree with the scope. Complex types are the right modelling tool for value objects and the documented replacement for owned entity types, and EF Core 10 completed them enough — optional types, JSON mapping, structs, ExecuteUpdate support — that new work should use them. So: adopt complex types broadly, yes. JSON columns are a different decision and belong only where the data is genuinely part of the aggregate and nothing needs to join to it, because you give up foreign keys, easy indexing and some translations, and on SQL Server you cannot even DISTINCT over a JSON array. I would also want the migration risk understood before anyone starts: converting owned types to complex types changes column names, EF Core 10 changed nested complex-type column naming to full paths and started uniquifying clashes, and with UseAzureSql or compatibility level 170 the first migration will alter every existing JSON column to the native json type. So the plan is: complex types for new aggregates now, a scheduled conversion for existing ones with the migration reviewed by hand, and JSON case by case.

How do you teach a team to think about EF rather than memorise rules?

By making the SQL visible, constantly. Most EF mistakes come from writing C# without a picture of the statement it becomes, so the highest-leverage thing I can do is put that picture in front of people: logging on in development, ToQueryString() in the debugger, snapshot tests where the SQL is part of the code review. Then I teach the three-part model — model, query pipeline, change tracker — because almost every question decomposes into which part is involved, and someone who has that can derive the answer to a question they have never seen. Then I replace rules with feedback: instead of "do not cause N+1", a test that fails on query count; instead of "remember the audit columns", an interceptor; instead of "be careful with migrations", a CI check. Rules degrade as the team changes; feedback does not. And I would pair on the first few incidents rather than write a document, because the reasoning is what transfers, and reading a log together teaches it faster than any style guide.

What is the most expensive EF mistake you have seen, and what was the systemic fix?

The pattern I have seen cost the most is a soft-delete or multi-tenant filter that was bypassed — a bulk operation using ExecuteDelete, or an admin feature calling IgnoreQueryFilters() to see deleted rows and switching off tenancy with it. It is expensive because it is silent, correctness-level rather than performance-level, and often only discovered by a customer. The systemic fix is defence in depth rather than more care: enforce the tenant boundary in the database with row-level security so the model is a convenience and not the guarantee; use EF Core 10's named filters so the security-relevant predicate cannot be disabled by a call aimed at the convenience one; add generated tests that hit every endpoint as tenant A with tenant B's ids and assert nothing comes back; and ban the parameterless IgnoreQueryFilters(). The general lesson I would draw is the one that separates a rule from an engineering practice: if the only thing standing between you and a data leak is a developer remembering, you do not have a control.

If you could change one thing about how most teams use EF, what would it be?

I would make them treat the generated SQL as part of the source code — reviewed, tested, and diffed. Almost every EF problem I have dealt with, from N+1 and cartesian explosion to a post-upgrade plan regression, is invisible in the C# and obvious in the SQL, and the reason teams do not see it is not skill but that nothing puts it in front of them. Snapshot-testing the SQL of the twenty queries that matter costs an afternoon and changes the relationship with the framework permanently: an EF major upgrade becomes a code review, a refactor that accidentally changes a join shows up as a diff, and a junior can see the consequence of an Include without profiling. The second thing, closely related, is that the query-count assertion should be as normal as an assertion about the response body. Both are cheap; both convert a class of production incident into a build failure; and both teach the model better than any amount of documentation.

14 Night-before cheat sheet

Ten sentences to say out loud until they are yours. Every one is defensible and current as of 2026-09-08.

  1. State of the art. "EF Core 10 shipped on 11 November 2025 with .NET 10 as an LTS release, supported to November 2028; 10.0.11 from August 2026 is the current patch, and EF Core 11 is at RC1 for a November 2026 GA. EF6.5 is maintenance-mode — security fixes only — and does not run on the same line at all."
  2. The mental model. "EF is three things: a model, a LINQ-to-SQL translation pipeline, and a change tracker that implements unit of work. Almost every EF question is really about which of the three is involved, and that is how I reason about ones I have not seen before."
  3. Change tracking. "Tracking is snapshot-based: DetectChanges compares each tracked entity to the snapshot taken at materialisation, so UPDATE only touches changed columns. That is why db.Update(dto) is dangerous — it marks everything modified and writes defaults over columns the DTO never carried."
  4. Loading. "Lazy loading is off by default in EF Core and I keep it that way: it is synchronous, it produces N+1 from inside property getters, and it throws after the context is disposed. Select for read paths, Include for write paths, and AsSplitQuery when two collection includes would explode cartesianly."
  5. Translation. "Since EF Core 3.0 untranslatable LINQ throws instead of silently evaluating on the client, and only the final projection may run client-side. EF Core 10 added first-class LeftJoin/RightJoin, so the GroupJoin-SelectMany-DefaultIfEmpty incantation can be deleted."
  6. The EF10 upgrade risk. "Parameterized collections default to multiple scalar parameters now, padded to buckets, instead of EF8's single OPENJSON array — and parameter names were simplified from @__city_0 to @city, which changes the SQL text and therefore invalidates essentially every cached plan on the server. Both are tunable, and both belong in the deployment plan."
  7. Modelling. "Complex types are now the recommended way to model value objects, JSON columns and table splitting; owned entity types have entity semantics, so you cannot assign the same address to two properties and they compare by identity. EF10 gave complex types optional mapping, ToJson(), structs and ExecuteUpdate support; EF11 adds them to TPT and TPC hierarchies."
  8. Concurrency. "EF has no concurrency control unless you configure a token — the default is a silent lost update. A rowversion puts the token in the WHERE clause and turns a conflict into DbUpdateConcurrencyException; the framework detects, and the merge policy is a product decision, not a technical one."
  9. Migrations. "Schema changes roll forward, not back: Down methods are generated, never tested, and dropping a column is not a rollback. Production gets an idempotent script or a bundle applied by the pipeline with DDL rights the application does not have, and every change is decomposed expand/contract so the old and new binaries can both run against the schema."
  10. Performance and judgment. "Fix round trips, then rows, then columns, then plans — AsNoTracking and compiled queries are percentage-level wins and they come last. And I want the generated SQL in the test suite: snapshot the important queries and assert command counts, so an N+1 or a translation change from an EF upgrade fails the build instead of the site."
