01Querying and LINQ translation

This is the first thing asked and the last thing forgiven, because it is where EF stops being a library and becomes a compiler: your LINQ is an expression tree that EF must turn into one SQL statement, and everything it cannot translate either throws or silently escapes to the client. Screeners check IQueryable vs IEnumerable and deferred execution; mid-level checks that you can read the generated SQL; senior and principal are about predicting it — cardinality, plan reuse, parameterisation — and about knowing which EF version changed a translation under you. Expect a whiteboard query and the question "what SQL does this produce, and how many rows come back".

Docs: Microsoft Learn — Querying data

screenerWhat is the difference between IQueryable and IEnumerable in EF, and why does it matter?

Answer

IQueryable<T> carries an expression tree that EF's provider translates into SQL; IEnumerable<T> carries delegates that run in .NET on materialised objects. So the boundary between them is the boundary between "the database filters" and "your process filters". The moment you call AsEnumerable(), ToList(), AsAsyncEnumerable() or pass the query into a method typed IEnumerable<T>, everything after that point is client-side: the WHERE disappears from the SQL and the whole table streams into memory. Both interfaces are lazily evaluated, which is why the bug survives code review — the query still "works", it is just now a full table scan plus an in-process filter. In EF Core the failure mode is a silent performance cliff, not an exception, because only the final projection is allowed to run on the client.

Example

// Translated: WHERE [o].[Status] = 1 — one round trip, a few rows.
var open = await db.Orders.Where(o => o.Status == OrderStatus.Open).ToListAsync();

// Not translated: the cast to IEnumerable happens BEFORE Where,
// so EF issues SELECT * FROM Orders and .NET filters 20M rows.
IEnumerable<Order> all = db.Orders;
var open2 = all.Where(o => o.Status == OrderStatus.Open).ToList();

// The same trap, hidden behind a helper signature:
static IEnumerable<Order> Recent(IEnumerable<Order> src) => src.Where(o => o.CreatedUtc > DateTime.UtcNow.AddDays(-7));

Follow-ups

  • How would you catch this in review? — Ban IEnumerable<T> in repository/service signatures that are meant to compose; return IQueryable<T> or a materialised IReadOnlyList<T>, never the ambiguous middle.
  • How do you prove which one you got? — query.ToQueryString() on the IQueryable prints the SQL without executing it; if the method won't compile, you're already on IEnumerable.
  • Is IQueryable a leaky abstraction to expose from a repository? — Yes, deliberately: it leaks composability, which is the point, but it also leaks "any caller can write an untranslatable predicate", so many teams expose it only inside the data layer.

Wrong answer that gets people rejected

"IQueryable is lazy and IEnumerable is eager." Both are lazy. The difference is where the predicate executes, and saying "lazy vs eager" tells the interviewer you have never diagnosed a query that returned the whole table.

screenerWhat happens when EF Core cannot translate part of your LINQ query?

Answer

Since EF Core 3.0 it throws — InvalidOperationException: The LINQ expression '…' could not be translated — instead of quietly evaluating that fragment on the client, which was EF Core 1.x/2.x behaviour and the single biggest source of production incidents in early EF Core. The only client evaluation still allowed is in the top-level projection: you may call arbitrary .NET in the final Select, because that runs per materialised row after the SQL has already been shaped. The fix is either to express the operation in something EF knows (a translated method, EF.Functions.*, a mapped computed column, a user-defined function mapped with HasDbFunction) or to deliberately switch to client evaluation with AsEnumerable() after the filtering is done. At senior level the point to make is that the exception is a feature: it converts a silent scan into a build-time-visible failure.

Example

// Throws: EF cannot translate an arbitrary local method into SQL.
var bad = await db.Customers.Where(c => Normalize(c.Name) == "acme").ToListAsync();

// Fine: translated to a LIKE.
var ok = await db.Customers.Where(c => EF.Functions.Like(c.Name, "acme%")).ToListAsync();

// Fine: client evaluation in the final projection only.
var shaped = await db.Customers
    .Where(c => c.IsActive)
    .Select(c => new { c.Id, Display = Normalize(c.Name) })
    .ToListAsync();

Follow-ups

  • How do you push a genuinely SQL-side computation into the model? — Map a computed column with HasComputedColumnSql, or register a scalar UDF with modelBuilder.HasDbFunction, and index it if you filter on it.
  • What changed in EF Core 3.0 exactly? — Implicit client evaluation outside the projection was removed; queries that used to work slowly now fail fast, which is why EF6-era code breaks loudly on upgrade.
  • Can you make client evaluation legal again? — Only by materialising explicitly; there is no global "go back to 2.x" switch, and asking for one is the wrong instinct.

Wrong answer that gets people rejected

"EF just runs that bit in memory." That was EF Core 2.x. Saying it now signals you have not touched EF in six years, and worse, it is the exact belief that produces the SELECT * incidents the question is screening for.

midWalk me through what EF does with ids.Contains(x.Id), and what changed in EF Core 10.

Answer

This is the parameterised-collection problem, and its translation has changed three times, which makes it a favourite "are you current" question. Through EF Core 7 the values were inlined as constants — IN (1, 2, 3) — correct but generating a distinct SQL string per distinct list, which bloats and thrashes the database plan cache. EF Core 8 switched to a single JSON-array parameter unpacked server-side (OPENJSON(@ids) on SQL Server), which gave one stable plan but hid the collection's cardinality from the optimiser, so a plan tuned for three ids got reused for three thousand. EF Core 10 changed the default again: each element becomes its own scalar parameter, and EF pads the parameter list (a list of 8 produces 10 parameters, the last two repeating the final value) so that nearby cardinalities share a plan while the optimiser still sees roughly how many values there are. Because no default is right for every query, EF exposes the choice globally via UseParameterizedCollectionMode and per-query via EF.Constant and EF.Parameter.

Example

int[] ids = [1, 2, 3];

// EF10 default -> WHERE [o].[Id] IN (@ids1, @ids2, @ids3)
var a = await db.Orders.Where(o => ids.Contains(o.Id)).ToListAsync();

// Force inlining for a small, low-cardinality set you want planned exactly:
var b = await db.Orders.Where(o => EF.Constant(ids).Contains(o.Id)).ToListAsync();

// Global opt-out, e.g. back to the EF8/EF9 single-JSON-parameter behaviour:
options.UseSqlServer(cs, o => o.UseParameterizedCollectionMode(ParameterTranslationMode.Parameter));

Follow-ups

  • What breaks on upgrade to EF10? — Apps tuned around OPENJSON plans, and very large lists: thousands of scalar parameters hit SQL Server's 2,100-parameter limit, so those queries need ParameterTranslationMode.Parameter or a temp table.
  • What would you do for a 50,000-id list regardless of version? — Stop passing a list: bulk-load the ids into a temp table or TVP and join, or restructure the query so the ids come from a server-side set.
  • Why is plan-cache bloat a real problem and not a micro-optimisation? — On SQL Server it evicts good plans and burns CPU on compilation; a single hot endpoint with inlined lists can push a server to 100% CPU with no query itself looking slow.

Wrong answer that gets people rejected

"It just becomes an IN clause, same as always." It has not been "the same as always" since EF Core 8, and the follow-up — "so what happens to the plan cache?" — is exactly where the interviewer is heading.

midHow do you see the SQL EF is generating, in development and in production?

Answer

Three tools, and a senior answer names all three plus their safety properties. For a single query, ToQueryString() renders the SQL without executing it, which is the fastest loop in a unit test or the debugger. For a whole run, LogTo(Console.WriteLine, LogLevel.Information) or the standard ILogger pipeline with the Microsoft.EntityFrameworkCore.Database.Command category prints every command with its parameters and duration. In production you do not use either: you use the System.Diagnostics / OpenTelemetry instrumentation that EF emits, feed it to your APM, and leave EnableSensitiveDataLogging() off, because parameter values are the PII. EF Core 10 tightened this further: constants that EF inlines into the SQL are now redacted to ? in logs by default, closing a hole where EF.Constant values leaked into log storage.

Example

var q = db.Orders.Where(o => o.CustomerId == customerId).OrderByDescending(o => o.CreatedUtc).Take(20);
Console.WriteLine(q.ToQueryString());

// Dev only — parameter values are PII:
options.UseSqlServer(cs)
       .LogTo(Console.WriteLine, LogLevel.Information)
       .EnableSensitiveDataLogging()
       .EnableDetailedErrors();

Follow-ups

  • Why is EnableSensitiveDataLogging dangerous? — It writes parameter values and key values into logs, so email addresses, tokens and national ids end up in a log sink with a different retention and access policy than the database.
  • How do you catch a slow query you cannot reproduce locally? — Command-duration metrics or an IDbCommandInterceptor that logs anything over a threshold with the command text and the calling tag.
  • How do you correlate SQL back to the LINQ that produced it? — TagWith("…") (or TagWithCallSite()) prefixes the SQL with a comment that shows up in DMVs and query stores.

Wrong answer that gets people rejected

"I turn on sensitive data logging so I can see the values." Fine in dev, a data-protection incident in production — and answering without that caveat is how a security-minded interviewer ends the discussion.

midProjection: why is Select into a DTO usually better than returning entities?

Answer

Because a projection changes the SQL, not just the C#. Select narrows the column list, so you stop dragging nvarchar(max) blobs and unused columns across the wire, it lets the database satisfy the query from a covering index instead of a key lookup, and — crucially — a projection to a non-entity type is not tracked, so the change tracker never allocates snapshots for rows you are only going to serialise. It also flattens navigations into scalars, which turns what would have been an Include with a cartesian product into a couple of joined columns. The senior framing: Select is where EF stops being an ORM and becomes a query builder, and read endpoints should live there almost exclusively.

Example

// Reads every column of Order plus every column of every Line, tracked.
var bad = await db.Orders.Include(o => o.Lines).Where(o => o.CustomerId == id).ToListAsync();

// Reads five columns, untracked, one round trip, no cartesian explosion.
var good = await db.Orders
    .Where(o => o.CustomerId == id)
    .Select(o => new OrderSummary(
        o.Id,
        o.Number,
        o.CreatedUtc,
        o.Lines.Count,
        o.Lines.Sum(l => l.Quantity * l.UnitPrice)))
    .ToListAsync();

Follow-ups

  • Is AsNoTracking() still needed on a projected query? — No for anonymous/DTO projections (nothing to track), yes if the projection still contains an entity type anywhere inside it.
  • What does projecting into a constructor cost? — Nothing at the SQL level; EF binds constructor parameters by name, and records/positional DTOs work fine as long as the expression stays translatable.
  • When would you deliberately return entities? — Write paths: you need the tracked graph to mutate and save it, and projecting there just means loading it twice.

Wrong answer that gets people rejected

"I load the entity and then map it with AutoMapper." Mapping after materialisation is too late — the wide SELECT already happened. The correct version is projecting inside the query (AutoMapper's ProjectTo does exactly this by rewriting the expression tree).

midWhat is the difference between First, FirstOrDefault, Single and SingleOrDefault in EF?

Answer

They differ in the SQL and in the failure mode. First/FirstOrDefault emit TOP(1) (or LIMIT 1) and return the first row, so they need an OrderBy to be deterministic; Single/SingleOrDefault emit TOP(2) and throw if a second row comes back, which is a cheap integrity assertion that your predicate really is unique. The OrDefault variants return null instead of throwing when nothing matches. Practically: use SingleOrDefault when the predicate hits a unique key and you want a broken assumption to surface loudly, use FirstOrDefault with an explicit OrderBy when several rows can legitimately match. FindAsync is a fourth option and different in kind: it checks the change tracker by primary key first and only queries the database on a miss.

Example

// TOP(2) — throws if the "unique" email is not unique. That is the point.
var user = await db.Users.SingleOrDefaultAsync(u => u.Email == email);

// TOP(1) with an explicit order — deterministic "latest".
var latest = await db.Orders.Where(o => o.CustomerId == id)
                            .OrderByDescending(o => o.CreatedUtc)
                            .FirstOrDefaultAsync();

// No SQL at all if the entity is already tracked.
var tracked = await db.Orders.FindAsync(orderId);

Follow-ups

  • Why would First without OrderBy be a bug? — Row order is not guaranteed; a plan change or a parallel scan can silently return a different "first" row after an index is added.
  • When is FindAsync the wrong choice? — When you need Includes or a projection: Find only does key lookup, and its tracker hit can hand you a stale in-memory instance.
  • What does SingleAsync cost over FirstAsync? — One extra row fetched; on a unique index that is noise, and the assertion is worth it.

Wrong answer that gets people rejected

"They're the same, Single is just stricter in C#." No — the generated SQL differs (TOP(1) vs TOP(2)), and that is the detail the question exists to find.

seniorHow does EF decide what becomes a parameter, and why does that matter for the plan cache?

Answer

EF parameterises captured variables and inlines constants. Where(o => o.Status == status) where status is a local produces @status; Where(o => o.Status == OrderStatus.Open) with a literal produces the value baked into the SQL. This matters twice over: parameterised SQL is a single cache entry reused for every value (good for compilation cost, bad if the data is heavily skewed and one value deserves a different plan), while inlined constants give the optimiser exact values (good for skew, bad for cache bloat). Since EF Core 8 you control it explicitly with EF.Parameter(x) and EF.Constant(x), and EF Core 10 also simplified generated parameter names from @__city_0 to @city, which makes query-store analysis far easier. The senior point is that "parameter sniffing" incidents in .NET shops are usually an EF parameterisation decision meeting a skewed column, not a database bug.

Example

// One plan for every tenant — great cache behaviour, terrible if tenant sizes differ by 1000x.
var rows = await db.Orders.Where(o => o.TenantId == tenantId).ToListAsync();

// Force a per-tenant plan for the handful of whale tenants:
var rows2 = await db.Orders.Where(o => o.TenantId == EF.Constant(tenantId)).ToListAsync();

// Force parameterisation where EF would otherwise inline:
var rows3 = await db.Orders.Where(o => o.Status == EF.Parameter(OrderStatus.Open)).ToListAsync();

Follow-ups

  • What are the non-EF fixes for parameter sniffing? — OPTION (RECOMPILE) via a query hint or interceptor, filtered indexes, or splitting the endpoint into two queries; EF's own knob is usually cleaner.
  • Does EF cache the compiled query itself? — Yes: the LINQ expression's shape is the cache key, so structurally identical queries with different parameter values compile once per process.
  • What defeats that cache? — Building expression trees dynamically per call, or embedding varying constants, which produce a new cache key every time and show up as CPU burn plus growing memory.

Wrong answer that gets people rejected

"EF parameterises everything, so plans are always reused." It does not — literals are inlined by design — and believing otherwise means you will never look at EF when the DBA reports 40,000 single-use plans.

seniorWhat does LeftJoin in EF Core 10 replace, and when do you still write the old form?

Answer

.NET 10 added first-class LeftJoin and RightJoin LINQ operators and EF Core 10 recognises them, translating directly to LEFT JOIN/RIGHT JOIN. Before that, a left outer join in LINQ meant the GroupJoin + SelectMany + DefaultIfEmpty incantation, which is easy to get subtly wrong and produced translations that EF had to pattern-match. In practice most left joins in EF code should not be joins at all: if the relationship is mapped, an optional navigation (o.Customer.Name) already generates a LEFT JOIN, and explicit joins are for unmapped or cross-aggregate relationships. Two caveats worth naming: C# query syntax still cannot express LeftJoin, and EF Core 10 also fixed several long-standing DefaultIfEmpty translation bugs, so upgrading can change the SQL of existing hand-rolled left joins.

Example

// EF Core 10 + .NET 10
var q = db.Students.LeftJoin(
    db.Departments,
    s => s.DepartmentId,
    d => d.Id,
    (s, d) => new { s.FirstName, Department = d.Name ?? "[NONE]" });

// Pre-10 equivalent, still what you will find in existing code:
var old = from s in db.Students
          join d in db.Departments on s.DepartmentId equals d.Id into g
          from d in g.DefaultIfEmpty()
          select new { s.FirstName, Department = d.Name ?? "[NONE]" };

Follow-ups

  • When is a manual join the right call at all? — Joining on something that is not a mapped relationship (a date range, a computed key) or joining to a keyless view.
  • Why does an optional navigation give you a LEFT JOIN for free? — EF knows the FK is nullable, so it preserves the principal row rather than filtering it out.
  • Any risk in upgrading a codebase full of DefaultIfEmpty? — Yes: EF10 fixed lifting bugs (#33343, #19095, #35950), so some queries produce different — usually more correct — SQL. Re-baseline the SQL assertions in your tests.

Wrong answer that gets people rejected

"You have to use GroupJoin/DefaultIfEmpty, there's no left join in LINQ." True until November 2025. It is a clean, cheap signal that your knowledge stops at EF Core 8.

seniorWhat is a compiled query and when is it worth the ceremony?

Answer

Every EF query goes through expression-tree translation, and EF caches the result keyed on the expression's shape — so the second execution of the same query skips translation but still pays for building and hashing the tree. EF.CompileAsyncQuery hoists that work to a static delegate created once, removing roughly the last 10–20% of per-call overhead. It is worth it only for very hot, very simple queries executed thousands of times a second, and it costs you composability: a compiled query has a fixed shape, so you cannot conditionally add a Where. In EF Core 9 and 10 the more interesting relative is precompiled queries generated at build time by dotnet ef dbcontext optimize --precompile-queries, which exist mainly to make EF work under Native AOT, where runtime expression compilation is unavailable.

Example

private static readonly Func<AppDb, int, CancellationToken, Task<Order?>> GetOrder =
    EF.CompileAsyncQuery((AppDb db, int id, CancellationToken ct) =>
        db.Orders.AsNoTracking().FirstOrDefault(o => o.Id == id));

var order = await GetOrder(db, id, ct);

Follow-ups

  • What is the measured win? — Single-digit microseconds per call; real only when the query itself is sub-millisecond and the call rate is very high. Measure before adopting.
  • What does a compiled query not fix? — Bad SQL. If the plan is the problem, compiling the LINQ changes nothing.
  • Compiled query vs compiled model? — Different things: compiled queries cut per-call translation, the compiled model cuts one-time startup model building.

Wrong answer that gets people rejected

"Compiled queries make the SQL faster." They make the .NET side of issuing the query faster. Confusing the two suggests you have never profiled where EF time actually goes.

seniorHow do you do keyset ("seek") pagination in EF, and why not Skip/Take?

Answer

Skip(n).Take(m) translates to OFFSET n ROWS FETCH NEXT m, and the database must still walk and discard the first n rows — so page 1 is instant and page 5,000 is a scan, giving you a latency curve that degrades linearly with page depth. Keyset pagination instead carries the last row's sort key forward and filters on it, so every page costs the same index seek. The requirement is a stable, unique, indexed ordering — usually the sort column plus the primary key as a tiebreaker — and it costs you the ability to jump to an arbitrary page number, which is why it fits infinite scroll and APIs with cursors better than a classic page-number grid. It also fixes a correctness bug that offset paging has and people rarely mention: rows inserted between requests shift the window, so users see duplicates or miss records.

Example

// Offset paging: fine for page 3, disastrous for page 3000.
var page = await db.Orders.OrderByDescending(o => o.CreatedUtc)
                          .Skip(pageIndex * 50).Take(50).ToListAsync();

// Keyset: constant cost, stable under concurrent inserts.
var next = await db.Orders
    .Where(o => o.CreatedUtc < lastCreatedUtc
             || (o.CreatedUtc == lastCreatedUtc && o.Id < lastId))
    .OrderByDescending(o => o.CreatedUtc).ThenByDescending(o => o.Id)
    .Take(50)
    .ToListAsync();

Follow-ups

  • What index does that need? — A composite index on (CreatedUtc DESC, Id DESC) matching the order exactly, otherwise you have traded offset scans for sort spills.
  • How do you return a total count? — Usually you don't; if the product insists, compute an approximate count separately or cap it, because COUNT(*) over the filter is often the most expensive part of the endpoint.
  • What do you put in the cursor? — An opaque, signed/encoded token containing the tuple, so clients cannot forge it into an injection or a tenant-crossing filter.

Wrong answer that gets people rejected

"Add an index and Skip/Take is fine." An index does not remove the offset walk; the database still discards the skipped rows. This is the standard follow-up when a candidate proposes offset paging for a feed.

principalYour team's LINQ produces correct but slow SQL. How do you make "predict the SQL" a team capability rather than your personal skill?

Answer

You make the SQL visible in the places engineers already look. Concretely: SQL-snapshot tests, where a handful of representative queries assert their ToQueryString() output against a checked-in baseline, so any translation change — yours or an EF upgrade's — shows up as a diff in review rather than as a page at 3am; TagWith or TagWithCallSite on every non-trivial query so the DBA's query store maps SQL back to a file and line; command-duration and rows-returned metrics with alerting on the endpoint, not the query; and a short written standard covering the four or five decisions that matter (project don't include, no offset paging past N, tracking off by default on reads, no IEnumerable in composable signatures). Then you enforce it with an analyzer or a review checklist rather than with your own eyes, because the failure mode is volume, not ignorance. The principal-level framing is that this is a feedback-loop problem: today the cost of a bad query is invisible until production, and every intervention above is about moving that signal earlier.

Example

[Fact]
public void OrderSummary_query_stays_one_round_trip()
{
    using var db = new AppDb(TestOptions);
    var sql = db.Orders.Where(o => o.CustomerId == 1)
                       .Select(o => new { o.Id, Lines = o.Lines.Count })
                       .TagWith("OrderSummary")
                       .ToQueryString();
    sql.Should().NotContain("OPENJSON").And.Contain("COUNT(*)");
    Snapshot.Match(sql); // checked in; an EF upgrade that changes it fails review, not prod
}

Follow-ups

  • Aren't SQL snapshot tests brittle? — Deliberately: brittleness here is the alarm. Keep them to a dozen high-value queries, not every query.
  • How do you handle the EF upgrade that changes 40 baselines? — Do it as its own PR with the release notes linked, review the diffs as a group, and use it as the upgrade's regression evidence.
  • What do you do about the team member who keeps writing the same mistake? — Turn it into a Roslyn analyzer or an architecture test if it is mechanical; pair on it if it is judgment.

Wrong answer that gets people rejected

"I review every data-access PR myself." That is a bottleneck disguised as diligence, it does not survive your holiday, and it is the answer that separates a strong senior from a principal in this question.

02Change tracking and SaveChanges

The change tracker is the half of EF that is not a query builder, and it is where the interesting bugs live: stale entities, duplicate-key tracking exceptions, accidental updates, and SaveChanges doing seventeen round trips. Screeners want the entity states and what SaveChanges does; mid-level wants disconnected-graph handling in a web API; senior and principal want the cost model — when DetectChanges runs, what it costs at 10,000 tracked entities, and how the unit of work maps onto a request or a message handler. If you can narrate the journey from "I mutated a property" to "an UPDATE with a WHERE on the concurrency token", you pass this section.

Docs: Microsoft Learn — Change tracking

screenerWhat are the entity states, and what does SaveChanges actually do?

Answer

Five states: Detached (not tracked), Unchanged, Added, Modified, Deleted. SaveChanges first calls DetectChanges, which compares every tracked entity against the snapshot taken at materialisation and promotes changed ones to Modified; then it orders the operations so that foreign-key dependencies are satisfied (principals inserted before dependents, dependents deleted before principals); then it executes them inside a single transaction — implicitly created if you have not started one yourself — batching multiple statements into as few round trips as the provider allows; then it propagates database-generated values (identity keys, computed columns, rowversion) back into your objects and resets every surviving entity to Unchanged. If anything fails, the transaction rolls back but your in-memory state is not rolled back, which is why a context that has thrown should generally be discarded.

Example

var order = await db.Orders.FirstAsync(o => o.Id == id);   // Unchanged
order.Status = OrderStatus.Shipped;                        // still Unchanged until DetectChanges
db.Orders.Add(new Order { CustomerId = 7 });                // Added
db.Entry(oldLine).State = EntityState.Deleted;              // Deleted

Console.WriteLine(db.ChangeTracker.DebugView.ShortView);    // inspect before saving
await db.SaveChangesAsync();                                // one transaction, batched

Follow-ups

  • Does SaveChanges return anything useful? — The number of state entries written, which is a useful assertion in tests but not a row count in the SQL sense.
  • What happens to the tracker if SaveChanges throws? — Nothing is reset; entities keep their pending states, so retrying naively can re-apply the same intent against a rolled-back database.
  • How does EF order inserts? — By a topological sort of the dependency graph it builds from FKs; cycles need a temporary nullable FK or two saves.

Wrong answer that gets people rejected

"SaveChanges writes each entity one at a time as you change it." EF is deferred and batched — nothing hits the database until SaveChanges, and then it goes in one transaction. Getting this backwards means you cannot reason about transactions at all.

screenerWhat does AsNoTracking() do, and when should it be the default?

Answer

AsNoTracking() tells EF not to create change-tracking entries or snapshots for the materialised entities, so you get plain objects: less allocation, no DetectChanges cost later, and no identity resolution — meaning the same database row appearing twice in the result gives you two distinct .NET objects. For read-only endpoints it is a straightforward win, typically 10–30% on large result sets and much more when the tracker would otherwise hold tens of thousands of entities. The variant to know is AsNoTrackingWithIdentityResolution(), which skips tracking but keeps a lookup so duplicate rows collapse to one instance — needed when you project a graph and object identity matters, for instance to avoid duplicating children under a parent. You can flip the default per context with QueryTrackingBehavior.NoTracking, which many teams do, then opt into tracking on write paths with AsTracking().

Example

// Global default for a read-heavy service:
options.UseSqlServer(cs).UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);

// Opt back in where you intend to mutate:
var order = await db.Orders.AsTracking().FirstAsync(o => o.Id == id);
order.Status = OrderStatus.Shipped;
await db.SaveChangesAsync();

Follow-ups

  • Does AsNoTracking help a projection to a DTO? — No, that is already untracked; adding it is harmless noise.
  • What breaks if you set NoTracking globally? — Any write path that loads-then-mutates without AsTracking() silently saves nothing. That is a real migration hazard and needs a test sweep.
  • Why does identity resolution matter? — Without it, an Included parent repeated across ten children materialises ten parent objects; mutating one does not affect the others, and serialisers may emit ten copies.

Wrong answer that gets people rejected

"AsNoTracking makes the query faster." It makes materialisation and SaveChanges cheaper; the SQL is byte-for-byte identical. If the interviewer asks "so the SQL changes?" and you say yes, you're done.

midA client POSTs a modified entity to your API. How do you save it correctly?

Answer

This is the disconnected-graph problem and there are two honest answers. The load-then-apply pattern is the one to lead with: fetch the tracked entity by id, copy the allowed fields onto it (or use Entry(target).CurrentValues.SetValues(dto)), and save — EF then generates an UPDATE containing only the columns that actually changed, and, critically, the client cannot set fields you did not intend to expose. The attach-and-mark pattern (db.Update(entity) or setting State = Modified) skips the read but marks every mapped property modified, so you overwrite columns the client never sent with whatever the DTO's defaults were — the classic "our audit columns all became null" incident. Attach-and-mark is defensible only when the payload genuinely is the complete row and you have a concurrency token to protect you. For graphs with children, neither is enough on its own: you need to diff the collection, or use TrackGraph with a rule that decides Added vs Modified per node.

Example

// Safe: only the fields you name, only the columns that really changed.
var order = await db.Orders.FirstOrDefaultAsync(o => o.Id == dto.Id);
if (order is null) return NotFound();
db.Entry(order).Property(o => o.RowVersion).OriginalValue = dto.RowVersion; // optimistic check
order.ShippingAddress = dto.ShippingAddress;
order.Notes = dto.Notes;
await db.SaveChangesAsync();

// Dangerous: UPDATE sets every mapped column, including ones the client never sent.
db.Update(mapper.Map<Order>(dto));
await db.SaveChangesAsync();

Follow-ups

  • How do you handle the child collection? — Load it, match by key, mark missing ones Deleted, new ones Added; or model the child as an owned/complex type so EF replaces the whole thing.
  • Is the extra SELECT a real cost? — Almost never compared with the risk; and it is the read you need anyway to authorise the operation and to build a meaningful audit entry.
  • What does TrackGraph give you? — A callback per node so you can set state by inspecting the key (default key ⇒ Added, otherwise Modified), which is how generic "save this aggregate" helpers are written.

Wrong answer that gets people rejected

"Just call db.Update(entity), EF works out what changed." It does not: on a detached entity there is no original snapshot to compare against, so EF marks everything modified. This is the single most common EF mistake in web APIs, and it is why the question is asked.

midWhat causes "The instance of entity type 'X' cannot be tracked because another instance with the same key value is already being tracked"?

Answer

The change tracker is an identity map: at most one tracked instance per (entity type, primary key). The exception means you attached or added a second object with a key that is already in the map — typically because you mapped a DTO to a fresh entity and called Update while the original was still tracked from an earlier query in the same request, or because a scoped DbContext is being reused across operations that each load the same row. Fixes, in order of preference: load once and mutate the tracked instance (the load-then-apply pattern); use AsNoTracking() on the read if it was only for validation; or, as a last resort, ChangeTracker.Clear() before attaching. Long-lived contexts make this dramatically more likely, which is why the exception is really a symptom of context-lifetime design.

Example

// Boom: the first query tracked Order#5; Update attaches a second Order#5.
var existing = await db.Orders.FirstAsync(o => o.Id == 5);      // tracked
db.Update(new Order { Id = 5, Notes = "changed" });             // InvalidOperationException

// Fix A — mutate the tracked instance:
existing.Notes = "changed";

// Fix B — the read was only a check, so don't track it:
var exists = await db.Orders.AsNoTracking().AnyAsync(o => o.Id == 5);

Follow-ups

  • Is ChangeTracker.Clear() a good fix? — It is a sledgehammer: it also discards other pending changes in the unit of work. Use it in batch loops, not in request handlers.
  • Why does this show up more with a singleton or captive context? — The identity map keeps growing across requests, so collisions and memory both climb; it is the classic symptom of a DbContext captured by a singleton service.
  • Does it apply to owned types? — Yes, and more confusingly, because owned entities have hidden keys tied to their owner; complex types (EF8+, and JSON-capable in EF10) avoid the whole class of problem by having value semantics.

Wrong answer that gets people rejected

"You detach the old one and attach the new one." That works mechanically and hides the real defect — you are loading the same row twice in one unit of work — so you will hit the next variant of the bug next sprint.

midWhen does DetectChanges run, and what does it cost?

Answer

For entities with plain (non-proxy) properties, EF uses snapshot change tracking: at materialisation it stores a copy of every mapped property, and DetectChanges walks every tracked entity and every property comparing current values against that snapshot. It runs automatically before SaveChanges, and also before most ChangeTracker and DbSet.Local operations, and its cost is O(tracked entities × mapped properties) — irrelevant at 50 entities, very visible at 50,000, and quadratic-feeling in a loop that calls SaveChanges or Add repeatedly. The mitigations are: track less (projections, AsNoTracking), batch and clear (ChangeTracker.Clear() between chunks), AddRange instead of Add in a loop, and only as a measured last resort ChangeTracker.AutoDetectChangesEnabled = false around a tight block with an explicit DetectChanges() before saving. Change-tracking proxies remove the scan entirely by notifying on property set, at the cost of virtual properties and proxy-typed objects everywhere.

Example

// 20k inserts: without care this is O(n^2) in DetectChanges.
db.ChangeTracker.AutoDetectChangesEnabled = false;
foreach (var chunk in rows.Chunk(1000))
{
    db.AddRange(chunk);
    db.ChangeTracker.DetectChanges();
    await db.SaveChangesAsync();
    db.ChangeTracker.Clear();      // stop the identity map from growing
}
db.ChangeTracker.AutoDetectChangesEnabled = true;

Follow-ups

  • What is the real fix for 20k inserts? — Not EF: SqlBulkCopy, COPY on PostgreSQL, or a bulk-extension library. EF's job is aggregates, not ETL.
  • What breaks when you disable auto-detect? — Anything relying on implicit detection — Local, relationship fixup, cascade decisions — sees stale state until you call DetectChanges().
  • How do you spot this in production? — CPU-bound time inside SaveChanges with fast SQL: the database says 2ms, the endpoint says 900ms.

Wrong answer that gets people rejected

"EF knows what changed because it hooks the property setters." Only with change-tracking proxies, which almost nobody enables. The default is a snapshot comparison, and the whole cost discussion follows from that.

seniorHow does EF batch SaveChanges, and what limits the batch?

Answer

The relational provider groups pending inserts, updates and deletes into batched commands rather than one round trip per row — on SQL Server, multiple statements in one command, historically wrapped with MERGE … OUTPUT when it needs generated values back, and since EF Core 7 mostly as plain statements with an OUTPUT clause. The batch size is bounded by MaxBatchSize (SQL Server defaults to 42 commands), by the provider's parameter limit (2,100 for SQL Server, so wide entities batch fewer rows), and by EF's own heuristic MinBatchSize below which batching is not worth it. Ordering is not negotiable: FK dependencies force principals before dependents, so a graph with cycles or many interleaved types batches worse than a flat list of the same size. This matters because the difference between 1 round trip and 200 on a 10ms-RTT connection is 2 seconds of latency that no index will fix.

Example

options.UseSqlServer(cs, o => o.MaxBatchSize(100));

// Observe it: one command, many statements.
db.AddRange(newLines);            // 100 order lines
await db.SaveChangesAsync();      // ~1-3 round trips, not 100

Follow-ups

  • Why would you ever lower MaxBatchSize? — Lock footprint and log pressure: huge batches hold locks longer and can escalate; some teams cap it to keep p99 predictable.
  • Does batching apply across entity types? — Yes, within the ordering constraints; it is command batching, not per-table.
  • What about ExecuteUpdate/ExecuteDelete? — Those bypass the tracker entirely and are a single statement each, but they are not part of the SaveChanges batch or its implicit transaction.

Wrong answer that gets people rejected

"EF sends one command per entity, that's why it's slow." It has batched since EF Core 1.0 (and EF6 never did, which is where the myth comes from). Repeating the EF6-era complaint dates you badly.

seniorHow do you implement audit fields and domain-event dispatch around SaveChanges?

Answer

Two supported hooks: override SaveChangesAsync on your DbContext, or register an ISaveChangesInterceptor (EF Core 5+) — prefer the interceptor, because it composes, can be registered per-context in DI, and keeps the context free of application concerns. In SavingChangesAsync you walk ChangeTracker.Entries<IAuditable>() and stamp CreatedUtc/ModifiedBy for Added/Modified states; you must call ChangeTracker.DetectChanges() first if you are outside the normal flow, and you must be careful that stamping a property does not itself resurrect a Deleted entity. Domain events are the harder half: collect them off the aggregates before saving, but dispatch them after the transaction commits (SavedChangesAsync), otherwise a handler observes state that later rolls back. If a handler must be atomic with the write — the usual case for integration events — write it to an outbox table in the same SaveChanges and let a separate process publish it.

Example

public sealed class AuditInterceptor(TimeProvider clock, ICurrentUser user) : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData e, InterceptionResult<int> result, CancellationToken ct = default)
    {
        var ctx = e.Context!;
        foreach (var entry in ctx.ChangeTracker.Entries<IAuditable>())
        {
            if (entry.State is EntityState.Added)
                entry.Entity.CreatedUtc = clock.GetUtcNow().UtcDateTime;
            if (entry.State is EntityState.Added or EntityState.Modified)
                entry.Entity.ModifiedBy = user.Id;
        }
        return base.SavingChangesAsync(e, result, ct);
    }
}

options.UseSqlServer(cs).AddInterceptors(new AuditInterceptor(clock, user));

Follow-ups

  • Why dispatch after commit, not before? — Before-commit dispatch publishes facts that may never become true; after-commit risks losing the event, which is exactly the trade-off the outbox exists to remove.
  • Where do you put the outbox insert? — In SavingChanges, as ordinary entities, so it lands in the same transaction as the aggregate change with zero extra ceremony.
  • Temporal tables instead of audit fields? — SQL Server temporal tables (mapped in EF Core 6+ with IsTemporal()) give you full row history for free and answer "what did this look like on 3 June", which audit columns cannot.

Wrong answer that gets people rejected

"I publish the domain events inside SaveChanges so it's all atomic." Publishing to a broker is not part of the database transaction — you have built dual-write with extra steps. Naming the outbox unprompted is what a senior answer looks like here.

seniorWhat is the unit of work in your architecture, and who calls SaveChanges?

Answer

DbContext is a unit of work plus a set of repositories — that is not an analogy, it is the documented design — so the real question is what business operation the unit of work corresponds to. The defensible answer for a web API is: one DbContext per request (scoped), one SaveChanges per command, called at the edge of the application layer — a command handler, a MediatR behaviour, or a transaction filter — never inside a repository method. That gives you a single atomic boundary per business operation, makes "did this endpoint write?" answerable, and stops the pattern where three repositories each save and you get partial writes. For message consumers the unit of work is the message; for background jobs it is the batch, and there you deliberately save every N items and clear the tracker. The anti-pattern to name is a repository that calls SaveChanges internally: it destroys atomicity across aggregates and makes every caller's transactional intent unknowable.

Example

// One save per command, at the boundary. Handlers never call SaveChanges themselves.
public sealed class UnitOfWorkBehavior<TReq, TRes>(AppDb db) : IPipelineBehavior<TReq, TRes>
    where TReq : ICommand
{
    public async Task<TRes> Handle(TReq req, RequestHandlerDelegate<TRes> next, CancellationToken ct)
    {
        var response = await next();
        await db.SaveChangesAsync(ct);   // the only call site
        return response;
    }
}

Follow-ups

  • What about an operation spanning two aggregates that must both change? — Same SaveChanges if they share a database; otherwise it is a distributed-consistency problem and you need an outbox and eventual consistency, not a bigger transaction.
  • Do you still add a repository layer on top? — Only when it buys you something concrete (a domain-language API, enforced query filters, a seam for a non-EF store). "Because the book says so" is not a reason.
  • How do you enforce it? — An architecture test (NetArchTest/ArchUnitNET) asserting that SaveChanges is referenced only from the behaviour and the composition root.

Wrong answer that gets people rejected

"I wrap DbContext in an IUnitOfWork so I'm not coupled to EF." You are still coupled — IQueryable, tracking semantics and lazy loading all leak through — and you have added a layer whose only method is SaveChanges. Have a reason or don't do it.

seniorHow do cascade deletes work in EF Core, and where do they bite?

Answer

EF has two cascade behaviours that people conflate: the OnDelete setting configures both the database FK action written by migrations and EF's own in-memory behaviour when a principal is deleted or a relationship is severed. Defaults follow optionality: required relationships get Cascade, optional ones get ClientSetNull — meaning EF nulls the FK on loaded children but does nothing to children it has not loaded, which is the classic "it worked in tests and left orphans in production" trap. The other trap is SQL Server's rejection of multiple cascade paths: two required relationships converging on one table produce a migration that fails with "may cause cycles or multiple cascade paths", and the answer is DeleteBehavior.Restrict on one leg plus explicit deletion in code, not blindly switching everything to NoAction. At senior level, add that cascade delete on a large aggregate is a lock-duration problem, and that soft delete via query filters is usually the real requirement.

Example

modelBuilder.Entity<Order>()
    .HasMany(o => o.Lines)
    .WithOne(l => l.Order)
    .HasForeignKey(l => l.OrderId)
    .OnDelete(DeleteBehavior.Cascade);      // DB-level ON DELETE CASCADE + EF cascade

modelBuilder.Entity<Order>()
    .HasOne(o => o.Customer)
    .WithMany(c => c.Orders)
    .OnDelete(DeleteBehavior.Restrict);     // break the multiple-cascade-path cycle

Follow-ups

  • What is ClientCascade vs Cascade? — ClientCascade makes EF delete loaded children itself and writes NO ACTION to the database; useful when the DBA forbids DB-level cascades.
  • Why do orphans appear with ClientSetNull? — EF can only null FKs on children it is tracking; unloaded children keep pointing at a deleted principal unless the database enforces it.
  • How do you delete a 500k-row aggregate? — Not with cascade: batch it with ExecuteDeleteAsync in chunks, or partition/archive, to keep the transaction and the lock window bounded.

Wrong answer that gets people rejected

"Cascade delete is a database feature, EF just configures the FK." Half right, and the missing half — EF's in-memory cascade over the tracked graph — is exactly where the orphan and multiple-cascade-path bugs come from.

principalA background job holds one DbContext for a two-hour run and memory climbs to 6 GB. Diagnose and fix.

Answer

The diagnosis is almost certainly the change tracker's identity map: every entity the job has ever materialised is still referenced, along with its property snapshot, so the "leak" is a design decision rather than a bug — .NET cannot collect what the context holds. Confirm it cheaply with db.ChangeTracker.Entries().Count() logged per batch, or a dump showing InternalEntityEntry and snapshot arrays dominating gen-2. The fix is to make the unit of work small: process in chunks, and per chunk either create a fresh context from an IDbContextFactory or call ChangeTracker.Clear() after saving; read the work list with AsNoTracking() and keyset pagination rather than one giant tracked query; and where the job is pure data movement, replace EF with ExecuteUpdateAsync/ExecuteDeleteAsync or bulk copy so nothing is tracked at all. Secondary contributors worth naming: DbContext pooling does not help here (it resets on return, not during use), and a long-lived context also pins a connection and a transaction if one was opened, so you are risking lock duration alongside memory.

Example

await foreach (var batch in ReadKeysetBatchesAsync(500, ct))
{
    using var db = await factory.CreateDbContextAsync(ct);   // fresh tracker per batch
    var entities = await db.Invoices.Where(i => batch.Contains(i.Id)).ToListAsync(ct);
    foreach (var i in entities) i.Recalculate();
    await db.SaveChangesAsync(ct);
}   // nothing survives the batch

Follow-ups

  • How would you have prevented it in review? — A rule that background jobs take IDbContextFactory<T>, never a scoped DbContext, plus a metric on tracked-entity count.
  • Does ChangeTracker.Clear() fully release the memory? — It drops EF's references; the objects then die at the next GC provided your own code is not holding them in a list, which is the second half of most of these incidents.
  • When is a long-lived context legitimate? — Desktop/Blazor-Server-style session scopes where you deliberately want an in-memory graph, and even then with a bounded working set.

Wrong answer that gets people rejected

"Add GC.Collect() / increase the container memory limit." Both treat a symptom of a retained object graph. Also wrong: "use pooling" — pooled contexts are reset on return, so a context you never return pools nothing.

03Loading related data

Every EF interview contains an Include question, because how you load a graph decides the shape of the SQL, the size of the result set, and whether you have an N+1. Screeners want eager vs lazy vs explicit; mid-level wants filtered includes and split queries; senior and principal want you to argue that most reads should not Include at all but project. The strongest signal here is that you talk about rows returned, not just round trips: cartesian explosion is the failure mode that survives every "just add an index" suggestion.

Docs: Microsoft Learn — Loading related data

screenerEager, lazy, explicit loading — what are they and which do you default to?

Answer

Eager loading is Include/ThenInclude in the query: EF joins (or issues a second query with AsSplitQuery) and fills the navigations up front — predictable, one place to reason about. Explicit loading is Entry(e).Collection(x => x.Lines).LoadAsync() after the fact: a deliberate extra round trip when a branch of your code needs the data and others do not. Lazy loading issues a query automatically the first time you touch a navigation, via proxies (UseLazyLoadingProxies plus virtual navigations) or an injected ILazyLoader; it is off by default in EF Core, and it is off by default for a reason. My default is neither: project what the caller needs with Select, use Include when I genuinely need tracked entities to mutate, use explicit loading for conditional branches, and enable lazy loading essentially never in a server application because it turns a loop over 500 orders into 500 queries invisibly.

Example

// Eager
var o = await db.Orders.Include(x => x.Lines).ThenInclude(l => l.Product)
                       .FirstAsync(x => x.Id == id);

// Explicit — only when this branch is taken
await db.Entry(o).Collection(x => x.Lines).LoadAsync();

// Lazy — requires Microsoft.EntityFrameworkCore.Proxies and virtual navigations
options.UseLazyLoadingProxies().UseSqlServer(cs);
public virtual ICollection<OrderLine> Lines { get; set; } = [];

Follow-ups

  • Why is lazy loading especially bad in an API? — Serialisation touches every navigation, so the serialiser itself triggers the queries — and in a disconnected/no-tracking scenario it silently returns nothing or throws.
  • Is there a safe lazy option? — ILazyLoader injection avoids proxy types and virtual, but it has the same N+1 risk; the safety comes from discipline, not the mechanism.
  • How do you detect accidental lazy loads? — Log the Database.Command category with a per-request query counter and fail the build/test when a request exceeds a threshold.

Wrong answer that gets people rejected

"Lazy loading is convenient, I turn it on and let EF handle it." That is the N+1 generator, and in EF Core it also requires proxies, which quietly breaks serialisation, equality and AutoMapper conventions.

midWhat is cartesian explosion, and how does AsSplitQuery fix it?

Answer

When you Include two or more collection navigations in one query, the SQL joins them all, and the database returns the cross product: an order with 20 lines and 15 shipments comes back as 300 rows, each repeating every column of the order. The row count multiplies per collection, so a three-collection include on a wide parent can turn a 2 KB result into tens of megabytes — the query looks fine in the plan, and the pain is entirely in network and materialisation. AsSplitQuery() tells EF to issue one query per collection instead (parent, then lines, then shipments) and stitch them in memory, trading N round trips for no duplication. The cost is that the queries are no longer a single atomic read: without a serialisable transaction, another writer can change data between them — and EF Core 10 specifically fixed the ordering of split queries so that a Take plus OrderBy no longer risks returning children of a different parent set.

Example

// One query, 20 x 15 = 300 rows, Order columns repeated 300 times.
var single = await db.Orders.Include(o => o.Lines).Include(o => o.Shipments)
                            .FirstAsync(o => o.Id == id);

// Three queries, 1 + 20 + 15 rows.
var split = await db.Orders.Include(o => o.Lines).Include(o => o.Shipments)
                           .AsSplitQuery()
                           .FirstAsync(o => o.Id == id);

// Or make it the default and opt out per query with AsSingleQuery():
options.UseSqlServer(cs, o => o.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery));

Follow-ups

  • When is a single query still better? — One collection only, or small children, or when a high round-trip latency dominates; splitting three tiny collections over a 40ms link is a net loss.
  • What consistency guarantee do you lose? — Cross-query atomicity; wrap in a transaction with an appropriate isolation level (or snapshot isolation) if the read must be coherent.
  • What warning does EF give you? — MultipleCollectionIncludeWarning; many teams escalate it to an error so the choice is always explicit.

Wrong answer that gets people rejected

"Split query is faster, so always turn it on." It is not universally faster — it multiplies round trips and loses read consistency. The expected answer is a trade-off, decided per query by collection count and row width.

midHow do you load only some of a collection — the last 10 comments, say?

Answer

Filtered Include, available since EF Core 5: you can apply Where, OrderBy, Skip and Take inside the Include lambda, and EF pushes them into the join or the split query. Two rules people get wrong: the same navigation may only be included once with a filter per query (a second, unfiltered Include of the same navigation overrides it and loads everything), and the filtered result is still tracked, so the navigation on a tracked entity now holds a partial collection — if other code assumes order.Lines is complete, you have created a subtle bug. The alternative, and usually the better one for read endpoints, is to project: Select the parent's scalars plus a nested Select over the ordered, taken children, which is untracked and makes the partiality explicit in the DTO's name.

Example

// Filtered include (EF Core 5+)
var post = await db.Posts
    .Include(p => p.Comments.Where(c => !c.IsHidden)
                            .OrderByDescending(c => c.CreatedUtc)
                            .Take(10))
    .FirstAsync(p => p.Id == id);

// Projection — clearer, untracked, and the DTO name says "latest 10"
var dto = await db.Posts.Where(p => p.Id == id)
    .Select(p => new PostWithLatestComments(
        p.Id, p.Title,
        p.Comments.Where(c => !c.IsHidden)
                  .OrderByDescending(c => c.CreatedUtc).Take(10)
                  .Select(c => new CommentDto(c.Id, c.Body)).ToList()))
    .FirstAsync();

Follow-ups

  • What SQL does a filtered include produce? — A ROW_NUMBER()/lateral-join shape (OUTER APPLY on SQL Server) so the Take applies per parent, not globally.
  • What if you also need the total comment count? — Project it as a separate scalar (p.Comments.Count); do not count the partial collection in memory.
  • Does the filter apply on a tracked entity already in the identity map? — Relationship fixup will merge whatever is loaded, so a previously-loaded full collection stays full: another reason to prefer projection for read paths.

Wrong answer that gets people rejected

"Include(p => p.Comments).Take(10)." That Take applies to the parent query, not the collection — you get 10 posts with all their comments. It is the exact mistake filtered include was introduced to fix.

midWhat is relationship fixup and why does data appear that you did not Include?

Answer

When EF materialises a tracked entity it wires it into the navigations of everything else already in the identity map: load 50 order lines and, if their order is already tracked, order.Lines silently fills up. This is relationship fixup, and it is why a graph can look complete in a debugger or a test while the same code in production returns null navigations — the difference is only which entities happened to be tracked. Two consequences to state: fixup happens per DbContext, so it never crosses a request boundary, and it does not mean the collection is complete — it contains exactly the children that have been loaded, with no marker distinguishing "empty" from "not loaded". Untracked queries (AsNoTracking) skip fixup entirely unless you use AsNoTrackingWithIdentityResolution, which is why moving a read path to no-tracking sometimes "loses" data that was never really loaded.

Example

var order = await db.Orders.FirstAsync(o => o.Id == 1);
Console.WriteLine(order.Lines.Count);       // 0 — nothing loaded

await db.OrderLines.Where(l => l.OrderId == 1).LoadAsync();
Console.WriteLine(order.Lines.Count);       // 12 — fixup filled the navigation

// Ask EF whether it is actually loaded, rather than trusting Count:
bool loaded = db.Entry(order).Collection(o => o.Lines).IsLoaded;

Follow-ups

  • How do you tell "empty" from "not loaded"? — Entry(e).Collection(...).IsLoaded; there is no way to tell from the collection itself, which is why null-checking navigations is unreliable.
  • Does fixup fire for AsNoTracking? — No; use AsNoTrackingWithIdentityResolution() if you need a coherent graph without tracking.
  • Why do tests pass and production fail? — Tests often load everything into one context, so fixup masks a missing Include; a fresh-context assertion catches it.

Wrong answer that gets people rejected

"If the navigation has items, the data was loaded." Not necessarily — it may be partial from fixup, or empty because nothing was loaded. Building logic on collection counts is how "the order has no lines" bugs ship.

seniorWhy is Include often the wrong tool for a read endpoint?

Answer

Because Include is defined by the model, not by the use case: it loads whole entities, all columns, tracked, with the join shape that follows from the mapping. A read endpoint almost never wants that — it wants six fields, an aggregate or two, and no change tracking. Projection gives you exactly the columns, computes counts and sums in SQL instead of materialising children to count them in C#, avoids cartesian explosion without needing split queries, and produces a DTO whose shape is a contract you can version. The rule I use: Include on write paths where I will mutate the graph, Select everywhere else. The senior nuance is that projections defeat some model-level protections — global query filters still apply, but soft-delete/tenant logic living in a repository method does not — so the discipline has to live in the model, not in a wrapper.

Example

// Include: 300 rows, 40 columns, tracked, then you count in C#.
var o = await db.Orders.Include(x => x.Lines).FirstAsync(x => x.Id == id);
var total = o.Lines.Sum(l => l.Quantity * l.UnitPrice);

// Projection: 1 row, 4 columns, SUM computed by the database.
var view = await db.Orders.Where(x => x.Id == id)
    .Select(x => new { x.Id, x.Number, LineCount = x.Lines.Count,
                       Total = x.Lines.Sum(l => l.Quantity * l.UnitPrice) })
    .FirstAsync();

Follow-ups

  • How do you keep DTO projections maintainable at scale? — Expression-bodied static Expression<Func<Order, OrderDto>> mappers, or AutoMapper's ProjectTo, so the projection is defined once and stays translatable.
  • Doesn't this duplicate the domain model? — Yes, and that duplication is the point: read models and write models have different lifetimes and different consumers.
  • Where does Include still win? — Loading an aggregate you are about to mutate and save, and anywhere you need EF to track deletes of children.

Wrong answer that gets people rejected

"I include everything and let the API serialiser pick fields." You have paid for all the I/O and materialisation already; the serialiser only hides the cost. It is also how reference-loop and over-exposure bugs happen.

seniorWhat is AutoInclude, and would you use it?

Answer

modelBuilder.Entity<Order>().Navigation(o => o.Customer).AutoInclude() (EF Core 5+) makes a navigation load on every query of that entity unless the query calls IgnoreAutoIncludes(). It exists mainly for value-like references — a currency, a country, a small lookup — where the parent is meaningless without it. I use it sparingly and only for lookups that are small and always needed, because it makes the cost of a query invisible at the call site: someone writes db.Orders.ToListAsync() and gets four joins they never asked for, and the fix requires knowing that IgnoreAutoIncludes exists. Owned types are auto-included by definition and cannot be opted out of the same way, which is one of the reasons EF10's complex types are a better modelling choice for value objects.

Example

modelBuilder.Entity<Order>().Navigation(o => o.Currency).AutoInclude();

var orders = await db.Orders.ToListAsync();                    // joins Currency
var lean   = await db.Orders.IgnoreAutoIncludes().ToListAsync(); // opts out

Follow-ups

  • Better alternative for small lookups? — Cache them in memory and map by id in the projection, or model them as an enum/value converter so there is no join at all.
  • Does AutoInclude apply to projections? — No: a Select takes exactly what you ask for, which is another reason projections are predictable.
  • How do you audit its impact? — ToQueryString() on the "simple" query; teams are usually surprised by the join count.

Wrong answer that gets people rejected

"I set AutoInclude on all navigations so I never forget an Include." That is lazy loading's cost profile with none of its laziness — every query drags the whole graph, whether the caller wanted it or not.

seniorHow do you load a many-to-many relationship, and what changed in EF Core 5?

Answer

EF Core 5 introduced skip navigations: you declare Post.Tags and Tag.Posts and EF creates and manages the join table implicitly, so Include(p => p.Tags) just works and adding to the collection inserts the join row. Before that (and still, in EF Core 2/3 codebases you inherit) you had to model the join entity explicitly with a composite key and navigate through it in two hops, which leaked into every query. You can still map the join entity explicitly with UsingEntity<PostTag>(…), and you should whenever the relationship has its own data — an AddedUtc, a role, a sort order — because payload on a join table is a real entity, not plumbing. The performance note that separates a senior answer: a skip navigation Include is still two joins, and if you only need tag names, projecting p.Tags.Select(t => t.Name) avoids materialising tag entities at all.

Example

// Implicit join table (EF Core 5+)
modelBuilder.Entity<Post>().HasMany(p => p.Tags).WithMany(t => t.Posts);

// Explicit, because the relationship carries data
modelBuilder.Entity<Post>()
    .HasMany(p => p.Tags).WithMany(t => t.Posts)
    .UsingEntity<PostTag>(
        j => j.HasOne(pt => pt.Tag).WithMany().HasForeignKey(pt => pt.TagId),
        j => j.HasOne(pt => pt.Post).WithMany().HasForeignKey(pt => pt.PostId),
        j => { j.Property(pt => pt.AddedUtc).HasDefaultValueSql("SYSUTCDATETIME()"); });

Follow-ups

  • How do you update a many-to-many set efficiently? — Load the current set, diff against the incoming ids, add/remove only the differences; replacing the whole collection deletes and re-inserts every row.
  • Can you query the implicit join table? — Only through the navigations, or via Set<Dictionary<string, object>>("PostTag"); if you need to query it regularly, map it explicitly.
  • What indexes matter? — Both directions: the join table needs a composite PK plus a covering index on the reversed pair, or one direction always scans.

Wrong answer that gets people rejected

"You always have to create the join entity yourself." True in EF Core 3.1 and EF6, false since November 2020. It is a cheap way for the interviewer to date your last EF project.

principalYour API's p99 is 4 seconds on one endpoint. The SQL is fast. Where do you look?

Answer

Fast SQL plus slow endpoint points at everything between the plan and the response: row volume, materialisation, tracking, and round trips. The order I work it: count the round trips per request (a query counter on the Database.Command events immediately exposes lazy loading or an N+1 inside a loop); measure rows returned, because a cartesian-exploded include can be 300× the rows with a 2ms query time; check tracking, since materialising 50,000 tracked entities costs snapshots and a DetectChanges pass that never shows up in database metrics; then look at the serialisation of that same over-fetched graph, which frequently doubles the cost. Only after that do I look at pooling, connection saturation and retries. The structural fix is almost always the same — project to a DTO, page with keyset, split or de-include the collections — and the organisational fix is a per-request query-count and rows-returned metric so the next occurrence is caught by an alert instead of by a customer.

Example

// Cheap per-request instrumentation that finds N+1 in staging, not production.
public sealed class QueryCountInterceptor : DbCommandInterceptor
{
    public override ValueTask<InterceptionResult<DbDataReader>> ReaderExecutingAsync(
        DbCommand command, CommandEventData e, InterceptionResult<DbDataReader> r,
        CancellationToken ct = default)
    {
        RequestQueryCounter.Increment();     // AsyncLocal counter, asserted in tests
        return base.ReaderExecutingAsync(command, e, r, ct);
    }
}

Follow-ups

  • How do you distinguish materialisation cost from serialisation cost? — Time ToListAsync() separately from the response write, or profile: InternalEntityEntry allocations point at EF, Utf8JsonWriter at the serialiser.
  • What if the round trips are unavoidable? — Batch them: one query returning the union, or AsSplitQuery with a bounded number of collections; also check RTT — split queries on a 40ms link are a different calculation than on 0.4ms.
  • What is the guardrail you put in place afterwards? — A test that fails when a representative request exceeds N queries or M rows; it is the only thing that stops the regression returning.

Wrong answer that gets people rejected

"The database is fine, so it must be the network / GC / the framework." Naming a culprit before counting round trips and rows is the answer that ends senior interviews; the expected move is a measurement plan, not a suspect.

screenerWhat is the N+1 problem in EF, and how do you find and fix it?

Answer

One query returns N parents, and then something — a lazy-loaded navigation, an explicit load inside a loop, or a per-item service call — issues one more query per parent, so you pay N+1 round trips for data one join could have fetched. In EF Core specifically it comes from three places: lazy-loading proxies, a foreach that calls the database inside the body, and the sneakiest one, an IEnumerable that was materialised early and is then re-queried. You find it by counting queries per request — the Microsoft.EntityFrameworkCore.Database.Command log category, a command interceptor with a counter, or an APM trace showing 400 identical spans. You fix it with an Include or, better, a projection that pulls what you need in one statement; when the child data is genuinely conditional, batch the second query with a single Where(x => ids.Contains(x.ParentId)) and group in memory — two round trips instead of N+1.

Example

// N+1: 1 + 500 queries
var orders = await db.Orders.Take(500).ToListAsync();
foreach (var o in orders)
    o.Total = (await db.OrderLines.Where(l => l.OrderId == o.Id).ToListAsync())
              .Sum(l => l.Quantity * l.UnitPrice);

// 1 query
var totals = await db.Orders.Take(500)
    .Select(o => new { o.Id, Total = o.Lines.Sum(l => l.Quantity * l.UnitPrice) })
    .ToListAsync();

// 2 queries when the child data is conditional
var ids = orders.Select(o => o.Id).ToArray();
var lines = (await db.OrderLines.Where(l => ids.Contains(l.OrderId)).ToListAsync())
            .ToLookup(l => l.OrderId);

Follow-ups

  • How do you stop it coming back? — A test asserting the query count for representative requests; N+1 is a regression class, not a one-off bug.
  • Is N+1 always bad? — No: for N=3 with tiny queries it can beat a cartesian join. The failure is when N is unbounded by input.
  • Where does the "hidden" N+1 come from in a well-behaved codebase? — Mapping code (AutoMapper touching a navigation), serialisation, and validation rules that query per item.

Wrong answer that gets people rejected

"Caching fixes N+1." Caching hides it for repeat traffic and does nothing for the first request or for cold caches; and cache invalidation is a strictly harder problem than writing one join.

midWhat is DbContext pooling and when does it help?

Answer

AddDbContextPool keeps a pool of context instances and resets each one on return instead of constructing a new one per request — it saves the allocation and initialisation of the context object, not the connection (that is already pooled by ADO.NET) and not the model (already cached per service provider). The win is real but narrow: it shows up on very high-throughput, low-work-per-request services, typically a few percent, and it is invisible on anything doing meaningful I/O. The cost is a constraint: a pooled context must not carry per-request state in fields, so a context that takes a tenant id or a user in its constructor breaks — the EF Core 8+ answer is a pooling factory with IDbContextFactory plus explicit state passing, or simply not pooling. Also worth naming: a pooled context is reset on return, so it does nothing for a long-lived context that keeps accumulating tracked entities.

Example

builder.Services.AddDbContextPool<AppDb>(o => o.UseSqlServer(cs), poolSize: 256);

// Breaks pooling assumptions: per-request state stored on the context.
public sealed class AppDb(DbContextOptions<AppDb> o, ITenant tenant) : DbContext(o)
{
    // tenant is captured for the pooled instance's whole lifetime -> cross-tenant leak risk
}

Follow-ups

  • Is a captured tenant really a leak? — With pooling, the injected dependency is resolved once per pooled instance, so a later request can be served by a context bound to another tenant. It is a genuine security bug, not just a design smell.
  • What if the pool is exhausted? — EF falls back to creating new instances; you do not get a deadlock, you get lost benefit, so a too-small poolSize is a silent non-issue.
  • Bigger wins to look at first? — Query shape, tracking, round trips, connection-pool sizing. Pooling contexts is a last-percent optimisation.

Wrong answer that gets people rejected

"Pooling reuses database connections so it's much faster." Connection pooling is ADO.NET's job and has been on by default forever. Conflating the two says you have not read what AddDbContextPool does.

midA query is slow. Walk me through your diagnostic order.

Answer

First, get the actual SQL and the actual parameters (ToQueryString(), or the command log), because the LINQ is not the query. Second, run it in the database with an actual execution plan and look for the three usual suspects: a scan where you expected a seek, a key-lookup loop that a covering index removes, and a sort or hash spill to tempdb. Third, look at cardinality — is the plan bad because the statistics are stale, or because the value is skewed and the cached plan was compiled for a different one (the parameter-sniffing case, which EF's parameterisation choices control). Fourth, look at what EF adds: rows returned versus rows needed, tracking, the number of round trips, and whether the "one slow query" is actually 200 fast ones. Only then do I consider changing the query shape, adding an index, or dropping to raw SQL — and I write down which of the five it was, because the fix and the prevention differ per cause.

Example

var q = db.Orders
    .Where(o => o.TenantId == tenantId && o.CreatedUtc >= from)
    .OrderByDescending(o => o.CreatedUtc)
    .Take(50)
    .TagWith("orders/recent")      // shows as a comment in the plan cache / query store
    .Select(o => new OrderRow(o.Id, o.Number, o.CreatedUtc));

Console.WriteLine(q.ToQueryString());   // paste into SSMS with the real parameter values

Follow-ups

  • Which index would you add for that query? — (TenantId, CreatedUtc DESC) including Number so the top-50 is a seek plus a range scan with no lookups.
  • How do you know statistics are the problem? — Estimated vs actual row counts diverging by an order of magnitude in the actual plan.
  • When do you stop tuning LINQ and write SQL? — When the shape you need (window functions, hints, recursive CTEs, hand-tuned plans) is not expressible; EF's FromSql lets you do that without leaving the model.

Wrong answer that gets people rejected

"I'd add an index on the column in the WHERE." Sometimes right, always premature — without the plan you do not know whether the problem is the seek, the sort, the lookup, the row count or the plan cache, and single-column indexes on wide tables often make things worse.

seniorHow do you make EF work well with connection resiliency and retries?

Answer

EnableRetryOnFailure() installs an execution strategy that retries transient failures — SQL Azure throttling, connection resets, deadlock victims if you configure them — with exponential backoff. Two things you must say alongside it. First, retries and user-initiated transactions do not mix: if you call BeginTransaction yourself, EF throws, because it cannot know how much of your transaction already ran; the fix is to wrap the whole unit of work in Database.CreateExecutionStrategy().ExecuteAsync(...) so the strategy owns the retry boundary and re-runs the entire block. Second, retry means at-least-once execution, so every retried operation must be idempotent — a "retry" of a SaveChanges whose commit actually succeeded but whose acknowledgement was lost will insert twice unless you have a natural key, a unique constraint, or a concurrency token to stop it. That second point is what separates people who have configured resiliency from people who have operated it.

Example

options.UseSqlServer(cs, o => o.EnableRetryOnFailure(
    maxRetryCount: 5, maxRetryDelay: TimeSpan.FromSeconds(10), errorNumbersToAdd: null));

// A user transaction under a retrying strategy MUST own the whole block:
var strategy = db.Database.CreateExecutionStrategy();
await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);
    await db.SaveChangesAsync(ct);
    await outbox.PublishAsync(ct);
    await tx.CommitAsync(ct);
});

Follow-ups

  • Why can't EF just retry inside your transaction? — Because it would have to replay statements it did not issue and cannot roll back your side effects; the strategy needs an idempotent unit to re-execute.
  • What about deadlocks? — Add error 1205 to errorNumbersToAdd only after fixing the ordering that causes them; retrying deadlocks is a bandage that raises latency and hides a real lock-order bug.
  • How do you make a write idempotent? — Client-supplied idempotency key with a unique index, or a concurrency token so the second write fails loudly instead of duplicating.

Wrong answer that gets people rejected

"I turn on EnableRetryOnFailure and everything transient is handled." Then the first explicit transaction in the codebase throws at runtime, and the first lost acknowledgement duplicates a payment. Retries are a correctness decision, not a checkbox.

seniorWhen do you stop using EF for a workload, and what do you replace it with?

Answer

Three workloads where EF is the wrong tool and saying so is a strength, not a heresy. Bulk ingest — tens of thousands of rows: the change tracker and the batch limits make EF an order of magnitude slower than SqlBulkCopy or PostgreSQL COPY; use those, or a bulk-extension library, and keep EF for the aggregate work around them. Complex analytical reads — window functions, recursive CTEs, pivots, hand-tuned hints: express them as SQL against a view or a keyless entity type, or with Dapper, because forcing them through LINQ produces unreadable code and worse plans. Very high-rate simple point reads, where EF's per-query overhead is a meaningful fraction of a sub-millisecond call. The important framing is that this is not "EF vs Dapper" as a religious choice: you keep EF for the transactional aggregate model and drop to SQL for the two or three endpoints that need it, in the same context, using FromSql or SqlQuery<T> so you keep one connection, one transaction and one migration story.

Example

// Scalar/unmapped result set inside the same DbContext and transaction (EF Core 8+):
var rows = await db.Database
    .SqlQuery<RevenueByDay>($@"
        SELECT CAST(CreatedUtc AS date) AS [Day], SUM(Total) AS [Revenue]
        FROM Orders WHERE TenantId = {tenantId}
        GROUP BY CAST(CreatedUtc AS date)")
    .ToListAsync();

// Bulk path: EF stays out of it entirely.
using var bulk = new SqlBulkCopy(conn) { DestinationTableName = "Staging.Events", BatchSize = 10_000 };
await bulk.WriteToServerAsync(reader);

Follow-ups

  • How do you keep the SQL from rotting? — Integration tests against a real database in CI, and schema ownership through migrations so a column rename fails a test rather than production.
  • Is mixing EF and Dapper a smell? — Only if it is unprincipled. A written rule ("EF for writes and aggregates, SQL for reporting reads") is a design; ad-hoc mixing is not.
  • What do you lose dropping to SQL? — Global query filters, including your tenant filter — which is precisely how cross-tenant leaks happen, so raw SQL needs the filter written by hand and tested.

Wrong answer that gets people rejected

"EF can do everything if you write the LINQ well enough." It cannot express hints, some window-function shapes, or bulk copy, and insisting otherwise reads as inexperience with production data volumes.

seniorWhat database-side costs does EF hide that engineers routinely miss?

Answer

Four, in the order they bite. Plan cache pressure: inlined constants and dynamically built expression trees generate distinct SQL per call, filling the cache with single-use plans and burning CPU on compilation. Lock duration: SaveChanges is one transaction, so a batch of 5,000 updates holds write locks for the whole batch and can escalate to a table lock — the fix is smaller units of work, not a bigger timeout. Read amplification: SELECT *-shaped queries from Include read pages you did not need, evicting the buffer pool and making other queries slower, so the symptom appears somewhere else. Implicit conversions: a mismatched column type — nvarchar in the model against varchar in the database, or the wrong precision on a decimal — makes the predicate non-SARGable and turns a seek into a scan, with no EF-side symptom at all. The last one is the classic invisible killer, and it usually comes from a database EF did not create.

Example

// Column is varchar(50) but EF maps string -> nvarchar: every comparison converts and scans.
modelBuilder.Entity<Customer>()
    .Property(c => c.Code)
    .HasColumnType("varchar(50)")
    .IsUnicode(false);                 // restores the index seek

modelBuilder.Entity<Order>()
    .Property(o => o.Total)
    .HasPrecision(18, 2);              // stop silent rounding + conversion

Follow-ups

  • How do you catch the unicode mismatch systematically? — Scaffold the real database into a throwaway model and diff it against yours, or assert column types in a model test.
  • How do you bound lock duration? — Chunked ExecuteUpdate loops with an explicit key range, smaller MaxBatchSize, and never a user-interactive transaction.
  • Who should see these metrics? — The team owning the endpoint: plan cache size, page reads per request and lock waits belong on the service dashboard, not only on the DBA's.

Wrong answer that gets people rejected

"EF generates good SQL, the database will handle it." EF generates correct SQL; whether it is good depends on your model, your types and your indexes. This answer is why teams end up with a DBA who bans ORMs.

seniorHow would you introduce caching around EF without creating a correctness problem?

Answer

I would cache results of read models, not entities, and I would cache at the application boundary where I know the invalidation rule, not inside the data layer where I do not. Concretely: memory-cache the small, rarely-changing lookups (currencies, feature config, tenant metadata) with a short absolute expiry, because those are safe and remove real joins; cache expensive computed read models keyed by their inputs with explicit invalidation on the write path that produces them, ideally via the same domain event that already fires. What I would not do is install a second-level cache interceptor that transparently caches arbitrary queries: it makes correctness depend on a global invalidation heuristic, interacts badly with tenant filters, and turns "why is this stale" into an unanswerable question. The other honest option is to skip application caching and make the query cheap enough not to need it — a covering index plus a projection beats a cache you have to invalidate.

Example

// Safe: small, versioned lookup, explicit expiry, tenant-scoped key.
var rates = await cache.GetOrCreateAsync($"fx:{tenantId}:{DateOnly.FromDateTime(today):O}", async e =>
{
    e.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(15);
    return await db.FxRates.AsNoTracking()
                   .Where(r => r.TenantId == tenantId)
                   .ToDictionaryAsync(r => r.Code, r => r.Rate);
});

Follow-ups

  • What about a distributed cache? — Same rules plus serialisation cost and a network hop; if the query is 2ms, Redis is not an optimisation.
  • How do you handle multi-tenancy in cache keys? — Tenant id in the key, always, and a test that fails if a key-building helper omits it. Cross-tenant cache bleed is the worst bug in this space.
  • Where does EF's own caching sit? — It caches the compiled query and the model, never data; there is no first-level data cache beyond the change tracker's identity map within one context.

Wrong answer that gets people rejected

"I'd add a second-level cache library so all queries are cached automatically." Transparent query caching pushes invalidation into a heuristic nobody owns, and it is how stale prices and cross-tenant reads ship.

principalYou inherit a service where every endpoint is slow and the team blames "the ORM". What do you do in the first two weeks?

Answer

Week one is measurement and one visible win. I instrument first — per-request query count, rows returned, command duration, and the top statements from the database's own query store — because "the ORM is slow" is a hypothesis and I need the distribution: is it one endpoint at 4s, or everything at 300ms? Then I take the single worst endpoint, fix it properly (usually projection plus keyset plus an index), and publish the before/after with the numbers, because credibility buys the rest of the programme. Week two is systemic: a written data-access standard covering the five decisions that matter, guardrail tests for query count on the top endpoints, and an EF version check — a service still on EF Core 6 or 7 is leaving free translation and batching improvements on the table, and EF Core 8 leaves support on 10 November 2026, so an upgrade to EF10 is both a performance and a compliance item. What I explicitly do not do is propose replacing EF with Dapper in week one: that is a 6-month rewrite that fixes the diagnosis nobody has made yet.

Example

// The guardrail that keeps the win: a test that fails on regression.
[Fact]
public async Task Dashboard_endpoint_stays_under_five_queries()
{
    using var counter = QueryCounter.Start();
    var res = await client.GetAsync("/api/dashboard");
    res.EnsureSuccessStatusCode();
    counter.Count.Should().BeLessThanOrEqualTo(5);
}

Follow-ups

  • How do you handle the engineer who wants the rewrite? — Give them the measurement task; either the data supports a targeted replacement for specific endpoints, or it does not, and both outcomes are useful.
  • What if the real problem is the schema? — Then say so early: no ORM choice survives a missing index or a table with 200 nullable columns, and the fix is a schema roadmap, not a library swap.
  • How do you keep the improvement after you move on? — Ownership: dashboards on the team's board, guardrail tests in their pipeline, and the standard in their repo, not in your head.

Wrong answer that gets people rejected

"Replace EF with Dapper / move the reads to a NoSQL read store." Both are plausible endpoints and terrible starting points. A principal-level answer starts with measurement and a visible, cheap win — proposing the big rewrite first is the classic failure mode this question is designed to catch.

principalHow do you budget and enforce data-access performance as a non-functional requirement?

Answer

Turn it into numbers a pipeline can check. I set per-endpoint budgets in three dimensions — p99 latency, database round trips, and rows/bytes returned — because latency alone hides the design errors that only show up under production data volume. Those budgets go into contract tests (query-count assertions and a load-shape test against a database seeded to realistic cardinality, not 12 rows), into the definition of done for new endpoints, and onto a dashboard the team owns. For the database side I ask for two standing signals: the query store's top-by-CPU list reviewed monthly, and an alert on plan-cache single-use plans, which is the earliest indicator of EF parameterisation problems. The organisational half matters more than the technical half: budgets without an owner become a wiki page, so each budget names a team, and a breach opens a ticket automatically rather than waiting for someone to notice.

Example

// Seed realistic cardinality, then assert the shape, not just the clock.
[Fact]
public async Task Search_stays_within_budget_at_2m_rows()
{
    await SeedAsync(orders: 2_000_000);
    using var counter = QueryCounter.Start();
    var sw = Stopwatch.StartNew();
    var res = await client.GetAsync("/api/orders/search?q=widget&take=50");
    sw.Elapsed.Should().BeLessThan(TimeSpan.FromMilliseconds(300));
    counter.Count.Should().BeLessThanOrEqualTo(2);
    counter.RowsRead.Should().BeLessThan(5_000);
}

Follow-ups

  • Where do the budget numbers come from? — The product's latency SLO decomposed across the request path; a 500ms endpoint budget with a 200ms data budget is a decision, not a guess.
  • How do you seed realistic data without a 40-minute test? — A bulk-loaded, cached test database image (containerised, restored per run) rather than EF-inserted rows.
  • What do you do when a budget is repeatedly breached? — Treat it like any SLO: either the budget is wrong and you renegotiate it explicitly, or the work is real and it gets scheduled. Silently ignoring it is what kills the practice.

Wrong answer that gets people rejected

"We do load testing before each release." Late, coarse, and it tells you the system is slow without telling you which decision made it slow. The expected answer ties budgets to the design choices — round trips and rows — that engineers can act on in a PR.

05Modelling and configuration

Everything downstream — the SQL, the migrations, the concurrency story — falls out of the model, so interviewers use this sub-area to check whether you can design a schema through EF rather than just annotate classes. Screeners want conventions vs data annotations vs Fluent API and how relationships are configured; mid-level wants inheritance mapping, keys, value converters and owned types; senior and principal want the judgment calls: where the domain model and the persistence model diverge, how you keep a 300-entity model maintainable, and who owns the schema. Naming EF10's complex-type changes here is an easy way to sound current.

Docs: Microsoft Learn — Creating and configuring a model

screenerConventions, data annotations, Fluent API — which wins, and which do you use?

Answer

Precedence runs Fluent API > data annotations > conventions, so the Fluent API can always override what an attribute says. Conventions get you a long way: a property called Id or <Type>Id becomes the key, matching navigation/FK pairs become relationships, and a DbSet<T> plus everything reachable from it becomes the model. My default is Fluent API in IEntityTypeConfiguration<T> classes, one per entity, applied with ApplyConfigurationsFromAssembly — it keeps persistence concerns out of the domain classes, it can express everything (annotations cannot configure delete behaviour, composite keys, filters, indexes with includes, or splitting), and one file per entity scales to hundreds of entities where a single OnModelCreating does not. Annotations still earn their place for a few universally understood ones — [Key], [Required], [MaxLength] — especially when the same class is a DTO, but mixing both without a rule is how models become unreadable.

Example

public sealed class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> b)
    {
        b.ToTable("Orders", "sales");
        b.HasKey(o => o.Id);
        b.Property(o => o.Number).HasMaxLength(32).IsUnicode(false).IsRequired();
        b.HasIndex(o => new { o.TenantId, o.CreatedUtc }).IsDescending(false, true);
        b.Property(o => o.Total).HasPrecision(18, 2);
        b.HasMany(o => o.Lines).WithOne(l => l.Order).OnDelete(DeleteBehavior.Cascade);
    }
}

protected override void OnModelCreating(ModelBuilder mb)
    => mb.ApplyConfigurationsFromAssembly(typeof(AppDb).Assembly);

Follow-ups

  • How do you apply a rule across every entity? — Pre-convention model configuration (ConfigureConventions, EF Core 6+) for things like "every decimal is (18,2)" or "every string defaults to 256"; a loop over Model.GetEntityTypes() for the rest.
  • Do annotations affect validation too? — [Required]/[MaxLength] are read by both EF and ASP.NET model validation, which is convenient and also a coupling you should be deliberate about.
  • Where do you keep the configurations? — In the infrastructure assembly with the DbContext, so the domain project has no EF reference.

Wrong answer that gets people rejected

"Data annotations override the Fluent API because they're on the class." Backwards. And a candidate who does not know which wins cannot debug the case where two sources disagree — which is most legacy models.

midHow do you map inheritance, and which strategy do you pick?

Answer

Three strategies. TPH (table-per-hierarchy) is the default: one table, a discriminator column, subtype properties nullable — fastest to query, no joins, but wide tables and no NOT NULL on subtype-specific columns. TPT (table-per-type) gives one table per type joined on the key — clean schema, real constraints, but every read joins and performance degrades quickly with hierarchy depth; EF's own guidance is that TPT is usually slower than people expect. TPC (table-per-concrete-type, EF Core 7+) gives one table per leaf with no joins and no shared table, which reads fastest for polymorphic queries over a single type but needs sequences rather than identity to keep keys unique across tables and cannot enforce FKs to the base type. My default is TPH with the discriminator mapped explicitly and mostly-common columns; I move to TPC when the leaves are genuinely disjoint and read-heavy, and I avoid TPT unless a DBA requires normalised tables.

Example

// TPH with an explicit, stable discriminator (never rely on the class name)
mb.Entity<Payment>()
  .HasDiscriminator<string>("PaymentType")
  .HasValue<CardPayment>("card")
  .HasValue<BankTransfer>("transfer");

mb.Entity<Payment>().UseTptMappingStrategy();   // or .UseTpcMappingStrategy() (EF Core 7+)

Follow-ups

  • Why map the discriminator value explicitly? — Otherwise it defaults to the CLR type name and a rename becomes a data migration; it also makes the column readable to non-.NET consumers.
  • Can you query the discriminator? — Yes, and you can map it as a normal property (EF Core 7+) to filter on it directly; OfType<T>() is the usual route.
  • What does TPC cost? — Key generation across tables (use a shared HiLo or sequence), and no single table to FK against, so relationships to the base type become awkward.

Wrong answer that gets people rejected

"TPT is the correct one because it's normalised." Normalisation is not the only axis. EF's TPT joins every level on every query, and teams that chose it "because it's proper" are the ones filing the performance tickets.

midWhat are value converters and value comparers, and when do you need each?

Answer

A ValueConverter translates between the CLR type and the database type — a strongly-typed id to a Guid, an enum to its string name, a DateOnly to a provider type, a value object to JSON. A ValueComparer tells the change tracker how to snapshot and compare that value; you need one whenever the converted type is mutable or a reference type, because otherwise EF's default reference comparison either misses changes (a mutated list looks identical to its snapshot) or reports false positives. The classic bug is converting a List<string> to a JSON string without a comparer: edits to the list are never saved, silently. Two caveats worth stating: converted columns are usually not usable in translated predicates in the way you expect (comparing an enum stored as text does work, but arbitrary conversions can defeat index usage), and since EF Core 8 primitive collections and since EF10 JSON-mapped complex types cover many cases that used to need a hand-rolled converter.

Example

// Strongly-typed id
mb.Entity<Order>().Property(o => o.Id)
  .HasConversion(id => id.Value, value => new OrderId(value));

// Mutable reference type: the comparer is NOT optional
mb.Entity<Doc>().Property(d => d.Tags)
  .HasConversion(
      v => JsonSerializer.Serialize(v, (JsonSerializerOptions?)null),
      v => JsonSerializer.Deserialize<List<string>>(v, (JsonSerializerOptions?)null)!,
      new ValueComparer<List<string>>(
          (a, b) => a!.SequenceEqual(b!),
          v => v.Aggregate(0, (h, s) => HashCode.Combine(h, s.GetHashCode())),
          v => v.ToList()));

Follow-ups

  • What is the third comparer delegate for? — Snapshotting: it must deep-copy, otherwise the snapshot aliases the live object and every comparison says "unchanged".
  • Enum as int or as string? — String is self-describing and survives reordering; int is smaller and faster to index. Pick one per codebase and configure it in ConfigureConventions.
  • Do converters affect queries? — Yes: EF converts the constant too, so equality works, but Contains/ranges over a converted type can become non-SARGable or untranslatable.

Wrong answer that gets people rejected

"I add the converter and it just works." Without a comparer for a mutable type, edits are silently not persisted — and "silently" is why this question is asked. Since EF Core 8 you should also ask whether a primitive collection removes the need entirely.

midHow do you configure keys, alternate keys and indexes properly?

Answer

The primary key is the clustering decision on SQL Server, so it is a physical design choice, not a formality: a monotonically increasing int/bigint identity keeps inserts at the end of the index, a random Guid as a clustered PK fragments it badly — if you need GUIDs, use sequential ones (NEWSEQUENTIALID or .NET 9's Guid.CreateVersion7()) or make the GUID a non-clustered unique key over an identity clustered key. Alternate keys (HasAlternateKey) create a unique constraint that other tables can FK to, which is different from a unique index (HasIndex(...).IsUnique()) — use the index unless something actually references it, because an alternate key is heavier semantically. Indexes should be configured in the model, with the column order matching the query's filter-then-sort shape, IncludeProperties for covering, HasFilter for filtered/partial indexes (soft delete is the standard case), and a name so migrations and DBAs agree on what is what.

Example

b.HasKey(o => o.Id);
b.HasAlternateKey(o => o.Number);                        // something FKs to it
b.HasIndex(o => new { o.TenantId, o.CreatedUtc })
 .IsDescending(false, true)
 .IncludeProperties(o => new { o.Number, o.Total })      // covering
 .HasDatabaseName("IX_Orders_Tenant_Created");
b.HasIndex(o => o.ExternalRef).IsUnique().HasFilter("[ExternalRef] IS NOT NULL");

Follow-ups

  • Composite key or surrogate? — Surrogate for aggregates you will reference widely; composite natural keys are fine for join tables and genuinely composite identities, but they propagate into every FK.
  • Why a filtered unique index for nullable columns? — SQL Server treats multiple NULLs as duplicates in a unique index; the filter restores the "unique when present" semantics.
  • Should EF own index definitions at all? — Yes if EF owns the schema; if the DBA owns it, keep the index in the model anyway so scaffolding and migrations do not fight, and mark the migration as no-op.

Wrong answer that gets people rejected

"Use a Guid PK everywhere, it's cleaner for distributed systems." Not without saying "sequential" or "non-clustered": random GUID clustered keys are the standard cause of page splits and bloated indexes in .NET shops, and interviewers ask this precisely to hear the caveat.

seniorOwned types vs complex types — what is the difference, and what changed in EF Core 10?

Answer

Both let you model a value object like Address inside an entity, but owned types are still entity types: they have hidden identities and reference semantics, so you cannot assign the same instance to two properties, you cannot compare them by value in LINQ, and bulk update over them is unsupported. Complex types, introduced in EF Core 8, have proper value semantics and are the recommended modelling tool. EF Core 10 is the release where they became genuinely usable: optional complex types (previously required-only, though the type still needs at least one required property), struct support, and — the big one — mapping a complex type to a single JSON column with ComplexProperty(x => x.Details, b => b.ToJson()), which finally allows collections inside the mapped type and full ExecuteUpdateAsync support over JSON properties. The practical advice for an interview: new code uses complex types; existing owned-type mappings for value objects should be migrated, and EF10's guidance says so explicitly.

Example

// Table splitting: columns ShippingAddress_City, BillingAddress_City, ...
mb.Entity<Customer>(b =>
{
    b.ComplexProperty(c => c.ShippingAddress);
    b.ComplexProperty(c => c.BillingAddress);       // optional in EF10
});

// JSON mapping (EF10): one json column, collections allowed inside
mb.Entity<Blog>().ComplexProperty(b => b.Details, d => d.ToJson());

// Works with complex types, throws with owned entity types:
customer.BillingAddress = customer.ShippingAddress;
await db.Blogs.ExecuteUpdateAsync(s => s.SetProperty(b => b.Details.Views, b => b.Details.Views + 1));

Follow-ups

  • What is the EF10 breaking change here? — Nested complex types now use the full path in column names (Complex_NestedComplex_Property), so upgrading generates renames you must review.
  • When is an owned type still right? — When the contained thing genuinely has identity and lifecycle tied to the owner but is queried as an entity — otherwise prefer complex types.
  • Collections of complex types? — Supported when mapped to JSON; collections of structs are not supported yet.

Wrong answer that gets people rejected

"Owned types are EF's value objects." They were the workaround; since EF8 (and properly since EF10) they are not the recommendation, and answering this way suggests your mental model froze around EF Core 3.

seniorHow do you model a value object like Money across a 200-entity model without repeating yourself?

Answer

Three levers, used together. Pre-convention configuration (ConfigureConventions, EF Core 6+) lets you register a converter or a precision for every property of a type at once, which is the right home for "all decimals are (18,2)" and "all strongly-typed ids convert to their primitive". Complex types (EF8+, EF10 for JSON and optionality) give you the structural mapping once, so Money { Amount, Currency } becomes a pair of columns or a JSON column wherever it appears. And a small set of reusable IEntityTypeConfiguration base classes or extension methods captures the recurring shapes — auditable entities, soft-deletable entities, tenant-owned entities — so a new entity gets the whole policy in one line. The alternative to all three is a 4,000-line OnModelCreating, which is the state most large EF codebases are actually in, and it is worth saying that the migration to conventions is incremental and safe because the generated schema can be diffed.

Example

protected override void ConfigureConventions(ModelConfigurationBuilder cb)
{
    cb.Properties<decimal>().HavePrecision(18, 2);
    cb.Properties<string>().HaveMaxLength(256);
    cb.Properties<OrderId>().HaveConversion<OrderIdConverter>();
    cb.ComplexProperties<Money>();                 // structural mapping, once
}

public abstract class TenantEntityConfig<T> : IEntityTypeConfiguration<T> where T : class, ITenantOwned
{
    public virtual void Configure(EntityTypeBuilder<T> b)
    {
        b.Property(x => x.TenantId).IsRequired();
        b.HasIndex(x => x.TenantId);
    }
}

Follow-ups

  • How do you verify a convention change did not alter the schema unexpectedly? — Add a migration and read the diff; an empty migration is your proof of a pure refactor.
  • What breaks with a global string max length? — Columns that legitimately need nvarchar(max); override them explicitly, and treat the noise as a feature since unbounded strings are usually a mistake.
  • Does this help startup time? — Slightly (less reflection over attributes), but the real win is consistency; startup is a compiled-model problem.

Wrong answer that gets people rejected

"I write a base entity class and put the attributes there." Attributes cannot express most of what matters (precision per provider, delete behaviour, filtered indexes, complex types), and inheritance in the domain model to satisfy the ORM is exactly the coupling you are trying to avoid.

seniorShould the EF model be your domain model?

Answer

It can be, and for most line-of-business services it should be, because two models means two mappings and a synchronisation problem that buys you nothing until the domain is genuinely complex. EF Core makes the "persistence-ignorant domain" position much more affordable than EF6 did: it maps private fields and backing fields, supports parameterless-constructor-free construction, honours encapsulated collections (Metadata.FindNavigation(...).SetPropertyAccessMode(PropertyAccessMode.Field)), and all the mapping lives in configuration classes in the infrastructure assembly, so the domain project has no EF reference. Where I do split is when the write model wants behaviour and invariants and the read model wants flat, wide, denormalised shapes — that is CQRS-lite, and it is a read-side split, not a second entity model. The honest caveat: EF constrains the domain in real ways — no constructor-only aggregates without configuration work, identity semantics for owned types, lazy-loading temptations — and a principal answer names the constraints rather than claiming purity.

Example

public sealed class Order                      // no EF attributes, no EF reference
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyCollection<OrderLine> Lines => _lines;
    private Order() { }                        // EF uses this; callers cannot
    public Order(CustomerId customer) { CustomerId = customer; }
    public void AddLine(ProductId p, int qty) { /* invariants live here */ }
}

// Infrastructure assembly:
b.Metadata.FindNavigation(nameof(Order.Lines))!
 .SetPropertyAccessMode(PropertyAccessMode.Field);

Follow-ups

  • What does EF need from a "pure" aggregate? — A way to construct it (private ctor is fine) and access to state (fields are fine); it does not need public setters or virtual members unless you use lazy proxies.
  • When is a separate persistence model justified? — Legacy schemas you cannot change, or a domain whose shape genuinely differs from any sane table layout; both are rarer than DDD enthusiasm suggests.
  • How do you keep the read side from corrupting the domain? — Read models are DTOs projected in queries; they never round-trip through the aggregates.

Wrong answer that gets people rejected

"Always separate them — the domain must never know about persistence." Dogma without cost accounting. The interviewer is looking for whether you can name what the split costs (two models, mapping, drift, more tests) and when that price is worth paying.

seniorHow do you map an existing legacy database that you cannot change?

Answer

Scaffold first, then curate. dotnet ef dbcontext scaffold reverse-engineers a context and entity classes from the real schema, which gives you an accurate starting point including the column types, nullability and indexes that a hand-written model reliably gets wrong. Then you take ownership of the output: move the configuration into IEntityTypeConfiguration classes, rename CLR properties to sensible names while keeping HasColumnName, map the columns EF cannot infer (composite keys without conventions, varchar versus nvarchar, decimal precision, computed columns with ValueGeneratedOnAddOrUpdate), and use shadow properties for columns the domain should not see. Two structural tools do most of the heavy lifting: keyless entity types over views for read shapes that have no key, and value converters to hide legacy encodings — a char(1) flag becoming a bool, a status string becoming an enum. Finally, decide the migration story explicitly: either baseline the schema as migration zero and take ownership going forward, or keep the database authoritative and add a CI check that re-scaffolds and fails on drift.

Example

dotnet ef dbcontext scaffold "$CONN" Microsoft.EntityFrameworkCore.SqlServer \
  --table Orders --table OrderLines --use-database-names --no-onconfiguring --force
b.ToTable("ORD_HDR", "legacy");
b.Property(o => o.Number).HasColumnName("ORD_NO").HasColumnType("varchar(20)").IsUnicode(false);
b.Property(o => o.IsActive).HasColumnName("ACT_FLG")
 .HasConversion(v => v ? "Y" : "N", v => v == "Y");
b.Property<DateTime>("LAST_UPD").ValueGeneratedOnAddOrUpdate();   // shadow property

Follow-ups

  • Why not just hand-write the model? — You will get unicode, precision and nullability wrong somewhere, and those produce implicit conversions that silently turn index seeks into scans.
  • What if the schema has no foreign keys? — Configure the relationships in the model anyway (HasOne/WithMany/HasForeignKey); EF will navigate correctly even though the database does not enforce it — and flag the missing constraints as a risk.
  • How do you handle triggers? — SQL Server tables with triggers need ToTable(t => t.HasTrigger("…")) (EF Core 7+), otherwise EF's OUTPUT-clause save strategy fails at runtime.

Wrong answer that gets people rejected

"I'd scaffold it and use the generated code as-is." The generated context has a hard-coded connection string in OnConfiguring, database-shaped names throughout, and no configuration you own — regenerate it once and every manual fix is gone. Scaffolding is a starting point, not an output.

principalWho owns the database schema — the application or the DBA — and how do you make that work?

Answer

Someone must own it, and the failure mode is "both", where EF migrations and hand-run DDL drift until nobody can reproduce the schema. My default is that the service owns its schema and expresses it as migrations in the same repository as the code, because that is what makes a deployment a single reviewable artefact and lets you roll forward reliably. The DBA's role becomes review and standards — index strategy, naming, partitioning, storage — exercised on the generated migration SQL in the pull request, which is a far better review surface than a Word document. Where the database is genuinely shared by several applications, or the organisation requires DBA-executed DDL, invert it: the database is the source of truth, EF scaffolds from it (dotnet ef dbcontext scaffold), and CI fails if the scaffolded model differs from the checked-in one. What I will not accept is EF migrations in dev and hand-written scripts in production, because then the migration history is fiction and the first emergency rollback discovers it.

Example

# App-owned: reviewable SQL in the PR, executed by the pipeline, not by the app.
dotnet ef migrations script --idempotent --output artifacts/migrate.sql
dotnet ef migrations bundle --self-contained -o artifacts/migrate     # EF Core 6+

# DBA-owned: CI proves the model still matches the real database.
dotnet ef dbcontext scaffold "$CONN" Microsoft.EntityFrameworkCore.SqlServer \
  --output-dir Generated --force
git diff --exit-code Generated/    # fails the build on drift

Follow-ups

  • How do you handle a shared database across five services? — Ideally you don't; if you must, one service owns each table, others read through views or an API, and ownership is written down per table.
  • What about DBA-required changes EF cannot express? — Custom SQL inside a migration (migrationBuilder.Sql(...)) keeps them in the same ordered history; a side-channel script does not.
  • How do you audit drift? — A scheduled job that scaffolds production's schema into a temp model and diffs; drift found on a Tuesday is cheaper than drift found during an incident.

Wrong answer that gets people rejected

"Developers should never touch the schema, the DBA runs the scripts." That is a defensible policy only with a mechanism that keeps the model honest. Stated without one, it describes exactly the drift that makes deployments unrepeatable.

06Migrations and schema change

Migrations are where EF meets operations, so this sub-area is asked heavily at lead level and barely at all at junior level. Screeners want the commands and what a migration file contains; mid-level wants merge conflicts, seeding and rollback; senior and principal want zero-downtime deployment, who runs the migration, and what happens when it fails half-way on a Friday. The tell for a strong candidate is that they never run migrations from application startup and can explain exactly why.

Docs: Microsoft Learn — Migrations

screenerWhat does a migration consist of, and how does EF know what to generate?

Answer

Three artefacts per migration: the migration class with Up and Down, a designer file holding a snapshot of the model as of that migration, and an updated ModelSnapshot for the context as a whole. When you run dotnet ef migrations add, EF builds your current model from OnModelCreating, diffs it against the snapshot, and emits the operations that close the gap — so migrations are generated from a model diff, not from your database. That has two consequences people trip over: a change made directly in the database is invisible to EF and will be re-applied or clobbered, and deleting the snapshot desynchronises everything. At runtime, applied migrations are recorded in the __EFMigrationsHistory table by id, which is how database update knows what to run.

Example

dotnet ef migrations add AddOrderNumberIndex --project src/Infrastructure --startup-project src/Api
dotnet ef migrations script FromMigration ToMigration --idempotent -o migrate.sql
dotnet ef database update --connection "$CONN"
dotnet ef migrations remove          # only if it has not been applied anywhere

Follow-ups

  • What changed for the tooling in EF Core 10? — On a multi-targeted project you must pass --framework; the tools no longer pick one for you.
  • Why does the designer snapshot exist per migration? — So EF can diff correctly even when you check out an older commit or apply migrations out of a linear order.
  • What if someone changed the database by hand? — Reconcile deliberately: scaffold, compare, and either write a migration that no-ops the existing change or bring the database back in line.

Wrong answer that gets people rejected

"EF compares the model to the database and generates the difference." It compares the model to the snapshot. That distinction is the entire explanation for drift, phantom operations and "it generated a migration that drops a column that exists in prod".

midTwo developers add migrations on separate branches. What happens on merge?

Answer

You get a conflict in the model snapshot file and a broken linear history: both migrations declare the same predecessor, so whichever is applied second was generated against a stale model and may emit operations that no longer make sense. The mechanical fix is: merge, keep both migration classes, delete and regenerate the later one so it is diffed against the merged model — or, if the changes are independent, resolve the snapshot conflict by regenerating it with a throwaway migrations add followed by migrations remove. The organisational fix matters more: keep migrations small and frequent, merge often, and treat a snapshot conflict as a signal to rebase rather than to hand-edit. Never hand-merge the snapshot file line by line — it is generated code, and a wrong merge produces a model that compiles and lies.

Example

# After merging main into your branch:
dotnet ef migrations remove              # drops YOUR migration + snapshot entry
git checkout --theirs -- **/AppDbModelSnapshot.cs   # take main's snapshot
dotnet ef migrations add AddMyColumn     # regenerate against the merged model
dotnet ef migrations script --idempotent # read the SQL before you trust it

Follow-ups

  • Does migration order matter if the changes are independent? — For the schema usually not; for the history table it always does, and idempotent scripts make the ordering survivable across environments.
  • How do you prevent this? — Short-lived branches, a "migrations must be the last commit" convention, and a CI check that migrations add on the merged branch produces an empty migration.
  • What is that CI check? — Generate a migration in the pipeline; if it is non-empty, the model and the migrations disagree and the build fails.

Wrong answer that gets people rejected

"I resolve the snapshot conflict manually in the editor." It is machine-generated code representing the whole model; a plausible-looking manual merge produces silent drift that surfaces three migrations later.

midHow do you seed data, and what changed in EF Core 9?

Answer

Two mechanisms with different jobs. HasData puts seed rows into the model, so migrations generate inserts/updates/deletes to keep them in sync — perfect for genuinely static reference data (countries, statuses, roles) with fixed keys, and unusable for anything needing generated keys, computed values or FKs to rows EF does not control. EF Core 9 added UseSeeding/UseAsyncSeeding on the options, which run arbitrary code after the database is created or migrated — the right place for "insert the admin user if none exists", environment-specific demo data, or anything requiring queries. The rule I apply: HasData for data that is part of the schema's meaning, UseAsyncSeeding for data that is part of an environment's setup, and neither for large volumes — that is a data-loading job, not a migration.

Example

// Model-level, versioned with the schema
mb.Entity<OrderStatus>().HasData(
    new { Id = 1, Code = "open" }, new { Id = 2, Code = "shipped" });

// EF Core 9+: runs after migrate, can query first
options.UseSqlServer(cs)
       .UseAsyncSeeding(async (ctx, _, ct) =>
       {
           if (!await ctx.Set<Tenant>().AnyAsync(ct))
           {
               ctx.Set<Tenant>().Add(new Tenant("default"));
               await ctx.SaveChangesAsync(ct);
           }
       });

Follow-ups

  • Why does HasData require explicit key values? — Because the migration diff must be able to identify each seed row across versions; generated keys would make every migration ambiguous.
  • What happens when you change a HasData row? — The next migration emits an UPDATE; deleting the entry emits a DELETE, which can fail on FK references.
  • Is seeding in Program.cs acceptable? — For dev, yes; in production it has the same concurrency hazards as startup migrations and belongs in a deployment step.

Wrong answer that gets people rejected

"I seed by inserting rows in OnModelCreating with Add." OnModelCreating builds a model; it has no context to add to. And a candidate who mixes the two has not actually written a migration-backed seed.

seniorDo you run migrations at application startup? Defend your answer.

Answer

No, not in production. db.Database.Migrate() in Program.cs is convenient and it fails badly at scale for four reasons: multiple instances race — several replicas start simultaneously and run DDL concurrently, and while EF takes a lock, timeouts and partial application are real; the application identity needs DDL rights it should not have at runtime; a failed migration takes the whole deployment down in a way that is hard to diagnose from the app's logs; and rolling deployments mean old and new code run against the same schema simultaneously, which the startup model cannot express. The alternative is a deliberate deployment step: dotnet ef migrations bundle (EF Core 6+) produces a self-contained executable, or migrations script --idempotent produces SQL, and either runs as a pipeline stage or an init container with a dedicated migration identity, before the new pods take traffic. For a single-instance internal tool, startup migration is a reasonable, explicitly-taken shortcut — say that, because unqualified absolutism is also a wrong answer.

Example

# Deployment stage, not application startup
dotnet ef migrations bundle --self-contained -r linux-x64 -o ./efbundle
./efbundle --connection "$MIGRATION_CONN"     # separate identity with DDL rights

# Kubernetes: an initContainer or a Job that must complete before the rollout continues

Follow-ups

  • What is PendingModelChangesWarning for? — EF Core 9 added a check that throws when the model has drifted from the last migration, catching "someone changed the model and forgot to add a migration" at startup or in tests.
  • How do you roll back? — You mostly do not: Down methods are rarely exercised and data loss is irreversible. Roll forward with a corrective migration, and design changes to be backward-compatible so the previous app version still works.
  • What about EF9's "all migrations in one transaction"? — It was reverted in EF Core 10 because it broke scenarios that need their own transactions; do not rely on cross-migration atomicity.

Wrong answer that gets people rejected

"We call Migrate() on startup, it's fine, EF handles locking." It is the most common production-grade mistake in .NET services: it grants the app DDL rights permanently, and the first time three replicas restart together during an incident, you find out how "fine" it was.

seniorWalk me through renaming a column with zero downtime.

Answer

Expand–migrate–contract, in three deployments. Expand: add the new column, nullable, and deploy code that writes to both columns and reads the old one — the schema is now compatible with both the old and the new application version, which is the requirement for a rolling deploy. Migrate: backfill in bounded batches (an ExecuteUpdateAsync loop over key ranges, not one statement over 80 million rows, so locks stay short and the log does not explode), then deploy code that reads the new column and still writes both. Contract: once no running version reads the old column and you have kept a safety window, drop it and remove the dual write. EF's RenameColumn operation is the trap here — it is a single DDL that instantly invalidates every currently-running instance of the previous version, so it is only safe when you can tolerate downtime or you deploy with a full stop. The same pattern covers splitting a table, changing a type, and making a column non-nullable.

Example

// Backfill in bounded batches, resumable, no giant transaction.
long lastId = 0;
while (true)
{
    var affected = await db.Customers
        .Where(c => c.Id > lastId && c.EmailAddress == null && c.Email != null)
        .OrderBy(c => c.Id).Take(5_000)
        .ExecuteUpdateAsync(s => s.SetProperty(c => c.EmailAddress, c => c.Email), ct);
    if (affected == 0) break;
    lastId = await db.Customers.Where(c => c.EmailAddress != null)
                               .MaxAsync(c => c.Id, ct);
    await Task.Delay(50, ct);        // be kind to replication lag
}

Follow-ups

  • How do you enforce dual-write? — A computed column or a trigger works, but application-level dual write in one place (an interceptor or the aggregate) is easier to remove later; whichever you pick, write down the removal date.
  • How do you know nothing reads the old column? — Extended events / query store filtered on the column name, plus a deprecation log line on any code path that still touches it.
  • What about adding a NOT NULL column? — Add nullable with a default, backfill, then add the constraint — three steps, same shape.

Wrong answer that gets people rejected

"Add a migration with RenameColumn and deploy." That works on a laptop. In a rolling deploy the old instances start throwing Invalid column name the moment the DDL commits, and you have taken an outage to rename a field.

seniorHow do you apply migrations across hundreds of tenant databases?

Answer

You stop treating it as a deployment step and start treating it as a job with state. The shape that works: a catalogue of tenants with their connection strings and current schema version; a migration runner that iterates tenants with bounded parallelism (10–20, not 400, or you saturate the database server), applies the idempotent script or bundle per tenant, records success/failure per tenant, and is safely resumable after a crash; and an application that can serve a tenant at either schema version during the roll-out, which again forces backward-compatible changes. Two operational requirements complete the answer: canary tenants first — internal, then small, then the whale — with an automatic stop on the first unexpected failure; and observability per tenant, because "migration succeeded" is a per-tenant fact, not a global one. If migrations take hours, you also need a plan for what happens to a tenant whose migration is running when they log in, which is usually "the change is additive, so nothing".

Example

await Parallel.ForEachAsync(tenants, new ParallelOptions { MaxDegreeOfParallelism = 12 },
    async (tenant, ct) =>
    {
        await using var db = factory.Create(tenant.ConnectionString);
        try
        {
            await db.Database.MigrateAsync(ct);            // idempotent per tenant
            await state.RecordAsync(tenant.Id, "ok", ct);
        }
        catch (Exception ex)
        {
            await state.RecordAsync(tenant.Id, "failed: " + ex.Message, ct);
            // do not rethrow: one bad tenant must not stop the other 399
        }
    });

Follow-ups

  • Shared schema vs database-per-tenant — how does this change? — Shared schema makes migration a single operation but makes noisy-neighbour and blast radius worse; database-per-tenant inverts both. This is the core trade-off in the design exercise later.
  • How do you handle a tenant that fails? — Quarantine: mark it, keep it on the old app version if you can route per tenant, and fix forward; never block the fleet.
  • Where does the connection catalogue live? — A control-plane database with its own (small) migration story; do not store tenant connection strings in the tenant databases.

Wrong answer that gets people rejected

"Loop over the tenants at application startup and call Migrate()." Now every replica migrates every tenant on every restart, sequentially, holding the startup probe hostage — and a single failing tenant crash-loops the whole service.

seniorA migration failed half-way in production. What now?

Answer

First establish what actually got applied, because that determines everything else: read __EFMigrationsHistory, then inspect the schema — on SQL Server most DDL is transactional so an interrupted migration usually rolls back cleanly, but on MySQL (and for some operations elsewhere) DDL is not transactional and you can be left genuinely half-applied. If the history row is absent and the schema is unchanged, you re-run after fixing the cause. If the schema is partially changed, you do not re-run the same migration: you write a corrective migration that brings the schema to the intended state from where it actually is, and if necessary insert the history row manually so ordering stays consistent. Meanwhile the application question is separate and more urgent: is the currently-deployed code compatible with the schema as it stands right now? If your changes were backward-compatible, the answer is yes and you have time; if they were not, you are in an outage, which is the argument for expand–contract made concrete. Afterwards: a post-incident item to make the migration reviewable as SQL and to test it against a production-sized restore.

Example

-- What does EF think has been applied?
SELECT TOP 10 MigrationId, ProductVersion FROM __EFMigrationsHistory ORDER BY MigrationId DESC;

-- If a migration ran but the row is missing (e.g. the script was killed after commit):
INSERT INTO __EFMigrationsHistory (MigrationId, ProductVersion)
VALUES ('20260904120000_AddOrderNumberIndex', '10.0.11');

Follow-ups

  • Why not just restore the backup? — For a large production database that is a multi-hour outage plus data loss since the last point-in-time; it is the fallback, not the first move.
  • How do you prevent it recurring? — Run the idempotent script against a restored copy of production in CI, with production-sized data, so long-running DDL and timeouts show up before the change ships.
  • What about migration timeouts? — Set an explicit longer command timeout for the migration connection only; the default 30s kills index builds on large tables mid-flight.

Wrong answer that gets people rejected

"Run Down to roll back." Down methods are almost never tested, frequently lose data, and on a partially-applied migration they fail on the first statement. Rolling forward with a corrective migration is the expected answer.

principalHow do you make schema change safe by default across many teams?

Answer

Make the safe path the easy path and make the unsafe path visible. Concretely, four things. A policy encoded as a check: a CI step that renders every new migration to SQL and fails on the dangerous operations — DROP COLUMN, RENAME, non-nullable additions without defaults, type narrowings — unless the PR carries an explicit, reviewed override label. A shared runner: one internal tool or pipeline template that everyone uses to apply migrations, so identity, timeouts, retries, logging and the tenant loop are solved once. A rehearsal environment: migrations run against a recent production restore before release, which is the only way to learn that an index build takes 40 minutes. And a documented pattern library — expand–contract for renames, batched backfills, additive-first defaults — so that "how do I rename a column" has an answer that is copied rather than invented. The meta-point I would make to an interviewer: the goal is not to review every migration personally, it is that the review is cheap because dangerous things are labelled by a machine.

Example

# CI gate: fail the build on destructive DDL unless the PR is labelled schema-breaking.
dotnet ef migrations script --idempotent -o migrate.sql
if grep -Ei 'DROP COLUMN|DROP TABLE|EXEC sp_rename|ALTER COLUMN .* NOT NULL' migrate.sql; then
  [ "$PR_LABEL" = "schema-breaking" ] || { echo "destructive DDL without review label"; exit 1; }
fi

Follow-ups

  • How do you avoid the gate becoming theatre? — Keep the rule list short and true; a check that fires on everything gets bypassed on everything.
  • What about teams on different EF versions? — Standardise the tooling version in the pipeline template, and track EF support dates as a fleet-level item — EF Core 8's support ends 10 November 2026, which is a scheduling fact, not a preference.
  • How do you handle the "we need it tonight" exception? — A named override with an owner and a follow-up ticket; unlogged exceptions are how policies die.

Wrong answer that gets people rejected

"We require a DBA to approve every migration." That is a queue, not a control: it scales linearly with teams, it delays safe changes as much as dangerous ones, and the DBA cannot tell from the DDL alone whether the deploy is rolling.

07DbContext lifetime and DI

Short sub-area, asked in almost every loop, and a fast disqualifier: a candidate who registers DbContext as a singleton has told the interviewer they have never debugged a concurrency exception in a web app. Screeners want the lifetime and the reason; mid-level wants the factory, Blazor and background services; senior and principal want the failure modes — captive dependencies, connection-pool exhaustion, and how you would catch them before production.

Docs: Microsoft Learn — DbContext lifetime, configuration and initialization

screenerWhat lifetime should DbContext have, and why?

Answer

Scoped — one per request in ASP.NET Core, which is what AddDbContext registers by default. The reasons are three: DbContext is not thread-safe, so a shared instance running two operations concurrently throws "A second operation was started on this context instance"; the change tracker accumulates entities, so a long-lived context leaks memory and hands out stale data; and the unit-of-work boundary should match the business operation, which for an API is the request. A singleton is wrong on all three counts, and a transient DbContext is subtly wrong too — different services in the same request would get different contexts and therefore different units of work, so a single SaveChanges no longer covers the whole operation. The related trap is the captive dependency: injecting a scoped DbContext into a singleton service pins one context for the process lifetime, which reproduces every singleton problem while looking correct in the registration code.

Example

builder.Services.AddDbContext<AppDb>(o => o.UseSqlServer(cs));   // scoped

// Captive dependency: this singleton holds one context forever.
builder.Services.AddSingleton<IPriceCache>(sp =>
    new PriceCache(sp.GetRequiredService<AppDb>()));   // wrong

// Correct: resolve a scope (or a factory) per unit of work.
builder.Services.AddSingleton<IPriceCache, PriceCache>();        // takes IServiceScopeFactory

Follow-ups

  • How do you catch captive dependencies? — ValidateScopes/ValidateOnBuild (on by default in Development) throws at startup; enable it in all environments and in a test.
  • What about parallel work inside one request? — Each parallel branch needs its own context from IDbContextFactory; you cannot share one across Task.WhenAll.
  • Does pooling change the lifetime? — No: AddDbContextPool is still scoped from the consumer's perspective; it only changes how the instance is obtained and reset.

Wrong answer that gets people rejected

"Singleton, so we don't pay the construction cost." Construction is cheap, the identity map is not, and the first concurrent request gives you an exception or, worse, interleaved reads. This is the single fastest way to fail an EF screen.

midWhen do you use IDbContextFactory instead of injecting the context?

Answer

Whenever the unit of work is not the DI scope. Four cases: background services and hosted jobs, where the "scope" is the whole process, so you create a context per work item; parallel work within one request, since a context cannot be shared across concurrent operations; Blazor Server, where the DI scope is the user's circuit — potentially hours long — and a scoped context would accumulate state for the whole session; and any code that needs several independent units of work in one call. AddDbContextFactory registers it, and you can register both the factory and a scoped context for the same type when different parts of the app need different patterns. The factory also composes with pooling (AddPooledDbContextFactory), which is the usual choice for high-rate background processing.

Example

builder.Services.AddPooledDbContextFactory<AppDb>(o => o.UseSqlServer(cs));

public sealed class ReconcileJob(IDbContextFactory<AppDb> factory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await using var db = await factory.CreateDbContextAsync(ct);   // fresh unit of work
            await ProcessBatchAsync(db, ct);
            await Task.Delay(TimeSpan.FromSeconds(30), ct);
        }
    }
}

Follow-ups

  • Why not just create a DI scope in the background service? — You can, and it is fine; the factory is simply more explicit about the lifetime and does not drag the rest of the scoped graph along.
  • Blazor Server specifics? — Microsoft's own guidance is the factory, because a circuit-scoped context also breaks under concurrent component renders.
  • Can you use both registrations? — Yes, AddDbContextFactory with lifetime: ServiceLifetime.Scoped or alongside AddDbContext; be deliberate about which one each layer takes.

Wrong answer that gets people rejected

"I inject the DbContext into my BackgroundService." That is a singleton capturing a scoped service; it either fails validation at startup or gives you one context alive for weeks.

midWhat causes "A second operation was started on this context instance"?

Answer

Two async operations on the same DbContext overlapping in time. The usual causes are a missing await (fire-and-forget query), Task.WhenAll over queries that share one context, an event handler or middleware touching the request's context concurrently with the handler, and — the sneaky one — a scoped context injected into something that outlives the scope, so two requests genuinely collide. The fix is never a lock: it is one context per concurrent operation, via IDbContextFactory for genuine parallelism, or sequential awaits when the parallelism was accidental. It is worth noting that database round trips are usually not your bottleneck in the way people assume — running three queries in parallel against the same database often just moves contention rather than removing it, so the sequential fix is frequently the right one on its own merits.

Example

// Throws: three concurrent operations on one context.
var (a, b, c) = await (db.Orders.CountAsync(),
                       db.Customers.CountAsync(),
                       db.Products.CountAsync()).WhenAll();

// Correct if you really want parallelism: a context per branch.
async Task<int> CountAsync<T>(Func<AppDb, IQueryable<T>> set)
{
    await using var ctx = await factory.CreateDbContextAsync();
    return await set(ctx).CountAsync();
}

Follow-ups

  • Why can't EF just queue the operations? — It could, and it deliberately does not: silently serialising would hide a concurrency bug in your code and make the transaction semantics ambiguous.
  • Is parallel querying worth it? — Sometimes, for genuinely independent, latency-bound calls; measure, because you are also multiplying connections and database contention.
  • How does this manifest intermittently? — Under load only, when the timing overlaps — which is why it typically ships to production and is diagnosed there.

Wrong answer that gets people rejected

"I wrap the context access in a SemaphoreSlim." You have serialised your own concurrency to work around a lifetime mistake, added a bottleneck, and left the actual bug — shared mutable state across operations — in place.

seniorHow do you configure per-request state — a tenant id, a user — on the context?

Answer

Through DI, into the context's constructor, with the deliberate consequence that you cannot use AddDbContextPool — a pooled instance resolves its dependencies once and reuses them, so a captured tenant becomes a cross-tenant data leak. The safe patterns are: inject an ITenantContext abstraction that reads from the ambient request (so the value is resolved per access, not captured), or pass the tenant explicitly to the factory when creating the context, or use pooling with an IDbContextFactory and set the state immediately after creation. Whichever you choose, the tenant filter itself belongs in OnModelCreating as a global query filter — and note that EF caches the compiled model per IModelCacheKeyFactory, so a filter that closes over a per-request value requires either a context-instance field (evaluated as a parameter at query time, which works) or a custom model cache key (which builds a model per tenant and is usually a mistake).

Example

public sealed class AppDb(DbContextOptions<AppDb> options, ITenantContext tenant) : DbContext(options)
{
    protected override void OnModelCreating(ModelBuilder mb)
        => mb.Entity<Order>().HasQueryFilter("Tenant", o => o.TenantId == tenant.Id);
        // EF10 named filter; the closure reads the instance field, so it becomes a parameter
}

// NOT AddDbContextPool: the injected ITenantContext would be captured by the pooled instance.
builder.Services.AddDbContext<AppDb>(o => o.UseSqlServer(cs));

Follow-ups

  • Why does a filter closing over a field work but a captured constant not? — EF parameterises the field read per query execution; a constant would be baked into the cached query and reused across tenants.
  • How do you test that isolation holds? — An integration test that writes as tenant A and asserts tenant B's context sees nothing, including through raw SQL paths, which filters do not cover.
  • What about connection-per-tenant? — Then the context needs the connection string at construction; use a factory and never pool across tenants.

Wrong answer that gets people rejected

"I inject the tenant and use AddDbContextPool for performance." That combination is a cross-tenant data leak waiting for the second request. If you name pooling here, you must name the constraint in the same breath.

seniorHow does EF interact with the ADO.NET connection pool, and what exhausts it?

Answer

EF opens a connection lazily, holds it for the duration of the operation, and returns it to the ADO.NET pool when the command or the enclosing transaction finishes — so under normal use a request holds a connection for milliseconds. Exhaustion (Timeout expired. The timeout period elapsed prior to obtaining a connection from the pool, default pool size 100 on SQL Server) comes from holding connections longer than that: a transaction opened across a slow external call, an IAsyncEnumerable that streams results while the consumer does I/O per row, a context that is never disposed because it escaped its scope, sync-over-async deadlocking threads, or simply more concurrent work than the pool allows. The diagnosis is to look at connection-pool counters and at how long connections are held, not at the query duration; the fix is almost always to shorten the hold — do the external call outside the transaction, buffer the stream, dispose properly — rather than to raise Max Pool Size, which just moves the failure to the database's connection limit.

Example

// Holds a connection AND a transaction across a network call: the classic exhauster.
await using var tx = await db.Database.BeginTransactionAsync(ct);
var order = await db.Orders.FirstAsync(o => o.Id == id, ct);
await paymentGateway.ChargeAsync(order.Total, ct);   // 2s p99, connection held throughout
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);

// Better: charge outside the transaction, record the result idempotently inside it.

Follow-ups

  • Which counters tell you? — Microsoft.Data.SqlClient event counters (active/free connections, pool waits) and EF's own connection events; APM traces showing time between "connection opened" and "closed".
  • Is raising Max Pool Size ever right? — Occasionally, for a genuinely high-concurrency, short-transaction service — after you have proven the holds are short.
  • What about MARS? — Multiple Active Result Sets lets one connection carry overlapping readers; it is a compatibility feature, not a concurrency strategy, and it does not make DbContext thread-safe.

Wrong answer that gets people rejected

"Increase the pool size / add retries." Both hide a hold-time problem and make the eventual failure worse — you now have 500 connections waiting on the same external call, and the database is the thing that falls over.

principalHow do you structure DbContextes in a large system — one, or many?

Answer

One context per bounded context (or per service), not one per aggregate and not one per database. A single giant context across a whole enterprise domain gets slow to build, impossible to reason about transactionally, and couples teams through OnModelCreating; a context per aggregate loses the ability to save related aggregates atomically and multiplies model-building cost with no benefit. Within one service, one context is usually right, with the model split across IEntityTypeConfiguration files so the file structure carries the modularity that the type does not. Two refinements worth naming: a separate read-only context (or just no-tracking queries) for reporting is fine and sometimes valuable if it points at a replica; and if two contexts must share a database, they must not both own the same tables — pick an owner, and have the other read through a view or a keyless entity type so migration ownership stays unambiguous. Model-building cost is real at scale (hundreds of entities can cost hundreds of milliseconds), and that is what compiled models are for.

Example

// Same database, two contexts, unambiguous ownership.
public sealed class SalesDb : DbContext            // owns sales.* tables + migrations
{
    protected override void OnModelCreating(ModelBuilder mb)
        => mb.HasDefaultSchema("sales")
             .ApplyConfigurationsFromAssembly(typeof(SalesDb).Assembly);
}

public sealed class ReportingDb : DbContext         // read-only, keyless views, no migrations
{
    protected override void OnModelCreating(ModelBuilder mb)
        => mb.Entity<OrderReportRow>().HasNoKey().ToView("vw_OrderReport", "reporting");
}

Follow-ups

  • How do you keep two contexts' migrations from colliding? — Separate history tables (MigrationsHistoryTable("__EFMigrationsHistory", "sales")) and separate schemas; run them in a defined order.
  • Cross-context transactions? — Share a connection and an explicit transaction (UseTransaction) if the same database; across databases you are into distributed transactions, which is a design smell to avoid.
  • When is model-building cost a real problem? — Serverless and scale-to-zero workloads, where every cold start pays it; that is the case compiled models exist for.

Wrong answer that gets people rejected

"One DbContext per aggregate root, that's proper DDD." Nothing in DDD says that, and it makes atomic multi-aggregate operations impossible while multiplying startup cost. Bounded context, not aggregate, is the unit.

08Concurrency and transactions

The correctness half of EF, and the sub-area where senior candidates most often fall apart: plenty of people can write a query, far fewer can say what happens when two users save the same row at the same instant. Screeners want optimistic concurrency and rowversion; mid-level wants DbUpdateConcurrencyException handling and explicit transactions; senior and principal want isolation levels, lock ordering, deadlock strategy, and the interaction between EF's execution strategy and transactions. Be concrete about the SQL: "EF adds the token to the WHERE clause and checks the affected row count" is the sentence that earns credit.

Docs: Microsoft Learn — Handling concurrency conflicts

screenerHow does optimistic concurrency work in EF Core?

Answer

You mark a property as a concurrency token — on SQL Server usually a rowversion mapped with [Timestamp] or IsRowVersion(), on PostgreSQL the system xmin column, or any column with IsConcurrencyToken(). EF then includes that token's original value in the WHERE clause of every UPDATE and DELETE for that entity and checks the affected row count: zero rows means somebody else changed (or deleted) the row since you loaded it, and EF throws DbUpdateConcurrencyException. Nothing is locked at any point — that is what "optimistic" means — so the cost is one extra column and a conflict you must handle, and the benefit is no blocking. The important part is what you do on conflict, which is a business decision: reload and merge, let the user resolve, retry with fresh data, or fail the request; silently retrying a blind overwrite defeats the entire mechanism.

Example

public class Order
{
    public int Id { get; set; }
    [Timestamp] public byte[] RowVersion { get; set; } = default!;   // or b.Property(...).IsRowVersion()
}

// UPDATE Orders SET Status = @p WHERE Id = @id AND RowVersion = @original;
// @@ROWCOUNT = 0  ->  DbUpdateConcurrencyException

Follow-ups

  • How does the client get the token back? — Round-trip it (in an ETag header or the DTO) and set it as the original value before saving: db.Entry(e).Property(x => x.RowVersion).OriginalValue = dto.RowVersion;
  • Concurrency token on a non-versioned column? — Any column works (IsConcurrencyToken), e.g. LastModifiedUtc; rowversion is preferred because the database maintains it and it changes on every write.
  • What about deletes? — Same mechanism; a zero row count on delete means someone already deleted or changed it, which is often benign and should be handled rather than thrown.

Wrong answer that gets people rejected

"EF locks the row when you load it." That is pessimistic concurrency and EF does not do it by default — reads take no locks beyond the isolation level's. Saying EF locks tells the interviewer you have never seen a lost update in production.

midYou catch a DbUpdateConcurrencyException. What do you actually do?

Answer

Decide, per field, whose value wins — there is no generic correct handler, which is exactly why EF throws instead of choosing. The mechanics: from the exception's Entries you get the entity, its CurrentValues (what you wanted to write), its OriginalValues (what you read), and GetDatabaseValuesAsync() (what is there now); with those three you can implement store-wins (refresh and abandon your change), client-wins (copy the database's token into your original values and re-save, overwriting), or a genuine merge where non-conflicting fields are combined and only true conflicts go to the user. Deleted-by-someone-else appears as a null from GetDatabaseValuesAsync and needs its own branch. Two production notes: retry loops must be bounded, and the merge must be applied to a fresh context in most designs, because a context that has thrown carries pending state you would otherwise re-apply.

Example

try { await db.SaveChangesAsync(ct); }
catch (DbUpdateConcurrencyException ex)
{
    foreach (var entry in ex.Entries)
    {
        var db_ = await entry.GetDatabaseValuesAsync(ct);
        if (db_ is null) throw new EntityDeletedException(entry.Metadata.Name);

        // Store wins for price, client wins for notes: an explicit business rule.
        var proposed = entry.CurrentValues.Clone();
        entry.OriginalValues.SetValues(db_);
        entry.CurrentValues.SetValues(db_);
        entry.CurrentValues["Notes"] = proposed["Notes"];
    }
    await db.SaveChangesAsync(ct);   // bounded retry, once
}

Follow-ups

  • What does the user see? — For an interactive edit, a diff and a choice; silently taking one side is how customers lose work and never find out.
  • How do you avoid the conflict entirely? — Narrow the write: ExecuteUpdateAsync with a predicate, or a counter/append model, so two users editing different fields never conflict.
  • Does EnableRetryOnFailure retry this? — No; concurrency conflicts are not transient failures, and retrying them blindly is a lost-update bug.

Wrong answer that gets people rejected

"Catch it and retry the save." Re-saving the same CurrentValues against refreshed originals is client-wins — you have deleted the other user's change and called it error handling.

midWhen do you need an explicit transaction, given that SaveChanges already has one?

Answer

When the atomic unit is bigger than one SaveChanges. The three real cases: two or more SaveChanges calls that must succeed together (usually a design smell, but real when a generated key from the first is needed by the second); mixing SaveChanges with ExecuteUpdateAsync/ExecuteDeleteAsync or raw SQL, which are not covered by the SaveChanges transaction; and coordinating two contexts on the same connection. You open it with Database.BeginTransactionAsync(), and if a retrying execution strategy is configured you must wrap the whole block in CreateExecutionStrategy().ExecuteAsync(...) or EF throws. TransactionScope also works and enlists ambient operations, but on .NET it needs care — async flow requires TransactionScopeAsyncFlowOption.Enabled, and promotion to a distributed transaction is only supported on Windows, so it is a poor default in containerised services.

Example

var strategy = db.Database.CreateExecutionStrategy();
await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    db.Orders.Add(order);
    await db.SaveChangesAsync(ct);                       // needs order.Id

    await db.Inventory.Where(i => i.Sku == sku)
        .ExecuteUpdateAsync(s => s.SetProperty(i => i.Reserved, i => i.Reserved + qty), ct);

    await tx.CommitAsync(ct);
});

Follow-ups

  • Why isn't ExecuteUpdate in the SaveChanges transaction? — It executes immediately as its own statement; if you need atomicity with tracked changes, you must open the transaction yourself.
  • How do two contexts share a transaction? — Create one DbConnection, pass it to both, and ctx2.Database.UseTransaction(ctx1.Database.CurrentTransaction!.GetDbTransaction()).
  • What about savepoints? — EF Core 5+ creates them automatically around SaveChanges inside a user transaction so a failure rolls back only that save; you can also create them explicitly.

Wrong answer that gets people rejected

"SaveChanges is transactional, so I never need one." True until the first ExecuteDelete or the first two-step save — and then you have a partial write with no transaction, which is the bug this question exists to find.

seniorWhat isolation level does EF use, and when would you change it?

Answer

EF does not choose one: it uses the connection's/database's default, which is READ COMMITTED on SQL Server (locking, unless READ_COMMITTED_SNAPSHOT is on) and on PostgreSQL, and it never changes it implicitly. You raise it when you need a guarantee the default does not give: REPEATABLE READ or SERIALIZABLE for read-modify-write logic that must not see a changed row mid-transaction, and SNAPSHOT on SQL Server when you want consistent reads without blocking writers. You lower it essentially never — READ UNCOMMITTED / NOLOCK buys you dirty reads, missing rows and duplicated rows from page splits, which is a much worse trade than most .NET teams believe. My default recommendation on SQL Server is to turn on READ_COMMITTED_SNAPSHOT at the database level, which removes most reader-writer blocking without changing a line of application code, and then use optimistic concurrency tokens for the lost-update problem rather than reaching for higher isolation.

Example

await using var tx = await db.Database
    .BeginTransactionAsync(System.Data.IsolationLevel.Serializable, ct);

// Read-modify-write that must be serialisable:
var seat = await db.Seats.FirstAsync(s => s.Id == seatId, ct);
if (seat.IsBooked) throw new SeatTakenException();
seat.IsBooked = true;
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);

Follow-ups

  • What does SERIALIZABLE cost? — Range locks and a much higher deadlock rate; on SQL Server it is often better to use a unique constraint or an atomic conditional update instead.
  • Is the seat example better done another way? — Yes: ExecuteUpdateAsync with Where(s => s.Id == id && !s.IsBooked) and checking the affected count is a single atomic statement with no transaction at all.
  • Why is NOLOCK so popular then? — It made blocking disappear on pre-snapshot SQL Server installations; READ_COMMITTED_SNAPSHOT solves the same problem correctly.

Wrong answer that gets people rejected

"We use NOLOCK everywhere for performance." It is not a performance feature, it is a correctness downgrade: you can read rows twice, miss committed rows, and read data that never existed. Saying it casually is a red flag for a senior data role.

seniorHow do you deal with deadlocks in an EF-based service?

Answer

Deadlocks are almost always a lock-ordering problem, so the first move is to capture the deadlock graph (extended events on SQL Server) and find the two resource orders that cross. Common EF-specific causes: a batch of updates whose order varies per request because it comes from a HashSet or LINQ over a dictionary; two code paths that touch parent and child in opposite order; and an index or lock-escalation issue where a large SaveChanges batch escalates to a table lock. Fixes in order: make the order deterministic (sort by key before saving); shrink the transaction so the window is smaller; add or fix indexes so the update seeks instead of scanning a range; and only then add a bounded retry for error 1205, understanding that a retry is compensation, not a cure. Framing that earns points: a deadlock is the database enforcing a correctness invariant you violated by design, so treating it as a transient error to be retried is how a 0.1% error rate becomes a 5% one under load.

Example

// Deterministic lock order: every writer touches rows in ascending key order.
foreach (var line in incoming.OrderBy(l => l.Id))
    db.Entry(line).State = EntityState.Modified;
await db.SaveChangesAsync(ct);

// Only after that, a bounded retry for the residual:
options.UseSqlServer(cs, o => o.EnableRetryOnFailure(
    maxRetryCount: 3, maxRetryDelay: TimeSpan.FromSeconds(2), errorNumbersToAdd: [1205]));

Follow-ups

  • Why does EF's batch ordering matter? — EF orders by dependency, not by key, so within a table the order follows your enumeration; making that deterministic is on you.
  • How do you catch it before production? — A concurrency test that runs the same operation from N tasks against a real database; deadlocks are reproducible under load in a way they are not in unit tests.
  • What about lock escalation? — Above ~5,000 locks SQL Server escalates to a table lock; smaller MaxBatchSize and chunked ExecuteUpdate loops keep you under it.

Wrong answer that gets people rejected

"Add a retry policy for deadlocks." That is step four presented as step one. Without the deadlock graph you do not know whether you are retrying a 1-in-10,000 race or papering over an ordering bug that will scale linearly with traffic.

seniorHow do you implement pessimistic locking when you genuinely need it?

Answer

EF Core has no first-class pessimistic locking API, so you drop to SQL for the lock hint and keep everything else in EF. On SQL Server that is FromSql with WITH (UPDLOCK, ROWLOCK) inside an explicit transaction; on PostgreSQL it is SELECT … FOR UPDATE. You need it when the work between read and write is not expressible as an atomic conditional update and a conflict is expected rather than rare — an inventory allocation across several rows, a ticketing seat map under a flash sale, or an external side effect you cannot compensate. The costs to name unprompted: the lock is held for the whole transaction, so any slow call inside it multiplies contention; the lock order must be deterministic or you have swapped concurrency conflicts for deadlocks; and it does not survive a distributed system — two services on two databases need a different mechanism entirely. For everything else, optimistic concurrency plus a conditional ExecuteUpdate is cheaper and scales better.

Example

await using var tx = await db.Database.BeginTransactionAsync(ct);

var account = await db.Accounts
    .FromSql($"SELECT * FROM Accounts WITH (UPDLOCK, ROWLOCK) WHERE Id = {accountId}")
    .SingleAsync(ct);                       // row is locked until commit

account.Balance -= amount;
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);

Follow-ups

  • Can you avoid the lock here? — Usually: ExecuteUpdateAsync with Where(a => a.Id == id && a.Balance >= amount) and a zero-affected-rows check is atomic, lock-free and one round trip.
  • Does FromSql still respect query filters? — Composition over FromSql applies filters to the outer query, but the raw SQL itself does not; check your tenant predicate is present.
  • Distributed alternative? — A lease/lock row with an expiry, or a dedicated lock service; database row locks do not extend across services.

Wrong answer that gets people rejected

"I'd use a C# lock or a distributed cache lock." A process-level lock protects nothing once you scale to two instances, and a cache lock without fencing tokens is not a lock at all. If the invariant is in the database, the enforcement belongs there.

principalDesign the write path for a system where the same record is updated by a UI, a batch job and a webhook.

Answer

I would start by refusing the framing: three writers on one mutable row is the problem, so the first design question is whether the record can become append-only — events or state transitions with the current state derived or maintained incrementally — because that removes conflicts rather than resolving them. If it must stay a mutable row: give it a rowversion and make every writer round-trip it, so lost updates become explicit failures; make each writer's update as narrow as possible (ExecuteUpdateAsync with a conditional predicate, touching only its own fields) so the UI's note edit and the batch's status change do not collide at all; give the webhook an idempotency key with a unique index, because webhooks retry and at-least-once delivery is guaranteed; and define, in writing, a precedence rule for genuine conflicts — typically system-of-record wins over batch wins over UI, with the UI told what happened rather than silently overwritten. Operationally I would add a conflict-rate metric, because the design's assumption ("conflicts are rare") must be monitored, not assumed.

Example

// Narrow, atomic, conflict-free per writer:
var updated = await db.Shipments
    .Where(s => s.Id == id && s.Status == ShipmentStatus.Pending)
    .ExecuteUpdateAsync(s => s
        .SetProperty(x => x.Status, ShipmentStatus.Dispatched)
        .SetProperty(x => x.DispatchedUtc, now), ct);

if (updated == 0)      // someone else moved it on: not an error, a state fact
    await HandleAlreadyDispatchedAsync(id, ct);

Follow-ups

  • Why does the webhook need an idempotency key rather than a token? — It has no "loaded version" to compare against; deduplication is the only correct mechanism for at-least-once delivery.
  • What if the batch job must win? — Then say so explicitly and enforce it (the batch's update is unconditional, the UI's is conditional); undocumented precedence is the actual bug in most such systems.
  • How do you make the append-only version work? — Store transitions as rows with a unique constraint on (aggregate, sequence) so concurrent writers collide on the constraint rather than overwriting each other.

Wrong answer that gets people rejected

"Serialise all writes through a queue so there's only one writer." It is a real pattern, but offered as the first answer it trades an availability and latency problem for a concurrency one and does not remove the need for idempotency — the queue also delivers at least once.

09Bulk operations

Asked more each year, because ExecuteUpdate/ExecuteDelete (EF Core 7+) changed what EF can do without a third-party library, and because the trade-offs are a clean test of whether you understand the change tracker. Expect one mechanical question and one judgment question about when EF stops being the right tool. EF Core 10's additions — JSON/complex-type support and the statement-lambda signature — are current-knowledge markers here.

Docs: Microsoft Learn — ExecuteUpdate and ExecuteDelete

midWhat do ExecuteUpdateAsync and ExecuteDeleteAsync do, and how do they differ from SaveChanges?

Answer

They translate a LINQ query into a single UPDATE … FROM or DELETE … FROM statement and execute it immediately, returning the number of affected rows. Nothing is loaded, nothing is tracked, no SaveChanges is involved — which is why they can change a million rows in one statement rather than a million round trips. The differences that matter: they run immediately, so they are not part of the SaveChanges transaction unless you opened one yourself; they bypass the change tracker, so entities already tracked in your context are now stale and will happily overwrite your bulk change on a later save; and they bypass SaveChanges interceptors, so audit stamping and domain events do not fire. Global query filters are applied, which is the one safety net that survives. Use them for set-based maintenance — soft-delete sweeps, status transitions, backfills — and keep SaveChanges for aggregate-shaped work where the invariants live in the domain.

Example

var deactivated = await db.Users
    .Where(u => u.LastLoginUtc < cutoff && u.IsActive)
    .ExecuteUpdateAsync(s => s
        .SetProperty(u => u.IsActive, false)
        .SetProperty(u => u.DeactivatedUtc, now), ct);

var purged = await db.AuditEvents
    .Where(a => a.CreatedUtc < retentionCutoff)
    .ExecuteDeleteAsync(ct);

Follow-ups

  • What happened to the old RemoveRange approach? — It loads every entity, tracks it, and issues a batched DELETE per row; ExecuteDelete is one statement and no materialisation.
  • How do you keep audit fields correct? — Set them explicitly in the SetProperty calls; interceptors do not run, and forgetting this is the most common bug when teams adopt these APIs.
  • Is there a bulk insert equivalent? — Not in EF as of EF Core 10; use AddRange + SaveChanges for moderate volumes, or SqlBulkCopy/COPY/a bulk-extension library for large ones.

Wrong answer that gets people rejected

"They're just a faster SaveChanges." They are a different execution model — immediate, untracked, uninterceptable — and treating them as a drop-in replacement is how audit columns stop updating and tracked entities silently revert changes.

midWhat changed about ExecuteUpdateAsync in EF Core 10?

Answer

Two things, and both matter in real code. First, the setters argument is now a regular statement lambda instead of an expression tree, so you can build the set of updates conditionally with ordinary if statements — previously this required hand-constructing Expression.Call nodes, which was the single ugliest snippet in most EF codebases. Second, ExecuteUpdateAsync now works over JSON columns, provided the type is mapped as a complex type with ToJson() rather than as an owned entity; on SQL Server 2025 / Azure SQL it emits the efficient .modify() JSON function, and on older versions it falls back to string manipulation of the nvarchar(max). The first change is also a breaking change: code that built Expression<Func<SetPropertyCalls<T>, SetPropertyCalls<T>>> no longer compiles, which is one of the more likely compile errors on an EF9 → EF10 upgrade.

Example

// EF Core 10: plain statement lambda, conditional setters
await db.Blogs.Where(b => b.Id == id).ExecuteUpdateAsync(s =>
{
    s.SetProperty(b => b.Views, b => b.Views + 1);
    if (nameChanged) s.SetProperty(b => b.Name, newName);
}, ct);

// EF Core 10: update a property inside a JSON-mapped complex type
mb.Entity<Blog>().ComplexProperty(b => b.Details, d => d.ToJson());
await db.Blogs.ExecuteUpdateAsync(s => s.SetProperty(b => b.Details.Views, b => b.Details.Views + 1), ct);

Follow-ups

  • Why does it only work for complex types, not owned entities? — Owned types are entity types with identity and reference semantics; bulk assignment over them has no well-defined meaning, which is a large part of why complex types exist.
  • What SQL does the JSON update produce? — On SQL Server 2025: SET [Details].modify('$.Views', JSON_VALUE(...) + 1) — an in-place JSON mutation rather than a rewrite of the whole document.
  • Any other EF10 gotcha in the same area? — Nested complex-type column names changed to full-path form, so an upgrade generates renames you must review before shipping.

Wrong answer that gets people rejected

"You still have to build expression trees for dynamic setters." That was the pain point EF10 removed. Not knowing it suggests you have not touched the current LTS.

seniorYou need to update 20 million rows. Walk me through it.

Answer

Not in one statement. A single 20-million-row UPDATE is one enormous transaction: the log grows to hold every row image, locks escalate to a table lock so the application blocks, replication or Always On lags, and if it fails at minute 40 you roll back for another 40. Instead, chunk it by key range — Where(x => x.Id > last && x.Id <= last + 5000) with ExecuteUpdateAsync — recording progress so the job is resumable, with a small delay between batches to let replication and other workloads breathe, and a kill switch. Size the batch by measured duration, not by row count: aim for roughly one to five seconds per batch so a cancellation never leaves a long-running transaction. Do it during a low-traffic window if the table is hot, monitor lock waits and replication lag while it runs, and — because this is a data change, not a schema change — make it a job with observability rather than a migration, since migrations have no progress reporting and a failed one leaves ambiguous state.

Example

long last = await state.GetCursorAsync(ct);
while (!ct.IsCancellationRequested)
{
    var sw = Stopwatch.StartNew();
    var n = await db.Invoices
        .Where(i => i.Id > last && i.Id <= last + BatchSize && i.Currency == null)
        .ExecuteUpdateAsync(s => s.SetProperty(i => i.Currency, "EUR"), ct);

    last += BatchSize;
    await state.SaveCursorAsync(last, ct);
    if (last >= maxId) break;
    if (sw.Elapsed > TimeSpan.FromSeconds(5)) BatchSize /= 2;   // adapt to load
    await Task.Delay(100, ct);
}

Follow-ups

  • Why range by key rather than Take? — Take without a cursor re-scans from the start each iteration and gets slower every batch; a key range is a seek.
  • What do you watch while it runs? — Lock waits, log growth/VLF count, replication or AG lag, and application p99 — any of which is a reason to slow down.
  • Would you ever use a migration for this? — Only for small, deterministic data fixes; anything measured in minutes belongs in a job, with the migration confined to the schema part.

Wrong answer that gets people rejected

"One ExecuteUpdateAsync over the whole table — that's what it's for." It is not: one statement means one transaction, one lock escalation and one very long rollback. Batching is the expected answer, and the interviewer is listening for log and lock reasoning.

seniorHow do you do a bulk insert with EF, and when do you leave EF behind?

Answer

EF has no bulk-insert API even in EF Core 10, so the options are graded by volume. Up to a few thousand rows, AddRange + one SaveChanges is fine — it batches, and if you disable auto-detect and clear the tracker between chunks it is acceptable. Beyond that, the change tracker and the parameter limits dominate, and you switch to the provider's native bulk path: SqlBulkCopy on SQL Server (which streams through TDS and bypasses per-row logging with minimal-logging conditions), COPY via Npgsql's binary importer on PostgreSQL, or a well-maintained bulk-extension library if you want to stay in EF's idiom. The pattern that keeps both worlds honest is to bulk-load into a staging table and then do the set-based MERGE/insert-select from there, which gives you validation, idempotency and a transaction boundary you control. Keep EF for the model and the migrations that define the staging table, so there is still one source of truth for the schema.

Example

// Stage with SqlBulkCopy, then merge set-based — EF still owns the schema.
using var conn = new SqlConnection(cs);
await conn.OpenAsync(ct);
using (var bulk = new SqlBulkCopy(conn) { DestinationTableName = "staging.Prices", BatchSize = 10_000 })
    await bulk.WriteToServerAsync(ToDataReader(rows), ct);

await db.Database.ExecuteSqlRawAsync("""
    MERGE dbo.Prices AS t
    USING staging.Prices AS s ON t.Sku = s.Sku
    WHEN MATCHED THEN UPDATE SET t.Amount = s.Amount
    WHEN NOT MATCHED THEN INSERT (Sku, Amount) VALUES (s.Sku, s.Amount);
    """, ct);

Follow-ups

  • What limits AddRange + SaveChanges? — MaxBatchSize (42 by default on SQL Server), the 2,100-parameter limit, and DetectChanges cost as the tracker grows.
  • Do bulk-extension libraries have a downside? — They track EF's internals, so they can lag a major EF release — a real scheduling risk when you plan an upgrade to a new LTS.
  • How do you make the load idempotent? — Stage plus MERGE on a natural key, or a unique index and INSERT … WHERE NOT EXISTS; re-running an ETL must be safe.

Wrong answer that gets people rejected

"Loop with Add and call SaveChanges every iteration." Worst of both worlds: one round trip per row plus a quadratic DetectChanges cost. Interviewers ask this specifically because they have seen it in production.

seniorHow do bulk operations interact with soft delete, auditing and multi-tenancy?

Answer

Query filters do apply to ExecuteUpdate/ExecuteDelete, so your tenant and soft-delete predicates are still in the WHERE clause — that is the good news and it is worth stating precisely, because people assume otherwise. Interceptors and SaveChanges overrides do not run, so audit stamping, domain events and outbox writes are all skipped: if your soft-delete is implemented in a SaveChanges override that flips Deleted to Modified, then ExecuteDeleteAsync performs a hard delete and quietly defeats it. The practical rules I would give a team: implement soft delete as a query filter plus an explicit SetProperty(x => x.IsDeleted, true) in bulk paths, never rely on an override to catch it; set audit columns explicitly in every bulk statement; and if a bulk change must produce events, write the outbox rows in the same explicit transaction. A lint rule or code review checklist for "every ExecuteUpdate sets the audit columns" is cheap and catches the recurring case.

Example

// Filter applies automatically; audit does not — set it explicitly.
await db.Documents
    .Where(d => d.ProjectId == projectId)          // + tenant filter + !IsDeleted filter
    .ExecuteUpdateAsync(s => s
        .SetProperty(d => d.IsDeleted, true)
        .SetProperty(d => d.DeletedUtc, now)
        .SetProperty(d => d.ModifiedBy, userId), ct);

Follow-ups

  • How do you bypass the filter deliberately? — IgnoreQueryFilters(), and in EF Core 10 you can disable a single named filter — IgnoreQueryFilters(["SoftDeletionFilter"]) — keeping the tenant filter in force.
  • Why is that EF10 feature important? — Before it, "show me deleted rows too" meant dropping all filters including the tenant one, which is a genuine data-leak footgun.
  • How do you test it? — Assert the generated SQL contains the tenant predicate for bulk paths; it is one ToQueryString-style test per bulk operation.

Wrong answer that gets people rejected

"Bulk operations skip query filters too, so they're dangerous." Half-true reversed: filters apply, interceptors do not. Getting it backwards means you would either add redundant predicates or, worse, assume audits are being written when they are not.

10JSON, complex and owned types

This is the fastest-moving part of EF and therefore a favourite "are you current" probe: JSON columns arrived in EF Core 7, complex types in 8, primitive collections in 8, and EF Core 10 made complex types optional, struct-capable, JSON-mappable and bulk-updatable while adding the native SQL Server 2025 json type and vector search. The question behind the questions is a modelling one — when does a chunk of data deserve its own table, and when is it a document inside a row.

Docs: Microsoft Learn — Complex types

midHow does EF map JSON columns, and can you query inside them?

Answer

Since EF Core 7 you can map an owned type — and since EF Core 10 a complex type — to a single JSON column with ToJson(), and EF translates LINQ over its properties into the database's JSON functions: JSON_VALUE on SQL Server, the ->> operators on PostgreSQL. So Where(b => b.Details.Viewers > 3) becomes a real SQL predicate, not client-side filtering, and you can project, order and update individual JSON properties. EF Core 10 added the native SQL Server 2025 / Azure SQL json data type: with UseAzureSql or compatibility level 170+, EF now defaults to json instead of nvarchar(max), which is more efficient and safer — and note the migration consequence, that existing JSON columns are automatically changed to the new type on the first migration unless you opt out. The performance caveat that separates a strong answer: a predicate on a JSON property is generally not indexable the way a column is, so filtering by it at scale needs a computed column with an index, or a real column.

Example

mb.Entity<Blog>().ComplexProperty(b => b.Details, d => d.ToJson());   // EF10

var busy = await db.Blogs.Where(b => b.Details.Viewers > 3).ToListAsync(ct);
// SELECT ... WHERE JSON_VALUE([b].[Details], '$.Viewers' RETURNING int) > 3

// Indexable filter over a JSON property:
mb.Entity<Blog>().Property<int>("ViewersIdx")
  .HasComputedColumnSql("CAST(JSON_VALUE([Details], '$.Viewers') AS int)", stored: true);

Follow-ups

  • What does the automatic column-type change mean for an upgrade? — Review the first EF10 migration: it will alter nvarchar(max) JSON columns to json on compatible servers; opt out by pinning the column type or the compatibility level.
  • Owned or complex for JSON? — Complex, in EF10: it supports collections, value semantics and ExecuteUpdateAsync, none of which owned types give you.
  • What about updating one property? — EF10 emits an in-place .modify() on SQL Server 2025 rather than rewriting the whole document.

Wrong answer that gets people rejected

"JSON columns are just strings, you have to filter in memory." Not since EF Core 7 — the properties are translated. This one dates you by three major versions in a single sentence.

midWhat are primitive collections, and when do you use one instead of a table?

Answer

EF Core 8 added first-class mapping for collections of primitives — string[], List<int>, List<DateOnly> — stored as a JSON array in a single column, with LINQ support: Contains, Count, indexing, and even Any/All over the elements translate to the database's JSON functions. They replace the old pattern of a value converter plus a hand-written comparer, and on SQL Server 2025 / Azure SQL EF10 stores them in the native json type. Use one when the collection is small, owned entirely by the row, and never queried in a way that needs an index — tags, feature flags, a handful of allowed values. Use a real table when you need to join to the elements, enforce referential integrity, index them, or when the collection can grow unbounded; a JSON array of 50,000 ids is a design mistake that will only surface under production data volume.

Example

public class Blog { public string[] Tags { get; set; } = []; }

// EF8+: one column, no configuration needed; json type on SQL Server 2025 with EF10.
var tagged = await db.Blogs.Where(b => b.Tags.Contains("efcore")).ToListAsync(ct);
var many   = await db.Blogs.Where(b => b.Tags.Length > 3).ToListAsync(ct);

Follow-ups

  • How is Contains over a mapped column translated? — Via the provider's JSON reader (OPENJSON on SQL Server); note this is the column case, distinct from the parameterised-collection case EF10 changed.
  • Can you index a primitive collection? — Not directly; a computed column or a full-text/JSON index depending on the provider, or a join table if querying matters.
  • What did this replace? — HasConversion to a JSON string plus a ValueComparer, which people routinely got wrong and lost updates with.

Wrong answer that gets people rejected

"You need a value converter for that." Not since EF Core 8 — and the converter version needs a comparer you probably would have forgotten, which is precisely the bug primitive collections removed.

seniorWhen should a piece of data be a JSON document rather than related tables?

Answer

The test I use is three questions. Does anything outside this row need to reference it — a foreign key, a report, another service? If yes, it is a table. Do you need to query or aggregate across many rows by its contents at scale? If yes, it is a table (or at minimum a computed, indexed column). Does it change independently of its owner, with its own concurrency? If yes, it is a table. If all three are no — configuration blobs, snapshots of an external payload, a form's answers, versioned settings, an address that is only ever read with its customer — then JSON is a genuinely better fit: fewer joins, no cartesian explosion, and the shape can evolve without a migration. The last point is also the main risk: schema-on-read means bad data is only discovered when something tries to deserialise it, so JSON needs validation on the write path and a plan for versioning the document shape.

Example

// Good JSON: the third-party payload we store verbatim for audit and replay.
mb.Entity<WebhookDelivery>().ComplexProperty(d => d.Payload, p => p.ToJson());

// Bad JSON: line items, which reporting joins to and finance aggregates over.
mb.Entity<Order>().HasMany(o => o.Lines).WithOne(l => l.Order);

Follow-ups

  • How do you version a document shape? — A version discriminator inside the document plus tolerant deserialisation; migrations cannot help you here, which is the trade.
  • Does JSON hurt row size? — On SQL Server large documents go off-row (LOB), so a wide JSON column can add a lookup to queries that do not select it — another reason to project.
  • Cosmos changes this calculus? — Yes: on a document database the default is the document, and EF's Cosmos provider models exactly that; EF10 also made Cosmos vector search stable and added full-text and hybrid (Rrf) search.

Wrong answer that gets people rejected

"JSON is faster because there are no joins." Sometimes, for the read that matches the document's shape — and much slower for every read that does not, with no index to save you. The expected answer is a decision rule, not a preference.

seniorWhat is EF Core 10's vector search support, and where does it fit?

Answer

EF Core 10 added full support for the vector data type on Azure SQL Database and SQL Server 2025: you declare a property of type SqlVector<float> with a dimension (vector(1536)), store an embedding through normal SaveChanges, and query similarity with EF.Functions.VectorDistance("cosine", …) in an OrderBy — which means retrieval-augmented generation over your existing relational data does not require a separate vector database. On the Cosmos side, EF10 took vector similarity search out of preview, renamed the model-building APIs to IsVectorProperty/IsVectorIndex, and added full-text search plus hybrid search combining both via EF.Functions.Rrf (reciprocal rank fusion). The honest architectural point to add: this is exact/brute-force distance in EF10 — approximate nearest-neighbour with DiskANN indexes and VectorSearch()/WithApproximate() is arriving in EF Core 11 — so at large corpus sizes you are still choosing between recall, latency and a purpose-built store.

Example

public class Blog
{
    [Column(TypeName = "vector(1536)")]
    public SqlVector<float> Embedding { get; set; }
}

var top = await db.Blogs
    .OrderBy(b => EF.Functions.VectorDistance("cosine", b.Embedding, queryVector))
    .Take(3)
    .ToListAsync(ct);

Follow-ups

  • Why keep embeddings next to the relational data? — You can filter by tenant, permissions and date in the same query, which is exactly the part that is painful when the vectors live in a separate store.
  • What is the EF11 addition? — DiskANN vector indexes and approximate search (VectorSearch() with WithApproximate()), turning an exact scan into an indexed ANN lookup.
  • What about generating the embeddings? — Outside EF: IEmbeddingGenerator<string, Embedding<float>> from Microsoft.Extensions.AI, then store the result like any other property.

Wrong answer that gets people rejected

"EF doesn't do vectors, you need a vector database." As of November 2025 it does, on Azure SQL and SQL Server 2025 and on Cosmos. Saying otherwise in 2026 is the clearest possible signal that you have not looked at the current LTS.

seniorHow do you migrate an existing owned-entity model to complex types?

Answer

Incrementally, one type at a time, and with a migration diff as the proof at each step. For a table-split owned type the column names are usually the same shape (Address_City), so the change is often schema-neutral: switch OwnsOne to ComplexProperty, add a migration, and confirm it is empty — that is your evidence. Where it is not neutral, EF Core 10's breaking change bites: nested complex types now use the full path in column names, so a two-level nesting that was Nested_Property becomes Complex_Nested_Property and you get renames to review. The behavioural differences are the reason to do it: complex types compare by value in LINQ, can be assigned between properties, support ExecuteUpdateAsync, and can be optional and struct-typed in EF10. The constraints to check before you start: the complex type needs at least one required property if it is optional, and collections of structs are not supported — so a few types will have to stay as they are.

Example

// Before (EF Core 3–9 style)
mb.Entity<Customer>().OwnsOne(c => c.ShippingAddress);

// After (EF Core 8+, fully capable in EF10)
mb.Entity<Customer>().ComplexProperty(c => c.ShippingAddress);

// The proof: this migration should be empty for a table-split move.
// dotnet ef migrations add MoveAddressToComplexType

Follow-ups

  • What if it is not empty? — Read every operation; a rename is fine after review, a drop-and-add is data loss and must be rewritten by hand in the migration.
  • Which owned types should stay owned? — Ones that genuinely behave like entities (queried independently, referenced, with their own lifecycle) — those were never value objects.
  • Is there a runtime behaviour change to test? — Yes: equality and assignment semantics change, so any code relying on reference identity of the owned instance needs a test pass.

Wrong answer that gets people rejected

"Just change OwnsOne to ComplexProperty everywhere and ship it." Without reading the generated migration — especially on EF10 with the nested-column-name change — you can ship a migration that drops columns and their data.

principalA team wants to store a large, evolving document per record "so we stop doing migrations". How do you respond?

Answer

I would agree that it removes migrations and point out precisely what it substitutes for them, then let the trade-off decide rather than the preference. What you gain: schema evolution without DDL, no cross-team migration coordination, and a natural fit for genuinely heterogeneous data. What you pay: validation moves from the database to every reader, so bad data is discovered at read time in production rather than at write time in a migration; you still have versioning, just implicit and untested; querying and reporting across records becomes expensive and often needs a computed column, a projection table or a separate analytics path; and referential integrity is gone, so orphan references become an application concern. My concrete counter-proposal is usually a split: the fields the system reasons about — the ones in queries, joins, indexes and reports — stay as columns, and the genuinely open-ended part becomes a JSON complex type, which EF10 supports natively including bulk updates. If they still want the full document, I would ask for three things before agreeing: a version field, a validation schema enforced on write, and a named owner for the read-side query story.

Example

public class Submission
{
    public Guid Id { get; set; }                 // queried
    public string TenantId { get; set; } = "";   // queried, indexed, filtered
    public SubmissionState State { get; set; }   // queried, reported on
    public DateTime CreatedUtc { get; set; }     // queried, ordered by
    public FormAnswers Answers { get; set; } = new();   // genuinely open-ended -> JSON
}

mb.Entity<Submission>().ComplexProperty(s => s.Answers, a => a.ToJson());

Follow-ups

  • What if reporting later needs a field inside the document? — Promote it: a stored computed column with an index, or a real column with a backfill — which is a migration, demonstrating that the cost was deferred, not removed.
  • How do you validate on write? — A JSON schema check in the application (or a database CHECK with ISJSON/schema validation where supported), plus contract tests for each document version.
  • Does this change if they move to Cosmos? — The document becomes the natural unit, and EF's Cosmos provider models it well — but the query and indexing costs move to RU planning, not away.

Wrong answer that gets people rejected

"No, we use a relational database, everything should be normalised." Refusing without engaging the trade-off is the wrong altitude for a principal question; so is agreeing without naming validation, versioning and the read-side query story.

11Testing EF code

Asked because it separates people who have shipped an EF service from people who have read about one: the in-memory provider is a trap that every team falls into once, and testcontainers are now the default answer. Mid-level questions are about the mechanics; senior and principal questions are about the test pyramid for a data layer — what is worth a real database, what is worth a fake, and how you keep the suite under a few minutes with hundreds of tests.

Docs: Microsoft Learn — Testing EF Core applications

screenerHow do you test code that uses EF Core?

Answer

Three layers, deliberately unequal in size. Pure domain logic gets ordinary unit tests with no DbContext at all, which is the argument for keeping invariants in entities rather than in query code. Anything that queries gets an integration test against the real database engine, because the thing you are testing — translation, filters, constraints, concurrency — only exists in the provider; Testcontainers spinning up SQL Server or PostgreSQL per test run is the standard approach and is fast enough with a shared container and per-test transactions or a respawned schema. The third layer is a small number of "SQL shape" tests using ToQueryString() to assert that a critical query stays one round trip and keeps its tenant predicate. What I avoid is the in-memory provider, which does not behave like a relational database in the ways that matter, and heavy mocking of DbSet, which tests the mock rather than the code.

Example

public sealed class DbFixture : IAsyncLifetime
{
    private readonly MsSqlContainer _sql = new MsSqlBuilder().Build();
    public string ConnectionString => _sql.GetConnectionString();

    public async Task InitializeAsync()
    {
        await _sql.StartAsync();
        await using var db = new AppDb(Options(ConnectionString));
        await db.Database.MigrateAsync();     // proves the migrations work, too
    }
    public Task DisposeAsync() => _sql.DisposeAsync().AsTask();
}

Follow-ups

  • How do you isolate tests sharing one container? — A transaction rolled back per test, Respawn to reset tables, or a schema/database per test class; pick by how much data each test needs.
  • Doesn't this slow CI down? — Container start is seconds and amortised across the run; the alternative is a fast suite that fails to catch the bugs it exists for.
  • What about SQLite in-memory? — A reasonable middle ground for simple models, but its type system and constraint behaviour differ from SQL Server, so it still gives false confidence on the hard cases.

Wrong answer that gets people rejected

"I mock DbSet<T> with Moq and assert the LINQ." You have tested LINQ-to-Objects. Every translation, filter, constraint and concurrency behaviour — the actual risk surface — is untested by construction.

midWhy is the in-memory provider a bad test database?

Answer

Because it is not a relational database and Microsoft explicitly says not to use it for testing query behaviour. It enforces no referential integrity, no unique constraints beyond keys, no NOT NULL, no column length; it has no notion of transactions or concurrency tokens in the way a real provider does; and above all it does not translate — every LINQ query runs as LINQ-to-Objects, so queries that would throw "could not be translated" against SQL Server pass happily, and case sensitivity, collation, null-ordering and decimal precision are all wrong. The consequence is the worst kind of test suite: green locally, failing in production for reasons the tests were meant to cover. If you cannot run a container, SQLite (file or :memory: with a kept-open connection) is a far better fake because it is at least a real relational engine with real translation — with the caveat that its type affinity and lack of some SQL Server features still differ.

Example

// SQLite in-memory: a real provider, real translation. Keep the connection open
// or the database disappears.
var conn = new SqliteConnection("Filename=:memory:");
await conn.OpenAsync();
var options = new DbContextOptionsBuilder<AppDb>().UseSqlite(conn).Options;
await using var db = new AppDb(options);
await db.Database.EnsureCreatedAsync();

Follow-ups

  • Is the in-memory provider ever appropriate? — For testing code that merely uses a context as a store with no query semantics — rare, and usually a sign the abstraction is wrong.
  • What breaks first when teams use it? — Unique constraints and required-field violations that the database would have caught, followed by untranslatable queries reaching production.
  • Does EnsureCreated replace migrations in tests? — It creates the schema from the model, which is faster but means your migrations are never exercised; run Migrate() at least in one test.

Wrong answer that gets people rejected

"In-memory is fine for unit tests, we use a real database for integration." It sounds balanced and is still the trap: the "unit" tests then assert query behaviour that the in-memory provider gets wrong, and people trust them.

midHow do you keep an integration suite fast and isolated?

Answer

Share the expensive thing, reset the cheap thing. One container (or one database server) per test run, created once in a collection fixture with the migrations applied; then per test, either wrap in a transaction that is rolled back — fast and perfectly isolated but incompatible with code that opens its own transactions — or reset the data with Respawn, which deletes in FK order and is fast enough for hundreds of tests. Seed the minimum: a builder per aggregate producing valid objects, not a giant shared fixture, so tests state their own preconditions. Parallelise by database rather than by table: xUnit collections mapped to separate databases in the same container gives you real parallelism without cross-test interference. Finally, always create a fresh DbContext to assert results — asserting through the same context that wrote them tests the change tracker's memory, not the database.

Example

[Fact]
public async Task Soft_deleted_orders_are_invisible()
{
    await using (var write = NewContext())
    {
        write.Orders.Add(new Order { Id = 1, IsDeleted = true });
        await write.SaveChangesAsync();
    }
    await using var read = NewContext();          // fresh tracker: a real round trip
    (await read.Orders.CountAsync()).Should().Be(0);
    (await read.Orders.IgnoreQueryFilters().CountAsync()).Should().Be(1);
}

Follow-ups

  • Why a fresh context for assertions? — Otherwise the identity map returns your in-memory object and the test passes even if nothing was written.
  • Transaction rollback or Respawn? — Rollback when the code under test does not manage transactions; Respawn when it does (which includes anything using an execution strategy).
  • How do you keep the suite under five minutes? — Reuse the container, avoid re-migrating per test, seed narrowly, and parallelise across databases.

Wrong answer that gets people rejected

"Each test creates and migrates its own database." Correct and unbearably slow — a few hundred tests becomes a 40-minute build, and slow suites get skipped, which is worse than no suite.

seniorHow do you test that a migration is safe before it reaches production?

Answer

Test three separate properties, because "the migration ran" is not the interesting one. First, correctness: apply the full migration chain from empty in CI, and also apply just the new migration to a database restored at the previous release's schema — the second catches migrations that only work from scratch. Second, compatibility: run the previous version's test suite against the new schema, which is the mechanical way of proving a rolling deploy will not break in-flight instances; if it fails, the change is not expand-safe. Third, cost: run the migration against a restore of production-sized data and measure duration and lock behaviour, because an index build that takes eight seconds on 10,000 rows takes forty minutes on 200 million. On top of that, render the migration to SQL in the pipeline and put it in the PR so it is reviewed as SQL, not as C#, and use EF Core 9's PendingModelChangesWarning as a build-time check that the model and the migrations have not drifted.

Example

# 1. from scratch
dotnet ef database update --connection "$FRESH"
# 2. from the last released schema (restored snapshot)
dotnet ef database update --connection "$PREV_RELEASE_RESTORE"
# 3. previous app version's tests against the new schema
git checkout $PREVIOUS_TAG -- tests/ && dotnet test --filter Category=Integration
# 4. the SQL a human reviews
dotnet ef migrations script $PREV $NEW --idempotent -o pr/migrate.sql

Follow-ups

  • How do you get production-sized data safely? — A masked/anonymised restore refreshed weekly; if that is impossible, a synthetic data generator matched to real cardinality and skew.
  • What does PendingModelChangesWarning catch? — Model changes with no corresponding migration, which otherwise appear as a runtime failure at Migrate() or as silent drift.
  • Do you test Down? — Only if you actually intend to use it; most teams do not and should stop generating the illusion that rollback is available.

Wrong answer that gets people rejected

"CI applies the migrations, so they're tested." That proves the chain works from empty on an empty database. It says nothing about duration on real data, about locks, or about whether the currently-running app version survives the change.

principalWhat is the right test strategy for a data layer, and what would you cut?

Answer

I optimise for the failure modes that actually occur, which for a data layer are: an untranslatable or accidentally-client-evaluated query, a missing tenant or soft-delete predicate, a constraint the model does not know about, a concurrency conflict handled wrongly, and a migration that is slow or non-rolling. So the suite I want is a modest number of integration tests against a real engine covering exactly those five, a handful of SQL-shape and query-count guardrail tests on the hottest endpoints, unit tests for domain invariants with no database, and one migration-rehearsal job. What I would cut, in order: mock-based repository tests (they assert the mock), CRUD tests that verify EF works (Microsoft has those), redundant per-entity round-trip tests, and any test using the in-memory provider — each of which costs maintenance and buys confidence it does not deliver. The principal framing is that a data-layer suite is a risk-allocation decision: I would rather have 60 tests that fail only for real reasons than 600 that everyone has learned to re-run until green.

Example

// The kind of test that earns its keep: an invariant the model must enforce.
[Fact]
public async Task Tenant_filter_applies_to_bulk_updates()
{
    await SeedAsync(tenant: "a", count: 3);
    await SeedAsync(tenant: "b", count: 3);
    await using var db = NewContext(tenant: "a");

    var n = await db.Orders.ExecuteUpdateAsync(s => s.SetProperty(o => o.Notes, "x"));
    n.Should().Be(3);                                  // never 6
}

Follow-ups

  • How do you get a team to delete tests? — Show the flake rate and the maintenance cost, delete a batch together, and replace them with one test that would have caught the last real incident.
  • What about coverage targets? — Coverage on data-access code is a poor proxy; behaviour coverage of the five failure modes is the metric that matters.
  • Where do contract tests fit? — Between services: if another service reads your tables, that coupling needs a test or, better, needs removing.

Wrong answer that gets people rejected

"Aim for 80% coverage on the repositories." Coverage of glue code measures nothing about correctness here, and chasing it produces exactly the mock-heavy tests that a principal should be removing.

12Raw SQL, procs and providers

Two related themes: how you escape LINQ when you need to, and how much of what you know is actually provider-specific. Interviewers use this sub-area to check both pragmatism (can you drop to SQL without abandoning the model?) and safety (do you know which API is injection-safe?). EF Core 10's new analyzer for string concatenation in raw SQL calls is a current-knowledge marker.

Docs: Microsoft Learn — SQL queries

midWhat are the raw-SQL APIs in EF Core, and which are safe?

Answer

For queries returning mapped entities: FromSql (takes a FormattableString, interpolated values become parameters — safe) and FromSqlRaw (takes a string plus explicit parameters — safe only if you parameterise). For queries returning scalars or unmapped types: Database.SqlQuery<T> (EF Core 8+, FormattableString) and SqlQueryRaw. For non-queries: Database.ExecuteSql/ExecuteSqlAsync (safe interpolation) and ExecuteSqlRaw. The naming rule is worth stating explicitly because it is the whole safety story: the Raw suffix means "you are responsible for parameterisation". EF Core 10 added an analyzer that warns when you concatenate strings inside a raw SQL call, which is exactly the shape of a SQL-injection bug; you can suppress it when the fragment is genuinely trusted, such as a validated column name from an allow-list. A composability bonus: FromSql results are still IQueryable, so you can add Where, Include and paging on top and EF wraps your SQL as a subquery.

Example

// Safe: interpolation becomes a parameter, and the result composes.
var recent = await db.Orders
    .FromSql($"SELECT * FROM Orders WHERE TenantId = {tenantId}")
    .Where(o => o.Total > 100)
    .OrderByDescending(o => o.CreatedUtc)
    .Take(20)
    .ToListAsync(ct);

// EF10 analyzer warns here — and it is right to.
var bad = db.Users.FromSqlRaw("SELECT * FROM Users WHERE [" + column + "] IS NULL");

Follow-ups

  • What must a FromSql query return? — All the columns the entity type needs (or, from EF Core 8, at least the ones for the properties you use); missing columns fail at materialisation.
  • Do query filters apply? — To the composed outer query, yes; to your raw SQL, no. Tenant predicates must be written by hand inside the SQL.
  • How do you handle a dynamic column name safely? — Validate against an allow-list derived from the model's metadata, then interpolate; never accept it from the request directly.

Wrong answer that gets people rejected

"FromSqlRaw parameterises automatically." It does not — that is the entire meaning of Raw. Confusing the two APIs in an interview is a security answer, not a trivia slip.

midHow do you call stored procedures from EF Core?

Answer

For a proc returning rows that map to an entity or a keyless type, use FromSql($"EXEC …") — remembering that the result cannot be composed on (no Where on top, because EF cannot wrap EXEC in a subquery) unless you use AsEnumerable() and accept client evaluation. For a proc returning a scalar or an ad-hoc shape, Database.SqlQuery<T>. For a proc that only writes, Database.ExecuteSqlAsync. Output parameters need explicit SqlParameter objects with Direction = Output. Separately, EF Core 7 added CUD stored-procedure mapping (InsertUsingStoredProcedure/UpdateUsingStoredProcedure/DeleteUsingStoredProcedure), which makes SaveChanges call your procedures instead of generating SQL — this is the migration path for shops whose DBAs require all writes through procs, and EF Core 10 improved its ergonomics. The trade-off to name: procs move logic out of source control's dependency graph and out of the migration story unless you also version them as migration scripts.

Example

var rows = await db.Orders
    .FromSql($"EXEC dbo.GetOrdersForCustomer @CustomerId = {customerId}")
    .ToListAsync(ct);          // no composing on top of EXEC

mb.Entity<Order>().InsertUsingStoredProcedure("Order_Insert", s => s
    .HasParameter(o => o.CustomerId)
    .HasParameter(o => o.Total)
    .HasResultColumn(o => o.Id));

Follow-ups

  • How do you version the procs? — As migrationBuilder.Sql(...) in migrations, or a separate idempotent script run by the same pipeline; a proc that only exists in production is undeployable.
  • What breaks with CUD proc mapping? — Concurrency tokens and generated values need explicit mapping, and batching is reduced because each row becomes a proc call.
  • Keyless entity types? — HasNoKey() plus ToView/ToSqlQuery is the clean way to map a read-only result shape without pretending it is an entity.

Wrong answer that gets people rejected

"You can't use stored procedures with EF Core." You can, three different ways, and one of them makes SaveChanges itself go through procs. This claim is common and immediately checkable.

seniorHow provider-specific is EF Core, really?

Answer

More than the marketing suggests, and being specific here is a strong signal. The model API is shared, but translation is per-provider: string functions, date arithmetic, JSON access, Contains over collections, and paging all generate different SQL and have different support matrices. Value generation differs — SQL Server IDENTITY or sequences, PostgreSQL serial/identity, and PostgreSQL's xmin for concurrency versus SQL Server's rowversion. Type mapping differs: string maps to nvarchar on SQL Server and text on PostgreSQL, case sensitivity is a collation question on one and a default on the other, and DateTime/DateTimeOffset semantics differ enough that EF Core 10 shipped a fix specifically for Microsoft.Data.Sqlite's UTC handling. Migrations generate provider-specific DDL, and features like temporal tables, HierarchyId, vector search or SQL Server 2025's json type exist only where the provider supports them. Practical consequence: "provider-agnostic" code is a goal you pay for, and testing against a different engine than production is a false economy.

Example

// Provider-specific by design, and that is fine — isolate it.
if (db.Database.IsSqlServer())
    mb.Entity<Order>().ToTable(t => t.IsTemporal());
else if (db.Database.IsNpgsql())
    mb.Entity<Order>().UseXminAsConcurrencyToken();

Follow-ups

  • Can you support two providers in one codebase? — Yes, with separate migration assemblies per provider and provider checks in configuration; the cost is real and only worth it if you actually ship both.
  • Which third-party providers are production-grade? — Npgsql for PostgreSQL and Pomelo for MySQL are the mature ones; check their release cadence against the EF major you plan to adopt, because provider lag is a real upgrade blocker.
  • What is the risk of developing on SQLite and deploying on SQL Server? — Collation, type affinity, constraint enforcement and translation differences; you will find them in production.

Wrong answer that gets people rejected

"EF abstracts the database, so you can swap providers." You can swap the ones you have tested. Translation coverage, type mapping and migration DDL are all provider-specific, and the abstraction leaks exactly where it hurts.

seniorHow do you map database views and read-only query shapes?

Answer

Keyless entity types: HasNoKey() plus ToView("vw_Something") for a database view, or ToSqlQuery("SELECT …") to define the shape inline without creating a database object. They are queryable and composable like any other entity type — you can filter, page and join them — but they are never tracked and never saved, which is exactly right for reporting shapes. This is the clean answer to "we have a complicated reporting query": put it in a view the DBA can index (an indexed/materialised view where the engine supports it), map it keyless, and query it with LINQ, keeping the model as the single source of truth about what shapes exist. Migrations do not create views for you, so the view's DDL goes in a migration via migrationBuilder.Sql(...) — and that is the part teams forget, ending up with a model that only works against a manually-prepared database.

Example

mb.Entity<OrderReportRow>(b =>
{
    b.HasNoKey();
    b.ToView("vw_OrderReport", "reporting");
});

// The view itself is schema, so it belongs in a migration:
migrationBuilder.Sql("""
    CREATE OR ALTER VIEW reporting.vw_OrderReport AS
    SELECT o.TenantId, CAST(o.CreatedUtc AS date) AS [Day], COUNT(*) AS Orders, SUM(o.Total) AS Revenue
    FROM dbo.Orders o GROUP BY o.TenantId, CAST(o.CreatedUtc AS date);
    """);

Follow-ups

  • Can a keyless type be included from an entity? — No navigations to keyless types in the usual sense; join explicitly in the query.
  • Do query filters work on keyless types? — Yes, they can have global query filters, which matters for tenant-scoped reporting views.
  • View or projection? — Projection when the shape is a service concern; a view when several consumers (including non-.NET ones) need the same shape or when the DBA needs to index it.

Wrong answer that gets people rejected

"Map the view as a normal entity with a fake key." You will get tracking, identity-map collisions on duplicate rows, and EF believing it can write to it. HasNoKey exists precisely so you do not have to lie to the model.

principalYour DBA insists all data access goes through stored procedures. How do you respond?

Answer

I would separate the requirement from the mechanism. The requirement behind "procs only" is usually one of three things: security (no ad-hoc SQL rights, no injection surface), performance predictability (plans the DBA can see and tune), or change control (schema changes reviewed by the database team). Each of those has answers that do not require procs — parameterised queries and least-privilege database roles for the first, query store plus tagged queries and reviewable generated SQL for the second, migration review in the PR for the third — and I would put those on the table before arguing. If the policy stands, EF Core supports it: CUD stored-procedure mapping (EF Core 7+) routes SaveChanges through procs, reads go through FromSql/keyless types over procs and views, and the model still owns the shape. What I would insist on in return is that the procs live in the repository and deploy through the same migration pipeline, because a proc that exists only in production is an undeployable, untestable dependency — and that is a point most DBAs will concede, since it also protects them.

Example

// Writes through procs, reads through views: EF still owns the model and the deployment.
mb.Entity<Order>()
  .InsertUsingStoredProcedure("Order_Insert", s => s.HasParameter(o => o.Total).HasResultColumn(o => o.Id))
  .UpdateUsingStoredProcedure("Order_Update", s => s
      .HasOriginalValueParameter(o => o.RowVersion)     // concurrency still works
      .HasParameter(o => o.Status)
      .HasRowsAffectedResultColumn());

Follow-ups

  • What do you lose with proc-only writes? — Batching (each row is a call), some concurrency ergonomics, and the ability to change the write shape without a database deployment.
  • How do you keep the two in sync? — Procs in migrations, integration tests that exercise them, and a CI check that the model's proc mapping matches the deployed signature.
  • When would you simply accept it and move on? — When the organisation's audit or compliance regime genuinely requires it; the cost is real but manageable, and dying on this hill costs more than it saves.

Wrong answer that gets people rejected

"Stored procedures are legacy, we should refuse." Dismissing a stakeholder's constraint without understanding its driver is the failure mode this question tests; the interviewer wants to see negotiation with a technical alternative attached.

13Multi-tenancy and query filters

Global query filters are a small feature with outsized interview value, because they are how soft delete and tenant isolation are usually implemented and because the failure mode is a data leak rather than an exception. EF Core 10's named filters changed the shape of the best answer here, so this is a good place to demonstrate currency. Expect a design-flavoured question even at mid level.

Docs: Microsoft Learn — Global query filters

midWhat is a global query filter and what are its limits?

Answer

A predicate declared in OnModelCreating that EF appends to every query for that entity type, including when it appears inside an Include, a navigation or a bulk ExecuteUpdate/ExecuteDelete. That coverage is why it is the right place for soft delete and tenant isolation: you cannot forget it at a call site. The limits, which are the actual question: filters do not apply to raw SQL, to Find by key (it can return a filtered-out tracked entity from the identity map), or to anything outside EF such as a Dapper query or a stored proc; a filter on a required navigation can produce surprising results when the principal is filtered out; and before EF Core 10 there was one filter per entity type, so combining soft delete and tenancy meant a single && expression and IgnoreQueryFilters() dropped both at once — a genuine leak risk. EF Core 10 fixed exactly that with named filters.

Example

// EF Core 10: two independent, individually-disablable filters
mb.Entity<Blog>()
  .HasQueryFilter("SoftDeletionFilter", b => !b.IsDeleted)
  .HasQueryFilter("TenantFilter", b => b.TenantId == _tenant.Id);

// Show deleted rows to an admin — WITHOUT dropping the tenant filter:
var all = await db.Blogs.IgnoreQueryFilters(["SoftDeletionFilter"]).ToListAsync(ct);

Follow-ups

  • Why is the pre-EF10 behaviour dangerous? — One combined filter means the only way to see deleted rows was IgnoreQueryFilters(), which also removed tenancy: an admin screen quietly showing other tenants' data.
  • How does the filter see the current tenant? — Through a field on the context instance, which EF evaluates as a parameter per execution; do not close over a captured constant.
  • Do filters compose across inheritance? — A filter defined on a base type applies to derived types; you cannot define separate ones per derived type in a TPH hierarchy.

Wrong answer that gets people rejected

"Query filters make the data secure." They make the EF queries filtered. Raw SQL, procs, Dapper, a second context and IgnoreQueryFilters all bypass them, so they are a convenience mechanism with a security benefit, not a security boundary.

midHow do you implement soft delete properly?

Answer

Three parts, and teams usually implement one and a half of them. A flag (IsDeleted plus DeletedUtc and DeletedBy — the timestamp and actor are what make it auditable); a global query filter so reads exclude them everywhere; and an interception of the delete itself, either by never calling Remove and instead setting the flag explicitly, or by a SaveChanges override that converts Deleted state to Modified. The override version is elegant and has a sharp edge worth naming: ExecuteDeleteAsync does not go through it, so a bulk delete performs a real hard delete and silently defeats the whole design. The other things to get right: a filtered unique index (WHERE IsDeleted = 0) so a "deleted" row does not block re-creating the same natural key; cascade behaviour, since deleting a parent does not soft-delete children unless you handle it; and a retention job that eventually hard-deletes, because soft delete without expiry is an unbounded table and, under GDPR-style rules, a compliance problem.

Example

mb.Entity<Document>().HasQueryFilter("SoftDeletionFilter", d => !d.IsDeleted);
mb.Entity<Document>().HasIndex(d => d.Slug).IsUnique().HasFilter("[IsDeleted] = 0");

public override Task<int> SaveChangesAsync(CancellationToken ct = default)
{
    foreach (var e in ChangeTracker.Entries<ISoftDeletable>().Where(e => e.State == EntityState.Deleted))
    {
        e.State = EntityState.Modified;
        e.Entity.IsDeleted = true;
        e.Entity.DeletedUtc = DateTime.UtcNow;
    }
    return base.SaveChangesAsync(ct);
}

Follow-ups

  • What about foreign keys to soft-deleted rows? — They remain valid at the database level, so the application must decide whether a child of a deleted parent is visible; the filter on the child is usually the answer.
  • Right to erasure? — Soft delete is not deletion; you need a real purge path, and designing it late is expensive.
  • Performance impact? — Every index that matters should include or filter on IsDeleted, otherwise the filter turns seeks into scans as the deleted rows accumulate.

Wrong answer that gets people rejected

"Add an IsDeleted flag and a query filter, done." Missing the unique-index filter, the cascade question, the ExecuteDelete hole and the retention story — four issues that all show up within a year of shipping.

seniorCompare the multi-tenancy models EF supports and the cost of each.

Answer

Three models. Shared schema, discriminator column: one database, a TenantId on every table, enforced by a query filter. Cheapest to operate and to migrate (one migration run), worst blast radius — one missing predicate and you have a cross-tenant leak — and noisy-neighbour effects are unmitigated. Schema per tenant in one database: better logical separation, but migrations multiply by tenant count and the model needs a per-tenant schema, which EF handles awkwardly. Database per tenant: best isolation, per-tenant backup/restore and per-tenant scaling, natural fit for enterprise customers who demand it — and the highest operational cost, because migrations, connection management, pooling and monitoring all become fleet problems. Most SaaS products end up hybrid: shared schema for the long tail, dedicated databases for large or regulated customers, with the same code path selecting a connection string per tenant. The decision drivers I would state: regulatory requirements, the largest tenant's size relative to the median, per-tenant restore requirements, and how many tenants you expect at year three.

Example

// Hybrid: the catalogue decides where a tenant lives; the model is identical.
public sealed class TenantDbFactory(ITenantCatalog catalog)
{
    public AppDb Create(string tenantId)
    {
        var t = catalog.Get(tenantId);
        var o = new DbContextOptionsBuilder<AppDb>().UseSqlServer(t.ConnectionString).Options;
        return new AppDb(o, new TenantContext(tenantId, isolated: t.IsDedicated));
    }
}

Follow-ups

  • How do you move a tenant from shared to dedicated? — Export/import with a cutover window, or dual-write plus verification; design the tenant id to be stable so nothing else changes.
  • Can you use SQL Server row-level security instead of a filter? — Yes, and it is a genuine defence in depth because it also covers raw SQL — at the cost of database-side session context plumbing.
  • What does pooling do here? — Connection pools are per connection string, so database-per-tenant multiplies pools; watch total connections against the server's limit.

Wrong answer that gets people rejected

"Database per tenant, it's the safest." Safest and most expensive; with 5,000 tenants it is a migration fleet, thousands of connection pools and a monitoring problem. The expected answer names drivers, not a favourite.

seniorHow do you prove tenant isolation actually holds?

Answer

By testing the boundary rather than the mechanism, and by covering the paths that bypass EF. Concretely: an automated test that seeds two tenants and, for every exposed endpoint, authenticates as tenant A and attempts to read and write tenant B's ids, expecting 404/403 — driven from a route inventory so new endpoints are covered by default rather than by memory. A model test asserting that every entity type implementing ITenantOwned has the tenant filter applied, which catches the new entity someone added without it. SQL-shape assertions on bulk operations and raw SQL paths, since filters do not apply to the latter. And defence in depth outside the application: SQL Server row-level security or per-tenant credentials so that a missed predicate does not become a leak. The organisational half: treat a cross-tenant read as a sev-1 class of bug in the definition of done, and make the isolation test suite non-skippable in CI.

Example

[Fact]
public void Every_tenant_owned_entity_has_the_tenant_filter()
{
    using var db = NewContext();
    var missing = db.Model.GetEntityTypes()
        .Where(t => typeof(ITenantOwned).IsAssignableFrom(t.ClrType))
        .Where(t => !t.GetDeclaredQueryFilters().Any(f => f.Key == "TenantFilter"))
        .Select(t => t.ClrType.Name)
        .ToArray();

    missing.Should().BeEmpty();
}

Follow-ups

  • What is the most common leak path in practice? — A reporting or export feature written with raw SQL or Dapper, where the filter never applied in the first place.
  • How does caching complicate this? — Cache keys missing the tenant id serve one tenant's data to another; the key builder deserves its own test.
  • Does row-level security replace filters? — No, it complements them: filters give good SQL and good errors, RLS gives an enforcement point the application cannot forget.

Wrong answer that gets people rejected

"We use a global query filter, so tenants are isolated." That is the mechanism, not the proof — and it is untrue for raw SQL, IgnoreQueryFilters, caches and any second data path. The interviewer is listening for verification, not intention.

principalA shared-schema SaaS has one tenant generating 60% of the load. What do you do?

Answer

First measure whether the problem is capacity or interference: a whale tenant that simply uses a lot is a capacity question, but a whale whose queries evict everyone else's plans and pages is an isolation question, and the fixes differ. Short term, on a shared schema, I would look at plan skew — one parameterised plan compiled for the median tenant and reused for the whale is a classic p99 killer, and EF's EF.Constant/EF.Parameter or an OPTION (RECOMPILE) hint for the affected queries is a targeted fix — plus per-tenant rate limiting and making sure every index leads with TenantId so the whale's scans stay inside its own range. Medium term, move that tenant to a dedicated database: the code path already selects a connection per tenant if you designed for it, so this becomes a data migration and a cutover rather than a rewrite, which is the strongest argument for building the tenant-catalogue indirection early even when everyone shares one database. Long term, the architecture should place tenants by size class, with the whale on its own resources and a documented threshold that triggers the move — so the next whale is a runbook, not an incident.

Example

// Whale tenants get their own plan; the long tail shares one.
var q = db.Orders.Where(o => o.TenantId == (tenant.IsLarge ? EF.Constant(tenant.Id) : tenant.Id));

// Every index leads with the tenant so one tenant's scan stays in its own range.
mb.Entity<Order>().HasIndex(o => new { o.TenantId, o.CreatedUtc });

Follow-ups

  • How do you migrate the whale with minimal downtime? — Backfill to the new database, dual-write or replicate, verify with checksums, then flip the catalogue entry and drain; the tenant id never changes.
  • What is the threshold? — Pick a measurable one (share of IOPS, rows, or p99 contribution) and write it down, so the decision is not political each time.
  • What if the customer refuses a maintenance window? — Then it is a dual-write migration with verification, which costs more engineering and no downtime — a legitimate trade to put in front of them.

Wrong answer that gets people rejected

"Scale up the database." It buys time proportional to money and does nothing about interference or plan skew — and it is the answer that gets given right up until the largest instance size is already in use.

14Security

Fewer questions than you would expect, but they are disqualifiers: an EF candidate who is casual about FromSqlRaw, sensitive-data logging or over-posting will not get a lead role near customer data. EF Core 10 made two changes here worth knowing by name — constant redaction in logs and the raw-SQL concatenation analyzer.

Docs: Microsoft Learn — Passing parameters to SQL queries

screenerIs EF Core safe from SQL injection?

Answer

LINQ queries are, because everything a user supplies becomes a parameter — there is no string to inject into. The exposure is the raw-SQL surface: FromSqlRaw, ExecuteSqlRaw and SqlQueryRaw take a string you build, and string-concatenating user input into them is a textbook injection. The interpolated variants (FromSql, ExecuteSql, SqlQuery) look like string interpolation but take a FormattableString and parameterise every hole, which is why they are the default recommendation. The genuinely hard case is dynamic identifiers — a sort column or table name from the request — which cannot be parameterised at all and must be validated against an allow-list derived from the model. EF Core 10 added an analyzer that flags concatenation inside raw SQL calls, so this class of bug now shows up as a build warning; treat suppressing it as a reviewed decision, not a formality.

Example

// Injectable
var bad = db.Users.FromSqlRaw($"SELECT * FROM Users WHERE Name = '{name}'");

// Parameterised
var good = db.Users.FromSql($"SELECT * FROM Users WHERE Name = {name}");

// Dynamic identifier: allow-list from the model, never the raw input
var allowed = db.Model.FindEntityType(typeof(User))!.GetProperties().Select(p => p.Name).ToHashSet();
if (!allowed.Contains(sortBy)) throw new ArgumentException(nameof(sortBy));

Follow-ups

  • Does ExecuteSqlInterpolated still exist? — Yes, and ExecuteSql is the current name for the same FormattableString overload; both parameterise.
  • What about ordering by a user-chosen column in LINQ? — Build the expression from the allow-list, or map to a fixed set of Expression<Func<T, object>> — never string-based dynamic LINQ over unvalidated input.
  • Does parameterisation cost anything? — Only the plan-shape trade-off discussed earlier; it is never a reason to concatenate.

Wrong answer that gets people rejected

"EF uses parameters so injection isn't possible." Not for the Raw APIs, and not for dynamic identifiers. An unqualified "we're safe" is the answer that precedes the incident report.

midWhat is over-posting / mass assignment in an EF-backed API, and how do you prevent it?

Answer

Binding a request body directly to an entity and saving it, so the client can set fields the UI never exposed — IsAdmin, Price, TenantId, Balance. EF makes it worse than plain model binding because db.Update(entity) marks every mapped property modified, so even fields the client omitted get overwritten with defaults. The prevention is structural: bind to a request DTO containing exactly the fields the operation allows, load the entity, and copy only those fields — the load-then-apply pattern again. Secondary defences: never expose entity types on the API surface, keep domain setters private and mutate through methods, and add a test per endpoint that posts a payload containing a forbidden field and asserts it did not change. The subtle variant worth mentioning is the navigation case: accepting a nested object graph lets a client attach or create related entities they should not, which is how "update my order" becomes "create a product".

Example

public sealed record UpdateOrderRequest(string? Notes, string? ShippingAddress);   // no TenantId, no Total

var order = await db.Orders.FirstOrDefaultAsync(o => o.Id == id, ct);   // tenant filter applies
if (order is null) return Results.NotFound();
order.Notes = req.Notes;
order.ShippingAddress = req.ShippingAddress;
await db.SaveChangesAsync(ct);

Follow-ups

  • Isn't [Bind]/[JsonIgnore] enough? — They are opt-out lists that rot as the entity grows; a DTO is opt-in and cannot silently acquire a new field.
  • How does the tenant filter help? — The load returns null for another tenant's id, so the endpoint 404s instead of updating — which is why load-then-apply is also an authorisation step.
  • What test proves it? — Post the forbidden field and assert both the response and the database row are unchanged.

Wrong answer that gets people rejected

"AutoMapper maps only the matching properties, so it's fine." It maps whatever the names match, including the ones you did not intend, and then Update writes all of them. Mapping is not authorisation.

seniorWhat does EF leak into logs and telemetry, and how do you control it?

Answer

By default EF logs command text without parameter values, which is the right default: the SQL shape is diagnostic, the values are the PII. EnableSensitiveDataLogging() turns that off and also puts key values into exception messages, so it belongs in development only and ideally behind a configuration check that cannot be true in production. Two subtler leaks: inlined constants — values EF bakes into the SQL rather than parameterising — used to appear in the logged command text, which EF Core 10 fixed by redacting them to ? by default; and exception messages, which can carry key values and constraint details into an error-reporting service with different access controls than the database. On the telemetry side, EF emits DiagnosticSource events and OpenTelemetry-compatible spans whose db.statement attribute is the command text — worth checking your exporter's redaction, because APM tools are frequently readable by a much wider audience than the database.

Example

var builder = new DbContextOptionsBuilder<AppDb>().UseSqlServer(cs);
if (env.IsDevelopment())
    builder.EnableSensitiveDataLogging().EnableDetailedErrors();

// Prod: shape only. EF10 additionally redacts inlined constants to '?'.
builder.LogTo(msg => logger.LogDebug("{Sql}", msg),
              [DbLoggerCategory.Database.Command.Name], LogLevel.Information);

Follow-ups

  • How do you enforce it? — A startup assertion that throws if sensitive logging is on outside Development, plus a config-lint rule in the pipeline.
  • What about the connection string? — Never in logs or exception messages; use managed identity / token authentication so there is no password to leak in the first place.
  • EF10's connection-string change? — EF now injects an Application Name containing EF/SqlClient version info when none is supplied, which is useful for DBAs but is also new information appearing in server-side logs.

Wrong answer that gets people rejected

"We log everything, it's behind the firewall." Log sinks routinely have broader access and longer retention than the database, and "behind the firewall" is not a data-protection argument any auditor accepts.

principalWhat database permissions should your service have, and how do you get there?

Answer

The runtime identity should have no DDL rights at all — SELECT, INSERT, UPDATE, DELETE and EXECUTE on exactly the objects it uses, granted through a role, with a separate identity used only by the migration pipeline that has the schema rights. That separation is the concrete reason not to run migrations at application startup, and stating the link is what makes this a senior answer rather than a checklist. Beyond that: use managed identity / Entra authentication so there is no password to rotate or leak; consider separate read and write identities if you have a read replica, since the read path can be granted strictly less; and use row-level security or per-tenant credentials where isolation is a compliance requirement rather than a convention. Getting there from a service that currently runs as db_owner is incremental: create the restricted role, run in staging with it and fix the failures (usually a forgotten table or a proc), then flip production and remove the elevated grants — and add a check that fails CI if the application's connection can execute DDL.

Example

CREATE ROLE app_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA::sales TO app_runtime;
GRANT EXECUTE ON SCHEMA::sales TO app_runtime;
ALTER ROLE app_runtime ADD MEMBER [svc-orders-api];      -- managed identity, no password

-- Migrations run as a different principal entirely:
ALTER ROLE db_ddladmin ADD MEMBER [svc-orders-migrator];

Follow-ups

  • What breaks first when you drop DDL rights? — Startup migration calls, EnsureCreated in tests pointed at a shared database, and any code doing ad-hoc DDL for temp tables.
  • How do you handle temp tables then? — Local temp tables (#tmp) are allowed for the session on SQL Server; permanent staging tables need to be created by the migration, not at runtime.
  • How do you verify continuously? — A test that asserts a CREATE TABLE attempt with the runtime identity fails; permissions drift silently otherwise.

Wrong answer that gets people rejected

"The app needs db_owner because EF runs the migrations." That is the design being questioned. Coupling runtime privileges to a deployment concern is exactly the mistake, and the fix — a separate migration identity — is well known.

15Diagnostics and interceptors

Asked when the interviewer wants to know whether you have operated an EF service rather than only written one. The mechanics are small — interceptors, logging categories, diagnostic events, DebugView — but the questions behind them are about observability design: what would you have needed to diagnose last quarter's incident, and would you have had it? Interceptors are also the cleanest cross-cutting extension point EF has, so expect a "how would you implement X for every query" question.

Docs: Microsoft Learn — Logging, events and diagnostics

midWhat interceptors does EF Core offer and what would you use each for?

Answer

Four families. IDbCommandInterceptor sees every command before and after execution — the place for query tagging, slow-query logging, per-request query counting, and adding hints or a command timeout for specific statements. ISaveChangesInterceptor brackets SaveChanges — audit stamping, outbox writes, domain-event collection and post-commit dispatch. IDbConnectionInterceptor sees connection open/close — the usual home for injecting an access token, setting SESSION_CONTEXT for row-level security, or per-tenant connection routing. IMaterializationInterceptor sees entities being created and initialised — useful for injecting services into entities or for lazy-loading plumbing, and rarely needed. They are registered per context with AddInterceptors and can be resolved from DI, which is why they beat overriding DbContext methods: the context stays free of application concerns and the same interceptor can be applied to several contexts.

Example

public sealed class SlowQueryInterceptor(ILogger<SlowQueryInterceptor> log) : DbCommandInterceptor
{
    public override DbDataReader ReaderExecuted(DbCommand cmd, CommandExecutedEventData e, DbDataReader r)
    {
        if (e.Duration > TimeSpan.FromMilliseconds(200))
            log.LogWarning("Slow SQL {Duration}ms {Sql}", e.Duration.TotalMilliseconds, cmd.CommandText);
        return base.ReaderExecuted(cmd, e, r);
    }
}

options.UseSqlServer(cs).AddInterceptors(sp.GetRequiredService<SlowQueryInterceptor>());

Follow-ups

  • Interceptor or SaveChanges override? — Interceptor: composable, DI-friendly, and it does not put application logic in the context class.
  • Do interceptors run for ExecuteUpdate? — Command interceptors do (it is a command); SaveChanges interceptors do not, which is the audit hole discussed earlier.
  • Can an interceptor change the SQL? — Yes, you can mutate CommandText — powerful and dangerous; use it for hints, not for logic.

Wrong answer that gets people rejected

"I'd override SaveChanges in a base DbContext for all of that." It works and it does not compose: two concerns fight over one override, the base class accumulates dependencies, and nothing can be added per-environment.

midHow do you instrument EF for production observability?

Answer

Use the built-in signals before writing anything. EF emits DiagnosticSource events and an ActivitySource, so OpenTelemetry's SQL client and EF instrumentation gives you spans per command with duration and the statement text (check redaction), which is enough to see round trips per request in a trace. Add metrics for the three things traces do not show well: connection-pool waits, per-request query count, and rows returned — the last two via a command interceptor, since EF does not expose them as counters. Set the log level for Microsoft.EntityFrameworkCore.Database.Command to Warning in production and to Information behind a per-request debug flag, so you can turn on SQL logging for one customer's request without flooding the sink. Finally, tag the SQL: TagWith or TagWithCallSite puts a comment in the command that shows up in SQL Server's query store, which is the only reliable way to map a DBA's "this query is killing us" back to a line of C#.

Example

builder.Services.AddOpenTelemetry().WithTracing(t => t
    .AddEntityFrameworkCoreInstrumentation(o => o.SetDbStatementForText = false)   // redact by default
    .AddSqlClientInstrumentation()
    .AddAspNetCoreInstrumentation());

var q = db.Orders.Where(o => o.TenantId == tenantId).TagWithCallSite();

Follow-ups

  • What single metric would you add first? — Queries per request: it catches N+1, accidental lazy loading and loop-bound queries in one number.
  • How do you avoid trace cardinality explosion? — Tag by query name, not by SQL text; parameterised SQL already normalises, but inlined constants do not.
  • What do you keep from EF's own logging? — Warnings especially: MultipleCollectionIncludeWarning, and EF9+'s PendingModelChangesWarning, both of which predict incidents.

Wrong answer that gets people rejected

"We log all SQL to the APM." Cost, cardinality and PII all bite, and the volume means nobody reads it. Sampling plus targeted metrics is the answer that survives contact with a real bill.

seniorHow do you debug a change-tracking problem — "my save didn't save"?

Answer

ChangeTracker.DebugView first: ShortView lists every tracked entity with its state, LongView adds each property's current/original values and whether it is modified. That immediately distinguishes the four usual causes: the entity is Detached (loaded with AsNoTracking, or from a different context); the entity is Unchanged because the value you set equals the original; the property is not mapped, or is a converted mutable type with no ValueComparer so EF cannot see the change; or the save happened on a different context instance than the one you mutated. The fifth, less obvious cause is a global filter or a bulk operation making the entity you think you updated invisible or already changed. If DebugView shows the entity Modified with the right values and the row still does not change, the problem has moved to SQL — check the affected row count and whether a concurrency token or a filter narrowed the WHERE clause to nothing.

Example

order.Notes = "changed";
db.ChangeTracker.DetectChanges();
Console.WriteLine(db.ChangeTracker.DebugView.LongView);
// Order {Id: 5} Modified
//   Notes: 'changed' Modified   Originally 'old'
// ...or 'Detached', which is the answer 80% of the time.

Follow-ups

  • Why would a mutable converted property never look modified? — Missing ValueComparer: the snapshot aliases the same object, so current and original are always equal.
  • How do you check what EF sent? — Log the command; an UPDATE with @@ROWCOUNT = 0 and a concurrency token in the WHERE is a conflict, not a no-op.
  • Is DebugView safe in production? — It materialises values, so treat it like sensitive logging: development and targeted debugging only.

Wrong answer that gets people rejected

"I add db.Update(entity) to force it." That "fixes" the symptom by marking every column modified — reintroducing the over-posting problem — and leaves you not knowing why tracking was wrong.

seniorHow would you enforce a cross-cutting rule — "every query must have a timeout" or "no query without a tenant filter"?

Answer

Pick the enforcement point by whether the rule is mechanical or semantic. A command timeout is mechanical: a DbCommandInterceptor can set CommandTimeout on every command, with a per-query override via a tag, which is one class and cannot be forgotten. A tenant predicate is semantic and belongs in the model as a query filter, backed by a model test that enumerates entity types and asserts the filter exists — because the failure you are guarding against is a new entity added without it, and no interceptor can tell whether a predicate is the right one. For rules that are neither, an interceptor can inspect the generated SQL and fail fast in development and test environments while merely logging in production, which gives you enforcement without a new production failure mode. The general principle I would articulate: enforce in the model where possible, test where the model cannot express it, and use interceptors for mechanical properties of commands — never rely on a code-review convention for anything a machine could check.

Example

public sealed class TenantGuardInterceptor(IHostEnvironment env) : DbCommandInterceptor
{
    public override InterceptionResult<DbDataReader> ReaderExecuting(
        DbCommand cmd, CommandEventData e, InterceptionResult<DbDataReader> r)
    {
        if (cmd.CommandText.Contains("[Orders]", StringComparison.Ordinal)
            && !cmd.Parameters.Contains("@tenantId"))
        {
            if (!env.IsProduction()) throw new InvalidOperationException("Query on Orders without tenant filter");
            // production: log and continue, never add a new failure mode in an incident
        }
        return base.ReaderExecuting(cmd, e, r);
    }
}

Follow-ups

  • Why not throw in production too? — A guard that can crash the service under an unforeseen query shape is a bigger risk than the bug it prevents; fail loudly where it is cheap.
  • Where does a Roslyn analyzer fit? — For call-site rules ("no FromSqlRaw outside the data layer", "no IEnumerable in repository signatures") an analyzer beats a runtime check.
  • How do you keep interceptors from becoming a dumping ground? — One concern each, DI-registered, with tests; an interceptor doing four things is as bad as the overridden SaveChanges it replaced.

Wrong answer that gets people rejected

"We document it and check in code review." Any rule that a machine could verify and a human is asked to remember will be violated the week you are on holiday — and this question exists to see whether you reach for a mechanism.

principalWhat would you need in place to diagnose an EF-caused production incident in under 15 minutes?

Answer

Four things, and I would audit for them before an incident rather than during one. Attribution: every query tagged so the database's top-consumers list maps directly to a code location, and the connection carrying an application name and a version so the DBA can tell which deployment started the problem. Request-level shape: query count, rows returned and command duration per endpoint, so "which endpoint changed" is a dashboard question rather than an investigation. Correlation: trace ids that span the request and the database spans, so a slow request expands into its statements. A comparison baseline: the same metrics from before the deploy, plus the SQL-shape snapshots from the test suite, so "did the SQL change?" is answerable in seconds — which matters disproportionately after an EF upgrade, since EF10 changed parameterised-collection translation and split-query ordering, and both can move a plan without any application code changing. On top of that I want a documented mitigation ladder: the feature flag or config switch that turns a heavy endpoint off, and the query hint or UseParameterizedCollectionMode setting that can be flipped without a deploy.

Example

// Attribution the DBA can use without reading C#:
options.UseSqlServer($"{cs};Application Name=orders-api/{BuildInfo.Version}");
var q = db.Orders.TagWith($"orders/search v{BuildInfo.Version}");

// A mitigation that does not require a deploy:
options.UseSqlServer(cs, o => o.UseParameterizedCollectionMode(config.CollectionMode));

Follow-ups

  • What is the first thing you look at? — Whether it correlates with a deploy; if yes, the diff and the SQL-shape baselines; if no, data volume, a plan change or an upstream traffic shift.
  • How do you handle "the database is slow" from another team? — Attribution data turns it into a specific statement and a specific service, which is the difference between a fix and an argument.
  • What do you add after the incident? — Exactly the signal that was missing; incidents are the only reliable source of requirements for observability.

Wrong answer that gets people rejected

"We'd turn on sensitive data logging and reproduce it." Toggling PII logging during an incident is a second incident, and "reproduce it" is not a 15-minute plan for a production-only, data-volume-dependent problem.

16EF in distributed architecture

At lead and principal level the EF questions stop being about EF: they are about where the transaction boundary is, what happens when the database is one of several stores, and how a data layer behaves inside a service that publishes events. This sub-area is where "senior engineer who knows EF" becomes "architect who happens to use EF", and it is the one most likely to appear as a whiteboard discussion rather than a question.

Docs: Microsoft Learn — DDD and CQRS patterns for microservices

midHow do you implement the transactional outbox with EF?

Answer

Write the message as an ordinary entity in the same SaveChanges as the state change, so the database transaction covers both — that is the whole idea, and it removes the dual-write problem where the row commits and the broker publish fails (or vice versa). A separate publisher then polls or tails the outbox table, sends each message, and marks it dispatched; because the send can succeed and the mark can fail, delivery is at least once and every consumer must be idempotent. The EF-specific details worth naming: collect the messages in a SaveChanges interceptor from the aggregates' domain events so handlers never have to remember; index the outbox on (DispatchedUtc, Id) or use a partial index on undispatched rows so the poller's query stays a seek as the table grows; and delete or archive dispatched rows on a schedule, because an unbounded outbox becomes the slowest table in the database. If your broker and database support it, change-data-capture tailing avoids the polling entirely.

Example

public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
    DbContextEventData e, InterceptionResult<int> result, CancellationToken ct = default)
{
    var ctx = e.Context!;
    var events = ctx.ChangeTracker.Entries<IHasDomainEvents>()
        .SelectMany(x => x.Entity.DrainEvents())
        .Select(ev => new OutboxMessage(ev.GetType().FullName!, JsonSerializer.Serialize(ev, ev.GetType())));

    ctx.Set<OutboxMessage>().AddRange(events);      // same transaction as the state change
    return base.SavingChangesAsync(e, result, ct);
}

Follow-ups

  • How do you keep ordering? — Per-aggregate ordering via a sequence column and a single-threaded dispatcher per partition key; global ordering is usually neither needed nor affordable.
  • What if the publisher crashes mid-send? — The message is re-sent; consumers deduplicate by message id, which is why idempotency is a requirement not a nicety.
  • Does ExecuteUpdate break this? — Yes: it does not go through SaveChanges, so bulk state changes must write their outbox rows explicitly inside the same explicit transaction.

Wrong answer that gets people rejected

"Publish to the broker inside the transaction and roll back if it fails." The broker is not enlisted in the database transaction; you can publish and then roll back, telling the rest of the system about something that never happened.

seniorTwo services need each other's data. What are your options and how does EF constrain them?

Answer

Four options, roughly in increasing order of independence. Shared database, shared tables: both services map the same tables — fastest to build, and it couples deployments, migrations and models permanently; EF makes this deceptively easy, which is why it happens. Shared database, owned tables: each service owns its tables and reads the other's through a view or a keyless entity type, which at least makes ownership explicit and keeps migrations unambiguous. Synchronous API call: clean ownership, but you have coupled availability and added latency to every request, and EF is irrelevant to the consumer. Replicated read model: the owner publishes events, the consumer maintains its own table with EF and queries it locally — best availability and latency, at the cost of eventual consistency and the operational burden of a projection that can fall behind or corrupt. My default for a genuine service boundary is the fourth with a fallback to the third for rarely-needed data, and I would say plainly that the first is not a service boundary at all, it is one database with two deployment units.

Example

// Consumer-owned read model, maintained from events, queried like any other table.
public sealed class CustomerSnapshot            // owned by THIS service
{
    public Guid CustomerId { get; set; }
    public string Name { get; set; } = "";
    public DateTime UpdatedUtc { get; set; }     // staleness is visible, by design
}

public async Task On(CustomerRenamed e, CancellationToken ct) =>
    await db.CustomerSnapshots.Where(c => c.CustomerId == e.Id)
        .ExecuteUpdateAsync(s => s
            .SetProperty(c => c.Name, e.Name)
            .SetProperty(c => c.UpdatedUtc, e.OccurredUtc), ct);

Follow-ups

  • How stale is acceptable? — A product question, answered in seconds and written into the SLO; make the timestamp visible so consumers can decide.
  • How do you rebuild a corrupted projection? — Replay from the event log or a snapshot endpoint; a projection you cannot rebuild is a liability, so build the rebuild path first.
  • What if you need a transaction across both? — You do not get one. Either the boundary is wrong and they are one service, or you need a saga with compensations.

Wrong answer that gets people rejected

"Both services use the same DbContext against the same tables." That is a distributed monolith with the worst properties of both models: coupled schema, coupled deploys, and no transaction boundary anyone can reason about.

seniorHow do EF and CQRS fit together in practice?

Answer

The version that pays for itself immediately is the cheap one: the write side uses EF with tracked aggregates, invariants in the domain and one SaveChanges per command; the read side uses EF too, but as a query builder — projections to DTOs, no tracking, sometimes over views or keyless types, sometimes against a read replica. That is CQRS in the sense that matters (separate models for reading and writing) with none of the operational cost, and it removes the usual conflict where one model is dragged in two directions. The expensive version — separate read stores maintained asynchronously by projections — buys you independent scaling and denormalised shapes at the cost of eventual consistency, projection rebuilds and a whole new class of bug; take it only when the read load or the shape genuinely demands it. What I would warn against is the middle position many teams land in: separate handlers, separate folders and identical models, all the ceremony with none of the benefit.

Example

// Write side: tracked aggregate, invariants inside, one SaveChanges.
var order = await db.Orders.Include(o => o.Lines).SingleAsync(o => o.Id == cmd.Id, ct);
order.AddLine(cmd.ProductId, cmd.Quantity);      // throws if the invariant is violated
await db.SaveChangesAsync(ct);

// Read side: no tracking, projection, possibly a replica connection.
var view = await readDb.Orders.AsNoTracking()
    .Where(o => o.CustomerId == q.CustomerId)
    .Select(o => new OrderListItem(o.Id, o.Number, o.Total, o.Lines.Count))
    .ToListAsync(ct);

Follow-ups

  • How do you point reads at a replica? — A second context (or a second options instance) with the replica connection string and ApplicationIntent=ReadOnly; make replica lag visible to the caller.
  • Where do the invariants live? — In the aggregate, enforced on the write side; read models must never be a place where rules are re-implemented.
  • Does CQRS require event sourcing? — No, and conflating them is the most common way teams talk themselves into a much larger project than they need.

Wrong answer that gets people rejected

"CQRS means a separate read database and event sourcing." It means separate read and write models. Insisting on the maximal version signals that you would import a lot of complexity into a service that needed a projection.

seniorRepository pattern over EF: yes or no, and what does it cost?

Answer

My position is: not by default, and never for the stated reason of "so we can swap the ORM", because that swap essentially never happens and the abstraction does not survive it anyway — IQueryable, tracking semantics, lazy loading and migrations all leak through. DbContext is already a unit of work and DbSet<T> is already a repository, so a generic IRepository<T> with GetAll/Add/Remove is a layer that adds indirection and removes composability. Where a repository does earn its place is when it is a domain-language API rather than a data-access one: IOrderRepository.FindOpenOrdersForCustomer(...), returning fully-loaded aggregates, hiding the include/projection strategy and enforcing invariants such as "aggregates are always loaded whole". That version is a real boundary, it is testable, and it lets you change the loading strategy without touching handlers. The cost either way is one more indirection and the temptation to leak IQueryable through it, which reintroduces every coupling you were avoiding.

Example

// Not this: a generic wrapper that adds nothing.
public interface IRepository<T> { IQueryable<T> Query(); void Add(T e); void Remove(T e); }

// This: domain language, aggregate-shaped, strategy hidden.
public interface IOrderRepository
{
    Task<Order?> FindAsync(OrderId id, CancellationToken ct);          // loads the whole aggregate
    Task<IReadOnlyList<Order>> OpenForCustomerAsync(CustomerId id, CancellationToken ct);
    void Add(Order order);
}

Follow-ups

  • How do you handle reads that do not fit the aggregate? — They do not go through the repository at all: query handlers project directly, which keeps the repository from growing 40 methods.
  • Does it help testing? — Marginally, and mocking it produces tests that assert the mock; a real database test is more valuable and not much slower.
  • What is the strongest argument for one? — Enforcing that aggregates are loaded and saved whole, which is genuinely hard to enforce with bare DbSet access.

Wrong answer that gets people rejected

"Always use a repository so you're not tied to EF." Say this without being able to name what the abstraction actually buys and you have described cargo-cult layering — which is exactly what the question is probing.

principalYou are splitting a monolith's database. How does the EF model change, and in what order?

Answer

The order matters more than the mechanics. First, find the seams in the data, not in the code: which tables are written by which module, and where are the foreign keys that cross a candidate boundary — those FKs are the real cost, because breaking one converts a join into either an API call or a replicated read model. Second, split the model before splitting the database: one DbContext per bounded context against the same physical database, each owning its tables with its own migrations history, cross-boundary access converted to views or read models. This step is reversible, ships incrementally, and surfaces every accidental coupling as a compile error. Third, remove cross-boundary joins one at a time, replacing each with an event-fed projection or an API call, and only then physically separate the databases — at which point the change is a connection string, not a rewrite. Throughout, keep a written ownership map, and expect to discover a handful of tables that no boundary wants, which is a domain question rather than a technical one and should be escalated rather than guessed.

Example

// Step 2: two contexts, one database, unambiguous ownership and separate histories.
services.AddDbContext<SalesDb>(o => o.UseSqlServer(cs, s => s
    .MigrationsHistoryTable("__EFMigrationsHistory", "sales")));
services.AddDbContext<BillingDb>(o => o.UseSqlServer(cs, s => s
    .MigrationsHistoryTable("__EFMigrationsHistory", "billing")));

// Cross-boundary read, explicitly a snapshot rather than a join:
mb.Entity<CustomerSnapshot>().HasNoKey().ToView("sales.vw_CustomerSnapshot");

Follow-ups

  • What if a transaction currently spans both sides? — That is the hardest case: either the boundary is wrong, or the operation becomes a saga with compensation, and that redesign should happen before the physical split.
  • How do you stop new couplings appearing mid-migration? — An architecture test that fails when one context's assembly references another's entity types, plus schema-level permissions once you are ready.
  • When do you actually separate the servers? — Last, and only if you need independent scaling, isolation or lifecycle; logical separation delivers most of the benefit at a fraction of the risk.

Wrong answer that gets people rejected

"Create the new databases first and migrate the data." Physical separation before logical separation leaves you with cross-database joins you cannot write, distributed transactions you cannot have, and a rollback path that involves restoring two databases to a consistent point.

Rarely asked, and a good differentiator when it is — it comes up for serverless, scale-to-zero and container-density workloads, and as an "are you current" probe, because precompiled queries and Native AOT support are recent and still evolving. midWhat actually happens on the first query after startup?

Answer

Several one-time costs stack up before a single row comes back. EF builds the model — running conventions over every entity type, applying your configuration, validating relationships — which is reflection-heavy and scales with the number of entities and properties: negligible at 20 entities, and hundreds of milliseconds to several seconds at 500. Then it compiles the query from the expression tree, which is per query shape and cached afterwards. Then ADO.NET opens the first physical connection and does the TLS/authentication handshake. And, if you are on a cold container, the CLR is also JIT-compiling everything on that path. The distribution matters: in a long-running service this is a one-off you never think about, while in a serverless function or an aggressively scaled deployment it is on the critical path of many requests, and that is when compiled models and precompiled queries stop being trivia.

Example

// Force the one-time costs during startup rather than on a user's request.
var db = await factory.CreateDbContextAsync();
_ = db.Model;                                     // build the model
await db.Database.OpenConnectionAsync();          // handshake
_ = await db.Orders.Where(o => o.Id == -1).ToListAsync();   // compile a representative query

Follow-ups

  • Is the model per context instance? — No, it is cached per IModelCacheKeyFactory key on the service provider, so it is built once per process unless you have a custom cache key (e.g. per tenant, which multiplies the cost).
  • Does pooling help startup? — No; it helps steady-state allocation, not the first-request costs.
  • What is the practical fix for serverless? — Compiled model plus a warm-up path, and a hard look at whether the model needs 500 entities.

Wrong answer that gets people rejected

"The first query is slow because the connection pool is cold." That is one of four costs and usually the smallest. Missing model building means you would optimise the wrong thing.

seniorWhat is a compiled model and what does it not solve?

Answer

dotnet ef dbcontext optimize generates C# that constructs the model directly, skipping the convention and reflection pass at runtime; you register it with UseModel(MyCompiledModel.Instance) and startup model-building time drops by an order of magnitude on large models — Microsoft's own numbers show a model with hundreds of entities going from over a second to tens of milliseconds. What it does not solve: per-query compilation (that is compiled/precompiled queries), connection latency, or JIT. And it comes with a maintenance obligation that is the real interview point — the generated code is a build artefact that must be regenerated whenever the model changes, so it belongs in the build pipeline, not in a developer's memory; a stale compiled model silently uses the old schema mapping, which is a genuinely nasty class of bug. It also does not support every feature (global query filters and some conventions have had limitations), so check the current constraints before adopting.

Example

dotnet ef dbcontext optimize --output-dir Generated --namespace App.Generated

options.UseSqlServer(cs).UseModel(App.Generated.AppDbModel.Instance);

Follow-ups

  • How do you keep it from going stale? — Regenerate in CI and fail the build if the output differs from what is checked in — the same pattern as the scaffold-drift check.
  • When is it worth it? — Large models plus frequent cold starts; on a service that starts twice a week it is pure maintenance cost.
  • What about --precompile-queries? — EF Core 9+ also generates query code at build time, which is what makes EF usable under Native AOT where runtime expression compilation is unavailable.

Wrong answer that gets people rejected

"Compiled models make queries faster." They make model building faster, once, at startup. Confusing them with compiled queries suggests you have read the feature name and not the page.

seniorCan you run EF Core under Native AOT, and what are the constraints?

Answer

Partially, and the direction of travel matters more than a yes/no. EF's classic execution model relies on runtime expression compilation and reflection, both of which Native AOT forbids or trims away, so EF Core 9 introduced precompiled queries — generated at build time with dotnet ef dbcontext optimize --precompile-queries — alongside compiled models, which together move the reflective work to compile time. The practical position today is that AOT support exists for constrained scenarios, not as a drop-in for an arbitrary EF application: dynamic query shapes, some providers and some features are still unsupported, and the tooling requires your queries to be statically discoverable. So the interview-safe answer is to describe the mechanism, note that it is an evolving capability across EF9/EF10/EF11, and say that for a genuinely AOT-constrained workload today I would evaluate whether a lighter data-access approach (Dapper, or a source-generated micro-ORM) fits better than fighting the constraints — while keeping EF where AOT is not a requirement.

Example

dotnet ef dbcontext optimize --precompile-queries --nativeaot --output-dir Generated
dotnet publish -r linux-x64 -p:PublishAot=true

Follow-ups

  • Why does AOT care about expression trees? — Compiling one at runtime emits IL, which a fully-AOT-compiled application cannot do; the work must happen ahead of time.
  • What do you gain? — Startup in milliseconds and a much smaller memory footprint, which matters for serverless and high-density containers — not throughput.
  • Would you adopt it now? — Only where cold start is a first-class requirement; otherwise the constraints cost more than the milliseconds are worth.

Wrong answer that gets people rejected

"EF doesn't work with AOT." Too absolute since EF Core 9; equally wrong is claiming full support. The credible answer names precompiled queries and the remaining constraints.

principalYour service runs in a scale-to-zero environment and cold starts are hurting p99. How do you approach it?

Answer

Measure the cold-start breakdown before touching EF, because in most .NET services the split is roughly: runtime and JIT, DI container build, EF model building, first connection, and first query compilation — and only two of those are EF's. If model building is significant (it will be with a large model), a compiled model is the highest-value change and is purely additive. Then warm the path at startup, so the first user request does not pay connection handshake and query compilation. Then consider whether the model is too big for the service — 400 entities in one context in a function that touches six of them is an architecture smell, and splitting the context is often a bigger win than any EF feature. Only after that would I look at Native AOT with precompiled queries, because it constrains what the code can do and costs build complexity. And I would question the environment itself: if cold starts dominate p99, minimum instances or a different hosting model may be cheaper than months of engineering.

Example

// Warm-up hosted service: pay the one-time costs before traffic arrives.
public sealed class DbWarmup(IDbContextFactory<AppDb> f) : IHostedService
{
    public async Task StartAsync(CancellationToken ct)
    {
        await using var db = await f.CreateDbContextAsync(ct);
        _ = db.Model;
        await db.Database.OpenConnectionAsync(ct);
        _ = await db.Orders.Where(o => o.Id == -1).ToListAsync(ct);
    }
    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}

Follow-ups

  • How do you measure the breakdown? — Timestamps around each startup phase plus dotnet-counters/EventPipe on a cold container; guessing here wastes the most time.
  • Does the warm-up hurt readiness? — Run it before reporting ready, so the platform does not route traffic to a cold instance; that is the point.
  • When would you conclude EF is the wrong fit? — A function with a handful of queries and a hard cold-start SLO: a thin data-access layer over ADO.NET may simply be the right tool there.

Wrong answer that gets people rejected

"Switch to Dapper, EF is too heavy for serverless." Possibly the right destination, definitely the wrong first step: without the breakdown you may be rewriting the data layer to save 40ms of a 900ms cold start dominated by runtime initialisation.

18EF6 and legacy migration

Asked when the role involves a legacy estate, which in the .NET world is often. You need to know what EF6 is, why it still exists, what breaks when moving to EF Core, and how to sequence a migration that cannot be a big bang. It is also a favourite way to check whether "10 years of EF experience" means EF6 habits applied to EF Core.

Docs: Microsoft Learn — Compare EF Core and EF6

midWhat is EF6, and is it still supported in 2026?

Answer

EF6 is the original Entity Framework, a .NET Framework-era ORM with a separate codebase from EF Core; it also runs on modern .NET (since 6.3/6.4) so a migrated application can keep using it. It is supported but frozen: under the Modern Lifecycle Policy only the latest patch of the latest version (6.5) is supported, it receives security fixes and occasionally very-high-impact bug fixes only, and Microsoft has committed to 12 months' notice before ending support with no end date announced. The most recent runtime release, 6.5.2, shipped in April 2026 mainly to keep EF6 working correctly on .NET 10. Practically: EF6 is a maintenance dependency, not a platform to build on — no new features, no vector search, no JSON mapping, no ExecuteUpdate, and none of the translation improvements of the last decade. If you are choosing today, you choose EF Core; if you have EF6, you plan a migration on business terms rather than in a panic.

Example

// EF6 idioms you will meet — and their EF Core equivalents:
// db.Database.SqlQuery<T>(...)      -> db.Database.SqlQuery<T>($"...")     (EF Core 8+)
// db.Entry(e).Reload()              -> db.Entry(e).ReloadAsync()
// [Table]/[Column] + EDMX designer  -> Fluent API / IEntityTypeConfiguration (no EDMX in EF Core)
// Database.SetInitializer(...)      -> migrations only

Follow-ups

  • What has no EF Core equivalent at all? — EDMX/designer-based models and the ObjectContext APIs; those must be re-expressed as code-first configuration.
  • Can EF6 and EF Core coexist? — Yes, in the same application against the same database, which is the standard incremental-migration path.
  • Why does the version 6.5.2 date matter? — It shows EF6 is still serviced (a .NET 10 compatibility fix in April 2026) — useful when arguing that migration is a planned project, not an emergency.

Wrong answer that gets people rejected

"EF6 is dead / unsupported." Wrong on the facts and it damages your credibility in the follow-up, which is usually "so should we drop everything and migrate?" — where the correct answer depends on business value, not on a false urgency.

seniorWhat breaks when you move a codebase from EF6 to EF Core?

Answer

Five categories, in rough order of pain. Client evaluation: EF6 silently evaluated untranslatable fragments in memory; EF Core throws, so queries that "worked" now fail at runtime and must be rewritten — this is the largest single bucket and it is only discoverable by executing the queries, which is why the test suite matters. Lazy loading: on by default in EF6 with virtual navigations, off in EF Core, so code that relied on it returns empty collections instead of loading — a silent correctness change, worse than an exception. EDMX: no designer support in EF Core at all, so a designer-based model must be re-expressed as configuration. API differences: ObjectContext, DbSet.SqlQuery, database initializers, some validation hooks, and the DbContext lifetime idioms all changed. Migrations: EF6 and EF Core use different history tables and formats, so you baseline — take the existing schema as migration zero rather than replaying history. The sequencing advice: run both in the same application, move one bounded area at a time, and keep an integration test suite as the safety net, because the silent changes are the dangerous ones.

Example

// EF6: worked (client-evaluated). EF Core: throws.
var bad = ctx.Orders.Where(o => MyHelper.IsRecent(o.CreatedUtc)).ToList();

// EF6: lazy-loaded. EF Core: empty, silently.
foreach (var line in order.Lines) { /* zero iterations without Include */ }

// Baseline migration for an existing database:
// dotnet ef migrations add Initial   -> then delete the Up() body / apply with --no-op

Follow-ups

  • How do you find the lazy-loading dependencies? — Enable EF Core's lazy-loading proxies temporarily with a logger that flags every lazy load, then fix them one by one and turn it off.
  • How do you baseline safely? — Generate the initial migration from the model, verify its SQL matches the real schema, then insert the history row without executing it.
  • What is the smallest safe first step? — Move reads for one bounded area to an EF Core context alongside EF6, since reads are reversible and prove the model.

Wrong answer that gets people rejected

"It's mostly a package swap, the APIs are similar." They look similar and behave differently in exactly the places that matter — client evaluation and lazy loading — which is how "two-week upgrade" becomes a six-month firefight.

seniorHow do you plan an EF Core major-version upgrade — say EF8 to EF10?

Answer

Treat it as a release with its own risk assessment, not a package bump. Read the breaking-changes page for every version you skip and turn it into a checklist — for EF8 → EF10 that includes the ExecuteUpdateAsync signature change (expression-tree setters no longer compile), the new default parameterised-collection translation, nested complex-type column renaming, the JSON column type switch on SQL Server 2025/Azure SQL, the --framework requirement in the tooling, and the automatic Application Name injection. Then: upgrade in a branch, run the full integration suite against a real engine, diff the SQL-shape baselines (which is where the translation changes show up), add a migration and inspect it before assuming it is empty, and load-test the endpoints whose queries use large Contains lists, because that is where the new parameter mode can change plans. Sequence it against the support calendar — EF Core 8's support ends 10 November 2026 and EF Core 9 already ended in May 2026 — so the upgrade is scheduled work with a deadline, not an optional improvement. Finally, check your provider and any bulk-extension libraries support the target major before you start; provider lag is the most common blocker.

Example

// EF8/EF9 code that does not compile on EF10:
Expression<Func<SetPropertyCalls<Blog>, SetPropertyCalls<Blog>>> setters =
    s => s.SetProperty(b => b.Views, 8);
await db.Blogs.ExecuteUpdateAsync(setters);

// EF10:
await db.Blogs.ExecuteUpdateAsync(s => { s.SetProperty(b => b.Views, 8); });

Follow-ups

  • How do you de-risk the translation changes? — SQL-shape snapshot tests on the top queries; the diff is the risk assessment.
  • What if a third-party provider lags? — Then the upgrade waits, or you change provider — either way it is a dependency to check first, not to discover mid-upgrade.
  • Skip versions or go one at a time? — Skipping is fine for EF; the breaking-changes pages are cumulative and the test suite is what actually validates it.

Wrong answer that gets people rejected

"Bump the package version and run the tests." That is the execution step, not the plan — and with EF10 it will fail to compile on the first ExecuteUpdateAsync and silently change SQL for every Contains query that does compile.

principalYou own a 15-year-old EF6 application. Make the case for or against migrating to EF Core.

Answer

I would make the case on three axes and let the numbers decide. Risk: EF6 is supported but frozen — security fixes only, no new features, and it depends on a .NET Framework or older-.NET context that has its own support horizon; the question is whether the application's remaining lifetime is shorter than the platform's. Capability: what does EF Core unlock that we actually want — ExecuteUpdate/ExecuteDelete, JSON and complex types, better translation, vector search for an AI feature, and the ability to run on current .NET at all? If the answer is "nothing we need", the case is weak and honesty about that is worth more than enthusiasm. Cost: sized from the query inventory, because client evaluation and lazy loading are the two work drivers and both are countable — number of queries, number of virtual navigations. My recommendation is usually incremental: run EF Core alongside EF6, migrate one bounded area at a time behind the existing test suite, and tie each increment to a feature the business wanted anyway, so the migration is funded by value rather than by a "modernisation" line item that gets cut in the next budget round. And I would set a decision point: if after two increments the estimate has doubled, we stop and re-evaluate rather than continuing on sunk cost.

Example

// Both contexts, one database, one transaction — the incremental path.
using var conn = new SqlConnection(cs);
await conn.OpenAsync();
using var tx = conn.BeginTransaction();

var legacy = new LegacyEf6Context(conn, contextOwnsConnection: false);
legacy.Database.UseTransaction(tx);

await using var modern = new AppDb(new DbContextOptionsBuilder<AppDb>().UseSqlServer(conn).Options);
await modern.Database.UseTransactionAsync(tx);

Follow-ups

  • How do you size it credibly? — Inventory the queries and navigations, migrate one representative module, and extrapolate from measured effort rather than from a guess.
  • What if the answer is "don't migrate"? — Then say so and write down the conditions that would change it (a needed feature, an end-of-support notice, a hiring problem), so the decision gets revisited on evidence.
  • How do you keep the team motivated on a long migration? — Ship user-visible value in every increment; a pure-refactor programme with no visible output loses funding and morale together.

Wrong answer that gets people rejected

"It's legacy, we should rewrite it on EF Core." A rewrite proposal with no cost model, no risk comparison and no incremental path is the answer that gets principal candidates rejected — the interviewer is testing judgment about when not to migrate as much as how.

19Internals: the query pipeline

Rarely asked directly, and excellent for demonstrating depth when it is: understanding how a LINQ expression becomes SQL is what lets you predict translation failures, explain the query cache, and reason about why a small code change altered the SQL. Treat these as bonus questions — worth knowing, never worth leading with.

Docs: Microsoft Learn — EF Core internals and extensibility

seniorWalk me through how a LINQ query becomes SQL.

Answer

Five stages. The C# compiler turns your lambda into an expression tree hanging off the IQueryable's provider. On execution, EF computes a cache key from the tree's shape (plus context options and, importantly, whether values are constants or captured variables) and looks for a compiled plan. On a miss, it runs preprocessing: evaluating client-side subexpressions into parameters, expanding navigations into joins via the NavigationExpandingExpressionVisitor, and applying global query filters and Includes. Then translation converts the tree into a provider-agnostic SelectExpression tree of relational concepts, which the provider's QuerySqlGenerator renders into SQL text and parameters. Finally EF compiles a shaper — a delegate that reads the DbDataReader and materialises entities, wires up navigations and registers them with the change tracker. The reason to know this: translation failures happen at stage four, and the query cache at stage two is why dynamically built expression trees are expensive and why a captured variable behaves differently from a literal.

Example

// Same SQL, one cache entry, different parameter values:
db.Orders.Where(o => o.Status == status)

// Different SQL per value, one cache entry per value:
db.Orders.Where(o => o.Status == OrderStatus.Open)

// A new cache entry on every call — this is the expensive mistake:
var predicate = BuildPredicateDynamically(filters);   // new tree shape each time
db.Orders.Where(predicate)

Follow-ups

  • Where does client evaluation happen? — In the shaper, for the final projection only; anything else must translate.
  • What is the shaper? — A compiled delegate over the reader; it is why materialisation of a large result set is CPU work in your process, not in the database.
  • How would you add a translation for your own function? — HasDbFunction for a mapped UDF, or a custom IMethodCallTranslator registered through a provider extension for something more involved.

Wrong answer that gets people rejected

"EF parses the C# code." It never sees your source — it sees an expression tree built by the compiler, which is exactly why some perfectly ordinary C# (a local function, a method call) cannot be translated.

seniorWhat is the model cache key and when would you change it?

Answer

EF caches the built model per key produced by IModelCacheKeyFactory, which by default is the context type — so all instances of AppDb share one model however they are configured. You change it when the model itself must differ per instance: the textbook case is a multi-tenant system where different tenants have different entity configurations or table names. The cost is precisely what the cache exists to avoid — one model built and held per distinct key, so a per-tenant key with 500 tenants means 500 models in memory and 500 model-building passes. That is why the correct answer for the common tenancy case is not a custom cache key: a global query filter reading an instance field is evaluated per query as a parameter and needs only one model. Reserve custom cache keys for genuine schema variation, and even then consider whether the variation belongs in the data instead.

Example

public sealed class TenantModelCacheKeyFactory : IModelCacheKeyFactory
{
    public object Create(DbContext context, bool designTime)
        => context is AppDb db
            ? (context.GetType(), db.TenantSchema, designTime)   // one model per schema
            : context.GetType();
}
options.ReplaceService<IModelCacheKeyFactory, TenantModelCacheKeyFactory>();

Follow-ups

  • What is the memory cost? — A model for a few hundred entities is megabytes; multiply by tenants and it becomes the dominant allocation in the process.
  • Does a compiled model still work? — Not straightforwardly with per-tenant models, since the compiled model is a single generated artefact.
  • Better alternative for per-tenant tables? — Separate databases with an identical model, which keeps one model and moves the variation to the connection string.

Wrong answer that gets people rejected

"Use a custom model cache key per tenant so the filter picks up the tenant id." The filter does not need it — it parameterises the field read — and you have just multiplied model-building cost and memory by your tenant count.

seniorHow would you extend EF with a custom translation or convention?

Answer

Three levels of intervention. For a database function, modelBuilder.HasDbFunction maps a static .NET method to a SQL function so it becomes translatable in queries — the cheapest and the right answer for 90% of cases. For a model-wide rule, write an IConvention (EF Core 6+ has a public convention API) and add it in ConfigureConventions, or use the simpler pre-convention model configuration for type-level rules; this is how you enforce things like "every entity implementing IAuditable gets these three columns and an index". For a genuine translation of a .NET method EF does not know, you implement an IMethodCallTranslator and register it via IMethodCallTranslatorPlugin in a provider extension — powerful, provider-specific, and a real maintenance commitment because it depends on EF internals that change between majors. My advice in an interview: reach for the first, accept the second, and treat the third as a last resort that needs an owner and a test suite.

Example

public static class DbFunctions
{
    public static double Distance(Point a, Point b) => throw new NotSupportedException();
}

mb.HasDbFunction(typeof(DbFunctions).GetMethod(nameof(DbFunctions.Distance))!)
  .HasName("fn_Distance").HasSchema("dbo");

// Now translatable:
var near = await db.Stores.OrderBy(s => DbFunctions.Distance(s.Location, here)).Take(5).ToListAsync(ct);

Follow-ups

  • Who maintains the SQL function? — A migration, like any other schema object; a UDF that only exists in one environment is the same problem as an undeployed proc.
  • Why are custom translators risky? — They bind to EF's internal expression APIs, which are not part of the compatibility promise, so a major upgrade can break them.
  • Convention or configuration? — Convention when the rule must apply to types that do not exist yet; explicit configuration when the set is closed and you want it visible.

Wrong answer that gets people rejected

"You can't extend EF's SQL generation." You can, at several levels, and knowing the ladder — HasDbFunction, conventions, translator plugins — is what distinguishes someone who has actually pushed EF into a corner.

principalWhen is depending on EF internals justified, and how do you manage that debt?

Answer

Rarely, and only with an explicit owner and an exit plan. The legitimate cases are a translation your workload genuinely needs and Microsoft has not shipped, a provider-level capability you must expose, or a diagnostic tool that inspects the model. Everything else — clever reflection over InternalEntityEntry, replacing internal services to change behaviour, or depending on a bulk-extension library that hooks internals — buys convenience against a real, recurring cost: EF's internal APIs carry no compatibility guarantee, so every major version is a potential break, and that break lands on the critical path of an upgrade you are doing for a support deadline. The management practice I would put in place: an inventory of every internal dependency with a named owner and a test that fails loudly on upgrade; a preview-testing step in the release cycle so breaks are found against EF previews rather than after GA; and a standing bias to contribute the capability upstream or drop to raw SQL instead, because both have stable contracts. Concretely, before adopting anything that touches internals I ask "what is our plan when this blocks an LTS upgrade?" — and if there is no answer, the dependency does not get added.

Example

// A stable alternative to reaching into internals: public metadata APIs.
foreach (var entity in db.Model.GetEntityTypes())
foreach (var prop in entity.GetProperties().Where(p => p.ClrType == typeof(decimal)))
    if (prop.GetPrecision() is null)
        throw new InvalidOperationException($"{entity.Name}.{prop.Name} has no precision configured");

Follow-ups

  • How do you evaluate a third-party EF library? — Release cadence against EF majors, how deeply it hooks internals, and whether a maintained fallback exists.
  • What is the cheapest mitigation? — Run the test suite against EF previews in CI; you learn about breaks months early and can raise the issue upstream.
  • When would you contribute upstream instead? — When the need is general; EF takes community contributions, and several EF10 features (named query filters, the ExecuteUpdate lambda change) came in that way.

Wrong answer that gets people rejected

"We only use public APIs, so it's not a problem." Most teams do depend on internals indirectly, through libraries. Not knowing your transitive exposure is the version of this answer that fails during an upgrade.

20Judgment calls

Open-ended questions with no single right answer, asked from senior upwards and used to see how you reason rather than what you recall. The hidden part of each block says what a strong answer demonstrates and which trade-offs you are expected to name without being prompted. The failure mode in all of them is the same: picking a side quickly and defending it, instead of naming the drivers and then choosing.

Docs: Microsoft Learn — EF Core documentation

seniorRepository and unit-of-work layers over EF: worth it or not?

What a strong answer demonstrates

That you know DbContext already is a unit of work and DbSet already is a repository, so the burden of proof is on adding the layer. A strong answer distinguishes the generic IRepository<T> (usually pure cost) from a domain-language, aggregate-shaped repository (sometimes real value: it enforces "load and save aggregates whole", hides the include strategy, and gives handlers a vocabulary). It also refuses the standard justification — "so we can swap the ORM" — with the specific reason that the abstraction leaks IQueryable, tracking semantics, lazy loading and migrations, so the swap would not be cheap anyway.

Trade-offs to name unprompted

  • Composability lost: a repository returning materialised lists forces every caller into the shapes you anticipated; one returning IQueryable gives back all the coupling you removed.
  • Testability gained is mostly illusory — mocking the repository tests the mock, and a container-backed integration test is more valuable.
  • Team-scale value: a boundary that new engineers cannot accidentally cross is worth more in a 40-person org than in a 4-person one.
  • The honest alternative: no repository, plus architecture tests that enforce the rules you would have enforced with one.
seniorShould reads default to tracking or no-tracking?

What a strong answer demonstrates

That you understand what tracking buys (change detection, identity resolution, relationship fixup) and what it costs (snapshots per entity, DetectChanges at save, memory proportional to result size), and that the choice is a default with an escape hatch either way. A strong answer picks no-tracking as the default for a read-heavy service via QueryTrackingBehavior.NoTracking — and immediately names the migration hazard: every existing write path that loads-then-mutates silently stops saving unless it opts back in with AsTracking(), which needs a test sweep, not a flag flip.

Trade-offs to name unprompted

  • Silent failure mode: a no-tracking default turns a missing AsTracking() into "the save did nothing", with no exception.
  • Identity resolution: without it, duplicate rows materialise as duplicate objects, which changes serialisation output and object equality.
  • Projections make the question mostly moot — a DTO projection is untracked regardless, so the real answer may be "project more".
  • Measure before switching: the win is proportional to result-set size, and on small results it is noise.
seniorWhere does the schema's source of truth live — the model or the database?

What a strong answer demonstrates

That "both" is the only truly wrong answer, and that either single-owner model works if it has a drift-detection mechanism. Model-owned means migrations in the repo, generated SQL reviewed in the PR, and the application never running DDL at runtime. Database-owned means scaffolding in CI with a build failure on drift. A strong answer picks one for the context described — service-owned database → model-owned; shared enterprise database with a database team → database-owned — and names the mechanism, not just the policy.

Trade-offs to name unprompted

  • Model-owned gives one reviewable deployment artefact but requires developers to understand DDL cost (index builds, locks) they cannot see in C#.
  • Database-owned gives DBA control but decouples schema change from application release, which makes rolling deploys harder to reason about, not easier.
  • Whoever owns it, the deployment identity must differ from the runtime identity, or "owned by the DBA" is fiction.
  • Drift detection is not optional in either model; without it you find out during an incident.
seniorWhen do you introduce a second data-access technology alongside EF?

What a strong answer demonstrates

Pragmatism with a written rule. The defensible position is that EF owns the transactional model and the migrations, and a second tool (Dapper, raw ADO.NET, a bulk library) is admitted for specific, named workloads: reporting queries with shapes LINQ cannot express, bulk ingest, and very hot point reads. A strong answer notes that EF can often absorb the first case itself via FromSql/SqlQuery<T>/keyless types, keeping one connection, one transaction and one schema story — so the second technology should be justified by something more than "SQL is easier here".

Trade-offs to name unprompted

  • Global query filters — including tenant isolation — do not apply outside EF, so every raw path needs the predicate written and tested by hand.
  • Two technologies means two mental models for the team and two places a schema change must be checked.
  • The migration story must stay single: whichever tool queries, EF should still own the schema, or you have two sources of truth.
  • Unprincipled mixing is the real risk; the rule matters more than which side of it you land on.
seniorSoft delete everywhere, or hard delete with an audit trail?

What a strong answer demonstrates

That soft delete is a product decision with a long operational tail, not a default. A strong answer asks what the requirement actually is — undo, audit, referential safety, or regulatory retention — because each has a different best answer: undo wants a status field with an expiry, audit wants an audit log or temporal tables, referential safety wants proper FK design, and retention wants an explicit policy with a purge path. It also names the specific EF consequences: filtered unique indexes, cascade behaviour, the ExecuteDelete hole in SaveChanges-override implementations, and index bloat as deleted rows accumulate.

Trade-offs to name unprompted

  • Right-to-erasure obligations make "we never delete" a compliance liability, so a purge path must exist regardless.
  • Every index must account for the filter or reads degrade as the deleted proportion grows.
  • SQL Server temporal tables give history for free and answer "what did this look like then", which soft delete does not.
  • Blanket soft delete across every entity is usually cargo cult; per-aggregate decisions are cheaper to live with.
principalA senior engineer wants to replace EF with Dapper across the service. How do you handle it?

What a strong answer demonstrates

That you engage the underlying complaint rather than the proposal. The complaint is usually one of: unpredictable SQL, slow endpoints, an opaque change tracker, or a bad experience with a specific EF version. A strong answer asks for the evidence, offers to fix the top three endpoints with EF first (projection, keyset, indexes) as a cheap experiment, and frames the decision in terms the business understands: migration cost, the loss of migrations and change tracking, and who maintains the hand-written SQL in three years. It also leaves room for the possibility that the engineer is right for a subset of the system, and proposes the hybrid rather than a binary.

Trade-offs to name unprompted

  • Dapper gives predictable SQL and no tracking — which means you also hand-write every update, every graph save, and every schema change's consequences.
  • You lose migrations, global query filters (tenant isolation!), and concurrency-token handling as framework features.
  • Team fit matters: hand-written SQL raises the floor of SQL skill required from every contributor.
  • The hybrid is usually right, and it needs a written rule to stop it becoming ad-hoc.
principalHow much consistency do you give up for scale?

What a strong answer demonstrates

That you can locate the boundary deliberately instead of drifting across it. A strong answer keeps strong consistency inside an aggregate and inside a service's own database — where EF's transaction gives it to you for free — and accepts eventual consistency across services, with the outbox as the mechanism and idempotent consumers as the requirement. It names the user-visible consequences (read-your-writes, stale lists, duplicate messages) and the mitigations (read from the writer for a short window, show staleness, deduplicate by message id) rather than pretending the trade is invisible.

Trade-offs to name unprompted

  • Eventual consistency is a product decision: someone must own what the user sees during the window.
  • Read replicas introduce the same problem inside one service — replica lag breaks read-your-writes on the endpoint right after a save.
  • Split queries trade cross-query atomicity for row-count sanity; that is the same decision in miniature.
  • Distributed transactions are not the escape hatch: they trade availability for a consistency guarantee you probably do not need.
principalDo you let developers write raw SQL, and under what conditions?

What a strong answer demonstrates

That "no" is unrealistic and "yes, anywhere" is unsafe, so the answer is a set of conditions. A workable policy: raw SQL is allowed inside the data-access layer only, always through the parameterising APIs (FromSql, ExecuteSql, SqlQuery), never with concatenation — enforced by EF Core 10's analyzer and a Roslyn rule about call sites — with tenant predicates written explicitly and covered by a test, and with an integration test per statement so a schema change breaks CI rather than production. A strong answer also notes that raw SQL is where filters and interceptors stop applying, which is the real risk, not injection.

Trade-offs to name unprompted

  • Raw SQL bypasses global query filters, so tenant and soft-delete isolation must be re-established by hand.
  • It also bypasses SaveChanges interceptors, so audit and outbox writes must be explicit.
  • Schema changes no longer break the build — only tests catch them, so the tests are mandatory rather than nice to have.
  • A blanket ban pushes people to worse workarounds (client-side filtering, N+1 loops) that are harder to spot.
principalWhen do you upgrade EF majors, and who pays for it?

What a strong answer demonstrates

That support dates make this a scheduling fact rather than a preference: EF Core 9 went out of support with .NET 9 in May 2026, EF Core 8's LTS support ends on 10 November 2026, and EF Core 10 is supported to 10 November 2028 — so a service on EF8 has a deadline, not an option. A strong answer proposes an LTS-to-LTS cadence for most services, budgeted as standing platform work rather than negotiated per release, with the upgrade risk managed by the integration suite, SQL-shape baselines and a preview-testing step, and with third-party provider support checked before committing.

Trade-offs to name unprompted

  • Skipping an LTS doubles the breaking-change surface but halves the number of upgrade projects; either is defensible if chosen deliberately.
  • STS releases carry newer features and a shorter runway — fine for a service that upgrades continuously, poor for one that ships twice a year.
  • Provider and bulk-library lag is the most common blocker and must be verified first.
  • Deferring past end of support converts a planned cost into an unplanned security risk, which is the argument that actually funds the work.
principalYour team keeps shipping N+1s and cartesian explosions. Process, tooling, or people?

What a strong answer demonstrates

That you diagnose before prescribing, and that you prefer mechanisms over exhortation. A strong answer treats recurring identical defects as a systems signal: the cost of the mistake is invisible at the time it is made, so the intervention is to make it visible — query-count and rows-returned guardrail tests, SQL-shape snapshots on hot paths, a short written standard covering the five decisions that matter, and EF's own warnings escalated to errors where appropriate. Training has a place, but only after the feedback loop exists, because knowledge without a signal decays in a sprint.

Trade-offs to name unprompted

  • Guardrail tests are maintenance: keep them to the top endpoints or they get disabled wholesale.
  • Escalating warnings to errors can block legitimate work; pair each with a documented, reviewable suppression.
  • A written standard is only load-bearing if it is short — a 20-page document is a wiki page nobody reads.
  • If one person is the bottleneck for data-access review, that is the actual defect in the system.

Exercise 1 — Multi-tenant SaaS data layer

Prompt. You are designing the data layer for a B2B SaaS product on .NET 10 and EF Core 10. Expected scale at year three: 5,000 tenants, of which perhaps 20 are 100× the median size; two enterprise customers contractually require their data in a separate database in a specific region. Every table is tenant-scoped. Design the tenancy model, the EF configuration, the migration strategy and the isolation guarantees.

Clarifying questions to ask. What are the regulatory constraints (data residency, per-tenant encryption, right to erasure)? What is the per-tenant restore requirement — can we restore one tenant without affecting others? What is the size distribution, and how fast does the biggest tenant grow? Is there cross-tenant reporting? What is the acceptable downtime for a tenant migration? Who operates the database fleet, and how many databases can they realistically manage?

principalSolution outline and expected trade-offs

Shape of a strong solution

A hybrid with a tenant catalogue. A small control-plane database maps tenant id to a connection string and a tier; the application resolves the tenant from the request (host, token claim, or path), looks it up, and creates the context from an IDbContextFactory with that connection. The long tail shares one database with a TenantId column on every table and a named tenant query filter; whales and the two contractual customers get dedicated databases with the identical model, so the code path is the same and only the connection differs. That single decision — indirection through a catalogue from day one — is what makes moving a tenant later a data migration rather than a rewrite.

EF specifics

// Named filters (EF10) so admin views can drop soft-delete without dropping tenancy.
mb.Entity<Order>()
  .HasQueryFilter("TenantFilter", o => o.TenantId == _tenant.Id)
  .HasQueryFilter("SoftDeletionFilter", o => !o.IsDeleted);

// Every index leads with TenantId so one tenant's scan stays in its own range.
mb.Entity<Order>().HasIndex(o => new { o.TenantId, o.CreatedUtc }).IsDescending(false, true);

// No AddDbContextPool: the tenant is per-request state on the context.
services.AddDbContext<AppDb>((sp, o) =>
    o.UseSqlServer(sp.GetRequiredService<ITenantContext>().ConnectionString));

Migrations

Not at startup, and not one command. A migration job reads the catalogue, applies the idempotent script or an efbundle per tenant with bounded parallelism (10–20), records per-tenant status, is resumable, and rolls out canary → small → large with an automatic stop on unexpected failure. Every change is expand–contract so the application serves tenants at either schema version during the roll-out. The shared database migrates once; the dedicated ones migrate individually, and the job must not stop the fleet for one failing tenant.

Isolation guarantees

Filters are the convenience layer, not the boundary. Add defence in depth: SQL Server row-level security or per-tenant database credentials so a missed predicate cannot leak; a model test asserting every ITenantOwned entity has the tenant filter; an endpoint-sweep test attempting cross-tenant access on every route; tenant id in every cache key with its own test; and explicit tenant predicates in any raw SQL, since filters do not reach it.

Trade-offs you are expected to name unprompted

  • Shared schema: cheapest to migrate and operate, worst blast radius, noisy neighbours unmitigated, plan skew between whale and median tenants (mitigate with EF.Constant for large tenants).
  • Database per tenant: best isolation and per-tenant restore, but N migration runs, N connection pools, N monitoring targets — an operations problem long before it is an engineering one.
  • The catalogue is a single point of failure and must be cached, replicated and independently deployable.
  • Connection-pool arithmetic: pools are per connection string, so a few hundred dedicated tenants can exhaust the server's connection limit before the application notices.
  • Cross-tenant reporting is hard in the hybrid model and needs its own path — a warehouse or per-tenant extracts, not a query over both.
  • Tenant migration (shared → dedicated) needs a documented, rehearsed runbook, or the first whale becomes an incident.

Exercise 2 — Order system whose reads are drowning the writes

Prompt. An order-management service on EF Core: 3,000 writes/minute and 60,000 reads/minute, one SQL Server. The order list and dashboard endpoints are at 4s p99 and the write path is now timing out under load. Orders have lines, shipments, payments and a status history. Redesign the data access. You may not rewrite the whole service.

Clarifying questions to ask. What does the dashboard actually show, and how fresh must it be? What is the read/write ratio per endpoint, and which endpoints dominate? Are reads and writes hitting the same rows? Is there a read replica available? What are the current indexes, and what does the query store say is top by CPU and by reads? Is the write timeout caused by lock waits, or by the writes themselves being slow?

principalSolution outline and expected trade-offs

Shape of a strong solution

Measure first, then apply four changes in increasing cost order. (1) Fix the read queries: replace Include-heavy list endpoints with projections computing counts and sums in SQL, add keyset pagination, and add covering indexes matching the filter-then-sort shape — this alone typically removes most of the 4s. (2) Stop reads from blocking writes: enable READ_COMMITTED_SNAPSHOT on the database, which removes reader-writer blocking without an application change, and confirm the write timeouts were lock waits rather than slow writes. (3) Split read and write paths: a no-tracking read context, pointed at a read replica with ApplicationIntent=ReadOnly for the dashboard, accepting replica lag with a visible "as of" timestamp. (4) Only if still needed, maintain a denormalised OrderListView table updated from the write path (or from the outbox), so the list endpoint is a single-table seek.

EF specifics

// The list endpoint, rewritten: one query, five columns, no cartesian product.
var page = await read.Orders.AsNoTracking()
    .Where(o => o.TenantId == tenantId
             && (o.CreatedUtc < cursorCreated
                 || (o.CreatedUtc == cursorCreated && o.Id < cursorId)))
    .OrderByDescending(o => o.CreatedUtc).ThenByDescending(o => o.Id)
    .Take(50)
    .Select(o => new OrderListItem(
        o.Id, o.Number, o.Status, o.CreatedUtc,
        o.Lines.Count,
        o.Lines.Sum(l => l.Quantity * l.UnitPrice)))
    .TagWith("orders/list")
    .ToListAsync(ct);

// Status transitions: narrow, atomic, no read-modify-write.
var moved = await db.Orders
    .Where(o => o.Id == id && o.Status == OrderStatus.Picked)
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Shipped), ct);

Write path

Shrink the transactions: no external calls inside them, smaller MaxBatchSize if lock escalation is visible, deterministic ordering of updates to remove deadlocks, and optimistic concurrency (rowversion) instead of pessimistic locks. Status changes become conditional ExecuteUpdate statements so two workers racing produce a zero-row result rather than a lost update.

Trade-offs you are expected to name unprompted

  • Read replica: cheap and effective, but lag breaks read-your-writes right after a save — route the post-write read to the primary or show the timestamp.
  • READ_COMMITTED_SNAPSHOT moves cost to tempdb version store; it is a database-wide change that needs a maintenance window and monitoring.
  • The denormalised view table is eventual consistency inside one service: it can drift, so it needs a rebuild path and a drift check.
  • Every added index costs write throughput and storage; on a write-heavy table that is a real budget, not a free lunch.
  • Keyset paging removes "jump to page 500", which is a product change that must be agreed, not smuggled in.
  • Doing (4) before (1) is the classic over-engineering failure — it adds a consistency problem to a service whose queries were simply wrong.

Exercise 3 — Zero-downtime schema evolution across 40 services

Prompt. Your organisation runs 40 EF Core services, deployed continuously, several instances each. Last quarter three incidents were caused by migrations: a column rename that broke in-flight instances, an index build that locked a table for 25 minutes, and a migration that ran three times concurrently from application startup. Design the schema-change process.

Clarifying questions to ask. Are deploys rolling or blue/green? Who currently runs migrations, and with what identity? Is there a production-sized restore available for rehearsal? Do any services share tables? What is the largest table, and what is the acceptable maintenance window? What EF versions are in the fleet, and are any past end of support?

principalSolution outline and expected trade-offs

Shape of a strong solution

Four mechanisms, plus one cultural rule. Migrations leave application startup: a pipeline stage or init container runs dotnet ef migrations bundle (or an idempotent script) under a dedicated migration identity, while the runtime identity loses DDL rights entirely — that removes the concurrent-startup incident by construction. Expand–contract is the default, taught as a pattern library with worked examples (rename, type change, NOT NULL, table split) so the safe path is the copy-paste path; the cultural rule is that every migration must leave the previous application version working. A CI gate renders the migration to SQL and fails on destructive or blocking operations unless the PR carries a reviewed label, and long index builds must use ONLINE = ON or be scheduled. A rehearsal stage applies the migration to a recent production-sized restore and reports duration and lock behaviour, which is the only reliable way to catch the 25-minute index build before customers do.

The pattern, concretely

// Expand: additive only, previous version still works.
migrationBuilder.AddColumn<string>("EmailAddress", "Customers", nullable: true);
migrationBuilder.CreateIndex("IX_Customers_EmailAddress", "Customers", "EmailAddress")
    .Annotation("SqlServer:Online", true);      // no long table lock

// Migrate: a resumable job, not a migration — batched, observable, cancellable.
// Contract: a later release drops the old column, after the safety window.

Fleet-level concerns

Standardise the pipeline template so identity, timeouts, retries and logging are solved once for all 40 services; publish the EF support calendar as a fleet obligation (EF Core 8 leaves support on 10 November 2026, EF Core 9 already has) so upgrades are scheduled rather than discovered; and maintain an ownership map for shared tables, converting shared writes into an owner plus views or read models over time.

Trade-offs you are expected to name unprompted

  • Expand–contract triples the number of deployments per change and requires someone to actually do the contract step, which is the step that gets forgotten.
  • The CI gate will produce false positives; a short, true rule list with a logged override beats a comprehensive one that everyone bypasses.
  • Rehearsal needs a production-sized, anonymised restore — real cost in storage and in data-protection work.
  • Init containers serialise the rollout and can slow deploys; a pipeline stage is faster but needs network access to the database.
  • Removing DDL rights from the runtime identity will break something on the first attempt (usually a test or a temp-table pattern) — plan the staging soak.
  • Centralising the pipeline template creates a platform-team dependency; it needs an owner and an escape hatch, or it becomes the new bottleneck.

22Night-before cheat sheet

The ten questions most likely to be asked, with the one-sentence answer to have ready. If you can say each of these cleanly and then expand on the follow-up, you are prepared for the screen and most of the loop.

  1. What lifetime should DbContext have? Scoped — one per request: it is not thread-safe, its change tracker accumulates state, and the unit of work should match the business operation; watch for scoped contexts captured by singletons.
  2. What is the difference between IQueryable and IEnumerable? Both are lazy; IQueryable translates the predicate to SQL while IEnumerable runs it in .NET after materialising every row.
  3. Eager, lazy or explicit loading? Project with Select for reads, Include when you need a tracked graph to mutate, explicit loading for conditional branches, and lazy loading essentially never in a server app because it silently generates N+1.
  4. What is cartesian explosion and how do you fix it? Two or more collection Includes cross-multiply the rows; AsSplitQuery() issues one query per collection instead, at the cost of more round trips and cross-query consistency.
  5. What does AsNoTracking change? The materialisation, not the SQL: no snapshots, no DetectChanges cost, no identity resolution — use AsNoTrackingWithIdentityResolution when duplicate rows must collapse to one object.
  6. How do you save a modified entity from a client? Load it by id and copy the allowed fields; db.Update(detached) marks every column modified and overwrites fields the client never sent.
  7. How does optimistic concurrency work? A rowversion/concurrency token goes into the UPDATE's WHERE; zero affected rows throws DbUpdateConcurrencyException, and the resolution — store wins, client wins or merge — is a business decision, never a blind retry.
  8. Do you run migrations at application startup? No: replicas race, the runtime identity needs DDL rights it should not have, and rolling deploys need expand–contract — use migrations bundle or an idempotent script in the deployment pipeline.
  9. What do ExecuteUpdate/ExecuteDelete do differently? One SQL statement, executed immediately, nothing loaded or tracked — query filters still apply but SaveChanges interceptors do not, so audit stamping and outbox writes must be explicit.
  10. What is the latest EF and what changed? EF Core 10 (11 November 2025, LTS to 10 November 2028, requires .NET 10): named query filters, complex types mapped to JSON plus optional and struct support, ExecuteUpdateAsync taking a plain lambda and working over JSON, a new default scalar-parameter translation for collections, LeftJoin/RightJoin, vector search on Azure SQL / SQL Server 2025, and log redaction of inlined constants — with EF Core 11 due 10 November 2026.
