.NET Aspire

interview · Aspire 13.5 · released 2026-08-18

Aspire interviews are rarely about API recall — they test whether you understand what Aspire actually is: a dev-time orchestrator plus an application model that also emits deployment artifacts, not a runtime, not a PaaS, not a replacement for Kubernetes. Interviewers separate candidates in three places: can you explain what happens between aspire run and a running container graph (DCP, endpoint allocation, configuration injection); can you say precisely what survives into production and what does not (service discovery variables and OpenTelemetry survive, the AppHost process does not); and can you make the adoption call for a team, including when the answer is "no". One naming note, because it dates candidates instantly: the product dropped its ".NET" prefix at 13.0 (11 Nov 2025) and is now just Aspire, a polyglot platform — this bank is filed under the older name but expects you to use the current one out loud. Facts are pinned to 8 Sep 2026: Aspire 13.5 (18 Aug 2026) is current and, under the Modern Lifecycle policy, the only supported release. Work the 20 sub-areas in map order — roughly the order real loops reach for them — then the judgment calls and the design exercises.

The recency facts an interviewer uses to date you. Aspire 8.0 (May 2024) shipped as a workload; 9.0 (Nov 2024) dropped the workload for the Aspire.AppHost.Sdk and added WaitFor, resource commands and persistent containers. 13.0 (11 Nov 2025) is the watershed: the product dropped ".NET" from its name, jumped 9.5 → 13 to decouple its version from .NET's, moved its repo from dotnet/aspire to microsoft/aspire, requires the .NET 10 SDK, folded Aspire.Hosting.AppHost into the SDK (Sdk="Aspire.AppHost.Sdk/13.x" on the project element), removed lifecycle hooks in favour of eventing, removed the publisher interfaces (IDistributedApplicationPublisher, PublishingContext, WithPublishingCallback) in favour of the aspire do pipeline model, renamed Aspire.Hosting.NodeJs → Aspire.Hosting.JavaScript and AddNpmApp → AddJavaScriptApp, and added single-file apphost.cs. 13.2 (Mar 2026) added aspire run --detach, aspire start/stop/ps, aspire agent, WithMcpServer(), dashboard telemetry export and the TypeScript AppHost in preview. 13.3 added Helm-based Kubernetes/AKS deployment and aspire destroy. 13.4 took the TypeScript AppHost to GA, added Aspire.Hosting.Go/AddGoApp(), made aspire publish/aspire deploy GA, removed aspire exec, and bumped the default PostgreSQL image 17.6 → 18.3 (which breaks existing data volumes). 13.5 (18 Aug 2026) added WithTerminal() in-dashboard terminals, a stable Interaction Service shared by C# and TypeScript, WithHttpsDeveloperCertificate(), cross-scope Azure references (AsExistingInResourceGroup/InSubscription/InTenant), the CLI on npm as @microsoft/aspire-cli, experimental Kubernetes AddPersistentVolume(), and the preview Aspire.Hosting.Radius target; it also obsoleted PublishAsConnectionString in favour of AddConnectionString. Support is Modern Lifecycle: only the newest release is supported — there is no LTS.

01Positioning and the mental model

Every Aspire loop opens here, and a surprising number end here too. The interviewer wants to know whether you have a correct model of what the product does — dev-time orchestration plus a declarative app model, with deployment as a derived output — or whether you have absorbed marketing. Screeners want a crisp one-sentence definition and one honest limitation; mid-level wants the comparison to Docker Compose and to Kubernetes; senior and principal are asked the "should we adopt this" question and are expected to answer with conditions, not enthusiasm. Getting the boundary wrong ("Aspire runs your app in production") is the single most common instant fail.

Docs: aspire.dev — Glossary of terms and concepts

screenerWhat is Aspire, in one or two sentences?

Answer

Aspire is an application platform built around a single C# (or, since 13.4, TypeScript) program — the AppHost — in which you declare every part of your distributed app: projects, containers, executables, cloud resources and the references between them. Locally that model is executed by an orchestrator that starts everything, wires connection strings and endpoints into each process as configuration, and streams logs, traces and metrics into a developer dashboard. The same model is then compiled into deployment artifacts for a target — Azure Container Apps, Azure App Service, Kubernetes via Helm, Docker Compose — so the topology you debugged is the topology you ship. It is not a runtime: nothing called "Aspire" is running in production.

Example

var builder = DistributedApplication.CreateBuilder(args);

var cache = builder.AddRedis("cache");
var db    = builder.AddPostgres("pg").AddDatabase("catalogdb");

var api = builder.AddProject<Projects.Catalog_Api>("catalog-api")
                 .WithReference(cache)
                 .WithReference(db)
                 .WaitFor(db);

builder.AddProject<Projects.Web>("web")
       .WithReference(api)
       .WithExternalHttpEndpoints();

builder.Build().Run();

Follow-ups

  • What is the AppHost at runtime? — A normal .NET console app built with Aspire.AppHost.Sdk; Run() starts the orchestrator, the dashboard and every declared resource.
  • Is it a service mesh? — No. There is no sidecar, no proxy in the request path, no mTLS layer. Service discovery is configuration, resolved in-process by the calling HttpClient.
  • What does it require? — The .NET 10 SDK (since 13.0), a container runtime (Docker Desktop or Podman) for containerised resources, and the aspire CLI or an IDE that ships it.

Common wrong answer

"Aspire is Microsoft's Kubernetes alternative / a cloud-native runtime that hosts your microservices." It is the most plausible wrong answer because the marketing word "cloud-native" invites it — and it is fatal, because every follow-up (scaling, failover, rolling deploys) then gets answered against a product that does not exist. Aspire's runtime story ends at the local machine and at the artifacts it generates.

screenerWhat problem was Aspire built to solve?

Answer

The gap between "I cloned the repo" and "the whole system runs on my machine". Before Aspire, a .NET solution with six services, Postgres, Redis and a queue meant a hand-written docker-compose.yml that drifted from the code, a README of environment variables, per-developer launchSettings.json port conflicts, and no shared way to see traces across services. Aspire replaces the YAML with typed C# that the compiler checks, generates the connection strings and endpoints instead of having you copy them, and gives every developer a dashboard with distributed traces on day one. The secondary problem it solves is consistency: OpenTelemetry, health checks, service discovery and HTTP resilience come pre-wired through the ServiceDefaults project rather than being reinvented per team.

  • Does that value disappear once the app is deployed? — No: ServiceDefaults' telemetry and resilience run in production, and the emitted artifacts keep the topology honest. But the biggest win stays the inner loop.
  • What if the team is one service and one database? — Then the win is small; Aspire pays off in proportion to how many moving parts a developer must start.

Common wrong answer

"It solves microservice deployment." Deployment is the part Aspire delegates: it emits artifacts and hands them to ACA, App Service, Kubernetes or Compose. Candidates who lead with deployment usually cannot then explain what the AppHost does locally, which is the actual product.

midAspire versus Docker Compose — when would you still choose Compose?

Answer

Compose is a static description of containers; Aspire is a program that describes resources, of which containers are one kind. The Aspire advantages are typed refactorable code, automatic configuration injection, projects that run as local processes with a debugger attached rather than as containers, and the dashboard. The costs are real: you need the .NET 10 SDK on every machine, the model is expressed in a language your Python or Go colleagues may not read (mitigated but not erased by the TypeScript AppHost, GA in 13.4), and you inherit Aspire's release cadence. I would still choose Compose when the stack has no .NET in it at all, when the artifact must be readable by a platform team that only speaks YAML, or when the environment is a CI runner that just needs three containers up. Note the two are not exclusive — AddDockerComposeEnvironment lets Aspire generate the Compose file, which is the pragmatic answer when the target is a VM running Compose.

Example

// Aspire as a Compose generator: model once, emit compose.yaml for the VM.
var builder = DistributedApplication.CreateBuilder(args);
var compose = builder.AddDockerComposeEnvironment("prod");

builder.AddPostgres("pg").WithDataVolume();
builder.AddProject<Projects.Api>("api").WithExternalHttpEndpoints();

builder.Build().Run();
// aspire publish -o ./artifacts  →  ./artifacts/compose.yaml + .env

Follow-ups

  • Can Aspire run a project as a container locally instead of a process? — Yes, PublishAsDockerFile() / container-ising the project; but the default is a local process precisely so F5 debugging works.
  • What do you lose by generating Compose rather than writing it? — Direct control of the file; you tune through the app model and callbacks instead, and hand-edits are overwritten on the next publish.
  • Does Compose give you the dashboard? — You can run the dashboard standalone as a container (mcr.microsoft.com/dotnet/aspire-dashboard) and point OTLP at it, with no AppHost involved.

Common wrong answer

"Aspire replaces Compose, so there is never a reason to use it." This reads as a fanboy answer and invites the interviewer to press until you concede — badly. The strong answer names the concrete costs (SDK prerequisite, C#-centric model, cadence) before the benefits.

midAspire versus Kubernetes — do they compete?

Answer

They operate at different times. Kubernetes is a runtime control plane: it schedules, restarts, scales and rolls out. Aspire is a build-time and dev-time model: it runs your app on your laptop and emits artifacts for a target. Since 13.3 one of those targets is Kubernetes — Aspire generates a Helm chart from the app model and applies it against your current kubectl context, and 13.4 added AddHelmChart(), Gateway API and cert-manager support. So the correct framing is "Aspire can be how you get to Kubernetes", not "instead of". The important caveat to volunteer: the generated chart is a starting point, and a platform team with an established GitOps pipeline, admission policies and a chart library will usually want Aspire's output as an input to their process rather than as the deployment mechanism.

Example

var builder = DistributedApplication.CreateBuilder(args);
var k8s = builder.AddKubernetesEnvironment("cluster");

builder.AddProject<Projects.Api>("api")
       .WithExternalHttpEndpoints();   // required for routed endpoints since 13.4

builder.Build().Run();
// aspire publish -o ./chart   → Helm chart
// aspire deploy               → applies to the current kubectl context

Follow-ups

  • What about stateful resources like Postgres? — In production you normally point at a managed service via AddConnectionString or AsExisting; the containerised Postgres is a dev-only convenience. 13.5 added experimental AddPersistentVolume() if you genuinely want it in-cluster.
  • Does the app know it is on Kubernetes? — Only through configuration. Service discovery falls back to DNS/DNS SRV resolution, which is why Microsoft.Extensions.ServiceDiscovery ships DNS SRV resolvers.
  • Would you commit the generated chart? — Yes for review and GitOps; regenerate and diff on change rather than hand-editing.

Common wrong answer

"You don't need Kubernetes any more because Aspire handles orchestration." It conflates two meanings of "orchestration": starting processes on one machine versus scheduling across a fleet with failure recovery. Interviewers ask this exact question to catch that conflation.

seniorWhat exactly runs in production when you deploy an Aspire app?

Answer

Your services, and nothing else that is called Aspire. The AppHost is a build-time and dev-time program: in publish mode it walks the resource graph and emits artifacts — a Helm chart, a Compose file, Bicep and container images for ACA — then exits. What follows your code into production are ordinary NuGet libraries: Microsoft.Extensions.ServiceDiscovery resolving logical names from configuration, the OpenTelemetry SDK exporting over OTLP, Microsoft.Extensions.Http.Resilience policies, and health-check endpoints — all of which you added yourself through ServiceDefaults and can keep or drop independently. The dashboard can optionally be deployed too (it is a standalone container image and ACA publishing includes it by default), but it is a telemetry viewer, not a control plane.

Example

// ServiceDefaults — this is the only "Aspire" that ships to prod, and it is
// just Microsoft.Extensions.* libraries wired up in one place.
public static IHostApplicationBuilder AddServiceDefaults(this IHostApplicationBuilder builder)
{
    builder.ConfigureOpenTelemetry();
    builder.AddDefaultHealthChecks();
    builder.Services.AddServiceDiscovery();
    builder.Services.ConfigureHttpClientDefaults(http =>
    {
        http.AddStandardResilienceHandler();
        http.AddServiceDiscovery();
    });
    return builder;
}

Follow-ups

  • Can you tell at runtime whether you are in publish mode? — In the AppHost, yes: builder.ExecutionContext.IsPublishMode / IsRunMode. Services themselves have no such notion.
  • If Aspire disappeared tomorrow, what would break in prod? — Nothing at runtime. You would lose artifact generation and the local loop, and would maintain the emitted manifests by hand.
  • Is the deployed dashboard safe? — Only behind authentication; it shows environment variables and telemetry for every resource. Treat it as an admin surface.

Common wrong answer

"The AppHost runs in production and supervises the services." Plausible because the AppHost is a long-running process locally, but wrong, and it destroys the follow-up conversation about scaling and failover. The AppHost has no production role.

seniorAspire versus Dapr, Tye and Radius — where does each fit?

Answer

Project Tye was the experiment Aspire superseded — same local-orchestration idea, archived, and naming it shows you know the lineage. Dapr is a runtime sidecar offering building blocks (pub/sub, state, bindings, service invocation) that your code calls over HTTP/gRPC; it competes with nothing in Aspire, and Aspire has a Dapr hosting integration so you can model sidecars in the app model. Radius is a deployment/application platform from the same corner of Microsoft that owns the environment-and-recipe abstraction; since 13.5 Aspire ships Aspire.Hosting.Radius in preview so Radius is just another publish target. The framing I use: Dapr is about what your code calls at runtime, Aspire is about how the system is described and started, Radius (and ACA, and Helm) is about where it lands.

Example

// Dapr modelled inside the Aspire app model — complementary, not competing.
var api = builder.AddProject<Projects.Api>("api")
                 .WithDaprSidecar(new DaprSidecarOptions { AppId = "api" });

Follow-ups

  • Would you use Dapr and Aspire together? — Yes, if you already want Dapr's building blocks; Aspire just makes the sidecars part of the declared topology instead of a compose fragment.
  • What killed Tye? — It stayed an experiment with no deployment story and no integration ecosystem; Aspire absorbed the idea with first-party investment.
  • Why does Radius matter to a principal? — It is the seam where an app model meets a platform team's environment definitions; naming it signals you understand platform engineering, not just dev tooling.

Common wrong answer

"Aspire is basically Dapr for .NET." They solve orthogonal problems, and the answer signals you have used neither. Dapr injects a sidecar into the request path; Aspire never touches the request path.

seniorWhere does Aspire genuinely not help, and where does it actively hurt?

Answer

It does not help a single service with a single database — the AppHost is then pure overhead over dotnet run. It does not help a team whose bottleneck is production reliability rather than onboarding. It actively hurts in three situations. First, when developers cannot run containers (locked-down laptops, no Docker licence, ARM images missing) the promise inverts and you spend the week debugging DCP. Second, when the org already has a mature platform — Backstage templates, a Helm chart library, GitOps — Aspire's generated artifacts fight the golden path and you get two sources of truth. Third, on the Modern Lifecycle support policy: only the newest release is supported, so a team that cannot upgrade quarterly is knowingly running unsupported infrastructure code. My rule is that Aspire earns its place when a developer must start four or more moving parts to do useful work.

Example

SituationVerdict
8 services, Postgres, Redis, a bus, all .NETclear yes
1 API + 1 DBno — overhead without payoff
Polyglot with 2 .NET services out of 12maybe — TypeScript AppHost, or Compose
Mature platform team with GitOpsdev-loop only; do not adopt the deploy path
No container runtime on dev machinesno

Follow-ups

  • Can you adopt only half of it? — Yes, and it is the usual right answer: use the AppHost for the inner loop, keep your existing deployment pipeline, and ignore aspire deploy.
  • What is the exit cost? — Low for the app model (delete the AppHost, restore your compose file), low for ServiceDefaults (it is plain Microsoft.Extensions.*), higher if you built custom resources and pipeline steps.

Common wrong answer

"There is no downside, it is all opt-in." Everything is opt-in until the AppHost becomes the only way the app starts and a new hire cannot run it. Interviewers at senior level are explicitly testing whether you can criticise a technology you like.

principalThe product renamed itself from ".NET Aspire" to "Aspire" and jumped 9.5 → 13. Why does that matter to you as an architect?

Answer

Three concrete consequences. First, versioning: Aspire's number no longer tracks .NET's, so "Aspire 13 works with .NET 10" is a compatibility statement you must check per release rather than infer — 13.0 raised the floor to the .NET 10 SDK. Second, scope: the rename signalled that Python, JavaScript/TypeScript, Go and containers are first-class, not bolt-ons, which changes the adoption calculus for polyglot orgs — a Node team can now own an apphost.mts (GA in 13.4) without learning C#. Third, support: an independent cadence with roughly quarterly minors and a Modern Lifecycle policy means the newest release is the only supported one, so I budget an upgrade slot every quarter and pin versions centrally. Practically I also update my searching habits: the repo moved from dotnet/aspire to microsoft/aspire and the docs moved from learn.microsoft.com to aspire.dev.

Example

<!-- 9.x: SDK as a child element, plus an explicit AppHost package -->
<Project Sdk="Microsoft.NET.Sdk">
  <Sdk Name="Aspire.AppHost.Sdk" Version="9.5.0" />
  <ItemGroup><PackageReference Include="Aspire.Hosting.AppHost" Version="9.5.0" /></ItemGroup>
  <PropertyGroup><TargetFramework>net9.0</TargetFramework></PropertyGroup>
</Project>

<!-- 13.x: the SDK is the project SDK; the AppHost package is folded in -->
<Project Sdk="Aspire.AppHost.Sdk/13.5.0">
  <PropertyGroup><TargetFramework>net10.0</TargetFramework></PropertyGroup>
</Project>

Follow-ups

  • How do you actually perform the upgrade? — aspire update (and aspire update --migrate, added in 13.5) rewrites package versions including under Central Package Management; aspire update --self updates the CLI itself.
  • What breaks going 9.x → 13? — Lifecycle hooks, the publisher interfaces, AddNpmApp, the Aspire.Hosting.NodeJs package id, and net9.0 targets. Coming from 8.x you must also dotnet workload uninstall aspire.
  • How do you keep a monorepo coherent? — Central Package Management with one AspireVersion property, and the SDK version pinned in global.json/aspire.config.json so CI and laptops agree.

Common wrong answer

"It's just marketing, nothing changed." The rename came with a hard .NET 10 floor, removed public extension points and a support policy with no LTS — all of which land on the architect. Waving it off is exactly the answer that shows you have not upgraded a real codebase.

02The AppHost and the app model

This is the technical core and the longest section, because everything else is downstream of it. Interviewers probe it three ways: can you write a small AppHost from memory; do you understand that the AppHost is a builder that runs to completion before anything starts, so callbacks and eventing exist for anything dynamic; and can you keep a 40-resource AppHost maintainable. At screener level you need AddProject, AddContainer, WithReference; at mid, endpoints and WaitFor; at senior, the run-mode/publish-mode split and expression values; at principal, how you would structure the model across teams.

Docs: aspire.dev — What is the Aspire AppHost?

screenerWhat is in an AppHost project, and how does it find your services?

Answer

It is a console project whose SDK is Aspire.AppHost.Sdk (since 13.0 declared as the project SDK, Sdk="Aspire.AppHost.Sdk/13.5.0"), targeting net10.0. It references every service project you want to orchestrate with an ordinary ProjectReference; the SDK marks those as Aspire project resources and a source generator emits a Projects namespace with one class per referenced project. That is why AddProject<Projects.Catalog_Api>("catalog-api") compiles: Projects.Catalog_Api is generated metadata carrying the project path, not a reference to your Program class. The dots in the project name become underscores, which is the detail people trip over.

Example

<Project Sdk="Aspire.AppHost.Sdk/13.5.0">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <IsAspireHost>true</IsAspireHost>
  </PropertyGroup>
  <ItemGroup>
    <ProjectReference Include="..\Catalog.Api\Catalog.Api.csproj" />
  </ItemGroup>
  <ItemGroup>
    <PackageReference Include="Aspire.Hosting.PostgreSQL" Version="13.5.0" />
  </ItemGroup>
</Project>

Follow-ups

  • Does the AppHost's ProjectReference create a compile-time dependency on the service's code? — No; the SDK rewrites those references so no assembly is linked, only metadata is generated. That is why an AppHost can reference a project it could not otherwise compile against.
  • Can you avoid the generated types? — Yes: AddProject("api", "../Catalog.Api/Catalog.Api.csproj") takes a path, which is what you use for dynamically discovered projects and what the TypeScript AppHost always does.
  • What is IsAspireHost for? — It marks the project so tooling (IDEs, the CLI's aspire ls) can find AppHost candidates.

Common wrong answer

"The AppHost references and calls into your services." It never loads your service assemblies; it starts them as separate processes. Candidates who think otherwise then propose sharing types or singletons through the AppHost, which cannot work.

screenerWhat does WithReference actually do?

Answer

It records a dependency in the model and, at start time, injects configuration into the consuming resource's environment. What gets injected depends on the referenced resource: for a resource with a connection string (Postgres, Redis, a Service Bus) you get ConnectionStrings__<name>; for a project or container with endpoints you get service discovery variables shaped services__<name>__<endpoint>__<index>. Crucially it is configuration only — no network policy, no ordering guarantee, no proxying. Ordering is a separate concern handled by WaitFor, and that separation is the single most-tested nuance in this area.

Example

var db  = builder.AddPostgres("pg").AddDatabase("catalogdb");
var api = builder.AddProject<Projects.Api>("api").WithReference(db).WaitFor(db);

// api receives:
//   ConnectionStrings__catalogdb = Host=localhost;Port=54321;Username=postgres;Password=...;Database=catalogdb
builder.AddProject<Projects.Web>("web").WithReference(api);
// web receives:
//   services__api__https__0 = https://localhost:7123
//   services__api__http__0  = http://localhost:5123

Follow-ups

  • Does WithReference wait for the dependency? — No. That is WaitFor (healthy/running) or WaitForCompletion (exited successfully, for migration jobs).
  • Can you reference a single endpoint? — Yes: WithReference(api.GetEndpoint("grpc")) injects only that endpoint.
  • How do you rename what the consumer sees? — WithReference(db, connectionName: "Default") changes the config key, useful when the app expects a legacy name.
  • What about a resource outside the model? — AddConnectionString("legacy") or AddExternalService("payments", "https://…"), then reference it like anything else.

Common wrong answer

"WithReference makes sure the database is up before the API starts." It is the most common answer given, and it is wrong — which is exactly why interviewers ask. Referencing wires configuration; waiting is opt-in and costs startup time, so Aspire refuses to do it implicitly.

midExplain WaitFor versus WaitForCompletion, and what "ready" means.

Answer

WaitFor(x) holds the dependent resource until x is running and all of its health checks report Healthy; if x has no health checks, running is enough, which is why a bare WaitFor on a container often lets the consumer start against a database that is still initialising. WaitForCompletion(x) waits for x to exit, optionally asserting an exit code — that is the migration-job pattern. Both were added in 9.0 and are the reason the old "retry in a loop at startup" code can be deleted. The senior nuance: waiting is a local-loop convenience that also has meaning in publish mode for some targets, but you must not rely on it as a distributed-systems guarantee — services still need retry, because in production nothing enforces this ordering.

Example

var pg  = builder.AddPostgres("pg").WithDataVolume();
var db  = pg.AddDatabase("catalogdb");

var migrations = builder.AddProject<Projects.MigrationService>("migrations")
                        .WithReference(db)
                        .WaitFor(db);

builder.AddProject<Projects.Api>("api")
       .WithReference(db)
       .WaitForCompletion(migrations, exitCode: 0);   // API starts only after migrations succeed

Follow-ups

  • How do you make WaitFor meaningful for a bespoke container? — Give it a health check: WithHttpHealthCheck("/ready"), or a custom AddCheck registered against the resource.
  • What if the dependency never becomes healthy? — The dependent stays in Waiting; the dashboard shows the blocking resource, and since 13.4 the dependency-waiting state is visualised explicitly.
  • Does waiting slow down every developer? — Yes, measurably; chain it only where a cold start genuinely fails, not everywhere.

Common wrong answer

"WaitFor guarantees ordering in production too." It is a dev-loop and publish-time modelling construct; ACA, Kubernetes and Compose have their own (weaker) notions. Saying it guarantees production ordering signals you have never had a service restart while its database was failing over.

midHow are endpoints modelled, and how are ports chosen?

Answer

Every resource can expose named endpoints, each with a scheme, a target port (inside the process or container) and a host port (outside). For projects, endpoints come from launchSettings.json by default; for containers, from WithEndpoint/WithHttpEndpoint/WithHttpsEndpoint or the integration's defaults. If you do not pin a host port the orchestrator allocates a free one at start, which is what stops two developers colliding — and why hard-coding localhost:5001 anywhere in your code defeats the whole design. WithExternalHttpEndpoints() marks endpoints that should be publicly routable when deployed; since 13.4 it is required for routed endpoints on Kubernetes targets rather than merely advisory. Endpoints are referenced as expression values, e.g. api.GetEndpoint("http"), which resolve at start time.

Example

var api = builder.AddProject<Projects.Api>("api")
                 .WithHttpEndpoint(name: "admin", port: 5199)   // pinned host port
                 .WithHttpsEndpoint(name: "grpc")               // allocated
                 .WithExternalHttpEndpoints();

builder.AddProject<Projects.Worker>("worker")
       .WithReference(api.GetEndpoint("grpc"))
       .WithEnvironment("ADMIN_URL", api.GetEndpoint("admin"));

Follow-ups

  • Why does a container endpoint have both port and targetPort? — targetPort is the port inside the container; port is what the host publishes. Getting them backwards is the classic "connection refused".
  • Can two resources share a port? — Only if you pin the same host port, which will fail; leave them unpinned unless an external tool needs a stable URL.
  • How do containers reach a project running as a host process? — Through the host-gateway address the orchestrator injects, not localhost; this is why container-to-project references must go through the model.
  • What changed for HTTPS in 13.5? — WithHttpsDeveloperCertificate() makes the ASP.NET Core dev cert available to containers and non-.NET resources, replacing hand-rolled cert mounting.

Common wrong answer

"Ports come from launchSettings.json, so they are fixed." Half true for projects and false for everything else — and if you pin every port you reintroduce the collisions Aspire exists to remove. The right instinct is: unpinned by default, pinned only where an external consumer demands stability.

midWhat is the difference between a project, container, executable and parameter resource?

Answer

A project resource (AddProject) is a .NET project run as a local process with the debugger attachable, and containerised at publish time. A container resource (AddContainer, and everything AddRedis/AddPostgres builds on) runs an image through Docker or Podman. An executable resource (AddExecutable) runs any command line — a Python script, a Go binary, npm run dev — as a process. A parameter resource (AddParameter) has no process at all: it is a value, possibly a secret, that other resources consume and that deployment prompts for. There are also value-only resources such as AddConnectionString and, since 9.5, AddExternalService for third-party URLs you want visible in the graph. The unifying idea is that everything is an IResource in one graph, so tooling treats them uniformly.

Example

var pw   = builder.AddParameter("pg-password", secret: true);
var pg   = builder.AddPostgres("pg", password: pw);           // container
var mail = builder.AddContainer("mailpit", "axllent/mailpit")
                  .WithHttpEndpoint(targetPort: 8025, name: "ui");
var tool = builder.AddExecutable("codegen", "npx", "./tools", "openapi-gen");
var pay  = builder.AddExternalService("payments", "https://api.stripe.com");

Follow-ups

  • What happens to an AddExecutable at publish time? — Nothing useful unless you tell it: give it a Dockerfile (PublishAsDockerFile) or use a language-specific integration such as AddPythonModule or AddGoApp, which know how to build an image.
  • Why model an external service you do not control? — It shows in the graph, gets health checks, and its URL becomes a parameter rather than a hard-coded string.
  • Is there a resource with no runtime at all? — Yes, parameters and connection strings; they exist purely to be referenced.

Common wrong answer

"Projects are just containers with a shortcut." They are deliberately not containers in run mode — that is what preserves hot reload and a native debugger. Missing this leads candidates to propose containerising everything locally and wondering why the inner loop got slow.

seniorRun mode versus publish mode: how does one AppHost serve both?

Answer

The AppHost program runs in one of two execution contexts, exposed as builder.ExecutionContext.IsRunMode and IsPublishMode. In run mode the goal is a fast local loop, so you use emulators and containers; in publish mode the goal is artifacts, so the same logical resource points at a managed service. The idiomatic expression of this is the RunAsEmulator() / RunAs...() family on Azure integrations, or an explicit if. The senior point to volunteer is that this is where an AppHost becomes hard to reason about: the more branching, the less "the topology you debugged is the topology you ship" holds. I keep the branches to one obvious block near the resource definition, and I make the difference visible in the dashboard rather than hidden in a helper.

Example

var sb = builder.AddAzureServiceBus("bus");
if (builder.ExecutionContext.IsRunMode)
{
    sb.RunAsEmulator();                       // container emulator locally
}

var storage = builder.AddAzureStorage("storage").RunAsEmulator();  // Azurite locally
var blobs   = storage.AddBlobs("blobs");

var cache = builder.ExecutionContext.IsRunMode
    ? builder.AddRedis("cache")                                  // container
    : builder.AddAzureRedis("cache").AsExisting(name, group);     // managed, existing

Follow-ups

  • What is the difference between RunAsEmulator() and RunAsContainer()? — Both are run-mode-only substitutions; RunAsEmulator is used where Azure ships an official emulator (Storage/Azurite, Cosmos, Service Bus, Event Hubs), RunAsContainer where a plain OSS container stands in (e.g. Azure Redis → Redis).
  • And PublishAs…? — The mirror image: keep the local container, change what publish emits, e.g. PublishAsAzureContainerApp, or the now-obsolete PublishAsConnectionString (use AddConnectionString since 13.5).
  • How do you test publish mode without deploying? — aspire publish -o ./artifacts and diff the output in review; it is a pure function of the model.

Common wrong answer

"You keep two AppHosts, one for dev and one for prod." Duplicating the model reintroduces exactly the drift Aspire removes; the whole design is one graph with mode-conditional bindings. This answer usually comes from someone who hit a hard case and forked instead of using ExecutionContext.

seniorWhat are expression values (ReferenceExpression), and why can't you just use string interpolation?

Answer

Because the AppHost's builder phase completes before anything starts: at the moment you write the line, no port has been allocated, no parameter resolved, no connection string materialised. Aspire therefore models values that are not known yet as IValueProvider/ReferenceExpression — an interpolated-string handler builds a deferred expression, and the orchestrator resolves it just before the consuming resource starts. In publish mode the same expression is emitted unresolved, as a Bicep parameter, a Compose ${VAR}, or a Helm value. Plain interpolation would either capture an empty string locally or bake a developer's laptop port into a production manifest.

Example

var pw  = builder.AddParameter("api-key", secret: true);
var api = builder.AddProject<Projects.Api>("api");

// Deferred: resolved at start time locally, emitted as a reference at publish time.
builder.AddProject<Projects.Worker>("worker")
       .WithEnvironment("CALLBACK", ReferenceExpression.Create(
           $"{api.GetEndpoint("https")}/callbacks?key={pw}"));

// Broken: evaluated during the builder phase, before endpoints exist.
// .WithEnvironment("CALLBACK", $"{api.GetEndpoint("https")}/callbacks");

Follow-ups

  • How do you compute something genuinely dynamic? — The callback overload: WithEnvironment(ctx => { ctx.EnvironmentVariables["X"] = …; }) runs per resource start, with resolved values available.
  • What does a secret expression become in publish mode? — A parameter the target must supply — a Key Vault reference or Bicep secure parameter on Azure, a Compose .env entry, a Helm value — never a literal in the artifact.
  • Where does this bite people? — ToString() on an endpoint or parameter during the builder phase; it compiles and silently produces the wrong string.

Common wrong answer

"Interpolation works fine, I've done it." It appears to work when the value happens to be known (a literal parameter default), which is why the mistake survives to production and then emits a laptop URL into a Bicep file. The distinction between builder time and start time is the thing being tested.

seniorHow do you keep a 40-resource AppHost maintainable?

Answer

Treat it as production code, because it is. I split it into extension methods per bounded context — builder.AddCatalog(), builder.AddOrdering() — each returning the resources the rest of the model needs, so Program.cs reads as a table of contents. Shared conventions (tagging, standard health checks, telemetry env vars) become one extension method applied uniformly rather than copy-paste. Cross-cutting behaviour that must apply to every resource goes into an eventing subscriber, not into forty call sites. I keep mode branching in one place per resource and forbid it in helpers. And I write tests: DistributedApplicationTestingBuilder can assert on the model without starting anything, so "every project has a health check" and "no resource is missing WaitFor on its database" become unit tests.

Example

public static class CatalogModule
{
    public static IResourceBuilder<ProjectResource> AddCatalog(
        this IDistributedApplicationBuilder builder, IResourceBuilder<IResourceWithConnectionString> db)
    {
        return builder.AddProject<Projects.Catalog_Api>("catalog-api")
                      .WithReference(db).WaitFor(db)
                      .WithHttpHealthCheck("/health")
                      .WithStandardTelemetry();       // your own convention
    }
}

// Program.cs stays a table of contents:
var db = builder.AddPostgres("pg").AddDatabase("catalogdb");
var catalog = builder.AddCatalog(db);
var orders  = builder.AddOrdering(db, catalog);

Follow-ups

  • Would you split into multiple AppHosts? — Only along team-ownership lines where people genuinely never run the other half; the cost is losing cross-service traces in one dashboard. A sub-set alternative is one AppHost with launch profiles that start subsets.
  • How do developers run only part of it? — Launch profiles, or a parameter/environment switch guarding whole modules; since 13.2 aspire start/aspire stop also let you manage instances without restarting everything.
  • Who owns the AppHost in a multi-team repo? — Make it CODEOWNERS-owned by the platform team with per-module ownership delegated; otherwise it becomes an unreviewed merge-conflict magnet.

Common wrong answer

"Keep it all in Program.cs, it's just configuration." At forty resources that file is 800 lines, every team edits it, and every PR conflicts. Interviewers ask this specifically to see whether you apply normal engineering standards to infrastructure code.

seniorWhat is the single-file AppHost, and when would you use it?

Answer

Since 13.0, backed by .NET 10's file-based apps, an AppHost can be one apphost.cs with no .csproj: #:sdk Aspire.AppHost.Sdk@13.5.0 and #:package directives declare the SDK and integrations inline. It exists to lower the barrier — a sample, a demo, a repo that is mostly Python with two containers — and pairs with aspire init, which drops a single-file AppHost into an existing solution. I would use it for samples, spikes and polyglot repos where a .csproj would be noise; I would not use it for a real multi-team system, where you want MSBuild, Central Package Management, analyzers and tests around the model. Note the sharp edge: since 13.2 project-scoped configuration lives in aspire.config.json, and running a single-file AppHost through dotnet run apphost.cs rather than aspire run can miss the launch-profile environment it expects.

Example

#:sdk Aspire.AppHost.Sdk@13.5.0
#:package Aspire.Hosting.Redis@13.5.0

var builder = DistributedApplication.CreateBuilder(args);
var cache = builder.AddRedis("cache");
builder.AddJavaScriptApp("web", "../web", "dev").WithReference(cache);
builder.Build().Run();
// aspire run

Follow-ups

  • How do you graduate from single-file to a project? — aspire init/templates produce the project form; the C# body is unchanged, you move #:package lines to PackageReference.
  • What is aspire.config.json? — Rooted project-scoped configuration introduced in 13.2: AppHost discovery, SDK version, launch profiles and package pins in one file.
  • Is there a TypeScript equivalent? — Yes: apphost.mts with createBuilder(), preview in 13.2, GA in 13.4, with SDK modules generated under .aspire/modules/.

Common wrong answer

"It's the new default, projects are legacy." Both are supported and the project form is still what production repos use; calling the project form legacy suggests you read one release blog rather than shipping with it.

seniorThe TypeScript AppHost went GA in 13.4. What does that change architecturally?

Answer

It removes the "you must have a C# developer to own the topology" objection, which was the biggest blocker in polyglot orgs. An apphost.mts calls createBuilder() and the same resource API in camelCase (addRedis, withReference, waitFor), with integration SDKs generated into .aspire/modules/ by aspire restore. 13.3 closed the expression gap (withEnvironment handling endpoints, parameters and connection strings; endpoint.url/host/port), 13.4 declared GA, and 13.5 added addHealthCheck() and withContainerFiles(). Architecturally the consequence is that the AppHost can now live with the team that owns the frontend or the Python services, so I would still standardise on one language per repo — mixing them means two toolchains for one artifact — but I would no longer force C# on a Node-majority team.

Example

// apphost.mts
import { createBuilder } from "@aspire/hosting";

const builder = createBuilder();
const cache = builder.addRedis("cache");
const api = builder.addProject("api", "../Api/Api.csproj")
                   .withReference(cache)
                   .waitFor(cache);
builder.addJavaScriptApp("web", "../web", "dev")
       .withReference(api)
       .withExternalHttpEndpoints();
await builder.build().run();

Follow-ups

  • Is parity complete? — Close but not total; C# leads on new APIs and some Azure customisation still assumes Azure.Provisioning types. Check the release notes for the feature you need before committing a team.
  • What regenerates the typed modules? — aspire restore, after adding an integration; they live under .aspire/modules/ (moved there in 13.4 from .modules/).
  • Does a TS AppHost still need the .NET SDK? — For orchestrating .NET projects, yes — you are building them. For a pure Node/Python/Go stack you need the CLI, which 13.5 also ships on npm as @microsoft/aspire-cli.

Common wrong answer

"TypeScript AppHost means Aspire no longer needs .NET at all." The CLI and the orchestrator are still .NET-built; what changed is the language you author the model in. Overclaiming here gets punished immediately by "so how does it build my C# project, then?"

principalHow would you extend the app model for a resource type your company owns — say an internal feature-flag service?

Answer

I would ship an internal NuGet package with a hosting integration that mirrors the first-party shape, so it composes with everything else. That means a resource type implementing IResourceWithConnectionString (and IResourceWithEndpoints if it listens), an AddFeatureFlags(name) extension that registers the container or points at the managed instance depending on ExecutionContext, a health check so WaitFor is meaningful, and a ConnectionStringExpression built from ReferenceExpression so references work. Publish behaviour is contributed through pipeline steps (the 13.0 model that replaced IDistributedApplicationPublisher) rather than by writing manifests. And a matching client integration — AddFeatureFlagsClient — so the consuming side is one line too. The rule I apply: if a team has to write WithEnvironment by hand to use your service, the integration is not finished.

Example

public sealed class FeatureFlagsResource(string name)
    : ContainerResource(name), IResourceWithConnectionString
{
    internal EndpointReference Endpoint => new(this, "http");
    public ReferenceExpression ConnectionStringExpression =>
        ReferenceExpression.Create($"Endpoint={Endpoint.Property(EndpointProperty.Url)}");
}

public static IResourceBuilder<FeatureFlagsResource> AddFeatureFlags(
    this IDistributedApplicationBuilder builder, string name) =>
    builder.AddResource(new FeatureFlagsResource(name))
           .WithImage("contoso/flags", "3.2")
           .WithHttpEndpoint(targetPort: 8080, name: "http")
           .WithHttpHealthCheck("/healthz");

Follow-ups

  • How do you version it against Aspire's cadence? — Pin one Aspire minor per internal release, run the integration's own tests against the next minor in CI, and publish within a sprint of each Aspire release since only the newest is supported.
  • How do you avoid forty teams writing forty variants? — Own it centrally, review the public API like any library, and give it the same docs page as a first-party integration.
  • What if the resource has no container? — Model it as a value/external service resource with a connection string; not everything needs a process.

Common wrong answer

"Just call AddContainer and WithEnvironment in each AppHost." It works for one team and rots across ten — the image tag, health path and config keys drift, and nothing composes with WithReference. The point of the extension model is that consumers should never see the wiring.

03Integrations: hosting vs client

The hosting/client split is the most-asked factual question in Aspire loops, because it is a clean discriminator: people who have used Aspire answer it in ten seconds, people who read a blog post conflate the two. Beyond the definition, interviewers probe what an integration gives you for free (health checks, telemetry, resilience, keyed registration), how you configure it without an AppHost, and — at senior level — how you decide whether to use the Aspire client integration at all versus registering the SDK client yourself.

Docs: aspire.dev — Integrations overview

screenerWhat is the difference between a hosting integration and a client integration?

Answer

A hosting integration is referenced by the AppHost and adds a resource to the model — Aspire.Hosting.Redis gives you builder.AddRedis("cache"), which knows the image, the default port, the health check and how to build a connection string. A client integration is referenced by the service and configures the SDK client that talks to it — Aspire.StackExchange.Redis gives you builder.AddRedisClient("cache"), which reads ConnectionStrings:cache, registers IConnectionMultiplexer, and adds a health check, tracing, metrics and logging. The naming tells you which is which: Aspire.Hosting.* is always AppHost-side, everything else is app-side. The name string is the contract between them.

Example

// AppHost (Aspire.Hosting.Redis)
var cache = builder.AddRedis("cache");
builder.AddProject<Projects.Api>("api").WithReference(cache);

// Api service (Aspire.StackExchange.Redis)
builder.AddRedisClient("cache");     // reads ConnectionStrings:cache, injected by WithReference
// then: app.MapGet("/", (IConnectionMultiplexer mux) => …);

Follow-ups

  • Can you use one without the other? — Yes, both ways. A client integration works against any connection string, with no AppHost; a hosting integration is useful even if the consumer is Python.
  • What links them? — Only the resource name, which becomes the configuration key. Misspell it and you get a clear "no connection string named X" failure at startup.
  • Where do the docs list them? — Since 13.4 the CLI does too: aspire integration list and aspire integration search redis.

Common wrong answer

"They're the same package, one just runs in the AppHost." They are separate NuGet packages with separate versioning and different dependencies, and putting Aspire.Hosting.Redis in a service project (or the client package in the AppHost) is a real mistake people make on day one.

midWhat does a client integration give you beyond a connection string?

Answer

Four things, and naming all four is what makes the answer senior. It registers the SDK client with correct lifetimes and options bound from configuration. It adds a health check for that dependency so /health reflects reality. It wires OpenTelemetry — the SDK's ActivitySource and meters — so calls appear as spans in the dashboard without extra code. And it applies sensible defaults such as retry/timeout on HTTP-based clients. Each is individually disableable through the settings object, which matters because the defaults are opinionated: DisableHealthChecks, DisableTracing, DisableMetrics, and per-client retry knobs.

Example

builder.AddNpgsqlDataSource("catalogdb", settings =>
{
    settings.DisableHealthChecks = false;
    settings.DisableTracing = false;
    settings.CommandTimeout = 30;
});
{
  "Aspire": {
    "Npgsql": {
      "ConnectionString": "…",
      "DisableHealthChecks": false,
      "DisableTracing": false
    }
  }
}

Follow-ups

  • Where does the settings section live in config? — Under Aspire:<vendor>:<product>, e.g. Aspire:StackExchange:Redis, Aspire:Npgsql:EntityFrameworkCore:PostgreSQL — bindable per named connection too.
  • Do the health checks cost anything? — Yes: each one opens a connection on the health endpoint's cadence. On a service with eight dependencies, a naive /health becomes an expensive endpoint — separate liveness from readiness.
  • What about multiple instances of the same resource? — Use the keyed overloads (AddKeyedRedisClient("cache")) and inject with [FromKeyedServices("cache")].

Common wrong answer

"It's just a wrapper that reads the connection string." That undersells it and, worse, leads to the follow-up "so why is my health endpoint timing out?" — which you cannot answer if you did not know the integration registered health checks on your behalf.

midCan you use Aspire client integrations without an AppHost?

Answer

Yes, and it is a common incremental-adoption path. The client packages are ordinary libraries that read ConnectionStrings:<name> plus their Aspire:* settings section from whatever configuration providers you already use — appsettings, environment variables, Key Vault. So an existing service deployed to App Service can adopt AddRedisClient, get health checks and tracing, and never know Aspire exists. The reverse is also true: a hosting integration can front a Python or Go consumer that just reads the environment variables. Saying this out loud is a strong signal, because it shows you understand the coupling is configuration, not framework.

Example

// appsettings.Production.json in a service with no AppHost anywhere
{
  "ConnectionStrings": {
    "cache": "my-redis.redis.cache.windows.net:6380,ssl=true,password=…"
  },
  "Aspire": { "StackExchange": { "Redis": { "DisableTracing": false } } }
}

Follow-ups

  • Is ServiceDefaults usable standalone? — Yes; it is a project template, not a package, and it only wires Microsoft.Extensions.* libraries. Many teams adopt it first and the AppHost later.
  • Any downside to adopting clients only? — You take a dependency on Aspire's release cadence for those packages without getting the local-loop payoff; weigh it.

Common wrong answer

"No — client integrations need the AppHost to inject the connection string." The AppHost is one config source among many. This answer reveals a mental model where Aspire is a runtime, which is the failure mode unit 01 is about.

midHow do you connect to two Redis instances (or two databases) in one service?

Answer

Use the keyed variants. AddRedisClient("cache") registers IConnectionMultiplexer as the default; a second call would collide, so you use AddKeyedRedisClient("cache") and AddKeyedRedisClient("ratelimits") and resolve with [FromKeyedServices("ratelimits")]. The same pattern exists across the integrations — AddKeyedNpgsqlDataSource, AddKeyedAzureBlobClient, and so on. On the AppHost side nothing special is needed: two resources with distinct names, both referenced. Keyed DI is .NET 8+, so this is available everywhere Aspire runs.

Example

// AppHost
var cache  = builder.AddRedis("cache");
var limits = builder.AddRedis("ratelimits");
builder.AddProject<Projects.Api>("api").WithReference(cache).WithReference(limits);

// Service
builder.AddKeyedRedisClient("cache");
builder.AddKeyedRedisClient("ratelimits");

app.MapGet("/x", ([FromKeyedServices("ratelimits")] IConnectionMultiplexer limits) => …);

Follow-ups

  • What about EF Core DbContexts? — AddNpgsqlDbContext<CatalogContext>("catalogdb") is already keyed by the context type; two contexts against one database is normal, one context against two databases is not.
  • Does each keyed client get its own health check? — Yes, named after the connection, which is what makes a failing dependency identifiable in /health output.

Common wrong answer

"Call AddRedisClient twice with different names." The non-keyed overloads register the same service type, so the second registration wins silently and you spend an afternoon wondering why writes land in the wrong instance.

seniorWhen would you not use an Aspire client integration?

Answer

When you already have a hardened, opinionated registration of that client. Aspire's client integrations apply defaults, and if your platform already sets connection pool sizes, a custom retry policy, a specific SocketsHttpHandler lifetime, or a bespoke telemetry enrichment, you will spend more time turning defaults off than you save. The other cases: when the integration lags the SDK version you need (they track releases, but not instantly); when the vendor SDK has no Aspire integration and rolling your own registration is three lines; and when you are deliberately minimising dependency surface in a service that must be supportable for years without upgrading Aspire quarterly. The mature position is that the connection-string contract is the valuable part — you can keep that and register the client yourself.

Example

// Skip the integration, keep the contract: the name still comes from WithReference.
var cs = builder.Configuration.GetConnectionString("cache")
         ?? throw new InvalidOperationException("Missing ConnectionStrings:cache");

builder.Services.AddSingleton<IConnectionMultiplexer>(_ =>
{
    var options = ConfigurationOptions.Parse(cs);
    options.ConnectRetry = 5;                   // our standard, not Aspire's
    options.AbortOnConnectFail = false;
    return ConnectionMultiplexer.Connect(options);
});
builder.Services.AddHealthChecks().AddRedis(cs, name: "cache");

Follow-ups

  • What do you lose? — Automatic tracing/metrics registration and the health check; both are a line each to add back, so the loss is small and explicit.
  • How do you keep the team consistent? — Wrap your choice in your own extension method so the decision is made once, not per service.

Common wrong answer

"Always use the integration, it's the Aspire way." Framework loyalty over engineering judgment is the exact failure mode a senior loop screens for. The strong answer names what the integration actually buys and when that is not worth it.

seniorA hosting integration's default container image just changed under you. How do you handle that?

Answer

This is a live problem, not a hypothetical: 13.4 moved the default PostgreSQL image from 17.6 to 18.3 and RabbitMQ from 4.2 to 4.3, and a Postgres major bump does not read an old data volume — developers upgrade, the container crash-loops, and the loop is broken until someone deletes the volume. The disciplined answer: pin images explicitly for anything with persistent state (WithImageTag/WithImage), treat the pin as a deliberate upgrade with a migration note, and read the breaking-changes section of every Aspire release rather than only the feature list. For a shared repo I add a smoke job in CI that runs aspire run against a clean volume and against a restored volume snapshot, so the failure surfaces before forty developers hit it.

Example

var pg = builder.AddPostgres("pg")
                .WithImage("library/postgres", "17.6")   // pinned: our volumes are 17.x
                .WithDataVolume("catalog-pgdata")
                .WithLifetime(ContainerLifetime.Persistent);

Follow-ups

  • What is the recovery when it already happened? — docker volume rm the dev volume (data is disposable locally) or run pg_upgrade if someone kept real data there — which is itself a smell.
  • Should you pin every image? — Pin stateful ones and anything a test asserts against; leaving stateless dev containers floating keeps you current cheaply.
  • Where do you find these changes? — The release's breaking-changes page and the version change log on the microsoft/aspire wiki; they are separate from the what's-new post.

Common wrong answer

"Container images don't matter, it's just local dev." Until a developer's week disappears, or until the same integration's tag is what your publish pipeline emits for a Compose target. "It's only dev" is how a two-hour outage becomes a two-day one.

seniorHow do integrations handle telemetry, and what do you get in the dashboard for free?

Answer

Client integrations enable the underlying SDK's OpenTelemetry instrumentation — the ActivitySource and Meter names the vendor library already publishes — and ServiceDefaults' ConfigureOpenTelemetry exports them over OTLP to whatever OTEL_EXPORTER_OTLP_ENDPOINT points at, which the AppHost sets to the dashboard. The practical result is that an HTTP call from web → api → Postgres shows as one trace with three spans, without you writing instrumentation. What you do not get for free is business context: baggage, custom spans around domain operations, and useful span names for background work. At senior level I expect you to say that the dashboard is a local viewer with in-memory storage and retention limits, so it complements but never replaces a real backend.

Example

builder.Services.AddOpenTelemetry()
    .WithTracing(t => t.AddSource("Contoso.Ordering"))   // your own spans join the same trace
    .WithMetrics(m => m.AddMeter("Contoso.Ordering"));

// In domain code:
using var activity = OrderingTelemetry.Source.StartActivity("SubmitOrder");
activity?.SetTag("order.items", order.Items.Count);

Follow-ups

  • Which variables does the AppHost inject for telemetry? — OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_SERVICE_NAME, OTEL_RESOURCE_ATTRIBUTES and protocol/header settings; in production you point the same variables at your collector.
  • Do database spans include the SQL? — Only if the integration's settings enable it; capturing statement text is off or redacted by default for privacy, and turning it on is a deliberate decision.
  • Does the dashboard keep telemetry across restarts? — No, it is in memory with configurable limits; 13.2 added export/import of logs and telemetry as JSON in a zip so you can keep a snapshot.

Common wrong answer

"Aspire gives you full observability, so you don't need APM." The dashboard has no persistence, no alerting, no long-range queries and no RBAC beyond a token. Saying this in a senior loop suggests you have never been on call.

seniorHow do you audit and govern which integrations a large organisation uses?

Answer

Treat them like any dependency, with two Aspire-specific wrinkles. First, hosting integrations pull container images, so the image source is a supply-chain decision: point defaults at your internal registry (WithImageRegistry/WithImage) rather than Docker Hub, and mirror the tags you pin. Second, integrations are versioned in lockstep with Aspire and the support policy covers only the newest release, so a central version property plus Central Package Management is not optional at scale — you want one place to bump. Beyond that: an allowlist of blessed integrations with a documented owner, a template AppHost that new services copy, and a CI check that fails on unpinned tags or unknown package ids. I would also make aspire integration list output part of an inventory job so the platform team knows what is actually in use.

Example

<!-- Directory.Packages.props: one knob for the whole monorepo -->
<Project>
  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
    <AspireVersion>13.5.0</AspireVersion>
  </PropertyGroup>
  <ItemGroup>
    <PackageVersion Include="Aspire.Hosting.PostgreSQL" Version="$(AspireVersion)" />
    <PackageVersion Include="Aspire.Hosting.Redis" Version="$(AspireVersion)" />
    <PackageVersion Include="Aspire.StackExchange.Redis" Version="$(AspireVersion)" />
  </ItemGroup>
</Project>

Follow-ups

  • Do client and hosting packages have to match versions? — Not strictly, but keep them aligned; mismatches surface as missing APIs after an upgrade and are pure noise to debug.
  • Community integrations? — There is a healthy community ecosystem; allow them individually, with the same review you would give any third-party package, and note they are outside Microsoft's support policy.
  • How do you handle an integration your platform must fork? — Wrap rather than fork: your own AddContosoRedis calling the upstream one, so upstream upgrades stay cheap.

Common wrong answer

"Renovate/Dependabot handles it." Automated bumps handle versions, not policy: they will not stop a team pulling an unvetted image from Docker Hub into every developer's machine, and they will happily bump a Postgres major that eats dev volumes.

principalAn integration you depend on lacks a feature you need. Fork, wrap, or contribute?

Answer

Default to wrap, contribute in parallel, fork only as a time-boxed bridge. Wrapping works because the model is composable: almost anything an integration does can be adjusted afterwards with WithEnvironment, WithArgs, WithBindMount, WithImage, an eventing subscriber, or a publish-time callback — you rarely need the source. Contributing matters because Aspire is a fast-moving first-party repo (microsoft/aspire) that ships minors quarterly, so a merged PR usually lands within one release, which is faster than most internal forks get maintained. Forking is the worst option under a support policy where only the newest release is supported: you inherit a permanent merge burden on a codebase that changes every quarter. I would only fork when the gap blocks production and the upstream design conversation will clearly take longer than the deadline — and I would write the deletion ticket at the same time.

Example

// Wrap: keep upstream, add what we need in one place.
public static IResourceBuilder<PostgresServerResource> AddContosoPostgres(
    this IDistributedApplicationBuilder builder, string name) =>
    builder.AddPostgres(name)
           .WithImageRegistry("contoso.azurecr.io")      // our mirror
           .WithImage("library/postgres", "17.6")        // our pin
           .WithArgs("-c", "max_connections=300")        // our tuning
           .WithDataVolume($"{name}-data")
           .WithLifetime(ContainerLifetime.Persistent);

Follow-ups

  • What if the gap is in publish output, not the local resource? — Contribute a pipeline step or use the target's customisation hooks (ConfigureInfrastructure for Azure, chart values for Helm) before considering a fork.
  • How do you keep a wrapper honest? — A test that constructs the model and asserts the image, tag and args, so an upstream default change is caught at build time.
  • How do you decide it's worth upstreaming? — If more than one team would use it and it does not encode company policy, it belongs upstream.

Common wrong answer

"Fork it, we need control." It sounds decisive and is usually the most expensive option available — quarterly rebases against a repo with removed public APIs (lifecycle hooks, publishers) is a real cost people underestimate. Interviewers listen for whether you price maintenance, not just delivery.

04Service discovery and configuration injection

This is where interviewers check whether you can debug Aspire rather than only use it. The mechanism is deliberately boring — environment variables in a documented shape, resolved by a client-side library — and being able to recite the shape lets you diagnose "service unavailable" in thirty seconds. Expect a screener definition question, a mid-level "show me the variables", and at senior level the production question: what resolves names once the AppHost is gone.

Docs: aspire.dev — Service discovery

screenerHow does one Aspire service call another by name?

Answer

You register a typed or named HttpClient with a logical base address like https+http://catalog-api, and service discovery rewrites that scheme-and-name into a real address before the request goes out. The address comes from configuration: WithReference(catalog) in the AppHost injected services__catalog-api__https__0 into the caller's environment, and Microsoft.Extensions.ServiceDiscovery — enabled by AddServiceDiscovery() in ServiceDefaults — resolves it at request time. No proxy, no sidecar, no DNS trick locally: it is a DelegatingHandler doing configuration lookup.

Example

builder.Services.AddHttpClient<CatalogClient>(c =>
{
    c.BaseAddress = new Uri("https+http://catalog-api");
});
// ServiceDefaults already did: services.AddServiceDiscovery();
//   and ConfigureHttpClientDefaults(h => h.AddServiceDiscovery());

Follow-ups

  • What does the https+http scheme mean? — An ordered preference: use the https endpoint if one is configured, otherwise http. Locally that avoids a dev-cert dependency; in production you configure only https.
  • What if the name has no configuration? — The request fails fast with a resolution error naming the service, which is the error you want rather than a DNS timeout.
  • Does it work for non-HTTP protocols? — Resolution is generic (there are DNS and DNS SRV resolvers), but the ergonomic path is HttpClient; for gRPC you use the same handler under GrpcChannel via HttpClientFactory.

Common wrong answer

"Aspire runs a DNS server / registry that services query." There is no registry. Believing there is one leads to the wrong debugging move (looking for a discovery service) instead of the right one (printing the environment variables).

midWrite out the exact environment variables WithReference produces.

Answer

For an endpoint-bearing resource the shape is services__<resourceName>__<endpointKey>__<index>, with the double underscore being .NET's configuration-hierarchy separator so it binds to Services:name:endpoint:0. The endpoint key is the scheme (http, https) for endpoints named "http"/"https", and otherwise the endpoint's name. The resource name keeps the casing you wrote in the AppHost. For a connection-string resource you instead get ConnectionStrings__<name>. The index exists because a name can have multiple addresses. Being able to write this from memory is the difference between guessing and grepping when a call fails.

Example

# injected into "web" by .WithReference(api).WithReference(cache)
services__catalog-api__https__0=https://localhost:7241
services__catalog-api__http__0=http://localhost:5241
services__catalog-api__grpc__0=https://localhost:7295
ConnectionStrings__cache=localhost:54367
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:19001
OTEL_SERVICE_NAME=web

Follow-ups

  • How do you address a named endpoint from code? — https://_grpc.catalog-api; the leading underscore marks a named endpoint rather than a subdomain, mirroring DNS SRV convention.
  • How do you see them for a running resource? — The dashboard's resource details pane; 13.2 added exporting them as a .env file, which is the fastest way to reproduce a service's environment outside Aspire.
  • Why double underscores rather than colons? — Colons are not portable in environment variable names across shells and containers; .NET maps __ to :.

Common wrong answer

"Something like SERVICE_CATALOG_URL." Vague answers here are read as "never debugged it". The precise shape is the whole value of the question, and it is exactly what you grep for at 2am.

midWhat happens to service discovery in production, where there is no AppHost?

Answer

The same library resolves the same logical names from whatever configuration the platform supplies. On Azure Container Apps, the publish step writes the services__… values into each container app's environment pointing at the internal FQDNs. On Kubernetes the generated chart does the same, or you switch to the DNS/DNS SRV resolvers so names resolve through cluster DNS — Microsoft.Extensions.ServiceDiscovery.Dns exists precisely for that, and DNS SRV handles named ports on a Service. Nothing changes in your code: the HttpClient base address stays https+http://catalog-api. That invariance is the actual product benefit, and it is what the question is testing.

Example

// Optional in-cluster resolution instead of injected config
builder.Services.AddServiceDiscovery()
                .AddDnsSrvServiceEndpointProvider(o => o.QuerySuffix = ".default.svc.cluster.local");
// or plain configuration, from a ConfigMap
{ "Services": { "catalog-api": { "https": [ "https://catalog-api.internal:8443" ] } } }

Follow-ups

  • Which resolver wins when several are registered? — They are tried in registration order; configuration first is the usual arrangement so an override beats DNS.
  • Is there caching? — Yes, with refresh intervals; a stale endpoint after a scale event is the classic symptom, and the DNS resolvers honour TTL.
  • What about mTLS or auth between services? — Out of scope for service discovery; it resolves an address, nothing more. That is a mesh or gateway concern.

Common wrong answer

"You have to change the URLs to real ones before deploying." It is the answer of someone who never deployed an Aspire app, and it throws away the main reason to use logical names at all.

midA call between two services fails with "no endpoints found". Walk through your debugging.

Answer

Four checks, in order, and each takes seconds. One: is there a WithReference in the AppHost from caller to callee — the most common cause is a reference added to the wrong resource. Two: does the caller's environment actually contain services__<name>__… — read it in the dashboard's resource details, or export the .env. Three: does the name in the HttpClient base address exactly match the AppHost resource name, including case and hyphens. Four: is service discovery enabled on that client at all — AddServiceDefaults() wires ConfigureHttpClientDefaults, but a client created with new HttpClient() bypasses the factory entirely and therefore bypasses discovery. That fourth one catches most of the remaining cases.

Example

// Silent failure: no factory, no handler, no discovery.
var http = new HttpClient { BaseAddress = new Uri("https+http://catalog-api") };  // ✗

// Works: goes through IHttpClientFactory, which ServiceDefaults configured.
public class CatalogClient(HttpClient http) { … }
builder.Services.AddHttpClient<CatalogClient>(c => c.BaseAddress = new("https+http://catalog-api"));

Follow-ups

  • How would you catch this in review? — Ban raw new HttpClient() with an analyzer or a code-review convention; it is also a socket-exhaustion smell independent of Aspire.
  • What if the endpoint exists but returns 502? — Then discovery worked and the problem is the callee: check its health and its logs, not the wiring.
  • What if it works locally and fails in ACA? — Compare the injected variables in the deployed revision; usually a missing WithExternalHttpEndpoints or an internal-only ingress.

Common wrong answer

"Restart the AppHost." Sometimes it helps, which is why it is the answer people give — but it teaches nothing and hides a missing reference that will fail in CI too. Interviewers are grading the method, not the fix.

seniorHow do you consume an external, non-Aspire service the same way?

Answer

Two options, and the choice signals maturity. If it is just a URL, model it with AddExternalService("payments", "https://api.stripe.com") (9.5+) and reference it — it appears in the dashboard, can carry a health check, and its URL becomes a parameter rather than a hard-coded constant, so staging and production differ by configuration. If it is a datastore-shaped dependency, AddConnectionString("legacy-crm") pulls the value from configuration or user secrets and injects it exactly like a modelled resource. Either way the consuming code is unchanged — logical name in, discovery out — which is what lets you migrate that dependency into the model later without touching services.

Example

var payments = builder.AddExternalService("payments", builder.AddParameter("payments-url"));
var crm      = builder.AddConnectionString("legacy-crm");   // from user secrets / env

builder.AddProject<Projects.Orders>("orders")
       .WithReference(payments)
       .WithReference(crm);

Follow-ups

  • Why bother modelling something you do not run? — Visibility and uniformity: it shows in the graph, it is one place to change per environment, and health status tells you whether an outage is yours.
  • Does the external service get health checks? — You can attach an HTTP health check; be careful not to hammer a third party's endpoint from every developer's laptop.
  • What replaced PublishAsConnectionString? — AddConnectionString; the old method is obsolete as of 13.5.

Common wrong answer

"Just put the URL in appsettings, it's outside Aspire." It works and it is what most teams do first — but it puts one dependency outside the graph, so the dashboard lies about the system's shape and the URL drifts per environment in a second place.

seniorAspire's service discovery is client-side. What are the consequences?

Answer

Client-side means resolution happens in the calling process, so there is no extra hop, no sidecar memory cost and no proxy to operate — but also no central place to enforce policy. Load balancing is whatever the client does across the resolved list (round-robin at best), there is no circuit breaking except what AddStandardResilienceHandler gives you per client, no traffic shifting for canaries, no mTLS, and no server-side authorization on who may call whom. In production this usually means the platform still provides those: ACA's ingress and Dapr, or a Kubernetes mesh. My framing in an interview: Aspire's discovery is a developer-experience feature that also happens to work in production; it is not a traffic-management layer, and pretending otherwise is how teams end up with no circuit breakers.

Example

// The resilience you get is per-client and in-process, not platform-wide.
builder.Services.ConfigureHttpClientDefaults(http =>
{
    http.AddStandardResilienceHandler(o =>
    {
        o.Retry.MaxRetryAttempts = 3;
        o.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(30);
        o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(10);
    });
});

Follow-ups

  • How would you do a canary? — At the platform layer (ACA revisions with traffic weights, a mesh, a gateway), not through service discovery configuration.
  • Is round-robin enough? — For homogeneous replicas behind a platform load balancer, usually yes; the platform address is normally a single service DNS name anyway.
  • Retry safety? — The standard handler retries on transient failures; make sure the endpoints are idempotent or the retries are scoped, which is a design conversation, not a config one.

Common wrong answer

"It handles load balancing and failover for you." It resolves a list and picks from it. Claiming failover invites "what happens to in-flight requests when an instance dies", and the answer is: exactly what your resilience handler does, which you must have configured.

principalWould you keep Aspire's service discovery in a large production estate, or standardise on the platform's?

Answer

I would keep the abstraction and let the platform provide the values. The abstraction — code refers to https+http://catalog-api and never to a hostname — is worth keeping regardless of runtime, because it decouples services from topology and makes local, CI, staging and production identical in code. What I would not do is let each environment invent its own resolver stack: I would pick one mechanism per platform (injected configuration on ACA, DNS/DNS SRV in Kubernetes), make it part of the golden ServiceDefaults, and forbid ad-hoc Services: overrides in appsettings except for local diagnostics. The trade-off I would name unprompted is testability versus transparency: logical names are one indirection when someone tcpdumps a call, so the resolved endpoint must appear in logs and in the trace's server.address attribute.

Example

// Golden ServiceDefaults: one resolver strategy per platform, chosen by config.
var sd = builder.Services.AddServiceDiscovery();
if (builder.Configuration.GetValue<bool>("Platform:UseDnsSrv"))
    sd.AddDnsSrvServiceEndpointProvider();
else
    sd.AddConfigurationServiceEndpointProvider();

Follow-ups

  • How do you keep 60 services on the same ServiceDefaults? — Ship it as an internal NuGet package rather than a copied template project; the template is fine for one repo, fatal across sixty.
  • What breaks when a service is renamed? — Every caller's configuration key. Treat resource names as a public contract with a deprecation path, aliasing both names during migration.
  • Would you expose the resolved address in telemetry? — Yes; without it, "which instance served this" is unanswerable, and that is a genuine cost of the indirection.

Common wrong answer

"Standardise on the mesh and drop Aspire's discovery entirely." Defensible for the runtime, but it usually means services go back to hostnames in appsettings, and the local loop regresses to per-developer overrides. The nuance is that you can keep the client-side abstraction while the mesh does traffic management — they are not competing.

05Observability, OpenTelemetry and the dashboard

Aspire's observability story is the part most likely to come up in an SRE-flavoured loop, and the part candidates most often overclaim. What is being tested: do you know that ServiceDefaults is just OpenTelemetry wired up, can you say what the dashboard is and is not, and can you take the same telemetry to a real backend. At principal level the question becomes governance — what a standard telemetry contract looks like across dozens of services, and what it costs.

Docs: aspire.dev — Telemetry: OpenTelemetry logs, traces and metrics

screenerWhat is the ServiceDefaults project and what does it configure?

Answer

It is a class library the templates generate, referenced by every service, exposing AddServiceDefaults() and MapDefaultEndpoints(). It configures four things: OpenTelemetry (logging with formatted messages and scopes, ASP.NET Core and HttpClient and runtime instrumentation, OTLP export), default health checks, service discovery, and HttpClient defaults with the standard resilience handler. It is deliberately source, not a package, so you can edit it — and editing it is expected: most teams add their own ActivitySources, resource attributes and exporters. It is also the piece that runs in production, so it is the highest-leverage file in an Aspire solution.

Example

// Program.cs of every service
var builder = WebApplication.CreateBuilder(args);
builder.AddServiceDefaults();          // ← telemetry, health, discovery, resilience

var app = builder.Build();
app.MapDefaultEndpoints();             // ← /health and /alive
app.Run();

Follow-ups

  • Why is MapDefaultEndpoints separate? — Because mapping endpoints needs the built app, and because the template guards it: by default the health endpoints are only mapped in Development.
  • Is ServiceDefaults a NuGet package? — No, a generated project. At scale, converting it into an internal package is the standard move so sixty services do not drift.
  • Does it depend on Aspire? — Only on Microsoft.Extensions.* and OpenTelemetry packages; it runs fine with no AppHost.

Common wrong answer

"It's Aspire's runtime library that connects services to the AppHost." There is no connection to the AppHost; it reads environment variables the AppHost happens to set. Getting this wrong usually pairs with thinking the AppHost runs in production.

screenerWhat is the Aspire dashboard, and how does telemetry reach it?

Answer

It is a Blazor app that the AppHost starts alongside your resources. It shows the resource graph with state and health, streams console logs, and hosts an OTLP endpoint — the AppHost sets OTEL_EXPORTER_OTLP_ENDPOINT in every resource so structured logs, traces and metrics arrive there over gRPC or HTTP and are stored in memory with configurable retention limits. It also exposes resource commands (start, stop, restart, and any custom ones you declare) and, since 13.5, an interactive terminal for resources marked WithTerminal(). It ships as a standalone container image too — mcr.microsoft.com/dotnet/aspire-dashboard — so you can use it as a lightweight OTLP viewer for anything, Aspire or not.

Example

docker run --rm -p 18888:18888 -p 4317:18889 -d \
  --name aspire-dashboard \
  mcr.microsoft.com/dotnet/aspire-dashboard:13.5
# point any OTLP exporter at http://localhost:4317, open http://localhost:18888

Follow-ups

  • Where is the data stored? — In memory in the dashboard process, bounded by telemetry limits; restarting it loses everything. 13.2 added export/import of a telemetry snapshot as JSON in a zip.
  • How is it authenticated locally? — A browser token in the launch URL; the standalone container can use that token mode or OpenID Connect, configured through Dashboard:Frontend:AuthMode.
  • What changed in 13.5? — A refreshed, officially branded UI, better telemetry filtering (timestamp search, numeric ==/!= operators) and the terminal view.

Common wrong answer

"It's like Application Insights for local dev, it persists your traces." No persistence, no alerting, no query language, and limits that silently drop the oldest data. The consequence matters: you cannot investigate this morning's incident in the dashboard this afternoon.

midHow do you send Aspire's telemetry to a real backend?

Answer

Nothing Aspire-specific — it is standard OpenTelemetry. You either point OTEL_EXPORTER_OTLP_ENDPOINT at an OTel Collector or a vendor's OTLP endpoint (adding OTEL_EXPORTER_OTLP_HEADERS for an API key), or you add a vendor exporter in ServiceDefaults, such as AddAzureMonitorExporter. The recommended shape at scale is a collector per cluster: services always export OTLP to localhost/in-cluster collector, and routing, sampling and vendor lock-in stay in the collector's config rather than in sixty Program.cs files. Locally the AppHost overrides the endpoint to the dashboard, so the same code works both places.

Example

// ServiceDefaults: OTLP if configured, plus a vendor exporter when the key is present.
if (!string.IsNullOrEmpty(builder.Configuration["OTEL_EXPORTER_OTLP_ENDPOINT"]))
    builder.Services.AddOpenTelemetry().UseOtlpExporter();

if (!string.IsNullOrEmpty(builder.Configuration["APPLICATIONINSIGHTS_CONNECTION_STRING"]))
    builder.Services.AddOpenTelemetry().UseAzureMonitor();

Follow-ups

  • Can you export to the dashboard and a backend at once? — Yes, multiple exporters or a collector fan-out; useful in staging.
  • What about sampling? — Configure it in the SDK (OTEL_TRACES_SAMPLER) or the collector. Aspire's defaults sample everything, which is correct locally and ruinous in production.
  • What sets the service name? — OTEL_SERVICE_NAME, which the AppHost sets to the resource name; keep the same convention in production so dashboards match.

Common wrong answer

"You export from the dashboard to your backend." The dashboard is a sink, not a relay in that direction — it receives OTLP, it does not forward it to Application Insights. Services export to whatever endpoint they are told about; the dashboard is one possible destination.

midWhy do your logs appear in the console but not in the dashboard's structured logs view (or vice versa)?

Answer

Because they arrive by two different paths. Console output is captured by the orchestrator from the process's stdout/stderr and shown in the console-logs view. Structured logs arrive over OTLP through the OpenTelemetry logging provider, with severity, scopes and attributes, and appear in the structured view where you can filter by field. A resource that writes to stdout but has no OTLP exporter — a bare container, a Python script without instrumentation — will only show console logs; a .NET service whose AddServiceDefaults() is missing or whose OTLP endpoint is unset shows the same symptom. The fix is usually one of: call AddServiceDefaults, check OTEL_EXPORTER_OTLP_ENDPOINT is present in that resource's environment, or accept that a third-party container will only ever give you console output.

Example

builder.Logging.AddOpenTelemetry(o =>
{
    o.IncludeFormattedMessage = true;   // otherwise the message body is empty in the viewer
    o.IncludeScopes = true;
});

Follow-ups

  • Why would a message body be blank in structured logs? — IncludeFormattedMessage = false; you see the template and attributes but no rendered text. The template sets it to true for exactly this reason.
  • Can a container send OTLP? — Yes if the image supports it; the AppHost injects the endpoint into every resource, so an instrumented image works with no extra config.
  • Where does the trace id come from? — W3C traceparent propagation via HttpClient instrumentation; a hand-rolled client that drops the header breaks the trace, and the dashboard shows two disconnected traces.

Common wrong answer

"The dashboard scrapes the logs from the console into structured logs." Two separate pipelines, and conflating them makes the fix unfindable — people go looking for a parsing setting that does not exist instead of checking the exporter.

seniorWould you deploy the Aspire dashboard to production? Defend it.

Answer

To a non-production or internal environment, sometimes — it is genuinely useful in staging and for a small internal system with no APM budget, and ACA publishing includes it by default. To production for a real system, no, and for concrete reasons: telemetry lives in memory so it disappears on restart and is capped; there is no alerting, no long-range query, no per-team RBAC beyond an auth mode; and the resource view exposes environment variables, which for many resources includes credentials. If it is deployed at all it must sit behind authentication (Dashboard:Frontend:AuthMode set to OIDC, never Unsecured), on a private network, with the OTLP endpoint API-key protected. My default recommendation is: real backend for production, dashboard for local and staging.

Example

# Standalone dashboard, hardened
Dashboard__Frontend__AuthMode=OpenIdConnect
Dashboard__Otlp__AuthMode=ApiKey
Dashboard__Otlp__PrimaryApiKey=…
Dashboard__TelemetryLimits__MaxLogCount=50000
# never: Dashboard__Frontend__AuthMode=Unsecured on a routable address

Follow-ups

  • What is the single biggest risk? — Environment variables and connection strings visible to anyone who reaches the URL. Treat the dashboard as an admin console, not a status page.
  • How would you scale it? — You would not; it is single-instance and in-memory by design. That is the honest reason it is not a production APM.
  • Any middle ground? — Deploy it in staging, and use the 13.2 telemetry export to attach a snapshot to a bug report.

Common wrong answer

"Yes, it's free observability." It is free until it exposes secrets to whoever finds the URL, or until an incident review needs data from six hours ago that no longer exists. The interviewer is testing risk awareness, not enthusiasm.

seniorA trace stops at a service boundary. How do you diagnose it?

Answer

Broken propagation, almost always. I check in this order: is the caller using an HttpClient from the factory (a raw new HttpClient() has no instrumentation handler, so no traceparent header); is the callee's ASP.NET Core instrumentation registered (missing AddServiceDefaults, or a filter excluding the path); is there a queue or a background job in between, where context must be propagated manually through message headers and re-attached with a link or a parent context; and is a proxy stripping headers. For messaging the correct pattern is to inject the W3C context into the message on publish and extract it on consume, creating a span with the remote context as parent or as a link — Aspire's messaging integrations do this for you, hand-rolled publishers do not.

Example

// Manual propagation across a queue
var props = new Dictionary<string, string>();
Propagators.DefaultTextMapPropagator.Inject(
    new PropagationContext(Activity.Current!.Context, Baggage.Current),
    props, (d, k, v) => d[k] = v);

// consumer side
var parent = Propagators.DefaultTextMapPropagator.Extract(default, props, (d, k) => new[] { d[k] });
using var activity = Source.StartActivity("process-order", ActivityKind.Consumer, parent.ActivityContext);

Follow-ups

  • What about a background IHostedService? — It has no ambient activity; start a root span per iteration or you get orphan logs with no trace id.
  • How do you spot it in the dashboard? — Two traces with the same wall-clock window and no parent; the structured logs view filtered by trace id shows the break point.
  • Does sampling cause this? — It can look identical if the sampler drops the child; check the sampler before blaming propagation.

Common wrong answer

"Aspire handles propagation automatically, so it must be a dashboard bug." Automatic propagation covers instrumented HTTP and the supported messaging integrations — not your custom publisher, your background worker, or your raw HttpClient. Blaming the tool is the answer that ends the section.

seniorWhat telemetry standard would you enforce across an estate, and how?

Answer

A single internal ServiceDefaults package (not a copied template) that fixes: resource attributes (service.name, service.version, deployment.environment, team and cost-centre tags), the semantic-convention-compliant span attributes we require, a sampling policy configurable per environment, log severity mapping, and one exporter path — OTLP to a collector, never a vendor SDK per service. On top I would define a small set of RED/USE metrics every service must emit and wire them into a template dashboard, so a new service is observable on day one without anyone designing charts. Enforcement is a build-time check (the package version is centrally managed and a CI rule fails a service that does not call AddServiceDefaults) plus a runtime check: the collector rejects or flags spans missing required attributes.

Example

builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r
        .AddService(serviceName: builder.Environment.ApplicationName,
                    serviceVersion: ThisAssembly.InformationalVersion)
        .AddAttributes(new Dictionary<string, object>
        {
            ["deployment.environment"] = builder.Environment.EnvironmentName,
            ["contoso.team"] = builder.Configuration["Contoso:Team"] ?? "unknown",
        }));

Follow-ups

  • What does this cost? — Telemetry volume is a real bill; sampling and attribute cardinality are the two knobs, and high-cardinality tags (user ids, order ids) on metrics are the classic budget killer.
  • How do you migrate sixty services onto it? — Ship the package, land it via automated PRs, and delete the local ServiceDefaults project as the last step so nothing is half-migrated.
  • Does the local dashboard still work with a collector in front? — Yes; locally the AppHost points the endpoint at the dashboard, so the collector is a production-only hop.

Common wrong answer

"Let each team configure their own exporters." You get sixty conventions, unjoinable traces and no cost control. The template's editability is a feature for one repo and a liability across an estate — which is the insight the question is looking for.

principalThe dashboard's telemetry limits are dropping data during a load test. What do you do?

Answer

First, recognise the category error: the dashboard is an in-memory developer viewer, and a load test is a production-grade telemetry workload. The tactical fixes are to raise Dashboard:TelemetryLimits (max log/trace/metric counts and attribute lengths) and to sample aggressively at the source so you keep a representative slice rather than the last thirty seconds. The right fix is to stop using the dashboard for this: run the load test against a real collector with a backend that persists, and keep the dashboard for the interactive part. I would also use this as evidence in the standing argument that load-test observability and production observability should use the same pipeline — if you cannot analyse a load test with your production tooling, you cannot analyse an incident with it either.

Example

Dashboard__TelemetryLimits__MaxLogCount=100000
Dashboard__TelemetryLimits__MaxTraceCount=50000
Dashboard__TelemetryLimits__MaxAttributeLength=2048
# and at the source, so you keep a representative sample rather than a tail:
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.05

Follow-ups

  • What is the memory consequence of raising limits? — Linear growth in the dashboard process; on a laptop it competes with the containers you are testing, which distorts the very measurement you are taking.
  • How do you keep evidence from a run? — 13.2's telemetry export writes a JSON-in-zip snapshot you can attach to a ticket or re-import later.
  • Would you tail-sample? — Yes, in the collector: keep all errors and slow traces, sample the rest. That cannot be done in the dashboard.

Common wrong answer

"Increase the limits and re-run." It is the first thing to try and the wrong thing to conclude with — it treats a design boundary as a configuration bug, and at principal level the expected answer is to move the workload to the right tool.

06The local loop: DCP and the CLI

This sub-area separates users from operators. Every Aspire developer eventually hits "it won't start", and the interviewer wants to see a systematic response rather than "delete bin and obj". You need to know what DCP is, what the CLI can do (it grew enormously across 13.x), how container lifetime and volumes work, and how to make a large graph start quickly. Principal-level probing goes to developer-experience economics: what a slow local loop costs a team of forty.

Docs: aspire.dev — Aspire CLI reference

midWhat is DCP, and what happens when you run aspire run?

Answer

DCP — the Developer Control Plane — is the component that actually executes the model locally. The AppHost builds the resource graph, then hands it to DCP, which starts processes for projects and executables, talks to Docker or Podman for containers, allocates host ports, injects the computed environment (connection strings, service discovery, OTLP endpoint) into each one, and reports state back so the dashboard can show it. It is a separate, closed-source, per-RID component delivered through Aspire.Hosting.Orchestration.<rid> packages. The sequence: build → model → DCP starts the dashboard → resources start in dependency order with WaitFor gates honoured → endpoints allocated → environment injected → your browser opens on the dashboard.

Example

aspire run                      # build + orchestrate + open the dashboard
aspire run --detach             # 13.2: run in the background
aspire ps                       # 13.2: list running apphost instances
aspire stop                     # 13.2 (--force added in 13.5)
aspire doctor                   # environment diagnostics; 13.5 adds DCP health checks

Follow-ups

  • Is DCP open source? — No; Aspire itself is MIT on GitHub, but DCP ships as binaries. Worth knowing if your org has source-availability requirements.
  • Does DCP run in production? — Never. It is dev-loop only.
  • What does aspire doctor check? — SDK and CLI versions and installs, OS details, container runtime, and since 13.5 DCP health — it is the first command to run on a broken machine.

Common wrong answer

"The AppHost starts the containers directly with the Docker API." The indirection matters: DCP is why the same model can start a process, a container and an executable uniformly, and why the failure messages you see come from DCP rather than Docker. Candidates who do not know DCP exists cannot read its errors.

midHow do container lifetime and data volumes work locally?

Answer

By default containers are session-scoped: they are created on aspire run and destroyed on shutdown, so every run is clean and every run pays the startup cost. WithLifetime(ContainerLifetime.Persistent) (9.0+) keeps the container across runs, which turns a 20-second Postgres start into an instant reconnect — the single biggest local-loop speedup in most solutions. Data is separate: WithDataVolume() creates a named Docker volume that survives even session containers, and WithDataBindMount(path) maps a host folder, which is slower on macOS/Windows but lets you inspect files. The trade-off to state explicitly: persistence makes the loop fast and makes "works on my machine" possible, so a documented reset command matters.

Example

var pg = builder.AddPostgres("pg")
                .WithLifetime(ContainerLifetime.Persistent)   // survives aspire run/stop
                .WithDataVolume("catalog-pgdata")             // survives even without that
                .WithPgAdmin();                               // dev-only companion container

Follow-ups

  • How do you reset? — Remove the named volume (docker volume rm catalog-pgdata); make it a documented script, because "delete everything Docker" is what people do otherwise.
  • Bind mount or volume? — Volume by default (faster, isolated); bind mount when you need to read the files or seed from the repo.
  • Do persistent containers get reused across different AppHosts? — They are keyed by a name derived from the resource; two solutions using the same name will share, which is occasionally a nasty surprise.
  • Project/executable lifetimes? — 13.4 added experimental WithPersistentLifetime()/WithSessionLifetime() for those too.

Common wrong answer

"Volumes persist, containers don't, that's all there is." It misses that persistent containers are the actual performance lever, and that data outliving a schema change is the most common source of a corrupted local environment. Both halves matter.

midA developer says "aspire run hangs / a resource never becomes healthy". How do you triage?

Answer

Start at the dashboard, because it names the blocking resource: since 13.4 the dependency-waiting state is shown explicitly, so you can see that api is Waiting on pg. Then read that resource's console logs — a crash-looping Postgres almost always says why (incompatible data directory after an image bump, port in use, out of disk). If there are no logs, the container never started: check the container runtime is up, the image pulled, and the platform matches (an amd64-only image on arm64 is a slow, confusing failure). If it starts but stays unhealthy, the health check is wrong — wrong path, wrong port, TLS mismatch. Then aspire doctor for environment problems and, as the last resort, remove the data volume. The discipline being tested is reading the graph rather than guessing.

Example

aspire doctor                          # SDK, CLI, container runtime, DCP
docker ps -a                           # did the container start at all?
docker logs <container>                # why did it exit?
aspire logs --search "FATAL"           # 13.4: search across resources
docker volume rm catalog-pgdata        # last resort after an image major bump

Follow-ups

  • Ports already in use? — Something pinned a host port, or a persistent container from another solution is holding it; unpin, or stop the other instance with aspire ps/aspire stop.
  • Everything is slow the first time? — Image pulls. Pre-pull in onboarding, or mirror to an internal registry to avoid Docker Hub rate limits across a team.
  • Only on one machine? — Architecture (arm64 Macs), a corporate proxy blocking the registry, or a container runtime with too little memory allocated.

Common wrong answer

"Delete bin/obj and restart." It occasionally works, which is why it persists, and it teaches the team nothing — the same developer files the same ticket next week. Interviewers grade the sequence, and "read the dashboard first" is the sequence.

midHow do you debug a single service while the rest of the graph runs?

Answer

Because projects run as local processes, an IDE that understands Aspire attaches to all of them at F5 — that is the point of not containerising projects locally. For a service you want to run outside the graph (a different branch, a profiler, a rewrite in another language), the trick is to take its environment with it: export the resource's environment as a .env file from the dashboard (13.2) and run the service yourself with those variables, so it still resolves the same dependencies. The converse case — the rest of the graph must talk to your locally-run copy — is handled by pinning that resource's endpoint to a fixed port so the injected discovery values match. Since 13.2 you can also aspire run --detach and manage instances with aspire ps/aspire stop, so the graph is not tied to a terminal window.

Example

# 1. run everything in the background
aspire run --detach
# 2. export the api's environment from the dashboard → .env
# 3. run your own copy with the same wiring
dotnet run --project ./src/Catalog.Api    # with the exported env loaded

Follow-ups

  • Can you exclude a resource from starting? — Guard it in the AppHost behind a parameter or launch profile; there is no supported "skip this one" flag, and 13.4 removed aspire exec.
  • What about hot reload? — Works for projects run as processes; a containerised project loses it, which is one reason not to containerise locally.
  • Remote debugging a container? — Possible but painful; 13.5's WithTerminal() at least gives you an in-dashboard shell into the container for inspection.

Common wrong answer

"You can't — everything runs inside Aspire." Nothing is trapped: every resource is a process or a container with a knowable environment, and the whole point of exporting .env is that you can reproduce it. This answer signals someone who has only pressed F5.

seniorThe local loop takes four minutes to start. What do you actually change?

Answer

Measure first — the dashboard shows per-resource start times, so you know whether it is image pulls, container boot, migrations or WaitFor chains. Then, in rough order of payoff: make stateful containers ContainerLifetime.Persistent so they are started once a week rather than ten times a day; remove WaitFor edges that are not genuinely required, since each one serialises the graph; mirror images to an internal registry and pre-pull during onboarding; move seeding out of the critical path (seed once into a persistent volume rather than on every start); and split the AppHost so a developer starts the four resources their task needs rather than all twenty-two, via launch profiles. If it is still slow, the honest answer may be that the system is too big for one machine and the team needs shared dev infrastructure for the heavy dependencies, referenced with AddConnectionString.

Example

// Seed once into a persistent volume instead of on every run.
var pg = builder.AddPostgres("pg")
                .WithLifetime(ContainerLifetime.Persistent)
                .WithDataVolume("catalog-pgdata");

var seed = builder.AddProject<Projects.Seeder>("seed")
                  .WithReference(pg).WaitFor(pg)
                  .WithExplicitStart();      // run on demand from the dashboard, not every boot

Follow-ups

  • What is the cost of persistent containers? — Stale state; pair it with a documented reset script and a CI job that runs clean.
  • How do you quantify the win? — Startups per developer per day × seconds saved. Forty developers × ten starts × ninety seconds is fifteen hours a day; that is how you get the work prioritised.
  • Does --detach help? — It removes restart-for-a-rebuild in some workflows and keeps the graph warm between tasks.

Common wrong answer

"Buy faster laptops." Sometimes true, never sufficient, and it skips the measurement step. The specific levers — persistent lifetime, fewer wait edges, pre-pulled images, subset profiles — are what the question is fishing for.

seniorWhat are resource commands, and what would you use them for?

Answer

Resource commands (9.0+) put buttons on a resource in the dashboard and expose the same actions to the CLI. Built-ins are start, stop and restart; you add your own with WithCommand. They are the right home for the scripts that otherwise live in a README: reset the database, reseed demo data, clear the cache, rotate a test token, run a one-off import. In 13.3 commands gained structured results — text, JSON or Markdown surfaced in the dashboard's notification centre, the CLI and MCP tools — and 13.4/13.5 added typed arguments through CommandOptions.Arguments with InteractionInput, so a command can prompt for a value. That turns the dashboard into a small, discoverable operator console for the dev environment, which is a real onboarding win.

Example

var db = builder.AddPostgres("pg").AddDatabase("catalogdb");

db.WithCommand(
    name: "reseed",
    displayName: "Reseed demo data",
    executeCommand: async ctx =>
    {
        await Seeder.RunAsync(ctx.ServiceProvider, ctx.CancellationToken);
        return CommandResults.Success();
    },
    commandOptions: new CommandOptions { IconName = "DatabaseLightning" });

Follow-ups

  • Can a command be dangerous? — Yes, and it is one click away in a shared environment; gate destructive commands behind a confirmation input and never ship them to a deployed dashboard.
  • Can the CLI run them? — Yes: aspire resource <name> --help (13.4) lists resource-specific commands.
  • How do they relate to aspire exec? — aspire exec was removed in 13.4; modelled commands (and 13.5's WithTerminal()) are the supported replacements.

Common wrong answer

"They're just the start/stop buttons." Missing the custom-command extension point means missing the cleanest place to put team scripts — and the answer stays at "we keep a scripts/ folder nobody runs", which is the problem the feature solves.

seniorHow does the Aspire CLI relate to the IDE, and does it matter which one the team uses?

Answer

The CLI is the ground truth and the IDEs are clients of the same model. That matters because a team split across Visual Studio, Rider and VS Code needs one reproducible command in CI and in onboarding docs, and aspire run is it. The CLI has grown into the primary surface across 13.x: init, new, ls, add/integration search, run --detach, ps, start/stop, logs --search, otel --search, publish, deploy, destroy, do, doctor, update and agent. Distribution improved too: 13.5 ships it on npm as @microsoft/aspire-cli and on Nix, and new C# projects get a CLI bundle by default (AspireUseCliBundle=true) so the version is pinned with the repo rather than per machine. My rule: document the CLI, let people use whichever IDE they like, and pin the CLI version in the repo.

Example

npm i -g @microsoft/aspire-cli      # 13.5: no .NET SDK install step needed for the CLI
aspire --version
aspire update --self                # update the CLI in place
aspire update --migrate             # 13.5: migrate the repo's Aspire packages

Follow-ups

  • How do you pin the CLI per repo? — The CLI bundle plus aspire.config.json, so CI and laptops resolve the same version.
  • Do the IDEs add anything real? — Debugger attach across the graph, and the VS Code Aspire extension for integration management and deployment; the model and the commands are identical.
  • What about CI? — Use the CLI; there is no IDE in CI, and aspire publish is what the pipeline calls.

Common wrong answer

"Visual Studio is required for Aspire." It was closer to true in the 8.x workload era and has been false for years; saying it dates you by two major versions and rules out Linux and Mac developers who are perfectly well served.

principalHalf the team is on Podman, corporate laptops block Docker Desktop, and CI has no container runtime. What now?

Answer

Separate the three problems. Podman is supported — Aspire talks to a container runtime, not Docker specifically — so the work is making rootless Podman's socket and networking behave identically, pinning that in the onboarding script, and testing it in CI so it does not silently rot. The blocked-Docker-Desktop case is a licensing and policy problem, not a technical one: either the org licenses it, or the team standardises on Podman/Rancher Desktop, or the heavy dependencies move to shared dev infrastructure referenced by connection string, which degrades the loop but keeps people working. CI without a runtime means integration tests that need containers cannot run there, so I would either use a runner image that has one (most hosted runners do) or split the suite: model-level and unit tests everywhere, container-backed integration tests on a capable runner. What I would not do is let three different local setups exist undocumented — that is how "works on my machine" becomes structural.

Example

# pin the runtime per machine, and assert it in onboarding
export DOCKER_HOST=unix:///run/user/$(id -u)/podman/podman.sock
aspire doctor        # verifies SDK, CLI, runtime and DCP in one shot

Follow-ups

  • Are all integrations Podman-clean? — Mostly; the usual friction is rootless port binding below 1024 and host-gateway networking. Test the specific images your team uses rather than assuming.
  • What is the fallback if containers are impossible? — Point client integrations at shared services via AddConnectionString; you lose isolation and gain a shared-state failure mode, so it is a last resort.
  • How do you keep it from regressing? — A scheduled CI job that runs aspire run on both runtimes and fails loudly.

Common wrong answer

"Aspire requires Docker Desktop." False, and it also gives up on the actual problem. A principal-level answer treats the container runtime as a platform dependency to be chosen, documented and tested — the same as an SDK version.

07Parameters, secrets and configuration

Every loop with a security-conscious interviewer lands here, and it is one of the easiest places to fail: the wrong answer is to say secrets go in appsettings.json, or to not know that dashboard users can read environment variables. What is tested: the parameter model, how secrets flow differently in run mode and publish mode, and — at senior level — where the boundary between Aspire's job and your secret manager's job sits.

Docs: aspire.dev — External parameters and secrets

midWhat is a parameter resource and how is its value supplied?

Answer

builder.AddParameter("name") declares an external value the model needs but does not own. In run mode the value is read from the AppHost's configuration under Parameters:name — user secrets, environment variables, appsettings — and since 13.2 the dashboard can prompt for it and optionally persist it to user secrets. Marking it secret: true changes behaviour meaningfully: the dashboard masks it, and at publish time it becomes a secure parameter the target must supply (a Bicep secure parameter, a Key Vault reference, a Compose .env entry, a Helm value) rather than a literal in the artifact. Parameters are how you keep credentials, tenant ids and per-environment URLs out of the AppHost source.

Example

var pw  = builder.AddParameter("pg-password", secret: true);
var tier = builder.AddParameter("sku", "Standard");        // with a default

var pg = builder.AddPostgres("pg", password: pw);
builder.AddProject<Projects.Api>("api").WithEnvironment("Sku", tier);
// AppHost user secrets (never appsettings.json)
{ "Parameters": { "pg-password": "dev-only-value" } }

Follow-ups

  • What if a secret parameter has no value in run mode? — Startup fails with a clear message naming the parameter; since 13.2 the dashboard offers to prompt for it instead.
  • What if the AppHost generates the password? — Integrations generate a random dev password by default; you supply a parameter when you need it stable or shared.
  • Can a parameter be a URL or a boolean? — Parameters are strings; convert where you consume them, and give a default for non-secret values.

Common wrong answer

"Put the password in the AppHost's appsettings.json — it's only dev." That file is committed, so a dev credential becomes a repo credential, and the same pattern gets copied to the staging file three months later. Parameters exist precisely so the value never has to be in source.

midWhere do secrets live during local development?

Answer

In .NET user secrets keyed to the AppHost project, or in environment variables — never in a committed file. The AppHost is the only place that needs them, because it injects the derived values (connection strings) into the services, so individual service projects usually need no secrets of their own. Practically: dotnet user-secrets set "Parameters:pg-password" "…" in the AppHost directory, and for anything shared across a team, a documented bootstrap script that pulls from your vault rather than a value in the wiki. The nuance worth adding: even a dev-only secret is visible in the dashboard's environment view for any resource that receives it, so treat "dev secret" as "shared secret", not as "no secret".

Example

cd ./src/AppHost
dotnet user-secrets init
dotnet user-secrets set "Parameters:pg-password" "$(openssl rand -base64 24)"
dotnet user-secrets set "Parameters:stripe-key" "sk_test_…"

Follow-ups

  • How do you onboard a new developer? — A script that authenticates to the vault and writes user secrets; anything manual gets pasted into Slack eventually.
  • Can Aspire read from Key Vault directly in run mode? — The AppHost is a normal .NET host, so add the Key Vault configuration provider and parameters resolve from it.
  • What about service-level secrets? — Keep them in the AppHost as parameters and inject them, so there is one source of truth per environment rather than one per project.

Common wrong answer

"Environment variables on the developer's machine are enough." They work, and they also leak into shells, CI logs and screen shares, and nothing rotates them. User secrets plus a vault-backed bootstrap is the answer that survives a security review.

seniorWhat happens to a secret parameter at publish and deploy time?

Answer

The two modes differ deliberately. aspire publish emits artifacts as a one-way handoff and preserves the requirement unresolved: the Bicep gets a @secure() parameter, the Compose output gets a .env placeholder, the Helm chart gets a value — so the artifact is safe to commit and review. aspire deploy resolves values internally and applies them, prompting or reading from deployment state so nothing is written to disk in the clear. On Azure the typical landing place is Key Vault with the app referencing it through managed identity, so the secret never appears in an environment variable at all. The security property to state out loud: the generated artifact should never contain a resolved secret, and if it does, that is a bug worth failing a review over.

Example

// emitted by aspire publish — the requirement, not the value
@secure()
param pg_password string

resource pg 'Microsoft.DBforPostgreSQL/flexibleServers@2024-08-01' = {
  properties: { administratorLoginPassword: pg_password }
}

Follow-ups

  • What is deployment state? — Locally cached deployment configuration (subscription, resource group, prior answers) introduced in 13.0, so repeat deploys do not re-prompt. It is developer-local; CI supplies values explicitly.
  • How do you supply parameters in CI? — Environment variables or CLI arguments in the pipeline, sourced from the pipeline's secret store; never checked in.
  • Does the dashboard show the resolved secret? — Masked in the parameter view, but a secret injected as an environment variable is visible in that resource's environment — which is why deployed dashboards must be authenticated.

Common wrong answer

"The publish output contains the values so you can just apply it." That would make the artifact a secret-bearing file that people commit and paste into tickets. The distinction between publish (preserve requirements) and deploy (resolve internally) is precisely what the question is testing.

seniorConfiguration precedence: AppHost, appsettings, environment, Key Vault — who wins?

Answer

Normal .NET rules, with one Aspire twist. Inside a service, the standard provider order applies and environment variables sit near the top, so the values the AppHost injects (ConnectionStrings__*, services__*, OTEL_*) override the same keys in appsettings — that is exactly what you want locally, and it is also the trap: a developer editing appsettings.Development.json to point at a different database will see no effect and conclude Aspire is broken. Inside the AppHost, Parameters:* resolves through its own provider chain, so user secrets beat appsettings and a vault provider can beat both. The rule I teach: in an Aspire solution, the AppHost is the source of truth for anything that describes topology, and appsettings is for things that are genuinely local to a service.

Example

// Deliberate escape hatch when a developer must override an injected value:
// set the environment variable, not appsettings — same precedence tier, explicit intent.
//   ConnectionStrings__catalogdb=Host=my-shared-db;…
// Or in the AppHost, make the override first-class:
var sharedDb = builder.AddConnectionString("catalogdb");   // resolves from config if present

Follow-ups

  • How do you make the override discoverable? — Model it: a parameter with a default that points at the local container, overridable per developer. Hidden precedence rules are a support burden.
  • Does the AppHost pass its own configuration to services? — No; only what you inject through WithEnvironment/WithReference. Services do not inherit the AppHost's config.
  • What about launchSettings.json? — It supplies the project's own profile (URLs, environment) and the AppHost merges it; conflicting values there are a common source of confusion.

Common wrong answer

"Aspire overrides everything, appsettings is ignored." Only the keys it injects are overridden; everything else in appsettings works normally. The over-broad version of the answer leads people to delete configuration they still need.

seniorHow do you handle per-environment differences — dev, staging, production — in one AppHost?

Answer

Three mechanisms, applied in this order of preference. Parameters for values (SKUs, region, external URLs, feature switches) — they flow through publish and deploy without branching the model. ExecutionContext.IsRunMode plus RunAsEmulator/RunAsContainer for the dev-substitution axis, which is a different axis from environment. And the deployment --environment flag, which identifies the pipeline context (Development/Staging/Production) so steps can vary — deliberately distinct from the compute environment resource. What I avoid is a cascade of if (env == "Production") in the AppHost: each one weakens the guarantee that what you ran locally resembles what you ship, and they are untested by definition because nobody runs the production branch locally.

Example

var sku    = builder.AddParameter("db-sku", "Standard_B1ms");
var region = builder.AddParameter("region", "westeurope");

var pg = builder.AddAzurePostgresFlexibleServer("pg")
                .ConfigureInfrastructure(infra =>
                {
                    var server = infra.GetProvisionableResources().OfType<PostgreSqlFlexibleServer>().Single();
                    server.Sku.Name = sku.Resource.Value;
                })
                .RunAsContainer();     // plain Postgres locally
// aspire deploy --environment Production

Follow-ups

  • How many environments should the AppHost know about? — Ideally zero by name: parameters carry the differences, the pipeline supplies them.
  • What about resources that only exist in production (a WAF, a CDN)? — Model them and let them be no-ops in run mode, or keep them in the platform's own IaC if they are not part of the app's topology.
  • How do you review the difference? — aspire publish -o ./artifacts --environment Staging and diff against production's output; the model is a pure function, so the diff is the review.

Common wrong answer

"Use ASPNETCORE_ENVIRONMENT in the AppHost and branch on it." It conflates the service-level environment with the deployment target, and it is the pattern that produces an AppHost nobody dares to change. Parameters plus explicit publish-mode substitution is the maintainable version.

principalA security review asks "where do our secrets go and who can see them" for an Aspire estate. Answer it.

Answer

I would answer in three layers. At rest: nothing in source — the AppHost holds parameter declarations, values come from user secrets locally, from the pipeline's secret store in CI, and from Key Vault or the platform's secret store in deployed environments; generated artifacts carry secure-parameter placeholders, and a CI check greps published output for anything that looks resolved. In transit and in use: secrets reach services as environment variables or platform secret references; where the platform supports it we use managed identity and no secret at all, which is the direction the Azure integrations push. Who can see them: anyone with access to a resource's environment view in a dashboard, anyone who can read the container's environment, and anyone with the pipeline's secret access — so the deployed dashboard is behind OIDC, the local dashboard is loopback-only with a token, and dev secrets are assumed shared and rotated on team changes. The gap I would flag unprompted is that environment variables are visible to anything running in the process and to the dashboard, so for the highest-sensitivity values I would use runtime secret retrieval rather than injection.

Example

// Prefer identity over secrets where the platform allows it.
var kv = builder.AddAzureKeyVault("secrets");
builder.AddProject<Projects.Api>("api")
       .WithReference(kv);        // the app gets a vault URI + managed identity, not a password

Follow-ups

  • Rotation? — Platform-side: rotate in Key Vault, restart or let the app re-read. Aspire has no rotation story of its own, and saying so is better than implying one.
  • Audit trail? — From the vault and the pipeline, not from Aspire; the AppHost is not an audited system of record.
  • What about the DCP/dashboard on a shared dev box? — Do not run it on a shared box with real secrets; that is the configuration where the environment view becomes a credential dump.

Common wrong answer

"Aspire handles secrets securely for you." It provides a model and safe defaults for artifacts; it does not store, rotate or audit anything. A security review that receives that answer will (rightly) assume nobody has thought about it.

08Publish, deploy and pipelines

This is the sub-area that changed most in 13.x, so it doubles as a recency test. The publisher interfaces of 9.x are gone; the model is now composable pipeline steps entered through aspire publish, aspire deploy and aspire do, with compute environments as resources in the graph. Expect a definitional question, a "what does it actually emit" question, and at senior level the important one: how this fits an existing CI/CD process that you are not going to replace.

Docs: aspire.dev — Deploy with Aspire

midWhat is the difference between aspire publish and aspire deploy?

Answer

aspire publish emits target-specific artifacts to a folder and stops — a one-way handoff, with parameters left unresolved so the output is reviewable and committable. aspire deploy runs the same pipeline further: it resolves parameters, provisions infrastructure, builds and pushes images, and applies the change to the target. Both entered GA in 13.4. The third entry point is aspire do <step>, which runs one named step and its dependencies — useful in CI when you want just the image build, or just the infrastructure. And aspire destroy (13.3) tears down what deploy created, across Azure, Kubernetes and Compose targets.

Example

aspire publish -o ./artifacts               # review-able output, secrets unresolved
aspire deploy --environment Production      # resolve, provision, push, apply
aspire do build --pipeline-log-level debug  # one step, verbose
aspire destroy                              # tear down what deploy created

Follow-ups

  • Which do you run in CI? — Usually publish in the build stage and either deploy or your existing tooling in the release stage, so approvals stay where your org already has them.
  • Is the output deterministic? — It is a function of the model and the parameters, so yes for a given input; diffing successive publishes is a good review practice.
  • What replaced the 9.x publishers? — The pipeline model; IDistributedApplicationPublisher, PublishingContext and WithPublishingCallback were removed in 13.0.

Common wrong answer

"Publish generates the manifest file that azd reads." That was the 8.x/9.x aspire-manifest.json world; since 13.0 publish emits real target artifacts — Bicep, a Compose file, a Helm chart — through the pipeline. Describing the manifest as the current mechanism dates you by two majors.

midWhat is a compute environment, and why is it a resource in the model?

Answer

A compute environment is the deployment target expressed as a resource: AddAzureContainerAppEnvironment, AddAzureAppServiceEnvironment, AddKubernetesEnvironment, AddDockerComposeEnvironment, and since 13.5 the preview Aspire.Hosting.Radius. Making it a resource means it participates in the graph: it contributes pipeline steps for the compute resources it can host, it can be configured like anything else, and a single AppHost can declare more than one so different services land in different places. The consequence people miss is that adding a compute environment changes what publish emits — without one, Aspire does not know what shape of artifact you want.

Example

var aca = builder.AddAzureContainerAppEnvironment("app-env");

builder.AddProject<Projects.Api>("api")
       .WithComputeEnvironment(aca)
       .WithExternalHttpEndpoints();

builder.AddProject<Projects.Worker>("worker")
       .WithComputeEnvironment(aca)
       .PublishAsAzureContainerAppJob();   // stable in 13.4: a job, not a service

Follow-ups

  • Can one app target two environments? — Yes; assign per resource with WithComputeEnvironment. It is how you keep a batch job on ACA Jobs while the API is on App Service.
  • What if you declare none? — There is nothing to publish for compute resources; the CLI tells you so.
  • Scheduled work? — PublishAsScheduledAzureContainerAppJob(), stable in 13.4.

Common wrong answer

"You choose the target with a CLI flag." There is a --environment flag but it selects the pipeline context (Development/Staging/Production), not the compute target. Conflating the two is the standard confusion here, and the docs call it out explicitly.

midWhat does aspire deploy to Azure Container Apps actually do?

Answer

It provisions the Container Apps environment, an Azure Container Registry, managed identities and the container apps for each compute resource; builds each project or Dockerfile into an image and pushes it to the registry; resolves parameters (prompting or reading deployment state); and applies the resulting Bicep. Ingress is configured from your endpoint model — external for anything with WithExternalHttpEndpoints(), internal otherwise — and service discovery variables are written into each app pointing at internal FQDNs. 13.4 added WithAcrPullIdentity() for controlling which identity pulls images, and 13.5 added experimental WithUniqueResourceNaming() for deployments that must avoid name collisions. The dashboard is included by default in ACA deployments, which is convenient and a thing to review before production.

Example

var aca = builder.AddAzureContainerAppEnvironment("env");

builder.AddProject<Projects.Api>("api")
       .WithExternalHttpEndpoints()
       .PublishAsAzureContainerApp((infra, app) =>
       {
           app.Configuration.Ingress.AllowInsecure = false;
           app.Template.Scale.MinReplicas = 2;      // no cold start for the public API
       });

Follow-ups

  • How do you tune scaling? — Through PublishAsAzureContainerApp's callback with the Azure.Provisioning.AppContainers types, or KEDA scale rules; defaults are min 0 / max 10, and min 0 means cold starts.
  • Where do connection strings land? — As container app secrets or Key Vault references, with managed identity preferred where the resource supports it.
  • How do you review the infrastructure before applying? — aspire publish -o ./infra and read the Bicep; treat it as code in review.

Common wrong answer

"It's just az containerapp up under the hood." The distinguishing work is deriving ingress, identity, registry and inter-app configuration from the model. Waving it off as a CLI wrapper means you cannot answer the next question, which is always about scaling or identity.

seniorHow does Aspire relate to azd now?

Answer

azd was the original deployment path — azd init detected an AppHost, consumed the manifest and owned provisioning and the pipeline. Since 13.x, Aspire's own publish/deploy pipeline is the primary route and reached GA in 13.4, while azd remains fully supported for teams already invested in it, including reading azd's infrastructure inputs from .azure/<name>/config.json as Bicep parameters. My decision rule: if you already have azd environments, pipelines and RBAC set up, keep them — the migration buys little. If you are starting now, use aspire deploy, because it is the path getting the investment (Kubernetes, App Service, Compose, Radius) and it keeps a single mental model across targets. Either way, azd infra synth or aspire publish gives you the Bicep to review and, if you want, to own outright.

Example

# legacy-but-supported path
azd init && azd up
azd infra synth          # materialise the Bicep to own it

# current path
aspire publish -o ./infra
aspire deploy --environment Production

Follow-ups

  • Can you use both? — Yes, though picking one as the source of truth avoids two teams provisioning the same resource group differently.
  • What about GitHub Actions/Azure DevOps? — azd pipeline config still scaffolds one; with the Aspire CLI you write the workflow yourself around aspire publish/deploy.
  • Which gives more control over Bicep? — Both end at Bicep; ConfigureInfrastructure in the AppHost is the supported customisation point, and synthesising to own the files is the escape hatch.

Common wrong answer

"You must use azd to deploy Aspire apps." True in 2024, false since 13.x and increasingly so — Kubernetes, Compose, App Service and Radius targets have nothing to do with azd. It is the single most common stale answer in this sub-area.

seniorYour org has an established GitOps pipeline. How do you use Aspire without replacing it?

Answer

Use aspire publish as a code generator and stop there. The build pipeline runs publish, the output (Helm chart, Bicep, Compose file) is committed to the environment repo or opened as a PR, and the existing GitOps controller applies it with the existing approvals, policies and drift detection. Aspire never gets credentials to the cluster or the subscription, which is usually the deciding factor for a platform team. The discipline this requires: the generated artifact must be diffable and stable — so pin image tags to the build's digest rather than latest, keep the model free of machine-dependent values, and review the first few diffs carefully. The failure mode to avoid is a half-adoption where some resources are generated and others hand-written in the same chart; draw the boundary at whole artifacts.

Example

- name: Generate manifests
  run: aspire publish -o ./generated --environment Staging
- name: Open PR to the environment repo
  run: |
    cp -r ./generated/* ../env-repo/staging/
    cd ../env-repo && git checkout -b aspire/${{ github.sha }} \
      && git commit -am "chore: regenerate staging manifests" && git push
# Argo CD / Flux applies after review — Aspire never touches the cluster.

Follow-ups

  • What if the platform team wants to hand-edit the chart? — Then generation is over: either they own it and you stop regenerating, or you add the setting to the model. Two owners of one file is the worst outcome.
  • How do you keep image tags stable? — Build and push in CI with an immutable tag/digest and pass it as a parameter, rather than letting deploy build implicitly.
  • Does this keep the dev-loop benefit? — Entirely; that was always the main value, and this arrangement gets it without a deployment fight.

Common wrong answer

"Replace the GitOps pipeline with aspire deploy." Technically possible, organisationally suicidal, and it discards audited approvals and drift detection for a newer tool. The expected senior answer is to slot in as a generator, not as a deployer.

seniorHow would you add a custom step to the deployment pipeline?

Answer

Through the pipeline model that replaced the publisher interfaces in 13.0: steps are named, declare dependencies, can run in parallel, and are contributed by resources or by the AppHost itself, then invoked by aspire do <step> or as part of publish/deploy. Typical additions are a security scan of the built images, a database migration gate, a smoke test after deploy, or pushing a manifest to an internal service catalogue. The important design point is that a step is part of the model, so it is visible, ordered and reusable rather than a bash block in one pipeline YAML — and it runs identically from a laptop and from CI, which is what makes it debuggable. Use --pipeline-log-level debug when a step misbehaves.

Example

# composable steps, invoked individually or as part of publish/deploy
aspire do build
aspire do scan-images          # your step, dependent on build
aspire do deploy --pipeline-log-level debug

Follow-ups

  • What happened to WithPublishingCallback? — Removed in 13.0 along with the publisher interfaces; the pipeline steps are the supported replacement.
  • Where does a migration belong? — As a step gated before the app rollout, or as an ACA job / Kubernetes job in the model — not as an app-startup side effect.
  • How do you test a step? — Run it in isolation with aspire do against a scratch environment; that isolation is the main reason to model it rather than script it.

Common wrong answer

"Implement IDistributedApplicationPublisher." Correct for 9.x, removed in 13.0 — and this is exactly the question interviewers use to find out whether your Aspire experience predates the rewrite. If your answer is the old interface, say so and name the replacement.

seniorHow do you do zero-downtime deploys and rollbacks with an Aspire-generated deployment?

Answer

You do not — the platform does, and your job is to model the app so the platform can. Concretely: health endpoints wired correctly so the platform's readiness probe is meaningful (readiness that checks dependencies, liveness that does not); replica counts above one with a sensible surge policy; migrations decoupled from startup and made backwards-compatible so old and new versions coexist during the rollout; and idempotent, retry-safe consumers. ACA does this with revisions and traffic weights, Kubernetes with rolling updates and a Deployment strategy. Rollback is likewise the platform's: previous revision on ACA, helm rollback or the previous Git commit under GitOps. What Aspire contributes is that the artifact is regenerated from a model, so "roll back the app" and "roll back the topology" are the same operation.

Example

builder.AddProject<Projects.Api>("api")
       .WithHttpHealthCheck("/health")           // readiness: dependencies included
       .PublishAsAzureContainerApp((infra, app) =>
       {
           app.Template.Scale.MinReplicas = 2;   // no single-replica rollout gap
       });

Follow-ups

  • What breaks zero-downtime most often? — A migration that is not backwards-compatible; expand-migrate-contract is the answer, not a maintenance window.
  • Can you do canary? — With ACA revision traffic weights or a mesh; not through the Aspire model itself.
  • Does aspire destroy have a place here? — For ephemeral PR environments, yes; never wired to a production pipeline.

Common wrong answer

"Aspire handles rolling deployments." It generates a description; the rollout semantics belong to ACA, Kubernetes or Compose. Claiming otherwise leads straight into a question about traffic weights that has no Aspire answer.

principalWould you let Aspire own your production infrastructure definition?

Answer

For application-scoped infrastructure — the container apps, their ingress, the identities they use, the databases and caches that belong to this system — yes, because keeping it in the same model as the topology is what stops drift, and the generated Bicep or chart is reviewable code. For platform-scoped infrastructure — networking, DNS, subscriptions, shared clusters, policy, WAF, private endpoints across systems — no: that has a longer lifecycle, different owners, and a blast radius that spans applications. So the boundary I draw is ownership lifetime: things created and destroyed with the application belong to Aspire; things that outlive it belong to the platform's Terraform or Bicep. Two further conditions before I would say yes at all: the output must be committed and reviewed, not applied straight from a developer's laptop, and the team must accept a quarterly upgrade cadence, because only the newest Aspire release is supported and the generator's output changes between versions.

Example

LayerOwnerWhy
VNet, DNS, subscriptions, policyPlatform IaCoutlives any app, cross-cutting blast radius
ACA environment / AKS clusterPlatform IaCshared by several apps
Container apps, ingress, identitiesAspire modellifecycle == the app's

SecretsVault + platformrotation and audit are not Aspire's job

Follow-ups

  • How do you consume platform-owned resources? — AsExisting(...), and since 13.5 AsExistingInResourceGroup/InSubscription/InTenant for cross-scope references — the model refers to them without claiming ownership.
  • What if generated Bicep drifts from what is deployed? — Whoever applies last wins, so pick one applier. Drift detection belongs to the platform pipeline, not to Aspire.
  • Exit strategy? — Synthesise the artifacts once and own them; the generated Bicep and charts are ordinary files, which keeps the decision reversible.

Common wrong answer

"Yes, single source of truth for everything." Attractive and wrong: it puts a VNet's lifecycle inside an application repo, on a tool with no LTS. The expected principal answer draws the line at ownership lifetime and names the support-policy risk out loud.

principalHow do you build ephemeral per-PR environments with Aspire?

Answer

The pieces exist: a namespaced deployment per PR (a resource group or Kubernetes namespace named for the PR), parameters supplied by the pipeline, aspire deploy --environment PR-1234, and aspire destroy on close — plus 13.5's experimental WithUniqueResourceNaming() to avoid collisions on Azure. The engineering is in the parts Aspire does not do: seeding realistic data, wiring identity and secrets per environment without human approval, keeping cost bounded with TTLs and hard destroy jobs (destroy-on-close is not enough; PRs get abandoned), and keeping provisioning under ten minutes or nobody uses it. My usual compromise is a shared long-lived environment for the heavy stateful dependencies plus per-PR compute, which cuts provisioning time and cost by an order of magnitude at the price of test isolation — and that trade-off is the thing to say out loud.

Example

on: [pull_request]
jobs:
  preview:
    steps:
      - run: aspire deploy --environment "pr-${{ github.event.number }}"
  teardown:
    if: github.event.action == 'closed'
    steps:
      - run: aspire destroy --environment "pr-${{ github.event.number }}"
# plus a nightly sweeper: destroy anything older than 72h, because PRs get abandoned.

Follow-ups

  • Why not per-PR databases? — Provisioning a managed database is minutes and money; a schema-per-PR on a shared server is usually the better trade.
  • How do you keep secrets out of PR environments? — Separate, low-privilege credentials scoped to the preview subscription; never production secrets, and never from a fork's workflow.
  • What is the real cost driver? — Idle compute in abandoned environments; the sweeper is not optional.

Common wrong answer

"Just run aspire deploy per PR." That is the easy 20% — the hard 80% is data, secrets, cost control and teardown of abandoned environments. Answers that stop at the command are read as never having operated one.

09Azure provisioning and identity

Asked whenever the role is Azure-flavoured, which is most .NET roles. The testable content is the emulator-versus-managed split, how Bicep is generated and customised, and how identity replaces connection strings. Senior candidates are expected to know AsExisting and why it matters for a platform-owned estate; principal candidates get the "who owns the Bicep" argument, which overlaps with unit 08.

Docs: aspire.dev — Customize Azure resources

midWhat happens when you write builder.AddAzureServiceBus("bus")?

Answer

You add an Azure resource to the model, described with Azure.Provisioning types, and its behaviour differs by mode. In publish mode it emits Bicep to provision a Service Bus namespace and its queues/topics, wires the app's identity to it, and injects the connection information. In run mode, unless you say otherwise, Aspire will try to provision a real Azure resource for you — which is why the idiomatic line is .RunAsEmulator() where an emulator exists (Service Bus, Storage via Azurite, Cosmos, Event Hubs) or .RunAsContainer() where an OSS equivalent stands in (Azure Cache for Redis → Redis, Azure Database for PostgreSQL → Postgres). The decision you are being asked about is whether developers need real cloud resources for the inner loop; usually they should not.

Example

var bus = builder.AddAzureServiceBus("bus").RunAsEmulator();
bus.AddServiceBusQueue("orders");

var storage = builder.AddAzureStorage("storage").RunAsEmulator();   // Azurite
var blobs   = storage.AddBlobs("uploads");

builder.AddProject<Projects.Api>("api").WithReference(bus).WithReference(blobs);

Follow-ups

  • What does local provisioning need? — An authenticated Azure context (az login), a subscription, location and resource-group prefix in the AppHost's Azure: configuration; deployment state (13.0+) remembers them.
  • Are emulators faithful? — Close but not identical: quota behaviour, some auth flows and a few APIs differ. Have at least one integration environment that uses the real service.
  • What is the risk of real resources in run mode? — Cost, drift and per-developer resource groups nobody cleans up. Make it a deliberate choice, not a default.

Common wrong answer

"It creates a local emulator automatically." Only if you ask for it. The default is real provisioning, and the surprise arrives as an Azure bill or an az login prompt in someone's first ten minutes.

midHow do you customise the generated Bicep?

Answer

Through ConfigureInfrastructure, which hands you the Azure.Provisioning object graph before it is rendered, so you set SKUs, capacity, network rules, retention, diagnostic settings and anything else in strongly typed C#. That is the supported customisation point and it composes with the rest of the model — a parameter can feed a SKU, so the same code produces different Bicep per environment. If you need more than that, aspire publish (or azd infra synth) materialises the Bicep files and you can own them outright, at the cost of losing regeneration. The rule I apply: customise in C# while the change is expressible there; take ownership of the Bicep only when you have accepted that Aspire is no longer generating it.

Example

var sku = builder.AddParameter("sb-sku", "Standard");

builder.AddAzureServiceBus("bus")
       .ConfigureInfrastructure(infra =>
       {
           var ns = infra.GetProvisionableResources().OfType<ServiceBusNamespace>().Single();
           ns.Sku = new ServiceBusSku { Name = ServiceBusSkuName.Premium, Capacity = 1 };
           ns.Tags.Add("cost-centre", "orders");
       });

Follow-ups

  • What if the property is not exposed by Azure.Provisioning? — Escape to raw Bicep with AddBicepTemplate, or own the file. The provisioning libraries lag the ARM API surface occasionally.
  • Can you reference an existing resource instead? — Yes: AsExisting, and 13.5's AsExistingInResourceGroup/InSubscription/InTenant for cross-scope references.
  • How do you review these changes? — Publish and diff the Bicep in the PR; the C# alone does not make the impact obvious.

Common wrong answer

"Edit the generated Bicep." It is overwritten on the next publish, so the fix silently disappears at the worst moment. Either customise in the model or take formal ownership of the files — never both.

seniorHow does Aspire handle managed identity, and why prefer it to connection strings?

Answer

For Azure resources that support Entra authentication, the generated infrastructure creates managed identities and role assignments, and the app receives an endpoint URI rather than a key — the client integration then uses DefaultAzureCredential, which resolves to the managed identity in Azure and to your developer credential locally. The benefit is that there is no secret to store, leak, or rotate, and access is auditable and revocable per identity. The costs to name: local development needs your az login identity to hold the same roles, role assignment propagation is eventually consistent (the classic "it works five minutes later" deploy failure), and not every resource or client library supports it — Redis and some third-party services still mean a key. Recent releases pushed further in this direction: 13.4 added WithAcrPullIdentity() so image pulls use a specific identity too.

Example

// AppHost
var storage = builder.AddAzureStorage("storage");
var blobs   = storage.AddBlobs("uploads");
builder.AddProject<Projects.Api>("api").WithReference(blobs);

// Service — no key anywhere
builder.AddAzureBlobClient("uploads");   // uses the endpoint + DefaultAzureCredential

Follow-ups

  • Why does it work in Azure but not locally? — Your developer identity lacks the data-plane role (e.g. Storage Blob Data Contributor); control-plane Owner is not enough, which trips up nearly everyone once.
  • User-assigned or system-assigned? — User-assigned is easier to pre-create and grant ahead of deploy, avoiding the propagation race; recent Aspire versions lean that way for compute resources.
  • What about local emulators? — Emulators use well-known credentials; the identity path only engages against the real service, so test it in an integration environment.

Common wrong answer

"Aspire puts the connection string in Key Vault for you." Sometimes it does, for resources without identity support — but leading with that misses the direction of travel and the actual security win, which is having no secret at all.

seniorYour platform team owns the databases. How do you reference them without letting Aspire provision anything?

Answer

Use AsExisting so the resource appears in the model, gets referenced normally, and produces no provisioning Bicep — and since 13.5 use the cross-scope variants when the resource lives in another resource group, subscription or tenant, which is the common shape in a landing-zone estate. The alternative for anything non-Azure or fully external is AddConnectionString, where the value comes from configuration or Key Vault. Locally you still want a container, so the pattern is RunAsContainer() plus AsExisting… in publish mode. What this buys is that services keep referring to catalogdb and nothing in application code knows whether that database is provisioned by this repo or by the platform's Terraform — which is exactly the seam you want when ownership changes later.

Example

var name  = builder.AddParameter("pg-name");
var group = builder.AddParameter("pg-rg");

var pg = builder.AddAzurePostgresFlexibleServer("pg")
                .RunAsContainer()                             // dev: local container
                .AsExistingInResourceGroup(name, group);      // 13.5: platform-owned, cross-scope

var db = pg.AddDatabase("catalogdb");
builder.AddProject<Projects.Api>("api").WithReference(db);

Follow-ups

  • Does AsExisting still create role assignments? — It can attempt them; if the platform owns RBAC, supply the identity's access out of band and keep the model to a plain reference.
  • What if the platform team renames the resource? — It is a parameter, so it is a pipeline variable change, not a code change. That is the point of parameterising it.
  • Any downside? — Your model no longer describes the whole system, so the "one source of truth" claim weakens. Say so rather than pretending otherwise.

Common wrong answer

"Just don't add the resource — put the connection string in appsettings." Then the dependency is invisible in the graph and the dashboard, and every environment gets its own hand-edited string. AsExisting/AddConnectionString keep it visible without claiming ownership.

seniorAzure Container Apps versus App Service versus AKS as an Aspire target — how do you choose?

Answer

ACA is the default and the best-supported path: it is container-native, scale-to-zero capable, has jobs (PublishAsAzureContainerAppJob, stable in 13.4) for batch work, and Aspire generates identity, ingress and registry wiring for it. App Service suits teams already there, especially with existing networking and slots, and is supported as a compute environment. AKS is right when you already run a cluster and have the platform capability to operate it — Aspire generates a Helm chart (13.3, with Gateway API, cert-manager and AGC support in 13.4), which is an on-ramp rather than a reason to adopt Kubernetes. The decision drivers I would name: existing operational capability first, then scale-to-zero and cost shape, then networking requirements, and only then feature parity. Choosing AKS because it is the most powerful is how a four-person team acquires a full-time platform job.

Follow-ups

  • Can services split across targets? — Yes, per-resource WithComputeEnvironment; useful for a job on ACA and an API on App Service.
  • What about cold starts? — Min replicas ≥ 1 for anything user-facing; scale-to-zero belongs to background and internal workloads.
  • Where does Radius fit? — Preview in 13.5 (Aspire.Hosting.Radius); interesting if your platform team already uses Radius environments and recipes.

Common wrong answer

"AKS, because it's the most flexible." Flexibility is a cost centre. Interviewers use this question to see whether you weigh operational capability, and "we already run a cluster" is a much better reason than "it can do anything".

seniorA deploy fails with an RBAC/role-assignment error that goes away on retry. What is happening and how do you fix it properly?

Answer

Azure role assignments are eventually consistent: the deployment creates the identity and the assignment, then immediately does something that requires it — pulling from ACR, reading a Key Vault secret, connecting to Storage — and the assignment has not propagated. Retry "works", which is why it survives in pipelines as a flaky step. The proper fixes are to pre-create user-assigned identities and their role assignments in the platform's IaC so the app deploy only uses them, or to sequence the pipeline so provisioning completes and settles before the compute rollout, or to grant the assignment at a stable scope (resource group) rather than per-resource so it exists before the resource does. In the model, WithAcrPullIdentity() (13.4) lets you point image pulls at an identity you control rather than one created inline.

Example

# Split provisioning from rollout so assignments settle between them.
aspire do provision --environment Production
aspire do deploy    --environment Production

Follow-ups

  • Is a retry ever acceptable? — As a bounded backoff in the pipeline, yes; as the explanation, no. Unexplained flakiness erodes trust in the whole deploy.
  • Why does it fail more on first deploy? — Everything is new at once; subsequent deploys reuse settled assignments.
  • Local equivalent? — Your az login identity missing the data-plane role, which does not resolve on retry — different problem, same error text.

Common wrong answer

"Add a retry, Azure is flaky." It is not flaky, it is eventually consistent, and the distinction points at the real fix. This is a favourite question because the lazy answer is so tempting and so common in real pipelines.

principalHow do you keep an Aspire-generated Azure estate compliant with landing-zone policy?

Answer

Make policy the gate, not a convention. Azure Policy at the management-group level rejects non-compliant resources regardless of who generated them, so the first move is to test the generated Bicep against policy in CI — a what-if or a policy evaluation on the published artifact — rather than discovering it at deploy. The second is to constrain the model: private endpoints, no public ingress by default, required tags and diagnostic settings encoded once in a shared ConfigureInfrastructure extension that every team's AppHost applies, so compliance is the default path rather than a review checklist. The third is the ownership split from unit 08: networking and policy stay in the platform's IaC and the app model references them with AsExisting…. And I would state the residual risk plainly: an Aspire minor upgrade can change generated output, so the policy evaluation must run on every publish, not just when the model changes.

Example

public static IResourceBuilder<T> WithContosoPolicy<T>(this IResourceBuilder<T> b)
    where T : AzureProvisioningResource =>
    b.ConfigureInfrastructure(infra =>
    {
        foreach (var r in infra.GetProvisionableResources().OfType<ProvisionableResource>())
        {
            // required tags, diagnostic settings, no public network access
        }
    });

Follow-ups

  • How do you catch it before deploy? — aspire publish in CI, then az deployment group what-if plus a policy scan on the output.
  • What if policy blocks something Aspire needs? — Usually public ingress or a missing private endpoint; fix in the model, or grant a scoped exemption with an expiry date.
  • How do you stop each team solving this differently? — The shared extension package plus a template AppHost; documentation alone does not survive contact with a deadline.

Common wrong answer

"Review the Bicep in PRs." Necessary, insufficient, and it fails exactly when the estate grows past the point where anyone reads it. Policy-as-code enforcing at deploy time is what makes compliance structural rather than aspirational.

10Health checks and startup order

A small sub-area that punches above its weight, because it is where local-loop convenience and production correctness are most easily confused. Interviewers check that you can distinguish liveness from readiness, that you know Aspire's health checks feed WaitFor, and that you understand why the templates do not expose health endpoints outside Development.

Docs: aspire.dev — Health checks and readiness gates

midWhat health endpoints does the template give you, and why are they not mapped in production?

Answer

MapDefaultEndpoints() maps /health — all registered checks, i.e. readiness — and /alive, filtered to checks tagged live, i.e. liveness. The template wraps both in an IsDevelopment() guard, for two reasons the interviewer wants to hear: the endpoints are unauthenticated and expose your dependency topology and failure details to anyone who can reach them, and running every dependency check on demand is a cheap denial-of-service amplifier. In production you either expose them only on an internal port or path not routed publicly, or add authorization, or map them deliberately knowing the ingress restricts access. Shipping the guard unchanged and then wondering why the platform probe fails is a very common first-deploy incident.

Example

public static WebApplication MapDefaultEndpoints(this WebApplication app)
{
    if (app.Environment.IsDevelopment())          // ← the template's guard
    {
        app.MapHealthChecks("/health");
        app.MapHealthChecks("/alive", new() { Predicate = r => r.Tags.Contains("live") });
    }
    return app;
}

Follow-ups

  • Which does a Kubernetes readiness probe use? — /health; liveness uses /alive. Pointing liveness at /health is how one slow database restarts every pod in the deployment.
  • How do you tag a check as live? — AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"]), as the template does.
  • What is the safe production shape? — Map them on a separate internal port, or require an auth policy; not "leave them off and hope the platform does not need them".

Common wrong answer

"They're mapped everywhere by default." They are not, and the resulting symptom — probes failing after the first production deploy — is exactly the incident this question is about.

midExplain liveness versus readiness with an Aspire-flavoured example.

Answer

Liveness answers "is this process wedged, should it be killed"; readiness answers "should this instance receive traffic right now". The distinction matters because dependency checks belong in readiness only: if your Redis is down and liveness includes a Redis check, the platform kills and restarts every replica, turning a degraded cache into a full outage and a crash loop. In an Aspire service the client integrations register dependency checks automatically, and they all land in /health — which is correct for readiness and precisely why /alive filters to the live tag. The senior addition: even readiness should be tolerant of optional dependencies. If the cache being down means "slower", the service is still ready.

Example

builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddCheck<CacheHealthCheck>("cache", failureStatus: HealthStatus.Degraded);  // optional dep

// /alive  → only "self"        → never fails because Redis is down
// /health → everything          → Degraded, not Unhealthy, when only the cache is out

Follow-ups

  • What does Degraded mean to a platform? — By default it is still "healthy" to ASP.NET Core's status mapping; decide deliberately whether Degraded should remove an instance from rotation.
  • What about startup probes? — Kubernetes startup probes protect slow starters from liveness kills; map them to /alive with a generous failure threshold.
  • How does this interact with WaitFor? — WaitFor uses the resource's health state, so a resource with only a liveness-style check is "healthy" long before it is usable.

Common wrong answer

"Both endpoints check the same thing, one is just an alias." That is functionally what you get if you ignore the tags — and it is the configuration that turns a dependency blip into a cluster-wide restart storm.

midHow do you add a health check to a container resource in the AppHost?

Answer

The quickest is WithHttpHealthCheck("/path") (9.x+), which polls an HTTP endpoint on the resource and feeds the result into the dashboard and into WaitFor. For non-HTTP resources you register a check in the AppHost's service collection and attach it with WithHealthCheck(name) — the standard AspNetCore.HealthChecks.* packages work here, so a TCP or database-specific check is a line. First-party integrations already ship checks, which is why WaitFor(postgres) is meaningful without you doing anything. The reason this matters: a container without a health check is "healthy" the instant it starts, so every WaitFor on it is theatre.

Example

var legacy = builder.AddContainer("legacy-api", "contoso/legacy", "2.4")
                    .WithHttpEndpoint(targetPort: 8080, name: "http")
                    .WithHttpHealthCheck("/status", endpointName: "http");

builder.AddProject<Projects.Api>("api")
       .WithReference(legacy.GetEndpoint("http"))
       .WaitFor(legacy);      // now actually means something

Follow-ups

  • Can the TypeScript AppHost do this? — Yes, builder.addHealthCheck() landed in 13.5.
  • What is the polling cost? — Non-trivial across twenty resources on a laptop; keep intervals sane and paths cheap.
  • Does the container's own HEALTHCHECK instruction count? — Aspire's model uses its own checks; do not assume the image's Dockerfile healthcheck drives WaitFor.

Common wrong answer

"Containers get health checks automatically." First-party integrations do; a bare AddContainer does not, and that is the case where WaitFor silently degrades to "wait for the process to exist".

seniorShould a service refuse to start if its database is unavailable?

Answer

Almost never. Failing to start turns a transient dependency outage into a crash loop, and crash loops interact badly with every platform's backoff — you extend a 30-second database failover into minutes of unavailability, and you cannot deploy during an incident because new pods will not come up. The right shape is: start, report not-ready until the dependency is reachable, retry with backoff, and let the platform keep the instance out of rotation meanwhile. Aspire's WaitFor makes the local loop nicer by not starting a service before its database, and that convenience is exactly what tempts people to remove startup resilience from the code. In an interview I name both: WaitFor locally, retry-and-report-unready in production, and the two are not substitutes.

Example

// Don't do this in production code:
// await db.Database.MigrateAsync();   // at startup, throws if the DB is down → crash loop

// Do this: start, report unready, retry.
builder.Services.AddHealthChecks()
    .AddNpgSql(cs, name: "catalogdb", failureStatus: HealthStatus.Unhealthy);

Follow-ups

  • What about migrations at startup? — Move them to a separate job gated with WaitForCompletion locally and a pipeline step or Kubernetes/ACA job in production; startup migrations also race across replicas.
  • Is there a case for failing fast? — Yes: misconfiguration. A missing connection string is a permanent error, and failing loudly beats reporting unready forever.
  • How do you tell them apart? — Configuration validation at startup, dependency reachability at readiness. Different failure classes, different handling.

Common wrong answer

"Yes — fail fast, it's cleaner." Fail-fast is right for configuration errors and wrong for transient dependency outages, and the answer that does not distinguish them is the one that produces a crash-looping fleet during a failover.

seniorYour /health endpoint is timing out under load. Diagnose.

Answer

Almost always because /health executes every registered check on every request, and Aspire's client integrations register one per dependency — eight dependencies means eight round trips, some of which open connections, per probe, per replica, at whatever interval the platform polls. Under load those checks compete with real traffic for the same connection pools, so health degrades exactly when you need it. The fixes: cache health results for a few seconds; split the endpoints so the platform's frequent probe hits a cheap one; drop or downgrade checks for optional dependencies; and use failureStatus: Degraded so a slow non-critical dependency does not evict the instance. If you need per-dependency status for humans, put it on a separate authenticated diagnostics endpoint rather than the one the load balancer hammers.

Example

// Cheap probe for the platform, full check for humans.
app.MapHealthChecks("/alive",  new() { Predicate = r => r.Tags.Contains("live") });
app.MapHealthChecks("/health", new() { Predicate = r => r.Tags.Contains("ready") })
   .RequireHost("localhost");   // or an auth policy / internal port

builder.Services.AddHealthChecks()
    .AddNpgSql(cs, name: "db", tags: ["ready"])
    .AddRedis(redisCs, name: "cache", failureStatus: HealthStatus.Degraded, tags: ["ready"]);

Follow-ups

  • How do you disable an integration's automatic check? — DisableHealthChecks = true in that client integration's settings, per connection.
  • Does caching hide real failures? — For a few seconds, yes — which is an acceptable trade against probing a database every second from thirty replicas.
  • What probe interval is sane? — Tie it to how fast you need eviction; 10 seconds with a 3-failure threshold is a reasonable default, not 1 second.

Common wrong answer

"Increase the probe timeout." It hides the symptom and keeps a failing instance in rotation longer. The interviewer is looking for the realisation that the endpoint itself is doing too much work, which is a direct consequence of what the client integrations registered for you.

principalDefine a health-check standard for forty services. What is in it?

Answer

Four rules, in the shared ServiceDefaults package so they are the default rather than a document. One: /alive is process-only and never touches a dependency — it exists solely to answer "restart me". Two: /health is readiness, includes required dependencies, marks optional ones Degraded, is cached for a few seconds and is not publicly routable. Three: configuration validation happens at startup and fails hard, because a missing connection string is not a health condition. Four: every check has a name that matches the dependency's resource name in the AppHost, so a failing check maps to a node in the topology without translation. On top of that, one dashboard panel per service driven by the same names, and a CI check that a new service exposes both endpoints. The trade-off I would name unprompted: standardising readiness semantics makes individual services slightly less expressive, and that is worth it because on-call staff can then read any service's health without reading its code.

Example

public static IHostApplicationBuilder AddContosoHealth(this IHostApplicationBuilder builder)
{
    builder.Services.AddHealthChecks()
        .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"]);

    builder.Services.Configure<HealthCheckPublisherOptions>(o =>
    {
        o.Delay  = TimeSpan.FromSeconds(5);
        o.Period = TimeSpan.FromSeconds(15);   // one cached evaluation for all probes
    });
    return builder;
}

Follow-ups

  • How do you enforce it? — Package plus an architecture test that fails the build if MapDefaultEndpoints is missing or a check is untagged.
  • What about legacy services? — Give them a shim that reports live-only, so the platform treats them uniformly while they migrate.
  • Does the Aspire dashboard use these? — It shows the resource-level health that the AppHost's checks produce, which is why naming them after resources keeps local and production stories aligned.

Common wrong answer

"Every service defines its own health checks — they know their dependencies best." True and irrelevant: without shared semantics, on-call cannot tell whether Unhealthy means "restart it" or "wait". The standard is about the meaning of the signal, not the list of checks.

11Testing with Aspire

Asked in most senior loops because it is where Aspire's promise meets CI reality: real dependencies in containers give you honest tests and a slow pipeline. Interviewers want the API (DistributedApplicationTestingBuilder), an understanding of what it costs, and a testing-pyramid opinion. This is also where the comparison with Testcontainers comes up, and having a clear position on it is worth points.

Docs: aspire.dev — Write your first Aspire test

midHow do you write an integration test that starts the whole app?

Answer

Reference Aspire.Hosting.Testing, create the host with DistributedApplicationTestingBuilder.CreateAsync<Projects.AppHost>(), build and start it, then get a resilient HttpClient for a resource with app.CreateHttpClient("api"). Before asserting, wait for the resource to be healthy through app.ResourceNotifications.WaitForResourceHealthyAsync("api") — skipping that is the number one cause of flaky Aspire tests, because the client is ready before the service is. Resource logs are surfaced through the DistributedApplication, so a failing test can print why. It is the real graph: real containers, real ports, real service discovery.

Example

[Fact]
public async Task Catalog_returns_items()
{
    var appHost = await DistributedApplicationTestingBuilder.CreateAsync<Projects.AppHost>();
    appHost.Services.ConfigureHttpClientDefaults(h => h.AddStandardResilienceHandler());

    await using var app = await appHost.BuildAsync();
    await app.StartAsync();

    await app.ResourceNotifications.WaitForResourceHealthyAsync("catalog-api")
             .WaitAsync(TimeSpan.FromSeconds(60));

    var client = app.CreateHttpClient("catalog-api");
    var response = await client.GetAsync("/items");

    Assert.Equal(HttpStatusCode.OK, response.StatusCode);
}

Follow-ups

  • Why the explicit timeout? — Container pulls and cold starts make the first test in a run much slower; a generous per-wait timeout beats a flaky suite.
  • How do you avoid starting the graph per test? — A shared fixture (xUnit IClassFixture/collection fixture) so one start serves many assertions.
  • Can you override resources for a test? — Yes; the builder exposes the service collection and the model, so you can swap a resource or inject a parameter before BuildAsync.

Common wrong answer

"Start the app and immediately call the endpoint." It passes on a warm machine and fails in CI, and then someone adds Thread.Sleep(5000). The notification API exists precisely so you wait on a signal rather than on the clock.

midAspire testing versus Testcontainers versus WebApplicationFactory — when do you use which?

Answer

WebApplicationFactory is in-process, sub-second, and perfect for testing one service's HTTP surface with fakes behind it — most of your tests should be here. Testcontainers gives one service plus one or two real dependencies, controlled precisely, without an AppHost; it is ideal for repository and data-access tests. Aspire's testing builder starts the whole declared graph, which is right for a handful of end-to-end journeys that cross service boundaries and for validating the wiring itself — that WithReference injected what you thought. The trap is using the third for everything: startup cost is measured in tens of seconds, so a 200-test suite becomes an hour. My split is roughly 80% unit, 15% WebApplicationFactory or Testcontainers, 5% full-graph.

Example

ToolScopeTypical startUse for
WebApplicationFactoryone service, in-process< 1sendpoint behaviour, auth, validation
Testcontainersone service + real depssecondsrepositories, migrations, SQL

Follow-ups

  • Can you combine them? — Yes, and you should: they are different layers, not competitors.
  • Does Aspire use Testcontainers? — No; DCP drives the container runtime directly. Same idea, different implementation.
  • What about testing the model without starting anything? — Build the model and assert on resources and annotations — fast, and the right place for "every project has a health check" rules.

Common wrong answer

"Aspire testing replaces the others." It replaces neither, and teams that believe it do get a CI pipeline that takes forty minutes and a suite people skip. Naming the cost is what makes this answer senior.

seniorHow do you keep Aspire integration tests fast and non-flaky in CI?

Answer

Five things. Share one application instance across a test collection instead of per test. Always wait on resource notifications rather than sleeping. Pre-pull and cache container images on the runner, and mirror them internally so you are not rate-limited by Docker Hub mid-run. Trim the graph the tests need — a test AppHost that starts six resources instead of twenty-two is legitimate and much faster. And isolate state: unique database or schema names per test run so parallel jobs do not collide, with cleanup in disposal. Beyond that, accept a slower dedicated job for the full-graph suite rather than blocking every PR on it: run it on merge to main and on a schedule, and keep the PR gate fast.

Example

public sealed class AppFixture : IAsyncLifetime
{
    public DistributedApplication App = default!;

    public async Task InitializeAsync()
    {
        var b = await DistributedApplicationTestingBuilder.CreateAsync<Projects.AppHost>(
            ["--environment", "Testing"]);
        App = await b.BuildAsync();
        await App.StartAsync();
        await App.ResourceNotifications.WaitForResourceHealthyAsync("catalog-api")
                 .WaitAsync(TimeSpan.FromSeconds(120));
    }
    public Task DisposeAsync() => App.DisposeAsync().AsTask();
}
[CollectionDefinition("app")] public sealed class AppCollection : ICollectionFixture<AppFixture> { }

Follow-ups

  • Can you run tests in parallel against one instance? — Yes if the tests are data-isolated; xUnit collections give you the control.
  • What makes the first run so much slower? — Image pulls and cold container starts; a warm cache changes the numbers by minutes.
  • How do you debug a CI-only failure? — Capture resource logs on failure; the DistributedApplication surfaces them, and attaching them to the run is far better than re-running hopefully.

Common wrong answer

"Add retries to the flaky tests." Retries convert a diagnosable failure into an intermittent one and hide real races. Every flake here has a specific cause — usually a missing readiness wait or shared state — and the interviewer wants to hear you name them.

seniorHow do you test the AppHost model itself?

Answer

Build the model without starting it and assert on the resource graph — the testing builder gives you the DistributedApplicationModel, so you can check that every project has a health check, that no service references a resource it does not wait for, that every Azure resource has the required tags, or that a specific image tag is pinned. These run in milliseconds and catch the class of mistake that would otherwise surface as a broken deploy. The second half is asserting on output: run aspire publish in CI and snapshot-test the generated Bicep or Helm chart, so an Aspire upgrade that changes generation shows up as a reviewable diff rather than a surprise in production. Together those two give you a safety net over infrastructure code that is otherwise only validated by deploying it.

Example

[Fact]
public async Task Every_project_has_a_health_check()
{
    var b = await DistributedApplicationTestingBuilder.CreateAsync<Projects.AppHost>();
    await using var app = await b.BuildAsync();     // built, not started

    var model = app.Services.GetRequiredService<DistributedApplicationModel>();
    foreach (var p in model.Resources.OfType<ProjectResource>())
        Assert.True(p.TryGetAnnotationsOfType<HealthCheckAnnotation>(out _), $"{p.Name} has none");
}

Follow-ups

  • Is the model stable enough to assert on? — Public annotation types are stable within a major; expect churn across majors, which is itself useful upgrade signal.
  • What about snapshot-testing Bicep? — Yes, with normalisation for timestamps and generated names; the diff on an Aspire upgrade is exactly the review you want.
  • Where do these tests live? — Next to the AppHost, running on every PR — they are fast enough to have no gate cost.

Common wrong answer

"You can't test infrastructure code without deploying it." You can test the description, which is most of what breaks. This answer is the reason a lot of AppHosts have no tests at all and drift until a deploy fails.

seniorHow do you stub or replace a dependency in an Aspire test?

Answer

At three levels, and choosing correctly is the point. In the model: build a test-specific AppHost, or branch on an argument such as --environment Testing, to swap a real container for a fake — a WireMock container instead of a third-party API, an in-memory or lighter database. At the configuration level: override a parameter or connection string before BuildAsync, so the same model points somewhere else. Inside a service: that is WebApplicationFactory territory, not Aspire's, and trying to reach into a service's DI from an Aspire test is a sign the test is at the wrong level. For third-party HTTP dependencies I model a stub as a first-class resource so the topology is honest and the stub is visible in the dashboard.

Example

// AppHost: a stub instead of the real payment provider when testing.
var payments = builder.ExecutionContext.IsRunMode && builder.Environment.EnvironmentName == "Testing"
    ? builder.AddContainer("payments", "wiremock/wiremock", "3.9.1")
             .WithHttpEndpoint(targetPort: 8080, name: "http")
             .WithBindMount("./stubs", "/home/wiremock").GetEndpoint("http")
    : builder.AddExternalService("payments", paymentsUrl).GetEndpoint("https");

builder.AddProject<Projects.Orders>("orders").WithReference(payments);

Follow-ups

  • Does swapping resources undermine the test's realism? — Yes, deliberately: you are testing your system, not the vendor's. Keep one contract test against the real API on a schedule.
  • How do you avoid an AppHost full of test branches? — Prefer a separate test AppHost project referencing the same module extension methods.
  • Can you fake time or randomness? — Inside services, yes; not something the app model addresses.

Common wrong answer

"Mock the dependency in the test's DI container." There is no shared container — services are separate processes. This answer reveals the same mental model error as unit 02's: thinking the AppHost hosts your services in-process.

principalWhat is your testing strategy for a system whose local topology is an Aspire graph?

Answer

I would define four layers with explicit budgets. Unit tests, in-process, thousands, sub-second — the bulk. Component tests with WebApplicationFactory and Testcontainers for anything touching a real database or driver. Model tests over the AppHost graph and snapshot tests over published artifacts, cheap and run on every PR, because infrastructure regressions are otherwise invisible until deploy. And a deliberately small number — five to fifteen — of full-graph journey tests that prove the wiring: a request crossing three services, a message consumed, a trace spanning both. The PR gate runs the first three; the fourth runs on merge and nightly with a hard time budget, and if it exceeds it, we cut tests rather than accept a slow gate. The trade-off I name unprompted: full-graph tests are the only ones that catch configuration-injection mistakes, so cutting them to zero is not an option — they are the tax for having a declarative topology.

Follow-ups

  • What do you do when the nightly suite is red for a week? — Treat it as a broken build: either fix it or delete the test. A permanently red suite is worse than none.
  • How do you test deployment itself? — A smoke test as a pipeline step after deploy to a staging environment; that is the only honest test of the generated artifacts.
  • Contract tests? — Yes between services, so the full-graph count can stay small; the graph tests prove wiring, contracts prove behaviour.

Common wrong answer

"Aspire makes end-to-end testing easy, so test everything end to end." Easy to write is not cheap to run: a suite of 200 graph tests is an hour of CI and a queue of blocked PRs. The budget-per-layer framing is what an interviewer at this level is listening for.

12Databases, migrations and seeding

Every real Aspire system has a database, so this comes up as the practical follow-on to the app model. The interesting content is not AddPostgres — it is where migrations run, how you seed without slowing every start, and how the local container story maps to a managed service in production. Expect the migration question in almost every loop that reaches this depth.

Docs: aspire.dev — Database integrations

midModel a Postgres server with two databases and wire an EF Core service to one.

Answer

The server is one resource and databases are children of it: AddPostgres("pg") then AddDatabase("catalogdb") and AddDatabase("ordersdb"). Each database resource has its own connection string, so services reference exactly the database they own rather than the server. On the service side, AddNpgsqlDbContext<CatalogContext>("catalogdb") registers the context with the injected connection string, health check, tracing and retry-on-failure defaults. The naming discipline matters: the resource name is the configuration key, so it becomes a contract between the AppHost and the service.

Example

// AppHost
var pg      = builder.AddPostgres("pg").WithDataVolume().WithLifetime(ContainerLifetime.Persistent);
var catalog = pg.AddDatabase("catalogdb");
var orders  = pg.AddDatabase("ordersdb");

builder.AddProject<Projects.Catalog_Api>("catalog-api").WithReference(catalog).WaitFor(catalog);
builder.AddProject<Projects.Orders_Api>("orders-api").WithReference(orders).WaitFor(orders);

// Catalog.Api
builder.AddNpgsqlDbContext<CatalogContext>("catalogdb");

Follow-ups

  • Does AddDatabase create the database? — The integration ensures it exists on the container; against a managed server in production, creation is usually a provisioning concern, so check the target's behaviour rather than assuming.
  • Should two services share one database? — Separate databases on one server is the pragmatic middle ground: isolation of schema and permissions, one thing to run locally.
  • What about the default image? — Pin it. 13.4 moved the default to Postgres 18.3 and old data volumes do not load.

Common wrong answer

"Reference the server and pick the database in the connection string in code." Then the service owns topology knowledge, the dashboard cannot show which service uses which database, and per-database credentials become impossible. The child-resource model exists for exactly this.

midWhere should EF Core migrations run?

Answer

Not in the application's startup path. The Aspire-idiomatic local pattern is a dedicated migration project modelled as its own resource, with the API using WaitForCompletion(migrations) so it starts only after migrations succeed. In production the same project becomes a pipeline step, an ACA job or a Kubernetes job that runs before the rollout. The reasons are the ones that bite in production: startup migrations race across replicas, they hold the app in a not-ready state while a long migration runs, they need elevated database permissions the runtime should not have, and they make rollback ambiguous. The local WaitForCompletion pattern is nice precisely because it rehearses the production shape rather than replacing it.

Example

var db = builder.AddPostgres("pg").AddDatabase("catalogdb");

var migrate = builder.AddProject<Projects.Catalog_Migrations>("migrate")
                     .WithReference(db).WaitFor(db);

builder.AddProject<Projects.Catalog_Api>("catalog-api")
       .WithReference(db)
       .WaitForCompletion(migrate, exitCode: 0);

Follow-ups

  • What about EnsureCreated? — Fine for throwaway tests, never for anything with a migration history; it and migrations do not mix.
  • Zero-downtime migrations? — Expand-migrate-contract: add nullable columns and new tables first, deploy code that writes both, backfill, then remove. Aspire changes none of this.
  • Who has DDL permission? — The migration identity, not the app identity. Splitting them is the practical benefit of a separate job.

Common wrong answer

"Call db.Database.Migrate() at startup, it's simplest." It is simplest until three replicas start simultaneously, or until a five-minute migration makes the deploy look hung, or until rollback needs a schema that no longer exists. Interviewers ask this specifically to see whether you have run it in production.

midHow do you seed development data without slowing every start?

Answer

Three options with different costs. Cheapest: a persistent data volume seeded once — the data survives restarts, so seeding is a rare operation rather than a per-start one. Next: SQL scripts mounted into the container's init directory (WithBindMount to /docker-entrypoint-initdb.d for Postgres), which run only when the data directory is empty, or WithContainerFiles/withContainerFiles for file injection. Most flexible: a seeding resource with WithExplicitStart() so it appears in the dashboard as a button rather than running automatically, or a resource command (WithCommand("reseed", …)) which is the nicest developer experience because it is discoverable and re-runnable. What I avoid is seeding inside the application's startup, which couples demo data to production code paths.

Example

var pg = builder.AddPostgres("pg")
                .WithDataVolume("catalog-pgdata")
                .WithLifetime(ContainerLifetime.Persistent)
                .WithBindMount("./seed", "/docker-entrypoint-initdb.d");   // runs on empty volume

var db = pg.AddDatabase("catalogdb");
db.WithCommand("reseed", "Reseed demo data",
    async ctx => { await Seeder.RunAsync(ctx.ServiceProvider, ctx.CancellationToken);
                   return CommandResults.Success(); });

Follow-ups

  • Why does the init script not re-run? — Postgres only runs it when the data directory is empty; with a persistent volume that means once. That is the feature, and the confusion.
  • How much data? — Enough to exercise pagination and joins; a three-row seed hides every performance problem until staging.
  • Production seeding? — Reference data belongs in migrations; demo data does not belong in production at all.

Common wrong answer

"Seed on startup if the table is empty." It adds a query to every start, races across replicas, and eventually someone ships it to production and inserts test customers. Move it out of the app.

seniorLocal Postgres in a container, Azure Database for PostgreSQL in production. What actually differs?

Answer

More than teams expect, and the point of the question is whether you can list it. Authentication: local uses a password, production should use Entra managed identity, so the connection code path differs and only production exercises token refresh. Networking: private endpoints, firewall rules and forced TLS exist only in production, and TLS misconfiguration is the classic first-deploy failure. Version and extensions: the container's version and available extensions must match the managed service's or you find out at deploy — and the default image moved to 18.3 in 13.4, so an unpinned local container may now be ahead of production. Behaviour under load: connection limits, pooling (managed services often front with PgBouncer), timeouts and failover semantics have no local equivalent. My mitigation is an always-on integration environment using the real managed service, on the same migration and deploy path, so the difference is caught by CI rather than by users.

Example

var pg = builder.AddAzurePostgresFlexibleServer("pg")
                .RunAsContainer(c => c.WithImage("library/postgres", "17.6")  // match prod's major
                                      .WithDataVolume());
var db = pg.AddDatabase("catalogdb");

Follow-ups

  • How do you catch TLS problems earlier? — Enable TLS on the local container and use the same connection-string options; 13.5's WithHttpsDeveloperCertificate() helps for HTTP resources.
  • Connection pooling differences? — Set MaxPoolSize deliberately in both; the local default is generous and the managed service's connection cap is not.
  • What about identity locally? — Some teams run Entra auth against a dev server for one service to keep the code path exercised; otherwise it is only tested in staging.

Common wrong answer

"Nothing differs, it's the same Postgres." Same engine, different auth, network, limits, extensions and possibly major version. The candidates who say "nothing" are the ones whose first deploy fails on TLS and whose second fails on connection limits.

principalTwelve services, one database server locally. How do you keep data ownership honest?

Answer

The local convenience of one container is fine; the danger is that it quietly licenses cross-service queries because the tables are all right there. I enforce ownership at three levels. Schema and permissions: one database (or at least one schema) per service, with a per-service role that has no grants on other services' objects — so a cross-service query fails locally, not in production. Migrations: each service owns its own migration project, and a service may not have a migration touching another's schema. Review: a CI check that a service's connection string name matches the resource it owns, so a copy-pasted WithReference to somebody else's database fails the build. Beyond that, model the boundary explicitly — if service A needs B's data, that is an API or an event, and the AppHost should show the dependency as a service reference rather than a shared database reference. The trade-off I would name: one server locally is faster and cheaper than twelve, and the permission model is what stops that efficiency becoming a coupling.

Example

var pg = builder.AddPostgres("pg").WithLifetime(ContainerLifetime.Persistent);

// one database per owner, referenced only by its owner
var catalog = pg.AddDatabase("catalogdb");
var orders  = pg.AddDatabase("ordersdb");

builder.AddProject<Projects.Catalog_Api>("catalog-api").WithReference(catalog);
builder.AddProject<Projects.Orders_Api>("orders-api").WithReference(orders)
       .WithReference(catalogApi);     // needs catalog data? go through the API

Follow-ups

  • What about reporting across services? — A read model or a warehouse fed by events, not a join across schemas — that decision belongs in design, and the AppHost should make the intended path the easy one.
  • Does one server hide performance problems? — Yes: shared cache and no network hop flatter everything. Load test against production-shaped topology.
  • When do you split the server locally? — When a service genuinely needs a different engine or version; otherwise the start-time cost is not worth it.

Common wrong answer

"Trust the team not to query across boundaries." Boundaries that are only conventions get crossed under deadline, and the resulting coupling is discovered a year later during a migration. Permissions make the boundary real at zero ongoing cost.

13Custom resources and eventing

The extensibility sub-area. It is asked less often, but when it comes up it is a strong differentiator, because the honest answer requires knowing that 13.0 removed lifecycle hooks and the publisher interfaces in favour of eventing and pipeline steps. If your Aspire experience is from 2024–2025, this is the sub-area most likely to expose it. Expect one definitional question and then an open design question about extending the platform for your organisation.

Docs: aspire.dev — Resource model examples for AppHost authors

seniorWhat is Aspire's eventing model, and what did it replace?

Answer

IDistributedApplicationEventing lets you subscribe to points in the application's and each resource's lifecycle: application-level events such as BeforeStartEvent and AfterEndpointsAllocatedEvent, and resource-level events such as InitializeResourceEvent, BeforeResourceStartedEvent, ConnectionStringAvailableEvent and ResourceReadyEvent. Handlers are async and can be registered globally or per resource. It replaced IDistributedApplicationLifecycleHook, which was removed in 13.0 — the hook interface had one coarse set of stages for the whole application, whereas eventing is per resource, ordered, and can await work. Practically you use it for anything that must happen at a precise moment: provisioning something external once a connection string exists, registering a resource with an internal catalogue when it becomes ready, or applying a company-wide convention across every resource in the graph.

Example

var db = builder.AddPostgres("pg").AddDatabase("catalogdb");

builder.Eventing.Subscribe<ResourceReadyEvent>(db.Resource, async (evt, ct) =>
{
    var logger = evt.Services.GetRequiredService<ILogger<Program>>();
    logger.LogInformation("catalogdb ready — applying dev grants");
    await DevGrants.ApplyAsync(evt.Resource, ct);
});

builder.Eventing.Subscribe<BeforeStartEvent>((evt, ct) =>
{
    // one convention applied to the whole model instead of forty call sites
    foreach (var r in evt.Model.Resources.OfType<ProjectResource>()) { /* … */ }
    return Task.CompletedTask;
});

Follow-ups

  • Does a handler block startup? — Yes, it is awaited at that point, so slow work delays the loop. Keep it fast or fire-and-forget deliberately.
  • Does eventing run in publish mode? — Application lifecycle events fire, but resources are not started, so resource-ready events do not. Guard on ExecutionContext.
  • What replaced WithPublishingCallback? — Pipeline steps; eventing is for run-time lifecycle, pipelines for publish/deploy.

Common wrong answer

"Implement IDistributedApplicationLifecycleHook." The canonical answer for 9.x, removed in 13.0 — this is the single sharpest recency test in the whole bank. If that is what you know, say so and name eventing as the replacement; the interviewer is often checking exactly that self-awareness.

seniorWrite the shape of a custom resource with a connection string.

Answer

Derive from ContainerResource (or Resource/ExecutableResource), implement IResourceWithConnectionString by exposing a ConnectionStringExpression built from ReferenceExpression and an EndpointReference, and provide an Add… extension that registers the resource with an image, endpoints and a health check. That is all it takes for WithReference, WaitFor, the dashboard and publish to work with it, because every consumer of the model programs against the interfaces rather than against concrete types. Add annotations for anything extra — icons, commands, relationships — and a matching client integration on the service side so consumers write one line.

Example

public sealed class VaultResource(string name) : ContainerResource(name), IResourceWithConnectionString
{
    internal const string HttpEndpointName = "http";
    private EndpointReference? _ep;
    private EndpointReference Endpoint => _ep ??= new(this, HttpEndpointName);

    public ReferenceExpression ConnectionStringExpression =>
        ReferenceExpression.Create($"{Endpoint.Property(EndpointProperty.Url)}");
}

public static class VaultBuilderExtensions
{
    public static IResourceBuilder<VaultResource> AddVault(
        this IDistributedApplicationBuilder builder, string name, int? port = null) =>
        builder.AddResource(new VaultResource(name))
               .WithImage("hashicorp/vault", "1.18")
               .WithHttpEndpoint(port: port, targetPort: 8200, name: VaultResource.HttpEndpointName)
               .WithHttpHealthCheck("/v1/sys/health")
               .WithEnvironment("VAULT_DEV_ROOT_TOKEN_ID", "dev-only-token");
}

Follow-ups

  • How do you make it publishable? — Give it publish behaviour through the compute environment's steps or PublishAsDockerFile; a dev-only resource can legitimately have none.
  • Where do annotations fit? — They are how the model carries metadata (health checks, commands, relationships, icons); most With… methods just add one.
  • Should you ship it internally? — Yes; a shared package beats ten copies, and it gives you one place to react to Aspire's quarterly changes.

Common wrong answer

"Return the connection string as a plain string property." It compiles and then bakes a builder-time value — usually empty, because endpoints are not allocated yet — into every consumer. The whole point of ReferenceExpression is deferral, which unit 02 covers.

seniorWhat is the Interaction Service, and what would you use it for?

Answer

It is the API that lets an AppHost or an integration ask the developer something — a prompt, a confirmation, a set of typed inputs, a file upload, a progress dialog — surfaced in the dashboard and the CLI. It was preview through 9.x/13.x and its core APIs became stable in 13.5, with a unified surface across C# and TypeScript. It is what makes aspire deploy able to ask for a subscription, and what lets your own resource commands take arguments (via CommandOptions.Arguments and InteractionInput). I use it for anything that would otherwise be an environment variable nobody sets: prompting for a missing parameter on first run, confirming a destructive reseed, or showing progress for a long-running seed so the dashboard does not look hung.

Example

db.WithCommand("reset", "Reset database",
    executeCommand: async ctx =>
    {
        var interaction = ctx.ServiceProvider.GetRequiredService<IInteractionService>();
        var confirm = await interaction.PromptConfirmationAsync(
            "Reset database", "This deletes all local data. Continue?", ct: ctx.CancellationToken);
        if (!confirm.Data) return CommandResults.Success();

        await Reset.RunAsync(ctx.ServiceProvider, ctx.CancellationToken);
        return CommandResults.Success();
    });

Follow-ups

  • What happens in CI, where nobody can answer? — Prompts must have non-interactive paths: supply values via parameters or flags, and fail fast rather than hanging a pipeline.
  • What did 13.5 add? — File imports and progress dialogs, plus API stabilisation and TypeScript parity.
  • Is it a good place for secrets? — For a one-off local value, yes — it can persist to user secrets; for anything shared, use the vault-backed bootstrap.

Common wrong answer

"It's the dashboard's notification system." Notifications are output; the Interaction Service is a request-response channel that blocks on a human. Confusing them leads to designs that hang unattended pipelines.

seniorHow do you model relationships and presentation so a 40-resource dashboard stays readable?

Answer

Use the model's presentation affordances rather than accepting a flat list. WithParentRelationship nests companion resources under their owner, so pgAdmin sits under Postgres and a migration job under its database instead of competing for top-level space. WithIconName and display names make scanning fast. WithHidden() and WithHiddenOnCompletion() (13.4) remove noise — a one-shot init container does not need to occupy a row forever. WithExplicitStart() keeps optional resources present but idle. And resource commands put the operations people actually perform on the resource itself. The principle: the dashboard is the primary UI for the system during development, so treat its information architecture as a design task, not as an accident of declaration order.

Example

var pg = builder.AddPostgres("pg").WithLifetime(ContainerLifetime.Persistent);
pg.WithPgAdmin(admin => admin.WithParentRelationship(pg));       // nested, not top-level

var seed = builder.AddProject<Projects.Seeder>("seed")
                  .WithParentRelationship(pg)
                  .WithExplicitStart()                            // present but not automatic
                  .WithHiddenOnCompletion();                      // 13.4: disappears when done

Follow-ups

  • Does presentation affect publish? — No; these are dashboard concerns. That separation is why using them freely is safe.
  • What about the graph view? — It reflects references and relationships, so modelling parents accurately makes the graph legible too.
  • Is hiding resources risky? — Hiding a resource that can fail silently is; hide completed one-shots, not long-running dependencies.

Common wrong answer

"The dashboard is what it is." It is configurable in exactly the ways that matter, and a team staring at forty undifferentiated rows every day is paying a real tax. This question is a proxy for whether you treat developer experience as engineering work.

principalDesign a platform layer on top of Aspire for twelve teams. What do you build?

Answer

Four artifacts, no more. First, an internal ServiceDefaults package — telemetry conventions, resilience, health semantics, auth defaults — versioned and centrally managed, replacing the copied template. Second, an internal hosting-integration package: AddContosoPostgres, AddContosoKafka and friends that encode the registry mirror, pinned tags, tags/policy via ConfigureInfrastructure, and health checks — so a team gets compliance by using the obvious API. Third, an AppHost template plus model tests that new services scaffold from, encoding the module structure and the naming contract. Fourth, an upgrade process: because only the newest Aspire release is supported, the platform team runs the next minor in CI ahead of teams, publishes a migration note, and lands automated PRs. What I would deliberately not build is a wrapper that hides Aspire's own API — abstractions over a fast-moving first-party platform become the thing that blocks upgrades, and the whole value proposition depends on staying current.

principalHow do you extend Aspire for a resource type it has no concept of — say an on-prem mainframe gateway?

Answer

Start by deciding what the model needs to know, which is usually less than people assume: an address, credentials, and a health signal. That is an external service or connection-string resource plus a health check — no container, no publish behaviour — and it takes ten lines. Locally you point it at a stub (WireMock, or a recorded-response container) so developers are not dialling into a mainframe; in publish mode it becomes a parameter-supplied endpoint the platform provides. Where I would invest further is in an eventing subscriber that validates connectivity at start and fails loudly with a good message, because the failure mode for these dependencies is a five-minute timeout with no explanation. What I would not do is model the mainframe itself: the app model should describe what the application depends on, not everything that exists.

Example

var gwUrl = builder.AddParameter("mainframe-gateway-url");

var gateway = builder.ExecutionContext.IsRunMode
    ? builder.AddContainer("mainframe-gw", "wiremock/wiremock", "3.9.1")
             .WithHttpEndpoint(targetPort: 8080, name: "http")
             .WithBindMount("./stubs/mainframe", "/home/wiremock")
             .GetEndpoint("http")
    : builder.AddExternalService("mainframe-gw", gwUrl).GetEndpoint("https");

builder.AddProject<Projects.Billing>("billing").WithReference(gateway);

Follow-ups

  • How do you keep the stub honest? — Generate it from a contract (OpenAPI, recorded traffic) and run a scheduled contract test against the real gateway.
  • What if it needs a VPN? — That is a platform concern; model the endpoint and let connectivity be an environment property, or the local loop becomes VPN-dependent for everyone.
  • When would you write a full custom resource instead? — When more than one team needs it and it has real lifecycle (start, health, commands) worth encoding.

Common wrong answer

"Write a full custom resource with a container image for it." Over-engineering: the mainframe is not going to run on a laptop, and a heavyweight resource for something with no lifecycle is maintenance for nothing. Choosing the smallest sufficient model is the judgment being tested.

14Polyglot and container resources

Since the 13.0 rebrand this is no longer a footnote, and interviewers use it to check whether your knowledge is current. The content: how Python, JavaScript/TypeScript and Go resources are modelled, what happens to them at publish time, and what the practical limits are. It comes up most in orgs that are not .NET-only, which is exactly where the "should we adopt Aspire" conversation is hardest.

Docs: aspire.dev — What's new in Aspire 13

midHow do you add a Node or Python app to the model, and what changed in 13.0?

Answer

13.0 renamed the package Aspire.Hosting.NodeJs to Aspire.Hosting.JavaScript and replaced AddNpmApp with AddJavaScriptApp, which auto-detects the package manager (npm, yarn, pnpm, and Bun since 13.3/13.4) and takes an app directory plus a script name. Python got first-class support with AddPythonModule, AddUvicornApp and package management through uv, pip or venv, plus automatic Dockerfile generation for production. 13.4 added Go through Aspire.Hosting.Go/AddGoApp() with build options, and AddBunApp(). All of them receive the same injected environment as a .NET project — service discovery variables, connection strings, the OTLP endpoint — so the polyglot part is genuine rather than cosmetic; what differs is that the language's own OpenTelemetry SDK must be configured to use the endpoint.

Example

var api = builder.AddProject<Projects.Api>("api");

builder.AddJavaScriptApp("web", "../web", "dev")     // 13.0: was AddNpmApp
       .WithReference(api)
       .WithHttpEndpoint(env: "PORT")
       .WithExternalHttpEndpoints();

builder.AddUvicornApp("scoring", "../scoring", "main:app").WithReference(api);
builder.AddGoApp("edge", "../edge").WithReference(api);   // 13.4

Follow-ups

  • How does the JS app learn its port? — WithHttpEndpoint(env: "PORT") injects the allocated port under the variable the dev server reads; hard-coding it reintroduces collisions.
  • What about publishing a SPA? — The PublishAs* family (13.3) covers static SPAs, SSR Node servers and npm-script deployments; PublishAsNpmPackageScript was renamed PublishAsPackageScript in 13.4.
  • Certificates? — 13.0 added automatic certificate trust for Python, Node and containers; 13.5 added WithHttpsDeveloperCertificate().

Common wrong answer

"Use AddNpmApp." Deprecated at 13.0 in favour of AddJavaScriptApp, and the package id changed too — so this answer both fails to compile on a current AppHost and dates you precisely.

midHow do you run an arbitrary container, and what are the essential knobs?

Answer

AddContainer(name, image, tag), then compose: WithHttpEndpoint/WithEndpoint for ports, WithEnvironment for configuration (including deferred expressions referencing other resources), WithBindMount/WithVolume for storage, WithArgs for command-line arguments, WithImageRegistry for an internal mirror, WithLifetime for persistence, WithHttpHealthCheck so WaitFor means something, and WithContainerFiles (13.x) to inject files without a bind mount. Always pin the tag. That set covers essentially every third-party container people add — Mailpit, WireMock, Keycloak, MinIO, Kafka UI — and if you find yourself needing more, it is usually a sign the thing deserves a proper integration.

Example

var kc = builder.AddContainer("keycloak", "quay.io/keycloak/keycloak", "26.0")
                .WithImageRegistry("contoso.azurecr.io")
                .WithHttpEndpoint(targetPort: 8080, name: "http")
                .WithEnvironment("KEYCLOAK_ADMIN", "admin")
                .WithEnvironment("KEYCLOAK_ADMIN_PASSWORD", builder.AddParameter("kc-pw", secret: true))
                .WithArgs("start-dev", "--import-realm")
                .WithBindMount("./realms", "/opt/keycloak/data/import")
                .WithLifetime(ContainerLifetime.Persistent)
                .WithHttpHealthCheck("/health/ready");

Follow-ups

  • Bind mount versus volume? — Bind mount for repo-provided files you edit; volume for data. Bind mounts are noticeably slower on macOS and Windows.
  • How does the container reach a project? — Reference the project's endpoint through the model; the orchestrator injects a host-reachable address, not localhost.
  • Multi-arch images? — Check arm64 support before standardising, or half the team runs everything under emulation.

Common wrong answer

"Use latest and move on." Unpinned tags mean the graph changes under you without a commit, which is precisely the drift Aspire exists to remove — and it makes "works on my machine" unfalsifiable.

seniorWhat happens to a Python or Node resource at publish time?

Answer

It has to become a container image, so the integration either generates a Dockerfile (Python support includes automatic production Dockerfile generation; JavaScript has container-based build pipelines) or uses one you provide with PublishAsDockerFile(). For a static SPA the PublishAs* family emits a build-and-serve arrangement rather than a Node process. The important senior caveat: generated Dockerfiles are a starting point, not a production artifact — they may not match your base-image policy, your non-root user requirement, your layer-caching needs or your vulnerability-scanning baseline. So my default is to let Aspire generate one to learn the shape, then check in an owned Dockerfile and point the resource at it, which keeps image policy where the security team can review it.

Example

builder.AddJavaScriptApp("web", "../web", "dev")
       .WithExternalHttpEndpoints()
       .PublishAsDockerFile(df => df.WithDockerfile("../web", "Dockerfile.prod"));

Follow-ups

  • Where does the build happen? — In the publish/deploy pipeline; in CI you typically build and push images yourself and pass the tag as a parameter for reproducibility.
  • Does the executable resource publish at all? — Not on its own; a bare AddExecutable has no publish behaviour until you give it one.
  • How do you enforce base images? — Own the Dockerfiles, or add a pipeline step that scans and fails on policy violations.

Common wrong answer

"Aspire containerises it automatically, so we're done." It generates something runnable, not something compliant. Shipping a generated Dockerfile to production without review is how you end up running as root on an unpatched base image.

seniorWhat are the real limits of Aspire in a polyglot shop today?

Answer

Three, honestly stated. First, depth of support is uneven: .NET gets projects with debugger attach and the richest integrations; JavaScript, Python and Go get solid hosting support but you configure their telemetry yourself and the client-integration ecosystem is .NET-only, so the "batteries included" experience is asymmetric. Second, the toolchain: even with the TypeScript AppHost GA in 13.4 and the CLI on npm in 13.5, orchestrating .NET projects still means a .NET SDK, and the deep customisation APIs (especially Azure provisioning) lead in C#. Third, culture: the AppHost is one shared file that every team edits, and in a polyglot org it will be owned by the group most comfortable with its language. My recommendation in such a shop is to adopt Aspire where the .NET services are, use it as a Compose or Helm generator for the rest, and revisit once your specific gaps close — the release notes move fast enough that "not yet" is often "not this quarter".

principalYour frontend team wants to own the AppHost in TypeScript; your backend team wants C#. Decide.

Answer

One AppHost, one language, chosen by who maintains it most — and I would document the decision rather than let it be settled by whoever commits first. The technical inputs: C# still leads on new APIs and Azure customisation, so if the model does heavy provisioning work, C# is lower-friction; TypeScript reached GA in 13.4 with real parity for the common surface, so if the majority of the resources and the people are JS, TypeScript is the better home. The organisational input dominates though: the AppHost is a shared file with a merge-conflict surface, and a model owned by a team that cannot read it becomes stale and defensive. If both teams genuinely need to evolve it independently, that is a signal to split by ownership boundary — two AppHosts, each in its own language, with the cost being that you lose the single-dashboard cross-service trace, which I would weigh explicitly rather than assume away.

Example

// apphost.mts — viable as the single model since 13.4 GA
import { createBuilder } from "@aspire/hosting";
const builder = createBuilder();
const db  = builder.addPostgres("pg").addDatabase("catalogdb");
const api = builder.addProject("api", "../Api/Api.csproj").withReference(db).waitFor(db);
builder.addJavaScriptApp("web", "../web", "dev").withReference(api).withExternalHttpEndpoints();
await builder.build().run();

Follow-ups

  • Can the two languages coexist in one repo? — Technically yes; it doubles the toolchain for one artifact, which is rarely worth it.
  • What if the choice turns out wrong? — Porting an AppHost is a day of work — the model is small and the APIs mirror each other. Say that: it lowers the stakes of the decision.
  • How do you avoid merge conflicts either way? — Module extension functions per bounded context, so teams edit different files.

Common wrong answer

"C#, because Aspire is a .NET product." That was true before 13.0 and is now both wrong and politically tone-deaf in a polyglot org. Equally weak is deciding purely on team preference without naming the API-parity trade-off.

15Kubernetes and Docker Compose targets

A small but sharply discriminating sub-area: it was preview or absent before 13.3, so answers here reveal how current you are. Interviewers want to know what Aspire generates for each target, what it does not do, and how the generated artifact fits an existing platform. Four questions, all senior-flavoured.

Docs: aspire.dev — Deploy with Aspire

seniorWhat does Aspire generate for a Kubernetes target?

Answer

Since 13.3 it generates a complete Helm chart from the app model and can apply it end-to-end against your current kubectl context, with no separate manifest tooling. Ingress and Gateway API routing are modelled as first-class resources in the AppHost, and 13.4 added AddHelmChart() for composing existing charts, WithHelm() for consolidated configuration, cert-manager integration, and Azure Application Gateway for Containers. Two 13.4 breaking changes matter in practice: WithRoute() became WithPath() for ingress, and routed endpoints now require WithExternalHttpEndpoints(). 13.5 added experimental persistent volumes via AddPersistentVolume(). AKS gets the additional ability to provision the cluster itself rather than only deploying to it.

Example

var k8s = builder.AddKubernetesEnvironment("cluster");

builder.AddProject<Projects.Api>("api")
       .WithComputeEnvironment(k8s)
       .WithExternalHttpEndpoints();      // required for routed endpoints since 13.4

builder.Build().Run();
// aspire publish -o ./chart   → Helm chart
// aspire deploy               → helm install/upgrade against the current context

Follow-ups

  • Is the chart production-ready? — It is a good starting point; resource requests/limits, PodDisruptionBudgets, network policies and affinity rules are yours to add or to layer on.
  • Where do you customise? — In the model where the API exists, and through chart values otherwise; hand-editing generated files loses on regeneration.
  • Stateful workloads? — AddPersistentVolume() is experimental in 13.5; managed services referenced by connection string remain the safer answer.

Common wrong answer

"It emits raw YAML manifests you apply with kubectl." That was roughly the 9.x preview shape; the current mechanism is Helm, and knowing that is the point of the question.

seniorWhen is Docker Compose the right publish target?

Answer

When the runtime is a single machine: an on-prem box, an edge device, a customer-hosted appliance, a demo environment, or a CI job that needs the stack up. AddDockerComposeEnvironment emits a compose.yaml plus a .env with the parameters left unresolved, which is exactly the handoff you want for something an operator will run. It is also the honest answer for teams without Kubernetes capability: a well-run Compose deployment on a maintained VM beats a badly-run cluster. What you give up is scheduling, self-healing beyond restart policies, rolling updates and horizontal scale — so I would name a growth path at the same time, which is easy here because the same model retargets to Kubernetes or ACA by swapping the compute environment.

Example

var compose = builder.AddDockerComposeEnvironment("edge");

builder.AddProject<Projects.Api>("api").WithComputeEnvironment(compose).WithExternalHttpEndpoints();
builder.AddPostgres("pg").WithDataVolume();

// aspire publish -o ./out  → out/compose.yaml + out/.env (parameters unresolved)

Follow-ups

  • How do secrets work? — As .env entries or Compose secrets; the published file carries placeholders, and the operator supplies values.
  • Can you hand-edit the output? — You can, and then you own it. Prefer model changes so regeneration stays viable.
  • What about the dashboard there? — Add the standalone dashboard container if you want telemetry on the box; it is a normal image.

Common wrong answer

"Compose is only for local dev." A very large amount of software runs on one well-maintained VM, and dismissing that target reads as inexperience with anything outside a hyperscaler.

seniorHow do you handle Kubernetes concerns the model has no opinion about — requests/limits, PDBs, network policy?

Answer

Three layers, chosen by who owns the concern. Anything the app knows about — resource requests based on its own profiling, readiness probe paths, replica floors — I set in the model where the API exists, or via chart values that the model emits. Anything the platform owns — network policy, PodSecurity standards, node affinity, PDB defaults — belongs to the cluster's admission and policy layer (Kyverno/Gatekeeper, default PDBs by label), so it applies to every workload regardless of who generated the chart, including the ones Aspire did not. Anything in between goes into a thin wrapper chart that takes Aspire's chart as a dependency, which keeps regeneration intact. What I avoid is patching generated files, because the next aspire publish silently deletes the patch.

Example

# wrapper chart: keep the generated chart as a dependency, add platform concerns around it
dependencies:
  - name: contoso-orders          # the Aspire-generated chart
    version: "0.1.0"
    repository: "file://./generated"
# templates/pdb.yaml, templates/networkpolicy.yaml live here, not in the generated chart

Follow-ups

  • How do you set requests/limits from the model? — Through chart values the model exposes; where an API is missing, values-file overrides in the wrapper chart.
  • Does this defeat "one source of truth"? — Partly, and deliberately: app topology in the model, cluster policy in the cluster. That split is defensible; a patched generated file is not.
  • How do you catch drift? — GitOps diffing plus admission policy failing non-compliant workloads at apply time.

Common wrong answer

"Post-process the generated YAML with kustomize patches." It works until the generator's output shape changes in the next minor and the patch silently no-ops or mis-targets. A dependency chart or policy-layer answer survives upgrades; a patch does not.

principalWould you adopt Aspire's Kubernetes deployment for a team already running Kubernetes well?

Answer

Usually no for the deploy path, and yes for everything else. A team running Kubernetes well already has a chart library, values conventions, GitOps, policy enforcement and an on-call runbook; replacing the chart source with a generator adds a new failure mode — an Aspire minor changing generated output — in exchange for a benefit they already have. What I would adopt is the AppHost for the local loop, which is where their pain actually is, and possibly aspire publish as an input to a chart review rather than as the deployed artifact. The condition under which I would change my mind: if their charts have drifted from the code so badly that nobody trusts them, then generating from the model is a genuine correctness improvement, and the migration cost is worth paying once. Either way I would say the quiet part out loud — Aspire's Modern Lifecycle support means the generator is a dependency you must upgrade quarterly, and a platform team should price that before putting it in the deployment path.

16Security and hardening

Asked in any loop with a security-minded interviewer, and a reliable way to separate people who have deployed Aspire from people who have demoed it. The testable content: the dashboard as an attack surface, secrets in environment variables, the supply chain of container images the model pulls, and what Aspire deliberately does not secure.

Docs: aspire.dev — Dashboard configuration and security

midWhat is the security posture of the dashboard, locally and deployed?

Answer

Locally it binds to loopback and uses a browser token in the launch URL, which is appropriate for a single-developer machine and inappropriate for anything shared — on a shared dev box or a VM with a public interface it becomes a credential dump, because the resource details view shows every environment variable including injected connection strings. Deployed, the standalone dashboard supports token or OpenID Connect authentication for the frontend (Dashboard:Frontend:AuthMode) and API-key or client-certificate authentication for the OTLP ingestion endpoint (Dashboard:Otlp:AuthMode). The rule I state plainly: treat the dashboard as an administrative console. Never expose it unauthenticated, never on a public address, and review the fact that ACA deployments include it by default before that reaches production.

Example

Dashboard__Frontend__AuthMode=OpenIdConnect
Dashboard__Otlp__AuthMode=ApiKey
Dashboard__Otlp__PrimaryApiKey=…
ASPNETCORE_URLS=http://+:18888          # behind an internal ingress only
# Dashboard__Frontend__AuthMode=Unsecured  ← only ever on loopback

Follow-ups

  • Why is the OTLP endpoint a risk too? — Unauthenticated ingestion lets anyone inject or flood telemetry, and telemetry drives your incident response.
  • What about the resource commands? — A deployed dashboard with custom commands is remote code execution by design; do not ship destructive commands.
  • Is there RBAC? — No per-resource authorization model; it is all-or-nothing per user. That alone rules it out as a shared production console for many orgs.

Common wrong answer

"It's local-only, so it's not a security concern." It is deployable, it is deployed by default in ACA publishing, and it shows secrets. "Local-only" is the assumption that puts an unauthenticated environment-variable browser on a routable address.

seniorSecrets arrive as environment variables. What are the consequences and what would you do instead?

Answer

Environment variables are readable by anything in the process, by anything that can inspect the container, by crash dumps and by diagnostic tooling — including the Aspire dashboard's resource view — and they are set once at start, so rotation means a restart. That is acceptable for most values and unacceptable for the highest-sensitivity ones. What I do instead: prefer identity over secrets wherever the platform supports it (managed identity plus DefaultAzureCredential, so there is nothing to leak); use platform secret references (Key Vault references, Kubernetes secrets mounted as files with a refresh mechanism) rather than literals; and for values that must rotate without downtime, retrieve at runtime through a client that caches with a TTL. Aspire is fine with all of these — the model injects a vault URI or a secret reference rather than a value — so the constraint is the platform's, not the tool's.

Example

// Inject an identity-scoped endpoint, not a credential.
var kv = builder.AddAzureKeyVault("secrets");
builder.AddProject<Projects.Api>("api").WithReference(kv);

// Service: no secret in the environment at all.
builder.Configuration.AddAzureKeyVault(
    new Uri(builder.Configuration["ConnectionStrings:secrets"]!), new DefaultAzureCredential());

Follow-ups

  • Does Aspire ever write secrets to disk? — Locally, user secrets (already a developer-scoped store); artifacts carry placeholders, not values — and if a published artifact ever contains a resolved secret, treat it as a bug.
  • What about the dashboard masking? — Parameters marked secret: true are masked in the parameter view, but a secret injected as an environment variable is still visible in that resource's environment.
  • Rotation without restart? — Runtime retrieval with a cache, or a sidecar/CSI driver that refreshes a mounted file; not something environment variables can do.

Common wrong answer

"Environment variables are the standard, so they're fine." They are the pragmatic default and they have specific, well-known weaknesses. An answer with no awareness of those weaknesses is what a security interviewer is listening for.

seniorWhat is Aspire's supply-chain surface, and how do you control it?

Answer

Three surfaces. NuGet packages: the hosting and client integrations, plus community ones, which get the same review as any dependency, with Central Package Management so versions move in one place. Container images: every hosting integration pulls an image with a default tag, so by default your developers' machines and your Compose output pull from public registries — mirror them to an internal registry with WithImageRegistry, pin tags, and scan them. And the tooling itself: the CLI, the templates and the closed-source DCP binaries, which come from Microsoft feeds and should be pinned per repo (the 13.5 CLI bundle and aspire.config.json make that straightforward). The failure I have actually seen is the middle one: a team hits Docker Hub rate limits or pulls an image whose default tag moved, and discovers there was no policy at all.

Example

public static IResourceBuilder<T> Mirrored<T>(this IResourceBuilder<T> b)
    where T : ContainerResource => b.WithImageRegistry("contoso.azurecr.io");

var redis = builder.AddRedis("cache").Mirrored().WithImageTag("8.0");
var pg    = builder.AddPostgres("pg").Mirrored().WithImage("library/postgres", "17.6");

Follow-ups

  • How do you find every image in use? — Walk the model in a test and assert registry and tag; that inventory doubles as a scanning input.
  • Are the images signed? — Verify what your registry and policy support; do not assume a default tag from a public registry carries provenance.
  • What about the generated Dockerfiles? — Their base images are your responsibility; own the Dockerfile if base-image policy matters.

Common wrong answer

"We scan our NuGet packages, so we're covered." Half the surface. The images an AppHost pulls are code executing on every developer machine and, for some targets, in production — and nothing scans them unless you arrange it.

seniorDoes Aspire provide any network isolation between resources?

Answer

No, and saying so quickly is the right answer. Locally everything runs on the developer's machine with ports on the host or on a shared container network; there is no policy layer, and any process on that machine can reach any resource. In deployed environments isolation is entirely the platform's: ACA internal ingress and VNet integration, Kubernetes NetworkPolicy, private endpoints, subnets and NSGs. Aspire's model influences this only where it declares intent — WithExternalHttpEndpoints() marks what should be publicly routable, and everything else is internal by default on targets that support the distinction. So the correct framing is that the model expresses intent and the platform enforces it; if you need enforcement locally, you are asking the wrong tool.

Example

builder.AddProject<Projects.Web>("web").WithExternalHttpEndpoints();   // public
builder.AddProject<Projects.Api>("api");                              // internal only
builder.AddPostgres("pg");                                            // never routable

Follow-ups

  • Is the local exposure a real risk? — On a laptop, low; on a shared build agent or a jump box, real — dev databases with default credentials on a routable interface.
  • What enforces service-to-service auth? — Your application (tokens, mTLS) or the platform/mesh; there is no Aspire-level authorization.
  • Private endpoints? — Configured in the model via ConfigureInfrastructure or owned by the platform's IaC; 13.5 also added VNet delegation support.

Common wrong answer

"Resources are isolated because each is a container." Containers are a packaging boundary, not a network policy. This answer is how a dev environment ends up with a Postgres reachable from the office network.

principalA pen test flags the Aspire dev environment. What is your remediation plan?

Answer

I would triage into three buckets and fix the class, not the finding. Exposure: nothing binds beyond loopback on developer machines, no shared dev box runs an AppHost with real credentials, and any deployed dashboard sits behind OIDC on a private network — enforced by configuration defaults in the template rather than by a policy document. Credentials: dev credentials are generated per developer rather than shared, no production credentials exist in any developer's user secrets, and the vault-backed bootstrap is the only sanctioned way to obtain values; rotate anything the test found. Supply chain: images mirrored and pinned, packages centrally managed, scanning wired into CI. Then the structural fix — a hardened AppHost template plus a CI check for the specific anti-patterns (unpinned tags, Unsecured dashboard auth, secrets in appsettings) — so the next audit finds fewer instances of the same class. And I would push back on one framing: a developer laptop is not a production environment, so remediation should be proportionate, or the team quietly routes around it.

Example

# CI guardrails for the classes, not the instances
grep -R "Unsecured"        --include=*.json  . && exit 1     # dashboard auth
grep -RE "WithImageTag\(\"latest\"\)" --include=*.cs . && exit 1
grep -RE "\"(Password|ApiKey)\"\s*:" --include=appsettings*.json . && exit 1

Follow-ups

  • What if the finding is "the dashboard shows secrets"? — Working as designed; the remediation is access control around the dashboard, not a change to the dashboard.
  • How do you handle shared dev environments? — Treat them as production for access-control purposes: authenticated dashboard, no real credentials, separate low-privilege identities.
  • Who owns this? — The platform team owns the template and the guardrails; individual teams own their own findings.

Common wrong answer

"It's dev, we'll accept the risk." Sometimes correct as a decision, never correct as an answer without naming what is being accepted and by whom. The expected principal answer converts findings into guardrails and states the proportionality argument explicitly.

17Versions, upgrades and support policy

Rarely asked directly, but a strong signal when it comes up: it separates people who have run Aspire for a year from people who tried it once. The content is small and specific — the version history, the support policy, the upgrade mechanics — and it is the fastest way to demonstrate that you are current.

Docs: aspire.dev — Aspire support policy

midWhat is Aspire's support policy, and what does it mean operationally?

Answer

Modern Lifecycle: only the latest release is supported, and to be in support you must be on the latest servicing level of it. There is no LTS and no STS designation, and the cadence is roughly one major a year with minors through the year — 13.0 in November 2025, then 13.1 through 13.5 by August 2026. Operationally that means an upgrade is not an optional improvement, it is maintenance: budget a slot every quarter, keep versions centrally managed so the bump is one property, and read the breaking-changes page each time (13.4 alone removed aspire exec, renamed WithRoute and moved the default Postgres image). For a team that cannot upgrade quarterly, that is a genuine argument against putting Aspire in the deployment path — the local loop is more forgiving than the generator.

Example

aspire update --self        # the CLI
aspire update               # the repo's Aspire packages, CPM-aware
aspire update --migrate     # 13.5: apply migrations for known breaking changes
aspire doctor               # verify SDK/CLI/runtime/DCP afterwards

Follow-ups

  • Can you stay on 13.3 for a year? — Technically it keeps working; you are simply unsupported, and you accumulate a larger upgrade later.
  • How do you reduce upgrade risk? — Model tests and artifact snapshot tests, so the diff is visible; a canary repo that upgrades first.
  • Does this apply to the client integrations too? — Same versioning and the same policy; keep them aligned with the hosting packages.

Common wrong answer

"It follows .NET's LTS cycle." It explicitly does not, and that decoupling is the reason for the 9.5 → 13 jump. Assuming three years of support for the version you shipped on is a planning error with real consequences.

midWalk through upgrading a solution from Aspire 9.x to 13.x.

Answer

Run aspire update first — it is the recommended path and handles Central Package Management — then fix what it cannot. The project file changes shape: Sdk="Aspire.AppHost.Sdk/13.5.0" on the <Project> element, drop the explicit Aspire.Hosting.AppHost package (the SDK includes it), and retarget from net9.0 to net10.0. Then the code: lifecycle hooks are gone (move to eventing), the publisher interfaces are gone (move to pipeline steps), AddNpmApp becomes AddJavaScriptApp and its package id changes to Aspire.Hosting.JavaScript, and the Node signature now takes an app directory with relative script paths. If you are coming from 8.x, uninstall the old workload (dotnet workload uninstall aspire) first. Finally refresh templates (dotnet new install Aspire.ProjectTemplates) and re-run your model and snapshot tests to see what the generated artifacts now look like.

Example

<!-- before (9.x) -->
<Project Sdk="Microsoft.NET.Sdk">
  <Sdk Name="Aspire.AppHost.Sdk" Version="9.5.0" />
  <PropertyGroup><TargetFramework>net9.0</TargetFramework></PropertyGroup>
  <ItemGroup><PackageReference Include="Aspire.Hosting.AppHost" Version="9.5.0" /></ItemGroup>
</Project>

<!-- after (13.x) -->
<Project Sdk="Aspire.AppHost.Sdk/13.5.0">
  <PropertyGroup><TargetFramework>net10.0</TargetFramework></PropertyGroup>
</Project>

Follow-ups

  • Biggest source of work? — Custom extensions: anything built on lifecycle hooks or publishers has no drop-in replacement, only a redesign onto eventing and pipeline steps.
  • What about data volumes? — Pin image tags before upgrading, or a default image major bump (Postgres 17.6 → 18.3 in 13.4) breaks every developer's volume.
  • How do you sequence it across a monorepo? — One PR that bumps the central version and fixes the AppHost, behind a green model/snapshot test suite.

Common wrong answer

"Bump the package versions and rebuild." It will not build — the SDK declaration moved and the target framework floor changed — and if it did, the removed APIs would surface at runtime. The upgrade is mechanical but not trivial, and knowing which parts are mechanical is the answer.

seniorHow do you keep an estate of 30 repos on the same Aspire version?

Answer

Centralise the number, automate the bump, and stage the rollout. Central Package Management with a single AspireVersion property per repo, plus the SDK version pinned in aspire.config.json/global.json and the CLI pinned via the 13.5 bundle, means a repo is upgraded by changing one place. A bot opens the PR on all thirty when a release ships. The platform team runs the new version first in a canary repo with model and snapshot tests, publishes a short migration note naming the breaking changes that actually affect us, and only then lets the bot loose. Repos that fail get triaged centrally rather than left to each team, because the failure is usually the same one thirty times. The metric I track is lag: days between an Aspire release and the last repo being on it — if that exceeds a quarter, the estate is structurally unsupported.

Example

// aspire.config.json — SDK, launch profiles and pins in one rooted file (13.2+)
{
  "sdk": { "version": "13.5.0" },
  "appHostPath": "./src/AppHost/AppHost.csproj"
}

Follow-ups

  • What if one repo cannot upgrade? — Make it explicit and time-boxed with an owner, not a quiet exception; unsupported infrastructure code should be visible on a dashboard.
  • Do you upgrade on day one? — No: canary first, estate within a few weeks. Day-one upgrades of a fast-moving product buy you the bugs.
  • Who reads the breaking changes? — The platform team, once, and translates them into a note. Thirty teams reading the same page is waste.

Common wrong answer

"Dependabot will handle it." It opens PRs; it does not read breaking changes, sequence a canary, or fix thirty identical build failures. Automation is the cheap part, and answering only with automation is what makes the estate drift.

principalHow do you present Aspire's support policy to a risk-averse stakeholder?

Answer

By scoping the risk to where it actually is. Aspire is Modern Lifecycle with no LTS, so I present it as two different decisions. The dev-loop decision carries low risk: nothing Aspire-specific runs in production, the exit cost is deleting an AppHost, and an upgrade that breaks the local loop costs a day, not an outage. The deployment-path decision carries the real risk: a generator you must upgrade quarterly sits between your code and your infrastructure, and its output changes between minors. I would quantify the mitigation — snapshot tests over generated artifacts, a canary repo, one platform engineer-week per quarter — and I would name the fallback explicitly: the generated Bicep and charts are ordinary files, so if we ever need to stop, we own the last output and continue. Stakeholders accept a policy risk far more readily when there is a stated exit and a costed maintenance line, and refusing to state either is what turns a technology choice into a trust problem.

  • What if they ask for a guarantee of five years? — There is none, and saying so is better than implying one; the mitigation is the exit path, not a promise.
  • How does this compare to other dependencies? — Many popular OSS dependencies have weaker guarantees; the difference is that this one is visible because Microsoft publishes the policy.
  • Would you write it into an ADR? — Yes, with the review date tied to the next major.

Common wrong answer

"It's Microsoft, it'll be supported." Microsoft publishes a policy that says the opposite of what that reassurance implies, and a stakeholder who later discovers the gap will discount everything else you told them.

18CI/CD, performance and cost

Rarely the focus of a whole section, but the questions here differentiate: they are about the second-order costs of the thing you just advocated. Interviewers want to see that you think about build times, CI minutes, cloud spend and developer time as first-class constraints rather than afterthoughts.

Docs: aspire.dev — Deploy with Aspire (pipelines and steps)

seniorWhat does an Aspire-aware CI pipeline look like?

Answer

Four stages, and the ordering matters for feedback speed. Build and unit tests, no containers, fastest signal. Model and artifact tests — build the AppHost model, assert the conventions, run aspire publish and snapshot-diff the output — still seconds, and it catches infrastructure regressions before anything is deployed. Integration tests with the container-backed graph, on a runner with a warm image cache, scoped to a handful of journeys. Then publish or deploy: aspire publish to produce reviewable artifacts, and either aspire deploy or your existing release process. The pinned CLI matters here: use the repo's version (the 13.5 CLI bundle or an explicit install step) so CI and laptops generate identical output.

Example

jobs:
  build:
    steps:
      - run: dotnet test ./tests/Unit
      - run: dotnet test ./tests/Model            # model + snapshot assertions
      - run: aspire publish -o ./artifacts --environment Staging
      - uses: actions/upload-artifact@v4
        with: { name: manifests, path: ./artifacts }
  integration:
    needs: build
    steps:
      - run: docker pull postgres:17.6 && docker pull redis:8.0   # warm the cache
      - run: dotnet test ./tests/Integration

Follow-ups

  • Why snapshot the artifacts? — An Aspire upgrade can change generated output; a diff in a PR is far better than a surprise at deploy.
  • Which stage gates the PR? — The first two always; integration on merge or on a label if it is slow.
  • How do you pin the CLI in CI? — The repo's CLI bundle, or an explicit versioned install; never "latest" in a pipeline that produces artifacts.

Common wrong answer

"Just run dotnet test and aspire deploy." No artifact review, no model assertions, and a deploy that is the first place anyone sees the generated infrastructure. The stages exist to move failure earlier.

seniorWhat does Aspire cost you in CI minutes, and how do you control it?

Answer

The dominant cost is container-backed integration tests: image pulls, container starts and health waits, paid on every run. Controls, in order of effect: cache or pre-bake images on the runner (a runner image with your dependencies baked in is the single biggest win); share one application instance across a test collection instead of per test; run the full-graph suite on merge and nightly rather than on every PR; and trim the test AppHost to the resources the tests need. Second-order costs are container registry egress if you are not mirroring, and cloud spend for any integration environment that aspire deploy creates and nobody destroys — which is why a sweeper job matters more than teardown-on-close. I would put a number on it before optimising: measure minutes per PR and per month, because the fix is often "move one suite off the PR gate", not an architecture change.

Example

- name: Cache container images
  run: |
    docker pull contoso.azurecr.io/library/postgres:17.6
    docker pull contoso.azurecr.io/library/redis:8.0
# and: full-graph suite only on main + nightly
on:
  push: { branches: [main] }
  schedule: [{ cron: "0 2 * * *" }]

Follow-ups

  • Does aspire publish cost anything? — Seconds; it is a pure model-to-artifact transform, which is why it belongs on the PR gate.
  • Where does cloud spend leak? — Abandoned preview environments and per-developer Azure resources created by run-mode provisioning. Both need sweepers.
  • Self-hosted runners? — Often the right answer when image pulls dominate, because the cache persists between runs.

Common wrong answer

"CI minutes are cheap." They are cheap per minute and expensive in aggregate — and the real cost is queue time blocking developers, which is what makes teams start skipping the suite. Naming developer wait time rather than the invoice is the stronger answer.

seniorDoes Aspire have any production runtime performance impact?

Answer

The AppHost, no — it does not run in production. What can have impact is what ServiceDefaults switched on: OpenTelemetry instrumentation adds per-request work and allocation, unsampled tracing is expensive at high throughput, health endpoints that check every dependency cost connections, and the standard resilience handler adds retries that multiply load on a struggling dependency if it is not configured with care. None of these are Aspire-specific, and all of them are defaults that are correct for development and need tuning for production scale: sample traces, cache health results, and set retry budgets and circuit breakers deliberately. The honest summary is that Aspire's production cost is the cost of the observability and resilience you would otherwise have added yourself — plus the risk of never revisiting its defaults.

Example

# production defaults worth setting explicitly
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.05
OTEL_METRIC_EXPORT_INTERVAL=60000

Follow-ups

  • How much does tracing cost? — Measure it; a few percent CPU is typical, but high-cardinality attributes and 100% sampling on a hot path can be much worse.
  • Retry amplification? — Three retries across three hops is up to 27 requests from one; circuit breakers and retry budgets exist for that reason.
  • Is service discovery a hot path cost? — Negligible; it is cached configuration lookup, not a network call per request.

Common wrong answer

"None, Aspire is dev-only." Correct about the AppHost and wrong about the outcome — the template put instrumentation and retry policies into every service, and those absolutely have production characteristics. The nuance is the answer.

principalJustify Aspire's cost to a CTO who sees it as a developer toy.

Answer

With numbers on both sides. Benefit: onboarding time from days to hours (measure it on the next three hires), local start time and the number of starts per developer per day, incident time saved by having distributed traces from day one rather than added after the first outage, and the elimination of drift between a compose file and reality. Cost: a quarterly upgrade slot, container-runtime licensing if applicable, CI minutes for container-backed tests, and the learning curve for the app model. I would frame the decision as two separable bets, as in unit 17, and recommend the low-risk one first — adopt the dev loop, keep the deployment pipeline — so the payoff arrives before the commitment deepens. And I would name the honest failure mode: if the team's real bottleneck is production reliability or requirements churn, Aspire will not touch it, and adopting it will look like activity rather than progress.

  • What is the strongest argument against? — Support policy and cadence; put it in the proposal rather than waiting to be asked.

Common wrong answer

"It's the Microsoft-recommended way to build cloud-native .NET apps." Appeal to authority with no numbers, and it invites the reply "so was every previous recommended way". Executives fund measured bets with stated exits, not endorsements.

19AI agents and MCP

New, rarely load-bearing, and a cheap way to show you follow the product: 13.0 added Model Context Protocol integration, 13.1 expanded it, and 13.2 added aspire agent and WithMcpServer(). Three questions is the right size — enough to answer credibly, not enough to overweight a preview-era feature.

Docs: aspire.dev — What's new in Aspire 13.2

seniorWhat is Aspire's MCP integration for?

Answer

Two directions, and keeping them separate is the whole answer. Outward: Aspire exposes MCP tools so an AI coding agent can inspect and drive your running application — list resources, read logs and telemetry, run resource commands — which is why 13.2 framed the CLI as "a first-class agent interface" and added aspire agent to manage those integrations, with a dashboard dialog for connecting agents added in 13.4. Inward: WithMcpServer() marks a resource in your own app model that hosts an MCP server, so an AI-featured application's servers are part of the declared topology like anything else. The practical value of the first is that an agent debugging a failing test can read the actual logs and traces instead of guessing; the practical value of the second is that MCP servers stop being untracked side processes.

Example

builder.AddProject<Projects.Tools_McpServer>("tools-mcp")
       .WithMcpServer()                 // 13.2: declares this resource as an MCP server
       .WithReference(db);
aspire agent            # 13.2: manage AI agent integrations over MCP

Follow-ups

  • What is the security consideration? — An agent with these tools can read environment variables, logs and telemetry and run commands; scope it to local development and treat it as you would dashboard access.
  • Does it help non-AI teams? — Only indirectly; the same underlying capabilities (structured logs, telemetry search via aspire logs/aspire otel) are useful to humans too.
  • Is it stable? — It has moved every release since 13.0; check the current shape before relying on it.

Common wrong answer

"It adds AI features to your app." It exposes your app's operational surface to an agent; the AI features in your app are your problem. Conflating the two makes the security follow-up impossible to answer.

seniorHow would you model an AI-featured application in Aspire?

Answer

Like any other dependency graph, with the models as resources. Aspire has hosting integrations for the pieces — Azure AI Foundry, local model runners (Foundry Local, whose lifecycle management improved in 13.5), Ollama through the community ecosystem, and vector stores such as Qdrant, plus Postgres with pgvector. The pattern is a local model or emulator in run mode and the managed service in publish mode, exactly like a database. One current-events note worth having: Aspire.Hosting.GitHub.Models was deprecated in 13.5 with migration to Azure AI Foundry, so if you built on it there is work to do. The architectural points I would raise unprompted are that model calls are slow and expensive so they need timeouts, budgets and caching modelled explicitly, and that prompts and responses are high-cardinality telemetry you must decide about deliberately.

Example

var vectors = builder.AddQdrant("vectors").WithDataVolume();

var models = builder.ExecutionContext.IsRunMode
    ? builder.AddOllama("models").AddModel("llama3.2")            // local in dev
    : builder.AddAzureAIFoundry("models").AddDeployment("chat");   // managed in prod

builder.AddProject<Projects.Assistant>("assistant")
       .WithReference(models).WithReference(vectors).WaitFor(vectors);

Follow-ups

  • Should a local model be the dev default? — It keeps the loop offline and free, but behaviour differs enough that some tests must run against the real deployment.
  • How do you control cost? — Budgets and caching in the app, plus a parameter-controlled switch so dev cannot accidentally call the production deployment.
  • Telemetry? — Token counts and latency as metrics; prompt/response content only with an explicit privacy decision.

Common wrong answer

"Point it at OpenAI and put the key in configuration." It works and it skips every question that matters — local development story, cost control, timeouts, and what happens when the provider is slow rather than down.

principalShould AI agents be able to run resource commands against a developer environment?

Answer

Read access, yes — logs, telemetry, resource state and topology are exactly the context that makes an agent useful instead of speculative, and the cost of it being wrong is a bad suggestion. Write access needs a boundary. Restarting a container is recoverable; running a command named "reset database" against a persistent volume with a colleague's fixture data is not, and commands are one call away once the tooling is connected. My position: allow read tools by default, mark commands as agent-invocable explicitly rather than implicitly, keep destructive commands behind an interaction confirmation, and never connect an agent to a shared or deployed environment's dashboard. The broader principle is the one I would state at any level of seniority: an agent's blast radius should be the same as a new team member's on their first day — real, useful, and bounded by things that are cheap to undo.

Example

// Destructive commands ask a human, whoever (or whatever) invoked them.
db.WithCommand("reset", "Reset database", async ctx =>
{
    var interaction = ctx.ServiceProvider.GetRequiredService<IInteractionService>();
    var ok = await interaction.PromptConfirmationAsync("Reset database",
        "Deletes all local data. Continue?", ct: ctx.CancellationToken);
    return ok.Data ? await Reset.RunAsync(ctx) : CommandResults.Success();
});

Follow-ups

  • What about CI? — No agent write access in CI; pipelines should be deterministic, and an interaction prompt in CI hangs the job.
  • How do you audit what an agent did? — Command invocations appear in dashboard/CLI results; treat that as the audit trail and keep it.
  • Does this change with better models? — The reasoning improves; the blast radius argument does not. Undo-ability is the invariant.

Common wrong answer

"Sure, it's just a dev environment." Dev environments hold shared fixtures, real integration credentials, and days of someone's setup. "It's just dev" is the same reasoning that made the dashboard exposure question interesting in unit 16.

Explicitly a senior-and-above section: the questions have no API answer, and interviewers use them to see how you sequence change across people rather than code. seniorHow do you introduce Aspire to an existing solution without a big-bang rewrite?

Answer

In four reversible steps, each delivering value on its own. One: add ServiceDefaults to one service and get telemetry and resilience — no AppHost, nothing to roll back but a package reference. Two: add an AppHost that models what exists today, with aspire init if you want the scaffolding, and keep the old way of running things working in parallel for a sprint. Three: move developers over once the loop is genuinely faster, measuring start time and onboarding, and delete the old compose file only when nobody has used it for two weeks. Four — separately, and only if it earns its place — evaluate the deployment path. The sequencing matters because each step is independently valuable and independently reversible, so the initiative survives a bad week; a big-bang adoption that includes deployment on day one usually dies in the first incident.

Example

aspire init                    # scaffold an AppHost into an existing solution
# keep docker-compose.yml alive alongside for one sprint
aspire run                     # measure: start time, time-to-first-request

Follow-ups

  • What do you do first, ServiceDefaults or AppHost? — ServiceDefaults: smaller, safer, and it delivers tracing which is usually the most visible win.
  • How do you know step three is ready? — When the AppHost start is faster than the manual sequence and the last three onboardings used it.
  • What if the team resists? — Find out whether it is the tool or the change; usually it is a specific broken thing (a container that will not start on their machine), and fixing that converts more people than advocacy.

Common wrong answer

"Convert everything in a spike week." Spike weeks produce a half-working AppHost that one person understands and nobody else can fix, and the first failure kills the initiative. Incremental and reversible is the answer, and naming the rollback point for each step is what makes it credible.

seniorThe team tried Aspire and rejected it. How do you find out why?

Answer

By separating the tool from the experience, because the stated reason is rarely the real one. I would watch three people run it from a clean checkout and time each step — most rejections trace to one concrete blocker: containers that will not start on a locked-down laptop, an eight-minute cold start, a persistent volume broken by an image bump, a corporate proxy blocking image pulls, or an AppHost so tangled that changing anything is scary. Each of those has a fix. The rejections I would accept are structural: a single service where the AppHost is pure overhead, a platform team whose golden path Aspire fights, or an org that cannot upgrade quarterly. And I would take one thing seriously as a signal rather than an obstacle: if the people who tried it could not explain what it does, the adoption failed at explanation, not at engineering.

  • Would you overrule the team? — Not on a developer-experience tool. If they will not use it, it has no value.

Common wrong answer

"Mandate it and they'll adapt." A dev-loop tool that developers resent gets bypassed, and you end up maintaining both paths. Every credible answer here starts with finding the specific blocker.

principalWho owns the AppHost in a multi-team repository?

Answer

Shared ownership with a structural split, because an AppHost is simultaneously a shared artifact and a per-team concern. Concretely: a platform or infrastructure group owns Program.cs, the conventions and the module contract; each team owns its own module file (CatalogModule.AddCatalog(...)), enforced through CODEOWNERS so a team's changes do not need a central review and central changes do get one. That structure also solves the merge-conflict problem, which is the practical reason teams start asking for their own AppHost. If a team genuinely needs to evolve topology independently — different release cadence, different deployment target, no shared dependencies — that is a real signal to split into a second AppHost, and the cost to weigh is losing the single dashboard where cross-service traces appear. What I would not do is leave it unowned: an AppHost with no owner accumulates every team's workaround and becomes the file nobody will touch.

Example

# CODEOWNERS
/src/AppHost/Program.cs            @org/platform
/src/AppHost/Modules/Catalog.cs    @org/catalog-team
/src/AppHost/Modules/Ordering.cs   @org/ordering-team
/src/ServiceDefaults/              @org/platform

Follow-ups

  • How do you stop teams adding resources that slow everyone's loop? — A start-time budget as a CI check, and WithExplicitStart() for anything not universally needed.
  • What about cross-team dependencies in the model? — They are visible in the graph, which is a feature: an unexpected reference is an architecture conversation with evidence.
  • When is splitting clearly right? — When two halves have no shared resources and different release trains; then one AppHost is coordination for nothing.

Common wrong answer

"Every team gets its own AppHost." It removes the conflicts and the shared value at the same time — no single dashboard, no cross-service traces, and drift between overlapping definitions of the same resource. Split by ownership boundary, not by convenience.

principalSix months in, adoption stalled: two teams use it, four do not. What do you do?

Answer

Decide, and stop drifting — the worst outcome is a permanent half-adoption where both paths must be maintained and neither is good. I would first check whether the two adopting teams actually got the benefit: if their start time, onboarding time and trace coverage improved measurably, the case is proven and the problem is rollout; if not, the premise was wrong and I would stop the initiative and say so. Assuming the benefit is real, the four non-adopters usually have a specific blocker each, and I would fund fixing those rather than repeating the pitch — including making the platform package do the boring work so adoption costs a team a day, not a sprint. If two of them are structurally poor fits (a single service, a team on someone else's golden path), I would exempt them permanently and write it down. What I would not do is let it sit unresolved for another six months, because the cost of two parallel developer workflows compounds quietly and shows up as onboarding confusion rather than as a line item.

Example

OutcomeAction
Benefit proven, blockers specificfund the fixes, set a completion date
Benefit proven, teams are poor fitsexempt explicitly, document why
Benefit not measurablestop; remove the AppHosts or freeze them
Nobody can say either wayinstrument first, decide in one month

Follow-ups

  • What is the cost of half-adoption? — Two onboarding paths, two sets of docs, two failure modes for the platform team, and a constant low-grade argument.
  • How do you unwind it if you stop? — Keep ServiceDefaults (it is plain libraries and valuable regardless), delete the AppHosts, restore the compose files from history.
  • How would you have avoided this? — A decision date and success metrics at the start; open-ended adoption drifts by default.

Common wrong answer

"Keep evangelising, it'll catch on." Six months of evidence says it will not, and the answer avoids the actual decision. Interviewers ask this to see whether you can kill your own initiative, which is the harder half of owning one.

21Judgment calls

Ten open questions with no single right answer. At lead and principal level these are most of the interview: the interviewer is listening for which trade-offs you name unprompted, whether you can argue the position you did not take, and whether you state the condition that would change your mind. Attempt each out loud before opening it — the hidden part describes what a strong answer demonstrates rather than giving you a script.

judgmentShould a five-person startup with three services adopt Aspire?

What a strong answer shows

That you size the decision to the team rather than to the technology. Three services plus a database is right at the threshold: enough moving parts that the loop hurts, few enough that a compose file is manageable. A strong answer asks what the team's actual bottleneck is (shipping features, not running services, in most startups), notes that the adoption cost is roughly a day and the exit cost is roughly a day, and lands on "yes for the AppHost, no for the deployment path — you do not have platform problems yet". It names the specific risk for a small team: the Modern Lifecycle policy means quarterly upgrade work that a five-person team will resent, and the mitigation is that the dev loop tolerates a late upgrade far better than a generator in the deploy path.

Trade-offs named unprompted

  • Time-to-value now versus a maintenance obligation later.
  • Hiring: .NET developers increasingly expect it; a compose file is universally readable.
  • Reversibility as the deciding factor — cheap exits make small bets rational.
  • The real question behind the question: is developer onboarding actually the bottleneck?
judgmentIs "the topology you debug is the topology you ship" true, or marketing?

What a strong answer shows

That you can hold both. It is true about shape — the same graph produces the local run and the deployment artifacts, so a service cannot appear in production without appearing in the model. It is false about behaviour: emulators are not the real services, local Postgres is not a managed instance with connection caps and failover, one machine has no network partitions, and every RunAsEmulator or ExecutionContext branch weakens the claim further. A strong answer says the guarantee is structural rather than behavioural, and that its value is real but bounded: it eliminates a category of drift (the compose file nobody updated) without eliminating environment-specific bugs. The best answers add that the number of mode branches in the AppHost is a measurable proxy for how much of the claim you have given up.

Trade-offs named unprompted

  • Structural parity versus behavioural parity — different guarantees, different value.
  • Each IsRunMode branch is a small tax on the claim; count them.
  • An always-on integration environment on real services is the missing half.
  • Over-claiming this internally sets up the blame when a prod-only bug appears.
judgmentShould the AppHost be the single source of truth for infrastructure?

What a strong answer shows

An ownership-lifetime boundary rather than a yes or no. Application-scoped infrastructure — the container apps, their identities, the databases and caches this system owns — benefits enormously from living with the topology. Platform-scoped infrastructure — networking, DNS, clusters, policy, anything shared across systems — has a different lifecycle and different owners, and putting it in an application repo on a tool with no LTS is a poor bet. A strong answer names AsExisting (and 13.5's cross-scope variants) as the seam that lets the model reference platform-owned resources without claiming them, and notes that "single source of truth" is worth less than "unambiguous owner per resource". The strongest answers add that the claim is testable: publish the artifacts in CI and diff them, or the single source of truth is only aspirational.

Trade-offs named unprompted

  • Drift prevention versus blast radius when the generator changes.
  • Reviewability: generated Bicep is code, and nobody reviewing it is the failure mode.
  • Two appliers of one resource is worse than two sources of truth.
  • The exit: generated artifacts are ordinary files you can adopt permanently.
judgmentLocal containers versus shared development infrastructure — where do you draw the line?

What a strong answer shows

That you optimise for isolation first and concede it deliberately. Local containers give every developer an independent, resettable environment, which is what makes destructive experiments cheap; shared infrastructure gives faster starts, realistic data and lower laptop requirements, at the price of contention, shared corruption, and "who broke dev". A strong answer draws the line by weight and realism: light stateful dependencies stay local (Postgres, Redis, a queue), heavy or unreplicable ones go shared (a mainframe gateway, a licensed vendor system, a 200 GB dataset), and anything a developer needs to break freely stays local. It names the hybrid explicitly — AddConnectionString/AsExisting for shared pieces, containers for the rest — and points out that the moment a shared dependency is on the critical path, an outage there blocks every developer, which is a reliability requirement people forget to fund.

Trade-offs named unprompted

  • Isolation versus start time and machine requirements.
  • Shared dev infrastructure needs an SLO, or it blocks the whole team when it breaks.
  • Data realism versus data safety — shared environments accumulate real-looking PII.
  • Laptop constraints (arm64, memory, blocked Docker) can force the decision.
judgmentAspire's dashboard versus investing in production-grade observability first?

What a strong answer shows

That you recognise them as the same investment at different ends. The instrumentation is identical — OpenTelemetry in ServiceDefaults — and the dashboard is one exporter destination among several, so "adopt the dashboard" and "adopt an APM" are not competing purchases; the sequencing question is where you point the exporter first. A strong answer says instrument once, view locally in the dashboard, and route to a collector for anything deployed, and warns against the specific failure mode of treating the dashboard as sufficient: no persistence, no alerting, no long-range queries, no RBAC. It also names the cost the dashboard hides — telemetry volume and cardinality are free locally and expensive in production — so the decisions you defer (sampling, attribute discipline) arrive later with more services attached.

Trade-offs named unprompted

  • Same instrumentation, different sinks: this is a routing decision, not a tooling one.
  • Dashboard's in-memory limits versus an incident timeline that spans hours.
  • Sampling and cardinality decisions get harder the longer you defer them.
  • A deployed dashboard is an admin surface with no RBAC.
judgmentAspire ships breaking changes roughly quarterly. Is that acceptable for infrastructure code?

What a strong answer shows

Calibration rather than outrage or dismissal. A strong answer separates blast radius: a breaking change in the local loop costs a day and blocks nobody's customers; a breaking change in the generator that produces your production manifests is a different risk class. It cites real examples to show this is concrete — lifecycle hooks and publishers removed in 13.0, aspire exec removed and WithRoute renamed in 13.4, the Postgres default image bumped in a way that breaks existing volumes — and then describes the mitigations that make the cadence tolerable: central version management, model and artifact snapshot tests, a canary repo, and a standing quarterly slot. The judgment on display is whether you can accept a fast-moving dependency with eyes open, and whether you would make a different call for the dev loop than for the deploy path.

Trade-offs named unprompted

  • Velocity of the product versus stability of your pipeline — you cannot have both.
  • Modern Lifecycle means "not upgrading" is a support decision, not a neutral one.
  • Snapshot tests over generated artifacts convert a surprise into a diff.
  • Different answer for dev loop versus deployment path is the mature position.
judgmentShould services use Aspire's service discovery, or the platform's DNS?

What a strong answer shows

That you separate the abstraction from the resolver. The valuable part is that code refers to a logical name and never to a hostname; how that name resolves is a per-platform decision, and Microsoft.Extensions.ServiceDiscovery supports configuration, DNS and DNS SRV resolvers precisely so the abstraction survives the change. A strong answer keeps the abstraction, standardises one resolver per platform in a shared ServiceDefaults, and forbids ad-hoc overrides. It also concedes the genuine cost: an indirection makes "which instance served this request" harder to answer, so the resolved address must appear in traces and logs — and it notes that client-side discovery gives you no traffic management, so canaries, mTLS and circuit breaking come from elsewhere.

Trade-offs named unprompted

  • Portability of the abstraction versus transparency when debugging.
  • Client-side resolution means no central policy enforcement point.
  • Resource names become a public contract; renaming one breaks every caller.
  • One resolver strategy per platform, or you get environment-specific bugs.
judgmentIs Aspire a developer-experience tool or an architecture tool?

What a strong answer shows

That you notice it started as the first and became the second by accident, and that this has consequences. As a DX tool it is opt-in, low-stakes and easy to remove. But the AppHost is a machine-readable description of your system's topology, and once it exists it becomes the place architecture decisions get made and recorded: an unexpected WithReference in a PR is an architectural change, visible for the first time. A strong answer treats that as an opportunity — reviewing the model is reviewing the architecture, and the graph makes coupling arguable with evidence — while naming the risk: an artifact that is architecturally significant but was adopted as a convenience often has no owner, no tests and no review standard. The best answers connect this to concrete practice: CODEOWNERS on the AppHost, model tests for conventions, and treating resource names as contracts.

Trade-offs named unprompted

  • A DX tool adopted casually becomes an architecture artifact with no governance.
  • Machine-readable topology enables real review — if anyone actually reviews it.
  • It describes structure, not behaviour: no contracts, no SLOs, no data flows.
  • Ownership must be assigned deliberately, or the file rots.
judgmentThe rename to "Aspire" and the polyglot pivot — strategic strength or dilution?

What a strong answer shows

An opinion with evidence on both sides. The case for strength: distributed systems are polyglot, a .NET-only orchestrator would have been a niche tool, and 13.4's TypeScript AppHost GA plus Go, Bun and Python support removes the biggest adoption objection in mixed shops. The case for dilution: .NET was where the integration depth and the client-side ecosystem lived, engineering effort spent on parity is effort not spent on depth, and a .NET team gets a product whose roadmap now serves several audiences. A strong answer picks a side, names what would falsify it (does the .NET integration surface keep improving at the same rate?), and connects it to a practical consequence — for a .NET-only shop, nothing changes today except the version numbering and a slightly broader release-note surface.

Trade-offs named unprompted

  • Breadth versus depth in a product with finite engineering.
  • Version decoupling from .NET is real and changes your compatibility checking.
  • Polyglot support is asymmetric: hosting yes, client integrations .NET-only.
  • Rename plus repo and docs moves — a small but real tax on institutional knowledge.
judgmentIf you had to remove Aspire from a system that depends on it, how bad would it be?

What a strong answer shows

A layered exit analysis rather than a number. ServiceDefaults costs nothing to keep — it is Microsoft.Extensions.* and OpenTelemetry, and you would keep it whatever happens. Client integrations are a few lines each to replace with direct SDK registration, and the connection-string contract is unchanged. The AppHost is the real loss: you write a compose file (or generate one first with aspire publish against a Compose environment, which is the clever answer) and you lose the dashboard, so you deploy the standalone dashboard container or point OTLP elsewhere. Generated deployment artifacts you simply keep and own. The remaining cost is anything bespoke — custom resources, eventing subscribers, pipeline steps — which has no equivalent and must be rewritten. A strong answer concludes with the number that matters to a decision-maker: weeks, not quarters, and lower if you never put Aspire in the deployment path.

Trade-offs named unprompted

  • Exit cost is proportional to how much bespoke extension you built.
  • Generating the compose file on the way out is the cheapest migration.
  • The dashboard is separable — the standalone container survives the removal.
  • Knowing the exit cost up front is what makes the adoption decision rational.

22Design exercises

Three exercises where Aspire connects to system design. Each gives the prompt, the clarifying questions you should ask before designing anything, and — collapsed, so you can attempt it first — a strong solution outline with the trade-offs you are expected to name unprompted. Treat the clarifying questions as part of the answer: in a real loop, designing before asking them is itself a signal.

Exercise 1 — Model an e-commerce platform end to end

Prompt. Six .NET services (catalog, basket, ordering, payments, identity, notifications), a React frontend, Postgres, Redis, a message broker, and a third-party payment provider. Design the Aspire app model, the local development story and the path to production on Azure. You have twenty minutes and a whiteboard.

Clarifying questions to ask first

  • How many developers, and does everyone need all six services running?
  • Who owns deployment today — is there an existing pipeline I must fit into?
  • Are the databases per-service or shared, and who owns the schemas?
  • Is the payment provider callable from a laptop, or do we need a stub?
  • What is the target: ACA, AKS, App Service? Is that decided or am I deciding it?
  • Are there compliance constraints on where secrets and PII may live?
solutionA strong solution outline

Model

One AppHost, one module extension per bounded context so teams edit different files. One Postgres server with a database per service (isolation of schema and permissions without six containers), Redis for basket and caching, the broker as a container locally and a managed service in publish mode. The payment provider is an AddExternalService in publish mode and a WireMock container in run mode, so the local loop never dials a vendor. The React app is AddJavaScriptApp with its port injected via WithHttpEndpoint(env: "PORT") and WithExternalHttpEndpoints(). Migrations are a per-service job resource gated with WaitForCompletion. Persistent lifetime and data volumes on the stateful containers, with pinned image tags.

var builder = DistributedApplication.CreateBuilder(args);

var pg    = builder.AddPostgres("pg").WithLifetime(ContainerLifetime.Persistent)
                   .WithImage("library/postgres", "17.6").WithDataVolume();
var cache = builder.AddRedis("cache").WithLifetime(ContainerLifetime.Persistent);
var bus   = builder.AddRabbitMQ("bus").WithManagementPlugin();

var payments = builder.ExecutionContext.IsRunMode
    ? builder.AddContainer("payments-stub", "wiremock/wiremock", "3.9.1")
             .WithHttpEndpoint(targetPort: 8080, name: "http")
             .WithBindMount("./stubs/payments", "/home/wiremock").GetEndpoint("http")
    : builder.AddExternalService("payments", builder.AddParameter("payments-url")).GetEndpoint("https");

var catalog  = builder.AddCatalog(pg, cache);          // module extensions per context
var basket   = builder.AddBasket(cache, bus);
var ordering = builder.AddOrdering(pg, bus, catalog);
var billing  = builder.AddPayments(pg, bus, payments);

builder.AddJavaScriptApp("web", "../web", "dev")
       .WithReference(catalog).WithReference(basket).WithReference(ordering)
       .WithHttpEndpoint(env: "PORT")
       .WithExternalHttpEndpoints();

builder.Build().Run();

Local story

Persistent containers plus a seeded data volume so a cold start is under ninety seconds; launch profiles so a developer working on catalog starts four resources rather than fourteen; a reseed resource command instead of a README script; ServiceDefaults everywhere so the first trace crossing web → ordering → payments is visible on day one.

Path to production

ACA as the compute environment, with the worker-shaped services published as Container App Jobs where they are batch. Postgres and the broker become managed services referenced with AsExisting… if the platform team owns them, or provisioned by the model if not. Migrations run as a pipeline step before rollout. aspire publish in CI produces reviewable Bicep; the existing release pipeline applies it.

Trade-offs to name unprompted

  • One Postgres server locally is fast and cheap; per-service roles are what keep the boundary real.
  • Stubbing the payment provider costs realism — pay for it with a scheduled contract test against the real API.
  • Fourteen resources will not all fit comfortably on every laptop; subset profiles are a requirement, not a nicety.
  • Every IsRunMode branch weakens dev/prod parity; there are two here and I would not add a third without a reason.
  • ACA min-replicas of zero is cheap and gives the public API cold starts; set it to two for anything user-facing.

Exercise 2 — Retrofit Aspire onto a legacy .NET Framework estate

Prompt. Twelve services: four modern .NET 10, five on .NET Framework 4.8 running on IIS, three third-party containers. Two SQL Server databases, MSMQ, and a scheduled job on a Windows VM. Developers currently need three days to get a working environment. Design the adoption.

Clarifying questions to ask first

  • Are the .NET Framework services being modernised, or are they staying?
  • Do developers run Windows, and is IIS Express or full IIS in use?
  • Can SQL Server run in a container on developer machines (licensing, arm64)?
  • What is the three days actually spent on — is it environment setup, or data?
  • Is there budget for a modernisation, or is this purely a developer-experience effort?
solutionA strong solution outline

Approach

Aspire's AppHost requires .NET 10, but the resources it orchestrates do not have to be .NET at all — so the AppHost is a modern project that orchestrates a mixed estate. The four modern services are AddProject. The .NET Framework services are the interesting part: model them as AddExecutable (running the built binary or an IIS Express command line) or, better where feasible, as Windows containers or Linux containers after a targeted migration; whichever you choose, they receive the same injected environment, so service discovery and connection strings work if the app reads configuration from environment variables — which .NET Framework does not do natively, so this is where a small shim earns its place. SQL Server runs as a container (AddSqlServer) with a restored bacpac in a persistent volume, which usually removes most of the three days. MSMQ has no container story, so it is either replaced with a broker as part of the work, or modelled as an external dependency on a shared machine. The Windows scheduled job becomes an executable resource with WithExplicitStart().

var sql = builder.AddSqlServer("sql").WithLifetime(ContainerLifetime.Persistent)
                 .WithDataVolume("legacy-sqldata");
var billing = sql.AddDatabase("billing");

// modern service
builder.AddProject<Projects.Orders_Api>("orders-api").WithReference(billing);

// legacy 4.8 service, run as a process, config injected via a small shim
builder.AddExecutable("legacy-web", "iisexpress.exe",
                      workingDirectory: "../src/Legacy.Web",
                      "/path:.", "/port:44310")
       .WithReference(billing)
       .WithHttpEndpoint(port: 44310, name: "http")
       .WithHttpHealthCheck("/health");

Sequencing

Phase one: SQL Server in a container with restored data and the three third-party containers modelled — that alone probably takes three days to three hours, and it is reversible. Phase two: the four modern services into the AppHost with ServiceDefaults, delivering the first cross-service traces. Phase three: the legacy services as executables, accepting that hot reload and some debugging ergonomics are worse than the status quo — and stopping if they are. Deployment stays exactly as it is; this is a developer-experience programme, not a platform migration.

Trade-offs to name unprompted

  • The AppHost's .NET 10 requirement is a build-machine concern, not a constraint on the services it orchestrates.
  • .NET Framework services need a configuration shim to read injected environment variables; that is real work and it is where this stalls.
  • SQL Server containers are heavy and licensing/arm64 constrained — verify before designing around them.
  • MSMQ is the genuine blocker; either it is out of scope, or replacing it is a separate project.
  • The biggest win is almost certainly the database, so ship that first and let it fund the rest.
  • If phase three makes the legacy developers' lives worse, stop at phase two — partial adoption is a legitimate end state here.

Exercise 3 — Design the platform layer for twelve teams on Aspire

Prompt. You are the principal engineer for a platform group. Twelve product teams, ~60 .NET services, Azure, an existing Kubernetes cluster with GitOps, and a mandate to "standardise on Aspire". Design what your group builds, what it mandates, and how you handle the quarterly release cadence.

Clarifying questions to ask first

  • What problem is the mandate actually solving — onboarding, consistency, or someone's preference?
  • Is the deployment path in scope, or only the developer loop?
  • Who owns the cluster and the charts today, and are they in this conversation?
  • What is the current onboarding time and local start time — do we have baselines?
  • Is there an existing internal ServiceDefaults or telemetry standard to converge with?
  • How much of my group's capacity is this allowed to consume, ongoing?
solutionA strong solution outline

What the platform group builds

Four artifacts and no framework. An internal ServiceDefaults NuGet package replacing the copied template: telemetry conventions and required resource attributes, health semantics (/alive process-only, /health readiness with Degraded for optional dependencies), resilience defaults, one exporter path to the collector. An internal hosting-integration package: AddContosoPostgres and friends encoding the mirrored registry, pinned tags, required tags and policy through ConfigureInfrastructure, and health checks — compliance by using the obvious API. An AppHost template with the module structure, CODEOWNERS layout and model tests (every project has a health check; no unpinned image tags; every database reference matches its owner). And an upgrade pipeline: a canary repo that takes each Aspire minor first, a short migration note, then bot-raised PRs across the estate, with lag-to-current tracked as the platform group's own SLO.

What it mandates, and what it does not

Mandate ServiceDefaults (it is the telemetry and health contract on-call depends on) and the AppHost for local development. Do not mandate the deployment path: the cluster already has GitOps, policy enforcement and approvals, and displacing it buys nothing while adding a quarterly-changing generator between code and infrastructure. Offer aspire publish as an input to chart review for teams who want it, with the generated chart consumed as a dependency of a thin wrapper chart that carries platform concerns (PDBs, network policy, requests and limits).

Handling the cadence

Because only the newest release is supported, the upgrade is scheduled work, not opportunistic: one platform engineer-week per quarter, canary first, estate within three weeks, breaking changes read once centrally and translated into a note. Model and artifact snapshot tests in every repo turn generator changes into reviewable diffs. Teams that cannot upgrade get an explicit, time-boxed exception with a named owner, visible on a dashboard — not a quiet drift.

Trade-offs to name unprompted

  • Mandating a developer-experience tool is self-defeating if it is slower than what teams do now — measure before mandating.
  • An internal package is leverage and a bottleneck; everything must be opt-out-able down to raw Aspire APIs.
  • Refusing the deployment mandate will be politically unpopular and is the right call here; be ready to say what would change it.
  • The platform package falling behind Aspire is the main failure mode — teams route around it and the investment is lost.
  • Success metrics up front: onboarding time, local start time, trace coverage, lag-to-current. Without them this becomes a taste argument.

23Night-before cheat sheet

The ten questions most likely to be asked in some form, with a one-sentence answer each. If you can say these cleanly you will survive any screener; the depth lives in the sections above.

  1. What is Aspire? A dev-time orchestrator plus a declarative application model — projects, containers, executables and cloud resources in one C# or TypeScript program — that runs the whole system locally with wired-up configuration and telemetry, and compiles the same model into deployment artifacts for ACA, App Service, Kubernetes or Docker Compose.
  2. What runs in production? Only your services and ordinary libraries (service discovery, OpenTelemetry, resilience, health checks) that ServiceDefaults wired up — the AppHost is build-time and dev-time only.
  3. Hosting versus client integration? Aspire.Hosting.* goes in the AppHost and adds a resource (AddRedis); the client package goes in the service and configures the SDK client (AddRedisClient), with the resource name as the contract between them.
  4. What does WithReference do? Injects configuration into the consumer — ConnectionStrings__<name> or services__<name>__<endpoint>__<index> — and nothing else; ordering is WaitFor (healthy) or WaitForCompletion (exited).
  5. How does service discovery work? An HttpClient base address of https+http://catalog-api is resolved in-process by Microsoft.Extensions.ServiceDiscovery from configuration — or from DNS/DNS SRV in a cluster — with no registry, proxy or sidecar anywhere.
  6. What is the dashboard? A Blazor app started by the AppHost that shows the resource graph, streams console logs, and receives OTLP telemetry into memory with retention limits — great locally, not an APM, and an admin surface if you deploy it.
  7. Where do secrets go? AddParameter(name, secret: true), valued from user secrets or the environment locally; publish emits an unresolved secure parameter and deploy resolves it internally, with managed identity preferred over any secret at all on Azure.
  8. Publish versus deploy? aspire publish emits reviewable artifacts with parameters unresolved; aspire deploy resolves, provisions, pushes images and applies; aspire do <step> runs one pipeline step, and aspire destroy tears it down.
  9. How do you test it? DistributedApplicationTestingBuilder.CreateAsync<Projects.AppHost>(), then app.CreateHttpClient("api") after WaitForResourceHealthyAsync — keep it to a handful of journeys, because starting the graph costs tens of seconds.
  10. What changed in 13.x? The product dropped ".NET" and jumped 9.5 → 13 (Nov 2025), requires the .NET 10 SDK, removed lifecycle hooks and the publisher interfaces in favour of eventing and aspire do pipelines, renamed AddNpmApp → AddJavaScriptApp, took the TypeScript AppHost to GA in 13.4, and reached 13.5 on 18 Aug 2026 — the only supported release, since Aspire has no LTS.
