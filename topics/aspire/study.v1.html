.NET Aspire

study · Aspire 13.5 · released 2026-08-18

Assumption: the topic says “.NET Aspire”, but Microsoft dropped the “.NET” with the 13.0 release (11 Nov 2025) — the product is now just Aspire, lives at aspire.dev, versions independently of .NET, and is pitched as a polyglot application platform; this guide covers it under both names. Aspire is an opinionated orchestration and composition layer for local development plus a deployment-artifact generator: a C# (or, since 13.5, TypeScript) AppHost describes your app’s topology as a resource graph, the AppHost injects configuration and connection strings into the child processes and containers it launches, and a dashboard collects their OpenTelemetry. The current release is 13.5 (13.5.0 on 18 Aug 2026, patched to 13.5.3 on 25 Aug 2026); it made TypeScript AppHosts GA, added interactive terminals in the dashboard via the experimental WithTerminal(), shipped the CLI as @microsoft/aspire-cli on npm, and removed the dashboard AI Assistant. Aspire follows the Modern Lifecycle policy — only the newest release is supported, support for 13.4 ended the day 13.5 shipped — so “which version are you on” is a real interview question, and 13.x moves fast enough that a 9.x codebase will not compile against it.

01 What Aspire is — and is not

Start with the problem, because every good answer about Aspire is really an answer about the problem it attacks. A modern service-oriented .NET solution is five projects, a Postgres, a Redis, a RabbitMQ, an Azure Storage emulator and a front-end dev server. Before Aspire, the glue holding that together was a hand-written docker-compose.yml that duplicated your connection strings, a README with eleven manual steps, a launchSettings.json per project with hard-coded ports, and a Slack thread titled “anyone else getting connection refused on 5432?”. None of that glue was code, none of it was tested, none of it was reviewed, and it drifted from production continuously.

Aspire’s bet is that the topology of a distributed app should be a compiled, refactorable, debuggable program — one C# file that says “this API references that Postgres database and waits for it to be healthy” — and that everything downstream (the environment variables in the child process, the Docker Compose file, the Bicep for Azure Container Apps, the Kubernetes manifests, the integration-test harness) should be derived from that one description instead of maintained beside it. That single idea is the mental model to carry into the interview: the app model is the source of truth; everything else is a projection of it.

What Aspire concretely gives you is four things. (1) An AppHost: a small program using DistributedApplication.CreateBuilder(args) that declares resources and the edges between them. (2) An orchestrator — the Developer Control Plane, DCP — that at aspire run starts your projects as real local processes and your dependencies as real containers, wires them together, restarts them, and streams their logs. (3) A catalogue of integrations (150+): a hosting half that knows how to model Redis or Azure Service Bus in the app model, and a client half that configures the corresponding .NET client with health checks, telemetry, resilience and keyed DI. (4) A dashboard that ingests OTLP from every resource and shows resources, console logs, structured logs, traces and metrics in one place.

Equally important is what Aspire is not, and lead-level candidates are expected to say this unprompted. Aspire is not a runtime: your published containers do not contain an Aspire agent, and if the AppHost process dies in production it does not matter, because it was never there. It is not a service mesh, so it does no retries, mTLS or traffic shifting at the network layer — resilience is a client-side AddStandardResilienceHandler in your own process. It is not a PaaS or a hosting product; it emits artifacts for Azure Container Apps, Azure App Service, Kubernetes, Docker Compose and (since 13.5, in preview) Radius, then hands them over. It is not a replacement for Terraform or Bicep in an organisation that already governs infrastructure centrally — you can and often should let Aspire own the dev loop and let the platform team own production. And it is not a microservices framework: it gives you no messaging abstraction, no saga engine, no RPC contract system.

Two recent facts to have at your fingertips. First, the rebrand: 9.5 (Sept 2025) was the last “.NET Aspire”; 13.0 shipped 11 Nov 2025 as plain “Aspire”, skipping 10–12, with the explicit goal of decoupling from the .NET release train and signalling first-class Python, JavaScript, Go and Java support. Second, the support policy: Aspire is a Modern Lifecycle product with roughly one major a year and minors throughout — only the latest release is supported, and support for a version ends when the next one ships. That is a genuine architectural consideration, not trivia: Aspire is a build-and-dev-time dependency, so aggressive upgrade cadence is cheap compared to a runtime framework, but it also means an AppHost is the fastest-moving file in your repo.

Interview trap

The single most common wrong answer is “Aspire is Microsoft’s Docker Compose / Kubernetes replacement”. It is a red flag because it implies a runtime role Aspire does not have. The right framing: Aspire is a modelling layer whose output can be a Compose file, a set of K8s manifests or Azure Bicep — and whose main value is that the same model drives your F5 experience, your integration tests, and your deployment artifacts, so those three can never disagree. The second most common trap is answering with 9.x vocabulary (“.NET Aspire workload”, dotnet workload install aspire). The workload was removed back in 9.0 in favour of plain NuGet packages plus the aspire CLI; saying “workload” dates you by two years.

What you should observe

aspire init adds an AppHost (project or single-file apphost.cs) and an aspire.config.json, and does not modify your service projects except to offer a ServiceDefaults reference. The publish output is the interesting part: for a Docker Compose environment you get a docker-compose.yaml plus a .env file of parameters; for Azure you get Bicep modules per resource and a container-app definition per project. Every service-discovery value you never wrote by hand shows up there as a concrete environment variable — that is the “projection of the model” idea made visible, and it is the demo that convinces skeptical teams faster than any slide.

What problem does Aspire solve that Docker Compose does not?

Compose describes containers; Aspire describes an application. The difference shows up in three places. First, Aspire runs your .NET services as local processes, not containers, so you keep hot reload, breakpoints and fast rebuilds while your dependencies still run in Docker — Compose forces you to choose. Second, the wiring is derived: I write api.WithReference(db) once, and Aspire computes the connection string, the environment variable names and the service-discovery entries, so there is no duplicated connection string to drift. Third, the same model emits the Compose file, the Kubernetes manifests or the Bicep, so the dev topology and the deployed topology are the same artifact by construction. The trade-off is that you have taken on a fast-moving, opinionated dependency in your build, and you have moved topology into C#, which is unfamiliar to platform engineers who live in YAML.

Does Aspire run in production? What exactly ships?

No — the AppHost is a development and build-time tool. What ships is whatever your publisher emitted: container images for your services plus a Compose file, Kubernetes manifests, or Azure Bicep, with the environment variables that the app model computed baked in. The one Aspire component that can legitimately run outside dev is the standalone dashboard container, which is just an OTLP receiver with a UI, and even that is optional. I make this explicit early with platform teams, because the fear “we now have a Microsoft orchestrator in our critical path” is the usual blocker, and it is unfounded. The genuine production coupling is small but real: your services take a dependency on the Aspire.* client packages and on service-discovery configuration conventions.

Why did the version jump from 9.5 to 13.0, and why does that matter?

13.0 shipped in November 2025 as the rebrand release: “.NET Aspire” became “Aspire”, docs moved to aspire.dev, and the version was deliberately detached from the .NET major it used to shadow — the team never gave a serious reason for landing on 13 specifically. It matters because it signals intent: Aspire now ships on its own cadence, roughly a major a year with frequent minors, and it is positioned as polyglot rather than as a .NET feature. Practically, it means a 9.x AppHost does not compile on 13.x — AddNpmApp became AddJavaScriptApp, lifecycle hooks and publishing callbacks were removed in favour of aspire do pipeline steps, and .NET 10 SDK became the floor. I treat AppHost upgrades as routine planned work rather than as a surprise.

When would you tell a team not to adopt Aspire?

Three cases. When the organisation already has a mature platform — a Backstage-style scaffolder, Terraform modules, a golden pipeline — and the local dev story is solved by a devcontainer and a Tilt/Skaffold setup: Aspire’s deployment half would be a competing standard, and I would either adopt it dev-only or not at all. When the team is one service with no dependencies: the payoff is thin. And when the team cannot absorb the upgrade cadence — Modern Lifecycle means only the newest release is supported, and if you cannot touch the AppHost for a year, you will be unsupported and unable to take security fixes. The nuance I add is that “dev-only Aspire” is a completely legitimate end state and the easiest sale: no production blast radius, immediate onboarding win.

What is the relationship between Aspire and OpenTelemetry?

Aspire is deeply committed to OTel but does not own it. The ServiceDefaults project configures the OpenTelemetry SDK with ASP.NET Core, HttpClient and runtime instrumentation and exports over OTLP; the AppHost sets OTEL_EXPORTER_OTLP_ENDPOINT on every child resource to point at the dashboard; the dashboard is a plain OTLP receiver with an in-memory store. Nothing in that chain is Aspire-proprietary, which is the point: in production you change one environment variable and the same telemetry flows to Application Insights, Grafana, Honeycomb or an OTel collector. Interviewers like this answer because it shows you know the observability story survives the removal of Aspire, and that the dashboard is a dev convenience, not a monitoring product.

Is Aspire opinionated in ways that could hurt?

Yes, and naming them is what separates a lead answer from a brochure answer. It assumes an environment-variable-and-connection-string configuration model, which fights a team standardising on a secrets operator or a config service. Its Azure integrations are far richer than any other target, so “cloud agnostic” is true in principle and lopsided in practice. Resource names become part of your service-discovery contract, so renaming catalog is a breaking change across the graph. And the app model is C# in a project that must reference every service project, which creates a build-order coupling teams sometimes dislike. None of these is fatal; all of them are worth surfacing before adoption rather than after.

How does Aspire compare to Dapr, Tye and Radius?

Tye was the direct ancestor — a dev-time orchestrator experiment that was archived; Aspire is its productised successor with a real app model and integrations. Dapr is a runtime sidecar offering building blocks (state, pub/sub, bindings) with a portable API, so it competes at a different layer and actually composes with Aspire, which can model Dapr sidecars. Radius is an application platform for deploying and operating apps; since 13.5 Aspire can publish to Radius in preview, which is the clearest evidence that Aspire wants to be the modelling front end rather than the operator. The clean summary: Dapr abstracts what your code calls at runtime, Aspire abstracts how your app is composed and shipped, and they solve different problems.

What does Aspire require of my machine and my SDK?

Aspire 13.x requires the .NET 10 SDK or later even if your services target older frameworks, plus a container runtime — Docker Desktop, Podman or Rancher Desktop — for any container resource. The aspire CLI is a separate install and is now distributed several ways: dotnet tool install -g aspire.cli, a shell one-liner, the npm package @microsoft/aspire-cli as of 13.5, and a Nix flake. There is no workload to install any more; that mechanism was dropped in 9.0. In CI, the requirement to remember is the container runtime: integration tests that use the testing builder will start real containers, so your agents need Docker and enough headroom.

How would you introduce Aspire to a skeptical platform team?

I would scope the first conversation to the dev loop only and take deployment entirely off the table. The pitch is “delete the compose file and the README, keep everything else”, with a measurable claim: new-joiner time-to-first-request, and the number of files that currently repeat a connection string. I would run the migration on one service pair as a spike, show aspire publish output side by side with their existing manifests so they can see there is no runtime agent, and agree explicitly that production artifacts stay in their Terraform/Bicep until they choose otherwise. The concession that usually closes it is offering to own the AppHost upgrade cadence as a standing chore, because that is the real cost they are being asked to accept.

Where does Aspire fit in a repo that also has Terraform for production?

The pragmatic split is: Aspire owns dev-time topology and, optionally, publish artifacts for ephemeral environments (PR previews, integration test rigs); Terraform owns durable production infrastructure — networks, managed databases, DNS, IAM. The join is a connection string: in the AppHost you use AddConnectionString("db") or a parameter for anything Terraform provisions, and AddPostgres(...) only in run mode via RunAsContainer(), so locally you get a container and in the published model you get a reference to the real resource. That pattern — real resource in publish mode, container in run mode — is the single most useful idiom for teams with an existing IaC estate, and being able to name it is a strong signal.

02 The AppHost and the app model

The AppHost is a normal executable. That sentence is doing real work: it means the topology is expressible with loops, conditionals, methods and configuration, it can be unit-tested, it shows up in code review as a diff, and you can set a breakpoint in it. A minimal one is three lines — CreateBuilder, some Add* calls, Build().Run() — and the entire Aspire API surface is extension methods on the builder and on IResourceBuilder<T>.

Since 13.0 the AppHost does not even need a project file. A single-file AppHost is an apphost.cs whose first lines are C# file-based-app directives, using the .NET 10 file-based apps feature. This is now what aspire init produces for a lightweight setup, and it is a good answer to “how do I add Aspire to a repo without adding ceremony”.

#:sdk Aspire.AppHost.Sdk@13.5.0
#:package Aspire.Hosting.PostgreSQL@13.5.0

var builder = DistributedApplication.CreateBuilder(args);

var pg  = builder.AddPostgres("pg").WithDataVolume().WithPgWeb();
var db  = pg.AddDatabase("catalogdb");
var cache = builder.AddRedis("cache");

var api = builder.AddProject<Projects.Catalog_Api>("catalog-api")
                 .WithReference(db).WaitFor(db)
                 .WithReference(cache)
                 .WithHttpHealthCheck("/health");

builder.AddJavaScriptApp("web", "../web", "dev")
       .WithReference(api).WaitFor(api)
       .WithHttpEndpoint(env: "PORT")
       .WithExternalHttpEndpoints();

builder.Build().Run();

Read that as a graph. builder.Resources is a collection of IResource objects, each carrying a bag of annotations — an endpoint annotation, an environment-variable callback annotation, a wait annotation, a container-image annotation. Every fluent method you call is just “append an annotation”. That is the whole extensibility story, and it is why WithX methods compose in any order and why writing your own is easy (unit 13). When someone asks “how does Aspire actually work”, the honest answer is: it builds an annotated graph, then a set of hosted services walks that graph and turns annotations into behaviour.

The second structural idea is two modes. builder.ExecutionContext.IsRunMode is true under aspire run / F5, and IsPublishMode is true under aspire publish / aspire deploy. The same file is executed in both, and resources routinely behave differently: AddAzureRedis("cache").RunAsContainer() is a real Azure Cache for Redis in the emitted Bicep and a local Redis container on your laptop. Getting candidates to articulate this is a favourite interview move, because it explains how one description can serve both worlds — and it explains the class of bug where someone does expensive work unconditionally in the AppHost and then wonders why aspire publish tries to start Docker.

var builder = DistributedApplication.CreateBuilder(args);

// Real Azure resource when published; a container when running locally.
var cache = builder.AddAzureRedis("cache").RunAsContainer();

// Seed data only on a developer machine.
if (builder.ExecutionContext.IsRunMode)
{
    builder.AddContainer("seed", "ghcr.io/acme/seeder:latest")
           .WithReference(cache)
           .WithExplicitStart();          // sits idle until you press Start in the dashboard
}

// Choose the compute target only when publishing.
if (builder.ExecutionContext.IsPublishMode)
{
    builder.AddAzureContainerAppEnvironment("cae");
}

Underneath aspire run sits DCP, the Developer Control Plane: a small Kubernetes-flavoured control loop (not Kubernetes itself) shipped as a native executable in the Aspire packages. The AppHost hands DCP a desired state — these executables, these containers, these endpoints — and DCP reconciles it: allocates ports, starts processes, pulls images, creates networks, restarts on demand, and reports status back over gRPC to the AppHost and thence to the dashboard. You rarely touch DCP directly, but you will meet it in two places: log noise (filter Aspire.Hosting.Dcp to Warning in tests) and port allocation (proxied vs proxyless endpoints, where 13.5 changed proxyless port allocation to happen during service preparation, with a default range of 10000–32767).

Gotcha

The AppHost is a program, so people write programs in it — HTTP calls to fetch config, file IO, Task.Delay, Environment.GetEnvironmentVariable reads that only make sense on a laptop. All of that runs during aspire publish too, on a build agent with no Docker and no network egress, and it is a recurring source of “works locally, hangs in CI”. The rule I enforce in review: the AppHost body must be pure declaration; anything that touches the world goes behind IsRunMode, into an eventing subscription, or into a pipeline step. The related trap is a Projects.MyApi that does not resolve — that type is source-generated from the AppHost’s ProjectReference items, so a missing reference is a compile error, not a runtime one, and single-file AppHosts need the reference declared with AddProject("name", "../path/Api.csproj") or the Aspire.Hosting.Dotnet package’s path-based modelling added in 13.5.

Try it

1. Add Console.WriteLine(builder.ExecutionContext.IsPublishMode) to an AppHost, then run aspire run and aspire publish -o out and watch it print both ways. 2. Break it on purpose: put new HttpClient().GetStringAsync("https://example.com").Wait() at the top of the AppHost and run aspire publish with networking disabled.

Expected outcome

The first shows that the AppHost really is executed for publishing — it is not parsed, reflected over, or interpreted; the resource graph is produced by running your code. The second hangs or throws during publish and produces no artifacts, demonstrating why side effects must be mode-guarded. The sketch of the fix is to move the call into builder.Eventing.Subscribe<BeforeStartEvent>, which only fires in run mode, or into a custom pipeline step that participates in aspire do and can be skipped.

Walk me through what happens between aspire run and your first HTTP request.

The CLI locates the AppHost (project or apphost.cs), builds it and runs it. The AppHost executes your declarations, producing an annotated resource graph, then starts its hosted services: the dashboard, the resource notification service, and the DCP-backed orchestrator. DCP reconciles the graph — allocating ports for endpoints, pulling and starting containers, launching project processes with computed environment variables — while the AppHost evaluates connection strings and service-discovery values lazily as each resource starts. WaitFor relationships gate starts on the dependency reaching Running or Healthy. Meanwhile the dashboard opens with a login token and begins receiving OTLP from each child. Your first request then goes through the endpoint DCP allocated, possibly via its reverse proxy.

What is DCP and why is it not Kubernetes?

DCP — the Developer Control Plane — is the local orchestrator that Aspire ships as a native binary. It borrows Kubernetes’ shape: a desired-state API, controllers, and a reconciliation loop over objects like Executable, Container and Endpoint. It is not Kubernetes because there is no cluster, no kubelet, no etcd, no scheduling across nodes and no production ambition; it exists to start a handful of processes and containers on one machine reliably and to report their state. The practical consequences are that failures show up as DCP log lines, that container runtime choice (Docker/Podman) matters, and that the abstraction does not carry into production — your published Kubernetes manifests come from a publisher, not from DCP.

Run mode versus publish mode — give me a concrete design that depends on it.

The canonical one is a cloud resource with a local stand-in: builder.AddAzureServiceBus("bus").RunAsEmulator() gives the emulator container locally and a real namespace in Bicep, with the same connection string name and the same WithReference edges in both. A second is environment shaping: seed containers, a mail-catcher, pgweb or Redis Insight only under IsRunMode so they never leak into artifacts. A third is compute targets: AddAzureContainerAppEnvironment or AddDockerComposeEnvironment only matter when publishing. The judgment call is to keep the two modes as close as possible — every extra branch is a way for “works locally” to stop meaning anything — so I prefer RunAsX/PublishAsX helpers over hand-rolled if blocks.

What are annotations and why does that design choice matter?

Every resource carries an ordered collection of annotation objects, and every fluent method appends one: WithEnvironment adds an environment callback annotation, WithReference adds a reference (and its env callbacks), WaitFor adds a wait annotation. Nothing is executed at declaration time; the annotations are interpreted later by hosted services and publishers. This matters for three reasons: extension is trivial because a third party can add an annotation type and a service that reads it; ordering of WithX calls is mostly irrelevant, which makes the fluent API safe; and diagnosing odd behaviour means asking “which annotation produced this”, which you can literally inspect via resource.Annotations in a test.

How do you keep a large AppHost maintainable?

Once you pass roughly fifteen resources, a single Program.cs stops being reviewable. I factor it into extension methods per bounded context — builder.AddCatalog(), builder.AddOrdering() — each returning the handles the next needs, and I keep cross-cutting policy (health check paths, common environment, OTel resource attributes) in one helper applied uniformly. Configuration-driven selection of a subset (“start only the catalog slice”) is worth adding early via an aspire.config.json setting or a launch profile, because otherwise developers on a 30-container graph start disabling things by commenting out code. I also unit-test the AppHost: build the model without running it and assert the edges exist.

What is a single-file AppHost and when would you use one?

Since 13.0 the AppHost can be a bare apphost.cs using .NET 10 file-based apps, with #:sdk Aspire.AppHost.Sdk@13.5.0 and #:package directives at the top instead of a csproj. It exists to lower the adoption barrier: no new project, no solution churn, one file to review, and it is what aspire init offers by default in a lightweight setup. I would use it for small repos, for polyglot repos where a csproj feels out of place, and for demos. I would move to a project-based AppHost when I need typed Projects.* references without path strings, MSBuild-level control, custom extension code compiled alongside, or when the AppHost itself grows enough to want multiple files.

Can the AppHost be tested, and what would you test?

Yes, and it is underused. DistributedApplicationTestingBuilder.CreateAsync<Projects.AppHost>() gives you the built model without necessarily starting it, so you can assert structural invariants: every project has a health check, no resource is missing a WaitFor on its database, secrets are marked secret, resource names match your naming convention, and the set of externally exposed endpoints is exactly the intended one. Those tests run in milliseconds and catch the mistakes that otherwise surface as a broken environment. The heavier flavour — actually starting the application and hitting it — belongs in a smaller number of integration tests, because it costs container startup time (unit 10).

The AppHost references every service project. Isn’t that a coupling problem?

It is a real build-graph coupling and worth acknowledging: the AppHost must reference each project to get the generated Projects.* types and to know how to launch them, so it rebuilds whenever any service changes and it cannot live in a repo that does not contain them. The mitigations are: reference by path with AddProject("api", "../Api/Api.csproj") or the 13.5 Aspire.Hosting.Dotnet package when you want a looser link; model services you do not build as containers or as AddExternalService entries; and in a multi-repo world, have each repo own an AppHost for its own slice plus external-service entries for its neighbours, rather than one mega-AppHost that must clone the world.

How does the AppHost pass configuration into a child process?

Almost entirely through environment variables, computed at start time. Each resource accumulates environment callbacks — from WithEnvironment, from WithReference, from the endpoint and telemetry defaults — and just before launch Aspire evaluates them, resolving ReferenceExpression values like endpoint URLs and connection strings that are only known once dependencies are up. That is why WithEnvironment takes callbacks and EndpointReferences rather than plain strings: the value genuinely does not exist yet at declaration time. The observable consequences are that ConnectionStrings__catalogdb and services__api__https__0 appear in the child’s environment, that the dashboard can show you exactly what was injected, and that anything you need in a child must be modelled — a variable you export in your shell will not reach it.

What did 13.0 remove from the AppHost API, and why does it matter for upgrades?

13.0 deleted the old extensibility seams: publishing callbacks, IDistributedApplicationLifecycleHook, and a set of diagnostic APIs, replacing them with the eventing model (builder.Eventing.Subscribe<T>) and aspire do pipeline steps. It also renamed Aspire.Hosting.NodeJs to Aspire.Hosting.JavaScript and AddNpmApp to AddJavaScriptApp, and made DefaultAzureCredential use only managed identity in deployed Azure environments. For an upgrade this means the mechanical part is quick but any custom hosting extension a team wrote against lifecycle hooks needs rewriting. I plan 9.x→13.x as a spike: upgrade the AppHost, run aspire doctor, fix the removed APIs, then verify publish output diff before and after rather than trusting that the app still runs.

03 Resources, endpoints, references and ordering

Everything in the app model is a resource, and there are only a handful of shapes. A project resource is a .NET project launched as a process. An executable resource is any other process (a Go binary, npm run dev, a script). A container resource is an image DCP runs. A parameter resource is an externally supplied value (unit 08). A connection string resource is a value that other resources can reference. And a growing set of specialised resources — Azure Bicep resources, compute environments, external services — behave like the above with extra publish-time behaviour.

The edges between them are where the design lives. WithReference means “this resource needs to be able to talk to that one”, and it does two different things depending on the target. If the target exposes a connection string (a database, a cache, a queue), it injects ConnectionStrings__<name>. If the target is a service with endpoints (a project, an executable, a container with HTTP), it injects service-discovery variables (unit 04). Both are just environment variables in the end; the abstraction is that you never write the value.

WaitFor is the other essential edge and it is often confused with WithReference. WithReference is about configuration; WaitFor is about startup ordering. They are deliberately separate because most services should start immediately and retry rather than block — that is how they behave in production, where nothing waits for anything. You add WaitFor where the ordering genuinely matters: a migration job that must not run before the database accepts connections, or a service whose startup performs a schema check and would crash-loop noisily. WaitForCompletion is the stronger form: wait until the referenced resource exits, with an expected exit code — exactly what a one-shot migration container needs.

var pg = builder.AddPostgres("pg")
                .WithDataVolume()                       // named volume, survives aspire run cycles
                .WithLifetime(ContainerLifetime.Persistent);  // survives AppHost restarts too

var db = pg.AddDatabase("catalogdb");

// One-shot migration: runs to completion before the API is allowed to start.
var migrations = builder.AddProject<Projects.Catalog_Migrations>("migrations")
                        .WithReference(db).WaitFor(db);

var api = builder.AddProject<Projects.Catalog_Api>("catalog-api")
                 .WithReference(db)
                 .WaitForCompletion(migrations)          // blocks until migrations exits 0
                 .WithHttpHealthCheck("/health")
                 .WithReplicas(3);                       // three instances behind one discovery name

var gateway = builder.AddProject<Projects.Gateway>("gateway")
                     .WithReference(api).WaitFor(api)    // WaitFor honours api's health check
                     .WithExternalHttpEndpoints();       // only this is reachable from outside

Endpoints deserve their own mental model. A resource declares endpoints — WithHttpEndpoint, WithHttpsEndpoint, WithEndpoint(scheme: "tcp", ...) — each with a name, a scheme, a target port (inside the process/container) and an allocated port (outside). By default endpoints are internal: reachable by other resources in the model, and reachable from your browser locally, but not marked as public when published. WithExternalHttpEndpoints() is what flags them as ingress in the emitted artifacts. This is the moment where a local convenience becomes a production security decision, and it is exactly the sort of thing to flag in code review: every project with WithExternalHttpEndpoints is a service you have chosen to put on the internet.

Endpoints locally can be proxied or proxyless. By default DCP allocates a host port and runs a small reverse proxy in front of the resource, which is how replicas work — several instances behind one stable port. WithEndpoint(..., isProxied: false) removes the proxy so the process binds the host port directly, which you need for protocols the proxy does not understand or for tools that inspect the real port. 13.5 changed proxyless allocation to happen during service preparation, before workload creation, with a default port range of 10000–32767; if you have scripts that assumed a port, that is a breaking change worth knowing.

Interview trap

“Use WaitFor everywhere so nothing races.” It is the wrong instinct and interviewers probe it. A dependency chain of WaitFor serialises your entire startup — a graph that could be up in eight seconds takes fifty — and worse, it trains your services to assume dependencies are present at startup, which is precisely the assumption that fails in production during a rolling restart or a database failover. The lead answer: prefer resilient clients that retry (that is what the ServiceDefaults resilience handler is for), use WaitFor only where startup is genuinely non-resilient, and use WaitForCompletion for true ordering constraints like migrations. The related subtlety: WaitFor waits for healthy when the resource has a health check and merely for running when it does not — so a WaitFor on a resource with no health check gives you far weaker guarantees than people assume.

Try it

Expected outcome

With replicas you will see requests spread across three process ids, proving the proxy is load balancing and that your service-discovery name resolves to a set, not a single address — a cheap way to catch code that secretly assumes one instance (in-memory caches, local file locks, singleton schedulers). Removing the reference produces an InvalidOperationException from the service-discovery resolver saying no endpoints were found for the scheme, not a connection-refused: the failure happens at resolution time, before any socket is opened. That distinction is the fastest way to teach a team that WithReference is configuration, not networking.

Explain the difference between WithReference and WaitFor.

WithReference is a configuration edge: it makes the target’s connection string or endpoint addresses available in the source’s environment, and it is what service discovery and client integrations read. WaitFor is a scheduling edge: it delays the source’s start until the target reports Running, or Healthy if the target has a health check. They are orthogonal — you can reference without waiting, which is usually what you want, and you can wait without referencing, for example to serialise two containers that share a port. Conflating them causes two bugs: missing configuration (“no endpoints for service X”) when people add only WaitFor, and needlessly serial, slow startups when people add WaitFor everywhere out of superstition.

How do you run database migrations in an Aspire app?

Model the migrator as its own resource — a project or container that runs to completion — give it WithReference(db).WaitFor(db), and have the services that need the schema declare WaitForCompletion(migrations). That reproduces the real deployment sequence locally and it fails loudly rather than racing. In production the same shape becomes a pre-deploy job (an ACA job, a Kubernetes Job, a Compose depends_on: service_completed_successfully) generated from the model. The judgment part: EnsureCreated or Migrate() on startup inside the API is the pattern you will meet in existing codebases, and it is fine for a single-instance dev app but dangerous with replicas — concurrent migrations on three instances is a real outage — so I treat “migrations are a separate resource” as a code-review rule.

What does WithExternalHttpEndpoints actually change?

Locally, almost nothing: you can already reach every endpoint from your browser. What it changes is the emitted model — the resource is marked as having external ingress, so an Azure Container Apps publisher gives it an external ingress with a public FQDN, a Compose publisher maps its port on the host, and a Kubernetes publisher gives it a Service and ingress rules. That makes it a security-relevant declaration: the default is internal, and every call to it should be justified. In review I ask for exactly one or two — the gateway and maybe a webhook receiver — and I check that internal APIs, dashboards, admin tools and dev-only utilities (pgweb, Redis Insight, mail catchers) never get it.

What is a proxied endpoint, and when do you turn the proxy off?

By default DCP allocates a host port and puts a small reverse proxy between it and your resource. That indirection is what makes WithReplicas possible, keeps the port stable across restarts, and lets DCP start the listener before the process is ready. You turn it off with isProxied: false when the protocol is not something the proxy handles well, when a tool needs to see the real listening port (some debuggers, some database clients with strict TLS/SNI expectations), or when you are diagnosing whether an issue is yours or the proxy’s. The 13.5 change to be aware of is that proxyless port allocation now happens earlier, during service preparation, using the 10000–32767 range by default, so hard-coded expectations about ports can break on upgrade.

How do you model a service that already exists and you do not run?

builder.AddExternalService("payments", "https://payments.internal.acme.com") — or backed by a parameter so the URL differs per environment. It participates in the model like any other service: you can WithReference it, so your code uses the same https+http://payments logical name it would use for an in-model service, and it appears in the dashboard as a resource with a health check if you add one. That is how you avoid the anti-pattern of half your dependencies being Aspire-managed and half being raw configuration in appsettings. It also gives you a clean migration path: the day the team brings that service into the repo, you swap AddExternalService for AddProject and nothing else changes.

How do replicas behave, and what do they teach you?

WithReplicas(3) starts three instances of the resource behind one proxied endpoint, so consumers see a single stable address and requests are distributed. Locally it is primarily a correctness tool: it exposes services that were accidentally stateful — in-memory session state, a background scheduler that assumes it is alone, a file cache on a local path, an IHostedService that migrates the database. It is not a performance-testing feature and it does not model autoscaling. The caveat is that some resources do not tolerate replicas (anything holding an exclusive lock or a single-writer file volume), and that debugging attaches to one process, so an F5 session with replicas can be confusing — I usually keep replicas behind a flag and enable them deliberately.

How do resource names function as a contract?

The name you pass to AddX("catalogdb") becomes the connection-string key, part of the service-discovery variable names, the dashboard label, the container name and — in published artifacts — often the actual resource name in Azure or Kubernetes. So renaming is a distributed breaking change: consumer code that says GetConnectionString("catalogdb") stops working, and deployed infrastructure may be recreated rather than updated. I treat names as public API: lower-case, hyphenated, stable, meaningful without the environment prefix, and reviewed at introduction. When a rename is unavoidable I do it in two steps, adding the new name alongside the old before removing it, exactly as I would for any other contract.

A container resource needs a file from my repo. How do you wire that?

WithBindMount(source, target, isReadOnly) maps a host path in — the right choice for seed SQL, config files, TLS certs and anything you edit and want reflected without rebuilding. WithVolume/WithDataVolume creates a named Docker volume instead, which is for data you want to persist but not read from the host. The trap is portability: bind mounts encode host paths and file permissions, break between Windows/WSL/macOS, and do not survive publishing — nothing in a Compose or Bicep artifact should depend on a developer’s directory layout. So bind mounts are a run-mode tool; for anything the deployed app needs, model it as a parameter, a config resource, or content baked into the image.

What is WithExplicitStart for?

It creates the resource in the model but leaves it idle until someone presses Start in the dashboard or runs the CLI start command. The use case is a big graph where some dependencies are expensive and rarely needed — a search cluster, an ML model server, a legacy SQL Server image that takes 40 seconds and 2 GB. Everyone gets the full topology and its documentation value; only the developer who is working on search pays for search. It pairs well with health checks and WaitFor, since dependents will simply sit waiting until you start the thing. The alternative pattern — commenting out resources — is worse because it drifts and gets committed by accident.

How do you keep the local graph honest about production?

Three habits. First, prefer RunAsContainer/RunAsEmulator on real cloud resources rather than modelling a different technology locally, so the connection semantics match. Second, keep run-mode-only extras (admin UIs, seeders) visibly separated in the AppHost, ideally in one method called AddDeveloperExtras, so a reviewer can see at a glance what does not exist in production. Third, do not hide production concerns you cannot reproduce — if production sits behind a VNet and a private endpoint, model it with a comment and an external service rather than pretending direct access is normal. The failure mode to avoid is a beautiful local graph that gives false confidence; the value of Aspire is that dev and prod come from one model, and every unguarded divergence erodes that.

04 Service discovery

Service discovery is the piece that makes the app model pay off, and it is much simpler than the name suggests. Your code never holds an address. It holds a logical name — https+http://catalog-api — and a resolver turns that into a real address at request time. Locally the resolver reads configuration that the AppHost injected; in production it reads whatever the platform injected, or falls back to DNS. The abstraction is a single IServiceProvider-registered set of resolvers plugged into HttpClient’s handler pipeline.

The configuration shape is worth memorising because it appears in every debugging session. WithReference(api) writes variables of the form services__<resource>__<endpoint-key>__<index>. In 13.2 the endpoint key changed from the endpoint name to the endpoint scheme for endpoints named http/https — so a value that was services__catalog__myendpoint__0 on 13.0/13.1 is services__catalog__https__0 on 13.2+ (endpoints with other names still key by name). That is a genuine breaking change: anything reading those variables directly, or a YARP config keyed on the old shape, needs updating. Being able to name it is a good “are you current” signal.

// ServiceDefaults (or any host) — one call turns on the resolvers.
builder.Services.AddServiceDiscovery();

builder.Services.ConfigureHttpClientDefaults(http =>
{
    http.AddStandardResilienceHandler();
    http.AddServiceDiscovery();
});

// Consuming code: a logical name, never an address.
builder.Services.AddHttpClient<CatalogClient>(c =>
    c.BaseAddress = new Uri("https+http://catalog-api"));

// A named endpoint on a resource that exposes several.
builder.Services.AddHttpClient("admin", c =>
    c.BaseAddress = new Uri("https+http://_admin.catalog-api"));
{
  "services": {
    "catalog-api": {
      "https": [ "https://localhost:7241" ],
      "http":  [ "http://localhost:5241" ],
      "admin": [ "http://localhost:5399" ]
    }
  }
}

The https+http scheme is not decoration. It means “resolve HTTPS if the target has an HTTPS endpoint, otherwise fall back to HTTP”, evaluated per target. That lets one code path work in a local environment where a container only speaks HTTP and in production where everything is TLS, without conditional configuration. There is a security consideration bundled in: the resolver enforces an allowed-schemes rule so a service cannot be silently downgraded to HTTP when you asked for HTTPS only — write https://catalog when you mean it.

Three resolvers ship. The configuration resolver reads the services: section (what Aspire injects) and is what you use locally and in any platform that can set environment variables. The DNS resolver does an A/AAAA lookup on the logical name — the natural fit for Kubernetes, where catalog-api is already a Service name. The DNS SRV resolver queries SRV records, which is what you want with Consul or with headless Kubernetes services because it gives you ports and multiple instances. They are tried in order, so the production story is usually “configuration if present, else DNS”, and no code changes between environments.

Gotcha

Service discovery is not magic ambient networking, and the failure looks nothing like a network error. If you forget WithReference, the configuration has no entry for the name and you get an InvalidOperationException — “no endpoints found for service …” — thrown by the resolver before a socket exists. Candidates who say “DNS would fail” are betraying that they think the logical name is resolved by the OS; it is not, locally. Two more sharp edges: the resolver only applies to HttpClients configured with AddServiceDiscovery (a raw new HttpClient() knows nothing), and it only handles HTTP — for a gRPC channel you either configure the same handler pipeline or resolve the address explicitly. Non-HTTP protocols (Postgres, Redis, AMQP) do not use service discovery at all; they go through connection strings.

You will see the exact services__catalog-api__https__0 shape, including the index that supports multiple addresses, and you will notice that the variables exist only on resources that declared a reference — discovery is scoped, not global. The second exercise proves the mechanism is plain configuration: hand-writing the services section restores resolution with no Aspire involvement at all, which is exactly how the same code works in a deployed environment where a Helm chart or a Compose file supplies those values. How does Aspire service discovery work end to end?

The AppHost knows every resource’s allocated endpoints, so when A declares WithReference(B) it writes B’s addresses into A’s environment as services__B__<key>__<index>, where the key is the scheme for http/https endpoints and the endpoint name otherwise. In A, AddServiceDiscovery registers a set of endpoint providers and a delegating handler on configured HttpClients. When code requests https+http://B/path, the handler asks the providers for endpoints named B, picks a scheme according to the requested scheme list and the allowed-scheme policy, load-balances across returned addresses, and rewrites the URI. Nothing is cached forever — providers can refresh — and nothing is Aspire-specific at runtime: the same code resolves through DNS in Kubernetes.

What changed about service-discovery variables in 13.2?

The endpoint key switched from the endpoint name to the endpoint scheme for endpoints named http or https. Previously an endpoint named myendpoint produced services__svc__myendpoint__0; now the common case produces services__svc__https__0, which makes the shape predictable when several endpoints share a scheme and matches how consumers actually ask (https+http://svc). Endpoints with custom names still key by name, which is what _endpointName.serviceName addressing targets. It broke anything reading the variables directly — reverse-proxy configuration, scripts, tests asserting on environment — and it landed alongside the config consolidation into aspire.config.json, so 13.1→13.2 is the upgrade where I would read the breaking-change list line by line.

Why https+http rather than just https?

Because the same code has to run where TLS is available and where it is not. https+http is an ordered preference: use the HTTPS endpoint if the target has one, otherwise the HTTP one. Locally a container-based dependency often only exposes HTTP while your projects have dev certificates; in production everything is HTTPS. Without the fallback you would need environment-specific base addresses, which is exactly the configuration sprawl Aspire removes. The security nuance worth stating: https+http is a downgrade you have explicitly permitted, so it is fine for intra-cluster development traffic and wrong for anything crossing a trust boundary — there you write https:// and let resolution fail loudly if no TLS endpoint exists.

Does service discovery work for non-HTTP protocols?

Not through the HTTP resolver. Databases, caches, brokers and anything else with its own wire protocol are wired by connection strings: WithReference(db) injects ConnectionStrings__catalogdb, and the client integration reads it. The endpoint information is still in the model, so you can build a connection string from an EndpointReference when you need one for a custom protocol. For gRPC you can reuse the HTTP path because gRPC rides on HttpClient — configure the channel with the service-discovery handler. The clean way to say this in an interview: Aspire has two wiring channels, service discovery for HTTP-ish traffic and connection strings for everything else, and WithReference picks the right one based on what the target exposes.

How does this survive deployment to Kubernetes?

Two ways, and you can use either. The publisher can emit the same services__* environment variables pointing at cluster-internal DNS names, in which case the configuration resolver keeps working exactly as locally. Or you register the DNS or DNS SRV resolver and let catalog-api resolve through cluster DNS to the Service, with SRV giving you ports and multiple endpoints for client-side load balancing. I usually prefer plain DNS in Kubernetes because it lets the platform own routing and works for traffic that did not come from an Aspire-configured client, and I keep the configuration resolver first so that overrides are still possible per environment.

How do you address one of several endpoints on the same service?

Use the named-endpoint form: https+http://_admin.catalog-api, where the leading underscore segment is the endpoint name. It maps to the services__catalog-api__admin__0 configuration entry, and it is how you reach a management port, a metrics port or a second protocol on the same resource. In the AppHost you create those with WithHttpEndpoint(name: "admin", ...). It is a small piece of syntax that comes up in interviews because it reveals whether you have used the feature or only read about it — and the practical warning is that named endpoints are also the case where the 13.2 scheme-keying change does not apply, so the variable still uses the name.

How do you override a discovered address for local debugging?

Because it is plain configuration, the ordinary .NET precedence applies: put a services:catalog-api:https:0 entry in user secrets or appsettings.Development.json, or set the services__catalog-api__https__0 environment variable, and it wins over — or supplements — what the AppHost injected. That is how you point one service at a colleague’s branch deployment or at a locally running instance outside Aspire while everything else stays in the model. The alternative, and often cleaner, approach is to model it: replace the resource with AddExternalService pointing at a parameterised URL, so the override is visible in the AppHost rather than hidden in someone’s user secrets.

Is there load balancing, and what are its limits?

Yes, client-side and deliberately simple: when a name resolves to multiple endpoints the handler picks among them per request, giving you round-robin-ish distribution. There is no health-aware ejection, no outlier detection, no zone awareness, no weighting — if you need those you want a real mesh or a proxy. Locally the picture is muddied by the DCP reverse proxy, which is itself doing the balancing across replicas behind a single address, so you often see one endpoint client-side and distribution server-side. The honest framing for an interview: Aspire gives you enough to develop against multiple instances and enough to work in production behind a platform that does the serious routing, and it does not pretend to be a mesh.

What are the security implications of the service-discovery configuration?

The variables are injected into process environments, so anything that can read a process’s environment — a crash dump, a debug endpoint, the dashboard — can see internal topology, and if you put credentials in connection strings, those too. Three practices follow. Mark secret parameters as secret so they are masked in the dashboard and stored appropriately when published. Prefer managed identity or workload identity over embedded credentials, which is why 13.0 changed deployed Azure credential resolution to managed identity only. And do not expose the dashboard outside the developer machine without auth — standalone dashboards need the OTLP endpoint protected and the frontend behind a token, because it displays exactly this environment data.

A developer says “service discovery is flaky, sometimes it 404s”. How do you debug it?

First, confirm it resolves at all: an unresolvable name throws rather than 404s, so a 404 means the request reached something. Second, look at what it reached — in the dashboard, open the caller’s environment and read the services__* values, then open the trace: distributed tracing shows the outgoing HTTP span with the resolved URI, which usually reveals a path bug or the wrong scheme, not a discovery bug. Third, check schemes: https+http can land on an HTTP endpoint that serves a different app (a dev proxy, a front-end dev server) and returns 404 happily. Fourth, check replicas: if one instance is unhealthy but still routed to, you will see intermittent failures, and that is a health-check gap rather than a discovery gap. The general lesson I would give the team is that discovery failures are loud and configuration failures are quiet, so a 404 is almost never discovery.

05 Integrations: hosting vs client

“Integration” is an overloaded word in Aspire and the interview question is nearly always “explain the two halves”. A hosting integration is a package referenced by the AppHost that teaches the app model about a technology: Aspire.Hosting.PostgreSQL gives you AddPostgres, knows which image and tag to run, what the connection string looks like, which health check to use, and how to publish it as an Azure Database for PostgreSQL if asked. A client integration is a package referenced by your service that configures the corresponding client library: Aspire.Npgsql.EntityFrameworkCore.PostgreSQL gives you builder.AddNpgsqlDbContext<CatalogContext>("catalogdb"), which reads ConnectionStrings:catalogdb, registers the context, and switches on health checks, tracing, metrics, logging and retries with sensible defaults.

The naming convention makes them easy to tell apart, which is a cheap thing to know: hosting packages are Aspire.Hosting.*; client packages are named after the client library — Aspire.StackExchange.Redis, Aspire.Npgsql, Aspire.Azure.Messaging.ServiceBus, Aspire.Confluent.Kafka. There are 150+ of them across databases, caches, messaging, Azure/AWS/GCP services, observability and polyglot runtimes.

// AppHost (hosting integration): Aspire.Hosting.Redis
var cache = builder.AddRedis("cache")
                   .WithRedisInsight()                       // run-mode admin UI
                   .WithPersistence(TimeSpan.FromMinutes(5)); // RDB snapshots

builder.AddProject<Projects.Web>("web").WithReference(cache);
// Service (client integration): Aspire.StackExchange.Redis.OutputCaching
builder.AddRedisOutputCache("cache");          // name matches the resource name

// Or the plain client, with settings and options callbacks:
builder.AddRedisClient("cache", settings =>
{
    settings.DisableTracing = false;
    settings.DisableHealthChecks = false;
}, options => options.ConnectTimeout = 3000);

// Multiple instances of the same technology → keyed DI
builder.AddKeyedRedisClient("cache");
builder.AddKeyedRedisClient("sessions");
// consume with [FromKeyedServices("sessions")] IConnectionMultiplexer sessions

The thing to internalise is that the name is the contract. AddRedis("cache") in the AppHost and AddRedisClient("cache") in the service agree on the string "cache"; the AppHost writes ConnectionStrings__cache, the client reads it. Nothing else connects them — no shared assembly, no code generation, no registry. This is why a client integration works perfectly well without Aspire: point ConnectionStrings:cache at a real production Redis via Key Vault or a Helm secret and the same code runs. That decoupling is the answer to “does using client integrations lock my services to Aspire?” — they are thin opinionated wrappers over the normal client libraries plus Microsoft.Extensions.* registrations.

Each client integration follows a standard shape, which is worth reciting: a settings class bound from configuration under Aspire:<Vendor>:<Component>, with uniform opt-outs (DisableHealthChecks, DisableTracing, DisableMetrics, and where relevant DisableRetry); registration of the client, keyed or unkeyed; a health check registered under the resource name; OTel instrumentation registered so traces and metrics flow to the dashboard automatically; and, for HTTP-ish clients, resilience defaults. That uniformity is the product: you get four production concerns per dependency without writing them, and you get them the same way for every technology.

Explain hosting versus client integrations to a new team member.

Hosting integrations are for the AppHost and describe what exists: AddPostgres says “there is a Postgres, here is the image, here is how to build its connection string, here is its health check, and here is what it becomes when published”. Client integrations are for your services and describe how to talk to it: AddNpgsqlDbContext<T>("catalogdb") registers the DbContext, wires health checks, tracing, metrics and retries, and binds settings from configuration. They are joined only by the resource name string. The rule of thumb I give people: if the code is in the AppHost it is hosting, if it is in a service it is client, and if you find yourself referencing Aspire.Hosting.* from a service, something has gone wrong.

What exactly does a client integration configure for you?

Five things, uniformly. The client itself, registered in DI (keyed if you asked). A health check under the resource name, which surfaces in /health and in the dashboard. OpenTelemetry tracing and metrics instrumentation for that client, so the dependency shows up as spans in your traces. Configuration binding to a strongly typed settings class under Aspire:<Vendor>:<Component> with consistent Disable* switches. And, where the client supports it, sensible retry/timeout defaults. The value is not any single item — it is that every dependency gets the same treatment, so “is the cache instrumented?” stops being a per-team question. The cost is a layer of indirection when you need unusual client options, which the options callback overload exists to solve.

How do you handle two instances of the same technology?

Keyed DI. In the AppHost you add two resources with distinct names; in the service you call the keyed variant — AddKeyedRedisClient("cache") and AddKeyedRedisClient("sessions") — and inject with [FromKeyedServices("sessions")]. Each gets its own settings section, its own health check and its own telemetry attributes, so you can tell them apart in the dashboard. The failure mode when people do not do this is registering the same interface twice unkeyed, where last-registration-wins and half your code silently talks to the wrong instance. It is one of my standard code-review checks whenever I see two resources of the same type in an AppHost.

What if there is no integration for the technology I use?

Then you write the wiring yourself, and it is not much work because the pieces are standard. In the AppHost, AddContainer("thing", "image:tag") with WithEndpoint, plus WithConnectionStringRedirection or a custom resource implementing IResourceWithConnectionString so consumers can WithReference it (unit 13). In the service, register the client normally, add a health check from AspNetCore.HealthChecks.* or hand-written, and add the OTel instrumentation package if one exists. I would also wrap that in an internal extension method so it looks like every other integration to the team. The important judgment is not to fake an integration by copying an existing one’s internals — keep it simple and obviously yours.

Do client integrations lock my services to Aspire?

No, and this is the argument that wins the adoption debate. A client integration depends on Microsoft.Extensions.* abstractions and the underlying client library; it reads a connection string from configuration and registers services. Run the same service in a Kubernetes cluster with the connection string coming from a mounted secret and everything works — Aspire is not in the process. The residual coupling is a NuGet dependency on Aspire.* packages and their versioning cadence, plus the configuration key convention. If a team is anxious, the fallback is to use hosting integrations only and wire clients by hand, which keeps the entire Aspire footprint in the AppHost — a legitimate, if slightly poorer, position.

What is the difference between RunAsContainer, RunAsEmulator and PublishAsX?

They are the mode-switching helpers that let one declaration serve both worlds. AddAzureRedis("cache").RunAsContainer() declares an Azure Cache for Redis for publishing but starts a Redis container locally. AddAzureStorage("storage").RunAsEmulator() starts Azurite locally while publishing real storage accounts. The PublishAsX family goes the other way: start from a container declaration and change what it becomes when published — for example AddPostgres("pg").PublishAsAzurePostgresFlexibleServer(). Choosing between them is mostly about which side you consider the default. I prefer AddAzureX().RunAsY() when the cloud service is the truth, because then the published artifact is the primary declaration and the local shortcut is visibly a shortcut.

How do you keep integration versions consistent across a solution?

Central Package Management: a Directory.Packages.props with one <PackageVersion> per Aspire.* package, so the AppHost, ServiceDefaults and every service move together. Aspire packages are versioned in lockstep with the release, and mixing 13.4 hosting with 13.5 client packages is a supported-but-unnecessary risk. The CLI helps: aspire update updates the Aspire packages across the solution to a chosen version, and aspire update --self updates the CLI itself. In CI I add a check that fails if any Aspire.* version differs from the AppHost SDK version, because that mismatch produces confusing errors that cost far more than the check.

Are the container images used by hosting integrations pinned, and does that matter for security?

Each hosting integration ships with a default image and tag that moves with the Aspire release, and Microsoft explicitly does not vet those third-party images — the support policy says the containers are your responsibility for security, compliance and cryptographic requirements. That has two consequences at lead level. First, in a regulated environment you should override images to point at your internal registry with WithImageRegistry/WithImageTag, so scanning and provenance apply. Second, an Aspire upgrade can quietly bump Postgres or Redis a minor version underneath your team, which is usually harmless locally but is exactly the kind of change that should show up in a release note rather than a surprise. I pin images explicitly in any repo where reproducibility matters.

How do integrations interact with health checks and readiness?

A client integration registers a named health check for its resource, so /health in your service becomes an aggregate over the dependencies it actually uses. That is genuinely useful and genuinely dangerous: if you expose that aggregate as your Kubernetes readiness probe, a Redis blip will take your pods out of rotation even though your service could still serve most requests. The convention ServiceDefaults sets up is two endpoints — /health for “everything including dependencies” and /alive for liveness only, tagged live — and the guidance I give teams is: liveness on /alive, readiness on a curated subset, and the full aggregate for humans and dashboards. That distinction is a favourite senior interview probe.

How would you review a PR that adds a new integration?

I check five things. The resource name is meaningful, lower-case and matches the client call exactly. The dependency is added in both halves — hosting in the AppHost, client in the services that use it, not just one. Anything that carries credentials is a secret parameter or uses managed identity rather than an inline string. There is a health check and it is wired into the right endpoint, and if the dependency is optional, the health check is not on the readiness path. And the publish shape is deliberate: does this become a real cloud resource, a container in the emitted Compose file, or an external service the platform team already owns? The last one is the question people forget, and it is the one that has cost the most money in my experience.

06 ServiceDefaults: OpenTelemetry, health, resilience

ServiceDefaults is the most misunderstood piece of Aspire, and understanding it is a fast way to sound senior. It is not a NuGet package: it is a project template that Aspire scaffolds into your solution as ordinary source code, referenced by each of your services, exposing builder.AddServiceDefaults() and app.MapDefaultEndpoints(). The design decision is deliberate. These are cross-cutting production policies — how you sample traces, what your health endpoints are called, how aggressively you retry — and every organisation wants to change them. Shipping them as code you own means you can edit them; shipping them as a package would mean fighting defaults.

What the template contains is four blocks. OpenTelemetry: logging with formatted messages and scopes, metrics from ASP.NET Core, HttpClient and the .NET runtime, tracing from ASP.NET Core and HttpClient with the health-check endpoints filtered out, and an OTLP exporter enabled whenever OTEL_EXPORTER_OTLP_ENDPOINT is set. Health checks: a default liveness check plus MapDefaultEndpoints, which maps /health (all checks) and /alive (checks tagged live) — and in the shipped template these are mapped only in development, precisely because exposing them publicly is a decision you must make. Service discovery: AddServiceDiscovery plus ConfigureHttpClientDefaults so every HttpClient resolves logical names. Resilience: AddStandardResilienceHandler() from Microsoft.Extensions.Http.Resilience, which is Polly v8 under the hood — a rate limiter, a total timeout, retries with jittered backoff, a circuit breaker and an attempt timeout, in that order.

public static TBuilder AddServiceDefaults<TBuilder>(this TBuilder builder)
    where TBuilder : IHostApplicationBuilder
{
    builder.ConfigureOpenTelemetry();
    builder.AddDefaultHealthChecks();

    builder.Services.AddServiceDiscovery();
    builder.Services.ConfigureHttpClientDefaults(http =>
    {
        http.AddStandardResilienceHandler();   // Polly v8 pipeline
        http.AddServiceDiscovery();            // logical names → addresses
    });

    return builder;
}

public static WebApplication MapDefaultEndpoints(this WebApplication app)
{
    if (app.Environment.IsDevelopment())
    {
        app.MapHealthChecks("/health");
        app.MapHealthChecks("/alive", new() { Predicate = r => r.Tags.Contains("live") });
    }
    return app;
}

In production you set the same variable to your collector, Application Insights endpoint or vendor URL, and nothing else changes — no code, no package swap. That is the sentence to say out loud: Aspire’s observability is OpenTelemetry configuration, not an Aspire product.

Why is ServiceDefaults a template project rather than a NuGet package?

Because its content is policy, not mechanism. Sampling rates, retry aggressiveness, which health endpoints exist and whether they are public, what gets logged — these are decisions each organisation makes differently, and a package would either force one answer or grow a configuration surface as complex as the code it hides. Shipping it as source you own means editing it is normal, reviewable and diffable. The practical consequence in a multi-repo organisation is that you should not copy the template ten times; you take it once, adapt it to your standards, and publish your internal package or template from it. That is the answer that shows you have run this at scale rather than in a sample.

What does AddStandardResilienceHandler actually do?

It attaches a Polly v8 pipeline to the HttpClient, in a fixed order: a concurrency/rate limiter, a total request timeout (default around 30 s), a retry strategy with exponential backoff and jitter (a handful of attempts on transient failures and 5xx/408), a circuit breaker over a sampling window, and a per-attempt timeout (default around 10 s). Everything is configurable through options. The important behaviours to name: the total timeout bounds all attempts, so retries do not extend it indefinitely; the circuit breaker is per client, not per host by default; and it retries on transient HTTP conditions, which includes timeouts — hence the idempotency problem. In an interview, being able to say “timeout, retry, circuit breaker, and the ordering matters” is the differentiator.

Should /health be your Kubernetes readiness probe?

Usually not as-is. /health aggregates every registered check, including dependencies contributed by client integrations, so it answers “is everything I touch healthy”, which is a great question for a human and a bad question for a load balancer. If Redis is down and Redis is a cache, taking every pod out of rotation converts a degraded experience into an outage. My rule: liveness on /alive (process-level only), readiness on a curated set that includes only dependencies without which the service cannot serve any request — typically its primary datastore — and the full aggregate exposed internally for diagnostics. Aspire’s two-endpoint split plus health-check tags gives you exactly the machinery to express that.

How do you keep trace volume sane in production?

Change the sampler, and do it in ServiceDefaults so every service inherits it. A parent-based sampler with a ratio root (say 1–5%) keeps traces complete — either the whole trace is sampled or none of it is — while cutting volume by orders of magnitude. Add tail sampling in a collector if you want to keep all errors and slow requests, which is where most of the value is; that belongs in the OTel Collector, not in the app. Then reduce cardinality: strip high-cardinality route parameters from span names and metric labels, filter noisy spans (health probes are already filtered by the template), and be careful with per-customer attributes. Finally, remember logs: OTLP log export at debug level in production is the quiet way to a very large bill.

Does a service need ServiceDefaults to work with Aspire?

No. Aspire will happily run a project that never calls AddServiceDefaults — it will still be launched, still get environment variables, still get its connection strings. What you lose is telemetry in the dashboard (no OTLP configuration means no traces or metrics, only console logs), health checks that WaitFor can gate on, service-discovery resolution for logical names, and the resilience defaults. That makes ServiceDefaults the natural first step when adding Aspire to an existing solution, and it is also the piece to introduce gradually: a team can adopt ConfigureOpenTelemetry alone, get value from it in their existing environment, and adopt the AppHost later.

What is the relationship between health checks and WaitFor?

WaitFor(x) waits for x to be Running if x has no health check, and for x to be Healthy if it does. So adding WithHttpHealthCheck("/health") to a project materially strengthens every WaitFor pointing at it, and it is why containers from hosting integrations feel more reliable than hand-added ones — the integrations register proper checks (a TCP connect, a PING, a SELECT 1). The trap is a service whose /health depends on a dependency that is itself waiting on this service: you get a deadlock that looks like a hang. Keep health checks on the startup path shallow, and keep deep dependency checks out of whatever WaitFor or readiness consumes.

How do you handle secrets and PII in telemetry?

Assume the dashboard and your backend will show everything you export. Practically: turn off or filter db.statement-style attributes where queries embed values, scrub query strings on HTTP spans, avoid logging request bodies, and use the OTel processors in ServiceDefaults to redact rather than trying to police every call site. The dashboard specifically displays environment variables for each resource, so a secret passed as a plain parameter is visible to anyone who can reach the dashboard — mark it secret: true so it is masked, and never expose a dashboard beyond the developer’s machine without authentication. In regulated environments I would also review what the standard instrumentation captures by default before enabling it broadly, because “it is just OTel defaults” is not a compliance argument.

Where do custom metrics belong in this architecture?

Define a Meter in the owning service (or a shared library for cross-cutting domain metrics), register its name in the ServiceDefaults metrics callback, and let the OTLP exporter do the rest. Prefer a small number of well-chosen instruments — a counter for business events, a histogram for the operation you actually care about latency on — over mirroring everything. Two lead-level cautions: cardinality is the cost driver, so no customer ids or unbounded route values as tags; and metrics that duplicate what the runtime and ASP.NET Core meters already provide are pure overhead. The dashboard will chart them immediately, which is a good feedback loop for getting the shape right before they hit production volumes.

Your team wants retries everywhere. What do you say?

That retries are a correctness decision, not a reliability knob. The standard handler retries transient failures including timeouts, and a timeout does not tell you whether the server processed the request — so any non-idempotent operation needs either an idempotency key honoured by the server or a client that does not retry. I would split the clients: keep the standard handler as the default for reads and idempotent calls, configure a no-retry or retry-on-connect-failure-only pipeline for commands, and make sure retries exist at exactly one layer — if a gateway and the client both retry three times you have nine requests and a self-inflicted load spike during exactly the incident where you can least afford it. Then I would add a metric on retry counts so the behaviour is visible.

How do you roll ServiceDefaults changes across many repositories?

Turn it into an internal package or template with a version, because copy-paste source in twenty repos is unmaintainable — you will never again change a sampling rate consistently. The shape that works: an internal NuGet package that contains your organisation’s AddServiceDefaults, built from the Aspire template but owned by the platform team, versioned, with a changelog and a deprecation policy. Repos reference it and can still override individual pieces through options. The trade-off is you have recreated the “package versus source” tension Aspire deliberately avoided, so keep the package thin and every behaviour overridable, and expect to accept per-team escape hatches rather than mandating uniformity.

07 The dashboard and observability

The dashboard is a Blazor application that does two independent jobs, and separating them in your head explains everything about how it is deployed. Job one: it is an OTLP receiver with an in-memory store and a UI over structured logs, distributed traces and metrics. Job two: it is a resource console, talking gRPC to the AppHost’s resource service to list resources, stream console output, show environment variables and endpoints, and issue commands — start, stop, restart, plus any custom commands your resources declare.

Only job one works without an AppHost. That is standalone mode: run the dashboard container, point any OTel-instrumented application at its OTLP endpoint, and you have a local telemetry viewer for a Python service, a Java service, or an application that has never heard of Aspire. It is one of the most useful things in the box and it is frequently overlooked.

# Standalone dashboard: an OTLP viewer for any app, no Aspire required.
docker run --rm -it -p 18888:18888 -p 4317:18889 \
  -e DASHBOARD__FRONTEND__AUTHMODE=BrowserToken \
  mcr.microsoft.com/dotnet/aspire-dashboard:13.5

# Then in any service:
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
export OTEL_SERVICE_NAME=my-python-worker

Because the store is in memory and bounded, the dashboard is explicitly not a monitoring system: telemetry is capped (on the order of ten thousand log entries and traces by default, configurable), it disappears when the process restarts, and there is no query language, no alerting and no long retention. 13.2 softened the “it vanishes” problem by adding telemetry export and import — you can export what the dashboard holds and re-import it later or elsewhere, which is exactly what you want when a flaky test fails on CI and you want the traces on your laptop — plus HTTP APIs for reading telemetry programmatically. 13.0 added the Aspire MCP server, letting an AI coding agent query logs and traces from the running app directly instead of you copy-pasting; 13.5 removed the in-dashboard AI Assistant chat UI, so the agent story is now “your agent connects to Aspire”, not “Aspire has a chat box”.

Security matters more than people expect, because the dashboard shows environment variables — which is to say, connection strings and any parameter not marked secret. Locally the CLI opens it with a browser token in the URL. When you deploy it (Aspire can include the dashboard in Azure App Service and Container Apps deployments), it must be behind real authentication: it supports browser token and OpenID Connect for the frontend, and an API key for the OTLP endpoint so arbitrary senders cannot inject telemetry. “The dashboard is unauthenticated by default in standalone mode if you disable the token” is a genuine, findable misconfiguration.

Docs: Dashboard overview · Dashboard configuration and security

What is the dashboard architecture?

It is a Blazor Server app with two data planes. Telemetry arrives over OTLP (gRPC on 18889 by default, HTTP also supported) into a bounded in-memory store that backs the logs, traces and metrics pages. Resource information arrives over gRPC from the AppHost’s resource service, which streams resource state, endpoints, environment variables and console output, and accepts commands. That split is why standalone mode exists — drop the AppHost connection and you still have a complete OTLP viewer — and why the dashboard shows console logs for a resource that emits no telemetry at all. It also explains the security surface: two endpoints to protect, the frontend with browser token or OIDC and the OTLP ingress with an API key.

Can the dashboard be used in production?

Only with clear eyes about what it is. It is in-memory, capped, has no persistence, no alerting and no query language, so it is not a monitoring system. There are two legitimate production-adjacent uses: as a lightweight telemetry viewer for a small internal environment where standing up a full stack is disproportionate, and as a debugging surface in a staging environment. Aspire will even deploy it alongside your app on Azure App Service and Container Apps. If you do that, it must be authenticated — OIDC for the frontend, an API key on OTLP — and network-restricted, because it displays environment variables. For real production I fan telemetry into an OTel collector and forward to a proper backend, optionally keeping the dashboard as a second consumer.

What is the difference between console logs and structured logs in the dashboard?

Console logs are the raw stdout/stderr of the process or container, captured by the AppHost and streamed over gRPC — they exist for every resource including containers and non-.NET processes, and they are the only thing you get when a process dies during startup. Structured logs are ILogger records exported over OTLP, with attributes, levels, scopes and a trace id that links them to the trace view. The practical rule: startup failures, container image errors and stack traces from crashes live in console logs; anything you want to filter, correlate or search lives in structured logs. Knowing which pane to open is a small thing that makes you look experienced during a debugging screen.

How does a trace get from three services into one waterfall?

W3C trace context. The ASP.NET Core instrumentation starts (or continues) an Activity per incoming request and the HttpClient instrumentation injects traceparent on outgoing calls, so the child service continues the same trace id with the caller’s span as its parent. Everything downstream — EF Core commands, Redis calls, Service Bus sends — attaches spans to the ambient Activity, which is flowed on the async context. The exporter ships them independently to the dashboard, which reassembles by trace id, so partial traces appear while a request is still running. The pieces that break it are worth naming: manual HttpClient instances outside the factory, thread-hopping code that loses Activity.Current, and queue-based hops where you must propagate the context in message headers yourself.

What is the Aspire MCP server for?

It exposes the running application to AI coding agents through Model Context Protocol: the agent can list resources, read console and structured logs, and pull traces from the live app instead of you pasting them into a chat. Introduced in 13.0 and expanded since, it is part of a deliberate theme — 13.2 was explicitly “CLI as a first-class agent interface” — where the CLI and dashboard are designed to be driven by an agent as well as a human. Worth pairing with the 13.5 fact that the dashboard’s own AI Assistant chat UI was removed: the direction is Aspire as a well-instrumented target for external agents, not Aspire as an assistant. In an interview this is a good “what is current” answer.

Telemetry from a failed CI run is gone. What do you do?

Two options, and both are worth knowing. Since 13.2 the dashboard supports telemetry export and import, so a CI job can export the collected telemetry as an artifact and you can import it locally to browse the traces from a failure you cannot reproduce — that is the cheapest fix. The more robust option is to not rely on the dashboard in CI at all: run an OTel collector in the pipeline with a file exporter, or ship to your normal backend with a CI-specific service name and retention. Either way the underlying lesson is the dashboard’s store is ephemeral and bounded by design, and building a debugging workflow on it is building on sand.

How do you secure a deployed dashboard?

Frontend authentication first: browser token is fine for a laptop but not for anything shared, so use OIDC against your identity provider and restrict by group. Then the OTLP ingress: set an API key so arbitrary clients cannot push telemetry into your view (telemetry injection is a real, underrated attack — it can hide or fabricate evidence). Then the network: the dashboard should not be publicly routable; put it behind the same private ingress as your internal tools. Finally, remember what it displays — environment variables of every resource. Marking parameters as secret masks them, but the durable answer is to use managed identity so there are no credentials in the environment at all.

What are the dashboard’s retention limits and can you change them?

The store is in-memory and capped by count — on the order of 10,000 log entries and a similar cap for traces by default — with the oldest evicted first; the limits are configurable through dashboard configuration, but raising them just moves the memory cost onto your machine. There is no disk persistence and nothing survives a restart of the dashboard process. The design intent is “what happened in the last few minutes of this dev session”, and the correct response to needing more is to export (13.2+) or to point OTLP at a real backend. Being able to state that unprompted signals you have actually used it beyond a demo.

How do you get telemetry from a non-.NET resource?

Instrument it with the OTel SDK for its language and let Aspire supply the endpoint: the AppHost sets OTEL_EXPORTER_OTLP_ENDPOINT and OTEL_SERVICE_NAME on every resource it launches, including Python, JavaScript, Go and Java ones, so the app just has to honour them. For containers you do not control, the options are an OTel collector sidecar scraping their metrics endpoint, or accepting console logs only. The pattern to avoid is bespoke exporters per language pointing at different backends: keep OTLP as the single contract, which is exactly why Aspire’s polyglot support was built around setting standard OTel environment variables rather than around language-specific integrations.

What do custom resource commands add?

WithCommand lets a resource publish an action that appears as a button in the dashboard and, since 13.5, can take user-defined arguments that surface both as dashboard controls and as CLI options. Typical uses: reseed the database, flush the cache, rotate a test tenant, trigger a background job, toggle a feature flag. It turns the dashboard into a small operations console for the dev environment and removes a whole category of README instructions. 13.5 also added the experimental WithTerminal(), which hosts a REPL, shell or TUI for a resource inside the dashboard (with aspire terminal to attach from your own shell) — that is a strong “what shipped recently” answer, and its caveat is that anything you expose this way is a privileged action available to whoever can reach the dashboard.

08 Parameters, secrets and configuration

Every real system has values the model cannot invent: an API key for a third-party service, the administrator password for a database, a feature-flag endpoint that differs per environment, a tenant id. Aspire models these as parameters — first-class resources that can be referenced like any other, so a value flows through the graph rather than being pasted into three places.

var builder = DistributedApplication.CreateBuilder(args);

// Non-secret, environment-specific.
var region = builder.AddParameter("region");

// Secret: masked in the dashboard, stored securely by publishers.
var apiKey = builder.AddParameter("stripe-key", secret: true)
                    .WithDescription("Stripe restricted key for the sandbox account");

// Generated on demand — never typed by a human, stable across restarts.
var pgPassword = builder.AddParameter("pg-password", secret: true,
                     value: ParameterDefault.CreateGenerated(minLength: 24));

var pg = builder.AddPostgres("pg", password: pgPassword);

// A connection string owned by someone else (Terraform, the platform team).
var reporting = builder.AddConnectionString("reporting");

builder.AddProject<Projects.Api>("api")
       .WithReference(reporting)
       .WithEnvironment("STRIPE_KEY", apiKey)
       .WithEnvironment("REGION", region);

Resolution follows normal .NET configuration precedence in the AppHost, under a Parameters section: environment variables (Parameters__stripe-key), then configuration files including user secrets — which is where a developer’s values belong, never appsettings.json — and finally an interactive prompt. The prompt is the nice part: if a parameter has no value, the CLI or the dashboard asks for it, with the description and any custom input type you declared through WithCustomInput, and in publish mode aspire deploy asks and can persist the answer in deployment state so the next run does not ask again.

  },

If you upgrade from 13.0/13.1 this is one of the migrations you actually have to do, and it is a good thing to mention as evidence you have done a real upgrade rather than a greenfield sample.

The distinction between a parameter and a connection string is worth stating crisply because interviews probe it. AddParameter is a value; AddConnectionString is a value that behaves like a resource with a connection string, so consumers can WithReference it and client integrations find it under ConnectionStrings:name exactly as they would for a container Aspire started. That is the seam between Aspire-managed and externally-managed infrastructure, and it is how you adopt Aspire in an organisation where the databases are already provisioned by Terraform. Note the 13.5 deprecation: PublishAsConnectionString is obsolete, use AddConnectionString in publish-mode app model code.

How do secrets flow through an Aspire application?

Declared in the AppHost as AddParameter(name, secret: true), sourced at run time from environment variables, user secrets or an interactive prompt, then injected into the consuming resource’s environment through WithEnvironment or a connection string. At publish time the secret flag changes the artifact: a placeholder plus a .env for Compose, a secure parameter or Key Vault reference for Bicep, a Secret for Kubernetes. Nothing is encrypted at rest by Aspire itself, and the value is plaintext in the child process environment. So the honest summary is: Aspire gives you a consistent way to declare and route secrets, and you still need a real secret store and, ideally, credential-free authentication in production.

When do you use AddConnectionString instead of adding the resource?

When someone else owns the resource. If the database is provisioned by Terraform, managed by a platform team, or shared across applications, you do not want Aspire creating it — but you do want it to be a node in the model so that consumers reference it uniformly and client integrations find it. AddConnectionString("reporting") gives exactly that: a referenceable resource whose value comes from configuration. It is also the standard incremental-adoption move: model everything as connection strings first, then convert the ones you genuinely want Aspire to run into AddPostgres etc. Note the 13.5 change — PublishAsConnectionString is obsolete in favour of AddConnectionString in publish-mode code.

What is aspire.config.json?

The single configuration file introduced in 13.2 that consolidated what used to be spread across .aspire/settings.json, environment variables and ad-hoc files: which AppHost the CLI should use, feature settings, and per-environment configuration for the CLI and publishing. It sits at the repo root and is committed. The practical relevance is upgrade work — a 13.0/13.1 repo needs the migration — and discoverability: a new joiner can see how the repo is wired without reading shell history. It also matters for multi-AppHost repos, where the CLI otherwise has to guess or be told which AppHost to run.

How do you avoid every developer being prompted for the same parameters?

Give non-secret parameters a default in the AppHost’s appsettings.json (committed, since they are not secrets), and keep secrets in user secrets with a documented dotnet user-secrets set block in the README or, better, a small setup script or a custom aspire do step that seeds them from your team’s vault. For shared dev credentials, the strongest option is not to have any: use developer identity — DefaultAzureCredential picking up the developer’s Azure login locally and managed identity when deployed, which is exactly what 13.0’s credential change formalised for deployed environments. Generated parameters cover the third case, passwords for local containers that nobody should ever choose or share.

How does aspire deploy handle parameters differently from aspire run?

In run mode, unresolved parameters are prompted for interactively and used immediately. In publish mode, parameters become part of the artifact contract: non-secrets can be inlined, secrets become references to a secure store, and aspire deploy resolves them — prompting if needed — and records the answers in deployment state, so the next deploy to the same environment reuses your Azure subscription, resource group and previously supplied values instead of asking again. That state was a headline 13.0 feature and it is what makes repeated deploys tolerable. For CI you avoid prompts entirely by supplying every parameter as an environment variable, which is the shape you should design for from the start.

What is a generated parameter and when is it right?

ParameterDefault.CreateGenerated produces a value — typically a password — with a length and character policy, generated once and kept stable across restarts by being persisted in user secrets or deployment state. It is right whenever a credential exists only because a piece of software demands one and no human should ever know it: the Postgres superuser password for a local container, an internal service token between two components you both own. It is wrong for anything a person or another system must also know, and it is not a substitute for a secret manager in production. The benefit beyond convenience is cultural: a generated password cannot be the one from the wiki that also works in staging.

A parameter changed and services did not pick it up. Why?

Because parameter values are resolved when a resource starts and injected as environment variables — there is no live reload. Changing user secrets or the config file requires restarting the affected resource, which you can do from the dashboard rather than restarting the whole app. If you need genuinely dynamic configuration, that is a different mechanism: a configuration provider in the service (Azure App Configuration, a config service, a file watcher on a mounted volume) that Aspire simply points at. This is a good question to answer with the general principle: Aspire’s configuration flow is start-time injection, so anything requiring runtime refresh must be modelled inside the service, not in the app model.

How do you keep a Compose or Bicep artifact free of secrets?

Mark them secret and let the publisher do the right thing — Compose gets a git-ignored .env, Bicep gets secure parameters or Key Vault references, Kubernetes gets Secrets — then verify by reading the artifact, because “I assumed it was handled” is how credentials reach a repository. In CI, supply the values as pipeline secrets mapped to Parameters__* environment variables so nothing interactive is required and nothing is written to disk. And prefer to eliminate the secret: managed identity to Azure resources, workload identity in Kubernetes, IAM roles on AWS. The published artifact should ideally contain no credential at all, only identity references — that is the bar I would hold a design review to.

Where do you draw the line between Aspire config and app config?

Aspire owns topology and wiring: which resources exist, how they find each other, and the values that differ per environment because of that topology — endpoints, connection strings, credentials for infrastructure. The service owns its own behavioural configuration: feature flags, business thresholds, cache durations, retry policy details. Blurring them creates AppHosts that become a second configuration system for the whole company, with a change to a timeout requiring an AppHost deployment. My rule in review: if the value would still exist if the service ran alone with no Aspire, it belongs in the service’s configuration; if it only exists because two resources need to find each other, it belongs in the app model.

How do you handle multiple environments (dev, staging, prod) in one AppHost?

Prefer parameters plus deployment state over branching on an environment name, because if (env == "prod") in the AppHost is how the model quietly stops describing production. Concretely: the resource graph stays the same across environments; parameters carry the differences; publish-mode compute environment selection picks the target; and aspire deploy keeps per-environment state so subscriptions, resource groups and prior answers are remembered. Where the graph genuinely differs — a dev-only mail catcher, a prod-only WAF — isolate it behind IsRunMode or a single, obvious, named helper. The failure I have seen most is nested environment conditionals in the AppHost until nobody can say what production looks like without running the publisher; at that point the model has stopped being the source of truth.

09 The dev loop: containers, data, lifetimes

Adoption succeeds or fails on the inner loop. If aspire run takes ninety seconds and wipes your database every time, people go back to the compose file. Aspire has a small vocabulary for controlling that, and knowing it is the difference between a pleasant environment and a slow one.

Start with where the data lives. A container with no volume loses everything on every run — fine for a cache, infuriating for the database you just seeded with a realistic dataset. WithDataVolume() creates a named Docker volume for the container’s data directory, so it survives restarts and is the sane default for a local database. WithDataBindMount(path) puts the data in a host folder instead, which you should reach for only when you genuinely need to inspect or ship those files, because bind mounts bring permission and portability pain. And WithInitBindMount/WithInitFiles-style helpers on several integrations let you drop SQL or scripts into the image’s initialisation directory so a fresh volume gets seeded automatically.

Then how long the container lives. By default a container is created when the AppHost starts and destroyed when it stops. WithLifetime(ContainerLifetime.Persistent) changes that: the container survives AppHost restarts and is reused, keyed by a hash of its configuration, so restarting your app becomes near-instant instead of paying container startup again. This is the single biggest inner-loop win in Aspire and it is under-used. The cost is that stale state now persists across sessions and configuration changes recreate the container, so you need to know how to blow it away (stop it in Docker, or change the configuration) when something is wedged.

var pg = builder.AddPostgres("pg")
    .WithDataVolume()                                   // data survives restarts
    .WithLifetime(ContainerLifetime.Persistent)         // container survives too
    .WithPgAdmin();                                     // run-mode admin UI, own container

var db = pg.AddDatabase("catalogdb")
           .WithCreationScript(File.ReadAllText("./db/schema.sql"));

var kafka = builder.AddKafka("kafka")
    .WithKafkaUI()
    .WithExplicitStart();                               // idle until someone needs it

var legacy = builder.AddContainer("legacy-sql", "mcr.microsoft.com/mssql/server", "2022-latest")
    .WithEnvironment("ACCEPT_EULA", "Y")
    .WithEnvironment("MSSQL_SA_PASSWORD", saPassword)
    .WithEndpoint(port: 1433, targetPort: 1433, name: "tcp")
    .WithImagePullPolicy(ImagePullPolicy.Missing)       // do not re-pull every run
    .WithContainerRuntimeArgs("--memory=2g");

The third lever is what starts at all. WithExplicitStart() keeps a resource in the model but idle. On a large graph this is how you keep aspire run honest without forcing everyone to boot the whole company. Combined with dashboard start/stop and custom commands, the dev loop becomes: start the slice you are working on, start extra dependencies on demand, and never edit the AppHost to disable something.

Finally, hot reload and debugging. Because projects run as ordinary processes, F5 from Visual Studio, JetBrains Rider or VS Code attaches to them normally, and dotnet watch-style hot reload works. The VS Code extension gained a lot here: a dedicated Aspire panel in the Activity Bar and inline CodeLens for resource state in 13.2, plus debugging for polyglot resources including Go in 13.5. Debugging containers is different — you attach to the process inside, or you do not debug them at all — which is a good reason to run the code you are working on as a project resource rather than as a container.

Gotcha

Persistent containers are a double-edged tool and the second edge is sharp. Because the container is reused based on a hash of its configuration, a developer can end up running last week’s Postgres with last week’s schema while their branch expects a new column — and the symptom is a mystifying runtime error, not an obvious “stale container” message. The habits that avoid it: make migrations a modelled resource so the schema is applied on every start (unit 03); document one command to reset (docker rm -f the persistent containers, or delete the volume); and do not make everything persistent — reserve it for slow, stable dependencies like databases, not for the thing you are actively changing. The related trap is the opposite: adding WithDataVolume to a container whose image writes data somewhere other than the expected path, quietly persisting nothing at all.

Try it

1. Measure cold aspire run time, then add WithLifetime(ContainerLifetime.Persistent) to your database and cache and measure again. 2. Deliberately wedge it: change the database image tag, restart, and see what happens to your data.

Expected outcome

The first typically cuts startup dramatically — on a graph with Postgres, Redis and a broker, tens of seconds down to a few — because the expensive part was never your code, it was container creation and readiness. Write the numbers down: this is the concrete evidence that wins the “Aspire makes my machine slow” argument. The second shows the recreation rule: changing configuration that participates in the container identity forces a new container, so the old volume may or may not be reattached depending on how you named it — which is exactly the confusion to pre-empt with a documented reset command and migrations that run on every start.

How do you make aspire run fast on a large graph?

Four levers, in order of impact. Persistent container lifetimes for stable dependencies, so container creation is paid once rather than per run. ImagePullPolicy.Missing so Docker does not check registries on every start. WithExplicitStart for expensive resources most developers do not need, turning a 20-resource boot into a 6-resource boot. And splitting the graph so a developer can run a slice — either by configuration read in the AppHost or by having more than one AppHost for genuinely separate subsystems. Beyond that, the honest answer is that the remaining time is your own services’ startup, which is now measurable in one place, and that measurement usually finds something worth fixing.

Volume, bind mount, or nothing — how do you choose?

Nothing for anything genuinely ephemeral: caches, brokers in tests, emulators you want clean. A named volume for data you want to keep across runs but never touch from the host — local databases are the canonical case, and it is the portable choice because Docker owns the path and permissions. A bind mount only when the host must see or provide the files: seed SQL you edit, certificates, a folder of fixtures, an output directory you inspect. The reason to prefer volumes is that bind mounts encode absolute host paths and Unix permissions, which breaks between Windows, WSL and macOS and makes the AppHost machine-specific — and none of it survives publishing, so a bind mount is always a run-mode-only decision.

What is ContainerLifetime.Persistent and what are its risks?

It tells DCP to keep the container alive between AppHost runs and reuse it, identified by a hash of its configuration, instead of creating and destroying it each session. The benefit is a much faster inner loop and preserved state. The risks are staleness — an old container with an old schema or old data silently serving a new branch — and resource leakage, since these containers keep running after you stop working and can accumulate. My guidance: use it for databases, caches and brokers; do not use it for anything under active development; make schema application idempotent and automatic so staleness self-heals; and give the team a documented reset command, because the failure mode is confusing enough that people otherwise reinstall Docker.

How does debugging work across a distributed Aspire app?

Project resources are ordinary processes, so your IDE attaches to them normally — set breakpoints in two services and step across an HTTP call, with the trace in the dashboard showing you the path. Visual Studio and Rider launch the AppHost and attach to children automatically; VS Code gained a dedicated Aspire panel and inline resource-state CodeLens in 13.2, and polyglot debugging including Go in 13.5. The awkward cases are replicas (you attach to one instance, so make sure the request lands there — reduce to one replica while debugging) and containers (you are debugging inside an image, which usually means you should have modelled that component as a project instead). Console logs remain the fallback for anything that dies before the debugger attaches.

A developer says Aspire eats their laptop. What do you do?

Measure first: the dashboard shows per-resource state and your container runtime shows memory, and usually two or three resources dominate — a SQL Server image, a search cluster, an emulator. Then apply the levers: explicit start for those, memory limits via container runtime args, persistent lifetimes so the cost is paid once, and a slice-based launch so nobody runs the whole graph by default. If the graph is genuinely too big for a laptop, that is architectural feedback, and the answer may be shared dev infrastructure modelled with AddConnectionString/AddExternalService rather than local containers. What I would not do is let each developer solve it by commenting out resources, because that drift is invisible and ends up committed.

How do you seed realistic data?

Three options with different trade-offs. Creation/init scripts attached to the database resource run when the data directory is initialised — simple, but only on a fresh volume. A dedicated seeder resource (a project or container) with WaitFor(db), ideally idempotent, gives you full language power and reruns on demand via a dashboard command; this is my default. Or bake data into a custom image, which is fastest to start and worst to maintain. Whatever you choose, keep seeding out of your application’s startup path — a service that seeds itself will race under replicas and will eventually run in an environment you did not intend. And make the dataset small enough that a reset is cheap; nobody resets a 40-minute seed.

How do you handle a dependency that has no usable container?

Model it honestly rather than pretending. Options in order of preference: an emulator if the vendor ships one (RunAsEmulator covers Azure Storage, Cosmos DB, Service Bus and Event Hubs); a shared dev instance referenced with AddConnectionString or AddExternalService, with a parameter for the URL and per-developer credentials via developer identity; a stub or WireMock container that implements the contract you depend on, which is often better for tests than the real thing; or, last, a build-time flag that disables the feature locally, which must be visible in the model rather than hidden in code. The mistake is a local fake with materially different semantics — a queue that never reorders, a store that is strongly consistent when the real one is not — because it manufactures confidence rather than removing risk.

Do you run your own service as a container locally?

Rarely, and only deliberately. Running it as a project resource keeps hot reload, breakpoints, fast rebuilds and a real stack trace; containerising it costs an image build on every change and gives up the debugger. The times it is worth it: verifying the Dockerfile itself, reproducing a container-only bug (file permissions, missing native dependency, culture or timezone differences), or when the component is not .NET and containerising is the natural way to run it. A useful pattern is having both available — the project as the default and a container variant behind a flag — so you can flip when you need to, which is much easier in an app model than in a hand-written compose file.

What breaks when a teammate has Podman instead of Docker?

Mostly nothing — Aspire supports Docker Desktop, Podman and Rancher Desktop — but the edges are real: rootless Podman changes file ownership semantics for bind mounts, network aliasing and host-gateway behaviour differ slightly, and some images assume Docker-specific defaults. The mitigations are the same practices that make the setup portable anyway: prefer volumes to bind mounts, do not hard-code host ports, and avoid depending on container names or the default bridge network. aspire doctor (13.2+) is the first thing to run when a machine misbehaves, because it checks the runtime, SDK, certificates and CLI versions and turns “it does not work on my machine” into a concrete list.

How do you keep dev-only resources out of production artifacts?

Guard them with builder.ExecutionContext.IsRunMode, and keep them together so a reviewer can see them at a glance. Admin UIs from integrations (WithPgAdmin, WithRedisInsight, WithKafkaUI) are already run-mode-only by construction in most integrations, but hand-added containers — mail catchers, mock services, seeders, tracing debuggers — are not. Then verify rather than trust: aspire publish -o out in CI and a check that the artifact contains only the expected resources is a cheap regression test, and it catches the day someone adds a debugging container without the guard. This is the same class of control as “which endpoints are external”, and I would review both in the same pass.

10 Testing distributed apps

Aspire’s testing story is the app model turned into a fixture. Aspire.Hosting.Testing gives you DistributedApplicationTestingBuilder, which builds and optionally starts your real AppHost from a test project, so your integration test gets the same topology developers get — the same containers, the same wiring, the same connection strings — without a bespoke test harness or a second compose file.

public class CatalogApiTests
{
    [Fact]
    public async Task Get_products_returns_seeded_items()
    {
        var appHost = await DistributedApplicationTestingBuilder
            .CreateAsync<Projects.MyApp_AppHost>();

        appHost.Services.AddLogging(l => l
            .AddFilter("Aspire.Hosting.Dcp", LogLevel.Warning));   // DCP is chatty

        appHost.Services.ConfigureHttpClientDefaults(http =>
            http.AddStandardResilienceHandler());

        await using var app = await appHost.BuildAsync();
        await app.StartAsync();

        await app.ResourceNotifications
                 .WaitForResourceHealthyAsync("catalog-api")
                 .WaitAsync(TimeSpan.FromMinutes(2));

        var client = app.CreateHttpClient("catalog-api");
        var response = await client.GetAsync("/products");

        Assert.Equal(HttpStatusCode.OK, response.StatusCode);
    }
}

The three APIs that matter: CreateAsync<TAppHost>() to get the builder (you can mutate the model here — swap a resource, add a parameter, remove something expensive); app.ResourceNotifications.WaitForResourceHealthyAsync(name) to wait for readiness instead of sleeping; and app.CreateHttpClient(name, endpointName) to get a client pointed at a resource’s allocated endpoint, with service discovery already resolved. Templates exist for xUnit, MSTest and NUnit (dotnet new aspire-xunit and friends).

The judgment question — the one that separates levels — is how much of your suite should look like this. The answer is: a thin layer. Starting the whole graph costs container startup per fixture, needs Docker on every CI agent, and produces tests whose failures are ambiguous (was that the assertion, or a slow container?). The shape I recommend: the bulk of tests are unit tests with no Aspire at all; a middle layer uses WebApplicationFactory with a real database container via Testcontainers or a single Aspire-managed dependency; and a small top layer — a handful of true smoke tests over the whole model — uses the testing builder. Share one application instance across a test class or collection rather than per test, and keep those tests boring: does the graph start, do the services find each other, does the happy path return 200.

Interview trap

The trap is enthusiasm: “now every test can run the whole system!”. That produces a suite that takes forty minutes, needs Docker on every agent, and flakes in ways nobody can reproduce — and the team’s response is to disable tests, which is worse than not having them. The lead answer names the cost model out loud: containers per fixture, parallelism limits, port pressure, image pull time on cold agents, and the ambiguity of a failure. It also names the underused half — building the model without starting it is nearly free and catches a genuinely valuable class of bug: a service missing a WithReference, a secret not marked secret, a new resource accidentally given WithExternalHttpEndpoints. Structural assertions over the app model are the highest value-per-millisecond tests Aspire enables, and almost nobody writes them.

Try it

1. Write a test that builds the model without starting it and asserts that no resource except the gateway has external HTTP endpoints, and that every project has a health check. 2. Then write one real smoke test and time it on a cold machine.

Expected outcome

The structural test runs in milliseconds and will very likely fail the first time — most AppHosts have at least one accidental external endpoint or an unhealthy-checked service. Wire it into CI and it becomes a permanent guard on two things reviewers routinely miss. The smoke test is the reality check: on a cold agent, expect image pulls plus container readiness before your assertion even runs, which tells you the real budget for this layer and therefore how many such tests you can afford. Do both and you will naturally arrive at the recommended pyramid rather than arguing about it in the abstract.

How does DistributedApplicationTestingBuilder work?

It loads your AppHost assembly, runs its entry point to produce the resource graph, and hands you the builder before Build() — so you can mutate the model — then lets you build and start a real DistributedApplication in-process. From there you get the resource notification service for readiness, an HttpClient factory that resolves resource endpoints, and access to the model for assertions. Because the AppHost is executed, everything a developer gets locally is what the test gets, which is the whole point: no separate compose file to drift. The costs are equally real — containers start, ports are allocated, and teardown must be awaited or you leak containers between runs.

How do you avoid flaky Aspire integration tests?

Never sleep; wait on the resource notification service for a resource to be Healthy, which requires the resource to actually have a health check — that is a prerequisite people skip and then wonder why they get connection-refused races. Give the wait a generous but bounded timeout, longer on cold CI than locally. Share one application per test class or collection rather than starting it per test, and be careful with parallelism, which multiplies container count and port pressure. Make tests independent of leftover data by seeding per test or using unique keys. And disable retry policies in the test client where you are asserting failure behaviour, or a resilience handler will paper over exactly the bug you are testing for.

What can you assert about the model without starting anything?

A surprising amount, all of it cheap: every project resource has a health check; only the intended resources have external endpoints; every service that uses the database declares a reference to it; every parameter that looks like a credential is marked secret; resource names match your convention; no dev-only container escapes its IsRunMode guard; the number of resources has not grown unexpectedly. These are architectural rules expressed as tests, they run in milliseconds, and they fail with a precise message at PR time instead of during a security review. I consider this the most under-appreciated feature in Aspire’s testing story.

Should CI run the full graph?

Once, as a smoke stage, and not in the fast feedback loop. My layout: a PR pipeline that runs unit and model tests in under a couple of minutes with no Docker, plus component tests against single containers; then a post-merge or nightly stage that starts the full model and runs a handful of end-to-end journeys. That keeps the signal that matters — “the app actually composes” — without taxing every push. Practical requirements to plan for: agents with a container runtime and enough memory, image caching or a pull-through registry to avoid re-downloading, and a hard timeout so a hung container fails fast rather than consuming the job budget.

How do you substitute a resource in a test?

Mutate the model before building: find the resource in appHost.Resources and remove or replace it, or add configuration that overrides it — for example, replace a cloud-backed resource with a container, swap a third-party dependency for a WireMock container, or point an AddExternalService at a stub you start in the fixture. You can also inject configuration into the AppHost builder so parameters resolve to test values without prompts. The design implication is worth noting: an AppHost written as pure declaration is easy to mutate this way, while one full of side effects and environment reads is not — testability is another argument for keeping the app model declarative.

What is the relationship between this and Testcontainers?

They overlap and they compose. Testcontainers gives a test full control over individual containers with no app model; Aspire’s testing builder gives you the whole modelled topology. For a component test of one service against one real database, Testcontainers (or a single Aspire resource) is lighter and more focused. For a test that the system composes correctly, only the app model gives you that. Many teams end up with both, and that is fine as long as it is deliberate — the anti-pattern is maintaining two descriptions of the same dependency, where the Testcontainers image version drifts from the AppHost one. If you keep both, source the image and tag from one place.

How do you get useful logs out of a failing test?

Route the application’s logging into the test output — appHost.Services.AddLogging(...) with the framework’s logging bridge (MartinCostello.Logging.XUnit, the NUnit logging extension) — and filter Aspire.Hosting.Dcp to Warning, because DCP is extremely verbose and will bury your signal. Remember that configuration files from your services are not automatically inherited by the test host, so log levels must be set explicitly. For cross-service failures, telemetry beats logs: since 13.2 you can export the dashboard’s telemetry and import it locally, so a CI job can attach the traces from a failed run as an artifact. That workflow turns “cannot reproduce” into an actual waterfall you can read.

How do you test the published artifacts, not just the run-mode app?

Run aspire publish in CI and assert on the output. At minimum, check that it succeeds — publishing exercises code paths that run mode never does, and a publish break otherwise surfaces at deploy time. Beyond that, snapshot-test the generated Compose or Bicep so a diff shows up in review when someone changes topology, and add assertions for the rules you care about: no plaintext secrets, only the expected external ingress, image tags pinned. For real confidence, deploy the artifacts to an ephemeral environment and run the smoke suite against it — that is the only way to catch the class of bug where run mode and publish mode diverge, which is precisely where Aspire’s two-mode design carries risk.

Is there a place for Aspire in load or contract testing?

Indirectly. The app model makes it trivial to add a load generator (k6, NBomber, Locust) as a resource pointed at your gateway, and to add a contract-verification container to the graph, so those tools stop being someone’s local script. But the environment is a laptop or a CI agent, so absolute numbers are meaningless — treat it as change detection (“this PR made the p99 three times worse”) rather than capacity planning. For contract testing, the more valuable Aspire angle is that consumer and provider run together with real wiring, which catches the integration mistakes that pure contract tests miss. I would still do capacity work in a production-like environment against deployed artifacts.

What is your policy on test data and isolation?

Prefer per-test isolation that is cheap: unique tenant ids, prefixes or schemas rather than a fresh database per test, because container startup dominates. Where a fresh database is needed, create it per test class from a template or use the database-per-test-class pattern against one server container. Never share mutable global state between tests running in parallel — the classic failure is two tests seeding the same key and passing individually but failing together, which reads as flakiness and burns days. And keep the seed small: the temptation with a realistic local dataset is to test against production-like volumes, which makes every test slow and every failure ambiguous. Realistic data belongs in the dev environment; tests want minimal, explicit fixtures.

11 Publish and deploy: the pipeline model

This is the half of Aspire that changed most in 13.x, and the half where candidates are most likely to be out of date. The old world had a manifest file and azd reading it. The current world has a pipeline: your AppHost runs in publish mode, resources and API calls contribute steps, the steps are resolved into a dependency graph and executed with parallelism where possible.

The two verbs are deliberately distinct. aspire publish produces artifacts — a Compose file, Kubernetes manifests, Bicep modules, container images — parameterised, and stops. It is a one-way handoff: hand the output to a platform team, a GitOps repo or an existing pipeline. aspire deploy goes further: it resolves parameters (prompting or reading deployment state), applies the artifacts to a target environment, and remembers what it did so the next deploy does not re-ask for your subscription and resource group. aspire do <step> is the lower-level entry point into the same pipeline, with --list-steps to see what would run — which is how you debug a deployment that is doing something surprising.

aspire publish -o ./artifacts        # generate artifacts, stop
aspire deploy                        # generate, resolve params, apply
aspire do --list-steps               # what would run, and in what order
aspire do build push                 # run specific steps and their dependencies
// Choosing a compute environment is a publish-mode decision.
var builder = DistributedApplication.CreateBuilder(args);

builder.AddAzureContainerAppEnvironment("cae");
// or: builder.AddDockerComposeEnvironment("compose");
// or: builder.AddKubernetesEnvironment("k8s");

var api = builder.AddProject<Projects.Api>("api")
                 .WithExternalHttpEndpoints();

// A custom step in the pipeline (replaces 9.x publishing callbacks).
builder.AddPipelineStep("smoke-test", async ctx =>
{
    // ... hit the deployed endpoint, fail the pipeline if it is unhealthy
})
.DependsOn(WellKnownPipelineSteps.Deploy);

Well-known steps give you the vocabulary: Publish (artifact generation), Build and Push (container images), Deploy (the primary entry point), and prerequisite steps such as DeployPrereqs, BuildPrereq, PublishPrereqs and PushPrereq. Steps declare DependsOn/RequiredBy, the resolver rejects cycles and dangling references, and execution is parallel where the graph allows. Custom steps are how you add smoke tests, database migrations, cache warming, CDN purges or notifications — and they are what replaced the publishing callbacks and lifecycle hooks that 13.0 deleted.

Targets, as of 13.5: Azure Container Apps (the deepest integration, including deployment slots and the dashboard deployed alongside), Azure App Service, Azure Kubernetes Service, generic Kubernetes, Docker Compose (stable since 13.2), and Radius in preview. 13.2 also added Azure Virtual Network and private endpoint support, which is the feature that unblocks regulated environments where nothing may be publicly routable. Note also that pipeline APIs are still marked experimental in 13.x — the compute-environment types carry an evaluation-only diagnostic — so a lead should be careful about building a company-wide deployment platform on them without an upgrade plan.

Explain publish versus deploy.

Publish runs the AppHost in publish mode and emits parameterised deployment artifacts — Compose YAML, Kubernetes manifests, Bicep — plus, where relevant, built and pushed container images. It stops there, which makes it a clean handoff to a GitOps repo, a platform team or an existing CD pipeline, and the artifacts are diffable in review. Deploy runs the same generation and then applies it: resolving parameters (prompting or reading persisted deployment state), provisioning infrastructure and rolling out the services. The organisational split is what matters: publish keeps Aspire out of your delivery governance, deploy makes Aspire part of it. I default to publish for anything with real users and deploy for ephemeral environments where speed beats ceremony.

What is aspire do and why did it replace publishing callbacks?

aspire do is the pipeline runner: steps registered by resources and by your own code, resolved into a dependency graph, executed with parallelism, and individually invocable. It replaced 9.x publishing callbacks and lifecycle hooks — deleted in 13.0 — because callbacks were opaque and serial: you could not see what would run, could not run part of it, and could not express that two independent steps may proceed concurrently. With explicit steps you get --list-steps, selective execution, dependency validation that rejects cycles, and a natural place to hang custom work like migrations or smoke tests. The caveat to voice: these APIs are still experimental in 13.x, so pin versions and expect churn.

How would you fit Aspire into an existing GitHub Actions or Azure DevOps pipeline?

A build job that restores, builds and tests as usual, then runs aspire publish -o ./artifacts with every parameter supplied as an environment variable so nothing prompts. Upload the artifacts. Then environment-specific jobs apply them with the tooling the organisation already trusts — kubectl/Helm/Flux for Kubernetes, az deployment for Bicep, docker compose up for a small target — behind whatever approvals exist. Add a check that diffs the artifacts against the previous run so an unexpected infrastructure change is visible before it is applied. This shape keeps Aspire in the build stage where its fast release cadence is low-risk, and keeps deployment governance where it already lives.

What is deployment state and what are its risks?

Deployment state is the record aspire deploy keeps of what it deployed and with what values — the Azure tenant, subscription, resource group, and previously answered parameters — so repeat deploys are not an interrogation. The benefit is real: without it, deploying is unusable for iterative work. The risks are equally real. It is a piece of local or repo-adjacent state that determines what production-shaped thing you are about to change, so it must never be shared casually or committed with production values; a stale entry can point a deploy at the wrong environment; and it can hide the fact that a parameter was answered once, months ago, by someone who has left. In a team setting I would rather supply parameters explicitly in CI and keep state out of the loop entirely.

How do you handle infrastructure Aspire should not own?

Model it as a reference rather than a resource: AddConnectionString for a database Terraform provisions, AddExternalService for a service someone else runs, parameters for anything else. Then the published artifact contains a reference and a parameter, not a provisioning template, and the platform team’s ownership is unambiguous. Where Aspire does provision — and its Azure integrations will happily create databases, caches and namespaces — decide that explicitly per resource, because the default is convenient and easy to adopt accidentally. The clearest boundary I have used in practice: Aspire may create anything ephemeral or per-application, and may reference but never create anything durable or shared.

What does the Azure Container Apps path actually generate?

Bicep: a container-apps environment, a container app per compute resource with ingress configured according to your external-endpoint declarations, environment variables carrying the service-discovery and connection-string values computed from the model, managed identity plus role assignments for the Azure resources you referenced, and modules for those resources themselves (Redis, Postgres, Service Bus, storage). 13.2 added Virtual Network and private endpoint support, and deployment slots; 13.0 made the dashboard deployable alongside the app. The two things to review carefully in that output are which apps got external ingress and which role assignments were granted — Aspire is generous by default in the interest of things working, and least privilege is your responsibility.

Is Docker Compose publishing production-ready?

The integration is stable as of 13.2, meaning the generated docker-compose.yaml is a supported output rather than a preview. Whether Compose is a production-ready platform is a separate question and usually the answer is no for anything with uptime requirements — no rolling updates worth the name, no scheduling, single host. Where it genuinely shines is single-node deployments, on-premises boxes, edge installations, customer-hosted appliances and CI environments, and it is an excellent bridge for teams who want Aspire’s model without Kubernetes. It is also the fastest way to show a skeptical team what Aspire believes the app is, because a Compose file is something everyone can read.

How do you do zero-downtime deployments with Aspire?

You do not — the target does. Aspire produces artifacts; rolling updates, readiness gating, surge capacity and traffic shifting come from Azure Container Apps revisions, Kubernetes deployment strategies or App Service slots. What Aspire contributes is the inputs those mechanisms need: correct readiness signalling through health checks, endpoints that are declared rather than assumed, and migrations modelled as a separate step so schema changes can be sequenced ahead of the rollout. The application-level work is unchanged and is where the real difficulty lives: backwards-compatible schema changes, expand-then-contract migrations, and not breaking in-flight messages. Saying that clearly is a strong signal, because it shows you know which problems a tool can and cannot move.

How do you review an AppHost change that affects deployment?

I read the artifact diff, not just the C#. aspire publish in CI on every PR, with the output diffed against the base branch, turns an innocuous-looking one-line change into a visible infrastructure change — a new public ingress, a new role assignment, a changed image tag, a resource that will be recreated rather than updated. Then I check the usual suspects by hand: external endpoints, secrets, whether anything durable is being provisioned by Aspire that should be referenced instead, and whether resource names changed (which can mean deletion and recreation in the target). This is the same discipline as reviewing a Terraform plan, and Aspire without it is Terraform without plan.

What would make you keep Aspire out of deployment entirely?

An organisation with an established platform: golden pipelines, Terraform modules with policy, a service catalogue, environment promotion and audit requirements. In that world Aspire’s deployment half is a competing standard with a fast, still-partly-experimental API surface, and the political cost of introducing it exceeds the benefit. I would take the dev-loop value, use aspire publish at most for ephemeral PR environments, and keep production on the existing rails. The other trigger is regulatory: if every infrastructure change must be reviewed as declarative IaC in a specific format with specific approvals, generated Bicep that changes shape between Aspire minors is a poor fit — and the Modern Lifecycle policy means you cannot simply freeze the version.

12 Polyglot Aspire and the CLI

The 13.0 rebrand was not marketing; it followed a real change in scope. Aspire now models Python, JavaScript/TypeScript, Go and Java resources as first-class citizens rather than as “an executable you happen to run”, and since 13.5 the AppHost itself can be written in TypeScript. For a .NET lead this matters in a very practical way: the front end and the ML service that used to live outside your dev environment can now be inside the same model, with the same telemetry, the same discovery names and the same publish path.

var api = builder.AddProject<Projects.Api>("api");

// JavaScript / TypeScript: package manager auto-detected, Vite aware.
var web = builder.AddJavaScriptApp("web", "../web", scriptName: "dev")
                 .WithReference(api)
                 .WithHttpEndpoint(env: "PORT")
                 .WithExternalHttpEndpoints();

// Python: uv / pip / venv, Uvicorn-aware, Dockerfile generated on publish.
var scoring = builder.AddUvicornApp("scoring", "../scoring", "main:app")
                     .WithReference(api);

// Go and Java resources are modelled similarly; Go gained debugging in 13.5.
var worker = builder.AddGolangApp("worker", "../worker")
                    .WithReference(api);

The mechanism that makes polyglot work is unglamorous and worth naming: environment variables plus OpenTelemetry conventions. Aspire injects OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_SERVICE_NAME, PORT, connection strings and service-discovery values; the other language runtime uses its own OTel SDK and its own HTTP client. There is no cross-language runtime and no proprietary protocol. 13.0 added multi-format connection information for exactly this reason — a database resource can expose a URI form for Python, a JDBC form for Java and the classic keyword form for .NET, so each ecosystem gets a string its drivers accept. That is the detail that shows you understand the design rather than the feature list.

The CLI became the centre of gravity in 13.x, explicitly framed as “a first-class agent interface” in 13.2 — designed to be driven by AI coding agents as well as humans. It is installed independently of the SDK, and 13.5 added npm (@microsoft/aspire-cli) and Nix distribution alongside the existing dotnet tool and script installs.

What does “polyglot” actually mean in Aspire 13?

Three concrete things. Resource types that understand each ecosystem’s conventions — AddJavaScriptApp with package-manager detection and Vite awareness, AddUvicornApp with uv/pip/venv support, Go and Java resources — instead of a generic “run this command”. Multi-format connection information, so a database exposes URI, JDBC and keyword forms and each language gets a string its driver accepts. And standard OTel environment injection into every resource regardless of language, so telemetry converges in one dashboard. What it does not mean is cross-language client integrations: the health checks, resilience and instrumentation that .NET services get for free must be arranged in each ecosystem’s own way. Since 13.5 the AppHost itself can be TypeScript, which removes the “I have to write C# to orchestrate my Node app” objection.

Would you use a TypeScript AppHost?

It went GA in 13.5, so it is a real option rather than a preview curiosity — createBuilder() in TypeScript, running as a guest process alongside the .NET orchestration, with integration SDKs generated by aspire restore. I would use it when the team’s centre of gravity is JavaScript and a C# file would be the only .NET in the repo, because the AppHost should be readable and editable by the people who own the topology. I would stay with C# in a .NET-majority repo: the typed Projects.* references, the mature extension ecosystem and the ability to unit-test the model with the same tooling as everything else are worth more than language uniformity with a front end. Either way, one AppHost language per repo — mixing them would be a maintenance tax with no benefit.

How does a browser front end consume service discovery?

It does not, and this is the wiring people get wrong. Service discovery resolves inside processes Aspire launched; a browser is outside the model and knows only what it is told. Two correct patterns: inject the API address into the front-end build or dev server as an environment variable that its framework exposes to client code (for example a Vite VITE_API_URL sourced from the reference), or — usually better — do not expose the API separately at all and route browser traffic through the same origin via a gateway or the dev server’s proxy, so the client uses relative URLs. The second is more robust because it matches production, avoids CORS entirely, and means the front end has no environment-specific configuration at all.

What is aspire exec for?

Running a command with a resource’s resolved environment — its connection strings, its service-discovery values, its parameters — so tools see exactly what the service sees. The everyday case is EF Core: aspire exec --resource api -- dotnet ef database update instead of hunting the connection string in the dashboard and pasting it into a shell, where it also ends up in your history. It is equally useful for one-off scripts, data fixes and diagnostics. Conceptually it closes a gap in the model: without it, everything the app needs is modelled and everything a human needs is manual, which is precisely the drift Aspire exists to remove.

Why does the CLI matter more in 13.x than it used to?

Because it became the primary interface, for humans and for agents. 13.2 was explicitly themed “CLI as a first-class agent interface” and added detached mode, process management, diagnostics, certificate and secret handling, and telemetry APIs — the surface an automated caller needs. Combined with the MCP server, the design intent is that an AI coding agent can start your app, inspect resources, read logs and traces, and iterate without a human relaying output. For a lead, the practical read is twofold: your dev workflows should be CLI-expressible rather than IDE-only, which also makes them CI-expressible; and if your organisation is investing in agentic development, Aspire is one of the few stacks where the local environment is genuinely machine-drivable.

How do you add Aspire to an existing multi-language repo?

aspire init at the root, which offers a single-file AppHost and creates aspire.config.json without restructuring anything. Then add resources incrementally, starting with the dependencies everyone runs by hand — the database, the cache, the broker — because that is where the immediate win is and it requires no changes to any service. Next, bring in the services one at a time, .NET first (they get the most benefit from ServiceDefaults), then the front end and other runtimes. Model anything you do not run as an external service so the picture is complete rather than half-true. And leave deployment alone until the dev loop is unambiguously better; adoption fails when the first PR touches both the developer experience and the production pipeline.

What does aspire doctor check, and why does it exist?

Environment prerequisites: SDK version, the container runtime and whether it is actually running, the ASP.NET Core developer certificate and its trust, CLI and package version alignment, and common misconfigurations. It exists because the overwhelming majority of “Aspire does not work” reports are environmental rather than code — Docker not started, a dev certificate that was never trusted or expired, an SDK mismatch after a machine reimage, a CLI several minors behind the packages. Making it the first response to any environment complaint saves hours; making it part of onboarding saves more. It arrived in 13.2, alongside certificate and secret management commands that address the same class of problem.

How do you handle certificates for HTTPS across languages?

13.0 made certificate trust configured automatically across languages, which matters because a Node or Python process calling your .NET service over HTTPS will otherwise reject the ASP.NET Core development certificate — each runtime has its own trust store and its own environment variable for a CA bundle. Aspire injects the right ones. When it still fails, the usual causes are a certificate that was never trusted on the host (dotnet dev-certs https --trust, or the CLI’s certificate commands), a container that has no notion of your host’s trust store, or a runtime that ignores the standard variables. The pragmatic fallback for container-to-service traffic is plain HTTP internally via https+http, keeping TLS at the edges where it is actually enforced.

Where does Aspire fit with AI-assisted development?

Two integration points, and it is worth being precise because the feature set moved. The MCP server (13.0) exposes the running application to agents — resources, console and structured logs, traces — so an agent debugging a failure can read the actual telemetry instead of asking you to paste it. The CLI expansion (13.2) makes the whole lifecycle scriptable by an agent: start detached, inspect, run a step, stop. Meanwhile 13.5 removed the dashboard’s built-in AI Assistant chat, which tells you the strategy: Aspire is being built as a well-instrumented target for whatever agent you already use, not as a place to host a chat box. That contrast is a good way to demonstrate you are tracking the last two releases rather than reciting an old blog post.

What are the risks of putting your front end in the AppHost?

Mostly organisational and build-related. Front-end teams have strong, valid opinions about their dev server, and wrapping it in another orchestrator can feel like a regression if it makes hot module replacement slower or hides their console output — check that HMR still works before declaring victory. The build path is the second risk: generated Dockerfiles are convenient but rarely match a serious front-end build, and 13.0’s container-file-as-build-artifact feature (extracting front-end output to serve from a backend) is worth knowing precisely because it avoids shipping a Node server at all. The third is coupling: a front end that only builds inside the AppHost is harder to work on standalone, so keep npm run dev working on its own and treat Aspire as an additional way to run it, not the only way.

13 Extending the app model

Every real adoption reaches the point where the built-in integrations run out — an internal service that everyone runs locally, a licensed database with a bespoke container, a company-standard sidecar. Extending Aspire is deliberately shallow, because the whole model is “resources carrying annotations”, and adding your own is mostly a matter of implementing an interface and writing extension methods that look exactly like the built-in ones.

// A custom resource that exposes a connection string.
public sealed class FeatureFlagsResource(string name, ParameterResource token)
    : ContainerResource(name), IResourceWithConnectionString
{
    internal EndpointReference Http => new(this, "http");

    public ReferenceExpression ConnectionStringExpression =>
        ReferenceExpression.Create($"Endpoint={Http.Property(EndpointProperty.Url)};Token={token}");
}

public static class FeatureFlagsBuilderExtensions
{
    public static IResourceBuilder<FeatureFlagsResource> AddFeatureFlags(
        this IDistributedApplicationBuilder builder, string name, IResourceBuilder<ParameterResource> token)
    {
        var resource = new FeatureFlagsResource(name, token.Resource);

        return builder.AddResource(resource)
            .WithImage("ghcr.io/acme/flags", "4.2")
            .WithHttpEndpoint(targetPort: 8080, name: "http")
            .WithEnvironment("FLAGS_TOKEN", token)
            .WithHttpHealthCheck("/healthz")
            .WithUrlForEndpoint("http", url => url.DisplayText = "Flags console")
            .WithCommand("reload", "Reload flags", async ctx => { /* ... */ });
    }
}

Three extension seams are worth knowing by name. Custom resources, as above: implement IResourceWithConnectionString (or IResourceWithEndpoints, IResourceWithEnvironment) so consumers can WithReference your thing like any other. Eventing: builder.Eventing.Subscribe<BeforeStartEvent> and per-resource events such as ResourceReadyEvent and ConnectionStringAvailableEvent let you run code at defined points in the lifecycle — this is the 13.0 replacement for the deleted IDistributedApplicationLifecycleHook. Pipeline steps: AddPipelineStep with DependsOn/RequiredBy, the replacement for publishing callbacks (unit 11).

Smaller but heavily used seams round it out: WithCommand for dashboard buttons (with user-defined arguments since 13.5), WithUrlForEndpoint and WithUrls to control the links the dashboard shows, WithInteraction-style prompting through the Interaction Service (stable across C# and TypeScript AppHosts in 13.5, with file uploads, progress dialogs and notifications), and WithTerminal() (experimental, 13.5) to host a REPL or shell for a resource in the dashboard.

How would you model an internal service nobody has an integration for?

Start with the composition primitives: a container resource with an endpoint, environment variables, a health check, and an Add* extension method that hides the details. If consumers need a connection string, make the resource implement IResourceWithConnectionString and build the value with ReferenceExpression so it is resolved lazily once the endpoint is allocated. Add a client-side helper in a shared library if the consuming code deserves the same treatment as a client integration — registration, health check, telemetry. Then package it internally so every team gets the same thing. What I would avoid is a one-off block of AppHost code copied between repos, because that is the drift Aspire was adopted to remove.

What replaced lifecycle hooks, and why?

Eventing. 13.0 removed IDistributedApplicationLifecycleHook and the publishing callbacks in favour of builder.Eventing.Subscribe<TEvent> for lifecycle points such as before-start and resource-ready, and aspire do pipeline steps for publish/deploy-time work. The reasons are consistency and visibility: events are typed, ordered and discoverable, and pipeline steps declare their dependencies so the runner can order and parallelise them and you can list or run them individually. Hooks were opaque, ran serially, and had no way to express “this can happen concurrently with that”. For an upgrade this is the change most likely to require real work, because any custom orchestration a team wrote must be rewritten rather than adjusted.

What is ReferenceExpression and why can you not just use a string?

Because the values are not known when you declare the resource. An endpoint URL exists only after DCP allocates a port; a parameter may be prompted for at start; a connection string may depend on both. ReferenceExpression.Create($"...") captures the shape with placeholders for endpoint properties and parameter resources, and Aspire evaluates it at the moment the value is needed — differently in run mode and publish mode, where the same expression becomes a template parameter rather than a literal. Using plain interpolation captures whatever was there at declaration time, which is usually null or a placeholder, and produces the classic bug where a connection string works locally by accident and is empty when published.

When should an extension be a resource versus just a method?

Make it a resource when it has identity in the graph — it starts, stops, has health, appears in the dashboard, and other resources reference it. Make it an extension method over existing resources when it is policy — “apply our standard health check path, our OTel resource attributes and our naming convention to every project” is a method, not a resource. The mistake I see is inventing resource types for what are really configuration conventions, which produces a graph full of nodes that do not correspond to anything running and makes the dashboard less useful. A good test: if it would not appear in a deployment diagram, it is probably not a resource.

How do you keep an internal Aspire extension library maintainable?

Pin it to one Aspire minor at a time and treat upgrades as scheduled work, because the support policy means you will be moving several times a year. Keep the surface small and built on stable primitives; every experimental API you touch is a future migration. Give it real ownership and a changelog, since AppHost breakage blocks every developer simultaneously and an unowned internal package becomes a company-wide outage the first time it lags a release. Provide escape hatches — expose the underlying IResourceBuilder so teams can apply their own WithX calls rather than waiting for you to add a parameter. And test it: build the model in a test and assert the resulting annotations, which is fast and catches regressions from Aspire changes.

What are custom resource commands good for?

Turning tribal knowledge into buttons. Reset the database, reseed, flush the cache, rotate a test tenant, trigger the nightly job, clear a poison queue — all things that currently live in a README, a gist, or one person’s shell history. WithCommand puts them in the dashboard next to the resource, and since 13.5 they can take user-defined arguments that render as dashboard controls and CLI options, so a parameterised action does not need a bespoke tool. The caution is authorisation: a command is an arbitrary action available to anyone who can reach the dashboard, so keep destructive ones out of any dashboard that is deployed rather than local, and never assume the dashboard’s audience equals the repo’s audience.

How does the Interaction Service change AppHost design?

It lets the app model ask the developer something — a prompt with dynamic inputs, a choice, a file upload, a progress dialog, a notification — routed to the dashboard or the CLI depending on where they are. That turns previously impossible setups into modelled ones: prompting for a licence key on first run, asking which tenant to seed, uploading a fixture file. 13.5 made it consistent across C# and TypeScript AppHosts and stabilised the prompts. The design caution is that interaction is only available in run mode with a human present; anything on the publish path or in CI must have a non-interactive route, or your pipeline hangs waiting for an answer nobody will give. Design for “prompt if interactive, parameter otherwise”.

How do you write a custom pipeline step responsibly?

Declare its dependencies explicitly with DependsOn/RequiredBy against the well-known steps rather than assuming order, so the resolver can validate and parallelise. Make it idempotent, because steps get re-run — a deploy retried after a transient failure should not double-apply anything. Make it fail loudly and specifically; a step that swallows errors turns a deployment problem into a mystery. Keep it fast or make it optional, since it is now on everyone’s deploy path. And accept that the API is experimental in 13.x, so isolate it behind your own thin abstraction if you are going to have many, and expect to revisit it at the next minor.

How do you decide between extending Aspire and doing it outside?

Ask whether the thing belongs to the application’s topology. Starting a dependency, exposing an endpoint, providing a connection string, gating startup — that is the model’s job and belongs in an extension. Building images, running policy checks, publishing artifacts to a registry, notifying Slack — that is your pipeline’s job, and pushing it into the AppHost couples your dev loop to your CI concerns and makes the AppHost slower and more fragile for everyone. The middle ground is deploy-time pipeline steps, which are legitimately Aspire’s but should stay thin. My default is: if removing Aspire tomorrow would leave the capability needed, it should not live inside Aspire.

What would you check in review of a custom hosting extension?

That it looks like the built-ins — an Add* that returns IResourceBuilder<T> so callers can keep chaining, and no swallowing of configuration. That values are composed with ReferenceExpression, not interpolated strings. That it registers a health check, because WaitFor is much weaker without one. That the image and tag are explicit and overridable, so a regulated environment can point at an internal registry. That anything sensitive comes in as a secret parameter rather than a string. That run-mode-only extras are guarded. And that experimental APIs are used deliberately, with the suppression and a comment explaining the accepted risk, rather than silently — because the next person to hit that diagnostic will otherwise assume it is safe.

14 The big Q&A

Everything that does not belong to a single building block: the cross-cutting decisions, the security questions, the debugging stories, the migration reality and the “how would you lead this” scenarios. Twenty-two questions, grouped.

Architecture & ecosystem decisions

Aspire, Dapr, or neither — how do you decide?

They answer different questions, so the first move is to make the team state the problem. If the pain is “our dev environment is a mess and our topology is undocumented”, that is Aspire. If the pain is “we want portable pub/sub, state and secrets abstractions with a sidecar so our services do not bind to a cloud”, that is Dapr, and it is a runtime commitment with real operational cost. They compose — Aspire can model Dapr sidecars — but adopting both at once doubles the concepts a team must hold. Neither is the right answer surprisingly often: a team with two services, one database and a working compose file gets little from either, and the honest recommendation is to spend the effort on their deployment pipeline instead.

Does Aspire push you towards microservices?

It makes multiple processes cheap to run locally, and cheap things multiply — that is a genuine architectural force worth naming. But the model works just as well for a modular monolith with real infrastructure dependencies, and I would argue that is where the effort-to-value ratio is best: one service, a database, a cache, a broker, no compose file, full telemetry. My guidance to teams is to keep service boundaries a domain decision and treat Aspire as neutral tooling; if anything, use the app model as a design mirror — when the AppHost graph becomes unreadable, that is a signal about your architecture, not about your tooling. Watching the number of edges in that graph over time is a cheap, honest complexity metric.

Multi-repo: one AppHost or many?

Many, one per repo, each modelling its own services plus AddExternalService/AddConnectionString entries for neighbours. A single mega-AppHost requires every developer to clone and build the world, couples release cadences, and becomes owned by nobody. The trade-off is that no single artifact shows the whole system, so you lose the “one diagram” benefit at the organisation level — I compensate with a service catalogue rather than by centralising the AppHost. Where a genuine cross-repo dev experience is needed, a thin composition AppHost that references published container images rather than source is the least-bad option, and it should be optional, not the default path.

How does Aspire change your CI pipeline?

Three additions and one caution. Add aspire publish so publishing breakage surfaces at PR time, and diff the artifacts so infrastructure changes are visible in review. Add model-level tests, which are nearly free and enforce architectural rules. Add a smoke stage that starts the full graph, outside the fast loop. The caution is agent requirements: anything using the testing builder needs a container runtime, memory, and image caching, and cold agents pull gigabytes. I would also pin the CLI version in CI and align it with the packages, because a CLI that drifts from the AppHost SDK produces confusing failures that look like code problems.

What is the cost of adopting Aspire, stated honestly?

A fast-moving dependency in your build with a support policy that only covers the newest release, so upgrades are recurring, not optional. A new concept for the team — the app model — that must be taught and reviewed. Machine load, because everyone now runs the real dependencies. Some coupling of services to Aspire.* client packages if you use client integrations. And, if you adopt the deployment half, a partly experimental API surface in your delivery path. Against that: onboarding measured in minutes, a topology that is code, telemetry by default, and a single description behind dev, test and deploy. I would say the numbers plainly and let the team decide, rather than selling.

Security

What are the security-relevant defaults you would review first?

Four. Which resources call WithExternalHttpEndpoints — that is your public attack surface, declared in code, and it should be one or two things. Whether /health is mapped outside development, because it enumerates dependencies for free. Whether secrets are declared with secret: true and, better, whether they exist at all versus managed identity. And the dashboard: authenticated, network-restricted, OTLP endpoint API-keyed, never publicly reachable, because it displays every resource’s environment. In generated Azure artifacts I additionally read the role assignments, since Aspire grants what is needed to make things work and least privilege is a decision you must make deliberately.

Where do credentials actually live in an Aspire app?

In development: user secrets on the AppHost, generated parameters for local containers, and the developer’s own cloud identity for real services. At runtime, resolved values sit in child-process environment variables, which is a plaintext surface visible to anything that can read the process or the dashboard. In published artifacts: a git-ignored .env for Compose, secure parameters or Key Vault references for Bicep, Secrets for Kubernetes — determined by the secret: true flag. The strategic answer is to have as few credentials as possible: 13.0 made DefaultAzureCredential use only managed identity in deployed Azure environments precisely to close the “it silently fell back to something else” gap, and workload identity does the same job in Kubernetes.

Is the dashboard a security risk?

It is a high-value target because it aggregates everything: environment variables (so connection strings and any unmasked parameter), console output, structured logs and traces that may contain request data. Locally, behind a browser token on loopback, that is acceptable. Deployed, it needs OIDC on the frontend, an API key on the OTLP ingress so nobody can inject fabricated telemetry, and private networking. The failure I would specifically look for is a standalone dashboard container deployed to a shared environment with authentication disabled “temporarily”. Also worth remembering: custom resource commands and the 13.5 terminal feature are privileged actions exposed through that same UI.

Who is responsible for the container images Aspire runs?

You are. The support policy is explicit that Microsoft does not evaluate the third-party containers used by integrations, and that meeting your security, regulatory and cryptographic requirements is the consumer’s responsibility. Practically that means: in a regulated environment, override images to an internal registry with WithImageRegistry/WithImageTag so your scanning and provenance apply; pin tags rather than inheriting whatever the Aspire release chose, because an upgrade can move Postgres or Redis underneath you; and remember these are dev-time images, so the risk is developer machines and CI agents rather than production — which does not make it zero, since a compromised dev image sits next to source code and cloud credentials.

Performance & debugging

A request is slow in the dev environment. Walk me through your debugging.

Trace first, always. Open the trace in the dashboard, find the span that owns the latency, and see whether it is your code, a downstream call, or a dependency — that answers in seconds what log grepping answers in minutes, and it is the habit I most want a team to build. If the slow span is a database call, the client integration’s instrumentation gives you the operation; if it is an HTTP call, check whether the resilience handler is retrying (a 3× multiple of a timeout is a giveaway). Then check for local artefacts before concluding anything: a cold container, a proxied endpoint, a debugger attached, or an under-resourced container runtime can dominate. Confirm on a second run, because the first run of anything in a container environment is not representative.

What Aspire-specific performance traps exist in production?

Not Aspire itself, since it is not there — but its defaults travel. Always-on trace sampling from ServiceDefaults is the big one; at production volume it is an exporter bottleneck and a bill. Blanket resilience on every HttpClient is the second: retries at multiple layers turn a partial outage into a self-inflicted load test, and a circuit breaker with default thresholds may be wrong for your traffic shape. Third, health checks: an aggregate /health polled frequently and hitting every dependency is a real load source, and if it is your readiness probe, a dependency blip becomes an outage. Fourth, metric cardinality from custom meters. All four are one-line changes in code you own, which is the argument for treating ServiceDefaults as a thing you actively maintain.

“It works locally but fails when deployed” — how do you approach it with Aspire?

The two modes are the first suspect: something guarded by IsRunMode, or an emulator whose semantics differ from the real service (Azurite versus real storage, an in-memory broker versus a real one). Second, service discovery: locally the configuration resolver reads AppHost-injected variables, while deployed you may be on DNS or on generated variables with different names — the 13.2 scheme-keying change bit exactly this path. Third, identity: locally you use your own credentials, deployed you use managed identity, and a missing role assignment looks like a connectivity bug. Fourth, network policy: private endpoints and VNets (13.2) mean something reachable locally is unroutable in the target. The generalisable move is to read the published artifact and compare it with what you assumed, rather than reasoning about the C#.

How do you debug a resource that will not start?

Console logs, not structured logs — a process that dies before telemetry initialises produces nothing over OTLP, and this is the single most common reason people say “the dashboard shows nothing”. Read the resource’s state in the dashboard (a failed image pull, a non-zero exit, a health check never going green), then its console output, then its environment variables to check that what you think you injected actually arrived. If it is a WaitFor chain, look upstream: a resource waiting on an unhealthy dependency shows as pending forever, and the real failure is one node away. Then aspire doctor for environmental causes. If it is a persistent container, suspect stale state and recreate it.

How do you keep telemetry costs under control once this reaches production?

Sampling in the app (parent-based ratio so traces stay whole), tail sampling in a collector if you want to keep all errors and slow requests, and a hard look at log export level — OTLP logs at Debug is the quiet path to an enormous bill. Then cardinality: strip route parameters and identifiers from span names and metric labels, and audit custom meters for unbounded tags. Then scope: not every service needs the same fidelity, and a sampling policy per service tier is legitimate. Do all of this in ServiceDefaults so it is one change for the estate, and add a dashboard or alert on telemetry volume itself, because the failure mode is a gradual increase nobody notices until invoicing.

Tooling, versions & upgrades

How do you manage Aspire upgrades across a large codebase?

Treat them as scheduled maintenance with an owner, because the Modern Lifecycle policy means the previous release is unsupported the day a new one ships. Central Package Management so one file moves every Aspire.* version together; aspire update to do the mechanical work and aspire update --self for the CLI; a pinned CLI version in CI matching the packages. Then a checklist per upgrade: read the breaking-change list (13.2’s service-discovery variable rename and aspire.config.json consolidation, 13.5’s ServiceProvider→Services rename and PublishAsConnectionString obsolescence), rebuild, run the model tests, and diff aspire publish output before and after. That diff is the step people skip and the one that catches infrastructure surprises.

What actually breaks between 9.x and 13.x?

More than a version bump suggests. Package and API renames: Aspire.Hosting.NodeJs→Aspire.Hosting.JavaScript, AddNpmApp→AddJavaScriptApp. Removed extensibility: publishing callbacks and lifecycle hooks are gone, replaced by eventing and aspire do steps, so custom orchestration must be rewritten. The SDK floor moved to .NET 10. Deployed Azure credential resolution narrowed to managed identity only. Then the 13.x minors add their own: service-discovery variables keyed by scheme (13.2), configuration consolidated into aspire.config.json (13.2), shortened resource command names, connection property suffix renames, and in 13.5 the ServiceProvider→Services rename plus a handful of removals. I would budget a spike, not an afternoon.

How do you decide when to take a new Aspire minor?

Quickly, because the support policy leaves little choice, but not blindly. My cadence is: read the release notes and breaking changes the week it ships, upgrade on a branch, run the full suite including publish-artifact diffs, and merge within a sprint unless something surfaces. Where a change is risky — an experimental API you depend on, a deployment behaviour change — I stage it: upgrade the dev loop first, hold the publish path until the artifact diff is understood. What I would not do is skip minors to batch them, because the breaking changes then arrive together and the debugging is harder. The cost of this discipline is real and should be named in planning rather than absorbed silently.

What is your view on experimental APIs in Aspire?

Use them with eyes open and a suppression comment that says why. Compute environments (ASPIRECOMPUTE001), pipeline APIs, WithTerminal, and the 13.5 path-based DotnetProjectResource (ASPIREDOTNETPROJECT001) are all marked evaluation-only, and the 13.0 removals prove that the team will delete things. My rule: experimental APIs are acceptable in an AppHost, where breakage is a compile error a developer fixes in minutes; they are risky in an internal framework used by twenty teams; and they need a named owner and an upgrade plan in a deployment path. The diagnostic exists to make you have this conversation, so suppressing it project-wide in a props file — which I have seen — defeats the mechanism entirely.

Legacy and migration reality

How would you migrate a solution with a hand-written docker-compose.yml?

Incrementally, and in a specific order. First, add ServiceDefaults to the .NET services — telemetry and health checks with no orchestration change, valuable on its own and reversible. Second, add an AppHost that models only the dependencies (database, cache, broker) and run the app against it, keeping the compose file alive in parallel until people trust the new path. Third, move the services in, one at a time, deleting their entries from compose as you go. Fourth, decide about publishing separately and much later. The rule that keeps this safe is that every step is independently valuable and independently revertible, and the compose file is deleted only when nobody has used it for a fortnight.

What do you meet in older Aspire codebases that is now wrong?

The workload (dotnet workload install aspire), removed in 9.0 in favour of NuGet packages and the CLI. AddNpmApp, renamed in 13.0. Lifecycle hooks and publishing callbacks, deleted in 13.0. The old manifest-plus-azd deployment story, superseded by the pipeline. PublishAsConnectionString, obsolete in 13.5. Scattered configuration files, consolidated into aspire.config.json in 13.2. Code that reads services__svc__endpointname__0, re-keyed by scheme in 13.2. And .NET Aspire branding everywhere, including in docs links to Microsoft Learn that now redirect to aspire.dev. Recognising these in a code-review exercise is a fast way to demonstrate currency.

Can you adopt Aspire without touching your services at all?

Yes, and it is the lowest-friction path. An AppHost can run existing projects with AddProject and existing containers with AddContainer, injecting connection strings under the names those services already read from configuration — no code change, no new package in the service. You give up service discovery by logical name (services keep whatever addressing they had), the automatic telemetry and health checks from ServiceDefaults, and the client-integration niceties. What you keep is the orchestration, the dashboard’s resource view and console logs, and a topology in code. I often propose exactly this as phase one, because it produces a working demo in an afternoon and it makes the subsequent phases an easy sell.

A team wants Aspire only for local dev and never for deployment. Is that legitimate?

Completely, and it is the most common steady state I have seen. Aspire’s dev-loop value stands alone: one command to start everything, no compose drift, telemetry by default, and topology in code. Deployment is a separate decision with separate governance, and refusing it keeps Aspire out of your production blast radius entirely. The one thing I would still do is run aspire publish in CI, even if the artifacts are discarded — it costs nothing and it keeps the option open, while also catching publish-mode-only errors that otherwise lie dormant. The risk of dev-only adoption is that dev and prod topologies can drift again; the mitigation is periodically diffing the published artifact against the real deployment.

Judgment & scenarios

What do you flag in code review of an AppHost?

Unnecessary WithExternalHttpEndpoints; missing health checks on projects; WaitFor used as a substitute for resilient startup; secrets not marked secret, or worse, literals; side effects outside a mode guard; dev-only containers without IsRunMode; resource renames, which are breaking changes to connection-string keys and can recreate deployed infrastructure; durable infrastructure being created by Aspire when it should be referenced; unpinned or non-internal container images in a regulated environment; and experimental APIs used without an explicit, commented decision. Beyond the checklist, I read the artifact diff from aspire publish, because a one-line C# change can be a significant infrastructure change and the C# will not show it.

How do you onboard a team that has never seen the app model?

Teach three concepts and nothing else on day one: resources, references, and the two modes. Then have them do the exercise that makes it click — add a Redis, reference it from a service, watch the connection string appear in the dashboard’s environment view. Establish two habits immediately: read traces before logs, and treat the AppHost as production code in review. Provide a reset command and a troubleshooting page starting with aspire doctor, because environmental failures are the main source of early frustration and they are not conceptual. Explicitly defer the deployment half; teaching publish pipelines in week one buries the ideas that actually pay off.

Production incident: a downstream dependency is degraded and your service is failing. What has Aspire given you, and what has it not?

It has given you telemetry: the same OTel configuration that fed the dashboard locally is feeding your backend, so you have traces that attribute failure to a span, correlated logs, and standard runtime metrics — and the team has practised reading them, which is the underrated part. It has given you health endpoints and, through ServiceDefaults, circuit breakers and timeouts that may already be shedding load. It has given you nothing at the network layer: no traffic shifting, no failover, no bulkheads beyond what the resilience pipeline does per client. And the AppHost is irrelevant during the incident. The corrective work afterwards mostly lands in ServiceDefaults — sampling, retry policy, readiness definition — which is a good argument for owning that code well.

How would you decide whether Aspire has actually paid off, six months in?

Measure the things it claimed to fix. Time-to-first-successful-request for a new joiner, before and after. The number of places a connection string or endpoint is written by hand. Frequency of “works on my machine” incidents. Whether the topology diagram in the wiki still exists, and whether anyone updates it (they should not need to). Whether dev and deployed environments have diverged. Then the costs: hours spent on Aspire upgrades, CI minutes added by container-based tests, and support load on whoever owns the AppHost. If the qualitative benefits are real but the upgrade tax is dominating, the answer is usually to narrow the surface — dev-only, fewer custom extensions — rather than to abandon it.

15 Night-before cheat sheet

  1. What it is. Aspire is a dev-time and build-time application platform: an AppHost program describes your app as a resource graph, an orchestrator runs it locally, integrations wire dependencies, a dashboard collects OpenTelemetry, and publishers project the same model into Compose, Kubernetes or Bicep. It does not run in production.
  2. Where it is now. 13.5, released 18 August 2026 (13.5.3 on 25 August). The “.NET” was dropped at 13.0 on 11 November 2025, docs moved to aspire.dev, and versioning detached from .NET; only the newest release is supported under Modern Lifecycle, and the SDK floor is .NET 10.
  3. What shipped recently. 13.2: expanded CLI (start/ps/stop/doctor/describe), stable Docker Compose publishing, aspire.config.json, service-discovery variables keyed by scheme, Azure VNet and private endpoints. 13.5: TypeScript AppHosts GA, experimental WithTerminal(), CLI on npm, dashboard AI Assistant removed, PublishAsConnectionString obsoleted.
  4. The core idea. The app model is the source of truth; the dev environment, the integration-test harness and the deployment artifacts are all projections of it, so they cannot silently disagree.
  5. The two edges. WithReference is configuration — connection strings and service-discovery variables. WaitFor is ordering, and it waits for healthy only if the target has a health check. Prefer resilient startup over waiting; use WaitForCompletion for migrations.
  6. Two modes, one file. IsRunMode versus IsPublishMode, with RunAsContainer/RunAsEmulator/PublishAsX as the idiomatic switches. Keep the AppHost declarative: side effects run during publish too, on a build agent with no Docker.
  7. Two halves of an integration. Hosting (Aspire.Hosting.*, AppHost only) models the resource; client (Aspire.StackExchange.Redis and friends, in your service) configures the client with health checks, telemetry, resilience and keyed DI. They are joined only by the resource name, and client integrations work fine without Aspire.
  8. ServiceDefaults is your code. A template, not a package, on purpose: OTel, /health and /alive, service discovery, and AddStandardResilienceHandler. Change three things before production — sampling, retries on non-idempotent calls, and what your readiness probe actually checks.
  9. Discovery is configuration. services__<resource>__<scheme>__<index> environment variables plus a resolver on configured HttpClients; https+http://name is an explicit downgrade preference; DNS and DNS SRV resolvers cover Kubernetes and Consul. A missing WithReference throws at resolution, it does not 404.
  10. Publish versus deploy. aspire publish emits parameterised artifacts and stops; aspire deploy resolves parameters and applies them, remembering deployment state. aspire do --list-steps shows the pipeline that replaced 13.0’s deleted publishing callbacks. Publish plus your existing CD for anything with users; deploy for ephemeral environments.
  11. The security shortlist. Which resources are externally exposed, whether /health is public, whether secrets are marked secret or eliminated by managed identity, whether the dashboard is authenticated and network-restricted, and who owns the container images — Microsoft explicitly does not vet them.
  12. The honest costs. A fast-moving dependency with only-latest support, an upgrade tax paid several times a year, heavier developer machines, and a partly experimental deployment API — against onboarding in minutes, topology in code, telemetry by default, and one description behind dev, test and deploy.
