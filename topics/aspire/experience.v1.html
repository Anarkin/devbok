Twenty story scaffolds for the behavioural half of an Aspire-flavoured loop — platform, backend or lead .NET roles where someone will ask how you actually got a distributed application onto developers' laptops and into production — plus a cross-cutting Q&A and a night-before sheet. Three threads run through the whole bank, and naming them out loud is what turns a set of stories into a point of view rather than a list. The AppHost is a development-time orchestrator, not a runtime — everything Aspire does at F5 is DCP starting processes and containers on your machine, and everything it does at deploy time is generating artefacts for somebody else's runtime. The app model is the single source of truth for topology — who talks to whom, what has to be healthy before what starts, which connection string reaches which resource — and every good Aspire decision comes from keeping that model honest. Aspire removes glue, not architecture — it will not make a distributed system correct, it will only stop you re-deriving the wiring by hand in four places. When a drill-down surprises you, fall back to one of those three.

01The 47-second F5

tier · senior performance problem diagnosed

Example — replace with your own

Nobody filed a ticket about it, which is exactly why it took me four months to look. The complaint arrived sideways, in a retro: "I stopped running the whole app locally, I just run the API and point it at the shared dev database." That is the real cost of a slow inner loop — people quietly leave it. I timed it properly on a clean machine: 47 seconds from F5 to the last resource going green on the dashboard, every single time, and 12 seconds of that after every code change because the AppHost tore everything down and rebuilt the graph.

The mechanism matters, because the fix is not "buy faster laptops". The AppHost is not a runtime; it is a build-time app model that DCP — the Developer Control Plane, the orchestrator process Aspire starts underneath you — turns into actual processes and containers on your machine. DCP starts resources in parallel by default. Anything that is not parallel is something I asked for, and I had asked for a lot without realising. Three separate mistakes were serialising a graph that had no business being serial.

First, WaitFor semantics. WaitFor(x) does not mean "start after x"; it means "do not start until x is running and healthy", and if x has a health check registered, that is a real probe with a real interval. I had chained api behind postgres, web behind api, and a worker behind web because the diagram looked like that — but the worker never called the web front end at all. Second, the migration project. WaitForCompletion(migrations) is the right tool for a one-shot job, but ours ran EF Core migrations against a container that had just booted, and the default Postgres container health check plus EF's own connection retry meant a cold start of nine seconds before the first statement executed. Third, and this was the embarrassing one: every container was on the default session lifetime, so Postgres, Redis and RabbitMQ were created and destroyed on every run. Creating a Postgres container is not free, and initialising an empty data directory is a lot less free.

var builder = DistributedApplication.CreateBuilder(args);

// Persistent: the container survives between AppHost runs, so the data directory
// is initialised once, not once per F5. Pin the tag: an unpinned default image
// silently changes under you when you upgrade Aspire (see story 12).
var pg = builder.AddPostgres("pg")
    .WithImageTag("18.3")
    .WithDataVolume("acme-pgdata")
    .WithLifetime(ContainerLifetime.Persistent);

var db = pg.AddDatabase("appdb");

var cache = builder.AddRedis("cache")
    .WithLifetime(ContainerLifetime.Persistent);

// One-shot job: WaitForCompletion gates on the exit code, not on health.
var migrations = builder.AddProject<Projects.Acme_MigrationService>("migrations")
    .WithReference(db).WaitFor(db);

var api = builder.AddProject<Projects.Acme_Api>("api")
    .WithReference(db).WithReference(cache)
    .WaitForCompletion(migrations);

// The worker talks to the database and the queue. It does NOT talk to the web
// front end, so it must not wait for it - that edge was pure diagram-copying.
builder.AddProject<Projects.Acme_Worker>("worker")
    .WithReference(db).WaitForCompletion(migrations);

builder.AddProject<Projects.Acme_Web>("web")
    .WithReference(api).WaitFor(api);

builder.Build().Run();

Straightening the wait graph and moving the three infrastructure containers to ContainerLifetime.Persistent took the cold start to 19 seconds and the warm start — the one that happens forty times a day — to 9. The rest came from two smaller things: pinning image tags so a pull never happens on a normal day, and turning off the resources most people do not need on most days behind a launch-profile switch, so the default F5 starts eleven resources rather than nineteen. Adoption went from "three of us" to "everyone" within a sprint, and the shared dev database stopped being a source of mystery test failures.

What I would do differently: measure before assuming. I spent the first afternoon convinced the bottleneck was container image pulls, because that is the folklore answer, and it was worth less than four seconds. The graph edges I had written myself — without thinking, months earlier — were the expensive part. I also should have put a stopwatch in the team's hands rather than my own; the number that changed behaviour was not "47 seconds", it was "you get 25 minutes of your day back".

What the interviewer is really probing. Whether you treat developer experience as an engineering problem with measurements, or as a vibe. Anyone can say "I made the local environment faster"; the signal here is that you can name what was actually serialising — and that you know Aspire starts resources in parallel unless you tell it not to, which means a slow startup is usually a statement about your own dependency graph. The mistake candidates make on this archetype is quoting a percentage with no mechanism behind it, and forgetting to say what the speed-up bought: the business case is behaviour change, not seconds.

(c) Recall prompts

When did you last time a developer workflow instead of guessing about it?

Build times, test suites, container starts, a deploy. The story lives in the gap between what you assumed was slow and what the stopwatch said. If your first guess was right, the interesting part is how you knew to look there.

Where in your app model is there a dependency edge that reflects a drawing rather than a call?

Look for a WaitFor, a startup ordering script, a depends_on in Compose, or an init container, and ask what would actually break if you deleted it. Most teams have at least one; being the person who deleted it is a small, very credible story.

What did people on your team quietly stop doing because it was too slow?

Running the full stack, running the integration tests locally, running the linter before pushing. The abandonment is the symptom; the interviewer cares that you noticed a behaviour change rather than waiting for a complaint.

Have you ever traded local fidelity for local speed? What went wrong later?

Persistent containers, shared dev databases, mocked dependencies, an in-memory provider standing in for a real database. Each buys speed and sells accuracy; name the bug that eventually escaped because of it.

(d) Follow-up drill chain

Why does WaitFor cost anything at all? Explain what it is waiting on.

Because it waits on health, not on process start. DCP marks a resource Running as soon as the process or container is up, but WaitFor holds the dependent resource until the target reports healthy, and health comes from the health checks that the hosting integration registered — a TCP connect and a real command for Postgres, a ping for Redis. That is a polling loop with an interval, so a chain of four WaitFor edges is four sequential health-check latencies stacked end to end, even though nothing is CPU-bound. The value is that your API never starts against a database that is listening but not accepting connections, which is the classic Compose race; the cost is that the edge is real and you should only draw the ones that exist.

What did you trade away by making the containers persistent?

Reproducibility. A session-lifetime container gives every run a pristine database, which is the strongest possible guarantee that the state you are debugging came from the code you are running. Persistent containers keep schema drift, half-applied migrations and yesterday's test data around, and those produce the worst kind of local bug — one that only exists on your machine. I bought the speed back with two things: a one-command reset that removes the volume and re-seeds, and CI that always runs on a clean session-lifetime graph, so nothing persistent can ever be load-bearing for correctness. If a team is not disciplined about that reset, session lifetime is genuinely the better default.

At what scale does this approach stop working?

Around the point where the machine, not the graph, is the constraint — roughly two dozen resources on a typical developer laptop, and much sooner if several of them are JVM-based or run a database engine each. Past that, trimming wait edges buys nothing because everything is competing for CPU and memory, and the answer changes shape: split the AppHost per bounded context, point at shared instances with AddExternalService for the things you are not editing, or move the whole loop into a dev container or Codespace where the resources are somebody else's. That is story 07 rather than this one, and knowing which of the two problems you have is most of the skill.

How would you keep it fast a year from now?

Make the number visible and give it an owner. Startup duration is reported per resource on the dashboard, and the AppHost is a normal program, so a small step in the nightly pipeline can start the graph, wait for everything to report healthy and record how long that took. Once it is a tracked number, a pull request that adds a gratuitous WaitFor shows up as a regression rather than as folklore six months later. The cultural half matters more than the automation: I put "does this edge represent a call?" into the review checklist for the AppHost, because that file is the one place in the repository where an offhand line costs everyone thirty seconds a day.

Your inner loop got fast. Did it get less like production?

Yes, and that is the honest trade. Aspire's promise is topological fidelity — the same resource graph and the same connection-string wiring locally and in the cloud — not operational fidelity, and the moment you trim resources out of the default run you have two topologies. I handled that by keeping the full graph as the named default in CI and in the pre-merge run, so the trimmed one is a convenience rather than the truth, and by making the trim explicit in a launch profile with a comment naming what is missing. What Aspire genuinely does buy you is that the wiring cannot drift: the connection strings and service-discovery variables are generated from one model, so a resource that is present behaves the same way it will in the deployed environment.

02Aspire's Bicep, or our Terraform

tier · principal hard architectural trade-off

Example — replace with your own

The question arrived as a one-liner in a design review — "if Aspire can generate the infrastructure, why are we still writing Terraform?" — and it took me three weeks and a written decision record to answer properly, because both answers are defensible and the wrong one is expensive for years.

Here is the mechanism the argument turns on. When you write builder.AddAzurePostgresFlexibleServer("pg"), you are not just declaring a dev-time container; you are declaring an Azure resource, and at publish time Aspire emits Bicep for it and wires the connection information into the consuming services automatically. Locally, RunAsContainer() swaps that same node for a container so nobody provisions cloud infrastructure at F5. That is a genuinely good property: one declaration, two materialisations, and the application code never knows which it got because it only ever reads a connection string by resource name. The catch is ownership. Our platform team owned the subscriptions, the network topology, the private endpoints and the compliance posture in Terraform, with state in a storage account and a policy that nothing enters production except through that pipeline. Aspire's deployment path wanted to provision too, and two systems that both believe they own a resource is not a preference argument, it is a drift generator.

I refused to make it a binary. The framing I landed on — the one that actually ended the debate — was to sort every resource by who owns its lifecycle, not by which tool could create it. A resource whose lifetime is the application's lifetime and whose blast radius is one application belongs to the app model. A resource that is shared, stateful, expensive to recreate, or subject to a compliance control belongs to the platform's Terraform, and the app model references it rather than creating it. Aspire 13.5 made the second half considerably cleaner: AsExistingInResourceGroup(), AsExistingInSubscription() and AsExistingInTenant() let a resource sit in a different scope from the deployment while still participating in the model, which previously meant hand-rolling a connection-string parameter and losing the typed wiring.

var builder = DistributedApplication.CreateBuilder(args);

// Platform-owned: Terraform creates it, the app model only references it, and
// AsExistingInResourceGroup keeps the typed wiring while the resource lives in
// another scope entirely. (AsExistingIn* landed in Aspire 13.5.)
var sharedPg = builder.AddAzurePostgresFlexibleServer("pg")
    .AsExistingInResourceGroup(
        builder.AddParameter("platform-rg"),
        builder.AddParameter("pg-name"))
    .RunAsContainer();                 // ...but a plain container at F5

// App-owned: created and destroyed with this application, blast radius of one.
var bus = builder.AddAzureServiceBus("bus");

// Truly external, or owned by a system with no Aspire representation at all:
// a connection string parameter, injected by the pipeline from Key Vault.
var legacy = builder.AddConnectionString("legacy-erp");

builder.AddProject<Projects.Acme_Api>("api")
    .WithReference(sharedPg.AddDatabase("appdb"))
    .WithReference(bus)
    .WithReference(legacy);

builder.Build().Run();

The result was a boundary anybody could apply without me in the room, written down as a two-column table in the decision record: nine resource types on the platform side, four on the app side, and a rule that moving one across the line needs a pull request against the record itself. Six months in, one resource has crossed — the Service Bus namespace, which grew into a shared asset the moment a second team subscribed to it, exactly as the rule predicted. What I would do differently is the sequencing: I ran the debate as an architecture question for two weeks before realising it was an ownership question, and the platform lead had been trying to tell me that from the first meeting. I also under-weighted the day-2 argument — who gets paged when the provisioning fails at 3am is a better decision criterion than which syntax is nicer, and it is the one that convinced the sceptics.

Whether you can hold a genuine trade-off without collapsing it into a tool preference — and whether you know that infrastructure arguments are really ownership arguments. At principal level they also want the governance half: a decision that only holds while you are in the room is not a decision. (c) Recall prompts

When have you had two tools that both wanted to own the same thing?

IaC versus a platform portal, a service mesh versus an SDK, two CI systems, an ORM versus hand-written migrations. The story is not which won; it is the boundary you drew and whether it held.

What is the most expensive architectural decision you have written down rather than just made?

Look for an ADR, a decision record, a wiki page people still link to. If you have never written one, the honest version — "we decided in a meeting and re-litigated it three times" — is itself a good answer with a real lesson.

Where do you have infrastructure drift today, and how did you find out?

A hand-edited setting in a portal, a resource nobody can find the code for, a Terraform plan that always shows the same three changes. Drift stories are unusually convincing because everyone in the room has one.

Have you deliberately chosen the slower-to-adopt option? Why?

This tests whether you optimise for the first ninety days or the next three years. Name the property you were protecting — auditability, a single provisioning story, an existing on-call contract — and what it cost in velocity.

(d) Follow-up drill chain

Why not just let Aspire own all of it? It is one tool instead of two.

Because provisioning is not the hard part of infrastructure — owning it for three years is. Aspire's generated Bicep is genuinely good at the resources whose lifecycle matches the application's: create them with the app, destroy them with the app, and let the app model carry the wiring. It is a poor fit for a resource that outlives every application touching it, sits behind a compliance control, or has a network topology somebody else is accountable for, because then the app repository becomes the place where production policy is decided by whoever merges fastest. There is also a practical asymmetry: our Terraform estate predated Aspire by four years and encoded rules nobody had written down anywhere else. If I were greenfield, with no platform team and no existing estate, I would let Aspire own everything and be happy about it.

How do you stop the boundary eroding once you stop watching it?

Put it where the work happens rather than in a wiki. The decision record has a table of resource types with an owner column, and the AppHost has a review rule that adding an AddAzure* resource requires either a matching row or a change to the record in the same pull request. The platform side has the mirror control — their pipeline refuses to create a resource type that the table assigns to the app model. Neither of those is airtight, and I said so at the time; what makes it hold is that both controls are cheap to satisfy for the common case, so nobody is incentivised to route around them. The escape hatch is deliberate and loud rather than absent.

At what scale does the split model break down?

When the number of teams exceeds the number of people who understand the boundary — in practice, somewhere past a dozen application teams sharing one platform. At that size the classification stops being obvious at the margin, every ambiguous resource becomes a meeting, and the meeting cost exceeds whatever the split was saving. The move then is to stop classifying resources and start shipping paved paths: a small set of blessed application environments where the platform pre-provisions the whole shape and applications get references, never creation rights. That is a bigger organisational change than a tooling choice, and it is worth saying out loud that it is a trade of flexibility for scale rather than a strict improvement.

What did you give up by not letting the app model provision everything?

Two real things. First, the one-command story: a new engineer cannot go from clone to a fully provisioned personal environment without the platform pipeline, which costs about a day of onboarding. Second, a class of fidelity — the resource the app model describes and the resource Terraform creates can differ in settings the app model does not model at all, such as a firewall rule or a private endpoint, so "it worked in the generated environment" is weaker evidence than it would have been. I mitigated the first with a shared ephemeral environment per team and the second by having the app model reference the real resource in every non-local environment, so the very first integration test runs against the Terraform-shaped article, not against an idealised one.

If the platform team had refused entirely, what would you have done?

Kept Aspire for the inner loop and testing, and used aspire publish rather than aspire deploy — generate the artefacts, commit or review them, and let the existing pipeline apply them. That preserves the majority of the value, because the expensive problems Aspire solves for us are local orchestration, service-discovery wiring and integration testing, none of which need provisioning rights. I would have been explicit with my own team that we were taking the smaller win deliberately rather than being blocked, because the failure mode I have seen elsewhere is a team that adopts half a tool while telling itself it has adopted all of it, and then argues for two years about why the promised benefits did not arrive.

03The health check that cycled the fleet

tier · staff production incident / outage

Example — replace with your own

Eleven minutes of total outage, caused by a cache being slow. Not down — slow. That sentence is the whole story, and it is the one I lead with, because every experienced interviewer leans forward at it.

The chain was this. Aspire's service defaults map two endpoints, and they are not the same thing: /alive runs only the checks tagged live and answers "is this process still a going concern, or should it be killed and restarted", while /health runs every registered check and answers "is this instance ready to take traffic". Aspire maps both only when the environment is Development, and the template says so in a comment, because these endpoints are unauthenticated and running every check on every probe is a real cost. Somebody on the team wanted to see health in production, removed the IsDevelopment() guard, and pointed the Container Apps readiness probe at /health. That looks harmless and it is the single most common Aspire-shaped production mistake I have seen.

What made it fatal is what was registered in /health by then. Every client integration adds its own check by default — AddRedisClient adds a Redis ping, AddNpgsqlDataSource adds a connection probe — and a well-meaning engineer had added an outbound check against a partner API. So /health had become a logical AND over four dependencies, three of which the service could survive without. Redis went into a 90-second latency spike during a planned failover on the managed instance. The ping check timed out. Every one of our 42 replicas returned Unhealthy within one probe interval. The orchestrator did exactly what we told it to: it removed all 42 from rotation. The application itself was perfectly capable of serving traffic — the cache path had a fallback to the database and had been tested — but no request ever reached it.

// ServiceDefaults - the corrected version. Two endpoints, two questions.
public static WebApplication MapDefaultEndpoints(this WebApplication app)
{
    // Liveness: only checks tagged "live". If this fails, restarting helps.
    app.MapHealthChecks("/alive", new HealthCheckOptions
    {
        Predicate = r => r.Tags.Contains("live")
    });

    // Readiness: only checks tagged "ready" - the dependencies without which
    // this instance genuinely cannot serve. NOT "every check ever registered".
    app.MapHealthChecks("/health", new HealthCheckOptions
    {
        Predicate = r => r.Tags.Contains("ready")
    });

    return app;
}

// ...and in AddServiceDefaults, tag deliberately:
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"]);

// A hard dependency: no database, no service.
builder.AddNpgsqlDataSource("appdb", s => s.HealthCheckTags = ["ready"]);

// A soft dependency: degrade, do not evacuate. Surfaced as a Degraded
// result on a separate diagnostic endpoint, never on the readiness probe.
builder.AddRedisClient("cache", s => s.DisableHealthChecks = true);

Mitigation was crude and fast: I pointed the readiness probe at /alive from the portal, which brought the fleet back in about ninety seconds, and only then went looking for why. The durable fixes were three. Tag every check as live or ready deliberately and make an untagged check a build failure in the shared defaults, so nobody accidentally promotes a dependency to load-bearing. Take soft dependencies off the readiness probe entirely and express them as Degraded on a separate authenticated diagnostics endpoint, which is where humans should look anyway. And add a game-day: we now deliberately break the cache in staging once a quarter and assert that traffic keeps flowing.

What I would do differently: I would have caught this in review if I had been reading the service defaults as production code rather than as boilerplate. Shared templates are the highest-leverage code in the estate — one line there is 42 replicas — and we were reviewing them with less care than a feature branch. I also owned a share of the cause honestly in the postmortem: I had approved the pull request that removed the Development guard, six weeks earlier, in about forty seconds.

(b) STAR / CARL scaffold

Why does Aspire only map those endpoints in Development by default?

Because they are unauthenticated and they run work. The subtler point is that the orchestrator does not need a rich endpoint at all: a readiness probe wants a fast, boring boolean about this instance, and everything diagnostic belongs somewhere humans look.

Would a cache circuit breaker have prevented it?

Not on its own, and this is the distinction I would want a candidate to draw. We already had graceful degradation in the request path — the cache miss fell through to the database and had been load-tested — so the application was genuinely fine. The failure was entirely in the control plane: the probe reported unhealthy, so no request ever reached the code that would have degraded gracefully. A breaker would have made the health check itself fail fast rather than time out, which changes the latency of the wrong answer, not its correctness. The fix has to be at the semantic level: a readiness probe must only assert things whose failure genuinely means this instance cannot serve.

At what scale does an aggregated readiness check become dangerous?

The instant the dependency is shared, regardless of fleet size. This is about correlation, not scale: if all N replicas check the same external thing, that check has a fleet-wide blast radius by construction, so one dependency blip removes 100% of capacity simultaneously. With per-instance state — a local disk, a warmed cache, a leader lease — readiness is exactly the right place, because failures are independent and the load balancer routes around them. The rule I teach is: put a dependency in readiness only if you would be happy for every replica to leave rotation at the same moment for that reason.

By breaking it on purpose, on a schedule. A postmortem action item that says "tagged the checks correctly" decays — six months and forty pull requests later, someone adds a check without a tag. (d) Follow-up drill chain

Why sequence it? Why not do the whole upgrade in one branch?

Because a single branch collapses attribution. With the SDK bump, the Aspire major and the package renames in one change, every failure has four candidate causes and you spend the debugging time bisecting your own work. Sequencing means each step has exactly one variable, so a failure names its own cause — and each step is independently revertible, which matters when the pressure to ship a feature arrives on day four. There is a real cost: sequencing is slower in wall-clock terms when nothing goes wrong, and it needs the intermediate states to be shippable, which is not free. I take that trade whenever the change touches the build, because build breaks block everyone rather than just me.

How did you find the silent breaks?

By reading the breaking-changes list for every intermediate version, not just the target, and turning each entry into a search. The scheme-keyed service-discovery variables from 13.2 were found by grepping for services__ across the whole repository including scripts and test fixtures, which turned up two hand-rolled readers. The general rule I now apply: anywhere the application reads a framework-generated environment variable or connection string by literal name is a place a minor release can break you silently, so those get wrapped in one helper with a test. I also ran the full integration suite against each intermediate version rather than only the final one, which is how the port-allocation change in 13.5 surfaced as a test failure rather than as a mystery in someone's afternoon.

What did you trade away by deleting the custom publisher?

Control, and a small amount of output fidelity. Our publisher emitted a Helm values file shaped exactly the way the platform team's charts expected, including two annotations no generator was going to produce. Deleting it meant accepting the generated artefacts plus a thin transformation step, so we now own a transformation instead of a generator — less code, but a seam that can drift when the generated shape changes between versions. I made that trade because the custom publisher had cost us roughly a week a year in maintenance and was understood by one person, and because the pipeline-step model in 13 gave a supported extension point where previously we had been working around the absence of one. If our platform requirements had been genuinely unusual rather than merely specific, porting would have been right.

Only the latest release is supported. How do you plan for that permanently?

By making the upgrade a routine rather than a project. A minor lands roughly every couple of months, and each one ends support for its predecessor, so the only sustainable posture is a standing cadence: a scheduled branch that bumps the pinned version, runs the full suite, and produces a one-page diff of the breaking-changes list for a human to read. Two things make that cheap — central package pinning so the bump is one file, and integration tests that exercise the resource graph rather than mocking it, since those are what catch the behavioural changes. The organisational half is a stated policy that we stay within one minor of current, agreed with the people who own the risk, so it is a commitment rather than a heroic effort each time.

Nine days against a two-day estimate. What do you tell your manager on day three?

On day three, with two of the eleven services done and the publishing rewrite still unscoped, I told them the estimate was wrong, gave the new number with the reason — a replaced publishing model rather than a rename list — and offered the option I thought they should take: keep going, because the alternative is running unsupported, and the sunk work does not transfer. What I would not do is deliver the revision at day eight, which is how a technical delay becomes a trust problem. I also gave them a checkpoint: if the publishing rewrite was not done by day six, we would ship the intermediate state, which was already on the supported version, and defer the publishing change. Having a fallback with a date attached is what makes a bad estimate recoverable.

A senior engineer I respected pushed back hard on service discovery in a design review, and his argument was good: "It is a URL. We have had URLs in configuration for twenty years. You are adding a resolver, a scheme I have to explain to every new joiner, and a magic environment variable, to solve a problem that appsettings.json already solves." He was not being obstructive; he had been burned by a service mesh that added latency and mystery, and he was pattern-matching.

I lost the first conversation because I argued the wrong axis. I talked about elegance. What actually settled it, a week later, was counting edits. I took a real change we had made two months earlier — renaming a service and moving it to a different host in one environment — and counted the places that had to change under each model. With configuration files: six, across four repositories, plus a Helm values file and one place we had missed at the time, which is why that change had caused a twenty-minute outage in staging. With the app model: one, in the AppHost, and the value is generated everywhere it is consumed.

The mechanism is worth being precise about, because "magic" is exactly the objection and the answer to it is that there is no magic. WithReference(api) does one thing: it injects configuration into the consumer, keyed by resource name and endpoint scheme, in a format the .NET service-discovery library understands — services__api__https__0 and so on. In Aspire 13.2 that key changed from the endpoint's name to its scheme, which is worth knowing because anything reading those keys by hand broke silently at that version. Then AddServiceDiscovery — already there inside AddServiceDefaults — registers a resolver on HttpClient so that a request to https+http://api reads that configuration, picks the first scheme it can satisfy, and rewrites the URI. That is it: environment variables in, configuration provider, an HttpClient handler. No sidecar, no control plane, no runtime dependency, no added hop. In production the same configuration keys can be populated by whatever your platform uses — DNS names in Kubernetes, ingress names in Container Apps — because the abstraction is the configuration key, not the mechanism behind it.

// AppHost: one declaration of the edge.
var api = builder.AddProject<Projects.Acme_Api>("api");

builder.AddProject<Projects.Acme_Web>("web")
    .WithReference(api)   // injects services__api__https__0 / services__api__http__0
    .WaitFor(api);
// Consumer: the scheme list is a preference order, not a protocol.
// "https+http" means "use https if the resource publishes one, else http" -
// which is what makes the same code work locally and behind TLS termination.
builder.Services.AddHttpClient<CatalogClient>(c =>
    c.BaseAddress = new Uri("https+http://api"));

// AddServiceDefaults() already called AddServiceDiscovery() and added the
// standard resilience handler; the resolver is a DelegatingHandler, nothing more.

He conceded on the edit-count argument, and I conceded on two of his points, which is the part I would want an interviewer to hear. First, he was right that the scheme string is a genuine learning cost, so we put a three-line comment above every BaseAddress and a paragraph in the onboarding guide. Second, he was right that it is worth knowing how to get out: because the whole thing resolves through configuration, any environment can override a service's address with a plain configuration value, and we documented that escape hatch explicitly. We also agreed a rule that ended the class of argument: the app model owns addresses of things inside the application; anything genuinely external gets declared with AddExternalService so it is still in the model, still visible on the dashboard, but obviously not ours to start.

What I would do differently: lead with the incident. I had a real twenty-minute staging outage caused by the sixth place nobody updated, and I did not use it in the first conversation because it felt like point-scoring. It was not; it was evidence, and withholding it cost a week.

(d) Follow-up drill chain

Explain exactly what https+http://api does. Is it a protocol?

No — it is a scheme preference list consumed by the service-discovery resolver, and it never goes on the wire. When the HttpClient handler sees it, it looks up configuration under services:api, finds the entries for https and http, and rewrites the request URI to the first scheme that has an address, preferring https. Locally that resolves to the loopback address and port DCP allocated; in a deployed environment it resolves to whatever populated those configuration keys. The reason to write both rather than just https is that it degrades cleanly where TLS is terminated upstream, which is the common Container Apps and Kubernetes shape, without the calling code knowing. If the key is missing entirely you get a failure at first use rather than a mysterious connection to the wrong place, which is the behaviour you want.

What happens to service discovery in production? Does Aspire run there?

Aspire does not run there — the AppHost is a development-time orchestrator, and nothing of it is deployed. What survives into production is the configuration contract: the consuming service still reads services__* keys through the same resolver, and the deployment artefacts Aspire generates populate those keys with the platform's real addresses, whether that is a Container Apps ingress FQDN or a Kubernetes service name. You can equally populate them yourself from Helm values or app settings, which is exactly the escape hatch we documented. The important framing for an interview is that the abstraction is a configuration key with a defined shape, not a runtime component, so there is nothing to be operationally afraid of and nothing extra to run.

At what scale does configuration-based service discovery stop being enough?

When you need per-request routing decisions rather than per-process addresses: weighted traffic splitting for a canary, mutual TLS enforced independently of application code, retries and circuit breaking governed centrally rather than per client, or fine-grained authorisation between services. The .NET resolver gives you a list of endpoints and simple round-robin over them, which covers a surprising amount, and the standard resilience handler covers retry and breaker policy per client. Past that you want a mesh or a gateway, and the two compose rather than compete — service discovery resolves the name, the mesh governs the traffic. I would push back hard on adopting a mesh for discovery, though; that is buying an operational estate to solve a configuration problem.

What did you trade away?

Explicitness, and a bit of grep-ability. When the URL was in appsettings.json, a new engineer could search for the hostname and find every caller; now they have to know that WithReference in the AppHost is the edge declaration and that the scheme string in BaseAddress is a resource name. That is a real cost and I did not pretend otherwise — it is why the comment and the onboarding paragraph were part of the deal rather than an afterthought. The compensating property is that the AppHost becomes the one file that describes the topology, so the question "who calls whom" has a single answer instead of being reconstructed from six configuration files. On balance I would take that trade every time, but the honest version names both sides.

How would you introduce this to a team that had already rejected it once?

Narrowly, and with the evidence they already have. I would not re-open the general argument; I would take one new service pair where the wiring did not exist yet, use the pattern there, and let it sit for a month. Then the conversation is about something running rather than something proposed, and the sceptic gets to inspect the environment variables themselves — which is what defuses "magic" better than any explanation. I would also ask directly what would change their mind, because if the answer is "nothing" then it is not a technical disagreement and pretending otherwise wastes everyone's month. In my case the answer was concrete: he wanted to see the escape hatch work, so I showed him a configuration override before I asked for anything.

The reason it took two days rather than twenty minutes is that I looked in the wrong layer. Everything Aspire wires for you is correct by construction — WithReference injects addresses that are already resolved from the container's point of view, and Aspire 13.3 turned on a container tunnel by default specifically so that container-to-host connectivity is uniform rather than depending on whether your engine supports a magic host name. A lint rule, a review checklist item, a test, a wiki page people actually link to. Interviewers at senior and above are listening for the durable artefact.

(d) Follow-up drill chain

Why is container-to-host the awkward direction, when the other three work?

Because it is the only direction where the network namespace boundary is crossed in the direction the container runtime does not naturally publish. A host process reaching a container works because the runtime maps a host port to the container. Container-to-container works because they share a user-defined network with name resolution. But a container reaching back to a process on the host has no default route to a host loopback address, and the historical workarounds — a magic host name that resolves to the host gateway — behave differently across engines and platforms. Aspire 13.3 made the container tunnel the default precisely to make this direction uniform, so the practical answer today is: take the injected endpoint and do not think about it. The reason to still understand the mechanism is that the moment something is not injected — a baked config file, a third-party image's defaults — you are back in the raw problem.

Why was it intermittent? Intermittent usually means concurrency.

Here it meant port allocation, which behaves a lot like concurrency from the outside. The container had a diagnostics listener on a port near the one it was dialling, and whether the dial hit a closed port or that listener depended on which port DCP had allocated on that machine on that run — so it looked non-deterministic while being entirely deterministic given the allocation. That is the general shape: when something is intermittent across machines but stable within a session, suspect an allocated resource — a port, a temporary directory, a generated name — before you suspect a race. It is also why the fix had to be structural rather than picking a different port: pinning a port would have made it work today and broken on the next machine that had that port taken.

At what scale does this class of problem get worse?

It scales with the number of resources you did not author — third-party images, another team's container, anything with its own configuration file. A model with twenty first-party projects has essentially none of this problem, because every address is generated; a model with four third-party images has four independent chances to hard-code something. So the mitigation is not technical scale but a policy at the boundary: when a container joins the model, its configuration gets templated from the model or it does not join. In one estate I would go further and require that any image we do not build ourselves is wrapped in a thin first-party image whose entrypoint reads environment variables, so the hand-written surface is one file we own rather than whatever the upstream author decided.

What would you have done if you could not change the image or its config format?

Generate the file at start-up rather than baking it, which is what we ended up doing anyway — a container-files callback runs after endpoint allocation, so it can write a real address into whatever format the image expects. If even that were closed, the next option is an environment-variable substitution entrypoint, and after that a small sidecar or reverse proxy that owns a stable address the image can hard-code while forwarding to the real one. I would take them in that order because each step adds a moving part; the general principle is to push the indirection as close to the untouchable component as possible, so that the rest of the model stays generated. What I would not do is pin ports globally to make the hard-coded value true — that trades a local bug for an estate-wide constraint.

Two days is a long time. How do you decide when to ask for help?

My rule is a timebox plus a written hypothesis: if I cannot state what I currently believe and what observation would falsify it, I am no longer debugging, I am browsing, and that is the moment to pull someone in. I broke my own rule here because each new hypothesis felt fresh, which is exactly how a day disappears. What I do now is write the hypothesis in the incident or issue thread as I go, which has two effects — it forces the falsification question, and it means the colleague I eventually ask can join at my current state instead of my starting state. In this case, writing "I believe the API is not listening" would have immediately raised "not listening from where?", which was the whole answer.

07Thirty-one resources, one laptop

tier · staff scaling challenge

Example — replace with your own

Success created the problem. The AppHost had started with six resources and worked so well that every team added theirs, and eighteen months later it described thirty-one: fourteen .NET projects, a React front end, nine containers, a couple of one-shot jobs and a handful of Azure resources running as emulators. On a 16 GB machine it did not start. On a 32 GB machine it started in about two and a half minutes and left roughly nothing for an IDE. People had begun commenting out chunks of the AppHost locally and, inevitably, committing those comments.

The instinct is to optimise, and that was wrong. The real diagnosis was that the app model had stopped describing an application and started describing an estate. Aspire's app model is scoped to a deployable unit that shares a lifecycle; once it spans four teams with independent release cadences, the model is fighting the organisation. The size was the symptom, and I said that out loud early, because it reframed the work from "make it faster" to "draw a boundary".

What we shipped was four AppHosts along the bounded contexts that already existed in the org chart, plus a rule for the seams. Anything you are not editing right now is not a resource you run: it is an AddExternalService pointing at the team's shared development instance, which keeps it in the model — visible on the dashboard, participating in service discovery, showing up in the topology — while costing nothing to start. Anything you are editing runs locally. Then the ergonomics: parameterise which optional resources start so the default F5 is the ten things you almost always need, and use the CLI's isolated mode so two AppHosts can run side by side without fighting over ports or container names, which matters enormously the day someone is working across a seam.

// Orders AppHost - owns what this team edits, references what it does not.
var builder = DistributedApplication.CreateBuilder(args);

var pg = builder.AddPostgres("pg").WithLifetime(ContainerLifetime.Persistent);
var orders = builder.AddProject<Projects.Orders_Api>("orders")
    .WithReference(pg.AddDatabase("ordersdb"));

// Another team's service: in the model, on the dashboard, not on your CPU.
var catalog = builder.AddExternalService("catalog",
    builder.AddParameter("catalog-url"));   // dev instance by default

orders.WithReference(catalog);

// Heavy, rarely-needed extras behind a switch, so the default F5 stays small.
if (builder.Configuration.GetValue("Local:RunSearch", false))
{
    var search = builder.AddContainer("search", "opensearchproject/opensearch", "3.2")
        .WithLifetime(ContainerLifetime.Persistent);
    orders.WithReference(search.GetEndpoint("http")).WaitFor(search);
}

builder.Build().Run();

Numbers: the orders AppHost starts eleven resources in 22 seconds and holds around 4 GB, and it runs on the 16 GB machines that previously could not start anything. The commented-out AppHost lines stopped appearing in pull requests within two weeks, which was the metric I actually cared about, because it meant the tool matched how people worked instead of being routed around. For the genuinely cross-cutting work — a change that spans orders and catalog — you run two AppHosts in isolated mode and point one parameter at the other's local endpoint, which happens perhaps twice a month and is fine when it is a deliberate act rather than the default.

What I would do differently: draw the boundary at fifteen resources rather than thirty-one. I could see the trajectory a year earlier and did not act because no single addition was unreasonable — each team was adding one thing, politely. That is the classic shape of an architectural erosion, and the lesson I took is that shared artefacts need a stated limit before anyone is near it, because arguing for a limit while people are over it reads as blame.

(d) Follow-up drill chain

Why split by bounded context rather than just running fewer resources?

Because "run fewer" has no stopping rule and no owner. If everyone trims to taste you get thirty personal topologies, none of which match CI, and the failures that result are unattributable. Splitting on an existing organisational seam gives each model a team that owns it, a release cadence it matches, and a natural answer to "should this resource be here?" — does this team deploy it? The cost is that cross-context work now needs two AppHosts and a parameter, which I would rather have as an explicit occasional act than as a permanent ambient cost. I also would not invent a boundary for this: if the org has no bounded contexts, splitting the AppHost creates a fiction, and the honest answer is a dev container or a bigger machine.

Does AddExternalService not just recreate the shared-dev-environment problem you were escaping?

Partly, yes, and it is worth being honest about that. Pointing at a shared instance reintroduces shared state, other people's deploys and the "who broke dev" conversation. The difference from where we started is scope and choice: it applies only to services this team does not edit, and any engineer can flip the parameter to a local instance for the day they need isolation. It also keeps the dependency in the app model rather than in a config file, so the topology stays truthful and the dashboard still shows it. Where that trade fails is a dependency that is both shared and unstable — if the catalog team deploys broken builds to dev twice a week, external references make your morning depend on their afternoon, and then you run it locally regardless of the memory cost.

At what point would you move the whole thing off laptops?

When the smallest useful slice does not fit — that is the test I would use, not total size. If one team's own context genuinely needs twenty resources, including something like a full search cluster or a GPU-backed model, then no amount of boundary-drawing helps and you are paying for hardware one way or another. At that point dev containers or Codespaces are the cheaper answer, and Aspire supports that path directly. The thing I would want to decide deliberately rather than drift into is who pays and what the idle policy is, because remote development environments are excellent until they are a five-figure monthly line item nobody owns — which is a cousin of story 16.

How did you get four teams to agree?

By not asking them to agree on much. The split followed boundaries they had already accepted for deployment and on-call, so the proposal was "the app model should match the boundary you already own" rather than a new taxonomy, and that is a very short argument. I did the first split myself, end to end, including the CI changes, so the other three teams were reviewing a working example rather than a plan. The one genuine negotiation was the seam contract — what a team guarantees about its shared dev instance — and I deliberately made that small: a URL that resolves and a health endpoint that is honest. Anything more ambitious would have become a standards project and died.

What broke that you did not anticipate?

Integration tests that spanned two contexts. They had been quietly relying on the single AppHost bringing up the whole world, and after the split they needed either a test-scoped model of their own or a real environment to run against. We ended up moving four of them up to a thin end-to-end suite that runs against the deployed development environment, and deleting two that were asserting things a contract test could assert better. That took an extra week I had not planned for, and it is the part I would flag first if I did this again — when you split an app model, you split every test that depended on its scope, and those tests are usually the ones nobody has looked at in a year.

08The password in plain sight

tier · senior security issue found / fixed

Example — replace with your own

I found it while doing something else entirely: screen-sharing the Aspire dashboard in a demo to about twenty people, clicking into a resource to show the environment variables, and reading out loud a connection string that contained a real password for a partner sandbox — on a call that was being recorded. I finished the sentence, closed the panel, and spent the afternoon working out how far it went.

The mechanism is not a flaw; it is a default that people misread. Aspire distinguishes plain parameters from secret ones. A plain parameter is configuration — it has a value you can see, it shows up in the dashboard's Parameters tab, and it is meant to be visible. A parameter declared with secret: true is masked in the dashboard and treated as sensitive by the tooling. Whoever added the partner credential had used a plain parameter, because it worked, and nothing told them otherwise. Worse, the value had been supplied through the AppHost's configuration file rather than user secrets, which meant it was in git. Aspire 13.2 consolidated AppHost configuration into aspire.config.json, and consolidation is good, but it also means there is now one obvious file people put things in — and it is in the repository.

// Wrong: value in aspire.config.json, in git, visible in the dashboard.
var partnerKey = builder.AddParameter("partner-api-key");

// Right: marked secret, so the dashboard masks it and the tooling knows.
var partnerKey = builder.AddParameter("partner-api-key", secret: true);

// Better still: never have a dev value at all. Let Aspire generate one for
// local containers, and take real values from a real store per environment.
var pg = builder.AddPostgres("pg");   // password generated per run, not typed

var apiKey = builder.AddParameter("partner-api-key", secret: true);
builder.AddProject<Projects.Acme_Api>("api")
    .WithEnvironment("Partner__ApiKey", apiKey);
// Local values live in user secrets - outside the repository, per developer.
// dotnet user-secrets set "Parameters:partner-api-key" "..."   (AppHost project)
{
  "Parameters": {
    "partner-api-key": "the-real-value-never-committed"
  }
}

The response had three parts and I did them in this order. Contain: rotate the partner credential, which took a support ticket and four hours, and ask for the recording to be pulled. Assess: search git history for the value and every parameter that looked credential-shaped, which found two more — a webhook signing secret and, tediously, a personal access token in a comment. Prevent: a secret scanner in CI on both the repository and the history, a review rule that any AddParameter whose name matches a credential-ish pattern must be secret: true, and the more useful structural change — local development should not need real credentials at all. We stood up a fake partner endpoint as a container in the app model, so the default local run has no secret to leak. The container passwords Aspire generates per run are the right model to copy: the best-protected secret is one that never existed.

Two related exposures came out of the same review, worth knowing because interviewers probe here. The dashboard is not just a local UI — it can be run standalone against any OTLP source, and in that mode it needs its authentication configured deliberately rather than assumed. And the OTLP endpoint the dashboard exposes accepts telemetry from anything that can reach it, which is a fine default on a laptop and not a fine default anywhere else. Neither was a live problem for us, but "we checked and here is why it was fine" is a much better answer than not having looked.

What I would do differently: I disclosed the recording issue late in the day, after I had a fix, because I wanted to bring a solution rather than a problem. That was the wrong instinct for a credential exposure — the clock on containment starts when you know, not when you have a plan, and I should have told security within the hour and done the analysis in parallel.

(d) Follow-up drill chain

Why does a plain parameter show its value at all? Is that not a poor default?

No, because most parameters are genuinely configuration and hiding them would make the dashboard useless for the thing it is for — seeing what your application was actually given. A region, a feature flag, a tenant name, a URL: you want those visible, and the Parameters tab added in 13.1 exists precisely to make them easy to inspect. The design puts the decision where it belongs, on the person declaring the parameter, and gives an explicit marker for the sensitive case. Where I think it is genuinely sharp-edged is discoverability: nothing warns you at declaration time that a parameter named api-key is probably a secret, which is why we added that as a review rule rather than relying on judgment. The deeper answer is that a secret you have to remember to mark is a weaker control than a secret that does not exist locally.

You rotated the credential. How did you decide the blast radius?

By treating exposure as a set of channels rather than a single event, and enumerating each: the call recording and who could access it, the git history and everyone who had ever cloned the repository, any CI logs that had printed the environment, and the dashboard sessions themselves, which are local and therefore not a channel. Git history was the one that mattered — the value had been committed eleven months earlier, so every clone since had it, and no amount of rewriting history retracts that. That is why rotation was non-negotiable rather than a judgment call, and why I did not spend time debating whether the recording was really accessible. The general rule I use: if the secret has ever been at rest somewhere you cannot enumerate readers of, it is burned.

What is the risk with the dashboard itself, beyond this?

Two things worth naming. First, it can run standalone against any OTLP source rather than only as part of an AppHost run, and in that mode it is a real service with real access to your telemetry, so its authentication has to be configured deliberately — a browser-facing UI showing traces and environment details is a rich target. Second, its OTLP receiver accepts whatever can reach it, which is exactly right on a loopback interface and exactly wrong on a shared network, because both injecting misleading telemetry and reading other people's becomes possible. Neither was live for us; the point is that the safe local default and the safe shared default are different, and any tool you promote out of the inner loop needs that conversation before it moves.

At what scale does the "no real credentials locally" approach break?

It breaks against integrations you cannot faithfully fake — a payment provider with subtle asynchronous callbacks, an identity provider whose token shapes you depend on, anything where the fake diverges and you ship against the divergence. There the honest answer is a contained real credential rather than no credential: a per-developer sandbox account with the narrowest possible scope, short-lived tokens issued on demand, and a rotation that is cheap enough to do casually. The principle stays the same — reduce the value of what leaks — but the instrument changes from elimination to scope and lifetime. What I would resist is one shared sandbox credential for the whole team, which is the worst of both: real enough to matter, shared enough that nobody owns it, and long-lived because rotating it interrupts everyone.

Where is the goal state, and how far did you get?

The goal state is no static credentials anywhere: managed identity or workload identity federation for every cloud resource, so the deployed application holds nothing, and developer identity locally, so the laptop holds nothing either. Aspire supports that path directly — the Azure integrations default toward identity-based access rather than connection strings, and the Azure security guidance in the docs is explicit about it. We got most cloud resources onto managed identity within two quarters; what remains is the long tail of partner integrations that only offer an API key, which is a vendor constraint rather than an engineering one. I would report the position as a percentage of resources rather than as done, because the last 10% is the part that takes a year and pretending otherwise costs credibility.

09Deleting compose.yaml and 600 lines of bash

tier · staff tech-debt paydown / refactor

Example — replace with your own

The onboarding document was nineteen steps long and the third step was "ask in the channel if ./scripts/dev-up.sh hangs", which tells you everything. What we actually had was a 240-line compose.yaml, a dev-up.sh that ran migrations and waited on things with sleep loops, a .env.example that had drifted from .env, and four appsettings.Development.json files whose URLs and ports had to agree with the Compose file by hand. Roughly 600 lines of glue, none of it tested, all of it load-bearing. New joiners took a day and a half to get a working environment; the record was three days.

The refactor was worth doing for one specific reason, and I want to be precise because "we replaced Compose with Aspire" is not by itself an argument. Compose is a good tool for declaring containers. What it cannot do is know that your API is a .NET project with a launch profile, that the connection string it needs is the one belonging to the Postgres resource three lines up, or that the front end should not start until migrations have exited zero. So teams write that knowledge by hand, in three places, and the hand-written copies drift — which is what the sleep loops and the port table in the README actually were. Moving to an app model collapses those copies into one typed declaration: the resource graph is C#, so the connection string and the discovery variables are produced from the same object that declares the resource, and waiting is a first-class edge rather than a sleep.

I did it in four increments, each of which left the team with a working environment. First, an AppHost that ran only the containers Compose had run, with the projects still started by hand — that proved the container story and touched nobody's workflow. Second, move the projects in and delete the hand-maintained connection strings and URLs, which is where most of the 600 lines died. Third, replace the sleep loops with WaitFor and WaitForCompletion, and delete the migration bash. Fourth — and this is the step people skip — regenerate a Compose file from the app model for the two consumers who genuinely needed one, because Docker Compose publishing became a stable target in Aspire 13.2 and our QA rig ran on a plain VM with no .NET SDK on it.

# Before: the port and the connection string are hand-copied into three files,
# and 'depends_on' only waits for the container to start, not to be usable.
services:
  postgres:
    image: postgres:17
    ports: ["5432:5432"]
    environment: { POSTGRES_PASSWORD: devpassword }
  api:
    build: ./src/Api
    depends_on: [postgres]
    environment:
      ConnectionStrings__appdb: "Host=postgres;Database=appdb;Password=devpassword"
// After: one declaration. The connection string is produced from the resource,
// the password is generated per run, and the wait is on health, not on start.
var pg = builder.AddPostgres("pg").WithImageTag("18.3").WithDataVolume();
var db = pg.AddDatabase("appdb");

var migrations = builder.AddProject<Projects.Acme_MigrationService>("migrations")
    .WithReference(db).WaitFor(db);

builder.AddProject<Projects.Acme_Api>("api")
    .WithReference(db)
    .WaitForCompletion(migrations);

The numbers: onboarding went from a day and a half to about twenty minutes, measured on the next three joiners; 600 lines of untested glue became roughly 80 lines of C# that the compiler checks; and a whole category of ticket — "my environment is broken" — dropped to near zero, which I could show because we tagged them. The unexpected win was the dashboard: the first time someone debugged a failing local run by reading the structured logs and the trace of a request across three services, rather than by tailing four terminal windows, the argument for the change stopped needing to be made.

What I would do differently: I nearly did it as one big change over a long weekend, and the incremental version was slower in calendar time but is the only reason it landed. I also kept the old scripts in the repository "just in case" for two months, which was a mistake — two people kept using them, discovered bugs in a path nobody was maintaining, and the coexistence made both worse. Delete the old path on a date, and say the date up front.

(d) Follow-up drill chain

Compose works everywhere and needs no .NET SDK. Why give that up?

We did not give it up — we changed where it comes from. The app model can publish a Compose file as a build output, which has been a stable target since 13.2, so the QA rig and the two engineers on a machine without the SDK still get exactly what they had. The difference is that the file is now generated from the same declaration the developers run, so it cannot drift from it, which was the actual defect: our hand-written Compose file and our local setup had disagreed about two port numbers for months. Generated artefacts also review differently — you review the model, and the diff of the output is a consequence rather than a source of truth. Where I would still hand-write Compose is a context with no .NET at all, because then the app model has nothing to attach to and you are adding a toolchain for no benefit.

Why four increments rather than one change?

Because the team had to keep shipping and because a big-bang change makes every subsequent bug ambiguous. Each increment left a working environment, so at any point we could stop and still have made things better, and each one was independently reviewable — the container step was a 40-line pull request that anyone could reason about. The cost is calendar time and a period where two mental models coexist, which is real friction; I bounded it by doing all four within three weeks and announcing the sequence up front so people knew what was coming. The version I would defend hardest is the ordering: containers first, because that step touches nobody's daily workflow and buys credibility for the steps that do.

What did the refactor not fix?

Anything that was wrong with the architecture rather than the glue. We still had a service that owned two bounded contexts' data and a chatty call pattern between the API and the pricing service, and moving the wiring into a typed model made both of those more visible without making them better — if anything, the topology being obvious in one file is what finally got the chattiness onto the roadmap. It also did not fix test coverage; the same integration tests that were thin before were thin after, though they became much easier to write. I try to say this explicitly in interviews, because a tech-debt story that claims a refactor fixed everything is not credible, and naming the residual problems is what shows you understood the boundary of the change.

At what scale would you not do this?

Two cases. First, a polyglot estate where .NET is a minority: Aspire supports Python, JavaScript, TypeScript, Go and Bun resources now, so that objection is much weaker than it was in the 9.x era, but if there is no .NET at all, adopting a .NET-hosted app model to orchestrate other people's runtimes is a hard sell and I would not make it. Second, a team of two with a five-line Compose file, where the glue is not costing anything — the whole justification here was 600 lines and a day and a half, and without those numbers this is churn. The threshold I use is whether the same fact is duplicated across files; one duplication is tolerable, three is a drift generator.

How did you know it worked, beyond your own opinion?

Three signals, deliberately chosen before the work rather than after. Time-to-first-successful-run for the next new joiners, which we timed with a stopwatch rather than asked about. The count of tickets tagged "environment", which we had been tagging for a year already, so there was a baseline nobody could dispute. And the number of files changed in a typical pull request that added a resource, which went from four to one — that one is my favourite because it measures the actual defect rather than a proxy for it. I would avoid the metric everyone reaches for, which is lines of code deleted; it is satisfying and it measures nothing anyone outside engineering cares about.

Example — replace with your own

The same question reached me eleven times in two months, from five different people, always phrased as a bug: "I added Redis to the AppHost but the API says the connection string is missing." The eleventh time I stopped answering it and treated the frequency as the actual signal. A question that recurs across people is not eleven knowledge gaps; it is one missing mental model, and answering it individually is a way of feeling helpful while guaranteeing a twelfth.

The model is small once you see it, and it is the thing I would want any engineer on an Aspire codebase to be able to draw on a whiteboard. There are two entirely separate package families. A hosting integration — Aspire.Hosting.Redis, used in the AppHost as AddRedis("cache") — declares a resource in the app model: it starts a container locally, knows how to publish itself for deployment, and it produces a connection string named after the resource. A client integration — Aspire.StackExchange.Redis, used inside the service as AddRedisClient("cache") — consumes that connection string and registers a configured client with health checks, tracing, metrics and retry policy already attached. The two are joined by exactly one thing: the resource name, matched as a string, and delivered to the process as the ConnectionStrings__cache environment variable because WithReference put it there. Nothing else connects them. So the three ways to produce the reported symptom are: the names do not match, WithReference was never called, or the service is being run outside the AppHost so nothing injected anything.

// AppHost (hosting integration): produces the resource and its connection string.
var cache = builder.AddRedis("cache");           // Aspire.Hosting.Redis

builder.AddProject<Projects.Acme_Api>("api")
    .WithReference(cache)                        // injects ConnectionStrings__cache
    .WaitFor(cache);

// Service (client integration): consumes it by the SAME name.
// Aspire.StackExchange.Redis - registers IConnectionMultiplexer, plus a health
// check, OTel tracing and metrics, and the standard resilience settings.
builder.AddRedisClient("cache");

// The name is the contract. "cache" here must equal "cache" there. That is it.

A one-page diagram with the two families, the arrow labelled "the resource name", and the three failure modes — put in the repository, not the wiki, because people read what is next to the code. She did it better than I would have. (d) Follow-up drill chain

Why is the split between hosting and client integrations there at all? Would one package not be simpler?

They run in different processes with different dependencies, and merging them would drag orchestration concerns into every deployed service. The hosting integration is a build-time and development-time concern: it knows how to start a container, how to generate deployment artefacts, and how to describe the resource in the model — none of which the running service should carry into production. The client integration is pure runtime: a configured client, a health check, telemetry, and sensible retry defaults. Keeping them apart is also what lets the same service code run against a container locally and a managed cloud instance in production without recompilation, because the only thing crossing the boundary is a connection string. The cost is exactly the confusion in this story: two similarly named methods, and a string that has to match.

The join is a matched string. Is that not fragile?

It is the weakest part of the design, and I would say so plainly. A typo produces a runtime failure rather than a compile error, and the default framework message does not point at the cause. The mitigations are all about turning a late failure into an early one: fail fast at startup with a message that names the expected environment variable, and — the better fix — check the names across the solution at build time, which is what the analyser we wrote does. You can go further and generate constants for resource names from the AppHost so consumers reference a symbol, though that adds coupling I would only take on in a large estate. The general principle is the interesting bit: when a system joins two things by convention, invest in the diagnostic, because the convention is not going away.

How did you know the mentoring worked rather than the documentation?

Because of what she built that I had not asked for. Documentation and a better error message would plausibly have taken eleven questions down to three; what took it to one was the analyser, and the analyser was her idea. That is my test for whether ownership actually transferred: the owner does something outside the brief that is better than the brief. I also watched where the remaining questions went — they went to her, not to me, which is the boring administrative evidence that the ownership was real rather than nominal. If the questions had kept arriving in my inbox, I would have concluded I had delegated the work and kept the authority, which is the most common way this fails.

What if she had not been ready for it?

Then the brief was wrong, not the person — that is the framing I try to hold. I picked her because she had already asked the question twice, which meant she had the motivation and the context, and because the scope was bounded: one project, a clear success measure, and a failure mode that costs a build break rather than an outage. If she had stalled, my next move would have been to pair on the first diagnostic rather than to take it back, because taking work back after delegating it teaches everyone watching that delegation is provisional. There is also a version where the answer is genuinely no — if the person is already over capacity, handing them a stretch project is not development, it is offloading, and I have got that wrong before.

At what point does "make the mistake impossible" become over-engineering?

When the guard costs more than the mistakes it prevents, measured honestly. Eleven occurrences in two months across five people, each costing perhaps forty minutes of two people's time, is several days a year — an analyser is comfortably worth that. One occurrence, once, by one person who has now learned it, is worth a sentence in a code comment and nothing more. The trap at principal level is that building the guard is more fun than measuring whether it is needed, and every estate I have joined has three abandoned guards protecting against something that happened once in 2021. So I ask for the count before I build anything, and I put an expiry review on guards that are cheap to remove.

The adoption proposal I wrote was for the whole thing: app model, integration testing, generated deployment artefacts, the lot. Inner loop and integration testing reduce pre-launch risk directly — the team was losing time to environment problems every week and our integration coverage was thin, and both of those were on the critical path to a launch we could not slip. 12Postgres 18.3 ate the seed volume

tier · senior data-loss / corruption scare

Example — replace with your own

A routine Aspire upgrade, merged on a Tuesday afternoon, and by Wednesday morning nine developers had a Postgres container that refused to start with a message about an incompatible data directory version. The scare was not the container; it was what was in the volume. Over about two years the team had accumulated a local dataset that was genuinely valuable — roughly 40 curated scenarios built by hand while chasing production bugs, several of which existed nowhere else because the production data they came from had since been deleted under a retention policy.

The mechanism is worth stating precisely, because it is a general trap and not a Postgres quirk. A named data volume is bound to the resource, not to the image. When Aspire 13.4 moved the default Postgres image to 18.3, an AppHost that had never specified a tag silently changed major version — and Postgres refuses to start against a data directory written by an older major, by design, because the on-disk format is not compatible. So the volume was not corrupted and nothing was deleted; the engine simply could not read it, which is a much better position to be in than it felt like at 09:20 on Wednesday. The same release also moved the default RabbitMQ image to 4.3, which mattered less only because nobody kept anything in it.

// What we had: no tag, so the default image floats with the Aspire version.
var pg = builder.AddPostgres("pg").WithDataVolume("acme-pgdata");

// What we have now: an explicit tag, so the upgrade is a code change with a
// review, and the volume name carries the major version so a bump cannot
// silently point a new engine at an old data directory.
var pg = builder.AddPostgres("pg")
    .WithImageTag("18.3")
    .WithDataVolume("acme-pgdata-18")
    .WithLifetime(ContainerLifetime.Persistent);

// And the real fix: the dataset is code, not sediment. Seed scripts run on an
// empty database, so any developer can rebuild the whole thing in ~30 seconds.
var db = pg.AddDatabase("appdb");
builder.AddProject<Projects.Acme_SeedData>("seed")
    .WithReference(db).WaitFor(db);

The recovery took an afternoon and one important decision. The wrong move — which two people had already started — was to delete the volume and move on, because that is the fastest way back to a working machine and it destroys the evidence. I asked everyone to stop, and we recovered the data properly: start a container of the old major against a copy of the volume, dump, then restore into the new one. We got everything back from the two machines that still had an untouched volume. Three machines had already been reset and lost their local-only scenarios; those were gone, and I said so plainly in the write-up rather than rounding it to "we recovered the data".

The durable changes were three, and only one of them is about pinning. Pin the image tag, so an engine upgrade is a deliberate reviewed change. Put the major version in the volume name, so a future bump creates a fresh volume instead of failing against an old one. And the one that actually matters: treat local test data as code. Those 40 scenarios became a seed project, reviewed, versioned, and rebuildable in about thirty seconds, which means the volume is now disposable by design. That is the general lesson I take from the whole episode — the problem was never the upgrade, it was that irreplaceable data had accumulated somewhere nobody had decided was durable.

What I would do differently: read the breaking-changes list before merging, which would have cost ten minutes and turned a scare into a paragraph in the pull request. I would also have said the word "stop" faster. There were about twenty minutes where people were independently deleting volumes to unblock themselves, and each one of those was an irreversible act taken under mild time pressure without anyone deciding it was acceptable.

(d) Follow-up drill chain

Why does the volume survive the image change at all? Would deleting it not be safer?

Because the volume belongs to the resource, and its whole purpose is to outlive the container — that is what makes a restart fast and what makes a persistent development database possible. Deleting it on an image change would be a data-destroying default, which is far worse than a start-up failure; a refusal to start is loud, reversible, and gives you the chance to migrate. Postgres's behaviour here is the right one: the on-disk format is major-version-specific, so it checks the version file and stops rather than attempting to read a layout it does not understand. What I would criticise is not the mechanism but the silence upstream of it — an unpinned tag means a framework upgrade can change your engine major without anything in your diff saying so, and that is why pinning is the actual control.

Walk me through the recovery. Why not just restore from a backup?

There were no backups, because these were development machines and nobody had ever decided the data was durable — which is the real finding of the incident. The recovery was therefore a version migration: start a container of the old major mounted against a copy of the volume, take a logical dump, then restore into a fresh directory created by the new major. Copying the volume first is the non-obvious step and the one I would insist on, because it means a mistake during the dump is not a second data-loss event. The alternative in-place upgrade tooling is faster but operates on the original directory, and speed was not the constraint at that point. I also did it once myself, wrote it down as five commands, and then let everyone else run it, rather than nine people improvising in parallel.

At what scale does "treat test data as code" stop working?

When the dataset is large enough that rebuilding it costs minutes rather than seconds, or when it derives from production data you cannot commit. For volume, the answer is usually to split it: a small seed that every developer runs, plus a larger generated set produced by a script with a fixed random seed, so it is reproducible without being stored. For production-derived data, the seed project becomes an anonymisation pipeline rather than a set of scripts, and that is genuinely more work — but the alternative, which is real customer data sitting in developer volumes, is a much worse problem than the one in this story. The principle survives at every scale: the data has to be a product of something reviewed, not sediment that accumulated.

Three people lost data. How did you handle that in the write-up?

By naming it as lost, in the summary rather than buried in a timeline, and by not attributing it to the people who deleted their volumes. They did a reasonable thing with the information they had at 09:15 — the failure was that there was no instruction to hold, which is mine, because I saw the first message twenty minutes before I said anything decisive. I also asked the three of them what they had lost and wrote it into the seed project where it could be reconstructed, which turned an apology into a partial recovery for two of the scenarios. The general habit: the write-up should make it safe to have been the person who deleted the volume, otherwise the next person hides it and you find out a week later.

How do you stop an upgrade silently changing infrastructure again?

Pin everything that has a version, and make the pins visible in the diff. Every container resource in the AppHost now carries an explicit tag, so bumping the engine is a line someone reviews rather than a consequence of bumping a package; the same rule applies to base images in Dockerfiles. Then the process half: reading the breaking-changes list is a checklist item on any framework upgrade pull request, not an optional courtesy, and for a stateful resource the reviewer specifically asks what happens to existing volumes. Neither of those is exotic, and both were things we "obviously" should have been doing — which is usually the case with incidents of this shape. (d) Follow-up drill chain

Why is choosing a deployment target an architectural decision rather than a flag?

Because the target determines the runtime contract, and the application is written against that contract whether you admit it or not. Container Apps gives you scale-to-zero, revisions, built-in ingress and a managed identity story; Kubernetes gives you far more control and expects you to bring an operating model, ingress, and a GitOps discipline; Compose on a VM gives you neither and costs almost nothing to run. Those differ in how you do zero-downtime deploys, how health probes are interpreted, what happens to in-flight work when an instance is replaced, and how secrets arrive. Aspire makes the target explicit in the model, which is the honest design — it does not pretend the choice is invisible. The application-level consequence people underestimate is scale-to-zero: it is a wonderful cost property and it breaks any component that assumed it was always running.

Ephemeral per-PR environments sound expensive. How did you control that?

Three controls, and the tooling made two of them easy. Destruction is part of the pipeline rather than a cleanup job — the environment is torn down on merge or close, using the same model that created it, which is what aspire destroy exists for. Everything in a review environment is scaled to the minimum and uses scale-to-zero where the target supports it, because these environments are idle for the large majority of their life. And there is a hard time-to-live: anything older than 72 hours is destroyed regardless, because the failure mode is always an environment that outlived the pull request that made it. The cost landed at a level nobody argued about, but I would say the honest version in an interview: I did not know the number in advance, so I put a budget alert on the resource group before the first one was created.

You told a stakeholder their problem was something else. How did that land?

Badly for about ten minutes, then well, and the difference was that I brought the evidence rather than the opinion. I had taken two specific incidents where staging and production diverged and traced each to a secret that had been set by hand in one environment and not the other, which made it concrete that a deployment tool would have reproduced the same divergence faithfully. I also did not leave them empty-handed: I named the actual fix, sized it roughly, and offered to sponsor it in the following quarter. The thing I try to avoid is the diagnosis-and-walk-away, where you have demonstrated cleverness and transferred a problem back to someone with less context. At principal level the diagnosis is only half the job.

At what point does a week of investigation become procrastination?

When it stops changing what you would build. I timebox it explicitly and check daily against one question: has anything I learned today altered the shortlist? On day four the answer became no, and that is when I stopped, wrote the recommendation and started. The other guard is that investigation should produce artefacts, not just understanding — if at the end of a week I cannot hand someone a page that survives without me, I was thinking rather than working. I have got this wrong in the other direction too, most memorably by starting a build on day one of an ambiguous mandate and discovering in week five that the sponsor wanted something adjacent; the cost asymmetry is what makes a bounded week cheap insurance.

What would you have done if the sponsor had insisted on a specific target?

Asked what would happen if it turned out to be wrong, and made the answer cheap. I would still have said, once, in writing, that I thought the choice was premature and why — and then committed to it properly rather than half-implementing my own preference alongside. Visible disagreement followed by genuine commitment is the only version of this that works; the alternative teaches people that your agreement is unreliable.

(d) Follow-up drill chain

Does putting a Python service in a .NET-hosted app model not couple the teams more tightly?

It couples the development topology, not the runtime, and that distinction is the whole answer. Their service still builds, tests and deploys through their own pipeline; nothing in the AppHost is present at runtime. What the model adds is a declaration that our application, in development, consists of these things — and that declaration lives in our repository, so if they leave the topology, we change one file. The coupling that does appear is a version expectation: their service has to be startable in a way our model can describe, which in practice means a documented entry point and a port from an environment variable. That is a lightweight contract and arguably one they should have had anyway; it is also the thing I would renegotiate first if the relationship became strained.

Why did shared telemetry matter so much?

Because a cross-language latency question used to require two teams in a room correlating timestamps. That turns "recommendations feel slow on the product page" from a scheduling problem into a four-minute lookup, and it does it without either team adopting the other's tooling, because the protocol is the standard and the dashboard is just a consumer of it. It is also the part of the change that keeps paying: the trace view was what convinced their lead, and six months later it is what the data team uses to argue for their own performance work.

If the other team's service is genuinely heavy — a model server that wants a GPU, or something with a ten-minute warm-up — then putting it in everyone's local run is a bad trade, and the right answer is a shared instance referenced as an external service, or a lightweight stub with contract tests guarding the shape. I would also not do it if the two services deploy on wildly different cadences and the local declaration would be perpetually stale. The test I apply is whether the local copy is meaningfully the same thing as the deployed one; if it is not, you have added a maintenance burden and a false sense of coverage, which is worse than the honest gap you started with.

What did you actually give up by escalating in week two?

A little of the credit for how the change landed, and a bit of the goodwill I had spent two weeks building. Their manager handled it well — he asked their lead, got the date, and told me — but the lead now knew I had gone around him over something he had already answered, and I could feel that in the next conversation. The scope would move from one integration to the pattern. Example — replace with your own

The bet was reasonable at the time. We accepted that deliberately and compensated where it mattered: the integration suite runs against real provisioned resources in CI on the main branch, in a single shared environment that exists for the duration of the run. (d) Follow-up drill chain

Why not just use emulators everywhere and be done with it?

Because emulators are approximations, and the places they diverge are exactly the places that hurt in production. Consistency and concurrency semantics, throttling behaviour under load, indexing and query-cost characteristics, authentication paths, and any feature added to the service recently but not to the emulator — those are the usual gaps. The practical consequence is that a query which looks fine against a local emulator can be an expensive scan against the real service, because the emulator does not model the cost engine. So the position I hold is: emulators for the inner loop, where speed and cost dominate and you are iterating on your own logic; the real service in CI on anything that merges, where correctness dominates. The thing to avoid is having no layer at which you touch the real service before production, which is the failure this trade can slide into.

Per-developer resources gave isolation. What did sharing cost you?

Cross-talk and a coordination problem. One shared Service Bus namespace means two developers can consume each other's messages, which produces genuinely confusing bugs, so we scoped it: each developer gets their own queues and subscriptions, prefixed by identity, inside the shared namespace. That preserves the isolation that mattered while sharing the thing that was expensive, which is usually where the answer lives — share the container, not the contents. It is not free: the naming convention is a thing to remember, and orphaned entities accumulate, so there is a weekly cleanup job. I would still take it at fourteen engineers; at fifty I would want per-team namespaces rather than one, because the blast radius of a bad actor in a shared namespace grows with the number of people who can reach it.

At what scale does this problem change shape?

At the point where the dominant cost stops being idle development resources and becomes CI. Once every pull request provisions a real environment, you are paying per merge rather than per engineer, and the levers change completely: how long the environment lives, whether it is provisioned from scratch or reused, whether deployment state caching lets you skip work, and how aggressively you can parallelise without multiplying the bill. That is a nicer problem to have because it scales with output rather than headcount, but it is also the one where a small default — a resource tier, a retention period — multiplies by thousands of runs a month. I would want a cost-per-merge number tracked the same way a build-duration number is tracked, because otherwise it is only visible in aggregate.

How do you stop the bill drifting back up?

By making the cost visible to the people who cause it, at the moment they cause it. Tags per environment and per owner so the bill decomposes to a team rather than to a subscription; a budget alert with a threshold low enough to fire on a trend rather than on a disaster; and a monthly two-line report in the team channel, which is the part that actually changes behaviour because it is social rather than administrative. The structural control is the teardown being part of the pipeline rather than a scheduled cleanup: anything that requires someone to remember will drift. I also review the "why is this real rather than emulated?" decision quarterly, because emulators improve and the answer that was right last year sometimes is not.

Was the original decision wrong?

The decision was defensible; the missing artefact was a cost model. Choosing real resources for fidelity is a legitimate engineering position, and the person who made it was optimising for something that mattered. What was absent was anyone asking "what does this cost at fourteen engineers, and who will notice if it grows?" — and that question was mine to ask as much as theirs. I try not to tell this story as somebody making a bad call, partly because it is not true and partly because interviewers hear how you talk about colleagues. The systemic fix is that any pull request adding a cloud resource to the app model now answers two questions in the description: what does it cost per developer per month, and what destroys it.

The mechanism behind that is worth understanding, because it is a legitimate feature with a sharp edge. (d) Follow-up drill chain

Why is deployment state caching a sharp edge rather than just a feature?

Because it makes the deploy depend on where it was run from. Caching what was provisioned — subscription, resource identities, last-applied configuration — is what makes an incremental deploy fast instead of a full re-provision, and iterating without it would be painful. The consequence is that two operators with different cached state and different local parameter values can produce different outcomes from the same command, which is exactly the ambiguity that made 02:40 harder than it needed to be. The resolution is not to disable the caching but to make CI the only place with credentials, so there is one cache, one parameter source and one audit trail. Local deploys then target throwaway environments only, where divergence is harmless and actually useful.

Rollback is easy for stateless services. What about a schema change?

Then rollback stops being an option and you need the change to have been designed for it, which is a decision made weeks earlier rather than at 02:40. The discipline is expand-and-contract: add the new column or table, deploy code that writes both and reads the old, then switch reads, then remove the old shape in a later release — so at every point the previous version of the application can still run against the current schema. Our migrations ran as a one-shot job gated on completion before the API started, which is the right structure, but that only guarantees ordering, not reversibility. If I had been rolling back across a destructive migration that night, the honest answer is that I would have been fixing forward under pressure, which is precisely the situation the discipline exists to avoid.

At what scale does "roll back to the previous revision" stop working?

When a single service's version is no longer an independent variable. With a handful of services and versioned APIs it works well. Once you have many services deploying independently several times a day, rolling one back can put it on the wrong side of a contract another service has already adopted, so the safe unit becomes a compatible set rather than a service. Past that, teams move to progressive delivery — canary a small traffic share, watch error budgets, promote or abort automatically — so the rollback is a weight change that never reached most users. That is strictly better and considerably more machinery, and I would not build it for a system where a revision swap answers the question in two minutes.

How do you make sure the next on-call can do what you did?

By writing the runbook from the pager's point of view rather than the author's: the alert name, the two commands, the expected recovery signal, and what to do if it does not recover — short enough to execute at 02:40 with adrenaline. Then test it, which is the part people skip: we now do a rollback drill in production once a quarter during business hours, which has caught a stale command and a permissions gap that would both have cost minutes at night. The cultural half is that I stopped being the person who knows; if a recovery procedure lives in one head, the system's availability depends on that person's phone being charged. Writing it down is also how I found out our staging revision naming differed from production's, which would have been an unpleasant surprise.

You did not wake the engineer. Would you have escalated for a worse incident?

Immediately, and I think my threshold was wrong here rather than my principle. The rule I use now is that the cost of a two-minute call is always lower than the cost of twenty minutes of uncertainty during an active incident — and people are far less annoyed at being woken than leaders imagine, particularly when it is their change. What I would preserve is how I did it in later incidents: call with a specific question, not a summary. "Did your 22:15 deploy include a configuration change?" is answerable in ten seconds by someone half asleep; "can you get online, we have an incident" costs them twenty minutes and gets you the same information.

Example — replace with your own

The number that made the case was not a failure rate. It was this: over six weeks, 41% of pull requests had at least one re-run of CI, and in 38 of the 44 re-runs the second attempt passed with no code change. That is not a test suite, that is a coin toss with a fourteen-minute wait attached, and its real cost was cultural — people had learned that a red build means "press the button again", which means a genuine regression gets pressed through too.

Three distinct causes hid behind one symptom, and separating them was most of the work. The largest was time-based waiting: the tests started the application graph and then slept — a fixed delay tuned on someone's laptop — before making the first request. CI machines are slower and noisier than laptops, so the delay was sometimes too short. The fix is not a longer sleep; it is to wait on the actual signal. The testing package exposes the same notification service the AppHost uses internally, so a test can wait until a named resource reports healthy and then proceed, with a timeout that fails loudly rather than a delay that fails silently.

await app.StartAsync();
await Task.Delay(TimeSpan.FromSeconds(10));      // hope

// Deterministic: wait for the resource to actually be healthy, and fail loudly.

await app.StartAsync();

         .WaitForResourceHealthyAsync("api", cts.Token);

var client = app.CreateHttpClient("api");

The second cause was shared state between tests that ran in parallel: two tests using the same database and the same seeded order id, passing in isolation and failing together roughly one run in nine. The third was genuine resource contention on the CI agents: nine containers on a two-core agent, where things time out for no interesting reason. That one was solved with money, not cleverness, by moving the integration job to a larger agent class, and I want to name that honestly because engineers are reluctant to propose the boring expensive answer.

(d) Follow-up drill chain

Why is waiting on health better than a longer sleep? A sleep is simpler.

Because a sleep encodes an assumption about hardware you do not control, and it is wrong in both directions. Too short and you get a flake on a loaded agent; too long and every one of two hundred tests pays the worst case, which is how a suite becomes fourteen minutes. Waiting on the resource notification stream asks the orchestrator the actual question — is this resource healthy yet — so the test proceeds as soon as it truly can and fails with a clear message when a timeout expires, which turns a mysterious assertion failure into "the api resource never became healthy". The deeper reason is diagnostic: a sleep-based failure tells you nothing about what was wrong, and a health-wait failure tells you exactly which resource did not come up.

Per-test-class databases on one server — why not one server per test class?

Because the isolation people actually need is data isolation, and an engine per class buys very little of that at a very high cost. Starting a database server takes seconds and hundreds of megabytes; creating a database on a running server takes milliseconds. With twenty test classes that is the difference between a suite that runs in minutes and one that does not run at all. The cases where you genuinely need a separate engine are narrow and worth naming: testing server-level configuration, extensions, version behaviour, or anything where one test can affect the engine globally. For everything else, one server and many databases, created and dropped per class, is the right shape — and it maps neatly onto the app model, where the server is a resource and databases hang off it.

At what scale does this approach stop working?

When the container startup cost dominates the test cost, which happens sooner than people expect — at a few hundred integration tests you are spending more time starting the graph than asserting things. The moves then are to share one application instance across a whole class or assembly rather than per test, which trades isolation for speed and needs the tests to be written for it; to push coverage down the pyramid, since a lot of what people write as integration tests are really contract or unit tests wearing a costume; and to run the full graph suite on merge rather than on every push. I would resist the instinct to parallelise harder as the first move, because parallelism without data isolation is what created the second cause in this story.

A one-week quarantine deadline sounds harsh. What if nobody fixes it?

Then it is deleted, and that is the point — the deadline only works because the default action is deletion rather than indefinite quarantine. A quarantine list with no expiry becomes a graveyard of tests that nobody runs and nobody removes, which is the same as deleting them except that it costs maintenance and creates a false impression of coverage. In practice about a third get deleted, and I have not yet regretted one, because a test that nobody will spend a week fixing is a test nobody believes in. What I do insist on is that deletion is visible: it goes in the pull request with a one-line reason, so if the coverage was genuinely important someone can object at that moment rather than discovering the gap in an incident.

What did the reliability improvement not fix?

Coverage shape, which is a different problem and one I would flag rather than let the numbers imply it was solved. We had good coverage of the paths that were easy to test and thin coverage of the ones that mattered most — failure handling, retries, partial outages — and making the existing suite reliable does not change that distribution at all. It did make the gap addressable, because a trustworthy suite is the precondition for anyone bothering to add hard tests to it, and we spent the following quarter on fault-injection cases. But I would not claim the reliability work improved quality by itself; it improved the signal, and the signal is what lets you improve quality.

The temptation is to answer with the architecture, and that answer — correct, detailed, faintly condescending — would have lost the room.

What I said first was that the underlying instinct was right: he had noticed that our production environment was harder to reason about than our development one, and that is a defect worth a quarter of someone's time. Then the substance. The AppHost is a development-time orchestrator. At F5 it hands a resource graph to DCP, which starts processes and containers on one machine with a lifetime tied to that session. It has no scheduler, no replica management, no rolling update, no node failure handling, no traffic shifting, no secret management, no persistence of its own. It is not a small orchestrator that needs hardening; it is a different kind of thing, in the way a build script is not a small CI system. Running it on a server would give us a single machine with no redundancy, a dashboard exposing environment variables and telemetry with development-grade access control, and a process whose crash takes the entire estate with it.

Then the part that actually mattered, because "no" is not an answer at this level. What he wanted was the properties, not the mechanism: one description of the system, a single place to see what is running and why it is unhealthy, and a one-command path to a working environment. All three are achievable and two of them we shipped that quarter. The one description already existed — the app model — and the deployment work he was questioning was precisely what makes it generate the production topology instead of being a development-only artefact, which is the argument I should have made in the original proposal. The single place to look became a real observability stack, fed by the same OpenTelemetry the dashboard consumes, so the continuity he liked is genuine: the same traces, exported somewhere with authentication and retention. And the one-command environment became the per-pull-request environments from story 13, which gave him something better than what he was asking for.

Development                         Production
-----------                         ----------
AppHost + DCP                       Container Apps / Kubernetes / Compose
  starts processes & containers       schedules replicas, restarts, rolls out
  one machine, one session            many nodes, indefinite lifetime
  dashboard: local, open              your observability stack: authenticated
  generated passwords                 managed identity / secret store
  parallel start, health gating       probes, traffic shifting, autoscale

  The app model is what is shared. The AppHost is not deployed - it generates
  the artefacts that the production runtime consumes.

He accepted it in the meeting, and the reason was the first sentence rather than the diagram. Two things came out of it that I did not expect. He asked, fairly, why the dashboard could not simply be run against production telemetry — and the honest answer is that it can be run standalone, but doing so is a real service with real access to your telemetry that needs authentication and network placement decided deliberately, and that is a project rather than a shortcut. And I realised my original proposal had been written in mechanism rather than in properties, which is why it had looked like a quarter of tooling rather than a quarter of making production comprehensible. I rewrote it in a page and it was approved without discussion.

What I would do differently: notice earlier that a question like that is feedback on my communication, not a misunderstanding to correct. When a smart stakeholder proposes something that looks obviously wrong, the most likely explanation is that I have described the work in a way that made it look optional.

What the interviewer is really probing. Whether you can say no upward without being either deferential or condescending, and whether you serve the need behind the request. The strongest move here is opening by agreeing with the instinct, then separating properties from mechanism — and then delivering two of the three properties. At principal level they are also listening for the self-critical turn: the question happened because your proposal was written badly. The mistake candidates make is telling a pushback story where they were simply right and the stakeholder simply learned, which reads as either fictional or as a description of someone who does not get much pushback.

(c) Recall prompts

The public part is what makes it hard and what makes it a good story. What did you do to let them change position without losing face?

This reframe is the highest-value line in the archetype. Find one instance where you rewrote a proposal and it was suddenly uncontroversial.

Saying no and then delivering the underlying property is the pattern interviewers are listening for. Be specific about which parts you delivered and which you did not.

If the answer is "in several ways", that gap is a genuine finding and a good thing to have acted on rather than tolerated.

(d) Follow-up drill chain

Be precise: what exactly is missing from the AppHost for production use?

Everything a scheduler does. There is no replica management or horizontal scaling, no rolling update or traffic shifting, no node-failure handling because there is only one machine, no autoscaling, no secret management beyond development conveniences like generated passwords and user secrets, and no persistence of orchestration state — the graph exists for the session. Its restart behaviour is designed for a developer watching a terminal, not for unattended recovery at 3am. It also intentionally starts things in parallel and gates on health for developer speed, which is not the same as a controlled rollout with a failure budget. The framing I use is that it is not an immature orchestrator on a path to becoming one; it is a development-time tool whose output is artefacts for a real runtime.

What about the dashboard? He liked the dashboard.

The dashboard can genuinely run standalone against any OTLP source rather than only inside an AppHost run, so the idea is not absurd — but promoting it out of the inner loop turns it into a service with real properties to decide. It shows environment details and telemetry, so it needs authentication, network placement and a decision about who can see what; its OTLP receiver accepts what can reach it, which is right on loopback and wrong on a shared network; and it holds telemetry in memory rather than being a retention system, so it answers "what is happening now" and not "what happened last Tuesday". That last property is the one that settles it for production. What we did instead preserves what he actually liked: the same OpenTelemetry data, exported to a backend with authentication and history, so the local and deployed experiences are continuous rather than identical.

Is there any environment where running the AppHost is legitimate?

Yes, and being able to say so is what keeps the "no" credible. A demo environment on a single machine, a workshop, an air-gapped evaluation, a personal sandbox — anywhere a session-scoped, single-machine, non-redundant, unauthenticated environment is genuinely acceptable, running the AppHost is a fast and legitimate answer. I have done it for a customer proof of concept that lived for two days. The line is anything with users, uptime expectations, or data worth protecting. I would also warn about the specific failure mode: those environments have a habit of becoming permanent because they work, so if you stand one up, put an expiry date on it and tell people what it is not.

How did you avoid the director feeling corrected in front of his peers?

By making the first sentence about what he was right about, and meaning it. He had spotted a real asymmetry — our development environment was more comprehensible than our production one — and that framing let the rest be an explanation of how we would fix it rather than a rebuttal. I also gave him the credit for the reframing afterwards, in writing, because the proposal genuinely was better for the question having been asked. The tactical detail I would pass on is to answer in operational terms rather than architectural ones: "there is no rolling update and one crash takes everything down" is a sentence a director can evaluate, whereas "it is a development-time orchestration abstraction" asks them to take your word for it, which is what makes people dig in.

What if he had insisted?

I would have asked for the decision to be recorded with its risks, and then complied with anything short of a safety issue. Concretely, I would have written a short note listing what we would be accepting — single point of failure, no rolling updates, telemetry access control — asked him to acknowledge it, and proposed a bounded version, perhaps the internal-only service, so the blast radius was known. That is not passive aggression; it is how you keep disagreement from becoming either capitulation or obstruction, and it protects him as much as me. The place I would not have gone along is anything exposing customer data through a development-grade access path, and I would have said that as a hard line rather than as a preference, because a principal engineer who never has a hard line does not really have any.

21The big behavioural Q&A

cross-cutting 21 prompts mid → principal

These are the prompts that are not tied to one story — the ones that open a loop, close it, or arrive when an interviewer wants to see how you generalise. Each answer names which of the twenty stories to deploy and what the interviewer is listening for. Do not memorise the wording; memorise the mapping, so that under pressure you are choosing a story rather than inventing one. If two prompts map to the same story, use it once and go elsewhere: an interviewer who hears the same migration three times learns one thing about you.

Failure & ownership

Tell me about a time you were responsible for an outage.

Deploy: story 03 (the health check that cycled the fleet), or story 12 (the volume) if you want the version where your own team's work-around made it worse. They want: a clean separation of detection, mitigation and diagnosis, an impact number, and ownership that neither slides into self-flagellation nor relocates the fault to a vendor. Say what you decided, not only what happened — the strongest beat in 03 is that you repointed the probe before you understood the cause. Close on the systemic change and, if it exists, on the game day that later proved it worked.

What is the biggest mistake you have made?

Deploy: story 15 (the publishing bet you proposed and then cancelled) at staff or principal, story 12 (the twenty minutes before you said "stop") at senior. They want: proportion. Too small reads as evasion; catastrophic and uncontained reads as risk. The structure that works: the decision, the reasoning that was wrong, the moment you knew, what you did, and the structural change — here, kill criteria in every proposal and validating the organisational assumption first. Avoid the disguised strength ("I care too much about quality"), which interviewers hear as a refusal to answer.

Tell me about something you should have caught earlier.

Deploy: story 07 (an AppHost that grew to 31 resources over eighteen months while you watched the trajectory), or story 16 (a cost problem that finance found before engineering did). They want: evidence you notice your own blind spots rather than rationalising them. The strongest version names the duration — a year, four months — because the discomfort of that number is what makes the reflection credible, and it sets up a systemic fix rather than a promise to pay more attention.

How do you run a postmortem?

Deploy: the mechanics from story 03, the blame handling from story 12 (three people deleted volumes and the write-up did not name them). They want: blameless in substance rather than as a slogan — describe the change, not the author; the system that permitted it, not the person who tripped it. Go first if you were involved: in 03 you approved the pull request that caused it, in forty seconds, and saying that in the timeline is what makes everyone else's honesty possible. Name one action item that shipped and one you declined because it would only have prevented that exact incident.

Conflict & influence

Tell me about a disagreement with a colleague.

Deploy: story 05 (service discovery versus URLs in configuration). They want: their argument stated fairly and strongly — his was good, and he had been burned by a mesh — then a resolution mechanism rather than a victory. State the criterion that settled it (edit sites per change, and the outage the missed one caused), because a criterion generalises and a preference does not. Include what you conceded, and never present a disagreement you won entirely.

How do you influence a team you have no authority over?

Deploy: story 14 (the Python team) at mid or senior, story 02 (the platform team and the ownership boundary) at staff or principal. They want: lowering the cost of yes — a working branch and a screenshot rather than a request, and a distinction between the objection you can answer and the one that is not yours to touch. Owning the unnecessary escalation in 14 is worth more than a story where you were diplomatic throughout.

Tell me about a time you had to say no to someone senior.

Deploy: story 20 (running the AppHost in production), with story 11 as the inverse — saying yes to a deadline while extracting the part that mattered. They want: serving the need behind the request rather than defending a principle. The content is agreeing with the instinct first, translating mechanism into properties, and delivering two of the three properties that quarter. Say the self-critical part out loud: the question happened because your proposal was written in mechanism.

Describe delivering bad news upward.

Deploy: story 15 (recommending your own project be cancelled) or story 04 (revising a two-day estimate to nine on day three). They want: that you brought a decision rather than a confession — options, costs, a recommendation, and a fallback with a date on it. Say how quickly you escalated relative to when you knew, because the gap between those two is the actual question, and say who you told first.

Leadership, mentoring & delegation

Tell me about someone you levelled up.

Deploy: story 10 (handing over ownership of the shared defaults after the eleventh identical question). They want: the difference between teaching and transferring ownership, and evidence the person went beyond your plan — the analyser was her idea, not yours. Name the success measure you gave her, and how you knew the transfer was real: the remaining questions went to her, not to you.

How do you decide what to delegate?

Deploy: story 10 for the mechanism, story 17 for the counter-example — you deliberately did the first AppHost migration yourself because a working example beats a plan when you are asking a sceptical team for a decision. They want: a rule rather than a vibe. Mine is that a question I can answer without thinking is a question that should not be reaching me; a task where my context is genuinely load-bearing is one to do and then write down.

How do you raise the technical bar across a team?

Deploy: story 03 (a review rule and a build-time check on shared defaults) and story 10 (making the mistake impossible instead of explaining it). They want: leverage — defaults, diagnostics and analysers rather than documents and reminders. The honest counterweight is worth adding: guards cost something, and every estate has three abandoned ones protecting against a 2021 incident, so you ask for the occurrence count before you build one.

Ambiguity & prioritisation

Tell me about working with unclear requirements.

Deploy: story 13 ("deploy with Aspire" meaning three different things to three people). They want: inference from what hurts, not a request for clarification — real ambiguity is when the people asking do not know either. The strongest beat is the requirement you concluded the tool could not fix. Add the delivery lesson: publish the competing interpretations on day two, because thinking is invisible and a one-page comparison is not.

How do you prioritise when everything is urgent?

Deploy: story 11 (splitting an adoption proposal by pre-launch risk reduction). They want: the axis, stated explicitly. Effort, phase numbering and personal preference are weak axes; risk reduction against a fixed date is a strong one. Say that half your own proposal was appetite and that you separated it yourself — and that the deferred half was written down with a cost, so it stayed a decision rather than becoming a silent drop.

Tell me about a time you had to cut scope.

Deploy: story 11, or story 15 if you want the version where the thing you cut was the whole project. They want: that the smaller version had standalone value — the test is whether you would have been content if nothing followed it. Avoid "phase one", which usually means an incomplete thing with a promise attached.

How do you estimate?

Deploy: story 04 (nine days against a two-day estimate) and story 15 (six weeks costed with no allowance for preview-feature friction). They want: a calibration story with a named bias. Mine is that I estimate migrations by the number of renames the compiler will find rather than the number of behavioural changes it will not, and that anything depending on a preview feature needs roughly a third more because you spend time distinguishing your bugs from theirs. Then the communication half: revise on day three, not day eight.

Platform judgment & adoption

Tell me about introducing a technology into an organisation.

Deploy: story 17. They want: that you knew the other party's first question was support liability, not features, and that you could answer it with a demonstration rather than an assertion. The two details that carry the answer are pre-agreed failure criteria and a stated exit cost. Add the restraint: you did not centralise at the moment of enthusiasm, and two teams still have not adopted it.

How do you decide whether to adopt a preview or brand-new feature?

Deploy: story 15 (a preview Kubernetes publishing path) against story 13 (shipping on a stable deployment target). They want: three questions with real answers — can we ship without it, is the surface we depend on small enough that a break is a day rather than a rewrite, and does someone credible say what stable will require. Then the version discipline this topic rewards: only the latest Aspire release is supported, each version ends support when the next ships, so "we will upgrade later" is a decision to run unsupported.

How do you think about build-versus-buy, or framework-versus-glue?

Deploy: story 09 (600 lines of hand-written glue replaced by a typed model) and story 02 (declining to let one tool own everything). They want: a criterion. Mine is duplication of truth: when the same fact is written in three places by hand, adopt the thing that generates it; when a tool wants to own something whose lifecycle belongs to someone else, reference rather than adopt. Name what the old thing was better at — Compose runs anywhere with no SDK — because a candidate who cannot is not evaluating, they are advocating.

Values & motivation

What kind of work do you want to do next?

They want: a direction consistent with the stories you have just told, and an honest read of the role. If your stories are leverage — 07, 10, 17, 19 — say you want problems whose fix is a default rather than an instance. If they are incident-shaped, say so. The failure mode is describing an ambition the role cannot satisfy, which tells the interviewer you will leave within a year; if the role genuinely is narrower than you want, say what would make it interesting anyway rather than pretending.

What do you do when you disagree with a decision that has already been made?

Deploy: story 13 (what you would have done had the sponsor insisted on a target) and story 20 (recording the risks and complying). They want: disagree-and-commit with an actual mechanism — say it once in writing, ask for the risk to be recorded, then implement it properly rather than half-implementing your own preference alongside. Naming the hard line you would not cross, and how rarely you use it, is what makes the commitment believable.

Do you have any questions for us?

Deploy: questions your own stories make natural, which demonstrates depth without repeating yourself. How long does it take a new engineer to run the whole system locally? What is your CI re-run rate? Who decides what goes into the shared service defaults, and how is that reviewed? What runs in a review environment, and what destroys it? When you deploy, where does that run from? They want: evidence you evaluate them with the same instruments you build — and their answers will tell you more about the engineering culture than any of their questions told them about you.

22Night-before cheat sheet

delivery read once

Ten sentences to read the night before and once more in the car park. They are about delivery, not content — by this point the content is either in your head or it is not, and delivery is where prepared candidates still lose.

  1. Open with the situation in one sentence, and put a number in it. "Eleven minutes of total outage caused by a cache being slow, not down." The interviewer now knows the shape of the story and will let you take the next two minutes uninterrupted; a rambling three-sentence setup invites them to redirect you before you reach the point.
  2. Say what you decided, not only what happened. Aspire stories drift into tooling narration — then we added this, then the dashboard showed that — and the interviewer is assessing judgment. Every ninety seconds, return to a decision you made and the alternative you rejected.
  3. Keep the development-time and runtime halves separate, out loud. It is the single most important distinction in this topic and the one candidates blur. "The AppHost orchestrates my machine; what reaches production is artefacts plus two libraries" is a sentence that instantly separates people who have run this in anger from people who have watched a demo.
  4. Quantify the result, and prefer a rate over an absolute. Minutes of team time per week, tickets per week, re-runs per pull request, cost per developer per month. Absolute numbers invite "compared with what?"; rates carry their own denominator and hold up when the interviewer probes.
  5. Separate "I" from "we" deliberately and out loud. Say "the team migrated eleven services; my part was the sequencing and the publishing decision". Interviewers are trained to notice a candidate who says "I" about work that obviously took four people, and it costs you more than modesty ever will.
  6. Own the failure inside the win. Every story here has one — a forty-second review that approved an outage, twenty minutes before saying "stop", an escalation over your own bad memory, a folklore diagnosis worth four seconds. Volunteer it before you are asked; the interviewer will find it anyway, and finding it themselves converts a strength into a doubt.
  7. Tie the technical decision back to a real trade-off. Persistent containers buy speed and sell reproducibility. Emulators buy cost and sell fidelity. Generated infrastructure buys consistency and sells ownership. One sentence of "it depends, because…" does more than a paragraph of mechanism.
  8. Be current, and be precise about versions. Aspire 13.5 shipped on 18 August 2026 and needs the .NET 10 SDK; only the latest release is supported, so each version ends support when the next ships. Naming one recent change you have actually dealt with — the Postgres default image moving to 18.3 in 13.4, or service-discovery variables keyed by scheme since 13.2 — does more for your credibility than any amount of general enthusiasm.
  9. Answer a drill-down in three to six sentences, then stop. The follow-up chains in this page are calibrated to that length. Silence afterwards is the interviewer's turn, not a gap you are obliged to fill, and continuing to talk is how a correct answer becomes an uncertain one.
  10. Close each story on the systemic change, not the fix. The analyser instead of the explanation, the seed project instead of the recovered volume, the pinned tag instead of the apology, the quarantine policy instead of the fixed test. Fixing the incident is the mid-level answer; making that class of incident impossible — or merely visible — is what they are hiring for.
