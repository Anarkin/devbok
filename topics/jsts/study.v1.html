01 Values, types, coercion

Everything in JavaScript is either a primitive or an object, and that single split explains most of the language's surprising behaviour. There are seven primitives — undefined, null, boolean, number, string, symbol, bigint — and they are immutable values compared by content. Everything else is an object compared by reference. TypeScript sits directly on top of this: its primitive types are exactly those seven, and every type it invents (interfaces, unions, generics) is erased at runtime, so the runtime you reason about is always the JavaScript one underneath.

The mental model that pays off: JavaScript never refuses a value, it converts it. Almost every operator is defined in terms of abstract operations — ToPrimitive, ToNumber, ToString, ToBoolean — and the specification's "surprises" are just those operations composed. ToPrimitive(obj, hint) calls obj[Symbol.toPrimitive] if present, otherwise tries valueOf then toString for the "number" hint and the reverse order for "string". That is why [] + {} is "[object Object]" (both sides become strings because + falls back to string concatenation when either primitive is a string) and why new Date() - 0 is a timestamp while new Date() + 0 is a sentence. You do not memorise the outcomes; you evaluate the two-step algorithm.

Numbers are IEEE-754 doubles — one type for integers and floats. That gives you exact integers only up to Number.MAX_SAFE_INTEGER (253−1 = 9007199254740991), the reason every serious API sends 64-bit ids as strings. BigInt (ES2020) covers arbitrary integers but does not mix with Number in arithmetic, deliberately: mixing would silently lose precision. Two live 2026 details worth naming in an interview: Math.sumPrecise reached Stage 4 for ES2026 and gives a correctly-rounded sum of an iterable of numbers, which is the answer to "how do I add a column of floats without drift" that used to require Kahan summation by hand; and Error.isError, also ES2026, is a brand check that works across realms and iframes where instanceof Error quietly fails.

Strings are sequences of UTF-16 code units, not characters. "😀".length is 2. Iterating with for…of or spreading gives code points, which is better but still not user-perceived characters: Intl.Segmenter (baseline in every engine since 2024) is the only correct way to count or slice grapheme clusters. This matters at lead level because it is the root cause of a whole class of production bugs — truncated names, broken emoji in SMS length counters, off-by-one cursor positions.

Dates are the other historic wound, and 2026 is the year it closed. Temporal reached Stage 4 in March 2026 (tracked for the ES2027 edition) and is already shipping by default in Firefox 139, Chrome 144 and Edge 144, and enabled by default in Node.js 26 (May 2026, V8 14.6). Safari stable is still behind, so browser code that must support it still ships the polyfill. Temporal gives you immutable types with explicit calendars and time zones — Temporal.Instant, Temporal.ZonedDateTime, Temporal.PlainDate, Temporal.Duration — instead of one mutable Date that silently means "milliseconds since epoch, rendered in whatever zone the machine happens to be in". TypeScript 6.0 shipped the built-in lib types for Temporal, so you get it from "target": "es2025" upwards without a @types package.

Where TypeScript adds and where it lies

TypeScript's contribution here is literal types and narrowing. const x = "a" has type "a", not string; let x = "a" widens to string. as const freezes an entire object literal into its most specific readonly form, which is the idiomatic way to build a lookup table whose keys you then want as a union. What TypeScript does not do is change any runtime rule: 1 + "1" is still "11", and TypeScript merely refuses to compile it. And it will happily lie when you tell it to — as, non-null !, and any un-validated JSON boundary are all places where the static type and the runtime value diverge (unit 10 is entirely about that seam).

Try it

1. Break float summation on purpose. Generate 100 000 random values in [0, 1), sum them with reduce, then with Math.sumPrecise, and print the difference. Then sum the same array sorted ascending and sorted descending with reduce and compare again.

Interview Q&A — 01

Why is typeof null "object", and how do you actually distinguish the empty-ish values?

It is a bug from the original 1995 implementation: values were tagged with a low bit pattern and the null pointer shared the object tag. It was proposed for a fix and rejected because too much code depends on it. In practice you distinguish deliberately: x === null for null, x === undefined or typeof x === "undefined" for undefined, and x == null when you genuinely mean "either". At lead level the follow-on point is that null and undefined should carry different meanings in your own APIs — undefined for "absent/not supplied", null for "explicitly empty" — and TypeScript's exactOptionalPropertyTypes is what stops the two from blurring in optional fields.

Walk me through what the engine does for [] + {} and {} + [].

+ evaluates ToPrimitive on both operands with the default hint. For [] that is valueOf (returns the array itself, not a primitive), then toString giving ""; for {} it is "[object Object]". Since one side is a string, + concatenates, so you get "[object Object]". {} + [] in a statement position is different only because the leading {} parses as an empty block, so what is evaluated is unary +[], which is 0 — that is a parsing question, not a coercion question. The reason to know this is not the puzzle; it is that + is the one operator whose behaviour depends on the runtime types of both sides, which is why concatenating with + in a template-heavy codebase is a lint rule for us.

When would you ever use == in code you would approve?

Exactly one pattern: if (value == null) as shorthand for null-or-undefined, and even that is a team convention worth writing down rather than assuming. Everything else — "" == 0, [] == false — is a source of bugs whose only benefit is brevity. The modern alternative for the common cases is the nullish operators: ?? for defaults and ?. for access, both of which trigger on exactly null and undefined and not on 0 or "", which is the bug || defaults produce. In review I flag x || defaultValue on anything numeric or string-shaped far more often than I flag ==.

Number.MAX_SAFE_INTEGER — why does it matter for API design?

Doubles have 53 bits of mantissa, so integers above 253−1 lose precision silently: 9007199254740993 round-trips as 9007199254740992. Any backend that emits 64-bit identifiers (Twitter snowflakes, Postgres bigint keys, .NET long) will corrupt them the moment they pass through JSON.parse. The fix is to serialise those ids as strings at the API boundary, and it must be a contract decision, not a client workaround, because JSON.parse has already lost the digits before your code sees them. If you cannot change the contract, ES2026's JSON.parse source-text access proposal lets a reviver read the original text of the number and build a BigInt from it — that is the standards-track answer to a problem people used to solve with regex pre-processing.

What is the difference between Object.is, === and SameValueZero, and where does each show up?

=== (strict equality) says NaN !== NaN and 0 === -0. Object.is (SameValue) says NaN is itself and 0 is not -0. SameValueZero is Object.is except it merges the zeros, and it is what Map keys, Set members, Array.prototype.includes and Object.groupBy use — which is why [NaN].includes(NaN) is true while [NaN].indexOf(NaN) is -1. React's useMemo and Object.is-based bail-outs are the everyday place this matters: a component re-renders because -0 and 0, or two structurally identical objects, are not the same value.

Give me a concrete reason to reach for BigInt, and one reason not to.

Reach for it when you need exact integer arithmetic beyond 253: cryptographic maths, financial cent totals that exceed the safe range, snowflake-id arithmetic, or checksum algorithms. Do not reach for it as a general "safer number": it cannot be mixed with Number without an explicit conversion (by design, so precision loss is visible), it is markedly slower — allocation per operation rather than a register value — it does not serialise through JSON.stringify without a custom replacer, and Math.* functions do not accept it. For money the boring answer is still better: integers of minor units, or a decimal library, with the unit encoded in the type.

Why is "😀".length 2, and how do you correctly truncate a user-facing string?

JavaScript strings are UTF-16 code unit sequences, and any code point above U+FFFF is stored as a surrogate pair, so .length counts storage units, not characters. Spreading or for…of iterates code points, which fixes surrogate pairs but not combining marks or ZWJ sequences — a family emoji is still four code points. The correct truncation uses Intl.Segmenter with granularity: "grapheme", takes N segments, and joins them; anything else can cut a string in half and produce a replacement character. I treat this as a boundary concern: one truncateGraphemes helper, unit-tested against emoji and Devanagari, rather than slice scattered through the view layer.

What changed about dates in the last year, and would you migrate a large codebase to Temporal today?

Temporal reached Stage 4 in March 2026 and is on by default in Node.js 26, Firefox 139 and Chrome 144; Safari stable has not shipped it as of mid-2026, and the tc39 tracker slots it into the ES2027 edition. It replaces one mutable, zone-ambiguous Date with immutable types that force you to say what you mean: Instant for a point in time, ZonedDateTime when the zone is part of the meaning, PlainDate for a birthday that has no zone. For a Node-only service on 26 I would adopt it now at the boundaries and let it spread inward. For a browser app I would keep the polyfill until Safari ships, and I would not do a big-bang migration either way: I would introduce it behind our own date module so the swap is one file, because that abstraction is also what lets you delete Moment or date-fns incrementally.

Explain as const and when it is the right tool.

A const assertion tells the compiler to infer the narrowest possible type and mark everything readonly: array literals become readonly tuples, object properties keep their literal types instead of widening to string or number. The payoff is deriving types from values instead of duplicating them — keyof typeof CONFIG gives you a union of the real keys, so adding a key to the object automatically extends the union and every exhaustive switch starts failing to compile until it is handled. That is the single highest-leverage TypeScript idiom I push in review: one source of truth, expressed as a value, with the types derived. The limits: it is compile-time only — nothing is frozen at runtime unless you also call Object.freeze — and it does not survive a JSON.parse round trip.

How do you decide between unknown, any and never?

unknown is the honest top type: anything is assignable to it, and nothing can be done with it until you narrow, so it forces a check at exactly the place where a check belongs — parsed JSON, catch clauses (which are unknown under useUnknownInCatchVariables, part of strict and therefore on by default since TypeScript 6.0), and third-party boundaries. any switches the checker off and, worse, spreads: every expression derived from an any is any, so one un-typed helper can silently un-type a whole call chain — that is why I treat noImplicitAny plus a lint rule against explicit any as non-negotiable and allow it only with a comment naming the reason. never is the bottom type: no value has it, so it is the return type of a function that always throws, the type of an impossible narrowing, and the tool for exhaustiveness checks — assigning the fall-through case to never makes an unhandled union member a compile error.

02 Objects, prototypes, classes

An object is a bag of property descriptors plus a link to another object. That link — the internal [[Prototype]], readable as Object.getPrototypeOf(o) — is the whole inheritance model. Property lookup walks the chain until it finds a key or hits null; assignment does not walk it, it writes an own property on the receiver (unless a setter higher up intercepts). Keep those two asymmetric rules in your head and prototype behaviour stops being mysterious: shared state on a prototype looks like it works until the first write, at which point every instance silently forks its own copy.

The confusion that trips people up is .prototype versus [[Prototype]]. A function's .prototype property is not that function's prototype — it is the object that will become the [[Prototype]] of instances the function constructs. fn.prototype is a plan; Object.getPrototypeOf(instance) is the wiring. instanceof is defined as "walk the left operand's prototype chain looking for the right operand's .prototype object", which is exactly why it fails across realms — two iframes have two distinct Array.prototype objects — and why Array.isArray exists, and why ES2026 added Error.isError.

class (ES2015) is sugar over this, but not only sugar: classes are strict-mode by default, their methods are non-enumerable, they cannot be called without new, and the body has a temporal dead zone. ES2022 completed the picture with three additions that are now universally available: private fields (#count, genuinely inaccessible from outside — a syntax error, not a convention), static blocks (static { … } for initialisation that needs statements), and ergonomic brand checks (#x in obj, the correct way to write an isFoo guard for a class you own).

class Cache<V> {
  #store = new Map<string, V>();          // private: not reachable, not enumerable, not spreadable
  static #instances = 0;
  static { Cache.#instances = 0; }         // ES2022 static block

  constructor(private readonly ttlMs: number) {}   // TS parameter property - see the trap below

  // ES2026 "Upsert": getOrInsertComputed replaces the has/get/set dance.
  ensure(key: string, make: () => V): V {
    return this.#store.getOrInsertComputed(key, make);
  }

  // Brand check that works across realms and survives minification.
  static is(x: unknown): x is Cache<unknown> {
    return typeof x === "object" && x !== null && #store in x;
  }
}

Class fields have define semantics, not set semantics, and this is the single most consequential detail in the modern class. class A { x = 1 } performs Object.defineProperty(this, "x", …), which means it shadows an inherited accessor rather than calling it. TypeScript's useDefineForClassFields switched to true whenever target is ES2022 or later — and since TypeScript 6.0 defaults target to es2025, it is on by default in any new project. The visible symptom is a subclass field quietly clobbering a base-class getter, or a framework that relied on set-semantics decorators breaking on upgrade. Knowing this is a reliable signal that you have shipped a real TypeScript upgrade rather than read about one.

Objects as data: the modern toolkit

For plain data, the last few ECMAScript editions replaced most of Lodash. Object.entries/fromEntries for transforms, Object.groupBy and Map.groupBy (ES2024) for bucketing, structuredClone for a real deep clone that handles Map, Set, Date, typed arrays and cycles (but not functions, DOM nodes or class identity — it returns plain objects), and the ES2023 non-mutating array quartet toSorted/toReversed/toSpliced/with. The Records & Tuples proposal that promised deeply immutable primitives was withdrawn in 2025; the practical answer to immutability today is readonly types plus discipline, or a library like Immer, not a language feature that is coming.

// Deep copy without JSON round-tripping (which loses Date, Map, undefined, and cycles).
const snapshot = structuredClone(state);

// ES2024 grouping, replacing the reduce-into-an-object pattern.
const byStatus = Object.groupBy(orders, (o) => o.status);   // { open: [...], closed: [...] }
const byUser   = Map.groupBy(orders, (o) => o.user);        // keys can be objects

// Ordering rule people forget: integer-like keys sort numerically and come FIRST.
Object.keys({ b: 1, 2: 1, a: 1, 1: 1 });   // ["1", "2", "b", "a"]
Interview trap

Arrow-function class fields are not free. Candidates reach for handleClick = () => {} to "fix this", but that creates a new closure per instance, puts an enumerable own property on every object (so it shows up in spreads and JSON.stringify), and makes the method unpatchable from the prototype — which breaks spying in tests and monkey-patching in instrumentation. The senior answer: bind at the call site (onClick={() => obj.method()}) or in the constructor when you need a stable identity, and keep methods on the prototype. The second half of the trap is Object.freeze: it is shallow, it silently does nothing to nested objects, and in sloppy mode a write to a frozen property fails silently — one more reason everything is a module (modules are always strict) so it throws.

Try it

1. Prove define-vs-set semantics. Write a base class with get name() and set name(v) that logs, then a subclass with name = "x" as a field. Run it with useDefineForClassFields: true and then false and compare whether the setter fires.

2. Break a prototype on purpose. Create function Counter() {} with Counter.prototype.hits = 0, make two instances, increment a.hits++, then read b.hits.

Expected outcome

(1) With true (the modern default) the setter never runs: the field is defined as an own data property that shadows the accessor, and super.name is the only way to reach it. With false (legacy emit) the setter logs. This is the exact break teams hit upgrading past TypeScript 5.x with an ES2022+ target, and it is why the declare modifier exists.

(2) b.hits is still 0. a.hits++ read 0 through the chain and then wrote an own property on a. Shared mutable state on a prototype works exactly until the first write, which is why prototypes hold behaviour and instances hold state.

Interview Q&A — 02

Explain the difference between __proto__, Object.getPrototypeOf and a function's .prototype.

Object.getPrototypeOf(o) reads the internal [[Prototype]] link that lookup follows. __proto__ is a legacy accessor on Object.prototype that does the same thing; it is standardised only in Annex B for web compatibility and you should not use it — it is also the vector for prototype-pollution attacks, which is why Object.create(null) is the right base for a user-controlled dictionary. fn.prototype is an ordinary property on constructor functions holding the object that new fn() will link instances to. In one sentence: .prototype is what a constructor gives out, [[Prototype]] is what an object has.

What do private # fields give you that TypeScript's private does not?

TypeScript's private is a compile-time visibility annotation and nothing more — it is erased, the property is a normal enumerable own property at runtime, and any JavaScript caller or obj["secret"] reaches it. # fields are enforced by the engine: access outside the class body is a syntax error, the field is invisible to Object.keys, spreads, JSON.stringify and structuredClone, and #x in obj is a brand check that survives minification and works across realms. Use # when the boundary is real — anything shipped as a library, or state that must not be observed — and TypeScript private when it is only a team-facing hint. The cost of # is that it is genuinely unreachable, which occasionally makes testing and serialisation harder; that is the trade-off to name.

How does super actually resolve, and why can it not be a dynamic lookup?

Methods that use super capture a [[HomeObject]] — the object they were defined on — at definition time. super.m() means "look up m on Object.getPrototypeOf([[HomeObject]]), then call it with the current this". It is lexical, not dynamic, so ripping a method off a class and attaching it to another object breaks super even though this still works. That is also why super is unavailable in an object literal's ordinary function property but works in its shorthand method — only shorthand methods get a home object. In practice this is the reason mixin helpers must return classes rather than copying methods around.

When is instanceof the wrong check?

Whenever values cross a realm — iframes, vm contexts, worker messages, some test-runner sandboxes — because each realm has its own intrinsics, so an array from an iframe is not instanceof your Array. It is also wrong when the shape matters more than the lineage (structural, duck-typed data), and it is fragile across duplicated copies of a library in a bundle, which is why a node_modules version skew shows up as "this error isn't my error". Use the purpose-built brand checks — Array.isArray, Error.isError (ES2026), #field in obj for your own classes — or a discriminated union with an explicit kind property, which is what I prefer for data crossing a wire.

What is useDefineForClassFields and why did it break code?

It selects between the standard define semantics for class fields (Object.defineProperty) and TypeScript's original set semantics (plain assignment). Define semantics is what the ECMAScript standard specifies, and TypeScript switched the default to true for targets ES2022 and above; since TypeScript 6.0 defaults target to es2025, new projects get it silently. It breaks two patterns: a subclass field that was supposed to trigger an inherited setter now shadows it, and a declared-but-uninitialised field (foo!: string) now defines the property as undefined, overwriting a value a base constructor or a decorator had already set. The fixes are declare foo: string for the second case and an explicit accessor override for the first. I would raise this proactively in any upgrade plan, because the failures are runtime, not compile-time.

How do you get deep immutability in JavaScript today?

You do not get it from the language. Object.freeze is shallow and only prevents writes on that one object; the Records & Tuples proposal that would have given deeply immutable primitives was withdrawn in 2025. So the practical stack is: readonly and ReadonlyArray in the type system to make mutation a compile error, the ES2023 non-mutating array methods (toSorted, with, toSpliced) so the ergonomic path is also the immutable one, structuredClone when you genuinely need a detached copy, and a library like Immer if you want structural sharing with mutable-looking code. At lead level I would add: enforce it at the boundary of a module rather than everywhere, because deep-freezing large state in hot paths is a measurable cost.

What is prototype pollution and how do you prevent it?

It is an attack where user-controlled input reaches a recursive merge or a dynamic property assignment with the key __proto__ (or constructor.prototype), writing a property onto Object.prototype that every object in the process then appears to have. The classic impact is authorisation bypass — if (user.isAdmin) becomes true for everyone — or gadget chains that reach code execution. Prevention: never merge untrusted data with a naive recursive merge; reject or skip __proto__, constructor and prototype keys; build lookup maps with Object.create(null) or a real Map; parse with a schema validator that strips unknown keys; and on Node run with --frozen-intrinsics where practical. In review, any obj[key] = value where key traces back to a request body is the thing I stop on.

Getters and setters — when are they a good idea in a public API?

When the read is cheap, side-effect free and genuinely derived — a fullName from two fields, a size that reads an internal map. They are a bad idea when they hide cost or I/O, because callers reasonably assume property access is free and will put them in loops and in render paths; a method named computeTotal() tells the truth that get total() hides. They are also awkward for serialisation: accessors on a prototype are skipped by spread, Object.assign and JSON.stringify of a plain instance unless you add toJSON. My rule in review is: accessor if it is O(1) and pure, method otherwise, and never an accessor that can throw.

Do you use decorators, and what is their status?

The standard decorators proposal is Stage 3 and TypeScript has implemented it since 5.0 — that is the version you write today, with no experimentalDecorators flag. The old flag enables a completely different, TypeScript-only design from the 2015 proposal, which is what Angular and older NestJS/TypeORM code is written against; the two are not interchangeable, and mixing them in one project is a real migration hazard, so the honest answer for a large Angular codebase is "we stay on legacy decorators until the framework moves". Standard decorators are much better behaved: they receive a typed context object, they can add initialisers, and crucially accessor fields plus [Symbol.metadata] give a defined place for metadata rather than reflect-metadata patching the global. Where I actually reach for them is cross-cutting instrumentation — timing, retries, logging — and I keep them out of business logic, because a decorator is invisible control flow at the call site.

WeakMap, WeakRef, FinalizationRegistry — what are they for and what would you refuse to use them for?

WeakMap/WeakSet hold keys weakly, so an entry disappears when the key is otherwise unreachable: the right structure for attaching metadata to objects you do not own (DOM node → handler, request → span) without leaking. WeakRef gives a weak reference to a single object and FinalizationRegistry gives a callback after collection. I use WeakMap freely; I treat the other two as last resorts, because collection timing is entirely unspecified — callbacks may fire late, in a batch, or never (they are not run at process exit), and code that depends on them is non-deterministic across engines and versions. If cleanup must happen, it needs an explicit lifecycle — close(), AbortSignal, or using with Symbol.dispose — not the garbage collector. The one genuine WeakRef use case is a cache that should not keep large objects alive, and even then I would want a size-bounded strong cache in front of it.

03 Functions, closures, this

A function in JavaScript is an object with a callable slot, a captured environment record, and — for ordinary functions — a this that is supplied fresh at every call. Those three facts generate almost every question you will be asked in this area. A closure is not a special construct; it is the unavoidable consequence of functions being values: when a function is created it keeps a reference to the scope chain it was created in, and that chain stays alive as long as the function does. Closures are how you get private state, memoisation, partial application and event handlers — and they are also the most common cause of retained memory in a long-lived Node process, because one small callback can pin a large object graph.

Scope is lexical and determined at parse time. var is function-scoped and hoisted to undefined; let and const are block-scoped and hoisted into a temporal dead zone — the binding exists from the top of the block but touching it before the declaration throws ReferenceError. The TDZ is a feature, not a wart: it turns "I used this before it was ready" from a silent undefined into a loud error. Function declarations are hoisted whole (callable before their line); function expressions are not. In 2026 the only reason to write var is when you are reading someone else's 2014 code.

this is decided at the call site, by four rules checked in order: new fn() binds a fresh object; fn.call/apply/bind binds explicitly; obj.fn() binds obj; otherwise it is undefined in strict mode (which is all module code) or the global object in sloppy mode. Arrow functions have no this of their own — they close over the enclosing one lexically, along with arguments, super and new.target — which is precisely why they are right for callbacks and wrong for object methods and prototype methods. The compact rule: an arrow inherits, a function receives.

const counter = {
  n: 0,
  incArrow: () => { this.n++; },        // WRONG: `this` is module scope (undefined), not counter
  inc() { this.n++; },                  // right
  incAll(list) {
    list.forEach(() => this.inc());     // right: arrow inherits `this` from incAll
    list.forEach(function () { this.inc(); });        // TypeError: this is undefined
    list.forEach(function () { this.inc(); }, this);  // legacy fix: thisArg
  },
};

const { inc } = counter;   // classic detach
inc();                     // TypeError - the method lost its receiver
counter.inc.call(counter); // or bind once at the boundary

The other side of closures is identity. Every evaluation of a function expression creates a new function object, so a.filter(x => x.ok) allocates on every call, fn.bind(obj) returns a new function each time (which is why removeEventListener(fn.bind(this)) never removes anything), and a fresh callback passed to a memoised component defeats the memoisation. Stable identity is a design decision: hoist the function to module scope if it captures nothing, bind once in the constructor if it must capture this, or memoise it deliberately.

Three things worth knowing precisely. The loop-closure question is still asked, and the modern answer has two halves. for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)) logs 3 3 3 because var creates one binding for the whole function; let logs 0 1 2 because the spec creates a fresh binding per iteration and copies the value forward. The half candidates miss: this per-iteration binding applies to for(let) and for…of, but a let declared inside a while loop body is also fresh per iteration, while a single let declared outside is not — so the rule is "one binding per block entry", not "let is magic". The related production bug is the leak: a closure that captures a huge object only to read one field keeps the whole object alive. Destructure what you need at capture time.

Interview Q&A — 03

Explain the four this binding rules and their precedence.

In order: new binding wins — new f() creates a fresh object and binds this to it; then explicit binding via call, apply or a previously applied bind; then implicit binding, where obj.f() binds obj; then the default, which is undefined in strict mode and globalThis in sloppy mode. Arrow functions sit outside this entirely: they have no this slot, so the lookup walks the scope chain like any other variable. The practical consequence I would state at review time is that this is a property of the call, so any API that hands methods around as values — event listeners, map, dependency injection containers — must either bind or wrap, and the safest library design is not to depend on this at all.

What exactly is the temporal dead zone and why is it useful?

let, const and class bindings are created when the block is entered but left uninitialised; any read or write before the declaration executes throws ReferenceError. That window is the TDZ. It is useful because the alternative — var's silent undefined — turns an ordering mistake into a value bug that surfaces far from its cause, and because it makes const genuinely meaningful (you can never observe it before assignment). It also has a real cost to know about: TDZ checks are why circular imports between ES modules fail loudly with "Cannot access before initialization" rather than yielding undefined the way CommonJS does — which is a better failure, but it does mean an ESM migration surfaces cycles that CommonJS had been hiding.

When should a method be an arrow-function class field, and when not?

Use it only when you need a stable, pre-bound reference and the alternative is worse — for example a handler you must pass by reference to addEventListener and later remove. Everywhere else, prototype methods are better: they are shared rather than allocated per instance, non-enumerable so they stay out of spreads and JSON, and patchable for spies and instrumentation. In a class with thousands of instances the per-instance closure is measurable memory. My default in review: methods on the prototype, binding done at the boundary where the function escapes the object.

How do closures cause memory leaks in a Node service, and how do you find one?

A closure keeps its entire enclosing scope alive, not just the variables it reads, so a callback registered on a long-lived emitter, timer, or module-level cache can pin request-scoped objects forever. The classic shapes are: an unbounded Map keyed by request id, an EventEmitter listener added per request and never removed (you will see the "possible EventEmitter memory leak, 11 listeners added" warning), and a setInterval whose callback captures a connection. To find one: take two heap snapshots under steady load, diff them, sort by retained size, and follow the retainer path back to the GC root — it usually terminates at a module-level structure. The fixes are ownership-shaped: bound caches with an eviction policy, AbortSignal/removeListener on teardown, and WeakMap when metadata should not extend a lifetime.

What does fn.bind return, and what are its gotchas?

A new exotic function object with this and any leading arguments fixed, a name of "bound f", and a length reduced by the number of pre-applied arguments. Gotchas: it is a new object every call, so binding inline in addEventListener/removeEventListener never unregisters; a bound function cannot be re-bound (a second bind silently has no effect on this); and new on a bound function ignores the bound this but keeps the partial arguments. In modern code I mostly reach for an arrow wrapper instead, and use bind only for partial application where the fixed identity is stored somewhere.

Why does arr.map(parseInt) not do what people expect?

map calls its callback with three arguments — value, index, array — and parseInt takes a radix as its second parameter, so ["1","2","3"].map(parseInt) evaluates parseInt("1",0), parseInt("2",1), parseInt("3",2) and returns [1, NaN, NaN]. The general lesson is that point-free style is unsafe whenever the receiving function has optional parameters, which is most built-ins; write the explicit arrow, map(s => parseInt(s, 10)) or better map(Number). TypeScript catches some of these but not this one, because parseInt's signature happens to accept the extra numeric argument — a good example of why "it compiles" is not the same as "it is right", and a reason we keep the unicorn/no-array-callback-reference-style lint rule on.

Are tail calls optimised in JavaScript?

Proper tail calls are in the ES2015 specification, but in practice only JavaScriptCore (Safari) implements them; V8 and SpiderMonkey shipped and then withdrew or never enabled the work, largely over debugging and stack-trace concerns. So the honest engineering answer in 2026 is: assume no TCO. Deep recursion will hit a stack limit around ten thousand frames in V8, and the limit depends on frame size, so it is not a number you can rely on. Anything that recurses over user-sized data — a tree walk, a JSON transform, a parser — should be written iteratively with an explicit stack, or chunked across event-loop turns if it also needs to yield.

Overloads or a union parameter — how do you choose?

Use a union parameter when the return type does not depend on which member you passed; it keeps the implementation honest, because the compiler checks the body against the union rather than trusting you. Use overloads when the caller-visible relationship between argument and return really is a set of discrete pairs — document.createElement is the canonical example. The trap with overloads is that the implementation signature is invisible to callers and unchecked against them, so a mismatch between the overload list and the body is a silent lie; and overloads compose badly with generics and spread arguments. My default is a generic function with a conditional or mapped return type, falling back to overloads only when the conditional type becomes unreadable.

What is satisfies for, and how is it different from as or a type annotation?

A type annotation (const x: T = …) checks the value and widens its inferred type to T, losing literal detail. as asserts without checking, so it can lie. satisfies checks the value against a constraint but keeps the narrow inferred type — so a config object can be validated as Record<string, RouteSpec> while its keys stay a literal union you can index with. The everyday payoff is exactly that: catch a typo in a route table at the point of definition, and still get autocomplete for the concrete keys downstream. It is a compile-time construct with no emit, and it is one of the first things I teach on a team because it removes the usual reason people reach for as.

Explain currying and partial application, and where they actually earn their place in production code.

Partial application fixes some arguments and returns a function of the rest; currying is the stricter form where every function takes exactly one argument. They earn their place where you build a pipeline of small transformations that must be configured once and applied many times — a logger pre-bound to a request id, a comparator factory, middleware, or a validator parameterised by schema. Where they stop earning it is in ordinary application code, because the stack traces get worse, the types get harder to read, and a plain function with an options object is clearer to the next person. TypeScript handles curried generics poorly when inference has to flow across several returns, which is a practical argument against over-currying a public API.

04 The event loop

JavaScript runs on one thread with one call stack, and it never interrupts itself. A function runs to completion; only when the stack empties does the runtime pick the next unit of work. Everything else — concurrency, responsiveness, "async" — is scheduling policy around that single rule. The model to hold: a call stack, a set of task queues (macrotasks: timers, I/O completions, DOM events, messages), and one microtask queue (promise reactions, queueMicrotask, MutationObserver). After every task, and after the stack empties, the runtime drains the microtask queue completely — including microtasks enqueued while draining — before it takes another task. That "drain to empty" rule is the source of both the ordering questions you will be asked and the starvation bugs you will debug.

In the browser there is a third beat: rendering. The loop is roughly task → microtask drain → (if it is time to paint) requestAnimationFrame callbacks → style → layout → paint. Anything that keeps the stack busy for more than a frame budget (~16 ms at 60 Hz) delays that paint, and anything above 50 ms is a "long task". Since Google promoted INP (Interaction to Next Paint) to a Core Web Vital in March 2024, this is not an academic concern: INP measures the worst-case delay from a user input to the next frame, and the fix is almost always "break the work up and yield", not "make the work faster". The modern primitive for that is await scheduler.yield(), which yields to the browser but keeps your continuation at higher priority than fresh tasks — unlike the old setTimeout(0) trick, which puts you at the back of the queue behind everything else.

// The ordering question, with the answer derivable from two rules.

// Rule 1: synchronous code first (the async fn body runs sync until its first await).
// Rule 2: drain ALL microtasks (3,4,6) before ANY macrotask (2).

// Keeping a long job responsive (browser):
async function processAll(items) {
  for (const [i, item] of items.entries()) {
    doWork(item);
    if (i % 50 === 0) await scheduler.yield();   // yields to paint, resumes at high priority
  }
}

Node's loop is libuv's, with named phases that run in a fixed order each turn: timers (expired setTimeout/setInterval), pending callbacks, idle/prepare, poll (I/O — where the loop blocks when there is nothing else), check (setImmediate), close callbacks. Two queues sit outside the phases and are drained after each phase and between each callback: process.nextTick callbacks first, then promise microtasks. That ordering is why process.nextTick can starve the loop entirely — a nextTick that schedules another nextTick never lets I/O run — and why the Node docs themselves recommend setImmediate for "run after the current operation" in almost every case.

When one thread is genuinely not enough

The loop only helps with waiting. CPU-bound work — parsing a 50 MB payload, image processing, crypto, a synchronous template render — occupies the stack and nothing else runs, so throughput and latency both collapse. The answer is real parallelism: worker_threads in Node (with a pool, because thread startup is ~10–30 ms), Web Workers in the browser, and SharedArrayBuffer plus Atomics when workers must share memory rather than copy it. Worth naming as a current detail: Atomics.pause reached Stage 4 and is slated for ES2027 — a hint to the CPU that you are in a spin-wait loop, which is the missing piece for efficient user-space locks in SharedArrayBuffer code. In Node, also remember that a few things already are multi-threaded under you: libuv's default four-thread pool serves fs, DNS lookups, zlib and crypto.pbkdf2, and UV_THREADPOOL_SIZE is a real tuning knob when a service does heavy file or compression work.

Interview trap

"Async" does not mean "off the main thread". Candidates say async makes code non-blocking; it does not. await only yields at the point it suspends — the synchronous parts of every async function still run on the one thread, and JSON.parse on a 50 MB body inside an async handler blocks the loop just as hard as it would anywhere else. The related trap is await inside a for loop: it is correct when the iterations genuinely depend on each other, and a 10× latency bug when they do not. Use Promise.all for independent work, or a bounded-concurrency pool when the work hits a rate-limited dependency — unbounded Promise.all over 10 000 items is how you DoS your own database. That bounded pool, not Promise.all, is the answer a lead is expected to give.

(2) You will see a single ~300 ms entry, and any click during it is delayed by up to that long — that is your INP. Interview Q&A — 04

Explain the difference between a task and a microtask, and why the distinction exists.

A task (macrotask) is one unit of work the event loop picks up: a timer callback, an I/O completion, a dispatched DOM event. A microtask is a continuation scheduled to run at the end of the current task, and the queue is drained completely — including microtasks added during the drain — before the next task or before rendering. The distinction exists so that promise reactions observe a consistent world: everything a promise chain does happens before the browser paints or another event is dispatched, so you never see a half-updated state on screen. The price is that microtasks can starve everything, which is why an infinite .then chain freezes a tab in a way an infinite setTimeout chain does not.

Walk me through Node's event loop phases and where promises fit.

Each turn goes: timers (expired setTimeout/setInterval), pending callbacks (deferred system errors), idle/prepare (internal), poll (retrieve new I/O events and run their callbacks — the loop blocks here if there is nothing else scheduled), check (setImmediate), then close callbacks. Promises are not a phase: the microtask queue plus Node's nextTick queue are drained between individual callbacks and between phases, with nextTick taking priority over promise microtasks. The practical consequences are that setImmediate always runs before a timer if you schedule both from inside an I/O callback, that setTimeout(fn, 0) ordering against setImmediate at the top level is genuinely non-deterministic (it depends on how long process startup took relative to the 1 ms timer), and that a long-running callback delays every phase behind it.

A service's p99 latency spikes but CPU is at 40%. How do you approach it?

Forty percent average CPU on a single-threaded runtime is consistent with the loop being blocked in bursts, so the first measurement is event-loop lag, not CPU: perf_hooks' monitorEventLoopDelay histogram, or the loop-lag metric your APM already collects, correlated with the latency spikes. If lag tracks the spikes, I look for synchronous work in the hot path — large JSON.parse/stringify, sync fs calls, crypto without the async variant, a regex with catastrophic backtracking, or a template render — and I profile with --cpu-prof or a continuous profiler to find it. If lag is flat, the delay is downstream: connection-pool saturation, a dependency's own p99, or DNS. The fixes differ completely, which is why measuring loop lag first is the discriminating step, and it is also the metric I would put on the dashboard permanently.

When do you reach for worker threads instead of async I/O?

When the work is CPU-bound, because async I/O buys you nothing there — the thread is busy either way. Concretely: parsing or transforming large payloads, image or PDF generation, compression, cryptographic key derivation, and anything that measures as a long task in a profile. The design points that matter more than the decision itself: use a pool with a bounded queue rather than spawning per request (startup is tens of milliseconds and each worker has its own heap and V8 isolate), decide deliberately between transferring an ArrayBuffer (zero-copy, but the sender loses it) and structured-cloning it (copy, so large payloads cost real time), and give the pool a timeout and a kill path so a runaway worker cannot pin a core forever. In the browser the same logic applies to Web Workers, with the extra note that SharedArrayBuffer needs cross-origin isolation headers.

What is INP and what actually improves it?

Interaction to Next Paint became a Core Web Vital in March 2024, replacing First Input Delay. It measures the full latency from a user interaction to the next rendered frame — input delay plus handler time plus presentation delay — reported at roughly the 98th percentile of a page's interactions, with a "good" threshold of 200 ms. What improves it is almost never micro-optimising the handler: it is shortening the longest tasks so the browser can paint. Concretely, yield inside long work (await scheduler.yield()), do the visual acknowledgement first and defer the expensive part, move computation to a worker, avoid layout thrash by batching DOM reads and writes, and cut the amount of JavaScript that has to execute during hydration. The measurement lever is the Long Animation Frames API, which attributes a slow frame to a script and a source location — much more actionable than the old long-task entries.

Why is setTimeout(fn, 0) not actually zero?

Two reasons. The spec clamps nesting: after five levels of nested timers the minimum becomes 4 ms, so a self-rescheduling timer chain caps out around 250 iterations per second. And even at the first level the callback only runs when the loop reaches its timers phase with the stack empty, so any long task ahead of it delays it arbitrarily — the delay is a floor, not a promise. Browsers additionally throttle timers in background tabs, often to once per second or slower, and freeze them entirely under some conditions. If you need "as soon as possible without blocking", the right tools are queueMicrotask (same task, after the current stack), setImmediate in Node, or scheduler.postTask with an explicit priority in the browser.

How would you implement a bounded-concurrency map?

Keep a set of in-flight promises; start work until the set reaches the limit; then await Promise.race(inFlight) to free a slot and start the next. Each promise removes itself from the set on settle, and you collect results by index so ordering is preserved even though completion is not. The details that separate a good answer: use Promise.allSettled semantics or an explicit error policy so one rejection does not silently drop the remaining work; make the limit configurable per dependency rather than global, because the right number for a database pool is not the right number for an object store; and add an AbortSignal so the whole batch can be cancelled. In a library-friendly world I would reach for p-limit rather than hand-rolling it, but I would still expect an engineer at this level to be able to write the fifteen lines on a whiteboard.

Microtask starvation — what does it look like and how do you avoid it?

It looks like a completely frozen tab or a Node process that stops serving traffic while burning 100% of one core, with no long task attributable to a single function. It happens when a promise chain schedules another microtask unconditionally — a recursive .then, a poll loop written as await Promise.resolve(), or a queue drain that re-enqueues itself — because the loop refuses to move on until the microtask queue is empty. The fix is to yield to a real task boundary at intervals: setImmediate in Node, scheduler.yield() or setTimeout(0) in the browser. This is also the reason a "busy wait until a flag flips" never works in JavaScript: nothing can flip the flag while you are on the stack.

What does AbortController actually do, and why is it the cancellation story?

It is a signal object with an aborted flag and an abort event; consumers opt in by listening and rejecting with an AbortError. It does not stop running code — nothing can preempt a synchronous JavaScript frame — it just gives every layer a shared, composable way to notice that the caller has gone away. It is the standard everywhere now: fetch, most Node stream and timer APIs, addEventListener({ signal }) (which also removes the listener on abort, the neatest cleanup idiom in the language), and AbortSignal.any/timeout for composing deadlines. The lead-level framing is that cancellation must be threaded through your own APIs the same way — a function that starts I/O and does not accept a signal cannot participate in a request deadline, and that is an API-review issue, not an implementation detail.

What breaks when someone calls a blocking synchronous API in a request handler?

Everything queued behind it: not just that request, but every other connection, timer and health check on that process, because there is one stack. A 200 ms readFileSync in a handler serving 500 rps means roughly 100 requests waiting, and the effect is superlinear once queues build. It also poisons your metrics — latency looks like a downstream problem, and the health check itself times out, so an orchestrator may restart a process that is merely busy. In review the rule is simple and absolute: no *Sync API on a request path, no unbounded synchronous loops over request-sized data, and any CPU work above a few milliseconds goes to a worker pool. Startup code is the one place where sync calls are legitimate, and saying that distinction out loud is what makes the answer credible.

05 Promises and async/await

A promise is a state machine with exactly one transition: pending → fulfilled or pending → rejected, permanently. Everything else follows. Because settlement is final, a promise is a value you can hold, pass around and subscribe to more than once — unlike a callback, which is a one-shot handoff. Because then returns a new promise, chains compose and errors propagate down the chain like exceptions propagate up a stack. And because reactions are queued as microtasks, a .then callback never runs synchronously even if the promise is already settled — which is the guarantee that makes promise-based code deterministic to reason about.

async/await is syntax over that machine, not a different mechanism. An async function always returns a promise; its body runs synchronously up to the first await, then suspends and resumes as a microtask when the awaited value settles. That "synchronously up to the first await" detail is where most ordering questions live, and it is also why moving a validation check above the first await changes whether a caller sees a thrown error or a rejected promise. await on a non-promise still costs a microtask tick, so it is not free, but it is cheap enough that clarity wins.

// The four combinators, and when each is right.
const [a, b] = await Promise.all([getA(), getB()]);        // fail fast; both must succeed
const results = await Promise.allSettled(tasks);           // never rejects; inspect each
const firstOk  = await Promise.any(mirrors);               // first FULFILLED; AggregateError if all fail
const firstAny = await Promise.race([work, timeout]);      // first SETTLED, success or failure

// ES2024: withResolvers - the deferred pattern, without the constructor dance.
const { promise, resolve, reject } = Promise.withResolvers<Data>();

// ES2025: Promise.try - run a possibly-sync function and get a promise either way,
// so a synchronous throw becomes a rejection instead of blowing up the caller.
const p = Promise.try(() => maybeThrowsSynchronously(input));

// A deadline that actually cancels the work, rather than just ignoring it.
const res = await fetch(url, { signal: AbortSignal.timeout(2_000) });

The distinction between Promise.all and Promise.allSettled is a design decision, not a style preference. all rejects at the first failure but does not cancel the others — they keep running, and if one of them later rejects with nobody listening you get an unhandled rejection. Use all when partial results are worthless (you need both halves of a page), allSettled when they are not (a dashboard of six independent widgets, where one dead service should degrade one tile). any is for redundancy — first success wins, and you get an AggregateError with all the reasons if everything fails. race is for deadlines, and its trap is that the losing promise is still running and still holding its resources; pair it with an AbortSignal if the loser matters.

Errors, floating promises and context

Two failure modes dominate real incidents. The first is the floating promise: a call whose promise nobody awaits or catches. The work still happens, but errors surface as an unhandledRejection, which in Node has terminated the process by default since Node 15 — so a forgotten await in a logging call can crash a service. The defence is mechanical, not cultural: typescript-eslint's no-floating-promises and no-misused-promises rules, on as errors, with void somePromise as the explicit "I meant to fire and forget" escape hatch. The second is the lost context: once execution crosses an await, you are on a different stack, so naive request-id propagation breaks. In Node the answer is AsyncLocalStorage (stable, and what OpenTelemetry uses under the hood); the language-level version, the AsyncContext proposal, is still working through TC39 and is not something to build on yet.

// Retry with exponential backoff, jitter, a deadline, and cancellation.
async function retry<T>(
  fn: (signal: AbortSignal) => Promise<T>,
  { attempts = 4, baseMs = 100, signal }: { attempts?: number; baseMs?: number; signal?: AbortSignal } = {},
): Promise<T> {
  let lastError: unknown;
  for (let i = 0; i < attempts; i++) {
    signal?.throwIfAborted();
    try {
      return await fn(AbortSignal.any([signal, AbortSignal.timeout(5_000)].filter(Boolean) as AbortSignal[]));
    } catch (err) {
      if (!isRetryable(err)) throw err;                       // never retry a 400
      lastError = err;
      const delay = baseMs * 2 ** i * (0.5 + Math.random());  // full-ish jitter
      await new Promise((r) => setTimeout(r, delay));
    }
  }
  throw lastError;
}
Interview trap

try/catch only catches what you await. try { doAsync(); } catch {} catches nothing, because doAsync() returns before it fails. The same trap wearing a different hat: return await x versus return x inside a try — with a bare return x the function's frame is gone before the promise rejects, so the local catch and finally do not see it, and your stack trace loses the frame. Outside a try the two are equivalent in modern V8 (the historical performance argument for return x disappeared with zero-cost async stack traces), so the safe habit is return await. Third variant, the one that bites in code review: array.forEach(async (x) => { … }) — forEach discards the returned promise, so the loop "finishes" instantly, errors become unhandled rejections, and any code after it runs before the work does. Use for…of with await, or Promise.all(array.map(…)).

(1) "before" logs synchronously, then the code after the call, then "after" — because the body runs to the first await on the caller's stack and the remainder is a microtask. This is the mental model that makes every "what does this print" question mechanical rather than memorised.

(2) The race version leaves the request in flight — you have a timeout in your code and no timeout on the wire, so under load you accumulate sockets and the server keeps doing work nobody will read. The AbortSignal version shows the request as cancelled. The general principle: race abandons, AbortSignal cancels, and the difference only shows up under load, which is exactly when it hurts.

Interview Q&A — 05

Promise.all versus Promise.allSettled — how do you choose, and what does all do to the losers?

all rejects as soon as any input rejects and gives you a single array of values on success; allSettled always fulfils with a status-tagged entry per input. The choice is about whether partial results have value: a page that needs both the user and their permissions should fail fast, a dashboard of independent tiles should not. The critical detail people miss is that all's early rejection does not cancel anything — the other promises keep running, keep holding connections, and if one of them rejects afterwards with no handler you get an unhandled rejection that can take the process down. So when I use all on anything expensive, the operations also share an AbortController that I abort in the catch.

What is an unhandled rejection, and what should a service do about it?

It is a rejected promise with no rejection handler attached by the time the microtask queue drains. Node's default since v15 is --unhandled-rejections=throw, which raises an uncaughtException and terminates the process; browsers fire an unhandledrejection event and log to the console. The right posture for a service is: keep the crash-on-unhandled default, because an unknown-state process is more dangerous than a restart, but wire the handler to flush logs and traces with the rejection reason before exiting, and run under a supervisor. Then prevent them structurally — no-floating-promises as a lint error, void for deliberate fire-and-forget, and a .catch on anything genuinely detached like a background refresh. Downgrading to --unhandled-rejections=warn to "stop the crashes" is the wrong answer and is worth saying so explicitly.

Why does await in a loop show up in code review, and when is it correct?

Because it serialises work that is usually independent: ten 100 ms calls become one second instead of one hundred milliseconds. It is correct when iteration N+1 genuinely needs the result of N (pagination cursors, dependent writes), when the downstream system requires ordering, or when you are deliberately rate-limiting. When it is not correct, the fix is not automatically Promise.all — that is right for small bounded N, but for a thousand items you need a bounded-concurrency pool, because unbounded fan-out just moves the failure into the database's connection pool or gets you rate-limited. So the review comment is a question: "are these independent, and if so what is the right concurrency for this dependency?"

How does async/await desugar, and why does it matter that the body runs synchronously to the first await?

An async function is a coroutine: the body compiles to a state machine that returns a promise immediately, runs synchronously until the first await, then registers a continuation on the awaited value and returns control to the caller; each resumption is a microtask. It matters for three practical reasons. Argument validation placed before the first await throws synchronously into the caller's frame rather than producing a rejection — which is usually not what you want for an async API, since callers expect a rejection, so many teams standardise on rejecting for everything. Second, side effects before the first await happen eagerly at call time, which makes "lazy" async functions a trap: if you want laziness you need a thunk. Third, it explains ordering puzzles without memorisation — every await is one microtask boundary.

You need per-request context — request id, tenant, user — across await boundaries. How?

In Node, AsyncLocalStorage from node:async_hooks: you run the request handler inside als.run(context, fn) and any code beneath it, however deeply awaited, reads it with als.getStore(). It is stable, it is what OpenTelemetry and most logging libraries use internally, and it costs a small but non-zero amount of async-hook bookkeeping — measurable but almost always worth it. What I would not do is thread a context parameter through every function signature (it rots, and third-party callbacks break the chain) or stash it on a module-level variable (concurrent requests interleave and it is silently wrong). In the browser there is no equivalent yet; the AsyncContext proposal is the standards-track answer and is not ready to build on, so you pass context explicitly or scope it to a class instance.

Design a retry policy for an unreliable dependency.

Start with what is retryable: idempotent operations only, and only on transient signals — timeouts, connection resets, 429, 502/503/504 — never on a 400 or a 409, and only on a POST if it carries an idempotency key. Then exponential backoff with jitter, because synchronised retries from many instances are how a degraded service becomes a dead one; a base of 100 ms doubling, with full jitter, and a hard cap on both attempts and total elapsed time so retries live inside the caller's deadline rather than multiplying it. Wrap the whole thing in a circuit breaker so that a sustained outage stops generating load, and emit metrics for attempts and for exhausted retries, because a retry that succeeds still hides a problem you want to see. The failure I look for in candidates' answers is retrying inside three layers at once: the SDK, the service client, and the handler — that turns a 3× policy into 27×.

What is Promise.withResolvers and when is a deferred legitimate?

ES2024's Promise.withResolvers() returns { promise, resolve, reject }, replacing the old pattern of declaring two lets and assigning them inside a new Promise executor. It is legitimate whenever the settling event arrives from outside the function that created the promise: adapting an EventEmitter or a WebSocket message, a queue where a consumer waits for a producer, a one-shot "ready" signal, or bridging a callback API you cannot change. What it is not for is wrapping code that is already promise-based — the explicit-construction antipattern, new Promise(r => existing.then(r)), which loses rejections and is the most common misuse. The other thing to say is that a deferred escapes the chain, so nothing propagates errors for you: you own the reject path.

How do you time out an operation properly?

AbortSignal.timeout(ms) is the primitive, and AbortSignal.any([userSignal, AbortSignal.timeout(ms)]) is how you combine a caller's cancellation with your own deadline. The important part is that the timeout must reach the thing doing the I/O — passing the signal into fetch, into the database driver, into the child process — because a Promise.race against a timer only stops you waiting, while the socket, the query and the server-side work all continue. At system level I would add that timeouts should be budget-based rather than fixed per call: a request arrives with a deadline, each hop subtracts its elapsed time and passes the remainder down, so a chain of four services with 5-second timeouts each cannot produce a 20-second user-visible wait. And every timeout needs a metric, because a timeout that fires constantly is a capacity signal, not an error.

Is return await inside a try different from return?

Yes, and it is the one place the distinction is real. With return promise, the async function's frame completes and the promise is handed to the caller, so a later rejection is not seen by the local catch, and a finally runs before the operation actually finishes. With return await promise, the function stays suspended until settlement, so the local catch and finally behave as you would expect and the frame appears in the async stack trace. Outside a try the two are semantically equivalent and the historical "extra microtask" cost is negligible in current V8, which is why the ESLint rule no-return-await was retired in favour of return-await: always in typescript-eslint. I teach "always return await in an async function" because the exception is not worth the rule.

A promise-based library you depend on never settles under some condition. How do you find and contain it?

Containment first: nothing in a request path should await something without a deadline, so I would add an AbortSignal.timeout or a race-with-timeout wrapper around the call and get an error instead of a hang, plus a metric on the timeout so I can see the rate. To find it: Node's --async-stack-traces (on by default in current versions) plus process.getActiveResourcesInfo() or why-is-node-running to see what handles are keeping the loop alive, and a heap snapshot to find promises retained in the pending state. If it is a browser, the Performance panel plus a deliberate reproduction with logging around the suspect calls. Then the real fix is upstream — a bug report with a minimal repro — with the timeout wrapper staying permanently, because "the library will never hang again" is not a property you can rely on.

06 Iterators and generators

The iteration protocol is one of the best-designed corners of the language and it is under-used. An object is iterable if it has a [Symbol.iterator]() method returning an iterator: an object with next() that yields { value, done }, and optionally return() for early cleanup and throw() for injecting an error. That single contract is what for…of, spread, array destructuring, Promise.all's argument, new Map(pairs) and yield* all speak. Implement it once on your own type and every one of those constructs works on it for free — which is exactly the kind of leverage a lead should be looking for when reviewing a domain model.

Generators are the ergonomic way to produce an iterator. A function* returns an object that is both iterable and an iterator, and each yield suspends the function with its whole local state intact until the next next() call. That gives you laziness for free: an infinite sequence costs nothing until consumed, and a pipeline of generators processes one element at a time rather than materialising an array per stage. The less-known half is that next(v) sends a value into the generator — const x = yield y — which makes generators two-way coroutines. That is the mechanism behind redux-saga and behind every "effect as data" testing pattern: the generator yields a description of work, the driver performs it and sends the result back, so the business logic is testable with no I/O at all.

// A domain type that speaks the protocol - now for...of, spread and destructuring all work.
class Ring<T> {
  #items: T[] = [];
  *[Symbol.iterator](): Iterator<T> { yield* this.#items; }
}

// Lazy pipeline: nothing is computed until something pulls.
function* naturals() { for (let i = 0; ; i++) yield i; }

// ES2025 iterator helpers: the same combinators as arrays, but lazy and on ANY iterator.
const firstTenEvenSquares = naturals()
  .filter((n) => n % 2 === 0)
  .map((n) => n * n)
  .take(10)
  .toArray();

// ES2026 iterator sequencing: concatenate iterables without materialising them.
const all = Iterator.concat(pageOne(), pageTwo(), pageThree());

Iterator helpers (Stage 4, ES2025, shipping in every current engine and in Node 22+) are the biggest quality-of-life change here in years. Before them, using map/filter on anything that was not an array meant [...iterable] first — which defeats laziness and blows up on infinite or huge sources. Now map, filter, take, drop, flatMap, reduce, toArray, forEach, some, every and find live on Iterator.prototype and are lazy end-to-end. ES2026 adds iterator sequencing (Iterator.concat) to chain sources, and Array.fromAsync as the async counterpart of Array.from. The one thing to keep in mind: helpers return stateful, single-use iterators, so unlike array methods you cannot iterate the result twice.

Async iteration and backpressure

The async half of the protocol is [Symbol.asyncIterator](), consumed with for await…of, and produced most easily by async function*. The important property is that it is pull-based: the consumer asks for the next value and the producer does not run ahead. That is backpressure, built into the language — the reason streaming a million-row query as an async generator uses constant memory while await getAllRows() does not. Node streams are async iterables, Web ReadableStream is async iterable in current engines, and fetch response bodies stream, so you can write an ETL pipeline as a chain of async generators with no framework at all.

// Constant-memory paging: the consumer controls the rate, and cleanup is guaranteed.
async function* pages(url: string, signal: AbortSignal): AsyncGenerator<Row, void> {
  let cursor: string | undefined;
  try {
    do {
      const res = await fetch(`${url}?cursor=${cursor ?? ""}`, { signal });
      const { rows, next } = await res.json();
      yield* rows;
      cursor = next;
    } while (cursor);
  } finally {
    // Runs when the consumer breaks out of `for await`, throws, or returns early.
    // The consumer calling .return() is what triggers it - this is where you release resources.
  }
}

Interview Q&A — 06

What is the difference between an iterable and an iterator, and why does the distinction matter?

An iterable has a [Symbol.iterator]() method that produces an iterator; an iterator has next() and holds the position. An array is iterable and gives you a fresh iterator each time, so you can loop it repeatedly; a generator object is both — its [Symbol.iterator]() returns itself — which is why it can only be consumed once. The distinction matters the moment you accept "an iterable" as a function parameter: if you iterate it twice, or iterate it after the caller already did, you get silently empty results for generators and correct results for arrays. My rule in API design is to accept an iterable, consume it exactly once, and document that — or take an array when you genuinely need multiple passes.

Where would you actually use a generator in production code?

Four places I have used them for real: streaming pagination, where the generator hides the cursor loop and the consumer just writes for await; tree and graph traversal, where recursion with yield* is dramatically clearer than an explicit stack; parsing and tokenising, where the lazy pull model matches the problem; and state machines or effect-as-data patterns where you want the business logic testable without I/O. Where I would not use them: as a general replacement for array methods on small collections (the allocation and the indirection are not free, and the code is less familiar), and anywhere the single-use semantics would surprise a caller. The honest trade-off is readability for the team versus laziness for the machine, and I would only pay it where the data can be large.

Explain iterator helpers and what changed with them.

They are ES2025's addition of map, filter, take, drop, flatMap, reduce, toArray, forEach, some, every and find to Iterator.prototype, so any iterator — from a generator, a Map, a Set, NodeList, a regex matchAll — gets lazy combinators without being converted to an array first. Before, "map over a Set" meant [...set].map(), which materialises everything and is impossible on an infinite source. They also make take the natural way to bound an unbounded stream. Two caveats worth naming: the result is a single-use stateful iterator, not an array, and helper chains have real per-element call overhead, so for a small array that already exists, plain array methods are still faster. ES2026 adds Iterator.concat for sequencing several sources, which completes the set for paging scenarios.

How do async generators give you backpressure?

Because iteration is pull-based: the producer's body is suspended at each yield until the consumer's for await asks for the next value, so a slow consumer automatically throttles a fast producer without any buffering logic. Contrast that with a push model — an EventEmitter firing data events, or an unbounded queue — where the producer runs ahead and memory grows until something falls over. This is why a Node stream pipeline and an async-generator pipeline both hold memory constant on a 50 GB file while readFile plus split does not. The limitation to acknowledge is that async generators serialise: you get one in-flight value at a time, so if you need concurrency you must add it explicitly with a bounded pool between stages.

What does yield* do, and why is it more than a loop?

yield* inner delegates to another iterable: it forwards every yielded value outward, and — this is the part a for…of plus yield loop does not do — it also forwards values sent in with next(v), forwards throw() into the inner generator, propagates return() so the inner finally runs, and evaluates to the inner generator's return value. That makes it the composition operator for coroutines, not just a flattening shortcut. Practically it is what lets you split a large traversal into small named generators — yield* walkChildren(node) — with correct cleanup and cancellation semantics all the way down.

A generator holds a database cursor. How do you guarantee it is released?

Put the release in a finally inside the generator, and then make sure the consumer's exit path calls .return(). for…of and for await…of do that automatically on break, return and exceptions, so ordinary consumption is safe. The dangerous case is manual .next() driving, or handing the generator to code that abandons it — then the frame stays suspended and the cursor leaks. The robust answer today is Explicit Resource Management: give the wrapper a [Symbol.asyncDispose] and let callers write await using cursor = openCursor(), which the language guarantees to dispose at scope exit even on a throw. That reached Stage 4 (ES2027), ships in Node 24+, and TypeScript has supported using since 5.2 — it is the JavaScript answer to C#'s using and Python's with, and it is the pattern I would standardise on for anything with a lifetime.

How do you type a generator in TypeScript?

Generator<Y, R, N> has three parameters: what it yields, what it returns when done, and what next() accepts. Most code only cares about the first, but the third is what makes two-way coroutines type-safe, and getting it wrong is why "sent" values so often end up any. For async, it is AsyncGenerator<Y, R, N>, and consumers usually want the narrower AsyncIterable<T> in their signatures so any async iterable can be passed. The related config detail is that for await and generator downleveling used to need downlevelIteration; since TypeScript 6.0 deprecated that flag along with the ES5 target, and 7.0 removed ES5 entirely, iteration just works — one of the small simplifications that comes with dropping ES5.

When is a stream better than an async generator, and vice versa?

Async generators win on readability and composition for logic you write: pipelines of transformations, paging, and anything you want to unit-test, because they are just functions. Streams win where you need the surrounding machinery: Node's pipeline() gives you correct error propagation and destruction across stages, Web ReadableStream is transferable to a worker and integrates with fetch, Response and the Compression Streams API, and both give you a tunable queuing strategy rather than a fixed one-at-a-time pull. They interoperate — Readable.from(asyncGen) and for await (const chunk of stream) — so the pragmatic architecture is streams at the I/O edges and async generators for the business transformations in the middle. The failure mode to call out is mixing them without pipeline(): a manual .pipe() chain silently leaks file descriptors when a downstream stage errors.

Why can you not use await inside a plain for…of over promises and expect concurrency?

Because for…of pulls one value at a time and await suspends the loop body, so each iteration waits for the previous — the array of promises has already started running (promises are eager), but you are consuming them serially. That is an important nuance: const ps = xs.map(f) starts everything immediately, and a later serial await loop over ps is actually concurrent execution with serial collection, whereas for (const x of xs) await f(x) is genuinely serial because f is not called until its turn. for await…of over an async generator is serial by design, which is the backpressure you usually want. If you need real concurrency with a bound, that is a pool, and I would rather see an explicit one than a clever loop.

What is Array.fromAsync and when would you use it?

It is the ES2026 async counterpart to Array.from: it consumes an async iterable (or an iterable of promises) sequentially and resolves to an array, with an optional mapping function. The use case is the last mile of a streaming pipeline where you have decided the result is small enough to materialise — collecting a page of results, or a test asserting on everything a generator produced. The reason it needed to be standardised rather than left to Promise.all([...gen]) is that you cannot spread an async iterable at all, and hand-rolled loops get the error and cleanup semantics wrong. The judgement to apply is the same as always: fromAsync defeats the memory benefit of the stream, so it belongs at a boundary where you know the bound, not in the middle of a pipeline.

07 Modules and packaging

There are two module systems in this ecosystem and you will be asked to reason about both for years yet. CommonJS is dynamic: require() is a function call that runs at any point, returns a plain object, and can be conditional. ES modules are static: import declarations are hoisted and resolved before any code executes, which is precisely what makes tree shaking, live bindings and top-level await possible. The key structural difference is not syntax, it is when the graph is known: ESM's graph is known before evaluation, CJS's is discovered during it.

Three consequences follow directly. Live bindings: an ESM import is a view onto the exporter's binding, so if the exporter reassigns it the importer sees the new value; a CJS require copies a reference to whatever the object held at that moment. Cycles behave differently: CJS gives you a partially-populated exports object (often silently undefined), while ESM's hoisted bindings plus the temporal dead zone give a loud "Cannot access before initialization" — a better failure, but one that surfaces cycles a CJS codebase had been quietly tolerating. And tree shaking only works on the static form, which is why a barrel file re-exporting a hundred modules is a real build and bundle-size problem, not a style preference.

The migration reality, and what TypeScript 6/7 changed

The bimodal world is closing but not closed. Node's require(esm) — backported to 22.12 and unflagged from 23 — removed the worst wall: a CommonJS codebase can now consume an ESM-only dependency synchronously, unless that dependency uses top-level await, in which case you still need dynamic import(). The dual package hazard remains the thing to design against: if a package ships both a CJS and an ESM build, a dependency graph can load both, and then instanceof fails, module-level singletons duplicate, and caches diverge. The clean answers are to ship ESM-only when your consumers allow it, or to keep all state in a small CJS core that both entry points wrap.

On the TypeScript side, TypeScript 6.0 (March 2026) deprecated moduleResolution: "node" (node10) and "classic", and defaulted module to esnext; TypeScript 7.0 (July 2026) removed the amd, umd, systemjs and none module targets and the outFile option outright. In practice that means every project should now be on "module": "nodenext" (libraries and Node apps, where the emitted format must match the file's real format) or "module": "preserve" with "moduleResolution": "bundler" (apps compiled by Vite, esbuild or Rolldown, where the bundler owns the output). Alongside that, verbatimModuleSyntax is the flag that ends a decade of confusion: it emits your import statements exactly as written and makes import type mandatory for type-only imports, so what you write is what runs — no more elided imports quietly removing a side-effectful module.

Barrel files. export * from "./x" aggregated into one index.ts feels tidy and is one of the most expensive habits in a large TypeScript repo. It forces the compiler and the bundler to load and type-check the entire subtree for a single symbol, it defeats tree shaking whenever any file in the barrel has a side effect (or lacks sideEffects: false), it creates import cycles that are invisible at the call site, and it inflates cold-start in serverless because require-ing the barrel pulls in everything. The measurable version of this argument: on large repos, deleting barrels is routinely worth double-digit percentages of type-check time. The related trap is thinking TypeScript 7's Go compiler makes this a non-issue — it makes the check 10× faster, but the bundle-size and cycle problems are unchanged, and 10× faster on a graph that is 5× larger is not a win.

Interview Q&A — 07

What is a live binding and where does it actually matter?

An ESM import is a reference to the exporter's binding, not a copy of its value, so if the exporting module reassigns the variable later, every importer observes the new value. CommonJS copies whatever the property held at require time, so a later reassignment is invisible. It matters in two real situations: lazy initialisation, where a module exports let client and assigns it after connecting — this works in ESM and silently gives undefined forever in CJS; and hot-module replacement and test mocking, where the binding indirection is what lets a replacement take effect. It is also why circular ESM imports can work as long as the value is only read inside a function, after both modules have evaluated.

Explain the dual package hazard and how you avoid it.

If a package ships both CJS and ESM builds, a dependency tree can end up loading both — your app imports the ESM entry while a transitive dependency requires the CJS one — and you get two independent copies with separate module state. The visible symptoms are instanceof returning false across the boundary, singletons initialising twice, registries and caches that only half-populate, and "two versions of React" style errors. Avoidance, in order of preference: ship ESM-only if your consumer set allows it, which is increasingly realistic now that Node's require(esm) works; otherwise keep all mutable state in a single CJS core that both wrappers import, so there is one instance regardless of entry; and always define exports so there is exactly one entry per subpath rather than a filesystem people can pick from. Tools like publint and arethetypeswrong in CI are the cheap way to keep the contract honest.

What does verbatimModuleSyntax do and why would you turn it on?

It stops TypeScript from deciding for you which imports are types. Historically the compiler elided any import whose bindings were only used in type positions, which meant an import kept for its side effects could silently vanish, and the emitted module format could differ from what you wrote. With verbatimModuleSyntax, import and export statements are emitted exactly as written and type-only imports must be marked import type — so the emitted JavaScript is predictable, and single-file transpilers (esbuild, SWC, Node's own type stripping) produce identical output to tsc. That last point is the real reason to turn it on: it is a precondition for using a fast transpiler for the build and reserving tsc for checking, which is the standard modern pipeline. It replaced the older, more confusing pair importsNotUsedAsValues and preserveValueImports.

nodenext, bundler, node16 — which module resolution do you pick?

nodenext for anything Node actually runs or that you publish as a library: it models Node's real algorithm, including exports/imports conditions, the type field, and the rule that relative specifiers need file extensions — which is exactly the strictness you want when the output has to run unbundled. bundler for application code that a bundler compiles, because it allows extensionless specifiers and exports conditions without imposing Node's ESM/CJS file-format rules. node16 is effectively frozen at Node 16 semantics; node10 (spelled "node") is the legacy algorithm and was deprecated in TypeScript 6.0 and removed as a valid choice going forward. The mistake I see most is a library authored with bundler resolution: it type-checks fine and then fails for consumers on nodenext, because the extensionless imports it emitted are not valid ESM.

How do you migrate a large CommonJS codebase to ESM?

Incrementally, and from the leaves inward. First get the build honest: "module": "nodenext", verbatimModuleSyntax, and extensions on every relative import — TypeScript 5.7's rewriteRelativeImportExtensions makes writing ./x.ts and emitting ./x.js workable. Then convert leaf packages or directories, use .mts/.cts for the awkward files, and rely on require(esm) (Node 22.12+) so the remaining CJS can still consume converted modules — that support is what turned this from a big-bang into a gradual migration. The things that actually take the time are not the syntax: they are __dirname/__filename (import.meta.dirname), require.resolve (import.meta.resolve), Jest's CJS-centric mocking (which is why many teams take the opportunity to move to Vitest or node:test), and any code doing conditional or lazy require, which has to become dynamic import() and therefore async. I would sequence it behind a CI check that fails on new CJS files, so the boundary only moves one way.

Why are barrel files a problem, and what do you do instead?

A barrel makes one import pull the type-check and often the runtime cost of an entire subtree, creates cycles that are invisible at the call site, and blocks tree shaking whenever side effects are possible. On a large repo, removing barrels is one of the highest-leverage build-time improvements available, and it also cuts serverless cold starts because require-ing an index pulls in everything it re-exports. What to do instead: import from the concrete module path, expose a deliberately small public barrel at each package boundary (not each folder), and enforce the boundary with the exports field or an ESLint import-restriction rule rather than with a convention. If DX is the objection, editor auto-import plus path aliases gives the same ergonomics without the graph.

What are import attributes and what happened to assert?

Import attributes are the ES2025 syntax import data from "./x.json" with { type: "json" }, which tells the host how to interpret a module — currently JSON modules, with CSS and other types following in the web platform. They replace the earlier assert { type: "json" } keyword, which was renamed because the committee decided these are instructions to the loader, not assertions about it; TypeScript 6.0 deprecated the assert form and 7.0 removed it. Practically, the attribute is a security feature as much as an ergonomics one: without it, a server that flips a response's content type could turn a data import into executable code, so the host is required to check. In Node, JSON modules need the attribute; in a bundler it is usually optional but you should write it anyway so the source is portable.

How does tree shaking actually work, and what defeats it?

A bundler builds the static import graph, marks the exports reachable from the entry points, and drops the rest — which is only sound because ESM imports cannot be conditional. What defeats it: CommonJS anywhere in the chain (the graph is not statically known), a package without "sideEffects": false (the bundler must assume evaluating a module does something observable, so it keeps it), top-level code with real side effects such as registering a polyfill or mutating a prototype, re-export barrels that make everything look reachable, and class methods or object properties, which are not shaken at all — only module-level bindings are. Two practical corollaries: prefer named function exports to giant option objects in library design, and measure rather than assume, because a single mis-annotated dependency can add hundreds of kilobytes and no amount of application-side care will find it.

When is dynamic import() the right tool?

Three legitimate uses: code splitting, where a route or a heavy widget should not be in the initial bundle; genuinely conditional loading, such as a platform-specific implementation or an optional peer dependency you only need if the user configured it; and loading an ESM-only module from CommonJS when require(esm) cannot be used, typically because the target uses top-level await. What to watch: it returns a promise, so it makes the calling function async and that asynchrony propagates; the specifier should be statically analysable — a fully dynamic string defeats bundling and forces the bundler to include everything it might match; and errors are runtime, not build time, so a missing chunk after a deploy is a real failure mode that needs a retry-and-reload strategy. In a browser I would also preload predictable chunks with <link rel="modulepreload"> so splitting does not cost a round trip on interaction.

What belongs in a package's public contract, and how do you keep it stable?

The contract is the exports map plus the types each entry resolves to, the supported engines, the peer dependencies, and the documented runtime conditions (browser, node, worker). Keeping it stable is mostly mechanical: define exports so nothing beyond it is reachable, put "types" first in every condition block, ship "./package.json", and run publint and arethetypeswrong in CI so a build change cannot silently break consumers' resolution. Then add an API-surface snapshot — api-extractor or a checked-in .d.ts report — so any change to the public types shows up in a diff and forces a conscious semver decision. The organisational half matters more than the tooling: the reason packages break consumers is almost never a wrong flag, it is that nobody owned the question "is this a breaking change?"

08 The TypeScript type system

TypeScript's type system is structural, erased, and deliberately unsound. Each of those three words is a design decision you should be able to defend. Structural means compatibility is decided by shape, not by name or declaration site: anything with a { id: string } is a { id: string }, which is what makes it possible to type a language where objects are literals and duck typing is the norm. Erased means every type disappears at emit, so no runtime check comes for free — the entire content of unit 10. And unsound means the team knowingly accepts a small number of holes where the alternative would be a type system nobody would use.

The soundness holes worth naming, because interviewers use them to separate people who have read the handbook from people who have shipped: arrays are covariant (Dog[] is assignable to Animal[], and then you can push a Cat into it), method parameters are bivariant (a legacy of modelling the DOM and Array.prototype; strictFunctionTypes makes standalone function types contravariant but deliberately exempts method syntax), and index signatures lie unless you turn on noUncheckedIndexedAccess — rec[key] is typed as present even when the key is absent. None of these are bugs to fix; they are ergonomics-versus-soundness trades, and a lead is expected to know which ones their codebase has opted out of.

// Structural: no `implements` needed, no nominal identity.
interface HasId { id: string }
const row = { id: "u1", email: "a@b.c" };
const h: HasId = row;                      // fine - extra properties are OK on a variable

const h2: HasId = { id: "u1", email: "a@b.c" };
//                            ~~~~~ excess property check: object literals are checked strictly
// The rule: freshness. A literal assigned directly is "fresh" and gets the extra check;
// the same object via a variable is not. This is a usability heuristic, not a type rule.

// Covariance hole, in three lines:
const dogs: Dog[] = [new Dog()];
const animals: Animal[] = dogs;            // allowed
animals.push(new Cat());                   // compiles; dogs now contains a Cat

Narrowing is the engine

Most of the day-to-day power comes from control-flow analysis: the compiler tracks how each check refines a variable's type along each path. It understands typeof, instanceof, in, literal comparison, truthiness, Array.isArray, discriminant properties, assignment, and — since 5.5 — inferred type predicates, so a plain const isString = (x: unknown) => typeof x === "string" now narrows without you writing x is string. The two constructs you write by hand are type predicates (function isUser(x: unknown): x is User) and assertion functions (function assertUser(x: unknown): asserts x is User), and both are promises the compiler cannot verify — they are the sanctioned place to put a runtime check, and the place where a wrong implementation poisons everything downstream.

The single most valuable pattern built on narrowing is the discriminated union: a union of object types sharing a literal-typed kind field. It gives you exhaustive switch statements that fail to compile when a new variant is added, which turns "we forgot to handle the new state" from a production incident into a build error. Combine it with a never exhaustiveness check and you have the closest thing TypeScript has to an algebraic data type.

type Result =
  | { kind: "ok"; value: Buffer }
  | { kind: "retry"; afterMs: number }
  | { kind: "fail"; error: Error };

function handle(r: Result): string {
  switch (r.kind) {
    case "ok":    return `${r.value.byteLength} bytes`;   // narrowed, .value exists
    case "retry": return `retry in ${r.afterMs}ms`;
    case "fail":  return r.error.message;
    default:      return assertNever(r);                  // adding a variant breaks the build here
  }
}
function assertNever(x: never): never { throw new Error(`unhandled: ${JSON.stringify(x)}`); }

type OrderId = Branded<string, "OrderId">;

Interview Q&A — 08

What does "structurally typed" mean, and when do you need nominal typing?

Compatibility is by shape: two types with the same members are the same type regardless of their names or where they were declared. That is the right default for JavaScript, where objects are literals and most APIs are duck-typed, and it is why you can pass a plain object where an interface is expected without ceremony. You need nominal typing when two values have the same shape but different meaning and mixing them is a bug — a UserId and an OrderId that are both strings, cents versus dollars, an escaped versus unescaped HTML string, or a validated versus unvalidated email. The idiom is branding: intersect with a unique symbol-keyed phantom property so the types are incompatible at compile time and identical at runtime. I introduce brands surgically at the places where mixing has actually caused an incident, not across the whole domain, because they add friction at every boundary.

Why are excess property checks only applied sometimes?

Because they are a usability heuristic layered on top of structural assignability, not a rule of the type system. Structurally, an object with extra properties is assignable, so the compiler adds a special check only for "fresh" object literals — a literal written directly at the assignment or argument position — on the theory that extra keys there are almost always typos or misunderstandings. Assign the same literal to a variable first and the freshness is gone, and so is the check. This surprises people, and the honest framing is that it is a deliberate trade: catching colour/color typos at the point of writing is worth an inconsistency. When you need the check to survive, the tools are satisfies at the definition site or a mapped type that explicitly forbids extra keys.

Explain variance in TypeScript and where it is unsound.

For function types under strictFunctionTypes, parameters are contravariant and return types covariant, which is the sound rule — a handler that accepts any Animal can stand in where a Dog handler is needed, but not the reverse. Two deliberate holes remain. Methods declared with shorthand syntax are checked bivariantly, because Array<T>, the DOM and thousands of existing interfaces depend on it. And mutable arrays are covariant: Dog[] is assignable to Animal[], after which pushing a Cat corrupts the original. The practical defence is readonly T[] in parameter positions, which is covariant and safe because there is no way to write; that one habit removes most real variance bugs. Since TypeScript 4.7 you can also annotate type parameters with in/out, which mostly helps compiler performance on large generic types rather than changing checking.

Type predicate versus assertion function versus as — when do you use each?

as is a bare claim: no check, no emit, and the compiler simply believes you — appropriate only when you genuinely know something the type system cannot express, and worth a comment saying what. A type predicate (x is User) is a function whose body does a real runtime check and whose signature tells the compiler what a true result means; it is the right shape for filtering and branching. An assertion function (asserts x is User) throws instead of returning false, which is right at a boundary where continuing makes no sense — parsing a config, validating a webhook. The risk that unites all three is that the compiler cannot verify the body, so a predicate that checks only one field is a lie that propagates; that is exactly why I prefer schema validators, which generate the predicate from the schema so the check and the type cannot drift apart.

What is noUncheckedIndexedAccess and would you enable it?

It adds | undefined to the result of indexing an array or a type with an index signature, because the compiler otherwise assumes every index is populated — const x: string = arr[999] type-checks today and is wrong. I would enable it, and it is the first non-strict flag I reach for, because "undefined from an array or a map lookup" is a top cause of real runtime errors. It is noisy: loops with an index, and record lookups where you have just checked in, both need adjusting. Mitigations that keep it pleasant: iterate with for…of and entries() rather than indices, use Map where the API already models absence, and use a small typed helper for "get or throw" at the places where absence is genuinely impossible. It is worth noting it does not track that if (arr[i]) proves anything about a later arr[i], so destructure once.

How do you model exhaustiveness, and why is it worth the ceremony?

Discriminated union plus a default branch that assigns the narrowed value to never, usually through an assertNever(x: never): never helper. Because the union is narrowed away by the handled cases, the default branch has type never — until someone adds a variant, at which point the assignment fails and every unhandled site becomes a compile error. It is worth the ceremony because it converts the most common class of feature-addition bug ("we added a status and three switch statements didn't know") from something you hope tests catch into something the build catches, at zero runtime cost. The version I insist on also throws at runtime rather than silently returning, because the compile-time guarantee disappears the moment data arrives from a network boundary where an unknown variant is entirely possible.

interface or type?

For a plain object shape, either — the differences are small enough that consistency matters more than the choice. interface can be augmented via declaration merging, which you need for declare module augmentation of libraries and globals, and which is a downside inside your own code because the shape can be extended from anywhere; it also composes via extends, which the compiler can cache by name and which historically produced better error messages on deep hierarchies. type is required for unions, tuples, mapped types, conditional types and template literal types, and it can express things interface cannot. My rule is interface for extensible object contracts and public API surfaces, type for everything else, and I would not spend team time relitigating it.

You inherit a 400k-line codebase with strict: false. What is your plan?

Measure first: how many files, how many anys, and which modules have caused null-related incidents — that last one decides the order. Then set up the ratchet rather than the big bang: a base tsconfig with strict: true, and per-package or per-directory configs that opt out where necessary, so all new code is strict from day one and the exceptions are visible and enumerated. Convert leaf-first, because types flow from dependencies upward, and use @ts-expect-error with an owner and a ticket for anything that cannot be fixed now, tracked as a count in CI that is only allowed to decrease. Do not accept ! and as as fixes — they satisfy the compiler and keep the bug — and do not couple the migration to a feature deadline. Realistically this is quarters, not weeks, on that size of codebase, and the way to keep it funded is to report it as defects prevented rather than as percentage typed.

What is declaration merging and when is it legitimate?

Multiple declarations of the same name in the same scope combine: interfaces merge their members, namespaces merge and can attach to functions or classes, and declare module can augment another package or the global scope. The legitimate uses are augmentation you do not own — adding your properties to Express's Request, extending ProcessEnv, declaring a plugin's addition to a framework interface, and adding types for an untyped module. Inside your own codebase it is mostly a liability: a reader cannot see the whole shape of a type from its declaration, and a stray merge in a test file can widen a production type silently. I also flag global augmentation in library code as a code smell, because it forces the augmentation on every consumer.

Where does the type system genuinely fail you, and what do you do about it?

Four places, all at boundaries. Anything crossing the process edge — HTTP responses, message queues, files, localStorage, environment variables — has a type that is a claim, not a check, so it needs runtime validation (unit 10). any from an untyped dependency spreads silently through inference, so I lint against it and prefer unknown plus narrowing at the seam. The erasure means no reflection: you cannot ask "what fields does T have" at runtime, which is why ORMs and DI containers either generate code or ask you to repeat the shape as a value. And the deliberate unsoundness — array covariance, method bivariance, unchecked index access — means "it compiles" is not "it is correct". The lead-level framing is that the type system is a tool for expressing intent inside a trust boundary, and every place data crosses that boundary needs a validator, a test, or both.

09 Generics and type-level code

TypeScript's type layer is a small, lazily-evaluated functional language. Generics are its functions, conditional types are its if, infer is its destructuring, mapped types are its map, and recursion is its loop. Once you see it that way, the utility types stop being magic incantations to memorise — Partial, Pick, Omit, ReturnType and Awaited are twenty lines of that language that ship in lib.d.ts, and you can read and write them.

A generic parameter is a placeholder the compiler fills by inference from the call site. The lever that matters is where inference happens: a parameter position is an inference site, a return position is not, and a parameter mentioned in two positions has to reconcile candidates from both. That is why function id<T>(x: T): T infers cleanly and function make<T>(): T is a lie — it will infer unknown or whatever the caller annotates, which is an as wearing a costume. Two modern tools tighten this: const type parameters (TypeScript 5.0), which make a call site infer literal types as if the argument were written as const, and NoInfer<T> (5.4), which excludes a position from inference so one argument can be the source of truth for another.

// Inference control: `const` keeps literals, NoInfer stops a second site from widening.
declare function pick<const K extends readonly string[]>(keys: K): K[number];
pick(["a", "b"]);        // "a" | "b"   (without `const`: string)

declare function withDefault<T>(items: T[], fallback: NoInfer<T>): T;
withDefault([1, 2, 3], 0);     // T is number; the fallback cannot widen it

// Conditional + infer: destructuring at the type level.
type ElementOf<T> = T extends readonly (infer E)[] ? E : never;
type Unwrap<T> = T extends Promise<infer U> ? Unwrap<U> : T;   // recursion

// Mapped type with key remapping (TS 4.1+) and a template literal type.
type Events<T> = { [K in keyof T & string as `on${Capitalize<K>}`]: (value: T[K]) => void };
type H = Events<{ open: boolean; id: string }>;
//   { onOpen: (v: boolean) => void; onId: (v: string) => void }

Distributivity is the rule that catches almost everyone once. A conditional type whose checked type is a naked type parameter distributes over a union: T extends X ? A : B with T = "a" | "b" evaluates each member separately and unions the results. That is usually what you want (it is how Exclude works) and occasionally exactly what you do not — when you want to ask a question about the union as a whole. The fix is to defeat distribution by wrapping both sides in a tuple: [T] extends [X] ? A : B. That one-line idiom is the difference between IsNever<never> returning never and returning true.

Where type-level code earns its keep — and where it does not

It earns its keep when the types are derived from a single source of truth rather than hand-maintained in parallel: a router that extracts :id from a path string so handlers get typed params, a query builder whose result type follows the selected columns, an event emitter whose on and emit signatures come from one map, a config loader whose output type is the schema. In every one of those, the payoff is that adding a field to the source automatically updates or breaks everything downstream.

It stops earning its keep when it becomes a puzzle. Deeply recursive conditional types hit the instantiation depth limit (Type instantiation is excessively deep and possibly infinite), they are the number-one cause of pathological compile times, and — this is the part that matters for a team — a type nobody but the author can read is a maintenance liability that shows up as "I'll just cast it". TypeScript 7.0's Go compiler makes checking 8–12× faster, which raises the ceiling but does not change the judgement: the constraint on type-level cleverness was always the next engineer, not the CPU.

Solution sketch

(1) Partial<T> = { [K in keyof T]?: T[K] }; Pick<T, K extends keyof T> = { [P in K]: T[P] }; Exclude<T, U> = T extends U ? never : T (its whole behaviour is distributivity); ReturnType<T extends (…a: any) => any> = T extends (…a: any) => infer R ? R : any. If you can write these four, you can read any type in a modern library, which is the actual goal.

(2) IsString<"a" | 1> is boolean (that is true | false, one per union member), and IsString<never> is never — distributing over an empty union produces an empty union, which is the classic "why is my type never" bug. The tupled version [T] extends [string] gives false and true respectively, because it asks about the union as a whole.

Interview Q&A — 09

Explain distributive conditional types and how to turn distribution off.

When the checked type of a conditional is a naked type parameter and it is instantiated with a union, the conditional is applied to each member independently and the results are unioned. Exclude<T, U> = T extends U ? never : T works entirely because of this. Two consequences: distributing over never, which is the empty union, yields never — the usual explanation for a helper that mysteriously evaluates to nothing; and you sometimes want to ask about the union as a whole, for which you defeat distribution by wrapping both sides in a one-tuple, [T] extends [U] ? … : …. Knowing both directions is what lets you write utility types that behave correctly on unions instead of only on the single type you tested with.

What are const type parameters and NoInfer for?

Both are inference controls. A const type parameter (TypeScript 5.0) makes the compiler infer the argument as if it had been written with as const, so pick(["a","b"]) gives "a" | "b" rather than string[] — it removes the need for callers to remember as const at every call site, which is exactly the kind of ergonomics fix that decides whether a typed API is adopted. NoInfer<T> (5.4) marks a position as a non-inference site, so when a type parameter appears in two places you can designate which one is authoritative: a default value cannot widen the type that the data argument established. Before these existed people used overloads or a dummy second type parameter, both of which produced worse error messages.

How do you debug a slow TypeScript build?

tsc --extendedDiagnostics first, to see where the time goes — parse, bind, check, or emit — and --generateTrace plus the analyser to find the specific types and files that dominate. The usual culprits are large union or intersection cross-products, deeply recursive conditional types, huge inferred types from object literals that should have been annotated, @types packages pulled in wholesale because types was not restricted, and barrel files that force whole subtrees into every compilation. The structural fixes are project references or a package-per-domain layout so incremental builds are small, explicit return-type annotations on exported functions (which also lets isolatedDeclarations generate .d.ts in parallel), and simplifying the worst types rather than trying to speed everything up. And the 2026 answer that has to be part of this: moving to TypeScript 7's native compiler is typically an 8–12× reduction on its own, which for many teams is the single largest available win — with the caveat that if you depend on the compiler API, you wait for 7.1.

When would you write a mapped type with key remapping?

When the derived shape's keys are a function of the source's keys: turning a state object into an event map (open → onOpen), generating getters, prefixing or namespacing a config, or filtering keys by their value type using as K extends … ? K : never. The payoff is that the two shapes cannot drift, because one is computed from the other. Two details worth knowing: remapping makes the mapped type non-homomorphic, so it stops automatically preserving readonly and optionality — you have to reapply modifiers deliberately; and mapping with template literals over a large key union multiplies quickly, so it is a place where compile time can quietly get away from you.

Where do you draw the line on type-level complexity?

My test is whether a competent teammate can predict what the type does from reading it, and whether a wrong usage produces an error message they can act on. Deriving route params from a path literal passes: it is one recursive type, the error when you mistype a param is comprehensible, and it removes real duplication. A type-level SQL parser does not: the errors are unreadable, the compile cost is real, and the failure mode is that people cast around it. The framing I use with teams is that types are documentation the compiler checks — so if a type is harder to read than the invariant it encodes, express the invariant as a runtime assertion plus a test instead. I would also rather ship a simpler type with an explicit escape hatch than a perfect one that makes every consumer fight it.

What is isolatedDeclarations and why does it matter now?

It (TypeScript 5.5) requires every exported symbol to have an explicit type annotation so that a .d.ts file can be produced from a single file without type-checking the whole program. That unlocks parallel and incremental declaration emit and lets non-TypeScript tools — esbuild, SWC, Oxc — generate declarations correctly, which is the last thing that used to force tsc into the build path of a monorepo. The cost is annotation churn on public APIs, which is a real but mostly one-time expense and has the side benefit of stabilising your public types and speeding up inference generally. In a large monorepo where package builds serialise on declaration emit, this is often a bigger practical win than any single type simplification.

Explain Awaited<T> and why it needed to be a built-in.

Awaited<T> recursively unwraps promises and thenables, so Awaited<Promise<Promise<string>>> is string. It had to be built in because the correct semantics are subtler than the obvious T extends Promise<infer U> ? U : T: it must handle arbitrary nesting, custom thenables whose then has its own signature, unions where only some members are promises, and any/never. Before it existed, every library shipped a slightly different, slightly wrong version, and the divergences showed up as bad inference in Promise.all results. It is a good example of the general lesson: when a type-level function turns out to have many edge cases, check whether the standard library already got it right.

How do you type a function whose return shape depends on its arguments?

Preference order: a generic with a conditional return type when the relationship is a rule (parse<T extends Schema>(s: T): Infer<T>); overloads when it is a short, fixed list of discrete pairs; and a discriminated-union return when the caller should be forced to handle each case rather than being handed the right shape silently. The trap with conditional returns is that the implementation cannot easily satisfy them — inside the function the conditional is unresolved, so you usually end up with one internal as, which is acceptable if it is one line, tested, and commented. The trap with overloads is that the implementation signature is unchecked against the overload list. If neither is clean, that is usually a sign the function is doing two jobs and should be two functions — which is also the better answer for readability.

What is the difference between unknown, {} and object as a constraint?

unknown is the top type: everything is assignable, nothing can be done without narrowing — the right constraint when you accept anything and will validate. {} means "anything except null and undefined", including primitives, which surprises people who read it as "an empty object"; it is occasionally the right constraint for "must be non-nullish" but it reads badly and I would use NonNullable<unknown> or a comment. object means a non-primitive, so strings and numbers are excluded — the right constraint for things you will spread, key, or attach metadata to via a WeakMap. Choosing precisely matters because a too-loose constraint pushes the error to the call site's caller, where the message is much worse.

Someone submits a PR with a 60-line recursive type. How do you review it?

I ask three questions and let the answers decide. What invariant does it encode, and would a runtime assertion plus a test encode it as well? What does the error message look like when a caller gets it wrong — I will actually write a wrong call and read the output, because an unreadable error is worse than no type. And what does it cost: run --extendedDiagnostics before and after, because a single type can add seconds to every build and every editor keystroke. If it passes all three, it goes in with a comment explaining the intent and a test file of positive and negative cases using @ts-expect-error, so the next person can change it safely. If it fails one, the usual outcome is a simpler type plus a validator — and I would say that out loud as a trade we are making deliberately, not as a rejection of the author's work.

10 Types at the boundary

Every TypeScript type is erased before the code runs, so at every point where data enters your process the type is a claim, not a check. const user = await res.json() as User is the most common lie in the ecosystem: json() returns any, the assertion silences the compiler, and from there the wrongness propagates through inference into code that looks fully typed. The whole discipline of this unit is one idea, borrowed from Alexis King: parse, don't validate. Do not check a value and carry on with the same loose type — transform it into a value whose type proves the check happened, and make the unparsed form unrepresentable past the boundary.

The boundaries are more numerous than people first list: HTTP request bodies, query strings and headers; responses from services you do not control (including your own, across a deploy skew); message-queue payloads; database rows, especially from a schemaless store or a raw query; files and CSV; process.env; localStorage and cookies; postMessage and worker messages; and anything from a third-party SDK typed as any. A common failure at lead level is validating the public API carefully and treating the internal queue as trusted — but the queue contains messages written by an older version of your own code, which is a different schema by definition.

Errors are a boundary too

Under strict, a catch variable is unknown, which is correct: JavaScript lets you throw anything, and in practice you will receive strings, DOM exceptions, and rejected values from libraries. Modern error handling has three pieces worth knowing precisely. new Error("x", { cause: err }) (ES2022) preserves the chain without string-concatenating stack traces. AggregateError carries multiple failures — it is what Promise.any throws and the right shape for a batch operation. And Error.isError (ES2026) is the reliable brand check that instanceof Error is not, because instanceof fails across realms, across duplicated copies of a library in a bundle, and on objects from a worker.

// A typed error hierarchy plus safe narrowing.
class AppError extends Error {
  constructor(message: string, readonly code: string, options?: ErrorOptions) {
    super(message, options);
    this.name = new.target.name;            // not "Error"
  }
}

function describe(e: unknown): string {
  if (!Error.isError(e)) return `non-error thrown: ${String(e)}`;
  const chain: string[] = [];
  for (let cur: unknown = e; Error.isError(cur); cur = cur.cause) chain.push(`${cur.name}: ${cur.message}`);
  return chain.join(" <- ");
}

// Expected failures are values, not exceptions.

Interview trap

"We use TypeScript, so the API response is typed." This is the single most revealing question in a TypeScript interview, and the wrong answer is confident. Generated clients (OpenAPI codegen, GraphQL codegen, a shared types package) give you types that match the specification, not the bytes on the wire — they are still assertions, and they go stale the moment a producer deploys a change the spec did not capture, or a proxy returns an HTML error page with a 200. The nuance that separates a lead: you do not have to validate everything the same way. Validate at trust boundaries with a schema; inside the boundary, rely on types. And decide deliberately what a contract violation does — fail the request, or degrade with a metric — because for a non-critical field, hard-failing on an unexpected enum value can turn a producer's minor change into your outage.

Try it

1. Break a typed client. Take a fetch wrapper that uses as, point it at a stub that returns {"id": 1} where the type says id: string, and follow how far the wrong value travels before anything throws. Then add a schema parse and see where it fails instead.

2. Parse your environment. Replace every process.env.X! in a service with a single schema-parsed config module that runs at import time, and deliberately remove a required variable.

Expected outcome

(1) The number is usually carried a long way — through a cache key, into a template, maybe into a database — and the eventual error (id.startsWith is not a function, or a row that never matches) points at code that is entirely innocent. With the parse, you get a failure at the fetch with the exact path and expected type. That distance between cause and symptom is the real cost of as, and it is the argument that persuades teams.

(2) The service should refuse to start with a clear message naming the missing variable, rather than serving traffic and failing on the first request that needs it. Fail-fast at boot is free to implement and turns a 3am page into a deploy that never went green — and it is a good example of moving a failure earlier in time, which is the same instinct as moving it from runtime to compile time.

Interview Q&A — 10

Why is as on a parsed response dangerous, and when is as acceptable?

Because it is an unchecked promise to the compiler that switches off every downstream check, so the error surfaces far from its cause and the intervening code — which looks fully typed — is what gets blamed. It is acceptable in three narrow cases: narrowing a value you have just checked in a way the compiler cannot follow (and then a type predicate is usually better); inside the implementation of a well-tested helper whose signature is honest, such as a conditional-return generic; and in test fixtures where the shape is deliberately partial. The rule I enforce is that every as outside those cases needs a comment naming the invariant, and any as applied to data from outside the process is a review blocker.

How do you keep a schema and a type from drifting?

By having only one of them. Define the schema and derive the type with z.infer (or the equivalent), so there is nothing to keep in sync — a schema change is a type change and every consumer updates or breaks. The inverse direction, deriving a validator from a type, is not possible in general because types are erased; the tools that appear to do it (TypeBox with JSON Schema, or codegen from OpenAPI/Protobuf) actually move the source of truth outside TypeScript, which is a perfectly good answer as long as the generation runs in CI and the output is checked in or verified. What does not work is hand-maintaining an interface next to a validator: it will drift within weeks, and the drift is silent.

Where do you draw the trust boundary in a system with several internal services?

At every process edge, but with different strictness. Anything from the public internet gets full validation and rejection. Between internal services I still parse, because during a rollout the producer and consumer are different versions of the code — that is not a hypothetical, it is every deploy — but I would use a tolerant reader: validate the fields I depend on, ignore unknown fields rather than rejecting them, and never fail on an added enum value I do not recognise unless it changes semantics. Inside a process, types are enough. The judgement to voice is that strict validation between internal services trades availability for correctness, and for a non-critical field that trade is usually wrong: I would rather log a contract violation with a metric and degrade than turn a colleague's additive change into my incident.

What is Standard Schema and why does it matter?

It is a minimal shared interface, agreed in 2025 and implemented by Zod, Valibot and ArkType, that exposes validation and inferred input/output types under a ~standard property. It matters because it decouples frameworks from validators: a router, a form library or an RPC layer can accept "any Standard Schema" and work with whichever library the consumer chose, instead of each ecosystem bundling its own or forcing a choice. For a lead, that changes a technology decision from "which validator do we marry" to "which validator do we start with", which lowers the cost of being wrong — and it means a bundle-size problem can be fixed later by swapping Zod for Valibot without touching the call sites.

How do you validate configuration and environment variables?

One module, parsed once at startup, exporting a frozen typed object; nothing else in the codebase reads process.env, enforced with a lint rule. The schema coerces types (PORT is a string on the way in and a number on the way out), applies defaults, marks which values are secrets so they never reach a log, and fails the process on boot with a message naming every missing or invalid variable at once rather than the first. That converts a whole class of 3am incidents into a deploy that fails its health check. The nuance for a large system is environment layering — defaults, per-environment overrides, secret-manager values — which should be resolved before the parse so there is exactly one validation point, and validated in CI against each environment's variable set so a missing production secret is caught before the rollout.

Zod, Valibot, ArkType, TypeBox — how would you choose?

By the constraint that actually binds. If bundle size is the constraint — a widget, a mobile web app — Valibot's modular design tree-shakes to a small fraction of Zod's footprint, and that is decisive. If you need JSON Schema for OpenAPI, AJV compilation, or an LLM function-calling contract, TypeBox produces it natively rather than through a converter. If the constraint is developer familiarity and ecosystem integrations, Zod is the default and its error objects are the best to render into form messages. ArkType is compelling when you want one syntax for the type and the validator and you value its inference speed. Because they all implement Standard Schema now, I would pick the ecosystem default, keep the schemas in one module, and treat a later swap as a contained refactor rather than a rewrite.

How should errors be modelled in a TypeScript codebase?

Split expected failures from unexpected ones. Expected outcomes — validation failed, not found, insufficient permission — are values: a discriminated union return type, so the compiler forces callers to handle them and the failure is part of the signature. Unexpected failures — a bug, a dependency down, out of memory — are exceptions, because there is nothing useful for an intermediate frame to do and the right behaviour is to propagate to a boundary that logs, traces and returns a 500. For the exceptions, a small class hierarchy extending Error with a stable machine-readable code, cause chaining so the original is never lost, and no PII in the message. I would resist a full Result type everywhere — it is correct and it makes every call site noisier, and teams tend to abandon it halfway, which is worse than either extreme.

Why is catch (e: unknown) the right default, and how do you narrow?

Because JavaScript permits throwing any value, and in practice you receive strings from old libraries, DOMExceptions, rejected non-error values, and objects from other realms — so typing the clause as Error would be a lie, which is exactly what useUnknownInCatchVariables (part of strict, on by default since TypeScript 6.0) fixes. Narrow with Error.isError(e) in ES2026 runtimes, since it is a brand check that survives realm boundaries where instanceof silently returns false; then check your own code property or use a type predicate for domain errors. Always keep the original around via cause, and always have a final String(e) fallback so a non-error throw still produces a usable log line rather than [object Object].

What is the runtime cost of validation, and when does it matter?

For typical request bodies it is microseconds and irrelevant next to the I/O you just did. It starts to matter in three places: very high-throughput paths where the parse is a measurable share of per-request CPU, large payloads where a schema library walks a megabyte of JSON field by field, and cold starts where importing a heavy validator adds to startup. The mitigations are ordinary engineering — compile the schema once at module scope rather than per call (a surprisingly common bug), validate only the fields you depend on for large payloads, use a compiled validator such as AJV over a JSON Schema for the hottest paths, and stream instead of buffering when the payload is big. I would measure before optimising, because the usual result is that the validator is a rounding error and the real cost is the JSON.parse that preceded it.

A producer adds a field and your consumer starts rejecting messages. What went wrong and how do you fix it?

The consumer's schema was strict — unknown keys rejected — which makes an additive, backwards-compatible change a breaking one. That is a design error on the consuming side: for internal contracts the right posture is the robustness principle applied carefully, ignore unknown fields, require only what you consume, and treat unrecognised enum values as a known "other" case rather than an error. The fix is to loosen the schema to a tolerant reader and to add a metric for unknown fields so additions are visible without being fatal. The organisational fix matters more: schema ownership and a compatibility rule written down — additive changes are safe, removals and type changes require a version — plus a contract test in the producer's pipeline that runs consumers' schemas against sample payloads, so the failure happens in the producer's CI rather than in my consumer at 3am.

11 Compiler and toolchain

The most important structural fact about a modern TypeScript build is that type checking and emitting are separate jobs, and almost every fast pipeline separates them. A transpiler — esbuild, SWC, Oxc, or Node's own type stripping — deletes types file by file, with no cross-file knowledge, in milliseconds. tsc --noEmit builds the whole program graph and checks it, which is the slow part and the part that finds bugs. Once you see the split, the tool choices follow: transpile in the dev loop and the bundler, type-check in the editor and in CI, and never let "it builds" be mistaken for "it type-checks".

TypeScript 7: the Go rewrite

TypeScript 7.0 went GA on 8 July 2026 (7.0.2), and it is a reimplementation of the compiler and language service in Go rather than a feature release. The numbers are the headline: 8–12× faster full builds, with VS Code's own codebase dropping from 125.7 s to 10.6 s and Slack's CI type-check from 7.5 minutes to about 1.25; roughly 18% less memory; and editor error surfacing in VS Code down from ~17.5 s to under 1.3 s. It gets there through native code plus real parallelism — parsing, checking and emitting run concurrently, tuned with --checkers and --builders, with --singleThreaded for constrained environments — and the editor path is now a proper Language Server Protocol implementation rather than the old TSServer protocol.

The catch, and the thing to lead with in an interview because it is the actual adoption decision: 7.0 ships without a stable programmatic compiler API. That is planned for 7.1, expected around October 2026. Anything that embeds the compiler — typescript-eslint, ts-morph, Vue's Volar, Svelte and Astro's checkers, Angular's compiler, tsup --dts, ts-loader — cannot move until then. So the realistic 2026 posture for most teams is: adopt 7.0 for the tsc --noEmit check in CI and in the editor where you can, keep TypeScript 6 pinned for the tools that need the API, and complete the move when 7.1 lands. Saying that trade-off out loud, rather than "we upgraded to 7", is what a staff-level answer sounds like.

Running TypeScript without a build

Node now runs .ts files directly by type stripping: it removes annotations with SWC and leaves the JavaScript, without type-checking anything. It was experimental in 22, enabled by default from 22.18/24.3, and stabilised in 25.2, so on Node 24 (Active LTS) and Node 26 you can simply node script.ts. Because it only erases, it cannot handle syntax that needs code generation — enum, namespace with runtime members, and constructor parameter properties — which is precisely what erasableSyntaxOnly (TypeScript 5.8) enforces at compile time. Turning that flag on is the cheap way to guarantee your code will run under any type-stripping runtime, and it is a good default for new projects regardless.

Around that, the build tier moved to Rust. Vite 8 (12 March 2026) made Rolldown the default production bundler in place of Rollup, reported at 10–30× faster on production builds; Rolldown and Oxlint both come from the Oxc toolchain, and in June 2026 VoidZero — the company behind Vite, Rolldown and Oxc — joined Cloudflare, with a public commitment to keep the tooling vendor-neutral. On linting, ESLint plus typescript-eslint is still the reference for type-aware rules and remains pinned to TypeScript 6 until the 7.1 API; Oxlint is 50–100× faster and is designed to run alongside ESLint so you can move the fast, non-type-aware rules first; Biome 2.4 is the single-binary lint-plus-format option and has been adding type-aware rules of its own.

Interview trap

"We use esbuild/SWC/Node type stripping, so our types are checked." They are not — every one of those tools deletes types without looking at them, by design, because that is what makes them fast. A codebase can be full of type errors and build perfectly. The consequence is architectural, not cosmetic: tsc --noEmit must be a required CI job, and it must run on the whole program, not per-package with skipLibCheck hiding the seams. The second half of the trap is skipLibCheck: true, which almost everyone sets and few can justify — it skips checking .d.ts files, which is a large speedup and hides genuine conflicts between two versions of a dependency's types. It is a reasonable default; knowing that it is a trade, and that a mysterious "types don't line up" bug can be hiding behind it, is the part that gets noticed.

Try it

1. Measure your own build. Run tsc --noEmit --extendedDiagnostics and record check time and memory. Then set "types": ["node"] explicitly if it is not set, and measure again. Then install TypeScript 7 in a scratch branch and measure once more.

2. Prove the transpile/check split. Add a deliberate type error to a file, then run your bundler or node file.ts. Watch it succeed.

Expected outcome

(1) Explicit types commonly buys 20–50% because auto-enumeration was loading every @types package in node_modules including ones nothing imports. TypeScript 7 should land somewhere in the 8–12× range on top of that; if it does not, your bottleneck is probably a pathological type or a barrel-heavy graph, and --generateTrace will show which.

(2) It builds and runs, and the error only appears when you run tsc. If your CI does not run tsc --noEmit, you have just demonstrated that type errors can reach production — which is the most persuasive way to get that job added.

What actually changed in TypeScript 7.0, and would you adopt it today?

I would also do the 6.0 deprecation cleanup first, because that is what makes the switch uneventful.

Why was TypeScript 6.0 released at all if 7.0 was weeks away?

Because 7.0 removes a decade of options and changes several defaults, and dropping all of that on users at once would have made the upgrade a project rather than a bump. 6.0 is the last release on the JavaScript codebase and its job is to surface every 7.0 breaking change as a warning you can fix while everything still works: deprecations for the ES5 target, AMD/UMD/SystemJS modules, node10 and classic resolution, outFile, baseUrl, downlevelIteration and assert import syntax, plus --stableTypeOrdering so you can adopt 7.0's deterministic type ordering early and see the diff. It also flipped defaults that most projects should have set anyway — strict, module: esnext, target: es2025, and an empty types. Understanding that sequencing is a useful thing to have opinions about generally: it is how you ship a breaking change to millions of consumers.

How would you design the build pipeline for a large TypeScript monorepo?

Separate the jobs. A fast transpiler (esbuild, SWC or Rolldown via Vite) produces runnable output for dev and for the bundle; tsc --noEmit — or per-package project references with --build — does the checking, in the editor and as a required CI job. Declaration emit is the usual serialisation point in a monorepo, so isolatedDeclarations plus explicit return types lets .d.ts generation be parallel and cacheable. Above that, a task runner with content-addressed remote caching (Turborepo or Nx) so unaffected packages are not rebuilt, package boundaries enforced by exports rather than convention, and no barrel files across package lines. Then measure: --extendedDiagnostics and --generateTrace tell you whether your problem is the graph, a pathological type, or just the old compiler — and in 2026 the answer is often "just the old compiler", which makes TypeScript 7 the first thing to try.

Node can run .ts directly now. Does that remove the need for a build step?

For scripts, tools and many services, yes — Node 24 and 26 strip types by default and it is stable as of 25.2, so node server.ts works with no loader and no dist folder. What it does not do is type-check, so you still need tsc --noEmit somewhere, and it does not handle non-erasable syntax — enum, runtime namespace, parameter properties — which is why you should turn on erasableSyntaxOnly to keep the codebase compatible. For published libraries I would still build, because consumers need .d.ts files, a defined exports map and JavaScript that does not depend on the consumer's runtime supporting stripping. And for browser apps a bundler is doing far more than type removal — splitting, minification, asset handling — so the build stays. The honest summary: it removes the build step from the inner loop, which is where it hurt most.

ESLint, Oxlint or Biome?

ESLint with typescript-eslint remains the reference because type-aware rules — no-floating-promises, no-misused-promises, await-thenable, strict-boolean-expressions — catch real bugs no syntactic linter can see, and the plugin ecosystem is unmatched. Its cost is speed, and its 2026 constraint is that it is pinned to TypeScript 6 until the 7.1 compiler API. Oxlint is 50–100× faster, deliberately does not replace your formatter, and is designed to run alongside ESLint, which makes it the low-risk move: run Oxlint on every save and in a fast pre-merge check, keep ESLint for the type-aware rules on a slower job. Biome is the "one binary, one config" option covering lint and format for JS, TS, JSON and CSS, at 2.4 with a growing set of type-aware rules, and is attractive for a new project that wants to delete Prettier too. What I would not do is run two formatters, or migrate a large config wholesale for speed alone — the rules you lose are the ones that were catching things.

What does skipLibCheck hide?

It skips type-checking of all .d.ts files, including your dependencies'. It is a large speedup and almost universally enabled, and what it hides is genuine conflicts: two versions of the same @types package with incompatible declarations, a library whose types reference DOM lib types your lib setting excludes, or global augmentations from two packages that contradict each other. Those show up later as confusing errors at usage sites, or as behaviour that works in one package of a monorepo and not another. My position is to keep it on because the cost of off is real, but to have a scheduled or nightly job that runs with it disabled so the conflicts are visible somewhere, and to treat types and dependency deduplication as the real fixes.

How do you keep source maps useful in production?

Generate them, upload them to your error tracker at deploy time, and do not serve them publicly — that means hidden-source-map style output where the bundle has no sourceMappingURL, or serving maps behind authentication, because a public map hands over your source. Make sure the mapping chain survives every stage: if you transpile with SWC and then bundle with Rolldown and then minify, each step has to consume and re-emit the previous map or the stack traces point at nonsense. Tie each upload to an immutable release identifier that the runtime also reports, so a stack trace from a week-old client resolves against the right build. And check it end to end by throwing a deliberate error in staging and reading the symbolicated trace — this is one of those things that is either configured correctly or silently useless, and you only find out during an incident.

What is your position on enums?

Avoid them in new code. Numeric enums are not type-safe — any number is assignable to a numeric enum in older configurations — they generate a runtime object with a reverse mapping you did not ask for, const enum breaks under isolated-module transpilation, and none of them survive type stripping, so a codebase using enums cannot run under Node's native .ts support. The replacement is an as const object plus keyof typeof for the union, which gives you literal types, a real runtime value you can iterate, and zero non-erasable syntax; string enums are the least-bad variant if you must interoperate with existing code. Practically, I would turn on erasableSyntaxOnly in new packages so this is enforced rather than argued about, and leave existing enums alone until the file is being changed for another reason.

How do you choose a test runner in 2026?

Vitest if the project already uses Vite, because it shares the transform pipeline and config so there is one set of aliases and plugins rather than two, and its watch mode is the fastest inner loop available. node:test with Node's built-in runner when I want zero dependencies — it now covers test isolation, coverage, mocking and snapshots well enough for a backend service, and combined with type stripping you can test a TypeScript codebase with nothing installed. Jest only for existing investment, and I would flag that its CJS-centric module mocking is the single biggest friction point in an ESM migration. Whatever the runner, the things that actually determine test-suite health are unchanged: no shared mutable state between tests, real timers faked deterministically, no network by default, and a type-check job that is separate from the tests so a type error does not masquerade as a test failure.

Your CI type-check takes 12 minutes. Walk me through fixing it.

First establish where it goes: --extendedDiagnostics for the phase breakdown and --generateTrace for the hot types and files. Then take the cheap wins in order — an explicit types array, which alone is often 20–50%; incremental with the .tsbuildinfo cached between runs; project references so only affected packages rebuild; and deleting barrel files, which frequently forces the whole graph into every package. Then the structural one: TypeScript 7's native compiler, which for a pure --noEmit check is a drop-in and is typically 8–12×, and which is available to CI even while your lint job stays on 6. If it is still slow after that, the remaining cost is usually one or two pathological types that the trace names explicitly, and the fix is to simplify them rather than to buy a bigger runner. I would also check the boring things — is CI cold-installing node_modules every run, is the machine CPU-starved — because those have embarrassed me before.

12 Engine, memory, performance

V8 is a tiered JIT, and knowing the tiers explains most performance advice you will ever be given. Source is parsed (lazily — function bodies are only pre-parsed until first call) and compiled to bytecode for Ignition, the interpreter. Hot functions are compiled by Sparkplug, a non-optimising baseline compiler that is essentially a fast bytecode-to-machine-code transcription, then by Maglev, a mid-tier optimiser, and finally by TurboFan, the heavy optimiser. Each tier trades compile time for run time, so a function's speed depends on how often it has run — which is why a naive microbenchmark that runs a function ten times measures the interpreter, not the code you ship. Node 26 carries V8 14.6 (from Chromium 146), which is also where Temporal and the ES2026 Map.getOrInsert methods arrive by default.

The optimisation that matters most is inline caching over hidden classes (V8 calls them maps or shapes). Objects with the same properties added in the same order share a shape, so a property access can be compiled to "load at offset 3" guarded by a shape check. A call site that sees one shape is monomorphic and fast; two to four shapes is polymorphic and slower; beyond that it goes megamorphic and falls back to a hash lookup. This is the real reason behind advice that otherwise sounds superstitious: initialise all fields in the constructor in a consistent order, do not add properties conditionally later, avoid delete (which can force the object into dictionary mode), and keep arrays homogeneous — V8 tracks elements kinds (packed small-integer, packed double, packed object, and holey variants of each), and transitions are one-way, so one undefined hole or one string in a numeric array permanently downgrades the representation.

// Shape-stable: every instance shares one hidden class.
class Point { constructor(x, y) { this.x = x; this.y = y; this.label = ""; } }

// Shape-unstable: three different hidden classes, and the call site goes polymorphic.
function makePoint(x, y, label) {
  const p = { x, y };
  if (label) p.label = label;        // conditional property = second shape
  if (x < 0) delete p.y;             // delete = possible dictionary mode
  return p;
}

// Elements kinds are one-way transitions:
const a = [1, 2, 3];          // PACKED_SMI_ELEMENTS  - fastest
a.push(4.5);                  // PACKED_DOUBLE_ELEMENTS
a.push("x");                  // PACKED_ELEMENTS
a[10] = 1;                    // HOLEY_ELEMENTS       - and it never goes back

Memory is generational. New objects go into a small young generation collected by a copying scavenger — cheap, because most objects die young and the cost is proportional to survivors, not to garbage. Survivors are promoted to the old generation, which is collected by a mostly-concurrent, incremental mark-compact collector. Two practical consequences: allocation rate matters more than heap size, because a hot loop allocating short-lived objects drives frequent scavenges and, worse, can promote objects that a slower loop would have let die; and long-lived caches are expensive twice over, once for the memory and once because the marker must traverse them on every major GC. Node's default old-space limit is tied to available memory on modern versions but is still worth setting explicitly with --max-old-space-size in a container, because a limit above the cgroup memory limit means the OOM killer arrives before V8 ever decides to collect harder.

Measuring, not guessing

The order of operations is fixed: measure in an environment that resembles production, find the dominant cost, fix that, measure again. In Node the first-line tools are --cpu-prof and --heap-prof (which write .cpuprofile/.heapprofile files you open in Chrome DevTools), --trace-gc for collection behaviour, perf_hooks' monitorEventLoopDelay for loop lag, and a continuous profiler in production because the interesting cost is usually load-dependent. In the browser it is the Performance panel plus the Long Animation Frames API, and field data — INP and LCP from real users — rather than a lab score, because the p75 device is nothing like a developer laptop.

Microbenchmarks deserve specific scepticism. Dead-code elimination removes work whose result you never use, so measure something observable; the JIT tiers mean you must warm up and then measure; and a benchmark that allocates in a loop measures your GC as much as your code. If a change is worth making, it should be visible in a realistic end-to-end measurement — and if it is not, it is not worth the readability cost. That is the sentence to say when an interviewer offers you a "which is faster, for or forEach" question: they are within noise of each other for any realistic workload, and choosing on that basis is optimising the wrong thing.

Interview trap

Repeating old V8 folklore. "try/catch prevents optimisation", "let is slower than var", "arrow functions are faster", "always use for loops" — these were true for Crankshaft, the optimiser V8 retired in 2017, and repeating them signals knowledge that has not been refreshed in a decade. The current true statements are narrower and more useful: keep object shapes stable, keep call sites monomorphic where they are hot, avoid delete on hot objects, keep arrays homogeneous and hole-free, do not use arguments in a function you also want optimised (use rest parameters), and remember that string concatenation in a loop is fine because V8 uses rope structures but += on a string you then measure the length of forces flattening. The meta-answer that lands better than any of these: "I would profile it, because the last three performance problems I fixed were all in a different place than I expected — an N+1 query, a JSON serialisation, and a regex."

Try it

1. Make a call site megamorphic. Write a function read(o) { return o.x } and call it a million times with objects of one shape; time it. Then create six differently-shaped objects with an x and interleave them; time it again.

2. Find a leak with two snapshots. Start a small server with a module-level Map that stores each request's body keyed by request id and never deletes. Drive load, take a heap snapshot, drive more load, take a second, and use "Comparison" in DevTools sorted by delta in retained size.

Expected outcome

(1) The polymorphic version is measurably slower — usually a small multiple, not an order of magnitude, which is itself the lesson: shape discipline is worth having as a habit in hot paths and is not worth contorting ordinary code for. Make sure you consume the result so it is not eliminated as dead code.

(2) The comparison view names your Map and the retainer path shows it rooted at the module. This is the single most valuable debugging skill in this unit, because the same three-step recipe — snapshot, load, snapshot, diff by retained size, follow the retainer path — finds essentially every JavaScript memory leak regardless of what it turns out to be.

Interview Q&A — 12

Explain hidden classes and inline caches, and what they mean for how you write code.

V8 gives every object a shape describing its property layout, and objects created the same way share one. A property access site caches the shape it saw and the offset the property lives at, so a repeated access becomes a shape check plus a fixed-offset load. One shape at a site is monomorphic and fastest; up to four is polymorphic; more goes megamorphic and degrades to a dictionary lookup. What follows for code is modest and specific: initialise every field in the constructor in the same order, do not add properties conditionally after creation, avoid delete on objects in hot paths, and normalise the shape of data at the boundary rather than letting fifteen response variants flow into one hot function. What does not follow is contorting readable code everywhere — this matters at the handful of sites a profile identifies, and nowhere else.

How does V8's garbage collector work, and what does that mean for a service?

Generationally. New objects are allocated in a small young generation and collected by a copying scavenger whose cost scales with the number of survivors, not with the garbage, so short-lived allocation is genuinely cheap. Objects surviving a couple of scavenges are promoted to the old generation, collected by an incremental, mostly-concurrent mark-compact collector that does its marking off-thread but still needs pauses. Two consequences shape service design: allocation rate matters more than total heap, because promoting objects that should have died young is what makes major GC frequent; and a large long-lived heap — a big cache, a fat in-memory index — costs you on every major cycle even when it is not changing, so it shows up as periodic latency spikes rather than as a steady tax. In containers, set --max-old-space-size below the memory limit so V8 collects harder before the kernel kills you.

A Node service leaks memory. Walk me through the investigation.

Confirm it is a leak and not just a large working set: watch RSS and heapUsed over hours; a leak climbs monotonically across GCs, a working set plateaus. Then two heap snapshots under steady load, compared in DevTools by delta in retained size, and follow the retainer path of the biggest growers back to a GC root — it almost always terminates at a module-level structure. The usual suspects, in the order I find them: an unbounded cache or memo keyed by something request-scoped, event listeners added per request and never removed (the "11 listeners added" warning is the tell), timers or intervals holding closures, and a promise chain that never settles so its continuations are retained. If snapshots are impractical because the heap is huge, --heap-prof gives allocation-site sampling instead, which points at the code that allocates rather than the structure that retains. The fix is almost always ownership: give the cache a bound and an eviction policy, tie listeners to an AbortSignal, and use WeakMap where the metadata should not extend a lifetime.

What actually makes a page's JavaScript slow to start?

Bytes and execution, in that order of frequency. The browser must download, parse and compile before anything runs, and compilation is roughly linear in code size, so the biggest lever is shipping less JavaScript — code splitting per route, deferring anything not needed for first interaction, and auditing dependencies, since a single date or icon library can dominate. After that it is execution: hydration work that runs on the main thread, expensive module-level side effects, and polyfills shipped to browsers that do not need them. The measurement to argue from is field data — INP and LCP at p75 from real users — because a fast local test on a fast laptop hides exactly the population that suffers. And I would frame the fix as a budget rather than a one-off: a size budget enforced in CI, so the regression is caught the week it is introduced instead of a year later.

How do you profile CPU in production without wrecking it?

Sampling, not instrumentation: a continuous profiler that takes stack samples at a low frequency has a cost in the low single-digit percent and can run permanently, which is what you want because the interesting behaviour only exists under real load and real data. Node's --cpu-prof works for a bounded window and is fine on one instance; an inspector-based profiler can be attached on demand if you can reach the process safely. Two practices make the results usable: deploy with source maps uploaded to the profiler so frames resolve to your source, and profile a canary or a single instance rather than the fleet. What I avoid is manual timing instrumentation sprinkled through the code — it biases toward the places you already suspected, and it is the reason teams spend a week optimising something that was 3% of the time.

Why are microbenchmarks so often misleading?

Three reasons that all bite at once. The JIT tiers mean an unwarmed loop measures the interpreter and an over-warmed one measures code specialised to your synthetic input in a way it never will be in production. Dead-code elimination deletes work whose result is unobserved, so the "faster" option is often the one the optimiser noticed it could skip. And the allocation behaviour of the benchmark harness itself — plus GC timing — frequently dominates the difference you are trying to measure. On top of that, benchmarks use uniform data, while real code sees polymorphic shapes and cold caches. My rule is that a performance claim needs an end-to-end measurement on realistic data, and that a microbenchmark is only useful for confirming a mechanism you have already identified in a profile.

When are typed arrays and ArrayBuffer the right tool?

When the data is numeric, large, and either binary on the wire or shared with another thread. A Float64Array stores raw doubles contiguously with no per-element object header, which is a large memory and cache-locality win over a JavaScript array of numbers, and it is the only representation you can hand to a worker without copying — transferring an ArrayBuffer is O(1) and detaches it from the sender, while structured-cloning a large object graph is genuinely expensive. Concretely: binary protocol parsing, image and audio processing, WebGL and WebGPU buffers, hashing, and shared state under SharedArrayBuffer with Atomics. What to watch: they are fixed-length and untyped in the domain sense, so you are managing offsets by hand, and SharedArrayBuffer requires cross-origin isolation headers in browsers. For a few thousand numbers a plain array is fine and clearer.

What is the cost of JSON.parse and JSON.stringify at scale, and what do you do about it?

Both are synchronous and roughly linear in payload size, so on a 20 MB body they block the event loop for a noticeable fraction of a second, and stringify additionally allocates the entire output string before anything is written. In a service that is the classic hidden long task: CPU looks moderate, p99 is terrible. The remedies in order: do not move the data at all if you can avoid it (pagination, field selection, or a binary format such as Protobuf or MessagePack where volume justifies it); stream instead of buffering, using a streaming JSON parser or Response.body so memory and latency stay bounded; move the work to a worker thread if it must be synchronous; and cache the serialised form when the same object is sent repeatedly, since serialisation is often more expensive than the fetch it followed. I would also check that we are not serialising then re-parsing internally, which is a surprisingly common accident in logging and in cache layers.

What is the difference between event-loop lag and CPU saturation, and why does it matter operationally?

Loop lag measures how long a scheduled callback waits beyond its due time — it goes up when the current stack is busy or when the queue is deep. CPU saturation measures the core being full. They diverge in both directions: a single-threaded process can be at 40% CPU with terrible lag because the work arrives in long blocking bursts, and it can be at 100% CPU with low lag because it is genuinely saturated with small units of work. Operationally the distinction determines the fix — long tasks need to be broken up or moved to workers, saturation needs more instances or less work per request — so I put both on the dashboard and alert on lag percentiles, not on CPU. It is also the metric that tells you whether adding replicas will help at all, which is the question a manager is really asking during an incident.

Your service's p99 doubled after a release with no obvious hot spot. How do you proceed?

Bisect on evidence rather than on intuition. First confirm the change is real and in our code: compare the canary against the previous version on the same traffic, and check whether a dependency's latency moved at the same time. Then look at the shape of the regression — a uniform shift suggests more work per request, a heavier tail suggests GC pauses, lock-step spikes suggest a periodic job or a cache expiry stampede. Pull a CPU profile from a canary and diff it against one from the old version, because a diff of two profiles finds things neither profile alone makes obvious; check GC traces and loop lag for the pause hypothesis; and check allocation rate, since a new per-request object or a wider log line can push the heap into more frequent major collections. If nothing shows, I look at what changed that is not code: a dependency bump, a Node version, a config value, an instance-type change. And I would say plainly that reverting first and investigating second is usually the right call when customers are affected — the investigation is easier with the pressure off.

13 The big Q&A

Twenty-two questions that do not belong to any single building block: the architecture calls, the security questions, the migration realities, and the "how would you lead this" scenarios that separate a senior answer from a principal one.

Architecture & ecosystem decisions

Would you start a new backend service on Node, Deno or Bun in 2026?

Node, unless there is a specific reason not to — Node 24 is Active LTS with support to April 2028, Node 26 becomes LTS in October 2026, and the ecosystem, hiring pool, observability tooling and operational knowledge all assume it. The things that used to be Deno's and Bun's differentiators have largely landed in Node: native TypeScript execution via type stripping, a built-in test runner, fetch, watch mode, and a permission model. I would choose Bun where startup time and its integrated toolchain genuinely dominate — short-lived CLI tools, some edge workloads — and Deno where its permissions model and standard library are a real fit, typically for untrusted-ish scripting. The decision I would push back on is picking a runtime for benchmark numbers: the difference almost never survives contact with a database, and the cost of being the only team on a different runtime is paid every week in tooling gaps.

How do you decide what belongs in a shared internal package versus duplicated in each service?

My test is whether the thing has a single correct definition that changes for one reason. Wire contracts, auth token handling, telemetry conventions and domain identifiers qualify — divergence there is a real bug. Utility helpers and "our React components" often do not, because they end up as a coupling surface that forces every consumer to upgrade in lockstep for changes most of them do not want. When I do create a shared package, I make it small, versioned semantically, published with a defined exports map, and owned by a named team with a deprecation policy — an unowned shared package becomes a bottleneck within two quarters. And I would rather duplicate a hundred lines than create a dependency that makes two teams coordinate a release, which is a trade I would state explicitly in a design review because it reliably surprises people.

Monorepo or polyrepo for a TypeScript estate?

Monorepo, in most organisations, because the dominant cost in a polyrepo is cross-repo change: a shared type change becomes a chain of PRs, version bumps and skew windows, and refactoring across boundaries stops happening. What makes a TypeScript monorepo work is specific: project references or a build system with content-addressed remote caching so CI is proportional to what changed, explicit package boundaries enforced by exports rather than convention, no barrel files across package lines, and code ownership so "everyone can edit everything" does not mean "nobody owns anything". What makes it fail is treating it as one big program — a single tsconfig over 400k lines, a test suite that runs everything on every commit, and a release process that versions the world. Polyrepo remains right when teams genuinely ship independently on different cadences with a stable contract between them, and when the org's tooling investment cannot support the monorepo machinery.

Where do you draw the line between the type system and runtime tests?

Types prove shape and reachability cheaply, everywhere, at every keystroke; tests prove behaviour on examples. So I use types for anything expressible as a shape or a state — discriminated unions for state machines, exhaustive switches, branded identifiers, readonly for immutability intent — because those checks are free and total. I use tests for behaviour, boundaries and integrations: what the function actually computes, what happens on a malformed payload, whether the query is correct. The failure I look for is teams spending days on a type that encodes an invariant a three-line assertion and one test would cover better, and the opposite failure of a thousand tests re-checking that a field is a string. A useful heuristic to say out loud: if getting it wrong produces a compile error the author sees in under a second, it belongs in types; if it needs data to demonstrate, it belongs in a test.

Security

How do you manage supply-chain risk in an npm-based estate?

Assume compromise is a matter of when — the 2025 incidents where popular packages such as chalk and debug shipped malicious versions via maintainer account takeover made that concrete for everyone. The controls that actually help: commit lockfiles and install with npm ci so builds are reproducible; disable lifecycle scripts by default (--ignore-scripts, with an allowlist) since that is the usual execution vector; pin or at least range-limit and use a delay window before adopting new versions, so the community finds the bad release before you do; verify npm provenance attestations where publishers supply them; run npm audit and a proper SCA tool in CI but treat the output as triage, not gospel; and mirror through an internal registry so a yanked or poisoned package cannot break or infect a build retroactively. Above the tooling, the organisational control is a dependency budget — every new direct dependency is a decision with an owner, because a hundred transitive packages you have never heard of is the actual attack surface.

What is your XSS defence strategy in a modern front end?

Layered, with the framework doing most of the work: contextual auto-escaping means template interpolation is safe by default, so the job is to make the unsafe path visible and rare — dangerouslySetInnerHTML and its equivalents restricted by lint rule and reviewed individually, and any HTML that must be rendered passed through a sanitiser, now increasingly the built-in setHTML/Sanitizer API rather than a library. On top of that, a strict Content Security Policy with nonces or hashes rather than unsafe-inline, which turns a successful injection into a blocked script; Trusted Types where supported, which makes assigning a raw string to a sink a runtime error and is the strongest available mitigation for DOM XSS; and the boring hygiene of HttpOnly, Secure, SameSite cookies so a successful XSS cannot trivially steal a session. I would also name the sinks people forget: javascript: URLs in a user-supplied href, srcdoc, and markdown renderers configured to allow raw HTML.

What Node-specific security issues would you check for in a review?

Five, in the order I find them. Command injection from child_process.exec with interpolated input — use execFile/spawn with an argument array. Path traversal in any file served or read from a user-supplied name — resolve and then verify the result is inside the intended root. SSRF from a server-side fetch to a user-supplied URL, which in a cloud environment reaches the instance metadata endpoint, so it needs an allowlist and DNS-rebinding-aware validation, not a regex. Prototype pollution from recursive merges of request bodies. And ReDoS from a regex applied to user input with nested quantifiers, which is a genuine single-threaded outage on a runtime with one event loop. Beyond code, I check that secrets come from a secret manager rather than baked into an image or a bundle, and that the process does not run as root in the container.

Is vm a sandbox? How would you run untrusted JavaScript?

No — Node's vm module explicitly does not provide a security boundary, and every "safe eval" wrapper built on it has been escaped, usually by reaching a constructor from an object that crossed the context boundary. If I genuinely had to run untrusted code, I would use an isolate-level boundary with a hardened API surface (isolated-vm, or a separate process), or better, a real OS or VM sandbox — a container with a seccomp profile, gVisor, Firecracker — or a WebAssembly runtime where the guest has no capabilities except what you import. In the browser the equivalent is a cross-origin iframe with a restrictive sandbox attribute, treated as a separate origin. And whichever I chose, I would add the controls that matter as much as the boundary: CPU and memory limits, a wall-clock timeout, no network by default, and no ambient credentials — because most "sandbox" incidents are resource exhaustion or credential theft rather than a clever escape.

Performance & debugging

A user reports the app "feels slow" but your dashboards are green. What do you do?

Green dashboards usually mean I am measuring the server and they are experiencing the client. So I go to field data first: INP, LCP and CLS at p75 segmented by device class, country and route, because an average hides exactly the population complaining. Then I try to reproduce with their constraints — CPU throttling and a slow network profile in DevTools, not a laptop on office wifi — and look for the specific pattern: a long task on interaction, a layout shift, a waterfall of dependent requests, an unindexed query behind one route. I would also check what "slow" means to them, because it is frequently a specific action rather than the whole app, and that single detail usually collapses the search. The structural fix afterwards is to make the client experience a first-class metric with alerting, because "the servers are fine" is not a statement about the product.

How do you debug a bug that only reproduces in production?

Increase observability before increasing guesses. Structured logs with a correlation id threaded through AsyncLocalStorage, distributed traces so I can see the request across services, and error reports with source-mapped stacks and enough context — user segment, feature flags, release id — to spot the pattern. Then I look for what is different about production rather than about the code: data shape and scale, concurrency, latency between services, cache state, a config value, a browser or device the team does not use. If it is still opaque, a feature flag lets me enable verbose logging or an experimental fix for a small percentage of traffic, which is far better than a full deploy. And I try to end the investigation with a regression test that fails on the old code — otherwise the same bug returns under a different name in six months.

What do you look for first in a slow front-end build?

Whether the type-check and the transpile are tangled together, because that is the most common single cause: a bundler plugin doing full type-checking on every change turns a 200 ms rebuild into ten seconds. Split them — transpile in the dev server, check in a separate watch process and in CI. Then the graph: barrel files pulling whole subtrees into every entry, a monolithic entry point that should be route-split, and source-map settings that are appropriate for production but not for the dev loop. Then the tools themselves, which in 2026 means Vite 8 with Rolldown as the production bundler and, for the check, TypeScript 7 — those two changes have been worth an order of magnitude for a lot of teams without any code change. What I would not do is start by upgrading tools: I would take one measurement first, because a build that is slow because of one pathological dependency will still be slow on a faster bundler.

Tooling & delivery

How do you enforce code quality without making CI a bottleneck?

Tier the checks by cost and by how often they catch something. Fast, deterministic checks run on every save and as a pre-merge gate — format, fast lint (Oxlint or Biome), and unit tests for the affected packages. Slower checks — full type-check, type-aware lint rules, integration tests — run on the merge request with caching so unaffected packages are skipped. The slowest — end-to-end, cross-browser, performance budgets — run on a schedule or pre-release, with a clear owner for failures. Everything is auto-fixable where possible, so review is spent on design rather than on style, and nothing that a machine can decide is left to a human. The rule I hold to is that a required check must be fast and must almost never be flaky, because a flaky required check trains the team to re-run rather than to read, and after that the signal is gone.

What belongs in a code review of TypeScript specifically?

Beyond the ordinary: every any and every as, which should each have a reason; non-null ! assertions, which are almost always a missing narrowing; whether new data crossing a boundary is parsed rather than asserted; whether a new union is exhaustively handled; whether a public function's return type is explicit, since inference on exported symbols slows builds and makes API changes invisible in diffs; and whether types were duplicated instead of derived — a hand-written interface next to a schema will drift. I also look for floating promises and async functions passed where a void callback is expected, which lint should catch but frequently does not if the rule is off. And I try to review the API before the implementation, because the implementation is cheap to change and the signature is not.

How do you introduce a static-analysis rule to a large codebase without a big-bang PR?

Turn it on as a warning first to size the problem, then ratchet: enable it as an error only for new and changed files, or enable it globally with an auto-generated suppression file that lists the existing violations, and make the suppression count a metric that CI forbids from increasing. Auto-fix everything the tool can fix in a separate, review-free commit so the meaningful diff is small, and add that commit to a .git-blame-ignore-revs file so history stays useful. Pick rules that catch real bugs first — no-floating-promises, no-misused-promises, exhaustive switch — rather than stylistic ones, because the first rule you introduce sets the team's expectation of whether this process is worth their time. And I would pair the rollout with an explanation of the bug class it prevents, ideally one from our own incident history.

Legacy & migration reality

You inherit a service on Node 18 with JavaScript, CommonJS and no tests. Where do you start?

Not with TypeScript. First, get a safety net and a runway: Node 18 is end-of-life, so an upgrade to 24 (Active LTS) is a security requirement with a deadline, and I need characterisation tests around the highest-risk paths before I change anything — a handful of end-to-end tests that pin current behaviour beats a hundred unit tests written against code I do not understand yet. Then observability, so I can see what the service actually does and which code paths are live; dead code is the cheapest code to migrate. Only then the type migration, and incrementally: checkJs with JSDoc types gives real checking with zero file renames, then convert leaf modules, then enable strict for new code via a ratchet. The ESM migration is a separate project with its own risk, sequenced after, and made much easier by require(esm). Throughout, I would tie each step to a business-visible outcome — the security upgrade, the incident rate — because "we are modernising" does not survive the first competing priority.

How do you handle a critical dependency that is unmaintained?

Assess before acting: how much of it do we use, is there a maintained fork or a standard replacement, and what is the actual risk — an unmaintained package with no network access and a small surface may be fine for years, while an unmaintained HTTP or crypto library is an incident waiting to happen. The options in ascending cost are pinning with a private mirror and a documented risk acceptance; vendoring the subset we use, which is often surprisingly small; adopting a maintained fork; contributing maintenance ourselves if it is strategically important; and replacing it. Whichever I choose, I put an abstraction between it and the codebase first, so the replacement is one module rather than four hundred call sites — and that wrapper is worth writing even if we never replace it, because it is also where I would add the timeout, the metric and the validation. The thing I would not do is nothing, quietly.

Half the team wants to rewrite the front end. How do you handle it?

I ask what problem the rewrite solves and insist it be stated as a measurable outcome — change failure rate, time to ship a feature, INP at p75, onboarding time — because "the code is bad" is a feeling and cannot be validated on completion. Then I look for whether the problem is the framework or the architecture, because most rewrites reproduce the original architecture in new syntax and land in the same place two years later. If the case survives that, I still would not do a big-bang: strangler-fig it, route by route behind a proxy or a shell, with both stacks live and a measurable share of traffic moving, so value ships continuously and we can stop halfway if the premise turns out to be wrong. And I would be honest with the team about the part nobody enjoys: the rewrite is also a re-derivation of years of undocumented business rules, and that, not the framework, is what makes rewrites overrun.

Judgment & scenarios

How would you introduce TypeScript to a skeptical JavaScript team?

By making it useful before making it mandatory. Start with checkJs and JSDoc annotations, which gives real type checking on existing .js files with no renames, no build change, and an immediate payoff in editor autocomplete — most of the objection is to disruption, not to types. Turn on the checks that find live bugs first, show the actual defects it finds in our own code, and let the team see the editor experience improve. Then convert one module the team already dislikes maintaining, so the first TypeScript file is the one that most obviously benefits. What I would avoid: converting everything with any, which produces all of the friction and none of the benefit and is the reason most skeptics are skeptical; mandating strict on day one; and arguing about it in the abstract. The measure of success is that someone who resisted it asks for the next module to be converted.

What do you do when the team disagrees about a technical decision and you have to call it?

Separate reversible from irreversible. If it is reversible — a lint rule, a test runner, a folder convention — I timebox the discussion, pick, write down why, and move, because the cost of the debate exceeds the cost of being wrong. If it is not easily reversible — a runtime, a data model, a public API, a framework — I want the disagreement written down as options with trade-offs and a recommendation, so we are arguing about the same thing, and I want the strongest version of the case I disagree with stated by someone who holds it. Then I decide, name the assumption that would change my mind, and set a review point. What I try hard not to do is let seniority end the discussion, or let it run indefinitely because nobody wants to overrule anyone — both produce the same outcome, which is that the team stops bringing decisions forward.

Production is down and the last deploy is the prime suspect. Walk me through your first fifteen minutes.

Roll back first if the deploy is a plausible cause and the rollback is safe — mitigation before diagnosis, always, because the investigation is easier without customers on fire. In parallel, establish scope and impact from the dashboards (which endpoints, which regions, what percentage) so I can communicate something concrete, and get one person on comms so the rest of us are not answering the same question repeatedly. Then check the obvious correlations: deploy time versus error onset, config or flag changes, a dependency's status page, and whether the errors are ours or a downstream's. I state hypotheses out loud with their disconfirming evidence so we do not all anchor on the first idea, and I keep a running timeline as we go because reconstructing it afterwards is always worse. Afterwards: a blameless review focused on what made the failure possible and what made it hard to see, and one or two concrete actions with owners — not fifteen, because fifteen means none.

What do you consider the biggest risk in JavaScript codebases today?

Accumulated dependency surface. A typical application ships thousands of transitive packages, most of them never audited by anyone on the team, and each one is a supply-chain vector, a bundle-size cost, a maintenance liability and a possible reason you cannot upgrade a runtime. The 2025 npm compromises made the security half concrete, but the slower damage is that a large dependency graph makes every upgrade a negotiation and eventually freezes the codebase. What I do about it: a dependency budget with a named approver, a preference for the platform where it now suffices — fetch, Intl, Temporal, structuredClone, node:test — over a package, periodic pruning as real scheduled work, and abstractions around the dependencies most likely to need replacing. It is unglamorous, and it is the difference between a codebase that can adopt Node 26 and TypeScript 7 in an afternoon and one that cannot.

What would you flag in a code review that most reviewers miss?

Things that are correct today and fragile tomorrow. An async function with no timeout or cancellation path, which is fine until the dependency slows down. An unbounded cache or queue, which is fine until traffic doubles. A Promise.all over a list whose length comes from user input. A schema that rejects unknown fields between internal services, which turns a colleague's additive change into my outage. Error handling that logs and continues, leaving the system in a state nobody designed. A new any at a boundary, which silently un-types everything downstream. And the non-code one I care most about: a change that is correct but that the next person cannot understand without the author — because at lead level the thing I am optimising is not this commit, it is the team's ability to change this code in a year.
