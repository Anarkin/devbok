01 Async, promises & the event loop

This is the single most-probed area of the topic and the one that separates levels fastest: everyone can use await, few can say what it schedules. Interviewers test it because every real JavaScript bug of consequence — a frozen UI, a 30-second p99, a memory leak, a lost error — is an async bug. Screeners want "single-threaded, non-blocking, callback queue"; mid level wants correct output-order reasoning and Promise combinator choice; senior wants cancellation, concurrency limits and backpressure; principal wants event-loop starvation diagnosed from production symptoms and a retry policy that does not amplify an outage.

Explain the event loop. What is the difference between a macrotask and a microtask?screener

JavaScript runs on one thread with one call stack. When the stack empties, the event loop takes the next task (macrotask) from the task queue — a timer callback, an I/O completion, a DOM event — and runs it to completion. Crucially, after every task (and, in browsers, before rendering), the engine drains the entire microtask queue: promise reactions, queueMicrotask callbacks, MutationObserver records. Microtasks can enqueue further microtasks, so the queue is drained until empty, which is why an infinite microtask loop hangs the page in a way an infinite setTimeout(0) loop does not.

The practical consequence: promise continuations always run before the next timer, and nothing — not rendering, not input — happens while your synchronous code or your microtask chain is running.

console.log('1');
setTimeout(() => console.log('4 – macrotask'), 0);
queueMicrotask(() => console.log('3 – microtask'));
console.log('2');
// 1, 2, 3 – microtask, 4 – macrotask
Follow-ups
  • Where does rendering fit? Between tasks, after the microtask queue is drained — roughly once per frame; a long microtask chain delays paint just like a long task does.
  • Is setTimeout(fn, 0) really 0 ms? No: HTML clamps nested timers to ≥4 ms after five levels of nesting, and the callback only runs when the loop reaches it.
  • Does async make JavaScript multi-threaded? No. Concurrency, not parallelism; parallelism needs Web Workers or worker_threads.
Common wrong answer"setTimeout(fn, 0) runs the callback immediately after the current line" — or the subtler version, that promises and timers share one queue in FIFO order. Candidates who believe this cannot predict output order and write race conditions they cannot explain.
What does await actually do, and what does an async function return?screener

An async function always returns a promise; a return v resolves it with v, a throw rejects it. await suspends the function, registers a continuation as a microtask on the awaited value, and returns control to the caller — the rest of the function body becomes the .then callback. Awaiting a non-promise still yields to the microtask queue, so await 1 is not free. The function resumes with the fulfilled value, or the await expression throws the rejection reason, which is what makes try/catch work across async boundaries.

async function f() {
  console.log('a');          // synchronous, runs on call
  const x = await 1;         // yields here, even for a plain value
  console.log('c', x);       // microtask
  return x + 1;              // resolves f()'s promise
}
f().then(v => console.log('d', v));
console.log('b');            // a, b, c 1, d 2
Follow-ups
  • Is return await p ever different from return p? Yes — inside try, only return await p lets the local catch see the rejection; outside a try it just costs one extra microtask tick.
  • Top-level await? Legal in ES modules only (ES2022); it makes the module itself async and delays every importer.
  • Does async change the function's synchronous part? No — everything before the first await runs synchronously on call.
Common wrong answer"await blocks / pauses the thread." It suspends one function; the thread keeps running everything else. Saying "blocks" signals a mental model borrowed from threads, and it leads straight to code that awaits in a loop and then blames the network.
Predict the output: mixed synchronous code, timers and promises.mid

The trick is to trace three phases in order: the current synchronous run-to-completion, then the microtask drain, then the next macrotask. Promise callbacks registered while microtasks are draining still run in this drain. await is a .then, so it queues a microtask exactly like an explicit one.

console.log('script start');
setTimeout(() => console.log('timeout'), 0);
Promise.resolve().then(() => console.log('p1')).then(() => console.log('p2'));
(async () => { console.log('async start'); await null; console.log('after await'); })();
console.log('script end');
// script start, async start, script end, p1, after await, p2, timeout

Walk it out loud: synchronous logs first (script start, async start, script end), then the microtask queue in registration order — p1 was queued before the await null continuation, and p2 is only queued once p1 returns — then the timer.

Follow-ups
  • Why does p2 come after after await? Each .then queues its continuation only when the previous one settles, so chains interleave with other microtasks.
  • What if you await a thenable instead of a promise? It costs extra ticks — the engine calls then through PromiseResolveThenableJob.
  • Does this ordering differ between Node and browsers? Microtask semantics are identical; only host tasks (timers, setImmediate, rendering) differ.
Common wrong answerPutting timeout before the promise logs because "the timer was registered first". Registration order does not matter across queues — the microtask queue is fully drained before any timer runs.
Promise.all, allSettled, race, any — when do you reach for each?mid

all is fail-fast: it rejects on the first rejection and you lose the other results, so use it when partial success is worthless (fan-out where every piece is required). allSettled never rejects and gives you a status per entry — the right default for a dashboard, a batch job or anything where you want to render what succeeded. race settles with the first settled promise, rejection included, which makes it a timeout primitive. any settles with the first fulfilled promise and only rejects, with an AggregateError, if all reject — hedged requests across replicas.

The senior-level point: none of them cancels the losers. Promise.race with a timeout leaves the slow request running and its socket held; pair it with an AbortController or you have built a leak.

const results = await Promise.allSettled(ids.map(fetchOne));
const ok = results.filter((r): r is PromiseFulfilledResult<Row> => r.status === 'fulfilled').map(r => r.value);
const failed = results.filter(r => r.status === 'rejected').length;
if (failed) logger.warn({ failed, total: ids.length }, 'partial fan-out');
Follow-ups
  • What does Promise.all do with a rejection after it has already rejected? Nothing — it is settled; the later rejection is swallowed, not "unhandled", because all attached handlers.
  • Combinator for "first success, but give up after 2 s"? Promise.any plus AbortSignal.timeout(2000), or race against a rejecting timer.
  • Does Promise.all start the work? No — the promises are already running when you construct the array; all only joins.
Common wrong answer"Use Promise.all and wrap each in try/catch" — reinventing allSettled — or, worse, claiming Promise.all "cancels the rest when one fails". It cannot; promises have no cancellation.
How do you cancel an in-flight async operation?mid

Promises are not cancellable — once started, work runs to completion. Cancellation is a separate signalling channel: AbortController produces an AbortSignal you thread into anything that supports it (fetch, addEventListener, Node streams, most modern libraries). The consumer either aborts eagerly or the promise rejects with an AbortError/DOMException. Since ES2024 and Node 18 you also get AbortSignal.timeout(ms) and AbortSignal.any([...]), which compose a user cancel with a deadline without hand-rolled plumbing.

const ac = new AbortController();
const signal = AbortSignal.any([ac.signal, AbortSignal.timeout(2_000)]);
try {
  const res = await fetch(url, { signal });
  return await res.json();
} catch (e) {
  if (e instanceof Error && e.name === 'AbortError') return null; // user navigated away or we timed out
  throw e;
}
// elsewhere: ac.abort() on unmount / route change
Follow-ups
  • Does aborting stop the server work? No — it closes the client side; the request may already have committed. Design for idempotency, not for abort.
  • Cancelling a chain of your own async functions? Pass the signal down and check signal.throwIfAborted() at each await point; there is no ambient cancellation.
  • Why does addEventListener(..., { signal }) matter? One abort() removes every listener registered with that signal — the cleanest teardown in the language.
Common wrong answer"Set a flag and check it after the await" — that leaks the underlying socket/timer and still runs the work; or claiming Promise.cancel() exists (it does not, and the cancellable-promise proposal was withdrawn in 2016).
What happens to an unhandled promise rejection, in the browser and in Node?senior

A rejection with no handler attached by the end of the microtask drain fires unhandledrejection on window/self in browsers — logged to the console, cancellable with preventDefault(). In Node, the default since v15 is --unhandled-rejections=throw: the process emits an uncaughtException and, with no handler, crashes. That is a deliberate change from the v10-era warning, and it is the reason a fire-and-forget void doThing() in a request handler can take down a pod.

The senior answer names the detection rule: "handled later" counts. Attaching a catch in a later tick fires rejectionhandled rather than saving you from the report, so store the promise and attach handlers synchronously.

// Node: observe, log with context, then let the process die — do not swallow.
process.on('unhandledRejection', (reason) => {
  logger.fatal({ reason }, 'unhandled rejection');
  process.exit(1);
});
Follow-ups
  • Should a server swallow unhandled rejections to stay up? No — the process is in unknown state. Log, drain, exit, let the orchestrator restart it.
  • How do you fire-and-forget safely? void task().catch(logAndSwallow), and lint it: @typescript-eslint/no-floating-promises catches the whole class.
  • What about a rejection inside Promise.all whose sibling also rejects? Siblings are handled by all, so no report — a common source of silently lost errors.
Common wrong answer"Node just prints a warning." That was true through Node 14; since Node 15 it terminates the process by default. Quoting the old behaviour dates a candidate by a decade.
Why is await inside a loop usually wrong, and when is it right?mid

Serial await makes latency the sum of the calls: 100 items at 50 ms is 5 s. Starting the work first and awaiting the aggregate makes it the max. But the fix is not "always parallelise" — unbounded Promise.all over 10 000 items opens 10 000 sockets, blows past connection pools and gets you rate-limited or OOM-killed. The correct answer names the third option: bounded concurrency.

Serial is genuinely right when iterations depend on each other (cursor pagination, a write that reads the previous result), when the remote demands ordering, or when you are deliberately being gentle with a fragile dependency.

// serial: sum of latencies
for (const id of ids) rows.push(await fetchOne(id));
// parallel, unbounded: max latency, unbounded pressure
const rows = await Promise.all(ids.map(fetchOne));
// bounded: what you should actually reach for
const rows = await mapWithConcurrency(ids, 8, fetchOne);
Follow-ups
  • How do you pick the concurrency limit? From the downstream constraint — pool size, rate limit, or measured knee of the latency curve; not a round number you like.
  • Does forEach with an async callback work? No: forEach ignores the returned promises, so nothing is awaited and errors float. Use for...of or map + all.
  • What breaks first under unbounded fan-out? Usually the connection pool or file descriptors, then memory from buffered responses.
Common wrong answer"Just replace the loop with Promise.all." It is the right instinct and the wrong reflex — a senior candidate who never mentions a bound has never run this against a real dependency.
In Node, order these: process.nextTick, promise microtasks, setTimeout(0), setImmediate.senior

Node drains two microtask-ish queues after each phase, with process.nextTick callbacks before promise reactions — nextTick is Node-specific and higher priority. Then the loop proceeds through its phases: timers (setTimeout/setInterval), pending callbacks, poll (I/O), check (setImmediate), close callbacks. So from the main module, setTimeout(0) vs setImmediate is genuinely non-deterministic — it depends on how long process startup took relative to the timer threshold — but inside an I/O callback, setImmediate always wins, because you are already past the timers phase and the check phase comes next.

const fs = require('node:fs');
fs.readFile(__filename, () => {          // inside the poll phase
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));   // deterministically first
  process.nextTick(() => console.log('nextTick')); // before both
  Promise.resolve().then(() => console.log('promise')); // after nextTick
});
// nextTick, promise, immediate, timeout
Follow-ups
  • Why can nextTick starve the loop? Its queue is drained to exhaustion before the loop advances, so a recursive nextTick blocks I/O forever; recursive setImmediate does not.
  • Which should library code use? queueMicrotask for spec-consistent deferral; reserve nextTick for "run before anything else" invariants inside Node internals-style code.
  • Do browsers have setImmediate? No — it never standardised; the closest is MessageChannel or scheduler.postTask().
Common wrong answer"setTimeout(0) always fires before setImmediate." Confidently asserting a fixed order from the main module is wrong; the honest, correct answer is "non-deterministic there, deterministic inside I/O".
Implement bounded concurrency over a list of async tasks.senior

Keep n workers pulling from a shared cursor — no queue object, no per-item promise juggling. The pattern is short enough to write on a whiteboard, preserves input order in the results array, and fails fast or collects errors depending on how you join. Interviewers use it to check that you understand promises as values rather than as syntax, and that you think about error semantics unprompted.

async function mapWithConcurrency<T, R>(items: readonly T[], limit: number, fn: (item: T, i: number) => Promise<R>): Promise<R[]> {
  const out = new Array<R>(items.length);
  let next = 0;
  const worker = async () => {
    while (true) {
      const i = next++;                       // single-threaded: no lock needed
      if (i >= items.length) return;
      out[i] = await fn(items[i], i);
    }
  };
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return out;
}
Follow-ups
  • Why is next++ safe without a mutex? Run-to-completion: no other code interleaves between the read and the write in a single-threaded runtime.
  • How do you make it collect errors instead of failing fast? Wrap fn in a try/catch that stores a tagged result, then join with all — an allSettled shape with a bound.
  • What is still missing for production? Cancellation (an AbortSignal checked in the loop) and per-item timeouts.
Common wrong answerChunking the array into batches of n and awaiting each batch. It is simpler but strictly worse: every batch runs at the speed of its slowest item, so utilisation collapses on skewed latency.
What are async iterators, and how do they give you backpressure?senior

An async iterable implements Symbol.asyncIterator and returns a promise per next(); for await...of consumes it, awaiting each value. Because the producer only advances when the consumer asks for the next value, the consumer's speed throttles the producer — that is backpressure, for free, without a queue. Node streams are async iterable, so for await (const chunk of readable) is the idiomatic way to process a large file or HTTP body without buffering it, and an async generator is the cleanest way to wrap a paginated API.

async function* pages(url: string, signal: AbortSignal): AsyncGenerator<Row[]> {
  let cursor: string | undefined;
  do {
    const res = await fetch(`${url}?cursor=${cursor ?? ''}`, { signal });
    const page = await res.json() as { rows: Row[]; next?: string };
    yield page.rows;                 // consumer's pace sets ours
    cursor = page.next;
  } while (cursor);
}
for await (const rows of pages(url, signal)) await sink.write(rows);
Follow-ups
  • What happens on break inside for await? The iterator's return() is called, so a generator's finally runs — that is where you close handles.
  • Are async generators concurrent? No, strictly sequential; for parallelism, fan out from the loop with a bounded pool.
  • ES2026 relevance? Iterator sequencing (Iterator.concat) and the ES2025 iterator helpers give lazy map/filter/take on sync iterators; the async helper set is still catching up.
Common wrong answer"Use readable.on('data') and push into an array" — that is exactly the unbounded buffering async iteration exists to prevent, and it is how a service OOMs on one large upload.
A Node service has a p50 of 20 ms and a p99 of 4 s under load, with low CPU on average. What is happening and how do you prove it?principal

That signature is event-loop blocking: most requests fly through, but any request unlucky enough to queue behind a long synchronous task waits for it. Typical culprits are JSON.parse/stringify on multi-MB payloads, synchronous crypto (pbkdf2Sync, large bcrypt rounds), regex catastrophic backtracking, image or CSV processing, and huge Array.sort. Average CPU looks fine because the spikes are short and rare relative to the sample window.

Prove it rather than guess: monitor perf_hooks.monitorEventLoopDelay() (an interval histogram) and export p99 loop lag as a first-class metric; correlate the lag spikes with request traces; then take a CPU profile during a spike (--cpu-prof, or the inspector) and look for one long synchronous frame. The fix hierarchy: remove the work (stream instead of buffer, precompute), move it off-thread (worker_threads pool for CPU-bound work, native async crypto APIs), or partition it (chunk and yield with setImmediate) — and add a payload size limit so a single request cannot buy 4 s of CPU.

const { monitorEventLoopDelay } = require('node:perf_hooks');
const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();
setInterval(() => metrics.gauge('loop_lag_p99_ms', h.percentile(99) / 1e6), 5_000);
Follow-ups
  • Why not just add more pods? It shifts the histogram slightly but the tail persists — one blocking request still blocks every co-tenant request on its instance.
  • When is a worker pool the wrong fix? When the work is I/O-bound (workers add copies and complexity) or when the payload is so large that structured-clone transfer dominates; prefer streaming or a separate service.
  • How do you stop it regressing? An SLO on loop lag with an alert, plus a load test that includes worst-case payload sizes.
Common wrong answer"Wrap it in async/Promise.resolve().then() so it doesn't block." Marking a function async does not move synchronous work off the thread — it only delays when it blocks. This is the most common senior-level misconception in the whole topic.
Design a retry policy for an async call. What makes retries dangerous?principal

Retries turn a partial failure into a self-inflicted DDoS unless three things hold. First, only retry what is safe and retryable: idempotent operations (reads, PUT/DELETE, writes carrying an idempotency key) and transient signals (network errors, 429, 502/503/504, explicit Retry-After) — never a 400 or a validation failure, and never a non-idempotent POST without a dedupe key. Second, back off exponentially with jitter: synchronised clients retrying at 1 s, 2 s, 4 s produce retry storms that keep a recovering dependency down; full jitter spreads them. Third, cap total attempts against the caller's deadline, not a fixed count, and combine with a circuit breaker so a hard-down dependency fails fast instead of consuming the whole thread's worth of pending work.

async function withRetry<T>(fn: (s: AbortSignal) => Promise<T>, { attempts = 4, baseMs = 100, deadline }: RetryOpts): Promise<T> {
  let lastErr: unknown;
  for (let i = 0; i < attempts; i++) {
    const budget = deadline - Date.now();
    if (budget <= 0) break;
    try { return await fn(AbortSignal.timeout(budget)); }
    catch (e) {
      if (!isRetryable(e)) throw e;
      lastErr = e;
      await sleep(Math.random() * Math.min(baseMs * 2 ** i, 5_000)); // full jitter
    }
  }
  throw lastErr;
}
Follow-ups
  • Why full jitter rather than "exponential + a bit of noise"? Full jitter minimises both contention and completion time in AWS's published simulations; capped exponential alone re-synchronises clients.
  • Retries at multiple layers? Multiply — three layers of three attempts is 27 requests. Pick one layer, usually the outermost with a budget, and make the inner layers pass through.
  • How do you make a POST retryable? Client-generated idempotency key, server-side dedupe window, and a stable response for a repeat.
Common wrong answer"Retry three times with a 1-second delay." No jitter, no budget, no retryability check, applied uniformly to every call — the policy that has amplified more outages than any other line of JavaScript.

02 Closures, scope & this

The oldest interview material in JavaScript and still the most reliable filter, because the two mechanisms are unrelated and candidates routinely conflate them: closures are decided lexically, at authoring time, and this is decided dynamically, at call time. Screeners ask for a definition and a use; mid level gets a trick snippet and has to reason about the binding; senior is asked where closures leak memory and how to encapsulate state in 2026 without the module pattern; principal gets asked to justify a style choice to a team, which is really a question about whether you can teach it.

What is a closure, and what problem does it solve?screener

A closure is a function together with the lexical environment it was created in: the inner function keeps a live reference to the outer scope's bindings, not copies of their values, and that scope survives as long as the function does. It is not a feature you switch on — every function in JavaScript is a closure; the term matters when a function outlives the call that created it. The payoff is private state without an object: factories, memoisation, event handlers that remember their context, and the entire pre-ES2015 module pattern.

function makeCounter(start = 0) {
  let n = start;                       // not reachable from outside
  return { inc: () => ++n, value: () => n };
}
const c = makeCounter(10);
c.inc(); c.inc();
c.value(); // 12 — n lives on, one copy per makeCounter() call
Follow-ups
  • Do two closures from the same call share state? Yes — inc and value above close over the same n; a second makeCounter() gets its own.
  • Value or reference? Reference to the binding: reassigning the outer variable is visible inside the closure afterwards.
  • Is there a cost? The captured environment cannot be collected while the closure is reachable — real, and the source of the leak question below.
Common wrong answer"A closure is a function inside a function." That describes the syntax, not the mechanism, and it fails the very next question — why the inner function still works after the outer one returned.
var vs let vs const: scoping, hoisting and the temporal dead zone.screener

var is function-scoped and hoisted initialised to undefined, so reading it before the declaration is legal and silently wrong. let and const are block-scoped and also hoisted, but uninitialised: the span from the top of the block to the declaration is the temporal dead zone, and touching the binding there throws a ReferenceError. const prevents rebinding, not mutation — const arr = []; arr.push(1) is fine. var additionally creates a property on the global object at top level in scripts, which let/const do not.

console.log(a); // undefined  — var is hoisted and initialised
var a = 1;
console.log(b); // ReferenceError: Cannot access 'b' before initialization (TDZ)
let b = 2;
Follow-ups
  • Why is the TDZ a feature? It turns a whole class of ordering bugs into a loud error at the exact line, instead of an undefined that propagates.
  • Are function declarations hoisted differently? Yes — fully, body included, so you can call them above their definition; function expressions follow the variable's rules.
  • Any reason to write var in 2026? None in new code; you meet it in legacy files and in transpiler output.
Common wrong answer"let and const are not hoisted." They are — the binding exists from the top of the block; what is missing is the initialisation. Getting this wrong means you cannot explain why the error says "cannot access before initialization" rather than "is not defined".
Why does this loop log 3 3 3, and what are three ways to fix it?mid

With var there is exactly one i, function-scoped; all three callbacks close over the same binding, and by the time the timers fire the loop has finished and i is 3. let in a for header is special-cased by the spec: a fresh binding is created per iteration and copied forward, so each closure captures its own. The historical fixes were an IIFE per iteration or setTimeout's extra-argument trick; the modern fix is one keyword.

for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));      // 3 3 3
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i));      // 0 1 2
for (var i = 0; i < 3; i++) (j => setTimeout(() => console.log(j)))(i); // 0 1 2 (IIFE)
Follow-ups
  • Does let also create a per-iteration binding in for...of? Yes, and in for...in; the classic bug only exists with var.
  • What if the callback is synchronous? No bug — the difference only shows once the closure outlives the iteration.
  • Is this a closure bug or a scoping bug? Scoping. The closure behaves correctly; there simply was only one variable to close over.
Common wrong answer"setTimeout runs after the loop, so it prints the last value" — true but incomplete, and it does not explain why let fixes it. Interviewers ask the follow-up specifically to catch memorised answers.
How is this determined at a call site?mid

For a normal function, this is bound at call time by four rules, in precedence order: new (a fresh object), explicit binding (call/apply/bind), implicit binding (the object left of the dot), and default (undefined in strict mode and in modules, the global object in sloppy mode). Arrow functions have no this of their own at all — they close over the this of the enclosing lexical scope, which is why they cannot be used as methods that need the receiver, and why they are perfect as callbacks inside methods.

const obj = {
  name: 'obj',
  regular() { return this.name; },
  arrow: () => this?.name,          // enclosing scope's this — not obj
};
obj.regular();                       // 'obj'
const f = obj.regular; f();          // TypeError in a module: this is undefined
obj.regular.call({ name: 'other' }); // 'other'
Follow-ups
  • What is this in a module's top level? undefined in ESM; module.exports in CommonJS; globalThis in a classic script.
  • Can you bind an arrow function? You can call bind, but the this argument is ignored — it has no binding to override.
  • Does class change the rules? Class bodies are always strict, so an unbound extracted method gets undefined rather than the global object — the loud version of the same bug.
Common wrong answer"this refers to the function's own scope / the object where the function was defined." Both are wrong: it is the call site, not the definition site, that decides — except for arrows, where the definition site decides and there is no binding at all.
A method loses this when passed as a callback. Explain and fix it.mid

Passing obj.method passes the function value alone; the receiver was never part of it. When the host later calls it plainly, implicit binding is gone and strict-mode this is undefined, producing the familiar "cannot read properties of undefined". The fixes, in ascending order of preference: wrap in an arrow at the call site (() => obj.method()) — explicit and cheap; bind in the constructor — one bound copy per instance; or define the member as a class field holding an arrow, which bakes the instance this in at construction.

class Counter {
  #n = 0;
  handleClick = () => { this.#n++; };        // class field: bound per instance
  reset() { this.#n = 0; }                    // prototype method: needs a receiver
}
const c = new Counter();
btn.addEventListener('click', c.handleClick); // fine
btn.addEventListener('click', c.reset);       // TypeError — use () => c.reset()
Follow-ups
  • Trade-off of arrow class fields? They live on the instance, not the prototype: one function object per instance, not overridable by subclasses, and invisible to prototype-based spies in tests.
  • Can TypeScript catch this? Yes — strictBindCallApply plus an explicit this parameter (function f(this: Counter)) makes the unbound extraction a compile error.
  • What about bind in render code? Creating a new bound function every render defeats memoisation and reference equality checks.
Common wrong answer"Use self = this." It works and it is 2011. Reaching for it in 2026 says you have not internalised arrows, and it hides the actual mechanism from whoever reads the code next.
How do closures cause memory leaks?senior

A closure keeps its whole captured environment alive, and engines capture at the granularity of the variables actually referenced — but a single retained closure pins the scope object it shares with its siblings, so one small callback can hold a large buffer alive if both were declared in the same function. The realistic leak shapes: event listeners or subscriptions never removed (the handler pins the component, the DOM node and everything it captured); timers/intervals never cleared; a cache keyed by object that grows forever; and long-lived module-scope arrays that closures push into. In Node, request-scoped closures captured by a module-level array leak per request — the classic slow OOM.

// Leaky: the interval closure pins `rows` (100 MB) for the process lifetime.
function start(rows) {
  setInterval(() => console.log(rows.length), 1000);
}
// Better: capture only what you need, and own the teardown.
function start(rows, signal) {
  const n = rows.length;
  const id = setInterval(() => console.log(n), 1000);
  signal.addEventListener('abort', () => clearInterval(id), { once: true });
}
Follow-ups
  • How do you prove it in production? Two heap snapshots under steady load, compare retained size by constructor, follow the retainer path to the closure's scope object; in Node, --heapsnapshot-signal or node --inspect.
  • Do WeakMap/WeakRef help? WeakMap yes for object-keyed caches; WeakRef/FinalizationRegistry rarely — GC timing is unspecified, so they are a last resort, not a design.
  • Is a closure worse than a class here? No — an instance method capturing this retains exactly as much; the discipline is about lifetime ownership, not syntax.
Common wrong answer"JavaScript is garbage-collected, so you can't leak." GC frees the unreachable; every leak in a managed runtime is unintended reachability, and closures are the most common root.
Encapsulation in 2026: closure-captured variables, #private fields, or TypeScript private?senior

All three hide state, at different times. TypeScript's private is a compile-time convention: it is erased, so the property is plainly visible at runtime and reachable via obj['x'] — fine for team discipline, worthless against untrusted callers. #private fields (ES2022) are enforced by the engine: not enumerable, not reachable by string key, and accessing them on a wrong receiver throws a TypeError. Closure variables are equally hard-private and additionally invisible to reflection, which is why factory functions still win for capability-style APIs and for objects you serialise. The practical rule: # for class state that must not escape, closures for factories and for hiding a whole implementation, TypeScript private only where erasure is acceptable.

class Token {
  #secret: string;                       // truly private at runtime
  constructor(s: string) { this.#secret = s; }
  matches(other: Token) { return this.#secret === other.#secret; } // same-class access is allowed
  toJSON() { return { kind: 'token' }; } // # fields never serialise by accident
}
Follow-ups
  • Do # fields survive type stripping in Node? Yes — they are standard JavaScript syntax, unlike private, enum or parameter properties.
  • Testing private state? Test through the public surface; if you must reach in, that is a design smell, and # makes the smell impossible to ignore.
  • Cost of #? Historically slower in some engines and awkward with Proxy receivers; in current V8 the gap is negligible.
Common wrong answer"TypeScript private makes it private." It makes it private to the type checker. A candidate who claims runtime enforcement will happily ship a "private" API key on an object that gets JSON.stringify'd into a log.
Write debounce and explain how it differs from throttle.senior

Debounce collapses a burst into one call after the input goes quiet — right for search-as-you-type, resize-settled, autosave. Throttle guarantees at most one call per interval while the burst continues — right for scroll, pointer-move, progress reporting. Production versions need more than the four-line version: this and argument forwarding, a cancel() and flush(), an optional leading edge, and a promise-returning variant so callers can await the eventual result. Interviewers watch for whether you handle the trailing call's arguments (the last ones, not the first) and whether you clean the timer up.

function debounce<A extends unknown[]>(fn: (...args: A) => void, ms: number) {
  let t: ReturnType<typeof setTimeout> | undefined;
  const wrapped = function (this: unknown, ...args: A) {
    if (t) clearTimeout(t);
    t = setTimeout(() => { t = undefined; fn.apply(this, args); }, ms); // last args win
  };
  wrapped.cancel = () => { if (t) clearTimeout(t); t = undefined; };
  return wrapped;
}
Follow-ups
  • Where do you put cancel() in a component? In teardown — a pending debounce that fires after unmount is a classic "setState on unmounted component" bug.
  • Debounce a network call? Debounce the trigger and abort the in-flight request, otherwise responses arrive out of order; track a request id or use AbortController.
  • Throttle with leading and trailing? Both edges: call immediately, then schedule one trailing call if events kept arriving — that is what users expect from scroll handlers.
Common wrong answerDescribing debounce as "limit to once every N ms" — that is throttle. Mixing the two up is extremely common and immediately visible when the interviewer asks which one you would put on a search box.
What are partial application and currying, and where do they earn their keep?mid

Partial application fixes some arguments now and returns a function taking the rest; currying is the stricter form where an n-ary function becomes n unary functions. Both are just closures. They earn their keep for configuration-at-the-edge — a logger bound to a request id, a fetcher bound to a base URL and auth — and for building small, testable pipelines. They stop earning it when they obscure arity: deep curry chains are hard to read, hard to type, and hard to stack-trace, which is why the ecosystem largely settled on plain factory functions plus bind-free arrows.

const createClient = (baseUrl: string, token: string) =>
  (path: string, init?: RequestInit) =>
    fetch(new URL(path, baseUrl), { ...init, headers: { ...init?.headers, authorization: `Bearer ${token}` } });

const api = createClient('https://api.example.com', token); // partial application
await api('/users/42');
Follow-ups
  • How does TypeScript type a generic curry? With variadic tuple types (...args: A) — doable, but inference degrades quickly; a reason to prefer explicit factories.
  • Is bind partial application? Yes, plus a this binding — fn.bind(null, a) is the built-in version.
  • Composition order? pipe reads left-to-right and is what teams actually understand; compose reads right-to-left and causes review arguments.
Common wrong answerPresenting currying as inherently superior style. At lead level the expected answer names the readability and debuggability cost, not just the elegance.
A team disagrees: factory functions returning closures, or classes? How do you settle it?principal

Settle it on properties, not taste. Classes win when you need many instances (prototype methods are shared, closures allocate per instance), inheritance or instanceof checks, real private state with #, and good interop with DI containers, ORMs and serialisers. Factories win when the object is a small capability bundle, when you want to hide the implementation type entirely, when you want to avoid this semantics in callbacks, and when the thing is naturally immutable configuration. The decision that actually matters is consistency plus a written rule, because both work and mixed idioms are what makes a codebase feel foreign.

The lead-level framing to say out loud: "I'd optimise for the code review, not the microbenchmark — pick one idiom per layer, document why in the style guide, and let the linter enforce it. The measurable exception is hot paths creating millions of objects, where per-instance closures show up in heap profiles; then classes, and I'd want the profile in the PR."

Follow-ups
  • Does the answer change for a public library? Yes — factories give you freedom to change the internal representation without a breaking instanceof or subclassing contract.
  • What about tree-shaking? Free functions and factories shake better than a class with many methods, which is retained wholesale once referenced.
  • How do you avoid relitigating it? An ADR plus an ESLint rule; unwritten preferences get relitigated every quarter.
Common wrong answer"Classes are not idiomatic JavaScript" (or its mirror, "closures are a functional-programming fad"). Dogma without a property-based argument is the failure mode this question is designed to surface.

03 TypeScript type system fundamentals

Every TypeScript interview has a block here, and it is where "I've used TypeScript for years" gets separated from "I understand what the checker is doing". The recurring theme is that TypeScript is a structural, erased, deliberately unsound checker: it describes shapes, it disappears at runtime, and it trades a few holes for usability. Screeners want any/unknown/never and type vs interface; mid level wants narrowing and discriminated unions; senior wants the strictness flags and the enum question; principal is expected to name the soundness holes without prompting and to say what the type system is not buying you.

TypeScript is structurally typed. What does that mean in practice?screener

Compatibility is decided by shape, not by name or declaration lineage: any value with the required members is assignable, whatever it was declared as. That is why an object literal from an API response satisfies an interface User it has never heard of, and why two unrelated types with identical members are interchangeable. C# and Java are nominal, so this is the single biggest adjustment for engineers coming from there. The escape hatch when you genuinely need identity — currency amounts, user ids, sanitised HTML — is branding: intersect with a unique unexported marker so the compiler stops treating a UserId as just another string.

interface Point { x: number; y: number }
const p = { x: 1, y: 2, label: 'origin' };
const q: Point = p;             // OK — structural; extra members are fine on a variable

declare const brand: unique symbol;
type UserId = string & { readonly [brand]: 'UserId' };
const id = '42' as UserId;      // nominal-ish: a plain string is no longer assignable
Follow-ups
  • Then why did my object literal error on an extra property? Excess property checking — a special rule that only applies to fresh object literals assigned directly; assign via a variable and it disappears.
  • Are classes structural too? Yes, except that #private or private members make a class effectively nominal.
  • When is branding worth it? When mixing up two strings is a production incident: ids, tokens, units, pre-escaped strings.
Common wrong answer"Types are checked at runtime" or "an interface guarantees the object really has those fields". Nothing is checked at runtime; a JSON response typed as User is an assertion of faith until you validate it.
any vs unknown vs never.screener

any disables checking in both directions — it is assignable to everything and accepts every operation — so it does not stay local: one any spreads through every expression it touches. unknown is the safe top type: everything is assignable to it, but you can do nothing with it until you narrow, which makes it the correct type for JSON, catch parameters and any untrusted boundary. never is the bottom type — no value has it — so it is what a function that never returns is typed as, what an impossible branch narrows to, and the tool you use to make exhaustiveness failures compile errors.

function assertNever(x: never): never { throw new Error(`unexpected ${JSON.stringify(x)}`); }

function handle(e: unknown) {
  if (e instanceof Error) return e.message;   // narrowed
  if (typeof e === 'string') return e;
  return 'unknown error';                     // e is still unknown here — that is the point
}
Follow-ups
  • Why is catch (e) unknown? Under useUnknownInCatchVariables (on with strict since 4.4) — because JavaScript can throw anything, including a string or undefined.
  • Where does never appear unexpectedly? As the element type of an empty array literal without context, and as the result of an impossible intersection like string & number.
  • Is any ever right? Rarely, and always locally with a comment; unknown plus a narrowing function is almost always the better shape.
Common wrong answer"unknown is just a safer any, so they're interchangeable." They are opposites in variance: any lets values flow out unchecked, unknown blocks them until proven. Using any "temporarily" is how codebases end up with thousands of them.
type or interface?mid

They overlap almost completely for object shapes. interface can be re-opened (declaration merging) and extended, which is exactly what you want for a public library surface others may augment, and what you do not want for a closed domain model. type can express everything else — unions, intersections, tuples, mapped, conditional and template-literal types — so it is the only option once the shape is not a plain object. Performance is a real tiebreaker at scale: interface extends is cached by the checker while large intersection types are re-elaborated, so deep intersection chains can slow a big project's check measurably.

interface Plugin { name: string; setup(ctx: Ctx): void }   // extensible surface
type Result<T> = { ok: true; value: T } | { ok: false; error: Error }; // must be a type
Follow-ups
  • A rule you'd put in a style guide? interface for object shapes you own and may extend, type for unions, aliases and anything computed — and stop arguing about it in review.
  • Which produces better error messages? interface — errors report the name; large anonymous intersections print as a wall of members.
  • Can a type implement-check a class? Yes, class C implements SomeObjectType works for object types.
Common wrong answer"interface is for objects and type is for primitives" — a half-remembered rule that falls apart the moment you need a discriminated union, which is the single most useful shape in TypeScript.
Explain discriminated unions and exhaustiveness checking.mid

A discriminated (tagged) union is a union of object types sharing a literal-typed field. Narrowing on that field tells the checker exactly which member you have, so each branch gets precise types with no casts. Pair it with a never-typed default and the compiler becomes a change detector: add a variant, and every unhandled switch in the codebase fails to compile. This is the highest-value pattern in applied TypeScript — it is how you model state machines, API results, events and reducer actions — and interviewers use it as the fastest read on whether you model data with types or just annotate it.

type State =
  | { status: 'idle' }
  | { status: 'loading'; startedAt: number }
  | { status: 'ok'; data: Row[] }
  | { status: 'error'; error: Error; retryable: boolean };

function render(s: State) {
  switch (s.status) {
    case 'idle': return 'Ready';
    case 'loading': return `Loading since ${s.startedAt}`;  // startedAt only exists here
    case 'ok': return `${s.data.length} rows`;
    case 'error': return s.retryable ? 'Retrying…' : s.error.message;
    default: return assertNever(s);                          // compile error if a variant is added
  }
}
Follow-ups
  • Why not one interface with optional fields? Because it permits impossible states — status: 'ok' with an error and no data — and forces non-null assertions everywhere.
  • Can the discriminant be a boolean or an enum? Yes — any literal type, including true/false, which is how a Result type narrows on ok.
  • What if the data comes from the wire? Narrowing is only as true as your parse step; validate at the boundary first.
Common wrong answerAdding default: throw new Error('unreachable') without the never parameter. It looks identical and buys nothing: the failure moves from compile time to a production 500 the first time someone adds a variant.
How does narrowing work, and how do you extend it to your own checks?mid

Control-flow analysis narrows a union as it walks the code: typeof, instanceof, in, truthiness, equality against literals, discriminant checks, and Array.isArray are all understood natively. For your own checks you write a type predicate (x is Foo) or, since 4.4, an assertion function (asserts x is Foo) which narrows the caller's variable for the rest of the scope. TypeScript 5.5 added inferred type predicates, so a small arrow like (x) => x !== null used in filter now narrows without an explicit annotation — the fix for the years-old "filter(Boolean) doesn't narrow" complaint.

function isRow(x: unknown): x is Row {
  return typeof x === 'object' && x !== null && 'id' in x && typeof (x as Row).id === 'string';
}
function assertOk(res: Response): asserts res is Response & { ok: true } {
  if (!res.ok) throw new HttpError(res.status);
}
const defined = maybes.filter(x => x !== undefined); // TS 5.5+: string[], not (string|undefined)[]
Follow-ups
  • What defeats narrowing? A closure or an await between check and use when the value is a mutable let or a property; TypeScript conservatively resets property narrowing across function boundaries.
  • Why are assertion functions dangerous? They must be declared with an explicit type annotation and the compiler trusts the body blindly — a wrong predicate is a silent lie.
  • Predicate vs schema validator? Hand-written predicates drift from the type; a schema library (Zod, Valibot, ArkType) derives both from one source.
Common wrong answerWriting x is Foo over a body that checks nothing meaningful (return true, or only typeof x === 'object'). It compiles, it narrows, and it is a cast wearing a costume — the reason predicates should be reviewed like as.
When is a type assertion (as) acceptable, and what does as const do?mid

as is you overruling the checker; it generates no runtime code and no runtime check. It is defensible in three places: after a validation you performed yourself, when modelling something the type system cannot express (a branded id, a builder's final shape), and in tests where a partial fixture stands in for a big type. It is indefensible as a way to silence an error you do not understand, and as unknown as T should be a review blocker. as const is a different thing entirely: it makes a literal deeply readonly and keeps its literal types, which is how you build lookup tables, tuple types and unions derived from data instead of duplicated by hand.

const ROLES = ['admin', 'editor', 'viewer'] as const;
type Role = typeof ROLES[number];        // 'admin' | 'editor' | 'viewer'

const config = { retries: 3, mode: 'strict' } as const; // readonly, mode: 'strict' not string
Follow-ups
  • satisfies vs as? satisfies (TS 4.9) checks the value against a type without widening it — the right tool for config objects where you want both validation and precise inference.
  • Non-null assertion !? Same category as as: a claim, not a check. Ban it in application code and allow it behind a comment in tests.
  • How do you police as at scale? Lint (@typescript-eslint/consistent-type-assertions), a CODEOWNERS review on shared types, and a count in CI that must not grow.
Common wrong answer"as converts the value to that type." It converts nothing — no coercion, no validation. Candidates who believe otherwise write await res.json() as User and call it type safety.
Which strictness flags matter, and what does strict actually turn on?senior

strict is a bundle: strictNullChecks (the one that matters — null/undefined stop being members of every type), noImplicitAny, strictFunctionTypes, strictBindCallApply, strictPropertyInitialization, noImplicitThis, alwaysStrict and useUnknownInCatchVariables. As of TypeScript 6.0 strict defaults to true, so new projects get it whether or not they ask. The flags worth arguing for beyond the bundle are noUncheckedIndexedAccess (array and index access yields T | undefined — the single highest-value non-default flag, and the noisiest to adopt), exactOptionalPropertyTypes (distinguishes "absent" from "present and undefined", which matters for PATCH semantics), noImplicitOverride, noFallthroughCasesInSwitch and verbatimModuleSyntax.

{ "compilerOptions": {
  "strict": true,
  "noUncheckedIndexedAccess": true,
  "exactOptionalPropertyTypes": true,
  "noImplicitOverride": true,
  "verbatimModuleSyntax": true,
  "erasableSyntaxOnly": true,
  "isolatedModules": true
} }
Follow-ups
  • How do you migrate a large codebase to strictNullChecks? Flag on, errors triaged per directory with a baseline file or per-file // @ts-nocheck retired on a schedule — never a big-bang PR nobody can review.
  • Why do teams reject noUncheckedIndexedAccess? Loop-heavy code gets noisy; the counter is that every one of those undefineds is a real possibility, and for...of avoids most of the noise.
  • Does strict affect emitted JavaScript? No, except alwaysStrict's "use strict" — type checking is erased.
Common wrong answer"We have strict: true, so we're type safe." strict says nothing about any already in the codebase, unvalidated I/O, or assertions — the three places production type errors actually come from.
enum, a union of string literals, or a const object? Argue it with 2026 constraints.senior

Prefer a union of string literals, or a const object plus a derived union. The reason is no longer stylistic: enum is one of the few TypeScript constructs that emits runtime code, so it is not erasable — it is rejected by erasableSyntaxOnly (TS 5.8), it cannot run under Node's native type stripping, and it breaks isolatedModules-style single-file transpilation used by esbuild/SWC/Vite. Numeric enums are additionally unsound: any number is assignable to a numeric enum in older versions, and reverse mappings pollute the emitted object. const enum is worse still — inlined, invisible across module boundaries, and disallowed under isolatedModules.

// Prefer this
const Status = { Idle: 'idle', Running: 'running', Done: 'done' } as const;
type Status = typeof Status[keyof typeof Status];   // 'idle' | 'running' | 'done'

// Over this: emits an IIFE, blocks type stripping, fails erasableSyntaxOnly
enum StatusEnum { Idle = 'idle', Running = 'running' }
Follow-ups
  • What else is non-erasable? Parameter properties (constructor(private x: number)), namespaces with runtime members, and legacy experimental decorators' metadata emit.
  • We already have hundreds of enums — now what? Leave them; ban new ones with a lint rule and convert opportunistically. The migration is mechanical but the diff noise is not worth a sprint.
  • Do string enums have any advantage? One: a nominal-ish identity, since a bare string is not assignable to a string enum. Branding gets you the same thing without the emit.
Common wrong answer"Enums are the idiomatic way to model a closed set — that's what they're for." It was defensible in 2018. In 2026 it collides with type stripping, single-file transpilers and the direction of the language, and a candidate who cannot name that collision is behind.
Explain declaration merging and module augmentation. When do you use them?senior

Interfaces and namespaces with the same name in the same scope merge into one declaration. That is how lib.dom.d.ts can be extended, and how you legitimately add a property that a runtime really does put there: declare global for globals, declare module 'x' to augment a third-party package's types. Legitimate uses are narrow — typing Express's Request.user added by your auth middleware, adding an env var to ProcessEnv, describing a plugin registry. The cost is that augmentation is global and invisible at the use site: a reader sees req.user and has no idea which file promised it, and two packages augmenting the same interface can conflict irreconcilably.

// types/express.d.ts
import 'express';
declare module 'express-serve-static-core' {
  interface Request { user?: { id: string; roles: readonly string[] } }
}
Follow-ups
  • Why is Request.user optional here even though middleware always sets it? Because the type is global but the guarantee is route-local; the honest fix is a narrowed AuthedRequest type after the middleware.
  • Augmentation vs a wrapper type? Prefer a wrapper or a branded context object in application code; reserve augmentation for genuine framework extension points.
  • Where do the files have to live? Anywhere include picks up; they must be modules (have an import/export) for declare module, and non-modules for plain declare global scripts.
Common wrong answerUsing declare global to paper over a missing dependency type ("just declare it as any"). It compiles everywhere and lies everywhere; the correct move is a minimal local .d.ts describing only what you use.
What does TypeScript not protect you from?principal

The honest list, and interviewers at this level are listening for you to volunteer it. TypeScript is erased, so nothing about types survives to runtime: every I/O boundary — HTTP responses, JSON.parse, localStorage, env vars, message queues, database drivers — is unvalidated unless you validate it. It is deliberately unsound in specific places: bivariant method parameters, array covariance (Dog[] assignable to Animal[], then push a Cat), any, assertions, non-null !, index signatures without noUncheckedIndexedAccess, and third-party .d.ts files that simply describe the wrong thing. It says nothing about concurrency, ordering, resource lifetime, or business invariants, and a mutation through an aliased reference will happily invalidate a narrowing.

const dogs: Dog[] = [new Dog()];
const animals: Animal[] = dogs;   // allowed: arrays are covariant
animals.push(new Cat());          // compiles; dogs now contains a Cat

const user = await res.json() as User;  // no check happened at all
const parsed = UserSchema.parse(await res.json()); // this is where safety starts
Follow-ups
  • Why did the designers accept unsoundness? Explicit non-goal: a sound system for existing JavaScript would reject too much real code. Usability was chosen over completeness, on purpose.
  • What is the highest-leverage mitigation? One validated boundary layer: parse at the edge into domain types, and forbid as on parsed data.
  • Method bivariance — what is the safe alternative? Declare callbacks as properties with function-type syntax; strictFunctionTypes then checks them contravariantly.
Common wrong answer"TypeScript catches type errors, so we don't need runtime validation." This is the single most expensive misconception in the ecosystem, and it is exactly what the question is fishing for; the strong answer names where the boundary is and what parses it.

04 Objects, prototypes & classes

Objects are where JavaScript's oldest machinery still shows through, and interviewers use it to check that class is not a black box to you. Screeners want the prototype chain explained without arm-waving; mid level gets copying, immutability and the modern optional-chaining family; senior gets Symbol, Proxy/Reflect and the "why not a plain object" collection question. At principal level the expectation is that you can say when each mechanism is worth its debugging cost — metaprogramming that nobody on the team can profile is a liability, not cleverness.

How does property lookup work? Distinguish prototype from __proto__.screener

Reading a property walks the object's own keys, then its prototype, then that object's prototype, up to Object.prototype and finally null. __proto__ (properly Object.getPrototypeOf) is the link on an instance; prototype is a property on a constructor function that becomes the link for objects it creates with new. Writes do not walk the chain: assigning creates an own property that shadows the inherited one — except when the inherited property is a setter or the object is frozen. This is also why hasOwnProperty exists, and why the modern spelling is Object.hasOwn(obj, key) (ES2022), which works on Object.create(null) objects too.

function Dog(name) { this.name = name; }
Dog.prototype.speak = function () { return `${this.name} barks`; };
const d = new Dog('Rex');
Object.getPrototypeOf(d) === Dog.prototype;  // true
d.speak();                                    // found two links up
Object.hasOwn(d, 'speak');                    // false — inherited, not own
Follow-ups
  • Why is mutating __proto__ discouraged? It deoptimises the object in V8 (hidden-class change) and is a well-known prototype-pollution vector; use Object.create at construction.
  • What does Object.create(null) buy you? A dictionary with no inherited keys — no toString, no __proto__ setter — the safe shape for user-controlled keys.
  • Cost of a deep chain? Lookups are inline-cached, so depth is cheap once warm; the real cost is unpredictable shapes, not depth.
Common wrong answer"d.prototype is the prototype of d." Instances have no prototype property — only functions do. Getting this backwards is the classic sign of memorised rather than mechanical understanding.
What does class desugar to, and what is not just sugar?mid

Methods land on C.prototype and statics on C itself, so far so sugary. But several things have no pre-ES2015 equivalent: class bodies are always strict; class declarations are not hoisted in a usable way (TDZ); a class cannot be called without new; super() must run before this is accessible in a derived constructor; #private fields are engine-enforced; instance fields are installed per instance in declaration order, after super(); and static blocks (ES2022) run once at class evaluation. Field-initialisation order is the one that bites — a field initialiser cannot see a value assigned later in the constructor, and a derived field shadows a base-constructor assignment.

class Base { constructor() { this.init(); } init() { /* ... */ } }
class Derived extends Base {
  value = 42;                     // installed AFTER super() returns
  override init() { console.log(this.value); } // undefined — called from Base's constructor
}
new Derived();                     // logs undefined, then value becomes 42
Follow-ups
  • Why is calling an overridable method from a constructor a smell? Exactly the above: the subclass is not fully constructed yet, in JavaScript as in C# and Java.
  • Getters/setters — prototype or instance? Prototype, as accessor descriptors; class fields holding arrows are per-instance.
  • Do decorators change this? Standard decorators (TC39 stage 3, TypeScript 5.0) run at class definition time and can wrap methods and fields; the legacy experimentalDecorators form is a different, incompatible design still required by some frameworks.
Common wrong answer"class is purely syntactic sugar over functions and prototypes." Repeated everywhere and no longer true since ES2015 shipped — # privates, new.target enforcement, and field semantics have no function-syntax equivalent.
Shallow vs deep copy: what do spread, Object.assign and structuredClone actually do?mid

Spread and Object.assign copy own enumerable properties one level deep: nested objects are shared, the prototype is not copied, getters are invoked and become plain data, and non-enumerable or symbol-keyed-but-non-enumerable members are skipped. structuredClone (standard since 2022, available in browsers, Node 17+, Deno and workers) does a true deep clone using the structured-clone algorithm: it handles cycles, Map, Set, Date, RegExp, ArrayBuffer, typed arrays and Error, but throws on functions, DOM nodes, symbols and class identity — you get a plain object back, not an instance. JSON.parse(JSON.stringify(x)) remains the wrong default: it drops undefined, functions and symbols, turns Date into a string, NaN/Infinity into null, and throws on cycles.

const src = { a: 1, nested: { b: 2 }, when: new Date() };
const shallow = { ...src };          shallow.nested.b = 99;  // src.nested.b is now 99
const deep = structuredClone(src);   deep.nested.b = 7;      // src untouched; when is still a Date
const lossy = JSON.parse(JSON.stringify(src));               // when is a string
Follow-ups
  • Cheapest correct deep copy for hot paths? Do not copy — use immutable update patterns, or persistent structures; structuredClone is deep-copy cost, not free.
  • What about class instances? Write an explicit clone()/with() method; no generic cloner can restore behaviour and privates.
  • Does spread copy getters? It evaluates them and stores the result — a real source of surprise with lazily computed properties.
Common wrong answer"Spread deep-copies the object." It copies one level; the interview follow-up is always a nested mutation, and this is where the answer collapses. The 2026-dated version of the mistake is not knowing structuredClone exists.
How do you make an object immutable, and what are the limits?mid

Object.freeze makes own properties non-writable and non-configurable and prevents additions — one level deep, so a "frozen" object with a nested array is still mutable inside. Object.seal prevents add/delete but allows writes; preventExtensions only blocks additions. In sloppy mode a write to a frozen object fails silently; in strict mode (so: in every module) it throws, which is what you want. TypeScript's readonly and Readonly<T> are compile-time only and shallow, and as const gives deep readonly types but no runtime enforcement. For real deep immutability you either freeze recursively (expensive, and it changes engine behaviour) or use a library with structural sharing.

const config = Object.freeze({ retries: 3, hosts: ['a', 'b'] });
config.retries = 5;      // TypeError in strict mode
config.hosts.push('c');  // works — freeze is shallow

type DeepReadonly<T> = { readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K] };
Follow-ups
  • Does freezing help performance? Not reliably; it can help V8 keep a stable shape but is not a speed technique. Freeze for correctness.
  • Freeze in production or only in dev? A common pattern is dev-only deep freeze to catch accidental mutation, dropped in production builds for cost.
  • Property descriptors? Object.defineProperty controls writable/enumerable/configurable and accessors — the mechanism freeze is built on.
Common wrong answer"const makes it immutable." const forbids rebinding the identifier; the object is as mutable as ever. Fully half of junior candidates say this, and some senior ones say it about readonly.
What are Symbols for, and which well-known symbols matter?senior

A Symbol is a unique, non-string property key: two symbols with the same description are different, so symbol-keyed properties cannot collide with anyone else's keys and are skipped by Object.keys, JSON.stringify and for...in. That makes them the right key for metadata you attach to objects you do not own. The well-known symbols hook into language protocols: Symbol.iterator makes a value work with for...of and spread, Symbol.asyncIterator with for await, Symbol.toPrimitive controls coercion, Symbol.toStringTag changes Object.prototype.toString, Symbol.hasInstance customises instanceof, and Symbol.dispose/Symbol.asyncDispose drive using/await using in explicit resource management (TC39 stage 4, shipping as ES2027; TypeScript support since 5.2).

class Range {
  constructor(private from: number, private to: number) {}
  *[Symbol.iterator]() { for (let i = this.from; i <= this.to; i++) yield i; }
  get [Symbol.toStringTag]() { return 'Range'; }
}
[...new Range(1, 4)];             // [1, 2, 3, 4]
String(new Range(1, 4));          // '[object Range]'
Follow-ups
  • Symbol.for vs Symbol()? Symbol.for uses a cross-realm global registry — the right choice when two copies of a library must agree on a key.
  • Are symbol keys private? No — Object.getOwnPropertySymbols and Reflect.ownKeys find them. They are collision-proof, not secret.
  • What does using buy over try/finally? Deterministic, composable cleanup at scope exit for multiple resources, in declaration-reverse order — the JavaScript answer to IDisposable.
Common wrong answer"Symbols are for private properties." Close enough to sound right and wrong in the way that matters: they are enumerable via reflection, and # fields are the actual privacy mechanism.
When would you reach for Proxy and Reflect, and what does it cost?senior

A Proxy intercepts fundamental operations — get, set, has, deleteProperty, apply, construct — and Reflect gives you the default behaviour to delegate to, with the correct receiver so getters and inheritance keep working. Legitimate uses are frameworks and infrastructure: reactive state (Vue 3, MobX, Valtio), ORM lazy loading, mock/spy objects, deprecation shims, and negative-index or default-value collections. The costs are real: proxied property access is substantially slower than a plain object and defeats inline caches; proxies break #private field access when the receiver is the proxy rather than the target; invariants must be respected or the engine throws; and DevTools, structured clone and many libraries do not see through them. TypeScript cannot express the transformation, so the type is usually a lie you write by hand.

const withDefault = <T,>(target: Record<string, T>, fallback: T) =>
  new Proxy(target, {
    get: (t, k, recv) => (Reflect.has(t, k) ? Reflect.get(t, k, recv) : fallback),
  });
const counts = withDefault<number>({}, 0);
counts.missing; // 0
Follow-ups
  • Why use Reflect.get(t, k, recv) instead of t[k]? The receiver argument keeps this correct inside getters, so inherited accessors see the proxy, not the target.
  • Where does a proxy leak? Identity: proxy !== target, so Map keys, WeakMap lookups and === checks diverge if both escape.
  • Would you use one in application code? Rarely — a proxy in business logic makes stack traces and profiles lie. Keep them at the framework boundary.
Common wrong answer"Use a Proxy for validation on every model object." It is the demo everyone writes and the design that regresses performance and debuggability; the expected senior answer names the cost before the trick.
Optional chaining, nullish coalescing and logical assignment — what exactly do they test for?mid

?. short-circuits the whole chain to undefined when the left side is null or undefined — and only those two — including for calls (fn?.()) and indexes (a?.[i]). ?? falls back only on null/undefined, which is precisely why it beats || for numbers and strings: count || 10 replaces a legitimate 0, count ?? 10 does not. ??=, ||= and &&= (ES2021) assign conditionally and short-circuit the assignment itself, so a setter is not invoked when the condition fails. Under strictNullChecks TypeScript will flag ?. on a value that cannot be nullish, which is a useful signal that a type or a guard is wrong.

const timeout = options.timeoutMs ?? 30_000;     // 0 stays 0
const name = user?.profile?.displayName ?? 'anon';
cache.entry ??= await load();                    // assign only if null/undefined
const n = list?.length ?? 0;
Follow-ups
  • Does ?. swallow errors? No — only nullish access; calling a non-function still throws a TypeError.
  • Why can't you mix ?? with ||/&& unparenthesised? The grammar forbids it deliberately, because the precedence would be a coin flip for readers.
  • Overuse smell? Long a?.b?.c?.d chains usually mean the data was never validated at the boundary — fix the parse, not the access.
Common wrong answer"?? and || are the same." They differ on every falsy-but-valid value — 0, '', false, NaN — and that difference is behind a large share of "why is my configured value being ignored" bugs.
Map/Set/WeakMap versus a plain object — how do you choose?senior

Use a Map when keys are dynamic, non-string, or user-controlled: it preserves insertion order, accepts any value as a key (objects included), has a real size, iterates without prototype surprises, and does not risk prototype pollution from a key called __proto__. Plain objects still win for fixed, known-at-author-time shapes: they are JSON-serialisable, monomorphic and faster for small record-like access. WeakMap/WeakSet hold keys weakly, so entries vanish when the key object is collected — the correct structure for per-object metadata caches that must not pin their keys, and the reason they are non-iterable. Performance-wise, Map is generally faster for frequent add/delete of many keys; the object's advantage is inline caching on stable shapes.

const meta = new WeakMap<object, Meta>();      // entries die with their keys
const byId = new Map<string, Row>();           // dynamic keys, ordered, size
const FLAGS = { darkMode: true } as const;      // fixed shape, serialisable
Follow-ups
  • What equality does Map use? SameValueZero: NaN matches NaN, +0 and -0 are the same key, objects by identity.
  • How do you serialise a Map? JSON.stringify gives {}; convert with [...map] and rebuild on read — a very common bug in cached payloads.
  • ES2026 relevance? Map.prototype.getOrInsert/getOrInsertComputed (the "upsert" proposal) removes the has/get/set dance for memo tables.
Common wrong answer"Objects and Maps are basically the same, use whichever." The differences that matter — prototype-key collisions with untrusted input, non-string keys, and iteration order guarantees — are exactly the ones that produce security and correctness bugs.

05 Generics & type-level programming

This is the unit that decides whether you are hired as a senior or a lead on a TypeScript-heavy team, because it is where shared libraries, framework code and internal DX live. The progression interviewers walk is predictable: constraints and keyof at mid level, mapped and conditional types with infer at senior, then variance, inference control and — the real principal question — when to stop, because a clever type that produces a forty-line error message costs more than the any it replaced.

What problem do generics solve, and what does extends mean in a type parameter?mid

A generic parameterises a type over another type so that a relationship between inputs and outputs survives the call — without one, identity(x: any): any loses everything. extends in a type-parameter position is a constraint: it says which types may be substituted, and it is what lets the body use members safely. Defaults (<T = string>) fill in when inference has nothing to work with. The rule of thumb interviewers listen for: a type parameter that appears only once in the signature is not doing any work and should be a plain type.

function pluck<T, K extends keyof T>(items: readonly T[], key: K): T[K][] {
  return items.map(i => i[key]);
}
const names = pluck(users, 'name');   // string[] — inferred, not asserted
pluck(users, 'nope');                 // error: not a key of User
Follow-ups
  • When is a type parameter pointless? When it occurs once — function log<T>(x: T): void is just unknown with extra ceremony.
  • Constrain to an object? extends object or extends Record<string, unknown>; avoid extends {}, which also accepts strings and numbers.
  • Generic classes vs generic methods? Put the parameter at the narrowest scope that still expresses the relationship.
Common wrong answer"Generics are for reuse, like C# generics — same thing." Similar syntax, different semantics: TypeScript generics are erased entirely (no reified type at runtime, no typeof(T)) and are structural, so constraints are shape checks, not class hierarchies.
Explain keyof, typeof, indexed access types and Record.mid

keyof T is the union of T's keys. typeof x in type position lifts a value into the type world — the bridge that makes as const tables useful. T[K] is indexed access: the type of that property, and T[keyof T] is the union of all property types. Record<K, V> builds an object type from a key union and a value type, and using a literal union as K makes the record exhaustive — add a variant to the union and every table missing an entry fails to compile.

const HANDLERS = { click: onClick, keydown: onKey } as const;
type EventName = keyof typeof HANDLERS;         // 'click' | 'keydown'
type Handler   = (typeof HANDLERS)[EventName];  // union of the function types

type Labels = Record<Status, string>;           // must cover every Status
Follow-ups
  • keyof on a type with an index signature? Yields string | number, which is usually a sign the type is too loose to be useful.
  • Why is Record<string, T> risky? Every lookup claims to return T; turn on noUncheckedIndexedAccess so it returns T | undefined.
  • How do you get a union of values? T[keyof T] — the idiom behind the const-object-instead-of-enum pattern.
Common wrong answerConfusing keyof typeof obj with keyof Obj for a value versus a type, and then reaching for as when it does not compile. The typeof bridge is the piece being tested.
Write a mapped type. How do you add or remove readonly/optional, and how do you rename keys?senior

A mapped type iterates a key union to build a new object type: { [K in keyof T]: F<T[K]> }. Modifiers can be added (readonly, ?) or removed with the - prefix — that is exactly how Required<T> and Mutable<T> are written. Key remapping with as (TS 4.1) lets you rename or filter keys: mapping a key to never drops it, which is how you build "only the function-valued properties" or "getters for every field" types.

type Mutable<T>  = { -readonly [K in keyof T]: T[K] };
type Required2<T> = { [K in keyof T]-?: T[K] };
type Getters<T>   = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] };
type OnlyFns<T>   = { [K in keyof T as T[K] extends Function ? K : never]: T[K] };
Follow-ups
  • Why does mapping lose the original's JSDoc and name? Mapped types produce anonymous types; that is the readability tax, and a reason to alias them well.
  • Homomorphic mapped types? When the type is { [K in keyof T]: ... } over a bare T, modifiers and array/tuple-ness are preserved — Partial<string[]> stays an array.
  • Mapping over a union? Distribute first with a conditional, or you map over the union's common keys only.
Common wrong answerWriting { [K in keyof T]?: T[K] } and calling it DeepPartial. It is one level; a real deep variant needs recursion plus care with arrays, tuples, Date and functions — and interviewers ask exactly that follow-up.
Explain conditional types and infer.senior

A extends B ? X : Y is a type-level branch resolved by assignability. infer declares a placeholder inside the extends clause and binds whatever matches, which is how you destructure types: element type of an array, resolved type of a promise, return type or parameter tuple of a function. The whole utility-type library is built from these two features, and being able to write Awaited-like recursion from memory is the standard senior probe.

type ElementOf<T>  = T extends readonly (infer U)[] ? U : never;
type Unwrap<T>     = T extends Promise<infer U> ? Unwrap<U> : T;   // recursive, like Awaited
type FirstArg<F>   = F extends (a: infer A, ...rest: never[]) => unknown ? A : never;
type Route<S>      = S extends `${string}:${infer P}/${infer Rest}` ? P | Route<Rest> : never;
Follow-ups
  • What limits recursion? An instantiation-depth cap (~50 by default, with a tail-recursion optimisation since 4.5); exceeding it is a hard error, not a slowdown.
  • Multiple infer sites for the same variable? In a covariant position they union, in a contravariant position they intersect — a favourite trick question.
  • infer U extends string? TS 4.8 constrained infer, which avoids a second nested conditional just to narrow.
Common wrong answerTreating conditional types as runtime branching ("it picks the type based on the value"). They are resolved entirely by the checker on types; nothing about them exists at runtime.
What is a distributive conditional type, and how do you switch distribution off?senior

When the checked type is a naked type parameter and the argument is a union, the conditional distributes over each member and unions the results. That is why Exclude<'a'|'b'|'c', 'a'> works at all. It also produces surprises: T extends unknown[] ? ... : ... applied to a union evaluates per member, and never as input yields never because distributing over the empty union produces nothing. Wrapping both sides in a tuple — [T] extends [U] ? X : Y — makes it non-distributive and checks the union as a whole, which is how IsNever and most "does this union contain…" helpers are written.

type Boxed<T>     = T extends unknown ? { v: T } : never;
type A = Boxed<string | number>;    // { v: string } | { v: number }  (distributed)

type IsNever<T>   = [T] extends [never] ? true : false;
type NonDist<T>   = [T] extends [string] ? 'all strings' : 'mixed';
type B = NonDist<string | number>;  // 'mixed'
Follow-ups
  • Why does Exclude<never, 'a'> give never? Distribution over an empty union produces an empty union.
  • Does distribution apply to boolean? Yes — boolean is true | false, so conditionals split it, which surprises people building flag types.
  • Performance angle? Distributing over a large union multiplies work; unions of hundreds of literals in a recursive conditional are a known check-time cliff.
Common wrong answer"Conditional types always evaluate the union as one type." Then Exclude and every filter utility become inexplicable, and the candidate cannot debug the never that appears out of nowhere.
Where are template literal types genuinely useful?senior

Template literal types (TS 4.1) build string literal types from other types, and combined with infer they can parse strings at the type level. The uses that pay for themselves are API surfaces where strings carry structure: event names (on${Capitalize<K>}), CSS or design tokens, i18n key checking, route parameter extraction, SQL-ish or query-builder DSLs, and prefixed environment variables. The intrinsic helpers Uppercase, Lowercase, Capitalize, Uncapitalize are compiler built-ins, not library types.

type Params<P extends string> =
  P extends `${string}:${infer K}/${infer R}` ? { [X in K | keyof Params<R>]: string }
  : P extends `${string}:${infer K}`          ? { [X in K]: string }
  : {};

declare function link<P extends string>(path: P, params: Params<P>): string;
link('/users/:id/posts/:postId', { id: '1', postId: '2' });  // both keys required, checked
Follow-ups
  • What is the cost? Cross-product explosion: a union of 50 prefixes times 50 suffixes is 2 500 literal types, and the checker feels it.
  • When would you not do this? When a plain object argument would be clearer — string-parsing types are impressive in a demo and brutal in an error message.
  • Do these help at runtime? Not at all; you still parse the string yourself.
Common wrong answerReaching for a template-literal DSL as the first answer to every string-shaped problem. The senior-level answer names the compile-time cost and the error-message cost before the feature.
Explain variance in TypeScript. What does strictFunctionTypes change?senior

Variance describes how assignability of a container follows assignability of its parameter. Return positions are covariant (a function returning Dog is usable where one returning Animal is expected); parameter positions should be contravariant (a handler accepting Animal is usable where one accepting Dog is expected). TypeScript checks function type parameters contravariantly only under strictFunctionTypes, and — deliberately — never for methods declared with method syntax, which stay bivariant so that array and DOM APIs keep working. Since 4.7 you can annotate variance explicitly with in/out on type parameters, which is mainly a check-time optimisation and a documentation device for large invariant generics.

interface Handler<in T> { (value: T): void }        // explicitly contravariant
declare let animalH: Handler<Animal>;
declare let dogH: Handler<Dog>;
dogH = animalH;   // OK: an Animal handler can handle Dogs
animalH = dogH;   // error under strictFunctionTypes — Dog handler can't take any Animal

interface Bad { onEvent(e: Animal): void }          // method syntax: still bivariant, unsound
Follow-ups
  • Why keep method bivariance? Backwards compatibility with Array<T> and event-handler patterns; making it sound would break most real code.
  • Are arrays covariant? Yes, and unsoundly so — you can push a Cat through an Animal[] alias of a Dog[]. Use readonly T[] where you only read.
  • When do in/out annotations pay? On large recursive generic interfaces where the checker's structural variance computation is the bottleneck.
Common wrong answer"TypeScript is covariant everywhere" or "variance doesn't exist in a structural system". Both miss the practical consequence: callbacks declared as methods are checked more loosely than callbacks declared as properties, and that is a real bug source.
Which built-in utility types should be second nature, and what do they hide?mid

Partial, Required, Readonly, Pick, Omit, Record, Exclude, Extract, NonNullable, ReturnType, Parameters, ConstructorParameters, InstanceType, Awaited, NoInfer (TS 5.4). The one worth a caveat is Omit: it is key-based and non-distributive, so omitting from a union collapses it to the common keys, and it silently accepts keys that do not exist — Omit<User, 'nmae'> compiles. Teams that care write a stricter StrictOmit constrained to keyof T, and a DistributiveOmit for unions.

type DistributiveOmit<T, K extends PropertyKey> = T extends unknown ? Omit<T, K> : never;
type StrictOmit<T, K extends keyof T> = Omit<T, K>;

declare function pick<T>(v: T, fallback: NoInfer<T>): T;   // fallback can't widen T
Follow-ups
  • Why does Omit on a discriminated union break narrowing? It flattens to the intersection of keys, losing the discriminant per member — hence the distributive variant.
  • What is NoInfer for? Blocking a parameter from participating in inference, so a default or fallback argument cannot widen the inferred type.
  • Awaited<T> vs UnwrapPromise? Awaited is recursive and handles thenables correctly; hand-rolled versions usually do not.
Common wrong answer"Omit is type-safe, it errors on a bad key." It does not, by design, and that typo has shipped more than one wrong API shape.
Why does my generic infer string instead of the literal, and how do you control inference?senior

Inference widens literals by default because most values are meant to be mutable. Three levers fix it: constrain the parameter to a literal-ish type (T extends string makes the literal survive), use as const at the call site, or — since TS 5.0 — declare a const type parameter (<const T>) so arguments are inferred as if written with as const. Related gotchas: inference from a later parameter can widen an earlier one (fix with NoInfer), a type parameter used only in a return position infers unknown, and providing one type argument explicitly forces you to provide all of them unless the rest have defaults.

declare function route<const T extends readonly string[]>(paths: T): T;
const r = route(['/a', '/b']);        // readonly ['/a', '/b'] — not string[]

declare function tag<T extends string>(t: T): T;
tag('ok');                            // 'ok' — the constraint keeps it literal
Follow-ups
  • Why not just as const everywhere? It pushes the burden onto every caller; const type parameters move it into the API where it belongs.
  • What happens with multiple candidates? The checker picks the best common supertype; conflicting candidates widen to a union or fail.
  • Partial type-argument inference? Still not supported (the perennial request); the workaround is a curried factory that fixes one parameter and infers the rest.
Common wrong answerFixing widening with as at every call site. It compiles, hides genuine mismatches, and leaves the API just as awkward for the next caller.
When does type-level programming stop paying for itself?principal

When the cost lands on people who did not write it. Three measurable signals: check time (a recursive conditional over a large union can add seconds to every editor keystroke — tsc --extendedDiagnostics and --generateTrace tell you which types), error-message quality (if a one-character mistake yields a screenful of instantiation stack, juniors will "fix" it with any), and turnover risk (types only one person can modify are a bus factor of one). The principal-level answer offers a policy, not an opinion: clever types belong behind a package boundary with tests (expectTypeError, tsd/vitest type tests), a documented rationale, and a simpler fallback signature; application code should prefer boring types plus runtime validation.

The 2026 wrinkle worth naming: TypeScript 7.0's Go-based compiler makes full builds roughly 10× faster and cut memory noticeably, which changes the arithmetic — but it does not make an exponential type cheap. It removes the excuse for slow projects, not for pathological types.

Follow-ups
  • How do you measure? tsc --diagnostics/--extendedDiagnostics for totals, --generateTrace plus the trace analyzer for hot types, and an editor-responsiveness check on the worst file.
  • Budget you would set? A CI check that check time and instantiation count do not regress beyond a threshold — same discipline as a bundle-size budget.
  • How do you say no in review without demoralising? Ask for the error message the type produces when misused, and let that decide.
Common wrong answer"More types are always better — if it compiles, it's safer." At lead level this is the wrong instinct: types are code, they have maintenance and performance costs, and a type nobody can read is a comment that lies with compiler backing.

06 Values, equality & coercion

Frequently asked because it is quick to test and quick to fail. The screener version is == versus ===; the useful version is whether you can predict coercion instead of avoiding it, whether you understand floating point well enough not to store money in a number, and whether you have a defensible team policy on null versus undefined. At senior level the Unicode question separates people who have shipped internationalised software from people who have not.

What are JavaScript's types, and why does typeof null return 'object'?screener

Seven primitives — string, number, bigint, boolean, undefined, symbol, null — plus objects (functions included). Primitives are immutable and compared by value; objects are compared by reference. typeof null === 'object' is a bug from the first implementation: values were tagged and the null pointer's tag collided with the object tag. It was proposed for a fix and rejected because too much code depends on it. The practical consequence is that a null check needs x === null or x == null (which catches both null and undefined), never typeof.

typeof null;          // 'object'  — historical bug
typeof undefined;     // 'undefined'
typeof function(){};  // 'function' — not a separate type, a callable object
typeof NaN;           // 'number'
Array.isArray([]);    // true — typeof [] is 'object'
Follow-ups
  • How do you reliably tag a value? Object.prototype.toString.call(x) for built-ins, Array.isArray, instanceof within one realm, or a schema validator at boundaries.
  • Why do primitives have methods? Autoboxing: 'a'.toUpperCase() wraps in a temporary String object and discards it.
  • Is document.all really falsy? Yes — a spec-mandated legacy quirk, and the only object with typeof 'undefined'.
Common wrong answerListing arrays and null as their own types, or claiming function is a primitive type. It signals a memorised list rather than a model of values versus references.
==, ===, Object.is — and what is special about NaN?screener

=== compares type and value with no coercion, except that NaN !== NaN and +0 === -0. == applies the abstract equality algorithm: null == undefined (and nothing else), numbers and strings compare numerically, booleans coerce to numbers, and objects coerce via Symbol.toPrimitive/valueOf/toString — which is where [] == false and '0' == false come from. Object.is is === with two corrections: NaN equals itself and +0 does not equal -0. Map/Set use SameValueZero, which is Object.is except that +0 and -0 are the same key.

0 == '';            // true       0 === '';           // false
null == undefined;  // true       null === undefined; // false
NaN === NaN;        // false      Object.is(NaN, NaN);// true
Object.is(0, -0);   // false      [NaN].includes(NaN);// true (SameValueZero)
[NaN].indexOf(NaN); // -1 (uses ===)
Follow-ups
  • Any acceptable use of ==? One: x == null as a concise "null or undefined" check — eqeqeq lint rules have a smart/null exception for it.
  • How do you detect NaN? Number.isNaN (ES2015), never the global isNaN, which coerces (isNaN('abc') is true).
  • Where does -0 ever matter? Division sign (1/-0 === -Infinity), and in numeric keys — rare, but it is the reason Object.is exists.
Common wrong answer"== compares value, === compares value and type." A memorised slogan that does not predict [] == ![] being true; the expected answer names coercion, not "type".
Which values are falsy, and what bugs does that cause?mid

Exactly eight: false, 0, -0, 0n, '', null, undefined, NaN. Everything else is truthy, including [], {}, '0', 'false' and every function. The bug pattern is always the same: using truthiness as an existence check on a value that can legitimately be zero or empty. if (count) skips zero; if (name) rejects an empty string a user deliberately entered; value || default overrides a valid false. The fix is to check what you mean — != null, ?? , or an explicit length/NaN test.

if (opts.retries) use(opts.retries);            // silently ignores retries: 0
if (opts.retries !== undefined) use(opts.retries);
const port = env.PORT ?? 3000;                   // '' would still slip through — validate instead
Follow-ups
  • Is [] == false true? Yes — both coerce to 0 — while [] alone is truthy. Coercion in == and truthiness are two different algorithms.
  • Does TypeScript help? Partly: strictNullChecks plus explicit unions catches many, and @typescript-eslint/strict-boolean-expressions catches the rest at the cost of noise.
  • Filtering nullables? arr.filter(x => x != null) narrows correctly in TS 5.5+; filter(Boolean) also drops 0 and ''.
Common wrong answer"Empty arrays and empty objects are falsy." They are truthy — a mistake with real consequences in guard clauses, and one that C#, Python and Ruby habits actively encourage.
Explain coercion: how does + differ from -, and how does an object become a primitive?mid

+ is overloaded: if either operand becomes a string after primitive conversion, it concatenates; otherwise it adds numerically. Every other arithmetic operator converts to number unconditionally. Object-to-primitive conversion consults Symbol.toPrimitive first; failing that it tries valueOf then toString for a "number" or "default" hint, and toString then valueOf for a "string" hint. That is the whole explanation for the party tricks: [] + {} is '[object Object]' because both stringify, while [] - 1 is -1 because [] numifies to 0.

1 + '2';        // '12'   — string wins for +
'3' - 1;        // 2      — numeric conversion
[] + {};        // '[object Object]'
[1,2] + '';     // '1,2'  — Array#toString joins with commas
new Date() - 0; // epoch ms — Date's valueOf returns a number
`${obj}`;       // string hint: toString first
Follow-ups
  • Why is Date special? Its Symbol.toPrimitive defaults to the string hint for +, which is why date + 1 concatenates but date - 1 subtracts.
  • How do you make your own class coerce sensibly? Implement Symbol.toPrimitive(hint) and return a number for 'number', a formatted string for 'string'.
  • Safe conversion of user input? Number(x) is strict about whitespace-only and rejects garbage as NaN; parseInt stops at the first invalid character and needs an explicit radix.
Common wrong answer"JavaScript coercion is random / you just have to memorise it." It is a small, specified algorithm; interviewers ask precisely to see whether you know the rules or fear them.
Why is 0.1 + 0.2 !== 0.3, and how do you handle money?mid

number is IEEE-754 binary64: 0.1 and 0.2 have no exact binary representation, so the sum is 0.30000000000000004. Integers are exact only up to Number.MAX_SAFE_INTEGER (2^53 − 1 = 9 007 199 254 740 991), which is why 64-bit database ids must travel as strings. For comparisons use a tolerance (Math.abs(a - b) < Number.EPSILON * Math.max(1, Math.abs(a), Math.abs(b))), and for money use integer minor units (cents as number or bigint) or a decimal library — then format with Intl.NumberFormat, never with hand-rolled rounding. BigInt is arbitrary-precision integer only: no decimals, no mixing with number in arithmetic, and JSON.stringify throws on it.

0.1 + 0.2;                       // 0.30000000000000004
(0.1 + 0.2).toFixed(2);          // '0.30' — display only, never arithmetic
9007199254740993;                // 9007199254740992 — silently wrong
BigInt('9007199254740993');      // exact
new Intl.NumberFormat('de-DE', { style: 'currency', currency: 'EUR' }).format(1234.5); // '1.234,50 €'
Follow-ups
  • Why not toFixed for rounding money? It rounds inconsistently at ties across values and returns a string; do the arithmetic in minor units and format once.
  • Does Math.sumPrecise help? Yes for summing many floats without accumulated error — an ES2026 addition; it does not make binary floats decimal.
  • JSON and big ids? JSON.parse loses precision silently; ES2026's source-text access proposal lets a reviver see the original digits, which is how you can round-trip int64 safely.
Common wrong answer"Round with toFixed(2) and you're fine." It converts to a string, uses binary rounding underneath, and stacks error across operations — the reason ledgers drift by cents.
What is a JavaScript string made of, and where does that bite?senior

Strings are sequences of UTF-16 code units. Characters outside the BMP — most emoji, many CJK extensions — are surrogate pairs, so '😀'.length is 2, slice can split a character in half, and reversing by index produces mojibake. Iterating with for...of or spreading yields code points, which is better but still not user-perceived characters: a flag or a family emoji is several code points joined by ZWJ. For real text you need Intl.Segmenter (grapheme clusters), and for comparison you need String.prototype.normalize() because 'é' has two encodings, plus localeCompare/Intl.Collator for sorting.

'😀'.length;                       // 2
[...'😀'].length;                  // 1 (code points)
'é' === 'é';            // false
'é'.normalize('NFC') === 'é'; // true
const seg = new Intl.Segmenter('en', { granularity: 'grapheme' });
[...seg.segment('👩‍👩‍👧')].length;  // 1 grapheme, 5 code points
Follow-ups
  • Truncating a display string safely? Segment by grapheme, then slice — never slice(0, n) on the raw string.
  • Validating a max length server-side? Decide and document the unit: code units, code points or bytes; mismatched units between client and server is a classic bug.
  • Sorting names? Intl.Collator with the user's locale; < compares code units and puts 'Z' before 'a'.
Common wrong answer"length gives the number of characters." It gives code units; every emoji-in-a-username bug and every off-by-one truncation in a notification comes from this assumption.
null or undefined? Set a policy for a codebase.senior

The language gives them different flavours: undefined means "absent" — an unset property, a missing argument, a value not yet assigned — and null means "explicitly empty". They diverge everywhere it matters: JSON.stringify drops undefined properties but keeps null; default parameters and destructuring defaults trigger on undefined only; Object.keys includes a key set to undefined; and databases have NULL but no undefined. A workable policy: use undefined internally and let it mean absent; accept null at wire boundaries and normalise it on parse; distinguish the two only where PATCH semantics need "clear this field" (null) versus "leave it alone" (absent), and turn on exactOptionalPropertyTypes so the type system can express that difference.

interface PatchUser { nickname?: string | null }   // absent = leave, null = clear, string = set
const clean = <T,>(v: T | null): T | undefined => (v === null ? undefined : v);
Follow-ups
  • Why not ban null outright? You cannot — the DOM, JSON and most drivers return it; you can only normalise at one boundary.
  • What does exactOptionalPropertyTypes change? { a?: string } no longer accepts an explicit a: undefined, so "absent" and "present but undefined" stop being interchangeable.
  • Effect on API design? Document the tri-state in the schema; a client that cannot express "clear the field" will send empty strings instead, and you will inherit them forever.
Common wrong answer"They're interchangeable, just pick one." True until the first PATCH endpoint, the first JSON.stringify round-trip, or the first default parameter that mysteriously does not apply.

07 Arrays, iterators & data transformation

Asked constantly in live-coding rounds, where the interviewer is watching your defaults: do you mutate shared data, do you reach for reduce when a loop is clearer, do you know which methods copy. The 2023–2025 additions changed the idiomatic answers — toSorted, at, Object.groupBy, iterator helpers — so this is a cheap place to sound current or dated.

map, filter, reduce: when is reduce the wrong tool?screener

map transforms one-to-one, filter selects, reduce folds a sequence into an accumulator. reduce is the wrong tool whenever the accumulator is an object you spread on every iteration — that is O(n²) and unreadable — or when the operation is really a loop with early exit, which reduce cannot do. Prefer for...of for side effects and early exit, flatMap for one-to-many, Object.groupBy/Map.groupBy (ES2024) for grouping, and reduce mainly for genuine folds: sums, mins, merges of a fixed shape.

// O(n²) and a common review finding
const byId = rows.reduce((acc, r) => ({ ...acc, [r.id]: r }), {});
// O(n)
const byId2 = new Map(rows.map(r => [r.id, r] as const));
const byStatus = Object.groupBy(rows, r => r.status);   // ES2024
Follow-ups
  • Why is spreading in a reduce quadratic? Each iteration copies the whole accumulator — n copies of average size n/2.
  • Early exit from map? Not possible; use some/find/for...of. Throwing to break out of a callback is a smell.
  • Chained map().filter().map() over a million rows? Three passes and two intermediate arrays — one loop, or lazy iterator helpers.
Common wrong answerUsing reduce as a general-purpose loop to look clever. Interviewers read it as a readability judgment failure, not as functional sophistication — especially at lead level, where you set the house style.
Which array methods mutate, and what are the copying alternatives?mid

Mutating: push, pop, shift, unshift, splice, sort, reverse, fill, copyWithin. ES2023 added non-mutating twins — toSorted, toReversed, toSpliced, with — available in every current browser and Node 20+, and they are now the idiomatic choice in any code holding shared or reactive state. at() (ES2022) gives negative indexing, so arr.at(-1) replaces arr[arr.length - 1]. In TypeScript, typing a parameter as readonly T[] makes the mutating methods a compile error, which is the cheapest way to enforce this at a boundary.

function topThree(rows: readonly Row[]): Row[] {
  return rows.toSorted((a, b) => b.score - a.score).slice(0, 3); // input untouched
}
const patched = rows.with(2, { ...rows[2], seen: true });        // copy with one index replaced
const last = rows.at(-1);                                        // Row | undefined
Follow-ups
  • Cost of the copying versions? One allocation of n — fine for UI-sized data, worth avoiding in a hot loop over millions.
  • What does readonly T[] actually prevent? Calling mutators and assigning to indices; it does not deep-freeze, and a plain T[] is still assignable to it.
  • Legacy pattern to recognise? [...arr].sort() — correct, and now redundant.
Common wrong answer"sort returns a new array." It sorts in place and returns the same reference — the bug that silently reorders props, store state or a cached array shared with another component.
What is wrong with [10, 9, 100].sort()?mid

The default comparator converts every element to a string and compares UTF-16 code units, so you get [10, 100, 9]. Always pass a comparator for numbers. The comparator must be consistent — return a negative number, zero or a positive number, be antisymmetric and transitive — or the result is implementation-defined; returning a boolean (a common slip) coerces to 0/1 and produces a subtly wrong order. Sort has been required to be stable since ES2019, so equal elements keep their relative order, which is what makes multi-key sorting by successive passes valid.

[10, 9, 100].sort();                       // [10, 100, 9]
[10, 9, 100].toSorted((a, b) => a - b);    // [9, 10, 100]
rows.toSorted((a, b) => a.name.localeCompare(b.name, 'de') || a.id - b.id); // locale + tiebreak
[3, 1, 2].sort((a, b) => a > b);           // wrong: boolean comparator
Follow-ups
  • Sorting objects by several keys? One comparator with || chaining, or successive stable sorts from least to most significant key.
  • Sorting user-visible strings? localeCompare/Intl.Collator; code-unit order is wrong for accents and case.
  • Where do undefineds go? Always to the end, regardless of the comparator — the spec sorts them last without calling it.
Common wrong answer"sort is numeric by default for a number array." Extremely common, and it produces a plausible-looking wrong order that survives small test data and breaks on real data.
Iterables versus array-likes, and how do generators fit in?mid

An iterable implements Symbol.iterator: Array, String, Map, Set, NodeList, arguments, typed arrays, generators. An array-like merely has length and numeric keys and may not be iterable — old DOM collections, arguments in legacy code. Spread and for...of need iterability; Array.from handles both and takes a mapping function, so Array.from({ length: 5 }, (_, i) => i) is the idiomatic range. Generators (function*) are the easy way to author custom iterables: yield produces lazily, and yield* delegates.

function* chunk<T>(items: Iterable<T>, size: number): Generator<T[]> {
  let buf: T[] = [];
  for (const item of items) { buf.push(item); if (buf.length === size) { yield buf; buf = []; } }
  if (buf.length) yield buf;
}
for (const batch of chunk(rows, 500)) await insert(batch);   // constant memory
Follow-ups
  • Are generators reusable? No — the generator object is a one-shot iterator; return a fresh one from a factory (or implement Symbol.iterator on a class).
  • What does gen.return() do? Runs finally blocks and finishes the generator — how break in a for...of triggers cleanup.
  • Spread on a Map? Gives [key, value] pairs — the basis of Object.fromEntries([...map]).
Common wrong answer"You can spread anything object-like." Spreading a non-iterable in an array literal throws; only object spread ({ ...obj }) works on plain objects, and that copies properties, not elements.
What are iterator helpers, and when do they beat array methods?senior

ES2025 added map, filter, take, drop, flatMap, reduce, toArray, some, every, find directly on Iterator.prototype, plus the Iterator global and Iterator.from. They are lazy and single-pass: no intermediate arrays, and take(10) stops the producer after ten items, so they work on infinite generators and on streams where array methods cannot. Use them when the source is a generator, a Map/Set, or a large sequence you only partly consume; stick with array methods when you already have an array and need multiple passes or random access. ES2026 adds Iterator.concat for sequencing several iterables lazily.

function* naturals() { for (let i = 1; ; i++) yield i; }
const firstSquares = naturals().map(n => n * n).filter(n => n % 2 === 1).take(5).toArray();
// [1, 9, 25, 49, 81] — nothing is materialised until toArray()
const activeNames = users.values().filter(u => u.active).map(u => u.name).take(20).toArray();
Follow-ups
  • Where are they available? All current browsers and Node 22+; check your minimum target before relying on them without a polyfill.
  • Do they replace lodash chains? For sequence work largely yes, and without the bundle cost or the eager evaluation.
  • Async iterator helpers? Still a separate, later proposal; today you compose async generators by hand.
Common wrong answerAssuming array methods are already lazy ("filter stops early when I only need one"). They always process the whole array and allocate a new one; laziness is exactly what the helpers add.
When do you reach for typed arrays and ArrayBuffer?senior

When the data is binary or numeric and large: file and network payloads, WebSocket frames, canvas pixels, audio, WASM memory, protocol parsing. A regular array of numbers is an array of boxed values with a flexible representation; a Float64Array is a contiguous block with no per-element overhead, which is both faster and predictable for the GC. ArrayBuffer is the raw bytes, a typed array is a typed view, and DataView is the view you use when endianness matters — network data is big-endian and the platform usually is not. Buffers are transferable: you can move one to a worker with zero copy, or share it via SharedArrayBuffer with Atomics when both sides need it (subject to cross-origin isolation headers in browsers). ES2025 added Uint8Array.prototype.toBase64/fromBase64, finally removing the btoa/binary-string dance.

const buf = new ArrayBuffer(16);
const view = new DataView(buf);
view.setUint32(0, 0xdeadbeef, false);       // false = big-endian, as on the wire
const b64 = new Uint8Array(buf).toBase64(); // ES2025
worker.postMessage(buf, [buf]);             // transfer: zero copy, buf is now detached
Follow-ups
  • What happens to a transferred buffer? It is detached — byteLength becomes 0 and any access throws; that is the price of zero copy.
  • Node's Buffer versus Uint8Array? Buffer is a Uint8Array subclass with extra methods; prefer plain Uint8Array in code shared with the browser.
  • Is SharedArrayBuffer usable in browsers? Only under cross-origin isolation (COOP/COEP headers) — a deployment decision, not just a code one.
Common wrong answer"Typed arrays are just faster arrays, use them everywhere." They are fixed-length, numeric-only, and lack most array conveniences; using them for ordinary object collections costs readability and buys nothing.

08 Modules, ESM/CJS & the build pipeline

Asked more often than candidates expect, because it is where teams actually lose days. The interviewer usually has a scar: a dual-published package that broke, a require() of ES Module error, a tree-shaking failure that doubled a bundle. Screeners want the ESM/CJS differences; mid level wants Node's resolution rules and import type; senior is expected to reason about exports maps, tree shaking and side effects; principal is asked how you govern bundle size rather than fix it once.

ESM versus CommonJS: what actually differs?screener

ESM is statically analysable: imports and exports are declarations hoisted before evaluation, bindings are live (the importer sees later reassignments), the module graph is resolved before any code runs, and modules are always strict with their own this === undefined. CommonJS is dynamic: require is a function call that runs at that point, executes the module synchronously, and returns a snapshot of module.exports. ESM supports top-level await; CJS cannot. ESM gives you import.meta.url instead of __dirname/__filename. Because ESM is static, bundlers can tree-shake it; CJS generally cannot be shaken safely.

// ESM: hoisted, live bindings, async graph
import { counter, bump } from './counter.js';
bump(); console.log(counter);       // sees the new value

// CJS: executed inline, snapshot
const { counter, bump } = require('./counter.js');
bump(); console.log(counter);       // stale copy
Follow-ups
  • Can CJS load ESM? Historically only via await import(); Node 22+ can require() a synchronous ES module (no top-level await) — unflagged and backported, which finally softens the split.
  • Can ESM load CJS? Yes — default import gives module.exports; named imports work only when Node's static analysis can detect them.
  • Why does ESM need file extensions? Spec resolution does no extension guessing; ./util must be ./util.js (which is why TS code imports the .js path).
Common wrong answer"They're the same, just different syntax." The live-bindings and static-graph differences are exactly what break real migrations, and dismissing them predicts a candidate who will "fix" a dual-package hazard with a bundler flag.
How does Node decide whether a file is ESM or CommonJS?mid

By extension first: .mjs is always ESM, .cjs always CommonJS. For .js, Node walks up to the nearest package.json and reads "type": "module" means ESM, absent or "commonjs" means CJS. TypeScript mirrors this with .mts/.cts and the nodenext module mode, which is the only mode that models Node's real behaviour — including that an ESM file's relative imports need extensions. Package entry points are a separate mechanism: the exports field maps subpaths to files per condition (import, require, types, node, browser, default) and, unlike main, it encapsulates — anything not listed cannot be imported at all.

{
  "name": "@acme/lib", "type": "module",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js", "require": "./dist/index.cjs" },
    "./package.json": "./package.json"
  }
}
Follow-ups
  • Why must "types" come first in a condition object? Conditions are matched in declaration order; a later types entry can be shadowed by import/require.
  • What is the dual-package hazard? The same package loaded as both ESM and CJS gives two module instances with separate state — two singletons, two registries, failing instanceof.
  • Deep imports? Blocked once exports exists unless you list them — a feature, but a breaking change for consumers who relied on internal paths.
Common wrong answer"Set type: module and you're done." Without matching exports conditions, correct extensions in relative imports, and a TypeScript module setting of nodenext, you get runtime resolution errors that no amount of bundler configuration fixes.
Named or default exports? And what happens with circular imports?mid

Prefer named exports: they are refactor-safe (rename propagates), autocompletable, tree-shakeable, and they stop the same module being imported under five different local names. Default exports are worth it for a module whose whole purpose is one thing — a React component file, a config — and they are mandatory for some framework conventions. Circular imports are legal in ESM and usually work because bindings are hoisted and live, but they fail when a module reads an imported value during its own evaluation: the binding exists in the TDZ and you get a ReferenceError, or in CJS you get undefined instead of an error. The real answer is that a cycle is a design signal — extract the shared piece into a third module.

// a.ts
import { b } from './b.js';
export const a = () => b();          // fine: used later, not during evaluation
// b.ts
import { a } from './a.js';
export const b = () => 'b';
export const eager = a();            // ReferenceError: a is in the TDZ
Follow-ups
  • How do you find cycles? madge --circular, import/no-cycle in ESLint, or the bundler's own warning — and gate it in CI before the graph gets ugly.
  • Barrel files (index.ts re-exports)? Convenient and a common cause of cycles, slow cold builds and broken tree shaking; keep them at package boundaries, not inside a package.
  • Does export default hurt tree shaking? Not directly, but default-exporting an object of functions does — the whole object is retained.
Common wrong answer"Circular imports don't work in JavaScript." They do, often; the interesting answer is when they fail (value read during evaluation) and why ESM's failure mode is louder than CJS's.
What do import type, isolatedModules and verbatimModuleSyntax solve?mid

Single-file transpilers — esbuild, SWC, Babel, Vite, and Node's own type stripping — compile each file without a type checker, so they cannot know whether import { User } from './types' is a type (to be erased) or a value (to be kept). Getting it wrong either leaves a runtime import of a file with no runtime content or drops an import with a needed side effect. import type/export type states the intent explicitly; isolatedModules makes the compiler reject constructs that cannot be transpiled file-by-file; verbatimModuleSyntax (TS 5.0, replacing importsNotUsedAsValues/preserveValueImports) says: emit exactly what I wrote, dropping only type-marked imports. Together they are effectively mandatory in 2026, because almost nobody type-checks and emits with the same tool any more.

import type { User } from './types.js';        // erased, guaranteed
import { logger } from './logger.js';          // kept, side effects preserved
import { type Role, hasRole } from './auth.js'; // inline type specifier
Follow-ups
  • What else does isolatedModules forbid? const enum, re-exporting a type without export type, and non-module files in the program.
  • Does this matter if tsc emits? Less, but verbatimModuleSyntax still removes surprises in the emitted import list — and TS 7 no longer offers the legacy elision behaviour.
  • Relation to Node type stripping? Same constraint, stricter: Node erases without a checker at all, so anything non-erasable fails.
Common wrong answer"import type is just documentation." It changes emit. Omitting it is how a build ends up importing a .d.ts-only module at runtime, or dropping a polyfill import that only looked like a type.
How does tree shaking work, and what defeats it?senior

Bundlers build the ESM import graph, mark reachable exports, and drop the rest — but only when they can prove removal is safe. What defeats it: CommonJS (dynamic, unanalysable); module-level side effects (code that runs on import, like registering a polyfill or mutating a prototype); re-export barrels that pull in whole subtrees; class methods, since a class is retained wholesale once referenced; and getters or Object.defineProperty at module scope. Packages declare their cleanliness with "sideEffects": false (or an array of the files that do have side effects) — omit it and a conservative bundler keeps everything. Transpiler helpers matter too: TypeScript and Babel emit /*#__PURE__*/ annotations that let a bundler drop an unused call, and losing them in a custom pipeline silently inflates the output.

{ "sideEffects": ["./src/polyfills.js", "*.css"] }
Follow-ups
  • Does import lodash from 'lodash' shake? No — CJS; lodash-es or per-method imports do, and native alternatives usually beat both.
  • Why did my barrel double the bundle? Importing one symbol evaluates the whole barrel graph unless every module in it is side-effect free.
  • Code splitting versus shaking? Different tools: shaking removes dead code, splitting defers live code behind import() boundaries.
Common wrong answer"Tree shaking removes anything I don't use." It removes what the bundler can prove is unused; the interesting engineering is in making that proof possible.
Which moduleResolution should a project use in 2026?senior

nodenext for anything Node runs, bundler for anything a bundler resolves. Both understand the exports/imports fields; the old node/node10 algorithm does not, which is why a package with an exports map appears to have no types under it. This stopped being a preference in TypeScript 7.0: moduleResolution: node/node10 and classic were removed, along with target: es5, downlevelIteration, baseUrl, the amd/umd/systemjs module formats, and the ability to set esModuleInterop or allowSyntheticDefaultImports to false. TypeScript 6.0 deprecated all of them first and lets you keep going with "ignoreDeprecations": "6.0" — that release exists precisely as the migration step.

{ "compilerOptions": {
  "module": "nodenext", "moduleResolution": "nodenext",
  "target": "es2023", "lib": ["es2023"],
  "paths": { "@app/*": ["./src/*"] }
} }
Follow-ups
  • Why did baseUrl go? It made resolution depend on an implicit root; explicit relative paths entries are unambiguous and portable.
  • Do paths aliases work at runtime? No — TypeScript only rewrites types; the runtime needs bundler aliases, Node's imports field (#app/*), or a loader.
  • What is the fastest check that a dependency is packaged correctly? attw ("Are the types wrong?") plus publint in CI.
Common wrong answerRecommending "moduleResolution": "node" as the safe default. It is no longer available in TypeScript 7, and it was already the reason for most "cannot find module or its type declarations" reports against modern packages.
You are publishing a library used by both ESM and CJS consumers. How do you package it?senior

Build both formats, describe them with an exports map, and ship types per condition. Keep state out of module scope where you can, because the dual-package hazard means both copies may load: two instances, two caches, failing instanceof. If singleton state is unavoidable, keep it in one CJS core wrapped by an ESM façade, or key it on a Symbol.for registry so both copies find the same object. Ship .d.ts alongside each format (.d.mts/.d.cts when the syntax genuinely differs), verify with attw and publint, set "engines" honestly, and treat adding an exports map to an existing package as a breaking change because it removes deep imports.

{ "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js", "require": "./dist/index.cjs" },
    "./client": { "types": "./dist/client.d.ts", "browser": "./dist/client.browser.js", "default": "./dist/client.js" }
  },
  "sideEffects": false, "files": ["dist"], "engines": { "node": ">=20" } }
Follow-ups
  • Would you ship ESM only? Increasingly viable in 2026 — Node 22+ can require() sync ESM — but it still breaks older CJS consumers, so it is a major version with a migration note.
  • Bundle your dependencies? No for libraries (duplication, patchability); yes for leaf CLIs where startup time matters.
  • How do you avoid breaking type consumers? Snapshot the public .d.ts in CI (an API-extractor report) and review changes to it like an API diff.
Common wrong answer"Just publish ESM and let consumers transpile." It pushes your packaging problem onto every consumer's build, and for CJS-only test runners and older tooling it simply does not work.
The web bundle grew 40% in a quarter. How do you diagnose it and stop it recurring?principal

Diagnose with data: a bundle analyser on two builds (source-map-explorer, rollup-plugin-visualizer, webpack-bundle-analyzer) diffed by module, so you attribute the growth to specific dependencies or chunks rather than "the app got bigger". The usual suspects are a moment/lodash-shaped dependency pulled in whole, an icon or locale set imported as a barrel, a polyfill target regression (someone widened browserslist), duplicated versions of the same library from transitive ranges, and a lazy route that stopped being lazy because a shared import moved.

Stopping it is a process answer: a per-chunk size budget enforced in CI on the compressed size, a bot comment on every PR showing the delta, an owner for the budget, and a dependency-review rule that a new runtime dependency needs a size justification. Add "sideEffects" hygiene, keep route-level import() boundaries, and re-baseline deliberately rather than raising the limit whenever it goes red — the budget only works if going over it is an event.

Follow-ups
  • Which metric? Compressed transfer size per route plus the number of blocking requests — raw bytes flatter and mislead.
  • How do you find duplicate versions? npm ls <pkg> / lockfile inspection, then dedupe or an overrides/resolutions pin.
  • When is the bundle the wrong thing to optimise? When the field data says the bottleneck is server latency or render work — measure INP/LCP before spending a sprint on bytes.
Common wrong answer"Turn on more aggressive minification / switch bundlers." A one-time few percent against a structural problem. The expected lead-level answer is attribution plus a governing budget, not a tool swap.

09 TypeScript at scale: config & API boundaries

This unit is the difference between "writes TypeScript" and "owns TypeScript for a hundred engineers". It comes up in lead and principal loops as a scenario — a slow monorepo, a migration, a shared package whose types keep breaking consumers — and the questions are as much about process as about flags. It is also the most 2026-sensitive part of the topic, because the TypeScript 6.0 → 7.0 transition is a live migration in most organisations right now.

Walk through the tsconfig options that matter and why.mid

target sets the syntax level of the emit (and, with lib, which built-ins the checker believes exist); lib should be set explicitly when the runtime differs from the target, and DOM libs should be off in server code so document is not silently typed. module/moduleResolution must match how the code is actually loaded. jsx, paths, rootDir/outDir, declaration, sourceMap and skipLibCheck round out the set. How do you make a large monorepo type-check quickly?senior

Project references with composite: true: each package declares its dependencies, emits .d.ts, and tsc --build checks only what changed, reusing .tsbuildinfo for the rest. Consumers then type-check against generated declarations instead of re-checking source, which is the whole win — and it forces an explicit dependency graph, which catches accidental cycles between packages. Layer on incremental, a build-cache-aware task runner (Turborepo, Nx, Bazel) so CI restores unchanged package outputs, and skipLibCheck. The 2026 addition: TypeScript 7.0's native compiler is roughly 8–12× faster with parallel checking (--checkers, --builders), so many repos that needed references purely for speed now need them mainly for correctness and boundaries.

  • What is declarationMap for? Go-to-definition jumps to the source instead of the generated .d.ts — a large DX win in a references setup.
  • Where does it get slow anyway? Very large union or conditional types, deeply generic library types, and one enormous "shared types" package everything depends on.

Common wrong answer"Just run tsc --noEmit in CI and buy a bigger runner." It scales until it does not, and it gives contributors a fifteen-minute feedback loop locally — the thing that actually erodes type discipline.
Where should runtime validation live, and how do types relate to it?senior

At every trust boundary, exactly once: HTTP request bodies and query strings, third-party API responses, message-queue payloads, environment variables, localStorage, and anything read from a file. The discipline that makes it maintainable is deriving the static type from the schema rather than writing both — one source of truth that cannot drift. Inside the boundary you then work with parsed domain types and no defensive checks; outside it, nothing is trusted. This is also the answer to "TypeScript doesn't help at runtime": it is not supposed to, and the boundary is where you buy the guarantee.

import { z } from 'zod';
const Env = z.object({ PORT: z.coerce.number().int().positive().default(3000), DATABASE_URL: z.url() });
export const env = Env.parse(process.env);      // fails fast at boot, not at 3am
export type Env = z.infer<typeof Env>;          // type derived from the schema
Follow-ups
  • Cost on a hot path? Measurable for large payloads; compile-schema validators (Ajv with precompiled JSON Schema, TypeBox, Valibot's smaller runtime) or validating only the fields you use are the usual answers.
  • Schema-first or type-first? Schema-first when data crosses a wire; type-first for purely internal shapes. Never both by hand.
  • What about OpenAPI/protobuf? Generate types from the contract and validate against the same contract — the generator becomes the single source.
Common wrong answer"We type the response as User, that's enough." That is an assertion, not a check; a nullable field the backend added last week becomes a TypeError in production with a stack trace nowhere near the cause.
How do you design the types of a public API so it can evolve?senior

Treat the .d.ts as the API. Accept wide, return narrow: parameters as readonly and as loose as correctness allows, return types explicit and as specific as you can commit to — an inferred return type leaks internals and turns a refactor into a breaking change. Prefer a single options object over long positional parameters, because adding an option stays backwards compatible. Prefer discriminated unions over boolean flags and over overloads; overloads are for genuinely different shapes (like addEventListener), and they resolve top-down, so ordering is part of the contract. Mark evolution explicitly with @deprecated JSDoc (editors strike it through), and snapshot the public surface in CI so a type-level breaking change cannot merge unnoticed.

export interface QueryOptions { readonly limit?: number; readonly signal?: AbortSignal }
export function query(sql: string, opts?: QueryOptions): Promise<Result>;      // extensible

/** @deprecated since 3.2 — use `query(sql, { limit })` */
export function queryLimited(sql: string, limit: number): Promise<Result>;
Follow-ups
  • Why are inferred return types risky in a library? They expose internal type names and change silently; an explicit return type is a promise you can keep.
  • Is adding an optional property breaking? Not for consumers who only read it — but it is for anyone implementing your interface, so interfaces meant for implementation evolve differently from interfaces meant for consumption.
  • How do you version types? Semver on the package plus a generated API report reviewed in the PR; there is no separate type-version channel.
Common wrong answerAdding an overload for every new case until the signature list is unreadable and resolution order becomes load-bearing. A union parameter with a discriminant is almost always the better shape.
How would you migrate a large JavaScript codebase to TypeScript?senior

Incrementally, with the build always green. Turn on allowJs and check nothing at first; add checkJs with JSDoc types on the highest-value modules (JSDoc gets you most of the type system without renaming a single file); then convert file by file, leaf-first, starting where bugs actually cluster. Ratchet the strictness: noImplicitAny first, then strictNullChecks per directory, using a baseline file or @ts-expect-error with an owner and a date rather than blanket @ts-ignore. Ban new any with lint, track the count in CI so it can only fall, and — the part teams skip — convert the tests too, since untyped tests silently accept the wrong shapes.

Follow-ups
  • Big-bang codemod instead? Only for small repos; a mass conversion produces a PR nobody can review and a wall of any.
  • @ts-ignore or @ts-expect-error? Always expect-error — it fails when the underlying problem is fixed, so suppressions self-clean.
  • How do you keep momentum? Publish the coverage number, tie conversion to files people are already touching, and make new files TypeScript-only from day one.
Common wrong answer"Rename everything to .ts, add any where it complains, tighten later." "Later" does not arrive; you get the cost of TypeScript with none of the guarantee, and the team concludes TypeScript does not help.
Your repo is on TypeScript 6.0. What does moving to 7.0 involve?senior

7.0 (2026-07-08) is the Go-native port: the same type-checking semantics, structurally ported rather than rewritten, but a new binary and a much smaller option surface. The migration is mostly deleting deprecated configuration. Everything 6.0 deprecated is gone: target: es5, downlevelIteration, moduleResolution: node/node10 and classic, module: amd/umd/systemjs/none, baseUrl, outFile, and the ability to set esModuleInterop/allowSyntheticDefaultImports/alwaysStrict to false; namespaces can no longer be written with the module keyword, and Closure-style JSDoc is no longer understood. Defaults moved too — most notably types now defaults to [], so ambient @types packages must be listed. Tools that consume the TypeScript API programmatically (typescript-eslint, some bundler plugins, embedded-language servers for Vue/Angular/Svelte) may still need the JavaScript implementation, which ships as @typescript/typescript6 with a tsc6 binary for side-by-side use.

The order that works: upgrade to 6.0 first, set "ignoreDeprecations": "6.0", fix every deprecation warning while still on the old compiler, then flip to 7.0 and expect a build that is 8–12× faster with 6–26% less memory. Run both in CI for a sprint if your editor tooling is not ready.

Follow-ups
  • Will type errors change? The checker is a faithful port, so the answer is "not intentionally" — but message wording and some edge-case ordering differ, so expect churn in snapshot-tested error output.
  • What about --checkers? Parallel checking with a small worker count by default; --singleThreaded exists for constrained CI containers and for debugging.
  • Template literal types with emoji? 7.0 treats Unicode code points naturally rather than as UTF-16 surrogate pairs — a small but real behaviour difference.
Common wrong answer"It's a rewrite, so we should wait for it to stabilise." It is a port with the same semantics, and 6.0's deprecations exist to make the move mechanical; the risk is in your tooling integrations, not in the checker, and saying so is the informed answer.
How do you keep types honest in CI without slowing everyone down?senior

Separate the fast and the slow. Editors and pre-commit get the fastest possible feedback (incremental tsc --build --watch, or a lint-staged subset); CI runs one authoritative full check with a warm .tsbuildinfo cache restored from the previous run, in parallel with lint and tests rather than after them. Gate on things that cannot be argued about: no new any, no new suppressions, the public API report unchanged unless the PR says so, and check time within a budget. Keep the ratchets machine-enforced — human review does not reliably catch a slowly rising any count.

Follow-ups
  • Why not rely on the bundler's transpile? esbuild/SWC do not type-check at all; if tsc is not in CI, your types are decoration.
  • Monorepo affected-only checking? Fine for PRs with a correct dependency graph, but run the full check on main so a graph mistake cannot hide a break.
  • Flaky check times? Usually cache misses; measure cache hit rate as a first-class CI metric.
Common wrong answer"The IDE shows errors, so CI doesn't need to check." Different tsconfig, different version, different files open — the IDE is a convenience, not a gate.
Two teams want incompatible strictness settings in one monorepo. What do you do?principal

Allow local variation, forbid boundary variation. A per-package tsconfig extending a shared base is normal and healthy — a legacy package can sit at a lower rung while a new one runs every strict flag — but the published types of any package that others consume must meet the org standard, because a loose type crosses the boundary and infects consumers, while a loose internal implementation does not. Encode the standard as a versioned base config package, make each rung an explicit extend (@acme/tsconfig/strict, /legacy), report per-package conformance on a dashboard, and require an expiry date and an owner on any package still on the legacy rung. Then let teams schedule their own climb.

Say the trade-off out loud: uniformity is not the goal, predictable boundaries are. Forcing a flag day on a team mid-quarter buys a wall of suppressions and a lasting grudge against the standard.

Follow-ups
  • What if a team refuses entirely? Make the cost visible — incident attribution, review time — rather than escalating on principle; and hold the boundary rule regardless.
  • How do you prevent the "legacy" rung being permanent? Expiry dates in the config with a CI warning that becomes an error, and no new packages on it.
  • Is a single flag day ever right? For a small repo, yes; the cost scales with the number of teams who did not choose it.
Common wrong answer"Mandate the strictest setting everywhere from Monday." Technically defensible, organisationally naive: it produces mass @ts-ignore, which is strictly worse than an honest lower rung with a migration plan.

10 Performance, memory & the engine

Asked whenever the role owns a product with users, and almost always as a scenario rather than a definition. What is being tested is method: do you measure before you change anything, can you name what the engine is actually doing, and do you know which numbers matter to a user. Mid level should explain JIT and hidden classes at a working level; senior should profile and reason about GC pressure; principal should be able to install a performance budget that survives contact with a roadmap.

How does a modern engine execute JavaScript, and what are hidden classes and inline caches?mid

V8 parses to bytecode and runs it in the Ignition interpreter, collecting type feedback; hot functions are optimised by Sparkplug/Maglev/TurboFan into machine code, and are deoptimised back if an assumption breaks. Objects get a hidden class (a "shape" or "map") describing their layout; two objects created with the same properties in the same order share a shape, which lets a property access compile to a fixed offset. The call site caches that shape — an inline cache. A site that sees one shape is monomorphic and fast; a few shapes make it polymorphic; many make it megamorphic and it falls back to a dictionary lookup. Practical consequence: initialise all properties in the constructor, in a consistent order, and do not delete properties (that switches the object to dictionary mode).

// Same shape every time — monomorphic access sites
class Point { constructor(x, y) { this.x = x; this.y = y; } }
// Different shapes — the second object gets a new hidden class
const a = { x: 1, y: 2 };
const b = { y: 2, x: 1 };      // different property order = different shape
delete a.y;                     // pushes `a` into dictionary mode
Follow-ups
  • Does this mean I should hand-optimise everything? No — write clear, consistently shaped code; engines punish irregularity, not abstraction.
  • What triggers deoptimisation? A type the optimiser did not expect: a number field that suddenly holds a string, an array that becomes holey, an arity change.
  • Holey arrays? new Array(1000) or assigning past the end creates holes and a slower element kind; prefer push or Array.from({length}).
Common wrong answer"JavaScript is interpreted, so it's slow." It is JIT-compiled with type feedback and, for shape-stable numeric code, within small factors of native. The interesting answer is what makes it slow, not that it is.
How does garbage collection work, and what creates GC pressure?senior

V8 uses a generational collector on the weak generational hypothesis: most objects die young. New objects go into a small "young generation" collected by a fast copying scavenger; survivors are promoted to the old generation, collected by a mark-compact major GC that runs incrementally and concurrently to keep pauses small. Pressure comes from allocation rate, not from total size: a hot loop allocating a closure, an object literal, or an intermediate array per iteration keeps the scavenger running, and promoted-but-short-lived objects force expensive major GCs. Symptoms are sawtooth heap graphs and periodic latency spikes rather than a steady slowdown.

// Allocates a new array and a new closure per call — visible in a profile at high rates
const parse = (line) => line.split(',').map(s => s.trim());
// Reuse buffers and avoid intermediates on genuinely hot paths
const parseInto = (line, out) => { let i = 0, start = 0;
  for (let k = 0; k < line.length; k++) if (line[k] === ',') { out[i++] = line.slice(start, k); start = k + 1; }
  out[i++] = line.slice(start); return i; };
Follow-ups
  • How do you distinguish a leak from pressure? A leak is monotonic growth in retained heap across GCs; pressure is high allocation with a stable baseline.
  • Can you force GC? Only with --expose-gc for diagnostics; production code should never depend on GC timing, which is also why FinalizationRegistry is a poor design tool.
  • Node heap limits? --max-old-space-size; and in containers, set it below the cgroup limit or the OOM killer arrives before V8 collects.
Common wrong answer"Set variables to null to help the GC." Reachability is what matters; nulling a local that is about to go out of scope does nothing. It only helps for long-lived containers that genuinely hold references.
How do you benchmark a JavaScript change credibly?senior

Measure the thing users experience, in an environment like production, with enough repetitions to see variance. Microbenchmarks lie in specific ways: the JIT specialises to the benchmark, dead-code elimination removes work whose result is unused, the first iterations run unoptimised, and the GC's timing shifts cost between runs. So: warm up, run many iterations, report a distribution (median and p95) rather than a mean, keep the result alive, randomise order between variants, and compare against a control on the same machine in the same session. In the browser use the Performance API and performance.measure marks that show up in the profiler; in Node use perf_hooks, --cpu-prof and a harness like mitata/tinybench. Then confirm with field data — a lab win that does not move real-user metrics is not a win.

performance.mark('parse:start');
const rows = parse(payload);
performance.mark('parse:end');
performance.measure('parse', 'parse:start', 'parse:end'); // appears in the DevTools timeline
Follow-ups
  • Why report p95, not mean? Users feel the tail; a mean hides the bimodal distribution that a GC pause or a cache miss produces.
  • How many samples? Enough that a re-run of the control against itself shows less difference than the effect you claim.
  • Biggest microbenchmark trap? Comparing two implementations in one process, where the first one's feedback pollutes the second's inline caches.
Common wrong answer"I ran it in a loop with console.time and it was 3× faster." One sample, no warm-up, no variance, usually optimised away — the answer that most reliably ends a performance discussion badly.
Which web performance metrics matter, and how does JavaScript affect them?senior

Core Web Vitals in 2026 are LCP (largest contentful paint — loading), INP (Interaction to Next Paint — responsiveness; it replaced FID in March 2024) and CLS (layout stability). JavaScript is the main lever on INP: every long task blocks the main thread, so a click cannot be processed and painted. The mechanics to name are the long-task threshold (50 ms), that INP measures the worst (near-worst) interaction over the page's life rather than the first, and that the fix is usually yielding — break long work into chunks with await scheduler.yield() (or setTimeout/postTask), move computation to a worker, and defer non-urgent work with scheduler.postTask({ priority: 'background' }). JavaScript also affects LCP through parse/execute cost of the bundle and through render-blocking, and CLS through layout-shifting DOM insertions.

async function processAll(items) {
  for (const [i, item] of items.entries()) {
    handle(item);
    if (i % 50 === 0) await scheduler.yield();  // give input a chance to run
  }
}
Follow-ups
  • Lab or field? Both: Lighthouse to debug, RUM (web-vitals + your analytics, or CrUX) to decide — field data is what the ranking and your users reflect.
  • Why is INP harder than FID was? It covers every interaction and includes rendering, so slow re-renders count, not just a blocked first input.
  • Where does hydration fit? A large hydration pass is a long task at exactly the moment users first click — the classic INP regression in SSR apps.
Common wrong answerNaming FID as a current Core Web Vital, or optimising for a Lighthouse score rather than field percentiles. Both date the candidate and both lead to work that does not help users.
When do Web Workers or worker_threads actually help?senior

When the work is CPU-bound and long enough to pay for the transfer. Workers give real parallelism on separate threads with separate heaps; communication is by message passing with structured clone, which copies — so the break-even depends on payload size versus compute time. Use transferables (ArrayBuffer, MessagePort, ImageBitmap) to move data with zero copy, or SharedArrayBuffer plus Atomics when both sides need concurrent access (browser: requires cross-origin isolation). Good candidates: parsing or diffing large payloads, image and audio processing, crypto, compression, WASM workloads, and in Node a pool for CPU-heavy request handling. Bad candidates: I/O-bound work (already async), tiny tasks, and anything needing the DOM — workers have none.

// Node: a small pool so CPU work never blocks the request loop
import { Worker } from 'node:worker_threads';
const run = (data: ArrayBuffer) => new Promise((res, rej) => {
  const w = new Worker(new URL('./hash.worker.js', import.meta.url));
  w.once('message', res); w.once('error', rej);
  w.postMessage(data, [data]);          // transferred, not copied
});
Follow-ups
  • Cost of spawning? Milliseconds plus a fresh heap — pool workers, never spawn per request.
  • Does structuredClone handle everything? No functions, no DOM nodes, no class identity — design the message as plain data.
  • Node cluster versus worker_threads? cluster forks processes for connection-level scaling; worker_threads shares a process for CPU offload within one request path.
Common wrong answer"Put the async I/O in a worker so it doesn't block." I/O never blocked; you have added copying and a thread for nothing. Workers are for CPU, and saying otherwise reveals the same misunderstanding as "make it async so it doesn't block".
What is layout thrashing, and how do you spot it?mid

Reading a geometry property (offsetHeight, getBoundingClientRect, scrollTop, getComputedStyle) forces the browser to flush pending style and layout so the answer is current. Interleaving reads and writes in a loop therefore forces a synchronous layout per iteration — O(n) reflows instead of one. The fix is to batch: read everything, then write everything, ideally aligning the write phase with requestAnimationFrame. In DevTools it shows as a stack of purple "Layout" bars with the "Forced reflow" warning in the performance panel.

// Thrashing: read, write, read, write…
for (const el of items) el.style.height = `${el.offsetHeight * 2}px`;
// Batched: one layout, then one write pass
const heights = items.map(el => el.offsetHeight);
requestAnimationFrame(() => items.forEach((el, i) => { el.style.height = `${heights[i] * 2}px`; }));
Follow-ups
  • Which properties are cheap to animate? transform and opacity — composited, no layout or paint; animating top/width forces both.
  • What about ResizeObserver? It reports sizes without you measuring, and its callback runs at a point where measurement is already valid.
  • content-visibility? Lets the browser skip layout and paint for off-screen subtrees — a large win for long lists without virtualisation.
Common wrong answer"Wrap it in requestAnimationFrame" without separating reads from writes. The reflows still happen, just one frame later; the batching is the fix, not the callback.
A page feels sluggish only for some users. How do you find out why?senior

Start from field data segmented by device class, network, geography, browser and route, because "some users" is a segmentation statement. Collect RUM: the web-vitals library reporting LCP/INP/CLS with attribution (which element, which script, which interaction), long-task entries, and your own performance.measure marks around suspicious phases. Compare the p75 of the slow segment against the fast one to find the differing phase, then reproduce with CPU throttling (4–6×) and a throttled network — low-end Android is usually where the missing 90th percentile lives. Only then profile locally, and confirm the fix in the field, not in the lab.

Follow-ups
  • Common culprit for one segment only? A third-party script or an A/B variant loaded conditionally; unsampled RUM by variant finds it fast.
  • What if RUM does not exist? Adding it is the first fix — you cannot manage a distribution you cannot see, and CrUX gives you an origin-level baseline meanwhile.
  • Sampling rate? High enough to see p95 per route; sampling at 1% on a low-traffic route measures nothing.
Common wrong answer"It's fast on my machine, so it's their network." An M-series laptop on office fibre is not the population; the expected answer names segmentation and device-class throttling before any code change.
How do you stop performance regressing over a year, across several teams?principal

Make it a budget with an owner and a gate, not a campaign. Pick a small number of user-visible metrics (field p75 INP and LCP per key route, plus compressed bundle size per route as the leading indicator), set budgets that reflect the current state plus an intended trajectory, and enforce them in CI with a PR comment showing the delta. Regressions block or require an explicit, time-boxed exception — the point is that going over budget is a decision someone makes, not something that happens. Around the gate: a dashboard people actually see, a recurring review of the worst route, and one named owner per budget. And be honest about the trade: a hard gate on a noisy metric trains teams to disable it, so gate on the stable proxy (bytes, long tasks in a scripted flow) and alert on the field metric.

Follow-ups
  • Bundle size or field metrics? Both — bytes are stable and gateable, field metrics are true; use bytes as the gate and field metrics as the goal.
  • How do you handle a legitimate regression, like a big new feature? Explicit budget re-baselining with sign-off, recorded — otherwise the budget erodes silently.
  • What kills these programmes? Flaky CI checks and unowned dashboards; both teach people to ignore the signal.
Common wrong answer"We do a performance sprint each quarter." Regression is continuous, so periodic cleanup means you pay the same cost forever and users live with the bad state in between.

11 Error handling & resilience

Interviewers use this to find out whether you have run something in production. The mechanical parts — Error subclassing, try/catch across await — are mid level; the interesting parts are the policy questions: which failures deserve an exception and which deserve a value, what you catch versus what you let crash, and how an error becomes a diagnosable event rather than a line in a log.

How do you define a custom error type properly?mid

Extend Error, set name, pass a message, and attach structured fields the caller can branch on. Use the ES2022 cause option to keep the original error instead of stringifying it — it preserves the underlying stack and is what modern loggers print. Two pitfalls: instanceof fails across realms (iframes, worker boundaries, two copies of a package), so for cross-boundary checks add a discriminant field or use Error.isError() (ES2026) to at least identify errors reliably; and when targeting ES5 output, subclassing Error silently breaks the prototype chain — a legacy problem you still meet in old build configs, fixed with Object.setPrototypeOf(this, new.target.prototype).

export class HttpError extends Error {
  readonly kind = 'HttpError' as const;          // realm-safe discriminant
  constructor(readonly status: number, readonly url: string, options?: { cause?: unknown }) {
    super(`HTTP ${status} for ${url}`, options);
    this.name = 'HttpError';
  }
}
throw new HttpError(503, url, { cause: err });
Follow-ups
  • Why not throw plain objects or strings? No stack, no name, and every logger and framework special-cases Error; you lose the diagnosis.
  • Should errors carry user-facing messages? No — carry a code and structured data; render messages at the presentation layer where you know the locale and the audience.
  • AggregateError? What Promise.any rejects with, and the right shape for "several things failed" — it holds an errors array.
Common wrong answerCatching, wrapping in a brand-new Error(String(e)), and rethrowing. The original stack and type are gone, and every downstream handler now sees a useless generic error — the single most common way teams destroy their own debuggability.
What are the exact semantics of try/catch/finally, especially with async?mid

finally runs on every exit path — normal completion, throw, and return — and a return or throw inside finally overrides whatever the try block was doing, which silently swallows errors. In async functions, await inside try makes rejections catchable normally, but a promise you create and do not await escapes the block entirely: try { doAsync(); } catch {} catches nothing. That is also why return await p matters inside try — without the await, the promise is returned before it settles and your local catch never sees the rejection. In ES2019 you can omit the binding (catch {}) when you do not need the error.

async function load(id: string) {
  const conn = await pool.acquire();
  try {
    return await query(conn, id);   // `await` required for catch/finally to be meaningful here
  } catch (e) {
    throw new DataError(`load ${id}`, { cause: e });
  } finally {
    conn.release();                 // runs on success, throw, and return
  }
}
Follow-ups
  • Can finally swallow an error? Yes — return in finally discards a pending exception; lint it (no-unsafe-finally).
  • Catch and rethrow — worth it? Only if you add context; a bare rethrow is noise that hides the real handler.
  • Errors in an event handler or a timer? They surface as an uncaught exception on the host, not to the code that scheduled them — wrap them yourself.
Common wrong answer"try/catch around a function that returns a promise catches its failures." Only if you await it there; otherwise the rejection escapes to the unhandled-rejection handler, which in Node kills the process.
Exceptions or a Result type?senior

Exceptions are the language's native mechanism and cheap to write, but they are invisible in the type system: TypeScript has no checked exceptions, so a signature tells you nothing about what can fail. A Result<T, E> union makes failure explicit, forces handling at the call site, and composes well for expected failures — validation, parse errors, "not found", a payment declined. The pragmatic split most teams settle on: Result for domain-expected outcomes at module boundaries, exceptions for programmer errors and truly exceptional infrastructure failure, and never both for the same failure. Say the costs out loud: Result is viral through call chains, verbose without helpers, and awkward across framework code that expects throws.

type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E };

const parsed = UserSchema.safeParse(body);        // Result-shaped by design
if (!parsed.success) return reply.code(400).send({ code: 'invalid_body', issues: parsed.error.issues });
const user = parsed.data;                          // narrowed, no try/catch
Follow-ups
  • What about the Promise.try and "safe assignment" style? Promise.try (ES2025) normalises sync throws into rejections; a language-level ?= operator is only a proposal, not something to design around.
  • How do you stop Result leaking everywhere? Convert at a boundary — HTTP layer, job handler — and keep the core consistent.
  • Performance? Throwing is not free (stack capture), so a hot validation path is a legitimate reason to prefer Result.
Common wrong answer"Result types are strictly better, exceptions are legacy." Dogma without cost analysis; in a codebase full of framework callbacks, half-applied Result is worse than consistent exceptions.
What do using and await using give you?senior

Explicit resource management (TC39 stage 4, in the ES2027 batch; TypeScript support since 5.2, Node behind support for the syntax and V8 shipping it). A using declaration binds a value implementing Symbol.dispose, and its [Symbol.dispose]() runs when the enclosing block exits — in reverse declaration order, on every path. await using does the same for Symbol.asyncDispose. It replaces nested try/finally pyramids for connections, file handles, locks, spans and temporary directories, and DisposableStack/AsyncDisposableStack let you compose disposables built conditionally. Errors from disposal are aggregated with the original error via SuppressedError rather than replacing it — the flaw of hand-written finally blocks.

class Conn { async [Symbol.asyncDispose]() { await this.close(); } /* ... */ }

async function handler() {
  await using conn = await pool.acquire();   // released at block exit, any path
  await using span = tracer.start('handler');
  return await conn.query(sql);
}
Follow-ups
  • Is it available today? The syntax needs a compiler or a recent runtime; TypeScript downlevels it, and the Symbol.dispose polyfill is a one-liner. Check your minimum runtime before using it in a library.
  • Difference from C# using? Very close by design — same disposal-on-scope-exit, plus an async variant and error suppression semantics.
  • What still needs try/finally? Cleanup that is not tied to a lexical scope, such as a resource handed to a callback that outlives the block.
Common wrong answerConfusing it with TypeScript's using-like decorators or claiming it is a TypeScript feature. It is a JavaScript language feature TypeScript implements early — a distinction worth getting right when you are the person choosing the target.
A production error report says "Script error." with no stack. What is going on?senior

That is the browser's cross-origin sanitisation: an error thrown by a script served from another origin is reported without message, file or line unless the script is served with Access-Control-Allow-Origin and loaded with crossorigin="anonymous". So the fix is deployment, not code: serve bundles from a CDN with CORS headers, add the attribute, and upload source maps to the error tracker (private maps, not public) so minified frames resolve. Round it out with the things that make an error diagnosable at all: a correlation id propagated from the request through AsyncLocalStorage on the server and a header on the client, release/version tagging so you can tell which deploy introduced it, breadcrumbs, and grouping by error name plus a stable code rather than by the message string.

<script src="https://cdn.example.com/app.js" crossorigin="anonymous"></script>
Follow-ups
  • Where do unhandled rejections show up? The unhandledrejection event — make sure the tracker hooks it, or you lose most async failures.
  • Why not ship source maps publicly? It publishes your source; upload them to the tracker and set SourceMap/X-SourceMap only for internal builds.
  • How do you avoid noise? Ignore known extension and third-party frames, sample high-volume groups, and alert on new groups and rate changes rather than on totals.
Common wrong answer"Wrap everything in try/catch to get better reports." It changes nothing about the sanitisation and hides errors from the global handler; the actual cause is a missing CORS header and a missing crossorigin attribute.
What should a service catch, and what should it let crash?principal

Catch what you can act on: expected domain failures (map to a 4xx), transient dependency failures inside a retry/circuit-breaker policy, and anything at a boundary where you can degrade — serve stale cache, skip an optional enrichment, return a partial response with a header saying so. Let it crash when the process state is no longer trustworthy: unhandled rejections, uncaught exceptions, failed invariants, OOM. The reasoning to say out loud is that a process in unknown state can corrupt data, and a fast crash with a restart is a well-understood recovery, while a catch-all handler converts a loud failure into silent, ongoing wrongness. Around that: readiness probes that fail before liveness so traffic drains first, graceful shutdown on SIGTERM that stops accepting and finishes in-flight work with a deadline, structured logs with correlation ids, and a bulkhead so one dependency's failure cannot exhaust every worker.

Follow-ups
  • What about a crash loop? Backoff at the orchestrator plus a circuit breaker on the dependency; and alert on restart rate, which is the earliest signal you have.
  • Degrade or fail? Depends on the contract — a recommendations panel degrades, a payment does not; write it down per feature rather than deciding at 3am.
  • How do you test this? Fault injection in staging and a game day: kill a dependency and check that the SLO story you wrote is what actually happens.
Common wrong answer"Add a global try/catch so the service never goes down." Availability measured as "the process is alive" while it returns wrong answers is worse than a restart, and this is exactly the judgment the question tests.

12 Browser runtime: DOM, events, storage

Asked whenever the role touches a front end, and usually framework-free on purpose — interviewers want to know whether you understand the platform your framework sits on. Event propagation and delegation are mid-level table stakes; storage choice, CORS and service workers are senior; and there is a reliable "what has changed on the platform recently" question that is easy to fail if you stopped reading release notes.

Explain event propagation and event delegation.mid

A dispatched event travels in three phases: capture from window down to the target, the target phase, then bubbling back up (most, but not all, events bubble — focus, blur, load and scroll on elements do not). addEventListener(type, fn, true) or { capture: true } listens on the way down. Delegation exploits bubbling: one listener on a container handles events for any number of descendants, matched with event.target.closest(selector) — cheaper to attach, and it works for elements added later. stopPropagation halts travel (and is a frequent cause of "the framework's outside-click handler stopped working"), while preventDefault only cancels the default action; they are independent.

list.addEventListener('click', (e) => {
  const row = (e.target as Element).closest('[data-id]');
  if (!row || !list.contains(row)) return;
  open(row.getAttribute('data-id')!);
}, { signal });      // one listener; removed with the controller
Follow-ups
  • What is { passive: true } for? It promises not to call preventDefault, so the browser can scroll without waiting for your handler — required for smooth touch/wheel scrolling, and now the default for those events on the document.
  • stopPropagation vs stopImmediatePropagation? The latter also stops other listeners on the same element.
  • How do you remove listeners cleanly? { signal } from an AbortController, or { once: true } — both beat keeping a reference to the function.
Common wrong answer"preventDefault stops the event from bubbling." They do different things; conflating them produces handlers that neither cancel the default nor stop propagation, and bugs that look like framework problems.
Walk the browser's rendering pipeline and say where JavaScript fits.mid

Per frame: run JavaScript tasks and microtasks, then requestAnimationFrame callbacks, then style recalculation, layout, paint and composite; ResizeObserver and IntersectionObserver callbacks and MutationObserver microtasks are woven in at defined points. Because it is one thread, long JavaScript delays the whole pipeline — that is why a 200 ms task means a dropped frame and a laggy interaction. requestAnimationFrame is for visual updates just before paint; requestIdleCallback (and better, scheduler.postTask with a priority) is for non-urgent work; scheduler.yield() lets you break a long task and let input in without losing your place in the queue.

// Non-urgent work at background priority, cancellable
const controller = new TaskController({ priority: 'background' });
scheduler.postTask(() => prefetchNextPage(), { signal: controller.signal });
Follow-ups
  • Why can a microtask loop freeze the page but a timer loop not? The microtask queue is drained before rendering; timers yield between tasks.
  • Where do CSS animations run? transform/opacity animate on the compositor, off the main thread — which is why they survive a busy main thread.
  • What is the View Transitions API for? Browser-managed cross-fade/morph between two DOM states (same-document, and cross-document for MPAs), replacing hand-rolled FLIP animations.
Common wrong answer"requestAnimationFrame makes code run in parallel / faster." It schedules a callback before the next paint on the same thread; if your callback is slow, the frame is still late.
Which client-side storage do you choose, and why?mid

localStorage/sessionStorage: synchronous, string-only, ~5 MB, same-origin — fine for a UI preference, wrong for anything large or hot because every access blocks the main thread. IndexedDB: asynchronous, structured-clone values, large quotas, transactional and indexable — the right default for real client data, usually behind a wrapper. Cookies: sent on every matching request, so keep them small; the security-relevant flags are HttpOnly, Secure, SameSite and Path. Cache API: request/response pairs for a service worker. All of it is evictable under storage pressure unless you request persistence, and all of it is per-origin, so treat it as a cache, never as the source of truth.

// localStorage is sync: read once at boot, not per render
const theme = localStorage.getItem('theme') ?? 'system';
// anything bigger belongs in IndexedDB
const db = await openDB('app', 1, { upgrade: (d) => d.createObjectStore('rows', { keyPath: 'id' }) });
Follow-ups
  • Where do you keep an auth token? Ideally not in JavaScript-readable storage at all: an HttpOnly, Secure, SameSite cookie, because localStorage is readable by any XSS.
  • How do tabs stay in sync? The storage event, or BroadcastChannel for structured messages.
  • What about quota? navigator.storage.estimate() to inspect, persist() to request durability; handle QuotaExceededError rather than assuming writes succeed.
Common wrong answer"Use localStorage, it's simpler." For anything beyond a few small keys it is a main-thread blocker with a hard size cap and no transactions — and for tokens it is a security decision, not a convenience one.
Explain CORS: what triggers a preflight, and what does credentials change?senior

CORS is a browser-enforced relaxation of the same-origin policy: the request is usually sent, but the browser hides the response unless the server opts in with Access-Control-Allow-Origin. Simple requests (GET/HEAD/POST with a small set of content types and no custom headers) go straight out; anything else — a custom header like Authorization, content-type: application/json, PUT/DELETE/PATCH — triggers an OPTIONS preflight that must be answered with the allowed origin, methods and headers, cacheable via Access-Control-Max-Age. With credentials: 'include' the rules tighten: the server must send Access-Control-Allow-Credentials: true and an explicit origin — the wildcard is rejected — and cookies additionally need SameSite=None; Secure to travel cross-site at all.

Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, PATCH
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Max-Age: 600
Follow-ups
  • Does CORS protect the server? No — it protects the user's data from other sites' scripts. A non-browser client ignores it entirely; server-side authorisation is still mandatory.
  • Why can I see the response in the network tab but not in code? The request succeeded; the browser blocked your access to the response.
  • Reading a custom response header? Only if the server lists it in Access-Control-Expose-Headers.
Common wrong answer"Fix CORS by adding mode: 'no-cors'." That gives an opaque response you cannot read — it hides the error rather than solving it, and it is the single most common wrong fix in front-end code.
Which platform observers and APIs should replace hand-rolled code?senior

IntersectionObserver for visibility (lazy loading, infinite scroll, impression tracking) instead of scroll handlers plus getBoundingClientRect; ResizeObserver for element size instead of window resize plus measurement; MutationObserver for DOM changes; PerformanceObserver for long tasks, layout shifts and Web Vitals entries. All of them report asynchronously at points where measurement is already valid, so they do not force layout the way manual polling does. Add AbortController for teardown, structuredClone for deep copies, Intl for anything locale-shaped, and navigator.sendBeacon/fetch(..., { keepalive: true }) for telemetry on unload.

const io = new IntersectionObserver((entries) => {
  for (const e of entries) if (e.isIntersecting) { load(e.target); io.unobserve(e.target); }
}, { rootMargin: '200px' });   // start loading before it is visible
items.forEach(el => io.observe(el));
Follow-ups
  • Why is a scroll handler worse? It runs on every scroll event and forces synchronous layout when it measures; the observer batches off the critical path.
  • How do you unsubscribe? disconnect() in teardown — observers keep their targets alive and are a real leak source in SPAs.
  • Detecting "the tab went away"? visibilitychange plus the pagehide event; unload is unreliable and blocks back/forward cache.
Common wrong answerReaching for a library for each of these. In 2026 the platform covers them, the library adds bytes and a version to maintain, and interviewers notice when a candidate's toolbox is entirely npm.
How do service workers change an app's architecture, and what are the traps?senior

A service worker is a separate, event-driven worker that proxies network requests for its scope, enabling offline support, precaching, background sync and push. Architecturally it introduces a second deployment artefact with its own lifecycle — install, waiting, activate — so a user can be running old application code against a new API for as long as a tab stays open. The strategies to name are cache-first (immutable hashed assets), network-first (HTML and API reads), stale-while-revalidate (fast, slightly stale content) and network-only (mutations). The traps are real: an over-eager cache-first rule on HTML pins users to a broken version; a bad worker persists until it is replaced, so ship an escape hatch (an unregister path, versioned cache names, skipWaiting used deliberately rather than always); and cache invalidation becomes your problem, not the CDN's.

Follow-ups
  • How does a user get the new version? The new worker installs, waits until all controlled tabs close, then activates — unless you call skipWaiting() and clients.claim(), which risks mixed old/new assets in an open tab.
  • Do you write one by hand? Usually not — Workbox or the framework's plugin, because the lifecycle edge cases are where the incidents are.
  • Alternative for pure speed? HTTP caching plus the back/forward cache and speculation rules get most of the win with none of the lifecycle risk.
Common wrong answer"Cache everything with cache-first so the app is fast offline." That is how you ship a permanently stale app; HTML and API responses need a revalidation path, and the update story has to be designed before the caching one.
What has changed in the browser JavaScript platform recently that you would actually use?senior

The headline is Temporal: after roughly nine years it reached Stage 4 in 2026 (shipping in the ES2027 batch) and is available by default in Firefox since 139 and in Chrome/Edge since 144, with Safari in progress. It replaces Date with immutable types that separate instants, wall-clock times, dates, durations and time zones — the end of "install a date library by default", although you still need one until your support matrix covers it. Beyond that: iterator helpers, Promise.try, Set methods, RegExp.escape and Float16Array from ES2025; Object.groupBy/Map.groupBy; Error.isError, Math.sumPrecise, Array.fromAsync, Uint8Array base64/hex and Map.getOrInsert in ES2026; and using/await using plus Atomics.pause queued for ES2027.

const now = Temporal.Now.zonedDateTimeISO('Europe/Berlin');
const due = now.add({ days: 30 }).with({ hour: 9, minute: 0, second: 0 });
due.since(now).total({ unit: 'hour' });        // no library, no timezone guesswork
Error.isError(e);                               // realm-safe, unlike instanceof
Follow-ups
  • Should you migrate off date-fns/Luxon now? Not wholesale — adopt Temporal in new code behind a thin adapter, and switch once your baseline browsers and Node version support it unflagged.
  • How do you decide what is safe to use? Baseline status on web.dev/MDN checked against your own analytics, not "it works in my browser".
  • Why does Error.isError matter? instanceof Error fails across realms and lies for objects with a doctored prototype; the new check is a brand check.
Common wrong answerListing features from 2019 (optional chaining, Promise.allSettled) as "recent". The question is a currency check; the strong answer names something from the last twelve months and says where it is and is not yet safe to use.

13 Node.js & server-side JavaScript

Essential for full-stack and backend roles and increasingly asked of front-end leads too, since the build tooling, SSR layer and BFF all run here. Mid level should explain the threading model and streams; senior should handle scaling, graceful shutdown and diagnostics; and 2026 adds a currency dimension — Node has absorbed a great deal (native TypeScript, a test runner, .env support, require() of ESM) that used to be dependencies.

Node is "single-threaded" — so what does libuv's thread pool do?mid

Your JavaScript runs on one thread, but Node is not single-threaded as a process. Network I/O is genuinely asynchronous at the OS level (epoll/kqueue/IOCP) and needs no threads. File system operations, DNS lookups via getaddrinfo, zlib compression and some crypto have no portable async syscall, so libuv runs them on a thread pool — four threads by default, sized with UV_THREADPOOL_SIZE. That is why a burst of file reads or pbkdf2 calls can queue behind each other while HTTP requests fly, and why a pool exhausted by compression makes DNS look slow.

UV_THREADPOOL_SIZE=16 node server.js   # more pool threads for fs/zlib/crypto-heavy workloads
Follow-ups
  • How do you tell pool saturation from event-loop blocking? Loop lag stays low while specific operation latencies rise — the loop is idle, the pool is full.
  • Is crypto.randomBytes pooled? The async form uses the pool; the Sync variants block the loop directly.
  • Does raising the pool size always help? No — it competes for CPU; past core count you trade latency for context switching.
Common wrong answer"Everything in Node is non-blocking." fs.readFileSync, JSON.parse on a large buffer, synchronous crypto and a bad regex all block the loop; knowing which operations are truly async is the point of the question.
Explain streams and backpressure.mid

Streams process data in chunks with bounded memory. A readable produces, a writable consumes, a transform does both; highWaterMark sets the buffer threshold. Backpressure is the writable telling the readable to slow down: write() returning false means the buffer is full and you should wait for 'drain'. Almost nobody should implement that by hand — pipeline() (or its promise form) wires the chain, propagates backpressure, and, crucially, destroys every stream on error, which manual pipe() chains do not, leaking file descriptors and sockets on failure. Node also supports the WHATWG web streams (ReadableStream) with conversion helpers, which matters when sharing code with edge runtimes or the browser.

import { pipeline } from 'node:stream/promises';
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';

await pipeline(createReadStream(src), createGzip(), createWriteStream(dst)); // bounded memory, cleanup on error
Follow-ups
  • Why not readFile then writeFile? It buffers the whole file; one large upload can exhaust the heap, and concurrency multiplies it.
  • Object mode? Streams of arbitrary values rather than bytes — useful for record pipelines, at some per-chunk overhead.
  • Async iteration? for await (const chunk of readable) gives backpressure automatically and reads more clearly than event handlers.
Common wrong answer"pipe() handles errors." It does not — an error in one stream leaves the rest undestroyed. This is exactly why pipeline exists, and it is a favourite senior-level detail.
How do you scale a Node service across cores, and when does that not help?senior

One process uses one core for JavaScript, so you run one process per core — with cluster (a primary distributing connections to forked workers) or, more commonly in 2026, with the orchestrator running N containers, which keeps scaling, health checks and rollout in one system rather than two. worker_threads is the different tool: same process, shared memory possible, for CPU-bound work inside a request. Scaling out does not help when the bottleneck is downstream (a database at its connection limit — note that N processes multiply your pool size), when the work is memory-bound, or when a single request blocks the loop for seconds, since every co-tenant request on that instance still waits.

// Prefer the orchestrator; use cluster when you must self-manage
import cluster from 'node:cluster';
import { availableParallelism } from 'node:os';
if (cluster.isPrimary) for (let i = 0; i < availableParallelism(); i++) cluster.fork();
else startServer();
Follow-ups
  • Connection pools under cluster? Each worker has its own — 8 workers × 20 connections is 160 against the database; size per worker, not per service.
  • Sticky sessions? Avoid them; keep state in a shared store so any worker can serve any request.
  • Memory per process? Each has its own heap and its own copy of the code — count that against the container limit.
Common wrong answer"Add cluster and it scales linearly." It multiplies downstream pressure and does nothing for a blocked loop; the expected senior answer names the bottleneck before the topology.
What can Node do natively in 2026 that used to need dependencies?senior

Run TypeScript directly: since Node 22 (flagged) and unflagged from Node 23/24 onwards, Node strips type annotations rather than transpiling, replacing them with whitespace so line numbers and stack traces stay exact. Because it only erases, non-erasable syntax fails — enums, parameter properties, runtime namespaces — which is why erasableSyntaxOnly exists in TypeScript 5.8+. Also native now: a test runner (node:test with node --test, coverage and watch), --env-file for .env, fetch/WebSocket/FormData globals, node --watch, a SQLite module, a permission model (--permission with --allow-fs-read and friends), and require() of synchronous ES modules from Node 22. Node 24 is the current LTS line; Node 26 becomes LTS in October 2026, when releases move to one major per year and every release becomes LTS.

node --env-file=.env --test --experimental-test-coverage
node server.ts                 # type stripping, no build step
node --permission --allow-fs-read=./data server.js
Follow-ups
  • Should you drop your bundler or tsx for production? For services, often yes — but you still run tsc --noEmit in CI, because stripping does not type-check.
  • Source maps? Enabled by default for stack traces; whitespace-preserving stripping means positions match without one for plain .ts.
  • What about the node: prefix? Use it for every builtin — it is unambiguous, unshadowable by an npm package, and required in some runtimes.
Common wrong answer"Node runs TypeScript now, so we don't need the compiler." Stripping does no checking whatsoever; a codebase without tsc in CI has types that are comments.
How do you shut a Node service down gracefully?senior

On SIGTERM: fail the readiness probe first so the load balancer stops sending new traffic, wait a beat for propagation, stop accepting new connections (server.close()), let in-flight requests finish under a deadline, drain queues and close pools, flush logs and metrics, then exit 0 — with a hard process.exit(1) on a timer so a stuck connection cannot hang the rollout forever. The details that separate a real answer: server.close() does not close idle keep-alive sockets (use closeIdleConnections()/closeAllConnections()), the readiness-before-liveness ordering, and idempotency so a job killed mid-flight can be retried safely.

let shuttingDown = false;
process.on('SIGTERM', async () => {
  if (shuttingDown) return; shuttingDown = true;
  health.ready = false;                       // fail readiness first
  await sleep(5_000);                         // let the LB notice
  server.closeIdleConnections();
  await new Promise(r => server.close(r));    // finish in-flight
  await Promise.allSettled([pool.end(), queue.close(), metrics.flush()]);
  process.exit(0);
});
setTimeout(() => process.exit(1), 30_000).unref();
Follow-ups
  • Why the sleep? Load balancers poll; without it you reject requests that were already routed to you.
  • What about SIGINT and Windows? Handle both; Windows has no real signals, so orchestrators terminate differently — test the path you actually deploy.
  • In-flight jobs from a queue? Stop consuming first, then let current jobs finish or nack them for redelivery.
Common wrong answer"Kubernetes handles it." It sends the signal and waits terminationGracePeriodSeconds; if your process ignores it, you get dropped requests on every deploy — one of the most common sources of mysterious 502s.
How do you carry request context (trace id, tenant) without threading it through every function?senior

AsyncLocalStorage from node:async_hooks: run the request handler inside als.run(store, fn) and any code in that async context — across await, timers and callbacks — can call als.getStore(). It is what OpenTelemetry and modern loggers use for automatic trace correlation. The trade-offs to name: there is a real (though much reduced in recent versions) overhead; context can be lost across boundaries that break the async chain, such as pooled connections, some event emitters and native addons; and it is easy to abuse as an ambient global for business data, which makes functions untestable. Keep it to cross-cutting concerns — trace id, tenant, request-scoped logger — and pass domain data explicitly.

const als = new AsyncLocalStorage<{ traceId: string }>();
app.use((req, _res, next) => als.run({ traceId: req.headers['x-trace-id'] ?? randomUUID() }, next));
export const log = (msg: string) => logger.info({ traceId: als.getStore()?.traceId }, msg);
Follow-ups
  • Alternative? An explicit context object as the first parameter — more verbose, entirely predictable, and the right call for a library.
  • What is diagnostics_channel for? Low-overhead publish/subscribe for instrumentation points, so tracing does not need monkey-patching.
  • Does it survive worker_threads? No — separate contexts; propagate explicitly in the message.
Common wrong answerUsing a module-level mutable variable as "request context". Under concurrency it is one variable shared by every in-flight request — the classic way tenant A's data ends up in tenant B's response.
A Node service's memory grows steadily until it is OOM-killed. How do you find the cause?senior

Confirm it is a leak, not high water: plot RSS and V8 heap-used across GCs — a leak is monotonic growth in retained heap after major collections. Then take two heap snapshots under steady load, minutes apart, and diff by constructor to see which objects accumulate; follow one instance's retainer path to the root, which almost always lands on a module-level Map or array, an unremoved listener, a timer, or a closure capturing a request. Snapshots can be triggered without an inspector via --heapsnapshot-signal=SIGUSR2 or v8.writeHeapSnapshot(), and --cpu-prof/--heap-prof add allocation profiles. Also check the non-heap suspects: unbounded Buffer allocation (outside the JS heap), native addon leaks, and a container limit lower than --max-old-space-size, which produces an OOM kill before V8 ever feels pressure.

Follow-ups
  • Warning sign in code review? Any collection at module scope that is only ever written to; caches need bounds and eviction, not good intentions.
  • Does MaxListenersExceededWarning matter? Yes — it is usually a listener added per request to a long-lived emitter.
  • How do you prevent recurrence? Alert on heap-used growth rate per pod, and add a soak test to the release pipeline.
Common wrong answer"Restart it on a schedule / raise the memory limit." It buys hours and hides the cause; interviewers ask this question specifically to see whether you diagnose or paper over.

14 Testing & quality

Asked in most lead loops, rarely as trivia and almost always as judgment: what do you test, what do you mock, and how do you keep a suite people trust. The JavaScript-specific content is async testing and fake timers, ESM in test runners, and — the part that is genuinely unusual to this ecosystem — testing the types of a library, not only its behaviour.

What is your testing strategy for a TypeScript service or app?mid

Weight by cost of failure and cost of maintenance, not by a pyramid drawing. Most value usually sits in fast integration tests that exercise a real boundary with a real dependency where feasible — an in-memory or containerised database rather than a mocked repository — because those catch the wiring and serialisation bugs that unit tests with mocks are structurally blind to. Keep unit tests for logic with branches worth enumerating (pricing, parsing, state machines) and a thin layer of end-to-end tests for the two or three flows that must never break. The rule to state: mock what you do not own and cannot run (a payment provider, a third-party API), not your own modules; every internal mock is a copy of an assumption that will drift.

Follow-ups
  • Coverage target? Use coverage to find untested branches, not as a goal; a mandated number produces assertion-free tests that execute code.
  • How do you keep e2e from becoming flaky? Deterministic data setup, no arbitrary sleeps, retry only on documented external flakiness, and quarantine plus a fix deadline rather than a permanent retry.
  • What do you test in a UI? Behaviour through the accessibility tree (Testing Library), not implementation details; snapshot tests of markup rot fast and get approved blindly.
Common wrong answer"Unit test everything, mock all dependencies, aim for 100%." It produces a suite that passes while the system is broken and that makes every refactor a test-rewriting exercise — the exact failure mode a lead is supposed to prevent.
How do you test asynchronous code without introducing flakiness?mid

Never sleep for a duration and hope. Await the promise the code returns; assert on rejections with the runner's rejects matcher rather than a hand-rolled try/catch that can pass when nothing throws; use fake timers to advance time deterministically for debounce, retry and polling logic; and for event-driven code, await an explicit condition (a promise resolved by the event) rather than a timeout. Remember to await the microtask queue when testing code that schedules continuations — most runners' fake timers include an async advance API for exactly that.

it('retries with backoff', async () => {
  vi.useFakeTimers();
  const fn = vi.fn().mockRejectedValueOnce(new Error('boom')).mockResolvedValue('ok');
  const p = withRetry(fn, { attempts: 2, baseMs: 100, deadline: Date.now() + 10_000 });
  await vi.advanceTimersByTimeAsync(5_000);      // deterministic, instant
  await expect(p).resolves.toBe('ok');
  expect(fn).toHaveBeenCalledTimes(2);
});
Follow-ups
  • Biggest source of flakiness? Shared state between tests — a module-level cache, a real clock, a database row — plus unawaited promises leaking into the next test.
  • How do you catch unawaited promises? no-floating-promises in lint, and failing the suite on unhandled rejections.
  • Testing timeouts and cancellation? Inject the AbortSignal and the clock; code that reads Date.now() directly is hard to test for a reason.
Common wrong answerawait new Promise(r => setTimeout(r, 500)) to "let it settle". It is slow, it is machine-dependent, and it converts a logic bug into an intermittent failure that eventually gets a retry: 3.
How do you test types?senior

For anything with non-trivial generics — a library, a shared client, a builder API — the types are part of the contract and deserve tests. Modern runners support it directly (expectTypeOf in Vitest, tsd, @ts-expect-error as an assertion that something must not compile), and a type test suite catches inference regressions that a behavioural test cannot see. Combine it with an API report snapshot so a change to the emitted .d.ts shows up as a reviewable diff rather than as a downstream compile error a week later.

expectTypeOf(pluck(users, 'name')).toEqualTypeOf<string[]>();
// @ts-expect-error 'nope' is not a key of User — this line must NOT compile
pluck(users, 'nope');
Follow-ups
  • Why @ts-expect-error and not @ts-ignore? It fails when the error disappears, so it is an assertion rather than a suppression.
  • Do type tests slow CI? They add a type-check pass; run them with the rest of the check, not per test file.
  • What do they catch that behaviour tests miss? Widening regressions, lost narrowing, an accidental any in a public signature — all invisible at runtime.
Common wrong answer"If it compiles, the types are right." Compiling proves nothing about what was inferred; an accidental any compiles beautifully and silently disables checking for every consumer.
What does the JavaScript test-runner landscape look like in 2026, and how do you choose?senior

Vitest is the common default for anything already using Vite: native ESM and TypeScript, fast watch, browser mode, and a Jest-compatible API that makes migration mechanical. Jest still runs an enormous amount of existing code and remains reasonable, with the caveat that its ESM support has been the long-standing friction point. node:test is built in, dependency-free and increasingly capable — the right choice for libraries and services that want zero test dependencies. For end-to-end, Playwright is the default. The selection criteria worth saying: ESM/TypeScript handling without a bespoke transform config, watch-mode speed (it sets the inner loop), a debugging story in your editor, and a migration path if you change your mind.

Follow-ups
  • Why is ESM hard for runners? Module mocking depends on interception; ESM's static graph and immutable bindings make the Jest-style jest.mock hoisting trick awkward, which is why loader-based or DI-based approaches win.
  • Would you migrate a large Jest suite? Only with a reason — speed or ESM pain — and incrementally, running both runners during the transition.
  • Coverage? V8 coverage is fast and good enough; instrumented coverage is more precise and slower.
Common wrong answerChoosing on popularity alone, or claiming a runner is "faster" without saying at what — cold start, watch re-run, or full CI. Those are three different numbers and teams feel the second one most.
When is mocking a design smell, and what do you do instead?senior

When you must mock a module's internals to test it, the code has hidden dependencies. Module-level mocking (vi.mock/jest.mock) reaches through the public surface and couples the test to the implementation's import list, so a refactor that changes nothing observable breaks the tests. The alternative is boring: pass dependencies in — a constructor parameter, an options object, a small factory — so tests supply a real fake (an in-memory repository, a stub clock, a recorded HTTP layer) with no runner magic. For HTTP specifically, intercept at the network layer (MSW, nock, Playwright routes) rather than mocking your own client, so the serialisation path is exercised.

// Testable without module mocking: dependencies are parameters
export function createOrderService({ repo, clock = () => Date.now(), pay }: Deps) {
  return { place: async (o: Order) => { /* ... */ } };
}
const svc = createOrderService({ repo: new InMemoryRepo(), clock: () => 1_700_000_000_000, pay: fakePay });
Follow-ups
  • Is a DI container needed? No — plain parameters and factories cover almost everything; containers earn their keep at a certain size, not by default.
  • What about mocking time and randomness? Inject them; they are dependencies like any other, and code that calls Date.now() or Math.random() directly is untestable by construction.
  • Contract tests? Worth it where a fake stands in for a service you own — otherwise the fake and the real thing drift.
Common wrong answer"Mock every dependency so the unit is isolated." Perfect isolation tests that your mocks agree with your mocks; the bugs that reach production live in the seams you just replaced.

15 Security

Asked in most senior and lead loops, usually with one deep question rather than a survey. What is being checked is whether you know which defences are structural (escaping by construction, CSP, HttpOnly cookies, lockfiles) and which are wishful (blocklists, sanitising on output, "we review dependencies"). JavaScript's specific exposure is the browser trust boundary and the npm supply chain, so expect XSS, prototype pollution and dependency questions.

Explain XSS and how you actually prevent it.mid

XSS is attacker-controlled data being interpreted as code in a user's page: stored (persisted then rendered), reflected (echoed from the request) and DOM-based (client-side code writing untrusted data into a sink like innerHTML, document.write, eval, or a javascript: URL). The structural defence is contextual escaping by construction — a framework that treats interpolation as text (React's JSX, Angular's binding, a templating engine with auto-escaping) — plus never using the dangerous sinks with untrusted input. Layer on a Content Security Policy that forbids inline script (nonce or hash based, not unsafe-inline), and Trusted Types, which makes assigning a raw string to innerHTML a runtime error unless it went through a vetted policy — the only mechanism that eliminates DOM XSS as a class rather than case by case. If you must accept HTML, sanitise with a maintained library (DOMPurify) on the way in and keep the CSP.

Content-Security-Policy: default-src 'self'; script-src 'nonce-r4nd0m' 'strict-dynamic';
  object-src 'none'; base-uri 'none'; require-trusted-types-for 'script'
Follow-ups
  • Why is dangerouslySetInnerHTML named that way? Because it opts out of the framework's escaping — every use needs sanitisation and a review.
  • Does escaping on output cover everything? Only if the context is right: HTML text, attribute, URL, JavaScript and CSS contexts each need different escaping.
  • What does XSS get an attacker? Everything the user can do, including reading localStorage — which is why tokens belong in HttpOnly cookies.
Common wrong answer"We strip <script> tags and escape quotes." Blocklist filtering loses to event-handler attributes, javascript: URLs, SVG and mutation XSS; the defence is context-correct encoding plus CSP, not pattern matching.
What is prototype pollution, and how do you prevent it?mid

A merge, clone or path-set function that copies attacker-controlled keys into an object can write to __proto__, constructor or prototype and thereby add a property to Object.prototype — visible to every object in the process. Consequences range from denial of service to authentication bypass (a polluted isAdmin that every object now inherits) and in Node to RCE via polluted options that reach child_process. Prevention: reject or skip those keys explicitly in any recursive merge, use Object.create(null) or a Map for dictionaries built from untrusted input, prefer Object.hasOwn over in, validate with a schema that strips unknown keys, and use structuredClone or a maintained utility rather than a hand-rolled deep merge.

const BAD = new Set(['__proto__', 'constructor', 'prototype']);
function safeSet(target, path, value) {
  const keys = path.split('.');
  if (keys.some(k => BAD.has(k))) throw new Error('unsafe path');
  /* ... */
}
const dict = Object.create(null);   // no prototype to pollute
Follow-ups
  • Is JSON.parse safe? The parse itself is; the danger is what you do with the result — merging it into a config or an options object.
  • Does Object.freeze(Object.prototype) help? It is a real hardening step for a service, at the cost of breaking libraries that patch prototypes.
  • How do you find it in a codebase? Grep for recursive merges, lodash.merge/set on request data, and query-string parsers with nesting enabled.
Common wrong answer"We use TypeScript, so unknown keys can't get in." Types are erased; the JSON body has whatever keys the attacker sent, and the merge does not consult the type.
How do you manage npm supply-chain risk?senior

Assume any dependency can become hostile, because in this ecosystem it periodically does — through a compromised maintainer account, a hijacked or renamed package, or a typosquat. Structural controls: commit lockfiles and install with npm ci; disable lifecycle scripts by default (--ignore-scripts, with an allowlist for the few that genuinely need them) since that is the usual execution vector; pin or narrowly range direct dependencies and use overrides for transitive pins; verify provenance/attestations where publishers offer them; and run an SCA scanner plus npm audit in CI with a policy for what blocks a release. Process controls matter as much: a review requirement for adding a runtime dependency, a preference for the platform or a small vetted set over "there's a package for that", a private registry proxy with a cooldown on brand-new versions, and an SBOM so that on the next incident you can answer "are we affected?" in minutes rather than days.

Follow-ups
  • Why is --ignore-scripts not the default everywhere? Native modules and some tooling need postinstall; allowlist those explicitly rather than enabling it globally.
  • Automated dependency PRs — good or bad? Good, with grouped updates, a delay window for brand-new releases and a strong test suite; unreviewed auto-merge is how a malicious patch ships.
  • What about the runtime side? Node's permission model (--permission) limits what a compromised dependency can reach at run time.
Common wrong answer"We run npm audit and fix the criticals." Audit reports known CVEs in published versions; it says nothing about a fresh malicious release, which is the attack that actually happens.
Where do you keep an auth token in a browser app, and why?senior

Prefer a session cookie the JavaScript cannot read: HttpOnly, Secure, SameSite=Lax (or None; Secure when genuinely cross-site), with a short-lived access token and a rotating refresh token bound to the session. localStorage is readable by any XSS, so storing a JWT there means one injection equals full account takeover with no expiry pressure; in-memory storage is better than localStorage but dies on reload. Cookies bring CSRF into scope, so pair them with SameSite, an anti-CSRF token or the double-submit pattern for state-changing requests, and an Origin header check server-side. And keep the boring truths: no secrets in front-end code (everything shipped is public), validate and authorise on the server for every request, and treat the JWT's claims as untrusted until the signature and expiry are verified server-side.

Follow-ups
  • Why not "JWT in localStorage plus a short expiry"? An attacker with XSS refreshes it as easily as your app does; expiry does not help against a live script in the page.
  • Can you revoke a JWT? Not by itself — that is the trade-off of stateless tokens; you need short lifetimes plus a revocation list or a session lookup.
  • Does SameSite=Lax remove the need for CSRF tokens? It removes most of the risk for modern browsers, not all of it (top-level GET navigations, older clients) — defence in depth.
Common wrong answer"Store the JWT in localStorage — it avoids CSRF." It trades a well-mitigated risk for an unmitigable one, and the reasoning shows the candidate has not weighed the two threat models.
How can a regular expression take down a service?senior

Catastrophic backtracking (ReDoS): a pattern with nested or ambiguous quantifiers — (a+)+$, (\s*,)*, overlapping alternations — can take exponential time on a crafted input, and because the regex engine is synchronous it blocks the event loop for the whole process, not just that request. It is especially dangerous because the vulnerable pattern is often in a dependency's input validation. Defences: prefer simple, anchored, non-ambiguous patterns; avoid nested quantifiers over character classes that overlap; bound input length before matching; test patterns with a ReDoS analyser (eslint-plugin-regexp, recheck, safe-regex); and for user-supplied patterns, do not run them in-process at all — use a linear-time engine or a separate sandboxed worker with a timeout. The same "one request buys unlimited CPU" logic applies to unbounded JSON.parse, zip bombs and image processing, so pair it with request size limits.

const bad = /^(\w+\s?)*$/;            // exponential on 'aaaaaaaaaaaaaaaaaaaaaaaa!'
const good = /^\w+(?:\s\w+)*$/;       // unambiguous, linear
if (input.length > 256) throw new BadRequest('too long');   // bound first
Follow-ups
  • How would you detect it in production? Event-loop lag spikes correlated with specific endpoints, plus a CPU profile showing time in RegExp.
  • Does the v flag or a new engine fix it? No — the flags change semantics, not the backtracking algorithm; a non-backtracking engine would, and V8 has a limited one for some patterns.
  • What other single-request DoS should you bound? Body size, JSON depth, decompression ratio, image dimensions, and the number of items in a batch endpoint.
Common wrong answer"Add a timeout around the regex." There is no way to interrupt a synchronous match on the same thread — the timer cannot fire until the regex finishes. That mistaken fix is itself a good tell.

16 Tooling, standards & evolution

Rarely decisive on its own, but it is where interviewers calibrate how current you are and how you make technology decisions for other people. Nice to know rather than critical — nobody is rejected for not knowing a bundler's internals — yet a lead who cannot explain the TC39 process or justify a toolchain choice on anything but popularity will be marked down.

How does a feature get into JavaScript?mid

TC39 runs a five-stage process: 0 strawperson, 1 proposal (a champion and a rough API), 2 draft (spec text; 2.7 added later means the design is settled and tests are written), 3 candidate (spec complete, implementations and feedback wanted), 4 finished (two independent shipping implementations, test262 coverage, ready for the next annual edition). The spec is cut once a year in spring, and the edition is named for that year — anything that reached Stage 4 before the cutoff is in. Practical consequence for a team: Stage 3 is usually safe to adopt behind a transpiler if you accept possible churn (decorators changed shape at that stage, which burned a lot of code), Stage 2 is not, and "it's in TypeScript" is not the same as "it's in the language".

Follow-ups
  • Where is Temporal in this? Stage 4 reached in 2026, so it lands in the ES2027 edition — already shipping in Firefox and Chrome/Edge ahead of the edition.
  • What is in ES2026? Error.isError, Math.sumPrecise, Array.fromAsync, Uint8Array base64/hex, iterator sequencing, JSON.parse source-text access, and Map.getOrInsert.
  • Why did TypeScript ship legacy decorators? They predated the final proposal; the standard version arrived in TypeScript 5.0 and is a different, incompatible design — a cautionary tale about pre-Stage-3 adoption.
Common wrong answer"Browsers decide what goes into JavaScript." Implementations are part of the gate at Stage 4, but the process is a committee with a written spec and a test suite; getting this wrong makes the "should we use a Stage 3 feature" answer unreasoned.
What does the 2026 toolchain look like, and what would you pick?senior

The trend is consolidation onto native-speed tools with fewer moving parts. Vite is the default application dev server and build tool, with Rolldown (Rust) taking over the bundling role from Rollup/esbuild; esbuild and SWC remain the common transform layers; Rspack/Turbopack serve the webpack-shaped world; Biome and Oxc offer fast lint/format in one binary while ESLint (flat config since v9) plus typescript-eslint remains the standard for type-aware rules; TypeScript itself is now a Go binary. Package managers: npm for simplicity, pnpm for monorepos and disk efficiency, with Corepack pinning the version. Choose on constraints, not novelty: does it type-check or only transpile, does it handle your framework's compiler plugins, what is the migration cost, who maintains it, and how fast is the inner loop for the developer who runs it two hundred times a day.

Follow-ups
  • Would you replace ESLint with Biome? For formatting and basic rules, often yes; type-aware rules (the ones that catch floating promises and unsafe any) still argue for typescript-eslint.
  • How do you avoid churn fatigue? Change one layer at a time, behind a measurable goal (build time, CI minutes), and never during a delivery crunch.
  • What about "no build step"? Viable for services now that Node runs TypeScript; front ends still need a bundler for splitting, hashing and asset handling.
Common wrong answerRecommending a rewrite of the build "because it's Rust and faster". The expected lead-level answer starts from the measured pain, not from the tool.
Node, Deno, Bun, or an edge runtime — how do you choose?senior

Node is the default: the largest ecosystem, the most operational knowledge, LTS discipline, and it has closed most of the DX gap (native TypeScript, test runner, fetch). Deno's pitch is security-by-default permissions, a batteries-included toolchain and first-class TypeScript; Bun's is speed and an all-in-one runtime plus package manager, with npm compatibility that is good but not total. Edge runtimes (Cloudflare Workers, Deno Deploy, Vercel Edge) run a Web-API subset on V8 isolates with millisecond cold starts and geographic distribution, at the cost of no full Node API, execution-time and memory limits, and different database access patterns. The decision framework to state: what does the workload need (long-lived connections? native modules? CPU?), what does the team already operate, and what is the exit cost if the choice is wrong — which favours writing to Web-standard APIs so the runtime is a deployment decision rather than an architectural one.

Follow-ups
  • Where do edge runtimes genuinely win? Latency-sensitive read paths, auth/routing middleware, personalisation at the CDN — not long transactions or heavy CPU.
  • Biggest hidden cost of a non-Node runtime? The long tail of libraries and observability agents that assume Node APIs.
  • Portability trick? Depend on fetch, web streams and Request/Response; keep runtime-specific code in one adapter module.
Common wrong answer"Bun, because it's faster." Startup and benchmark speed rarely dominate real service latency, and the question is about judgment under organisational constraints, not about a benchmark chart.
How do you decide what to transpile and polyfill?senior

From data, not habit. Set browserslist from your own analytics with an explicit support policy, and let the toolchain derive targets from it; ship modern syntax to modern browsers and stop shipping ES5 to everyone — in 2026 a "supports the last two versions plus Safari 16" baseline removes a large fraction of transpiled output and its runtime helpers. Polyfill by feature detection and only what you use (core-js with useBuiltIns: 'usage'), not a blanket bundle, and prefer progressive enhancement where a missing API can degrade. TypeScript's target is a separate decision from the bundler's: set it to what your runtime supports so tsc does not downlevel syntax the bundler would have kept — and note that target: es5 no longer exists in TypeScript 7.

Follow-ups
  • How much does an old baseline cost? Downlevelled async/generators and class fields add meaningful bytes and slower code paths — measure it as bundle delta per target.
  • Differential serving (modern/legacy bundles)? Possible via module/nomodule, but it doubles the build; usually only worth it with a large, measured legacy segment.
  • What replaced "just use Babel"? esbuild/SWC/Rolldown for transforms; Babel remains where you need custom AST plugins.
Common wrong answer"Target ES5 to be safe." It is not safe, it is expensive: bigger, slower bundles for every modern user to serve a segment that in most products no longer exists — and it is not even available in the current compiler.
How do you keep a team current without chasing every release?senior

Make currency a maintained process rather than an individual hobby. Concretely: a quarterly dependency and runtime upgrade cadence with a named owner so upgrades are routine rather than heroic; an ADR for anything that changes a boundary, so the reasoning outlives the person; a small "evaluate before adopt" rubric (does it solve a pain we measured, what is the migration and exit cost, who maintains it, how many people must learn it); one shared channel for release notes worth reading (TC39 finished proposals, Node LTS schedule, TypeScript release blog, browser Baseline updates); and a modest time budget for a spike that produces a written recommendation. The lead-level framing: the goal is not to be on the newest thing, it is to never be more than one comfortable upgrade away from it.

Follow-ups
  • How do you handle a team that wants to adopt everything? Require the rubric and a rollback plan; enthusiasm is cheap, migrations are not.
  • And a team that never upgrades? Make the cost visible — a security deadline, an LTS end-of-life date, the size of the eventual jump.
  • What is a good forcing function? Node LTS end-of-life and browser Baseline, because both come with dates you do not control.
Common wrong answer"We upgrade when something breaks." Deferred upgrades compound into a migration nobody has budget for, and it is usually a security advisory that eventually sets the schedule.

17 Judgment calls

Open-ended questions with no single right answer. They are asked at lead and principal level to see how you reason under constraints, whether you name trade-offs before you are pushed, and whether your position survives a counter-argument. Each block below says what a strong answer demonstrates and which trade-offs you are expected to raise unprompted — attempt yours out loud first.

Is TypeScript worth it for a three-person team shipping a prototype?principal

What a strong answer shows. That you separate the cost of the type system from the cost of the toolchain, and that you have an opinion about when the prototype becomes production. The strong position in 2026 is usually "yes, with loose settings", because the toolchain cost has collapsed — Node runs .ts directly, the compiler is a fast native binary, editors give you inference regardless — while the benefit (refactoring confidence, autocomplete as documentation, safe onboarding) arrives immediately. The weak position is not "no", it is any answer that treats it as an identity question.

Trade-offs to name unprompted. Types slow the first draft of exploratory code and can push a team into modelling before it understands the domain; a prototype that survives ends up with the types you chose in week one; strictness ratchets are cheap to add later and expensive to add much later; and if the team has no TypeScript experience, the learning cost lands exactly when velocity matters most. Name the escape hatch you would accept (any at the edges, strict off initially) and the date by which you would tighten it.

How much any is acceptable in a production codebase?principal

What a strong answer shows. That you distinguish where from how much. A localised any behind a validated boundary is a contained decision; an any in an exported signature is a hole with unlimited blast radius, because it disables checking in every consumer. So the policy is positional: none in public APIs, none on parsed I/O, tolerated in test fixtures and in narrow interop with untyped dependencies — always with a comment and preferably as unknown plus a guard instead.

Trade-offs to name unprompted. A hard ban produces as unknown as T, which is worse because it is invisible to the no-explicit-any lint rule; a ratchet (count may not increase) is more effective than a threshold; measuring "type coverage" is a proxy, not a goal; and the real cost of a permissive stance is not the any itself but the false confidence that "we have TypeScript".

Should internal service-to-service calls be validated at runtime, or is that paranoid?principal

What a strong answer shows. Risk-weighted thinking rather than a blanket rule. Validation buys a clear failure at the boundary instead of a confusing failure three layers in, and it is what makes independent deployment safe: the other team can ship a schema change on Tuesday whether or not you agreed. The nuanced answer distinguishes full parse (small payloads, high blast radius, money or auth involved) from cheap structural checks or contract tests (hot paths, large payloads, same-team services).

Trade-offs to name unprompted. CPU cost on large bodies and its effect on p99; the maintenance cost of a second source of truth if the schema is hand-written rather than generated; that validation is not a substitute for versioning and consumer-driven contract tests; and that being strict about unknown fields breaks forward compatibility — the usual answer is strict on shape, permissive on additions.

Monorepo or many repositories for a JavaScript/TypeScript estate?principal

What a strong answer shows. That you know what each choice actually optimises. A monorepo makes atomic cross-package changes, one dependency version and shared tooling cheap, at the cost of needing serious build infrastructure — affected-graph task running, remote caching, project references, CODEOWNERS — and of coupling everyone's CI. Many repos give teams independence and small blast radius, and charge for it in version skew, duplicated tooling and multi-PR changes that go out of order.

Trade-offs to name unprompted. The deciding variable is usually how often changes cross package boundaries, not repository count; a monorepo without caching becomes a shared queue everyone waits in; publishing internal packages introduces a release cadence that slows cross-cutting work; and the migration between models is expensive in both directions, so the right answer names what evidence would change it.

Where do you draw the line between framework-agnostic core code and framework-native code?principal

What a strong answer shows. A defensible boundary rather than a purity claim. Domain logic, validation, and the API client are worth keeping in plain TypeScript with no framework imports: they are testable without a renderer, portable across a rewrite, and shareable between a web app, a worker and a server. Rendering, routing, forms and data fetching are usually better done the framework's way, because fighting the framework's idioms costs more than the portability is worth.

Trade-offs to name unprompted. An abstraction layer over a framework is itself a framework you now maintain; premature portability produces adapters nobody uses; the honest reason for the boundary is usually testability and onboarding rather than a hypothetical migration; and the cost of the line being in the wrong place shows up as either untestable components or a "core" that quietly reimplements the framework.

A five-year-old JavaScript codebase is slowing the team down. Rewrite or migrate?principal

What a strong answer shows. That you start from a diagnosis, not a preference: which specific properties are costing time — no types, no tests, tangled module graph, dead code, an unsupported framework version — and which of those can be fixed in place. Incremental migration behind a stable boundary (strangler pattern, new code in TypeScript, module-by-module conversion, characterisation tests before touching behaviour) keeps value flowing and is right the large majority of the time.

Trade-offs to name unprompted. Rewrites lose undocumented behaviour that the old system encodes and that users depend on; they run against a moving target because the old system keeps changing; the honest case for a rewrite is a hard external forcing function (an unsupported runtime, a platform being shut down) or a genuinely small system. Also name the human factor: a migration is unglamorous and needs explicit recognition or it stalls at 60%.

The platform can do it now — when should you still use a library?senior

What a strong answer shows. A cost model. The platform wins when the API is stable, sufficient and already loaded: fetch, Intl, structuredClone, observers, AbortController, increasingly Temporal. A library still wins when it absorbs genuine complexity you would otherwise own (a rich text editor, a validation ecosystem, a virtualised table), when it smooths a browser matrix you must support, or when its ergonomics measurably reduce mistakes on something risky.

Trade-offs to name unprompted. Every dependency is bytes, a supply-chain surface, an upgrade obligation and a thing to learn; every hand-rolled utility is code you own forever and will get wrong at the edges; the worst outcome is a thin wrapper around a platform API that adds an abstraction without removing a decision. Say how you would decide: measure the bytes, check Baseline support against your analytics, and prefer the option with the cheaper exit.

Should the team standardise on exceptions or on Result types?principal

What a strong answer shows. That consistency is the actual goal and that you can pick a defensible split: Result for expected domain outcomes at module boundaries, exceptions for programmer errors and infrastructure failure, with a documented rule for which is which. A strong answer also says how it is enforced — lint, review, a shared Result helper — because a policy nobody can apply mechanically decays into both styles everywhere.

Trade-offs to name unprompted. Result is viral and verbose without helper combinators, awkward at framework callbacks, and tempting to unwrap carelessly (result.value!), which loses the whole benefit; exceptions are invisible in signatures, and TypeScript will never have checked exceptions. Note the migration cost of switching an existing codebase, and that half-applied is worse than either.

SPA, server-rendered with hydration, or islands — how do you argue it?principal

What a strong answer shows. That the decision is driven by the product's interaction profile and audience devices, and that you can name the JavaScript cost of each: an SPA pays a large upfront bundle and a slow first render but is cheap per interaction; SSR with full hydration pays twice — render on the server, then execute and reconcile on the client, which is the classic INP regression exactly when users first click; islands/partial hydration ships interactivity only where it exists, at the cost of a more constrained programming model and a smaller ecosystem.

Trade-offs to name unprompted. SEO and first-paint requirements, device mix in the field (a mid-range Android is where hydration hurts), operational cost and complexity of running SSR, caching strategy (a static page at the CDN beats every rendering strategy), and team familiarity — the architecture the team can debug at 3am usually wins over the one that benchmarks better.

When is it right to make a breaking change in a shared internal package?principal

What a strong answer shows. That you count the total cost across consumers rather than the cost to the owning team, and that you know the cheaper alternatives: add the new API alongside the old, deprecate with @deprecated and a codemod, migrate consumers yourself, then remove. A breaking change is right when the old API is actively causing defects, when maintaining both is materially expensive, or when a security or correctness fix demands it — and it comes with a migration guide, a codemod where possible, and a deadline.

Trade-offs to name unprompted. N teams × migration effort is the real price; in a monorepo you can pay it yourself atomically, which changes the calculus completely; type-level breaking changes are invisible to semver tooling, so an API report and a major version are the only signals consumers get; and a long deprecation window means supporting two paths, which is its own tax.

18 Design exercises

Three exercises where this topic meets system design. These are the shapes JavaScript and TypeScript questions actually take in a design round: the language is the medium, but the discussion is about contracts, failure and scale. Read the prompt, write down the clarifying questions you would ask, sketch your design, and only then open the solution outline.

Exercise 1 — A typed contract between a TypeScript front end and its services

Prompt. Your web app talks to six backend services owned by four teams. Front-end engineers keep discovering field changes in production; hand-written response interfaces have drifted; errors are inconsistent; and nobody can tell which client versions are still calling a deprecated endpoint. Design the client-side contract layer.

Clarifying questions to ask. Do the services publish a machine-readable contract (OpenAPI, protobuf, GraphQL schema) or would we be reverse-engineering? Who owns the schema, and can we make CI on their side break when they break us? What is the deploy relationship — can the client be older than the server, and for how long? What are the payload sizes and the latency budget, so we can afford validation? Do we need offline or optimistic updates? What is the error taxonomy the UI must distinguish (retryable, user-fixable, fatal)?

Show a strong solution outline and the trade-offs to name unpromptedprincipal

Shape. One generated source of truth per service: types and a runtime validator generated from the published schema, checked into the client repo and regenerated in CI so a schema change shows up as a reviewable diff. A single thin transport layer wraps fetch and owns cross-cutting concerns — base URL and versioning, auth, correlation id, timeout via AbortSignal.timeout, retry with jitter for idempotent verbs only, and a normalised error model. Responses are parsed at that boundary into domain types; nothing downstream sees an unvalidated object or a raw Response. Errors become a discriminated union (network, timeout, http with status, validation, aborted) so UI code branches exhaustively. Deprecation is observable: the client sends its version, the server can return a deprecation header, and usage is logged per endpoint per client version.

type ApiError =
  | { kind: 'network'; cause: unknown }
  | { kind: 'timeout'; ms: number }
  | { kind: 'http'; status: number; code?: string; retryable: boolean }
  | { kind: 'validation'; issues: Issue[] }   // our contract broke — alert, don't retry
  | { kind: 'aborted' };

export async function call<T>(req: TypedRequest<T>, signal?: AbortSignal): Promise<Result<T, ApiError>> { /* ... */ }

Trade-offs to name unprompted. Validation costs CPU on large payloads — measure it, and consider validating only in non-production or only the fields you consume for the biggest responses. Strict validation on unknown fields breaks forward compatibility, so be permissive about additions and strict about the shape you use. Generated code is only as good as the published contract: if the services do not publish one, the first deliverable is making them, and until then a hand-written schema is a second source of truth that will drift. Codegen adds a build step and a review burden; the payoff is that a breaking change surfaces in a pull request instead of in production. Finally, note the organisational half: consumer-driven contract tests running in the producers' pipelines are what actually stop the drift — the client-side layer only detects it.

Exercise 2 — A collaborative editing surface in the browser

Prompt. Add multi-user real-time editing to a document view: several people typing at once, presence indicators, sane behaviour on a flaky mobile connection, and no data loss if the tab is closed mid-edit. It must stay responsive on a mid-range Android phone with documents up to a few megabytes.

Clarifying questions to ask. How many concurrent editors per document — three, or three hundred? Is the content plain text, rich text, or a structured model? Do we need true offline editing or just resilience to short drops? Is a server-authoritative model acceptable, or must merges work peer-to-peer? What is the durability requirement — can we lose the last 200 ms? Is there an existing backend we must fit, and does it support WebSocket at the edge?

Show a strong solution outline and the trade-offs to name unpromptedprincipal

Shape. Local-first: apply every edit to local state immediately and render optimistically, then reconcile. Choose the merge model deliberately — a CRDT (Yjs/Automerge) for real offline and peer merging, or server-authoritative OT/version-vector reconciliation when a server is always in the loop and you want smaller payloads and simpler debugging. Transport is a WebSocket with an explicit protocol: an outbound queue with sequence numbers, acknowledgements, exponential backoff with jitter on reconnect, and resume-from-sequence so a drop replays rather than resyncs. Persist the pending queue and the last known document version to IndexedDB on every change so a closed tab loses nothing. Keep the main thread free: run the CRDT/diff work in a Web Worker, batch remote updates per animation frame rather than per message, and throttle presence to a few updates per second. Wire teardown to an AbortController so listeners, observers and the socket die with the view.

Trade-offs to name unprompted. CRDTs buy offline correctness and pay in document size and memory (tombstones grow; you need compaction/garbage collection), plus a merge result that is convergent but not always what a human meant. Server-authoritative is simpler to reason about and debug but needs the server online and a conflict story when it is not. Presence is high-frequency, low-value traffic — sample it and drop it first under pressure. Backpressure matters in both directions: a burst of remote updates must be coalesced, or you rebuild the DOM faster than you can paint. Security is part of the design: authorise per document on the socket, validate every inbound operation server-side, and never trust a client-supplied version. Finally, name the mobile constraints explicitly — background tabs get throttled timers, sockets are killed by the OS, and memory limits are lower, so reconnect and rehydrate must be routine, not exceptional.

Exercise 3 — A Node ingestion pipeline for large third-party files

Prompt. Partners upload CSV/JSONL files ranging from kilobytes to several gigabytes. Each row must be validated, enriched by a rate-limited third-party API, and written to a database. Files arrive in bursts. Failures must be resumable, nothing may be double-charged in the enrichment step, and one bad file must not take the service down.

Clarifying questions to ask. What is the acceptable end-to-end latency — minutes or hours? What are the enrichment API's rate limits and its idempotency semantics? What should happen to a file that is 90% valid: partial ingest, or all-or-nothing? Is ordering within a file significant? What is the retention and audit requirement for rejected rows? Do we control the upload path (can we get object storage plus an event) or must the HTTP service accept the bytes?

Show a strong solution outline and the trade-offs to name unpromptedprincipal

Shape. Decouple upload from processing: the HTTP tier streams the body straight to object storage and enqueues a job — never buffers the file, never processes inline. A worker streams the object with pipeline() through a line splitter, a parser and a validating transform, so memory stays bounded regardless of file size; invalid rows go to a rejects file with line numbers rather than aborting the run. Enrichment runs through a bounded concurrency pool sized to the partner's rate limit, with retry-with-jitter on 429/5xx, a circuit breaker, and a client-generated idempotency key per row so a retry cannot double-charge. Writes are batched (a few hundred rows per statement) and idempotent via a natural key upsert. Resumability comes from a checkpoint — the last committed byte offset or line number, stored per job — so a restart resumes rather than replays. CPU-bound parsing goes to worker_threads if profiling shows the loop blocking. Observability: rows/second, reject rate, enrichment latency and 429 rate, queue depth, and event-loop lag, with the job id as the correlation id throughout.

await pipeline(
  s3.getObject(key).Body as Readable,
  split2(),                                   // line framing
  validateRows({ onReject: rejects.write }),  // never throws on one bad row
  enrichBounded({ concurrency: 8, signal }),  // rate-limit shaped
  batchInsert({ size: 500, idempotent: true }),
);

Trade-offs to name unprompted. Partial ingest is friendlier and makes reconciliation harder — pick one and make it contractual, with a per-file report either way. Checkpoint granularity trades duplicate work against bookkeeping cost, and only works if the write step is idempotent. Concurrency is bounded by the partner's limit, not by your cores, so throughput is theirs to give; if the SLA needs more, the answer is negotiation or caching enrichment results, not more workers. Bursts need queue-depth-based autoscaling plus a per-partner fairness rule, or one large upload starves everyone else — a bulkhead per partner is worth the complexity. Note the failure isolation explicitly: one poison row goes to rejects, one poison file fails its job and stops after N attempts on a dead-letter queue, and neither takes the service down. And name what you would test: a soak run with a multi-gigabyte file to prove memory is flat, and a fault injection that kills the worker mid-file to prove resume works.

19 Night-before cheat sheet

The ten questions most likely to be asked in any JavaScript/TypeScript loop, with the one-sentence answer to have ready. If you can say each of these cleanly and then go one level deeper when pushed, you are prepared for the first thirty minutes of almost any interview in this topic.

#QuestionOne-sentence answer
01What is a closure?A function plus the lexical environment it was created in, keeping live references to the outer bindings so the scope survives as long as the function does.
02Macrotask vs microtask?After each task the engine drains the entire microtask queue (promise reactions) before the next task or a repaint, so promises always beat timers.
03What does await do?Suspends the function and schedules the rest of it as a microtask on the awaited value — it never blocks the thread.
04How is this bound?At the call site by four rules — new, explicit call/bind, the object before the dot, then default — except in arrows, which have no this and use the enclosing scope's.
05any vs unknown?any switches checking off in both directions and spreads; unknown accepts anything but permits nothing until you narrow it.
06Structural typing?Assignability is decided by shape, not by name — which is why an unvalidated JSON response "is" a User until it isn't.
07Discriminated union + exhaustiveness?A union tagged by a literal field, plus an assertNever(x: never) default, so adding a variant turns every unhandled switch into a compile error.
08== vs ===?=== compares without coercion (except NaN !== NaN and +0 === -0); == runs the coercion algorithm, and its only defensible use is x == null.
09ESM vs CommonJS?ESM is a statically analysed graph with hoisted, live bindings and top-level await; CJS is a synchronous function call returning a snapshot — hence tree shaking works for one and not the other.
10Why isn't TypeScript enough?It is erased at runtime and deliberately unsound (assertions, any, array covariance, bivariant methods), so every I/O boundary needs a real parse.
