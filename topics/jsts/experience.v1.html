01The event loop that looked like a slow database

senior → staff performance diagnosis

EXAMPLE — replace with your own

We ran a pricing API on Node, about 3,000 requests per second across twelve pods. The p50 was a comfortable 12 ms and had been for a year. Then, over about three weeks, the p99 crept from 90 ms to 1.8 seconds — and only the p99. Everyone's first instinct, mine included, was the database: the checkout team had just added an index, and "slow tail, must be Postgres" is the cheapest story in the building. I spent two days on that theory before I noticed the thing that killed it: our own database driver reported a p99 of 9 ms for the same window. The queries were fine. The time was disappearing after the driver handed the rows back.

What I did next is the part I'd tell an interviewer, because it's the part that generalises. Node is single-threaded for your JavaScript: one call stack, one event loop cycling through timers, pending callbacks, poll, check and close phases, draining the microtask queue completely between every callback. If any callback holds the stack for 400 ms, every request that was ready to be served during those 400 ms waits — and none of that wait appears in any downstream client's own timing. So the tail latency of a Node service is, more often than people expect, a measure of the worst synchronous block anywhere in the process. I stopped instrumenting dependencies and instrumented the loop itself with perf_hooks.monitorEventLoopDelay(), which uses a libuv timer to sample how late the loop is running and gives you a real histogram rather than an average.

import { monitorEventLoopDelay, performance } from 'node:perf_hooks';

const h = monitorEventLoopDelay({ resolution: 10 }); // ms sampling
h.enable();

setInterval(() => {
  // nanoseconds -> ms; report as a gauge, alert on p99, not on mean
  metrics.gauge('eventloop.delay.p50', h.percentile(50) / 1e6);
  metrics.gauge('eventloop.delay.p99', h.percentile(99) / 1e6);
  metrics.gauge('eventloop.delay.max', h.max / 1e6);
  h.reset();
}, 10_000).unref();

Event-loop delay p99 came back at 1.4 seconds, which matched the missing time almost exactly. From there it was three offenders, found by turning on --cpu-prof on one pod for sixty seconds and reading the flame graph. First, an internal /catalog/export endpoint that JSON.parse-d a 40 MB response body — JSON.parse is a synchronous C++ call, it does not yield, and 40 MB cost about 380 ms every time. Second, a token check that used crypto.pbkdf2Sync instead of the callback form, so it burned 90 ms on the main thread rather than on libuv's thread pool. Third — and this was the ugly one — a validation regex of the shape /^(\w+\s?)+$/ against a free-text description field. On most inputs it was microseconds; on a 200-character string ending in a non-word character it backtracked catastrophically and pinned a core for seconds. Someone had pasted a product description with a trailing em dash and we had accidentally built a denial-of-service endpoint.

The fixes ranked by effort against payoff: the regex was replaced with a linear /^[\w\s]+$/ and a length cap, which took ten minutes and removed the multi-second spikes entirely; pbkdf2Sync became the async form, which moves the work to libuv's pool (four threads by default, tunable with UV_THREADPOOL_SIZE) and cost one line; the big parse moved into a worker_threads pool with a bounded queue, which took two days because we had to make the export endpoint asynchronous end to end. p99 landed at 74 ms. We also added event-loop delay as a first-class SLI with an alert at 200 ms, and a small load shedder that returns 503 on non-critical routes when lag exceeds 500 ms, so the next time this happens the service degrades instead of timing out.

What I'd do differently: I'd have instrumented the loop on day one. Two days went into a database theory that a single gauge would have refuted in ten minutes. And I'd have caught the regex in review — I have since put a linter rule for super-linear regexes in the shared config, because "spot it in code review" is not a control, it's a hope.

What the interviewer is really probing. Whether you diagnose from evidence or from folklore. "The tail got worse so it must be the database" is folklore; a histogram of event-loop delay is evidence. They also want to see that you know Node's concurrency model well enough to explain why only the tail moved — one blocked callback penalises whoever was unlucky enough to be queued behind it, which shows up at p99 long before it shows up at p50.

The mistake candidates make on this archetype. Narrating the tools instead of the reasoning ("I opened Chrome DevTools, then I looked at a flame graph, then…"), and never stating the number they moved. The other classic is claiming the whole diagnosis solo when a colleague pointed you at the flame graph — say who did what; interviewers hear the difference.

(c) Recall prompts

When did a latency problem you owned turn out to be somewhere other than where everyone assumed?

Look for the moment a shared assumption got disproved by a measurement. Cache, GC, DNS, TLS handshakes, a connection pool ceiling, a serialization cost, a sidecar. The story is the disproof, not the fix.

When did you last see JavaScript behave differently under load than in dev?

Things that only appear under concurrency: connection pool exhaustion, thread-pool saturation, a cache stampede, a promise that fans out unbounded, an in-memory map that grows with traffic. Dev has one user; that's the whole difference.

What is the worst synchronous block you have ever shipped?

Candidates: JSON.parse/stringify on a large payload, readFileSync in a request path, a sync crypto call, Array.prototype.sort on a huge array, a catastrophic regex, a template render. Owning one of your own is worth more than describing someone else's.

What did you add so the same class of problem gets caught next time?

The strongest ending to a performance story is a control, not a patch: a new SLI, an alert threshold you argued for, a load test in CI, a lint rule, a budget in the build.

(d) Follow-up drill chain

Why did only p99 move, and not p50?

Because the block is rare but total. A 400 ms synchronous callback that fires on one request in two hundred delays every request that was ready during those 400 ms. At 3,000 rps that is roughly 1,200 requests wearing part of the delay, so the tail smears badly while the median — served on a loop that happened to be idle — never notices. That is also why averaging event-loop delay is useless: you have to look at percentiles and max, because the whole signal lives in the outliers.

Why not just add pods until the tail is acceptable?

Because the block is per-process, not per-cluster. Doubling pods halves the chance a given request lands on a blocked one, so the tail improves sub-linearly while cost rises linearly — and the catastrophic regex could still pin a core for seconds on whichever pod got the bad input. Horizontal scale is the right answer for throughput saturation; it is the wrong answer for a synchronous stall. I'd rather spend ten minutes on the regex than 40% more on compute forever.

At what scale does the worker-thread pool stop being the answer?

Roughly when the CPU work starts to dominate the box. Workers move the block off the loop but they still compete for the same cores, and moving a 40 MB payload costs a structured clone unless you use SharedArrayBuffer or transferable ArrayBuffers. Once export volume grew past a few per second we would have been running a batch system inside a request server, so the honest next step is a queue and a separate worker deployment that can scale on its own metric. I'd also stop using Node for the transform at that point — this is exactly the case where a different runtime earns its keep.

What did you trade away?

Three things. The export endpoint became asynchronous, so callers had to poll for a result — a worse API in exchange for a service that stays up. The load shedder can reject requests that would have succeeded, which is a deliberate choice to fail fast rather than time out. And the stricter validation regex rejects a small number of legitimate descriptions with unusual punctuation, which we accepted after checking it was under 0.1% of writes and gave product a way to allow-list.

How would you find this on a service you had never seen, in the middle of an incident?

Three moves, in order. Compare the service's own latency against the latency its dependencies report — a gap that big means the time is being spent in-process. Turn on event-loop delay, either through monitorEventLoopDelay if it's already wired or via the runtime's metrics endpoint, because it separates "we are blocked" from "we are waiting". Then take a 60-second CPU profile on one instance with --cpu-prof and read the widest frame. That sequence tells you in-process versus downstream, blocked versus waiting, and which function, and it takes about ten minutes.

Would anything about this diagnosis change on the current Node release?

The mechanism is unchanged — that is the point of understanding it rather than memorising a tool. What has improved is the ergonomics: the built-in diagnostics channel and the stable node --run and test-runner tooling in the Node 24 LTS line make it easier to ship this instrumentation without extra dependencies, and Node 26 (Current since May 2026, entering LTS in October) tightens permission and startup behaviour. I would still reach for monitorEventLoopDelay plus --cpu-prof first; they are stable, dependency-free, and safe to enable on one pod in production.

02Shared types package vs generated clients

staff → principal architectural trade-off

EXAMPLE — replace with your own

Six product teams, one TypeScript monorepo for the front ends, eight backend services in a mix of TypeScript and another language. The question on the table was how the front ends should know the shape of a backend response. Two camps, both reasonable. Camp A wanted a hand-written @org/contracts package: interfaces authored by humans, versioned on npm, imported by everybody. Camp B wanted types generated from each service's OpenAPI document at build time, with nothing hand-written at all. I was asked to decide, and the deciding argument turned out not to be about types at all.

The technical fact that framed it is that TypeScript is structurally typed and its types are erased. An interface OrderDto in a shared package does not check anything at runtime; it is a compile-time assertion that the JSON you parsed happens to match a shape you asserted it has. So the real question was: what mechanism makes that assertion true, and what happens when it stops being true? A hand-written package makes it true by human discipline — someone remembers to update the interface when the service changes. Generation makes it true by construction, but only as true as the OpenAPI document, and only at the moment you regenerate.

I ran a two-week spike and measured the failure mode rather than the ergonomics. Over the previous six months we had eighteen incidents caused by a front end reading a field the backend had renamed or made nullable. Every one of them had a green build. That number is what settled it: hand-written contracts had been failing silently at a rate of three a month, and no amount of "be more careful" was going to change that.

We landed on generation plus a runtime boundary, which is a third option neither camp had proposed. Types are generated from each service's OpenAPI spec on every build and committed, so a spec change shows up as a diff in a pull request that a human reviews. At the edge of the front end — exactly one place, the fetch wrapper — the response is parsed by a schema validator rather than cast. Everything inside the app then works with a type the compiler can trust, because something checked it at runtime.

// The dangerous version: a lie the compiler cannot catch.
const order = await res.json() as OrderDto;   // `any` in a nice suit

// The version we shipped: one runtime check at the boundary.
import * as v from 'valibot';                 // any Standard Schema library works

const OrderDto = v.object({
  id: v.string(),
  total: v.number(),
  placedAt: v.string(),
  discount: v.nullable(v.number()),           // nullable is part of the contract
});
type OrderDto = v.InferOutput<typeof OrderDto>;

export async function getOrder(id: string): Promise<OrderDto> {
  const res = await fetch(`/api/orders/${id}`);
  if (!res.ok) throw new HttpError(res);
  return v.parse(OrderDto, await res.json()); // throws here, not three screens later
}

The hidden win was the review surface. Because generated types are committed, a backend making discount nullable produces a red diff in six front-end repositories before it ships, and the conversation happens in a pull request instead of in an incident channel. Silent contract breaks went from three a month to two in the following year, both of which were fields the OpenAPI document itself described wrongly — which told us the next place to invest was spec accuracy, not the client generator.

What I'd do differently: I let the spike run two weeks when one would have done, because I was building consensus rather than gathering evidence, and I should have named that honestly. I'd also have set the deprecation policy for @org/contracts on day one; we let it linger for eight months and people kept importing from it out of habit.

What the interviewer is really probing. Whether you can hold two defensible options in your head and choose on evidence rather than taste — and whether you understand that TypeScript's types vanish at runtime, which is the single fact this decision turns on. At staff and above they also want to see you reframe: the winning answer was not "A or B" but "generation plus a runtime boundary", and finding the third option is the job.

The mistake candidates make on this archetype. Arguing aesthetics ("generated types are ugly"), or presenting the trade-off as if one side had no case. If you cannot state the strongest version of the option you rejected, the interviewer concludes you never really evaluated it.

(c) Recall prompts

Where in your stack does a type assertion stand in for a real check?

Hunt for as casts at I/O boundaries: res.json() as T, JSON.parse(...) as T, process.env reads, message queue payloads, browser storage reads, database driver rows. Each one is a place your types are a promise nobody keeps.

What is a decision you made that you had to sell twice?

Once to the room, once again six months later when someone new asked why. If you wrote the decision down — an ADR, a doc, a comment in the config — that is the detail that reads as staff-level.

When did counting past incidents change a design argument you were in?

The strongest version of this story has a number that ended the debate. Look for a time you went to the incident log, the bug tracker, or the git history instead of arguing from principle.

Which option did you reject, and can you still make its case?

Rehearse the steelman out loud. For this one: hand-written contracts read better, review better, and do not need build-time tooling in six repositories — genuinely good arguments that lost to a failure count.

(d) Follow-up drill chain

Why is a runtime check necessary at all, if the types are generated correctly?

Because generation is correct at build time and the network is a runtime concern. The service can deploy a change after your bundle shipped; a proxy can rewrite a body; the spec itself can be wrong; and a cached client can be weeks behind. TypeScript erases everything at compile time, so once the JSON crosses the wire the compiler has no further opinion. A parse at the boundary converts a silent wrong-shape bug three screens deep into a loud error at the fetch, with the offending field named.

What does that parse cost, and at what scale does it start to hurt?

For typical API payloads it is tens of microseconds and invisible next to the network. It starts to matter in two places: very large arrays — validating 50,000 rows one object at a time is real work — and hot server-to-server paths where you are parsing millions of messages. Our rule was to validate every response at the browser edge unconditionally, and on the server to validate at trust boundaries only, sampling rather than checking every message on internal high-volume queues. If validation ever showed up in a profile, the answer would be a compiled validator or checking a hash of the payload shape rather than dropping the check.

How did you get the team that lost the argument to actually adopt it?

By giving them the part of their proposal that was right. Their real objection was reviewability — generated code is hard to reason about — so we committed the generated output, which made every contract change a reviewable diff, which is the thing they wanted. I also had them own the fetch wrapper, because the person who was most worried about the boundary is the right person to own it. Neither of those was a concession on the decision; both were concessions on how it was implemented, and that is usually where agreement is available.

What if half your consumers are not TypeScript?

Then the schema-first option collapses, and that is exactly why we did not make zod the source of truth. A TypeScript schema library is a great single source of truth in a TypeScript-only stack, but the moment a Kotlin or Go consumer appears you need a language-neutral description — OpenAPI, protobuf, or a JSON Schema — and the TypeScript types become one generated output among several. I would rather generate from a neutral spec that everyone can consume than make five other teams depend on our type system.

What would you do differently with today's tooling?

Two things. I would target the Standard Schema interface rather than a specific validator, so the choice between zod, valibot and arktype is a swap rather than a rewrite. And I would turn on isolatedDeclarations in the shared packages: it forces explicit return types on exports, which makes declaration emit parallelisable and is one of the ways TypeScript 7's native compiler gets its speed. Both are cheap now and expensive to retrofit later.

03The Sunday outage from a floating version range

mid → senior production incident

EXAMPLE — replace with your own

On a Sunday at 02:10 the checkout service started returning 500s on every request. Nobody had deployed anything since Thursday. That last sentence is the interesting one, because it is almost always false — and it was false here too. Nobody had merged anything, but the service had been rebuilt: an autoscaling event triggered a fresh image build, and that build resolved dependencies differently from the one running since Thursday.

The Dockerfile said npm install, not npm ci. Those two commands are not variations on a theme. npm install treats the lockfile as a suggestion: if package.json allows a newer version inside its range, it takes it and rewrites the lock. npm ci deletes node_modules and installs exactly what the lockfile pins, failing if the lock and the manifest disagree. We had a caret range on a small date-formatting library, that library's maintainer had published a minor release nine hours earlier that changed its default export from a function to an object with a format property, and our code called it as a function. TypeError: fn is not a function, on every request, from a build nobody triggered on purpose.

The interesting failure was not the library — maintainers publish breaking minors, that is the world we live in — it was that our build was not reproducible and we did not know it. Rollback took four minutes once we understood it, because the previous image was still in the registry, but understanding it took thirty-eight, and the whole thirty-eight went into "but nothing changed". The lesson I now repeat to everyone I onboard: if your build is not pinned, "nothing changed" is not a fact you have, it is a fact you are assuming.

# What we had — resolves ranges afresh, rewrites the lockfile, non-reproducible
RUN npm install --omit=dev

# What we shipped — exact lockfile install, fails if lock and manifest disagree
RUN npm ci --omit=dev --ignore-scripts

# The guard in CI, so a drifting lockfile is a red build, not a 02:10 page
RUN npm ci --dry-run && git diff --exit-code package-lock.json

The remediation was four things and only one of them was the obvious one. npm ci everywhere, enforced by a CI check that fails if the lockfile changes during install. --ignore-scripts in the build, with an explicit allow-list for the two packages that genuinely need a postinstall, because a rebuild that fetches new code is also a rebuild that runs new code — and by 2026 that is the primary npm attack path, with worms observed abusing CI trusted-publishing tokens to republish themselves under every namespace a runner can reach. A minimum release age of three days on the registry proxy, so a package published nine hours ago simply is not available to our builds. And an image digest pin in the deployment, so an autoscale event redeploys a byte-identical artifact rather than rebuilding one.

What I'd do differently: I would have written down the "nothing changed" claim and then tried to falsify it, instead of believing it for half an hour. In an incident, "what is different between the working thing and the broken thing" is the only question, and "the image hash" is a difference even when the git SHA is not. I would also have pushed the minimum-release-age control earlier; I had read about it months before and filed it under "nice idea".

(d) Follow-up drill chain

Why didn't the lockfile save you?

Because npm install is allowed to ignore it. It reads the lock as a starting point, then re-resolves anything the ranges in package.json permit, installs the newer version and rewrites the lock in place. Inside a container that rewrite is thrown away with the layer, so the drift leaves no trace. npm ci is the opposite contract: it installs the lock exactly, refuses to update it, and errors if the manifest and lock disagree. The lockfile was never the problem; the command reading it was.

Wouldn't pinning exact versions instead of caret ranges solve this?

Only for your direct dependencies, and it trades one risk for another. Exact pins in package.json do nothing about transitive ranges, which is where most of the surface lives — you'd need overrides or a resolutions field to reach those. And exact pins everywhere means security patches stop arriving on their own, so you accumulate a different kind of debt. The lockfile is the right place for exactness, because it covers the whole tree; package.json ranges are the right place for intent. What I actually needed was a build command that honours the lockfile.

Does --ignore-scripts actually protect you?

Partly, and it is worth being precise about the limits because that is what separates a real answer from a checklist. It removes install-time execution, which is the most-used path in the current wave of npm worms. It does nothing about malicious code inside a module you then import and run, and nothing about a registry-level version substitution. Yarn Berry has disabled third-party scripts by default since v2 and pnpm and Bun offer comparable consumer-side controls, which is a genuine argument for switching package managers rather than bolting a flag onto npm. My layered answer is: block scripts, pin by digest, delay new releases, and treat provenance attestation as evidence of origin rather than evidence of safety.

At what scale does the minimum-release-age control become a problem?

When you have an urgent CVE and the fix is six hours old. The control is a bet that most bad publishes are caught within days and most good publishes can wait — true for a product team, less true for a security team. My rule: the review names the systemic cause and at most three controls, ranked by how many future incident classes each one removes. npm ci went in because it removes a whole category; "add a test for the date formatter" did not, because it removes one bug. 06The leak that only showed after 36 hours

senior → staff nasty debugging session

EXAMPLE — replace with your own

A Node service that was fine in every load test and died in production roughly every 40 hours with the container OOM-killed at its 2 GB limit. Restarting fixed it, and a Kubernetes liveness probe was quietly doing exactly that, so for two months it had been a graph nobody looked at rather than an incident. It surfaced when a bigger instance size made the cycle longer and the restarts started landing mid-request on a payment path.

The reason load tests never caught it is worth understanding, because it is the general lesson. V8 splits the heap into a small young generation collected by a copying scavenger — cheap, frequent, and it copies only the survivors — and an old generation collected by an incremental mark-and-sweep. Objects that survive two scavenges get promoted to old space. A leak is not "we allocate a lot"; a leak is "we keep a reference to things we are done with", so they survive scavenges, get promoted, and old space grows monotonically. A 20-minute load test allocates furiously and shows a beautiful sawtooth, because the scavenger is doing its job on short-lived garbage. It cannot show you a slow promotion of a few thousand objects an hour. Only wall-clock time shows that.

The method that actually found it: three heap snapshots from one pod at hour 2, hour 12 and hour 30, taken with v8.writeHeapSnapshot() triggered by a signal handler, then compared in DevTools using the summary-comparison view. The comparison is the whole technique — a single snapshot of a 1.6 GB heap is unreadable, but "what class of object grew by 400,000 instances between snapshot two and three" is a one-line answer. It was a Map of request-id to an abort controller and some request context. Entries were added on every request and removed in a finally block — except on the path where the client disconnected early, where the code returned before the try was entered. Roughly one in 900 requests, which at our volume was about 3,000 stranded entries an hour, each retaining a request context, each retaining a parsed body. The retainer path in the snapshot showed it in one screen.

// The shape of the bug: an unbounded map keyed by something ephemeral,
// with a cleanup path that a rare branch skips.
const inflight = new Map(); // request id -> { controller, ctx }

// Fix 1 - make cleanup structural, not a branch you must remember.
async function handle(req, res) {
  const entry = { controller: new AbortController(), ctx: makeCtx(req) };
  inflight.set(req.id, entry);
  try { await run(req, res, entry); }
  finally { inflight.delete(req.id); } // runs on every exit, including throws
}

// Fix 2 - make the cache incapable of unbounded growth.
// A WeakMap keyed by the request object lets GC reclaim entries once the
// request is unreachable; it is not a substitute for correct cleanup,
// it is the seat belt for when cleanup is missed again.
const byRequest = new WeakMap();

We shipped three things. The finally restructure, which was the actual fix. A hard cap on the map with a "this should never happen" metric when eviction fires, because an unbounded collection keyed on anything request-shaped is a leak waiting for a rare branch. And a heap-size alert based on the trend rather than a threshold — old-space growth over a six-hour window — because the previous alert only fired when we were already close to the limit, by which time you have minutes rather than hours to look. Memory flattened at 600 MB and stayed there.

What I'd do differently: I would have treated the restart graph as an incident two months earlier. A liveness probe that hides a leak is a control working exactly as designed and doing real harm, and I had walked past that graph myself. I also spent most of a day trying to reason about the leak from the code before taking snapshots — reading is seductive and comparing snapshots is decisive, and I now do the snapshots first.

(d) Follow-up drill chain

Why didn't the load test catch it?

Because it ran for twenty minutes and the leak was about 3,000 objects an hour. In that window V8's scavenger reclaims almost everything the test allocates — short-lived objects die in the young generation and never get promoted — so the graph is a healthy sawtooth. The leaked entries were a rounding error against test allocation volume. Duration and branch coverage were both wrong, and the second one is the harder problem.

Would a WeakMap have prevented it?

In this shape, yes, and it is worth being precise about why. WeakMap holds its keys weakly, so once the request object is unreachable the entry becomes collectable without anyone calling delete. But it only works if the key is the ephemeral thing — our map was keyed by a request-id string, and a string key is strongly held, so a WeakMap keyed that way would be no better. That distinction is the whole lesson: weak collections are keyed on the object whose lifetime you want to follow. I would still fix the finally, because relying on GC for correctness makes the behaviour non-deterministic and hard to test.

At what point does a leak stop being worth fixing?

When the growth rate multiplied by the deploy interval stays comfortably under the memory limit, and the process is genuinely stateless on restart. A service that gains 5 MB a day and deploys weekly does not have a problem worth a sprint. I would still want it measured and alerted on trend, because the calculation depends on a deploy cadence that will change without anyone revisiting the leak. What makes it non-negotiable is the restart landing mid-request on a path that is not idempotent — that is what turned this from a graph into an incident.

How would you find this in a browser instead of Node?

Same technique, different retainers. Take heap snapshots from the DevTools memory panel at intervals while driving the app through the suspect flow, and compare. The dominant browser leak is detached DOM: a node removed from the document but still referenced by a listener, a closure, or a framework's cached ref, which you find by filtering the snapshot on Detached. The structural fixes are the mirror image of the Node ones — remove listeners in the teardown path, use AbortController with addEventListener(..., { signal }) so one abort detaches everything, and be careful with anything module-level that outlives a route.

What would you build so nobody has to do this again?

Three cheap things. A trend alert on old-space growth rather than a threshold, because a threshold only fires when you are out of runway. A soak stage in the pipeline — one pod, realistic traffic mix including disconnects, twelve hours, assert heap slope — which is not free but is far cheaper than the incident. And a lint rule plus a review norm against module-level unbounded collections, so the shape that causes almost every leak needs an explicit justification. Detection first, though: I would rather find the next leak in six hours than prevent this exact one.

Number two was JSON. We were parsing four upstream responses and serialising one, and at that volume serialisation was 20% of CPU. We fixed the cheap half by not parsing fields we never read — several upstream responses were passed through almost verbatim, and streaming the bytes through instead of round-tripping them through objects removed the cost entirely for those. The expensive half we left alone, because a schema-compiled serialiser would have been a real speedup and a real maintenance burden, and we did not need it once the other work landed. Knowing which optimisation to not do is part of this story.

Number three was concurrency discipline. Under burst we were fanning out without any bound, so a slow partner turned into thousands of in-flight requests, which turned into memory pressure, which turned into GC pauses, which slowed everything including the healthy paths. The fixes were a bounded queue with explicit rejection, per-dependency timeouts and a deadline propagated through the fan-out, and a circuit breaker on the one partner that was reliably unreliable. This is where Promise.allSettled replaced Promise.all: with all, one rejection abandons the composition and we return nothing; with allSettled and a deadline, a degraded response beats no response.

We landed at 41,000 rps on 46 pods, against the 380 in the first model — about eight times better per pod, and none of it was a clever algorithm. It was connection reuse, not doing unnecessary work, and putting a bound on everything unbounded. What I'd do differently: I would have tested the failure shape earlier. We tuned for throughput for three weeks and only tested "what happens when a partner gets slow" in week four, which is when we found the unbounded fan-out. Load testing the sad path is more valuable than load testing the happy path, and it is always the thing that gets scheduled last.

(d) Follow-up drill chain

Why did connection pooling matter so much more than the code?

Because a TLS handshake is far more expensive than the request it protects, and without keep-alive you pay one per call. At four fan-out calls per request, connection setup was doing more cryptographic work per second than all our business logic combined. It is invisible in a normal profile because it shows up as time in native and kernel frames rather than in a function you wrote, and it does not appear at low load where the same few connections happen to get reused. That combination — expensive, invisible, and load-dependent — is why it survives to production so often.

Why not just use cluster and more pods?

We did run multiple workers per pod, so that lever was already pulled; the question is what you multiply. Clustering multiplies your per-request cost by your worker count, so if that cost is 44% too high, you are buying 44% more of everything forever. Horizontal scale is right for genuine CPU saturation with an efficient per-request path, and it does nothing at all for the collapse mode — thirty-eight more pods all fanning out unboundedly to a slow partner just brings the partner down faster. Fix the unit cost, then scale the unit.

At what scale does this architecture stop working?

Two ceilings. Fan-out amplification: at 40k rps we are issuing 160k downstream calls per second, so the partner services and the connection counts, not us, become the constraint — the next move is request coalescing and a short-TTL cache in front of the two hottest dependencies, which changes the shape from four calls to about 1.3. The second ceiling is the composition itself: past roughly 100k rps I would stop composing per-request and precompute, pushing the fan-out onto a stream consumer that maintains a materialised view. That is a different system with different consistency, and I would not build it until the cache tier stopped paying.

What did the bounded queue cost you?

We now reject requests we would previously have queued, which turns some latency into visible errors — a deliberate trade that needed a product conversation, not just an engineering one. It also added a tuning surface: queue depth, per-dependency timeouts, breaker thresholds, all of which drift as traffic changes and none of which has an obviously correct value. We set them from the load rig, wrote down the reasoning, and put the rejection rate on the dashboard next to latency so the trade stays visible. The alternative was a system that looked fine until it fell over entirely, which is a worse trade dressed up as a better one.

How did you make the deadline actually propagate?

One AbortSignal created per inbound request with the remaining budget, passed into every outbound call, so a partner cannot spend time we no longer have. AbortSignal.timeout() and AbortSignal.any() make this cheap to express — any lets a call be cancelled either by the client disconnecting or by the deadline. The discipline part is that the signal must be threaded through every layer, and any function that does I/O without accepting a signal is a hole in the scheme; we made that a review rule. Client disconnects then cancel the fan-out immediately, which was a meaningful saving on a page users abandon.

08Prototype pollution in a config merge

mid → senior security issue found and fixed

EXAMPLE — replace with your own

I was reviewing a pull request that added tenant-level feature overrides. The code took a JSON blob supplied through an admin API and deep-merged it into the service's default configuration object. Forty lines, well tested, and it handed any tenant admin the ability to change the behaviour of every request in the process.

The mechanism is prototype pollution, and it is a direct consequence of how JavaScript inheritance works. Every plain object delegates to Object.prototype, and the string "__proto__" in an assignment is not an ordinary key — it goes through a setter that reassigns the object's prototype. A recursive merge that walks the source object's keys and assigns them onto the target will, on seeing {"__proto__": {"isAdmin": true}}, write isAdmin onto Object.prototype. From that moment every object in the process that does not define isAdmin itself appears to have it, because property lookup walks the prototype chain. Somewhere else in the codebase there is an if (user.isAdmin) against an object built from a database row, and now it is true for everyone.

// The vulnerable shape - looks like every deep-merge helper ever written
function merge(target, source) {
  for (const key of Object.keys(source)) {
    if (isPlainObject(source[key])) merge(target[key] ??= {}, source[key]);
    else target[key] = source[key];        // "__proto__" here poisons everything
  }
  return target;
}

// Attack payload, arriving as ordinary tenant JSON
// {"features": {"__proto__": {"isInternalUser": true}}}

// Fixes, in order of how much they actually buy you
// 1. Do not build objects you then trust - validate against a schema and
//    take only the keys the schema declares. This removes the class.
// 2. Structural: null-prototype targets have no prototype to poison.
const cfg = Object.create(null);
// 3. Belt and braces inside any merge you must keep:
const BLOCKED = new Set(['__proto__', 'constructor', 'prototype']);
// 4. Read with Object.hasOwn, never a bare truthiness check:
if (Object.hasOwn(user, 'isAdmin') && user.isAdmin) { /* ... */ }

I did three things with it, in this order. I wrote a failing test that demonstrated the escalation end to end — from an HTTP request with the payload to a different endpoint returning internal data — because a proof of exploitability moves a ticket from "the linter is complaining" to "we fix this today", and I have watched theoretical findings sit in a backlog for a year. I raised it privately with the author first rather than in the public review thread, because a security finding in someone's pull request is a place where humiliation is easy and pointless. Then I went looking for the pattern elsewhere and found two more deep-merge helpers, one of which was reachable from an unauthenticated webhook endpoint and was substantially worse than the one I had started with.

The fix that shipped was not the blocklist, though we added one. The real fix was that tenant overrides now go through a schema parse that only emits the keys the schema declares, so unknown keys are dropped rather than merged — the merge no longer sees attacker-controlled key names at all. We also switched the config root to Object.create(null), added the CodeQL query for this pattern to CI, and I ran a 30-minute session for the team on why "__proto__", "constructor" and "prototype" are special, because the pattern will come back if only I understand it.

What I'd do differently: I framed it as a code-review finding when it was an architectural one — "we deep-merge untrusted input in three places" is a design problem, and treating it as three bugs meant we fixed three bugs. And I should have checked whether the same shape existed in the front end, where a polluted prototype can turn into DOM-based XSS through a templating library. I did that two months later and found one.

(d) Follow-up drill chain

Explain exactly why assigning "__proto__" is different from assigning any other key.

Object.prototype defines __proto__ as an accessor property whose setter changes the receiver's internal prototype link. So obj["__proto__"] = value is not a data write; it invokes that setter and re-parents the object. In a recursive merge the recursion then walks into the prototype and writes ordinary properties there, and because property lookup falls back along the prototype chain, every plain object in the realm that lacks its own copy of that key now appears to have it. Two related traps: Object.defineProperty and JSON.parse treat "__proto__" as an ordinary key, so data can carry it safely right up until a merge assigns it, and constructor.prototype reaches the same place by a different path, which is why blocklists that only cover __proto__ fail.

Why is the schema parse a better fix than the blocklist?

Because the blocklist enumerates the bad and the schema enumerates the good, and only one of those is future-proof. A blocklist has to anticipate every path to the prototype — __proto__, constructor.prototype, computed keys, nested cases, whatever the next disclosure adds — and it silently stops being sufficient without any signal. A schema that emits only its declared keys means attacker-controlled key names never enter the object graph at all, so the vulnerability class is structurally absent rather than filtered. It also gives you input validation you wanted anyway. I still added the blocklist, because defence in depth is cheap here, but I would not have shipped it alone.

What would the blast radius have been?

Process-wide and cross-tenant, which is what made it urgent. Object.prototype is shared by every plain object in the realm, so one tenant's payload changes what every other tenant's requests observe until the process restarts. In our case the reachable escalation was a truthiness check on an internal-user flag, giving read access to another tenant's data. Prototype pollution also composes with whatever else is in the process — a polluted key that a templating engine reads can become XSS, and one that a child-process helper reads can become argument injection. That "it depends what else is in the realm" quality is why I rate it higher than its own direct effect.

How did you get it fixed the same day rather than in the backlog?

The failing test. I wrote an integration test that posted the payload to the admin endpoint and then asserted that a completely different endpoint returned data it should not — one file, runs in CI, impossible to argue with. A description of a vulnerability invites a debate about likelihood; a red test is a statement about the current build. I also gave the author the fix rather than just the finding, so the ask was "review this" instead of "go and research prototype pollution", which is the difference between a same-day merge and a ticket.

Would freezing Object.prototype at startup be a reasonable blanket defence?

It genuinely stops the writes, and I have seen it used successfully in tightly controlled services. The cost is that it breaks anything that legitimately mutates built-in prototypes — some polyfills, some instrumentation and APM agents, some older libraries — and it fails at a distance, with an error far from the freeze. So my position is: worth doing in a small service where you control the dependency tree and can test the whole surface; risky as a blanket policy in a large application, where I would rather remove the class at the input boundary and keep the freeze as an idea for the highest-value processes.

09Untangling the CommonJS/ESM dual package

senior → staff tech-debt paydown

EXAMPLE — replace with your own

An internal SDK, five years old, about 30,000 lines, consumed by nineteen services and three front ends. It shipped a CommonJS build and an ESM build from the same source, and it had been quietly broken for two years in a way that produced one weird bug a quarter and no obvious cause. The symptom that finally got it funded: an instanceof check on our own error class returning false in production, in a service where the error had definitely come from the SDK.

That is the dual-package hazard, and it is worth explaining precisely because it is the kind of thing that reads as deep knowledge in an interview. A package that ships both formats can be loaded twice in one process — once as CommonJS by a transitive dependency that still uses require, once as ESM by the application's import. Node keeps separate module registries for the two, so you get two copies of every class, every symbol, and every module-level variable. instanceof compares prototype identity, so an error created by copy A fails the check against copy B's class. In our case the module-level registry of retry policies also existed twice, so half our configuration silently did nothing.

// The exports map that ended the ambiguity - one runtime shape, two type shapes,
// and no "import" condition pointing at a second copy of the runtime code.

  "type": "module",

    ".": {
      "types": "./dist/index.d.ts",
      "default": "./dist/index.js"
    },
    "./testing": {
      "types": "./dist/testing.d.ts",
      "default": "./dist/testing.js"
    }
  },
  "engines": { "node": ">=22" }
}

The fix that a year earlier would have been impossible is that Node can now require() an ES module — it landed behind a flag in Node 22, was unflagged in the 22 and 23 lines, and is ordinary behaviour on Node 24 LTS and Node 26. That changes the calculus completely. Previously, shipping ESM-only meant abandoning every CommonJS consumer, so everybody shipped dual builds and everybody had this hazard. Now a single ESM build serves both, as long as the CommonJS consumer does not need synchronous access to a module with top-level await. So the migration was: ship one ESM build, keep the CommonJS entry point only as a deprecated shim that re-exports from the same file, and delete it once every consumer was on Node 22 or later.

The engineering was three weeks; the coordination was three months. Nineteen services had to be on a supported Node version, and four were not. I built a dashboard from the deployment metadata showing Node version per service with a red line at the minimum, published the date the CommonJS entry would go away, and — this is the part that worked — offered to do the Node upgrade myself for any team that asked in the first month. Six asked. That offer cost me about ten days and removed the entire long tail of "we'll get to it", which would otherwise have cost far more in chasing.

Results: one copy of the SDK in every process, the quarterly weird bug gone, and the published bundle 40% smaller because we stopped shipping two builds. The instanceof class of bug has not recurred in the year since. What I'd do differently: I would have written the exports map with a single default condition from the start of the migration rather than trying to be clever with import/require conditions in the first attempt — my first exports map had both, which reintroduced the exact hazard I was removing, and a colleague caught it in review. That was a genuinely humbling three days.

(d) Follow-up drill chain

Explain the dual-package hazard as if to a mid-level engineer.

If your package can be loaded two ways, it can be loaded twice. Node keeps separate caches for CommonJS and ESM, so a transitive dependency doing require('@org/sdk') and your app doing import '@org/sdk' produce two independent module instances. Everything module-scoped is duplicated: classes, so instanceof across the boundary is false; symbols, unless they came from the global registry; caches and registries, so writes to one are invisible to the other. It is nasty because both copies work correctly in isolation and the failures look like unrelated bugs scattered across a year.

Why not keep the dual build and just make it stateless?

It is a real option and it is what many libraries do — no module-level mutable state, no classes whose identity matters, and the hazard mostly evaporates. Two reasons I did not. First, it is a constraint you have to enforce forever across every future contributor, with no compiler help, and our SDK genuinely wanted an error hierarchy and a policy registry. Second, it does not help bundle size or maintenance: two builds means two sets of build config, two sets of test runs, and subtle differences in behaviour between them. Statelessness is a good discipline for a small utility library and a bad bet for a stateful SDK.

What breaks for a CommonJS consumer doing require() of your ESM?

The hard limit is top-level await: require() is synchronous, so a module graph that awaits at the top level cannot be loaded that way and throws. That was a real constraint on our design — we removed the one top-level await we had, which was eagerly loading a config file, and made it lazy. Beyond that the ergonomics differ: the namespace object is frozen and the default export arrives as .default rather than as the module itself, which surprises people migrating from a CommonJS build that assigned module.exports directly. We documented that in the release notes and it caused two support questions, both in the first week.

How did you handle the teams that simply would not upgrade?

By separating "will not" from "cannot", because they need different answers. Two of the four were blocked by a native dependency that had no build for the newer Node, which is a real engineering problem I could help with and did. The other two had no capacity, so I did the upgrade for them — ten days of my time bought the deprecation date, which was worth far more than the ten days. What I did not do is extend the date; I had learned from a previous migration that a date that slips once stops functioning as a date, and every later conversation becomes a negotiation.

What would you tell a team starting a new internal package today?

ESM only, one build, "type": "module", an exports map with no import/require split for the runtime code, a Node engines floor at the current LTS, and verbatimModuleSyntax so import elision never surprises you. If a consumer needs CommonJS, require(esm) covers them on any supported Node. The dual build was the right answer in 2021 and is a liability now, and that is the general lesson worth carrying: a lot of JavaScript "best practice" is a workaround for a constraint that has since been removed, and nobody sends a notification when that happens.

10Teaching the type system without type golf

EXAMPLE — replace with your own

A strong mid-level engineer joined my team from a mostly-JavaScript background and, within two months, became the person writing the most elaborate types in the repository. Conditional types nested four deep, a template-literal type that parsed route strings into a parameter object, mapped types with three levels of infer. It was genuinely impressive, and it was making the codebase worse. Nobody else could review her pull requests, error messages from her utilities ran to eighty lines, and the editor had started to lag in the files that used them.

The hard part of this mentoring story is that "you are too good at this" is a terrible piece of feedback and an easy one to deliver badly. She was doing exactly what an ambitious engineer should do — pushing on a tool until she understood its limits — and the enthusiasm was an asset. What she was missing was the idea that types have a readership, and that a type is a design artifact with the same review-cost economics as any other code.

I did three things. First, I asked her to pair with me on reviewing someone else's pull request that used one of her utilities, so she watched the other engineer fail to understand the error message in real time. That did more than any feedback I could have given, because the cost stopped being abstract. Second, I gave her a heuristic she could apply herself rather than a rule I would enforce: a type should be easier to read than the runtime check it replaces. If explaining what the type does takes longer than the code it constrains, the type is the problem. Third, I gave her the interesting version of the problem — the same route-parsing utility, but with a budget: it had to produce an error message that named the offending route in under three lines, and it had to be understandable by someone who had learned conditional types that morning. She rewrote it in half the code with an explicit union instead of template-literal parsing, and it was better.

// The clever version: correct, unreviewable, and its errors are unreadable.
type Params<S extends string> =
  S extends `${string}:${infer P}/${infer Rest}` ? { [K in P]: string } & Params<Rest>
  : S extends `${string}:${infer P}` ? { [K in P]: string }
  : {};

// The version that shipped: a discriminated union anyone can read,
// generated from the route table we already had. Boring, and the
// error message says which route and which parameter.
type Routes = {
  '/orders/:id':            { id: string };
  '/orders/:id/items/:sku': { id: string; sku: string };
};
function href<R extends keyof Routes>(route: R, params: Routes[R]): string { /* ... */ }

The wider lesson I tried to land, which is the technical content of this story, is that TypeScript's type system is Turing-complete and that this is a hazard rather than a feature for application code. Type-level computation has real costs the compiler pays on every check and every editor keystroke, it degrades error messages sharply, and it moves logic into a place where you cannot log, breakpoint or unit-test it. The right defaults for application code are unions, discriminated unions, generics with clear constraints, and satisfies to check a value against a type without widening it. Conditional types and infer earn their place in library code where one hard type serves a thousand call sites — the same trade a compiler writer makes, and a bad trade in a feature module.

She was promoted eight months later, and the thing I pointed to in the case was the route utility rewrite — not because it was the hardest thing she did, but because she chose the simpler design after building the complicated one, and could explain the trade-off to the panel. What I'd do differently: I sat on the feedback for about five weeks because I did not want to discourage her, and in those five weeks two more of those utilities landed. Delaying feedback to protect someone's enthusiasm mostly protects your own comfort, and it made the eventual conversation bigger than it needed to be.

What the interviewer is really probing. Whether you can grow someone rather than correct them, and whether you have a defensible position on type-system complexity. The strongest version of this story shows the mentee reaching the conclusion themselves — you designed an experience, not a lecture. At staff level they are also listening for whether you can articulate when the clever type is correct, because a blanket "keep types simple" is as unthinking as type golf.

Name what they did, not what you said. The other mistake is picking a mentee who was struggling — mentoring a strong person into a better judgment is a harder and more interesting story than unblocking a weak one.

If the only evidence I had was that she said the sessions were useful, I would not claim the outcome.

That is a cheap experiment with an unambiguous outcome, and I would be genuinely willing to lose it — if the reviewer follows it easily, my premise about readership cost is wrong for our team. Turning a taste disagreement into an observation is nearly always available, and it is how you avoid mentoring becoming an argument about authority.

EXAMPLE — replace with your own

A scheduling product where every recurring booking one hour after the spring clock change was landing an hour wrong for users in a handful of time zones. About 900 bookings a year, each one a support ticket and an angry customer. The team's proposal was a full migration off Date to the Temporal API, estimated at a quarter. The deadline pressure was a contractual commitment to a customer whose bookings were among the affected ones, six weeks out. I had to negotiate what actually shipped in six weeks.

The technical context matters for the negotiation, so here it is. JavaScript's Date is a millisecond offset from the epoch with a local-time interpretation bolted on, no notion of a time zone beyond the host's, and no way to represent "9am on the 14th in Berlin" as a distinct thing from an instant. Recurring events are exactly that kind of value: the user means a wall-clock time in a named zone, and storing an instant throws away the information you need to reconstruct it after a DST transition. Temporal fixes this properly with separate types — Instant, PlainDateTime, ZonedDateTime — and it reached Stage 4 in March 2026 and is part of ES2026, shipping natively in Chrome 144 and Firefox 139 and in Edge, with Safari still behind. So the destination was not in doubt. The question was how much of it we needed in six weeks.

What I did was separate the bug from the migration, which sounds obvious written down and took two uncomfortable meetings to establish. The bug was a data-modelling error: we stored recurring bookings as UTC instants plus a recurrence rule, so the wall-clock time was unrecoverable. That has nothing to do with which date library we use. We could fix it by adding two columns — the local wall-clock time and the IANA zone identifier — and computing the instant at read time, which is about 400 lines and touches the booking write path and the expansion job. Six weeks was comfortable. The Temporal migration is a separate, larger, better piece of work: it makes the whole codebase harder to get wrong, and it does not need to be on the critical path of a contractual commitment.

// The bug, in one line: an instant cannot answer "what time did the user mean?"
// stored: 2026-03-28T08:00:00Z  ->  after the transition this is 09:00 local, not 08:00

// The six-week fix - store the intent, derive the instant.
// Recurrence expansion, using Temporal where available:
const zoned = Temporal.PlainDateTime
  .from('2026-03-29T08:00')                  // what the user meant
  .toZonedDateTime('Europe/Berlin');          // resolved against that day's rules

// Same idea without Temporal, for the environments that lag:

EXAMPLE — replace with your own

Finance reported that a monthly settlement report disagreed with the ledger by €0.02 on a total of about €4.1 million. Two cents. The instinct in the room was to write it off as a rounding artifact, and I have some sympathy for that instinct — until you ask the question that actually matters, which is not "is two cents material" but "do we know why". An unexplained discrepancy of two cents and an unexplained discrepancy of two million have exactly the same root-cause profile; only the luck differs.

It took a day and it was IEEE-754. JavaScript numbers are double-precision binary floats: 53 bits of significand, and decimal fractions like 0.1 and 0.07 have no exact binary representation. Individually the error is around 10−17 and invisible. Our report summed roughly 240,000 line items in a plain reduce, and floating-point addition is not associative — each partial sum is rounded, and the rounding errors accumulate in a way that depends on the order of the terms. The ledger totalled the same amounts grouped by account and then summed the groups. Different order, different accumulated error, two cents apart. Neither number was "right"; both were approximations that had drifted differently.

// The demonstration that ended the debate about whether this mattered
0.1 + 0.2 === 0.3            // false  -> 0.30000000000000004
Number.MAX_SAFE_INTEGER      // 9007199254740991 - integers are exact only below this

// What we shipped: integer minor units everywhere money is stored or summed.

// For the aggregates we could not convert immediately (ES2026, and in Node 24+):

// And for identifiers that are big integers, the parse is the dangerous step:
JSON.parse('{"id": 9007199254740993}').id;   // 9007199254740992  <- silently wrong

What we changed. Money is stored and summed as integer minor units — cents as a plain integer, which is exact up to about 90 trillion, far beyond anything we handle — and converted to a decimal string only for display. Where an aggregate genuinely had to stay in floating point during a transition, we used Math.sumPrecise, which is part of ES2026 and gives a correctly rounded sum independent of term order; that closed the drift without a schema change while the real fix landed. And we added an invariant test on the settlement job asserting that the sum of parts equals the whole exactly, which is the control I care most about, because it converts "someone in finance notices" into "the job fails".

The nastier discovery came from pulling the thread. A partner integration sent transaction identifiers as JSON numbers, and some of them exceeded Number.MAX_SAFE_INTEGER. JSON.parse silently produced the nearest representable double, so a handful of identifiers were quietly wrong — and unlike the two cents, that is a data-integrity bug with no self-evident symptom. We fixed it by parsing those fields from the raw source text, which ES2026's JSON parse source access makes a supported operation rather than a regex hack, and by getting the partner to send identifiers as strings, which is what they should always have been.

What I'd do differently: I would have escalated the "it's only two cents" conversation faster. I spent half a day building a case that a two-cent discrepancy was worth investigating, when the sentence "we do not know why these numbers differ, and that is the problem" would have done it in one meeting. And we should have found the identifier truncation before the two cents did — a contract test on the partner payload with a value above 253 is a five-minute test that nobody wrote.

(d) Follow-up drill chain

Why did the two totals differ if both used the same numbers?

Because floating-point addition is not associative. Each addition rounds its result to the nearest representable double, so the error introduced depends on the magnitude of the running total when each term is added. Summing 240,000 items in insertion order and summing them grouped by account produce different intermediate magnitudes, hence different accumulated rounding, hence different totals. Neither is the true value; both are approximations of it. That is also why "just round the final result to two decimals" does not fix it — the error is already larger than a cent by the time you round.

Why integer minor units rather than a decimal library?

Because it is exact, free, and has no dependency or performance cost, and a JavaScript number holds integers exactly up to 253, which is about 90 trillion cents — comfortably beyond anything we settle. A decimal library is the right answer when you need genuine decimal arithmetic with defined rounding: multi-currency conversion, interest, tax with regulated rounding rules, or sub-minor-unit precision. It brings a dependency, a conversion at every boundary, and a discipline problem — one place that unwraps to a number reintroduces the bug. Start with integers; adopt decimals when the domain actually demands them.

At what scale does Math.sumPrecise stop being enough?

It solves summation exactly — correctly rounded regardless of order and count — so as a fix for aggregate drift it does not really run out. What it does not solve is everything else: multiplication for tax, division for splits, and the fact that each individual value is already an inexact binary approximation of a decimal amount. So it is the right tool for "our totals disagree" and the wrong tool for "our money model is float". We used it as a bridge while the representation change rolled out, and I would be uneasy leaving it as the permanent answer, because it makes an incorrect representation produce correct-looking numbers.

How would you find the identifier truncation on a system you had just joined?

Look for JSON numbers larger than 253 at every ingestion point — a scan of raw payloads, not of parsed objects, because by the time it is parsed the evidence is gone. Then check every place an id crosses a language or storage boundary, since 64-bit integer ids from another system are the usual source. The structural fix is to insist identifiers are strings on the wire; the detection fix is a contract test with a value above the safe range, which fails immediately on any consumer that parses it as a number. ES2026's JSON parse source access makes reading the original text a supported operation, which is what we used until the partner changed the schema.

How do you argue for time on a two-cent bug?

Not on the amount — on the ignorance. The sentence that works is "we cannot explain why two systems that should agree do not, and until we can, we do not know the bound on the error." Two cents and two hundred thousand euros come from the same class of defect; we observed the cheap instance. I would also point at what an unexplained reconciliation gap does to an audit, which converts an engineering curiosity into a compliance question and finds budget that engineering arguments cannot. That framing took one meeting; my first framing, which was about correctness, took half a day and did not land.

You have to decide whether the data is a log or a state, and dashboards are almost always state. Sending every event and letting the client buffer is how a dashboard tab ends up using a gigabyte of memory after an afternoon. The general principle: for state, drop and coalesce; for a log or an audit trail, you need real backpressure and a durable cursor, and SSE is the wrong transport for that.

Around the point where the number of concurrent streams times the update rate exceeds what one process can serialise — for us, a few thousand connections per pod, since each one needs its own serialised payload. Our ceiling was about 400 concurrent users, so none of that was worth building, and I said so explicitly in the design rather than leaving it as an implied assumption.

By making it small enough to stay true — one page, three numbers, three named owners — and by treating a change to it as the change-control mechanism rather than an update after the fact. Both mid-build changes went through it, which meant it stayed current, which meant people kept referring to it. Long specification documents rot because updating them is expensive; a one-page target sheet survives because it is cheaper to change than to work around. Our code did session.user.id, TypeScript was perfectly happy, and roughly one login in four thousand — the ones where a token refresh raced a logout — threw a TypeError at the top of a request handler.

The technical point worth understanding is that a hand-written declaration file is an assertion, not a derivation. TypeScript trusts .d.ts completely; there is no check that the declaration matches the JavaScript it describes. And skipLibCheck: true, which almost everyone enables because it speeds up compilation, means the compiler will not even check declaration files for internal consistency. So a wrong .d.ts is worse than no types at all: with no types you write defensive code, with wrong types you write confident code that is wrong. We had been given a confident wrongness and had built on it.

// What the SDK declared - an assertion nothing verifies
declare function getSession(): Session;

// What it actually returned since a change 18 months earlier
// Session | null

// Our defence while the platform team fixed it upstream:
// narrow the lie locally rather than sprinkle optional chaining everywhere.
import { getSession as unsafeGetSession } from '@org/auth';

export function getSession(): Session | null {
  return unsafeGetSession() as Session | null;   // one cast, in one file, with a comment
}

The interesting part was not the fix, which took an afternoon, but getting it fixed at the source when I had no authority over the platform team and they had a full roadmap. What worked was making the problem theirs in a way that was useful rather than accusatory. I wrote a consumer-driven contract test suite — about forty assertions describing what our team actually relied on, executed against the real SDK, checking runtime behaviour rather than types — and I sent it to them as a gift: "here is a test suite you can run in your CI that tells you when you break us." Then I found two other teams with similar breakage, and their assertions went in too. What had been one team complaining became a shared artifact that made the platform team's job easier, and they adopted it within a month.

The durable fix was that the SDK stopped hand-writing declarations and started emitting them from TypeScript source, which makes the declaration a derivation rather than an assertion and removes the whole class. That was a quarter of work on their side and I did not ask for it in the first conversation — I asked for the contract tests, and the contract tests made the case for the rewrite far better than I could have. What I'd do differently: my first message to them was a bug report with a slightly sharp tone, written at the end of an incident, and it cost me a week of cold responses. I have a rule now about not sending cross-team messages within an hour of an incident.

A cast that widens confidence is dangerous; one that removes it is defensive. It also gave us one place to delete when upstream was fixed, rather than optional chaining scattered across forty call sites, which would have been permanent. Containment in a single seam is the pattern; the cast is just how it was expressed.

Then the wrapper stays, the contract tests run in our CI against each new SDK version, and I escalate with data rather than with frustration — three teams, a measured failure rate, the cost in support load. I would also stop expecting the declarations to be true and treat the SDK as an untyped boundary, which is a real cost but an honest one. What I would not do is fork it: a fork of a security-relevant SDK is a much larger commitment than it looks on the day you make it, and I have watched a team do that and regret it for two years.

How would you prevent this class of problem in a new organisation?

One rule and one habit. The rule: no hand-written declaration files for internal packages — either the package is written in TypeScript and emits its own, or it is treated as untyped and wrapped at a boundary. The habit: every cross-team dependency has a small consumer-driven contract test suite that the provider runs, because the provider cannot otherwise know what consumers actually depend on. Both are cheap at the start of a package's life and expensive to retrofit, which is exactly the kind of thing a staff engineer should be spending influence on early.

I instrumented every pipeline stage and found that a typical pull request spent 51 minutes of billed compute in typescript-related work, split across 60 packages, and that 44 of those minutes were re-checking packages the pull request had not touched. Every job started from a cold cache, every job ran tsc over the whole world, and this had been true since the monorepo was created — nobody had built it that way deliberately, it had simply never been revisited after the repo grew from four packages to sixty.

// Project references: the compiler learns the dependency graph, so it can
// check what changed and skip what did not - and emit declarations in parallel.

    "composite": true,               // required for references; emits .d.ts + .tsbuildinfo
    "incremental": true,
    "isolatedDeclarations": true,    // declarations from each file alone -> parallelisable
    "skipLibCheck": true
  },
  "references": [
    { "path": "../core" },
    { "path": "../http" }
  ]
}

Four changes, in the order I made them, which is also the order of value per unit of effort. First, project references with composite: true and a persisted .tsbuildinfo cache keyed on the lockfile and source hashes: tsc --build then checks only what actually changed and its dependents. Third, isolatedDeclarations, which forces explicit return types on exported functions so declaration emit does not need to infer across files — annoying for a fortnight, and it makes emit parallelisable. Fourth, and last because I wanted the structural work done first, the TypeScript 7 native compiler, which took the full cold check from 12 minutes to 96 seconds.

The result was the CI bill at about $7,400 a month against a projection of $23,000, so roughly $15,600 a month against the trajectory. That is 50 minutes per pull request, at about 40 pull requests a day, which is a much larger number in engineer-hours than the money — and it is the number that made people care. The finance question got the project funded; the developer-experience number got it adopted, because teams cooperated with the migration to project references instead of treating it as someone else's tax.

What I'd do differently: I would have done the cheap wins first and communicated them immediately, rather than doing three weeks of measurement and arriving with a complete plan. Why did project references help so much more than throwing hardware at it?

Because the work itself was redundant, and a bigger machine does redundant work faster while paying for it. Without references, tsc has no model of package boundaries, so a one-line change means re-checking all sixty packages; with composite: true the compiler knows the graph, persists per-project state in .tsbuildinfo, and rebuilds only what changed and what depends on it. Rolldown is also young relative to webpack; 1.0 in May 2026 means its edge cases are less explored, and I would weigh that more heavily for a build with unusual requirements than for a conventional application.

How did you decide on require.context?

By treating it as a design question rather than a translation problem. require.context is a webpack-specific runtime API; import.meta.glob is a build-time construct that produces static imports, which is why it code-splits and tree-shakes properly. So the port was also an improvement — our route registration became statically analysable, and we found two route files that had been in the directory for a year and were never reachable. The wider point: when migrating, some things translate and some things want rethinking, and taking the mechanical translation every time is how you carry a previous tool's assumptions into the new one forever.

At what point would you not have recommended this?

If the app had a heavy investment in webpack-only plugins we could not port in the spike window, or if the team had been mid-crunch with no capacity for a parallel-run period — a migration that people cannot opt into is a migration that becomes an incident. I would also have hesitated if the tooling depended on the TypeScript compiler's programmatic API in a way that constrained versions, since 7.0 does not expose a stable one until 7.1. None of those applied. Having a written "conditions under which I would say no" is also what made the two-week spike honest rather than a foregone conclusion.

How do you avoid this becoming another 1,400-line config in three years?

The config grew because every requirement was solved inside it, and nothing was ever removed. Two habits push back: every config addition needs a comment explaining what breaks without it — which sounds trivial and is the single best predictor of whether it can be deleted later — and an annual read-through where anything nobody can justify gets removed behind a flag for a sprint. I would also resist per-app divergence: our 1,400 lines included roughly 300 that existed because two apps had drifted apart for no remaining reason. Tools do not create config sprawl; the absence of a deletion habit does.

18On-call: the rejection that killed the fleet

EXAMPLE — replace with your own

03:40 on a Tuesday, paged for a service with zero healthy instances. Every pod was in a crash loop: start, serve for 20 to 90 seconds, exit, restart. Because they were restarting rather than hanging, the platform's own health checks kept declaring them unhealthy and killing them faster, and the whole fleet was down while looking, on the dashboard, like it was constantly recovering.

The exit was an unhandled promise rejection. Since Node 15 the default for an unhandled rejection is to throw and terminate the process — which is the right default, because the alternative is a process running with a silently failed operation — and it means one missing .catch() on a background task is a fatal error. Ours was in a cache-warming routine kicked off at startup with a fire-and-forget call. It had been there for a year. That night a downstream service started returning 503s, the warming call rejected, nothing was awaiting it, and every pod in the fleet died within ninety seconds of starting, forever, because the failure was in the startup path.

// The bug: fire-and-forget with no rejection handler.
warmCache();                       // returns a promise nobody owns -> fatal on reject

// Mitigation at 03:52: make the failure explicit and non-fatal, and say so loudly.
warmCache().catch((err) => {
  log.error({ err }, 'cache warm failed; serving cold');   // degraded, not dead
  metrics.increment('cache.warm.failed');
});

// The guard that catches the next one, wherever it is.
process.on('unhandledRejection', (reason) => {
  log.fatal({ reason }, 'unhandled rejection');   // log BEFORE exiting - the default
  process.exit(1);                                // is to die without telling you why
});

Timeline, because an incident story without one is not an incident story. Paged 03:40. Confirmed all instances down and declared an incident at 03:44. Tried a rollback first — right instinct, wrong answer here, since the last deploy was four days old and the trigger was external, so it changed nothing and cost four minutes. At 03:51 I got a full stack trace by catching one pod's logs in the window before the platform reaped it, which pointed straight at the warming routine. Mitigated at 03:55 by setting an environment variable that skipped cache warming — a switch that existed only because someone had added it for local development eighteen months earlier, and which I want to be honest about: I got lucky. Fleet healthy at 03:58, 18 minutes total. The real fix, a .catch() and a startup path that cannot take the process down, shipped at 09:30.

A repository-wide audit for floating promises, using the linter rule for it, which found 23 more — four of them in startup paths and therefore capable of exactly the same fleet-wide failure. (d) Follow-up drill chain

Should an unhandled rejection really kill the process?

Yes, and I would not change it. The alternative — Node's pre-15 behaviour of warning and continuing — leaves a process running after an operation has failed in a way nobody observed, so you get silent data loss and corrupted state instead of a crash, which is far harder to detect and much worse to clean up. Crashing is loud, safe and recoverable. What that default demands is that you never create a promise nobody owns: every asynchronous operation is either awaited by someone who handles its failure, or explicitly backgrounded with a handler. The default is not the bug; the floating promise is.

Why did the whole fleet go down at once rather than a few instances?

Because the failure was in the startup path and the trigger was shared. Every pod runs the same warming call on boot, and the downstream 503s hit all of them, so every restart re-entered the same failure — a correlated failure with no jitter and no partial survivors. That is the structural lesson: work in the startup path is fleet-correlated by construction, so anything there needs a much higher bar than the same code in a request handler. It is also why the crash loop accelerated: the platform restarted pods faster than they could become ready, which added load to the already-struggling downstream service.

Would a linter rule have caught it?

Yes — the no-floating-promises rule catches exactly this shape, and it was not enabled because it requires type information and someone had turned off the type-aware rules years earlier to speed up linting. That is a genuinely annoying root cause: a performance optimisation on the linter, made by someone reasonable, removed the check that would have prevented a fleet-wide outage. We turned it back on during the audit, which is how we found the other 23. It also became an argument in the CI work — faster type-checking meant type-aware linting was affordable again, which is a connection I would not have predicted.

How would you make the startup path safe in general?

Decide, per piece of startup work, whether it is required or optional, and encode that decision. Required work is awaited before the readiness probe passes, and failing it should fail the pod — that is correct, because a pod without its required state should not receive traffic. Optional work is started explicitly in the background with a handler, a timeout, and a metric, and its failure degrades the service rather than killing it. What you must not have is the third case we had: optional work that behaves like required work because nobody decided. I would also add a startup timeout so a hanging dependency does not produce pods that never become ready.

You mitigated with a flag that happened to exist. What if it had not?

Then the next options, in order: ship the one-line .catch() as an emergency deploy, which is maybe fifteen minutes through our pipeline; or scale the downstream dependency or fail its calls open so the warming stops rejecting; or, as a last resort, start pods with the warming module stubbed via an override. All of those are slower than a flag, so the outage would have been 30 to 45 minutes rather than 18. The lesson I took is not "get lucky more" — it is that expensive optional startup work deserves a documented kill switch on purpose, which is now part of our service checklist.

19Making a flaky async test suite honest

senior → staff CI / test reliability improvement

EXAMPLE — replace with your own

A suite of 4,300 tests with a 31% chance that any given run failed for no reason. The team's coping mechanism was a "retry failed jobs" button, pressed several times a day, and a shared understanding that a red build meant "run it again" rather than "you broke something". That last part is the real damage: a suite nobody believes provides no signal at all, so the 12% of failures that were genuine were also being retried away.

I started by measuring rather than fixing, because "the tests are flaky" is not actionable. Two weeks of collecting every failure with its test name, error, and timing gave a distribution that was much more concentrated than anyone expected: 4,300 tests, and 60% of all flakes came from 31 of them. That number is why the project was tractable — the team's belief was that the whole suite was rotten, and the data said we needed to fix thirty-one tests.

The causes clustered into four kinds, and three of the four were the same underlying misunderstanding of JavaScript's asynchrony. Sixty percent were timing assumptions: setTimeout(done, 50) waiting for something to "settle", which passes on a fast machine and fails on a loaded CI runner. Twenty percent were shared state between tests — a module-level cache, a stubbed global that one test forgot to restore — surfacing only when the runner's parallelism happened to order things badly. Fifteen percent were unawaited promises inside tests: the assertion ran, the test passed, and the rejection landed during a later test and failed that one, which is why the failures looked random and unrelated to the code being changed. The last five percent were genuine race conditions in the product code, and those were the valuable ones — the flaky test was correctly reporting a real bug that would occur in production.

// Flaky: a sleep is a guess about someone else's scheduling.
it('updates the cache', async () => {
  triggerRefresh();
  await new Promise((r) => setTimeout(r, 50));  // hope
  expect(cache.get('k')).toBe('v');
});

// Deterministic: wait for the event you actually mean.
it('updates the cache', async () => {
  const done = once(cache, 'refreshed');        // subscribe BEFORE triggering
  triggerRefresh();
  await done;
  expect(cache.get('k')).toBe('v');
});

// The microtask/macrotask distinction that explains most "await once more" fixes:
Promise.resolve().then(() => console.log('microtask'));  // drains before...
setTimeout(() => console.log('macrotask'), 0);           // ...the next macrotask
// A single `await` flushes ONE microtask checkpoint, not the whole timer queue.

The fixes, in order of value. Replacing every sleep with an explicit signal — an event, a promise the code under test exposes, or fake timers with an advanced clock — which is more work than it sounds because it often means the code under test has no way to say "I am done", and adding one improves the design. Enforcing test isolation by making the runner fail on leaked global state and giving each test its own module registry. Enabling the linter rule for unawaited promises inside tests. And for the five percent that were real races, fixing the product code, which found two bugs that were also happening in production at low rates.

We went from 31% run failure to 0.4% over ten weeks, and I banned the retry button — a decision that was unpopular for about a fortnight and was the single most important part, because as long as retry is available nobody has to care. Suite time also dropped from 19 to 7 minutes, which was a side effect: most of the sleeps were 50 to 500 ms and there were hundreds of them.

What I'd do differently: I would have published the "31 tests cause 60% of flakes" chart in week one instead of week three. The team's morale problem was that the suite felt unfixable, and that one chart changed the problem from a swamp into a list. I had the data on day four and spent two weeks building a complete plan before showing anyone.

(d) Follow-up drill chain

Why does an unawaited promise inside a test fail a different test?

Because the test function returns before the promise settles, so the runner marks it passed and moves on. When the rejection lands, the runner is executing a later test, and whichever handler catches it — the runner's unhandled-rejection hook or the current test's context — attributes it there. That is why the failures look random and uncorrelated with the change: the test that fails is chosen by timing, not by cause. It is the single most confusing flake shape, and it is fully preventable with the type-aware no-floating-promises rule, which is why I rate that rule so highly.

Why not just quarantine the flaky tests?

Because quarantine is a permanent state that looks temporary, and because in our data five percent of the flakes were real production races — quarantining them would have deleted the only evidence we had of two live bugs. I do use quarantine, but with rules: a quarantined test has an owner and a date, the quarantine list is visible and shrinking, and a test quarantined twice gets deleted rather than ignored, because a test nobody will fix is worse than no test. The failure mode I have seen is a quarantine list of 200 tests that nobody has looked at in two years, which is the same as deleting them but with maintenance cost.

How did you handle the pushback on removing the retry button?

I did not remove it on day one. It came out after the 31 worst tests were fixed and the failure rate was already down to about 6%, so what people experienced was mostly not the pain they feared — sequencing was the whole trick. I also committed publicly that I would personally fix any flake reported in the following month, which cost me about six days and removed the legitimate objection that people would be stuck. And I kept an override for a genuine infrastructure outage, requiring a written reason, because a rule with no escape hatch gets routed around rather than followed.

At what scale do these techniques stop working?

The per-test fixes scale fine; what stops scaling is the human attention. At 4,300 tests I could look at 31 problems personally. At 100,000 tests across many teams, you need the infrastructure to do it: automatic flake detection from historical runs, automatic attribution to the owning team, a dashboard per team, and a policy with teeth. The failure at that scale is not technical but ownership — a shared suite with no per-test owner will rot regardless of how good the individual fixes are, and I would spend my effort on the attribution pipeline before the fixes.

What is your position on fake timers?

Excellent for testing time-dependent logic, dangerous as a way to make a test pass. Use them when time is the subject — a debounce, a retry backoff, a scheduler, a cache TTL — because they make the test deterministic and instant, and you control the clock explicitly. Do not use them to paper over a missing completion signal, because you end up mocking the scheduler to hide the fact that the code cannot tell you when it is done, and the test then passes for reasons unrelated to correctness. The tell is a test that advances timers by an arbitrary amount until things happen to work; if you cannot say why that number, you have moved the guess rather than removed it.

I want to be clear that the goal was right. Isn't checkJs a half-measure that leaves you with two systems?

By defect data, not by architecture opinion. It removes the build-step objection, which used to be a real part of the cost — type stripping is stable in Node 26 and node app.ts runs without flags, so adopting TypeScript in a service no longer means adopting a bundler or a compile step. It does argue for erasableSyntaxOnly from day one, so you avoid enums, parameter properties and namespaces — the constructs that need real emit rather than erasure — and keep the option of running your source directly.

I would also have asked for the one thing I most wanted, which is the definition of done — because a mandate with a quality bar is survivable even at a bad deadline, and one without a quality bar produces 340,000 lines of files that end in .ts and change nothing. If I could win only one point, that was the one.

Deploy: 14 (the drifted .d.ts and the contract-test suite you gave away). They want: the artifact you built that changed their economics, and evidence you understood their constraints. "I escalated to their manager" is a weak answer; "I wrote the test suite they needed and found two other teams with the same problem" is a strong one. Be generous about the other team, always.

Tell me about pushing back on a manager or executive.

Deploy: 20 (the "TypeScript everywhere" mandate). They want: that you separated the goal from the plan, brought data, and asked what the mandate needed to achieve. Include the relationship cost of disagreeing publicly in his third week — that reflection is what distinguishes a principal answer from a merely confident one.

Tell me about receiving difficult feedback.

Deploy: 15 (your director asking whether you would have raised it if the migration had gone slightly better). They want: that you heard the actual criticism rather than a softer version of it, and that you changed something concrete. The strong answer restates the feedback in its sharpest form before answering it — that alone signals you did not flinch.

Tell me about a time you were the blocker.

Deploy: 05 if you slowed a change down, or 11 if you held a line on a data model under deadline pressure. They want: whether you can tell the difference between principled and obstructive, and whether you know the cost of your own carefulness. Name what your caution cost in weeks, and say whether you would do it again — the honest answer is sometimes no.

Leadership & mentoring

Tell me about developing someone.

Deploy: 10 (the type-golf mentee). They want: a capability they gained, evidence you can point at, and an experience you designed rather than advice you delivered. Mentioning that she began giving the same feedback to others is the strongest evidence available, because it shows the idea propagated past you.

How do you raise the technical bar of a team?

Deploy: 19 (removing the retry button) plus 05 (the one-way strictness ratchet). They want: mechanisms over exhortation. The pattern to articulate: make the good path easy, make regression impossible rather than discouraged, and sequence so people feel the benefit before they feel the constraint. Two mechanisms explained well beat six listed.

Tell me about a time you had to deliver bad news.

Deploy: 15 (recommending cancellation of your own project). They want: that you brought recalculated evidence and an alternative in the same conversation, and that you told the team properly. Own the ordering mistake — telling your director a day before the team — because it is exactly the kind of detail that makes the rest believable.

How do you decide what your team works on when everything is urgent?

Deploy: 20 (defect data choosing 25,000 lines out of 340,000) or 16 (value-per-effort ordering in the CI work). They want: a repeatable method, not a story about working hard. Say the method in one sentence — "effort follows change rate and defect density" — then show the story where you applied it and what you consciously did not do.

Tell me about setting technical direction others followed.

Deploy: 02 (generation plus a runtime boundary) or 04 (the two-hop TypeScript plan). They want: that the direction outlived your attention. The evidence is other teams adopting it without you in the room, and a written decision people could find six months later. If you never wrote it down, say that as your "differently".

Ambiguity & prioritisation

Tell me about an ambiguous problem you were handed.

Deploy: 13 (the "real-time" dashboard). They want: that your first deliverable was a definition, not code, and that you went and watched people work. The detail that three groups meant three different things — and that one of them belonged to another system — is what makes this more than a requirements-gathering anecdote.

Tell me about negotiating scope under a hard deadline.

Deploy: 11 (the Temporal migration split in two). They want: that you negotiated scope rather than estimates, and that the interim work fed the eventual work rather than becoming debt. Say what you refused to trade and why, and be honest about whether the follow-up quarter actually happened.

How do you make a decision without enough information?

Deploy: 02 (a two-week spike that answered one question) or 07 (build the realistic load rig before optimising anything). They want: that you can name the one piece of information that would change the decision, and design the cheapest experiment that produces it. Reversibility is the other axis worth naming: cheap-to-reverse decisions deserve less evidence.

Tell me about something you decided not to do.

Deploy: 07 (declining the schema-compiled serialiser) or 20 (converting nothing in decommissioning code). They want: restraint with a stated threshold for revisiting. "We didn't need it" is weak; "we didn't need it, and I'd revisit at 100k rps or if serialisation showed up in a profile" is a senior answer.

Craft & judgment in JavaScript and TypeScript

What is your position on how much typing is the right amount?

Deploy: 10 (type golf) plus 20 (checkJs as a gradient). They want: a position with a boundary, not a preference. Mine: strictness is nearly free and worth having everywhere; type-level computation is a library-boundary tool because it costs compile time, error quality and reviewability. Name the three tests — behind a boundary, improves the call site, still produces a decent error message.

How do you keep up with a fast-moving ecosystem?

Deploy: 17 (Vite 8 as a two-week evidence exercise) or 09 (require(esm) removing a constraint that justified an old practice). They want: a filter, not a firehose. The most useful thing to say is that a lot of JavaScript best practice is a workaround for a constraint that has since been removed, and nobody sends a notification — so you periodically re-examine your defaults, and you adopt via time-boxed spikes with honest negative reporting rather than enthusiasm.

Values & motivation

What kind of work do you want to be doing in three years, and why should we believe you?

Deploy: whichever two stories genuinely show what you enjoy — for most lead-level engineers that is 02 or 04 (direction that outlived them) and 10 (someone who levelled up). They want: consistency between what you say you want and what you actually chose to spend time on. The evidence is in the stories you reached for first, so make sure your favourite stories point in the direction of the job you are interviewing for. If they do not, that is worth knowing before the interview rather than during it.

22Night-before cheat sheet

mid → principal delivery

Ten sentences to read the night before, and one thing to do afterwards.

  1. Lead with the situation in one line, then stop. "A pricing API where p99 went from 90 ms to 1.8 seconds over three weeks, and everyone including me was sure it was the database." One sentence, with a number and a tension in it, buys you the next three minutes.
  2. Quantify the result, always, and give it a denominator. "p99 to 74 ms" beats "much faster"; "51 minutes of CI to 12, on 40 pull requests a day" beats "we saved 60%". If you genuinely have no number, say what you have instead — a bug class that has not recurred in a year is a number too.
  3. Say "I" for what you did and "we" for what the team did, and never blur the line. Interviewers probe ownership by asking what you specifically wrote or decided. If your story falls apart under that question, it was the wrong story.
  4. Own the "what I'd do differently" before they ask for it. Make it a decision you would make differently, not a circumstance you regret. "I should have instrumented the event loop on day one" is a reflection; "we should have had better monitoring" is a complaint.
  5. Explain the mechanism, not the tool. "Floating-point addition is not associative, so a different summation order accumulates different rounding" is the answer. "We used a decimal library" is not. The mechanism is what makes the story transferable and what makes you sound like you understood it rather than fixed it.
  6. Name the trade-off out loud, unprompted. Every good decision cost something: a worse API, rejected requests, a pinned old version, annotations forever. Volunteering the cost is the fastest way to sound senior, and it pre-empts the follow-up that would otherwise catch you.
  7. Be current, and be specific about it, once. One well-placed contemporary fact — TypeScript 7's native compiler and its missing programmatic API until 7.1, Temporal in ES2026 with Safari still behind, type stripping stable in Node 26, Vite 8 unifying dev and prod on Rolldown — signals that you work with the ecosystem rather than remember it. Once is calibration; three times is a lecture.
  8. Be modern-first and legacy-aware in the same breath. "Today I'd ship one ESM build and let require(esm) cover CommonJS consumers; the dual build was right in 2021 and is a liability now." Interviewers reward people who can navigate the codebase they actually have.
  9. Answer follow-ups by returning to the mechanism, not by adding detail. "At what scale does this break?" is a question about the constraint, so answer with the constraint — connection counts, fan-out amplification, reviewer attention, coordination cost — and then the number where it bites.
  10. Keep every worked example yours. The examples on this page are fiction and are labelled as such; the only story you can survive four drill-downs on is one you lived. If you have no story for an archetype, say so and offer the nearest real thing — that is a far better outcome than an invented one that collapses on the second question.

The one thing to do after reading this. Take the coverage table at the top, pick the four archetypes where you have nothing, and write one paragraph each about the nearest real experience you do have — even if it is imperfect. Four paragraphs is about forty minutes and it is worth more than re-reading twenty stories, because the failure mode in a behavioural interview is not delivering a story badly, it is not having one.
