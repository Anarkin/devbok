01The Monday-morning refresh storm

Senior Performance problem diagnosed

Worked example EXAMPLE — replace with your own

Every Monday between 09:02 and 09:11 our sign-in endpoint's P95 latency went from 80ms to somewhere north of 4 seconds, and roughly 1-in-6 users landed on an interactive re-login screen instead of a silent one. It never happened on any other day. I pulled a week of Application Insights dependency data and lined up the timestamps of failed acquireTokenSilent calls against token iat claims from the previous Friday — they clustered almost exactly 72 hours apart. Our SPA registration was a public client, and Entra ID caps refresh token lifetime for that client type at 24 hours regardless of activity; MSAL.js was supposed to renew silently via a hidden iframe before that, but renewal only fires while the tab is open and focused, and nobody's laptop is open at 6pm Friday. So every session that had been idle since Friday afternoon expired at almost the same moment on Monday morning, and every one of those users hit the token endpoint within the same nine-minute window when they opened their laptops.

The fix had two parts. Short term: stop scheduling renewal purely on a fixed timer and instead renew opportunistically on tab focus and network reconnect, with a random 0-90s jitter so five thousand laptops opening in the same nine minutes didn't all call the token endpoint in the same seven seconds. Longer term — the real fix, which shipped a quarter later — was moving session state behind a BFF (see story 04) so the browser held an opaque cookie instead of a token with a hard 24h ceiling, and the refresh happened server-side on a schedule we controlled.

// before: fixed-interval silent renewal, no jitter — everyone fires together
setInterval(() => msalInstance.acquireTokenSilent(request), 15 * 60 * 1000);

// after: renew on focus/reconnect, with jitter, and a floor so we don't spam
let lastAttempt = 0;
async function renewIfNeeded() {
  const now = Date.now();
  if (now - lastAttempt < 60_000) return;          // don't hammer on rapid focus events
  lastAttempt = now;
  const jitterMs = Math.random() * 90_000;         // spread the herd across 90s
  await new Promise(r => setTimeout(r, jitterMs));
  await msalInstance.acquireTokenSilent(request).catch(() => promptInteractive());
}
window.addEventListener('focus', renewIfNeeded);
window.addEventListener('online', renewIfNeeded);

Drill chain

Why does Entra ID give public clients (SPAs, mobile apps) shorter refresh token lifetimes than confidential clients?

A public client can't hold a secret — anyone can read its client ID out of the compiled bundle — so there's no way to prove the token request is coming from a trusted server process. Shortening the refresh token's blast radius limits how long a stolen token is useful if it leaks from browser storage or a compromised device. Confidential clients authenticate with a secret or certificate on every token request, so a stolen refresh token alone isn't enough to mint new access tokens, and Entra can afford to let those live longer — up to 90 days by default.

Why did the failures cluster instead of spreading evenly through the day?

Tokens were being renewed on a fixed wall-clock timer while the tab was open, so a token issued Friday afternoon and never refreshed over a closed-laptop weekend expired at almost the exact same offset for everyone who logged in around the same time Friday. When people opened laptops Monday morning in a tight nine-minute band, every one of those expired sessions hit the token endpoint in that same window — it's a thundering herd caused by synchronized token issuance, not synchronized user behavior.

Why is jitter alone not a complete fix?

Jitter smooths the arrival curve so the token endpoint doesn't see a spike, but it doesn't change the underlying fact that every session still has a hard 24-hour ceiling and still depends on the browser tab being open and focused to renew. Any week where unusually many people are off on a Friday and back en masse Monday can still produce a smaller version of the same herd. It's a mitigation, not a fix for the root constraint.

How does moving to a BFF change this specific failure mode?

In a BFF, the browser never holds the token with the 24h public-client ceiling — it holds an httpOnly session cookie, and the server-side session refreshes tokens against Entra as a confidential client on its own schedule, independent of whether any particular browser tab is open. The synchronized-idle-expiry pattern disappears because renewal isn't gated on client-side wall-clock timers or tab focus at all.

What would you monitor going forward to catch this class of problem earlier?

A percentile latency metric on the token endpoint sliced by time-of-day and day-of-week, plus a count of interactive-fallback events versus silent-renewal successes. Either one trending against day-of-week seasonality, rather than absolute thresholds, would have surfaced this pattern in the first affected week instead of the fourth.

02The alg nobody pinned

Senior Security issue found and fixed

Worked example EXAMPLE — replace with your own

During a routine dependency-audit pass ahead of a SOC 2 renewal, I was reviewing every service's JWT validation setup and found one internal API that constructed its own TokenValidationParameters instead of using the shared library the rest of the org had standardized on two years earlier. It set IssuerSigningKey to the tenant's RSA public key correctly, but it never set ValidAlgorithms. Microsoft.IdentityModel doesn't refuse an HMAC-signed token just because you handed it an RSA public key for validation — if the key material can also be interpreted as bytes for an HMAC, and the token's header claims alg: HS256, some validation paths will happily try to verify the HMAC signature using the RSA public key's bytes as the shared secret. Since our JWKS endpoint published that public key openly, anyone could compute a valid HS256 signature over an arbitrary payload using bytes we ourselves were broadcasting, and forge a token that service would accept as genuinely signed by our IdP.

I built a proof-of-concept against a sandboxed copy of the service — not production — that minted an HS256 token claiming an admin role, using nothing but the tenant's published JWKS, and confirmed the endpoint accepted it. I filed it as a critical finding same day, and we shut off the code path within a few hours by pinning ValidAlgorithms to exactly ["RS256"] everywhere, then wrote a static-analysis rule that fails CI on any TokenValidationParameters construction missing an explicit algorithm allow-list.

// vulnerable: no algorithm pin — alg-confusion window is open
var tvp = new TokenValidationParameters {
    IssuerSigningKey = rsaSecurityKey,
    ValidIssuer = issuer,
    ValidAudience = audience
};

// fixed: only the algorithm we actually issue is ever accepted
var tvp = new TokenValidationParameters {
    IssuerSigningKey = rsaSecurityKey,
    ValidAlgorithms = new[] { SecurityAlgorithms.RsaSha256 },
    ValidIssuer = issuer,
    ValidAudience = audience
};

What the interviewer is really probing: whether you understand JWT validation as a set of independent checks that must all be pinned — signature, algorithm, issuer, audience, expiry — rather than a single black-box "is this token valid" call. Alg-confusion is a classic because it's invisible in code review unless you already know to look for the missing allow-list.

Drill chain

Walk me through exactly how the RS256/HS256 confusion attack works.

The server's validation code is handed one key object meant for RS256 (an asymmetric public key) but decides which verification algorithm to run based on the untrusted alg header inside the token itself. If the library allows HMAC verification and the attacker sets alg: HS256, the verifier treats the RSA public key's raw bytes as the shared HMAC secret. Since the public key is, by design, public — published on the JWKS endpoint — the attacker can compute a correct HMAC signature over any payload they want using those same bytes, producing a token the server will accept as authentic.

Why does pinning ValidAlgorithms fully close this, and is any part of it still your responsibility afterward?

Pinning tells the validator to reject any token whose header algorithm isn't on your explicit allow-list, so an attacker's HS256 token is rejected before signature verification is even attempted, regardless of what key material is loaded. It closes this specific attack, but it's still your job to keep the allow-list in sync if you ever legitimately rotate to a new algorithm, and to make sure every service — not just the one you found — enforces it.

Why didn't code review catch this originally?

The vulnerable code looked completely idiomatic — it set an issuer, an audience, and a signing key, which is what most examples show — and the absence of a line is much harder to spot in review than the presence of a wrong one. It also required knowing the specific alg-confusion attack class to know that one more property needed setting; most reviewers were checking for "does this validate what it should," not "does this reject what it shouldn't."

Could this same class of bug show up anywhere other than JWT libraries?

Yes — anywhere a protocol lets the sender declare which algorithm or format the receiver should use to interpret their data, and the receiver trusts that declaration without an allow-list. Deserialization gadgets, content-type sniffing, and some encryption-mode negotiation bugs are the same shape: never let untrusted input pick the security mechanism used to validate itself.

What's the CI rule you added, concretely?

A simple static-analysis check that flags any construction of TokenValidationParameters (or the equivalent in whatever stack a repo uses) that doesn't set an explicit, non-empty algorithm allow-list, failing the build rather than just warning. It's intentionally narrow and pattern-based rather than a general security linter, because narrow rules that fire reliably get fixed, and broad ones that fire noisily get suppressed.

03Retiring ADAL

Staff Migration / version upgrade

Worked example EXAMPLE — replace with your own

We had eleven services still using ADAL (Azure AD Authentication Library) years after Microsoft's stated end-of-support date, because every one of them worked and nobody wanted to touch working auth code. The forcing function was a v1-endpoint deprecation notice from our IdP team with a real shutoff date, which meant "it still works" was about to stop being true all at once, for every service, on the same day. I ran the migration as a staff-level program rather than eleven separate tickets: one reference implementation migrated first (the lowest-traffic service, converted from ADAL's AuthenticationContext to MSAL's IConfidentialClientApplication, with the v1 resource parameter replaced by v2 scope arrays), a migration guide written directly from what broke during that first conversion, then the other ten services split across three engineers over six weeks.

The sharpest edge wasn't the library swap — MSAL's API is a reasonable analog of ADAL's — it was the v1-to-v2 token shape change underneath it. v1 tokens used resource-scoped access tokens and a different claim set; v2 tokens are scope-scoped and, critically, the aud claim format and some optional-claims defaults differ. Two services had downstream token validation that hardcoded assumptions about v1 claim shapes, and those broke silently in staging until we added a full-coverage integration test that decoded and asserted on every claim we depended on, not just "token validates."

Drill chain

Why did Microsoft deprecate ADAL and the v1 endpoint instead of just patching them indefinitely?

The v1 endpoint and ADAL predate a lot of what became core to modern OAuth/OIDC practice — cleaner scope-based consent, the id_token/access_token separation OIDC formalizes, and a claims model that generalizes better across app types including v2's unified personal-and-work-account support. Maintaining two parallel identity stacks indefinitely means every new security capability has to be built twice or only ships to one; retiring the older one is what let Microsoft actually invest in things like Conditional Access and CAE on a single modern surface.

What's the concrete difference between a resource-scoped and a scope-scoped access token request?

A v1 resource parameter names one target API and the resulting token is implicitly scoped to whatever permissions the app was granted against that resource as a whole. A v2 scope parameter is a space-delimited list where each entry names a specific permission on a specific resource, so a single token request can ask for narrower, explicit permissions across multiple resources, and the resulting access token's claims reflect exactly those granted scopes rather than a broader resource-level grant.

Why would a claim shape change silently instead of causing an obvious error?

Token validation in most stacks only asserts on the specific claims your code reads, and it will happily accept a token whose optional claims are absent, renamed, or reshaped as long as issuer, audience, signature and expiry check out. A service that read a claim positionally or assumed a default that v1 always set doesn't get an exception — it gets a null, an empty role list, or a fallback path, and that only surfaces as a functional bug days later, not a validation failure at token-acceptance time.

How would you have caught the claim-shape issue before staging?

A contract test against the actual v2 token shape — decoding a real v2 token from a test tenant and asserting on every claim the service depends on, not just checking that validation returns true — run in the same PR that changed the library. That's exactly the integration test we ended up writing during the migration; doing it as step one instead of a fix-after-the-fact would have caught both instances before they ever reached staging.

If you had to do this again with twenty services instead of eleven, what would you change?

I'd invest more upfront in an automated compatibility check — a script that scans each service's token-handling code for known v1-only assumptions (resource-parameter usage, specific claim names) — so the program starts with a prioritized, evidence-based list instead of "probably fine, we'll find out in migration." At twenty-plus services the cost of building that scanner pays for itself quickly.

04BFF or bust

Staff Hard architectural trade-off

Worked example EXAMPLE — replace with your own

After the Monday-morning refresh storm (story 01) and a separate finding that our SPA's access token, sitting in sessionStorage, was readable by any script that executed on the page, I was asked to make the call on whether to move the SPA to a Backend-for-Frontend pattern — an httpOnly session cookie plus a confidential-client server component holding the actual tokens — or stay token-in-browser and just harden what we had (short token lifetimes, aggressive CSP, subresource integrity). Both were real options with real costs. The BFF closes the XSS-can-steal-the-token risk almost entirely, because a script running on the page never has anything better than a cookie it can't read, only ride along on requests it can already make. But it trades that for a CSRF surface — cookies get sent automatically by the browser on any request to the cookie's domain, so now the BFF has to enforce anti-forgery tokens or strict SameSite correctly, and it adds a server-side session store and an extra network hop for every API call that used to go browser-to-API directly.

I made the call for BFF, but the deciding factor wasn't "BFF is more secure" in the abstract — it was that our specific threat model already had a confirmed XSS finding from a third-party npm package six months earlier, and a working CSRF-mitigation pattern already existed in two other services I could copy the double-submit-cookie logic from. If we'd had a clean XSS record and no existing CSRF tooling to reuse, hardening in place would have been the more defensible short-term call. I wrote the trade-off up as a one-page decision doc so the next person facing this doesn't have to re-derive it from scratch.

Drill chain

Why can't you just set the token cookie's SameSite to Strict and skip anti-forgery tokens entirely?

SameSite=Strict stops the cookie from being sent on cross-site navigations and requests, which blocks most CSRF, but it also breaks legitimate cross-site flows like a link from an email or another site landing the user on an authenticated page, and it doesn't help at all against attacks originating from a subdomain of your own site if you have one that's less trusted. Most BFF implementations use SameSite=Lax or Strict as a strong first layer but still add an anti-forgery token as defense in depth, because relying on a single browser-enforced attribute for your entire CSRF posture is fragile against edge cases and future browser behavior changes.

What does the BFF's server component actually need to be, technically, to be a confidential client?

It needs to hold a client secret or certificate that only it — never the browser — has access to, and use that credential when it exchanges an authorization code for tokens or refreshes them, proving to the IdP that the request is coming from a trusted server process rather than an arbitrary caller. That's the whole reason a confidential client can be trusted with longer-lived refresh tokens: possession of the token alone isn't sufficient to get new access tokens without also proving possession of the secret.

If the org had no existing CSRF tooling to reuse, how would that change your recommendation?

It would raise the near-term cost of BFF meaningfully, since building and testing anti-forgery handling from scratch is real work with its own risk of getting subtly wrong. I'd likely recommend hardening in place first — short token lifetime, strict CSP, dependency-scanning to prevent a repeat of the XSS source — and revisit BFF once either a second XSS incident occurred or the CSRF tooling existed to make the migration cheaper.

Does moving to a BFF eliminate the need for CSP and dependency scanning?

No — it removes token theft as a payoff for XSS, but an XSS vulnerability still lets an attacker perform any action the logged-in user's cookie allows, make requests on their behalf, exfiltrate whatever's rendered on the page, or manipulate the DOM. CSP and dependency hygiene remain necessary; BFF narrows what a successful XSS can achieve, it doesn't make XSS itself irrelevant.

05"Just put it in localStorage"

Mid Technical disagreement with a colleague

Worked example EXAMPLE — replace with your own

A colleague on my team building a new internal dashboard wanted to store the access token in localStorage so it would survive a page refresh without a redirect round-trip, which is a completely reasonable thing to want. I pushed back, and the disagreement got a little heated in a PR thread before we took it to a fifteen-minute call. My concern wasn't abstract "localStorage is insecure" — it was that this specific dashboard rendered user-submitted freeform text (support ticket notes) without sanitizing it server-side, which meant a stored-XSS payload was a realistic risk, not a hypothetical one, and anything in localStorage is readable by any script that executes on that origin, no exceptions, no flags.

He countered, correctly, that an httpOnly cookie has its own problem: it's automatically attached to every request to that domain, so we'd need CSRF protection we didn't currently have anywhere in the app. We ended up compromising on a middle path for this one app rather than either extreme: keep the access token in memory only (a module-level variable, gone on refresh) backed by a silent-refresh call on load using a refresh token that itself lived in an httpOnly cookie, so the worst an XSS payload could do was ride the current in-memory access token until the tab closed, not exfiltrate a durable credential that worked from anywhere. It cost us one extra round trip on every page load, which we measured at under 120ms, and we thought that was a fair price given the actual XSS exposure. It wasn't the "correct" universal answer — it was the right answer for that app's specific risk profile.

What the interviewer is really probing: whether you can disagree productively — with evidence about the actual app's risk, not a rule quoted from a blog post — and whether you can reach a real compromise instead of "I was right and they backed down." A story where you simply won is much less interesting than one where the resolution was better than either person's starting position.

Is an in-memory-only access token actually meaningfully safer than one in localStorage?

A cookie is attached by the browser automatically to any matching request, including ones triggered by a malicious page the user happens to have open in another tab — the browser doesn't ask whether the request is "supposed" to be authenticated, it just sends the cookie because the domain matches. Once malicious JavaScript executes in the page's origin — through an unsanitized rendering of attacker-controlled content, a compromised dependency, or a vulnerable third-party script — it has the same privileges as any other script on that page, which includes full read/write access to window.localStorage for that origin. There's no browser-level isolation between "your app's code" and "code that ended up running in your app's page" once execution happens; the origin, not the source of the script, is what storage access is scoped to.

Drill chain

Why does JWT validation include a not-before check at all — what attack does it prevent?

The nbf claim lets an issuer mint a token now that shouldn't be usable until some future time — for example, a scheduled permission grant that shouldn't take effect until a maintenance window ends. Without it, there'd be no way to issue a token in advance for future use without it being immediately valid, which matters for pre-provisioning access or coordinating a time-gated rollout.

Why is ClockSkew = TimeSpan.Zero dangerous rather than just occasionally inconvenient?

It assumes perfect clock synchronization between every token issuer and every validating server in the system, which is never actually true — NTP drift, container cold-start delay, and clock skew in virtualized environments are all real and common. Setting it to zero doesn't make validation more secure against a real attacker, who doesn't need to exploit clock skew to forge a token; it just makes the system fragile against ordinary infrastructure reality, trading reliability for a security property that was never actually at risk from clock tolerance in the first place.

What's actually at risk if you set ClockSkew too generously, say 30 minutes?

A token whose exp has technically passed remains usable for up to that skew window past its stated expiry, and a token whose nbf hasn't technically arrived yet becomes usable that much early. For most access tokens with reasonably short lifetimes this is a minor extension of an already-bounded window, but for anything security-sensitive — a one-time step-up-auth token, a short-lived elevation grant — a large skew tolerance meaningfully extends the window an attacker has if they've somehow obtained a token near its boundary.

Because the underlying cause was cold-start NTP convergence time, which happens again every time a fresh container starts — a restart doesn't fix a systemic timing characteristic, it just resets the clock to the same not-yet-converged state that caused the bug in the first place. Any new container hitting the token endpoint in that same post-start window would reproduce it, which is exactly why it looked "random" rather than tied to any one host.

An integration test that explicitly simulates clock skew — mocking the system clock to be, say, 30 seconds behind the token's issuance time and asserting validation still succeeds under the configured tolerance — would have caught a zero-skew regression immediately. That kind of test is easy to write and almost nobody writes it, because "the token is valid" tests default to using perfectly synchronized clocks.

07The JWKS stampede

Staff Scaling challenge

Worked example EXAMPLE — replace with your own

During a scheduled signing-key rotation on our IdP — a routine, announced event — every one of our roughly ninety API instances started returning 401s for a two-to-three minute window, right at the rotation timestamp. Each instance's ConfigurationManager (the piece of Microsoft.IdentityModel that fetches and caches the JWKS) had cached the old signing key set, and when the new key started signing tokens, every instance simultaneously discovered its cached key set no longer had a matching kid, and every one of them went and re-fetched the JWKS endpoint at effectively the same moment. Ninety near-simultaneous requests isn't a large number in absolute terms, but the JWKS endpoint sat behind the same shared IdP infrastructure that was also mid-rotation and momentarily under elevated load from every other tenant's fleet doing the exact same thing at the exact same second, and a chunk of our requests got rate-limited, which meant those instances kept the stale key set a little longer and kept failing.

The actual fix wasn't caching harder — caching was already correctly in place — it was making key rotation itself non-instantaneous from the validator's point of view. We moved to a rotation runbook where the IdP publishes both the outgoing and incoming signing keys in the JWKS simultaneously for a defined overlap window before and after the cutover, so a validator with a slightly stale cache still finds the new key present, and a validator that already refreshed still finds the old key present for tokens issued moments before rotation. That converts "everyone must refresh in the same instant or fail" into "refresh whenever, both keys are valid for the whole overlap window," which eliminates the stampede's root cause rather than just spreading it out.

What the interviewer is really probing: whether you understand that key rotation is a distributed-systems coordination problem, not just a caching problem, and whether you can name the actual fix (overlap window) instead of a band-aid (retry with backoff, which helps but doesn't remove the root cause).

Drill chain

Why does caching the JWKS make this worse instead of better, at first glance?

Caching isn't the problem — not caching at all would mean every single token validation hits the JWKS endpoint, which is far worse under normal load. The problem is that a naive cache invalidates on a single trigger (cache-miss on an unknown kid) with no jitter or staggering, so when the trigger fires for one instance it fires for all of them at essentially the same instant, turning what should be background refresh traffic into a synchronized burst.

Why is an overlap window a strictly better fix than exponential backoff with jitter on the client?

Backoff with jitter spreads the retry traffic out over time, which reduces the peak load on the JWKS endpoint, but it doesn't change the fact that some tokens will still be rejected by some validators during the window before their cache catches up — it shrinks the failure window, it doesn't remove it. An overlap window removes the failure mode entirely: any validator, whether it refreshed a second ago or an hour ago, finds a valid key for any token issued during the transition, so there's no window in which a legitimately issued token fails validation anywhere in the fleet.

How long should an overlap window be, and what determines that?

Long enough to cover the slowest realistic cache-refresh interval across your entire validator fleet, plus margin — if your ConfigurationManager refreshes on a fixed interval or on cache-miss with some minimum refresh spacing, the window needs to exceed the longest gap any instance could plausibly go without picking up the new key. In practice this is usually measured in tens of minutes to a few hours for JWKS rotations, not seconds, precisely because you want it to be safe even for a validator that's been unusually slow to refresh.

Does this same coordination problem show up anywhere outside of signing-key rotation?

Yes — TLS certificate rotation, feature-flag config changes read from a cached config source, and DNS record changes with a low-but-nonzero effective TTL are all the same shape: many independent caches, each individually reasonable, that invalidate on the same external trigger at the same moment. The general fix pattern is the same too — overlap the old and new state for a window rather than cutting over instantaneously.

What would you monitor to catch a rotation problem before it caused customer-visible 401s?

An alert on the 401 rate specifically correlated with the scheduled rotation window, and separately, a synthetic canary that validates a freshly-issued token against every environment continuously through a rotation event, so you'd see the failure in a synthetic check seconds before real traffic was affected, rather than finding out from a customer-impact dashboard after the fact.

Why can't a stateless JWT be instantly revoked?

The whole point of a self-contained, signed token is that any validator can check it's genuine and unexpired using only the signing key, without asking a central authority — that's what makes it fast and horizontally scalable. It keeps the expensive, centralized check off the hot path — the vast majority of requests just validate a signature and an expiry claim locally — while still bounding how long a revoked token can be used to at most one refresh interval. Ten minutes was chosen as short enough that a compromised or explicitly-revoked session doesn't stay usable for long, but long enough that the refresh traffic itself doesn't become the new scaling bottleneck.

I'd have kept per-request central validation but attacked the latency differently — moving the revocation check to a fast in-memory store like Redis instead of SQL Server, and making sure that store itself was horizontally scaled and close to the compute. That trades the "no per-request call at all" win for a "the per-request call is now single-digit milliseconds" win, which is a legitimate alternative if instant revocation is a hard requirement.

Related but distinct — the BFF story (04) is about where the token lives and who can read it (browser vs server), while this one is about whether validating it requires a central lookup at all (stateful session vs self-contained token). You can combine them: a BFF's server-side session can itself be backed by either a database session table or a self-contained token that the BFF holds — the two decisions are largely independent.

Drill chain

What exact attack does PKCE prevent that the authorization code flow alone doesn't?

Without PKCE, if an attacker can intercept the authorization code — through a malicious app registered on the same custom URI scheme on a mobile device, or a compromised network path on the redirect — they can exchange that code for tokens themselves, because the code alone is normally enough at the token endpoint for a public client. PKCE ties the code to a secret (the code verifier) generated fresh by the legitimate client at the start of that specific flow, so an attacker holding only the intercepted code can't complete the exchange without also having generated the matching verifier, which they never saw.

Why is SHA-256 used to derive the challenge instead of sending the verifier directly in the authorization request?

The code challenge is sent in the authorization request, which travels through the browser or system browser and can end up in logs, browser history, or referrer headers — sending the raw verifier there would defeat the purpose, since anything that could see the challenge could also see the verifier. Hashing means only a value derived from the verifier is exposed early in the flow, and the actual verifier is only ever sent once, directly to the token endpoint over TLS, at the very end.

Is PKCE only relevant for mobile and SPA clients?

It's most critical for public clients that genuinely can't hold a secret, but OAuth 2.1 requires it for every client type, confidential clients included, because it's cheap to implement and adds a layer of protection against authorization code interception regardless of client type — there's no meaningful downside to using it even where a client secret also exists.

I'd have asked them to actually try extracting the secret from a built APK or IPA using a decompiler, rather than debating it in the abstract — a hands-on demonstration that the "secret" is trivially recoverable is usually more convincing than any argument, and it turns an abstract security claim into something they've personally verified.

Drill chain

Why does caching authentication state introduce a data-loss risk that stateless token validation doesn't have?

A cache is, by definition, holding a copy of state that something else considers authoritative, and if that copy is lost or corrupted, the system's behavior depends entirely on what the fallback does — deny by default, which causes exactly this kind of false lockout, or fail open, which is far worse from a security standpoint. Pure stateless token validation has no separate cache layer to lose; the token itself carries everything needed to validate it, so there's no intermediate copy of session truth that can silently drift or vanish.

Why fail closed (deny access) rather than fail open when the cache has a gap?

Failing open on an authentication cache miss means anyone whose session isn't found gets treated as authenticated by default, which turns any cache bug into a wide-open security hole rather than a contained availability problem. Failing closed is the safer default because the worst case is a false lockout — annoying, visible, and fixable — rather than a false authorization, which could go unnoticed and be actively exploited.

Shared infrastructure for unrelated consumers is efficient right up until an incident in one blast-radius takes out something with a completely different risk profile.

What's the synthetic canary actually checking, mechanically?

It writes a known session record into the cache on a short interval, then immediately reads it back and verifies the value matches what was written, alerting if a read ever returns missing or stale data within a time bound that should be well inside normal replication lag. It's deliberately simple — it doesn't try to validate real auth logic, just that write-then-read consistency holds, because that's the specific property that silently broke.

Possibly — a staging environment that exercised a failover during the upgrade under realistic write load might have surfaced the persistence misconfiguration before production, but failover timing is notoriously hard to reproduce deterministically in a lower environment. Drill chain

Why does the aud claim matter at all — what does it actually protect against?

The aud claim states which API or resource a token was issued for, and validating it stops a token legitimately issued for one API from being replayed against a different API that trusts the same issuer and signing key. Without audience validation, a token meant only for a low-sensitivity read API could be presented to a higher-sensitivity API and, if that API only checked signature and issuer, be accepted — audience validation is what confines a token to its intended purpose.

Why would a service accept multiple audience values instead of just the one correct one?

In practice, different client libraries or SDK versions sometimes populate the audience differently — one sending the App ID URI, another sending the client ID — often for legitimate historical or ecosystem reasons, and a service trying to be compatible with all of them accretes a tolerance list rather than pushing every caller to conform to one value. That's a reasonable short-term accommodation; the failure here was that it was never centralized, reviewed, or bounded, so it silently grew to include values nobody could justify anymore.

Why is a "temporary" debug override that accepts any audience so dangerous specifically, compared to other kinds of debug code left behind?

Because it defeats the one check that confines a token to its intended API — with it in place, any valid token from the trusted issuer, regardless of what it was actually issued for, is accepted, effectively merging the trust boundary of every API sharing that issuer into one. Most leftover debug code causes a narrow functional bug; this specific kind silently deletes a security boundary while everything continues to look and behave normally for legitimate traffic.

What would you put in place to make sure a shared validation policy doesn't just drift apart again in another two years?

A single versioned, tested library or shared configuration that all four services import rather than reimplement, plus a lightweight automated check — even just a scheduled diff against the canonical policy — that flags if any service's actual runtime configuration diverges from what the shared source declares. Ownership without a mechanism to detect drift tends to erode the same way the original inconsistency did: quietly, one local fix at a time.

How would you have caught this before a partner integration exposed it?

A cross-service contract test suite that sends the same set of tokens — including edge cases like an unexpected but structurally valid audience — against every service that's supposed to enforce the same policy, and asserts they all respond identically. That test would have failed the moment any one service's tolerance list diverged from the others, long before an external partner's traffic pattern happened to expose it.

Drill chain

Why are passkeys phishing-resistant in a way passwords and even most MFA aren't?

A passkey is bound cryptographically to the specific origin it was registered for during the WebAuthn ceremony, so the browser or platform simply won't offer or use it on a look-alike phishing domain, regardless of how convincing the page looks to a human. Passwords and most OTP-based MFA rely on the human correctly recognizing the real site before entering a value that works anywhere it's typed, which is exactly the step phishing attacks exploit.

What does "requiring at least one fallback method" actually protect against, and does it weaken the phishing-resistance property?

It protects against total account lockout when someone loses their only enrolled device or authenticator, without which the only recovery path is a manual, harder-to-scale support process. It doesn't weaken passkey's phishing-resistant sign-in path itself, since the fallback is only used for account recovery, not day-to-day authentication — the trade-off is that the fallback mechanism (a recovery code) is only as strong as how well the user protects it, so it's worth being deliberate about not making the fallback itself the weak link an attacker targets instead.

Why introduce this to an internal team before customers instead of doing a small opt-in customer beta first?

An internal team gives faster, higher-bandwidth feedback — people who'll actually report a confusing recovery flow in detail rather than just churning silently — and any problems discovered have zero customer-facing blast radius or support-ticket cost while being fixed. A customer beta is still valuable for validating real-world behavior across a more diverse device and platform mix, which is exactly why the customer rollout that followed was itself staged and gradual rather than a single flip.

What platform-dependent rough edges specifically did you run into?

Cross-device passkey sync behaves differently depending on which platform ecosystem a user's devices are in, so a user who enrolls a passkey on one device doesn't always get a consistent experience finding or using it from a different device or browser without understanding their own platform's sync model. That inconsistency is exactly what made the recovery-path gap more urgent to fix — losing track of which device holds a usable passkey is a more common user experience than losing a device outright.

How do you decide when a new authentication mechanism is mature enough to become the default rather than an option?

I'd want to see enrollment and successful sign-in rates for the new mechanism approach parity with the existing default across a representative slice of the user base, plus a support-ticket rate for the new mechanism at or below the old one, sustained over at least one full quarter, before considering flipping the default. Making something the default is a much bigger commitment than offering it as an option, since it changes the experience for users who never explicitly opted in.

Why would a confidential client use a certificate instead of a client secret in the first place?

Building that inventory, by querying the IdP's own app-registration data rather than relying on tribal knowledge of what's supposed to exist, is what actually closes the blind spot this incident exposed.

That story was about the IdP's own signing keys rotating on schedule and every validator needing to keep up with a known, planned change; this one is about a client-side credential expiring unnoticed because no process tracked it at all. Both are "a credential's lifecycle wasn't handled gracefully," but one is a coordination problem between many validators and a planned rotation, and the other is a monitoring and ownership gap on an unplanned-for, single credential.

Worked example EXAMPLE — replace with your own

Our authentication integration test suite had a roughly 8% flake rate — failing intermittently with no code change involved — which had gotten bad enough that engineers had started reflexively re-running failed CI jobs without reading the failure first, which is exactly the habit that lets a real regression slip through disguised as "probably just flaky again." Drill chain

Why is testing against a real IdP appealing in the first place, if it causes this much flakiness?

It gives you confidence that your code works against the actual protocol implementation and its real quirks, not just against your own assumptions encoded in a fake — a fake issuer can be wrong in ways that a real IdP integration test would catch. The trade-off is reliability and speed versus that extra fidelity, and the right answer for most of a test suite is a fast, deterministic fake for unit and most integration tests, with a much smaller number of true end-to-end tests against a real (or realistic sandboxed) IdP to catch the fidelity gaps the fakes can't.

How do you make sure the fake token issuer stays faithful to how the real IdP actually behaves?

By building the fake against the same claims schema, signing mechanism, and validation edge cases the real IdP exposes, and periodically running a small set of contract tests against the real IdP to confirm the fake hasn't drifted — the fake is a stand-in for behavior you've already characterized, not a guess at how auth in general should work. Any time the real IdP changes something material, the fake needs a corresponding update, or it starts giving false confidence.

Why does a virtual clock fix the expiry-assertion flakiness better than just adding a longer buffer, like sleeping for 30 seconds instead of 6?

A longer sleep reduces the chance of flaking under moderate load but doesn't eliminate the dependency on wall-clock timing under load at all — it's still possible, just less likely, and it makes every test run slower for everyone regardless of whether that particular run was under load. A virtual clock removes the dependency on real elapsed time entirely: advancing a fake clock by six seconds is instantaneous and deterministic, so the test can never flake due to CI runner scheduling variance, no matter how loaded the runner is.

What's the risk of over-relying on fakes across the whole suite?

You can end up with a suite that passes consistently while the real integration has silently drifted out of sync with what the fakes assume — every fake is only as good as how faithfully and recently it was validated against the real thing. That's exactly why a smaller layer of genuine end-to-end tests against a real or realistic IdP sandbox needs to stay in the pipeline, even after the bulk of the suite moves to fast, deterministic fakes.

How would you convince a team that's grown used to re-running flaky tests to change that habit?

Showing them the specific regression that slipped through because of exactly that habit is more persuasive than any general argument about test hygiene — concrete, recent, and painful beats abstract best practice. I'd pair that with making the fix visibly reduce their day-to-day pain (faster, more reliable CI) so the behavior change is reinforced by their own experience, not just a policy announcement.

Drill chain

Why exactly is ROPC being removed in OAuth 2.1, in concrete technical terms?

It requires the client application to collect the resource owner's actual credentials and forward them directly to the authorization server, which means the client sees the raw password — defeating the core OAuth principle that the client never needs to see the user's actual credentials, only a token scoped to what it's allowed to do. It also has no clean way to support anything beyond a single factor, since there's no interactive step for the authorization server to challenge with MFA, and no way for the user to see or control what scopes they're consenting to, since there's no consent screen in the flow at all.

Why is client-credentials a legitimate compromise here, when it also skips the interactive user-consent flow?

Client credentials is designed for exactly this shape of problem — machine-to-machine access where there's no human resource owner in the loop at all, which is different from ROPC's shape of "a human's credentials, handled by a client on their behalf." The scoped alternative treated the legacy integration as a service-to-service call under the customer's own organizational credential, not as a stand-in for an individual user's login, which is the correct model for what was actually a backend system integration wearing a "user login" costume.

What would you have done if the director had insisted on ROPC anyway, after hearing your case?

I'd escalate the decision explicitly to whoever owns risk acceptance at that level — a CISO-equivalent or VP engineering — framed as "here's the liability, here's my recommended alternative, this needs a risk-acceptance decision above my authority if we proceed with ROPC anyway," rather than either quietly complying or refusing to implement a decision made above me. Principal-level pushback means making sure the right person makes an informed decision, not that you personally get to veto it forever.

Is there ever a legitimate use case for ROPC even under OAuth 2.1's guidance?

Essentially no for anything user-facing or externally exposed; the specification itself frames it as something to actively avoid and phase out, reserved historically for narrow legacy migration scenarios where no better option existed yet. Its removal from the 2.1 spec reflects that the ecosystem has matured to the point where those narrow scenarios can and should be solved with device-code flow, client-credentials, or a proper interactive flow instead.

How do you generally decide when a security concern is worth a formal pushback versus just noting it and moving on?

I weigh how hard the resulting liability would be to unwind later against how much friction pushing back adds right now — a decision that's cheap to reverse if wrong gets a lighter-weight objection, while one that creates a durable liability, a precedent other teams will point to, or direct handling of sensitive data gets the full written-case treatment. ROPC scored high on all three: hard to unwind once customers depend on it, an obvious precedent for the next "just this once" request, and direct exposure to raw user passwords.

20The cookie that broke the load balancer

Staff Production incident / outage

Worked example EXAMPLE — replace with your own

Users in one large customer's tenant started getting 400 Request Header Or Cookie Too Large errors from our load balancer on every request, for that tenant only, with no deploy correlated to the start time. That customer had recently completed an internal reorg that put a large fraction of their employees into a deeply nested set of Entra security groups, and our app's authentication cookie carried every group claim from the token verbatim — a design that had worked fine for years because most tenants' users belonged to a handful of groups, and nobody had built for the case of a user belonging to hundreds.

Entra ID actually has a built-in mechanism for exactly this — when a user's group membership count exceeds a threshold, the token stops including the full list of group object IDs and instead includes a hasgroups: true indicator plus an overage claim pointing the app at the Microsoft Graph API to fetch the actual group list on demand — but our cookie-construction code had been written before that tenant ever hit the overage threshold, and it silently fell back to whatever partial or malformed group data made it into the token rather than detecting the overage indicator and switching to the Graph lookup path. The cookie kept growing as more of the reorg's group assignments propagated, until it crossed the load balancer's header-size limit and every request from that tenant started failing outright.

// missing: no check for the overage indicator before trusting groups claims
var groups = principal.FindAll("groups").Select(c => c.Value);
cookie.Claims.AddRange(groups);   // grows unbounded with group count

// fixed: detect overage, fetch on demand instead of inflating the cookie
if (principal.HasClaim("hasgroups", "true")) {
    // don't trust an incomplete groups claim — resolve via Graph when needed,
    // and cache that resolution server-side, never in the cookie itself
    groups = await graphClient.GetUserGroupsAsync(principal.GetObjectId());
} else {
    groups = principal.FindAll("groups").Select(c => c.Value);
}

Drill chain

Why does Entra ID switch to an overage indicator instead of just always including the full group list?

Tokens have practical size limits — they typically travel in HTTP headers, and some protocols and infrastructure components have hard caps on header size — so a token that tried to include the full group membership for a user in hundreds or thousands of groups could itself become too large to transmit reliably. The overage mechanism keeps the token itself small and predictable in size regardless of a user's group count, deferring the potentially large group list to an on-demand API call only for the applications that actually need it.

Why put groups in a cookie at all instead of just re-checking the token's claims on every request?

Cookies here were standing in for a lightweight session cache, avoiding re-parsing and re-validating the full token or re-querying Graph on every single request — a reasonable performance optimization for the common case, which is exactly why it had worked fine for years before this tenant's structure exceeded the threshold it was never designed to handle. The fix keeps that caching benefit but moves the actual group data to server-side session storage instead of a cookie the client round-trips on every request, so the cookie itself stays small regardless of how large the resolved group list gets.

What would you do differently in a fresh design to avoid this failure mode from the start?

I'd design claims-to-cookie mapping with an explicit size budget and a hard assertion that fails fast in a lower environment — rather than silently truncating or growing unbounded in production — the moment any single claim's serialized size approaches a meaningful fraction of the cookie or header limit. Catching "this claim can be unboundedly large" during design or in CI, using a test fixture with a large synthetic group count, is far cheaper than discovering it in production against one customer's real reorg.

Is caching resolved groups server-side instead of in the cookie itself risk-free?

No — it reintroduces a version of the same staleness and cache-invalidation trade-off discussed in the JWKS stampede (07) and the Redis session-cache scare (11) stories: a server-side cache of group membership can go stale if a user is removed from a sensitive group and the cache isn't invalidated promptly, briefly granting access that should have been revoked. The mitigation is a bounded cache lifetime short enough that stale authorization data doesn't persist meaningfully longer than the token's own lifetime would have allowed anyway.

How does this connect to the audience-ownership story (13) about cross-team drift?

Both are examples of an authentication-adjacent design decision that was correct under the assumptions true at the time it was made, and silently stopped being correct as some external condition — a partner's client library default, a customer's org structure — changed without anyone re-examining the original assumption. The general lesson across both: claims-handling code needs periodic re-validation against real-world data shape, not just correctness at ship time, because the inputs to auth logic are, in practice, controlled by parties outside your own change-management process.

22Night-before cheat sheet

Ten sentences to have loaded and ready to say out loud, not to read from. If you can say each one in your own words without looking, you're ready.

  1. OAuth 2.1 is still a draft — draft-16, published 2026-09-03, targeting IESG submission in December 2026 — and it formally retires the implicit and password grants while mandating PKCE for every client and expecting sender-constrained tokens.
  2. DPoP, the sender-constrained-token mechanism OAuth 2.1 leans on, has no native support in ASP.NET Core's JWT bearer handler as of .NET 10 — it's tracked for .NET 12 planning, so anyone doing it today is doing it by hand or through a third-party library.
  3. JWT validation is several independent checks, not one — signature, algorithm allow-list, issuer, audience, expiry, not-before — and skipping the algorithm allow-list specifically opens the door to RS256/HS256 confusion attacks against a publicly-published signing key.
  4. Entra ID's default ClockSkew is five minutes for a reason — real infrastructure clocks drift — and setting it to zero doesn't add security against a real attacker, it just makes the system fragile against ordinary NTP and container-startup timing.
  5. Signing-key rotation is a distributed-coordination problem: the fix for a rotation-time outage is publishing old and new keys simultaneously for an overlap window, not just adding client-side retry with jitter.
  6. Public clients (SPAs, mobile apps) get shorter refresh-token lifetimes than confidential clients because they can't prove their identity with a secret — an embedded "secret" in a distributed binary isn't a secret, which is exactly the PKCE story.
  7. A Backend-for-Frontend trades XSS-can-steal-the-token risk for a CSRF surface you now have to defend — it's a real trade-off decided by threat model, not a free security upgrade you should default to without reason.
  8. Entra's groups-overage mechanism (hasgroups plus a Graph lookup) exists because a user in hundreds of groups can't have every group ID stuffed into a token or cookie without hitting real header-size limits — code that doesn't check for it silently breaks the moment one tenant's org structure grows past the threshold.
  9. Continuous Access Evaluation gets you near-real-time revocation for CAE-capable resources via critical events and Conditional Access re-evaluation — both the app and the resource API have to declare the cp1 client capability for it to apply.
  10. Both .NET 9 and .NET 8 reach end of support on 2026-11-10 — if anything you'd talk about is still running on either, know your migration plan for that date, because it's close.

If you only remember one thing under pressure: every one of these stories is really about the same question — what happens when the credential, the clock, the claim shape, or the org structure stops matching what the code assumed on day one. Anchor your own answers in the moment you noticed the mismatch and what you did about it, not in a description of how the protocol is supposed to work.
