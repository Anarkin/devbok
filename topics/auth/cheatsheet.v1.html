01 OAuth 2.1 grants & flows

OAuth 2.1 is a consolidating IETF draft, not yet a published RFC: it folds RFC 6749/6750 plus the Security BCP, PKCE, Native Apps and Browser-Based Apps guidance into one document. It removes the Implicit grant and Resource Owner Password Credentials (ROPC) outright, and makes PKCE mandatory for every client using the authorization code grant.

04 JWT structure, algorithms & validation

header.payload.signature, each segment base64url-encoded (RFC 7519 JWT, RFC 7515 JWS, RFC 7518 JWA).

AlgorithmKindUse it when
RS256RSA, asymmetricDefault for OIDC/Entra ID — verifier only ever needs the public key from JWKS
ES256ECDSA, asymmetricSmaller signatures, cheaper to verify; growing adoption alongside RS256
EdDSA (Ed25519)AsymmetricNewest, fast and misuse-resistant; check library support before committing
HS256HMAC, symmetricOnly when issuer and verifier share the secret directly (e.g. your own service-to-service tokens) — never for third-party-issued tokens
none—Never valid. Reject it — this is the classic "alg confusion" attack vector

Validate with Microsoft.IdentityModel.JsonWebTokens (modern)

var handler = new Microsoft.IdentityModel.JsonWebTokens.JsonWebTokenHandler();
var result = await handler.ValidateTokenAsync(rawJwt, new TokenValidationParameters
{
    ValidIssuer = "https://login.microsoftonline.com/{tid}/v2.0",
    ValidAudience = "api://my-api",
    ValidAlgorithms = ["RS256"],           // allowlist — never trust the header's alg alone
    IssuerSigningKeyResolver = (t, tok, kid, p) => ResolveFromJwks(kid),
    ValidateLifetime = true,
    ClockSkew = TimeSpan.FromMinutes(2),
});
if (!result.IsValid) throw result.Exception!;

Legacy: System.IdentityModel.Tokens.Jwt.JwtSecurityTokenHandler does the same job through reflection-heavy JwtSecurityToken objects. JwtBearerOptions.TokenHandlers (since ASP.NET Core 8) lets you swap it for JsonWebTokenHandler, which is the current default and materially faster.

Docs: RFC 7519 JWT · JsonWebTokenHandler

07 Cookies vs bearer tokens / the BFF pattern

TaskCookie sessionBearer JWT
Where the credential livesBrowser cookie jar, invisible to page JS when HttpOnlyWherever the client code puts it — the risk surface is exactly that choice
Cross-site request forgeryNeeds an antiforgery token (ambient credential auto-attaches)Not applicable — nothing auto-attaches a header
Cross-site theft via scriptImmune if HttpOnly — JS can't read it even via XSSAny XSS that finds it in localStorage/sessionStorage/JS memory can exfiltrate it
Cross-origin API callsAwkward — needs SameSite=None; Secure, still first-party-adjacentNatural fit — just a header, any origin
Key flagsHttpOnly, Secure, SameSite=Lax\|Strict\|None—

Modern default for browser apps: the SPA never holds an OAuth token at all. A same-site, confidential Backend-for-Frontend (BFF) does the OAuth dance and keeps access/refresh tokens server-side; the browser gets only a same-site HttpOnly session cookie to talk to its own BFF. This is the consolidated guidance formerly known as "OAuth 2.0 for Browser-Based Apps", now folded into the OAuth 2.1 draft. Duende.BFF is the common off-the-shelf implementation on ASP.NET Core; a hand-rolled version is just AddCookie + a reverse proxy (e.g. YARP) that attaches the real token server-side.

Docs: Duende.BFF · SameSite cookies

09 Token lifetimes, revocation & CAE

Token / mechanismDefaultNotes
Entra ID access tokenRandomized 60–90 min (~75 min average)The jitter spreads renewal load; override with a Configurable Token Lifetime (CTL) policy
Access token with CAE enabledLong-lived window 20–28 hTrades a longer nominal lifetime for near-real-time revocation on critical events (see below)
Refresh token90-day sliding inactivity windowSingle-use — rotates on every redemption; revoked immediately by a password reset or security-stamp change
Explicit client-side revokeRFC 7009 — POST /revoke {token, token_type_hint}What a real "log out everywhere" button should call, in addition to clearing local state
Centralized active/inactive checkRFC 7662 — POST /introspect {token} → {"active": true, ...}For opaque/reference tokens, or when you don't trust exp alone
ASP.NET Core Identity "sign out everywhere"await userManager.UpdateSecurityStampAsync(user)Invalidates every existing cookie/session tied to that stamp; polled via SecurityStampValidatorOptions.ValidationInterval

Continuous Access Evaluation (CAE): instead of waiting out a token's nominal lifetime, Entra ID pushes near-real-time revocation to CAE-aware resources (Graph, Exchange, SharePoint, and your own CAE-enabled API) when a user is disabled, a password changes, or a risky sign-in is detected. Distinct from Token Protection, Entra's own device-bound Primary Refresh Token mechanism (GA for native Windows/iOS/macOS apps, still preview for browsers and limited to Azure Resource Manager) — that's a proprietary PRT binding, not the IETF DPoP standard from unit 02.

Docs: Entra access tokens · Continuous Access Evaluation

10 Idioms & gotchas

  • Always check alg against a server-side allowlist — never let the token header pick its own verification algorithm.
  • aud must exactly match your API's own identifier; accepting a token meant for a different resource is the confused-deputy bug.
  • Validating a multi-tenant issuer: substitute the token's own tid into the templated {tenantid} issuer, then compare exactly — don't just accept any tenant.
  • A client that merely received an access token shouldn't parse or trust its contents — it's opaque to that client; only the resource server validates it.
  • Rotate signing keys by kid: refresh your JWKS cache on a kid miss, not purely on a fixed timer, or a rotation window locks users out.
  • Never put a refresh token in localStorage/sessionStorage. MSAL.js keeps it in memory and relies on silent renewal or a BFF instead.
  • SameSite=None cookies must also set Secure, or the browser drops them silently.
  • Access-Control-Allow-Credentials: true can never be paired with a wildcard Access-Control-Allow-Origin: * — the browser rejects that combination.
  • A cookie-authenticated endpoint still needs CSRF/antiforgery protection; a pure bearer-token endpoint doesn't (no ambient credential to forge).
  • On ASP.NET Core 10, an unauthenticated call to an API-shaped endpoint now 401s instead of redirecting — check any SPA logic that used the old redirect response to detect a dead session.
