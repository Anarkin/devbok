Authn & authz (.NET, OAuth/OIDC)

study · .NET 10 (LTS) · released 2025-11-11

OAuth 2.1 is in its final lap, not yet an RFC: draft-ietf-oauth-v2-1-16 (3 Sep 2026) folds PKCE, the native-apps BCP and the 2020 security BCP into one spec, drops the implicit and password grants outright, and targets the IESG by December 2026 — but ASP.NET Core and Entra ID already default to its stricter posture years ahead of ratification, which is the normal way OAuth evolves. OpenID Connect is unchanged as the identity layer on top, JWTs remain the shared token format, and the live 2026 argument is not "OAuth vs something else" but where a token lives — in the browser, or behind a server via the now-default-advice BFF pattern. This guide is anchored on .NET 10 (LTS, shipped 11 Nov 2025) and current Entra ID behaviour; its freshest thread is Entra's 2026 push to extend Conditional Access, short-lived tokens and revocation to AI-agent identities, not just human ones. Assumption: "the ASP.NET Core authn/authz stack" means Microsoft.AspNetCore.Authentication/Authorization on .NET 10, and "Entra ID" means the Microsoft identity platform (v2.0 endpoint), not the legacy ADAL/AAD Graph surface.

01Authn vs authz, and the ASP.NET Core pipeline

Authentication answers "who are you" — it produces an identity. Authorization answers "are you allowed to do this" — it makes a decision using that identity plus context (a resource, a scope, a tenant, a risk score). Every framework that gets this right keeps the two as separate, composable stages, because they change for different reasons: you swap identity providers on a business timeline (an acquisition, a compliance mandate, a new IdP contract) but you tune authorization rules constantly, feature by feature. If your codebase can't answer "which of these two just failed" without a debugger, the separation has already leaked.

OAuth 2.0 named four actors that are worth keeping in your head even for a single in-house app: the resource owner (the user), the client (the app requesting access), the authorization server (issues tokens, verifies identity), and the resource server (the API that trusts those tokens). A monolith often collapses AS and RS into "the app", but the moment you split a frontend from an API, or add a mobile client, or federate to Entra ID, the four roles resurface exactly as OAuth describes them — which is why OAuth, not a bespoke session scheme, is the vocabulary every modern stack converges on.

ASP.NET Core mirrors this split in its own primitives. IAuthenticationService (wired up by AddAuthentication and driven by UseAuthentication middleware) is responsible for producing a ClaimsPrincipal — a bag of claims (name, email, roles, scopes, tenant id, whatever the token carried) attached to HttpContext.User. IAuthorizationService (wired up by AddAuthorization, invoked by UseAuthorization middleware, or explicitly via [Authorize]/RequireAuthorization) takes that principal and a policy and returns allow/deny. Everything downstream — controllers, minimal API endpoints, Razor pages, SignalR hubs — reads HttpContext.User; none of it needs to know whether the identity came from a cookie, a JWT, Entra ID, or a unit test's fake handler. That indirection is the entire payoff: a principal engineer who gets this boundary right can replace the identity provider under an app without touching a single authorization policy, and can unit-test authorization logic by constructing a ClaimsPrincipal by hand, no HTTP or IdP involved.

One recent, easy-to-miss default: for a long time ASP.NET Core required you to name a DefaultScheme explicitly the moment you registered more than a trivial setup, or you'd hit InvalidOperationException: No authenticationScheme was specified. Current ASP.NET Core (the behaviour is stable through .NET 10) auto-promotes a single registered scheme to the default — you only need to disable that via AppContext.SetSwitch("Microsoft.AspNetCore.Authentication.SuppressAutoDefaultScheme") if you're deliberately deferring scheme selection. The instant you register a second scheme (cookie for the UI, JWT bearer for the API, say), the auto-default goes away and you're back to naming one explicitly or attaching schemes per-endpoint — a detail that trips people upgrading an old sample.

Interview trap

Candidates routinely say "401 means access denied" and stop there. It doesn't — 401 means "I don't know who you are, and here's how to prove it" (it comes with a WWW-Authenticate challenge header naming the scheme). 403 means "I know exactly who you are, and the answer is still no." Returning 401 for an authorization failure leaks nothing extra, but returning 403 to an anonymous caller leaks that the resource exists and is protected — which is why some APIs deliberately return 404 instead of 403 for resources whose existence itself is sensitive. If you can't explain when your app would emit each of 401/403/404 for the same URL, you don't yet have this boundary straight.

Try it
  1. Register both a cookie scheme and a JWT bearer scheme in a throwaway minimal API with no explicit default. Hit a protected endpoint with no credentials and read the exact exception message; then set a default scheme and observe the challenge response change.
  2. Swap the order of UseAuthentication() and UseAuthorization() and hit an [Authorize] endpoint with a valid bearer token. Predict what happens before you run it.
Expected outcome

(1) With two schemes and no default, ASP.NET Core throws InvalidOperationException: No authenticationScheme was specified... as soon as authorization needs to challenge — because with more than one scheme the auto-default rule no longer applies. (2) If UseAuthorization() runs before UseAuthentication(), the authorization middleware reads an unauthenticated HttpContext.User (authentication hasn't populated it yet), so a request with a perfectly valid token still gets a 401/challenge — a classic "it works with one scheme registered by accident, then breaks" bug.

Why does ASP.NET Core model authentication as "schemes" instead of hard-coding cookie vs. bearer logic?

Because a real app runs more than one login mechanism at once — a cookie for the browser UI, a JWT bearer scheme for the mobile client and third-party API consumers, maybe an OpenID Connect scheme for a federated login. A scheme is just a name bound to a handler plus its options, so the rest of the app (controllers, policies, [Authorize]) can say "authenticate me with this scheme" or "any of these schemes" without caring how each one actually verifies the caller. It's the same reasoning as dependency injection: name the capability, not the implementation, so you can register several implementations side by side and pick per call site.

What's the practical difference between [Authorize] with no arguments and [Authorize(Roles = "Admin")]?

Bare [Authorize] only checks that HttpContext.User.Identity.IsAuthenticated is true — any successfully authenticated principal passes, regardless of role or claims. [Authorize(Roles = "Admin")] additionally requires a role claim matching "Admin" (OR semantics across a comma-separated list). Under the hood both compile to authorization policies; the role check is sugar over RequireRole. At lead level the important habit is to prefer named policies ([Authorize(Policy = "AdminOnly")]) over inline role/claim strings scattered across controllers, so the actual rule lives in one place and can be unit-tested and audited.

Why is ClaimsPrincipal the shared currency between authentication and authorization, rather than something IdP-specific?

ClaimsPrincipal is deliberately provider-agnostic: it's a collection of Claim objects (type/value/issuer triples) wrapped in one or more ClaimsIdentity. Whether the identity came from a Windows token, a SAML assertion, a JWT, or a hand-rolled test double, it gets normalized into the same shape before authorization ever sees it. That's what lets a single [Authorize(Policy = "ApiScope")] work unchanged whether the caller authenticated via Entra ID, a partner's OIDC provider, or an internal STS — the policy only reasons about claims, never about the wire format that produced them.

What actually happens, step by step, when an anonymous request hits an [Authorize] endpoint?

Routing matches the endpoint and sees it requires authorization. The authorization middleware asks IAuthorizationService to evaluate the endpoint's policy against the current (empty/anonymous) ClaimsPrincipal; it fails. Because the failure reason is "not authenticated" rather than "authenticated but forbidden", ASP.NET Core triggers a challenge on the relevant scheme instead of a flat 403 — for cookies that's typically a 302 redirect to a login page, for JWT bearer it's a 401 with a WWW-Authenticate: Bearer header. If the principal had been authenticated but failed a role/claim requirement, you'd get a forbid instead — 403, no redirect, no challenge header.

Why does ASP.NET Core support multiple authentication schemes active in the same app, and how do you pick which one runs for a given endpoint?

Because real backends serve more than one kind of client from the same host — a server-rendered admin UI (cookies) and a public JSON API (bearer tokens) is the canonical case. You pick per endpoint by passing scheme names into [Authorize(AuthenticationSchemes = "Bearer")] or into the authorization policy, or by grouping routes so an entire area defaults to one scheme. A policy scheme can also inspect the request (e.g. is there an Authorization header?) and forward to the right concrete scheme dynamically, so callers don't have to know which mechanism the server expects.

What's a policy scheme, and when would a principal engineer reach for one?

A policy scheme is an authentication scheme whose "handler" is just a delegate that forwards to another registered scheme, chosen at request time — no token validation logic of its own. The textbook use is a single public endpoint that must accept both cookie-authenticated browser calls and bearer-token API calls: the policy scheme looks for an Authorization: Bearer header and forwards to the JWT scheme if present, otherwise forwards to the cookie scheme. It's the right tool when the *decision* of which scheme to use is itself request-dependent, rather than something you can fix per route at startup.

Can authorization ever run without authentication having happened first? What breaks if it does?

Yes — if UseAuthorization() is registered before UseAuthentication(), or if a handler runs on a code path that never called authenticate, authorization evaluates against whatever HttpContext.User currently is, which defaults to an empty, unauthenticated principal. Every claim-based check fails, every role check fails, and — misleadingly — the failure looks identical to "the user's token was invalid," which is a nasty thing to debug in production because it only manifests on endpoints that need authorization, and works fine for anonymous ones.

How would you unit-test an authorization policy without spinning up HTTP or a real identity provider?

Construct a ClaimsPrincipal directly with the claims your test scenario needs, resolve the real IAuthorizationService (with the app's actual policies registered) from a minimal service provider, and call AuthorizeAsync(principal, resource, policyName). This tests the actual policy logic — requirement handlers included — with no network calls and no dependency on how the principal would really be produced. It's the cleanest way to pin down "does 'AdminOnly' really require the Admin role AND an active tenant" as an executable spec instead of tribal knowledge.

As a lead, how do you review a PR that adds a new protected endpoint?

Check that the endpoint states an explicit policy rather than bare [Authorize] when "any authenticated user" isn't really the intended rule — bare [Authorize] is a common accidental under-restriction. Check which scheme(s) apply, especially in multi-scheme apps, since an endpoint with no scheme constraint accepts whichever scheme authenticates first. Check that a failure returns the status you'd expect (401 vs 403) and doesn't leak resource existence where it shouldn't. And check that the policy is testable and named, not an inline role string copy-pasted from another controller — that's how "AdminOnly" quietly drifts into three slightly different definitions across a codebase.

Why do interviewers ask about this pipeline instead of just asking "what is OAuth"?

Because knowing OAuth's grant types is trivia; knowing where authentication ends and authorization begins in your own framework is what actually prevents production incidents — wrong-status bugs, accidental open endpoints, authorization logic duplicated and drifting across controllers. At principal level, interviewers are really probing whether you can reason about *this* boundary well enough to review someone else's mistake in it, not whether you can recite RFC section numbers.

02OAuth 2.0 to 2.1: grants, PKCE, and client types

OAuth is a delegation protocol: it lets a resource owner grant a client limited access to a resource server without handing over their password. It was never an authentication protocol, and the single most common interview misconception is treating "I got an access token" as "I know who the user is" — an access token proves the client was granted some scope, nothing about identity. (OpenID Connect, unit 03, is the layer that actually answers "who".) Everything else in OAuth is mechanics for issuing, constraining and revoking that delegated access safely.

OAuth 2.1 (currently draft-ietf-oauth-v2-1-16, last updated 3 Sep 2026, targeting IESG submission by December 2026 — still a draft, not yet an RFC) isn't a new protocol; it's OAuth 2.0 plus a decade of security best-current-practice folded into one document: RFC 7636 (PKCE), RFC 8252 (native apps), the OAuth 2.0 Security BCP (RFC 9700), and browser-based-app guidance. Its job is to stop being "OAuth 2.0, plus seven other RFCs you have to know to implement it safely" and become one spec that already bakes in the hardening. Concretely, it removes two grants outright and tightens two more behaviours everyone already treats as best practice today.

Removed: the implicit grant (response_type=token). It returned the access token directly in the redirect URI fragment, with no client authentication and no code-exchange step — meaning the token lands in browser history, referrer headers, and any JS on the page, with no way to bind it to the client that requested it. It existed only because browsers in 2012 couldn't do cross-origin POST requests reliably; that constraint is gone, so the grant has no remaining justification. Removed: Resource Owner Password Credentials (ROPC) — the client collects the user's actual username and password and trades them directly for a token. It trains users to type credentials into arbitrary app UIs (the exact habit federated login exists to break), and it structurally cannot support MFA, step-up auth, or Conditional Access, because the authorization server never gets an interactive session with the user.

Tightened: PKCE is now mandatory for every client using the authorization code grant, confidential clients included — not just public clients (mobile/SPA) as most people learned it. The reasoning: PKCE defends against authorization-code interception (a malicious app on the same device intercepting a custom-scheme redirect, a code leaking through a referrer header or a shared proxy log), and that risk doesn't disappear just because the client also holds a secret; it just becomes a second independent layer. Tightened: redirect URI matching must be exact string comparison registered value to presented value, no wildcard or prefix matching, with a single narrow exception allowing the port to vary on loopback ("http://127.0.0.1:*") redirects for native apps that bind an ephemeral local port. Tightened: refresh tokens issued to public clients must be either sender-constrained (bound to the client via DPoP or mTLS, unit 09) or rotated on every use with reuse detection, because a public client can't be trusted to keep a long-lived bearer refresh token secret the way a confidential client with a real secret can.

"PKCE is for public clients that can't hold a secret" is only half the current answer, and giving only that half in a 2026 interview signals stale knowledge. Under OAuth 2.1, PKCE is required for every client on the authorization code grant — a server-side confidential client with a client secret still generates a code_verifier/code_challenge pair, because PKCE and client authentication defend against different attackers (code interception vs. impersonating the client at the token endpoint) and neither substitutes for the other.

That's precisely the interception scenario PKCE closes.

Why was the implicit grant removed instead of just "discouraged" as before?

Discouragement wasn't working — the grant was still in the spec, still implemented by every AS, and still the path of least resistance for anyone copying an old tutorial. Its failure mode (token in the URL fragment, in browser history, in the Referer header, with no client authentication at all) has no fix that preserves the grant's shape; the only way to actually retire the risk was to delete the option, which is exactly what a "best current practice" consolidation like 2.1 exists to do. The pattern to recognize: OAuth doesn't deprecate by adding a warning, it deprecates by removing the grant from the next spec revision.

Is ROPC ever legitimate in 2026?

Only as a time-boxed migration shim — e.g. an old client that already holds user passwords being ported to a new AS, using ROPC once to exchange stored credentials for tokens while the client is rewritten to use the code flow. It should never appear in new client code, and any AS you're evaluating that still advertises it as a first-class option for interactive login is a signal to look harder at the rest of its defaults.

What specifically does PKCE prevent, mechanically?

The client generates a random code_verifier, derives a code_challenge (its SHA-256 hash, base64url-encoded — S256, the only method 2.1 permits), and sends the challenge in the authorization request. The AS stores it alongside the issued code. At the token endpoint the client must present the original code_verifier; the AS re-derives the hash and compares. An attacker who intercepts only the authorization code (via a malicious app registering the same custom URI scheme, a leaked log line, a compromised network hop) cannot redeem it without the verifier, which never travels over the network until that final step.

Why must redirect URI matching be exact, with no wildcards?

A wildcard or prefix-matched redirect URI turns the authorization server into an open redirector for anything matching the pattern — an attacker registers or finds a path under the allowed prefix and the AS will happily send a fresh authorization code (or, historically, an implicit-grant token) to that attacker-controlled endpoint. Exact matching closes that off entirely; the one sanctioned exception (variable port on a loopback redirect) exists purely because native apps can't predict which ephemeral local port the OS will hand them, and loopback isn't reachable by a remote attacker anyway.

What is a "mix-up attack" and how does OAuth 2.1 guidance address it?

A mix-up attack targets a client talking to multiple authorization servers: the attacker tricks the client into sending a code or token intended for AS #1 to AS #2 (or a malicious AS impersonating one), by manipulating which endpoint the client believes it's talking to. The Security BCP folded into 2.1 mitigates it by requiring the AS to return its own iss (issuer) identifier alongside the authorization response, so the client can verify the response actually came from the AS it thinks it started the flow with, not just trust the redirect blindly.

Confidential vs public client — what's the actual dividing line, and why does it matter more than "web app vs mobile app"?

The dividing line is whether the client can keep a secret confidential from the end user and from anyone who can inspect the app's binary or bundle — not the platform. A server-side web app is confidential because its secret lives on a server the user never touches. A SPA, mobile app, or desktop app is public because any secret embedded in client-side code or a distributable binary can be extracted. This is why "just add a client secret to our SPA" is a non-fix people still propose in interviews: the secret is visible in the shipped JS bundle, so it authenticates nothing.

Why does OAuth 2.1 require rotation or sender-constraining for public clients' refresh tokens specifically?

A refresh token is long-lived and, if it's a plain bearer token, anyone who steals it (from local storage, a compromised device, a logged redirect) can use it indefinitely to mint fresh access tokens, indistinguishable from the legitimate client. Rotation means every use invalidates the old refresh token and issues a new one, so a stolen-then-reused token gets detected the moment both the attacker and the legitimate client try to use their (now divergent) copies — "refresh token reuse detection". Sender-constraining (DPoP or mTLS) instead binds the token to a specific private key the client holds, so possession of the token string alone isn't enough to use it. Confidential clients get a weaker requirement because the client secret already provides some of this binding.

How would you explain to a skeptical team lead why "OAuth 2.1" matters if it's still just a draft?

Because the draft doesn't invent new rules — it documents the rules every serious authorization server (Entra ID, Okta, Auth0, Duende) already enforces by default today, sourced from BCPs published years earlier. Waiting for the RFC number before adopting PKCE-everywhere or killing implicit grant usage in your own client code is backwards: the security community's practice already moved, the document is just catching up to give it one canonical name. Treat "2.1" as the name for "current OAuth security posture", not as a future feature to wait for.

What would you flag in a code review if you saw a new internal service using ROPC or the implicit grant?

For ROPC: ask why the client needs to see the password at all — it almost always means there's no real federation, someone is validating credentials against a local user store instead of delegating to the AS, and MFA/Conditional Access silently doesn't apply to this path. For implicit grant: check what's actually being extracted from the fragment and where it's stored; the fix is nearly always "move to authorization code + PKCE", and if the blocker was "our SPA has no backend to hold a secret", that's the cue to introduce a BFF (unit 05) rather than keep the token in the browser.

Client Credentials and Device Authorization grants survive into 2.1 unchanged — why did those not need hardening?

Client Credentials has no user and no redirect step at all — it's a direct, back-channel exchange of a client's own credentials for a token, so none of the vulnerabilities that motivated 2.1 (front-channel token exposure, redirect URI abuse, code interception) apply to it. Device Authorization is front-channel but never redirects — the device polls a token endpoint while the user authorizes on a separate, already-trusted device — so it sidesteps the same class of attack by construction rather than needing a patch.

03OpenID Connect: identity layered on OAuth

OpenID Connect (OIDC) is a thin, standardized identity layer on top of OAuth 2.0: same authorization endpoint, same token endpoint, same authorization code grant — plus a new token (the ID token), a new scope (openid) that requests it, a discovery document so clients don't need out-of-band configuration, and a small standard claim set so "who logged in, and how" means the same thing across every OIDC provider. Where an OAuth access token says "this bearer may call this API with these scopes" and is opaque-by-design to the client that requested it, an ID token says "this specific user authenticated, at this time, this way" and is meant to be read by the client itself. Mixing these two up — reading claims off an access token as if they were identity facts, or handing an ID token to an API expecting an access token — is the single most common OIDC bug in real codebases.

The ID token is always a JWT (unlike access tokens, which OIDC/OAuth never mandate a format for) and carries a fixed core: iss (the AS that issued it), sub (a stable, provider-scoped identifier for the user — never assume it's an email, emails change), aud (the requesting client's ID — not a resource server), exp/iat, and usually nonce, auth_time, acr (authentication context class — roughly "how strong was this login") and amr (authentication methods reference — e.g. ["pwd","mfa"]). nonce is the client-generated random value sent in the authorization request and echoed back inside the ID token; verifying it matches is what stops a replayed or substituted ID token from a previous session being accepted for a new one — skipping nonce validation is a real, exploitable gap, not pedantry.

Discovery removes almost all manual configuration: every conformant OIDC provider publishes /.well-known/openid-configuration — a JSON document listing the authorization, token, userinfo and JWKS (signing key) endpoints, supported scopes, response types, and signing algorithms. ASP.NET Core's AddOpenIdConnect fetches this once at startup (and refreshes it periodically) so you configure a client with an authority URL and a client ID/secret, not five hand-typed endpoint URLs that will silently rot when the provider rotates infrastructure.

The freshest wrinkle in 2026 is logout. OIDC originally offered front-channel logout: the relying party embeds each other logged-in RP's logout URL in a hidden iframe so the browser fires a logout request to each one when the user signs out anywhere. That pattern depends on third-party cookies working inside those iframes — and third-party cookies are now blocked by default in every major browser, so front-channel logout silently stops reaching RPs it used to reach. The direction of travel (and what current Entra ID and Duende guidance both push toward) is back-channel logout: the AS calls each RP's logout endpoint directly, server-to-server, with a signed logout token — no browser, no third-party cookie dependency, no reliance on an iframe actually loading. This is the same underlying force (third-party-cookie death) behind the 24-hour refresh-token lifetime Entra ID applies to SPA redirect URIs, covered in unit 09 — cookies quietly stopped being a reliable cross-context signal, and every spec in this space has been re-architected around that fact over the last few years.

Interview trap

"We validated the token, so we're secure" is meaningless without saying which token and against which audience. A shockingly common bug: an API accepts any JWT whose signature checks out, without pinning aud to itself — which means a perfectly valid ID token issued to a completely different client (or an access token scoped for a completely different API) sails through. Signature validity proves the AS issued the token; aud validation proves it was issued for this recipient. Skipping the second half turns every token from the same tenant into a skeleton key.

Try it
  1. Complete a real login against any OIDC provider you have access to, capture the ID token, and decode it by hand (base64url-decode the middle segment). Cross off which claims are OIDC-standard vs provider-specific extensions.
  2. Take the access token from the same login and try to call the provider's UserInfo endpoint with it. Compare what UserInfo returns to what was already in the ID token.
Expected outcome

(1) iss, sub, aud, exp, iat, nonce are OIDC-standard; things like tid (tenant id), roles, or custom claims are provider extensions layered on top. (2) UserInfo typically returns a superset of profile claims (matching whatever scopes — profile, email — were granted) but is fetched fresh per call rather than cached in a token, which is why it's the right place to look for claims that can change between logins (like a display name), while the ID token is a frozen snapshot of the login event itself.

What does OpenID Connect add to OAuth 2.0 that OAuth alone genuinely cannot provide?

OAuth alone has no standard way to answer "who is this" — an access token is deliberately opaque to the client and carries no mandated identity claims. OIDC adds the ID token (a JWT with a fixed identity claim set), the openid scope that requests it, the UserInfo endpoint for richer profile data, and discovery/session-management conventions so every provider exposes identity the same way. Without OIDC, "login with X" implementations were bespoke per provider — which is exactly the fragmented state OAuth 1.0-era "social login" was in before OIDC standardized it.

Why is sub the identifier you should key user records on, not email?

sub is defined by the spec to be stable and unique within the issuer for the lifetime of the account; email addresses get changed, reassigned, or shared with an alias, and using email as a primary key silently merges or orphans accounts when that happens. sub is also scoped per client for some providers ("pairwise" subject identifiers) specifically to prevent correlating a user across unrelated relying parties — another reason to treat it as an opaque key, not a human-readable one.

What is nonce actually defending against, concretely?

Without a nonce, an attacker who can get an old, previously-valid ID token (e.g. from a stale cached response, a replayed request, or a token bound to a different session) could resubmit it and have the client accept it as proof of a fresh login. The client generates a fresh random nonce per authorization request and checks the ID token echoes exactly that value; a replayed token from a different flow won't carry the current nonce and gets rejected. It's the ID-token analogue of a CSRF token — single-use, request-bound, and useless once consumed.

What are acr and amr for, and where would you actually use them?

amr lists the actual methods used (password, OTP, hardware key, biometric); acr is a coarser, provider-defined "assurance level" label. A step-up authorization check for a sensitive action — approving a large payment, say — reads these claims to decide "was this login strong enough for what's being requested," and if not, triggers a fresh, stronger authentication rather than trusting a login that happened under weaker conditions minutes or hours earlier. This is the mechanism behind "step-up MFA" (unit 10), not a separate protocol.

Why did front-channel logout stop being reliable, and what replaced it?

Front-channel logout relies on the browser loading each relying party's logout endpoint inside a hidden iframe with that RP's own session cookie attached — which requires third-party cookies to work in an iframe context. Browsers now block third-party cookies by default, so those iframe requests frequently can't see the RP's session at all, and logout silently fails to propagate to some apps. Back-channel logout replaces the iframe dance with a direct server-to-server call: the AS POSTs a signed logout token straight to each RP's back-channel logout endpoint, with no browser and no cookie dependency in the path at all.

Your API receives what looks like a valid JWT with a correct signature. What else must it check before trusting it, and why isn't signature validation alone enough?

Signature validation proves the token was issued by a key the AS controls and hasn't been tampered with — it says nothing about who the token was issued to or for. The API must also check iss (issued by the AS I actually trust, not a lookalike), aud (issued for me specifically, not some other client or API), exp/nbf (currently valid), and ideally the signing algorithm itself (reject alg: none and reject unexpected algorithm families — see unit 04's "alg confusion" trap). Any one of these skipped turns "valid signature" into "valid signature on a token meant for someone else."

Should a client send its ID token to a backend API to authenticate API calls?

No — an ID token's audience is the client itself, not any API, and a well-behaved API should reject an ID token presented as a bearer credential precisely because its aud won't match the API. The client should request an access token scoped for that specific API (a separate token, possibly from a separate token request or via token exchange) and send that instead. Conflating the two is usually a sign the app never went through a proper scope/audience design and is just passing around "whatever JWT I happen to have."

What does the discovery document actually buy you operationally, beyond convenience at startup?

It means your app never hard-codes signing keys or endpoint URLs that the AS might legitimately rotate — the JWKS URI in the discovery document is itself fetched dynamically, so a key rollover on the AS side (unit 04) requires zero client-side deployment. It's also the reason federation metadata drift ("the login URL changed and now everyone's broken") is rare with OIDC compared to older, statically-configured SAML setups: the contract is "trust this authority URL," not "trust these five URLs I copy-pasted once."

How would you explain the relationship between OAuth and OIDC to someone who insists "OAuth is for login"?

OAuth is for delegated access — it was built so a photo-printing app could get permission to read your photos from another service, with no concept of "identity" baked in. "Login with X" only became possible, standardized, and safe because OIDC added an identity layer on top: a token specifically about the authentication event, with a fixed claim set every provider agrees on. If someone built "login" directly on bare OAuth (reading arbitrary API responses as a proxy for identity, which is exactly what many early "social login" integrations did), that's the fragile, non-standard pattern OIDC was created to replace.

What's the risk of an app that never validates aud on incoming tokens, in a multi-tenant or multi-client environment specifically?

Any token issued by the same authorization server — regardless of which client or which tenant it was meant for — becomes acceptable to that API. In a multi-tenant SaaS this is especially dangerous: a token minted for Tenant A's client could be replayed against an API instance serving Tenant B if audience (and often tenant claim) checks are missing, turning a scoping bug into a cross-tenant data leak. This is exactly the class of bug security reviews for multi-tenant Entra ID apps focus on first.

04JWTs: structure, signing, and validation

A JWT is three base64url segments joined by dots: header.payload.signature. The header names the signing algorithm and (usually) a key ID; the payload is a JSON object of claims; the signature covers header+payload so any change to either invalidates it. Crucially, base64url is encoding, not encryption — anyone can decode a JWT's header and payload with no key at all, they just can't produce a valid signature over modified content without the signing key. "The token is a JWT" therefore says nothing about confidentiality; if a payload must be unreadable to whoever holds the token (rare for access/ID tokens, more relevant for tokens carrying sensitive PII), you need JWE (an encrypted JWT), not JWS (a signed one) — and "JWT" in everyday conversation almost always means JWS.

Signing comes in two families with very different trust implications. Symmetric (HS256/HMAC-SHA256): one shared secret both signs and verifies. Fast, simple, and wrong the moment signer and verifier aren't equally trusted — if a browser-held SPA and a backend API "share" an HS256 secret, the SPA effectively holds a key that can forge tokens, because verifying and signing use the identical key. Asymmetric (RS256/RSA or ES256/ECDSA): a private key signs, a public key verifies. This is what every real OAuth/OIDC deployment uses for tokens that cross a trust boundary — the resource server only ever needs the AS's public key (fetched from the JWKS endpoint) to verify tokens; it can never forge one, because it never holds the private key. If an interview asks "when would you use HS256 for OAuth tokens," the honest answer is "essentially never, once more than one untrusted party needs to verify."

The historical vulnerability that every serious library now defends against by default is algorithm confusion: a verifier that trusts the alg value written inside the untrusted token itself, rather than pinning an expected algorithm server-side. Two concrete exploits followed from this: switching a token's alg to none (some early libraries would then skip signature checking entirely), or switching an RS256 token to HS256 and using the AS's known public RSA key — a value that's deliberately public — as the HMAC secret, which a naive verifier happily accepts because it just looks up "the key" without checking it's the right type of key for the claimed algorithm. The fix, and the thing to actually name in an interview, is that validation must specify an explicit, server-controlled allow-list of acceptable algorithms and reject anything else outright — never branch validation logic on what the token claims about itself.

Key rotation is what makes long-lived deployments safe without downtime: every signing key gets a kid (key ID) in the JWT header, and the AS publishes its current (and often next) public keys at a JWKS URI, discoverable via the OIDC discovery document. A verifier looks up the matching key by kid at validation time instead of hard-coding one key — so an AS can rotate its signing key on a schedule, publish the new public key ahead of the switch, and old still-valid tokens signed with the previous key keep verifying until they naturally expire, with zero client redeploys. On the .NET side, Microsoft.IdentityModel.JsonWebTokens.JsonWebTokenHandler is now the modern default token handler behind AddJwtBearer (faster and lower-allocation than the older System.IdentityModel.Tokens.Jwt.JwtSecurityTokenHandler, which still exists for compatibility) — worth knowing the name exists even if you never touch it directly, because it's what actually executes every TokenValidationParameters check under the hood.

Interview trap

"We use JWTs, so we can validate tokens without hitting the database" is true only for signature/expiry checks — it says nothing about revocation. A self-contained JWT is valid, by definition, until it expires; there's no built-in way to invalidate one early short of maintaining a deny-list (which reintroduces the state lookup JWTs were meant to avoid) or keeping access token lifetimes short and relying on refresh-token revocation instead (unit 09). Candidates who say "just delete the JWT server-side" are describing a session token, not a JWT.

Try it
  1. Take any JWT (from a real login or a sample), decode header and payload by hand without a library, then flip one character in the payload's role claim and re-encode it. Feed the modified token to a real verifier and confirm exactly which check fails.
  2. Look up your AS's JWKS endpoint (usually /.well-known/jwks.json off the discovery document) and match a token's kid header to one of the published keys by hand.
Expected outcome

(1) The verifier rejects it with a signature-mismatch error — changing even one payload byte changes the bytes the signature was computed over, so the signature no longer matches under the real key. This is the concrete, hands-on proof that a JWT's integrity guarantee is real and not just "hard to read." (2) You should find the exact public key (by kid) the token was signed with; if the AS is mid-rotation you may see two keys published simultaneously — the old one still verifying not-yet-expired tokens, the new one already signing fresh ones.

Someone says "JWTs are encrypted so they're safe to put anything in." What's wrong with that sentence?

Standard JWTs (JWS) are signed, not encrypted — the payload is plainly readable by anyone who has the token, including the end user's own browser dev tools. "Safe" here can only mean tamper-evident, not confidential. Never put secrets, unhashed PII beyond what's necessary, or anything you wouldn't want the token bearer to read in a JWT payload; if genuine confidentiality is required, that's what JWE is for, and it's rare in access/ID tokens specifically because the client and resource server are usually the intended readers anyway.

Why is pinning the expected algorithm on the verifier side non-negotiable, rather than just trusting the token's alg header?

The alg header is attacker-controlled input — it's inside the very token you haven't verified yet. A verifier that branches its validation logic based on that header (e.g. "if alg says HS256, verify with this secret; if RS256, verify with that public key") lets an attacker choose which check runs, and the classic exploit swaps a public verification key into the role of an HMAC secret. The safe pattern hard-codes, server-side, exactly which algorithm(s) are acceptable for this token type and rejects everything else before even looking at what the token itself claims.

What's the actual, mechanical difference between JWS and JWE, and which one is "a JWT" in everyday usage?

JWS (JSON Web Signature) produces the familiar three-segment, signed-but-readable token — this is what people mean 95% of the time they say "JWT." JWE (JSON Web Encryption) produces a five-segment structure where the payload itself is encrypted, not just signed, so a party without the decryption key can't read the claims at all, only verify (if nested) that it came from the right issuer. JWE shows up mainly when a token must pass through an untrusted intermediary that shouldn't be able to read its contents, which is uncommon for typical access/ID tokens flowing directly between a known client and a known resource server.

Why does the JWKS + kid mechanism matter operationally, beyond "it lets you rotate keys"?

It decouples key rotation from client deployment entirely. Without it, rotating a signing key means every relying party needs a coordinated config update at the exact moment of rotation, which is exactly the kind of multi-team synchronized change that causes outages. With JWKS, the AS publishes the new key before switching to it, every verifier is already fetching keys dynamically by kid, and the rotation is invisible to anyone except the AS operator — no client-side change, no downtime window to coordinate.

What is the default ClockSkew in ASP.NET Core's JWT validation, and why would a lead care?

Five minutes, applied on both sides of the token's validity window — meaning a token can still validate up to five minutes after its stated exp, and be accepted up to five minutes before its stated nbf/iat. This exists to absorb ordinary clock drift between the AS and resource server, but it also means "the token should have expired 3 minutes ago" is not a bug if it still validates — and conversely, a security requirement for very tight token lifetimes (say, 60-second access tokens for a high-risk operation) needs an explicitly reduced ClockSkew, or the effective lifetime is longer than the nominal one by up to 10 minutes total.

What's the difference between a self-contained (JWT) access token and an opaque/reference access token, and when would you deliberately choose the opaque one?

A self-contained JWT carries its own claims and can be validated by the resource server with no network call — fast, but effectively impossible to revoke early without a deny-list. An opaque token is a random string that means nothing on its own; the resource server (or a gateway) calls the AS's introspection endpoint to resolve it into claims and a live validity status. You'd choose opaque when instant, guaranteed revocation matters more than validation latency — e.g. Duende IdentityServer's "reference tokens," or MS Graph's own access tokens, which are opaque by design so Microsoft can revoke or reshape them without every client parsing a stable format.

Why shouldn't you decode a JWT client-side and trust its claims to make an authorization decision, even if you never modify it?

Decoding without verifying tells you what the token claims, not what's actually true — you have no idea if the signature is valid, if it's expired, or if it was even issued by the party you think issued it, unless you run it through real validation. This matters in practice: a frontend reading a JWT's claims to decide what UI to render is fine (it's a UX shortcut, the real enforcement is server-side), but any authorization-relevant decision made purely from a decoded-not-verified token — including inside your own backend, if a developer reaches for a quick "just base64-decode it" helper instead of the validation pipeline — is a live vulnerability.

How would you explain "the JWT is stateless" to someone who thinks that means "the JWT can't be revoked, full stop"?

Stateless means the resource server doesn't need a database lookup to validate the token's integrity and freshness claims — the token carries everything needed for that check. It does not mean revocation is impossible; it means revocation has to happen at a different layer than "check the token itself." In practice that's short access-token lifetimes plus revocable refresh tokens (unit 09), or a deny-list checked at the gateway, or switching to opaque tokens for the specific APIs that need instant revocation. "Stateless" is a property of validation, not a ban on ever changing your mind about a token.

What would you look for in a code review of a hand-rolled JWT verification routine (instead of using a library)?

Whether it pins the algorithm server-side rather than reading alg from the token; whether it checks iss, aud, and exp/nbf at all (not just the signature); whether the signing-key lookup is keyed correctly by kid against a real, dynamically-refreshed key set rather than one hard-coded key; and — the fastest way to end the review — whether there's a good reason not to delete the hand-rolled code and use Microsoft.IdentityModel or an equivalent vetted library instead. Token validation is exactly the kind of security-critical, subtly-wrong-in-non-obvious-ways code that shouldn't be reinvented per project.

Two microservices need to trust each other's JWTs. What's the trade-off between them sharing one signing authority vs. each running its own?

One shared authority (a single AS or a shared JWKS) means every service verifies with the same public keys and trusts the same issuer — simpler operationally, and the natural choice inside one organizational trust boundary. Separate authorities per service means each verifies only its own issuer and explicitly maps trust relationships between services (issuer allow-lists, token exchange) — more setup, but it contains a compromise: a leaked signing key or a misconfigured claim in one service's tokens doesn't automatically grant trust everywhere else. Principal-level judgment here is about blast radius, not raw simplicity.

05Session models: JWT vs cookies, and the BFF pattern

"JWT vs cookies" is a slightly wrong framing — the real question is where does the token live, and what can touch it. A traditional server-rendered app uses a cookie holding an opaque session ID; the server looks up session state on every request, and the token itself carries no information. A pure SPA calling an API directly often does the opposite: it gets a real OAuth access token (often a JWT) and attaches it as Authorization: Bearer … from JavaScript. Both are valid architectures for the right context, and both have a specific, well-known failure mode: a cookie-based session is exposed to CSRF (the browser attaches cookies automatically to requests from any origin, so a malicious page can trigger authenticated actions without ever reading the cookie); a token held in JS-reachable storage (a JS variable, localStorage, sessionStorage) is exposed to XSS (any script injected into the page — via a dependency, a stored XSS bug, a compromised CDN — can simply read and exfiltrate the token, full stop).

The asymmetry matters: CSRF is well-mitigated by SameSite=Lax/Strict cookies plus a standard anti-forgery token, and the residual risk is one forged action per successful attack. XSS-driven token theft, once it happens, hands the attacker the actual bearer credential — they don't need to keep exploiting the page; they replay the stolen token from anywhere, for as long as it's valid. That's why "we moved off cookies to avoid CSRF, so we put the JWT in localStorage" is a regression, not a fix — it traded a well-mitigated, moderate-impact risk for a poorly-mitigated, severe one. There is no browser storage location reachable by your app's own JavaScript that isn't also reachable by an attacker's JavaScript, if they get any injection at all.

The pattern that resolves this without giving up a SPA/mobile-friendly architecture is the Backend-For-Frontend (BFF): the browser holds only an ordinary HttpOnly, Secure, SameSite session cookie — never a real OAuth token, never anything JS can read. A same-origin server component (the BFF) is the actual OAuth client: it performs the authorization code + PKCE flow, holds the resulting access and refresh tokens entirely server-side, and on each browser request swaps the session cookie for the real token before proxying the call on to the API. The SPA gets to feel like it's "just calling an API," but the only thing ever exposed to browser-side script is a cookie that carries no bearer value of its own. This is now the default advice, not an edge case — it's the pattern Microsoft's own guidance and library work (the ASP.NET Core YARP reverse proxy combined with cookie auth, or Duende's dedicated BFF package) target explicitly, it's what Auth0 and Okta both ship starter templates for, and it's the outcome the OAuth working group's browser-based-apps guidance (folded into the 2.1 effort) converges on: a "pure SPA as OAuth public client, holding its own tokens" is now explicitly the discouraged shape, not the default one, for anything beyond a quick demo.

Why is XSS-driven token theft categorically worse than a typical CSRF exploit?

CSRF lets an attacker trigger one action using the victim's ambient session, blind — they can't read the response, and the blast radius is whatever that one forged request can do. Stealing a bearer token via XSS hands the attacker the actual credential: they can replay it from their own infrastructure, for its full remaining lifetime, making arbitrary calls with the victim's full privileges and reading every response. One is a single forced action; the other is a portable copy of the user's session.

What does HttpOnly actually do, and what does it not protect against?

HttpOnly makes a cookie invisible to document.cookie and any JS running on the page — it stops token theft via XSS reading the cookie directly. It does nothing about CSRF, because the browser still automatically attaches the cookie to requests regardless of which page triggered them; HttpOnly and SameSite defend against two different attacks and you need both (plus anti-forgery tokens for state-changing requests) for a cookie-based session to be genuinely safe.

Concretely, what problem does the BFF pattern solve that a well-configured cookie session alone doesn't?

A plain cookie session works great when the browser only ever talks to one server-rendered app. It breaks down the moment that app needs to call a separate API (possibly cross-origin, possibly one it doesn't own) using OAuth tokens — now something has to hold and refresh those real tokens, and "something" can't safely be the browser. The BFF is that something: it's the actual OAuth client, the browser never becomes one, and the browser keeps the same simple cookie-session relationship with the BFF regardless of how many downstream APIs the BFF talks to on the user's behalf.

If BFF is now the recommended default, why did "SPA holds its own tokens" become common practice in the first place?

It followed naturally from OAuth's public-client model (unit 02) once mobile and SPA apps needed delegated access without a backend of their own to hold a secret — PKCE made that pattern cryptographically sound for the code-interception threat it targeted, and it genuinely works for many mobile and desktop apps that have no shared, JS-accessible execution context an attacker can inject into. The gap specifically for browser apps is that the "client" and the "attacker's injection point," if XSS ever occurs, are the same execution context — a risk mobile apps' OS-level sandboxing doesn't share to the same degree.

Does the BFF pattern eliminate the need for CSRF defenses?

No — the browser-to-BFF leg is still cookie-based, so it still needs SameSite plus anti-forgery tokens on state-changing requests, exactly like any cookie-session app. What BFF removes is the token-theft-via-XSS risk, by never letting a real bearer token reach the browser at all. CSRF and XSS are separate problems with separate defenses; BFF is specifically an answer to the second one for the token itself, not a replacement for the first.

How would you migrate an existing SPA that stores its access token in localStorage to a BFF architecture, and what's the hardest part?

Introduce a same-origin backend (or a reverse-proxy layer like YARP) that becomes the OAuth client, move the authorization code + PKCE flow entirely server-side, replace the SPA's token storage with a same-origin cookie session, and rewrite API calls to go through the BFF's proxy routes instead of hitting the API origin directly with a bearer header. The hardest part in practice is usually CORS and deployment topology — the SPA and BFF need to be same-origin (or the cookie needs careful SameSite/domain configuration) for the whole scheme to avoid reintroducing cross-site cookie problems, which sometimes forces a hosting or routing change, not just a code change.

Native mobile apps also can't hold a client secret — why don't they need a BFF the way browser SPAs do?

A mobile OS gives each app its own sandboxed storage and process; there's no equivalent of "any script on this page can read anything any other script put there," which is exactly the shared-execution-context risk that makes browser-held tokens dangerous. A malicious app on the same device generally can't read another app's secure storage (Keychain/Keystore) the way an XSS payload can read anything in the same page's JS context. Mobile still uses PKCE and short-lived tokens for other reasons (interception during the redirect, device compromise), but the specific "my own execution context is also the attacker's" problem doesn't apply the same way.

What would you flag in a security review of a new SPA that says "we don't have CSRF risk because we use bearer tokens, not cookies"?

That statement is locally true but incomplete — ask where the bearer token is stored and how it got there. If it's in localStorage/sessionStorage or a JS-reachable variable, the app has traded a mitigated risk (CSRF) for a much more severe, often less-defended one (XSS-driven full token theft), and that trade should be made consciously, not by default. The review should also check whether the app even needs to be a public OAuth client at all, or whether a BFF would remove the trade-off entirely.

Why does the OAuth working group's browser-based-apps guidance specifically call out SPAs, when the same logic seems to apply to any JS running in a browser?

Because SPAs are exactly the architecture that historically pushed people toward treating the browser as a first-class, credential-holding OAuth client — a server-rendered app never faced this choice, since it never needed the browser to hold a token in the first place. The guidance targets SPAs because that's where the anti-pattern actually gets built, not because the underlying browser risk is unique to any one framework.

Give a scenario where a lead engineer would deliberately choose a plain bearer-token SPA over a BFF, despite the guidance above.

A short-lived internal tool with a small, trusted user base, no third-party script dependencies (so XSS surface is minimal and audited), where standing up and operating an additional backend component is a genuinely disproportionate cost relative to the risk — e.g. an internal admin dashboard behind a VPN, built and maintained by the same team that owns the API. Even then, the honest framing is "we accepted this risk consciously, here's why," not "this risk doesn't apply to us" — and the moment the app grows a public surface, third-party dependencies, or a larger blast radius, the calculus flips.

06ASP.NET Core authentication: schemes and handlers

Unit 01 introduced schemes as "a name bound to a handler plus options." This unit is about what the handler actually does, because "just call AddJwtBearer" hides a machine worth understanding when something breaks. Every authentication handler implements (directly or through a base class) a common contract: AuthenticateAsync (inspect the request, produce an AuthenticateResult — success with a ClaimsPrincipal, "no result" meaning this handler has no opinion, or failure with a reason), ChallengeAsync (react to "you need to prove who you are" — redirect to a login page for cookies, emit a WWW-Authenticate header for bearer schemes), and ForbidAsync (react to "you're known but not allowed" — usually just a 403, though some handlers customize this). [Authorize] and the authorization middleware never call handler methods directly; they go through IAuthenticationService, which resolves the right handler(s) by scheme name and delegates.

Handlers split into two practical families. Local/stateless handlers (cookie, JWT bearer) validate the request entirely against something already present — a signed cookie, a signed token — with no outbound network call during authentication itself (JWT bearer may have already fetched JWKS at startup/on a refresh timer, but that's decoupled from the per-request path). Remote handlers — everything built on RemoteAuthenticationHandler<TOptions>, which is what AddOpenIdConnect, AddOAuth, and social-login handlers all derive from — involve a redirect away from your app to an external authorization endpoint and back. A remote handler's AuthenticateAsync doesn't authenticate the *current* request at all; it reads the result of a *previous* redirect round-trip (via a correlation cookie and callback path) and, on success, signs the user into a *local* scheme (typically cookies) so that subsequent requests are handled by a local handler instead of repeating the remote round-trip on every single page load. This is why an OIDC setup always pairs AddCookie() with AddOpenIdConnect() — OIDC is the one-time login mechanism, cookies are what actually carries the session afterward.

Signing in and out are explicit, first-class operations, not side effects of validation: HttpContext.SignInAsync(scheme, principal) asks a handler to persist an identity (a cookie handler writes the encrypted cookie; a remote handler generally doesn't implement this meaningfully on its own scheme, since it delegates to a local one), and SignOutAsync(scheme) asks it to clear that persisted state. This is the actual mechanism behind "log out of everything": a typical OIDC + cookie setup signs out of both the local cookie scheme (clearing your own session) and the remote OIDC scheme (which triggers a round-trip to the AS's own logout endpoint, ending the AS-side session too) — skipping the second half is the classic bug where a user clicks "log out," the app's session ends, but the AS still considers them logged in, so the next login silently re-authenticates with no credential prompt.

One thing worth knowing by name rather than by magic: AuthenticationHandler<TOptions>'s HandleAuthenticateAsync result is cached per-request the first time any code asks — calling AuthenticateAsync for the same scheme twice in one request doesn't re-run validation twice. This matters when debugging "why did my custom middleware's manual AuthenticateAsync call seem to have no effect the second time" — it didn't need to; the result was already cached and reused.

{
    protected override async Task<AuthenticateResult> HandleAuthenticateAsync()
    {

            return AuthenticateResult.NoResult();               // "I have no opinion" — let other schemes try

        var ticket = new AuthenticationTicket(principal, Scheme.Name);
        return AuthenticateResult.Success(ticket);
    }

    {
        Response.StatusCode = StatusCodes.Status401Unauthorized;
        Response.Headers.WWWAuthenticate = "ApiKey";
        return Task.CompletedTask;
    }

Interview trap

"We call SignOutAsync so the user is logged out" is incomplete in any app that pairs a remote scheme (OIDC) with a local one (cookie) — you must sign out of both named schemes, and in the right order, or you get a local logout with a still-live AS session. A common wrong fix people ship: await HttpContext.SignOutAsync() with no scheme argument, relying on a default that may only clear one of the two. The correct call is explicit about both scheme names, and for OIDC specifically often needs a post-logout redirect URI configured on the AS side too.

Try it
  1. Wire up cookie + OpenID Connect in a throwaway app, log in, then call SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme) only. Try logging in again and observe whether you get a credential prompt.
  2. Write a custom handler's HandleAuthenticateAsync that returns AuthenticateResult.NoResult() and register it alongside JWT bearer with a policy scheme that tries yours first. Confirm the request falls through to JWT bearer instead of failing outright.
Expected outcome

(1) You'll typically be silently re-authenticated with no prompt — the AS still has an active session cookie of its own, so the OIDC redirect round-trip completes instantly without the user ever seeing a login form, which is the "logged out of the app but not really" bug in miniature. (2) NoResult() is explicitly the "not my problem, try someone else" signal — distinct from Fail(), which says "I looked, and this credential is bad." A policy or fallback scheme correctly treats these two differently.

What's the practical difference between AuthenticateResult.NoResult() and AuthenticateResult.Fail(...)?

NoResult() means the handler found nothing relevant to itself in the request (no cookie present, no bearer header at all) and defers — a policy scheme or a chain of schemes should keep looking elsewhere. Fail() means the handler found something meant for it and it was invalid (expired token, bad signature, tampered cookie) — that's a definite negative, not a "maybe someone else knows." Conflating them in a custom handler breaks multi-scheme setups, because a wrongly-returned Fail() can stop a fallback chain that should have kept trying other schemes.

Why does OpenID Connect need a cookie scheme at all — why can't the app just re-run the OIDC redirect on every request?

Because the whole point of a redirect-based login is that it's expensive and interactive — the user leaves your app, authenticates at the AS, and comes back. Doing that per request would mean every page load bounces the user through the AS, which defeats the purpose of "being logged in." The remote scheme's job is exactly one thing: run that round-trip once, then hand off to a local scheme (the cookie) that can cheaply re-authenticate the user on every subsequent request without leaving the app.

What actually gets stored inside the authentication cookie when options.SaveTokens = true is set on an OIDC handler?

The cookie's encrypted payload (the AuthenticationTicket) includes the tokens returned from the AS — ID token, access token, refresh token if issued — alongside the claims principal, stored as authentication properties. This is how a later request can retrieve the access token via HttpContext.GetTokenAsync("access_token") to call a downstream API (exactly the BFF pattern from unit 05) without a second round-trip to the AS. The trade-off is cookie size — a large ID token plus a large access token can push the cookie close to browser header-size limits, which is one real reason some setups switch to a server-side ticket store instead of an in-cookie one.

How would you add a scheme that accepts either a cookie or a bearer token on the same endpoint, and why not just list both scheme names in [Authorize(AuthenticationSchemes = "Cookie,Bearer")]?

Listing both scheme names in AuthenticationSchemes does work for simple cases — ASP.NET Core will try each listed scheme and succeed if any one does — but it means every endpoint that needs this dual behavior has to repeat the list, and the actual selection logic (should we even try cookie auth for an API-only client?) isn't visible in one place. A policy scheme centralizes that decision: register one scheme whose handler inspects the request (is there an Authorization header? a specific path prefix?) and forwards to exactly the right concrete scheme, then reference just that one policy scheme name everywhere. It's a maintainability choice, not a functional requirement for simple cases.

Why is per-request handler-result caching relevant to a bug where a custom middleware's manual authentication check "doesn't seem to run twice"?

AuthenticationHandler<TOptions> caches its own AuthenticateAsync result for the duration of the request the first time anything invokes it — by design, since re-validating a token or re-decrypting a cookie on every single call within one request would be wasteful. If a developer expects a second manual call to "re-check" something that changed mid-request (e.g. a claim mutated by earlier middleware), they'll get the cached, stale result instead — the fix is either to work with the already-authenticated principal directly rather than re-authenticating, or to explicitly sign in a new principal if state genuinely changed.

What's the difference between what happens on ChallengeAsync for a cookie scheme versus a JWT bearer scheme, and why does that matter for an API that's accidentally using the cookie scheme as its default?

A cookie scheme's challenge is a 302 redirect to a login page — appropriate for a browser, useless for a JSON API client, which will follow the redirect (or, more likely, choke on receiving HTML where it expected JSON) instead of getting a clean 401 it can branch on. If an API accidentally ends up authenticated by the cookie scheme's default challenge (a common misconfiguration when DefaultChallengeScheme isn't set explicitly per area), API clients start seeing confusing redirect responses instead of a bearer challenge — a classic symptom that scheme selection wasn't pinned per endpoint.

Explain what "signing out of the remote scheme" actually does over the wire, for OIDC.

SignOutAsync("oidc-scheme-name") triggers the OIDC handler's remote sign-out behavior: it redirects the browser to the AS's end-session endpoint (from the discovery document), typically passing an id_token_hint and a post-logout redirect URI. The AS clears its own session (its login cookie, any SSO state) and then redirects the browser back to your app. Without this call, your app's local session ends but the AS's session doesn't — leading to the "logged out but instantly re-logged-in" behavior described above.

If you're building a health-check or metrics endpoint that must never trigger a login redirect, what's the correct way to exempt it?

Don't rely on it "just not having [Authorize]" if the app's authorization is configured with a fallback policy requiring authentication globally (a common hardening pattern via options.FallbackPolicy). Explicitly mark the endpoint with .AllowAnonymous() (or [AllowAnonymous]) so it's excluded regardless of global defaults — that's the one attribute/method specifically designed to override a broader authorization requirement for a named endpoint, rather than depending on absence of configuration.

Two teams disagree: one wants every API endpoint to use JWT bearer only; another wants to also accept the app's own session cookie so their internal admin UI can call the same API directly. What questions would you ask before picking a design?

Whether the admin UI genuinely needs to call the exact same API surface as external/mobile clients, or whether a thin BFF-style proxy (unit 05) that holds the real bearer token server-side and forwards on behalf of the cookie session is a better fit — accepting cookies directly on a public-facing API reintroduces CSRF exposure for every endpoint that now accepts cookie auth, which a pure-bearer API never had to think about. If the two client types truly need direct API access, a policy scheme picking cookie-vs-bearer per request is the mechanism, but the CSRF conversation (anti-forgery tokens on the cookie-authenticated paths specifically) has to happen alongside it, not after.

What would you check first if a newly added authentication scheme seems to have "broken" an existing, unrelated scheme that was working fine before?

Whether adding the second scheme silently removed the single-scheme auto-default-scheme promotion (unit 01) that the first scheme had been implicitly relying on — this is one of the most common "I added scheme #2 and now scheme #1's endpoints 401 unexpectedly" bugs. The fix is to set DefaultScheme (and, if needed, DefaultChallengeScheme/DefaultAuthenticateScheme) explicitly the moment a second scheme is registered, rather than continuing to rely on a convenience default that only applied when exactly one scheme existed.

07ASP.NET Core authorization: policies, roles, and claims

The weakest authorization design is a scatter of if (user.IsInRole("Admin")) checks across controllers — it works until the rule needs a second condition ("Admin, but only for their own tenant"), at which point every call site needs the same fix, applied consistently, forever. ASP.NET Core's policy system exists to make the rule live in exactly one place: a named policy is a collection of requirements, each evaluated by a handler that inspects the current ClaimsPrincipal (and optionally the resource being accessed) and votes to succeed, fail, or abstain. RequireRole and RequireClaim are just pre-built requirements for the common cases; nothing stops you from writing a custom requirement/handler pair for anything more specific — "the caller's tenant claim matches this resource's tenant," "the caller's acr claim indicates MFA," "it's currently business hours in the caller's region."

Role-based (RBAC) and claims-based authorization aren't actually different systems — a role is just a claim with the well-known type ClaimTypes.Role, and RequireRole("Admin") compiles down to a claim check under the hood. The real design axis is granularity: roles model "what kind of user is this" (coarse, small, stable set — Admin, Member, Guest), while arbitrary claims model "what specific fact about this principal or their grant matters here" (fine-grained, can be numerous, can vary per token — a scope, a tenant ID, a subscription tier, a feature flag). A system that only has roles eventually grows roles like AdminButOnlyForBillingAndOnlyOnTuesdays as a workaround for needing finer distinctions; the fix isn't more roles, it's moving the finer distinction into claims and writing a requirement that reads them.

Resource-based authorization is the piece people skip until they need it and then reinvent badly: some decisions can't be made from the principal alone, because they depend on the specific object being acted on — "can this user edit this order" requires looking at the order's owner, not just the caller's role. IAuthorizationService.AuthorizeAsync(user, resource, policyName) takes the resource as a parameter specifically so a requirement handler can compare, say, resource.OwnerId against a claim on user. Doing this check manually and inline ("if user.Id != order.OwnerId, return Forbid()") works for one call site and then drifts the moment a second endpoint needs the identical rule with a slightly different bug.

AddAuthorizationBuilder() (the modern, chainable registration API — replacing the older services.AddAuthorization(options => options.AddPolicy(...)) callback style, though both still work) plus RequireAuthorization() on minimal API route groups is the current idiomatic shape for wiring all of this without repeating scheme/policy names across dozens of individual endpoint calls: define policies once at startup, group related endpoints, and apply a policy to the whole group in one line.

Interview trap

"We use role-based access control" is often said as if it's a complete answer, when the actual follow-up — "how do you handle a rule that depends on the specific resource, not just the user's role" — reveals whether the candidate has ever needed resource-based authorization at all. A shop that's only ever built "is Admin / is not Admin" checks hasn't hit the harder, far more common enterprise case: "can this specific manager approve this specific expense report," which needs the resource in the decision, not just the caller's role.

Try it
  1. Write a policy with two requirements that both must succeed (e.g. role "Manager" AND a custom "same department" requirement), and one where either of two requirements succeeding is enough. Confirm ASP.NET Core's actual combination semantics for each shape.
  2. Write an authorization handler that calls context.Fail() explicitly rather than simply not calling Succeed(). Trigger a scenario where another handler for the same requirement type would have voted yes, and observe the outcome.
Expected outcome

(1) Multiple requirements added to one policy are AND'd — all must succeed. To get OR semantics between two conditions, you typically write a single custom requirement/handler that internally checks "condition A or condition B," rather than relying on adding two separate requirements and hoping for OR. (2) An explicit Fail() is a hard veto: even if every other handler for that requirement type would Succeed(), one Fail() call makes the overall requirement fail — this is intentional and is exactly the mechanism for "deny always wins," which is why Fail() should be reserved for genuine hard-stop conditions, not casually.

Is a "role" fundamentally different from a "claim" in ASP.NET Core's model, or just a convention?

Just a convention — a role is a claim whose Type is the well-known ClaimTypes.Role (or whatever the app's RoleClaimType is configured to), and User.IsInRole("Admin")/RequireRole are just convenience helpers over that specific claim type. There's no separate "role store" consulted at authorization time by default; roles arrive on the token/cookie exactly like any other claim and are checked the same way underneath.

When would you reach for a custom IAuthorizationRequirement instead of composing existing RequireRole/RequireClaim calls?

The moment the rule needs logic beyond "does this claim exist with this value" — comparing two claims to each other, comparing a claim to the resource being accessed, calling out to a database or a feature-flag service, or expressing OR logic between conditions (built-in requirement composition is AND-only across separate requirements). If you find yourself wanting "claim A OR claim B" or "claim A AND (claim B is a recent timestamp)," that's the signal to write one requirement with the actual logic inside its handler.

What's the difference in outcome between a handler that never calls Succeed() and one that explicitly calls Fail()?

Not calling Succeed() just means this handler didn't vote yes — if no handler for that requirement succeeds, the requirement fails by default, but a different, unrelated handler failing loudly doesn't poison anything else. Calling Fail() explicitly is a hard veto across the whole authorization evaluation for that resource/policy — once any handler calls Fail(), the overall result is failure regardless of how many other handlers would have succeeded. Reserve explicit Fail() for genuine "this must never be allowed" conditions (e.g. a suspended account), not as the default way to express "this particular check didn't pass."

How would you implement "an Admin can do this, OR the resource owner can do this" as a single policy?

Not as two separate requirements added to the same policy — that would AND them, requiring both to be true simultaneously. Either write one custom requirement whose handler internally checks "is Admin, or IsOwner(resource)" and calls Succeed() if either is true, or register two handlers for the *same* requirement type where each independently calls Succeed() under its own condition — a requirement succeeds if *any* registered handler for it succeeds, so two handlers for one requirement do give you OR semantics, unlike two different requirements on one policy, which give AND.

Why does IAuthorizationService.AuthorizeAsync accept a resource parameter at all — isn't the ClaimsPrincipal enough?

Because plenty of real authorization rules are inherently about the relationship between the caller and a specific object — ownership, tenancy, department membership on that record — not a fact you can determine from the principal in isolation. Passing the resource lets a handler compare, e.g., the resource's TenantId against a claim on the user, which is impossible if the API only ever hands the handler a principal and a policy name.

What's a realistic failure mode of putting authorization logic directly in a controller action instead of a named policy?

The rule gets copy-pasted (often slightly wrong the second time) to every other action that needs the same check, and a later change to the rule — adding a new exception, tightening a condition — has to be found and applied at every copy, which is exactly how "AdminOnly" ends up meaning three subtly different things in different parts of a codebase. A named, centrally-defined policy means the rule is defined once, is independently unit-testable, and a change to it automatically applies everywhere it's referenced.

How do you unit test a custom resource-based authorization handler in isolation?

Construct the requirement, a ClaimsPrincipal with the claims your scenario needs, the resource object, and an AuthorizationHandlerContext wrapping all three; call the handler's HandleRequirementAsync directly (it's protected, so typically via a small test subclass or by testing through AuthorizeAsync on a service built with just that handler registered) and assert on context.HasSucceeded. No HTTP pipeline, no real database — just the decision logic, which is the entire point of separating requirements/handlers from the endpoints that invoke them.

A junior engineer proposes encoding a user's full permission set as one giant claim containing a comma-separated list, checked with string contains. What would you push back on?

String-contains matching on a serialized list is fragile (partial matches, e.g. "orders" matching both "orders.read" and "orders.readonly"), doesn't compose with the existing requirement/handler model, isn't independently testable per permission, and grows unwieldy as the permission set grows — every check re-parses and re-scans the same string. The idiomatic fix is one claim per permission (or scope) with a well-known type, checked via RequireClaim or a small custom requirement — which is exactly what scopes in OAuth access tokens already look like, so it also aligns with how the rest of the stack represents grants.

Why might "Admin" in your own app's role claims not be the right long-term substitute for real, per-resource authorization, even in a fairly small app?

Because "Admin" as a role tends to accrete meaning over time — first it means "can manage users," then "can also manage billing," then "can also impersonate other tenants" — and a single flag can't express "Admin, but scoped to their own tenant only" without either a proliferation of near-duplicate roles or a claim/requirement that actually carries the scoping information (a tenant ID claim, checked against the resource). The moment "Admin" needs a qualifier in a sentence describing what it means, that qualifier belongs in a claim or a resource-based requirement, not folded silently into the role name.

08Microsoft Entra ID: tenancy, app registrations, and MSAL

Entra ID (renamed from Azure AD, but the underlying identity platform — the "v2.0 endpoint" — is unchanged by the rename) is a multi-tenant identity provider: a tenant is a dedicated, isolated directory instance — one per organization, identified by a tenant ID (a GUID) or a verified domain. Every app that authenticates against Entra ID does so through an app registration, which is where you declare the client ID, redirect URIs, requested API permissions, and whether the app is single-tenant (only this org's users), multi-tenant (any Entra ID org), or multi-tenant-plus-personal-accounts. Getting this scope wrong is a common early misconfiguration: a genuinely internal line-of-business app registered as multi-tenant will happily authenticate a user from a completely unrelated organization's directory unless the app itself also checks the token's tenant claim (tid) and rejects anything outside the expected tenant — the registration setting controls who can sign in, not who your app should actually trust.

App registrations distinguish delegated permissions (the app acts as the signed-in user, limited to what that user could do themselves — "read the signed-in user's mailbox") from application permissions (the app acts as itself, with no signed-in user at all — used with the client credentials grant, unit 11 — "read every mailbox in the tenant"). Application permissions are inherently higher-privilege and require admin consent; a common review flag is an app requesting an application permission for something a delegated permission would have covered, which usually means the app is over-scoped relative to what it actually needs.

MSAL (Microsoft Authentication Library) is the client library family — MSAL.NET, MSAL.js, MSAL for Android/iOS — that implements the actual OAuth/OIDC flows against Entra ID correctly, including the parts that are easy to get subtly wrong by hand: PKCE, token caching (so a silent token acquisition doesn't force a fresh login every time), automatic retry on transient failures, and the specific claims/endpoint quirks of the v2.0 endpoint. Microsoft.Identity.Web then wraps MSAL.NET specifically for ASP.NET Core, wiring it into AddAuthentication/AddMicrosoftIdentityWebApp or AddMicrosoftIdentityWebApi so a typical app barely touches MSAL directly — the library handles token acquisition, caching, and even incremental consent (requesting additional scopes later without a full re-login) behind a small, declarative setup surface.

The freshest thread here, and worth naming as the "very current" fact for this unit: Conditional Access — Entra ID's policy engine for "require MFA / block legacy auth / require a compliant device, based on signal" — has been extended through 2026 to cover AI agent identities specifically, not just human and traditional service-principal sign-ins. Agent identities can now be evaluated against Conditional Access policies, tracked via dedicated risk signals ("Agent Risk"), and tagged with Custom Security Attributes the same way a human account can be — including agent identities running inside Windows 365 for Agents. This matters concretely for anyone building agentic systems on the Microsoft stack in 2026: an autonomous agent calling Graph or an internal API with its own identity is no longer an edge case the platform's policy engine ignores — it's now a first-class principal type Conditional Access can gate exactly like a user or a service principal.

Interview trap

"Our app registration is single-tenant, so we don't need to check the tenant claim" sounds reasonable but skips a real scenario: guest/B2B users. Entra ID supports inviting external users into a tenant as guests, and a single-tenant app registration will happily authenticate a guest whose home tenant is a completely different org — the tid in their token is still your tenant's ID (that's what "single-tenant registration" actually pins), but understanding who that guest really is often needs looking at additional claims, not just trusting "single-tenant, so we're safe." The deeper trap: "single-tenant" restricts which directory can issue the token, not which humans that directory considers valid members.

Try it
  1. Register an app as multi-tenant in a free Entra ID tenant, sign in with an account from a different tenant (or a personal Microsoft account, if enabled), and inspect the resulting token's tid and iss claims.
  2. Request a delegated Graph permission (e.g. User.Read) versus the equivalent application permission, and compare what each actually lets a client credentials call retrieve.
Expected outcome

(1) tid reflects whichever tenant the user actually authenticated against (or a special value for personal accounts), and iss is templated with that same tenant ID — proving the "multi-tenant" setting is about who's allowed to reach your app's /authorize endpoint successfully, not a filter your app gets for free afterward. (2) The delegated permission, used interactively, only ever returns the signed-in user's own profile; the application permission, used with client credentials (no user context at all), can query any user's profile in the tenant by ID — a concrete demonstration of why application permissions need admin consent and careful review.

What's the actual difference between "Azure AD" and "Entra ID" that a candidate should know beyond the rename?

Functionally, for the v2.0 endpoint and modern app registrations, effectively none — it's a rebranding of the same underlying identity platform, not a protocol or architecture change. The distinction that does matter is the older ADAL library and the legacy Azure AD Graph API, which are genuinely deprecated in favor of MSAL and Microsoft Graph respectively; "Entra ID" as a name change is cosmetic, but "stop using ADAL / legacy AAD Graph" is a real, substantive migration that happened to coincide with it.

Why does a multi-tenant app registration need its own tenant check in code, when Entra ID already gates who can sign in?

"Multi-tenant" as a registration setting means "any Entra ID tenant's users are permitted to reach the authorization endpoint and receive a token for this app" — it says nothing about whether your specific app's business logic should trust every one of those tenants equally. An app meant for one customer organization but registered as multi-tenant (often done for convenience during development) will issue valid, correctly-signed tokens to users from completely unrelated companies unless the app itself checks tid against an allow-list, which is exactly the check that's easy to forget once the happy-path login flow "just works."

When would an app need application permissions rather than delegated permissions, concretely?

Any scenario with no interactive user present at the moment access is needed — a nightly batch job syncing data from Microsoft Graph, a backend service processing webhooks, a daemon reconciling directory data — where there's no one to redirect to a login page and no "signed-in user" whose delegated access would even make sense to invoke. This pairs directly with the client credentials grant (unit 11): the app authenticates as itself and needs its own, tenant-wide permission grant rather than borrowing a user's.

Why does Microsoft.Identity.Web exist as a layer on top of MSAL.NET rather than apps just calling MSAL.NET directly?

MSAL.NET is a general-purpose token acquisition library — it knows how to get tokens, cache them, and refresh them, but it has no opinion about ASP.NET Core's authentication/authorization pipeline, middleware ordering, or configuration conventions. Microsoft.Identity.Web is the glue that wires MSAL.NET's token acquisition into AddAuthentication/AddOpenIdConnect-shaped configuration, handles incremental consent and token cache persistence idiomatically for a web app or web API, and gives you a declarative appsettings.json-driven setup instead of hand-wiring MSAL calls into every controller.

What is "incremental consent" and why does it matter for an app whose required scopes grow over time?

Incremental consent lets an app request additional scopes later, in context (e.g. only when the user first tries a feature that needs Calendar access), rather than demanding every scope the app might ever need up front at first login — which both improves the user's understanding of why access is being requested and avoids over-broad consent grants sitting unused. Without it, apps tend toward requesting the maximal permission set at initial sign-in "just in case," which is worse for both user trust and blast radius if the app is later compromised.

What does it mean, concretely, for Conditional Access to now cover AI agent identities?

An autonomous agent that authenticates to Entra ID with its own distinct identity (rather than borrowing a human's token or running under an undifferentiated service principal) can now be targeted by the same policy engine that gates human sign-ins — requiring specific conditions before the agent's calls succeed, being scored for "Agent Risk" the way user sign-ins get a risk score, and being tagged with Custom Security Attributes for governance and reporting. Practically, this means an org building agentic automation on Entra ID can apply the same "block if risk is high," "require specific network/device posture," or "restrict by attribute" controls to agents that it already applies to people and traditional service accounts, rather than treating agent access as an ungoverned gap.

Why might a security review flag an app registration that requests an application permission when only a handful of specific delegated calls are actually needed?

Because application permissions are tenant-wide by nature — "read every user's calendar" instead of "read the signed-in user's calendar" — so requesting one when a delegated permission would suffice needlessly expands the blast radius if the app's credentials are ever compromised. The review question is always "does this code path actually run with no user present," and if the answer is no, the fix is to switch to the narrower delegated permission and accept that it requires an interactive user context, rather than reaching for the broader application permission out of convenience.

A guest user from Tenant B signs into an app registered in Tenant A. What claims would you inspect to understand who they actually are?

tid will show Tenant A (the tenant the token was issued from, i.e. the one the app trusts), but claims like an immutable ID, UPN, or (depending on configuration) an idp/home-tenant-related claim can reveal that the account is a guest whose home identity lives elsewhere. This is exactly why "single-tenant registration" alone doesn't answer "is this really one of our own employees" — B2B collaboration means a single-tenant app can still authenticate people whose home organization is different from yours, and any app with a strict "employees only" requirement needs to check for guest status explicitly, not just trust the registration boundary.

How would you explain to a new team member why "just add the tenant ID to the config" isn't a complete multi-tenancy story for a SaaS app built on Entra ID?

Setting a specific TenantId in config pins your app to accept sign-ins from exactly one Entra ID directory — great for an internal LOB app, wrong for a SaaS product meant to serve many different customer organizations, each with their own tenant. A real multi-tenant SaaS app registers as multi-tenant (or uses the "organizations" endpoint), accepts tokens from any tenant, and then does its own application-level mapping from the incoming tid to which of your customers that sign-in belongs to — the config-level tenant ID and the app's own customer/tenant data model are two different concepts that happen to share the word "tenant."

09Token lifetime, rotation, revocation, and Conditional Access

Every token has two independent lifetime questions: how long is it valid for (its stated exp), and can it be invalidated early. Access tokens answer the second question badly by design (unit 04) — the standard mitigation is simply making them short-lived (minutes to an hour) so an uncontrolled leak has a small blast-radius window. Refresh tokens carry the opposite trade-off: they must live long enough to avoid forcing constant re-logins, so their design has to answer "how do we revoke this early" seriously, because "short-lived" isn't an option for something whose entire purpose is staying valid for days or months.

Entra ID's concrete 2026 refresh-token defaults are worth knowing exactly, because "refresh tokens last 90 days" is only true for some clients: 24 hours for SPA-registered clients using the redirect-URI-based auth code flow (a direct consequence of third-party-cookie blocking — see unit 03 — SPAs can no longer rely on a silent, cookie-based re-authentication fallback the way they once could, so Microsoft tightened the token's own lifetime instead), 24 hours for sign-ins via email one-time-passcode, and 90 days otherwise (confidential clients, native apps). On top of the base lifetime, refresh tokens rotate on every use — redeeming one always returns a brand-new refresh token alongside the new access token, and the old one is invalidated, which is both a security property (limits the value of a single stolen token) and the mechanism behind sliding-window renewal (a client that refreshes regularly effectively never hits the base lifetime, as long as it keeps using the token before it expires).

Revocation happens for specific triggers, and — this is the detail that actually gets asked in depth — the trigger list differs by what changed and what kind of client is involved. A password change or SSPR (self-service password reset) revokes refresh tokens for password-based sessions but does not necessarily revoke sessions established via a passwordless method (FIDO2, Windows Hello, an already-issued token from before the change) unless a broader revocation is also triggered. An admin-initiated "revoke sessions" action is a blunt, broader instrument, intended to work regardless of how the session was established. SSO logout at the browser level revokes the browser's SSO session cookie but does not, on its own, revoke already-issued refresh tokens held by native apps that cached them outside the browser — which is exactly why "I signed out of the browser but my phone's app is still logged in" is expected behavior, not a bug, unless the org also applies Conditional Access or a Continuous Access Evaluation policy that reacts to the sign-out signal.

Configurable Token Lifetime Policies reached general availability in 2026, letting an org override the platform defaults above per application or per service principal — shortening a SPA's effective session for a high-sensitivity app, or lengthening a trusted internal tool's, rather than accepting the one-size-fits-all default. Conditional Access is the layer that reacts to context rather than just issuing/expiring tokens on a timer: it evaluates signals (network location, device compliance, sign-in risk score, and — per unit 08 — now agent risk for AI agent identities too) at token-issuance time and can require step-up MFA, block the sign-in outright, or restrict what the resulting session can do, all without touching the token lifetime settings themselves. Continuous Access Evaluation (CAE) goes further: for CAE-enabled resources, a token can be revoked near-real-time in reaction to a critical event (user disabled, password changed, location moved outside a trusted named location) rather than waiting for its stated expiry — closing the gap that "the token just hasn't expired yet" would otherwise leave open for up to its full lifetime.

Expected outcome

(2) A CAE-enabled resource can react to a critical event within minutes; a non-CAE resource is bounded only by the access token's stated lifetime, which for many setups is up to an hour — a meaningful difference for how fast "we disabled the account" actually stops live access.

Why do SPA clients specifically get a shorter refresh-token lifetime (24h) than confidential or native clients (90 days) in Entra ID?

SPAs are public clients running in the browser, the exact environment that lost its old fallback — silently re-authenticating via a first-party session cookie inside a hidden iframe — once browsers started blocking third-party cookies (unit 03). Rather than leave SPAs with a long-lived refresh token and no reliable silent-renewal backstop, Microsoft shortened the token's own lifetime, forcing a real (though often still fast, same-device) re-authentication more frequently — trading convenience for reduced exposure on the client type that can't hold a secret and runs in the most attack-exposed execution context.

What does "refresh token rotation" actually protect against, precisely?

It limits how long a single stolen refresh token remains useful: since redeeming a refresh token always issues a new one and invalidates the old, an attacker who steals a token and uses it once gets one shot before their copy is invalidated — and if the legitimate client also tries to use its (now-stale) copy afterward, that mismatch is a detectable signal of compromise ("refresh token reuse detection," referenced back in unit 02's OAuth 2.1 rules). Without rotation, a stolen bearer refresh token would remain a valid, reusable credential for its entire base lifetime.

Give a concrete scenario where "we forced a password reset" would give a false sense of security.

An account was compromised and the attacker enrolled a passwordless method (e.g. a FIDO2 key or an app-based passkey) or is holding a still-valid native-app refresh token obtained before detection. The security team forces a password reset, assuming this ends all attacker access — but a passwordless sign-in path doesn't necessarily get invalidated by a password-only revocation trigger, and an already-cached native token isn't touched either. The actually safe response is an explicit admin-initiated full session revocation (and, ideally, review/removal of any authentication methods the attacker may have registered), not a password reset alone.

What problem does Continuous Access Evaluation solve that ordinary short-lived access tokens don't?

Even a short access token lifetime (say, 60-90 minutes) still leaves a window where a token that "should" be dead — because the user was just disabled, or moved to an untrusted network, or had their password changed — keeps working until it naturally expires. CAE closes that specific gap for CAE-enabled resources by pushing near-real-time revocation signals to the resource provider itself, so critical events take effect in roughly minutes rather than waiting out the token's full remaining lifetime — it's not a replacement for short-lived tokens, it's a faster override on top of them for the events that matter most.

How would Configurable Token Lifetime Policies and Conditional Access divide responsibility if you wanted a highly sensitive internal app to have both short sessions and step-up MFA for risky sign-ins?

A Token Lifetime Policy assigned to that app's service principal shortens the access and/or refresh token lifetimes specifically for that app, independent of the tenant-wide default — that's a static, always-applied constraint. Conditional Access is layered on top and reacts to context at sign-in/token-issuance time — requiring MFA, blocking non-compliant devices, or reacting to a risk score — regardless of how long the resulting token is valid for. You'd use both together: the lifetime policy bounds how long any session can last once granted, and Conditional Access controls the conditions under which a session is granted in the first place.

Why does "SSO logout in the browser" not affect a native mobile app's cached tokens?

Browser SSO logout clears the browser's own session cookie/state with the AS — it's a browser-scoped operation. A native app that already completed its own authorization code flow and cached a refresh token via the OS's secure storage (Keychain/Keystore) never touches that browser session again for ordinary token refresh; it talks directly to the token endpoint using its cached refresh token. The two are genuinely separate credential stores, and a full "log out everywhere" needs to either explicitly revoke at the AS/admin level or wait for the native app's refresh token to naturally reach its own lifetime limit.

What would you check if a security incident report says "we revoked the user's sessions but their access token kept working for 40 more minutes" — is that a bug?

Not necessarily — check whether the resource the attacker was calling is CAE-enabled. If it isn't, "revoke sessions" typically invalidates refresh tokens (stopping future renewal) but doesn't retroactively kill an access token that was already issued and hasn't hit its stated exp yet; the attacker's access naturally ends once that access token expires, which for a non-CAE resource can be the full nominal lifetime. This is expected behavior given the architecture, and the actionable follow-up is either enabling CAE for that resource where supported, or shortening the access token lifetime via a Token Lifetime Policy if that residual window is unacceptable for this specific app.

Why is "refresh tokens for public clients must be rotated or sender-constrained" (OAuth 2.1, unit 02) and "Entra ID rotates refresh tokens on every use" the same underlying idea applied at two different layers?

OAuth 2.1 states the requirement as a spec-level rule for any conformant authorization server issuing refresh tokens to public clients; Entra ID's behavior is a concrete implementation of exactly that rule for its own token endpoint. Recognizing this connection is the difference between memorizing "Entra ID rotates refresh tokens" as an isolated fact and understanding it as one AS's compliant implementation of a general security requirement — which is also why you'd expect the same rotation behavior from any other OAuth 2.1-conformant AS (Duende, Okta, Auth0), not something unique to Microsoft.

10Passwordless and phishing-resistant authentication

"Passwordless" and "phishing-resistant" get used interchangeably and shouldn't be — they're different axes. Passwordless means the user never types a password (SMS OTP, email OTP, a magic link, an authenticator app push) — it removes password-specific risks (reuse across sites, credential-stuffing databases, weak passwords) but several passwordless methods are still fully phishable: a user tricked by a convincing fake login page can be talked into approving a push notification or reading out an OTP to an attacker in real time, because nothing about those methods cryptographically ties the approval to the legitimate site. Phishing-resistant is the narrower, stronger property: the authentication mechanism cryptographically binds the credential to the specific origin it was registered for, so even a perfect pixel-for-pixel phishing site cannot obtain a usable credential, because the browser/OS itself refuses to release one for the wrong origin.

WebAuthn / FIDO2 is the standard that actually delivers phishing resistance: a public/private key pair is generated per site (per "relying party ID"), the private key never leaves the authenticator (a hardware security key, a platform authenticator like Windows Hello or a phone's biometric sensor, or a roaming passkey synced via a platform account), and the browser enforces origin binding as part of the WebAuthn API itself — a credential registered for example.com simply cannot be invoked for examp1e.com, regardless of how convincing the fake page looks to a human. Passkeys are WebAuthn credentials designed for consumer-friendly sync and discoverability (no separate username-entry step, credentials sync across a user's devices via their platform account) — the same underlying cryptographic property, packaged for a mainstream "just tap to sign in" UX rather than a security-team-only hardware token workflow.

Step-up authentication is the pattern where a session's existing authentication level is judged insufficient for a specific, higher-risk action, and the app or platform demands a fresh, stronger proof before allowing it — approving a large financial transaction, changing account recovery details, accessing an admin console. Mechanically, this reads the acr/amr claims from unit 03 (what method, how strong) and, if insufficient, triggers a fresh authorization request with a stronger required method (often expressed via the OIDC acr_values parameter or a Conditional Access policy targeting that specific action/app) rather than trusting a login that happened under weaker conditions minutes or hours earlier. This is also the mechanism behind Entra ID's Conditional Access requiring MFA only for risky sign-ins rather than always — the policy engine reads context (device, location, risk score) and decides, per sign-in, whether the existing assurance level is enough.

The practical migration reality most orgs are actually living through in 2026 isn't "delete all passwords tomorrow" — it's a layered rollout: phishing-resistant methods (FIDO2/passkeys) for admins and high-privilege roles first (where compromise is most damaging), broader passwordless (Authenticator app push, Windows Hello for Business) for the general workforce, with SMS/email OTP treated as a legacy fallback to actively reduce, not a target state — SMS OTP specifically remains vulnerable to SIM-swapping and real-time phishing relay, and its continued prevalence is a compatibility/adoption compromise, not a security recommendation.

The correct claim is narrower: MFA reduces risk versus password-only, but only phishing-resistant methods (FIDO2/WebAuthn) close the relay-phishing gap specifically.

Why isn't "passwordless" a sufficient answer to "how do you prevent phishing"?

Because most passwordless methods still rely on a human correctly judging that they're interacting with the legitimate site before approving or providing a code — and phishing attacks are specifically designed to defeat exactly that human judgment. A convincing fake page can still trigger a real OTP send or push notification by relaying the victim's initial input to the real site in real time, and the victim, seeing a legitimate-looking prompt, approves it. Only origin-bound cryptographic methods remove the human judgment step from the security boundary entirely.

What specifically makes WebAuthn immune to real-time relay phishing, mechanically?

The credential is bound to a relying party ID at registration time, and the browser (not the website, not the user) enforces that the WebAuthn ceremony can only complete for the origin matching that ID — an attacker's relay server, even if it perfectly proxies every visual element of the real site, is still a different origin from the browser's point of view, so the browser simply won't release a signed assertion for it. There's no step where a human has to notice anything is wrong; the enforcement is structural and happens below the level a phishing page can influence.

How do "MFA fatigue" attacks work, and what does that reveal about push-based approval as a security control?

An attacker who already has a valid password triggers repeated push notifications (or a single well-timed one) to the legitimate user's device, hoping the user approves one out of habit, annoyance, or confusion about what they're approving — no cryptographic weakness is exploited, just human decision fatigue under an ambiguous prompt. It reveals that push approval's security ultimately rests on a human correctly interpreting a notification's context every single time, which is a much softer guarantee than a protocol-level structural constraint like WebAuthn's origin binding.

Why would an org roll out FIDO2/passkeys to admins first rather than the whole workforce simultaneously?

Admin and other high-privilege accounts represent the highest-impact compromise scenario — an attacker with admin access can often pivot to compromise many other accounts or systems, making them the highest-value phishing target and the accounts where the strongest available protection pays off fastest. Broader workforce rollout involves more device diversity, more support burden, and more change-management friction, so a staged rollout (highest-risk roles first, broader adoption following) balances security urgency against practical deployment cost — a standard risk-prioritized rollout strategy, not a technical limitation of the protocol itself.

What's the relationship between step-up authentication and the acr/amr claims from unit 03?

Step-up authentication is the behavior; acr/amr are the concrete signal it reads to decide whether that behavior is needed. A relying party checking "was this session's login strong enough for the action being attempted" is literally inspecting those claims from the existing ID token or session, and if they indicate an insufficient method or assurance level, the app triggers a fresh authorization request specifying a stronger required method — the claims are the vocabulary the step-up decision is expressed in.

Why does SMS OTP remain widely deployed in 2026 despite being neither phishing-resistant nor immune to SIM-swapping?

Universal compatibility — every phone can receive an SMS with no app install, no hardware purchase, and no platform-specific setup, which makes it the lowest-friction fallback for account recovery, for users without a smartphone capable of running an authenticator app, and for markets/demographics where phishing-resistant hardware isn't practically deployable yet. It persists as a compatibility floor and a recovery mechanism, not because anyone actively recommends it as a primary method — most current guidance (including Microsoft's own) explicitly frames it as the method to actively migrate users away from, not toward.

A team wants to enforce "phishing-resistant MFA required for all admin actions" — what would you check to confirm the policy actually achieves that, rather than just requiring "MFA"?

Check that the policy's authentication strength (in Entra ID terms, an Authentication Strength Conditional Access control) is explicitly scoped to the phishing-resistant method set (FIDO2, certificate-based auth, Windows Hello for Business in its phishing-resistant configuration) rather than a generic "require MFA" grant control, which would also be satisfied by an OTP or push approval. "MFA required" and "phishing-resistant authentication required" are different policy configurations in Entra ID specifically because the platform recognizes they're different security guarantees, not synonyms.

Why can't a password manager's autofill or a browser extension "fix" phishing the way WebAuthn does?

A password manager that correctly matches credentials to the exact saved origin does help — it won't autofill a password for a lookalike domain, which is a genuine, useful mitigation. But it only helps if the user relies on autofill and doesn't manually type or copy-paste the password when autofill "doesn't work" on a slightly-off domain (which a user might attribute to a glitch rather than a red flag), and it does nothing for OTP or push-based flows at all, since there's no credential for it to withhold. WebAuthn's guarantee doesn't depend on a tool being present and correctly used — it's enforced by the browser's own implementation of the ceremony, with no user behavior able to override it.

11Machine-to-machine and workload identity

Everything in units 01-10 assumed a human at the keyboard. A huge and growing share of real traffic doesn't have one: a nightly batch job, a microservice calling another microservice, a CI pipeline deploying to cloud infrastructure, or — per unit 08 — now an autonomous agent. OAuth's client credentials grant is the standard shape for this: the client authenticates directly to the token endpoint using its own credential (a client secret, or better, a certificate/signed assertion) and receives an access token representing itself, not a delegated user — there's no authorization code, no redirect, no browser involved at all, because there's no user to redirect.

The security-critical question for client credentials is exactly what it always is for anything holding a long-lived secret: how is that secret protected, and what happens the moment it leaks. A plaintext client secret checked into config or an environment variable is a standing risk — anyone with read access to that config effectively has the app's full identity. This is why cloud-native patterns increasingly avoid client secrets entirely in favor of workload identity federation: instead of the workload holding a long-lived secret, it presents a short-lived token issued by its own runtime platform (a Kubernetes service account token, a CI provider's OIDC token, a cloud VM's attested identity) to the target identity provider, which has been configured to trust that specific external issuer for that specific workload — the target IdP verifies the incoming token's signature and claims (issuer, subject, audience) against a trust policy and, if it matches, mints its own access token in return. No long-lived secret ever exists anywhere in this flow; the trust relationship is entirely federation-based and the actual bearer credential is short-lived and platform-issued.

Certificate-based client authentication is the middle ground still common in enterprise settings: instead of a shared-secret string, the client proves its identity by signing a JWT assertion with a private key (a "client assertion," per RFC 7523) and presenting that signed assertion — plus, for mutual TLS setups, the certificate itself at the transport layer — to the token endpoint. This avoids ever transmitting a shared secret over the wire at all (the private key never leaves the client), and it composes naturally with sender-constrained tokens (DPoP or mTLS, referenced back in unit 02 and unit 09): the resulting access token can be bound to the same key/certificate that authenticated the client, so even if the token itself leaked, a party without the private key can't actually use it — the resource server checks that the caller presenting the token can also prove possession of the bound key.

Entra ID's application permissions (unit 08) are the concrete shape client credentials takes on that platform: a service principal (the app registration's runtime identity) is granted application permissions, consented by an admin, and a client-credentials token request against that service principal's client ID/secret-or-certificate returns a token scoped to exactly those tenant-wide permissions — with no delegated user context anywhere in the flow. Reviewing what a given service principal can do, in this model, means reading its granted application permissions directly, not inferring capability from "which user typically runs this job," because there often isn't one.

Why does the client credentials grant have no redirect_uri and no user interaction at all?

Because there's no resource owner delegating anything — the client is requesting a token to act as itself, not on behalf of a user. What's the practical risk of a client secret sitting in a CI pipeline's environment variables, even if the pipeline's own logs are private?

Anyone with permission to view or edit the pipeline configuration, anyone who can trigger a debug/verbose run that might echo environment variables, and anyone who compromises the CI runner itself effectively gains the full identity the secret represents — and unlike a compromised human credential, there's often no MFA or Conditional Access layer sitting in front of a client-credentials flow to catch anomalous use. The secret's blast radius is exactly as wide as its access to the pipeline's configuration, which in practice is often wider than the team maintaining the pipeline initially assumes.

How does workload identity federation avoid needing any long-lived secret at all — what actually gets trusted?

The target identity provider is configured, ahead of time, to trust tokens issued by a specific external OIDC issuer (say, GitHub Actions' own token service) that match specific claims (repository, branch, environment). At runtime, the workload's own platform mints it a short-lived, signed token asserting exactly those claims — no configuration or secret store on the workload's side holds a credential at all. The "secret," if there is one conceptually, is the trust policy itself sitting on the identity provider's side, and it's not something that can leak the way a string value can, because possessing knowledge of the trust policy's rules doesn't let you satisfy them without actually being the trusted workload.

What does sender-constraining a client-credentials-issued access token actually add, given the client already proved its identity to get the token?

Proving identity at token *issuance* time and proving possession at token *use* time are different guarantees — a token, once issued, is normally a plain bearer credential from that point forward, so if it's intercepted or logged anywhere downstream (a proxy, an internal log, a misconfigured trace), whoever has the string can use it, regardless of how carefully the original client authenticated. Sender-constraining (DPoP/mTLS) means the resource server checks that whoever is *presenting* the token can also prove possession of the same key that was bound to it at issuance — so a leaked token string alone, without the private key, is useless to a third party.

Why does .default as the requested scope make sense specifically for client credentials, when delegated flows request specific named scopes?

Delegated flows negotiate scopes per request because different call sites might need different subsets of what the user could grant, and incremental consent (unit 08) depends on being able to ask for more later. Client credentials has no such per-request negotiation concept — the service principal's application permissions were already fixed at admin-consent time, so .default just means "give me a token for whatever this service principal was actually granted," which is the only sensible framing when there's no user-in-the-loop scope negotiation happening at all.

A batch job needs to call Microsoft Graph nightly with no human involved. Walk through choosing between a client secret, a certificate, and workload identity federation for it.

If the job runs on infrastructure that already has a federatable identity (a CI system with OIDC support, an Azure/AWS/GCP-hosted compute identity), workload identity federation is the strongest choice — no secret to store, rotate, or leak. If it runs somewhere without that support (an on-prem server, a legacy scheduler), a certificate-based client assertion is the next best option — the private key can live in a proper secret store or HSM and never travels over the wire. A plain client secret is the fallback only when neither of the above is feasible, and it should come with active rotation and monitoring precisely because it's the weakest of the three options being accepted, not because it's "good enough" on its own merits.

How does an AI agent identity (unit 08) fit into this unit's client-credentials/workload-identity picture?

An agent that authenticates with its own distinct identity (rather than impersonating a human or hiding behind an undifferentiated shared service principal) is, mechanically, doing exactly what any other non-interactive workload does — presenting a credential (ideally federated or certificate-based, not a shared secret) to get a token representing itself, then calling downstream APIs with that token. What's new (per unit 08 and unit 09) is that the platform's governance layer — Conditional Access, risk scoring, Custom Security Attributes — now applies to that identity the same way it applies to a human or traditional service principal, rather than the agent's access being an ungoverned corner of the identity model.

What would you flag reviewing an app registration where the client secret has no expiration set, or an expiration years in the future?

A secret with no practical expiration is a standing credential with no forcing function to ever rotate it — the review should ask whether the workload could instead use a certificate or workload identity federation, and if a secret genuinely must remain, push for a short, enforced expiration (Entra ID's own portal guidance nudges toward this) plus monitoring/alerting well before expiry, rather than leaving a years-long-lived secret as the status quo simply because rotating it is inconvenient.

12The big Q&A

Everything below is deliberately outside the eleven core sections — no repeats, no rephrasing. These are the questions that probe the seams between topics, the ones an interviewer asks after the "textbook" material to see whether you actually integrate it.

Architecture & ecosystem

Why do most real systems end up running OAuth, OIDC, and a session-cookie mechanism simultaneously, rather than picking just one?

They answer different questions for different legs of the same system: OIDC handles the initial "who is this and how did they prove it" at login, OAuth access tokens handle "what can this specific call do" against downstream APIs, and a session cookie is usually still what actually carries state between the browser and the app's own backend request-to-request, because re-running a token-bearing request model for every page load is unnecessary overhead when a cheap, local cookie check does the same job. A system that thinks it uses "just OAuth" almost always still has a session mechanism hiding somewhere underneath — recognizing that layering, rather than treating them as competing choices, is the mark of someone who's actually operated one of these stacks.

How would you design authentication for a system with three distinct client types — a public website, an internal admin SPA, and a partner's server-to-server integration — sharing one API?

Three different flows converging on one authorization model, not three separate APIs: the public website likely doesn't need authentication until checkout, at which point it's authorization code + PKCE through a BFF; the internal admin SPA is the same shape, scoped to internal-only app roles via Conditional Access; the partner integration is client credentials with a certificate or federated workload identity, scoped to exactly the application permissions that partner needs. All three ultimately hand the shared API a validated access token with the right audience and scopes, and the API's authorization policies (unit 07) don't need to know or care which flow produced the token — only what claims it carries.

SAML is still common in large enterprises. What would you need to know to integrate a SAML-only identity provider into an otherwise OIDC-based system?

That SAML and OIDC solve the same problem (federated authentication) with a different wire format (signed XML assertions vs. signed JWTs) and different flows (mostly browser-POST-based redirects vs. authorization code exchange) — they don't compose directly, so the usual integration point is a gateway or a broker (Entra ID itself can act as one, translating an upstream SAML IdP's assertions into an OIDC-shaped login for your app) rather than teaching your app to speak both protocols natively. Recognizing "this is a protocol-translation problem, not an authentication-logic problem" is the useful framing.

Why does the industry keep converging on Google, Microsoft, or a small number of large IdPs for "login with X," rather than every company running its own?

Running an authorization server correctly is a genuinely hard, security-critical, and never-finished job — key rotation, breach monitoring, spec compliance as it evolves (exactly the OAuth 2.1 consolidation this guide covers), phishing-resistant method support, and Conditional-Access-grade risk evaluation are all things a large IdP amortizes across millions of users and dedicated security teams. Most companies are better served treating identity as a managed dependency (Entra ID, Okta, Auth0, or a self-hosted but actively maintained option like Duende) than building and indefinitely maintaining their own — this is the same "don't roll your own crypto" argument extended to the whole authentication stack.

Security

What's the difference between authentication being "broken" and authorization being "broken," in terms of what an attacker actually gains?

Broken authentication means an attacker can obtain a valid identity they shouldn't have — impersonating a real user, forging a token, bypassing a login check — and everything downstream trusts them as if they were legitimate. Broken authorization means the identity check was correct, but the decision about what that identity is allowed to do was wrong — a genuinely logged-in low-privilege user reaching an admin action. The former is usually the more catastrophic finding (it undermines every subsequent check), which is part of why authentication logic gets the heavier security review scrutiny, but authorization bugs (especially resource-based ones, unit 07) are far more common in practice because there are so many more of them to get right.

What's a "confused deputy" attack in the context of OAuth, and where does it actually show up?

A confused deputy is a client that's been tricked into using its own legitimate authority to perform an action on an attacker's behalf — the classic OAuth example is a client that accepts an authorization code or token from anywhere without verifying it was actually issued for the current, expected flow (missing state validation is the textbook version: an attacker gets their own valid code linked into the victim's browser session, and the victim's client, not checking state, completes the flow believing it's the victim's own authorization). It shows up wherever a component blindly trusts an input that should have been tied to a specific request or session and wasn't.

Why is comparing two secrets (a token, a signature, an API key) with a naive == string comparison a security bug, even if the values themselves are never logged?

A naive comparison typically short-circuits on the first mismatched byte, so the time it takes to return false leaks information about how many leading bytes were correct — a timing side-channel that, given enough attempts, lets an attacker recover a secret byte-by-byte purely from response timing, with no access to logs or the value itself. The fix is a constant-time comparison function (most crypto/token libraries provide one) specifically for anything that compares a caller-supplied value against a real secret or signature.

An API rejects malformed JWTs with a detailed error message naming exactly which validation step failed (bad signature vs. expired vs. wrong audience). Why might a security review flag this as too helpful?

Detailed, differentiated error messages give an attacker a free oracle for probing a token-forgery or token-manipulation attempt — "wrong audience" versus "bad signature" tells them exactly which part of a forged token to fix next, turning trial-and-error into a guided search. The safer pattern returns a uniform, generic failure (a flat 401 with a generic message) to the caller while still logging the specific reason in detail server-side for legitimate debugging and monitoring — informative to defenders, uninformative to an attacker probing from outside.

What's the actual risk of logging full request headers (including Authorization) at a gateway or reverse proxy, "just for debugging"?

Bearer tokens and session identifiers in headers are live credentials for as long as they're valid — logging them verbatim means every place that log flows to (a log aggregator, a support ticket with attached logs, a long-retention archive) becomes a place a stolen or leaked log can hand out working credentials, often for longer than the original request's lifetime would suggest, especially if logs are retained for months. The fix is redacting or hashing the Authorization header (and any token-bearing cookie) at the logging layer specifically, treating it the same way you'd treat a password field.

Performance & debugging

An API's JWT validation is suddenly adding noticeable latency to every request. What would you check first?

Whether the JWKS key set is being re-fetched from the AS on every request instead of being cached with a sensible refresh interval — this is a very common regression after a library upgrade or a misconfigured cache setting, and it turns a normally-cheap local signature check into a network round-trip per request. Second, check whether discovery document fetching (the OIDC metadata itself) is similarly uncached. Both should be fetched once and refreshed on a timer or on a kid-miss, never on every incoming request.

Users intermittently get logged out for no apparent reason, seemingly at random, across multiple instances of a load-balanced app. What's the most likely root cause?

Session or authentication-ticket state (a signing/encryption key for cookies, or a server-side session store) that isn't actually shared across instances — one instance encrypts a cookie with its own local key, a subsequent request lands on a different instance that can't decrypt it, and the user appears logged out. The fix is a shared data-protection key ring (ASP.NET Core's AddDataProtection().PersistKeysToX().ProtectKeysWithY() configured against shared storage) or a centralized session store, rather than each instance defaulting to its own local, ephemeral key material.

How would you debug "this specific user can't log in, but everyone else can," when the login flow appears to complete successfully in logs?

Suspect an authorization decision failing silently after a successful authentication — check whether the user's specific claims (a missing role assignment, an expired group membership, a tenant mismatch) cause an authorization policy to reject them post-login, which from the outside looks identical to "login failed" but is actually "login succeeded, then access was denied." Compare that specific user's actual claims (decode their token, don't guess) against what the failing policy requires, rather than re-testing the login flow itself, which already isn't the broken part.

A JWT-based API's throughput doesn't scale the way a load test predicted, even though validation is fast and local. What's a non-obvious cause worth checking?

Whether the token validation path is allocating heavily per request — parsing and validating a JWT via an older or misconfigured handler can allocate more than expected (part of why JsonWebTokenHandler, unit 04, exists as a lower-allocation alternative to the legacy handler), and under sustained load that shows up as GC pressure rather than an obviously slow single request. It's easy to miss in a load test that measures latency per request rather than allocation/GC behavior under sustained concurrent load.

Tooling & operational reality

What would make you choose Duende IdentityServer (self-hosted) over Entra ID (managed) for a new product's authorization server?

Needing full control over the AS's behavior, custom grant types, or on-premises/air-gapped deployment requirements that a managed cloud IdP can't satisfy; being a B2C/B2B product where your own customers are the "tenants," which fits Duende's model more naturally than shoehorning external customers into Entra ID's org-tenant concept; or already having deep .NET operational expertise and wanting the AS to be "just another service we run and deploy," accepting the licensing cost (free for dev/test and up to 10 clients on the Community Edition, tiered beyond that) in exchange for that control. Entra ID wins when you're already invested in the Microsoft identity ecosystem and want managed infrastructure, automatic compliance/feature updates, and no AS of your own to operate.

What's the actual operational cost of "we'll just add one more OAuth scope" that makes scope design worth taking seriously up front?

Every scope that exists needs a clear story for who can request it, who consents to it, and which resource server actually enforces it — a scope sprawl (dozens of narrowly-named, overlapping scopes accumulated ad hoc) becomes something no one can audit confidently, and "does this client really need orders.write or would orders.read have been enough" stops being answerable quickly. Treating scope design as a deliberate, reviewed surface (similar to API versioning) rather than "add a string whenever a new permission is needed" keeps the system auditable as it grows.

How do you test authentication/authorization logic in CI without hitting a real identity provider on every build?

For unit-level tests, construct ClaimsPrincipal objects directly and exercise policies/handlers in isolation (unit 07) — no HTTP, no IdP. For integration tests that need a real token flow, run a lightweight local test IdP (several exist specifically for this, mimicking a minimal OIDC provider) or use a test-only JWT signed with a locally-generated key that the test API is configured to trust only in the test environment — never point CI at a real, shared authorization server, both for reliability (external dependency, rate limits) and for the obvious risk of test-environment credentials leaking into a real IdP's configuration.

An app's authentication works fine locally but fails only when deployed behind a corporate reverse proxy or load balancer. What's a common category of cause?

The app receiving requests that appear to originate from the proxy (wrong scheme, wrong host, wrong client IP) rather than the original client, because forwarded-header handling (X-Forwarded-Proto/-Host/-For) isn't configured — this commonly breaks OAuth/OIDC redirect URIs (the app constructs a callback URL using "http" when the real client connected via "https," which then mismatches the registered redirect URI) or cookie Secure-flag logic (the app thinks the connection is plain HTTP behind a TLS-terminating proxy and refuses to set a secure cookie). The fix is ASP.NET Core's forwarded headers middleware, configured to trust only the actual known proxy.

Legacy & migration reality

A codebase still uses System.IdentityModel.Tokens.Jwt.JwtSecurityTokenHandler directly. Is that a problem, and what would migrating look like?

Not a correctness problem — it's still supported and correct — but it's the legacy, higher-allocation handler that AddJwtBearer no longer uses by default (unit 04); code that references it directly (rather than going through the framework's own configuration) is worth revisiting for the lower-allocation Microsoft.IdentityModel.JsonWebTokens.JsonWebTokenHandler, especially in a hot path. The migration is usually mechanical (equivalent APIs, different namespace/types) but worth doing deliberately with tests around token validation rather than as an incidental drive-by change, since it's security-critical code.

What does migrating an app off ADAL (the legacy Azure AD library) onto MSAL actually involve, beyond a package swap?

ADAL targets the older Azure AD Graph / v1 endpoint concepts; MSAL targets the v2.0 endpoint, which has different token shapes, different endpoint URLs, and different scope conventions (v2.0 scopes are full URIs or .default-style, not the older resource-URI model). A real migration means re-registering or updating the app registration for v2.0 semantics, updating scope requests throughout the codebase, and testing token validation logic against the new token shape — not just changing which NuGet package issues the token request.

Why would a team migrating from a legacy ROPC-based login (unit 02) to authorization code + PKCE resist the change, and how would you address that resistance?

ROPC lets the app keep its own custom-branded login form, collecting username/password directly — switching to the code flow means redirecting to the AS's own hosted login page, which teams often perceive as a UX regression (losing brand control) even though it's what actually enables MFA, Conditional Access, and passwordless methods to work at all. The honest answer is that most modern AS's support significant branding/customization of their hosted login page, closing much of the perceived UX gap, and that the security capabilities unlocked (which ROPC structurally cannot support) are the actual trade being made, not a purely cosmetic downgrade.

An old integration hard-codes a specific signing key instead of using JWKS. What's the actual failure this causes eventually, and how urgent is fixing it?

The moment the AS rotates its signing key (which every well-run AS does periodically, and sometimes on an emergency basis after a suspected compromise), every token signed with the new key fails validation against the old hard-coded key, and the integration breaks entirely with no warning — often during exactly the kind of unplanned security-driven rotation where a fast, working fallback matters most. This is worth fixing proactively rather than waiting for the outage; it's a small, mechanical fix (point at the JWKS URI instead of one static key) that removes an entire class of "surprise, everything's down" incident.

Judgment & scenario questions

Product wants "remember me for 90 days" on a consumer app. As the engineer responsible for the auth design, what do you push back on, and what do you actually build?

Push back on where that 90 days lives and how it's revoked — a 90-day session that's just a long-lived cookie or bearer token with no rotation and no revocation path is a standing risk if the device is lost or the account is compromised mid-window. What you actually build: a long-lived refresh mechanism that rotates on use with reuse detection (unit 02/09's pattern), tied to a device/session record the user can see and revoke individually ("sign out this device"), rather than a single opaque long-lived credential with no visibility or kill switch.

You inherit a system where every microservice independently validates JWTs against the same AS's JWKS. A teammate proposes centralizing validation at the gateway instead. What are the real trade-offs?

Centralizing at the gateway removes duplicated validation logic and gives one place to update when validation rules change, but it also means every internal service now implicitly trusts whatever the gateway forwards — if an attacker can reach a service directly (bypassing the gateway, a real risk in many network topologies), there's no validation left standing. Keeping validation in each service is more repetitive but defense-in-depth; a common middle ground is gateway-level coarse filtering (reject obviously invalid tokens early, cheaply) plus service-level validation still enforced independently, rather than treating the gateway as the sole trust boundary.

A stakeholder asks "can we just turn off MFA for this one internal tool, it's slowing people down"? How do you respond as the person who owns the auth architecture?

Ask what specifically makes MFA slow for this tool — often the answer is "no phishing-resistant/passwordless method is configured, so it's a password plus a manual OTP entry every time," which is a UX problem with a better fix (WebAuthn/passkeys, unit 10, which are often faster than typing an OTP) rather than a reason to remove the control entirely. If the tool genuinely has a narrow, low-risk profile (fully internal network, no sensitive data), a Conditional-Access-based conditional relaxation (unit 09) targeted at that specific context is a more defensible middle ground than a blanket "MFA off," which removes protection for every future use of that tool, including ones the current request didn't anticipate.

Six months after launch, you discover a background job has been using an application permission scoped far wider than it actually needs. What's the right way to fix this without breaking anything?

Identify the actual Graph/API calls the job makes today, determine the minimal permission set that covers them, add the narrower permission and get it consented, verify the job still works end-to-end against the narrower grant in a non-production environment, and only then remove the old, over-broad permission — never remove the wide permission first and "see what breaks" in production. This is the same "expand, verify, contract" pattern used for any breaking-capable production change, applied to authorization scope specifically.

13Night-before cheat sheet

Ten sentences, said out loud, no notes. If any one of them doesn't come out confidently, that's the unit to reread first.

  1. Authentication answers who you are; authorization answers what you can do — 401 means "prove who you are," 403 means "I know who you are, and no."
  2. OAuth is delegated access, not identity — an access token proves a grant, never a login; OpenID Connect is the identity layer on top, and its ID token is for the client, never for an API.
  3. OAuth 2.1 (still a draft in September 2026, targeting IESG by December) removes the implicit and password grants and makes PKCE mandatory for every client, confidential ones included — code interception doesn't care whether you also hold a secret.
  4. A JWT is signed, not encrypted, by default — anyone can read the payload; never trust the token's own alg header, always pin the expected algorithm and audience server-side.
  5. Stateless validation is not the same as unrevocable — short access-token lifetimes plus revocable, rotating refresh tokens (or an opaque/reference token when instant revocation matters) is how JWTs get real revocation.
  6. A token in browser-reachable storage is one XSS bug away from full theft — the BFF pattern keeps the browser holding only an ordinary HttpOnly/SameSite cookie, never the real bearer token.
  7. ASP.NET Core keeps authentication (schemes/handlers, populating ClaimsPrincipal) and authorization (policies/requirements, allow-or-deny) as two separate services, wired by UseAuthentication then UseAuthorization, in that order.
  8. Roles are just claims with a well-known type; resource-based authorization exists because plenty of real rules ("do you own this record") need the object being acted on, not just the caller.
  9. Entra ID refresh tokens default to 24 hours for SPAs and email-OTP logins, 90 days otherwise, rotate on every use, and revoke on different triggers depending on how the session was established — a password reset doesn't kill a passwordless session.
  10. Passwordless is not the same claim as phishing-resistant — only WebAuthn/FIDO2/passkeys are origin-bound by the protocol itself; MFA push and OTP can still be relayed by a real-time phishing attack.

Say all ten from memory before checking this page again — that's the actual test.
