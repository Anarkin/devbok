01 OAuth 2.0/2.1 flows & grant types

OAuth is a delegation protocol for authorization, not an identity protocol — it exists so a client can obtain a scoped, time-limited credential to call an API on a user's behalf without ever seeing that user's password. Interviewers open here because almost every real defect in this space starts with the wrong flow for the wrong client type, and because OAuth 2.1 (still an IETF draft, not an RFC, as of today) is really just OAuth 2.0 with the flows that turned out to be dangerous removed. At mid level you are expected to name the flows and pick the right one; at senior to explain why the deprecated ones are dangerous in terms of an actual attack; at principal to make a flow/client-type decision for a new product and defend it against a vendor SDK's defaults.

draft: OAuth 2.1 · RFC 6749: OAuth 2.0 · RFC 7636: PKCE

What problem does OAuth actually solve, and what is it explicitly not? screener

OAuth lets a resource owner (usually a user) grant a client application limited, delegated access to a resource server's API, without handing the client the owner's credentials. The client ends up with an access token — a scoped, time-limited bearer of specific permissions — instead of a password. OAuth by itself says nothing about who the user is; it has no concept of an identity claim, a login event, or "this token proves you are Alice." That is exactly the gap OpenID Connect fills on top of it.

Example

A photo-printing site wants to fetch your Google Photos album to print from. With OAuth, the site never sees your Google password; Google issues it a token scoped to photos.readonly for your account, which you can revoke without changing your password.

Follow-ups

  • So how do you actually authenticate a user with OAuth alone? — You don't, safely; using an access token as proof of identity is the "OAuth as login" antipattern that OIDC exists to fix.
  • What is a resource server vs an authorization server? — The resource server hosts the protected API and only checks tokens; the authorization server authenticates the owner and issues them.
  • Is a scope a permission? — It's a permission the client is asking for and the AS grants; the resource server still makes its own authorization decision using it as one input, not as the final word.

Wrong answer: "OAuth is how you log a user in." This is the single most common misconception in the space, and it is exactly the bug class (using an access token as an identity assertion, forgeable and audience-agnostic) that OIDC's ID token was invented to close.

Walk me through the authorization code flow, step by step. screener

The client redirects the browser to the authorization server's /authorize endpoint with its client id, requested scopes, a redirect URI and a random state. The user authenticates and consents there — never on the client. The AS redirects back to the client's redirect URI with a short-lived, single-use authorization code and the same state. The client then calls /token directly (server-to-server, not through the browser) exchanging that code — plus its client secret if it has one, or a PKCE verifier if not — for an access token and, for OIDC, an ID token. The code itself is never usable as an access credential; it only unlocks a token exchange that must originate from the party that started the flow.

Example 
GET /authorize?response_type=code&client_id=abc&redirect_uri=https://app/cb&scope=openid%20profile&state=xyz&code_challenge=E9M...&code_challenge_method=S256

POST /token
grant_type=authorization_code&code=SplxlOB...&redirect_uri=https://app/cb&client_id=abc&code_verifier=dBjftJe...

Follow-ups

  • Why is the code exchanged server-to-server instead of just returning the token in the redirect? — Redirect URLs land in browser history, referrer headers and server logs; a code is single-use and short-lived, so intercepting it alone is far less useful.
  • What stops someone from replaying an intercepted code? — It's one-time use — the AS invalidates it on first redemption — and, with PKCE, redemption also requires the verifier that only the original requester holds.
  • Why include redirect_uri again in the token request? — The AS checks it matches the one used to obtain the code, closing a class of code-injection attacks across redirect URIs.

Wrong answer: "The /authorize redirect comes back with the access token in the URL fragment." That's the implicit grant, removed in 2.1 for exactly this reason — putting a bearer token in a URL exposes it to browser history, referrers and any script running on the page.

What is PKCE, and why does OAuth 2.1 require it for every client, not just public ones? mid

PKCE (Proof Key for Code Exchange) has the client generate a random code_verifier, send its hash as code_challenge in the /authorize request, and present the original verifier at /token. The AS only issues the token if the verifier hashes to the challenge it stored — binding the code redemption to whoever started the authorization request. It was originally aimed at public clients (native and mobile apps) that can't hold a secret, defending against a malicious app on the same device intercepting the redirect and racing to redeem the code. OAuth 2.1 mandates it everywhere because it also defends confidential clients against authorization code injection, at essentially zero cost, so there was no principled reason to make it optional.

Example

A mobile app registers a custom URI scheme as its redirect URI. A second, malicious app on the device can register the same scheme and receive the redirected code — but without the original app's code_verifier, it cannot redeem it.

Follow-ups

  • S256 vs plain challenge method? — Always S256 (SHA-256 hash); plain exists only for constrained devices that cannot hash and offers no protection if the challenge itself leaks.
  • Does PKCE replace the client secret for confidential clients? — No, it's additive — a confidential web app keeps its secret and also uses PKCE under 2.1.
  • Does PKCE protect against a stolen authorization code being replayed later? — No, that's what the code's short single-use lifetime is for; PKCE protects against a different requester redeeming it.

Wrong answer: "PKCE is only relevant for mobile and native apps." That was true under 2.0's original framing but is exactly the assumption 2.1 removed — a confidential server-side web app skipping PKCE is now a finding in a 2026 security review, not a non-issue.

Why was the implicit grant removed in OAuth 2.1? mid

Implicit (response_type=token) returned the access token directly in the redirect URI fragment, designed for browser-only SPAs that couldn't do a server-side code exchange. That token now sits in browser history, in the Referer header of any subsequent request, and in any log that captures the URL — with no way to prove the token wasn't intercepted in transit, since there is no client secret or PKCE verifier involved at all. The fix wasn't a replacement grant; it was giving public clients (SPAs included) a safe way to use the authorization code flow, via PKCE, so the code exchange itself never needs a secret.

Example

A browser extension or a malicious script with access to window.location can read a token straight out of the fragment; nothing about the implicit flow prevents this because the token is deliberately placed somewhere JavaScript can reach it.

Follow-ups

  • So how should a 2026 SPA get tokens? — Authorization code + PKCE, either directly if it can accept the CORS and token-storage trade-offs, or via a Backend-for-Frontend that keeps tokens server-side entirely.
  • Is the URL fragment (after #) not sent to the server, so is it really exposed? — It's not sent over the network on that request, but it persists in browser history and is exposed to any script, extension or library running on the page — the client-side exposure is the actual threat.
  • Does 2.1 also drop the implicit-like id_token-only response type from OIDC? — Hybrid/implicit OIDC response types face the same scrutiny; code flow with PKCE is the recommended replacement there too.

Wrong answer: "Implicit is fine for SPAs since there's no client secret to steal anyway." That reasoning is precisely backwards — the absence of a secret is why PKCE-protected code flow was invented, not a reason the exposed-token flow was safe.

When would you use the client credentials grant instead of authorization code? mid

Client credentials is for when there is no resource owner in the loop at all — a service authenticating as itself to call another service, a batch job, a CI pipeline. The client presents its own credentials (a secret or, better, a signed assertion/certificate) directly to /token and gets back a token representing the application's own identity and permissions, never a user's. Authorization code is for the opposite case: a human is present, must consent, and the resulting token represents that human's delegated authority.

Example 
POST /token
grant_type=client_credentials&client_id=order-service&client_secret=***&scope=inventory.read

Follow-ups

  • Can client credentials tokens carry user context at all? — Not natively; if you need "service acting on behalf of user X" you want the token exchange or delegation patterns in unit 10, not client credentials with a smuggled user id claim.
  • Secret or certificate for the client credential? — Certificate/assertion (private_key_jwt) where you can manage it — it isn't transmitted, can't be replayed after theft of the request alone, and is what Entra ID pushes app registrations toward.
  • Where do these tokens get cached? — In the calling service, keyed by scope/audience, refreshed proactively before expiry — never re-requested per outbound call.

Wrong answer: Using client credentials for a user-facing scenario "because it's simpler than the redirect dance" — this silently drops per-user authorization and audit trail, and is a common root cause of "why does every request look like it came from the same identity" incidents.

What is the device authorization grant, and where have you actually seen it used? mid

The device flow is for clients with no usable browser or a painful text-only input surface — a smart TV, a CLI, an IoT device. The device calls /device_authorization and gets back a short user code and a verification URL; it displays both, then polls /token while the user opens that URL on a phone or laptop, authenticates, and enters the code. Once approved there, the next poll from the device returns real tokens. It moves the interactive part of the flow off the constrained device entirely.

Example

az login --use-device-code and signing into a streaming app on a TV both follow exactly this pattern: a code shown on the device, entered at a URL on another screen.

Follow-ups

  • What stops someone else from entering the code first? — The code alone grants nothing without the user then authenticating at the AS; a short expiry (typically minutes) also limits the phishing window.
  • Is polling /token wasteful? — The response includes a suggested interval, and the AS returns slow_down if you poll faster — well-behaved clients back off.
  • Known abuse pattern? — "Device code phishing" — an attacker starts the flow and sends the user code to a victim to enter, effectively granting the attacker's session; user-facing messaging should make this risk explicit.

Wrong answer: Confusing this with client credentials because "there's no browser redirect either" — device flow still authenticates a specific human and produces a delegated user token; client credentials never involves a user at all.

Why is the Resource Owner Password Credentials (ROPC) grant deprecated, and what should replace it? senior

ROPC has the client collect the user's username and password directly and post them to /token — which reintroduces the exact problem OAuth exists to remove: the client now handles raw credentials, can't support anything the credential form doesn't (MFA, passkeys, conditional access, federation), and trains users that entering a password into a random app's own form is normal, which is a phishing enabler at scale. Its only legitimate remaining niche is trusted first-party migration scenarios with a hard deadline to move off it. The replacement is always an interactive flow — authorization code with the AS's own hosted login page, so the AS (not the client) owns the credential and can layer MFA, risk evaluation and passkeys without the client changing anything.

Example

Entra ID still exposes ROPC for narrow automation/testing scenarios but explicitly documents that it cannot satisfy Conditional Access policies requiring MFA or device compliance — a hard functional wall, not just a security recommendation.

Follow-ups

  • Is ROPC in OAuth 2.1 at all? — No, it's removed entirely, alongside implicit.
  • What about a legacy desktop app that genuinely can't open a browser? — Device authorization grant, or an embedded system browser (not a WebView) invoking the interactive flow — both keep the credential entry inside the AS's surface.
  • Why can't MFA just be bolted onto ROPC? — The grant's token request has no channel for an interactive challenge/response; MFA needs a UI turn the client doesn't own.

Wrong answer: "ROPC is fine, it's just a username and password over TLS, same risk as any login form." The risk isn't transport, it's that the client now custodies the credential and cannot support MFA, passkeys, or Conditional Access — capabilities that are now table stakes, not extras.

What's the difference between a confidential and a public client, and why does it change your security obligations? senior

A confidential client can keep a secret from the end user and attacker with reasonable confidence — a server-side web app whose secret lives only in server config. A public client cannot — a SPA (secret would ship in the JS bundle), a native mobile app (secret would be extractable from the binary), a CLI. The classification decides what the AS can trust the client to prove about itself: a confidential client authenticates at /token with its secret or a signed assertion; a public client authenticates only via PKCE binding to the original request, because it has nothing else to present. Misclassifying a client as confidential when it can't actually protect a secret means the "secret" is really a public, extractable constant — worse than no secret, because it creates false confidence.

Example

A React SPA that embeds a client_secret in its bundle so the backend "checks" it is not doing anything a public client with PKCE doesn't already do better — the secret is visible in the browser's network tab and the built JS, full stop.

Follow-ups

  • Can a client be both, depending on deployment? — Yes — the same logical app might register once as confidential (server-rendered Blazor/Razor) and once as public (its mobile client), each with its own registration.
  • Does client type affect refresh token handling? — Yes, 2.1 requires public-client refresh tokens to be sender-constrained or rotated on use, because there's no secret backing their possession.
  • How does Entra ID represent this at registration time? — The app registration's platform configuration (Web vs SPA vs Mobile/Desktop) sets this, and it changes which grants and redirect URI rules are even allowed.

Wrong answer: "It's our own app, we trust it, so we can treat it as confidential and skip the extra PKCE ceremony." Trust in the app's authors is irrelevant; the question is whether the runtime environment (browser, device) can keep a secret from an attacker who controls that environment.

Explain the state parameter. What attack does it actually prevent? senior

state is an opaque value the client generates before redirecting to /authorize, stores tied to the current browser session, and verifies matches on the callback. Its security job is CSRF protection on the callback: without it, an attacker can initiate their own authorization flow, capture the resulting code, and trick a victim into visiting the callback URL with that code — linking the victim's session to the attacker's account. It's also commonly (and legitimately) used to carry small amounts of app state — like "return to this page after login" — through the redirect, but that convenience use is secondary to the security purpose.

Example 
var state = Convert.ToBase64String(RandomNumberGenerator.GetBytes(32));
HttpContext.Session.SetString("oauth_state", state);
// ...later, on callback:
if (callbackState != HttpContext.Session.GetString("oauth_state")) return BadRequest();

Follow-ups

  • Isn't PKCE's code_verifier check enough on its own? — It stops code redemption by the wrong party but doesn't by itself stop a CSRF-style session-linking attack at the callback before redemption; OIDC also adds nonce for a related but distinct replay concern on the ID token.
  • What if state is predictable or omitted? — Then login CSRF is possible: the attacker's session gets silently attached to whatever the victim authenticates as.
  • Should state be signed or encrypted? — It only needs to be unguessable and session-bound; if you stuff sensitive data into it, encrypt it, but the common pattern is to keep it opaque and store the real payload server-side.

Wrong answer: "state is just for passing my app's return-to URL through the redirect." That's a real, common use, but describing only the convenience use and missing the CSRF defense is the answer that gets probed hardest — and is the answer of someone who copied the parameter without understanding why it's mandatory.

You're adding OAuth to a new native mobile app in 2026. What flow, what client type, and what do you insist on regardless of what the vendor SDK defaults to? principal

Authorization code with PKCE, public client, using the system browser or an in-app browser tab (Android Custom Tabs / iOS ASWebAuthenticationSession) — never an embedded WebView, which can't be trusted not to intercept credentials and doesn't get the user's existing SSO session. I'd insist on exact redirect URI matching (no wildcard paths), a claimed HTTPS redirect URI or a well-registered custom scheme (not a generic one collidable by another app), and short-lived refresh tokens with rotation and reuse detection rather than a single long-lived refresh token baked into the app. I'd also push back on any SDK default that stores tokens in plain shared preferences/UserDefaults instead of the platform keystore/keychain, and would want biometric-gated access to the stored refresh token as a baseline, not an upsell feature.

Example

MSAL for iOS/Android already implements this correctly by default (system browser, PKCE, secure storage) — the judgment call is refusing an older or third-party SDK that still defaults to a WebView "for a smoother UX."

Follow-ups

  • What if product insists on an embedded, branded login screen? — Push back with the SSO-session-loss and phishing-surface argument; if the business truly requires it, isolate the WebView to the AS's own domain and never let the app itself read the DOM.
  • How do you validate the vendor SDK is actually doing this correctly? — Read the actual network trace of a login, not just the docs — confirm the system browser is invoked and the code exchange happens off the WebView.
  • What's your fallback if the platform keystore isn't available (rooted/jailbroken device)? — Detect it and degrade deliberately — shorter token lifetime and re-auth prompts, not silent storage in a less secure location.

Wrong answer: Accepting the SDK's defaults without inspection "because it's from a reputable vendor" — vendor defaults optimize for adoption and UX, and the embedded-WebView shortcut still ships in real SDKs in 2026; principal-level judgment is verifying, not trusting.

02 OpenID Connect fundamentals

OIDC is a thin identity layer on top of OAuth 2.0: it standardizes how a client learns who authenticated, not just what they're authorized to call. Interviewers probe this right after OAuth because the two are constantly conflated, and because almost every "we rolled our own SSO" incident traces back to treating an OAuth access token as proof of identity. At mid level you're expected to name the ID token and its claims; at senior to validate one correctly and explain the discovery document; at principal to reason about subject identifiers and logout semantics across a federated estate.

OpenID Connect Core 1.0 · OIDC Discovery 1.0 · RP-Initiated Logout 1.0

What's the difference between an ID token and an access token? screener

The ID token is a JWT for the client: it's a signed assertion that says "this specific user authenticated, at this time, at this authorization server," addressed to this client's aud, and the client is meant to read it, validate it once, then throw it away. The access token is an opaque-to-the-client credential for the resource server: the client never inspects it, just attaches it to API calls, and the resource server is the one that validates it. Conflating them is the root of most OIDC-shaped bugs: sending an ID token to an API as if it were a bearer credential, or trying to use an access token's claims as user profile data.

Example

After code exchange you get back { access_token, id_token, token_type, expires_in }. You decode id_token once to get sub/name/email for the session; you never decode access_token at all — you just forward it as Authorization: Bearer <access_token>.

Follow-ups

  • Is an access token always a JWT? — No — the spec treats it as opaque; Entra ID's are JWTs, but a compliant client must not assume that and should never parse it to make decisions.
  • Can the ID token have an audience restriction that matters? — Yes, aud must equal this client's own client_id; a different client's ID token replayed at yours must be rejected.
  • Does the ID token expire the same way as the access token? — No — it's validated once at the moment of sign-in and then discarded; its exp isn't meant to gate later requests the way an access token's is.

Wrong answer: "The ID token is just a longer-lived access token with more claims." That collapses the client/resource-server boundary the two tokens exist to separate, and is exactly the mistake behind "use the ID token as your API bearer token" advice you'll still find in old blog posts.

Walk through the OIDC discovery document. Why does it matter operationally? mid

GET /.well-known/openid-configuration returns a JSON document listing every endpoint (authorization_endpoint, token_endpoint, userinfo_endpoint, jwks_uri, end_session_endpoint), the supported scopes, response types, signing algorithms, and claims. A conformant client is configured with just the issuer URL and fetches this document once (caching it) rather than hardcoding every endpoint, which is what lets an IdP rotate infrastructure or add capabilities without every client shipping a config change. jwks_uri is the operationally critical one: it's where the client fetches the current signing keys to validate tokens, and it's expected to be polled/cached with a refresh-on-kid-miss strategy so key rotation doesn't require a client deploy.

Example 
{
  "issuer": "https://login.microsoftonline.com/{tenant}/v2.0",
  "authorization_endpoint": "https://login.microsoftonline.com/{tenant}/oauth2/v2.0/authorize",
  "token_endpoint": "https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token",
  "jwks_uri": "https://login.microsoftonline.com/{tenant}/discovery/v2.0/keys"
}

Follow-ups

  • How often should a client refetch the discovery document itself? — Rarely — cache it long-term (hours to a day) and refetch on validation failure; most libraries (including ASP.NET Core's OIDC handler) do this automatically.
  • What happens if jwks_uri rotates a key without warning? — A correct client re-fetches the JWKS when it sees an unrecognized kid in a token header rather than failing hard, which is exactly how Microsoft.IdentityModel's key resolution behaves.
  • Is the discovery document itself signed? — No, it's fetched over TLS; its authenticity rests on the issuer's HTTPS endpoint, which is why the issuer value in every token must be checked against a known-good, explicitly configured value, not just "whatever the discovery doc said."

Wrong answer: Hardcoding the token/authorize/JWKS URLs from documentation instead of using discovery. It works until the IdP does a routine infrastructure change, at which point every hardcoded client breaks simultaneously with no warning — discovery exists precisely so that never happens.

What is nonce for, and how is it different from state? mid

nonce is a random value the client sends in the /authorize request and that the AS is required to echo back as a claim inside the ID token itself. Its job is replay protection for the ID token: without it, a captured ID token from one login could be replayed into a different session as if a fresh authentication had just happened. state protects the OAuth callback (CSRF at the redirect URI); nonce protects the OIDC token (replay of the identity assertion) — they solve adjacent but distinct problems and a correct implementation uses both, independently generated and independently verified.

Example

The client stores nonce=n-0S6_WzA2Mj before redirecting; on callback it decodes the returned id_token and checks its nonce claim matches the stored value before accepting the token as valid.

Follow-ups

  • Can you skip nonce if you already validate state? — No — state never enters the token, so validating it says nothing about whether the ID token itself is fresh or being replayed.
  • Does the authorization code flow still need nonce, given PKCE already binds redemption? — Yes; PKCE binds who can redeem the code, nonce binds the resulting ID token to this specific authentication request — different guarantees.
  • Where do most real bugs with nonce come from? — Not validating it at all (many hand-rolled integrations skip it silently) or storing it in a way that survives across tabs/sessions, defeating its purpose.

Wrong answer: "nonce and state are basically the same thing, pick one." They protect different messages (the callback vs. the token) against different attacks (CSRF vs. replay), and a library that only implements one has a real, exploitable gap.

What exactly must a client check to correctly validate an ID token? senior

Signature first — verify against a key fetched from jwks_uri matching the token's kid, using the algorithm the AS is configured to use (never trusting an algorithm named inside the token itself, see unit 03). Then the claims: iss equals the expected issuer exactly, aud contains this client's own client_id, exp hasn't passed and iat is sane (reject tokens claiming to be issued in the future beyond clock-skew tolerance), and nonce matches what was sent. For the authorization code flow specifically, also check at_hash if present (a hash of the access token, binding the two together so one can't be swapped for another issued in a different response). Skipping any one of these — especially aud or issuer — is how a token minted for a different app or a different tenant gets accepted.

Example 
var result = await tokenHandler.ValidateTokenAsync(idToken, new TokenValidationParameters {
    ValidIssuer = "https://login.microsoftonline.com/{tenant}/v2.0",
    ValidAudience = clientId,
    IssuerSigningKeys = jwks.Keys,
    ClockSkew = TimeSpan.FromMinutes(2)
});

Follow-ups

  • Why validate the algorithm explicitly rather than trust the token's alg header? — Because "trust the header" is exactly the alg: none / algorithm-confusion class of bug covered in unit 03 — the validator must be pinned to expected algorithms server-side.
  • What clock skew tolerance is reasonable? — A couple of minutes; ASP.NET Core's default is 5, which is generous — tightening it is a defensible senior-level hardening call for high-security systems.
  • Do you validate the ID token on every request or only at sign-in? — Only at sign-in — after that you rely on your own session (cookie or server-side session store), not on re-checking the ID token per request.

Wrong answer: "I decode the JWT, check it's not expired, and read the claims." Decoding without signature verification accepts any token an attacker crafts with an arbitrary sub and no proof it came from the real AS — this is the single most common auth vulnerability found in code review.

Why is using the ID token to call your own API a bad pattern, even though it's technically a valid JWT? mid

The ID token's aud is the client, not the API — a resource server accepting it has to either ignore audience validation (a real hole: any client the same IdP serves can mint a token that validates) or special-case its own client id as an acceptable API audience, which quietly merges the "prove who signed in" and "prove what this call may do" concerns. Access tokens carry scopes and can be revoked, refreshed, and audience-restricted per resource independently of the identity assertion; ID tokens have none of that machinery and typically live far longer in client memory than an interviewer expects an API credential to.

Example

A team wires [Authorize] against the ID token because "it already has the user's claims," then can't add a second downstream API without either minting a second IdP client or leaking the same token to two audiences — the access-token-with-scopes model that OAuth already solved for this gets reinvented badly.

Follow-ups

  • What if I genuinely only ever have one API and one client? — Even then, request an access token for that API's scope; it costs one extra field in the token response and buys you revocation and scope narrowing for free later.
  • Does Entra ID make this mistake easy to fall into? — Yes — MSAL returns both tokens together, and copy-pasted samples sometimes grab id_token for the Authorization header by accident; it's worth a lint/code-review check.
  • Is there any legitimate use for sending an ID token to a backend? — A BFF's own backend validating the ID token once at the login callback, before it establishes the session cookie — that's the identity-assertion use case it was built for.

Wrong answer: "It's still a valid, signed JWT with the user's identity in it, so the API can just validate it the same way." Validity isn't the issue — audience scoping and revocation semantics are, and the API accepting a token minted for a different purpose is a design smell that shows up in security review.

When do you call the UserInfo endpoint versus just reading claims off the ID token? mid

The ID token is meant to carry the minimal claims needed to establish who signed in (sub, and whatever the requested scopes add — name, email, etc.) and is size-constrained since it round-trips through a redirect in some flows. UserInfo is a bearer-token-protected REST endpoint you call with the access token when you need claims that either weren't included in the ID token, are large or slow to compute (group memberships, custom directory attributes), or need to be fresher than the moment of login — a call to /userinfo reflects current directory state, not what was true when the token was issued.

Example 
GET /userinfo
Authorization: Bearer eyJ0eXAiOiJKV1Qi...

Follow-ups

  • Does UserInfo require its own scope? — It requires whatever scopes gate the claims you're asking for (profile, email, etc.) — same scopes that would have populated the ID token, just fetched out-of-band.
  • Is UserInfo data more trustworthy than ID token claims? — Not more trustworthy, just fresher — both ultimately come from the same directory; the ID token is a point-in-time signed snapshot, UserInfo is a live read.
  • Should a session be refreshed from UserInfo periodically? — For anything security-sensitive (role/group membership), yes — caching a login-time snapshot for the lifetime of a long session is a real source of stale-authorization bugs.

Wrong answer: Calling UserInfo on every single request "to always have fresh claims." That turns every request into two network calls and a dependency on the IdP's uptime; the fix is refreshing on a sane interval or on token refresh, not per-request.

What do the standard scopes openid, profile and email actually control? screener

openid is what turns an OAuth request into an OIDC request at all — without it you get an OAuth authorization response with no ID token. profile adds a bundle of claims (name, family_name, picture, locale, etc.) to the ID token/UserInfo response; email adds email and email_verified specifically, since some IdPs treat email as sensitive enough to gate separately from the rest of the profile. None of these scopes grant any API access on their own — they only shape what identity claims come back; a resource-server scope like api://orders/read is a completely separate request on the same call.

Example

scope=openid profile email api://orders.read in one authorize request returns both an ID token populated with name/email claims and an access token scoped for the orders API — two different mechanisms sharing one round trip.

Follow-ups

  • What happens if you request scopes the IdP doesn't recognize? — Behavior varies by AS — some silently drop unknown scopes, some error; never assume a typo'd scope fails loudly.
  • Is offline_access a standard OIDC scope? — It's from the OIDC spec's optional set, and it's what actually gets you a refresh token, independent of openid/profile/email.
  • Can a resource-owner deny individual claims within a granted scope? — Depends on the IdP's consent UI; some let users grant profile but redact specific fields, most just grant-or-deny the whole scope.

Wrong answer: "I request profile to get the user's roles for authorization." Roles/groups are not part of the standard profile claim set; they come from provider-specific claims (Entra ID's roles/groups) or a dedicated API call, and treating profile as an authorization signal conflates identity with permissions.

How does OIDC logout actually work — what's the difference between RP-initiated logout and front-/back-channel logout? senior

RP-initiated logout is the simple case: the client redirects the browser to the AS's end_session_endpoint with an id_token_hint and a post_logout_redirect_uri; the AS clears its own session and redirects back. That only ends the session at the AS and at the one client that initiated it — if the user is signed into three apps via SSO, the other two still think they're logged in until their own cookies expire. Front-channel and back-channel logout exist to fan that out: front-channel loads tiny hidden iframes for each other logged-in RP so their JS can clear local session state; back-channel has the AS call each RP's logout endpoint server-to-server with a signed logout token, which works even for RPs with no active browser tab open, at the cost of every RP needing a publicly reachable logout webhook.

Example

Signing out of one Microsoft 365 app while still holding an open tab of another and finding the second app requires a fresh interactive login next click, rather than being silently signed out, is exactly what happens when only RP-initiated logout is wired up and front-/back-channel isn't.

Follow-ups

  • Which does ASP.NET Core support out of the box? — SignOutAsync against the cookie and OIDC schemes drives RP-initiated logout cleanly; front-/back-channel logout requires wiring up the relevant endpoints yourself or via a library that implements the spec.
  • Why is back-channel logout considered more reliable? — It doesn't depend on the user having a tab open or third-party cookies/iframes working, which browsers increasingly restrict — front-channel logout is getting less reliable as browsers tighten cross-site iframe behavior.
  • Does logging out at the AS invalidate already-issued access tokens? — Not by itself, unless the AS also revokes them or they're short-lived enough that this doesn't matter much — see unit 08 on revocation.

Wrong answer: "Logout just means clearing the local cookie/session — the protocol doesn't need to be involved." That leaves the AS's own SSO session alive, so the very next login attempt silently re-authenticates the user without a credential prompt, which is rarely what "log out" was supposed to mean to the user.

Why would an identity provider issue a pairwise sub instead of a public one, and what does that cost you? principal

A public subject identifier is the same sub value for a given user across every client the IdP serves — convenient, but it lets two unrelated relying parties collude (or a single breached RP leak the value) to correlate the same person's activity across services. A pairwise identifier is deliberately different per (issuer, client) pair — the same human gets a different, stable sub at app A than at app B — which kills that cross-client correlation at the protocol level, at the cost that you can no longer use sub as a natural key if you ever need to match the same person across two of your own client registrations (you need a separate, IdP-specific mapping or a different claim like an internal directory id).

Example

A consumer IdP serving many unrelated third-party apps (the B2C shape in unit 13) is the typical case for pairwise; an internal enterprise IdP where every client belongs to the same organization usually has no correlation risk to defend against and stays with public identifiers for simplicity.

Follow-ups

  • Is pairwise sub stable over time for the same user at the same client? — Yes, by definition — it must remain constant for that (issuer, client, user) triple across logins, or session/account linkage would break on every sign-in.
  • Does Entra ID support pairwise identifiers? — It defaults to a tenant-and-app-specific sub already close to pairwise in spirit; the OIDC-spec pairwise/public toggle is more commonly a consumer-IdP (B2C-style) configuration choice.
  • What claim would you use instead if you need cross-client correlation deliberately? — A directory-level immutable id exposed as a custom claim under an explicit data-sharing agreement — never by repurposing sub against its intended privacy property.

Wrong answer: "sub is sub, it's the user's unique ID everywhere." Whether that's true is exactly the public-vs-pairwise design decision, and assuming public semantics when the IdP is pairwise silently breaks any code that tries to correlate users across app registrations.

03 JWT structure, validation & pitfalls

JWTs are the wire format almost everything in this topic eventually rides on — access tokens, ID tokens, and often session tokens too — so interviewers use them to test whether you understand a bearer credential is only as safe as its validation code. This is also where the classic, still-exploitable bugs live: algorithm confusion, missing signature checks, treating the payload as confidential. At mid level you're expected to know the structure and the standard claims; at senior to explain a real JWT vulnerability class in attacker terms; at principal to make claim-design and key-rotation calls for a system you don't fully control end to end.

RFC 7519: JWT · RFC 7515: JWS · RFC 7517: JWK

What are the three parts of a JWT, and what does each one actually do? screener

A JWT is three base64url segments joined by dots: header.payload.signature. The header names the signing algorithm (alg) and, usually, a key id (kid) telling the verifier which key to use. The payload is the set of claims — standard ones like iss, aud, exp, sub, plus whatever custom claims the issuer adds — and it is only base64url-encoded, not encrypted, so anyone holding the token can read it. The signature is computed over the header and payload with the algorithm the header names, and is the only part that makes the token trustworthy: it's what a verifier checks against a known key before believing anything in the payload.

Example 
eyJhbGciOiJSUzI1NiIsImtpZCI6ImFiYzEyMyJ9   ← header: {"alg":"RS256","kid":"abc123"}
.eyJzdWIiOiIxMjM0NSIsImV4cCI6MTc1NzQwMDAwMH0   ← payload: {"sub":"12345","exp":1757400000}
.dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk   ← signature

Follow-ups

  • Can you read the payload without a library? — Yes — base64url-decode the middle segment; this is exactly why JWTs must never carry secrets.
  • What happens if you tamper with the payload without re-signing? — The signature no longer matches and a correct verifier rejects the token outright.
  • Is kid mandatory? — No, but any issuer rotating keys needs it so a verifier can pick the right key from a JWKS with multiple entries.

Wrong answer: "The payload is encoded so it's basically encrypted." Base64url is an encoding, not encryption — no key is needed to read it, only to forge a valid signature over a modified version, and confusing the two leads people to put secrets in JWT payloads.

Explain the alg: none / algorithm-confusion vulnerability. How does a correct verifier avoid it? senior

Some early JWT libraries let the caller pass the token's own alg header into the verification call, "so it can verify with whatever algorithm was used." An attacker exploits that by crafting a token with alg: none (no signature required at all) or, more dangerously, by taking a token meant to be RS256-signed and re-labeling it HS256 — then signing it with the RS256 public key (which is, by definition, public) used as an HMAC secret. If the verifier's HMAC check happens to accept that, the attacker has forged a token the server trusts, entirely from public information. The fix is structural, not a patch: the verifier must be configured with an explicit allow-list of algorithms it will accept and never let the token's own header pick the verification algorithm.

Example 
new TokenValidationParameters {
    ValidAlgorithms = new[] { SecurityAlgorithms.RsaSha256 }, // pinned — never read from the token
    IssuerSigningKey = knownRsaPublicKey
};

Follow-ups

  • Is this still exploitable against modern libraries? — Well-maintained libraries (including .NET's) fixed this years ago by requiring explicit algorithm pinning, but it still shows up in custom JWT code and less mature ecosystems — it's a design-review question, not just a library-version question.
  • What's the underlying principle to state in an interview? — Never let untrusted input (the token itself) choose the security policy used to validate that same input.
  • Does this affect symmetric-only systems too? — A pure-HS256 system avoids the RSA-key-as-HMAC-secret variant, but still needs to reject alg: none and any algorithm switch away from HS256.

Wrong answer: "As long as you check the signature is present, you're safe." Presence isn't the bar — the vulnerability is specifically about the verifier trusting the token to name its own correct algorithm; a present-but-wrong-algorithm signature can still validate successfully if the algorithm isn't pinned server-side.

RS256 vs HS256 — when do you use which, and why does it matter for a multi-party system? mid

HS256 is symmetric: the same secret signs and verifies, so every party that can verify a token can also forge one — fine when the issuer and the only verifier are the same process or a tightly controlled pair. RS256 (and its cousins) is asymmetric: the issuer signs with a private key and publishes only the public key via JWKS, so any number of resource servers can verify tokens without ever holding anything that lets them mint new ones. Any OIDC/OAuth AS serving more than one downstream API uses RS256 (or ES256) for exactly this reason — it's the difference between "give every microservice the ability to impersonate the identity provider" and "give every microservice a read-only verification key."

Example

Entra ID signs access and ID tokens with RS256 and rotates the private key behind the scenes; every resource server across every tenant verifies against the public keys published at jwks_uri, never touching a private key at all.

Follow-ups

  • Would you ever choose HS256 for a new OAuth deployment? — Only for a same-team, single-verifier internal token (e.g., a short-lived service-to-service token where issuer and verifier are the same trust boundary) — never for anything a third party or another team's service must verify.
  • What's the elliptic-curve alternative and why might you prefer it? — ES256 — smaller signatures and faster verification than RS256 at equivalent security strength; increasingly the default for new deployments that don't need RS256 for legacy compatibility.
  • What's the actual attack if you use HS256 across a multi-team system? — Any team holding the shared secret to verify can also mint arbitrary tokens for any user or scope — a lateral-trust blast radius that RS256's public/private split eliminates by construction.

Wrong answer: "HS256 is fine, it's simpler and the secret is just an environment variable." Simplicity is real, but "just an environment variable" shared across every verifying service is exactly the single point of total compromise RS256 was designed to avoid in a multi-verifier system.

Beyond the signature, which claims must a resource server always validate, and what does each one actually stop? screener

iss (issuer) must equal a known, explicitly configured value — never "whatever the token says," or a token from a different tenant/AS validates. aud (audience) must include this specific API/resource — otherwise a token minted for a different downstream API is accepted here too, a real and common multi-API misconfiguration. exp (expiry) and, if present, nbf (not-before) bound the token's validity window against replay of an old token or premature use of one issued for the future. Most middleware (ASP.NET Core's JWT bearer handler included) checks all of these by default when configured with the right issuer/audience — the bug is almost always disabling one of these checks "to make an integration work" and forgetting to re-enable it.

Example 
options.TokenValidationParameters = new TokenValidationParameters {
    ValidateIssuer = true,  ValidIssuer = expectedIssuer,
    ValidateAudience = true, ValidAudience = "api://orders",
    ValidateLifetime = true, ClockSkew = TimeSpan.FromMinutes(2)
};

Follow-ups

  • What's a realistic incident caused by skipping aud validation? — A token meant for the "reports" API accepted by the "orders" API too, because both trust the same issuer and nobody checked audience — effectively merging two APIs' authorization boundaries by accident.
  • Is iat (issued-at) worth checking? — It's informational more than a hard gate; some systems use it to enforce a maximum token age independent of exp, which is a reasonable defense-in-depth addition.
  • What if the AS issues tokens for multiple valid issuers (multi-tenant)? — Validate against the set of issuers your app is actually configured to trust, dynamically resolved per tenant — never a wildcard match on the issuer pattern.

Wrong answer: "If the signature checks out, the token is legitimate, that's the important part." A validly-signed token from the right issuer but the wrong audience, or one that's expired, is still a legitimate credential — just not one that authorizes this call; signature validity and claim validity are separate, both-required checks.

What's the difference between a JWS and a JWE? Are the access tokens you work with usually encrypted? mid

A JWS (JSON Web Signature) is the signed-but-readable format almost everyone means when they say "JWT" — anyone can decode the payload, only the signer can produce a valid signature over it. A JWE (JSON Web Encryption) additionally encrypts the payload, so only a holder of the decryption key can read the claims at all; it costs more to produce and verify and is used when the claims themselves are sensitive enough that even the token's bearer/transport path shouldn't see them in the clear — nested JWTs (a signed JWT wrapped inside an encrypted one) show up in some high-assurance OIDC profiles (FAPI) for exactly this reason. In the vast majority of everyday OAuth/OIDC deployments — Entra ID included — access and ID tokens are JWS, not JWE: the payload is signed and readable, and the actual sensitive data (a password, a secret) is simply never put in a claim.

Example

Anyone can paste an Entra ID access token into jwt.ms and read every claim in plain text — that's expected behavior for a JWS, not a bug, which is exactly why nothing sensitive is ever placed in one.

Follow-ups

  • When would you actually reach for a JWE? — When the token transits through an untrusted intermediary that must not read its contents (e.g., a token routed through a third-party proxy) — genuinely rare outside high-assurance financial-grade profiles.
  • Does encrypting a token remove the need to sign it? — No — encryption gives confidentiality, not integrity/authenticity; a nested JWT (signed then encrypted) is the pattern that gets both.
  • Is TLS not "encryption enough" for a JWS in transit? — TLS protects the token in transit between two parties; it says nothing about a party downstream of the original recipient (a logging system, a third intermediary) that also sees the raw token.

Wrong answer: "JWTs are encrypted, that's what makes them secure." The security property a signed JWT gives you is integrity and authenticity, not confidentiality — believing otherwise is precisely how sensitive data ends up in a claim that then leaks via logs, browser history, or a JWT debugger site.

Why shouldn't you put sensitive data — a password, an SSN, a full PII record — in a JWT payload, even one that's signed correctly? mid

A JWS payload is base64url-encoded plaintext, readable by anyone who ever holds the token: the browser, any proxy or load balancer that logs headers, any APM/observability tool that captures request bodies, the token itself sitting in browser storage or history. Signing proves the issuer produced it and it hasn't been altered; it does nothing to hide it. Beyond confidentiality, size is a second, more mundane reason: bloating every token with data the recipient rarely needs makes every request heavier and makes tokens land in HTTP logs and URL-length limits more often than teams expect.

Example

An access token carrying a customer's full billing address "so the API doesn't have to look it up" means that address now sits in every access log, every APM trace, and every browser dev-tools network tab for the token's entire lifetime — a data-classification finding waiting to be discovered.

Follow-ups

  • What should go in the token instead? — A stable identifier (sub) and coarse-grained authorization signals (scopes, roles); the API looks up anything sensitive or volatile from its own store keyed by that identifier.
  • Does this apply to internal service-to-service tokens too? — Yes — internal doesn't mean untraceable; the same log/APM/storage exposure applies inside your own network.
  • Is there a size-based rule of thumb? — If a claim would meaningfully grow with data unrelated to authorization, it's the wrong place for it — token size should scale with the number of permissions, not the size of the user's profile.

Wrong answer: "It's fine, only the client that requested the token ever sees it." Tokens are attached to every subsequent request as a bearer header, which means every hop, proxy, and log along the request's path sees it too — "only the client sees it" is false the moment the token leaves the client.

How does key rotation work for JWT signing keys without breaking tokens already in flight? senior

The AS publishes a JWKS (a set, not a single key) at jwks_uri, and every signed token's header carries a kid identifying which key in that set signed it. To rotate, the AS adds the new key to the JWKS before switching to sign with it, keeps the old key published (but no longer used for signing) for at least as long as its longest-lived already-issued token could still be valid, then finally removes it. A verifier that fetches the JWKS lazily on kid cache miss — rather than only at startup — never notices the rotation happen; one that hardcodes a single key or caches the JWKS forever will start rejecting every new token the moment the AS rotates.

Example

Entra ID rotates its signing keys on its own schedule and simply expects every relying party's JWKS cache to refresh on a kid miss — there's no coordination email, because the protocol is designed not to need one.

Follow-ups

  • What's the overlap window based on? — The maximum lifetime of a token signed with the old key — for short-lived access tokens (minutes) the overlap can be short; a rotation policy that ignores refresh-token or ID-token lifetimes can retire a key too early.
  • What breaks if a verifier caches the JWKS forever? — Every token signed after rotation fails signature validation with no useful error beyond "unknown kid" — a classic silent-outage-until-someone-checks-logs bug.
  • Should you rotate on a schedule or only on suspected compromise? — Both — routine rotation (so the mechanism is exercised and nobody's code has bit-rotted around a "key never changes" assumption) plus immediate rotation on suspected compromise.

Wrong answer: "Rotate by replacing the key and redeploying every verifier at the same time." That reintroduces exactly the tight-coupling problem asymmetric keys and JWKS were meant to remove — the whole point of the overlap-and-kid design is that verifiers never need a coordinated deploy.

JwtSecurityTokenHandler vs JsonWebTokenHandler in .NET — what's the practical difference, and which should new code use? mid

JwtSecurityTokenHandler (in System.IdentityModel.Tokens.Jwt) is the original .NET JWT handler and is synchronous end to end; JsonWebTokenHandler (in Microsoft.IdentityModel.JsonWebTokens) is the newer implementation with an async validation path, materially faster parsing, and lower allocations, and since .NET 8 it's the default the ASP.NET Core JWT bearer handler wires up via JwtBearerOptions.TokenHandlers. Functionally they validate the same tokens against the same rules — this is a performance and API-shape difference, not a security-semantics one — but new code should default to JsonWebTokenHandler both for the performance and because it's where Microsoft's own investment (and newer features like PoP validation) is landing.

Example 
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options => {
        options.TokenHandlers.Clear();
        options.TokenHandlers.Add(new JsonWebTokenHandler()); // explicit; .NET 8+ prefers this by default
    });

Follow-ups

  • Do you need to change validation code when switching handlers? — TokenValidationParameters is shared between both, so the switch is mostly additive configuration, not a rewrite.
  • Is JwtSecurityTokenHandler deprecated? — Not removed, but treated as the legacy path — still fine for existing code that has no performance pressure to migrate, worth flagging in a code review of new code.
  • Does this distinction matter outside ASP.NET Core, e.g., in a console app validating tokens? — Yes, both are usable directly; the same async/perf trade-off applies wherever you're validating JWTs in .NET.

Wrong answer: "They're interchangeable so it doesn't matter which one a codebase uses." True functionally for basic validation, but citing no preference in a 2026 interview reads as not knowing where the ecosystem has actually moved — the modern-vs-legacy distinction is exactly what senior-level "be precise about versions" answers are checked for.

A token keeps growing as more roles and permissions get added to it. What's the actual problem, and how do you fix it? senior

A JWT that enumerates every role or permission a user has, rather than a small set of coarse claims, grows with the org chart: a user in twelve groups with forty effective permissions produces a token that's kilobytes of header alone, which then rides on every single API call, gets copied into every access log line, and can bump into hard size limits (some proxies/load balancers cap header size around 8–16 KB). The fix is almost never "compress the token" — it's to shrink what the token asserts: carry an opaque group/role reference or a small set of high-level scopes, and let the resource server (or a dedicated policy/authorization service) resolve fine-grained permissions from a system of record, cached appropriately, rather than shipping the whole permission graph on every request.

Example

Entra ID actually enforces this at the platform level: it caps the number of groups claims it will emit directly in a token and falls back to a "has more groups" overage indicator plus a Microsoft Graph call to fetch the rest — a real, load-bearing example of exactly this trade-off.

Follow-ups

  • Isn't fetching permissions per-request slower than reading them off the token? — It adds a lookup, but a cached policy decision point (or a locally cached permission set with a short TTL) is usually cheaper in practice than the header-size and log-volume cost of an ever-growing token.
  • Is there a middle ground short of a full policy service? — Coarse roles in the token (admin, member) plus fine-grained, resource-specific checks (can this admin touch this specific record) done in application code against a database — token carries the coarse signal, app carries the rest.
  • Does this affect refresh-token design too? — Yes, indirectly — a heavier access token means a heavier refresh cycle; keeping the token lean keeps the whole token lifecycle cheap.

Wrong answer: "Just base64-compress the claims before encoding, or switch to a shorter claim naming scheme." That treats a modeling problem as an encoding problem — it buys a little size back and defers the real issue, which is that the token is being asked to be an authorization database instead of an identity/coarse-scope credential.

You're designing the JWT claims for a token that will flow through four hops of a microservice call chain. What do you put in it, and what do you deliberately leave out? principal

I'd keep the token itself minimal and stable across hops — sub, aud scoped to the chain's trust boundary (or exchanged per-hop via unit 10's token-exchange pattern if hops cross trust boundaries), a small set of coarse scopes, and a correlation id for tracing, deliberately excluding anything that changes based on which hop is currently handling the request. I'd resist the temptation to let each service add "just one more claim it needs" — that's how a token designed for hop one silently becomes a shared, ever-growing contract every downstream service depends on and none of them owns. Where a downstream hop needs fine-grained data (the caller's specific entitlements for this resource), I'd have it look that up from its own store or a shared policy service keyed by sub, not read it off a claim that hop one had no reason to know about.

Example

An order goes through gateway → orders-service → inventory-service → shipping-service; the token that traverses all four carries the same sub and a orders.write scope throughout, while shipping-service independently looks up the user's shipping-address permissions rather than expecting them to have been threaded through as a claim by a service two hops upstream that has never heard of shipping addresses.

Follow-ups

  • Do all four hops trust the same signing key? — Only if they're inside one trust boundary; crossing boundaries (a different team, a different security domain) is exactly when you introduce token exchange rather than passing the same bearer token through unmodified.
  • How do you prevent claim creep once several teams own different hops? — Treat the claim schema as a versioned, reviewed contract with an owning team, the same discipline you'd apply to a shared API schema — not an implicit free-for-all.
  • What if hop three needs to know something about the original caller that hop one never included? — That's a signal the claim design was incomplete, or that hop three should be looking the data up itself rather than expecting an upstream hop to have anticipated its need.

Wrong answer: Letting every service along the chain append whatever claims it personally finds convenient. It produces an unbounded, unowned, ever-growing token whose schema nobody can safely change because nobody knows which of the four services actually reads which claim — the microservices version of a God object.

04 Tokens vs cookies: session architecture

Once the protocol mechanics are settled, interviewers pivot to where you actually keep the credential between requests — and this is where "technically correct" OAuth advice collides with real browser security constraints. Every one of these questions is really asking whether you understand the browser as the hostile-by-default environment it is. At mid level you're expected to know cookies vs bearer tokens by name; at senior to reason about XSS/CSRF trade-offs concretely; at principal to design the session architecture for a system with more than one kind of client.

MDN: SameSite cookies · OAuth for Browser-Based Apps

Cookie-based sessions vs bearer tokens — what's the fundamental trade-off? screener

A cookie is attached to requests automatically by the browser based on domain/path rules, can be marked HttpOnly so JavaScript can never read it, and is naturally scoped to same-origin/same-site requests — but that automatic attachment is also what makes CSRF a cookie problem in the first place. A bearer token has to be attached explicitly by application code on every request, which means JavaScript must be able to read it to do that — so it can't be HttpOnly, and anything that can run script on the page (an XSS bug, a compromised dependency) can read and exfiltrate it. Neither is unconditionally safer; they trade one attack surface (CSRF, mitigated by SameSite) for another (XSS-driven token theft, mitigated by never letting JS hold the token at all).

Example

A traditional server-rendered app naturally fits cookies (no JS needs the credential); a SPA calling a separate API historically reached for a bearer token in localStorage simply because it was easier to wire up — which is exactly the choice unit 04 spends most of its time complicating.

Follow-ups

  • Is a cookie holding a JWT still a "bearer token" in spirit? — Yes — the transport (cookie vs header) is orthogonal to the payload format; you can and often should combine an HttpOnly cookie with a JWT or opaque session id inside it.
  • Which does OAuth's spec assume? — The core spec is transport-agnostic on this; the "OAuth for Browser-Based Apps" guidance folded into 2.1 is what explicitly steers browser clients toward keeping tokens out of JS reach.
  • Does this trade-off disappear for native mobile apps? — Mostly — a native app storing a token in platform keychain/keystore doesn't face the DOM-based XSS threat a browser page does, so the calculus shifts back toward "bearer token, safely stored" being fine.

Wrong answer: "Bearer tokens are stateless and therefore always more scalable/secure than cookies." Statelessness is a server-side scaling property, not a security property, and conflating the two is how teams end up shipping tokens to localStorage "for scalability" while accepting a much larger client-side attack surface than a cookie-based design would have had.

Why are HttpOnly/Secure/SameSite cookies considered more resistant to token theft than tokens in localStorage? mid

HttpOnly means the cookie is invisible to document.cookie and any other JS API — an XSS payload running on the page simply cannot read it, full stop, whereas anything in localStorage (or sessionStorage) is readable by any script on the page, first-party or injected. Secure stops the cookie from ever being sent over plain HTTP, closing a network-level downgrade path. SameSite=Lax or Strict stops the cookie being sent on most cross-site requests, which is the CSRF defense. None of this makes cookies immune — a same-site request can still trigger unwanted actions under SameSite=Lax for simple GETs, and CSRF tokens or double-submit patterns still matter for state-changing requests — but the specific, high-frequency "XSS steals the whole session in one fetch to an attacker server" failure mode is categorically closed off when the credential is HttpOnly.

Example 
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/

Follow-ups

  • Does HttpOnly stop XSS itself? — No — the page can still be defaced, other cookies without HttpOnly can still be read, and any action the session cookie already authorizes can still be triggered by script running in that same authenticated context; it specifically stops the credential itself from being exfiltrated and replayed elsewhere.
  • Can an XSS bug still do damage against an HttpOnly-cookie app? — Yes, plenty — it can call your own APIs as the logged-in user from within the page; it just can't hand that ability to an attacker's own server via a stolen token.
  • Is localStorage ever an acceptable place for a token? — Only with a strong CSP, no untrusted third-party scripts, and eyes open about the residual risk — it's a defensible call for a low-risk internal tool, not a default for anything handling real user data.

Wrong answer: "Cookies are old and insecure, tokens in localStorage are the modern approach." This is the opposite of where the ecosystem actually landed — the BFF pattern below exists specifically because the industry moved back toward cookies for browser session credentials once the XSS exposure of localStorage tokens became well understood.

What is a Backend-for-Frontend (BFF), and why has it become the recommended pattern for SPA authentication? senior

A BFF is a server-side component — often just the app's own backend — that owns the entire OAuth/OIDC token dance on the browser's behalf: it runs the authorization code + PKCE flow, holds the access and refresh tokens server-side (in a session store or encrypted server-side session), and gives the browser only an HttpOnly, Secure, SameSite session cookie. The SPA never sees an access token at all; it calls its own BFF, which attaches the real token to the downstream API call itself. This closes the "SPA holds a bearer token somewhere JS can reach" problem categorically rather than mitigating it, at the cost of needing a server component even for an otherwise fully static frontend, and an extra network hop between browser and downstream API.

Example 
Browser --(session cookie)--> BFF --(access token, server-side)--> Orders API

Follow-ups

  • Doesn't this just move the token to another place that can be attacked? — Yes, but that place is a server you control with server-side secret management, not a browser tab reachable by any script that runs on the page — a meaningfully smaller and better-understood attack surface.
  • Does the BFF need its own OIDC client registration? — Yes — it's the confidential client in the flow now, which is part of the point: a confidential client can hold a secret and do things a public SPA client structurally cannot.
  • What's the ASP.NET Core building block for this? — Microsoft.Identity.Web's cookie + OIDC scheme pairing, or the more explicit Duende.BFF package, both wire this pattern up without hand-rolling the token relay.

Wrong answer: "A BFF is just an API gateway, any reverse proxy in front of your APIs counts." A generic gateway that merely forwards requests doesn't itself hold the OAuth client role or manage the token lifecycle — the defining property of a BFF here is that it, not the browser, is the OAuth client.

Sliding vs absolute session expiration — what's the difference and when do you pick each? mid

Absolute expiration sets a hard deadline from the moment of login regardless of activity — after 8 hours you're signed out even if you've been actively using the app the whole time. Sliding expiration extends the session on activity, so an active user effectively never sees a forced logout while idle users time out after a period of inactivity (typically shorter than the absolute ceiling). Most real systems combine both: a sliding window bounded by a hard absolute maximum, so an attacker who steals a live session can't ride it forever just by keeping it "active," and a legitimate user who's actually working doesn't get logged out mid-task.

Example 
options.SlidingExpiration = true;
options.ExpireTimeSpan = TimeSpan.FromMinutes(30);   // idle timeout
// paired, at the token/claims layer, with an absolute re-authentication requirement after e.g. 12 hours

Follow-ups

  • Does sliding expiration re-issue the cookie on every request? — No — ASP.NET Core's cookie middleware only re-issues once past a fraction of the expiry window (default ~50%) to avoid rewriting the cookie on every single request.
  • How does this interact with refresh tokens? — The session cookie's sliding window and the refresh token's own rotation/expiry are separate mechanisms that both need to be configured coherently, or the two can disagree about when the user is actually "still signed in."
  • What's a reasonable absolute ceiling for a sensitive app? — Short enough to bound stolen-session risk, long enough not to annoy legitimate users — a common concrete pattern is a short sliding idle timeout with a same-day absolute cap, tightened further for step-up-sensitive actions.

Wrong answer: "Sliding expiration alone is enough, since inactive sessions time out." Sliding-only means an actively-used stolen session (an attacker who keeps making requests) never expires at all — the absolute ceiling is what actually bounds that risk.

Walk through SameSite=Strict, Lax and None. What CSRF risk does each leave open? mid

Strict never sends the cookie on a cross-site request, including a user clicking a link from another site into yours — which kills CSRF but also breaks the "click a link, land already logged in" experience, so it's rarely used for a main session cookie. Lax (the browser default since Chrome 80/2020) sends the cookie on top-level cross-site navigations that use a "safe" method (a normal GET link click) but not on cross-site POSTs or subresource requests — which stops classic form-based CSRF while keeping normal link-following working, and is why it's the sane default for most session cookies. None sends the cookie on every cross-site request regardless of method, and must be paired with Secure; it's needed for legitimate cross-site embedding (a payment widget, a third-party iframe) but reopens the full CSRF surface Lax/Strict were closing, so anything using None needs an explicit CSRF token defense of its own.

Example

A malicious page auto-submitting a hidden POST form to your-bank.com/transfer succeeds if the session cookie is SameSite=None (or missing entirely, on an old browser) and fails outright under Lax or Strict.

Follow-ups

  • Do you still need CSRF tokens if you use SameSite=Lax? — Defense in depth still argues yes for state-changing endpoints, especially since Lax still allows top-level GET navigations and older/misbehaving browsers exist; don't treat SameSite as a total replacement.
  • Why would a cookie need SameSite=None at all? — Genuine cross-site embedding scenarios — an auth cookie used inside a third-party iframe, which is also exactly the scenario third-party cookie deprecation (unit 04's principal question) is killing off.
  • Does SameSite=Lax protect against a cross-site GET that has a side effect? — No — this is why REST conventions matter operationally, not just stylistically: a GET that mutates state defeats Lax's entire model.

Wrong answer: "Setting SameSite=Strict everywhere is the safest default." It's the most CSRF-resistant setting, but breaking the logged-in-after-following-a-link experience is a real UX cost most session cookies shouldn't pay — Lax is the actual recommended default for a reason.

Server-side sessions vs self-contained (JWT) session tokens — what do you actually give up with each? senior

A server-side session stores session data (user id, claims, whatever else) in a shared store (Redis, SQL) keyed by an opaque session id the cookie carries; the server can invalidate it instantly by deleting the row, and the cookie itself leaks nothing if intercepted. A self-contained JWT session token needs no shared store and validates on any node without a lookup — but that statelessness is exactly what makes it hard to revoke before its natural expiry (see unit 08), and it's larger on the wire than an opaque id. The trade is server-side simplicity/scalability vs instant revocability and payload size; most production systems land on short-lived JWTs (bounding the revocation problem by keeping the window small) backed by a server-side refresh mechanism that can be revoked immediately.

Example

ASP.NET Core's cookie authentication scheme defaults to a self-contained encrypted ticket in the cookie itself; swapping in a distributed cache-backed ticket store (ICookieManager/session-store extensions) trades that simplicity for instant server-side invalidation across all nodes.

Follow-ups

  • Does horizontal scaling favor one over the other? — Self-contained tokens scale trivially (no shared state to check); server-side sessions need a shared store reachable from every node, which is one more piece of infrastructure to keep available.
  • Can you get both instant revocation and statelessness? — Not for free — a short-TTL access token plus a checked-on-refresh revocation list gets you close: most of the time no lookup happens, and revocation takes effect within one refresh cycle.
  • Which do most real systems actually use for the browser session cookie itself, as opposed to the API access token? — Server-side (or at least revocable) sessions for the browser cookie are common precisely because that's the credential you most want to be able to kill instantly on logout/compromise.

Wrong answer: "JWTs are always better because they're stateless." Statelessness is a scaling convenience with a real cost (hard revocation) that a screener-level answer glosses over; a senior answer names the trade explicitly rather than treating either option as a free win.

Your app needs to share a login session across app.example.com and api.example.com. What are your options, and what's the catch with each? senior

A cookie scoped to Domain=.example.com is sent to both subdomains automatically — simple, but it also gets sent to every subdomain, so a vulnerability on an unrelated, less-trusted subdomain (a marketing site, a demo environment) can potentially read or ride on the same cookie, and it doesn't help at all if the two need genuinely different origins (e.g. a different top-level domain, or a customer-specific subdomain your infra doesn't fully control). The BFF pattern sidesteps the problem differently: the browser only ever holds a cookie scoped to the BFF's own origin, and the BFF makes the authenticated calls to api.example.com server-side, so no cross-origin cookie sharing is needed at all. A third option, a shared session store looked up by a token passed explicitly (not a shared cookie), works across genuinely separate domains but reintroduces the "where does the browser keep that token" question from earlier in this unit.

Example

A shared Domain=.example.com cookie means a subdomain takeover of old-marketing-campaign.example.com — a common, overlooked asset — could potentially set or read cookies that the main app trusts, unless cookie prefixing (__Host-) or careful subdomain governance closes that gap.

Follow-ups

  • What does the __Host- cookie prefix buy you? — It forces Secure, no Domain attribute (host-only, not shared across subdomains), and Path=/, which is exactly the opposite of subdomain sharing — useful when you specifically want to prevent it.
  • Does this change if the two are on entirely different top-level domains? — Yes — no cookie-domain trick works across different eTLDs; that's squarely a BFF or token-relay problem, not a cookie-attribute problem.
  • How does Entra ID's own hosted login handle this across your app's domains? — It doesn't try to — each relying party gets its own session via the standard redirect flow; cross-domain SSO is handled by the AS's own session (unit 02's front-/back-channel logout territory), not by sharing your app's cookies.

Wrong answer: "Just set the cookie's domain to the parent domain and it'll work everywhere you need it." It will work everywhere, including places you didn't intend, which is precisely the risk — the question is testing whether you name that trade-off, not whether you know the Domain attribute exists.

Third-party cookie deprecation in browsers — does it actually affect your auth architecture, or only ad tech? principal

It affects auth architecture directly wherever a login or SSO pattern relied on a cookie set in a cross-site iframe context — classic examples are silent-SSO "check if the user is already logged in" hidden iframes, and OIDC front-channel logout's own hidden-iframe fan-out from unit 02. Browsers increasingly partition or block cookies in third-party iframe contexts by default, which silently breaks both without an obvious error — the iframe loads, the cookie just isn't there. The durable fix is the same one identity architects have been pushing anyway: move session state to first-party contexts (top-level redirects, not iframes) and rely on protocol-level mechanisms — refresh tokens, back-channel logout, redirect-based re-authentication — instead of a browser storage side channel that was never a standardized part of any spec to begin with.

Example

A "seamless SSO" implementation that quietly probed a hidden IdP iframe to auto-log-in returning users now increasingly fails in Safari (ITP) and Chrome's newer partitioning, forcing an interactive redirect where none was previously needed — worth calling out as a live migration a lot of mid-2020s-built SSO integrations are dealing with.

Follow-ups

  • Does this affect the BFF pattern? — No — the BFF's cookie is first-party (set by the app's own origin, in a top-level context), which is exactly the shape third-party cookie restrictions don't touch.
  • What's the OIDC-spec-level answer to losing iframe-based silent SSO? — Rely on short, cheap redirect-based re-authentication (prompt=none via full navigation rather than an iframe) or accept a slightly less seamless re-auth experience as the honest cost.
  • Is this a browser-vendor-specific migration or a converged direction? — Converged — every major browser is restricting third-party storage access in some form; treating it as "just a Safari thing" underestimates the timeline.

Wrong answer: "That's a marketing/analytics problem, our auth doesn't use third-party cookies." Any hidden-iframe-based silent-SSO or front-channel-logout implementation is a third-party cookie dependency, whether or not the team labeled it that way — this is the kind of blind spot a principal-level review is expected to catch before it breaks in production.

Design the session architecture for a product with a SPA web frontend, a native mobile app, and three backend APIs. What credential does each client actually hold? principal

The SPA gets a BFF: it holds only an HttpOnly/Secure/SameSite=Lax session cookie scoped to the BFF's own origin, and the BFF — a confidential client — holds the real access/refresh tokens server-side and fans calls out to the three APIs, doing token exchange per-API if their trust boundaries differ. The native mobile app is a public client doing authorization code + PKCE directly against the AS, storing tokens in the platform keychain/keystore — it doesn't need a BFF because it doesn't face the browser's DOM-based XSS threat model, though a thin BFF is still defensible if the mobile team wants to centralize API-shape changes away from a store-gated release cycle. Each of the three APIs validates access tokens as a resource server, with audiences scoped per-API so a token for API A doesn't validate against API B; none of them ever see the SPA's session cookie, and none of them are handed a client secret, since none of them is an OAuth client in this design — they're resource servers.

Example

A checkout flow: the browser calls the BFF with its session cookie; the BFF, holding a server-side access token audience-scoped to api://orders, calls the orders API; the orders API calls the inventory API using a token-exchange-minted token scoped down further (unit 10) rather than forwarding its own inbound token unchanged.

Follow-ups

  • Why not give the SPA its own tokens directly, since PKCE makes it "safe enough" as a public client? — PKCE secures the code exchange, not what happens to the token afterward in the browser's DOM — the BFF is about post-issuance custody, a separate concern PKCE doesn't touch.
  • Does the mobile app need a different client registration than the SPA? — Yes — different platform configuration (native/public vs the BFF's confidential registration), different redirect URI scheme, and arguably different token lifetimes given the different theft/loss threat model (a lost phone vs a stolen browser session).
  • What single failure mode does this design most need a runbook for? — The BFF's own token store being compromised — since it now custodies tokens for every SPA user, its blast radius on compromise is the whole web user base, which argues for it being one of the most hardened, most monitored components in the system.

Wrong answer: Using one token/credential shape uniformly across SPA, mobile, and APIs "for consistency." Consistency is being optimized at the wrong layer — the SPA, mobile app, and APIs face genuinely different threat models (DOM-based XSS, device loss, server compromise), and a uniform credential design usually means the SPA inherited the mobile app's risk profile or vice versa.

05 ASP.NET Core authentication middleware

This is where protocol knowledge has to turn into working code: ASP.NET Core's authentication layer is a small number of concepts (schemes, handlers, principals) that compose in ways that trip people up mainly at the seams — ordering, defaults, and what happens with more than one scheme registered. At mid level you're expected to wire up cookie or JWT bearer auth correctly; at senior to reason about scheme selection and claims transformation; at principal to design for an app that must support more than one credential type at once.

ASP.NET Core authentication overview · Authentication policy schemes

What is an authentication "scheme" in ASP.NET Core, and why can an app have more than one? screener

A scheme is a named registration pairing an AuthenticationHandler implementation with its options — "Cookies" backed by the cookie handler, "Bearer" backed by the JWT bearer handler, "oidc" backed by the OIDC handler, and so on. An app registers as many as it needs because it may need to authenticate different kinds of caller differently: a browser session via a cookie scheme, an API caller via a bearer scheme, a third-party webhook via yet another. Each [Authorize] (or endpoint) can name which scheme(s) it accepts; without a name, it falls back to the configured default.

Example 
builder.Services.AddAuthentication()
    .AddCookie("Cookies")
    .AddJwtBearer("Bearer", options => { options.Authority = authority; options.Audience = "api://orders"; });

Follow-ups

  • Does registering a scheme make it active automatically? — No — it only becomes the one actually used for a given request when it's the default, explicitly named on [Authorize(AuthenticationSchemes = "...")], or selected by a policy scheme (see the principal question below).
  • Can two schemes of the same handler type coexist? — Yes — two AddJwtBearer registrations under different names, each with its own Authority/Audience, is the standard way to accept tokens from two different issuers.
  • What does "handler" mean concretely? — The class that actually inspects the request (a header, a cookie) and produces (or fails to produce) an authenticated ClaimsPrincipal.

Wrong answer: "There's basically one 'authentication' in an app, you just configure it." The scheme abstraction exists precisely because real apps often need several authentication mechanisms simultaneously — treating it as singular misses the entire reason multi-scheme configuration exists.

Walk through what happens, in order, from an incoming request to HttpContext.User being populated. mid

UseAuthentication middleware runs early in the pipeline and asks the current request's default (or per-endpoint) scheme's handler to attempt authentication — for a cookie scheme that means decrypting and validating the cookie; for a JWT bearer scheme, extracting and validating the Authorization: Bearer header. If it succeeds, the handler produces a ClaimsPrincipal and sets it on HttpContext.User; nothing here decides whether the request is allowed, only who it claims to be. Later, UseAuthorization middleware (or endpoint-level [Authorize] evaluation) checks that principal against whatever policy the matched endpoint requires, and only then decides to let the request through, 401, or 403.

Example 
app.UseRouting();
app.UseAuthentication();   // who are you?
app.UseAuthorization();    // are you allowed here?
app.MapControllers();

Follow-ups

  • What if authentication fails — does the request stop there? — No, by default the request continues with an unauthenticated (anonymous) HttpContext.User; it's UseAuthorization/[Authorize] on the matched endpoint that turns "unauthenticated" into an actual 401.
  • Does middleware order actually matter here, or is it just convention? — It matters — UseAuthorization before UseAuthentication means authorization checks run against an unpopulated principal, effectively disabling auth; UseRouting must precede both so endpoint metadata (which policy applies) is known.
  • Where do multiple registered schemes get resolved to one, for a given request? — The endpoint's configured scheme(s), or the app's default scheme if none is specified — this is exactly the seam the principal-level policy-scheme question below is testing.

Wrong answer: "UseAuthentication decides if the request is allowed." That's authorization's job; authentication only establishes identity — the two middleware are separate for exactly this reason, and merging them in your mental model is a common source of "why is this endpoint letting anyone through" bugs.

What's the difference between the default, challenge, and sign-in scheme, and when does the distinction actually bite you? senior

The default authenticate scheme is what handles incoming requests generally; the default challenge scheme is what runs when an unauthenticated request hits a protected endpoint (for a cookie app, that's typically a redirect to a login page; for an OIDC app, it's the redirect to the AS's /authorize); the default sign-in scheme is what actually persists the result of a successful authentication (usually the cookie handler, even in an OIDC app — OIDC itself doesn't persist anything long-lived, it just produces the initial identity that gets signed into a cookie). They bite you in the classic "cookie + OIDC" combo: if you don't explicitly set the challenge scheme to "oidc", an unauthenticated request might get challenged by the cookie handler instead, which just redirects to a login page that doesn't exist — a confusing 404/loop instead of the expected redirect to the identity provider.

Example 
builder.Services.AddAuthentication(options => {
    options.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;      // read/persist
    options.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;    // redirect to IdP
}).AddCookie().AddOpenIdConnect(/* ... */);

Follow-ups

  • Does the sign-out scheme matter the same way? — Yes — signing out needs to hit both the cookie scheme (clear the local session) and the OIDC scheme (RP-initiated logout at the AS), which is why SignOutAsync is often called with both scheme names explicitly.
  • Is this specific to OIDC, or does it show up with JWT bearer + cookies too? — It shows up any time two schemes are combined and their default roles (authenticate/challenge/sign-in) aren't set explicitly — the JWT bearer handler has no meaningful "challenge" beyond a 401, which is usually the desired behavior for an API but wrong for a browser-facing endpoint sharing the same app.
  • How do you debug "why did I get redirected to the wrong place"? — Log which scheme actually handled the challenge (HttpContext.Features / the auth middleware's diagnostics), rather than guessing from the symptom.

Wrong answer: "There's just 'the' authentication scheme for the app, this default/challenge/sign-in split is unnecessary complexity." The split exists because "who reads the identity," "what happens on a failed check," and "where does the result get stored" are genuinely different questions once more than one scheme is involved — collapsing them is exactly what produces the login-redirect-loop bugs this question is checking for.

.NET 10 changed how cookie-authenticated endpoints behave for unauthenticated API calls. What changed, and why? mid

Before .NET 10, an unauthenticated request to a cookie-scheme-protected endpoint always got the cookie handler's default challenge behavior: a 302 redirect to a login path, which makes sense for a browser navigating to a page but is actively wrong for a fetch/XMLHttpRequest call from a SPA expecting a 401 it can handle in code — historically, teams worked around this with custom Events.OnRedirectToLogin logic that inspected the Accept header. As of .NET 10, endpoints identified as API-shaped (minimal APIs, controllers marked appropriately) get a direct 401/403 instead of the redirect by default, removing the need for that workaround — a genuinely breaking change for anyone whose client code depended on following the redirect.

Example 
// pre-.NET 10 workaround, now largely unnecessary for API endpoints:
options.Events.OnRedirectToLogin = ctx => {
    if (ctx.Request.Path.StartsWithSegments("/api")) { ctx.Response.StatusCode = 401; return Task.CompletedTask; }
    ctx.Response.Redirect(ctx.RedirectUri); return Task.CompletedTask;
};

Follow-ups

  • Does this affect Razor Pages/MVC views the same way? — No — a page-rendering endpoint still gets the redirect-to-login behavior a browser navigation expects; the change targets API-shaped responses specifically.
  • What should you check when upgrading to .NET 10 for this reason? — Any client code (a SPA, a mobile app, an integration test) that was relying on following a 302 to detect "not logged in" instead of checking for 401 directly.
  • Does this interact with the BFF pattern favorably? — Yes — a BFF's API surface wants 401/403 for its SPA to handle in code, not a redirect it would otherwise have to special-case away.

Wrong answer: "ASP.NET Core has always returned 401 for an unauthenticated API call." That was only true if you'd already special-cased it yourself pre-.NET 10 — stating it as always-true default behavior misses a real, recent, citable platform change worth knowing walking into a 2026 interview.

What's the correct order for UseRouting, UseAuthentication, UseAuthorization, and UseCors? What breaks if you get it wrong? screener

Routing first (endpoint metadata, including which policy applies, must be resolved before authorization can check it), then CORS (a preflight or cross-origin decision generally needs to happen before the request is treated as authenticated/authorized, and CORS failures shouldn't leak information about auth state), then authentication, then authorization, then the endpoints themselves. Getting authentication and authorization swapped means authorization evaluates against a principal that hasn't been populated yet — every [Authorize] effectively runs against an anonymous user, which either locks everyone out or, depending on policy design, silently lets requests through that shouldn't.

Example 
app.UseRouting();
app.UseCors();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

Follow-ups

  • Does UseRouting before authentication leak anything? — It only resolves which endpoint would handle the request and its metadata; it doesn't execute the endpoint, so this ordering is safe and required.
  • What's a realistic symptom of this being wrong in code review? — "Some endpoints that should require auth don't seem to enforce it" is the most common bug report that traces back to authorization middleware running before authentication.
  • Does minimal API routing change this ordering rule? — No — the same middleware ordering rules apply regardless of whether endpoints are minimal APIs or MVC controllers.

Wrong answer: "As long as both UseAuthentication and UseAuthorization are somewhere in Program.cs, the order between them doesn't matter." It matters specifically and mechanically — authorization needs a populated HttpContext.User to check against, which only exists after authentication middleware has run.

What is IClaimsTransformation for, and why shouldn't you just add claims inside your JWT bearer handler's OnTokenValidated event instead? senior

IClaimsTransformation.TransformAsync runs once per request, after authentication succeeds regardless of which scheme produced the principal, and lets you enrich it with claims that don't come from the token itself — a database-driven permission set, a computed display name, a feature-flag claim. Putting the same logic in OnTokenValidated ties it to one specific scheme's handler, so a cookie-authenticated request (which never fires the JWT bearer handler's events at all) silently skips the enrichment — a real bug in any app combining schemes. IClaimsTransformation is scheme-agnostic by design, which is exactly the property you want for logic that should apply to "whoever is now authenticated," not "whoever came in via this one specific handler."

Example 
public class AddTenantClaim : IClaimsTransformation {
    public async Task<ClaimsPrincipal> TransformAsync(ClaimsPrincipal principal) {
        var tenantId = await tenantLookup.GetTenantIdAsync(principal.FindFirst("sub")!.Value);
        ((ClaimsIdentity)principal.Identity!).AddClaim(new Claim("tenant_id", tenantId));
        return principal;
    }
}

Follow-ups

  • Does it run more than once per request if called multiple times? — It can be invoked more than once depending on how many times authentication is triggered in a request; idempotent logic (check-before-add) avoids duplicate claims.
  • Is there a performance cost to a database lookup here? — Yes, on every request unless cached — a short-TTL cache keyed by user id is the usual mitigation, same trade-off as unit 03's claim-bloat discussion.
  • Does this replace claims mapping done by the OIDC handler itself (e.g. renaming roles)? — No, that's a separate, earlier concern (TokenValidationParameters.RoleClaimType and similar) about how inbound claims are named, not about adding new ones from outside the token.

Wrong answer: "It doesn't matter where you add claims, as long as they end up on the principal somewhere." It matters exactly when a second scheme is introduced later and the enrichment silently doesn't apply to it — a scheme-agnostic mechanism is the difference between a bug that shows up immediately and one that shows up months later when someone adds cookie auth to what was JWT-only.

You need to accept tokens from two different Entra ID tenants in the same API. How do you configure that? senior

Register two named JWT bearer schemes, each with its own Authority pointed at the respective tenant's issuer and its own expected Audience/ValidIssuer, then combine them behind a policy scheme (or explicitly list both scheme names on the endpoints/[Authorize] that must accept either) so a request is accepted if it validates against either registration. A single JWT bearer scheme's Authority can only point at one issuer's metadata document, so a naive single-scheme setup either rejects one tenant's tokens outright or, worse, someone tries to work around it by disabling issuer validation — reopening exactly the cross-tenant token acceptance bug unit 03's claim-validation question warns about.

Example 
.AddJwtBearer("TenantA", o => { o.Authority = "https://login.microsoftonline.com/tenantA/v2.0"; o.Audience = "api://orders"; })
.AddJwtBearer("TenantB", o => { o.Authority = "https://login.microsoftonline.com/tenantB/v2.0"; o.Audience = "api://orders"; })
.AddPolicyScheme("MultiTenant", "MultiTenant", o => {
    o.ForwardDefaultSelector = ctx => /* inspect the token's iss/tid claim, unvalidated, to pick a scheme */ "TenantA";
});

Follow-ups

  • Is peeking at the unvalidated token to pick a scheme itself a risk? — It's reading, not trusting — the actual validation still happens inside the chosen scheme's handler afterward; the selector only decides which validator to hand the token to.
  • Does this scale to many tenants, or is it a two-scheme trick? — For many tenants, most teams switch to a single multi-tenant-aware validation path that resolves issuer/keys dynamically per request rather than one static scheme per tenant.
  • What's the audience-validation gotcha here specifically? — Both tenants' apps might share the same Audience value (api://orders) by convention, which is fine as long as issuer validation per scheme still correctly separates them — audience alone isn't the tenant boundary here, issuer is.

Wrong answer: "Just turn off issuer validation so tokens from either tenant pass." That collapses the tenant boundary entirely — any token from any Entra ID tenant, not just the two intended ones, would then validate, since issuer is the only thing distinguishing them.

What cookie authentication options actually matter for security, beyond just setting up AddCookie()? mid

Cookie.SameSite, .SecurePolicy, and .HttpOnly (on by default, rarely worth changing) set the transport-level protections from earlier in this unit. ExpireTimeSpan plus SlidingExpiration control the session lifetime trade-off. Events.OnValidatePrincipal is the hook for revocation — it runs on (a throttled subset of) requests and lets you reject an already-issued cookie against a server-side "this session/user was signed out" check, which is how you get instant logout-everywhere for an otherwise self-contained cookie ticket. Skipping that last one is the most common gap: without it, a stolen or "revoked" cookie stays valid until it naturally expires, no matter what your admin panel's "force logout" button claims to do.

Example 
options.Events.OnValidatePrincipal = async ctx => {
    var stamp = ctx.Principal?.FindFirstValue("security_stamp");
    if (await securityStore.IsRevokedAsync(stamp)) ctx.RejectPrincipal();
};

Follow-ups

  • Does OnValidatePrincipal run on every single request? — ASP.NET Core Identity's own security-stamp validator throttles this (a configurable interval) to avoid a store lookup on every request while still bounding how long a revoked session can survive.
  • What's the cost of setting that interval too long? — A revoked session/password-changed event takes up to that interval to actually lock the user out, even though the UI might claim it happened immediately.
  • Is CookieBuilder.IsEssential relevant here? — Only for cookie-consent scenarios — it's about whether the cookie is exempt from a GDPR-style consent gate, unrelated to the security properties above.

Wrong answer: "Cookie auth security is basically just HttpOnly and Secure, the rest is defaults." The defaults don't give you server-side revocation at all — OnValidatePrincipal (or an equivalent store-backed check) is what closes the "I clicked logout everywhere but the stolen cookie still works" gap, and it's opt-in.

Design authentication for an app that must accept both a browser session cookie and a JWT bearer token on the same set of endpoints, depending on the caller. principal

I'd register both schemes ("Cookies", "Bearer") and put a policy scheme in front as the default, whose ForwardDefaultSelector inspects the incoming request — presence of an Authorization: Bearer header routes to the JWT scheme, absence falls back to cookies — rather than trying to make either handler natively understand the other's credential shape. I'd deliberately keep the two credential lifecycles independent (the cookie's revocation story from the question above; the JWT's short-lifetime-plus-refresh story from unit 08) rather than trying to unify them into one mechanism, since they're serving genuinely different callers (a browser tab vs. a script/mobile client) with different threat models. The one thing I'd insist on is that authorization policies stay scheme-agnostic — a policy checks claims on the resulting ClaimsPrincipal, not "which scheme authenticated this," so the same [Authorize(Policy = "CanEditOrders")] works unmodified regardless of which credential got the caller there.

Example 
.AddPolicyScheme("Smart", "Smart", o => o.ForwardDefaultSelector = ctx =>
    ctx.Request.Headers.ContainsKey("Authorization") ? "Bearer" : "Cookies");

Follow-ups

  • Why not just always require a bearer token, even from the browser, and skip the cookie scheme entirely? — That pushes the browser back toward holding a bearer token in JS-reachable storage — exactly the risk the BFF pattern in unit 04 exists to avoid; the two-scheme design is what lets the browser keep using a safe cookie while other clients use bearer tokens natively.
  • What's the failure mode if the selector logic is wrong? — A request gets routed to the wrong handler and fails authentication entirely (a safe failure) rather than being incorrectly authenticated as someone else — worth stating explicitly, since "which way does it fail" is what a reviewer actually cares about.
  • Does CSRF protection still apply to the cookie-authenticated path here? — Yes, unconditionally — introducing a bearer option for other clients doesn't reduce the CSRF surface on the endpoints still reachable via cookie, so SameSite plus, where needed, explicit anti-forgery tokens still apply there.

Wrong answer: Trying to make one handler (usually by stretching the cookie handler) accept both shapes of credential. Handlers are built around one credential format's validation semantics; forcing one to also parse bearer headers duplicates and diverges from the JWT bearer handler's own, already-correct validation logic — a policy scheme in front of two separately-correct handlers is simpler and safer than one handler doing two jobs.

06 ASP.NET Core authorization: policies & handlers

Once a request has an identity, the question shifts to "is this identity allowed to do this specific thing" — and ASP.NET Core's answer is a small requirement/handler engine sitting behind the deceptively simple [Authorize] attribute. Screeners want role checks; mid-level candidates need policies and custom requirements; senior and principal levels are about resource-based authorization and not letting policy logic leak into controllers.

ASP.NET Core authorization overview · Policy-based authorization

What's the difference between role-based and policy-based authorization, and why does .NET push you toward the latter? screener

[Authorize(Roles = "Admin")] checks a single claim type (role) against a fixed list — simple, but it hardcodes "who can do this" as "which role" directly in the attribute, and roles multiply awkwardly once permissions get fine-grained ("Admin,Manager" unions, no way to express AND). Policy-based authorization names a requirement ("CanEditOrders") and evaluates it via one or more handlers that can look at any claim, any injected service, even the specific resource being acted on — the role check becomes just one possible handler implementation, not the whole model. .NET's own recommendation, and the pattern AddAuthorizationBuilder nudges you toward, is to define named policies even for what's logically a role check, so switching the underlying rule later doesn't mean hunting down attribute strings across the codebase.

Example 
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("CanEditOrders", p => p.RequireRole("Admin", "OrderManager"));
// [Authorize(Policy = "CanEditOrders")]  — not [Authorize(Roles = "Admin,OrderManager")]

Follow-ups

  • Is [Authorize(Roles = "A,B")] an OR or an AND? — OR — comma-separated roles on one attribute mean "any of these"; stacking multiple [Authorize] attributes on the same target is how you express AND.
  • Does policy-based authorization cost more at runtime? — Negligibly — it's still a claims check in the common case, just routed through the requirement/handler indirection instead of inline attribute logic.
  • What is AddAuthorizationBuilder specifically, versus the older AddAuthorization? — The newer, chainable registration API (introduced around .NET 8) that also wires up minimal-API-friendly extension points; behavior is equivalent, ergonomics differ.

Wrong answer: "Roles are the old way, policies are the new way, always use policies for everything." Role checks aren't deprecated — RequireRole is a normal, supported policy requirement; the point is naming the policy rather than repeating raw role strings everywhere, not abandoning roles as a concept.

Write a custom authorization requirement and handler for "the caller must be the owner of the order they're editing." mid

This needs resource-based authorization, not attribute-based: the decision depends on which specific order is being accessed, which the routing/attribute layer doesn't know about. Define an IAuthorizationRequirement marker, a handler implementing AuthorizationHandler<TRequirement, TResource>, and call IAuthorizationService.AuthorizeAsync(User, order, requirement) explicitly inside the action once the order is loaded — resource-based checks generally can't be expressed as a static [Authorize] attribute because the attribute runs before the resource exists.

Example 
public class SameOwnerRequirement : IAuthorizationRequirement { }
public class SameOwnerHandler : AuthorizationHandler<SameOwnerRequirement, Order> {
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext ctx, SameOwnerRequirement req, Order order) {
        if (order.OwnerId == ctx.User.FindFirstValue("sub")) ctx.Succeed(req);
        return Task.CompletedTask;
    }
}
// in the action:
var result = await authz.AuthorizeAsync(User, order, new SameOwnerRequirement());
if (!result.Succeeded) return Forbid();

Follow-ups

  • Can a handler call Fail() to short-circuit other handlers? — It can, but by default a requirement succeeds if any registered handler for it succeeds — calling Fail() explicitly overrides that and fails the whole evaluation even if another handler would have succeeded, so it's used sparingly, for hard vetoes.
  • What if the owner check needs a database lookup? — Fine — handlers are regular DI-constructed classes, they can inject a repository or DbContext just like any other service.
  • Does minimal APIs support this the same way? — Yes, IAuthorizationService is injected the same way into a route handler delegate.

Wrong answer: "Put if (order.OwnerId != userId) return Forbid(); directly in the controller action." That works for one check in one place, but it's exactly the logic that becomes untestable and inconsistent once three more actions need the same "must be owner" rule — a requirement/handler is the same check made reusable and independently testable.

What's the difference between Forbid() and throwing an exception, or returning NotFound(), when an authorization check fails? mid

Forbid() (or letting [Authorize]/AuthorizeAsync fail naturally) produces the correct 403 — "I know who you are, you're not allowed." NotFound() is sometimes used deliberately instead, specifically to avoid confirming a resource exists to a caller who isn't allowed to see it (a common choice for multi-tenant data, where a 403 on someone else's order ID leaks that the ID is valid). Throwing an unhandled exception is close to always wrong here — it turns an expected authorization outcome into an error-handling/logging-noise event and, depending on exception middleware, can return the wrong status code or leak stack detail.

Example 
if (!result.Succeeded) return tenantIsolationMode ? NotFound() : Forbid();

Follow-ups

  • Is choosing 404-over-403 always the right multi-tenant call? — It's a trade-off, not a default — it trades a small UX cost (an owner can't tell "doesn't exist" from "not yours") for not confirming resource existence to unauthorized callers; teams differ on which side they land on.
  • What does Forbid() actually do for a cookie-scheme request versus a bearer-scheme request? — For a scheme with challenge behavior configured (a login redirect), the exact response can differ from a pure 403 unless configured explicitly — this is the same authenticate/challenge scheme distinction from unit 05.
  • Should a 403 response body ever explain why? — Usually kept minimal in production for the same reason as the 404 choice above — detailed "you lack permission X" messages are an information-disclosure surface for probing what permissions exist.

Wrong answer: "It doesn't matter which status you return as long as the request is blocked." The status code is part of the contract API clients rely on to distinguish "retry with different data" (400), "log in again" (401), "you'll never be allowed, don't retry" (403), and "this doesn't exist" (404) — collapsing them into whichever is convenient breaks client error handling.

How do you apply a default authorization policy to every endpoint in the app, with per-endpoint opt-outs for the few that must stay anonymous? senior

Configure a FallbackPolicy (applies to any endpoint with no [Authorize]/[AllowAnonymous] at all) or, more commonly and more safely, set the app-wide default so every endpoint requires authentication unless explicitly marked [AllowAnonymous] — the "secure by default, opt out explicitly" posture. This matters because the alternative — annotating every sensitive endpoint individually — fails open: a new controller or minimal API route added later with no attribute at all is anonymous by accident, not by decision.

Example 
builder.Services.AddAuthorizationBuilder()
    .SetFallbackPolicy(new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build());
// [AllowAnonymous] on the health-check endpoint, the login endpoint, etc.

Follow-ups

  • Is FallbackPolicy the same as DefaultPolicy? — No — DefaultPolicy is what a bare [Authorize] (no policy name) resolves to; FallbackPolicy is what applies when there's no [Authorize] attribute present at all. Setting only one of them without understanding the difference leaves a gap.
  • Does this affect endpoints outside MVC, like static files or Swagger UI? — It generally applies only to routed endpoints; middleware-served content (static files) needs its own protection if it should also be gated.
  • How would you catch a route added later without meaning to be public? — A fallback policy is exactly that catch; some teams add a startup-time or test-time audit that lists all endpoints and their effective authorization requirement as a second line of defense.

Wrong answer: "Just remember to add [Authorize] to every new controller." Relying on every future contributor remembering an attribute is precisely the fail-open pattern that FallbackPolicy/default-authenticated-user configuration exists to eliminate — "secure by default" means the omission is safe, not that it's forbidden.

What is IAuthorizationRequirementData / policy-per-endpoint via minimal APIs, and how does it differ from named policies registered at startup? senior

Named policies (via AddPolicy at startup, referenced by string) are the general mechanism; IAuthorizationRequirementData lets a custom attribute generate its own requirement(s) directly, so [MinimumAge(21)] can attach a parameterized requirement without a corresponding AddPolicy("MinimumAge21", ...) having to be registered ahead of time for every possible parameter value. It's most useful exactly when the policy is parameterized per call site (an age threshold, a required scope string) — pre-registering a named policy for every combination doesn't scale, while an attribute that builds its own requirement from its constructor argument does.

Example 
public class MinimumAgeAttribute(int age) : AuthorizeAttribute, IAuthorizationRequirementData {
    public IEnumerable<IAuthorizationRequirement> GetRequirements() => [new MinimumAgeRequirement(age)];
}
// [MinimumAge(21)] on the endpoint — no AddPolicy call needed for this specific value

Follow-ups

  • Does this replace named policies for the common case? — No — for a fixed, small set of policies, named policies registered once are simpler and more discoverable; this feature targets the parameterized long tail.
  • Does it work with minimal APIs specifically, or only MVC? — Both — it's an authorization-layer feature, not MVC-specific, which is exactly why it was introduced around the time minimal APIs matured, when "declare a policy inline without a startup registration" became more valuable.
  • Is there a discoverability cost to per-attribute requirements versus a catalog of named policies? — Yes — named policies are easy to enumerate and audit ("what are all our policies"); attribute-generated requirements are more scattered, a real trade-off worth naming in a design discussion.

Wrong answer: "You always need a named policy registered at startup before you can use [Authorize(Policy = ...)] anywhere." That's true for the classic named-policy path, but not the only path — parameterized attribute-driven requirements are a real, supported alternative for exactly the cases where pre-registration doesn't fit.

How do authorization policies interact with output/response caching? What can go wrong? senior

Authorization runs per request, before the response is produced — but if a cached response from one user's authorized request gets served to a different, unauthorized request because the cache key didn't vary by identity (or by whatever claim the policy depends on), the caching layer has effectively bypassed authorization after the fact. The classic bug: an endpoint returns per-user data, is marked [OutputCache] with a cache key that only varies by URL, and a second user hitting the same URL gets the first user's cached, already-authorized response without ever being checked themselves.

Example 
[OutputCache(VaryByHeaderNames = ["Authorization"])] // crude; better: vary by resolved user/tenant id, not the raw token
public IActionResult GetMyOrders() { ... }

Follow-ups

  • Is this specific to output caching, or does it show up with CDN/reverse-proxy caching too? — Same failure mode, higher blast radius — a CDN caching an authenticated response keyed only by path can serve one user's private data to the entire edge network's next requester for that path.
  • What's the safe default? — Don't cache authenticated, per-user responses at all unless the cache key is proven to vary by everything the response's content depends on; caching is opt-in per endpoint for exactly this reason.
  • Does Cache-Control: private fully solve this? — It tells intermediate/shared caches not to store the response, which helps against CDN/proxy leakage, but a server-side output cache inside the app itself isn't a "shared cache" in that sense and needs its own vary-by-user configuration regardless.

Wrong answer: "Authorization happens before caching in the pipeline, so caching can't affect who sees what." Authorization gates the request that produces the cached entry — it says nothing about who a cache hit is served to on a later request, which is exactly where the vary-by-identity requirement comes from.

Two authorization handlers are registered for the same requirement. What's the evaluation semantics — does one veto the other? mid

By default, a requirement is satisfied if any registered handler for it calls Succeed, and no handler calling Fail explicitly — this is an OR across handlers for the same requirement, not an AND. Handlers that don't apply (wrong resource type, condition not met) simply return without calling either, leaving the requirement unresolved for that handler without blocking others. This surprises people who expect "multiple handlers" to mean "all must agree" — it doesn't, unless one of them explicitly calls Fail, which does override everything.

Example 
// Handler A: succeeds if user has role "Admin"
// Handler B: succeeds if user is the resource owner
// Requirement succeeds if EITHER A or B succeeds — this is usually what you want for "admin OR owner" rules,
// but it's a design decision, not an accident, and worth stating as such.

Follow-ups

  • How do you express "must satisfy both handler A's rule and handler B's rule"? — Combine both conditions inside one handler, or require two separate requirements (both attached to the policy) rather than two handlers for the same requirement — a policy's list of requirements IS evaluated as AND.
  • What happens if no handler for a requirement ever calls Succeed or Fail? — The requirement is never satisfied and the overall authorization fails — silent non-handling reads the same as an explicit failure.
  • Is this documented clearly, or a common source of bugs? — It's a common source of surprise specifically because "requirements in a policy = AND" and "handlers for one requirement = OR" look similar but aren't — worth stating explicitly in review when a new handler is added for an existing requirement.

Wrong answer: "Adding a second handler for a requirement makes the check stricter." It's the opposite by default — an additional handler for the same requirement is an additional way to satisfy it (OR), which can make a check strictly looser unless the new handler is very carefully scoped.

How would you unit-test a custom authorization handler without spinning up the whole ASP.NET Core pipeline? mid

Construct the handler directly (it's a plain DI-injected class, mock its dependencies as needed), build an AuthorizationHandlerContext with a hand-built ClaimsPrincipal and the resource under test, call HandleRequirementAsync directly, and assert on context.HasSucceeded. None of this needs TestServer, an HTTP pipeline, or a real authentication scheme — the handler is a pure-ish unit once its dependencies are supplied, which is exactly the value of pulling authorization logic out of controller actions in the first place.

Example 
var user = new ClaimsPrincipal(new ClaimsIdentity([new Claim("sub", "u1")]));
var ctx = new AuthorizationHandlerContext([new SameOwnerRequirement()], user, order);
await handler.HandleAsync(ctx);
Assert.True(ctx.HasSucceeded);

Follow-ups

  • Does this test the policy wiring (which handlers apply to which requirement) too? — No — that's a separate, thinner integration concern; unit-testing the handler in isolation and integration-testing that AddPolicy wires the right requirements together are complementary, not substitutes for each other.
  • How do you test the negative case — access correctly denied? — Same setup with a principal/resource combination that shouldn't succeed, asserting HasSucceeded is false (and, if relevant, HasFailed if the handler calls Fail explicitly).
  • Is mocking IAuthorizationService itself ever appropriate, versus testing real handlers? — For a controller-level test where the authorization outcome is a given ("assume the user is allowed, test the rest of the action"), mocking the service is fine; for testing the authorization logic itself, you want the real handler under test.

Wrong answer: "You need WebApplicationFactory/TestServer and a real bearer token to test authorization logic." That's the right tool for testing that the pipeline as a whole enforces authorization end-to-end, but it's overkill and slow for testing one handler's decision logic in isolation — a plain unit test on the handler is faster and more precise for that.

Design the authorization model for a project-management app: users belong to organizations, projects belong to organizations, and a user can have different roles on different projects within the same org. principal

I'd model this as resource-based authorization from the start, not attribute-based — the permission depends on which project, not just which endpoint, so the check has to happen after the project is loaded, using IAuthorizationService.AuthorizeAsync(User, project, requirement). Claims in the token would carry org membership (a stable, session-length fact worth putting in the token) but I would not try to cram every project-role assignment into the token — that's exactly the claim-bloat problem from unit 03, and project roles change far more often than a token's lifetime, meaning a token-baked role would go stale. Instead, project-role lookups go through a scoped, cached service the handler calls at authorization time, keyed by (user, project) — recent-enough to be enforced correctly, cached long enough not to hit the database on every request. The requirement/handler pair encodes "does this user's role on this project satisfy this action's minimum," and the same handler serves every project-scoped endpoint, so adding a new permission level later is a handler change, not a per-controller rewrite.

Example 
// Requirement carries the minimum role needed; handler compares against a cached per-(user,project) lookup.
public record ProjectRoleRequirement(ProjectRole Minimum) : IAuthorizationRequirement;

Follow-ups

  • Why not just put "projectRoles": {"p1":"Admin","p2":"Viewer",...} as a token claim? — It bloats the token linearly with project count, goes stale the moment a role changes mid-token-lifetime, and turns a data-authorization concern into an identity-token concern — the two should stay decoupled exactly because they change on different timelines.
  • How do you avoid a database round-trip on every project-scoped request? — A short-TTL cache (seconds to a couple of minutes) keyed by (user id, project id), invalidated proactively on role-change events where feasible — the same staleness-vs-freshness trade-off that runs through unit 03 and unit 08.
  • Does org-level membership need the same treatment, or is it fine as a token claim? — Org membership changes far less often and is coarser-grained, so it's a more reasonable token claim than a fine-grained, fast-changing per-project role — the design decision is about rate of change and grain, not a blanket rule against any authorization data in tokens.

Wrong answer: "Use [Authorize(Roles = "ProjectAdmin")] on every project endpoint." A static role attribute has no way to express "admin of this project, not that one" — it can only check a claim value against a fixed string, which is the wrong shape entirely for a per-resource role; this is precisely the scenario resource-based authorization exists for.

Most .NET shops authenticate against Entra ID (the renamed Azure AD) rather than a bespoke OIDC provider, so interviewers in this ecosystem often want to know the platform-specific vocabulary and gotchas, not just generic OIDC. Screeners get app registrations and MSAL basics; senior/principal levels get multi-tenant app models, app roles vs. groups, and the v1-vs-v2 endpoint distinction that still trips people up on older code.

What's the difference between an "app registration" and an "enterprise application" in Entra ID? screener

An app registration is the global definition of an application — its redirect URIs, exposed API scopes, client secrets/certificates, requested permissions — created once in the tenant that owns the app. An enterprise application (a service principal) is the tenant-local representation of that app being used in a given tenant, including a multi-tenant app being consented into a customer's tenant that doesn't own the registration. For a single-tenant app, the two are created together and the distinction is mostly invisible; for a multi-tenant SaaS app, one app registration in the vendor's tenant produces a separate enterprise application object in every customer tenant that consents to it.

Example 
App registration (vendor tenant): "Contoso Invoicing" — owns the client ID, redirect URIs, API permissions.
Enterprise application (customer tenant): the same app, represented locally once "Contoso Invoicing" is consented into that tenant, carrying tenant-specific consent grants and sign-in restrictions.

Follow-ups

  • Where do conditional access policies attach — the registration or the enterprise app? — The enterprise application (service principal) in the tenant applying the policy — a customer tenant admin controls conditional access for how their users use the app, independent of the vendor's registration.
  • Can a customer tenant admin disable sign-in to a multi-tenant app they didn't create? — Yes, via the enterprise application object in their own tenant — this is exactly the local-control point the two-object model exists to provide.
  • Does this distinction matter for a purely single-tenant internal app? — Barely in practice — both objects exist but are managed together, so the split becomes visible mainly once multi-tenancy or app-to-app permission grants enter the picture.

Wrong answer: "They're just two names for the same thing in the portal." They're genuinely different objects with different scopes of control — conflating them is where "why can't I see conditional access settings on my app registration" confusion comes from.

What's the difference between the Microsoft identity platform v1.0 and v2.0 endpoints, and why does it still matter in 2026? mid

v2.0 is the current, OIDC-conformant endpoint (/oauth2/v2.0/...), supports personal Microsoft accounts alongside work/school accounts, uses scope instead of the older resource parameter, and issues tokens whose iss/aud claims follow OIDC conventions. v1.0 (/oauth2/...) predates full OIDC conformance and is still around mainly for legacy app registrations and libraries (ADAL, the MSAL predecessor) that were never migrated. It matters in 2026 because plenty of long-lived enterprise apps and on-prem-adjacent tooling still authenticate against v1.0 semantics under the hood even when using a current MSAL version, and getting the endpoint version wrong when debugging a token's claims (expecting v2.0 iss shape, actually getting v1.0) is a real, recurring confusion.

Example 
v1.0 iss claim:  https://sts.windows.net/{tenantId}/
v2.0 iss claim:  https://login.microsoftonline.com/{tenantId}/v2.0

Follow-ups

  • Does MSAL let you choose which endpoint version to target? — Largely yes, via the app registration's supported-account-types configuration and library defaults — current MSAL defaults to v2.0 behavior for new registrations.
  • Is ADAL still supported? — No — ADAL has been out of support for some time; any app still on it is a migration item, not a maintained option, worth flagging in a legacy-audit conversation.
  • Does this affect which claims validation code needs to check? — Yes — token-validation code hardcoding one iss shape will reject tokens from the other version, a classic source of "valid token, rejected anyway" bug reports during a v1-to-v2 migration.

Wrong answer: "v1 and v2 are just old and new URLs for the same tokens." The claim shapes, supported account types, and parameter names (resource vs scope) genuinely differ — treating them as interchangeable is exactly what breaks token-validation code during a migration.

What's the difference between an Entra ID "app role" and a security "group," and when would you use one over the other for authorization? mid

App roles are defined per app registration (in its manifest) and assigned to users/groups/service principals specifically for that app — they show up in the token's roles claim and are meant to answer "what can this identity do in this app." Groups are tenant-wide organizational objects, independent of any one app, and show up in the groups claim (or, for larger tenants, require the Microsoft Graph group-membership API instead of an inline claim, because of the claim-size limit discussed below). App roles are the better default for app-specific authorization because they're explicitly scoped and centrally visible in the app's own access-review blade; groups are better when the permission genuinely maps to an existing organizational grouping (a department, a team) shared across multiple systems.

Example 
// App registration manifest excerpt defining an app role:
"appRoles": [{ "value": "OrderManager", "displayName": "Order Manager", "allowedMemberTypes": ["User"] }]

Follow-ups

  • What happens when a user is in more than 200 groups? — Entra ID omits the groups claim from the token entirely and adds an hasgroups/overage indicator instead, forcing the app to call Microsoft Graph to enumerate memberships — a real gotcha for any org with deep nested groups, and a reason some teams prefer app roles precisely to avoid this overage behavior.
  • Can app role assignment be delegated to non-admins? — Yes, via Entra ID's application access management / group-owner delegation features, without granting full admin rights — useful for scaling role assignment without expanding the admin population.
  • Do app roles appear for service principals too, not just users? — Yes — app roles can be assigned to another application's service principal, which is how app-to-app (client credentials) authorization is commonly scoped in Entra ID.

Wrong answer: "Just put everyone in security groups and check group membership for all authorization." That's exactly what runs into the 200-group claim overage problem and couples app-specific permissions to org-chart structure that changes for unrelated HR reasons — app roles exist specifically to decouple the two.

A multi-tenant app needs admin consent before it can read directory data. Walk through the admin consent flow and why it exists. senior

Some requested permissions (application permissions, and "high-privilege" delegated permissions like reading all users' profiles) can't be granted by an individual end user consenting for themselves — they affect the whole tenant, so Entra ID requires a tenant administrator to explicitly grant consent once, on behalf of the organization. The app redirects to a dedicated admin-consent endpoint (/adminconsent), the admin reviews the requested permission list, and on approval Entra ID records a tenant-wide grant so individual users in that tenant no longer see an individual consent prompt for those permissions. This exists because a single end user shouldn't be able to unilaterally grant an app access to, say, every other employee's directory data just by clicking "accept" on their own sign-in.

Example 
GET https://login.microsoftonline.com/{tenant}/adminconsent?client_id={id}&redirect_uri={uri}

Follow-ups

  • What's the difference between "delegated" and "application" permissions here? — Delegated permissions act as the signed-in user and are bounded by what that user could do anyway; application permissions act as the app itself with no signed-in user context, which is why they almost always require admin consent regardless of "risk" classification.
  • Can admin consent be pre-granted before any user signs in? — Yes — that's exactly what the dedicated admin-consent flow/URL is for, letting an admin onboard the app tenant-wide up front rather than waiting for the first user's sign-in to trigger a prompt.
  • What happens if a non-admin user hits a permission requiring admin consent that hasn't been granted? — They're blocked with a message that admin approval is required, and (depending on tenant settings) may be able to submit an admin-consent request that surfaces in the admin's approval queue instead of just failing silently.

Wrong answer: "Consent is consent — it doesn't matter if a regular user or an admin clicks accept." High-privilege and application permissions are deliberately gated so an individual user's click can't grant tenant-wide access on behalf of everyone else — that distinction is the entire point of admin consent existing as a separate flow.

Your app calls Microsoft Graph as itself (not on behalf of a user) using client credentials. What permission type do you request, and what's the security posture around the credential? mid

Application permissions (not delegated), granted to the app's service principal and requiring admin consent as above, obtained via the client credentials grant with either a client secret or, preferably, a certificate/managed identity as the credential. Because there's no user in this flow, the app effectively acts with whatever the application permission grants — it can't be scoped down per-call the way a delegated, on-behalf-of-user token is implicitly scoped to that user's own access — so the permission chosen should be the narrowest Graph permission that satisfies the need (e.g. User.Read.All rather than Directory.ReadWrite.All if only reads are needed), and the credential itself (secret or certificate) needs the same protection as any other long-lived, high-privilege secret: rotated, never in source control, ideally replaced with a managed identity when running in Azure.

Example 
var credential = new ClientSecretCredential(tenantId, clientId, clientSecret); // or, better, a certificate / managed identity
var client = new GraphServiceClient(credential);

Follow-ups

  • Why prefer a managed identity over a client secret here? — A managed identity has no secret value to leak, rotate, or accidentally commit — Azure handles credential issuance and rotation entirely, removing an entire class of operational risk.
  • Does an application-permission token expire the same way a delegated one does? — Yes, standard access-token lifetimes apply; the client credentials grant is repeated (typically by MSAL's token cache handling this transparently) rather than the token living forever.
  • Can application permissions be scoped to specific resources rather than "all"? — For some Graph resources, yes, via application access policies (e.g. restricting a mail-permission app to specific mailboxes) — worth mentioning as the more precise alternative to a blanket .All permission when it's available for the resource in question.

Wrong answer: "Application permissions and delegated permissions are interchangeable, just pick whichever the SDK defaults to." They have fundamentally different blast radii — an application permission grants the app power independent of any user, so picking the wrong one (or the broadest one "to be safe") is a real over-privilege risk, not a cosmetic choice.

What is Continuous Access Evaluation (CAE), and how does it change the "tokens are only as fresh as their last validation" assumption? senior

Normally, once an access token is issued, a resource API validates it locally (signature, expiry, claims) without checking back with the identity provider — meaning a user disabled, a password changed, or a risky-sign-in detected mid-token-lifetime has no effect until the token naturally expires. CAE-enabled resource APIs (Microsoft Graph and other first-party APIs support it, and it's extensible to third-party APIs) get near-real-time revocation signals pushed from Entra ID — critical events like account disable, password change, or a Conditional Access policy violation cause the resource API to reject the token immediately, even though it hasn't expired, instead of waiting out its lifetime. This lets Entra ID issue longer-lived tokens for CAE-aware clients/resources without the usual "long-lived token = slow revocation" trade-off from unit 08.

Example 
Without CAE: token valid 60-90 min regardless of events mid-lifetime.
With CAE: token can be revoked within minutes of a critical event, independent of its nominal expiry.

Follow-ups

  • Does CAE require anything from the client, or is it purely server-side? — The client (via MSAL) needs to understand CAE challenge responses (a WWW-Authenticate header signaling the token was rejected for a CAE reason) and re-acquire a token rather than treating it as a generic auth failure — so it's a client-and-server cooperative feature, not purely transparent.
  • What events trigger CAE revocation, specifically? — The commonly cited set is user account disabled/deleted, password changed or reset, and certain Conditional Access policy changes (e.g. a new location/device restriction) — not every possible token-invalidating event.
  • Does CAE replace short token lifetimes as a mitigation, or complement them? — It complements — CAE handles the "critical event happened" case fast; short lifetimes still bound the damage from events CAE doesn't cover, so teams shouldn't treat CAE support as a reason to stop thinking about token lifetime altogether.

Wrong answer: "Access tokens from Entra ID are always instantly revocable now, so lifetime doesn't matter." CAE covers a specific, real-time-critical set of events for CAE-aware clients and resources — it's not blanket instant revocation for every token everywhere, and non-CAE-aware resource APIs still behave the old way.

How does the Microsoft identity platform's "on-behalf-of" (OBO) flow work, and when do you need it? senior

OBO is for a middle-tier API that has already received a delegated access token from a client, and now needs to call a downstream API as the same user, without the user being present to authorize a second time. The middle-tier API exchanges the token it received (as its own client credential plus the incoming token as an assertion) for a new token scoped to the downstream API, still representing the original user. This is the standard shape for a layered architecture — SPA calls API A, API A needs data from API B on the user's behalf — and it preserves the delegated (user-scoped) nature of the access rather than falling back to a service-to-service, user-blind call.

Example 
POST /oauth2/v2.0/token
grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
&assertion={incoming_user_token}
&client_id={apiA_client_id}&client_secret={apiA_secret}
&scope=api://apiB/.default

Follow-ups

  • Why not just have API A call API B with its own client-credentials token instead? — That loses the user context entirely — API B would see "API A is calling me" with no idea which end user's data is actually being requested, breaking any per-user authorization or audit trail on API B's side.
  • Does the user need to be online/present during the OBO exchange? — No — that's the whole point; OBO happens server-to-server using the already-issued token as proof of the user's earlier authorization, without a new interactive step.
  • What's the token-lifetime relationship between the original and OBO-exchanged token? — The new token has its own lifetime and scope, but ultimately traces back to the same original user consent/session — if the original session is revoked, subsequent OBO exchanges for it should fail too.

Wrong answer: "OBO just means API A forwards the user's original token to API B unchanged." Forwarding the same token means API B sees an audience meant for API A (a token confusion/replay risk audited against in unit 03) — OBO specifically mints a new, correctly-audienced token for API B rather than reusing the original one.

Design the Entra ID app registration and permission model for a SaaS product sold to multiple customer organizations, each with their own tenant. principal

I'd register the app as multi-tenant in the vendor's own tenant, with a /common (or /organizations) authority so any customer tenant can sign in, and I'd require each customer's admin to go through the explicit admin-consent flow (not per-user consent) for any application permission the backend needs — end users clicking through their own consent for a SaaS product that reads company-wide data is exactly the unilateral-grant problem admin consent exists to prevent. For per-user, per-customer authorization inside the product, I'd rely on app roles assigned within each customer's tenant (each customer's admin manages their own users' roles for the app, in their own enterprise application object) rather than trying to centrally manage a single cross-tenant role list — that keeps each customer's access control inside their own governance boundary, which is usually a contractual/compliance expectation for enterprise SaaS. I'd also plan for tenant-level isolation of any application-permission client-credentials calls, since a compromised credential in this model could reach every onboarded customer tenant at once — the single highest-blast-radius secret in the whole design, worth extra protection (certificate over secret, tight rotation, alerting on anomalous use).

Example 
Vendor tenant: one multi-tenant app registration, signInAudience: AzureADMultipleOrgs.
Customer tenant A: enterprise app object + admin-granted app roles for A's users.
Customer tenant B: separate enterprise app object + independently admin-managed roles for B's users.

Follow-ups

  • How do you avoid one compromised customer's admin consent affecting other customers? — Each tenant's consent and enterprise-app object is genuinely separate — a compromise in one customer's tenant configuration doesn't grant access into another customer's tenant, since the application permission is consented per-tenant, not globally once.
  • What's the failure mode if the vendor's own multi-tenant client credential is compromised? — Depends on the permission model — if application permissions are used to reach into every customer tenant's data (a common SaaS backend pattern), a single compromised credential is a cross-customer breach, which is exactly why it deserves disproportionate protection relative to a normal service credential.
  • Would you ever recommend single-tenant app registrations per customer instead? — For very high-security customers, sometimes — a dedicated app registration per customer trades operational complexity for a harder isolation boundary; it's a real, occasionally justified alternative to the shared multi-tenant registration model.

Wrong answer: "Register the app once, ask each user to consent individually, and manage all roles centrally in the vendor's own tenant." Individual consent for a SaaS product reading organizational data is exactly the case admin consent exists to block, and centrally managing customer-specific roles from the vendor's tenant breaks the governance boundary most enterprise customers require for their own users' access.

08 Token lifetimes, rotation & revocation

Every token-based design eventually has to answer "how long does this live, and what happens when it needs to stop working before that." Screeners get access-vs-refresh-token basics; mid-level candidates need rotation and revocation mechanics; senior/principal levels get the harder trade-offs around offline access, refresh token theft detection, and revocation at scale.

RFC 6749 §1.5 refresh tokens · OAuth 2.1 draft

Why do OAuth systems use short-lived access tokens plus a longer-lived refresh token, instead of one long-lived token? screener

An access token is presented to resource servers on every API call, so its exposure surface is large — logs, intermediate proxies, browser memory — and it's typically validated locally without a round-trip to the issuer, meaning revocation only takes effect at expiry. Keeping it short-lived (minutes) bounds the damage of a leaked one. The refresh token is presented only to the authorization server's token endpoint, far less often and to a single trusted party, so it can safely live much longer (hours to days/weeks) while still being revocable server-side at any moment, since every use requires a live round-trip to the AS. Splitting the two lets you get both properties — a short blast radius for the widely-exposed token and real-time revocability for the long-lived one — that a single token of either lifetime alone can't provide.

Example 
Access token:  ~5-60 min, sent to every resource server, validated locally, can't be revoked before expiry (usually).
Refresh token: hours-to-weeks, sent only to the AS's token endpoint, revocable instantly server-side.

Follow-ups

  • Could you just make the access token itself short and skip refresh tokens, forcing re-login? — That's a valid, simpler design for some apps, but it trades user experience (re-authenticating every few minutes) for the property refresh tokens exist to give you — long-lived usable sessions with a short-lived credential doing the actual API work.
  • Is a refresh token itself ever sent to a resource server? — No, never — it should only ever go to the authorization server's token endpoint; a resource server receiving one is a sign something is misconfigured.
  • Does this two-token split apply to client-credentials-grant service-to-service calls? — Not usually — there's no user session to keep alive, so a service simply requests a fresh access token via client credentials again when needed, without a refresh token in the picture at all.

Wrong answer: "Refresh tokens exist just to avoid re-typing a password." That's a UX side-effect, not the design reason — the real point is decoupling a widely-exposed, hard-to-revoke credential from a narrowly-exposed, easily-revoked one.

What is refresh token rotation, and what problem does it solve that a static, reusable refresh token doesn't? mid

With rotation, every use of a refresh token to get a new access token also issues a brand-new refresh token and invalidates the one just used — so a refresh token is single-use. A static reusable refresh token, once stolen, works for its entire remaining lifetime with no way for the legitimate client or server to notice the theft, since both the attacker and the legitimate holder (if they still have a copy) would be using "the same valid token." Rotation turns reuse into a detectable signal: if a refresh token that's already been rotated-away-from is presented again, that's strong evidence of theft (both the legitimate client and an attacker had a copy, and one of them used it first) — the AS can respond by revoking the entire token family, not just the one reused token.

Example 
1. Client uses RT1 -> gets AT2 + RT2 (RT1 now invalid)
2. Attacker, who copied RT1 earlier, tries RT1 -> rejected AND the whole chain (RT2 onward) gets revoked

Follow-ups

  • What's "refresh token family" revocation, concretely? — All refresh tokens descended from one original grant are linked; detecting reuse of any token in that chain revokes the whole chain, not just the reused token, since you can no longer tell which of the two holders is legitimate.
  • Does rotation add latency or failure modes for legitimate clients? — It adds a requirement that the client reliably persist the new refresh token before discarding the old one — a client that crashes between receiving RT2 and saving it, then retries with RT1, can trigger a false-positive theft detection; robust clients handle this with a brief grace window or careful ordering.
  • Is rotation mandatory in OAuth 2.1? — The draft requires either rotation or another comparable mechanism (like sender-constraining via DPoP/mTLS) for public clients specifically — it's tightened from being merely recommended, reflecting how central this protection has become for the public-client threat model.

Wrong answer: "Rotation just means refresh tokens expire faster." Rotation is about single-use-and-replace, not shorter expiry — a rotated token could have the same nominal max lifetime as a non-rotated one; the security property comes from detecting reuse, not from shortening a timer.

How do you revoke a specific access token before it expires, given that resource servers usually validate JWTs locally without calling back to the issuer? senior

Strictly speaking, you usually can't revoke a bare self-contained JWT access token in the classic sense without giving up the "validate locally, no round trip" property that made JWTs attractive in the first place — the honest answer is that immediate access-token revocation and stateless local validation are in tension, and a design has to pick which one it needs more. Real mitigations: keep access tokens short-lived so "revocation" mostly means "wait a few minutes" (the dominant real-world answer); maintain a denylist/introspection check for the rare high-stakes case (RFC 7662 token introspection, or a fast in-memory revoked-jti cache) at the cost of reintroducing a round trip or shared state; or use a mechanism like CAE (unit 07) where the resource API itself is revocation-aware for a defined set of critical events. Revoking the refresh token is straightforward and immediate — it just doesn't retroactively invalidate access tokens already issued from it.

Example 
POST /revoke  (RFC 7009) — revokes a refresh token immediately; already-issued access tokens from it keep working until they expire.

Follow-ups

  • Does token introspection defeat the point of using JWTs at all? — Largely for the resources that need it — introspection reintroduces a network call per validation, the exact cost self-contained JWTs were meant to avoid; it's a deliberate trade for a specific high-value resource, not something you'd apply universally without reason.
  • What TTL do most production systems actually use for access tokens, given this trade-off? — Commonly 5-15 minutes for the general case, sometimes even shorter for high-sensitivity APIs — short enough that "can't revoke early" is an acceptable residual risk.
  • Is a revoked-jti denylist a good general-purpose answer? — It works but needs to be checked on every request, which is exactly the shared-state cost being avoided — reasonable at small scale or for a short list of "break glass" revocations, less so as a default for every token.

Wrong answer: "Just call an endpoint to revoke the access token and it stops working immediately everywhere." Unless every resource server is doing introspection or checking a shared revocation list on every request, nothing stops a self-contained JWT from continuing to validate successfully right up to its stated expiry — this is a structural property of local JWT validation, not a missing feature to configure away.

What token lifetimes would you actually configure for a consumer-facing mobile banking app, and why? senior

I'd lean short on the access token (5-15 minutes) given the earlier revocation trade-off, since banking data justifies erring toward "an attacker gets a shorter window" over convenience. The refresh token lifetime is the more interesting call: absolute lifetime capped fairly aggressively (say, a few days to two weeks) forcing periodic full re-authentication, combined with sliding renewal on active use so a daily user never notices, plus mandatory rotation and reuse detection given the higher value of the target. I'd also bind session risk to device/behavioral signals rather than pure token lifetime alone — step-up re-authentication (biometric prompt) for high-value actions (a large transfer) regardless of how fresh the session token is, since a stolen-but-still-valid refresh token shouldn't be sufficient on its own to move money.

Example 
Access token: 10 min. Refresh token: sliding, 14-day absolute cap, rotated on every use, reuse-detected.
High-value action: step-up re-auth regardless of token freshness.

Follow-ups

  • Why not just make everything expire in minutes for maximum safety? — A banking app with a 5-minute total session lifetime would force re-login constantly, which pushes users toward workarounds (staying logged into a browser tab, writing down credentials) that are worse for security than a well-designed longer-but-revocable session.
  • Is step-up authentication a token-lifetime concept at all? — Not directly — it's a complementary control that doesn't rely on token freshness; it's included here because a purely lifetime-based design still leaves a stolen-but-unexpired token able to do anything the original session could, which step-up specifically closes for the highest-value actions.
  • Does this differ for a business/corporate banking API rather than a consumer app? — Often tighter still — corporate banking APIs frequently use mTLS/DPoP-bound tokens and much shorter access-token lifetimes given the larger transaction sizes typically at stake.

Wrong answer: "Use whatever the identity provider's default lifetimes are." Defaults are chosen for a generic app, not calibrated to a specific risk profile — a banking app's token-lifetime choices should trace to an explicit threat model (transaction value, regulatory requirements), not an unexamined platform default.

What's the difference between token revocation and token expiration from a system-design standpoint? mid

Expiration is a property baked into the token itself at issuance (the exp claim) — no party needs to do anything for it to take effect, it just stops being valid once its stated time passes, and every relying party can check it locally. Revocation is an external event, decided later than issuance, that says "this specific still-unexpired token (or family of tokens) should stop being honored now" — and whether that "now" is actually enforceable depends entirely on whether the relying party checks for revocation at all (the tension explored above). Designing a system means choosing, for each token type, what the expiration window is and what revocation mechanism (if any) backs it up before that window closes.

Example 
Expiration: exp: 1735689600 — enforced by every validator automatically, no extra call needed.
Revocation: "invalidate refresh token RT2 right now" — only effective if the token endpoint checks a revocation store on use.

Follow-ups

  • Can a token be "revoked" after it has already expired? — It's a no-op in practice — there's nothing left to invalidate once it's already unusable, though revocation records sometimes still get written for audit purposes.
  • Which of the two is refresh token rotation-and-reuse-detection an instance of? — Revocation — reuse detection triggers an explicit "invalidate this token family now" decision, independent of whatever expiration timers were already set on those tokens.
  • Is there a middle ground, like a token that re-validates itself periodically? — CAE (unit 07) is close to this — a token nominally has a longer expiration but is subject to near-real-time revocation signals for specific events, blurring the line between the two mechanisms for CAE-aware resources specifically.

Wrong answer: "Revocation is just setting a shorter expiration after the fact." Expiration is a static, pre-committed value inside the token that can't be changed retroactively without the relying party doing extra work — that extra work (checking a revocation signal) is precisely what "revocation" as a mechanism refers to.

Your app uses long-lived refresh tokens for "remember me" functionality. What's your strategy for detecting and responding to a stolen refresh token? senior

Rotation-with-reuse-detection (above) is the primary mechanism — it turns theft into a detectable event automatically, without needing to guess at "suspicious" behavior. Beyond that, I'd bind refresh tokens to signals that don't normally change mid-session (a device fingerprint, an IP range, sometimes DPoP/mTLS-based sender-constraining per unit 08's harder end) so a token used from a wildly different context raises risk even without an outright reuse event; and I'd log every refresh-token use with enough detail (rough geolocation, device, timestamp) to support both automated anomaly detection and after-the-fact incident investigation (unit 15's territory). On detection, the response should be revoke-the-family plus force re-authentication, not a silent no-op — a user should be told "we signed you out of this session because something looked wrong," both for their own security awareness and to reduce support tickets about mysterious logouts.

Example 
On reuse detection: revoke entire token family, notify user of the security event, require full re-auth (ideally with step-up/MFA) for the next sign-in.

Follow-ups

  • Does device/IP binding risk false positives that annoy legitimate users? — Yes — mobile users change networks constantly, so this needs to be a risk signal that informs a decision (maybe trigger step-up rather than an outright block) rather than a hard binding that logs someone out every time they switch from Wi-Fi to cellular.
  • Should the user be notified even if the "theft" turns out to be their own second device? — Generally yes — a notification with a clear "was this you?" framing costs little and is exactly the kind of visibility that helps a real victim notice a real compromise faster.
  • How does this interact with a legitimate multi-device use case (phone + tablet)? — Each device should get its own token family from its own original authentication, not a shared one — conflating "multiple legitimate devices" with "one token copied across devices" is what causes both false positives and, worse, false negatives.

Wrong answer: "There's no way to detect refresh token theft, so just rely on short access token lifetimes." Rotation-based reuse detection is a real, standard, implementable mechanism specifically for this — dismissing detection entirely and falling back only on access-token TTL ignores the tool built for exactly this problem.

What is token binding / sender-constraining (DPoP, mTLS), and how does it change the value of a stolen token? senior

An unconstrained bearer token is valid for whoever presents it — possession alone is proof, which is why token theft (via XSS, a compromised log, a malicious proxy) is such a high-value attack. Sender-constraining ties a token to a specific cryptographic key the legitimate client holds, so presenting the token alone isn't enough — the presenter also has to prove possession of the bound key on every use. DPoP does this by requiring a client-signed proof-of-possession JWT alongside the token on each request; mTLS-based constraining binds the token to the client's TLS certificate used during issuance and requires the same certificate on use. Either way, a stolen token without the corresponding private key is worthless — this is the single biggest lever for reducing the impact of a leaked access or refresh token, more so than shortening lifetimes alone.

Example 
POST /resource
Authorization: DPoP eyJ...     (the access token)
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs...   (proof, signed with the client's private key, bound to this exact request)

Follow-ups

  • Does DPoP require server infrastructure like mTLS does (client certs, PKI)? — No, that's a large part of its appeal — DPoP is a JSON-based proof mechanism usable over plain TLS, no client-certificate PKI needed, which is why it's become the more commonly adopted option for public clients like SPAs and mobile apps versus mTLS's heavier infrastructure requirements.
  • Does sender-constraining eliminate the need for short token lifetimes? — No — it's a complementary control; a stolen token is now useless without the key, but the key itself could still be extracted in a sufficiently thorough compromise, so lifetime limits remain a second layer, not a redundant one.
  • Is DPoP required by OAuth 2.1? — Not mandated outright, but the draft treats sender-constraining mechanisms (DPoP or mTLS) as strongly recommended, especially as an alternative or complement to refresh token rotation for public clients — the direction of travel in the spec is clearly toward expecting one of them.

Wrong answer: "DPoP just adds another token to check, so it doesn't really add security beyond validating one more signature." The point isn't the extra signature check itself, it's that the proof requires possession of a private key never transmitted anywhere — an attacker with the access token alone (the thing that actually leaks in XSS/log-exposure scenarios) still can't use it without that key.

Design "logout everywhere" for a system with both a web app (cookie session) and a mobile app (refresh token) sharing one identity backend. principal

The core requirement is a single, queryable notion of "this user's sessions/grants," independent of which client type produced them — I'd maintain a session/grant store keyed by user id, with each row tracking enough to identify and individually revoke one session (cookie ticket id or refresh-token-family id, device info, last-used timestamp), and "logout everywhere" becomes one write against that store (mark all rows for this user revoked) rather than a per-client-type special case. The web app's cookie needs OnValidatePrincipal-style revocation checking (unit 05) against that same store; the mobile app's refresh token needs the token endpoint to check the same store before honoring a refresh — different enforcement points, same underlying source of truth, which is the design property that actually makes "everywhere" true rather than aspirational. I'd also expose this to the user as a real feature (a list of active sessions/devices with individual revoke buttons), not just an internal admin capability, since users increasingly expect that visibility and it turns a support-ticket-driven process into self-service.

Example 
sessions table: (user_id, session_id, client_type, device_info, created_at, revoked_at)
Web cookie validation:    check sessions WHERE session_id = ticket.session_id AND revoked_at IS NULL
Mobile refresh:           check sessions WHERE session_id = refresh_token.session_id AND revoked_at IS NULL
"Logout everywhere":      UPDATE sessions SET revoked_at = now() WHERE user_id = :id

Follow-ups

  • What's the latency for a logged-out session actually being rejected? — Bounded by how often each enforcement point checks the store — the cookie's OnValidatePrincipal throttle interval, and the refresh token endpoint, which should check on every single use since refresh happens far less often than API calls; access tokens already issued before revocation still work until they naturally expire, per the earlier revocation-vs-expiration discussion, so this design's access-token lifetime should stay short.
  • Does this scale to a high-request-volume system without the store becoming a bottleneck? — The cookie side is throttled already; the refresh-token side is checked far less frequently than raw API calls (refresh happens on the order of the access-token lifetime, not per-request), so the store's query volume is naturally bounded well below total API traffic.
  • How do you handle a client that's offline when revoked — does it "know" immediately? — It doesn't, and shouldn't be expected to — the guarantee is that the server will reject its next attempt to use a revoked credential, not that the client is proactively notified; that's an acceptable, standard limit on what "logout everywhere" can promise for an offline device.

Wrong answer: "Just tell the mobile app to delete its refresh token and the web app to clear its cookie via a push notification." That relies on the client cooperating and being reachable — a compromised or offline device won't clear anything on command; "logout everywhere" has to be enforceable from the server side regardless of client cooperation, which requires the shared revocation-checkable store, not a client-side instruction.

09 ASP.NET Core Identity & passwordless

ASP.NET Core Identity is the framework's own user-store-and-password-management layer, distinct from the OIDC/OAuth machinery covered earlier — plenty of apps use both together (Identity for local accounts, OIDC/external providers for social/enterprise login). This unit also covers the passwordless/passkey direction the industry has been moving, which is increasingly a live topic in 2026 interviews.

ASP.NET Core Identity overview · WebAuthn Level 3

What does ASP.NET Core Identity actually provide, and what's it not responsible for? screener

Identity is a user-store abstraction (backed by EF Core by default, but pluggable) plus the surrounding machinery for local-account concerns: password hashing and validation policy, email/phone confirmation, two-factor setup, lockout after failed attempts, and the security-stamp mechanism for invalidating existing sessions when something sensitive changes. It is not an OAuth/OIDC authorization server, and not a token-issuing service — those are separate concerns handled by the JWT bearer/OIDC handlers or a product like Duende IdentityServer, which can sit on top of an Identity-backed user store but aren't part of Identity itself. Conflating the two is a common source of "why doesn't Identity give me an /authorize endpoint" confusion.

Example 
builder.Services.AddIdentity<ApplicationUser, IdentityRole>()
    .AddEntityFrameworkStores<AppDbContext>()
    .AddDefaultTokenProviders();

Follow-ups

  • Can Identity be used with a non-EF store? — Yes — the store interfaces (IUserStore, IRoleStore, etc.) are the actual extension point; EF Core is the default, most common implementation, not a hard requirement.
  • Does ASP.NET Core Identity issue JWTs itself? — As of newer versions there's a lightweight bearer-token option for API scenarios, but it's a much thinner mechanism than a real OAuth authorization server — for real OAuth/OIDC flows, Identity is typically the user store behind a proper AS, not the AS itself.
  • Is Identity's cookie the same cookie scheme discussed in unit 04/05? — Yes — AddIdentity registers and configures the same underlying cookie authentication scheme, just pre-wired with Identity-specific event handlers (like the security-stamp validator).

Wrong answer: "ASP.NET Core Identity is Microsoft's OAuth server for .NET." It's a local user-account management layer, not an authorization server — the confusion is common enough to be worth heading off explicitly in an answer.

How does ASP.NET Core Identity hash passwords, and why shouldn't you ever write your own hashing code instead? screener

The default PasswordHasher<TUser> uses PBKDF2 (HMAC-SHA256) with a per-password random salt and a configurable, versioned iteration count — versioned so the format can be upgraded later (a v2 hash with a higher iteration count) while still being able to verify and rehash older v1 hashes on next successful login. Rolling your own hashing invites exactly the mistakes this area is famous for: no salt (identical passwords hash identically, enabling rainbow-table attacks), too few iterations (fast to brute-force on modern hardware), or picking a fast general-purpose hash like plain SHA-256 instead of a deliberately slow, tunable one — Identity's implementation exists specifically so individual apps don't have to get these judgment calls right themselves.

Example 
// Handled internally — you just call:
var result = hasher.VerifyHashedPassword(user, user.PasswordHash, providedPassword);
if (result == PasswordVerificationResult.SuccessRehashNeeded) { /* re-hash with current settings, save */ }

Follow-ups

  • Is PBKDF2 still considered adequate in 2026, versus Argon2/bcrypt? — It's still acceptable with a sufficiently high iteration count, though Argon2 (memory-hard, harder to accelerate with GPUs/ASICs) is increasingly the security community's preferred recommendation for new systems — worth naming as the more modern alternative even though Identity's default remains PBKDF2.
  • Can you plug a different hasher into Identity? — Yes — IPasswordHasher<TUser> is a replaceable service, so swapping in an Argon2-based implementation is supported without forking Identity itself.
  • What's the "rehash needed" mechanism protecting against? — It lets you raise the iteration count over time without forcing a mass password reset — existing hashes are silently upgraded to the new setting the next time each user successfully logs in.

Wrong answer: "Just use SHA256.HashData on the password, maybe add a salt." Plain SHA-256 is fast — exactly the property you don't want in a password hash, since it makes brute-forcing leaked hashes cheap; slow, tunable, salted algorithms (PBKDF2, bcrypt, Argon2) exist specifically to counter this.

What's the "security stamp" in ASP.NET Core Identity, and what triggers it to change? mid

The security stamp is a value stored on the user record and embedded as a claim in any issued cookie/session; Identity's SecurityStampValidator periodically re-checks the claim's value against the current database value and rejects the principal if they've diverged. Changing the password, changing two-factor settings, or explicitly calling UpdateSecurityStampAsync all rotate the stamp — which is the mechanism this unit's own cookie-revocation question (unit 05) was pointing at: it's specifically how "the user changed their password" propagates into "all their other existing sessions stop working," without needing a separate ad hoc revocation list.

Example 
await userManager.UpdateSecurityStampAsync(user); // invalidates every other existing session for this user

Follow-ups

  • How often does the validator actually check, by default? — On a configurable interval (commonly every 30 minutes by default) rather than every single request, for the same performance-vs-freshness trade-off discussed in unit 05 and unit 08.
  • Does the security stamp affect API/JWT-based sessions the same way? — Not automatically — it's wired into the cookie validation pipeline; a JWT-based session would need its own equivalent revocation check (introspection, a denylist) since a self-contained JWT doesn't get re-validated against the database the way a cookie principal does.
  • What happens between a password change and the next validator check? — The old session keeps working until the interval elapses and the stamp mismatch is caught — the same bounded-delay trade-off as any throttled revocation check.

Wrong answer: "Changing your password in ASP.NET Core Identity automatically and instantly logs out every other active session." It's throttled by the validator interval, not instantaneous — stating it as immediate misrepresents a real, bounded delay that matters for incident-response timelines.

What is a passkey, and how does it differ from a traditional password or even a TOTP-based second factor? mid

A passkey is a WebAuthn/FIDO2 credential: a public/private key pair, where the private key never leaves the user's device (or a synced platform keychain) and the relying party only ever stores the public key. Authentication is a signed-challenge exchange, not a shared secret being transmitted or compared — there's nothing server-side to leak that would let an attacker impersonate the user, unlike a password (a shared secret, stealable from either end) or even TOTP (a shared seed, still a secret both sides hold and which can be phished in real time via a proxy). Passkeys are also phishing-resistant by construction: the browser/OS ties the credential to the actual origin it was created for, so a look-alike phishing domain simply can't trigger the right credential to sign anything, unlike a password or OTP a user can be tricked into typing into the wrong site.

Example 
Password:  shared secret, both sides "know" it (or its hash) — phishable, leakable from a server-side breach.
TOTP:      shared seed, both sides "know" it — phishable in real time via a relay/proxy attack.
Passkey:   private key never leaves the device; server only ever has the public key — nothing secret to phish or leak.

Follow-ups

  • Does "the private key never leaves the device" mean passkeys can't be synced across devices? — Synced passkeys (via a platform's cloud keychain, e.g. across a user's own devices) replicate the private key material within that trusted, end-to-end-encrypted sync fabric — the key still never leaves that trust boundary to reach the relying party or an attacker, which is the property that actually matters.
  • Are passkeys resistant to a real-time phishing proxy the way TOTP isn't? — Yes — this is the core advantage; because the credential is origin-bound at the browser/OS level, a proxy relaying a phishing page can't get the user's device to produce a valid signature for the real origin.
  • Do passkeys replace the need for a username at all? — They can, via "discoverable credentials" letting a user sign in with just their device (no typed username), though many implementations still ask for one to speed up credential lookup.

Wrong answer: "Passkeys are just passwords stored more securely, like in a password manager." A password manager still stores (and can leak, or be phished into revealing) a shared secret — a passkey's entire security model is that there's no shared secret in the first place, which is a categorical difference, not a storage improvement on the same mechanism.

Walk through the WebAuthn registration (credential creation) ceremony at a level you'd explain in a design review. senior

The relying party's server generates a random challenge and sends it, along with relying-party and user metadata, to the browser's navigator.credentials.create() call. The browser/authenticator (a platform authenticator like a phone's biometric sensor, or a roaming one like a hardware security key) generates a new key pair scoped to that relying party's origin, signs the challenge with the new private key to prove freshness, and returns the public key plus an attestation object to the browser, which relays it back to the server. The server verifies the signature against the returned public key, checks the challenge matches what it issued (anti-replay) and that the origin matches what's expected, then stores the public key and a credential ID against the user's account — no private key material is ever transmitted at any point in this exchange.

Example 
const options = await fetch('/webauthn/register/options').then(r => r.json());
const credential = await navigator.credentials.create({ publicKey: options });
await fetch('/webauthn/register/verify', { method: 'POST', body: JSON.stringify(credential) });

Follow-ups

  • What's "attestation" for, and is it usually required? — It's a signed statement (varying in strength by authenticator) about what kind of device created the credential — useful for enterprise policies wanting to restrict to certified hardware, but most consumer-facing apps deliberately skip requiring strong attestation to stay compatible with the widest range of authenticators.
  • Why does the server need to check the origin explicitly, isn't that the browser's job? — The browser enforces origin-binding when creating/using the credential, but the server independently re-validates the origin claimed in the returned data as defense against a compromised or misbehaving client — never trust a security-relevant check to only happen client-side.
  • What library would you actually reach for in .NET for this? — Fido2NetLib is the commonly used open-source implementation for the server-side ceremony logic in .NET; ASP.NET Core Identity also has growing built-in passkey support in recent versions.

Wrong answer: "The browser handles all of WebAuthn, the server just gets a 'yes, authenticated' response." The server does real, security-critical verification work — checking the challenge, origin, and signature itself — treating it as a black box the browser fully handles is exactly the mistake that would let a forged or replayed ceremony through.

You're migrating an existing password-based user base to passkeys. What does the rollout actually look like, and what do you do about users who never adopt it? senior

Passkeys are additive, not a replacement flag-day — you'd add passkey registration as an optional account action ("add a passkey" in account settings, and a prompt post-login), let users accumulate one or more passkeys alongside their existing password, and let sign-in offer both options rather than forcing a choice. Over time, usage data (what fraction of logins use a passkey) tells you whether it's safe to start nudging harder — for instance, treating password-only sign-in as a lower-trust signal that triggers additional verification, rather than removing password login outright, since a meaningful fraction of any real user base won't adopt a new mechanism regardless of prompting. The honest answer to "what about the holdouts" for most consumer products is that passwords remain supported indefinitely, with passkeys pulling the security-conscious and lower-friction-conscious majority forward over time rather than a hard cutover.

Example 
Phase 1: passkey as optional add-on, password still primary.
Phase 2: passkey offered first at sign-in if registered, password as fallback.
Phase 3 (maybe, years out): password-only accounts get extra friction (step-up MFA) but aren't blocked outright.

Follow-ups

  • What's the account-recovery story if a user loses every device holding their passkeys? — Needs a real answer before rollout — commonly a fallback to password/email-based recovery, or a secondary passkey registered on a different device/platform account specifically for this scenario; recovery is often the actual hard part of a passkey rollout, not registration.
  • Does removing passwords entirely ever make sense? — For narrower, higher-trust user populations (an internal enterprise app with managed devices) a password-optional or password-eliminated posture is more realistic than for an open consumer product with wildly varied device capability.
  • How do you measure whether the rollout is working? — Passkey registration rate, percentage of logins actually using a passkey versus falling back to password, and — importantly — a drop in password-related support tickets and account-takeover incidents as leading indicators of real security benefit, not just adoption vanity metrics.

Wrong answer: "Just disable password login and force everyone onto passkeys on a set date." A hard cutover locks out every user who hasn't adopted the new mechanism yet, and cross-device/lost-device recovery for passkeys is genuinely less mature in many users' minds than password reset — a forced flag-day is a support and lockout disaster waiting to happen.

How does account lockout in ASP.NET Core Identity work, and what's the trade-off against a denial-of-service risk it introduces? mid

Identity's default lockout tracks failed access attempts per user and, after a configurable threshold, locks the account for a configurable duration (MaxFailedAccessAttempts, DefaultLockoutTimeSpan), returning a failure result distinct from "wrong password" so calling code can show an appropriate message. The trade-off: because lockout is keyed by username/account rather than by source IP, an attacker who knows (or guesses) a set of valid usernames can deliberately lock out legitimate users by repeatedly submitting wrong passwords for their accounts — a self-inflicted denial-of-service the defender's own protection enables. Mitigating this usually means adding IP/rate-based throttling alongside account lockout (so an attacker spraying wrong passwords from one source gets slowed down before enough attempts land to trigger account-level lockout) rather than relying on account lockout as the sole brute-force defense.

Example 
services.Configure<IdentityOptions>(options => {
    options.Lockout.MaxFailedAccessAttempts = 5;
    options.Lockout.DefaultLockoutTimeSpan = TimeSpan.FromMinutes(15);
});

Follow-ups

  • Is CAPTCHA a reasonable complementary control here? — Yes, especially triggered adaptively (after one or two failures) rather than always-on, to slow down scripted attempts without adding friction to every normal login.
  • Does lockout apply to external-login (federated) sign-in the same way? — No — lockout is specifically about local password attempts; a federated sign-in via unit 02's OIDC flow doesn't go through this local failed-attempt counter at all, since the password check happens at the external IdP, not locally.
  • What's a reasonable lockout duration in practice? — Long enough to meaningfully slow a brute-force attempt, short enough that a legitimate user who mistypes a few times isn't locked out for an unreasonable stretch — 15 minutes to an hour is a common range, sometimes with escalating duration on repeated lockouts.

Wrong answer: "Account lockout has no downside, just set the threshold low for maximum security." A low threshold makes the account-lockout-as-DoS-vector problem worse, not better — an attacker needs even fewer attempts to lock a legitimate user out, which is exactly the trade-off this question is testing whether the candidate has thought about.

10 Service-to-service & API security

Once identity crosses from "a human in a browser" to "one backend calling another," the questions shift toward credential types with no user present, audience/scope discipline across many small services, and the specific failure modes a mesh of internal APIs introduces. Screeners get client credentials basics; senior/principal levels get service-to-service authorization design across a whole system.

RFC 6749 §4.4 client credentials grant · App and identity types on the Microsoft identity platform

When would you use the client credentials grant instead of any user-delegated flow? screener

Whenever the caller is a service acting as itself, with no end user in the loop to delegate anything — a nightly batch job, a backend calling another backend's API on its own behalf, a webhook processor. The resulting token represents "this service," not "this service acting for user X," which is exactly wrong for any call whose authorization should depend on a specific user's permissions — that's what OBO (unit 07) or a delegated flow is for instead. Confusing the two produces either an over-broad token (a service token used where user-scoped access was actually needed) or unnecessary complexity (forcing a user through an interactive flow for a job that has no user at all).

Example 
POST /token
grant_type=client_credentials&client_id=nightly-job&client_secret=...&scope=api://orders/.default

Follow-ups

  • Does a client-credentials token expire the same way a user token does? — Yes, standard access-token lifetime rules apply; there's just no refresh token involved since the client can simply request a new token with the same credential whenever needed.
  • What scope conventions does Entra ID use for client-credentials tokens specifically? — The .default scope, which requests whatever application permissions have been statically configured and admin-consented for that app registration, rather than a dynamically negotiated scope list.
  • Is a shared client secret across many services a good idea? — No — each service should have its own registered client and credential, so a compromise or rotation is scoped to one service rather than requiring a coordinated rotation across everything sharing the secret.

Wrong answer: "Client credentials and delegated tokens are interchangeable, just use whichever is easier to wire up." They carry fundamentally different authorization semantics — using a client-credentials (service-identity) token where per-user authorization was actually required silently drops user-level access control, a real security bug, not a style preference.

In a microservices architecture, should service B trust a JWT that service A forwards from the original caller, or should A mint a new token for its call to B? mid

Forwarding the original token unchanged means B is validating a token whose aud was meant for A, not B — either B has to relax audience validation (reopening the token-confusion risk from unit 03) or the forward simply fails validation as designed. The correct pattern is the same one covered in unit 07's OBO discussion generalized beyond Entra ID specifically: A exchanges the incoming token for a new one correctly audienced for B (via OBO where the identity provider supports it, or a service-mesh/gateway-issued internal token carrying the original user's identity as a claim), so B always validates a token actually meant for it. This preserves defense in depth — B's validation logic doesn't have to special-case "sometimes I receive tokens meant for someone else," which is exactly the kind of exception that becomes a vulnerability once forgotten.

Example 
Caller -> A:  Authorization: Bearer {token, aud=A}
A -> B:       Authorization: Bearer {new_token, aud=B, sub=same original user}  — minted via OBO, not forwarded

Follow-ups

  • What if A and B are both fully internal and trust each other completely? — "Fully trust each other" is rarely true in practice once a system has enough services that one gets compromised or misconfigured independently — zero-trust-style internal validation (every hop checks audience properly) contains a compromise to the hop where it happened, rather than letting a forwarded, wrongly-audienced token cascade.
  • Does a service mesh (like a sidecar-based mTLS mesh) change this calculus? — It adds transport-level mutual authentication between services, which is valuable, but it's a different layer from application-level user-identity propagation — you'd still want correctly audienced tokens or claims for "which user is this on behalf of," mesh mTLS or not.
  • Is there a lighter-weight alternative to full OBO for this? — Some internal architectures use a signed "identity assertion" header from a trusted gateway instead of a full OAuth token exchange — simpler to implement, but it shifts trust onto the gateway's signature being verified correctly by every downstream service, a design choice with its own review burden.

Wrong answer: "Just forward the Authorization header as-is between services, it's simpler." Simpler until B either has to weaken its audience check to accept it (a real vulnerability) or an unrelated third service that also happens to accept A's tokens gets reachable using a token that was never meant for it.

How do you rotate a client secret used by dozens of services calling one API, without an outage? senior

The API (or identity provider validating the credential) needs to accept two valid secrets simultaneously during a transition window — register/generate a new secret, roll it out to consuming services incrementally while the old one still validates, then revoke the old one only once telemetry confirms nothing is still using it. Trying to rotate atomically (kill the old secret the instant the new one is issued) assumes every one of the dozens of consumers redeploys in perfect lockstep, which essentially never happens in practice — the overlap window is what actually makes rotation safe rather than a coordinated, fragile flag-day.

Example 
t0: secret_v2 created, added as a valid credential alongside secret_v1
t0..t1: services redeploy with secret_v2, at their own pace
t1: telemetry shows zero requests still using secret_v1
t1+: secret_v1 revoked

Follow-ups

  • How do you know when it's actually safe to revoke the old secret? — Log which credential/key ID each request authenticated with and watch for that count dropping to zero over a representative window (long enough to cover a full deploy cycle for every consumer, including the slowest one) — revoking based on a guess rather than telemetry is how you get a surprise outage from a forgotten consumer.
  • Does this generalize to signing-key rotation for JWTs, from unit 03's JWKS discussion? — Yes — it's the same overlap-window principle: publish the new key in the JWKS alongside the old one, sign new tokens with the new key, and only remove the old key from the JWKS once every already-issued token signed with it has expired.
  • What's the alternative to a shared static secret that avoids this whole problem? — Certificate-based credentials or managed identities, which are typically rotated by the platform automatically without the manual overlap-window choreography a static secret requires.

Wrong answer: "Rotate it by generating the new secret, updating it everywhere, and deleting the old one right after." "Right after" for dozens of independently deployed consumers is never actually simultaneous — this is the exact playbook for a partial outage where whichever services haven't redeployed yet start failing authentication the moment the old secret is deleted.

What's the difference between API keys and OAuth access tokens as an API authentication mechanism, and when is an API key actually the right choice? mid

An API key is a long-lived, opaque, typically non-expiring credential the issuing platform maps back to an account/project — simple to implement and use, but it carries none of OAuth's scoping, expiration, or delegation semantics natively, so those properties (if wanted) have to be built on top by the API provider rather than coming from the mechanism itself. It's a reasonable, even preferable choice for simple machine-to-machine access with a single, coarse-grained trust level (a third-party integration calling a public API with one fixed set of permissions) where OAuth's flow overhead (token endpoints, expiry handling, refresh logic) buys little; it's the wrong choice once you need per-request-scoped, time-limited, or user-delegated access, which is exactly OAuth's design target.

Example 
GET /v1/data
Authorization: Bearer sk_live_51Hcd...   -- an API key, not a signed, expiring OAuth token

Follow-ups

  • Can an API key be revoked? — Yes, but revocation is a manual/administrative action by the issuing platform, not a built-in protocol mechanism the way OAuth token revocation (RFC 7009) is — the platform has to build that capability itself.
  • Is an API key more or less exposed to leakage risk than a bearer token? — Similarly exposed as a bearer credential (same "possession is proof" property discussed in unit 08's sender-constraining question) but typically longer-lived, which raises the stakes of a leak since there's no short expiry naturally limiting the damage.
  • Should an API key ever be put in a URL query string? — No — URLs end up in server logs, browser history, and referrer headers; a header (or a signed request scheme) is the safer transport, same principle as never putting a bearer token in a URL.

Wrong answer: "API keys are just an insecure, outdated version of OAuth tokens, never use them." They're a legitimately simpler mechanism for a legitimately simpler problem — the "wrong" part is only using one where the other's properties (expiry, scoping, delegation) were actually needed, not using an API key at all.

How would you rate-limit an API in a way that's fair across many API-key or client-credential holders, without letting one bad actor degrade service for everyone? senior

Rate limits keyed per credential (per API key, per client ID) rather than a single global limit ensure one caller exhausting its own quota doesn't consume capacity meant for others — the naive global-limit design fails exactly the "one bad actor" scenario the question describes. Beyond that, a tiered design (different limits per plan/trust level) and a token-bucket or sliding-window algorithm (rather than a fixed window, which allows bursting right at window boundaries) gives smoother, more predictable behavior. I'd also make the limit itself visible to the caller (X-RateLimit-Remaining-style headers) so well-behaved clients can self-throttle before hitting a hard 429, and log/alert on sustained near-limit behavior as a signal worth investigating (compromised credential, misbehaving integration) independent of whether it ever actually breaches the limit.

Example 
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0

Follow-ups

  • Where should rate limiting actually be enforced — the app, or a gateway in front of it? — A gateway/API management layer in front of the app is usually preferable, since it protects the app itself from load even from requests that would eventually be rejected, and centralizes the policy rather than duplicating it per service.
  • Does authentication need to happen before rate limiting, or after? — Ideally rate limiting is keyed by the authenticated identity, which means at least a lightweight identity extraction has to happen first — an unauthenticated-tier limit (by IP, coarser and easier to spoof) usually exists as a fallback for calls that haven't authenticated yet.
  • What's the risk of rate-limiting by client-provided identifier instead of a verified one? — A caller could claim a different identifier per request to evade its own limit entirely — the key used for limiting has to be something the caller can't unilaterally change, which is exactly why it should derive from the verified credential, not a client-supplied header.

Wrong answer: "Set one rate limit for the whole API and let the load balancer handle it." A single global limit lets one high-volume or malicious caller consume the entire budget, starving every other legitimate caller — per-credential limiting is what actually delivers the "fair across holders" property the question is asking for.

What's mutual TLS (mTLS), and why would you choose it over a bearer token for service-to-service authentication? senior

In standard TLS, only the server presents a certificate the client verifies; in mTLS, the client also presents a certificate the server verifies, so both ends cryptographically prove their identity as part of establishing the connection itself, before any application-layer request/token is even sent. For service-to-service calls, this gives you transport-level identity that's inherently harder to steal and replay than a bearer token — there's no token sitting in a log or memory dump to copy, since the "credential" is a private key used to establish the TLS handshake, not a value transmitted in a header. The trade-off is operational: certificate issuance, rotation, and revocation infrastructure (a private CA, short-lived cert issuance, distribution to every service) is heavier to build and run than an OAuth token flow, which is why mTLS tends to show up in higher-security internal environments (a service mesh with automated cert rotation) rather than for every general API integration.

Example 
Bearer token: credential transmitted in a header on every request — a copyable secret.
mTLS: credential is a private key used at the TLS handshake — never transmitted, only proven via signature.

Follow-ups

  • Can mTLS and OAuth tokens be combined rather than being an either/or choice? — Yes — this is exactly unit 08's mTLS-based sender-constraining: the access token is bound to the client's TLS certificate, so both the token and the underlying transport identity have to match, combining OAuth's scoping/expiry semantics with mTLS's stronger possession proof.
  • Who typically operates the certificate infrastructure for internal mTLS? — Usually a service mesh's control plane (issuing short-lived certs automatically per workload) rather than a manually managed PKI, which is what makes mTLS operationally tractable at scale in modern internal architectures.
  • Does mTLS eliminate the need for application-layer authorization? — No — it authenticates the calling service's identity at the transport layer; deciding what that authenticated service is allowed to do is still a separate, application-layer authorization decision.

Wrong answer: "mTLS is strictly better than bearer tokens, so always use it." It solves a real problem (credential theft/replay) at a real operational cost (certificate lifecycle infrastructure) — for many service-to-service scenarios a well-managed, short-lived bearer token with sender-constraining is a perfectly adequate, lower-overhead alternative; "strictly better" ignores the trade-off entirely.

Design the service-to-service authentication and authorization model for a system of ~40 internal microservices, some of which also need to call two external partner APIs. principal

Internally, I'd put a service mesh (or at minimum a consistent sidecar/library pattern) in place providing mTLS between every service by default, so transport-level identity is a platform property nobody has to opt into per service — combined with correctly-audienced, short-lived tokens (via OBO where a user-context call is being propagated, client-credentials-style service identity tokens otherwise) for the application-layer authorization decisions the mesh's transport identity alone can't express (what is service X actually allowed to ask service Y to do). For the two external partner APIs, I'd deliberately not extend the internal trust model outward — a dedicated integration service (or a small number of them) holds the external credentials, translates internal service identity/authorization into whatever the partner's API actually expects (their own OAuth client credentials, an API key, whatever they support), and every other internal service goes through that boundary rather than each independently holding a copy of an external partner's credential. This keeps the blast radius of an external-partner credential leak contained to one owning service, and means a partner changing their auth mechanism is a one-place change, not a 40-service migration.

Example 
Internal: mesh-provided mTLS (transport identity) + short-lived, correctly-audienced tokens (app-layer authz).
External: one owning integration service per partner, holding that partner's credential; internal callers never see it directly.

Follow-ups

  • What if a partner's API needs to act on behalf of a specific end user, not just the integration service? — That reintroduces the OBO/delegated-token pattern at the boundary — the integration service would need to obtain a partner-scoped, user-context token (if the partner supports that) rather than always acting as its own generic service identity.
  • Isn't a service mesh a lot of infrastructure to introduce just for internal service auth? — It's a real cost, and for a smaller system a consistent library-level convention (rather than a full mesh) achieves similar properties with less operational overhead — the mesh becomes clearly worth it as the service count and the diversity of languages/frameworks involved both grow, which 40 services is comfortably past the point where I'd default to recommending it.
  • How do you audit "which service called which, doing what, on whose behalf" across this whole system? — Correlated logging keyed by a propagated request/trace ID plus the authenticated service identity and, where relevant, the delegated user identity at each hop — this is exactly the kind of cross-cutting concern that has to be designed in from the start rather than bolted on, since it's what makes unit 15's incident-response work possible after the fact.

Wrong answer: "Give every service that might need it a copy of the partner API credentials, it's simpler than routing through one integration service." That multiplies the number of places an external, hard-to-rotate credential is stored and multiplies the blast radius of any one leak — a single owning boundary service is a standard, deliberate containment pattern, not unnecessary indirection.

11 Session security: CSRF, XSS & cookies

Unit 04 introduced the cookie-vs-bearer trade-off; this unit goes deeper on the two attack classes that actually motivate cookie security configuration — CSRF and XSS — and how ASP.NET Core's own anti-forgery machinery fits in. Screeners need the basic attack shapes; senior/principal levels need to reason about defense in depth when any single control has a gap.

ASP.NET Core anti-request-forgery (CSRF) docs · OWASP CSRF

What is CSRF, concretely — walk through an attack against a cookie-authenticated app with no protection. screener

Cross-Site Request Forgery exploits the fact that a browser automatically attaches a site's cookies to any request to that site, regardless of which page triggered the request. If a user is logged into bank.example (holding a valid session cookie) and then visits an attacker's unrelated page, that page can silently submit a form (or fire a fetch, cookie/CORS rules permitting) to bank.example/transfer?to=attacker&amount=1000 — the browser attaches the legitimate session cookie automatically, and if the bank's server has no CSRF protection, it processes the request as if the real logged-in user had submitted it, because as far as the cookie is concerned, they did.

Example 
<!-- on evil.example, while victim is logged into bank.example -->
<form action="https://bank.example/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="1000">
</form>
<script>document.getElementById('f').submit();</script>

Follow-ups

  • Does this attack work against bearer-token auth the same way? — No — that's the core reason bearer tokens are CSRF-immune by construction (unit 04): the attacker's page has no way to attach a bearer token the victim's JS holds, since it's not automatically sent by the browser the way a cookie is.
  • Does the attacker need to see the response to succeed? — No, and that's what makes CSRF distinct from something like reading cross-origin data — the attack just needs the side effect (the transfer) to happen; the same-origin policy blocking the attacker from reading the response doesn't help here at all.
  • Does a GET-only API have the same risk? — It can, if a GET has side effects (violates HTTP semantics, but happens in practice) — an <img src="..."> tag alone can trigger a GET cross-site with cookies attached, no form or script needed.

Wrong answer: "CSRF means an attacker steals your session cookie." No credential theft happens at all — CSRF rides on a cookie the victim still legitimately holds; the attack is tricking the browser into using it, not obtaining a copy of it.

How does SameSite alone fail to fully solve CSRF, even set to Strict? mid

SameSite=Strict blocks the cookie from being sent on genuinely cross-site requests, closing the classic case above — but it doesn't help against a same-site attack (a vulnerability like an open redirect, or attacker-controlled content hosted on a subdomain of the same site, or content injected via a same-site XSS bug) where the malicious request effectively originates from the "same site" as far as the browser's SameSite check is concerned. It also, notoriously, breaks legitimate top-level cross-site navigation into the app (an email link, a payment-provider redirect back to your site) which is exactly why Lax exists as the practical default rather than Strict for cookies that need to survive a user arriving via an external link. Belt-and-suspenders defenses — an explicit anti-forgery token — remain valuable specifically for the gaps SameSite doesn't cover.

Example 
SameSite=Strict: blocks cross-site POST from evil.example — but a same-site XSS bug can still forge the request from inside the trusted origin itself, where SameSite doesn't apply at all.

Follow-ups

  • Is anti-forgery-token protection then strictly necessary even with SameSite=Strict? — "Strictly necessary" is debatable and often decided per risk tolerance, but defense in depth is the standard recommendation — relying on one browser-enforced attribute alone, with no fallback if a browser has a bug or an edge case in SameSite handling, is a single point of failure for a well-understood attack class.
  • Does an old/misbehaving browser undermine SameSite protection? — Historically yes — some older browser versions had inconsistent or buggy SameSite enforcement; modern evergreen browsers are reliable here now, but it's a reason CSRF tokens remained standard practice through the transition period and haven't fully disappeared.
  • Does SameSite protect against CSRF on subdomains of the same registrable domain? — It depends on the cookie's domain scoping — a cookie set broadly (e.g. Domain=example.com) is sent to every subdomain, so a vulnerability on an unrelated subdomain of the same site is effectively "same-site" from the browser's perspective and isn't stopped by SameSite at all.

Wrong answer: "Setting SameSite=Strict fully replaces the need for anti-forgery tokens." It closes the majority, most common case, but same-site-originating attack vectors (XSS, open redirects, sibling-subdomain compromise) are outside what a same-site check can ever distinguish — it's a strong control, not a complete one.

How does ASP.NET Core's built-in anti-forgery token mechanism work, end to end? mid

The server generates a random token pair on rendering a form-bearing page: one half embedded in the page (a hidden form field or, for AJAX/SPA scenarios, a value the client reads and sends as a custom header), the other half set as a separate cookie. On form submission, the server checks that the submitted token and the cookie's token both match and are both present — a cross-site attacker can trigger the victim's browser to send the cookie automatically (that's the whole CSRF problem), but has no way to read the page they didn't load and therefore no way to know the value that needs to accompany it in the form field/header, which is the entire point: the attack can forge the cookie's automatic delivery, but not the paired value the attacker never saw.

Example 
// Razor Pages/MVC: automatic via tag helpers
<form asp-action="Transfer" method="post"> @* anti-forgery hidden field auto-injected *@
// For an SPA/API calling back: [ValidateAntiForgeryToken] + client reads the cookie value and sends it as a header
services.AddAntiforgery(o => o.HeaderName = "X-CSRF-TOKEN");

Follow-ups

  • Why does the value need to be in two places (a cookie AND a form field/header), rather than just a form field alone? — The "double submit" pattern with a cookie lets the server validate without needing server-side session state to remember what token it issued — matching the cookie against the submitted value is enough, avoiding a server-side token store.
  • Does this protect a JSON API the same way it protects a rendered HTML form? — Yes in principle, but the client has to explicitly read the anti-forgery cookie's value and attach it as a header on every mutating request — this doesn't happen automatically the way form-field injection does for server-rendered pages, so SPA integrations need to wire it up deliberately.
  • Is a bearer-token-authenticated API endpoint expected to also use anti-forgery tokens? — No — CSRF protection is specifically for cookie-authenticated endpoints; a pure bearer-token endpoint isn't exposed to CSRF in the first place, per the earlier follow-up, so applying anti-forgery there is unnecessary overhead.

Wrong answer: "The anti-forgery cookie itself is the CSRF protection." The cookie alone is exactly as automatically-sent as the session cookie and offers no protection by itself — the protection comes specifically from requiring a second value the attacker can't have seen, submitted alongside it and checked for a match.

What is XSS, and why does even a "just" reflected/stored XSS bug undermine cookie-based session security specifically? screener

Cross-Site Scripting is attacker-controlled script running in the context of your own origin — via unescaped user input reflected back into a page, or stored and later rendered to other users. Once attacker script executes on your origin, it runs with the same privileges any legitimate script on that page has: it can read document.cookie (unless the session cookie is HttpOnly, which specifically blocks this one avenue), make authenticated requests using the ambient session (cookies are attached automatically regardless of which script triggered the request, same-origin or not), and read/manipulate the DOM including anything a legitimate script could see. HttpOnly closes the "read the cookie value directly" path, but it does nothing to stop the script from just making an authenticated request itself using the cookie that's still automatically attached — XSS inside your own origin sidesteps CSRF's cross-origin premise entirely, since the malicious code isn't cross-origin at all.

Example 
// injected via an unescaped user-supplied field rendered into the page
fetch('/api/transfer', { method: 'POST', body: JSON.stringify({to:'attacker', amount:1000}) });
// runs same-origin, cookie attaches automatically, HttpOnly doesn't block THIS — only blocks reading document.cookie directly

Follow-ups

  • Does this mean HttpOnly is pointless against XSS? — Not pointless — it still stops the specific, very common pattern of exfiltrating the raw cookie value to an attacker-controlled server for reuse elsewhere or later; it just doesn't stop same-origin, same-session abuse happening live, in the moment, from within the compromised page.
  • Is a bearer token in localStorage strictly worse here than an HttpOnly cookie? — Against XSS specifically, yes — localStorage has no HttpOnly-equivalent protection at all, so XSS can both read and exfiltrate a bearer token trivially, whereas an HttpOnly cookie at least survives the "read and take away for later" variant of the attack even though it doesn't survive the "abuse live in the moment" variant.
  • What's the actual best defense against XSS itself, rather than mitigating its blast radius? — Output encoding/escaping everywhere user content is rendered (the framework's default Razor encoding, or React's default JSX escaping, both on by default for good reason) plus a strict Content-Security-Policy as defense in depth — preventing the injection in the first place beats mitigating what an XSS bug can do once it exists.

Wrong answer: "As long as cookies are HttpOnly, XSS can't do anything session-related." It closes one specific exfiltration path but leaves same-origin, in-session request forgery — the browser still attaches the cookie automatically to any request the injected script makes, HttpOnly or not.

What is Content-Security-Policy, and how does it help against XSS specifically? mid

CSP is a response header that tells the browser which sources of script, style, and other resources are allowed to execute/load on the page — a well-configured script-src that excludes 'unsafe-inline' means even a successful injection of <script>evil()</script> into the page simply won't execute, because inline scripts aren't on the allow-list. It's a defense-in-depth layer specifically for the case where an XSS injection point exists despite output encoding (a missed edge case, a third-party widget, a template engine quirk) — CSP doesn't prevent the injection, it prevents the injected content from actually running.

Example 
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdnjs.cloudflare.com; object-src 'none'

Follow-ups

  • Why is 'unsafe-inline' specifically dangerous to allow in script-src? — It's exactly the mechanism most reflected/stored XSS payloads rely on — an inline <script> tag or an inline event handler; allowing it defeats most of CSP's practical protection against the most common injection shape.
  • How do you use inline scripts safely under a strict CSP, if you need any? — Nonces or hashes — the server generates a per-response random nonce, includes it both in the CSP header and as an attribute on the specific inline scripts it actually intends to allow, so an attacker-injected script (lacking the correct, unguessable nonce) still doesn't execute.
  • Does CSP protect against CSRF too? — Not directly — it's an XSS/resource-loading control; frame-ancestors (CSP's clickjacking-related directive) is the closest CSP gets to a CSRF-adjacent protection, and even that addresses a different attack (clickjacking) than CSRF proper.

Wrong answer: "CSP stops XSS injections from happening." It doesn't stop the injection into the page's HTML/DOM at all — it stops the browser from executing disallowed content once it's there, which is a meaningfully different, narrower, but still valuable guarantee.

Your SPA needs to call a third-party analytics or payment widget's script, hosted on their CDN. How does that interact with your CSRF and CSP posture? senior

The third-party script needs an explicit script-src allowance for its exact origin, which is itself a trust decision — that script now runs with the same page-level privileges as your own code, including the ability to read the DOM and make same-origin requests, so a compromise of that third party's CDN-hosted script is effectively an XSS vector against your own app regardless of how tight your own code's CSP discipline is. Subresource Integrity (integrity="sha384-..." on the script tag) mitigates this specifically for the "CDN serves a tampered file" case, by having the browser refuse to execute the script if its hash doesn't match what you pinned — it doesn't help if the legitimate, correctly-hashed script itself is malicious from the start, only against it being swapped out later. On the CSRF side, a third-party widget generally doesn't change your cookie posture directly, but if it makes its own authenticated calls back to your API using your session cookie, you'd want to review exactly what it's calling and whether that's an intended, reviewed integration rather than an assumed-safe black box.

Example 
<script src="https://partner-cdn.example/widget.js"
        integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
        crossorigin="anonymous"></script>

Follow-ups

  • Does adding integrity mean you no longer need to trust the third party's code review practices? — No — it only protects against the file changing after you pinned its hash; you're still fully trusting whatever that specific, hash-verified script actually does the day you pinned it.
  • What happens if the third party updates their script and you haven't updated your pinned hash? — The browser refuses to execute it (a hash mismatch), which fails safe but also breaks the integration until you update the pin — a real operational cost of SRI that teams sometimes underweight when adopting it.
  • Is there a safer alternative to loading arbitrary third-party script directly on your page at all? — A sandboxed iframe for the widget, if the integration supports it, contains the third party's script to its own origin/context rather than granting it full access to your page's DOM and cookies — a meaningfully stronger isolation boundary than CSP allow-listing alone.

Wrong answer: "As long as it's in the CSP allow-list, a third-party script is safe to include." Allow-listing only says the browser will load and run it — it says nothing about what that script actually does once running, which is a full-trust decision, not a security control in itself.

Design the cookie, CSRF, and CSP posture for a new SPA + API product from scratch — what do you set, and in what order do you reason about it? principal

I'd start from the BFF decision (unit 04): if the SPA is served and API-proxied through a backend that holds the actual OAuth tokens, the browser only ever needs an HttpOnly, Secure, SameSite=Lax (or Strict if no external-link entry points exist) session cookie — that single decision eliminates the bearer-token-in-JS-reachable-storage risk entirely, before any CSRF/CSP tuning even starts. On top of that cookie, I'd add anti-forgery token validation on every mutating (non-GET) endpoint as defense in depth against the SameSite gaps discussed above, propagated to the SPA via a header the BFF's own JS reads from a non-HttpOnly companion value (mirroring ASP.NET Core's own double-submit pattern). Then a strict CSP with no 'unsafe-inline', nonce-based allowances for any inline script the build process actually needs, and an explicit, reviewed allow-list for every third-party script origin — treating each addition to that allow-list as a real trust decision, not a rubber stamp. I'd sequence it exactly in that order — architecture decision first, then defense-in-depth layers — because getting the BFF/cookie architecture right removes an entire class of risk that no amount of CSRF-token or CSP tuning downstream can fully compensate for if the underlying design still exposes a bearer token to JS.

Example 
1. BFF holds tokens; browser gets HttpOnly/Secure/SameSite=Lax session cookie only.
2. Anti-forgery token (double-submit) required on every state-changing request.
3. Strict CSP: no unsafe-inline, nonces for necessary inline script, explicit third-party allow-list with SRI.

Follow-ups

  • What would you cut first under a real deadline, if forced to ship with less? — Not the BFF/cookie architecture decision — that's structural and expensive to retrofit later; CSP strictness is the more realistic thing to phase in incrementally (start with report-only mode, tighten over successive releases) without leaving a structural gap in the meantime.
  • How would you verify this posture actually holds once shipped, not just on paper? — Automated header/cookie-attribute assertions in the deployment pipeline (a test that fails the build if Secure/HttpOnly/CSP headers regress), plus periodic scanning (a tool checking for missing security headers) rather than relying on the initial design surviving unreviewed over time as the app evolves.
  • Does this design change at all for a native mobile client added later alongside the SPA? — The mobile client doesn't have cookies/CSRF/CSP concerns at all in the same way — it would use OAuth bearer tokens directly per unit 04's mobile-app discussion, entirely separate from the SPA's BFF-fronted cookie session; the two client types genuinely need different postures, not one unified scheme stretched across both.

Wrong answer: "Add CSRF tokens and a CSP, that covers session security." Both are real, valuable layers, but treating them as the starting point rather than the BFF/cookie-vs-bearer architecture decision misses the layer that actually determines how much any of this even matters — a bearer token exposed to JS undermines the whole picture regardless of how well-tuned the CSRF/CSP layers on top of it are.

12 Authorization architecture at scale

This unit zooms out from ASP.NET Core's specific requirement/handler engine (unit 06) to the broader architectural question every growing system eventually faces: where does authorization logic live, how is it kept consistent across many services, and when does a centralized policy engine earn its cost. Mostly senior/principal territory.

Open Policy Agent documentation · OpenFGA documentation

What's the difference between RBAC, ABAC, and ReBAC as authorization models, and what's each actually good at? mid

Role-based access control (RBAC) grants permissions to roles and assigns users to roles — simple to reason about and audit, but coarse: it struggles to express "this specific resource" without exploding into a role per resource. Attribute-based access control (ABAC) evaluates a policy against arbitrary attributes of the user, resource, and context (department, resource sensitivity, time of day, request IP) — far more expressive, at the cost of policies becoming harder to enumerate and audit ("what can Alice actually do" requires evaluating logic, not just reading a role list). Relationship-based access control (ReBAC) — the model behind Google Zanzibar and tools like OpenFGA — expresses permissions as graph relationships ("Alice is an editor of Document 7, which is inside Folder 3, which Bob owns") and resolves access by traversing that graph, which is the natural fit for deeply nested, ownership/sharing-heavy resource hierarchies (a Google-Drive-style product) that RBAC and even ABAC handle awkwardly.

Example 
RBAC:  user -> role -> permission               ("Alice is an Admin, Admins can edit orders")
ABAC:  policy(user.dept, resource.owner, time)   ("allow if user.dept == resource.dept AND business hours")
ReBAC: user --relation--> object --relation--> object   ("Alice is editor of Doc7; Doc7 is in Folder3")

Follow-ups

  • Can these be combined in one system rather than picking exactly one? — Commonly yes — a system might use RBAC for coarse, app-wide permissions (who can access the admin panel at all) and ReBAC or resource-based checks (unit 06) for fine-grained, per-resource decisions layered on top.
  • Which model is easiest to audit for compliance purposes? — RBAC, generally — "list every user with the Admin role" is a simple query; ABAC and ReBAC require evaluating logic or traversing a graph to answer the same "who can do X" question, which is a real cost worth naming when compliance/audit requirements are a driving concern.
  • Is ReBAC just a fancier name for resource-based authorization from unit 06? — Related but broader — unit 06's resource-based authorization is about checking a specific resource at the point of use; ReBAC is a full modeling approach for representing an entire graph of relationships as the source of truth for what resource-based checks evaluate against.

Wrong answer: "ReBAC is strictly more advanced, so it's always the better choice." It's the better fit for a specific shape of problem (deep resource hierarchies with sharing/inheritance) — for a system whose authorization is genuinely just "which role can do which action," introducing a relationship graph is unnecessary complexity, not an upgrade.

What is a centralized policy engine (like OPA), and what problem does it solve that scattering authorization checks through each service's code doesn't? senior

When every service implements its own authorization logic inline, keeping the rules consistent across services (does "Manager" mean the same permissions in the billing service as in the orders service) becomes a coordination problem with no single source of truth, and auditing "what can this role actually do across the whole system" means reading code in every service. A policy engine like Open Policy Agent centralizes policy definition (in a dedicated policy language, Rego for OPA) while still letting each service make its own fast, local decision — services query the engine (often via a local sidecar to avoid a network round trip on every check) with a structured question ("can user U do action A on resource R") and get a decision back, decoupling "what the rule is" from "which service is asking."

Example 
package authz
default allow = false
allow { input.user.role == "OrderManager"; input.action == "edit"; input.resource.type == "order" }

Follow-ups

  • Does using OPA mean giving up unit 06's in-process ASP.NET Core authorization handlers entirely? — Not necessarily — a handler can be the integration point that calls out to OPA for the actual decision, keeping the ASP.NET Core-native [Authorize]/requirement plumbing while delegating the rule evaluation itself to the centralized engine.
  • What's the latency cost of a centralized policy check per request? — Minimal if deployed as a local sidecar (the common pattern) evaluating policy in-process on the same host rather than a true network call to a shared remote service — a remote, shared policy service reintroduces exactly the latency/availability coupling the sidecar pattern avoids.
  • How do policy changes get rolled out without redeploying every service? — Policies are typically pushed/pulled independently of service deployments (a bundle distribution mechanism), which is one of the main operational payoffs — a permission rule change ships without touching application code at all.

Wrong answer: "A policy engine replaces the need for any authorization logic in your services." Services still need to gather the right inputs (who's asking, what resource, what action) and enforce the returned decision — the engine centralizes the rule evaluation, not the entire responsibility of calling it correctly at every enforcement point.

What's the difference between "coarse-grained" authorization at the API gateway and "fine-grained" authorization inside the service? Do you need both? senior

A gateway can cheaply reject requests that are obviously unauthorized before they consume any backend resources — "does this token have a valid scope for this API at all," "is this client rate-limited," "is this endpoint even allowed for this client type" — decisions that don't require loading any specific resource. Fine-grained checks — "can this specific user edit this specific order" — need the actual resource loaded and can only happen inside the service that owns that data; a gateway generally can't (and shouldn't be architected to) make that call, since it would need to replicate or query every service's data model just to gate a request. Both layers earn their keep: the gateway sheds obviously-invalid traffic cheaply and consistently across every service, while fine-grained checks stay where the actual data and business rules live.

Example 
Gateway: reject if token missing "orders:write" scope — cheap, no data lookup needed.
Service: reject if token has "orders:write" scope but this order belongs to a different tenant — needs the loaded resource.

Follow-ups

  • Is it safe to skip the service-level check if the gateway already validated the scope? — No — that's exactly the trap of relying on one layer alone; the gateway's coarse check doesn't know which specific order is being requested, so the "is this the caller's own resource" decision has to happen somewhere, and only the service has the data to make it.
  • Does putting the coarse check at the gateway create a single point of failure? — It's a single point of enforcement for the coarse layer, which is a deliberate trade — a gateway outage generally fails closed (no traffic gets through at all) rather than silently skipping the check, so it's not usually the riskier kind of single point of failure.
  • How does this map onto zero-trust thinking? — Zero trust explicitly argues against relying on the gateway/perimeter check alone — every service should re-verify what it needs regardless of what already passed upstream, which is exactly the "don't skip the service-level check" answer above generalized into a stated principle.

Wrong answer: "Put all authorization logic at the gateway so services don't have to worry about it." The gateway structurally can't make resource-specific decisions without the resource's data, which lives in the service — pushing everything there either doesn't work or forces the gateway to duplicate every service's data access, defeating the whole point of the layering.

How do you keep authorization policy consistent across a system where some checks live in ASP.NET Core policies, some in a database row-level security feature, and some in frontend UI logic hiding buttons? senior

The frontend hiding a button is a UX affordance, never a security boundary — it has to be treated as advisory, with the actual enforcement living server-side (in the API's authorization layer and/or the database), and I'd flag any design where the frontend check is the only check as an outright gap, not a style choice. Between the API-layer policy and database row-level security, the real risk is drift: if both independently encode "which rows can this user see," they can silently diverge as one gets updated and the other doesn't — I'd pick one as the source of truth for a given rule (commonly the database RLS for raw data access, with the API layer's policy checks covering business-level actions that aren't just "can you see this row") and be explicit in documentation/code about which layer owns which class of decision, rather than letting both grow independently and hoping they stay in sync.

Example 
-- Database RLS as the source of truth for row visibility:
CREATE POLICY tenant_isolation ON orders USING (tenant_id = current_setting('app.tenant_id')::uuid);
-- API-layer policy handles business actions (e.g. "can approve," not just "can see"), not duplicate row filtering.

Follow-ups

  • Is duplicating a check across two layers ever the right call, rather than picking one owner? — Yes, deliberately, for defense in depth on the highest-stakes checks — the goal isn't zero duplication everywhere, it's knowing which checks are intentionally duplicated as a safety net versus which are accidentally duplicated and drifting apart unnoticed.
  • How would you catch drift between the two layers in practice? — Integration tests that assert the same access decision from both layers for a representative set of scenarios, and periodic manual audits comparing what a role/user can actually do against what the documentation claims — this is genuinely hard to fully automate, worth naming as an honest limitation.
  • What's a concrete failure mode of over-trusting frontend-only checks? — A user opens dev tools, calls the API endpoint directly (bypassing the UI entirely) that a hidden button was "protecting," and the request succeeds because no server-side check was actually enforcing it — an extremely common real-world finding in security reviews.

Wrong answer: "As long as the button is hidden in the UI, unauthorized users can't reach that action." Hiding a UI element controls nothing about what the API accepts — any client capable of issuing an HTTP request bypasses this entirely, which is why frontend checks are UX, not security.

What is Zanzibar-style authorization, and why did Google build a dedicated system for it rather than using per-service checks? senior

Zanzibar (Google's globally-consistent authorization system, publicly described in a 2019 paper and the model behind the open-source OpenFGA/Ory Keto family) exists to answer relationship-graph authorization questions ("can user U view document D," where D's visibility depends on chains of sharing/ownership/group-membership relationships) at massive scale, with strong consistency guarantees (a permission revoked must be respected by the very next check, everywhere, not eventually) and low latency for every single content-access check across Google's entire product surface. Building this centrally, rather than per-service, let every product (Drive, Calendar, Photos) reuse one correctly-built, heavily-tested relationship-authorization engine instead of each reinventing sharing/permission graph logic independently — and, critically, gave them one place to get the hard distributed-systems problem (consistent reads of recently-changed permissions across a globally distributed system) right once.

Example 
check(user: alice, permission: view, object: doc:7)
-- resolves by traversing: alice --editor--> doc:7 OR alice --member--> group:eng --viewer--> doc:7

Follow-ups

  • What does "new enemy problem" mean in this context? — The specific consistency failure Zanzibar guards against: if Alice removes Bob's access to a document, and Bob is (unknown to Alice) still able to read it for even a moment due to eventual-consistency lag, that's a security-relevant staleness window Zanzibar's consistency model is specifically designed to close — an unusually strong requirement compared to most systems' tolerance for eventual consistency elsewhere.
  • Is OpenFGA/Ory Keto a drop-in replacement for ASP.NET Core's authorization handlers? — No — they solve the relationship-graph modeling and evaluation problem specifically; you'd still typically call them from within a custom AuthorizationHandler (unit 06) as the thing that actually resolves whether a requirement succeeds, rather than replacing the ASP.NET Core authorization pipeline wholesale.
  • When is adopting a ReBAC system like this actually justified for a smaller company? — When the product's core value is genuinely a deep sharing/permission graph (a document collaboration tool, a project-management app with nested workspaces) — for a simpler app where RBAC or straightforward resource-owner checks suffice, the operational cost of running a dedicated relationship-authorization system usually isn't justified.

Wrong answer: "Zanzibar is just Google's internal name for role-based access control." It's a fundamentally different model (relationship graph traversal with strong consistency guarantees), purpose-built for a class of sharing/permission problems RBAC has no natural way to express at all.

Design the authorization architecture for a project-management SaaS scaling from one team's tool to an enterprise product with nested workspaces, folders, and per-item sharing. What changes as it grows? principal

Early on, a straightforward RBAC-plus-resource-owner-check model (unit 06's project-role design) is genuinely the right level of complexity — building a relationship-graph authorization engine for a single team's tool before there's real nesting/sharing depth is premature. The inflection point is when the product's actual feature set grows real hierarchy and sharing (a workspace contains folders, folders contain items, an item can be individually shared to someone outside its folder's normal access, permissions should cascade down the hierarchy unless explicitly overridden) — at that point, encoding "can Alice view Item 42" as ad hoc joins across workspace/folder/share tables starts breaking down exactly the way generic SQL struggles with arbitrary-depth graph traversal, and that's the signal to introduce a dedicated ReBAC model (self-hosted OpenFGA, or an equivalent) rather than continuing to patch the relational approach. I'd migrate incrementally — model the relationship graph in the new system while the legacy checks stay authoritative, dual-run and compare decisions in production without enforcing the new system's answer yet, and only cut over once the comparison shows sustained agreement — the same overlap-window discipline as the credential-rotation pattern from unit 10, applied to an authorization-model migration instead of a secret.

Example 
Stage 1 (single team): RBAC + owner check, plain SQL joins — adequate, simple.
Stage 2 (nested workspaces, per-item sharing, cascading overrides): ReBAC engine (OpenFGA-style) becomes justified.
Migration: dual-run new model against legacy decisions in production before cutting over enforcement.

Follow-ups

  • How do you decide the inflection point isn't premature optimization? — Concretely, when the relational authorization queries start requiring recursive CTEs or an unbounded number of joins to answer "can this user see this item," or when a real customer-reported bug traces back to permission-inheritance logic that the current model can't express cleanly — actual pain, not a hypothetical future need, is the trigger.
  • What's the audit/compliance story once you're on a ReBAC model? — Harder to answer "list everyone who can see document X" from raw relationship tuples alone at scale — most ReBAC systems provide (or need to be paired with) a "list objects/list users" reverse-query capability specifically because forward checks and audit-style enumeration are different query shapes with different performance characteristics.
  • Does the API-layer/gateway split from earlier in this unit still apply once ReBAC is introduced? — Yes — the gateway's coarse checks stay coarse (valid scope, valid client); the ReBAC engine becomes the fine-grained decision-maker the service calls into, replacing what used to be ad hoc resource-owner SQL checks, not replacing the layering itself.

Wrong answer: "Start with a full relationship-graph authorization engine from day one so you never have to migrate later." Introducing that complexity before the product actually has the sharing/nesting depth to justify it is its own real cost — in engineering effort, operational surface, and slower iteration on a still-evolving data model — premature architecture is a genuine mistake, not free future-proofing.

13 Multi-tenancy, B2B & B2C identity

SaaS products almost always have to answer "how do tenants map to identity" — a question that touches token design, federation, and provisioning all at once. This unit is mostly senior/principal territory, extending the multi-tenant Entra ID model from unit 07 to the vendor-agnostic version of the same questions.

Microsoft Entra External ID for customers (CIAM) · SCIM core schema (RFC 7643)

What's the difference between a B2B and a B2C identity model, and why do they usually need genuinely different infrastructure? mid

B2B identity is about letting organizations (each with their own existing identity provider — their own Entra ID/Okta/Google Workspace tenant) federate into your app, so their employees sign in with credentials their own IT department already manages — the core problem is federation and per-organization policy (which IdP, which claims mapping, which access rules), and the user base is bounded and known. B2C identity is about a large, self-service, often anonymous-until-registration user base with no existing organizational IdP behind most of them — the core problems are self-service sign-up flows, social login aggregation (Google/Facebook/Apple sign-in), scale (millions of users), and much lighter-weight per-user administration. Trying to serve both with one identity model tends to strain in different directions: B2B needs strong per-tenant federation/admin controls that B2C's self-service model doesn't need at all, while B2C needs sign-up/social-login/scale machinery that a B2B-federation-only system wasn't built for.

Example 
B2B: "Acme Corp's employees sign in via Acme's own Entra ID tenant, federated into our app."
B2C: "Anyone can self-register with an email or their Google account, no organizational IdP involved."

Follow-ups

  • Can a single product need both models at once? — Yes, commonly — an enterprise-tier product might offer B2B SSO for large customers while individual/small-team signups go through a B2C-style self-service path, which is exactly why platforms like Entra External ID offer distinct B2B and CIAM (B2C) product lines rather than one undifferentiated offering.
  • What's the licensing/cost difference typically like between the two? — B2C-style consumer identity platforms are typically priced per monthly active user at a much lower per-user rate than B2B/workforce identity, reflecting the very different usage and support cost profiles of the two populations.
  • Does B2B ever involve self-service sign-up too? — Sometimes, for smaller B2B customers without their own IdP — a lightweight local-account fallback alongside federation, which starts to blur into B2C-style mechanics for that segment specifically.

Wrong answer: "B2B and B2C are just marketing terms, the underlying identity mechanics are the same." The federation-vs-self-service distinction drives genuinely different infrastructure requirements (per-tenant IdP configuration vs. social-login/sign-up flows and scale) — treating them as interchangeable misses why platforms build separate product lines for each.

How do you determine which tenant an incoming request belongs to, and where does that decision get made in the request pipeline? senior

Common approaches: a claim in the access token itself (a tid/tenant_id claim set at token-issuance time, the most reliable source once a token exists), a subdomain (acme.myapp.com) resolved before authentication even happens, or a header/path segment the client includes explicitly. The right answer depends on when tenant identity needs to be known — subdomain resolution can happen at the routing layer before any auth check, which is useful if the tenant determines which identity provider to challenge with (a subdomain-per-tenant B2B setup routing to that tenant's own federated IdP); a token claim is authoritative but only available after authentication, so it can't drive an unauthenticated request's routing decision. Mixing the two carelessly is a real bug source — trusting a client-supplied header or path segment for tenant identity without cross-checking it against the authenticated token's own tenant claim lets a caller potentially claim to be a different tenant than the one their token actually belongs to.

Example 
Pre-auth (routing which IdP to challenge): subdomain acme.myapp.com -> resolve to Acme's tenant config
Post-auth (authoritative, for every data-access decision): token's tid claim, never trust a client-supplied tenant header alone

Follow-ups

  • What's the concrete risk of trusting a client-supplied tenant header? — A malicious or buggy client could send a different tenant ID than the one their actual token belongs to, and if the backend uses that header (rather than the verified token claim) for data scoping, it's a direct path to cross-tenant data access — exactly the isolation failure a multi-tenant system most needs to avoid.
  • Does every request need explicit tenant resolution, or can it be inferred entirely from the token? — Once authenticated, the token's own tenant claim should be the single source of truth for every subsequent data-scoping decision in that request — any earlier subdomain/header-based resolution was only ever a hint for routing to the right challenge, not a fact to keep trusting afterward.
  • How does this interact with the row-level-security discussion from unit 12? — The verified tenant claim is exactly what should feed the database session variable/context an RLS policy checks against — the same "don't trust a client-supplied value for a security-critical scoping decision" principle applies at the database layer too.

Wrong answer: "Just read the tenant ID from a request header the client sends, it's simpler than parsing claims." That's exactly the cross-tenant data leakage risk above — a header is client-supplied and unverified; the token's tenant claim is cryptographically backed by the issuer and is what data-scoping decisions must actually rely on.

What is SCIM, and what problem does it solve for a B2B SaaS product's enterprise customers? senior

SCIM (System for Cross-domain Identity Management) is a standard protocol and schema for automating user/group provisioning and deprovisioning between an identity provider (the customer's Entra ID/Okta tenant) and your app — when an employee joins, is renamed, changes role, or (critically) is offboarded in the customer's own IdP, SCIM pushes that change to your app automatically via a defined REST API, rather than relying on the customer's IT admin to separately, manually remember to also deactivate that user in every third-party SaaS product they use. For enterprise customers, automated deprovisioning specifically is often a hard security/compliance requirement — "an offboarded employee must lose access to all systems within N hours" is much harder to guarantee across dozens of SaaS vendors without SCIM (or an equivalent) than with it.

Example 
PATCH /scim/v2/Users/2819c223
{ "Operations": [{ "op": "replace", "path": "active", "value": false }] }
-- pushed automatically by the customer's IdP the moment the employee is deactivated there

Follow-ups

  • Does SCIM replace the OIDC/SAML federation flow discussed for B2B sign-in? — No — they're complementary: federation (OIDC/SAML) handles the live sign-in moment, SCIM handles the out-of-band lifecycle (provisioning, attribute updates, deprovisioning) that needs to happen independent of whether that user ever actually signs in again.
  • What happens if a customer relies only on federation (SSO) and never sets up SCIM? — An offboarded employee typically loses the ability to complete a new sign-in once their account is disabled at the IdP (since SSO re-checks with the IdP), but any already-established session/token for that user may persist until it naturally expires or is otherwise revoked — SCIM's proactive deprovisioning closes that gap faster and more explicitly than relying on SSO's federation check alone.
  • Is implementing SCIM support a common enterprise-sales requirement? — Yes, frequently listed explicitly in enterprise procurement/security-questionnaire checklists — for a B2B SaaS product targeting larger customers, SCIM support is often a genuine deal-blocking feature gap if missing, not a nice-to-have.

Wrong answer: "SSO already handles offboarding, since the user can't sign in once their account is disabled at the IdP." SSO blocks new sign-ins going forward, but doesn't retroactively revoke already-issued sessions/tokens, and doesn't clean up any account state (roles, group memberships) your app is independently tracking — SCIM's explicit provisioning events are what closes both of those gaps.

A B2C product wants to let users sign in with Google, Apple, or a local email/password account, and later "link" a social login to an existing local account. What are the identity-design challenges here? senior

The core challenge is that "who is this user" now has multiple possible answers depending on which method they used this time, and the product has to define a canonical user identity that all of those methods resolve to, rather than accidentally creating a second account when someone who registered with email/password later tries "Sign in with Google" using the same email address. Matching by email alone is a common but risky shortcut — email addresses can be unverified at the IdP, reused, or later changed, so a naive "if the email matches, it's the same person" auto-link can be exploited (register with victim's email locally before they ever use social login, then legitimate Google sign-in with that same email either fails confusingly or, worse, gets auto-merged into the attacker's pre-created account). A safer pattern: only offer to link accounts when the user is already authenticated on one side and explicitly confirms the link (e.g., logged in locally, then choosing "connect your Google account" from account settings) rather than silently auto-merging based on a matching but unverified email claim at sign-in time.

Example 
Risky: sign in with Google, email matches an existing local account -> auto-merge without confirmation.
Safer: sign in with Google, email matches an existing local account -> prompt "an account with this email exists,
       sign in with your password first, then link Google from account settings" (or verify via email confirmation link).

Follow-ups

  • Why can't you just always trust the social provider's email claim as verified? — Most major providers do mark email as verified in their claims when it genuinely is, but the app still shouldn't treat "email matches" alone as sufficient proof of "same person, safe to silently merge accounts" given the pre-registration attack above — verification of the email and authorization to merge accounts are two different questions.
  • What data model represents "one user, multiple linked login methods"? — A canonical user record with a separate table of linked external identities (provider name + provider's subject id, unique per provider), rather than trying to cram multiple providers' identifiers onto a single flat user row — this is exactly the shape ASP.NET Core Identity's AddLogin/external-login-store design uses.
  • What happens if a user unlinks their only remaining sign-in method? — The product needs to prevent a user from removing their last usable sign-in method (or force setting a password first) — a real edge case worth testing explicitly, since it's an easy way for a user to accidentally lock themselves out entirely.

Wrong answer: "If the email matches, just merge the accounts automatically, it's what the user obviously wants." That's exactly the pre-registration account-takeover vector described above — convenience at sign-in time versus a genuine, exploitable security gap; the safer pattern requires an explicit, authenticated linking step rather than an implicit match-and-merge.

Design the identity architecture for a B2B SaaS product where some customers want SSO via their own Entra ID/Okta tenant, and others (smaller customers with no IdP) just want email/password. principal

I'd treat this as a policy scheme decision generalized to the multi-provider case (the same shape as unit 05's cookie-plus-bearer policy scheme, applied one level up): per-tenant configuration determines which authentication method(s) that tenant's users are routed through, resolved before challenge — a subdomain or email-domain lookup identifies the tenant, whose configuration says "federate to this SAML/OIDC endpoint" or "use local email/password" (or both, if the tenant wants a fallback). Critically, I would not let a self-registered local account and a federated-tenant account for the same email silently coexist without a clear rule — once a customer turns on SSO, I'd generally want new sign-ins for that tenant's domain forced through federation, with existing local accounts explicitly migrated/linked during onboarding rather than left as an ambiguous parallel path an attacker (or a confused user) could exploit, echoing the account-linking risk from the B2C question above. I'd also keep the tenant-level SSO configuration itself behind a real admin approval flow (only an authenticated tenant admin can configure or change their own tenant's federation settings) since misconfigured or maliciously-configured federation is a direct path to impersonating any user in that tenant.

Example 
Tenant config: { tenantId: "acme", authMethod: "saml-sso", idpMetadataUrl: "...", fallbackLocalAuth: false }
Tenant config: { tenantId: "smallco", authMethod: "local", fallbackLocalAuth: true }

Follow-ups

  • What happens when a customer wants to migrate from local accounts to SSO after already onboarding? — A defined migration flow — notify existing local-account users, require them to link/verify via the new SSO before a cutover date, then disable local auth for that tenant's domain — rather than an instant flag flip that locks out users who haven't linked yet.
  • Who resolves which tenant an unauthenticated sign-in attempt belongs to, before any credential is checked? — Typically an email-domain lookup ("this email's domain belongs to tenant Acme, redirect to Acme's configured IdP") or a tenant-specific subdomain/login URL — the same pre-auth tenant-resolution problem discussed earlier in this unit, now driving which challenge to issue rather than just data scoping.
  • Does this design need to prevent a user typing an email at the wrong tenant's login page? — Yes ideally — resolving tenant from the email/domain before presenting a password field (rather than a generic email+password form regardless of tenant) avoids leaking which auth method a given domain uses and avoids the confusing failure of typing a password where the tenant actually expects SSO.

Wrong answer: "Just support both SSO and local password login for every account, and let users pick whichever they want at sign-in." Leaving both paths open unconditionally per account is exactly the ambiguous-coexistence risk called out above — once a tenant has SSO, an unmanaged parallel local-password path for the same users is an access-control gap their IT department didn't sign up for and can't govern.

14 Federation & legacy protocols

OIDC/OAuth dominate new work, but SAML and older federation patterns are still very much alive in enterprise environments, and knowing where they show up (and why they haven't been fully displaced) is a mark of someone who has worked on real integration projects rather than only greenfield apps.

SAML 2.0 Core specification · Microsoft identity platform and SAML SSO

What's the high-level difference between SAML and OIDC, and why is SAML still around in enterprise environments in 2026? mid

Both solve federated single sign-on, but SAML is XML-based, older (originating in the early 2000s), and built around a browser-redirect exchange of signed XML assertions between an identity provider and service provider; OIDC is JSON/REST-based, layered on OAuth 2.0, and generally lighter-weight and easier to implement correctly, especially for mobile and API-heavy scenarios SAML was never designed for. SAML persists because enormous amounts of enterprise software — many still-supported legacy applications, and a long tail of vendors who built SAML support years ago and never added OIDC — only speak SAML, and enterprise IT departments have deep existing investment in SAML-based SSO tooling; ripping that out for OIDC-only support isn't something a vendor can force on customers without losing deals. Any team building a B2B product with enterprise customers should expect to support both, not just the newer, technically nicer option.

Example 
<!-- SAML assertion, signed XML -->
<saml:Assertion><saml:Subject><saml:NameID>alice@acme.com</saml:NameID></saml:Subject></saml:Assertion>
// vs OIDC's JSON-based ID token — same underlying purpose, very different wire format

Follow-ups

  • Is there a meaningful security difference between the two protocols today, correctly implemented? — Both can be implemented securely; SAML's XML signature validation has historically been a richer source of subtle implementation bugs (XML signature wrapping attacks, discussed below) than OIDC's comparatively simpler JWT signature checks, which is a real, if implementation-dependent, difference in practice.
  • Does ASP.NET Core have first-class SAML support the way it does OIDC? — Not built into the framework the way AddOpenIdConnect is — SAML support in .NET typically comes from a third-party library (e.g. Sustainsys.Saml2) or is handled by an intermediary IdP product that translates SAML into OIDC for the app.
  • Would you recommend a greenfield project ever choose SAML over OIDC? — Essentially never by choice — SAML support is something you add because a customer's existing IdP requires it, not a protocol you'd pick for a new integration if OIDC were equally available.

Wrong answer: "SAML is deprecated and nobody should still be building against it." It's not deprecated in any formal sense and remains a hard requirement for plenty of real enterprise deals — dismissing it outright is a mismatch with how enterprise identity actually works in practice, not a technically informed position.

What is an XML signature wrapping attack against SAML, at a conceptual level? senior

SAML assertions are signed XML, and the signature covers a specific element by reference (an ID pointing at the element that was actually signed) — a wrapping attack exploits implementations that verify a signature is valid somewhere in the document without correctly confirming that the element the application actually processes as the assertion is the same element the signature actually covers. An attacker takes a legitimately signed assertion (perhaps their own, low-privilege one) and wraps or relocates it inside a modified XML structure that also contains a forged, unsigned (or differently-referenced) assertion claiming to be a different, higher-privilege user — if the validating library checks "is there a valid signature in this document" and separately, carelessly, processes "the assertion the code finds by some other means" as if they're guaranteed to be the same element, the forged content sails through despite the signature actually covering different content entirely.

Example 
Legitimate signed assertion for "alice" wrapped inside attacker-modified XML that also contains an
unsigned/forged assertion for "admin" — a naive validator confirms *a* signature is valid, then a separate,
uncoordinated step reads the forged "admin" assertion as the one to trust.

Follow-ups

  • Is this an OIDC/JWT vulnerability too? — Not in the same form — a JWT's signature covers the entire compact-serialized token as one string, with no equivalent "which sub-element does this signature actually cover" ambiguity; this is a specifically XML-shaped problem, arising from XML's more flexible document structure and the reference-based signature model.
  • How do modern SAML libraries defend against this? — By validating the exact structural position of the signed element relative to the document root (not just "a valid signature exists somewhere"), and by using a proper, well-audited SAML library rather than hand-rolled XML signature checking — this is exactly the kind of protocol-parsing subtlety not worth reimplementing yourself.
  • Does this mean SAML is inherently less secure than OIDC? — It means SAML's implementation surface has historically had a harder, more mistake-prone class of parsing bug to get right — a correctly implemented, well-audited SAML stack closes this, but the risk of a subtly wrong homegrown implementation is real and has caused actual production vulnerabilities across multiple SAML libraries historically.

Wrong answer: "As long as the assertion is signed, you can trust its contents." Signature presence and signature correctly covering the exact content you're about to trust are different guarantees — wrapping attacks exploit exactly that gap, which is why the answer emphasizes structural validation, not just "a signature exists."

What is SP-initiated vs. IdP-initiated SAML SSO, and why is IdP-initiated flow considered riskier? senior

In SP-initiated SSO, the user starts at your app (the service provider), which redirects them to the IdP with a signed AuthnRequest carrying a request ID the SP remembers and later validates the response against — establishing a clear, SP-controlled expectation of "I asked for this, here's proof the response corresponds to my request." In IdP-initiated SSO, the user starts at the identity provider's own portal (e.g. clicking an app tile in Okta's dashboard) and the IdP sends an unsolicited assertion straight to the SP with no prior request to correlate it against — which removes the natural anti-replay/anti-CSRF correlation SP-initiated flow gets almost for free, and has historically been a vector for assertion replay if the SP doesn't independently enforce its own freshness/one-time-use checks on the assertion.

Example 
SP-initiated: App -> AuthnRequest(id=abc123) -> IdP -> Response(InResponseTo=abc123) -> App validates match.
IdP-initiated: IdP -> Response (no InResponseTo at all) -> App has nothing of its own to correlate against.

Follow-ups

  • Does IdP-initiated SSO have to be insecure, or can it be done safely? — It can be done safely if the SP independently enforces assertion freshness (NotOnOrAfter), single-use tracking (rejecting an assertion ID it's already processed), and audience restriction checks — the risk comes specifically from skipping those checks on the assumption that the missing InResponseTo correlation was providing protection it never actually was.
  • Why would an enterprise still want IdP-initiated flow despite the added risk? — Convenience — a portal of app tiles where clicking any tile just works, without every app needing to be visited first to trigger the SP-initiated redirect; it's a real UX pattern many enterprise IT departments rely on, not a mistake to eliminate outright.
  • Is there an OIDC equivalent of this SP-initiated/IdP-initiated distinction? — Not really in the same shape — OIDC's authorization code flow is inherently SP(client)-initiated by design; there isn't a standard "IdP pushes an unsolicited ID token" pattern in mainstream OIDC usage.

Wrong answer: "IdP-initiated SSO is simply broken and should never be supported." It's a real, supportable pattern with a genuine convenience benefit — the correct response to its added risk is stricter server-side assertion validation, not blanket refusal to support a flow enterprise customers commonly expect.

What is WS-Federation, and where might you still encounter it? mid

WS-Federation is another, older browser-based federation protocol (part of the broader WS-* family), conceptually similar in purpose to SAML but with its own distinct message format and flow — it was historically the default federation option in some Microsoft-centric stacks (classic ASP.NET's System.IdentityModel, older Active Directory Federation Services deployments) before OIDC support matured in those same products. You're most likely to encounter it maintaining or migrating a legacy on-prem .NET Framework application still integrated with an older ADFS deployment, rather than in any new work — it's very much legacy at this point, more so even than SAML, which at least still sees active new integrations.

Example 
Legacy ASP.NET (System.IdentityModel) <-- WS-Federation --> on-prem AD FS
vs. modern ASP.NET Core <-- OIDC --> Entra ID / any current OIDC IdP

Follow-ups

  • Does ASP.NET Core have built-in WS-Federation middleware? — There's a Microsoft.AspNetCore.Authentication.WsFederation package for interoperating with legacy WS-Federation IdPs from a modern app, but it's very much a migration/interop tool, not something you'd build a new integration around.
  • What's the typical migration path away from WS-Federation? — Reconfigure the same ADFS (or replace it with Entra ID) to expose an OIDC endpoint instead, and switch the app to AddOpenIdConnect — most modern federation servers support both protocols simultaneously during a transition period, echoing the overlap-window pattern from earlier units.
  • Is WS-Federation meaningfully less secure than SAML or OIDC? — Not inherently, if correctly implemented and kept patched — the concern is less about the protocol's own cryptography and more that it's rarely under active security scrutiny or improvement anymore, and the systems still running it also tend to be behind on other, unrelated patching.

Wrong answer: "WS-Federation is the same thing as WS-Security, just an older name." They're related but distinct parts of the WS-* specification family — WS-Federation is specifically about federated identity/SSO, WS-Security is a broader message-security specification for SOAP; conflating them misidentifies what either one actually does.

You're integrating a new product with an enterprise customer whose IT team says "we only support SAML." How do you architect your app's authentication layer so this doesn't become a special case bolted onto an OIDC-only design? principal

I'd design the app's own internal session/identity model to be protocol-agnostic from the start — regardless of whether a user arrived via OIDC or SAML, both flows should terminate in the exact same internal outcome: a validated set of claims (name, email, tenant, roles) mapped into the app's own canonical ClaimsPrincipal/session representation, with the specific federation protocol treated as an input adapter, not something the rest of the app (authorization policies, session cookie issuance, audit logging) needs to know or care about. Concretely in ASP.NET Core, that means both AddOpenIdConnect and a SAML library's handler ultimately funnel into the same sign-in/cookie-issuance pipeline and the same IClaimsTransformation/claims-mapping layer (unit 05), so a new SAML-only enterprise customer is a configuration addition (a new IdP entry, a claims-mapping profile for their specific attribute names) rather than a structural fork in the codebase. I'd also expect this customer's SAML metadata to use different attribute names for the same concepts your OIDC-based customers provide (e.g. http://schemas.xmlsoap.org/claims/EmailAddress vs. OIDC's plain email), so the claims-mapping layer needs to be per-IdP configurable, not hardcoded to one protocol's naming conventions.

Example 
OIDC IdP  --> claims mapping A --> canonical ClaimsPrincipal --> app's session/cookie pipeline
SAML IdP  --> claims mapping B --> canonical ClaimsPrincipal --> same app's session/cookie pipeline

Follow-ups

  • Does this design cost more up front than just special-casing this one SAML customer? — Somewhat, yes — but the alternative (a one-off SAML integration that doesn't go through the same claims-mapping/session pipeline as everyone else) tends to accumulate as separate, divergent authorization and audit-logging code paths the moment a second SAML customer arrives, which is a worse long-term cost than the modest upfront abstraction.
  • What if the enterprise customer's SAML assertion doesn't include an attribute your app actually needs (e.g. no explicit role claim)? — That's a real, common gap to negotiate with their IT team directly — often resolved by either configuring their IdP to release an additional attribute, or falling back to a locally-managed role assignment inside your app for that tenant's users rather than expecting every IdP to supply every claim you'd ideally want.
  • How do you test a new SAML integration without a live enterprise IdP available yet? — A self-hosted test IdP (many SAML libraries ship one, or a tool like SimpleSAMLphp) configured with representative metadata lets you validate the claims-mapping and session pipeline end to end before the real customer's IT team is even engaged.

Wrong answer: "Just add a separate SAML-specific login path and session flow alongside the existing OIDC one." That's exactly the special-case-bolted-on outcome the question is asking how to avoid — a second, protocol-specific pipeline duplicates (and risks diverging from) the authorization, session, and audit logic the OIDC path already has, rather than reusing it.

15 Auth incident response & abuse detection

The rarest-probed area of this bank, but the one that most reveals whether someone has actually operated an authentication system in production rather than only built one. Fewer questions here, weighted toward senior/principal, since this is where judgment under pressure matters more than protocol trivia.

OWASP Automated Threats to Web Applications · Microsoft Entra ID Protection overview

You get an alert that a set of user accounts have had a spike in failed logins followed by a successful one, from IP ranges the users don't normally use. What's your investigation and response process? senior

This pattern — a failed-login spike followed by success — is the signature of credential stuffing (an attacker trying leaked username/password pairs from an unrelated breach) succeeding against a subset of reused passwords, not a targeted attack on your app's own auth logic specifically. First step is scoping: pull the actual login logs for the affected accounts and surrounding time window to confirm the pattern and identify exactly which accounts had a successful login from an anomalous source, rather than acting on the alert's summary alone. Immediate containment for confirmed-affected accounts: force a session/token revocation (unit 08's "logout everywhere") and a mandatory password reset, ideally with a notification to the account owner describing what happened. Medium-term: check whether MFA was enabled for the affected accounts (if not, that's very likely how a correct-password login still succeeded), and check rate-limiting/CAPTCHA thresholds on the login endpoint, since a spike large enough to be alertable suggests those controls have room to be tightened.

Example 
1. Confirm scope: query login logs for the affected accounts + time window.
2. Contain: revoke sessions/tokens for confirmed-compromised accounts, force password reset.
3. Notify affected users with specifics (when, roughly from where).
4. Review: were these accounts missing MFA? Was the login endpoint's rate limiting/CAPTCHA threshold too loose?

Follow-ups

  • How do you distinguish credential stuffing from a targeted brute-force against one specific account? — Credential stuffing typically shows many different accounts each getting a small number of attempts from a wide/rotating set of sources (testing many leaked pairs broadly); a targeted brute-force shows many attempts concentrated against one specific account — the shape of the failed-attempt distribution across accounts and sources is the key signal.
  • Should you notify users whose accounts were targeted but NOT successfully compromised? — Generally worth considering, especially if their password was clearly part of the attempted list (a strong nudge to change it even though this particular attempt failed), though it's a judgment call weighed against alert fatigue from over-notifying for every failed attempt.
  • What's the longer-term structural fix, beyond this one incident? — Checking newly-set passwords against known-breached-password lists at signup/change time (a widely recommended practice) so a reused, already-leaked password never gets accepted as valid in the first place, closing the root cause rather than just responding to each wave of attempts.

Wrong answer: "Just force a password reset for the affected accounts and close the ticket." That addresses the immediate compromised credential but skips confirming scope (are there more affected accounts the alert didn't catch), skips checking whether MFA gaps or weak rate limiting let this succeed in the first place, and skips the systemic fix (breached-password checking) that would prevent a recurrence.

How would you design abuse detection for a login endpoint to catch credential stuffing and brute-force attempts before they succeed, not just after? senior

Layer several signals rather than relying on any single threshold: per-account failed-attempt rate limiting (unit 09's lockout, tuned to avoid the self-inflicted-DoS trap), per-IP/per-range rate limiting independent of which account is being targeted (catches an attacker spraying attempts across many accounts from one source, which per-account lockout alone misses), and anomaly-based signals — a login attempt from a geographically implausible location relative to the account's recent history, an unusual device/user-agent, or attempt velocity across the whole login endpoint spiking well above baseline. None of these alone is sufficient — an attacker distributing attempts across many IPs defeats per-IP limiting, an attacker with patience defeats per-account rate limiting — so the detection should combine signals into a risk score that can trigger escalating friction (CAPTCHA, then step-up MFA, then temporary block) rather than a single hard binary gate.

Example 
Signal 1: per-account failed attempts (existing lockout, tuned).
Signal 2: per-IP/range attempt velocity across ALL accounts (catches distributed targeting).
Signal 3: impossible-travel / anomalous-device risk scoring.
Combined risk score -> escalating response: CAPTCHA -> step-up MFA -> temporary block, not one hard threshold.

Follow-ups

  • Is building this detection logic yourself the right call, or should you use a managed service? — For most teams, a managed identity-protection feature (Entra ID Protection's risk-based sign-in, or an equivalent from another IdP) already implements this kind of multi-signal risk scoring at a scale and sophistication most individual teams can't easily replicate — building it from scratch is usually only justified for very specific, unmet requirements.
  • How do you avoid this system generating so many false positives that legitimate users get blocked constantly? — Escalating friction rather than an outright block for lower-confidence signals (a CAPTCHA is a much smaller cost to a legitimate user than a lockout), and tuning against real historical data for what "normal" travel/device variance actually looks like for your specific user base before setting thresholds.
  • Does rate-limiting/anomaly detection at the login endpoint interact with the account-lockout DoS risk from unit 09? — Yes directly — per-IP rate limiting is exactly the complementary control that unit 09 named as the fix for account-lockout-as-DoS, since it slows down an attacker before their attempts accumulate enough to lock out the legitimate account holder.

Wrong answer: "Set a strict per-account lockout threshold, that covers credential stuffing." Credential stuffing typically spreads attempts thin across many accounts specifically to stay under any one account's lockout threshold — per-account limiting alone is close to useless against the distributed shape of this specific attack.

A customer reports their account was compromised and used to access data they didn't authorize. Walk through what logs and evidence you'd need to reconstruct what happened. senior

You need, at minimum: authentication logs (every sign-in attempt for that account — timestamp, source IP, device/user-agent, success/failure, which method — password, MFA, social login) to establish when and how the account was actually accessed; session/token issuance and use logs (which tokens were issued from that authentication, and every resource-server call that token was used for, ideally correlated by a request/trace ID per unit 10's cross-service audit discussion) to establish exactly what the attacker did once in; and any authorization-decision logs (which of unit 06's policy checks were evaluated, and their outcomes) if the question is specifically about unauthorized data access rather than just unauthorized login. The investigation has to establish a timeline: when did the anomalous sign-in happen, what token(s) came from it, and what did each of those tokens actually touch — without a correlated trace across all three layers, you can confirm "someone logged in from an odd location" but not concretely answer "and here specifically is what they accessed," which is usually what the customer (and any compliance/legal follow-up) actually needs answered.

Example 
1. Auth log: sign-in at 03:14 UTC from IP 203.0.113.9, password+MFA both succeeded, device fingerprint unseen for this account.
2. Token log: access token issued at 03:14, jti=abc123, used against /api/orders 14 times before expiry.
3. Resource log: each of those 14 calls -- which specific order IDs were read/modified.

Follow-ups

  • What if the resource-server-side call logs don't include enough detail to know WHICH records were touched, just that a call succeeded? — That's a real, common logging gap discovered only during an actual incident — it's worth treating as a finding in itself (audit logging should capture resource-level identifiers for sensitive read/write operations, not just endpoint-level "someone called /api/orders") and fixing prospectively, even if it limits what you can determine for this particular incident.
  • How do you determine whether the MFA that "succeeded" for this login was actually the legitimate user's, versus something like an MFA-fatigue attack? — Check the MFA method and its own logs specifically — a push-notification approval has a timestamp and (on some systems) a device/location of the approving action, which can reveal whether the approval itself came from a plausible device or looks like a fatigued/mis-tapped approval, a real and increasingly common attack pattern worth naming explicitly.
  • Should you assume the account's credentials are now known to the attacker and force a reset regardless of root cause? — Yes, essentially always — reset credentials and revoke all existing sessions/tokens as an immediate containment step in parallel with, not after, the investigation, since containment shouldn't wait on fully understanding root cause first.

Wrong answer: "Check the authentication logs to see if the login looks suspicious, that answers the question." Confirming a suspicious login happened doesn't tell you what was actually accessed afterward — the customer's specific complaint is about unauthorized data access, which needs the token-use and resource-access logs correlated with the authentication event, not the authentication event alone.

Design the auth-related logging and alerting you'd want in place before an incident happens, for a system handling sensitive data, knowing what you now know about investigating one after the fact. principal

Working backward from the previous question's gap (auth logs alone don't tell you what was accessed), I'd insist on three correlated log streams sharing a common trace/correlation ID end to end: authentication events (who, when, how, from where, MFA method and outcome), token lifecycle events (issuance, refresh, revocation, and critically the jti so a specific token's entire usage history is traceable), and resource-level access events (not just "called /api/orders" but which specific resource IDs were touched, tagged with the token's jti and the underlying user id) — the absence of that third layer's granularity is the single most common gap that turns "we know something happened" into "we can't say what." On top of the logs, alerting needs to cover both anomaly detection (the credential-stuffing-shaped signals from the earlier question) and policy-violation detection (an access pattern that, even from a legitimately-authenticated session, deviates sharply from that account's normal behavior — bulk-exporting far more records than usual, accessing resources outside their normal tenant/scope). I'd also make sure retention is long enough to matter: a compromise is often discovered weeks after it happened, and logs rotated out after a few days are useless for exactly the investigation this whole unit is about.

Example 
Correlated by trace_id across all three streams:
auth_events:      {trace_id, user_id, method, mfa_outcome, ip, device, timestamp}
token_events:      {trace_id, jti, issued_at, revoked_at, aud}
resource_events:  {trace_id, jti, user_id, resource_type, resource_id, action, timestamp}
Retention: long enough to cover "discovered weeks later" -- not just a few days.

Follow-ups

  • Doesn't resource-level logging at this granularity create its own sensitive-data/privacy concern? — Yes, worth designing deliberately — log resource identifiers and the action taken, not the sensitive data's actual content, and apply the same access controls and retention discipline to the audit log itself that you'd apply to the underlying data, since an audit log is itself now a sensitive asset.
  • How do you balance comprehensive logging against the cost/volume of storing it at scale? — Tiered retention (detailed logs for a shorter hot window, aggregated or sampled data for longer-term retention) is a common compromise — the goal is making sure the level of detail available at the time an incident is typically discovered (which, per the answer, is often weeks out) is still sufficient, not necessarily keeping full-fidelity logs forever.
  • Would you build this logging/correlation infrastructure yourself, or lean on an existing SIEM/observability platform? — Almost always the latter for the underlying storage/correlation/alerting infrastructure — the auth-specific design work is deciding what to emit and how to correlate it (the trace ID discipline above), not reinventing log aggregation and search from scratch.

Wrong answer: "Log every authentication attempt, that's the important part for security." Authentication-only logging is exactly the gap the previous question exposed — without token-lifecycle and resource-level correlation sharing a common trace ID, you can detect that logins happened but never reconstruct what an attacker actually did with the access those logins produced.

16 Judgment calls

These don't have a single correct answer — they exist to see how you reason under genuine ambiguity, the way an actual architecture review or incident retro would. Each hidden block names what a strong answer demonstrates at the top of the ladder and the trade-offs it names without being prompted for them; there's no "wrong answer" callout here because the point isn't a fact you either know or don't, it's the quality of the reasoning.

A new API has no constraints stated up front — greenfield, web and mobile clients both planned. Cookies or bearer tokens for session state?

A strong answer demonstratesRecognizing this is a false binary once both client types are in scope: the web client is best served by a BFF holding tokens server-side and issuing a cookie, while the mobile client is best served by bearer tokens directly against the API — the "cookies or bearer" framing is really "which client, which trust boundary," and a strong answer restructures the question rather than picking one universally.

Trade-offs named unpromptedThe BFF's added operational component and latency hop for the web path; the fact that a shared API now needs to authenticate both a forwarded/validated session and a directly-presented bearer token, which touches unit 05's policy-scheme design; and that this costs more up front than picking one uniform mechanism, justified by not forcing a worse security posture onto whichever client type didn't get the mechanism suited to it.

How do you decide when to build custom authorization logic versus adopting a policy engine like OPA or a ReBAC system like OpenFGA?

A strong answer demonstratesTying the decision to a concrete signal — authorization rules currently require joins/logic that's outgrown plain code or SQL, or the same rule needs to be enforced consistently across more services than one team can keep synchronized by convention — rather than adopting either out of general modernization enthusiasm. Naming the actual inflection point (unit 12's "recursive CTEs and unbounded joins" signal) shows this is learned from consequence, not from a framework's marketing.

Trade-offs named unpromptedA dedicated engine adds an operational component, a new language/model the team has to learn, and a migration risk (the dual-run discipline from unit 12) — versus the ongoing, compounding cost of authorization logic drifting across services when nothing centralizes it. A strong answer also flags that adopting either prematurely, before the actual complexity exists, is itself a real cost, not free future-proofing.

A team wants to skip refresh token rotation "to keep things simple" for an MVP. How do you respond?

A strong answer demonstratesNot reflexively blocking the simplification — asking what "MVP" actually means for this product's risk profile (internal tool with a handful of trusted users vs. a consumer product about to onboard real payment data) before deciding whether the corner is safe to cut, and being explicit that "simple for now" needs a stated, tracked plan to revisit before the user base or data sensitivity grows, not an indefinite deferral.

Trade-offs named unpromptedThe actual exposure if a refresh token leaks with no rotation/reuse-detection (unbounded validity until the token's own long expiry, no automatic containment) versus the real engineering time saved by deferring it; and that this is a decision worth writing down explicitly (a dated follow-up, not a silent gap) so it doesn't quietly become permanent as the MVP calcifies into production.

When is zero-trust-style re-verification at every service worth its complexity, versus trusting a perimeter/gateway check once?

A strong answer demonstratesDistinguishing coarse-grained checks that are genuinely safe to trust once (a gateway's scope/client validation, per unit 12) from resource-specific decisions that structurally cannot be made anywhere but the owning service — the zero-trust argument isn't "re-check everything everywhere identically," it's "know which decisions actually need re-verification because no earlier layer had the data to make them correctly."

Trade-offs named unpromptedThe latency and implementation cost of re-verifying at every hop versus the risk of a compromised or misconfigured internal service being trusted by everything downstream once it's past the perimeter — and that a blanket "re-verify everything" policy without this distinction just duplicates the gateway's own logic everywhere without addressing what a gateway can't see in the first place.

Is it ever right to delay MFA enforcement past a launch date rather than block the launch on it?

A strong answer demonstratesWeighing the actual data/action sensitivity behind the login (a read-only marketing site vs. an app handling financial transactions or health data) rather than treating "ship with MFA" as a universal non-negotiable or "ship without it" as an automatic acceptable risk — and naming who has the authority to accept that risk explicitly (a security/compliance owner signing off with a stated remediation date) rather than the engineering team quietly deciding alone.

Trade-offs named unpromptedBusiness cost of a delayed launch versus the concrete exposure window and what's actually reachable without MFA in the meantime; and that "we'll add it in v1.1" needs a real forcing function (a tracked date, a following release actually blocked on it) or it tends to never happen once the launch pressure that created the exception has passed.

How do you evaluate whether a vendor's "we support SSO" claim is actually deep enough for your enterprise customers?

A strong answer demonstratesGoing past the marketing claim to concrete protocol and feature questions — SAML, OIDC, or both; SP-initiated only or also IdP-initiated; SCIM provisioning support or SSO alone; per-tenant configuration or one shared IdP setting for the whole product — because "SSO support" spans a wide range of actual capability, and enterprise procurement checklists (unit 13) routinely surface gaps a vendor's homepage claim glossed over.

Trade-offs named unpromptedThe cost of digging into this deeply during vendor evaluation (time, needing the right technical questions ready) versus discovering the gap only after a signed contract and an enterprise customer's IT team asking for a capability that isn't actually there; and that a vendor's roadmap promise ("SCIM is coming next quarter") is a real risk to weigh, not equivalent to it already existing.

How do you set token lifetime defaults for a brand-new product with no real usage or attack data yet?

A strong answer demonstratesStarting from documented, well-reasoned industry defaults (short access tokens in the 5-15 minute range, longer refresh tokens with rotation) rather than either an arbitrary guess or over-engineering a bespoke scheme before there's any real usage pattern to tune against — and being explicit that these are a starting hypothesis meant to be revisited once actual session-length and risk data exists, not a permanent decision made once and never revisited.

Trade-offs named unpromptedShorter lifetimes meaning more frequent refresh traffic and a slightly rougher experience if refresh ever fails, against tighter exposure if a token leaks; and the operational cost of having no real data yet to justify deviating from the sane default in either direction, which argues for starting conservative rather than optimizing prematurely.

Should authentication be centralized behind one IdP for the whole company, or allowed to vary per product line/business unit?

A strong answer demonstratesNaming the real tension: centralization gives one place to enforce MFA/Conditional Access policy and a single source of truth for "who can sign in at all" (valuable for security and compliance), while per-business-unit variance can be a legitimate response to genuinely different customer bases (an internal tool's workforce IdP vs. a consumer product's B2C-style identity) rather than always organizational sprawl to be stamped out.

Trade-offs named unpromptedThe audit/consistency cost of letting business units diverge versus the real friction of forcing a workforce IdP's constraints onto a consumer-facing product that needs self-service sign-up and social login it was never designed for; and that "centralize everything" without acknowledging B2B/B2C's genuinely different requirements (unit 13) is itself a naive answer.

You're building an internal platform team's shared auth SDK used by dozens of other teams. How do you balance developer convenience against security rigor in its design?

A strong answer demonstratesRecognizing that a shared SDK's defaults become every consuming team's defaults at scale — so the SDK should make the secure choice the path of least resistance (secure token storage, correct validation, sane lifetimes baked in) rather than exposing every knob and trusting each team to configure it correctly, while still leaving genuine, justified escape hatches for teams with real, different requirements rather than making the SDK rigid to the point teams route around it entirely.

Trade-offs named unpromptedA more opinionated, locked-down SDK is more secure by default but slower for the platform team to extend and more frustrating for a team with a legitimate edge case; a more flexible one accommodates more teams' needs but risks becoming the same "insecure by default, secure only if configured carefully" problem the SDK was supposed to solve in the first place.

A confirmed account-compromise incident affects a handful of specific users. Do you force a password reset/session revocation for those users only, or for the entire user base?

A strong answer demonstratesScoping the response to what the actual investigation (unit 15) established — targeted action for confirmed-affected accounts is the right default when the root cause is specific to those accounts (a reused, breached password) — while being able to articulate the conditions that would change that call, such as evidence the compromise came through a shared vulnerability (a bug in the login endpoint itself) that plausibly exposed every account, not just the ones currently confirmed.

Trade-offs named unpromptedA broad, whole-user-base reset is disruptive and costly in support load and user trust if the root cause turns out to be narrow, while a narrowly-scoped response risks under-reacting if the true blast radius is larger than what's been confirmed so far — a strong answer treats "how wide" as a call that should be revisited as the investigation's scope understanding evolves, not fixed at the first response.

17 Design exercises

Full system-design prompts where authn/authz is the centerpiece, not a side detail. Try each one cold: read the prompt, ask yourself (or an interviewer) the clarifying questions, sketch an answer, then open the solution to compare. These are where a principal-level conversation actually happens — the prompt alone is underspecified on purpose.

Exercise 1 — Greenfield B2B SaaS: design the auth architecture from scratch. You're the founding engineer on a new B2B SaaS product. Some customers will want SSO via their own Entra ID/Okta tenant; others (smaller, no IdP of their own) just want email/password. The product has a web app today, with a mobile app planned for next year. Design the authentication and session architecture.

Clarifying questions to ask:

  • Is there a target enterprise customer segment already in the sales pipeline, or is B2B-with-SSO aspirational at this stage?
  • Does the product need to support a user belonging to more than one tenant (e.g. a consultant working with several customers)?
  • Is there a compliance requirement (SOC 2, a specific customer's security questionnaire) already driving MFA/session-length expectations?
  • What's the tolerance for a first version that's simpler than the full end-state, given the mobile app is a year out?
Solution outline & expected trade-offs

Start with a BFF-fronted web app (unit 04/11): the browser gets an HttpOnly/Secure/SameSite=Lax session cookie, tokens live server-side. Authentication resolves per-tenant (unit 13): an email-domain or subdomain lookup decides whether that tenant routes to a configured SAML/OIDC IdP or to local email/password, implemented as a policy-scheme-style dispatch (unit 05) so adding a new enterprise customer's IdP is configuration, not a code fork. Authorization starts as straightforward RBAC plus a resource-owner check (unit 06) — no need for a policy engine or ReBAC model yet, since the product doesn't have deep sharing/nesting at this stage. For the mobile app arriving later, plan (but don't build yet) for it to get bearer tokens directly against the same API rather than trying to force it through the BFF's cookie session, which doesn't fit a native client.

Trade-offs expected unprompted
  • Building the per-tenant auth-routing abstraction now costs more than hardcoding one auth method, but retrofitting multi-method tenant routing after the first enterprise SSO customer signs is a much larger, riskier change than building it in from day one.
  • Choosing RBAC now instead of a ReBAC/policy-engine model is deliberate simplicity, not a mistake to correct pre-emptively — the migration path (unit 12's dual-run pattern) exists for when the product's actual sharing complexity justifies it.
  • Deferring mobile-specific design work is reasonable, but the web app's token/session design should already anticipate a bearer-token-consuming API existing later, so the API's authorication layer isn't rebuilt around cookie-only assumptions that would need undoing.

Exercise 2 — Splitting a monolith: token and session architecture for the new microservices. A company is breaking a monolithic ASP.NET Core app (currently cookie-authenticated, one database, one deployable) into ~15 microservices, while keeping the existing web app and adding a new mobile app. Design how authentication and service-to-service authorization work in the new world.

Clarifying questions to ask:

  • Is the monolith's existing session/cookie infrastructure staying in place for the web app during the transition, or is everything cut over at once?
  • Do the new microservices need to call each other directly, or does every call route back through a gateway/BFF?
  • Is there an existing Entra ID tenant or IdP already in use for the workforce/customers, or is this greenfield too?
  • What's the expected trust boundary — are these 15 services all first-party, or does any external partner need to call into some of them?
Solution outline & expected trade-offs

Keep the web app's cookie-based session and BFF pattern unchanged at the edge — the split is behind that boundary, so the browser's auth story doesn't need to change on day one. The BFF/gateway validates the incoming session and calls downstream services with a token representing the user, using the on-behalf-of pattern (unit 10) so each service gets a token scoped to itself rather than forwarding one broad token everywhere. Service-to-service calls with no user in the loop (a background job calling inventory) use client credentials, ideally backed by a service mesh's mTLS for transport-level service identity rather than juggling 15 sets of client secrets. The mobile app gets bearer tokens directly against the gateway, following the same OBO pattern downstream — it doesn't need its own separate design, it plugs into the same token-exchange architecture the web path already established. Authorization: keep policy checks in the owning service for resource-specific decisions, with the gateway handling only coarse scope/client checks (unit 12) — don't try to centralize per-resource authorization at the gateway, it doesn't have the data.

Trade-offs expected unprompted
  • The OBO/token-exchange machinery is real added complexity over the monolith's single in-process authorization check — justified once there are 15 independently deployed services needing consistent per-user scoping, not before.
  • mTLS via a service mesh has real operational setup cost (certificate issuance/rotation infrastructure) versus simple shared secrets — worth it at this scale specifically because rotating 15 services' worth of shared secrets by hand doesn't stay manageable.
  • Doing the split incrementally (strangler-fig style, keeping the cookie/BFF boundary stable while the backend splits underneath) is slower than a big-bang rewrite but avoids the substantial risk of changing the user-facing auth experience and the backend architecture at the same time.

Exercise 3 — Project-management SaaS: authorization from RBAC to fine-grained sharing. Your project-management product started with simple per-project roles (owner/editor/viewer). Customers now want nested workspaces, folders inside workspaces, and the ability to share an individual item with someone outside its folder's normal access, with permissions cascading down the hierarchy unless explicitly overridden. Design the authorization model for this, and the migration from what exists today.

Clarifying questions to ask:

  • How deep does the nesting actually go today, and is it likely to grow further, or is this the final shape?
  • Are per-item overrides expected to be common, or a rare escape hatch a small fraction of customers use?
  • Is there an existing audit/compliance requirement to answer "who can see item X" quickly, or is that query rare enough to tolerate being slower?
  • What's the acceptable downtime/risk tolerance for the migration itself — can authorization decisions be dual-run in production before cutover?
Solution outline & expected trade-offs

This is exactly the inflection point named in unit 12: the moment cascading permissions with per-item overrides enters the picture, plain relational joins for "can Alice see item 42" start requiring recursive queries that get harder to reason about and slower as nesting grows. Model the hierarchy and sharing as a relationship graph in a dedicated ReBAC engine (OpenFGA-style, self-hosted or managed) — a workspace/folder/item hierarchy with inheritance, plus explicit item-level relation tuples for the override case, resolved by graph traversal rather than SQL joins. Migrate incrementally: stand up the ReBAC model alongside the existing relational checks, dual-run both on every authorization decision in production while only enforcing the legacy result, log disagreements, and only cut enforcement over to the new model once disagreement is at zero for a sustained period. Keep a "list everyone who can see item X" reverse-query capability in mind from the start (most ReBAC engines need a distinct query path for this versus the forward "can user see item" check) since compliance/audit needs will ask exactly that question.

Trade-offs expected unprompted
  • Introducing a ReBAC engine is a real new operational dependency and a new mental model for the team — justified here because the actual feature (cascading permissions with overrides) is the thing customers are asking for, not a speculative future need.
  • The dual-run migration is slower and more expensive than a hard cutover, but a hard cutover on authorization — the one thing that, if wrong, either locks legitimate users out or leaks data to the wrong ones — is the wrong place to accept that risk to save migration time.
  • Reverse "who can see this" queries at scale are a known harder problem than forward checks in most ReBAC systems — worth surfacing to the team early rather than discovering it only when the first audit request comes in.

18 Night-before cheat sheet

The ten most-asked questions across the whole bank, one sentence each. Read this last, right before you go in — it's recall, not learning.

  1. What does OAuth actually solve, and what is it not? — It's delegated, scoped authorization for a client to call an API on a user's behalf without ever seeing their password; it has no concept of identity on its own, which is exactly the gap OpenID Connect fills.
  2. Walk through authorization code + PKCE. — The client redirects the browser to /authorize with a PKCE challenge, the user authenticates and consents at the AS, the AS redirects back with a short-lived single-use code, and the client exchanges it server-to-server at /token using the matching PKCE verifier.
  3. ID token vs access token? — The ID token is a signed assertion of who the user is, meant for the client itself to consume; the access token authorizes calling a resource server's API and should never be used as proof of identity.
  4. What must you always verify when validating a JWT? — The signature against the correct, expected algorithm and key (never trust the token's own alg header), the issuer, the audience, and the expiry — skipping any one of these is a real, exploitable bug.
  5. Why are access tokens short-lived and refresh tokens longer-lived? — Short access-token lifetimes limit the damage window if one leaks, since it can't be individually revoked cheaply; the longer-lived refresh token re-obtains new access tokens without re-prompting the user, and carries its own rotation/reuse-detection to contain a leak of itself.
  6. Cookies or bearer tokens for a web app's session? — An HttpOnly/Secure/SameSite cookie behind a BFF keeps tokens out of JS-reachable storage and is the safer default for a browser-based session; bearer tokens fit native apps and direct SPA-to-API calls a cookie's same-site model can't reach.
  7. How does ASP.NET Core separate authentication from authorization? — UseAuthentication populates HttpContext.User from whichever scheme handled the request; UseAuthorization, which must run after it in the pipeline, evaluates policies and handlers against that already-established principal.
  8. Role-based or policy-based authorization? — Roles are a simple, built-in claim check that's fine for coarse "is in role X" gates; policy-based authorization with custom requirements and handlers is what you reach for the moment a decision needs more context than a role name alone provides.
  9. What is CSRF, and why doesn't it touch a pure bearer-token API? — CSRF abuses the browser automatically attaching a site's cookies to any request regardless of origin; a bearer token in an Authorization header is never attached automatically, so a cross-site page has nothing to ride on.
  10. Why rotate refresh tokens with reuse detection? — Replaying an already-used, rotated refresh token is a strong signal of theft, so the server can revoke the entire token family immediately — containing a stolen refresh token's blast radius instead of waiting out its full, otherwise long-lived expiry.
