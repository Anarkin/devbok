Docker / Containerization

study · Docker Engine 29.8 · released 2026-09-03

Docker today is two things at once, and a lead-level answer keeps both in view: a mature, boring-in-a-good-way container runtime built on the OCI trio of containerd + runc + BuildKit, and — as of 2026 — the company's second act as a supply-chain-security and AI-agent-sandboxing vendor (Docker Hardened Images, Docker Scout, Docker Sandboxes). Engine 29.8.0 (3 Sept 2026) is current; the 29.x line made the containerd image store the default backend for fresh installs, folded an experimental embedded-containerd daemon mode into the CLI, and finished removing Docker Content Trust. Compose has quietly become its own product: it is at v5.5 with a from-scratch state-reconciliation engine, no relation to the old "Compose file version:" numbers, which the Compose Specification retired years ago. The legacy you will still meet in real codebases: the overlay2 graph driver, cgroup v1 hosts (deprecated but supported through May 2029), Compose V1 (Python, EOL since mid-2023), and Docker Swarm, which Mirantis keeps patched but which lost the orchestration argument to Kubernetes years ago. None of that legacy is hypothetical — you will be debugging it in production long after it stops shipping new features.

01 Architecture: daemon, containerd, runc

Start from the question an interviewer is really asking when they say "what is Docker": not "what commands do you type" but "what layers of software turn a JSON file into an isolated process, and who owns each layer". The honest answer today is that "Docker" is a product built almost entirely on top of the Open Container Initiative (OCI) stack it helped create, and most of what used to be Docker-proprietary has been donated out. runc is the low-level runtime: it reads an OCI runtime-spec bundle (a root filesystem plus a config.json) and makes the one clone()/unshare() syscall dance that turns it into a namespaced, cgrouped process. containerd sits above runc: it manages the container lifecycle (create, start, pause, checkpoint), image pulls and pushes, and content-addressable storage, and it exposes all of that over a gRPC API that both the Docker daemon and Kubernetes (via the CRI plugin) talk to. The Docker daemon, dockerd, is the top of the stack: it owns the parts that are Docker's real product surface — the CLI-facing API, networking (libnetwork/CNM), volumes, Compose orchestration, build (BuildKit), and the developer experience — and it delegates almost everything else down to containerd.

The mental model worth carrying into the interview: an image is a read-only, content-addressed bundle of filesystem layers plus metadata (entrypoint, env, exposed ports) — a value, not a process. A container is a running (or stopped) instance created from an image: a thin writable layer on top of the image's read-only layers, plus a set of namespaces and a cgroup that isolate and bound it. Nothing about a container is special hardware-wise; it is Linux kernel features — namespaces for "what can you see", cgroups for "how much can you use" — wrapped in tooling that makes them reproducible and shippable. This is precisely why "Docker" and "a container" are not synonyms: podman, containerd's own ctr/nerdctl, and Kubernetes's kubelet can all run the exact same OCI image without Docker ever being installed.

What changed recently and is worth naming unprompted: Docker Engine 29.0 made the containerd image store the default image storage backend on fresh installs, replacing the classic overlay2 graph driver as the out-of-the-box behavior (existing upgraded hosts stay on overlay2 until you opt in). Engine 29.7 went a step further with an experimental "embedded containerd" mode, where containerd runs inside the dockerd process instead of as a separate daemon+socket — fewer moving parts to operate, at the cost of being new enough that most production guidance still says "run them separately, and know why." Both changes are about operational simplicity, not about the architecture: the layering (runc under containerd under dockerd) hasn't changed since Docker split itself apart in 2016–2017; only who ships as one process has.

Interview trap

"Docker containers are lightweight VMs" is the single most common wrong mental model, and it fails the very next question: "so what's the kernel inside the container?" There is no kernel inside the container — every container on a host shares that host's one kernel, which is exactly why a container starts in milliseconds and a VM doesn't, and exactly why a kernel-level vulnerability (e.g. a namespace escape) is a shared-host risk, not a per-tenant one. The corollary trap: "so containers are less secure than VMs" is directionally true but glosses over the actual mitigations (seccomp, capabilities, rootless, gVisor/Kata as VM-backed runtimes) covered in unit 05 and 10 — say both halves.

Try it

1. Run any container, then in another terminal find its runc and containerd-shim processes with ps -ef | grep -E 'runc|shim' and its namespaces with ls -la /proc/<pid>/ns/. 2. Kill the containerd-shim process for a running container and observe what happens to the container itself.

What you should observe

You'll see one containerd-shim-runc-v2 process per running container — it's the process that owns the container's stdio and reaps its exit code even if dockerd restarts, which is exactly why systemctl restart docker doesn't kill your containers. runc itself only exists transiently during create/exec; it hands the running process off to the shim and exits. Killing the shim, in most configurations, kills the container with it — it's the single point that would need to survive for "live-restore" to work, and is why Docker's --live-restore daemon flag exists.

Walk through exactly what happens between typing docker run nginx and the process existing.

The Docker CLI is a thin HTTP client: it POSTs to dockerd's REST API over the Unix socket. dockerd checks its local image store for nginx:latest; if missing, it asks containerd to pull it, which fetches the manifest, then each layer, from the registry and stores them content-addressed by digest. dockerd then asks containerd to create a container: containerd assembles an OCI bundle — a merged root filesystem via a snapshotter, plus a generated config.json describing namespaces, cgroup limits, mounts and the entrypoint — and hands it to a containerd-shim-runc-v2 process, which execs runc create then runc start. runc does the actual clone() with namespace flags, writes the cgroup, and execve()s nginx as PID 1 inside the new namespaces. The shim stays alive as the parent, streaming stdio back up through containerd to the Docker API to your terminal.

Why does Kubernetes talk to containerd directly instead of through Docker?

Because Docker was never the layer Kubernetes needed — it needed a container runtime, and Docker bundled that with a build system, a CLI, a network stack and an API surface Kubernetes doesn't use. Kubernetes defines the Container Runtime Interface (CRI), a gRPC contract for "pull this image, run this pod sandbox, run this container in it"; containerd implements a CRI plugin natively, so kubelet can talk to it with no extra hop. Historically kubelet talked to Docker through "dockershim," a CRI-to-Docker-API translation layer that Kubernetes maintained itself; it was removed in Kubernetes 1.24 (2022) once containerd's native CRI support was solid, which is why "Kubernetes deprecated Docker support" became a headline even though the actual runtime under most Docker installs — containerd — kept running Kubernetes pods the whole time.

What's the practical difference between the containerd image store and the classic overlay2 graph driver?

They're two different implementations of "how do I materialize layered images as a filesystem," with different capability sets. The graph drivers (overlay2, and historically aufs/devicemapper/btrfs) are Docker-specific code that predates containerd owning storage. The containerd image store uses containerd's own snapshotter abstraction, the same one Kubernetes nodes use, and it unlocks things the graph drivers structurally can't do: building and storing multi-platform images locally without a remote builder, images that carry attestations (SBOM/provenance) as part of the manifest, and pluggable snapshotters like stargz for lazy pulling or nydus for P2P distribution. The trade-off, and a good one to name unprompted, is disk usage: the containerd store currently keeps both the compressed and uncompressed layer representations, so it uses more disk than overlay2 for the same images.

If containers share the host kernel, how does docker run --platform linux/arm64 work on an x86_64 host?

It doesn't run natively — there's no such thing as a foreign-architecture container process on a kernel that can't execute that instruction set. What actually happens is emulation: Docker Desktop and buildx set up binfmt_misc handlers backed by QEMU, so the kernel transparently routes exec of an ARM64 ELF binary through a QEMU user-mode emulator instead of failing. It works, and it's exactly what lets you build and smoke-test multi-arch images on a laptop, but it's meaningfully slower than native execution — one to two orders of magnitude for CPU-bound work — which is why CI systems doing real multi-arch builds use native arm64 runners plus buildx's cross-compilation rather than relying on emulation for the whole build.

What does docker info actually tell you that's worth reading in an incident?

Past the version numbers, the fields that matter operationally: Storage Driver (overlay2 vs the containerd snapshotter — different failure modes and disk math), Cgroup Version and Cgroup Driver (v1 vs v2, systemd vs cgroupfs — a mismatch here is a classic "works on my laptop, OOM-kills wrong on the server" bug), Live Restore Enabled (whether a daemon restart kills running containers), and the security options block (seccomp, apparmor, rootless — telling you what's actually enforced on this host versus what the image assumes). I read this before I read logs when a container behaves differently on one host than another.

Is BuildKit part of containerd, or part of Docker, or its own thing?

Its own thing, and that independence is the point. BuildKit is a separate project and daemon (or embeddable library) for executing build graphs efficiently — content-addressed caching, parallel stage execution, pluggable frontends (Dockerfile is one frontend among several). Docker ships it embedded and drives it through buildx, which since Docker 23 is the default backend for docker build; containerd can also drive BuildKit as a way to produce images without Docker at all. Treating BuildKit as "the thing that reads my Dockerfile" undersells it — the Dockerfile is one possible input; BuildKit's actual job is scheduling and caching an arbitrary build DAG.

What is a containerd "shim," and why does the design put one per container instead of one per host?

The shim is the process that directly parents a container's process tree so that containerd (and dockerd above it) can restart or crash without taking containers down with them — a deliberate answer to a real operational problem in pre-containerd Docker, where the monolithic daemon dying could mean every container dying too. One shim per container, rather than one per host, also means a shim crash or a slow shim only affects its own container, and it's the seam where alternative runtimes plug in: a gVisor or Kata container uses a different shim (containerd-shim-runsc-v1, containerd-shim-kata-v2) that starts a sandboxed or VM-backed environment instead of calling runc, with zero changes needed above containerd.

You inherit a host with both Docker and Podman installed, running different containers. What's the risk?

Mainly resource and observability blind spots, not a fundamental incompatibility — both ultimately drive runc (or crun) against the same kernel primitives, so a well-behaved container from either tool won't corrupt the other's state. The real risks: cgroup and network accounting split across two supervisors makes host-level capacity planning harder (two tools each reporting "their" usage, no unified view), Podman's default rootless-and-daemonless model means its containers won't show up in docker ps or Docker's own metrics at all, and if both are managing iptables/nftables rules for port publishing you can get subtly conflicting NAT rules. I'd treat "two container engines on one host" as a smell to resolve, not a supported topology, unless there's a deliberate reason (e.g. migrating one workload at a time).

How would you explain to a junior engineer why "the container" and "the image" are different things they keep conflating?

I use a concrete analogy: the image is a class, the container is an instance. You can docker run the same postgres:17 image ten times and get ten independent containers, each with its own writable layer, its own PID namespace, its own lifecycle — deleting one doesn't touch the image or the others, exactly like instantiating a class doesn't mutate the class definition. The concrete proof that lands it: docker images lists a handful of images that might back dozens of entries in docker ps -a, and docker commit on a running container produces a new, independent image — turning an instance back into a class, which usually clicks for people coming from OOP.

Lead-level: a team wants to drop Docker Desktop entirely and drive everything through raw containerd/nerdctl. What do they gain and lose?

They gain a lighter, license-cost-free (Docker Desktop's subscription terms only bite larger companies, but it's a real conversation) toolchain that's identical to what their Kubernetes nodes run, which is genuinely valuable for a platform team debugging node-level issues — no translation layer to second-guess. They lose the entire Docker Desktop developer-experience layer: the GUI, the VM/WSL2 integration that makes Linux containers work transparently on macOS/Windows, Compose orchestration (nerdctl has a compose subcommand but with narrower compatibility), and the vast majority of "how do I fix X" answers on the internet, which assume the Docker CLI. My honest recommendation is nearly always "keep Docker (or Podman) for developer machines, and let the platform/SRE team use containerd tooling directly on nodes where they're already debugging at that layer" — optimizing the same tool for two very different audiences rarely wins.

02 Images and layers

An image is a manifest plus a list of layers, and everything about how Docker behaves — build caching, push/pull speed, disk usage, even security posture — falls out of that one sentence. Each instruction in a Dockerfile that touches the filesystem (RUN, COPY, ADD) produces one layer: a tarball (or, with the containerd snapshotter, an OCI-compliant diff) of exactly what changed versus the layer below it. Layers are content-addressed — identified by the SHA-256 digest of their contents — which is what makes them shareable: if two images both have a layer with the identical digest, Docker stores and transfers it exactly once, whether that's two of your own images sharing a base, or your image sharing Ubuntu's base layer with a thousand other images on the same registry.

At runtime, those read-only layers are stacked by a union filesystem — historically AUFS, now almost universally OverlayFS (the overlay2 graph driver, or the containerd overlayfs snapshotter) — and Docker adds one more layer on top: the thin, writable "container layer" unique to that specific container instance. Every file write inside a running container lands there, using copy-on-write: modifying a file that exists in a lower, read-only layer first copies it up into the writable layer, then modifies the copy. This is why containers are cheap to start (no data copying up front) and why a container's writable layer disappears with docker rm — it was never the image, and nothing written there was ever visible to other containers from the same image.

Layer order in the Dockerfile is a caching decision, not just a syntax choice: BuildKit caches each layer keyed by (roughly) the instruction plus its inputs, and a cache miss on layer N invalidates every layer after it. This is why the canonical Dockerfile pattern for any dependency-manager-based project is "copy only the manifest, install dependencies, then copy the rest of the source" — a source-code change shouldn't force a reinstall of unchanged dependencies. What's new enough to be worth naming: since the containerd image store became the default (Engine 29.0+), a single image can be a genuine multi-platform manifest list stored and inspectable locally — one tag, several architecture-specific manifests, each with its own layer set — where under the classic graph driver a multi-arch image was something you could push but not meaningfully store or run more than one architecture of at a time.

Interview trap

"Squashing layers with docker build --squash (or multi-stage) always makes images smaller and better" is only half true. Squashing collapses history into fewer layers, which can shrink an image that deletes large files in a later layer (the deleted bytes are gone from the final layer instead of dead weight in an earlier one) — but it also destroys the layer-sharing story: a squashed image can no longer share common layers with siblings built from the same base, so a registry or node pulling many of your squashed images can end up transferring and storing more total bytes, not fewer. The candidate answer that scores well distinguishes "smaller image" from "smaller total transfer/storage across your fleet," and reaches for multi-stage builds (unit 03) first, since they avoid ever creating the bloat rather than squashing it away after the fact.

Try it

1. Build the same Dockerfile twice, changing only a comment in the source after the dependency-install line; time both builds and confirm the second reuses cache up to that line. 2. Then move the COPY . . above the dependency install and repeat — watch cache stop helping at all.

What you should observe

With manifest-only copied first, the second build's RUN npm ci line shows CACHED in the BuildKit output and the whole build finishes in well under a second past the final COPY. With source copied first, any source change — even a comment — changes the digest BuildKit hashes for that COPY layer, which invalidates it and every layer after, so npm ci reruns on every build regardless of whether dependencies actually changed. This single reordering is the highest-leverage Dockerfile change most teams can make and often the first thing worth checking in a slow-CI complaint.

What exactly does copy-on-write mean for a file that's 2 GB in a lower layer and you change one byte of it?

OverlayFS's copy-up is whole-file, not block-level: modifying any byte of that file copies the entire file up into the writable layer before applying the change, so a one-byte edit to a 2 GB file costs a 2 GB copy and briefly doubles that file's disk usage. This is a genuinely bad interaction with large mutable files (databases, log files) living inside the writable layer, and it's the practical reason "put your data directory on a volume" is not just a persistence best practice but a performance one — volumes bypass the union filesystem and its copy-up cost entirely.

Why are Docker image digests SHA-256 of the content, and what does that buy you over a mutable tag like latest?

A digest is a cryptographic function of the exact bytes, so two things with the same digest are provably identical and a digest can never be silently repointed — which is exactly what a tag can be. myapp:latest is a mutable pointer someone can docker push over at any time; myapp@sha256:abcd... is immutable by construction. The practical consequence for a lead: any deployment manifest, Helm chart, or Kubernetes pod spec that cares about reproducibility and auditability should pin by digest, not tag, and "which digest is running in prod right now" should always be a one-command answer, not an investigation.

What's the difference between ADD and COPY, and why does the current guidance say to avoid ADD?

COPY does exactly one thing: copies files/directories from the build context (or, with BuildKit, from another stage or image) into the image. ADD does that plus two extra, surprising behaviors: it auto-extracts local .tar/.tar.gz/etc. archives into the destination, and it can fetch a remote URL directly into the image. Both extra behaviors are footguns in practice — auto-extraction hides what layer content actually is, and fetching a URL at build time means your build isn't reproducible or offline-capable and skips any credential/verification step you'd normally want. Current guidance is COPY by default, ADD only for the narrow local-archive-extraction case where you deliberately want that behavior and understand it.

Why does docker system df sometimes show gigabytes of "reclaimable" space, and where does it come from?

Three usual sources. Dangling images — layers left over from superseded builds that no tag points to any more, typically from repeated docker build without cleanup. Build cache — BuildKit deliberately retains intermediate layers to make the next build fast, and that cache has no automatic size cap by default. And stopped containers' writable layers, which persist until docker rm even though the container isn't running. docker system prune (and its more aggressive -a --volumes variant) reclaims these, but I never run the aggressive form on a shared host without checking what "unused" volumes actually are first — an unused-to-Docker volume can still be someone's only copy of data.

How do multi-platform (multi-arch) image manifests actually work under the hood?

A multi-platform tag doesn't point at one image — it points at an OCI/Docker "manifest list" (a.k.a. image index): a small JSON document listing several platform-specific manifests (linux/amd64, linux/arm64, etc.), each with its own digest and its own layer set. When you docker pull or docker run a multi-platform tag, the client reads the manifest list and the daemon automatically selects the manifest matching the host's architecture — you never see the ones that don't apply. Building one requires buildx (unit 04); a plain docker build with the classic builder only ever produces a single-platform image.

Your image is 1.8 GB and a teammate's equivalent Go service is 12 MB. What's actually different?

Almost certainly the base image and what's left in the final layer, not the application code. A common full-fat base like ubuntu or node:22 carries a whole userland — package manager, shells, compilers, docs — most of which a running service never touches. The Go binary case is the extreme end of a real spectrum: statically linked, it needs no runtime at all, so it can run FROM scratch or FROM gcr.io/distroless/static with nothing else in the image. For anything with a real runtime dependency (Node, Python, JVM), the achievable middle ground is a slim or distroless base plus a multi-stage build that discards the compiler toolchain, dev dependencies, and package manager caches from the final stage — 1.8 GB down to 150–300 MB is a realistic, unglamorous win most teams haven't done.

What is a "distroless" image and when would you not use one?

A distroless image ships only an application and its direct runtime dependencies — no shell, no package manager, no coreutils — which shrinks both attack surface and size, and is one of the ideas Docker Hardened Images build on (unit 10). The cost is operational: no shell means docker exec sh for live debugging doesn't work, and any deployment tooling that assumes it can curl or cat from inside the container breaks. My rule of thumb: distroless for stable, well-observed production services where you debug via logs/traces, not live shells; a slim-but-not-distroless base while a service is new enough that you're still routinely shelling in to figure out what's wrong.

How would you estimate, without pulling anything, whether two images share layers?

docker manifest inspect (or skopeo inspect) against the registry returns each image's layer digest list without downloading layer contents; a shared base shows up as identical leading digests. Practically, I care about this when deciding whether to standardize a team on one base image tag — if ten services all build FROM company/base:22, a node pulling all ten only ever downloads that base's layers once, and CI build agents warm-cache it once, which is a real, measurable cost saving at fleet scale that's invisible if you only ever look at one image's size in isolation.

Why is .dockerignore a build-cache concern and not just a "keep secrets out" concern?

The build context — everything BuildKit is allowed to see for COPY/ADD — is hashed and sent to the builder (or, for a remote builder, over the network) on every build; a .git directory, node_modules, or build artifacts left un-ignored bloats that context and, worse, its contents feed into cache-key hashing for any COPY . instruction. A stray file that changes on every build (a log, a lockfile regenerated with volatile ordering) inside an un-ignored path can silently defeat caching for everything after it, which is a frustrating one to diagnose because the Dockerfile itself never changed.

Lead-level: how do you get a whole org's Dockerfiles converging on one small set of approved base images without a mandate nobody follows?

Make the approved path strictly easier than the alternative, and make drift visible. Concretely: publish a small internal registry of pre-approved, pre-hardened base images (often just re-tagged Docker Hardened Images with an internal name), provide a copy-pasteable Dockerfile snippet and a lint rule (hadolint or a custom OPA/Conftest policy) that flags FROM lines outside the approved set in CI, and pair that with a Scout- or Trivy-based dashboard showing CVE counts per image across the org so the cost of non-compliance is visible to the team owning it, not just to platform. I've seen mandates alone fail repeatedly; visible, comparative CVE dashboards combined with a genuinely lower-friction approved path is what actually moves the median.

03 Dockerfiles that scale: multi-stage builds and BuildKit

Since Docker 23.0, docker build is buildx build under the hood by default, which means BuildKit — not the legacy builder — is what actually executes every Dockerfile you write today, and it changes how you should think about a Dockerfile: not as a sequential script, but as the source for a build graph. BuildKit parses the Dockerfile into a DAG of operations, figures out which nodes are independent, runs them in parallel, and caches each node by the content hash of its inputs (base image digest, prior layer digest, instruction text, and any files it copies in). This is why two unrelated RUN chains in a multi-stage build — say, compiling a frontend bundle and compiling a backend binary — genuinely execute concurrently, something the old builder never did.

Multi-stage builds are the single highest-leverage Dockerfile pattern and the direct answer to "my image has a whole compiler toolchain in it for no reason." A Dockerfile can declare multiple FROM lines, each starting a new, independently-cached stage; later stages pull specific artifacts from earlier ones with COPY --from=stagename, and only the final stage becomes the shipped image. The compiler, the test runner, the dev dependencies — everything that produced the artifact — simply never exists in the final layer set, because it was never COPY'd there. This is strictly better than squashing (unit 02) because the bloat is never created in the shipped image's history at all, rather than being created and then hidden.

Three BuildKit-only Dockerfile features are worth having cold, because they each fix a real, common mistake: cache mounts (RUN --mount=type=cache,target=/root/.npm) persist a directory across builds without it becoming part of any image layer — the package-manager download cache survives even though the Dockerfile has no line that copies it in or out. Secret mounts (RUN --mount=type=secret,id=npmrc,target=/root/.npmrc) make a credential available to exactly one RUN step's filesystem, never written to any layer, versus the old and still-too-common anti-pattern of ARG/ENV or a plain COPY of a credentials file, both of which bake the secret into image history forever even if a later step deletes it. Heredocs (RUN <<EOF ... EOF) let a multi-line script be one readable block instead of an unreadable chain of && and \ continuations, with no change in caching behavior.

# syntax=docker/dockerfile:1
FROM golang:1.24 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build -o /out/app .

FROM gcr.io/distroless/static-debian12 AS final
COPY --from=build /out/app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]

Interview trap

Candidates often say "multi-stage builds reduce image size" and stop there, missing the security half interviewers are often fishing for: a stage that never ships is a stage whose vulnerabilities never ship either. A build stage can have a stale, CVE-riddled compiler toolchain and it's irrelevant to your runtime image's CVE scan, because that stage's layers are never part of the final image and never get pushed. Naming both the size and the CVE-surface benefit, unprompted, is what separates "read a tutorial" from "operates this in production."

Try it

1. Take a Dockerfile that installs a package manager's dependencies with a plain RUN npm ci and no cache mount; time a from-scratch build (docker builder prune -a first). 2. Add --mount=type=cache,target=/root/.npm to the same line, prune the build cache except the cache mount cannot be pruned by builder prune the same way, and compare a second from-scratch (image-cache-cleared) build's time.

What you should observe

Without a cache mount, every dependency has to be re-downloaded from the registry on every build that misses the layer cache — a full node_modules reinstall from a clean state. With a cache mount, BuildKit persists /root/.npm in a separate, named build-cache volume that survives even when the image layer cache is invalidated (e.g. by a lockfile change), so the package manager finds most packages already downloaded locally and only fetches the delta — often turning a 40-second install into a 3-second one, even on a build that otherwise starts from zero.

Why does the Dockerfile need # syntax=docker/dockerfile:1 at the top, and what breaks without it?

That directive pins which BuildKit Dockerfile frontend parses the file — Dockerfile syntax isn't hardcoded into BuildKit, it's itself a pluggable, versioned frontend distributed as an image, which is how features like heredocs, cache mounts and secret mounts shipped without needing a new Docker Engine release. Without the pin, BuildKit falls back to whatever frontend version it bundles by default, which is usually recent enough for basic syntax but can lag the newest features and, more importantly, means your build's behavior can drift as the daemon's bundled default changes over time. Pinning docker/dockerfile:1 (the floating "1.x latest" tag) is the pragmatic default; pinning an exact 1.7.0-style tag is what a team with strict reproducibility requirements does instead.

What's the actual difference in caching semantics between ARG and ENV?

ARG is build-time-only by default — available during the build, not present in the final image's runtime environment — while ENV persists into the running container. Both participate in cache invalidation: changing an ARG's value (or an ENV derived from one) invalidates the cache for every subsequent instruction, same as changing a RUN command's text would. The trap is assuming ARG values are secret because they're "build-time only" — they're not: an ARG's value is recorded in the image's build history and inspectable with docker history unless you take deliberate steps, which is precisely why secret mounts exist as a separate mechanism rather than "just use ARG."

When would you deliberately break BuildKit's parallelism by adding a dependency between stages that don't actually need one?

Rarely, but it happens for resource-contention reasons: if two independent stages both spin up heavy, memory-hungry compilation (a large C++ build and a large Rust build, say) on a resource-constrained CI runner, running them in true parallel can thrash memory or disk I/O badly enough that serializing them with an artificial COPY --from dependency is faster in practice than the "correct" parallel graph. This is the exception, not the rule — I only reach for it after profiling shows contention, since undoing real parallelism for imagined contention is a common premature "optimization" that just makes builds slower for no reason.

How do you keep a private registry credential out of both the image and the build logs?

Secret mounts solve the image-layer half (RUN --mount=type=secret,id=creds,target=/root/.npmrc npm ci — the file exists only for that RUN's filesystem view and is never committed to a layer), but the logs half needs separate care: BuildKit doesn't echo secret values automatically, but a command that itself prints the secret (a misconfigured set -x, a tool that logs its auth header) will leak it into build output regardless of the mount type. I treat "does this command ever print what it received" as part of the review, not just "is the credential mounted correctly" — the mount mechanism and log discipline are two different controls for two different leak paths.

Your multi-stage Dockerfile's final image still contains a package manager's cache and lockfile-adjacent cruft. Why, and how do you fix it?

Almost always because the final stage's COPY --from=build is copying a directory that itself contains the cruft (e.g. copying the whole /app working directory instead of just the built artifact), or the final stage runs its own RUN apt-get install without cleaning the cache in that same layer. The fix is precision: COPY --from=build /out/app /app naming the exact artifact rather than a whole directory, and for any package installs that must happen in the final stage, chaining the cache cleanup into the same RUN instruction so it lands in the same layer rather than a separate one that can't undo a prior layer's size.

What's the difference between BuildKit's cache and Docker Compose's build.cache_from, and do you need both?

They're the same underlying mechanism at different scopes. BuildKit's own layer/content cache is local to wherever the builder runs; cache_from/cache_to (in a Dockerfile build or a Compose build: block) tells BuildKit to additionally import/export cache to an external location — a registry, GitHub Actions cache, or a local directory — so that a fresh CI runner with no local cache can still benefit from a previous run's cache. You need the external cache config specifically for ephemeral build environments (most CI); for a long-lived developer machine or a persistent CI cache volume, BuildKit's local cache alone already does the job.

Why does adding a seemingly unrelated RUN apt-get update near the top of a Dockerfile sometimes fix a "package not found" error that looked intermittent?

Layer caching can serve a stale apt-get update result: if that instruction's layer was cached from days or weeks ago, the package index inside it is that old, and a package that's since been added, renamed, or moved to a different repo section will 404 even though the live upstream mirror has it. The fix isn't really "add an update" — it's understanding that update and install belong in the same RUN instruction (so cache invalidation of one invalidates both together) and that a long-lived cached update layer is the actual bug, not the missing package. A cache-busting ARG CACHEBUST=1 trick or periodic --no-cache rebuilds are the pragmatic mitigations for base images that go stale between real Dockerfile changes.

Should test execution live inside the Dockerfile as a build stage, or outside it in CI?

I lean outside, with a caveat. A test stage that runs inside the multi-stage build (and whose failure fails the build) guarantees tests ran against exactly the environment being shipped and can't be skipped by a misconfigured CI step — genuinely valuable for supply-chain-conscious teams. The cost is build-graph coupling: test execution is usually far slower than compilation, and bundling it into the image build means every image build pays that cost, including local "just let me try this" builds, and the image build's own cache semantics (rebuild on any source change) don't line up well with what you actually want from test caching (rerun on any logic change). My default is tests in CI, outside the Dockerfile, with the image build gated on CI passing rather than the image build itself running tests — but I don't fight a team that prefers the stricter, coupled version for a genuinely high-stakes artifact.

Lead-level: a 40-minute Docker build in CI is blocking every PR. Where do you actually look first?

Before touching the Dockerfile at all, I check whether the CI runner has any persistent cache at all — a huge fraction of "slow Docker build" complaints are simply "every CI run starts from a cold cache," which no Dockerfile restructuring fixes, only --cache-from/--cache-to against a registry or the CI-native cache backend does. Once caching exists, I profile with BuildKit's own timing output (each step reports its wall time) to find the actual long pole — it's very often one under-cached dependency-install step, not a diffuse "everything is slow" problem. Only after those two are addressed do I reach for restructuring: splitting independent concerns into parallel stages, moving rarely-changing setup earlier, or, if the codebase genuinely warrants it, splitting one monolithic build into per-service builds that only run when their own path changed.

04 Buildx, Bake and multi-platform builds

buildx is the CLI plugin that gives Docker's build system everything the classic builder never had: a driver model (where does BuildKit actually run — locally in a container, remotely, in Docker Build Cloud), multi-platform output from a single invocation, and a declarative alternative to long docker build command lines called Bake. Since Docker 23, docker build silently is docker buildx build with the default driver — most developers use buildx every day without ever typing the word. Where it becomes a deliberate choice rather than invisible plumbing is multi-platform builds, remote/shared builders, and Bake-driven multi-target builds, which is where this unit lives.

Building for a platform your host can't natively execute has two genuinely different strategies, and conflating them is a common mistake. Emulation (via QEMU and binfmt_misc, unit 01) lets every instruction in the Dockerfile run as if native, just slowly — correct for anything, including running arbitrary compilers, but one to two orders of magnitude slower for CPU-bound steps. Cross-compilation uses BuildKit's automatic TARGETPLATFORM/BUILDPLATFORM build args plus a toolchain that natively supports cross-compiling (Go and Rust both do this well) to build an arm64 binary on an amd64 host with no emulation at all for the compile step — only the final, cheap step of assembling the image needs any platform awareness. A well-written multi-stage Dockerfile for a compiled language should nearly always cross-compile in the build stage and only "become" the target platform in the final, mostly-static-copy stage.

Bake replaces a Makefile of ever-growing docker build --build-arg ... --platform ... --tag ... invocations with a single declarative file (HCL by default, docker-bake.hcl, or JSON/Compose-compatible) describing named targets, their inheritance, and shared variables — then docker buildx bake builds however many targets you name, in parallel, sharing cache between them where the graph allows it. What's genuinely new since 2026: buildx 0.37 added a first-class cloud driver, letting a builder instance point straight at Docker Build Cloud without any custom binary or manual remote-builder setup, and 0.37 also made newly-started container builders wait for BuildKit readiness before their first use — a small but real reliability fix for the "first build after buildx create randomly fails" complaint teams used to work around with retry loops.

// docker-bake.hcl
variable "TAG" { default = "dev" }

group "default" { targets = ["api", "worker"] }

target "base" {
  context = "."
  args = { BUILDKIT_INLINE_CACHE = "1" }
}

target "api" {
  inherits = ["base"]
  dockerfile = "api/Dockerfile"
  tags = ["registry.example.com/api:${TAG}"]
  platforms = ["linux/amd64", "linux/arm64"]
}

target "worker" {
  inherits = ["base"]
  dockerfile = "worker/Dockerfile"
  tags = ["registry.example.com/worker:${TAG}"]
}

# Cross-compiling Go instead of emulating the whole build
FROM --platform=$BUILDPLATFORM golang:1.24 AS build
ARG TARGETOS
ARG TARGETARCH
WORKDIR /src
COPY . .
RUN --mount=type=cache,target=/root/.cache/go-build \
    GOOS=$TARGETOS GOARCH=$TARGETARCH CGO_ENABLED=0 go build -o /out/app .

FROM --platform=$TARGETPLATFORM gcr.io/distroless/static-debian12
COPY --from=build /out/app /app
ENTRYPOINT ["/app"]
Gotcha

Writing FROM golang:1.24 with no --platform in a multi-platform build looks harmless but silently defeats cross-compilation: BuildKit will emulate that stage for every non-native target platform, because nothing told it the stage's tools can run on the build host and target a different OS/arch. The fix is the pair shown above — --platform=$BUILDPLATFORM on the build stage (run it natively, on the host's real architecture) and --platform=$TARGETPLATFORM (or nothing, since it's the default) on the final stage — and it's the single most common reason someone's "multi-arch build" is mysteriously slow despite having "done cross-compilation."

Try it

1. Build a small Go service for linux/amd64,linux/arm64 two ways: with --platform=$BUILDPLATFORM on the build stage, and without it. Compare wall time. 2. Inspect the resulting multi-platform tag with docker buildx imagetools inspect.

What you should observe

The $BUILDPLATFORM-pinned version builds both architectures in roughly the time of one native compile plus a fast cross-compile, often several times faster than the unpinned version, which emulates the entire non-native compile through QEMU. imagetools inspect shows the manifest list: one digest per platform under a single tag, confirming both were actually produced and pushed as a coherent multi-platform artifact rather than the last --platform silently overwriting the first.

What are the buildx "driver" options and when do you reach for something other than the default?

The default docker-container driver runs BuildKit inside a local container — fine for most work, and what gives you multi-platform output on a single machine via emulation. A remote driver points at a BuildKit instance running elsewhere (useful for a fleet of native-arch build machines you already operate). Docker Build Cloud's cloud driver, first-class since buildx 0.37, offloads the build entirely to Docker's managed, always-warm-cache remote builders — the pitch is CI build times that don't regress to a cold cache on every ephemeral runner, at the cost of a subscription and data leaving your infrastructure. There's also a kubernetes driver for teams that want build capacity scaled the same way they scale everything else. I reach past the default when either cold-cache CI time is a measured, real cost, or when a genuinely native arm64 build host is needed because emulation is too slow for a compile-heavy image.

How does BuildKit decide what's "the same" cache key across a cross-compiled multi-platform build?

Cache keys are computed per build graph node and include the resolved platform as part of their identity, so the amd64 and arm64 branches of a cross-compiling build are cached independently — a change that only affects one architecture's output (rare, but possible with platform-specific code paths) only invalidates that platform's cache. This is different from, and often confused with, image-layer digests: two platforms' final layers are never identical (different binaries), but shared early stages — say, a common COPY go.mod go.sum ./ — can still share cache across platforms if their inputs are genuinely identical.

What's the practical difference between --cache-to type=inline and --cache-to type=registry?

inline embeds cache metadata directly in the pushed image's own manifest — zero extra artifacts, but limited to caching only what ends up in the final exported image, so intermediate/build-only stages aren't cached this way. type=registry pushes a separate cache manifest (optionally to a dedicated cache repository) and can cache intermediate stages too, at the cost of an extra push and a second thing to manage/expire in your registry. For a simple single-stage-that-matters build, inline is less operational overhead; for a real multi-stage build where the expensive work happens in a stage that's discarded from the final image, registry-backed cache is what actually speeds up the next build.

Why would Bake share cache between the api and worker targets in the example above, and why might it not?

It shares cache when their build graphs genuinely overlap — both inherits = ["base"], and if both Dockerfiles start with identical early instructions against identical inputs (same base image, same dependency-install step), BuildKit's content-addressed cache recognizes the duplication and only executes it once, regardless of which target "asked" for it first. It won't share past the point where the Dockerfiles diverge — different application source, different final dependencies — which is exactly the layer-invalidation behavior from unit 02, just now visibly paying off across multiple targets in one bake invocation instead of within one Dockerfile.

A build that works fine locally fails only in CI with a QEMU-related error. What's the likely cause and fix?

Almost always a missing or mismatched binfmt_misc registration on the CI runner — Docker Desktop configures this automatically for you locally, but a bare Linux CI runner needs an explicit docker run --privileged --rm tonistiigi/binfmt --install all (or the equivalent GitHub Actions docker/setup-qemu-action) before a multi-platform build can emulate anything. The other frequent cause is a CI runner that's already inside a container without the privileges needed to register binfmt handlers — nested-virtualization or sandboxed CI environments sometimes block this outright, which is one more reason to prefer cross-compilation over emulation wherever the toolchain allows it: it needs no QEMU or elevated privileges at all.

What does docker buildx bake --print buy you that you'd miss without it?

It resolves the entire Bake file — variable interpolation, target inheritance, group expansion — into the flat set of build invocations that would actually run, without running them. I use it constantly during Bake file changes to catch mistakes that are invisible in the HCL itself: a variable that silently defaulted because an env var wasn't exported, an inheritance chain that didn't override what you expected, or a group that expanded to more (or fewer) targets than intended. Treating a Bake file as "obviously correct because it looks right" is a bad habit — --print is the equivalent of terraform plan and costs nothing to run first.

How do provenance and SBOM attestations get attached during a buildx build, and what do they actually contain?

docker buildx build --provenance=true --sbom=true (or Bake's equivalent target attributes) tells BuildKit to generate, alongside the image, an in-toto/SLSA-style provenance attestation — recording the build's inputs, the builder identity, and the exact steps taken — and a Software Bill of Materials enumerating packages and versions detected in the final image. Both are stored as extra manifests referenced from the image's manifest list (or as a separate referrers entry), inspectable with docker buildx imagetools inspect --format '{{json .SBOM}}'. This is the mechanism Docker Hardened Images (unit 10) build on, and increasingly what supply-chain policy tooling (in-toto verification, admission controllers) checks before letting an image run in a regulated environment.

Why might a team standardize on Bake even for single-target builds, rather than only adopting it once they have multiple images?

Mainly for the variable/inheritance ergonomics and the fact that a Bake file is a reviewable, diffable artifact in version control, versus build flags scattered across a Makefile, a CI YAML file, and a README's "remember to also pass --build-arg" note that inevitably drifts. Even a single target benefits from named, typed variables with defaults, and it's a much smaller migration to add a second target later if the team already thinks in Bake rather than retrofitting it under time pressure once a second service shows up.

What's the risk of pointing CI at Docker Build Cloud's shared remote builders for a codebase with proprietary source?

The build context and any secrets mounted during the build leave your infrastructure's network boundary, which is a real data-residency and compliance question, not a hypothetical one — the same conversation you'd have before adopting any managed CI/build SaaS. Docker's contractual answer is standard SaaS data-handling terms and isolation between tenants' builders, but "contractually isolated" and "physically on infrastructure we control" are different risk postures, and which one a given org needs is a decision for security/compliance, not something to default into because it's the fastest CI fix available.

Lead-level: how would you decide whether a growing monorepo needs Bake groups, or whether that's premature structure?

I look for the actual pain, not the theoretical elegance: are people already hand-writing near-duplicate docker build invocations for each service in a Makefile or CI YAML, and is that duplication causing real drift (one service's build quietly missing a flag the others have)? If yes, Bake groups pay for themselves immediately — one file, inheritance instead of copy-paste, and --print as a review tool. If a monorepo has two services with genuinely different build needs and no shared base, forcing them into a shared Bake file's inheritance model just to have "one file" can obscure more than it clarifies. The tell I actually use: if I can't describe the shared "base" target in one sentence, the services probably don't share enough to warrant one.

05 The runtime: namespaces, cgroups, rootless

Everything about container isolation reduces to two independent Linux kernel mechanisms, and being able to say precisely which mechanism handles which concern is the fastest way to sound senior on this topic. Namespaces answer "what can this process see": PID (its own process tree, starting at PID 1), NET (its own network stack — interfaces, routing table, iptables rules), MNT (its own filesystem mount table), UTS (its own hostname), IPC (its own shared memory/semaphores), and USER (its own UID/GID mapping, the one rootless mode depends on). Cgroups (control groups, now overwhelmingly v2) answer "how much can it use": CPU shares and quotas, memory limits and OOM behavior, block I/O weight, and pids-count limits, all enforced by the kernel regardless of what the process inside believes about its own resources.

The two are genuinely orthogonal, and mixing them up is a real interview trap: a container with no memory cgroup limit set can still see (via /proc/meminfo, unless it's masked) the host's total memory, believe it has that much available, and get OOM-killed by the kernel the instant it tries to actually use more than its unset-but-still-real default — while a container with namespaces disabled entirely (--pid=host, say) can still have a perfectly enforced memory limit. Debugging "my container thinks it has 64 GB but only gets 2 GB before dying" is a namespace-visibility problem; debugging "my container got killed with no OOM message in its own logs" is a cgroup-limit problem the container often can't even see was applied.

What's genuinely current: cgroup v2 has been the default on any modern distro (Ubuntu 22.04+, RHEL 9+, Debian 11+) for years now, and Docker Engine 29.0 formally deprecated cgroup v1 support — it still works, patched through May 2029, but any new host should assume v2, and any runbook or monitoring dashboard still assuming v1's per-controller file layout (/sys/fs/cgroup/memory/... versus v2's unified /sys/fs/cgroup/...) needs updating. Rootless mode — running the entire Docker daemon and every container as an unprivileged host user, via a user namespace that remaps container UID 0 to an unprivileged host UID — has been stable and packaged since Docker 20.10 and remains the strongest "what if the container breaks out" mitigation available without reaching for a different runtime entirely, at a real cost: it needs subordinate UID/GID ranges configured per user, some storage drivers and networking setups behave differently (slower userspace networking via slirp4netns/RootlessKit unless you configure a faster alternative), and binding ports below 1024 needs an explicit capability grant it doesn't have by default.

docker run -d --name api \
  --cpus="1.5" --memory="512m" --memory-swap="512m" --pids-limit=200 \
  myapp:latest

# See what the kernel is actually enforcing, not what the flag said

A container's process shows PID 1 inside the container but a large number on the host. Why does that matter beyond curiosity?

It matters because PID 1 has special kernel responsibilities — it's expected to reap zombie child processes and it receives signals differently (a bare SIGTERM is not delivered with a default handler the way it is for other PIDs unless the process explicitly handles it). Many application binaries were never written expecting to run as PID 1, so docker stop sending SIGTERM can be silently ignored, forcing a slow fallback to SIGKILL after the timeout, and orphaned child/zombie processes inside long-running containers can accumulate. The standard fix is a minimal init (--init flag, which injects tini) or an application-level signal handler — "why does my container take exactly 10 seconds to stop every time" is almost always this.

How does the kernel decide which process to kill when a container's memory cgroup hits its limit, and can you influence it?

The kernel's OOM killer picks a victim based on badness scores influenced by memory usage and an adjustable oom_score_adj; inside a cgroup-limited container, the kill is scoped to processes within that cgroup, so a memory-hungry sidecar-style process inside the same container can be killed before your main process is, not necessarily the biggest overall consumer on the host. You can influence priority per-container with the daemon's --oom-score-adjust-equivalent settings, but the more reliable lead-level answer is architectural: one process per container wherever practical, so an OOM kill has an unambiguous, restartable target instead of taking down a multi-process container's healthy work alongside the actual offender.

What's the difference between a Linux capability and a seccomp profile, concretely?

Capabilities are coarse-grained permission bits layered on top of the traditional root/non-root split — CAP_NET_BIND_SERVICE lets a non-root process bind low ports, CAP_SYS_ADMIN is a notoriously broad grab-bag many "just add this" fixes reach for without realizing how much it grants. Seccomp is finer-grained and orthogonal: it's a syscall allow/deny filter, independent of capabilities entirely — Docker's default seccomp profile blocks around 40+ syscalls outright (things like keyctl, raw mount, kernel-module loading) regardless of what capabilities a process holds, because some syscalls are dangerous enough to block by default even for a process that's technically privileged. A hardened container config layers both: drop capabilities to the minimum needed (--cap-drop=ALL --cap-add=...), and leave the default seccomp profile in place rather than disabling it for convenience.

Why is rootless Docker's networking sometimes noticeably slower, and how do you fix it?

Without a real NET namespace mapping to privileged host networking setup, rootless mode by default routes traffic through a userspace network stack (slirp4netns, historically, or RootlessKit's VPNKit-style backend) that adds a genuine per-packet overhead versus the kernel's native bridge networking a rootful daemon uses. The fix, where the host allows it, is switching RootlessKit's port-forwarding/network mode to a faster backend (--net=lxc-user-nic\-based setups, or a newer pasta-based network mode where available) which gets much closer to native throughput at the cost of slightly more host configuration. This is a real, measurable trade-off to name when someone proposes "just run everything rootless" as a blanket security win — it usually is a net win, but not a free one.

Your host is on cgroup v1 and a teammate's is on cgroup v2 — what actually breaks, versus what just looks different?

Most application-level behavior is identical — Docker abstracts the controller differences for the common flags (--memory, --cpus) so a typical docker run behaves the same either way. What breaks is anything that reaches past Docker's abstraction directly into /sys/fs/cgroup: v1's per-controller hierarchy (/sys/fs/cgroup/memory/docker/<id>/memory.limit_in_bytes) versus v2's single unified hierarchy with differently-named files (memory.max instead of memory.limit_in_bytes) means any custom monitoring script, sidecar, or debugging one-liner written against v1's paths silently returns nothing (or errors) on v2, and vice versa. This is exactly the kind of "it works on my machine" bug that only shows up when a runbook written years ago meets a host provisioned this year.

How do gVisor and Kata Containers change the security model versus plain runc, and when do you reach for them?

Both intercept the layer that runc leaves shared: the kernel itself. gVisor (runsc) implements a userspace kernel that intercepts syscalls and re-implements the ones it allows, so even a full kernel exploit inside the sandbox mostly can't reach the real host kernel — at some CPU/syscall-emulation performance cost. Kata Containers goes further, running each "container" inside a lightweight, hardware-virtualized micro-VM with its own real (but minimal) kernel, giving VM-grade isolation with container-like tooling and startup time close to (but not equal to) a plain container. I reach for either specifically for genuinely untrusted or multi-tenant workloads — running third-party or user-submitted code — where the blast radius of a kernel-level container escape is unacceptable; for trusted first-party services, the operational and performance cost usually isn't worth it over well-configured runc plus seccomp/capabilities/rootless.

What does "the container sees the host's CPU count" cause in practice, and how do you fix it for a specific runtime?

A cgroup CPU quota limits how much CPU time a container can consume, but many language runtimes size their default thread/worker pools off /proc/cpuinfo or nproc, which report the host's full core count regardless of the container's cgroup quota — a container limited to 1 CPU on a 64-core host can still spin up 64 garbage-collector or thread-pool workers, thrashing far past its actual quota's effective throughput. The fix is runtime-specific: recent JVMs are cgroup-aware by default and size correctly out of the box, while Node's UV_THREADPOOL_SIZE, Go's GOMAXPROCS, and various thread-pool configs in other runtimes may need an explicit override tied to the same number you set in --cpus, or the container will misbehave in a way that's invisible until you specifically go looking for it.

Lead-level: a security review flags every service running as root inside its container. How do you drive that fleet-wide fix without breaking things?

I'd sequence it rather than mandate a flag-day switch. First, an audit distinguishing images that already run non-root but were overridden at deploy time (a quick, low-risk fix — just stop overriding USER) from images that genuinely need root inside the container (binding privileged ports, writing to root-owned paths baked into the image) from images nobody's checked yet. Second, fix the easy majority by adding a USER appuser line and testing in staging — this alone usually resolves 70–80% of a typical fleet. Third, for the genuine holdouts, look for the underlying cause (a privileged port that should be handled by a proxy, a directory owned by root at build time that should be chown'd to the app user in the same Dockerfile layer) rather than accepting root as permanent. I'd track this as a CVE-dashboard-style burndown, same instinct as the base-image convergence problem in unit 02 — visible, incremental, not a big-bang mandate that stalls on the 20% of hard cases.

06 Networking: drivers, DNS, port publishing

Docker's networking is built on the Container Network Model (CNM), and the practical entry point is the driver you pick when you create a network: bridge (the default — an isolated virtual switch on the host, one per network, NATed to the outside world), host (no isolation at all — the container shares the host's network namespace directly), overlay (a VXLAN-backed network spanning multiple Docker hosts, used by Swarm), macvlan/ipvlan (the container gets its own MAC/IP directly on the physical network, no NAT, common in network-appliance and some on-prem setups), and none (no networking at all, for batch jobs that genuinely need isolation from the network entirely). Every container you run without specifying --network lands on the default bridge network unless you've created and attached a custom one — and that default bridge is worth actively avoiding for anything beyond a quick manual test, for reasons the next paragraph covers.

The most consequential, least-obvious behavior in Docker networking is that the default bridge network has no built-in DNS-based service discovery, and every user-defined bridge network does. On the default bridge, containers can only reach each other by IP (or via the legacy, deprecated --link flag), and those IPs are not stable across restarts. On a user-defined network, Docker runs an embedded DNS server (at 127.0.0.11 inside each container) that resolves other containers' names to their current IP automatically — curl http://api:8080 from a container named worker just works, with no manual IP tracking, as long as both are on the same user-defined network. This single fact is why "create a custom network and attach your services to it" is close to a universal first recommendation, and it's also exactly what Compose does for you by default (unit 08) — Compose creates a project-scoped user-defined bridge network automatically, which is why service-name-based discovery "just works" in Compose but silently doesn't in a hand-written docker run without --network.

Port publishing (-p host:container) is not the same thing as EXPOSE in a Dockerfile — EXPOSE is documentation and a hint to tools (it does nothing to actually open a port), while -p is what creates the real, enforced path. Under the hood, publishing a port programs the host's packet filter — iptables rules historically, and increasingly nftables as distros migrate their default backend — to DNAT traffic arriving on the host's port to the container's internal IP and port. This has a real, frequently-misunderstood consequence: those NAT rules bypass any host firewall rule you might have written to block that port, because Docker's rules are typically inserted with higher priority than a generic host firewall's default chain — "I blocked port 5432 in ufw but it's still reachable" is almost always this, not a bug.

Why does Docker's embedded DNS run at 127.0.0.11 specifically, and what happens if a container's app hardcodes a different resolver?

127.0.0.11 is a fixed, Docker-chosen address written into each container's /etc/resolv.conf on a user-defined network, proxying to the daemon's actual DNS resolution logic (which knows about container names, network aliases, and falls through to the host's real upstream DNS for external names). An application that hardcodes a different resolver, or that caches DNS aggressively at startup and never re-resolves, breaks the "container IPs can change on restart, names stay stable" contract Docker's networking is built around — a container that resolved db once at boot and cached that IP forever will silently talk to a stale, possibly now-nonexistent address after the database container restarts and gets a new IP.

What's the actual risk of --network=host, beyond "it's less isolated"?

Concretely: the container can bind any port the host itself could bind, including ones your other services or the host's own management tools use, with no Docker-level protection against a collision; it can see and potentially interfere with every network interface and route on the host, including ones on other VLANs the host straddles; and any container-side vulnerability that achieves arbitrary network access has that access at the host's actual network position, not a NATed, firewalled slice of it. It's a legitimate choice for specific cases (a network monitoring tool that needs to see host-level traffic, or squeezing out NAT overhead for genuinely network-bound workloads), but "I used host networking because I couldn't figure out port publishing" is a red flag, not an optimization.

How would you connect two containers running under different Compose projects (different default networks) without exposing ports to the host?

Create a shared, externally-defined user-defined network first (docker network create shared-net), then in each Compose file declare that network as external: true and attach the relevant service to it alongside its project's own default network — a service can be on multiple networks simultaneously. This gets you name-based discovery across project boundaries with no host port exposure at all, which is the right shape for, say, a shared internal API gateway that several independently-deployed Compose stacks need to reach without any of that traffic touching the host's public interfaces.

Your host migrated from iptables to nftables as the default backend. What, if anything, should change in how you reason about Docker's port publishing?

Conceptually nothing — Docker still programs NAT rules to achieve the same DNAT-on-publish behavior, just through a different backend API depending on the Engine version and host configuration (recent Engine versions increasingly manage this through nftables directly or via iptables-nft compatibility shims). Practically, anything that used to inspect rules with raw iptables -t nat -L for debugging may need the nftables-native equivalent (nft list ruleset) if the host has fully switched, and any custom firewall automation that assumed the legacy iptables rule ordering/priority Docker relies on should be re-verified against the new backend rather than assumed to behave identically.

Why can two containers on the same user-defined bridge network sometimes still not reach each other, even with correct names and no firewall involved?

The most common non-obvious cause is that they're actually on different networks that merely look similar — a typo'd network name creating a second, distinct network with a similar name, or one container attached via docker network connect after the fact to a network the other was never actually placed on despite both Compose services appearing to share a networks: block (a scoping mismatch between top-level and per-service network names is a classic Compose-specific version of this). The fast diagnostic is docker network inspect <name> listing actual connected containers by ID — comparing that list against what you assumed is nearly always faster than guessing from configuration alone.

How does Docker Desktop's networking differ from a native Linux Docker install, and why does it matter for a "works on my Mac, fails on the Linux server" bug?

Docker Desktop on macOS/Windows runs the daemon inside a lightweight Linux VM (historically HyperKit/WSL2-backed), and its networking layer includes translation shims that make things like localhost inside a container reachable from the host, and vice versa, transparently — behavior that native Linux Docker never needed to fake because the daemon runs directly on the same network stack as the host. The most common resulting bug is a container that binds 0.0.0.0 and is reachable via localhost:PORT on a Mac purely because of that VM's port-forwarding magic, then genuinely fails to be reachable the same way on a bare Linux server where "reachable via localhost" was never actually about the container's own binding — always test the same commands on the actual target OS before trusting a networking "it works" from Docker Desktop.

Lead-level: a platform team wants to standardize network policy (which services can talk to which) across dozens of Compose-deployed hosts. What does Docker's native tooling give you, and where does it fall short?

Docker's native primitives are genuinely thin here: you get network segmentation (which containers share a network at all) and that's close to the whole story — there's no first-class, declarative "allow service A to reach service B on port X, deny everything else" policy engine built into the Engine or Compose the way Kubernetes NetworkPolicy or a service mesh's authorization policy provides. In practice, teams either accept segmentation-only isolation (multiple purpose-scoped networks instead of one flat one, which covers a surprising amount of real-world need) or bolt on host-level nftables/iptables rules generated from a separate policy source of truth, which works but is now something your team, not Docker, has to keep correct and auditable. My honest answer to that request is usually "this is a strong signal you've outgrown single-host Compose for this concern" — it's one of the more concrete, defensible reasons to move a workload to Kubernetes (unit 09), which has fine-grained network policy as a first-class object rather than something to reconstruct by hand.

07 Storage and volumes

Every container has exactly three ways to interact with a filesystem path, and the interview-worthy skill is picking the right one for a reason, not by habit. The writable container layer (unit 02) is the default for anything you don't explicitly mount — copy-on-write, tied to that one container's lifecycle, gone on docker rm. A bind mount (-v /host/path:/container/path) maps an exact host path straight through — the container sees literally the host's files, changes are instantly visible in both directions, and Docker exercises zero management over it: no lifecycle, no backup tooling, just a mount. A named volume (-v myvolume:/container/path, or Compose's volumes: top-level key) is Docker-managed storage with its own lifecycle independent of any single container, living under a volume driver's control (locally, a directory under /var/lib/docker/volumes/; for real production storage, a plugin backing NFS, EBS, or another network-attached backend).

The decision rule that actually holds up under scrutiny: bind mounts for anything you, the developer, need to edit directly and see reflected live — source code during local development, a config file you're actively tuning — because that's exactly the "host and container see the same bytes" behavior bind mounts guarantee and named volumes don't (a named volume's data lives in Docker's own managed location, not somewhere you'd casually vim into from the host). Named volumes for anything that's genuinely the application's data — a database's data directory, an uploaded-files store — because they're portable across container recreation (rebuild the image, keep the volume, data survives), manageable with docker volume commands, and don't assume a particular host directory layout that breaks the moment you deploy to a different machine. tmpfs mounts, the third and least-discussed option, live entirely in host memory, never touch disk, and disappear completely on container stop — the correct choice for secrets or scratch data that must never be written to persistent storage at all, deliberately.

The single most consequential thing to know about named volumes: a volume's lifecycle is decoupled from every container that uses it, including the one that created it. docker rm on a container never deletes its volumes unless you pass -v (bare docker rm) or use docker compose down --volumes explicitly — this is a deliberate, load-bearing safety default, and also the reason "I ran docker system prune and lost my database" is almost always actually "I ran the --volumes variant, or I never had a named volume at all and was relying on the writable layer." Volumes created without an explicit name (an "anonymous" volume, from a Dockerfile VOLUME instruction with no corresponding named mount at run time) are the trap here: they persist data correctly but with an unmemorable auto-generated name, and they do get cleaned up by docker system prune --volumes once nothing references them, which surprises people who assumed "it's a volume, it's safe" without checking whether it was ever named.

Why does everyone recommend running a database in a container with a volume for local dev, but often not for production?

For local dev, a containerized database with a named volume gives fast, disposable, reproducible environments — tear down and recreate the whole stack in seconds, with the data optionally persisted across that churn via the volume. For production, the calculus shifts: a database now needs to survive host failure, not just container recreation on the same host, which means the volume needs real redundancy (network-attached storage, replication) that a bare local volume doesn't provide, plus operational concerns — backup automation, point-in-time recovery, patching, failover — that a managed database service (RDS, Cloud SQL, or a well-run Postgres operator on Kubernetes) already solves. It's not that containers can't run production databases well — many teams do, successfully, with real engineering behind the storage layer — it's that doing it well is a substantial ongoing commitment most teams underestimate when they extrapolate from "it worked great in dev."

What's the read/write performance difference between a bind mount and a named volume, and when does it actually matter?

On Linux, functionally none — both ultimately resolve to the same underlying filesystem with no meaningful overhead difference, since a bind mount is just a direct kernel bind-mount and a local named volume is also just a directory on the host filesystem underneath Docker's management. On Docker Desktop (macOS/Windows), it can matter a lot: bind-mounting a large source tree from the host into the Linux VM historically carried real filesystem-translation overhead (slow node_modules installs, slow file-watching), which is exactly the gap Compose Watch (unit 08) and Docker Desktop's newer VirtioFS/gRPC-FUSE-based sharing improvements were built to close. Named volumes on Desktop live natively inside the VM and don't pay that translation cost, which is why "put node_modules in a named volume instead of letting the bind mount cover it" is a genuine, measurable performance trick on Mac/Windows dev machines specifically.

How do volume drivers/plugins change this model for a multi-host or cloud deployment?

A volume driver replaces "a directory on this one host's disk" with whatever the plugin implements — an NFS mount, an EBS volume that can attach to whichever host a container is scheduled on, a distributed storage system like Longhorn or Ceph. The container-facing API is unchanged (-v myvolume:/path still works identically); what changes is where the bytes actually live and whether they survive the specific host dying, which is precisely the gap between "has a volume" and "has durable storage" from the interview trap above. In practice, most teams running real multi-host container orchestration hit this problem and solve it at the orchestrator level (Kubernetes PersistentVolumes with a CSI driver) rather than with raw Docker volume plugins, which is worth naming as the more common real-world path.

Your container's Dockerfile has a VOLUME /data instruction. What does that actually do, and what's the common surprise?

It declares that /data should always be a volume mount point, and if you run the container without explicitly mounting something there, Docker creates an anonymous volume automatically to satisfy it — the data still persists across a container restart, just under an auto-generated name you didn't choose and likely won't remember. The common surprise is exactly the anonymous-volume accumulation problem: every plain docker run of that image without an explicit -v creates a new anonymous volume, so repeated testing of an image with a baked-in VOLUME instruction can quietly accumulate dozens of orphaned, unnamed volumes that docker volume ls shows as a wall of hashes with no obvious owner.

How would you migrate a stateful container's data from one host to another without a shared network filesystem?

The pattern in the "Try it" backup example generalizes directly: run a throwaway container that mounts the source volume read-only and streams a tar archive out (to stdout, piped over SSH, or to a bind-mounted destination), then on the target host run a throwaway container that mounts a freshly created volume and untars the archive into it. This works identically whether the destination is a bare-metal box, a cloud VM, or another Docker host entirely, and it's the same primitive underlying most "volume backup/restore" tooling in the ecosystem — worth knowing how to do by hand because it demystifies what those tools are actually doing and lets you debug them when they fail.

What's the risk of bind-mounting the Docker socket itself (-v /var/run/docker.sock:/var/run/docker.sock) into a container, and why do so many CI and monitoring tools ask for it anyway?

A container with the host's Docker socket mounted in can, functionally, control the entire host's Docker daemon — create privileged containers, mount arbitrary host paths, read every other container's environment variables — which is root-equivalent access to the host in almost every practical sense, regardless of what capabilities or user the container itself runs as. Tools ask for it because it's the simplest way to let a containerized process manage sibling containers (a CI runner spinning up build containers, a monitoring agent inspecting other containers) without nesting a whole Docker-in-Docker setup. The mitigation, where the tool supports it, is a socket proxy that exposes only a restricted subset of the Docker API rather than the raw socket — and where it doesn't, treating that container as equivalent to root-on-host for every security and access-control decision you make about it.

Lead-level: how would you decide whether a team's growing use of bind-mounted config files should move to a different mechanism entirely?

The tell I look for is whether the bind-mounted config is actually being hand-edited on running hosts, or whether it's really deployment-time configuration that happens to be implemented as a bind mount out of habit. If it's the latter — a config file that's identical across all instances of a service and only changes on deploy — it usually belongs as a COPY'd file baked into the image (fully reproducible, versioned with the code) or, if it needs to vary per-environment without a rebuild, in environment variables or a proper secrets/config-management system (Docker/Compose secrets, a Kubernetes ConfigMap, Vault) rather than a host path someone SSHes in to edit by hand. Bind-mounted, hand-edited config on a production host is a specific, recognizable smell — it's undocumented, unversioned, and the first thing that's wrong after any disaster-recovery restore, because nobody wrote down that it needed to exist.

08 Compose for local development

Compose's job is narrow and worth stating precisely: it's a declarative, single-host tool for defining and running a multi-container application from one YAML file, and nothing in the current Compose Specification assumes or requires the older "docker-compose" Python tool — docker compose (no hyphen, a Go-based Docker CLI plugin) has been the default, actively developed implementation since Compose V2, and V1 stopped receiving updates back in mid-2023. Compose v5, the current major version as of 2026 (v5.5.x), is best understood as a reconciliation engine, not a script runner: docker compose up diffs the desired state in your YAML against what's actually running and converges toward it — recreating a service whose config changed, leaving an unchanged service alone, rather than blindly tearing everything down and rebuilding on every invocation the way a naive script would.

Three features distinguish "using Compose" from "using Compose well" for local development specifically. Profiles (profiles: ["debug"] on a service, activated with --profile debug or COMPOSE_PROFILES) let one Compose file describe an optional service — a debug proxy, a seed-data job, an admin UI — that most invocations skip entirely, instead of maintaining a second file or commenting lines in and out. Healthchecks plus depends_on: condition: service_healthy fix the single most common Compose bug: a dependent service starting before its dependency is actually ready to accept connections, not just "the container process has started" (which depends_on alone only guarantees). Compose Watch (develop: watch:) is the modern answer to live-reload — it syncs specific file changes into a running container (action: sync) or triggers a targeted rebuild-and-restart (action: rebuild) based on path patterns, replacing the older, cruder pattern of bind-mounting an entire source tree and hoping the app's own dev-server file-watcher behaves well across the host/container boundary (unit 07's Docker Desktop filesystem-performance note).

The reconciliation behavior has a sharp edge worth naming explicitly: docker compose up without --build will not rebuild a service's image just because its Dockerfile or source changed — Compose only rebuilds when you tell it to (--build), when the image doesn't exist yet, or when Watch's rebuild action fires for a matched path. "I changed the code but the container is running the old version" after a plain up is almost always this, not a caching bug — and it's exactly the gap Compose Watch closes for active development without requiring a manual --build every time.

What's the actual relationship between "the Compose Specification" and the docker compose CLI?

The Compose Specification is an open, versioned schema (maintained collaboratively, with Docker as the primary steward) describing what a compose.yaml file may contain — services, networks, volumes, and their fields — independent of any one implementation. docker compose is Docker's own implementation of that spec, bundled as a CLI plugin (Go, using the same libraries as the Engine itself) rather than a separate Python tool shelling out to the Engine API the way the legacy V1 docker-compose did. Other tools (some Kubernetes-adjacent projects, some CI systems) can and do read Compose-spec files without being Docker's own CLI, which is part of why "the Compose file format" and "the docker compose command" are worth keeping conceptually separate even though almost everyone only ever touches the latter.

Why does Compose create one network per project by default, and what determines the "project" boundary?

Every service in a Compose file gets attached to a project-scoped user-defined bridge network automatically (unit 06) specifically so that name-based discovery — curl http://db:5432 — works with zero networking configuration. The project boundary is the directory name (or an explicit name: field in the compose file, or -p/COMPOSE_PROJECT_NAME on the command line) — two compose files with the same project name, even in different directories, are treated as the same project and can collide or merge depending on what you're doing, which is a real gotcha when someone copies a project directory without renaming it and ends up fighting containers/networks from the "other" copy.

How would you run the exact same Compose file with different settings for local dev versus CI, without duplicating the whole file?

Compose's override mechanism is built for exactly this: a base compose.yaml plus a second file (compose.override.yaml is picked up automatically with no flag; anything else needs explicit -f base.yaml -f ci.yaml) that Compose merges on top, field by field — override a service's environment, add a profiles entry, swap an image for one built locally. This keeps the shared shape in one file and isolates only the genuinely environment-specific differences, which is both easier to review and harder to let drift than two independently-maintained full copies of the same stack.

What actually happens to named volumes when you run docker compose down versus docker compose down --volumes?

Plain down stops and removes the project's containers and default network but explicitly leaves named volumes alone — the same "volumes outlive containers by default" safety property from unit 07, just at the project level instead of the single-container level. --volumes additionally removes every named volume declared in the compose file (not volumes merely referenced as external: true, which Compose never owns and never deletes). This is the single most consequential flag in the entire Compose CLI from a data-loss perspective, and it's worth having muscle memory around never typing it out of habit.

A service's healthcheck passes when you run it manually inside the container, but Compose still reports it unhealthy. What do you check?

First, that the healthcheck command is actually reachable in the same way Compose runs it — a shell builtin or alias that works in your interactive shell but isn't available via CMD-SHELL's /bin/sh -c invocation is a common gap. Second, timing: a start_period that's too short for a genuinely slow-starting service causes early failing checks to count against it before it's had a fair chance, though Compose does discount failures during start_period if configured. Third, and most overlooked: the healthcheck test running against a port or path that's only correct from outside the container (localhost on the host) rather than from inside it, where the command actually executes.

Why might a team deliberately avoid Compose Watch's sync action for a compiled language's source directory?

Sync is best suited to interpreted languages or anything with its own in-process hot-reload (Node, Python, most frontend dev servers) where dropping a changed file into the running container is immediately useful. For a compiled language, syncing raw source into the container accomplishes nothing on its own — the container still needs to notice the change and recompile, which usually means either running a file-watching compiler inside the container (adding its own complexity) or just using Watch's rebuild action instead, which handles the whole rebuild-and-restart cycle for you at the cost of being slower per-iteration than a sync.

How do Compose's environment, env_file, and a plain .env file in the project directory interact, and what wins on conflict?

A .env file in the project root is read automatically by the Compose CLI itself for variable substitution within the compose file's own YAML (e.g. image: myapp:${TAG}) — it never directly becomes the container's runtime environment. env_file: on a service loads a file's contents into that container's actual runtime environment, and environment: entries on the service take precedence over anything from env_file: when both define the same key. Mixing these up — expecting a .env file to set a container's runtime variable directly — is a frequent point of confusion precisely because the two mechanisms look similar but operate at genuinely different stages (compose-file templating versus container runtime).

What's the risk of committing a compose.yaml that pins service images with :latest for a team's shared local dev environment?

Different teammates pulling at different times get different actual image contents behind the identical tag, which produces exactly the "works for me, broken for you" class of bug that a shared dev environment is supposed to eliminate — someone's stack is running last week's Postgres minor version with a schema quirk someone else's already-updated image doesn't have. The fix is the same discipline as production images generally: pin an explicit version tag (and, for anything genuinely sensitive to drift, a digest) in the committed compose file, and treat a deliberate version bump as its own reviewable change rather than something that happens silently to whoever pulls next.

What's the difference between scaling a service with docker compose up --scale api=3 and just defining three separate services?

--scale runs multiple, identically-configured replicas of the same service definition behind whatever load-balancing the surrounding setup provides — useful for a quick local test of "does my app behave correctly with more than one instance" (shared-nothing assumptions, session affinity bugs), but it's a blunt instrument: every replica is identical, and a service using --scale can't publish a fixed host port the normal way (multiple replicas can't all bind the same host port), so Compose auto-assigns or requires a range. Defining separate named services makes sense only when the instances genuinely differ (different config, different roles); for "just run more of the same thing," --scale is simpler and is also the more honest local approximation of what a real orchestrator's replica count does, which is precisely why it's worth exercising locally before assuming a service is safe to scale in production.

Lead-level: a team's Compose-based local dev environment has grown to fifteen services and now takes minutes to start and gigabytes of RAM. How do you approach trimming it without breaking anyone's workflow?

I'd start by asking which services a given developer actually needs running to do their specific work — this is almost always less than "everything," and it's exactly what profiles are for: group services into profiles by team or workflow (frontend, backend-core, full-integration) so a frontend developer's default up starts three services, not fifteen, with the full set still one flag away when genuinely needed. Second, look for services that don't need to be containers at all for local dev — a message broker or cache that has a hosted free tier or a lightweight native alternative can sometimes just not be part of the stack locally. Third, profile what's actually slow to start (often one or two services with real cold-start costs, not an even distribution across all fifteen) rather than assuming the fix is uniformly "fewer services" — sometimes it's "fix this one service's healthcheck timing" and the perceived slowness mostly disappears.

09 From Compose to orchestration: Swarm, Kubernetes, containerd

Compose's reconciliation loop runs once, on one host, when you invoke it — it does not watch for a container dying at 3am and restart it on a different, healthier host, because there is no "different host" in its model at all. Orchestration is what a platform adds on top of that gap: continuous reconciliation, scheduling across a fleet of machines, rolling updates, and self-healing when a node disappears. Docker shipped its own orchestrator, Swarm mode, built into the Engine since 1.12 — and it's important to be precise about its current status rather than either dismissing it as dead or overselling it as active: Docker still ships and documents Swarm mode, it still receives Engine-cycle security patches, but it has not been where Docker's own product investment or the wider ecosystem's attention has gone for years, and essentially every "which orchestrator should we adopt new" conversation today ends at Kubernetes, not Swarm, unless a team already has deep, working Swarm infrastructure and no compelling reason to migrate it.

Kubernetes won that conversation for reasons worth naming precisely rather than hand-waving as "more popular": a genuinely pluggable, declarative API (CRDs let the ecosystem extend it instead of waiting on the core project), a much larger set of production-grade controllers for the problems real fleets hit (autoscaling, network policy as a first-class object — unit 06's gap — StatefulSets for ordered stateful rollout, PodDisruptionBudgets), and critically, Kubernetes decoupled itself from Docker specifically years ago via the Container Runtime Interface (CRI) — dockershim, the compatibility layer that let Kubernetes talk to the Docker Engine directly, was removed in Kubernetes 1.24 (2022), and every current Kubernetes cluster talks to a CRI-compliant runtime directly, overwhelmingly containerd itself (the same containerd from unit 01, running standalone rather than fronted by dockerd) or CRI-O. This is the single fact that resolves the "wait, does Kubernetes even use Docker?" confusion for good: Kubernetes never used "Docker" the product, it used containerd underneath Docker, and now it just talks to containerd (or another CRI runtime) with dockerd's layer skipped entirely.

What this means practically for a team on Docker-plus-Compose today: your images are unaffected — an OCI image built by docker build/BuildKit is exactly as runnable on Kubernetes as anywhere else, because OCI image format was never Docker-proprietary (unit 01). What doesn't carry over cleanly is the Compose file — Kubernetes doesn't read compose.yaml natively, though translation tools exist (kompose being the best-known) and produce a rough first draft, never a finished migration; the concepts that don't map cleanly (Compose's simple depends_on healthcheck-gating versus Kubernetes' readiness/liveness probes and init containers; Compose's flat network model versus Kubernetes' Services/Ingress/NetworkPolicy layering) are exactly where a naive auto-translation produces something that runs but isn't actually using the target platform well.

What specifically was dockershim, and why did its removal in Kubernetes 1.24 not break most people's clusters?

dockershim was a compatibility shim built into kubelet that translated CRI calls into the Docker Engine API so Kubernetes could keep using dockerd as its runtime before CRI-native runtimes matured. Its removal didn't break most clusters because most managed Kubernetes offerings (EKS, GKE, AKS) had already switched their default node images to containerd well before 1.24 shipped, and the CNCF/Kubernetes project gave a long, well-publicized deprecation runway specifically so operators could migrate node pools ahead of the hard cutover. The clusters that did get bitten were almost always ones pinning an old Kubernetes version on self-managed nodes with a docker-based runtime configuration nobody had revisited in years — a good illustration of why "it still works" isn't the same question as "is this still supported."

If Kubernetes doesn't use dockerd, why do so many tutorials still say "make sure Docker is installed" before working with Kubernetes?

Almost always because you still need Docker (or another OCI-image builder) on your development machine to build the images you'll deploy — that's a build-time tool dependency, entirely separate from what runtime the cluster itself uses to run those images. The confusion is understandable because for years "install Docker" genuinely did mean "and that's also what your cluster nodes will run," which stopped being true for most clusters years ago; a tutorial that hasn't been revisited since then keeps repeating advice that's now solving a different problem than the one it originally solved.

What does Swarm mode actually get right that makes it a defensible choice for a specific team today, rather than pure legacy inertia?

Genuine operational simplicity: a Swarm cluster is a handful of docker swarm init/join commands and stack files that look almost exactly like the Compose files a team already knows, with no separate YAML dialect, no cluster-add-on ecosystem to evaluate, and a dramatically smaller operational surface than a Kubernetes control plane. For a small team running a modest number of services who has evaluated Kubernetes and concluded its complexity buys them nothing they need, staying on Swarm (or even just single-host Compose, unit 08) is a legitimate, deliberate choice — the trap is only in defaulting to it by inertia without having actually made that comparison.

How does a Kubernetes readiness probe differ from Compose's healthcheck-plus-depends_on, beyond just syntax?

Compose's healthcheck gates startup ordering once, at up time — get past that gate and the mechanism is largely done influencing behavior. A Kubernetes readiness probe runs continuously for the pod's entire lifetime and controls something Compose has no equivalent for: whether the Service's load balancer sends the pod traffic at all, moment to moment — a pod that starts healthy and later fails its readiness probe (say, it's overloaded and its own health endpoint reports degraded) gets pulled out of rotation immediately without being restarted, which is a meaningfully different and more powerful lever than Compose's one-time startup gate.

What happens to a running container if you kill dockerd on a node, and does the equivalent question have the same answer under Kubernetes/containerd?

Under modern Docker (containerd-integration since Engine 27+, unit 01), killing dockerd does not kill running containers — containerd, which actually supervises them via runc/shim processes, keeps them running independently, and dockerd reattaches to that existing state on restart rather than needing to relaunch anything. Under Kubernetes, the equivalent question — what happens to running pods if kubelet or containerd is restarted on a node — has a similarly reassuring answer for containerd itself (it's designed for exactly this decoupled-supervision property), though kubelet restarting means the node briefly stops reporting status/reconciling until it comes back, which can matter for scheduling decisions during that gap even though the containers themselves are unaffected.

A team wants to move from Compose-based single-host deployment to "real" orchestration but is intimidated by full Kubernetes. What intermediate options exist?

A few genuine middle grounds exist depending on what's actually driving the need: if it's multi-host reliability without wanting Kubernetes's full surface, Swarm mode itself is the intentionally lighter-weight option built for exactly this. If it's "I want managed infrastructure without operating a control plane," a managed container-runtime platform (a cloud provider's "run this container" service — Cloud Run, App Runner, Container Apps) trades flexibility for near-zero operational burden, at the cost of being a less portable, more provider-specific target than either Swarm or Kubernetes. I'd push back gently on skipping straight to full self-managed Kubernetes for a team that hasn't actually hit a wall Swarm or a managed platform can't solve — Kubernetes's complexity is worth paying for when you need its specific power, not by default.

Why do some teams run Kubernetes and Compose side by side rather than picking one?

They're solving different problems that happen to both involve containers: Compose for fast, disposable local development loops (unit 08's whole point), Kubernetes for the production, multi-host, self-healing runtime — and the same image built by the same Dockerfile serves both, because OCI images don't care which orchestrator eventually runs them. A team abandoning Compose "because we have Kubernetes now" often ends up reinventing a worse local-dev experience (a local single-node Kubernetes cluster is genuinely heavier and slower to iterate against than Compose for pure development loops), which is why "Compose for dev, Kubernetes for prod, same images" remains an extremely common and sensible split rather than something to consolidate away.

What's CRI-O, and why would a Kubernetes distribution choose it over containerd?

CRI-O is a CRI-native runtime built from the start specifically and only to satisfy Kubernetes's CRI, with no other product (there's no "CRI-O the standalone CLI tool" the way containerd has ctr/nerdctl beyond Kubernetes) — some distributions (notably Red Hat's OpenShift) choose it for a smaller, more tightly-scoped surface area purpose-built for exactly one API rather than containerd's broader general-purpose runtime scope. For most teams evaluating this today the choice is made for them by their platform/distribution rather than something they pick independently, and functionally both are mature, CRI-compliant, runc-backed runtimes for the vast majority of workloads.

Does migrating a Swarm-based production system to Kubernetes actually require rewriting the application, or is it mostly infrastructure work?

Almost entirely infrastructure and deployment-definition work, not application rewriting — the same container images run unchanged on either platform, since neither Swarm nor Kubernetes changes anything about what runs inside a container. What genuinely needs rewriting is the deployment layer: stack files become Kubernetes manifests (or Helm charts), Swarm's simpler built-in service discovery and secrets model gets replaced by Kubernetes Services/ConfigMaps/Secrets, and any Swarm-specific operational tooling or runbooks need Kubernetes-native replacements. The size of that work scales with how much Swarm-specific behavior the application's deployment leaned on, not with the application's own complexity — a useful thing to say explicitly when someone assumes a migration is bigger (or smaller) than it actually is.

Lead-level: how do you decide when a team genuinely needs to move off Compose/Swarm onto Kubernetes, versus when that's resume-driven architecture astronautics?

I look for a specific, currently-unmet operational need, not a vibe. Concrete triggers I'd accept: the team needs autoscaling based on real load signals Compose/Swarm can't express; they need fine-grained network policy or multi-tenant isolation that unit 06's "you've outgrown single-host networking" gap already flagged as a real Kubernetes-shaped hole; they're already running enough separate services/hosts that Swarm's simpler tooling is visibly straining. What I push back on is "everyone else uses Kubernetes" or "it looks better on our infrastructure diagram" as the actual reason — migrating a working, appropriately-scoped system onto a materially more complex platform for reasons that don't trace to an unmet operational need is a cost with no matching benefit, and it's my job to say that plainly even when it's not the popular answer in the room.

10 Security and the supply chain

Container security decomposes into three genuinely separate questions that are worth answering separately rather than as one vague "is this secure": is the runtime configured defensively (unit 05's namespaces/cgroups/capabilities/seccomp/rootless), is the image itself free of known vulnerabilities and built from a trustworthy base, and can you prove, after the fact, exactly what went into a given running image and where it came from. That third question — supply-chain provenance — is where the most consequential 2026-era Docker developments live, driven by the same industry pressure (SolarWinds-style and npm/PyPI-style supply-chain incidents) that produced SLSA, in-toto, and Sigstore as an ecosystem, and Docker's own product response as Docker Hardened Images and Docker Scout.

Docker Hardened Images (DHI) are Docker's own curated, minimal, continuously-patched base and application images — the pitch is a base image with a near-zero known-CVE count at time of publish, built with SBOMs and provenance attestations (unit 04's --sbom/--provenance mechanics) generated by default, distroless-style minimal surface where practical, and Docker's own SLA on patch turnaround for newly disclosed CVEs rather than "whenever the community image maintainer gets to it." This matters concretely because base-image CVE count is disproportionately what a security scanner flags in most real audits (unit 02's base-image convergence problem, revisited) — swapping a general-purpose Ubuntu-based image for a hardened, minimal equivalent is very often the single highest-leverage change available to reduce a fleet's total flagged-CVE count, and it's why DHI is a paid product rather than a free convenience: someone has to do the continuous patching and rebuilding work DHI is selling.

Docker Scout is the analysis half — CVE scanning against an image's actual SBOM, cross-referenced against multiple vulnerability databases, integrated into docker scout cves, into Docker Hub's repository pages, and into CI via Scout's GitHub Action. What Scout adds over a generic scanner is remediation guidance tied to Docker's own base-image knowledge — "this CVE would be resolved by moving to this specific newer base image tag" rather than just a flat list of CVE IDs with no actionable next step. The other half of the "prove where this came from" story is signing: Docker Content Trust (Notary-based, the older mechanism) is deprecated and removed from current Engine releases, and Sigstore/cosign-based signing — keyless, backed by a transparency log rather than a long-lived private key you have to protect and rotate — is the current, ecosystem-wide direction, with Docker's own tooling (buildx attestations, Scout) built around SBOM/provenance formats that a cosign-based verification pipeline consumes.

Why was Docker Content Trust deprecated rather than kept alongside newer signing mechanisms?

Content Trust was built on Notary, which required managing long-lived signing keys (a root key and repository keys) with all the operational burden that implies — secure storage, rotation, recovery if lost, and a real single-point-of-failure risk if a key leaked. The Sigstore-based model the ecosystem converged on instead uses short-lived, workload-identity-bound certificates issued at sign time and recorded in a public transparency log (Rekor), so there's no long-lived secret to protect at all — signing becomes an ephemeral, auditable event rather than a key-custody problem. Docker's removal of Content Trust tooling reflects that the whole industry, not just Docker, moved away from long-lived-key signing as the pattern.

What does an SBOM actually protect against, and what does it not protect against?

An SBOM tells you precisely which packages and versions are present in an image, which is exactly what lets a vulnerability scanner (today's, or a future one checking against a CVE disclosed after the image was built) match your actual contents against known-vulnerable versions without needing to re-scan the filesystem from scratch. It does not, by itself, prove the image wasn't tampered with after the SBOM was generated, and it says nothing about vulnerabilities in your own application code versus its dependencies — an SBOM is a manifest of ingredients, not a guarantee of safety, and conflating the two is a common overselling of what SBOMs actually buy you.

A CVE scanner flags a vulnerability in a package that's present in the image but never actually invoked by the running application. How do you reason about the real risk?

Genuinely lower risk than an actively-invoked vulnerable package, but not zero — "never invoked today" can change with the next code path added, and some vulnerability classes (a vulnerable library loaded into the same process memory space, even unused) carry risk independent of direct invocation. The pragmatic response is rarely "ignore it because it's unused" and rarely "block the release over an unreachable CVE" either — it's usually removing the unused package from the image entirely if it's not actually needed (which a minimal/hardened base image does by construction, per this unit's main point) or explicitly, visibly suppressing the specific finding with a documented justification if removal isn't currently feasible, so the decision is auditable rather than silently accepted.

How does keyless signing with cosign actually establish trust, if there's no private key to check?

Trust shifts from "does this key match" to "was this identity, verified via OIDC (a CI system's workload identity, a specific GitHub Actions workflow), actually who signed this, and is that recorded immutably in a public transparency log." A verifier checks the certificate's identity claims (which repository, which workflow, sometimes which specific commit) against a policy — "only accept images signed by our own CI pipeline's specific workflow identity" — and checks the transparency log entry exists and is consistent, which makes forgery detectable (a fraudulent signing event would need to appear in the same public, append-only log) rather than preventing it by a secret nobody else has.

Why does Docker's SLA-style patch-turnaround promise for Hardened Images matter more than the initial CVE count at time of publish?

A base image's CVE count at publish time is a snapshot that starts decaying the moment a new CVE is disclosed against something it contains — the real differentiator between a "hardened" image and an ordinary one isn't day-zero cleanliness (many images look clean on the day they're built) but how quickly a newly-disclosed CVE gets a patched image available, and how automatically that reaches teams already depending on that base. A base image nobody's actively maintaining accumulates disclosed-but-unpatched CVEs over months; the maintenance commitment behind DHI's turnaround SLA is the actual product being purchased, not the marketing-page CVE-count screenshot.

What's the relationship between least-privilege container configuration (unit 05) and image hardening — do you need both?

Yes, and they defend against different failure modes: image hardening reduces the odds a vulnerability exists to be exploited in the first place (fewer packages, fewer known CVEs, smaller attack surface), while runtime least-privilege (dropped capabilities, seccomp, non-root user, no --privileged) limits the blast radius if something gets exploited anyway — a zero-day in your actual application code, not a known CVE in a dependency, isn't something any base-image hardening prevents, but a properly capability-dropped, non-root container contains what that exploited process can then do. Treating either alone as "our security strategy" leaves a real gap the other half was specifically designed to close.

How would you verify, in a CI pipeline, that an image about to be deployed was actually built by your own pipeline and not substituted or tampered with?

A deploy-gate step that runs cosign verification against the image's signature and checks the identity claims match your pipeline's specific workflow (not just "signed by someone"), combined with checking the provenance attestation's recorded build inputs match what you expect (source repo, commit, builder identity) — both checks running as an actual gate that blocks deployment on failure, not just a dashboard someone might glance at. Admission controllers on the deployment platform side (Kubernetes' built-in policy admission, or a dedicated tool) can enforce the same check at the cluster boundary as a second, independent layer, which matters because a CI-only check can be bypassed by anyone with direct deploy access that skips CI.

What's the practical downside of adopting Docker Hardened Images or an equivalent commercial hardened-base program, beyond cost?

Minimal/distroless-style images intentionally lack a shell, package manager, and many debugging tools a traditional image has by default, which makes ad hoc "exec into the container and poke around" debugging harder — you plan for that with a separate debug-image variant or ephemeral debug containers (kubectl debug's equivalent, or a sidecar approach) rather than expecting the production image itself to double as a debugging environment. There's also a real, if smaller, migration cost: application assumptions baked in from years of Ubuntu-based images (a specific libc version's behavior, an assumed-present CLI tool) sometimes surface only when you actually swap the base and something subtly breaks, which is exactly why the swap deserves real testing, not a blind Dockerfile find-and-replace.

Lead-level: how would you roll out a mandatory image-signing-and-verification policy across an organization that currently has none?

Sequenced the same way as the rootless/non-root rollout in unit 05: start by signing everything in CI with no enforcement yet, purely to establish the pipeline and confirm it doesn't break anything, and to build up a body of correctly-signed images before anyone's blocked by a gate. Then turn on verification in a non-blocking, log-only mode at the deployment boundary, review what would have been blocked for a realistic window, and fix the false positives (an internal tool that builds images outside the sanctioned pipeline, say) before flipping to actually enforcing. Only after that do I make it a hard, blocking gate — a security control that ships as a surprise blocking gate on day one reliably gets bypassed via an emergency exception that then never gets revoked, which defeats the entire point more thoroughly than a slower, deliberate rollout would have.

11 Production operations and debugging

Running containers in production surfaces a specific, recurring set of operational questions that are worth having crisp, tested answers for, because they're exactly what a debugging-focused interview round tends to probe: what happens when a container misbehaves, how do you find out why after the fact, and how do you get a live look inside something that's currently broken. Restart policies (--restart=unless-stopped, or the near-equivalent always, versus on-failure[:max-retries], versus no) determine whether the daemon relaunches a dead container automatically, and the trap is picking one without thinking through the failure mode it interacts with: always/unless-stopped restarting a container that crashes instantly on a bad config produces a tight restart-loop that can genuinely hammer a dependency (a database getting hit with a fresh connection attempt every second) worse than the original failure did, which is exactly why on-failure with a bounded retry count is often the more defensible default for anything talking to a shared downstream resource.

The debugging toolchain worth having cold, in the order you'd actually reach for it: docker logs (and --since/--tail/-f to keep it manageable) for what the process itself said; docker inspect for the container's actual resolved configuration — mounts, environment, restart count, exit code and OOMKilled status, all the ground truth that resolves "wait, what did I actually configure here" disputes; docker exec -it <container> sh for a live shell into a running container's namespace (only works if the image has a shell — unit 10's hardened-image debugging tradeoff); docker stats for a live view of CPU/memory/network/block-IO per container, the fastest way to confirm or rule out a resource-limit hypothesis; and docker events for a live stream of daemon-level lifecycle events (start, die, oom, health_status) across every container, invaluable for catching an intermittent crash-and-restart cycle you can't reproduce on demand but can leave a terminal tailing until it happens again.

Logging drivers are worth understanding because the default (json-file, unbounded unless you set max-size/max-file) has caused more than one real incident by quietly filling a host's disk with unrotated log files from a chatty container nobody was watching — setting log-opts: max-size` and `max-file` (or switching the driver entirely to something that ships logs off-host, like a syslog, journald, or a cloud-native log driver) is not an optional nicety on any long-running host, it's a default every production Docker deployment needs to set deliberately because the daemon's own default doesn't protect you from it. The other recurring production question — "why did my container die with no error in its logs" — is very often the OOM-killer case from unit 05 (check docker inspect's OOMKilled field specifically, since the container's own stdout genuinely has nothing to say about a kernel-level kill) or a failed healthcheck triggering an orchestrator-level restart the application logs never saw coming.

A container shows as "healthy" in docker ps but the application inside is clearly not serving requests correctly. What does that tell you, and what doesn't it tell you?

It tells you the configured healthcheck command is returning success, and nothing more — a healthcheck is only as good as what it actually tests, and a shallow one (checking that a process is listening on a port, say, without checking it can actually complete a real request end-to-end) will happily report healthy while the application behind it is deadlocked, returning errors, or serving stale data. This is a real, common gap: writing a healthcheck that pings /healthz and calling it done, when /healthz itself doesn't exercise the actual failure mode that's currently occurring. The fix is treating healthcheck design with the same rigor as the code it's checking — a healthcheck that can't fail when the thing it's protecting against happens isn't actually protecting against it.

Why might docker stats show low CPU usage for a container that users are reporting as slow?

CPU usage being low doesn't rule out the container being CPU-throttled — a container with a --cpus quota can show low average utilization while still being throttled during specific bursts if the quota's accounting period catches a spike unevenly (cgroup CPU throttling is enforced per accounting period, and a burst that exceeds the quota within one period gets throttled even if the overall average looks modest). It also doesn't rule out the bottleneck being somewhere else entirely — I/O wait on a slow disk or network call, or contention on a shared downstream dependency — that docker stats's per-container view genuinely can't see because the container's own CPU is idle while it's blocked waiting on something outside itself.

What's the actual difference between docker stop and docker kill, and when does that difference matter?

docker stop sends SIGTERM, waits a grace period (10 seconds by default, configurable via -t), then sends SIGKILL only if the process hasn't exited — it's a cooperative shutdown request. docker kill sends SIGKILL (or another signal you specify) immediately, no grace period, no chance for the process to clean up. This matters directly for anything doing graceful shutdown work — draining in-flight requests, flushing a write buffer, closing a database connection cleanly — which only stop's grace period allows time for; a kill, or a stop whose grace period is shorter than the app's actual cleanup time, can leave work half-done or a downstream connection in a bad state the next start has to detect and recover from.

Your container keeps restarting with exit code 137 but OOMKilled is false in docker inspect. What else produces that exit code?

137 is 128+9, meaning the process received SIGKILL — the OOM killer is the most common cause, but not the only one: an external docker kill, a healthcheck-driven orchestrator restart that escalates to a hard kill after a grace period, the host itself running out of memory at a level above the container's own cgroup accounting (host-wide memory pressure triggering a different kill path than the container's own OOM event), or a supervisor process inside a multi-process container sending SIGKILL to its child. OOMKilled being false specifically rules out that particular container's own cgroup limit as the trigger — the next place to look is the host's own dmesg/kernel log for a host-level OOM event, and the orchestrator's or monitoring system's own action log for anything that issued an external kill.

How would you debug a container that appears to hang on startup with no log output at all, where docker exec also doesn't seem to help?

If docker exec genuinely doesn't work (the container has no shell — a scratch/distroless image, unit 10), the fastest path is often docker cp-ing a static debugging binary in, or, more robustly, an ephemeral debug container attached to the same namespaces (docker run --pid=container:<id> --network=container:<id> alpine sh-style, sharing the target's PID and network namespaces without needing anything installed in the target image itself) which lets you inspect the actual running process tree, open file descriptors, and network state from an entirely separate, fully-equipped container. This namespace-sharing trick is worth having ready specifically because it's the one technique that works regardless of how minimal the target image is.

What's the risk of relying solely on docker logs for a production incident review months after the fact?

docker logs reads from the log driver's own on-host storage, which for the default json-file driver is subject to whatever rotation policy you've set (or the unbounded growth this unit already flagged if you haven't) — logs from a container that's since been removed, or that rotated past your retention window, are simply gone, with no daemon-level backup. This is exactly why production logging strategy should ship logs to a durable, centralized destination (a log aggregation platform, via a shipping log driver or a sidecar) rather than treating docker logs on the host itself as the system of record — it's a fine tool for live/recent debugging and a poor one for anything you might need to review after the container is long gone.

A team wants alerts the instant any container OOM-kills. What's the most reliable signal to build that on?

docker events --filter event=oom is the direct, daemon-level signal — it fires specifically on the OOM condition being hit, independent of whatever exit-code or restart behavior follows, and is the same event stream a monitoring agent would subscribe to rather than polling docker inspect after the fact and hoping to catch the state before something else changes it. Piping that event stream into whatever the team's actual alerting pipeline is (a log shipper watching for the event, a small daemon subscribing directly) is more reliable than inferring OOM from exit-code-137 patterns alone, since (per an earlier question) 137 has multiple possible causes and oom as an explicit event does not.

Lead-level: after a production incident caused by a silent disk-filling log file, how do you make sure this specific failure mode doesn't recur, beyond just fixing this one container's log-opts?

I'd treat the single fix as necessary but insufficient and look for the systemic gap it revealed: if one container's logging config was left at the unbounded default, it's likely others are too, so I'd audit the fleet for the same missing max-size/max-file (or equivalent for whatever driver is in use) rather than assuming this was an isolated oversight. Then I'd push the fix upstream of individual container configs where possible — a shared base Compose fragment, a Dockerfile/deployment template, or a daemon-level default (dockerd's own log-opts default in daemon.json applies to every container that doesn't override it) — so the safe behavior is what happens automatically, and a new service has to opt out of safety rather than opt into it. Finally, disk-usage alerting on the hosts themselves as a second, independent line of defense, because whatever this incident's specific root cause was, the actual production risk was "disk filled with no warning," and that deserves its own monitoring regardless of which application eventually causes it next.

12 Registries, tagging and CI/CD

A registry's job is simple to state — store and serve OCI images by name and tag/digest — but the operational decisions around it are where real incidents live. Docker Hub, the default and still most widely used public registry, enforces pull-rate limits that have tightened over the product's history and now apply meaningfully even to some authenticated tiers, not just anonymous pulls — a detail that matters directly for CI, because a fleet of ephemeral CI runners all pulling the same base images anonymously from the same shared IP ranges (common on hosted CI platforms) can hit those limits collectively even though no single developer feels like they're pulling often. The practical fixes, in order of how most teams actually adopt them: authenticate pulls (authenticated limits are higher than anonymous), pull-through-cache or mirror frequently-used base images in a registry you control, or move genuinely high-volume CI pulls to a private registry entirely.

Tag immutability is the single most consequential registry-configuration decision most teams never make deliberately. A mutable tag — the default everywhere unless you configure otherwise — means myapp:1.4.2 can be silently overwritten by a later push using the identical tag, so "the same tag" stops being a reliable pointer to "the same bytes" the moment anyone (accidentally or deliberately) re-pushes it. The fix most registries now support is an immutability policy on tags matching a pattern (semver-shaped tags, say) that rejects a second push to an already-existing tag outright — combined with the discipline of never reusing a version tag for a genuinely different build, this is what makes "deployed myapp:1.4.2" an actually falsifiable, auditable statement rather than a snapshot of whatever happened to be there at push time. :latest is the extreme, deliberately-mutable case — fine for a quick local test, actively dangerous as a production deployment target for exactly the reasons unit 08's Compose section already named for the dev-environment version of this same mistake.

A promotion pipeline — build once, then move the same, unchanged artifact through progressively more trusted environments (a CI-internal registry → a staging registry/namespace → a production registry/namespace, often via re-tagging or copying the same digest rather than rebuilding) — is the pattern that actually delivers on "what we tested is what we shipped." Rebuilding an image separately for each environment (even from the identical source, with the identical Dockerfile) risks a subtle but real gap: a base-image tag that resolved to a different digest between the staging build and the production build, a dependency resolution that picked up a newer transitive version between builds, anything non-bit-for-bit-reproducible in the build process — all invisible until it causes an environment-specific bug nobody can reproduce because "it's the same code." Promoting the same digest closes that gap entirely, at the modest cost of a registry-to-registry copy step in the pipeline instead of a second build.

# Build once, promote the same digest -- not a second build per environment
docker buildx build --push -t ci-registry.internal/api:build-1842 .
digest=$(docker buildx imagetools inspect ci-registry.internal/api:build-1842 --format '{{json .Manifest.Digest}}')

docker buildx imagetools create \
  -t prod-registry.example.com/api:1.4.2 \
  ci-registry.internal/api@$digest

# Multi-arch publish from CI: one tag, multiple platform manifests underneath
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  --push -t registry.example.com/api:1.4.2 .

Gotcha

"We deploy by tag, and our tags are semver, so we're fine" quietly assumes the registry actually enforces that a semver tag, once pushed, can never be silently replaced — most registries don't enforce this unless you turn on an immutability policy explicitly, so the assumption is usually untested rather than actually true. The way this bites in practice: a hotfix gets pushed under the same tag as the original release "just this once, to save a version bump," and now every audit trail, every "what exactly is running in production" question, and every attempt to reproduce a bug against "the same version" is potentially working from stale or simply wrong information, with no error or warning anywhere that this happened.

Try it

1. Push an image to a local registry (docker run -d -p 5000:5000 registry:2 is enough to try this against) under a tag, then push a different image under the identical tag, and confirm the registry accepted the overwrite silently. 2. Pull the same tag by both its tag name and its resolved digest (docker pull myrepo/img@sha256:...) after that overwrite, and compare what each retrieves before and after.

What you should observe

The tag-based pull after the overwrite retrieves whatever was pushed most recently under that tag name, with no indication anything changed — exactly the silent-mutability risk this unit describes, reproduced hands-on. A digest pinned before the overwrite continues to resolve to the original content forever, regardless of what happens to the tag afterward, which is the concrete demonstration of why a digest is the only truly stable reference and a tag, absent an explicit immutability policy, never actually is one.

Why does pinning a dependency or base image by digest rather than tag matter even in a registry where you fully control every push?

Even with perfect internal discipline about not overwriting your own tags, a base image you depend on that lives in a registry you don't control (a public image on Docker Hub, say) is fully subject to its maintainer's tagging practices, and python:3.13-slim resolving to a genuinely different digest next month than it did today — a routine, expected patch update — is exactly the behavior a tag is supposed to allow. Pinning by digest for anything where reproducibility matters more than automatically picking up upstream patches (a compliance-sensitive build, a bug you're actively trying to reproduce exactly) trades that automatic-patching convenience for certainty about what you're actually building against — a real tradeoff, not a strictly-better choice in every case.

What's the difference between a registry mirror and a registry proxy/cache, and which problem does each solve?

A mirror is a separate, independently-updated copy of a registry's contents you push to explicitly (or that syncs on a schedule) — useful for full redundancy or geographic locality, but it's a second thing you have to actually keep in sync. A pull-through cache (many registries, including Docker's own, support this mode) instead sits in front of the origin registry and transparently caches whatever gets pulled through it the first time, serving subsequent identical pulls from the cache without re-hitting the origin — this is specifically what fixes the CI-rate-limit problem from this unit's opening paragraph, because most of a CI fleet's pulls are the same handful of common base images repeated constantly, which a pull-through cache serves almost entirely from its own cache after the very first pull.

How would you publish a genuinely multi-architecture image such that a user on either amd64 or arm64 pulling the exact same tag gets a native image automatically?

A single docker buildx build --platform linux/amd64,linux/arm64 --push invocation (or the Bake equivalent from unit 04) produces one tag backed by a manifest list — a small index referencing one digest per platform — and the client's own docker pull automatically resolves to whichever platform-specific digest matches the machine doing the pulling, with zero user-facing complexity beyond the one shared tag. This is precisely the mechanism that makes "just docker pull python:3.13" work identically and natively on an Intel laptop and an Apple Silicon Mac and an arm64 cloud instance, without anyone needing to know or specify which architecture they're on.

Why might a private registry deployment choose to run its own vulnerability scanning rather than relying solely on a scan performed once at push time?

A CVE disclosed after an image was pushed and scanned clean doesn't retroactively re-scan itself — an image that was genuinely clean the day it was pushed can become known-vulnerable a month later purely because a new CVE was disclosed against something already sitting unchanged in its layers, and a push-time-only scan has no mechanism to ever surface that unless something re-scans the existing, already-stored image against the now-updated vulnerability database. Continuous or periodic re-scanning of images already at rest in the registry (which Docker Scout and most serious registry products support) is what actually closes that gap — treating a scan result as a permanent, one-time verdict rather than something with an implicit expiration is a common and avoidable blind spot.

What goes wrong when a CI pipeline builds an image, runs tests against it, and then rebuilds it again for the actual deployment push?

This is exactly the "build once, promote" principle's negative case spelled out: the image that was actually tested and the image that actually gets deployed are, strictly, two different builds, and any non-determinism between them (a floating base-image tag resolving differently between the two build invocations, a dependency resolver picking up a newly-published patch version in the gap between builds, cache-state differences) means "tests passed" is no longer a guarantee about what's running in production — it's a guarantee about a similar-but-not-identical artifact. The fix is mechanical, not aspirational: build exactly once, tag/push that one artifact to wherever tests run against it, and promote that same digest forward rather than triggering a second build step anywhere in the pipeline.

How should image retention/cleanup policy differ between a CI-internal registry and a production-facing registry?

A CI-internal registry accumulates an image per build, often many per day, and the vast majority are never referenced again within days of being superseded — an aggressive, short retention window (keep the last N builds per branch, or N days) is usually the right default, since the cost of a wrongly-deleted CI artifact is just re-running a build. A production-facing registry holding images that are or were actually deployed needs a much more conservative policy — anything that's ever been deployed to a still-running or recently-running environment, or that a rollback might need to reach for, shouldn't be casually garbage-collected on a time window alone; retention there is better tied to "is this still reachable by any deployment history" than to raw age.

What's the risk of a CI pipeline authenticating to a production registry using long-lived, broadly-scoped credentials?

A leaked long-lived credential (checked into a repo by accident, exposed via a misconfigured CI log, present in a compromised runner) grants whoever has it push access for as long as it remains valid and unrotated, which for a broadly-scoped credential can mean push access to every repository in that registry, not just the one pipeline that needed it. The mitigation is the same principle as least-privilege container configuration from unit 05, applied to CI identity instead of runtime configuration: scope credentials to exactly the repositories a given pipeline needs, prefer short-lived, workload-identity-based tokens (OIDC-federated cloud registry auth, where supported) over long-lived static secrets, and rotate anything that can't avoid being long-lived on a real schedule rather than "whenever someone remembers."

Lead-level: a security review wants every image in production traceable back to the exact CI run, commit, and approver that shipped it. How do you actually build that, rather than just promising it?

This is the provenance-attestation and promotion-pipeline machinery from this unit and unit 10, wired together deliberately rather than left as separate capabilities: build-time provenance attestations (unit 04's --provenance) capture the commit and builder identity automatically; the promote-by-digest pattern here means that same attested artifact, not a rebuild, is what actually reaches production; and an approval gate in the deployment pipeline itself (a required, logged sign-off before a specific digest is promoted to the production registry namespace) captures the human approver. The traceability claim is only as strong as its weakest link, so I'd specifically audit for any path that bypasses this chain — a manual docker push straight to the production registry by someone with direct credentials is the most common gap, and closing it usually means removing broad push credentials from human hands entirely, not just asking people not to use them.

Architecture & ecosystem decisions

When would you recommend a team not containerize a workload at all?

When the operational cost of containers buys nothing over the alternative — a single, simple script or long-running process on a well-understood host, deployed via a mature non-container pipeline the team already trusts, where the main things containers are good at (dependency isolation across many services, reproducible multi-environment parity, packaging heterogeneous stacks) genuinely don't apply because there's exactly one thing, in one language, on one kind of host. I'd also flag it for extremely latency- or hardware-sensitive workloads where even the modest namespace/cgroup overhead is unacceptable and a bare-metal or VM deployment is the honest answer. Containerizing everything by default, regardless of whether the problem it solves is present, is cargo-culting, not engineering judgment.

How do you decide between Docker Compose and a full orchestrator for a production system that's currently small?

I look at what's actually failing today, not what might fail at hypothetical future scale — a single-host Compose deployment with good monitoring, a solid backup strategy for its volumes, and a documented recovery runbook is a completely legitimate production architecture for many real, profitable systems, and adopting Kubernetes preemptively adds real operational surface (unit 09) for problems that haven't materialized. The concrete triggers that flip my answer: the system now needs to survive a single host failing without manual intervention, needs to scale a specific service independently of others under real load, or needs network-policy/multi-tenancy guarantees Compose has no model for at all — any of those is a legitimate "time to move" signal; "it feels more grown-up" is not.

What's the actual architectural difference between a sidecar pattern and just running two processes in one container?

A sidecar is a separate container, sharing specific namespaces or a network context with its main container (or, in Kubernetes, literally co-scheduled in the same pod) but independently deployable, independently restartable, and independently image-versioned — a logging shipper or a service-mesh proxy updates on its own release cadence without touching the main application's image at all. Two processes crammed into one container share fate completely: one process's crash, restart, or resource spike affects the other with no isolation, and there's no way to update one without rebuilding and redeploying both together. The one-process-per-container discipline from unit 05's PID-1 discussion is precisely what makes the sidecar pattern possible in the first place.

Is Docker Desktop necessary for a professional development setup, or is it overhead?

Depends entirely on the OS: on native Linux, Docker Engine runs directly with no VM layer and no Desktop product needed at all — Desktop there is a GUI convenience, not a requirement. On macOS and Windows, some VM-backed layer is unavoidable because the Linux kernel features containers depend on don't exist natively, and Docker Desktop (or an alternative like Podman Desktop, Colima, or a raw WSL2 setup) is what provides it — the real decision on those platforms is which specific implementation, given Desktop's licensing terms for larger commercial use and the genuine alternatives that have matured particularly on the WSL2/Linux-VM side.

How do you evaluate whether a team should adopt Docker Sandboxes or similar AI-agent container isolation, versus building their own sandboxing?

The build-vs-buy calculus here is unusually favorable to buying: correctly isolating an AI agent that can execute arbitrary generated code touches every mechanism from unit 05 (namespaces, cgroups, capabilities, seccomp) plus network egress control and filesystem scoping, all of which need to be right simultaneously, and getting any one wrong is a real security hole, not a minor bug. A purpose-built product doing exactly this (Docker's own Sandboxes offering being one recent, direct example) has almost certainly hardened against more of the actual escape techniques than a team's first internal attempt will have. I'd still push a team to understand what the product is actually doing under the hood — every mechanism named above — rather than trusting the isolation boundary as an unexamined black box, because "we bought a sandboxing product" isn't a substitute for knowing what question it answers.

Security

What's the single highest-leverage security change most teams haven't made yet?

Almost always base-image hygiene — running as non-root by default, on a minimal/hardened base rather than a general-purpose distro image (units 05 and 10 both converge on this from different angles). It's high-leverage specifically because it's a one-time, largely mechanical fix per image rather than an ongoing operational commitment, and in most real audits it resolves the visible majority of flagged findings faster than any runtime policy or scanning-tool rollout does. It's also usually the fix teams have heard about and simply haven't gotten to, which is exactly what makes naming it, unprompted, land well in an interview — it signals you know where the actual leverage is, not just the vocabulary.

How would you explain to a non-technical stakeholder why "we scan our containers" isn't the same as "our containers are secure"?

Scanning answers one question — does this image contain packages with publicly known vulnerabilities — out of the three-layer model this unit's u10 lays out (runtime configuration, image contents, provenance). I'd use an analogy stakeholders already have intuition for: scanning is like checking a building's fire code compliance for known hazardous materials — valuable and necessary, but it says nothing about whether the doors are locked (runtime configuration) or whether you can prove who actually built the building and with what materials (provenance/supply chain) if something goes wrong later. All three matter, and a team that's only invested in one has real, unaddressed exposure regardless of how clean their scan reports look.

What's the actual blast radius difference between a container escape on a rootful versus rootless Docker installation?

On a rootful daemon, a successful escape from the container's isolation typically lands the attacker with root on the host directly — full control. On a properly configured rootless installation, the same escape technique lands the attacker as the unprivileged host user the daemon itself runs as — a meaningfully smaller blast radius, since that user still needs a separate privilege-escalation path to reach actual root, rather than already being there. It's not a complete defense (the unprivileged user can still do real damage — read the operator's own files, pivot to whatever that user has access to) but "meaningfully smaller blast radius, not zero risk" is the precise, defensible characterization, versus either "rootless is a silver bullet" or "rootless barely matters," both of which overstate in opposite directions.

Should container image scanning be a CI gate that blocks merges, or an informational dashboard?

I lean toward a graduated gate rather than either extreme: block on newly-introduced critical/high findings in a team's own application code's direct dependencies (things a PR's author can actually act on immediately), but don't block merges over pre-existing findings in a base image the team doesn't control the patch timeline for — that belongs on a tracked, owned remediation backlog instead, the same CVE-burndown instinct from unit 05's lead-level question. A pure informational dashboard nobody's accountable for checking reliably gets ignored; a gate that blocks on everything, including things the current PR didn't introduce and can't fix, trains people to route around it rather than respect it.

Performance & debugging

A container's startup time has crept up over months of incremental changes. How do you find out why?

I'd time the build separately from the run — a slow build (more layers, uncached dependency installs) is a completely different problem from a slow runtime startup (application initialization, a healthcheck's start_period masking a genuinely slow boot, a dependency wait that's grown). For the runtime half specifically, instrumenting the application's own startup sequence with timestamps at each phase (config load, DB connection, cache warm) almost always finds one dominant contributor rather than a diffuse slowdown, mirroring the unit 03 lead-level answer about not assuming a build's slowness is evenly distributed — the same discipline applies to any "this got slower over time" investigation.

How do you distinguish a container that's slow because of resource limits from one that's slow for an unrelated reason?

docker stats during the slow period is the fast first check — pinned CPU near 100% of its quota or memory near its limit (with associated throttling or swap activity) points at the limit itself; low, unremarkable resource usage during the observed slowness points elsewhere, usually a downstream dependency call, lock contention, or I/O wait the container's own resource graph won't show. The trap worth naming explicitly (unit 11) is that low CPU usage doesn't rule out throttling within a sub-second accounting window that an average obscures — if the symptom is bursty, intermittent slowness rather than sustained slowness, I'd check for throttling events specifically rather than trusting an averaged utilization number.

What's the most common root cause behind "container performance is fine in isolation but degrades under real load"?

Shared-resource contention that a single-container test never exercises — several containers on the same host competing for the same CPU cores, disk I/O, or network bandwidth with no cgroup limits differentiating who gets priority under contention, which only manifests once enough load is actually competing simultaneously. The fix is rarely "make this one container faster" and usually "set explicit, deliberate resource requests/limits across the whole host's containers" so the scheduler (or, on Kubernetes, the actual scheduler) can make informed placement and throttling decisions instead of every container silently assuming it has the whole host to itself, which was only ever true in the isolated test.

How would you profile exactly which layer of a slow multi-stage build is the bottleneck?

BuildKit's own per-step timing output (visible in the default progress display, and more precisely with --progress=plain) reports wall time per instruction directly — no separate profiling tool needed for the first pass. Once the slow instruction is identified, the follow-up question is whether it's slow because of genuine work (a real compile, a real test suite) or avoidable re-work (a cache miss that shouldn't be missing, unit 03's stale-apt-get-update-layer pattern) — I'd check cache-hit status for that specific step before assuming the underlying work itself needs optimizing, since a huge fraction of "slow build step" complaints are actually "cache miss that a small Dockerfile reordering would fix," not a genuinely slow operation.

Tooling, versions & upgrades

How do you decide which Docker Engine version to run in production, given the pace of releases?

I don't chase every release — I track the maintained-release lifecycle (Docker publishes a defined support window per major version) and stay within it, upgrading on a scheduled cadence rather than immediately on every release or, at the other extreme, only when forced by an EOL deadline. For anything handling genuinely sensitive workloads, I'd also watch the security-advisory feed specifically and pull forward an upgrade that addresses a CVE relevant to my actual configuration, rather than waiting for the next scheduled window regardless of severity — the schedule is a default, not an excuse to ignore an urgent patch.

What's your approach to keeping Compose files and Dockerfiles from silently drifting from current best practice as the ecosystem moves?

Periodic, deliberate review rather than assuming "it still works" means "it's still good" — the two are different claims, and a Dockerfile written years ago that still builds and runs correctly can easily be missing cache mounts, secret mounts, or multi-stage patterns that didn't exist or weren't yet idiomatic when it was written. I'd treat this the same as dependency-update hygiene: a recurring, scheduled pass (not necessarily frequent) specifically asking "would we write this differently today," rather than only touching these files reactively when something breaks.

How do you keep a team's local Docker Desktop versions from becoming a source of "works for me" bugs?

Pin a minimum supported version organization-wide and check for it in an onboarding script or a Makefile target rather than trusting everyone remembers to update, since Desktop's own update cadence and default settings (resource allocation, filesystem-sharing mode) can meaningfully change behavior between versions in ways that are easy to miss until someone's bug report only reproduces on their machine. For anything genuinely version-sensitive, documenting the minimum tested version explicitly, in the same place the Compose file itself lives, closes the gap between "should be using a current version" and actually knowing whether the team is.

What's the honest tradeoff in adopting Docker Build Cloud versus self-hosted build infrastructure?

Build Cloud trades infrastructure ownership and the data-residency question (unit 04's big-Q&A-adjacent point) for near-zero setup and a persistently warm cache across your whole team and CI fleet — genuinely valuable for teams whose CI is currently paying a cold-cache tax on every ephemeral runner. Self-hosted remote builders keep everything inside your own network boundary and let you tune hardware exactly to your build profile, at the cost of someone on your team owning that infrastructure's uptime and capacity planning. Neither is unconditionally better — it's a genuine buy-versus-build tradeoff that depends on how sensitive the build context is and how much spare engineering capacity exists to own infrastructure.

Legacy and migration reality

A codebase still uses Compose V1 syntax and the standalone docker-compose binary. What's the actual migration path?

Mechanically smaller than it sounds for most files: the Compose Specification V2/V3-era files that docker-compose V1 read are, for the large majority of common fields, directly compatible with what docker compose (V2, the current plugin) reads — the migration is mostly "stop invoking the standalone binary, invoke the plugin subcommand instead" plus a review pass for any V1-specific quirks (some deprecated top-level version declarations, a handful of fields that changed meaning). The bigger risk isn't syntax incompatibility, it's teams that never revisit the file at all once it "still works" with the old binary installed alongside the new plugin — which papers over the migration rather than completing it, and eventually breaks when the old binary stops being available on a fresh machine.

What do you meet in older Docker-based codebases that's now clearly outdated?

docker-compose (hyphenated, V1) invocations instead of docker compose; single-stage Dockerfiles installing a full build toolchain that ships in the final image with no multi-stage split; --link flags instead of user-defined networks with embedded DNS; images built and pushed with mutable :latest-only tagging and no digest pinning anywhere in the deployment path; Content Trust references in old security documentation that no longer apply to current Engine releases; and Dockerfiles with no # syntax=docker/dockerfile:1 pin, quietly depending on whatever frontend version the daemon happens to bundle. Spotting these unprompted in a code-review exercise is a fast, concrete way to demonstrate currency.

Is it worth migrating a stable, working Swarm cluster to Kubernetes purely to "modernize"?

Not on that reasoning alone — this is the direct case where unit 09's lead-level judgment question applies concretely: modernization for its own sake, with no specific unmet operational need driving it, is a real cost (migration effort, new operational surface, a genuine learning curve for the team) against a benefit that's mostly reputational rather than functional. I'd want a specific answer to "what can't we do today that we need to do" before recommending the migration — if that answer is solid (a genuine scaling, network-policy, or ecosystem-tooling need Swarm can't meet), migrate deliberately; if it's "everyone else has moved on," that's a weaker basis for taking on real migration risk and cost.

What's the risk of a team that's been running the same base images, unpatched, for a long stretch because "nothing's broken"?

Accumulated, disclosed-and-unpatched CVEs that a scan run today will surface all at once, in a pile large enough to be genuinely intimidating to triage — the exact opposite of the steady, small-batch remediation this unit's security material recommends, and a predictable consequence of treating "still builds and runs" as evidence of health rather than checking directly. The fix, once discovered, is the same incremental burndown discipline named repeatedly across this guide (units 02, 05, 10): don't try to fix everything in one heroic push, prioritize by actual exploitability and exposure, and put a recurring update cadence in place going forward so the pile can't silently regrow to this size again.

Judgment & scenarios

What do you flag in code review of a new Dockerfile?

Missing multi-stage split for anything with a build toolchain; a base image that isn't pinned to a specific tag (or, better, digest) for anything deploy-bound; secrets reaching the image via ARG/ENV/plain COPY instead of a secret mount; no non-root USER; a missing or overly-broad # syntax pin; cache-unfriendly instruction ordering (invalidating everything on every source change instead of installing dependencies before copying source); and no healthcheck on anything meant to be depended on by another service. None of these individually block a PR outright in every context, but a Dockerfile hitting several of them at once is a signal the author hasn't internalized current practice yet, worth a substantive review comment rather than a rubber stamp.

How do you onboard a team that's never worked with containers onto a Docker-based workflow?

Teach the two-mechanism split (namespaces answer "what can it see," cgroups answer "how much can it use," unit 05) and the layer-caching model (unit 02) first — those two concepts explain the majority of "why does it behave this way" questions a newcomer hits. Then get them running something real quickly with Compose (unit 08) rather than starting with raw docker run flags, since Compose's declarative shape matches how most people actually think about "the app I'm running" better than a long flag list does. I'd explicitly defer BuildKit internals, multi-platform builds, and orchestration to a second pass — front-loading everything at once is how a promising onboarding turns into "containers are confusing" as the lasting impression.

Production incident: a service is intermittently unreachable, and nobody's sure if it's the application, the network, or the host. How do you triage with only Docker-native tools?

I'd separate the layers in the order this unit's material builds them: first, is the container itself healthy (docker inspect's state, restart count, OOMKilled) — rule out the runtime crashing outright. Second, is the network layer actually correct (unit 06's diagnostics — is it on the network it's supposed to be, is the embedded DNS resolving, is the app bound to the interface it needs to be) rather than assuming the app logic itself is at fault. Third, only once both of those check out clean, look at the application's own behavior under the specific conditions the intermittent failures correlate with (load, time of day, a specific request pattern). Most "intermittent and nobody's sure" incidents resolve once someone actually walks this order instead of guessing at the most dramatic-sounding layer first.

How would you decide, six months into adopting a new container-security tool or process, whether it's actually paid off?

Measure what it claimed to fix, concretely: has the fleet's total flagged-CVE count actually trended down, or just moved to a dashboard nobody triages; has time-to-patch for a newly disclosed critical CVE against a widely-used base image measurably shortened; has the number of containers still running as root, or still using --privileged without a documented justification, gone down. Then weigh the honest cost side too — engineering time spent maintaining scanning-tool false-positive suppressions, CI time added, developer friction from a new blocking gate — the same way any adoption decision in this guide should weigh benefits against a real, named cost rather than treating adoption as automatically justified once it's underway. A security process that's added real friction with no measurable improvement in the metrics it was meant to move is worth revisiting, not defending on principle.

14 Night-before cheat sheet

  1. What it is. Docker is a layered system: the docker CLI talks to dockerd (the daemon, handling images/networks/volumes/the API), which delegates actual container execution to containerd (image storage, lifecycle), which delegates process creation to runc (the OCI-runtime-spec reference implementation). Images and the runtime spec are OCI-standard, not Docker-proprietary.
  2. Where it is now. Docker Engine 29.8.0 (2026-09-03); Compose v5.5.1; Buildx v0.37.0 with a first-class Docker Build Cloud driver. containerd's image-store snapshotter is the default for fresh installs since Engine 29.0 (existing hosts keep the legacy overlay2 graph driver until migrated). cgroup v1 is deprecated but patched through May 2029; assume cgroup v2 on any current host.
  3. The two isolation mechanisms. Namespaces (PID/NET/MNT/UTS/IPC/USER) answer "what can it see"; cgroups answer "how much can it use." They're orthogonal — a container can be resource-limited but namespace-unisolated (--pid=host), or vice versa. --privileged disables essentially all of them at once; never a production default.
  4. Images are layers, containers add one more. Each Dockerfile instruction that changes the filesystem creates an immutable, content-addressed, shareable layer; a running container adds one thin writable layer on top (copy-on-write) that's discarded with the container unless explicitly persisted. Multi-stage builds keep build-only tooling out of the shipped layers entirely, which is both a size and a CVE-surface win.
  5. BuildKit is a DAG executor. Independent Dockerfile stages build in parallel; cache keys are content-addressed. Know the three BuildKit-only features cold: cache mounts (persist across builds, never in a layer), secret mounts (available to one RUN, never in a layer), heredocs (readable multi-line RUN blocks). Cross-compile (--platform=$BUILDPLATFORM on the build stage) instead of emulating, wherever the toolchain allows it.
  6. Storage: three choices, one rule. Bind mount for live host-path editing; named volume for data that must survive container recreation and be portable; tmpfs for secrets/scratch that must never touch disk. Volumes outlive containers unless you pass -v to rm or --volumes to compose down — deliberately, as a safety default.
  7. Networking: use a user-defined network, always. The default bridge has no name-based DNS; every user-defined bridge gets Docker's embedded DNS at 127.0.0.11. Port publishing (-p) programs real NAT rules (iptables/nftables) that bypass generic host firewall rules — and the classic bug is an app bound to 127.0.0.1 instead of 0.0.0.0 inside the container.
  8. Compose is a reconciliation engine, not a script. docker compose up converges toward the YAML's desired state; it does not rebuild on source changes without --build or Watch's rebuild action. Use healthchecks plus depends_on: condition: service_healthy for real readiness gating — plain depends_on only orders container start, not application readiness.
  9. Kubernetes replaced Swarm and dropped dockerd, not Docker. dockershim was removed in Kubernetes 1.24; every current cluster talks CRI-native to containerd or CRI-O directly, with no dockerd in the path. OCI images built by Docker run unchanged on any of them. Swarm is still shipped and patched, just not where new adoption or ecosystem investment goes.
  10. Security is three separate questions. Runtime configuration (rootless, dropped capabilities, seccomp, non-root), image contents (CVE scanning — Docker Scout; minimal/hardened bases — Docker Hardened Images), and provenance (SBOM and build attestations, Sigstore/cosign keyless signing — Docker Content Trust is deprecated and removed). A clean scan says nothing about the other two.
  11. Tags lie unless you make them not. A tag is mutable by default on almost every registry — the same tag can point at different bytes over time unless an immutability policy is configured. Pin by digest for anything needing real reproducibility; promote the same built digest through environments rather than rebuilding per environment, so "tested" and "deployed" are provably the same artifact.
