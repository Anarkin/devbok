Payment systems & integrations

cheatsheet · PCI DSS v4.0.1 · released 2024-06-11

This card treats payments as a field rather than one product, so it anchors on PCI DSS v4.0.1 (2024-06-11) — the only active version of the industry's baseline standard — while naming the Stripe and Adyen API generations, the EMVCo 3-D Secure revision and the card-network dispute rules current as of 2026-09-08 alongside it. Stripe and Adyen are the reference PSPs throughout, with .NET (Stripe.net / Adyen .NET SDK) syntax wherever a concrete example helps, matching the stack the topic names. The most recent citable move: EMVCo published a public-comment draft of 3-D Secure 2.4.0.0 in June 2026 (comment period closes 2026-07-01), and Stripe's next major API generation, Dahlia (2026-08-26), is already in preview one release behind the current stable line, Clover (2025-10-29).

01Stripe API essentials

docs: Stripe API reference
Auth
Authorization: Bearer sk_test_... / sk_live_... — test and live are fully separate stacks: customers, payment methods, webhooks, everything
Pin your API version
Stripe-Version: 2025-10-29.clover header, or set the account default in Workbench — never rely on the implicit default drifting under you
Create a payment (modern)
POST /v1/payment_intents with automatic_payment_methods[enabled]=true — one PaymentIntent per checkout attempt, confirmed client-side via Stripe.js/Elements
Create a payment (legacy)
POST /v1/charges — still works, but no 3DS/SCA branch; treat as legacy since PaymentIntents GA legacy since ~2019
Auth now, capture later
create with capture_method=manual, then POST /v1/payment_intents/{id}/capture
Off-session (saved card, no shopper present)
PaymentIntentCreateOptions { Customer, PaymentMethod, OffSession = true, Confirm = true } — C#/Stripe.net
Expand nested objects, one round trip
GET /v1/payment_intents/{id}?expand[]=latest_charge&expand[]=customer
Cursor pagination
GET /v1/payment_intents?starting_after={id}&limit=100
Fire a test webhook locally
stripe trigger payment_intent.succeeded
Forward webhooks to localhost
stripe listen --forward-to localhost:5000/webhooks/stripe — prints a real, throwaway signing secret
Tail live API calls while debugging
stripe logs tail

{
    Amount = 2000,
    Currency = "usd",

    AutomaticPaymentMethods = new PaymentIntentAutomaticPaymentMethodsOptions { Enabled = true },

02Adyen API essentials

docs: Adyen API Explorer
Auth
X-API-Key: <key> — not Bearer; generated per merchant/company account in the Customer Area
Create a payment (modern)
POST /checkout/v72/payments — one endpoint that adapts to the payment method offered
Classic integration (legacy)
Payment / Recurring / Payout APIs, frozen at v68 — don't start new integrations here
Idempotency
idempotency-key: <uuid-v4> header, unique per company account, valid 7–14 days after first submission
.NET SDK, idempotent create
checkoutApi.PaymentsAsync(request, new IdempotencyRequestOptions(idempotencyKey))
Auth now, capture later
captureDelayHours at create time, or explicit POST /payments/{pspReference}/captures
Card on file, merchant-initiated
shopperInteraction=ContAuth + recurringProcessingModel=Subscription on the stored payment method
Branch on the result
resultCode: Authorised · Refused · Pending · RedirectShopper · ChallengeShopper · IdentifyShopper
Duplicate submission in flight
HTTP 422/409, error code 704 ("request already processed or in progress") — back off, don't immediately resubmit
Breaking-change rule differs by API family
adding a response field is non-breaking on "new" APIs (Checkout, Balance Platform) but breaking on "classic" ones (Payment, Recurring, Payout, BinLookup)

03Idempotency & retries

docs: Stripe idempotent requests
Stripe header
Idempotency-Key: <key> on any POST, cached 24 hours — same key + same params replays the cached response; same key + different params errors
Adyen header
idempotency-key: <key>, cached 7–14 days
Key shape
derive from your own request id — order:{orderId}:attempt:{n} — never a fresh GUID per HTTP retry of the same logical operation
What it does NOT cover
it dedupes the PSP-side write, not your own side effects — still need a unique constraint on your own ledger/order row
Retry policy
exponential backoff + jitter on 5xx and timeouts; never blind-retry a 4xx except 409/429
Two different bugs, same symptom
"payment charged twice" (network-level, idempotency key fixes it) vs "fulfillment ran twice" (your webhook handler re-processing one event) — dedupe events by id too
Client-side double submit
disable the pay button on click and reuse the same PaymentIntent/idempotency key if the user double-taps
Amount changed, same key?
rejected by design — an idempotency key is a promise about one exact request, not "retry this order"

04Webhook handling

docs: Stripe webhooks
Verify before trusting (Stripe)
HMAC-SHA256 of {timestamp}.{raw_body} compared against the v1= value in Stripe-Signature, constant-time compare — only the v1 scheme is trusted; ignore any other scheme prefix
Verify before trusting (Adyen)
HMAC-SHA256 over the notification's additionalData.hmacSignature fields, base64-decoded key from the Customer Area
Stripe retry window
up to 3 days, exponential backoff, live mode — sandbox retries 3× over a few hours
Adyen retry behaviour
resends on any non-2xx response — return [accepted] fast, then process asynchronously
Ordering
not guaranteed by either PSP — dedupe/order by event id or pspReference, never by a created timestamp (distinct events can share one)
New in Stripe (Clover+)
thin events (v2 — small pointer, fetch the object on demand) vs snapshot events (v1 — full object embedded) — pick one shape per event destination, they use separate endpoints
Return 2xx fast
ack in well under 5s, queue the real work — a timeout looks exactly like a failure and triggers the retry train
Replay protection
Stripe's signature check tolerates a 5-minute clock skew on the timestamp by default; never set the tolerance to 0
Local dev
stripe listen --forward-to ... mints a throwaway signing secret without touching the live one
var json = await new StreamReader(Request.Body).ReadToEndAsync();
try
{
    var stripeEvent = EventUtility.ConstructEvent(
        json, Request.Headers["Stripe-Signature"], webhookSecret);
    // handle stripeEvent.Type, dedupe on stripeEvent.Id
}
catch (StripeException)
{
    return BadRequest(); // signature failed - never process an unverified payload
}
return Ok();

053-D Secure 2.x & SCA/PSD2

docs: EMVCo 3-D Secure
Current spec
EMV 3DS 2.3.1.1 (published 2025-08-11) — v2.4.0.0 is a draft in public comment, closing 2026-07-01; expect frictionless-flow refinements, not a rewrite
Frictionless vs challenge
risk-based — most authenticated 3DS2 transactions never show the cardholder a challenge screen at all
Legal driver
PSD2 SCA in the EEA/UK — two of {something you know, have, are} for most e-commerce card payments
Exemptions an issuer can apply
low-value (≤€30, with cumulative caps) · TRA (transaction-risk-analysis, below the issuer/acquirer fraud-rate threshold) · trusted beneficiary (shopper-whitelisted merchant) · recurring (after the first SCA'd payment)
Merchant-initiated / off-session
no challenge — authenticate once at setup, then ContAuth (Adyen) / off_session=true (Stripe) for renewals
3RI (3DS Requestor Initiated)
non-payment or delayed-authorization flows can still get a 3DS authentication without the cardholder present
Decoupled authentication
issuer authenticates out-of-band (a push into the banking app) instead of blocking the checkout on a redirect
SDK vs browser flow
native app uses the 3DS2 SDK integration; web checkout uses the browser (redirect/iframe) flow — different device-fingerprint payloads, don't mix them up
Liability shift
a completed 3DS authentication shifts most fraud-reason chargeback liability to the issuer — it does not cover "goods/services not received" disputes

06PCI DSS & scope reduction

docs: PCI SSC — PCI DSS
Current standard
PCI DSS v4.0.1 (2024-06-11) — the only active version; v3.2.1 retired 2024-03-31
Future-dated requirements
became mandatory 2025-03-31 (expanded MFA coverage, targeted risk analyses, authenticated internal vuln scans, etc.) — anything still labelled "best practice" in your gap analysis is stale; it's required now
Cheapest scope reduction
never let cardholder data touch your infrastructure — hosted redirect / PSP iframe (Stripe Checkout, Adyen Drop-in / Hosted Payment Page)
SAQ A
fully outsourced e-commerce, PAN never touches your infra (redirect or third-party iframe) — smallest questionnaire
SAQ A-EP
your page's own JS/DOM influences the payment iframe, even though the PSP's iframe still captures the PAN — easy to trip into by accident, e.g. a custom validation script on the checkout page
SAQ C-VT
virtual terminal, manual keying, one transaction at a time, no local card storage — common for phone-order flows
SAQ D
everyone else, and every service provider — full requirement set
PSP tokens
a token stands in for the PAN in your database; useless outside that PSP/merchant pairing
Network tokens (different from PSP tokens)
Visa Token Service / Mastercard MDES token, bound to a device or merchant, survives card reissue and updates automatically — increasingly what "save this card" actually stores under the hood

07Refunds & chargebacks

docs: Stripe disputes
Refund vs cancel/void
refund reverses a captured charge (funds move back, fees may not); cancelling an uncaptured/authorized intent just releases the hold, no fee
Partial refunds
supported by both PSPs, any number of partials up to the original captured amount
Refund timing
settles back to the issuer over days, not instantly — the cardholder's bank posts it, not the PSP
Dispute lifecycle
chargeback → PSP debits the merchant + opens a dispute → merchant submits evidence within the deadline (typically 7–21 days, network-dependent) → issuer/network decides → arbitration as a last resort
Reason code drives the evidence
fraud disputes and "goods/services not received" disputes need completely different evidence packets — never submit generic paperwork
Visa Compelling Evidence 3.0
for fraud disputes, cite ≥2 prior undisputed transactions (120–365 days old) sharing the same credential, plus one more matching signal (device/IP/shipping/user-id) effective 2023-04-15
Pre-dispute alerts
Verifi (Visa) / Ethoca (Mastercard) push real-time alerts so you can refund before the chargeback posts — cheaper than fighting it
Dispute fee
non-refundable on most PSPs regardless of outcome — budget it into unit economics, not just the disputed amount
Friendly fraud vs true fraud
identical reason code either way — only your own device/behavioural history across orders tells them apart

08Ledgers & reconciliation

docs: Stripe balance transactions
Golden rule
never mutate a ledger row — append-only entries; a correction is a new reversing entry, never an edit
Double-entry invariant
every entry has ≥2 legs (debit/credit) that net to zero per transaction — the trial-balance check is what catches bugs
Settlement ≠ revenue
a Stripe balance_transaction splits gross charge into amount / fee / net — reconcile against net, book fee as an expense; don't compare gross to your books
Idempotent ledger writes
unique constraint on (psp, event_id) or (psp, charge_id, type) so a re-delivered webhook can't double-post
Two reconciliation feeds, one truth
webhook (near-real-time, drives the ledger) vs the PSP's settlement/payout report file (daily or periodic, the audit check) — they must eventually agree
Multi-currency
store minor units (cents) as integers, convert only for display; capture the FX rate actually used at settlement, not at capture, if the PSP settles in a different currency
Available vs pending balance
payouts draw only from available — a fresh charge sits in pending until the PSP's hold period clears
Refund/dispute reversal
a new reversing entry dated at the reversal event, never a retroactive edit of the original charge's entry
-- append-only double-entry ledger, dedupe key is the natural key
CREATE TABLE ledger_entries (
  id           BIGSERIAL PRIMARY KEY,
  psp          TEXT NOT NULL,
  event_id     TEXT NOT NULL,
  account      TEXT NOT NULL,
  direction    TEXT NOT NULL CHECK (direction IN ('debit', 'credit')),
  amount_cents BIGINT NOT NULL,
  currency     TEXT NOT NULL,
  posted_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (psp, event_id, account, direction)
);

09Gotchas & pitfalls

docs: Stripe testing & edge cases
  • An idempotency key dedupes the HTTP write, not your own side effects. A webhook you process twice for the same event id is a different bug than a duplicated charge — dedupe both, separately.
  • Authorization holds expire (issuer-dependent, often around a week). A capture_method=manual intent left too long fails to capture even though the authorization once succeeded.
  • Turning on every payment method offers wallets/BNPL you never tested — automatic_payment_methods without a currency/country allowlist silently expands your error-path surface.
  • PaymentIntents can land in requires_action. Skip that branch and checkouts on 3DS-mandatory cards silently die instead of redirecting to the challenge.
  • A webhook signing secret is per-endpoint, not per-account. Rotating it for one registered endpoint and forgetting a second breaks that second endpoint silently, until the next event fires.
  • Resending an event doesn't cancel the automatic retry already in flight. Both the manual resend and the original retry can arrive — dedupe by event id regardless of how many times you asked for a redelivery.
  • Not every decline is terminal. insufficient_funds / do_not_honor are often worth an issuer-side retry after a delay; stolen_card / fraudulent must never be retried.
  • SAQ scope creep from a "harmless" custom field. A save-card form on your own domain that only forwards into a PSP iframe can reclassify you from SAQ A to SAQ A-EP without anyone noticing until the next assessment.
  • Reconciling by created timestamp instead of event id. Two distinct events can legitimately share a timestamp; only the id is a safe dedupe/order key.
  • Floating-point rounding on split payments or tax shares is where off-by-one-cent reconciliation breaks first show up — do the math in integer minor units.
