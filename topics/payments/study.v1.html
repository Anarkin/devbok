Payment systems & integrations

study · Stripe API 2026-08-26 “Dahlia” · Adyen .NET SDK v35.0.0 · PCI DSS 4.0.1 · released 2026-08-26

Payment integration in 2026 means orchestrating one or more PSPs (Stripe, Adyen, and increasingly a second processor for resiliency) behind idempotent, webhook-driven state machines, with PCI scope pushed onto the PSP via tokenization and hosted UI rather than absorbed by your own servers. Stripe's API now ships two webhook shapes side by side — full “snapshot” events, and, from the Clover release onward, lean “thin” events you fetch on demand — and its latest named version, Dahlia (2026-08-26), keeps extending Billing and Connect. Adyen's official .NET library jumped to a breaking v35 in mid-2025, replacing constructor-based models with object initializers; EMV 3-D Secure sits at 2.3.1.1, with 2.3.x's richer risk data now live on major PSPs. Most consequentially, PCI DSS 4.0.1's future-dated requirements — payment-page script inventory and tamper detection (11.6.1) chief among them — stopped being optional on 31 March 2026, so a “grandfathered” SAQ A integration that still loads third-party scripts unmonitored is now non-compliant, not just risky. Code throughout is C#/.NET (Stripe.net, Adyen's .NET library, ASP.NET Core) since that's the stated audience, but the underlying models — idempotency, webhook trust, state machines, ledgers — hold in any language.

01  PSP integration models

A payment service provider (PSP) exists to hide an ugly graph from you: card networks (Visa, Mastercard, Amex), issuing banks, acquiring banks, and increasingly local rails (Pix, iDEAL, Bacs, SEPA) that all speak different protocols and settle on different schedules. Stripe and Adyen are both PSP-plus-acquirer stacks — they hold the acquiring relationship themselves rather than routing through a third party — which is why they can offer a single API for authorization, capture, refunds and payouts instead of stitching together a gateway, a processor and a merchant account yourself. The mental model that matters at lead level isn't “how do I call the API”, it's “where does raw card data live, and who is liable for it while it's there”. Every integration choice below is really a choice about that.

There are four integration shapes, and they trade PCI scope against UI control. Direct/server-side API means your backend receives the PAN (card number) directly, typically from a form your frontend posts to your own server; you then forward it to the PSP. This is the highest-scope, and Stripe and Adyen actively discourage it — Stripe's raw card-token endpoints require special permission and Adyen's is intentionally undocumented for that flow. Client-side tokenization with hosted fields — Stripe Elements/Payment Element, Adyen Web Components — renders the card inputs inside an iframe the PSP controls; your JavaScript never sees the PAN, only a token or a completed PaymentMethod/payment-method encrypted blob. This is the sweet spot for most product teams: full control over surrounding UI, PCI scope collapses to SAQ A (or A-EP if you touch the iframe's integrity, see unit 06). Fully hosted checkout — Stripe Checkout, Adyen Drop-in in redirect mode, or a PSP-hosted payment page — hands the whole page over; you get a return URL and a webhook. Least engineering effort, least brand control, and it's still the right default for a first payment integration or a low-volume side project. Orchestration sits a layer above all three: a routing service (built in-house, or a vendor like Spreedly/Primer) that picks a PSP per transaction based on cost, success rate or geography, and normalizes their different object models behind one internal API.

Concretely, Stripe models a payment as a PaymentIntent: a stateful object you create once (amount, currency, capture method) and then confirm, possibly multiple times, as the customer completes authentication or retries. A PaymentMethod (card, wallet, bank redirect) attaches to it, and a successful confirmation produces one or more underlying Charge objects. Adyen's equivalent is the /payments call plus a PaymentDetails follow-up call for the same reason — both APIs had to solve “this might take three network round-trips because the issuer wants to challenge the customer,” and both converged on the same shape: create, then resolve. That convergence is the real lesson — once you've internalized Stripe's model, reading Adyen's docs is translation, not re-learning.

Recent reality: Stripe's default recommendation is now the unified PaymentElement, a single client-side component that renders whichever of 100+ payment methods you've enabled (cards, wallets, BNPL, bank debits) instead of one Element per method; the older per-method Elements (cardElement, ibanElement) still work but are the path you'll find in a five-year-old codebase, not the one you'd start today. Adyen's parallel move is Drop-in over hand-assembled Components for the same reason: one integration point, server-driven method list, less client code to keep in sync with what Risk has enabled this week.

Interview trap

Candidates say “we use Stripe Elements so we're PCI compliant.” Elements reduces scope (you self-attest with the shorter SAQ A questionnaire); it does not make you compliant by itself — you still have to actually complete the SAQ, keep TLS current, and, as of PCI DSS 4.0.1's now-mandatory 11.6.1, inventory and monitor every script that runs on the checkout page for tampering. A second, subtler trap: a PSP token is not a harmless opaque string forever — it can usually be charged again without re-authentication, so treat stored tokens (and the customer/PaymentMethod IDs that reference them) as sensitive credentials with their own access control, not as free-to-log identifiers.

Why do Stripe and Adyen both require a two-step create-then-confirm flow instead of a single call?

Because authentication (3-D Secure) is asynchronous by nature — the issuer might approve instantly, might redirect the customer to their banking app, or might need a second round-trip after a challenge. Modeling the payment as a persistent object you can re-query and re-confirm means your server doesn't have to hold a synchronous connection open for however long the issuer takes, and it gives you a stable ID to reconcile against webhooks, retries and support tickets. A single call-and-response API would force you to either block indefinitely or lose the transaction context between steps.

When would you deliberately choose a fully hosted checkout page over Elements/Components, at a company that already has frontend engineers?

When the cost of maintaining PCI scope and UI consistency for a low-traffic or non-core flow exceeds the value of owning the pixels — think an internal admin tool that occasionally takes a manual card payment, a one-off invoice-payment link, or a new market you're testing before investing in a branded flow. Hosted checkout also wins when you need the PSP's fraud and localization logic (available payment methods per country, language) with zero maintenance, which matters more early on than brand polish.

What's the actual difference between a PSP token (Stripe's PaymentMethod ID) and a card-network token (Visa Token Service / Mastercard MDES)?

A PSP token is scoped to that PSP — it's meaningless outside Stripe's or Adyen's systems and is what you store to charge a returning customer. A network token is issued by the card network itself and replaces the PAN everywhere, including inside the PSP; its value is that it survives card reissuance (a lost card gets a new PAN, but a well-implemented network token updates automatically via Account Updater-style flows) and it can carry better interchange rates. Increasingly, PSPs request network tokens under the hood on your behalf, so you may be benefiting from this without any code change — but if you're asked in an interview, know that they solve different problems: PSP tokens are about vaulting, network tokens are about the PAN's own lifecycle.

Your team wants to switch primary PSP without a customer-facing outage. What's the hard part?

It's rarely the API integration — it's the stored payment methods. Card tokens are not portable between PSPs; Stripe can't charge an Adyen token and vice versa. You either re-collect payment details from customers (friction, drop-off), use a PSP-agnostic vault like Basis Theory or VGS that both PSPs can tokenize from, or run a migration window where new charges go to the new PSP while old customers' saved cards are charged through the old one until they naturally re-enter details. The second hard part is webhook and reconciliation logic: it's usually written assuming one PSP's event shapes and IDs, so a second processor means an abstraction layer, not a find-and-replace.

What's the practical benefit of an orchestration/routing layer over multiple PSPs, beyond avoiding lock-in?

Success-rate arbitrage: issuers and networks have processor-specific quirks, and routing a declined authorization to a second PSP before giving up (“cascading”) recovers a real, measurable slice of revenue at scale — often 1–3% of otherwise-lost transactions. It also gives you leverage in interchange-plus pricing negotiations and a blast-radius limit when one PSP has an outage or a compliance freeze on your account. The cost is real: you now maintain two integrations, two webhook contracts, and a reconciliation process that has to merge two settlement report formats into one ledger.

What does "PSP-plus-acquirer" mean, and why does it matter that Stripe and Adyen are both that?

A classic gateway (like a legacy Authorize.Net setup) only routes the transaction to a separate acquiring bank you contract with directly; Stripe and Adyen are acquirers themselves (or have acquiring licenses), so they underwrite your merchant risk, hold the settlement funds, and can offer one contract and one API for authorization through payout. It matters because it's why disputes, reserves and payout holds come from the PSP directly rather than a bank you've never spoken to, and why "switching acquirers" and "switching PSPs" are the same project when you're on Stripe or Adyen.

How would you explain to a skeptical product manager why the checkout page can't just POST the card number to your own API?

Frame it as scope, not paranoia: the instant your server process handles a raw PAN, your entire deployment — logs, backups, load balancers, the VM images — falls inside PCI DSS's strictest tier (SAQ D), with quarterly scans and an on-site-equivalent assessment. Tokenizing client-side keeps the PAN inside the PSP's iframe and collapses that same checklist to a one-page self-attestation. It's a business decision with a dollar figure attached (assessor fees, engineering hours, ongoing scans), not a preference.

What breaks if you try to reuse the same client-side Elements instance across two different PaymentIntents?

An Elements/Components instance is bound to the client secret (Stripe) or session data (Adyen) it was mounted with; the DOM nodes stay but the underlying payment context doesn't follow a new intent. In practice teams hit this when retrying a failed payment without a full page reload — they update state but keep the old mount, and confirmation silently targets the expired intent. The fix is always the same: fetch a fresh client secret/session for the new intent and re-mount, rather than trying to "rebind" the existing instance.

A junior engineer proposes storing the last 4 digits and expiry of a card in your own database "for the receipts page." Where's the line?

That's fine and normal — last-4, brand, and expiry are explicitly out of PCI's cardholder-data definition when stored without the PAN, and every PSP returns them on the PaymentMethod/Card object precisely so you can display them. The line is anything that, combined with other fields, could reconstruct or verify the PAN: full card number, CVV (never store CVV, full stop, even encrypted), or magnetic-stripe track data. Storing the PSP's own token alongside last-4 is the standard, safe pattern.

How do you decide, at the architecture level, whether a new payment method (say, a BNPL provider or a local bank redirect) belongs behind your existing PaymentElement/Drop-in or needs its own bespoke integration?

If the PSP you're already on supports it as a payment method inside their unified element, that's almost always the right default — you inherit their webhook events, dispute handling and compliance work for free. Bespoke integration is justified when the method isn't offered by your PSP at all, when contractual terms require going direct (some BNPL providers negotiate better rates outside PSP resale), or when the method has fundamentally different settlement timing (e.g., a multi-day bank transfer) that your PSP's abstraction doesn't model well and you need the raw provider API to build correct customer messaging.

Stripe's automatic_payment_methods versus explicitly listing payment_method_types — why does the recommended default matter architecturally?

automatic_payment_methods lets the Dashboard-configured, Risk-approved method list drive what the PaymentIntent will accept, so enabling a new wallet or BNPL option for a market is a Dashboard change, not a deploy. Explicitly listing types is more predictable for testing and for markets with regulatory constraints on which methods you're allowed to surface, but it means your code and your Dashboard configuration can silently drift — someone disables a method in the Dashboard and your list still offers it, and the confirm call fails. Default to automatic unless you have a specific compliance reason not to.

02  Payment lifecycle & state

Every PSP payment is a state machine, and the state machine exists because authorization and capture are two different, separately reversible operations that happen to usually occur together. Authorization asks the issuer “will you honor this charge” and, if yes, places a hold on the cardholder's available credit or balance — no money has moved. Capture is the instruction to actually pull the funds; it can happen at authorization time (the default, capture_method=automatic in Stripe, straight-through in Adyen) or be deferred (capture_method=manual / Adyen's separate /payments/{id}/captures call). Deferred capture is what lets an e-commerce checkout authorize at order time but only capture — and only for the shipped amount — once the warehouse confirms stock. Get this wrong and you either capture money for items you can't fulfil, or you let an authorization expire (issuers release holds after a network-defined window, commonly around seven days, longer for some merchant categories and travel/hospitality) and have to re-authorize, which the customer's bank sees as a second hold.

Stripe's PaymentIntent.status and Adyen's resultCode encode the same underlying machine with different vocabularies: both need a state for “needs a payment method,” “needs the customer to complete authentication,” “an async method is pending bank confirmation,” and terminal success/failure/cancellation states. The states that trip people up are the non-terminal ones: requires_action (Stripe) / RedirectShopper (Adyen) means a 3-D Secure challenge or bank-redirect is in flight and your UI must resume the flow, not treat it as failure; processing means an async payment method (ACH debit, some wallets) has been accepted by the rails but won't have a final outcome for one to several business days — your order-fulfillment logic has to decide whether “processing” is good enough to ship (usually: not for high-value goods) or whether you wait for the terminal event.

The other axis of the lifecycle is cancellation. A void cancels an authorization before capture — no money ever moved, so it's free and instant from the network's perspective (the hold simply expires early). A refund reverses a capture that already happened — money moved and now has to move back, which takes the same multi-day settlement time as the original payment and, unlike a void, usually carries no processing-fee refund from the network even though your PSP may refund its own fee. Confusing the two in your data model (treating every cancellation as a refund, or vice versa) is a common source of finance-team escalations, because voids and refunds appear completely differently on a statement and in dispute defense.

Recent reality: both Stripe and Adyen now support multiple partial captures against a single authorization as a first-class feature (useful for split shipments), where a few years ago multi-capture required contacting support to enable. The design implication: your order model should track a list of captures against an authorization, not a single capture flag, even if today you only ever capture once.

Interview trap

“payment_intent.succeeded fired, so the money is in our account” is wrong twice over. First, succeeded means the authorization-and-capture sequence completed from the PSP's point of view — settlement into your bank account is a separate, batched process that lags by days (see unit 09). Second, for async methods like ACH, “succeeded” can still be followed by a return/failure days later if the bank account had insufficient funds or was closed — there is no card-network-style dispute here, it's a different failure mode that arrives as its own webhook and has to debit your ledger retroactively. Design your order-fulfillment gate around the payment method's actual finality window, not around the first success event you see.

Expected outcome

Cancelling an already-fully-captured intent fails with a state error — cancellation only works on an intent that still has money on hold, not money already moved, which is exactly the void-vs-refund distinction from the prose above made concrete.

Why does deferred (manual) capture exist at all — why not always capture immediately and refund if something goes wrong?

Refunding costs more than voiding in every dimension that matters: refunds take days to settle back to the customer (voids are same-day, since the hold simply lapses), refunds don't return the network's processing fee in most cases while voids never incurred a capture fee, and a pattern of frequent refunds on your account is a signal card networks' monitoring programs watch — too many can trigger scrutiny that a clean authorize/void cycle never will. Deferred capture is the correct default whenever fulfillment isn't instantaneous or certain, which is most physical-goods commerce.

A customer's authorization holds funds for a week, then your capture attempt fails with "the PaymentIntent could not be captured because it has expired." What happened and what do you do?

The issuer's authorization hold window lapsed before you captured — each network defines a rough validity period (commonly around seven days) after which the hold is automatically released back to the cardholder, and neither Stripe nor Adyen can force a capture past that. The fix is not retrying the same intent; you need a fresh authorization, which means the customer's payment method has to be re-run (ideally without re-prompting them if you have a stored, reusable PaymentMethod), and your fulfillment SLA should be built around not exceeding this window in the first place.

How would you model captures in your own database schema, given multi-capture is now standard?

Never a single boolean or amount on the order row. Model an authorizations table (one row per PaymentIntent/payment, with the authorized amount and status) and a captures table with a foreign key to it, one row per capture call, each carrying its own idempotency key and its own amount. Sum captured amounts against the authorized amount to know what's capturable-remaining, and treat "fully captured" as a derived state, not a stored one, so it can never drift out of sync with reality.

What's the risk of shipping product as soon as an async payment method (e.g., ACH debit) shows "processing" or "succeeded" rather than waiting for final settlement?

ACH debits can be returned by the receiving bank up to several business days after initial acceptance — insufficient funds, closed account, or an unauthorized-transaction claim — and unlike a card chargeback there's typically less structured evidence/defense tooling. For low-value, low-risk goods (a $10 digital download) many businesses accept this risk for better conversion; for high-value or easily-resold physical goods, gating fulfillment on the final settlement webhook (which both Stripe and Adyen expose distinctly from the initial acceptance event) is the standard risk control.

Adyen exposes both a synchronous /payments response and asynchronous webhooks for the same authorization. Which do you trust as the source of truth, and why?

The webhook, always — for exactly the reason 3-D Secure and async methods exist: the synchronous response can legitimately be a non-final "pending further action" state, and even a synchronous "authorised" response is Adyen's immediate read, not a guarantee that a later fraud check or issuer-side reversal won't change it before capture. The synchronous response is useful for immediate UI feedback ("processing your payment…"); the webhook (AUTHORISATION notification, correctly signature-verified) is what should actually flip your order state, exactly as covered in unit 04.

Why do both Stripe and Adyen require a separate confirm/complete step instead of returning a final result from the create call, even for a simple card payment with no 3-D Secure?

Because the API can't know in advance whether this particular transaction will need a challenge until the issuer's authorization response comes back with that information — risk-based authentication decides per-transaction (see unit 05), not per-integration. Splitting create from confirm also lets you build the payment method and validate the amount/currency before committing to the network call, and lets the same PaymentIntent be confirmed with a different payment method if the first attempt fails, without allocating a new object and a new ID for what is, to the customer, one attempt to pay.

How do you handle a capture call that times out at the network level — you don't know if it succeeded on the PSP's side?

Retry the exact same capture request with the exact same idempotency key. That's the entire point of unit 03: a timed-out request is ambiguous locally but not on the PSP's side, and re-sending with the same key returns the original result (whether that was success or a specific failure) rather than risking a second real capture. Never retry a capture with a freshly generated key "to be safe" — that's precisely how double-captures happen.

What does it mean for an authorization to be "incremental," and when would you use it?

Incremental authorization lets you raise the held amount on an existing, uncaptured authorization instead of voiding and re-authorizing for a higher figure — used for open-ended holds like hotel stays or car rentals where the final bill isn't known upfront, or a restaurant tab. Both major PSPs support it as an explicit API call distinct from a new authorization; it preserves the original auth date for expiry-window purposes and avoids putting a second hold on the cardholder while the first is still outstanding.

Your on-call engineer sees an order stuck in "requires_action" for six hours with no customer follow-up. What do you tell them to check, and what's the eventual resolution?

First check whether this is expected: requires_action is a customer-facing state, meaning the shopper abandoned the challenge page or closed the tab — it's often not a system bug at all. If it's genuinely stuck (webhook never arrived, or your handler crashed processing it), the resolution is to re-fetch the PaymentIntent/payment object directly from the PSP's API (never trust only the webhook stream for state you can also pull), and if it's still non-terminal after a reasonable window, treat it as abandoned: cancel it if uncaptured, or surface it to the customer to retry, rather than leaving orders in limbo indefinitely.

Why is "cancel an authorization" sometimes rejected by the PSP even though no capture has happened?

Some issuers process the authorization hold on their own timeline and won't accept a reversal message before it's fully posted on their side, or the acquirer's processor doesn't support real-time voids for that card brand/region, silently downgrading a void request into "let the hold expire naturally." This is one of the sharper edges of the abstraction: the PSP's API can accept your cancel call successfully while the actual release of funds to the cardholder still takes the network's normal expiry window — worth knowing before promising a customer "the hold will disappear immediately" in a support macro.

03  Idempotency & retries

The fundamental problem is simple to state and expensive to get wrong: over a network, a client that doesn't receive a response cannot distinguish “the server never got my request” from “the server processed it and the response was lost.” Every payment API call is a request to move or hold money, so retrying blindly after a timeout risks charging the customer twice; not retrying at all risks silently dropping a payment the issuer actually approved. Idempotency keys resolve this by moving the decision from “did the network succeed” to “did this specific logical operation already happen,” a question the PSP, not the network, can answer definitively.

Mechanically: you generate a unique key (Stripe and Adyen both recommend a UUID v4, but any sufficiently unique string works) once per logical operation — not once per HTTP attempt — and attach it to the request (Stripe: an Idempotency-Key header; Adyen: a idempotencyKey field in the request body). The PSP caches the first response it produced for that key, for a bounded window (Stripe currently retains keys for 24 hours), and returns the identical cached response — same object, same ID, same status code — for any subsequent request bearing that key, without re-executing the underlying charge. If you send the same key with a different request body, that's treated as a bug, not a retry, and the PSP rejects it rather than guessing which version you meant. If two requests with the same key arrive concurrently while the first is still being processed, only one is allowed to proceed; the other fails immediately with an in-progress error rather than racing.

The subtlety lead engineers are expected to know: the key has to be generated once, at the point where the logical operation is decided, and then reused across every retry of that same operation — not regenerated inside the retry loop. This sounds obvious written down and is nonetheless the single most common idempotency bug in real codebases, usually introduced by a well-meaning refactor that moves key generation from “when the job is created” to “when the HTTP call is made.” A durable job queue or outbox pattern is the natural home for the key: persist it alongside the job the moment you decide to charge someone, so a process crash and restart still retries with the same key instead of a fresh one.

Idempotency at the PSP boundary doesn't absolve you of idempotency at your own boundary. Your webhook handler, your internal “mark order as paid” endpoint, anything with an externally-visible side effect and at-least-once delivery upstream (which, per unit 04, webhooks always are) needs the same treatment: either natural idempotency (an UPSERT keyed on a business key, where applying the same write twice is a no-op) or an explicit dedup table — a unique constraint on the event/operation ID that makes a second attempt fail fast and get treated as “already handled” rather than reprocessed.

Retry strategy is the other half. Not every failure is the same: a 5xx or a connection timeout is transient and safe to retry (with the same key); a 4xx almost always means the request itself is wrong (bad parameter, expired card) and retrying identically will just fail identically — the fix is to change the request, or stop. Exponential backoff with jitter avoids synchronized retry storms across many customers' failed requests hitting the PSP at the same moment; a sane default is a handful of attempts capped at a total budget of well under a minute for anything in a synchronous checkout path, with genuinely async operations (payouts, batch refunds) allowed a longer, queued retry horizon.

Why 24 hours, specifically, for Stripe's idempotency key retention — what would break with a much shorter or much longer window?

It's a pragmatic bound on how long a retry is plausible versus how long the PSP is willing to keep response caches around: 24 hours comfortably covers any realistic retry storm, including a client that was down for a few hours and replays its outbox on recovery, without keeping unbounded state. Shorter (say, five minutes) would fail legitimate slow-recovery scenarios — a queue consumer that was paused for an hour would generate what looks like a brand-new charge on resume. Much longer serves little purpose since any client design should have converged on success or a permanent failure well within a day, and it costs the PSP more storage for the tail of keys nobody will ever replay.

Your service calls a downstream PSP, the HTTP call times out, but the PSP actually processed it successfully. What's the correct recovery, in order?

Retry the identical request with the identical idempotency key — that's it, that's the mechanism working as designed; the retried call returns the already-created object rather than creating a second one. What you must not do is fall back to "check some other way first" as a required step (e.g., always list recent charges before retrying) — that's extra complexity the idempotency key already makes unnecessary, though querying to confirm before user-facing messaging is reasonable defensive UX, not a correctness requirement.

How do you generate idempotency keys for an operation that can legitimately happen more than once for the same order — e.g., multiple partial captures?

The key has to encode the specific instance of the operation, not just the order: something like capture-{orderId}-{shipmentId} rather than capture-{orderId}. Get the granularity wrong in either direction and you either collide two legitimately-different captures into one (the second silently no-ops, and that shipment never gets billed) or fail to dedupe retries of the same capture (defeating the whole point). The rule of thumb: the key should be derivable purely from data that already uniquely identifies "this exact side effect," so recomputing it from scratch after a crash gives you back the same value.

Do you need an idempotency key for a refund the same way you do for a charge?

Yes, for the same reason and with the same failure mode if you skip it — an ambiguous-outcome retry of a refund call can double-refund a customer, which is a real financial loss with no dispute-style clawback path. It's easy to underweight because refunds feel "safer" than charges, but from the PSP's perspective a refund is just another money-moving POST, and it gets the identical idempotency treatment.

What's the difference between PSP-level idempotency keys and idempotency in your own internal APIs (e.g., an internal "mark order as fulfilled" endpoint)?

They solve the same problem at different boundaries. The PSP's key protects you from your own client-to-PSP network being unreliable. Your internal API needs the same protection against unreliability between your services — a retrying HTTP client, a message queue redelivering, a Kubernetes pod restarting mid-request — and the PSP's key does nothing for that hop. In practice this usually means propagating a request ID or using natural idempotency (an upsert on order ID) at every internal boundary that has a side effect, not just the outermost one.

How would you design idempotency for a webhook handler that has to call a downstream PSP API as part of processing the event (e.g., automatically issuing a follow-up refund when a fraud-review webhook fires)?

Two layers, composed: dedupe the inbound webhook by event ID first (unit 04) so a redelivered webhook doesn't even reach your business logic twice, and separately derive the outbound refund's idempotency key from the event ID itself (e.g. refund-for-event-{eventId}) so that even if your dedup layer had a gap, the downstream call is still safe. Defense in depth here is cheap and the failure mode (duplicate refund) is expensive enough to justify it.

A teammate argues idempotency keys are unnecessary if you just wrap the charge and the order-update in one database transaction. What's wrong with that reasoning?

A local database transaction can make your own state changes atomic, but it has no power over whether the PSP actually executed the charge before your process crashed or the network dropped — the transaction boundary is on the wrong side of the failure. You can roll your database transaction back perfectly and still have genuinely charged the customer at the PSP, or roll it back and have not charged them while your retry logic (lacking a key) charges them a second time on resume. Idempotency keys and local transactions solve different halves of the same problem and you need both.

How does idempotency interact with rate limiting — if a request is rejected with a 429, do you retry with the same key?

Yes: a 429 means the request was never processed at all, so it's unambiguously safe (and correct) to retry with the same key after backing off for the duration the PSP suggests (often via a Retry-After header). This is different from a genuine idempotency conflict (400 on key reuse with different parameters) or an in-progress conflict (409-style, meaning a concurrent identical request is still running) — both of those mean "don't just retry," where a 429 means "retry, just not yet."

What would you look for in a code review of someone's payment retry logic, beyond key placement?

Whether the retry budget is bounded and appropriate to the calling context (a synchronous checkout request shouldn't retry for two minutes while a customer stares at a spinner); whether backoff includes jitter to avoid thundering-herd retries after a PSP-side blip affecting many customers at once; whether the code distinguishes retryable failure classes (timeouts, 5xx, 429) from non-retryable ones (4xx validation errors, declined cards) instead of catching every exception the same way; and whether the idempotency key is derived deterministically from durable state, so a process restart mid-retry reconstructs the same key rather than losing it.

Is it ever correct to intentionally omit an idempotency key?

For genuinely read-only calls, yes — there's no operation to deduplicate. For anything that creates or mutates state, omitting the key is only defensible when you've made retries structurally impossible (a strictly one-shot, fire-and-forget call with no retry path anywhere in the stack, including infrastructure-level ones like a load balancer's automatic retry-on-timeout), which in a production payment path is rare enough that "we didn't bother" is the honest and wrong answer far more often than "we deliberately verified no retry path exists."

04  Webhook handling

A webhook exists because the synchronous API response you get from creating a PaymentIntent is a snapshot, not a promise: the customer's bank can still take seconds to minutes (card 3DS challenge) or days (SEPA Direct Debit, ACH) to actually settle the payment, and your checkout process can't hold an HTTP connection open that long. Webhooks are the PSP's way of telling you, out of band, “this thing you were watching just changed state.” That reframes the whole design problem: your webhook endpoint isn't a notification inbox, it's a second entry point into your payment state machine, one that fires asynchronously, out of order, and potentially more than once for the same event.

Every serious PSP webhook design shares three guarantees, and all three are guarantees of unreliability, not reliability: delivery is at-least-once (expect duplicates — your handler must be idempotent, per unit 03), delivery is not ordered (a payment_intent.succeeded can arrive before a payment_intent.created you'd naively expect first, especially across retries), and delivery is not guaranteed within any particular time bound (an outage on your end queues retries for hours). The corollary that trips people up: never trust the timestamp inside the payload to establish order. Use the object's own resource state fetched fresh, or compare event IDs/sequence data the PSP explicitly provides for ordering, not the event's created field.

Verification is non-negotiable and is the part people skip under deadline pressure. Anyone can POST a JSON blob that looks like a Stripe event to your public endpoint; without verifying it, an attacker can fabricate a payment_intent.succeeded and get you to ship goods for free. Stripe signs every webhook with a per-endpoint signing secret: the Stripe-Signature header carries a timestamp and an HMAC-SHA256 computed over {timestamp}.{raw request body}, and you recompute the same HMAC server-side and compare; Stripe's official libraries also enforce a default five-minute tolerance on the timestamp to blunt replay of an old, legitimately-signed payload. Adyen's HMAC verification works on the same principle over its own notification payload shape. The detail that breaks people in practice: you must verify against the raw, unparsed request body bytes, not a re-serialized version of the JSON your framework parsed and reformatted — ASP.NET Core model binding will happily hand you a re-shaped object whose byte-for-byte serialization no longer matches what was signed, so the signature check has to run on the raw stream before any model binding touches it.

What changed recently: Stripe's newer API versions (from the 2024-2025 “Clover” lineage onward, current as of this writing being the 2026-08-26 “Dahlia” release) support thin events as an alternative to the long-standing snapshot payload: instead of embedding the full object state at the moment the event fired, a thin event carries just the event type, the object ID, and a related-object reference, and your handler is expected to fetch the current state via the API when it needs it. This flips the reliability model in your favour — a thin event you process ten minutes late (after a retry backlog) always reflects a fetch-fresh state rather than a potentially-stale embedded snapshot, which directly closes the out-of-order-delivery gap described above. It's an opt-in, additive change; snapshot events remain fully supported, and most existing integrations still use them, so recognize both shapes rather than assuming one.

Your webhook handler needs to call your database and, on success, call a downstream service. The downstream call fails. Should you retry it inline before returning a response to the PSP, or return success and handle the downstream failure separately?

Return success to the PSP as soon as the event is durably recorded (written to your own event/outbox table), then process the downstream effect asynchronously with your own retry policy. Blocking the webhook response on a downstream call couples your PSP's retry timing and backoff to a dependency it knows nothing about, and if the downstream call fails, you now have to decide whether a non-2xx response (triggering a PSP-level retry of the whole webhook, including whatever already succeeded) is even the right recovery mechanism. Decoupling means the webhook's only job is "durably record that this happened," which is fast and rarely fails.

How do you decide what HTTP status code to return from a webhook handler when processing partially fails?

The status code is entirely a signal to the PSP about whether to redeliver, so the decision is "would redelivery help or hurt": a genuinely transient failure (DB connection blip) should return a 5xx so the PSP retries; a permanently unprocessable event (a bug that will fail identically every time) should still often return 2xx to stop a retry storm you can't benefit from, paired with alerting on your side, because an infinite redelivery loop for an error only you can fix wastes both sides' resources.

Why can't you rely on webhook delivery order to reconstruct a PaymentIntent's lifecycle (created → processing → succeeded)?

Retries are per-event: if the "created" webhook's first delivery attempt fails and gets queued for retry while "succeeded" fires and is delivered successfully on its first attempt, "succeeded" can physically arrive at your endpoint before "created" does. Your handler has to be written so that receiving events out of order still converges to the correct final state — typically by treating each event as "go re-check/reconcile the object's authoritative current state" rather than "apply this event's delta to whatever state I already have."

What's the security risk of logging the full raw webhook payload for debugging, and how do you mitigate it?

Payment webhook payloads routinely include PII and payment-adjacent metadata (customer email, last-4, billing address, sometimes internal order notes echoed back) that shouldn't sit unencrypted in a general-purpose log aggregator with broad read access — it quietly expands your compliance surface. Mitigate by redacting known-sensitive fields before logging, or logging only the event ID and type by default with full-payload capture gated behind a specific, audited debug flag.

A teammate wants to skip signature verification in a staging environment "since it's not real money anyway." What do you say?

Staging environments are a common vector for exactly this kind of forged-event testing precisely because they're assumed to be low-stakes, and staging code has a habit of getting copy-pasted into production or left half-migrated. There's also a practical cost to skipping it: you lose the chance to catch signature-verification bugs (wrong secret, body being re-serialized before the check) before they reach production. Keep verification on everywhere; use the PSP's official test-event triggers (which sign correctly) rather than disabling the check.

How would you design monitoring/alerting specifically for webhook health, separate from general API monitoring?

Track delivery lag (time between the PSP's event timestamp and your processing timestamp) and endpoint error rate as first-class metrics, alerting on both — a rising error rate means your handler is broken and the PSP's retry queue is silently growing as your safety net; rising lag with a flat error rate can mean you're falling behind on volume. Also alert on "PSP dashboard shows the endpoint disabled/failing," since PSPs will auto-disable a chronically-failing webhook endpoint after enough consecutive failures, which is a silent, total loss of your async payment-state pipeline if nobody's watching for it.

Explain thin events vs snapshot events, and when you'd choose one over the other for a new integration.

A snapshot event embeds the full object state as of the moment it fired; a thin event carries only the event type and an object reference, requiring a follow-up API call to get current state. For a new integration, thin events are generally preferable specifically because they can't go stale between firing and processing — a delayed retry re-fetches truth rather than replaying an old snapshot — at the cost of one extra API call per event and a hard dependency on the API being reachable when you process the backlog. Existing integrations built on snapshot events don't need to migrate reactively; it's an additive option, not a deprecation.

What's the failure mode of using a single shared webhook secret across multiple environments (dev, staging, prod)?

Any environment with access to that secret can forge signed events indistinguishable from real ones for every other environment sharing it, and a leak in your least-protected environment (dev, typically) compromises verification everywhere. Each environment should have its own webhook endpoint registration and its own distinct signing secret, so a compromise is contained.

Your on-call engineer wants to manually replay a webhook event from the PSP's dashboard to fix a stuck order. What should they check before doing that?

Whether the handler is genuinely idempotent by event ID for that event type — if it is, replaying is safe and often the fastest fix; if the handler has any non-idempotent side effect for that path (a bug, or a code path that predates the dedup layer), a manual replay can duplicate the very side effect you're trying to trigger, like re-sending a fulfillment notification. When in doubt, check the effect directly (was the order actually marked paid) rather than only checking whether the webhook fired.

How do webhooks interact with idempotency keys from unit 3 — are they the same mechanism?

No, they solve adjacent but distinct problems at different points in the flow. An idempotency key protects an outbound request you make to the PSP from being duplicated by your own retries. Webhook event-ID deduplication protects your handler from an inbound, PSP-initiated redelivery of the same notification. You need both, and confusing them (e.g., assuming your idempotency key somehow also dedupes webhook deliveries) leaves one side unprotected.

Design review: a webhook handler processes the event, updates the order, and then, in the same request, calls Stripe again to capture a manual-capture PaymentIntent. What would you flag?

Two things: first, that outbound call needs its own idempotency key derived from the event ID (unit 3's cross-boundary composition), or a retry of the webhook will attempt a duplicate capture. Second, and more structurally, doing a slow outbound API call synchronously inside the webhook handler risks the whole request exceeding the PSP's response-time expectations and being treated as a failed delivery even though your side effect actually succeeded — safer to durably record the intent to capture and perform the capture asynchronously, decoupled from the webhook's own request/response cycle.

05  3-D Secure & SCA

3-D Secure (3DS) exists to shift liability. Card networks and issuers built it so that, for a properly-authenticated transaction, fraud liability moves from the merchant to the issuer — which is why merchants care about it even though it adds friction: an unchallenged, undisputed chargeback for card-not-present fraud otherwise lands on the merchant's books. In the EU/UK, this got a regulatory teeth-grind with PSD2's Strong Customer Authentication (SCA) mandate: most online card payments now legally require two of three independent authentication factors (something you know, something you have, something you are) unless a specific exemption applies, and 3DS2 is the mechanism the industry converged on to satisfy that requirement while still authenticating in milliseconds for the overwhelming majority of transactions.

The generational shift that matters for anyone building today is 3DS1 → 3DS2. 3DS1 (the old pop-up asking for a static password) is deprecated everywhere that matters and increasingly rejected outright by networks; it's a legacy pattern you should recognize in an old codebase, never implement fresh. 3DS2 (EMV 3-D Secure, current stable spec version 2.3.1.1) is built around risk-based authentication: the issuer receives a rich device/browsing/transaction data payload (frictionless flow data) and, for a large majority of low-risk transactions, authenticates silently in the background with zero customer-visible friction — no OTP, no redirect, nothing. Only transactions the issuer's risk engine flags go to a challenge flow, the visible step-up (an OTP text, a banking-app push approval, a biometric prompt) that most people picture when they hear "3D Secure." Designing for 3DS2 correctly means designing the whole flow to gracefully branch at that point, not assuming every transaction challenges.

Concretely, in Stripe's model this surfaces as a PaymentIntent moving into a requires_action status: your client-side code (via Stripe.js/`PaymentElement`, or the mobile SDK equivalent) has to hand off to Stripe's own UI to render whatever the issuer demands — frictionless is invisible, a challenge shows a hosted iframe/redirect — and then resume confirmation once the customer completes it. Adyen's `/payments` + `PaymentDetails` two-call pattern is the same shape under different names: the first call can come back with an action object describing exactly what UI to render for the challenge, and the second call submits the result. In both models, the critical engineering point is the same: your backend does not implement the challenge UI itself, ever — that's exactly the part PCI DSS and card-network rules require to be handled entirely within the PSP/issuer's own controlled context, precisely so your servers never see or need to see the OTP or biometric result directly.

SCA exemptions are the practical lever for reducing friction without giving up liability shift entirely, and a lead engineer is expected to know they exist and roughly what they trade off, even without being an SCA compliance specialist: low-value transactions (below a small per-transaction threshold), transaction-risk-analysis exemptions (issuer or acquirer self-certifies low fraud rates and requests an exemption), recurring/subscription "merchant-initiated transactions" after an initial customer-present authentication, and trusted-beneficiary allowlisting the customer sets up with their bank. Exemptions are requested, not guaranteed — the issuer can still force a challenge regardless of what exemption flag you send, so your integration has to handle the challenge path even when you're actively trying to avoid it.

What changed recently: EMVCo's 3-D Secure spec sits at 2.3.1.1 as the current published, implemented version; EMVCo has a 2.4.0 version in its specification pipeline (public comment period activity through 2026) aimed at further data-element and messaging refinements, not yet the deployed baseline — treat 2.4.0 as "coming, track it" rather than "implement this instead of 2.3.1.1 today." On the PSP side, Stripe's current-generation API versions (the “Clover”/“Dahlia” lineage) carry full 2.3.1.1 support end to end, and both major PSPs have continued tightening their default frictionless-vs-challenge risk scoring, meaning the practical challenge rate for a well-configured integration keeps trending down year over year even as the underlying spec version hasn't jumped.

Why does risk-based/frictionless 3DS2 authentication still count as "strong customer authentication" if the customer does nothing visible?

The strength comes from the issuer's real-time risk assessment substituting for an explicit two-factor challenge, which regulators accepted specifically to avoid degrading conversion for the (very large) fraction of transactions that are obviously legitimate from device, behavioral, and transaction-context signals. It's a regulatory-sanctioned trade: friction is reserved for transactions where the risk signal genuinely warrants it, rather than applied uniformly.

A PaymentIntent is stuck in requires_action for three days because the customer never returned to complete the challenge. What do you do?

Nothing forces a resolution on its own — the PaymentIntent simply stays in that state until the customer resumes and completes (or definitively abandons) the flow, subject to the PaymentIntent's own expiry window. Operationally, treat it like an abandoned cart: don't reserve inventory or promise fulfillment against it, surface a "resume payment" path if the customer returns, and let it lapse if they don't rather than building special-case cleanup logic around it.

How would you decide whether to request an SCA exemption for a given transaction, as an architectural/product decision rather than a technical one?

It's a fraud-rate-vs-conversion trade the business has to own, informed by data: low exemption use maximizes liability protection but adds friction (and challenge abandonment) to more transactions; aggressive exemption use improves conversion but accepts more fraud liability landing on the merchant. Transaction-risk-analysis exemptions in particular require the requesting party (acquirer/PSP) to maintain a low enough fraud rate to keep qualifying, so it's not a one-time settings toggle — it needs ongoing monitoring.

Explain why your backend never directly handles the 3DS challenge UI, in terms of what problem that restriction actually solves.

It keeps the OTP/biometric/challenge result inside a context the issuer and PSP fully control end-to-end, so your servers never see (and therefore never have to protect) that authentication material — which both shrinks your compliance surface (unit 6) and closes off an entire class of attack where a compromised merchant server could intercept or replay authentication data. The PSP's SDK/hosted iframe is the trust boundary by design, not an implementation convenience.

What's the difference in how Stripe and Adyen structurally represent "the issuer wants a challenge" in their APIs?

Stripe surfaces it as a PaymentIntent status transition to requires_action, with the client secret driving the front-end SDK to render the right UI. Adyen surfaces it as an action object returned directly in the /payments response, which your front end passes to the Web/Native Components library to render, then submits the result via PaymentDetails. Different object shapes, same underlying idea: the response tells the client "render this specific thing, then call back."

Why is 3DS1 considered deprecated rather than just "older but still fine"?

Beyond the weaker security model (a static password is phishable and often poorly remembered, undermining the whole point), card networks have been actively sunsetting 3DS1 message support, and issuers increasingly don't process 3DS1 authentication requests at all, meaning an integration still built on it will see authentication attempts silently degrade or fail rather than merely underperform. It's not a stylistic legacy pattern, it's on a real deprecation timeline.

How do you test 3DS flows without waiting for real issuer behavior, and what's the limit of that testing?

Both major PSPs provide dedicated test card numbers that deterministically trigger frictionless-success, challenge-required, and challenge-failure paths in test/sandbox mode, which is sufficient for verifying your integration handles every status transition correctly. What it can't validate is your actual real-world frictionless rate, since that depends on live issuer risk scoring you don't control and can't simulate — that only shows up in production analytics after launch.

A mobile app team wants to build their own native challenge UI instead of using the PSP SDK's rendering, for better brand consistency. What do you tell them?

It's generally not permitted by the card network / EMV 3DS specification for exactly the trust-boundary reason above — the challenge has to be rendered within the flow the issuer's ACS (Access Control Server) expects, and the SDK exists specifically to implement that spec correctly (including things like a required "in-app" 3DS SDK integration mode with its own certification). Brand consistency has to be achieved through the SDK's supported customization hooks, not a full rebuild, or the integration risks failing certification or issuer-side rejection.

Where does 3DS fit for a merchant-initiated recurring subscription charge — does every renewal go through a challenge?

No — the standard pattern is to run full customer-present authentication (potentially including a 3DS challenge) once, at the initial subscription setup, then use the merchant-initiated-transaction exemption for subsequent automatic renewals, since the customer isn't present to complete a challenge anyway. The initial authentication is what establishes the mandate/consent that justifies the exemption on every renewal after it.

What operational metric would tell you your 3DS integration is misconfigured, versus just seeing normal issuer-driven friction?

An abnormally high challenge rate relative to industry/PSP benchmarks for your transaction profile is the first signal — it often means you're not sending enough of the optional-but-recommended risk data (billing address, browser/device fingerprint fields, prior-transaction history) that lets the issuer's risk engine confidently go frictionless. A high challenge-abandonment rate specifically (challenge shown, never completed) points more at UX friction than at the underlying auth decision.

Is 3DS relevant outside the EU/PSD2 context, e.g. for a US-only merchant?

Yes, though the regulatory mandate is EU/UK-specific — US card networks still support and encourage 3DS2 for its liability-shift benefit on card-not-present transactions, it's simply optional rather than legally required. A US merchant with meaningful card-not-present fraud exposure often adopts it voluntarily for the same liability-shift economics, just without a regulator forcing the decision.

06  PCI DSS scope

PCI DSS (Payment Card Industry Data Security Standard) exists because the card networks, not any government, wanted a shared floor for how anyone touching cardholder data protects it, enforced through the acquiring relationship rather than statute: fail to comply and your acquiring bank can fine you or terminate your ability to process cards at all. The single most important architectural idea in this unit, and the one that actually shows up in interviews, is that PCI scope is not about how big your company or codebase is — it's about which systems touch, process, transmit, or store the primary account number (PAN) or other sensitive card data, full stop. The entire practice of "PCI scope reduction" is the engineering discipline of architecting your systems so that as few of them as possible ever touch that data, because every system in scope inherits the full weight of the standard's ~300+ requirements, and every system kept out of scope doesn't.

This is where the integration-model choice from unit 01 pays off concretely. A fully-hosted checkout redirect or a properly-implemented client-side tokenization flow (Stripe Elements, Adyen Web Components/Drop-in) means raw card data flows from the customer's browser directly to the PSP — your servers never receive it, so your servers are dramatically reduced in scope. A direct-API integration where your backend receives raw PAN and forwards it to the PSP puts your backend, and everything that backend talks to, fully in scope. This single decision is why "just use the PSP's hosted fields" is the overwhelmingly dominant recommendation for any team without a very specific reason to handle raw card data themselves.

SAQ (Self-Assessment Questionnaire) types formalize how much scope you're claiming and, correspondingly, how much you have to prove: SAQ A is the lightest, for merchants who fully outsource all cardholder-data handling to a PCI-compliant third party via redirect or an iframe they don't control the content of (roughly 20-odd requirements); SAQ A-EP applies when your page directly controls the payment page/iframe container even though the card data itself still flows straight to the PSP (client-side tokenization, e.g. Stripe.js's Elements embedded in your own page) — more requirements than A because your page's own script-injection and man-in-the-browser risk is now in scope; SAQ D is the heaviest, for anyone actually storing, processing, or transmitting PAN themselves, and covers essentially the full requirement set. Landing in A versus A-EP versus D is a direct, mechanical consequence of the integration architecture, not a paperwork classification you can talk your way into after the fact.

What changed recently, and this is the single most citable fact in this whole document: PCI DSS 4.0.1 included a set of requirements that were published as "future-dated" — effective and auditable, but not mandatory until March 31, 2026. As of today (2026-09-08), that date has already passed, meaning every one of those future-dated requirements is now a hard mandatory control, not an upcoming one. The highest-profile of these for anyone running a payment page is Requirement 11.6.1: a change-and-tamper-detection mechanism for payment pages that must, at minimum, maintain an inventory of all scripts that execute in the customer's browser on the payment page and detect unauthorized modification of the page's script/HTTP header content — a direct regulatory response to e-skimming/Magecart-style attacks that inject malicious JavaScript into checkout pages. If you're advising a team today, "we'll get to 11.6.1 eventually" is no longer an accurate posture; it's already a compliance gap if unaddressed.

Requirement 6.4.3 (also future-dated, now mandatory) is the closely related sibling: it requires all payment-page scripts to be authorized, with a documented business justification, and to have their integrity verified (e.g., via SRI hashes or an equivalent mechanism) — the two requirements together mean "know every script that runs on your checkout page, know why it's there, and detect if it changes," which is a materially higher bar than most teams' pre-4.0.1 checkout security posture. Practically, this pushes toward Content-Security-Policy reporting, subresource integrity, and third-party tag-management audits as standard checkout-page hygiene rather than optional hardening.

Interview trap

“We use Stripe, so we're PCI compliant” is a category error candidates make constantly. The PSP being compliant says nothing about your own systems' scope — you can absolutely build a non-compliant integration on top of a fully-compliant PSP, most commonly by logging raw request bodies that happen to contain card data submitted through a form your server touches, or by building a "quick admin tool" that lets support staff type in a customer's card number to retry a charge. Compliance is a property of your architecture and operational practices, not something you inherit by vendor choice.

Try it
  1. Take an existing (or hypothetical) checkout page and classify it: does raw PAN ever touch a server you control, even transiently in memory or a log line? Map that answer to SAQ A, A-EP, or D.
  2. Audit the page for Requirement 11.6.1 in miniature: list every third-party script that executes on the page (payment SDK, analytics, tag managers, chat widgets, A/B testing tools) and, for each, write one sentence justifying why it needs to run there.
Expected outcome

Most teams doing the first exercise honestly discover at least one code path (a legacy support tool, a debug log statement, a manual-entry fallback for phone orders) that quietly pulls them toward SAQ D even though their "main" checkout flow is properly tokenized end-to-end — scope is determined by the worst-case path, not the intended one. The script audit typically surfaces at least one script nobody currently owns a justification for, which is precisely the gap 6.4.3/11.6.1 are designed to force into the open.

Why does using an iframe for card collection reduce PCI scope compared to a plain HTML form on your own page, even though both visually look like "a card form on our checkout page" to the customer?

The browser's same-origin model means your page's JavaScript has no access to the contents of a properly-configured cross-origin iframe — a malicious or compromised script running on your page literally cannot read the keystrokes typed into the PSP's iframe. A plain form on your own page has no such boundary: any script that runs on that page, including a supply-chain-compromised third-party script, can read the DOM your form lives in. That isolation is the entire mechanism by which SAQ A-EP's scope stays smaller than D's despite the card data still passing "through" your page visually.

Requirement 11.6.1 asks for a script inventory and tamper detection. What would you actually build to satisfy it, concretely?

A maintained manifest of every script permitted to execute on the payment page (ideally enforced via CSP so unlisted scripts are blocked, not just documented), paired with a monitoring mechanism that alerts on unexpected script changes — commonly implemented via CSP violation reporting, SRI hash mismatches, or a dedicated third-party page-integrity monitoring service that periodically snapshots and diffs the live page's script tags. The requirement is deliberately mechanism-agnostic; what it insists on is that unauthorized script changes get detected, not prevented by luck.

A support team wants an internal tool where an agent can type a customer's card number to process a manual retry over the phone. What's the PCI implication, and what's the better pattern?

That tool, the moment it exists, drags your servers into SAQ D scope, because raw PAN now transits a system you built and operate — regardless of how rarely it's used. The standard scope-preserving pattern is a PSP-hosted virtual terminal (both Stripe and Adyen offer this) that the agent uses directly, so the card data goes straight to the PSP's own compliant environment and never touches your infrastructure at all.

Does storing a PSP token (not raw PAN) in your database put you in PCI scope?

Generally no, for a properly-opaque PSP token that can only be redeemed by the specific merchant account that created it via the PSP's own API — the token itself isn't cardholder data, it's a reference to cardholder data the PSP holds. This is exactly why tokenization is the recommended pattern for "save this card for next time": you get the reusability without the storage liability. The nuance: verify the PSP's own documentation on what their specific token format guarantees, since not all "tokens" in the industry are created with the same security properties.

How would you explain the difference between PCI DSS and GDPR/data-privacy regulation to a teammate who conflates them?

PCI DSS is a card-network-enforced contractual security standard specifically about payment card data, enforced through your acquiring relationship; GDPR (and similar privacy laws) is government-enforced regulation about personal data broadly, with a completely different enforcement mechanism (regulatory fines) and a much wider scope of covered data (a customer's name and address are personal data under GDPR but aren't cardholder data under PCI DSS). A system can be perfectly PCI compliant and still badly non-compliant with privacy law, and vice versa — they're answering different questions.

What's the risk of "we'll just ask our PSP for an Attestation of Compliance and consider ourselves covered"?

The PSP's AoC covers the PSP's own environment, not yours — it says nothing about whether your integration architecture and operational practices keep your own systems out of scope or handle the scope they're in correctly. Relying on the PSP's AoC as your compliance answer is the same category error as "we use Stripe so we're compliant," just with a document attached to make it feel more official.

You're advising a team migrating from a direct-API card-collection integration to client-side tokenization purely for scope reduction. What do you tell them to expect, beyond "less PCI paperwork"?

Beyond the SAQ D→A-EP/A downgrade, expect a real engineering migration: the card form moves from your own markup to a PSP-controlled iframe/Component, which changes styling flexibility (you're customizing within the PSP's theming API, not writing arbitrary CSS), changes client-side validation and error-display flow, and removes any code path that read or logged raw card fields — which is worth auditing explicitly rather than assuming it's gone, per the earlier trap about logging.

Why does PCI DSS scope reduction matter enough to be a lead-engineer-level topic rather than purely a compliance/legal concern?

Because the architectural decisions that reduce scope (hosted checkout vs. Elements vs. direct API, from unit 1) are made by engineers, early, and are expensive to unwind later — a team that backs into SAQ D by accident because a "quick" feature routed raw card data through a backend often can't cheaply retrofit their way back to A-EP without a real redesign. Treating scope as an architectural constraint from day one, not a checkbox exercise after launch, is exactly the kind of judgment call a lead is expected to make proactively.

How does 6.4.3's "documented business justification for every script" requirement interact with common third-party tooling like tag managers, which dynamically load arbitrary scripts?

It creates real friction: a tag manager's whole value proposition is letting marketing add scripts without an engineering deploy, which is structurally at odds with "every script has a documented, reviewed justification." Teams satisfying 6.4.3 on a payment page typically either exclude the payment page from the tag manager's reach entirely, or lock the tag manager container itself down to a reviewed, versioned allowlist rather than letting it load dynamically on that specific page — the payment page ends up held to a stricter script-governance bar than the rest of the site.

If a merchant has been future-dated-noncompliant with 11.6.1/6.4.3 since March 31, 2026 and it's now September, what's the practical exposure?

Exposure runs through the same acquirer-enforcement path as any other PCI gap: at the next assessment (annual for most SAQ D/A-EP merchants, though timing varies), an assessor or the merchant's own honest self-assessment will flag the missing controls as a non-compliance finding, which the acquiring bank can act on — fines, increased transaction fees, or in a serious/persistent case processing restrictions. There's also the underlying risk the requirement exists to address: a checkout page without script-tamper detection has had six extra months of exposure to exactly the e-skimming attack class 11.6.1 targets.

07  Refunds & chargebacks

Refunds and chargebacks are both "the customer gets their money back," and interviewers specifically probe whether you understand why treating them as the same event is wrong. A refund is voluntary and merchant-initiated: you decide to return the money, you call the PSP's refund API, the PSP reverses the transaction, and (aside from the PSP's own processing/refund fee policy) the story ends there. A chargeback (dispute) is adversarial and issuer-initiated: the cardholder (or, less often, the issuer proactively on fraud signals) contests the charge with their bank, the bank yanks the funds back from you immediately, pending resolution, and typically levies a separate dispute fee on top — regardless of whether you ultimately win. A merchant with a healthy refund rate and a healthy dispute rate are two completely different signals: high refunds might mean generous policy or product-fit issues; high disputes usually means fraud, unclear billing descriptors, or a support/communication failure that pushes customers to their bank instead of to you.

The chargeback lifecycle, and the part most engineers have never actually seen because it lives mostly in ops/support tooling: a dispute opens (funds debited from your PSP balance immediately, a `charge.dispute.created`-style webhook fires), you have a limited window (commonly a few weeks, network- and reason-code-dependent) to submit evidence if you want to contest it, the issuer/network reviews and decides, and funds either return to you (won) or stay reversed (lost) — with the dispute fee typically non-refundable either way. Reason codes matter: "fraudulent transaction," "product not received," "duplicate charge," and "subscription canceled" each call for different evidence (proof of delivery/tracking for the second, cancellation-flow logs for the fourth), and a generic "here's our terms of service" response performs poorly across the board.

Dispute-prevention programs are the modern, pre-chargeback layer worth knowing exists even if you never operate one directly: Visa's Verifi and Mastercard's Ethoca are alert networks that notify a merchant when a cardholder contacts their bank about a transaction, before a formal dispute is filed — giving the merchant a window to refund voluntarily (cheaper, no dispute fee, no ding to dispute-rate metrics that risk network monitoring programs) instead of letting it escalate into a full chargeback. Stripe and other PSPs surface these alerts through their own APIs/dashboards as an integration option, and a mature payments stack increasingly treats "did we get a Verifi/Ethoca alert" as an earlier, cheaper intervention point than "did we get a dispute."

What changed recently: PSPs have been investing heavily in automating the evidence-submission side of dispute defense — Stripe's Smart Disputes (built on Stripe's own AI tooling) automatically assembles and submits chargeback evidence for eligible disputes, pulling from data Stripe already has about the transaction and, where connected, from the merchant's own order/fulfillment data, meaningfully raising win rates on op-ex-losing "not worth a human's time" small disputes that merchants previously wrote off. This matters architecturally: if you want automated evidence submission to work well, your order/fulfillment/customer-communication data needs to be reachable in a shape the automation can actually consume (structured, timestamped, linkable by PaymentIntent/charge ID) — which is a real integration requirement, not just a dashboard feature you toggle on.

The engineering-relevant nuance beyond the money: a chargeback almost always needs a corresponding update to your internal state, not just the PSP's balance — the order needs to reflect "disputed" (possibly distinct from "refunded," since you might still win it back), inventory/fulfillment decisions may need to pause pending outcome, and your ledger (unit 08) needs an entry type that isn't a plain refund, because the money movement timing and the possible-reversal-of-the-reversal shape is genuinely different from a refund's clean, final, one-directional flow.

Interview trap

“We refund the customer as soon as they open a dispute, to avoid the dispute fee” sounds proactive but is usually backwards as a blanket policy: a chargeback debit already happened the moment the dispute opened, so refunding on top of that after the fact double-returns the money (once via the automatic chargeback debit, once via your voluntary refund) unless you're very careful about the sequencing and cancel/skip the refund if a dispute is already in flight. The dispute-fee-avoidance window is before a formal dispute is filed — that's exactly what Verifi/Ethoca alerts exist to catch — not after.

  2. Draft, in writing, what evidence you'd submit to contest a "product not received" dispute for a real order in your system, based only on data your system actually captures today. Note any gaps.

The simulated dispute fires a dispute-created event and debits the test balance immediately, mirroring production behavior exactly (minus real money). Why does a high dispute rate matter more to a PSP/acquirer than a high refund rate, even if both represent "money going back to customers"?

Card networks run monitoring programs (Visa's and Mastercard's each have their own) that trigger real consequences — increased fees, mandatory remediation, eventual account termination — once a merchant's dispute rate crosses defined thresholds, because a high dispute rate is a proxy for fraud risk or systemic customer-experience failure the network doesn't want propagating through the system. Refund rate has no equivalent network-level enforcement; it's purely a business-health signal you and your PSP care about, not one the networks police.

A customer disputes a charge as "fraudulent" but you have strong evidence they made the purchase themselves (matching IP, device fingerprint, delivery to their verified address). Is it worth contesting?

Generally yes if the evidence is genuinely strong and well-organized, since "fraudulent transaction" disputes with solid counter-evidence (matching AVS/CVV results at time of purchase, delivery confirmation to the cardholder's own address, prior purchase history) have real win rates — but weigh the dispute fee (already sunk either way) plus the time cost against the transaction value; for very small amounts many merchants have a documented threshold below which they don't contest even strong cases, purely on cost-efficiency grounds.

How should your system distinguish "refunded" from "disputed, funds withheld pending resolution" in your order state model?

They need to be genuinely distinct states, not two labels for the same underlying "money went back" bucket, because a dispute can resolve in the merchant's favor (funds return) while a refund never reverses itself — collapsing them means you can't correctly represent "we might get this money back" versus "this money is gone," which matters for both customer communication and financial reporting/ledger entries (unit 8).

What's the engineering implication of Verifi/Ethoca-style pre-dispute alerts for your webhook handling architecture?

They're a distinct event type from a formal dispute-created webhook and need their own handling path — typically triggering a fast, automated "proactively refund and notify the customer" flow rather than waiting for a full dispute to form, since the entire value of the alert is the earlier, cheaper intervention window. Treating an alert as equivalent to (or routing it through the same code path as) a real dispute event misses the point of having the alert at all.

Why would a PSP's automated evidence-submission tooling need access to your order/fulfillment data specifically, rather than just PSP-side transaction data?

The PSP already has everything it captured about the payment itself (card details, AVS/CVV match, IP, timestamp), but the evidence that actually wins "product not received" or "not as described" disputes is fulfillment-side: shipping confirmation, tracking data, delivery timestamps, product descriptions the customer saw — data that lives in your systems, not the PSP's, unless you've explicitly connected it. This is exactly why the brief's "what changed recently" fact (Smart Disputes) has a real integration prerequisite, not just a dashboard toggle.

Should refund reason codes/categories be free text or a constrained enum in your system, and why does it matter for chargebacks?

A constrained enum, because refund-reason data feeds two things that both want structure: your own analytics on why customers are asking for money back (a real product signal), and, when a dispute later lands on a transaction you already voluntarily refunded, being able to programmatically prove "we already resolved this, here's exactly when and why" rather than digging through free-text support notes under a dispute-response deadline.

A partial refund is issued, then the full remaining balance is later disputed. Walk through what your ledger needs to represent correctly.

Three distinct money movements against one original charge: the original capture (money in), the partial refund (money out, voluntary, final), and the dispute debit on the remaining balance (money out, adversarial, provisionally reversible). A naive single "amount refunded so far" counter can't represent this correctly — the ledger needs separate entry types for refund versus dispute-debit specifically because only one of them can later reverse itself if you win the contest.

How do you handle a subscription-cancellation dispute ("subscription canceled" reason code) when your system shows the customer never actually canceled?

This is a strong-evidence case if your cancellation flow logs are solid: submit the absence of a cancellation record, ideally alongside proof the customer used the service after the disputed charge date (login activity, feature usage) which directly undercuts "I canceled and was still charged." It's also a prompt to audit your cancellation UX — a surprising fraction of these disputes trace back to a cancellation flow that's genuinely confusing or has a bug, which is cheaper to fix than to keep winning disputes against.

What would you flag in a design review where a team proposes auto-refunding any transaction older than 90 days to "avoid dispute risk"?

That it conflates two unrelated things — transaction age isn't a proxy for dispute risk, and network dispute time limits vary by reason code and don't map cleanly to "90 days is safe." A blanket time-based auto-refund policy also creates its own problem: it trains fraudulent actors that a long-dormant legitimate-looking charge gets refunded automatically, and it needlessly gives back money on transactions nobody was ever going to dispute. Better to target actual risk signals (alerts, reason-code patterns, customer contact) than a fixed time window.

Does issuing a refund yourself protect you from a subsequent chargeback on that same transaction?

Not entirely — a cardholder can still, in some circumstances, dispute a transaction they were already refunded for (confusion, a refund posting slower to their statement than expected, or in rarer cases genuinely fraudulent double-dipping), which is exactly why the refund needs to be recorded with enough detail (timestamp, amount, method) to let you respond quickly with "this was already resolved" evidence rather than treating it as a fresh, unexplained dispute.

08  Ledgers & double-entry accounting

The instinctive first design for "track how much money everyone has" is a `balance` column on an `accounts` table, incremented and decremented as money moves. It works in a demo and fails in production for a reason that's worth internalizing precisely: a mutable balance column has no memory of why it is what it is. When support asks "why does this customer's balance show $47.32," a plain balance gives you today's number and nothing else — you're forced to reconstruct history from scattered application logs, hoping they're complete and consistent, exactly when you most need certainty (a dispute, an audit, a reconciliation mismatch). Double-entry bookkeeping, a centuries-old accounting technique with nothing payments-specific about it, solves this by making every single money movement an immutable, dual-sided fact rather than a mutation: every entry simultaneously debits one account and credits another, for the same amount, and a balance is never stored — it's derived by summing entries, on demand or via a maintained (but always re-derivable) projection.

The mental model that makes this click: think of every account — a customer's wallet balance, your platform's Stripe-held funds, a merchant's payable balance, a "revenue" account, a "PSP fees" account — as a bucket, and every transaction as moving water from one bucket to another, never creating or destroying water. A $50 charge that nets $48.20 after a $1.80 PSP fee isn't one number changing, it's (at minimum) three buckets moving in concert: customer's payment obligation decreases by $50, your platform's PSP-held-funds bucket increases by $48.20, and a fees-expense bucket increases by $1.80 — and because every entry is dual-sided, the sum of every debit across the whole ledger always equals the sum of every credit, which is a mechanically checkable invariant, not a hoped-for property. If that invariant ever breaks, you have a bug, immediately provably, rather than a slowly-drifting number nobody notices until it's a crisis.

For a payments system specifically, the ledger needs to model more buckets than beginners expect, because a single "charge" event is actually several distinct economic events bundled together: the gross amount the customer paid, the PSP's processing fee (which is your expense, not the customer's), any platform/marketplace commission if you're a multi-sided platform splitting funds between yourself and a merchant, and eventually a payout when funds actually move from the PSP's held balance to your (or the merchant's) bank account — each of these is its own ledger entry pair, at its own point in time, and conflating them (e.g., treating "charge succeeded" and "money is in our bank account" as the same event) is exactly the mistake unit 02 warned about, now showing up as a ledger-design consequence rather than just a status-tracking one.

Immutability is the other non-negotiable property. A ledger entry, once written, is never updated or deleted — a mistake or a reversal is corrected by writing a new, opposite entry, never by editing the old one. This is what makes a ledger auditable in the sense regulators and finance teams actually mean: a complete, tamper-evident history of every claim about where money went, in the order it was recorded. It also composes naturally with everything in the units before this one — a refund is a new entry reversing the original capture's economic effect, not a mutation of it; a dispute debit is a new entry, distinct in type from a refund entry per unit 07's point about needing that distinction representable.

Multi-currency and FX add a real wrinkle worth naming even briefly: if a customer pays in EUR but your platform's base reporting currency is USD, an entry pair needs to record both the original currency/amount and the converted amount at the FX rate applied at that moment — because the rate moves, and "what rate did we actually get charged/paid at" is itself a fact your ledger needs to preserve immutably, not recompute later from a rate table that's since moved on.

Interview trap

“We'll just add an `is_reversed` flag and a `reversed_at` timestamp to the entry, so we can edit it instead of writing a new one” is the most common way teams accidentally throw away double-entry's core guarantee. The moment an entry is mutable, even by adding a flag rather than changing the amount, you've broken the property that lets you trust the historical record without cross-checking it against something else — and in practice, "just this one flag" tends to grow more mutable fields over time. The correct fix for "this entry was wrong" is always a new, opposite entry; the original stays exactly as it was recorded.

Try it
  1. Model a $100 charge with a $3 PSP fee as a balanced set of ledger entries across at least three accounts (held funds, fee expense, customer obligation), and verify by hand that total debits equal total credits.
  2. Break it on purpose: write the entries with a deliberate one-cent mismatch (e.g., forget the fee leg) and write a small check function that would have caught it. Confirm it does.
Expected outcome

The correctly-modeled transaction balances exactly: $97 + $3 (debits) = $100 (credit). Omitting the fee leg leaves debits at $97 against a $100 credit — a $3 imbalance a "sum all debits, sum all credits, assert equal" check catches immediately and mechanically, which is precisely the point: the invariant turns a subtle accounting bug into a loud, immediate assertion failure instead of a silent drift discovered weeks later during reconciliation.

Why is "derive the balance from entries" preferred over "maintain a running balance column, updated on each entry" if the running column would be faster to read?

In practice, most production ledgers do maintain a cached/projected balance for read performance, but treat it strictly as a derived, rebuildable projection — never the source of truth — precisely so that if it ever drifts (a bug, a partial write, a migration issue) you can recompute it from the entry log and know the recomputed value is correct by construction. A pure running column with no underlying entry log has no such recovery path; if it's wrong, you have no independent record of what it should be.

How does double-entry accounting help specifically with the reconciliation problem in unit 9, beyond general "good practice"?

Reconciliation is fundamentally a comparison between two independent records of the same economic reality — your ledger and the PSP's settlement report — and that comparison is only meaningful if your side is a complete, immutable, entry-level record rather than a mutated summary number. A balance-column design can't tell you which individual transaction caused a mismatch; a double-entry ledger can, by comparing entry-for-entry against the PSP's own itemized report.

A marketplace platform splits a $100 sale into an $85 merchant payout and a $15 platform commission. Model this as ledger entries.

At minimum: the charge itself (debit PSP-held funds $100, credit customer obligation $100), then a split entry moving the held funds into two sub-accounts (debit PSP-held funds $100, credit merchant-payable $85 and platform-revenue $15), and finally, separately, the payout entry when the $85 actually leaves for the merchant's bank account. Collapsing the split and the payout into one event loses the ability to answer "how much do we currently owe this merchant but haven't paid yet," which is a question a marketplace gets asked constantly.

What's the risk of recording an FX-converted amount without also recording the original currency, amount, and rate applied?

You lose the ability to explain or audit the conversion after the fact — if a customer disputes the converted amount, or your reporting later needs to reconcile against the PSP's own FX-rate records, "we converted €50 to $54.32" is only verifiable if you kept both sides and the rate, since recomputing from a live rate table gives you today's rate, not the one actually applied at transaction time.

Should refunds and disputes (unit 7) share the same ledger entry type, since both move money back?

No — they need distinct entry types because they have different reversibility and different account implications: a refund entry is final and typically debits customer obligation / credits held funds directly; a dispute entry needs an intermediate "pending/receivable" account state precisely because it might later reverse (if the merchant wins the contest), which a plain refund entry structurally can't represent.

How would you test that a ledger implementation actually enforces the double-entry invariant, rather than just hoping application code always writes balanced entries?

Push the invariant down to the storage layer rather than trusting every call site: a database-level check constraint or trigger that rejects any committed transaction where debits and credits for a given transaction ID don't sum to zero net, or, in an append-only event-sourced design, a periodic background job that verifies the invariant across the full entry log and pages someone the moment it doesn't hold. Relying purely on "the application code always calls the right helper function" is exactly the kind of assumption that fails the first time someone writes a one-off migration script.

Why might a lead engineer resist a request to "just show negative available balance instead of blocking the withdrawal" as a UX shortcut?

Because it usually signals someone reaching for a mutable-state shortcut around a ledger question that has a real, entry-based answer: "available balance" should be a derived query (held funds minus pending payouts minus reserved-for-disputes amounts), and if that query says negative, the fix is figuring out which of those components is wrong or missing, not special-casing the display to tolerate an impossible number.

What's the relationship between your internal ledger and the PSP's own internal ledger of your account?

They're two independent double-entry systems tracking overlapping but not identical things — the PSP's ledger tracks money moving through their platform on your behalf (charges, fees, payouts, holds), while yours tracks the business meaning of that money (which customer, which order, which merchant's payable balance). You don't get to skip your own ledger just because the PSP maintains one; you need both, and unit 9's reconciliation is precisely the process of keeping them provably in agreement.

A junior engineer proposes storing amounts as floating-point numbers to "keep things simple." What's your response, and how does it connect to ledger correctness?

Floating-point arithmetic's rounding behavior is exactly the kind of thing that breaks the "sum of debits equals sum of credits" invariant in ways that are maddening to debug — a chain of additions and subtractions that should net to zero can land on a value like 0.00000000001 instead, which either fails a strict equality check that should have passed, or worse, silently accumulates over millions of transactions. Amounts belong in integer minor units (cents) or a fixed-point decimal type, never floating point, specifically because the ledger's core invariant depends on exact arithmetic.

How far back should ledger entries be retained, and does that interact with any of the earlier units?

Retention is generally driven by the longest of: regulatory/financial record-keeping requirements (often several years), the maximum dispute time limit for any card network you accept (unit 7, so a dispute can still be evidenced against the original entries), and your own audit needs. Because entries are immutable and small, retaining them indefinitely is usually cheap relative to the cost of ever needing one you deleted — the practical constraint is almost always storage/query-performance tiering (archive old entries to cold storage), not "when is it safe to actually destroy this data."

09  Reconciliation & resiliency

Reconciliation is the process of proving, systematically rather than by spot-check, that your internal ledger (unit 08) and the PSP's own record of what actually happened agree — and, critically, surfacing every case where they don't so a human can investigate before it compounds. The reason this is a distinct discipline rather than "the ledger is correct, so what's to check": your ledger records what your application believes happened, built from API responses and webhooks, both of which can be missed, delayed, duplicated, or (rarely but not never) simply wrong due to a bug on either side. The PSP's settlement report — a batch file (commonly CSV or a structured API feed) itemizing every transaction that actually settled into your bank account for a given period — is an independent source of truth generated from the PSP's own ledger, not derived from anything your application told it. Reconciliation is comparing the two, transaction by transaction, and treating every unexplained mismatch as a bug until proven otherwise.

The concrete workflow: pull the PSP's settlement report for a period (daily is typical), match each line item against your internal ledger by a shared identifier (charge/PaymentIntent ID, ideally — not amount-and-date fuzzy matching, which produces false matches the moment two customers pay the same amount on the same day), and bucket the result into three piles: matched (both sides agree, nothing to do), in your ledger but missing from settlement (a webhook you processed didn't actually settle — classic async-payment-method risk from unit 02, or a genuine PSP-side delay), and in settlement but missing from your ledger (a webhook you never received or never processed — this is the scarier bucket, because it usually means real money moved that your system has no record of, silently). The second and third buckets are where the actual engineering and ops work lives; a reconciliation process that only reports "N transactions matched" without surfacing and routing the mismatches for investigation isn't doing the job.

Fee verification is a reconciliation sub-problem worth calling out on its own: settlement reports itemize the exact fee taken per transaction, and comparing that against what your ledger's fee-expense entries assumed (unit 08) catches PSP fee-schedule changes, misconfigured pricing tiers, or currency-conversion fee surprises that a pure "did the money arrive" check would miss entirely — this is real money leaking quietly if nobody checks it, and it's one of the more common concrete findings a first reconciliation pass turns up in a system that's never had one.

Multi-PSP resiliency is reconciliation's cousin at the architecture level, and matters more the larger the payment volume: relying on a single PSP means a PSP-side outage, a regional processing degradation, or even a sustained latency spike is a full checkout outage for you, with zero mitigation available on your end. The mature pattern is a routing/orchestration layer (mentioned in unit 01 as an integration model) that can direct traffic across multiple PSPs based on health, cost, or geography, and fail over automatically when one PSP degrades — at the cost of real complexity: every unit in this document (idempotency, webhooks, 3DS, PCI scope, disputes, ledger entries) now needs to work correctly per PSP, and your ledger needs a PSP identifier as a first-class dimension so reconciliation runs per-PSP-per-period rather than assuming one settlement report format and cadence.

What changed recently, tying back to unit 04: Stripe's thin-events shift toward "fetch current state rather than trust the embedded snapshot" directly improves reconciliation accuracy for teams that adopt it — a reconciliation process built on always-fresh-fetched state is less likely to have processed and recorded a since-superseded status, closing one of the more common root causes behind "in your ledger but doesn't match settlement" mismatches that trace back to a stale snapshot processed after a later event should have superseded it.

// Simplified daily reconciliation pass: match by charge ID, bucket the rest.
public record ReconciliationResult(List<string> Matched, List<string> LedgerOnly,
                                    List<string> SettlementOnly, List<(string Id, decimal Diff)> FeeMismatches);

public ReconciliationResult Reconcile(IReadOnlyDictionary<string, LedgerRow> ledger,
                                       IReadOnlyDictionary<string, SettlementRow> settlement)
{
    var matched = new List<string>();
    var feeMismatches = new List<(string, decimal)>();

    foreach (var (id, ledgerRow) in ledger)
    {
        if (!settlement.TryGetValue(id, out var settled)) continue;   // handled below
        matched.Add(id);
        var diff = Math.Abs(ledgerRow.ExpectedFee - settled.ActualFee);
        if (diff > 0.005m) feeMismatches.Add((id, diff));            // penny-tolerant compare
    }

    return new ReconciliationResult(
        matched,
        ledger.Keys.Except(settlement.Keys).ToList(),   // ledger-only: investigate delay
        settlement.Keys.Except(ledger.Keys).ToList(),   // settlement-only: URGENT, missed money
        feeMismatches);
}
Interview trap

“We reconcile by comparing total daily volume between our ledger and the settlement report” is a real anti-pattern that interviewers specifically listen for: aggregate-total reconciliation can have a missing $500 transaction perfectly offset by a duplicated $500 transaction elsewhere and report a clean match, because the totals happen to agree. Reconciliation has to be transaction-by-transaction, matched by a stable identifier, precisely to catch the cases where errors cancel out in aggregate but represent two genuinely separate, dangerous bugs.

Try it
  1. Take a small set of mock ledger entries and a mock settlement report (as two lists/CSVs) with a few deliberately introduced mismatches (one missing from each side, one fee discrepancy), and write the three-bucket matching logic to surface all of them.
  2. Break it on purpose: introduce a case where the totals happen to match despite a missing-plus-duplicated pair canceling out, and confirm your transaction-level matcher still catches it even though a naive total-comparison wouldn't.
Expected outcome

The transaction-level matcher correctly places every deliberately-introduced discrepancy into its bucket, including the offsetting pair a total-based check would have missed entirely — concretely demonstrating why aggregate reconciliation is a false sense of safety rather than a lighter-weight equivalent to the real thing.

Why can't you reliably reconcile using amount-and-date fuzzy matching instead of a shared transaction identifier?

Any two customers paying the same round amount on the same day produce ambiguous matches, and at real volume this isn't a rare edge case, it's a routine occurrence — the reconciliation process ends up guessing which settlement line corresponds to which ledger entry, silently mismatching some pairs while reporting a clean result. A shared, PSP-issued identifier (charge/PaymentIntent ID) removes the ambiguity entirely and is available specifically because you should already be storing it against every ledger entry from the moment it's created.

You find a transaction in the settlement report with no corresponding ledger entry. What's your incident-response priority order?

First, confirm it's real money (check the PSP dashboard directly, not just the report) rather than a report-generation glitch; second, check whether a webhook for it exists anywhere in your logs/dead-letter queue but failed to process, versus never arrived at all, which tells you whether the fix is "reprocess a stuck event" or "investigate why delivery failed entirely" (unit 4's monitoring gap); third, backfill the missing ledger entry once you understand why it's missing, not before, since backfilling blind risks recording it wrong the same way it was missed.

How does reconciliation change for a multi-PSP setup versus a single-PSP one, beyond "there's more than one report to pull"?

Each PSP has its own settlement report format, cadence, and fee structure, so the matching and fee-verification logic needs to be PSP-aware rather than assuming one shape — and because a transaction routed through PSP A never appears in PSP B's report at all, your ledger's PSP identifier becomes load-bearing for correctly scoping which report to check each entry against, not just a descriptive field.

What's the argument for running reconciliation daily rather than, say, weekly or monthly?

The cost of finding a discrepancy scales with how much has piled up on top of it and how stale the context is when you finally investigate — a missing-webhook root cause is far easier to diagnose and fix within a day of it happening (logs are fresh, the on-call engineer who touched that code remembers it) than a month later across potentially hundreds of accumulated instances of the same underlying bug. Daily reconciliation turns "one big scary investigation" into "routine, small, cheap checks."

Design question: how would you decide which PSP to route a given transaction to in a multi-PSP orchestration layer?

Typically a combination of real-time health signals (recent error rate/latency per PSP, to route around active degradation), cost (interchange-plus and PSP fee schedules differ, and blended cost matters at scale), and capability fit (does this PSP support the customer's payment method, currency, or region well) — with health/failover taking priority over pure cost optimization, since a cheaper PSP that's currently failing is a checkout outage, not a savings.

Your fee-verification step finds that a PSP's actual fee consistently runs 0.1% higher than your ledger's assumed fee, across thousands of transactions. What do you do?

Investigate the pricing schedule first — a consistent, systematic delta almost always means your fee-expense entries are computed from a stale or wrong pricing assumption (a rate that changed, a currency-conversion fee component you're not modeling) rather than PSP-side error, since PSPs don't quietly overcharge at scale without it being a contract term you missed. Fix the ledger's fee-calculation logic to match the actual schedule, then backfill/correct the historical fee-expense entries as new, explicit correcting entries (unit 8) — never by editing the old ones.

How would you build alerting around reconciliation so that "settlement has it, ledger doesn't" mismatches get urgent attention while minor timing-lag mismatches don't create alert fatigue?

Tier by bucket and age: a settlement-only mismatch should page immediately regardless of amount, since it represents unaccounted-for real money; a ledger-only mismatch is expected to briefly appear for genuinely async payment methods and should only alert once it's aged past the PSP's normal settlement window for that method, at which point it graduates from "expected lag" to "investigate." Treating every mismatch identically either buries the urgent ones in noise or trains the team to ignore the alert channel entirely.

Why is a routing/orchestration layer described as adding real complexity rather than being a strictly-better default for every payments integration?

Because every capability discussed in this document (idempotency key scoping, webhook signature verification, 3DS challenge handling, PCI-scope boundaries, dispute evidence formats, settlement report shapes) now needs to be correctly implemented and tested against each PSP behind the router, and the router itself becomes a new critical-path component with its own failure modes and its own need for observability. It's the right trade for volume/risk profiles where single-PSP outage exposure genuinely outweighs that added complexity, not a universal best practice — a small team on one PSP that reconciles well and has clean webhook handling may have no real need for it.

What would make you trust an automated reconciliation pipeline enough to stop manually spot-checking it?

A track record of the pipeline itself being tested against known-bad synthetic data (deliberately introduced mismatches, per this unit's try-it exercise) and caught them correctly, plus monitoring on the pipeline's own health (did it actually run today, did it process the expected row counts) so a silent pipeline failure doesn't masquerade as "everything matched." Manual spot-checking is a reasonable stopgap early on, but the actual goal is trusting the automation enough that spot-checking becomes redundant, not a permanent parallel process.

A settlement report arrives in a currency different from the one your ledger recorded the original charge in. How does that affect matching?

You still match by transaction identifier, never by amount, but the fee-verification and net-amount comparison now needs to account for the FX conversion applied between charge and settlement — which is exactly why unit 8's requirement to record the original currency, amount, and applied rate on the ledger entry matters here specifically: without it, you have no independently-computed expectation to compare the settled, converted amount against, and any discrepancy is unexplainable.

10  The big Q&A

Architecture & ecosystem

How would you decide, from scratch, whether a new product needs Stripe, Adyen, both, or an orchestration layer over several PSPs?

Start from the actual requirements: geographic coverage and local payment method support (Adyen's strength in certain regions and alternative payment methods can outweigh Stripe's superior developer experience for a global, method-diverse product), expected volume and whether single-PSP outage risk is tolerable at that scale, and existing team expertise (a small team's velocity cost of learning a second PSP's object model is real and often underweighted). Most products should start single-PSP and earn their way into multi-PSP complexity through actual volume or coverage gaps, not adopt it speculatively.

What's the actual difference between a payment processor, a payment gateway, an acquirer, and a PSP — terms often used loosely?

A gateway is the technical pipe that transmits transaction data to the card networks; an acquirer is the bank that holds the merchant relationship with the card networks and receives settled funds; a processor handles the back-end transaction processing on the acquirer's behalf; a PSP (Stripe, Adyen) typically bundles all of these into one merchant-facing product, acting as gateway, and often as acquirer or working tightly with one, so you integrate with a single API instead of assembling the stack yourself. In casual usage people say "payment processor" to mean "PSP," which is imprecise but rarely causes real confusion in context.

Why do PSPs push so hard toward unified integration primitives (PaymentIntent + PaymentElement, /payments + Components) rather than leaving per-method integration to the merchant?

Every new payment method (a new BNPL provider, a new regional wallet) historically meant every integrated merchant doing custom integration work, which slowed adoption industry-wide and multiplied the PSP's own support burden across countless bespoke implementations. A unified primitive means the PSP can add support for a new method server-side and have it show up in every existing integration's Element/Component automatically, which is a much better leverage point for both sides.

How would you introduce PSP migration risk (e.g., moving primary volume from Stripe to Adyen) to a skeptical leadership team?

Frame it honestly as touching nearly every unit in this document simultaneously — idempotency key formats, webhook payload shapes and signature schemes, 3DS flow integration, PCI scope boundaries if the integration model changes, dispute evidence workflows, and ledger/reconciliation logic all need parallel implementations during a transition, typically run side-by-side with gradual traffic shifting rather than a hard cutover, specifically because a hard cutover has no rollback path if something in that large a surface area breaks post-migration.

Security

Beyond webhook signature verification and PCI scope, what's an underrated security consideration in payment integrations?

Secrets management for API keys and webhook signing secrets specifically — a leaked Stripe secret key is directly usable to create real charges or issue refunds against your account, unlike most leaked credentials which need further exploitation to cause damage. Rotation procedures, scoping keys to the minimum required permission (restricted API keys rather than one all-powerful key), and never logging keys even in error traces are all disproportionately high-value relative to how often they're actually enforced.

How would you defend against card testing (attackers using your checkout to validate stolen card numbers in bulk) without adding friction to legitimate customers?

Rate-limit and fingerprint at the attempt level rather than the account level (attackers don't have accounts), watch for the tell-tale pattern of many small-amount authorization attempts against sequential or similar card numbers from the same session/IP/device, and lean on the PSP's built-in fraud/risk tooling (Stripe Radar, Adyen RevenueProtect) which is specifically tuned for this pattern rather than building bespoke detection from scratch. CAPTCHA or step-up friction should be reserved for signals that actually correlate with this behavior, not applied to every checkout by default.

What's the security argument for never letting your backend construct or store a full PAN, even encrypted at rest, "just in case"?

Encrypted-at-rest PAN storage still means the decryption key, key-management infrastructure, and every code path that ever handles the decrypted value are all in full PCI DSS scope (SAQ D territory) and represent a standing target — a single key-management mistake or a compromised process with decrypt access defeats the encryption entirely. The tokenization pattern avoids this exposure altogether by never having the sensitive value on your infrastructure in any form, which is a strictly stronger security posture than "encrypted well."

Performance & debugging

A customer reports their payment "hung" for 45 seconds before succeeding. How would you investigate?

Check whether the 45 seconds includes a 3DS challenge round-trip (unit 5) — that's often the actual explanation and not a bug at all, since a challenge involving an OTP the customer had to receive and type genuinely takes tens of seconds. If it's not that, check your own PSP API call latency and retry behavior (unit 3) for evidence of a slow or retried request, and check whether your webhook processing lag (unit 4) delayed the client-visible confirmation even after the PSP-side authorization was already fast.

Your checkout success rate drops 3% overnight with no code deploy on your end. What's your triage order?

Check the PSP's own status page/dashboard first for an ongoing incident, since PSP-side degradation is the most common "nothing changed on our end" cause; then check whether the drop is concentrated in a specific payment method, region, or card issuer (a specific issuer's authorization system having problems looks exactly like this from your side); then check your own webhook/API error rates and 3DS challenge rates for a shift, since an issuer tightening risk scoring can spike your challenge rate and, if your challenge-abandonment UX is weak, your effective success rate.

How would you load-test a payment integration without accidentally processing real charges or exhausting a PSP's test-mode rate limits?

Use the PSP's documented test-mode card numbers and endpoints, which process without touching real money, but still respect the PSP's own rate limits and typically coordinate with them in advance for anything resembling genuine load testing, since test-mode infrastructure is often less provisioned than production and an unannounced load test can look identical to an attack from their side. Never load-test against production endpoints with real cards "at a small scale" to save setup time — the blast radius of a mistake is real charges.

Tooling

What's the value of the Stripe CLI / Adyen's equivalent local tooling beyond "convenient for demos"?

Local webhook forwarding (stripe listen --forward-to) lets you develop and debug webhook handlers against real, properly-signed test events without deploying a publicly reachable endpoint first, which meaningfully shortens the feedback loop for exactly the part of the integration (unit 4) that's hardest to test otherwise. stripe trigger-style event simulation also makes it practical to exercise rare event types (a specific dispute reason code, a specific failure mode) on demand rather than waiting for one to occur naturally.

How do you approach testing 3DS and webhook flows in CI, where you can't interactively complete a challenge?

Use the PSP's deterministic test card numbers/payloads that resolve to known outcomes (frictionless success, challenge-then-success, challenge-then-failure) without any actual interactive step, combined with recorded or synthetically-constructed, correctly-signed webhook payloads for handler-level tests that don't need a live PSP round-trip at all. The interactive-challenge UI itself is the PSP's tested surface, not yours, so CI should verify your handling of each possible outcome rather than the challenge UI itself.

What observability would you insist on before letting a payment integration go to production, beyond generic API monitoring?

Per-PSP success/decline/error rate dashboards broken out by payment method and, where relevant, issuer/region; webhook delivery lag and error-rate monitoring (unit 4); and a reconciliation-pipeline health check (unit 9) confirming it actually ran and processed expected volume, not just that it didn't crash. Generic "is the API up" monitoring misses almost everything that actually goes wrong in payments, which tends to be domain-specific degradation, not outright downtime.

Legacy & migration reality

You inherit a codebase still using Stripe's legacy Charges API and per-method Elements instead of PaymentIntents/PaymentElement. Do you migrate it immediately?

Not reflexively — the Charges API still works for simple, non-3DS, single-currency use cases, and a forced migration purely for modernity's sake is real risk and effort for no functional gain if the product genuinely never needs SCA/3DS support or multi-method flexibility. The migration becomes necessary, not optional, the moment you need SCA compliance for EU customers or want to add payment methods beyond cards easily — at which point the PaymentIntents model's design (built around exactly those needs) stops being a nice-to-have.

What's the tell-tale sign in a codebase that a payment integration was built before idempotency keys were well understood by the team?

Retry logic that generates a fresh key (or no key at all) per attempt, often wrapped in a generic HTTP retry middleware applied uniformly across all outbound calls without payment-specific awareness that side-effecting calls need different treatment than idempotent GETs — usually discovered only after a duplicate-charge incident, since the bug is invisible until a retry actually fires under real network conditions.

How do you handle a legacy system where card data genuinely does flow through and get logged by your own servers, and you've been asked to fix it without a full rewrite?

Prioritize stopping the logging/storage of raw PAN first — audit every log statement, error handler, and debug trace on the payment code path and strip or redact card fields, since that's both the fastest compliance-risk reduction and independent of the harder architectural fix. Then plan the migration to client-side tokenization as the real fix, treating the logging fix as a stopgap that reduces exposure while the larger change is scoped and executed, not as the final state.

A legacy integration stores "last 4 digits and expiry" directly rather than via a PSP token, for display purposes. Is that a PCI problem?

Truncated PAN (last 4 digits) is explicitly not considered sensitive cardholder data requiring the same protection as full PAN under PCI DSS, so storing it alone for display purposes is generally fine. The risk is scope creep: verify nothing nearby is also capturing full PAN "just in case," and that the expiry date isn't stored alongside enough other data to reconstruct something more sensitive than intended — the last-4-plus-expiry pattern itself is standard and low-risk when it's genuinely isolated to just those fields.

Judgment & scenario questions

How would you decide whether a payment-related incident warrants an all-hands incident response versus a quiet, next-business-day fix?

Weigh active financial exposure (is money actively being lost or mis-recorded right now, e.g., a broken idempotency key causing live double-charges) against blast radius and reversibility (a webhook processing delay that will self-heal via retries once fixed is very different from silent data loss). Active, ongoing, hard-to-reverse financial impact warrants immediate escalation; a contained, already-stopped, cleanly-correctable issue can often wait, provided you've verified it's actually contained before deciding that.

How would you code-review a pull request that adds a new refund endpoint, focusing on what a less experienced reviewer might miss?

Beyond the obvious (does it call the right API), check: is there an idempotency key, and is it derived from stable, durable data rather than generated per-call; does it check for an existing pending dispute on the same charge before refunding, to avoid the double-return trap from unit 7; does the ledger update happen only after PSP confirmation, never optimistically; and is the refund amount validated against the original charge amount so a bug can't refund more than was ever charged.

How would you introduce double-entry ledger accounting to a team currently running on a simple balance-column model, without a disruptive big-bang rewrite?

Run the new ledger in parallel/shadow mode first — write entries to it alongside the existing balance-column updates without yet trusting it as source of truth, then compare derived balances against the legacy column over a real period to build confidence and surface any modeling gaps, before cutting reads over to the ledger and finally retiring the balance column. This mirrors the same gradual-migration instinct as the PSP-migration answer above: a financial-correctness change earns trust through parallel verification, not a leap of faith.

A product manager asks why "just add a retry button for failed payments" isn't a one-line fix. How do you explain the actual scope?

A naive retry button re-runs the same request, which without a properly-scoped idempotency key (unit 3) risks a duplicate charge on a request that actually succeeded but appeared to fail client-side (a timeout, a dropped connection) — so the "one line" is actually: ensure the original request's idempotency key is retrievable and reused, decide what UI state to show while retrying, and handle the case where the retry reveals the original already succeeded (show success, don't imply a new charge happened). Naming the specific risk in concrete terms usually lands better with a PM than an abstract "it's more complex than it looks."

How would you approach a situation where finance reports the ledger and the bank statement disagree by a small, persistent amount every month, and nobody can explain why?

Treat it as exactly the reconciliation problem from unit 9, applied retroactively: get itemized settlement reports for the affected periods and match transaction-by-transaction rather than accepting the aggregate discrepancy as unexplainable, since a persistent small gap almost always resolves to a specific, findable cause (a fee-schedule assumption that's slightly wrong, a category of transaction that's systematically mis-recorded) once you stop comparing totals and start comparing line items.

11  Night-before cheat sheet

  • A PSP (Stripe, Adyen) bundles gateway, processing, and often acquiring into one API; card data should flow client-side straight to the PSP via tokenization (Elements/Components) so your servers stay out of PCI scope, landing you in SAQ A or A-EP instead of the much heavier SAQ D.
  • Authorization and capture are separate steps — Stripe's PaymentIntent and Adyen's /payments both model a "hold the funds, decide to take them later" flow, and succeeded/authorised is never the same thing as money actually being in your bank account, especially for async methods like ACH and SEPA that can still fail or return days later.
  • Idempotency keys must be generated once, when the logical operation is decided, and reused across every retry — regenerating a key inside a retry loop silently disables the entire protection and is the single most common real-world payments bug.
  • Webhooks are at-least-once, unreliably ordered, and must be verified against the raw, unparsed request body (Stripe's Stripe-Signature HMAC) before any model binding touches it; dedupe your handler by event ID, never trust the event's embedded timestamp for ordering.
  • Stripe's newer API versions support thin events (fetch current state) alongside the long-standing snapshot events (embedded state) — thin events can't go stale on a delayed retry, which directly improves reconciliation accuracy.
  • 3-D Secure 2 (EMV 3DS 2.3.1.1 current) authenticates most transactions frictionlessly and reserves visible OTP/biometric challenges for issuer-flagged risk; a successful authentication shifts fraud liability to the issuer, while an SCA exemption trades that liability shift for reduced friction and stays with the merchant if the issuer grants it.
  • PCI DSS 4.0.1's future-dated requirements became mandatory on March 31, 2026 — already past as of today — meaning Requirement 11.6.1 (payment-page script inventory and tamper detection) and 6.4.3 (justified, integrity-verified scripts) are hard compliance gaps now, not upcoming ones, for anyone running a checkout page.
  • Refunds are voluntary, final, and merchant-initiated; chargebacks are adversarial, immediately debit funds, and carry a non-refundable dispute fee regardless of outcome — Verifi/Ethoca pre-dispute alerts let you refund proactively before a formal dispute forms, which is strictly cheaper than contesting one later.
  • Model money movement as immutable double-entry ledger entries, never a mutable balance column — every entry's debits must equal its credits, a mistake gets corrected with a new opposite entry, and amounts live in integer minor units or fixed-point decimals, never floating point.
  • Reconcile transaction-by-transaction against the PSP's settlement report using a shared identifier, never by comparing aggregate totals — offsetting errors (one missing, one duplicated) can make totals match perfectly while hiding two real, dangerous bugs.
