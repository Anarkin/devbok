interview · MongoDB 8.3.8 · released 2026-08-13

MongoDB interviews are not "explain BSON" quizzes — they test whether you can pick a document shape that survives three years of requirement changes, whether you can read an explain plan and name the missing index, and whether you know what a write actually costs on a replica set before it is acknowledged. 01Data modelling and schema design

This is where MongoDB interviews start and where most of them are decided. Screeners check that you know embedding exists; mid-level checks that you can apply "data that is accessed together is stored together"; senior and principal are really about reversibility — can you name the access patterns first, pick a shape that serves them, and say what it will cost when the requirements change. Expect a live modelling exercise where the interviewer adds a requirement halfway ("now we also need a feed of the 20 most recent comments across all posts") and watches whether your shape survives it. The failure mode that ends loops is designing a document model that is a relational schema with the joins removed.

Docs: MongoDB Manual — Data Modeling

screenerEmbed or reference — how do you decide?

Answer

I start from the access patterns, not from the entities. The rule of thumb is "data that is accessed together should be stored together": if the child is always read with the parent, has bounded cardinality, and changes at the same rate, embed it. Reference when the child is large, when it is read on its own, when many parents share it, or — the decisive one — when the array would grow without bound. The three concrete pressures that push toward referencing are the 16 MB document limit, write amplification (rewriting a 2 MB document to append one element), and contention (many writers hitting one document). I say out loud that the model is chosen per workload, and that a mixed model — embed a small subset, reference the rest — is usually the right answer for anything real.

Example

// Embed: an address is always read with the customer, there are 1-5 of them.
{ _id: 1, name: "Ada", addresses: [ { type: "home", city: "London" } ] }

// Reference: orders are unbounded, queried on their own, and written by a
// different part of the system.
{ _id: ObjectId("..."), customerId: 1, total: 42.50, placedAt: ISODate() }

// Mixed (the usual real answer): embed the last few, reference the rest.
{ _id: 1, name: "Ada",
  recentOrders: [ { _id: ObjectId("..."), total: 42.50, placedAt: ISODate() } ] }

Follow-ups

  • What if the embedded data changes often and is duplicated? — Then duplication has a maintenance cost; either accept eventual consistency and fix it with a background job or change stream, or reference and pay a second query.
  • How many is "too many" to embed? — There is no number; the test is whether the array is bounded by something in the domain. "Addresses per customer" is bounded, "events per device" is not.
  • Does $lookup make referencing free? — No. $lookup is a nested-loop join executed per input document; it is fine for tens of lookups against an indexed field and terrible as a substitute for modelling.

Common wrong answer

"Embed one-to-few, reference one-to-many, reference one-to-squillions." It sounds right — it is even a MongoDB blog title — but recited alone it shows you are matching cardinality rather than access patterns. Candidates who stop there embed a 50-element array that is never read and then wonder why every write rewrites 400 KB. Cardinality is one input; read/write ratio, update frequency and whether the child is queried independently are the others.

screenerWhat is the 16 MB document limit, and what else does it constrain?

Answer

A single BSON document may not exceed 16 MB. It exists to stop a single document consuming unbounded RAM and network buffers, since MongoDB always reads and writes whole documents. The practical consequences run further than "documents are small": every aggregation stage's output document must also fit in 16 MB, so a $group that accumulates an array can blow the limit even when your stored documents are tiny, and the same applies to $lookup results pushed into an array. For genuinely large binary payloads there is GridFS, which chunks a file across a fs.chunks collection — but in practice most teams should put blobs in object storage and keep only the key in MongoDB.

Example

// This can exceed 16 MB at the group stage even if every input doc is 2 KB:
db.events.aggregate([
  { $group: { _id: "$userId", all: { $push: "$$ROOT" } } }   // unbounded array
]);

// Bounded alternative: aggregate to a value, or use $topN / $firstN (5.2+).
db.events.aggregate([
  { $group: { _id: "$userId", recent: { $topN: { n: 20, sortBy: { ts: -1 }, output: "$$ROOT" } } } }
]);

Follow-ups

  • What is the practical target document size? — Well under a megabyte for hot documents; the real constraint is the WiredTiger cache and the fact that any update rewrites the whole document.
  • Does the aggregation pipeline have a memory limit too? — Yes: 100 MB per blocking stage by default, and since 6.0 stages spill to disk automatically instead of erroring (allowDiskUse defaults to true; 8.2 added spill metrics in $queryStats).
  • When would you actually use GridFS? — When you need file storage inside the database's replication and backup story and cannot run object storage; otherwise S3-style storage with a reference is simpler and cheaper.

Common wrong answer

"16 MB is plenty, so it never matters in practice." It matters constantly — not because stored documents get big, but because growing arrays and $push-based aggregations hit it in production at 3am. The right instinct is that any array without a domain-level bound is a future outage.

midWhat is the unbounded array anti-pattern, and how do you fix it?

Answer

An unbounded array is an embedded array whose length is driven by time or usage rather than by the domain — comments on a post, readings from a sensor, audit entries on an account. Three things degrade together: the document grows toward 16 MB; every append rewrites the whole document, so write cost grows linearly with history; and indexes on array fields become multikey, meaning one index entry per element, which bloats the index and can make it useless. The fixes, in order of preference, are: move the children to their own collection with a reference; use the bucket pattern (one document per parent per time window, with a bounded element count); or the subset pattern (embed the newest N with $push + $slice, keep the full history in a second collection).

Example

// Subset pattern: keep the 20 newest comments inline, cap the array atomically.
db.posts.updateOne(
  { _id: postId },
  { $push: { recentComments: { $each: [ comment ], $sort: { at: -1 }, $slice: 20 } },
    $inc:  { commentCount: 1 } }
);

// Bucket pattern for telemetry: one doc per device per hour, bounded at 3600.
{ deviceId: "d-17", hour: ISODate("2026-09-08T14:00:00Z"),
  count: 3600, first: ISODate("...14:00:00Z"), last: ISODate("...14:59:59Z"),
  readings: [ { t: 0, v: 21.4 }, { t: 1, v: 21.5 } ] }

Follow-ups

  • Why is a multikey index on a 10,000-element array bad? — It stores 10,000 index keys for that one document; index size explodes and any write to the array touches many index entries.
  • Can you have a compound index on two array fields? — No. A compound index may include at most one array field, because the key cardinality would be the Cartesian product.
  • When is the bucket pattern better than a time series collection? — When the bucketing key is not time-plus-metadata, when you need to update points in place, or when you are on a version where time series collections lack a feature you need (updates and deletes only became reasonable in 5.0/6.0, sharded time series in 5.1+).

Common wrong answer

"Just cap the array with $slice and it's fine." Capping fixes the size but not the requirement — the data you sliced off still has to live somewhere, and candidates who stop at $slice quietly lose history. The strong answer names both halves: bounded inline subset plus a durable home for the rest.

midModel comments on a blog post. Walk me through your reasoning.

Answer

First I ask the access patterns: is the post page the only reader, are comments paginated, is there a moderation queue, is there a "recent comments across all posts" feed? Given a typical answer — post page shows the first page of comments, moderators query across posts, comments are unbounded — I use a separate comments collection keyed by postId, with an index on { postId: 1, createdAt: -1 } so the post page reads one indexed range and paginates by createdAt rather than skip. I keep a denormalised commentCount on the post because it is read on every listing page and would otherwise be a count query per post. If the product guarantees "most posts have under ten comments", I would instead embed and accept the cap — but I say what would make me change my mind.

Example

db.comments.createIndex({ postId: 1, createdAt: -1 });

// Page 1
db.comments.find({ postId }).sort({ createdAt: -1 }).limit(20);
// Page 2: range, not skip - skip re-scans everything before the offset.
db.comments.find({ postId, createdAt: { $lt: lastSeenCreatedAt } })
           .sort({ createdAt: -1 }).limit(20);

Follow-ups

  • How do you handle threaded replies? — Either a parentId plus a materialised path array (ancestor array pattern) so a whole subtree is one indexed query, or embed replies under the top-level comment when depth is capped at one.
  • How do you keep commentCount correct? — $inc in the same operation where possible, a transaction if the two writes must be atomic, and a periodic reconciliation job because counters drift.
  • Why not skip? — skip(n) still walks and discards n documents; at page 500 it is a scan. Keyset (range) pagination is O(page size).

Common wrong answer

"Embed the comments in the post — that's the whole point of MongoDB." Comments are the textbook unbounded array, and the candidate who embeds them without asking about volume has skipped the only question that mattered. Equally weak is the opposite reflex: a fully normalised comments collection with no denormalised count, so the listing page fires N count queries.

midHow do you evolve a schema in production without downtime?

Answer

With the schema versioning pattern: every document carries a schemaVersion field, the application can read every version it has ever written, and migration is lazy — documents are upgraded when they are next written, with an optional background job to finish the tail. That is the crucial advantage over a relational ALTER TABLE: there is no lock and no big-bang cutover, because MongoDB does not enforce a single shape. The discipline that makes it safe is the expand/contract sequence: first deploy code that writes both old and new fields and reads either, then backfill, then deploy code that reads only the new field, then drop the old one. Schema validation with $jsonSchema is applied at the end of that sequence, not the start, and in validationLevel: "moderate" while old documents remain.

Example

// Read path tolerates both shapes.
const name = doc.schemaVersion >= 2 ? `${doc.first} ${doc.last}` : doc.name;

// Lazy upgrade on write, plus a throttled backfill for the tail.
db.users.updateMany(
  { schemaVersion: { $lt: 2 } },
  [ { $set: { first: { $arrayElemAt: [ { $split: ["$name", " "] }, 0 ] },
              last:  { $arrayElemAt: [ { $split: ["$name", " "] }, -1 ] },
              schemaVersion: 2 } },
    { $unset: "name" } ]
);

Follow-ups

  • How do you avoid a backfill hammering the cluster? — Batch by _id range with a bounded rate, run against a secondary-read-preference cursor where possible, and watch the replication lag and cache dirty percentage as the throttle signal.
  • What does validationAction: "warn" buy you? — It logs violations instead of rejecting writes, so you can measure how much of the collection would fail before you enforce.
  • Do you ever do a big-bang migration? — Only for small collections or when the old shape is actively harmful (a security field). Otherwise lazy migration removes the risky maintenance window entirely.

Common wrong answer

"MongoDB is schemaless, so there is no migration — just start writing the new field." That is how you get a collection with four shapes and no code that knows which is which. Schemaless means the database does not enforce a schema; the schema still exists, it just lives in your application, and unversioned drift is the most expensive form of technical debt in a document store.

seniorWhat is the extended reference pattern, and what does it cost?

Answer

An extended reference stores the foreign key plus the two or three fields you always need alongside it, so the common read needs no join. An order line stores { productId, name, price } rather than productId alone. The cost is duplication, and the design question is not "is this duplicated?" but "does the duplicate need to change?" — and in the order case it must not: the price at purchase time is a fact about the order, not a stale copy of the product. That distinction is the senior answer. Where the duplicate genuinely must track the source (a display name shown on a profile), you accept eventual consistency and drive the fan-out update with a change stream or an outbox job, and you size the fan-out before you commit to it — duplicating a field across ten million documents means a ten-million-document update every time it changes.

Example

// The price is a historical fact, not a cache: duplication is correct here.
{ _id: ObjectId("..."), placedAt: ISODate(),
  lines: [ { productId: 77, name: "Cable, 2m", unitPrice: 9.99, qty: 2 } ],
  total: 19.98 }

// The display name is a cache: it needs a fan-out policy.
db.products.watch([{ $match: { "updateDescription.updatedFields.name": { $exists: true } } }]);

Follow-ups

  • How do you decide which fields to extend with? — Only those needed by the read that motivated the pattern; every extra field widens the fan-out.
  • What is the failure mode when the source updates? — Divergence you cannot detect without a reconciliation job; build the job when you build the duplication, not after the first bug report.
  • How does this interact with sharding? — Favourably: it removes cross-shard lookups from the hot read path, which is often the whole reason to do it.

Common wrong answer

"Duplication is bad, normalise it and use $lookup." That is the relational reflex, and it is the single most common reason a MongoDB design interview goes badly. The right frame is that duplication is a deliberate trade of write cost and consistency for read cost — sometimes wrong, never automatically wrong.

midHow do you model a many-to-many relationship?

Answer

Three options, chosen by which side is read and how big the sets are. If one side is small and bounded, embed an array of references on that side — a student document with courseIds: [...] — and index it (multikey) so you can query from either direction. If both sides are large, or the relationship itself carries data (enrolment date, grade, role), use a dedicated relationship collection, exactly like a join table, with compound indexes for both directions. The third option, and the one that reads best in an interview, is the two-way embedded reference: keep bounded arrays on both sides when both directions are hot and the sets stay small, accepting that you now have two writes to keep aligned.

Example

// Relationship carries data -> its own collection, indexed both ways.
db.enrolments.insertOne({ studentId, courseId, enrolledAt: ISODate(), grade: null });
db.enrolments.createIndex({ studentId: 1, enrolledAt: -1 });
db.enrolments.createIndex({ courseId: 1, studentId: 1 }, { unique: true });

// Bounded on one side -> multikey array plus an index.
db.students.updateOne({ _id: s }, { $addToSet: { courseIds: c } });
db.students.createIndex({ courseIds: 1 });

Follow-ups

  • Why $addToSet rather than $push? — It is idempotent, which matters because retries in a distributed client are normal; $push duplicates on retry.
  • How do you enforce the uniqueness of a pair? — A unique compound index on the relationship collection; there is no way to enforce it inside an array across documents.
  • What breaks when you shard this? — The relationship collection can only be shard-key-efficient in one direction; the other direction becomes a scatter-gather, which is often the reason to duplicate the relationship in two collections shaped differently.

Common wrong answer

"Put an array of IDs on both sides and keep them in sync in application code." Fine at small scale, but candidates rarely mention that the two writes are not atomic across documents without a transaction, so a crash mid-way leaves a one-directional edge. Name that, and say how you would detect it.

midDo you use schema validation? How?

Answer

Yes, as a guardrail rather than a type system. $jsonSchema validators are attached to a collection and checked on insert and update; they are excellent for the invariants that must never be violated regardless of which service writes (required fields, types, enum values, numeric ranges) and poor as a substitute for application-level modelling. Since MongoDB 5.0 a rejected write returns the specific failing rule in the error, which finally made validators debuggable in production. The two knobs that matter are validationLevel (strict checks every write; moderate only checks documents that already pass, so existing bad documents are not blocked from being updated) and validationAction (error or warn). I roll a validator out as warn, measure the violations, fix them, then move to error.

Example

db.runCommand({ collMod: "orders",
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["customerId", "status", "total"],
    properties: {
      status: { enum: ["pending", "paid", "shipped", "cancelled"] },
      total:  { bsonType: "decimal", minimum: 0 }
    } } },
  validationLevel: "moderate", validationAction: "warn" });

Follow-ups

  • Why decimal for money and not double? — Decimal128 (3.4+) is exact base-10; double is binary floating point and will lose cents.
  • Does a validator apply retroactively? — No. Existing documents are untouched until they are written; that is what validationLevel: "moderate" is designed around.
  • Where does validation belong when several services share a collection? — In the database, precisely because you cannot trust every writer; that is the strongest argument for validators.

Common wrong answer

"Validation defeats the purpose of a schemaless database." It confuses "no imposed schema" with "no invariants". The interviewer is checking whether you understand that flexibility is about evolution, not about tolerating a status field containing "Paid", "PAID" and true.

seniorWhen would you put several entity types in one collection?

Answer

When they are read together. The single-collection pattern stores related entities of different types in one collection with a discriminator field and a shared partition key, so one indexed query returns a whole object graph without a join — an order plus its lines plus its shipments, all keyed by orderId. It is the document-store answer to "I need the aggregate in one round trip but the pieces are too big or too write-hot to embed". The costs are real and you must name them: indexes become sparser and more polymorphic, schema validation gets weaker (you validate a union), and every query must include the type discriminator or you will read the wrong shape. I would use it for a hot read path that currently does three round trips, and not as a default.

Example

// One indexed range returns the whole order aggregate, ordered by type.
{ _id: "order:1001",      pk: "1001", type: "order",    status: "paid" }
{ _id: "order:1001:l:1",  pk: "1001", type: "line",     sku: "C-2M", qty: 2 }
{ _id: "order:1001:s:1",  pk: "1001", type: "shipment", carrier: "DPD" }

db.orders.createIndex({ pk: 1, type: 1 });
db.orders.find({ pk: "1001" });                 // one query, whole graph

Follow-ups

  • How does this interact with the shard key? — Very well: pk becomes the shard key, so the whole aggregate lives on one shard and the read is targeted, not scatter-gather.
  • What about polymorphic documents inside one type? — The polymorphic pattern (different optional fields per subtype) is fine; use partial or sparse indexes so the index only carries the documents that have the field.
  • How do you keep this maintainable? — A strict discriminator, a shared prefix convention for _id, and repository code that never queries without type.

Common wrong answer

"Never — one collection per entity, like one table per entity." That is the relational default carried over unexamined. MongoDB collections are not tables; they are index scopes. The question is which documents you want to be able to read with one index, and sometimes that spans types.

seniorThe same data has to serve a transactional write path and an analytics read path. How do you model that?

Answer

I stop trying to make one shape serve both. The write path wants small, contention-free documents; the analytics path wants pre-aggregated documents that answer a dashboard in one index seek. So I keep the source of truth in its transactional shape, and maintain a second, derived collection with the computed pattern — rollups written incrementally ($inc on a per-day-per-dimension document) or materialised periodically with $merge. That gives idempotent, restartable refreshes and lets me rebuild the rollup from source at any time. At Atlas scale the alternative worth naming is analytics nodes: dedicated replica set members with a workload-specific read preference tag, so the reporting query never competes for the primary's cache.

Example

// Incremental materialisation: idempotent, restartable, cheap to re-run.
db.orders.aggregate([
  { $match: { placedAt: { $gte: since } } },
  { $group: { _id: { d: { $dateTrunc: { date: "$placedAt", unit: "day" } }, region: "$region" },
              revenue: { $sum: "$total" }, orders: { $sum: 1 } } },
  { $merge: { into: "daily_revenue", on: "_id", whenMatched: "replace", whenNotMatched: "insert" } }
]);

Follow-ups

  • $merge or $out? — $out replaces the whole target collection and cannot be incremental; $merge (4.2+) upserts into an existing collection and can write to another database, which is what you want for rollups.
  • How do you keep the rollup fresh in real time? — $inc on the rollup document in the same code path as the write, with the aggregation job as a periodic corrector, or drive it from a change stream with a resume token.
  • When is this the wrong answer? — When the analytics are genuinely ad hoc and unbounded; then you export to a columnar store rather than pretending MongoDB is one.

Common wrong answer

"Just run the aggregation on a secondary." Reading from a secondary moves the CPU but not the working set: the analytics scan still evicts the operational data from that node's WiredTiger cache, and secondaries also apply the full oplog. Reading from a secondary is a tactic; a derived collection is a design.

principalHow do you guide a team of relational engineers through their first MongoDB design?

Answer

I change the artefact they produce. A relational team starts with an ER diagram; I make them start with a written list of access patterns — for each one: the query shape, the expected frequency, the latency budget, and the result-set size. The model is then derived from that list and reviewed against it, so "why is this embedded?" always has an answer that points at a line in the list. I add three guardrails: a schema review checkpoint before any new collection ships, a rule that every query in the code must map to a declared index (enforced by a test that runs explain and fails on COLLSCAN above a row threshold), and a shared vocabulary of the named patterns so reviews are about "is the subset pattern right here?" rather than personal taste. The hardest habit to break is not normalisation, it is the assumption that the model can be fixed later with a migration.

Example

// The artefact that replaces the ER diagram, one row per access pattern:
// pattern              | shape                        | freq/s | p99 budget | rows
// post page            | find(comments by postId)     |  1,200 |  40 ms     | 20
// moderation queue     | find(status:pending, sort at)|      2 | 200 ms     | 50
// "my comments"        | find(authorId, sort at)      |     30 | 100 ms     | 20
// Every index in the codebase must be justified by a row above.

Follow-ups

  • How do you enforce it without becoming the bottleneck? — Codify it: a lint-level CI check for COLLSCAN, a template for the access-pattern doc, and two or three people trained as reviewers rather than one gatekeeper.
  • What do you do about the ORM instinct? — Be explicit that an ODM mapping one class to one collection reproduces the relational model in a document store; allow it only where the aggregate genuinely is one entity.
  • How do you handle the team that wants foreign keys? — Acknowledge the real loss (no referential integrity), and replace it with something concrete: a reconciliation job, and transactions where the invariant is genuinely cross-document.

Common wrong answer

"Train them on the patterns and review PRs." Too passive, and it is the answer everyone gives. What the interviewer wants at this level is a mechanism — a changed artefact, an automated check, a named review gate — that keeps working when you are on holiday.

principalYour model was right two years ago and is wrong now. How do you get out of it?

Answer

I treat it as a migration programme, not a refactor, and I sequence it so that every step is independently revertible. First, quantify: which access patterns are now dominant, and what do they cost today (from $queryStats, the profiler and Atlas Performance Advisor)? Second, introduce the new shape alongside the old one, populated by dual writes or a change-stream projector, with the read path behind a flag and a comparison mode that reads both and reports divergence. Third, cut reads over per access pattern, not per collection, watching error and latency budgets. Fourth, stop writing the old shape, and only then delete it. The two things I insist on are a divergence metric during the overlap and a written kill criterion, because the failure mode of these programmes is not a bad migration, it is a migration that stalls at 80% and leaves two shapes forever.

Example

// Change-stream projector: resumable, idempotent, restartable from a token.
const cs = db.orders.watch([], { fullDocument: "updateLookup", resumeAfter: token });
for await (const ev of cs) {
  await projected.updateOne({ _id: ev.documentKey._id },
                            { $set: project(ev.fullDocument) }, { upsert: true });
  await tokens.updateOne({ _id: "orders" }, { $set: { token: ev._id } });
}

Follow-ups

  • How do you handle the backfill of the existing hundreds of millions of documents? — Range-partition by _id, run bounded-rate workers, checkpoint per range, and throttle on replication lag and cache dirty percentage rather than on a fixed sleep.
  • What if the new shape needs a different shard key? — Since 5.0 you can reshard a collection online; on 8.0 that is hours rather than days for large collections, but plan for the extra disk and the write throughput hit, and rehearse it on a restored copy first.
  • How do you avoid a permanent double-write? — A dated kill criterion in the plan, owned by a named person, with the deletion PR written in advance.

Common wrong answer

"Write a migration script and run it in a maintenance window." At any real size there is no window long enough, and a single script has no revert. The senior signal is the overlap period with divergence measurement — the willingness to run both shapes deliberately for weeks.

02Indexing and the query planner

The second pillar, and the one where a wrong answer is most visible: everyone can write a query, far fewer can say why it is slow. Screeners want the definition and the write cost; mid-level wants ESR and a readable explain; senior wants plan selection, index builds on live systems, and the discipline of not having forty indexes. Principal gets asked how indexing is governed across many teams. MongoDB 8.3 changed the ground here: the Cost-Based Ranker is now the default plan-selection mechanism for eligible queries instead of the old "race the candidate plans over a sample" approach — knowing that, and knowing the old behaviour is still what you will meet on 8.0 and earlier, is a strong currency signal.

Docs: MongoDB Manual — Indexes

screenerWhat is an index in MongoDB, and what does it cost?

Answer

A B-tree (WiredTiger's B+-tree) mapping key values to record ids, maintained on every write. Without one, a query is a COLLSCAN: every document read and tested. With one, the planner can do an IXSCAN over a contiguous key range and fetch only matching documents. The costs are three: disk and — more importantly — RAM, because indexes compete with documents for the WiredTiger cache and an index that does not fit in cache is a random-I/O generator; write amplification, since every insert, delete and update of an indexed field updates the index too; and a small planning cost, since more candidate indexes means more work choosing between them. Every collection has a mandatory unique index on _id that you cannot drop.

Example

db.orders.createIndex({ customerId: 1, placedAt: -1 });
db.orders.totalIndexSize();          // bytes - compare against available cache
db.orders.aggregate([{ $indexStats: {} }]);   // ops since last restart, per index

Follow-ups

  • How much RAM do indexes need? — Ideally the whole working set of indexes fits in cache; WiredTiger defaults to 50% of (RAM − 1 GB), and 8.2 added the option to configure the cache as a percentage of RAM directly.
  • Does index direction matter? — Not for a single-field index (it can be walked either way); it matters for compound indexes when the sort mixes directions.
  • How do you find unused indexes? — $indexStats across all members over a full business cycle; drop only after hiding the index first (collMod hidden, 4.4+) so you can un-hide instantly if something regresses.

Common wrong answer

"Indexes make reads faster, so add one per query." That is how collections end up with 25 indexes, a write path three times slower than it needs to be, and an index working set larger than RAM. The senior framing is that an index is a write-time cost you pay to buy read latency, so the count is a budget, not a free variable.

screenerIn a compound index, does field order matter? What is the ESR rule?

Answer

Order matters completely: a compound index supports queries on a prefix of its fields, so {a:1,b:1,c:1} serves {a}, {a,b} and {a,b,c}, but not {b} or {b,c}. The rule for laying one out is ESR: Equality fields first, then Sort fields, then Range fields. Equality first because it narrows the scan to a contiguous region; sort next because an index can only supply an ordering if the sort keys directly follow the equality keys; range last because a range makes everything after it non-contiguous, so a sort field placed after a range field forces an in-memory sort. Naming ESR and then explaining why — contiguity of index keys — is the difference between reciting and understanding.

Example

// Query: equality on status, sort by createdAt desc, range on amount.
db.orders.find({ status: "paid", amount: { $gt: 100 } }).sort({ createdAt: -1 });

db.orders.createIndex({ status: 1, createdAt: -1, amount: 1 });   // ESR - no SORT stage
db.orders.createIndex({ status: 1, amount: 1, createdAt: -1 });   // range before sort
//   -> IXSCAN then an in-memory SORT; blows up past 100 MB without an index to help

Follow-ups

  • Can one index serve a sort in the opposite direction? — Yes for a whole-index reversal ({a:1,b:1} serves sort({a:-1,b:-1})), no for a mixed one (sort({a:1,b:-1}) needs {a:1,b:-1}).
  • What is index intersection and why do you rarely rely on it? — MongoDB can combine two single-field indexes for one query, but it is chosen rarely, cannot supply a sort, and is nearly always beaten by the right compound index.
  • Where does an equality on an array field sit in ESR? — Still in E, but the index becomes multikey, which forbids a second array field and can prevent covering.

Common wrong answer

"Order doesn't really matter, the planner will sort it out." It will not: the prefix rule is structural, not heuristic. The other common miss is putting the range field before the sort field — the query still uses the index, explain still shows IXSCAN, and it still does a blocking in-memory sort that falls over at scale.

midWhat is a covered query, and how do you know you got one?

Answer

A covered query is answered entirely from the index: every field in the filter, the sort and the projection is in the index, so there is no FETCH of the document at all. In explain("executionStats") you see an IXSCAN with no FETCH above it and totalDocsExamined: 0 — that zero is the tell. The catch is that you must explicitly exclude _id unless _id is in the index, because it is projected by default. Covered queries cannot happen over a multikey index for the array field, and not on a sharded cluster unless the shard key is also in the index (the router needs it). Covering is the single cheapest optimisation available for a hot read: it turns a random document fetch into a sequential index walk.

Example

db.users.createIndex({ tenantId: 1, email: 1 });

db.users.find({ tenantId: 7 }, { _id: 0, email: 1 })
        .explain("executionStats");
// winningPlan: IXSCAN (no FETCH)
// executionStats: { totalKeysExamined: 812, totalDocsExamined: 0, nReturned: 812 }

Follow-ups

  • Why does forgetting _id: 0 break it? — _id is returned unless excluded, so the engine must fetch the document to get it.
  • Should you add fields to an index just to cover? — Sometimes; that is the point of a "covering index", but each extra field enlarges the index and so the cache pressure. Measure the index size against the latency win.
  • Does a covered query still respect read concern? — Yes, covering is a plan property; it changes nothing about visibility or durability.

Common wrong answer

"A covered query is one that uses an index." That is just an indexed query. The distinguishing property is that the document is never read, and the candidate who cannot point at totalDocsExamined: 0 has not actually looked at an explain plan recently.

midWalk me through an explain plan. What do you look at first?

Answer

I run explain("executionStats") and read four numbers before anything else: nReturned, totalKeysExamined, totalDocsExamined and executionTimeMillis. The health check is the ratio — for a well-indexed query totalKeysExamined ≈ totalDocsExamined ≈ nReturned. Keys far above returned means the index is not selective enough for the predicate; docs far above returned means the index cannot evaluate part of the filter and the engine is fetching to test. Then I read the stage tree bottom-up: COLLSCAN is the obvious failure, SORT means a blocking in-memory sort, SORT_KEY_GENERATOR confirms it, PROJECTION_COVERED confirms covering, and FETCH above IXSCAN is normal but should be proportionate. On a sharded cluster I also check SHARD_MERGE versus SINGLE_SHARD — a scatter-gather that should have been targeted is the most common sharded performance bug.

Example

db.orders.find({ status: "paid" }).sort({ placedAt: -1 }).limit(20)
         .explain("executionStats");
// Bad:  IXSCAN {status:1} -> FETCH -> SORT
//       nReturned 20, totalKeysExamined 1,900,000, totalDocsExamined 1,900,000
// Fix:  db.orders.createIndex({ status: 1, placedAt: -1 })
// Good: IXSCAN {status:1, placedAt:-1} -> FETCH -> LIMIT
//       nReturned 20, totalKeysExamined 20, totalDocsExamined 20

Follow-ups

  • What does allPlansExecution add? — The trial results for every candidate plan, which is how you see that the plan you expected lost the race (and, on 8.3+, how you compare the Cost-Based Ranker's estimate against reality).
  • Does explain actually run the query? — queryPlanner mode does not; executionStats and allPlansExecution do execute it (writes are not applied).
  • How do you explain an aggregation? — db.coll.explain("executionStats").aggregate([...]); look for which prefix stages were pushed down into the query layer versus executed in the aggregation runtime.

Common wrong answer

"It says IXSCAN, so the query is fine." IXSCAN only means an index was used, not that it was the right one — a query examining two million keys to return twenty is an IXSCAN too. The number that matters is the ratio, and candidates who never mention totalKeysExamined have not debugged a slow query in anger.

midWhat is a multikey index and what are its restrictions?

Answer

Any index on a field whose value is an array becomes multikey automatically — MongoDB stores one index entry per array element, so a document with 200 tags contributes 200 keys. That is what makes find({ tags: "urgent" }) an indexed equality rather than a scan. The restrictions: a compound index may contain at most one array field (otherwise the key count would be the Cartesian product); multikey indexes cannot cover a query for the array field; and the multikey flag is a property of the index, set the first time an array document is inserted and never cleared, so an index can stay "multikey" after the arrays are gone. The subtle correctness trap is that a query with two conditions on the same array matches if different elements satisfy each condition — you need $elemMatch to require one element to satisfy all of them.

Example

// doc: { scores: [ { subject: "math", grade: 40 }, { subject: "art", grade: 95 } ] }
db.students.find({ "scores.subject": "math", "scores.grade": { $gt: 90 } });   // MATCHES (wrong)
db.students.find({ scores: { $elemMatch: { subject: "math", grade: { $gt: 90 } } } }); // no match

db.students.createIndex({ "scores.subject": 1, "scores.grade": 1 });  // multikey, one array path

Follow-ups

  • Why can't a multikey index cover the array field? — The index holds elements, not the array, so the original array cannot be reconstructed from index keys.
  • How do you index arrays of subdocuments efficiently? — Index the dotted paths you filter on; if the object shape varies, consider a wildcard index (4.2+) but expect a much larger index.
  • How do you find that an index went multikey unexpectedly? — explain reports isMultiKey and multiKeyPaths; a surprise there usually means a field is sometimes an array and sometimes a scalar.

Common wrong answer

"You create a multikey index with a special option." There is no option — it is automatic and inferred from the data, which is exactly why it can surprise you. Candidates who think it is opt-in also miss that a single stray array value changes the index's behaviour permanently.

midPartial index or sparse index — which and why?

Answer

Partial, almost always. A sparse index (old, still everywhere in existing codebases) omits documents that lack the field. A partial index (3.2+) indexes only documents matching an arbitrary partialFilterExpression, which is a strict superset of sparse behaviour and far more useful: index only the 0.5% of orders that are pending, and the index is a hundredth of the size with a hundredth of the write cost. The trap with both is that the planner will only use them when it can prove the query is a subset of the filter, so the query must repeat the partial condition. The other important pairing is partial + unique: that gives you "unique among documents where deleted is false", which sparse-unique cannot express.

Example

db.orders.createIndex(
  { placedAt: -1 },
  { partialFilterExpression: { status: "pending" }, name: "pending_by_date" });

db.orders.find({ placedAt: { $lt: cutoff } });                     // NOT used
db.orders.find({ status: "pending", placedAt: { $lt: cutoff } });  // used

// Unique only among live documents:
db.users.createIndex({ email: 1 }, { unique: true,
  partialFilterExpression: { deletedAt: { $exists: false } } });

Follow-ups

  • Is sparse ever still the right choice? — Rarely; effectively only for legacy compatibility. partialFilterExpression: { f: { $exists: true } } replicates it.
  • What happens to a unique+sparse index and documents missing the field? — They are simply not indexed, so many documents may miss the field without violating uniqueness — a common source of "why did the duplicate get in?".
  • Do partial indexes work with TTL? — Yes, TTL indexes accept a partialFilterExpression (3.2+), which is how you expire only some documents in a collection.

Common wrong answer

"They're basically the same thing." They are not, and the difference bites: a candidate who believes the planner will use the partial index for any query on the indexed field will ship a query that silently collection-scans, because the planner refuses to use an index whose coverage it cannot prove.

seniorHow does MongoDB choose between candidate plans, and what changed in 8.3?

Answer

Historically, empirically: for a new query shape the planner enumerated candidate plans and raced them, executing each for a trial period (by default up to 101 works or the first batch) and picking the one that produced results fastest, then caching that plan against the query shape. The cache entry is re-evaluated when performance degrades by a factor (10x works), on index or collection changes, and on restart — which is why a restart can change your latency profile. From MongoDB 8.3 the Cost-Based Ranker is the default for eligible queries: plans are ranked from statistics and a cost model, the way a relational optimiser does, with new serverStatus metrics for its behaviour; the trial-based path remains as the fallback for ineligible queries and is still what you get on 8.0 and earlier. What this changes practically is that plan choice becomes less sensitive to which documents happened to be near the start of the scan, and more sensitive to statistics being current.

Example

db.orders.getPlanCache().list();                 // cached shapes and their plans
db.orders.getPlanCache().clear();                // force re-planning
db.orders.find(q).hint({ status: 1, placedAt: -1 });   // pin a plan for one query
db.adminCommand({ getParameter: 1, planRankerMode: 1 });  // 8.3: ranker mode

Follow-ups

  • When is hint() the right answer? — As a targeted, documented fix for a query whose plan flips; never as a codebase-wide habit, because a hint freezes a decision that should track the data.
  • What are index filters / query settings? — Index filters (3.2) restrict the planner's candidate set per query shape but do not survive restart; setQuerySettings (8.0) replaced them with a persisted, replicated equivalent, which is the modern way to pin a plan cluster-wide.
  • Why can the same query be fast then slow after a deploy? — A new index changes the candidate set and evicts the plan-cache entry, so the query is re-raced against different competition.

Common wrong answer

"MongoDB uses a cost-based optimiser with table statistics, like SQL Server." That was flatly untrue until 8.3 and is only partly true now. Saying it unqualified marks you as answering from relational instinct; the accurate senior answer is "empirical racing plus a plan cache, and since 8.3 a cost-based ranker by default for eligible queries".

midMy query has an index but is still slow. What are the usual causes?

Answer

In rough order of frequency: (1) the index is used but not selective — totalKeysExamined is huge because the leading field has few distinct values; (2) an in-memory SORT because the sort field is not adjacent to the equality fields (an ESR violation); (3) a negation or a non-anchored regex — $ne, $nin, $not and /foo/ cannot use an index to narrow, only to scan; (4) a collation mismatch, where the query's collation differs from the index's so the index is ineligible; (5) type bracketing, where a numeric range predicate skips documents whose field is a string, and the query silently returns fewer rows than expected; (6) the index simply does not fit in cache, so every seek is disk I/O — visible as high bytes read into cache with low latency inside WiredTiger. And on a sharded cluster: the query lacks the shard key, so it fans out to every shard and takes the slowest one's latency.

Example

db.users.find({ status: { $ne: "active" } });        // scans; invert it if you can
db.users.find({ status: { $in: ["banned", "pending"] } });   // indexed

db.products.find({ name: /phone/ });                 // scan: not anchored
db.products.find({ name: /^phone/ });                // indexed prefix range

// Collation mismatch: the index is unusable for this query.
db.users.createIndex({ email: 1 }, { collation: { locale: "en", strength: 2 } });
db.users.find({ email: "A@b.com" });                 // default collation -> no index

Follow-ups

  • Why can't $ne use an index efficiently? — It matches everything except one contiguous range, so the "matching" region is the whole index minus a slice; scanning it is no better than scanning the collection.
  • What is type bracketing? — Comparison operators only compare within a BSON type, so { age: { $gt: 30 } } never matches age: "35". It is a correctness bug disguised as a performance one.
  • How do you spot cache pressure quickly? — serverStatus().wiredTiger.cache: "bytes currently in the cache" against the configured max, plus the dirty and eviction-triggered numbers; 8.3 added cachePressureQueryPeriodMilliseconds to tune how often that pressure is evaluated.

Common wrong answer

"Add another index." Sometimes right, usually a reflex that makes the write path worse and the plan cache noisier without fixing the actual cause. The strong answer diagnoses first — a specific explain number with a specific cause attached.

seniorHow do you add an index to a 500-million-document collection in production?

Answer

Since MongoDB 4.2 all index builds use the "simultaneous" (hybrid) protocol: the build holds an exclusive lock only briefly at the start and end, so the collection stays readable and writable throughout, and — importantly — the build runs on the primary and on every secondary simultaneously, replicated as a set of oplog entries. That means it is not free: it burns CPU and cache on every member at once, and the secondaries can fall behind. My procedure is: check the estimated index size against free RAM and disk first; build during the lowest-traffic window; watch replication lag, cache dirty percentage and the createIndexes progress in currentOp; and be ready to killOp, which aborts the build cleanly on all members. On very large deployments the older rolling build — one member at a time, taken out of the set, built standalone, resynced — still has a place, and 8.2 added better control over index builds during initial sync. I create indexes in the background of a deployment step, never inside the application's startup path.

Example

db.orders.createIndex({ tenantId: 1, placedAt: -1 }, { name: "tenant_recent" });

db.currentOp({ "command.createIndexes": { $exists: true } });   // progress + opid
db.adminCommand({ killOp: 1, op: <opid> });                      // clean abort everywhere
rs.printSecondaryReplicationInfo();                              // the number to watch

Follow-ups

  • Is { background: true } still a thing? — No: it is ignored from 4.2 and removed as an option in 5.0. Seeing it in a codebase dates the code, and repeating it in an interview dates you.
  • How do you build an index without touching read latency at all? — Rolling build across members, or on Atlas let the platform do a rolling build; either way you accept reduced redundancy while a member is out.
  • What about a unique index on data that might violate it? — The build fails at the end and rolls back; find duplicates first with a $group/$match: { count: { $gt: 1 } } aggregation.

Common wrong answer

"Use background: true so it doesn't lock." A textbook answer that has been wrong since 2019. Worse, it implies the build is cheap; the modern build does not block, but it saturates CPU and cache on every replica set member at once, which is what actually causes the incident.

midWhen would you use a wildcard index, a hidden index, or a TTL index?

Answer

A wildcard index (4.2+) indexes every field under a path — { "attrs.$**": 1 } — and is the right tool for genuinely unpredictable, user-defined attributes where you cannot enumerate the queried fields. It is not a substitute for thinking: it is much larger than targeted indexes, cannot be compound with normal fields (until the limited compound wildcard support in 7.0), and cannot cover. A hidden index (4.4+) is invisible to the planner but still maintained, which makes it the safe way to test dropping an index — hide it, watch for a week, then drop, and un-hide instantly if something regresses. A TTL index is a single-field index on a date whose documents a background thread deletes once past expireAfterSeconds; the sweep runs every 60 seconds and only on the primary, so expiry is approximate, and the deletes are real deletes that hit the oplog and every secondary.

Example

db.products.createIndex({ "attrs.$**": 1 });                       // unpredictable keys
db.orders.createIndex({ oldField: 1 }, { hidden: true });           // test before dropping
db.adminCommand({ collMod: "orders", index: { name: "oldField_1", hidden: false } });

db.sessions.createIndex({ lastSeen: 1 }, { expireAfterSeconds: 3600 });
db.runCommand({ collMod: "sessions",                                 // change it live (5.0+)
  index: { keyPattern: { lastSeen: 1 }, expireAfterSeconds: 7200 } });

Follow-ups

  • Why is TTL expiry not exact? — The background task runs every 60s and processes what it can; under load the backlog grows, so documents can outlive their TTL by minutes. Never use it as a security or correctness boundary.
  • How do you expire at a specific timestamp rather than after a delay? — Set expireAfterSeconds: 0 and store the exact expiry moment in the indexed date field.
  • What is the cheaper alternative to TTL for bulk expiry? — Time-partitioned collections you can drop wholesale, or a time series collection with expireAfterSeconds, which expires whole buckets instead of individual documents.

Common wrong answer

"A wildcard index means you never need to plan indexes again." It is the answer of someone who has not paid for one: wildcard indexes are large, cannot cover, and give the planner a worse candidate than a targeted index. They solve a specific problem — schemas you genuinely do not control — and create a new one everywhere else.

seniorText index or Atlas/MongoDB Search — how do you choose?

Answer

The built-in text index is a legacy capability: one text index per collection, basic stemming and stop words, no relevance tuning worth the name, no fuzzy matching, no faceting, and $text cannot be combined with $or freely or sorted efficiently by score. It is acceptable for "find a product whose name contains these words" on a small collection and nothing more. Real search means MongoDB Search (Lucene, via the separate mongot process): analysers, synonyms, autocomplete, fuzzy, faceting, relevance scoring, and $search as the first pipeline stage. The change worth knowing today is that this stopped being Atlas-only — Search and Vector Search entered public preview for self-managed deployments in 8.2 (Sept 2025) and reached GA on 30 June 2026, free in Community under SSPL, running as mongot alongside mongod. So "we can't use Atlas" is no longer an argument for the legacy text index.

Example

// Legacy: one text index per collection, coarse scoring.
db.products.createIndex({ name: "text", description: "text" });
db.products.find({ $text: { $search: "wireless headphones" } },
                 { score: { $meta: "textScore" } }).sort({ score: { $meta: "textScore" } });

// Modern: $search must be the FIRST stage of the pipeline.
db.products.aggregate([
  { $search: { index: "default",
      compound: { must: [ { text: { query: "wireles headphones", path: ["name","description"],
                                    fuzzy: { maxEdits: 1 } } } ],
                  filter: [ { range: { path: "price", lte: 200 } } ] } } },
  { $limit: 20 }
]);

Follow-ups

  • Why must $search be first? — It executes in mongot, not the query engine; the pipeline receives its results, so nothing can precede it.
  • How fresh are search results? — Eventually consistent: mongot follows the change stream, so there is a short indexing lag. Never read-your-own-write through $search.
  • What is $scoreFusion? — The hybrid-search stage that combines lexical and vector result sets with reciprocal-rank-style fusion; introduced in 8.2 and GA in 8.3, it replaces the hand-rolled $rankFusion-by-$unionWith recipes people wrote before.

Common wrong answer

"Use a text index — MongoDB has full-text search built in." It has full-text matching built in. Candidates who propose $text for a product search with typo tolerance and facets have not built search; and citing "Atlas Search is cloud-only" is now out of date by more than a year.

principalA collection has 27 indexes and nobody knows which are needed. What do you do?

Answer

Measure, hide, then drop — and fix the process that produced 27. Measurement is $indexStats collected from every member (secondaries serve different queries) over a full business cycle including month-end jobs, cross-referenced with $queryStats (7.0+, the sampled per-query-shape statistics that replaced guessing) and, on Atlas, the Performance Advisor's redundancy report. Candidates for removal are indexes with zero or near-zero accesses.ops and indexes that are a strict prefix of another (redundant by the prefix rule). Then I hide each candidate rather than dropping it, wait a week, and drop only after nothing regressed — hiding is instantly reversible, dropping a 40 GB index is a multi-hour rebuild. The process fix is the important half: an index budget per collection, index definitions living in migration code under review rather than being created ad hoc from a shell, and a CI check that fails a PR adding an index without an access pattern in the design doc.

Example

db.orders.aggregate([
  { $indexStats: {} },
  { $project: { name: 1, ops: "$accesses.ops", since: "$accesses.since", key: 1 } },
  { $sort: { ops: 1 } }
]);
// Prefix-redundant: {a:1} is covered by {a:1,b:1}; drop the shorter one.
db.adminCommand({ collMod: "orders", index: { name: "a_1", hidden: true } });

Follow-ups

  • Why is $indexStats from the primary alone misleading? — Counters are per-node and reset on restart, and analytics traffic on secondaries uses different indexes entirely.
  • How do you handle an index used only by a quarterly job? — Keep it and document it, or accept the job being slower; the point is that the decision is recorded, not that the index disappears.
  • What is the cost of the status quo if you do nothing? — Write amplification on every insert, a bigger index working set than RAM, longer index builds on every version upgrade, and slower initial syncs — quantify at least one of these to make the case.

Common wrong answer

"Drop the ones $indexStats shows as unused." Right instinct, dangerous execution: counters reset on restart and are per-member, so "unused" often means "the node restarted on Tuesday" or "only the analytics secondary uses it". Hiding first is what separates someone who has done this from someone who has read about it.

03The Query API: CRUD and operators

The verification layer. Nobody gets hired for knowing $addToSet, but plenty get filtered out for not knowing that an update is atomic at the document level, or for reaching for read-modify-write where a single atomic operator would do. Screeners check fluency; mid-level checks the array operators and upsert semantics; senior is about concurrency — expressing a state transition as one atomic operation instead of a transaction. Interviewers often make this a whiteboard exercise: "increment this counter, but only if the status is still pending".

Docs: MongoDB Manual — CRUD Operations

screenerWhat happens on the server when I run find()? Explain cursors and batching.

Answer

The driver sends a find command; the server plans it, executes enough of it to fill the first batch (101 documents or 16 MB, whichever comes first) and returns that batch plus a cursor id. Subsequent batches are fetched with getMore, each up to 16 MB, and the cursor lives server-side. Two consequences matter in interviews: a cursor holds resources, so it times out after 10 minutes of inactivity by default (cursorTimeoutMillis) and drivers must close cursors they abandon; and the results are not a snapshot — without a transaction or a snapshot read concern, documents can be missed or returned twice if they move during the scan. On a sharded cluster the mongos opens a cursor per targeted shard and merges, which is why an unsorted sharded query returns documents in shard-arrival order.

Example

const cursor = db.orders.find({ status: "paid" }).batchSize(500);
try { for await (const doc of cursor) { /* ... */ } } finally { await cursor.close(); }

// A cursor that must survive a long client-side job:
db.orders.find(q).noCursorTimeout();      // then you MUST close it yourself

Follow-ups

  • When would you change batchSize? — Smaller to bound memory and time-to-first-document for a UI; larger to cut round trips for a bulk export.
  • What is a tailable cursor? — A cursor over a capped collection that stays open at the end of the collection; the modern replacement for its use cases is change streams.
  • What does allowDiskUse mean for find? — From 4.4, a find with a large blocking sort can spill to disk instead of failing at the 100 MB sort limit; it is a safety net, not a design.

Common wrong answer

"find() returns all the matching documents." It returns a cursor and a first batch. Candidates who believe otherwise write code that loads a ten-million-document result set into memory, and they miss the follow-up about cursor timeouts entirely.

screenerWhat is the difference between updateOne, replaceOne and findOneAndUpdate?

Answer

updateOne applies update operators ($set, $inc, $push) to the first matching document and returns only counts. replaceOne swaps the whole document for the one you supply, keeping _id — which is how people accidentally delete fields that another service owns. findOneAndUpdate does the same modification but returns the document, before or after the change depending on returnDocument, in a single atomic round trip; that atomic read-back is what makes it the right primitive for claiming work from a queue or generating a sequence. All three are atomic at the document level — that guarantee is the sentence to say out loud, because it is the foundation of almost every "how do you avoid a race?" answer in MongoDB.

Example

// Atomically claim one job: no transaction needed, no race.
const job = await db.jobs.findOneAndUpdate(
  { status: "queued", runAfter: { $lte: new Date() } },
  { $set: { status: "running", claimedBy: workerId, claimedAt: new Date() } },
  { sort: { priority: -1, runAfter: 1 }, returnDocument: "after" });

Follow-ups

  • Why is replaceOne dangerous in a service-per-field world? — It removes any field not present in the replacement, including ones written by another service since you read.
  • What did returnNewDocument become? — The legacy shell option; drivers standardised on returnDocument: "before" | "after", and you will meet both in existing code.
  • Is updateMany atomic? — Only per document. Other readers can see a partially applied updateMany unless you wrap it in a transaction.

Common wrong answer

"Read the document, change it in the application, write it back." The read-modify-write cycle is the classic lost-update bug, and it is exactly what update operators exist to avoid. Interviewers ask this question specifically to see whether you reach for atomic operators or for application-side state.

midHow do upserts work, and how do you make them safe under retries?

Answer

With { upsert: true }, if the filter matches nothing the server creates a document from the equality clauses of the filter plus the update's operators. $setOnInsert applies only on the insert path, which is how you set a createdAt without overwriting it on every subsequent update. The concurrency subtlety, and the one interviewers probe, is that two concurrent upserts on a filter with no unique index can both insert — the upsert is only atomic because a unique index makes one of them fail with duplicate-key error 11000, which the server then retries as an update. So the rule is: an upsert is safe if and only if the filter is backed by a unique index, and your code still has to handle 11000 for the racing case.

Example

db.counters.createIndex({ tenantId: 1, day: 1 }, { unique: true });

db.counters.updateOne(
  { tenantId: 7, day: "2026-09-08" },
  { $inc: { hits: 1 },
    $setOnInsert: { createdAt: new Date() } },
  { upsert: true });

Follow-ups

  • Which parts of the filter end up in the new document? — Only equality conditions; { n: { $gt: 5 } } contributes nothing, which surprises people.
  • Can an upsert conflict with itself? — Yes: you cannot $set and $setOnInsert the same path, and the server rejects it as a conflicting update.
  • How do upserts behave on a sharded collection? — The filter must include the full shard key, otherwise the router cannot decide where to insert.

Common wrong answer

"Upsert is atomic, so duplicates are impossible." Without a unique index it is a find-then-insert with a window, and under load you will get two documents. This is one of the most common real-world MongoDB bugs and a favourite probe.

midHow do you update a specific element inside an array?

Answer

Four tools, in increasing power. The positional $ updates the first element matched by the query — it requires the array field in the filter and cannot reach a second level. The all-positional $[] updates every element. Filtered positional $[identifier] with arrayFilters (3.6+) updates exactly the elements matching a condition, and is the modern default because it is explicit and works for nested arrays. And since 4.2, an update can be an aggregation pipeline, which lets you compute the new array with $map/$filter when the change depends on existing values. For adding and removing there is $push (with $each, $sort, $slice, $position), $addToSet for idempotent adds, and $pull/$pullAll for removal by predicate.

Example

// Positional $ - first match only, array field must be in the filter.
db.orders.updateOne({ _id: o, "lines.sku": "C-2M" }, { $set: { "lines.$.qty": 3 } });

// arrayFilters - every element that matches, nested paths supported.
db.orders.updateOne({ _id: o },
  { $set: { "lines.$[l].discount": 0.1 } },
  { arrayFilters: [ { "l.unitPrice": { $gte: 100 } } ] });

// Pipeline update - the new value depends on the old one.
db.orders.updateOne({ _id: o }, [
  { $set: { total: { $sum: { $map: { input: "$lines", as: "l",
              in: { $multiply: ["$$l.unitPrice", "$$l.qty"] } } } } } }
]);

Follow-ups

  • Why does $ sometimes update the wrong element? — Because it binds to the first array element that matched the query, and with multiple conditions across different elements that is not the element you meant; $elemMatch in the filter or arrayFilters fixes it.
  • Is $push with $slice atomic? — Yes, the whole update document is applied atomically to that one document.
  • How do you sort an embedded array on write? — $push: { a: { $each: [], $sort: { k: 1 } } } — an empty $each sorts in place, which is the idiomatic trick.

Common wrong answer

"Read the array, modify it in the app, $set the whole array back." It works in a demo and loses concurrent writes in production, and it rewrites the entire array through the oplog for a one-element change. Interviewers use array updates precisely to see whether you know the server-side operators.

midHow do you write ten thousand documents efficiently?

Answer

bulkWrite with a batch of a few hundred to a few thousand operations, unordered unless order matters. ordered: true (the default) stops at the first error and guarantees sequential application; ordered: false lets the server parallelise and continue past failures, returning all the errors at the end — it is substantially faster and the right default for independent writes. The server splits a bulk into batches under the 16 MB / 100,000-operation limits automatically. Bulk writes are not transactional: each operation is independently atomic, so partial application is normal and your code must be able to re-run safely. The 8.0 additions worth naming are the new bulkWrite command that can span multiple collections in one round trip, and the driver-level support for it.

Example

await db.events.bulkWrite(ops, { ordered: false, writeConcern: { w: "majority" } });
// ops: [ { insertOne: { document: {...} } },
//        { updateOne: { filter: {...}, update: { $set: {...} }, upsert: true } },
//        { deleteOne: { filter: {...} } } ]
// On failure: err.writeErrors[] carries index + code per failed op; retry only those.

Follow-ups

  • What are retryable writes and when do they not apply? — Drivers retry a single failed write once after a transient network or failover error (default since 3.6/4.2); the retry is safe because of a per-write session id, but it does not apply to unacknowledged writes or to multi-document operations like updateMany.
  • How do you make a bulk load idempotent? — Deterministic _ids (a hash of the natural key) plus upserts, so a replay converges rather than duplicating.
  • What is the throughput limiter in practice? — Usually index maintenance and oplog write volume, not the insert itself; loading into a collection with eight indexes is a different exercise from loading into one with one.

Common wrong answer

"Use insertMany in a transaction so it's all-or-nothing." A ten-thousand-document transaction fights the 16 MB oplog entry limit and the default 60-second transaction lifetime, holds cache-dirtying snapshots open, and hurts the whole cluster. Bulk loads should be idempotent, not transactional.

seniorImplement compare-and-set without a transaction.

Answer

Put the precondition in the filter. Because a single-document update is atomic and the filter is evaluated as part of it, updateOne({ _id, status: "pending" }, { $set: { status: "paid" } }) is a compare-and-set: if another writer already moved it, matchedCount is 0 and you know you lost. For a general optimistic-concurrency scheme, carry a version field, filter on the version you read, and $inc it in the same update. This is the single most useful MongoDB concurrency idiom and it covers the great majority of cases people reach for transactions to solve. The two limits to name: it only works when the invariant lives inside one document, and it gives you no way to block — the loser retries, so the operation must be safe to retry.

Example

const res = await db.orders.updateOne(
  { _id: id, version: expectedVersion, status: "pending" },
  { $set: { status: "paid", paidAt: new Date() }, $inc: { version: 1 } });

if (res.matchedCount === 0) {
  // Someone else changed it: re-read, re-decide, retry. Do not blind-write.
}

Follow-ups

  • How do you bound retries? — Exponential backoff with jitter and a hard cap; unbounded CAS retries under contention are a livelock.
  • When must you escalate to a transaction? — When the invariant spans documents — the classic "move money between two accounts" — or spans collections.
  • How would you implement a distributed lock? — An upsert into a locks collection with a unique _id, a TTL index for the lease, and a fencing token ($inc) so a paused holder cannot act after its lease expired.

Common wrong answer

"Read it, check the status in code, then update." That is the race the question is about. The second-most-common miss is doing the CAS correctly but ignoring matchedCount, so the failed update looks identical to the successful one and the bug appears only under load.

midHow do you paginate correctly?

Answer

Keyset (range) pagination on a unique, indexed sort key — not skip. skip(n) must walk and discard n entries every time, so page 1,000 costs a thousand times page 1, and it is also incorrect under concurrent writes: an insert before your position shifts every subsequent page, duplicating or skipping rows. Keyset pagination filters on "after the last item I saw", which is O(page size) and stable. The requirement is that the sort key be unique; if it is not — sorting by createdAt where timestamps collide — you make it unique by appending _id as a tiebreaker and comparing the pair. For a UI that needs "jump to page 47" you either accept skip for shallow pages, or precompute page boundaries.

Example

db.orders.createIndex({ placedAt: -1, _id: -1 });

// Page N+1: compare the (placedAt, _id) pair to break ties correctly.
db.orders.find({ $or: [
    { placedAt: { $lt: last.placedAt } },
    { placedAt: last.placedAt, _id: { $lt: last._id } } ] })
  .sort({ placedAt: -1, _id: -1 }).limit(20);

Follow-ups

  • How do you give the user a total count? — countDocuments on the same filter is a full index scan; for large collections either show an approximate count (estimatedDocumentCount, from metadata), cap it ("1000+"), or maintain a counter.
  • Does this work on a sharded cluster? — Yes, and better than skip, which forces each shard to over-fetch skip + limit documents for the router to merge.
  • What about $facet for "results plus count"? — Convenient, but it runs both branches over the same input and the count branch is still a full scan; it saves a round trip, not work.

Common wrong answer

"skip((page-1)*size).limit(size), with an index it's fine." The index does not help: skip still traverses the skipped keys. And the correctness half — pages shifting under concurrent inserts — is the part almost nobody mentions and the part a senior interviewer is listening for.

seniorWhat are the sharp edges of the query language a senior engineer should know?

Answer

Five that cause real incidents. Type bracketing: comparison operators compare only within a BSON type, so { age: { $gt: 30 } } silently ignores documents where age is a string — a data-quality bug that looks like a query bug. Null versus missing: { f: null } matches both a null value and an absent field, and only { f: { $exists: true, $eq: null } } separates them. Dotted paths through arrays match if any element matches, which is why $elemMatch exists. Nested document equality is order-sensitive: { a: { x: 1, y: 2 } } does not match a stored { y: 2, x: 1 }, so query by dotted paths, never by whole subdocument. And $where and $expr: $where runs server-side JavaScript, cannot use indexes and is an injection risk — treat it as forbidden; $expr (3.6+) is the safe way to compare two fields of the same document and can use an index for equality on the leading field.

Example

db.c.find({ a: { x: 1, y: 2 } });              // exact subdoc, order matters
db.c.find({ "a.x": 1, "a.y": 2 });             // what you meant

db.c.find({ f: null });                         // null OR missing
db.c.find({ f: { $exists: true, $eq: null } }); // explicitly null only

db.orders.find({ $expr: { $gt: ["$shipped", "$ordered"] } });   // field vs field, safe
db.orders.find({ $where: "this.shipped > this.ordered" });      // never: no index, injection

Follow-ups

  • Is NoSQL injection a real risk? — Yes: passing an unvalidated object as a filter lets a caller supply { $ne: null } or $where. Validate types at the boundary and never build filters from raw request bodies.
  • Why does $expr perform poorly sometimes? — Most $expr forms cannot narrow with an index, so they degrade to a scan with a per-document expression evaluation.
  • How do you find type inconsistency at scale? — An aggregation grouping by { $type: "$field" }; run it before trusting any range query on legacy data.

Common wrong answer

"MongoDB is JavaScript, so comparisons work like JavaScript." They do not — BSON has its own type ordering and comparisons never coerce across types. Candidates carrying JavaScript intuitions write range queries that quietly miss a third of the collection and never see an error.

04Aggregation pipelines

Where mid-level candidates are separated from senior ones. Everyone can write $match then $group; far fewer can say which stages are blocking, which get pushed into the query layer, what $lookup actually executes, and when the pipeline is the wrong tool entirely. Expect a live exercise — "given these two collections, produce this report" — where the interviewer cares more about your stage ordering and your stated memory assumptions than about the exact operator names. Principal candidates get the governance version: when does aggregation belong in the database at all, versus in an analytics store.

Docs: MongoDB Manual — Aggregation Pipelines

screenerWhat is the aggregation pipeline and when do you use it instead of find?

Answer

A sequence of stages, each consuming a stream of documents and emitting a transformed stream — the document-store equivalent of composing SQL's WHERE, GROUP BY, JOIN, window functions and projections, but as an ordered, explicit list. You use find when you want documents that already exist; you use aggregation when you need to reshape, group, join, compute or materialise. Two properties matter for the follow-ups: some stages are streaming ($match, $project, $limit, $unwind) and pass documents through one at a time, while others are blocking ($group, $sort without a supporting index, $bucket, $facet) and must consume their whole input before emitting anything — those are where memory limits and latency come from. And the optimiser rewrites the pipeline before executing it, so the pipeline you wrote is rarely the pipeline that runs.

Example

db.orders.aggregate([
  { $match: { placedAt: { $gte: since }, status: "paid" } },   // streaming, indexed
  { $group: { _id: "$customerId", spend: { $sum: "$total" }, n: { $sum: 1 } } },  // blocking
  { $match: { spend: { $gt: 1000 } } },
  { $sort: { spend: -1 } },
  { $limit: 50 }
]);

Follow-ups

  • Is aggregate slower than find for a simple filter? — Effectively no; a pipeline whose first stage is $match is executed by the same query layer with the same index selection.
  • What replaced mapReduce? — The aggregation pipeline. mapReduce is deprecated since 5.0, is dramatically slower, and appearing to prefer it is a strong negative signal.
  • Where does the pipeline run on a sharded cluster? — Stages before the first blocking one run on each shard; the rest run on the merging node (a shard, or mongos for some stages).

Common wrong answer

"Aggregation is for analytics, so it's slow — avoid it in the request path." Plenty of production request paths are single-digit-millisecond aggregations. The distinction that matters is streaming versus blocking stages and whether the first $match is indexed, not the word "aggregation".

midWhich optimisations does the aggregation engine apply, and how do you help it?

Answer

The main ones are coalescence and reordering: $sort + $limit collapse into a top-k sort that only keeps k documents in memory; $match is pushed as early as possible, including before a $project, $unwind or $addFields when the fields it references are untouched; $limit moves earlier; consecutive $matches merge with $and; and a leading $match/$sort/$project prefix is pushed down into the query layer so it can use an index and be covered. The way you help is to put the most selective $match first with an index behind it, project away large unused fields before a blocking stage so less data is buffered, and never place a $match after a $group if it could have gone before. You verify with explain, which shows the rewritten pipeline — the first thing to check is whether your $match became an IXSCAN.

Example

// As written: unwind 40M subdocuments, then filter.
[ { $unwind: "$lines" }, { $match: { "lines.sku": "C-2M", status: "paid" } } ]

// The optimiser can only pull the `status` predicate before $unwind - it cannot
// know the lines predicate is safe. Write it yourself:
[ { $match: { status: "paid", "lines.sku": "C-2M" } },   // indexed, huge reduction
  { $unwind: "$lines" },
  { $match: { "lines.sku": "C-2M" } } ]                  // now per-element

Follow-ups

  • How do you see the optimised pipeline? — db.c.explain().aggregate([...]); the returned stages are the rewritten ones, not yours.
  • How do you turn the optimiser off for debugging? — { allowDiskUse: true, ... } is unrelated; use the disableAggPipelineOptimization failpoint or compare stage-by-stage in a test — never disable optimisation in production.
  • What is the slot-based execution engine (SBE)? — A compiled, columnar-ish executor introduced in 5.0 for eligible $group/$lookup shapes. It has had a bumpy life: disabled by default in 7.0.17+ patches, on by default again in 8.0, and since 8.0.0 the classic engine always does multiplanning even when SBE executes the winner.

Common wrong answer

"The optimiser reorders stages, so stage order doesn't matter." It reorders only where it can prove the rewrite is safe, which is a much smaller set than people assume — anything after a stage that creates the field being filtered on is stuck where you put it. Writing pipelines assuming the optimiser will fix them is how you get an $unwind over forty million subdocuments.

midExplain $group and its memory limits.

Answer

$group partitions the input by the _id expression and applies accumulators — $sum, $avg, $min/$max, $first/$last, $push, $addToSet, and since 5.2 the bounded $topN/$bottomN/$firstN/$lastN. It is blocking: it must see all input before emitting, so it holds one entry per distinct group in memory. The limit is 100 MB per blocking stage; since 6.0 stages spill to disk by default rather than failing (allowDiskUse is true by default for aggregate), which converts a crash into a slowdown — and MongoDB 8.2 added $queryStats metrics for exactly that disk spilling so you can see it in production. The two things that blow it up are a high-cardinality _id (grouping by a unique field) and unbounded $push, which can also breach the 16 MB output-document limit.

Example

// Bounded: keeps at most 5 per group, no 16 MB risk.
{ $group: { _id: "$customerId",
            spend: { $sum: "$total" },
            recent: { $topN: { n: 5, sortBy: { placedAt: -1 }, output: "$_id" } } } }

// $count is sugar for this, and $sortByCount for a group-then-sort-desc:
{ $sortByCount: "$region" }   // == $group by region + $sum:1 + $sort desc

Follow-ups

  • Can $group use an index? — Only via the DISTINCT_SCAN optimisation for simple cases (e.g. $group on an indexed field with $first and a matching sort); otherwise it consumes whatever the preceding stages produce.
  • Why is $sum: 1 cheaper than $push then $size? — It keeps one integer per group instead of materialising every document.
  • How do you get counts by several dimensions in one pass? — $facet, or group by a composite _id object and reshape afterwards; the composite key is usually cheaper.

Common wrong answer

"Set allowDiskUse: true and the memory limit goes away." Since 6.0 that is already the default, and spilling to disk is a performance cliff, not a fix — an aggregation that spills is doing sorted I/O for every group. The correct instinct is to reduce cardinality or bound the accumulators.

midHow does $lookup work, and when is it a bad idea?

Answer

$lookup is a left outer join executed per input document: for each document from the previous stage it runs a query against the foreign collection and pushes the results into an array field. So the cost model is "N foreign queries", and everything depends on whether the foreign field is indexed — unindexed, it is N collection scans and it will melt the cluster. It is fine when N is small (after a selective $match and a $limit) and the foreign key is indexed; it is a bad idea as a routine substitute for modelling, on large N, and on sharded collections, where until 5.1 the foreign collection had to be unsharded at all. The modern form uses let plus a sub-pipeline (3.6+), which lets you filter and project inside the join instead of joining everything and filtering after, and 8.3 improved the local-read fallback for sharded $lookup.

Example

db.customers.aggregate([
  { $match: { region: "EMEA" } },        // reduce N first - this is the whole game
  { $lookup: {
      from: "orders",
      let: { cid: "$_id" },
      pipeline: [
        { $match: { $expr: { $eq: ["$customerId", "$$cid"] },
                    placedAt: { $gte: since } } },   // filter inside the join
        { $project: { total: 1, placedAt: 1 } },
        { $sort: { placedAt: -1 } }, { $limit: 5 } ],
      as: "recentOrders" } }
]);
db.orders.createIndex({ customerId: 1, placedAt: -1 });   // without this, N scans

Follow-ups

  • What is $graphLookup? — A recursive self-join for hierarchies (org charts, category trees) with maxDepth; useful, but it materialises the traversal in memory and is subject to the 100 MB limit.
  • How do you join and then filter on the joined data efficiently? — Inside the sub-pipeline. A $match after the $lookup cannot be pushed into it.
  • What is $unionWith for? — The UNION ALL counterpart (4.4+): concatenating two collections' streams, often used for hybrid search recipes before $scoreFusion existed.

Common wrong answer

"$lookup is a join, so MongoDB does joins now — model it relationally." $lookup is a nested-loop join with no hash or merge strategy, no join reordering, and no cost-based choice between them. Treating it as a general join is the single fastest way to build a MongoDB application that cannot scale.

midWhat does $unwind cost, and what are its options for?

Answer

$unwind emits one output document per array element, so a collection of a million documents with fifty-element arrays becomes a fifty-million-document stream — the multiplication is the cost, and it happens in the pipeline, not on disk. It is streaming rather than blocking, so it does not buffer, but every downstream stage now processes fifty times the documents. The two options exist for correctness: preserveNullAndEmptyArrays: true keeps documents whose array is missing or empty (without it they vanish, which is the classic "my $lookup + $unwind dropped all the customers with no orders" bug), and includeArrayIndex emits the element's position. The senior instinct is to avoid unwinding at all where $filter, $map, $reduce or $size can compute the answer in place — and 8.3 added arrayIndexAs/$$IDX to those operators, which removes one more reason to unwind.

Example

// Unwind-free: compute the order total without exploding the stream.
{ $addFields: { total: { $sum: { $map: { input: "$lines", as: "l",
    in: { $multiply: ["$$l.unitPrice", "$$l.qty"] } } } } } }

// When you must unwind, keep the empty ones:
{ $unwind: { path: "$lines", preserveNullAndEmptyArrays: true, includeArrayIndex: "i" } }

Follow-ups

  • How do you filter array elements without unwinding? — $filter in a $project/$addFields, or $elemMatch in the projection for a single element.
  • When is unwind-then-regroup legitimate? — When you genuinely need per-element grouping across documents; then $match hard before the $unwind so the multiplication applies to a small set.
  • What is the sharded-cluster consequence? — The multiplied stream may have to cross the network to the merging node; project down to the needed fields before unwinding.

Common wrong answer

"$unwind is cheap because it's streaming." Streaming means it does not buffer; it says nothing about volume. And forgetting preserveNullAndEmptyArrays is a correctness bug that silently deletes rows from a report — the kind of thing an interviewer will hand you as a broken pipeline to debug.

seniorHow do you produce a faceted result — filters with counts — in one query?

Answer

$facet runs several sub-pipelines over the same input stream and returns their results as fields of one document — the results page, the count, and the counts per category all in one round trip. The important caveat is that each sub-pipeline processes the full input independently, so $facet saves round trips, not work, and no sub-pipeline can use an index beyond what the shared prefix already did. $bucket and $bucketAuto give you histogram-style grouping into ranges, and $sortByCount is the shorthand for the common "top values by frequency". For a real faceted search UI on a large collection, the right answer at senior level is usually not $facet at all: it is MongoDB Search facets, which are computed from the Lucene index rather than by re-scanning the collection per facet.

Example

db.products.aggregate([
  { $match: { category: "audio", inStock: true } },       // shared, indexed prefix
  { $facet: {
      page:      [ { $sort: { rating: -1 } }, { $limit: 20 } ],
      byBrand:   [ { $sortByCount: "$brand" }, { $limit: 10 } ],
      byPrice:   [ { $bucket: { groupBy: "$price", boundaries: [0,50,100,250,1000],
                                default: "1000+", output: { n: { $sum: 1 } } } } ],
      total:     [ { $count: "n" } ] } }
]);

Follow-ups

  • Why can't sub-pipelines use their own indexes? — They consume the stream produced by the stages before $facet; only that shared prefix touches the collection.
  • What is $bucketAuto for? — Equal-population buckets when you do not know the distribution; useful for exploratory histograms, unstable for a UI because boundaries move.
  • When do you precompute facets instead? — When the filter set is stable and the collection is large: a rollup collection refreshed with $merge answers in one index seek.

Common wrong answer

"$facet is efficient because it does everything in one pass." It is one request, not one pass: the input is duplicated to every sub-pipeline. Candidates who believe otherwise put $facet over a million-document match and are surprised by the latency.

seniorWhat are $merge and $out, and how do you use them safely?

Answer

Both write pipeline output to a collection. $out replaces the target collection wholesale — atomic from the reader's point of view but all-or-nothing and non-incremental, and it must be the last stage. $merge (4.2+) upserts into an existing collection with configurable whenMatched (replace, merge, keepExisting, fail, or a custom pipeline) and whenNotMatched, can target another database, and can write to a sharded collection — which makes it the tool for incremental materialised views. Safety comes from three habits: make the job idempotent so a retry converges (deterministic _id, whenMatched: "replace"), bound the input with a watermark $match so you re-derive only the recent window, and run it with a schedule and a lag metric so a stalled job is visible. Materialised views in MongoDB are a pattern, not a feature: you own the refresh.

Example

db.orders.aggregate([
  { $match: { placedAt: { $gte: watermark } } },
  { $group: { _id: { $dateTrunc: { date: "$placedAt", unit: "hour" } },
              revenue: { $sum: "$total" } } },
  { $merge: { into: { db: "reporting", coll: "hourly_revenue" },
              on: "_id", whenMatched: "replace", whenNotMatched: "insert" } }
], { comment: "hourly-revenue-rollup" });   // comment shows up in currentOp + slow log

Follow-ups

  • What does on require? — A unique index on those fields in the target collection; without it $merge refuses to run, which is the safety rail against duplicate rollup rows.
  • What happens if the job runs twice concurrently? — Both write; with replace semantics and deterministic keys the result converges, which is why idempotence is the design requirement.
  • Where does the work run on a sharded cluster? — The merging shard performs the writes; a large $merge concentrates write load, so schedule it off-peak.

Common wrong answer

"Use $out to refresh the report table." $out re-derives the entire history on every run, so the job gets slower forever, and it cannot write to a sharded collection. Reaching for $out in 2026 signals a mental model formed before 4.2.

seniorHow do you compute a running total or a rank per group?

Answer

$setWindowFields (5.0+) — MongoDB's window functions. You give it partitionBy, a sortBy, and an output map of fields to accumulators with a window specification, either documents (positional, e.g. ["unbounded", "current"] for a running total, [-3, 0] for a 4-point moving average) or range (value-based, including time units, which is what you want for "the last 7 days" regardless of gaps). It also provides $rank, $denseRank, $documentNumber, $shift, $derivative and $integral. Before 5.0 the only way to do this was $group into an array and $reduce over it — that pattern is all over older codebases, and recognising it as legacy is worth saying. The stage is blocking per partition, so partition cardinality and partition size are the performance levers.

Example

db.sales.aggregate([
  { $setWindowFields: {
      partitionBy: "$region",
      sortBy: { day: 1 },
      output: {
        runningTotal: { $sum: "$amount", window: { documents: ["unbounded", "current"] } },
        movingAvg7d:  { $avg: "$amount", window: { range: [-7, 0], unit: "day" } },
        rankInRegion: { $denseRank: {} },
        prevDay:      { $shift: { output: "$amount", by: -1, default: 0 } } } } }
]);

Follow-ups

  • documents or range windows? — documents counts rows and is wrong when data has gaps; range with a time unit is the honest "last 7 days".
  • What is $densify for? — Filling the missing points in a time series (5.1+) so a windowed average is not distorted by gaps; it pairs with $fill for the values.
  • How is the cost shaped? — Each partition is buffered and sorted; a partition key with few, huge partitions is the failure case, so check the partition size distribution first.

Common wrong answer

"MongoDB doesn't have window functions — pull the data out and do it in the application." It has had them since July 2021. Saying otherwise dates your knowledge by five years, and the application-side version transfers the whole partition over the network to compute a number the server could have produced.

midHow do you debug a pipeline that returns the wrong shape?

Answer

Bisect it: run the pipeline with a $limit near the front and then truncate after each stage in turn, inspecting the intermediate documents — the wrong shape almost always appears at one specific stage boundary. The usual culprits are the projection rules ($project is exclusive-or-inclusive and mixing them errors, except for _id; $addFields/$set add without removing; $unset removes), the difference between a field path "$x" and a variable "$$x", $$ROOT versus the current document inside $map, and null propagation — most expressions return null rather than erroring on a missing field, so a typo produces silence, not an error. I also add a comment to every production pipeline so it is identifiable in currentOp and the slow-query log.

Example

// Bisect with a bounded head so iteration is fast.
const head = [ { $match: { _id: sampleId } } ];
db.orders.aggregate([ ...head, stage1 ]);
db.orders.aggregate([ ...head, stage1, stage2 ]);

// The silent-null trap: a typo yields null, not an error.
{ $addFields: { t: { $multiply: ["$unitPrice", "$quantitiy"] } } }   // -> t: null

// 8.3: dump a document as Extended JSON inside the pipeline for eyeballing.
{ $addFields: { _debug: { $serializeEJSON: { object: "$$ROOT" } } } }

Follow-ups

  • What does $$ROOT mean inside $map? — Still the top-level input document, not the element; the element is the as variable.
  • How do you catch missing fields early? — $ifNull with a sentinel, or a $match: { field: { $exists: false } } probe on a sample before trusting the pipeline.
  • How do you keep complex pipelines maintainable? — Build them as composed arrays in application code with named fragments and unit tests over fixture documents, not as one 300-line literal.

Common wrong answer

"Add console.log-style stages everywhere and read the output." Not wrong so much as unsystematic; the answer an interviewer wants is bisection plus knowledge of which semantics silently produce nulls, because that is what makes the bug invisible in the first place.

principalWhen should aggregation work leave MongoDB entirely?

Answer

When the workload stops looking like "answer a bounded question about a known access pattern" and starts looking like "scan history in arbitrary ways". Three concrete triggers: the query touches a large fraction of the collection, so it evicts the operational working set from cache and the damage is to other queries, not the report; the questions are ad hoc and change weekly, so no index or rollup can be designed for them; or the analysis needs to join across systems MongoDB does not own. The staged answer is: first push what belongs in the operational store into materialised rollups ($merge) and isolate the rest on analytics nodes with a workload-tagged read preference; then, when that stops being enough, land the data in a columnar store — via Atlas Stream Processing or a change-stream/CDC pipeline into a lakehouse, or Atlas Data Federation and Online Archive for cold data. What I would not do is run the ad hoc analytics on the primary and call the resulting cache thrash "a MongoDB performance problem".

Example

// The operational store keeps a bounded, indexed rollup; the lake keeps history.
{ $merge: { into: "daily_metrics", on: "_id", whenMatched: "replace" } }

// Analytics traffic is routed away from the operational members, explicitly.
readPreference: { mode: "secondary", tags: [ { workload: "analytics" } ] }

Follow-ups

  • How do you decide the cutover point objectively? — Instrument it: cache eviction rate and p99 of the operational queries during the analytics window. If the report costs the transactional path measurable latency, it has outgrown its home.
  • What breaks when you move to CDC? — Ordering and exactly-once expectations; change streams give you ordered, resumable at-least-once delivery, and the sink must be idempotent.
  • Is Atlas Data Federation an answer or a stopgap? — Genuinely useful for querying archived and object-storage data with the same API, but it is not a warehouse; do not size a BI department around it.

Common wrong answer

"Run it on a secondary, that's what secondaries are for." Secondaries exist for availability first; using one for analytics still applies the full oplog on that node and still destroys its cache locality, and if the secondary falls behind you have degraded your failover story to buy a dashboard. Say the trade-off out loud, or the interviewer will.

05Replication and replica sets

Every MongoDB deployment worth the name is a replica set, so this is asked in almost every loop — usually as "what happens when the primary dies?" and then relentlessly deeper. Screeners want the topology and the oplog; mid-level wants elections and read preference; senior is where rollback, lag and multi-region topology live, and where interviewers find out whether you have actually run this or only drawn it. Be ready for the incident-command framing: "the primary is gone, the application is erroring, what do you check in what order?"

Docs: MongoDB Manual — Replication

screenerWhat is a replica set, and what happens when the primary fails?

Answer

A group of mongod processes holding the same data: exactly one primary, which takes all writes, and secondaries that replicate the primary's oplog asynchronously. Members heartbeat every two seconds; if a secondary has not heard from the primary within electionTimeoutMillis (10 seconds by default) it calls an election, and a member that can reach a majority of voting members and has the freshest data wins. Typical failover completes in under 12 seconds. Two consequences you should volunteer: the old primary steps down and, on rejoining, may have to roll back writes that never reached a majority; and modern drivers handle this transparently — server discovery and monitoring plus retryable writes and reads mean a single failover is usually a latency blip, not an outage, provided the application uses a connection string listing the whole set rather than one host.

Example

// Connection string lists the set, not a single node: the driver does discovery.
mongodb://a.db:27017,b.db:27017,c.db:27017/app?replicaSet=rs0&w=majority&retryWrites=true

rs.status();        // members, states, heartbeats, election metrics
rs.conf();          // priorities, votes, tags, settings
rs.printSecondaryReplicationInfo();   // lag per secondary

Follow-ups

  • Why an odd number of members? — Majority is floor(N/2)+1; a 4-member set needs 3 to elect, the same as a 5-member set, so the fourth adds cost without improving fault tolerance.
  • Can a secondary serve writes? — Never. Only the primary accepts writes; that is what makes MongoDB a single-writer, strongly-ordered-per-document system.
  • What is the minimum sensible production set? — Three data-bearing members across three failure domains. Two data-bearing plus an arbiter is a cost-saving that costs you majority writes when one member is down.

Common wrong answer

"The application reconnects to the new primary, so failover is invisible." Only if the connection string names the set, the driver is modern, and the writes are retryable — and even then, in-flight writes with w: "majority" may be uncertain. Candidates who say "invisible" have not handled the "did my write land?" question, which is the follow-up.

screenerWhat is the oplog and why does its size matter?

Answer

The oplog is a capped collection in the local database (local.oplog.rs) holding an idempotent record of every operation the primary applied; secondaries tail it and apply the same entries. Idempotence is the key property — the entries are rewritten so that replaying them repeatedly converges (an $inc becomes a $set to the resulting value), which is what makes recovery and resumption safe. The size matters because it defines your replication window: how far behind a secondary can fall, or how long a member can be offline, before the entries it needs have been overwritten and it must do a full initial sync instead of catching up. The default is 5% of free disk (min 990 MB, max 50 GB); the real sizing rule is "cover your worst realistic maintenance window", often 24–72 hours. Since 4.4 you can change it online with replSetResizeOplog, and set a minimum retention period in hours rather than bytes.

Example

db.getReplicationInfo();      // { logSizeMB, usedMB, timeDiffHours, tFirst, tLast }
db.adminCommand({ replSetResizeOplog: 1, size: 51200, minRetentionHours: 72 });

Follow-ups

  • What consumes oplog window fastest? — Bulk updates that touch many documents, large index builds, and updateMany on huge collections; a single migration can burn a 48-hour window in twenty minutes.
  • Is the oplog per collection? — No, one per replica set member, covering all databases; that is why one noisy collection can starve everything else's window.
  • What else reads the oplog? — Change streams (indirectly, via the change-stream layer), backup tools for point-in-time restore, and mongosync/cluster-to-cluster sync.

Common wrong answer

"The oplog is a transaction log for durability, like a WAL." It is not: durability comes from WiredTiger's own journal. The oplog is a replication log, and confusing the two leads to wrong answers about what survives a crash versus what survives a failover.

midWalk me through an election. What decides who wins?

Answer

MongoDB uses a Raft-like protocol (protocol version 1 since 3.2). When a secondary's heartbeat to the primary times out it increments the term and requests votes. To win, a candidate needs votes from a strict majority of voting members, and a member only votes for a candidate whose oplog is at least as fresh as its own — that is what prevents electing a node that would lose committed writes. priority biases the outcome: a higher-priority member that is eligible will call an election to take over even when a healthy lower-priority primary exists, and priority: 0 makes a member permanently ineligible (used for analytics, backup and remote-DR nodes). A member can be non-voting (votes: 0) but at most seven members vote. If no majority is reachable — a network partition leaving the minority side alone — that side has no primary and takes no writes, which is MongoDB choosing consistency over availability in CAP terms.

Example

cfg = rs.conf();
cfg.members[0].priority = 2;             // preferred primary (primary datacentre)
cfg.members[2].priority = 0;             // analytics node: never becomes primary
cfg.members[2].votes = 0;                // and does not vote
cfg.members[2].tags = { workload: "analytics" };
cfg.settings.electionTimeoutMillis = 10000;
rs.reconfig(cfg);

Follow-ups

  • What does lowering electionTimeoutMillis buy and cost? — Faster failover, but more spurious elections on a flaky network; each election is a brief write outage, so tuning it down on a noisy link makes things worse.
  • What is a hidden member? — priority: 0 plus hidden: true: invisible to clients' server selection, so it can carry a different index set or take backups without serving traffic.
  • What is catchup takeover? — When a higher-priority member is behind, it waits to catch up before forcing an election, so priority does not cost you data freshness.

Common wrong answer

"The member with the highest priority always becomes primary." Priority is a preference among eligible members; freshness and reachability of a majority come first. A high-priority node that is behind or partitioned wins nothing.

midWhat is an arbiter, and why is the advice to avoid them?

Answer

An arbiter is a voting member with no data — it exists only to break ties, so a two-data-node deployment can still form a majority. The reason to avoid it is that it makes your durability worse in exactly the situation you bought it for. In a P-S-A set (primary, secondary, arbiter), if the secondary is down you still have a primary — but there is now no second data-bearing member, so w: "majority" writes cannot be acknowledged and either block or fail, and the majority commit point stops advancing, which in turn pins WiredTiger's cache with un-committable history until the node runs out of cache. It also weakens rollback protection, since a write can be acknowledged by a majority that includes a node holding no data. The modern advice is three data-bearing members; if cost is the driver, make the third a low-spec priority: 0 member rather than an arbiter.

Example

// P-S-A with the secondary down: majority = 2 of 3, but only one node has data.
// w:"majority" writes cannot commit -> the app stalls, and cache pressure climbs.
db.serverStatus().wiredTiger.cache["tracked dirty bytes in the cache"];
// 5.0+ mitigates but does not remove this: see the P-S-A guidance in the manual.

Follow-ups

  • When is an arbiter still defensible? — Small, cost-constrained deployments where losing majority-write capability during a single-node outage is genuinely acceptable, and never for a sharded cluster's shards.
  • Can an arbiter be a tiebreaker across data centres? — It can, and it is a classic mistake: the arbiter's location decides which side of a partition keeps a primary, so put it in a third failure domain or not at all.
  • What replaced this pattern in Atlas? — Three-node replica sets by default, with the cheapest tiers still data-bearing; Atlas does not offer arbiters, which is itself the vendor's answer to the question.

Common wrong answer

"An arbiter gives you the same availability as a third node for free." It gives you the same election availability and strictly worse durability and write availability. The interviewer is checking whether you can distinguish "can elect a primary" from "can commit a majority write".

midExplain read preference. When would you read from a secondary?

Answer

Read preference tells the driver which members are eligible for a read: primary (default), primaryPreferred, secondary, secondaryPreferred, nearest, optionally narrowed by tag sets and bounded by maxStalenessSeconds (90 s minimum, 3.4+). The honest senior answer is that reading from secondaries is a latency and workload isolation tool, not a scaling one: secondaries apply the same write load as the primary, so you gain read capacity but no write capacity, and you trade away read-your-own-writes. Legitimate uses are geographically local reads with nearest, isolating reporting on tagged analytics members, and surviving a brief primary outage for read-only paths with primaryPreferred. Illegitimate use is "the primary is overloaded, point reads at secondaries" — that usually means the working set does not fit in RAM, and it will not fit on the secondary either.

Example

db.getMongo().setReadPref("secondary", [ { workload: "analytics" } ]);

// Bound the staleness you will tolerate; without it, "secondary" means any secondary.
readPreference: { mode: "secondaryPreferred", maxStalenessSeconds: 120 }

// Read-your-own-writes across members without pinning to the primary:
session.startSession();  // causal consistency: afterClusterTime is carried for you

Follow-ups

  • How do you keep read-your-own-writes when reading from a secondary? — A causally consistent session: the driver carries the operation time and the secondary waits until it has applied at least that point.
  • Does maxStalenessSeconds guarantee freshness? — It excludes members estimated to be staler than the bound; it is a filter on member selection, not a synchronisation primitive.
  • What happens to reads during an election? — With primary, they block until server selection succeeds or the timeout expires; drivers retry reads once by default since 4.2.

Common wrong answer

"Read from secondaries to scale reads." It is the single most common half-truth in MongoDB interviews. You add read throughput only if the secondaries have spare capacity after applying all the writes, and you pay in consistency; the real horizontal-scale answer is sharding.

seniorWhat is a rollback, and how do you avoid losing writes?

Answer

If a primary accepts writes that have not yet replicated to a majority and then goes down, a new primary is elected without them. When the old primary rejoins it must discard those divergent operations to match the new primary's history — that is a rollback. Since 4.0 it is done by "recover to a timestamp" using WiredTiger's stable checkpoints rather than by writing rollback BSON files, so it is fast, and by default a rollback exceeding 300 MB of oplog aborts and requires a resync. The way you avoid losing writes is to define what "written" means: use w: "majority", which does not acknowledge until a majority of data-bearing members have the write, and then a rollback cannot silently discard an acknowledged write. Since MongoDB 5.0 w: "majority" is the default write concern; a great deal of existing code and older tutorials assume w: 1, which is exactly the configuration that loses data on failover.

Example

// Acknowledged only once a majority has it - survives failover.
db.orders.insertOne(doc, { writeConcern: { w: "majority", wtimeout: 5000 } });

// Legacy default you will still meet in older code and drivers:
db.orders.insertOne(doc, { writeConcern: { w: 1 } });   // primary-only ack: rollback-able

Follow-ups

  • What does wtimeout actually do on timeout? — It returns an error but does not undo the write; the write may still commit later. Handling that ambiguity — usually with an idempotent retry — is the senior point.
  • What is the majority commit point? — The oplog timestamp a majority has applied; readConcern: "majority" reads at or before it, which is why it never sees data that could be rolled back.
  • Where do rollback files go if they are written? — rollback/ under the dbpath, as BSON; they are a forensic artefact, not a recovery mechanism, and nobody has a tested process for replaying them.

Common wrong answer

"MongoDB acknowledged the write, so it's durable." Acknowledged by whom is the whole question. With w: 1 the write is durable against a process crash (with journalling) but not against a failover. Candidates who cannot separate journal durability from replication durability get found out immediately here.

seniorA secondary is lagging by 40 minutes. How do you diagnose it?

Answer

I separate "cannot keep up" from "is being blocked". First the measurement: rs.printSecondaryReplicationInfo() and the repl section of serverStatus for apply-batch timings, plus the metrics for the oplog application queue. Then the causes in order of likelihood: the secondary is smaller than the primary or on slower disks, so it cannot apply the write rate; a long-running index build or a huge updateMany is generating oplog faster than any node can apply; long-running reads on the secondary are holding snapshots and blocking oplog application (batch application takes a lock); the disk is saturated (check I/O wait, not CPU); or the write pattern is pathological — an unindexed updateMany on the primary becomes an equally unindexed batch of operations on each secondary. The consequences to name are that lag past the oplog window forces a full initial sync, and that lag stalls the majority commit point, which pins cache on the primary and can cascade.

Example

rs.printSecondaryReplicationInfo();
db.serverStatus().metrics.repl.apply;      // batches, ops, timing
db.serverStatus().metrics.repl.buffer;     // is the apply queue backing up?
db.currentOp({ secs_running: { $gt: 60 }, op: { $ne: "none" } });   // blockers

Follow-ups

  • Why do long reads on the secondary cause lag? — Oplog batches are applied under a lock that conflicts with in-progress reads holding old snapshots; a 20-minute analytics scan can stall application for its duration.
  • Does lag affect the primary? — Yes: the majority commit point cannot advance, so WiredTiger must keep older versions in cache, and dirty-cache pressure rises until eviction stalls writes.
  • How do you fix it structurally? — Symmetric hardware across members, batch jobs that throttle on observed lag, and never running maintenance that is faster on the primary than any secondary can apply.

Common wrong answer

"Restart the secondary" or "just resync it." Resyncing is the sledgehammer that removes the evidence, takes hours on a large data set, and leaves the cause in place — usually a job that will do it again tomorrow. Diagnose the source of oplog volume first.

seniorHow do you add a member to a large replica set without hurting production?

Answer

A new member performs an initial sync: it clones every collection from a sync source, builds all indexes, and then applies the oplog accumulated during the clone. The cost lands on the sync source, so the first control is to choose it deliberately — initialSyncSourceReadPreference, or point it at a hidden member so no production traffic is affected. The second control is timing: an initial sync on a multi-terabyte set can take many hours and needs an oplog window longer than the sync, or it restarts. Since 4.4, initial sync resumes after a transient network failure rather than starting over, and 8.2 added finer control over index builds during initial sync. The alternative for very large data sets is to seed from a filesystem or Atlas snapshot and let the member catch up from the oplog — far faster, but it requires the snapshot to be within the oplog window.

Example

rs.add({ host: "d.db:27017", priority: 0, votes: 0 });    // join quietly first
db.adminCommand({ setParameter: 1, initialSyncSourceReadPreference: "secondary" });

// Watch progress; then promote once caught up.
db.serverStatus().initialSyncStatus;
rs.reconfig(cfgWithPriority1);

Follow-ups

  • Why add the member as non-voting first? — Adding a voting member changes the majority immediately; if it cannot sync you have raised the bar for elections while it is useless.
  • What if the initial sync exceeds the oplog window? — It fails and restarts. Raise minRetentionHours before you start, not after.
  • Snapshot seeding caveats? — The snapshot must be consistent (filesystem snapshot of a journalled dbpath, or a proper backup tool) and must be newer than the oldest oplog entry.

Common wrong answer

"Just rs.add() it, MongoDB handles the rest." Mechanically true, operationally naive: you have just pointed a full-collection clone at whichever member the new node picked, changed the voting majority, and started a race against your oplog window. The interviewer is looking for the three controls, not the command.

principalDesign a replica set across three regions. What are you optimising for?

Answer

I start by asking what failure I must survive and what latency the writes can tolerate, because those two conflict directly. A replica set spanning three regions survives a whole-region loss without data loss, because a majority still exists — but every w: "majority" write now costs a cross-region round trip, so if the regions are 80 ms apart your write latency floor is roughly that. If the application cannot pay it, the honest answer is that you do not get zero-RPO region failover for those writes; you either accept regional writes with asynchronous DR (a priority: 0 member in region C, RPO measured in seconds), or you shard by geography with zone sharding so each region owns its own data and writes stay local. I place the majority of voting members where the writes are, use nearest for reads with an explicit staleness bound, and I write down the RPO and RTO numbers the topology actually delivers rather than letting people assume zero.

Example

// Zone sharding: EU data lives on EU shards; writes never cross the Atlantic.
sh.addShardTag("shard-eu-1", "EU");
sh.addShardTag("shard-us-1", "US");
sh.addTagRange("app.users", { region: "EU", userId: MinKey },
                             { region: "EU", userId: MaxKey }, "EU");
// Shard key must lead with the geography field for this to target.

Follow-ups

  • What does data residency add? — A legal constraint that turns zone sharding from an optimisation into a requirement, and forbids the "DR copy in another region" answer for regulated data.
  • How do you handle a two-region requirement? — You cannot get automatic failover with a majority in two regions; either accept manual promotion (and its split-brain risk) or place a lightweight voting member in a third location.
  • What is Atlas Global Clusters? — The managed form of zone sharding with location-aware routing; worth naming as the "buy" option, along with the fact that it constrains your shard key choice permanently.

Common wrong answer

"Put a replica in every region so reads are fast and we survive anything." It ignores the write-side cost entirely. A principal-level answer states the majority-write latency the topology implies, and either accepts it explicitly or changes the topology — usually to zone sharding — rather than pretending the trade-off is not there.

06Sharding and horizontal scale

The area that most reliably separates people who have run MongoDB at scale from people who have read about it. Screeners want the components and the definition; mid-level wants shard key properties and chunk mechanics; senior and principal get the questions that decide the hire — "you picked the wrong shard key, now what?", "when would you refuse to shard?", and the multi-tenant key design that has to work for a 50-document tenant and a 500-million-document tenant in the same collection. Since MongoDB 8.0 the honest framing has shifted: sharding got dramatically better (faster data movement, embedded config servers, viable online resharding), so "sharding is a last resort you can never undo" is now overstated — but "the shard key is the most consequential decision in the system" still holds.

Docs: MongoDB Manual — Sharding

screenerWhat is sharding, and what are the pieces of a sharded cluster?

Answer

Horizontal partitioning of a collection across multiple replica sets, so that data and write throughput exceed what one machine can hold. Three components: the shards, each a full replica set owning a subset of the data; the config servers, themselves a replica set (CSRS, since 3.4) holding the cluster metadata — which ranges of shard-key values live on which shard; and mongos, the stateless router the application connects to, which caches the routing table and either targets one shard or fans out. Collections are sharded individually — an unsharded collection lives entirely on its database's primary shard, so a cluster is normally a mix. MongoDB 8.0 added embedded config servers, letting the first shard double as the config server for small clusters, which removes three machines from the minimum topology.

Example

sh.enableSharding("app");
sh.shardCollection("app.events", { tenantId: 1, ts: 1 });   // ranged
sh.status();                       // shards, chunk distribution, balancer state
db.adminCommand({ getShardMap: 1 });

Follow-ups

  • Do applications connect to shards directly? — Never in normal operation; they connect to mongos. Talking to a shard directly bypasses routing and shows you an incomplete, possibly orphaned view of the data.
  • What are orphaned documents? — Documents left on a shard after a range migration; reads through mongos filter them out, direct reads do not. 8.2 improved orphan cleanup and added sharding inconsistency detection.
  • How many mongos do you run? — Usually one per application host or a small pool behind a load balancer; they are stateless and cheap, and co-locating them removes a network hop.

Common wrong answer

"Sharding is how you scale reads." Sharding scales writes, working-set size and storage; reads scale with it only when they are targeted by the shard key. A scatter-gather read on a 20-shard cluster is slower than the same read on one machine, because you pay the slowest shard's latency plus a merge.

midHow do you choose a shard key?

Answer

Four properties, in this order. Cardinality: the key must have enough distinct values to produce more ranges than you have shards — country gives you at most a couple of hundred, and one of them will be 60% of the data. Frequency: the values must be evenly distributed, or the hot value becomes a hot shard. Monotonicity: a steadily increasing key (a timestamp, a default ObjectId) sends every insert to the shard owning the top range, so you get one write hotspot no matter how many shards you have. And, decisively, query alignment: the key must appear in your common queries, or every read is a scatter-gather. The practical shape that satisfies all four is usually a compound key leading with a high-cardinality entity that your queries always carry — { tenantId: 1, ts: 1 }, { userId: 1, _id: 1 } — or a hashed key when there is no such field and you only ever query by exact value.

Example

// Bad: monotonic. Every insert lands on the shard owning MaxKey.
sh.shardCollection("app.events", { createdAt: 1 });

// Bad: low cardinality. Two hundred ranges maximum, wildly uneven.
sh.shardCollection("app.users", { country: 1 });

// Good: high-cardinality prefix that every query carries, plus a tiebreaker.
sh.shardCollection("app.events", { tenantId: 1, createdAt: 1 });

// Good when queries are always exact-match on one field:
sh.shardCollection("app.sessions", { sessionId: "hashed" });

Follow-ups

  • Why is a compound key better than a hashed one so often? — Hashing destroys range locality, so any range query becomes a scatter-gather and zone sharding becomes impossible.
  • Does the shard key have to be unique? — No, but it must be present and immutable-ish; a document's shard key value could not be changed at all before 4.2, and can now be changed only inside a transaction or a retryable write.
  • What if no field satisfies all four? — Manufacture one: a synthetic key combining a coarse bucket with a hash, or reconsider whether the collection should be sharded at all.

Common wrong answer

"Use a hashed _id — it distributes perfectly." It distributes perfectly and targets nothing: every query that is not an exact _id lookup fans out to every shard, and you can never do zone sharding or an efficient range scan. Perfect distribution is the easiest property to get and the least valuable on its own.

midWhat are chunks, and what does the balancer do?

Answer

The shard-key space is divided into contiguous ranges (historically "chunks"), each owned by one shard; the config servers record the mapping. The balancer, which runs on the config server primary since 3.4, migrates ranges between shards to keep them even. The important modern change is what it balances: before 6.0 it balanced the number of chunks per shard, which could leave wildly uneven data; from 6.0 it balances actual data size, and chunk splitting became automatic based on data size rather than a fixed 64 MB chunk. MongoDB 8.0 made the migration path far faster, which is what turned resharding from a multi-day ordeal into an hours-long operation. The failure mode to know is the jumbo range: a range that cannot be split because every document in it has the same shard-key value, so it can never be migrated and grows unbounded — the direct consequence of a low-cardinality key.

Example

sh.getBalancerState(); sh.isBalancerRunning();
sh.startBalancer(); sh.stopBalancer();                       // e.g. during a bulk load
sh.setBalancerState(true);

// Restrict balancing to a window so migrations never collide with peak traffic.
db.settings.updateOne({ _id: "balancer" },
  { $set: { activeWindow: { start: "01:00", stop: "05:00" } } }, { upsert: true });

Follow-ups

  • What happens to reads during a migration? — They keep working; the source shard serves until the range is committed, then the router's cached routing table is invalidated and refreshed on the next request.
  • Why would you stop the balancer? — During a large bulk load or a backup, so migrations do not compete for I/O; remember to start it again, because a forgotten disabled balancer is a classic slow-burning incident.
  • How do you fix a jumbo range? — You cannot split it; you fix the shard key. refineCollectionShardKey (4.4+) to add a suffix field that gives it cardinality is the least disruptive route.

Common wrong answer

"Chunks are 64 MB and the balancer keeps chunk counts equal." That was true and is now two majors out of date — it is data-size-based since 6.0. It is a precise tell that someone learned sharding from older material.

midWhat is the difference between a targeted and a scatter-gather query?

Answer

If the query carries the shard key (or a prefix of it), mongos consults the routing table and sends the query to the one shard — or the few shards — that can hold matches: a targeted query, whose latency is that of a single replica set. Without the shard key it must broadcast to every shard and merge the results: a scatter-gather, whose latency is the slowest shard's, whose cost grows with cluster size, and which consumes a connection and a cursor on every shard. That asymmetry is why the fourth shard-key property — query alignment — matters more than distribution. Sorted scatter-gather is worse still, because each shard must produce sorted output and the router merges; and skip-based pagination is worst, since each shard must return skip + limit documents. You can see which you got in explain: SINGLE_SHARD versus SHARD_MERGE.

Example

// Shard key: { tenantId: 1, createdAt: 1 }
db.events.find({ tenantId: 42, createdAt: { $gte: t } });  // SINGLE_SHARD - targeted
db.events.find({ level: "error" });                         // SHARD_MERGE - all shards
db.events.find({ createdAt: { $gte: t } });                 // suffix only: still broadcast

db.events.find(q).explain().queryPlanner.winningPlan.stage;  // SINGLE_SHARD | SHARD_MERGE

Follow-ups

  • Can a secondary index make a scatter-gather fast? — It makes each shard's part fast; the broadcast, the merge and the tail latency remain, so it improves a bad plan rather than making it targeted.
  • Are all writes targeted? — Inserts must be (the shard key is required); updateOne/deleteOne require the shard key or must be broadcast, and updateMany broadcasts by design.
  • What is the mitigation when a scatter-gather is unavoidable? — A second, differently sharded collection maintained as a projection of the first, so both access patterns have a targeted home.

Common wrong answer

"With enough shards even a broadcast query is fast because each shard has less data." The per-shard work shrinks, but the fan-out, the merge and — decisively — the tail latency across N shards grow. At 40 shards a p99 broadcast is dominated by whichever shard is having a bad second.

seniorYou picked the wrong shard key. What are your options?

Answer

Three, in increasing cost. Refine it: refineCollectionShardKey (4.4+) appends fields to the existing key, which is cheap and metadata-only — it does not move data, but it gives an over-coarse key the cardinality to split jumbo ranges, and it is often the whole fix. Reshard it: reshardCollection (5.0+) rewrites the collection under a completely new key online; the collection stays writable for almost all of the process with a brief write block at cutover, and on 8.0+ this is hours rather than days for large collections — but it needs disk headroom for a second copy and it costs real throughput while running. Or rebuild: write to a new correctly sharded collection via dual writes or a change-stream projector, then cut reads over — the option you choose when the shape must also change, not just the key. The senior part is the rehearsal: restore a copy, measure the actual duration and disk delta, then schedule.

Example

// Cheap: add cardinality to an existing key (index must exist first).
db.events.createIndex({ tenantId: 1, createdAt: 1, _id: 1 });
db.adminCommand({ refineCollectionShardKey: "app.events",
                  key: { tenantId: 1, createdAt: 1, _id: 1 } });

// Expensive but online:
db.adminCommand({ reshardCollection: "app.events", key: { tenantId: "hashed" } });
db.adminCommand({ currentOp: 1, "type": "op", "desc": /ReshardingCoordinator/ });

Follow-ups

  • What does resharding actually do? — Builds a new copy under the new key while tailing the oplog for changes, then does a short write block to catch up and swap; abortReshardCollection cancels it cleanly.
  • Can you unshard? — Yes, since 8.0: unshardCollection moves a sharded collection back onto a single shard, and moveCollection relocates an unsharded one. Both are new enough that many candidates do not know they exist.
  • What is the disk requirement? — Room for a second full copy plus indexes on the target shards; running out mid-reshard is the failure people actually hit.

Common wrong answer

"You can't change a shard key — you have to dump and restore into a new cluster." True until 4.4, comprehensively false since 5.0, and MongoDB 8.0 made resharding genuinely practical. Saying it dates your knowledge by five years and gives away that you have not worked on a recent version.

seniorHow do you remove a shard, and what changed in 8.3?

Answer

The shard must first be drained: the balancer migrates every range it owns to the remaining shards, and any databases for which it is the primary shard must be moved with movePrimary — the step people forget, which leaves unsharded collections stranded. Historically this was driven by calling removeShard repeatedly and reading the progress out of its response, which was awkward and easy to script badly. MongoDB 8.3 deprecated removeShard in favour of an explicit lifecycle: startShardDraining, shardDrainingStatus (and stopShardDraining to cancel), then commitShardRemoval once draining is complete. The same release added the matching commands for converting an embedded config server to a dedicated one. Practically, draining a large shard takes hours to days and generates heavy migration I/O, so it goes in a balancer window and is monitored, not fired and forgotten.

Example

// 8.3+ (the modern form)
db.adminCommand({ startShardDraining: "shard-03" });
db.adminCommand({ shardDrainingStatus: "shard-03" });   // poll: remaining chunks, dbs
db.adminCommand({ movePrimary: "reporting", to: "shard-01" });
db.adminCommand({ commitShardRemoval: "shard-03" });

// Pre-8.3, still everywhere in runbooks:
db.adminCommand({ removeShard: "shard-03" });           // call repeatedly, read state

Follow-ups

  • What is a primary shard? — The shard holding a database's unsharded collections; it is chosen at database creation and is a common source of imbalance nobody notices.
  • Can you cancel a drain? — Yes, with stopShardDraining (8.3+); before that, cancelling meant re-adding the shard and letting the balancer put data back.
  • What is transitionToDedicatedConfigServer for? — Converting an 8.0 embedded config server back to dedicated config servers as the cluster grows, with the same start/status/commit shape added in 8.3.

Common wrong answer

"Call removeShard and wait." It is deprecated as of 8.3, and even before that it only worked if you also moved the primary databases — otherwise the command stalls forever in "dbsToMove" state and the on-call engineer at 2am has no idea why.

seniorWhen would you refuse to shard?

Answer

When the problem is not the one sharding solves. Sharding solves "more data or more writes than one replica set can hold"; it does not solve slow queries, missing indexes, a working set that does not fit in RAM on nodes you have not tried scaling vertically, or an aggregation that scans the world. Adding shards to any of those makes the system more expensive, more complex to operate, and often slower, because you have converted single-node queries into fan-outs. My checklist before agreeing to shard: are the top queries indexed and targeted; has vertical scaling been tried (modern instances go to terabytes of RAM); is there cold data that should be archived or TTL'd; and is the growth curve real or a spike. If those are all answered and the write rate or data size genuinely exceeds one replica set, then shard — early enough to choose the key deliberately rather than under duress, because choosing a shard key while the system is on fire is how you get the wrong one.

Example

// The numbers that justify sharding, gathered before the decision:
db.stats();                                     // dataSize, indexSize vs node RAM
db.serverStatus().opcounters;                   // write rate trend, not peak
db.serverStatus().wiredTiger.cache;             // is the working set resident?
db.aggregate([{ $queryStats: {} }]);            // 7.0+: what actually costs the most

Follow-ups

  • What is the operational cost of a sharded cluster? — Config servers, routers, balancer behaviour, backups that must be consistent across shards, and every incident becoming a distributed-systems incident.
  • Does 8.0 change this calculus? — Somewhat: embedded config servers lower the entry cost and faster migrations lower the correction cost, so sharding earlier is less punishing than it used to be.
  • What is the alternative for "too much cold data"? — Time-partitioned collections you can drop, TTL indexes, or Atlas Online Archive — remove the data instead of distributing it.

Common wrong answer

"We're at 500 GB, it's time to shard." Data size alone is not a trigger; a single replica set on modern hardware handles terabytes comfortably if the working set is resident and the queries are indexed. The interviewer wants to hear the diagnosis, not the threshold.

seniorDesign a shard key for a multi-tenant SaaS with wildly uneven tenants.

Answer

The tension is that tenantId alone gives perfect query targeting and terrible balance: the largest tenant becomes a jumbo range that can never be split, and one shard carries it. So the key leads with tenantId — because every query carries it and cross-tenant isolation is a product requirement — and adds a suffix that provides intra-tenant cardinality: { tenantId: 1, _id: 1 }, or { tenantId: 1, bucket: 1 } where bucket is a small hash of a natural key. That keeps small tenants inside a single range (targeted, cheap) while letting a huge tenant split across many. For the genuinely enormous tenants I would also plan for zone sharding, pinning them to dedicated shards so their load cannot hurt anyone else — which is also the answer to the "noisy neighbour" follow-up that always comes. The alternative architecture worth naming is collection- or database-per-tenant: excellent isolation, but it does not survive tens of thousands of tenants because of per-collection metadata and index overhead.

Example

sh.shardCollection("app.documents", { tenantId: 1, _id: 1 });

// Whales get their own shards; everyone else shares.
sh.addShardToZone("shard-whale-1", "WHALE");
sh.updateZoneKeyRange("app.documents",
  { tenantId: "acme", _id: MinKey }, { tenantId: "acme", _id: MaxKey }, "WHALE");

Follow-ups

  • Why not hash the tenant id? — It balances but destroys the ability to zone-pin a tenant or range-scan within one, and it does not help the whale, whose documents all hash to the same value.
  • How do you enforce tenant isolation? — Every query filtered by tenantId in a repository layer nobody bypasses, plus per-tenant credentials or field-level rules where the compliance story demands it. The shard key is a performance boundary, never a security one.
  • What is the migration path when a tenant becomes a whale? — Add a zone and let the balancer move it; with 8.0's faster migrations this is an afternoon rather than a project.

Common wrong answer

"Shard on tenantId — every query has it, so everything is targeted." Targeted and unbalanced. The moment one tenant is 30% of the data you have a jumbo range that cannot split and a shard that cannot be relieved. The suffix field is the entire point of the question.

principalYour cluster is 60% on one shard. Walk me through the incident.

Answer

First stabilise, then diagnose, then fix — and separate "hot shard" (uneven traffic) from "fat shard" (uneven data), because the remedies differ. I check sh.status() for range distribution and the balancer's state — a disabled balancer or a balancing window that never opens is the single most common cause, and it is a five-second fix. If the balancer is running and cannot even things out, I look for jumbo ranges (low-cardinality key), for a monotonic key sending all inserts to one shard, and for primary-shard concentration of unsharded collections, which no amount of balancing touches. For a hot shard I look at $queryStats and the per-shard op counters to find the tenant or key range generating the traffic. The remedies escalate: unstick the balancer; movePrimary for stranded databases; refineCollectionShardKey to give jumbo ranges cardinality; zone sharding to isolate a whale; and resharding as the real fix if the key is fundamentally wrong. Throughout, I would say what I am protecting — that shard's headroom — and set a concrete guard, like stopping the offending bulk job, before doing anything structural.

Example

sh.status();                                  // ranges per shard, jumbo flags
sh.getBalancerState(); sh.isBalancerRunning();
db.getSiblingDB("config").collections.find({ _id: "app.events" });
db.getSiblingDB("config").chunks.aggregate([   // where is the mass?
  { $match: { ns: "app.events" } },
  { $group: { _id: "$shard", n: { $sum: 1 }, jumbo: { $sum: { $cond: ["$jumbo", 1, 0] } } } }
]);

Follow-ups

  • What do you do first if that shard is nearly out of disk? — Buy time: stop the write source or the bulk job, expand the volume, and only then start migrations, because migrations themselves need disk on both sides.
  • How do you prevent a recurrence? — Alert on per-shard data-size skew and on balancer inactivity, not just on disk; both are leading indicators that fire days before the incident.
  • How do you communicate the resharding decision? — With the rehearsed numbers: duration, extra disk, throughput impact, and the abort path — so the decision is a risk trade-off other people can weigh, not a database-team assertion.

Common wrong answer

"Add another shard so the balancer spreads it out." Adding a shard to a cluster with a jumbo range or a monotonic key redistributes nothing — the jumbo range still cannot move, and the hot top range still takes every insert. You have added cost and an extra failure domain, and the imbalance is unchanged.

07Consistency, concerns and sessions

The distributed-systems core of a MongoDB interview, and the place where confident hand-waving is most visible. Almost every candidate can name w: "majority"; far fewer can say what it guarantees, what it does not, and what read concern pairs with it to make a guarantee end to end. Mid-level is tested on the vocabulary; senior on choosing the pair for a specific workload and knowing the cost; principal on explaining the trade-off to a team that wants "strong consistency" without knowing what they are asking for. MongoDB 5.0 changed the defaults — w: "majority" and readConcern: "local" — which is worth knowing precisely, because so much existing code was written against the old ones.

Docs: MongoDB Manual — Read Concern

screenerWhat is write concern, and what is the default?

Answer

Write concern is the acknowledgement contract: how many members must have the write before the server replies. w: 1 means the primary alone; w: "majority" means a majority of data-bearing voting members, which is what makes a write survive a failover; w: <n> or a tag set names specific members; w: 0 means fire-and-forget with no acknowledgement at all. j: true additionally requires the write to be in the on-disk journal of the acknowledging members, and wtimeout bounds how long the server waits. Since MongoDB 5.0 the default is w: "majority" (it was w: 1 before), which quietly made a lot of applications both safer and slower on upgrade. The sentence to have ready is that write concern controls durability against failover, while journalling controls durability against process crash — they are different failures.

Example

db.payments.insertOne(doc, { writeConcern: { w: "majority", j: true, wtimeout: 5000 } });
db.metrics.insertOne(sample, { writeConcern: { w: 1 } });     // cheap, loss-tolerant

// Cluster-wide default (4.4+), so applications cannot silently downgrade it:
db.adminCommand({ setDefaultRWConcern: 1,
  defaultWriteConcern: { w: "majority" }, defaultReadConcern: { level: "local" } });

Follow-ups

  • What does a wtimeout error mean? — Only that the concern was not met in time; the write may still be applied and later replicate. Treat it as "unknown", and make the operation idempotent so retrying is safe.
  • Does w: "majority" imply j: true? — Not by itself; the members must have applied it, and whether that includes a journal flush depends on j and the write-concern configuration. State them explicitly for money.
  • Why would anyone use w: 0? — High-volume telemetry where losing a sample is cheaper than the round trip; be explicit that errors — including duplicate-key — are invisible to the client.

Common wrong answer

"The default is w: 1, so you should set majority yourself." That has been wrong since July 2021. It is a clean date-stamp on someone's knowledge, and it matters practically: teams add explicit w: "majority" everywhere believing they are changing something, and miss the actual regression, which is that their read concern is still local.

screenerWhat are the read concern levels?

Answer

Five. local (default) returns the node's most recent data with no guarantee it is committed — it can be rolled back. available is local without the sharding orphan filter, so it is faster and may return orphaned documents; it exists for secondary reads on sharded clusters where speed beats precision. majority returns only data acknowledged by a majority, so it can never be rolled back — the guarantee people usually mean by "consistent". linearizable (primary only, single document) additionally waits to confirm the node is still primary, giving real-time linearizability at the cost of a majority round trip per read. snapshot reads from a single consistent point in time across the whole operation and is the read concern of multi-document transactions. The pairing rule to state: w: "majority" plus readConcern: "majority" is what gives an end-to-end "it will not disappear" guarantee; either alone does not.

Example

db.orders.find(q).readConcern("majority");                    // never rolled back
db.orders.find({ _id: id }).readConcern("linearizable")       // real-time, primary only
        .maxTimeMS(5000);                                     // ALWAYS bound this one
session.startTransaction({ readConcern: { level: "snapshot" },
                           writeConcern: { w: "majority" } });

Follow-ups

  • Why must linearizable always carry maxTimeMS? — It waits for a majority confirmation that can hang indefinitely during a partition; without a bound the client hangs with it.
  • Is majority the same as reading the latest data? — No: it returns the latest majority-committed data, which can be slightly behind the primary's most recent writes.
  • What does snapshot cost? — WiredTiger must retain the history needed for that point in time, so long snapshots increase cache pressure; that is why transactions have a 60-second default lifetime.

Common wrong answer

"readConcern: majority means the read goes to a majority of nodes." It does not — the read still goes to one node, which returns only data it knows is majority-committed. Getting this backwards suggests a quorum-read mental model borrowed from Dynamo-style systems, which is not how MongoDB works.

midWhat does the WiredTiger journal do, and how does it relate to replication?

Answer

The journal is a write-ahead log on each node: operations are written to it before they are applied to the data files, and it is flushed to disk at least every 100 ms (or immediately for a j: true write). WiredTiger also takes a checkpoint of the data files every 60 seconds; after a crash the node replays journal entries since the last checkpoint, which is why a crashed mongod recovers in seconds without losing acknowledged writes. Journalling has been mandatory since 4.0 — you cannot turn it off on a replica set member. The distinction to make explicitly is that the journal protects a single node against process or machine crash, while write concern protects the cluster against failover. A write can be journalled on the primary and still be lost if the primary dies before replicating and a new primary is elected without it — which is exactly the rollback scenario.

Example

db.serverStatus().wiredTiger.log;              // journal write and sync counters
db.serverStatus().wiredTiger.transaction["transaction checkpoint most recent time (msecs)"];

// Two different durability questions, two different knobs:
{ w: "majority" }   // survives losing the primary
{ j: true }         // survives the primary's process dying

Follow-ups

  • How much can you lose with j: false on a single node? — Up to the journal flush interval, so on the order of 100 ms of writes on that node.
  • What is the checkpoint interval for? — Bounding recovery time; a longer interval means less steady I/O but a longer replay after a crash.
  • Does j: true slow things down much? — On modern NVMe, modestly; on network storage it can be dramatic, because every acknowledgement waits for a durable flush.

Common wrong answer

"The oplog is the journal." Two different logs with two different jobs: the journal is WiredTiger's crash-recovery WAL, the oplog is the replication stream. Conflating them produces confident but wrong answers about what survives which failure — the exact thing this question exists to test.

midWhat is causal consistency, and how do you get read-your-own-writes?

Answer

Causal consistency guarantees that operations which are causally related are observed in that order — if you write and then read, you see your write, even across different nodes. MongoDB provides it through client sessions (3.6+): the driver tracks the cluster time and the operation time of your last write and attaches them to subsequent reads, so the server waits until that node has applied at least that point before answering. Every driver operation runs in an implicit session; you get the guarantee by passing an explicit session through the related operations, and it requires readConcern: "majority" to be a real guarantee rather than a best effort. This is the correct answer to "how do you read your own writes from a secondary" — better than pinning everything to the primary, because it costs a wait only when the secondary is actually behind.

Example

const session = client.startSession({ causalConsistency: true });
const orders = client.db("app").collection("orders");

await orders.insertOne({ _id: id, status: "pending" }, { session });
// Same session -> this read waits until the chosen node has that write.
const doc = await orders.findOne({ _id: id },
  { session, readConcern: { level: "majority" },
    readPreference: { mode: "secondaryPreferred" } });

Follow-ups

  • What if the request is served by a different application instance? — The session does not travel with the user; you must pass the operation time (cluster time) forward yourself, or route that user's reads to the primary for a short window.
  • Does causal consistency work across a sharded cluster? — Yes, on the logical cluster time, which is why the gossiped $clusterTime appears on every message.
  • Is it free? — Nearly: the cost is only the wait when the target node is behind, plus the discipline of threading the session through your code.

Common wrong answer

"Read from the primary — that's read-your-own-writes." It works and it throws away the reason you had secondaries. The stronger answer names causal sessions and, crucially, notes that they need readConcern: "majority" to be a guarantee rather than a probability.

midIs MongoDB CP or AP?

Answer

CP, by design and by default. Under a network partition the minority side has no primary and refuses writes, choosing consistency over availability; a majority-connected side keeps serving. But I would immediately complicate the label, because CAP is a coarse instrument: MongoDB's actual behaviour is a spectrum you configure. With w: 1 and readConcern: "local" from secondaries it behaves much more like an AP system with a single writer and stale reads; with w: "majority" and readConcern: "majority" it is genuinely CP; with linearizable reads it is linearizable for single-document operations. The more useful frame at senior level is PACELC: partitioned, MongoDB chooses consistency; else, it lets you choose between latency and consistency per operation. MongoDB has also passed Jepsen analyses for its transaction and session guarantees at recent versions, which is the citation to have ready if pushed.

Example

// Minority side of a partition: no primary, so this fails rather than diverging.
db.orders.insertOne(doc);   // MongoServerSelectionError: no primary available

// The knobs that move MongoDB along the spectrum, per operation:
{ w: 1,            readConcern: "local"     }   // fastest, weakest
{ w: "majority",   readConcern: "majority"  }   // no lost writes, no dirty reads
{ w: "majority",   readConcern: "linearizable" } // real-time order, primary only

Follow-ups

  • Can MongoDB have split brain? — Two primaries cannot both accept majority writes; an isolated old primary can accept w: 1 writes briefly before it steps down, and those are exactly the writes that get rolled back.
  • What is the availability cost of CP here? — During failover — typically under 12 seconds — writes fail; drivers retry, so the application sees latency rather than errors if it is configured properly.
  • Where does read preference fit? — It moves reads toward availability and away from consistency, independently of the write path.

Common wrong answer

"MongoDB is AP because it's NoSQL and eventually consistent." A decade-old stereotype that was never accurate for replica-set writes. Answering with the stereotype signals that your model of MongoDB predates 3.x, and the interviewer will usually follow up with rollback semantics to confirm it.

seniorChoose write and read concern for a payments workload, and for a telemetry workload.

Answer

For payments: w: "majority" with j: true, readConcern: "majority", causal sessions on the read-after-write paths, and every operation idempotent with a client-supplied key so a wtimeout or a failover retry cannot double-charge. I would push back on linearizable unless there is a genuine real-time requirement, because it costs a majority confirmation per read and its failure mode under partition is a hang. For telemetry: w: 1 — or even w: 0 for genuinely lossy metrics — with readConcern: "local", unordered bulk writes, and a TTL or time-series collection so the data expires without a delete storm. The point I would make explicitly is that these are per-operation decisions, not per-cluster ones: the same application should use both, and the cluster-wide default (setDefaultRWConcern, 4.4+) exists to make the safe one the default so that a careless service cannot silently downgrade durability.

Example

// Payments: durable, idempotent, retry-safe.
await payments.insertOne({ _id: idempotencyKey, ...payment },
  { writeConcern: { w: "majority", j: true, wtimeout: 5000 } });
// Duplicate key on retry == already applied. That is the design, not an error.

// Telemetry: cheap, unordered, self-expiring.
await metrics.insertMany(batch, { ordered: false, writeConcern: { w: 1 } });
db.metrics.createIndex({ ts: 1 }, { expireAfterSeconds: 604800 });

Follow-ups

  • How do you make a payment write idempotent? — Use the idempotency key as _id; the unique index turns a duplicate retry into error 11000, which the code treats as success.
  • What breaks if you use w: "majority" everywhere? — Throughput on high-volume paths, and coupling to replication health: a lagging secondary now slows your telemetry ingest.
  • How do you stop teams downgrading durability by accident? — Set the cluster default, and treat a per-operation weaker concern as something that needs a comment explaining why.

Common wrong answer

"Use w: "majority" everywhere, it's safest." Safe and undifferentiated. The question is explicitly about two workloads with different loss tolerances, and answering with one setting shows you have not thought about what durability costs — or that a single blanket setting is what makes teams turn it off entirely later.

seniorA user updates their profile and the next page shows the old value. Diagnose it.

Answer

Four candidate causes, and I would ask for one piece of evidence to separate them. (1) The read went to a secondary that has not applied the write — check the read preference and whether the two requests shared a causally consistent session. (2) The write used w: 1 and was rolled back by a failover — check for an election around that timestamp in the logs. (3) An application or CDN cache served the stale copy, and the database is innocent — check whether a direct query returns the new value. (4) The write silently did nothing: an updateOne whose filter matched no document, whose matchedCount nobody checked. In my experience (4) and (1) are the two most common, in that order, and (4) is the one that produces no anomaly in any dashboard. The structural fixes are causal sessions for read-after-write flows, w: "majority" for anything user-visible, and asserting on matchedCount/modifiedCount at the repository layer.

Example

const res = await users.updateOne({ _id, version }, { $set: patch });
if (res.matchedCount === 0) throw new ConflictError();   // never fail silently

// And make the following read causally ordered rather than lucky:
await users.findOne({ _id }, { session, readConcern: { level: "majority" } });

Follow-ups

  • How would you confirm cause (2) after the fact? — Election entries in the log around that time plus rollback records; if the write concern was w: 1, treat it as the leading hypothesis.
  • Why is modifiedCount: 0 with matchedCount: 1 not an error? — The update was a no-op because the values already matched; that is legitimate and worth distinguishing in the code.
  • How do you make this class of bug loud? — Metrics on zero-match updates per endpoint; they should be near zero, and a spike is a schema or routing bug.

Common wrong answer

"Eventual consistency — that's just how MongoDB works." It is not eventual on the primary, and treating a real bug as a property of the database means nobody investigates. This question is a trap for exactly that reflex.

principalA team wants "strong consistency everywhere". How do you handle that conversation?

Answer

I translate the request into the specific guarantees they actually need, because "strong consistency" is four different asks: no lost writes, no stale reads, real-time ordering, and multi-document atomicity — with four different prices. So I go per use case: money movement gets w: "majority", readConcern: "majority" and, where genuinely cross-document, transactions; a user's own profile gets a causal session, which is cheap and is what they usually mean; a dashboard gets whatever is fast, because a two-second-old number is fine and nobody will pay cross-region latency for it. Then I quantify the price of the blanket version — the latency floor of a majority write on their topology, the throughput drop, the coupling to replication health — because the useful outcome of the conversation is not "no", it is a shared understanding that consistency is bought per operation. Finally I make the safe thing the default (cluster-wide read/write concern) so that weakening it is a visible, reviewed choice rather than the outcome of a copy-pasted connection string.

Example

// The artefact I'd bring to the conversation, per use case rather than per cluster:
// use case        | w          | readConcern  | session  | why
// payment capture | majority+j | majority     | causal   | never lose, never double
// profile edit    | majority   | local        | causal   | read-your-own-writes
// feed render     | -          | local        | none     | 2s staleness is free
// metrics ingest  | 1          | local        | none     | loss-tolerant, high volume

Follow-ups

  • What if they insist on linearizable reads? — Show the cost: a majority confirmation per read, primary-only, single-document only, and a hang under partition unless every call carries maxTimeMS. Usually the requirement dissolves into "read-your-own-writes".
  • How do you stop this drifting back? — Encode it: the concerns live in a shared data-access layer keyed by use case, not sprinkled at call sites, and the cluster default is the safe one.
  • What about transactions as the blanket answer? — Transactions solve atomicity, not staleness, and cost cache pressure; reaching for them to fix a consistency conversation is a common and expensive misdiagnosis.

Common wrong answer

"Turn on majority everywhere and transactions where needed." It answers the words rather than the need, and it hides the cost until it shows up as a latency regression nobody can attribute. At principal level the expected move is to decompose the request into guarantees and price each one.

08Transactions and atomicity

Asked in almost every loop, usually as a trap. The naive question — "does MongoDB support ACID transactions?" — has an easy yes since 4.0 (replica sets) and 4.2 (sharded clusters), and candidates who stop there miss the point entirely. What the interviewer is testing is whether you know that a well-designed document model needs them rarely, what they cost the storage engine, how to write the retry loop correctly, and when a saga or an idempotent state machine is the better answer. At principal level the question becomes architectural: how do you stop a team from reproducing a relational transaction habit inside a document store.

Docs: MongoDB Manual — Transactions

screenerDoes MongoDB support ACID transactions?

Answer

Yes. Single-document operations have always been atomic — including updates to nested documents and arrays — and that covers most needs when the model is right. Multi-document, multi-collection ACID transactions arrived in 4.0 for replica sets and 4.2 for sharded clusters, using snapshot isolation and, across shards, a two-phase commit. They give you all-or-nothing across documents and a consistent snapshot for reads. The immediate qualifier a strong candidate adds unprompted: they are not free. A transaction holds a WiredTiger snapshot open, which means the engine must retain the history behind it, so long or large transactions cause cache pressure across the whole node; the default lifetime is 60 seconds; and write conflicts between concurrent transactions abort one of them, so the application must retry. The rule I use is that a transaction is a signal to re-examine the model first, and a legitimate tool second.

Example

const session = client.startSession();
await session.withTransaction(async () => {
  await accounts.updateOne({ _id: from, balance: { $gte: amount } },
                           { $inc: { balance: -amount } }, { session });
  await accounts.updateOne({ _id: to }, { $inc: { balance: amount } }, { session });
  await ledger.insertOne({ from, to, amount, at: new Date() }, { session });
}, { readConcern: { level: "snapshot" }, writeConcern: { w: "majority" } });

Follow-ups

  • What isolation level is it? — Snapshot isolation, with the write-conflict behaviour that implies: no dirty or non-repeatable reads, and write-write conflicts abort rather than block.
  • Can a transaction span databases? — Yes, and collections, and (since 4.2) shards. It cannot span clusters.
  • Do transactions work on capped collections or with DDL? — Writes to capped collections are not allowed in a transaction; collection creation inside a transaction became possible in 4.4, but avoid DDL in transactions as a habit.

Common wrong answer

"MongoDB doesn't have transactions, that's the trade-off for scale." Eight years out of date, and it usually comes with the follow-on claim that you must implement two-phase commit in application code — a pattern from the 3.x-era documentation that no longer belongs in a design.

midWrite a transaction correctly. What does the retry loop have to handle?

Answer

Two distinct error labels, and this is exactly what interviewers probe. TransientTransactionError means the whole transaction should be retried from the beginning — a write conflict, a failover, a stepdown. UnknownTransactionCommitResult means the commit's outcome is unknown and the commit should be retried; because commit is idempotent, retrying it is safe and will report the actual result. The driver's withTransaction helper implements both loops for you with a 120-second cap, which is why using it rather than hand-rolling startTransaction/commitTransaction is the correct answer. The other requirements: every operation inside must carry the session; the callback must be genuinely re-runnable, since it may execute several times; and it must contain no non-database side effects — no HTTP calls, no message publishing — because those will be repeated.

Example

// Correct: driver-managed retries, session threaded, callback idempotent.
await session.withTransaction(async () => { /* only DB work, using { session } */ });

// The hand-rolled version people get wrong - shown so you can recognise it:
try { session.startTransaction(); /* ... */ await session.commitTransaction(); }
catch (e) {
  if (e.hasErrorLabel("TransientTransactionError")) { /* retry WHOLE txn */ }
  else if (e.hasErrorLabel("UnknownTransactionCommitResult")) { /* retry COMMIT */ }
  else { await session.abortTransaction(); throw e; }
}

Follow-ups

  • Why must the callback be side-effect free? — It can run multiple times; publishing a message inside a retried transaction sends it twice, and the transaction cannot roll it back.
  • What is the first-operation behaviour? — The transaction starts lazily on the first operation, and the read concern is fixed at that point; the snapshot is taken then, not at startTransaction.
  • How do you publish an event atomically with the write? — The outbox pattern: insert the event into an outbox collection inside the transaction, and let a change-stream consumer publish it afterwards.

Common wrong answer

"Wrap it in try/catch and abort on error." That handles failure but not the two retryable classes, so under any real concurrency the application surfaces write conflicts to users as 500s. And aborting on UnknownTransactionCommitResult is actively wrong: the transaction may well have committed.

midWhy is the default transaction lifetime 60 seconds?

Answer

Because an open transaction pins a WiredTiger snapshot, and the engine must keep every version of every document that existed at that point available for the duration. The longer and larger the transaction, the more history is pinned in cache, and cache is shared by everything on the node — so one long transaction degrades unrelated workloads and can push the node into eviction stalls. transactionLifetimeLimitSeconds defaults to 60 and exists to bound that blast radius. It is a limit to respect rather than raise: the correct response to "my transaction times out" is a smaller transaction, batched work, or a redesign, not a bigger number. The related limit worth naming is that a transaction's oplog entry must fit in 16 MB — since 4.2 large transactions are split across multiple oplog entries, but the underlying pressure is the same.

Example

db.adminCommand({ getParameter: 1, transactionLifetimeLimitSeconds: 1 });   // 60
db.serverStatus().transactions;   // currentActive, currentOpen, totalAborted
db.currentOp({ "transaction": { $exists: true }, secs_running: { $gt: 10 } });

Follow-ups

  • What breaks first when transactions are too big? — Cache dirty percentage climbs, eviction threads engage, and write latency rises across the whole node — visible long before the transaction itself fails.
  • How do you handle work that genuinely takes minutes? — Chunk it into many small idempotent transactions with a checkpoint, or make it a state machine with a status field, not one long transaction.
  • Is maxTimeMS the same thing? — No: maxTimeMS bounds a single operation; the lifetime limit bounds the whole transaction.

Common wrong answer

"Raise transactionLifetimeLimitSeconds if 60 seconds isn't enough." It converts a bounded failure into an unbounded one and moves the damage onto every other query on the node. Interviewers ask this precisely because the tempting fix is the wrong one.

seniorHow do transactions work across shards, and what does that cost?

Answer

Since 4.2 a transaction can span shards, coordinated by a two-phase commit: one participant shard is chosen as the transaction coordinator, it asks each participant to prepare (durably, in the oplog), and once all vote yes it commits and tells them to commit. The costs are the ones you would expect from 2PC — extra network round trips, a prepared state that holds locks and snapshot history on every participant, and a coordinator failure window where participants sit prepared until recovery resolves them. In practice that means a cross-shard transaction is several times more expensive than a single-shard one and considerably more expensive than a single-document write. The design consequence is the interesting part: choose a shard key that keeps transactional units on one shard — the whole tenant, the whole order, the whole account — so that transactions stay single-shard. That is a modelling decision made months before the transaction is written.

Example

// Both accounts on one shard because the shard key leads with the owning entity:
sh.shardCollection("bank.accounts", { customerId: 1, _id: 1 });
// A transfer within one customer is single-shard; between customers is 2PC.

db.serverStatus().twoPhaseCommitCoordinator;   // totalCreated, totalStartedTwoPhaseCommit

Follow-ups

  • What happens if the coordinator dies mid-commit? — The decision is durable in the oplog; a new coordinator recovers and drives participants to the same outcome. Participants stay prepared until then, holding resources.
  • Do cross-shard transactions block reads? — Reads at snapshot/majority may have to wait for prepared transactions to resolve, which is how a stuck 2PC shows up as unrelated read latency.
  • What is the alternative for a genuinely cross-shard invariant? — A saga with compensating actions and an idempotent state machine, accepting eventual consistency and making the intermediate states explicit.

Common wrong answer

"It's the same as a normal transaction, MongoDB handles it." Mechanically true and operationally misleading: 2PC has a blocking window, prepared transactions hold resources on every participant, and the cost is high enough that it should shape your shard key. An answer that does not mention prepare, or the shard-key implication, is a mid-level answer.

seniorWhen should you not use a transaction?

Answer

Whenever the invariant fits in one document — which, with a well-designed model, is most of the time. If an order and its lines are one document, "add a line and update the total" is a single atomic update, not a transaction. Beyond that: not for bulk work, because ten thousand documents in one transaction fights the lifetime limit, the oplog entry size and the cache; not as a substitute for idempotence, because retries are a fact of distributed life and a transaction does not make a repeated request safe; and not for anything containing an external call, since you cannot roll back an HTTP POST. The senior formulation is that a transaction should feel like an admission that the model does not fit the invariant, and about once in five that admission is correct — genuinely cross-entity operations like a transfer between two accounts. The rest of the time the better tools are the atomic single-document update, compare-and-set on a version field, and the outbox pattern.

Example

// Transaction-free because the invariant lives in one document:
db.orders.updateOne(
  { _id: orderId, status: "open" },
  { $push: { lines: line }, $inc: { total: line.unitPrice * line.qty } });

// Transaction-free cross-document work via an outbox + change stream:
// (insert the event in the same document write, publish it asynchronously)
db.orders.updateOne({ _id }, { $set: { status: "paid" },
  $push: { outbox: { type: "OrderPaid", at: new Date() } } });

Follow-ups

  • How do you convince a team to stop wrapping everything? — Show the cache and latency numbers from a load test with and without; the argument that lands is the one measured on their own cluster.
  • What is a legitimate multi-document case? — Money movement between separately owned accounts, and any invariant across entities that genuinely cannot be co-located.
  • Does a transaction give you read-your-own-writes? — Inside itself, yes; outside, the same session and read concern rules apply as always.

Common wrong answer

"Use transactions whenever more than one write is involved — it's safer." It is safer only against partial failure, and it is worse against everything else: throughput, cache pressure, and the risk of the transaction becoming the place where all concurrency contention lands. The interviewer wants to hear "first, can the model make this a single document?"

seniorHow do you implement a workflow that spans MongoDB and an external service?

Answer

As an explicit state machine with an outbox, never as a transaction. The state lives in the document — pending, charging, charged, failed — and each transition is a compare-and-set that also records the intent. A durable outbox entry is written in the same atomic operation as the state change; a separate worker, driven by a change stream, reads the outbox and calls the external service, with an idempotency key so a retry is harmless, and records the result as the next transition. Failures become compensating transitions rather than rollbacks — a saga. The properties I would call out are that every step is idempotent, every step is resumable after a crash, and the intermediate states are visible to operators, which is precisely what a transaction hides. The cost is that the domain must tolerate intermediate states, which is a product conversation, not a technical one.

Example

// 1. Claim the work with a CAS; the transition and the intent are one atomic write.
const claimed = await orders.findOneAndUpdate(
  { _id, status: "pending" },
  { $set: { status: "charging", attemptId: newAttemptId },
    $push: { outbox: { type: "ChargeRequested", attemptId: newAttemptId } } },
  { returnDocument: "after" });

// 2. A worker publishes from the outbox with the attemptId as the idempotency key.
// 3. The result drives the next CAS: charging -> charged, or charging -> failed.

Follow-ups

  • Why is the outbox in the same document rather than a separate collection? — Same-document guarantees atomicity without a transaction; a separate outbox collection is fine too, but then the write does need a transaction.
  • How does the worker avoid double-publishing? — At-least-once delivery plus a downstream idempotency key; exactly-once across a network boundary does not exist, so make the consumer idempotent.
  • How do you handle a stuck charging state? — A reaper driven by a timestamp and a TTL-style sweep that queries the external service for the attempt id and resolves it, rather than guessing.

Common wrong answer

"Put the database write and the API call in a transaction so they both succeed or both fail." Nothing about a MongoDB transaction can un-send an HTTP request, and if the call succeeds while the transaction aborts you have charged a customer with no record. This is the highest-signal wrong answer in the whole section.

principalTransaction aborts have gone from 0.1% to 8%. What do you do?

Answer

Treat it as a contention problem until proven otherwise, and stabilise before redesigning. First, classify the aborts: db.serverStatus().transactions plus the error labels tell me whether these are write conflicts (contention on the same documents), timeouts (transactions running too long), or failovers. Write conflicts at that rate almost always mean many transactions touching one hot document — a shared counter, a "current state" singleton, a per-day rollup row that every request increments — so the fix is to remove the hotspot: shard the counter across N sub-documents and sum on read, move the increment out of the transaction entirely (it does not need snapshot isolation), or make the operation a single-document atomic update. Second, shrink the transactions: fewer statements, no external calls, tighter filters so the snapshot touches less. Third, verify the retry loop is exponential with jitter — a naive immediate retry turns contention into a stampede and is why 8% becomes 40%. Then I would set an SLO on abort rate so this is detected as a trend rather than as an incident.

Example

// The hotspot: every transaction increments one document.
{ _id: "counter:2026-09-08", value: 4_812_337 }

// Sharded counter: N documents, contention divided by N, summed on read.
db.counters.updateOne({ _id: `counter:${day}:${randomInt(64)}` },
                      { $inc: { value: 1 } }, { upsert: true });
db.counters.aggregate([{ $match: { _id: new RegExp(`^counter:${day}:`) } },
                       { $group: { _id: null, total: { $sum: "$value" } } }]);

Follow-ups

  • How do you find the hot document? — $queryStats and the profiler for the shapes involved, plus currentOp sampling during a spike; the same _id appearing everywhere is unmistakable.
  • What if the aborts are timeouts, not conflicts? — Look for a slow query inside the transaction — usually a missing index — because a transaction is only as fast as its worst statement, and it holds its snapshot the whole time.
  • What is the organisational fix? — An abort-rate SLO with an alert, and a review rule that any new transaction must state which invariant requires it.

Common wrong answer

"Increase the retry count." It papers over the symptom and amplifies the cause: more retries against the same hot document means more conflicts, and the cluster spends its capacity aborting work. Any answer that does not go looking for the contended document is missing the question.

09Performance debugging

The "you are on call" section. Interviewers give you a symptom — latency spike, CPU pegged, connections exhausted — and watch whether you have a method or a list of guesses. What distinguishes a strong candidate is ordering: measure before changing, separate "one query is slow" from "the server is slow", and know which single metric discriminates between the two. This is also where the modern tooling matters: $queryStats (7.0+) replaced a decade of ad hoc log parsing, and it is worth naming.

Docs: MongoDB Manual — Analyzing Performance

midAn endpoint went from 30 ms to 3 s overnight. Walk me through your investigation.

Answer

I start by deciding whether the database is even the cause, then whether it is one query or the whole server. First: is latency up for every query on that cluster, or just this one? If everything is slow, the cause is resource-level — cache, disk, CPU, connections, replication — and chasing the query wastes the outage. If it is one shape, I get the actual command from the slow-query log or $queryStats, run explain("executionStats"), and compare totalKeysExamined to nReturned. Then I ask what changed, because "overnight" is a strong hint: a deploy that altered the query shape, an index dropped or built, a data-volume threshold crossed so the working set no longer fits in cache, a plan-cache eviction after a restart choosing a different plan, or a TTL/batch job that started overlapping with peak. I would name the plan-cache case explicitly, because a query that was fast for a year and is slow after a restart with no code change is almost always that.

Example

// 1. Is it one shape or everything?
db.serverStatus().opLatencies;                  // reads/writes/commands histograms

// 2. Find the shape and its cost (7.0+; sampled, low overhead, survives restarts better).
db.aggregate([{ $queryStats: {} }, { $sort: { "metrics.execTimeMicros.sum": -1 } },
              { $limit: 10 }]);

// 3. Confirm the plan, and whether it is the plan you expect.
db.orders.find(theQuery).explain("allPlansExecution");
db.orders.getPlanCache().list();

Follow-ups

  • What if explain looks fine but production is slow? — You are reproducing with a warm cache and no concurrency; check queueing (globalLock.currentQueue), ticket exhaustion and disk latency instead.
  • How do you get the exact production query? — The slow-query log with slowms, the profiler at level 1, or $queryStats; add a comment to application queries so they are attributable.
  • What is your first mitigation while you diagnose? — If it is one shape and you know the right index, add it; otherwise shed load on that endpoint. Do not restart the primary as a first move — you will lose the evidence and force an election.

Common wrong answer

"Check the indexes." It is the right neighbourhood and the wrong altitude: it assumes the answer before measuring, and it is useless when the real cause is cache pressure or connection exhaustion. Interviewers are listening for the discriminating question first — one query, or all of them?

midHow do you use the profiler and the slow-query log?

Answer

The slow-query log is always on: any operation slower than slowms (100 ms by default) is logged with its plan summary, keys and documents examined, and lock times — for most investigations that is enough and it costs nothing. The profiler writes the same information into a capped collection, system.profile, so it is queryable: level 0 off, level 1 slow operations only, level 2 everything. Level 2 on a busy production system is a self-inflicted incident — it writes a document per operation — so the pattern is level 1 with a tuned slowms, or level 1 with sampleRate for a bounded sample. The profiler is per-database and per-node, so remember to enable it where the traffic actually goes. Since 7.0 $queryStats gives aggregated per-shape statistics continuously and is the better first stop; the profiler is for when you need the individual slow operations with their parameters.

Example

db.setProfilingLevel(1, { slowms: 50, sampleRate: 0.2 });
db.system.profile.find({ millis: { $gt: 200 } })
   .sort({ ts: -1 }).limit(20)
   .projection({ ts: 1, op: 1, ns: 1, millis: 1, planSummary: 1, keysExamined: 1, docsExamined: 1 });
db.setProfilingLevel(0);          // turn it off again - it is not free

Follow-ups

  • What does planSummary: COLLSCAN in the log mean immediately? — A missing or unusable index for that shape; it is the highest-value single grep in the log.
  • Why is the profile collection capped? — So it cannot fill the disk; it also means old entries vanish, so extract what you need promptly.
  • How do you attribute a query to a service? — comment on the operation and the driver's appName in the connection string; both appear in the log and in currentOp.

Common wrong answer

"Turn the profiler to level 2 to see everything." On a production primary that adds a write per operation to a capped collection and can noticeably degrade the system you are trying to diagnose. Level 2 belongs in a staging environment or a very short, deliberate window.

midWhat do you look at in currentOp during an incident?

Answer

Long-running operations, what they are waiting on, and whether one of them is blocking the others. I filter for secs_running above a threshold and inspect op, ns, planSummary, waitingForLock, and the lockStats. The patterns I am looking for: a COLLSCAN aggregation someone launched by hand; an index build; a long transaction holding a snapshot; a getMore on an abandoned cursor; a chunk migration. killOp is the blunt tool and it works — it aborts index builds cleanly on all members, and it terminates a runaway aggregation — but I would identify the operation and its origin before killing it, because killing the same query every hour is not a fix. Two practical notes: currentOp is a point sample, so take several; and on a sharded cluster run it through mongos for the cluster-wide view, since a per-shard view will not show you the fan-out.

Example

db.getSiblingDB("admin").aggregate([
  { $currentOp: { allUsers: true, idleConnections: false } },
  { $match: { secs_running: { $gt: 5 }, "command.$db": { $ne: "admin" } } },
  { $project: { opid: 1, secs_running: 1, op: 1, ns: 1, planSummary: 1,
                waitingForLock: 1, "command.comment": 1, appName: 1 } }
]);
db.adminCommand({ killOp: 1, op: 12345678 });

Follow-ups

  • Is killOp safe on a write? — It aborts the operation; single-document writes are atomic so you get all-or-nothing, but an updateMany stops partway, which is why idempotent batch jobs matter.
  • How do you find the culprit application? — appName from the connection string and client/clientMetadata in the op; teams that do not set appName lose an hour per incident.
  • What does waitingForLock: true point at? — Something holding a conflicting lock — a DDL operation, an index build, or a long transaction; find the holder rather than killing the waiters.

Common wrong answer

"Kill the long-running operations." Sometimes correct as a mitigation, never as an answer: it can kill a chunk migration or an index build that then has to start over, and it says nothing about why the operation existed. Identify, then kill, then fix the source.

seniorHow do you tell that the working set no longer fits in RAM?

Answer

The signature is a change in the shape of the metrics rather than any single number: read latency rises while CPU stays moderate, disk read IOPS and I/O wait climb, and WiredTiger's cache statistics show high eviction activity with "bytes read into cache" far above the steady-state baseline. The precise indicators I look at are wiredTiger.cache — bytes currently in cache versus the configured maximum, "pages read into cache" rate, and the "tracked dirty bytes" and eviction-thread counters — plus, at the operating-system level, whether the page cache is thrashing. The distinguishing test versus "one bad query" is that everything gets slower together, including trivially indexed point lookups. The fixes, in order: reduce the working set (archive, TTL, drop unused indexes — indexes compete for the same cache), then add RAM, then shard. 8.2 made the cache sizing configurable as a percentage of RAM, which is a better default for containerised deployments than the old absolute value.

Example

const c = db.serverStatus().wiredTiger.cache;
c["bytes currently in the cache"] / c["maximum bytes configured"];   // ~1.0 = full
c["pages read into cache"];        // rate matters, not the absolute
c["tracked dirty bytes in the cache"] / c["maximum bytes configured"];  // >5% = pressure
db.stats(1024*1024*1024);          // dataSize + indexSize in GB vs node RAM

Follow-ups

  • What is the working set, exactly? — The data and index pages actually touched by the current workload — not the whole database, which is why a 4 TB collection can be fine on a 128 GB node if queries only ever touch recent data.
  • Why do unused indexes hurt so much here? — They occupy cache and are updated on every write, so they consume the exact resource you are short of.
  • What about just adding a bigger disk? — Faster storage lowers the cost of a cache miss and buys real time on NVMe, but it does not change the shape of the problem.

Common wrong answer

"Check if data size is bigger than RAM." Data size is not working-set size, and plenty of healthy deployments have far more data than memory. The metric that discriminates is cache miss and eviction behaviour, not the size of the collection.

seniorConnections are exhausted and everything is timing out. What is happening?

Answer

Usually a connection storm: something made queries slower, application pools opened more connections to compensate, and each connection costs the server a thread and about a megabyte of stack, so the server got slower still — a positive feedback loop. The diagnosis is serverStatus().connections (current versus available) and globalLock.currentQueue, plus the number of application instances multiplied by their pool size, which is very often larger than anybody realises. The fixes are on both sides: bound the pool per instance (maxPoolSize, default 100 in most drivers, which is far too high when you run 60 pods), set maxIdleTimeMS so idle connections are reclaimed, and set sensible serverSelectionTimeoutMS and maxTimeMS so a slow database produces fast failures instead of a growing queue. On the server side, MongoDB 8.0 added an ingress admission rate limiter and 8.3 added pre-auth message-size and memory caps and per-application rate-limiter exemptions, which give you a way to protect the server from exactly this.

Example

db.serverStatus().connections;      // { current, available, totalCreated, active }
db.serverStatus().globalLock.currentQueue;   // readers/writers waiting

// Sized deliberately: 60 pods x 20 = 1,200 connections, not 60 x 100 = 6,000.
mongodb://.../app?maxPoolSize=20&maxIdleTimeMS=60000&serverSelectionTimeoutMS=5000

Follow-ups

  • Why is a bigger pool usually the wrong fix? — Concurrency at the storage engine is bounded by execution tickets; extra connections queue rather than execute, so you convert a latency problem into a memory problem.
  • What are WiredTiger tickets? — The concurrent read and write slots into the storage engine (historically 128 each; dynamically tuned since 7.0). Ticket exhaustion shows as a growing queue with idle CPU.
  • What does a serverless or Lambda workload change? — Every invocation wanting its own connection; use a proxy or the driver's connection reuse across invocations, or you will storm the cluster on any traffic spike.

Common wrong answer

"Increase maxIncomingConnections." It removes the ceiling that was protecting the server and lets the feedback loop run further; the server then spends its memory and scheduler on connections rather than on work. The correct direction is almost always to reduce the pool and add timeouts.

seniorWhat locking does MongoDB do, and what causes lock contention?

Answer

MongoDB has a hierarchy of intent locks — global, database, collection — while document-level concurrency is handled by WiredTiger's optimistic concurrency control, not by locks: two writers to the same document produce a write conflict, and the server retries transparently for ordinary writes (a transaction, by contrast, aborts and hands the retry to you). So in normal operation collection-level lock contention is rare, and the things that actually cause it are DDL: creating or dropping a collection or index, collMod, renameCollection, and compaction, all of which need exclusive locks. The other contention that shows up as "locking" but is not is ticket exhaustion — the bounded number of concurrent storage-engine operations — which since 7.0 is dynamically tuned rather than fixed at 128. I would look at globalLock.currentQueue and the locks section of serverStatus, and check for a DDL operation in currentOp before concluding anything.

Example

db.serverStatus().globalLock;      // currentQueue.readers / .writers, activeClients
db.serverStatus().locks;           // acquireCount / acquireWaitCount by lock type
db.serverStatus().wiredTiger.concurrentTransactions;   // available read/write tickets

Follow-ups

  • Why does a write conflict not surface for a normal update? — The server retries internally; only inside a transaction is the conflict promoted to a TransientTransactionError for the client.
  • What is the danger of renameCollection in production? — It takes a global-scope exclusive lock and blocks everything briefly; on a sharded cluster it has further restrictions.
  • Does a hot document serialise writes? — Effectively yes, through conflict-and-retry rather than blocking; the symptom is CPU spent retrying, which is why counters get sharded across documents.

Common wrong answer

"MongoDB locks at the database level, that's the known weakness." True in 2.x, replaced by collection-level intent locks plus document-level concurrency in 3.0 with WiredTiger. It is one of the most reliable indicators that a candidate's knowledge stopped a decade ago.

seniorHow do you load-test a MongoDB change before it ships?

Answer

With production-shaped data, production-shaped concurrency, and a cold cache — because the three ways a load test lies are a tiny data set (everything fits in cache), a single-threaded driver (no contention), and a warm cache after the first run. My approach: restore a recent production snapshot into an environment sized like production; replay a captured workload mix rather than a synthetic loop, keeping the ratio of reads to writes and the distribution of key access, since a uniform random key distribution understates cache behaviour badly; measure p99 and p999, not the mean; and watch the server-side metrics that predict a cliff — cache dirty percentage, ticket availability, replication lag — not just client latency. For a schema or index change specifically, I compare explain plans and index sizes before and after, and I run the migration itself under load, because the migration is usually the riskier half.

Example

// Capture the real shape mix rather than inventing one.
db.aggregate([{ $queryStats: {} },
  { $project: { shape: "$key.queryShape", n: "$metrics.execCount",
                p99: "$metrics.execTimeMicros" } },
  { $sort: { n: -1 } }, { $limit: 30 }]);

// Then assert on server-side signals during the run, not only client latency:
db.serverStatus().wiredTiger.concurrentTransactions;
rs.printSecondaryReplicationInfo();

Follow-ups

  • Why does a uniform key distribution mislead? — Real access is skewed (Zipfian), so real caches hit far more often; a uniform test either over- or under-states cache pressure, and never matches.
  • How do you test failover behaviour? — Step the primary down mid-test (rs.stepDown()) and assert on the application's error rate and retry behaviour; if a failover produces user-visible errors, the driver configuration is wrong.
  • What do you do when you cannot have production data? — Generate data with the real cardinalities and skew, especially the distribution of the shard key and the size distribution of arrays, which are what drive the behaviour.

Common wrong answer

"Run the query in a loop and time it." That measures a warm cache with no concurrency, which is the least informative configuration available, and it produces a number that will not survive contact with production. The tell an interviewer listens for is whether you mention cache state and concurrency at all.

principalWhat does good MongoDB observability look like across many teams?

Answer

Three layers, each owned by someone. Cluster health — replication lag, cache pressure, ticket availability, connections, disk headroom, election count, oplog window — alerted on leading indicators rather than on symptoms, because oplog window and cache dirty percentage predict incidents that disk-full and latency alerts only report. Workload — per-shape statistics from $queryStats exported continuously, so "what is the most expensive query shape this week" is a dashboard rather than an investigation, plus COLLSCAN rate and index growth as slow-moving quality metrics. Attribution — every service sets appName, every non-trivial query carries a comment, so any expensive operation maps to a team without archaeology. On top of that I would put two organisational mechanisms: a monthly index and slow-query review that produces owned tickets, and a database-change checklist in the deployment pipeline so index builds and migrations are announced and scheduled rather than discovered. The failure mode I am designing against is not a missing dashboard, it is nobody owning the number on it.

Example

// Attribution baked into the connection string and the query, not added at 2am:
mongodb://.../app?appName=checkout-api&maxPoolSize=20
db.orders.find(q).comment("checkout:cart-summary");

// Leading indicators worth an alert, in rough priority order:
// oplog window < 24h | cache dirty > 5% | repl lag > 60s
// tickets available < 10% | COLLSCAN rate rising | connections > 70% of available

Follow-ups

  • Which single metric would you keep if you could keep one? — Replication lag: it moves for almost every serious cause — disk, oplog volume, blocking reads, migrations — and it directly threatens both durability and recovery.
  • How do you handle Atlas versus self-managed? — Atlas gives you Performance Advisor, Query Insights and Real-Time Performance Panel out of the box; self-managed means exporting serverStatus and $queryStats yourself. The metric list is the same; only the plumbing differs.
  • How do you keep this from becoming a wall of noise? — Every alert has an owner, a runbook and a documented action; anything without all three gets deleted rather than tuned.

Common wrong answer

"Set up dashboards for CPU, memory and disk." That is host monitoring, and it will tell you an incident happened, not that one is coming. The database-specific leading indicators — oplog window, cache dirty ratio, ticket availability, replication lag — are the whole point, and a principal-level answer names them.

10WiredTiger and storage internals

Asked less often than the first nine units, but asked hard when it comes up — usually as the follow-up chain behind a performance question ("why did that fix the latency?"). Screeners rarely go here; senior and principal candidates are expected to know how the cache, MVCC and checkpoints interact, because that is what explains the behaviours you meet on call: dirty-cache stalls, disk space not being returned after a delete, and why a long-running snapshot hurts everyone.

Docs: MongoDB Manual — WiredTiger Storage Engine

midWhat is WiredTiger and what did it change?

Answer

WiredTiger has been the only supported storage engine since 4.2, when MMAPv1 was removed; it became the default in 3.2. It is a B+-tree engine with document-level concurrency via multi-version concurrency control, a write-ahead journal, compression, and an internal cache separate from the operating system's page cache. What it changed, historically, is the whole concurrency story: MMAPv1 locked at the collection (and before 3.0, database) level, which is the origin of the "MongoDB has coarse locks" folklore that still shows up in interviews. In-memory storage exists as an Enterprise engine for specific latency-critical use cases, and the encrypted storage engine is likewise Enterprise. The practically important part is the cache: it defaults to 50% of (RAM − 1 GB), it holds uncompressed pages while disk holds compressed ones, and it is where almost all MongoDB performance questions eventually land — MongoDB 8.2 added the ability to configure it as a percentage of RAM, which matters for containers where absolute values age badly.

Example

storage:
  wiredTiger:
    engineConfig:
      cacheSizeGB: 48            # or, 8.2+: cacheSizePct for container-friendly sizing
    collectionConfig:
      blockCompressor: zstd      # 4.2+; better ratio than snappy at modest CPU cost
    indexConfig:
      prefixCompression: true    # default; big win on compound indexes

Follow-ups

  • Why not set the cache to 90% of RAM? — The OS page cache also holds compressed pages, and the process needs memory for connections, sorts and aggregation; over-sizing the cache causes swapping, which is far worse than a cache miss.
  • Does data in the cache stay compressed? — No: on disk compressed, in the WiredTiger cache uncompressed. That is why "my data is 200 GB compressed" says little about the RAM you need.
  • What happened to MMAPv1? — Deprecated in 4.0, removed in 4.2. Any advice you find that mentions it is at least seven years old — a useful filter when reading blog posts.

Common wrong answer

"MongoDB memory-maps the data files, so the OS manages memory." That was MMAPv1 and has been gone since 4.2. It leads directly to wrong answers about locking granularity and about how to size a node, and it is one of the fastest ways to reveal that your knowledge comes from old material.

seniorExplain MVCC and checkpoints in WiredTiger.

Answer

Every operation runs against a consistent snapshot: readers see the version of each document as of their snapshot's timestamp, and writers create new versions rather than overwriting in place, so readers never block writers and writers never block readers. Concurrent writers to the same document collide, and the engine resolves it with a write conflict — retried internally for ordinary writes, surfaced as a transient error inside a transaction. Every 60 seconds WiredTiger takes a checkpoint: a consistent, durable image of the data files, after which the journal before that point is no longer needed for recovery. The two consequences that matter operationally are that old versions must be retained as long as any snapshot might need them — which is why a long transaction, a long secondary read or a stalled majority commit point inflates cache usage — and that recovery time after a crash is bounded by the journal since the last checkpoint, not by the database size.

Example

const wt = db.serverStatus().wiredTiger;
wt.transaction["transaction checkpoint most recent time (msecs)"];
wt.cache["tracked dirty bytes in the cache"];      // history that cannot yet be evicted
wt.cache["pages evicted by application threads"];  // non-zero = eviction is stalling users

Follow-ups

  • What is "pages evicted by application threads" telling you? — Background eviction cannot keep up, so user threads are doing eviction work themselves; that is the signature of a cache-pressure stall.
  • How does the majority commit point interact with this? — WiredTiger must retain history back to it, so a lagging secondary directly increases the primary's cache pressure — the mechanism behind the P-S-A problem.
  • What is the stable timestamp? — The point WiredTiger can recover to; rollback-to-timestamp uses it, which is why rollbacks since 4.0 are fast and no longer produce large BSON files.

Common wrong answer

"Writers take a lock on the document." They do not — it is optimistic MVCC with conflict detection, not pessimistic locking. The distinction matters because it explains why hot-document contention shows up as CPU spent on retries rather than as threads blocked on a lock.

midHow does compression work and which compressor would you choose?

Answer

Collections are block-compressed on disk — snappy by default, with zstd (4.2+) and zlib available — and indexes use prefix compression, which is very effective on compound indexes where leading fields repeat. Typical ratios are 2–4x with snappy and meaningfully better with zstd at a modest CPU cost, which is usually a good trade on modern hardware and network- or IOPS-limited storage. The nuance to state is that compression saves disk and disk I/O, not RAM: the WiredTiger cache holds uncompressed pages, so compression does not shrink the working set. The setting is per collection and applies at creation, so changing it means recreating the collection (or an initial sync per member with the new default) — which is why it is worth deciding deliberately for large, write-heavy or archival collections rather than accepting the default everywhere.

Example

db.createCollection("events", {
  storageEngine: { wiredTiger: { configString: "block_compressor=zstd" } } });

db.events.stats().wiredTiger["block-manager"]["file size in bytes"];
db.events.stats().size;      // uncompressed logical size - the ratio is the interesting part

Follow-ups

  • When would you keep snappy? — CPU-constrained nodes, or very hot small collections where the decompression cost per read matters more than the space.
  • Does compression help query performance? — Indirectly: fewer bytes read from disk per page, so a cache miss is cheaper. It does nothing for a cache hit.
  • What compresses badly? — Already-compressed payloads (images, encrypted fields); storing those in documents wastes CPU on every write for no benefit.

Common wrong answer

"Compression means we need less RAM." It is the most common misconception in this area. Cache pages are uncompressed, so a 4x disk ratio buys you nothing at all in cache residency — a distinction that changes how you size a node.

seniorWe deleted half the collection and disk usage did not drop. Why?

Answer

Because deletes free space within the WiredTiger data files rather than returning it to the filesystem: the pages become reusable by that collection, so the file stays the same size. To return it you must rewrite the collection. compact does this in place and, since 4.4, without blocking reads and writes on the collection for the whole operation — but it needs free space to work in and its behaviour has changed across versions, so check the docs for the exact version rather than trusting a memory. The alternative, and the one I would generally reach for on a replica set, is a rolling resync: take one secondary out at a time, wipe its dbpath, let it initial-sync, and repeat, finishing with a stepdown and the old primary — that rewrites everything compactly with no risky in-place operation. And the design lesson to state: if a collection is expected to shed large volumes regularly, do not delete from it — partition by time into separate collections and drop them, which returns space instantly.

Example

db.runCommand({ compact: "events" });          // in place; needs headroom; check version notes
db.events.stats().wiredTiger["block-manager"]["file bytes available for reuse"];

// The structural answer: drop, do not delete.
db.getCollection("events_2026_07").drop();     // instant space return

Follow-ups

  • Does a TTL index return space? — No: TTL deletes are ordinary deletes, so a TTL-heavy collection grows its file and reuses it internally forever.
  • What about db.repairDatabase()? — A last-resort, standalone-only recovery tool, not a space-reclamation strategy; using it in production is a red flag.
  • Why is a rolling resync often preferable? — It exercises the same path as adding a member, produces a fully compact file, and never touches the primary in place; the cost is time and temporarily reduced redundancy.

Common wrong answer

"Run compact, it's fine now." It is much better than it used to be, but it still needs headroom and its blocking behaviour depends on the version — and, more importantly, it treats the symptom. A collection that regularly loses half its data should be time-partitioned, and saying so is what an interviewer is waiting for.

midWhat is BSON, and why does it matter?

Answer

BSON is the binary serialisation format MongoDB stores and transmits: JSON's data model plus types JSON lacks — ObjectId, Date, Decimal128, BinData, 32- and 64-bit integers, regular expressions — and length prefixes so a parser can skip fields without scanning them. It matters in three practical ways. Types are not JavaScript types: Decimal128 exists because double loses money, and Long exists because JSON numbers are doubles and lose precision above 2^53. Comparison order across types is defined by BSON, which is what produces type bracketing in queries. And field names are stored in every document, so short field names measurably reduce storage and cache footprint on very large collections — a real optimisation on billions of documents and premature everywhere else. Extended JSON is the lossless textual representation used by tools; MongoDB 8.3 added $serializeEJSON/$deserializeEJSON so you can move between them inside a pipeline.

Example

{ _id: ObjectId("64f0..."),      // 12 bytes: 4-byte timestamp, 5 random, 3 counter
  amount: NumberDecimal("19.99"),// exact base-10; never use double for money
  count: NumberLong("9007199254740993"),
  at: ISODate("2026-09-08T10:00:00Z"),
  blob: BinData(0, "...") }

// ObjectId carries its creation time - free "created at" and a rough range scan:
ObjectId("64f0...").getTimestamp();

Follow-ups

  • Is ObjectId a good _id? — Usually yes: small, unique without coordination, and time-ordered. That ordering is also its weakness as a shard key, since it is monotonic.
  • When would you use a custom _id? — When a natural key exists (a tenant-scoped id, an idempotency key); it saves an index and makes upserts idempotent for free.
  • Why is UUID v4 a poor _id at scale? — Random insertion order fragments the B-tree and destroys index locality; UUID v7 (time-ordered) avoids that and is the modern choice if you need a UUID.

Common wrong answer

"BSON is just JSON in binary for speed." The extra types are the point, not the encoding speed. Candidates who think it is only an encoding put money in doubles and 64-bit ids in JSON numbers, and both are silent data-corruption bugs.

seniorWhy does an update sometimes cost far more than the field you changed?

Answer

Because the unit of storage is the document. Changing one field means the whole document is re-serialised and rewritten into a new version, every index that covers a changed field is updated, and an oplog entry is generated and shipped to every secondary. The cost therefore scales with document size and index count, not with the size of your change. WiredTiger does have a delta-encoding optimisation for small updates to large documents, which reduces the write amplification, but the model to reason with is still "whole document per update". The design consequences are the ones to state: a two-megabyte document with a counter in it is a bad design because every increment rewrites two megabytes; hot, frequently updated fields belong in their own small document; and this is the real cost behind the unbounded-array anti-pattern, more than the 16 MB limit.

Example

// Bad: every view rewrites the whole document and its oplog entry.
{ _id: postId, body: "<200 KB of content>", tags: [...], views: 1_204_331 }

// Better: the hot counter is its own tiny document.
{ _id: postId, body: "...", tags: [...] }
{ _id: `views:${postId}`, views: 1_204_331 }

Follow-ups

  • How does this show up in metrics? — Oplog volume disproportionate to the logical write rate, and secondaries struggling to apply; measure bytes of oplog per operation.
  • Does $inc on one field avoid it? — It avoids sending the document over the wire, but the server still writes a new version of the document.
  • What about very large documents that are only read? — Fine; the cost here is specifically on the update path.

Common wrong answer

"MongoDB updates in place, so it only writes the changed field." In-place updates were an MMAPv1 concept (with padding factors and document moves) and do not describe WiredTiger's MVCC, where a write creates a new version. The practical consequence — do not put a hot counter inside a fat document — is what the question is really about.

11Security and access control

Increasingly asked, and asked with more edge than it used to be, because MongoDB's public reputation for exposed databases is a real thing an interviewer may probe. Screeners want authentication and authorisation basics; mid-level wants TLS, network exposure and encryption at rest; senior gets field-level encryption, injection and the patching conversation. Since December 2025 there is a very concrete anchor for the last one: MongoBleed.

Docs: MongoDB Manual — Security

screenerHow do authentication and authorisation work in MongoDB?

Answer

Authentication is off until you enable it (security.authorization: enabled), and the default mechanism is SCRAM — SCRAM-SHA-256 since 4.0, with SHA-1 still present for old drivers. Other mechanisms are x.509 certificates (common for internal cluster membership and for service accounts), and in Enterprise/Atlas, LDAP, Kerberos, AWS IAM and OIDC/workforce federation. Authorisation is role-based: users are created in a specific authentication database and granted built-in roles (read, readWrite, dbAdmin, clusterAdmin, root) or custom roles composed of individual actions on specific resources. The practices that matter are least privilege per service (an application user with readWrite on one database, never root), separate credentials per service so an incident is attributable, and — for internal traffic — keyfile or x.509 authentication between members, without which the members would trust anyone who can reach the port.

Example

db.createRole({ role: "ordersService", privileges: [
  { resource: { db: "app", collection: "orders" }, actions: ["find","insert","update"] },
  { resource: { db: "app", collection: "outbox" }, actions: ["find","insert"] } ],
  roles: [] });

db.createUser({ user: "svc-orders", pwd: passwordPrompt(),
                roles: [ { role: "ordersService", db: "app" } ] });

Follow-ups

  • What is the authentication database? — Where the user is defined (authSource in the connection string), independent of which databases they can access; getting it wrong is the most common "authentication failed" cause.
  • How do you rotate credentials without downtime? — Create the new user, roll the application, then drop the old one; x.509 makes it a certificate rotation, which is easier to automate.
  • What is field-level access control? — Not a built-in role feature; you achieve it with views (a read-only projected collection) plus a role granted only on the view.

Common wrong answer

"MongoDB has authentication on by default now." It does not for a self-managed mongod; what changed (in 3.6) is that it binds to localhost by default, so an unconfigured server is unreachable rather than unauthenticated. That distinction is exactly what produced years of exposed databases when people changed bindIp without enabling auth.

midHow do you secure a self-managed deployment end to end?

Answer

Layered, and in this order. Network: never expose 27017 to the internet — private subnets, security groups, and bindIp restricted to the interfaces that need it. Authentication: enabled, SCRAM-SHA-256 or x.509, with keyfile/x.509 for internal cluster authentication. Transport: TLS for client and intra-cluster traffic, with certificate validation actually on. Authorisation: least-privilege roles per service. At rest: encrypted storage — the Enterprise encrypted storage engine, or filesystem/volume encryption for Community, with keys in a KMS rather than on the box. Auditing: the Enterprise audit log for privileged actions. Patching: a defined SLA for security releases, which is the layer most teams have as an aspiration rather than a process — and the one MongoBleed punished, since Atlas clusters were patched automatically while self-managed ones sat exposed. I would also disable server-side JavaScript (security.javascriptEnabled: false) unless something genuinely needs it.

Example

net:
  bindIp: 10.0.1.11,127.0.0.1        # never 0.0.0.0 without a firewall in front
  tls: { mode: requireTLS, certificateKeyFile: /etc/ssl/mongod.pem,
         CAFile: /etc/ssl/ca.pem, allowConnectionsWithoutCertificates: false }
security:
  authorization: enabled
  clusterAuthMode: x509
  javascriptEnabled: false

Follow-ups

  • What does Atlas change here? — Network isolation (VPC peering or private endpoints), TLS and encryption at rest are defaults, auth cannot be disabled, and patching is automatic — which is a substantial part of its actual value proposition.
  • How do you handle secrets? — A secrets manager injecting the connection string at runtime, x.509 where possible, and rotation that does not require a deploy.
  • What about backups? — They contain everything the database does; encrypt them, restrict who can restore, and test restoration into an isolated environment.

Common wrong answer

"It's in a private VPC, so it's fine." Network isolation is one layer, and every large MongoDB breach involved something that was supposed to be private. The expected answer is defence in depth with authentication and TLS on regardless, because "internal" is a temporary property of any network.

seniorExplain client-side field level encryption and Queryable Encryption.

Answer

Both encrypt individual fields in the driver, so the server stores and returns ciphertext and a database administrator — or an attacker with the data files — cannot read them. CSFLE (4.2) supports deterministic encryption, which allows equality matching at the cost of leaking equality (identical plaintexts produce identical ciphertexts), and random encryption, which allows no querying at all. Queryable Encryption (GA in 6.0) is the newer scheme built on structured encryption: equality from 6.0, range queries GA in 8.0, and prefix, suffix and substring queries which entered preview in 8.2 and are generally available for 9.0 — where the API was renamed, with TextOpts replacing the preview TextPreview naming. Keys are per-field data keys wrapped by a customer master key in a KMS. The costs to name: ciphertext and metadata expansion, no server-side aggregation over encrypted fields, and index limitations — so encrypt the fields that genuinely need it (identifiers, health, payment data) rather than everything.

Example

// Queryable Encryption: the encrypted schema is declared once, per collection.
const encryptedFieldsMap = { "app.patients": { fields: [
  { path: "ssn",  bsonType: "string", queries: { queryType: "equality" } },
  { path: "dob",  bsonType: "date",   queries: { queryType: "range" } } ] } };

// The driver encrypts on write and rewrites the query on read - application code is normal:
await patients.findOne({ ssn: "123-45-6789" });

Follow-ups

  • Why is deterministic CSFLE encryption risky? — Equal ciphertexts leak the frequency distribution, so a low-cardinality field (a country, a diagnosis code) is effectively de-anonymisable by frequency analysis.
  • Does Queryable Encryption work with Community? — Yes for the driver-side scheme; it is not an Enterprise-only feature, and 8.2 extended the newer query types to Community and Enterprise Server as well as Atlas.
  • What breaks in your application? — Aggregations over encrypted fields, server-side sorting on them, and any reporting pipeline that expected to read them; plan the key management and the analytics story together.

Common wrong answer

"Encryption at rest covers it." Encryption at rest protects stolen disks; it does nothing against a compromised application, an over-privileged DBA, or a leaked backup that is restored somewhere with the key. Field-level encryption exists precisely because the threat models are different, and conflating them is the answer that fails a security-focused interviewer.

seniorIs NoSQL injection real? Show me one.

Answer

Very real, and it does not need string concatenation — it needs a request body being used as a query object. If a login handler does find({ user: req.body.user, pass: req.body.pass }) and the body is parsed JSON, an attacker sends {"pass": {"$ne": null}} and the filter becomes "any password that is not null". The same class covers $gt: "", $regex for blind extraction one character at a time, and $where or $function, which execute server-side JavaScript and turn injection into remote code execution — which is why javascriptEnabled: false is a real hardening step. Prevention is at the boundary: validate and coerce types before building any filter (a password must be a string, not an object), never pass a request body as a filter, use a schema validator, and prefer parameterised repository methods that construct the filter from typed values. Frameworks with query-string parsers (Express's extended query parser) turn ?pass[$ne]= into an object for free, which is how this reaches applications that never intended to accept JSON.

Example

// Vulnerable: the body becomes the filter.
db.users.findOne({ user: req.body.user, pass: req.body.pass });
// POST {"user":"admin","pass":{"$ne":null}}   -> logs in as admin

// Fixed: coerce, then build.
const user = String(req.body.user ?? ""), pass = String(req.body.pass ?? "");
const doc = await db.users.findOne({ user });
if (!doc || !(await verify(pass, doc.hash))) throw new AuthError();

Follow-ups

  • How do you find this in an existing codebase? — Grep for request objects reaching driver calls, and add a lint rule or a repository layer that only accepts primitives.
  • Is $regex from user input safe if you escape it? — Escaping helps against injection but not against ReDoS or full-scan cost; bound it and prefer anchored prefixes or a search index.
  • What does $function add to the risk? — Server-side JavaScript execution (4.4+), so an injected filter can run arbitrary code; disable JavaScript unless a specific workload needs it.

Common wrong answer

"There's no SQL, so there's no injection." The vulnerability is operator injection through structured input, and it is arguably easier than SQL injection because no quoting is involved — the attacker just sends an object. Answering "not applicable" is a security-interview fail.

principalA critical MongoDB CVE drops. What happens in your organisation?

Answer

I would answer this against MongoBleed, because it is the recent worked example everyone can check. CVE-2025-14847, disclosed December 2025: mismatched length fields in zlib-compressed protocol headers caused mongod to return uninitialised heap memory to an unauthenticated caller — credentials, tokens, previously queried documents — affecting 8.2.0–8.2.2, 8.0.0–8.0.16, 7.0.0–7.0.27, 6.0.x, 5.0.x, 4.4.x and everything older. A public exploit appeared on 26 December 2025, exploitation in the wild followed, it went into CISA KEV, and Censys found roughly 87,000 exposed instances. Atlas patched itself; self-managed did not. So: hour one, inventory — every cluster, its version, and its network exposure, which only works if you already have that inventory. Hour two, contain: block untrusted network access and, here specifically, disable zlib compression on the wire as a mitigation while patching. Then patch in dependency order — 8.2.3, 8.0.17, 7.0.28, 6.0.27, 5.0.32, 4.4.30 — secondaries first, then stepdown and primary, per cluster. Then rotate anything the leak could have exposed, because "we patched" is not "we are clean" for a memory-disclosure bug. Afterwards, the review question is not "why were we slow" but "why did we have 4.4 clusters at all", since half the exposure is always end-of-life versions nobody owns.

Example

// Inventory in one command per cluster - this must already be automated.
db.version(); db.serverStatus().host; db.adminCommand({ getCmdLineOpts: 1 });

// Rolling patch order, per replica set:
// secondaries one at a time -> rs.stepDown() on the primary -> patch the old primary
rs.stepDown(60);

Follow-ups

  • What is the difference between patching a replica set and a sharded cluster? — Order: config servers, then each shard, then the routers; the manual's upgrade sequence exists because doing it out of order breaks metadata compatibility.
  • How do you keep the version inventory honest? — Automated discovery reporting version and end-of-life date per cluster, with an owner; an inventory maintained by hand is wrong within a month.
  • What does the release cadence change since 8.2 mean for this? — Minor releases stop being patched as soon as the next minor ships, so a cluster on a minor version carries a standing obligation to upgrade; that is a policy decision, not an ops detail.

Common wrong answer

"Patch as soon as possible and monitor." True and empty. What the question is testing is whether you have an inventory, a containment step you can take before patching, a rolling procedure that does not cause an outage, and a rotation step afterwards. Naming MongoBleed's specifics is also the fastest available proof that you follow this ecosystem.

12Operations, backup and upgrades

Asked whenever the role has any on-call or platform component, and asked sharply of leads — because a lead is expected to have opinions about restore testing, upgrade cadence and end-of-life policy, not just about queries. The current-events hook here is MongoDB's changed release model: since 8.2 there are two-year majors with a five-year window and short-lived minors in between, and a minor stops being patched the moment the next minor ships. Knowing that is a version-policy question with a real operational consequence.

Docs: MongoDB Manual — Backup and Recovery

midHow do you back up MongoDB, and what are the trade-offs?

Answer

Three approaches. Filesystem or volume snapshots of a member's data directory — fast, cheap, and the standard for large deployments; they must be consistent (a point-in-time volume snapshot with journalling enabled, or the member stopped/fsync-locked), and for a sharded cluster the snapshots must be coordinated across shards and config servers or the restore is inconsistent. Logical dumps with mongodump/mongorestore — portable, selective, good for small data sets and for moving collections, but slow, not consistent across collections without --oplog, and rebuild-all-indexes on restore, which makes them impractical past a few hundred gigabytes. Continuous backup — Atlas Backup or Ops Manager, snapshots plus oplog capture, which is what gives you point-in-time recovery. The number I would quote is not "we back up nightly" but the tested RTO and RPO, and I would insist on scheduled restore drills, because an untested backup is a hypothesis.

Example

# Consistent logical dump from a secondary, capturing the oplog for a PIT restore.
mongodump --uri "$URI" --readPreference=secondary --oplog --gzip --archive=dump.gz
mongorestore --uri "$URI" --oplogReplay --gzip --archive=dump.gz

# Snapshot path: fsyncLock only if the volume snapshot is not atomic.
mongosh --eval 'db.fsyncLock()'   # ... take snapshot ... then db.fsyncUnlock()

Follow-ups

  • Why back up from a secondary? — It removes the I/O and cache impact from the primary; use a hidden member so no application traffic is affected either.
  • What makes a sharded backup hard? — Cross-shard consistency: you must stop the balancer and coordinate the snapshot moment across every shard and the config servers, or restore ranges that disagree.
  • How often do you test restores? — On a schedule, into an isolated environment, timed — the drill produces the RTO number you quote to the business.

Common wrong answer

"mongodump nightly to S3." Fine at 50 GB, unworkable at 5 TB — the restore alone takes days because every index is rebuilt — and it is not consistent across collections unless you captured the oplog. The interviewer is checking whether you have thought about restore time, which is the number that matters during an incident.

midHow do you upgrade a replica set, and what is the FCV?

Answer

Rolling, one member at a time, secondaries first: stop a secondary, replace the binary, restart, wait for it to be SECONDARY and caught up, repeat; then rs.stepDown() the primary and upgrade it last. The piece people miss is the feature compatibility version. After the binaries are upgraded, the cluster still runs with the previous FCV, which keeps new on-disk formats and features disabled so you can downgrade the binaries safely. You verify the application against the new binaries, then setFeatureCompatibilityVersion to the new value — and only then are you committed, because features written under the new FCV may not be readable by the old binaries. Two hard rules: you cannot skip major versions (7.0 to 9.0 means going through 8.0), and since 8.2 you cannot skip minor versions either (8.1 → 8.2 → 8.3, no jumping). On a sharded cluster the order is config servers, then shards, then mongos, with the balancer stopped throughout.

Example

db.adminCommand({ getParameter: 1, featureCompatibilityVersion: 1 });
// ... rolling binary upgrade, verify the application ...
db.adminCommand({ setFeatureCompatibilityVersion: "8.3", confirm: true });   // 7.0+ needs confirm
rs.stepDown(60);     // move the primary deliberately, at a time you choose

Follow-ups

  • Why not set the FCV immediately? — It is the point of no easy return; leaving it a version behind for a soak period is what makes the upgrade reversible.
  • What does the minor-release cadence imply? — Running a minor (8.1, 8.2, 8.3) means committing to upgrading again soon, because patches stop as soon as the next minor ships; running the major (8.0) buys a five-year window.
  • What breaks most often on a major upgrade? — Removed options and deprecated commands in operational scripts (background: true, removeShard), and driver versions too old for the new wire protocol.

Common wrong answer

"Upgrade the binaries and you're done." Skipping the FCV step means either you never get the new features or you get them without the deliberate soak, and skipping intermediate versions produces a cluster that will not start. The FCV is the single most commonly missed step, and interviewers know it.

seniorSomeone dropped a collection an hour ago. Recover it.

Answer

Point-in-time recovery: restore the most recent snapshot from before the incident, then replay the oplog forward to a moment just before the drop. That works only if you were capturing the oplog continuously — Atlas Continuous Backup or Ops Manager do it for you; self-managed means snapshots plus an oplog archive. So my sequence is: stop the bleeding (revoke the credentials that could do it again and freeze writes if the data is diverging), determine the exact timestamp of the drop from the oplog or the audit log, restore into a separate cluster rather than over production, replay to just before that timestamp, verify the collection, and then copy it back — because restoring over production to recover one collection destroys the hour of legitimate writes to everything else. If there is no oplog capture, the honest answer is that you lose everything since the last snapshot, and the retrospective action is that this gap existed at all.

Example

// Find the exact moment, if the oplog still covers it.
use local;
db.oplog.rs.find({ op: "c", "o.drop": "orders" }).sort({ ts: -1 }).limit(1);

// Restore to a side cluster, replay up to just before that ts, then copy the collection.
// mongorestore --oplogReplay --oplogLimit <ts> ...

Follow-ups

  • How do you prevent a recurrence? — Least-privilege roles (application users have no dropCollection), separate credentials for humans, and auditing on DDL.
  • What is the "drop is instant" trap? — drop is a fast metadata operation, so there is no window to interrupt it and no soft delete; renaming instead of dropping is a cheap safety habit for risky cleanups.
  • How long does PITR take? — Snapshot restore plus oplog replay; measure it in a drill, because that number is your actual RTO and it is almost always larger than people assume.

Common wrong answer

"Restore last night's backup." It recovers the collection and discards a day of everything else, which is frequently a worse incident than the original one. The senior move is restoring to a side cluster and copying back only what was lost.

midWhat is in the modern MongoDB toolbox, and what is deprecated?

Answer

mongosh replaced the legacy mongo shell — the old shell was deprecated in 5.0 and removed in 6.0; mongosh is a Node-based REPL with real autocompletion, syntax highlighting and support for modern JavaScript, and it is what any current answer should reference. The Database Tools (mongodump, mongorestore, mongoexport, mongoimport, mongostat, mongotop) ship separately from the server now and version independently. Compass is the GUI, with an aggregation-pipeline builder and a schema analyser that is genuinely useful for auditing an undocumented collection. mongosync is the supported cluster-to-cluster synchronisation tool for migrations — note that it does not support the new minor releases, only majors, which is a real constraint when planning a migration. And deprecated things to recognise in an old codebase: mapReduce (5.0), $eval, background: true index builds, the legacy mongo shell, and as of 8.3, removeShard.

Example

mongosh "mongodb+srv://cluster/app" --eval 'db.orders.countDocuments({})'
mongostat --uri "$URI" 5          # per-second op counters, a fast triage view
mongotop --uri "$URI" 5           # time spent per collection, read vs write

Follow-ups

  • Why did the tools split out of the server release? — So they can be updated independently and support multiple server versions; it also means "my tools are the same version as my server" is no longer a given.
  • What is mongosh's scripting story? — Real JavaScript with async/await and the ability to require modules, so operational scripts are no longer written against the old shell's peculiar semantics.
  • What replaced mongoreplay? — Nothing directly; workload capture and replay is now done with third-party tooling or by replaying application traffic.

Common wrong answer

"Use the mongo shell to connect." Removed in 6.0. It is a small thing, but it is an immediate signal about when you last used the product, and interviewers who use mongosh daily notice it within a sentence.

seniorHow do you size a cluster for a new workload?

Answer

From the working set and the write rate, not the total data size. I estimate: how much data is actually touched by the live workload (recent orders, active users) plus the indexes serving it — that sum should fit comfortably in the WiredTiger cache, which is about half of RAM; the sustained and peak write rate, which sets the oplog volume and therefore the oplog window and secondary requirements; the read concurrency, which sets CPU and ticket needs; and the growth rate, which sets when the answer changes. Then I add the operational headroom people forget: enough disk for an index build, a compact or a resharding operation (a second copy), and enough oplog for your longest realistic maintenance window. I would size for the peak the system must survive, not the average, and I would say plainly that the first estimate is a hypothesis to be corrected by a load test with production-shaped data — cache behaviour is not something you can compute from a spreadsheet.

Example

db.stats(1024*1024*1024);         // dataSize, indexSize in GB
db.orders.stats().indexSizes;      // per-index, so you can see what to remove
db.getReplicationInfo();           // current oplog window under today's write rate
// Rule of thumb to state and then test: working set + hot indexes < 0.5 x RAM.

Follow-ups

  • How do you estimate a working set before you have traffic? — From the access pattern doc: which time window or entity subset the queries touch, times the average document size, plus the indexes on those fields.
  • What disk do you specify? — Low-latency SSD/NVMe with provisioned IOPS; MongoDB is far more sensitive to random-read latency than to sequential throughput.
  • What do you do about spiky workloads? — Size for the spike or shed load at the edge; auto-scaling a database is slower than the spike, so it protects your bill, not your latency.

Common wrong answer

"Enough RAM to hold the whole database." Wasteful for large archival collections and irrelevant if the access pattern is narrow; it also skips the two things that actually bite — the oplog window and the disk headroom for maintenance operations.

principalWhat is your version and end-of-life policy for a fleet of clusters?

Answer

A written policy with an owner, because the alternative is what MongoBleed exposed: organisations discovering they had 4.4 clusters nobody remembered. Mine would be: run majors, not minors, as the default — 8.0-style majors get a five-year window and predictable patching, while minors stop receiving patches as soon as the next minor ships and cannot be skipped when upgrading, which is a continuous obligation most teams should not take on. Minors are for teams that specifically need a new capability (self-managed Search on 8.2, the Cost-Based Ranker on 8.3) and can commit to the cadence. Then: no cluster more than one major behind; upgrade begins within a defined window of a new major, not "when there is time"; security patches within days, tracked as an SLA; an automated inventory that reports version and end-of-life per cluster with an owner; and end-of-life dates on the same roadmap as feature work, so the upgrade is funded rather than being an unbudgeted emergency. The measure of the policy is not compliance on paper but how quickly you could answer "which clusters are affected?" during a CVE.

Example

// The inventory line that a policy needs, produced automatically per cluster:
// cluster        | version | FCV | EOL        | owner        | exposure
// prod-orders    | 8.0.17  | 8.0 | 2029-10-31 | orders-team  | private
// prod-analytics | 7.0.28  | 7.0 | 2027-08-31 | data-eng     | private
// legacy-crm     | 4.4.30  | 4.4 | ENDED      | unowned      | investigate

Follow-ups

  • How do you make upgrades cheap enough to happen? — Automate the rolling procedure, rehearse it on a restored copy, and run it often enough that it is routine; upgrades that are rare are always risky.
  • What about the FCV backlog? — Track FCV separately from binary version; a fleet on new binaries with old FCVs is a half-finished upgrade and it hides feature-availability surprises.
  • How do you handle a team that refuses? — Make the risk theirs and visible: end-of-life status on the service's own dashboard, and a named accountable owner. Escalation is a last resort; visibility usually suffices.

Common wrong answer

"Stay on the latest version." Expensive, and with the post-8.2 cadence it means signing up for a minor upgrade every few months across the whole fleet. The considered answer distinguishes majors from minors and states which one is the default and why.

13Drivers and application integration

The bridge between the database questions and the engineering ones, and where a lot of real production pain actually lives: pool sizing, timeouts, retry semantics and ODM choices. Interviewers ask this to see whether you treat the driver as a configured component with failure modes or as a black box that "just connects". Language specifics matter less than the concepts, which are the same across every official driver.

Docs: MongoDB — Drivers

midWhat does the driver do behind a connection string?

Answer

Rather a lot. It performs server discovery and monitoring: it connects to the seeds, learns the full topology from the hello response, and monitors every member with periodic heartbeats, so it always knows who the primary is. It maintains a connection pool per server, does server selection for each operation based on read preference and latency, and implements retryable reads and writes, which is why a failover is usually invisible. mongodb+srv:// resolves the seed list and options from DNS SRV and TXT records, which is how Atlas hands you a topology that can change without a config change. The practical consequence to state is that the driver client is expensive to construct and is designed to be a long-lived singleton — creating one per request is the classic mistake, and it defeats every one of these mechanisms while creating a connection storm.

Example

// One client for the process lifetime; never per request.
const client = new MongoClient(uri, {
  maxPoolSize: 20, minPoolSize: 2, maxIdleTimeMS: 60000,
  serverSelectionTimeoutMS: 5000, connectTimeoutMS: 5000,
  retryWrites: true, retryReads: true, appName: "checkout-api" });
await client.connect();

Follow-ups

  • What does serverSelectionTimeoutMS control? — How long the driver waits for a suitable server before failing; the default (30 s in most drivers) is far too long for a web request and should usually be a few seconds.
  • Which operations are retryable? — Single-document writes and most reads; updateMany/deleteMany are not, because they are not idempotent.
  • What does +srv cost? — A DNS dependency at connect time; a DNS outage becomes a database outage, which is worth knowing before it happens.

Common wrong answer

"The connection string points at the primary." It points at the set; the driver discovers the primary and re-discovers it after every election. Believing otherwise leads to hard-coding a host, which turns every failover into an outage.

midHow do you size a connection pool?

Answer

Total connections across the fleet is what the server sees, so the arithmetic is instances × maxPoolSize, and that number should be comfortably under the server's capacity — a few thousand at most, and far fewer for smaller instances. The default maxPoolSize of 100 is a single-application default, not a Kubernetes default: sixty pods at 100 is six thousand connections, each costing the server a thread and about a megabyte. The right size is close to the concurrency each instance genuinely needs, which is bounded by its own thread or event-loop model and the latency of the operations — Little's law, roughly: concurrency = throughput × latency. Then set minPoolSize to avoid cold-start latency, maxIdleTimeMS so idle connections are reclaimed, and a short serverSelectionTimeoutMS so failures are fast rather than queued. Serverless platforms need explicit thought: either connection reuse across invocations or a proxy, because the naive pattern storms the cluster on any spike.

Example

// 200 req/s per pod at 10 ms average -> ~2 concurrent ops; 20 is generous headroom.
maxPoolSize: 20, minPoolSize: 2, waitQueueTimeoutMS: 2000
db.serverStatus().connections;    // verify against reality: current vs available

Follow-ups

  • What happens when the pool is exhausted? — Operations wait for a connection up to waitQueueTimeoutMS, then fail; a growing wait queue is the signal that either the pool is too small or the database is too slow.
  • Does a bigger pool increase throughput? — Only up to the server's concurrency limit (storage-engine tickets); beyond that it converts latency into queueing and memory.
  • How does this interact with mongos? — Each mongos maintains its own pools to every shard, so router count multiplies connections at the shards too.

Common wrong answer

"Leave the default, the driver handles it." The default is per-client and knows nothing about how many clients you run. It is the direct cause of most connection-exhaustion incidents in containerised deployments, and the interviewer usually has one in mind.

midDo you use an ODM like Mongoose, and what does it cost?

Answer

Situationally. An ODM buys application-level schema definition, validation, casting, middleware hooks and population — real value on a team that would otherwise have no schema discipline at all. The costs are three, and they are worth naming precisely: it encourages a one-model-per-collection design that reproduces a relational schema in a document store; populate() looks like a join but is N+1 queries issued by the client, which is much worse than $lookup and far worse than modelling; and it adds a layer between you and the query, so the actual command sent is not obvious when you are debugging a slow query. My position is that an ODM is fine for validation and typing, and that the data-access layer should still be written in terms of the access patterns — with raw driver calls for anything performance-sensitive, especially aggregations. In typed languages the equivalent question is the official driver's POCO/POJO mapping versus hand-written serialisation, with the same trade-offs at lower intensity.

Example

// populate() is N+1 round trips - fine for 10 documents, ruinous for 10,000.
const posts = await Post.find({ authorId }).populate("comments");

// Model it, or aggregate deliberately, and know which you chose.
db.posts.aggregate([{ $match: { authorId } },
  { $lookup: { from: "comments", localField: "_id", foreignField: "postId",
               pipeline: [{ $limit: 20 }], as: "comments" } }]);

Follow-ups

  • Where should validation live? — Both: the ODM for developer feedback, $jsonSchema on the collection for the invariants that must hold no matter which service writes.
  • How do you see what an ODM actually sent? — Enable the driver's command monitoring or the ODM's debug mode, and cross-check against the slow-query log.
  • What about transactions through an ODM? — Supported, but the session must be threaded through every call; the usual bug is an ODM call that quietly runs outside the session.

Common wrong answer

"Mongoose gives MongoDB a schema, so it fixes the schemaless problem." It gives your application a schema, enforced only by the code that uses it — another service, a script or the shell writes whatever it likes. And it does nothing about the modelling problem; if anything it makes relational-shaped modelling easier to fall into.

seniorHow do you set timeouts so a slow database does not take the application down?

Answer

Bound every layer, and make the bounds nest correctly. connectTimeoutMS and socketTimeoutMS bound the network; serverSelectionTimeoutMS bounds how long the driver waits for a suitable server (crucially, this is the one that governs behaviour during a failover); waitQueueTimeoutMS bounds waiting for a pooled connection; and maxTimeMS — the important one — bounds execution server-side, so the server actually stops doing the work rather than the client walking away while the query continues to consume resources. Newer drivers unify this behind a single timeoutMS (client-side operation timeout) which propagates to all of the above, and it is the modern recommendation. Each must be shorter than the caller's own deadline, or a slow database turns into thread exhaustion upstream. And a timeout is not a result: the operation may have succeeded, so anything retried must be idempotent.

Example

// Server-side bound: the server abandons the work too.
db.orders.find(q).maxTimeMS(2000);

// Modern unified form, propagated to selection, connection and execution:
const client = new MongoClient(uri, { timeoutMS: 3000, serverSelectionTimeoutMS: 3000 });
await coll.findOne(q, { timeoutMS: 500 });   // per-operation override

Follow-ups

  • Why is maxTimeMS different from a client timeout? — A client timeout abandons the response; the server keeps executing. maxTimeMS makes the server give up, which is what protects the cluster.
  • What should a web request's database budget be? — A fraction of the endpoint's SLO, so a slow query fails fast and the endpoint degrades rather than hanging.
  • How do timeouts interact with retries? — Multiply: a 2-second timeout with two retries is a 6-second worst case. Budget the total, not the attempt.

Common wrong answer

"Set a socket timeout." It only closes the connection; the server keeps running the query, so under a slow-query incident you get the worst of both — the client retries, the server accumulates abandoned work, and load climbs. maxTimeMS (or the unified timeoutMS) is the answer the question is looking for.

seniorHow do you test code that talks to MongoDB?

Answer

Against a real MongoDB, in a container, at every level above unit tests — because the interesting failures are semantic (index usage, unique constraints, aggregation behaviour, upsert races) and no fake reproduces them. Testcontainers or a disposable local instance per test run, seeded with fixtures, with each test isolated by using its own database name so tests can run in parallel. In-memory fakes such as the various "mock MongoDB" packages diverge from real behaviour in exactly the places that matter — aggregation semantics, index enforcement, type coercion — so a green suite tells you nothing. Two things I add beyond correctness: an explain-based assertion in CI that the hot queries do not COLLSCAN, which catches a missing index at review time rather than in production; and a test that exercises the failover path (step the primary down mid-test) for anything with a durability requirement. Replica-set-in-a-container is required anyway if the code uses transactions or change streams, since neither works on a standalone.

Example

// A CI guard that costs nothing and catches the most common production regression.
const plan = await coll.find(hotQuery).explain("queryPlanner");
expect(plan.queryPlanner.winningPlan.inputStage.stage).not.toBe("COLLSCAN");

// Transactions and change streams need a replica set, even a single-node one:
// mongod --replSet rs0 --port 27017  &&  rs.initiate()

Follow-ups

  • How do you keep tests fast with a real database? — One container per suite, a database per test, and truncation rather than re-seeding; container startup dominates, so amortise it.
  • What do you still unit-test with fakes? — Pure logic above the repository boundary; the repository itself is integration-tested.
  • How do you test migrations? — Against a restored production-shaped fixture, asserting both the outcome and the runtime, because a migration that works but takes six hours is a failed migration.

Common wrong answer

"Mock the driver so tests are fast." You end up asserting that your code calls the methods your code calls. Every genuine MongoDB bug — a wrong index, a broken aggregation, a unique-constraint violation, a filter that matches nothing — passes straight through a mock.

14Change streams and event-driven MongoDB

Asked whenever the role touches integration, CDC or event-driven architecture, and asked as a design question rather than an API question: interviewers want to know whether you understand the delivery guarantees, because that is what determines whether the downstream system is correct. Five questions is right for the frequency — it comes up in maybe a third of loops, but when it comes up it goes deep.

Docs: MongoDB Manual — Change Streams

midWhat is a change stream and what guarantees does it give?

Answer

A change stream (3.6+) is a cursor over the changes to a collection, database or the whole deployment, built on the oplog but exposed with a stable API and — critically — a resume token on every event. Requirements: a replica set or sharded cluster (not a standalone), and readConcern: "majority", which means you only ever see majority-committed changes, so a change stream never emits something that is later rolled back. The delivery guarantee is at-least-once with total ordering: if you persist the resume token with the side effect it produced and restart with resumeAfter, you get every change from that point, possibly re-delivering the last one — so consumers must be idempotent. The limit that shapes designs is that resumption is bounded by the oplog window: if your consumer is down longer than that, the token is invalid and you must resynchronise from a full read, which is why startAfter and invalidate handling matter.

Example

const stream = db.orders.watch(
  [ { $match: { operationType: { $in: ["insert", "update"] }, "fullDocument.status": "paid" } } ],
  { fullDocument: "updateLookup", resumeAfter: savedToken });

for await (const ev of stream) {
  await handleIdempotently(ev);                     // side effect first...
  await tokens.updateOne({ _id: "orders" },         // ...then checkpoint
                         { $set: { token: ev._id } }, { upsert: true });
}

Follow-ups

  • Why checkpoint after the side effect, not before? — Because at-least-once is the guarantee you can build on; checkpointing first turns a crash into a lost event, which nothing downstream can detect.
  • What does fullDocument: "updateLookup" cost? — An extra read per update, fetching the current document — which may already have changed again, so it is not a snapshot of the post-update state.
  • What is fullDocumentBeforeChange? — The pre-image (6.0+), available when changeStreamPreAndPostImages is enabled on the collection; it costs storage, and pre-images expire.

Common wrong answer

"It's exactly-once because of the resume token." The token gives you resumability, not exactly-once — a crash between the side effect and the checkpoint replays the event. Every correct design here says "idempotent consumer" out loud; an interviewer who does not hear it will ask about the crash.

midHow do you filter a change stream efficiently?

Answer

With an aggregation pipeline passed to watch(), containing $match, $project, $addFields, $replaceRoot, $redact and $unset — the pipeline runs server-side, so filtered-out events never cross the network. Filter on operationType, on fields of fullDocument, and — the one people miss — on updateDescription.updatedFields, so you react only to changes to the fields you care about rather than to every write to the document. The important caveat is that filtering does not reduce the server's work of reading the oplog, only the transfer and client-side processing, so a very chatty collection is expensive to watch even with a narrow filter. Watching a whole database or deployment is possible and correspondingly heavier; scoping to one collection is the default I would defend.

Example

db.users.watch([
  { $match: { operationType: "update",
              "updateDescription.updatedFields.email": { $exists: true } } },
  { $project: { _id: 1, docId: "$documentKey._id",
                email: "$updateDescription.updatedFields.email" } }
]);

Follow-ups

  • Can you filter on the pre-image? — Yes, if pre-images are enabled for the collection; that is how you detect a transition ("status went from pending to paid") rather than just the new value.
  • What happens on a collection drop or rename? — An invalidate event closes the stream; handle it explicitly rather than treating it as an error, and restart with startAfter.
  • How many change streams can you run? — Each is a cursor with its own oplog scan; dozens are fine, hundreds against a hot collection are a load-planning question.

Common wrong answer

"Watch everything and filter in the application." It ships every change over the network and burns client CPU on events you discard, and on a busy collection it will be the thing that falls behind. Server-side filtering is free to write and materially cheaper.

seniorDesign a reliable CDC pipeline out of MongoDB.

Answer

Change stream in, idempotent sink out, with the resume token stored transactionally with the consumer's own progress. The shape: a single consumer per collection partition (change streams are ordered, so parallelism means partitioning by document key, not competing consumers on one stream); the resume token persisted in the same store as the side effect where possible, so recovery is exact; a dead-letter path for events the sink rejects; and a monitored lag metric — the age of the last processed event — because a silently stalled consumer is the failure mode. For the "consumer was down too long" case I need a documented resynchronisation path: full read of the collection with a snapshot, then resume from a token captured before the read started. If I do not want to own this, the managed options are the MongoDB Kafka Connector, Atlas Stream Processing or Atlas Triggers — worth naming, along with the fact that all of them inherit the same at-least-once, oplog-window-bounded semantics, so the design constraints do not go away.

Example

// Capture the token BEFORE the backfill so nothing is missed in between.
const token = (await db.orders.watch().next())._id;   // or watch().resumeToken
await backfillEverything();                            // full snapshot read
const stream = db.orders.watch([], { startAfter: token });

Follow-ups

  • Why can you not run two consumers on the same stream for throughput? — Ordering is per stream; two consumers would interleave and break causal order. Partition by documentKey hash into separate streams instead.
  • What lag metric do you alert on? — Wall-clock age of the last processed event's cluster time, not queue depth — it is the one number that captures both slowness and stalls.
  • How does this interact with the oplog window? — The window is your maximum consumer downtime; alert when it drops below your recovery time, not when a consumer is already lost.

Common wrong answer

"Poll the collection for documents with updatedAt greater than the last watermark." It misses deletes, misses changes within a clock tick, depends on every writer maintaining the field, and re-scans an index constantly. It is the pattern change streams exist to replace, and proposing it in 2026 signals unfamiliarity.

midChange streams or the oplog directly?

Answer

Change streams, essentially always. Tailing local.oplog.rs yourself was the pre-3.6 technique and it survives in old codebases and a few tools; the reasons not to do it are concrete. The oplog's format is internal and has changed across versions (transactions produce applyOps entries that must be unwound; large transactions span multiple entries since 4.2). You must handle failover and re-election yourself, including finding your position on a new primary. You see uncommitted operations that could be rolled back. And on a sharded cluster you must tail every shard and merge, with no global ordering. Change streams solve all of that: a stable API, majority read concern, resume tokens that survive failover, cluster-wide ordering, and server-side filtering. The only remaining reasons to touch the oplog are forensic — finding when a collection was dropped, for instance.

Example

// Forensics: legitimate direct oplog use.
use local;
db.oplog.rs.find({ ns: "app.orders", op: "d" }).sort({ ts: -1 }).limit(5);

// Everything else:
db.orders.watch([], { fullDocument: "updateLookup" });

Follow-ups

  • Is there a performance argument for the oplog? — Marginally lower overhead, comprehensively outweighed by having to reimplement correctness.
  • How do transactions appear in a change stream? — As individual change events carrying a common lsid and txnNumber, so you can group them if you need transactional boundaries downstream.
  • What about tools like Debezium? — Its MongoDB connector uses change streams for exactly these reasons; the ecosystem has converged.

Common wrong answer

"Tail the oplog, that's how CDC works for MongoDB." True in 2016. It signals that your reference material predates 3.6, and the follow-up about transactions and applyOps usually confirms it.

seniorWhat are the operational risks of building on change streams?

Answer

Four. Oplog window as a hard deadline: a consumer down longer than the window cannot resume, and the window shrinks exactly when the system is busiest — so alert on the window, not on the consumer. Silent stalls: a change stream that stops delivering looks identical to a quiet collection, so a heartbeat or last-event-age metric is mandatory, not optional. Load on the source: many streams over a hot collection each scan the oplog, and pre-images add storage and write cost. Coupling: downstream systems now depend on your document shape, so a schema change becomes a cross-team event — which is an argument for publishing a deliberate event contract from an outbox rather than exposing raw documents. I would also note that pre- and post-images have their own retention, so a consumer that needs them has a second, shorter deadline than the oplog window.

Example

// The two alerts that matter, in the order they save you:
db.getReplicationInfo().timeDiffHours;             // oplog window vs your recovery time
// consumer: now() - lastProcessedEventClusterTime  // stall detection

// Decouple the contract from the document shape:
{ $set: { status: "paid" }, $push: { outbox: { type: "OrderPaid", v: 1, at: new Date() } } }

Follow-ups

  • How do you recover a consumer that missed the window? — Full resynchronisation with a token captured first; it must be a rehearsed, documented procedure, because it will be needed at a bad moment.
  • What is the cost of pre-images? — Extra storage in a system collection plus write amplification, with their own expiry — so enable them per collection, never globally.
  • Why prefer an outbox event over the raw change? — It is a versioned contract you can evolve; raw documents make every internal field a public API.

Common wrong answer

"They're managed by MongoDB so they're reliable." They are reliable within their stated guarantees, and every operational risk above is in the space those guarantees do not cover. The senior answer is about the operational envelope, not the feature.

15Time series, TTL and special collections

A narrower area, asked when the role involves telemetry, IoT, metrics or financial ticks — but asked confidently by interviewers who work in those domains, and a real differentiator because many candidates have never used time series collections. Five questions covers it: what they are, when they beat a hand-rolled bucket pattern, how expiry works, and the special collections you should recognise.

Docs: MongoDB Manual — Time Series Collections

midWhat is a time series collection and when do you use one?

Answer

A collection type (5.0+) optimised for measurements over time: you declare a timeField, an optional metaField identifying the series, and a granularity, and MongoDB stores the data internally in columnar buckets grouped by metadata and time window. The benefits are substantial — often an order of magnitude less storage thanks to columnar compression, and much faster range and aggregation queries — and MongoDB's own benchmarks put 8.0's time series query performance more than 200% ahead of 7.0. You use one when the shape genuinely is "measurements arriving in time order, queried by series and time range": metrics, IoT readings, ticks, events. You do not use one when documents are updated frequently, when there is no natural series identifier, or when you need the full flexibility of a normal collection — updates and deletes are supported (5.0/6.0 onwards) but they are not the design centre. Sharded time series arrived in 5.1.

Example

db.createCollection("readings", {
  timeseries: { timeField: "ts", metaField: "sensor", granularity: "minutes" },
  expireAfterSeconds: 60 * 60 * 24 * 90 });     // 90-day retention, bucket-level expiry

db.readings.insertOne({ ts: new Date(), sensor: { id: "d-17", site: "LHR" },
                        temp: 21.4, humidity: 44 });
db.readings.createIndex({ "sensor.id": 1, ts: 1 });

Follow-ups

  • What does granularity control? — The bucket time span; mismatching it with your ingest interval produces either too many tiny buckets or oversized ones. 6.3+ lets you specify bucketMaxSpanSeconds/bucketRoundingSeconds directly for finer control.
  • Why is the metaField important? — It is the grouping key for buckets and the natural index prefix; choosing it badly (something high-cardinality and unrelated to your queries) removes most of the benefit.
  • How does expiry differ from a TTL index? — Whole buckets are dropped once every measurement in them is expired, which is far cheaper than per-document deletes and does not generate a delete storm.

Common wrong answer

"It's just a normal collection with a TTL index." The storage layout is different — columnar buckets rather than one document per measurement — which is where the compression and the query speed come from. Treating it as a naming convention means you will also miss the constraints, such as the design assumption of append-mostly data.

midTime series collection or a hand-rolled bucket pattern?

Answer

Time series collections, unless you need something they do not do. The bucket pattern — one document per series per time window, with an array of measurements — was the standard advice before 5.0 and is still all over existing codebases; it works, but you own the bucketing logic, the bucket-full handling, the index design and the expiry, and you get none of the columnar compression. The remaining reasons to hand-roll are: you need to update individual measurements frequently in place; your bucketing key is not "metadata plus time"; you are on a version predating the feature you need; or you need a document shape the time series constraints do not allow. In an interview I would name the pattern, say it is legacy for this purpose, and then say what would make me still choose it — the qualification is what shows judgment rather than fashion-following.

Example

// Legacy bucket pattern - recognise it, and know what it costs you.
{ sensorId: "d-17", hour: ISODate("2026-09-08T14:00:00Z"), count: 3600,
  min: 20.1, max: 23.8, sum: 77_412.0,      // pre-computed, because scanning is expensive
  readings: [ { t: 0, v: 21.4 }, { t: 1, v: 21.5 } ] }

// Modern equivalent: one document per measurement, bucketed by the engine.
db.createCollection("readings", { timeseries: { timeField: "ts", metaField: "sensorId" } });

Follow-ups

  • How do you migrate from the pattern to the collection type? — Read, $unwind the arrays, insert into the new collection; it is a rewrite, not an ALTER, so plan it as a dual-write and cutover.
  • What about the computed rollups the bucket pattern carried? — Keep them, in a separate rollup collection maintained with $merge; a time series collection is fast, but a dashboard still wants pre-aggregation.
  • Do window functions work on time series collections? — Yes, and $densify/$fill pair naturally with them for gap handling.

Common wrong answer

"Bucket pattern — that's the MongoDB way for time series." It was, until July 2021. Recommending it now without qualification means giving up an order of magnitude of storage and a large chunk of query performance, and it dates your reference material precisely.

midHow would you implement data retention at scale?

Answer

By dropping rather than deleting, wherever the shape allows. A TTL index is the easy answer and it is right for moderate volumes, but understand what it does: a background thread sweeping every 60 seconds on the primary, issuing real deletes that hit the oplog and every secondary, and never returning disk to the filesystem. At high volume that is a continuous background write load and a permanently inflated data file. The alternatives are far better: a time series collection with expireAfterSeconds, which expires whole buckets; or time-partitioned collections (events_2026_09) created by a scheduled job and dropped wholesale, which returns space instantly and costs nothing at expiry. Above that sits archival — Atlas Online Archive or an export to object storage queried through Data Federation — for data that must be retained but not served. Whatever I choose, retention becomes a documented policy with an owner, because "we'll clean it up later" is how a 40 TB collection happens.

Example

// Moderate volume: fine.
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 86400 });

// High volume: partition and drop.
db.getCollection(`events_${ym}`).insertMany(batch);
db.getCollection(`events_${oldYm}`).drop();      // instant, no oplog storm, space returned

Follow-ups

  • Why does a TTL sweep sometimes fall behind? — It processes a bounded amount per pass; if the expiry rate exceeds it, the backlog grows and documents outlive their TTL by a long way.
  • How do you query across partitioned collections? — $unionWith, or a view over the union; the application must know which partitions to touch, which is the cost of the approach.
  • What about compliance deletion (GDPR)? — TTL is not a deletion guarantee — it is approximate and primary-only. For a legal deletion requirement you need an explicit, verified deletion process, including backups.

Common wrong answer

"Add a TTL index, done." It works and then quietly becomes the largest single source of write load on the cluster, while the disk never shrinks. The interviewer is listening for whether you know that deletes in MongoDB are not free and do not return space.

midWhat are capped collections and views, and when do you meet them?

Answer

A capped collection is a fixed-size, insertion-ordered ring buffer: once full, the oldest documents are overwritten. The oplog is one; system.profile is another. You cannot delete individual documents, updates must not grow a document, and they cannot be sharded — so for application use they are almost always the wrong tool today, and a TTL index or a time-partitioned collection is the right one. A view is a stored aggregation pipeline over a collection, read-only and computed on demand — useful for exposing a projected or filtered subset with a role granted only on the view, which is how you do field-level access control. A materialised view in MongoDB is not a feature at all: it is a real collection maintained by a scheduled $merge, and calling it a feature is a small but real accuracy point. From 7.0 there are also on-demand materialised views in the same sense — the pattern, made routine.

Example

// A view as an access-control boundary: the role is granted on the view only.
db.createView("patients_deidentified", "patients",
  [ { $project: { name: 0, ssn: 0, address: 0 } } ]);

// "Materialised view" = a collection plus a scheduled $merge. There is no magic.
db.orders.aggregate([ ...rollup, { $merge: { into: "daily_revenue" } } ]);

Follow-ups

  • Can you index a view? — Not directly; the underlying collection's indexes are used by the view's pipeline, so a view over an unindexed filter is a scan every time.
  • Is a view a security boundary? — It can be, with roles granted only on the view and not the source; it is only as strong as the role configuration behind it.
  • Why do capped collections still exist? — Internal uses like the oplog, and a small number of legitimate fixed-size log cases; recognise them rather than reaching for them.

Common wrong answer

"Use a capped collection for logs, it self-manages." It self-manages by silently destroying data with no time guarantee — you get "the last N bytes", not "the last 7 days" — and it cannot be sharded when the volume grows. A TTL index or time-partitioned collections give you a policy you can actually reason about.

seniorDesign ingestion for a million measurements per minute.

Answer

Roughly 17,000 writes a second, which is very achievable but only with the right shape. A time series collection with a well-chosen metaField and a granularity matched to the ingest interval; unordered bulkWrite batches of a few hundred to a few thousand from each producer, with w: 1 because a lost sample is cheaper than a doubled latency; the minimum number of indexes — every index multiplies the write cost, and on ingest that is the dominant term. Sharding by { metaField, ts } if one replica set cannot hold the write rate, deliberately avoiding a purely time-based key so inserts do not all land on one shard. Retention via bucket-level expiry, and rollups maintained by a scheduled $merge so dashboards never scan raw data. The two things I would watch during the ramp are oplog volume — because at this rate the oplog window shrinks fast and every secondary must apply all of it — and cache dirty percentage, which is the first thing to move when ingest outruns the disk.

Example

db.createCollection("readings", {
  timeseries: { timeField: "ts", metaField: "sensor", granularity: "seconds" },
  expireAfterSeconds: 7 * 86400 });
sh.shardCollection("iot.readings", { "sensor.id": 1, ts: 1 });   // not ts alone

await readings.insertMany(batch, { ordered: false, writeConcern: { w: 1 } });
db.getReplicationInfo().timeDiffHours;   // the number that shrinks first at this rate

Follow-ups

  • Why is w: 1 defensible here and not for payments? — Loss tolerance: a dropped sample is noise in an aggregate, whereas a dropped payment is a defect. State the tolerance rather than assuming it.
  • What if late-arriving data is common? — Buckets are time-windowed, so very late arrivals create extra buckets and hurt compression; either buffer upstream or accept the cost and measure it.
  • Where would you put a queue? — Between producers and MongoDB, so ingest spikes and database maintenance are decoupled; the database should never be the backpressure mechanism for a firehose.

Common wrong answer

"Shard on the timestamp so the data spreads over time." It spreads over time and concentrates in space: at any instant all inserts target the shard owning the newest range, so you have one hot shard and N-1 idle ones. It is the textbook monotonic shard key mistake, and this question is designed to elicit it.

16Search, Vector Search and AI workloads

The fastest-moving corner of the topic, and increasingly asked because so many teams are building retrieval on the database they already have. It is "sometimes asked" overall but close to certain if the role mentions AI, search or personalisation. The recency facts here carry a lot of weight: MongoDB acquired Voyage AI in February 2025 for its embedding and reranking models, Search and Vector Search left Atlas for self-managed deployments in 8.2 and reached GA on 30 June 2026 free in Community, mongot's source was published under SSPL, and $scoreFusion went GA in 8.3.

Docs: MongoDB — Vector Search

midHow does vector search work in MongoDB?

Answer

You store an embedding — an array of floats — as a field on the document, define a vectorSearch index over it declaring the dimensions and the similarity function (cosine, euclidean or dotProduct), and query with the $vectorSearch aggregation stage as the first stage of a pipeline. It builds an HNSW graph in mongot, the same Lucene-based process that serves $search. The parameters that matter are numCandidates (how many nodes the approximate search explores — the recall/latency dial, typically 10–20× your limit) and limit; exact: true switches to exhaustive nearest-neighbour, which is correct but linear and only sensible on small filtered sets. The property that sells the whole approach is pre-filtering: the filter clause is applied inside the vector index, so "documents similar to this, but only for tenant 42 and in stock" is one query — not a vector search followed by a post-filter that returns nothing.

Example

db.products.aggregate([
  { $vectorSearch: {
      index: "vec_idx", path: "embedding",
      queryVector: queryEmbedding,        // same model, same dimensions, always
      numCandidates: 200, limit: 10,
      filter: { tenantId: 42, inStock: true } } },   // pre-filter, inside the index
  { $project: { name: 1, score: { $meta: "vectorSearchScore" } } }
]);

Follow-ups

  • Why is co-locating vectors with the data an advantage? — No separate vector database to keep in sync, no dual-write consistency problem, and filters on operational fields work natively — that is MongoDB's actual argument, and it is a good one.
  • What is the 8.2/2026 change? — Vector Search runs on self-managed deployments (public preview in 8.2, GA 30 June 2026), free in Community, via the separate mongot binary — so it is no longer an Atlas-only capability.
  • Where do embeddings come from? — Any model; MongoDB's own are Voyage AI's (the voyage-4 family, with voyage-4-nano open-weight), and Atlas offers automated embedding generation so the pipeline does not have to call an API itself.

Common wrong answer

"Store the vectors and use $lookup or a normal index to find similar ones." A B-tree cannot answer nearest-neighbour queries; there is no ordering in 1,536 dimensions to index. Without a vectorSearch index you are computing similarity per document, which is a full scan with arithmetic on top.

midWhen do you use $search, $vectorSearch, or neither?

Answer

find for exact and range predicates on structured fields — always the cheapest and the only one with transactional freshness. $search for lexical relevance: keyword matching with analysers, synonyms, fuzzy tolerance, autocomplete and faceting, where the user's words appear in the text. $vectorSearch for semantic similarity: "find things that mean this", where the words may not overlap at all. In practice a good search product uses at least two of them, because they fail differently — lexical search cannot match "laptop bag" to "notebook sleeve", and vector search cannot reliably match an exact SKU. That is exactly what hybrid search and $scoreFusion are for. Both search stages share two properties worth stating: each must be the first stage of the pipeline because it executes in mongot, and both are eventually consistent, so neither can serve read-your-own-writes.

Example

// Hybrid: lexical and semantic, fused by the engine (8.2; GA in 8.3).
db.products.aggregate([
  { $scoreFusion: {
      input: { pipelines: {
        lexical:  [ { $search: { index: "text_idx",
                       text: { query: q, path: ["name","description"] } } }, { $limit: 50 } ],
        semantic: [ { $vectorSearch: { index: "vec_idx", path: "embedding",
                       queryVector: qv, numCandidates: 200, limit: 50 } } ] } },
      combination: { weights: { lexical: 0.4, semantic: 0.6 } } } },
  { $limit: 20 }
]);

Follow-ups

  • What did people do before $scoreFusion? — Hand-rolled reciprocal rank fusion with $unionWith and manual score arithmetic; recognising that pattern in an existing codebase and knowing it is now a stage is a good signal.
  • How do you evaluate which is better? — Offline with a labelled relevance set (recall@k, NDCG), then online with interleaving or an A/B test; "it looks better" is not an answer at senior level.
  • What about reranking? — A cross-encoder reranker over the top 50 candidates usually beats any amount of fusion-weight tuning; Voyage's rerank models are the in-house option.

Common wrong answer

"Vector search is strictly better, use it for everything." It is worse than lexical search at exact identifiers, product codes, names and rare terms, and it cannot explain itself. Teams that replace keyword search wholesale with embeddings usually ship a regression on the queries users care most about.

seniorYou have 50 million vectors and the index does not fit in memory. What do you do?

Answer

Quantisation, first. Fifty million 1,536-dimension float32 vectors is roughly 300 GB of raw vector data before the graph. Scalar quantisation maps each float to an 8-bit integer for about 4× compression with small recall loss; binary quantisation maps each to one bit for about 32× compression, which works well for high-dimensional models (1,024 dimensions and up) and poorly for small ones. MongoDB can do this automatically at index time with the quantization option, or ingest already-quantised vectors from the embedding provider; the standard recipe is binary quantisation plus rescoring — retrieve a wider candidate set cheaply, then re-rank the top ones against full-fidelity vectors. Compensate for the recall loss by raising numCandidates and measuring recall against an exact search on a held-out sample, rather than guessing. Beyond that: reduce dimensions by choosing a smaller model (Matryoshka-style truncation where the model supports it), filter aggressively so the graph traversal is over a smaller subset, and only then add hardware or shard.

Example

// Automatic binary quantisation at index build; keep full fidelity for rescoring.
{ fields: [ { type: "vector", path: "embedding", numDimensions: 1536,
              similarity: "cosine", quantization: "binary" },
            { type: "filter", path: "tenantId" } ] }

// Measure, do not assume: recall of the ANN result against exact:true on a sample.
{ $vectorSearch: { ..., exact: true, limit: 10 } }   // ground truth for the sample

Follow-ups

  • When is quantisation not worth it? — Under roughly 100,000 vectors, where everything fits comfortably and the recall loss buys nothing.
  • What does raising numCandidates cost? — Latency, roughly linearly in graph exploration; it is the dial you trade against recall, and it should be set from measurement.
  • Does filtering help memory? — It reduces the traversal, not the index size; the memory fix is quantisation or fewer/smaller vectors.

Common wrong answer

"Add more RAM." Sometimes necessary, but it skips a 4–32× reduction that is one index option away, and it does not scale with the collection. An answer that does not mention quantisation has not operated a vector index at this size.

seniorDesign a RAG system on MongoDB.

Answer

Ingestion: chunk the source documents deliberately — semantic or structural boundaries rather than fixed character counts — store each chunk as a document with its text, its embedding, its source metadata and a stable id, and re-embed on change driven by a change stream so the index never drifts from the source. Retrieval: hybrid search ($scoreFusion) over lexical and vector pipelines with a pre-filter for tenancy and permissions, then a reranker over the top candidates, then assemble the context. Three things I would insist on. Permissions must be a pre-filter, never a post-filter — filtering after retrieval both leaks (through the model's context) and silently returns nothing for restricted users. Store the retrieval trace — which chunks, which scores — with each answer, because otherwise you cannot debug a bad answer or measure a change. Evaluate offline with a labelled set before shipping any retrieval change. The architectural argument for MongoDB here is that the chunks, the vectors, the metadata and the permissions live in one place with one consistency story, rather than in a database plus a vector store that must be kept in sync.

Example

{ _id: "doc-91#c-14", docId: "doc-91", chunk: 14,
  text: "...", embedding: [/* 1024 floats */],
  acl: ["team-platform", "role-admin"],      // pre-filter, not post-filter
  source: { url: "...", updatedAt: ISODate() }, embedModel: "voyage-4", v: 3 }

db.chunks.watch([{ $match: { "updateDescription.updatedFields.text": { $exists: true } } }]);
// -> re-embed and update in place; the index follows automatically.

Follow-ups

  • How do you handle a model change? — Embeddings from different models are not comparable, so a model change is a full re-embed; version the model on the document (embedModel) and run both indexes during the cutover.
  • How do you chunk? — By structure where it exists (headings, sections), with overlap, and with the parent document's context prepended; measure the effect on retrieval quality rather than picking a number.
  • What is the freshness guarantee? — Eventually consistent: mongot follows the change stream, so a just-written chunk is not immediately searchable. Design the UX around that.

Common wrong answer

"Chunk at 512 tokens, embed, cosine search, done." That is the tutorial, and it fails on exactly the things production RAG fails on: permissions, freshness, re-embedding on change, and having no way to tell whether a retrieval change helped. Naming the evaluation loop is the senior differentiator here.

seniorWhat does running Search self-managed actually involve?

Answer

A second process. mongot runs alongside mongod, follows a change stream to keep its Lucene indexes current, and answers $search and $vectorSearch when mongod routes those stages to it. So you now operate two systems with two resource profiles: mongot is memory-hungry in its own right (Lucene indexes, HNSW graphs), needs its own disk, and has its own failure modes — most importantly indexing lag, which presents to users as "my document is not searchable yet". You must monitor that lag, size the host for both processes or separate them, include the search indexes in your capacity and backup planning, and handle the bootstrap when a new index has to backfill an entire collection. This went from preview in 8.2 (September 2025) to GA on 30 June 2026, free in Community under SSPL, with mongot's source published — which is why "we can't use Atlas so we can't have search" stopped being a valid position over a year ago.

Example

// mongod is told where mongot lives; the search stages are routed to it.
// mongod --setParameter mongotHost=127.0.0.1:27027 ...

db.products.createSearchIndex("vec_idx", "vectorSearch", { fields: [
  { type: "vector", path: "embedding", numDimensions: 1024, similarity: "cosine" } ] });
db.products.getSearchIndexes();     // status: PENDING -> BUILDING -> READY

Follow-ups

  • What is the freshness lag in practice? — Sub-second to seconds under normal load, longer during bulk writes or an index build; monitor it as a first-class metric, not an afterthought.
  • How does it behave on a replica set? — mongot follows a member; plan which member and what happens on failover, because a search outage is not automatically covered by your database HA story.
  • Atlas or self-managed? — Atlas removes the operational burden entirely; self-managed is the answer when data residency, cost or platform constraints make Atlas impossible — and it is now a genuine option rather than a workaround.

Common wrong answer

"Search is built into MongoDB now, so it's just another index." It is a separate process with a separate resource profile and a separate lag; treating it as an index means nobody sizes it, nobody monitors indexing lag, and the first symptom is users reporting missing results with every dashboard green.

principalYour team wants a dedicated vector database. What is your position?

Answer

I would ask what problem the dedicated store solves that the existing one does not, and make the default "use what we already run" unless the answer is specific. The costs of a second store are concrete and always underestimated: a dual-write or CDC pipeline with its own consistency and backfill problems, two permission models to keep aligned, two backup and DR stories, two things to patch, and the loss of pre-filtering across operational and vector data in a single query — which is the capability people most often discover they needed after the split. The cases where a dedicated store genuinely wins are scale far beyond what the operational cluster should carry, a need for index types or algorithms MongoDB does not offer, or a team that already operates one well. Otherwise, keeping vectors next to the documents means one query, one consistency story, one backup. And I would frame the decision as reversible in one direction only: it is much easier to move out of MongoDB later than to unpick a dual-write pipeline that has been running for a year.

Example

// The capability that disappears the moment vectors live elsewhere:
{ $vectorSearch: { ..., filter: { tenantId: 42, acl: { $in: userRoles },
                                  status: "published", deletedAt: null } } }
// In a split architecture this is: query vector store -> filter results -> discover
// the top-k are all filtered out -> re-query with a larger k -> repeat.

Follow-ups

  • How do you make the decision reviewable? — Write down the specific requirement that MongoDB cannot meet, with a number attached; if nobody can supply one, the answer is already known.
  • What if the team has already started? — Let them prove the requirement with a benchmark on real data and a real filter workload; benchmarks without filters flatter the dedicated store enormously.
  • What would change your mind? — Vector volume an order of magnitude beyond the operational cluster's sizing, or a genuinely unsupported algorithm — and I would say so upfront so the position does not read as territorial.

Common wrong answer

"Specialised tools are better, so use a vector database." It is the argument that ignores the cost of the seam. At principal level the expected reasoning is about the integration cost, the permission model and the pre-filtering capability — not about which engine has the better benchmark on an unfiltered ANN query.

17Migration and the relational comparison

Rarely the core of a MongoDB loop, but almost always present as one or two questions — often the opening icebreaker ("so why MongoDB rather than Postgres?") and sometimes the closing judgment question. It is a trap in both directions: dismissing relational databases marks you as a zealot, and conceding everything marks you as someone who does not know what document modelling buys. Four questions is the right weight.

Docs: MongoDB Manual — SQL to MongoDB Mapping

midHow would you migrate a relational schema to MongoDB?

Answer

Not table by table. The first step is to identify the aggregates — the units the application actually loads and saves together — which usually collapse a group of tables (order, order_lines, shipping_address) into one document, while other tables that were only ever joined incidentally stay separate collections. The second step is the access-pattern list: every query the application issues, with frequency and latency budget, because that is what decides embed-versus-reference. Only then do you design collections and indexes. For the migration itself: dual writes or CDC from the relational source into MongoDB, a backfill, a comparison period where reads are served from the old system while the new one is validated, then a per-access-pattern read cutover, then stop writing to the old store. What I would refuse is the "lift and shift" migration that creates one collection per table and reproduces the joins with $lookup — it delivers all of the migration risk and none of the benefit, and it performs worse than the database it replaced.

Example

-- Relational: 3 tables, 2 joins, 1 round trip if you are careful.
orders(id, customer_id, placed_at, status)
order_lines(id, order_id, sku, qty, unit_price)
order_addresses(order_id, line1, city, postcode)
// Document: 1 aggregate, 0 joins, 1 round trip always.
{ _id: 1001, customerId: 42, placedAt: ISODate(), status: "paid",
  lines: [ { sku: "C-2M", qty: 2, unitPrice: 9.99 } ],
  shipTo: { line1: "1 High St", city: "London", postcode: "N1 1AA" } }

Follow-ups

  • What about the reporting queries that relied on joins? — They usually do not survive the move as-is; plan rollups, or keep the relational store for reporting during and after the migration.
  • What tooling exists? — mongosync for MongoDB-to-MongoDB, Relational Migrator for schema and data mapping from relational sources, plus ordinary CDC tooling; all of them still need the model designed first.
  • How do you validate correctness? — A comparison period reading from both and reporting divergence per access pattern, with a divergence budget agreed before cutover.

Common wrong answer

"One collection per table, then use $lookup where we had joins." The most common failed MongoDB migration in existence: you inherit a design tuned for a join engine and run it on a database with a nested-loop join and no query optimiser for joins. If the model does not change, the migration has no upside.

midWhen is MongoDB the wrong choice?

Answer

When the data is genuinely relational and the queries are unpredictable: many-to-many relationships everywhere, and analysts writing ad hoc joins across a dozen entities — a relational engine's cost-based optimiser and join algorithms are a real, mature advantage there and MongoDB has nothing equivalent. When the workload is analytical: large scans, aggregations across the whole history, columnar access patterns — that is a warehouse or a lakehouse, not an operational document store. When the domain requires cross-entity transactional invariants constantly, rather than occasionally, so almost every operation is a multi-document transaction. And when the team has deep relational expertise, a small and stable schema, and no scaling pressure — "we know how to run Postgres" is a legitimate engineering argument. What I would not concede are the obsolete objections: no transactions (since 4.0), no schema enforcement (validators since 3.2), no joins ($lookup since 3.2), and no window functions (since 5.0).

Example

// The shape that argues for a document store: one aggregate, read as a unit,
// variable structure, high write volume, queries always scoped by one entity.

// The shape that argues against it: this query, written by a different analyst
// every week, against eight entities, with no predictable access pattern.
// SELECT ... FROM a JOIN b JOIN c JOIN d ... GROUP BY ... HAVING ...

Follow-ups

  • What about "we might need to scale later"? — A weak argument on its own; a well-run relational database scales a long way, and premature distribution costs more than it saves.
  • Is "flexible schema" a good reason by itself? — Only when the flexibility is real and ongoing (genuinely varying documents, frequent shape evolution); "we don't know the schema yet" usually means the modelling has not been done.
  • How do you argue for MongoDB honestly? — Aggregate-shaped data read as a unit, a schema that evolves continuously, horizontal write scaling, and geographic distribution — those are the ones that hold up.

Common wrong answer

"MongoDB can do everything, there's no wrong choice." It fails the judgment test instantly. Interviewers ask this specifically to see whether you can criticise the technology you are being hired for; a candidate with no honest limitations to offer is a candidate who has not hit any.

seniorMongoDB or PostgreSQL with JSONB?

Answer

The honest answer is that the document-model gap has narrowed a lot and the differences are now mostly operational. JSONB gives you documents with GIN indexes, plus real joins, a mature cost-based optimiser, strict constraints and every relational tool that exists — an excellent choice when the data is mostly relational with some flexible parts, and when your team already runs Postgres well. MongoDB's remaining advantages are the ones that show up at scale and in operations: built-in horizontal sharding with online resharding, replica sets with automatic failover as the default deployment rather than an add-on, a query language designed around documents (so nested arrays and updates to them are first-class rather than function calls), change streams, and integrated search and vector search in the same query. Postgres's advantages are joins, constraints, the optimiser and the ecosystem. My decision rule: if the aggregate is the unit of work and horizontal scale or geographic distribution is a real requirement, MongoDB; if the relational structure is real and the flexibility is a subset of the model, Postgres with JSONB. What I would not do is claim a decisive technical win either way — that is the answer of someone selling, not deciding.

Example

-- Postgres: capable, but nested array updates are function calls on a blob.
UPDATE orders SET doc = jsonb_set(doc, '{lines,0,qty}', '3') WHERE id = 1001;
CREATE INDEX ON orders USING GIN (doc jsonb_path_ops);
// MongoDB: the array is a first-class citizen of the query language.
db.orders.updateOne({ _id: 1001, "lines.sku": "C-2M" }, { $set: { "lines.$.qty": 3 } });

Follow-ups

  • What about sharding Postgres? — Citus and similar exist and work, but sharding is native, online-reshardable and first-class in MongoDB, and that difference is operational rather than theoretical.
  • What about vector search? — pgvector is good and widely deployed; MongoDB's advantage is integration with the operational filter and permission data in one query, not the ANN algorithm itself.
  • Which is cheaper to operate? — Whichever your team already operates; the dominant cost is expertise, and saying so is usually the most credible line in the answer.

Common wrong answer

"JSONB is just a blob, MongoDB is a real document database." Comprehensively out of date: JSONB is indexed, queryable and path-addressable. Dismissing it makes you sound like you have not evaluated the alternative, which is the actual thing being tested — whether your technology choices are informed or tribal.

principalHalf your estate is MongoDB, half is SQL Server. How do you decide what goes where?

Answer

With a written default and an exception process, not a per-team debate every time. My default is: a service owns its data in one store; the store is chosen by data shape and access pattern — aggregate-shaped, evolving, horizontally scaled goes to MongoDB; relational, constraint-heavy, ad hoc-queried goes to the relational store; analytics goes to neither and lives in the warehouse. Then the rules that stop the estate degrading: no shared databases between services, no dual writes without a documented consistency story (they will diverge and you will find out from a customer), and cross-store consistency handled by events with idempotent consumers rather than distributed transactions. I would also be explicit about the cost of two ecosystems — two backup and DR stories, two sets of on-call expertise, two patching cadences — and either accept it deliberately for the value it provides or consolidate. The failure mode I am designing against is not having both; it is having both by accident, with nobody able to say which one a new service should use.

Example

// The decision record every new service fills in, in one screen:
// service | data shape        | access pattern      | scale need | store   | exception?
// orders  | aggregate         | by customer, by id  | high write | mongo   | -
// billing | relational, strict| ad hoc + reporting  | moderate   | sqlsrv  | -
// search  | derived           | text + semantic     | high read  | mongo   | -

Follow-ups

  • How do you handle a service that genuinely needs both? — One is the source of truth and the other is a derived projection maintained by events; never two writable copies.
  • What do you do about the existing dual writes? — Inventory them, measure divergence, and convert them to source-of-truth-plus-projection one at a time; do not attempt a big-bang consolidation.
  • When would you consolidate to one engine? — When the operational cost of two exceeds the fit benefit — usually a function of team size, not of technology.

Common wrong answer

"Use the right tool for the job." Correct and useless: it is what every team says while making inconsistent choices. What is being tested is whether you can turn that platitude into a written default, an exception process and a rule about who owns which data — the mechanism, not the sentiment.

18Atlas, cloud and cost

The least-asked unit, and included because it comes up reliably in two situations: the company runs on Atlas and wants to know you can operate it, or the company is deciding whether to move and wants your judgment on the trade. Four questions is honest weighting — do not over-prepare this at the expense of schema design and indexing.

Docs: MongoDB Atlas Documentation

midAtlas or self-managed — how do you decide?

Answer

By pricing the operational work honestly. Atlas gives you automated backups with point-in-time recovery, automated patching (which MongoBleed made worth real money — Atlas clusters were patched without customer action while self-managed instances sat exposed for weeks), rolling upgrades, monitoring with Performance Advisor and Query Insights, one-click sharding and resharding, and integrated Search and Vector Search. Self-managed gives you control, potentially lower infrastructure cost at large scale, and no data-residency or vendor questions — at the price of employing people who know how to do all of the above, and doing it at 3am. My rule of thumb: below the scale where you would employ a dedicated database team, Atlas almost always wins on total cost including salary; above it, the calculation depends on how good your platform team already is. The 2026 wrinkle is that the historical "we need Search so we need Atlas" argument is gone, since Search and Vector Search have been GA for self-managed deployments since 30 June 2026.

// infrastructure cost + (engineer-days/year for patching, backups, upgrades,
//   incident response, capacity work) x loaded cost
//   + the cost of the incident you have not had yet
// vs Atlas list price minus the same engineer-days.

Follow-ups

  • What does Atlas not solve? — Your schema, your indexes and your queries. The most expensive Atlas bills are almost always a modelling problem, not a pricing problem.
  • What about lock-in? — The database is the same MongoDB; the lock-in is in the surrounding services (Triggers, Data Federation, Stream Processing, Online Archive), so use those deliberately.
  • Data residency? — Atlas runs in most regions on three clouds, and Global Clusters handle residency by zone; it is a solvable constraint rather than an automatic disqualifier.

Common wrong answer

"Self-hosting is cheaper." Only if engineering time is free. The honest comparison includes patching, backup verification, upgrade projects and out-of-hours incidents — and, since December 2025, the specific question of how many days your self-managed clusters were exposed to MongoBleed.

midWhat drives an Atlas bill, and how do you reduce it?

Answer

Instance size across all members (you pay for the whole replica set, so a three-node M40 is three M40s), storage and IOPS, backup retention, data transfer — especially cross-region and cross-AZ — and the add-on services. The reductions that work, in order of impact: fix the schema and the indexes, because an oversized cluster is usually compensating for a working set inflated by unused indexes and unbounded documents; drop unused indexes, which shrink both storage and the cache requirement; archive cold data with Online Archive or a partition-and-drop policy, so you are not paying premium storage to hold last year; right-size after measuring rather than before, and use auto-scaling with a ceiling so a runaway query cannot buy you a bill; and keep application and cluster in the same region to stop paying for transfer. I would also point out that the biggest single lever is usually a query nobody has looked at — Performance Advisor exists precisely to find it.

Example

// The two queries that usually pay for themselves within a week:
db.collection.aggregate([{ $indexStats: {} }, { $sort: { "accesses.ops": 1 } }]);
db.aggregate([{ $queryStats: {} }, { $sort: { "metrics.execTimeMicros.sum": -1 } },
              { $limit: 10 }]);

Follow-ups

  • How does auto-scaling behave? — It scales compute within a configured range on sustained utilisation, with a cooldown; it is protection against gradual growth, not against a spike, and it should always have a ceiling.
  • Are Flex/serverless tiers useful? — For development, spiky low-volume workloads and prototypes; the per-operation pricing model becomes unpredictable at steady high volume.
  • What is the cheapest capacity win nobody takes? — Deleting or hiding unused indexes: less storage, smaller working set, faster writes, and no application change.

Common wrong answer

"Downsize the cluster." Without fixing the cause you get an outage instead of a saving. Cost work on a database is schema and index work; the instance size is the symptom, and interviewers who own a budget know it.

seniorWhat Atlas features change how you design an application?

Answer

A handful genuinely do, and it is worth being precise because each is also a lock-in decision. Global Clusters — managed zone sharding with location-aware routing — change your shard key permanently, so they are a design-time choice, not an operational one. Online Archive changes retention design: cold data moves to object storage and is still queryable through a federated endpoint, so "delete or keep" becomes "keep cheaply". Atlas Search and Vector Search change whether you need a separate search system at all. Triggers and Stream Processing change whether you run consumer infrastructure for change streams. Data Federation changes where analytics can run. The judgment to show is that each of these is a real capability with a real coupling cost, so I would adopt the ones whose value is large and whose replacement path is clear — Search, Online Archive — and be more careful with the ones that embed themselves in application logic, like Triggers, where the migration path off is a rewrite.

Example

// Global Clusters make the location field part of the shard key - permanently.
sh.shardCollection("app.users", { region: 1, userId: 1 });
// Online Archive: the same query, transparently spanning hot and archived data.
// (federated endpoint; slower, cheaper, still MongoDB Query API)

Follow-ups

  • Which has the worst migration path off? — Triggers and Stream Processing, because business logic ends up living in the platform; Search and Archive have clear self-managed or self-built equivalents.
  • Does Online Archive affect query semantics? — Archived data is read through a federated endpoint with much higher latency and no writes; design the access pattern accordingly.
  • How do you keep the option to leave? — Keep application logic in the application, use the platform for infrastructure concerns, and write down what a migration off would cost while the decision is fresh.

Common wrong answer

"Atlas is just hosted MongoDB." For the database, largely true; for the platform features, not at all — and the ones that change your shard key or hold your business logic are architectural commitments. Treating them as conveniences is how a "we can move any time" assumption quietly becomes false.

seniorDoes the SSPL licence matter to you?

Answer

For almost every user, no; for a specific class, decisively. MongoDB moved from AGPL to the Server Side Public License in October 2018 to prevent cloud providers from offering MongoDB as a managed service without contributing back; the SSPL is not OSI-approved, and several Linux distributions dropped MongoDB packages as a result — which is why installing it means adding MongoDB's own repository. The obligation only bites if you offer MongoDB itself as a service to third parties, in which case section 13 requires releasing the entire service's source. Using MongoDB as the database behind your own product, at any scale, triggers nothing. The parts worth knowing beyond the basics: the drivers are Apache 2.0, so client code is unaffected; Enterprise Advanced is a separate commercial licence for features like the audit log and the encrypted storage engine; and mongot — the engine behind Search and Vector Search — was published under SSPL in 2026 as part of bringing those capabilities to Community. I would raise it in a legal or platform-vendor context and not otherwise.

Example

# The practical consequence for most people: the distro package is not the real one.
curl -fsSL https://www.mongodb.org/static/pgp/server-8.0.asc | gpg --dearmor ...
# Ubuntu/Debian/RHEL dropped MongoDB from their own repositories after the SSPL change.

Follow-ups

  • Does SSPL affect a SaaS product using MongoDB? — No, as long as you are not offering MongoDB's own functionality as the service; that distinction is the whole of section 13.
  • What are the alternatives if a policy forbids SSPL? — FerretDB (a Postgres-backed MongoDB-compatible layer), DocumentDB-style API-compatible services, or a genuinely different database; each has real compatibility gaps to test.
  • Why do interviewers ask this at all? — Usually because they hit it — an internal open-source policy, a distribution question, or a vendor conversation — and want to know you will not be surprised by it.

Common wrong answer

"MongoDB is open source." It is source-available under a licence the OSI does not approve, which is precisely why distributions dropped it. Getting this wrong in a company with an open-source policy is a small factual error with disproportionate consequences.

19Judgment calls

Open-ended questions with no single right answer, asked from senior level upwards to see how you reason under ambiguity. There is no answer hidden in these blocks — instead, what a strong response demonstrates and which trade-offs the interviewer expects you to name without being prompted. The failure mode in every one of them is a confident universal rule; the winning move is a decision framework, a stated default, and the specific evidence that would change it.

Docs: MongoDB Manual — Schema Design Anti-Patterns

seniorEmbed or reference — and what would make you change your mind six months later?

What a strong answer demonstrates

That you decide from access patterns and then name the observable signal that would reverse the decision, rather than treating the model as permanent. A strong answer states a default ("embed when the child is bounded, read with the parent and written at the same rate; reference otherwise"), then gives the tripwires: document size approaching a few hundred kilobytes, an array without a domain-level bound, write amplification visible as oplog volume out of proportion to logical writes, or a new access pattern that reads the child on its own. It also treats the reverse migration as a known cost with a known procedure — dual writes, backfill, cutover — rather than as a disaster.

Trade-offs to name unprompted

  • One read versus N reads, against rewriting the whole parent on every child change.
  • Atomicity for free inside one document, against contention when many writers touch it.
  • Duplication as a deliberate purchase of read latency, with a reconciliation job as its maintenance cost.
  • That the 16 MB limit is the cliff, but write amplification is what actually hurts long before it.
principalWhen is it right to shard, and when is it an expensive way to avoid fixing a query?

What a strong answer demonstrates

Diagnosis before architecture. The strong version separates the three problems people bring to sharding — data too big for one node, writes beyond one primary, working set beyond RAM — and points out that only the first two are actually solved by it. It names the checks that come first (indexes, archived cold data, vertical scaling, unused index removal), gives a default ("shard when the write rate or data size genuinely exceeds one replica set, and shard early enough to choose the key deliberately"), and acknowledges honestly that MongoDB 8.0 lowered both the entry cost, through embedded config servers, and the correction cost, through practical online resharding — so the historical "never shard until you must" advice is softer than it was.

Trade-offs to name unprompted

  • Every unaligned query becomes a scatter-gather; you can make reads worse while making writes better.
  • Operational surface: config servers, routers, balancer behaviour, cross-shard backups, distributed incidents.
  • The shard key is a design decision with a months-long shadow, and choosing it under duress is how it goes wrong.
  • Sharding late is expensive; sharding early is expensive too, just in a different currency.
seniorHow much duplication is too much?

What a strong answer demonstrates

That "duplication" is not one thing. A strong answer separates historical facts — the price at time of purchase, the address a parcel went to — which must be duplicated because they are not copies at all, from caches of a mutable source, which carry a fan-out obligation. For caches, the limit is set by the fan-out: how many documents change when the source changes, how often that happens, and whether you have a reconciliation mechanism. A senior answer quantifies at least one of those ("duplicating a display name across ten million documents means a ten-million-document update per rename, so we do not") and pairs every duplication with a detection story, because divergence you cannot see is worse than divergence you planned for.

Trade-offs to name unprompted

  • Read cost versus write cost versus consistency window — you are buying one with the other two.
  • Fan-out size and frequency as the actual limit, not an abstract normalisation principle.
  • Every duplicate needs an owner, a refresh mechanism and a reconciliation job, or it will silently drift.
  • Duplication also removes cross-shard lookups, which can be the entire justification on a sharded cluster.
seniorTransactions or a redesign?

What a strong answer demonstrates

That the question is really about where the invariant lives. A strong answer starts by asking whether the invariant could live in one document — because if it can, the atomic single-document update is faster, simpler and contention-free — then falls back to compare-and-set with a version field for optimistic concurrency, then to a saga with an outbox for anything crossing a service boundary, and only then to a transaction. It states honestly that transactions are a legitimate tool for genuinely cross-entity invariants like money movement, and names their costs specifically: snapshot retention and cache pressure, write conflicts under contention, a 60-second lifetime, and much higher cost across shards.

Trade-offs to name unprompted

  • Correctness guarantees against throughput and cache pressure on the whole node, not just that operation.
  • Redesigning the model is a bigger change now and a smaller cost forever.
  • Cross-shard transactions are two-phase commit with a blocking prepare window — a shard-key design input.
  • A transaction cannot make a non-idempotent operation safe to retry; that is a separate problem.
seniorReads are slow. Do you add an index, change the model, or scale the hardware?

What a strong answer demonstrates

A diagnostic order rather than a preference. The strong version measures first: is it one query shape or everything (opLatencies, $queryStats)? Is the index missing, or present and unselective (totalKeysExamined versus nReturned)? Is the working set resident (cache eviction and bytes-read-into-cache)? Only then does it choose, and it explains the cost of each option — an index is a permanent write-side tax, a model change is expensive now and structural, hardware is immediate and recurring. A good answer also notes that adding an index is the reversible option and a model change is not, which is a legitimate reason to sequence them that way.

Trade-offs to name unprompted

  • Indexes buy read latency with write throughput and cache — the count is a budget.
  • Hardware buys time, not a fix, and the bill recurs monthly.
  • A model change is the only option that changes the asymptotics, and the only one that needs a migration plan.
  • Doing all three at once means you learn nothing about which one worked.
principalA team wants a separate database for their new service. Yes or no?

What a strong answer demonstrates

That you have a default and an exception process rather than an instinct. A strong answer usually defaults to "yes to a separate logical database with its own credentials and its own collections; no to a separate cluster unless there is a specific reason", and names the reasons that would justify a cluster: isolation of a noisy or risky workload, a genuinely different availability or residency requirement, a different scaling profile, or a compliance boundary. It weighs the costs honestly — more clusters means more patching, more backup verification, more monitoring, more per-cluster overhead — and against them the benefit that a blast radius is smaller and ownership is clearer. It also states the non-negotiable: no shared collections between services, because that is the coupling that makes every future change a cross-team negotiation.

Trade-offs to name unprompted

  • Blast radius and clear ownership against fleet-wide operational cost.
  • Cross-service queries become network calls or event pipelines — a real cost that must be paid somewhere.
  • Cluster proliferation is the thing that makes CVE response slow; the inventory grows faster than the team.
  • Logical separation (database, roles) gets most of the benefit at a fraction of the cost.
seniorHow consistent do reads need to be — and who decides?

What a strong answer demonstrates

That consistency is a product decision priced by engineering, not a database setting chosen by whoever wrote the connection string. A strong answer decomposes "consistent" into the four distinct asks — no lost writes, no stale reads, real-time ordering, multi-document atomicity — maps each to a mechanism and a cost, and then goes per use case rather than per cluster. It names causal sessions as the cheap answer to what people usually mean (read-your-own-writes), pushes back on linearizable with its concrete cost, and insists that the safe setting be the cluster default so that weakening it is a visible, reviewed choice.

Trade-offs to name unprompted

  • Majority writes cost a replication round trip — cross-region, that is the write latency floor.
  • Secondary reads buy latency and isolation and spend consistency; causal sessions recover most of it cheaply.
  • Stronger defaults are safer and slower, and teams route around them if the cost is unexplained.
  • The failure mode is not choosing badly; it is nobody choosing, so the default is whatever was copied.
principalDo you keep the vectors in MongoDB or run a dedicated vector database?

What a strong answer demonstrates

That you price the seam, not the benchmark. A strong answer defaults to keeping vectors with the documents — one consistency story, one permission model, one backup, and pre-filtering on operational fields inside the vector index, which is the capability most teams discover they needed only after splitting — and then names the specific conditions that would justify a separate store: vector volume an order of magnitude beyond what the operational cluster should carry, a required algorithm MongoDB does not offer, or an existing well-run platform. It also notes that the decision is asymmetric: a dual-write pipeline running for a year is much harder to unpick than a migration out of MongoDB would have been.

Trade-offs to name unprompted

  • Integration cost: dual writes or CDC, backfills, two permission models, two DR stories.
  • Pre-filtering inside the index versus post-filtering a top-k that comes back empty for restricted users.
  • Operational maturity of the specialised tool against the cost of one more thing to run and patch.
  • Benchmarks without filters and without permissions flatter the dedicated store and mislead the decision.
seniorEnforce schema in the database, in the application, or not at all?

What a strong answer demonstrates

That the answer depends on how many things write to the collection. A strong answer puts the invariants that must hold regardless of writer into the database with $jsonSchema — types, required fields, enums, ranges — keeps richer domain validation in the application where the error messages are useful, and describes the safe rollout: validationAction: "warn" and validationLevel: "moderate" first, measure violations, fix them, then enforce. It distinguishes "no imposed schema" (a real, valuable property that makes lazy migration possible) from "no invariants" (a bug factory), and it pairs validators with the schema-versioning pattern so evolution stays cheap.

Trade-offs to name unprompted

  • Validators are enforced for every writer including scripts and the shell; application validation is not.
  • Strict validation makes lazy migration harder, so it goes at the end of an evolution, not the start.
  • Validator errors are less friendly than application errors — you want both layers, for different audiences.
  • Enforcement without a versioning strategy is how a collection ends up permanently unmigratable.
principalHow much MongoDB expertise should a product team have?

What a strong answer demonstrates

That you think in mechanisms rather than in training courses. A strong answer sets a floor for every engineer — read an explain plan, know ESR, know that an unbounded array is a future outage, know what w: "majority" costs — and then puts the deeper knowledge behind automation and review rather than expecting everyone to hold it: a CI check that fails a COLLSCAN, an access-pattern document per new collection, index definitions in reviewed migration code, a schema review gate for new collections, and a small group of trained reviewers rather than one gatekeeper. It also names the failure mode of the alternative — a single database expert who becomes a bottleneck and then leaves — and treats knowledge distribution as an availability concern.

Trade-offs to name unprompted

  • Depth in a few people is fast and fragile; breadth is slower to build and survives departures.
  • Automated checks scale and are impersonal; review gates catch design, not syntax — you need both.
  • Every gate is a tax on delivery, so each one must earn its place with a class of incident it prevents.
  • Platform teams that own the mechanisms without owning the schemas end up accountable for decisions they did not make.

Exercise 1 — A multi-tenant document collaboration platform

Prompt. Design the data layer for a document collaboration product: tenants ranging from three-person teams to fifty-thousand-employee enterprises, documents with folders and permissions, full-text and semantic search, activity feeds, and a hard requirement that one tenant can never see another's data. Assume ten million documents today and a 3× annual growth rate.

Clarifying questions to ask first

  • What is the tenant size distribution? "Some big ones" and "one tenant is 40% of the data" are completely different designs.
  • Is there a data-residency requirement per tenant? That decides whether zone sharding is an optimisation or a constraint.
  • How are permissions expressed — per document, per folder with inheritance, or per group? Inheritance changes everything about the read path.
  • What is the read/write ratio, and how live must the activity feed and search results be?
  • Is there a per-tenant export, deletion or audit obligation (GDPR, enterprise contracts)?
principalStrong solution outline and expected trade-offs

Shape of the answer

One shared cluster with tenantId as the leading field of every shard key and every index — collection-per-tenant does not survive tens of thousands of tenants, because per-collection metadata and index overhead grow with the count. The shard key is { tenantId: 1, _id: 1 }: the tenant prefix targets every query, and the _id suffix gives the largest tenants the cardinality to split across shards instead of becoming a jumbo range. Whale tenants get a zone pinning them to dedicated shards, which is also the noisy-neighbour answer.

Documents are an aggregate: metadata, current version pointer, and permissions inline; content lives in object storage with a key on the document, because content is large, immutable per version, and never filtered on. Folder permissions become a materialised acl array on each document — an ancestor-path array plus effective principals — so a permission check is a filter, never a traversal; folder moves trigger a bounded re-materialisation driven by a change stream. Search is $search plus $vectorSearch fused with $scoreFusion, with tenantId and acl as pre-filters inside the index — post-filtering search results is both a leak and a correctness bug. The activity feed is append-only, time-partitioned per month and dropped on expiry rather than TTL-deleted.

// One aggregate, tenant-prefixed, permissions materialised for filtering.
{ _id: ObjectId("..."), tenantId: "acme", title: "Q3 plan",
  path: ["root", "f_ops", "f_plans"],            // ancestors, for subtree queries
  acl: ["u:1042", "g:ops", "r:tenant-admin"],    // effective principals, materialised
  currentVersion: 7, contentKey: "s3://.../v7", embedding: [/* ... */],
  updatedAt: ISODate() }

db.documents.createIndex({ tenantId: 1, path: 1, updatedAt: -1 });
db.documents.createIndex({ tenantId: 1, acl: 1, updatedAt: -1 });
sh.shardCollection("app.documents", { tenantId: 1, _id: 1 });

Trade-offs to name unprompted

  • Shared cluster versus per-tenant isolation. Shared is operationally sane and cost-effective; it makes isolation a discipline (every query filtered by tenantId, enforced in a repository layer nobody bypasses) rather than a physical boundary. Say plainly that the shard key is a performance boundary, never a security one.
  • Materialised ACLs versus computing inheritance at read time. Materialising makes reads a single indexed filter and makes permission changes a fan-out job with a bounded but real latency; computing at read time is always correct and always slow. Name the fan-out size for the worst case (a permission change at the root of a large folder tree).
  • Content out of the database. Cheaper storage, smaller working set, no 16 MB problem — at the cost of two systems in the read path and a consistency question on delete.
  • Search freshness. mongot is eventually consistent, so a just-saved document is not immediately findable; either accept it in the UX or read-through from the primary for the author's own view.
  • Whale tenants. Zones fix the load problem and create an operational one — someone has to notice a tenant becoming a whale and act. Name the metric (per-tenant data size and op rate) and the trigger.
  • Per-tenant deletion. With a tenant-prefixed shard key, deletion is a targeted range operation and an archive is a targeted export; that is a design benefit worth stating, because it is a contractual requirement in enterprise SaaS.

Exercise 2 — Telemetry for a fleet of connected devices

Prompt. Two million devices, each reporting ten metrics every thirty seconds — roughly 670,000 measurements per second. Requirements: live dashboards showing the last hour, historical analysis over two years, alerting on threshold breaches within a minute, and the ability to answer "show me everything device X did on this date" for support.

Clarifying questions to ask first

  • What is the loss tolerance? A dropped sample in an aggregate is very different from a dropped safety-critical reading.
  • What resolution must be retained for two years — raw, or is a rollup acceptable after 30 days? This single answer changes the storage estimate by an order of magnitude.
  • Are late and out-of-order arrivals common (devices with intermittent connectivity)? That drives bucketing and correction behaviour.
  • Are alerts evaluated per device, per fleet, or both? Per-fleet aggregation within a minute is a much harder requirement.
  • Is MongoDB required for the whole path, or can there be a queue and a separate analytical store?
principalStrong solution outline and expected trade-offs

Shape of the answer

A queue in front — Kafka or equivalent — so ingest spikes and database maintenance are decoupled and the database is never the backpressure mechanism for the fleet. Writers consume from the queue and do unordered bulkWrite batches into a time series collection with metaField: "deviceId" and a granularity matched to the 30-second interval, w: 1, and the absolute minimum number of indexes because at 670k writes per second every index is a large fraction of the cost. Shard on { deviceId: 1, ts: 1 } — never on ts alone, which would make one shard take every insert.

Three tiers of data, not one: raw retained for 30 days with bucket-level expiry; one-minute and one-hour rollups maintained by scheduled $merge jobs, retained for two years and serving every dashboard and historical query; and cold rollups archived to object storage or Online Archive. Live dashboards read rollups, never raw. Alerting does not poll the collection: it evaluates thresholds in the stream, before or beside the database — a change stream is an acceptable second path for state-transition alerts, but a per-minute scan of a 670k/s collection is not a design. Support's "device X on this date" query is a targeted range on the shard key, which is exactly why deviceId leads it.

db.createCollection("readings", {
  timeseries: { timeField: "ts", metaField: "device", granularity: "seconds" },
  expireAfterSeconds: 30 * 86400 });
sh.shardCollection("iot.readings", { "device.id": 1, ts: 1 });

// Rollup: idempotent, restartable, watermark-bounded.
db.readings.aggregate([
  { $match: { ts: { $gte: watermark } } },
  { $group: { _id: { d: "$device.id", m: { $dateTrunc: { date: "$ts", unit: "minute" } } },
              avg: { $avg: "$temp" }, max: { $max: "$temp" }, n: { $sum: 1 } } },
  { $merge: { into: "readings_1m", on: "_id", whenMatched: "replace" } }
]);

Trade-offs to name unprompted

  • Raw retention versus rollups. Two years of raw at this rate is tens of terabytes and buys almost nothing; rollups are cheap and answer 99% of questions. Name what you lose — the ability to re-derive a metric you did not think of — and how long the raw window needs to be to make that acceptable.
  • Write concern. w: 1 is defensible for telemetry and indefensible for a safety-critical reading; make the loss tolerance an explicit product answer, not an engineering default.
  • Shard key. deviceId-first gives targeted per-device queries and even distribution; the cost is that fleet-wide time-range queries are scatter-gather — which is precisely why they are served from rollups instead.
  • Alerting path. Evaluating in the stream is fast and duplicates logic outside the database; evaluating from a change stream is simpler and inherits the oplog window as a recovery deadline. Pick one, name the failure mode of the other.
  • Late data. Late arrivals create extra buckets and hurt compression, and they invalidate rollups already computed; either buffer upstream, or make rollups recomputable over a trailing window and say how wide it is.
  • Oplog window. At this write rate the window shrinks dramatically; size it deliberately with minRetentionHours, because it is simultaneously your maintenance window, your secondary-recovery budget and your CDC deadline.

Exercise 3 — An event-sourced order system with a read model

Prompt. Design an order management system on MongoDB where the order's history must be auditable and replayable, several downstream systems (fulfilment, billing, analytics) need to react to changes, and the customer-facing order page must render in under 100 ms at the 99th percentile. Peak is 5,000 orders per minute with a 10× seasonal spike.

Clarifying questions to ask first

  • Is the audit requirement "who changed what, when" or true event sourcing where state is derived from events? They lead to very different designs.
  • How stale may the read model be — sub-second, or is a few seconds acceptable? This decides synchronous versus asynchronous projection.
  • Do downstream systems need ordered delivery, exactly-once semantics, or just eventual convergence?
  • What is the retention obligation for the event history — regulatory years, or operationally useful months?
  • Does the 10× spike apply to reads, writes, or both? A read spike and a write spike have different answers.
principalStrong solution outline and expected trade-offs

Shape of the answer

An append-only orderEvents collection with _id: { orderId, seq } — a compound _id gives you uniqueness, ordering and idempotent appends in one, and a duplicate-key error is your optimistic-concurrency check for free. A separate orders read model holds the current state as one document, shaped exactly for the order page so rendering is a single _id lookup — that is how you get the 100 ms p99, not by optimising a join. The read model is updated in the same operation as the event where it can be (both writes in one transaction, or the event appended with the state change in one document if the aggregate allows), and reconciled by a replay job that can rebuild any order from its events.

Downstream systems consume a change stream over orderEvents with persisted resume tokens and idempotent handlers — at-least-once, ordered per stream, resumable. Publishing an event contract from the event collection rather than exposing the read model's shape keeps downstream systems decoupled from your internal document. Sharding, if needed, is on { orderId: 1 } so every event for an order and its read-model document are co-located and a projection update is single-shard. The 10× spike is absorbed by the queue in front of the write path and by the read model on the read path; the event collection is time-partitioned so old partitions can be archived rather than deleted.

// Append-only, idempotent, ordering built into the key.
{ _id: { orderId: "o-1001", seq: 7 }, type: "OrderPaid", v: 1,
  at: ISODate(), actor: "svc-payments", data: { amount: 19.98 } }
// A retried append fails with 11000 - that IS the concurrency check.

// Read model: one document, shaped for the page, one _id lookup to render.
{ _id: "o-1001", status: "paid", customer: { id: 42, name: "Ada" },
  lines: [ /* ... */ ], total: 19.98, lastSeq: 7, updatedAt: ISODate() }

db.orderEvents.watch([{ $match: { operationType: "insert" } }]);   // fan-out to downstream

Trade-offs to name unprompted

  • Event sourcing versus an audit log. Full event sourcing gives replay and temporal queries and costs you a projection to maintain, a versioning problem for event schemas, and a much steeper on-call learning curve. If the requirement is only "who changed what", an append-only audit collection alongside a normal mutable document is far cheaper — say so, and make the interviewer confirm which they want.
  • Synchronous versus asynchronous projection. Updating the read model in the same transaction gives read-your-own-writes and couples the write path to the projection's cost; projecting from a change stream decouples them and introduces a visible lag. State the lag budget and how you would measure it.
  • Delivery semantics. Change streams are at-least-once and ordered per stream. Downstream consumers must be idempotent; parallelism means partitioning by orderId, not competing consumers on one stream.
  • The oplog window as a hard deadline. A downstream system down longer than the window needs a documented resynchronisation from the event collection — which is the one genuine advantage of having the events durably stored rather than relying on the oplog.
  • Event schema evolution. Version every event (v: 1) and keep upcasters, because replay means today's code will read events written years ago. This is the cost people forget when they choose event sourcing.
  • Retention and cost. Events grow forever; time-partition the collection and archive old partitions, and be explicit that "replayable from the beginning" and "we archive after two years" are in tension — choose one and write it down.

21Night-before cheat sheet

The ten questions most likely to be asked, with the one-sentence answer to have ready. If you can say each of these cleanly and then add one sentence of "and the reason is…", you will pass the screening layer of almost any MongoDB loop.

  1. Embed or reference? Store together what is read together — embed when the child is bounded, read with the parent and written at the same rate; reference when it is unbounded, large, shared, or queried on its own, and say that the decision comes from access patterns rather than from cardinality alone.
  2. What is the ESR rule? Compound index fields go Equality, then Sort, then Range, because equality narrows the scan to a contiguous key region and a range field placed before the sort field destroys that contiguity and forces a blocking in-memory sort.
  3. How do you know a query is healthy? In explain("executionStats"), totalKeysExamined ≈ totalDocsExamined ≈ nReturned; IXSCAN alone means nothing if you examined two million keys to return twenty.
  4. What makes a good shard key? High cardinality, even frequency, non-monotonic, and — decisively — present in your common queries, because a key that distributes perfectly but appears in no query turns every read into a scatter-gather.
  5. What happens when the primary dies? Secondaries detect the missing heartbeat after electionTimeoutMillis (10 s), a member with the freshest oplog that can reach a majority is elected, and any writes that had not reached a majority are rolled back — which is why w: "majority" matters.
  6. What is the default write concern? w: "majority" since MongoDB 5.0 (it was w: 1 before), and the read concern default is still local — so a majority write does not by itself give you a majority read.
  7. Does MongoDB have transactions? Yes — multi-document ACID since 4.0 on replica sets and 4.2 across shards — but single-document operations are already atomic, and a transaction should prompt you to check whether the model could put the invariant in one document.
  8. What is the unbounded array anti-pattern? An embedded array that grows with time or usage: it heads toward the 16 MB document limit, makes every append rewrite the whole document, and bloats multikey indexes — fix it with a separate collection, the bucket pattern, or a capped subset plus a durable home for the rest.
  9. How do you add an index to a huge live collection? Just createIndex — since 4.2 builds do not block reads or writes and background: true is gone — but the build runs on every member at once, so schedule it, watch replication lag and cache pressure, and be ready to killOp.
  10. What is the latest MongoDB and what changed? 8.3 is the current stable series (GA 31 May 2026, newest patch 8.3.8 on 13 Aug 2026): the Cost-Based Ranker became the default plan selector, $scoreFusion went GA and removeShard was deprecated in favour of the explicit shard-draining commands — and the security event to know is MongoBleed, CVE-2025-14847, the unauthenticated zlib heap-memory leak exploited in the wild from December 2025.
