MongoDB

study · MongoDB 8.3 · released 2026-05-04

MongoDB in 2026 is a general-purpose transactional database that happens to store documents, not the schemaless toy of the 2013 blog posts — and interviews now probe exactly that gap. The current stable series is 8.3, GA on 4 May 2026 (latest patch 8.3.8, 11 Aug 2026), claiming up to 45% more reads and 35% more writes than 8.0 with no application change, largely from profile-guided and link-time optimisation of the server binary itself. The two structural shifts worth knowing cold: since 8.2 the "minor" releases ship on-premises as well as in Atlas, and full-text Search and Vector Search now run outside Atlas via a separate mongot binary alongside mongod; and in 8.3 a cost-based ranker became the default plan-selection mechanism for eligible queries, ending fifteen years of pure trial-execution multiplanning. Security is a live interview topic because of MongoBleed (CVE-2025-14847, CVSS 8.7) — an unauthenticated heap-memory leak in the zlib wire-compression path, added to CISA KEV after in-the-wild exploitation, patched in 8.2.3 / 8.0.17 / 7.0.28 and below. Everything here targets self-managed and Atlas equally, and labels the version where each feature became stable, default, or deprecated.

01The document model & BSON

Start with the claim MongoDB actually makes, because candidates routinely defend the wrong one. MongoDB is not "schemaless" and it is not "for unstructured data". Its claim is that the unit of storage, the unit of atomicity and the unit of retrieval should be the same thing as the unit your application works with — an object. A relational database shreds an order into orders, order_lines, addresses and payments because rows are flat and joins are cheap in a single-node engine; MongoDB stores the order as one document because the read that matters ("show me this order") then touches exactly one place on disk, and the write that matters is atomic without a transaction. Everything else in the product — indexing, the aggregation framework, sharding, the durability model — is downstream of that one decision.

The concrete artefact is BSON: a binary serialisation that looks like JSON but is neither text nor a superset of it. Three properties matter in interviews. It is length-prefixed, so the server can skip a subdocument or an array element without parsing it, which is why projections and index scans on nested fields are not disastrous. It is typed beyond JSON, adding 64-bit integers, 128-bit decimal128, date (a signed 64-bit millisecond offset from the Unix epoch, so pre-1970 dates are negative), binData, objectId, regex and the internal sentinels minKey/maxKey. And it is ordered: a BSON document is an ordered list of key/value pairs, so {a: 1, b: 2} and {b: 2, a: 1} are different documents, which is exactly why an exact-match query on a whole subdocument is order-sensitive and a dotted-path query is not. That single fact accounts for a large share of "why doesn't my query match?" incidents.

The hard limits are small in number and you should be able to recite them: a single document is capped at 16 MB; nesting is capped at 100 levels; a fully-qualified namespace (db.collection) is capped at 255 bytes; the _id field is mandatory, unique, immutable after insert, and always indexed by an index you cannot drop. The 16 MB limit is not an arbitrary annoyance — it is the mechanism that keeps the "document is the unit of atomicity" promise affordable, because the server must be able to hold and replicate a whole document. When a design pushes against it, the design is wrong, not the limit. Since 8.3 the validate command explicitly checks that stored documents do not exceed 16 MB, and an upsert that would produce an oversized document now returns error code 10334 (BSONObjectTooLarge) instead of the older 17419/17420 — a small change that breaks application code doing string or numeric matching on error codes.

The default _id is an ObjectId: 12 bytes made of a 4-byte big-endian seconds-since-epoch timestamp, a 5-byte per-process random value, and a 3-byte counter starting at a random value. That layout gives you a free creation timestamp (ObjectId.getTimestamp()) and roughly-sorted insertion, which is friendly to B-tree inserts on a single node — and actively hostile as a shard key, because "roughly sorted" means every insert in the cluster lands on the shard owning the top range. Generating _id client-side in the driver rather than letting the server do it is the default in every modern driver, and it is what makes retryable writes safe: the retry can be recognised as a duplicate rather than inserting twice.

Type gotchas that decide interviews

MongoDB compares values across types using a fixed total order (MinKey < Null < Numbers < String < Object < Array < BinData < ObjectId < Boolean < Date < Timestamp < Regex < MaxKey), which means {age: {$gt: 30}} silently ignores documents where age is the string "31". Numeric types compare by value, so 1, 1.0 and NumberLong(1) all match each other — but they do not round-trip identically, and a JavaScript driver that reads a 64-bit integer into a double loses precision above 2^53. Money is decimal128 or scaled integers, never double; that is a code-review line, not a preference.

The subtlest rule is how queries treat arrays. A query predicate on a field matches if it matches the field or any element of it, which is why {tags: "urgent"} matches {tags: ["urgent", "billing"]}. Combine that with multiple conditions and the semantics diverge: {scores: {$gt: 70, $lt: 80}} matches a document with scores: [65, 90], because 90 satisfies $gt and 65 satisfies $lt — different elements. If you mean "one element satisfies both", you need $elemMatch. Interviewers love this because it is the point where relational intuition breaks.

// Ordered documents: exact-match subdocument queries are order- and
// completeness-sensitive; dotted paths are neither.
db.users.insertOne({ _id: 1, name: { first: "Ada", last: "Lovelace" } });

db.users.find({ name: { first: "Ada", last: "Lovelace" } });   // matches
db.users.find({ name: { last: "Lovelace", first: "Ada" } });   // NO match: field order
db.users.find({ name: { first: "Ada" } });                      // NO match: not a subset
db.users.find({ "name.first": "Ada" });                         // matches, and can use an index

// Arrays: the implicit "any element" rule
db.results.insertOne({ _id: 1, scores: [65, 90] });
db.results.find({ scores: { $gt: 70, $lt: 80 } });              // MATCHES (65 and 90 split the work)
db.results.find({ scores: { $elemMatch: { $gt: 70, $lt: 80 } } }); // no match - correct semantics

// Types: existence vs null vs missing are three different states
db.users.find({ middleName: null });                    // missing OR explicitly null
db.users.find({ middleName: { $exists: false } });      // missing only
db.users.find({ middleName: { $type: "null" } });       // explicitly null only

What changed recently

MongoDB 8.3 pushed a surprising amount of type machinery into the aggregation layer, and it is the kind of detail that signals currency in an interview. $convert gained an optional base argument (2, 8, 10, 16) for string-to-number conversion; $toString now handles objects, arrays, regexes, timestamps and min/max keys; $toObject and $toArray parse strings that represent objects and arrays, and binData converts to and from arrays of numbers. New expressions $subtype, $createObjectId, $hash (MD5, SHA-256, XXH64), $hexHash, $serializeEJSON and $deserializeEJSON mean a class of "export it, transform it in Python, import it back" pipelines can now run server-side. Separately, 8.3 can parse the full range of double-precision values including subnormals, where earlier versions raised an error.

Interview trap

Saying "MongoDB is schemaless." It has not been a defensible statement since 3.2 introduced document validation, and it is a red flag at lead level because it implies you have never had to evolve a production dataset. The accurate framing: MongoDB enforces schema on read by your application, and on write by whatever you configure — $jsonSchema validators with validationLevel (strict/moderate) and validationAction (error/warn). The schema always exists; the choice is whether it lives in one enforced place or is scattered across every service that touches the collection. Note that 8.3 changed collection-validation semantics in a way that blocks downgrade until validated collections are dropped or relaxed, so validators are now a real part of the upgrade plan.

Interview Q&A

What is BSON and why not just store JSON?

BSON is MongoDB's binary document format: length-prefixed, so the server can skip fields and subdocuments without parsing them, and richly typed where JSON has only strings, doubles, booleans, null, objects and arrays. The extra types are what make the database usable — 64-bit integers and decimal128 for exact arithmetic, native date, binData, objectId, and internal min/max keys used for index bounds. Storing text JSON would mean parsing every document on every read, no type fidelity for money or timestamps, and no way to index a numeric field distinctly from its string form. The trade-off is that BSON is slightly larger than compact JSON for small documents because of the length prefixes and type bytes, and that it is order-sensitive, which surprises people writing exact-match queries on whole subdocuments.

Why is a document limited to 16 MB, and what do you do when a design approaches it?

The limit exists to keep the document as a cheap unit of atomicity and transfer: the server must be able to buffer, replicate and hand back an entire document, and updates rewrite the whole record because WiredTiger has no partial-document update. Practically, long before 16 MB you are already paying for it — every small append rewrites megabytes and produces a megabyte-sized oplog entry, so replication lag and cache churn arrive first. When a design approaches the limit it is almost always an unbounded array, and the fix is structural: bucket the array into fixed-size child documents (say 500 events per bucket), or move it to its own collection with a reference. For genuinely large binary payloads I would use object storage and keep a URL plus metadata in MongoDB; GridFS exists and chunks files into 255 KB pieces, but in 2026 it is rarely the right answer over S3-compatible storage.

Explain how MongoDB matches queries against array fields.

A predicate on a field matches if the field itself matches or if any single element of an array in that field matches, which is what makes {tags: "urgent"} work on an array of tags. The subtlety is that when you put several conditions in one predicate object, each condition may be satisfied by a different element, so {scores: {$gt: 70, $lt: 80}} matches [65, 90]. $elemMatch is the operator that says "one element must satisfy all of these", and it is also what you need for arrays of subdocuments, where {"items.sku": "A", "items.qty": 0} can match a document where those two conditions come from different items. There is a matching projection form, $elemMatch or the positional $ operator, to return only the matching element. At review time I treat any query with two conditions on the same array path and no $elemMatch as a bug until proven otherwise.

What is an ObjectId made of and when would you not use one?

Twelve bytes: a 4-byte seconds-since-epoch timestamp, a 5-byte per-process random value, and a 3-byte counter that starts randomly. That gives you a free creation time, uniqueness without coordination, and near-monotonic insertion order which is friendly to B-tree page splits. I would not use it as a ranged shard key, because the monotonic timestamp prefix funnels every insert into the shard owning the maximum range — that is the classic hot-shard mistake, fixed by a hashed shard key or a genuinely distributed key. I also would not expose one as a public identifier that must be unguessable, since the timestamp and counter leak information and are trivially enumerable; a UUIDv4 or v7 in binData subtype 4 is the alternative, with UUIDv7 giving you back the sortability. Finally, if a natural unique key exists — an order number, a tenant-scoped slug — putting it in _id saves an index and an extra lookup.

How does MongoDB treat missing fields, null, and explicit absence?

They are three states and MongoDB conflates two of them in one common case: {f: null} matches documents where f is explicitly null and documents where f is missing, because a missing field compares equal to null in the BSON total order. To distinguish, use $exists for presence and $type: "null" for an explicit null. This matters for indexing: a sparse index skips documents missing the field, so a query for {f: null} cannot use it correctly and the planner will avoid it; a partial index with $exists: true is the modern replacement and is more flexible. It also matters for unique constraints, since multiple documents missing the field all count as a single null value and collide, unless the index is sparse or partial.

How do you compare documents that hold numbers of different BSON types?

Numeric types — int, long, double, decimal — are compared by mathematical value, so 1, 1.0 and NumberDecimal("1.00") all match a query for 1 and sort together. Across non-numeric types MongoDB uses a fixed total order (MinKey, null, numbers, string, object, array, binData, ObjectId, boolean, date, timestamp, regex, MaxKey), so a range query on a numeric field silently excludes string-typed values of the same field rather than erroring. That is the mechanism behind the classic "half our data disappeared from the report" bug after a service started writing "42" instead of 42. The defences are a $jsonSchema validator pinning bsonType, and a periodic aggregation that groups by $type per field to detect drift — I have used exactly that as a data-quality canary.

Is MongoDB schemaless? Answer as a lead.

No — it is schema-flexible, and the schema is always somewhere. The database does not require a schema up front, which is genuinely valuable during early iteration and for heterogeneous data like event payloads or per-tenant custom fields, but every read path encodes assumptions about shape. My position is that a collection touched by more than one service or that has survived one product pivot needs an explicit $jsonSchema validator, versioned in the repo and deployed with collMod, plus a schemaVersion field on the document so migrations can be lazy. Start with validationAction: "warn" to measure violations without breaking writes, then flip to error. The trade-off is real: strict validators make rolling deploys harder, because the new writer and old writer must both satisfy the validator during the rollout window.

What is the difference between a collection and a view, and when is a view the right tool?

A view is a stored aggregation pipeline over a source collection, evaluated at query time — it stores no data, cannot be written to, and its performance is exactly the performance of the underlying pipeline, so it can only use indexes that the pipeline's leading $match and $sort can push down. I use read-only views mainly for security and for hiding legacy shape: grant a role read on a view that projects away PII rather than on the base collection. When the pipeline is expensive, the right tool is instead a materialised view maintained with $merge on a schedule, which trades freshness for predictable latency. One current gotcha worth knowing: views built on new expressions are a downgrade hazard — MongoDB 8.3 explicitly warns that views using 8.3-only expressions such as $$IDX must be updated or dropped before downgrading.

How would you introduce document validation to an existing high-traffic collection?

In four steps, none of which blocks writes. First, derive the actual schema empirically with an aggregation over a sample — group by field presence and $type — rather than trusting the code. Second, apply the validator with collMod using validationAction: "warn" and validationLevel: "moderate", so existing non-conforming documents are untouched and violations only appear in the log. Third, watch the log for a full business cycle, since the weekly batch job is always the one that violates it, and fix the writers. Fourth, flip to error and, if I want old documents cleaned up too, move to strict after a backfill. The lead-level point is sequencing this with deployments: the validator must accept both the old and new document shapes for the entire duration of a rolling deploy, so schema tightening is always at least two releases.

Where does the document model fit badly, and what would you say to a team defaulting to MongoDB?

It fits badly when the access patterns are genuinely many-to-many and unpredictable — an ad-hoc analytics workload where every query joins a different pair of entities, or a domain with heavy cross-entity referential integrity like a general ledger with double-entry constraints spanning rows. It also fits badly when you need multi-row constraints the database must enforce (unique across a computed set, foreign keys with cascade), because MongoDB gives you unique indexes and nothing else declarative. My advice to a team defaulting to it is to write down the top five queries and the top three writes first: if those cluster into a small number of aggregates that are read whole, the document model will be faster and simpler than the relational equivalent; if they fan out arbitrarily, you are choosing to reimplement joins in application code. And I would say the honest thing about 2026: PostgreSQL's JSONB has closed much of the "flexible schema" gap, so the argument for MongoDB now rests on horizontal scaling, the aggregation and search stack, and operational ergonomics — not on "we don't know our schema".

02Schema design & patterns

Relational modelling starts from the data and derives the queries; document modelling starts from the queries and derives the data. That inversion is the single most important thing to internalise, and it is what interviewers are testing when they hand you a domain and ask you to model it. The rule of thumb that actually generalises is "data that is accessed together should be stored together", and its corollary: if you find yourself doing the same $lookup on every read path, the model is wrong. There is no normal form to fall back on, so the discipline has to come from somewhere else — from an explicit list of access patterns, with a read/write ratio and a cardinality attached to each.

Use a running example for the whole unit: an e-commerce order system with customers, orders, order lines, products, reviews and an audit trail. The first design question is always embed-or-reference, and it is decided by three inputs, in this order: cardinality, whether the child is ever accessed on its own, and update independence. One-to-few and always-read-together (order lines inside an order, a shipping address inside a customer) embeds. One-to-many where the child is queried independently or updated at a different rate (reviews of a product, orders of a customer) references. One-to-squillions (log lines of a server, ticks of a sensor) always references, and usually buckets. If in doubt, ask "would I ever want to update just this child under concurrency?" — because an embedded child is rewritten as part of its parent, and two concurrent writers to different children of the same document contend on the same document lock.

Anti-patterns, named

Massive arrays — the one that kills clusters. Every append rewrites the whole document and produces a full-document oplog entry, so a 4 MB document appended to 10 times per second is 40 MB/s of replication traffic from one logical write path. Multikey indexes on a large array also generate one index key per element per document, which is how a 200-element array turns a 10 GB index into a 2 TB index. Bloated documents — pulling everything into one document so that reads which need 200 bytes must fetch 2 MB into the WiredTiger cache, evicting everything else. Unnecessary indexes — each index is a write amplification multiplier and cache competitor; a collection with 20 indexes writes 21 B-trees per insert. Case-insensitive queries without a collation index — $regex with /i cannot use a normal index efficiently, and the fix is a collation with strength: 2 on the index and the query, not a lowercase duplicate field (though that legacy trick is everywhere and still works). Separate collection per tenant/customer — thousands of collections means thousands of index B-trees and a catalogue that dominates the cache; the modern answer is a single collection with a tenantId leading every index, and Atlas even flags this one automatically.

Interview trap

Answering "embed or reference?" with "it depends on the access patterns" and stopping there. Everyone says that; nobody gets credit for it. The differentiator is naming the bound: "I'd embed order lines because a checkout basket is capped at 100 items by the UI, so the document has a hard ceiling of maybe 30 KB — and I'd reference reviews, because there is no business rule that limits how many a popular product gets." The second trap is the mirror image: candidates who have been burned once and then reference everything, rebuilding a relational schema in a database with no join optimiser, no foreign keys and no query-side referential integrity. That design gets the worst of both worlds, and a good interviewer will push on it by asking what happens to your five-$lookup read path at 10k rps.

(2) The multikey index is roughly 500× the key count, and index size scales with it. This is the concrete number to quote when someone proposes indexing tags on documents with hundreds of tags: you are not adding an index, you are adding a collection.

Interview Q&A

Walk me through how you'd model a social feed in MongoDB.

I would start from the two dominant operations — write a post, read a timeline — and their fan-out ratio. For most consumer feeds, reads massively outnumber writes, so I would fan out on write: a posts collection as the source of truth, and a timelines collection bucketed by {userId, bucketSeq} holding denormalised post stubs (author, text preview, mediaUrl, timestamp) in arrays of a few hundred. That makes the timeline read a single indexed lookup of one or two documents. The exception is the celebrity problem: fanning a post from an account with 20 million followers into 20 million buckets is unacceptable, so those accounts get the outlier treatment — their posts are pulled at read time and merged with the precomputed timeline. I would name the trade-off explicitly: fan-out-on-write costs storage and makes edits/deletes expensive, fan-out-on-read costs tail latency, and every real system is a hybrid keyed on follower count.

When is duplicating data the right answer, and how do you keep the copies honest?

Duplication is right in two cases. The first is point-in-time capture, where the copy is semantically different from the source — the price on an order line must not change when the catalogue changes, so that is not really duplication at all. The second is the extended reference: copying a handful of stable fields to kill a $lookup on a hot read path, where "stable" means it changes at a rate low enough that the update job is cheap. To keep copies honest I do three things: keep the copied field set as small as possible, drive the update from a change stream on the source collection so the propagation is asynchronous but reliable, and run a periodic reconciliation aggregation that reports drift as a metric rather than silently repairing it. What I would refuse is duplicating a field that changes frequently and must be consistent — a running balance, an inventory count — because then you have built a distributed transaction with no coordinator.

What is the bucket pattern and when does it stop working?

Bucketing groups many small, time-ordered items into one document per entity per time window, so you trade a large number of tiny documents for a small number of medium documents — fewer index entries, fewer round trips, and far better locality when you read a range. It stops working in three places. If items arrive out of order across window boundaries you get many partially-filled buckets and the win evaporates. If you need to update or delete individual items frequently, every operation rewrites the whole bucket. And if the bucket can grow unbounded — you forgot the count cap — you have reinvented the massive array anti-pattern with extra steps. For pure metrics workloads I would not hand-roll buckets at all in 2026: native time series collections have done exactly this internally since 5.0, with columnar compression and query rewrites the manual pattern cannot match.

A team has one collection per customer, 4,000 collections. What do you tell them?

That it will fall over on catalogue overhead before it falls over on data volume. Every collection carries its own WiredTiger file handle, its own _id index B-tree, and a catalogue entry that participates in cache; a few thousand collections means startup, initial sync, backup and any listCollections-driven tooling gets slow, and in a sharded cluster each one needs its own routing metadata. The fix is a single collection with tenantId as the leading field of every index and of the shard key, which also gets you tenant-targeted queries for free. The legitimate reasons to keep separation are hard data-residency or per-tenant encryption-key requirements, and there the right granularity is a database or a cluster per tenant tier, not a collection per tenant. I would migrate incrementally: dual-write into the merged collection, backfill, flip reads, then drop — and I would size the effort honestly, because the application's query layer has to learn to always pass the tenant filter, ideally enforced by a repository wrapper rather than by discipline.

How do you evolve a schema on a 2 TB collection without downtime?

Schema versioning plus lazy migration. Every document gets a schemaVersion; the application's read path understands the current version and the one before it, and any write upgrades the document it touches. That covers the hot data immediately and for free. For the cold tail I run a throttled background backfill — batches of a few thousand by _id range, with a sleep tuned to keep replication lag under a threshold I actually watch — and I never run it as one giant updateMany, because that is a single long-running operation holding a snapshot and producing an unbounded oplog burst. When the backfill reports zero remaining, I remove the old branch from the read path in a later release, then tighten the validator. The sequencing rule I state out loud: readers before writers, validators last, and every intermediate state must be deployable and rollback-able on its own.

What is the attribute pattern, and is it obsolete now that wildcard indexes exist?

The attribute pattern reshapes an object with many unpredictable keys into an array of key/value pairs so a single compound index on {attrs.k: 1, attrs.v: 1} can serve queries on any of them — the classic case is a product catalogue where every category has different specs. Wildcard indexes ({"specs.$**": 1}) solve the same read problem without reshaping the data, so for pure lookup the pattern is largely superseded. It is not obsolete though: wildcard indexes cannot be compound with a non-wildcard field in the general case, do not support many index options, and are less efficient than a targeted index; and 8.3 tightened wildcardProjection validation (backported to 8.2.4, 8.0.18 and 7.0.29), so some previously-accepted definitions are now rejected on creation. My rule: wildcard index for exploratory or genuinely arbitrary attributes, the attribute pattern when the pairs are a first-class part of the domain and you need range queries on typed values.

How do you handle many-to-many relationships?

Three options and they are chosen by cardinality and query direction. If both sides are small and one direction dominates — a document with a handful of tags — embed an array of references on the side you query from, and index it as a multikey index. If both directions are queried and both sides are bounded, embed arrays of IDs on both sides and accept the dual-write, which is not atomic across documents unless you use a transaction. If the relationship carries its own attributes or is unbounded — enrolments with grades, memberships with roles and dates — model it as its own collection, which is a junction table and there is no shame in it. What I would avoid is the reflex to always use a junction collection, because the two-collection version turns a single indexed read into a $lookup that cannot be pushed down as effectively, especially once the collection is sharded.

How does sharding change your schema design?

It moves the shard key from an operational detail to the primary modelling constraint, because every query that does not contain the shard key becomes a scatter-gather across every shard, and every unique index must be prefixed by the shard key. So I design the shard key at the same time as the document, not afterwards: for a multi-tenant system that usually means {tenantId: "hashed"} or a compound {tenantId: 1, _id: 1}, which keeps a tenant's data co-located and makes the common queries single-shard. It also changes embedding decisions, since a $lookup whose foreign collection is sharded is far more expensive, which pushes marginal cases toward embedding or the extended reference. And it kills some patterns outright: a global unique constraint on email is not available unless email is in the shard key, so you either put it there or enforce uniqueness with a separate small unsharded collection used as a claim table.

What do you look for in a schema during code review?

Five things, in order. Any array without a documented upper bound — that is the highest-severity finding and I want a bucket, a subset or a separate collection. Any field that is sometimes a string and sometimes a number, or a date stored as a string, because that is a query correctness bug not a style issue. Any new index, which I treat like a new dependency: what query needs it, what is the ESR ordering, and which existing index does it make redundant. Any $lookup on a request path, which needs a justification against denormalisation. And the tenant/partition field, which must lead every index in a multi-tenant collection. Beyond the mechanics I look for whether the document reads as a coherent business object; a document that is really three unrelated things joined by convenience will grow badly in exactly the way nobody predicted.

Would you use MongoDB's document model for an event-sourced system?

Yes, and it is a good fit — an append-only events collection with a compound index on {aggregateId: 1, version: 1}, a unique constraint on that pair to enforce optimistic concurrency, and snapshots in a second collection to bound replay cost. The append-only write pattern suits WiredTiger well, and the shard key almost writes itself: hashed aggregateId, so a single aggregate's stream is always on one shard and appends are perfectly distributed. The two things I would be careful about are that a single write must be one document (so one event per document, never an events array on the aggregate — that is the massive array trap again), and that projections are the real work: I would build them from a change stream with a resume token persisted transactionally alongside the projection, so a consumer restart does not replay or skip. The place it gets uncomfortable is cross-aggregate consistency, where you either accept eventual consistency or reach for a multi-document transaction and pay the coordination cost.

03CRUD, atomicity & the consistency knobs

MongoDB's write API looks trivial and hides a genuinely subtle consistency model. The foundation is one sentence: a write to a single document is always atomic, isolated and durable at the level you asked for — and nothing larger is, unless you open a transaction. "Single document" includes every subdocument and array element inside it, no matter how deep, which is precisely why the modelling decisions in unit 02 are consistency decisions. If a business invariant spans two documents, you have chosen either a transaction or eventual consistency; there is no third option and pretending otherwise is how data corruption stories start.

The update operators are the interesting half of the API, because they are executed server-side against the current value, which makes them safe under concurrency where a read-modify-write is not. $inc, $mul, $min, $max, $push with $each/$slice/$sort/$position, $addToSet, $pull, $pop, $rename, $setOnInsert, $currentDate, and the array-targeting forms $[] (all elements), $[<identifier>] with arrayFilters (matching elements, since 3.6) and the positional $ (the first element matched by the query). Two decrements racing on {$inc: {stock: -1}} both land correctly; two clients reading stock and writing back stock - 1 lose one. Since 4.2 updates can also be expressed as an aggregation pipeline, which unlocks conditional and self-referential updates that previously required a round trip.

// Aggregation-pipeline update (4.2+): compute the new value from the old one,
// server-side, atomically. Impossible with classic update operators.
db.orders.updateOne(
  { _id: oid },
  [
    { $set: {
        total: { $sum: { $map: { input: "$lines", as: "l",
                                 in: { $multiply: ["$$l.unitPrice", "$$l.qty"] } } } },
        status: { $cond: [{ $gt: ["$paidAmount", 0] }, "partially-paid", "$status"] },
        updatedAt: "$$NOW"
    } }
  ]
);

// arrayFilters (3.6+): update only the matching elements of an array
db.orders.updateOne(
  { _id: oid },
  { $set: { "lines.$[l].qty": 3 } },
  { arrayFilters: [ { "l.productId": pid } ] }
);

const job = db.jobs.findOneAndUpdate(

The three knobs: write concern, read concern, read preference

These are orthogonal and candidates conflate them constantly. Write concern answers "when may the driver tell me the write succeeded?" — {w: 1} means the primary applied it, {w: "majority"} means a majority of voting members have it and therefore it cannot be rolled back, {j: true} means it is on disk in the journal, and wtimeout caps how long you wait (and, importantly, a timeout does not undo the write). Since 5.0 the default write concern is majority, which is the single most consequential default change in modern MongoDB: it made the out-of-the-box configuration correct and slightly slower, and it is why upgrade-related latency regressions from 4.x are a real interview anecdote.

Read concern answers "how durable must the data I read be?" — local (default) returns the node's latest data, which may later be rolled back; majority returns only data acknowledged by a majority, so it can never be un-read; linearizable (primary only, single document) additionally guarantees you see all writes that completed before your read began, at the cost of waiting for a confirming majority round trip; snapshot gives a consistent point-in-time view across documents and is what transactions use; and available is local minus the orphan-document filtering on sharded clusters, so it is faster and can return duplicates. Read preference answers "which node do I talk to?" — primary, primaryPreferred, secondary, secondaryPreferred, nearest, with optional tag sets and maxStalenessSeconds (minimum 90).

Inside a driver session, MongoDB tracks an operation time and cluster time, so a read issued after a write in the same session waits until the node it is reading from has caught up past that write — read-your-own-writes, monotonic reads, and "writes follow reads", even when reading from a secondary. Retryable writes, idempotency and bulk

Retryable writes (on by default since driver-side retryWrites=true became the default, backed by server 3.6+) let the driver transparently retry a single-document write once after a transient network or failover error. The mechanism is worth knowing: the driver attaches a session ID and a monotonically increasing txnNumber to the write, and the server records the outcome, so the retry returns the original result rather than applying twice. It covers insertOne, updateOne, deleteOne, findAndModify and unordered bulkWrite of those — it does not cover updateMany or deleteMany, because those are not idempotent and cannot be safely resumed. That asymmetry is a favourite interview question.

For throughput, bulkWrite batches heterogeneous operations into one round trip; ordered: false lets the server apply them in parallel and continue past failures, which is typically 2–5× faster than ordered for independent writes. MongoDB 8.0 added a new client-level bulkWrite command that can span multiple collections and even databases in a single request — client.bulkWrite([...]) in modern drivers — which is the right tool for a fan-out write that previously needed one call per namespace. Combined with the 8.0 storage work, MongoDB measured bulk inserts around 54% faster than 7.0.

Interview trap

Two classics. First: believing {w: "majority"} means other clients immediately see the write. It does not — it means the write is durable. A concurrent reader with readConcern: "local" on a lagging secondary can still miss it, and a reader on the primary can see a write that has not yet reached a majority and could still be rolled back. Durability and visibility are separate axes; write concern controls one, read concern the other. Second: assuming wtimeout cancels a write. It only stops you waiting. The write is already in the oplog and will replicate; returning "failed" to the user and then retrying is how you create duplicates. The correct response to a wtimeout is to treat the outcome as unknown and reconcile with an idempotent key.

Expected outcome & solution sketch

(1) With majority nothing you were told succeeded disappears. With w: 1 you will eventually find writes that the old primary accepted but never replicated; when it rejoins, those are rolled back into a BSON file in rollback/ and are gone from the database. Seeing that file once permanently changes how you think about write concern — and note that a rollback is silent from the application's perspective, which is the whole point.

(2) $inc ends at exactly 2,000; read-modify-write ends somewhere below it, non-deterministically. If you need read-modify-write semantics you either use an aggregation-pipeline update, or optimistic concurrency: include a version field in the filter and $inc it in the update, then treat matchedCount === 0 as a conflict and retry.

Interview Q&A

What exactly is atomic in MongoDB?

A single write operation against a single document, including all of its nested subdocuments and arrays, and including an update expressed as an aggregation pipeline. That atomicity is not a lock you take — WiredTiger gives each operation a snapshot and detects write conflicts, so concurrent updates to the same document are serialised and the loser retries internally. Anything spanning more than one document — updateMany, a bulk write, two collections — is not atomic by default: updateMany can be observed halfway through by another reader, and it can fail partway leaving earlier documents modified. Since 4.0 on replica sets and 4.2 on sharded clusters you can wrap multiple documents in a multi-document transaction with snapshot isolation, but the design guidance has not changed: if you need a transaction for a routine operation, the schema is usually telling you those documents wanted to be one document.

Explain write concern, read concern and read preference, and how they interact.

Write concern is durability: how many nodes must acknowledge before the driver returns, with majority being the default since 5.0 and the only setting that guarantees a write cannot be rolled back. Read concern is data visibility guarantees: local gives you the node's latest, which might vanish in a failover; majority gives you only committed data; snapshot gives point-in-time consistency across documents; linearizable adds real-time ordering for one document at the price of a confirming round trip. Read preference is routing: which member you talk to, optionally with tags and a staleness cap. They compose in ways that bite — secondary plus local means you can read arbitrarily stale, possibly-doomed data, while secondary plus majority inside a causally consistent session gives you read-your-writes off the primary. The lead-level point is that these are per-operation settings, so the interesting engineering is deciding which few operations deviate from the defaults and documenting why.

Which writes are retryable, and why aren't they all?

Retryable writes cover operations that affect at most one document: insertOne, updateOne, replaceOne, deleteOne, findAndModify, and unordered bulk writes composed of those. They work because the driver stamps the write with a session ID and a transaction number, and the server durably records the result, so a retry after a network blip or a failover returns the original outcome instead of applying the write twice. updateMany and deleteMany are excluded because the server cannot know how far the first attempt got, so a retry could double-apply a non-idempotent operator like $inc to some documents and not others. The practical consequence is that any bulk maintenance operation needs its own idempotency design — batch by _id range with a filter that excludes already-processed documents, so a re-run is a no-op.

How do you get read-your-own-writes when reading from secondaries?

Use a causally consistent client session with readConcern: "majority". The session carries the cluster time and the operation time of your last write, and any subsequent read in that session blocks until the chosen node has replicated past that point, giving read-your-writes and monotonic reads without pinning traffic to the primary. The costs are a small latency tax on the first read after a write, the requirement that the session travels with the logical user request — which in a microservice architecture means propagating the cluster time across service boundaries, and most teams do not, which is why they end up reading from the primary instead. The failure mode to name is a badly lagging secondary: the read waits rather than returning stale data, so a lag spike turns into a latency spike, and you want maxTimeMS plus a fallback to the primary.

A write times out with wtimeout. What do you tell the caller?

That the outcome is unknown, not that it failed — and then I design so that this answer is actionable. wtimeout only bounds how long the client waits for replication acknowledgement; the write is already applied on the primary and in the oplog, and will almost certainly replicate a moment later. If the application reports failure and retries blindly with a fresh _id, you get duplicates; if it reports failure to a user who retries, the same. The fix is an idempotency key: derive _id deterministically from the business operation, or carry a client-supplied request ID with a unique index, so the retry is a duplicate-key no-op you can recognise. Operationally, a rash of wtimeouts is a signal about replication health — a lagging or down secondary in a three-node set makes every majority write wait on the slow member — so it should be an alert, not just an error log.

How does an upsert behave under concurrency?

An upsert is atomic for the document it touches, but two concurrent upserts whose filters match nothing can both decide to insert, and one gets a duplicate-key error. That is the intended design: MongoDB relies on the unique index as the arbiter rather than taking a range lock, so a correct upsert pattern requires a unique index on exactly the fields in the filter, and application code that catches error 11000 and retries as an update. Without the unique index you silently get two documents, which is the common production bug. $setOnInsert is the operator for fields that should only be written on creation — creation timestamps, defaults — and it is ignored on the update path. In a bucket or counter pattern where the filter includes a mutable predicate like count: {$lt: 200}, the race is more likely, so a retry loop with a bounded number of attempts is not optional.

When would you use findOneAndUpdate over updateOne?

When I need the document as part of the same atomic operation — either the before image or the after image. The canonical use is claiming work: a job queue where the worker atomically flips status from queued to running, stamps a lease, and gets the job back in one round trip, so no two workers can claim the same job without any external lock. It also supports sort, which updateOne does not, so you can claim the highest-priority matching document. The costs are that it returns only one document, it is slightly more expensive than a plain update because the document must be returned, and in a sharded cluster the query must target a single shard. The related lead-level detail is lease expiry: the claim must include a leaseUntil so a crashed worker's job becomes claimable again, which turns a hard distributed-locking problem into a bounded staleness problem.

What changed about bulk writes in MongoDB 8.0?

8.0 introduced a client-level bulkWrite command: instead of one bulk operation per collection, drivers expose client.bulkWrite() which accepts operations across multiple collections and databases in a single request, each entry naming its own namespace. That removes a real inefficiency in fan-out workloads — writing an event plus updating three projections used to be four round trips even when batched per collection. Alongside it, 8.0's storage and replication work made bulk inserts roughly 54% faster than 7.0, and 8.3 adds another 35% on writes over 8.0, mostly from profile-guided and link-time optimisation of the binary rather than from API changes. The operational caveats stay the same: prefer ordered: false when operations are independent, keep batches in the low thousands rather than tens of thousands so a single failure does not cost you a huge retry, and remember that only the single-document operations in the batch are retryable.

Your service reports occasional duplicate records despite a unique index. How do you investigate?

A unique index cannot be violated on an unsharded collection, so the first hypothesis is that the duplicates differ in some way the index does not cover — trailing whitespace, case, a different BSON type for the same logical value, or a null/missing field where multiple documents each count as a distinct-but-equal null unless the index is sparse. The second hypothesis is a sharded collection where the unique index is not prefixed by the shard key, which MongoDB will not even let you create, so more likely the "uniqueness" is enforced only in application code. The third is the retry path: a wtimeout or a driver-level retry with a client-generated new _id. I would confirm by aggregating on a normalised form of the key with $group and $count, then look at the two documents' _id timestamps and any request IDs to tell a race from a data-quality issue. The fix is nearly always a collation-aware or normalised unique index plus a deterministic idempotency key, not more application-level checking.

Would you ever use w:0, and what is the modern alternative?

Almost never — w: 0 disables error reporting entirely, so you do not learn about duplicate keys, validation failures or a document over 16 MB, and you cannot distinguish "accepted" from "the connection was already dead". The historical justification was throughput for firehose telemetry, and in 2026 that use case belongs somewhere else: a time series collection with unordered bulk writes at w: 1, or a proper streaming path with Atlas Stream Processing or Kafka in front. If someone insists on it, the compromise I would accept is unordered bulk inserts with w: 1 and no journal wait, batching a few thousand documents per call — you keep error reporting and get most of the throughput, because the expensive part was never the acknowledgement, it was the per-operation round trip. I would also insist on measuring rather than assuming: on modern hardware the difference between w: 1 and w: "majority" within a region is often single-digit milliseconds, and the write path is rarely the actual bottleneck.

04Indexes that actually work

Every MongoDB index is a B-tree of index keys mapping to record IDs, stored as its own WiredTiger table. That one sentence explains most index behaviour: keys are sorted, so an index gives you equality lookup, range scan and ordering for free; keys are separate from documents, so using an index that does not contain every field you need costs a second random read (the FETCH stage); and each index is a separate B-tree, so every insert writes N+1 trees and every index competes for the same cache. An index is not free storage — it is a write tax you pay forever in exchange for a read you had better actually be doing.

The ESR rule

The most valuable thing to know cold is the field ordering rule for compound indexes: Equality, Sort, Range. Fields matched with equality go first, then the fields you sort by, then the fields used in range predicates. The reason is mechanical. Equality fields narrow the scan to a single contiguous region of the B-tree. Within that region, keys are already in index order, so if the sort fields come next the sort is free (no blocking SORT stage). Range fields must come last because once you scan a range, everything after it in the key is no longer in sorted order — put a range before a sort and the planner must materialise and sort the results in memory.

Consider db.orders.find({tenantId: t, status: "shipped", total: {$gt: 100}}).sort({placedAt: -1}). ESR gives {tenantId: 1, status: 1, placedAt: -1, total: 1}. The naive ordering {tenantId: 1, status: 1, total: 1, placedAt: -1} looks reasonable and is much worse: it produces a blocking sort over every matching document, which fails outright past the 32 MB in-memory sort limit for find. Being able to derive that on a whiteboard, and to explain the "why" rather than reciting the acronym, is a reliable senior/lead differentiator.

Two adjacent facts complete the picture. Prefixes: a compound index {a: 1, b: 1, c: 1} also serves queries on {a} and {a, b}, so you need far fewer indexes than you think — and any index whose key pattern is a prefix of another is redundant and should be dropped. Sort direction: an index can be walked backwards, so {a: 1, b: 1} serves sort({a: -1, b: -1}) but not sort({a: 1, b: -1}), because that requires mixed direction and no single walk produces it.

// ESR in practice
db.orders.createIndex(

Covered queries, selectivity and the index that never gets used

A covered query is answered entirely from the index — no FETCH — which requires every field in the filter, the sort and the projection to be in the index key, and the projection to exclude _id unless _id is in the index too. Covered queries are typically 3–10× faster because they skip a random read per result, and they are the reason a slightly wider index sometimes beats a narrower one. Multikey indexes can never cover a query, because the index key does not preserve the original array.

Selectivity decides whether the planner bothers. An index on a boolean field with a 50/50 split will lose to a collection scan for many queries, because scanning half the index and then fetching half the documents is worse than scanning the collection once sequentially. That is not a bug: index scans produce random I/O, collection scans produce sequential I/O. The practical version of this rule is that low-cardinality fields belong in the middle of a compound index, not at its head — {status: 1} alone is usually a wasted index, while {tenantId: 1, status: 1, createdAt: -1} is excellent.

Building indexes in production changed shape in 4.2, when the old foreground/background distinction was replaced with a single hybrid build that holds an exclusive lock only briefly at the start and end and yields in between. On a replica set it still applies simultaneously across members and can saturate I/O, so for large collections the conservative route is a rolling build: take each secondary out of the set one at a time, build standalone, rejoin, then step down the primary and repeat. Builds are capped by maxIndexBuildMemoryUsageMegabytes (200 MB by default) and spill to disk beyond it. MongoDB 8.2 added control over whether index builds run during initial sync, which matters when you are adding a node to a cluster whose collections have dozens of indexes.

Interview trap

"Just add an index" as a universal answer, with no accounting for the write side. Every index multiplies write cost, consumes cache that would otherwise hold documents, and adds time to every index build, initial sync and backup restore. The lead-level answer names the trade and the evidence: I would look at $indexStats for indexes with near-zero accesses.ops since the last restart, drop the redundant prefixes, and only then add — and I would add it hidden: true first (4.4+) to confirm the planner would actually pick it and that nothing regresses, because hiding is instant and reversible while dropping-and-rebuilding a 500 GB index is not. The related trap is not knowing the ceiling: 64 indexes per collection, 32 fields per compound index, one array field per compound index.

State the ESR rule and justify it from first principles.

Equality fields first, then sort fields, then range fields. The justification is that a B-tree scan is a walk over sorted keys: equality predicates on the leading fields collapse the walk to one contiguous region, and inside that region the remaining key components are still in sorted order, so a sort on the next field costs nothing. A range predicate breaks that property — after scanning a range of values, subsequent key components are no longer globally ordered, so anything sorted after a range must be sorted in memory, producing a blocking SORT stage that is capped at 32 MB for find and fails past it. The practical test is that the right index makes the SORT stage vanish from explain. The rule bends in one case worth mentioning: if the range is extremely selective and the sort returns few documents, putting the range earlier can win, which is why I verify with explain rather than trusting the acronym.

What is a covered query and what prevents one?

A query the server answers entirely from an index, never touching the documents — explain shows IXSCAN with a PROJECTION_COVERED stage and no FETCH. It requires every field in the filter, sort and projection to be present in the index key, and requires _id to be excluded from the projection unless it is part of the index. Things that break it: any multikey (array) field in the index, because the index key does not reconstruct the array; a projection field not in the index; and on a sharded cluster, the shard key fields must also be in the index because mongos needs them for orphan filtering. The payoff is skipping one random read per returned document, which is typically the dominant cost of a range query, so I actively design "read-mostly" access paths to be covered — for example a listing endpoint whose projection is deliberately limited to the four fields already in the index.

Partial vs sparse index — which do you reach for and why?

Partial, essentially always. A sparse index only omits documents missing the indexed field; a partial index omits everything not matching an arbitrary filter expression, so it can express "only pending orders" or "only documents where the field is actually a string". Partial indexes are also better understood by the planner, which will only use one when it can prove the query predicate implies the partial filter — a subtlety worth stating, because it explains why an index you created is not being used: your query says status: {$in: ["pending","held"]} but the index is filtered on status: "pending". Sparse remains only for legacy compatibility. The combination that earns its keep is unique plus partial: uniqueness scoped to non-deleted rows, which is how you implement soft delete without inventing a tombstone value.

How do TTL indexes actually work, and where do they surprise people?

A TTL index is an ordinary single-field index on a date, plus expireAfterSeconds; a background thread on the primary wakes roughly every 60 seconds, scans the index for expired keys, and issues deletes that replicate to secondaries like any other write. That design produces four surprises. Deletion is not prompt — documents can outlive their expiry by a minute or much longer if the deleter is behind, so it is not a security control. The field must be a BSON date or an array of dates; a string or a number is silently ignored. The deletes are real writes, so a large expiry wave shows up as oplog volume, replication lag and cache churn, which is why staggering the expiry timestamps matters. And it only runs on the primary, so on a secondary the documents are simply removed when the delete replicates. When I need precise expiry semantics I filter by time in the query as well and treat the TTL index purely as space reclamation.

How do you decide which indexes to drop?

Evidence first: $indexStats gives per-index access counters since the last mongod restart, so I look for indexes with near-zero ops over a period that covers a full business cycle — including the monthly report that runs once and needs an index nobody uses otherwise. Then structural redundancy: any index whose key pattern is a strict prefix of another is unconditionally droppable, and any two indexes differing only in the direction of a single field are usually duplicates because a B-tree can be walked backwards. On a replica set I gather stats per-member, since analytics traffic often goes to a tagged secondary. Then the safe removal procedure: hide the index (4.4+), which makes the planner ignore it while still maintaining it, run for a business cycle watching for regressions, and only then drop. The reason hiding matters is that dropping a large index on a 1 TB collection is minutes to remove and hours to rebuild if you were wrong.

How do you build an index on a huge collection in production?

Since 4.2 there is a single hybrid build that takes an exclusive lock only at the start and end, so on a moderately sized collection I just build it, off-peak, and watch currentOp for progress. For very large collections or latency-sensitive clusters the safer route is a rolling build: remove one secondary from the replica set, restart it as a standalone on a different port, build the index, restart it back into the set, let it catch up, repeat for each secondary, then step down the primary and do the same. That keeps index-build I/O off every node serving traffic. Either way I plan for the memory limit — maxIndexBuildMemoryUsageMegabytes defaults to 200 MB and builds spill to disk beyond it — and I check the oplog window, because a node out of the set for hours must still be able to catch up. On Atlas the rolling build is a checkbox, which is the honest reason many teams never learn the manual procedure.

What is a multikey index and what are its restrictions?

It is what MongoDB automatically creates when an indexed field contains an array: one index key per array element, so a document with 50 tags contributes 50 keys. That makes array containment queries fast and makes index size proportional to total element count rather than document count, which is the trap — a 200-element array turns a modest index into a huge one, and every update to the array rewrites all of its keys. The restrictions are worth reciting: a compound index may contain at most one array field (creating one where two fields are arrays fails, and inserting a document that makes two indexed fields arrays fails at write time), multikey indexes cannot cover a query, and the multikey flag is sticky — once set on an index it stays even if all arrays are removed, which permanently changes how the planner reasons about bounds. For arrays of subdocuments I index the specific paths I query, use $elemMatch, and I check that the index bounds in explain are what I expect, because multikey bound tightening is where surprising full scans hide.

How do you handle case-insensitive search efficiently?

With a collation, not a regex. A collation with {locale: "en", strength: 2} makes comparisons case- and diacritic-insensitive at the index level, so find({email: "Ada@Example.com"}) uses the index — but only if the query's collation matches the index's collation, which is the detail everyone forgets; set the collation on the collection so every query inherits it, or pass it explicitly. The legacy approach you will find in older codebases is a duplicated lowercase field with its own index, which works, costs storage and write amplification, and needs discipline to keep in sync. What is not acceptable is $regex with the i flag, because a case-insensitive regex cannot use index bounds even when anchored, so it degrades to a full scan. If the requirement is really fuzzy or partial matching rather than case folding, that is a search problem and belongs in Atlas Search or a self-managed mongot, not in a regex.

What should you know about wildcard indexes today?

They index every field under a path — {"attrs.$**": 1} — which makes them the answer for genuinely unpredictable keys such as per-tenant custom fields, at the cost of size and of being less efficient than a targeted index. The key current fact is that MongoDB 8.3 introduced stricter validation of wildcardProjection specifications, backported to 8.2.4, 8.0.18 and 7.0.29: existing indexes keep working, but definitions that were previously accepted may now be rejected at creation time, which surprises teams whose infrastructure-as-code recreates indexes on deploy. Beyond that: one wildcard component per index, compound wildcard indexes are supported since 7.0 but with restrictions, they cannot be unique or TTL, and the planner will not use one for a sort. My default guidance is that a wildcard index is a discovery tool — use it to survive an unknown workload, then measure which fields are actually queried and replace it with two or three explicit indexes.

Your p99 read latency doubled after a deploy with no query changes. Indexes are unchanged. What now?

My first hypothesis is not the index set but the plan: the plan cache is per-mongod and is cleared on restart, index change or a catalogue change, and the winning plan is chosen from a short trial on whatever data happened to be sampled. A deploy that changed data distribution — a bulk import, a new tenant that is 100× larger than the others — can flip the planner to a worse plan for a parameterised query shape. So I would pull $queryStats (or the slow-query log at a lowered threshold) to identify the shapes whose latency moved, then explain(allPlansExecution) them and compare against the plan I expect. If the planner is genuinely choosing badly, the modern remedy is setQuerySettings to pin an index hint for that query shape — index filters are deprecated as of 8.0 — rather than embedding a hint() in application code. The other candidates I would rule out in parallel: working set no longer fitting the WiredTiger cache after a data growth step, a secondary that fell out and doubled the load on the rest, and on 8.3 the fact that the cost-based ranker is now the default plan-selection mechanism, which is a genuine behaviour change to look for right after an upgrade.

05Query planning, explain & tuning

MongoDB's query optimiser has historically been unusual: instead of estimating costs from statistics like a relational planner, it raced candidate plans against real data. For a new query shape the planner enumerates plans (one per usable index, plus a collection scan), runs each in parallel for a trial period — bounded by a work limit and by whichever plan first produces enough results — and declares a winner by a scoring function that rewards results produced per unit of work and penalises blocking stages. The winner is cached, keyed by query shape, and reused until it is evicted or until replanning triggers: if a cached plan performs an order of magnitude worse than its trial, the cache entry is evicted and the race is re-run. That design trades a little startup cost for immunity to stale statistics.

That is now changing, and it is the most citable planner fact of 2026. MongoDB has been building a cost-based ranker (CBR) — histogram-backed cardinality estimation, like a classical optimiser — available behind planRankerMode since 8.0/8.1. In MongoDB 8.3, "multi-planning with CBR backup" became the default plan-selection mechanism for eligible queries, with new explain output and serverStatus metrics under metrics.query.cbr.* and additional $queryStats counters. Practically: the racer still runs, but the cost model breaks ties and handles cases the trial cannot resolve. If you upgrade to 8.3 and see plan changes, this is the first thing to look at — and knowing it exists is a strong currency signal in an interview.

Reading explain like an operator

explain() has three verbosities: queryPlanner (what would be chosen, no execution), executionStats (runs the winning plan and reports counters), and allPlansExecution (also reports the losers' trial statistics). Ninety per cent of tuning is one ratio in executionStats:

db.orders.find({ tenantId: t, status: "shipped" })
         .sort({ placedAt: -1 }).limit(20)
         .explain("executionStats").executionStats
// {
//   nReturned: 20,
//   executionTimeMillis: 3,
//   totalKeysExamined: 20,     // index keys read
//   totalDocsExamined: 20,     // documents fetched  -> ratio 1:1 = ideal
//   executionStages: { stage: "LIMIT", inputStage: { stage: "FETCH",

Interpret it as three questions. Did it use the index I expect? — look for IXSCAN and the indexName; COLLSCAN at the leaf means no usable index. How much work per result? — totalDocsExamined / nReturned near 1 is ideal, 1,000 means the index is not selective for this query. Is anything blocking? — a SORT stage means an in-memory sort (32 MB limit for find, and it will error rather than spill), and SORT_KEY_GENERATOR above an IXSCAN is the classic symptom of an index whose ESR ordering is wrong. Also watch totalKeysExamined vastly exceeding totalDocsExamined: that is a broad index scan being filtered afterwards, typical of a $or or a leading range.

Finding the queries worth tuning

Three instruments, in order of preference. $queryStats (7.0+, and extended in every release since) is an aggregation stage that reports per-query-shape counters — execution time, docs examined, keys examined, and since 8.2 disk-spill and "delinquent ticket" metrics — with literals redacted so shapes group properly. It is the modern replacement for scraping logs and the right answer when asked "how do you find your worst queries?". The slow query log is always on: any operation slower than slowOpThresholdMs (100 ms default) is logged with its plan summary, keys and docs examined, and since 4.2 a queryHash/planCacheKey you can correlate. The database profiler (db.setProfilingLevel) writes to a capped system.profile collection: level 1 logs slow operations, level 2 logs everything and will hurt, and sampleRate lets you profile a fraction of traffic — useful, but 8.3 added guardrails (internalProfilingMaxAbandonedWritesPerSecondPerDb, profiler.totalAbandonedWrites) precisely because profiling can itself become the bottleneck.

Once you have found a bad plan, the escape hatches are hint() per query (blunt, and it lives in application code), and query settings (setQuerySettings, 8.0+) which attach an index hint or a rejection filter to a query shape, persist across restarts, and replicate. Query settings deprecate the older index filters, which were per-node and lost on restart — if a codebase still uses planCacheSetFilter, that is a migration item worth naming in an interview.

One structural fact that shapes tuning advice: MongoDB has two execution engines. The slot-based engine (SBE), introduced in 5.1, compiles a query into a tree of slot-based operators and is much faster for $group/$lookup-heavy pipelines; the classic engine handles everything else. MongoDB 8.0 narrowed SBE's remit (the internalQueryFrameworkControl default became trySbeRestricted), so most find queries run on the classic engine again — a deliberate reversal after mixed real-world results. If you tuned a pipeline on 7.0 and it behaves differently on 8.0, that is a leading suspect.

Interview trap

Running explain() without executionStats and drawing conclusions. Plain explain() is queryPlanner verbosity: it tells you which plan would be selected, with zero information about how much work it does — no totalDocsExamined, no timing. Candidates confidently declare "it's using the index, so it's fine" while the index scans two million keys to return three documents. The second trap is tuning against an empty or tiny collection: the planner races plans on the data present, so on 100 documents everything wins, and the plan you "verified" in staging is not the plan production picks. Always explain against production-shaped data, and remember the plan cache is per-node — the primary and each secondary can genuinely be running different plans for the same shape.

Try it

1. Take a query with a $or over two fields and explain it, then create an index for only one branch and explain again — watch the SUBPLAN stage and what happens to the branch with no index. 2. Force a replan: create a query shape, run it 20 times so the plan is cached, then insert a million documents that make the cached plan terrible, and watch planCacheKey, $planCacheStats and the eviction.

Expected outcome & solution sketch

(1) MongoDB evaluates each $or branch separately and unions the results with deduplication, so a single unindexed branch forces a collection scan for the whole query — the index on the other branch buys you nothing. This is the mechanical reason "$or is slow" is folklore: it is not slow, it is as slow as its worst branch. The remedy is an index per branch, or rewriting to $in when the branches are on the same field, which produces a single index scan with multiple bounds.

(2) You will see the cached plan continue until performance degrades roughly tenfold, at which point the entry is evicted and multiplanning re-runs. Watching this once explains a whole category of "it was fine for two hours then fell off a cliff" incidents, and it explains why plan pinning via query settings is sometimes the right answer for a shape whose data distribution is bimodal.

Interview Q&A

How does MongoDB choose an execution plan?

Traditionally by experiment rather than by statistics: for an unseen query shape it enumerates candidate plans — one per index that could serve the query, plus a collection scan — and runs them concurrently for a bounded trial, scoring each on results produced per unit of work with penalties for blocking stages like in-memory sorts. The winner is cached against the query shape and reused, and if a cached plan later performs about an order of magnitude worse than it did in its trial, it is evicted and the race re-runs. What is new is that MongoDB 8.3 made multi-planning with a cost-based ranker as backup the default selection mechanism for eligible queries, so histogram-based cardinality estimates now participate, with dedicated explain and serverStatus output. The practical implications I would raise are that plans are per-node and lost on restart, that the trial happens on whatever data is present so tiny test datasets teach you nothing, and that after an 8.3 upgrade a plan regression is a legitimate thing to look for first.

Walk me through diagnosing a slow query in production.

I start by identifying it rather than guessing: $queryStats for the worst shapes by total time and by docs-examined, or the slow-query log filtered by queryHash. Then explain("executionStats") on the real shape with real parameters, and I read three numbers — nReturned, totalDocsExamined, totalKeysExamined — plus whether a SORT or COLLSCAN appears. A high docs-to-returned ratio means the wrong index or the wrong field order; a SORT stage means ESR is violated; high keys with low docs means broad bounds, often a leading range or a $or. If the plan looks right and it is still slow, I move outward: is the working set exceeding the WiredTiger cache (rising bytes read into cache, eviction pressure), is the operation queueing on tickets, is it a secondary with replication lag, is it a scatter-gather on a sharded cluster because the shard key is absent. The last step is the fix with the smallest blast radius — usually a new index built hidden first, occasionally a query settings pin, rarely a schema change.

What is a query shape and why does it matter?

A query shape is the query with its literal values abstracted away — the namespace, the predicate structure and field names, the sort, the projection and a few relevant options — so that {age: {$gt: 21}} and {age: {$gt: 65}} are the same shape. It matters because the plan cache is keyed by shape, so all queries of a shape share one plan, and because $queryStats aggregates by shape, which is what makes it possible to reason about a workload at all rather than about millions of individual queries. MongoDB 8.0 formalised the vocabulary by introducing a distinct "query shape" and renaming the older concept to the "plan cache query shape", which is a nice detail to know because it explains why queryHash and planCacheKey are two different values in the logs — the second incorporates the available indexes, so it changes when you add one. The design consequence is that parameterisation is not free: a shape whose selectivity varies wildly with the literal, like a tenant filter where one tenant is 1000× larger, is exactly where a single cached plan serves everyone badly.

When would you use a hint, and when is that a mistake?

I use a hint when I have evidence the planner is repeatedly choosing badly for a shape and I need a fix now — an incident, or a bimodal data distribution the trial cannot resolve. It is a mistake as a default habit, because a hint freezes a decision made against today's data and indexes: drop or rename that index and the query errors or degrades, and add a better index and the hint prevents it being used. It is also a mistake in application code, because it puts an operational decision into a release cycle. The modern way to do this is setQuerySettings (8.0+), which attaches allowed indexes to a query shape server-side, persists across restarts and replicates — replacing the deprecated index filters, which were per-node and evaporated on restart. And whichever mechanism I use, I attach an expiry to it in my own process: a pinned plan is a TODO with a date, not a solution.

Explain the difference between the classic and slot-based execution engines.

The classic engine executes a tree of document-at-a-time stages; SBE, introduced in 5.1, compiles the query into lower-level operators working on individual value "slots", which avoids repeatedly materialising whole BSON documents and is substantially faster for aggregation-heavy work like $group and $lookup, where it can also use hash join and index nested-loop join strategies. The important current fact is that MongoDB pulled back: in 8.0 the default of internalQueryFrameworkControl became trySbeRestricted, so SBE is used for a narrower set of eligible queries rather than for most finds. That was a response to real-world regressions where SBE's plan cache and higher compilation cost hurt short queries. For an interview the useful takeaway is not the flag name but the judgment: engine selection is invisible until it is not, so when a workload's performance changes across a major upgrade, the execution engine and the planner defaults are on the checklist alongside index and data changes.

How do you stop a runaway query?

Prevention first: every query from an application should carry maxTimeMS, which makes the server abort it rather than letting it run until the client gives up — a client timeout alone leaves the operation running and holding resources. In the moment, db.currentOp() filtered by secs_running and namespace identifies it, and db.killOp(opid) stops it at the next yield point; note that operations only die at yield points, so a long-running command in a tight non-yielding phase can take a while. For repeat offenders I add server-side protection: setQuerySettings can reject plans, the ingress rate limiter and the 8.x intelligent workload management features can shed load before it reaches execution, and I would look at whether the endpoint should be paginated with range-based pagination rather than skip. Culturally, the fix I push hardest is that "no maxTimeMS" is a code-review blocker, because it is the cheapest possible guardrail.

Why is skip-based pagination a problem and what do you use instead?

skip(n) must walk and discard n index entries every time, so cost grows linearly with page number — page 5,000 of a listing scans five thousand pages worth of keys to return twenty documents, and the same query gets more expensive the deeper users go, exactly when they are least valuable. It is also incorrect under concurrent writes: a document inserted or deleted between page fetches shifts the window, so users see duplicates or gaps. The replacement is keyset (range) pagination: sort by a unique, stable key — typically {placedAt: -1, _id: -1} — and pass the last seen values as a $lt filter for the next page, which is a constant-cost indexed seek. The cost is that you lose random access to page N, so if the product truly needs numbered pages I would cap the depth, or precompute page boundaries. For very large result exports the right answer is neither: it is a cursor with batchSize, or an aggregation writing to a collection with $merge.

What do the slow query log and the profiler each give you, and what are their costs?

The slow query log is always on and free: any operation exceeding slowOpThresholdMs (100 ms by default) is written to the standard log with plan summary, keys and docs examined, response length, lock and flow-control waits, and a queryHash/planCacheKey pair to correlate shapes. The profiler is opt-in per database and writes structured entries into a capped system.profile collection, so you can query it — level 1 for slow operations, level 2 for everything. The cost differs sharply: level 2 profiling on a busy database is a serious write amplifier and can itself cause the latency you are debugging, which is why sampleRate exists and why 8.3 added abandoned-write guards and counters for profiling pressure. My default posture is slow log always, profiler at level 1 with a lowered slowms temporarily during an investigation, level 2 only on a single low-traffic node, and $queryStats as the everyday instrument since it is always-on, aggregate and redacted.

How does the planner handle $or and $in differently?

$in on a single field becomes one index scan with multiple bounds — cheap, and it preserves the ability to sort from the index. $or across different fields becomes a SUBPLAN: the planner picks a plan for each branch independently, runs them, and deduplicates the union by record ID, so the whole query can only be efficient if every branch has a usable index; one unindexed branch forces a collection scan and the other indexes are wasted. There is a second penalty: deduplication requires tracking seen record IDs, and a sort across branches is usually a blocking sort because no single index produces the union in order. So my tuning moves are, in order: rewrite $or on one field to $in; ensure an index per branch when the fields genuinely differ; and if the query is a hot path with a sort, consider a denormalised discriminator field that turns the disjunction into an equality — for example a precomputed state field rather than {$or: [{cancelledAt: {$ne: null}}, {refundedAt: {$ne: null}}]}.

How would you build a query-performance practice for a team, not just fix one query?

Three layers. Guardrails in code: every query carries maxTimeMS, no skip-based pagination beyond a capped depth, no new index merged without an explain in the pull request showing the before and after, and a repository layer that forces the tenant/shard-key filter so scatter-gather cannot happen by accident. Observability: $queryStats scraped on a schedule into whatever the team already uses for metrics, with alerts on new shapes appearing in the top ten by total time and on docs-examined-to-returned ratios crossing a threshold — the ratio catches regressions that raw latency hides while the cache is warm. And a review rhythm: a short monthly pass over the top shapes, over $indexStats for unused indexes, and over the slow-query log's plan summaries, treating unused indexes as debt to be paid down rather than harmless. The cultural point I would make to a skeptical team is that this costs an hour a month and it converts a class of 3 a.m. incidents into a backlog item, which is the trade every platform decision should be arguing.

06The aggregation framework

The aggregation pipeline is MongoDB's query language for anything more than a filter: a sequence of stages, each consuming a stream of documents and emitting a stream of documents. The mental model that makes it click is Unix pipes over BSON — $match is grep, $project is cut/awk, $group is sort | uniq -c, $sort is sort, $lookup is join. The important difference from SQL is that the pipeline is explicitly ordered by you, not reordered by a planner with full freedom, so stage order is a performance decision you own. The server does apply a set of well-defined optimisations — pushing $match before $project and before $lookup where provably safe, coalescing $sort + $limit into a top-k sort, absorbing $limit into $skip, converting $sort + $group into a streaming group — but it will not rescue a pipeline that filters last.

The rule that follows from that: filter early, project early, sort with an index, and put $lookup as late and as narrow as possible. A leading $match is the only stage that can use an index for the initial scan (plus a leading $sort, and $geoNear/$search which must be first); once any stage transforms documents, subsequent stages operate on the in-memory stream and no index is available. That single fact explains most "my aggregation is slow" tickets.

Memory, spilling and the numbers to quote

Each blocking stage — $group, $sort without an index, $bucketAuto, $setWindowFields — is capped at 100 MB of RAM. Historically exceeding that was an error unless you passed allowDiskUse: true; since 6.0 the server parameter allowDiskUseByDefault is true, so stages spill to disk automatically and the failure mode changed from "error" to "mysteriously slow". That is why MongoDB 8.2 added disk-spill metrics to $queryStats and serverStatus: spilling is now the thing you monitor rather than the thing you crash on. $facet keeps a hard 100 MB limit, and in 8.3 the error it raises changed from code 4031700 to the generic ExceededMemoryLimit (code 146) — a small but real breaking change for anything matching on error codes. Text search in 8.3 also gained a 100 MB cap on the TextOr stage with spilling.

// Revenue per product per month for one tenant, last 90 days.
db.orders.aggregate([
  // 1. $match FIRST: uses {tenantId:1, placedAt:-1}; nothing else can use an index.
  { $match: { tenantId: t, placedAt: { $gte: since }, status: { $in: ["shipped", "delivered"] } } },
  // 2. Narrow the stream before it multiplies.
  { $project: { _id: 0, placedAt: 1, lines: 1 } },
  { $unwind: "$lines" },
  { $group: {
      _id: { productId: "$lines.productId",
             month: { $dateTrunc: { date: "$placedAt", unit: "month" } } },
      revenue: { $sum: { $multiply: ["$lines.unitPrice", "$lines.qty"] } },
      units:   { $sum: "$lines.qty" }
  } },
  { $sort: { revenue: -1 } },
  { $limit: 50 },
  // 3. $lookup LAST, on 50 documents instead of 400,000.
  { $lookup: { from: "products", localField: "_id.productId", foreignField: "_id",
               as: "product", pipeline: [ { $project: { name: 1, category: 1 } } ] } },
  { $set: { product: { $first: "$product" } } }
], { allowDiskUse: true, maxTimeMS: 30000, comment: "revenue-by-product-monthly" });

Two things in that pipeline are worth arguing about in an interview. First, $lookup placement: moving it after $limit turns 400,000 foreign lookups into 50. Second, the pipeline form of $lookup (3.6+, with localField/foreignField combinable since 5.0) lets you project inside the join so you do not drag whole foreign documents through memory. And the comment option is not decoration — it shows up in the slow log, currentOp and $queryStats, which is how you attribute a rogue aggregation to a service at 3 a.m.

What is new, and why it matters

8.3 significantly extended expressions in ways that pull work back to the server. Array iteration finally exposes the element index: $map, $filter and $reduce accept an arrayIndexAs field, and the $$IDX system variable holds the current index — which removes a long-standing reason to $unwind with includeArrayIndex. Conversion got much stronger: $convert with a base argument, $toObject/$toArray, binData ↔ numeric array, and a much broader $toString. And a set of genuinely new expressions arrived — $hash and $hexHash (MD5, SHA-256, XXH64), $subtype, $createObjectId, $serializeEJSON/$deserializeEJSON, plus $mergeObjects support inside $setWindowFields. Concretely: deterministic pseudonymisation of a field, or building a stable dedup key, is now a one-stage server-side operation instead of an export/transform/import cycle. 8.0 made $rankFusion GA and 8.3 made $scoreFusion GA — the hybrid-search stages covered in unit 11.

Interview trap

Putting $match after $lookup or after $unwind and assuming the optimiser will fix it. It sometimes can — the pipeline optimiser does push a $match before a $lookup when the predicate only touches local fields, and before $unwind when it only touches non-unwound fields — but it cannot when the predicate references the joined or unwound data, which is precisely the interesting case. The way to answer this well is not to recite the rule but to say how you check: run db.coll.explain().aggregate(pipeline) and read the stages array, which shows the pipeline after optimisation, so you can see whether your $match moved and whether the first stage became an IXSCAN. The related trap is $unwind before $match on a 200-element array: you have just multiplied your working stream by 200 and then filtered it.

db.orders.aggregate([

              revenue: { $sum: "$total" }, orders: { $sum: 1 } } },

]);

Interview Q&A

How do you make an aggregation pipeline fast?

Shrink the stream as early as possible and keep index usability alive. Concretely: a leading $match that a real index serves, immediately followed by a $project or $unset that drops fields you will not need, then a $sort that the same index can satisfy so it does not become a blocking sort, then the expensive stages — $unwind, $group, $lookup — on the smallest possible stream, with $limit before any join if the query is a top-N. I verify with explain() on the aggregation, which prints the optimised pipeline, and I check that stage one is an IXSCAN. Beyond ordering, the levers are: use the sub-pipeline form of $lookup to project the foreign side, prefer $setWindowFields to self-joins, and if the same expensive aggregation runs on every page load, stop optimising and materialise it with $merge on a schedule. I would also add comment to every application pipeline so it is attributable in the slow log.

What are the memory limits in aggregation and what happens when you hit them?

Blocking stages — $group, an unindexed $sort, $bucketAuto, $setWindowFields — are limited to 100 MB in RAM. Since MongoDB 6.0, allowDiskUseByDefault is true, so instead of erroring these stages spill to temporary files in the dbpath and keep going, which means the modern symptom is latency and disk I/O rather than a failure. $facet is the exception with a hard 100 MB limit, and in 8.3 exceeding it returns ExceededMemoryLimit (146) where it used to return 4031700 — worth knowing if any application code matches on that. Because spilling is silent, I treat spill metrics as first-class: 8.2 added disk-spill counters to $queryStats and serverStatus, and a pipeline that starts spilling is either missing an index for its sort or is doing analytics that should have been materialised. On a cluster where multiple such pipelines run concurrently, spilling also competes for the same disk as the storage engine, which is how one report degrades everything.

$lookup versus denormalisation — how do you decide?

By where the join sits and how often it runs. On an analytical path that runs once an hour, $lookup is fine and denormalisation is premature. On a request path serving thousands of reads per second, a $lookup is a per-document foreign query — indexed nested loop at best — and it is exactly what the document model exists to avoid, so I would denormalise with the extended reference pattern. Sharding sharpens the decision: a $lookup whose foreign collection is sharded is substantially more expensive and historically was restricted, so on a sharded cluster the bias toward denormalisation is much stronger. My rule of thumb is that one $lookup on a well-indexed foreign key with a narrow projection is acceptable on a read path; two or more is a modelling smell; and any $lookup in a loop from application code is a defect, because that is an N+1 across the network.

$out or $merge?

$merge, in nearly every case. $out replaces the target collection wholesale: readers see the old data and then abruptly the new, the collection's indexes are recreated, and it cannot write into a sharded collection or perform an incremental update. $merge (4.2+) upserts into an existing collection on a unique key, supports whenMatched strategies including replace, merge, keepExisting, fail and a custom update pipeline, works with sharded targets, and lets you re-run only the affected window — so an hourly rollup can recompute the last two hours to absorb late-arriving data. The design point I would make is idempotency: choose the on key and whenMatched strategy so a re-run produces the same result, because scheduled jobs get retried and a "merge with $inc" rollup that double-counts on retry is a data corruption bug that takes weeks to notice.

How do change streams and the aggregation framework relate?

A change stream is an aggregation pipeline whose first stage is $changeStream, reading from the oplog and emitting change events, and you can append ordinary stages to it — $match to filter by operation type or by fields of the changed document, $project to narrow the event, even $addFields. Filtering server-side matters a great deal at scale, because otherwise every consumer receives every change and discards most of it, multiplying network and CPU. The parts that are change-stream-specific rather than aggregation-specific are the resume semantics — every event carries a resume token, and resumeAfter, startAfter and startAtOperationTime let a consumer restart — and the fact that the oplog window bounds how far back you can resume. It is a genuinely elegant piece of design: the same pipeline language serves batch queries, real-time streams and, with Atlas Stream Processing, continuous processing over Kafka topics.

What is $setWindowFields for?

It brings SQL window functions to MongoDB (5.0): partition the stream, order it, define a window in documents or in a value range, and compute $sum, $avg, $rank, $denseRank, $shift, $derivative, $integral, $expMovingAvg and friends over that window. Before it, a seven-day moving average or a per-customer running total required a self-$lookup or client-side processing, both of which are slow and awkward. Two practical notes: it is a blocking stage, so the 100 MB limit and spilling apply per partition, and a good partition key that matches an index keeps the memory bounded; and MongoDB 8.3 added $mergeObjects as a window accumulator, which is handy for collapsing a partition into one shaped document. It is one of the stages that changed my default answer to "should this analysis run in the database or in the application?" — for time-ordered analytics over data already in MongoDB, in the database.

Someone shows you a mapReduce job in a 2019 codebase. What do you do?

Rewrite it as an aggregation pipeline, and say why rather than just asserting it. Map-reduce has been deprecated since MongoDB 5.0; it executes user JavaScript per document in an embedded interpreter, which is far slower than native aggregation operators, it takes coarser locks, its behaviour on sharded clusters is awkward, and it is effectively unmaintained. The mechanical translation is straightforward: the map function's emit keys become $group._id, the reduce function becomes accumulators, the finalize function becomes a trailing $project or $set, and the output collection becomes $merge. The genuinely hard cases are reduce functions with non-associative logic or that rely on being called repeatedly, which is a semantic that $group does not have — those need rethinking rather than translating, and $accumulator/$function exist as a JavaScript escape hatch I would treat as a last resort because they reintroduce exactly the performance problem. I would also treat the rewrite as an opportunity to check whether the job needs to exist at all, since half of these are reports nobody reads.

How would you compute a rolling 30-day active-user count?

Not by aggregating the raw event collection on every request. I would build a two-tier pipeline: a scheduled job that groups raw events into a daily-uniques collection with $merge, storing per-day distinct user sets as either an array (if small) or a probabilistic sketch, and then a cheap query that unions the last 30 daily documents. For exact distinct counts across a 30-day window, the honest answer is that this is expensive in any database, and I would ask whether an approximate count within a percent is acceptable — because if it is, HyperLogLog sketches stored as binData and merged in application code are orders of magnitude cheaper. If it must be exact and interactive, that is a signal the workload belongs in a columnar store fed from MongoDB, or in Atlas's analytics nodes so the scan does not touch the operational cluster. What I would avoid is the naive $group with $addToSet over 30 days of raw events, which builds a giant in-memory set, spills to disk, and eventually breaks on cardinality.

Which new 8.3 aggregation features would actually change your code?

Three. $hash/$hexHash with SHA-256 means deterministic pseudonymisation and stable dedup keys can be computed server-side in a pipeline — previously that was an export, a script, and a reimport, or a per-document round trip. The arrayIndexAs option and the $$IDX variable in $map/$filter/$reduce remove a family of awkward $unwind-with-includeArrayIndex-then-$group workarounds, which are both slow and hard to read. And the conversion work — $convert with a numeric base, $toObject, $toArray, binData to numeric arrays — makes a whole class of data-cleanup migrations expressible as a single pipeline with $merge, which is dramatically safer than a script that pages documents through a client. The caveat I would attach in a design review is downgrade: 8.3 explicitly warns that views and validators using these new expressions must be updated or dropped before downgrading the FCV, so adopting them is a one-way door until you are confident in the version.

When should analytics not run on the operational MongoDB cluster at all?

When the query pattern is scan-heavy and unbounded rather than selective — full-collection aggregations, arbitrary ad-hoc slicing by analysts, joins across many collections — because those pull cold data into the WiredTiger cache and evict the working set that your latency-sensitive traffic depends on, and that eviction damage outlasts the query. The staged answers, cheapest first: route the workload to a dedicated analytics member with a tagged read preference and zero priority so it can never become primary; materialise the recurring shapes with $merge so analysts query pre-aggregated collections; and if the demand is genuinely open-ended, export to a columnar system — Atlas gives you federated queries and an object-storage tier for exactly this, and self-managed teams usually land on a CDC pipeline from change streams into a warehouse. The judgment I would articulate is that the cost is not CPU, it is cache: MongoDB does not have a separate buffer pool per workload, so an analytics query is a noisy neighbour by construction.

07Replica sets, elections & change streams

A replica set is a Raft-like consensus group: one primary accepts all writes, and secondaries replicate by tailing the primary's oplog. Understanding the oplog is understanding replication. It is a capped collection, local.oplog.rs, holding idempotent descriptions of every change — idempotent is the key word, because a secondary may apply an entry more than once during recovery, so an update like {$inc: {n: 1}} is rewritten in the oplog as the resulting $set. Secondaries fetch batches, apply them in parallel across writer threads while respecting document-level ordering, and report their progress back; the primary tracks those positions to compute the majority commit point, the timestamp before which data exists on a majority of voting members and therefore can never be rolled back.

Elections use protocol version 1 (Raft-derived, since 3.2). Members heartbeat every 2 seconds; if a secondary hears nothing from the primary for electionTimeoutMillis (10 seconds by default), it stands for election, and it wins only with votes from a strict majority of voting members and only if its oplog is at least as recent as any voter's. Failover in practice is typically 5–12 seconds end to end, of which most is the detection timeout — and modern drivers hide it, because they retry once for retryable writes and reads. Two configuration facts follow: a set has at most 50 members but only 7 voting members, and you should always have an odd number of voters, which is what the arbiter exists to provide.

Topology decisions that come up in interviews

The most common bad topology is PSA — primary, secondary, arbiter — chosen to save the cost of a third data node. It works until the secondary is down or lagging: with only one data-bearing secondary, w: "majority" can no longer be satisfied by data nodes (an arbiter holds no data and cannot acknowledge writes), so every majority write blocks, the majority commit point stalls, and because WiredTiger must retain history back to that commit point, cache pressure grows until the primary degrades. Since 5.0 made majority the default write concern, the PSA failure mode became far more visible, and MongoDB added automatic write-concern adjustment for PSA sets to soften it. The lead answer is: use PSS; an arbiter is a cost optimisation that trades away your durability guarantee at exactly the moment you need it.

Other member flags worth knowing: priority: 0 (never becomes primary — for a member in a distant region or a reporting node), hidden: true (invisible to drivers, so it serves no reads — backups, ETL), votes: 0 (needed once you exceed 7 voting members), secondaryDelaySecs (a delayed member, a human-error time machine: a dropped collection is still there for N hours), and buildIndexes: false. For geography, spread members across at least three failure domains, because a two-datacentre split has no majority side.

// A PSS set with an analytics member and a 6-hour delayed member.

Change streams

Change streams (3.6, cluster-wide since 4.0) turn the oplog into a supported, resumable API: db.coll.watch(pipeline, options) yields insert, update, replace, delete, drop, rename, dropDatabase and invalidate events. They are the correct answer to "how do I do CDC / cache invalidation / search indexing?", and the correct answer to "should I tail the oplog myself?" is a firm no — that was the 2015 pattern, it breaks on failover, and it exposes internal formats.

Three mechanics decide whether your consumer is production-grade. Resume tokens: every event carries _id, an opaque resume token; you persist it with whatever side effect you produced (ideally in the same transaction, or as a field on the projection document) and pass it as resumeAfter on restart, which gives at-least-once delivery. The oplog window bounds resumability — if your consumer is down longer than the window, the token is gone and you need a full resync, which is why oplog sizing is a consumer-availability decision, not just a replication one. Pre- and post-images: by default an update event carries only the delta (updateDescription) plus the document key; fullDocument: "updateLookup" re-reads the current document (so you may see a later version), while 6.0's changeStreamPreAndPostImages collection option gives true before/after images at the cost of extra storage. For very large events, 6.0.9/7.0 added $changeStreamSplitLargeEvent to split events that would exceed 16 MB.

// Production-shaped consumer: server-side filtering, durable resume token.
const token = await projections.findOne({ _id: "orders-search-indexer" });
const stream = db.collection("orders").watch(
  [ { $match: { operationType: { $in: ["insert", "update", "replace"] },
                "fullDocument.status": { $in: ["shipped", "delivered"] } } },
    { $project: { _id: 1, operationType: 1, documentKey: 1,
                  "fullDocument.tenantId": 1, "fullDocument.status": 1 } } ],
  { fullDocument: "updateLookup",
    resumeAfter: token?.resumeToken,          // startAfter: survives an invalidate event
    maxAwaitTimeMS: 1000 }
);
for await (const ev of stream) {
  await applyToSearchIndex(ev);
  await projections.updateOne({ _id: "orders-search-indexer" },
                              { $set: { resumeToken: ev._id } }, { upsert: true });
}
Interview trap

Treating change streams as a message queue with exactly-once semantics. They are at-least-once and ordered per document key, not exactly-once and not globally ordered across a sharded cluster in any way you should rely on. A consumer that crashes after acting but before persisting its token will replay, so every handler must be idempotent — which usually means an upsert keyed by documentKey plus a version, not an $inc. The second half of the trap is durability of the token: storing it in memory or in a file on the consumer's local disk means an instance replacement loses it, and the fallback of "start from now" silently drops events. The third is fan-out: pointing fifty consumers at the same collection means fifty oplog readers on the primary, which is a real load; at that point you put one consumer in front of Kafka, or use Atlas Stream Processing.

1. Run a 3-node set with a write loop at w: 1, then rs.stepDown() the primary while partitioning it, and go find the rollback BSON file. Repeat at w: "majority". 2. Deliberately fall off the oplog: set a tiny oplog (replSetResizeOplog to 200 MB), stop a secondary, write a few GB, restart it and watch it go to RECOVERING.

Expected outcome & solution sketch

(1) At w: 1 you get a file under <dbpath>/rollback/<db>.<coll>/ containing writes that the application was told succeeded and that no longer exist. Nothing replays it; recovery is a manual, human decision. At majority there is nothing to roll back. This exercise is the single best way to make write concern feel real rather than theoretical.

(2) The secondary reports it is too stale and stops. The only fix is a resync — either an initial sync from scratch, or since 4.4 the file-copy-based initial sync in Enterprise. The lesson is the formula: oplog window in seconds = oplog size ÷ oplog bytes per second, which you can read directly from db.getReplicationInfo(), and you want that window comfortably longer than your worst maintenance operation and your slowest consumer's downtime — 24 to 72 hours is a common target.

Interview Q&A

Walk me through what happens when a primary dies.

Secondaries stop receiving heartbeats and, after electionTimeoutMillis (10 seconds by default), an eligible secondary increments the term and calls for votes. It can only win with a strict majority of voting members, and voters refuse anyone whose oplog is behind their own, so the winner always has the most recent data among the majority. The new primary runs catch-up — briefly pulling any remaining entries from a more advanced secondary, bounded by catchUpTimeoutMillis — then transitions to primary and starts accepting writes. Drivers discover the change through their own monitoring, mark the topology stale, and retry the in-flight retryable operation once, so a well-configured application sees a latency blip rather than errors. When the old primary comes back, any writes it accepted that never reached the majority are rolled back into files on disk and are gone from the database, which is exactly why the default write concern is majority. Realistic total failover time is single-digit to low-double-digit seconds, and if someone needs it faster the lever is electionTimeoutMillis, at the cost of spurious elections on a jittery network.

What is the oplog and how do you size it?

It is a capped collection in the local database holding an idempotent record of every change on the primary, which secondaries tail to replicate and which change streams read. Idempotency is the design constraint: relative operations are converted to their absolute results before being logged, so re-applying an entry during recovery is safe. Sizing is a time question, not a space question — what matters is the window, oplog size divided by write throughput, which db.getReplicationInfo() reports directly. It must exceed the longest period a secondary can be behind: a maintenance window, a rebuild, an initial sync of a large dataset, or a change-stream consumer being down. The default is 5% of free disk capped at 50 GB, which is often far too small for write-heavy workloads and is why teams discover the problem when a node goes RECOVERING. Since 3.6 you can resize it online with replSetResizeOplog, so there is no excuse for leaving it at the default; I target 24 to 72 hours and alert on the window shrinking, not on the disk.

Why is a PSA topology a bad idea?

Because the arbiter contributes a vote but no data, so the set has only two copies of the data and only two members that can acknowledge a majority write. Lose or slow one data node and w: "majority" — the default since 5.0 — can no longer be satisfied by data-bearing members, so writes stall; worse, the majority commit point stops advancing, and WiredTiger must retain all history back to it, so cache pressure builds and the surviving primary degrades even for reads. You also cannot take a member down for maintenance without entering that state deliberately. Teams choose PSA to avoid paying for a third data node, and it is a false economy: the arbiter saves you storage and pays for it with your durability guarantee at the exact moment you need it. If cost is genuinely binding, a third node with lower specs, priority: 0 and no client traffic is still strictly better than an arbiter.

How do you read from secondaries safely?

Decide first whether staleness is acceptable for that specific query, because secondary reads are eventually consistent by construction — a secondary applies the oplog asynchronously, so it lags by anywhere from milliseconds to minutes. If some staleness is fine, use secondaryPreferred with a maxStalenessSeconds (minimum 90) so the driver excludes badly lagging members, and use tag sets to pin analytics traffic to a specific tagged member rather than spraying it across the ones serving users. If you need read-your-own-writes, use a causally consistent session with readConcern: "majority", which makes the secondary wait until it has caught up past your write instead of returning stale data. What I would push back on is the common motivation: "we'll read from secondaries to scale reads" is often wrong, because every secondary applies the entire write workload anyway, so you are adding read capacity without adding write capacity, and you are converting a consistency problem into a bug report. Sharding adds capacity; secondary reads redistribute it.

How would you build CDC out of MongoDB?

Change streams, with a single well-instrumented consumer per logical purpose rather than one per downstream. The consumer opens watch() with a server-side $match so filtering happens on the server, persists its resume token atomically with whatever it produced, and is fully idempotent because delivery is at-least-once. For anything beyond a couple of consumers I put a broker in the middle — the official MongoDB Kafka Connector is the well-trodden path — so the database sees one oplog reader and downstreams scale independently. Sizing the oplog is part of the design, because the resume token is only valid inside the oplog window, and I would alert on consumer lag measured as wall-clock distance between the event's cluster time and now. The two failure modes to design for explicitly: an invalidate event (from a collection drop or rename) terminates the stream and requires startAfter rather than resumeAfter to continue, and events approaching 16 MB need $changeStreamSplitLargeEvent.

What is a rollback and how do you detect one?

When a primary accepts writes that never reach a majority and then loses an election, those writes are not in the new primary's history; when the old node rejoins it must discard them to converge. Since 4.0 the discarded documents are written to BSON files under <dbpath>/rollback/ and the node then resumes as a secondary. Nothing replays those files — recovering them is a manual, case-by-case decision, and often impossible to do correctly because the world moved on. Detection is a monitoring job: alert on the ROLLBACK member state, on the presence of files in the rollback directory, and on the replSetRollback log lines; if you have an application-level idempotency key you can also reconcile. The permanent fix is to write with w: "majority", which is the default from 5.0 onward, so in practice rollbacks today mean either someone deliberately lowered the write concern for throughput, or an unacknowledged legacy driver path.

How do drivers know about topology changes?

Each driver runs a Server Discovery and Monitoring engine: it maintains a background monitoring connection to every known member, sends hello at heartbeatFrequencyMS (10 seconds by default, and immediately when an error suggests staleness), and builds a topology description from the responses. Server selection then picks a member that satisfies the read preference within serverSelectionTimeoutMS (30 seconds), preferring lower-latency members inside a localThresholdMS window. When a node reports a new primary or a network error occurs, the driver marks the topology unknown and re-scans aggressively, which is what makes a failover appear as a brief pause rather than an outage — combined with retryable reads and writes, which retry once against the newly discovered primary. Two operational consequences: an SRV connection string lets the driver learn about added members without a config change, and MongoDB 8.x added server-side signals — overload-aware server selection and ingress rate limiting — that let the cluster push back on clients rather than queueing indefinitely.

Design a multi-region MongoDB deployment for a global product.

First I would establish what the requirement actually is, because "multi-region" hides three different ones: disaster recovery, low-latency reads, or low-latency writes. For DR, a replica set spread over three regions with the majority in the primary region gives automatic failover with a write-latency penalty equal to the round trip to the second-closest region; that is the simplest thing that works and I would start there. For low-latency reads, add priority: 0 members in the read regions and route with tag-aware read preferences plus causal consistency where correctness demands it. For low-latency writes you need the data itself to be regional, which means a sharded cluster with zone sharding on a region field so each zone's ranges live on shards in that region — this also happens to be how data-residency requirements are met, which is usually the real driver. What I would say plainly is that you cannot have single-copy strong consistency and local write latency in every region simultaneously; the choice is regional partitioning of the data, and that choice has to be visible in the schema as a region key on every document.

Replication lag is at 15 minutes on one secondary. Walk me through it.

I want to know whether the secondary cannot keep up or is not being allowed to. First, is it applying at all — rs.status() for state, currentOp on the secondary for a long-running operation such as an index build or a foreground compaction, which blocks oplog application. Second, is it I/O-bound: disk latency and queue depth on that host, cache eviction pressure, and whether it is a smaller instance type than its peers, which is a startlingly common cause. Third, is the workload producing pathological oplog entries — a massive-array $push pattern generates full-document entries, so a modest logical write rate becomes hundreds of megabytes per second of oplog, and the secondary applies them single-file per document. Fourth, is something else on the box, like a backup or an antivirus scan. The immediate mitigations are to shed read traffic from that member and to pause whatever is generating the write burst; the durable fixes are schema (kill the unbounded array), capacity (match instance types), or scheduling (never build indexes and run backups on the same node at the same time). Throughout I watch the oplog window, because the real deadline is falling off it.

When would you use a delayed member, and what are its limits?

A delayed member is a human-error time machine: it applies the oplog N hours late, so if someone drops a collection or a bad migration corrupts data, you have a live copy of the world before the mistake, and you can extract from it without restoring a whole backup. I have found it most valuable when the delay comfortably exceeds the detection time for the kinds of mistakes you actually make — typically 3 to 24 hours; less than an hour is not enough to notice, more than a day gets expensive and is what real backups are for. Its limits matter: it must be priority: 0 and is usually hidden, it holds the same storage cost as any data node, and it is not a backup — it is one machine, in one place, with no history beyond its delay, and it will happily replicate a corruption you did not notice in time. It also drags on the oplog window and, if it votes, on the majority commit point, so I configure it with votes: 0. In cloud deployments continuous backup with point-in-time restore covers the same failure mode with better economics, so I would treat a delayed member as a fast-recovery convenience layered on top of backups, not instead of them.

08Sharding

Sharding is horizontal partitioning of a collection across independent replica sets. Three components: the shards (each a replica set owning a subset of the data), the config servers (a replica set, CSRS, holding the routing metadata — which ranges live where), and mongos, a stateless router that caches the routing table and forwards or scatter-gathers queries. Applications talk only to mongos. Since 8.0 you can also run a config shard, where the config server replica set also holds user data, which removes the fixed cost of three dedicated config nodes from small clusters — and 8.3 added a proper command sequence (startTransitionToDedicatedConfigServer and friends) to migrate off it later.

Everything hinges on the shard key. Documents are partitioned into contiguous ranges (called chunks) of shard-key values; the balancer moves ranges between shards to even out data size. A query that includes the shard key is targeted — routed to the one shard that owns the value. A query without it is a scatter-gather: sent to every shard, results merged by mongos. At ten shards a scatter-gather is ten times the work and its latency is the slowest shard's; that is why the interview answer to "how do you pick a shard key?" is always framed as "which queries must be targeted?".

Choosing a shard key

Three properties, and a good key needs all three. Cardinality: the number of distinct values bounds how many ranges can ever exist — sharding on country in a two-country business caps you at two ranges and therefore two shards' worth of capacity. Frequency: even if cardinality is high, a skewed distribution creates hot ranges — customerId looks fine until one customer is 40% of the data. Monotonicity: a key that increases with time (a timestamp, an ObjectId, an auto-increment) sends every insert to the single shard owning the top range, so you get a permanent hot shard while the others idle. Hashed sharding fixes monotonicity by hashing the key, at the cost of destroying range queries and ordered scans.

Since 4.4 you can refineCollectionShardKey to append fields to an existing key (useful to add cardinality), and since 5.0 you can reshardCollection to change it entirely — an online copy-and-switch that was originally very expensive and got dramatically faster in 8.0, which also added unshardCollection and moveCollection for moving an unsharded collection to a specific shard. The old "your shard key is forever, choose perfectly" framing is out of date, and saying so — with the version numbers — is a good currency signal. It is still true that resharding a multi-terabyte collection is a project, not an afternoon.

// Multi-tenant SaaS: tenant-targeted queries, even distribution, no hot range.
sh.shardCollection("shop.orders", { tenantId: "hashed", _id: 1 });

// Time-ranged analytics with hot/cold zones: ranged key + zones

The balancer, chunks and orphans

The balancer runs on the config server primary, compares data size per shard (since 6.0 it balances by data size, not by chunk count) and migrates ranges until the imbalance is below a threshold. The default range size is 128 MB (raised from 64 MB in 6.0). Auto-splitting was removed in 6.1: ranges are now split as part of migration rather than by a background splitter, which removed a whole class of contention. A migration copies documents to the destination, catches up on changes, enters a brief critical section where writes to that range block, then commits the metadata change; that critical section is why a migration storm shows up as latency spikes, and why you configure a balancing window during off-peak hours.

Orphans are documents left on a shard that no longer owns their range — after a failed or interrupted migration, or during the cleanup delay. Queries filter them out using the SHARDING_FILTER stage (which is why a query needs the shard key fields in its index to be covered), and a background cleaner deletes them; 8.2 changed orphanCleanupDelaySecs from 900 to 3600 seconds, giving in-flight cursors more room at the cost of orphans living longer, and 8.2/8.3 added smarter orphan-cleanup handling and sharding-inconsistency detection. Orphans matter operationally because they inflate db.stats(), they make an unfiltered count() wrong, and a large accumulation is a symptom of repeatedly failing migrations.

The last structural constraint: unique indexes must be prefixed by the shard key, because uniqueness can only be enforced locally on a shard. A globally unique email on a collection sharded by tenantId is simply not expressible; you either put the field in the shard key, or you enforce uniqueness in a separate small unsharded "claim" collection that you write to first. Candidates who know this without prompting have actually run a sharded cluster.

Interview trap

Sharding too early, and sharding for the wrong reason. Sharding multiplies operational complexity — three more replica sets to run, routers to size, a balancer to schedule, backups that must be consistent across shards, and a query layer that must carry the shard key everywhere — and it does not make individual queries faster; it makes capacity larger. A single modern replica set comfortably handles several terabytes and tens of thousands of operations per second, and most "we need to shard" conversations are actually missing indexes, an unbounded array, or a working set that no longer fits in cache. The lead answer names the three legitimate triggers: the working set no longer fits in the largest affordable machine's RAM, write throughput exceeds one primary's capacity, or data residency requires geographic partitioning. And it names the prerequisite: you must be able to state which shard key makes your top queries targeted, before you shard.

(2) With the shard key, explain shows a single entry under shards and SINGLE_SHARD; without it, every shard appears and the merge happens on mongos (SHARD_MERGE). Add a sort without the shard key and the merge becomes a sorted merge, which is where scatter-gather gets genuinely expensive.

Interview Q&A

How do you choose a shard key?

I start from the query list, not from the data: which operations must stay single-shard at target scale, because those determine what has to be in the key. Then I test the candidate against three properties — high cardinality so ranges can keep splitting, even frequency so no single value is a hotspot, and non-monotonicity so inserts spread rather than piling on the shard owning the maximum. For most business systems the answer is a tenant or customer identifier, hashed or compounded with a second field, because it makes the dominant access pattern targeted and distributes naturally. I would also check the write pattern separately from the read pattern, since they often disagree: a time-ordered key is great for range reads and terrible for inserts, which is what zone sharding or a compound key with a high-cardinality prefix resolves. Finally I would say out loud that this is no longer irreversible — refineCollectionShardKey since 4.4 appends fields, and reshardCollection since 5.0, much faster in 8.0, changes it entirely — but that resharding a multi-terabyte collection is still a planned project with a real cost.

What is the difference between hashed and ranged sharding?

Ranged sharding partitions on the raw value, so documents with adjacent key values live together — which makes range queries and sorts on the key efficient, and makes zone sharding possible, but concentrates writes if the key is monotonic. Hashed sharding partitions on a hash of the key, giving near-perfect distribution regardless of the input distribution, at the cost that any range query on that field becomes a scatter-gather because adjacent values are deliberately scattered. The compromise I most often use is a compound key with a hashed prefix and a ranged suffix, which gives even distribution across tenants and ordered locality within one. One detail worth knowing: hashed indexes hash to a 64-bit value, so they are equality-only and cannot support sorts, and MongoDB will not let you create a unique hashed index on its own. And zone sharding effectively requires a ranged component, because zones are defined as key ranges — which is why data residency and hashed keys are in tension.

What is a scatter-gather query and how do you avoid one?

A query without the shard key, which mongos must broadcast to every shard, then merge. Its cost is N times the work and its latency is bounded below by the slowest shard's response, so tail latency degrades as you add shards — the exact opposite of the scaling you wanted. Avoiding it is a design activity: the shard key must appear in the filter of your hot queries, which usually means threading a tenant or partition identifier through the entire application, enforced in a repository layer rather than by convention. When a query genuinely cannot carry the key — a global admin search, say — the options are a secondary index-only collection keyed differently, an Atlas Search index which is maintained separately from the shard topology, or accepting the scatter for a low-volume path. I would also monitor it rather than assume: the profiler and explain both tell you how many shards a query touched, and "percentage of operations that are single-shard" is a metric worth having on a dashboard.

Explain the balancer and what it can and cannot fix.

The balancer runs on the config server primary and moves ranges between shards to equalise data size — since 6.0 it balances by size rather than chunk count, and since 6.1 splitting happens during migration rather than via a separate auto-splitter. Each migration copies the range, catches up, enters a short critical section during which writes to that range block, and then commits the routing change, which is why heavy balancing shows up as latency spikes and why you set a balancing window for off-peak hours. What it cannot fix is a bad shard key: if inserts are monotonic, the balancer will move ranges away from the hot shard while new writes keep landing there, so you get continuous migration overhead and no relief. It also cannot split a jumbo range whose entire key value is identical — low-cardinality keys create indivisible ranges. So the balancer is a data-placement mechanism, not a load-balancing mechanism, and diagnosing "one shard is at 90% CPU while the others idle" starts with the key, not with the balancer settings.

What are orphaned documents?

Documents physically present on a shard that no longer owns their range — the residue of a migration that was interrupted, or the copy left behind during the cleanup delay. They are invisible to normal queries because each shard applies a SHARDING_FILTER stage using the shard key, which is also why a query wanting to be covered must include the shard key fields in its index. They do consume storage and cache, they inflate db.stats() and collection.count() estimates, and they can be read by anything that bypasses the router or uses readConcern: "available". A background cleaner removes them after orphanCleanupDelaySecs, which MongoDB 8.2 raised from 900 to 3600 seconds to give long-running cursors more room; 8.2 and 8.3 also added better cleanup handling and sharding inconsistency detection. Operationally, a growing orphan count means migrations are failing repeatedly, and that is the thing to investigate rather than the orphans themselves.

When should a team not shard?

When they have not exhausted vertical and structural options, which is most of the time. A single replica set on modern hardware handles multiple terabytes and very high operation rates, so before sharding I want to see: the working set actually measured against the WiredTiger cache, an index review with $queryStats and $indexStats, no unbounded arrays, archived cold data moved out to a cheaper tier, and analytics moved off the operational nodes. Sharding costs you a permanent tax — the shard key must be in every hot query, unique constraints become shard-key-prefixed, backups must be coordinated, cross-shard transactions are slower, and every incident now has a routing dimension. I would also push on the timeline: if the trigger is projected growth eighteen months out, the right move is to make the schema shard-ready now (introduce the tenant key, keep queries targeted) and defer the actual sharding, because a shard-ready schema is cheap and a premature sharded cluster is expensive every day.

How do transactions behave across shards?

Multi-document transactions have worked across shards since 4.2, implemented as a two-phase commit coordinated by one participating shard, with snapshot read concern giving a consistent cross-shard view. They are correct, and they are considerably more expensive than single-shard transactions: extra round trips for prepare and commit, coordination state that must itself be durable, and a longer window in which conflicting operations block. So the guidance is to keep a transaction on one shard whenever you can, which is a modelling instruction — put the documents that must change together under the same shard key value, so the transaction is single-shard and takes the fast path. There are also operational interactions to name: a transaction that spans a range being migrated can abort, and the default 60-second transactionLifetimeLimitSeconds applies. My rule in review is that a cross-shard transaction on a hot path is a design smell; on a rare administrative path it is perfectly reasonable.

How do you remove a shard from a cluster?

By draining it: the balancer moves every range it owns to the remaining shards, any unsharded collections whose primary shard it is get moved with movePrimary, and only then is it removed from the cluster metadata. Historically this was the single removeShard command, called repeatedly to poll progress — and as of MongoDB 8.3 that command is deprecated in favour of an explicit sequence: startShardDraining, shardDrainingStatus to poll, stopShardDraining to abort, and commitShardRemoval to finish. The new commands exist because the old overloaded one made it easy to commit a removal before draining had really finished. Practically, draining a large shard takes hours to days and generates continuous migration load, so I schedule it into balancing windows, watch for jumbo ranges that cannot move, and confirm with sh.status() that no ranges and no primary-shard databases remain before committing.

What is zone sharding for?

Pinning ranges of the shard key to a labelled group of shards. Two uses dominate. Data residency: tag shards in the EU with an EU zone and map the key range where region: "EU" to it, which enforces at the database level that European users' documents never leave European hardware — and note this requires the region to be part of the shard key, which is a schema decision made long before the compliance conversation. Tiered storage: map recent time ranges to shards with fast NVMe and older ranges to cheaper, larger shards, so hot and cold data get different hardware without the application knowing. The mechanics to remember are that zones are defined on key ranges so they need a ranged (not purely hashed) key component, the balancer will not move a range outside its zone, and changing zone boundaries triggers migrations, so it is an operation you schedule. The trap is defining zones that leave part of the key space unassigned or that overlap, which produces confusing balancing behaviour.

Your cluster has one shard at 90% CPU and three at 15%. Diagnose it.

I would separate three candidate causes before touching anything. First, data skew: sh.status() and per-shard db.stats() tell me whether that shard simply holds more data, which points at a low-cardinality or badly distributed shard key, or at one dominant tenant — the jumbo-range case. Second, traffic skew with even data: the shard key distributes storage fine but the hot key values all land on one shard, classic for a monotonic time-based key where all recent documents are on the maximum range, and visible as a per-shard write-rate imbalance in the metrics. Third, something local to that host — a slow disk, a failing member forcing all reads to one node, an index build, a backup running. The fixes differ completely: skewed data with a bad key means refineCollectionShardKey or a resharding project; hot-range writes mean a hashed prefix or a bucketed key; a local problem means fixing that host. What I would not do first is fiddle with the balancer, because balanced bytes and balanced load are different things and the balancer only manages the former.

09Transactions & concurrency

Concurrency in MongoDB is WiredTiger's MVCC, and everything else follows from it. Every operation runs inside a WiredTiger transaction with a read timestamp, seeing a consistent snapshot of the data as of that timestamp; writers do not block readers, and readers do not block writers, because a writer creates a new version rather than mutating in place. Two writers touching the same document collide at commit time and one gets a WriteConflict — which, for ordinary single-document operations, the server retries internally so the application never sees it. This is optimistic concurrency, not locking, and it is why "MongoDB has document-level locking" is a slightly misleading phrase you will nonetheless hear.

Above WiredTiger sits a hierarchy of intent locks (global, database, collection) that exist to coordinate DDL, not data. A createIndex, a collMod, a drop or a rename takes an exclusive collection lock briefly; ordinary reads and writes take intent locks that do not conflict with each other. That is why an index build in 4.2+ is mostly non-blocking but still has two short exclusive moments, and why a drop on a busy collection can produce a visible latency spike.

Multi-document transactions

Introduced for replica sets in 4.0 and for sharded clusters in 4.2, transactions give snapshot isolation across multiple documents, collections and databases. They are real ACID transactions and they are the right tool for genuine cross-aggregate invariants — but they carry costs the document model was designed to avoid, and knowing those costs is the interview question.

The single most important implementation detail is that you must use the driver's withTransaction helper, not a hand-rolled start/commit. // C#/.NET driver 3.x - withTransaction equivalent, with the retry semantics built in.
using var session = await client.StartSessionAsync();

await session.WithTransactionAsync(async (s, ct) =>
{
    var from = await accounts.FindOneAndUpdateAsync(s,
        Builders<Account>.Filter.Eq(a => a.Id, fromId) &
        Builders<Account>.Filter.Gte(a => a.Balance, amount),
        Builders<Account>.Update.Inc(a => a.Balance, -amount),
        cancellationToken: ct);

    await accounts.UpdateOneAsync(s,
        Builders<Account>.Filter.Eq(a => a.Id, toId),
        Builders<Account>.Update.Inc(a => a.Balance, amount),
        cancellationToken: ct);

    await ledger.InsertOneAsync(s, new Entry(fromId, toId, amount, DateTime.UtcNow),
        cancellationToken: ct);
    return true;
},
new TransactionOptions(

    writeConcern: WriteConcern.WMajority,
    maxCommitTime: TimeSpan.FromSeconds(5)));

Note the guard inside the update filter (Balance >= amount) rather than a read-then-check: even inside a transaction, expressing the precondition as part of the write is what makes the operation resilient, and it means the same code degrades gracefully into a single-document version if you later decide the ledger entry does not need to be transactional.

The alternatives you should reach for first

Most invariants that look transactional are not. Single-document atomicity covers anything you can co-locate — this is the real reason to embed. Optimistic concurrency with a version field in the filter and $inc in the update handles read-modify-write without any transaction. The outbox pattern — write the state change and an outbox event in the same document (or the same transaction) and let a change-stream consumer publish it — solves the "update the database and publish a message atomically" problem that people reach for distributed transactions to solve. And for long multi-step workflows, a saga with explicit compensating actions is the correct pattern, because a 60-second transaction limit is not a bug to work around, it is the database telling you that a five-minute business process is not a database transaction.

Interview trap

Answering "MongoDB doesn't support transactions" — badly out of date since 4.0/4.2 — or the mirror image, using transactions everywhere as if MongoDB were a relational database with a funny query language. Both signal that you have not run it at scale. The precise position: transactions are ACID and correct, they cost roughly an order of magnitude more than the equivalent single-document write on a hot path, and their existence does not change the modelling advice, because a schema that needs a transaction for its most common operation is a schema that split one aggregate across two documents. The subtler trap is not knowing the error taxonomy: a transaction that fails with TransientTransactionError must be retried in full, and one that fails with UnknownTransactionCommitResult must have its commit retried — treating both as failures loses writes, and treating both as successes duplicates them.

(1) With heavy contention on the same two documents you will see repeated write conflicts and retries, and throughput will be a fraction of the non-transactional version — which is the honest cost of the guarantee. The instructive part is watching how quickly contention on one hot document dominates: if both transfers touch a single "totals" document, you have serialised the entire system on it, and the fix is sharding that counter into N sub-counters summed at read time.

(2) You get TransactionTooOld / a transaction-expired error at commit, because the server reaped it at transactionLifetimeLimitSeconds. The lesson to carry into design reviews: never hold a transaction open across a network call to another service, a user interaction, or a large batch — chunk the batch, and use a saga for the workflow.

Interview Q&A

Explain MongoDB's concurrency model.

WiredTiger provides multi-version concurrency control: each operation gets a read timestamp and sees a consistent snapshot, writers create new versions instead of mutating, so readers never block writers and vice versa. Conflicts are detected at commit — two writers to the same document produce a WriteConflict, and for ordinary single-document operations the server transparently retries, so applications rarely see it. Above that sits a lock hierarchy of global, database and collection locks, but ordinary reads and writes take only intent locks that do not conflict with each other; the exclusive locks exist for DDL like index creation, collMod and drops. The practical implications are that hot-document contention is the real bottleneck rather than any collection-level lock, that long-lived snapshots — big transactions, long-running cursors, a stalled majority commit point — force WiredTiger to retain history and put pressure on the cache, and that concurrency limits are enforced by a ticket system, which MongoDB has been making adaptive since 7.0.

When should you use a multi-document transaction?

When a business invariant genuinely spans documents that cannot be co-located, and the cost of a temporary inconsistency is unacceptable — a double-entry ledger, moving an item between two aggregates with a uniqueness constraint on both sides, or writing a state change plus an outbox event when the two cannot live in one document. Before reaching for one I ask whether embedding would put the whole invariant in one document, whether an optimistic-concurrency update with a version field solves it, and whether an eventually consistent compensating flow is actually acceptable — often it is, and it is cheaper and more available. When I do use one I keep it short and single-shard, put the precondition in the update filter rather than in a preceding read, use the driver's withTransaction helper for the retry semantics, and set an explicit maxCommitTimeMS. And I would say plainly that a hot path taking a transaction on every request is a modelling failure I would want to fix, not an implementation to optimise.

What isolation level do MongoDB transactions provide?

Snapshot isolation: with readConcern: "snapshot" a transaction sees a consistent view of the data as of a single point in time, and its writes are invisible to others until commit. That prevents dirty reads, non-repeatable reads and, for the data it reads, phantom-free behaviour within the snapshot — but it is not serialisable, so write skew is possible: two transactions can read overlapping data, each check an invariant that holds in its own snapshot, and both commit into a state where it does not. The classic example is two transactions each verifying that at least one doctor remains on call and each removing a different doctor. MongoDB detects write conflicts on documents actually written, not on documents merely read, so the defence is to make the invariant a write: touch the document you are asserting about — bump a version on the shared record — so the conflict is detected. Being able to name write skew and its mitigation is a strong senior-plus answer.

How do you implement optimistic concurrency without a transaction?

Put a monotonically increasing version field on the document, include the version you read in the update's filter, and increment it in the update: updateOne({_id: id, version: 7}, {$set: {...}, $inc: {version: 1}}). If matchedCount is zero, somebody else won and you re-read and retry — with a bounded retry count and jittered backoff, because an unbounded retry loop under contention is a livelock. This is a single atomic operation with no transaction, no locks and no coordination, and it composes with retryable writes. It is the right default for the "read a document, compute something, write it back" pattern that people wrongly wrap in a transaction. Its limits are that it only protects one document, and that under very high contention on the same document the retry rate becomes the bottleneck — at which point the answer is to decompose the hot document, for example by splitting a global counter into per-shard counters summed on read.

What are TransientTransactionError and UnknownTransactionCommitResult?

They are the two error labels the transaction specification defines, and handling them correctly is the whole of correct transaction code. TransientTransactionError means the transaction was aborted before commit for a reason that may not recur — a write conflict, a primary stepping down, a chunk migration — and the correct response is to retry the entire transaction callback from the beginning, because none of its writes were applied. UnknownTransactionCommitResult means the commit was sent but the outcome is unknown, typically a network failure during commit, and the correct response is to retry the commit only, which is safe because commit is idempotent within the session. Getting these backwards is dangerous: retrying the whole transaction after an unknown commit can double-apply, and failing outright on a transient error turns a routine conflict into a user-visible error. The reason I insist on withTransaction in review is that it implements exactly this, including a sensible overall time limit, and hand-rolled code almost never does.

What is the outbox pattern and why does MongoDB suit it?

It is the standard solution to the dual-write problem: you cannot atomically update the database and publish a message to a broker, so instead you write the state change and the event into the same database atomically, and a separate process reads the events and publishes them. MongoDB suits it unusually well because the event can often be a field or subdocument of the same document you are already updating, which makes the "transaction" a single-document write with no transaction at all — and because change streams give you a supported, resumable reader for the publishing side, with a resume token you persist alongside your progress. The delivery guarantee is at-least-once, so consumers must be idempotent, which is true of any broker-based system anyway. The alternatives I would compare it against are two-phase commit across the database and the broker, which nobody should build, and dual writes with compensation, which quietly loses messages under partial failure.

A batch job updates two million documents. How do you structure it?

Not as one updateMany and not as one transaction. One updateMany is a single long-running operation holding a snapshot, producing a huge oplog burst that lags secondaries, non-retryable if it fails, and unstoppable without killOp. A transaction would blow the 60-second lifetime limit. Instead I chunk by _id range or by an indexed key, a few thousand documents per batch, with a filter that excludes already-processed documents so the job is idempotent and resumable, and I throttle between batches with a controller that watches replication lag and backs off when it rises — that feedback loop is the part people skip and the reason batch jobs cause incidents. I run it with maxTimeMS per batch, log progress to a control document so it can resume after a restart, and prefer ordered: false bulk writes for throughput. If the transformation is expressible server-side, an aggregation with $merge over the same ranges is often faster than pulling documents through the client.

How do write conflicts show up, and what do you do about them?

For ordinary operations they mostly do not: WiredTiger detects the conflict at commit and mongod retries internally, so the application sees only latency. They surface explicitly inside multi-document transactions, where the conflict aborts the transaction with a TransientTransactionError for the driver to retry, and they surface indirectly as rising latency and CPU when a single document is contended. Diagnosing them means looking at serverStatus().wiredTiger.transaction counters for rollbacks, at the slow log for operations with high writeConflicts, and then finding the hot document — it is almost always a counter, a "current state" singleton, or a queue head. The fixes are structural rather than configurational: split the hot document into N shards summed at read time, replace read-modify-write with a server-side operator that cannot conflict semantically, batch updates so fewer writers touch the document, or move the contended value out of the database entirely into something built for it. Increasing retries is not a fix; it converts a throughput problem into a latency problem.

Do transactions work the same on sharded clusters?

Semantically yes — snapshot isolation across shards, atomic commit or abort — but the implementation is a two-phase commit with a coordinator elected among the participating shards, so the cost profile is different. A cross-shard transaction pays extra network round trips for prepare and commit, keeps locks and snapshots held for longer, and interacts with chunk migrations: a migration touching a range under an open transaction can cause aborts. There are also practical limits — the transaction still has to finish inside transactionLifetimeLimitSeconds, and the coordinator's state must itself be durable, which adds writes. So the design instruction is to make transactions single-shard by construction: choose a shard key such that documents that change together share a shard-key value, which usually means the tenant or aggregate identifier. When I see a design requiring frequent cross-shard transactions, I treat it as evidence the shard key is wrong rather than as a performance problem to tune.

How would you explain to a skeptical relational team that MongoDB's consistency story is sound?

By being precise rather than defensive. MongoDB is a single-master-per-shard system using a Raft-derived election protocol; with the default w: "majority" write concern an acknowledged write cannot be lost to a failover, and with readConcern: "majority" you never read data that can vanish. It offers snapshot-isolated multi-document ACID transactions since 4.0/4.2, including across shards. It has been through Jepsen analyses, which found real problems in older versions — notably around read concern and causal consistency defaults — and those findings drove the changes that landed by 4.x and 5.0, including making majority the default write concern. What I would not claim is serialisability, unlimited transaction duration, or that transactions are cheap; and I would point out that the honest comparison is against how the relational system is actually configured, since a Postgres cluster with asynchronous replication and read replicas has exactly the same staleness properties. The strongest argument is usually to show them the knobs — write concern, read concern, sessions — and let them see that the guarantees are explicit and per-operation rather than global and implicit.

10WiredTiger & performance operations

WiredTiger has been the only storage engine since MMAPv1 was removed in 4.2, and almost every MongoDB performance question reduces to how it uses memory. The model: documents and index pages live in the WiredTiger cache, which by default is max(50% of (RAM − 1 GB), 256 MB); the operating system's page cache holds the compressed on-disk form, so a machine effectively has two caches with different contents — uncompressed pages in WiredTiger, compressed blocks in the OS. Data is written to checkpoints roughly every 60 seconds, and durability between checkpoints comes from the journal (write-ahead log), which is flushed at least every 100 ms or on a j: true write. Since 8.2 you can express the cache size as a percentage of RAM rather than an absolute number, which finally makes a single configuration template correct across heterogeneous instance sizes.

The number that decides whether a deployment is healthy is the working set — the documents and index pages actually touched by live traffic — versus the cache. When the working set fits, reads are memory-speed and the disk sees mostly writes. When it does not, every read may fault a page in and evict another, and performance does not degrade gracefully: it falls off a cliff, because eviction itself consumes CPU and the application's threads start doing eviction work. The symptoms to name in an interview, in order of appearance: rising wiredTiger.cache.bytes read into cache, then pages evicted by application threads becoming non-zero, then cache overflow/dirty-bytes climbing, then latency and ticket queueing.

Compression, and the storage numbers people get wrong

Collections are compressed with snappy by default (fast, ~2–4×); zstd (4.2+) typically gives 20–50% better ratios for a few percent more CPU and is the right default for cold or archival collections; zlib is the legacy high-ratio option. Indexes use prefix compression, which is why a compound index whose leading field repeats compresses extremely well — and why putting the low-cardinality field first is good for size even when it is bad for selectivity. Two consequences that surprise people: the on-disk size is not the memory size, because the cache holds uncompressed pages, so "my data is 200 GB on disk" tells you little about the RAM you need; and changing the compressor only affects newly written blocks, so you need a resync or a rewrite to realise it.

Saturation: tickets, queues and load shedding

WiredTiger admits a bounded number of concurrent read and write operations — historically a fixed 128 each, and since 7.0 dynamically adjusted by an execution-control algorithm that watches throughput and latency. When the tickets run out, operations queue, and serverStatus().wiredTiger.concurrentTransactions (or the queues.execution.* metrics expanded in 8.3) shows available tickets at zero with a growing queue. That is the canonical saturation signal, and it is much more actionable than CPU: tickets exhausted with low CPU means you are I/O-bound or lock-bound, tickets exhausted with high CPU means you are genuinely compute-bound. MongoDB 8.2 added query-stats metrics for delinquent tickets — operations that held a ticket far longer than expected — which is a direct pointer at the queries hogging concurrency.

The 8.x line has also grown genuine load shedding, marketed as Intelligent Workload Management: an ingress request rate limiter with per-application exemptions (ingressRequestRateLimiterApplicationExemptions, 8.3), pre-authentication connection limits (preAuthMaximumMessageSizeBytes, capMemoryConsumptionForPreAuthBuffers), overload-aware server selection so drivers steer away from a struggling node, and client backoff parameters the server can dictate (defaultClientBaseBackoffMillis, defaultClientMaxBackoffMillis, defaultClientRetryAttempts). Node.js driver 7.2 (April 2026) added client-side support for these. The shift is important to articulate: MongoDB is moving from "queue everything and hope" to explicit admission control, which is what mature databases do.

Interview trap

Raising the WiredTiger cache to 80–90% of RAM "because MongoDB needs memory". That starves the OS page cache — which holds the compressed blocks WiredTiger reads from — and leaves nothing for connection buffers, sorts, aggregation spill files and the operating system itself, so the usual result is worse performance and eventually an OOM kill. The 50% default is deliberate. The second trap is diagnosing by CPU alone: a MongoDB node at 40% CPU with zero available write tickets and a growing queue is completely saturated, and adding CPU will not help. The third is treating db.stats()'s storageSize as a memory requirement — it is compressed, and the cache holds uncompressed pages, so the honest sizing exercise is measuring the working set (index sizes plus the hot fraction of documents), not the total.

Try it

1. Push a node over the eviction cliff on purpose: set cacheSizeGB to 1, load 10 GB of data, and run a random-access read workload while watching pages evicted by application threads and p99 latency. Then add a covering index for the query and watch the working set shrink. 2. Compare compressors: create the same 5 GB collection with snappy and with zstd and compare storageSize, insert throughput and CPU.

Expected outcome & solution sketch

(1) Latency stays flat while the working set fits, then degrades sharply — not linearly — once application threads start evicting. The covering index is the interesting half: by answering the query from the index alone you shrink the working set to the index pages, which can turn a 10 GB working set into a 400 MB one. That is the mechanism behind "add the right index" being a memory fix, not just a CPU fix.

(2) Expect zstd to be roughly 20–50% smaller with a few percent more CPU on write. The decision rule I would state: snappy for hot collections where CPU per operation matters, zstd for large, less-hot collections where the storage and the resulting cache efficiency dominate — and remember the change only applies to newly written blocks.

Interview Q&A

How does the WiredTiger cache work and how big should it be?

It holds uncompressed B-tree pages — both documents and index pages — and defaults to half of RAM minus a gigabyte, with the OS page cache holding the compressed on-disk blocks underneath. That split is deliberate: raising the WiredTiger cache to 80% of RAM starves the page cache, the connection buffers, sort and aggregation memory and the OS, and usually makes things worse or triggers an OOM kill. Since 8.2 you can configure it as a percentage of RAM, which is a genuine operational improvement because one configuration template now works across instance sizes. The size that actually matters is not total data but the working set: index pages that are traversed plus the fraction of documents your live traffic touches. I size by measuring — cache hit behaviour, bytes read into cache per second, and whether application threads are doing eviction — rather than by a rule of thumb, and when the working set does not fit, my first move is usually a covering index or a schema change that shrinks hot documents, because that is far cheaper than more RAM.

What does it mean when application threads are evicting pages?

It means the cache crossed the 95% eviction_trigger threshold and the background eviction threads could not keep up, so MongoDB conscripts the threads that are serving your queries into doing eviction work before they can proceed. That is the performance cliff: throughput collapses non-linearly, latency spikes, and the node can appear to be doing nothing useful while CPU is high. The equivalent for writes is the 20% dirty-bytes trigger, which shows up as write latency spikes. Diagnosis is a handful of serverStatus().wiredTiger.cache counters — pages evicted by application threads, tracked dirty bytes, bytes read into cache — which should be on a dashboard before you need them. The causes are almost always one of: the working set outgrew the cache, an analytical query scanned a huge cold collection and flooded the cache, a stalled majority commit point or long-lived snapshot forced history retention, or a massive-document update pattern is generating enormous dirty pages.

How do you tell whether a MongoDB node is saturated?

Tickets and queues, not CPU. WiredTiger admits a bounded number of concurrent read and write operations — 128 each historically, adaptive since 7.0 — and when the available count reaches zero, operations queue, which is visible in serverStatus().wiredTiger.concurrentTransactions and globalLock.currentQueue, plus the richer queues.execution.* metrics in 8.3. Tickets exhausted with modest CPU means the bottleneck is I/O or contention; tickets exhausted with pegged CPU means you are compute-bound and probably scanning too much. From there I go to currentOp sorted by running time to see what is holding the tickets, and to $queryStats — including the delinquent-ticket metrics added in 8.2, which point directly at operations that hold concurrency far longer than expected. The reason this matters organisationally is that autoscalers usually watch CPU, so a MongoDB cluster can be completely saturated while every autoscaling signal looks fine.

Why is my disk usage not going down after deleting millions of documents?

Because WiredTiger marks the space as reusable inside its data files rather than returning it to the filesystem; the files stay the same size and new inserts fill the freed space. The obvious tool, compact, rewrites the collection and releases space, and it is far less disruptive than it used to be, but it still consumes I/O and on older versions took a blocking lock, so on a replica set I run it member by member, taking each out of rotation. The alternative that is often better is an initial resync of one secondary at a time, which rebuilds the files compactly and also fixes index bloat, then step down and repeat. What I would question first is the deletion pattern itself: recurring mass deletes usually mean the data should be in a TTL-indexed collection, a time series collection, or partitioned so old data is dropped by dropping a whole collection — because dropping a collection is instant and returns the space immediately, which is why time-partitioned collections remain a legitimate design in 2026.

What do checkpoints and the journal each protect against?

Checkpoints are consistency snapshots written roughly every 60 seconds; after an unclean shutdown WiredTiger can recover to the last checkpoint without any log replay. The journal is the write-ahead log covering the window between checkpoints, flushed at least every 100 milliseconds and synchronously when a write uses j: true, so it bounds how much a single node can lose to a crash to roughly the flush interval. The interaction to understand is that the journal protects a single node, while write concern protects the cluster: {w: "majority"} means a majority of nodes have the write, which survives losing a machine entirely, whereas {j: true, w: 1} means one node has it on disk and survives that node's power loss but not its destruction. For most systems majority write concern is the more valuable guarantee, and j: true is added only when correlated power loss across the replica set is genuinely in the threat model. Operationally, checkpoints are also worth knowing about because they produce a periodic I/O burst you can see as a 60-second sawtooth in latency graphs on I/O-constrained hardware.

Which compressor would you choose, and why?

snappy is the default and is right for hot, latency-sensitive collections: decompression is cheap enough to be nearly free, and the ratio is typically two to four times. zstd, available since 4.2, gives noticeably better ratios — often 20 to 50% smaller than snappy — for a modest CPU increase, and I default to it for large, less-hot collections, archives, and anywhere storage cost or cache efficiency dominates. zlib is the legacy high-ratio option and is generally dominated by zstd. Indexes use prefix compression, which is separate and always on, and it is why a compound index with a repeated leading value is much smaller than its key count suggests. Two operational notes: the setting applies per collection at creation (or via collMod for new blocks), so realising a change requires rewriting the data, typically via a rolling resync; and because the cache holds uncompressed pages, a better compressor reduces disk and page-cache pressure but does not directly buy you more WiredTiger cache headroom.

How do you plan capacity for a MongoDB deployment?

I work from four numbers rather than a rule of thumb. Working set: total index size plus the fraction of documents that live traffic touches, which I measure rather than guess, and which must fit comfortably in the WiredTiger cache with room for growth. Write throughput in bytes per second, because that determines the oplog window for a given oplog size and drives replication capacity. IOPS and latency of the storage, since the eviction and checkpoint behaviour is unforgiving on slow disks and MongoDB is far more latency-sensitive than throughput-sensitive. And connection count, because each connection has a memory cost and drivers with badly sized pools across many application instances routinely exhaust a server. Then I plan the growth curve and the failure state — capacity must be sufficient with one node down, since that is when the remaining members carry the load. Finally I decide the scaling axis honestly: vertical until the working set no longer fits the largest affordable machine, then shard, and never shard as a first response to a query problem.

What is MongoDB doing about overload in the 8.x line?

Adding real admission control instead of unbounded queueing. The pieces are an ingress request rate limiter with per-application exemptions, pre-authentication limits on connection memory and message size so an unauthenticated flood cannot consume the server, overload-aware server selection so drivers steer traffic away from a struggling member, and server-dictated client backoff and retry parameters that the Node.js driver picked up in version 7.2 in April 2026. There is also better visibility: expanded execution-queue metrics, connection-pool statistics collected into FTDC for mongod, delinquent-ticket metrics in query stats, and cache-pressure query parameters. The judgment I would offer is that this changes how you design for overload: previously the only defence was client-side — circuit breakers, bounded pools, timeouts on every operation — and those are still mandatory, but now the server can shed load deterministically rather than degrading for everyone, which makes the failure mode partial and recoverable instead of total.

Your p99 is fine but p999 has periodic 500 ms spikes. Where do you look?

Periodicity is the clue, so I start by measuring the period. A 60-second sawtooth points at WiredTiger checkpoints flushing dirty pages, which is an I/O capacity problem rather than a query problem. A spike every few minutes can be TTL deletion waves or a scheduled job — a large TTL expiry batch is a burst of real writes that hits the oplog and the cache. Around 10 seconds suggests election timeouts or driver heartbeat interactions; longer, irregular spikes often correlate with chunk migrations entering their critical section on a sharded cluster, or with a backup or index build on the node being read. I would correlate the latency histogram against serverStatus time series — dirty bytes, eviction counters, tickets, oplog write rate — and against the balancer's migration log. The fixes follow the cause: faster or less contended storage and more frequent smaller checkpoints for the first, staggering TTL timestamps for the second, balancing windows for migrations, and moving backups to a hidden member. What I would resist is treating tail latency as noise, because at scale p999 is somebody's whole experience.

How do you approach an incident where MongoDB is "slow" and nobody knows why?

I run a fixed sequence so I do not thrash. First, scope: is it one operation shape, one collection, one node, or everything — because that immediately splits query problems from capacity problems from cluster problems. Second, currentOp sorted by running time, which usually names the culprit within seconds and tells me whether to kill something. Third, the saturation trio: tickets available, queue depth, and whether application threads are evicting. Fourth, cluster health: rs.status() for a down or lagging member, since one lost secondary redistributes its load and can stall majority writes; on a sharded cluster, whether migrations are running. Fifth, what changed — a deploy, an index change, a data import, a new tenant, an expired certificate — because "nothing changed" is false about 90% of the time. Only then do I look at query plans in detail. Throughout, I mitigate before I diagnose where I safely can: shed the offending workload, kill the runaway operation, pause the balancer — and I capture currentOp, serverStatus and FTDC diagnostic data before restarting anything, because a restart destroys the evidence along with the symptom.

Time series collections

Introduced in 5.0, a time series collection is a first-class collection type that looks like a normal collection to your queries but stores data as internal buckets: measurements sharing a metaField value and a time window are packed into a single hidden document with columnar storage per field. That is the bucket pattern from unit 02, implemented by the server with compression the hand-rolled version cannot match — typically several times smaller — and with query rewrites that unpack lazily. You declare timeField, optionally metaField (the identity of the series: device, host, symbol), and a granularity or explicit bucketMaxSpanSeconds/bucketRoundingSeconds.

The evolution matters: 5.0 was insert-only, 5.1 added deletes, 6.0 added updates on the meta field, secondary indexes on measurements, sharding of time series collections and columnar-style improvements, and 8.0 brought roughly 60% faster aggregations on time series data. The rules to remember: pick the metaField as the thing you always filter by, because it is the bucketing dimension; expiry is a TTL on the whole bucket via expireAfterSeconds, which is far cheaper than deleting individual measurements; and out-of-order or wildly-spread timestamps defeat bucketing, so a backfill of historical data should set an appropriate granularity or it will produce thousands of tiny buckets.

db.createCollection("readings", {
  timeseries: { timeField: "ts", metaField: "device", granularity: "minutes" },
  expireAfterSeconds: 60 * 60 * 24 * 90        // 90-day retention, bucket-level TTL
});
db.readings.createIndex({ "device.siteId": 1, ts: 1 });

Search: $search and the mongot process

MongoDB's built-in text index is a weak stemmer-and-stopwords implementation, one per collection, with no analyzers, no faceting worth the name and no relevance tuning; treat it as legacy. Real full-text search runs in mongot, a separate Lucene-based process that follows the change stream of your collection and maintains its own indexes, exposed through the $search and $searchMeta aggregation stages. For years this was Atlas-only, which was the honest objection to it. That changed in 2026: MongoDB Search and Vector Search became generally available for self-managed deployments on 1 July 2026 — free with Community Edition 8.2+ under the SSPL, and as a paid add-on for Enterprise Advanced deployed via MongoDB Controllers for Kubernetes — with parity on $search, $searchMeta, $vectorSearch, $rankFusion and $scoreFusion. If your knowledge of this stops at "that's an Atlas feature", you are a year out of date.

The architectural consequence is the interesting part: because mongot is a separate process with its own indexes, search is eventually consistent with the database (a document is searchable milliseconds to seconds after it is written), it scales independently (Atlas calls these Search Nodes), and a $search stage must be the first stage of a pipeline, since it is the source. You can then $lookup or $match on the results as normal.

Vector search and hybrid retrieval

$vectorSearch performs approximate nearest-neighbour search over a vector-typed index, using HNSW under the hood. The parameters that matter: path (the embedding field), queryVector, numCandidates (how many candidates the ANN traversal considers — typically 10–20× your limit; too low and recall suffers, too high and latency suffers), limit, and filter for pre-filtering on scalar fields, which is the feature that makes it usable for multi-tenant systems. Exact nearest neighbour (ENN) is available for small collections or recall benchmarking. Quantisation — scalar and binary — trades a little recall for a large reduction in memory, which is what makes tens of millions of vectors affordable.

Hybrid search is the current best practice, and MongoDB now expresses it declaratively: $rankFusion (GA in 8.0) combines several ranked result sets with reciprocal rank fusion, and $scoreFusion (GA in 8.3) combines them by normalised score with weights. In practice: run a lexical $search and a semantic $vectorSearch over the same corpus and fuse them, because keyword search nails exact identifiers and rare terms while vector search handles paraphrase — each covers the other's failure mode. MongoDB has also folded in Voyage AI (acquired 2025): automated embedding generation, so the database creates and refreshes embeddings on write rather than requiring an application-side pipeline, plus rerankers for a final precision pass. That is the RAG story you should be able to sketch on a whiteboard.

Interview Q&A

What is a time series collection and when would you use one?

It is a collection type where the server transparently groups measurements sharing a metadata value and a time window into internal buckets with columnar storage, so you write and query individual measurements but store them compactly. I use it for any append-mostly, time-ordered, high-cardinality-by-series workload — device telemetry, application metrics, market data, IoT — where reads are almost always "this series over this window". The wins are storage, often several times smaller than equivalent documents, and aggregation speed, roughly 60% better since 8.0. The design decisions that matter are the metaField, which must be what you filter by because it is the bucketing dimension, and granularity, which should match your write frequency. It is not the right tool when measurements are heavily updated or individually deleted, when timestamps arrive wildly out of order, or when you need arbitrary per-document indexing beyond what secondary indexes on measurements (6.0+) support — and I would say that a hand-rolled bucket pattern is now only justified if you need control the built-in type does not give you.

How does $search differ from a text index?

A text index is a modest inverted index built into mongod: one per collection, basic stemming and stop words, no analyzers, no relevance tuning, no faceting, and it participates in normal query planning so it is strongly consistent. $search runs against mongot, a separate Lucene-based process that follows the collection's change stream and maintains its own indexes, giving you real analyzers, synonyms, fuzzy matching, autocomplete, faceting, highlighting and score tuning. The trade-offs are that search is eventually consistent — a write is searchable milliseconds to seconds later — that $search must be the first pipeline stage since it is the source, and that you now operate a second process. The 2026 headline is that this stopped being an Atlas-only capability: MongoDB Search and Vector Search went generally available for self-managed deployments on 1 July 2026, free with Community 8.2+ and as an Enterprise Advanced add-on deployed through the Kubernetes controllers, with parity on $search, $searchMeta, $vectorSearch, $rankFusion and $scoreFusion.

Design a RAG system on MongoDB.

Chunk the source documents with overlap, embed each chunk, and store the chunk text, its embedding, the source pointer and the access-control fields in one collection — access control in the same document matters, because it lets you pre-filter inside $vectorSearch rather than filtering after retrieval, which is both faster and the only correct way to do multi-tenant retrieval. Build a vector index with an appropriate similarity metric and quantisation if the corpus is large, plus a search index over the same text. At query time run hybrid retrieval — lexical $search and semantic $vectorSearch fused with $rankFusion or the score-weighted $scoreFusion — take the top 20 to 50, rerank with a cross-encoder for precision, and pass the top handful to the model with citations back to the source pointer. MongoDB now offers automated embedding generation via Voyage AI, so embeddings can be created and refreshed by the platform on write instead of by an application pipeline, which removes the most common source of drift: documents updated without their embeddings being regenerated. The parts I would call out as the real engineering are chunking strategy, an evaluation set with measured recall and answer quality, and re-embedding when the model changes — that last one is a migration, and it needs a plan.

How do you tune $vectorSearch?

Three levers and one measurement. The measurement comes first: build a ground truth with exact nearest neighbour on a sample of queries, then measure recall at your target limit. The levers are numCandidates, which controls how much of the HNSW graph is explored and is the main recall-versus-latency dial — a rule of thumb is 10 to 20 times limit, then tuned against the measured curve; quantisation, where scalar or binary compression dramatically reduces memory at a modest recall cost and is what makes large corpora affordable; and filtering, where pre-filtering on indexed scalar fields inside the stage is far better than post-filtering, though a very selective filter can hurt ANN recall because the graph traversal has fewer valid neighbours to walk. Beyond those, the biggest quality lever is not the index at all — it is the embedding model and the chunking, and a reranker on the top 50 usually buys more than any parameter change.

What is hybrid search and why does it beat either half?

Hybrid search runs a lexical and a semantic retrieval over the same corpus and merges the ranked lists. It wins because the two have complementary failure modes: keyword search cannot match a paraphrase or a synonym but is exact on identifiers, error codes, product SKUs and rare proper nouns, where embeddings are unreliable because those tokens are poorly represented. MongoDB expresses this natively — $rankFusion, GA in 8.0, merges by reciprocal rank, which is robust because it ignores incomparable score scales; $scoreFusion, GA in 8.3, merges by normalised scores with weights, which gives you finer control when you know the relative quality of your retrievers. Doing it server-side matters practically: the alternative is fetching both lists to the application, normalising and merging there, which is more code, more latency and one more place for the ranking logic to drift from what you tested. I would still measure — fusion weights are workload-specific, and the honest way to set them is an evaluation set, not intuition.

MongoDB search or a dedicated Elasticsearch cluster?

I would frame it as an operational question, not a feature question, because the feature gap has narrowed a lot. Running search inside MongoDB means one datastore, one security model, one backup story, and no synchronisation pipeline — and the pipeline is where two-system architectures actually fail, through drift, reindexing incidents and permanently ambiguous "which one is right?" moments. Elasticsearch still wins on breadth of analysis features, on very large dedicated search corpora, on log and observability use cases, and when a team already has deep expertise. What changed the calculus is that self-managed MongoDB Search went GA on 1 July 2026, so choosing it no longer implies choosing Atlas. My decision rule: if search is a feature of an application whose source of truth is already MongoDB, keep it in MongoDB; if search is the product, or the corpus and query language demands exceed what $search exposes, run the dedicated system and invest properly in the pipeline.

Why is search eventually consistent, and how do you design around it?

Because mongot is a separate process that follows the collection's change stream and maintains Lucene indexes independently, so there is a replication delay between a committed write and its searchability — usually milliseconds, but it can grow under load or if the search process falls behind. You design around it by never making a user-visible flow depend on immediate searchability: after a create, show the user the document you just wrote rather than a search result; in tests, poll with a timeout instead of asserting immediately; and for "did my save work?" flows, query by _id through the normal path, which is strongly consistent. Operationally, index lag is a metric to monitor and alert on, because a stalled search index looks like missing data to users rather than like an outage. And when a use case genuinely cannot tolerate staleness — an inventory check at checkout — that query belongs on the ordinary indexed path, not on the search path.

How would you migrate a hand-rolled bucket collection to a time series collection?

Time series collections cannot be converted in place, so it is a copy-and-switch. I would create the new collection with the timeField, metaField and granularity chosen from the actual write pattern, then backfill in time-ordered batches — order matters, because inserting historical data out of order produces fragmented buckets and gives away the compression advantage — while the application dual-writes to both. Then I would validate: compare counts and aggregate results over several windows, and compare storage and query latency to confirm the win is real. Then flip reads, watch, and finally stop writing to the old collection and drop it, which returns the disk space instantly. The parts to plan explicitly are index parity (secondary indexes on measurements have been available since 6.0, but the set you need may differ), the retention story, since expiry is now a bucket-level TTL rather than per-document deletes, and any code that updates individual measurements, since update support is limited by design and that code may need rethinking rather than porting.

What are the cost drivers for vector search at scale?

Memory, primarily: HNSW graphs are traversed in RAM, so the index must effectively fit, and index size scales with the number of vectors times the dimension count times bytes per component. That gives you the three levers directly — fewer vectors through better chunking, fewer dimensions through a smaller embedding model or dimensionality reduction, and fewer bytes per component through scalar or binary quantisation, which is usually the highest-leverage change and costs surprisingly little recall. After memory, the drivers are query volume against numCandidates, since that determines CPU per query, and the embedding generation itself, which is a real recurring cost when documents update frequently. The architectural lever, on Atlas, is running search on dedicated Search Nodes so vector workloads do not compete with the operational database for cache — and the equivalent self-managed decision is where you place mongot. The cost mistake I see most often is embedding everything, including boilerplate and navigation text, instead of curating what is worth retrieving.

How do you evaluate whether your retrieval is actually good?

With an evaluation set, built before tuning anything: a few hundred realistic queries with human-judged relevant documents, versioned in the repo like tests. Then measure retrieval quality with recall at k and NDCG or MRR, separately from end-to-end answer quality, because conflating them means you cannot tell whether a bad answer came from bad retrieval or a bad prompt. For the ANN component specifically, measure recall against exact nearest neighbour on a sample, which turns numCandidates from guesswork into a curve. Then track the metrics over time in CI, because retrieval quality degrades silently as the corpus grows and as the mix of queries shifts — and re-run the whole set whenever the embedding model, the chunking or the fusion weights change. The organisational point I would make is that most teams skip this and end up tuning by anecdote, which is why their retrieval quality is unknowable and every change is a debate rather than a measurement.

12Security & encryption

MongoDB's security reputation was made by a wave of ransomed, internet-exposed instances around 2017, and the defaults have been fixed since: bindIp has defaulted to localhost since 3.6, and SCRAM-SHA-256 has been the default authentication mechanism since 4.0. But authentication is still off unless you enable it (security.authorization: enabled, or --auth), which is the single most important operational fact in this unit — a mongod started without it and reachable on a network is an open database, and that is still how most MongoDB breaches happen. Atlas and every managed offering enable auth by design; a hand-rolled Docker Compose file usually does not.

The 2026 fact you must know: MongoBleed

CVE-2025-14847, "MongoBleed", CVSS 8.7, disclosed in December 2025 by security researcher Joe Desimone. MongoDB's handling of zlib-compressed wire-protocol headers mishandled mismatched length fields, so a crafted message caused the server to return uninitialised heap memory in its response — a Heartbleed-shaped information disclosure, unauthenticated, low complexity, remotely exploitable against any reachable instance. Leaked memory can contain previously handled query data, credentials, API keys and tokens. A public proof of concept appeared on 26 December 2025, exploitation in the wild followed, CISA added it to the Known Exploited Vulnerabilities catalogue, and Censys reported roughly 87,000 potentially vulnerable instances exposed. Fixed in 8.2.3, 8.0.17, 7.0.28, 6.0.27, 5.0.32 and 4.4.30; Atlas clusters were patched automatically, self-hosted ones were not.

Three lessons to draw in an interview, because the point is not the CVE trivia. First, it exploited a path before authentication, so "we require auth" was no defence — network exposure is a separate control from authentication, and it is the one that saved anybody. Second, it is the strongest possible argument for the boring practices: patch currency, an inventory of every MongoDB instance including the forgotten staging one, and network policy that makes a database unreachable from anywhere it has no business being. Third, MongoDB 8.3's hardening work (pre-auth message-size and buffer-memory limits, stricter SASL enforcement, and fixes for 5 CVEs, with 25 more in 8.3.8) is a direct descendant of it.

Interview trap

Treating "encryption at rest" as if it protected data from an application compromise. Disk encryption protects against a stolen disk or a decommissioned volume; the database decrypts everything for anyone who can authenticate, so it does nothing against SQL-injection-equivalents, a leaked connection string, an over-privileged service account, or an insider with database access. The layers are distinct and you should name them: TLS protects the wire, at-rest encryption protects the media, and field-level encryption (CSFLE or Queryable Encryption) is the only one that protects data from the database operator and from a compromised server — which is why regulated workloads care about it. The second trap is granting the application readWrite on the whole database or, worse, root, and then arguing that it is fine because the credentials are in a secret manager; least privilege is what limits the blast radius when those credentials leak, and they do.

Try it

1. Start a mongod without --auth and connect from another machine to feel how open it is; then enable auth, create a least-privilege role for a fake service, and confirm it cannot read a collection you did not grant. 2. Set up Queryable Encryption with a local KMS provider for one field, insert a document, and then read that collection with a plain mongosh session without the key.

Expected outcome & solution sketch

(1) The unauthenticated instance lets you do anything, including dropDatabase — this is what an exposed instance actually is. On the second half, the useful discovery is how many actions a "read-only" role really needs (find, plus listCollections and often listIndexes for tooling), which is why people give up and grant readWrite; enumerate them properly once and reuse the role.

(2) You will see ciphertext as binData and the auxiliary metadata collections (prefixed enxcol_.) sitting next to the collection. That makes the guarantee concrete: a DBA, a backup thief and a compromised server all see the same nothing. Then try an unsupported operation — an aggregation over the encrypted field — and observe the failure, because knowing the limits is what makes you credible when someone proposes encrypting everything.

Interview Q&A

How do you secure a MongoDB deployment? Give me the checklist.

Network first, because it is the control with the largest effect: no public IP, bound to private interfaces, firewalled or in a VPC with peering or PrivateLink, and an inventory of every instance including the ones nobody owns. Then authentication enabled — it is off by default in a self-managed mongod — with SCRAM-SHA-256 at minimum and OIDC or x.509 for human and service identity where available. Then authorization: one least-privilege role per service, no shared credentials, no root for applications, and separate credentials for migrations and for humans. TLS everywhere including intra-cluster. Encryption at rest via the platform, and field-level encryption for the specific fields that need protection from the database itself. Auditing shipped off the host. And finally the boring operational half that MongoBleed made unarguable: patch currency with a defined SLA for critical CVEs, and monitoring that would actually tell you if an instance appeared on the public internet. I would also add backups with tested restores to a security checklist, because ransomware is a security event and an untested backup is not a control.

Explain CSFLE versus Queryable Encryption.

Both encrypt fields in the driver so the server never holds the plaintext or the keys, and both use a key vault collection plus a KMS-held customer master key. CSFLE, from 4.2, offers deterministic encryption — the same plaintext always produces the same ciphertext, which permits exact equality matching but leaks frequency information, so an attacker with the ciphertext can infer that a value is common — and random encryption, which leaks nothing but cannot be queried at all. Queryable Encryption, GA in 6.0, replaces that trade-off with structured encryption: the ciphertext is randomised, and separate metadata structures let the server evaluate predicates without decrypting, so you get equality without frequency leakage, range queries since 8.0, and prefix, suffix and substring matching on strings since 8.2. Queryable Encryption is the default choice for new work; CSFLE remains where you already have it or need a deterministic ciphertext for some external reason. The costs to state honestly are storage overhead from the metadata collections, higher query latency, restricted operations — no arbitrary aggregation on encrypted fields — and the fact that key management is now part of your architecture and your disaster recovery plan.

What was MongoBleed and what would you have done during it?

CVE-2025-14847, disclosed in December 2025 and rated CVSS 8.7: MongoDB's zlib wire-compression path mishandled mismatched length fields, so a crafted, unauthenticated request could make the server return uninitialised heap memory — potentially containing prior query data, credentials or tokens. A public proof of concept landed on 26 December 2025, exploitation in the wild followed, and CISA added it to the KEV catalogue; Censys counted roughly 87,000 exposed instances. Fixes shipped in 8.2.3, 8.0.17, 7.0.28, 6.0.27, 5.0.32 and 4.4.30, and Atlas was patched automatically while self-hosted deployments were not. My response would have been: inventory every instance including forgotten ones, confirm which are network-reachable from outside a trusted boundary and cut that reachability first because that is the fastest mitigation, then patch in priority order starting with anything internet-facing, then rotate credentials and tokens that could have been resident in server memory, and finally check logs for anomalous compressed-message traffic. Afterwards the retrospective question is not "why were we vulnerable" — everyone was — but "why did it take us N hours to answer how many MongoDB instances we run and which are exposed".

How do you design RBAC for a microservices platform on MongoDB?

One database user per service, with a custom role scoped to exactly the collections and actions that service needs, defined as code alongside the service so it is reviewed and versioned with the application. That means enumerating actions rather than granting readWrite: find, insert, update on the collections it owns, find only on collections it consumes, and nothing on anything else. Separate credentials for migrations, which need DDL rights the runtime should not have, and separate human access through OIDC or LDAP so people never share a service password and access is revoked by the identity provider. Rotation should be automatic through a secret manager, with the application able to pick up new credentials without a restart. On a multi-tenant collection, RBAC cannot enforce row-level isolation, so the tenant filter has to be enforced in a shared data-access layer, and I would back that with a read-only view per tenant class where the isolation genuinely matters. The failure mode to design against is the "temporary" admin credential that becomes the service's permanent identity, so I would make the least-privilege role the path of least resistance in the service template.

What is the practical difference between encryption at rest and field-level encryption?

Threat model. Encryption at rest protects the media: a stolen disk, an improperly decommissioned volume, a snapshot copied to the wrong account. Once the server is running, it decrypts everything for anyone who can authenticate, so it offers nothing against a compromised application, a leaked connection string, an over-privileged account or a malicious operator. Field-level encryption moves the boundary: the driver holds the keys, the server sees only ciphertext, so a compromised database server, a database administrator and a stolen backup all see nothing useful for the encrypted fields. That is why regulated workloads — health records, national identifiers, payment metadata — increasingly require it, and why "the cloud provider encrypts our disks" is not an answer to that requirement. The cost is that the protection is real, so the constraints are real too: you cannot aggregate over encrypted fields arbitrarily, key loss means data loss, and key management becomes a first-class part of your DR plan. I would encrypt the few fields that carry the risk, not everything.

How do you handle credentials and connection strings?

They come from a secret manager at runtime, never from a repository, an image or an environment file baked into a build, and they are rotated automatically with the application able to reload without a restart — modern drivers support callback-based credential providers for exactly this. For cloud deployments I would prefer to eliminate the shared secret entirely: AWS IAM authentication or x.509 certificates issued by a workload identity system means there is no password to leak. Human access goes through OIDC so that access is granted and revoked in the identity provider and every session is attributable to a person, which also solves the audit question. Beyond storage, I care about blast radius: distinct credentials per service and per environment so one leak is contained, and monitoring for authentication failures and for logins from unexpected sources. And the detail people miss — connection strings end up in logs, in error messages, in APM traces and in support tickets, so the data-access layer should redact them, and I would test that it does.

What is your backup and restore strategy, and how does it relate to security?

Backups are a security control, because ransomware and destructive mistakes are the failure modes they actually cover. For a self-managed cluster I would use filesystem or volume snapshots of a hidden, non-voting secondary — consistent because WiredTiger's checkpointing plus the journal makes a snapshot recoverable — combined with oplog capture for point-in-time restore; mongodump is a logical tool that does not scale past modest datasets and is a poor fit for a large production restore. Backups must be encrypted, stored in an account or project with separate credentials so a compromise of production does not reach them, immutable or versioned so they cannot be deleted by an attacker, and geographically separate. The part that distinguishes a real strategy is testing: a restore rehearsal on a schedule, measuring the actual time to recover, because an untested backup is a hypothesis. I would also define RPO and RTO explicitly and check that the mechanism can meet them, since oplog-based point-in-time recovery has a granularity and a replay time that people discover during the incident rather than before it.

An auditor asks how you prove who accessed customer records. What do you say?

That the answer has three parts and that only one of them is the database. Database auditing — available in Enterprise and Atlas — logs authenticated actions filtered by user, action and namespace, and it must be shipped off the host into a system the database administrators cannot alter, or it is not evidence. Identity is the second part: if services share credentials or humans share an admin account, the audit log records a role, not a person, so OIDC or x.509 with per-person identities is a prerequisite for the audit trail to mean anything. The third part is the application, because most customer-record access happens through it, and the database sees only the service account — so the application must emit its own access events with the acting user, correlated by a request identifier. I would also be honest about the gap this leaves: a person with direct database access and a legitimate role can read data, and the only technical control that changes that is field-level encryption with keys the database operators do not hold, which is precisely the argument for Queryable Encryption in regulated environments.

How do you keep a fleet of MongoDB clusters patched?

By making it routine rather than eventful. That means an inventory that is generated, not maintained by hand — every cluster, its version, its exposure, its owner — because MongoBleed showed that the first hour of a security incident is usually spent building that list. Then a defined cadence: patch releases applied within a fixed window, with a documented emergency path for KEV-listed CVEs measured in hours, not sprints. Rolling upgrades are the mechanism, secondaries first then a step-down, which is a routine, automatable procedure, and the FCV should be advanced deliberately after the binaries are stable rather than in the same change. Non-production environments get patched first and act as the canary, which requires them to actually resemble production. And the version strategy has to be explicit, because since 8.2 MongoDB stops patching a minor release once the next one ships — so a fleet on 8.2 must move to 8.3 to keep receiving security fixes, while a fleet on the 8.0 major gets five years of support. Choosing which of those two tracks you are on is a decision to make consciously, not one to discover during a CVE.

What would you flag in a code review as a MongoDB security problem?

A connection string with credentials in it, anywhere. An application role broader than the collections it uses, especially readWrite on a whole database or any use of root. A query built by string concatenation or by passing a user-controlled object straight into a filter — MongoDB injection is real: a JSON body that supplies {"$ne": null} where the code expected a string turns an authentication check into a bypass, so user input must be cast to the expected type before it reaches a query. A $where or $function containing anything derived from user input, which is server-side JavaScript execution. A multi-tenant query missing the tenant filter, which I treat as a data-leak defect regardless of how unlikely the path looks. Personal data written to a field that is not in the encryption schema, or logged. And on the operational side, a Docker Compose or Helm chart that starts mongod without authentication, because that is how a development shortcut becomes an exposed production instance.

13Drivers, deploys & upgrades

The driver is not a thin wrapper — it is a distributed-systems client that maintains a topology model, selects servers, pools connections, retries, and implements the session and transaction specifications. Most "MongoDB is flaky" reports are driver configuration problems, so this is a genuinely load-bearing interview topic for a lead.

Connections and pooling

A driver holds one connection pool per server it knows about, with maxPoolSize defaulting to 100 and minPoolSize to 0. The arithmetic that catches teams out is multiplicative: 40 application pods × 100 connections × 3 replica set members is 12,000 connections, and each one costs the server memory and a thread in the default networking model. Size the pool from Little's law instead — concurrency equals throughput times latency — so a service doing 500 ops/s at 5 ms needs about 3 connections, not 100. The other settings that matter: serverSelectionTimeoutMS (30 s) is how long a driver waits for a suitable server before erroring, and it should usually be shorter than your HTTP timeout so failures are attributable; connectTimeoutMS and socketTimeoutMS bound the network; maxIdleTimeMS lets idle connections be reaped; heartbeatFrequencyMS (10 s) controls topology monitoring; and retryWrites/retryReads are on by default and should stay on. Use an mongodb+srv:// connection string so members can change without a redeploy.

// One MongoClient per process, injected as a singleton. Creating clients per request
// is the most common and most damaging MongoDB mistake in application code.
var settings = MongoClientSettings.FromConnectionString(cfg["Mongo:Uri"]);
settings.MaxConnectionPoolSize   = 20;                        // sized from throughput x latency
settings.MinConnectionPoolSize   = 2;
settings.ServerSelectionTimeout  = TimeSpan.FromSeconds(5);   // shorter than the request budget
settings.ConnectTimeout          = TimeSpan.FromSeconds(3);
settings.RetryWrites             = true;                      // default; keep it
settings.ReadConcern             = ReadConcern.Majority;
settings.WriteConcern            = WriteConcern.WMajority;
settings.ApplicationName         = "orders-api";              // shows up in currentOp and logs
services.AddSingleton<IMongoClient>(new MongoClient(settings));

Versions, upgrades and FCV

MongoDB's release model changed in 8.2 and you should be able to state it precisely. There are major releases roughly every two years (7.0, 8.0) with a five-year support window, and minor releases (8.1, 8.2, 8.3) that are production-quality and ship features earlier. Since 8.2, minor releases are also available for on-premises Community and Enterprise Advanced for specific use cases — Search, Vector Search and Queryable Encryption. The catch, and it is a big one: once a new minor ships, MongoDB stops patching the previous minor, and you cannot skip minors when upgrading (8.1 → 8.2 → 8.3). So the strategic choice is explicit: ride the major track for predictable five-year support and slower features, or the minor track for early features and a continuous upgrade obligation. 8.0 is supported until 31 October 2029; 7.0 until August 2027; 6.0 went end of life in July 2025.

The upgrade mechanism is a rolling binary replacement plus a separate feature compatibility version step. Upgrade secondaries one at a time, step down the primary and upgrade it, run on the new binaries with the old FCV for long enough to be confident, then setFeatureCompatibilityVersion — which since 7.0 requires confirm: true, precisely because it is the point of no easy return. Anything that depends on new on-disk formats or new expressions is gated behind the FCV, which is what makes the rollback window possible. MongoDB 8.3 is a good illustration of why that window matters: 2dsphere index version 4 becomes the default and must be dropped before downgrading the FCV, and views or validators using 8.3 expressions must be updated or removed first.

# Rolling upgrade, one member at a time. Never all at once, never skip a minor.
# 1. Secondaries first
systemctl stop mongod && dnf upgrade mongodb-org && systemctl start mongod
mongosh --eval 'rs.status().members.map(m => [m.name, m.stateStr])'   # wait for SECONDARY

# 2. Step down the primary, upgrade it, let it rejoin
mongosh --eval 'rs.stepDown(120)'

# 3. Soak on new binaries with the OLD FCV - this is your rollback window
mongosh --eval 'db.adminCommand({getParameter: 1, featureCompatibilityVersion: 1})'

# 4. Only then, deliberately:
mongosh --eval 'db.adminCommand({setFeatureCompatibilityVersion: "8.3", confirm: true})'
Interview trap

Creating a MongoClient per request. The client owns the connection pool, the topology monitor and the background heartbeats; constructing one per request means a fresh TCP and TLS handshake plus a full topology discovery on every call, which shows up as unexplained multi-hundred-millisecond latency and, eventually, connection exhaustion on the server. It is a singleton, for the process lifetime, and this belongs on a code-review checklist. The adjacent traps: leaving maxPoolSize at 100 across dozens of pods, which multiplies into thousands of server connections; setting serverSelectionTimeoutMS longer than the caller's own timeout, so a failover produces mysterious hung requests instead of clean errors; and disabling retryWrites because someone once saw a duplicate — the duplicate was almost certainly a non-idempotent write pattern, not the retry mechanism.

Try it

1. Instrument a small service to log pool events (connectionPoolCleared, checkout duration) and run it against a replica set while you step down the primary; watch what a failover looks like from the client with and without retryWrites. 2. Do a full rolling upgrade of a local three-node set across one minor version, deliberately leaving the FCV old for a while, and then try a downgrade.

Expected outcome & solution sketch

(1) With retries on, you see a pause of a few seconds and no errors; with them off you see a burst of NotWritablePrimary errors. The pool-clear event on topology change is the thing to recognise in production logs — a cleared pool means every in-flight checkout must re-establish, so a failover briefly costs you handshake latency, which is why minPoolSize above zero is worth setting for latency-sensitive services.

(2) The downgrade succeeds while the FCV is old and fails once you have advanced it — that asymmetry is the whole reason FCV exists, and doing it once makes the upgrade runbook obvious: binaries first, soak, FCV last, and never advance the FCV in the same maintenance window as the binary upgrade unless you are willing to give up the rollback.

Interview Q&A

How do you size a connection pool?

From concurrency, not from a default. Little's law gives required concurrency as throughput multiplied by average latency, so a service doing 500 operations per second at 5 milliseconds needs about three concurrent connections; I would set maxPoolSize to a small multiple of that to absorb bursts, not to 100. The reason the default hurts is multiplicative: pool size times instance count times replica set members is the connection count the server sees, and a few dozen pods at the default will happily open thousands of connections, each costing server memory. I also set minPoolSize above zero for latency-sensitive services so a burst does not pay handshake and TLS costs, set maxIdleTimeMS so idle connections are reaped, and make serverSelectionTimeoutMS shorter than the caller's request budget so failures surface as clean errors instead of hangs. Then I verify with the server: serverStatus().connections and, in 8.x, connection-pool statistics collected into FTDC, which finally makes this measurable from the server side rather than inferred.

What breaks when you move to the .NET driver 3.x?

Three things, and they are all mechanical but not always small. The LINQ2 provider is removed, so every LINQ query now goes through LINQ3 — mostly compatible, but expressions LINQ2 silently evaluated client-side now translate differently or fail, which is a correctness issue as much as a compile issue. Client-side projections throw ExpressionNotSupportedException by default; you either rewrite them to something translatable or explicitly opt in with EnableClientSideProjections, and I would treat the opt-in as a temporary measure, because a client-side projection means the driver is fetching whole documents and shaping them in memory. And the legacy v1 API package mongocsharpdriver is gone, along with deprecated MongoDB.Driver.Core and MongoDB.Bson members that are now internal or removed, so any codebase still on the v1 API has a real migration rather than a version bump. My approach is to upgrade in a branch with the full test suite plus a set of integration tests that assert the generated queries, because the failures that matter are the ones that still compile.

Should a team use an ODM like Mongoose or the EF Core provider?

It depends on what the team gains and what it hides. Mongoose gives schema declaration, validation, hooks and population in a Node codebase that would otherwise have none of it, and for a team without strong data-modelling discipline that is real value; the cost is an abstraction that makes it easy to write N+1 populate calls and hard to see the actual query. The EF Core MongoDB provider makes MongoDB approachable for a .NET team, which is exactly its risk: LINQ over DbSet encourages relational habits — navigation properties, joins, per-entity tables — in a database whose entire advantage comes from modelling aggregates. My guidance is that an ODM is fine for validation and mapping, but the team must still be able to state the resulting query and the index that serves it, and code review should look at the query, not the LINQ. Where I push back hardest is on any layer that generates queries the team cannot predict, because the failure appears at scale, in production, in a query nobody wrote.

Explain MongoDB's release model and how you would choose a version.

Major releases arrive roughly every two years — 7.0, 8.0 — and carry a five-year support window; minor releases like 8.1, 8.2 and 8.3 are production-quality and ship features earlier, and since 8.2 they are available on-premises for Community and Enterprise Advanced for specific use cases such as Search, Vector Search and Queryable Encryption. The consequential detail is that once a new minor ships, the previous minor stops receiving patches, and minors must be upgraded sequentially, so being on the minor track is a standing commitment to upgrade every few months. For most organisations I would recommend the major track — 8.0, supported to 31 October 2029 — because the operational cost of a continuous upgrade treadmill outweighs early features. I would choose the minor track deliberately when a specific capability justifies it, self-managed Search being the obvious example, and only with the automation and staging environments to make quarterly upgrades routine. Either way the decision should be explicit and written down, because the worst position is drifting onto a minor and then discovering during a CVE that it is no longer patched.

Walk me through upgrading a production cluster from 7.0 to 8.0.

First, prerequisites: confirm the current FCV is 7.0, check the compatibility-changes page for anything that affects us, upgrade drivers first since newer drivers support older servers but not the reverse, and rehearse the whole thing in staging on a restored production backup. Then the rolling binary upgrade, one member at a time — secondaries first, waiting for each to return to SECONDARY and for lag to clear, then rs.stepDown() on the primary and upgrade it. On a sharded cluster the order is config servers, then shards, then mongos. Then a soak on the new binaries with the FCV still at 7.0, which is the rollback window and should last long enough to cover a full business cycle including the weekend batch. Only then setFeatureCompatibilityVersion: "8.0", confirm: true, deliberately and as its own change. Throughout I watch replication lag, the slow-query log and $queryStats for plan regressions — 8.0 narrowed the slot-based engine's remit, so aggregation performance can genuinely shift — and I have a documented rollback for each phase, remembering that after the FCV advance the rollback is a restore, not a downgrade.

What is feature compatibility version and why does it exist?

FCV is a cluster-wide setting, separate from the binary version, that gates features which change on-disk formats or replication semantics. It exists to make upgrades reversible: you can run new binaries at the old FCV, so if something regresses you downgrade the binaries without a restore, and only when you advance the FCV do you commit to the new formats. That is why the sequence is always binaries, soak, FCV — and why advancing it since 7.0 requires confirm: true, an explicit acknowledgement that you are giving up the easy path back. The practical consequences show up as pre-downgrade checklists: MongoDB 8.3, for instance, makes 2dsphere index version 4 the default and those indexes must be dropped before downgrading the FCV, views and validators using new 8.3 expressions must be updated or removed, and validated collections using the new semantics must be relaxed or dropped. Teams that advance the FCV in the same maintenance window as the binaries have effectively converted a reversible change into an irreversible one, and that is the mistake I would look for in a runbook review.

How do you migrate an application from another database to MongoDB?

Not by translating tables into collections, which is the failure mode that produces a slow relational schema in a document database. I would start from the application's access patterns and design the aggregates first, then map the source data into them, accepting that one document may draw from five tables. Mechanically I favour dual-write with a read-side cutover: write to both systems, backfill history in batches, run a comparison job that reports divergence as a metric, move reads over feature-flagged by cohort, and keep the old system readable for a rollback window. Change data capture from the source database is the usual backfill mechanism and it is worth the effort, because a one-shot export always misses the tail. The parts teams underestimate are the queries that have no document equivalent — arbitrary reporting joins, which should go to a warehouse rather than be forced into $lookup — and the transactional invariants that were free in the relational model and now need either co-location in one document or an explicit transaction. And I would insist on writing down what success looks like before starting, because "we migrated" is not a measurable outcome and these projects drift.

What tooling belongs in a MongoDB team's toolbox in 2026?

mongosh for anything interactive, since the legacy mongo shell was removed in 6.0 and old scripts need porting. Compass for exploration, schema analysis and building aggregation pipelines visually — the schema analyser is genuinely useful for discovering the shape of a collection nobody documented. The Database Tools (mongodump, mongorestore, mongoexport, mongoimport) with a clear understanding that they are logical tools for modest datasets, not a backup strategy. mongosync for cluster-to-cluster migration. For observability, FTDC diagnostic data plus whatever exporter feeds the team's existing metrics stack, and $queryStats scraped on a schedule. Indexes, roles and validators defined as code and applied by a migration tool rather than by hand in a shell. And increasingly the MongoDB MCP Server, which as of the winter 2026 release can create and manage local clusters, so a developer's local setup is a command rather than a page of Docker instructions — useful, and worth treating with the same review discipline as any other tool that can write to a database.

How do you manage indexes and schema changes as code?

Same way as any other schema: versioned migration scripts in the repository, applied by a tool that records what has run, executed by a credential with DDL rights that the application itself does not have. Index creation needs care because it is not instantaneous on large collections, so migrations should create indexes in a way that tolerates being slow — and on very large collections the migration should register the intent while the actual build is done as an operational task, rolling member by member. I create new indexes hidden first when the goal is to replace an existing one, so the change is observable and reversible. Validators are versioned the same way, deployed in warn mode ahead of the code that satisfies them, and tightened in a later release, which means every schema tightening is at least two deployments. The rule that ties it together is that the deploy must be safe in both orders — old code against the new schema and new code against the old schema — because rolling deployments guarantee both states exist simultaneously.

How would you introduce MongoDB to a team that only knows relational databases?

By starting with the modelling shift, because that is the only part that is genuinely different and it is where every failure comes from. I would run a workshop on one real feature: list the access patterns, design the aggregate, and show why embedding order lines is not denormalisation-as-sin but the correct unit of storage — then show the counter-example where referencing wins, so nobody leaves thinking "embed everything". Then the operational fundamentals: write concern and read concern as explicit per-operation choices rather than an implicit global setting, and the fact that indexes work the way they expect but with the ESR rule and no query planner freedom to reorder pipeline stages. I would put guardrails in the codebase early — a data-access layer that enforces tenant filters and maxTimeMS, explain output required in pull requests that add a query — because habits form in the first month. And I would be honest about where it is worse: no declarative foreign keys, no arbitrary joins at speed, and a schema discipline that must come from the team rather than from the engine. Teams that hear that up front trust the rest of the advice.

Everything that is not a core building block but is asked constantly: the architecture arguments, the "when would you not", the incident stories, the code-review judgment, and the questions that are really about how you lead.

Architecture & ecosystem decisions

MongoDB or PostgreSQL? Argue both sides.

The honest 2026 answer starts by admitting the gap narrowed from both directions: PostgreSQL's JSONB with GIN indexing handles flexible documents well, and MongoDB gained real transactions, so the old talking points are mostly dead. What remains genuinely different is the scaling model and the workload shape. MongoDB's horizontal sharding is native, online and operationally routine, whereas PostgreSQL's is an extension or an application concern; MongoDB's aggregation plus search plus vector stack in one system is a real simplification for an application whose source of truth is documents. PostgreSQL wins where the data is genuinely relational and the queries are unpredictable — declarative foreign keys, arbitrary joins, window functions over normalised data, decades of tooling, and a query planner that will reorder your query for you. My decision rule: if the domain decomposes into aggregates that are read and written whole, and you expect to scale horizontally or need the search and vector story, MongoDB; if the domain is relational and the query patterns are open-ended, PostgreSQL. What I would not accept as an argument in either direction is team familiarity alone, though it is a legitimate tiebreaker, or a benchmark from a vendor.

Atlas or self-managed?

Atlas unless there is a specific reason not to, and the reasons are usually regulatory, contractual or cost at very large scale. What Atlas actually buys is the operational work nobody wants to be excellent at: automated patching — MongoBleed is the concrete example, where Atlas clusters were patched without customer action while self-hosted ones were not — backups with tested point-in-time restore, rolling upgrades, monitoring, and Search and Vector Search as managed components. What it costs is money at scale, a degree of lock-in around the managed features, and less control over version timing. The calculus changed in one important way in 2026: Search and Vector Search went GA for self-managed deployments on 1 July 2026, so "we need Atlas for search" is no longer automatically true, and a Kubernetes-based self-managed platform is a more credible option than it was. My framing for a decision meeting is to price the self-managed option honestly — including the on-call rota, the upgrade treadmill, and the restore rehearsals — because that comparison is usually what settles it.

When is MongoDB the wrong choice outright?

Three cases I would say no to without much hesitation. A workload whose value is in ad-hoc analytical queries across normalised data — that belongs in a columnar warehouse, and forcing it into aggregation pipelines produces slow, unmaintainable analytics that also damage the operational cluster's cache. A domain with hard multi-entity invariants that the database must enforce declaratively, such as a general ledger with referential integrity across accounts and periods; MongoDB can do it with transactions and application discipline, but a relational engine does it with constraints and you will sleep better. And a small application with a stable, well-understood relational schema and no scaling story, where MongoDB adds a modelling discipline burden for no benefit. A fourth, softer case: a team with no appetite for owning schema design, because the database will not stop them, and the failure arrives eighteen months later as a collection nobody can reason about.

How does MongoDB fit into an event-driven architecture?

Well, and change streams are the reason. The pattern I would sketch: MongoDB as the source of truth for a service's aggregates, the outbox pattern to make state change and event emission atomic within a single document write, and a change-stream consumer publishing to a broker with a durably persisted resume token. Downstream, projections and read models are ordinary collections maintained by consumers, which is exactly the CQRS shape. The properties to be explicit about are at-least-once delivery, so every consumer must be idempotent; ordering guaranteed per document key but not globally, especially across shards; and resumability bounded by the oplog window, which makes oplog sizing a coupling between database configuration and consumer availability. Where I would not use MongoDB is as the broker itself — a capped collection as a queue was a 2014 pattern, and Kafka or a cloud queue does that job properly with consumer groups, retention and backpressure that a database does not provide.

What is your position on multi-tenancy in MongoDB?

A single collection with a tenant identifier leading every index and the shard key, for all but the largest or most regulated tenants. Collection-per-tenant and database-per-tenant both look tidy and both collapse on catalogue overhead in the low thousands: file handles, per-collection index B-trees, slow listCollections, painful backups and, on a sharded cluster, routing metadata per namespace. The shared-collection model needs three things to be safe: the tenant filter enforced in a data-access layer rather than by developer discipline, since one missing filter is a cross-tenant data leak; the tenant in the shard key so queries stay single-shard; and a plan for the outlier tenant that is a hundred times bigger than the median, which is where the outlier pattern or a dedicated cluster comes in. The legitimate exceptions are hard data residency, per-tenant encryption keys, and contractual isolation — and there the right granularity is a cluster per tenant tier, not a collection per tenant.

Performance & debugging

Give me your first five minutes on a MongoDB performance incident.

Scope, then evidence, then mitigation. Minute one: is it one query shape, one collection, one node, or everything — that single distinction routes the entire investigation. Minute two: db.currentOp() sorted by running time, which names the culprit surprisingly often and tells me whether there is something to kill. Minute three: the saturation trio — available WiredTiger tickets, queue depth, and whether application threads are evicting pages — because those distinguish "a bad query" from "the box is full". Minute four: cluster health, rs.status() for a down or lagging member since one lost secondary redistributes load and can stall majority writes, and on a sharded cluster whether migrations are running. Minute five: what changed — a deploy, an index, a data import, a new large tenant, an expired certificate. I mitigate as soon as I safely can, and I capture currentOp, serverStatus and the FTDC data before restarting anything, because a restart clears the plan cache and destroys the evidence along with the symptom.

Queries got slower over three months with no code changes. Why?

Almost always one of four things, and I would rule them out in order of likelihood. The working set outgrew the cache: data grew, index pages no longer fit, and reads that used to be memory-speed now fault from disk — the tell is rising bytes-read-into-cache and eviction counters rather than any change in plans. An unbounded array or document growth: documents that were 2 KB are now 200 KB, so every read pulls more into cache and every update rewrites more. Index bloat or fragmentation after heavy churn, where a resync or compaction restores performance. Or a distribution shift — one tenant grew a hundredfold, so the cached plan for a parameterised shape is now wrong for the queries that matter. I would confirm with data rather than intuition: compare $queryStats docs-examined ratios over time, look at average document size trends from collStats, and check index sizes against cache. The reason to be systematic is that the obvious answer — "add an index" — makes three of those four cases worse.

How do you load-test MongoDB properly?

With production-shaped data, production-shaped concurrency and a workload mix that includes writes, because read-only benchmarks are meaningless for a database whose bottleneck is usually cache and eviction. Concretely: a dataset large enough that the working set does not trivially fit in cache, the real index set, the real document sizes including the fat tail, and a client that models think time rather than hammering in a tight loop, since an unthrottled loop measures your client. I measure latency percentiles rather than averages, and I run long enough for checkpoints, TTL waves and cache steady state to appear — a five-minute test hides everything interesting. I also test the failure states explicitly: step down a primary mid-test, kill a secondary, saturate the disk, and see whether the application degrades or falls over. And I would record the server-side numbers alongside the client numbers — tickets, eviction, oplog rate — because a test that only produces a throughput figure tells you nothing about why.

What are the highest-leverage MongoDB metrics to alert on?

Six. Replication lag per member, because it precedes almost every other failure and it bounds your recovery options. Oplog window in hours, alerted on the window rather than on disk, because that is what determines whether a member can catch up and whether a change-stream consumer can resume. Available WiredTiger tickets and queue depth, which is the real saturation signal and is invisible to CPU-based autoscaling. Pages evicted by application threads, which is the cache cliff. Connection count against the server's limit, since driver pool misconfiguration is a common and sudden failure. And query-level health: the count of slow operations, plus the docs-examined-to-returned ratio for the top shapes from $queryStats, because that catches plan regressions while the cache is still hiding them. I would add member state changes and elections as events rather than thresholds, and I would tie each alert to a runbook — an alert without a first action is just noise with a pager attached.

A single document is contended by thousands of writers. What do you do?

Recognise it as a design problem, not a tuning problem, because MongoDB's optimistic concurrency serialises writers to one document and no configuration changes that. The standard remedy is sharded counters: replace the single document with N sub-documents keyed by a random or hashed suffix, write to a random one with $inc, and sum them on read — you trade a slightly more expensive read for a write path that scales linearly with N. If the exact value is not needed in real time, buffer in the application and flush periodically, which reduces write volume by orders of magnitude. If the contended document is a queue head, the answer is usually a proper queue or a lease-based claim with findOneAndUpdate and a randomised sort so workers do not all target the same document. What I would avoid is wrapping it in a transaction, which makes contention worse by holding the conflict window open longer, or increasing retries, which converts a throughput problem into a latency problem and hides it until it is worse.

Security, compliance & data protection

How do you meet a data-residency requirement in MongoDB?

Zone sharding, decided at schema-design time rather than retrofitted. You put a region field in the shard key, tag the shards in each jurisdiction with a zone, and map the key range for that region to the zone — after which the balancer will not move those ranges outside their zone, so residency is enforced by the database rather than by application convention. The consequences to state up front: the region must be part of the shard key, which is a modelling decision made long before the compliance conversation; queries must carry it to stay targeted; and moving a user between regions is a document move, not an update, since the shard key is what places the data. Backups and any downstream copies — search indexes, warehouses, logs — inherit the requirement, and that is where most implementations actually fail an audit. The alternative for stricter regimes is a separate cluster per jurisdiction with no cross-cluster replication, which is simpler to prove and more expensive to run, and I would choose based on whether the auditor needs to see isolation or placement.

How do you handle GDPR-style deletion in MongoDB?

By designing for it, because deleting a person from a document database is not a single deleteOne. I would map every place the personal data lands: the primary collection, denormalised copies from the extended reference pattern, search and vector indexes, change-stream-fed projections, backups, and logs. For the live data, either delete or, more often, crypto-shred — if the personal fields are encrypted with a per-subject key using Queryable Encryption or CSFLE, destroying the key renders the data unrecoverable everywhere at once, including in backups, which is the only practical answer to "delete me from your backups". For denormalised copies, a change stream on the deletion is the propagation mechanism, with a reconciliation job that reports stragglers. And I would insist on a data inventory as a maintained artefact, because the hardest part of these requests is not the deletion, it is proving you found every copy — which is also a good argument for keeping denormalised copies of personal data to an absolute minimum.

What does MongoDB injection look like?

It does not look like string concatenation, which is why people believe it cannot happen. The common form is operator injection: application code takes a JSON body and passes a field straight into a filter, so a client that sends {"password": {"$ne": null}} where a string was expected turns an authentication query into "any user whose password is not null". The defence is type validation before the value reaches a query — cast to the expected type, reject objects where a scalar is expected — and it belongs in the framework layer, not in each handler. The second form is server-side JavaScript: $where, $function and $accumulator execute JavaScript on the server, and any user input reaching them is remote code execution in the database process; I would ban them outright in application code and disable server-side scripting where it is not needed. The third is less an injection than an amplification: an unvalidated filter object lets a caller construct an unindexed query and take the cluster down, which is why untrusted callers should never control query structure at all.

A backup restore has never been tested. How do you make the case to fix it?

By converting it from a hygiene argument into a measured one. I would run the restore, once, in a non-production account, and time it end to end — provisioning, transfer, restore, index rebuild, replication catch-up, application verification. That number is almost always dramatically larger than whatever RTO the business believes it has, and the gap is the argument; nobody debates a spreadsheet cell that says "our stated recovery time is four hours and the measured time is nineteen". I would also test the thing people skip: restoring to a point in time rather than to the last full backup, because oplog replay has its own duration and its own failure modes. Then I would make it recurring and automated, with the restore rehearsal producing a metric that appears on the same dashboard as availability, so it decays visibly if it stops running. The framing that works with leadership is that an untested backup is not a control, it is a hypothesis — and that ransomware and a bad migration are the two scenarios where the hypothesis gets tested for you.

Legacy reality & migration

You inherit a MongoDB 4.4 cluster with no auth and 40 indexes on the main collection. Where do you start?

Triage by blast radius, not by ugliness. First, exposure: is this reachable from anywhere it should not be, and given MongoBleed and 4.4's status, is it patched at all — 4.4 is long past end of life, so the honest assessment is that it is an unpatched, unauthenticated database, and that is the emergency. Network isolation is the fastest mitigation, then enabling authentication, which requires a coordinated change with the applications and is the first real project. In parallel I would establish visibility: slow log, metrics, backups with a tested restore, because I do not want to change anything on a system I cannot observe or recover. The 40 indexes are a real problem but a slower one: $indexStats over a full business cycle, drop the prefix-redundant ones, hide the apparently-unused ones before dropping. Then the upgrade path, which from 4.4 is a sequence of major versions with FCV steps and driver upgrades, rehearsed on a restored copy. What I would resist is starting with the interesting engineering — the schema — because on a system like this the unglamorous half is what is actually going to hurt.

What legacy MongoDB patterns do you still find, and what do you replace them with?

Oplog tailing, replaced by change streams, which are supported, resumable and survive failover. Map-reduce, deprecated since 5.0, replaced by aggregation with $group and $merge. $out for materialised views, replaced by $merge so the target is updated incrementally instead of swapped wholesale. Sparse indexes, replaced by partial indexes. A duplicated lowercase field for case-insensitive search, replaced by a collation-aware index. Manual bucket collections for metrics, replaced by time series collections. Scripts written for the legacy mongo shell, which was removed in 6.0, ported to mongosh. The count() command, replaced by countDocuments or estimatedDocumentCount depending on whether you need accuracy or speed. And on the client side, the .NET driver's LINQ2 provider and the v1 mongocsharpdriver API, both gone in driver 3.x. I would not rewrite all of these on sight — I would attach each to a change already happening in that area, because a migration nobody asked for is a migration nobody reviews carefully.

How do you get off a shard key you now know is wrong?

The answer changed and it is worth saying so: since 4.4 you can refineCollectionShardKey to append fields, which is enough when the problem is insufficient cardinality, and since 5.0 you can reshardCollection to change the key entirely, with the operation getting dramatically faster in 8.0, plus unshardCollection and moveCollection for related cases. So the old "your shard key is forever" framing is out of date. What has not changed is that resharding a multi-terabyte collection is a project: it copies the data, so you need the space and the I/O headroom, it runs for hours or days, and it ends with a brief critical section at the switchover. I would rehearse on a restored copy to get a real duration, run it in a low-traffic window with monitoring on lag and disk, and have a decision point where I abort. And I would fix the cause, not just the symptom — a wrong shard key usually means the access patterns were not written down before sharding, so I would produce that document as part of the work.

Judgment, review & leading a team

What do you look for when reviewing MongoDB code?

In rough order of severity: an unbounded array, which is the highest-severity design finding; a missing tenant or shard-key filter, which is a data-leak and a scatter-gather at once; a query whose plan nobody has checked, which is why I ask for explain output in the pull request when a new query or index appears; a missing maxTimeMS; a MongoClient constructed anywhere other than composition root; a transaction that is not using the driver's withTransaction retry helper; a $lookup on a request path; a read-modify-write that should be an atomic operator or an optimistic-concurrency update; user input reaching a filter without type validation; and any new index without a justification and a check of what it makes redundant. Beyond the checklist I look for whether the document being written is a coherent aggregate, because the mechanical issues are cheap to fix later and a bad aggregate boundary is not.

How do you introduce MongoDB to a skeptical team?

By taking the skepticism seriously, because it is usually well-founded and usually about the wrong decade. I would concede the historical points explicitly — the unauthenticated-by-default era, the pre-4.0 absence of transactions, the "webscale" marketing — and then show what changed and when, with version numbers, because specificity is what earns trust with engineers. Then I would pick one bounded, real service and build it properly with them: aggregates designed from access patterns, ESR indexes with explain output, write and read concerns chosen deliberately, and guardrails in the data-access layer. Let the comparison be empirical rather than rhetorical. I would also name the costs honestly — no declarative foreign keys, no free ad-hoc joins, schema discipline that must come from the team — because a proposal that admits its weaknesses is far more persuasive than one that does not. And I would give them a way out: a decision record with the criteria we would use to conclude it was the wrong choice.

How do you decide between fixing a query, adding an index, changing the schema, and scaling the cluster?

In that order, because that is the order of cost and reversibility. Fixing a query is free and instant. Adding an index is cheap but permanent-ish: it taxes every write and consumes cache forever, so I want evidence from explain that it will be used and a check of which existing index it makes redundant, and I create it hidden first when it is replacing something. Changing the schema is expensive in engineering time and needs a migration plan, but it is the only fix for structural problems like unbounded arrays or a bad aggregate boundary, and it is the fix that compounds. Scaling — vertical first, then sharding — is the last resort not because it is wrong but because it is the only one that costs money forever and hides the underlying problem while doing so. The exception that reverses the order is an incident: during an outage I will scale or pin a plan immediately and do the proper fix afterwards, as long as the follow-up is a ticket with a name on it and not a vague intention.

Tell me about a MongoDB decision you would make differently now.

The pattern worth describing is choosing a shard key from the write pattern alone. It is easy to reason "hashed on this identifier gives perfect distribution" and ship it, and then discover six months later that the dominant read pattern — a dashboard query filtered on something else entirely — is a scatter-gather across every shard, so tail latency degrades as the cluster grows and the sharding actively made the product slower. The lesson is a process one: write down the top five reads and top three writes with their volumes before choosing a key, and check each against the candidate. What I would do differently in the recovery is also worth saying: I would reach for refineCollectionShardKey or reshardCollection earlier instead of accumulating application-side workarounds, because the workarounds became the thing that made the eventual fix expensive. Interviews reward this shape of answer — a specific decision, the mechanism of the failure, and the process change rather than a resolution to be more careful.

What would you say in a design review about a proposal to shard?

I would ask for four things before agreeing. The measurement that motivates it: working set against cache, write throughput against one primary's capacity, or a residency requirement — because "we might grow" is a reason to become shard-ready, not to shard. The proposed shard key, with the top queries checked against it one by one to show which stay targeted, and an honest note about which do not. The unique constraints, since they must be shard-key-prefixed and there is usually one that cannot be, which needs a claim-collection design. And the operational plan: backup coordination across shards, the balancing window, monitoring per shard, and who is on call for a routing problem at 3 a.m. If those four exist, sharding is a reasonable decision; if they do not, the honest recommendation is to spend two weeks on indexes, document size and archiving first, because that resolves the majority of these proposals and costs a fraction as much.

What is the one thing you would change about how most teams use MongoDB?

Make the access patterns an artefact. Almost every serious MongoDB problem I have seen — the wrong shard key, the unbounded array, the collection nobody can query, the five-$lookup read path — traces back to a schema designed from the data rather than from the queries, and to nobody writing down what the queries actually are. It costs an afternoon at the start of a service and it makes every subsequent decision mechanical: which fields embed, what the indexes are, what the shard key must be, which reads must be targeted. The second-order benefit is review: with the list written down, a pull request that adds a query pattern nobody anticipated is visible as a change to the design rather than as an innocuous new method. It is unglamorous advice, and it is the one practice that separates the MongoDB estates I have enjoyed operating from the ones I have spent months rescuing.

Ten sentences to have loaded. Each one is speakable as-is and each one opens a door to the depth above it.

  1. MongoDB 8.3 is the current stable series, GA on 4 May 2026, latest patch 8.3.8 on 11 August 2026 — up to 45% more reads and 35% more writes than 8.0 with no code change, largely from profile-guided and link-time optimisation. MongoDB 8.0 is the current major with support to 31 October 2029; majors ship roughly every two years with a five-year window, minors (8.1, 8.2, 8.3) ship features early but stop being patched once the next minor lands and must be upgraded sequentially.
  2. The document is the unit of storage, atomicity and retrieval — 16 MB, 100 levels of nesting, single-document writes always atomic. Everything else follows: model from access patterns, store together what is read together, and treat any array without a documented upper bound as the highest-severity design defect.
  3. Embed for one-to-few, bounded and always-read-together; reference for one-to-many and independently-updated. Name the bound out loud — "a checkout basket is capped at 100 lines, so this document has a ceiling of ~30 KB" — because "it depends on access patterns" earns no credit on its own.
  4. Equality, Sort, Range. Compound index fields go in that order, because equality collapses the scan to one contiguous B-tree region where the remaining key components are still ordered, and a range before a sort forces a blocking in-memory sort capped at 32 MB for find. Verify by the disappearance of the SORT stage in explain("executionStats"), and judge every query by totalDocsExamined / nReturned.
  5. MongoDB 8.3 made multi-planning with a cost-based ranker the default plan-selection mechanism for eligible queries, after fifteen years of pure trial-execution multiplanning — with new explain and serverStatus output. Related currency: index filters are deprecated in favour of setQuerySettings (8.0), and 8.0 narrowed the slot-based engine's remit back to trySbeRestricted.
  6. Write concern is durability, read concern is visibility, read preference is routing — three orthogonal knobs. w: "majority" has been the default since 5.0 and is what makes a write un-rollbackable; wtimeout does not cancel a write, it only stops you waiting, so the correct response is an idempotency key, not a retry. Read-your-own-writes from a secondary is a causally consistent session, not a trip to the primary.
  7. Shard key = cardinality + frequency + non-monotonicity, chosen so your hot queries stay single-shard. A query without the shard key is a scatter-gather whose latency is the slowest shard's. It is no longer irreversible — refineCollectionShardKey (4.4) appends fields, reshardCollection (5.0, much faster in 8.0) replaces it — and 8.3 deprecated removeShard in favour of explicit startShardDraining / shardDrainingStatus / commitShardRemoval.
  8. Transactions are real ACID with snapshot isolation, and their existence does not change the modelling advice. 60-second default lifetime, use the driver's withTransaction helper for the retry semantics, retry the whole callback on TransientTransactionError and only the commit on UnknownTransactionCommitResult — and prefer single-document atomicity, optimistic concurrency with a version field, or the outbox pattern first.
  9. Saturation is tickets and eviction, not CPU. The WiredTiger cache defaults to half of RAM minus a gigabyte (settable as a percentage of RAM since 8.2), application threads start evicting at 95% of cache, and that is the cliff. The 8.x line added real admission control — ingress rate limiting, pre-auth buffer caps, overload-aware server selection, server-dictated client backoff — so the database can shed load instead of degrading for everyone.
  10. Search and Vector Search went GA for self-managed deployments on 1 July 2026 — free with Community 8.2+ via the mongot binary, with parity on $search, $vectorSearch, $rankFusion (GA 8.0) and $scoreFusion (GA 8.3). And the security line to have ready: MongoBleed, CVE-2025-14847, CVSS 8.7 — an unauthenticated heap-memory leak in the zlib wire-compression path, exploited in the wild and CISA-KEV listed, patched in 8.2.3 / 8.0.17 / 7.0.28 and below, automatic on Atlas and manual everywhere else.

If you get exactly one "what's new?" question, answer with this: 8.3 shipped in May 2026 with a cost-based query planner as the default ranker and double-digit throughput gains from PGO/LTO; Search and Vector Search left Atlas and went GA for self-managed clusters in July; hybrid retrieval is now declarative with $rankFusion and $scoreFusion; the release model split into two-year majors with five-year support versus continuously-upgraded minors; and MongoBleed made patch currency and network exposure the security conversation of the year.
