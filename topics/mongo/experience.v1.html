01The query that stopped using its index

tier · senior → staff archetype · performance diagnosis

EXAMPLE — replace with your own

The complaint was narrow and therefore useful: one screen, the order-history list for business accounts, went from “instant” to “about nine seconds” some time over a weekend, and only for accounts with more than a few thousand orders. Nothing had deployed. The orders collection held roughly 340 million documents on a three-node replica set, and the API p99 for that route had gone from 180ms to 8.6s while every other route stayed flat.

I went to the database profiler first, because “nothing deployed” usually means something did, just not by us. Setting db.setProfilingLevel(1, { slowms: 200 }) for ten minutes on a secondary gave me the actual shape of the slow op, and explain("executionStats") on it told the whole story: totalKeysExamined: 0, totalDocsExamined: 341,882,004, winning plan COLLSCAN. The index it should have used, { accountId: 1, status: 1, createdAt: -1 }, existed and was healthy. What had changed was the query: a product change had added an optional date range, and the ORM was emitting createdAt as a $gte/$lte pair before the sort field in a way that made the compound index only partially usable — and, worse, an added $regex on a free-text reference field with a leading wildcard, which no b-tree can seek into.

Two mechanisms are worth being able to explain here, because interviewers drill straight into them. The first is the ESR rule: in a compound index, put Equality predicates first, then the Sort keys, then Range predicates. Get that order wrong and the index can still be used for the equality prefix, but the sort spills into an in-memory SORT stage that is capped at 100 MB and, above that, either fails or spills to disk. The second is the plan cache: MongoDB caches a winning plan per query shape, and a change in shape — one extra predicate — is a new shape, replanned from scratch. What looked like “the index stopped working” was “a new shape appeared and the planner honestly picked the least-bad plan available for it”.

// What the app had started sending (new shape, no usable index)
db.orders.find({
  accountId: ObjectId("..."),
  status: { $in: ["shipped", "delivered"] },
  createdAt: { $gte: from, $lte: to },
  reference: { $regex: "INV-2026", $options: "i" }   // unanchored + case-insensitive: no index seek
}).sort({ createdAt: -1 }).limit(50);

// Diagnosis
db.orders.find(q).sort({ createdAt: -1 }).limit(50).explain("executionStats");
// -> stage: COLLSCAN, totalDocsExamined: 341882004, executionTimeMillis: 8611

// The index built to match ESR: equality, then sort, then range
db.orders.createIndex(
  { accountId: 1, status: 1, createdAt: -1 },
  { name: "acct_status_created", background: true }   // 'background' is a no-op since 4.2; builds are hybrid
);

// And the free-text predicate moved off the b-tree entirely
db.orders.aggregate([
  { $search: { index: "orders_text", text: { query: "INV-2026", path: "reference" } } },
  { $match: { accountId: ObjectId("...") } },
  { $limit: 50 }
]);

The fix took two days and three moves. The date range moved to the end of the predicate so the existing compound index served equality-then-sort and applied the range as a bounded scan; the regex came out of the query entirely and became an Atlas Search $search stage, because a case-insensitive unanchored regex is a collection scan wearing a costume; and I added a planCacheShapeHash alert on the slow-query log so a new shape on a hot collection pages someone rather than waiting for a customer. Results: p99 8.6s → 210ms, totalDocsExamined per query 341M → 62, and CPU on the primary down from a sustained 85% to 22%.

What I would do differently: I spent the first afternoon comparing index definitions between environments, convinced someone had dropped an index, when thirty seconds of explain on the actual query would have shown me a query I did not recognise. I now start every performance investigation by capturing the real operation from the profiler or $currentOp, not by reading the code that I think produces it.

What the interviewer is really probing. Whether you reason about the query planner rather than about indexes as magic. The signal is naming the tool (profiler, explain("executionStats"), $currentOp), quoting totalKeysExamined against totalDocsExamined against nReturned, and knowing that a query shape — not a collection — is the unit the planner caches.

The mistake candidates make. “I added an index and it got faster” with no before/after numbers and no explanation of why the old plan lost. The other classic is claiming the planner “chose wrong”; it almost never does — it chose the best of the plans you gave it, and your job is to give it a better one.

(c) Recall prompts

When did a MongoDB query behave differently in production than it did on your machine?

Almost always a data-shape difference: cardinality, skew, or a collection that fits in cache locally and does not in production. Hint — if your dev database has ten thousand documents and production has ten million, every plan you tested was chosen against the wrong statistics. If nothing comes to mind, think of a demo that hung, or a report that timed out only for your biggest customer.

What is the worst totalDocsExamined to nReturned ratio you have personally seen?

Run explain("executionStats") on your current app's three hottest queries today; most people find at least one scanning thousands of documents to return ten. The story is the surprise plus what you did — including “nothing, it was 4ms on a small collection and I moved on”, which is a perfectly senior answer if you can say why.

Which index of yours turned out to be the wrong fix?

Wrong fixes are the strongest material: an index that duplicated an existing prefix, one that made writes 30% slower for a query run twice a day, one that was never chosen because a different plan won the trial period. Say what $indexStats told you afterwards.

Have you had to explain a query plan to someone who did not believe you?

Usually a developer certain their index “should” work, or a vendor blaming the database. If you have ever pasted an explain output into a thread and ended an argument with it, that is the story — and the staff-level version is what you changed so the argument did not recur.

(d) Follow-up drill chain

Why does index field order matter, in mechanical terms?

Because a MongoDB index is a B-tree over a composite key, and the keys are ordered left to right. A seek can only use a contiguous prefix of that key: equality predicates pin a prefix to a single value, so everything after them is still sorted; a range predicate leaves the remaining fields unordered within the range, which is why a sort key placed after a range has to be re-sorted in memory. That is the whole content of the ESR rule — equality first because it preserves order for free, then sort so the index scan comes out already ordered, then ranges because they are the last thing that can still be a bounded scan.

At what scale does the in-memory sort actually break?

The blocking SORT stage has a 100 MB memory limit per operation. Under that it is invisible; over it, a plain find errors with Sort exceeded memory limit unless you enable disk use, and an aggregation spills to disk — which since 6.0 it does by default, because allowDiskUseByDefault is on. Spilling is not free: it writes temp files under the dbPath and turns a CPU-bound operation into an IO-bound one, so at any real concurrency you feel it as latency long before you see an error. My rule is that a sort which is not served by an index is a bug on any collection that grows.

How would you catch this before a customer does?

Three layers. Slow-query logging with a threshold that means something for your service (we used 200ms, not the 100ms default), shipped to the same place as application logs so a shape can be correlated with a deploy. Second, an alert on the ratio of documents examined to documents returned rather than on raw latency, because that ratio moves first and is scale-independent. Third — and this is the one people skip — a check in CI that runs explain against a production-shaped dataset for the routes you care about and fails the build on a COLLSCAN. Latency alerts tell you that you already have an incident; plan alerts tell you that you are about to.

What did you trade away by moving the text predicate to Atlas Search?

Consistency and a dependency. $search reads from a Lucene index that is maintained asynchronously from the change stream, so it is eventually consistent — a document written and immediately searched may not be found, which mattered for our “create then look it up” flow and forced an explicit read-your-writes path through _id. It also cannot be combined freely with the rest of the pipeline: $search must be the first stage, so any filter you want applied before scoring has to live inside the search operator's own compound clause. In exchange we got relevance ranking, language analysers and predictable latency on a query no b-tree could serve.

Would the 8.3 cost-based ranker have changed the outcome?

Probably at the margins, not fundamentally. Since 8.3 the cost-based ranker is the default plan-selection mechanism for eligible queries, with classic multi-planning as the fallback, so instead of racing candidate plans for a trial period the planner estimates cost from statistics. That helps most when two plausible index plans differ subtly; it does not conjure a plan that does not exist, and our problem was that no index could serve an unanchored case-insensitive regex. What it did change for us operationally is monitoring: 8.3 adds metrics.query.cbr.* to serverStatus and CBR fields to explain, so a plan-choice regression is now something you can watch rather than infer.

What would you do differently now?

Own query shapes explicitly. The root cause was that an ORM could emit a brand-new shape against a 340-million-document collection with no review, because nobody treated “the set of shapes this service sends” as an artefact. I would keep that list in the repository, generated from the profiler in a load-test environment, diffed in CI, with an index named for each shape. I would also use query settings rather than the deprecated index filters to pin a plan when we genuinely need to, since index filters are deprecated and do not survive a restart, while query settings are persisted in the cluster.

02Embed or reference: the document that grew

tier · staff → principal archetype · architectural trade-off

EXAMPLE — replace with your own

We modelled a logistics shipment as one document with its events embedded: { _id, shipmentRef, customer, status, events: [ … ] }. It was the right call at design time — a shipment had four or five scans, one read fetched everything, and there were no joins. Eighteen months later we onboarded a customer whose parcels were scanned at every conveyor junction, and shipments started accumulating two to three thousand events. Writes to those documents went from 3ms to 400ms, the working set stopped fitting in cache, and one shipment finally hit BSONObjectTooLarge — the hard 16 MB document limit — which is how a modelling decision announces itself as an outage.

The mechanism is worth stating precisely, because “MongoDB is bad at large documents” is not an answer. WiredTiger stores a document as a unit: any update to any field rewrites the whole document into the cache and, at the next checkpoint, to disk. A 4 MB shipment updated on every scan means 4 MB of cache churn and 4 MB of oplog entry per scan, replicated to every secondary. Add an array that grows and every $push is also a document move risk and an index-key rewrite for any index on the array. The 16 MB limit is the cliff, but the cost curve starts long before it — my rule of thumb is that an array is safe when it is bounded by something in the real world (addresses per customer, sizes per product) and dangerous when it is bounded only by time.

I did not simply split it. I wrote down three candidate models and what each cost, then made the team argue about the read patterns rather than about elegance. We ended with the subset pattern: the shipment document keeps the last twenty events inline, which is what 94% of reads actually need, and the full history lives in an events collection keyed by { shipmentId: 1, at: -1 }. The list screen and the API's default response never touch the second collection; the “full audit trail” view does one extra query. Because events are immutable and time-ordered, we later moved that collection to a time series collection, which stores them column-wise in buckets and cut its storage by about 4× — but I deliberately did that as a second step, months later, so we were not debugging two changes at once.

// Before: unbounded array, whole-document rewrite on every scan
db.shipments.updateOne(
  { _id: id },
  { $push: { events: { at: new Date(), scan: "HUB_OUT", site: "LEJ" } } }
);

// After: bounded inline subset + an append-only history collection
db.shipments.updateOne(
  { _id: id },
  { $push: { recentEvents: { $each: [ev], $sort: { at: -1 }, $slice: 20 } },
    $set:  { status: ev.scan, updatedAt: ev.at } }
);
db.shipmentEvents.insertOne({ shipmentId: id, ...ev });

// The history collection, once the pattern had settled (5.0+ time series)
db.createCollection("shipmentEvents", {
  timeseries: { timeField: "at", metaField: "shipmentId", granularity: "minutes" },
  expireAfterSeconds: 63072000   // 2 years, enforced by the bucket TTL
});

Numbers after the change: p99 write latency 400ms → 6ms, oplog throughput on that cluster down 71% (which incidentally doubled our oplog window from nine hours to nineteen), and the largest shipment document went from 4.1 MB to 38 KB. The read path cost us one extra round trip on 6% of requests, measured at +11ms.

What I would do differently: I would have written the “what bounds this array?” question into our design template from day one. The original decision was not wrong — it was un-revisited. I would also have shipped a monitoring query for document size ($bsonSize in an aggregation, run weekly) years earlier; we had no idea we were at 4 MB until we were at 16.

What the interviewer is really probing. Whether you model from access patterns or from entity diagrams. At staff and above they want to hear you name the physical consequence — document rewrite cost, oplog size, cache residency — not just “embed for one-to-few, reference for one-to-many”, which is a slogan anyone can repeat.

The mistake candidates make. Presenting the relational answer (“I normalised it”) as obviously correct, or the document answer (“embedding is faster”) as obviously correct. The senior signal is that you changed the model because a specific read/write ratio changed, and that you can say what you would have done if the ratio had been the other way.

(c) Recall prompts

Which document in a system you own has grown in a way nobody designed for?

Look for arrays named history, events, comments, lineItems, auditLog. Run db.coll.aggregate([{ $project: { s: { $bsonSize: "$$ROOT" } } }, { $sort: { s: -1 } }, { $limit: 5 }]) on a secondary today — the top five will tell you a story you did not know you had.

When did you choose embedding and later regret it — or choose referencing and later regret that?

The referencing regret is just as common and less often told: three collections and an application-side join for data that is always read together, costing three round trips per page. That version of the story shows range, because most candidates only have the “array got too big” one.

Have you migrated a document model in production without downtime?

Recall the mechanics: did you dual-write, backfill in batches with a resumable cursor, version the documents with a schemaVersion field, or read-repair lazily? The chosen mechanism is the answer to “how did you de-risk it”.

When did a modelling decision of yours show up as an operational problem somewhere else?

Oplog window, backup duration, restore time, replication lag, index build time, cache eviction. Being able to trace “I embedded an array” to “our backups stopped finishing overnight” is a principal-level connection.

(d) Follow-up drill chain

Why is a growing array worse than a growing collection?

Because the document is the unit of atomicity, of storage and of replication. Updating one element rewrites the entire document in the WiredTiger cache and emits an oplog entry sized by the change — and for array updates that entry can be the whole array unless the update is expressible as a targeted $set on a positional path. A separate collection turns an O(document size) write into an O(one small document) insert, and inserts are the cheapest thing MongoDB does. The collection also gives you independent indexing and independent TTL, neither of which an embedded array can have.

At what array length would you actually worry?

I do not use a length threshold, I use two other tests. First: is the bound a real-world quantity or a clock? Anything bounded by time is unbounded. Second: what is the document's size at the 99.9th percentile of your data, and what does it cost to rewrite that on every update? In practice a few hundred small elements is fine, a few thousand is a smell, and any array that also carries a multikey index is worse than its size suggests because every write rewrites index keys for every element. The 16 MB limit is a backstop, not a target.

You split the collection — how did you keep the two consistent?

Deliberately not with a transaction. The inline subset is a cache of the history collection, so I made the history collection the source of truth, wrote to it first, and updated the subset second; if the second write fails the worst outcome is a stale list that self-heals on the next event, and a nightly reconciliation job that rebuilds subsets for shipments whose last event timestamps disagree. Wrapping both writes in a multi-document transaction was possible and I rejected it: it would have added a distributed-commit cost to the hottest write path in the system to protect against an inconsistency that was cosmetic and self-correcting. Transactions are for invariants, not for tidiness.

What did the time series conversion actually buy, and what did it cost?

Time series collections, GA since 5.0 and considerably improved through 7.0's compression and 8.0's block processing for aggregations, store measurements in buckets grouped by the metaField and time, then columnar-compress each bucket. For us that was roughly a 4× storage reduction and a large win on range scans, because one bucket read replaces hundreds of document reads. The costs are real: updates and deletes are restricted (arbitrary updates only arrived in 8.0 and are still not something I would build a workflow on), the metaField choice is effectively permanent because it determines bucketing, and you cannot shard on an arbitrary key. It suits append-only telemetry; it does not suit anything you will edit.

How did you get the team to agree, given half of them wanted a full relational split?

I refused to run it as an opinion contest. We spent one session collecting the actual access patterns from the profiler — read/write ratio per collection, which fields were projected, what the p99 payload size was — and only then looked at models. Once the data said 94% of reads wanted the last twenty events, the subset pattern stopped being my preference and became the obvious answer, and the person who had argued hardest for a full split wrote the migration. The general technique: turn an architecture argument into a measurement argument, then let the measurement be the authority instead of you.

What would you do differently now?

Design the escape hatch at the start. The expensive part was not the new model, it was that a hundred call sites assumed shipment.events existed. If the original API had returned events through an accessor from day one — even one that just read the embedded array — the migration would have been a week instead of a quarter. I now treat “can this shape change without touching every caller?” as a first-class design question, and I add a document-size dashboard to any collection with an array in it before it ships.

03The primary that stepped down mid-checkout

tier · senior → staff archetype · production incident

EXAMPLE — replace with your own

At 14:07 on a Tuesday the checkout service started returning 500s at about 12% of requests. It lasted nine minutes, recovered on its own, then did it again forty minutes later. The database dashboards looked fine in every one-minute aggregate, which is exactly why the first twenty minutes went badly: we were looking for a slow database and the database was not slow, it was absent for about eleven seconds at a time.

What had happened was a replica set election. A kernel upgrade rolling through the fleet had briefly starved the primary of IO, its heartbeats to the other members timed out, and the set elected a new primary — twice. An election is normal and healthy; the incident was that our application handled it badly. Two mechanisms explain the whole outage. First, during an election there is no primary, so every write fails fast and every read with readPreference: primary fails with it, for as long as the driver's serverSelectionTimeoutMS allows — ours was set to 5 seconds but the retry loop above it gave up after one attempt. Second, our writes used writeConcern: { w: 1 } and the service had disabled retryable writes years earlier because someone had hit a bug in a driver version we no longer ran, so an in-flight write during a step-down was simply lost rather than retried against the new primary.

I was incident commander, not the fixer. The sequence I ran: declare, mitigate, then diagnose. Mitigation was pausing the kernel rollout, which stopped the bleeding within four minutes of us understanding it — I did not wait to understand why the node was IO-starved before stopping the thing that was causing elections. Diagnosis came from correlating rs.status() election terms with the application error timestamps: two elections, two error windows, exact overlap. That correlation took one query and it is the thing I would teach a junior to reach for first.

// The evidence that ended the debate: election terms against error windows
db.getSiblingDB("local").oplog.rs.find(
  { op: "n", "o.msg": /new primary|election/i }, { ts: 1, "o.msg": 1 }
).sort({ ts: -1 }).limit(10);

rs.status().members.map(m => ({ name: m.name, state: m.stateStr, term: m.electionTerm }));
// The fix, at the connection string: retryable writes and majority durability
// mongodb+srv://…/?retryWrites=true&w=majority&readConcernLevel=majority
//   &serverSelectionTimeoutMS=30000&heartbeatFrequencyMS=5000

// and the invariant that had been silently unenforced
db.orders.insertOne(order, { writeConcern: { w: "majority", wtimeout: 5000 } });

The follow-ups mattered more than the fix. We turned retryWrites back on — it has been the driver default since MongoDB 4.2 and our explicit false was a fossil — moved order writes to w: "majority" so an acknowledged order survives a failover, raised serverSelectionTimeoutMS to 30 seconds so the driver rides out an election instead of erroring during it, and added a synthetic check that steps down a primary in staging every week so failover is a rehearsed event rather than an incident. Measured: the next real election, six weeks later, produced 40 failed requests instead of 14,000, and a 900ms latency bump instead of a nine-minute outage.

What I would do differently: I would not have accepted “the database was fine” from a one-minute dashboard. Eleven-second events are invisible at one-minute resolution, and that single observability gap cost us twenty minutes of an incident. I would also have found the disabled retryWrites in a config audit rather than in an outage — a setting that overrides a safe default deserves a comment explaining why, and ours had none.

What the interviewer is really probing. Incident-command judgment: did you mitigate before you diagnosed, did you communicate, did you know your role. Technically they want to hear that you understand a step-down is a normal event and that availability during one is an application property — driver settings, retryability, write concern — not something the database owes you.

The mistake candidates make. Telling it as a solo rescue. Real incidents have a commander, a person on the keyboard and someone writing the customer update; say which you were and name what the others did. The second mistake is stopping at the fix and never mentioning the follow-ups, which is where all the staff-level signal lives.

(d) Follow-up drill chain

Walk me through what actually happens during an election.

Members heartbeat every two seconds by default and consider a peer down after ten. When a secondary stops hearing from the primary it increments the term and calls for votes; a candidate needs a strict majority of votes from the configured members, and it must have an oplog at least as fresh as any voter's. Priorities and electionTimeoutMillis shape who wins and how fast. Meanwhile the old primary, if it is merely partitioned rather than dead, steps down when it discovers it cannot see a majority — that is what prevents split brain. Practically: no writes for the duration, typically a couple of seconds up to about twelve, and any writes acknowledged only by the old primary at w: 1 can be rolled back when it rejoins.

What exactly does retryWrites guarantee, and what does it not?

The driver attaches a statement id to eligible writes and the server records the outcome per session, so if the connection dies or a new primary appears, the driver retries once and the server recognises a duplicate and returns the original result rather than applying it twice — that is the exactly-once part. What it does not cover: multi-document writes such as updateMany and deleteMany, which are not retryable because they are not idempotent by statement id; unacknowledged writes; and anything inside a transaction, which has its own retry semantics via TransientTransactionError. It also only retries once, so it survives a failover, not a sustained outage.

Why not just set w: "majority" everywhere?

Because it couples your write latency to your slowest majority member, and in a cross-region set that can be a round trip you did not budget for. It also does not do what people assume: majority acknowledgement means durable against rollback, not visible to subsequent readers — for read-your-writes you need readConcern: "majority" plus causal consistency in the session, or you read from the primary. I use majority for anything a customer would notice losing, and w: 1 for high-volume, reconstructible data such as telemetry, and I write the reason next to the setting.

At what point does riding out elections stop working?

When the elections stop being transient. Raising serverSelectionTimeoutMS to 30 seconds converts a short unavailability into latency, and that is the right trade for a checkout; it is the wrong trade for a request with a 2-second SLA, where you want to fail fast and shed load. It also stops working when the cause is not a step-down but a majority loss — two of three nodes gone means no primary and no election, and no client-side timeout saves you. That is when the answer becomes capacity and topology: more voting members across more failure domains, and a documented decision about whether you will ever accept stale reads to stay up.

How do you rehearse this without risking production?

Deliberate step-downs. rs.stepDown() on a staging primary weekly, in business hours, with the same client configuration as production, asserting on error counts — that converts a rare scary event into a routine one and catches config drift in the drivers. In production I do the same during planned maintenance windows rather than pretending failovers only happen to other people. The cultural half matters more than the technical half: teams that have never seen a failover write applications that assume a database is a single always-present machine.

What would you do differently now?

Instrument the client, not just the server. Every driver exposes command-monitoring and SDAM events — topology changes, server heartbeats, connection-pool churn — and shipping those as metrics would have shown us “primary disappeared” from the application's own point of view, which is the only point of view that matters to a user. I would also alert on election count per cluster as a leading indicator, because two elections in an hour is a story regardless of whether anyone has complained yet.

04Four major versions in one year

EXAMPLE — replace with your own

We were on 4.4, two years past its end of life, on self-managed hardware, with eleven services and one very old data-access library between them and the database. The trigger was not engineering enthusiasm — it was an audit finding that we were running an unsupported version with unpatched CVEs. My job was to get us to 8.0 without a maintenance window longer than a rolling restart, and the constraint that made it interesting is the one everybody discovers late: you cannot skip majors. 4.4 → 5.0 → 6.0 → 7.0 → 8.0, four hops, each one gated on setting the feature compatibility version.

The FCV mechanism is the heart of this story and it is what interviewers drill on. When you upgrade binaries, the server keeps behaving like the previous version until you run setFeatureCompatibilityVersion. That gap is the safety net: binaries up, soak, and if anything is wrong you downgrade binaries cleanly because no on-disk format or feature that the old version cannot read has been enabled. The moment you raise FCV, downgrade stops being a restart and starts being a restore. So the shape of each hop was: upgrade secondaries one at a time, step down the primary, upgrade it, run for a week on the new binaries at the old FCV, then raise FCV as a separate, tiny, reversible-in-principle change.

The things that actually bit us were not the server, they were the periphery. The driver had to be upgraded first and independently, because a driver more than one major behind the server is unsupported and ours was three. mapReduce, deprecated since 5.0, was still in two reporting jobs and had to become aggregation pipelines. In 5.0 the default writeConcern for the majority calculation changed and an under-provisioned analytics node started delaying majority commits. In 6.0 aggregations began spilling to disk by default (allowDiskUseByDefault), which turned two queries that used to fail loudly into two queries that succeeded slowly — arguably worse. And in 8.0 the storage-engine concurrency parameter was renamed: wiredTiger.concurrentTransactions became queues.execution, so a dashboard we had relied on for years quietly went blank.

// The per-hop ritual, in order

The payoff was concrete rather than ideological: on 8.0 the same read workload ran at roughly two-thirds of the previous CPU on the same hardware, our p99 on the two heaviest aggregation pipelines dropped by about 40%, and we could finally use reshardCollection and Queryable Encryption range queries, which unblocked two projects that had been parked.

What I would do differently: I sequenced by version instead of by risk. The right first move was to upgrade the driver and delete the deprecated usages while still on 4.4, because that work was independent of the server and could have been done by three teams in parallel months earlier. I also should have insisted on a production-shaped restore test at the start; our first “can we actually restore a 4.4 backup?” rehearsal happened in month three, and it failed.

(d) Follow-up drill chain

Why can you not skip major versions?

Because each major only knows how to read, and upgrade, the on-disk and replication formats of its immediate predecessor, and the FCV machinery only accepts a transition of one step. Skipping would mean the new binaries encountering catalog and oplog structures they have no migration path for. Practically it also protects you: each hop is a separate soak with a separate rollback, so a problem is attributable to one version's changes rather than to four at once. The one exception people quote is that rapid releases within a major (8.1, 8.2, 8.3) fold forward into the next yearly major, so you are never forced to adopt them individually.

What exactly happens when you raise the FCV, and why is it a one-way door?

Raising FCV flips on features and on-disk formats that older binaries cannot interpret — new index versions, new catalog fields, new oplog entry shapes. Once written, a previous-version binary meeting them will refuse to start or, worse, misread them. There is a setFeatureCompatibilityVersion downgrade path and in a clean cluster it can work, but it must undo anything already written in the new format, so it can fail partway and it is not a plan I would bet a Saturday on. My operational rule: treat binary upgrade as reversible and FCV as irreversible, put a soak period between them proportional to how long your slowest bug takes to appear, and never do both in the same change window.

How did you decide the soak period was long enough?

By asking what our slowest-appearing failure class was. Ours was month-end reporting, so a soak shorter than a full month-end could not have surfaced it; we settled on a week for ordinary hops and made the hop before month-end wait. I also weighted it by blast radius — the analytics replica set went first every time as a canary, because its consumers could tolerate a bad day and its workload was the most aggregation-heavy, which is where behaviour changes concentrate. A soak with no defined signal is just a delay; we listed what we were watching (replication lag, plan changes, error classes, p99 per pipeline) before each one.

What did you trade away by doing it this slowly?

Eleven months of engineering attention and a real opportunity cost — two teams deferred work waiting for Queryable Encryption range support, which only landed for us at the end. A faster path existed: dump and restore into a fresh 8.0 cluster with a cutover, which would have taken weeks rather than months. I rejected it because our largest collection could not be restored inside the acceptable window and because a cutover concentrates all the risk into one irreversible night. If our data had been a tenth of the size, I would have chosen the cutover and I would say so in an interview, because the point is that the decision followed the constraint rather than a preference.

How did you handle the teams who did not want to upgrade their drivers?

I removed the ambiguity and then removed the work. First the ambiguity: a shared page showing, per service, its driver version, the versions it would be compatible with after each hop, and the date it would break — facts rather than requests. Then the work: I wrote and tested the upgrade for the two oldest services myself and opened the pull requests, which turned “please do this” into “please review this”. One team still pushed back, with a legitimate reason — a serialisation behaviour change in the new driver — so we found it, fixed it, and it became a note in the shared page for everyone else. Making other people's cost small is more effective than making their risk loud.

What would you do differently now?

Never get four majors behind again, which means treating the version as a service-level objective with an owner rather than as a project. Concretely: a quarterly patch cadence, an alert when the running version enters its final year of support, and a standing staging cluster one major ahead of production so the next hop is continuously rehearsed instead of planned. That is the difference between an upgrade programme and an upgrade habit, and only the habit survives the next reorganisation.

05Transactions versus document design

EXAMPLE — replace with your own

A senior engineer joining from a decade of SQL wrote a proposal to standardise on multi-document transactions for “all business operations”. It was a good proposal: clearly argued, honest about the cost, and it came with a working prototype. I disagreed with it and I want to be accurate about why, because “MongoDB transactions are slow, avoid them” is the lazy version of this answer and it is wrong.

His best argument was the strongest one anybody makes: correctness should not depend on every developer remembering to design documents so that an operation touches only one of them. He had found three real bugs where a partial write left a booking without its payment record. Those bugs existed. What I disagreed with was the generalisation, and I said so by putting numbers on it rather than by asserting a principle. We benchmarked his prototype against the same operations restructured to be single-document: on our cluster, the transactional version ran at about 4,100 ops/sec with a p99 of 96ms, the single-document version at about 23,000 ops/sec with a p99 of 11ms, and under a deliberately induced failover the transactional version produced a burst of TransientTransactionError retries that his code did not handle.

The mechanism matters here. A MongoDB transaction takes a snapshot at start and holds it; WiredTiger must keep every version of every document touched since that snapshot in cache, so long transactions cost memory across the whole cluster, and the default transactionLifetimeLimitSeconds of 60 exists precisely to stop one from pinning cache indefinitely. Write conflicts are detected at commit and surfaced to the client as retryable errors, so the application must implement a retry loop — the driver's withTransaction helper does this for you, and code that calls startTransaction directly usually does not. On a sharded cluster the commit becomes a two-phase commit across shards, adding a coordinator round trip. None of this makes transactions bad; it makes them a tool with a price tag.

// The pattern we standardised on: single-document atomicity where the invariant allows it
db.bookings.updateOne(
  { _id: id, status: "held", "payment.state": { $ne: "captured" } },   // the guard IS the concurrency control
  { $set: { status: "confirmed", "payment.state": "captured", "payment.ref": ref },
    $push: { audit: { at: new Date(), by: actor } } }
);
// matchedCount === 0 means someone else got there first — a business outcome, not an error

// And where the invariant genuinely spans documents, the correct shape:
await session.withTransaction(async () => {          // retries TransientTransactionError for you
  await ledger.insertOne(entry, { session });
  await accounts.updateOne({ _id: from }, { $inc: { balance: -amount } }, { session });
  await accounts.updateOne({ _id: to },   { $inc: { balance:  amount } }, { session });
}, { readConcern: { level: "snapshot" }, writeConcern: { w: "majority" }, maxCommitTimeMS: 5000 });

Where we landed was not my position and not his. We agreed a written rule: an invariant that can be expressed within one document is enforced by the document — with a guarded update whose filter carries the precondition — and an invariant that genuinely spans entities uses withTransaction, with a hard rule that a transaction touches at most three collections and runs for under a second. We wrote the double-entry ledger, which is a real cross-document invariant, as a transaction and I reviewed it myself. He owned the rule document; a year later he was the person enforcing it in reviews, which is a better outcome than my having won the argument.

What I would do differently: I let the disagreement run for three weeks in pull-request comments before we sat down with a benchmark. Twenty minutes of agreeing on how we would decide, at the start, would have saved all of it. I also under-credited his point at first — the partial-write bugs were real and my initial response was too close to “you are thinking relationally”, which is dismissive and, worse, unhelpful.

(d) Follow-up drill chain

What does a MongoDB transaction actually cost, mechanically?

Three things. Snapshot retention: WiredTiger must keep the pre-images of everything the transaction reads or writes for its whole life, so cache pressure scales with duration times footprint, and that pressure is felt by every other operation on the node. Conflict handling: writes conflict at commit, so throughput degrades non-linearly under contention on hot documents, and the client must retry. And on sharded clusters, a two-phase commit coordinated by one shard, adding at least one extra round trip and a coordination document. The 60-second default lifetime limit is a guard rail against the first of those, not a suggestion.

At what point does the single-document approach stop working?

When the entities have genuinely independent lifecycles or independent access patterns, and squeezing them into one document creates the array-growth problem from story 02. A booking and its payment can live in one document; an account and its ten million ledger entries cannot. It also stops working when two different consumers need to lock different parts of the same document at high frequency — then you are serialising unrelated work on one write lock, and splitting into two documents plus a transaction is genuinely the better design. The test I use: would I still model these as one document if there were no transaction question at all? If yes, the single-document answer is honest; if I am only merging them to avoid a transaction, that is a smell.

How do you handle a transaction that keeps aborting under contention?

First measure whether it is a write conflict or a timeout, because the fixes diverge. Write conflicts mean two transactions touched the same document — reduce the footprint, shorten the transaction, or remove the hot document entirely by sharding the counter into buckets summed at read time. Timeouts mean the transaction is doing too much: move reads outside it, do validation before opening it, and never call an external service inside one. Retrying harder is the wrong answer; an exponential backoff on a contended document converts a latency problem into a thundering herd. If contention is inherent — everyone decrementing one inventory count — the right fix is usually a queue or a reservation model, not a stronger isolation level.

What isolation guarantee do you actually get?

Snapshot isolation, with readConcern: "snapshot" giving a consistent view as of a majority-committed point in time, and — importantly — writes conflicting rather than blocking. There is no read-write blocking as in a lock-based system, and there are no gap locks, so phantom-prevention patterns you might carry from SQL do not transfer; a uniqueness invariant still needs a unique index, not a read-then-write inside a transaction. Outside a transaction, single-document operations are atomic and readers never see partial documents, which covers far more real invariants than people expect.

How did you make sure the rule was actually followed after the debate ended?

By making it cheap to follow and visible when it was not. The data-access library grew a helper that wrapped withTransaction with our limits baked in — commit timeout, collection count assertion, metrics — so the compliant path was also the easiest path. Then a dashboard of transaction count, duration and abort rate per service, reviewed monthly, which turned drift into a conversation rather than a discovery. Written rules with no instrumentation decay in about two quarters in my experience; the instrumentation is what makes the rule real.

What would you do differently now?

Start with the bugs, not the design. He had three concrete partial-write defects; the fastest route to agreement would have been to fix those three, together, one at a time, and let the general rule emerge from what each one actually needed. Two of them turned out to be single-document problems and one was a genuine cross-entity invariant — which is exactly the rule we eventually wrote, arrived at three weeks late by argument instead of two days early by doing the work.

06The duplicate key that only happened at 3am

tier · mid → senior archetype · nasty debugging session

EXAMPLE — replace with your own

An ingestion service raised E11000 duplicate key error on a collection whose whole point was that it used an upsert to be idempotent. It happened roughly eleven times a night, always between 02:40 and 03:20, never during the day, and never in staging. It had been failing for four months and had been triaged twice as “transient, retried successfully” — which was true, and which is why nobody had looked properly.

The code looked correct: updateOne({ externalId }, { $setOnInsert: … }, { upsert: true }) against a collection with a unique index on externalId. Upserts are supposed to be safe. The part that is not in most people's heads is that an upsert is not a single atomic find-and-insert against the index: the server first looks for a match, and if it finds none it attempts an insert. Two concurrent upserts for the same missing key can both find nothing and both attempt the insert, and one of them will lose to the unique index. The documentation says this plainly and recommends exactly one mitigation — a unique index, so the loser gets a duplicate-key error rather than a duplicate document — plus retrying the operation on that error, which turns it into a matched update.

So why 3am? That was the second half of the puzzle and the part I got wrong twice. Our upstream partner sent a nightly reconciliation batch that replayed the last 24 hours of events, and our consumer processed it with a concurrency of 32 across two pods. During the day, events for one externalId arrived seconds apart and never overlapped; in the nightly replay the same id could appear four times inside the same millisecond, on different workers. The bug was not in the database and not really in the upsert — it was that our consumer had no per-key ordering, and the nightly batch was the only workload that exposed it.

// The race: both workers match nothing, both insert, one loses to the unique index
db.events.createIndex({ externalId: 1 }, { unique: true });
db.events.updateOne(
  { externalId: id },
  { $setOnInsert: { externalId: id, createdAt: now }, $set: { payload, seenAt: now } },
  { upsert: true }
);
// -> MongoServerError: E11000 duplicate key error collection: app.events index: externalId_1
// Mitigation 1: treat 11000 on an upsert as "someone else inserted it" and retry once
try { await coll.updateOne(filter, update, { upsert: true }); }
catch (e) { if (e.code === 11000) await coll.updateOne(filter, update, { upsert: true }); else throw e; }

// Mitigation 2 (the real fix): make the key deterministic so the write is naturally idempotent
const _id = createHash("sha256").update(externalId).digest("hex").slice(0, 24);
await coll.updateOne({ _id: ObjectId(_id) }, { $set: doc }, { upsert: true });

What actually found it: I stopped reading code and turned on the profiler with slowms: 0 for a sixty-second window during the batch, on one node, and sorted the captured operations by externalId. Four upserts for the same id inside two milliseconds, from two different appNames. That single output ended a four-month mystery in about ten minutes, and the lesson I took is that reproducing the concurrency is worth more than reading the code that produces it.

The fix was in two layers, deliberately. Immediately, the retry-on-11000, which is the documented mitigation and took an hour. Structurally, we made the identity deterministic — deriving _id from the external id so the insert itself is idempotent and the retry becomes a no-op update — and partitioned the consumer by a hash of externalId so the same key is always handled by the same worker in order. Errors went from eleven a night to zero over eight weeks, and, unexpectedly, the batch got 20% faster because we stopped doing duplicated work.

What I would do differently: I would have taken the “transient” triage seriously the first time. An error that only ever appears in one time window is not transient, it is periodic, and periodic means there is a caller you have not thought about. I also wasted a day on a theory involving clock skew because 3am felt like a time-related bug — the timestamp was a clue about a batch job, not about time.

What the interviewer is really probing. Debugging method under uncertainty: how you form and kill hypotheses, and whether you can reproduce a concurrency bug rather than reason about it. They also want to hear that you know upsert is not atomic against the index, which is a genuinely discriminating piece of MongoDB knowledge.

The mistake candidates make. A war story with no method — “I stared at it and eventually noticed”. Say which hypotheses you disproved and how, including the wrong one you spent a day on; a disproved hypothesis is stronger evidence of rigour than a lucky correct one.

(d) Follow-up drill chain

Why is an upsert not atomic in the way people assume?

Because it is a two-phase operation at the storage layer: match, and if no match, insert. Each phase is atomic, the pair is not, so two concurrent upserts for a key that does not yet exist can both reach the insert. The unique index is what saves you — it turns a would-be duplicate document into a duplicate-key error, which is why the documented guidance is to always have one on the upsert filter's fields and to retry on error 11000. Without the unique index the same race silently produces two documents, which is a far worse failure because nothing tells you.

Would a transaction have fixed it?

No, and this is a useful thing to be able to say cleanly. Snapshot isolation does not prevent two transactions from both observing the absence of a document and both inserting; there are no gap or predicate locks, so the second commit still hits the unique index and aborts. You would have converted a duplicate-key error into a write-conflict error and added a transaction's cost for nothing. Uniqueness in MongoDB is enforced by the unique index, full stop, and the application's job is to handle losing that race gracefully.

At what scale does retry-on-duplicate stop being enough?

When the contention is sustained rather than incidental. A retry is fine when collisions are rare, because the second attempt takes the matched-update path and succeeds. If a large fraction of writes collide — a replay of the whole day's events with high parallelism, say — you burn a round trip per collision and, worse, you can build a herd where retries collide with each other. That is why we did not stop at the retry: the deterministic _id makes the operation idempotent by construction, and hash-partitioning the consumer removes the concurrency for a given key entirely. Retry is a mitigation; ordering and determinism are the fix.

What did you trade away with a deterministic _id?

Two real things. ObjectIds are roughly monotonically increasing, which gives you insertion locality in the B-tree and a free creation timestamp; a hash-derived id is random, so inserts scatter across the index and you lose the timestamp, which we had to add as an explicit field. On a sharded cluster the randomness is actually an advantage — it spreads writes — but on a single replica set it costs you some index locality and a slightly larger working set for the _id index. I would make the same call again for anything ingesting from an external system, because idempotency by construction is worth more than index locality.

How would you have caught this in testing?

A concurrency test that is part of the suite, not a load test someone runs before a release. Ours now spins up a real single-node replica set in a container, fires the same key from sixteen tasks simultaneously, and asserts exactly one document and zero unhandled errors. It runs in about four seconds. The general principle: any code path whose correctness depends on “this will not happen twice at once” deserves a test that makes it happen twice at once, because staging traffic will never do it for you.

What would you do differently now?

Change how the error was labelled, not just the code. It was categorised as transient because it self-recovered, and that label removed it from anyone's field of view for four months. I would now hold the line that an error class is only "transient" if we can explain the mechanism that makes it transient — an unexplained self-recovering error is an unknown bug with a friendly name. That reframing has caught two other things since, which is a better return than the fix itself.

07The shard key we could not take back

tier · staff → principal archetype · scaling challenge

EXAMPLE — replace with your own

We sharded a 6 TB telemetry collection on { createdAt: 1 }. On paper it was defensible — every query was a time range, so a ranged key gave us perfect targeting. In practice it produced the textbook failure: because time is monotonically increasing, every insert went to whichever shard owned the top range, so one of our six shards took 100% of the write load while the other five idled. Write throughput plateaued at about 9,000 documents per second no matter how many shards we added, the hot shard's CPU sat at 90%, and the balancer spent its life migrating ranges away from the hot shard only for the next range to land there too.

There are three properties a shard key needs and this key had one of them. Cardinality: enough distinct values to make many chunks — timestamps have that. Frequency: no single value dominating — timestamps have that too. Monotonicity: values must not increase or decrease steadily, because that concentrates every new insert in one range — and this is where a timestamp, or an ObjectId, or an auto-increment id, fails absolutely. The fourth practical property is that most queries should include the key, otherwise every read becomes a scatter-gather across all shards.

The old answer to this was a hashed shard key, which spreads writes perfectly and destroys range targeting — every time-range query becomes a broadcast. I did not want to trade one pathology for another. What we did instead was a compound key of { tenantId: 1, createdAt: 1 }: tenant gives us thousands of distinct prefixes so writes land across all shards, and time as the second component keeps range queries within a tenant targeted to a small number of chunks. That works because our queries always carried a tenant, which is the constraint that made the design possible — without it I would have chosen hashed and accepted the scatter.

The part that made this a story rather than a design note is that we did it live. Before 5.0 changing a shard key meant dumping and reloading; reshardCollection made it an online operation, and on 8.0 it is substantially better — it copies the collection into the new distribution in the background and cuts over with a brief write block at the end. Ours ran for 31 hours on 6 TB and the cutover blocked writes for about 4 seconds. I would still not describe it as routine: it needs free disk space for a second copy of the collection on each shard, it saturates the network between shards, and you must be prepared to abort.

// The symptom, in one command
sh.status();                                   // chunk counts wildly skewed toward one shard
db.telemetry.getShardDistribution();           // 94% of recent docs on shard rs2

// The online fix (5.0+; markedly faster and safer on 8.0)
db.adminCommand({
  reshardCollection: "app.telemetry",
  key: { tenantId: 1, createdAt: 1 },
  numInitialChunks: 512
});
db.adminCommand({ currentOp: 1, "command.reshardCollection": { $exists: true } });  // progress

// 8.0 also added the two commands that make "wrong topology" recoverable at all:
db.adminCommand({ moveCollection: "app.lookups", toShard: "rs1" });   // unsharded coll to a chosen shard
db.adminCommand({ unshardCollection: "app.smallref" });               // collapse a wrongly-sharded coll

Results: writes spread to within 8% of even across six shards, sustained ingest 9,000 → 54,000 docs/sec on the same hardware, and p99 on the tenant-scoped range query improved from 340ms to 90ms because the queries were now targeted to one or two shards instead of contending with the write hotspot. The balancer went quiet, which was its own kind of relief.

What I would do differently: I would not have sharded when we did. Looking back at the data, the collection was 900 GB when we sharded it and a single replica set with more RAM would have carried it for another eighteen months, during which we would have learned the access patterns properly. Sharding early cost us a wrong key, an operational tier we were not ready for, and a year of complexity. My rule now is that sharding is the last scaling move, not an early one, and that the question to answer first is “what will every query carry?” rather than “what is unique?”.

(d) Follow-up drill chain

Why does a monotonic shard key create a hotspot even with a balancer?

Because the balancer moves ranges after the fact, and inserts always target the range containing the current maximum. Whichever shard owns the top range receives every insert; the balancer notices the imbalance, splits and migrates ranges away, and the shard that keeps the top range — often the same one — keeps receiving everything. You are paying migration cost continuously to chase a hotspot you re-create every second. Since 6.0 the balancer works on data size rather than chunk count, which makes it smarter about the aftermath but does nothing about the cause.

How do you choose between a compound key and a hashed one?

By asking what every query carries. If there is a field present in essentially all reads with high cardinality and reasonable distribution — a tenant, a customer, a device — a compound key led by it gives you both spread and targeting, which is strictly better. If no such field exists, or the leading field is badly skewed so one value would create a jumbo range that cannot be split, hashed is the honest choice and you accept scatter-gather reads, budgeting for a mongos that fans out to every shard and merges. A hashed key on a field you also range-query is the worst of both worlds, and I have seen that shipped more than once.

At what scale does a compound tenant key break?

When tenant sizes become extremely skewed. If one customer is 40% of your data, its ranges cannot be split below the granularity of the key's second component, and you get a jumbo range that the balancer cannot move — the classic “one shard is full and nothing helps” state. Mitigations are to add a third component with more entropy, to hash the tenant prefix, or to move the whale tenant to its own shard with zone sharding. The lesson is that shard-key quality is a property of your data distribution, not of the key, so it can degrade over time as your customer mix changes — which is why I now review distribution quarterly rather than treating the choice as done.

What did resharding cost you, honestly?

Disk, network, and nerve. You need room for a full second copy of the collection distributed across the shards while it runs, which for us meant temporarily adding storage we then paid for until the next hardware cycle. Inter-shard network was saturated for 31 hours, which slowed unrelated cross-shard queries measurably. And the operation holds a critical section at the end that blocks writes — four seconds for us, but it scales with how far behind the new distribution has fallen, so a heavy write workload lengthens it. I ran it starting on a Friday evening with an explicit abort criterion and a named decision-maker, because a 31-hour operation will cross a shift boundary and you do not want that decision made ad hoc at 4am.

How did you get the organisation to accept a 31-hour risky operation?

By making the alternative concrete. I showed the throughput ceiling as a graph against the forecast ingest curve, with the date we would start dropping data, and then presented two options with costs: reshard now with a rehearsed plan, or keep buying hardware for a shard that could not use it. Then I removed the fear from the risky option by rehearsing it end to end on a restored copy of production and reporting the actual numbers — including the four-second write block — before asking for approval. Executives do not reject risk, they reject unquantified risk.

What would you do differently now?

Delay sharding and instrument the decision. I would have written down, at 900 GB, the specific signals that would mean “shard now” — working set exceeding RAM, write throughput within 30% of a measured single-node ceiling, restore time exceeding the RTO — and kept scaling vertically until one tripped. And when the day came I would have chosen the key from the profiler's actual query shapes rather than from the data model, because the model told me time was the axis and the traffic told me tenant was.

08Operator injection in a search endpoint

tier · senior → staff archetype · security issue found / fixed

EXAMPLE — replace with your own

I found it in a code review, not in an incident, which is the good version of this story and also the harder one to tell well. A colleague's pull request added a flexible filter to an internal reporting API: the client posted a JSON object and the service passed it, essentially unchanged, into find(). The intent was “let analysts filter by any field”. The effect was that anyone who could reach the endpoint could send {"password": {"$ne": null}} and enumerate accounts, or {"$where": "sleep(5000)"} and stall a server thread per request.

NoSQL operator injection is the mechanism, and it is worth being precise because it is not SQL injection with different syntax. There is no string concatenation and no parser to trick; the danger is that a query is a document, and if user input becomes part of that document then user input can introduce operators. Any JSON body deserialised into a filter object is a candidate, and the classic amplifier is a body parser that turns ?user[$ne]= in a query string into a nested object. $where and $function are the severe end because they execute server-side JavaScript, but $ne, $gt and $regex are enough for authentication bypass and data exfiltration on their own.

I did not block the pull request and write “injection risk”. I wrote a failing test. It posted {"role": {"$ne": "nobody"}} to the endpoint on a branch build and asserted that it returned 400; it returned 200 and 14,000 documents. That test made the conversation about a fact rather than about my judgment, and the author fixed it in a day. Then I widened it, because the same pattern was almost certainly elsewhere: a grep for places where a request body reached a query without construction found four, one of them on a public endpoint. That escalated into a proper security review with the team that owns our appsec practice — I did not run it alone, and saying so matters, because a lone engineer quietly fixing security bugs is a worse outcome than an organisation that learns.

// The vulnerable shape: a user-controlled document becomes a query
const filter = req.body.filter;            // {"password": {"$ne": null}}
const rows = await users.find(filter).toArray();

// Fix 1 — construct the query; never pass one through
const filter = {};
if (typeof req.body.email === "string") filter.email = req.body.email;   // type check kills {$ne:…}
if (Number.isInteger(req.body.minAge))  filter.age = { $gte: req.body.minAge };

// Fix 2 — defence in depth at the server: no server-side JS at all
// mongod.conf
security:
  javascriptEnabled: false          // disables $where, $function, $accumulator, mapReduce

// Fix 3 — least privilege, so a leak is bounded
db.createRole({ role: "reportReader", privileges: [
  { resource: { db: "app", collection: "orders" }, actions: ["find"] }], roles: [] });

The outcomes: four call sites fixed, server-side JavaScript disabled on every cluster (we had never used it), a lint rule that fails a build when a request object reaches a driver call without passing through a validator, and a schema-validated allow-list for the reporting filter so analysts kept their flexibility. We also rotated the service credential that had far more privilege than the endpoint needed, because the exposure had been read access to every collection in the database rather than to the two it queried.

What I would do differently: I framed it as “a bug in your pull request” for the first hour, which put the author on the defensive and cost us both time. The right frame — the one I use now — is that the pull request revealed a gap in our defaults, because a framework that lets a request body become a query is a system problem and not a review-vigilance problem. I would also have gone looking for the other four call sites before, not after, the fix, so that we sized the exposure first and reported it accurately.

What the interviewer is really probing. Whether you handle a security finding proportionately and without theatre: sizing the exposure, involving the right people, fixing the class rather than the instance. Technically they want to hear that you can explain operator injection precisely, and that you know defence in depth here means input construction, disabled server-side JavaScript, and least-privilege roles — not one clever sanitiser.

The mistake candidates make. Making the colleague the villain, or making yourself the hero who single-handedly saved the company. Also: describing the fix as “I sanitised the input”, which for document databases is the weakest of the available controls. The strong answer names the systemic change.

(d) Follow-up drill chain

Why is parameterisation not the answer here, the way it is in SQL?

Because there is no query string to parameterise. A MongoDB query is already a structured document sent over the wire as BSON, so the driver is not concatenating anything and there is nothing to escape — the injection happens a layer earlier, when your application decides to let untrusted data be part of that structure. The correct control is therefore construction and type validation: build the filter field by field from values you have checked, and never let a deserialised body become a filter. Anyone who answers this with “use parameterised queries” has learned the SQL lesson without understanding the mechanism.

What can an attacker actually achieve with only $ne and $regex?

Authentication bypass, if a login lookup takes a document — { user: "admin", pass: { $ne: "" } } matches. Blind data extraction, by binary-searching a value with anchored regexes one character at a time and observing whether the response is empty. And denial of service, because a pathological regex or an unindexed predicate turns a cheap endpoint into a full collection scan; an attacker who can force a COLLSCAN on a large collection has a very effective amplification attack without needing any data back at all. $where is worse — arbitrary server-side JavaScript — which is exactly why disabling javascriptEnabled is a cheap, high-value control if you do not use it.

What else would you check on a cluster you inherited?

In order of return: authentication actually enabled and not bound to a public interface — the historical mass-exposure incidents were unauthenticated instances on default ports; TLS for client and intra-cluster traffic; roles scoped per service rather than a shared readWrite on every database; audit logging on for privileged actions; encryption at rest; and then the application-layer questions, including whether anything sensitive should be under Queryable Encryption, which since 8.0 supports range queries in production and since 8.2 has prefix, suffix and substring query types in public preview. The order matters — exotic controls on an unauthenticated cluster are decoration.

How did you decide how loudly to escalate?

By exposure, not by severity in the abstract. Three of the four call sites were behind internal authentication with a small, audited user set, which made them important but not urgent; one was reachable from a partner network, which made it a same-day fix with a notification to the security team and a check of access logs for prior exploitation. I write the exposure sentence first — who can reach this, with what credential, and what would they get — because that sentence, not the CVSS score, is what decides whether you wake someone up. Over-escalating burns credibility you will need for the next finding.

How do you keep this from reappearing when the team turns over?

Mechanism plus a small amount of story. The mechanism is the lint rule, the disabled JavaScript, the validator in the shared library, and a test in the security suite that fires operator payloads at every endpoint in CI. The story is a fifteen-minute internal write-up with the actual payload and the actual response, which is what people remember and what makes the lint rule feel reasonable rather than bureaucratic. Controls with no explanation get disabled by the next person under deadline pressure.

What would you do differently now?

Build the safe path before banning the unsafe one. What the analysts wanted — flexible filtering — was legitimate, and my first fix took it away. The version that stuck came a week later: a declarative allow-list of filterable fields with types and permitted operators per field, generated from the same schema we use for validation. If I had led with that, the whole thing would have been a one-day improvement rather than a three-day negotiation about a capability I had removed.

09Sixty indexes, eleven of them used

tier · senior → staff archetype · tech-debt paydown / refactor

EXAMPLE — replace with your own

The trigger was a write-latency complaint, not a tidiness urge. Inserts into our main customers collection had crept from 2ms to 19ms over about two years with no change in document size or hardware. When I listed the indexes there were 61 of them on one collection, totalling 140 GB against 210 GB of data — so more than a third of our cache was being spent on index pages, and every insert was writing 61 index entries.

That is the mechanism, and it is the whole reason this is worth doing. An index is not free storage that helps reads; it is a write amplifier. Every insert writes one entry per index, every update writes entries for every index covering a changed field, and every one of those pages competes for the same WiredTiger cache as your documents. A multikey index on an array of ten elements writes ten keys. So the cost of an unused index is paid on every write, forever, and it is invisible on the read path where people look.

$indexStats settled it in one query: 11 indexes had been used in the 90 days since the last restart, 3 more were used by monthly reports, and 47 had zero accesses. But I did not drop 47 indexes, and the discipline there is the actual story. $indexStats counters reset on restart and are per-node, so a low count can mean “used only by a report that runs on the first of the month” or “this node is a secondary that never serves that query”. I collected stats from every member over a full quarter, cross-checked against the slow-query log's index usage, and then used hidden indexes — available since 4.4 — to make each candidate invisible to the planner without dropping it. If something broke, unhiding is instant; dropping and rebuilding a 6 GB index on a large collection is not.

// What is actually used, across every member, over a long enough window
db.customers.aggregate([{ $indexStats: {} }, { $project: { name: 1, ops: "$accesses.ops", since: "$accesses.since" } },
                        { $sort: { ops: 1 } }]);

// Retire safely: hide first (4.4+), watch, then drop
db.customers.hideIndex("email_1_status_1_createdAt_-1");
// … two weeks, no regressions, no complaints …
db.customers.dropIndex("email_1_status_1_createdAt_-1");

// The redundancy that mattered most: a prefix of an existing compound index
// { tenantId: 1 }                          <- redundant
// { tenantId: 1, status: 1 }               <- redundant
// { tenantId: 1, status: 1, createdAt: -1 } <- keep; serves all three

The single biggest win was not exotic: fourteen of the indexes were strict prefixes of other indexes. A compound index on {a, b, c} already serves queries on {a} and {a, b}, so the standalone indexes on those prefixes were pure cost. Explaining that rule to the team took ten minutes and prevented more future debt than the cleanup removed.

Final numbers: 61 indexes down to 19, index storage 140 GB → 38 GB, insert p99 19ms → 3ms, cache hit ratio up from 91% to 99.4% because documents finally had room, and — the one nobody predicted — nightly backup time fell by 40 minutes. We deliberately stopped at 19 rather than pushing to a theoretical minimum: the last four were each defended by one team with a real quarterly report, and the return on removing them was smaller than the risk of the argument.

The debt accumulated because anyone could add an index in a migration script and nobody ever removed one — the incentives were entirely one-directional. The lasting fix was a rule that a new index needs a named query shape and an owner, plus a quarterly $indexStats report that goes to the owning teams, not to me.

(d) Follow-up drill chain

Why does an unused index cost anything if nobody queries it?

Because it is maintained on every write regardless of reads. An insert writes a key into every index on the collection; an update writes keys for every index whose fields changed, and for a moved value that means a delete plus an insert in the B-tree. Those pages are dirtied, must be evicted and checkpointed, and they occupy WiredTiger cache that would otherwise hold documents — so an unused index steals read performance from the queries that are running. It also lengthens initial sync, index builds after a restore, and backup size. The read side is where indexes are discussed and the write side is where they are paid for.

How reliable is $indexStats, really?

Reliable about what it counts, misleading about what you infer. The counters are per-mongod and reset on restart, so a rolling restart wipes your evidence; a secondary only shows usage for queries routed to it, so an index used exclusively by an analytics read preference looks dead on the primary. It also counts plan selection, so an index the planner evaluated and rejected can register accesses. That is why the safe procedure is: collect from every member, over a window longer than your longest business cycle, cross-check against the slow-query log, and then hide rather than drop. Anyone who drops indexes straight off a single node's $indexStats will eventually take out a month-end report.

What is the risk in building the index back if you are wrong?

Time and cache disruption, not correctness. Since 4.2 index builds are hybrid — they run simultaneously on primary and secondaries and only hold an exclusive lock briefly at the start and end — so the old foreground/background distinction is gone and the background option is a no-op. But a build on a large collection reads the whole collection, which evicts your working set and can take hours, and on a sharded cluster it runs per shard. For very large collections I still prefer a rolling build: take one secondary out of the set, build it standalone, put it back, repeat, then step down and do the old primary. That is why hiding is the right first move — it is instant in both directions.

When is an index that looks redundant actually not?

Three cases worth naming. Sort direction: {a: 1, b: 1} and {a: 1, b: -1} are not interchangeable when you need a compound sort, although a single-field sort can be walked backwards. Partial and sparse variants: an index with a partialFilterExpression is far smaller and may be chosen where the full one would not be, so the "duplicate" is genuinely doing different work. And collation: an index built with a case-insensitive collation only serves queries using that same collation, so it can look identical to a default-collation index and be useless for it. I check those three before calling anything redundant.

How did you convince the teams that owned the indexes?

I sent them their own data. Each team got a list of the indexes attributable to their collections, with usage counts, storage size and the write cost expressed as milliseconds added to their own insert path — their metric, not mine. Then I offered the hide-and-wait procedure with an explicit promise: unhiding takes ten seconds and I will do it without argument if anything regresses. Nobody objected to a reversible change backed by their own numbers, and one team found a report they had forgotten they owned, which was worth the exercise on its own.

What would you do differently now?

Attack the inflow rather than the stock. A quarterly cleanup is a treadmill; the durable change was requiring every new index to arrive with the query shape it serves and a named owner, checked in beside the migration, and a CI check that fails when a new index is a prefix of an existing one. I would also set a budget — index storage as a percentage of data size, alerted at a threshold — because a number with a limit gets managed and a number without one only gets cleaned up after it causes an incident.

(d) Follow-up drill chain

Why is stage order the first thing you teach?

Because the pipeline is a stream and every stage pays for every document it receives. A $match at the front can be pushed into an index scan, so the pipeline may only ever touch a few thousand documents; the same $match after a $group means you grouped the entire collection first and then threw most of it away. The optimiser does reorder some stages — it will move a $match ahead of a $project when it can prove the fields are untouched — but it cannot see through $group, $unwind with computed fields, or most $lookups, so relying on it is a coin flip. Teaching order teaches the execution model, which is what lets someone reason about a pipeline they have never seen.

What are the memory limits, and what changed?

Each blocking stage — $group, $sort, $bucket, $setWindowFields — has a 100 MB in-memory limit. Historically exceeding it was an error unless you passed allowDiskUse: true; since 6.0 the server parameter allowDiskUseByDefault is on, so pipelines spill to temporary files instead of failing. That is friendlier and genuinely worse to operate, because a query that used to fail loudly now succeeds slowly and quietly, consuming disk and IO. I tell teams to treat a spilling stage as a bug: it means the $match is not selective enough or the index is missing, and the fix is upstream of the stage that spilled.

When would you still not use the aggregation framework?

When the work is genuinely analytical rather than operational. A pipeline that scans a large fraction of a collection is competing for the same cache and the same ticket pool as your transactional traffic, so a heavy report on a primary is a self-inflicted incident. Then the answer is a secondary with an analytics tag, a dedicated node, or an offline copy — the framework is fine, the placement is the problem. I also avoid it for anything needing multi-pass logic that is naturally imperative, and for very large $lookup fan-outs, which are a nested loop join and behave like one.

What is the legacy pattern you will still meet, and what replaced it?

mapReduce, which has been deprecated since 5.0 and which you will still find in older codebases, usually for grouping. Its replacements are ordinary $group pipelines, with $accumulator and $function as the escape hatch for genuinely custom logic — and both of those run server-side JavaScript, which many hardened deployments disable, so I treat them as a smell rather than a migration target. The other legacy pattern is $out used as a poor man's materialised view; $merge, since 4.2, does incremental upserts into an existing collection and is almost always what people actually wanted.

How do you know your mentoring worked rather than just the code getting better?

By whether the next thing happened without me. The test I use is deliberate absence: after the second report I stopped attending their reviews for that area and watched what shipped. If the quality holds when you leave the room, you taught something; if it decays, you did the work with an audience. The second signal is whether they start disagreeing with you on the topic — the engineer who told me my proposed pipeline had an unnecessary $unwind was the moment I knew it had landed.

What would you do differently now?

Start with the blocker and start with one real problem. I would also write the loop down as a short internal guide — build incrementally with a $limit, check the explain for an IXSCAN in the first stage, watch for spilling — because that fits on a page and outlasts any session I run. And I would pick the report that hurt the team most rather than the one that demonstrated the most operators; motivation comes from relief, not from elegance.

(d) Follow-up drill chain

Why does a read-heavy report hurt a write-heavy primary so much?

Two shared resources. The WiredTiger cache is one pool: a scan pulls cold pages in and evicts the hot working set, so after the report finishes your ordinary queries are reading from disk until the cache re-warms — that was our eleven minutes. And concurrency tickets, exposed since 8.0 as queues.execution, are a bounded pool of slots for storage-engine operations; long-running reads hold them, so writes queue behind work that has nothing to do with them. The report does not need to be slow to be damaging; it needs to touch a lot of pages.

What are the real risks of reading from a secondary?

Staleness and the illusion of safety. A secondary is behind by the replication lag, so read-your-own-writes breaks — a user saves and immediately sees the old value — unless you use a causally consistent session or route that particular read to the primary. Lag is also not bounded: a secondary doing an index build or catching up after a network event can be minutes behind, so any UI on secondary reads needs to show data age rather than pretend it is live. And a secondary that is also a voting member is doing failover duty, so hammering it has availability consequences; that is why I set priority: 0 and votes: 0 on the analytics member.

At what point would you move reporting off the operational cluster entirely?

When the reporting workload stops being shaped like the operational one. The signals: queries that need different indexes than the application does, retention requirements that differ, joins across collections that the document model deliberately separates, or a user population whose questions change weekly. At that point every extra index you add for reporting taxes the write path, and you are contorting an operational schema to serve analysis. That is the moment for a real pipeline into a columnar store — and I would rather make that call early with a small dataset than after the tenth index nobody can remove.

What did you trade away by choosing option C?

Completeness, and some goodwill in the short term. Eight reports did not exist on day one and the operations lead was not thrilled, so I owed her a date and a mechanism for the deferred set, which I put in writing with the analytics roadmap item attached. We also took on staleness the UI had to communicate, which is a small permanent tax on every screen. In exchange we kept the write path's latency guarantee, which was in the contract, and we did not procure hardware under time pressure — a decision that ages well, because rushed capacity decisions tend to be permanent.

By closing the loop rather than moving on. I gave the operations lead the deferred list with owners and a date, invited her to the analytics design review, and — the part that actually mattered — went back at four months and asked which of the eight she still wanted. Three had become unnecessary, which I reported to her rather than to my own management, because the point was to demonstrate that deferral had not meant abandonment. She raised the next requirement six months early instead of six weeks late, which is the only real measure of whether that repair worked.

What would you do differently now?

Ask the reporting question at design time, always. Beyond that, I would build the measurement harness earlier: the reason I could reframe the conversation in ten minutes was a restored production-sized environment with a replayable write workload, and we only had one because of an unrelated project. Now I treat that as standard equipment — being able to answer "what would this cost us?" with a number, within a day, is the single highest-leverage tool in these negotiations.

12The updateMany that lost its filter

tier · senior → staff archetype · data-loss / corruption scare

EXAMPLE — replace with your own

A backfill script was meant to set region: "EU" on customers created before a cutover date. The filter was built from a variable that, in the production configuration, was undefined — so the filter serialised to {} and the script set region: "EU" on all 2.3 million customer documents, including the 1.1 million that were not in the EU. It ran in eleven seconds. Nobody noticed for forty minutes, until a support agent asked why a customer in Singapore was seeing EU pricing.

The recovery is the technical content and it is worth knowing cold. We had continuous backups with point-in-time restore, and the naive move — restore the cluster to 14:22 — would have thrown away forty minutes of real orders. So we did a partial restore: restore a snapshot plus oplog replay to just before the script into a separate cluster, then reconcile. The reconciliation was possible because of one lucky property: the script had only touched one field, and the pre-image of that field was recoverable. We exported _id and region from the restored copy for the 1.1 million wrongly-updated documents and replayed them as targeted updates against production, filtered to documents whose updatedAt matched the damage window.

Two mechanisms are worth naming. First, the oplog is an idempotent, ordered record of every change; point-in-time restore is a snapshot plus oplog replay to a chosen timestamp, so your recovery granularity is bounded by your oplog window — ours was nineteen hours, which was the reason this was recoverable at all. Second, the update itself was replicated as 2.3 million individual oplog entries, so the oplog contained an exact list of the affected _ids, which is how we scoped the repair precisely instead of guessing.

// What ran (the bug: an undefined variable collapses the filter to {})
db.customers.updateMany(
  { createdAt: { $lt: cutoff } },   // cutoff was undefined -> field dropped -> {}
  { $set: { region: "EU", updatedAt: new Date() } }
);

// The guard we adopted afterwards, in every maintenance script
function assertScoped(filter, coll, maxFraction = 0.25) {
  if (!filter || Object.keys(filter).length === 0) throw new Error("refusing an empty filter");
  const n = coll.countDocuments(filter), total = coll.estimatedDocumentCount();
  if (n / total > maxFraction) throw new Error(`filter matches ${n}/${total} — refusing`);
  return n;
}

// And the dry run that is now mandatory
const n = assertScoped(filter, db.customers);
print(`would update ${n}`); print(db.customers.find(filter).limit(5).toArray());
if (!process.env.CONFIRM) quit();

Timeline: damage at 14:22, noticed 15:02, incident declared 15:05, writes to the affected field paused via a feature flag at 15:11, restore cluster ready 16:40, reconciliation complete 17:20, verified 17:50. Three hours from detection, with wrong pricing shown to roughly 4,000 customers in that window and eleven orders that had to be corrected manually and credited.

The follow-ups were where the real work happened, and none of them were about the person who ran the script. Maintenance scripts now go through a helper that refuses an empty filter and refuses to touch more than a quarter of a collection without an explicit override; they run first against a restored copy with the output diffed; the production role used for backfills no longer has updateMany on customer collections without a change ticket; and we run a restore rehearsal quarterly with a stopwatch, because our 78-minute restore was slower than anyone had assumed.

What I would do differently: two things. I would have paused writes sooner — we spent nine minutes confirming the scope before stopping the bleeding, and every one of those minutes made reconciliation harder. And I would not have let a script with an unbounded write run under a role that permitted it; the strongest control here is not carefulness, it is that the credential should not have been able to do this.

What the interviewer is really probing. Whether you own a failure without either minimising it or performing contrition, and whether your recovery was reasoned rather than lucky. The mistake candidates make. Minimising — “only a subset of documents, and we fixed it quickly”. If customers saw wrong data, lead with that in human terms and then give the number. (d) Follow-up drill chain

Why restore into a separate cluster rather than roll production back?

Because a rollback discards every legitimate write since the damage, and forty minutes of a live order system is real money and real customer trust. Restoring aside turns an all-or-nothing decision into a data problem: you now have a known-good copy to diff against, you can compute exactly which documents to repair, and you can leave everything else untouched. It is slower and it needs capacity, which is why the restore rehearsal matters — if you do not know your restore takes 78 minutes, you cannot make this choice under pressure. A rollback in place is the right answer only when the damage is total or the window is empty.

What determines whether this kind of damage is recoverable at all?

The oplog window, principally. Point-in-time restore is a snapshot plus oplog replay, so you can only rewind to a moment covered by retained oplog; if the window is six hours and you notice after eight, you are restoring to a snapshot and losing everything since. Two things shrink the window silently: high write volume (which is why story 02's oversized documents mattered — cutting oplog throughput 71% doubled our window) and a large bulk operation like this one, which can flood the oplog and evict the history you would need. The second factor is whether the change is invertible: a field overwrite loses its pre-image unless you have it somewhere, and a delete loses everything. That is why change stream pre-images, available since 6.0, are worth enabling on collections whose history you might need.

Could a transaction have prevented it?

No — and this distinction is worth being crisp about. The operation was not partially applied; it was fully, atomically, correctly applied to the wrong set of documents. Transactions protect against partial application, not against a wrong predicate. The controls that would have prevented it are all outside the database's consistency model: input validation in the script, a dry-run diff, a cap on affected document count, and a credential that lacks the privilege. People reach for transactions when they mean "safety", and being able to say precisely which kind of safety a transaction provides is a good differentiator.

At what point would this have become unrecoverable?

Past the oplog window, or if the script had done something non-invertible at scale — deleted documents, or overwritten a field we had no other copy of and no pre-images for. It would also have been effectively unrecoverable if the affected set had been unidentifiable: we could scope the repair because the update stamped updatedAt and because the oplog listed the ids. A script that modified documents without leaving a marker, in a collection with heavy legitimate concurrent writes, would have left us unable to distinguish our damage from real changes — which is why "always stamp what you touched" is now in our script template.

How did you handle the engineer who ran it?

He was in the room for the whole recovery, which was right, and he wrote the guard function afterwards, which was better. I said once, publicly and early, that the script had done exactly what our tooling permitted it to do and that the tooling was mine to fix — because in a blameful review the useful details stop arriving. In the write-up we named actions, not people. The one thing I would not do is pretend there was nothing to learn personally: he and I went through the config-loading bug together privately, which is a different conversation from the incident review and belongs in a different room.

What would you do differently now?

Make the dangerous operation structurally hard rather than culturally discouraged. Concretely: bulk writes against customer-facing collections go through a job runner that requires a ticket, prints a diff from a dry run against a restored copy, and enforces the affected-count cap — a human cannot express this mistake in that interface. And I would run the restore rehearsal on a schedule with a stopwatch and a published number, because the 78 minutes we discovered under pressure should have been a known figure with an owner and a target.

13A schema that changed every sprint

tier · senior → staff archetype · ambiguous / shifting requirements

EXAMPLE — replace with your own

We were building a product-catalogue service for a business that genuinely did not know what a product was yet. In four months the shape changed eleven times: attributes became a nested object, then a list, then a list with per-locale variants; pricing gained tiers, then contracts, then a validity window. Half the team wanted to freeze the schema and make the business commit; the other half wanted no schema at all, because “that is the point of MongoDB”. Both positions were wrong in the same way — they treated schema flexibility as a binary rather than as a dial you set per field.

The position I argued for, and the one that held up, was flexible where the business is still thinking, rigid where the system depends on it. Concretely: _id, sku, tenantId, schemaVersion, status and updatedAt were enforced by a JSON Schema validator and could not be violated; everything under attributes was unvalidated and free to churn. That distinction is enforceable because MongoDB's $jsonSchema validation lets you require some properties without forbidding others, and because validationLevel: "moderate" applies the rules to inserts and to updates of already-valid documents while leaving legacy documents alone — which is what makes it adoptable on a collection that already has data.

The second half was the document versioning pattern: every document carries a schemaVersion, readers migrate on read, and a background job migrates lazily. That decoupled the deploy from the data. We never ran a big-bang migration in those four months; we shipped a reader that understood versions 3 and 4, then wrote version 4, then let the backfill catch up over days, then dropped the version 3 reader a sprint later once a count confirmed zero remaining.

// Rigid where it matters, open where it does not
db.createCollection("products", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["sku", "tenantId", "schemaVersion", "status", "updatedAt"],
    properties: {
      sku:           { bsonType: "string", pattern: "^[A-Z0-9-]{4,32}$" },
      tenantId:      { bsonType: "objectId" },
      schemaVersion: { bsonType: "int", minimum: 3 },
      status:        { enum: ["draft", "active", "retired"] },
      updatedAt:     { bsonType: "date" }
      // 'attributes' intentionally unlisted: free to change every sprint
    }
  }},
  validationLevel: "moderate",   // don't reject updates to pre-existing invalid docs
  validationAction: "error"
});

// Migrate on read, backfill in the background — never a big-bang migration
function toV4(doc) {
  if (doc.schemaVersion >= 4) return doc;
  return { ...doc, schemaVersion: 4,
           attributes: Object.entries(doc.attrs ?? {}).map(([k, v]) => ({ key: k, value: v })) };
}
// backfill, resumable, throttled

(d) Follow-up drill chain

If MongoDB is schemaless, why add a validator at all?

Because the schema exists regardless — it is just distributed across every piece of code that reads the data. A validator moves the parts that everyone depends on into one enforceable place, so a bug that would have produced a malformed document six months from now fails at write time instead. I validate exactly the fields that other systems, indexes or invariants depend on. What I do not do is mirror an application model into the database, because then every model change is a database change and you have bought all of the cost of a rigid schema with none of the benefit of a real one.

What do validationLevel and validationAction actually control?

validationLevel decides which documents are checked: strict checks every insert and update, moderate checks inserts and updates to documents that already satisfy the rules — so pre-existing invalid documents can still be updated — and off disables it. validationAction decides what happens on failure: error rejects the write, warn logs it and allows it. The combination that makes validation adoptable on a live collection is moderate plus warn first: you find out what would break without breaking it, fix the writers, then tighten to error. Going straight to strict + error on a collection with history is how people conclude that validation is unusable.

At what scale does migrate-on-read stop being viable?

It scales fine on the read path — the transformation is cheap and per-document — but it stops being viable organisationally. Every un-retired version is a branch in the reader, and the complexity is multiplicative across versions and services; three live versions across six consumers is eighteen combinations nobody tests. My rule is at most two live versions, with a named owner for retiring the older one and a dashboard showing the remaining count, so retirement is a task with a finish line rather than an aspiration. The other limit is indexing: if the shape change moves a field you index on, reads of old documents cannot use the new index, so the backfill stops being lazy and becomes urgent.

How do you run the backfill without hurting production?

Batched, resumable, throttled and observable. Batches of a few hundred to a few thousand by _id range so it is resumable from a stored cursor position rather than restarting; a sleep between batches tuned so replication lag stays under a threshold, which is the metric I actually watch because it is the first thing bulk writes damage; and a kill switch. I run it against a restored copy first to measure duration and oplog impact. And it writes progress to the same dashboard as the version counts, because a backfill nobody can see the progress of is a backfill that silently stops.

How did you handle the two camps on the team?

I refused the binary and gave both sides what they actually needed. The freeze camp wanted to stop being broken by surprises, so they got enforceable guarantees on the fields their code depended on. The flexibility camp wanted to ship without a migration project every sprint, so they got an unvalidated extension area and a lazy migration path. Framing it as "which fields do you need a promise about?" turned a philosophical argument into a list, and a list can be agreed in an afternoon. I have since found that most architecture disputes have this shape: the disagreement is about scope, and both sides are arguing as though it were about principle.

What would you do differently now?

schemaVersion from the first commit, and validation in warn mode from the first commit too — so that by the time anyone wants enforcement, you already know exactly what would break. I would also write down the boundary explicitly: a short document saying which fields are contract and which are open, reviewed when it moves. Ours was implicit for two months and drifted, with computed fields creeping into the open area where nothing protected them, and untangling that cost more than writing the page would have.

14Change streams as an integration contract

EXAMPLE — replace with your own

Another team needed to know when our orders changed. Their first proposal was to read our database directly with their own connection string — the classic shared-database integration, which couples two release cycles together forever. Their second proposal, after we said no, was that we publish events to a message broker on every write, which we agreed to in principle and then discovered was harder than it sounded: our service wrote to MongoDB and then published, and any crash between those two steps lost an event. We measured it, and over a month we had lost 41 events out of about 9 million — small, and completely unacceptable for a downstream system doing financial reconciliation.

The dual-write problem is the mechanism here and it is a genuinely good thing to be able to explain. Two systems, no shared transaction, so any ordering you choose has a failure window: write-then-publish loses events on a crash, publish-then-write emits events for writes that never happened. The two standard resolutions are the outbox pattern — write the event into the same document or the same transaction as the state change, then have a separate process publish from that record — and change data capture, which in MongoDB means change streams reading the oplog. We chose change streams, because the oplog already is a durable, ordered, exactly-once-per-change record of everything that happened, and building an outbox would have been re-implementing it.

What made this a cross-team story rather than a technical note is that the hard part was the contract, not the code. A change stream event exposes our raw document shape, so publishing it directly would have recreated the coupling we had just refused — their code would break when we renamed a field. So the publisher we built is a translation layer we own: it consumes the change stream, maps our internal documents to a versioned public event schema, and publishes that. Their team gets a contract; we keep the freedom to change our documents. I wrote that boundary down and both leads signed it, which sounds bureaucratic and saved us twice in the following year.

// Durable, resumable CDC: the resume token is the only state we persist
const pipeline = [
  { $match: { "ns.coll": "orders", operationType: { $in: ["insert", "update", "replace"] } } },
  { $project: { _id: 1, operationType: 1, fullDocument: 1, documentKey: 1, clusterTime: 1 } }
];
const stream = db.watch(pipeline, {
  resumeAfter: await loadToken(),                       // startAfter() to resume past an invalidate
  fullDocument: "updateLookup",                          // or "whenAvailable" with pre/post images (6.0+)
  fullDocumentBeforeChange: "whenAvailable",             // needs changeStreamPreAndPostImages enabled
  maxAwaitTimeMS: 1000
});
for await (const ev of stream) {
  await publish(toPublicEvent(ev));    // translation layer: our shape -> their contract
  await saveToken(ev._id);             // AFTER publishing: at-least-once, never at-most-once
}

Two operational details cost us a week each and are worth knowing before you meet them. First, the resume token is only usable while the corresponding oplog entry is still in the window — if the consumer is down longer than the oplog window, resumption fails and you need a reconciliation path, so we added a nightly diff by updatedAt that republishes anything missed. Second, an event carrying a large document can exceed the 16 MB BSON limit once fullDocument and pre-images are attached; $changeStreamSplitLargeEvent exists for exactly that, and we hit it before we knew it existed.

Results: zero lost events in the fourteen months since, measured by the reconciliation job; the downstream team decoupled from our schema entirely, and we renamed three fields in that period without telling them, which is the whole point. What I would do differently: I would have started with the contract document rather than the transport. We spent three weeks arguing about brokers and change streams before anyone wrote down what an order event actually means — and the transport turned out to be the easy half.

What the interviewer is really probing. How you handle a dependency you do not control: whether you can say no to a bad integration without becoming a blocker, and whether you understand delivery semantics. Technically they want the dual-write problem named and a real resolution, plus at-least-once versus exactly-once handled honestly.

The mistake candidates make. Describing the technology and skipping the negotiation, or telling it as “we told them no”. The staff-level content is that you refused the coupling and gave them something better within a timeframe they could plan around.

(d) Follow-up drill chain

Why are change streams more reliable than publishing from the application?

Because they read the oplog, which is written as part of the same replicated commit as the data change — so there is no window in which the state changed and the record of it does not exist. The stream also only surfaces majority-committed changes, so you never publish an event for a write that gets rolled back in a failover, which a naive application-side publisher absolutely will. And resumption is a first-class concept: the token identifies a position in the oplog, so a consumer restart continues rather than replaying from the beginning or skipping. You are consuming the database's own durable log instead of trying to keep a second log in step with it.

Do you get exactly-once delivery?

No, and anyone who claims otherwise is describing a system with an idempotent consumer. The stream delivers each change once, but the publish-then-save-token sequence means a crash between the two republishes the last event — so it is at-least-once, deliberately, because the alternative ordering loses events. The correctness therefore lives downstream: our public events carry the _id and the cluster time, and consumers deduplicate on that. I would rather have an honest at-least-once pipeline with an idempotent consumer than a fragile pipeline that claims exactly-once, because the first one degrades into duplicates and the second one degrades into silent loss.

At what scale or failure does this break?

Three ways. Oplog window: if a consumer is down longer than the window, its token is gone and it cannot resume — which is why the window is a capacity metric worth alerting on, and why we have a reconciliation path. Throughput: a single change stream cursor is one consumer, so beyond a certain event rate you need to shard consumption by namespace or by a hash of the document key, and ordering guarantees then only hold within a partition. And event size: fullDocument plus pre-images can push a change event past 16 MB on large documents, which needs $changeStreamSplitLargeEvent and a consumer that reassembles. On sharded clusters there is a fourth: events are merged from every shard through mongos, so ordering is by cluster time and cross-shard total ordering costs latency.

What did you trade away by owning the translation layer?

A permanent piece of software and a permanent on-call responsibility that exists purely for another team's benefit. That is a real cost and I would not pretend otherwise — it is roughly a quarter of an engineer's ongoing attention. What we bought is the ability to change our own documents freely, which over fourteen months we used repeatedly, and a single place to enforce redaction so we are not leaking internal fields into another team's system. If the downstream consumer had been one small team with a stable need, an outbox collection they polled might have been the cheaper honest answer.

How did you get the other team to accept a slower path than direct access?

By making the cost concrete for them, not for me. Direct access meant their code would break whenever we deployed, and they would find out in their own incident — I showed them two schema changes we had made in the previous quarter that would have broken them. Then I gave them a date and a draft event schema within a week, so "no" arrived attached to something they could start building against. The signed contract mattered because it made the boundary mutual: they committed to consuming only the public shape, and we committed to versioning it and to a deprecation notice period. Obligations in both directions are what make a boundary hold.

What would you do differently now?

Write the event contract on day one, in a shared repository, with an example payload and a version. Everything expensive that happened afterwards traced back to not having it: three weeks of transport debate, a field they depended on that we had not meant to expose, and a redaction rule we retrofitted. I would also build the reconciliation job at the same time as the pipeline rather than after the first gap — a CDC pipeline without an independent way to verify completeness is a pipeline you have to trust, and I would rather have one I can check.

15The active-active cluster we did not build

EXAMPLE — replace with your own

We had a mandate: “multi-region active-active, writes accepted in both Europe and North America, sub-100ms for everyone”. It came with a budget and a date, and I was the engineer who eventually recommended cancelling it. That recommendation is the story, and it is the kind interviewers value most because it requires having been publicly wrong about something you had spent months on.

The technical reality is not negotiable and it is worth stating precisely. A MongoDB replica set has exactly one primary; all writes go to it. You can place members in multiple regions, and you can use zone sharding to pin ranges of a sharded collection to a region so that writes for European customers land on shards whose primaries are in Europe — that is genuine multi-region write locality. What you cannot have is two primaries accepting writes to the same document, because that is multi-master with conflict resolution, and MongoDB deliberately does not do it. So “active-active” was achievable only in the sense of “each region actively serves its own data”, not “either region can write anything”.

The first three months were spent discovering that our data did not partition. We had modelled the requirement as regional customers, but the actual traffic was global accounts with users in both regions editing the same records — 34% of write traffic touched documents that had been read from the other region within the previous hour. Zone sharding on region would have meant a majority of writes crossing the Atlantic anyway, at a latency we could not fix, plus the operational complexity of a globally sharded cluster. The honest conclusion was that we were trying to solve an application-design problem with a database topology.

It was a two-hour query against existing logs and it would have ended the project before anyone built anything, because that single number — 34% — was the whole answer. I now insist that any architecture proposal names, up front, the one measurement that would falsify it, and that we take that measurement first.

(d) Follow-up drill chain

Why can a replica set not accept writes in two regions?

Because the single-primary model is what gives you linearisable writes and a straightforward consistency story. One primary orders all writes; secondaries replay that order. Two primaries would mean two independent orderings of the same document's history, which requires conflict detection and resolution semantics — last-writer-wins, CRDTs, or application callbacks — and every one of those pushes correctness decisions into the application. MongoDB's answer is to make the single primary cheap to relocate and to let you partition the data so different primaries own different parts. That is a deliberate trade: you give up multi-master writes and you get a consistency model most people can reason about.

So what can you do for a genuinely global write workload?

Partition it. Zone sharding lets you pin key ranges to shards whose primaries live in a chosen region, so each region writes locally to the data it owns — that is real and it works well, provided the data genuinely has a home. When it does not, your options are to give it one at the application level (an account is owned by a region, and cross-region edits are explicit and slower), to accept the latency for the minority of cross-region writes, or to change the data model so that concurrent regional writes touch different documents and are merged later. All three are application designs. The database can localise data that is localisable; it cannot make globally shared mutable state fast.

What does write concern do to you across regions?

It sets the floor on your write latency, because w: "majority" waits for a majority of voting members to acknowledge — and if your majority necessarily includes a member on another continent, every write pays that round trip. That is why member placement and vote configuration is a latency decision, not just an availability one: a three-region 1-1-1 layout survives losing any region but makes every majority cross an ocean, while a 2-2-1 layout keeps the common-case majority local at the cost of a more complicated failure story. Tag-based write concerns let you express "acknowledged in two data centres" precisely, and they are also an excellent way to configure yourself into a permanent stall if you name a tag that cannot be satisfied.

How did you deliver the recommendation without demoralising the team?

I told the three engineers first, in the room, before I sent anything — hearing it from a document would have been a betrayal. I made the case in terms of what we had learned rather than what we had wasted, and I was specific that the measurement we lacked was mine to have asked for, not theirs to have found. Then I made sure the six-week replacement project was theirs to build and ship, so the quarter ended with something in production under their names. The thing that would have made it unrecoverable is if I had presented the cancellation as a discovery of my own cleverness.

How did you handle the sponsor who set the mandate?

By separating the goal from the solution and never criticising the goal. Her requirement was legitimate — international customers were complaining and she had committed to fixing it. My document opened with her metric, showed that the proposed architecture would not move it for 34% of traffic, and offered three priced routes that would. I also gave her the decision rather than making it: I recommended, she cancelled, and that distinction matters both politically and honestly, because it was her budget and her commitment. She sponsored the replacement work the same week.

What would you do differently now?

Name the falsifier before starting, and structure the work so the cheapest thing to build is the thing most likely to kill the project. Our prototype was built in the order of "most interesting first" — zone sharding mechanics — when it should have been "most falsifiable first", which was a log analysis. I now open every architecture proposal with a section called "what would prove this wrong, and when will we know?", and I have killed two things early since. It is uncomfortable to write and it is the highest-value paragraph in the document.

EXAMPLE — replace with your own

Our managed MongoDB spend had reached about $41,000 a month and was the second-largest line in the infrastructure budget. Nobody had asked me to reduce it; I picked it up because the growth curve was steeper than our traffic curve, which is always a sign that something is being paid for that is not being used. I gave myself two weeks to find out where the money went before proposing anything, and I recommend that order to anyone doing this work — cost projects that start with a solution usually end up optimising the wrong thing.

Where it actually went, in order: 44% storage, 33% compute on nodes sized for a working set that no longer needed to be that large, 14% inter-region data transfer, and 9% backup retention. The most expensive single fact was that we had 3.1 TB of data of which 2.4 TB was event and audit history older than ninety days, queried on average four times a month, and it was sitting on the same provisioned storage tier as the working data — which also meant it was in every backup and had to be traversed by every initial sync.

Four changes, in the order of return per unit of risk. First, TTL indexes on the two collections with a genuine retention policy, which nobody had ever implemented because deletion felt scary — 900 GB gone over six weeks as the TTL monitor worked through it. Second, moving cold history to an archival tier with a query federation layer so the four-times-a-month queries still worked, just slower: 1.5 TB off the hot tier. Third, switching the two largest collections from the default snappy block compressor to zstd, which cost about 4% more CPU and returned 31% storage on those collections. Fourth — only after all of that, because rightsizing before shrinking the working set gets you a node that is too small — dropping the cluster tier by one step.

// 1. Retention that actually deletes (the TTL monitor runs every 60s, deletes in batches)
db.auditEvents.createIndex({ createdAt: 1 }, { expireAfterSeconds: 7776000 });   // 90 days

// 2. Find where the storage really is, before touching anything
db.getCollectionNames().map(c => {
  const s = db[c].stats();
  return { c, dataGB: +(s.size / 1e9).toFixed(1), idxGB: +(s.totalIndexSize / 1e9).toFixed(1),
           ratio: +(s.size / s.storageSize).toFixed(2) };   // ratio > 1 means compression is working
}).sort((a, b) => b.dataGB - a.dataGB);

// 3. zstd on the big collections (set at creation; existing data recompresses as it rewrites)
db.createCollection("events", { storageEngine: { wiredTiger: {
  configString: "block_compressor=zstd" } } });

I got that acceptance in writing before doing it, which is the difference between a cost saving and a surprise.

What I would do differently: I would have started with retention policy as a product conversation rather than as an engineering one. The reason we had 2.4 TB of history was that no one had ever been asked how long the data needed to live — and when I finally asked, legal said seven years for one collection and "we do not need this at all" for another. Very common — an undersized cluster, an archive nobody could query, a cache removed. That story is more instructive than a clean win and shows you can evaluate durability rather than just impact.

When did you take on work nobody assigned you?

Cost work is often self-initiated, which makes it a good answer to "tell me about something you did beyond your remit". Recall how you got permission to spend the time, or whether you asked.

(d) Follow-up drill chain

How do TTL indexes actually delete, and what surprises people?

A background thread wakes roughly every 60 seconds and removes documents whose indexed date field is older than expireAfterSeconds. Three surprises. It is not immediate — documents remain queryable past their expiry until the monitor reaches them, so it is a retention mechanism and not a security control. It deletes documents one at a time through the normal write path, so a large initial backlog generates enormous oplog volume and can crush replication lag — ours took six weeks deliberately, throttled, rather than deleting 900 GB at once. And on the field type: it must be a BSON date or an array of dates, and a document whose field is missing or of the wrong type is never expired, which is how people end up with a TTL index and no deletion.

Why not just compress everything with zstd from the start?

Because it is a CPU-for-storage trade and the right point on that curve depends on your workload. zstd gives meaningfully better ratios than snappy on text-heavy documents — 20 to 40% in what I have measured — at a few percent more CPU per operation, which is invisible on an IO-bound workload and quite visible on a CPU-bound one. Snappy is the default because it is fast and cheap. For a hot, small, CPU-bound collection I would leave snappy; for a large archive-ish collection I would use zstd every time. It is also worth knowing that changing the compressor only affects newly written blocks, so the benefit arrives as data is rewritten unless you force a rewrite.

At what point does a cost saving become a reliability risk?

When it removes headroom rather than waste. Dropping a cluster tier is safe if the working set genuinely shrank; it is dangerous if you sized to the new average and left nothing for a traffic spike, an index build or an initial sync — all of which need capacity you are not using on an ordinary Tuesday. The same applies to backup retention and to oplog size: shrinking the oplog saves storage and shortens your recovery window, which nobody notices until the day it matters (see story 12). My rule is that I will optimise waste aggressively and headroom never, and I make the distinction explicit in the proposal so the person approving it knows which one they are buying.

How did you keep the saving from being eaten back?

An owner and a visible number. Monthly spend per cluster on a dashboard the team sees, with an alert on a percentage increase rather than an absolute threshold, so growth that outpaces traffic gets noticed early. The retention policies went into the collection creation template so new collections arrive with a TTL or an explicit written exemption. And I published the attribution breakdown — storage, compute, transfer, backup — because a single total is impossible to act on. A year later it was still under $20,000, which is the only evidence that any of this was structural rather than a one-off clean-up.

How did you handle the two people whose queries got 20× slower?

I went to them before doing it, with the actual numbers from a prototype rather than an estimate, and asked what their tolerance was. It turned out they ran those queries as part of a monthly compliance export where a nine-second query was irrelevant, and they had assumed nobody could change it. Getting that in writing protected both of us — them because it documented that they had a requirement at all, me because a year later when someone complained about archive latency I could point to the agreement rather than to my memory. Disclosed regressions are fine; discovered ones cost you credibility you need for the next proposal.

What would you do differently now?

Ask the retention question in the design review, not in a cost project three years later. Every collection should be created with an answer to "how long does this live and who says so", and the default answer should be a TTL rather than forever. I would also attribute cost per team from the start — when the bill is one number owned by infrastructure, no product team has any reason to care; when each team sees their own storage line, the conversation happens without me. The technical levers saved money once; the attribution changed behaviour.

We ran a separate search cluster alongside MongoDB, fed by a bespoke sync job that had been written by someone who had left. It drifted: about once a fortnight a document existed in the database and not in the index, or the other way round, and support had a runbook entry called “reindex the thing”. It cost roughly $6,000 a month, one engineer's attention, and it was the source of more incidents than any other component we owned.

The trigger to act was a product requirement for semantic search over support articles — “find things like this”, not “find things containing this word”. That would have meant adding vector search to a component nobody wanted to own. So I ran a proper evaluation rather than a preference: two weeks, three options, with acceptance criteria written down before we started — relevance parity on a 200-query judged set, p95 under 200ms, and a sync mechanism nobody had to maintain.

We chose Atlas Search and Atlas Vector Search, and the deciding factor was not features, it was the sync. Search indexes are maintained from the change stream by the platform itself, so the drift class of bug ceased to exist — that removed our most frequent incident category outright. Being able to do lexical, vector and hybrid retrieval in the same pipeline as the rest of our query, against the same documents, is a genuine simplification and not just a consolidation.

(d) Follow-up drill chain

Why is a platform-maintained search index better than your own sync job?

Because the sync job is a dual write, with all the failure modes from story 14, plus a piece of bespoke software with a bus factor of one. A platform-maintained index is fed from the change stream by the platform, so it inherits the oplog's durability and ordering and it resumes correctly after an outage without anyone writing resumption logic. You are still eventually consistent — that does not go away and you must design for it — but the class of "the index and the database disagree permanently and nobody notices" disappears. The general principle transfers well beyond search: prefer a derived store maintained by a log you already trust over a second writer you have to keep honest.

What is $vectorSearch actually doing, and where does it cost you?

Approximate nearest-neighbour search over dense vectors, using an HNSW-style graph index. The knobs that matter are numCandidates, which controls how much of the graph is explored before returning the top limit — higher means better recall and more latency — and the embedding model itself, which is where most of the quality lives. The costs people underestimate are outside the query: generating and storing embeddings for every document, re-embedding the whole corpus when you change model, and the fact that your relevance is now a property of a model you may not control. It is also approximate by construction, so if you need exact nearest neighbours you need a different plan.

How did you decide the hybrid weights?

With a judged set, because there is no other honest way. We took 200 real queries from the logs, had support engineers judge the top ten results for each as relevant or not, and computed NDCG for a grid of weightings — that gave us 0.4 lexical / 0.6 semantic as a defensible number rather than a guess. The important part is that the judged set is a durable asset: it is now the regression test for any change to analysers, embeddings or weights, and it was the thing that caught the German compound-word problem. Anyone tuning search relevance without a judged set is tuning by anecdote, and the anecdotes are always the queries the loudest person tried.

At what point would you not consolidate onto the database's search?

When search is the product rather than a feature of it. If you need deep control over scoring, custom analysers per language at scale, ingestion from many sources that are not your database, or query volumes that dwarf your operational load, a dedicated engine with a team behind it is the right answer and consolidation is a downgrade. I would also not consolidate if it created an availability coupling I could not accept — search and the operational database sharing a fate is fine for us and would not be for a business whose homepage is a search box. Our case was the common one: search is important, it is not the product, and one fewer distributed system was worth more than the tail of features we gave up.

How did you get buy-in given someone had built the old system?

The author had left, which made it easier, but two engineers had inherited it and had real pride in keeping it alive. I made them the evaluators rather than the defendants: they wrote the acceptance criteria, they ran the shadow comparison, and one of them found the mapping typo that would have shipped a broken index. I also said plainly, in the review, that the sync job had held together a hard problem for four years and that the reason we could replace it was that the platform had caught up, not that it had been badly built. That is both true and necessary — people do not migrate off systems they are being blamed for.

What would you do differently now?

Budget the configuration work honestly and get a domain person involved from week one. I would also build the judged set before choosing, not during the migration — we assembled it under time pressure and it shaped every decision afterwards, so it deserved more care than it got. And I would decide the decommission date at the start, in writing: our old cluster ran for a month after the last tenant moved, which was right, but the decision to finally switch it off took three weeks of nobody wanting to be the one to do it.

18On-call for a cache-pressure stall

tier · senior → staff archetype · on-call firefighting

EXAMPLE — replace with your own

02:40, page: “API latency p99 above 5s”. Not down, not erroring, just glacial — the worst kind, because everything looks alive. CPU on the primary was 40%, disk was nearly idle, connections were normal, and every single operation was slow, including trivial _id lookups that should be sub-millisecond. When everything is uniformly slow and the obvious resources look fine, the bottleneck is almost always a shared queue rather than a workload.

It was WiredTiger cache pressure. The cache had gone to 97% used with dirty content above the 20% eviction trigger, so application threads were being conscripted into eviction — every operation was paying to evict pages before it could do its own work, which is why cheap and expensive queries were equally slow. The upstream cause was a data-science job someone had started before going to bed: an aggregation with no $match that scanned a 900 GB collection, pulling cold pages into the cache and evicting the entire working set as it went. The correct mental model is that WiredTiger's cache is a fixed pool, roughly half of RAM by default, and a large scan is not just slow for itself — it is an eviction attack on everyone else.

// What told me, in about ninety seconds
db.serverStatus().wiredTiger.cache["bytes currently in the cache"];
db.serverStatus().wiredTiger.cache["tracked dirty bytes in the cache"];
db.serverStatus().wiredTiger.cache["pages evicted by application threads"];   // non-zero = trouble
db.serverStatus().queues.execution;    // 8.0+ name; was wiredTiger.concurrentTransactions

// Who is doing it
db.currentOp({ secs_running: { $gt: 30 }, op: "command" })
  .inprog.map(o => ({ id: o.opid, secs: o.secs_running, ns: o.ns, plan: o.planSummary, by: o.appName }));

// Mitigation, in that order
db.killOp(180452);                              // stop the scan
// then, so it cannot recur:
db.coll.aggregate(pipeline, { maxTimeMS: 60000 });   // a ceiling on every analytical query

I killed the operation at 02:51 and latency recovered over the next four minutes as the cache re-warmed — not instantly, which is worth knowing, because the working set has to be read back from disk. Total: eleven minutes from page to recovery, about nine minutes of degraded service for users. I did not diagnose the root cause at 3am; I mitigated, wrote three lines in the incident channel, and went back to bed. Diagnosing at 3am is how you get a wrong root cause and a tired engineer.

The follow-ups, done in daylight, are the part that mattered. A maxTimeMS ceiling applied by default in the shared data-access library, so no query can run unbounded. Analytical read preference pinned to the tagged secondary from story 11, which is where that job should have run in the first place. An alert on application-thread evictions and on cache dirty percentage, which are leading indicators that fire minutes before latency does. And a short guide for the data-science team on how to run a scan safely, because they had done nothing wrong except lack a safe path — they had asked nobody because there was nobody obvious to ask.

What I would do differently: I would have looked at currentOp first instead of fourth. I spent six minutes on dashboards looking for a cause when the answer was “someone is running something enormous”, which is a single command. My on-call heuristic now is: check what is running before checking how the machine feels.

What the interviewer is really probing. Judgment at 3am: mitigate first, diagnose in daylight, and know which two or three commands answer the question. They also listen for whether your follow-ups blamed a person or built a safe path — “we told them not to do that” is a weak ending; “there was no safe way to do what they needed, so we built one” is a strong one.

The mistake candidates make. Telling it as a heroic all-nighter. Going back to bed after mitigating is the correct, senior answer and most candidates are afraid to say it. The other mistake is describing symptoms without the mechanism — "the cache was full" is not an explanation until you can say why a full cache makes cheap queries slow.

(d) Follow-up drill chain

Why does a full cache make even trivial queries slow?

Because when eviction cannot keep up, the server starts making application threads do the evicting. Normally dedicated eviction threads keep the cache below its targets; when dirty content passes the trigger — around 20% dirty by default, with a hard limit above that — the operation that wants a page must first evict pages to make room, so every query pays a tax proportional to how far behind eviction is. That is why the signature is uniform: an _id lookup does the same eviction work as a scan. The metric to look for is "pages evicted by application threads" being non-zero, which is the server telling you explicitly that this is happening.

What are execution tickets and how do they show up in this?

A bounded pool of slots for concurrent storage-engine operations, split between reads and writes, which exists to stop the engine being swamped. Historically they were the fixed 128/128 pair exposed as wiredTiger.concurrentTransactions; since 8.0 the server tunes the limits dynamically based on observed throughput and they are reported as queues.execution. When operations run long they hold tickets, so a queue forms and latency rises for work that is not itself slow. Seeing available tickets at zero is a strong signal that you have a small number of expensive operations rather than a capacity problem, and it points you straight at currentOp.

Should you have just made the cache bigger?

No, and this is a good place to say why. The cache defaults to about half of RAM minus a gigabyte, and the remaining half is not spare — the filesystem cache uses it, and WiredTiger reads compressed blocks through it, so a larger WiredTiger cache means less filesystem cache and often worse overall behaviour. More importantly it would not have helped: a scan of a 900 GB collection evicts any cache you can afford. Sizing the cache is a working-set question; this was a workload-isolation question, and answering it with hardware would have bought a slightly longer fuse at real cost.

What does 8.3 give you that would have helped here?

Two things worth naming. 8.3 adds cachePressureQueryPeriodMilliseconds, which controls how often the server checks for storage-engine cache pressure, making the detection and reaction path more tunable than the previously fixed behaviour. And it raises the default FTDC directory size from 200 to 500 MiB, which sounds trivial and is not — full-time diagnostic data capture is what lets you reconstruct an incident afterwards, and a bigger buffer means a longer retrospective window, which matters exactly when the incident happened at 3am and nobody was capturing anything by hand. 8.3 also collects connection-pool stats in FTDC, which closes a common blind spot.

How did you handle the data scientist who ran it?

I messaged him at a civilised hour, explained what happened with the actual graph, and asked what he had been trying to do — which turned out to be perfectly reasonable and impossible to do safely with the access we had given him. Then I built the safe path: the analytics read preference, a documented pattern, and a five-minute pairing session. He has since caught two other people about to make the same mistake, which is a much better outcome than a policy. The instinct to send a warning is the wrong one; the person who triggered an incident is the person most motivated to help you prevent the next one.

What would you do differently now?

Alert on the leading indicators rather than on the symptom. Application-thread evictions, cache dirty percentage and available execution tickets all move minutes before p99 does, and any of them would have paged me before users noticed. I would also put the default maxTimeMS in the shared library on day one of any new service — an unbounded query is a latent incident, and the cost of a ceiling is that occasionally someone has to ask for a higher one, which is a conversation rather than an outage.

19Making the database tests honest

tier · mid → senior archetype · CI / test reliability

EXAMPLE — replace with your own

Our test suite ran against an in-memory fake that mimicked MongoDB's query API. It was fast — the whole suite took ninety seconds — and it was lying to us. Over one quarter I counted eleven production bugs that the suite could not have caught: a query that worked against the fake and did a collection scan in production, an aggregation stage the fake implemented differently, a unique index that did not exist in production because nobody had added it to a migration, and a case-sensitivity difference in sorting that reached a customer.

The argument against using a real database was speed, and it was a serious argument, not an excuse — a suite that takes twenty minutes stops being run before pushing, and a suite nobody runs is worse than one that is slightly wrong. So I did not propose replacing the fake; I proposed a shape. Fast unit tests keep the fake for pure logic that happens to touch a repository interface. Everything that asserts on database behaviour — queries, indexes, aggregations, transactions, concurrency — runs against a real MongoDB in a container, started once per test session and shared, with each test isolated by using its own database name rather than by tearing anything down.

Two details made it fast enough to be adopted. First, a single container per session, not per test: startup is a couple of seconds and it happens once. Second, a container configured as a single-node replica set, because transactions and change streams require one — this is the detail everyone hits, and a standalone mongod will silently fail your transaction tests in a way that looks like a code bug. We also had the container run the same major version as production, and I made a CI job that runs the suite against the next major version nightly, which is how we found two behaviour changes before an upgrade rather than during one.

// One container per session, replica set enabled, real indexes applied from the real migrations
const mongo = await new MongoDBContainer("mongo:8.0").start();     // starts a single-node replica set
const client = new MongoClient(mongo.getConnectionString(), { directConnection: true });

beforeEach(async () => {
  db = client.db(`t_${randomUUID().slice(0, 8)}`);   // isolation by database, not by cleanup
  await applyMigrations(db);                          // the SAME migrations production runs
});

// The test that would have caught the worst of the eleven bugs
it("serves the tenant order list from an index", async () => {
  await db.collection("orders").insertMany(fixture(50_000));
  const plan = await db.collection("orders")
    .find({ tenantId, status: "shipped" }).sort({ createdAt: -1 }).limit(50)
    .explain("executionStats");
  expect(plan.executionStats.totalDocsExamined).toBeLessThan(200);   // fails loudly on a COLLSCAN
});

The assertion in that last test is the one I would put in every codebase: a test that fails when a query stops using an index. It converts the invisible regression from story 01 into a red build. It needs enough data to be meaningful — 50,000 documents, generated once and reused — which is why it lives in the integration tier and not the unit tier.

Results over two quarters: production bugs attributable to database behaviour went from eleven a quarter to one; the suite went from 90 seconds to 4 minutes 40, which the team accepted because the integration tier runs in parallel and only the changed packages run locally; and flaky failures went down, not up, because the fake had been non-deterministic in its sort ordering and nobody had realised.

What I would do differently: I would have led with the eleven bugs. My first proposal was framed as “our tests are not realistic”, which is an aesthetic argument and got a polite no. The version that was approved in ten minutes was a list of eleven specific defects with the sentence “each of these was catchable” next to them. Same proposal, evidence instead of principle.

What the interviewer is really probing. Whether you can improve engineering quality without slowing the team down, and whether you make the case with evidence. The strong signal is the trade you managed explicitly — you did not just make tests better, you kept them fast enough to be run.

The mistake candidates make. Arguing for test purity. Nobody funds purity. Also common: claiming a flake-rate improvement with no number, or omitting the cost — a suite that got three times slower is a real cost and saying so makes the rest credible.

(d) Follow-up drill chain

Why not just mock the database? It is faster and simpler.

Because for anything that asserts on database behaviour you are then testing your mock. A fake cannot tell you whether a query uses an index, whether a unique constraint exists, how the aggregation optimiser reorders your stages, or how a collation affects sorting — and those are exactly the things that break in production. Mocks are correct for the boundary: when a service calls a repository and you want to test the service's logic, mocking the repository is right and fast. The rule I use is that a mock is fine when the assertion is about your code and wrong when it is about the database's behaviour, and most codebases have that line drawn in the wrong place.

Why does the container need to be a replica set?

Because transactions, change streams and causally consistent sessions all require one — a standalone mongod has no oplog and no majority to commit against. Tests for those features against a standalone fail in confusing ways or silently do not exercise what you think, which is the worst outcome. A single-node replica set gives you all the semantics at essentially standalone cost, and it also means w: "majority" behaves as it will in production rather than being trivially satisfied in a way that hides a misconfiguration.

How do you keep integration tests from becoming flaky?

Isolation and determinism. Isolation by giving each test its own database name rather than cleaning up shared collections, because cleanup is where cross-test interference and ordering dependence come from — and dropping a database at the end is cheap. Determinism by never asserting on natural order (there is no such thing), always sorting explicitly, and by controlling anything time-dependent, since TTL and date comparisons are a classic source of tests that pass until they run at midnight. And a hard rule that a test may not sleep: if it needs to wait for something, it waits for a condition with a timeout.

At what point does the real-database approach stop scaling?

When the fixture data gets big enough that setup dominates. A 50,000-document fixture generated per test is unacceptable; generated once per session and inserted with an ordered bulk write it is a couple of seconds. Beyond a certain size the honest answer is a pre-baked container image with the data already in it, or a snapshot restored per session. The other limit is parallelism: many containers means many mongod processes competing for the CI machine's RAM, and WiredTiger's default cache sizing is not container-aware in older versions, so you must cap it explicitly or watch your CI box swap.

How did you stop the team from routing around the slower suite?

By making the fast path genuinely fast and obviously correct to use. Locally, only the packages you changed run their integration tier, which for most work means the suite still finishes in under a minute; the full run happens in CI where nobody is waiting. I also made the integration tier's value visible: every time it caught something, the failure message said what class of bug it had caught, and I mentioned the count in our monthly review. People tolerate a cost they can see the return on, and abandon one they cannot.

What would you do differently now?

Add the plan assertion first and the rest afterwards. That single test shape — assert on totalDocsExamined for the hot queries — would have caught the most expensive of the eleven bugs on its own, and it could have been added in a day without any of the restructuring. I would also have started the nightly next-major-version job at the beginning rather than as an afterthought; it costs nothing, it runs while everyone is asleep, and it turns upgrade surprises from story 04 into a build failure months in advance.

20Saying no to the event firehose

tier · staff → principal archetype · pushing back on a stakeholder

EXAMPLE — replace with your own

A director asked us to put a new product-analytics event stream — projected at 40,000 events per second, growing — into the same MongoDB cluster that ran order processing. His reasoning was sound from where he sat: we already had the cluster, the team knew it, and standing up something new would take a quarter he did not have. He was not being unreasonable; he was optimising for the constraint he could see.

My objection was not “MongoDB is the wrong database for events”, which would have been wrong as well as unhelpful — MongoDB handles high-volume append workloads well, particularly with time series collections. My objection was about isolation. Putting a 40,000/second write stream and a 4,000/second order workload on one cluster means they share the WiredTiger cache, the execution ticket pool, the oplog and the failure domain. The event stream would evict the order working set, flood the oplog and collapse our recovery window (story 12), and — the part that ended the discussion — a bad deploy on the analytics side would take down checkout. One system's incident would become the other's outage, permanently, and no amount of care would undo that coupling.

I made the case in his currency rather than mine. I estimated the revenue exposure of a checkout outage per hour from our own historical figures, showed the oplog window collapsing from nineteen hours to about forty minutes at the projected volume — which meant our point-in-time recovery for orders would effectively cease to exist — and put those next to the cost of a separate cluster, which was about $2,800 a month. Framed as “we can protect the order recovery guarantee for $2,800 a month”, it was not a difficult conversation. Framed as “this is architecturally wrong”, it would have been a stand-off I might have lost.

And I brought a way to say yes. A separate cluster was a quarter of work only if we treated it as a full platform project; provisioned as a managed cluster with a time series collection, a TTL policy and the same change-stream publisher we already ran (story 14), it was two weeks. I offered to have my team do it. That mattered more than the argument: the director's real constraint was time, so removing the time cost removed the disagreement.

// What we actually built, on its own cluster
db.createCollection("events", {
  timeseries: { timeField: "ts", metaField: "source", granularity: "seconds" },
  expireAfterSeconds: 2592000            // 30 days; analytics owns anything longer downstream
});
// Isolation is the point: separate cluster, separate oplog, separate cache, separate failure domain.
// Same team, same tooling, same runbooks — the familiarity argument was answered without the coupling.

Results: the event stream ran at 46,000/second within six months and never touched the order cluster; the order cluster's oplog window stayed at nineteen hours; and the analytics cluster had two incidents in the first year, both invisible to customers. What I would do differently: I would have written the isolation principle down before it was tested. We had no stated policy about which workloads may share a cluster, so every instance of this question was relitigated from scratch — and this was the third time. After this one I wrote a one-page rule with three criteria (shared failure domain acceptable? recovery objectives compatible? resource profiles compatible?), and the next two requests were settled in a comment thread rather than a meeting.

What the interviewer is really probing. Whether you can disagree upward without either capitulating or grandstanding. The signals: you stated their constraint fairly, you translated the risk into their language with a number, and you brought an alternative that addressed the thing they actually cared about.

The mistake candidates make. Telling it as a story about being right, or about a stakeholder who "did not understand engineering". Both read badly, and the second is disqualifying at lead level. Also: never end at "and they agreed" — end at what changed structurally so the argument does not recur.

(c) Recall prompts

When did you say no to someone more senior than you?

Recall what you offered instead, because that is what separates pushback from obstruction. Also recall whether you were nervous and what you did about it — a little honesty there makes the story human rather than performed.

Have you translated a technical risk into money or time?

Revenue per hour of downtime, engineer-days of rework, a recovery objective expressed as "how much data we would lose". If you have ever made that translation and watched the conversation change, that is the story.

What decision in your organisation gets relitigated every time it comes up?

Whatever it is, writing the rule down is a high-leverage staff move that most people never make. If you have done it, recall the meeting that stopped happening as a result.

When were you overruled, and what did you do?

Interviewers ask this deliberately. The good answer disagrees, commits, documents the risk and the trigger for revisiting, and does not sulk or say "I told you so" later. Have a real example, including one where you turned out to be wrong.

(d) Follow-up drill chain

Why is workload isolation worth real money?

Because on one cluster the resources are genuinely shared and none of them can be partitioned per workload. One WiredTiger cache, so a scan-heavy tenant evicts a latency-sensitive tenant's working set; one execution ticket pool, so long operations queue everyone; one oplog, so a high-volume writer collapses the recovery window that another workload depends on; and one failure domain, so a step-down, an upgrade or a bad index build is shared. You can mitigate at the edges — read preferences, maxTimeMS, separate databases — but none of those partition the cache or the oplog. Once one workload can determine another's availability, you have coupled two roadmaps forever, and that is a much more expensive thing than a cluster.

Could you have made it work on one cluster if you had to?

Partly, and it is worth being able to say how rather than just refusing. On a sharded cluster you can use zone sharding to pin the event collection to dedicated shards, which genuinely isolates storage and much of the cache — that is the standard technique and it works. What it does not isolate is the config servers, the mongos tier, the balancer's attention and the operational blast radius of a cluster-wide operation such as an upgrade. So it is a real option with a real cost: significantly more operational complexity than a second cluster, for less isolation. I would choose it if the workloads genuinely needed to be queried together, and they did not.

What would have happened to the oplog, concretely?

The oplog is a capped collection with a fixed size, so its time window is size divided by write throughput. Adding 40,000 small writes per second to a workload doing 4,000 would have raised throughput by roughly an order of magnitude and cut a nineteen-hour window to well under an hour. That window is what bounds point-in-time recovery and what determines how long a secondary can be down before it needs a full initial sync rather than a catch-up — so a change made for analytics would silently have destroyed a recovery guarantee for orders. Being able to name a second-order consequence like that, on a system nobody was talking about, is usually what actually wins these arguments.

How would you have handled it if he had said no?

Disagree, commit and document. I would have written down the specific risk, the estimated exposure and the trigger conditions that should make us revisit — oplog window below four hours, or the first shared-cause incident — and I would have got that acknowledged rather than filed. Then I would have built it as asked and instrumented exactly those triggers, because the fastest way to reopen a decision is data from the decision itself. What I would not do is comply grudgingly and wait to be proved right; that costs you the relationship you will need for the next disagreement, and the disagreement after that is always the more important one.

At what scale would you reconsider and consolidate?

If the event volume had been two orders of magnitude smaller — a few hundred writes a second, bounded, with a TTL — I would have put it on the existing cluster without hesitation, because the isolation argument is about magnitude, not about principle. A second cluster has real costs: another thing to patch, monitor, back up and page someone about, and a second copy of every operational habit. I try to be honest that "separate the workloads" is not free wisdom; it is a trade I would make above a threshold and refuse below it, and naming the threshold is what makes it a judgment rather than a rule.

What would you do differently now?

Write the policy before the third instance rather than after it. And I would build the "way to say yes" first — I spent two days assembling the risk argument and half a day discovering that a separate cluster was two weeks of work, when leading with the two-week estimate would have made most of the risk argument unnecessary. The general lesson I took: when pushing back on someone whose constraint is time, the fastest route through is almost always to attack the time cost rather than to strengthen the risk case.

21The big behavioural Q&A

cross-cutting 22 prompts tiers mid → principal

These are the prompts that are not tied to one incident. Each answer names the story from this page to deploy — swap in your own equivalent — and what the interviewer is listening for. The discipline: pick one story, tell it in ninety seconds with a number in it, and stop. Silence after a complete answer is the interviewer's job to fill, not yours.

Failure & ownership

Tell me about a technical decision you regret.

Deploy: 07 (the shard key) or 15 (the cancelled active-active project). They want: a decision that was genuinely yours, a cost you can quantify, and a changed process rather than a changed mood. Say what was reasonable about the decision at the time — sharding on createdAt was defensible given what we knew about the queries — because a story where past-you was obviously foolish reads as revisionism. End on the mechanism: the signals I now require before sharding, or the falsifying measurement I now take first.

Tell me about the worst production incident you were part of.

Deploy: 03 (the step-down) or 12 (the unfiltered updateMany). They want: the timeline in minutes, mitigation before diagnosis, and follow-ups that changed the system. Name your role precisely — commander, fixer, comms — and name someone else's contribution. If you were not the hero of your own incident, say so; interviewers trust that more than a solo rescue.

When did you ship something that reached users as a bug?

Deploy: 12 (4,000 customers saw wrong pricing) or 06 (duplicate keys for four months). They want: exposure quantified, the customer-facing consequence stated in human terms first, and a class-level fix. Minimising — "only a fraction of documents" — lands badly. Lead with what a customer experienced, then give the number.

Tell me about something you failed to deliver.

Deploy: 15, or 09 (the index cleanup we deliberately stopped at 19). They want: whether you can distinguish an incomplete outcome you chose from one that happened to you. "We stopped because the remaining four indexes each had a real owner and the return was under a gigabyte" is a decision; "we ran out of time" is a report.

Conflict & influence

Tell me about a disagreement with a colleague.

Deploy: 05 (transactions versus document design). They want: the other person's best argument, stated first and fairly, and a resolution mechanism other than seniority. Say what you conceded — his three partial-write bugs were real — and where he ended up: owning the resulting standard is the strongest possible ending.

Tell me about a time you had to say no to a stakeholder or a manager.

Deploy: 20 (the event firehose) or 11 (the fourteen reports). They want: evidence, an alternative, and their underlying constraint identified. Never tell this as a story about being right; tell it as one about getting both goals met, in their currency, and include how you removed their actual blocker.

Tell me about a time you influenced without authority.

Deploy: 04 (getting eleven teams to upgrade their drivers) or 14 (the signed integration contract). They want: that you made it easy for others to say yes — a pilot, a measurement, a pull request you opened for them — rather than running a campaign. The tell of a real story is that you name someone who initially disagreed and what changed their mind.

How do you handle a code review where you disagree with the author?

Deploy: 08 (the injection finding) or 05. They want: proportionality — a security defect and a stylistic preference are handled differently — and a bias toward a conversation over a comment thread. In 08 the useful detail is that I wrote a failing test instead of an opinion, and that my first framing was wrong. Mention the point at which you stop arguing and let a decision stand.

Tell me about working with a difficult team or person.

Deploy: 14 (the team that wanted direct database access) or 18 (the data scientist whose job took us down). They want: curiosity before judgment. The strong version discovers that the "difficult" behaviour was rational given constraints you could not see — they had no safe path — and that the fix was building one, not changing a personality.

Leadership & mentoring

Tell me about someone you helped grow.

Deploy: 10 (the aggregation pipeline). They want: a mechanism and an outcome for the person — they now give the internal talk — not a warm feeling. Include what you asked rather than what you told, and the fact that your first attempt, a lunchtime session, changed nothing for six weeks.

How do you set technical direction for a team?

Deploy: 05 (the written rule on transactions) plus 20 (the isolation policy). They want: criteria before conclusions, decisions written down, and a route for dissent. At principal level they also want direction that survives you leaving the room — a helper in the shared library, a lint rule, a dashboard — because conventions beat charisma.

How do you onboard engineers into a large data-heavy codebase?

Deploy: 13 (the documented schema contract) and 10. They want: that you optimise for the reader — a documented "how we model a collection", the version field that makes the estate legible, a first task with a real user outcome, and pairing early. Naming onboarding time as something you actually measured is a differentiator.

How do you handle an underperforming engineer?

Deploy: no story from this page — answer directly. They want: clarity and speed: separate can't from won't, give specific feedback with examples and dates, change the support before you change the assessment, and involve their manager rather than carrying it alone. Vagueness dressed as kindness is the wrong answer, and so is a story where you quietly did their work.

How do you run an incident review?

Deploy: 12. They want: blameless in practice, not just in name — actions not people, the timeline reconstructed from evidence rather than memory, and follow-ups with owners and dates. The detail that shows you have really done it: the engineer who ran the bad script was in the room and wrote the guard afterwards, and the personal conversation happened separately, in a different room.

Ambiguity & prioritisation

Tell me about a time requirements changed underneath you.

Deploy: 13 (eleven schema changes in four months). They want: a design response to uncertainty, not a complaint. Distinguish unknowable from unmanaged, and say how you made the churn visible — the documents-per-schemaVersion dashboard — so the cost was not silently absorbed by the team.

How do you decide what not to do?

Deploy: 09 (stopping at 19 indexes) or 11 (six reports instead of fourteen). They want: an explicit rule — reversibility, blast radius, return per unit of risk — and evidence you applied it against your own preference. The reusable technique from 11: ask what people actually open on a normal Tuesday, because nobody defends a hypothetical.

Tell me about delivering under a hard deadline.

Deploy: 11 (six weeks to a contractual go-live). They want: a scope trade offered rather than heroics performed. Overtime as the answer signals poor planning; three options with honest prices, and a measurement that reframed the conversation in ten minutes, signals judgment.

How do you prioritise technical work against features?

Deploy: 09 (write latency as a visible number), 16 (money) or 04 (an audit finding). They want: translation into the business's language — risk, rework, money, time to market — and a mechanism that keeps non-urgent work moving without a dedicated project. Be honest that the upgrade programme was funded by an audit, not by foresight.

Craft & technical judgment

What is the hardest technical problem you have solved?

Deploy: 06 (the 3am duplicate key), 18 (cache pressure) or 07 (the shard key) — pick by which mechanism you can explain most precisely. They want: depth of explanation, not exoticism of problem. A perfectly explained upsert race beats a hand-waved distributed system every time, and 06 lets you explain why a transaction would not have helped, which is a memorable answer.

How do you keep up with MongoDB, and what have you changed your mind about?

Deploy: the version facts — 8.3 GA on 4 May 2026 with the cost-based ranker as the default plan-selection mechanism and $scoreFusion GA; 8.2 in September 2025 bringing rapid releases and Search previews to Community and Enterprise Server; removeShard deprecated in 8.3 in favour of the four draining commands. They want: a filter, not a firehose — release notes and changelogs over conference hype — and one concrete opinion you have reversed. Mine: I used to treat multi-document transactions as a last resort, and the honest position is that they are a normal tool with a measurable price.

How do you make quality decisions when nobody is watching?

Deploy: 19 (the plan assertion in CI) or 08 (the lint rule and disabled server-side JavaScript). They want: standards that are mechanical rather than moral — a CI gate, a default in a shared library, a disabled server feature — because those survive deadline pressure and staff turnover, and personal diligence does not.

When have you chosen the boring option?

Deploy: 15 (single-region primary with regional read replicas) or 07's postscript (do not shard yet, buy RAM). They want: that you can resist an interesting architecture when a dull one meets the actual need, and that you can name the metric that made the dull option sufficient. This is one of the most under-told strong answers available at lead level.

Values & motivation

What kind of work do you want more of?

Deploy: whichever story you told with genuine energy. They want: coherence between what you say you enjoy and what your examples show. If every story you told was an incident, saying you want greenfield design work needs an explanation — and "I want to build the guard rails rather than keep discovering their absence" is a good one.

Why are you leaving, and what are you looking for?

Deploy: nothing — this one is short and forward-looking. They want: no bitterness and no vagueness. Name one thing you want more of and one thing you want less of, tie both to evidence from your own stories, and stop talking.

22Night-before cheat sheet

delivery read aloud

Ten sentences to read out loud the night before, then again in the car. They are about delivery, not content — the content is the twenty stories above, and by now they should be yours, not these.

  1. Lead with the situation in one line, then stop setting up. "One screen went from instant to nine seconds over a weekend, on a collection of 340 million orders." The interviewer now knows the stakes; everything after that is answer, not preamble.
  2. Put a number in the first thirty seconds and another at the end. 8.6s to 210ms, 9,000 to 54,000 writes a second, $41,000 to $19,400 a month. Numbers are what people remember and what makes the rest of the story credible.
  3. Say "I" for what you did and "we" for what the team did, in the same breath. "I was incident commander; the on-call engineer found the election correlation and the platform team paused the rollout." Interviewers listen for this specifically, and false modesty costs as much as inflation.
  4. Name the mechanism, not just the outcome. "Equality first, then sort, then range — a range predicate before the sort key forces an in-memory sort" is one mechanical sentence that proves you understood the fix rather than watched it happen.
  5. Tie every decision back to a real MongoDB trade-off. Document rewrite cost versus join cost. Write distribution versus query targeting. Durability versus latency in the write concern. Cache residency versus scan size. Every good story on this page is one of those underneath.
  6. Own the "what I would do differently" without apologising for it. One sentence, specific, structural: "I would have measured cross-region write overlap in week one; it was a two-hour query and it was the whole answer." Then move on — dwelling reads as insecurity.
  7. Say what you traded away. Atlas Search cost us read-your-writes; the analytics secondary cost us freshness; the deterministic _id cost us index locality. A story with no cost sounds rehearsed, because real work always costs something.
  8. Be precise about versions and dates. 8.3 GA on 4 May 2026, latest patch 8.3.8 on 11 August 2026; 8.0 GA on 2 October 2024; transactions since 4.0 and across shards since 4.2; mapReduce deprecated since 5.0; index filters deprecated in favour of query settings. Precision here signals currency better than any opinion.
  9. When you do not know, say the boundary of what you know and how you would find out. "I have not run Queryable Encryption with the 8.2 substring query types in production; here is what I would measure in the first week." This scores higher than a confident guess, every single time.
  10. Answer in ninety seconds and then be quiet. Let the interviewer drill — the drill chains are where lead-level signal actually lives, and you have prepared for them. Rambling past your own conclusion is the most common way strong engineers lose these interviews.
