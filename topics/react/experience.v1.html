01Re-render storm on a live dashboard

tier · senior → staff archetype · performance diagnosis

EXAMPLE — replace with your own

We ran an operations dashboard: about forty widgets on one screen, fed by a WebSocket that pushed roughly twenty price ticks a second. It had always felt “busy”, but the complaint that got it prioritised was specific and damning — typing in the instrument filter took about 400ms per keystroke, so the box lagged a whole word behind the user. Our RUM showed INP at the 75th percentile of 640ms on that route, against 180ms for the rest of the app, and support had three tickets a week about “the search box eating characters”.

I started with the React DevTools Profiler rather than guessing. One keystroke produced a commit of 180–210ms with every widget in the flamegraph, and “Why did this render?” said context changed on components that had nothing to do with the filter. Chrome’s React performance tracks — the Scheduler and Components tracks React 19.2 emits — made the shape obvious: a solid blocking-priority band per tick, no interruption, because a single long commit cannot be preempted no matter how concurrent the renderer is. The root cause was one provider holding both the tick data and the filter state, with a fresh object literal as its value on every tick. Every consumer under it re-rendered twenty times a second; React.memo on the widgets did nothing, because context propagation walks past memo boundaries by design.

The fix was three moves, in order of payoff. First, ticks stopped being React state at all: they went into a plain mutable store, and each widget subscribed to just its own symbol through useSyncExternalStore, so a tick re-renders one widget instead of forty. Second, I split the remaining context in two — a stable one holding callbacks and configuration that never changes identity, and a small changing one for genuinely shared UI state. Third, the filter input became fully controlled and cheap, with the expensive derived list wrapped in useDeferredValue so the keystroke commits immediately and the heavy list catches up at transition priority.

// Before: one provider, new identity every tick, forty consumers re-render.
<MarketContext.Provider value={{ ticks, filter, setFilter }}>{children}</MarketContext.Provider>

// After: ticks live outside React; each widget subscribes to one symbol.
function usePrice(symbol) {
  return useSyncExternalStore(
    (cb) => tickStore.subscribe(symbol, cb),   // subscribe
    () => tickStore.get(symbol),               // client snapshot (must be cached, not a new object)
    () => tickStore.get(symbol)                // server snapshot for SSR
  );
}

// And the filter stops blocking the keystroke:
const deferredQuery = useDeferredValue(query);
const rows = useMemo(() => filterInstruments(all, deferredQuery), [all, deferredQuery]);

Numbers after two weeks: commit time on a keystroke 180ms → 9ms, INP p75 640ms → 120ms, and CPU on the standard-issue mid-range laptop we tested on fell from about 70% sustained to 18%. What I would do differently: I let the team spend a sprint sprinkling useMemo and React.memo before I profiled, and it bought nothing measurable — the data-flow shape was the bug, not missing memoisation. I would also have set a performance budget on that route from the start, because the regression arrived gradually over a year and nobody owned the number.

What the interviewer is really probing. Whether you measure before you change, and whether you know the difference between a render problem and a data-flow problem. The signal is a named tool, a number before, a number after, and a hypothesis you disproved.

The mistake candidates make. Reciting “I added useMemo and React.memo” with no measurement, or claiming a percentage improvement they cannot source. The second-most common: taking sole credit for a fix that three people shipped — say what you did and what the team did.

(c) Recall prompts

When did you last watch React behave differently under real load than in dev?

Think of a screen that felt fine on your machine with seed data and fell over with production volume or a slow device. Hint: dev builds are slower but StrictMode’s double render also hides how cheap the real commit is, and your laptop is not the user’s laptop. If nothing comes to mind, remember a demo that stuttered on a projector or a conference wifi.

What is the largest number of components you have seen re-render for one user action?

Open the Profiler on your current app and type in a search box; count the commit. Most people find a surprise. The story is the surprise plus what you did about it — even if the answer was “nothing, it was 4ms and I moved on”, which is itself a good, senior answer.

Which performance fix of yours turned out to be the wrong one?

Wrong fixes are the strongest material: memoising a component whose render was 0.3ms, virtualising a list of forty rows, debouncing what should have been deferred. Say what the measurement told you afterwards.

Have you ever had to defend a performance number to a sceptical stakeholder?

Lab vs field is the usual fight: Lighthouse said 98, users said slow. If you have moved a team from lab scores to RUM percentiles, that is a staff-level version of this story.

(d) Follow-up drill chain

Why did React.memo not stop the re-renders?

Because memo only compares props from the parent. Context is delivered by a separate mechanism: when a provider’s value changes identity, React walks the tree to every consumer of that context and marks it for re-render, and a memo boundary in between does not stop it. The classic workaround before hooks-era tooling was to split providers so consumers only subscribe to the slice they need; the modern one is to keep high-frequency data out of context entirely and read it through useSyncExternalStore, which lets each subscriber decide whether its own snapshot changed.

At what update rate does the context approach break?

Roughly when consumers times updates per second times per-consumer render cost exceeds a frame budget — with forty consumers at half a millisecond each, twenty updates a second is already 400ms of render work per second, and that is before commit and paint. My rule of thumb is that context is for values that change on user actions or route changes, not for streams. Anything above a few updates a second, or any value where most consumers only care about one slice, belongs in an external store with selectors.

Would React Compiler have fixed this for you?

Partly, and not the important part. Compiler 1.0, stable since October 2025, auto-memoises component bodies and JSX, so it would have removed the hand-written useMemo churn and would have kept the provider value stable if it could prove the inputs unchanged — but the inputs did change, twenty times a second, so the fan-out is unchanged. I would still adopt it, for maintenance reasons, but I would not sell it to a team as a fix for an architecture that broadcasts a stream to forty subscribers.

What did you trade away with useSyncExternalStore?

Three things. Data is no longer part of React state, so time-travel debugging and the React DevTools state view lose visibility; the snapshot function must return a cached, referentially stable value or React loops, which is a sharp edge for newcomers; and server rendering needs a third argument, which forces you to think about what the server even knows about a live price. In return, updates become O(subscribers to that symbol) instead of O(consumers of the context).

How would you stop this regressing?

Budget plus signal. A CI check on bundle size and a Lighthouse or Playwright trace with an assertion on INP for that route, RUM percentiles on a dashboard someone actually reads, and — cheaply — a Profiler screenshot in the PR template for changes to that screen. The lasting fix was cultural: we agreed the route had an owner and a number, so the next slow change had somewhere to fail.

What would you do differently now, on 19.2?

Start with the performance tracks rather than the Profiler. The Scheduler track tells you immediately whether you are looking at one long blocking commit or many small ones, which is the fork in the road: a long commit means split the work or defer it, many small ones means fan-out. I would also reach for <Activity> for the off-screen panels — hiding them keeps their state but stops their effects and de-prioritises their renders, which is exactly what we hand-rolled with mount/unmount flags.

02Server components vs the client SPA

tier · staff → principal archetype · architectural trade-off

EXAMPLE — replace with your own

We had a five-year-old client-rendered React app — Vite, React Router, a REST gateway — and a mandate to cut time-to-first-content on the public catalogue pages, which were the only pages that mattered for acquisition. The obvious answer in the room was “move to the App Router and use Server Components”. I was the one who had to decide, and I refused to decide it as one question. I split it into three: do we need server rendering, do we need React Server Components, and do we need a different framework? Those are separable, and conflating them is how teams end up with an eighteen-month migration to fix a two-week problem.

Server rendering was clearly worth it for the catalogue: the pages were mostly static, the data was cacheable for minutes, and we were shipping 420KB of JavaScript before a single product name appeared. RSC was a real but narrower win — it would let the product detail page do its data fetching on the server without shipping the parsing, formatting and markdown libraries to the browser, which was about 140KB of that bundle. A framework change was the expensive part, and the part with no technical necessity attached to it.

What we did: kept the authenticated application exactly as it was, a client SPA, and moved only the catalogue — about 12% of the routes and 80% of the traffic — onto a server-rendered React setup with Server Components for the data-heavy pages. The seam was the URL, not a shared runtime: two deployables behind one CDN, no module federation, no shared React instance. I wrote a one-page decision record with the reversal cost of each option, because the thing that actually changes minds at this level is “here is what it costs us to be wrong”.

OptionWinsCostsReversal cost
Stay client-only, optimiseNo migration; code splitting and preloading are cheapTTFB-bound content stays behind a JS downloadZero
SSR the SPA (streaming, no RSC)First paint from HTML; keeps one mental modelEvery component must be SSR-safe; server cost per requestLow — you can turn it off
RSC for the data-heavy public routesData fetching and heavy deps stay on the serverTwo component worlds ("use client" boundaries), new mental model, framework-shapedMedium — the boundary rewrites are real
Full framework migrationOne stack, long-term simplicityAuth, routing, tests, CI, hiring, a year of half-migrated codeHigh

Results: LCP on catalogue pages went from 3.4s to 1.3s at p75 on 4G, JavaScript on those routes fell from 420KB to 96KB, and organic traffic rose enough that the team stopped arguing about the decision. The honest cost: for six months we had two ways to build a page, and I under-invested in explaining which to use — new engineers picked by taste. What I would do differently is write the “which world does this page live in” rule on day one, not month five, and make the RSC boundary a lint rule rather than folklore.

What the interviewer is really probing. Whether you can hold two credible options in tension and pick with stated criteria, or whether you pattern-match to whatever is fashionable. At staff and above they also want to hear reversal cost, blast radius and how you got the org to agree — not just the technical merit.

The mistake candidates make. Advocating RSC (or refusing it) as an identity rather than a trade-off, and never naming what the choice cost. If your architecture story has no downside, the interviewer assumes you have not run it long enough to see one.

(c) Recall prompts

What is the biggest React architectural decision you were on the hook for?

Look for: rendering strategy (CSR/SSR/SSG/RSC), state ownership, routing, micro-frontends, design system, or “build vs adopt a meta-framework”. Even choosing not to migrate counts, and is often the stronger story.

When did you decide against the more modern option?

Deciding to stay on a client SPA, or to keep Redux, or to not adopt RSC — with reasons and a review date — shows judgment. Hint: the credible version names what would change your mind.

How did you get people who disagreed to commit?

Decision record, spike with numbers, a trial route, a named reversal trigger. Recall an actual objection someone raised and what evidence moved them.

Which of your architectural decisions aged badly?

Everyone has one. The mature framing: what signal did I miss, what did I put in place so the next one is caught earlier.

(d) Follow-up drill chain

Why not just server-render the existing SPA and stop there?

That was genuinely on the table, and for two thirds of the win it would have been enough — streaming SSR gets HTML to the user without any component-model change. What it does not do is stop shipping the client bundle: with SSR alone every component still hydrates, so the markdown renderer, the date library and the price formatter all cross the wire. RSC is the option that changes what is sent, not just when it is rendered. I would have stopped at SSR if the bundle had been 150KB rather than 420KB.

What is the actual cost of the "use client" boundary?

Cognitive and structural. Server components cannot hold state, use effects or event handlers; the moment a leaf needs an onClick, the boundary moves up unless you pass server-rendered children through as props. Teams get this wrong by marking a page-level component as client, which quietly pulls the whole subtree into the browser and deletes the benefit. It also splits your library ecosystem: anything with hooks inside needs a client wrapper. I treat the boundary as a design artefact — reviewed, not accidental.

At what scale does this decision flip?

Two axes. Traffic shape: if the valuable pages are behind auth and personalised per user, server rendering buys much less and costs per request, so a client SPA with good caching often wins. Team size: below roughly ten front-end engineers, two rendering models is a tax you feel every sprint; above thirty, the specialisation is affordable and the bundle savings compound. Data freshness is the third: if everything is real-time, most of the page is client anyway.

How did you get the team to agree rather than comply?

I stopped defending a conclusion and started defending criteria. We agreed on four — first-contentful content on 4G, bundle bytes on the top three routes, reversal cost, and how many ways there would be to build a page — before anyone named a technology. Then the spike measured against those. Two people still preferred the full migration, and I wrote their objection into the decision record with the trigger that would make them right: if the authenticated app ever needs SSR for SEO or shares more than a third of its components with the public one, we revisit.

What would you do differently now?

Write the placement rule and enforce it mechanically from day one — a lint rule and a directory convention beat a wiki page. I would also budget explicitly for the second-system tax: the six months where both worlds exist is not free, and pretending it is is how these migrations acquire a bad reputation they mostly do not deserve.

03Hydration mismatch took the site down

tier · senior → staff archetype · production incident

EXAMPLE — replace with your own

A Tuesday afternoon deploy, and within four minutes the error rate on the server-rendered marketing pages went from background noise to about 8% of sessions, all with a blank page below the header. The alert that caught it was a client-side error-rate monitor, not a health check — the server was returning 200s with perfectly good HTML, which is exactly what makes hydration failures nasty: every server-side signal is green.

I took incident command. First decision, at minute six, was to roll back rather than diagnose — we had a two-minute rollback and no idea of the blast radius, and “diagnose in production while users see a blank page” is a choice you have to justify afterwards. Error rate returned to baseline by minute nine. Only then did we reproduce on staging with a build of the reverted commit.

The cause was almost boring: a personalisation banner that rendered a relative timestamp — “posted 3 hours ago” — computed with new Date() at render time. The server rendered “3 hours ago”, the client hydrated at a moment where the arithmetic rounded to “4 hours ago”, the text nodes disagreed, and React 19 does what it has always done in that situation: it discards the server HTML for that subtree and re-renders on the client. That alone is survivable. What killed the page was that the same commit had moved the error boundary above the banner, so the re-render threw on a null user object and took the entire route with it instead of one card.

// The bug: time-dependent output during render, so server and client disagree.
function PostedAt({ iso }) {
  return <span>{formatRelative(new Date(iso), new Date())}</span>;  // ← Date.now() differs per environment
}

// The fix: render a stable value, then upgrade on the client after mount.
function PostedAt({ iso }) {
  const [relative, setRelative] = useState(null);
  useEffect(() => { setRelative(formatRelative(new Date(iso), new Date())); }, [iso]);
  return <time dateTime={iso}>{relative ?? formatAbsolute(iso)}</time>;
}
// Or, when the mismatch is known and harmless: <span suppressHydrationWarning>…</span>

The follow-ups mattered more than the fix. React 19 turned hydration errors into a single readable message with a diff of the server and client trees instead of the old “Text content does not match” wall, so I made the error boundary report that diff to our error tracker with the component name; 19.1’s owner stacks (captureOwnerStack in development) meant the next one was a two-minute diagnosis. We added a Playwright check that loads the top ten server-rendered routes and fails the build on any hydration error in the console, and we wrote down the class of bug — anything reading Date.now(), Math.random(), window, localStorage or user-agent during render — as a review checklist item.

What I would do differently: I would not have let an error-boundary placement change ride along in a feature commit, and I would have had a synthetic check on rendered content, not just status codes. We were blind for four minutes to something a single browser check would have caught in the canary.

What the interviewer is really probing. Incident-command judgment: do you stop the bleeding before you satisfy your curiosity, do you communicate, and do the follow-ups change the system rather than blame a person. The React depth check is whether you can explain what hydration actually is.

The mistake candidates make. Telling the story as a heroic debugging session with no mitigation timeline, or blaming the engineer who wrote the banner. Also: not knowing whether the incident was detected by a monitor or by a customer — interviewers ask, and “a customer told us” is fine if you fixed the detection gap.

(d) Follow-up drill chain

Explain what hydration is doing, precisely.

The server renders your component tree to HTML with no event handlers and no state. On the client, hydrateRoot renders the same tree but, instead of creating DOM nodes, it walks the existing ones and attaches the fibre tree and listeners to them. It is an assertion that the two renders agree: if a text node or element type differs, React since 18 discards the server HTML for that boundary and client-renders it, logging a mismatch. That is why the failure mode is “flash of correct content, then a blank or different page” rather than a crash.

Why not just wrap everything in suppressHydrationWarning?

Because it silences the report, not the divergence — the client value still wins, and you have lost the signal that told you the server produced something different. It is the right tool for a genuinely intentional, single-element difference, such as a timestamp you accept will differ, and the wrong tool everywhere else. Used broadly it hides real bugs like locale or timezone drift between the render environments, which surface later as wrong data rather than a warning.

At what scale does this class of bug get worse?

It scales with personalisation and with streaming. The more the server output depends on cookies, geography, experiments or time, the more surfaces can diverge; and with streaming SSR plus Suspense the mismatch can land inside a boundary that resolves late, so it appears seconds after first paint and looks like a different bug entirely. React 19.2 also batches Suspense reveals, which is better for users but means you should test with throttled networks or you will never see the interleaving your users see.

What did you trade away by rolling back immediately?

Evidence and a day of the team’s time. Rolling back destroys the live reproduction, and we then spent two hours rebuilding the failing state on staging — with a canary and session replay we could have kept both. The trade was deliberate: user-visible breakage at 8% of sessions outweighed diagnostic convenience. If it had been 0.05% and cosmetic, I would have left it up behind a flag and watched.

How do you prevent the whole route dying when one component fails?

Error boundaries placed per feature, not per page, with a fallback that keeps the rest of the page usable — and, since React 19, wiring onCaughtError and onUncaughtError on the root so every boundary hit is reported with the component stack rather than swallowed. On the server, onError during streaming lets you decide whether a failed boundary means “send the shell without it” or “fail the response”. The rule I now use: any component that reads user, time or third-party data gets its own boundary.

04The React 18 to 19 upgrade

tier · senior → staff archetype · migration / version upgrade

EXAMPLE — replace with your own

An application of roughly 1,900 components, 60-odd internal packages and a UI library we did not own, sitting on React 18.2 about a year after 19 shipped. The pressure was not novelty: two dependencies had dropped 18 support, and our hiring pipeline kept producing people who wrote use and Actions by reflex. I owned the upgrade end to end and treated it as three separate pieces of work — deprecation cleanup on 18, the version bump, then adoption of the new APIs — because bundling them is how upgrades become quarter-long death marches.

Phase one was done entirely on 18.3.1, which exists precisely for this: it is 18.2 plus warnings for everything 19 removes. We fixed what it shouted about — string refs, defaultProps on function components, legacy context, ReactDOM.render in three old entry points, propTypes that nobody read since we were on TypeScript, and react-test-renderer in 140 tests. The official codemods did most of it; the residue was human. That phase took nine days and shipped in eleven small PRs, all on 18, all releasable.

Phase two, the bump itself, took an afternoon of build fixes and two weeks of canary. The real surprises were not in React: our UI library forwarded refs through a wrapper that assumed ref was not in props, which 19 changed by making ref a normal prop for function components; and a test helper depended on act being importable from react-dom/test-utils, which moved. StrictMode’s development-only double invocation caught two effects that were not idempotent — a duplicate analytics call and a WebSocket connected twice — and both were real bugs that would have bitten us in production later.

Phase three we deliberately did not do at once. We wrote a short “new code uses these, old code is not rewritten” note, enabled the new lint rules, and let the new APIs arrive with features. Numbers: bundle down 11KB from dropping our form-state helper in favour of Actions, and the upgrade shipped with one incident — a lazily loaded route whose ref forwarding broke on a component nobody had tested, caught in canary at 2% traffic.

What I would do differently: I under-communicated to the four teams whose libraries we changed. Two of them found out from a failing build. A one-page note and a fifteen-minute demo before the bump would have cost nothing and bought a lot of goodwill.

What the interviewer is really probing. Whether you can run a change that touches everything without stopping product work: sequencing, reversibility, canaries, and how you handled dependencies you do not control. At staff level they listen for how you got other teams to move.

The mistake candidates make. Describing the upgrade as a technical checklist with no risk management, or claiming it was painless. Also common: not knowing why the removals happened, which turns into a shallow answer the moment they ask “why did React remove string refs?”

(d) Follow-up drill chain

Why did React remove string refs and defaultProps on function components?

Both were features the modern architecture could not support cleanly. String refs need a mutable “current owner” during render, which is hostile to concurrent rendering and to any future where components can be interrupted or re-entered; they also cannot be typed or composed. defaultProps on function components required React to resolve props at element creation, which costs on every element and duplicates something the language already does with default parameters. Both had had documented replacements for years — callback refs and default parameters — so the removals were the end of a long deprecation, not a surprise.

What broke that you did not expect?

Everything outside React. Our own components were mostly fine; the failures were a UI library forwarding refs through a wrapper that assumed ref was separate from props, a test utility import that moved, and a server-side rendering helper that depended on the exact shape of a React internal. The lesson I now apply: budget the upgrade by dependency count, not component count, and audit anything that touches React internals, refs or test utilities first.

At what codebase size does this approach stop working?

The phased approach scales fine; what stops scaling is a single-version monorepo where the bump is atomic across hundreds of teams. Past that point you need either a compatibility period with two React versions in separate deployables — which has its own costs, see the micro-frontend story — or an org-level migration with a deprecation clock and a team funded to do it. The decision hinge is whether you can canary a subset of traffic on the new version; if you cannot, phase one becomes much more important because you must be right the first time.

What did you trade away by not adopting the new APIs immediately?

Consistency, for a while. Two ways to write a form lived side by side for months, and code review had to tolerate both, which is a real tax on newcomers. I judged it the cheaper trade than a mass rewrite with no user-visible benefit and a large regression surface — rewrites of working code have to earn their risk. The compromise was that anything we touched for other reasons got migrated, so the old pattern decayed naturally.

How would you do the 19.2 adoption differently now?

I would lead with the two APIs that delete code rather than add it: useEffectEvent, which kills the “ref holding the latest callback” pattern that appears in every mature codebase, and <Activity>, which replaces hand-rolled keep-alive logic for tabs and wizards. Both are small, mechanical and demonstrably safer than what they replace, so they build credibility for the larger changes. I would also turn on eslint-plugin-react-hooks v6 with its compiler-powered rules early, because it finds the code that will fight you later.

(d) Follow-up drill chain

Why is caching server data in a reducer worse than in a query library?

It is not worse in principle — it is worse in practice because you inherit the whole cache problem and solve it ad hoc. A query library gives you request deduplication, stale-while-revalidate, retry with backoff, cache lifetime and invalidation keys as declarative concerns; in a reducer each of those becomes bespoke code in a thunk, written slightly differently by each engineer. The moment you have two screens showing the same entity, you need invalidation, and that is where hand-rolled caches produce the “I updated it and the other tab still shows the old value” bugs.

Where does this split break down?

Offline-first and collaborative editing. When the client is allowed to make durable changes while disconnected, the client copy is not a cache any more — it is a replica with its own truth, needing conflict resolution, and then a normalised local store with an outbox is genuinely the right shape. Real-time collaborative documents are the same: CRDT or OT state does not belong in a query cache. I would also not use a query library for a high-frequency stream; that is the external-store case from the dashboard story.

Does RSC change this answer?

It changes where the fetch happens, not what state is. With Server Components the read path can move to the server entirely, so the client never holds a cache for that data, and a mutation plus revalidation replaces invalidation logic. What remains client state is exactly what always was: selections, drafts, optimistic UI — which is why useOptimistic exists. In a hybrid app you end up with three tiers rather than two, and the discipline is to be explicit about which tier a given piece of data is in.

Two deliberate things. I stated his design’s strongest point out loud, in the review, before I raised objections — normalisation genuinely is faster on repeat reads and he was right about that. And when we chose the split, I asked him to own it and present it to the wider group, so the outcome was not “the lead overruled him” but “he built the thing we agreed on”. He is the person people ask about data fetching now, which is the outcome I actually wanted.

Commit, and instrument. I would have asked for one guardrail — a lint rule or code-review convention forcing every mutation to declare what it invalidates — and a review date with an agreed signal: if stale-data tickets stayed above some threshold for a quarter, we revisit. Disagree and commit is only credible if you also define what would count as evidence you were right, and then genuinely accept the answer.

06The stale closure that ate the socket

tier · mid → senior archetype · nasty debugging session

EXAMPLE — replace with your own

A support chat widget that dropped messages — but only sometimes, only for agents handling more than one conversation, and never in development. About one message in forty vanished: the sender saw it delivered, the recipient never rendered it. Two engineers had looked at it, found nothing, and added a “refresh if messages look wrong” button, which is the kind of workaround that tells you the team has stopped believing it can be found.

I got it by instrumenting rather than reading. I logged every WebSocket open, close and message with a connection id and the conversation id the handler believed it was for, and shipped that behind a flag to the agents who complained. Within an hour the pattern was unmistakable: after an agent switched conversations, incoming messages were being appended to the previously selected conversation. The socket was fine. The handler was closed over an old value.

The effect subscribed once on mount — an empty dependency array, chosen deliberately to avoid reconnecting on every render — and its message handler referenced selectedId from the render in which it was created. That value never updated, so every message after the first conversation switch was filed under the wrong id, and the UI showed nothing because it was rendering a different conversation. In development it never reproduced because our seed data had one conversation and StrictMode’s remount happened to re-create the handler with the current value before anyone switched.

// The bug: the handler is created once and captures the first selectedId forever.
useEffect(() => {
  const socket = connect(roomUrl);
  socket.on("message", (m) => appendTo(selectedId, m));  // ← stale after the first switch
  return () => socket.close();
}, []);                                                   // ← lying dependency array

// The 19.2 fix: the effect depends on the connection, the event reads the latest values.
const onMessage = useEffectEvent((m) => appendTo(selectedId, m));
useEffect(() => {
  const socket = connect(roomUrl);
  socket.on("message", onMessage);   // effect events are not reactive: no reconnect on selection change
  return () => socket.close();
}, [roomUrl]);

Before 19.2 the honest fix was a ref holding the latest callback, updated in an effect — a pattern every mature codebase has three copies of, all slightly different. useEffectEvent, stable in 19.2, is that pattern given a name and enforced by the lint rule: the event always sees the latest props and state, and it does not become a dependency, so the socket reconnects only when the URL changes. The deeper lesson I made the team internalise is that the dependency array is not a performance knob — it is a claim about what the effect depends on, and lying to it produces exactly this bug.

Fix shipped, message loss went to zero over a fortnight, and the “refresh” button was deleted. What I would do differently: the flag-gated instrumentation should have been step one, not step three. I spent a day and a half reading code and reasoning about race conditions when ninety minutes of production logging answered it.

What the interviewer is really probing. Debugging method under uncertainty: can you form and kill hypotheses, do you reach for evidence over intuition, and do you understand closures well enough to explain the failure rather than describe it. They also listen for how you handled the two people who had already failed to find it.

The mistake candidates make. Narrating a random walk — “I tried this, then that, then it worked” — with no hypothesis, and skipping the part where they explain the underlying mechanism. On this archetype, vagueness reads as “someone else found it”.

(d) Follow-up drill chain

Explain the stale closure precisely — why does the handler not see the new value?

Each render creates new function objects that close over that render’s props and state; those bindings are constants for that render. An effect with an empty dependency array runs its setup once, so the handler it registered belongs to the first render and its selectedId is frozen at that render’s value. Nothing updates it, because there is no “live” link back to component state — React state is not a mutable box you read through, it is a value per render. That is also why the correct mental model of the dependency array is “inputs this effect closed over”, not “when should this re-run”.

Why not just add selectedId to the dependency array?

Because the effect’s cleanup closes the socket, so every conversation switch would disconnect and reconnect — reconnect storms, lost in-flight messages, and server load proportional to UI interaction. That is the tension useEffectEvent resolves: it separates the reactive part of the effect (the connection, which genuinely depends on the URL) from the non-reactive part (what to do when a message arrives, which should always use the latest state). Before it existed, the ref-with-latest-callback pattern did the same thing without a name or lint support.

At what scale does this class of bug get expensive?

It is not about traffic, it is about session length and interaction count: bugs of this shape only manifest after the user changes something the effect captured, so long-lived sessions with lots of switching — agent tools, trading screens, admin consoles — surface them constantly, while a page users load and leave never will. That is exactly why our test data hid it, and why I now insist that any long-session product has a “work here for an hour” test scenario rather than only per-page tests.

What did you trade away with the fix?

Effect events cannot be passed around freely — you cannot pass one to another component or call it from outside the effect that uses it, and the lint rule enforces that. That constraint is the point; it stops the escape hatch becoming a new global mutable channel. The cost is that a couple of our helpers had to be restructured rather than mechanically converted, and anyone who learned the old ref pattern had to unlearn it.

How do you stop the whole class of bug, not just this instance?

Turn the exhaustive-dependencies lint rule to an error and stop suppressing it — the majority of stale-closure bugs I have seen were preceded by a suppression comment. Then teach the two legitimate escape hatches (effect events, and refs for genuinely mutable non-render values) so people have somewhere to go when the rule is inconvenient. And review effects specifically: an effect with an empty dependency array that references props or state is a code smell worth a comment in every review.

07120k rows and a frozen tab

EXAMPLE — replace with your own

A reconciliation screen where an analyst compares two ledgers. It was built for a few thousand rows and the largest customer arrived with 120,000. Opening the screen froze the tab for eleven seconds — the browser’s “page unresponsive” dialog appeared — and after that, sorting a column froze it again for six. The feature request as filed was “make the table faster”. The real requirement, once I sat with two analysts for an hour, was narrower and much more achievable: they never read 120,000 rows; they filter to a few hundred exceptions and work those.

Three things were happening. We rendered every row as a React element, so React built 120,000 fibres and the DOM held about 900,000 nodes; we did the sort and the filter synchronously inside the render pass; and each row was a component with six children and an inline style object. The first is the classic virtualisation case. The second is what makes people wrongly conclude React is slow — the work was ours, not React’s.

The fix, in order: virtualise so only visible rows plus overscan exist — about 40 elements instead of 120,000 — using a windowing library rather than writing one, because the sharp edges are scroll anchoring, variable row heights and accessibility, and I had no appetite for owning them. Then move sorting and filtering off the render path: the comparison itself into a Web Worker that returns an index array, and the resulting UI update wrapped in startTransition so the filter input never blocks. Finally, keep the rows cheap — stable props, no inline object literals, and no context reads inside the row.

// Urgent: the text the analyst typed. Non-urgent: the 120k-row recompute.
function Exceptions({ rows }) {
  const [query, setQuery] = useState("");
  const [view, setView] = useState(rows);

  function onChange(e) {
    setQuery(e.target.value);                    // urgent — commits immediately
    startTransition(async () => {
      const next = await worker.filter(e.target.value);  // off the main thread
      startTransition(() => setView(next));      // 19: transitions may be async
    });
  }
  return <><input value={query} onChange={onChange} /><VirtualRows rows={view} /></>;
}

Numbers: first paint of the screen 11s → 400ms, sort 6s → 90ms of main-thread time with the work in the worker, and peak memory for the tab from 1.4GB to 210MB. The accessibility consequence was real and I want to be honest about it: virtualised rows are not in the DOM, so screen-reader users cannot navigate the full table and browser find-in-page stops working. We added an explicit “export current view” and a server-side search to compensate, and I would count that as a partial answer, not a solved problem.

What I would do differently: I would have gone to the analysts first. A week of engineering went into making 120,000 rows fast before anyone established that nobody wants to look at 120,000 rows — server-side pagination with good filters would have been a smaller, better product answer, and virtualisation would then have been a nice-to-have rather than the whole plan.

What the interviewer is really probing. Whether you scale the requirement, not just the implementation, and whether you know which costs are React’s and which are yours. Naming the accessibility trade-off unprompted is a strong senior signal.

The mistake candidates make. Saying “I used virtualisation” as though it were the whole answer, and never mentioning that windowing breaks find-in-page, screen readers and print. Also: no numbers for memory, which is usually the constraint that actually bit.

(d) Follow-up drill chain

Why is a large table slow in React specifically?

Mostly it is not React-specific: 900,000 DOM nodes are slow in any framework, and layout and style recalculation dominate. React adds its own per-element cost — a fibre per element, a props comparison per update, and a commit pass — which is small individually and enormous at six figures. The React-specific trap is that a single synchronous render of that size cannot be interrupted, so concurrent features do not save you; you must reduce the number of elements, not reschedule them.

Why a transition rather than a debounce?

A debounce delays the work by a fixed guess and still blocks when it runs. A transition marks the update as non-urgent, so React keeps the previous list on screen, commits the urgent keystroke immediately, and can abandon an in-progress transition render if the user types again — the work is interruptible, not merely postponed. In practice I use both: the transition for responsiveness and a small debounce before hitting the network. useDeferredValue is the same tool when you have a value rather than a setter.

At what point would you refuse to do this in the browser at all?

When the data no longer fits comfortably in a tab’s memory budget — a few hundred megabytes of parsed objects is the practical ceiling before garbage collection pauses become visible — or when the operations users need are genuinely set-based, like grouping and aggregation across the whole ledger. At that point the honest architecture is server-side query with pagination and a fast filter endpoint. My line is roughly: tens of thousands of rows, client-side is defensible; hundreds of thousands, you are building a database badly.

What did the virtualisation cost you?

Find-in-page, screen-reader traversal of the whole table, print, and the browser’s own scroll restoration — all of which assume the content is in the DOM. We mitigated with a server-side search that jumps and highlights, an export, and correct ARIA row/column counts so assistive technology at least knows the true size. I would not claim it is equivalent; for a compliance-sensitive product I would push harder for pagination, which is accessible by construction.

How does this connect to your other performance work?

Same principle, different lever. The dashboard story was about fan-out — too many components reacting to one change — and this one is about volume: too many elements for one change. Both are solved by reducing work rather than memoising it, and both are diagnosed the same way: look at the commit in the Profiler or the Scheduler track, and ask whether the problem is one long commit or many small ones.

EXAMPLE — replace with your own

Reviewing a pull request for a comments feature, I found dangerouslySetInnerHTML fed with server-stored HTML that users had authored in a rich-text editor. The author’s reasoning was reasonable on its face — the editor produced HTML, the API stored HTML, so the client rendered HTML — and sanitisation “happened on the way in”. That escalated it properly, because a working proof of concept moves a conversation from opinion to incident. The severity was real: comments were rendered on a page where an admin could be viewing another user’s content while holding a session with elevated rights, so the payload could act as that admin. We treated it as a security incident rather than a bug — audit of stored content for existing payloads (we found none, which is luck, not diligence), a fix, and a disclosure note to the security team.

The fix had three layers, because sanitisation alone is a single point of failure. Server-side, we stopped storing HTML and started storing a structured document format the editor could round-trip, rendering it to React elements at read time — no HTML string ever crosses the boundary. Where legacy content still existed, we sanitised on output with a maintained library and an allowlist, not a denylist. And we added a Content-Security-Policy with no unsafe-inline so that even a successful injection has nowhere to execute.

// Dangerous: trusts stored HTML, and "sanitised on input" ages badly.
<div dangerouslySetInnerHTML={{ __html: comment.html }} />

// Safer: render a structured document to elements — React escapes text by default.
function Rich({ node }) {
  switch (node.type) {
    case "text":   return node.value;                       // escaped, always
    case "link":   return <a href={safeHref(node.href)}>{node.children.map(render)}</a>;
    case "strong": return <strong>{node.children.map(render)}</strong>;
    default:       return null;                             // allowlist: unknown nodes are dropped
  }
}
// safeHref rejects anything but http/https/mailto — javascript: URLs are the other React XSS vector.

The part I care about most is what I did in the review. I did not comment “this is an XSS, please fix”; I paired with the author for an hour, walked through why input sanitisation is the weaker position (content outlives the sanitiser, and every new editor feature reopens the hole), and let him write the fix. He then gave the team a fifteen-minute walkthrough. We also added a lint rule flagging dangerouslySetInnerHTML so every future use is a deliberate, reviewed exception rather than a quiet one.

(d) Follow-up drill chain

What does React actually protect you from?

Exactly one thing, reliably: text interpolated into JSX is escaped, so {userInput} cannot become markup. It does not sanitise attribute values in any semantic sense — href={"javascript:…"} renders and, depending on version and context, may warn but is fundamentally your problem — and it deliberately hands you dangerouslySetInnerHTML, named to be uncomfortable. Anything reaching the DOM as HTML, any URL, any inline style string, and anything passed to a third-party component that renders HTML internally is outside the guarantee.

Why is sanitising on input weaker than on output?

Because stored content outlives the sanitiser and the assumptions it was written under. Content sanitised by last year’s rules is still in the database when this year’s browser adds a new attribute or your editor gains a feature; and any other write path — an import, an admin tool, a migration, a bug — bypasses the check entirely. Output sanitisation runs with today’s rules against every render, and it composes with a CSP. The strongest version is not sanitising at all: store structure, not markup, and never construct HTML from user data.

Does RSC change your threat model?

It adds a boundary that is easy to leak across. Anything passed as a prop from a server component to a client component is serialised and sent to the browser, so a convenient <Profile user={user} /> can ship the password hash and internal flags in the payload. React has experimental taint APIs for objects and values that make the framework throw if a marked value crosses the boundary, and I would pair that with the discipline of passing explicit fields rather than whole records. The other change is that server components run with server credentials, so an injection there is far more serious than one in the browser.

At what scale does this need to become a process rather than a review?

The moment more than one team can add a render path — so, in practice, almost immediately. Human review does not scale and does not survive turnover: the durable controls are a lint rule that makes the dangerous API an explicit exception, a CSP that removes the payoff, dependency scanning for the sanitiser, and a periodic grep in CI. I would rather have three mechanical controls than a strong review culture, because the mechanical ones still work on the Friday afternoon someone is rushing.

What would you do differently in how you raised it?

I would separate the two conversations more cleanly. The security escalation needed to happen immediately and formally; the teaching conversation with the author was better an hour later, in private, without the incident pressure. Doing both at once put him on the defensive for the first ten minutes, which cost time and goodwill I did not need to spend.

09Paying down class-component debt

EXAMPLE — replace with your own

About 380 class components left over from a 2017 codebase, including a base class every screen extended that did data loading, error handling and analytics in componentDidMount. It was not causing outages. What it was causing was a tax: new engineers could not reuse anything, the base class fought code splitting, and two React features we wanted — Suspense for data and concurrent transitions — do not work well with the legacy lifecycles, because componentWillReceiveProps-era assumptions about a single synchronous render are exactly what concurrency breaks.

(d) Follow-up drill chain

Why convert at all, if the class components worked?

Because of what they blocked, not what they were. The legacy lifecycles assume a render pass that runs once and commits, which is precisely the assumption concurrent rendering breaks — a component can render, be discarded, and render again. Class components still work in React 19 and are not deprecated, so “classes are old” is not an argument. getDerivedStateFromProps combined with setState callbacks. Both encode “do something after this specific update commits”, which hooks deliberately do not offer. When the remaining files are exactly the ones nobody touches — the tail is by construction the code with no active work — and when the two worlds cost more than the conversion. The no-behaviour-change rule, enforced in review: a conversion PR that also fixes something gets split. 10Teaching a team what effects are for

tier · senior → staff archetype · mentoring / levelling up

EXAMPLE — replace with your own

A mid-level engineer joining from an Angular background wrote correct, working code that was full of effects: an effect to compute a derived total when items changed, an effect to reset a form when the selected record changed, an effect to call the parent’s onChange when local state moved, an effect to sync a prop into state. It all worked, and it produced double renders, a flash of stale UI on every selection change, and one genuine infinite loop that a colleague fixed by removing a dependency — which is how a small misunderstanding becomes a codebase-wide pattern.

The wrong move here is a code-review comment saying “you don’t need an effect”. I have made that mistake; it teaches a rule, not a model, and the person then guesses. What worked was one hour of pairing on his own code, where I asked a single question of each effect: what external system are you synchronising with? Effects exist to step outside React — a socket, a browser API, a subscription, an analytics SDK, a third-party map. If the answer is “nothing, I’m computing something from props and state”, it belongs in render; if it is “I’m responding to the user clicking”, it belongs in the event handler.

// Three effects that should not exist:
useEffect(() => { setTotal(items.reduce(sum, 0)); }, [items]);        // derived → compute in render
useEffect(() => { onChange(value); }, [value]);                       // event → call it in the handler
useEffect(() => { setDraft(record); }, [record]);                     // reset → use a key instead

// What each becomes:
const total = items.reduce(sum, 0);                                   // cheap; memoise only if measured
function handleChange(next) { setValue(next); onChange(next); }       // one place, one render
<Editor key={record.id} record={record} />                            // identity change resets state

// A real effect: synchronising with something outside React.
useEffect(() => {
  const map = createMap(node.current, { center });
  return () => map.destroy();
}, [center]);

We turned the session into three artefacts, which is what made it stick beyond one person: a fifteen-minute team talk he gave (teaching is the fastest way to consolidate), a checklist in the pull-request template with the single question above, and the exhaustive-dependencies lint rule promoted from warning to error, with the agreement that a suppression comment needs a reason next to it. Within two months, effects per new screen dropped from around nine to two, and the “flash of stale content on selection” bug class disappeared because most of those effects had been reset-state-on-prop-change in disguise.

The measurable outcome I care about is not the effect count — it is that he became the person who taught this to the next two joiners, and was promoted eight months later. What I would do differently: I framed the first conversation around what was wrong before establishing what was right. Starting with the model — “effects are an escape hatch to leave React” — and then looking at his code would have taken the same hour and felt entirely different.

What the interviewer is really probing. Whether you scale yourself: did the teaching outlive the conversation, and did the person grow rather than merely comply. At lead level they want a mechanism — a rule, a template, a talk — not just good intentions.

The mistake candidates make. Mentoring stories where the mentee is a passive recipient and the mentor is the hero, and stories with no outcome for the person (promotion, ownership, teaching others). Also: describing what you told them, never what you asked.

(d) Follow-up drill chain

Give me the one-sentence rule for when an effect is correct.

An effect belongs where React needs to synchronise with something outside React that cannot be expressed as rendering — a subscription, a browser API, an imperative library, a network connection — and the cleanup must be able to undo it. Everything else is either derived data, which belongs in render, or a response to a user action, which belongs in the event handler. The test I give people: if you deleted the effect, would something outside React be left in the wrong state? If not, it should not be an effect.

Why is “set state in an effect when a prop changes” usually wrong?

Because it stores a second copy of a value that already exists, and copies drift. Mechanically it also costs an extra render pass: React renders with the stale value, commits, runs the effect, sets state, and renders again — which is the flash users see. The two correct alternatives are computing the value during render, or, when a component genuinely should reset, changing its key so React unmounts and remounts it with fresh state. That second one is the trick most people have not internalised, and it deletes a lot of code.

How do you teach this without making someone defensive?

Ask rather than assert, and use their code rather than a toy example, because the model has to survive contact with their real problem. I also say out loud that the code works — because it does — so the conversation is about cost, not correctness. And I try to give the person the artefact: they write the checklist item, they give the talk. People defend what they authored and resent what they were handed.

At what team size does pairing stop scaling?

Around ten to fifteen engineers, in my experience, and much earlier across time zones. Past that I invest in the artefacts that teach without me: lint rules that explain themselves, a short written “how we build screens” with worked examples, a review rota that spreads the knowledge rather than concentrating it in me. The failure mode of a strong lead is becoming the single point of review; the metric I watch is what fraction of reviews I am on, and I want it falling.

What would you do if the person did not improve?

Separate can’t from won’t, quickly and in writing. If it is a knowledge gap, change the medium — some people learn from docs, some from pairing, some from being handed a well-scoped piece of work with a safety net. If the pattern persists after clear feedback and support, it becomes a performance conversation with their manager, with specific examples and dates, and I would not let that drift: being vague to be kind is neither.

EXAMPLE — replace with your own

Two things were true at once: a contractual launch date eleven weeks out for a new customer-facing product area, and a component library that was half-finished, inconsistent between the two teams using it, and inaccessible in three specific ways our compliance review would eventually catch. Why is accessibility in the “expensive to change” bucket?

Because it is not a layer you add on top — it is structure. Focus order, roles, labelling and keyboard interaction come out of the DOM shape and the component API, so fixing them later means changing markup that every consumer has styled and every test has selected against. The hard part of these components is behaviour, not appearance: focus trapping, typeahead in a listbox, ARIA relationships, pointer and keyboard parity, and the long tail of assistive-technology quirks. That is expensive to write and expensive to keep correct. A full component library solves it too but couples your visual design to someone else’s decisions and is hard to escape. Headless primitives let us own styling completely and rent the behaviour, and the exit cost is bounded because our own API sits in front of theirs.

At what point would you have said the date was impossible?

When the remaining scope, after every trade I could offer, still exceeded the capacity — and I would say it early, with the arithmetic, not late with an apology. The threshold for me is when meeting the date requires skipping something irreversible: shipping an inaccessible flow to real users, or a data model we would have to migrate. Those are not trades, they are damage, and I would escalate rather than absorb them.

Badly at first — I treated it as non-compliance. What would you tell a team about to start a design system today?

Start from real screens, not from a component inventory — the components you actually need are always fewer and stranger than the ones you imagine. Version and document from day one so consumers can upgrade at their own pace. And treat it as a product with users, meaning: a roadmap, a way to contribute, and a support commitment. Systems die from being unmaintained far more often than from being poorly designed.

12Optimistic updates that lost work

tier · senior → staff archetype · data-loss scare

EXAMPLE — replace with your own

An internal editor where users write long structured notes. We had made saving optimistic — the UI showed “saved” immediately and reconciled with the server in the background — because the round trip was 600ms and the constant spinner felt awful. Three weeks later a user reported losing forty minutes of work. Then two more. This is the worst category of bug I have dealt with, because the product is telling the user a lie: it said saved.

The mechanism took a day to establish and was a combination, as these always are. The optimistic update applied locally and fired the request; if the request failed — and on a flaky office wifi it failed maybe 0.5% of the time — we rolled the UI back to the server state, which discarded whatever the user had typed since, because the rollback replaced the whole document rather than the failed delta. Worse, our retry closed over the request payload from the failed attempt, so a successful retry could write an older version over a newer one. Two users had, in effect, been overwritten by their own retry.

I treated it as an incident even though nothing was “down”: quantify exposure first. We had server-side revision history, so I could count documents where a revision was followed by a smaller one within a minute — 31 documents, 6 users, and we could restore all of them, which turned a catastrophe into an apology. That restore, done within a day, mattered more to those users than the fix.

// The 19 shape: an action owns the request; useOptimistic owns the temporary view.
const [optimisticNotes, addOptimistic] = useOptimistic(notes, (state, patch) => applyPatch(state, patch));

async function save(patch) {
  addOptimistic(patch);                 // shown immediately; reverts automatically when the action ends
  const result = await saveNote({ baseRevision: notes.revision, patch });   // ← version, not whole doc
  if (result.conflict) setConflict(result);   // surface it; never silently discard the user's text
}

The redesign had four parts. Send deltas against a base revision so the server can detect a conflict instead of last-write-wins. Never roll back to a server value without merging in anything the user typed since — and if we cannot merge, show a conflict UI rather than choosing for them. Keep an outbox in IndexedDB so unsent changes survive a reload or a crash. And be honest in the UI: “saving”, “saved”, and “not saved — retrying” are three different states, and collapsing them into an optimistic “saved” is a product decision with a data-loss failure mode attached.

What I would do differently: I would have asked “what does the user lose if this lies?” when we designed the optimistic save. Optimistic UI is correct for cheap, idempotent, low-stakes actions — a like, a reorder, a toggle. For a user’s authored content, the bar is much higher, and I approved it without applying that distinction.

What the interviewer is really probing. How you behave when users lost something: do you quantify exposure, communicate honestly, and fix the design rather than the symptom. Ownership without self-flagellation is the tone they are listening for.

The mistake candidates make. Minimising (“only a few users”), or making it a pure engineering story with no mention of telling the affected people. Also: not knowing whether the data was actually recoverable, which is the first question any interviewer asks.

(d) Follow-up drill chain

When is optimistic UI the right call?

When the action is cheap, idempotent, easy to retry, and the user can trivially see and redo it if it fails — likes, toggles, reordering, adding a tag. The moment the action carries authored content, has side effects the user cannot observe, or is not idempotent, the calculus changes: the latency win is small compared to the cost of being wrong. useOptimistic makes the mechanics easy, which is exactly why the judgment call matters more now than it did when you had to hand-roll it.

Why did the rollback lose data, precisely?

Because it treated the server’s copy as the truth for the whole document rather than for the specific failed change. Optimistic state is conceptually a stack of pending patches on top of a base; unwinding one patch should leave the others intact. We replaced the base and dropped the stack, so everything typed during the in-flight request vanished. useOptimistic models this correctly — the optimistic value is derived from the real state plus pending updates and reverts when the action settles — but it cannot save you if your patches are whole-document snapshots.

At what scale does last-write-wins stop being acceptable?

The moment two writers can exist, which includes one user with two tabs — far earlier than most teams assume. Below that, versioned writes with conflict detection are enough and cost almost nothing: a revision number and a 409. Above genuine concurrent editing, you need either operational transforms or CRDTs, and that is a large architectural commitment I would not make without the product actually requiring collaboration. The middle ground — detect and ask the human — is underrated and was right for us.

What did the offline outbox cost you?

Complexity in exactly the places that are hard to test: storage quota, schema migration of queued items when the app updates, ordering guarantees, and the question of what to do with a queued change that is now invalid because the document changed underneath. We time-box entries and surface anything unsendable to the user rather than silently dropping it. It is genuinely more machinery than the feature seems to deserve, and I would only build it again for content the user authored.

How did you communicate with the affected users?

Directly, by name, from a person rather than a no-reply address, within a day: what happened, what we recovered, what we could not, and what changed. I wrote the note and my manager reviewed it — I would not delegate that. The reaction was almost entirely positive, which surprised me at the time and no longer does: people forgive a mistake that is owned quickly and are unforgiving about silence.

13A form spec that would not sit still

tier · mid → senior archetype · ambiguous / shifting requirements

EXAMPLE — replace with your own

An onboarding flow for a regulated product. The brief was “five steps, we know what they are”. Over eleven weeks the steps became seven, then six, one became conditional on a country, two fields moved between steps, and the validation rules changed three times because legal was still reading a regulation while we built. The team’s frustration was reasonable and the conclusion they reached — “product does not know what they want” — was the wrong one to act on. What was actually happening was that the requirements genuinely could not be known yet; the regulator’s guidance did not exist in final form.

So I stopped trying to pin down the spec and changed what we were building. The question I put to the team was: what is stable here? The answer was the mechanics — a step is a set of fields, fields have types, some fields are conditional, validation happens per step and again at submit, progress must survive a refresh. What was volatile was the content: which fields, in which order, with which rules. That is a configuration problem wearing a code costume.

We built a small step engine: a schema describing steps and fields, a validation layer driven by that schema, and generic React components rendering field types. Crucially we did not build a general-purpose form framework — the temptation was enormous — we built exactly the field types the flow needed, six of them, with an explicit rule that a seventh required a conversation. The engine took nine days; each subsequent requirement change took hours instead of days, and two of them were made by the product manager directly in the schema with an engineer reviewing.

// Uncontrolled + Actions: the DOM holds the values, React holds the result.
function Step({ schema }) {
  const [state, formAction, pending] = useActionState(submitStep, { errors: {} });
  return (
    <form action={formAction}>
      {schema.fields.map((f) =>
        visible(f, state.values) && <Field key={f.name} field={f} error={state.errors[f.name]} />)}
      <button disabled={pending}>{pending ? "Checking…" : "Continue"}</button>
    </form>
  );
}

The technical choice that saved us most: fields are uncontrolled by default, with values read from the form on submit, and only the genuinely interactive ones — the conditional trigger, the formatted account number — controlled. A fully controlled form of 40 fields re-renders the whole step on every keystroke, and with React 19 Actions the uncontrolled path is now the ergonomic one too: useActionState holds the result and errors, useFormStatus gives nested buttons their pending state without prop drilling.

Result: eleven weeks of moving requirements absorbed without a slip, and the flow shipped with a completion rate of about 71% against a target of 60%. What I would do differently: I would have negotiated a “decision deadline” with legal at the start — a date after which changes go to the next release — because we absorbed the churn so gracefully that nobody felt the cost, and the team paid for it in context switching that never showed up in any plan.

What the interviewer is really probing. How you operate without a clear spec: do you go quiet and build the wrong thing, escalate blame, or change the design so uncertainty is cheap. They also want to see you distinguish “unknowable yet” from “unmanaged”.

(d) Follow-up drill chain

Controlled or uncontrolled — how do you decide?

Default to uncontrolled and let the DOM own the value; reach for controlled only when React needs to know the value during typing — live validation, formatting as you type, a field that drives conditional visibility, or a value shared with another component. Controlled means a render per keystroke, which is fine for five fields and painful for forty. React 19’s Actions push you toward uncontrolled by making the submit path ergonomic, and the compiler reduces the cost of the controlled case, but it does not eliminate the re-render.

Where would this schema-driven approach break down?

When the variability stops being data-shaped. Cross-field rules with real logic, multi-step conditional branching, or per-country flows that differ structurally start pushing you toward inventing a programming language in JSON — which is the point to stop and write code. My heuristic: if the schema needs conditionals more expressive than “show when field X equals Y”, or if reading it is harder than reading the equivalent component, the abstraction has failed. We hit that once and dropped back to a bespoke component for one country.

What did you trade away?

Type safety and directness. A schema-driven form is harder to type end-to-end than explicit components, errors move from compile time to runtime, and jumping to the definition of a field means reading data rather than code. We bought some of it back by generating types from the schema and validating the schema itself in CI. It is a real cost, and it only pays when change is frequent — for a stable form, explicit components are simply better.

How did you keep the team from burning out on the churn?

By making the churn cheap and by making it visible. Cheap was the engine; visible was a running list of changes with the date and requester, which I brought to the weekly. Nobody was blamed, but everyone could see eleven changes in eleven weeks, and that number did the negotiating for me when I asked for the decision deadline. Absorbing pressure silently protects the team this week and hurts them next quarter.

Would you use a form library instead today?

For a conventional form, yes — the mature libraries handle uncontrolled registration, validation resolvers and array fields better than I will in a sprint. What they do not give you is the schema-to-UI layer where product edits the flow, and that was the actual requirement here. So the shape I would build now is a thin schema layer over a form library rather than over raw React, which is roughly what we ended up with by the third month anyway.

14Two Reacts on one page

EXAMPLE — replace with your own

Our shell application owned the page; a partner team owned a checkout widget mounted inside it. They were on React 17, we were moving to 19, and the two shipped on different release trains — theirs monthly with a compliance sign-off, ours daily. The proposal I inherited was module federation with a shared React singleton, which requires both sides to agree on a version. That agreement was not achievable in any timeframe that mattered, and pretending otherwise would have made their compliance process our release blocker.

So I designed for the constraint instead of against it. Two React roots, two React copies, no shared runtime: their widget mounted into a DOM node we handed it, with a narrow, versioned message contract between us — events out, commands in, plain serialisable data, no React elements, no shared context, no shared store. We used a custom element as the seam, so their bundle attached itself to a tag and we never imported their code.

Two React copies cost about 45KB gzipped extra, which on a checkout page is not nothing. Events must be serialisable, so we could not pass callbacks or rich objects. function CheckoutSlot({ cart }) {

  useEffect(() => {
    const el = host.current;
    el.dispatchEvent(new CustomEvent("cart:update", { detail: { v: 1, cart } }));

What made it work was not the architecture, it was the contract discipline: a written interface with a version field, a compatibility test suite that both teams ran in their own CI against a recorded fixture of the other side, and a rule that additive changes need no coordination while breaking ones need a deprecation period. We ran that for two years; the widget went to React 18 at their pace and we never noticed.

What I would do differently: I would have set up the shared contract test in the first week rather than the third month. Between those points we had two production incidents caused by a field being renamed, and both were entirely preventable by a test that took a day to write.

What the interviewer is really probing. They will push on the costs — a candidate who cannot name them has not run this.

(d) Follow-up drill chain

What actually breaks when two React copies share a page?

Less than people fear, and in specific places. Each root has its own reconciler, scheduler and context — so context, Suspense boundaries and error boundaries do not cross, and nothing shared through React internals works. Events are the sharp edge: React attaches listeners at the root container, so a synthetic event in one tree does not exist in the other, and portals rendered outside a root can surprise you. Refs to DOM nodes still work because the DOM is shared, which is why a custom-element seam is a good boundary.

Why not module federation with a shared React?

It is the better answer when both sides can move together, and a trap when they cannot. Sharing a singleton means the runtime picks one version; if the partner’s code was built against 17 semantics and gets 19, you find out at runtime, in production, with a stack trace inside a minified vendor chunk. I have debugged that and it is genuinely awful. The 45KB was the price of never having that conversation, and on a checkout page where conversion mattered more than a hundred milliseconds, I would pay it again.

At what point does this architecture stop being worth it?

When the boundary stops matching the org. Micro-frontends buy independent deployment at the cost of duplication and coordination overhead, so they pay off when the teams genuinely are independent and the UI seam is stable. If the two teams merge, or the widget needs deep interaction with the host page — shared modals, shared form state, focus choreography — the seam becomes friction and you should collapse it. I have also seen it fail at four or more widgets on one page: bundle duplication and styling drift compound.

How did you handle accessibility across the boundary?

Explicitly, and imperfectly. Focus restoration after their widget opened a step needed a documented protocol — they emit an event, we decide where focus goes — because neither side can see the other’s DOM intent. Live-region announcements were worse: two independent polite regions can talk over each other, so we agreed they own announcements inside the widget and we suppress ours while it is active. This is the part of micro-frontend architecture nobody writes blog posts about, and it is where the user actually feels the seam.

How would you decide today?

Same question, in order: can the two sides ship on one train? If yes, one app — everything else is worse. If no, is the seam narrow and stable? If yes, separate roots with a versioned contract. If the seam is wide, fix the organisation rather than the architecture, because you will otherwise spend years paying for a boundary that does not match how the work actually flows.

15The RSC migration we stopped

EXAMPLE — replace with your own

We started migrating an internal analytics application — heavily interactive, entirely behind authentication, roughly 300 daily users, all on fast corporate networks — to Server Components. The rationale at kickoff sounded fine: smaller bundles, data fetching close to the database, and alignment with where the ecosystem was going. I supported it. Ten weeks in, I recommended we stop, and we did, with about six weeks of work thrown away and two weeks of it salvaged.

What went wrong was not RSC. It was that we had picked the application where its benefits are smallest and its costs are highest. Nearly every screen was a chart with cross-filtering, brushing and a live-updating grid — interactive to the leaves, so almost everything ended up inside a "use client" boundary anyway. The bundle savings we projected at 40% measured at 9% on the three converted screens. Meanwhile the costs were concrete: every chart library had to be wrapped, our test setup needed a second rendering path, local development gained a server dependency, and two engineers were reliably confused about where code ran — a confusion that produced one real bug where a server component read a database on every keystroke because someone put it under a client component that re-mounted.

The mechanism that let us stop cleanly was set up before we started: three checkpoints with pre-agreed signals — bundle bytes on converted screens, developer cycle time, and defects attributable to the boundary. At the second checkpoint two of the three were red. Without that, we would have argued about vibes and sunk cost, and I am fairly sure we would have continued, because by then three people had built expertise they did not want to waste.

I wrote it up honestly and presented it to the wider engineering group with the numbers, including my own error: I had approved the choice of pilot application because it was the one with the most engineering appetite, not the one where the technology fit. Appetite is a good input for change management and a bad input for technology selection. The salvage was real, though — the data layer we had extracted for the server side became a clean API boundary we kept, and the streaming Suspense patterns we learned went into the customer-facing app six months later, where they were worth it.

16When SSR became the biggest bill

tier · staff → principal archetype · cost optimisation

EXAMPLE — replace with your own

Our rendering tier had quietly become the largest line in the platform bill — more than the database — at roughly $18,000 a month for a site with modest traffic. The trigger for looking was a finance question, not an engineering one, which is often how these start. Nobody had done anything wrong: we had turned on server rendering for good reasons two years earlier and then added personalisation to the header, which made every page uncacheable, one small feature at a time.

I started by asking what we were actually paying for per request. Two things dominated: rendering the same catalogue page for thousands of users because the response varied by a greeting in the header, and a homepage that awaited three API calls before emitting a single byte, so each instance held a connection open for 700ms doing nothing. That framing — cache-blocking personalisation and serial awaits — turned out to be the whole problem.

Three changes. First, we moved personalisation out of the cache key: the header renders a placeholder on the server and the greeting fills in client-side after hydration, which made 94% of catalogue responses cacheable at the CDN for five minutes. Second, we adopted partial pre-rendering — React 19.2’s prerender plus resume — so the static shell of the page is generated at build time and only the dynamic holes are rendered per request; the shell comes from the CDN immediately and the personalised parts stream in. Third, we stopped awaiting everything before the shell: Suspense boundaries around each slow region so the server emits the shell first and streams the rest, which cut instance-seconds per request by more than half because instances stopped blocking on I/O.

(d) Follow-up drill chain

Why does streaming reduce cost rather than just improve perceived speed?

Because on a per-instance-second billing model you pay for time held, not work done. A handler that awaits three sequential APIs occupies memory and a concurrency slot for the whole 700ms while doing nothing. Emitting the shell immediately and streaming Suspense boundaries as data resolves lets the same instance interleave other requests, so throughput per instance rises and you need fewer of them. The user-visible benefit — content appearing sooner — is real but was the secondary effect for us.

What exactly is partial pre-rendering doing?

It splits a render in two. At build time React pre-renders as far as it can and stops at the boundaries whose data is not yet available, producing a static shell plus a resumable state; at request time the server resumes from that state and fills only the dynamic holes. React 19.2 stabilised the APIs for this — prerender to produce the prelude, and a resume step to complete it. The practical effect is that the shell can sit on a CDN with a long TTL while personalised regions stay per-request, so you stop choosing between fully static and fully dynamic per page.

At what traffic level would you have made a different call?

Below a few hundred thousand renders a month, none of this is worth engineering time — the bill is smaller than the salary cost of the work, and I would have said so. Very high traffic pushes further the other way: full static generation with client-side personalisation, or edge rendering close to users. The interesting middle is where we were, where cacheability is the dominant variable and one careless feature can move the bill by five figures.

What did you trade away, honestly?

Three things. A brief generic header, which is a real if small product regression. A build-time dependency for the shell, which means a content change needs a rebuild or a targeted invalidation. And less instance headroom after right-sizing, so a traffic spike now scales out rather than absorbing in place — we mitigated with a lower autoscaling threshold, but it is a genuine reduction in slack, and slack has value on the day something unexpected happens.

How do you stop the cost creeping back?

Make it visible where the decision is made. Cache hit ratio and cost per thousand renders went on the same dashboard as our web vitals, with an alert on hit ratio dropping below 85%, and a note in the pull-request template asking whether a change affects the cache key. That last one sounds trivial and caught two regressions in the following year — a cookie read added to a layout, and an experiment flag that varied the response. The guardrail has to sit at the moment of the change, not in a quarterly review.

17Rolling out React Compiler

EXAMPLE — replace with your own

React Compiler went 1.0 in October 2025, and I proposed adopting it about four months later — deliberately not on day one, because a build-time transform that rewrites every component is not where I want to be an early adopter. The pitch I made was not “free performance”. It was maintenance: our codebase had roughly 900 hand-written useMemo, useCallback and React.memo call sites, most added speculatively, a meaningful fraction with wrong dependency arrays, and every one of them a thing a reviewer had to reason about.

The rollout was boring on purpose, which is the whole skill. Step one was the linter, not the compiler: eslint-plugin-react-hooks v6 ships compiler-powered rules, so we ran them across the codebase in report-only mode to find where our code broke the Rules of React. That found 140 violations, and about 20 were genuine latent bugs — mutation of props, a component reading a mutable module variable during render, conditional hook calls hidden behind an early return. Fixing those was worth the exercise even if we had stopped there.

Step two was enabling the compiler on one low-risk directory with a gate. We measured three things per screen: interaction latency in RUM, bundle size (the compiler adds code, so it is not free — we saw about +3% on the affected chunks), and a snapshot count of renders in our component tests. Step three was expansion by directory over six weeks, with an escape hatch: a "use no memo" directive for the two components where the compiler’s output disagreed with a deliberately mutable pattern we had not yet cleaned up.

// Before: hand-maintained memoisation, and a dependency list that will drift.
const rows = useMemo(() => project(data, columns), [data, columns]);
const onSelect = useCallback((id) => setSelected(id), []);
export default React.memo(Grid);

// After: the compiler memoises at the granularity it can prove is safe.
const rows = project(data, columns);
function onSelect(id) { setSelected(id); }
export default Grid;
// Escape hatch for a component that intentionally breaks the rules:
function Legacy() { "use no memo"; /* … */ }

Results after the full rollout: about 700 of the 900 memoisation call sites deleted, INP at p75 improved by around 8% on the two heaviest screens and did not move measurably on the rest, and — the outcome I actually wanted — code review stopped containing dependency-array arguments. The honest negatives: bundle up ~3%, build time up about 15%, and one production bug where a component mutated an object it received as a prop and had been accidentally relying on re-renders that no longer happened. That bug was a rule violation the linter had flagged and we had waived. I would not waive one again.

What I would do differently: I let the team see the RUM numbers before I had explained what to expect, and the modest result on most screens read as disappointment. The compiler is not a performance product for an already-memoised codebase; it is a maintenance product with a performance tail. Framing that up front would have set the right expectation.

(d) Follow-up drill chain

What is the compiler actually doing?

It is a build-time transform — a Babel plugin, or the equivalent in a bundler’s pipeline — that analyses each component and hook and inserts memoisation automatically, caching values in a hidden per-component slot array so that recomputation and re-renders only happen when inputs actually change. It memoises at a finer granularity than a human would bother with: individual expressions and JSX subtrees, not just whole components. Its correctness depends entirely on the Rules of React holding — no mutation of props or state, no side effects during render — which is why the linter comes first.

When does it make things worse?

Two cases. Code that violates the rules, where memoising can change behaviour — that was our production bug, a component quietly depending on being re-rendered so it could re-read something it had mutated. And bundle-sensitive code, because the generated caching adds bytes; on a landing page where every kilobyte matters I would measure carefully rather than assume. There is also a build-time cost, which matters more in a large monorepo than the numbers suggest, because it lands on every developer every day.

Does it replace useMemo entirely?

Almost, but not for semantic memoisation. If a value must be referentially stable for correctness — an object passed to a third-party library that uses identity as a cache key, or a dependency of an effect where an extra run has real side effects — I still want that written explicitly, because the intent is not performance and I do not want it to depend on what the compiler could prove this month. The rule I gave the team: delete performance memos, keep correctness memos and comment why they exist.

How did you decide it was safe enough?

Three gates. It had been stable for months with major adopters reporting production use — Meta’s own numbers on the Quest Store were the public data point at 1.0. Our linter run gave us a concrete count of how far our code was from the rules, which is a proxy for risk. And the rollout was reversible per directory in a single commit, so the cost of being wrong was hours. If any one of those had been missing I would have waited.

What would make you turn it off?

A pattern of behaviour differences that the linter does not catch, or a build-time cost that pushes our feedback loop past the threshold where developers start batching changes — around a minute for an incremental build, in my experience. I would also turn it off in a heartbeat if it obscured a debugging path we needed during an incident; observability under pressure beats a few percent of INP.

18On-call for a leaking SPA

tier · senior → staff archetype · on-call firefighting

EXAMPLE — replace with your own

Support tickets said “the app gets slower during the day and I have to restart my browser”. Our monitoring said nothing at all, because the server was healthy and our RUM only sampled page loads — and this was a single-page app where a support agent loads the page once on Monday and keeps it open until Friday. That is the diagnostic gap that made this a five-day problem instead of a five-hour one.

I reproduced it by scripting the workday: a Playwright session that opened the app and cycled through 400 conversation switches with the heap snapshot taken every fifty. Memory went from 180MB to 1.6GB across the run, monotonically. Then it was ordinary heap-snapshot work in Chrome DevTools: compare two snapshots, sort by retained size, and look at what is holding the largest objects. The retainer chain pointed at an array of event listeners on a module-level singleton, each closing over a component’s props — which meant components were never being collected.

Two causes, both mundane, both classic. A custom hook subscribed to a global event bus and returned no cleanup, so every mount added a listener that lived forever, holding the entire props object and, through it, the conversation and its messages. And a chart component registered a ResizeObserver it never disconnected, keeping detached DOM nodes alive — the detached-node count in the memory panel was the giveaway, sitting at about 300,000.

// Leak: subscribe with no cleanup — every mount adds a permanent listener.
useEffect(() => { bus.on("conversation", handle); }, []);

// Fixed: the cleanup is not optional; it is what makes the effect correct.
useEffect(() => {
  bus.on("conversation", handle);
  return () => bus.off("conversation", handle);
}, []);
// StrictMode in development would have caught both: it mounts, unmounts and remounts,
// so a missing cleanup shows up immediately as a duplicated subscription.

The fix took an afternoon. The follow-ups took a fortnight and mattered more: StrictMode enabled in development, where it had been switched off years earlier by someone tired of double-logging; a lint rule requiring a return value from effects that call known subscribe APIs; a long-session synthetic test in CI that fails if heap growth over 200 interactions exceeds a threshold; and RUM extended to report memory periodically rather than only on load. Memory over an eight-hour session went from 1.6GB to a stable 240MB, and the tickets stopped.

What I would do differently: I would have taken the qualitative report seriously on day one. “It gets slow, I restart it” is a memory leak until proven otherwise, and I spent two days looking for a server-side or network explanation because that is where our instrumentation was. The lesson I took into the next team was to instrument for the session shape your users actually have.

What the interviewer is really probing. Whether you can work from a vague user report to a mechanism, using tools rather than guesses, and whether your fixes address the class. On-call stories also test judgment about severity: this was not paging anyone, and you have to explain why you prioritised it anyway.

The mistake candidates make. Saying “we had a memory leak, I added cleanup functions” with no method — no snapshot, no retainer chain, no reproduction. Interviewers ask “how did you find it?” and vagueness is fatal here.

(d) Follow-up drill chain

Why does a missing effect cleanup leak, mechanically?

The subscription holds a reference to the handler function; the handler closes over that render’s props and state; those reference the component’s data — so a listener on a long-lived object keeps the whole graph reachable and the garbage collector cannot touch it. Unmounting the component removes it from the tree but not from the external subscriber list, which is precisely why the cleanup exists. The same applies to timers, observers, animation frames, and anything registered on window or a module singleton.

How exactly did you find the retainer?

Two heap snapshots taken at a known-good and known-bad point, compared with the “Objects allocated between snapshot 1 and 2” filter so short-lived noise drops out. Sort by retained size, pick the largest constructor group, and read the retainers panel bottom-up until you hit something that should not be alive — in our case a module-scope array. The detached-DOM count is the fastest complementary signal: if it grows monotonically as you navigate, something is holding nodes, and a ResizeObserver or a listener is the usual suspect.

At what point does a slow leak become an incident?

When it crosses the user’s session length — which is the number that matters, not the leak rate. Ours leaked about 4MB per conversation switch, which is invisible in a ten-minute QA pass and fatal over eight hours. So I judge severity by projecting the rate over the realistic session: if the projection exceeds a couple of gigabytes, you are causing tab crashes and it is a production defect regardless of what the dashboards say. That framing is also how I got it prioritised over features.

Why had StrictMode been turned off, and how did you handle that?

Because double-invoked effects made the development console noisy and someone, reasonably, wanted quiet — the cost of that decision only appeared years later. I did not relitigate the original call; I fixed the noise instead. We made our logging idempotent, cleaned up the effects that double-fired, and turned StrictMode back on in a single PR with the fixes included. Turning a safety mechanism back on without removing the reason it was disabled just gets it disabled again.

How does <Activity> change this picture?

It gives a principled answer to the “keep it alive but idle” pattern that people otherwise hand-roll with hidden divs. A hidden Activity keeps state but unmounts effects, so subscriptions are torn down and re-created when it becomes visible — which means the leak surface of a background panel is the same as an unmounted one, provided your cleanups are correct. It does not fix missing cleanups; it makes the correct pattern cheaper to adopt, and it removes the temptation to keep everything mounted just to preserve scroll position.

19Fixing the flaky React test suite

tier · senior → staff archetype · CI / test reliability

EXAMPLE — replace with your own

A suite of about 4,300 component tests with a 14% flake rate on the main branch. That number is worse than it sounds: at 14%, almost every merge required a re-run, so the team had learned to click “retry” without reading, which means the suite had stopped catching real regressions. Two genuine bugs shipped in the quarter with a failing test in the history, dismissed as flake. That was the argument I used to get time allocated — the suite was not slow or annoying, it was actively lying.

The first job was data. I made CI record every failure with the test name and the error, and after a week 62% of the flakes came from 40 tests. That reframed the project from “fix the test suite”, which nobody funds, to “fix forty tests”, which is a sprint. The failure modes clustered into four kinds, and the deepest one was conceptual rather than technical: tests were asserting on timing rather than on outcomes.

Flake causeShareFix
Arbitrary waits before assertions~40%findBy* / waitFor on a real condition; never a fixed timeout
Unwrapped state updates (act warnings ignored)~25%Use user-event, await it, and treat act warnings as errors
Shared state between tests~20%Fresh query cache and store per test; no module-level fixtures
Real timers and animation~15%Fake timers, and assert on the end state rather than frames
 
// Flaky: a fixed wait, an assertion on an implementation detail, no act coverage.
fireEvent.click(button);
await new Promise((r) => setTimeout(r, 100));
expect(store.getState().items).toHaveLength(3);

// Stable: interact as a user, wait for a real condition, assert what the user sees.
await userEvent.click(screen.getByRole("button", { name: /add item/i }));
expect(await screen.findByRole("listitem", { name: /third item/i })).toBeInTheDocument();

Two policy changes did more than any individual fix. First, a quarantine: a test that flakes twice in a week is automatically moved to a quarantined suite that runs but does not block, with an owner and a two-week clock — this stops the team learning to ignore red. Second, act warnings became failures, which was painful for a week and then permanently removed a class of race. Concurrent rendering makes this stricter, not looser: with transitions and Suspense, “the update has been applied” is genuinely not synchronous with the click, so tests that assumed it were always wrong and merely lucky.

Results: flake rate 14% → 0.4% over six weeks, CI wall time also fell 30% because fixed waits disappeared, and — the real outcome — people started reading failures again. What I would do differently: I would have introduced the quarantine mechanism first, on day one. For the first three weeks we fixed tests while the team continued to ignore red, and the cultural repair only started when red meant something again.

What the interviewer is really probing. Whether you treat test reliability as an engineering problem with data behind it, and whether you understand that flakiness is a trust problem first. They also check whether you know why the flakes happened — a candidate who says “I added waits” has made it worse.

The mistake candidates make. Describing heroic individual fixes with no measurement, or claiming to have deleted the flaky tests. Deleting coverage to fix a signal problem is a red flag unless you can justify each deletion.

(d) Follow-up drill chain

Why do act warnings matter?

Because they mean a state update happened outside the window in which the test framework flushes React’s work, so your assertion may run against a tree React has not finished updating — the test passes or fails depending on timing. The fix is almost never to wrap more things in act manually; it is to await the interaction, since user-event and the async queries already handle flushing. React 19 moved the canonical act into the react package as part of retiring react-dom/test-utils, which is worth knowing if you maintain test helpers.

Why is a fixed wait worse than no wait?

Because it encodes a machine’s speed into an assertion. On a fast local machine 100ms is generous; on a loaded CI runner it is not, so the test fails for reasons unrelated to the code. And it makes the suite slower in exact proportion to how safe you try to make it. Waiting on a condition — the element appears, the text changes — is both faster and correct, because it terminates as soon as the thing you actually care about is true.

At what point would you replace component tests with end-to-end tests?

I would not replace, I would rebalance. Component tests are fast and precise but mock the boundaries, so they miss integration drift; end-to-end tests catch that and cost minutes and their own flakiness. My default shape is a thick layer of component tests around user-visible behaviour, a thin layer of end-to-end covering the three or four journeys that lose money if broken, and contract tests against the API so the mocks cannot drift silently. When a bug escapes, I ask which layer should have caught it, and that answers where to invest.

Did quarantining tests reduce your safety?

Temporarily and deliberately, yes — and it was the right trade because an ignored red build provides zero safety, not partial safety. The controls were that quarantine requires a named owner and a two-week expiry, quarantined tests still run and are reported, and anything unfixed at expiry gets escalated rather than silently deleted. Two tests were eventually deleted because they asserted behaviour the product no longer had, which is a legitimate outcome as long as it is a decision, not a default.

How do Suspense and transitions change how you test?

They make asynchrony explicit, so tests must be written around states rather than instants: assert the fallback appears, then that the content appears, rather than assuming a single synchronous update. A transition may intentionally keep the old UI visible while the new one renders, so a test that asserts immediately after the click will see the previous state and be right to. In practice this means async queries everywhere and no assumptions about update timing — the same discipline that fixed our flakes.

20Saying no to the third-party tag

tier · staff → principal archetype · pushing back on a stakeholder

EXAMPLE — replace with your own

A marketing director asked us to add a personalisation vendor’s script to the top of every page. It was a synchronous tag that mutated the DOM before our React app hydrated, and the vendor’s own documentation recommended an anti-flicker snippet that hides the page body until the script loads — up to two seconds. Marketing had already signed the contract. Saying “no” flatly would have been correct on the technical merits and would have made me an obstacle rather than a partner, which is the failure mode I care about at this level.

So I did three things. I quantified the cost rather than asserting it: a staged build with the tag on a copy of production measured LCP going from 1.4s to 3.1s at p75 on 4G, and a synthetic test showed the page body hidden for a median 900ms. I found what they actually needed, which was not this vendor — it was the ability to change hero copy and offers per segment without a deploy. And I offered an alternative that delivered that: segment resolution on the server, content from our CMS, rendered into the page with no client-side flicker and no third-party DOM mutation.

The other half of the story is the part I nearly skipped. Their contract was already signed, so “use something else” had a cost with their director’s name on it. I went with them to the vendor, and it turned out the same product had an asynchronous API mode — no DOM mutation, no anti-flicker snippet, we fetch the decision and render it ourselves. That was a two-week integration instead of a two-day tag, and it was the outcome everyone could live with: they kept the vendor and the contract, we kept the page fast, and the DOM stayed ours.

// What was asked for: a synchronous tag mutating the DOM before hydration.
<script src="https://vendor.example/personalise.js"></script>
<style>body { opacity: 0 } /* anti-flicker: hides the page until the vendor loads */</style>

// What we shipped: the decision is data, and React owns the DOM.
const variant = await personalise.decide({ segment, page });   // server-side, cached, 40ms p95
return <Hero {...content[variant]} />;                          // no flicker, no hydration mismatch

Beyond the one decision I pushed for a durable rule, because the next request was inevitable: a written policy that third-party scripts on customer-facing pages need an owner, a performance budget, an async loading strategy and a quarterly review, with the budget enforced in CI on the bundle and in synthetic monitoring on the field metrics. Two vendors have been declined under that policy since, by product managers, without me being in the room — which is the actual win.

What I would do differently: I would have built the relationship before I needed it. That director and I had spoken maybe twice in a year, so my first substantive contact was to complicate something she had already bought. The next quarter I set up a monthly half-hour with her, and the conversations since have been far cheaper for both of us.

What the interviewer is really probing. Whether you can disagree with someone who has power, with evidence and an alternative, and whether you understand their goal well enough to serve it differently. They are listening for “what they actually needed”, which separates a partner from a gatekeeper.

The mistake candidates make. A story where they blocked something and were vindicated, with no alternative offered and no relationship maintained. Also: treating the stakeholder as an adversary in the telling — interviewers hear the tone.

(d) Follow-up drill chain

Why is a third-party script that mutates the DOM particularly bad for React?

Because React assumes it owns the DOM it rendered. If a script changes text or attributes inside a React-managed subtree before hydration, the client render disagrees with the server HTML and you get a hydration mismatch — React discards and re-renders, which visibly undoes the vendor’s change. After hydration it is worse in a subtler way: React may not notice the external change until it re-renders that subtree, at which point it reverts it. The only safe integrations are outside the React root, or via a container React is told not to manage.

Is there a supported way to let a third party own part of the tree?

Yes: render an empty element and never give React any children for it, so reconciliation has nothing to diff — the widely used pattern is a container with a stable ref that you hand to the library, cleaned up on unmount. dangerouslySetInnerHTML with a constant value achieves a similar effect. What does not work is letting a script modify nodes React renders, or relying on React not to re-render that region. I would also require the vendor’s code to load asynchronously and to fail open, so an outage on their side does not blank our page.

At what point would you have accepted the tag?

If the measured cost had been small — say under 100ms of LCP with no anti-flicker snippet — and the page was not commercially critical, I would have accepted it with a budget and a review date rather than spending political capital. Not every hill is worth it, and being the person who objects to everything makes the important objections weaker. What made this one worth fighting was the combination of hiding the page body and mutating the DOM, both of which are categorical rather than marginal problems.

How do you make a performance budget stick when it blocks a launch?

By agreeing in advance who can grant an exception and on what basis, so the budget has a legitimate release valve and does not simply get ignored under pressure. Ours: a named product leader can waive it for a defined period with a written reason, which is recorded and reviewed. Two things follow — waivers are rare because they are visible, and when one is granted the team is not in the position of quietly breaking a rule everyone pretends to follow.

What if the vendor had had no async mode?

Then the honest options were to implement the segment decision ourselves against their data, to renegotiate the contract, or to accept the cost on a limited set of pages with a review date. I would have laid out all three with numbers and let the business choose, because the trade-off is genuinely commercial — the technical facts are mine to establish, the priority is not. What I would not have done is implement it as requested while grumbling, or refuse without offering a path.

22Night-before cheat sheet

delivery read aloud

Ten sentences to read out loud the night before, then again in the car. They are about delivery, not content — the content is the twenty stories above, and by now they should be yours, not these.

  1. Lead with the situation in one line, then stop setting up. “A dashboard froze for eleven seconds when our largest customer arrived with 120,000 rows.” The interviewer now knows the stakes; everything else is answer, not preamble.
  2. Put a number in the first thirty seconds and another at the end. 180ms to 9ms, 14% flake to 0.4%, $18,000 to $2,100. Numbers are what people remember and what makes the rest of the story credible.
  3. Say “I” for what you did and “we” for what the team did, in the same breath. “I found the retainer chain; the team turned StrictMode back on and wrote the CI check.” Interviewers listen for this specifically, and false modesty costs as much as inflation.
  4. Name the mechanism, not just the outcome. “Context propagates past memo boundaries, so splitting the provider was the fix” — one mechanical sentence proves you understood it rather than watched it get fixed.
  5. Tie the decision back to a real React trade-off. Fan-out versus volume, cacheability versus personalisation, memoisation versus data flow, server versus client boundary. Every good React story is one of these underneath.
  6. Own the “what I would do differently” without apologising for it. One sentence, specific, structural: “I would have instrumented in production on day one instead of reading code for a day and a half.” Then move on — dwelling reads as insecurity.
  7. Say what you traded away. Virtualisation cost us find-in-page and screen-reader traversal; two React copies cost 45KB. A story with no cost sounds rehearsed, because real work always costs something.
  8. Be precise about versions and dates. useEffectEvent and <Activity> are 19.2, October 2025; Compiler 1.0 is stable since 7 October 2025; <ViewTransition> is still canary. Precision here signals currency better than any opinion.
  9. When you do not know, say the boundary of what you know and how you would find out. “I have not run partial pre-rendering in production; here is what I would measure in the first week.” This scores higher than a confident guess, every time.
  10. Answer in ninety seconds and then be quiet. Let the interviewer drill — the drill chains are where lead-level signal actually lives, and you have prepared for them. Rambling past your own conclusion is the single most common way strong engineers lose these interviews.
