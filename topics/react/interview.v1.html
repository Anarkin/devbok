01Hooks and component state

Every React loop starts here, because hooks are where correctness and performance both begin. Screeners check that you know the rules and the difference between state and a ref; mid-level checks that you can debug "my state is stale"; senior and principal are really about state placement — the ability to say which value is state, which is derived, which belongs to an external store, and what that choice costs six months later. Expect at least one live-coding question where the interviewer changes the requirement halfway and watches whether your state shape survives it.

Docs: react.dev — Built-in React Hooks

screenerWhat are the Rules of Hooks, and what actually breaks if you violate them?

Answer

Two rules: call hooks only at the top level of a component or another hook, never inside conditions, loops or early returns; and call them only from React functions. The mechanical reason is that a component's hooks are stored as an ordered linked list on its fiber, and on every re-render React walks that list positionally — there are no names, only call order. Skip a useState behind an if and the next render reads the wrong slot, so a piece of state silently becomes another piece of state. This is not a style rule: it is why eslint-plugin-react-hooks is non-negotiable, and since v6 (shipped alongside React 19.2) the same plugin also carries the compiler-powered rules such as set-state-in-render and set-state-in-effect.

Example

// Broken: the hook list has two entries on some renders and three on others.
function Profile({ user }) {
  const [name, setName] = useState(user.name);
  if (user.isAdmin) {
    const [perms, setPerms] = useState([]);   // ← positional slot moves
  }
  const [theme, setTheme] = useState('light'); // ← sometimes reads perms' slot
}

// Fixed: unconditional hooks, conditional rendering.
function Profile({ user }) {
  const [name, setName] = useState(user.name);
  const [perms, setPerms] = useState([]);
  const [theme, setTheme] = useState('light');
  return user.isAdmin ? <AdminView perms={perms} /> : <UserView name={name} />;
}

Follow-ups

  • Why can an early return before a hook break things, even if the hook is at the top level? — An early return skips the remaining calls, which is the same positional mismatch as a conditional hook.
  • Can you call a hook in a plain helper function? — Only if that function is itself a hook (named use*) and is called from a component or hook; otherwise there is no fiber to attach state to.
  • What does use() change about this? — use() (React 19) is the one exception: it may be called conditionally and inside loops, because it reads a promise or context rather than allocating a hook slot.

Common wrong answer

"You can't call hooks conditionally because React needs to know how many hooks there are." Close but shallow — it suggests the count is the problem, so candidates then propose "just always call the same number" and break the ordering anyway. The invariant is order, not count, and saying so is what separates a memorised answer from an understood one.

screenerWhen do you use useState versus useRef?

Answer

Use state for anything the UI is derived from: changing it schedules a render, and reading it during render is safe and consistent. Use a ref for values the render output must not depend on — a DOM node, a timer id, a mutable "last seen" value, an AbortController. Mutating ref.current does not schedule a render and does not participate in reconciliation, which is exactly why writing to a ref during render is a rule violation: two concurrent renders would observe each other's writes. The one-line test I give in code review is "if this value changed and nothing repainted, is the screen wrong?" — if yes, it is state.

Example

function Search({ query }) {
  const [results, setResults] = useState([]);   // rendered → state
  const controller = useRef(null);              // machinery → ref

  useEffect(() => {
    controller.current?.abort();
    controller.current = new AbortController();
    fetch(`/api/search?q=${query}`, { signal: controller.current.signal })
      .then(r => r.json()).then(setResults)
      .catch(e => { if (e.name !== 'AbortError') throw e; });
    return () => controller.current?.abort();
  }, [query]);

  return <ResultList items={results} />;
}

Follow-ups

  • Why is reading a ref during render discouraged? — Under concurrent rendering a render can be started, thrown away and restarted; a ref read makes the output depend on mutable state outside React's control, so renders stop being pure.
  • What changed about ref in React 19? — Function components take ref as an ordinary prop, so forwardRef is no longer needed for new code (it still works, and is everywhere in existing codebases).
  • What is a ref cleanup function? — React 19 lets a ref callback return a cleanup function, which runs on unmount instead of React calling the callback with null.

Common wrong answer

"Use a ref when you want state that doesn't re-render, so it's a cheap useState." Candidates then store rendered values in refs and wonder why the UI is stale. A ref is not cheap state; it is state React deliberately does not observe.

midI call setCount(count + 1) twice in one handler and the count only goes up by one. Why, and what is the fix?

Answer

Because count is a value captured in that render's closure, not a live cell: both calls compute 0 + 1. React also batches the updates and re-renders once. The fix is the functional updater, setCount(c => c + 1), which queues a function React applies in order against the latest queued value. Worth adding that since React 18 batching is automatic everywhere — in promises, timeouts and native handlers, not just React event handlers — which is a common source of "this used to re-render twice" bugs when upgrading from 17.

Example

// 0 → 1
onClick={() => { setCount(count + 1); setCount(count + 1); }}

// 0 → 2
onClick={() => { setCount(c => c + 1); setCount(c => c + 1); }}

// Escape hatch when you need the DOM updated before the next line (rare):
import { flushSync } from 'react-dom';
flushSync(() => setCount(c => c + 1));
listRef.current.scrollTop = listRef.current.scrollHeight;

Follow-ups

  • Is the state variable mutated after setCount returns? — No. The current render's count is frozen for that render; the new value only exists in the next render.
  • When is flushSync justified? — When you must read layout after a specific update (scroll to bottom, focus a just-rendered node). It opts out of batching and concurrency, so it is a last resort, not a fix for stale reads.
  • Does React bail out if you set the same value? — Yes, Object.is-equal state bails out, though React may still render the component once more before deciding to stop.

Common wrong answer

"setState is asynchronous, so you need to wait for it." That framing leads to setTimeout hacks and await around setters. It is not asynchrony, it is closure capture plus a queued update — and the queue is exactly why the functional form works.

midWhen do you move from useState to useReducer?

Answer

When several pieces of state change together according to rules, or when the next state depends on the previous one in more than a trivial way. A reducer names the transitions instead of scattering them across handlers, makes illegal intermediate states unrepresentable, and — practically important — gives you a pure function you can unit-test without rendering anything. It also stabilises identity: dispatch is guaranteed stable, so passing it down never invalidates a memoised child, whereas a handful of setX callbacks wrapped in useCallback is noise the React Compiler now handles for you anyway. My rule of thumb: three or more related useState calls, or any state machine with a "loading / success / error" shape, is a reducer.

Example

// Four booleans → sixteen states, most of them illegal.
const [isLoading, setLoading] = useState(false);
const [error, setError] = useState(null);
const [data, setData] = useState(null);
const [isStale, setStale] = useState(false);

// One discriminated state, four legal transitions.
function reducer(state, action) {
  switch (action.type) {
    case 'fetch':   return { status: 'loading', data: state.data };
    case 'success': return { status: 'ready', data: action.data };
    case 'failure': return { status: 'error', error: action.error, data: state.data };
    case 'stale':   return { ...state, status: 'stale' };
    default:        return state;
  }
}
const [state, dispatch] = useReducer(reducer, { status: 'idle', data: null });

Follow-ups

  • Is the reducer allowed to be impure? — No; React may call it twice in StrictMode development renders, and it must be a pure function of state and action.
  • How do you combine a reducer with context without re-rendering everything? — Two contexts: one for the state value, one for the stable dispatch. Consumers that only dispatch never re-render.
  • Would you reach for a state machine library instead? — When the transitions have guards, entry/exit actions and hierarchy, yes; XState earns its weight around checkout or media-player complexity, not for four states.

Common wrong answer

"useReducer is for performance — it re-renders less than useState." It does not; both schedule the same update. Claiming a perf benefit signals that the candidate has not actually reasoned about why the reducer helps (testability and legal-state modelling).

midA prop changes and some state should reset. How do you do it?

Answer

Preferred: don't store it — derive it during render if it is computable from props and other state. If it genuinely is state that must reset, change the component's key so React unmounts the old instance and mounts a fresh one with fresh state; this is the idiomatic React 18/19 answer and it is one line. The third option, adjusting state during render (calling a setter in the render body, guarded by a comparison with a previous-value state variable), is officially supported for the narrow case where you only want to reset part of the state, and React re-renders immediately without painting the intermediate result. What you should not do is put it in an effect: that renders once with the wrong data, paints, then renders again.

Example

// Best: the key resets everything below it.
<ProfileEditor key={userId} userId={userId} />

// Narrow case: reset one field, keep the rest.
function List({ items }) {
  const [selection, setSelection] = useState(null);
  const [prevItems, setPrevItems] = useState(items);
  if (items !== prevItems) {          // adjusting state during render
    setPrevItems(items);
    setSelection(null);
  }
  // ...
}

// Anti-pattern: an extra paint with stale selection.
useEffect(() => { setSelection(null); }, [items]);

Follow-ups

  • What does changing key actually cost? — A full unmount/remount of that subtree: effects clean up and re-run, DOM nodes are recreated, focus and scroll inside are lost.
  • Why is the render-time setter not an infinite loop? — Because the guard makes it run only when the prop actually changed; React discards the in-progress output and re-renders the same component before committing.
  • Does the compiler change this advice? — No. The compiler memoizes; it does not fix state placement, and set-state-in-render lint still flags the unguarded version.

Common wrong answer

"Use useEffect with the prop in the dependency array." It works, so it survives code review, but it is the textbook "you might not need an effect" case: the user sees one frame of stale UI, and under Suspense or slow devices that frame is visible. Interviewers use this question specifically to catch effect-first thinking.

midWhat is lazy initial state, and when does it matter?

Answer

Passing a value to useState evaluates that expression on every render even though React discards it after the first; passing a function defers it so it runs once, on mount. It matters whenever the initialiser is expensive or has a side effect flavour — parsing localStorage, building a big Map, generating an id. The same distinction shows up in useRef, where there is no lazy form, which is why you sometimes see the if (ref.current === null) ref.current = expensive() idiom. At interview level the point is not the syntax, it is noticing that "runs every render" is the default for anything written in the component body.

Example

// Runs JSON.parse on every render, result thrown away after the first.
const [draft, setDraft] = useState(JSON.parse(localStorage.getItem('draft') ?? '{}'));

// Runs once.
const [draft, setDraft] = useState(() => JSON.parse(localStorage.getItem('draft') ?? '{}'));

// Ref equivalent, since useRef has no lazy form:
const observer = useRef(null);
if (observer.current === null) observer.current = new IntersectionObserver(onIntersect);

Follow-ups

  • Does the same apply to useReducer? — Yes, via the third argument: useReducer(reducer, initialArg, init) calls init(initialArg) once.
  • Is reading localStorage in an initialiser safe with SSR? — No; it throws or produces a hydration mismatch. Read it in an effect, or gate on the server-rendered value.
  • Would the React Compiler fix the eager version? — No. It memoizes values across renders but cannot know that useState ignores the argument after mount.

Common wrong answer

"React only evaluates the initial state once, so it doesn't matter." React only uses it once — JavaScript still evaluates the argument on every render. This is the single most common misconception in this area and it is easy to demonstrate with a console.log.

seniorWhat problem does useSyncExternalStore solve, and when would you write one by hand?

Answer

It is the supported way to read from a mutable source outside React — a Redux-style store, a browser API, a WebSocket cache — without tearing. Tearing is the concurrent-rendering failure where a long render is interrupted, the external value changes mid-render, and two parts of the same committed tree show different values. useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot) makes React re-read the snapshot at the right moments and forces a synchronous, consistent re-render when it changed. You rarely write one in product code — every serious store library uses it internally — but you do write one when you wrap a browser API (matchMedia, navigator.onLine, document.visibilityState) or an existing non-React singleton, and interviewers use it to see whether you understand why concurrent rendering needed a new primitive at all.

Example

const subscribe = (cb) => {
  const mql = window.matchMedia('(prefers-reduced-motion: reduce)');
  mql.addEventListener('change', cb);
  return () => mql.removeEventListener('change', cb);
};

export function useReducedMotion() {
  return useSyncExternalStore(
    subscribe,
    () => window.matchMedia('(prefers-reduced-motion: reduce)').matches,
    () => false,          // server snapshot: no window
  );
}

Follow-ups

  • Why must getSnapshot return a cached value? — React calls it repeatedly and compares with Object.is; returning a fresh object each call gives an infinite render loop.
  • What happens if you omit getServerSnapshot in an SSR app? — It throws during server rendering; you must supply the server value explicitly.
  • Does it opt out of concurrent features? — Updates from an external store are treated as synchronous/blocking, so they cannot be interrupted the way transition updates can — that is the price of consistency.

Common wrong answer

"It's for subscribing to stores instead of useEffect + useState, which is basically the same thing but tidier." The effect version is not equivalent: it can miss updates that happen between render and effect commit, and it tears under concurrent rendering. If the candidate cannot say the word tearing and describe the interleaving, they have read the API docs but not the reason.

seniorWhat makes a good custom hook, and what does a custom hook not give you?

Answer

A custom hook is just a function that calls hooks, so it shares logic, never state: two components calling useCart() get two independent cart states unless the hook reads from a shared source (context or an external store). A good one has a single responsibility, returns a stable shape (object or tuple, consistently), owns its own cleanup, and does not take a "config object" that quietly changes identity each render. The test I apply in review: could this be a plain function? If it calls no hooks, it should be — formatPrice is not useFormatPrice. The naming matters mechanically too, because the lint rules and the React Compiler both key off the use prefix to decide what to validate.

Example

// Shares logic, not state: each caller gets its own timer.
function useInterval(callback, delay) {
  const onTick = useEffectEvent(callback);      // React 19.2: always latest, never a dep
  useEffect(() => {
    if (delay === null) return;
    const id = setInterval(() => onTick(), delay);
    return () => clearInterval(id);
  }, [delay]);
}

// Shares state: because the state lives in a store outside React.
function useCart() {
  return useSyncExternalStore(cartStore.subscribe, cartStore.getSnapshot);
}

Follow-ups

  • How do you version or deprecate a widely used hook in a monorepo? — Ship useThingV2 next to it, codemod the call sites, delete the old one; a hook's signature is an API contract like any other.
  • Should a hook return an object or a tuple? — Tuple when callers rename freely and there are ≤3 values (like useState); object once there are optional members, because adding a field is then non-breaking.
  • What is the risk of a hook that takes an inline options object? — Every render creates a new object; if the hook puts it in a dependency array, the effect re-runs forever. Destructure primitives inside the hook.

Common wrong answer

"Custom hooks let you share state between components." This is the mistake that produces bug reports like "two components use useAuth but only one updates". Sharing requires a shared source — context, an external store, or a cache — and the hook is only the accessor.

seniorWhat is useEffectEvent, and how is it different from useCallback or a ref?

Answer

Shipped stable in React 19.2 (1 Oct 2025), useEffectEvent extracts the non-reactive part of an effect: the returned function always sees the latest props and state, but it is deliberately excluded from dependency arrays, so changing the values it reads does not re-run the effect. The classic case is a chat room that reconnects on roomId but must show a toast in the current theme — with useCallback you either lie in the dependency array or reconnect every time the theme changes. It is not a general-purpose callback: you may only call it from inside effects, never pass it to child components or into a dependency array, and the lint rule enforces that. The ref-based "latest value" idiom (ref.current = value in an effect) is the legacy hand-rolled version you will still find in older codebases.

Example

function ChatRoom({ roomId, theme }) {
  const onConnected = useEffectEvent(() => {
    showNotification('Connected!', theme);      // latest theme, not a dependency
  });

  useEffect(() => {
    const connection = createConnection(roomId);
    connection.on('connected', () => onConnected());
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]);                                 // ✅ theme is absent, legitimately
}

Follow-ups

  • What is the pre-19.2 workaround? — A ref updated in an effect (latest.current = onConnected) and called via latest.current(); correct but easy to get wrong under StrictMode double-invocation.
  • Why can't you pass an Effect Event to a child? — Its identity is not stable across renders in a meaningful way and it has no defined behaviour outside an effect's lifetime; React's lint rule rejects it.
  • Does it replace useCallback? — No. useCallback stabilises a function passed to children; Effect Events exist only to keep values out of dependency arrays.

Common wrong answer

"It's useCallback with an empty dependency array." That is the bug it exists to fix: an empty-deps useCallback closes over stale values, while an Effect Event reads the latest ones. Saying they are equivalent tells the interviewer the candidate has never debugged a stale-closure incident.

seniorHow do you decide what is state, what is derived, and what belongs outside React entirely?

Answer

I work from a single principle: state is the minimal set of values you cannot compute from something else. Anything computable — the filtered list, the total, whether the form is valid — is derived during render, not stored, because stored derivations are two sources of truth that will drift. Things that are neither, like the current URL, the network cache or a WebSocket feed, belong outside React and are read with the right adapter: the router for URL state, a query cache for server state, useSyncExternalStore for a store. That leaves genuinely local UI state — open/closed, focused index, draft text — which lives in the lowest common ancestor of its consumers. Most "state management is hard" complaints turn out to be server cache stored as component state.

Example

// Three sources of truth waiting to disagree.
const [items, setItems] = useState([]);
const [filtered, setFiltered] = useState([]);
const [count, setCount] = useState(0);

// One source, two derivations. Cheap, and the compiler memoizes them if they are not.
const [items, setItems] = useState([]);
const [query, setQuery] = useState('');
const filtered = items.filter(i => i.name.includes(query));
const count = filtered.length;

Follow-ups

  • When is caching a derivation worth it? — When the input is large and the computation is measurably slow (sorting 10k rows). Measure with the React Performance Tracks in Chrome DevTools (19.2) before adding memoization.
  • Where does URL state belong? — In the URL. Filters, tabs and pagination in the URL make the app linkable, back-button-correct and server-renderable for free.
  • How do you push this on a team? — Make it a review checklist item and an ADR; the durable version is a lint rule plus a shared query-cache library so the bad path is not available.

Common wrong answer

"Put everything in a global store so any component can reach it." It removes the placement question rather than answering it, and it turns every fetch result into app-wide state with manual invalidation. Interviewers hear it as "has not distinguished server cache from UI state".

principalYou inherit an app with 300 custom hooks and a "hooks are our architecture" culture. What do you change, and how?

Answer

First I would characterise the 300: most are usually plain functions wearing a use prefix, wrappers around one library call, or duplicated data-fetching. That triage — pure utilities, thin adapters, genuine stateful logic — is measurable with a script, so I would bring numbers, not opinions. The real problem with hook-as-architecture is that hooks compose logic but hide where state lives: a hook can quietly own state, subscribe to a store, and fire network requests, and no call site can tell. So my direction is boring: pure functions stay pure functions, server data goes through one query cache with one cache-key convention, and hooks are reserved for stateful, lifecycle-bound logic. I would sequence it as an ADR plus a codemod for the mechanical cases, a lint rule to stop the bleeding, and a "no new hook without a review" rule for one quarter — and I would leave the remaining bespoke hooks alone unless they are touched, because rewriting working code is how migrations get cancelled.

Example

# Triage in an afternoon, not a quarter: which "hooks" call no hooks at all?
rg --files -g 'use*.ts*' src | while read f; do
  rg -q 'use(State|Effect|Memo|Callback|Ref|Context|Reducer|SyncExternalStore)\(' "$f" \
    || echo "PLAIN FUNCTION: $f"
done

Follow-ups

  • How do you know the migration is working? — Track the count of components fetching directly, the number of distinct cache-key shapes, and p75 interaction latency; all three should move.
  • What do you do about the team member who wrote most of them? — Make them the owner of the new convention. Migrations fail on politics far more often than on code.
  • When would you not do this at all? — If the app is in maintenance or scheduled for replacement within a year, the correct answer is to leave it and spend the budget elsewhere.

Common wrong answer

"Rewrite them into a proper state-management layer with a big-bang migration." It sounds decisive and it is the classic principal-level trap: a six-month freeze, no incremental value, and a half-migrated codebase when priorities shift. Interviewers are listening for incrementalism, measurement, and the willingness to leave working code alone.

principalA junior's PR uses useState for the list of orders fetched from the API. Walk me through the code review.

Answer

I would not lead with "that's wrong" — I would ask what happens on the second mount, on a refocus, and when two components need the same orders. That surfaces the real issue: server data is a cache with staleness, deduplication, retry and invalidation semantics, and useState plus useEffect reimplements a quarter of that badly, usually without cancellation or race protection. Then I would name the modern options concretely: a query cache (TanStack Query, SWR, or the router's loader if there is one) for client fetching, use() with a Suspense boundary if promises come from a framework, or a Server Component if the data does not need client interactivity. Finally I would separate the teaching moment from the merge decision — if the PR is a one-off internal page, it may well ship as-is with a comment, because the review should be proportionate.

Example

// The PR: no cancellation, no dedupe, refetches on every mount, races on fast navigation.
useEffect(() => { fetch('/api/orders').then(r => r.json()).then(setOrders); }, []);

// Client-side alternative, with the semantics named.
const { data: orders } = useQuery({
  queryKey: ['orders', customerId],
  queryFn: ({ signal }) => fetchOrders(customerId, { signal }),
  staleTime: 30_000,
});

// Server Component alternative: no client state, no waterfall, no bundle cost.
async function Orders({ customerId }) {
  const orders = await getOrders(customerId);
  return <OrderTable orders={orders} />;
}

Follow-ups

  • What race condition specifically? — Two overlapping requests resolve out of order and the older response wins; an AbortController or an "ignore" flag in the cleanup fixes it.
  • How would you stop the next PR from doing this? — A lint rule banning bare fetch in components plus one documented data-access module; conventions that are not enforced do not exist.
  • When is the naive version actually fine? — A single-mount admin page with no navigation and no shared data; adding a cache there is over-engineering.

Common wrong answer

"Tell them to use useEffect with a cleanup function and move on." It fixes the race and leaves every other cache semantic unimplemented — and, at lead level, it misses that the interviewer is testing how you coach, not whether you can spot the bug.

02Rendering and reconciliation

This is the sub-area that separates people who use React from people who can debug it. Interviewers want a mental model they can push on: what triggers a render, what React does with the output, how it decides to keep or destroy a DOM node, and what key really means. Mid-level should be able to explain re-render propagation and keys; senior should be able to explain why a state update in a parent re-renders children that received no new props, and what to do about it; principal should be able to connect all of it to a measured performance problem.

Docs: react.dev — Preserving and Resetting State

screenerWalk me through what happens between setState and the browser painting.

Answer

Three phases. Trigger: the setter enqueues an update on the component's fiber and schedules work at a priority. Render: React calls the component function (and its children as needed), producing a new element tree, and diffs it against the current one to build a list of changes — this phase is pure, interruptible and may be thrown away and restarted. Commit: React applies the DOM mutations synchronously, then runs layout effects (useLayoutEffect, ref attachment) before the browser paints, and passive effects (useEffect) after. The important consequence for interviews is that "render" means "call the function", not "touch the DOM" — a component can render many times and change nothing on screen.

Example

function Row({ label }) {
  console.log('render', label);               // render phase: may run twice in StrictMode dev
  useLayoutEffect(() => { /* measure, before paint */ });
  useEffect(() => { /* subscribe, after paint */ });
  return <li>{label}</li>;
}

Follow-ups

  • Why is the render phase required to be pure? — Because concurrent React can start, pause, abandon and restart it; side effects would run an unpredictable number of times.
  • Where does useLayoutEffect fit and what does it cost? — Between mutation and paint, synchronously: it blocks the frame, so use it only for measurement that would otherwise flash.
  • What does StrictMode add in development? — Double-invoked render, double-invoked effects (mount, unmount, mount) to surface impurity and missing cleanup; production is unaffected.

Common wrong answer

"React re-renders, compares the virtual DOM with the real DOM, and patches the differences." React never reads the real DOM to diff; it compares the new element tree with the previous one it kept in memory. The distinction matters as soon as you discuss why external DOM mutation breaks React.

screenerWhy do you need key in a list, and why is the array index a bad key?

Answer

Keys tell React which element in the new list corresponds to which element in the old one, so it can move, keep or destroy fibers instead of matching by position. With index keys, inserting at the front makes every item's identity shift by one: React keeps the DOM nodes and just changes their text, which is fine for static content but destroys anything positional — component state, focus, uncontrolled input values, animations, scroll position. The rule is that a key must be stable, unique among siblings, and derived from the data's identity. Index keys are acceptable only when the list never reorders, never has items inserted or removed in the middle, and items hold no state.

Example

// Type into the second input, then prepend an item: your text moves to the wrong row.
{todos.map((todo, i) => <TodoInput key={i} todo={todo} />)}

// Identity travels with the data.
{todos.map(todo => <TodoInput key={todo.id} todo={todo} />)}

Follow-ups

  • What if the data has no id? — Generate one when the item is created and keep it with the item; never generate it during render, which produces a new key every time.
  • Do keys have to be globally unique? — No, only among siblings; React scopes reconciliation to one parent's children.
  • What is the performance impact of bad keys? — Usually the opposite of what candidates expect: index keys are often faster to diff and still wrong, because correctness, not speed, is the issue.

Common wrong answer

"Index keys are bad for performance." They are bad for correctness. A candidate who says "performance" has learned the rule without the mechanism and will use index keys anywhere the list "looks small".

midA parent re-renders. Do all its children re-render, even the ones whose props did not change?

Answer

Yes, by default: rendering a parent produces new element objects for its children, and React calls each child function. That is intentional and usually cheap — rendering is a function call, not a DOM write, and React commits nothing where the output is unchanged. Re-render propagation stops in three ways: the child is wrapped in React.memo and its props are shallow-equal, the child was passed as children/an element prop from higher up so its element identity is unchanged, or the React Compiler (1.0, Oct 2025) memoized it for you. The composition trick is worth naming explicitly, because it fixes the "context provider re-renders the world" problem without any memoization at all.

Example

// ExpensiveTree re-renders on every keystroke.
function App() {
  const [text, setText] = useState('');
  return (<><input value={text} onChange={e => setText(e.target.value)} />
          <ExpensiveTree /></>);
}

// Same element object every render → React skips it, no memo() needed.
function App() { return <TextBox><ExpensiveTree /></TextBox>; }
function TextBox({ children }) {
  const [text, setText] = useState('');
  return (<><input value={text} onChange={e => setText(e.target.value)} />{children}</>);
}

Follow-ups

  • Why does passing children work? — The element was created in the outer component, which did not re-render, so its identity is unchanged and React bails out on that subtree.
  • Does memo compare deeply? — No, shallow with Object.is per prop; an inline object or arrow function defeats it immediately.
  • With the compiler enabled, should you still write memo? — Rarely. The compiler memoizes at a finer grain; keep memo where you have measured a specific boundary that matters, such as a virtualized row.

Common wrong answer

"No — React only re-renders components whose props changed." That is what people expect from a props-diffing framework, and it leads to hours of confusion when profiling. React re-renders the subtree and relies on bailouts you opt into.

midWhen does React preserve component state, and when does it throw it away?

Answer

State lives on the fiber, and a fiber survives as long as the component stays at the same position in the tree with the same type and the same key. Same position and type: state is preserved even if props change completely. Different type at that position, or a different key: React unmounts the old fiber (running cleanups) and mounts a new one with fresh state. "Position" is structural, not visual — two sibling branches of a ternary are different positions, so a component rendered in both branches loses state when the condition flips, unless you keep it at the same position and vary props instead.

Example

// Same position, same type → state survives the toggle.
{isFancy ? <Counter isFancy={true} /> : <Counter isFancy={false} />}

// Different positions → state is reset each toggle.
{isFancy ? <div><Counter /></div> : <section><Counter /></section>}

// Deliberate reset without changing structure:
<Counter key={isFancy ? 'fancy' : 'plain'} />

Follow-ups

  • What happens if you define a component inside another component? — It is a new function type on every render, so React unmounts and remounts it every time: state resets, effects re-run, DOM is recreated. Never do it.
  • How does <Activity mode="hidden"> (19.2) change this? — It hides children and unmounts their effects while preserving their state, which is exactly the "keep the tab alive in the background" case that previously required lifting state.
  • Does moving a component in a list preserve state? — With correct keys, yes: React moves the fiber. With index keys, no — state stays with the position.

Common wrong answer

"State is preserved as long as the component isn't unmounted" — true but circular, and it dodges the actual question of what causes an unmount. Interviewers push exactly here, usually with the two-ternary-branches example.

midWhat is the difference between an element, a component and an instance?

Answer

A component is the function you write. An element is the plain object that function returns — { type, props, key }, a description, cheap to create and immutable. The instance is React's internal fiber: the thing that holds state, effects and the link to the DOM node. Creating elements is not rendering; JSX is only a call to jsx(). This distinction is what makes "pass the element as a prop" work as a performance technique, and it is why <Foo /> and Foo() are not interchangeable — the first creates an element React will manage as its own fiber, the second inlines the output into the caller's fiber, so hooks and state belong to the wrong component.

Example

const el = <Row id={1} />;
// ≈ { type: Row, key: null, props: { id: 1 } } — nothing has rendered yet.

function List() {
  return (
    <>
      <Row id={1} />   {/* its own fiber: own state, own hooks */}
      {Row({ id: 2 })} {/* inlined: its hooks become List's hooks */}
    </>
  );
}

Follow-ups

  • What is the new JSX transform? — Since React 17, JSX compiles to jsx() from react/jsx-runtime, so import React is no longer required just for JSX.
  • Why does calling a component directly sometimes "work"? — Because if it uses no hooks and no state there is nothing to break — until someone adds a useState to it.
  • Can you mutate an element? — No, elements are frozen in development and treated as immutable; use cloneElement if you truly need a variant (and prefer a prop).

Common wrong answer

"An element is a virtual DOM node, so it's basically a lightweight DOM node." That conflates the description with the tree React maintains, and it makes the next question — why passing children avoids re-renders — unanswerable.

seniorExplain the reconciliation heuristics and where they are wrong.

Answer

A general tree diff is O(n³); React gets O(n) with two assumptions. First, two elements of different type produce different trees, so React tears down the old subtree rather than trying to match inside it. Second, the developer supplies keys to identify children that are stable across renders. Both are heuristics and both can be wrong: moving a subtree between different parent types throws away state and DOM that could have been reused, and a wrapper added conditionally around a component (a "layout jitter" refactor) silently remounts everything below. The practical consequence I look for at senior level is that a candidate can predict a remount from a JSX structure change and knows the mitigations: keep the structure stable, vary props, or hoist the stateful component above the branch.

Example

// Adding an animation wrapper conditionally remounts <Video />: it restarts playback.
{isFullscreen ? <Overlay><Video src={src} /></Overlay> : <Video src={src} />}

// Stable structure, varying props: playback survives.
<Overlay enabled={isFullscreen}><Video src={src} /></Overlay>

Follow-ups

  • Could React reparent DOM nodes instead? — Not today; reparenting has been discussed for years but the DOM makes preserving state across parents very hard, which is why the workaround is portals or keeping the node mounted.
  • How do portals interact with this? — A portal changes the DOM parent but not the React tree position, so state and context are preserved — that is exactly why modals use them.
  • What is the cost of a wrong teardown in a real app? — Lost iframe/video/canvas state, refetches, dropped focus and, in one common case, a form the user had half-filled.

Common wrong answer

"React diffs the tree and only updates what changed, so structure changes are free." It is the marketing-level answer. The heuristic that different types imply different trees is precisely where the cost hides, and a senior candidate is expected to name it.

seniorWhat is <Activity>, and what problem does it replace?

Answer

Shipped in React 19.2, <Activity mode="visible" | "hidden"> lets you keep a subtree mounted with its state intact while hiding it: in hidden mode React unmounts the effects, hides the DOM, and deprioritises its updates until it is idle. It replaces two bad options — conditionally rendering (which destroys state and forces a refetch when you come back) and display: none with the tree fully live (which keeps subscriptions and timers running and pays full render cost). The natural uses are tab UIs where switching back should be instant, wizards, and pre-rendering the likely next route in the background. It is also the foundation for the <ViewTransition> work, which is still canary-only as of September 2026.

Example

<Activity mode={tab === 'search' ? 'visible' : 'hidden'}>
  <SearchResults query={query} />   {/* scroll position and state survive the switch */}
</Activity>

Follow-ups

  • Do effects run while hidden? — No: effects are unmounted (cleanups run) and re-mounted when it becomes visible again, which is why effects must be resilient to remounting.
  • What is the memory trade-off? — Hidden trees stay in memory; a tab bar with twenty heavy activities is a memory-pressure decision, especially on mobile.
  • How is this different from Suspense? — Suspense is about what to show while content is not ready; Activity is about keeping content that is ready but not visible.

Common wrong answer

"It's just display: none managed by React." Missing the effect unmount and the deprioritised rendering means missing the whole point: the reason people hand-rolled this with CSS was that they had no way to stop the hidden tree from doing work.

seniorA page renders 5,000 rows and typing in a filter box is janky. How do you diagnose and fix it?

Answer

Diagnose before touching anything: record with React's Performance Tracks (Chrome DevTools, since 19.2) or the Profiler, and find out whether the cost is the render of 5,000 components, the commit into the DOM, or a single expensive computation. Each has a different fix. Too many DOM nodes is a virtualization problem (render the visible window). Expensive computation on every keystroke is a memoization or a "debounce the derived value" problem. Everything-re-renders-on-every-keystroke is a state placement problem: the input's state should be local to the input, with the filtering deferred. React 18+ gives the last one a first-class answer: useDeferredValue keeps the input responsive while the list renders at lower priority — and the list stays interruptible, unlike a debounce, which just delays the same jank.

Example

function Filterable({ items }) {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);        // input stays at 60fps
  const isStale = query !== deferredQuery;
  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <div style={{ opacity: isStale ? 0.6 : 1 }}>
        <VirtualList items={items} query={deferredQuery} />
      </div>
    </>
  );
}

Follow-ups

  • Why is useDeferredValue better than a debounce here? — A debounce always waits; the deferred render starts immediately and is abandoned if the user types again, so on a fast machine there is no delay at all.
  • When is virtualization the wrong answer? — When the list must be findable with Ctrl+F, printable, or fully accessible to a screen reader that expects the whole list; those constraints beat the frame rate.
  • What number would you quote as "good"? — Keep interaction-to-next-paint under ~200ms (INP's "good" threshold); that is the metric the business cares about, not render counts.

Common wrong answer

"Wrap everything in memo and useMemo." It is the reflex answer and it usually does nothing here, because the cost is 5,000 commits, not prop equality — and with React Compiler enabled it is redundant work on top. The signal interviewers want is "measure first, then pick the fix that matches the phase".

principalHow would you set a rendering-performance budget for a large React app, and enforce it?

Answer

I would budget in user-visible terms, not React terms: INP under 200ms at p75 for the three interactions that matter, LCP under 2.5s, and a JS bundle ceiling per route. Then I would instrument for real: field data from the web-vitals library keyed by route and device class, because lab numbers on an M-series laptop hide everything. Enforcement is layered — a CI check on bundle size per route that fails the build, a synthetic run on a throttled profile for the top journeys, and a dashboard with the p75 field numbers that a named owner watches. The React-specific piece is a small one: enable the compiler and the hooks lint so the common memoization mistakes stop being individual judgment calls, and use <Profiler> or the 19.2 Performance Tracks only when a specific regression needs attribution. The organisational point I would make in the interview is that a budget nobody owns is a wish.

Example

import { onINP, onLCP, onCLS } from 'web-vitals';

const send = (metric) => navigator.sendBeacon('/rum', JSON.stringify({
  name: metric.name, value: metric.value, rating: metric.rating,
  route: currentRouteId(), build: __BUILD_SHA__,
  device: navigator.hardwareConcurrency <= 4 ? 'low' : 'high',
}));

onINP(send); onLCP(send); onCLS(send);   // p75 by route × device class is the budget

Follow-ups

  • What do you do when a team blows the budget for a genuinely valuable feature? — Budgets are negotiable with data: raise the ceiling deliberately with a written trade-off, or pay for it elsewhere. Silent breaches are the failure mode.
  • How do you attribute a regression to a specific PR? — Tag RUM events with the build SHA and alert on p75 shifts; without the SHA you get a mystery two weeks later.
  • Is render count a useful metric? — Only as a debugging aid. It is not a user-visible quantity and teams game it.

Common wrong answer

"Add a Lighthouse check in CI and require a score above 90." Lab-only, single-device, and easily gamed; it also misses interaction latency, which is where React apps actually hurt. The strong answer distinguishes lab from field and names an owner.

03Performance and the React Compiler

The most changed sub-area in React interviews. Until 2024 the expected answer was "wrap it in useMemo"; since React Compiler 1.0 (7 Oct 2025) the expected answer is "the compiler does that — here is what it can't do". Screeners still ask what memo does; mid-level is asked to justify a memoization; senior and principal are asked to profile, to decide what to split, and to run a compiler rollout across a real codebase. Being fluent in both the manual era and the compiler era is the differentiator, because every codebase you will join is half of each.

Docs: react.dev — React Compiler

screenerWhat does React.memo do, and when does it do nothing?

Answer

memo wraps a component so that when its parent re-renders, React compares the new props shallowly with the old ones and skips the render if every prop is Object.is-equal. It does nothing in three very common situations: when a prop is an inline object, array or arrow function created fresh each render; when the component takes children, since the children element is a new object each time; and when the component re-renders because of its own state or a context it consumes, which memo cannot stop. That is why memo historically came with a tail of useMemo/useCallback at every call site — and why the compiler, which memoizes both sides automatically, made most of that machinery obsolete.

Example

const Row = memo(function Row({ item, onSelect }) { /* ... */ });

// memo defeated: both props are new objects on every parent render.
<Row item={{ ...item }} onSelect={() => select(item.id)} />

// memo effective: stable references.
const onSelect = useCallback((id) => select(id), [select]);
<Row item={item} onSelect={onSelect} />

Follow-ups

  • Can you pass a custom comparison? — Yes, memo(Comp, areEqual), but a deep compare is usually slower than the render you are avoiding; treat it as a smell.
  • Does memo stop context updates? — No. A consumer re-renders whenever the context value changes, memo or not.
  • Where is memo still clearly worth it in 2026? — Leaf components rendered in the hundreds (virtualized rows, chart points) where you have measured the win.

Common wrong answer

"Wrap every component in memo — it can only help." It costs a props comparison on every render and a permanent maintenance tax on prop stability; applied everywhere it usually makes an app slower and definitely makes it harder to read. Interviewers are checking for cost-awareness, not enthusiasm.

screenerWhat is the difference between useMemo and useCallback?

Answer

useMemo(fn, deps) caches the result of calling fn; useCallback(fn, deps) caches the function itself. They are the same primitive — useCallback(fn, d) is useMemo(() => fn, d). Both exist for the same reason: referential stability, so that a memoized child bails out or an effect does not re-run. Neither is a guarantee: React may throw away a memoized value (for example to free memory), so they must never be used for correctness, only for performance. With the compiler enabled, the compiler produces the same caching automatically and at a finer grain, so new code generally has neither.

Example

const sorted   = useMemo(() => rows.sort(byName), [rows]);      // caches a value
const onSubmit = useCallback((data) => save(id, data), [id]);   // caches a function

// After the compiler: identical semantics, none of the ceremony.
const sorted   = rows.sort(byName);
const onSubmit = (data) => save(id, data);

Follow-ups

  • Is memoizing free? — No: an extra closure, an array allocation and a dependency comparison per render, plus retained memory. For a cheap computation it is a net loss.
  • Why must you never rely on it for correctness? — React explicitly reserves the right to discard cached values; code that assumes "this only runs once" belongs in a ref or state.
  • What is useMemo's cousin on the server? — cache() in React Server Components deduplicates async work for the lifetime of a request, and 19.2 added cacheSignal() to abort that work when the lifetime ends.

Common wrong answer

"useMemo is for values, useCallback is for functions" — correct but incomplete, and it usually comes with "so use them whenever you can". The follow-up ("what does it cost?") is where the interview is decided.

midWhat is the React Compiler, and what does it actually do to your code?

Answer

It is a build-time Babel plugin (stable at 1.0 since 7 October 2025) that analyses components and hooks and inserts memoization automatically, based on data flow and mutability analysis. Instead of you deciding what to wrap, it caches values at a granularity you cannot express by hand — including conditionally, and per-value inside a component rather than per-component. It supports React 17 and up (17 and 18 need the react-compiler-runtime package), it ships with lint rules in eslint-plugin-react-hooks v6, and Meta reported roughly 12% faster initial loads and up to 2.5× faster interactions on some surfaces. The important framing for an interview: it does not make bad architecture fast, it removes a class of manual bookkeeping — and it only works on code that follows the Rules of React, which it validates and silently skips when violated.

Example

npm install --save-dev --save-exact babel-plugin-react-compiler@latest
npm install --save-dev eslint-plugin-react-hooks@latest   # v6 carries the compiler rules
// vite.config.js
export default defineConfig({
  plugins: [react({ babel: { plugins: [['babel-plugin-react-compiler', {}]] } })],
});

Follow-ups

  • What happens to a component it cannot compile? — It bails out for that component and leaves it untouched; you see it in the compiler's build output or the ESLint report, not as a runtime error.
  • Does it change bundle size? — Slightly upward: memoization code has to live somewhere. The trade is CPU at runtime against a few bytes.
  • Why pin an exact version? — The React team's own advice: a compiler upgrade can change which values are memoized, which changes when effects fire, so pin and upgrade deliberately with tests.

Common wrong answer

"It compiles JSX ahead of time so there is no virtual DOM, like Svelte." A confident but wrong mental model — it produces the same React runtime work, just with better caching. Candidates who say this usually go on to claim it removes re-renders entirely.

midHow would you adopt the React Compiler in an existing large codebase?

Answer

Incrementally, and lint-first. Step one is to install eslint-plugin-react-hooks v6 with the compiler-powered rules and fix what it reports, because every violation is a place where the compiler will bail out or where your code was already subtly wrong. Step two is to enable the compiler for a directory or a glob rather than the whole app, using the plugin's opt-in configuration, and to verify with the build output that the components you expected actually compiled. Step three is measurement: profile a couple of representative interactions before and after, in production mode, so you can defend the change. Only then do you widen the glob. I would not delete manual memoization in the same change — one variable at a time.

Example

// Opt in by path while you build confidence.
['babel-plugin-react-compiler', {
  sources: (filename) => filename.includes('/src/features/checkout/'),
}]
// Opt a single file out while you fix a rule violation.
'use no memo';

Follow-ups

  • What is the rollback plan? — Remove the plugin; the compiler emits ordinary React code with no runtime dependency in React 19, so rollback is a build-config change.
  • What tends to break? — Code that mutates props or state objects in place, reads refs during render, or relies on a specific number of effect executions.
  • How do you know it is on in production? — Check the built output for the memo cache calls, and watch the bundle-size and INP dashboards; "we think it's enabled" is a real failure mode.

Common wrong answer

"Turn it on globally — it is safe by design, it bails out where it can't help." Technically defensible and operationally reckless in a codebase with weak test coverage: memoization changes when effects re-run, so a big-bang enable in a payments app is how you get a Friday incident.

midThe compiler is enabled. Should you delete the existing useMemo and useCallback calls?

Answer

Not as a sweep. The React team's guidance is explicit: for new code rely on the compiler; for existing code, test carefully before removing manual memoization, because some of it is load-bearing in ways nobody documented — a useMemo that keeps an object identity stable across renders may be the only reason an effect does not loop, or the only reason a third-party component does not reset. Manual memoization still works with the compiler on; it is redundant, not harmful. So the pragmatic answer is: stop writing new ones, remove them opportunistically when you are already changing a file and its tests, and treat a bulk codemod as a separate, measured project rather than a cleanup PR.

Example

// Load-bearing memo: deleting it re-runs the effect on every render.
const options = useMemo(() => ({ threshold: 0.5 }), []);
useEffect(() => {
  const io = new IntersectionObserver(onIntersect, options);
  io.observe(node);
  return () => io.disconnect();
}, [options, onIntersect]);

Follow-ups

  • Would the compiler have memoized options anyway? — Usually yes, but "usually" is not a migration strategy for an effect that opens a socket or an observer.
  • Are there cases you keep manual memoization forever? — Yes: expensive computations where you want an explicit, reviewable cache, and boundaries you deliberately control such as virtualized rows.
  • What does the lint say? — The v6 rules flag genuinely unnecessary memoization in some cases, which is a good queue to work from, file by file.

Common wrong answer

"Yes — run a codemod and delete them all, that's the whole point of the compiler." It is the answer that sounds most current and is the most dangerous: it changes effect timing across the entire app in one commit, with no way to bisect the resulting bug reports.

seniorWhat are the Rules of React the compiler depends on, and what happens when code breaks them?

Answer

Three that matter: components and hooks must be pure — same inputs, same output, no side effects during render; props, state and hook return values must be treated as immutable; and hooks must follow the ordering rules. The compiler's analysis is only sound if these hold, so it validates them and, where it cannot prove safety, it skips the component entirely rather than risk miscompiling. That means a rule violation in 2026 costs you performance silently rather than correctness loudly — which is exactly why the lint rules moved into the mainstream eslint-plugin-react-hooks. In review I treat "the compiler bailed out on this file" as a defect report about the code, not about the compiler.

Example

// Mutating a prop: the compiler cannot reason about aliasing here, so it bails out.
function Table({ rows }) {
  rows.sort(byName);              // ❌ mutates the caller's array during render
  return rows.map(r => <Row key={r.id} row={r} />);
}

// Pure: a new array, no mutation, fully compilable.
function Table({ rows }) {
  const sorted = [...rows].sort(byName);
  return sorted.map(r => <Row key={r.id} row={r} />);
}

Follow-ups

  • Is mutating a freshly created local object during render a violation? — No: values you created in this render are yours until you return them. The rule is about values you did not create.
  • How do you find bail-outs? — The compiler reports them at build time; the React DevTools also badge compiled components with a "Memo ✨" marker.
  • Does StrictMode help? — Yes, its double-invoked render surfaces exactly the impurity the compiler dislikes, which is why the two are usually adopted together.

Common wrong answer

"If the code breaks the rules the compiler will produce wrong output, so you have to be careful." It inverts the design: the compiler is conservative and bails out. Believing the opposite leads teams to avoid enabling it out of unfounded fear.

seniorHow do you profile a React performance problem in 2026?

Answer

Start from the user metric — usually INP — then attribute it. React 19.2 added React Performance Tracks to the Chrome DevTools performance panel: a Scheduler track showing update priorities (blocking vs transition) and where time is spent waiting, and a Components track showing which components rendered and how long their effects took, all on the same timeline as browser work. That is the first tool now, because it shows React work in context with paint, layout and network. The React DevTools Profiler is still the tool for "why did this component render", with the "record why each component rendered" setting. Always profile a production build (or at least without StrictMode's double render), and always on a throttled CPU, because the bug you are chasing is almost never reproducible on your laptop.

Example

// Targeted attribution when you need numbers in CI or RUM rather than a flamechart.
<Profiler id="OrderTable" onRender={(id, phase, actual, base, start, commit) => {
  if (actual > 16) report({ id, phase, actual });   // longer than one frame
}}>
  <OrderTable rows={rows} />
</Profiler>

Follow-ups

  • Why not trust development-mode numbers? — Dev builds are 2–5× slower, StrictMode renders twice, and the compiler's output differs; relative comparisons are fine, absolute ones are fiction.
  • What does the Scheduler track show that the Profiler cannot? — Priority and waiting: whether a transition was starved, whether an update was blocked behind a long task, and how it interleaves with network and paint.
  • What is your first question when someone says "React is slow"? — "Slow to load, slow to respond, or janky while scrolling?" — three different problems with three different fixes.

Common wrong answer

"Use the React DevTools Profiler and look for components with a high render count." Render count is not time, and the flamechart's dev-mode timings mislead. A senior answer names the production build, the throttling, and a user-visible metric.

seniorWhere do you code-split a React app, and what does each split cost?

Answer

Route boundaries first — they map to a user intent and to a natural loading state. Then heavy, rarely-used widgets: rich text editors, charting libraries, map SDKs, date pickers with locale data. Beyond that, splitting usually costs more than it saves, because each chunk is a request, a waterfall risk and a potential layout shift. The two mistakes I look for are splitting something that is needed immediately after the parent renders (you have created a waterfall, so preload it instead) and splitting so finely that the request overhead dominates on mobile networks. In an RSC app the calculus changes: components that never ship to the client are the ultimate code split, and React.lazy becomes a smaller part of the story.

Example

const Editor = lazy(() => import('./Editor'));

function Page() {
  return (
    <Suspense fallback={<EditorSkeleton />}>
      <Editor />
    </Suspense>
  );
}

// Preload on intent, so the chunk is in flight before the click resolves.
<button onMouseEnter={() => import('./Editor')} onFocus={() => import('./Editor')}>
  Edit
</button>

Follow-ups

  • How do you avoid the layout shift when a lazy chunk lands? — A fallback with the same dimensions as the real content; CLS regressions are the usual hidden cost of splitting.
  • What do the React 19 preloading APIs give you? — preload, preinit, prefetchDNS and preconnect from react-dom let a component declare resources it will need, and React hoists them into the document head.
  • How do you decide the split budget? — Per-route JS ceiling enforced in CI; anything that pushes a route over must justify itself or be split.

Common wrong answer

"Lazy-load every component; smaller bundles are always better." It produces dozens of tiny chunks, a request waterfall on 4G, and a page that renders in six visible steps. Bundle size is a proxy metric; the real one is time to interactive on the target device.

seniorA component is wrapped in memo and still re-renders on every parent update. How do you find out why?

Answer

Enumerate the four causes and eliminate them in order. One: a prop is a new reference each render — inline object, array, arrow function, or a style={{...}}. Two: it consumes a context whose value is a new object each render, which memo cannot intercept. Three: it has its own state or a hook that updates, so nothing about the parent matters. Four: it takes children, which is a fresh element every time. The React DevTools Profiler with "record why each component rendered" enabled answers it in about thirty seconds, and it will name the specific prop. If the compiler is enabled, the honest first check is whether that file compiled at all — an uncompiled file with hand-rolled memoization is where these bugs hide.

Example

// Two invisible new references per render.
<MemoRow style={{ padding: 8 }} onSelect={() => select(id)} />

// Context value recreated every render defeats every memo below it.
<Ctx.Provider value={{ user, logout }}>      // ❌ new object each render
<Ctx.Provider value={contextValue}>          // ✅ memoized or compiler-cached

Follow-ups

  • How do you make context not do this? — Split into a stable-value context and a state context, or memoize the value; the compiler does the latter for you.
  • Is re-rendering actually a problem here? — Often not. Confirm the render costs measurable time before spending effort; most "unnecessary" renders are sub-millisecond.
  • What is the quickest instrumentation? — A useEffect logging changed props, or the DevTools setting; a console.log in the body lies under StrictMode.

Common wrong answer

"Add a custom areEqual that deep-compares the props." It hides the problem behind a deep compare that is often slower than the render, and it breaks the moment a function prop is involved. Fix the reference, don't out-compare it.

principalYou own a platform of twelve React apps in a monorepo. Plan the React Compiler rollout.

Answer

I would treat it as a platform migration with a measurable hypothesis, not a toolchain upgrade. Phase 0: land eslint-plugin-react-hooks v6 in warn mode across the monorepo and publish the violation count per app — that is the honest map of which codebases follow the Rules of React. Phase 1: pick one mid-sized, well-tested app as the pilot, enable the compiler, and compare p75 INP and LCP from RUM before and after over two weeks; if there is no measurable win, that is a finding worth having early. Phase 2: promote the lint to error for new code only (via a baseline file) so the debt stops growing while existing violations are burned down by owning teams. Phase 3: enable per app, pinned to an exact compiler version, with each app's owner signing off after their own smoke tests. Throughout, the platform team owns the version pin and the upgrade cadence, because a compiler bump is a behaviour change and cannot be a Dependabot PR that merges itself.

Example

{
  "devDependencies": {
    "babel-plugin-react-compiler": "1.0.0",
    "eslint-plugin-react-hooks": "^6.0.0"
  },
  "pnpm": { "overrides": { "babel-plugin-react-compiler": "1.0.0" } }
}

Follow-ups

  • What would make you stop the rollout? — No measurable p75 improvement in the pilot plus any increase in error rate; the cost is not zero, so an unproven win is a reason to wait.
  • How do you handle the app that cannot adopt it? — Leave it. A legacy app with class components and mutation-heavy code gets no benefit and all the risk; document the exception.
  • Who owns regressions? — The platform team owns the pin and the rollback switch; app teams own their own rule violations. Ambiguous ownership is what turns a migration into a standoff.

Common wrong answer

"Enable it everywhere in one PR — it's opt-out per file if anything breaks." It sounds efficient and it removes your ability to attribute any regression to anything. The senior signal is a pilot with a measured hypothesis and a named rollback.

04Effects and side-effect discipline

Effects are where most React bugs live, so interviewers probe them hard and often with a code sample rather than a definition. Mid-level must know cleanup and dependencies; senior must be able to say when not to use an effect at all — the "You Might Not Need an Effect" material is now standard interview content — and must handle races and subscriptions correctly. At principal level the question becomes cultural: how do you stop a team of thirty from using effects as a general-purpose "run this later" mechanism?

Docs: react.dev — You Might Not Need an Effect

screenerWhat does useEffect do, and when exactly does the cleanup run?

Answer

It runs code after React has committed the render and the browser has painted, and it exists to synchronise the component with something outside React: a subscription, a network request, a DOM API, an analytics call. The cleanup function it returns runs before the next execution of that same effect and on unmount — so with dependencies [roomId], changing the room runs cleanup for the old room and then the effect for the new one. The mental model that survives every follow-up is "synchronise, don't sequence": an effect describes how to set up and tear down a connection to an external system for a given set of values, not "do this after that".

Example

useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  return () => connection.disconnect();   // before the next connect, and on unmount
}, [serverUrl, roomId]);

Follow-ups

  • What does an empty dependency array mean? — Set up once on mount, tear down on unmount. In StrictMode development that is mount → unmount → mount, deliberately.
  • What if you omit the array entirely? — The effect runs after every render; combined with a setState inside, that is the classic infinite loop.
  • Does the cleanup run before or after the DOM is updated for the next render? — Before the next effect runs, after the DOM commit; for layout effects the cleanup runs before paint.

Common wrong answer

"useEffect is componentDidMount plus componentDidUpdate plus componentWillUnmount." The lifecycle analogy is how people end up with effects that "run once on mount" and then break under StrictMode, Suspense or Activity. Effects are keyed to values, not to moments in a lifecycle.

screenerWhy do effects run twice in development, and what should you do about it?

Answer

StrictMode deliberately mounts, unmounts and remounts every component in development, so every effect runs setup → cleanup → setup. It is a test, not a bug: it proves that your effect can be torn down and set up again without breaking, which is required because React really does remount components in real situations — Fast Refresh, <Activity> becoming visible again, and future features that reuse state. The correct response is to make the effect idempotent: connect/disconnect, subscribe/unsubscribe, abort in-flight requests. The wrong response — using a ref as a "has run" guard — passes the test by cheating and leaves the real bug in production.

Example

// The cheat that hides the bug.
const didRun = useRef(false);
useEffect(() => { if (didRun.current) return; didRun.current = true; init(); }, []);

// The fix: make it survive a remount.
useEffect(() => {
  const controller = new AbortController();
  init({ signal: controller.signal });
  return () => controller.abort();
}, []);

Follow-ups

  • Does this happen in production? — Not the double-invocation, but the remount does, so an effect that only works once is a latent production bug.
  • What about an analytics "page view" event firing twice? — In development only; if it genuinely must fire once per navigation, fire it from the router event rather than a component effect.
  • What else does StrictMode double-invoke? — Render functions, state updater functions and reducers, to surface impurity.

Common wrong answer

"Turn off StrictMode — it causes double fetches." Extremely common, and it is the exact opposite of the intended lesson. Interviewers use this question to see whether you treat framework warnings as noise or as information.

midName the cases where people write an effect and shouldn't.

Answer

Four recur constantly. First, transforming data for rendering — compute it during render instead; a filtered list does not need to be state. Second, resetting or adjusting state when a prop changes — use a key, or adjust state during render with a guard. Third, handling user events — the logic belongs in the event handler, where you know why it happened; an effect only knows that something changed. Fourth, chains of effects that each set state to trigger the next one, which produce multiple render passes and are impossible to follow. The underlying rule: effects are for synchronising with systems outside React. If nothing outside React is involved, it is probably not an effect.

Example

// ❌ Effect chain: four renders, and no one can tell what triggers what.
useEffect(() => { if (card !== null) setGoldCount(c => c + 1); }, [card]);
useEffect(() => { if (goldCount > 3) setRound(r => r + 1); }, [goldCount]);
useEffect(() => { if (round > 5) setIsGameOver(true); }, [round]);

// ✅ One event handler that owns the whole transition.
function handlePlaceCard(nextCard) {
  const nextGold = card !== null ? goldCount + 1 : goldCount;
  const nextRound = nextGold > 3 ? round + 1 : round;
  setCard(nextCard); setGoldCount(nextGold); setRound(nextRound);
  setIsGameOver(nextRound > 5);
}

Follow-ups

  • What about fetching data — is that a legitimate effect? — It is an external system, so yes in principle, but a query cache, a route loader or a Server Component handles races, dedupe and caching that you would otherwise reimplement.
  • Is subscribing to a store a legitimate effect? — Prefer useSyncExternalStore; the effect version can miss updates and tears under concurrent rendering.
  • How do you spot effect chains in review? — Any effect whose only job is to call a setter based on other state; grep for useEffect bodies containing only a set* call.

Common wrong answer

"Effects are fine as long as the dependency array is right." Correct dependencies make an effect run at the right time; they do not make an unnecessary effect necessary. The extra render pass and the impossible-to-follow causality remain.

midThe lint rule wants a dependency you don't want to add. What do you do?

Answer

Treat it as a design problem, never as a lint problem — suppressing the rule is how stale-closure bugs are born. There are four honest fixes, in order of preference: move the value out of the effect if it is not reactive (a constant or a function that can live outside the component); wrap the non-reactive part in useEffectEvent (React 19.2) so the effect reads the latest value without depending on it; make the dependency stable at its source, by memoizing the object or by passing primitives instead; or accept that the effect really should re-run and fix whatever makes that expensive. The remaining case — a genuinely one-time initialisation — usually belongs outside React entirely, at module scope.

Example

// ❌ Lying to the linter: onMessage is captured from the first render forever.
useEffect(() => { socket.on('msg', onMessage); }, []); // eslint-disable-line

// ✅ The non-reactive part is an Effect Event.
const onMessage = useEffectEvent((msg) => append(msg, currentUser));
useEffect(() => {
  const socket = connect(roomId);
  socket.on('msg', (m) => onMessage(m));
  return () => socket.close();
}, [roomId]);

Follow-ups

  • Is there ever a legitimate suppression? — Rarely; the honest form is a comment explaining the invariant you are asserting. If you cannot write that sentence, the code is wrong.
  • What if the dependency is an object prop from a parent? — Depend on the fields you actually use, or ask the parent for a stable reference; depending on a whole object is usually the bug.
  • Does the compiler fix unstable dependencies? — It stabilises values it creates, but a prop from an uncompiled parent or a third-party hook can still change identity every render.

Common wrong answer

"Add // eslint-disable-next-line react-hooks/exhaustive-deps — I know the value doesn't change." Sometimes true today, never true after the next refactor, and the resulting bug is a stale value that appears only for users who navigate in a particular order. Interviewers who ask this have debugged that bug.

midWhen do you use useLayoutEffect instead of useEffect?

Answer

When you must read layout and change it before the user sees the first paint — measuring a tooltip to decide whether it flips above or below the trigger, measuring a list to size a virtualization window, or reading scroll position before restoring it. useLayoutEffect runs synchronously after the DOM mutation and before paint, so it blocks the frame: that is precisely its value and precisely its cost. Everything else — subscriptions, fetching, analytics, most DOM side effects — belongs in useEffect. The SSR caveat matters in interviews: useLayoutEffect does not run on the server and warns if a server-rendered component uses it, which is why libraries define an isomorphic wrapper.

Example

function Tooltip({ targetRect, children }) {
  const ref = useRef(null);
  const [height, setHeight] = useState(0);
  useLayoutEffect(() => {
    setHeight(ref.current.getBoundingClientRect().height); // measured before paint
  }, []);
  const flipped = targetRect.top - height < 0;
  return <div ref={ref} className={flipped ? 'below' : 'above'}>{children}</div>;
}

Follow-ups

  • Why does it warn during SSR? — There is no layout on the server, so the effect cannot run; the server HTML would differ from what the client measures.
  • What is the isomorphic workaround? — const useIsoLayoutEffect = typeof window !== 'undefined' ? useLayoutEffect : useEffect; — used by nearly every UI library.
  • Is there a modern alternative for measurement? — Often yes: ResizeObserver in a normal effect, CSS anchor positioning, or container queries remove the need to measure in JS at all.

Common wrong answer

"Use useLayoutEffect when you need the effect to run earlier / to avoid flicker." Half right, and it becomes a habit: candidates start using it everywhere "just in case", which serialises work into the critical frame and produces the jank they were trying to avoid.

seniorShow me how you handle a race condition when fetching in an effect.

Answer

The failure is ordering: the user types "ab" then "abc", the response for "ab" arrives last, and the UI shows results for the wrong query. Two correct patterns. The minimal one is an ignore flag captured in the effect's closure and flipped in the cleanup, so a late response from an obsolete effect is discarded. The better one is an AbortController, which additionally cancels the request so you stop paying for it — important on mobile. Either way the point is that the cleanup function is the cancellation mechanism, and the fact that this is manual and easy to get wrong is the strongest argument for using a query cache or a route loader instead of hand-written fetching.

Example

useEffect(() => {
  const controller = new AbortController();
  let ignore = false;
  fetchResults(query, { signal: controller.signal })
    .then(r => { if (!ignore) setResults(r); })
    .catch(e => { if (e.name !== 'AbortError' && !ignore) setError(e); });
  return () => { ignore = true; controller.abort(); };
}, [query]);

Follow-ups

  • Why keep ignore if you already abort? — abort() does not retroactively stop an already-resolved promise's .then from running; the flag closes that window.
  • How does a query cache solve it? — Requests are keyed, so a stale response is written to its own key and simply is not the one being read; dedupe and retry come along too.
  • Does use() with Suspense have this problem? — The race moves to whoever creates the promise: if the promise is created during render it must be cached, otherwise every render starts a new request.

Common wrong answer

"Debounce the input, so only the last request is sent." It reduces the probability without removing the race — a slow first response still lands after a fast second one. Interviewers explicitly listen for whether cancellation is about correctness or about saving requests.

seniorAn effect loops infinitely. Walk me through the debugging.

Answer

Almost always one of three causes. One: the effect sets state that is in its own dependency array — including indirectly, via a value derived from that state. Two: a dependency is a new reference every render, typically an object, array or function created in the component body or received as an inline prop, so the comparison never matches. Three: a parent re-renders on every commit — often because of the same problem one level up — so nothing below can stabilise. I would find which one by logging the dependency array with the previous values compared item by item, or with the DevTools "why did this render" data; then I would fix the source of instability rather than removing the dependency, because removing it converts a visible loop into an invisible stale value.

Example

// A five-line hook that names the culprit instead of guessing.
function useWhyDeps(name, deps) {
  const prev = useRef(deps);
  useEffect(() => {
    deps.forEach((d, i) => {
      if (!Object.is(d, prev.current[i])) console.log(name, 'dep', i, prev.current[i], '→', d);
    });
    prev.current = deps;
  });
}

Follow-ups

  • Why does [{ id }] as a dependency loop? — Object literals are compared by reference; a fresh literal is never Object.is-equal to the previous one. Depend on id.
  • Does setting state to the same value still loop? — No, React bails out on Object.is-equal state — but a new object with the same contents is not equal, which is the trap.
  • What if the loop only happens in production? — Suspect a different code path, a memoization the compiler applied differently, or an effect racing with a subscription; reproduce with a production build locally first.

Common wrong answer

"Remove the dependency that is changing, or use an empty array." It stops the loop and creates a stale closure that will produce a subtler bug next sprint. The interviewer is watching whether you fix causes or symptoms.

seniorHow do you make effects safe under Suspense, <Activity> and future state reuse?

Answer

By assuming any effect can be set up and torn down repeatedly on the same component instance, in any order, at any time. That means: every subscription has a cleanup; every request is abortable; nothing is guarded by a "has already run" flag; nothing assumes it runs exactly once per component lifetime; and nothing depends on paint having happened unless it is a layout effect. <Activity mode="hidden"> (19.2) makes this concrete — hidden trees keep state but unmount effects, so an effect that leaks a listener now leaks it every time the user switches tabs. The same discipline is what makes StrictMode's double-invocation a non-event, which is why I treat "does this survive StrictMode?" as the cheap proxy for "is this effect correct?".

Example

// Idempotent by construction: safe to run any number of times, in any order.
useEffect(() => {
  const el = ref.current;
  const observer = new ResizeObserver(onResize);
  observer.observe(el);
  return () => observer.disconnect();
}, [onResize]);

Follow-ups

  • What about effects that must run exactly once per user session? — Move them out of components: module scope, an app bootstrap, or a router event. Components are not the right lifetime.
  • How does this interact with Server Components? — Server Components have no effects at all; anything effect-shaped forces a Client Component, which is a useful architectural constraint.
  • How do you test it? — Render, unmount, render again in the same test and assert no duplicate listeners; a simple test that catches a whole bug class.

Common wrong answer

"Use a ref guard so the effect body only runs once — that makes it safe everywhere." It makes the symptom disappear on first mount and guarantees the effect never re-establishes itself after a legitimate remount, so the tab that used to work is dead the second time it is opened.

principalYour team writes effects for everything and the app has mysterious render cascades. How do you fix the culture, not just the code?

Answer

I would start by making the problem legible: count the effects whose body only calls setters, count the average renders per interaction on the two worst screens, and put both on a dashboard. Then I would give the team a replacement vocabulary rather than a prohibition — "derive during render", "handle it in the event handler", "use a key to reset", "use the query cache for server data" — because "stop using effects" without alternatives just produces guilt. Mechanically: the hooks lint at error level, a code-review checklist item, one worked refactor of a screen everybody knows, done in a pairing session and recorded. And I would put a ceiling on it: pick the three screens where the cascades actually hurt users and fix those, rather than launching an effect-elimination programme across the codebase, because the goal is user-visible latency, not effect count.

Example

# Make the debt countable before arguing about it.
rg -U --multiline 'useEffect\(\(\) => \{[^}]*\bset[A-Z][^}]*\}, \[' src --stats

Follow-ups

  • How do you handle the senior engineer who disagrees? — Take the disagreement seriously in public: pick a case they defend, profile it together, and let the numbers settle it. A decision imposed by title does not survive contact with the codebase.
  • What if the cascades come from a third-party library? — Isolate it behind an adapter component and, if the cost is real, budget for replacing it; document the constraint so nobody re-litigates it monthly.
  • How would you measure success? — Renders per interaction on the target screens, and p75 INP. If those do not move, the refactor was aesthetic.

Common wrong answer

"Write a lint rule that bans useEffect, and require an exception review." Effects are a legitimate primitive; banning them pushes the same logic into worse hiding places (layout effects, subscriptions in refs) and burns the credibility you need for the next change.

05State management at scale

The sub-area where opinions are strongest and interviewers are most alert to dogma. Nobody senior wants to hear "always Redux" or "Context is enough"; they want to hear you separate the four kinds of state — URL, server cache, shared client state, local UI state — and choose per kind. Mid-level is tested on Context mechanics and its re-render trap; senior on designing the layering for a real app; principal on what happens when several teams, or several deployment units, must share it.

Docs: react.dev — Scaling Up with Reducer and Context

screenerWhat is Context for, and what is it not for?

Answer

Context is dependency injection: it passes a value down the tree to any depth without threading props through components that do not care — theme, locale, the current user, a router instance, a store handle. It is not a state manager: it has no selectors, no partial subscriptions and no update batching, so every consumer re-renders whenever the provider's value changes by reference. The React 19 ergonomic change is worth knowing: <Context> can be rendered directly as the provider instead of <Context.Provider>, and use(Context) can read context conditionally, which useContext cannot.

Example

const ThemeContext = createContext('light');

// React 19: the context itself is the provider.
<ThemeContext value={theme}>
  <App />
</ThemeContext>

// Legacy form, still everywhere in existing codebases:
<ThemeContext.Provider value={theme}><App /></ThemeContext.Provider>

function Button() {
  const theme = use(ThemeContext);   // may be called conditionally
}

Follow-ups

  • What is the default value actually for? — Only for consumers rendered with no provider above them; in practice it is best used as a "you forgot the provider" error rather than a real default.
  • Does context cross a Server/Client boundary? — No. Context is a client concept; Server Components cannot consume it, which is why providers live in a client-side layout component.
  • How many contexts is too many? — There is no hard limit, but a provider pyramid twenty deep is a smell that shared state should live in a store instead.

Common wrong answer

"Context replaces Redux." It replaces prop drilling. Once you need selectors, middleware, devtools time travel or updates that do not re-render every consumer, you are rebuilding a store on top of context — badly.

midChanging one field in a context value re-renders every consumer. How do you fix it?

Answer

Three fixes, in order of how much they change. First, split the context by update frequency: a stable context for the dispatch/actions and a separate one for the changing value, so components that only act never re-render. Second, keep the provider's value referentially stable — memoize it, or let the compiler do it — because an inline object literal re-renders every consumer on every provider render regardless of content. Third, if you genuinely need many consumers reading different slices of a frequently-changing value, stop using context as the store: put the state in an external store and read it with useSyncExternalStore plus a selector, which is exactly what Zustand, Redux and Jotai do internally.

Example

const StateCtx = createContext(null);
const DispatchCtx = createContext(null);     // stable forever

function Provider({ children }) {
  const [state, dispatch] = useReducer(reducer, initial);
  return (
    <DispatchCtx value={dispatch}>
      <StateCtx value={state}>{children}</StateCtx>
    </DispatchCtx>
  );
}
// A component that only dispatches never re-renders when state changes.
const dispatch = use(DispatchCtx);

Follow-ups

  • Does memo on the consumer help? — No. Context propagation bypasses the props comparison entirely.
  • Would a selector-based context library help? — use-context-selector exists and works, but at that point an external store is simpler and better supported.
  • Is the re-render actually expensive? — Often not; measure before splitting contexts, because context splitting has a real readability cost.

Common wrong answer

"Wrap the consumers in React.memo." It is the reflex, it does nothing for context, and it tells the interviewer the candidate has not internalised how context propagation differs from props.

midRedux, Zustand, Jotai, TanStack Query — how do you choose?

Answer

They answer different questions, so the first move is to classify the state. Server data — anything that lives in a database and can go stale — belongs in a query cache (TanStack Query, SWR, or a framework's loader/RSC data flow), which gives you dedupe, revalidation, retries and cancellation for free. Genuinely shared client state — a multi-step wizard, an editor's selection, a design-tool canvas — belongs in a store: Zustand for a small imperative store, Jotai/Recoil-style atoms when the state graph is fine-grained and derived, Redux Toolkit when you need strict conventions, devtools and a large team's discipline. Local UI state stays in components, and URL state stays in the URL. The answer that lands in interviews is that most apps need a query cache plus almost no global state, and that "which library" is the least interesting part of the decision.

Example

Kind of stateHomeWhy
Filters, tab, pageURLLinkable, back-button-correct, server-renderable
Orders, profile, search resultsQuery cache / RSCStaleness, dedupe, retry, cancellation
Cart, wizard, editor selectionStoreShared across routes, survives navigation
Dropdown open, hover, draft textComponentNothing else needs it

Follow-ups

  • Is Redux dead? — No; Redux Toolkit is alive and reasonable, and RTK Query is a competent server-cache layer. What died is hand-written Redux boilerplate for server data.
  • What is the cost of Jotai-style atoms at scale? — Excellent granularity, but the state graph becomes implicit; debugging "who invalidated this atom" gets hard without discipline.
  • How does RSC change the answer? — It removes much of the client cache for read-mostly pages; the store shrinks to genuinely interactive state.

Common wrong answer

"Zustand, because it's the modern one / Redux, because it's the standard." A library-first answer with no classification of state. Interviewers are listening for the four categories; the library name is a detail you can change later.

midWhat is the difference between server state and client state, and why does it matter so much?

Answer

Client state is owned by the browser session: you created it, nobody else can change it, and it disappears when the tab closes. Server state is a cache of something owned elsewhere: it can be changed by other users, it goes stale the moment you receive it, it can fail to load, and two components asking for it should not produce two requests. Treating server state as client state is the single most expensive mistake in React apps, because you end up hand-implementing staleness, deduplication, retry, cancellation, refetch-on-focus and invalidation — usually incompletely, usually per feature. Once you name the distinction, the tool choice follows and most "global state" disappears.

Example

// Server state pretending to be client state: manual everything, no invalidation story.
const [orders, setOrders] = useState([]);
useEffect(() => { fetchOrders().then(setOrders); }, []);

// Server state as a cache, with the semantics named and shared across components.
const { data, isStale, refetch } = useQuery({
  queryKey: ['orders', customerId],
  queryFn: fetchOrders,
  staleTime: 30_000,
  refetchOnWindowFocus: true,
});

Follow-ups

  • How do you invalidate after a mutation? — Invalidate by key after the mutation settles, and optimistically update the cache if the interaction needs to feel instant.
  • What is a good default staleTime? — It is a product decision: zero for a trading screen, minutes for a settings page. Defaults that were never discussed are how apps get chatty.
  • How does this change with Server Components? — The cache moves to the server and to the framework's router cache; the client keeps only what interactivity requires.

Common wrong answer

"They're both just state — the difference is where it came from." That framing produces a global store full of API responses with manual invalidation, which is the exact architecture query caches were invented to replace.

seniorDesign the state architecture for a large app with 40 routes and 8 teams.

Answer

I would define four layers and make the boundaries explicit rather than cultural. URL owns navigational state — route params, filters, pagination, selected tab — with one convention for serialisation so teams do not invent their own. A single query-cache instance owns server data, with a documented cache-key convention ([domain, entity, id, params]) so that one team's mutation can invalidate another's list without knowing about it. A small, explicitly-owned global store holds cross-cutting client state — auth session, feature flags, toasts, a cart — and everything else is local. The organisational half matters more than the technical half: each layer needs an owner, the cache-key convention needs to be lint-checked or code-reviewed, and there must be a written rule for what may be added to the global store, because without one it becomes a junk drawer within two quarters.

Example

// One key factory per domain, exported from the domain package.
export const orderKeys = {
  all:    ['orders'] as const,
  list:   (f: Filters) => [...orderKeys.all, 'list', f] as const,
  detail: (id: string) => [...orderKeys.all, 'detail', id] as const,
};

// Any team can invalidate correctly without reading another team's code.
queryClient.invalidateQueries({ queryKey: orderKeys.all });

Follow-ups

  • How do you stop the global store growing? — A written admission test (cross-route, cross-team, survives navigation) plus a named owner who reviews additions.
  • What about state shared between two teams' features? — Prefer the URL or the server as the shared medium; a shared in-memory store between teams is a coupling you will pay for at release time.
  • How do you migrate an existing junk-drawer store? — Freeze additions, classify what is in it, move server data to the cache first (usually 60–70% of it), then re-home the rest.

Common wrong answer

"One Redux store, one slice per team, everything in it." It is legible and it makes every feature's data global, so nothing can be reasoned about locally and every mutation is a potential cross-team incident. Interviewers want boundaries, not a shared address space.

seniorWhen is prop drilling actually fine, and when is it a real problem?

Answer

Two or three levels of prop drilling is not a problem; it is explicit data flow, which is easier to read and refactor than any indirection you would replace it with. It becomes a problem when the intermediate components have no interest in the value — you are threading currentUser through six layout components — or when adding a field means touching a dozen files. Before reaching for context, though, the cheaper fix is usually composition: pass elements as children or as props so the consumer is created where the data already is. That removes the drilling and, as a side effect, stops the intermediate re-renders. Context is the right answer for genuinely ambient values, and a store for genuinely shared mutable ones.

Example

// Drilling user through components that do not use it.
<Layout user={user}><Sidebar user={user} /><Content user={user} /></Layout>

// Composition: build the consumers where the data lives.
<Layout
  sidebar={<Sidebar user={user} />}
  content={<Content user={user} />}
/>

Follow-ups

  • Does composition help performance too? — Yes: the element is created by a component that did not re-render, so React bails out on that subtree without any memoization.
  • What is the readability trade-off? — Element props can make a component's API sprawl; three or four slots is usually the limit before it reads worse than drilling.
  • How does this interact with RSC? — Passing a Server Component as children of a Client Component is the standard way to keep server-rendered content out of the client bundle.

Common wrong answer

"Prop drilling is an anti-pattern; use context." Applied consistently it produces an app where nothing has visible inputs and every component depends on ambient state — much harder to test and to move. The senior answer names composition as the middle option.

seniorHow do you implement optimistic updates, and what has to be true for them to be safe?

Answer

Show the intended result immediately, keep the pre-mutation value, and roll back on failure with a clear message. React 19 gives this a first-class hook: useOptimistic returns an optimistic view of a value plus a setter usable inside an Action or transition, and React automatically reverts to the real value when the action settles. What makes it safe is not the hook: the mutation must be idempotent or safely retryable, the failure must be visible and recoverable rather than silently rolled back, and the operation must be one where being wrong for 200ms is acceptable — a like button, yes; a payment confirmation, no. I would also insist the server response is authoritative, so the final state always comes from the server rather than from the optimistic guess.

Example

function Thread({ messages, sendMessage }) {
  const [optimistic, addOptimistic] = useOptimistic(
    messages,
    (state, text) => [...state, { text, pending: true }],
  );

  async function action(formData) {
    const text = formData.get('message');
    addOptimistic(text);                    // instant, reverted automatically on failure
    await sendMessage(text);                // server response becomes the real state
  }

  return <form action={action}>{optimistic.map(renderMessage)}</form>;
}

Follow-ups

  • What happens if the user navigates away mid-flight? — The optimistic state is gone with the component; the mutation must still complete server-side, or you need a durable queue.
  • How do you show the failure? — Restore the previous value and tell the user what failed with a retry; a silent revert reads as a bug and destroys trust.
  • Where does this break down? — Anything with server-side validation the client cannot replicate (stock levels, permissions, pricing) — you will optimistically show a state the server will reject.

Common wrong answer

"Update local state immediately and refetch afterwards; if it fails, refetch again." The refetch hides the failure behind a flicker, the user never learns their action did not happen, and with a slow network the wrong value is on screen for seconds. Interviewers ask specifically about the rollback UX.

principalTwo independently deployed React apps must share a cart. How do you design that?

Answer

My first answer is that shared client state between deployment units is a coupling to avoid if there is any alternative, because it turns two independent releases into one distributed system with no schema and no versioning. The alternative I would push first: make the server the source of truth, give the cart an API and a stable contract, and let each app read and mutate it — the shared state becomes a cache in each app, invalidated by events or polling, and the two apps can deploy independently. If they genuinely must share in-browser state (a hard requirement is usually latency or offline), then I would define an explicit, versioned contract — a tiny shared store published as a package, or BroadcastChannel messages with a versioned payload — owned by one team, with backward compatibility rules and a deprecation policy, exactly as you would treat a public API. What I would not accept is two apps reaching into the same global object with no contract, which is what "just put it on window" becomes within a month.

Example

// Versioned contract, single owner, backwards-compatible by rule.
type CartEvent =
  | { v: 1; type: 'cart/updated'; cartId: string; itemCount: number }
  | { v: 1; type: 'cart/cleared'; cartId: string };

const channel = new BroadcastChannel('cart');
channel.postMessage({ v: 1, type: 'cart/updated', cartId, itemCount } satisfies CartEvent);
// Consumers ignore unknown versions rather than crashing.

Follow-ups

  • What about two React roots on the same page? — Same answer, plus practical issues: duplicate React copies, duplicate context providers, and event-bubbling surprises between roots.
  • How do you version the contract? — Additive changes only, a version field on every message, and a written support window; treat consumers as external clients.
  • When is a shared store genuinely justified? — When the shared state changes many times per second (a collaborative canvas) and the round trip would be felt. Then the coupling is a deliberate, documented trade.

Common wrong answer

"Use Module Federation to share the store singleton." A real technique, but as the first answer it accepts tight runtime coupling, a shared React version, and lockstep deploys without ever asking whether the server could own the state. Interviewers are testing whether you reach for the architectural answer before the tooling one.

06Suspense and concurrent rendering

The area where candidates most often have vocabulary without a model. Interviewers ask because concurrency changed what "a render" means: it can be interrupted, abandoned, or run at a lower priority, and Suspense is the declarative surface for "not ready yet". Mid-level is expected to explain transitions and Suspense boundaries; senior to place boundaries deliberately, reason about waterfalls, and combine them with error boundaries; principal to define a loading strategy for a whole product surface.

Docs: react.dev — <Suspense>

screenerWhat is <Suspense>, and what can suspend?

Answer

A boundary that declares a fallback to show while something inside it is not ready. When a component suspends, React stops rendering that subtree, shows the nearest boundary's fallback, and retries when the pending work resolves — so loading states become a property of a region of the tree rather than a flag in every component. What can suspend today: a lazy component loaded with React.lazy, a promise read with use(), and data fetched by a Suspense-enabled framework or library (RSC, Next.js, Remix/React Router, Relay, TanStack Query in suspense mode). What cannot: an arbitrary promise you create inside a component body during render, which is a very common misconception because it appears to work and then re-fetches forever.

Example

<Suspense fallback={<ProfileSkeleton />}>
  <Profile userId={id} />      {/* suspends via use(promise) or a lazy import */}
</Suspense>

Follow-ups

  • What happens if there is no boundary above a suspending component? — React throws; every suspending subtree needs a boundary, and the root usually has one as a safety net.
  • Does the fallback replace already-visible content on an update? — Only if the update is not in a transition. Inside startTransition, React keeps the current UI and switches when ready.
  • Do boundaries nest? — Yes, and the nearest one wins, which is how you make one region reload without blanking the page.

Common wrong answer

"Suspense lets you fetch data without useEffect — just throw a promise." Throwing promises was the unofficial React 16/17 hack; the supported surface is use() and framework integrations, and a promise created during render must be cached or it restarts on every attempt.

midWhat is use(), and how is it different from a hook?

Answer

Introduced in React 19, use() reads a resource during render: pass it a promise and the component suspends until the promise resolves, then use() returns the value; pass it a context and it reads the context. It breaks the hook rules on purpose — it can be called inside conditions and loops — because it does not allocate a hook slot. The critical constraint is where the promise comes from: it must be created outside the render that reads it (in a Server Component, in a cache, in an event handler, or by a framework), because a promise created inline during render is a new promise on every attempt, so the component suspends forever. use() is the bridge between the Suspense machinery and ordinary component code.

Example

// Server Component starts the request and passes the promise down — no await, no waterfall.
async function Page({ id }) {
  const commentsPromise = getComments(id);          // not awaited here
  return (
    <Suspense fallback={<Skeleton />}>
      <Comments promise={commentsPromise} />
    </Suspense>
  );
}

'use client';
function Comments({ promise }) {
  const comments = use(promise);                    // suspends until resolved
  return <ul>{comments.map(c => <li key={c.id}>{c.text}</li>)}</ul>;
}

Follow-ups

  • What happens if the promise rejects? — The nearest error boundary catches it, so error UI is declarative too.
  • Can you call use() in an event handler? — No; it is a render-time API. Await the promise normally in handlers.
  • Why is use(Context) useful over useContext? — It can be called conditionally, e.g. after an early return, which removes a class of awkward wrapper components.

Common wrong answer

"use() replaces useEffect for data fetching in client components — call use(fetch(url))." That creates a new promise each render and suspends indefinitely. The interviewer's follow-up is always "where does the promise come from?", and this answer has no good response to it.

midWhat problem do transitions solve, and how do you use useTransition?

Answer

They let you mark an update as non-urgent, so React can keep the interface responsive while it renders it and can interrupt or abandon that render if something more urgent arrives. The canonical case is navigation or filtering: the click must feel instant, but the new screen may take 300ms to render, and without a transition the whole tab freezes during it. useTransition gives you [isPending, startTransition] so you can also show a pending indicator without a spinner replacing the current content. In React 19 transitions also became the substrate for Actions: async functions passed to startTransition are tracked, and useActionState/form actions build on that.

Example

const [isPending, startTransition] = useTransition();

function selectTab(next) {
  setActiveTab(next);                       // urgent: the tab highlights immediately
  startTransition(() => setContent(next));  // non-urgent: heavy content, interruptible
}

return <div style={{ opacity: isPending ? 0.7 : 1 }}>{content}</div>;

Follow-ups

  • What must not go in a transition? — Anything the user must see instantly: controlled input values, hover states, anything driving the caret.
  • Does a transition make rendering faster? — No, it reprioritises. If the render is slow, it is still slow — it just no longer blocks input.
  • How do transitions interact with Suspense? — Inside a transition React keeps showing the old UI instead of falling back to the boundary's fallback, which is what makes navigations feel smooth.

Common wrong answer

"startTransition runs the update asynchronously / in the background thread." There is one thread; the work is scheduled at a lower priority and can be interrupted. Describing it as a background thread leads people to expect parallelism that does not exist.

midWhen do you use useDeferredValue instead of useTransition?

Answer

Use useTransition when you control the update — you are the one calling the setter, so you can wrap it. Use useDeferredValue when you only have the value: a prop from a parent, or a value you must keep current for one part of the UI and may lag for another. It renders the expensive subtree with the previous value first, then re-renders with the latest one at lower priority, and comparing the deferred value to the current one gives you a free "stale" flag for a visual hint. In practice deferred values are the tool for the "responsive input, expensive list" pattern, and transitions are the tool for navigation and tab switches.

Example

const deferred = useDeferredValue(query);
const isStale = deferred !== query;
<Results query={deferred} className={isStale ? 'stale' : ''} />

Follow-ups

  • Does the expensive child need memo? — Yes, or compiler memoization: if it re-renders regardless of whether its props changed, deferring the value buys nothing.
  • What about the initial render? — React 19 added an optional initial value so the first render can show something cheap instead of the full result.
  • Deferred value or debounce? — Deferred value adapts to the device; debounce imposes a fixed delay on everyone, including users whose machine could keep up.

Common wrong answer

"They're the same thing with different ergonomics." They differ in what they defer — an update versus a value — and in whether you need to own the setter. A candidate who cannot say which one applies to a prop they do not control has memorised both API pages.

seniorHow do you decide where Suspense boundaries go?

Answer

Boundaries are a UX decision expressed in the tree, so I place them where a region of the page can meaningfully load independently and where a skeleton is honest about the final layout. Too few boundaries and the whole page waits for the slowest query; too many and the page assembles in a dozen visible steps, which measures well and feels terrible, and each one is a layout-shift risk. My defaults: one boundary per major region (header, primary content, sidebar), a boundary around anything with a p95 latency noticeably worse than its siblings, and no boundary at all around things that resolve in tens of milliseconds. React 19.2 made this easier by batching Suspense reveals during streaming SSR, so content appears in groups rather than one boundary at a time — but it does not fix boundaries placed around trivially small units.

Example

<Layout>
  <Header />                                  {/* fast: no boundary */}
  <Suspense fallback={<FeedSkeleton />}>      {/* p95 ~400ms */}
    <Feed />
  </Suspense>
  <Suspense fallback={<PanelSkeleton />}>     {/* slow third-party: isolate it */}
    <RecommendationsPanel />
  </Suspense>
</Layout>

Follow-ups

  • How do you avoid layout shift from fallbacks? — Skeletons must reserve the real dimensions; a fallback that is shorter than the content guarantees a CLS hit.
  • What does batching reveals change (19.2)? — Server-streamed boundaries that resolve close together are revealed together, matching client behaviour and reducing the "popcorn" effect.
  • Should every boundary have its own error boundary? — Wherever a partial failure should not take out the page, yes — the two usually come as a pair.

Common wrong answer

"Put one Suspense boundary at the root so nothing ever crashes into a missing fallback." That converts every slow query into a full-page spinner and throws away streaming entirely. It is safe, and it is the answer of someone who has never watched their page load on 4G.

seniorHow do error boundaries work, and what do they not catch?

Answer

An error boundary is a component with static getDerivedStateFromError and/or componentDidCatch — still class-only in React 19, which is why most teams use react-error-boundary. It catches errors thrown during rendering, in lifecycle methods and in constructors of the tree below it. It does not catch errors in event handlers, in async code (a rejected promise in a setTimeout or a fetch callback), in server-side rendering, or in the boundary itself. React 19 also improved the reporting story: uncaught errors go to onUncaughtError, handled ones to onCaughtError via createRoot options, and duplicate logging of caught errors was removed. Practically I pair boundaries with Suspense boundaries so one failing region degrades instead of blanking the app, and I always wire them to the error tracker with the component stack.

Example

const root = createRoot(container, {
  onUncaughtError: (error, { componentStack }) => report(error, componentStack),
  onCaughtError:   (error, { componentStack }) => report(error, componentStack, 'handled'),
});

<ErrorBoundary fallback={<PanelError />}>
  <Suspense fallback={<PanelSkeleton />}>
    <RecommendationsPanel />
  </Suspense>
</ErrorBoundary>

Follow-ups

  • How do you catch event-handler errors? — try/catch in the handler, plus a global window.onerror / unhandledrejection hook for the rest.
  • What happens on a hydration mismatch in React 19? — You get a single error with a diff of server vs client HTML instead of the old cascade of vague warnings — much faster to debug.
  • Should the boundary offer a retry? — Yes where the failure is transient; resetting the boundary's key re-mounts the subtree and re-runs the query.

Common wrong answer

"Error boundaries catch all errors in their subtree." The gaps — event handlers and async code — are exactly where most production errors happen, so a team relying on this ships an app whose error tracker is quiet while users see broken screens.

seniorWhat is a request waterfall in a Suspense app, and how do you eliminate it?

Answer

A waterfall is a sequence of requests where each can only start after the previous one finishes, usually because a parent awaits its data before rendering the child that starts the next request. Suspense makes waterfalls easy to create accidentally: await at the top of a Server Component, or a child component that fetches based on the parent's result. The fixes are to start requests as early as possible and in parallel — kick off all the promises at the top of the parent and pass them down unawaited, so children use() them independently; hoist data requirements to a route loader; or preload on the server with preload/preinit. React 19.2's Partial Pre-rendering attacks the same problem from the other side, letting a static shell go out from a CDN immediately and the dynamic parts resume later.

Example

// ❌ Serial: user → orders → recommendations, three round trips end to end.
const user = await getUser(id);
const orders = await getOrders(user.id);
const recs = await getRecommendations(user.id);

// ✅ Parallel: one round trip's latency, children suspend independently.
const userPromise = getUser(id);
const ordersPromise = getOrders(id);
const recsPromise = getRecommendations(id);
return (
  <>
    <Suspense fallback={<S />}><User promise={userPromise} /></Suspense>
    <Suspense fallback={<S />}><Orders promise={ordersPromise} /></Suspense>
    <Suspense fallback={<S />}><Recs promise={recsPromise} /></Suspense>
  </>
);

Follow-ups

  • How do you detect waterfalls? — The network panel's staircase, or server traces; in RSC apps the framework's own timing output usually shows nested awaits.
  • What if the second request genuinely needs the first result? — Then it is a data-modelling problem: change the API so one call returns what the screen needs, rather than chaining on the client.
  • Does cache() help? — It deduplicates identical calls within a request, which removes redundant fetches but not sequencing.

Common wrong answer

"Add more Suspense boundaries so the slow parts stream in separately." Boundaries change what the user sees while waiting; they do not make a serial chain parallel. The total time to the last byte is unchanged, and the page now assembles in three visible jumps.

seniorHow does Suspense behave differently on the server during streaming SSR?

Answer

On the server, a suspending boundary does not block the response: React streams the fallback markup immediately and, when the data resolves, streams the real HTML later with a small inline script that swaps it in — so the shell reaches the browser fast and slow regions fill in. Hydration is selective and boundary-scoped: React can hydrate the parts that have arrived while others are still streaming, and it prioritises the part the user interacted with. React 19.2 changed one visible behaviour here: server-rendered boundaries now batch their reveals for a short window instead of revealing one at a time, matching client behaviour and preparing for View Transitions. 19.2 also brought renderToReadableStream and prerender to Node, though the React team still recommends the Node Streams APIs (renderToPipeableStream) there for performance and compression.

Example

import { renderToPipeableStream } from 'react-dom/server';

const { pipe, abort } = renderToPipeableStream(<App />, {
  bootstrapScripts: ['/main.js'],
  onShellReady() { res.status(200).setHeader('content-type', 'text/html'); pipe(res); },
  onShellError() { res.status(500).send('<!doctype html><p>Something went wrong'); },
});
setTimeout(abort, 10_000);   // bound the tail: give up on slow boundaries

Follow-ups

  • What is the shell? — Everything outside all Suspense boundaries; it must be fast, because nothing is sent until the shell is ready.
  • What happens if a boundary errors on the server? — React streams the fallback and lets the client retry that boundary; a shell error, by contrast, is a failed response.
  • Why bound with abort? — Otherwise one slow dependency holds the connection open; aborting degrades to client rendering for that region.

Common wrong answer

"With SSR, React waits for all the data and sends the complete HTML." That is renderToString, the legacy synchronous API — still common in older codebases, and exactly what streaming replaced. Candidates who describe it as current have not worked with React 18+ SSR.

principalDesign the loading strategy for a dashboard with twelve widgets of wildly different latency.

Answer

I would start from what the user actually needs first, not from the component tree: identify the one or two widgets that carry the primary decision, and guarantee those are in the shell or the first streamed chunk. Everything else is tiered — fast widgets grouped into one reveal so the page does not popcorn, slow ones behind their own boundaries with honest skeletons that reserve layout, and genuinely optional ones (a third-party feed, a recommendation panel) rendered lazily on visibility with an error boundary so their failure is invisible. Operationally I would set a per-widget latency budget with an abort deadline on the server render, so a degraded dependency costs a placeholder rather than the page, and I would measure LCP against the primary widget rather than against whatever happens to paint first. The organisational rule that makes it stick: each widget's team owns its p95 and its skeleton, and a widget that misses its budget gets demoted a tier rather than slowing everyone down.

Example

<Shell>                                        {/* primary KPI: in the shell, no boundary */}
  <PrimaryKpi data={kpi} />

  <Suspense fallback={<FastRowSkeleton />}>    {/* tier 2: grouped, one reveal */}
    <Revenue /><Orders /><Conversion />
  </Suspense>

  <ErrorBoundary fallback={null}>              {/* tier 3: optional, failure is silent */}
    <Suspense fallback={<PanelSkeleton />}>
      <Activity mode={inViewport ? 'visible' : 'hidden'}><PartnerFeed /></Activity>
    </Suspense>
  </ErrorBoundary>
</Shell>

Follow-ups

  • How do you decide the tiers? — With the product owner, from the job the dashboard does; engineers guessing at importance is how the slowest widget ends up in the shell.
  • What do you do about a widget that is slow because of a third party? — Deadline it, cache aggressively server-side, and make its absence a designed state rather than an error.
  • How do you keep this from rotting? — Budgets in CI plus a p95-per-widget dashboard; tiering decays silently as soon as nobody is looking at the numbers.

Common wrong answer

"Wrap each widget in its own Suspense boundary and let them stream independently." Technically fine, experientially awful: twelve independent reveals, twelve layout shifts, and no statement about what matters. Interviewers want prioritisation and degradation, not uniform treatment.

07Server Components and SSR

The highest-variance sub-area: some interviewers still treat RSC as exotic, others build the whole loop around it. Since React 19 made Server Components stable and the December 2025 CVEs put Server Functions on every security review's radar, "I've read about it" is no longer enough at senior level. Expect to explain the difference between RSC and SSR precisely, to reason about the client/server boundary and serialisation, and — at principal level — to say when not to adopt it, with a migration and a security argument.

Docs: react.dev — Server Components

screenerWhat is a React Server Component, and how is it different from server-side rendering?

Answer

SSR runs your components on the server to produce HTML for the initial load, then ships the same component code to the browser to hydrate it — the component exists in both places. A Server Component runs only on the server: it never ships to the client, has no state, no effects and no event handlers, can talk directly to a database or an internal service, and its output is serialised into the RSC payload — a description of UI, not HTML — which the client merges into its tree. The two are complementary, not alternatives: a typical framework app renders Server Components, streams SSR HTML for the first paint, and hydrates only the Client Components. The headline benefit is that data-fetching code and its dependencies (a markdown renderer, a date library, an ORM) stay off the client entirely.

Example

// Server Component: no bundle cost, direct data access, async by nature.
async function ProductPage({ id }) {
  const product = await db.product.findUnique({ where: { id } });
  return (
    <article>
      <h1>{product.name}</h1>
      <AddToCart productId={product.id} />   {/* the only client JS on this page */}
    </article>
  );
}

Follow-ups

  • Why is the payload not just HTML? — Because it must describe where Client Components sit and what props they get, so the client can hydrate and re-render them independently.
  • Can a Server Component re-render? — Only via a new server request (a navigation or a router refresh); there is no client-side re-render for it.
  • Do you need a framework? — Effectively yes: RSC requires a bundler integration and a router. Vite's RSC plugin, Next.js, React Router and Parcel provide it.

Common wrong answer

"Server Components are just SSR with a new name." It misses the whole point — the component code never reaches the browser — and it makes every follow-up about bundle size, serialisation and the boundary unanswerable.

midWhat does 'use client' actually do?

Answer

It marks a module as the boundary between the server graph and the client graph. The file and everything it imports get bundled for the browser; the components it exports become the entry points the RSC payload references. It is not a per-component annotation you sprinkle around — it is a doorway, and everything imported below that doorway is client code whether it says so or not. The practical consequence people get wrong: adding 'use client' to a component near the root pulls the entire subtree into the client bundle, which is how apps "adopt RSC" and ship exactly as much JavaScript as before. The right shape is to push the directive as far down the tree as possible and pass server-rendered content in as children.

Example

'use client';
// Everything this file imports is now client code.
export function Tabs({ children }) {
  const [active, setActive] = useState(0);
  return <div role="tablist">{children}</div>;
}

// Server Component: passes server-rendered children through a client wrapper,
// so the heavy content never enters the client bundle.
<Tabs><ServerRenderedReport /></Tabs>

Follow-ups

  • Can a Client Component import a Server Component? — Not directly; it can receive one as children or as an element prop, which is the standard interleaving pattern.
  • Is 'use client' needed in a non-RSC app? — No; it is inert outside an RSC bundler, which is why libraries ship it defensively.
  • How do you audit the boundary? — Bundle analysis per route plus a lint rule; the failure mode is silent growth, not an error.

Common wrong answer

"It means this component renders on the client instead of the server." Half true and misleading: Client Components are still server-rendered to HTML for the first paint. The directive is about which bundle the code lands in, not about where it renders.

midWhat can and cannot be passed from a Server Component to a Client Component?

Answer

Props crossing the boundary are serialised into the RSC payload, so they must be serialisable: primitives, plain objects and arrays, Date, Map, Set, TypedArray, promises, JSX elements, and references to Server Functions. What cannot cross: arbitrary functions (a callback like onSelect), class instances (an ORM model, an Error subclass with methods), Symbols other than well-known ones, and anything with behaviour rather than data. The two consequences worth stating: you must map database rows to plain objects at the boundary, which is good discipline anyway; and everything you pass is visible in the payload sent to the browser, so passing a whole user record because it was convenient is a data-leak, not just a payload-size problem.

Example

// ❌ Not serialisable, and the ORM object may carry fields you never meant to expose.
<Chart onPointClick={handleClick} model={prismaUser} />

// ✅ Data crosses; behaviour stays on its own side.
<Chart points={points.map(p => ({ x: p.x, y: p.y }))} onPointClickAction={saveClick} />
// saveClick is a Server Function ('use server'), passed as a reference.

Follow-ups

  • Can you pass a promise? — Yes, and it is the recommended way to stream data: pass it unawaited and let the client use() it.
  • What happens if you pass something unserialisable? — A build-time or render-time error naming the prop; it is one of the better error messages in the ecosystem.
  • How do you avoid leaking fields? — An explicit DTO mapping at the boundary, ideally typed, plus a review rule against passing ORM objects.

Common wrong answer

"Anything JSON-serialisable, so just JSON.stringify the object and you're fine." It is broader than JSON (Dates, Maps, promises, elements) and — more importantly — the answer skips the security consequence, which is what senior interviewers are actually probing.

midWhat is hydration, and what causes hydration mismatches?

Answer

Hydration is React attaching to server-rendered HTML: it renders the same tree on the client and, instead of creating DOM nodes, adopts the existing ones and wires up events and state. It requires the first client render to produce the same output as the server did. Mismatches come from a short list: values that differ per environment (Date.now(), Math.random(), locale-dependent formatting, timezones), browser-only APIs read during render (window, localStorage), invalid HTML nesting that the browser silently repairs (a <div> inside a <p>), and third-party scripts or extensions mutating the DOM before hydration. React 19 improved diagnosis substantially: instead of a cascade of vague warnings you get a single error with a diff of the server and client output.

Example

// ❌ Server and client disagree on the very first render.
<time>{new Date().toLocaleTimeString()}</time>

// ✅ Render the stable value, upgrade after mount.
const [now, setNow] = useState(null);
useEffect(() => setNow(new Date()), []);
<time suppressHydrationWarning>{now ? now.toLocaleTimeString() : '—'}</time>

Follow-ups

  • What does React do when it finds a mismatch? — It discards the server HTML for that subtree and client-renders it, which is correct but costs you the SSR benefit exactly where it happened.
  • When is suppressHydrationWarning legitimate? — For a single node whose content is genuinely time- or locale-dependent; it suppresses the warning for that node only, and it is not a fix for structural mismatches.
  • Why is useId relevant? — Ids must match across server and client; useId guarantees it, and 19.2 changed the prefix to _r_ so the ids are valid CSS selectors and XML names.

Common wrong answer

"Add suppressHydrationWarning to silence it." It hides the symptom on one node while the subtree may still be re-rendered from scratch, and it becomes a habit that masks real structural bugs — invalid nesting in particular, which will also break in ways nobody connects back to hydration.

seniorHow do Server Functions work, and what are the security implications?

Answer

A function marked 'use server' is not shipped to the client; instead the bundler creates an HTTP endpoint for it and gives the client a reference. Calling it from the browser posts a serialised argument list to that endpoint, React decodes it on the server and invokes the function. The security model follows directly: every Server Function is a public, unauthenticated HTTP endpoint until you authenticate it yourself. Anyone can call it with any arguments; closure variables captured in the function are serialised into the client payload and sent back by the client, so they are attacker-controlled and must be treated as untrusted input. December 2025 proved the point at framework level — CVE-2025-55182 (CVSS 10.0) was an unauthenticated RCE in the payload decoder that affected apps even if they defined no Server Functions of their own, patched in 19.0.1 / 19.1.2 / 19.2.1, with follow-ups CVE-2025-55184 (DoS) and CVE-2025-55183 (source-code exposure) on 11 December. So: authenticate and authorise inside every action, validate every argument, never trust a captured id, and keep the RSC runtime patched.

Example

'use server';
import { z } from 'zod';

const Input = z.object({ orderId: z.string().uuid(), note: z.string().max(500) });

export async function addNote(raw) {
  const session = await requireSession();               // 1. authenticate, every call
  const { orderId, note } = Input.parse(raw);           // 2. validate every argument
  await assertCanEditOrder(session.user, orderId);      // 3. authorise this user for this row
  return db.note.create({ data: { orderId, note, authorId: session.user.id } });
}

Follow-ups

  • Why isn't "the id came from a closure" safe? — Closure variables are serialised to the client and returned with the call; the client can change them. Treat them exactly like request body fields.
  • How do you rate-limit them? — At the edge or in middleware, per session and per IP; they are endpoints, so they need the same protections as any API route.
  • What did the December 2025 CVEs change operationally? — Most teams added the RSC packages to their patch SLA and started auditing which routes expose Server Functions at all.

Common wrong answer

"They're safe because the code only runs on the server and the client just calls a function." The classic and dangerous answer: it treats the RPC boundary as a language boundary. Every serious RSC security incident starts from this assumption, and interviewers in fintech or health ask this question specifically to find it.

seniorWhat is Partial Pre-rendering, and what problem does it solve?

Answer

Shipped in React 19.2 as a react-dom API, it lets you render a page in two stages: prerender() produces a static shell — everything that does not depend on the request — plus a serialisable "postponed" state, and later resume() (or resumeAndPrerender() for SSG) continues rendering the dynamic parts from that state. The point is that you can put the shell on a CDN and serve it instantly for every user, while the personalised parts stream in from an origin server. Before this you had to choose per route: fully static and impersonal, or fully dynamic and slower. It is a framework-level primitive — you consume it through your framework rather than calling it directly — and it pairs naturally with Suspense boundaries, which mark exactly what is dynamic.

Example

import { prerender, resume } from 'react-dom/static';

// Build time: static shell + postponed state.
const controller = new AbortController();
const { prelude, postponed } = await prerender(<App />, { signal: controller.signal });
await savePostponed(postponed);          // shell → CDN

// Request time: resume the dynamic holes into the stream.
const stream = await resume(<App />, await loadPostponed());

Follow-ups

  • How is this different from ISR/SSG? — Those cache a whole page; PPR splits one page into cached and dynamic parts, so a personalised header no longer forces the whole route to be dynamic.
  • What marks the dynamic parts? — Suspense boundaries around anything request-dependent; the shell is what renders without them.
  • What is the operational cost? — The postponed state is an artifact you must store and version with the build; a mismatch between shell and code is a new failure mode.

Common wrong answer

"It's Next.js's feature." PPR as a product feature is a framework wrapper; the underlying prerender/resume APIs are in React 19.2's react-dom/static. Attributing it entirely to a framework suggests the candidate learned React through one vendor's docs.

seniorWhere does caching live in an RSC app, and how do you reason about invalidation?

Answer

There are at least four layers and conflating them is the usual source of "why is this stale" incidents. Innermost is per-request memoisation: cache() deduplicates identical calls within one render, and React 19.2's cacheSignal() lets that work be aborted when the request ends. Then the framework's data cache — persisted results with their own TTL and tags. Then the route/router cache, both server-side (rendered RSC payloads) and client-side (payloads the router keeps for back-navigation). Outermost, the CDN. Invalidation must be explicit at each layer, and the layer that bites teams is the client router cache, because a successful mutation plus a server-side revalidation still shows stale UI until the client cache is refreshed too. I insist on a written policy per data type: what its TTL is, what invalidates it, and who owns that decision.

Example

import { cache, cacheSignal } from 'react';

// Deduplicated for this request, and cancelled if the request is aborted.
export const getUser = cache(async (id) => {
  const res = await fetch(`${API}/users/${id}`, { signal: cacheSignal() });
  if (!res.ok) throw new Error('user fetch failed');
  return res.json();
});

Follow-ups

  • Why does cacheSignal matter? — Without it, a user navigating away leaves database queries and fetches running to completion, burning capacity under load.
  • How do you debug "stale after mutation"? — Walk the layers outward and check which one still holds the old value; nine times out of ten it is the client router cache.
  • Tag-based or path-based invalidation? — Tags scale better across teams, because the mutating code does not need to know which routes render the data.

Common wrong answer

"The framework handles caching, you just call revalidate." Teams that believe this get intermittent staleness they cannot reproduce, because the failing layer is the one they did not know existed. Naming the layers is the entire signal in this question.

seniorWhen should a team not adopt Server Components?

Answer

When there is no server to speak of: a pure SPA behind a login shipped as static assets, an Electron or Capacitor app, an embedded dashboard, or anything deployed to a CDN with no runtime. When the app is overwhelmingly interactive — a design tool, an IDE, a trading terminal — because almost every component ends up a Client Component and you pay the complexity of the boundary for a small share of the tree. When the team has no operational appetite for running and patching a Node runtime, which the December 2025 CVEs made a concrete, recurring obligation. And when the framework lock-in is unacceptable, since RSC in practice means adopting a framework's router, bundler integration and caching model. The strongest version of this answer names the benefit you would be buying — less client JavaScript and direct data access — and then says the app in question does not have that problem.

Example

App shapeRSC fitWhy
Content-heavy, read-mostly, SEO mattersStrongBig bundle savings, direct data access, streaming
Authenticated CRUD dashboardReasonableFewer client fetches; boundary discipline required
Highly interactive editor / canvasWeakNearly everything is a Client Component anyway
Static-hosted SPA, no server runtimeNoneRSC needs a server; SSG plus a client cache is simpler

Follow-ups

  • Can you adopt it partially? — Yes: a marketing surface or a documentation area can be RSC while the app shell stays a client SPA, if the router supports both.
  • What is the hidden cost people forget? — Debugging and observability: stack traces cross a network boundary, and local reproduction now involves the server runtime.
  • Does the compiler change the calculus? — Slightly: it reduces the client-side performance argument for RSC, since client rendering got cheaper.

Common wrong answer

"RSC is the future, so every new app should use it." It is a fashion answer, and interviewers at companies that tried and reverted will push hard on it. The senior signal is naming a concrete app shape where it is the wrong tool.

principalYour company runs a five-year-old CRA-era SPA. Make the call on modernising it, and justify it to a VP.

Answer

I would separate three decisions that people habitually bundle: the build tool, the React version, and the rendering architecture. The build tool is urgent and cheap — Create React App was sunset on 14 February 2025 and is unmaintained, so moving to Vite is a week or two with an immediate developer-experience win and no product risk. The React version is next: 18 to 19 is a real but bounded upgrade, and it unlocks the compiler, Actions and better error diagnostics. The rendering architecture — moving to RSC — is the expensive one, and I would only do it where there is a measured business problem it solves: slow first load on a public, indexable surface, or a client bundle that has stopped responding to code splitting. To the VP I would frame it as risk and cost, not novelty: unmaintained tooling is a security and hiring liability; the React upgrade is a bounded investment with concrete performance and DX returns; the architecture change is a product decision that needs its own business case and its own quarter. And I would propose doing the first two now and piloting the third on one route, with metrics agreed in advance.

Example

# Sequence the work so each step ships independently and can be stopped.
# 1. CRA → Vite (no React change), keep tests green
# 2. React 18 → 19: codemods, then StrictMode clean-up
npx codemod@latest react/19/migration-recipe
# 3. eslint-plugin-react-hooks v6 → fix violations → enable the compiler on one area
# 4. RSC pilot on the public marketing route only, with LCP/INP targets agreed up front

Follow-ups

  • What if the VP wants the rewrite? — Offer the pilot with a success metric and a stop condition. "We will know in six weeks" beats both "no" and "yes, twelve months".
  • How do you keep feature delivery going? — Steps 1 and 2 are cross-cutting but short; the pilot is one route with one team. Nothing here requires a freeze, and I would say that explicitly.
  • What is the risk you would flag loudest? — The RSC runtime becomes an operational responsibility, with a patch SLA — the December 2025 CVEs are the evidence, not a hypothetical.

Common wrong answer

"Rewrite it in Next.js — we get RSC, routing and performance in one move." It bundles three separable decisions into one irreversible project, hides the migration risk behind a framework choice, and gives the VP no way to stop halfway. The principal-level signal is decomposition and a stop condition.

08Forms, Actions and mutations

React 19 changed this area more than any other: form action props, useActionState, useFormStatus and useOptimistic replaced a decade of hand-rolled submit handlers with pending flags. Interviewers use it to check whether you are current, and because forms are where correctness (validation, double submits, error recovery) meets UX (pending states, optimistic feedback). Mid-level should know controlled versus uncontrolled and the new hooks; senior should be able to talk about progressive enhancement and idempotency.

Docs: react.dev — <form> and Actions

screenerControlled or uncontrolled inputs — how do you choose?

Answer

Controlled means React owns the value: value plus onChange, so every keystroke is a state update and the DOM is always in sync with your state. Uncontrolled means the DOM owns it and you read it when you need it, via a ref or, more idiomatically now, from the FormData the form action receives. Controlled is right when you need to react to every keystroke — live validation, formatting, dependent fields, a search-as-you-type. Uncontrolled is right for plain forms, is dramatically cheaper on big forms, and is what React 19's form actions assume. The mistake is treating "controlled" as the default professional choice; a 40-field form with controlled inputs re-renders the whole form on every keypress unless you work to prevent it.

Example

// Controlled: needed here, because the UI reacts to every keystroke.
<input value={query} onChange={e => setQuery(e.target.value)} />

// Uncontrolled + action: no state, no re-render per keystroke, works before hydration.
<form action={async (formData) => { await save(formData.get('email')); }}>
  <input name="email" defaultValue={user.email} />
  <button>Save</button>
</form>

Follow-ups

  • What causes the "changing an uncontrolled input to be controlled" warning? — Starting with value={undefined} and later supplying a value; use defaultValue, or initialise to an empty string.
  • How do you keep a big controlled form fast? — Isolate each field's state in the field component, or use an uncontrolled form library (React Hook Form) that subscribes rather than lifts.
  • Does React 19 reset the form after an action? — Yes, when a function is passed to action, React resets the uncontrolled form automatically after it completes.

Common wrong answer

"Always use controlled inputs — it's the React way." It is the React 16 way, it is the reason large forms feel sluggish, and it is at odds with React 19's own form APIs. Interviewers hear it as "learned React once and stopped".

midWhat are Actions in React 19?

Answer

An Action is an async function passed where React expects one — most visibly a <form action={fn}>, but also anything run inside startTransition. React tracks its lifecycle for you: it marks the transition pending while the function runs, keeps the UI responsive, applies optimistic updates and reverts them on failure, and surfaces errors to the nearest error boundary. The point is that the pending-state bookkeeping every team wrote by hand — isSubmitting, error, disabling the button, resetting the form — becomes framework behaviour. Actions are a client-side concept and work in a plain SPA; a Server Function ('use server') is an Action that happens to execute on the server, which is a separate idea people frequently merge.

Example

// No isSubmitting state, no try/finally, no manual reset.
<form action={async (formData) => {
  await updateName(formData.get('name'));
}}>
  <input name="name" defaultValue={name} />
  <SubmitButton />
</form>

Follow-ups

  • Do Actions require a framework? — No. Form actions and the hooks work in any React 19 app; only Server Functions need the RSC integration.
  • What happens to the form on success? — React resets uncontrolled fields after the action resolves; pass a controlled value if you need to keep the input.
  • How do errors surface? — A thrown error goes to the nearest error boundary; for user-facing validation you return an error value from useActionState instead of throwing.

Common wrong answer

"Actions are the React 19 name for Server Actions — they run on the server." Conflating the two is the most common React 19 error in interviews, and it makes the follow-up ("how would you use this in a static SPA?") unanswerable.

midWhat does useActionState give you, and how does it differ from useFormStatus?

Answer

useActionState(fn, initialState) wraps an action so that its return value becomes state: you get [state, formAction, isPending], where state is whatever the last invocation returned — perfect for validation errors or a result message — and formAction is what you pass to the form. It is the hook that lets you handle expected, user-facing failures without throwing. useFormStatus is different in kind: it is read from a component inside the form and reports the parent form's submission status, so a shared <SubmitButton> can disable itself without any prop drilling or context. One is about the action's result, the other about the enclosing form's pending state. Note the rename: this hook was useFormState in React 19 canaries and moved to react as useActionState for the stable release, so older tutorials are wrong.

Example

function SignupForm() {
  const [state, formAction, isPending] = useActionState(async (prev, formData) => {
    const email = formData.get('email');
    if (!email.includes('@')) return { error: 'Enter a valid email address' };
    await signup(email);
    return { ok: true };
  }, { });

  return (
    <form action={formAction}>
      <input name="email" aria-invalid={!!state.error} />
      {state.error && <p role="alert">{state.error}</p>}
      <SubmitButton />
    </form>
  );
}

function SubmitButton() {
  const { pending } = useFormStatus();          // reads the parent form
  return <button disabled={pending}>{pending ? 'Saving…' : 'Sign up'}</button>;
}

Follow-ups

  • Why must SubmitButton be a separate component? — useFormStatus reads the nearest form above it; called in the same component as the <form>, it returns no status.
  • Why does the action take prev as its first argument? — So you can accumulate state across submissions (retry counts, previously-entered values) rather than starting fresh each time.
  • Return an error or throw? — Return expected validation failures; throw for genuinely exceptional errors you want the error boundary to handle.

Common wrong answer

"They're two names for the same thing / you can use useFormStatus in the form component." The second half is a concrete, testable mistake: it silently returns pending: false forever, and the candidate has clearly not written the code.

midHow do you show a pending state and prevent double submits?

Answer

On the client, isPending from useActionState or useFormStatus disables the submit control and swaps the label, which handles the ordinary double-click. But a disabled button is a UX measure, not a correctness guarantee: the user can retry after a network timeout, a proxy can replay the request, and a fast double-tap on mobile can beat React's state update. Anything that mutates money or creates records needs server-side idempotency — a client-generated idempotency key sent with the request, which the server uses to return the original result instead of creating a second record. That distinction, UX versus correctness, is what the question is actually testing.

Example

function CheckoutForm({ cartId }) {
  const idempotencyKey = useRef(crypto.randomUUID()).current;   // one per attempt
  const [state, formAction, isPending] = useActionState(async (prev, formData) => {
    return placeOrder({ cartId, idempotencyKey, ...Object.fromEntries(formData) });
  }, {});
  return (
    <form action={formAction}>
      <button disabled={isPending}>{isPending ? 'Placing order…' : 'Place order'}</button>
    </form>
  );
}

Follow-ups

  • Where does the key come from? — Generated on the client per attempt and stored so a retry reuses it; a fresh key on retry defeats the mechanism.
  • How long must the server remember keys? — Long enough to cover retries and user impatience — typically 24 hours — with the original response stored, not just a "seen" flag.
  • What about optimistic UI here? — For a payment, no: never show success before the server confirms it.

Common wrong answer

"Disable the button while submitting — that prevents double submits." It prevents the double click. Duplicate orders in production come from retries, flaky networks and back-button resubmits, none of which a disabled button touches.

seniorWhat does progressive enhancement mean for React 19 forms, and do you care?

Answer

With an RSC framework, a form whose action is a Server Function works before any JavaScript has loaded: the browser posts the form natively, the server runs the action and responds, and once hydration completes React takes over the same form without a page reload. That is genuine progressive enhancement and it matters for the first moments of a slow load, for users on constrained networks, and for surfaces where a failed bundle should still let someone sign in or complete a purchase. Whether you care is a product decision: for a public checkout or a government service, absolutely; for an authenticated internal admin tool, it is usually not worth constraining your design for. What I would not accept is claiming it by accident — it only holds if the form is uncontrolled, the action is a Server Function, and the flow does not depend on client-only state.

Example

// Works with JS disabled or not yet loaded; upgrades silently after hydration.
<form action={subscribeAction}>
  <input name="email" type="email" required />
  <button>Subscribe</button>
</form>

// Not progressively enhanced: the handler needs JS, so nothing happens before hydration.
<form onSubmit={handleSubmit}>…</form>

Follow-ups

  • How do you test it? — Disable JavaScript in DevTools and submit; also throttle to Slow 3G and submit before hydration finishes, which is the realistic case.
  • What breaks progressive enhancement without you noticing? — Controlled inputs, onSubmit with preventDefault, client-only validation gates, and optimistic UI that assumes JS.
  • Does it help SEO? — Not directly; it helps resilience and time-to-usable, which are different (and more honest) arguments.

Common wrong answer

"Nobody disables JavaScript in 2026, so it doesn't matter." The real case is not disabled JS, it is JS that has not arrived yet or failed to load — which happens to a measurable share of sessions on mobile networks and is the reason the feature exists.

seniorWhere does form validation belong in a React 19 app?

Answer

In three places, deliberately. The browser handles the cheap, instant constraints (required, type="email", pattern, min) — free, accessible and available before hydration. The client re-validates with the same schema for good UX: inline errors, no round trip. The server validates the same schema again as the only enforcement that counts, because the client is attacker-controlled and, with Server Functions, the endpoint is public. The engineering move that makes this maintainable is one shared schema (Zod/Valibot/Standard Schema) imported by both sides, so the rules cannot drift; the action returns field-level errors through useActionState and the UI renders them with aria-describedby. Duplicated validation logic written twice in two styles is the failure mode I look for in review.

Example

// shared/schema.ts — one definition, both sides.
export const Signup = z.object({
  email: z.string().email('Enter a valid email'),
  age: z.coerce.number().int().min(18, 'You must be 18 or older'),
});

// action.ts
'use server';
export async function signup(prev, formData) {
  const parsed = Signup.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { errors: parsed.error.flatten().fieldErrors };
  await createAccount(parsed.data);
  return { ok: true };
}

Follow-ups

  • How do you surface errors accessibly? — aria-invalid on the field, the message linked with aria-describedby, and a summary with role="alert" that receives focus on submit failure.
  • What about async validation, like "is this username taken"? — Client check for UX, server check as the authority, and a uniqueness constraint in the database as the real guarantee against the race.
  • Does the browser's own validation get in the way? — It can: styling and messages are limited, so many teams use noValidate and re-implement. Know the trade-off rather than defaulting either way.

Common wrong answer

"Validate on the client for UX and let the API return 400s for the rest." It sounds layered but leaves the server rules undiscoverable and the two implementations free to drift — and with Server Functions the "API" is a public endpoint you wrote in the same file as your UI.

seniorA multi-step wizard with autosave, file uploads and a payment step. How do you structure the state and mutations?

Answer

I would separate the three kinds of state with different durability. Step navigation goes in the URL, so refresh, back and deep links work and support can ask "what URL are you on". Draft data goes to the server on a debounced autosave keyed by a draft id, with the local copy treated as a cache, not the source of truth — a wizard that loses data on refresh is the complaint that generates tickets. Uploads go directly to object storage with a pre-signed URL and the draft holds only the resulting keys, so a large file never travels through the action and a retry does not re-upload. The payment step is deliberately different: no optimism, an idempotency key generated at the start of the attempt, a server-authoritative result, and a completed state that is safe to land on twice. Each step's submit is its own action so failures are local, and the final submit re-validates the whole draft server-side, because steps were validated at different times.

Example

// URL owns the step; the server owns the draft; storage owns the files.
// /apply/step-2?draft=7f3c…
const [state, saveStep, isPending] = useActionState(saveDraftStep, { draftId });

useEffect(() => {
  const t = setTimeout(() => formRef.current.requestSubmit(), 1200);  // debounced autosave
  return () => clearTimeout(t);
}, [values]);

Follow-ups

  • What if the user opens two tabs? — Version the draft and reject stale writes with a conflict response; last-write-wins silently destroys work.
  • How do you handle a payment that succeeds but whose response is lost? — The idempotency key plus a status endpoint the client polls on reload; never re-charge to find out.
  • Where does validation live across steps? — Per-step schemas composed into a whole-application schema, re-validated at final submit.

Common wrong answer

"Keep the whole wizard in a client store and submit once at the end." It is the simplest to build and it loses everything on a refresh, times out on large uploads, and makes partial failure unrecoverable — the exact scenarios the interviewer will walk you through next.

09Composition and component APIs

The design-taste sub-area. Interviewers use it to see whether you can build components other people will use without asking you questions — which is most of a lead's actual job in a shared codebase. Mid-level is asked about children, render props and the legacy HOC pattern; senior about designing a component library API, controlled/uncontrolled duality and polymorphism; principal about governing a design system across teams.

Docs: react.dev — Passing Props to a Component

screenerWhat is children, and why is composition preferred over configuration?

Answer

children is just a prop that happens to be filled by what you nest inside a component's tags, so a component can accept arbitrary UI without knowing anything about it. Composition means letting the caller supply the content; configuration means adding props (showIcon, iconPosition, titleVariant) until the component encodes every caller's requirements. Composition wins because the prop surface stops growing, the component stays understandable, and the caller keeps control of their own markup. It also has a mechanical benefit: an element passed as children was created by the parent, so it does not re-render when the wrapper's state changes.

Example

// Configuration: nine props and counting, and the tenth caller needs a tenth.
<Card title="Orders" icon="box" iconColor="blue" action="View" onAction={fn} dense />

// Composition: no props to add, ever.
<Card>
  <Card.Header icon={<BoxIcon color="blue" />}>Orders</Card.Header>
  <Card.Body><OrderList /></Card.Body>
  <Card.Footer><Button onClick={fn}>View</Button></Card.Footer>
</Card>

Follow-ups

  • When is configuration the better choice? — When the variants are genuinely finite and you need to enforce consistency, e.g. a Button with three visual variants; unlimited composition inside a button is not a feature.
  • What is the downside of compound components? — Callers can assemble invalid combinations, and the implicit context between parts is harder to type and to discover.
  • How do you document a composition API? — With examples rather than prop tables; the API is the shape of the tree, not a list of props.

Common wrong answer

"children is a special React property that contains the nested elements." True and inert. The question is about API design; an answer that stops at the mechanism does not show you have ever maintained a component with thirty props.

midRender props, higher-order components, custom hooks — which and when?

Answer

Custom hooks are the default for sharing behaviour: no wrapper components, no prop collisions, no nesting, and full type inference. Render props are still the right tool when the shared thing must control what renders around the consumer's markup — virtualization, drag-and-drop surfaces, measurement wrappers — because a hook cannot inject elements into the tree. HOCs are the legacy option: they were how React 15/16 shared logic, they still appear in every mature codebase (connect, withRouter, withTranslation), and their costs are real — wrapper hell in the DevTools, invisible prop injection, and awkward typing. I would not write a new HOC, but I would expect to read plenty and to convert them incrementally rather than in one pass.

Example

// Hook: behaviour only.
const { x, y } = useMousePosition();

// Render prop: the shared code decides what wraps the consumer's UI.
<VirtualList items={rows} rowHeight={32}>
  {(row) => <OrderRow key={row.id} order={row} />}
</VirtualList>

// HOC: legacy, still ubiquitous.
export default withRouter(connect(mapState)(OrderPage));

Follow-ups

  • What is the performance concern with render props? — An inline arrow child is a new function each render; with the compiler this is usually moot, without it, it defeats memoization below.
  • How do you migrate a widely used HOC? — Publish a hook with the same semantics, make the HOC a thin wrapper over it, migrate call sites gradually, delete the HOC last.
  • Do hooks fully replace render props? — No — anything that must render around you, or that needs to control the boundary itself, still needs a component.

Common wrong answer

"HOCs and render props are obsolete — hooks replaced them." Half the sentence is right. A candidate who cannot name a case that still needs a component-shaped abstraction will reach for a hook when a hook cannot do the job.

midHow do you design a component that works both controlled and uncontrolled?

Answer

Mirror the DOM's own convention, because everyone already knows it: accept value + onChange for the controlled mode and defaultValue for the uncontrolled one, and decide which mode you are in by whether value is undefined. Internally you keep state either way and read from the prop when it is provided. Two rules make this survivable: the mode must not change during the component's lifetime (warn in development if it does — that is where React's own "changing an uncontrolled input to be controlled" warning comes from), and onChange must fire in both modes, so consumers can observe without taking control.

Example

function useControllable({ value, defaultValue, onChange }) {
  const isControlled = value !== undefined;
  const [internal, setInternal] = useState(defaultValue);
  const current = isControlled ? value : internal;
  const set = (next) => {
    if (!isControlled) setInternal(next);
    onChange?.(next);                      // fires in both modes
  };
  return [current, set];
}

Follow-ups

  • Why warn when the mode flips? — Because state silently jumps between two sources; the bug reports it produces ("the field cleared itself") are very hard to trace.
  • How do you type this in TypeScript? — A discriminated union of the two prop shapes so value without onChange is a type error.
  • Where does this pattern come from? — The DOM and React's own inputs; following it means consumers need no documentation.

Common wrong answer

"Take a controlled boolean prop." It makes the caller state something the component can already infer, and every caller will eventually pass an inconsistent combination — controlled true with no value, or a value with controlled false.

seniorYou are designing a shared component library for eight teams. What are your API rules?

Answer

Five rules I would write down on day one. Spread the rest of the props onto the underlying element and forward the ref, so consumers can do the 10% you did not anticipate without forking. Prefer composition slots over boolean props, and treat every new boolean as a design review. Make styling extensible in exactly one documented way — a token set plus className — rather than allowing arbitrary style overrides that turn your internals into public API. Version and deprecate like a public package: semver, codemods for breaking changes, and a deprecation window in the types. And ship accessibility inside the component so teams cannot get it wrong: focus management, roles, keyboard handling, tested. The hardest rule to hold is the last one on the list of things you say yes to: every escape hatch you add becomes a compatibility obligation.

Example

type ButtonProps = React.ComponentPropsWithoutRef<'button'> & {
  variant?: 'primary' | 'secondary' | 'ghost';
};

// ref is an ordinary prop in React 19 — no forwardRef needed.
export function Button({ variant = 'primary', className, ...rest }: ButtonProps) {
  return <button className={cx(styles[variant], className)} {...rest} />;
}

Follow-ups

  • How do you stop the library becoming a dumping ground? — An admission bar: used by three teams, or a design-system decision. One-team components live in that team's package.
  • How do you handle a team that needs a variant you rejected? — Give them the primitive to build it themselves; a component library that blocks work gets forked, and a fork is worse than a variant.
  • What does a breaking change cost? — Eight teams' calendars. Ship a codemod, or do not ship the change.

Common wrong answer

"Keep the API strict so teams can't misuse it — no className, no prop spreading." It sounds like good governance and it is how internal libraries get abandoned: the first unmet need becomes a wrapper, the second becomes a fork, and by the third nobody uses the library.

seniorWhat changed about refs and forwardRef in React 19, and what should a library do?

Answer

In React 19 function components receive ref as an ordinary prop, so forwardRef is no longer required for new code and is on a deprecation path — a codemod exists to remove it. Ref callbacks may now return a cleanup function, which runs on unmount instead of React calling the callback with null; that closes a long-standing hole where a callback ref had no clean teardown. For a library supporting React 18 and 19 the practical answer is to keep forwardRef until you drop 18, because the plain-prop form does not work on 18, and to document a single ref contract per component: what element you forward to, and whether you expose an imperative handle. I would also use useImperativeHandle sparingly — an imperative API is a second, undocumented interface that outlives the reason you added it.

Example

// React 19: ref is just a prop.
function Input({ ref, ...rest }) { return <input ref={ref} {...rest} />; }

// New in 19: ref callbacks can clean up after themselves.
<div ref={(node) => {
  const observer = new ResizeObserver(onResize);
  observer.observe(node);
  return () => observer.disconnect();     // runs on unmount
}} />

Follow-ups

  • What breaks if you return a value from a ref callback on React 18? — Nothing was expected there before, so returning a function in a codebase that runs on both versions can behave differently; guard by version or keep callbacks void.
  • When is useImperativeHandle right? — For genuinely imperative operations with no declarative equivalent: focus(), play(), scrollIntoView().
  • How do you type a forwarded ref now? — ref?: React.Ref<HTMLInputElement> in the props type; no generic wrapper needed.

Common wrong answer

"forwardRef is removed in React 19, so you must migrate." It is deprecated, not removed, and code using it still works — which matters because a library that drops it silently breaks every React 18 consumer.

seniorHow do you keep a component's props from growing into an unmaintainable surface?

Answer

I treat prop additions as API changes with a cost, and I look for three specific smells: boolean props that combine (isCompact + isInline + hasBorder = eight states, of which three are designed and five are accidents), props that only exist to be forwarded two levels down, and props whose value is a piece of UI. The fixes map directly: replace combining booleans with one variant union so the legal combinations are enumerable; replace pass-through props with composition; replace UI-shaped props with slots. When a component genuinely needs many independent options — a data table — the answer is usually a lower-level primitive plus a configured wrapper per use case, so the complexity lives in the wrappers rather than in a single component everyone is afraid to touch.

Example

// ❌ 2⁴ = 16 combinations, four of them designed.
<Alert isError isWarning isDismissible isInline />

// ✅ Enumerated variants, composition for the rest.
<Alert tone="error">
  <Alert.Title>Payment failed</Alert.Title>
  <Alert.Action><Button>Retry</Button></Alert.Action>
</Alert>

Follow-ups

  • How do you retire a prop that is in use? — Mark it deprecated in the types with a message, log in development, codemod the call sites, then remove in a major.
  • What is the "one more prop" review question? — "Which existing prop combination does this make illegal?" If nobody can answer, the state space is already out of control.
  • Does TypeScript help here? — Substantially: discriminated unions can make invalid combinations unrepresentable rather than merely discouraged.

Common wrong answer

"Accept a config object prop so the surface stays one prop wide." It renames the problem, defeats prop spreading and per-prop typing, and creates a new object identity on every render. Interviewers count it as avoiding the design question.

principalTwo teams have built competing design systems. You own the decision. What do you do?

Answer

First I would establish what problem the duplication is actually causing — inconsistent UX for users, doubled maintenance, or just aesthetic offence — because if the answer is the third, doing nothing is a legitimate option and saying so builds credibility. Assuming it is costing something real, I would not pick a winner on technical merit alone; I would pick on adoption, accessibility maturity and maintenance capacity, and I would put the losing team's people in ownership positions on the surviving system so the decision is not a defeat. Then a concrete convergence plan: freeze new components in the deprecated system, publish an adapter layer so migration is incremental, codemod what can be codemodded, and set a date after which the old package is unsupported rather than deleted. And I would write down the decision and its rationale, because the question "why did we pick that one" will be asked by people who were not in the room, repeatedly.

Example

CriterionWhy it decides
Adoption (surfaces, teams)Migration cost is roughly linear in what you have to move
Accessibility maturityHardest to retrofit; a system without it is a liability
Maintainer capacityA better library with no owner loses to a worse one with two

  • What if the better system has the smaller adoption? — Then the plan is longer and needs explicit investment; say the number out loud so the decision is made with the cost visible.
  • How do you handle the team that loses? — Ownership, not consolation. People defend what they own and abandon what was done to them.
  • When would you keep both? — Genuinely different domains (a marketing site and an internal tool) where the shared surface is small; forcing convergence there is cost with no user benefit.

Common wrong answer

"Evaluate both technically and standardise on the better one, with a deadline for migration." It is the answer that gets escalated back to you in three months: no ownership plan, no adapter, no incremental path, and one team told their work is being deleted.

10Testing React

Asked in almost every loop that has a code-review or take-home component, and it is a fast way to read seniority: what you choose to test says more than any framework opinion. Mid-level is expected to know Testing Library's philosophy and how to test async UI; senior to define a testing strategy with a sane pyramid, deal with flakiness, and test Server Components and Actions — which most teams have not solved well yet.

Docs: testing-library.com — React Testing Library

screenerWhat is React Testing Library's core philosophy, and what does it mean in practice?

Answer

"The more your tests resemble the way your software is used, the more confidence they give you." Concretely: query by what a user perceives — role, label, text — never by class names, test ids or component internals; assert on rendered output rather than on state; and interact through userEvent, which fires the full event sequence a real interaction produces rather than a single synthetic event. The practical payoff is that a refactor which changes internals but not behaviour does not break the suite, which is exactly what you want from a test. The practical cost is that queries force you to render accessible markup — which most teams discover is a feature, because a component you cannot query by role is usually a component a screen reader cannot use either.

Example

test('shows an error when the email is invalid', async () => {
  const user = userEvent.setup();
  render(<SignupForm />);
  await user.type(screen.getByLabelText(/email/i), 'not-an-email');
  await user.click(screen.getByRole('button', { name: /sign up/i }));
  expect(await screen.findByRole('alert')).toHaveTextContent(/valid email/i);
});

Follow-ups

  • getBy, queryBy or findBy? — getBy throws if absent, queryBy returns null (use it to assert absence), findBy returns a promise (use it for anything async).
  • When is a test id acceptable? — When there is genuinely no accessible handle — a chart canvas, a decorative container — and you note why.
  • Why userEvent over fireEvent? — A real click involves pointer, mouse and focus events; fireEvent dispatches one, so it passes tests that would fail in a browser.

Common wrong answer

"It tests components in isolation by mounting them shallowly." That is Enzyme's model, which React Testing Library exists to reject — and shallow rendering has no supported story in modern React at all.

midHow do you test asynchronous UI without flakiness?

Answer

Wait for the observable outcome, never for time. findBy* and waitFor poll until the assertion passes or the timeout expires, which adapts to a slow CI machine; an arbitrary setTimeout is a coin flip that gets slower every time someone raises it after a flake. Mock at the network boundary rather than mocking your own modules — MSW intercepts requests so the component under test uses its real data layer — because a mocked module tests your mock. And do not assert on loading states you did not deliberately design: asserting a spinner appears is a test of an implementation detail unless the spinner is part of the contract. Most React test flakiness I have debugged came from three sources: fake timers mixed with real promises, unmocked network, and missing await on a user event.

Example

const server = setupServer(
  http.get('/api/orders', () => HttpResponse.json([{ id: '1', total: 42 }])),
);
beforeAll(() => server.listen()); afterEach(() => server.resetHandlers()); afterAll(() => server.close());

test('renders orders', async () => {
  render(<Orders />);
  expect(await screen.findByText('$42.00')).toBeInTheDocument();   // no sleep, no act()
});

Follow-ups

  • When do you still need act()? — Rarely in RTL, which wraps interactions for you; an act warning usually means state updated after the test finished — an un-awaited promise or a missing cleanup.
  • How do you test a debounced input? — Fake timers advanced explicitly, with userEvent.setup({ advanceTimers }) so the two clocks agree.
  • How do you keep StrictMode from doubling side effects in tests? — Don't fight it: render in StrictMode so the tests catch the same non-idempotent effects your users would.

Common wrong answer

"Add a waitFor with a longer timeout, or a small sleep before asserting." It converts a flaky test into a slow flaky test, and it is the single most common cause of ten-minute CI suites that still fail once a week.

midWhat is your testing pyramid for a React app, and what do you deliberately not test?

Answer

Heavy on component-level integration tests — a feature rendered with its real children and a mocked network — because that is the level where React bugs actually live and where tests survive refactors. A thin layer of pure unit tests for logic worth isolating: reducers, formatters, schema validation, hooks with non-trivial rules. A small number of end-to-end tests for the flows that must never break: login, checkout, the primary create path. Deliberately not tested: implementation details (state variable names, render counts, whether a memo hit), third-party libraries, and pixel-level appearance in unit tests — visual regression belongs in a snapshot-image tool, not in an assertion. I would also say out loud that coverage percentage is a diagnostic, not a target; teams that chase it write tests for getters.

Example

LayerShareWhat it catches
Unit (reducers, schemas, hooks)~20%Logic errors, edge cases, fast feedback
Component integration (RTL + MSW)~70%Wiring, states, accessibility, real regressions
End-to-end (Playwright)~10%Routing, auth, deploy config, cross-service breakage

Follow-ups

  • Are snapshot tests useful? — Small, targeted ones, yes; a 400-line component snapshot is a change detector that everybody approves without reading.
  • How do you test accessibility? — jest-axe in component tests for the mechanical rules, plus real keyboard-navigation assertions for the parts axe cannot see.
  • Where do visual regressions belong? — A dedicated tool on a small set of representative screens; in-test image comparison is flaky across environments.

Common wrong answer

"Aim for 80% coverage with unit tests on every component." Coverage as a target produces tests that assert a component renders without crashing, which catches nothing and must be maintained forever. Interviewers want to hear what you choose not to test.

seniorHow do you test Server Components and Server Functions?

Answer

Split them, because they are different beasts. A Server Function is a plain async function with a directive: test it directly like any server-side unit — call it with the arguments an attacker could send, assert that it rejects an unauthenticated session, rejects invalid input and enforces row-level authorisation. Those are the three tests that matter, and they are the ones most teams do not write. A Server Component is an async function returning JSX; the ecosystem's support for rendering it in a unit test is still uneven in 2026, so the pragmatic strategy is to keep them thin — data in, markup out — unit-test the data functions beneath them, and cover the rendered result with an end-to-end test against a running server. I would say that limitation plainly in an interview rather than pretending there is a mature story; it is a real gap and knowing it is the senior signal.

Example

test('addNote rejects an unauthenticated caller', async () => {
  mockSession(null);
  await expect(addNote({ orderId: validId, note: 'x' })).rejects.toThrow(/unauthenticated/i);
});

test('addNote rejects an order the user does not own', async () => {
  mockSession({ user: { id: 'u1' } });
  await expect(addNote({ orderId: otherUsersOrder, note: 'x' })).rejects.toThrow(/forbidden/i);
});

Follow-ups

  • Why test authorisation at the function level rather than through the UI? — Because the function is a public HTTP endpoint; the UI is not the only caller, and after CVE-2025-55182 nobody should assume otherwise.
  • How do you keep Server Components thin enough to skip unit tests? — Push logic into plain async functions; the component becomes composition, which end-to-end covers adequately.
  • What does end-to-end give you here that nothing else does? — The real bundler boundary: serialisation failures and accidental client-bundle inclusion only appear in a real build.

Common wrong answer

"Mock the server parts and test the components normally." It skips exactly the code that carries the security risk, and the mock inevitably diverges from the real function's contract. The interviewer is checking whether you know where the untested surface is.

seniorYour CI suite takes 25 minutes and fails randomly twice a week. What do you do?

Answer

Treat flakiness as a priority-one defect, not a nuisance, because a suite people do not trust is a suite people re-run until it passes — at which point it protects nothing. I would instrument first: record every failure with its test name and build a leaderboard, because flakes are almost always concentrated in a handful of tests. Then quarantine the top offenders out of the blocking path with a deadline and an owner, so the signal is restored immediately while the fixes happen. The usual causes in React suites are timing (sleeps, fake-timer mixing), shared state between tests (a module-level cache, an unreset store, a leaked MSW handler), and real race conditions in the app that the test surfaces intermittently — that last category is the valuable one and must not be quarantined away. For the 25 minutes: parallelise by shard, cut the end-to-end suite to the flows that justify their cost, and only then look at the framework.

Example

// Common culprit: state that outlives a test.
afterEach(() => {
  queryClient.clear();
  server.resetHandlers();
  cleanup();
  vi.useRealTimers();
});

Follow-ups

  • Is retrying failed tests acceptable? — As a temporary bandage with the retries reported and tracked; as a permanent setting it hides real races and rots the suite.
  • How do you decide what to delete? — Tests that have never failed for a real reason and are expensive; a test's value is the bugs it has caught.
  • Who owns the suite? — A named team with time allocated. Unowned CI degrades monotonically.

Common wrong answer

"Enable automatic retries and increase the timeouts." It makes the dashboard green while the underlying races stay in the product, and the first customer-facing incident will be the one the flaky test was warning about.

principalHow do you raise testing quality across an organisation that has 30% coverage and no appetite for it?

Answer

I would not start with a coverage mandate, because "no appetite" usually means previous attempts produced tests that were expensive and caught nothing. I would start by connecting tests to pain the team already feels: take the last ten incidents, ask which would have been caught by a test at which level, and use that to define what is worth testing here — usually three or four flows, not everything. Then I would remove friction: fast local runs, a working test template, MSW handlers generated from the API schema, and a pairing session per team rather than a document. Ratchet rather than mandate: coverage may not decrease on changed files, which is enforceable per PR and never blocks unrelated work. And I would make one visible win — a bug caught before release, announced — because the culture changes when tests are seen to have saved someone, not when a policy says they must exist.

Example

# Ratchet, not a target: only the diff has to be covered.
- name: Coverage on changed files
  run: npx jest --changedSince=origin/main --coverage --coverageThreshold '{"global":{"lines":70}}'

Follow-ups

  • What if leadership wants a coverage number? — Give them incident-escape rate and change-failure rate instead; coverage is an input metric and gaming it is trivial.
  • How long before it shows? — Two to three quarters for culture; the friction removal shows within weeks and is what buys you the patience.
  • What do you do about the untested legacy core? — Characterisation tests only where you are about to change it; a retroactive testing project for stable code is rarely worth it.

Common wrong answer

"Set a coverage gate at 80% and enforce it in CI." It produces assertion-free tests within a sprint, blocks unrelated PRs, and confirms every sceptic's belief that testing is bureaucracy. Interviewers at this level have watched it happen.

11TypeScript with React

Nearly universal in job specs, rarely the centre of the interview — but a bad answer here is disproportionately costly because it shows up in every code sample you write. Expect prop typing, generics in components, and event/ref types. At senior level the interesting questions are about typing an API so misuse is impossible, and about how much type complexity a shared codebase can carry before it stops being an asset.

Docs: react.dev — Using TypeScript

screenerHow do you type a component's props, and why not React.FC?

Answer

Type the props parameter directly with an interface or type alias and let TypeScript infer the return; that is the idiom in modern React codebases and in React's own docs. React.FC fell out of favour because it used to imply an implicit children prop (removed in the React 18 types, which was itself a breaking change teams had to absorb), it complicates generic components, and it adds nothing you need. For props that wrap a DOM element, extend the element's own props with ComponentPropsWithoutRef<'button'> so consumers get every native attribute and correct event types for free — hand-listing onClick and disabled is how components end up missing aria-* and type.

Example

type CardProps = {
  title: string;
  children: React.ReactNode;
  onDismiss?: () => void;
};

export function Card({ title, children, onDismiss }: CardProps) { /* ... */ }

// Wrapping a DOM element: inherit everything.
type IconButtonProps = React.ComponentPropsWithoutRef<'button'> & { icon: React.ReactNode };

Follow-ups

  • ReactNode, ReactElement or JSX.Element? — ReactNode for anything renderable (the right type for children); ReactElement when you specifically need a single element you may clone.
  • Interface or type alias? — Either; interfaces merge declarations (useful for library augmentation), type aliases handle unions and mapped types. Pick one convention per codebase.
  • How do you type children as exactly one element? — children: React.ReactElement, and accept that TypeScript cannot enforce "exactly one of a specific component".

Common wrong answer

"Use React.FC — it's the standard way to type a component." It was, in 2019. It signals the candidate learned the types from an old tutorial, and the follow-up about generic components usually confirms it.

midHow do you type a generic component, like a <Select<T>>?

Answer

Write the component as a generic function and let inference flow from the props: function Select<T>(props: SelectProps<T>). The payoff is that options, value and onChange agree by construction, so passing a handler for the wrong element type is a compile error rather than a runtime surprise. Two practical notes: this is the concrete reason React.FC gets in the way, since it is not generic; and in a .tsx file a bare <T> is parsed as JSX, so you write <T,> for an inline generic arrow function. For a keyed accessor, a keyof T parameter keeps the "which field is the label" prop honest.

Example

type SelectProps<T> = {
  options: readonly T[];
  value: T | null;
  onChange: (value: T) => void;
  getLabel: (option: T) => string;
};

export function Select<T>({ options, value, onChange, getLabel }: SelectProps<T>) {
  return (
    <ul role="listbox">
      {options.map((o, i) => (
        <li key={i} role="option" aria-selected={o === value} onClick={() => onChange(o)}>
          {getLabel(o)}
        </li>
      ))}
    </ul>
  );
}

Follow-ups

  • How do you constrain T to have an id? — <T extends { id: string }>, which also lets you use o.id as the key instead of the index.
  • Why readonly T[]? — It accepts as const arrays and documents that the component will not mutate the input.
  • What breaks generic inference in practice? — Wrapping in memo or forwardRef, which historically erased the generic; casting the wrapped component back is the usual workaround.

Common wrong answer

"Type the options as any[] and cast in the handler." It compiles, it removes every guarantee the component could have offered, and in review it is the clearest possible signal that the candidate treats TypeScript as a syntax tax rather than a design tool.

midHow do you type events, refs and hook returns correctly?

Answer

Prefer inference: an inline handler on a JSX element already knows its event type, so annotating it is usually noise. When you must name the type — a handler defined outside JSX — use the React synthetic types (React.ChangeEvent<HTMLInputElement>, React.MouseEvent<HTMLButtonElement>) and not the DOM ones, because React's events are synthetic. Refs to DOM nodes are useRef<HTMLInputElement>(null), which types current as nullable and forces the null check you would otherwise forget; a mutable instance ref is useRef<T | null>(null). For custom hooks returning a tuple, add as const or an explicit return type, otherwise TypeScript widens it to an array union and destructuring loses the types.

Example

const inputRef = useRef<HTMLInputElement>(null);
inputRef.current?.focus();

function handleChange(e: React.ChangeEvent<HTMLInputElement>) { setValue(e.target.value); }

function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  return [on, () => setOn(v => !v)] as const;   // [boolean, () => void]
}

Follow-ups

  • Why is current nullable? — Because the ref is null before the first commit and after unmount; the nullability is the type system telling the truth.
  • How do you type a component that forwards a ref in React 19? — ref?: React.Ref<HTMLInputElement> as an ordinary prop; no forwardRef generics needed.
  • What is the trap with useState and null? — useState(null) infers null; write useState<User | null>(null).

Common wrong answer

"Type events as any to avoid the noise, or use the DOM's Event." The DOM types are subtly wrong for React's synthetic events (currentTarget in particular), and any removes the one place where the types genuinely prevent bugs.

seniorHow do you use types to make a component API impossible to misuse?

Answer

Model the legal states as a discriminated union rather than a bag of optional props, so the compiler rejects the combinations your documentation would otherwise have to warn about. A button that is either a link or a button, a modal that either has a title or is labelled by an element, a controlled-or-uncontrolled input — all of these are unions, not optional fields. The judgment part is knowing when to stop: type-level cleverness has a real cost in error messages and in the next engineer's comprehension, and a union of four variants with readable names beats a conditional mapped type that no one can debug. My rule is that a type may be complex if the failure it prevents is expensive and the error message it produces is comprehensible.

Example

type ButtonProps =
  | ({ href: string; onClick?: never } & React.ComponentPropsWithoutRef<'a'>)
  | ({ href?: never; onClick: () => void } & React.ComponentPropsWithoutRef<'button'>);

// <Button href="/x" onClick={fn} />  → compile error: a link is not a button.

Follow-ups

  • When does this go too far? — When an error message spans forty lines, or when the type must be updated for every new variant; then a runtime invariant with a clear message is kinder.
  • How do you enforce "one of these two props is required"? — A union with never on the excluded member, as above; it is the standard trick and it reads acceptably.
  • Do types replace runtime validation? — Never at a trust boundary: props from your own code, yes; data from the network or a Server Function argument, no.

Common wrong answer

"Make both props optional and throw at runtime if the combination is wrong." It moves a compile-time guarantee to a runtime crash the user experiences, which is strictly worse when the type system could have caught it in the editor.

principalThe codebase has 900 anys and strict: false. What is your plan?

Answer

Incremental and per-file, because a global strict: true flip produces thousands of errors, blocks everyone, and gets reverted. The mechanism I would use is a baseline: turn strict on, generate a file of currently-failing files, and fail CI only on new violations, so the debt is frozen while feature work continues. Then burn it down where it is worth it — the modules that carry money, permissions or data transformation get typed first, because that is where a type error is a bug and not a formality. I would also separate the two problems: strictNullChecks catches real crashes and is worth the effort, while noImplicitAny is mostly annotation work; enabling them on different timelines makes the project tractable. And I would set the expectation that some files stay untyped forever, because a dead admin page is not worth anyone's afternoon.

Example

{
  "compilerOptions": {
    "strict": true,
    "noImplicitAny": false,        // stage 2; strictNullChecks first
    "noUncheckedIndexedAccess": true
  },
  "exclude": ["src/legacy/**"]      // explicit, reviewed, with an owner
}

Follow-ups

  • How do you stop new anys? — A lint rule on changed files, plus a review convention that an any needs a comment explaining what it is hiding.
  • What about @ts-expect-error versus @ts-ignore? — Always expect-error: it fails when the error goes away, so the suppression cleans itself up.
  • How do you show progress? — Count errors under strict mode weekly; a downward line is the only argument that survives a re-prioritisation meeting.

Common wrong answer

"Turn on strict mode and fix everything in a dedicated sprint." Three thousand errors, a branch that cannot be rebased, and a merge conflict with every feature in flight. The principal-level answer is a ratchet, not a sprint.

12Routing and app architecture

React has no router, so this sub-area is really about the ecosystem choice and its consequences. Interviewers ask because routing is where data loading, code splitting, auth and URL state all meet — and because a candidate's routing answer reveals whether they think in pages or in components. Mid-level: nested routes, params, guards. Senior: loaders versus component-level fetching, and how the router shapes the loading strategy.

Docs: reactrouter.com

screenerWhy does React not ship a router, and what are the real options?

Answer

React is a rendering library; routing is an application concern that differs wildly between an SPA, an SSR app and a native app, so it lives in userland. In practice there are three serious families in 2026: React Router (v7 merged the Remix work back in, so it spans a plain SPA, SSR and framework mode with loaders and actions), Next.js's App Router (file-system routing built around Server Components), and TanStack Router (type-safe routes and search params, client-first). The choice is mostly a data-loading choice: a router with loaders lets you fetch per route before rendering, which removes a whole class of waterfalls that component-level fetching creates. I would also note that "no router in core" is why RSC needs a framework — the routing layer is what drives the server render.

Example

// Route-level data: the request starts before the component renders.
const router = createBrowserRouter([{
  path: '/orders/:id',
  loader: ({ params, request }) => getOrder(params.id, { signal: request.signal }),
  element: <OrderPage />,
  errorElement: <OrderError />,
}]);

Follow-ups

  • What does file-system routing buy and cost? — Convention over configuration and automatic code splitting; the cost is that the route tree is implicit and refactors mean moving files.
  • Where does type safety matter most? — Params and search params; a typo in params.orderid is a runtime undefined in most routers.
  • How do you handle auth? — In the loader or middleware, not in a component effect — an effect-based guard renders the protected page first and redirects afterwards.

Common wrong answer

"React Router is the standard, so use that." Not a wrong tool, but a non-answer: it skips the data-loading model, which is the part of the decision that actually shapes the app.

midHow do you protect routes, and where does the check belong?

Answer

As early as possible in the request path, and always on the server as the enforcement point. In a framework app that means middleware or the route loader, so an unauthenticated user is redirected before any protected data is fetched or rendered. A client-side guard component is a UX affordance, not security: it prevents a flash of protected UI, and that is all it does — the data endpoints must reject the request independently. The mistake I watch for in review is authorisation implemented only in the router, so an API call from a different screen, or a Server Function invoked directly, bypasses it entirely. Roles belong in the session, the check belongs next to the data, and the router just makes the experience coherent.

Example

// Loader: no protected render, no flash, no wasted fetch.
async function loader({ request }) {
  const session = await getSession(request);
  if (!session) throw redirect(`/login?next=${encodeURIComponent(new URL(request.url).pathname)}`);
  return getDashboard(session.userId);
}

// ❌ Effect-based guard: renders the protected page, then navigates away.
useEffect(() => { if (!user) navigate('/login'); }, [user]);

Follow-ups

  • How do you handle role-based visibility in the UI? — Send the permissions with the session and render accordingly, while the server re-checks every mutation.
  • What about deep links to a protected route? — Preserve the intended URL through login and redirect back; losing it is a small thing users complain about constantly.
  • Where do feature flags fit? — Same place as auth: evaluated server-side for anything that must not be discoverable in the client bundle.

Common wrong answer

"Wrap the routes in a <RequireAuth> component that redirects if there is no user." Fine as UX, presented as security it is a finding in any audit: the protected data has already been requested, and the bundle still contains the page.

midWhat state belongs in the URL, and how do you manage it?

Answer

Anything a user would reasonably expect to share, bookmark or reach with the back button: the current entity, the tab, filters, sort, pagination, and the open state of a full-screen modal. Putting it there gives you deep links, correct back/forward behaviour, server-renderable pages and free crash recovery, none of which you get from component state. The management questions are serialisation (keep it short and human-readable; avoid dumping JSON into a query param), validation (parse it defensively with a schema, because users edit URLs and old links outlive your code), and history semantics — a filter change should usually replace rather than push, or the back button becomes a keystroke-by-keystroke undo of the search box.

Example

const [params, setParams] = useSearchParams();
const status = Status.catch('all').parse(params.get('status'));   // schema-validated

function setStatus(next) {
  const p = new URLSearchParams(params);
  next === 'all' ? p.delete('status') : p.set('status', next);
  setParams(p, { replace: true });        // filters replace; navigation pushes
}

Follow-ups

  • What should not go in the URL? — Anything sensitive (URLs land in logs, referrers and analytics), and anything large enough to hit URL length limits.
  • How do you keep the URL from becoming an unversioned API? — Treat unknown or invalid params as defaults rather than errors, so old links keep working.
  • Push or replace? — Push for navigations the user thinks of as steps; replace for continuous adjustments.

Common wrong answer

"Keep filters in a store and sync them to the URL with an effect." Two sources of truth and a sync loop; the classic symptom is that the back button changes the URL but not the UI, or vice versa. The URL should be the state, read directly.

seniorRoute loaders versus fetching inside components — what is the real trade-off?

Answer

Loaders hoist data requirements to the route, so every request for a screen starts in parallel as soon as navigation begins, before any component renders — that is what removes waterfalls and lets the router show the old screen until the new one is ready. The cost is coupling: the route must know what its subtree needs, so a deeply nested component's new data requirement becomes a change to the route definition, and reusable components can no longer be self-sufficient. Component-level fetching with a query cache inverts the trade: components are self-contained and composable, but you get sequential requests unless you prefetch deliberately. In practice I use loaders for the primary data of the screen and a cache for secondary, lazily-needed data — and I would name Relay as the framework that solved this properly with fragments, since colocated declarations plus a hoisted query is the ideal both approaches approximate.

Example

// Loader: parallel and early.
loader: ({ params }) => Promise.all([getOrder(params.id), getCustomer(params.id)])

// Component-level: composable, but the second request waits for the first render.
function Order() {
  const { data: order } = useQuery({ queryKey: ['order', id], queryFn: getOrder });
  return <Customer id={order?.customerId} />;   // fetches only after order resolves
}

Follow-ups

  • How do you prefetch with component-level fetching? — On intent: hover, focus, or viewport entry triggers queryClient.prefetchQuery so the click is instant.
  • How do RSC change this? — The server component tree is the loader; the same waterfall risk exists if you await serially instead of starting promises in parallel.
  • What about revalidation after a mutation? — Loaders revalidate on navigation and after actions; caches invalidate by key. Mixing both without a rule is how stale screens appear.

Common wrong answer

"Loaders are better because they avoid waterfalls, so always use them." It ignores the coupling cost and the reusability problem, and it does not survive the follow-up about a shared widget used on nine routes.

principalHow do you structure a React codebase that eight teams work in?

Answer

By feature, with enforced boundaries — not by technical layer. A components/, hooks/, utils/ split scales badly because every feature touches every folder and nothing has an owner. I would give each feature a directory with its own components, data access and tests, a public entry point that defines what other features may import, and a lint rule (or an Nx/Turborepo project boundary) that makes cross-feature deep imports a build error rather than a review comment. Shared code lives in explicit packages with owners: the design system, the data-access layer, the auth client. CODEOWNERS follows the same shape so review routing is automatic. The rule I would state in the interview is that the structure exists to make ownership legible; if you cannot tell from the path who owns a file, the structure has failed regardless of how tidy it looks.

Example

src/
  features/
    checkout/        # owned by payments; imports only from its own dir + packages/*
      index.ts       # the public API: everything else is private
      components/ data/ tests/
    orders/
  packages/
    design-system/ data-client/ auth/
# eslint: no import from '../orders/components/...' — only from 'features/orders'

Follow-ups

  • Monorepo or polyrepo? — Monorepo for shared UI and lockstep releases; polyrepo when teams genuinely release independently and can tolerate version skew. The deciding factor is release cadence, not tooling taste.
  • What about a shared "utils" folder? — It becomes the junk drawer. Either it is a real package with an owner and tests, or it should not exist.
  • How do you migrate an existing layer-based codebase? — Move one feature at a time, add the boundary rule in warn mode first, and stop when the remaining shared code is genuinely shared.

Common wrong answer

"Atomic design: atoms, molecules, organisms, templates, pages." It is a vocabulary for a design system, not an ownership model for an application, and in a multi-team codebase it produces endless arguments about whether something is a molecule while nobody can tell who owns it.

13Accessibility

Asked less often than it should be, but increasingly a filter at senior level — partly because of legal exposure (the European Accessibility Act's obligations took effect in June 2025) and partly because it is a reliable proxy for craft. You are unlikely to get four accessibility questions; you are quite likely to get one, and a vague answer stands out. Know the semantics-first argument, focus management, and how to test.

Docs: react.dev — DOM components and ARIA

screenerWhat does React give you for accessibility, and what does it not?

Answer

Very little, deliberately: React renders the DOM you describe, so accessibility is almost entirely your markup. What it does provide is useId for stable ids that match between server and client (essential for aria-describedby and label associations), full support for aria-* and role attributes as ordinary props, and the caveat that JSX uses htmlFor and className but keeps aria-* and data-* hyphenated. What it does not give you is focus management across route changes, announcements for dynamic content, or any protection against the classic React failure mode — a <div onClick> that looks like a button and is invisible to keyboard and screen-reader users. Component libraries (Radix, React Aria) exist precisely because getting a listbox or a dialog right is genuinely hard.

Example

const id = useId();
<label htmlFor={`${id}-email`}>Email</label>
<input id={`${id}-email`} aria-describedby={`${id}-hint`} aria-invalid={!!error} />
<p id={`${id}-hint`}>We only use this for receipts.</p>

Follow-ups

  • Why useId rather than a counter? — It is stable across server and client renders; a module counter produces hydration mismatches. React 19.2 changed the prefix to _r_ so the ids work as CSS selectors.
  • Why not just add role="button" to the div? — Then you also owe keyboard handling, focus, and disabled semantics. Use a <button>.
  • Where does React actively help? — Nowhere automatic; treat every accessible behaviour as something you implemented and tested.

Common wrong answer

"React handles accessibility for you as long as you use semantic components." There is nothing automatic. This answer usually precedes a portfolio full of clickable divs.

midHow do you handle focus in a single-page app?

Answer

Client-side navigation does not move focus or announce anything, so a screen-reader user gets no signal that the page changed and a keyboard user is left at the bottom of the old page. The fix is explicit: on route change, move focus to the new page's heading or main landmark (with tabIndex={-1} so it is programmatically focusable), and announce the new title in a live region. Within a page, a dialog must trap focus while open, return it to the trigger on close, and be dismissible with Escape. Deleting the focused element — removing a row — needs a deliberate destination, otherwise focus falls to body and the user is teleported to the top. These behaviours are the reason most teams use a headless library for overlays rather than writing them again.

Example

function usePageFocus(routeKey, title) {
  const ref = useRef(null);
  useEffect(() => {
    ref.current?.focus();
    document.title = title;
    announce(title);              // aria-live="polite" region
  }, [routeKey, title]);
  return ref;
}

<h1 ref={usePageFocus(key, title)} tabIndex={-1}>{title}</h1>

Follow-ups

  • Heading or the main landmark? — Either works; be consistent, and make sure the target is not visually distracting when it receives a focus ring.
  • How do you test focus behaviour? — Keyboard-only assertions in Testing Library (expect(document.activeElement)), plus a manual pass with a screen reader for anything novel.
  • What about <Activity> hidden trees? — Hidden content must not be focusable; verify that the implementation removes it from the tab order rather than merely hiding it visually.

Common wrong answer

"Scroll to the top on navigation." That is the visual half of the problem and none of the assistive half; keyboard focus stays where it was and nothing is announced.

seniorHow do you make a custom component (a combobox, say) accessible?

Answer

My first answer is that I would not write one: a combobox is one of the hardest patterns in the ARIA Authoring Practices, with a keyboard model most people get wrong, and Radix or React Aria have solved it including the browser and screen-reader quirks. If it must be bespoke, the work is: correct roles and relationships (role="combobox", aria-expanded, aria-controls, aria-activedescendant pointing at the option), the full keyboard model (arrows, Home/End, Escape, Enter, type-ahead), focus that stays in the input while selection moves virtually, and announcements when the result count changes. Then testing across at least NVDA/Chrome and VoiceOver/Safari, because they disagree. The senior signal here is knowing the cost before starting, not reciting attributes.

Example

<input role="combobox" aria-expanded={open} aria-controls={listId}
       aria-activedescendant={active ? `${listId}-${active}` : undefined} />
<ul id={listId} role="listbox">
  {options.map(o => (
    <li id={`${listId}-${o.id}`} role="option" aria-selected={o.id === active} key={o.id}>
      {o.label}
    </li>
  ))}
</ul>
<p aria-live="polite" className="sr-only">{options.length} results available</p>

Follow-ups

  • Why aria-activedescendant instead of moving focus? — The typed text must keep receiving keystrokes; focus stays in the input while the "virtual" focus moves through options.
  • What do automated tools miss? — Nearly all of the keyboard model and every announcement; axe checks static attributes, not interaction.
  • How do you budget for this? — Treat a bespoke widget as a multi-week item including testing, and use that number to justify the library.

Common wrong answer

"Add role and aria-label attributes and it's accessible." ARIA without the matching keyboard behaviour makes things worse — a control that announces itself as a combobox but does not respond to arrow keys is more confusing than an unlabelled input.

principalHow do you make accessibility a property of the system rather than a periodic audit?

Answer

By moving it left into the places where it cannot be skipped. First, the design system: if every button, dialog, menu and form control in the shared library is accessible and tested, most product code inherits it without a single decision. Second, automation in CI — eslint-plugin-jsx-a11y for the static mistakes, axe in component tests for the rendered ones — knowing it catches perhaps a third of real issues, which is a third nobody has to argue about. Third, the parts automation cannot see: a keyboard-only pass in the definition of done for new interactive surfaces, and periodic testing with actual assistive technology and, ideally, actual users. Fourth, the organisational lever: a named accountable owner and a compliance driver — the European Accessibility Act's requirements applied from June 2025, which for most companies converts this from ethics to obligation and unlocks the budget. Audits then verify a system that works instead of generating a backlog nobody funds.

Example

// The cheap third, automated on every PR.
import { axe } from 'jest-axe';
test('dialog has no obvious a11y violations', async () => {
  const { container } = render(<ConfirmDialog open />);
  expect(await axe(container)).toHaveNoViolations();
});

Follow-ups

  • What do you do with a 400-item audit report? — Triage by user impact and frequency, fix the design-system causes first (one fix, many instances), and publish the burn-down.
  • How do you handle a team that says it slows them down? — Show that the library already does it; the cost is only high when everyone re-implements overlays.
  • What metric would you report? — Percentage of interactive surfaces built from the accessible library, plus keyboard-pass completion — not the axe violation count, which is easy to game.

Common wrong answer

"Run an annual audit and fix what it finds." It produces a large backlog against a codebase that keeps generating new violations faster than they are fixed, and it puts accessibility permanently in the "later" column.

14Security

Asked more often since December 2025, when CVE-2025-55182 gave every React shop an incident to remember. Even outside RSC, interviewers use security questions to check whether you understand what React protects you from (very little, by design) and where the framework's escape hatches are. Expect XSS, the RSC boundary, dependency risk, and secrets handling; at principal level, how you run patching as a process.

Docs: react.dev — dangerouslySetInnerHTML

screenerDoes React protect you from XSS?

Answer

Partly, and only in one direction: text interpolated into JSX is escaped, so {userInput} cannot inject markup. Everything else is on you. dangerouslySetInnerHTML bypasses it entirely and is the number one React XSS vector. A URL in href or src is not sanitised, so javascript: URLs from user data execute on click. Injecting user input into a <script>, a style attribute, or an SVG can execute too. And on the server, embedding unescaped state in the HTML — the classic window.__STATE__ = ${JSON.stringify(state)} — is an injection point because </script> inside the data closes the tag. The one-line summary I would give: React escapes text nodes, not decisions.

Example

<p>{userInput}</p>                                    {/* safe: escaped */}
<div dangerouslySetInnerHTML={{ __html: userInput }} /> {/* XSS unless sanitised */}
<a href={userProvidedUrl}>Link</a>                     {/* javascript: executes */}

// Sanitise if you must render HTML, and validate the scheme for URLs.
const clean = DOMPurify.sanitize(userInput);
const safeHref = /^https?:\/\//i.test(url) ? url : '#';

Follow-ups

  • Where would you sanitise, client or server? — Server, on write, and again on render if the storage is shared; client-only sanitisation is bypassable by anything that is not your UI.
  • What does a CSP add? — Defence in depth: a strict script-src with nonces turns many XSS bugs into blocked requests. React 19's script and style hoisting supports nonces.
  • How do you find these in a codebase? — Grep for dangerouslySetInnerHTML and require a review comment on each; there are usually fewer than twenty and most are unnecessary.

Common wrong answer

"Yes, React escapes everything, so XSS isn't a React concern." It is the belief that keeps dangerouslySetInnerHTML in code review unchallenged. The word "dangerously" is in the API name precisely because the framework's authors expected this answer.

midWhere do secrets leak in a React app?

Answer

Four places, in descending order of frequency. Environment variables with a public prefix (NEXT_PUBLIC_, VITE_) are inlined into the bundle at build time — anything there is public, and teams put API keys in them constantly. Props passed from a Server Component to a Client Component are serialised into the RSC payload and visible in the browser, so passing a whole user or config object leaks whatever else it contains. Server-side code accidentally imported into a client module pulls its constants with it — the reason server-only as an import guard exists. And error messages or stack traces returned to the client can carry connection strings and internal hostnames. The habit that prevents most of it is mapping to explicit DTOs at every boundary rather than passing whatever object you have.

Example

// Poisons the build if this module is ever imported from client code.
import 'server-only';

export const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);   // never prefixed public

Follow-ups

  • How do you detect a leak after the fact? — Scan built bundles for secret patterns in CI, and rotate anything that ever shipped — a secret in a deployed bundle is compromised permanently.
  • Is obfuscating the key enough? — No. Anything the browser can use, the user can extract; the fix is a server-side proxy that holds the key.
  • What about source maps? — Public source maps expose your source; either keep them private or accept that the code is readable.

Common wrong answer

"Keep secrets in .env and they stay on the server." The file is not the boundary — the prefix and the import graph are. This is the most common real-world React secret leak, and it is usually discovered by a third party.

seniorWalk me through the December 2025 React Server Components vulnerabilities and what you would have done.

Answer

On 3 December 2025 the React team disclosed CVE-2025-55182, CVSS 10.0: a flaw in how the RSC runtime decodes payloads posted to Server Function endpoints allowed unauthenticated remote code execution, and — the part that made it an emergency — applications were vulnerable even if they defined no Server Functions themselves, because the endpoint exists in the runtime. It affected react-server-dom-webpack, -parcel and -turbopack at 19.0, 19.1.0, 19.1.1 and 19.2.0, with fixes in 19.0.1, 19.1.2 and 19.2.1, and it reached every RSC framework — Next.js, React Router, Waku, Parcel, the Vite RSC plugin, Redwood SDK. A week later, researchers probing the patch found two more: CVE-2025-55184, a DoS where a crafted request hangs the server in an infinite loop, and CVE-2025-55183, source-code exposure. Operationally I would have done four things: patch within hours using the framework's advisory rather than hand-editing versions, check access logs for exploitation attempts against Server Function endpoints, rotate any credential the server process could reach, and then treat the follow-ups as evidence that the first patch is never the end — the December fixes themselves needed a second round.

Example

# Find every affected package across a monorepo, including transitives.
npm ls react-server-dom-webpack react-server-dom-parcel react-server-dom-turbopack
npm audit --audit-level=high
# Patch to a fixed line, then verify nothing resolves to a vulnerable version.
npm i react@19.2.8 react-dom@19.2.8

Follow-ups

  • Why were apps with no Server Functions still vulnerable? — The decoding endpoint is part of the RSC runtime, not of your code; the attack surface was the framework's, not yours.
  • What is the durable lesson? — Any RPC boundary generated by a framework is an endpoint you own operationally, with a patch SLA and monitoring.
  • How do you know you were not exploited? — You often cannot with certainty; that is the argument for logging Server Function calls and for rotating credentials rather than assuming.

Common wrong answer

"We don't use Server Actions, so we weren't affected." Precisely the assumption that made this CVE dangerous. An interviewer who lived through that week is asking specifically to hear whether you understand that the endpoint belongs to the runtime.

seniorHow do you manage supply-chain risk in a React project with 1,200 transitive dependencies?

Answer

Reduce, pin, verify, and monitor. Reduce: fewer direct dependencies, and a real bar for adding one — a date library that could be Intl, a UI kit for two components, and every "helper" package is a permanent supply-chain liability. Pin: an exact lockfile committed, and, where the ecosystem supports it, install with provenance checks and disable post-install scripts by default, since that is where most npm compromises execute. Verify: automated dependency review on PRs, and a policy that a new dependency needs an owner and a justification. Monitor: an SBOM, Dependabot or Renovate with grouped updates so upgrading is routine rather than an event, and a defined patch SLA — critical within 24 hours, high within a week. The organisational point is that a team which cannot upgrade quickly is more at risk than a team with more dependencies: what kills you is being three majors behind when the CVE lands.

Example

# Reduce blast radius of a compromised package's install script.
npm config set ignore-scripts true
npm ci --ignore-scripts
# Know what you ship.
npx @cyclonedx/cyclonedx-npm --output-file sbom.json

Follow-ups

  • How do you keep upgrades from being scary? — Small, frequent, automated, with a test suite you trust; the fear is a symptom of the batch size.
  • What about a package with a single maintainer? — Vendor it, fork it, or accept the risk explicitly. Pretending it is not a risk is the only wrong option.
  • Does React itself belong in the SLA? — Yes, and December 2025 is the reason: React and its RSC packages are now on most teams' critical-patch list.

Common wrong answer

"Run npm audit in CI and fix what it reports." It is noisy, it misses install-time attacks entirely, and teams learn to ignore it within a month. It is one input, not a strategy.

principalA critical CVE lands in React at 16:00 on a Friday. What happens in your organisation?

Answer

What happens is determined by what I set up months earlier, and that is the real answer. There is an inventory that says which services use the affected packages and at which versions, so triage takes minutes rather than a day of Slack archaeology. There is a documented patch path — pinned versions, a tested pipeline, and a deploy that does not require the one person who is on a plane. There is an on-call rotation with the authority to ship without a change-advisory meeting, and a communications template for customers and for the security team. On the night itself: assess exposure honestly (which surfaces are internet-facing, which endpoints exist), apply mitigations that buy time if patching is slow — a WAF rule, disabling the affected route — patch, verify, then rotate credentials and review logs. Afterwards, a blameless review whose output is a shorter time-to-patch, and — the part people skip — a re-check a week later, because the December 2025 sequence proved that the first patch is sometimes incomplete.

Example

HourAction
0:00Inventory query: which services, which versions, which are internet-facing
0:30Mitigate the exposed surface (block the route / WAF rule) while patching proceeds
1:00Patch, run the pipeline, deploy highest-exposure services first
3:00Verify resolved versions in production; scan logs for exploitation attempts
Day 2Rotate reachable credentials; customer communication; blameless review
Day 7Re-check the advisory for follow-up CVEs and incomplete fixes

Follow-ups

  • What if patching breaks the build? — That is what the mitigation window is for; a temporarily disabled feature beats an exploitable one.
  • Who decides to take a service offline? — Named in advance, with authority, or the decision takes three hours you do not have.
  • What is the metric you would improve afterwards? — Median time from advisory to fully patched production, tracked per incident.

Common wrong answer

"Upgrade React and deploy immediately." Right instinct, no plan: no exposure assessment, no inventory, no mitigation for the services that cannot deploy tonight, and no credential rotation. Interviewers are listening for preparation, not heroics.

15Build and delivery

Rarely the focus of a React interview, but it comes up as a "how do you ship" question and as a proxy for whether you have run something in production. The 2025 sunset of Create React App made the tooling question concrete for a lot of teams, and the compiler added a build step with behavioural consequences. Keep answers short and current.

Docs: react.dev — Build a React app from scratch

screenerCreate React App is gone. What do you start a new React project with in 2026?

Answer

React's own guidance since the 14 February 2025 sunset post is: use a framework if you can — Next.js, React Router (framework mode) or Expo for native — and if you genuinely want a plain SPA, use Vite, Parcel or Rsbuild directly. CRA was deprecated because it could not offer routing, data loading or server rendering, and because its dependency tree had become a maintenance liability; existing apps still run but receive no updates. My default for a product with any public surface is a framework, because routing and data loading are things you will build badly otherwise; my default for an internal tool or an embedded widget is Vite plus a router, which starts in milliseconds and keeps the deployment story trivial.

Example

npm create vite@latest my-app -- --template react-ts   # SPA, compiler-ready templates
npx create-next-app@latest                             # framework, RSC
npx create-expo-app@latest                             # native; compiler on by default (SDK 54+)

Follow-ups

  • What do you do with an existing CRA app? — Migrate to Vite; it is usually days, not weeks, and it is independent of any React version change.
  • Is Webpack dead? — No, it is everywhere and maintained, but it is no longer the default choice for a new app.
  • What about the compiler in a new project? — Vite and Next.js templates can start with it enabled, and Expo SDK 54+ has it on by default.

Common wrong answer

"Create React App, it's the standard starting point." An immediate date-stamp: it was deprecated in February 2025 and the docs now recommend against it for new apps.

midWhat actually goes into a production React build, and how do you keep it small?

Answer

Your components, your dependencies, the polyfills your browser targets require, and — if enabled — the compiler's memoization code. Keeping it small is mostly about dependencies and boundaries rather than about your own code: analyse the bundle per route, look for the moment/lodash-shaped libraries that could be Intl or three functions, make sure tree-shaking is not defeated by sideEffects: false being absent or by importing a barrel file, and set a browserslist target that does not ship polyfills for browsers you do not support. In an RSC app the largest lever is the client boundary: a 'use client' placed too high pulls an entire subtree into the bundle. And the number to enforce is per-route JavaScript, in CI, because a total-size budget hides the route that regressed.

Example

# See what is actually in each chunk before optimising anything.
npx vite-bundle-visualizer
npx source-map-explorer 'dist/assets/*.js'

Follow-ups

  • Why are barrel files a problem? — import { Button } from '@ui' can pull the whole library if the bundler cannot prove the rest is side-effect free.
  • Does the compiler increase bundle size? — Slightly; it trades a few bytes for runtime work, which is usually the right trade but should be measured.
  • What is a reasonable budget? — Depends on audience, but for a consumer web app, first-load JS under roughly 150–200 KB compressed is a defensible starting line.

Common wrong answer

"Enable minification and gzip." Table stakes that every bundler already does. The interviewer is asking what you would investigate, and this answer says you have never opened a bundle analyser.

seniorHow do you deploy a React app safely — versioning, caching, rollback?

Answer

Content-hashed asset filenames served with long immutable cache headers, and a short-cached or uncached HTML entry point that references them — that combination gives instant cache invalidation with no stale-asset risk. Keep old asset versions on the CDN for a window, because users with a loaded page will request chunks after you deploy: deleting them produces the "ChunkLoadError" spike that every SPA team eventually sees. Handle that case explicitly too, with a boundary that reloads once on a chunk-load failure. Roll out progressively where you can and keep rollback to a pointer change rather than a rebuild. And detect the new version client-side — a build id in a periodic health response — so a long-lived tab can prompt the user rather than silently running month-old code against a changed API.

Example

Cache-Control: public, max-age=31536000, immutable   # /assets/app.a3f9c2.js
Cache-Control: no-cache                              # /index.html
// Recover from a chunk that no longer exists on the CDN.
window.addEventListener('vite:preloadError', () => {
  if (!sessionStorage.getItem('reloaded')) {
    sessionStorage.setItem('reloaded', '1');
    location.reload();
  }
});

Follow-ups

  • How long do you keep old assets? — At least as long as a plausible session; a week is common, and storage is cheaper than the incident.
  • How do you roll back an SSR app? — Deploy the previous image and make sure the assets for both versions are still served; a mismatched HTML/asset pair is its own outage.
  • Does a service worker help or hurt? — Both: it improves repeat loads and it can pin users to a stale build for days if the update strategy is wrong.

Common wrong answer

"Upload the build to the CDN and purge the cache." Purging is slow, global and blunt; content hashing makes it unnecessary. This answer also has no story for the users who are mid-session during the deploy.

principalHow do you keep twelve React apps on compatible versions without freezing everyone?

Answer

Version skew is a platform problem, so I would give it a platform answer: a shared preset package that owns React, the build tooling, the lint config and the compiler pin, consumed by every app, upgraded centrally and rolled out per app on a published schedule. Apps stay one minor behind at most, with a hard rule that nobody is more than one major behind — the pain of a two-major upgrade is superlinear and it is how teams end up permanently stuck. The mechanism is automation plus a canary: Renovate opens grouped upgrade PRs, the pilot app takes them first, and the rest follow when it has been in production for a week. What makes it sustainable is not the tooling, though: it is that the platform team is accountable for the upgrade path being cheap, so app teams are never asked to spend a sprint on someone else's dependency choice.

Example

{
  "name": "@acme/react-preset",
  "peerDependencies": { "react": "19.2.x", "react-dom": "19.2.x" },
  "dependencies": { "babel-plugin-react-compiler": "1.0.0" }
}

Follow-ups

  • What about the app that cannot upgrade? — Time-boxed exception with a written reason and a date; permanent exceptions become permanent liabilities.
  • How do you handle a breaking change in a shared component library? — Ship a codemod with the major, and support the previous major for one quarter.
  • Who pays for the upgrade work? — The platform team, in engineering time; if the cost lands on product teams, upgrades stop happening.

Common wrong answer

"Mandate that all apps upgrade within a quarter." A policy without a mechanism. The teams with the most technical debt — the ones that most need the upgrade — will be the ones that miss the deadline, and the mandate will quietly lapse.

16Debugging and observability

Interviewers ask about debugging when they want to know whether you have operated software, not just written it. The React-specific parts changed recently: Owner Stacks arrived in 19.1, error handling moved to root-level options in 19, hydration errors became a readable diff, and 19.2's Performance Tracks put React work on the browser timeline. Expect a "production is broken, what do you do" scenario at senior level.

Docs: react.dev — captureOwnerStack and Owner Stacks

screenerA component is rendering the wrong data. What are your first three moves?

Answer

One: look at the actual props and state in React DevTools rather than at the code — half the time the data is right and the render is wrong, or vice versa, and this tells you which. Two: check the identity question — is this the component instance I think it is? A wrong key, a duplicated component in two branches, or a remount will present as "wrong data" when it is really "wrong instance". Three: walk one level up. The bug is more often in what the parent passed than in what the child did, and the Components panel's owner information makes that a ten-second check. Only after those would I start adding logs, because logs answer questions you already have and DevTools answers the ones you have not thought of yet.

Example

// In the browser console, with a component selected in the DevTools Components panel:
$r.props     // the selected component's props
$r.state     // its state (class components)
// React 19.1+: the owner stack tells you which component created this element,
// which is what the JS stack cannot show you.

Follow-ups

  • What is an Owner Stack and why is it new? — Shipped in 19.1, it shows the chain of components that created the element, which is different from the call stack and is usually the question you actually have.
  • What if it only happens for one user? — Data-dependent: get the exact input, reproduce with their payload, and look for null handling and locale differences before anything else.
  • When do you reach for a breakpoint? — When the value is right at one point and wrong at another; a conditional breakpoint beats twenty log lines.

Common wrong answer

"Add console.log everywhere and follow the values." It works eventually, and it is slow. It also lies under StrictMode's double render, which is where a surprising number of "impossible" logs come from.

midHow do you debug a hydration mismatch?

Answer

React 19 made this dramatically easier: instead of a stream of vague warnings you get one error containing a diff of the server output and the client output, which usually names the offending node directly. From there the causes are a short checklist — non-deterministic values (dates, random, locale, timezone), browser-only APIs read during render, invalid HTML nesting that the browser silently repairs, and third-party scripts or browser extensions mutating the DOM before hydration, which is the one that produces unreproducible reports from users. I check invalid nesting early because it is easy to miss in JSX: a <div> inside a <p> or a <form> inside a <table> renders fine on the server and is silently restructured by the browser.

Example

// The browser moves the div out of the p; the client tree no longer matches.
<p>Note: <div>{note}</div></p>         // ❌ invalid nesting
<p>Note: <span>{note}</span></p>       // ✅

Follow-ups

  • How do you rule out an extension? — Reproduce in a clean profile or incognito with extensions disabled; ad blockers and password managers both inject nodes.
  • What is the cost of a mismatch you ignore? — React discards the server HTML for that subtree and client-renders it, so you lose the SSR benefit precisely where you wanted it.
  • How do you catch these before production? — Run SSR locally in CI for the key routes and fail on hydration errors; they are deterministic for the non-extension causes.

Common wrong answer

"Wrap the component in a useEffect-gated client-only render." It silences everything by disabling SSR for that subtree, which is a real fix in a narrow case (a chart that needs window) and a way to lose your server rendering everywhere else.

seniorWhat does production observability look like for a React frontend?

Answer

Four streams. Errors: a tracker wired to the root's onUncaughtError and onCaughtError plus window.onerror and unhandledrejection, with source maps uploaded so stacks are readable and release tags so you can attribute a spike to a deploy. Performance: real-user Core Web Vitals — LCP, INP, CLS — reported at p75 and segmented by route and device class, because averages hide the users who are suffering. Product telemetry: the funnel steps that tell you whether the app is working from the user's point of view, which is often the first signal that something is broken. And traces that cross the boundary: a request id propagated from the browser into the server render and the API, so a slow page has one story rather than three. The rule I would state is that alerting belongs on user-visible symptoms — error rate, INP, funnel completion — not on technical proxies.

Example

const root = createRoot(el, {
  onUncaughtError: (error, info) => tracker.report(error, { componentStack: info.componentStack, release }),
  onCaughtError:   (error, info) => tracker.report(error, { handled: true, ...info }),
});

Follow-ups

  • How do you keep error volume manageable? — Group by fingerprint, filter known browser-extension noise, and alert on rate change rather than absolute count.
  • What is the highest-value single addition for most teams? — Source maps plus release tagging; without them the tracker is a list of minified mysteries.
  • What about session replay? — Powerful for hard bugs, and a privacy obligation: masking rules and a retention policy before you turn it on.

Common wrong answer

"Sentry catches everything, so we're covered." An error tracker is one of the four streams, and it is blind to the app being slow, to the funnel silently dropping, and to errors swallowed by a try/catch someone added to quiet the dashboard.

seniorUsers report the app "freezes" occasionally. Nothing in the error tracker. How do you investigate?

Answer

"Freeze" without errors means a long task blocking the main thread, so I would go looking for it in field data first: INP and the long-task attribution in RUM, segmented by route, device class and browser. That usually localises it to a route and a device tier, and often to a specific interaction. Then I reproduce with CPU throttling — 4× or 6× — because the bug is almost always invisible on developer hardware. The React-specific suspects are a large synchronous render (a list that grew with the customer's data), a synchronous layout effect measuring in a loop, an unintended flushSync, or a state update on every scroll or mousemove event. The 19.2 Performance Tracks are the right tool here because they show React's work interleaved with browser tasks, so you can see whether the frame was lost to render, to commit, or to something that is not React at all — which it sometimes is.

Example

// Field-side long-task attribution: find the route and device tier before you profile.
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 200) report('long-task', { duration: entry.duration, route: currentRouteId() });
  }
}).observe({ type: 'longtask', buffered: true });

Follow-ups

  • Why would this not appear in the error tracker at all? — Nothing threw; the app is working exactly as written, just too slowly to be usable.
  • What is the quickest structural fix if it is a big render? — Move the update into a transition or defer the value, so the render becomes interruptible; then virtualize if the size is inherent.
  • How do you prove it is fixed? — The same field metric, p75 by route, over a week — not a local profile that looks better.

Common wrong answer

"Ask users for reproduction steps and try it locally." You will not reproduce it: your machine is four times faster, your dataset is ten rows, and your network is not theirs. Field measurement first is the entire senior signal here.

principalHow do you run an incident where a bad frontend deploy breaks checkout?

Answer

Stop the bleeding before understanding it: roll back or kill the flag first, because a frontend deploy is usually reversible in minutes and diagnosis on a burning revenue path is a bad trade. In parallel, communicate — a named incident commander, a channel, a status update with a next-update time — because the second failure mode of frontend incidents is six people investigating the same thing while nobody talks to support. Then confirm recovery with the metric that made you notice, not with a manual click-through. Afterwards, the useful work: a blameless review that asks why this reached production and why it took as long as it did to detect, with two or three concrete outputs — usually a synthetic check on the checkout flow, a canary or progressive rollout so the next bad deploy hits 1% of users, and a rollback that does not require a rebuild. The failure I would name explicitly is prioritising root cause over recovery; understanding can wait an hour, revenue cannot.

Example

MinuteAction
0Declare, assign a commander, open the channel
2Roll back the deploy or disable the flag — recovery before diagnosis
10Confirm recovery on the conversion metric and the error rate
15Status update to support and stakeholders with a next-update time
Day 1Blameless review: detection gap, rollback speed, missing synthetic check

Follow-ups

  • What if rollback is not possible? — That is the finding. Fix-forward with a minimal patch, and make rollback a first-class capability afterwards.
  • How did it get past CI? — Usually an interaction with real data or a third party; that is an argument for synthetic checks against production, not for more unit tests.
  • Who talks to customers? — Someone other than the people fixing it, decided before the incident, not during.

Common wrong answer

"Find the root cause and push a fix." Under pressure this becomes a 90-minute outage that a two-minute rollback would have ended. Interviewers listen for the order: recover, communicate, then understand.

17Migration and legacy React

Asked rarely as a topic and constantly as a subtext, because every real codebase has legacy in it. You should be able to read class components fluently, explain what changed in 18 and 19 and why, and describe an upgrade you would actually be willing to run. At lead level this is where interviewers check whether you can modernise without stopping the business.

Docs: react.dev — React 19 Upgrade Guide

screenerMap the class lifecycle methods onto hooks.

Answer

Roughly: constructor becomes useState with a lazy initialiser; componentDidMount and componentDidUpdate become useEffect with the right dependencies; componentWillUnmount becomes the effect's cleanup; shouldComponentUpdate becomes memo; getDerivedStateFromProps usually becomes deriving during render or a key. But I would qualify the mapping immediately, because it is the trap in this question: effects are not lifecycle callbacks, they are synchronisation keyed to values, and porting a class one method at a time produces effects with wrong dependencies and "run once" assumptions. The two things with no hook equivalent are error boundaries — still class-only in React 19 — and getSnapshotBeforeUpdate.

Example

// Class
componentDidMount()    { this.sub = subscribe(this.props.id, this.onData); }
componentDidUpdate(pp) { if (pp.id !== this.props.id) { this.sub.close(); this.sub = subscribe(this.props.id, this.onData); } }
componentWillUnmount() { this.sub.close(); }

// Hook: one description of the synchronisation, all three cases covered.
useEffect(() => {
  const sub = subscribe(id, onData);
  return () => sub.close();
}, [id, onData]);

Follow-ups

  • Why is the hook version shorter and safer? — The update case is not a separate branch you can forget; it falls out of the dependency array.
  • Do you still need classes? — Only for error boundaries, or for legacy code you are not rewriting. New code has no other reason.
  • Is there a codemod? — Not a reliable one for lifecycle logic; the mapping needs judgment, which is why "convert every class" projects stall.

Common wrong answer

"useEffect(fn, []) is componentDidMount." It is the mental model that produces effects that break under StrictMode, Fast Refresh, <Activity> and any future state reuse. The mapping is a translation aid, not a definition.

midWhat actually breaks when you upgrade from React 17 to 18?

Answer

Three things in practice. Automatic batching now applies everywhere — promises, timeouts, native handlers — so code that relied on a re-render between two setState calls behaves differently; flushSync is the escape hatch, and needing it is a smell. StrictMode's double-invoked effects surface every non-idempotent effect in the codebase, which feels like the upgrade broke things when it actually revealed them. And the root API changed: ReactDOM.render is deprecated in favour of createRoot, and until you switch you are not really on 18. There are smaller edges — useEffect timing changes, stricter TypeScript types (children no longer implicit), and third-party libraries needing updates for concurrent rendering. The order that works is: upgrade the packages with the legacy root first, then switch to createRoot, then enable StrictMode.

Example

// Legacy
ReactDOM.render(<App />, container);

// React 18+
const root = createRoot(container);
root.render(<App />);

Follow-ups

  • Why stage the root switch separately? — It is the change that turns on concurrent behaviour; isolating it makes any regression attributable.
  • What did automatic batching break in real codebases? — Code reading the DOM between two updates, and tests asserting an intermediate render.
  • Do you have to adopt concurrent features? — No; createRoot enables the concurrent renderer, but transitions and Suspense-for-data are opt-in.

Common wrong answer

"Nothing breaks, 18 is backwards compatible." Mostly true and operationally misleading: the StrictMode and batching changes generate real bug reports on day one, and a team told to expect none will roll back at the first one.

midWhat are the breaking changes in React 19?

Answer

The removals are mostly things deprecated years earlier: legacy context (contextTypes), string refs, defaultProps on function components (use default parameters), propTypes (types belong in TypeScript), and the legacy ReactDOM.render/hydrate paths. Errors are no longer re-thrown to the console by default — they go to onUncaughtError/onCaughtError — so a tracker wired to window.onerror alone can silently go quiet. Refs became ordinary props with forwardRef deprecated, <Context> can be rendered as a provider, and useFormState was renamed useActionState and moved to react. There is an official codemod recipe that handles most of it mechanically; the parts that need judgment are error reporting and any library that has not shipped a React 19 compatible release.

Example

npx codemod@latest react/19/migration-recipe
// defaultProps on a function component no longer works.
function Badge({ tone = 'neutral' }) { /* default parameter instead */ }

Follow-ups

  • What is the sneakiest one? — The error-handling change: monitoring can look healthy because nothing is reaching the console any more.
  • What blocks most upgrades in practice? — A dependency without a 19-compatible release; check the tree before scheduling the work.
  • Is React 18 still supported? — It receives security patches (the December 2025 RSC advisories were backported across 19.0/19.1/19.2 lines), but features land on the current line.

Common wrong answer

"React 19 is mostly additive — Actions and the compiler." Additive is the headline, but a codebase with defaultProps, string refs or console-based error monitoring will notice the removals immediately.

seniorHow do you run a large React upgrade without freezing feature work?

Answer

Small, reversible steps on the main branch, never a long-lived migration branch — the branch is what kills these projects, because it accumulates conflicts faster than it accumulates progress. Concretely: upgrade dependencies to versions compatible with both old and new first; land codemods as their own mechanical PRs that are easy to review; put behavioural changes behind a flag or a per-route switch so you can enable them for 1% of traffic; and keep every step independently deployable so that stopping halfway leaves a working system. I would also fix the test suite before starting, because an upgrade without trustworthy tests is a series of guesses. And I would publish a burn-down so the work is visible — upgrades die of invisibility more often than of difficulty.

Example

# Each step ships on its own, in this order.
# 1. dependencies compatible with both versions   → deploy
# 2. codemods (mechanical, reviewable)            → deploy
# 3. React upgraded, legacy root retained         → deploy
# 4. createRoot behind a flag, 1% → 100%          → deploy
# 5. StrictMode on in development                 → fix what it reveals

Follow-ups

  • How do you handle a library with no compatible release? — Patch it (patch-package), fork it, or replace it — decided before you start, not discovered at step 3.
  • What if it stalls at 60%? — Because each step deployed, 60% is a working system. That property is the whole reason for the sequencing.
  • How do you keep feature teams from blocking? — Mechanical PRs land fast and touch many files; coordinate the big ones for a quiet window and merge the same day.

Common wrong answer

"Create a migration branch and merge it when everything works." Six weeks of conflicts, a merge nobody can review, and a rollback story that is "revert everything". Interviewers who have lived through it will push exactly here.

principalYou inherit a React 16 app with jQuery plugins and no tests. What is the plan?

Answer

First: find out whether it matters. What does this app earn, who uses it, what is the roadmap, and what specifically is going wrong — because "it's old" is not a business problem and a modernisation with no named pain gets cancelled the first time priorities move. Assuming there is real pain, I would sequence by risk rather than by tidiness: characterisation tests around the two or three flows that must not break, then dependency and security updates (a React 16 app has a long list), then the build tooling, and only then the React version. jQuery plugins get wrapped in a component with a lifecycle-managed adapter rather than rewritten, and they get replaced when someone is already changing that screen. The rule I would state is that the app must keep working and shipping the entire time, and that I expect to leave parts of it untouched permanently — modernising code nobody runs is a hobby, not engineering.

Example

// Contain the legacy widget instead of rewriting it: React owns the node's lifetime.
function LegacyDatePicker({ value, onChange }) {
  const ref = useRef(null);
  useEffect(() => {
    const el = ref.current;
    $(el).datepicker({ defaultDate: value }).on('change', (e) => onChange(e.target.value));
    return () => { $(el).datepicker('destroy'); };
  }, []);
  return <input ref={ref} readOnly />;
}

Follow-ups

  • Rewrite or strangle? — Strangle by default: route-by-route replacement behind a proxy keeps the business running. A rewrite needs an exceptional justification and a hard stop condition.
  • How do you get budget? — Attach it to something the business already wants — a feature that is expensive to build in the old app — rather than asking for a modernisation quarter.
  • What do you do first on day one? — Make it deployable and observable. You cannot change what you cannot ship or measure.

Common wrong answer

"Rewrite it in Next.js with modern tooling." Twelve months, no incremental value, and the old app still needs maintaining throughout. It is the single most common way senior candidates fail this question.

18Internals: fiber and scheduler

Rarely decisive, occasionally asked at staff-plus or by an interviewer who works on infrastructure. The value is not trivia: understanding the fiber architecture is what lets you explain why renders are interruptible, why refs and mutation are dangerous during render, and what "double buffering" implies for effects. Answer at the level of mechanism, and say plainly when something is an implementation detail that may change.

Docs: react.dev — Render and Commit

seniorWhat is a fiber, and why was the architecture rewritten?

Answer

A fiber is a unit of work: a mutable object per component instance holding its type, props, state, hooks list, effect list and pointers to its child, sibling and parent. The old (stack) reconciler recursed through the tree synchronously, so once a render started it ran to completion and blocked the main thread. Fiber replaced recursion with a linked-list traversal React can pause, resume, abandon and restart — which is what makes concurrent features possible. React keeps two trees, current and work-in-progress, and swaps them at commit; that double buffering is why the render phase can be thrown away safely and why mutating anything shared during render is dangerous. The honest caveat is that fiber internals are unstable implementation details: know the model, do not build on the field names.

Example

// The shape of the model, not an API to rely on.
fiber = {
  type, key, stateNode,
  child, sibling, return,     // the traversal links that replaced recursion
  memoizedProps, memoizedState,
  alternate,                  // the other tree: current ↔ work-in-progress
  flags, lanes,               // what to do at commit, and at which priority
};

Follow-ups

  • Why can the render phase run twice? — Because an interrupted render is discarded and restarted from the current tree; StrictMode makes this visible in development.
  • Where does hook state live? — In a linked list on the fiber, traversed positionally each render — the mechanical reason for the Rules of Hooks.
  • Is the commit phase interruptible? — No; commit is synchronous and atomic, which is why the DOM is never seen half-updated.

Common wrong answer

"Fiber is the virtual DOM." The element tree is the description; fibers are the persistent instances with state and scheduling information. Conflating them makes it impossible to explain why state survives some re-renders and not others.

seniorHow does React prioritise updates? What are lanes?

Answer

Every update is assigned a priority — internally a bitmask called lanes — and React renders the highest-priority pending work first, interrupting lower-priority work if necessary. Discrete input (click, keypress) is synchronous-priority so it feels instant; a transition is lower and interruptible; an offscreen or <Activity mode="hidden"> update is lower still, deferred until idle. Lanes as a bitmask matter because they let React batch and track several independent priorities at once rather than a single number. React 19.2's Scheduler performance track exposes this in Chrome DevTools — you can see which lane work ran in and where it was starved — which is the first time this has been observable without reading React's source.

Example

setQuery(next);                             // discrete input: highest priority
startTransition(() => setResults(next));    // transition lane: interruptible
<Activity mode="hidden"><NextRoute /></Activity>   // idle-ish: lowest priority

Follow-ups

  • Can starvation happen? — Yes; React expires low-priority work after a timeout and forces it through, so a transition cannot be postponed forever.
  • Does React use requestIdleCallback? — No — it schedules with a MessageChannel-based scheduler for finer control and better cross-browser behaviour.
  • Can you set a priority directly? — Only through the public APIs: transitions, deferred values, Activity. There is no user-facing priority number, deliberately.

Common wrong answer

"React renders in a Web Worker / off the main thread." There is one main thread. The work is sliced and prioritised, not parallelised, and believing otherwise leads to expecting throughput that does not exist.

seniorHow does hydration work internally, and what is selective hydration?

Answer

Hydration walks the server-rendered DOM alongside a client render, adopting existing nodes instead of creating them and attaching event handling at the root. Since React 18 it is selective: with Suspense boundaries, React can hydrate boundaries independently and in any order, and it does not have to wait for all the JavaScript to arrive. It is also interaction-driven — if the user clicks inside a boundary that has not hydrated yet, React prioritises hydrating that boundary and then replays the event, so the click is not lost. That is the mechanism behind "the page is usable before it is fully hydrated". The practical consequence for design: your Suspense boundaries are also your hydration units, so a page with one boundary hydrates as one monolith.

Example

// Each boundary is a hydration unit; a click in Comments hydrates Comments first.
<Suspense fallback={<S />}><Sidebar /></Suspense>
<Suspense fallback={<S />}><Comments /></Suspense>

Follow-ups

  • What happens to events fired before hydration? — React captures them at the root and replays them once the relevant boundary hydrates.
  • What is the cost of hydration overall? — Roughly a full client render plus DOM matching; it is why "SSR then hydrate everything" is slower to interactive than shipping less client code.
  • How do RSC change it? — Server Components never hydrate; only Client Components do, so the hydration cost scales with your client boundary, not with page size.

Common wrong answer

"Hydration attaches event listeners to the server HTML." Undersells it: React rebuilds the entire component tree in memory, which is why hydration costs real CPU and why a large hydrated page is slow to become interactive.

seniorWhy must the render phase be pure? Give a concrete failure.

Answer

Because React may call a component more than once for a single visible update, may throw away a render entirely, and may render a tree it never commits. Any side effect in the render body therefore happens an unpredictable number of times, at unpredictable moments, sometimes for a tree the user never sees. A concrete failure: a component that increments an analytics counter or pushes to a module-level array during render will double-count under StrictMode, count again when a transition is interrupted and restarted, and count for offscreen work in an <Activity mode="hidden"> subtree that is never shown. Purity is also what the React Compiler's analysis depends on — an impure component is silently skipped — so in 2026 impurity costs you both correctness and performance.

Example

let seen = [];                       // module scope: outlives every render
function Row({ item }) {
  seen.push(item.id);                // ❌ grows unpredictably; leaks memory
  analytics.track('row_rendered');   // ❌ fires for renders nobody sees
  return <li>{item.name}</li>;
}

Follow-ups

  • Where should that tracking go? — An effect (for "was displayed") or an event handler (for "was interacted with"); the distinction is usually the actual product question.
  • Is creating and mutating a local object during render impure? — No: values created in this render are yours until returned. The rule concerns values you did not create.
  • How do you catch impurity? — StrictMode's double render, plus the compiler's bail-out report, which is a surprisingly effective purity linter.

Common wrong answer

"Because React might render twice in StrictMode." True, incomplete, and it frames purity as a development-mode annoyance rather than a requirement of concurrent rendering — which is how people end up disabling StrictMode instead of fixing the component.

principalHow would you decide whether to build a custom React renderer?

Answer

Very reluctantly, and only when the target is a genuine rendering surface with a stable host API — canvas or WebGL scenes (react-three-fiber), terminal UIs (Ink), a PDF or document model, a hardware display. The value is real: you get React's component model, reconciliation, hooks and state management for free on a non-DOM target. The costs are structural and recur forever: react-reconciler is not a stable public API and changes between React versions, so you own an upgrade treadmill; you must implement the host config correctly, including the parts (mutation modes, text handling, priority) that are hard to get right; and every React feature that assumes the DOM — Suspense integration, event delegation, testing tools — is now partly yours. So the decision rule I would use: if the domain has fewer than a dozen node types and a straightforward mutation model, and the alternative is an imperative API that your product team would maintain anyway, it can pay off; otherwise use an existing renderer or a thin imperative wrapper.

Example

import Reconciler from 'react-reconciler';

const renderer = Reconciler({
  supportsMutation: true,
  createInstance(type, props) { return scene.create(type, props); },
  appendChild(parent, child) { parent.add(child); },
  commitUpdate(instance, _t, oldProps, newProps) { instance.apply(newProps); },
  removeChild(parent, child) { parent.remove(child); },
  // ...roughly thirty more host config methods, all of which you now own
});

Follow-ups

  • What is the maintenance cost in practice? — A React upgrade becomes a project rather than a version bump, because the reconciler contract can change between majors.
  • What is the alternative? — A declarative wrapper over the imperative API with your own diffing, which is less capable and dramatically cheaper to own.
  • How do you evaluate an existing renderer? — Maintenance activity and React-version support first; an abandoned renderer pins you to an old React forever.

Common wrong answer

"It's straightforward — implement the host config and you get React for free." The host config is the easy 20%; the ongoing coupling to an unstable internal API is the part that costs a team member indefinitely.

19Ecosystem and governance

Three questions at most, usually as conversation rather than assessment — but at lead and principal level "how do you keep up, and how do you decide what to adopt" is a real signal, and the February 2026 governance change is the kind of fact that shows you follow the platform rather than just use it.

Docs: react.dev — The React Foundation

screenerWho owns React now, and why does it matter?

Answer

Since 24 February 2026, React, React Native and supporting projects including JSX are owned by the React Foundation, hosted by the Linux Foundation, with eight platinum founding members: Amazon, Callstack, Expo, Huawei, Meta, Microsoft, Software Mansion and Vercel. It matters for the reason foundations usually matter — a neutral trademark and IP home reduces single-vendor risk, which is the objection enterprises and legal teams have raised about React since it was a Meta project. Technical direction still sits with the core team; the foundation governs stewardship, funding and trademarks rather than the roadmap. In an interview it is worth knowing because it is exactly the kind of question that separates people who read release notes from people who follow the ecosystem.

  • Does Meta still contribute? — Yes, as a platinum member, and React is still used at Meta scale — which is where the compiler's numbers came from.
  • Why would a company care? — Procurement and risk teams treat foundation-hosted projects differently from single-vendor ones.

Common wrong answer

"Meta owns React." True until February 2026, and it is the kind of confidently stale fact interviewers notice — especially at a company that had a governance concern about React.

seniorHow do you evaluate whether to adopt a new React feature or library?

Answer

I ask what problem it solves that we actually have, what it costs to reverse, and who maintains it. The reversibility question does most of the work: a library that touches one component is a cheap experiment, while a router, a state layer or a rendering architecture is effectively permanent, so it deserves a prototype, a written comparison and a decision record. For React's own features I weight release channel and time in production — canary features (<ViewTransition> is still canary in September 2026) are for experiments, stable features with a migration path are for products. And I would rather adopt one thing well than three things partially: half-adopted tools are worse than either alternative because the codebase now contains two patterns and neither is complete.

Follow-ups

  • How do you avoid resume-driven development on your team? — Require the problem statement before the tool, and make ADRs normal so the reasoning is public rather than personal.
  • When do you adopt something early? — When the pain is acute, the blast radius is small, and you can afford to be wrong — that combination is rarer than people think.
  • How do you retire a tool you adopted? — Plan the exit when you adopt it; "how would we remove this" is a question with a surprisingly clarifying effect.

Common wrong answer

"Check GitHub stars and whether it's actively maintained." Necessary and nowhere near sufficient; it says nothing about the problem you have, the cost of reversal, or the fit with what your team can operate.

principalHow do you keep a large frontend organisation current without chasing every trend?

Answer

By making currency routine instead of heroic. Routine upgrades — automated, small, frequent, owned by a platform team — mean the org is never more than one version behind, which is what makes security patching and feature adoption cheap. A small, explicit budget for exploration: one or two spikes per quarter with a written outcome, so curiosity has a channel that is not "someone shipped a new library into production on a Friday". Decision records so choices are revisitable and newcomers can read why, rather than re-litigating annually. And a stated principle that boring is a feature: the org's job is to ship product, and a technology choice needs to justify itself against the cost of everyone learning it. The trap on the other side is real too — an org that never adopts anything becomes unhirable and its people leave — so I would treat "we are two majors behind on everything" as an incident-level signal, not a preference.

Example

# The mechanism that makes "current" the default state.
# - Renovate: grouped, automated, weekly; platform team merges
# - One canary app takes upgrades first, one week ahead of the rest
# - Quarterly: 2 timeboxed spikes with a written ADR outcome
# - Rule: nothing more than one major behind, tracked publicly

Follow-ups

  • How do you handle the engineer who wants to rewrite in the newest thing? — Give them the spike and the ADR. Most enthusiasm survives contact with a written cost estimate, and the ones that do are usually right.
  • How do you know you have fallen behind? — Track version lag as a metric, and watch hiring and onboarding friction — both are lagging indicators of stagnation.
  • What is the cost of being too current? — Churn, half-migrations, and a codebase with four patterns for the same thing; that is why adoption needs a bar, not a ban.

Common wrong answer

"Standardise on a stack and freeze it for two years." It looks like discipline and produces a three-major upgrade cliff, an unpatched security surface, and engineers who leave to work on something current. Stability is a cadence, not a freeze.

20Judgment calls

Open-ended questions with no single right answer, asked from senior level upwards to see how you reason under ambiguity. There is no "answer" hidden in these blocks — instead, what a strong response demonstrates and which trade-offs the interviewer expects you to name without being prompted. The failure mode in all of them is a confident universal rule; the winning move is a decision framework plus a stated default plus the conditions that would change it.

Docs: react.dev — Thinking in React

principalServer Components or a client SPA for a new product — how do you decide?

What a strong answer demonstrates

That you start from the product's shape rather than the technology's momentum: how much of the UI is read-mostly versus interactive, whether the content must be indexable, whether there is a server runtime you are willing to operate, and what the team already knows. A strong answer states a default ("RSC for anything content-heavy and public; SPA for an authenticated, highly interactive tool") and then names the specific evidence that would flip it. It also treats the operational cost honestly — a Node runtime with a patch obligation, harder local debugging, framework lock-in — rather than pretending the choice is purely about bundle size.

Trade-offs to name unprompted

  • Less client JavaScript and direct data access, against a server you must run, scale and patch (December 2025's RSC CVEs made that concrete).
  • Framework lock-in: RSC in practice means adopting a framework's router, bundler and caching model.
  • Team learning curve: the client/server boundary is a genuinely new mental model and shows up in code review for months.
  • Hiring and ecosystem: SPA patterns are more widely understood; RSC expertise is thinner.
  • Reversibility: moving from SPA to RSC later is a large project, so this is one of the few genuinely expensive early decisions.
principalIs the React Compiler worth enabling in your codebase?

What a strong answer demonstrates

That you treat it as a measurable change rather than an obvious win. A strong answer proposes a pilot with a before/after on p75 INP from real users, notes that the benefit is proportional to how much manual memoization is missing today, and recognises that the prerequisite — code that follows the Rules of React — is itself the valuable part. It should also name the risk precisely: memoization changes when values change identity, which changes when effects re-run, so a codebase with weak tests is genuinely riskier here.

Trade-offs to name unprompted

  • Compile-time cost and a small bundle increase against runtime CPU savings.
  • Pinning an exact version (the React team's own advice) versus staying current automatically.
  • Silent bail-outs: rule violations cost performance invisibly, so you need the build report in CI or you will not know.
  • Existing manual memoization becomes redundant but is sometimes load-bearing; removing it is a separate, riskier project.
  • The honest null result: on a well-memoized codebase the win may be small, and saying so is better than assuming.
seniorBuild your own design system, or adopt an existing one?

What a strong answer demonstrates

That you separate the three layers — behaviour and accessibility, styling, and brand tokens — and recognise that "build" almost never means building the first one. The strong position in 2026 is to adopt headless behaviour (Radix, React Aria) and own the styling and tokens, because accessible overlays and menus are enormously expensive to get right and almost never a differentiator. A candidate at this level should also weigh the maintenance capacity of the team honestly: a bespoke system with one part-time maintainer is worse than an adopted one with a community.

Trade-offs to name unprompted

  • Control and brand fidelity against maintenance load and accessibility risk.
  • Dependency risk: an abandoned UI library is a large, slow migration.
  • Team velocity now versus the cost of an escape hatch you did not design for.
  • Hiring: engineers know the popular systems; your bespoke one has an onboarding cost forever.
  • The middle path — headless behaviour plus your own styling — is usually right, and saying why is the whole answer.
seniorHow much global client state is too much?

What a strong answer demonstrates

An operational definition rather than a number: state is too global when a change in one feature can break another feature that no one connected to it, when nobody can say who owns a slice, or when most of the store is server data with hand-written invalidation. A strong answer proposes the test ("would moving this local break anything?") and the process (an admission bar with a named owner) rather than a component-count rule, and it explains that the usual cure is not a smaller store but a query cache plus the URL absorbing most of what was in it.

Trade-offs to name unprompted

  • Convenience of reaching state from anywhere against the loss of local reasoning and testability.
  • Global state as an implicit coupling between teams that shows up at release time.
  • Debuggability: a store with devtools and time travel is easier to inspect than scattered state — genuinely a point in its favour.
  • Migration cost: shrinking a junk-drawer store is a quarter of work, so prevention beats cure.
  • Server-state-as-global is the specific failure mode; naming it is what distinguishes the answer.
principalWhen is a rewrite the right call rather than incremental refactoring?

What a strong answer demonstrates

Extreme reluctance, plus the specific conditions under which the reluctance is wrong: a genuinely small codebase, an obsolete platform with no upgrade path, or a product whose requirements have changed so fundamentally that the existing model is the obstacle. A strong answer insists on a strangler pattern by default — route by route behind a proxy, with both versions in production — and on a stop condition agreed before starting. It also names the organisational reality that kills rewrites: the old system keeps needing features, and a team maintaining two systems delivers slower than one team doing neither well.

Trade-offs to name unprompted

  • Feature freeze cost against accumulated maintenance cost — with real numbers, not vibes.
  • Knowledge loss: the old code encodes years of bug fixes and edge cases nobody documented.
  • Risk concentration: a big-bang cutover has a single, unforgiving failure moment.
  • Morale in both directions — rewrites are motivating to start and demoralising at 70%.
  • "Leave parts unrewritten forever" is a legitimate outcome, and planning for it is a sign of experience.
seniorShould every team in the org fetch data the same way?

What a strong answer demonstrates

That you can distinguish standards that pay for themselves from standards that are just uniformity. Data fetching is one of the strongest candidates for standardisation because the semantics are subtle — dedupe, staleness, cancellation, invalidation — and because cross-team invalidation is impossible without a shared cache-key convention. A strong answer standardises the contract (one cache, one key convention, one error and retry policy) while leaving room for a team with a genuinely different problem, and pairs the standard with a working library so it is the path of least resistance rather than a rule.

Trade-offs to name unprompted

  • Consistency and cross-team invalidation against local autonomy and fit for unusual cases.
  • A standard nobody enforces is documentation; a standard with no escape hatch gets forked.
  • Migration cost for teams already on something else — often the deciding factor.
  • Central ownership: the standard needs a maintainer, or it decays into three dialects.
  • Real-time data (websockets, SSE) usually does not fit the same model and needs an explicit exception.
seniorA feature is ready but has a known accessibility gap. Ship or hold?

What a strong answer demonstrates

That you triage by user impact rather than by policy reflex. A missing aria-label on a decorative icon is not the same as a modal that traps keyboard users or a form that cannot be completed without a mouse — the first ships with a ticket, the second does not ship. A strong answer also asks who the users are (an internal tool with known users differs from a public service under the European Accessibility Act), proposes a time-boxed mitigation where one exists, and refuses to let "we'll fix it later" be the answer without a date and an owner, because that is how permanent gaps are created.

Trade-offs to name unprompted

  • Business urgency against exclusion of real users — and the fact that "temporarily" tends to become permanent.
  • Legal and procurement exposure, which for public-facing EU products is now concrete.
  • Cost of fixing now versus after the pattern is copied into ten more screens.
  • Whether the gap can be mitigated (a documented alternative path) rather than only fixed or ignored.
  • Precedent: the decision teaches the team what the bar actually is, whatever the policy says.
seniorHow much testing is enough for a product that ships daily?

What a strong answer demonstrates

That "enough" is defined by consequences, not by coverage: enough to deploy on a Friday without a knot in your stomach, and enough that the flows whose failure costs money are covered end to end. A strong answer differentiates by blast radius — checkout and auth get more than the settings page — and considers alternatives to testing that buy the same confidence: feature flags, progressive rollout, fast rollback and good monitoring can be a better investment than another hundred unit tests. It also names the cost of a slow or flaky suite, since a suite people bypass provides negative value.

Trade-offs to name unprompted

  • Test-suite runtime against feedback speed — a 30-minute suite changes how people work.
  • Flakiness as a trust problem, not an inconvenience.
  • Tests as design pressure versus tests as change-detectors that ossify the code.
  • Observability and rollback as partial substitutes for pre-deploy confidence.
  • Different bars for different blast radii — a single org-wide number is the wrong shape.
seniorStrict TypeScript everywhere, or pragmatic escape hatches?

What a strong answer demonstrates

Judgment about where types earn their cost. Strict at trust boundaries and in domain logic — API responses, money, permissions, state machines — where a type error is a bug; pragmatic in throwaway or presentational code where the elaborate type mostly generates puzzles for the next reader. A strong answer treats any as a documented decision rather than a moral failing, prefers @ts-expect-error over @ts-ignore because it self-cleans, and insists that runtime validation, not types, guards data crossing a network boundary.

Trade-offs to name unprompted

  • Safety against velocity, and against the readability of the error messages complex types produce.
  • Onboarding: a codebase full of conditional types is hostile to new engineers.
  • Types are erased — they are not validation, and treating them as such at an API boundary is a security bug.
  • Incremental adoption via a baseline beats a global flip.
  • Team composition: what a five-person team can carry differs from what fifty can.
principalWhen do you accept a performance regression?

What a strong answer demonstrates

That you can hold a budget and still say yes. Accepting a regression is legitimate when the feature's value clearly exceeds the cost, when the affected metric is not the one your users feel, or when the regression is confined to a segment you can name — and it is illegitimate when nobody measured it, when it lands on the slowest device tier, or when it is being accepted silently because the deadline is Friday. A strong answer converts the decision into a written trade with an owner and a review date, and knows which metric to defend hardest: usually INP for interactive products, LCP for content ones.

Trade-offs to name unprompted

  • Conversion and retention effects of latency against the value of the feature.
  • Segment asymmetry: p50 unchanged and p95 doubled means you hurt the users already suffering most.
  • Compounding: five accepted 5% regressions are a rewrite in eighteen months.
  • Reversibility — behind a flag, a regression is an experiment; shipped to everyone, it is a commitment.
  • Precedent and process: an exception with a written rationale strengthens the budget; a silent one destroys it.

Exercise 1 — A collaborative document editor

Prompt. Design the frontend architecture for a collaborative rich-text editor: multiple users editing the same document simultaneously, with presence (cursors and selections), offline editing, and documents up to a few hundred pages. React is a given; everything else is yours.

Clarifying questions to ask first

  • How many concurrent editors per document — three colleagues, or a hundred-person class?
  • Is offline editing required, or only resilience to brief disconnections? Offline changes the data model, not just the transport.
  • What is the conflict policy: automatic merge, or is last-write-wins acceptable for some fields?
  • Do we need document history and comments, and must comments survive an edit that removes their anchor?
  • What are the client constraints — mobile browsers, low-end devices, enterprise browsers?
principalStrong solution outline and expected trade-offs

Shape of the answer

The document model does not belong in React state. Use a CRDT (Yjs or Automerge) as the source of truth, held outside React, with the editor (ProseMirror/Lexical/TipTap) bound to it directly and React used only for the shell — toolbars, menus, presence avatars, comment panels. React subscribes to the CRDT through useSyncExternalStore so reads are tear-free, and the editor surface itself is an uncontrolled component: routing every keystroke through React state is the design mistake that makes these editors unusable at scale.

Presence is a separate, ephemeral channel — cursors and selections at ~20–30 updates per second, throttled, never persisted, and rendered in a layer that is deliberately outside the document's render path so a remote cursor move cannot re-render the document. Offline is where the CRDT earns its cost: local persistence in IndexedDB, an update queue, and automatic convergence on reconnect with no merge dialog. Large documents get virtualized rendering by block, with the CRDT holding the whole document but React rendering a window.

// The document lives outside React; React reads a snapshot without tearing.
const doc = new Y.Doc();
const provider = new WebsocketProvider(WS_URL, docId, doc);
new IndexeddbPersistence(docId, doc);              // offline, automatic

function useAwareness() {
  return useSyncExternalStore(
    (cb) => { provider.awareness.on('change', cb); return () => provider.awareness.off('change', cb); },
    () => provider.awareness.getStates(),          // cached snapshot, not a new object
  );
}

Trade-offs to name unprompted

  • CRDT versus OT. CRDTs converge without a central server and handle offline well; they cost memory and metadata growth, and rich-text CRDTs are subtle. OT is leaner on the wire but needs an authoritative server and is harder to get right offline.
  • Presence frequency versus cost. Sixty cursor updates a second per user is bandwidth and re-render pressure; throttle to ~20–30ms and interpolate.
  • Document size. Virtualization breaks find-in-page, print and screen-reader flow; be explicit about which you sacrifice and what you provide instead (an export, a search of your own).
  • Where React is not the answer. Saying plainly that the editing surface should not be React-controlled is the single strongest signal in this exercise.
  • Access control and history. Permissions must be enforced server-side per update; CRDT history is not an audit log and does not answer "who could see this".
  • Testing. Concurrency bugs need multi-client integration tests; unit tests will not find them.

Exercise 2 — A multi-tenant analytics dashboard

Prompt. Design the frontend for an analytics product: users build dashboards from a library of ~60 widget types, each backed by its own query; dashboards can hold 50+ widgets; queries take between 50ms and 30 seconds; tenants customise layout and theming. It must feel responsive on a mid-range laptop.

Clarifying questions to ask first

  • Are dashboards mostly viewed or mostly edited? The read path and the edit path have different architectures.
  • Is the data real-time, near-real-time, or historical with an acceptable staleness window?
  • Who writes widgets — us only, or tenants and third parties? Third-party widgets force isolation.
  • What is the SLA on the slow queries, and is a partial dashboard acceptable while they run?
  • How deep does theming go: tokens, or arbitrary CSS per tenant?
principalStrong solution outline and expected trade-offs

Shape of the answer

Widgets are independent units of loading, error and rendering: each is its own Suspense boundary inside its own error boundary, so one slow or broken widget degrades alone. Queries are batched where the backend allows and deduplicated by a shared cache key, because 50 widgets on one dashboard routinely ask for the same time range and filters — without dedupe you send the same query eight times. Only widgets near the viewport execute their queries; the rest render placeholders and load on intersection, with <Activity mode="hidden"> keeping scrolled-past widgets warm without paying their update cost.

Rendering: virtualize the widget grid, memoize each widget on its data and config, and keep the dashboard's own state (layout, global filters) out of the widget render path so changing one filter does not re-render 50 charts synchronously — filter changes go through a transition with a deferred value. Theming is tokens (CSS custom properties) per tenant, not arbitrary CSS, so it cannot break layout or leak between tenants. Third-party widgets, if allowed, go in iframes with a message contract; anything else means one tenant's widget can read another's DOM.

function Widget({ config }) {
  const inView = useInViewport(ref);
  return (
    <ErrorBoundary fallback={<WidgetError id={config.id} />}>
      <Suspense fallback={<WidgetSkeleton height={config.h} />}>
        <Activity mode={inView ? 'visible' : 'hidden'}>
          <WidgetBody config={config} />   {/* queries only when it has been in view */}
        </Activity>
      </Suspense>
    </ErrorBoundary>
  );
}

Trade-offs to name unprompted

  • Batching versus isolation. One batched request is efficient and couples widgets' failure and latency; per-widget requests are resilient and chatty. A hybrid — batch fast widgets, isolate slow ones — usually wins.
  • Lazy loading versus completeness. Viewport-based loading is fast and breaks "export the whole dashboard to PDF"; that needs a separate server-side render path.
  • Skeletons versus layout shift. Skeletons must reserve real dimensions, which means widget sizes must be known before data.
  • Client aggregation versus server aggregation. Aggregating 100k rows in the browser is the classic mistake here; push it to the query.
  • Iframes for third-party widgets. Isolation and security against communication overhead, styling limits and worse accessibility.
  • Deferred filter application. A filter change that re-renders 50 widgets must be a transition, or the dashboard freezes on every click.

Exercise 3 — A global e-commerce product page

Prompt. Design the product detail page for a global retailer: it must rank in search, load fast on a mid-range Android phone on 4G, show personalised pricing and stock for the signed-in customer, support 20 locales, and handle a traffic spike of 50× during a sale.

Clarifying questions to ask first

  • What exactly is personalised — price, stock, recommendations, all three? Each has a different cacheability.
  • How fresh must stock be? "In stock" that is five minutes stale may be acceptable; "2 left" is not.
  • Is the catalogue mostly static between releases, or continuously updated?
  • What is the current LCP and conversion baseline — what are we trying to beat?
  • Do we control the CDN and the origin, or is this on someone else's platform?
principalStrong solution outline and expected trade-offs

Shape of the answer

Split the page by cacheability, not by component. The product content — images, description, specifications, reviews, structured data for search engines — is identical for everyone in a locale and belongs in a statically generated, CDN-cached shell that survives the 50× spike without touching an origin. Price, stock and personalised recommendations are per-user and stream in behind Suspense boundaries. This is precisely what React 19.2's Partial Pre-rendering formalises: prerender the shell at build or revalidation time, resume the dynamic holes per request.

For search: the indexable content must be in the static HTML, with JSON-LD product structured data rendered server-side — anything that only appears after a client fetch is a risk. For the phone on 4G: a hero image with correct sizes, formats and priority, minimal client JavaScript (an RSC page ships almost none for the static parts), and the interactive islands — variant selector, add to cart, image gallery — as small Client Components. Stock and price get a short server-side cache with a stale-while-revalidate window, and the add-to-cart action re-validates authoritatively so a stale price is never charged. Locales are separate static builds or cached variants, never a client-side translation load that delays LCP.

// Static shell (CDN) + dynamic holes (origin), one page.
export default function ProductPage({ sku, locale }) {
  return (
    <>
      <ProductMedia sku={sku} />               {/* static, cached, LCP element */}
      <ProductCopy sku={sku} locale={locale} />{/* static, indexable */}
      <Suspense fallback={<PriceSkeleton />}>
        <PersonalisedPrice sku={sku} />        {/* dynamic, per user */}
      </Suspense>
      <Suspense fallback={<StockSkeleton />}>
        <LiveStock sku={sku} />                {/* dynamic, short TTL */}
      </Suspense>
    </>
  );
}

Trade-offs to name unprompted

  • Cacheability versus personalisation. Every personalised element you move into the shell costs you the CDN; every one you stream costs a layout slot and a skeleton.
  • Stock freshness versus load. A 30-second cache is a business decision about how often you are willing to say "in stock" wrongly.
  • SEO versus streaming. Content that arrives after the initial HTML is a bet on crawler behaviour; keep indexable content in the shell.
  • LCP discipline. The hero image is the LCP element: correct dimensions, modern format, fetch priority, and no JavaScript in its path.
  • Spike behaviour. Define the degraded mode in advance — hide "2 left" and show "in stock" rather than failing the page when the stock service is saturated.
  • Localisation. Twenty locales as build variants costs build time and CDN storage but keeps the runtime simple; a client-side i18n bundle costs LCP on every visit.
  • Add-to-cart correctness. The action must re-validate price and stock server-side; an optimistic add that fails at checkout is worse than a slower button.

22Night-before cheat sheet

The ten questions most likely to be asked, with the one-sentence answer to have ready. If you can say each of these cleanly and then add one sentence of "and the reason is…", you will pass the screening layer of almost any React loop.

  1. What triggers a re-render, and does it re-render children? A state or context change re-renders the component and, by default, its whole subtree — bailouts come from memo with equal props, an unchanged element passed as children, or the React Compiler's automatic memoization.
  2. Why is key important and why is the index a bad key? Keys identify which child is which across renders; index keys break identity when the list reorders, so state, focus and DOM stay with the position instead of the item — a correctness bug, not a performance one.
  3. What are the Rules of Hooks and why do they exist? Hooks must be called unconditionally at the top level, because state is stored positionally in an ordered list on the fiber and React matches by call order, not by name.
  4. When should you not use useEffect? For deriving data (compute during render), for resetting state on a prop change (use a key), and for user-event logic (put it in the handler) — effects are for synchronising with systems outside React.
  5. Why do effects run twice in development? StrictMode mounts, unmounts and remounts to prove your effect is idempotent; the fix is cleanup and cancellation, never a "has run" ref guard.
  6. What is the React Compiler and should you still write useMemo? A build-time plugin (stable 1.0, October 2025, React 17+) that memoizes automatically; write no new manual memoization, and remove existing ones only deliberately, since they can be load-bearing for effect timing.
  7. How do Server Components differ from SSR? SSR renders your components on the server and ships them to the client to hydrate; Server Components run only on the server and never enter the client bundle at all.
  8. Are Server Functions safe? No — a 'use server' function is a public HTTP endpoint, so authenticate, authorise and validate every call; CVE-2025-55182 (CVSS 10.0, December 2025) made that concrete for the whole ecosystem.
  9. What are transitions for? Marking an update non-urgent so React can keep input responsive and interrupt or abandon the slower render — useTransition when you own the setter, useDeferredValue when you only have the value.
  10. What is the latest React and what changed? 19.2.8 (21 July 2026) is the newest patch; 19.2 (1 October 2025) added <Activity>, useEffectEvent, cacheSignal, Performance Tracks and Partial Pre-rendering, and React has been owned by the Linux-Foundation-hosted React Foundation since 24 February 2026.
