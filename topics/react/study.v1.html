01 The rendering model

Docs: react.dev — Render and Commit

Everything else in React is downstream of one idea: a component is a pure function from props and state to a description of UI, and React — not you — decides when to call it and what to do with the result. Nothing you write touches the DOM. <Profile user={u} /> compiles (via the automatic JSX runtime, default since React 17) to jsx(Profile, { user: u }), which returns a plain frozen object: { type: Profile, props: { user: u }, key, ... }. That object is an element. It is a description, not an instance, and creating one is nearly free — which is why "this component re-renders" is not by itself a performance problem.

The useful mental model is a three-beat cycle: trigger → render → commit. A trigger is the initial mount or a state update. Render means React calls your component functions top-down from the update's root, building a new tree of elements and diffing it against the previous one. Commit means React applies the minimal set of DOM mutations, then runs layout effects synchronously and passive effects after paint. Only the commit phase touches the browser; the render phase must be pure, because React reserves the right to run it twice, throw it away, or pause it in the middle.

The data structure that makes this possible is the fiber. Since React 16 (2017), React keeps two trees: current (what is on screen) and work-in-progress (what is being built). Each fiber is a mutable node holding a component's type, props, its hook state as a linked list, and pointers to child/sibling/return. Because the work-in-progress tree is built incrementally as a linked list rather than by recursion, React can stop after any fiber, yield to the browser, and resume — this is the machinery that concurrent features (unit 06) actually use. When work finishes, React swaps the pointer: the WIP tree becomes current. That swap is atomic, which is why you never see a half-updated screen.

Reconciliation: the two heuristics

A general tree-diff is O(n³). React gets O(n) by assuming two things. First, a different element type means a different subtree: if type changes from <div> to <span>, or from Chart to Table, React unmounts the old subtree (destroying state and running cleanups) and mounts the new one. Second, keys give siblings a stable identity across renders. Within one list of children, React matches old to new by key; without a key it matches by index, so inserting at the front shifts every item's identity by one.

// The single most consequential line in React: the element's IDENTITY is

Interview trap — "the virtual DOM is fast"

It is not. Diffing is extra work that a hand-written imperative update would skip; React's actual claim is that it is fast enough and predictable, and that you buy a declarative programming model with it. Say that out loud and you separate yourself from candidates reciting marketing. The related trap: "re-render means DOM update". A re-render that produces an identical element tree produces zero DOM mutations. Profiling React means asking whether the render is expensive (large subtree, heavy computation) or whether the commit is (layout thrash, huge list), and they have completely different fixes.

Interview trap — index as key

"Index keys are fine if the list never reorders" is only half true: they are also broken when items are inserted or deleted anywhere but the end, and the symptom is not a crash but state landing on the wrong row — a checked checkbox following the index, an input keeping the previous row's draft. Because it only shows with uncontrolled state or effects, it survives code review and shows up as a bug report. The lead-level answer names the failure mode, not the rule.

Try it — make identity visible

1. Render a list of three rows, each an <input> with no value prop (uncontrolled), keyed by index. Type into the second one, then prepend a new item to the array. 2. Then switch the key to a stable id and repeat.

Expected outcome

With index keys your typed text stays visually attached to the position — it appears to jump to the newly-inserted first row, because React matched old index 0 to new index 0 and merely changed the props; the DOM node (and its uncontrolled value) was reused. With stable ids, React inserts a new fiber at the front and your text stays with its row. Bonus: put console.log in the row component and watch that the number of renders is identical in both cases — this is an identity bug, not a performance one.

3. Define a component inside another component's body (like Inner above) and add useState to it. Type, then trigger a parent re-render.

Solution sketch

State resets on every parent render, because Inner is a new function object each time, so type differs and React unmounts/remounts. This is the number-one cause of "my input loses focus while typing" in real codebases. The fix is to hoist the component to module scope and pass data as props. The React Compiler's lint rules flag component definitions in render.

Walk me through what happens between setState and a pixel changing.

The setter enqueues an update on the fiber's hook queue and schedules work at a priority derived from the calling context — a discrete event like a click gets synchronous priority, an update inside startTransition gets a lower one. React then renders: it walks from the root of the update down, calls the component functions, and builds a work-in-progress fiber tree, bailing out of subtrees whose props and context are referentially unchanged. It diffs that against the current tree to produce an effect list of DOM mutations. In the commit phase it applies those mutations synchronously, runs useLayoutEffect cleanups and setups before the browser paints, swaps the current pointer, and finally flushes useEffect after paint. The important nuance for a lead is that only commit is atomic and non-interruptible; render can be thrown away and restarted, which is exactly why render must be pure.

Why is the render phase required to be pure, concretely?

Because React may call your component more than once for a single visible update and may discard the result. Concurrent rendering can start a low-priority render, abandon it when a click arrives, and restart it later. StrictMode in development deliberately double-invokes component bodies, initialisers and effects to surface impurity. Offscreen rendering via <Activity mode="hidden"> renders subtrees that are never committed. So mutating a module-level variable, pushing to an array prop, writing to localStorage, or reading Date.now() and branching on it in render produces results that are non-deterministic and version-dependent. The practical rule I give teams: if removing the line would change something outside the returned tree, it belongs in an event handler or an effect.

What exactly does a key do, and what does it not do?

A key gives an element a stable identity among its siblings in one parent, so React can match the previous fiber to the new element even when the position changed. It is not a global id and does not need to be unique across the app — only within the sibling list. Two things people expect that keys do not do: they do not make a component "faster", and they do not preserve state when the element moves to a different parent or a different position in the tree structure. Changing a key is the supported way to reset a subtree's state, which is worth stating positively — <Form key={userId} /> is idiomatic, not a hack.

Why does React use a linked-list fiber tree instead of recursion?

Recursion puts the traversal state on the JavaScript call stack, which you cannot pause and resume. Fibers move that state into the heap: each node has child, sibling and return pointers, so React can perform one unit of work, check whether it has exceeded its time slice, hand control back to the browser, and pick up exactly where it left off. That is the enabling mechanism for time-slicing, transitions, Suspense retries and offscreen rendering. It also makes the double-buffered current/work-in-progress arrangement natural, which is what gives you an atomic commit — the user never sees a partially rendered tree.

Is the virtual DOM faster than direct DOM manipulation?

No, and I would not claim it. A hand-tuned imperative update will always beat diff-then-patch on a micro-benchmark, because the diff is pure overhead. What the virtual DOM buys is a declarative model where you describe the target state and never write update code, plus batching so that N state changes produce one DOM pass, plus a portable render target — the same reconciler drives React Native and custom renderers. Frameworks with fine-grained reactivity, like Solid or Svelte, genuinely do less work at update time; React's bet is that a predictable component model plus the compiler doing the memoization is a better trade for large teams. Being able to argue both sides is what the question is testing.

What is the automatic JSX runtime and why does it matter?

Before React 17, JSX compiled to React.createElement, which is why every file needed import React from 'react'. The automatic runtime, introduced in 17 and the default everywhere now, compiles to jsx/jsxs imported from react/jsx-runtime by the transform itself. Practical consequences: no more React import in every file, slightly smaller output, and — the one that matters for a migration — the jsx factory takes key out of the props object, which fixed a class of bugs where spreading props leaked a key. If you inherit a codebase where every file imports React and TypeScript is set to "jsx": "react", flipping to "react-jsx" is a cheap, low-risk modernisation.

When does React bail out of re-rendering a subtree?

Three cases. If a component returns the exact same element object it returned last time — which happens with children passed through from a parent that did not re-render — React reuses the previous fiber and skips the subtree entirely. If a component is wrapped in React.memo and its props are shallow-equal, React skips it. And if a state setter is called with a value that is Object.is-equal to the current state, React may skip the update, though it sometimes renders that component once more before bailing out, so you cannot rely on it for correctness. The first case is the one people forget, and it is the mechanism behind the "pass children as a prop" optimisation: <Slow>{expensiveTree}</Slow> does not re-render expensiveTree when Slow's own state changes.

What is the difference between an element, a component and a fiber?

A component is your function — source code. An element is the immutable description that calling JSX produces: a small object with type, props and key, created fresh on every render and thrown away. A fiber is React's internal, mutable, persistent work unit — one per element position in the committed tree — and it is where hook state, the effect list and the child/sibling pointers live. The distinction matters in interviews because "state lives in the component" is wrong: state lives on the fiber, which is why it survives re-renders but dies when the element's type or key changes, and why two usages of the same component have completely independent state.

How is ReactDOM.render different from createRoot, and why was the old one removed?

ReactDOM.render created a legacy-mode root where all updates were synchronous and only React event handlers batched. createRoot (React 18) creates a concurrent root: automatic batching everywhere including promises, timeouts and native handlers, plus access to transitions, useDeferredValue, streaming SSR and Suspense on the client. React 19 deleted the legacy API entirely along with hydrate, unmountComponentAtNode and findDOMNode, so an app that never migrated cannot install 19 at all. In a migration I would land the createRoot switch on 18 first, under a flag if the app is large, because that is where behavioural differences surface — most commonly code that relied on an unbatched setState inside a setTimeout flushing immediately.

A colleague says "this component re-renders too often" in code review. What do you ask?

First: what is the observable symptom? If there is no measured jank, a re-render of a cheap subtree is a non-issue and memoizing it adds allocation and cognitive cost for nothing. Second: is the cost in render or in commit? The React DevTools Profiler and, since 19.2, the Chrome DevTools "React" performance tracks show the actual timings and let you distinguish a slow component body from a huge commit. Third: is the real problem identity churn — a new object or arrow function created in render defeating a memo downstream, or a context value recreated every render? And fourth, in a codebase on React 19: is the React Compiler enabled, because if it is, hand-written useMemo is usually the wrong answer and the right one is to fix the rule violation stopping the compiler from optimising that file.

02 State and the update cycle

Docs: react.dev — Queueing a series of state updates

State is the part of a fiber that survives a render. useState returns a pair whose setter does not assign anything: it enqueues. The variable you are holding is a snapshot of this render, captured in the closure, and it will never change value — a render is a photograph, not a live view. This is the single most useful sentence to internalise, because almost every "why is my state stale?" bug follows from ignoring it.

Concretely: setCount(count + 1) three times in one handler produces count + 1, not count + 3, because all three read the same snapshot. setCount(c => c + 1) three times produces count + 3, because React stores the functions in a queue and applies them in order at render time against the accumulated value. Use the updater form whenever the next value depends on the previous one; use the direct form when it does not. This is not a style preference — under concurrent rendering, updates from different priorities can interleave, and only the updater form is correct.

Batching, and what changed in 18

React 17 and earlier batched only inside React's own synthetic event handlers. Anything asynchronous — a setTimeout, a .then(), a native addEventListener — flushed each setter as its own synchronous render. React 18's automatic batching (which you only get through createRoot) batches all of them: multiple setters in the same task produce one render. The escape hatch is flushSync from react-dom, and you should be able to name a legitimate use — you need the DOM updated before the next line, typically to measure it or to scroll to a newly-added node.

import { flushSync } from 'react-dom';

function List() {
  const [items, setItems] = useState(initial);
  const endRef = useRef(null);

  function add(item) {
    // Without flushSync the DOM node does not exist yet when we scroll.
    flushSync(() => setItems(prev => [...prev, item]));
    endRef.current.scrollIntoView({ behavior: 'smooth' });
  }
  // flushSync forces a synchronous re-render + commit. It defeats batching and
  // concurrency for that update — correct here, a performance bug in a loop.
}

Immutability is a protocol, not a preference

React compares the previous and next state with Object.is. Mutating an object and passing the same reference back means React sees no change and bails out — or worse, renders for an unrelated reason and shows the mutated data, so the bug is intermittent. React 19 ships no built-in immutable helpers; the modern options are spread syntax for shallow updates, Immer (still the pragmatic choice for deep nested state, and what Redux Toolkit uses internally), or — increasingly — restructuring so the nesting does not exist. Note that Array.prototype.toSorted, toReversed, toSpliced and with are baseline-available now and are the right answer for list state, replacing the [...arr].sort() dance.

// Reducer: the right shape once transitions between states matter more than
// the values themselves. useReducer's dispatch is referentially stable forever,
// which is why it composes better with memo and context than a pile of setters.
function reducer(state, action) {
  switch (action.type) {
    case 'edit':   return { ...state, draft: action.text, dirty: true };
    case 'save':   return { ...state, saved: state.draft, dirty: false };
    case 'reset':  return init(action.payload);   // lazy re-init
    default:       throw new Error('unknown action: ' + action.type);

}

Derived state: the thing you should not store

If a value can be computed from props and other state, compute it during render. Storing it means keeping two sources of truth in sync, and the classic sync mechanism — an effect that calls a setter — costs an extra render pass and a flash of stale UI. React 19's guidance is explicit: adjust state during render if you must react to a prop change, using the "previous props in state" pattern, and prefer the key-reset trick when you want to discard everything.

Interview trap — "state updates are asynchronous"

Half-right, and the half that is wrong matters. They are not asynchronous in the promise sense; they are deferred to the next render. There is no await that makes the variable update, and there is no second-argument callback like class setState had — that API was never ported to hooks, and the answer for "do X after the update" is useEffect keyed on the value, or flushSync if you genuinely need it before the next statement. Candidates who say "asynchronous" and stop get the follow-up "so can I await it?" and fall over.

Gotcha — the setter identity you can rely on

useState's setter and useReducer's dispatch are guaranteed stable for the lifetime of the component, so they never need to be in a dependency array and never need useCallback. The values and handlers you build around them are not. This asymmetry is why "lift the reducer, pass dispatch through context" is a genuinely good architecture (unit 05): the dispatch context never changes, so consumers of it never re-render.

Try it — break batching on purpose

1. Write a handler that calls setA(a + 1) and setB(b + 1) and logs a render counter. Call the same pair from a setTimeout. Count renders on React 18/19 with createRoot. 2. Then write a counter with three setCount(count + 1) calls, and again with three updater calls.

Expected outcome

One render in both cases — automatic batching does not care that you were in a timeout. If you rebuild the same page with the legacy ReactDOM.render root (only possible on 18, since 19 removed it) you get two renders from the timeout, which is exactly the regression teams hit when they migrate: code that relied on an intermediate DOM state between the two setters. For the counter, the direct form yields +1 and the updater form +3; make sure you can explain that without hedging.

3. Mutate an array in state (items.push(x); setItems(items)) and observe.

Solution sketch

Nothing renders, because Object.is(items, items) is true. Now add an unrelated setOther in the same handler: the list suddenly appears, correct but one render late. That intermittency is the reason mutation bugs are expensive — they do not fail loudly, they fail sometimes. toSpliced/with/spread, or Immer, are the fixes.

Why does calling a setter three times with count + 1 only increment once?

Because count is a constant captured in this render's closure — all three calls read the same snapshot and enqueue "replace with 1". React applies the queue at render time and the last write wins. The updater form setCount(c => c + 1) enqueues a function instead of a value, and React applies each one to the accumulated result, so you get +3. Beyond the counter puzzle, the real reason to reach for the updater form is correctness under concurrency: a transition render can be interrupted and replayed, and only a pure function of the previous state is safe to replay.

What is automatic batching and what broke when it shipped?

React 18 batches every state update in the same task into a single render, regardless of where the update came from — previously only React event handlers batched, so promises, timeouts and native listeners each triggered their own synchronous render. You only get it with createRoot; a legacy root kept old semantics, which is how the team shipped it without a major version. What broke was code that depended on the DOM being updated between two setters — measuring after the first, or reading a ref, or third-party integrations that mutated the DOM in between. The escape hatch is flushSync, and treating the migration as "find the places that need flushSync" is the right framing for a team.

When would you legitimately use flushSync?

When you need the DOM committed before the very next statement runs. The canonical cases are measuring a node you just added, scrolling a newly-inserted element into view, and integrating with a non-React library or browser API that must observe the updated DOM synchronously — printing, focus management inside a native dialog, or a third-party grid. It is a real escape hatch, not a code smell, but it opts that update out of batching and concurrency, so it must not appear inside a loop or a scroll handler. In review I ask for a one-line comment explaining what has to be measured, because a flushSync without a reason is always a cargo-culted fix.

How do you decide between useState and useReducer?

The heuristic I use is whether the interesting thing is the values or the transitions. Independent values that change for independent reasons — a text field, a toggle — are fine as separate useStates. Once several fields must change together, or the same event means different things depending on current state, a reducer makes the state machine explicit, testable as a pure function, and reviewable in one place. Two secondary arguments matter at scale: dispatch is referentially stable so it composes cleanly with context and memo, and a reducer gives you a natural log of actions for debugging. The counter-argument is verbosity, so I would not push a reducer on a two-field form.

Is it ever right to store derived state?

Almost never, with two honest exceptions. If deriving is genuinely expensive and profiling proves it, memoize it in render with useMemo — that is still not "storing state", it is caching a computation. And if a value must be captured at a moment in time rather than recomputed — the price at the instant the user clicked buy, the search term that produced the currently-displayed results — then it is real state, not derived, and storing it is correct. Everything else is a synchronisation bug waiting to happen: the effect-plus-setter pattern renders twice, briefly shows stale data, and gets out of sync the first time someone adds a third way to change the source.

How do you reset a component's state when a prop changes?

If everything should reset, change the key: <ProfileForm key={userId} userId={userId} /> makes React unmount the old fiber and mount a fresh one, which is explicit, cheap and impossible to get subtly wrong. If only one field should adjust, keep the previous prop in state and compare during render — if (userId !== prevUserId) { setPrevUserId(userId); setSelection(null); } — which React supports specifically because it re-renders the component immediately without committing the intermediate output, so there is no flash. What I would flag in review is the third option, an effect that watches the prop and calls setters, because it commits the stale UI first and then corrects it.

Why does useState take a function for lazy initialisation, and when does it matter?

The argument to useState is evaluated on every render, even though React only uses it on the first one. If it is a literal or a cheap expression that is irrelevant; if it is JSON.parse(localStorage.getItem(...)) or building a lookup table over a thousand rows, you are paying that on every keystroke. Passing a function defers it to mount only. The classic mistake is passing the result of a function that looks like an initialiser — useState(createStore()) instantiates a store every render and throws all but the first away, which also means side effects in that constructor fire repeatedly. useReducer has the same escape via its third argument.

What does "state lives in the tree position, not the component" mean in practice?

React stores hook state on the fiber, and a fiber is identified by its type and position among siblings, not by the component's name. So rendering {show ? <Counter /> : <Counter />} keeps the state — same type, same position — while {show ? <div><Counter/></div> : <Counter/>} destroys it, because the structure changed. Two sibling <Counter />s have independent state, and conditionally rendering one of two branches at the same position silently shares it. In interviews this is usually asked as a puzzle; in real code it shows up as "state leaked between tabs" when someone renders the same panel component for every tab at the same position without a key.

Where does state belong — component, lifted, context, or a store?

My default ladder is: keep it local until two components need it, then lift it to the nearest common parent, then — if the prop drilling is genuinely deep and the value changes rarely — put it in context, and only reach for an external store when the state is shared widely, changes frequently, or must live outside React (a websocket connection, an undo stack, a cache). The nuance for React 19 is that server state should usually not be in client state at all: TanStack Query, a router loader, or an RSC fetch owns it, and the client store shrinks to genuine UI state, which is often small enough that context plus a reducer is sufficient. I would push back on a proposal to put everything in Redux by asking which of those four categories each slice actually is.

What replaced the second-argument callback of class setState?

Nothing directly, and that is deliberate. The options are: run the code in an effect that depends on the new value, if what you want is "after this state is on screen"; put it in the event handler after flushSync, if you need it before the next statement; or, most often, notice that you did not need a callback at all — you wanted a derived value, which belongs in render. React's position is that the callback encouraged imperative sequencing that breaks under concurrency, since there is no single "after the update" moment when an update can be interrupted, replayed at a different priority, or batched with others. If someone is porting a class component and reaches for a callback, that is a good prompt to look at what they are actually sequencing.

03 Hooks: rules and identity

Docs: react.dev — Rules of Hooks

A hook is a way for a function component to reach into the fiber that is rendering it. The implementation explains every rule: React keeps a linked list of hook records on the fiber and a cursor that advances by one on each hook call. The list has no names — useState does not know it is called "count". Position is identity. Call hooks in a different order and the cursor hands you the wrong slot; call fewer than last time and the tail is orphaned, which is why React throws "Rendered fewer hooks than expected" rather than silently corrupting state.

Hence the two rules: only call hooks at the top level (never inside conditions, loops, nested functions or after an early return) and only call them from React function components or custom hooks. eslint-plugin-react-hooks enforces both; since v6 (shipped alongside React 19.2, October 2025) it defaults to flat config, bundles the React Compiler's own diagnostics as lint rules, and — the change people notice — correctly excludes useEffectEvent functions from dependency arrays instead of warning about them. The legacy eslintrc setup is still available as recommended-legacy.

Closures are the other half of the model

Every render creates a fresh set of closures over that render's props and state. A callback registered in a render sees that render's values forever. This is a feature — it makes renders reasonable in isolation — but it produces the "stale closure" bug whenever a callback outlives its render: a setInterval registered once, a subscription with an empty dependency array, a debounced handler stored in a ref.

// Stale closure — the classic. count is frozen at 0 forever.
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []);                        // lies about its dependencies

// Fix 1 — updater form: no dependency on count at all.
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);
  return () => clearInterval(id);

Custom hooks: composition, not sharing

A custom hook is any function whose name starts with use and which calls other hooks. It shares logic, never state: two components calling useFilter() get two independent states, because each call runs against its own fiber. That single sentence answers a surprising number of interview questions. The naming convention is load-bearing — the linter and the compiler use it to decide what to enforce.

// Subscribing to an external store — the correct primitive since React 18.
// Do NOT hand-roll this with useState + useEffect: you get tearing under
// concurrent rendering, because different components can read the store at
// different points in one render pass.

  return useSyncExternalStore(

        window.removeEventListener('offline', cb);
      };
    },
    () => navigator.onLine,                    // getSnapshot (client)
    () => true                                 // getServerSnapshot (SSR)
  );
}

Interview trap — "use is a hook, so it follows the rules of hooks"

use is the deliberate exception and interviewers love it. It can be called conditionally and inside loops, because it does not allocate a hook slot — it either reads context by walking the tree, or suspends by throwing the promise to the nearest boundary. What it still cannot do is be called from an event handler, a try/catch, or outside a component. The reason it can be conditional is that resuming a suspended render replays the component from the top, so there is no positional state to keep aligned. If you say "you can't call it conditionally" you have just told the interviewer you have not used React 19.

Gotcha — the dependency array is not a cache key

People treat [] as "run once" and then fight the consequences. The array is a declaration that these are all the reactive values this code reads; if it is wrong, the code is wrong, and the linter is right. The three legitimate ways out are: move the value out of the component if it never changes, move it into the setter as an updater, or — since 19.2 — wrap the non-reactive part in useEffectEvent. Suppressing the rule with a comment is the pattern I flag hardest in review, because the resulting bug is a stale value that only appears on the second visit to a screen.

Solution sketch

The updater form is best here because the interval genuinely does not care about count. Adding count to the deps works but tears down and recreates the timer every second, which drifts and would drop a websocket if this were a subscription. useEffectEvent is the right tool when the callback reads several values that must be current but must not re-trigger the effect — a logging call, a toast with the current theme, an analytics payload. Being able to say which fix fits which shape is the lead-level answer.

Why can't hooks be called conditionally? Explain the mechanism, not the rule.

React stores hook state as an ordered linked list on the fiber and walks it with a cursor that advances once per hook call, with no names or keys involved. On the second render the cursor must land on the same slot for the same useState call, so the sequence of calls has to be identical. A conditional hook makes render N and render N+1 disagree, so the third hook reads the second's slot — you would get someone else's state, silently. React detects the count mismatch and throws instead. The design trade-off is worth naming: the alternative was named or keyed hooks, which the team rejected as too verbose for the ergonomic win.

What is a stale closure and how do you recognise one in review?

A callback created in one render captures that render's props and state, and if the callback outlives the render — stored in a ref, registered with setInterval, attached in an effect with an incomplete dependency array — it keeps reading values that are now old. The tell in review is an empty or short dependency array on an effect whose body references props or state, especially with an eslint-disable comment above it. The symptom in production is a value that is correct on first interaction and stuck thereafter, or a subscription that reports the state of a screen the user has already left. The fixes are the updater form, honest dependencies, or useEffectEvent.

When does a custom hook share state between components, and when doesn't it?

Never — a custom hook shares logic, not state. Each call site runs the hook body against its own fiber and gets its own hook slots, so two components using useCounter() have two independent counters. If you actually want shared state, you need a shared source: context, an external store read through useSyncExternalStore, a router loader, or a server cache. This misunderstanding is common enough that I ask it in interviews as a design question — "we want the sidebar and the header to show the same filter, someone proposes a custom hook" — because the right answer is to name the source-of-truth problem, not to recite the rule.

What problem does useSyncExternalStore solve that useState + useEffect does not?

Tearing. Under concurrent rendering React can start a render, yield to the browser, and finish later; if an external store changes in that gap, components rendered before and after the yield read different values and the committed screen is internally inconsistent. useSyncExternalStore gives React a getSnapshot it can call and re-check, so React detects the change and restarts the render rather than committing a torn tree. It also gives you a getServerSnapshot for SSR so hydration does not mismatch. Practically, app authors rarely call it directly — Redux, Zustand and Jotai all use it internally — but knowing why it exists is exactly the depth an interviewer is probing for when they ask "what changed for state libraries in React 18".

How is use different from every other hook?

It is not positional. use(promise) and use(Context) can appear inside an if or a loop, because they claim no hook slot: reading context walks up the fiber tree, and reading a promise either returns its resolved value or throws it to the nearest Suspense boundary, after which React replays the component from the top. That replay is why conditional calls are safe. The restrictions that remain are that it must run during render — never in an event handler or a try block — and that the promise must come from somewhere cache-stable, because creating a promise inside render and passing it to use creates a new one on every attempt and loops forever. In client components that means the promise comes from a cache, a framework loader, or a server component prop.

What is useEffectEvent and what does it replace?

Shipped stable in React 19.2, it lets you extract the non-reactive part of an effect into a function that always sees the latest props and state but never appears in a dependency array. The canonical case is an effect that must re-run for one value (reconnect when roomId changes) but reads others that should not re-trigger it (the current theme, the analytics context, a callback prop). Before it, the workarounds were a ref updated in a layout effect — the "latest ref" pattern you will find all over older codebases — or an eslint-disable and a stale closure. It replaces both. The constraints are that effect events can only be called from inside effects in the same component and cannot be passed to other components, which is what keeps the reactivity story honest.

What changed in eslint-plugin-react-hooks v6?

Three things worth naming. Flat config is the default export now, with the old eslintrc shape moved to recommended-legacy, so an upgrade is a config change, not just a version bump. The plugin's recommended preset now includes the React Compiler's diagnostics as lint rules, which means it flags impure renders, mutations of props and state, and component definitions inside render — rules that used to be tribal knowledge are now automated. And useEffectEvent is understood, so it stops warning about effect events in dependency arrays. For a team, the second point is the real value: it turns "why is the compiler skipping this file?" into a lint error at the point of the mistake.

Why are useLayoutEffect and useInsertionEffect separate hooks?

They are the same subscription model at three different points in the commit. useInsertionEffect runs before React mutates the DOM and exists so CSS-in-JS libraries can inject style rules without forcing a layout recalculation mid-commit; it cannot read layout or update state and is not meant for app code. useLayoutEffect runs after mutation but before the browser paints, synchronously, which is what you need to measure a node and adjust position — a tooltip that must not flicker into the wrong place. useEffect runs after paint and is the default, because anything you do there cannot block the frame. The interview follow-up is the SSR warning: useLayoutEffect does nothing on the server and warns, so measurement code needs a guard or a useEffect fallback.

How do you test a custom hook?

Prefer testing the component that uses it, because that is what ships and it keeps the test honest about rendering behaviour. When the hook is genuinely a reusable unit with meaningful logic — a state machine, a paging cursor, a retry policy — use renderHook from @testing-library/react and drive it through act, asserting on result.current. Note that React 19 deprecated react-test-renderer and removed react-dom/test-utils's act in favour of act exported from react itself, so older test suites need a mechanical update. The thing I would push back on is a hook with a hundred lines of pure logic tested only through hooks: extract the pure function and unit-test that directly.

A junior wraps every function in useCallback "for performance". What do you say?

That useCallback is not free — it allocates a dependency array, runs a comparison every render, and adds a line of noise — and it only pays off when the identity actually feeds something that compares it: a memo'd child, a dependency array, or an external subscription. Wrapping a handler passed to a plain <button> is strictly a loss. Then I would ask the more useful question: is the React Compiler enabled? On React 19 with the compiler at 1.0, memoization is generated automatically and correctly, and hand-written useCallback becomes something you delete rather than add — the team's energy is better spent on making components pure enough for the compiler to optimise them. If the compiler is not an option, the rule is "memoize at the boundary you measured, not everywhere".

04 Effects as synchronization

Docs: react.dev — Synchronizing with Effects · You Might Not Need an Effect

useEffect is the most misused hook in React, and the reason is a naming accident: people read it as "lifecycle" and translate componentDidMount to useEffect(fn, []). The correct model is synchronization. An effect says: given these reactive values, this external system should be in this state. React runs the setup when the values change and the cleanup when they change or the component unmounts. There is no mount and no unmount in the model — only "the dependencies changed, so re-synchronize". Once you think this way, the dependency array stops being a puzzle: it is the list of values the synchronization depends on, and the linter computes it for you.

The corollary is the more important half: most effects should not exist. An effect is for reaching outside React — a websocket, a browser API, an analytics SDK, a non-React widget, a subscription. It is not for transforming data for rendering (compute in render), not for handling user events (that is the handler's job), not for resetting state on a prop change (use a key), and not for fetching data in a modern app (a framework loader, a query library, or a server component owns that). The React docs page "You Might Not Need an Effect" exists because effect misuse was the dominant source of React bugs, and interviewers at lead level ask about it directly.

The cleanup is not optional

function ChatRoom({ roomId }) {
  useEffect(() => {
    const conn = createConnection(serverUrl, roomId);
    conn.connect();
    return () => conn.disconnect();     // cleanup: symmetric with setup
  }, [roomId]);                          // roomId changes -> disconnect, reconnect
}

// Race condition — the reason "ignore" flags exist. Without cleanup, a slow
// response for user 1 can land AFTER a fast one for user 2 and overwrite it.
useEffect(() => {
  let ignore = false;
  fetchUser(userId).then(u => { if (!ignore) setUser(u); });
  return () => { ignore = true; };
}, [userId]);

// Better in 2026: AbortController, so the request is actually cancelled.
useEffect(() => {
  const ac = new AbortController();
  fetch(`/api/users/${userId}`, { signal: ac.signal })
    .then(r => r.json()).then(setUser)
    .catch(e => { if (e.name !== 'AbortError') setError(e); });
  return () => ac.abort();
}, [userId]);

StrictMode double-invocation is a test, not a bug

Since React 18, <StrictMode> in development mounts, unmounts and remounts every component once — running setup, cleanup, setup. It is checking that your effect is resilient to being re-run, which is exactly what Fast Refresh, <Activity> and future offscreen features require. If the double-invocation breaks your code, the code has a real bug: a missing cleanup, a subscription that leaks, an analytics event fired without idempotency, a fetch without cancellation. The wrong fix — a useRef guard so the effect only runs once — is the single most common anti-pattern in React codebases written after 2022, and interviewers use it as a filter.

Gotcha — object and function dependencies

An effect that depends on an object or function created in render re-runs every render, because the identity is new every time. Wrapping it in useMemo/useCallback works but pushes the problem up a level. The better moves, in order: move the object inside the effect so it is not a dependency; depend on the primitive fields ([options.roomId, options.token]) instead of the object; or move the creation out of the component if it is constant. Under the React Compiler this class of bug largely disappears, because the compiler memoizes the object for you — one of the underrated arguments for enabling it.

Without the flag the screen settles on whichever request happened to finish last, not the one you asked for — the bug that looks like "sometimes the wrong profile loads". With the flag the stale response is discarded. Then note what the flag does not do: the request still runs and still costs bandwidth, so AbortController is strictly better, and neither of them dedupes or caches — which is the argument for a query library rather than hand-rolled fetching.

Explain useEffect without using the word "lifecycle".

An effect declares that some external system must be kept in sync with a set of reactive values. React runs the setup after commit, and before re-running it — or before unmounting — it runs the cleanup you returned, so the external system is torn down and rebuilt exactly when the values it depends on change. Mount and unmount are just the first setup and the last cleanup; nothing in the model is special about them. Framing it this way immediately answers the follow-ups: the dependency array is the sync key, the cleanup must undo the setup symmetrically, and an effect with no external system in it probably should not exist.

Why does React run effects twice in development, and what is the right response?

StrictMode deliberately mounts, unmounts and remounts each component in development to prove your effects are re-runnable. React needs that guarantee because Fast Refresh remounts, because navigating back to a cached screen remounts, and because <Activity> and future offscreen features unmount effects while keeping state. If double-invoking breaks something, the correct response is to add the missing cleanup or make the operation idempotent — never a ref guard, which hides the signal and does not survive a real remount. In production the effect runs once, so nobody is "paying" for StrictMode; you are paying for the bugs it finds.

What are the specific ways to fix an effect that fires too often?

In order of preference: remove the dependency by moving the value inside the effect or replacing a read with a state updater function; depend on primitives instead of the object or function that wraps them; extract the non-reactive part into useEffectEvent, stable since 19.2, so the effect stays reactive to the things that should re-trigger it and blind to the things that should not; and only then memoize the dependency with useMemo/useCallback, or let the React Compiler do it. What I will not accept is removing the dependency from the array with a lint suppression, because that does not make the effect fire less — it makes it fire with stale values, which is a worse bug that shows up later.

How do you handle a race condition in data fetching inside an effect?

The minimum is an ignore flag set in the cleanup so a late response for a previous key is discarded — without it, responses can land out of order and the screen shows data for a selection the user has already changed. The better version uses AbortController and passes the signal to fetch, so the request is actually cancelled and you stop paying for it, with a catch that ignores AbortError. But at lead level the real answer is that hand-rolled fetching in effects also lacks caching, deduplication, retry, focus revalidation and a loading-state protocol, so on a new codebase I would put server data behind a router loader, a server component, or TanStack Query, and reserve effects for genuinely imperative subscriptions.

Give three concrete cases where an effect is the wrong tool.

First, derived data: an effect that computes a filtered list into state renders twice and can show stale results between them, so compute it during render. Second, event responses: sending analytics or posting a form in an effect that watches a flag hides the causality and fires again on remount — the logic belongs in the handler that the user actually triggered. Third, notifying a parent: useEffect(() => onChange(value), [value]) makes the parent update one render late and creates ping-pong loops when the parent feeds the value back down; call onChange in the same handler that sets the state. A fourth that I see constantly is resetting state when a prop changes, which the key prop does correctly and atomically.

What is the difference between useEffect and useLayoutEffect, and how do you choose?

useLayoutEffect runs synchronously after React mutates the DOM but before the browser paints; useEffect runs after paint. So layout effects can measure and adjust without the user seeing an intermediate frame — a tooltip that must flip above the trigger when there is no room below is the standard example — but they block painting, so an expensive one directly hurts INP. The default is useEffect; reach for the layout variant only when a visible flicker is the alternative. The trap is SSR: useLayoutEffect does not run on the server and logs a warning, so measurement code needs to tolerate the first paint being unmeasured, or be moved into a client-only boundary.

How would you audit a legacy codebase for effect misuse?

I would start by counting effects with an empty dependency array and effects with an eslint-disable, because those two buckets contain most of the bugs. Then I would classify every effect against one question: what external system is it synchronizing with? Anything that answers "none" is either derived state, an event response, or a parent notification, and each has a mechanical fix. Next I would look for missing cleanups on subscriptions and timers, and for fetch effects without cancellation. Finally I would enable StrictMode in development if it is off — usually the largest single source of signal — and turn on the compiler lint rules, which flag mutations and impure renders that make effects behave unpredictably. I would sequence it screen by screen with tests, not as a big-bang refactor.

What does useEffectEvent not let you do, and why?

You cannot call an effect event during render, cannot pass it to another component or hook, and cannot call it from an event handler — only from effects in the same component. The restriction exists because an effect event is defined to always see the latest committed props and state, which is only well-defined at the moment an effect runs; letting it escape would make "latest" ambiguous and would let people build a general non-reactive callback that silently breaks the compiler's and the linter's reasoning about reactivity. The practical consequence is that if you find yourself wanting to pass one down, the design is wrong — usually the child should receive the data it needs, or the effect should live where the event does.

Someone proposes fetching data in useEffect for a new feature. What is your position?

I would ask what owns the data. If the app is on a framework — Next.js, React Router 7 in framework mode, TanStack Start — then loaders or server components already give you request deduplication, streaming, caching and a story for errors and pending states, and hand-rolled effects reintroduce waterfalls plus the race conditions we just discussed. If it is a plain SPA, a query library gives most of that. Effects remain right for imperative subscriptions and for the rare one-off where a dependency is not justified. I would also point at the waterfall risk specifically: an effect can only start fetching after the component renders, so nested fetching components serialise round trips, which is the performance problem that Suspense and server components were designed to remove.

How do you make an effect that must run only once per application, not once per mount?

Take it out of React. Initialising an SDK, registering a service worker, or setting up a global error handler is module-scope work: put it at the top of the module or in the app entry file, where it runs once per page load regardless of how many times components mount. If it must be lazy, use a module-level flag in that module — not a ref, because a ref is per-fiber and a remount creates a new one. Inside a component the honest question is whether "once" is really what you want: a remount usually means the user came back to a screen, and most setup genuinely should re-run then. Reserve the module-scope escape for things that are global by nature, and make sure they are safe under SSR, where module code runs on the server too.

05 Context and state architecture

Docs: react.dev — Passing Data Deeply with Context · createContext

Context is a mechanism for implicit prop passing down the tree, and it is worth being precise: it is not a state manager, it has no selectors, and it has no built-in equality bail-out. A provider publishes one value; every consumer below re-renders whenever that value's identity changes, full stop. Understanding that one sentence explains all of context's performance folklore and most of the wrong answers people give about it.

React 19 made two ergonomic changes. <Context> can be rendered directly as the provider — <ThemeContext value={theme}> instead of <ThemeContext.Provider value={theme}>, with .Provider deprecated. And use(Context) reads a context but, unlike useContext, may be called conditionally, which finally makes "read this context only in this branch" expressible without splitting the component.

Composition beats context more often than people think

Expected outcome

Solution sketch

They still re-render. memo compares props; context is not a prop, and a context change bypasses the bail-out entirely. This surprises people and is a great interview question, because the follow-up — "so how do you stop it?" — has real answers: split the context, push the consumption down to the smallest component, or use a store with selectors backed by useSyncExternalStore.

What exactly triggers a re-render of a context consumer?

A change in the provider's value by Object.is comparison. When that happens React walks the tree and schedules an update on every fiber that reads that context, regardless of whether the part of the value it reads changed, and regardless of React.memo — memo compares props, and context is not a prop, so it cannot stop the propagation. The two practical consequences are that an inline object or array as the value re-renders everything on every parent render, and that a coarse-grained context is a performance liability once it holds anything that updates frequently. The fixes are memoizing or splitting the value, moving consumption as low in the tree as possible, or using an external store with selector-level subscriptions.

How do you design context for an app that has one big "app state"?

I would not have one big app state. First I would separate server data out — that belongs in a query cache or a loader, not in a context. Then I would split what remains by change frequency and by consumer set: a session/auth context that changes on login, a theme/locale context that changes almost never, and any hot UI state kept local or in a store with selectors. Where a reducer is involved, I split state and dispatch into two contexts so the many components that only dispatch never re-render. And I export hooks rather than raw contexts, so the provider shape stays private, missing providers throw a useful error, and I can swap the implementation for a store later without touching consumers.

What changed about context in React 19?

You render the context object itself as the provider — <ThemeContext value={t}> — and Context.Provider is deprecated, with a codemod available; it will be removed in a future major. Context.Consumer, the render-prop form, is also deprecated. And use(Context) joined useContext as a way to read, with the difference that use may be called conditionally and inside loops, because it does not occupy a hook slot. None of this changes the semantics of propagation or the performance characteristics — it is ergonomics. The thing worth flagging in a migration is that .Provider deprecation touches every provider in the codebase, so it is a codemod-and-one-PR job rather than something to do incrementally.

Why can't server components use context?

Context is a runtime tree feature: a provider pushes a value onto a stack during render and consumers read it by walking up their fiber. Server components are rendered on the server, ahead of and separately from the client tree, serialised to a stream, and never re-rendered on the client, so there is no shared runtime tree for a client provider to publish into. The practical rule is that providers are client components ('use client') placed high in the tree — usually in the root layout — and server components pass data down as props instead. When people hit this in a migration, the answer is almost always to pass the value explicitly, or to move the small piece that needs the context into a client component.

When is prop drilling actually fine?

Two or three levels, along a path where the intermediate components are genuinely related to the data, is fine and often clearer than the alternative — the data flow is visible in the code and greppable. Drilling becomes a problem when the intermediate components have no interest in the value, when the path is long enough that a change touches many files, or when the same prop is drilled to many leaves. Even then my first move is composition: pass children or an element prop so the component that owns the data renders the one that needs it, which removes the drilling without adding indirection. Context is the answer for genuinely ambient values — theme, locale, current user, feature flags — where every part of the tree may need it.

Compare context+reducer with Zustand for a mid-sized app.

Context plus reducer has zero dependencies, is obvious to any React developer, and works well when the state is small or slow-moving; its ceiling is subscription granularity, since any change re-renders every consumer and you fix that by splitting providers, which becomes its own boilerplate. Zustand gives you selector-based subscriptions on top of useSyncExternalStore, so a component re-renders only when the slice it selected changes, requires no provider, and can be read outside React — useful in event handlers and non-React code. The trade is a dependency and a store that is easy to turn into a junk drawer. My rule: start with context and reducer, and move to a store the moment profiling shows context-driven re-renders or the moment you want to read state outside the tree.

How does React find the right provider, and what is the cost of deep nesting?

Reading a context walks up the fiber's return chain to the nearest provider for that context object, so lookup is O(depth) but with a very small constant, and React maintains dependency lists so that on a value change it can find consumers without re-rendering the whole tree. Deep provider nesting is therefore cheap to read; what costs is having many providers whose values change, because each change schedules work on its consumers. The pattern I would flag is the "provider pyramid" in the app root — ten nested providers — not for performance but for testability: every test now has to reconstruct that pyramid, which is an argument for a single composed <AppProviders> component exported for tests.

Where should server data live in a 2026 React app?

Not in client state. Server data has properties client state does not — it is a cache of something you do not own, it can be stale, it needs deduplication, revalidation and retry — and modelling it as useState plus effects means reimplementing all of that badly. The options are server components fetching directly (unit 07), a router loader in React Router 7 or TanStack Router, or a query library like TanStack Query or RTK Query. What is left for client state is genuine UI state: which modal is open, the current form draft, a selection, an optimistic overlay. This split is the single biggest architectural shift of the last few years and it is why "which state manager" is a much less interesting question than it was in 2020.

How do you keep a context from becoming a junk drawer?

Give each context a single reason to change and name it after that reason — AuthContext, ThemeContext, FeatureFlagsContext — rather than AppContext. Enforce it by exporting only hooks, never the context object, so nobody can add a field without touching the provider file, and by keeping the provider's value type explicit rather than inferred from a spread. In review, the questions I ask about a proposed context addition are: does more than one distant subtree need it, does it change more often than the existing consumers can afford, and would passing it as a prop or as children be simpler. If the answer to the last one is yes, the context does not get created.

A team wants to introduce Redux Toolkit to a codebase that currently uses context. How do you evaluate that?

I would ask what problem they are solving, and I would expect one of four legitimate answers: they need devtools and time-travel for a genuinely complex flow; they need selector granularity that context cannot give; they need strict conventions because many people touch the same state; or they want RTK Query's caching. If the real answer is "our contexts cause re-renders", a lighter store solves that with a fraction of the surface area. If the real answer is "we fetch a lot of data into contexts", the fix is a query layer, and RTK Query is a reasonable choice but so is TanStack Query without the rest of Redux. And I would insist on scoping the migration: new features in the new pattern, existing contexts converted only when touched, with a written rule for what belongs in the store at all. A half-migrated state layer is worse than either endpoint.

06 Concurrency, Suspense, transitions

Docs: react.dev — useTransition · Suspense · Activity

Concurrency is not multithreading. React is still single-threaded; what "concurrent React" means is that rendering is interruptible and updates carry a priority. Because the work-in-progress tree lives in fibers rather than the call stack (unit 01), React can render part of a tree, notice that its time slice is up or that a higher-priority update arrived, throw the partial work away, and start again. Nothing is committed until a complete, consistent tree is ready, so the user never sees a half-updated screen — only a screen that is briefly one update behind.

The user-facing API is small. useTransition marks an update as non-urgent and gives you an isPending flag: typing in the box stays instant while the expensive list re-renders at low priority, and if you type again mid-render React abandons the in-flight work. useDeferredValue is the same idea from the consumer side — you get a lagging copy of a value and render the expensive subtree from that. React 19 extended transitions to async functions, which is the foundation of Actions (unit 08): startTransition(async () => { await save(); setResult(...) }) keeps isPending true across the await and handles errors through the nearest error boundary.

function SearchPage() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);
  const [isPending, startTransition] = useTransition();

  function onChange(e) {
    setQuery(e.target.value);                 // urgent: the input must not lag
    startTransition(() => {
      setResults(searchLocally(e.target.value));   // non-urgent, interruptible
    });
  }
  return (
    <>
      <input value={query} onChange={onChange} />
      <ul style={{ opacity: isPending ? 0.6 : 1 }}>{/* stale, not blank */}</ul>
    </>
  );
}

Suspense: a boundary for "not ready yet"

A component that reads a value which is not available yet suspends — it throws a promise, React unwinds to the nearest <Suspense> boundary and renders its fallback, and when the promise settles React retries the subtree. Boundaries are how you decide the loading granularity of a page: one at the shell, one per independent panel. On the server, boundaries are also the streaming unit — the HTML before a boundary is flushed immediately and the boundary's content is streamed in later, which is what makes RSC pages feel fast.

The rule that trips people: a component only suspends if it reads from a Suspense-enabled source — a framework loader, use(promise) with a cached promise, React.lazy, or a library that integrates with it (TanStack Query's useSuspenseQuery). A raw fetch inside useEffect does not suspend, no matter how many boundaries you wrap it in. Also: an update that is not in a transition and causes an already-visible boundary to suspend again will hide the existing content and show the fallback; wrapping that update in a transition keeps the old content on screen instead. That single behaviour is why transitions and Suspense are taught together.

Interview trap — "concurrent mode makes React multithreaded / faster"

Neither. There is no extra thread, and total work goes up slightly because interrupted renders are discarded and redone. What improves is responsiveness: the main thread is handed back between units of work so an urgent input can be processed, and the resulting metric that moves is INP, not throughput. Also retire the phrase "concurrent mode" — it was the experimental name; since 18 there is no mode, only concurrent features that opt in per update, which is how React shipped it without a breaking change.

Gotcha — useDeferredValue without memo does nothing

Deferring a value only helps if the expensive subtree can skip re-rendering when the deferred value has not changed. If the consumer is not wrapped in React.memo (or optimised by the compiler), it re-renders anyway with every keystroke and you have added a hook for no benefit. The other half of the same trap: the first render after a deferred update is still expensive — deferring changes when and at what priority the work happens, not how much of it there is. If the list is slow because it renders 10,000 rows, virtualise it.

What does "concurrent rendering" actually mean in React?

That a render pass can be interrupted, paused, resumed or abandoned, and that updates carry priorities so React can work on the important one first. It is implemented by building the work-in-progress tree out of fiber nodes on the heap rather than the call stack, checking a deadline between units of work, and yielding to the browser. There is no additional thread and no mode to turn on — since React 18 it is always available on a createRoot root, and individual updates opt into low priority via startTransition or useDeferredValue. The consequences for your code are the ones worth naming in an interview: render must be pure and replayable, and external stores must be read through useSyncExternalStore to avoid tearing.

When do you use useTransition versus useDeferredValue?

useTransition when you own the state update and can wrap it — you get an explicit isPending for that transition and you mark the cause. useDeferredValue when the value arrives as a prop or from a hook you do not control, so you cannot wrap the setter; you take a lagging copy and derive your own pending flag by comparing it to the current value. Two things people miss: deferring only pays off if the expensive consumer is memoized, and both are about priority, not debouncing — a debounce delays work by a fixed time regardless of load, while a transition starts immediately and yields as needed, so the list updates as fast as the machine allows. On a fast machine a transition feels instant where a 300 ms debounce still feels like 300 ms.

Which components suspend, and which do not?

Only components that read from a Suspense-enabled source: React.lazy, use(promise) where the promise is stable, a framework's data API such as a React Router loader or a Next.js server component's await, or a library that opts in like TanStack Query's useSuspenseQuery. Everything else — a fetch in useEffect writing to useState — does not suspend, so wrapping it in a boundary shows the fallback for exactly zero milliseconds and then a component rendering its own loading flag. The mechanism is that suspending means throwing a thenable during render, which React catches at the nearest boundary; nothing that resolves in an effect can participate, because effects run after commit.

Why does an update sometimes replace visible content with a Suspense fallback, and how do you stop it?

If an update causes an already-mounted component inside a boundary to suspend again — navigating to a new record with the same component, say — React has nothing valid to show, so it falls back to the boundary's fallback and the user sees a flash of skeleton over content they were reading. Wrapping the update in startTransition tells React the update is non-urgent, so it keeps the previous content on screen and only commits when the new one is ready; isPending lets you dim or show a progress bar in the meantime. This is the concrete reason routers put navigations in transitions, and it is a good answer to "why did my page flash white on every navigation".

What is <Activity> and when would you reach for it?

Stable in 19.2, it renders a subtree in one of two modes. visible is normal. hidden hides the children, unmounts their effects, and defers their updates to the lowest priority, while keeping their state and DOM alive. So it gives you two things conditional rendering cannot: pre-rendering a screen the user is likely to visit next, so the navigation is instant, and preserving state — scroll position, form drafts, expensive component trees — across tab switches or back navigation. The cost is memory, since the DOM stays, and the discipline it demands is correct effect cleanup, because effects really do unmount when the subtree goes hidden. I would use it for tab panels, wizard steps, and predictive pre-rendering of the next route, not as a general "keep everything mounted" switch.

How does Suspense work with server-side rendering?

Since React 18, renderToPipeableStream (Node) and renderToReadableStream (Web) do selective hydration and streaming: React sends the HTML up to each Suspense boundary immediately with the fallback in place, then streams the boundary's real HTML plus a tiny inline script that swaps it in when the data resolves. Hydration is likewise per-boundary and prioritised by user interaction, so clicking an un-hydrated part of the page makes React hydrate that part first. 19.2 added batching of these reveals — boundaries that resolve close together are revealed in one go, which reduces layout jitter and aligns client and server behaviour ahead of ViewTransition support. The architectural point is that a Suspense boundary is simultaneously your loading UI, your streaming unit and your hydration unit, so where you put boundaries is a real design decision.

What is partial pre-rendering and why does it exist?

Introduced in 19.2, it splits a server render into two phases with new APIs: prerender produces the static shell plus a serialisable "postponed" state, which you can cache on a CDN and serve instantly; later, resume or resumeAndPrerender picks up exactly where the prerender stopped and streams the dynamic parts. The point is to stop choosing between a fully static page that cannot show personalised content and a fully dynamic page that pays for a server round trip before the first byte. Frameworks are the intended consumers — Next.js's Partial Prerendering is built on this — so as an app author you mostly benefit indirectly, but knowing the primitive exists and that the split happens at Suspense boundaries is the level of detail that lands well in a systems-flavoured interview.

What is tearing, and when can it happen in React 18+?

Tearing is committing a tree in which different components read different values from the same source, so the screen is internally inconsistent — one part of the page says the cart has three items and another says four. It became possible with concurrent rendering because React can yield mid-render, and an external mutable store can change during that gap; it cannot happen with React state, which is snapshotted per render. The fix is useSyncExternalStore, which lets React re-read the snapshot and restart the render if it changed before committing. This is why every serious state library adopted it in 2022, and why hand-rolling a store with a module-level variable plus useState and a subscription effect is subtly wrong on a concurrent root.

How do you decide where to put Suspense boundaries?

By asking what the user should be able to see and do while each piece loads. A boundary is a promise that everything inside it appears at once, so I place one around each independently useful region — the article body, the comments, the recommendations sidebar — and avoid a single boundary at the root, which turns the whole page into a spinner and destroys streaming. I also avoid boundaries so fine-grained that the page renders as a mosaic of skeletons popping in at different times, which measures well and feels terrible; 19.2's reveal batching helps but does not remove the design judgment. The fallbacks themselves should preserve layout — a skeleton with the right dimensions — because a fallback that is a different size is a CLS regression.

Your team wants to adopt transitions across the app. How do you sequence that?

I would not adopt them "across the app" — transitions are a targeted fix for a measured responsiveness problem, and adding them everywhere makes state updates lag for no reason and complicates reasoning about pending states. The sequence I would run is: measure INP in the field, find the interactions with long tasks, and for each one decide whether the right fix is a transition, virtualisation, memoization, or moving work off the main thread. Route navigations are the one place I would apply them by default, because keeping the old page visible instead of flashing a fallback is almost always right, and most routers already do it. I would also make sure the app is on a concurrent root and that any external store goes through useSyncExternalStore first, because those are prerequisites, and I would use 19.2's Chrome DevTools tracks in review so the discussion is about measurements rather than intuitions.

07 Server Components

Docs: react.dev — Server Components · 'use client'

React Server Components went stable in React 19.0 (December 2024) after four years in canary, and they are the biggest conceptual change since hooks. An RSC runs once, on the server or at build time, and its output is not HTML — it is a serialised description of the UI called the RSC payload (the "flight" format), a stream of element descriptions, plain data, and references to client components by module id. The browser receives that stream and reconstructs the tree. Server components ship zero JavaScript to the client: their code, their imports, and any library they use stay on the server.

The mental model that makes RSC click: you are not choosing where a component renders, you are drawing a boundary between two worlds. Above the boundary, components can await a database query, read a file, or use a 300 KB markdown parser, but they have no state, no effects and no event handlers, and they never re-render. Below it — after a 'use client' directive — you are in ordinary React 19: hooks, interactivity, the DOM. The directive is not a per-component label; it marks a module as the entry point to the client graph, and everything that module imports becomes client code transitively.

// app/post/[id]/page.jsx — a server component. No directive needed:
// server is the default in an RSC-enabled framework.
import { db } from '@/lib/db';            // never reaches the browser
import { marked } from 'marked';          // 40 KB parser, server-only
import LikeButton from './LikeButton';    // a client component

export default async function Post({ params }) {
  const post = await db.post.find(params.id);        // no useEffect, no loading state
  return (
    <article>
      <h1>{post.title}</h1>
      <div dangerouslySetInnerHTML={{ __html: marked(post.body) }} />
      <LikeButton postId={post.id} initial={post.likes} />
    </article>
  );
}
// LikeButton.jsx
'use client';                    // module-level: this file and its imports
                                 // become part of the client bundle
import { useState } from 'react';

export default function LikeButton({ postId, initial }) {
  const [likes, setLikes] = useState(initial);
  return <button onClick={() => setLikes(l => l + 1)}>{likes}</button>;
}

The composition rule everyone gets wrong

A client component cannot import a server component — the import would pull server code into the bundle. But it can render one passed as children or as any element-valued prop, because by then the server has already rendered it to payload and the client component just places it. This "server components as slots" pattern is what lets you keep an interactive shell (a tab bar, a modal, a theme provider) at the top while the expensive content below stays on the server.

// WRONG — pulls ServerSidebar into the client bundle (or fails to build)
'use client';
import ServerSidebar from './ServerSidebar';
export default function Shell() { return <div><ServerSidebar /></div>; }

// RIGHT — the server renders both and hands the result to the client shell
// page.jsx (server):
<Shell sidebar={<ServerSidebar />}>
  <ServerContent />
</Shell>
// Shell.jsx ('use client') just renders {sidebar} and {children}.

Interview trap — "RSC is just SSR"

They are orthogonal and usually used together. SSR renders your component tree to an HTML string for the first paint, then the same components hydrate and run again in the browser — the JavaScript still ships. RSC removes components from the client graph entirely and produces a payload rather than HTML, and it works on navigation too, not just the first load: a client-side route change fetches a new RSC payload and patches the tree without a full page load. A crisp way to say it: SSR is about when the first HTML appears; RSC is about what code ships at all. The follow-up interviewers like is "so does an RSC app still need hydration?" — yes, for the client components, which is why the payload contains module references.

Gotcha — the December 2025 RSC vulnerabilities

The first real security incident of the RSC era, and a fair interview question in 2026. CVE-2025-55184 (CVSS 7.5) let an attacker send a crafted request that hung the server's RSC decoder, a denial of service; CVE-2025-55183 (CVSS 5.3) let an attacker recover the source text of Server Functions, which exposes any secret hard-coded in one. Fixed in react-server-dom-webpack/-parcel/-turbopack 19.2.3, 19.1.4 and 19.0.3 (11 December 2025) — and note the trap: the earlier 19.2.2 / 19.1.3 / 19.0.2 patches, released a week before for a related issue, are still vulnerable. The durable lessons: secrets belong in environment variables read at call time, not inlined in module scope, and the server/client boundary is an attack surface, not a trust boundary you get for free.

The design consequence is that behaviour must be defined on the client side of the boundary and configured by data from the server, which is a genuinely different habit from "pass a callback down" and is what most RSC migration friction actually is.

Explain React Server Components to a senior engineer who has only used SSR.

An RSC runs once on the server and its output is a serialised element tree, not HTML, so the component's own code never enters the client bundle. That means it can await a database call directly, import heavy server-only libraries for free, and hold server-only concerns like access checks, but it cannot have state, effects, or event handlers, because none of those can be serialised. You interleave them with client components, marked by a module-level 'use client' directive, which are the interactive leaves. The practical wins are bundle size and the elimination of fetch waterfalls between parent and child; the practical costs are a build system that understands the boundary, a new mental model for the team, and props that must be serialisable.

What does 'use client' actually do?

It marks a module as an entry point into the client module graph. The bundler treats every export of that file as a client component, adds the file and everything it imports to the client bundle, and replaces the file with a reference in the server graph so the RSC payload can point at it. It is not a per-component annotation and it does not need to be repeated in files imported by an already-client module — those are client by transitivity. Two consequences worth stating: putting the directive too high in the tree silently pulls a large subtree into the bundle, and adding it to a file that imports a heavy server library is how bundles regress in an RSC codebase.

Why can a client component render a server component as children but not import one?

Importing would put the server component's code — and its whole import graph, including database drivers and secrets — into the client bundle, so the bundler forbids it. Passing it as children or as an element prop works because the composition happens on the server: by the time the client component exists, the server has already rendered that subtree into the payload, and the client component just places the resulting element in its output. This is why "lift the server content up and pass it down as a slot" is the standard refactor when you need a client wrapper — a theme provider, an animation container, a tab shell — around server content.

What can and cannot be passed as props across the boundary?

Anything the RSC serialiser understands: primitives, plain objects and arrays, Date, Map, Set, typed arrays, promises, JSX elements, and references to Server Functions. What cannot cross: arbitrary functions, class instances, symbols, and anything with a prototype the runtime cannot reconstruct — so an ORM model object, a Date-like wrapper from a library, or a callback all fail with an explicit error. The design pressure this creates is healthy: it forces you to send data rather than behaviour, and to convert domain objects into plain DTOs at the boundary, which is a discipline most teams should have had anyway. Promises being serialisable is the underrated one — a server component can start a fetch and pass the unresolved promise to a client component that reads it with use, so the client streams in without a waterfall.

How do server components change data fetching compared with the effect-based approach?

They remove the client waterfall. With effects, a parent must render before its child mounts, so nested data dependencies serialise into round trips; with RSC, the whole tree is rendered on the server where the data lives, so sibling fetches run in parallel and nested ones happen at server latency, not network latency. There is no loading state to hand-manage either: an await that has not resolved suspends, and the nearest <Suspense> boundary defines the loading UI and the streaming unit. What you lose is client-side cache semantics — revalidation, optimistic updates, background refetch — which is why RSC apps still use client caches for highly interactive data, and why "RSC replaces TanStack Query" is not a claim I would make.

Do you still need SSR if you have RSC? Do you still need hydration?

Yes to both, in a typical web app. RSC produces a payload, not HTML; a framework additionally runs SSR over the resulting tree to emit HTML for the first paint, otherwise the initial load would be a blank page while the client reconstructs the tree. And hydration is still required for the client components, because their event handlers and state have to attach to the server-rendered DOM — that is precisely why the payload carries module references. The mental split I use in interviews: RSC decides what code exists on the client, SSR decides what pixels exist before that code runs, and hydration is the handshake between them. An app could technically ship RSC without SSR — that is what a client-side navigation is — but you would not do it for the initial document.

What went wrong with RSC security in December 2025 and what did you take from it?

Two CVEs in the react-server-dom-* packages, disclosed 11 December 2025: a high-severity denial of service where a crafted request stalled the RSC decoder, and a medium-severity flaw that let an attacker recover the source text of Server Functions, exposing anything hard-coded inside one. They were fixed in 19.2.3 / 19.1.4 / 19.0.3, and importantly the patches from a week earlier — 19.2.2 and friends, for a separate RSC issue — did not cover them, so a team that patched once was not safe. What I took from it operationally is that the RSC endpoint is an untrusted input surface like any other API and belongs in the threat model, that secrets must be read from the environment at call time rather than inlined where they can end up in serialised source, and that these packages need to be in the dependency-alerting path explicitly, because they often sit behind a framework rather than in package.json.

What is the RSC payload, and why is it not just HTML?

It is a line-based stream in React's flight format describing the rendered tree: element types, props, plain data, references to client component modules by id, and placeholders for parts that are still pending. It is not HTML because it has to be reconcilable — on a client-side navigation React receives a new payload and diffs it against the current tree, preserving client component state, scroll position and focus, which you cannot do with a blob of markup. It also has to carry the client module references so hydration knows what to load. The streaming property matters too: suspended subtrees arrive as later rows in the same response, so the shell paints immediately and slow data fills in.

What are the honest downsides of adopting RSC?

You need a framework or a bundler plugin — Next.js App Router, React Router 7 in framework mode, TanStack Start, or the Vite RSC plugin — so it is a platform decision, not a library upgrade, and you now run and operate a Node (or edge) server. The mental model splits in two, and the errors people hit are unfamiliar: serialisation failures, "useState is not defined in a server component", accidental client boundaries pulling in the world. Debugging spans two runtimes. Third-party libraries were slow to add the directive and some still are. And the ecosystem's testing story is thinner than for client React. For a green-field content-heavy app I would take the trade readily; for an existing complex SPA I would be honest that the migration is a rewrite of the data layer, and would first ask whether the actual problem is bundle size, first paint, or waterfalls, because each has a cheaper fix.

How would you introduce RSC to a team running a large client-side React app?

Incrementally and with a measured reason. I would start by naming the metric — LCP, bundle size, or a specific waterfall — and pick one route that is content-heavy and low-interaction as a pilot, ideally behind a framework that supports mixed routing so the rest of the app is untouched. Then I would establish two conventions before anyone else writes RSC code: client components live as leaves and are marked deliberately, and data crossing the boundary is a plain DTO. I would invest in the boundary being visible — a lint rule or a naming convention — because the failure mode is silent bundle growth, and I would put bundle size in CI so a stray 'use client' shows up as a diff. The pitch to a skeptical team is not "RSC is the future" but "here is the number we are trying to move, here is the one route where we will find out, and here is how we roll it back".

08 Actions and async mutations

Docs: react.dev — useActionState · Server Functions

React 19's headline feature is Actions: the recognition that every mutation in a real app has the same four-part shape — pending state, optimistic update, error handling, and a result — and that hand-writing it for the twentieth time is how bugs get in. An Action is simply an async function passed into a transition. React tracks it, keeps isPending true for the whole thing including the awaits, routes thrown errors to the nearest error boundary, and reverts optimistic state automatically when it settles.

Four APIs make up the surface. useActionState(fn, initialState) wraps an async function and returns [state, formAction, isPending], where the wrapped function receives the previous state as its first argument — that is where validation errors live. <form action={fn}> accepts a function directly (React 19 extended the DOM action prop), calls it with the FormData, and resets the uncontrolled form on success. useFormStatus() lets a descendant — a submit button in a shared design-system component — read the enclosing form's pending state without prop drilling. useOptimistic(state, reducer) gives you a value that shows the intended result immediately and snaps back to the real state when the transition finishes.

'use client';
import { useActionState, useOptimistic } from 'react';
import { useFormStatus } from 'react-dom';        // note: react-dom, not react
import { addComment } from './actions';           // a Server Function

function SubmitButton() {
  const { pending } = useFormStatus();            // reads the PARENT form
  return <button type="submit" disabled={pending}>
           {pending ? 'Posting…' : 'Post'}
         </button>;
}

export function Comments({ comments }) {
  const [optimistic, addOptimistic] = useOptimistic(
    comments,
    (state, text) => [...state, { id: 'temp', text, sending: true }]
  );

  const [error, formAction, isPending] = useActionState(
    async (prevError, formData) => {              // prev state first!
      const text = formData.get('text');
      addOptimistic(text);                        // shows instantly
      const res = await addComment(text);         // network
      return res.ok ? null : res.message;         // becomes the next `error`
    },
    null
  );

  return (
    <>
      {optimistic.map(c => <p key={c.id} style={{ opacity: c.sending ? .5 : 1 }}>{c.text}</p>)}
      <form action={formAction}>                  {/* form resets on success */}
        <input name="text" />
        <SubmitButton />
      </form>
      {error && <p role="alert">{error}</p>}
    </>
  );
}

Server Functions: RPC with a directive

A 'use server' directive marks an async function (or a whole module of them) as callable from the client. The bundler replaces it with a reference; calling it from the browser issues a POST to the framework's RSC endpoint, which runs the real function on the server and streams back the result — possibly including a fresh RSC payload so the page updates without a refetch. The name is confusingly close to 'use client': 'use client' marks a client boundary; 'use server' marks a server-callable function, not a server component. Server components are the default and need no directive.

// actions.js
'use server';                       // every export here is a Server Function

import { auth } from '@/lib/auth';
import { db } from '@/lib/db';

export async function addComment(text) {
  const user = await auth();        // ALWAYS re-authorise: this is a public
  if (!user) throw new Error('unauthorized');   // HTTP endpoint, not a callback
  if (typeof text !== 'string' || text.length > 2000) throw new Error('bad input');
  await db.comment.insert({ userId: user.id, text });
  return { ok: true };
}

Interview trap — "Server Functions are just function calls"

They are public HTTP endpoints with a generated id. Anyone can POST to them with any arguments; the fact that your UI only calls one from a logged-in page is worth nothing. Every Server Function must independently authenticate, authorise, and validate its arguments — treat it exactly like a controller action. That last point is what made CVE-2025-55183 (unit 07) dangerous.

Gotcha — useFormStatus only sees a parent

It reads the status of the nearest <form> above it in the tree, so calling it in the same component that renders the form returns pending: false forever. It must live in a child — which is the point: your design system's <SubmitButton> can be pending-aware with no props. It also lives in react-dom, not react, which is a genuinely common import mistake. And useActionState is the renamed useFormState from the canaries; it moved from react-dom to react and gained the isPending return value, so canary-era code needs updating.

What is an Action in React 19, precisely?

An async function passed somewhere React can track it — a <form action>, a formAction on a button, startTransition, or wrapped by useActionState. React runs it inside a transition, which means isPending is true for the whole duration including awaits, the UI stays responsive because the update is non-urgent, thrown errors surface at the nearest error boundary, and any useOptimistic state reverts when it settles. The value of the abstraction is that it makes the four things every mutation needs — pending, error, optimism, result — into framework concerns instead of per-feature code, and it makes them behave consistently, which is what you actually want across a large app.

Explain the difference between 'use client' and 'use server'.

They are not opposites. 'use client' marks a module as an entry point to the client bundle — everything in it and everything it imports ships to the browser. 'use server' marks async functions as server-callable: the bundler replaces them with a reference, and calling one from the client performs a POST to the server. So 'use server' has nothing to do with server components, which are simply the default in an RSC framework and need no directive at all. The naming causes real confusion, and I would expect a lead to be able to correct a teammate who has put 'use server' at the top of a component file expecting it to become a server component.

How does useOptimistic work, and when is it the wrong choice?

It returns a derived value computed by applying your optimistic updates on top of the real state, and React discards those updates automatically when the surrounding transition finishes — so on success the real data has already arrived and looks identical, and on failure the UI snaps back without you writing rollback code. It is right when the operation almost always succeeds and the user's mental model is that it already happened: likes, reordering, marking read, sending a chat message. It is wrong when failure is common or expensive to undo visually, when the server computes something you cannot predict — a generated id, a price, a moderation verdict — or when showing a wrong state briefly would be misleading, as in a payment confirmation. In those cases a real pending state is more honest.

What are the security requirements for a Server Function?

Treat it as a public HTTP endpoint, because that is what it is: the bundler gives it a stable id and anyone can POST to it with arbitrary arguments. So every one must authenticate the caller, authorise the specific operation on the specific resource, and validate its inputs with a schema rather than trusting types, since TypeScript disappears at runtime. Beyond that: variables closed over by the function are serialised into the client-visible reference, so never close over secrets; read them from the environment inside the function instead. Rate limiting and CSRF considerations apply as they would to any mutation endpoint, and the December 2025 source-exposure CVE is the concrete reminder that the function's body is not as private as it looks.

When do you throw from an action versus return an error?

Return for expected, recoverable, field-level outcomes — "email already taken", "quantity exceeds stock" — because they belong next to the form as part of its state, and useActionState feeds the returned value straight back as the next state so you can render it inline. Throw for the unexpected: an auth failure, a downstream outage, a bug. Thrown errors propagate to the nearest error boundary, which is the right place for "something went wrong, here is a retry" and the right place to report to your telemetry. The failure mode I look for in review is throwing for validation, which replaces the user's half-filled form with an error screen and loses their input.

What is progressive enhancement in the Actions model, and does it matter?

Because <form action={serverFunction}> compiles to a real form post targeting the framework's endpoint, the form works before React hydrates and even with JavaScript disabled — the browser submits, the server runs the function, and the response re-renders the page. That closes a gap that SPAs have had for fifteen years: the window between first paint and hydration where clicking does nothing. Whether it matters depends on the product — for a public content site, a signup form, or anything in a low-bandwidth market, it is a real accessibility and conversion win; for an internal dashboard behind a login it is close to irrelevant. What I would not do is claim it as a headline benefit without knowing the audience.

How do Actions interact with transitions and Suspense?

An Action is a transition, which is why React 19 had to make startTransition accept async functions in the first place. That gives you three inherited behaviours: the update is non-urgent so the UI stays interactive, an already-visible Suspense boundary that re-suspends keeps showing its old content instead of flashing a fallback, and isPending spans the awaits. It also means that if the action triggers a re-fetch of server content, the transition holds the previous page on screen until the new one is ready, which is exactly what you want after a mutation. The subtlety worth knowing is that useActionState's isPending is per-action while useFormStatus's is per-form, so in a page with several forms you get independent pending states without any wiring.

What migration work do Actions imply for a React 18 codebase?

None that is forced — Actions are additive and old mutation code keeps working, which is the right thing to say first. Where I would spend effort is the shared layer: make the design system's submit button use useFormStatus, and give the team one useActionState-based pattern for forms so new code stops reinventing pending and error handling. Full value needs Server Functions, which needs an RSC-capable framework, so a plain SPA gets the client-side half — useActionState, useOptimistic and async transitions all work with a normal fetch. If the codebase came from React 19 canaries, there is one mechanical fix: useFormState was renamed to useActionState and moved from react-dom to react.

Do Actions replace React Hook Form, Formik, or TanStack Query?

Partly and not entirely. For simple forms — a handful of fields, server-side validation, a submit — <form action> plus useActionState genuinely removes the need for a form library, and the uncontrolled-plus-FormData approach is faster than a controlled form with a re-render per keystroke. What form libraries still do better is rich client-side validation with per-field errors as you type, complex dynamic field arrays, and integration with schema types. For mutations, Actions cover the transition and optimistic mechanics but not cache invalidation, so in a TanStack Query app you still want the query cache to know something changed. My default now is: uncontrolled forms with Actions as the baseline, reach for React Hook Form when the validation UX is genuinely complex, and keep the query library for cache management.

You are reviewing a PR that adds a Server Function. What is your checklist?

Does it authenticate and authorise inside the function, not just in the page that calls it? Are the arguments validated with a schema, given that anyone can call it with anything? Does it close over any secret, or read secrets from the environment at call time? Is the return value serialisable and free of internal domain objects? Does it invalidate or revalidate whatever cache the framework maintains, so the UI is not stale afterwards? Is the failure path distinguished — validation returned versus unexpected thrown — and is there an error boundary above the caller? And finally, is it doing too much: a Server Function that performs three unrelated writes without a transaction is the same design problem as a fat controller, and the fact that it is called from JSX does not change that.

09 Performance and the Compiler

Docs: react.dev — React Compiler · memo

The performance story changed shape in October 2025. React Compiler 1.0 shipped stable on 7 October 2025 — a Babel/SWC-stage build tool that analyses your components, proves which values can be reused between renders, and emits memoization automatically. Meta's numbers from production: up to 12% faster initial load and navigation, and specific interactions over 2.5× faster, with no memory increase. Its lint diagnostics ship in eslint-plugin-react-hooks v6's recommended preset, and Expo, Vite and Next.js can enable it in new projects out of the box.

What that means practically: hand-written useMemo, useCallback and memo are now something you remove, not something you add. The compiler memoizes at a finer granularity than a human would bother with — individual JSX subtrees, not just whole components — and it never gets the dependency array wrong. Its price is a rule: it only optimises code it can prove is pure and follows the Rules of React. Mutate a prop, read a ref during render, or define a component inside another and the compiler bails out of that function (safely, leaving it unoptimised) and the linter tells you why.

// vite.config.js — the compiler as a Babel plugin (Next.js has its own flag)
export default defineConfig({
  plugins: [react({ babel: { plugins: [['babel-plugin-react-compiler', {}]] } })],
});

// Incremental adoption: opt in directory by directory instead of all at once
// { sources: (filename) => filename.includes('src/features/checkout') }

// Before — hand-memoized, easy to get wrong, noisy
const visible = useMemo(() => items.filter(i => i.tag === tag), [items, tag]);
const onPick  = useCallback((id) => select(id), [select]);
export default memo(List);

// After — the compiler produces equivalent (usually better) caching.
// You write the obvious thing:
const visible = items.filter(i => i.tag === tag);
const onPick  = (id) => select(id);
export default List;

The performance hierarchy that still matters

Memoization is the fourth thing to try, and a lead who leads with it is answering the wrong question. In order of typical impact:

  1. Ship less JavaScript. Route-level code splitting with lazy, server components for anything non-interactive, and an actual bundle budget in CI. A 200 KB parser that runs on the server costs the user zero.
  2. Render less. Virtualise long lists (TanStack Virtual, react-window). Ten thousand rows is not a memoization problem.
  3. Move work off the critical path. Transitions and useDeferredValue for priority; a Web Worker for genuinely heavy computation; streaming SSR so the shell paints before the data arrives.
  4. Fix identity churn. Context values, inline objects, functions recreated in render. This is where memoization — or the compiler — belongs.

Measuring, and what 19.2 added

React DevTools' Profiler gives you flamegraphs, the ranked chart, and "why did this render" when you enable it in settings. React 19.2 added custom tracks to the Chrome DevTools Performance panel: a Scheduler track showing React's work by priority (blocking, transition, idle) and a Components track showing which component was rendering or running effects at each moment, lined up with real browser events. That is the tool to reach for when the question is "why is INP 400 ms", because it sits in the same timeline as long tasks, layout and paint.

Interview trap — "we memoize everything to be safe"

Gotcha — memo's comparison is shallow, and children defeat it

React.memo does a shallow compare of props, so <Row data={{id}} /> never bails out — new object, every render. Worse, children is a prop, so memo(Wrapper) around <Wrapper><Thing/></Wrapper> is defeated by the fresh element created for <Thing/> each render, unless that element itself comes from a parent that did not re-render. A custom areEqual comparator is usually a smell: if you are deep-comparing props on every render you have moved the cost, not removed it.

What is the React Compiler and what does it change about how you write React?

It is a build-time tool, stable since 1.0 on 7 October 2025, that understands React's semantics well enough to insert memoization automatically — it caches values, JSX subtrees and callbacks at a granularity finer than a human would hand-write, and it cannot get a dependency array wrong. What it changes is that useMemo, useCallback and memo stop being tools you reach for and become artefacts you delete; the discipline shifts from "where do I memoize" to "is this component pure enough to be optimised". Meta reported up to 12% faster loads and interactions over 2.5× faster in production. The important caveat for a lead is that it is not magic: it does not virtualise your list, shrink your bundle, or fix an N+1 query.

When does the compiler bail out, and how do you find out?

It bails out of any function whose purity it cannot prove — mutating props or state in place, reading or writing a ref during render, defining a component or hook inside another function, calling a hook conditionally, or using an unsupported dynamic pattern. The bail-out is per-function and safe: that component is simply left unoptimised, never mis-optimised. You find out three ways: the compiler's diagnostics as lint rules in eslint-plugin-react-hooks v6's recommended preset, which flag the violation at the line; the "Memo ✨" badge in React DevTools showing which components are compiled; and the compiler's own build output. That feedback loop is what makes incremental adoption practical — you can enable it on one directory, see what fails, and fix the rule violations as real bugs, because most of them are.

Is React.memo obsolete?

For most codebases on the compiler, yes in practice — the compiler memoizes inside components, which subsumes the common reason to wrap one. It still has a role where a component is a boundary you want to guarantee, such as a virtualised list row rendered thousands of times, or an expensive leaf receiving props from code the compiler cannot optimise (a third-party render prop, an un-compiled package). Without the compiler it remains a legitimate tool, with the two caveats that its comparison is shallow and that it is defeated by any prop whose identity changes — which is most of them unless the parent is also memoizing. The answer I want to hear from a senior candidate is that memo is a claim about a boundary, and a claim you have not measured is usually wrong.

Walk me through diagnosing a slow interaction.

Reproduce it with a profile, not a hypothesis. I record the interaction in the Chrome Performance panel, using React 19.2's Scheduler and Components tracks so React's work is aligned with input delay, long tasks and paint, and I split the INP into input delay, processing and presentation. If the processing is a single long render, I look at the Components track to see which component and whether the cause is a large subtree, an expensive computation, or a context change fanning out. If it is commit-heavy, the problem is DOM size or layout thrash, and virtualisation or CSS containment is the fix. Only after that do I look at memoization, and by then it is usually identity churn in a context value or a prop. Finally I check whether the work should happen at that priority at all — a transition often turns a 300 ms freeze into a responsive UI with a slightly stale list.

Why is virtualisation usually the answer for long lists rather than memoization?

Because the cost is in the DOM and in commit, not in re-rendering component functions. Ten thousand rows means ten thousand sets of nodes for the browser to lay out, style, paint and keep in memory, and memoizing the row components does not remove a single one of them — it only stops React from re-creating elements it was going to diff away anyway. Virtualisation renders the visible window plus a small overscan, so the DOM stays at a few dozen nodes regardless of data size, and scroll performance becomes independent of list length. The trade-offs to name: find-in-page and Ctrl+F stop working, screen-reader semantics need care with aria-setsize/aria-posinset, variable-height rows need measurement, and anchor links into unrendered items need special handling.

What would you put in CI to keep performance from regressing?

A bundle-size budget per route with a hard failure on regression, because bundle growth is the most common and most invisible regression, and in an RSC codebase a stray 'use client' shows up here first. Lighthouse or a synthetic run on a couple of key routes for LCP and CLS, treated as a trend rather than a gate, because they are noisy. Real-user INP and LCP from the field, since lab numbers on a developer laptop hide the problem. The React Compiler's lint rules on, so purity violations fail review rather than accumulating. And for a specific hot path, a rendering benchmark is worth it, though I would keep those few — they are expensive to maintain and go stale. The organisational half matters more than the tooling: someone has to own the numbers, or the dashboards get ignored within a quarter.

A controlled form re-renders the whole page on every keystroke. What are your options?

Move the state down: if the form's state lives at the page level, colocating it inside the form component immediately shrinks the blast radius, and that is usually the whole fix. If the form itself is large, uncontrolled inputs with FormData at submit — which React 19's <form action> makes idiomatic — remove per-keystroke rendering entirely, at the cost of instant validation. If you need controlled behaviour and live validation, isolate each field so only that field re-renders, which is roughly what React Hook Form does with subscriptions. And if something expensive elsewhere must react to the input, that is exactly the useDeferredValue or transition case. What I would not do first is wrap everything in memo, because the value changing every keystroke means nothing bails out.

How do you decide whether a performance problem is a React problem at all?

By looking at where the time goes before assuming. A profile that shows most of the time in scripting under React's render tells you it is a rendering problem; time in layout and paint points at DOM size, CSS, or images; time waiting on the network points at data fetching, waterfalls, or a slow API; and a slow LCP with a fast Time to First Byte usually points at bundle size or a render-blocking resource. I have seen entire sprints spent memoizing components when the actual problem was a 4 MB hero image or an API returning 12,000 rows the client then filtered. The habit I try to instil is that the first artefact in any performance discussion is a trace, and the first question is which of network, script, layout or paint is dominant.

What is the cost of the React Compiler, and when would you not enable it?

Build time goes up, since it is doing real analysis; the output is slightly larger because memoization code is emitted; and you inherit a dependency on a tool that must understand your syntax, so exotic Babel setups or very old code can need work. It also makes the Rules of React enforceable in a way some codebases will fail loudly — which is a benefit, but it is work to absorb. I would not enable it wholesale on a large legacy codebase in one go; I would use the incremental option to scope it to directories, or start with new features, and let the lint rules clean up the rest over time. I also would not enable it as a substitute for measuring — if the app is slow because it ships 3 MB of JavaScript, the compiler will not save it.

Your team keeps adding useMemo in code review "just in case". How do you change that?

I would replace the folklore with a rule and a tool. The rule: memoization is added in response to a profile, and the PR that adds it links the measurement — otherwise it is noise that costs allocation, comparison time and readability. The tool: enable the compiler, so the answer to "shouldn't we memoize this?" becomes "the compiler already did, and better". Then I would delete a batch of existing manual memoization in one visible PR with before/after profiles, because the fastest way to change a habit is to show that the thing everyone was afraid of does not happen. The one place I would keep manual memoization is genuinely expensive pure computation — a large sort or a parse — where the intent is documentation as much as caching, and I would ask for a comment saying what it costs.

10 Refs, the DOM, escape hatches

Docs: react.dev — Manipulating the DOM with refs · createPortal

A ref is a mutable box that survives renders and does not trigger them. That is the whole definition, and it has two uses that look unrelated but are the same thing: holding a DOM node so you can call imperative browser APIs on it, and holding a value that render must not depend on — a timer id, a websocket, a previous value, a "has the user scrolled yet" flag.

The rule that keeps refs safe: do not read or write ref.current during render. Render must be pure and replayable (unit 01), and a ref is by definition outside the data flow, so reading one during render makes the output depend on when React happened to run you. Write refs in event handlers and effects; read them there too. The React Compiler enforces this, and it is one of the more common bail-out causes in older code.

React 19 removed a long-standing piece of ceremony: ref is now an ordinary prop for function components, so forwardRef is deprecated and unnecessary. It also introduced ref cleanup functions — a ref callback may return a cleanup, which React calls on detach instead of calling the callback with null. That change is mildly breaking: an implicit-return arrow like ref={el => (map[id] = el)} now returns a value React tries to call, so the codemod adds braces.

// React 19 — ref as a prop. No forwardRef.
function Input({ ref, ...props }) {
  return <input ref={ref} {...props} />;
}

// React 18 and earlier — what you will still find everywhere:
const Input18 = forwardRef((props, ref) => <input ref={ref} {...props} />);

// Ref callback with cleanup (19+). Note the BRACES: an implicit return is
// now interpreted as a cleanup function and will throw.
<div ref={(node) => {
  const ro = new ResizeObserver(onResize);
  if (node) ro.observe(node);
  return () => ro.disconnect();     // called on detach
}} />

// Narrow the imperative surface instead of exposing the node:
function Video({ ref }) {
  const inner = useRef(null);
  useImperativeHandle(ref, () => ({
    play:  () => inner.current.play(),
    pause: () => inner.current.pause(),
  }), []);                           // parent cannot restyle or unmount it
  return <video ref={inner} />;
}

Portals, and the accessibility half nobody mentions

createPortal(children, domNode) renders into a different part of the DOM while keeping the React tree intact — so context still flows, and events still bubble through the React tree, not the DOM tree. That is the property that makes portals work for modals inside a table cell with overflow: hidden, and the property that surprises people when a click inside a portal triggers the handler on its logical parent. Note that the modern answer for dialogs is often the native <dialog> element plus showModal(), which gives you the top layer, focus trapping and inertness for free; a portal is still the tool for tooltips, popovers anchored elsewhere, and toasts.

Interview trap — using a ref to store state that the UI displays

Refs do not trigger re-renders, so a value the UI must reflect belongs in state. The tell is a ref plus a manual forceUpdate or an unrelated setter to "flush" it — at that point you have reimplemented useState badly. The inverse trap is equally common: putting a websocket, an interval id or a mutable observer in state, which re-renders on every change for no reason. The clean question to ask is "does the screen change when this value changes?" — yes means state, no means ref.

Gotcha — the ref is null on the first render

Refs are attached during commit, so any code that runs before commit — the component body, or a parent's render — sees null. Measure in useLayoutEffect if the result affects layout before paint, in useEffect otherwise, or use a ref callback when you need to react to attach and detach precisely, which since React 19 can return a cleanup. And when the node can appear or disappear (a conditionally rendered element, a list item), the callback form is the only correct choice, because an effect's dependency array cannot express "the node changed".

When do you use a ref instead of state?

When the value must survive renders but must not cause one, and nothing rendered depends on it — a timer or animation-frame id, a websocket or observer instance, the previous value of something for comparison in an effect, a flag like "has the user interacted". The test I use is simply: if this value changed and nothing else did, should the screen change? Yes means state. The other legitimate use is a handle to a DOM node for imperative APIs the declarative model does not cover: focus, text selection, scroll position, media playback, canvas, and integrating a non-React widget. Everything else — especially a value the UI displays — belongs in state, and a ref plus a forced update is a code smell.

Why is reading ref.current during render a problem?

Because render must be a pure function of props, state and context, and a ref is deliberately outside that data flow. React may render a component twice for one update, may discard a render, and may render offscreen work that is never committed — so a value read from a ref during render is a value read at an unspecified time, which makes the output non-deterministic. It also breaks the compiler's ability to prove the component is pure, so it bails out and stops optimising the whole function. The exception people cite is lazy initialisation of a ref's contents, and React's own guidance allows the narrow if (ref.current === null) ref.current = create() shape because it is idempotent — but I would still prefer useState with a lazy initialiser where possible.

What changed about refs in React 19?

Two things. ref is now a normal prop on function components, so you destructure it out of props and pass it along — forwardRef is deprecated and there is a codemod to remove it. And ref callbacks may return a cleanup function, which React calls when the node detaches, instead of the old convention of calling the callback again with null; that makes observers and node registries safe by construction. The second one is subtly breaking: an arrow function with an implicit return, which was extremely common for one-liner ref callbacks, now returns a non-function that React tries to invoke, so the upgrade adds braces. Both are the kind of detail that signals you have actually upgraded an app rather than read a changelog.

What does useImperativeHandle do and when is it justified?

It replaces what a parent sees through a ref with an object you define, so instead of handing out the raw DOM node you expose a narrow API — play(), focus(), scrollToRow(n). It is justified when a component genuinely owns imperative behaviour that a parent must trigger and that cannot be expressed as a prop, which is the case for media elements, editors, virtualised lists and animation controllers. It is not justified as a general "let the parent control me" mechanism — if the parent is calling setValue through a handle, that is state that should have been lifted. The design value is encapsulation: without it, any parent can restyle or measure your internals, and that becomes an accidental public API you cannot change.

How do portals interact with events, context and accessibility?

Context flows normally, because the React tree is unchanged — only the DOM insertion point differs. Events propagate through the React tree too, so a click inside a portal bubbles to the logical parent's handlers even though the DOM nodes are elsewhere; that is usually convenient and occasionally a bug you fix with stopPropagation. Accessibility is where portals need the most care: focus is not moved for you, focus is not trapped, the rest of the page is not made inert, and screen-reader reading order follows the DOM, so a portal at the end of body reads last. That is why for dialogs specifically I would reach for the native <dialog> with showModal(), which handles top layer, inertness, Escape and focus trapping, and keep portals for tooltips, popovers and toasts.

How does React 19 change document metadata and resource loading?

You can render <title>, <meta> and <link> anywhere in the component tree and React hoists them into <head>, deduplicating as it goes — which retires react-helmet and the class of bugs where two components fought over the title. Stylesheets can declare a precedence so React orders them deterministically instead of leaving it to insertion order, which is what made CSS-in-JS and lazy-loaded styles fragile. Async scripts are hoisted and deduped, so rendering the same third-party script in two components loads it once. And react-dom exports preload, preinit, preconnect and prefetchDNS so you can express resource hints from inside components, close to the code that needs them, instead of guessing in a static <head>.

What causes hydration mismatches and how do you fix them?

The server-rendered HTML disagreeing with what the client renders on its first pass. The usual causes are non-deterministic values — Date.now(), Math.random(), a locale-dependent format, typeof window branches — reading browser-only APIs during render, invalid HTML nesting that the browser silently repairs (a <div> inside a <p>), and third-party scripts or extensions mutating the DOM before hydration. React 19 improved the diagnostics substantially: instead of two vague warnings you get one error with a diff showing the server and client output. The fixes are to render the same thing on both sides and move the difference into an effect, to use useId for generated ids, and — as a last resort for a genuinely client-only leaf like a timestamp — suppressHydrationWarning, which should be rare enough to justify in review.

How do you integrate a non-React library that owns a DOM subtree?

Give it a container element, initialise it in an effect, and return a cleanup that destroys it — that is the whole pattern, and it is exactly what effects are for. The rules that make it work: React must not render children into that container, or the two will fight over the same nodes; the effect's dependencies should be the configuration the library needs, so it re-initialises when those change, and if re-initialisation is expensive you use the library's own update API instead; and if the library emits events you translate them into state updates rather than mutating React-owned DOM. The failure I have seen most often is a chart library initialised without a cleanup, so navigating away leaks the instance and its resize listeners, which the StrictMode double-invoke would have caught immediately.

Controlled or uncontrolled inputs — how do you choose in 2026?

Controlled when the value must be read, transformed or validated as it changes — a search box driving a query, a masked field, a form where one field enables another. Uncontrolled when you only need the value at submit, which is most forms, and which React 19's <form action> plus FormData now makes the idiomatic path; it also avoids a re-render per keystroke on large forms. The mistakes to name: switching a field from uncontrolled to controlled mid-life because value started as undefined, which React warns about; and using defaultValue and expecting it to update when the prop changes, which it does not — you need a key to reset it. My default is uncontrolled with a form library or Actions, and controlled only where the interaction demands it.

You see document.querySelector in a React component. What is your review comment?

I ask what it is reaching for and why a ref does not work. Querying the document bypasses React's ownership of the DOM, so it breaks the moment a class name changes, silently selects the wrong node when the component renders twice on a page, and is impossible to reason about in tests. In almost every case a ref on the element, or a ref callback if the element comes and goes, is the direct fix. The legitimate exceptions are reaching for something React does not own — a container rendered by the host page, document.body for a portal target, an element created by a third-party script — and for those I want a comment saying so, plus a null check, because the node may not exist yet. If the answer is "I needed to update it imperatively", the real conversation is about why that state is not in React.

11 Errors, testing, production

Docs: react.dev — Error boundaries · Root error options

React's error story is deliberately blunt: if a render throws and nothing catches it, React unmounts the whole tree. The reasoning is that a corrupted UI is worse than no UI — a half-rendered banking screen showing the wrong balance is a bigger problem than an error page. So error boundaries are not optional polish; they are the mechanism that decides how much of your app dies when one component fails.

An error boundary is still a class component — the only remaining thing hooks cannot express, because it needs static getDerivedStateFromError (to render a fallback) and componentDidCatch (to report). Most teams use react-error-boundary rather than writing their own, for its onReset and resetKeys ergonomics. What boundaries catch: errors thrown during render, in lifecycle methods, and in constructors below them. What they do not catch: event handlers, setTimeout callbacks, async code after an await that is not part of a transition, server-side rendering errors, and errors in the boundary itself.

class ErrorBoundary extends React.Component {
  state = { error: null };
  static getDerivedStateFromError(error) { return { error }; }
  componentDidCatch(error, info) {
    // info.componentStack — React 19 also gives you an owner stack in dev
    report(error, { componentStack: info.componentStack });
  }
  render() {
    return this.state.error
      ? this.props.fallback(this.state.error, () => this.setState({ error: null }))
      : this.props.children;
  }
}

// React 19: root-level error handlers, so you stop patching console.error
createRoot(container, {
  onCaughtError:      (error, info) => report(error, info),   // a boundary handled it
  onUncaughtError:    (error, info) => fatal(error, info),    // nothing did
  onRecoverableError: (error, info) => warn(error, info),     // e.g. hydration mismatch
});

Testing in 2026

The consensus is stable and worth stating crisply: Vitest + React Testing Library for component and integration tests, Playwright for end-to-end, MSW for network mocking, and Storybook where a design system needs visual review. Jest is still everywhere and still fine; Vitest wins on speed and on sharing the Vite config. React 19 deprecated react-test-renderer and removed react-dom/test-utils, so act now comes from react itself — a mechanical but repository-wide change on upgrade.

Two testing positions worth defending at lead level. First, test behaviour through the DOM, not implementation: query by role and accessible name, which makes the test double as an accessibility check, and never assert on state or on a component's internals. Second, server components are hard to unit-test today — an async component is not something RTL renders — so the pragmatic split is to extract data-fetching and business logic into plain functions you test directly, and cover the rendered result with Playwright.

Gotcha — one error boundary is not a strategy

A single boundary at the root turns any component failure into a blank page. Real granularity mirrors the product: a boundary around each independently useful region — a widget, a panel, a route — so a failing recommendations carousel does not take down checkout. Pair each with a Suspense boundary at the same level, since the two answer "not ready" and "broken" for the same region. And give boundaries a reset path: resetKeys tied to the route or the record id, so navigating away actually clears the error instead of leaving the user stuck on a fallback forever.

What do error boundaries catch, and what do they miss?

They catch errors thrown during render, in lifecycle methods, and in constructors of components below them, plus — since React 19 — errors thrown from Actions and async transitions. They miss errors in event handlers, in setTimeout or requestAnimationFrame callbacks, in promise chains that are not part of a transition, in server-side rendering, and in the boundary component itself. The reason is that a boundary works by React catching a throw while it is on the stack during render; anything that escapes into the browser's own task queue is outside that. So a complete strategy is boundaries plus a global error and unhandledrejection listener plus explicit handling in handlers that can fail, all reporting to the same place.

Why does React unmount the whole tree on an uncaught error?

Because the alternative is leaving a partially updated, internally inconsistent UI on screen, and React cannot know whether that is safe for your product — showing a stale balance, an unrelated user's data, or a form that will submit garbage is worse than showing nothing. It was a deliberate change in React 16 alongside the introduction of error boundaries: React gives you a mechanism to decide the granularity, and if you decline to use it, it fails loudly rather than quietly. The lead-level framing is that the default is a forcing function — it makes "where should failures be contained?" a design decision you have to make explicitly, region by region.

Where do you place error boundaries in a real application?

I mirror the product's independent regions. One at the root as a last resort with a real error page and a reload path. One per route, so a broken page does not take out the shell and navigation. And one around each independently useful widget — a chart, a comments section, a third-party embed — because those are exactly the things that should degrade rather than take the page with them. Each boundary gets a fallback that is honest about what is broken and offers a retry, plus resetKeys tied to the route or record id so navigation clears the error. I place a Suspense boundary at the same points, because "loading" and "failed" are two answers to the same question about the same region.

What error handling did React 19 add at the root?

createRoot and hydrateRoot take onCaughtError, onUncaughtError and onRecoverableError. The first fires when an error boundary handled something, the second when nothing did and the tree is coming down, the third for problems React worked around — most importantly hydration mismatches. Before this, teams monkey-patched console.error to get errors into their telemetry, which was fragile and noisy. React 19 also stopped logging duplicate errors and improved the hydration error to a single message with a server-versus-client diff, plus owner stacks in development that show which component rendered the failing one rather than just the DOM ancestry. Wiring these three handlers is a fifteen-minute change with a large payoff in production visibility.

How do you test a React component well?

Render it and interact with it the way a user does: query by role and accessible name, click and type with userEvent, assert on what is visible. That makes the test resilient to refactors, since it does not know about state or component structure, and it doubles as an accessibility check — a button with no accessible name fails the test. I mock at the network boundary with MSW rather than mocking modules, so the test exercises the real data flow. What I push back on in review: snapshot tests of large trees, which nobody reads and everybody rubber-stamps; tests that assert on internal state; and shallow rendering, which tests the JSX you wrote instead of the UI it produces. End-to-end coverage goes to Playwright, deliberately thin and focused on critical paths.

How do you test server components?

Honestly: the unit-testing story is still weak, and I would say so rather than pretend. An async server component is not something React Testing Library renders, and the RSC payload is not a useful assertion target. The pragmatic approach is to keep server components thin — fetch, authorise, and compose — and to push anything worth testing into plain functions and client components that are testable normally. Then cover the rendered result with Playwright against a real running app, which is where the interesting failures live anyway: serialisation errors, boundary mistakes, streaming behaviour. If a team is heavily invested in RSC, I would also add contract tests around Server Functions, treating them as the HTTP endpoints they are.

What are the real XSS risks in a React app?

Three. dangerouslySetInnerHTML with content that is not sanitised — and sanitisation belongs where the HTML enters the system, with DOMPurify or a server-side sanitiser, not as a render-time afterthought. URL-valued props: href or src taking a javascript: or data: URL from user input, which React 19 warns about but does not block, so validate the scheme against an allowlist. And SSR state injection: serialising data into an inline <script> without escaping </script> and Unicode line separators lets an attacker break out of the string. Beyond those, a Content Security Policy is genuine defence in depth, and third-party scripts remain the largest practical risk in most apps because they run with full page privileges regardless of how careful your React code is.

How would you approach upgrading a large app from React 17 to 19?

In stages, with 18 as a real stop. First to 18 with the legacy root still in place, then flip to createRoot behind a flag or route by route, because automatic batching is where behavioural regressions show up. Then fix everything React 18's StrictMode and the console tell you: missing effect cleanups, unsafe lifecycles, string refs, findDOMNode. Only then to 19, which removes the legacy APIs entirely and needs the official codemods for forwardRef, Context.Provider, useFormState, propTypes and defaultProps on function components. Throughout, I would lean on the codemods rather than hand edits, land each stage separately so a rollback is cheap, and keep a canary of real traffic on each stage before it goes wide. The dependency graph is usually the long pole, not React itself — the libraries that never adopted concurrent-safe patterns.

What do you monitor in a React app in production?

Core Web Vitals from real users, INP above all, segmented by device class and route, because a lab number on a developer machine hides the problem entirely. JavaScript errors with component stacks, fed by the root error handlers and a global listener so handler errors are not invisible. Hydration mismatches specifically, via onRecoverableError, because they silently degrade SSR and nobody notices until LCP drifts. Bundle size per route as a trend, with a CI budget so a regression is caught before it ships. And a small number of product-level success metrics — did the form submit, did the page render content — because a page that renders a skeleton forever is technically error-free. The organisational point is that someone must own these numbers; unowned dashboards decay within a quarter.

A team wants to skip error boundaries because "we do not have errors". What do you say?

That the question is not whether errors happen but what the user sees when they do, and that React's default answer is a blank page. Then I would make it concrete rather than argumentative: pull the last quarter's error tracking, show how many render-phase exceptions occurred, and demo the blank-page failure on a staging build. The cost of the alternative is small — a shared boundary component, one per route and one per risky widget — and the benefit is that a third-party embed or a malformed API response degrades one region instead of the session. I would also point out the second-order win: boundaries are where you attach reporting with component stacks, so they turn "the app broke" tickets into a stack trace with an owner.

12 The big Q&A

Everything the core units do not cover: the ecosystem, rendering strategy, security, tooling, migration reality, and the judgment questions that decide a lead interview.

Architecture & ecosystem decisions

It is 2026 and you are starting a new React app. What do you pick, and why?

First I ask what the app is. A content or commerce site where SEO and first paint matter: Next.js App Router or React Router 7 in framework mode, both RSC-capable, both giving me streaming SSR, routing, and data loading as one story. A logged-in dashboard where none of that matters: Vite plus React Router in library mode plus TanStack Query, which is simpler to operate and does not require a Node server. Cross-platform: Expo, which is now the officially recommended way to start a React Native app. What I would not do is start from Create React App — it was formally sunset in February 2025 and the docs point elsewhere — and I would not hand-roll a webpack config. Whatever I pick, I would enable the React Compiler on day one and put a bundle budget in CI, because both are far cheaper to adopt at the start than retrofit.

What did the React Foundation change, and does it matter to an engineering team?

React moved out of Meta's sole governance into an independent React Foundation, announced at React Conf in October 2025 and formally hosted by the Linux Foundation on 24 February 2026, with member companies including Meta, Vercel, Microsoft, Amazon, Callstack, Expo and Software Mansion. Practically it means neutral ownership of the trademark, the domain and the infrastructure, and a governance model where a single company's product priorities cannot unilaterally steer the library. For a team making a five-year bet, that reduces a real risk — the same risk that drove the Node/io.js split and the OpenJS Foundation. Day to day nothing changes: the same core team still does the technical work, and the release cadence has been steady patch releases since 19.2.

When is React the wrong choice?

When the page is mostly static content with a few islands of interactivity, where Astro or plain HTML with a sprinkle of JavaScript ships a fraction of the bytes. When you need genuinely fine-grained reactivity at very high update frequency — a trading blotter, a live audio editor — where Solid or Svelte's compiled reactivity avoids re-running component functions at all. When the team is small and already fluent in something else, because framework familiarity beats framework theory. And when the deliverable is a widget embedded in other people's pages, where a 45 KB runtime is a hard sell against web components. I would also flag the honest counterweight: React's ecosystem, hiring pool and long-term support are unmatched, and those are legitimate architectural inputs, not a cop-out.

How do you choose between CSR, SSR, SSG and RSC for a given route?

Route by route, driven by two questions: does this content need to be indexable or fast on first paint for an anonymous user, and how personalised is it? Fully static and shared: SSG or a cached prerender, served from a CDN. Public but dynamic: SSR or RSC with streaming so the shell paints immediately. Personalised but still first-paint-sensitive: RSC with Suspense boundaries around the personalised parts, or 19.2's partial pre-rendering, where a cached static shell is resumed with dynamic content. Behind a login with no SEO requirement: client rendering is perfectly fine and cheaper to operate. The mistake I look for is applying one strategy to the whole app because it is the framework's default, when the cost profiles of the marketing pages and the dashboard are completely different.

How do you keep a large React codebase from rotting?

Boundaries and conventions, enforced by tools rather than by review comments. Feature-based folders with a public API per feature, and a lint rule (dependency-cruiser or eslint-plugin-boundaries) that forbids reaching into another feature's internals. A design system that owns the primitives so product code cannot invent a fifth button. TypeScript in strict mode, because the alternative is that every refactor is archaeology. The compiler's lint rules on, so purity violations do not accumulate. A bundle budget and a dependency review, because most bloat arrives one convenient package at a time. And a written decision log for the handful of architectural choices — state management, data fetching, styling — so new joiners inherit the reasoning and not just the code.

Security

What are the highest-value security controls for a React app?

A Content Security Policy that actually blocks inline script, which is the single biggest lever and the one most teams skip because their SSR setup inlines state. Sanitising any HTML that reaches dangerouslySetInnerHTML, at ingestion rather than at render. Validating URL-valued props against a scheme allowlist. Treating every Server Function as a public endpoint with its own authn, authz and input validation. Keeping secrets out of anything that crosses the server/client boundary, including closures captured by Server Functions. And dependency hygiene with automated alerts — the December 2025 RSC CVEs sat in react-server-dom-* packages that most teams do not list directly, which is exactly how a patch gets missed. Beyond that, third-party scripts are the largest practical risk in most apps, because they execute with full page privileges no matter how careful your own code is.

How do you store authentication tokens in a React app?

Preferably not in JavaScript at all. An HttpOnly, Secure, SameSite cookie set by the server is the safest default, because it is unreachable from script and therefore not exfiltrable by an XSS payload; the trade is that you need CSRF protection, which SameSite=Lax plus a token covers. localStorage is the common alternative and is readable by any script on the origin, so it converts any XSS into full account takeover — I would only accept it with a clear-eyed threat model and a strict CSP. In-memory storage with a refresh cookie is a reasonable middle ground for SPAs. With RSC the calculus improves, because sessions can be read on the server and never reach the client at all, which is one of the underrated security arguments for it.

A dependency you rely on gets a CVE. Walk me through your response.

Establish exposure before urgency: which versions we run, whether the vulnerable code path is reachable in our usage, and whether it is client or server side. Then patch — usually a version bump — and verify the fix actually covers our case, because the React RSC advisories in December 2025 are the cautionary tale: an earlier patch released a week before did not fix the later CVEs, so a team that had already bumped once was still vulnerable. Deploy through the normal pipeline unless severity justifies an out-of-band release, and confirm in production rather than trusting the lockfile. Afterwards, the retrospective question is how we would have found out without the news cycle — which usually means fixing dependency alerting to cover transitive packages, and adding the framework's own security channel to whatever the on-call team reads.

Performance & debugging

INP regressed after a release. How do you find the cause?

Start with field data segmented by route and device, because INP is dominated by the slowest interactions on the slowest hardware and an average hides it. Identify which interaction and which route regressed, then reproduce locally with CPU throttling and record the Performance panel, using React 19.2's Scheduler and Components tracks to see whether the time is in React render, in commit, or in something else entirely. Split the number into input delay, processing and presentation delay: input delay points at work already running when the user clicked, processing at your handler and render, presentation at layout, paint or a huge DOM. Then check the release diff for the usual suspects — a new synchronous handler, a context value that started changing, a list that lost its virtualisation, a third-party script. The discipline is to attribute the number before changing code.

A page has a fast Time to First Byte but a slow LCP. What do you look at?

Everything between the first byte and the largest element painting. Render-blocking resources first — synchronous scripts and non-critical CSS in the head. Then the LCP element itself: if it is an image, is it discoverable in the initial HTML, is it preloaded, is it the right format and size, does it have fetchpriority="high". Then hydration: in a client-rendered or heavily hydrated page, the largest element may not exist until a large bundle has downloaded, parsed and run, in which case the fix is shipping less JavaScript — code splitting, server components, or moving the hero out of a client boundary. Font loading is a frequent hidden cause via font-display. And in an SSR app, check whether a hydration mismatch is silently forcing a client re-render of that subtree, which onRecoverableError will tell you.

How do you debug "this component re-renders and I do not know why"?

React DevTools Profiler with "Record why each component rendered" turned on gives you the reason directly: props changed and which one, state changed, context changed, or the parent rendered. That single setting resolves most of these questions in under a minute, and the answer is usually a context value or a prop whose identity is fresh every render. For a stubborn case, the why-did-you-render library logs the specific prop diffs, and a plain useEffect logging changed dependencies works when you want something in CI-visible output. Then the actual question is whether it matters: a re-render of a cheap subtree is not a bug, and I would want a measurement before anyone adds memoization. Since 19.2 the Chrome DevTools Components track is often the better first look, because it puts the render in the same timeline as the interaction that caused it.

What are the most common React memory leaks?

Subscriptions and timers without cleanup — the effect that adds a listener, opens a socket, or starts an interval and never removes it, so every mount adds another. Third-party library instances (charts, maps, editors) initialised in an effect without a destroy call. Closures captured in long-lived module-level structures, such as a cache keyed by component instance that nothing ever evicts. Refs holding DOM nodes for elements that have been removed, which the React 19 ref cleanup form fixes properly. And detached DOM retained by an observer that was never disconnected. The practical detection loop is Chrome's Memory panel: take a heap snapshot, navigate back and forth between two routes several times, snapshot again, and look at the retained-size delta and the detached nodes. StrictMode's double-invoke catches many of these in development, which is a large part of why it exists.

Tooling & TypeScript

How do you type React well without fighting TypeScript?

Type props as an explicit interface and let return types be inferred; React.FC is unnecessary now that it no longer implies children, and being explicit about whether a component takes children is better documentation. Use PropsWithChildren or declare children: React.ReactNode deliberately. For components that wrap DOM elements, extend the element's props — ComponentPropsWithRef<'button'> — so every native attribute passes through without an escape hatch. Prefer discriminated unions over optional-everything props, because they encode the states a component actually has and make invalid combinations unrepresentable. Note that React 19 removed propTypes and defaultProps for function components, so default values live in destructuring. And keep strict on; the codebases where TypeScript feels like a tax are usually the ones where it is half-enabled.

Vite, Next.js, or something else — how do you frame the build-tool decision?

The decision is really "do I want a framework or a bundler". Vite is the bundler answer: fast, unopinionated, and now the default recommendation for SPAs, with an RSC plugin if you want server components without adopting a full framework. Next.js is the framework answer and brings routing, data loading, caching, image handling and deployment conventions, at the cost of coupling to its model and, for many teams, its hosting story. React Router 7 in framework mode and TanStack Start are the credible middle: framework features with a lighter opinion set. Webpack is legacy for new work but still runs enormous amounts of production code and is not urgent to replace. What I would push on in an interview answer is that "which bundler" is far less consequential than the routing and data-fetching model it implies, and that is what the team will live with.

How do you approach styling in a React app in 2026?

The runtime CSS-in-JS era is over for new work: styled-components and Emotion inject styles at runtime, which conflicts with RSC and streaming and costs measurable time on every render. The durable options are plain CSS Modules, which every bundler supports and which have zero runtime; Tailwind, which most teams end up on for velocity and for constraining the design space; and zero-runtime CSS-in-JS like vanilla-extract or Panda if you want typed styles compiled at build time. React 19's precedence attribute on <link rel="stylesheet"> makes deterministic ordering possible for dynamically loaded styles, which used to be the hardest part. For an existing app on styled-components I would not do a big-bang migration; I would freeze new usage, migrate on touch, and prioritise the routes where SSR performance actually matters.

Legacy & migration reality

What legacy React patterns will you still find, and what do you do about them?

Class components with lifecycle methods, which work fine and are not worth converting for their own sake — convert when you are changing the file anyway, or when it needs a hook-based capability. Higher-order components and render props, superseded by hooks but still all over older libraries; they compose badly and produce the wrapper-hell you see in DevTools. componentWillMount, componentWillReceiveProps and string refs, which are genuinely unsafe under concurrency and should be fixed. Redux with hand-written action types and thunks, which Redux Toolkit modernises without a rewrite. And defaultProps and propTypes on function components, which React 19 removed and which need the codemod. My rule is that legacy patterns get fixed when they block something or when they are unsafe, not on aesthetics.

Class components — what can they still do that hooks cannot?

Exactly one thing: be an error boundary, which needs getDerivedStateFromError and componentDidCatch. Everything else has a hook equivalent, sometimes with a different shape — getSnapshotBeforeUpdate maps onto useLayoutEffect reading before the commit, and instance fields map onto refs. React has said classes are not deprecated and will not be removed, so there is no urgency, and I would resist a blanket "convert everything" project: the conversion is a behaviour-changing refactor, especially around lifecycle-to-effect mapping, and the payoff is usually consistency rather than correctness. Where I do push for conversion is any component still using the unsafe lifecycles, because those are actively incompatible with concurrent rendering.

How do you migrate from a home-grown state layer to something modern without a freeze?

Strangler pattern. Define the new boundary first — say, server data moves to TanStack Query and UI state stays in context — and write it down so people stop arguing case by case. Then pick one vertical slice, migrate it end to end, and use it as the reference implementation, including tests. New features use the new pattern from that point; old code migrates when it is touched for another reason, which spreads the cost across normal work. Keep a bridge so both layers can coexist — usually a thin adapter that reads from either — and delete it as a tracked task, because the failure mode of every incremental migration is a permanent halfway state. I would also put a number on it: percentage of routes migrated, reviewed monthly, so the work stays visible against feature pressure.

How do you keep React and its ecosystem up to date without a quarterly panic?

Automated dependency PRs with grouped, scheduled batches so upgrades are routine rather than events, and a test suite trustworthy enough that a green build is real evidence. Majors get treated as projects with a written plan, a canary, and a rollback, not as a Renovate PR someone merges on a Friday. I keep a short list of the dependencies that are load-bearing — React, the framework, the router, the state and data layers — and read their release notes, because those are the ones where a major has architectural implications. I also track the ones that are unmaintained, since a stale dependency is what blocks the React upgrade two years later. And I make sure security advisories for transitive packages reach a human, which is the specific gap the December 2025 RSC CVEs exposed for a lot of teams.

Judgment & scenarios

How would you introduce Server Components to a skeptical team?

By starting with their objection rather than my enthusiasm. The objections are usually real: it needs a framework, it splits the mental model, it means operating a server, and debugging spans two runtimes. So I would pick a metric the team already cares about — bundle size on the marketing routes, LCP on the product pages — and propose one route as an experiment with an explicit rollback. I would timebox it, do it with two people rather than alone so the knowledge is not siloed, and present the result as a number plus an honest list of what was annoying. If the number does not move, we do not adopt it, and saying that up front is what makes the experiment credible. The failure mode I would explicitly avoid is a top-down migration mandate, which produces a half-converted codebase and a team that resents it.

What do you look for in a React code review, in priority order?

Correctness of the data flow first: is state in the right place, is anything derived being stored, do the effects have honest dependencies and symmetric cleanups. Then boundaries: does this component do one thing, is a client boundary being drawn wider than necessary, does a new context have a single reason to change. Then user-facing quality that is easy to forget — loading and error states, accessible names, keyboard behaviour, layout stability. Then security if the change touches HTML, URLs or a server endpoint. Performance last, and only with a measurement, because unmeasured optimisation is the most common way to make a codebase worse. I try to distinguish blocking comments from preferences explicitly, because a review where everything sounds equally important teaches people to skim.

A junior engineer's PR works but the design is wrong. How do you handle it?

I separate the ship decision from the teaching. If it works, is contained, and is not a pattern others will copy, I would often merge it and open a follow-up, because blocking a working PR over design taste burns goodwill and slows people down. If it establishes a pattern — a new context, a new data-fetching approach, a new abstraction others will imitate — then it matters enough to fix now, and I would pair on it rather than leave twelve comments, because the design reasoning is not something a review thread conveys well. Either way I would explain the failure mode I am worried about in concrete terms — "this effect will refetch on every keystroke when we add the filter next sprint" — rather than asserting a rule, because the goal is that they can make the call themselves next time.

Production is down and the error is a React hydration failure. Walk me through the incident.

Mitigate first: if a recent deploy correlates, roll back, because a hydration failure means the page is being re-rendered on the client at best and blank at worst. While that runs, get the actual error — React 19's hydration errors include a server-versus-client diff, so the offending element is usually identifiable within minutes, and onRecoverableError in the tracker gives you the frequency and the affected routes. The usual causes are non-deterministic render output, a locale or timezone difference between server and client, invalid HTML nesting, or a third party injecting into the DOM. Then decide whether it is universal or environment-specific — if it only affects one region or one browser extension, the mitigation is different. Afterwards: a regression test on the specific route, and the broader question of why a hydration mismatch reached production, which usually means the recoverable-error handler was not wired to alerting.

How do you decide when an abstraction is worth creating?

My default is to wait for the third occurrence, because two similar things are frequently a coincidence and the abstraction you extract from two examples usually encodes the wrong axis of variation. When I do extract, I look for whether the duplicated thing is the same decision or merely the same shape — two forms that look alike but change for different reasons should stay separate. The cost side matters too: an abstraction with five boolean props and three escape hatches is worse than the duplication it replaced, and in React specifically, composition through children and element props usually beats configuration through props. The signal that I got it wrong is a stream of PRs adding options to the same component, at which point the right move is to un-abstract rather than add the sixth flag.

How do you keep a team current with React without chasing every release?

I separate what we must track from what is interesting. Must track: React's own releases and security advisories, the framework, and the handful of load-bearing libraries — someone reads those release notes and summarises the implications. Interesting: everything else, which belongs in a low-pressure channel and does not create work. I like a small, regular forum — a half-hour every couple of weeks where someone presents something they actually used, not something they read about — because it filters hype through experience. Adoption decisions get an explicit lightweight record: what problem, what we tried, what we decided. And I try to be the person who says "not yet" out loud, because the failure mode in React teams is not falling behind, it is adopting three half-understood things at once and then owning all of them.

13 Night-before cheat sheet

Ten sentences to say out loud until they are yours. Every one is defensible and current as of 2026-09-08.

  1. State of the art. "React 19.2 is the current feature release, from October 2025; 19.2.8 in July 2026 is the newest patch. Since 19.0 the big three are Actions, stable Server Components, and use — and 19.2 added <Activity>, useEffectEvent, cacheSignal and Chrome DevTools performance tracks."
  2. The model. "A component is a pure function from props and state to a description of UI. React does trigger, render, commit; only commit touches the DOM, and render must be pure because React may run it twice, discard it, or interrupt it."
  3. Identity. "State lives on the fiber, and a fiber is identified by type, key and position among siblings. That is why changing a key resets state, why index keys attach state to the wrong row, and why defining a component inside another one destroys its state every render."
  4. Effects. "useEffect is synchronization with an external system, not a lifecycle. If there is no external system, the effect probably should not exist — derived data belongs in render, event responses in handlers, and resets in a key."
  5. StrictMode. "The double-invoke in development is a test that your effects are re-runnable, which real remounts and <Activity> demand. The fix for a failure is a cleanup or idempotency, never a ref guard."
  6. Concurrency. "Concurrent React means interruptible rendering with priorities, not threads. It improves responsiveness, measured as INP, not throughput — and it is why external stores must be read through useSyncExternalStore to avoid tearing."
  7. RSC vs SSR. "SSR is about when the first HTML appears; Server Components are about what code ships at all. RSC runs once on the server, emits a serialisable payload rather than HTML, and its code never enters the bundle — and 'use client' marks a module boundary, not a component."
  8. Actions. "React 19 turned every mutation's four parts — pending, error, optimistic, result — into useActionState, useFormStatus and useOptimistic. And a Server Function is a public HTTP endpoint, so it authenticates, authorises and validates on its own."
  9. Performance. "React Compiler 1.0 shipped in October 2025 and memoizes automatically at a finer grain than a human would — Meta measured up to 12% faster loads and interactions over 2.5× faster. So manual useMemo is now something you delete; the real levers are still shipping less JavaScript, virtualising long lists, and fixing identity churn."
  10. Judgment. "Error boundaries go around every independently useful region, because React's default for an uncaught render error is to unmount the whole tree. And in December 2025 the RSC packages had their first real CVEs — a DoS and a Server Function source-code exposure, fixed in 19.2.3 — which is the reminder that the server boundary is an attack surface, not a free trust boundary."
