Redis (for .NET developers)

interview · Redis 8.10.1 · released 2026-08-17

Redis interviews for a lead or principal engineer rarely stay in command-syntax territory for long: screeners check that you know a hash from a sorted set, but the loop is really testing whether you understand that Redis is a single-threaded, in-memory, asynchronously-replicated store, and whether you can reason about what that buys you and what it costs under failure — a stalled BGSAVE fork, a network partition during a failover, a hot key that a whole Cluster slot cannot absorb. For a .NET-leaning candidate expect a second axis entirely: StackExchange.Redis's connection-multiplexing model, the sync-over-async deadlock that has taken down more than one ASP.NET app, and the cache-aside race conditions that only show up under load. Work down the map in frequency order — data structures, caching patterns, persistence and replication carry most of the loop — then use Judgment calls and Design exercises to rehearse the open-ended questions that senior loops actually decide on. Everything here is dated against Redis 8.10.1 (17 Aug 2026): the most recent citable fact worth having ready is CVE-2026-62356 and its sibling fixes in that release, including an RDB-loading path that could reach remote code execution and a TLS client-certificate check that a NUL byte in the Common Name could bypass — both patched the same day across every supported branch back to 6.2.

01Core data structures & commands

This is where every Redis loop starts: can you pick the right structure for a shape of data, and do you know the commands well enough to reach for the right one under pressure. Screeners check string/hash/list/set/sorted-set recall; mid-level candidates are expected to justify a choice against alternatives; senior+ candidates get asked about the operational landmines (KEYS, unbounded collections, encoding transitions) that only show up at scale. Docs: redis.io/docs/latest/develop/data-types.

screenerWhat are Redis's core data types, and how do you decide between them for a new key?

Answer

Redis's core types are String (binary-safe blob, up to 512MB — text, JSON, counters, serialized objects), Hash (field→value map, ideal for an object's attributes), List (ordered, doubly-linked-list-like sequence, ideal for queues/timelines), Set (unordered unique collection, ideal for membership tests and set algebra), Sorted Set / ZSet (unique members ranked by a floating-point score, ideal for leaderboards and range queries), Stream (append-only log with consumer groups), and the newer Bitmap, HyperLogLog, Geospatial index, JSON, Bloom/Cuckoo filter, and Vector Set types layered on top. The decision usually comes down to the access pattern you need, not the data's shape: if you need "give me the top N by score," reach for a ZSet even if the data looks like a list; if you need field-level partial reads/writes on an object, reach for a Hash instead of serializing the whole thing into a String.

Example

# object as a hash - partial field access without deserializing the whole thing
HSET user:1001 name "Ana" plan "pro" logins 42
HINCRBY user:1001 logins 1
HGET user:1001 plan

Follow-ups

  • Why not just store the object as a JSON string? — You'd pay full serialize/deserialize cost for any single-field read or update, and lose atomic per-field operations like HINCRBY.
  • When would you reach for the native JSON type instead of a Hash? — When the object is genuinely nested (arrays of sub-objects, variable schema) rather than flat key-value attributes.
  • What's the size ceiling that changes your answer? — A String value tops out at 512MB; large blobs (images, big blobs) usually don't belong in Redis at all regardless of type.

Common wrong answer

Naming the five classic types correctly but describing them purely by API shape ("a list is like a linked list") with no mention of access pattern — which signals command memorization without design judgment.

screenerWhat's the difference between SET key val EX 30 and running SET then EXPIRE separately?

Answer

They look equivalent but aren't atomic the same way: two separate commands leave a window between them where the key exists with no TTL — a crash, a network blip, or another client reading in between can observe or leave behind a key that never expires. SET key val EX 30 sets the value and the expiry as a single atomic operation, so there's no window at all. This matters most for cache-population code and for any lock or lease pattern, where a key that "leaks" its TTL turns into a permanent stale entry or a lock that's never released.

Example

SET session:abc "{...}" EX 1800 NX   # set only if absent, 30-minute TTL, atomically

Follow-ups

  • What do the NX/XX/GET options add? — NX sets only if absent (lock acquisition), XX only if present (refresh-only), GET returns the old value atomically alongside the write.
  • Does SET without any TTL option clear an existing TTL? — Yes, a plain SET replaces the whole key including any TTL, unless you add KEEPTTL.
  • How would you extend a lock's TTL without risking a race? — Use SET ... XX KEEPTTL-style refresh guarded by ownership token via a small Lua script, never a bare EXPIRE.

Common wrong answer

"They're the same, just fewer round trips" — missing that the atomicity, not the latency, is the real reason the combined form exists.

midWhen do you reach for a Sorted Set instead of a List or a Set?

Answer

A Sorted Set is the right tool whenever "unique members, ordered by some numeric value, with efficient range queries" describes the problem: leaderboards (score = points), priority queues (score = priority or due-timestamp), rate limiters (score = request timestamp, trimmed with ZREMRANGEBYSCORE), and delayed-job schedulers (score = run-at epoch, polled with ZRANGEBYSCORE ... LIMIT). Internally it's a skip list plus a hash table, so membership checks, score updates, and rank/range queries are all logarithmic, which a plain List can't give you — a List only supports positional access and has no notion of uniqueness or ordering-by-value. Use a Set instead when you only need membership and don't care about order or a score at all.

Example

ZADD leaderboard 4210 "player:7"
ZADD leaderboard 3980 "player:2"
ZREVRANGE leaderboard 0 9 WITHSCORES   # top 10

Follow-ups

  • How would you build a sliding-window rate limiter with a ZSet? — Score each request by its timestamp, ZREMRANGEBYSCORE everything older than the window on each check, then ZCARD against the limit.
  • What happens with duplicate scores? — Members are still unique and ties are broken by lexicographic member order, which matters for pagination stability.
  • Why not use a database index for the leaderboard instead? — You'd pay a query round trip and lose O(log N) live rank lookups (ZRANK) that Redis gives you essentially for free in memory.

Common wrong answer

Reaching for a List and re-sorting client-side on every read — works at small scale, then falls over as an O(N log N) operation on every request once the collection grows.

midWhat are the blocking list commands for, and what's the trap when using them for a work queue?

Answer

BLPOP/BRPOP block a client until an item appears on one of the given lists (or a timeout elapses), which turns a List into a simple, low-latency work queue without polling. BLMOVE (the modern replacement for the deprecated BRPOPLPUSH) atomically pops from one list and pushes onto another, which is what you actually want for reliable queues: a worker moves the job into a "processing" list first, so if the worker crashes mid-job the item isn't lost, it's just sitting visibly in the processing list for a reaper to reclaim. The trap is treating a bare BLPOP as durable: if the worker pops and then crashes before finishing, that job is gone — no in-flight state, no redelivery, no acknowledgment concept, which is exactly the gap Streams' consumer groups exist to close.

Example

BLMOVE jobs:pending jobs:processing LEFT RIGHT 5
# ... do the work ...
LREM jobs:processing 1 "job:123"   # remove once confirmed done

Follow-ups

  • Why is BRPOPLPUSH deprecated in favour of BLMOVE? — BLMOVE generalizes the direction (LEFT/RIGHT on both ends) instead of hard-coding one queue discipline.
  • What happens if two workers BLPOP the same list simultaneously? — Redis is single-threaded for command execution, so exactly one worker gets each item — no double delivery at that layer.
  • When would you reach for Streams instead of a blocking List queue? — When you need acknowledgment, redelivery of crashed consumers' work, multiple independent consumer groups, or replay from history.

Common wrong answer

Claiming a plain List-based queue with BLPOP is "just as reliable as a message queue" because Redis is durable — ignoring that durability of storage says nothing about at-least-once delivery to a specific consumer.

midYour KEYS user:* call froze production for two seconds. What happened and what should have been used?

Answer

KEYS does a full O(N) scan of the entire keyspace in one shot and, because Redis's command execution is single-threaded, every other client is blocked for the whole scan — on a large keyspace that's easily seconds of total unavailability. SCAN (and its type-specific siblings HSCAN/SSCAN/ZSCAN) does the same logical traversal but incrementally: each call does a small bounded amount of work and returns a cursor to resume from, so the keyspace stays responsive between calls. The trade-off is weaker consistency guarantees — SCAN guarantees every key present for the whole scan's duration is returned at least once, but keys added or removed mid-scan may or may not appear, and duplicates are possible, which is a fine trade for an operational tool but not a substitute for a real index if you need exact set semantics.

Example

SCAN 0 MATCH "user:*" COUNT 100
# returns a cursor and a batch; keep calling with the returned cursor until it's 0

Follow-ups

  • Does MATCH reduce the work SCAN does? — No, filtering happens after the same amount of internal traversal per call; it only reduces what's returned, not the cost.
  • Is SCAN safe to run against a Cluster? — Yes per-node, but you must scan every shard and merge cursors per node — client libraries like StackExchange.Redis's IServer.Keys() do this for you.
  • What about FLUSHALL or DBSIZE — do they share the same blocking risk? — DBSIZE is O(1) and safe; FLUSHALL/FLUSHDB can be made non-blocking with the ASYNC keyword since Redis 4.0.

Common wrong answer

"Use SCAN because it's faster" — it isn't faster in total, it's the same total cost spread out non-blockingly; the fix is about availability, not throughput.

midHow does a HyperLogLog let you count billions of unique items in 12KB, and what do you give up?

Answer

PFADD/PFCOUNT implement the HyperLogLog algorithm: instead of storing every distinct element, it hashes each element and keeps statistical registers tracking the pattern of leading zeros seen, from which the cardinality can be estimated. The structure is fixed at roughly 12KB regardless of whether you've added a thousand or a billion elements, with a standard error around 0.81%. What you give up is exactness and enumerability — you can't ask "which items were counted," only "how many distinct items," and two different counts run at different times can disagree slightly even against the same underlying set due to the probabilistic estimate.

Example

PFADD daily:2026-09-08 "user:1001" "user:1002" "user:1001"
PFCOUNT daily:2026-09-08   # 2, the duplicate doesn't double-count
PFMERGE weekly daily:2026-09-01 daily:2026-09-02 daily:2026-09-08

Follow-ups

  • What's PFMERGE for? — Combining several HyperLogLogs (e.g. daily unique-visitor counters) into one without re-processing raw events, ideal for rollups.
  • When is 0.81% error unacceptable? — Billing or fraud thresholds where an exact count is a compliance requirement — use a Set or an external exact counter there instead.
  • Can you use HyperLogLog for real-time dashboards at scale? — Yes, that's its best fit: approximate unique counts (visitors, distinct IPs) where trend matters more than the exact last digit.

Common wrong answer

Describing HyperLogLog as "a Set that's more memory-efficient" — it isn't a Set at all, it can't tell you membership or list members, only estimate cardinality.

seniorWhat's the difference between EXPIRE, PEXPIRE, EXPIREAT, and PERSIST, and where do TTL bugs actually come from?

Answer

EXPIRE takes a relative TTL in seconds, PEXPIRE the same in milliseconds, EXPIREAT/PEXPIREAT take an absolute Unix timestamp instead of a duration — useful when you want a key to die at a specific wall-clock moment (end of billing period) rather than N seconds from "whenever this code happened to run." PERSIST removes a TTL entirely, turning a volatile key permanent. Real TTL bugs are almost never about these commands' semantics; they come from a plain SET silently clobbering an existing TTL (fixable with KEEPTTL), from computing the TTL from a wall-clock time on a host with clock drift, or from expiring keys that a replica is still relying on because expiry logic runs differently there (see the replication unit).

Example

SET counter 0
SET counter 1 KEEPTTL   # keeps the previous TTL instead of clearing it
TTL counter

Follow-ups

  • How does Redis actually remove expired keys — immediately at the microsecond of expiry? — No: lazily on access (a read checks and deletes if expired) plus an active background cycle that samples keys periodically; see the persistence/memory units for the mechanics.
  • What does TTL return for a key with no expiry? — -1; it returns -2 if the key doesn't exist at all — candidates often confuse these two.
  • Can you set a TTL shorter than the code's own clock skew tolerance safely? — Only if you're deliberately treating Redis-side expiry as a backstop rather than the source of truth for time-sensitive logic.

Common wrong answer

Believing expired keys vanish from memory the instant their TTL elapses — the actual mechanism (lazy + active-cycle deletion) is why a fully idle expired key can still show up in DBSIZE briefly, which surprises people debugging memory numbers.

seniorWhat does OBJECT ENCODING tell you, and why does an interviewer care whether you check it?

Answer

Every core type has more than one internal representation, chosen automatically based on size: a small Hash/List/Set is stored as a compact listpack (a flat, memory-dense encoding), and once it crosses a configured threshold (hash-max-listpack-entries, -value, and the List/Set equivalents) Redis converts it to a hashtable/quicklist/skiplist-backed representation that's slower per-op but scales. OBJECT ENCODING key reveals which one you're currently on, and interviewers care because the transition is one-way in practice (a hash that grows big and shrinks back stays in the expensive encoding) and because tuning those thresholds is a real, low-risk memory optimization lever for workloads with many small collections. A candidate who's used it has actually debugged a memory or latency issue in production, not just read the docs.

Example

OBJECT ENCODING user:1001   # "listpack" while small
CONFIG GET hash-max-listpack-entries
# grow past 128 entries (default) and it becomes "hashtable"

Follow-ups

  • Why doesn't the encoding downgrade back to listpack after deletions? — Redis avoids the churn/cost of re-checking and re-encoding on every shrink; it only encodes upward, never back down.
  • What's the practical risk of raising the listpack thresholds too high? — Every operation on a large listpack-encoded collection becomes O(N) instead of O(1)/O(log N), so a "small collection" optimization backfires once collections grow past what you tuned for.
  • Does this matter for Redis 8's compact hashes? — Compact hashes (8.10) are a separate optimization sharing field-name schemas across many hash values with the same shape — complementary to, not a replacement for, the listpack/hashtable transition.

Common wrong answer

Treating all Hashes/Sets/Lists as uniform O(1) structures with no mention of encoding — which falls apart the moment the interviewer asks "what happens once this collection has ten thousand entries?"

seniorHow would you model a many-to-many "tags on posts" relationship using Redis Sets?

Answer

Model it bidirectionally with two Set families: post:{id}:tags holding the tags on a post, and tag:{name}:posts holding the posts under a tag — a classic inverted-index pattern that trades a little write duplication for O(1)-ish reads in both directions. Set algebra commands do the interesting queries for free: SINTER tag:redis:posts tag:dotnet:posts finds posts tagged with both, SUNION finds posts tagged with either, and SDIFF finds posts tagged with one but not the other — all computed server-side without pulling data into the client. The trade-off to name is fan-out on writes (adding/removing a tag touches two keys, so wrap it in a MULTI or Lua script for atomicity) and that this pattern doesn't scale gracefully to tags with millions of members without also considering Cluster hashing, since SINTER across differently-sharded keys requires them to land in the same slot (see the Cluster unit's hash-tag pattern).

Example

SADD post:501:tags "redis" "dotnet"
SADD tag:redis:posts "post:501"
SADD tag:dotnet:posts "post:501"
SINTER tag:redis:posts tag:dotnet:posts

Follow-ups

  • How do you keep the two sides consistent? — Either a Lua script doing both SADDs atomically, or a MULTI/EXEC transaction if no read-then-write logic is needed in between.
  • What if a tag has ten million posts and you need pagination? — Sets have no stable ordering for pagination; switch that side to a Sorted Set scored by post-id or timestamp and use ZRANGE.
  • Would SINTERCARD help here? — Yes, for "how many posts share both tags" without materializing the full intersection, and it supports a LIMIT to cap cost.

Common wrong answer

Storing tags as a comma-joined string field on the post and doing tag lookups by scanning all posts client-side — throws away exactly the set-algebra capability that makes Redis a good fit for this problem.

seniorWhat are Redis's bit-level commands actually used for in production?

Answer

SETBIT/GETBIT/BITCOUNT/BITOP treat a String as a raw bit array, which is a strikingly compact way to track boolean state per ID: a "user did X today" bitmap addressed by user-id as the bit offset costs one bit per user rather than one key per user, so a hundred million users fits in ~12MB. BITOP AND/OR/XOR (and, since 8.2, DIFF/DIFF1/ANDOR/ONE for richer set-like bit operations without a round trip) let you compute "active both yesterday and today" across two daily bitmaps directly in Redis. BITFIELD goes further, letting you pack multiple small counters (a 4-bit or 8-bit field per record) into one string for compact multi-counter storage, at the cost of readability and no native TTL per sub-field.

Example

SETBIT active:2026-09-08 1001 1
SETBIT active:2026-09-07 1001 1
BITOP AND active:both active:2026-09-08 active:2026-09-07
BITCOUNT active:both

Follow-ups

  • What's the catch with bitmaps at very large offsets? — The string grows to cover the highest bit offset used, so a sparse ID space (e.g. random 64-bit ids used directly as offsets) wastes enormous memory — hash or remap IDs to a dense range first.
  • Would a Bloom filter be a better fit for "has this been seen before"? — Yes for probabilistic membership across a huge unbounded set; bitmaps are best when the offset space is naturally dense and bounded (user ids, day-of-year).
  • What's BITPOS for? — Finding the first set/unset bit, useful for scanning a bitmap for the next available slot in a bounded allocation scheme.

Common wrong answer

Using a bitmap keyed directly by a random UUID-derived offset "for efficiency" — this is the sparse-offset trap that turns a supposedly compact structure into a multi-gigabyte string.

seniorHow do you design key names for a multi-tenant Redis deployment, and what goes wrong when you don't?

Answer

The convention that scales is a colon-delimited hierarchy with the tenant first — tenant:{id}:resource:{id}:field — because it makes per-tenant operations (bulk expiry, per-tenant memory accounting via MEMORY USAGE sampling, per-tenant rate limiting) tractable, and because on Cluster it lets you deliberately colocate a tenant's keys with a hash tag ({tenant:42}:orders) so multi-key operations for that tenant land on one shard. What goes wrong without a convention: keys collide across tenants when naming is ad hoc, there's no way to answer "how much memory does tenant X use" without a full scan, and a noisy-neighbor tenant's hot keys aren't distinguishable from anyone else's without the naming discipline to filter by. The trade-off to name unprompted is that hash-tagging for colocation concentrates a tenant's load on one shard — great for locality, bad if one tenant is disproportionately large, which reintroduces the hot-shard problem the whole scheme was meant to avoid.

Example

SET "{tenant:42}:config:theme" "dark"
LPUSH "{tenant:42}:jobs:pending" "job:9001"
# both keys hash on "tenant:42" only, so they always land on the same Cluster shard

Follow-ups

  • How would you enforce per-tenant memory budgets? — Redis has no native per-key-prefix quota; you'd sample with MEMORY USAGE, track it externally, or run genuinely noisy tenants in a separate logical database or instance.
  • Would separate logical databases (SELECT) be a good isolation mechanism? — Not recommended in Cluster mode (unsupported) and even standalone it doesn't isolate CPU/memory contention, only namespace.
  • What ACL angle does key naming enable? — Pattern-based ACL key permissions (~tenant:42:*) so a per-tenant credential can be scoped to only that tenant's keyspace.

Common wrong answer

"Just prefix every key with the tenant id" with no mention of Cluster hash-tag colocation or the hot-shard trade-off it introduces — a naming answer with no operational consequence attached.

principalA single very large collection key (a Hash with 40 million fields) is causing latency spikes cluster-wide. Walk through the diagnosis and the fix.

Answer

Diagnose with redis-cli --bigkeys or MEMORY USAGE plus SLOWLOG: a single command touching millions of fields (a full HGETALL, or even the background rehashing when a hashtable-encoded Hash grows) runs on Redis's single command-execution thread and blocks every other client for its whole duration — that's the mechanism behind "one huge key causes cluster-wide latency" even though only one shard actually holds the key. The fix is almost always to shard the logical entity across many physical keys — e.g. HSET user:{id % 1000}:profiles field ... — so no single Redis-level key ever grows unbounded, restoring O(1)/O(log N) per-op cost and spreading the memory (and the Cluster slot placement) across many keys instead of one. The trade-off to name unprompted: this makes any "read everything for this logical collection" query fan out across N keys client-side (or via a Lua script), trading one big blocking call for many small non-blocking ones — a straight win operationally, at the cost of a bit more application complexity.

Example

redis-cli --bigkeys
# *** Biggest hash found: 'sessions:all' has 41,203,880 fields
# fix: bucket - HSET "sessions:shard:{n}" <session_id> <payload>

Follow-ups

  • Why does one big key cause "cluster-wide" latency and not just latency on its own shard? — Anything waiting on a response from that blocked shard (including cross-shard operations and client connection pools shared across requests) backs up, and monitoring/alerting often surfaces it as a general slowdown.
  • Would switching that Hash to RedisJSON or a compact-hash encoding fix it? — No — those change memory layout, not the O(N) cost of a full-key scan/read; the fix is architectural sharding, not encoding.
  • How do you catch this before production, not after? — SLOWLOG thresholds, redis-cli --bigkeys in CI/staging against production-shaped data, and a hard code-review rule against unbounded collection growth on a single key.

Common wrong answer

Reaching straight for "add more replicas" or "upgrade the instance size" — throughput scaling doesn't fix a single-threaded blocking operation on one oversized key; only reducing that key's per-op cost does.

02Caching patterns & invalidation

Caching is the single most common reason Redis is in the stack at all, so this is where loops spend real time: not "what's SET" but "what happens when the cache and the database disagree." Screeners check cache-aside mechanics; senior+ candidates are expected to reason about stampedes, staleness windows, and invalidation strategy under concurrent writers. Docs: redis.io/docs/latest/develop/use/patterns.

screenerWalk through cache-aside (lazy loading) end to end.

Answer

On read: check Redis first; on a hit, return the cached value; on a miss, read from the database, write the result into Redis with a TTL, then return it. On write: update the database, then either delete the corresponding cache key (invalidate-on-write) or update it directly — deletion is usually preferred because it can't leave the cache holding a value that's inconsistent with a concurrent write. The app owns the logic in this pattern — Redis never talks to the database — which is exactly why it's the default choice: it's simple, it only caches what's actually read, and Redis being briefly unavailable degrades to "every read hits the database" rather than an outage.

Example

var cached = await db.StringGetAsync(key);
if (cached.HasValue) return Deserialize(cached);
var value = await repository.LoadAsync(id);
await db.StringSetAsync(key, Serialize(value), TimeSpan.FromMinutes(10));
return value;

Follow-ups

  • Why delete on write instead of updating the cache directly? — Updating risks a race where a slower earlier write overwrites a newer one's cached value; deleting just forces the next read to reload the current truth.
  • What happens on a Redis outage under cache-aside? — Every read falls through to the database — a latency/load spike, not a correctness bug, which is the pattern's main appeal.
  • Where's the staleness window? — Between the database write and the cache delete/expiry — anyone reading in that window can see the old cached value.

Common wrong answer

Describing cache-aside but forgetting the TTL — an un-expiring cache-aside key silently turns any missed invalidation into permanent staleness instead of a bounded one.

midCache-aside vs write-through vs write-behind — what's the actual trade-off?

Answer

Cache-aside is app-driven and lazy — only accessed data gets cached, and a miss costs one extra round trip. Write-through writes to the cache and the database synchronously on every write (often via a caching library or Redis in front of a data layer that owns both), guaranteeing the cache is never stale after a successful write but paying that latency on every write, including writes to data nobody will read soon. Write-behind (write-back) writes to the cache immediately and asynchronously flushes to the database later, giving the lowest write latency and a natural batching point, at the real risk of data loss if the cache fails before the flush — which makes it a poor fit for anything that must survive a crash without loss, and a good fit for high-volume, loss-tolerant telemetry-style writes.

Example

cache-aside:   read fills the cache, write invalidates it
write-through: write goes to cache AND db, synchronously, every time
write-behind:  write goes to cache, a background job flushes to db later

Follow-ups

  • Which pattern minimizes cold-cache thundering herds after a deploy? — None inherently — that's what request coalescing / locking (below) solves regardless of which of these three you pick.
  • Which is the default choice for a typical .NET web app cache? — Cache-aside, because it's simplest to reason about and IDistributedCache is built around it.
  • When would you genuinely pick write-behind? — High-frequency writes where occasional loss is acceptable and batching to the database meaningfully reduces load — analytics counters, not financial ledgers.

Common wrong answer

Calling write-behind "just an optimization with no downside" — the loss window on cache failure before flush is a real correctness trade-off, not a free lunch.

midA popular cache key just expired and 10,000 concurrent requests all missed at once. What's happening and how do you prevent it?

Answer

This is a cache stampede (thundering herd): every one of those requests falls through to the database simultaneously to recompute the same value, which can take the database down even though the underlying data hasn't changed at all. The standard fix is request coalescing — the first request to miss acquires a short-lived "rebuilding" lock (a SET key:lock val NX PX 5000) and does the recompute while every other request either waits briefly and retries the cache, or serves a slightly-stale value if one is available (stale-while-revalidate). A complementary mitigation is jittering TTLs (add ±10% randomness) so that many keys set at the same time don't all expire in the same instant in the first place.

Example

var ttl = TimeSpan.FromMinutes(10) + TimeSpan.FromSeconds(Random.Shared.Next(-60, 60));
await db.StringSetAsync(key, value, ttl);   // jittered TTL

Follow-ups

  • What's the "locked recompute" pattern's own failure mode? — If the lock holder crashes before releasing it, everyone waits out the lock's own TTL before anyone recomputes — size that TTL to the recompute's realistic worst case.
  • How does stale-while-revalidate differ from a hard lock? — It never blocks readers — everyone gets the old value immediately while one background refresh happens, trading a bounded staleness window for zero request-facing latency.
  • Does this only happen on expiry, or also on deploys? — Also on cold starts and cache flushes — any event that empties a hot key set simultaneously reproduces the same failure mode.

Common wrong answer

"Just increase the TTL" — reduces how often it happens but doesn't fix the mechanism, and just delays an eventual stampede at an even less predictable moment.

midHow do you avoid caching a value for a key that doesn't exist in the database — the "negative cache" problem?

Answer

Without a negative cache, every lookup of a nonexistent id (a typo'd id, a deleted resource, or a deliberate probing attack) falls through to the database on every single request forever, because there's nothing to cache — this is the cache-penetration problem. The fix is to explicitly cache the "not found" result itself, typically as a small sentinel value with a short TTL, so subsequent lookups of the same missing key hit Redis and return quickly instead of hammering the database. At larger scale, a Bloom filter in front of the cache (Redis's native Bloom filter type since 8.0, or an app-side one) can reject lookups for keys that provably never existed without even a Redis round trip.

Example

var cached = await db.StringGetAsync(key);
if (cached == "__NULL__") return null;                 // negative cache hit
if (cached.HasValue) return Deserialize(cached);
var value = await repository.LoadAsync(id);
await db.StringSetAsync(key, value is null ? "__NULL__" : Serialize(value), TimeSpan.FromMinutes(2));
return value;

Follow-ups

  • Why give the negative cache a shorter TTL than a positive hit? — A "not found" is more likely to become stale soon (the resource gets created) than an existing value is to disappear.
  • How does a Bloom filter help before the negative cache even runs? — BF.EXISTS answers "definitely not present" with zero false negatives in O(1)-ish time, filtering out most penetration attempts before they touch the cache or db at all.
  • What's the risk of negative caching for security-sensitive lookups? — Caching "user not found" can leak timing/existence information differently than a real lookup would — worth a deliberate constant-time approach for auth paths.

Common wrong answer

Treating "cache miss" and "confirmed doesn't exist" as the same state — conflating them is exactly what leaves the penetration path open.

seniorHow do you invalidate a cache entry that's derived from multiple underlying rows — e.g. an aggregated dashboard value?

Answer

Tag-based invalidation: instead of trying to compute which single cache key a write affects, maintain a reverse index — a Set per underlying entity that lists every cache key derived from it (SADD tag:order:501 "dashboard:tenant:9") — and on any write to that entity, look up and delete every cache key in its tag set. This trades a bit of bookkeeping (every cache-populate call must also register its tags) for correctness on fan-out invalidation, and is the same idea .NET's own output-cache tagging and several CDNs use. The alternative — a short TTL and accept the staleness window — is often the pragmatically better answer for dashboards specifically, since exact real-time correctness rarely matters as much as it feels like it should; naming that trade-off unprompted is what separates a senior answer from a mechanical one.

Example

SADD "tag:order:501" "dashboard:tenant:9" "report:monthly:2026-09"
# on write to order:501:
SMEMBERS "tag:order:501"   # -> delete each, then DEL "tag:order:501"

Follow-ups

  • What happens if the tag set itself is never cleaned up? — It grows unboundedly across the entity's lifetime; delete the tag set itself alongside the invalidation, or give it its own TTL slightly longer than the cache entries it tracks.
  • Would Pub/Sub-based invalidation broadcast work instead? — For multi-instance app-local (in-process) caches, yes — Redis Pub/Sub or keyspace notifications can tell every instance to drop a local entry; it doesn't apply when Redis itself is the cache.
  • Is TTL-only ever the right call for a derived aggregate? — Often yes — a 60-second staleness window on a dashboard is frequently a non-issue, and it removes an entire class of invalidation bugs.

Common wrong answer

Trying to enumerate all affected cache keys at write time by pattern-matching key names (KEYS dashboard:*) — slow, blocking, and fragile as soon as the key-naming scheme changes.

seniorWhat's the difference between IDistributedCache and using IDatabase directly for caching in .NET, and when do you drop to the raw client?

Answer

IDistributedCache is a minimal, provider-agnostic abstraction — GetAsync/SetAsync/RemoveAsync/RefreshAsync against a byte-array value with an absolute/sliding expiration — designed so app code doesn't hard-depend on Redis and could swap to SQL Server or an in-memory provider. It's the right default for straightforward key-value caching because it's what most middleware (session state, response caching helpers) already expects. You drop to IDatabase (via IConnectionMultiplexer) the moment you need anything IDistributedCache doesn't expose: Hash/Set/ZSet operations, pipelining multiple commands, Lua scripts, pub/sub, or atomic multi-key patterns like the locked-recompute pattern above — none of that fits through a byte-array-in/byte-array-out interface.

Example

// IDistributedCache: fine for a single serialized blob
await cache.SetAsync(key, bytes, new DistributedCacheEntryOptions { SlidingExpiration = TimeSpan.FromMinutes(20) });
// IDatabase: needed the moment you want e.g. HINCRBY or a Lua unlock script
var db = muxer.GetDatabase();
await db.HashIncrementAsync("stats:daily", "views", 1);

Follow-ups

  • Can you use both against the same Redis instance? — Yes, and it's common: IDistributedCache for generic caching, IConnectionMultiplexer injected separately for anything structure-specific.
  • Does IDistributedCache support sliding expiration natively in Redis? — The Redis provider simulates it by resetting the TTL on each GetAsync/RefreshAsync call — it's not a native Redis concept.
  • What's the risk of standardizing everything on IDistributedCache "for portability"? — You lose access to Redis-specific atomicity and structures, and "portability" is rarely exercised in practice — most teams never actually swap the backing store.

Common wrong answer

Claiming IDistributedCache "is Redis" — it's a generic abstraction that happens to have a Redis implementation (Microsoft.Extensions.Caching.StackExchangeRedis); conflating the two loses sight of what's provider-specific.

seniorHow do you keep a cache consistent when the same entity is written from two different services?

Answer

The safest default is invalidate-don't-update: whichever service writes the entity issues a DEL (or publishes an event another service's handler turns into a DEL) for every cache key derived from that entity, rather than trying to push the new value into the cache directly — pushing values from two writers risks a slower write landing after a faster one and leaving stale data cached with no signal anything's wrong. For true cross-service consistency, invalidation itself should ride the same event bus/outbox pattern used for the write (publish "OrderUpdated" after the database commit, have every service — including the writer — react to it uniformly) rather than each service independently deciding when to invalidate, which is what causes the classic "service A updated but service B's cache didn't know" bug.

Example

OrderService writes DB, commits, publishes OrderUpdated{id=501}
CacheInvalidationHandler (subscribed everywhere) does DEL "order:501" and DEL every tag-linked key

Follow-ups

  • What if the event publish fails after the database commit succeeds? — Use the transactional outbox pattern so the event is guaranteed to eventually publish — a dropped invalidation is a correctness bug, not a cosmetic one.
  • Is Redis keyspace notification a substitute for an app-level event bus here? — It can broadcast "this key changed" to subscribers, but it's fire-and-forget with no delivery guarantee and doesn't survive a Redis restart — not a replacement for a durable event bus.
  • Would a short universal TTL make the whole cross-service problem moot? — It bounds the damage but doesn't remove the underlying inconsistency — often the pragmatic backstop layered on top of proper invalidation, not instead of it.

Common wrong answer

Having each service push its own writes into the shared cache directly — a natural instinct that reliably produces exactly the lost-update race being asked about.

seniorWhat's the difference between response caching, output caching, and distributed caching in an ASP.NET Core app, and where does Redis fit?

Answer

Response caching (the older [ResponseCache]/middleware model) is essentially HTTP header manipulation — it tells the client or an intermediary proxy to cache, and the optional in-server response cache is memory-only, gone on restart, and doesn't scale across instances. Output caching (ASP.NET Core 7+) is a first-class server-side cache of full rendered responses keyed by route/query/vary rules, and — this is the part worth knowing cold — it supports a Redis-backed store (AddStackExchangeRedisOutputCache) so the cached output is shared across every instance behind a load balancer, with tag-based eviction built in. Distributed caching (IDistributedCache) is the general-purpose building block underneath both patterns for arbitrary data, not just full HTTP responses — Redis is the usual backing store for all three, but only output caching and IDistributedCache actually share state across instances.

Example

builder.Services.AddStackExchangeRedisOutputCache(o => o.Configuration = "redis:6379");
app.UseOutputCache();
app.MapGet("/products/{id}", Handler).CacheOutput(p => p.Tag("products").Expire(TimeSpan.FromMinutes(5)));

Follow-ups

  • Why did output caching replace the in-memory response cache for multi-instance apps? — Because a per-instance cache is inconsistent behind a load balancer — one instance's cached response can be stale relative to another's fresher write.
  • How does tag-based eviction work under the hood on Redis? — The Redis output-cache store tracks tag→key membership similarly to the tag-invalidation pattern above, so EvictByTagAsync is a targeted, not blanket, invalidation.
  • When is response caching (HTTP headers) still the right call over output caching? — When you actually want a CDN or browser to cache the response, not just your own servers — the two aren't mutually exclusive.

Common wrong answer

Treating output caching as "just a faster version of response caching" — the meaningful difference is the shared, tag-evictable server-side store, not raw speed.

principalDesign a caching strategy for an API that fronts a database under 5x normal read load during a flash sale, where 1% of products account for 90% of reads.

Answer

Start from the access-pattern skew, not a generic cache policy: the hot 1% needs to survive at almost any staleness cost, so give those keys (identified ahead of time from historical traffic, or detected live via a simple hit counter) a longer TTL and pre-warm them before the sale starts rather than relying on lazy population under load — that removes the worst stampede risk before it happens. Layer request coalescing (a short recompute lock) under every cache-aside miss regardless of hotness, since even correctly pre-warmed keys can expire mid-sale, and add stale-while-revalidate specifically for the hot set so a miss never blocks a request — serve the slightly-old value while one request refreshes it in the background. Trade-offs to name unprompted: pre-warming needs an accurate hotness prediction or it wastes memory on the wrong keys; stale-while-revalidate means some shoppers briefly see slightly wrong inventory/price, which is usually acceptable but must be a deliberate product decision, not an accident; and if Redis itself becomes the bottleneck under 5x load, the fix is read replicas fronting reads (see the replication unit), not a bigger cache TTL.

Example

pre-sale: warm top-N products from last sale's access log into cache with 30min TTL
at runtime: cache-aside + lock-based coalescing for misses
hot set: stale-while-revalidate, background refresh every 5s regardless of reads

Follow-ups

  • How do you detect the hot 1% live instead of only from history? — A rolling counter (Sorted Set scored by recent-access-count, trimmed by time) gives a cheap live "top N" without a separate analytics pipeline.
  • What if the sale makes a previously-cold product suddenly hot? — The coalescing lock is exactly the backstop for that case — no amount of pre-warming catches every surprise, so the generic protection still has to be there.
  • Would read replicas alone solve this without any caching changes? — They spread read load but don't remove per-key contention or database load for genuinely hot rows — caching and replication solve different parts of the same problem.

Common wrong answer

"Just cache everything with a long TTL" — ignores the skew (wasting memory caching the cold 99% at the same priority as the hot 1%) and does nothing about the stampede risk when the long TTLs eventually expire together.

principalWhen is caching in Redis the wrong answer entirely, and what would you push back with?

Answer

Caching is the wrong first move when the actual problem is an unindexed or badly-shaped database query — a cache just hides a fixable performance bug behind a TTL and adds an invalidation-correctness problem in its place; the right answer is to profile and fix the query first, then decide if caching is still worth the complexity. It's also the wrong answer for data that changes on nearly every read (a live stock ticker, a real-time counter under heavy write contention) where the cache hit rate will be near zero and the invalidation traffic will exceed the savings — there, either accept the direct database/Redis-as-source-of-truth cost or restructure the read pattern (e.g. push updates instead of pulling reads). And it's the wrong answer when strict consistency is a hard requirement (financial balances, inventory that must never oversell) unless the caching layer is paired with a correctness mechanism (optimistic locking, a authoritative recheck before commit) that most teams skip once "just cache it" ships and the pressure to iterate elsewhere returns.

Example

"Add a cache" request for a report that recomputes from a full table scan every load
-> push back: add the missing index / materialize the aggregate, THEN evaluate caching

Follow-ups

  • How do you distinguish "genuinely needs caching" from "papering over a query problem" in review? — Ask for the query plan and its cost before approving a cache — if the query itself is cheap and correct, caching is about read volume, not correctness rescue.
  • What's a safer alternative to caching for a near-real-time counter? — Keep the counter in Redis as the source of truth (INCR) rather than caching a database-derived snapshot of it — that removes the staleness question entirely.
  • How do you push back on a caching request without just saying no? — Quantify: show the query cost, the expected cache hit rate given the access pattern, and the invalidation complexity it would add, and let the numbers make the case.

Common wrong answer

Agreeing to add a cache to any slow endpoint on request — a cache is a mitigation for read volume against a query you've already made as cheap as it can be, not a substitute for making it cheap.

03Persistence: RDB and AOF

Redis is in-memory first, but almost every production deployment persists something, and interviewers use this unit to check whether you understand durability as a spectrum of trade-offs rather than a binary "does it save to disk." Expect questions on RDB snapshot mechanics, AOF's write-guarantee knobs, and — at senior+ — how the two combine and what actually gets lost in a crash. Docs: redis.io/docs/latest/operate/.../persistence.

screenerWhat's the difference between RDB and AOF persistence?

Answer

RDB is a point-in-time binary snapshot of the whole dataset, written on a schedule (save 3600 1-style rules) or on demand (SAVE/BGSAVE) — compact, fast to load on restart, but every write since the last snapshot is lost if the process crashes. AOF (Append-Only File) logs every write command as it happens, so replaying it on restart reconstructs the dataset with far less data loss — how much less depends entirely on the appendfsync policy, which trades durability against write latency. Most production deployments run both: RDB for fast restarts and portable backups, AOF for the tighter durability guarantee, and Redis rewrites/compacts the AOF in the background so it doesn't grow forever.

Example

CONFIG SET appendonly yes
CONFIG SET appendfsync everysec   # fsync at most once per second, the default trade-off

Follow-ups

  • Which loads faster on restart, RDB or AOF? — RDB, since it's already the final state; a large AOF must be replayed command-by-command (mitigated by the AOF rewrite producing a base RDB-like preamble).
  • Can you run with neither enabled? — Yes, pure in-memory cache mode — a valid choice when Redis holds nothing that isn't reconstructible from the source of truth.
  • What changed with "multi-part AOF" (Redis 7+)? — AOF is now a base file plus incremental files plus a manifest, making rewrites and truncation-safety far more robust than the old single-file AOF.

Common wrong answer

"AOF is strictly better because it's more durable" — ignores the write-latency and restart-time costs, and that appendfsync always is rarely used in practice because of the latency it adds.

midExplain the three appendfsync options and what each actually guarantees.

Answer

always calls fsync after every single write command — the strongest guarantee (lose at most the in-flight command on crash) at a real per-write latency cost, since every command now waits on a disk sync. everysec (the default) fsyncs once per second in a background thread, bounding data loss to roughly the last second of writes on a crash, with no per-command latency penalty — the trade-off almost every production deployment accepts. no lets the OS decide when to flush its own page cache, which can mean tens of seconds of writes lost and is really only appropriate when the OS/hardware is known to flush aggressively or durability is not a concern for this dataset.

Example

CONFIG SET appendfsync always    # slowest, safest
CONFIG SET appendfsync everysec  # default, ~1s loss window
CONFIG SET appendfsync no        # fastest, OS-dependent loss window

Follow-ups

  • Does everysec ever block a write waiting for the fsync? — Yes — if the background fsync is still running when the next one is due, Redis can briefly delay writes rather than let the AOF buffer grow unbounded.
  • Is this decision per-instance or per-command? — Per-instance config, not per-command — you can't ask for stronger durability on one write and weaker on another within the same AOF.
  • How does this interact with replication durability? — They're independent: a replica ack (WAIT) tells you data reached another process's memory, not that either side fsynced it to disk.

Common wrong answer

Assuming everysec means "at most 1 second of data ever at risk, guaranteed" — under sustained write pressure or a slow disk the window can be larger; it's a target, not a hard bound.

midWhat actually happens during BGSAVE, and why can it spike memory usage?

Answer

BGSAVE forks the Redis process; the child writes a consistent point-in-time snapshot from its own copy-on-write view of memory while the parent keeps serving traffic normally. The memory spike comes from copy-on-write: the fork itself is cheap (shared pages), but every write the parent makes afterward to a page the child still needs to read copies that page, so a write-heavy workload during a long-running BGSAVE can transiently double memory usage in the worst case. This is exactly why "why does memory spike right when the snapshot fires" is a real production question, not a trivia one — sizing headroom for the fork is a genuine capacity-planning input, not an edge case.

Example

BGSAVE
INFO persistence   # rdb_bgsave_in_progress, rdb_last_cow_size shows the copy-on-write cost

Follow-ups

  • Why does the OS's fork implementation matter here? — Linux's copy-on-write forking makes this pattern viable at all; without OS-level COW support the fork would need a full memory copy up front.
  • What if the host doesn't have enough free memory for the worst-case COW spike? — The fork can fail outright (fork() returning an error) or the OOM killer can intervene — a documented reason to keep meaningful memory headroom below maxmemory.
  • Does BGREWRITEAOF have the same fork-based mechanism? — Yes, the same fork/COW pattern underlies both background persistence operations.

Common wrong answer

Assuming BGSAVE is "free" because it's asynchronous from the client's point of view — the fork and COW cost are real server-side costs even though no client blocks waiting for it.

midWhat triggers an AOF rewrite, and why is it needed at all?

Answer

The AOF is a log, not a snapshot, so without compaction it grows forever — including commands whose effects have since been overwritten many times (ten increments to the same counter all sit in the log even though only the final value matters). BGREWRITEAOF forks (same COW mechanism as BGSAVE) and writes a new, minimal AOF that reconstructs the current dataset in the fewest commands, then atomically swaps it in; it's triggered manually, automatically when the AOF grows past auto-aof-rewrite-percentage relative to its size after the last rewrite, or as part of restart/loading logistics. Since Redis 7's multi-part AOF, the rewrite produces a new base file alongside existing incremental files rather than one monolithic file, which makes the whole operation safer against a crash mid-rewrite.

Example

CONFIG SET auto-aof-rewrite-percentage 100
CONFIG SET auto-aof-rewrite-min-size 64mb
BGREWRITEAOF   # manual trigger

Follow-ups

  • Can a crash during rewrite corrupt the AOF? — Multi-part AOF's manifest-plus-separate-files design makes this far safer than the old single-file approach, where a crash mid-rewrite could leave a genuinely truncated file.
  • Does AOF rewrite pause writes? — No — writes continue against the old AOF (buffered) while the child builds the new base file, then the buffered writes are appended and the swap happens.
  • Is there a tool to inspect or repair a damaged AOF? — redis-check-aof, which can also truncate a file to its last valid command after an unclean shutdown.

Common wrong answer

Thinking AOF rewrite "replays commands faster" — it doesn't replay anything, it regenerates a minimal command set from the current in-memory state, which is a very different operation.

seniorYou need to restore Redis from a backup after a full outage. RDB or AOF, and why?

Answer

If both exist and are current, Redis prefers AOF on startup by default because it has the tighter durability guarantee — but the right restore choice for a specific incident depends on which artifact is actually intact and how much loss is acceptable: a clean daily RDB snapshot copied off-host is often the safer disaster-recovery artifact precisely because it's simple, portable, and doesn't depend on correctly replaying a potentially-large command log. Interviewers are checking whether you know both exist as independent artifacts with different failure modes (a corrupted AOF tail vs. a slightly-stale RDB) and that a real restore runbook should specify which one to reach for and why, not "restore whatever's newest" as a snap decision made mid-incident.

Example

redis-check-rdb dump.rdb        # verify before trusting it for restore
redis-check-aof --fix appendonlydir/appendonly.aof.1.incr.aof

Follow-ups

  • How do you verify a backup is actually restorable before you need it? — Periodic restore drills against a scratch instance, not just checking the file exists — an untested backup is a hope, not a plan.
  • What's the operational advantage of RDB for cross-region backup? — It's a single compact file, trivially shippable to object storage, versus an AOF directory with a manifest and multiple parts.
  • Does a replica help here at all? — A healthy replica is usually your fastest actual recovery path (promote it) — backups are the fallback for when replication itself is also compromised (e.g. a bad write propagated everywhere).

Common wrong answer

"AOF, always, because it's more durable" stated without checking the AOF's actual integrity first — a durability guarantee on paper doesn't help if the specific file is truncated or corrupted from the outage itself.

seniorWhat's the "diskless replication" / RDB-over-socket option, and when do you need it?

Answer

By default a full sync writes the RDB to disk on the primary and then transfers the file to the replica; repl-diskless-sync yes instead streams the snapshot directly over the socket to the replica without touching disk on the primary side, which matters on hosts where disk I/O is the bottleneck or where the disk is slow/network-attached and would otherwise add real seconds to every full resync. The trade-off is that a diskless sync can't be reused for a second replica joining at nearly the same moment the way a cached-on-disk RDB file can (mitigated by repl-diskless-sync-delay, which waits briefly to let multiple replicas share one generation), and it adds transient memory pressure on the primary similar to the COW cost during a normal BGSAVE.

Example

CONFIG SET repl-diskless-sync yes
CONFIG SET repl-diskless-sync-delay 5   # wait 5s to batch multiple joining replicas

Follow-ups

  • Does diskless sync avoid the fork/COW cost too? — No — it still forks to get a consistent snapshot view, it only changes where the resulting stream goes (socket vs. file), not how it's produced.
  • What's diskless loading on the replica side? — A separate setting (repl-diskless-load) controlling whether the replica applies the incoming stream directly to memory or buffers it to disk first — tunable independently of the primary's setting.
  • When would you deliberately keep disk-based sync? — When primary disk I/O has slack and you want the resulting RDB file cached for fast reuse by several replicas joining in sequence.

Common wrong answer

Describing diskless sync as eliminating the fork — it changes the transport, not the snapshot-generation mechanism, which still forks and still has a COW memory cost.

seniorYour cache-only Redis (no persistence enabled) just restarted empty in the middle of peak traffic. Was disabling persistence the wrong call?

Answer

Not necessarily — for a pure cache, an empty restart is a cold-cache-refill problem, not a data-loss problem, and skipping persistence entirely removes real overhead (fork/COW spikes, disk I/O, AOF fsync latency) that a cache-only workload gets no benefit from paying. The actual failure here is more likely the lack of stampede protection during the refill (see the caching unit) combined with no read-replica or gradual-warmup strategy for exactly this scenario, which is an availability-under-restart problem the team should have designed for regardless of the persistence decision. The right response is to add pre-warming or a slower cutover on restart (route a percentage of traffic through until the cache reaches a healthy hit rate) rather than reflexively turning persistence back on, which would reintroduce the very overhead it was disabled to avoid without addressing the actual gap.

Example

restart runbook: hold behind LB health check until hit-rate probe > 70%, then admit traffic

Follow-ups

  • When would persistence actually have been the right call for this cache? — If refilling from the source of truth is itself expensive enough (a slow upstream API, a rate-limited third party) that an empty cache causes a cascading overload — then RDB-only (cheap, no durability need beyond "not empty") is worth it purely for faster warm restarts.
  • Would a Redis Cluster with replicas have avoided this? — A promoted replica already has the data in memory — no cold restart at all — which is the real fix if this instance is business-critical enough to justify the operational cost.
  • Does maxmemory-policy interact with this decision? — No — eviction policy governs what happens under memory pressure while running, unrelated to what happens to data across a restart.

Common wrong answer

"Turn persistence on" as the reflexive fix — treats a warm-up/availability gap as a durability gap, adding cost without addressing the actual failure mode.

principalDesign the persistence and backup strategy for a Redis deployment holding data you cannot regenerate from anywhere else — e.g. session state that, if lost, logs every active user out simultaneously.

Answer

Treat it like a real database, not a cache: enable AOF with appendfsync everysec as the durability baseline (accepting a ~1s loss window as the deliberate trade against write latency), keep RDB snapshots on a schedule purely for fast full restarts and as the artifact shipped to off-host/off-region backup storage, and run at least one replica so the primary failure mode is "promote a replica," with backups as the fallback for correlated failures a replica wouldn't survive (a bad command replicated everywhere, a full-region outage). The trade-off to name unprompted: this is meaningfully more expensive — write latency, disk I/O, replica cost, backup storage and restore-drill discipline — than treating Redis as disposable, and the decision to accept that cost should be explicit and revisited if the "cannot regenerate" premise ever changes (e.g. sessions become reconstructible from a token-refresh flow), because most teams over-apply durability engineering to data that was never actually irreplaceable.

Example

appendonly yes; appendfsync everysec
save 900 1  (RDB snapshot cadence, shipped to object storage hourly)
1 primary + 2 replicas across AZs; quarterly restore drill from the shipped RDB

Follow-ups

  • Would you ever reach for appendfsync always for session data specifically? — Rarely — the latency cost is usually worse than the risk it removes for session state, where a 1-second loss window on a rare crash is an acceptable trade most teams make.
  • How do you validate the backup strategy actually works, not just exists? — Scheduled restore drills into an isolated environment with a pass/fail check against expected key counts — the same discipline as any database backup program.
  • Is there a case for moving genuinely irreplaceable data out of Redis entirely? — Yes — if the durability requirements keep climbing, that's a signal the data may belong in a primary datastore with Redis only as an accelerator in front of it.

Common wrong answer

Applying default cache-style settings (no persistence, or RDB-only with a long snapshot interval) to data explicitly described as irreplaceable — the "it's just Redis" reflex applied without checking the actual data-loss consequence.

04Replication, Sentinel & high availability

This is where "Redis is fast" meets "Redis is a distributed system whether you wanted that or not." Expect mid-level candidates to know async replication mechanics and its consistency implications; senior+ candidates to reason about failover, split-brain risk, and what a promoted replica actually guarantees. Docs: redis.io/docs/latest/operate/.../replication.

screenerHow does Redis replication work, and is it synchronous?

Answer

Replication is asynchronous by default: a primary accepts a write, applies it, and returns to the client immediately, then propagates the write to its replicas over a replication stream — the client never waits for a replica to acknowledge. A new replica performs a full sync first (loads an RDB snapshot of the primary's current state), then switches to a continuous stream of write commands (a partial resync can reuse a replication backlog buffer to avoid a full resync after a brief disconnect). Because it's async, there's an inherent replication lag window during which a replica's data is slightly behind the primary — a fact that drives most of the "can I read from a replica" trade-off questions in this unit.

Example

REPLICAOF primary-host 6379   # on the replica
INFO replication               # shows master_repl_offset vs slave_repl_offset (the lag)

Follow-ups

  • Can replication be made synchronous? — Not natively per-write, but WAIT numreplicas timeout lets a client block until N replicas confirm receipt of writes up to that point, approximating synchronous behaviour when needed.
  • What happens to writes issued while a replica is disconnected? — They queue in the primary's replication backlog (bounded size); on reconnect within the backlog's window, a partial resync catches the replica up without a full RDB transfer.
  • Is a replica read-only by default? — Yes (replica-read-only yes), specifically to prevent divergent writes that replication has no mechanism to reconcile.

Common wrong answer

Assuming replication is synchronous "because that's safer" — Redis's default and dominant deployment pattern is async, and conflating the two misses the whole reason replication lag and failover data loss are real operational concerns.

midYou read a value from a replica immediately after writing it to the primary and got the old value. Is this a bug?

Answer

No — this is expected, textbook replication lag, not a bug: the write returned to the client as soon as the primary applied it, and the replica hadn't yet received/applied that command over the (async) replication stream. The lag is usually milliseconds under healthy conditions but can grow under primary load, a slow network link, or a replica busy with its own background work (e.g. a large key expiring, or its own BGSAVE). If an application genuinely needs read-your-writes consistency, the fix is architectural — read from the primary for that specific request, or use WAIT to confirm propagation before telling the client the write succeeded — not something you can configure away as a "setting."

Example

// read-your-own-write: route straight to primary for the immediate re-read
var db = muxer.GetDatabase();
await db.StringSetAsync(key, value, flags: CommandFlags.DemandMaster);
var readBack = await db.StringGetAsync(key, flags: CommandFlags.DemandMaster);

Follow-ups

  • How do you monitor replication lag in production? — INFO replication's offset delta between primary and replica, or master_repl_offset vs each replica's acked offset, alerted on a threshold.
  • Does StackExchange.Redis let you route specific commands to the primary explicitly? — Yes, CommandFlags.DemandMaster/PreferMaster vs DemandReplica/PreferReplica per call.
  • Would WAIT fully solve this for every write? — It confirms replicas received the write, adding latency to every write to buy a guarantee most requests don't actually need — apply it selectively, not globally.

Common wrong answer

Filing this as a Redis consistency bug and looking for a config fix — there isn't one; it's the direct, expected consequence of choosing asynchronous replication, and the fix is at the application's read-routing layer.

midWhat does Redis Sentinel actually do, and what does it not do?

Answer

Sentinel is a separate, dedicated process (run as a small quorum of its own, typically 3+) that monitors a primary/replica set, detects when the primary is unreachable via a quorum vote among Sentinels (avoiding a single Sentinel's network blip triggering a false failover), and automates promoting a replica to primary and reconfiguring the rest to follow it — plus notifying clients of the new topology via pub/sub so they can reconnect to the right host. It does not shard data (that's Cluster's job — Sentinel manages a single primary/replica set's availability, not horizontal scale), and it does not make writes synchronous or prevent data loss during failover — a failover can still lose whatever writes hadn't replicated to the promoted replica yet.

Example

SENTINEL get-master-addr-by-name mymaster
# client asks Sentinel for the current primary rather than hardcoding a host

Follow-ups

  • Why does Sentinel need a quorum instead of one watcher? — A single Sentinel can't distinguish "the primary is actually down" from "I lost network to the primary" — quorum voting cross-checks that across independent observers.
  • How does a .NET client discover the current primary through Sentinel? — StackExchange.Redis supports a Sentinel-managed connection string (ConfigurationOptions.ServiceName + Sentinel endpoints), reconnecting automatically after a failover it's told about.
  • Is Sentinel still relevant given Cluster exists? — Yes — Cluster is for scaling beyond one node's capacity; Sentinel-managed replication is often the simpler, sufficient choice for HA without sharding.

Common wrong answer

Describing Sentinel as "Redis's load balancer" — it doesn't route or balance traffic at all, it detects failure and orchestrates failover; routing is still the client's job once it learns the new primary.

seniorWalk through exactly what can be lost during a Sentinel-driven failover.

Answer

Because replication is asynchronous, any write acknowledged to a client but not yet propagated to the replica that gets promoted is lost the moment that replica becomes the new primary — there's no mechanism recovering it from the old primary once it's demoted (and the old primary, on rejoining, discards its own divergent writes and resyncs from the new primary). Sentinel mitigates but doesn't eliminate this: it picks the replica with the most up-to-date offset among those it can see, and min-replicas-to-write combined with min-replicas-max-lag can be configured so the primary refuses writes if it doesn't have enough healthy, sufficiently-current replicas — trading some availability for a bound on how much could be lost on a failover. There's also a detection-and-failover time window (seconds, tunable via down-after-milliseconds and the failover timeout) during which writes to the (soon-to-be-former) primary either succeed-then-get-lost or fail outright depending on exact timing.

Example

CONFIG SET min-replicas-to-write 1
CONFIG SET min-replicas-max-lag 10   # refuse writes if no replica has acked within 10s

Follow-ups

  • Does this make Redis unsuitable for financial transactions? — For the authoritative ledger, generally yes without extra safeguards — Redis's HA model optimizes for availability and speed, not zero-loss durability; that's a deliberate, nameable trade-off, not a flaw.
  • How would WAIT reduce (not eliminate) this risk on critical writes? — Blocking until N replicas ack before returning success to the client shrinks the "acknowledged but unpropagated" window for that specific write.
  • What happens to the old primary when it comes back online post-failover? — Sentinel reconfigures it as a replica of the new primary; any writes it accepted after being partitioned but before demotion are simply overwritten by the resync.

Common wrong answer

Claiming Sentinel failover is lossless "because it picks the most up-to-date replica" — most up-to-date among the visible replicas is not the same as caught-up to the primary's last acknowledged write; some loss window always exists under async replication.

seniorWhen should you read from replicas, and what has to be true for that to be safe?

Answer

Reading from replicas is a legitimate way to scale read throughput and reduce primary load, and it's safe for workloads that can tolerate the replication-lag staleness window described above — analytics, dashboards, "browse" pages where a few hundred milliseconds of staleness is invisible to the user. It's unsafe, or at least needs explicit handling, for read-your-writes flows (a user updates their profile then immediately views it) and for any read whose result feeds a decision that must reflect the very latest write (an inventory check right before charging a card) — those need routing to the primary or a freshness check, not a blanket "always read from replica" policy. The .NET-relevant detail is that StackExchange.Redis's CommandFlags.PreferReplica is a hint, not a guarantee — it falls back to the primary if no replica is available, which is the right default behaviour but means you can't assume every "prefer replica" read is actually hitting a replica.

Example

var stats = await db.StringGetAsync("dashboard:daily", flags: CommandFlags.PreferReplica);
var latestOrder = await db.StringGetAsync($"order:{id}", flags: CommandFlags.DemandMaster);

Follow-ups

  • How would you decide, per endpoint, whether replica reads are safe? — Ask whether staleness of up to the expected lag window would produce a wrong or confusing outcome for that specific use case — if yes, route to primary.
  • Does read-replica scaling help with write throughput too? — No — every replica still receives and applies every write, so write throughput is bounded by the primary regardless of replica count; only reads scale this way.
  • What's the Cluster-specific version of this trade-off? — Same idea, but per-shard: READONLY/READWRITE on a cluster connection to a replica node, with the same staleness caveat.

Common wrong answer

"Always read from replicas to reduce load on the primary" stated with no mention of which reads can tolerate staleness — a blanket policy that will eventually produce a very confusing read-your-own-write bug report.

seniorWhat's the difference between Sentinel-managed HA and Redis Enterprise's/Cluster's failover, at a level you'd explain in a design review?

Answer

Sentinel manages exactly one logical primary/replica set and externalizes failure detection and promotion to a separate quorum of watcher processes — it adds no sharding, so it's the right fit when the dataset fits on one primary and the only goal is availability. Redis Cluster bakes failure detection and failover into the data nodes themselves via a gossip protocol, and because data is already sharded across many primaries, a single shard's failover is a smaller-blast-radius event than a Sentinel-managed single-primary failover, at the cost of Cluster's own complexity (hash slots, multi-key operation restrictions, client-side topology awareness). Managed offerings (Redis Enterprise, ElastiCache, Azure Cache for Redis) typically build further HA orchestration (multi-AZ automatic failover, sometimes active-active conflict-free replication) on top of one of these two foundations, which is worth knowing exists even if you don't need the implementation detail.

Example

Sentinel: 1 primary + N replicas, HA via external quorum, no sharding
Cluster:  16384 slots across M primaries, HA via gossip + per-shard replicas, sharding built in

Follow-ups

  • Why would you choose Sentinel over Cluster if Cluster gives you HA too? — Simplicity — no slot management, no multi-key-operation restrictions, no client-side cluster-topology handling — when the dataset genuinely doesn't need sharding.
  • Does Cluster remove the async-replication data-loss risk during failover? — No — each shard's failover is still async-replication-based internally; Cluster changes the blast radius and detection mechanism, not the fundamental consistency model.
  • What's "active-active" and why is it a different category from either? — Multi-region writable replicas with conflict resolution (CRDT-based in Redis Enterprise) — a different consistency model entirely, solving multi-region write availability rather than single-region failover.

Common wrong answer

Treating Cluster as "Sentinel but newer" — they solve different primary problems (sharding vs. single-set availability) and are frequently used together, not as successive versions of the same feature.

seniorWhat is split-brain in a Redis HA context, and how does Sentinel avoid it?

Answer

Split-brain here means two nodes both believing they're the primary and both accepting writes — classically caused by a network partition that isolates the old primary from its replicas and Sentinels without actually killing the old primary process, so it keeps serving writes on one side of the partition while a new primary gets promoted on the other. Sentinel's quorum-based detection reduces (not eliminates) this risk: a failover is only initiated when enough independent Sentinels agree the primary is unreachable, and min-replicas-to-write can make the isolated old primary refuse writes once it can't see enough replicas — turning a potential split-brain into a clean unavailability on the partitioned side instead. The residual risk is the writes the old primary already accepted before it noticed the partition and stopped — that's the data genuinely at risk, not an ongoing dual-write scenario if the safeguards are configured.

Example

CONFIG SET min-replicas-to-write 1
CONFIG SET min-replicas-max-lag 10
# isolated ex-primary with 0 visible replicas now refuses writes instead of accepting them blindly

Follow-ups

  • Is this the same failure class CAP theorem talks about? — Yes — this is Redis choosing availability-leaning behaviour by default, and min-replicas-to-write is the lever that shifts it toward consistency (refuse writes) at the cost of availability during a partition.
  • Does Cluster have an equivalent safeguard? — Yes, cluster-require-full-coverage and per-shard majority requirements serve a similar role, refusing operations on slots that can't reach quorum.
  • What would a fencing token add here? — A monotonically increasing epoch a client/proxy could use to reject writes from a primary it knows has been superseded — Redis Cluster's own epoch mechanism plays a similar role internally.

Common wrong answer

Claiming Sentinel "prevents split-brain" outright — it substantially reduces the risk and bounds the damage with the right config, but doesn't provide the kind of formal consensus guarantee that would fully prevent it under all partition scenarios.

principalHow do you decide, for a specific service, whether Sentinel-managed replication is sufficient or Cluster is actually needed?

Answer

Start from the actual constraint: if the dataset and its working-set memory comfortably fit on one primary node's available memory (with headroom for COW spikes and growth) and the write throughput doesn't saturate a single core's command-processing capacity, Cluster's sharding buys you nothing — you'd be adding hash-slot management, multi-key-operation restrictions (no cross-slot MGET/transactions without hash tags), and client-side topology complexity purely to solve a problem you don't have. Reach for Cluster when either axis genuinely won't fit on one node — dataset size beyond a single reasonably-sized instance, or write throughput beyond one primary's single-threaded ceiling — and be honest that "we might need to scale eventually" is not, by itself, sufficient justification given how much operational complexity Cluster adds on day one. The trade-off to name unprompted: migrating from Sentinel to Cluster later is a real, nontrivial project (re-keying for hash-tag colocation, auditing every multi-key operation), so it's worth sizing generously rather than assuming a costless upgrade path — but that's a reason to size correctly now, not a reason to default to Cluster "just in case."

Example

50GB working set, 20k ops/sec, single-region -> Sentinel-managed replica set is enough
2TB working set OR sustained 200k+ ops/sec -> Cluster

Follow-ups

  • What's the actual single-primary throughput ceiling that forces the Cluster decision? — It varies by command mix and payload size, but low hundreds of thousands of simple ops/sec per core is a reasonable planning figure — benchmark your actual workload rather than trusting a rule of thumb.
  • Would you ever choose Cluster purely for the HA/failover model, not for sharding? — Rarely — Sentinel's HA is simpler and sufficient for single-primary workloads; Cluster's HA benefit is really a side effect of sharding reducing each shard's blast radius, not a reason to shard on its own.
  • How does a managed service change this calculus? — Managed offerings often abstract the Sentinel-vs-Cluster choice into a "cluster mode enabled/disabled" toggle with the underlying migration cost still real — the sizing question is the same, just the operational burden shifts to the provider.

Common wrong answer

Defaulting to Cluster "for future scale" without a concrete capacity number driving the decision — a costly complexity tax paid up front against a hypothetical need that may never materialize.

principalA .NET service's StackExchange.Redis connections all timed out for 8 seconds during a Sentinel failover, even though failover itself took 3 seconds. What's the extra 5 seconds?

Answer

The failover completing on the server side and the client actually discovering and reconnecting to the new primary are two different clocks: StackExchange.Redis has to notice the existing connection is broken (which can itself take a few seconds depending on TCP timeout settings and whether keep-alives are tuned aggressively), then re-resolve the primary through Sentinel, then re-establish and re-authenticate a new connection pool — each step adds latency, and a misconfigured ConnectTimeout/SyncTimeout or an app-level connection-per-request antipattern (see the .NET unit) makes every one of those steps worse. The fix is usually a combination of tuning abortConnect=false so the multiplexer keeps retrying instead of giving up, keeping keep-alive intervals tight enough to detect the dead connection quickly, and — most importantly — confirming the app uses one long-lived ConnectionMultiplexer so there's exactly one reconnect storm to manage instead of one per request.

Example

var options = new ConfigurationOptions {
    AbortOnConnectFail = false,
    ConnectTimeout = 3000,
    SyncTimeout = 3000,
    KeepAlive = 10,
    ServiceName = "mymaster" // Sentinel-managed
};

Follow-ups

  • Why would per-request ConnectionMultiplexer creation make this specific incident worse? — Every new request tries to establish a fresh connection during exactly the window when the topology is in flux, multiplying reconnect attempts instead of sharing one recovering connection.
  • What would you monitor to catch this class of incident faster next time? — StackExchange.Redis's own ConnectionFailed/ConnectionRestored events wired to logging/metrics, plus Sentinel's own failover-time logs, correlated on a timeline.
  • Does ReconnectRetryPolicy matter here? — Yes — an exponential-backoff retry policy avoids a reconnect storm hammering the newly-promoted primary the instant it comes up.

Common wrong answer

Blaming Redis/Sentinel entirely for "8 seconds of downtime" without separating server-side failover time from client-side reconnect behaviour — usually most of the gap is client-side and fixable with connection-handling tuning.

05Redis Cluster & sharding

Once a dataset outgrows one node, this unit is where a candidate either shows they understand hash-slot sharding at a mechanical level or reveals they've only ever used a single-node Redis. Mid-level candidates should know slot mechanics and the multi-key restriction; senior+ candidates get asked about resharding, hot-shard mitigation, and client-side topology handling. Docs: redis.io/docs/latest/operate/.../scaling.

midHow does Redis Cluster decide which node holds a given key?

Answer

The keyspace is divided into 16,384 fixed hash slots; each key's slot is CRC16(key) mod 16384, and each slot is owned by exactly one primary node (plus its replicas) at any time — the mapping of slot ranges to nodes is what "Cluster topology" means, and it's this mapping, not a consistent-hashing ring, that Redis Cluster uses. A client needs to know (or be told via a MOVED redirect) which node owns a key's slot before it can route the command correctly; a well-behaved Cluster-aware client caches this slot map and only re-fetches it after a redirect signals it's stale.

Example

CLUSTER KEYSLOT "user:1001"    # -> some number 0-16383
CLUSTER SHARDS                 # which node ranges own which slots

Follow-ups

  • Why 16,384 slots specifically, not a round number like 65,536? — It's small enough that the per-node slot bitmap stays compact for gossip messages, while still being far more than any realistic cluster's node count, so slot-to-node granularity is fine either way.
  • What happens if you run a command against the wrong node? — The node replies with a MOVED (or ASK during resharding) redirect telling the client the correct node — a well-behaved client follows it and updates its cached slot map.
  • Is this the same hashing scheme as consistent hashing? — No — it's a fixed, centrally-tracked slot assignment, not ring-based consistent hashing; rebalancing moves whole slots between nodes rather than recomputing a ring.

Common wrong answer

Describing Cluster sharding as consistent hashing — a common conflation with other distributed caches, but Redis Cluster's slot model is a distinct, simpler mechanism with different rebalancing behaviour.

midWhy does MGET key1 key2 fail on a Cluster when it works fine on standalone Redis?

Answer

Multi-key commands in Cluster mode require every key involved to hash to the same slot, because the operation has to execute atomically on one node — if key1 and key2 land on different shards, there's no node that can serve both, and the client gets a CROSSSLOT error. This is exactly what the hash-tag syntax exists to fix: wrapping the part of the key you want hashed in braces ({tag}) makes Redis hash only that substring, so {user:1001}:profile and {user:1001}:settings are guaranteed to colocate on the same slot regardless of the rest of the key name.

Example

MGET "{user:1001}:profile" "{user:1001}:settings"   # same slot, works
MGET "user:1001:profile" "user:2002:profile"          # different slots, CROSSSLOT error

Follow-ups

  • Does this affect Lua scripts and MULTI/EXEC too? — Yes — any command touching multiple keys, including inside a script or transaction, needs them all in the same slot in Cluster mode.
  • What's the downside of hash-tagging aggressively to work around this? — Colocating too much data under one tag defeats the purpose of sharding — that tag's data all lands on one shard, recreating a hot-shard risk.
  • Does StackExchange.Redis surface CROSSSLOT differently? — It throws a RedisServerException with the CROSSSLOT message — no automatic hash-tag insertion; that discipline is on the app.

Common wrong answer

"Cluster doesn't support multi-key commands at all" — it supports them fully, just constrained to keys sharing a slot; the fix is a naming convention (hash tags), not avoiding multi-key operations altogether.

seniorWalk through what happens when you add a node to a live Cluster and reshard.

Answer

The new node joins the cluster's gossip mesh empty, owning zero slots, and resharding is the explicit act of migrating a chosen set of slots from existing nodes to it — done gradually, slot by slot, via CLUSTER SETSLOT ... MIGRATING/IMPORTING and key-by-key MIGRATE commands (typically driven by an operator tool like redis-cli --cluster reshard rather than by hand). During migration of a given slot, a client's request for a key already moved gets an ASK redirect (a one-time, this-key-only follow instruction, distinct from MOVED's permanent remap), which is exactly why Cluster-aware clients need to handle two different redirect types, not one. Nothing blocks cluster-wide during a reshard — only the specific slot being migrated has a brief moment of "some keys here, some keys there" — but it is genuinely slow for a large slot's worth of large keys, since each key transfer is its own network round trip.

Example

redis-cli --cluster reshard 127.0.0.1:7000 --cluster-from <src-id> --cluster-to <dst-id> --cluster-slots 1000

Follow-ups

  • What's the difference between MOVED and ASK? — MOVED says "this slot now permanently lives elsewhere, update your map"; ASK says "this one key has already moved mid-migration, retry it there but don't update your map yet."
  • Can a reshard be paused or rolled back mid-flight? — It can be paused between key migrations, but a slot mid-migration should be driven to completion rather than left half-moved for long — tooling assumes forward progress.
  • What's the operational risk of resharding a slot containing one very large key? — MIGRATE on a huge key can take long enough to look like a stall on that slot — another reason the "one giant key" antipattern from unit 01 matters at the Cluster layer too.

Common wrong answer

Assuming adding a node automatically rebalances data — it doesn't; Cluster never moves slots on its own, resharding is always a deliberate, explicitly triggered operation.

seniorYou have one tenant whose traffic is 100x every other tenant's, all landing in one Cluster shard. What are your options?

Answer

This is the hot-shard problem, and Cluster's slot-based sharding doesn't solve it automatically — a single slot (or a hash-tagged group of keys) still lives on one primary regardless of how disproportionate its load is, so simply adding more nodes to the cluster doesn't spread that specific tenant's load unless their keys are deliberately split across more than one slot. Real options: split the noisy tenant's keys across multiple hash tags deliberately (sacrificing the colocation benefit for that tenant specifically, in exchange for spreading its load), give that tenant a dedicated, appropriately-sized Redis instance outside the shared Cluster entirely, or add read replicas specifically for that shard to absorb read load while writes still funnel through the one primary. The trade-off to name unprompted: none of these fully "fix" a genuinely oversized single-key or single-hot-write-path problem — if the hot spot is concentrated write traffic to very few keys, no amount of read-side mitigation helps, because the bottleneck is the single-threaded write path on one primary.

Example

"{tenant:big}:orders:0".."{tenant:big}:orders:15" -- bucket the tenant across 16 tags instead of 1

Follow-ups

  • Would moving the noisy tenant to its own Cluster/instance ever be simpler than re-sharding within one? — Often yes operationally — isolating the noisy neighbor removes the blast radius on everyone else even if the tenant's own scaling problem still needs solving.
  • How would you detect a developing hot shard before it pages someone? — Per-node INFO commandstats/latency metrics and CLUSTER SHARDS combined with per-tenant traffic tagging in your own telemetry, alerted on skew, not just absolute load.
  • Does this change your key-naming advice from unit 01? — It sharpens it: the hash-tag colocation convenience from unit 01 is exactly what creates this risk if one tag ends up disproportionately large — deliberate bucketing has to be designed in from the start for known-large tenants.

Common wrong answer

"Add more Cluster nodes" as the whole answer — more nodes only help if the hot tenant's keys are actually spread across more slots; otherwise the new nodes just sit idle while the same one shard stays overloaded.

seniorHow does StackExchange.Redis behave differently when talking to a Cluster versus a standalone instance?

Answer

The connection string/ConfigurationOptions just lists the cluster's endpoints; the multiplexer auto-detects Cluster mode from the server's handshake and maintains its own client-side slot map, transparently routing each command to the right node and following MOVED/ASK redirects without the app code needing cluster-awareness for single-key operations. The place it does surface is multi-key commands and Lua scripts: the app is still responsible for hash-tagging keys so a batched MGET or a transaction doesn't throw a CROSSSLOT-equivalent exception, and certain server-wide operations (like enumerating keys, or FLUSHALL) become per-node operations the client library exposes via GetServers() rather than a single call.

Example

var muxer = await ConnectionMultiplexer.ConnectAsync("node1:6379,node2:6379,node3:6379");
foreach (var server in muxer.GetServers())
    Console.WriteLine(server.EndPoint);   // one per Cluster node the client knows about

Follow-ups

  • Does the app need to specify all cluster nodes in the connection string? — No — a subset is enough for initial discovery; the client learns the rest of the topology from the cluster itself.
  • What happens to an in-flight request during a slot migration from the client's perspective? — StackExchange.Redis handles ASK/MOVED transparently for supported commands, retrying against the correct node without the app seeing an error in the common case.
  • How do you run a SCAN-equivalent across an entire Cluster? — Iterate GetServers() and run Keys()/SCAN per node — there's no single cluster-wide scan primitive.

Common wrong answer

Assuming application code needs manual slot-routing logic when using StackExchange.Redis against a Cluster — the client handles single-key routing; only multi-key hash-tagging discipline and per-node fan-out operations are the app's job.

seniorWhat's cluster-require-full-coverage, and what's the trade-off in either setting?

Answer

When set to yes (the default), the whole Cluster refuses all operations the moment any slot has no reachable primary — total unavailability on one shard failure, but a guarantee you're never silently serving a partial, incomplete view of the keyspace. Set to no, the Cluster keeps serving requests for every slot that's still reachable and only fails operations touching the down slot's range, trading a guarantee of "all or nothing" for graceful degradation — which is usually the better choice for availability-sensitive workloads that can tolerate "some keys are temporarily unreachable" better than "the entire dataset is unreachable."

Example

CONFIG SET cluster-require-full-coverage no
# one shard's primary and its replicas all down: only that shard's keys error, everything else keeps serving

Follow-ups

  • Why might a team deliberately keep the default yes? — When partial availability is worse than none for their use case — e.g. a system where "some data missing" would produce silently wrong aggregate results rather than a visible error.
  • Does this setting affect writes and reads the same way? — Yes — it's coverage-based, not operation-type-based; any operation touching an unreachable slot is refused either way, the setting only controls the blast radius.
  • How does this interact with replica promotion timing? — If a shard's replicas are still catching up or unreachable when its primary fails, there's a window with no coverage for that slot range regardless of this setting — it decides what happens during that window, not how long it lasts.

Common wrong answer

Treating no as strictly "more available, no downside" — it trades a correctness/completeness guarantee for availability, which is the right call for many workloads but a real trade-off, not a free upgrade.

principalDesign the migration plan for moving a single-node Redis (200GB, 40k ops/sec) to a 6-shard Cluster with zero data loss and minimal downtime.

Answer

First, audit every multi-key operation and Lua script currently in use against the future slot model — this is the part that actually breaks, not the data move, so every cross-key access needs a hash-tag scheme designed and rolled out to the application before the topology changes at all. Then stand up the new Cluster alongside the old standalone instance, dual-write from the application (or use replication-based migration tooling) so the Cluster is populated and kept current while still serving zero production reads, validate data parity with sampled comparisons, and only then cut reads over — ideally gradually (a percentage of traffic, or read-only endpoints first) with an instant rollback path to the standalone instance until confidence is high, followed by a full cutover and decommission of the old node. The trade-off to name unprompted: dual-writing doubles write-path complexity and risk of silent divergence during the transition window, so the validation step (parity checks, not just "no errors thrown") is not optional — skipping it is the single most common way this kind of migration ships a subtle data-loss bug that isn't discovered until well after the old instance is gone.

Example

1. audit & fix multi-key/Lua hash-tag compatibility
2. stand up Cluster, dual-write from app
3. backfill history, validate parity via sampling
4. gradual read cutover with rollback flag
5. full cutover, decommission old node

Follow-ups

  • Why fix the multi-key/hash-tag issue before touching data at all? — Because it's an application-code change with its own testing and rollout risk, entirely independent of the infrastructure migration — bundling them multiplies the blast radius of any single mistake.
  • Would MIGRATE-based online resharding tools be an alternative to app-level dual-write? — For a single-node-to-Cluster move specifically, dual-write from the app gives more control over validation and rollback than adapting the standalone-to-Cluster path with generic resharding tools, which are built for cluster-to-cluster rebalancing.
  • How do you size the 6 shards — evenly, or by predicted access pattern? — By predicted access pattern where it's known (avoid recreating today's hot-tenant problem on day one of the new topology), evenly as the default elsewhere.

Common wrong answer

Treating this as purely a data-transfer problem (RDB export/import into the new topology) with no mention of the multi-key/hash-tag compatibility audit — that's the step that actually produces production incidents, not the data move itself.

principalWould you ever choose Cluster mode for high availability alone, with only one node's worth of data?

Answer

Generally no — Cluster's HA comes bundled with sharding complexity you'd be paying for without using, and Sentinel-managed replication gives the same primary/replica failover semantics with a far simpler operational and client model. The one scenario where Cluster genuinely earns its keep at small scale is if you're already committed to Cluster-aware client tooling and infrastructure elsewhere in the organization and the marginal cost of running "Cluster with one shard" is lower than maintaining two different HA patterns (Sentinel here, Cluster there) — an organizational consistency argument, not a technical necessity. Naming that distinction — technical necessity versus operational consistency — is the senior-to-principal difference in this answer; either can be the right call, but for different reasons, and conflating them leads to defaulting to the more complex option without justification.

Example

single dataset, needs HA only -> Sentinel + replicas, unless org standard is Cluster everywhere

Follow-ups

  • What operational cost does single-shard Cluster add over Sentinel for the same HA outcome? — Slot management overhead, multi-key restrictions that buy nothing since there's only one shard anyway, and Cluster-aware client configuration — all real cost for zero sharding benefit.
  • Does a managed service change this calculus? — Often yes — some managed offerings make "Cluster mode" a checkbox with the operational burden absorbed by the provider, shifting the trade-off toward whichever the platform makes more turnkey.
  • Is there a migration cost if you start with Sentinel and later need to shard? — Yes, nontrivial (see the prior migration-plan question) — worth weighing against the cost of running single-shard Cluster from day one if sharding is a near-certain future need.

Common wrong answer

"Cluster is strictly more capable, so always use it" — more capability at zero cost is a myth here; the added complexity is real and unjustified when nothing needs sharding.

principalA Cluster client keeps seeing intermittent TRYAGAIN errors during business hours. What's happening and how do you fix it?

Answer

TRYAGAIN is returned specifically when a multi-key operation touches a slot that's currently mid-migration and the keys involved are split between their old and new location in a way the node can't resolve immediately — it's a transient, retry-safe signal, not a fatal error, but frequent occurrences during business hours point to reshards being scheduled (or auto-triggered by an autoscaling policy) during peak traffic instead of a quiet window. The fix is operational: schedule resharding operations for low-traffic periods, throttle the migration rate (most resharding tools support a pace/rate limit) so any given slot's migration window is short even under load, and confirm the client's retry policy actually retries TRYAGAIN with backoff rather than surfacing it as an application error — StackExchange.Redis retries these internally for supported commands, so seeing it bubble up to app code often means a script or custom command path that bypasses the client's normal retry handling.

Example

redis-cli --cluster reshard ... --cluster-pipeline 10   # slower per-batch, shorter TRYAGAIN windows

Follow-ups

  • Is TRYAGAIN the same thing as CROSSSLOT? — No — CROSSSLOT is a permanent error for keys that structurally can never share a slot; TRYAGAIN is transient, specific to an in-progress migration.
  • Would running resharding automatically based on load metrics make this worse? — It can, if the automation isn't also aware of current traffic and simply reacts to size/load thresholds that happen to peak during business hours — schedule-aware throttling is the fix.
  • How do you confirm this diagnosis versus another cause of intermittent errors? — Correlate the error timestamps against CLUSTER NODES/migration logs — if they align with an active reshard window, that's confirmation, not coincidence.

Common wrong answer

Treating TRYAGAIN as a client bug or a sign of cluster instability requiring a topology change — it's the expected, documented behaviour during slot migration; the fix is scheduling and retry handling, not re-architecture.

Given the ".NET developers" framing of this topic, expect a whole segment of the loop dedicated to the client library specifically — its connection model, its threading gotchas, and the difference between the abstractions ASP.NET Core hands you and the raw client underneath. This is where a candidate's actual production scars show up. Docs: stackexchange.github.io/StackExchange.Redis.

screenerWhy should ConnectionMultiplexer be a singleton, and what breaks if it isn't?

Answer

ConnectionMultiplexer is deliberately designed to be created once and reused for the app's lifetime: it manages a small pool of physical connections and multiplexes many logical commands over them concurrently, so creating a new one per request pays the full TCP-handshake-plus-Redis-handshake cost on every single request and can exhaust the server's connection limit under load. It's also thread-safe by design — the intended usage is exactly "one shared instance, called concurrently from everywhere" — so there's no thread-safety reason to create more than one, only a (usually wrong) instinct to scope it like a typical short-lived service dependency.

Example

// Register once, as a singleton
builder.Services.AddSingleton<IConnectionMultiplexer>(
    _ => ConnectionMultiplexer.Connect("redis:6379"));
// then inject IConnectionMultiplexer and call GetDatabase() per use - that part IS cheap

Follow-ups

  • Is GetDatabase() also expensive, so should that be cached too? — No — GetDatabase() returns a lightweight wrapper, essentially free to call repeatedly; only the multiplexer construction is expensive.
  • What actual symptom shows up in production from per-request multiplexers? — Connection-count exhaustion on the Redis server ("ERR max number of clients reached") and a visible per-request latency floor from repeated handshakes.
  • Does this mean one multiplexer for the whole app, even across unrelated features? — Typically yes, per logical Redis endpoint — one multiplexer per distinct Redis deployment the app talks to, shared across all its features.

Common wrong answer

Injecting IConnectionMultiplexer as Scoped or Transient "to follow DI best practices" — this is precisely the antipattern that causes connection exhaustion; it must be a singleton.

midWhat is connection multiplexing, mechanically, and why does it let one multiplexer serve high concurrency?

Answer

Rather than opening a connection per in-flight command, StackExchange.Redis pipelines many concurrent logical requests over a small number of shared physical TCP connections: each outgoing command is tagged and queued, sent to Redis as fast as the socket allows, and the responses are matched back to the right caller's awaited Task as they arrive — Redis itself processes them one at a time (it's single-threaded for command execution) but the network round-trip latency is amortized across many concurrent callers instead of paid serially per caller. This is what makes a single multiplexer genuinely sufficient for a busy web app: the bottleneck under multiplexing is Redis's own command-processing throughput, not the number of concurrent .NET callers waiting on results.

Example

// these all share the same underlying connection(s), interleaved efficiently
var t1 = db.StringGetAsync("a");
var t2 = db.StringGetAsync("b");
var t3 = db.StringGetAsync("c");
await Task.WhenAll(t1, t2, t3);

Follow-ups

  • Does more concurrent load ever justify more than one multiplexer? — Rarely, and only after profiling shows the shared connection(s) are themselves saturated — the default guidance is one multiplexer per Redis endpoint, not "add more for scale" reflexively.
  • How is this different from classic connection pooling (e.g. ADO.NET)? — Pooling hands out exclusive connections to callers; multiplexing shares connections concurrently among callers at the protocol level — a fundamentally different concurrency model.
  • What's ConnectionMultiplexer.GetCounters() useful for? — Inspecting in-flight/queued operation counts to detect saturation before it shows up as latency in production.

Common wrong answer

Describing multiplexing as "connection pooling with extra steps" — the mental model of exclusive-connection-per-caller from ADO.NET-style pooling doesn't match how StackExchange.Redis actually shares connections.

midWhat causes a sync-over-async deadlock with StackExchange.Redis in ASP.NET, and how do you avoid it?

Answer

Calling a blocking method like .Result or .Wait() on a StackExchange.Redis async call from a context with a captured SynchronizationContext (classic ASP.NET, or certain UI contexts) can deadlock: the blocking call occupies the thread while it waits for the async continuation, but that continuation is scheduled to resume on the very context now blocked, so neither ever proceeds. ASP.NET Core doesn't have the classic HttpContext SynchronizationContext that made this endemic in ASP.NET (Framework), which is why the same code that deadlocked reliably years ago sometimes "just works" today under Core — but relying on that is fragile; the real fix is async/await all the way down, never .Result/.Wait() on a Redis call in any code path that might run under a context that has one.

Example

// deadlock-prone (classic ASP.NET, or any captured context)
var value = db.StringGetAsync(key).Result;
// correct
var value = await db.StringGetAsync(key);

Follow-ups

  • Does ConfigureAwait(false) fix this if you can't avoid a blocking call? — It reduces the risk by not forcing the continuation back onto the captured context, but "always async, never block" is the actually reliable fix — treat ConfigureAwait(false) as a mitigation, not a license to block.
  • Why does this show up specifically with Redis more than other I/O? — It doesn't specifically — any awaited I/O has the same risk; Redis calls are simply extremely common and easy to reach for synchronously since the sync overloads exist right next to the async ones.
  • Are there still sync APIs on IDatabase — when are they legitimately safe? — Yes (e.g. StringGet), safe in genuinely synchronous call stacks (console tools, background workers with no captured context) — never inside a request-handling path.

Common wrong answer

"ASP.NET Core has no SynchronizationContext, so blocking on async Redis calls is fine there" — technically often survivable, but it's still a thread-pool-starvation risk under load and bad practice that becomes a real deadlock the moment the code is reused somewhere with a context.

midYour app throws RedisTimeoutException intermittently under load. How do you diagnose it?

Answer

A timeout means the client gave up waiting for a response within SyncTimeout/AsyncTimeout, and the exception message itself is the first diagnostic tool — StackExchange.Redis's timeout exceptions include an "in-flight/queued operation count" snapshot that tells you whether the client's own outbound queue was backed up (a sign of too much concurrent load relative to what the shared connection can drain) versus the server being slow to respond (check Redis-side latency/SLOWLOG and CPU). Common root causes, in likely order: a genuinely oversized/blocking command running server-side (a large KEYS, an unbounded SORT, a slow Lua script) blocking everything behind it on Redis's single command thread; thread-pool starvation on the .NET side delaying processing of completed responses; or simply undersized timeout values for the actual payload sizes involved.

Example

Timeout... IOCP: (Busy=2,Free=998) ... Local-CPU: n/a, ... , inst: 1, qu: 42, qs: 3, ...
                                                                    ^^ high "qu" (queued) points to client-side backlog

Follow-ups

  • What does a high "qu" (queued) count versus a low one tell you? — High queued-but-unsent points to client-side saturation (thread pool or connection backlog); a low queue with the server itself slow points to a server-side bottleneck instead.
  • Would increasing SyncTimeout be a reasonable fix? — Only as a stopgap while you find the root cause — raising the timeout hides the symptom and lets a genuinely slow operation degrade user-facing latency instead of failing fast.
  • How does SLOWLOG help here specifically? — It shows exactly which commands are actually slow server-side, which either confirms or rules out "Redis itself is the bottleneck" as the cause.

Common wrong answer

Reflexively raising the timeout value whenever this exception appears — treats a symptom as the problem and can mask a genuine server-side or thread-pool issue that will keep getting worse.

seniorHow do you implement pipelining/batching with StackExchange.Redis, and when does it actually help?

Answer

Firing off several async calls without awaiting each individually and then awaiting them together (Task.WhenAll) already pipelines them under the hood, since the multiplexer queues and sends them without waiting for each response serially — this is the default, idiomatic way to batch in StackExchange.Redis, distinct from explicit IBatch, which additionally guarantees the batched commands are sent as a contiguous block uninterrupted by other clients' commands interleaving on the wire (still not atomic — that's what a transaction is for). It helps specifically when you have many independent commands whose network round-trip latency, not server processing time, dominates — a loop issuing a hundred sequential await db.StringGetAsync() calls pays a hundred round trips; batching them pays roughly one.

Example

var batch = db.CreateBatch();
var tasks = ids.Select(id => batch.StringGetAsync($"item:{id}")).ToArray();
batch.Execute();
var results = await Task.WhenAll(tasks);

Follow-ups

  • Is IBatch atomic? — No — it only groups commands for efficient transmission; another client's commands can still interleave server-side between them. Use ITransaction for atomicity.
  • Would MGET be simpler than batching individual GETs here? — Yes, whenever the same command type applies to all keys — a native multi-key command is one round trip and simpler than manual batching; batching is for heterogeneous command sets.
  • Does batching help with Redis-side CPU cost, not just round trips? — No — it reduces network round trips only; the server still processes each command's actual work individually.

Common wrong answer

Assuming Task.WhenAll over unbatched fire-and-forget calls is meaningfully different from explicit IBatch for performance — for the common case they're close enough that reaching for IBatch "for performance" without a measured need is usually unnecessary complexity.

seniorHow would you implement a distributed lock correctly using StackExchange.Redis?

Answer

Acquire with SET key uniqueToken NX PX ttlMs (StackExchange.Redis's LockTake helper wraps this), where the token is a per-holder unique value (a GUID), not a fixed constant — the unique token is what makes release safe. Release must check that the caller still owns the lock before deleting it, and that check-then-delete has to be atomic, so it's done via a small Lua script (LockRelease wraps this too) rather than a plain GET followed by DEL, which would race if the lock expired and someone else acquired it in between those two calls. This is the naive-lock-bug-and-fix pair every senior Redis interview expects verbatim, and it's exactly what the library's built-in IDatabase.LockTake/LockRelease/LockExtend already implement — worth knowing they exist rather than hand-rolling this from scratch.

Example

var token = Environment.MachineName + ":" + Guid.NewGuid();
if (await db.LockTakeAsync("lock:invoice:501", token, TimeSpan.FromSeconds(10))) {
    try { /* critical section */ }
    finally { await db.LockReleaseAsync("lock:invoice:501", token); }
}

Follow-ups

  • Why can't release just be a plain DEL? — Because you might delete a lock someone else acquired after yours expired — the unique-token check prevents deleting a lock you no longer own.
  • Does this protect against a client holding the lock past its TTL due to a long GC pause or slow operation? — No — this is the fencing-token gap Redlock critiques raise (see unit 09); a TTL-based lock alone can't guarantee mutual exclusion under arbitrary pauses.
  • Is LockExtend safe to call repeatedly from a long-running critical section? — Yes, as long as it also checks token ownership atomically, which the library's implementation does — a heartbeat pattern for operations whose duration isn't known up front.

Common wrong answer

Implementing release as a GET to check the token followed by a separate DEL — the classic non-atomic check-then-act race that reintroduces exactly the bug the unique token was meant to prevent.

seniorHow do you choose a serialization strategy for cached objects in .NET — System.Text.Json vs MessagePack vs something else?

Answer

System.Text.Json is the pragmatic default: no extra dependency, human-readable payloads (useful for debugging via redis-cli), and fast enough for the vast majority of cache payloads — reach for it first and only move off it with a measured reason. MessagePack (via MessagePack-CSharp or the Microsoft.Extensions.Caching.StackExchangeRedis-adjacent ecosystem) buys meaningfully smaller payloads and faster (de)serialization for high-throughput or large-object caching, at the cost of opacity (you can't eyeball the value in a Redis CLI without a decoder) and a small integration/versioning-discipline overhead. The trade-off that actually matters at scale is schema evolution: whichever format you pick, adding/removing/renaming a field on a cached type without a compatibility plan will throw deserialization exceptions on stale cached payloads the moment a new deploy ships — plan for that (version the key, or tolerate unknown/missing fields) regardless of the format chosen.

Example

var bytes = JsonSerializer.SerializeToUtf8Bytes(dto);
await db.StringSetAsync(key, bytes, TimeSpan.FromMinutes(10));
// ...
var dto = JsonSerializer.Deserialize<Dto>((byte[])await db.StringGetAsync(key));

Follow-ups

  • How would you handle a breaking schema change to a cached type safely? — Bump a version segment in the key name (cache:v2:order:501) so old and new shapes never collide, and let the old keys simply expire out naturally.
  • Does payload size actually matter for a typical web app's cache? — Usually only at genuine scale (very high throughput, or large objects) — profile actual network/memory cost before treating serialization format as a performance lever.
  • Is compression (e.g. gzip before storing) ever worth adding? — For large, compressible payloads (big JSON blobs) yes, trading CPU for memory/bandwidth — measure both sides before adding it reflexively.

Common wrong answer

Picking MessagePack "for performance" by default without a measured need — it's a legitimate optimization, not a mandatory upgrade, and the opacity/versioning overhead is a real cost paid for a benefit that may not matter for the actual payload sizes involved.

seniorWhat's the modern (2026) recommended way to do ASP.NET Core session state and output caching with Redis, versus what you'd find in an older codebase?

Answer

The modern path is AddStackExchangeRedisCache for IDistributedCache-backed session state (via AddSession configured on top of it) and AddStackExchangeRedisOutputCache for full-response caching with tag-based eviction (ASP.NET Core 7+) — both first-class, actively maintained integration packages that share the app's existing ConnectionMultiplexer configuration story. An older codebase (pre-.NET-Core, or an early Core migration that never modernized) is more likely to show hand-rolled session providers directly against StackExchange.Redis's IDatabase, a custom middleware-based response cache, or — going back further — the ASP.NET (Framework) RedisSessionStateProvider from the old Microsoft.Web.RedisSessionStateProvider package, none of which are wrong per se but represent real migration debt worth naming when you see them in a legacy review.

Example

builder.Services.AddStackExchangeRedisCache(o => o.Configuration = "redis:6379");
builder.Services.AddSession(o => o.IdleTimeout = TimeSpan.FromMinutes(30));
builder.Services.AddStackExchangeRedisOutputCache(o => o.Configuration = "redis:6379");

Follow-ups

  • Why migrate off a hand-rolled session provider if it "still works"? — Maintenance burden and missing improvements (connection resilience, cluster support) that ship for free in the maintained package — a real but not always urgent argument.
  • Does output caching replace the need for a distributed cache for session data? — No — they solve different problems (full-response caching vs. per-user session state) and are commonly used together.
  • What should you check before trusting an old Redis session provider is still compatible with a Cluster backend? — Whether it issues any multi-key operations without hash tags — a common latent incompatibility uncovered only when the backend changes from standalone to Cluster.

Common wrong answer

Assuming any Redis-backed session code "is fine" without checking which era's integration pattern it follows — the difference matters for maintainability and for compatibility with newer Redis deployment topologies.

principalYour team wants to run Lua scripts from .NET for atomic multi-step operations. Walk through the StackExchange.Redis API and the operational trade-offs.

Answer

IDatabase.ScriptEvaluateAsync (or the newer LuaScript helper class, which handles parameterization more safely than manual string interpolation) sends a Lua script for atomic server-side execution — Redis caches scripts by SHA1 automatically (EVALSHA-equivalent under the hood), so repeated calls don't resend the script body over the wire. The operational trade-off worth naming unprompted: a Lua script runs on Redis's single command-processing thread just like every other command, so a slow or unbounded-loop script blocks the entire server for its duration exactly like a giant KEYS call would — code review for Redis Lua scripts needs the same "what's the worst-case runtime" scrutiny as any other blocking operation, and the newer Redis Functions (7.0+, server-persisted, versioned) are generally the better fit for anything beyond a one-off script since they're managed and replicated as first-class server objects rather than client-side strings.

Example

var script = LuaScript.Prepare(
  "if redis.call('get', @key) == @token then return redis.call('del', @key) else return 0 end");
var result = await db.ScriptEvaluateAsync(script, new { key = (RedisKey)"lock:x", token = "abc" });

Follow-ups

  • Why prefer LuaScript.Prepare over building the script string manually? — It handles parameter substitution safely and consistently, avoiding both injection-style bugs and the SHA-caching bookkeeping.
  • What happens if the script references keys on different Cluster slots? — Same restriction as any multi-key operation — every key the script touches must share a slot, or it fails with a cross-slot error.
  • When would Redis Functions be worth the extra setup over a client-side Lua script? — When the logic is shared across multiple services/languages, needs to survive independently of any one app's deploy, or benefits from being versioned and replicated as a server-side artifact.

Common wrong answer

Treating Lua scripts as "free atomicity with no performance cost" — they buy atomicity at the same single-threaded-blocking cost as any other command, scaled by however long the script actually runs.

principalA .NET service under load shows Redis command latency spiking even though Redis's own INFO and SLOWLOG look completely healthy. Where do you look next?

Answer

When the server-side signals are clean, the bottleneck is almost always client-side: .NET thread-pool starvation is the classic culprit — if the thread pool is saturated by other blocking or CPU-heavy work, completed Redis responses sit queued waiting for a thread to run their continuation, which shows up to the app as "Redis is slow" even though the actual server round trip was fast. Check ThreadPool.GetAvailableThreads/ETW thread-pool starvation events, look for synchronous blocking calls elsewhere in the request pipeline stealing pool threads, and check the multiplexer's own GetCounters() for a growing queued-but-unsent count, which distinguishes "the client can't even get the command onto the wire fast enough" from "the command is on the wire and just waiting." A secondary, common .NET-specific cause is GC pauses under memory pressure — a large object heap under stress can pause processing long enough to look exactly like network latency in application traces.

Example

ThreadPool.GetAvailableThreads(out var workerThreads, out var ioThreads);
// compare against ThreadPool.GetMinThreads/GetMaxThreads to spot starvation

Follow-ups

  • How would you confirm thread-pool starvation versus GC pauses as the specific cause? — ETW/dotnet-trace captures both distinctly — thread-pool starvation shows queued work items with no available threads; GC pauses show up as explicit GC events correlated with the latency spikes.
  • Would increasing ThreadPool.SetMinThreads be a legitimate fix? — As a mitigation for a burst-driven starvation pattern, sometimes yes — but if something is blocking threads synchronously, that's the root cause to fix, not just a bigger pool to hide it in.
  • Does this diagnosis change if the app is under Kubernetes with CPU limits? — Yes — CPU throttling under a tight limit can produce very similar symptoms (work queued, not enough CPU time to run it) and needs to be ruled out via the container's own throttling metrics.

Common wrong answer

Concluding "Redis is slow" and reaching for a bigger Redis instance when the server's own metrics are clean — the evidence already points away from the server; the investigation needs to move to the client process.

07Eviction & memory management

Redis is an in-memory store, so what happens at the memory ceiling is core, not peripheral, knowledge — mid-level candidates should know the eviction policies cold; senior+ candidates get asked to reason about which policy fits which workload and how to detect memory pressure before it becomes an outage. Docs: redis.io/docs/latest/develop/reference/eviction.

screenerWhat happens when Redis hits maxmemory?

Answer

Behaviour depends entirely on maxmemory-policy: with the default noeviction, Redis refuses further writes with an out-of-memory error while still allowing reads (and destructive-but-freeing operations like DEL) — a hard stop, not a graceful degradation. With any of the eviction policies (allkeys-lru, volatile-lru, allkeys-lfu, volatile-lfu, allkeys-random, volatile-random, volatile-ttl), Redis instead evicts existing keys to make room for the new write, according to whichever eviction strategy is configured, and only errors if it genuinely can't free enough (e.g. volatile-* policies with no keys carrying a TTL left to evict).

Example

CONFIG SET maxmemory 4gb
CONFIG SET maxmemory-policy allkeys-lru

Follow-ups

  • Why is noeviction the default rather than an eviction policy? — Because silently deleting a write-through-consistent dataset's keys is a correctness surprise for anyone not treating Redis purely as a cache — the default is safe-by-refusal, not safe-by-guessing.
  • Does maxmemory include replication backlog and client output buffers? — It's meant to, but transient overhead (fork COW, buffers) can push actual RSS above the configured limit briefly — leave real headroom, don't size to the exact ceiling.
  • What error does a client see under noeviction at the limit? — OOM command not allowed when used memory > 'maxmemory' on write commands specifically.

Common wrong answer

Assuming Redis "just evicts old stuff automatically" regardless of configuration — the default is actually to refuse writes outright; eviction only happens if you've explicitly opted into a policy.

midExplain the difference between LRU and LFU eviction, and when LFU is the better fit.

Answer

LRU (least recently used) evicts whatever hasn't been accessed in the longest time, approximated via sampling rather than tracking exact recency for every key (an exact LRU list would be too costly to maintain at scale) — it's the right default when recency genuinely predicts future usefulness, which is true for most caches. LFU (least frequently used, since Redis 4.0) instead tracks an access-frequency counter per key (with logarithmic decay over time so old bursts don't permanently inflate a key's score), which is the better fit when a key that's accessed constantly but happened to go quiet for a few minutes shouldn't be evicted just because LRU would see it as "not recently used" — a genuinely hot key surviving a brief lull is exactly the case LFU handles better than LRU.

Example

CONFIG SET maxmemory-policy allkeys-lfu
CONFIG SET lfu-log-factor 10   # tune how quickly the frequency counter saturates

Follow-ups

  • Why is Redis's LRU "approximated" rather than exact? — Exact LRU needs a globally ordered structure updated on every access; Redis instead samples a small set of candidate keys per eviction and picks the least-recently-used among the sample, which is far cheaper and close enough in practice.
  • What does maxmemory-samples control? — How many keys are sampled per eviction decision — higher gives a closer approximation to true LRU/LFU at a small CPU cost, lower is cheaper but noisier.
  • Would you ever pick random eviction over LRU/LFU deliberately? — Rarely, but it's the cheapest possible policy (no tracking overhead at all) and can be a reasonable choice when access patterns are genuinely uniform and eviction quality doesn't matter.

Common wrong answer

Assuming LFU is "just a more accurate LRU" — they optimize for different signals (frequency vs. recency) and can produce meaningfully different eviction choices on the same workload, not just different precision on the same metric.

midWhat's the difference between allkeys-* and volatile-* eviction policies?

Answer

allkeys-* policies consider every key in the keyspace eligible for eviction regardless of whether it has a TTL; volatile-* policies only ever evict keys that have an expiry set, leaving keys with no TTL untouched no matter how much memory pressure there is (and refusing further writes with an OOM error if every remaining candidate has no TTL left to evict). This maps directly onto whether Redis is a pure cache (everything disposable, allkeys-lru or allkeys-lfu is the natural fit) or a mixed workload where some keys are genuinely persistent state that must never be silently deleted under memory pressure (volatile-*, with those permanent keys deliberately left without a TTL so they're structurally exempt).

Example

# mixed workload: cache entries get a TTL, permanent state doesn't
CONFIG SET maxmemory-policy volatile-lru
SET cache:product:1 "..." EX 600      # eligible for eviction
SET config:feature-flags "..."         # no TTL - never evicted under volatile-lru

Follow-ups

  • What happens under volatile-lru if every key has a TTL and memory is still full? — It evicts among the TTL'd keys by recency exactly like allkeys-lru would across the whole keyspace — the restriction is which keys are candidates, not the algorithm.
  • Is mixing cache and permanent state in one Redis instance a good idea at all? — It's workable with careful policy choice and naming discipline, but many teams prefer separating them (different instances or logical databases) precisely to avoid the risk of a policy misconfiguration silently evicting something irreplaceable.
  • Would volatile-ttl ever be a deliberate choice over volatile-lru? — Yes, when "evict whatever's closest to expiring anyway" is a better heuristic than recency — effectively pulling forward inevitable expiry rather than guessing by access pattern.

Common wrong answer

Running allkeys-lru against a Redis instance that also holds data with no TTL meant to be permanent — under memory pressure that "permanent" data is just as evictable as anything else, which is a data-loss surprise waiting to happen.

seniorHow do you monitor memory pressure before it becomes an incident?

Answer

INFO memory's used_memory against maxmemory is the headline number, but the more actionable early signals are evicted_keys (a rising rate means the policy is actively shedding data, worth alerting on well before it's visible as a user-facing problem) and mem_fragmentation_ratio (well above 1.0 means the OS has allocated meaningfully more than Redis's logical usage, often from allocator fragmentation after many deletes/resizes, and can itself trigger OOM behaviour before the logical maxmemory figure would suggest). At the key level, MEMORY USAGE key and redis-cli --bigkeys find specific oversized offenders; at the aggregate level, tracking used_memory trend over time (not just a point-in-time snapshot) catches slow leaks — a steadily climbing baseline unrelated to traffic growth — before they become an eviction storm or an OOM.

Example

INFO memory | grep -E "used_memory:|maxmemory:|mem_fragmentation_ratio|evicted_keys"

Follow-ups

  • What causes high fragmentation specifically, and how do you fix it? — Frequent resizing of variable-size values (growing/shrinking strings, hash rehashing) fragments the allocator's free lists; activedefrag yes runs an online defragmentation cycle to reclaim it without a restart.
  • Is a rising evicted_keys rate always a problem? — Not for a pure cache workload behaving as designed — the question is whether it's rising unexpectedly relative to traffic, or crossing into evicting keys the workload actually needed to stay hit.
  • How would you distinguish a slow memory leak from organic data growth? — Correlate used_memory growth against key-count growth and traffic volume — genuine growth tracks one of those; a leak (e.g. a client library holding stale keys, or a bug appending without TTLs) doesn't.

Common wrong answer

Monitoring only the raw used_memory value against maxmemory with no eviction-rate or fragmentation tracking — by the time raw usage alone shows a problem, eviction may already be silently shedding data you needed.

seniorTwo Redis instances hold roughly the same number of similar-sized keys but wildly different memory usage. What would you check?

Answer

First check encoding via OBJECT ENCODING across a sample of keys on each — one instance may have crossed a listpack/hashtable (or list/quicklist, set/intset) threshold that the other hasn't, and the more expensive encoding carries real per-entry overhead the compact one doesn't; this is the single most common explanation for "same data shape, different memory" between two Redis deployments running slightly different config or having grown differently over time. Second, check mem_fragmentation_ratio — one instance may simply be more fragmented from its specific history of writes/deletes even holding logically identical data. Third, check whether one is running an older/newer Redis version with different default compact-encoding behaviour (e.g. Redis 8.10's compact hashes reduce per-field overhead for hashes sharing a schema, which a pre-8.10 instance wouldn't benefit from at all even with identical logical data).

Example

redis-cli --bigkeys        # both instances
OBJECT ENCODING <sample-key>   # compare across instances
INFO memory | grep fragmentation

Follow-ups

  • Would differing maxmemory-policy settings explain this directly? — Not the memory usage itself — policy only decides what gets evicted under pressure, not how much memory the same data costs to store.
  • How would compact hashes (Redis 8.10) specifically show up here? — A hash-heavy workload on 8.10+ with many same-shaped hash values could show noticeably lower memory than the identical data on an older version, purely from the shared-schema optimization.
  • Is comparing raw DBSIZE alone a reliable signal for "same amount of data"? — No — it counts keys, not memory; two datasets with the same key count can differ hugely in per-key value size and encoding cost.

Common wrong answer

Assuming the difference must be a memory leak on one instance without first checking encoding and fragmentation — those two factors explain the large majority of "same data, different memory" cases in practice.

seniorWould you ever deliberately choose noeviction for a cache workload?

Answer

Yes — when you'd rather have a loud, immediate failure (writes erroring, alerting fires, someone gets paged) than a silent one (the cache quietly evicting keys you assumed were staying warm, degrading hit rate gradually in a way that's hard to distinguish from normal variance). This trade-off matters most when the cost of an undetected low hit rate (a slow fallback path hammering the database) is worse than the cost of a brief, visible outage that forces immediate attention — naming that inversion is what shows real judgment rather than reciting "eviction is for caches, noeviction is for databases" as a rule with no exceptions. In practice, most teams still prefer an eviction policy for pure caches because the graceful-degradation story is usually better than an outage, but it's a deliberate choice with a real alternative, not a foregone conclusion.

Example

noeviction + tight maxmemory alerting -> forces capacity planning to stay honest, at the cost of hard failures if it's wrong

Follow-ups

  • What operational discipline does choosing noeviction require that eviction policies don't? — Proactive capacity planning and alerting well before the ceiling, since there's no graceful fallback once you hit it — the safety net has to be process, not policy.
  • Does this choice change based on whether Redis holds only derived/reconstructible data? — Yes — noeviction is far more defensible when a write failure just means "retry later" rather than "the only copy of this data is now unrecoverable."
  • How would you roll out a policy change like this safely? — Stage it with tight memory-usage alerting and headroom first, so the "loud failure" is caught by monitoring rather than by users.

Common wrong answer

"Never use noeviction for a cache, that's what eviction policies are for" stated as an absolute rule — it's the right default, but treating it as the only valid answer misses a legitimate, sometimes-better trade-off.

principalDesign the memory-management strategy for a Redis instance serving three workloads with different durability needs: a hot cache, rate-limiter counters, and feature-flag config.

Answer

The cleanest answer separates these by durability need rather than forcing one eviction policy to serve all three: feature-flag config (small, permanent, must never be evicted) gets no TTL and, ideally, lives in a separate logical instance or at minimum a clearly namespaced prefix excluded from eviction reasoning; rate-limiter counters are short-lived by nature (they self-expire via their own TTL logic) so they're naturally compatible with volatile-* eviction without special-casing; the hot cache is the actual memory-pressure driver and should carry TTLs so it's eligible under volatile-lru or volatile-lfu, sized generously enough that eviction is rare rather than constant. The trade-off to name unprompted: colocating all three in one instance is operationally simpler but couples their failure/capacity stories together — a cache-driven memory spike now risks the rate limiter's or config's availability too — whereas splitting them (separate instances, or at least separate maxmemory-bounded logical databases where Cluster isn't in play) isolates blast radius at the cost of running more infrastructure.

Example

redis-config:   noeviction, no TTLs, tiny footprint, own instance
redis-cache:    volatile-lfu, TTL'd entries, sized with headroom
redis-limiter:  volatile-ttl or allkeys-lru, self-expiring by design

Follow-ups

  • Would you ever accept colocating all three for cost reasons? — For a small enough deployment, yes — the isolation benefit has to be weighed against running (and paying for) multiple instances; this is a scale-dependent call, not a universal rule.
  • How would you catch a misconfigured eviction policy evicting the config keys before it caused an incident? — Alert on evicted_keys combined with a canary read confirming specific known-permanent keys are still present — a direct check beats inferring safety from policy alone.
  • Does Redis 8's native data types (Bloom filter, etc.) change this calculus for the rate limiter? — Not fundamentally — a rate limiter's memory profile is dominated by its own TTL discipline regardless of which structure (ZSet, bitmap, native counter) implements it.

Common wrong answer

Picking one eviction policy for the whole instance without separating workloads by durability need — the policy that's safe for config is wasteful for the cache, and the policy that's efficient for the cache is dangerous for config; one size doesn't fit all three.

08Transactions, Lua & Redis Functions

Redis's transaction model surprises people coming from relational databases — no rollback, and "atomic" means something narrower than they expect — so this is a reliable place to separate candidates who've only read the docs from ones who've hit the edge cases. Senior+ candidates are expected to know when to reach for Lua/Functions instead of MULTI/EXEC and why. Docs: redis.io/docs/latest/develop/interact/transactions and redis.io/docs/latest/develop/interact/programmability.

screenerWhat does MULTI/EXEC actually guarantee, and what does it not?

Answer

MULTI queues subsequent commands on the connection without executing them; EXEC runs all queued commands back-to-back with no other client's commands interleaved between them — that's the atomicity guarantee: isolation from concurrent commands, not all-or-nothing rollback. If a command inside the transaction fails at runtime (e.g. INCR on a string that isn't a number), Redis still executes every other queued command; there is no rollback of the commands that already ran. The only thing that aborts the whole transaction before execution is a syntax/queueing-time error (an unknown command, wrong arity), which flags the transaction and causes EXEC to refuse to run any of it.

Example

MULTI
INCR counter
SET wrong-type "abc"
INCR wrong-type      # runtime error - but still executes; no rollback
EXEC                  # returns results for all three; counter WAS incremented

Follow-ups

  • Why does Redis not support rollback? — Its transaction model deliberately trades that guarantee for simplicity and performance — no undo log, no locking overhead — on the assumption that runtime errors are application bugs to catch during development, not conditions to recover from at runtime.
  • What's the difference between a queueing-time error and a runtime error here? — Queueing-time (bad command name/arity) is caught immediately when queued and aborts the whole transaction; runtime (wrong type for the operation) is only discovered during EXEC and does not stop the rest of the batch.
  • Does DISCARD help with rollback? — No — it only cancels a transaction before EXEC is called; once EXEC has run, there is nothing to discard.

Common wrong answer

Assuming Redis transactions behave like SQL transactions with rollback on error — a runtime error inside a Redis MULTI/EXEC block does not undo the commands that already succeeded.

midHow does WATCH implement optimistic locking, and when would you use it?

Answer

WATCH key [key ...] marks keys to monitor for changes; if any watched key is modified by another client between the WATCH and the subsequent EXEC, the whole transaction aborts (EXEC returns a null reply) and nothing in it runs — the classic check-then-act race is closed by detecting the "check" became stale rather than by locking. The pattern is read the current value, decide what to write based on it, WATCH the key, re-verify inside MULTI, and retry the whole read-decide-write cycle on abort. It's the right tool for compare-and-swap style updates (e.g. "increment this counter only if it hasn't already crossed a threshold") without paying for a distributed lock.

Example

// StackExchange.Redis doesn't expose WATCH/MULTI/EXEC directly (it doesn't
// guarantee a fixed connection per call), so CAS is usually done via Lua instead:
var script = LuaScript.Prepare(
    "local v = tonumber(redis.call('GET', @key)) " +
    "if v and v < @limit then return redis.call('INCR', @key) end " +
    "return -1");
var result = await db.ScriptEvaluateAsync(script, new { key = (RedisKey)"quota:user:42", limit = 100 });

Follow-ups

  • Why doesn't StackExchange.Redis expose WATCH directly? — Because it multiplexes many logical callers over shared physical connections; there's no way to guarantee your WATCH...MULTI...EXEC sequence stays pinned to one connection, so the library steers you toward Lua for atomic check-and-set instead.
  • What happens on repeated contention — does the retry loop need backoff? — Yes for high-contention keys — a tight retry loop under contention can itself become the bottleneck; jittered backoff or falling back to a real lock is worth considering if aborts are frequent.
  • Is WATCH-based CAS still useful given Lua can do the same thing atomically? — Lua is generally preferred in .NET codebases for exactly this reason — it collapses the whole read-decide-write cycle into one atomic round trip with no retry loop needed at all.

Common wrong answer

Trying to use raw WATCH/MULTI/EXEC from a StackExchange.Redis IDatabase the way you would from redis-cli — the library's connection multiplexing makes that unreliable; Lua scripting is the .NET-idiomatic equivalent.

midWhy do Lua scripts run atomically in Redis, and what's the cost of that guarantee?

Answer

Redis is single-threaded for command execution, and a Lua script runs to completion as a single unit of work on that thread — no other client's command can be interleaved partway through, which is what makes a multi-step read-modify-write inside a script genuinely atomic, stronger than MULTI/EXEC's isolation-without-rollback. The cost is exactly that single-threadedness turned against you: every other client is blocked for the script's entire duration, so a slow script (an expensive loop, a large KEYS pattern scan, an accidental O(n²)) stalls the whole instance, not just its own caller — Redis calls this out explicitly as the main scripting risk.

Example

-- fine: bounded, fast
local v = redis.call('GET', KEYS[1])
if v then return redis.call('INCR', KEYS[1]) end
return redis.call('SET', KEYS[1], 1)

-- dangerous: unbounded loop over live data blocks everyone
for i=1,tonumber(ARGV[1]) do redis.call('LPUSH', KEYS[1], i) end

Follow-ups

  • What's lua-time-limit for, and why is it mostly a diagnostic, not a fix? — It controls how long a script may run before Redis starts allowing certain commands from other clients (mainly to let you kill it via SCRIPT KILL) — but the script itself keeps running and write commands remain blocked, so it's a way to detect a stuck script, not to make it safe.
  • Can a Lua script call another Lua script? — No nested EVAL from within a script; scripts call Redis commands via redis.call/redis.pcall, not other scripts.
  • Does this atomicity extend to replicas? — The script's effects (as the resulting write commands) propagate to replicas atomically as part of normal replication, so replicas never see a partially-applied script.

Common wrong answer

Treating "Lua scripts are atomic" as a reason to put arbitrarily complex logic in them without bounding their cost — atomicity in Redis is bought by blocking every other client for the duration, so an expensive script is an outage, not just a slow call.

seniorExplain EVAL vs EVALSHA vs SCRIPT LOAD, and how a .NET client should use them.

Answer

EVAL script ... sends the full script text every call — simplest, but wastes bandwidth and CPU re-parsing the script on every invocation for a hot path. SCRIPT LOAD script registers the script server-side once and returns its SHA1; EVALSHA sha ... then runs the cached script by hash, avoiding retransmission. The catch is the script cache isn't guaranteed persistent (it can be flushed, and isn't replicated the way data is), so a correct client always has a fallback: try EVALSHA, and on a NOSCRIPT error fall back to EVAL (which also (re-)caches it). StackExchange.Redis's LuaScript.Prepare handles exactly this dance for you, computing the hash, calling EVALSHA, and transparently reloading via EVAL on a cache miss — which is why idiomatic .NET code almost never calls EVAL/EVALSHA directly.

Example

var script = LuaScript.Prepare("return redis.call('GET', @key)");
var loaded = script.Load(server);           // registers + caches the SHA
var result = await db.ScriptEvaluateAsync(loaded, new { key = (RedisKey)"k" });
// ScriptEvaluateAsync retries via EVAL automatically on NOSCRIPT

Follow-ups

  • Why can the script cache be evicted or lost? — SCRIPT FLUSH, a server restart, or failover to a replica that never saw the SCRIPT LOAD can all leave a hash unrecognized — NOSCRIPT handling isn't an edge case, it's routine.
  • Are scripts replicated to replicas automatically? — The script's cache entry itself isn't guaranteed to propagate; what replicates is the effect of running it (the resulting writes) — which is another reason a naive client assuming the hash is always valid on any node will eventually hit NOSCRIPT.
  • Would you ever call EVAL directly instead of EVALSHA? — For a script called rarely enough that caching gains nothing, or during development/debugging where the transmission cost doesn't matter — for anything on a hot path, cache it.

Common wrong answer

Calling EVALSHA directly with a hardcoded hash and no fallback path — the cache can be evicted at any time, and an unhandled NOSCRIPT becomes a production error that a two-line fallback would have absorbed.

seniorWhat are Redis Functions (7.0+), and why prefer them over ad-hoc Lua scripts for production logic?

Answer

Functions (Redis 7.0+) package Lua code into named, versioned libraries registered with FUNCTION LOAD, then invoked by name via FCALL/FCALL_RO — unlike loose EVAL/EVALSHA scripts, a library is a first-class server object: it's included in DUMP/RDB persistence and AOF automatically, survives restarts and replication without any client-side re-registration dance, and can be introspected (FUNCTION LIST) and atomically replaced (FUNCTION LOAD REPLACE). For any script that's genuinely part of the application's logic (not a one-off), this solves the operational fragility of ad-hoc scripts — no more NOSCRIPT handling, no more wondering if a replica has the hash cached — at the cost of a slightly heavier registration step and a dependency on Redis 7.0+.

Example

#!lua name=mylib
redis.register_function('my_incr_capped', function(keys, args)
  local v = tonumber(redis.call('GET', keys[1]) or '0')
  local limit = tonumber(args[1])
  if v < limit then return redis.call('INCR', keys[1]) end
  return -1
end)
FUNCTION LOAD "#!lua name=mylib ..."
FCALL my_incr_capped 1 quota:user:42 100

Follow-ups

  • Does StackExchange.Redis have first-class Functions support? — It exposes them via the generic command path (ExecuteAsync("FCALL", ...)) rather than a dedicated typed API the way ScriptEvaluateAsync wraps EVAL — usable, but with less ceremony than scripts get.
  • Is atomicity the same as with plain scripts? — Yes — a function body runs with the same single-threaded, run-to-completion guarantee as a Lua script; the packaging changes, not the execution model.
  • Would you migrate existing production Lua scripts to Functions? — Worth it for anything long-lived and important enough that persistence/replication of the code itself matters — not worth the churn for a script that's genuinely ad-hoc or one-off.

Common wrong answer

Saying "Functions replaced Lua scripting in Redis 7" — EVAL/EVALSHA are still fully supported and still the simpler choice for ad-hoc or one-off logic; Functions are an additional, more operationally robust option for production-grade scripted logic, not a deprecation of scripts.

seniorA Lua script that's been running fine for months suddenly causes latency spikes across the whole instance. How do you diagnose it?

Answer

First confirm it's actually a script: SLOWLOG GET will show the EVALSHA/FCALL entry with its duration, and INFO commandstats shows call counts and cumulative time. If a script is genuinely stuck mid-execution right now, SCRIPT KILL can abort it if and only if it hasn't executed a write yet (Redis refuses to kill a script that's already written, to avoid leaving data in an inconsistent half-applied state) — otherwise a full SHUTDOWN NOSAVE/restart may be the only way out, which is the real cost of a stuck write-performing script. The actual root cause is almost always data growth: a script that iterated a bounded collection when written now iterates one that's grown 100x, and nothing about the script changed — only the size of what it's looping over did. The fix is bounding the work per invocation (paginating, capping, moving the iteration to the client with multiple smaller calls) rather than trying to make the single call faster in place.

Example

SLOWLOG GET 10
SCRIPT KILL          # only works pre-first-write
INFO commandstats | grep -i evalsha

Follow-ups

  • Why won't Redis kill a script that's already written data? — Because aborting mid-write could leave keys in a state no valid execution path would ever produce — Redis prioritizes not corrupting data over responsiveness here.
  • How would you have caught this before it became an incident? — Track the target collection's size over time (or the script's own SLOWLOG duration trend) — a script whose input is unbounded-by-design should be flagged as a latent risk at review time, not discovered when it finally blows up.
  • Would rewriting the logic as a Redis Function have prevented this? — No — Functions share the identical execution/blocking model; the fix is bounding the work, not the packaging.

Common wrong answer

Assuming SCRIPT KILL always safely stops a runaway script — it only works before the script's first write; a script that read, then wrote, then is looping cannot be killed without a full instance restart.

principalYou need to atomically move an item between two lists (a work queue and an in-progress queue) with retry-safe semantics. Would you use MULTI/EXEC, a Lua script, or client-side logic — and why?

Answer

The built-in LMOVE (or its blocking form BLMOVE) already does exactly this atomically as a single command — that's the first thing worth naming: reaching for scripting before checking whether a native command already provides the atomicity you need is itself a judgment call interviewers are probing for. Where this genuinely needs custom logic (e.g. the move is conditional on the item's content, or must also update a per-item status hash in the same atomic step), a Lua script is the right tool over MULTI/EXEC: the "read the item, decide, move it, stamp its status" sequence needs real conditional logic between the read and the write, which MULTI/EXEC can't express (its commands are queued blind, with no branching on intermediate results) but a script can, atomically. Client-side logic with WATCH-based retry is the fallback only if the logic is too complex or too dynamic to comfortably express in Lua — and it introduces exactly the retry-loop-under-contention cost that a script avoids by being a single round trip.

Example

-- move + conditionally stamp status atomically
local item = redis.call('RPOPLPUSH', KEYS[1], KEYS[2])
if item then redis.call('HSET', KEYS[3], item, 'in-progress') end
return item

Follow-ups

  • Why is retry-safety worth naming explicitly for a work-queue move? — A worker crashing after RPOPLPUSH/LMOVE but before finishing the job leaves the item stranded in the in-progress list — the atomic move alone doesn't solve at-least-once processing; that needs a separate reaper (a periodic scan for items stuck in-progress past a timeout, moved back to the work queue).
  • Would Redis Streams be a better fit for this than two lists? — Often yes at scale — Streams' consumer groups give you exactly this claim/ack/reclaim lifecycle (XREADGROUP, XACK, XCLAIM/XAUTOCLAIM) natively, without hand-rolling the two-list pattern and its reaper.
  • What's the cost of defaulting to Lua for everything instead of checking for a native atomic command first? — Unnecessary blocking-time-on-the-server for logic a single native command would have handled with less code and no scripting overhead at all.

Common wrong answer

Reaching straight for a Lua script (or worse, WATCH/MULTI/EXEC with client-side retry) without first checking that LMOVE/BLMOVE already provides the atomic move as a single native command — scripting should be the answer to logic Redis doesn't already express, not a replacement for commands that do.

09Distributed locking & concurrency

Distributed locking is where Redis interviews get genuinely hard: the basic pattern is easy to state, but the failure modes (clock drift, GC pauses, network partitions, lock-expiry-during-critical-section) are exactly the kind of thing that separates a candidate who's implemented this in production from one who's only read a blog post. Expect senior+ candidates to know the Redlock controversy by name and have an actual opinion. Docs: redis.io/docs/latest/develop/use/patterns/distributed-locks.

midWhat's the basic single-instance distributed lock pattern in Redis?

Answer

SET lock:resource token NX PX 30000 in one atomic command: NX means it only succeeds if the key doesn't already exist (so only one caller can "win" the lock), PX attaches a millisecond TTL so a crashed holder's lock self-expires rather than deadlocking everyone else forever, and the token is a unique value (a GUID, not a constant) identifying this specific acquisition. Doing the set-if-absent-with-expiry as one atomic command matters because two separate calls (SETNX then EXPIRE) leave a window where a crash between them creates a lock with no TTL at all — a permanent deadlock waiting to happen.

Example

var token = Guid.NewGuid().ToString();
bool acquired = await db.StringSetAsync("lock:order:42", token,
    TimeSpan.FromSeconds(30), When.NotExists);

Follow-ups

  • Why must the token be unique per acquisition rather than a fixed value? — So release can verify it's removing its own lock, not one a different holder acquired after this one expired — covered in depth in the next question.
  • What happens if the critical section takes longer than the TTL? — The lock expires while still "held," another caller can acquire it, and now two callers believe they hold the lock simultaneously — the core distributed-locking failure mode, addressed by lock extension (see below) or, better, by designing the critical section to be safely retryable/idempotent.
  • Is SET NX PX atomic even under StackExchange.Redis's connection multiplexing? — Yes — it's a single Redis command, so multiplexing (which affects how commands share connections, not command atomicity) is irrelevant to its correctness.

Common wrong answer

Implementing this as separate SETNX and EXPIRE calls — a crash or restart between the two leaves a lock key with no TTL, which never self-releases and deadlocks anyone waiting on that resource until manual intervention.

seniorWhy does releasing a lock need a unique token and a check-then-delete script, rather than just DEL?

Answer

If the holder's critical section runs longer than the lock's TTL, the lock can expire and be re-acquired by a different caller before the original holder finishes and calls DEL — an unconditional DEL at that point deletes the new holder's lock, not the caller's own (already-expired) one, so two callers now believe they're unlocked/holding correctly while a third caller could acquire next, and the mutual-exclusion guarantee is broken. The fix is storing a unique token as the lock's value at acquisition time and releasing only via a Lua script that atomically checks the stored value still matches the caller's own token before deleting — that single round trip closes the check-then-act race that a separate GET-then-DEL from the client would reopen.

Example

-- safe release: only delete if we still own it
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0

Follow-ups

  • Why can't the client just GET then conditionally DEL without Lua? — Between the client's GET and its subsequent DEL, the lock could expire and be re-acquired by someone else — the same TOCTOU race the token was meant to close, just moved one level up; the check-and-delete has to be atomic on the server.
  • Does StackExchange.Redis provide this pattern built in? — IDatabase.LockTake/LockRelease/LockExtend implement exactly this token-based take/verify-and-release/extend pattern, so idiomatic .NET code rarely hand-rolls the Lua script.
  • What should happen if release fails because the token no longer matches? — Nothing destructive — it means this caller's lock already expired and moved on; treat the critical section as having potentially run concurrently with someone else and let whatever idempotency/detection you built handle it, don't retry the delete.

Common wrong answer

Releasing with a plain DEL lock:key regardless of who currently holds it — this is safe only if the lock can never expire while still logically held, which is precisely the assumption that breaks under load, GC pauses, or a slow critical section.

seniorExplain the Redlock algorithm and what problem it's trying to solve beyond a single-instance lock.

Answer

Redlock runs the lock-acquisition attempt against N independent Redis instances (typically 5), requiring the majority (N/2+1) to grant the lock within a tight time budget before the total elapsed time exceeds the lock's validity window — the point is surviving the failure of any single instance: a lock backed by one Redis node is only as available as that node, and its failure (or a network partition isolating it) shouldn't take down every lock in the system. The algorithm accounts for network latency during acquisition by subtracting the time spent acquiring from the effective remaining validity, and only declares success if the majority-quorum was reached with enough validity time left to be useful.

Example

5 independent Redis nodes, lock TTL 10s
Client tries SET NX PX on all 5 sequentially with a short per-node timeout
Locked iff: quorum (3+) succeeded AND elapsed time << 10s remaining validity

Follow-ups

  • Why does it need a majority rather than all N nodes? — Requiring all N would make the lock unavailable the moment any single node is down or slow, defeating the purpose of distributing it — majority quorum tolerates minority failures while still preventing two disjoint majorities from both granting the same lock.
  • Do the 5 nodes need to be a Redis Cluster or replicated? — No — they're meant to be independent, unrelated instances (ideally no shared failure domain) specifically so one instance's failure doesn't correlate with another's; running them as a single Cluster/replica set undermines the independence assumption.
  • What's the practical adoption level of Redlock vs a single-instance lock? — Most real-world .NET systems use a single well-monitored Redis (or a Cluster/Sentinel-backed one for availability) with a token-based lock rather than running a bespoke 5-node Redlock deployment — Redlock is more discussed in interviews than actually deployed, precisely because of the controversy below.

Common wrong answer

Describing Redlock as "just take the lock on multiple Redis servers for redundancy" without mentioning the quorum-plus-timing-budget mechanics — the timing budget is exactly the part that's both essential to its safety argument and the part its critics say is unreliable in practice (see next question).

seniorWhat is Martin Kleppmann's critique of Redlock, and do you find it convincing?

Answer

Kleppmann's argument (in his widely-cited "How to do distributed locking" post) is that Redlock's safety depends on assumptions that don't hold in real systems: it assumes bounded clock drift and bounded process pauses, but a GC pause, a hypervisor stall, or NTP clock jump can make a client believe it still holds a valid, unexpired lock well after the lock has actually expired elsewhere — the client then proceeds into the critical section unaware another client has since acquired the same lock, exactly the failure Redlock was supposed to prevent. His broader point is that Redlock provides "locking with a deadline" (fine for reducing duplicate work, e.g. skipping a redundant cache refresh) but not the strict mutual-exclusion guarantee needed to protect something like a write to a shared external resource, for which he argues you need fencing tokens enforced by the resource itself, not trust in the lock alone. It's a strong, well-reasoned critique that most practitioners now treat as settled — the practical takeaway is to know whether your actual use case needs Redlock's stronger (but imperfect) guarantee or just "best-effort, reduce duplicate work," and to add fencing tokens at the protected resource if correctness genuinely depends on exclusivity.

Example

Client A acquires lock (TTL 10s), then GC-pauses for 15s
Lock expires at t=10s; Client B acquires it at t=11s, starts work
Client A resumes at t=15s, believes it still holds the lock, proceeds too
-> both clients now think they exclusively hold it

Follow-ups

  • What is a fencing token and how does it fix this? — A monotonically increasing number issued with each lock grant; the protected resource itself rejects any write tagged with a token lower than the highest it's already seen — so even if Client A proceeds believing it still holds the lock, its stale token gets rejected at the point of actual harm, rather than trusting the lock alone.
  • Does Redis's own creator (antirez) agree with Kleppmann? — He published a rebuttal defending Redlock's design under the assumptions it states, while acknowledging the assumptions themselves (bounded clocks/pauses) are the crux — it's a genuine, still-cited disagreement between two credible sources, not a settled "one side was simply wrong."
  • Does this critique mean Redis-based locking is useless? — No — for use cases tolerant of the rare double-execution (deduplicating a scheduled job, coalescing a cache refresh) a Redis lock is simple and effective; the critique specifically targets using it as the sole guarantee for something that must never run twice.

Common wrong answer

Dismissing the critique as purely theoretical ("GC pauses that long never happen in practice") — production GC pauses, container CPU throttling, and hypervisor stalls of several seconds are well documented and are exactly the scenario the critique is about, not an exotic edge case.

seniorHow would you implement lock extension (a "watchdog") for a critical section of unpredictable duration?

Answer

Acquire the lock with a modest TTL (long enough to cover typical work, short enough to fail fast if the holder dies), then run a background timer that periodically extends the TTL (via a check-and-set-expiry Lua script verifying the token still matches, the same safety property release needs) as long as the critical section is still running — if the holder crashes, the watchdog stops firing and the lock simply expires on its own after the last extension's TTL elapses, with no special crash-handling code needed. StackExchange.Redis's LockExtend exposes exactly this token-verified extend operation; the watchdog is usually a simple periodic timer in application code calling it every TTL/3 or so, cancelled when the critical section completes or the process is shutting down cleanly.

Example

var token = Guid.NewGuid().ToString();
await db.LockTakeAsync("lock:job:99", token, TimeSpan.FromSeconds(15));
using var timer = new Timer(async _ =>
    await db.LockExtendAsync("lock:job:99", token, TimeSpan.FromSeconds(15)),
    null, TimeSpan.FromSeconds(5), TimeSpan.FromSeconds(5));
try { /* critical section */ } finally { await db.LockReleaseAsync("lock:job:99", token); }

Follow-ups

  • What happens if the watchdog itself stalls (e.g. thread-pool starvation) while the critical section is still genuinely running? — The lock expires and can be re-acquired even though the original holder is still alive and working — this is the Kleppmann failure mode again; a watchdog reduces the window but doesn't eliminate the fundamental risk, which is why fencing tokens matter for anything where that matters.
  • Why extend at TTL/3 rather than right before expiry? — Margin for the extend call itself to be delayed or fail once and still succeed on a retry before the original TTL runs out.
  • Is this pattern specific to Redis, or does e.g. ZooKeeper avoid the need for it? — ZooKeeper's session-based ephemeral nodes tie lock lifetime to an active client session with server-side heartbeating, which is a materially different (and often considered stronger) model than a client-driven TTL extension — worth naming as an alternative if the interviewer asks "would another system handle this better."

Common wrong answer

Setting a very long TTL "to be safe" instead of implementing extension — that just trades one failure mode (premature expiry mid-critical-section) for another (a crashed holder's lock now blocks everyone for the full long TTL instead of failing fast).

principalDesign locking for a payment-reservation step that must never execute twice for the same order, even under node failures and clock skew.

Answer

The judgment call to name first: a bare Redis lock (single-instance or Redlock) is the wrong tool as the sole guarantee here, precisely because of the Kleppmann failure mode — "must never execute twice" is a correctness requirement, and Redis locking alone provides best-effort mutual exclusion, not a proof. The design layers three things: (1) a Redis lock (simple, single-instance is fine) to make the common case fast and avoid unnecessary contention/duplicate work; (2) a monotonic fencing token issued alongside the lock (e.g. an INCR'd sequence number stored with it) passed through to the actual payment-reservation call; (3) idempotency enforced at the resource that actually matters — the payment provider or the ledger itself rejecting (or safely no-op'ing) a reservation call carrying a token/idempotency-key it's already seen or one lower than the highest it's processed for that order. The lock optimizes the happy path; the fencing token plus provider-side idempotency is what actually makes the "never twice" guarantee hold even if the lock's assumptions are violated.

Example

token = INCR fence:order:42          -- monotonic, survives lock loss
acquire lock:order:42 (best-effort, reduces duplicate attempts)
call PaymentProvider.Reserve(orderId, idempotencyKey: $"order:42:fence:{token}")
-- provider rejects/no-ops a replay of the same or a stale fencing token

Follow-ups

  • Why not just make the Redis lock's TTL very generous and call it done? — No TTL choice removes the possibility of a paused/GC-stalled client resuming after expiry and believing it still holds the lock — the risk is structural to client-driven TTL locks, not a tuning problem.
  • What if the payment provider has no idempotency-key support? — Then the ledger/database write itself needs a uniqueness constraint (e.g. a unique index on (order_id, attempt_fence_token)) that rejects the duplicate at the last possible point — the guarantee has to live somewhere durable and transactional, not in Redis alone.
  • Does this change if you're allowed "at-most-once with manual reconciliation" instead of strict exactly-once? — Yes — if a rare double-charge can be caught and reversed by a reconciliation job, the bar drops and a simpler Redis-lock-plus-alerting design becomes acceptable; naming which guarantee the business actually needs (and its cost) is itself part of a strong answer.

Common wrong answer

Presenting a Redis distributed lock (even Redlock) as sufficient on its own for a "must never happen twice" financial operation — a strong answer explicitly identifies that the correctness guarantee has to be enforced at the resource itself via idempotency/fencing, with Redis locking as an optimization layered on top, not the source of truth for exclusivity.

10Pub/Sub & Streams

Pub/Sub is simple and everyone should know its one big caveat (no persistence, no replay); Streams are the more interesting territory for senior+ candidates because they're Redis's answer to "give me Kafka-like semantics without running Kafka," with genuine consumer-group mechanics worth understanding in depth. Docs: redis.io/docs/latest/develop/interact/pubsub and redis.io/docs/latest/develop/data-types/streams.

screenerHow does Redis Pub/Sub work, and what's its biggest limitation?

Answer

PUBLISH channel message sends a message to every client currently subscribed to that channel via SUBSCRIBE channel; delivery is fire-and-forget with zero persistence — if a subscriber isn't connected at the moment of publish (network blip, restart, slow consumer), that message is gone forever, with no buffering, no replay, and no delivery guarantee whatsoever. This makes Pub/Sub a good fit for ephemeral broadcast (cache-invalidation notifications, live presence/typing indicators, real-time dashboards where a missed update is harmless because the next one supersedes it) and a poor fit for anything where a missed message is a correctness problem — that's what Streams exist for.

Example

# subscriber
SUBSCRIBE cache-invalidations
# publisher (any other client)
PUBLISH cache-invalidations "product:123"

Follow-ups

  • Does a subscribed client block other operations on its connection? — Yes, largely — once a connection issues SUBSCRIBE it's mostly restricted to subscribe/unsubscribe/ping commands; StackExchange.Redis handles this by using a dedicated connection for subscriptions under the hood.
  • Does Pub/Sub work across a Redis Cluster? — Yes, but by default messages are propagated to every node in the cluster regardless of where subscribers are, which doesn't scale — sharded Pub/Sub (SPUBLISH/SSUBSCRIBE, Redis 7.0+) confines propagation to the slot's own shard for better scalability in Cluster mode.
  • Would you use Pub/Sub for anything involving money or state that must not be lost? — No — that's the canonical wrong use case; anything requiring durability or replay belongs in Streams or a proper message queue.

Common wrong answer

Assuming a message published while a subscriber's connection was briefly reconnecting is queued somewhere and delivered on reconnect — Pub/Sub has no buffering at all; a disconnected subscriber simply misses everything published during the gap.

midWhat does PSUBSCRIBE add over plain SUBSCRIBE, and how would you use it from StackExchange.Redis?

Answer

PSUBSCRIBE matches channels by glob-style pattern rather than exact name, so one subscription can receive messages published to any channel matching e.g. events.* without knowing every channel name in advance — useful when the set of channels is dynamic (per-tenant, per-user) rather than fixed. In StackExchange.Redis, ISubscriber.Subscribe/SubscribeAsync take a RedisChannel that can be constructed as a pattern (RedisChannel.Pattern("events.*")) versus a literal channel, and the same connection can hold many subscriptions (exact and pattern) simultaneously.

Example

var sub = redis.GetSubscriber();
await sub.SubscribeAsync(RedisChannel.Pattern("events.*"), (channel, message) =>
{
    Console.WriteLine($"{channel}: {message}");
});

Follow-ups

  • Does pattern matching cost more per-publish than exact-channel matching? — Yes, modestly — Redis has to check the published channel against every active pattern rather than a direct hash lookup, so a very large number of active patterns is a (rarely hit) scaling concern.
  • How does StackExchange.Redis keep pub/sub responsive alongside regular command traffic? — It maintains a separate physical connection dedicated to subscriptions, so a burst of published messages doesn't queue up behind (or block) unrelated command calls on the multiplexer.
  • What happens to subscriptions across a reconnect (e.g. after a failover)? — StackExchange.Redis automatically re-issues active subscriptions on the new connection, though messages published during the gap are still lost — reconnection restores the subscription, not the missed history.

Common wrong answer

Assuming PSUBSCRIBE patterns support regex — they're glob-style (*, ?, character classes), not regular expressions.

midDescribe the Streams data model: what is a stream entry, and what is an entry ID?

Answer

A stream (XADD) is an append-only log of entries, each entry a field-value map (like a mini hash) automatically assigned a unique, strictly increasing ID unless you supply your own — the default auto-generated ID is <millisecond-timestamp>-<sequence>, so IDs are naturally time-ordered and the sequence disambiguates multiple entries added within the same millisecond. Unlike Pub/Sub, entries persist in the stream (subject to trimming) so any consumer can read from any point in history by ID, including replaying from the beginning, which is the core capability Pub/Sub lacks entirely.

Example

XADD orders * order_id 42 status pending      # * = auto-generate ID
XRANGE orders - +                                # read all entries in order
XADD orders MAXLEN 10000 * order_id 43 status paid  # cap stream size while adding

Follow-ups

  • How do you keep an unbounded stream from growing forever? — MAXLEN (approximate, cheaper) or MINID trimming, either applied on every XADD or via a separate XTRIM call — a stream with no trimming strategy grows without bound just like an unbounded list.
  • Can you supply your own entry ID instead of *? — Yes, but it must be strictly greater than the stream's current last ID — this is occasionally used to encode meaningful IDs, but the auto-generated timestamp-sequence form is the common case.
  • How is this different from a List used as a queue? — A List is destructive-by-default (LPOP/RPOP remove the entry) with no native concept of "multiple independent readers each tracking their own position" — a Stream's entries persist and multiple consumers/consumer-groups can each read the same log at their own pace.

Common wrong answer

Treating a Stream like a List with extra metadata — the persistent, replayable, ID-addressed log model plus native consumer-group support is a different tool from a List, not a decorated version of one.

seniorExplain consumer groups: XREADGROUP, the pending entries list (PEL), and XACK.

Answer

A consumer group (XGROUP CREATE) lets multiple consumers cooperatively process one stream, each entry delivered to exactly one consumer within the group (load-balanced, not broadcast) via XREADGROUP GROUP group consumer .... When a consumer reads an entry via the group, it's added to that consumer's entry in the pending entries list (PEL) — a per-consumer record of "delivered but not yet acknowledged" — and stays there until the consumer calls XACK to confirm successful processing. This is what gives Streams at-least-once delivery: if a consumer crashes after reading but before acking, the entry remains in the PEL, visibly stuck against that (now-dead) consumer, ready to be claimed by someone else — nothing is silently lost the way an unacknowledged Pub/Sub message would be.

Example

XGROUP CREATE orders workers $ MKSTREAM
XREADGROUP GROUP workers consumer-1 COUNT 10 STREAMS orders >
# ... process entries ...
XACK orders workers 1694000000000-0

Follow-ups

  • What does the > in STREAMS orders > mean? — Deliver only entries never yet delivered to this group — as opposed to a specific ID, which would re-read that consumer's own already-delivered-but-unacked history instead of new entries.
  • Does an unacked entry get redelivered automatically? — Not automatically to a different consumer — it stays assigned to its original consumer in the PEL until something actively reclaims it (XCLAIM/XAUTOCLAIM, see below); a crashed consumer's entries don't move on their own.
  • How do you inspect what's stuck in the PEL? — XPENDING orders workers summarizes it; with extra arguments it lists individual pending entries, their consumer, and how long they've been pending — the starting point for building a reaper.

Common wrong answer

Assuming XREADGROUP alone guarantees delivery is "handled" — without a process that watches the PEL and reclaims entries stuck behind a dead consumer, at-least-once delivery is only a capability the API offers, not something that happens automatically.

seniorHow do you recover stream entries stuck behind a crashed consumer?

Answer

XCLAIM transfers ownership of specific pending entry IDs to a different (live) consumer, provided they've been pending longer than a specified idle time — you typically drive this from XPENDING's output, filtering for entries idle past your processing-timeout threshold. XAUTOCLAIM (Redis 6.2+) is the more convenient version: give it a min-idle-time and a starting cursor, and it finds and claims a batch of eligible stuck entries in one call, no separate XPENDING scan needed — this is the building block for a "reaper" background job that periodically claims and reprocesses anything left pending too long, closing the loop that makes consumer-group delivery genuinely at-least-once in practice, not just in theory.

Example

XAUTOCLAIM orders workers reaper-consumer 60000 0
# claims entries idle >=60s, starting cursor 0, assigns to reaper-consumer

Follow-ups

  • What idle-time threshold should a reaper use? — Comfortably above the slowest expected legitimate processing time for that stream — too short reclaims work that's still genuinely in progress (risking duplicate processing more often than necessary); too long delays recovery from real crashes.
  • Does claiming an entry guarantee it hasn't already been fully processed by the original consumer? — No — the original consumer might have finished the work but crashed before calling XACK; this is why stream-consumer logic needs to be idempotent, exactly like any at-least-once delivery system.
  • Is there a way to just delete entries that are permanently stuck (e.g. genuinely poison messages)? — Yes — after claiming, if processing repeatedly fails, ack it anyway (to remove it from the PEL) and route it to a dead-letter stream for manual inspection, rather than looping forever.

Common wrong answer

Assuming a crashed consumer's pending entries are automatically picked up by other consumers in the group — nothing reassigns them without an explicit XCLAIM/XAUTOCLAIM call; without a reaper process, they simply sit in the PEL indefinitely.

seniorHow do Redis Streams compare to Kafka, and when would you pick one over the other?

Answer

Streams give you a genuinely comparable core model — an append-only, ID-ordered log with consumer groups providing load-balanced, ack-tracked, replay-capable consumption — but at a very different operational scale and with very different durability defaults: Kafka's log is disk-backed, designed for retention measured in days/weeks and throughput in the millions of messages/second across partitioned topics with configurable replication, while a Redis Stream lives in the same memory-bound, (by default) less durable instance as everything else Redis holds, sized for retention measured in thousands-to-millions of entries via MAXLEN/MINID trimming rather than long-term archival. The practical decision: if you already run Redis and need reliable, replayable, moderate-volume event processing without standing up new infrastructure, Streams are a very good fit and meaningfully simpler to operate; if you need long-term retention, very high throughput, strong ordering guarantees across a large partition count, or a mature ecosystem of connectors, Kafka (or a managed equivalent) is the right tool and Streams would be straining past their design point.

Example

Redis Streams: order-status events for a mid-size app, retained 24-48h, <10k msgs/sec
Kafka: clickstream/analytics pipeline, retained weeks, 100k+ msgs/sec, multiple downstream consumers

Follow-ups

  • Does enabling AOF make Streams as durable as Kafka's log? — Closer, but not equivalent — Streams still live in a memory-bound dataset sized to fit RAM, and Redis's replication/failover story, while solid, doesn't match Kafka's partition-replica model built specifically for log durability at scale.
  • Can Streams do partitioned, ordered-per-key consumption like Kafka partitions? — Not natively in the same way — you'd typically use multiple streams (one per shard key) rather than partitions within one stream, which is a coarser mechanism than Kafka's partition assignment.
  • Would you migrate off Streams to Kafka as a system scales, or run both? — Often both, for different jobs — Streams for the lighter-weight, already-in-Redis event flows and Kafka introduced specifically when a workload's volume/retention/fan-out genuinely outgrows what Streams comfortably handles, rather than treating it as an all-or-nothing platform decision.

Common wrong answer

Claiming "Streams are just a lightweight Kafka" or, conversely, dismissing them as "not real messaging" — they cover a genuinely useful, materially different point on the durability/throughput/operational-complexity spectrum, not a strictly worse clone of Kafka.

midWhat are keyspace notifications, and what's a realistic use case?

Answer

With notify-keyspace-events configured (e.g. KEA for all key events), Redis publishes a Pub/Sub message on internal channels (__keyspace@0__:key and/or __keyevent@0__:expired-style channels) whenever a key is modified, expired, or evicted — turning otherwise-invisible internal events into something application code can subscribe to. The canonical use case is reacting to expiry: e.g. a session-timeout side-effect (notify a user, clean up related state) triggered by subscribing to expired-key events rather than polling for "is this key gone yet," or invalidating a local in-process cache the moment the backing Redis key changes.

Example

CONFIG SET notify-keyspace-events Ex     # expired events only
SUBSCRIBE __keyevent@0__:expired
# publishes the expired key's name as the message when it fires

Follow-ups

  • Does this add meaningful overhead? — Yes if enabled broadly (KEA, every event type) on a write-heavy instance — publishing a notification per relevant operation has a real cost; scope notify-keyspace-events to only the event classes you actually need (e.g. just Ex for expiry).
  • Are keyspace notifications reliable the way Streams are? — No — they're plain Pub/Sub under the hood, so they inherit the same no-persistence, no-replay limitation; a disconnected subscriber misses events just like any other Pub/Sub channel.
  • Would you use this for cache invalidation across multiple app instances? — It's a reasonable lightweight approach for "notify other instances a key changed so they can drop their local cache" — best-effort is acceptable there since a missed notification just means a slightly staler local cache, not a correctness failure.

Common wrong answer

Relying on keyspace notifications for something that must not be missed (e.g. as the sole trigger for a billing action on expiry) — they carry the same fire-and-forget guarantee as any other Pub/Sub channel, which is a poor fit for anything requiring reliable delivery.

principalDesign a reliable event pipeline for order-status changes that downstream services must not miss, using Redis. Would you use Pub/Sub, Streams, or Lists — and why?

Answer

Pub/Sub is disqualified immediately — "must not miss" is precisely the guarantee it doesn't offer. Lists (as a queue via LPUSH/BRPOP or the atomic LMOVE pattern) give reliable single-consumer-at-a-time delivery but no native replay, no multiple-independent-consumer-groups, and no visibility into what's in flight without extra bookkeeping. Streams with consumer groups are the right fit: XADD gives a durable (subject to persistence config), replayable log; consumer groups let multiple independent downstream services (billing, fulfillment, analytics) each track their own read position over the same underlying log without interfering with each other, exactly the fan-out reliable-delivery shape order-status changes need; the PEL plus a reaper (XAUTOCLAIM) gives at-least-once delivery with visibility into what's stuck. The trade-off to name unprompted: this durability still rides on the same instance's persistence/replication configuration as everything else in Redis (AOF with a sensible appendfsync, replicas, monitored trimming so the stream doesn't grow past available memory) — Streams get you the API and mechanics of reliable delivery, but the actual durability guarantee is only as strong as the surrounding Redis deployment's persistence and HA configuration, which has to be deliberately set up, not assumed.

Example

XADD orders:status * order_id 42 status shipped
XGROUP CREATE orders:status billing $ MKSTREAM
XGROUP CREATE orders:status fulfillment $ MKSTREAM
-- each service reads/acks independently via XREADGROUP; reaper claims stale PEL entries

Follow-ups

  • What if a downstream service needs to process events in strict order? — A single consumer per group per stream preserves order; parallelizing within a group (multiple consumers) trades ordering guarantees for throughput — name that trade-off explicitly if order matters for a given consumer.
  • How would you size MAXLEN trimming without losing data downstream still needs? — Trim based on the slowest consumer group's actual lag (visible via XINFO GROUPS), not a fixed arbitrary count — trimming past what a lagging consumer hasn't yet read is silent data loss for that consumer.
  • At what point would you tell the team Redis Streams are the wrong choice here? — If retention needs stretch to weeks, if throughput requirements push well past what a single Redis instance's memory/CPU can comfortably hold, or if the org already operates Kafka elsewhere and duplicating a second event-streaming platform adds more operational cost than it saves.

Common wrong answer

Reaching for Pub/Sub because "it's simpler" without registering that simplicity is bought by dropping the exact guarantee ("must not miss") the requirement states — for this specific requirement, Pub/Sub isn't a simpler valid option, it's a disqualified one.

11Performance & latency debugging

This is where lead/principal candidates are actually differentiated — not "is Redis fast" (everyone says yes) but "here's the specific methodology I'd use to find out why it isn't, right now, in this incident." Expect scenario-driven questions more than definitional ones. Docs: redis.io/docs/latest/operate/.../latency.

screenerWhat is SLOWLOG and how do you use it?

Answer

SLOWLOG records commands whose execution time exceeded slowlog-log-slower-than microseconds (default 10000 = 10ms), keeping the most recent slowlog-max-len entries in a ring buffer — SLOWLOG GET lists them with timestamp, duration, the command and its arguments, letting you see exactly which commands are the actual outliers rather than guessing from aggregate latency metrics. It's the first place to look when overall latency looks fine on average but something is intermittently slow.

Example

CONFIG SET slowlog-log-slower-than 5000   # 5ms threshold
SLOWLOG GET 10
SLOWLOG RESET

Follow-ups

  • Does the recorded duration include time waiting in the queue, or only actual execution? — Only the command's own execution time on the server, not time spent waiting behind other commands or in network transit — that's a separate thing to check (queue depth, network RTT) if slowlog looks clean but client-observed latency is still high.
  • What's a sane threshold to leave permanently enabled in production? — Something well above your P99 target but well below "clearly broken" — 5-10ms is common; too low fills the ring buffer with noise, too high hides real problems.
  • Does slowlog persist across restarts? — No — it's in-memory only, gone on restart; if you need historical trend data, ship it to external monitoring rather than relying on the ring buffer alone.

Common wrong answer

Treating slowlog duration as the client-observed latency for that request — it's server-side execution time only; the client may have experienced additional queueing or network delay on top of what slowlog reports.

midWhy is KEYS * dangerous in production, and what's the safe alternative?

Answer

KEYS is O(N) over the entire keyspace and, being a single command executed to completion on Redis's single command-processing thread, blocks every other client for however long that scan takes — on a large keyspace (millions of keys) that can be seconds, which on a production instance is an outage, not a slow query. SCAN (and its type-specific siblings HSCAN/SSCAN/ZSCAN) does the equivalent traversal incrementally via a cursor, returning a bounded batch per call and yielding control back to the server between calls — same eventual coverage, none of the single-call blocking cost.

Example

redis-cli --scan --pattern "session:*"   # uses SCAN under the hood, safe on prod

Follow-ups

  • Does SCAN guarantee no duplicates or a perfectly consistent snapshot? — It guarantees every key present for the entire scan duration is returned at least once, but keys added/removed during the scan may or may not appear, and a key can occasionally be returned more than once — treat it as eventually-complete-enough, not a transactional snapshot.
  • What other O(N) commands carry the same class of risk? — SMEMBERS/HGETALL/LRANGE 0 -1 on a very large collection, SORT without a limit, FLUSHALL/FLUSHDB on a big dataset — any command whose cost scales with collection or keyspace size rather than being O(1)/O(log N) deserves a second look before running against production.
  • How would you catch a risky command like this before it reaches production? — Code review discipline plus, defensively, rename-command or ACL-based denial of the most dangerous commands (KEYS, FLUSHALL) for application-facing credentials, reserving them for admin-only access.

Common wrong answer

Assuming KEYS is fine "because the pattern narrows it down" — the pattern filters what's returned, not what's scanned; Redis still walks the entire keyspace internally regardless of how selective the pattern looks.

midHow does pipelining reduce latency, and what's the trade-off?

Answer

Without pipelining, each command pays a full round trip (send, server processes, response returns) before the next is sent; pipelining writes many commands to the socket back-to-back without waiting for each response individually, then reads all the responses once they arrive — collapsing N round trips into effectively one, which matters enormously when per-command work is tiny and network latency dominates the total time (the common case for Redis). The trade-off is pipelining is not a transaction — commands in a pipeline are not guaranteed to execute atomically or contiguously relative to other clients' commands interleaved between them (unless combined with MULTI/EXEC), and a client has to buffer all the responses, so a very large pipeline batch trades round-trip savings for memory and delayed error visibility (you don't know command 3 failed until you've already sent commands 4 through 1000).

Example

var batch = db.CreateBatch();
var tasks = keys.Select(k => batch.StringGetAsync(k)).ToArray();
batch.Execute();                    // all requests sent together
var values = await Task.WhenAll(tasks);

Follow-ups

  • Is StackExchange.Redis pipelining transparently even without an explicit batch? — Yes to a degree — the multiplexer already pipelines independent concurrent requests issued on the same connection without an explicit IBatch; IBatch/ITransaction exist for when you want an explicit atomic or tightly-grouped unit, not for pipelining itself.
  • How large should a pipeline batch be in practice? — Large enough to amortize round-trip cost, small enough not to bloat memory or delay error handling too much — hundreds to low thousands of commands per batch is a common practical range, tuned to the payload size.
  • Does pipelining help with commands that are individually slow (not RTT-bound)? — Not much — pipelining attacks round-trip overhead, not per-command execution cost; a genuinely slow command is still slow, just no longer paying for a dedicated round trip on top of that.

Common wrong answer

Assuming pipelined commands are automatically atomic with respect to other clients — pipelining is purely a network-efficiency optimization; wrap with MULTI/EXEC (or a script) if isolation from concurrent commands is actually required.

seniorWalk through LATENCY DOCTOR/HISTORY/LATEST and the common causes of latency spikes they surface.

Answer

Redis's latency monitoring subsystem tracks time spent in specific "events" (fork, command execution, AOF fsync, expire cycles) that exceed latency-monitor-threshold milliseconds; LATENCY LATEST shows the most recent occurrence of each event class, LATENCY HISTORY event shows a time series for one, and LATENCY DOCTOR gives a human-readable analysis naming likely causes and suggested fixes based on what it finds. The most common culprits it surfaces in real deployments: fork latency from BGSAVE/AOF rewrite (proportional to process memory size — the bigger the dataset, the longer the fork takes, since even copy-on-write fork has real overhead scanning page tables), expire-cycle spikes when a huge batch of keys expires around the same time, and, on misconfigured hosts, transparent huge pages or swapping causing latency that isn't Redis's own logic being slow at all but the OS underneath it.

Example

CONFIG SET latency-monitor-threshold 100
LATENCY LATEST
LATENCY HISTORY fork
LATENCY DOCTOR

Follow-ups

  • Why does transparent huge pages (THP) cause Redis latency specifically? — THP makes copy-on-write during fork (for BGSAVE/AOF rewrite) copy in 2MB pages instead of 4KB pages, hugely amplifying the COW cost on writes to a forked process's memory — Redis's own docs recommend disabling THP on hosts running Redis for exactly this reason.
  • Would you expect fork latency to scale with dataset size or with write rate? — Primarily dataset/process size — a bigger resident set means more page-table bookkeeping for the fork itself, independent of how busy the write workload is at that instant.
  • What's the fix for expire-cycle spikes from a mass-expiry event? — Stagger TTLs (add jitter) rather than setting a large batch of keys to expire at exactly the same instant, spreading the eventual cleanup cost over time instead of concentrating it.

Common wrong answer

Assuming any Redis latency spike must be a Redis bug or a client-side problem without checking OS-level causes (THP, swap, CPU throttling/steal on a shared host) — a large share of real-world Redis latency incidents trace back to host configuration, not Redis's own code path.

seniorIs Redis still single-threaded? How does the I/O threading introduced in Redis 6 change the performance picture?

Answer

Command execution itself remains single-threaded — the core guarantee that makes every command (and every Lua script) atomic with respect to other commands depends on exactly that. What Redis 6 added is optional multi-threaded I/O (io-threads): reading requests off the socket and parsing the protocol, and writing responses back, can be parallelized across multiple threads, while the actual command execution against the dataset still happens on the single main thread. This helps specifically when raw network I/O (many concurrent connections, high request rate) — not command-execution CPU cost — is the bottleneck; it does nothing to speed up an individual slow command or a blocking Lua script, since those still run serially on the one thread that was always there.

Example

# redis.conf
io-threads 4
io-threads-do-reads yes

Follow-ups

  • When would enabling io-threads actually move the needle? — On a host with many cores and a workload bottlenecked on I/O syscall/protocol-parsing overhead at high connection counts and throughput — on a lightly loaded instance or one bottlenecked on command execution cost, it won't help.
  • Does this mean Redis can now use multiple CPU cores for a single command? — No — a single command's execution is still confined to the main thread; multi-core benefit here is specifically about I/O handling for many concurrent connections, not parallelizing a single command's work.
  • Is there any other multi-threading in Redis (outside command execution)? — Yes — background operations like lazy-freeing large deleted objects (lazyfree-lazy-* settings) and RDB/AOF-related work run on separate background threads specifically so they don't stall the single command-processing thread.

Common wrong answer

Saying "Redis 6 made Redis multi-threaded" without qualification — command execution is still strictly single-threaded, which is precisely what preserves atomicity guarantees; only I/O handling gained threads.

seniorProduction Redis latency has been fine for months and just started spiking intermittently, a few times an hour, for a few hundred milliseconds each. Walk through your diagnosis.

Answer

Start with SLOWLOG GET and LATENCY LATEST/HISTORY to see whether Redis itself is reporting the spikes and, if so, which event class — that alone often narrows it to "a specific command got slow" versus "a background event (fork, expire cycle) is the source" versus "Redis-side metrics are clean, so look outside Redis." Cross-reference the spike timestamps against BGSAVE/AOF-rewrite schedule and replica connect/reconnect events (both trigger fork), against your key-expiry distribution (a scheduled batch job that sets a huge number of same-TTL keys is a classic self-inflicted cause), and against host-level metrics (CPU steal on a shared/virtualized host, memory pressure/swapping, network packet loss) if Redis's own instrumentation looks clean. If it correlates with traffic volume rather than a fixed schedule, suspect a specific slow command whose cost scales with data size that's only now, months later, crossed a size threshold where it's actually slow (a big-key HGETALL/SMEMBERS the app has always run, just against collections that have grown).

Example

SLOWLOG GET 20
LATENCY HISTORY fork
INFO persistence | grep -E "rdb_bgsave_in_progress|aof_rewrite_in_progress"
redis-cli --bigkeys   # check whether any collection has grown into slow-command territory

Follow-ups

  • What would make you suspect the client side rather than Redis itself? — Redis-side SLOWLOG/LATENCY reporting nothing unusual while client-observed latency clearly spikes — that combination points at the network path or the client process (GC pause, thread-pool starvation), covered fully in the next unit's client-vs-server diagnosis question.
  • Would you correlate against deploy timestamps too? — Yes — a new code path added months ago that's only just started running against larger data, or a subtly different query pattern introduced in a recent release, are common "it was fine, then it wasn't" causes worth checking against a deploy timeline.
  • How would you confirm a scheduled job is the cause rather than just correlated with it? — Temporarily stagger or pause the suspected job (in a controlled window) and watch whether the spikes disappear — correlation from timestamps alone can be coincidental at a few-times-an-hour frequency.

Common wrong answer

Jumping straight to "must be a network issue" or "must be a Redis bug" without first checking the cheap, high-signal internal instrumentation (SLOWLOG, LATENCY) that Redis already provides — most of the time the answer is visible there before any external investigation is needed.

principalYour monitoring shows client-observed Redis call latency is high, but Redis's own SLOWLOG and LATENCY data are completely clean. Where do you look next?

Answer

This split is the key diagnostic signal: it means the time is being spent somewhere between the application code issuing the call and the response coming back, but not inside Redis's own command execution — which narrows the search to three places. First, the .NET client process itself: thread-pool starvation (queued work waiting for a worker thread, common after a sync-over-async deadlock elsewhere in the app) or GC pauses can make a call look "slow" from the caller's perspective purely because the continuation didn't get scheduled promptly, with Redis having answered fast all along — ThreadPool.PendingWorkItemCount/ETW traces or dotnet-trace distinguish this from genuine network/server latency. Second, the network path itself: a load balancer, proxy, or a noisy-neighbor network path between app and Redis adding latency neither side's own instrumentation sees — packet capture or a synthetic ping/round-trip probe between the exact same hosts isolates this. Third, StackExchange.Redis's own multiplexer queue: if a single connection is oversaturated (too many concurrent operations funneled through too few connections, or a slow operation from a different logical caller queued ahead of this one on a shared connection), the wait is inside the client library, not the network or Redis — ConnectionMultiplexer.GetCounters() exposes queue depth and this exact signal.

Example

var counters = redis.GetCounters();
Console.WriteLine(counters.ToString());  // includes pending/queued operation counts per connection type

Follow-ups

  • Why would thread-pool starvation specifically look like "Redis is slow" to a naive read of application metrics? — Because the metric usually measured is wall-clock time from call-start to call-complete in application code — that duration includes any time the continuation spent waiting for a free thread-pool thread after Redis had already responded, and nothing distinguishes that from Redis genuinely taking long unless you specifically instrument the split.
  • How would you rule the network path in or out quickly? — Compare Redis-side command-execution timestamps (if traceable) or a simple redis-cli --latency run from the same app host against the same endpoint at the same time — if that's clean too, the app process itself is the remaining suspect.
  • What's the fix if it turns out to be multiplexer queue saturation? — More connections (a connection pool rather than a single shared multiplexer instance for very high-throughput scenarios) or reducing the volume/size of concurrent operations competing for the existing connection — StackExchange.Redis's guidance is normally one multiplexer per app, but that guidance has limits under genuinely extreme concurrency.

Common wrong answer

Treating "Redis latency" as synonymous with "time spent in Redis" and escalating to the Redis team/vendor before checking the client process and network path — a clean SLOWLOG/LATENCY reading is strong evidence the problem is not inside Redis's command execution at all.

12Security, ACLs & the licensing story

Security questions test whether a candidate treats Redis as something to be locked down deliberately (it ships wide-open by default) rather than assumed-safe; the licensing story is squarely a "are you current" question that's been genuinely eventful since 2024 and is worth being able to narrate confidently. Docs: redis.io/docs/latest/.../security/acl.

screenerWhat's the difference between legacy requirepass and ACLs (Redis 6+)?

Answer

requirepass is a single shared password granting full access to everything — one secret, one privilege level, used via AUTH password. ACLs (Access Control Lists, Redis 6.0+) replace that with named users, each with its own password(s), and fine-grained rules over which commands and which key patterns that user may touch — AUTH username password instead of just a password. requirepass still works (it's implemented as convenience sugar that configures the special default user) but ACLs are the modern, recommended approach whenever more than one credential or any privilege separation is needed, which in practice is almost always in a real deployment.

Example

ACL SETUSER app-readonly on >strongpassword ~cache:* +get +mget -@all
AUTH app-readonly strongpassword

Follow-ups

  • Is requirepass deprecated? — Not formally removed, but treated as legacy — new deployments should configure ACL users directly rather than relying on the single shared-password model.
  • What does the default user mean for ACL adoption? — Every Redis instance has a default user (unrestricted unless you constrain it); if you set up new ACL users but leave default wide open with a known/no password, you haven't actually achieved least privilege — locking down or disabling default is part of doing ACLs properly.
  • Does StackExchange.Redis support ACL-based auth? — Yes — the connection string / ConfigurationOptions takes a User and Password, mapping directly onto AUTH username password.

Common wrong answer

Assuming a single requirepass password is "secure enough" for a multi-service deployment — every service sharing one all-powerful credential means a leak or compromise of any one of them exposes everything, with no way to scope or revoke access to just that service.

midHow would you design least-privilege ACL rules for an application that should only cache-read and cache-write under one key prefix?

Answer

Start from -@all (deny everything) rather than trying to enumerate every dangerous command to deny — allow-listing is far more robust against forgetting to block something new. Then grant only the specific command categories needed (+@read +@write, or narrower still, just the specific commands the app actually calls) and constrain key access to the app's own namespace via a key pattern (~cache:*), so even a compromised credential for this app can't read or write keys belonging to a different service sharing the same Redis instance. This is the same reasoning as least-privilege IAM policies elsewhere — the ACL should describe exactly what the app does, no more.

Example

ACL SETUSER cache-app on >secret ~cache:* resetchannels +get +set +del +expire +ttl -@all

Follow-ups

  • Why deny-all-then-allow rather than allow-all-then-deny-dangerous-commands? — A newly introduced command or feature is safe-by-default under deny-all (it's not granted until explicitly added) but silently permitted under allow-all-then-deny, which requires remembering to update the deny list every time Redis adds something new.
  • What does resetchannels do, and why include it for an app with no pub/sub need? — It removes any Pub/Sub channel access, following the same least-privilege logic — an app with no legitimate need to subscribe/publish shouldn't be able to, even if nothing else in its ACL happens to grant it.
  • How do you avoid ACL sprawl across many microservices? — Define a small number of ACL "roles" (read-only cache, read-write cache, admin) as templates and assign each service the closest-fitting role plus its own key-pattern scope, rather than hand-crafting a bespoke rule set per service.

Common wrong answer

Granting +@all and only denying a short list of obviously dangerous commands (FLUSHALL, CONFIG) — this misses that KEYS, cross-tenant key access, and any future command are all still allowed; least privilege means naming what's needed, not naming what's scary.

midWhat TLS options does Redis support, and how do you configure a .NET client to use them?

Answer

Redis supports TLS for client connections (and for replication/cluster bus traffic) since 6.0, including optional mutual TLS where the server verifies a client certificate in addition to the client verifying the server's — Redis 8.10.0 added the ability to use that verified client certificate's CN/subject for server-side authentication directly, tightening the mTLS story further. StackExchange.Redis enables TLS via ssl=true in the connection string (or ConfigurationOptions.Ssl), with certificate validation callbacks available for custom trust logic or client-certificate presentation.

Example

var options = ConfigurationOptions.Parse("myredis:6380,ssl=true,password=secret");
options.CertificateSelection += (sender, host, certs, cert, issuers) => myClientCert;
var redis = await ConnectionMultiplexer.ConnectAsync(options);

Follow-ups

  • Why was there a TLS vulnerability specifically involving client certificates in the CVE-2026-62356 batch? — A NUL-byte-in-CN bypass allowed a maliciously crafted client certificate to be accepted as matching a trusted CN pattern it shouldn't have matched — patched same-day as the RDB/CMSketch issues on 2026-08-17 across every actively maintained branch; the concrete illustration that TLS auth code itself needs the same security rigor as the data path.
  • Does TLS have a meaningful performance cost for Redis given its command-execution model? — The handshake and encryption overhead is real but generally small relative to typical command latency; multi-threaded I/O (io-threads) helps absorb TLS's added CPU cost on the read/write path without touching single-threaded command execution.
  • Is plaintext (no TLS) ever acceptable? — Only within a fully trusted, isolated network boundary (e.g. a private VPC with no untrusted tenants) — anything crossing a boundary you don't fully control should use TLS.

Common wrong answer

Assuming ACL-based authentication alone is sufficient security without TLS — ACLs control what an authenticated connection may do, not whether the credentials and data in transit are protected from interception; the two are complementary, not substitutes for each other.

seniorWalk through the Redis licensing story since 2024 — what changed, why, and where things stand now.

Answer

In March 2024, Redis Ltd. switched Redis from the permissive BSD license to a dual RSALv2 (Redis Source Available License) / SSPLv1 model, restricting the terms under which cloud providers could offer Redis as a hosted service without a commercial agreement — a licensing shift, not a change to the code's functionality, but one that broke the "purely open source" assumption a lot of infrastructure decisions had been made under. That triggered the Linux Foundation-backed Valkey fork (announced within days, launched by former Redis maintainers and major cloud/infra companies) as a permissively-licensed continuation for anyone unwilling or unable to accept the new terms. Redis Ltd. then partially reversed course: Redis 8.0 (GA May 2025), rebranded "Redis Open Source," added AGPLv3 as a third licensing option alongside RSALv2/SSPLv1 — AGPLv3 being a real OSI-approved open-source license, which addressed much (though for some organizations' license-compliance policies, not all) of the original objection. As of today both lineages are independently active and current: Redis is at 8.10.1 (2026-08-17) and Valkey at 9.1.2/9.0.6 (2026-09-01) — the split is now a settled, ongoing fact of the ecosystem rather than a resolving news story, and picking one over the other is a real architectural decision teams have to make, not a formality.

Example

2024-03: Redis -> RSALv2/SSPLv1 (source-available, not OSI open-source)
2024-03: Valkey forked (Linux Foundation, permissive BSD-style license)
2025-05: Redis 8.0 "Redis Open Source" adds AGPLv3 as a third option
2026-09: both Redis (8.10.1) and Valkey (9.1.2) independently active

Follow-ups

  • Does AGPLv3 fully satisfy organizations that objected to the 2024 change? — Mostly, for the "must be OSI open source" objection — but AGPLv3's copyleft terms (network-use triggers source-disclosure obligations) are themselves incompatible with some companies' internal license policies, so it's not a universal resolution.
  • Is Valkey a drop-in replacement for Redis today? — Largely protocol- and command-compatible at the point of the fork and for a good while after, but the two have been diverging feature-by-feature since — a "drop-in" claim needs verifying against whichever specific version and feature set you actually depend on, not assumed by default.
  • Which would you recommend for a new project today, and why? — Genuinely depends on organizational license policy and whether you need a feature that's landed in only one lineage (e.g. Redis's newest Query Engine/JSON/Search capabilities vs. Valkey's own independent feature additions) — a defensible answer names the actual deciding factors rather than picking a side on brand loyalty.

Common wrong answer

Saying "Redis is no longer open source" as a flat, unqualified statement, or conversely "the licensing drama is over, Redis is open source again" — both oversimplify a genuinely three-way current state (RSALv2/SSPLv1/AGPLv3 as options, with Valkey as a separate permissively-licensed fork actively maintained alongside it).

seniorWhat's wrong with Redis's out-of-the-box network exposure, and how do you harden it?

Answer

Historically Redis's biggest real-world security incidents weren't clever exploits — they were instances left bound to 0.0.0.0 with no password, directly reachable from the public internet, found by mass-scanning and abused within minutes. protected-mode (default enabled since 3.2) mitigates the worst of this by refusing external connections when no requirepass/ACL auth is configured and no explicit bind address is set — but it's a safety net, not a substitute for actually configuring bind to the specific interface(s) that should reach it, a firewall/security-group rule restricting the port to known application hosts, and real authentication (ACLs, not a blank password). Defense in depth here means: never rely on protected-mode alone, never expose the Redis port directly to the internet regardless of auth, and treat the ACL/TLS configuration from the previous questions as necessary, not sufficient, layered on top of network-level restriction.

Example

# redis.conf
bind 10.0.1.5 -::1
protected-mode yes
requirepass-or-acl-configured yes  # (conceptual - actual ACL/requirepass setup)
port 6379   # only reachable from the app subnet via security group / firewall

Follow-ups

  • Why is a firewall/security-group rule still needed if ACLs already require authentication? — Defense in depth — a misconfiguration that accidentally weakens or disables ACL auth (or a future vulnerability in the auth path itself, per CVE-2026-62356's TLS bypass) is contained by a network layer that doesn't depend on the application-layer auth being correct.
  • What real incidents made this a well-known problem? — Waves of ransomware/cryptomining campaigns scanning for open, unauthenticated Redis instances (particularly common with early cloud/container deployments defaulting to 0.0.0.0) — one of the most cited "how not to deploy Redis" cautionary stories in the industry.
  • Does running Redis inside a container change this calculus? — Not fundamentally — a container's port mapping can just as easily expose it publicly if misconfigured; the same bind/firewall/auth discipline applies regardless of the deployment mechanism.

Common wrong answer

Treating protected-mode yes as sufficient hardening on its own — it's a helpful default guardrail against the most careless misconfiguration, not a substitute for actually setting bind, a firewall rule, and real authentication.

principalDesign secure, isolated Redis access for a multi-tenant SaaS platform where a security incident in one tenant's credentials must not expose another tenant's data.

Answer

The strongest isolation is physical/logical separation, not ACL scoping alone: either separate Redis instances (or separate logical databases via SELECT where Cluster isn't in play — noting logical databases don't exist in Cluster mode) per tenant, or, at minimum, a strict per-tenant key-prefix convention (tenant:{id}:*) enforced by an ACL user scoped to exactly that tenant's prefix (~tenant:42:*) so a leaked credential's blast radius is provably one tenant's keyspace, not "whatever key pattern the app happened to remember to filter by" — the ACL enforcement matters because relying purely on application-code discipline to always prefix correctly means one bug anywhere in the app is a cross-tenant data leak, whereas ACL enforcement makes the isolation hold even if application code has a bug. The trade-off to name unprompted: per-tenant instances give the strongest isolation and blast-radius containment but multiply operational cost and complexity linearly with tenant count; shared-instance-with-ACL-scoping is cheaper to run but means a Redis-level vulnerability (or an ACL misconfiguration) risks all tenants at once rather than just one — the right point on that spectrum depends on tenant count, per-tenant scale, and how strict the isolation requirement actually is (e.g. regulated-data tenants might warrant dedicated instances while others share).

Example

# per-tenant ACL user, credential rotation isolates blast radius on leak
ACL SETUSER tenant-42 on >{per-tenant-secret} ~tenant:42:* resetchannels +@read +@write -@admin -@dangerous

Follow-ups

  • How would you handle credential rotation without downtime under this design? — ACL SETUSER supports multiple active passwords per user simultaneously — add the new password, roll the update out to that tenant's app instances, then remove the old one, avoiding a hard cutover.
  • Does this design protect against a compromised application server rather than a leaked credential specifically? — Only partially — a fully compromised app server that legitimately holds tenant 42's credential can still do anything that credential's ACL permits within tenant 42's own data; ACL scoping bounds the blast radius to that tenant, it doesn't protect that tenant's own data from its own compromised access path.
  • Would you apply the same per-tenant isolation to Streams and Pub/Sub channels, not just keys? — Yes — resetchannels plus a tenant-scoped channel pattern (&tenant:42:*) closes the same cross-tenant leak for Pub/Sub that key-pattern scoping closes for regular keys; it's easy to lock down keys and forget channels are a separate ACL dimension.

Common wrong answer

Relying solely on application-level tenant-ID filtering in queries with a single shared, unrestricted Redis credential across all tenants — this makes cross-tenant isolation entirely dependent on application code never having a bug, with no enforcement floor if it does.

13Internals: threading, encodings & memory

This is where candidates who've only used Redis as a black box get separated from ones who understand why it behaves the way it does — the single-threaded model and internal object encodings explain a huge share of the "why is this fast" and "why does memory usage jump here" questions from earlier units. Expect senior+ depth. Docs: redis.io/docs/latest/develop/reference/internals.

midWhy does Redis's single-threaded event loop perform well despite being single-threaded?

Answer

Redis uses a reactor-pattern event loop (built on epoll/kqueue/select depending on platform) that multiplexes many client connections on one thread — since almost every Redis operation is an in-memory data-structure manipulation (no disk I/O in the hot path, no lock contention with other threads), the single thread rarely sits idle waiting on anything, and avoiding multi-threaded locking entirely removes a whole class of overhead (mutex contention, cache-line bouncing between cores) that a naively-threaded equivalent would pay for every operation, even ones that don't touch shared state. This is the same design philosophy as Node.js's event loop, applied to a data store instead of a web server, and it's why Redis achieves very high single-instance throughput without ever needing to reason about concurrent command interleaving.

Example

Thread: accept connection -> read command -> execute against in-memory data -> write response -> repeat
No locks needed: only one command executes "inside" the data structures at any instant

Follow-ups

  • What's the actual limiting factor for single-instance Redis throughput, if not CPU contention? — Raw single-core CPU speed for command execution, plus (before Redis 6) I/O syscall overhead for reading/writing sockets — which is exactly what optional multi-threaded I/O (unit 11) addresses without touching the execution model.
  • Does this model make Redis vulnerable to one slow command hurting everyone? — Yes, directly — that's the same trade-off named in the Lua-scripting and KEYS discussions: single-threaded execution means there is no isolation between one client's expensive operation and every other client's latency during that operation.
  • Would adding full multi-threaded command execution make Redis faster overall? — It would remove the single-thread bottleneck for CPU-bound workloads but would also require fine-grained locking (or similar) around the data structures, reintroducing exactly the contention/complexity cost the current design avoids — a genuine engineering trade-off, not a simple win, which is why Redis has instead scaled out via Cluster/replicas rather than in via multi-core command execution.

Common wrong answer

Assuming single-threaded means "slow" — the model is a deliberate trade-off that removes locking overhead for the common case (fast, in-memory, no-I/O commands), which is why Redis is fast despite it, not in spite of some hidden multi-threading.

midExplain object encodings — why does the same logical type (hash, set, etc.) sometimes use a different internal representation?

Answer

Redis picks the cheapest internal encoding that still fits the data, switching automatically once a configured threshold is crossed: a small hash or set is stored as a compact listpack (a flat, serialized byte sequence — minimal per-entry overhead, O(N) scans, fine because N is small) while a large one converts to a hashtable (real hash-table structure — more per-entry overhead, but O(1) lookups, worthwhile once N is big enough that O(N) scanning would actually cost something) — the equivalent trade-off applies to sets (intset for all-integer small sets, listpack, then hashtable) and sorted sets (listpack then skiplist). The thresholds (hash-max-listpack-entries/-value, set-max-listpack-entries, zset-max-listpack-entries/-value, and similarly for lists via quicklist node sizing) are configurable, and OBJECT ENCODING key tells you which one a given key is currently using.

Example

HSET small-hash a 1 b 2
OBJECT ENCODING small-hash        # "listpack"
CONFIG SET hash-max-listpack-entries 2
HSET small-hash c 3
OBJECT ENCODING small-hash        # "hashtable" - crossed the threshold

Follow-ups

  • Is the ziplist-to-listpack rename just cosmetic? — No — listpack (Redis 7.0+, replacing the legacy ziplist encoding for hashes/sets/zsets) fixed a real cascading-reallocation issue in ziplist where updating one entry could force reencoding of every subsequent entry; it's a genuine internal improvement, not just a name change, though the observable behaviour (compact-then-converts-at-a-threshold) is conceptually the same.
  • Does converting from compact to full encoding ever convert back down? — No — once a key has been promoted to the larger encoding (e.g. after a temporary burst of entries), it stays there even if entries are later removed below the threshold; only recreating the key resets this.
  • Why does this matter for interview-level memory reasoning? — It directly explains counter-intuitive memory behaviour: many small hashes staying just under the threshold are dramatically cheaper than the same data as fewer, larger hashes that crossed it — a data-modeling decision (how you shape your keys) can have an outsized memory impact purely through encoding thresholds.

Common wrong answer

Assuming a "hash" always uses the same internal representation and memory cost regardless of size — the encoding (and therefore per-entry memory cost and access complexity) silently changes at a configurable threshold, which is invisible unless you specifically check OBJECT ENCODING.

midWhy does Redis use its own string type (SDS) instead of plain C strings internally?

Answer

Simple Dynamic Strings (SDS) store the string's length and allocated capacity alongside the character data itself, rather than relying on a null terminator to find the end — which makes strlen-equivalent lookups O(1) instead of O(N), makes strings safely binary (a Redis string value can contain embedded null bytes, since length is tracked explicitly rather than inferred from where a zero byte happens to appear), and enables amortized-cheap appends (SDS over-allocates a bit of extra capacity so repeated APPEND calls don't reallocate every single time, the same idea as a C# StringBuilder or a growable array). This is a foundational internals fact that explains both why Redis strings can safely hold arbitrary binary data (useful for anyone storing serialized/binary payloads, not just text) and why operations like STRLEN and APPEND are cheap.

Example

C string:  ['h','e','l','l','o','\0']              -- length found by scanning to \0
SDS:       {len: 5, alloc: 10, buf: "hello\0....."} -- length read directly, headroom for growth

Follow-ups

  • Does this mean Redis strings can safely store serialized binary blobs (e.g. a MessagePack payload)? — Yes — this is exactly why binary serialization formats are safe to store as Redis string values; nothing about SDS depends on the content being null-free text.
  • Is SDS specific to the String data type, or used more broadly internally? — It's used pervasively throughout Redis's internals — key names themselves, for instance, are also stored as SDS, not just String-type values.
  • Does SDS overhead matter for a workload with millions of tiny strings? — Yes, at scale, the small fixed header/allocation overhead per SDS string is exactly the kind of per-key cost that shows up in the "same data, more memory than expected" diagnosis discussed in the eviction unit.

Common wrong answer

Assuming Redis strings can't safely contain null bytes because "that's how C strings work" — SDS specifically exists to remove that limitation; Redis string values are binary-safe by design.

seniorWhere does per-key memory overhead actually come from — why isn't a tiny value "basically free"?

Answer

Every key pays fixed costs regardless of how small its value is: a dictionary entry in the keyspace's own hash table (pointer(s) to the key and value, plus the hash table's own load-factor overhead), the key's own SDS header, a Redis object header (robj — carrying the type, encoding, refcount, and LRU/LFU access metadata used for eviction) wrapping the value, and, if a TTL is set, an entry in the separate expires dictionary. None of this scales with the value's actual content size — a key storing the single byte "1" and a key storing a 50-byte string pay nearly the same fixed overhead on top of their (tiny, either way) content — which is precisely why "millions of tiny keys" is a materially worse memory shape than "fewer, larger keys/collections holding the same logical data," and why questions about data modeling (unit 01's big-key vs many-small-keys trade-off) circle back to this internals fact.

Example

1,000,000 keys each storing "1"           -> ~1M x (dict entry + robj + SDS header) overhead
1 hash with 1,000,000 fields each "1"     -> one dict-entry/robj/SDS overhead for the hash key,
                                              plus per-field overhead inside the hash's own encoding
                                              (cheaper again if it stays compact-encoded, per unit above)

Follow-ups

  • Does this argue for always modeling data as fewer, bigger collections? — It's a real consideration but not absolute — very large individual collections reintroduce the big-key latency and Cluster-hashing problems from earlier units; the practical answer is usually "group related small values into moderately-sized hashes," not "one giant structure."
  • How would you measure this overhead directly rather than reasoning about it abstractly? — MEMORY USAGE key on a representative sample of both shapes (many tiny keys vs. grouped into a hash) against the same logical data — direct measurement beats theoretical estimation for a specific workload's actual numbers.
  • Does Redis 8.10's compact hashes change this calculus? — Yes, meaningfully, for hash-shaped data specifically — see the next question.

Common wrong answer

Estimating Redis memory usage as roughly "sum of value sizes" — the fixed per-key overhead (dict entry, robj, SDS header, optional expires entry) is often the dominant cost for small values at scale, not a rounding error on top of content size.

seniorWhat are compact hashes, introduced in Redis 8.10 (2026-07-29), and what do they optimize?

Answer

Compact hashes reduce per-field memory overhead specifically for hashtable-encoded hashes whose fields share a common shape across many instances (e.g. many user:{id} hashes that all have the same field names: name, email, created_at) by sharing field-name/schema metadata across those hashes rather than each hash instance separately paying full per-field overhead for field names it has in common with every other instance of that shape — a genuinely new optimization layered on top of the existing listpack/hashtable encoding split (unit above), targeting the case where a workload has already outgrown listpack (so is paying full hashtable overhead) but still has a very repetitive field-name shape across many keys, which is an extremely common real-world pattern (object-per-entity hashes) that the older encoding split didn't specifically exploit.

Example

Before 8.10: 1M "user:{id}" hashes, each hashtable-encoded, each paying full
             per-field name+overhead cost independently
8.10+:       shared field-name schema metadata amortized across all 1M instances
             of that shape -> lower total memory for the identical logical data

Follow-ups

  • Does this require any application-level change to benefit from? — No — it's an internal storage optimization Redis applies automatically to eligible hashtable-encoded hashes; existing code and data benefit without modification once upgraded to 8.10+.
  • Does this replace the need for the listpack/hashtable threshold tuning discussed above? — No — it's complementary: listpack vs hashtable is still the first-order decision (small hashes stay maximally compact as listpack regardless); compact hashes specifically improve the hashtable side of that split for schema-repetitive workloads.
  • Why is this an example of "cite something recent" for a Redis interview? — It's a concrete, dated (2026-07-29), version-specific feature that a candidate reciting only pre-2024 Redis knowledge wouldn't know — exactly the kind of detail that signals genuinely current knowledge rather than memorized fundamentals.

Common wrong answer

Confusing compact hashes with the listpack encoding for small hashes — they solve different problems (listpack: small-collection compactness generally; compact hashes: shared-schema field overhead specifically for already-large, hashtable-encoded hashes) and both can apply to the same dataset at different scales.

principalA workload stores millions of small per-user preference hashes, each with 5-10 fields, all sharing the same field names. How would you reason about encoding thresholds and memory for this specifically?

Answer

First check where these land relative to hash-max-listpack-entries/-value — at 5-10 fields, they're very likely staying listpack-encoded by default, which is already close to memory-optimal for this shape (compact, sequential, minimal per-field overhead) and the compact-hashes optimization (unit above) wouldn't even apply, since that specifically targets hashtable-encoded hashes. The actual lever worth pulling is confirming the threshold is comfortably above the realistic field count (so a user with 11 preferences instead of 10 doesn't silently flip that one hash to the far more expensive hashtable encoding) — and, if profiling shows real memory pressure, deliberately widening hash-max-listpack-entries/-value a bit beyond the default trades a small amount of O(N) lookup cost (still cheap at N=10) for guaranteed compact storage across the whole dataset, a rare case where raising a size threshold is a memory-saving move rather than a memory-cost trade-off, precisely because it keeps hashes on the cheaper encoding rather than letting them tip over into the more expensive one.

Example

CONFIG SET hash-max-listpack-entries 16    # headroom above the realistic 5-10 field count
CONFIG SET hash-max-listpack-value 128     # headroom for occasional longer field values
redis-cli --bigkeys                        # confirm actual distribution matches assumption
MEMORY USAGE user:42:prefs                  # measure directly, don't just estimate

Follow-ups

  • Would you ever deliberately lower the threshold instead? — Only if profiling showed CPU cost from O(N) listpack scans was the actual bottleneck rather than memory — for 5-10 fields that's very unlikely to matter; this is a case where the memory side of the trade-off clearly dominates.
  • How would compact hashes (8.10+) change the recommendation if the field count were instead in the hundreds? — At hundreds of fields, listpack's O(N) scan cost starts mattering and hashtable encoding becomes the right choice on CPU grounds — at which point compact hashes' schema-sharing optimization is exactly what keeps the resulting per-hash memory cost down despite the switch to hashtable.
  • What's the risk of raising thresholds broadly across the whole instance rather than reasoning about this specific workload's shape? — A different key pattern elsewhere on the same instance with genuinely large collections would now also stay listpack-encoded longer than it should, trading away the CPU benefit of hashtable encoding where it was actually needed — thresholds are instance-wide, so the change has to be justified for the whole instance's key population, not just the one workload being optimized.

Common wrong answer

Assuming "more fields always means switch to hashtable for performance" and lowering thresholds preemptively — at the field counts described, listpack is both faster in practice (no hash-table overhead to maintain) and more memory-efficient; hashtable only wins once N is large enough that O(N) scanning genuinely costs something.

14Modern data types: JSON, Search, TS

These used to be separate paid/optional Redis Stack modules; Redis 8.0 (GA 2025-05-02) merged them into Redis Open Source core as the "Query Engine" plus native data types — a significant enough shift that even candidates with solid pre-2025 Redis knowledge may not know it happened. Expect this to come up as a "what's new" or "have you used the modern data types" question rather than deep internals. Docs: redis.io/docs/latest/develop/data-types/json and redis.io/docs/latest/develop/interact/search-and-query.

midWhat does the native JSON data type give you that storing serialized JSON in a String doesn't?

Answer

A String holding serialized JSON is opaque to Redis — reading or updating one field means fetching the whole blob, deserializing client-side, mutating, reserializing, and writing the whole thing back, with no atomicity against concurrent writers touching a different field. The native JSON type stores a parsed document server-side and exposes JSONPath-addressed operations (JSON.GET key $.field, JSON.SET key $.field value, JSON.NUMINCRBY, array append, etc.) that read or mutate just the addressed part atomically, without transferring or reserializing the whole document — genuinely cheaper for large documents with frequent small updates, and it composes with the Query Engine's secondary indexing (next question) in a way an opaque String blob never could.

Example

JSON.SET user:42 $ '{"name":"Ann","prefs":{"theme":"dark"}}'
JSON.SET user:42 $.prefs.theme '"light"'    # updates just that field, atomically
JSON.GET user:42 $.name

Follow-ups

  • What .NET client library exposes this? — NRedisStack (Redis's own .NET client for the modern data types/Query Engine) layers a typed JsonCommands API on top of an IDatabase-like connection; StackExchange.Redis alone doesn't natively understand JSON.* commands beyond issuing them generically.
  • Is this the same module that used to be called RedisJSON? — Yes — RedisJSON was the standalone Stack module; its functionality is what got merged into core as part of Redis 8.0's "Redis Open Source" relicensing and consolidation.
  • When would plain String-serialized JSON still be the right call? — When the app only ever reads/writes the whole document at once and never needs partial updates or server-side querying into it — the simplicity of "just deserialize the whole thing" is fine if partial-field access was never actually needed.

Common wrong answer

Assuming "Redis doesn't have real JSON support, you just store it as a string" — that was true before Redis 8.0 merged the JSON module into core; native, JSONPath-addressable JSON is now a first-class built-in data type, not a bolt-on module you have to separately install.

midHow does the Redis Query Engine (formerly RediSearch) let you query data by fields other than the key?

Answer

By default Redis only supports lookup by exact key — no "find all users where age > 30" without scanning everything yourself. The Query Engine adds real secondary indexing: define an index (FT.CREATE) over a key pattern's Hash or JSON fields, declaring each field's type (text for full-text search, tag for exact-match categorical values, numeric for range queries, geo for location), and then run structured queries (FT.SEARCH/FT.AGGREGATE) against it — full-text search with relevance ranking, numeric range filters, faceted aggregation — all served from an index Redis maintains automatically as the underlying keys change, not something you rebuild manually.

Example

FT.CREATE idx:users ON JSON PREFIX 1 user: SCHEMA $.name AS name TEXT $.age AS age NUMERIC
FT.SEARCH idx:users "@age:[30 +inf]"

Follow-ups

  • Does the index update automatically as documents change? — Yes — it's maintained incrementally as matching keys are written/updated/deleted, not a batch job you have to rerun.
  • Would you use this instead of a dedicated search engine like Elasticsearch? — For search/filtering needs that live naturally alongside data already in Redis and don't need Elasticsearch's broader ecosystem (complex analyzers, massive-scale text corpora, rich aggregation pipelines), yes — it avoids standing up and syncing a second system; for search as the primary, large-scale workload, a dedicated engine is often still the better fit (explored further in the closing design question).
  • Is this the same underlying engine that powers vector search? — Yes — the Query Engine's indexing infrastructure is what vector similarity search (next question) is built on top of, alongside text/tag/numeric/geo field types.

Common wrong answer

Trying to emulate secondary indexing by maintaining your own manual index structures (e.g. a Sorted Set keyed by age, updated by application code on every write) when the Query Engine already does this natively and keeps the index consistent automatically — reasonable before RediSearch/Query Engine existed, redundant complexity now for most cases.

seniorHow does vector search work in Redis, and what's it used for in a modern .NET application?

Answer

A vector field in the Query Engine schema stores a fixed-dimension embedding (a float array produced by an ML model — e.g. an OpenAI or local embedding model's output for a chunk of text) and supports K-nearest-neighbor similarity search over an index built with either a flat (exact, brute-force) or HNSW (approximate, much faster at scale) algorithm, queried via FT.SEARCH with a vector-similarity clause. The dominant real-world use case today is RAG (retrieval-augmented generation): store embeddings of document chunks, embed the user's query with the same model, run a KNN search to retrieve the most semantically similar chunks, and feed those into an LLM prompt as context — Redis competes here directly with dedicated vector databases, with the pitch being "you likely already run Redis for caching/sessions, so vector search is one more capability on infrastructure you already operate" rather than a new system to stand up.

Example

FT.CREATE idx:docs ON HASH PREFIX 1 doc: SCHEMA content TEXT embedding VECTOR HNSW 6 TYPE FLOAT32 DIM 1536 DISTANCE_METRIC COSINE
FT.SEARCH idx:docs "*=>[KNN 5 @embedding $vec AS score]" PARAMS 2 vec "<binary-float-array>" SORTBY score

Follow-ups

  • Flat vs HNSW — what's the trade-off? — Flat gives exact nearest-neighbor results by brute-force comparison against every vector, fine for small datasets; HNSW gives approximate results via a graph-based index that's dramatically faster at scale, the standard choice once the vector count is large enough that brute force becomes slow.
  • Where do the embeddings themselves come from in a .NET RAG pipeline? — Typically generated by calling an embedding model's API (or a local model) for each document chunk at ingestion time, and again for each user query at search time — Redis stores and searches the vectors, it doesn't generate them.
  • Is this feature part of the same 8.0 core merge as JSON and full-text search? — Yes — vector search came from the RediSearch module and is now part of the same consolidated Query Engine in Redis Open Source core, not a separately licensed add-on.

Common wrong answer

Describing vector search as "a separate product Redis added on" — it's an extension of the same Query Engine/indexing infrastructure that also does text, tag, and numeric search, and it ships in Redis Open Source core since the 8.0 module consolidation, not as a distinct paid module anymore.

seniorWhat is the Time Series data type for, and how does it handle retention and downsampling?

Answer

The Time Series type (TS.ADD/TS.RANGE) is purpose-built for sequences of timestamped numeric samples (metrics, sensor readings, financial ticks) — storing the same data as a Sorted Set or List works but pays far more per-sample memory overhead and gives none of Time Series' native features: automatic retention (old samples past a configured window are dropped without a manual cleanup job), compaction rules that automatically maintain downsampled aggregate series (e.g. a raw per-second series plus an auto-maintained per-minute average/max series) so you're not re-aggregating raw history on every query, and duplicate-policy handling for out-of-order or repeated timestamps. This is the right tool specifically when the workload is genuinely time-series shaped (ordered by time, queried by range, naturally aged out) rather than a general ordered-collection need better served by a Sorted Set.

Example

TS.CREATE sensor:temp RETENTION 86400000                 # keep 24h of raw samples
TS.CREATERULE sensor:temp sensor:temp:1min AGGREGATION avg 60000
TS.ADD sensor:temp * 21.5
TS.RANGE sensor:temp:1min - +                              # query the auto-maintained rollup

Follow-ups

  • Why not just use a Sorted Set with timestamp as score? — It works for basic range queries but has no native retention/downsampling — you'd hand-roll TTL-based trimming and separately compute and store rollups yourself, redoing what Time Series already automates.
  • Is Time Series also part of the Redis 8.0 core merge? — Yes — RedisTimeSeries followed the same path as JSON and Search: formerly a separate Stack module, now bundled into Redis Open Source core.
  • Would you use this for application metrics/observability instead of Prometheus? — It's a reasonable fit if you're already storing time-series-shaped data in Redis for other reasons and want it queryable alongside; for organization-wide observability infrastructure, a dedicated metrics/monitoring stack is still the more common choice.

Common wrong answer

Treating Time Series as "just a Sorted Set with a different name" — the native retention and auto-maintained downsampling rules are the actual value; without them you're back to hand-rolling the same cleanup/aggregation logic Time Series exists to remove.

seniorBeyond HyperLogLog, what other probabilistic data types does Redis offer, and what do they trade away for their space savings?

Answer

Bloom filters (BF.ADD/BF.EXISTS) answer "have I possibly seen this before?" in a fixed, tiny memory footprint regardless of how many items have been added, at the cost of a tunable false-positive rate (it may say "yes, seen" for something never actually added; it never says "no" for something that was) and no support for removal. Cuckoo filters (CF.ADD/CF.EXISTS/CF.DEL) solve the same approximate-membership problem with a similar space/false-positive trade-off but additionally support deletion, at a modest space-efficiency cost relative to an equivalently-tuned Bloom filter. The common thread across all of Redis's probabilistic types (these two, plus HyperLogLog for cardinality and Top-K/t-digest for frequency/quantile estimation) is the same trade: bounded, sublinear memory in exchange for an approximate rather than exact answer — appropriate whenever "approximately right, cheap" beats "exactly right, expensive" for the actual use case.

Example

BF.RESERVE seen-urls 0.01 1000000     # 1% false-positive rate, sized for 1M items
BF.ADD seen-urls "https://example.com/a"
BF.EXISTS seen-urls "https://example.com/a"   # 1 (definitely added, or a false positive)
BF.EXISTS seen-urls "https://example.com/z"   # 0 (definitely never added)

Follow-ups

  • What's a realistic use case for a Bloom filter over just checking a Set? — Deduplicating a very large stream of items (crawled URLs, processed event IDs) where exact membership via a Set would cost far more memory than the application can justify, and an occasional false-positive "treat as duplicate, skip it" is an acceptable cost.
  • Why would you pick Cuckoo over Bloom despite the space cost? — Specifically when items need to expire from the filter over time (e.g. "seen in the last 24 hours") — Bloom filters have no delete operation at all, so Cuckoo is the only one of the two that supports that requirement.
  • Are these also part of the 8.0 core merge? — Yes — they originated in the RedisBloom Stack module, now part of core Redis Open Source alongside JSON, Search, and Time Series.

Common wrong answer

Using a Bloom filter where exact membership actually matters (e.g. checking whether a payment has already been processed) — false positives are an inherent, non-zero property of the structure, not a rare edge case; anywhere a false "yes" is unacceptable, use a Set or a real uniqueness constraint instead.

seniorWhat actually happened in the Redis 8.0 "Query Engine" merge, and why does it matter beyond just "new features"?

Answer

Before Redis 8.0, JSON, full-text/vector search, Time Series, and the probabilistic types (Bloom/Cuckoo/Top-K) were Redis Stack modules — separately packaged, separately licensed (some under a more restrictive source-available license than the already-changed core license), and not guaranteed present on every Redis deployment (vanilla open-source Redis vs. Redis Stack were genuinely different products). Redis 8.0 (GA 2025-05-02, coinciding with the "Redis Open Source" rebrand and the AGPLv3 licensing addition from unit 12) merged all of that module functionality directly into core, under the same licensing terms as the rest of Redis, and added 8 new native data types built on that consolidated foundation — meaning any Redis 8+ deployment has this functionality by default, with no separate module installation, licensing consideration, or "is Stack available here" question to ask. This matters for architecture decisions made before mid-2025: a team that ruled out RedisJSON/RediSearch because of Stack's licensing or deployment friction should revisit that decision against Redis 8+'s core-bundled equivalent.

Example

Pre-8.0:  Redis (BSD/RSAL core) + Redis Stack (separate package, separate license) = full feature set
8.0+:     Redis Open Source (RSALv2/SSPLv1/AGPLv3) = full feature set, one product, one license choice

Follow-ups

  • Does Valkey have an equivalent to this merged Query Engine? — Valkey has been developing its own independent search/JSON capabilities post-fork rather than inheriting Redis's post-2024 module consolidation directly — feature parity between the two lineages on this specific front needs checking against current versions, not assumed.
  • Do managed Redis offerings (cloud providers) all support the merged Query Engine equivalently? — Not uniformly — some managed offerings lag core version adoption or gate certain modern-data-type features behind specific tiers; worth verifying against the specific provider rather than assuming parity with self-hosted Redis 8+.
  • Is this the kind of fact worth stating unprompted in an interview? — Yes — it's exactly the "shows I'm current" detail the topic brief calls for: a candidate who knows Stack-vs-core is now a pre-2025 distinction demonstrates they've tracked the ecosystem past their original learning period.

Common wrong answer

Describing JSON/Search/TimeSeries support as "you need to install Redis Stack for that" — accurate before mid-2025, outdated now; Redis 8+ ships this in core with no separate module or product to install.

principalWhen would you use Redis's native JSON + Query Engine for search/filtering, versus keeping Redis as a cache and running a dedicated search engine (e.g. Elasticsearch/OpenSearch) alongside it?

Answer

The deciding factors are scale, query sophistication, and operational surface, not "which is newer." Redis's Query Engine wins when the searchable data already naturally lives in Redis for other reasons (session data, product catalog cache) and the query needs are moderate — field filters, basic full-text, vector KNN for a RAG feature — because it avoids standing up, syncing, and operating an entirely separate system, and avoids the consistency-lag problem of keeping two data stores in sync. A dedicated search engine wins once query sophistication (complex relevance tuning, custom analyzers/tokenizers, faceted search UIs at scale) or data volume genuinely outgrows what's comfortable in a memory-bound store, or when search is the primary workload for that data rather than a secondary capability layered onto data that's there for caching reasons anyway — Elasticsearch/OpenSearch's ecosystem (Kibana, mature analyzer libraries, purpose-built cluster/shard tooling for search specifically) reflects years of investment specifically in that problem, which Redis's Query Engine, while genuinely capable, doesn't try to fully replicate.

Example

Redis Query Engine fit:  product catalog already cached in Redis; add @price/@category
                         filters and a RAG vector-search feature on top - no new system
Dedicated search fit:    the search experience itself is the product (e-commerce search-as-you-type
                         with rich relevance tuning across tens of millions of documents)

Follow-ups

  • Would you ever run both against the same logical data? — Yes, when different consumers have genuinely different needs — e.g. Redis's Query Engine for a fast, simple in-app filter, and a separate search engine for a full customer-facing search experience — accepting the sync cost because the two serve different enough purposes to justify it.
  • Does the licensing story (unit 12) factor into this decision at all? — Marginally — if an organization's license policy already rejects RSALv2/SSPLv1 and AGPLv3 doesn't fit their compliance model either, that alone might push them toward Valkey (if it has caught up on Query-Engine-equivalent features) or away from Redis's native search features entirely, independent of the technical trade-offs above.
  • What operational cost specifically does adding a dedicated search engine introduce that the Query Engine avoids? — A second system to provision, monitor, and keep in sync (via CDC, dual-writes, or a sync pipeline) — real, ongoing operational cost that a strong answer names explicitly rather than treating a second system's adoption as free once justified by feature needs.

Common wrong answer

Treating this as "Redis Query Engine is now good enough to always replace a dedicated search engine" or the opposite ("Redis can't really do search, always use Elasticsearch") — both ignore that the right choice genuinely depends on query sophistication and scale, which a strong answer names concretely rather than picking a default.

15Ecosystem: Valkey & managed services

Rarely the centerpiece of an interview but a reasonable closing area for a lead/principal conversation about how you'd actually procure and operate Redis in a real organization — expect it framed as "how would you decide" rather than trivia. Docs: valkey.io.

midIs Valkey a safe drop-in replacement for Redis today?

Answer

At the fork point (March 2024) it was essentially identical — same protocol, same commands, same on-disk formats. Since then the two lineages have genuinely diverged: Redis has shipped the 8.0 core module merge (JSON/Search/TimeSeries/probabilistic types, unit 14), compact hashes, native BACKUP, and the 8.10.1 security fixes, while Valkey (currently 9.1.2/9.0.6, 2026-09-01) has developed its own independent feature set and its own security patch cadence under Linux Foundation governance. "Drop-in" is no longer a safe blanket assumption — it has to be checked feature-by-feature and version-by-version against whatever specific capabilities your application actually depends on, particularly anything from the post-2024 module-merge feature set, which isn't guaranteed to have an equivalent on the Valkey side by the same name or interface.

Example

Safe to assume compatible:  core data types, replication basics, RESP protocol, Sentinel/Cluster fundamentals
Needs explicit verification: JSON/Search/vector/TimeSeries features, anything landed after March 2024

Follow-ups

  • Why would a team choose Valkey over Redis today? — Primarily licensing — Valkey's permissive, Linux Foundation-governed license is the deciding factor for organizations whose policies reject RSALv2/SSPLv1 and, for some, AGPLv3 as well; it's a licensing decision more often than a technical one.
  • Does StackExchange.Redis work against Valkey? — Yes, generally — it speaks the RESP protocol and standard commands both projects share, so a .NET client written against either behaves the same for the common, non-diverged feature surface.
  • Would you recommend migrating an existing Redis deployment to Valkey? — Only with a concrete reason (licensing policy, cost, a specific Valkey-only feature) — migrating purely for its own sake adds risk and testing burden without a corresponding benefit if the current Redis deployment already satisfies the organization's licensing constraints.

Common wrong answer

Repeating "Valkey is just Redis with a different name" as if the two are still identical today — that was true at the 2024 fork point; two years of independent development later, feature parity has to be verified, not assumed.

seniorWhat are the practical differences between running self-hosted Redis and a managed offering like Azure Cache for Redis, AWS ElastiCache, or Redis Cloud?

Answer

Managed services handle patching, failover orchestration, backup scheduling, and (usually) a polished dashboard for monitoring — trading operational burden for a per-node cost premium and, often, a version lag behind the very latest upstream release (a managed tier may not offer the newest release for weeks/months after it ships, which matters if you specifically need a just-released feature or security fix). They also vary in exactly which engine and version they offer: some managed tiers run genuine open-source Redis, others (like AWS ElastiCache's "Valkey" option, offered alongside its Redis-compatible tiers) explicitly let you pick the lineage, which is now a real decision point given unit 12's licensing split. Feature parity with self-hosted also isn't guaranteed — Cluster support, specific config flags, or the newest Query Engine capabilities may be gated behind specific tiers or unavailable entirely on a given managed product.

Example

Self-hosted:  full control, latest version immediately, you own patching/failover/backup ops
Managed:      less ops burden, cost premium, possible version lag, tier-gated feature availability

Follow-ups

  • How would you decide between a managed Redis-lineage and a managed Valkey-lineage offering on the same cloud? — The same licensing-policy question from unit 12, now applied at the procurement level — if your organization already has an opinion on RSALv2/SSPLv1/AGPLv3, that answer picks the lineage before any technical comparison is needed.
  • Would you trust a managed offering's failover to be as fast/reliable as a well-tuned self-hosted Sentinel/Cluster setup? — Generally yes for a well-established provider — but it's still worth verifying their documented failover time and testing it under realistic load rather than assuming, since "managed" doesn't automatically mean "as fast as your specific requirements need."
  • What's a concrete reason to prefer self-hosting despite the operational burden? — Needing the very latest release immediately (e.g. a just-patched CVE, or a feature not yet available on any managed tier), or cost at large enough scale where the managed premium outweighs the ops savings.

Common wrong answer

Treating all managed Redis offerings as interchangeable and equivalent to self-hosted — version lag, engine-lineage choice (Redis vs Valkey), and tier-gated feature availability differ meaningfully between providers and need checking against the specific requirement, not assumed uniform.

seniorWhat capabilities are specific to Redis Enterprise (the commercial offering) that aren't in the open-source core?

Answer

The headline Enterprise-only capabilities are Active-Active geo-distribution (multiple regions each accepting writes, with conflict-free replicated data type-based automatic conflict resolution — genuinely hard distributed-systems machinery, not something open-source Redis's standard primary-replica model provides at all) and Auto Tiering (transparently spilling less-hot data to SSD/flash so the effective dataset can exceed available RAM at a lower cost per GB than all-RAM, with the hot working set staying in memory) — both squarely aimed at large-scale, multi-region enterprise deployments rather than typical single-region application needs. Enterprise also bundles operational tooling (a management UI/API for multi-database provisioning, RBAC, enterprise support SLAs) that open-source deployments have to assemble themselves from other tools.

Example

Open source: single-region primary + replicas + Sentinel/Cluster, all-in-RAM dataset
Enterprise:  multi-region Active-Active writes, Auto Tiering beyond RAM, managed multi-tenant control plane

Follow-ups

  • Would a typical single-region .NET application ever need Active-Active? — Rarely — it solves a specific problem (accepting writes in multiple regions simultaneously with automatic conflict resolution) that most applications don't have; single-region deployments get no benefit from paying for it.
  • Is Auto Tiering the same idea as OS-level swap? — No — swap is an uncontrolled, often catastrophic-for-latency fallback; Auto Tiering is a deliberate, Redis-aware mechanism for keeping hot data in RAM and cold data on flash with predictable access patterns, not an emergency overflow valve.
  • Does the 2024 licensing change affect Enterprise's positioning? — Not really — Enterprise was always a separate commercial product/support offering layered on top of the core engine; the RSALv2/SSPLv1/AGPLv3 licensing conversation is about the core engine itself, which Enterprise deployments also run underneath their added capabilities.

Common wrong answer

Assuming any advanced HA/scaling feature you've heard of is available in open-source Redis "if you configure it right" — Active-Active geo-distribution and Auto Tiering specifically are not something Sentinel/Cluster configuration alone can replicate; they're genuinely separate Enterprise engineering, not a config flag away.

principalA .NET team is launching a new production service and asks you to decide: self-hosted Redis, a managed cloud offering, or Redis Enterprise. Walk through your framework.

Answer

Start from the requirements that actually discriminate between the options, not the options themselves: does the deployment genuinely need multi-region active writes (if yes, that's the one requirement only Enterprise's Active-Active answers — everything else can't substitute) or a dataset larger than comfortably fits in RAM at acceptable cost (Auto Tiering, or else careful capacity planning); does the organization's license policy already rule in or out RSALv2/SSPLv1/AGPLv3 (if it rules all three out, Valkey enters the conversation regardless of the technical comparison); does the team have the operational maturity and headcount to own patching, failover drills, and backup verification themselves, or is that better bought as a managed service given the team's actual size and on-call capacity. For the common case — single-region, RAM-fitting dataset, no license objection, small-to-mid team — a managed offering (Azure Cache for Redis or equivalent) is usually the pragmatic default: it removes real operational burden at a cost premium that's easy to justify against the cost of the team's own time, while self-hosting is reserved for cases with a specific reason (cost at large scale, need for bleeding-edge version access, or existing in-house Redis operations expertise) and Enterprise reserved for the specific capabilities only it provides.

Example

Decision order: 1) Active-Active or beyond-RAM dataset needed? -> Enterprise
                2) License policy rules out RSAL/SSPL/AGPL?    -> Valkey (managed or self-hosted)
                3) Otherwise: team ops maturity + cost at scale -> managed (default) vs self-hosted

Follow-ups

  • What's the risk of defaulting to self-hosted "for full control" without a concrete reason? — Underestimating the real ongoing cost of patching, monitoring, failover testing, and incident response that a managed service would otherwise absorb — "full control" is a genuine benefit only when something concrete actually needs it.
  • Would you revisit this decision later as the service grows? — Yes — this is explicitly a point-in-time decision against current requirements and team size; a service that later needs multi-region writes or outgrows managed-tier cost economics should revisit the same framework, not be locked into the original choice by inertia.
  • How does this framework change for a startup versus an established enterprise? — A startup's priority is usually minimizing ops burden and time-to-market (managed, by default, even more strongly) while an established enterprise with existing Redis operations expertise and negotiated infrastructure costs may find self-hosting or Enterprise more economical at their scale — team context changes the weighting, not the framework's structure.

Common wrong answer

Picking an option based on brand familiarity or what the team used at a previous job, rather than walking through which specific requirements (multi-region writes, dataset-beyond-RAM, license policy, ops capacity) actually discriminate between the choices — a defensible answer names the deciding factors explicitly.

seniorCache-aside, write-through, or write-behind — and what would make you switch?

What a strong answer demonstrates

That the choice follows from the read/write ratio and the tolerance for stale or lost data, not from familiarity. A strong answer defaults to cache-aside for read-heavy workloads where the source of truth is a database the application already owns — it is the simplest failure mode, a cache outage just means slower reads. It names write-through as the choice when reads must never see stale data right after a write and the write-latency cost is acceptable, and write-behind only when write throughput matters more than durability of the cache itself and there is a real plan for what happens when the buffered write is lost. It states the tripwire that would change the decision: a cache-aside stampede on a hot key, or a write-behind queue backing up under load.

Trade-offs to name unprompted

  • Cache-aside's simplicity against its first-request-always-misses and thundering-herd exposure.
  • Write-through's freshness against doubling write latency and coupling cache availability to write availability.
  • Write-behind's throughput against a durability gap that must be sized and owned, not ignored.
  • All three still need an eviction and expiry policy — none of them make the cache infinite.
principalA team wants to "just put it in Redis." When do you say no?

What a strong answer demonstrates

That you evaluate the request against what Redis actually is: an in-memory store where durability, secondary-index richness, and multi-key transactional guarantees are all weaker than a general-purpose database's. A strong answer says yes quickly to ephemeral or reconstructable data — sessions, caches, rate-limit counters, rankings — and pushes back when the data is the only copy of something valuable, needs ad-hoc relational queries, or needs strict multi-document ACID across unrelated keys. It offers the actual alternative (durable primary store with Redis as an accelerator in front of it) rather than a flat refusal, and it distinguishes this from Redis 8.0's native JSON/Search/vector capabilities, which widen but do not eliminate that boundary.

Trade-offs to name unprompted

  • RAM cost per byte versus disk cost per byte — the economic argument against Redis as a system of record.
  • AOF/RDB durability is good, not equivalent to a WAL-backed RDBMS with point-in-time recovery.
  • Query flexibility (ad-hoc joins, complex filters) versus Redis's access-pattern-shaped data structures.
  • Saying no well means naming the actual accelerator role Redis should play instead of a bare rejection.
seniorCluster, Sentinel, or a single primary-replica pair — how do you choose the topology?

What a strong answer demonstrates

That the decision is driven by two independent axes — do you need automatic failover, and does the dataset or throughput exceed one node — rather than picking the most sophisticated option by default. A strong answer defaults to a single primary with one or two replicas plus Sentinel once uptime actually matters, and reserves Cluster for when the working set or write throughput genuinely will not fit one primary. It calls out the real cost Cluster adds: no cross-slot multi-key operations without hash tags, and client-side awareness of resharding. It resists "we might need to scale later" as sufficient justification on its own.

Trade-offs to name unprompted

  • Sentinel gives HA without data partitioning; Cluster gives both but costs multi-key operation freedom.
  • Operational surface grows sharply from single pair to Cluster — more moving parts, more failure modes.
  • Client library maturity for Cluster topology-awareness (MOVED/ASK handling) is a real adoption cost.
  • Migrating from a single pair to Cluster later is a live-migration project, not a config flag.
principalRedis-based lock, a dedicated coordination service, or no lock at all — how do you decide?

What a strong answer demonstrates

That distributed locking is a last resort, and that "which lock implementation" is the second question, not the first. A strong answer starts by asking whether the operation can be made idempotent or atomic without a lock at all (a single Redis command, a conditional write, a queue that serialises access). Only then does it choose: a single-instance SET NX PX lock with a unique token for short, best-effort critical sections where an occasional double-execution is tolerable; Redlock or a purpose-built coordination service (etcd, ZooKeeper) when correctness under partition actually matters, naming that Redlock's timing assumptions are contested (Kleppmann's critique) and that a fencing token on the protected resource is what makes the guarantee real regardless of which lock service is used.

Trade-offs to name unprompted

  • A single-instance lock is simple and has a real failure window around failover; Redlock narrows but does not eliminate it.
  • Fencing tokens fix the actual correctness gap; the lock service alone does not, no matter which one you pick.
  • A dedicated coordination service adds another system to run and patch, for a stronger liveness/safety story.
  • The best answer is often "redesign so no lock is needed" — naming that option first is a signal of seniority.
seniorHow much persistence durability does a given workload actually need?

What a strong answer demonstrates

That durability posture is a product decision priced in RTO/RPO, not a default left at whatever the install script set. A strong answer separates pure-cache workloads (RDB snapshots or nothing at all — data is reconstructable) from workloads where Redis briefly is the only copy of something (session state mid-checkout, a rate-limit ledger) that need AOF with appendfsync everysec at minimum, and payment-adjacent or otherwise unrecoverable data that may justify appendfsync always despite the latency cost, or simply argues Redis is the wrong store for it. It states the actual loss window each option buys: RDB loses everything since the last snapshot, everysec loses at most one second of writes, always loses none but fsyncs every write.

Trade-offs to name unprompted

  • fsync policy is a direct trade of write latency for bounded data loss — quantify both, not just one.
  • AOF rewrite and RDB fork both cost memory and CPU at the moment they run — size headroom for it.
  • Mixing RDB+AOF (Redis 4+ default) gives fast restart plus a bounded loss window, at double the disk I/O.
  • None of this replaces replication — persistence protects against a full outage, not a single node failing.
principalMulti-tenant workload on Redis: one shared cluster with isolation, or one instance per tenant?

What a strong answer demonstrates

That the decision trades operational cost against blast radius, and that it usually defaults to shared with enforced isolation until a specific tenant earns an exception. A strong answer defaults to one cluster, key-prefixed per tenant, with ACLs restricting each application credential to its own key pattern (~tenant:42:*) and a resource-usage budget enforced at the application layer since Redis has no native per-tenant quota. It names the conditions that justify a dedicated instance: a tenant large enough to be a noisy neighbour, a contractual or regulatory isolation requirement, or a tenant whose eviction pattern would otherwise evict everyone else's data.

Trade-offs to name unprompted

  • Shared cluster: lower cost and simpler ops, at the cost of a noisy tenant affecting everyone via memory pressure or CPU.
  • ACL key-pattern isolation is a security boundary, not a performance one — a whale tenant still starves others.
  • Per-tenant instances scale operational overhead linearly with tenant count — patching, monitoring, backup times N.
  • maxmemory and eviction policy are cluster-wide, not per-tenant, so isolation must be designed around that limit.
seniorRedis Streams, or a dedicated broker like Kafka or a cloud service bus?

What a strong answer demonstrates

That the decision comes from retention, replay, and ecosystem needs, not "we already run Redis." A strong answer picks Streams when the team already operates Redis, message volume and retention needs are modest (hours to low days, not months), and consumer groups' at-least-once delivery with manual ack is sufficient — it is genuinely lighter to operate than standing up Kafka for a small pipeline. It picks a dedicated broker when retention must span weeks or months, when exactly-once or strict partition-ordering semantics are required at scale, or when multiple heterogeneous downstream systems and schema registries are already built around that ecosystem. It names Streams' actual limit: memory-bounded retention (or an explicit trim policy), not disk-tiered storage.

Trade-offs to name unprompted

  • Streams retention lives in RAM (or is trimmed) — long retention is a real memory cost, unlike Kafka's disk-tiered log.
  • One less system to run is a genuine advantage when the team is already all-in on Redis operationally.
  • Kafka's ecosystem (Connect, schema registry, tiered storage) pays off at a scale Streams was never meant to reach.
  • Consumer group rebalancing and stuck-message recovery (XCLAIM/XAUTOCLAIM) need the same operational discipline either way.
principalCache invalidation is getting messy as the team grows. TTL-only, event-driven, or versioned keys?

What a strong answer demonstrates

That invalidation strategy should match how tightly coupled the cache is to its source of truth, and that the answer usually changes as the team scales. A strong answer starts with TTL-only for a small team and low staleness tolerance — it is nearly free and needs no coordination — and names the point where it stops being enough: staleness windows that violate a product requirement, or too many call sites remembering to set the right TTL. It moves to event-driven invalidation (publish on write, subscribe to invalidate) once correctness matters more than simplicity, naming that this adds a real dependency: a missed event means permanently stale data with no self-healing TTL fallback. Versioned or generation-based keys (bump a version number instead of deleting keys) are the answer when invalidation must be atomic across many related keys at once.

Trade-offs to name unprompted

  • TTL-only self-heals from a missed invalidation; event-driven does not, unless paired with a TTL backstop.
  • Event-driven invalidation adds a pub/sub or Streams dependency and a new class of "the event never arrived" bug.
  • Versioned keys make bulk invalidation atomic but leave old-generation keys to expire or be reclaimed some other way.
  • Whatever is chosen, always keep a TTL as the fallback — a purely event-driven cache with no expiry is a leak waiting to happen.
seniorHow do you choose an eviction policy and memory headroom, and what would make you revisit it?

What a strong answer demonstrates

That the policy follows from what happens when a key is evicted — is it reconstructable (a cache) or not (session state, a queue)? A strong answer defaults to allkeys-lru for a pure cache with roughly uniform value, volatile-lru when some keys must never be evicted (only ones with a TTL are eligible), and noeviction when losing any key is unacceptable and backpressure via OOM errors is the safer failure. It sets maxmemory with real headroom above the working set — not the whole box's RAM, because fork-based persistence and replication buffers need spare memory too — and names the metrics that would trigger a revisit: rising evicted_keys against a shrinking hit ratio, or mem_fragmentation_ratio drifting away from 1.0.

Trade-offs to name unprompted

  • LRU approximates recency cheaply; LFU tracks actual frequency and suits a working set with a long tail of rarely-reused keys.
  • noeviction trades availability (writes start failing) for the guarantee that nothing silently disappears.
  • Headroom below 100% of RAM is not waste — fork-based RDB saves and replication backlog need it to avoid swapping.
  • An eviction policy chosen once at launch and never revisited is a common source of "the cache stopped working" incidents as the workload's shape changes.
principalWhere is the line between logic that belongs in a Lua script or Redis Function, and logic that belongs in application code?

What a strong answer demonstrates

That server-side scripting is justified by atomicity and round-trip elimination, not by convenience, and that pushing too much business logic into Redis creates a second codebase in a language the team is less fluent in. A strong answer keeps scripts small and focused on genuinely atomic multi-step operations that a client-side round trip cannot make safe (a CAS check-then-act, a rate-limiter's increment-and-check, a safe lock release) and keeps broader business rules, validation, and orchestration in the application where they are testable, debuggable, and owned by the whole team. It names the operational cost of scripts directly: they run on the single event-loop thread, so a slow script blocks every other client, and SCRIPT KILL cannot safely interrupt one that has already written data.

Trade-offs to name unprompted

  • Atomicity and one round trip instead of several, against a harder-to-test, harder-to-debug piece of logic living server-side.
  • A slow or buggy script blocks the entire instance — there is no per-script timeout that safely recovers state.
  • Redis Functions (7.0+) version and namespace scripts properly; ad-hoc EVAL calls do not, and drift silently across deployments.
  • The team's Lua fluency is itself a cost — a clever script nobody else can safely modify is a liability, not an asset.

Exercise 1 — A distributed rate limiter for a public API gateway

Prompt. Design a rate limiter in front of a public API: per-API-key limits (e.g. 1,000 requests/minute), a burst allowance, and correctness under a fleet of twenty gateway instances that must all agree on the same counter. The gateway does ~50,000 requests per second at peak across all keys, and a limiter outage must fail safe (never take the API down).

Clarifying questions to ask first

  • Fixed window, sliding window, or token bucket semantics — does the product need to tolerate a burst right at a window boundary, or is that an acceptable edge case?
  • Is per-key precision required, or is slightly-over-limit under contention acceptable for the throughput this buys?
  • What should happen if Redis itself is unavailable — hard-fail closed (reject all traffic) or fail open (allow all traffic)?
  • Are limits static per key, or do they change dynamically (tiered plans, temporary throttling during an incident)?
  • Is this single-region or must limits be enforced consistently across multiple regions with independent Redis deployments?
principalStrong solution outline and expected trade-offs

Shape of the answer

A sliding-window counter approximated with two fixed windows (current and previous), or an exact sliding-window log capped by a sorted set — the choice depends on the precision-versus-memory answer from the clarifying questions. For the common case, a Lua script (or a Redis Function) does the whole increment-and-check atomically in one round trip: INCR the current window's counter, set its expiry only on first increment, read the previous window's count, compute the weighted estimate, and return allow/deny in one call — this is the atomicity boundary that makes twenty gateway instances agree without a separate lock, because the script itself serialises on the single event-loop thread. Burst allowance is a second, shorter-window token-bucket check layered on top, refilled via the elapsed-time math done inside the same script rather than a background job.

Fail-safe behaviour is designed explicitly: gateway instances hold a short client-side circuit breaker around the Redis call, and on a Redis outage the design fails open with a coarser, per-instance in-memory fallback limit rather than blocking all traffic — a rate limiter that takes the API down on its own outage has the wrong failure mode. At 50k req/s, Redis itself is not the bottleneck (a single well-sized primary handles this easily), but replica lag and the blast radius of one Redis outage across every API consumer are the real operational risks, which argues for Sentinel-backed HA at minimum.

-- Sliding-window approximation, atomic, one round trip.
-- KEYS[1] = current window key, KEYS[2] = previous window key
-- ARGV[1] = limit, ARGV[2] = window seconds, ARGV[3] = elapsed fraction into current window
local current = tonumber(redis.call('INCR', KEYS[1]))
if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[2]) end
local previous = tonumber(redis.call('GET', KEYS[2]) or '0')
local estimate = previous * (1 - tonumber(ARGV[3])) + current
if estimate > tonumber(ARGV[1]) then return 0 end
return 1

Trade-offs to name unprompted

  • Fixed window versus sliding window versus token bucket. Fixed window is cheapest and allows a 2x burst at the boundary; sliding-window log is exact and costs O(n) memory per key; the weighted two-window approximation is the usual production compromise. Name which one you are choosing and why.
  • Fail open versus fail closed. Fail closed is "correct" and takes the API down with the limiter; fail open with a coarser fallback keeps the API alive at the cost of a temporarily unenforced limit — for most public APIs, fail open with monitoring is the right default.
  • Atomicity via Lua script versus client-side pipelining. A script guarantees the read-then-write is not interleaved with another gateway instance's; pipelining alone does not — this is the exact bug that lets concurrent requests all slip through at the limit boundary.
  • Hot-key contention. A single very high-traffic API key concentrates all its increments on one key on one shard; in a clustered deployment this is a partitioning hot spot worth calling out explicitly.
  • Cross-region consistency. Independent per-region counters are cheap and allow up to N-region overshoot; a single global counter is exact and adds cross-region latency to every request — most designs accept per-region approximation.

Exercise 2 — A real-time leaderboard for a mobile game with 20 million players

Prompt. Design a leaderboard: players submit scores continuously, the UI shows a player's current global rank, the top 100 players, and "the 5 players ranked just above and below me." Peak submission rate is 30,000 score updates per second, and there are separate leaderboards per game mode (a few dozen) plus a weekly-reset leaderboard.

Clarifying questions to ask first

  • Is the rank exact and real-time, or is a short staleness window (a few seconds) acceptable for the top-N and neighbour views?
  • What happens to a score on a tie — first-to-reach-it ranks higher, or is a tie displayed as a shared rank?
  • Does "weekly reset" mean the old leaderboard is discarded, or does it need to be archived for a "last week's results" view?
  • Is a player's own rank query (the expensive one) hit anywhere near as often as the leaderboard's top-N view?
  • How many game modes and concurrent leaderboards are there, and do any of them have dramatically more players than others?
principalStrong solution outline and expected trade-offs

Shape of the answer

A Redis Sorted Set per leaderboard (ZADD leaderboard:mode1 <score> <playerId>) is the whole data model — sorted sets give O(log n) insert/update, O(log n) rank lookup (ZRANK/ZREVRANK), and O(log n + m) range queries (ZRANGE/ZREVRANGE) for the top-100 and the "neighbours" view (ZREVRANGE around the player's own rank) — for free, with no separate ranking computation ever needed. Ties are broken deterministically by encoding a secondary tiebreaker (submission timestamp, inverted) into the score's fractional part or by using ZADD GT semantics plus a stable secondary sort key, so two equal scores never rank ambiguously.

Weekly reset uses a new sorted-set key per period (leaderboard:mode1:2026-w37) rather than deleting and rebuilding the same key — the old key is simply archived (or expired after a retention window) and the new one starts empty, which also means "last week's results" is just reading the previous key, free of any migration step. At 30k updates/second across a few dozen modes, each mode's sorted set is a single key and therefore lives on a single Cluster shard — the design explicitly does not shard within a leaderboard, and instead relies on modes being numerous enough to spread load, calling out any single mode that could itself exceed one shard's throughput as a design risk requiring a split (e.g. by region) with a fan-in for the global view.

ZADD leaderboard:mode1:2026-w37 GT 15230 player:8821   -- score with GT: only updates if higher
ZREVRANK leaderboard:mode1:2026-w37 player:8821        -- this player's current rank
ZREVRANGE leaderboard:mode1:2026-w37 0 99 WITHSCORES   -- top 100
ZREVRANGE leaderboard:mode1:2026-w37   WITHSCORES  -- neighbours

Trade-offs to name unprompted

  • Sorted set as the whole model versus a database plus a computed rank. A sorted set gives O(log n) rank for free; a relational "rank via window function" recomputes at query time and does not scale to this update rate.
  • One key per leaderboard means one shard per leaderboard in Cluster. This caps a single mode's throughput and memory to one node — fine at dozens of modes, a real limit if one mode dominates.
  • Persistence and HA. A leaderboard is exactly the kind of "briefly the only copy" data discussed under persistence trade-offs — losing an hour of score updates on an unreplicated instance is a real product incident, so replication (and AOF) earn their cost here, unlike a pure ephemeral cache.
  • Own-rank query cost at scale. ZREVRANK is O(log n) per call, cheap even at 20M members — the actual risk is calling it far more often than the leaderboard changes, which argues for a short client-side or edge cache on top.
  • Tie-breaking via score encoding. Packing a timestamp into the score's precision is simple and works within float64 limits for realistic score ranges, but must be sized and tested against the game's actual score magnitude.

Exercise 3 — A caching layer in front of a relational product catalog for a flash-sale event

Prompt. An e-commerce product catalog backed by SQL Server serves normal traffic fine, but a flash-sale event drives traffic to 100x normal for the featured products only. Design the caching layer: product detail pages must stay fast and correct (price and stock must never be visibly wrong), and a cold cache at the moment the sale opens must not fall over.

Clarifying questions to ask first

  • How many distinct products are "featured" in a given sale — tens, or thousands? This changes whether pre-warming is feasible.
  • Is stock count itself served from the cache, or does every "add to cart" hit the source of truth regardless of what the product page displayed?
  • Is a few-hundred-millisecond staleness window acceptable on price/description, or must it be read-your-own-writes fresh (e.g. right after an admin price correction)?
  • Is traffic evenly spread across featured products, or is there a single "doorbuster" item that dominates the 100x spike?
  • Is there an existing CDN or edge cache in front of this, or does Redis have to absorb the full spike alone?
principalStrong solution outline and expected trade-offs

Shape of the answer

Cache-aside for product detail data (description, images, price display) with a deliberately pre-warmed cache: since the sale's start time and featured-product list are known in advance, the design populates every featured product's cache entry before traffic arrives rather than relying on lazy population under 100x load — this eliminates the cold-cache stampede risk entirely for the predictable part of the spike. Stock count is treated differently: it is never served from a plain cache-aside read, because "must never be visibly wrong" for something that changes on every purchase means the read path has to go through an atomic decrement (DECR or a Lua script checking-and-decrementing in one call) directly against Redis acting as the fast, authoritative stock counter for the sale window, with the relational database as the asynchronously reconciled source of truth via a write-behind queue.

For the unpredictable part — a doorbuster item nobody anticipated getting hot, or any cache entry that does expire mid-sale — per-key request coalescing (a short-lived "building" lock via SET NX) prevents a stampede of concurrent misses all hitting SQL Server at once for the same key; every other concurrent request for that key waits briefly or serves a slightly stale value rather than joining the herd. TTLs on descriptive data are set generously long for the sale's duration (correctness there only needs eventual consistency), while the stock counter has no TTL at all — it is explicit application state with its own lifecycle, reconciled and cleared at sale end.

-- Atomic check-and-decrement for stock: source of truth during the sale window.
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock <= 0 then return -1 end          -- sold out
redis.call('DECR', KEYS[1])
return stock - 1

Trade-offs to name unprompted

  • Pre-warming versus lazy cache-aside. Pre-warming eliminates the cold-start stampede for known traffic but only works because the sale's timing and product list are known ahead — it does not generalise to unpredictable spikes.
  • Redis as the authoritative stock counter versus SQL Server. Making Redis authoritative for the sale window buys atomic, low-latency decrements at 100x scale; it requires a deliberate reconciliation and failure story if Redis loses data before it syncs back — this is exactly the "data Redis briefly is the only copy of" case from the persistence judgment call.
  • Request coalescing versus accepting a stampede. A short building-lock adds a small amount of complexity and latency for the unlucky first requester, in exchange for protecting SQL Server from a thundering herd on any cache miss.
  • TTL strategy differs by field. Treating "stock count" and "product description" as the same kind of cached value is the mistake that causes either stale stock (correctness bug) or an unnecessarily hot description cache (performance non-issue treated as a problem).
  • Single doorbuster item as a hot-key risk. Even inside Redis, one key taking 100x traffic is a single-shard, potentially single-thread hotspot — the mitigation (local in-process caching of that one key with a very short TTL, or read replicas) should be named explicitly, not assumed away.

18Night-before cheat sheet

The ten questions most likely to be asked, with the one-sentence answer to have ready. If you can say each of these cleanly and then add one sentence of "and the reason is…", you will pass the screening layer of almost any Redis loop.

  1. What is cache-aside, and why is it the default pattern? The application reads through the cache and falls back to the source of truth on a miss, populating the cache as it goes — it is the default because a cache outage degrades to slower reads instead of breaking the application.
  2. What is the default eviction behaviour, and what should it usually be? The default is noeviction (writes fail with an OOM error once maxmemory is hit), which is correct for data you cannot afford to lose but wrong for a pure cache, where allkeys-lru or allkeys-lfu is the usual choice.
  3. RDB or AOF? RDB is a periodic point-in-time snapshot (fast restart, can lose minutes of writes); AOF logs every write for a much smaller loss window (as low as one second with everysec) at a higher I/O cost — most production deployments run both together.
  4. How does Redis fail over automatically? Sentinel processes monitor the primary, agree by quorum that it is down, and promote the replica with the most complete replication offset — application clients must be Sentinel-aware (or go through a proxy) to discover the new primary.
  5. How does Redis Cluster distribute data? Every key hashes (CRC16) into one of 16,384 fixed hash slots, and each slot is owned by one shard — multi-key operations only work atomically when all keys land in the same slot, forced with a hash tag like {user:42}:profile.
  6. How should a .NET application manage its Redis connection? One ConnectionMultiplexer per application (or connection string), created once and reused for the process lifetime — it manages its own connection pool and multiplexes many concurrent commands over a small number of sockets, so creating one per request exhausts connections under load.
  7. Is Redis single-threaded? Command execution is single-threaded (which is why every command is effectively atomic), but since Redis 6 the I/O threading model offloads socket reads/writes to background threads — execution itself never became multi-threaded.
  8. Do Redis transactions roll back on error? No — MULTI/EXEC queues commands and runs them atomically without interleaving from other clients, but a runtime error in one command does not abort or roll back the others; only a queue-time syntax error aborts the whole transaction before it starts.
  9. How do you implement a safe distributed lock? SET key token NX PX ttl to acquire, releasing only with a Lua script that checks the token matches before deleting — the unique token prevents one client from releasing a lock it does not hold after its own lock already expired.
  10. What is the current Redis licensing and version state? Redis returned to source-available-plus-open-source with the AGPLv3 option added alongside RSALv2/SSPLv1 starting with Redis 8.0 (GA May 2025); the current stable series is 8.10, with 8.10.1 (17 Aug 2026) fixing CVE-2026-62356, and the Linux Foundation's Valkey fork (created after the 2024 licence change) is a genuine drop-in alternative now at 9.1.2/9.0.6 (1 Sep 2026).
