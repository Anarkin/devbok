01 The KEYS call that froze checkout

Tier: SeniorPerformance problem diagnosed
EXAMPLE — replace with your own

Checkout latency had a strange shape: p50 was fine, but p99 spiked to 4-6 seconds for a couple of minutes every hour, always on the hour. Nobody had touched the checkout code in weeks, so I didn't start there — I pulled up `redis-cli --latency-history` against the cache tier first, and it showed a clean 800ms plateau on that same cadence. `SLOWLOG GET 25` had the smoking gun: a `KEYS session:*` call from an hourly cleanup job, taking 780-900ms against a database holding about 4.1 million keys.

The reason it hurt is the thing people forget once they've been doing this for a few years: Redis executes commands on a single thread. The I/O-threading work that landed as Redis 8.0 parallelizes reading and writing bytes off the socket — it does not parallelize command execution. `KEYS` walks the entire keyspace inside the one thread that is also trying to serve every `GET` from checkout, so for that 800ms window nothing else runs. It's not "Redis is slow", it's "Redis is doing exactly the one thing you asked, and you asked for something O(N)."

The fix had two parts. Immediately: replace `KEYS session:*` with `SCAN 0 MATCH session:* COUNT 200` in a loop — `SCAN` walks a stable cursor over the hash table in small non-blocking increments, so each call is O(COUNT) instead of O(N), and it never blocks other clients for more than a slice. Structurally: the cleanup job shouldn't have been finding expired-ish sessions by pattern-matching at all — I moved session bookkeeping onto a Redis `TTL` per key (so Redis itself reclaims them) plus a `ZADD sessions:idx ` index the job could range-query with `ZRANGEBYSCORE`, which turned an O(N) sweep into an O(log N + M) one.

Safe in prodNever, above trivial key countsYes, with a sane COUNT

What I'd do differently: I'd have caught this in a pre-prod review, not a page. Any `redis-cli` or client call that isn't `SCAN`-family, `HSCAN`, `SSCAN` or `ZSCAN` on a keyspace of unknown size should be a lint rule, not a lesson learned at 4.1 million keys.

What the interviewer is really probing

Whether you actually understand Redis's execution model or just know "KEYS is bad" as folklore — push on why it's bad and watch for "single-threaded command execution" versus a vague "it's O(N) I think". They're also checking you diagnosed before you fixed (latency tooling, SLOWLOG) rather than pattern-matching the symptom to a remembered blog post, and that you closed the structural gap, not just swapped one command for another.

Follow-up drill chain

Why does I/O threading in Redis 8.0 not fix this?

Because I/O threading only parallelizes the read-parse-write work around the socket — pulling bytes in, encoding replies out. Command execution against the keyspace, including a full `KEYS` scan, still runs on the single main thread that owns the data structures. It buys you more connections and higher network throughput per core, not more concurrent command execution.

What if `SCAN` had returned duplicates or missed keys mid-cleanup — would that have mattered here?

`SCAN`'s only guarantee is that a key present for the entire scan duration is returned at least once; keys added or removed mid-scan may be seen zero, one, or more times. For a cleanup job that's idempotent — reprocessing a session twice is harmless, missing one just means it's picked up next run — so I accepted the weaker guarantee deliberately rather than paying for `KEYS`'s snapshot semantics.

At what key count does this stop being a "someday" problem and become a "this week" problem?

In my experience the pain is noticeable in the low hundreds of thousands and severe past a few million, because the blocking time scales roughly linearly with keyspace size regardless of how few keys actually match the pattern — `KEYS` still has to visit every hash bucket. I treat any keyspace expected to cross 100k keys as "needs a SCAN-safe access pattern from day one", not as a threshold to react to later.

What did you trade away by moving to the sorted-set expiry index instead of just fixing the command?

Extra write-path cost — every session write now also does a `ZADD`, and the index itself needs its own housekeeping. I judged that acceptable because reads (the cleanup job, plus any future "sessions expiring soon" feature) hugely outnumber writes, and because it turned an implicit invariant ("nothing scans the whole keyspace") into an explicit, reviewable data structure.

How would you have handled it if the cleanup job were a third-party tool you couldn't modify?

I'd run it against a read replica instead of the primary, accepting slightly stale results, so the blocking cost lands somewhere that doesn't threaten checkout. If even that were too disruptive, I'd rate-limit or reschedule it to a genuine low-traffic window and add an alert on `SLOWLOG` entries above a threshold so a regression doesn't silently come back.

What would you do differently if this happened again on Redis Cluster instead of a single primary?

`KEYS` and un-prefixed `SCAN` are per-node in cluster mode — a client has to iterate every shard and merge cursors itself, which most clients including StackExchange.Redis's `IServer.Keys` already do for you across `GetServer` calls, but it means the blocking cost is now paid on every shard simultaneously rather than once, which is worse, not better, if you get this wrong.

02 Cache-aside vs write-through for the catalog

Tier: StaffHard architectural trade-off
EXAMPLE — replace with your own

We were rebuilding the product-catalog read path in front of a relational store that could no longer take direct read load at peak (roughly 40k reads/sec against a database sized for a tenth of that). The obvious move was a Redis cache in front of it; the actual decision was which shape of cache, and I ran the trade-off as a proper architecture review rather than defaulting to whatever the team already knew.

Cache-aside (lazy loading) is simple and StackExchange.Redis-native: on a miss, read the database, write the value into Redis with a TTL, move on. Its failure mode is the thundering herd — when a hot key expires, dozens of concurrent requests all miss at once and all hammer the database simultaneously to refill it. Write-through inverts that: every catalog write goes through a code path that updates Redis and the database together, so reads almost never miss, at the cost of making every write more complex and slower, and of needing a reconciliation story for the write that updates the database but crashes before touching Redis.

I chose cache-aside, deliberately, for three reasons specific to this workload: catalog data is read orders of magnitude more than it's written, TTL-based staleness (we picked 10 minutes) was acceptable to the business, and I could kill the thundering-herd failure mode with two well-known techniques instead of taking on write-through's complexity: a per-key distributed lock on refill (`SET lock:{key} 1 NX PX 3000`, first-in refills, everyone else waits or serves slightly stale data) and TTL jitter (`baseTtl + random(-60, 60) seconds`) so thousands of keys set at deploy time don't all expire in the same second. Six months in, cache hit rate sat around 97%, and the one write-through-shaped requirement we did have — "price changes must be visible within a second" — I solved narrowly with an explicit `DEL` on the cache key inside the price-update transaction, rather than converting the whole catalog to write-through for one field.

Staleness windowUp to the TTL~0, until a write fails half-way

async Task<Product> GetProductAsync(string id)
{
    var key = $"catalog:{id}";
    var cached = await _db.StringGetAsync(key);
    if (cached.HasValue) return Deserialize(cached!);

    var lockKey = $"lock:{key}";
    var gotLock = await _db.StringSetAsync(lockKey, "1", TimeSpan.FromSeconds(3), When.NotExists);
    if (!gotLock)
    {
        await Task.Delay(50);           // brief backoff; a real impl polls/retries
        return await GetProductAsync(id);
    }

    var product = await _repo.LoadAsync(id);
    var ttl = TimeSpan.FromMinutes(10) + TimeSpan.FromSeconds(Random.Shared.Next(-60, 60));
    await _db.StringSetAsync(key, Serialize(product), ttl);
    return product;
}

What I'd do differently: I under-specified the price-update exception up front — it would have been cleaner to name "hot-path fields that need write-through semantics" as a first-class category in the design doc, instead of discovering it as a special case during implementation.

What the interviewer is really probing

Whether you can hold two designs in your head and argue the real trade-off ("it depends, because...") instead of reciting "cache-aside is standard" as if it were free. Weak answers stop at "we picked cache-aside because it's simpler"; strong ones name the specific failure mode of the choice they made and how they mitigated it — the herd, the jitter, the lock — because that's the part that only shows up once you've actually run it in production.

Follow-up drill chain

Why a lock instead of just letting the herd happen?

Because at 40k reads/sec, even a two-second refill window meant tens of thousands of duplicate database queries landing in that window — enough to tip the database over, which was the exact failure we were trying to prevent. The lock converts an unbounded stampede into one query plus a short wait for everyone else, which the database can absorb comfortably.

What if the process holding the lock crashes before it releases it?

That's why the lock is `SET ... PX 3000` rather than a plain flag with no TTL — it self-expires in three seconds even if the holder dies mid-refill, so the worst case is a bounded extra delay for waiters, not a permanently stuck cache. I picked the TTL to comfortably exceed the p99 database round trip, with margin.

At what write frequency would you flip this decision to write-through?

Once a meaningful fraction of catalog fields need sub-second consistency rather than one narrow field, the per-field `DEL` exceptions start to outnumber the simple cases, and that's the signal the abstraction is inverted — at that point I'd rather pay write-through's complexity uniformly than keep accumulating one-off cache-busting call sites that are easy to forget.

What did you trade away by choosing a ten-minute TTL specifically?

Freshness for hit rate and database protection — ten minutes was chosen empirically by watching hit rate flatten out above that point with diminishing returns, and confirming with the business that a customer seeing a ten-minute-old price on a non-flash-sale item was acceptable. It's a number I'd re-derive, not reuse, on a different catalog with different change frequency.

How would you extend this if you needed cross-instance cache invalidation instead of relying purely on TTL?

I'd reach for Redis's keyspace notifications or, since Redis 6, client-side caching (`CLIENT TRACKING`) so that a write anywhere invalidates the in-process copies everywhere, rather than every consumer inventing its own Pub/Sub-based busting scheme — that's a good bridge into story 17.

03 The CROSSSLOT outage during a resharding window

Tier: PrincipalProduction incident / outage
EXAMPLE — replace with your own

We ran a six-shard Redis Cluster (16,384 hash slots split across shards, each key's slot computed as `CRC16(key) mod 16384`, or the tag inside `{}` if the key uses one) and were adding a seventh shard to relieve memory pressure ahead of a seasonal peak. Fifteen minutes into the resharding window — slots being migrated shard-by-shard with `CLUSTER SETSLOT ... MIGRATING/IMPORTING` — checkout started throwing `CROSSSLOT Keys in request don't hash to the same slot` on a multi-key `MSET` that wrote a cart and its summary counter together, and error rates on checkout hit 8%.

The command itself hadn't crossed slots before that day. The cart key was `cart:{cartId}` and the summary key was `cart-summary:{cartId}` — two different key names, and without a hash tag, Cluster computes each key's slot independently from its own name, so they'd landed on different slots by chance, on different shards, for as long as the cluster had exactly the shard count it had when those keys were first designed. Resharding didn't create the bug — it just changed which shard combination was live at that moment and made the latent bug visible, because the two keys were now (also, coincidentally) mid-migration on the specific slots involved, which turned a rare CROSSSLOT into a near-constant one for that ID range.

The immediate fix was a one-line hot patch: `SET` the two keys independently instead of one `MSET`, which is always safe across slots since each command only ever touches its own key. The real fix, rolled out over the following sprint, was adding the hash tag both keys were missing — `cart:{cartId}` and `cart-summary:{cartId}` share the tag `{cartId}`, which Cluster hashes instead of the whole key name, guaranteeing they land on the same slot forever regardless of shard count. I also added a CI check that greps for any multi-key Redis command (`MSET`, `MGET`, `SUNIONSTORE`, transactions spanning keys) and asserts every key argument shares a hash tag, so this class of bug can't reach production silently again.

No hash tagShared hash tag {id}
Slot placementIndependent per key nameGuaranteed identical
Multi-key ops (MSET, transactions, Lua)Works only by accidentAlways safe
Load distributionFine-grained, evenCoarser — co-located keys move together
 
SET cart:{cartId} ...
SET cart-summary:{cartId} ...
-- both keys hash on "cartId" only, so CLUSTER KEYSLOT
-- always returns the same slot for both, on any shard count

What I'd do differently: hash-tag discipline should have been a pre-launch architecture review item, not a lesson from an 8% error-rate incident — any two keys with a real transactional relationship should be tagged from the day they're introduced, before the cluster is even large enough for it to matter.

What the interviewer is really probing

Whether you understand Cluster's data-distribution model well enough to explain why the bug was latent, not just that "resharding broke something" — and whether, at incident-command level, you separated the immediate mitigation (safe within minutes) from the structural fix (safe forever) rather than doing a rushed version of the second under pressure. They're also listening for whether you take ownership of the design gap rather than blaming "the resharding" as an external event.

Follow-up drill chain

Why does Redis Cluster use hash slots instead of, say, consistent hashing directly on nodes?

Hash slots decouple "how many partitions exist" (always 16,384) from "how many nodes serve them", so resharding is a slot-ownership reassignment — updating which node claims which slot range — rather than a full re-hash of every key, which is what would happen with pure consistent hashing on node identity whenever the node count changes.

What if the migrating slot had been fully importing rather than mid-migration when the CROSSSLOT hit — same bug?

Yes — the CROSSSLOT check is purely about whether the keys in one command map to the same slot number; it fires identically whether that slot is stable, migrating, or importing. The migration state made the specific shard topology at that moment surface the bug, but the bug itself was present the whole time the two keys existed without a shared tag.

At what cluster size does hash-tag discipline stop being optional?

Technically it matters even at a single shard added later — the risk is zero until the second shard exists, then present forever after. So the honest answer is "before you ever plan to grow past one shard", which for most systems is day one of the design, not a scaling milestone.

What did you trade away by adding a hash tag to co-locate those keys?

Slightly coarser load distribution — the cart and its summary now always move together during resharding rather than independently, which is a non-issue at this granularity but would matter if I were tagging something high-cardinality and hot enough to create a single oversized slot, since Cluster balances at slot granularity, not key granularity.

How would CLUSTER MIGRATION's newer atomic slot-migration path have changed this incident?

It wouldn't have prevented the CROSSSLOT error itself — that's a client-side key-design bug, not a migration-mechanics bug — but an atomic multi-slot migration reduces the total window during which the cluster is in a mixed MIGRATING/IMPORTING state, which shrinks how long any latent per-slot bug like this one has to manifest, and makes the blast radius of a bad resharding window smaller across the board.

04 Migrating onto StackExchange.Redis 3.0

Tier: SeniorMigration / version upgrade
EXAMPLE — replace with your own

StackExchange.Redis 3.0 (GA 2026-06-12) shipped a rewrite of the client's IO core — a new write path and a RESP3-by-default protocol negotiation — that the maintainers' own benchmarks put at roughly 2.3x the throughput of the 2.x line under load. That's a big enough number to justify a planned migration rather than picking it up incidentally on a routine `dotnet outdated` sweep, so I ran it as one: pinned the version in a feature branch, ran our existing integration suite against a real Redis instance (not mocks — this is exactly the kind of change a mock hides), and load-tested the hot paths before touching production.

Two things needed real changes, not just a version bump. First, RESP3 becoming the default protocol meant a few places in our code that inspected raw reply types (a legacy pattern from before the library abstracted this well) needed updating, because RESP3's richer type system (maps, sets, doubles, booleans as first-class reply types instead of RESP2's bulk-string-for-everything) changed what `IServer`/`IDatabase` calls returned in edge cases like `HGETALL` on an empty hash. Second, and more valuably, the upgrade forced a real audit of every `ConnectionMultiplexer` construction site — we found two services still building a fresh multiplexer per request instead of sharing one process-wide singleton, a classic anti-pattern that exhausts the thread pool under load because each multiplexer opens its own connection and warms its own state. That bug predated 3.0; the migration was just the excuse to go looking.

What the interviewer is really probing

Whether you treat a client-library major upgrade as an engineering exercise with real risk (protocol changes, connection-lifecycle bugs) or as a trivial version bump — and whether you can name a concrete anti-pattern (per-request multiplexer) rather than gesturing at "connection management issues". They also want to hear that you tested against a real server, since RESP2-vs-RESP3 differences are exactly the kind of thing a mocked test suite papers over.

Follow-up drill chain

Why would a mocked test suite miss the RESP3 reply-typing changes?

Because a mock returns whatever shape the test author wrote by hand, which encodes their existing assumptions about the reply type — it can't surface a real protocol-level difference in how the wire actually represents an empty hash or a double, since that difference lives in the server and the client's parser, neither of which the mock exercises.

What if the Redis server on the other end were still on an old version that doesn't speak RESP3?

StackExchange.Redis negotiates protocol version with the server at connection time and falls back to RESP2 automatically if RESP3 isn't supported, so the client degrades gracefully — but it means you can't assume RESP3 behavior in your own code just because you're on client 3.0; if you support mixed server versions across environments, test both paths.

At what request volume does the per-multiplexer-per-request bug actually start hurting, versus just being wasteful?

It's wasteful from the first request, but it becomes an outage risk once concurrent request volume approaches the thread pool's available worker threads, because each new multiplexer's connection handshake consumes a thread-pool thread that would otherwise serve a request — in our case that threshold was in the low hundreds of concurrent requests per instance.

What did you trade away by migrating instead of staying on 2.x longer?

Migration risk and engineering time now, in exchange for a real throughput ceiling increase and first-class client-side caching support we'd need anyway for a feature already on the roadmap — I judged it cheaper to absorb the risk on our schedule than to be forced into it later alongside an unrelated deadline.

How would you validate the vendor's 2.3x throughput claim rather than just trusting it?

I ran our own load test against our own hot paths and our own Redis topology rather than citing the vendor number in the postmortem — the actual gain we measured was smaller than 2.3x because our bottleneck wasn't purely client IO, but it was still a clear, positive, measured number, which is the only kind worth reporting.

05 Pub/Sub or Streams for order notifications

Tier: MidTechnical disagreement with a colleague
EXAMPLE — replace with your own

A colleague wanted to wire up order-status notifications (payment confirmed, shipped, delivered) using Redis Pub/Sub — `PUBLISH orders:status {...}`, with each downstream service `SUBSCRIBE`d. It's genuinely the simplest thing that could work, and for a "nice to have" internal dashboard it would have been fine. I pushed back because these notifications fed a customer-facing email trigger, and Pub/Sub in Redis is fire-and-forget, at-most-once delivery: if a subscriber is disconnected — a deploy, a restart, a network blip — every message published during that gap is gone. No replay, no consumer catch-up. "It worked in my local test" is exactly the trap here, because a local test never disconnects mid-stream.

I proposed Redis Streams instead: `XADD orders:status * status shipped orderId 12345`, with the email service as a consumer group member calling `XREADGROUP GROUP email-senders consumer-1 COUNT 10 STREAMS orders:status >`, then `XACK` once the email actually sends. The disagreement wasn't really about Redis at all — it was about whether "at most once, best effort" was an acceptable guarantee for something with a customer-visible consequence, and once we framed it that way instead of "which command is simpler", the colleague agreed quickly. We kept Pub/Sub for the internal ops dashboard's live tail, where losing a message during a deploy is a shrug, and used Streams for anything an email or an SLA depended on.

Follow-up drill chain

Why not just make Pub/Sub reliable by adding your own ack/retry layer on top?

You'd be rebuilding, badly, the exact mechanism Streams already gives you for free — a persisted log, per-consumer cursors, and acknowledgment. At that point you're maintaining bespoke reliability code with none of the operational tooling (`XPENDING`, `XINFO`) Streams already ships with, for no benefit over just using Streams.

What if a consumer never acks a message — does it just sit there forever?

Yes, until something claims it — it stays in the Pending Entries List for that consumer group. Since Redis 8.4, `XREADGROUP` supports a `CLAIM` mode that lets another consumer take over stuck entries after an idle threshold, which is the modern replacement for the older two-step `XPENDING` + `XCLAIM` dance; either way, someone has to actively reclaim abandoned work or it never gets a second attempt.

At what throughput would Streams' extra overhead start to matter versus Pub/Sub?

Streams persist every entry (subject to your trim/maxlen policy) and track consumer-group state, so there's real memory and write cost per message that Pub/Sub doesn't pay. For a use case doing tens of thousands of ephemeral messages per second where losing a burst is truly fine, I'd not default to Streams just because it's "safer" — that's over-engineering for a guarantee nobody needs.

What did you trade away by splitting the two notification paths (Streams for email, Pub/Sub for the dashboard) instead of standardizing on one?

Operational surface area — two mechanisms to monitor and reason about instead of one. I judged that acceptable because collapsing them onto Streams everywhere would mean paying persistence and ack overhead for a dashboard tail that explicitly doesn't need it, which is the wrong trade in the other direction.

How would idempotency change this design if the email service could receive the same shipped event twice?

At-least-once delivery means duplicates are expected, not exceptional, so the email send itself needs to be idempotent — I'd key the "already sent" check on the order ID plus status transition, either via a dedup set with a TTL or, since Redis 8.6, `XADD`'s idempotency options (IDMP/IDMPAUTO) at the producer side to prevent the duplicate entry from ever landing in the stream in the first place.

06 The hash that ate the memory budget

Tier: SeniorNasty debugging session
EXAMPLE — replace with your own

`maxmemory` alerts started firing on a Redis instance that, by row count, should have had headroom to spare — `DBSIZE` reported about 900k keys, which on paper fit comfortably under the 8GB cap we'd sized for. `INFO memory` told a different story: `used_memory` was climbing toward the cap steadily, with no obvious leak in the app's write rate. I reached for `redis-cli --bigkeys` first, which samples the keyspace and reports the largest key per type — it pointed at a single logical prefix, `user:profile:*`, as hashes with an unusually large average field count, some past 4,000 fields.

The actual cause was a data-modeling drift: a "user profile" hash that started small (a dozen fields) had grown, feature by feature, into a catch-all for every per-user setting anyone ever added, including several that were really per-session and should never have lived on a long-lived key. `OBJECT ENCODING` on the big ones confirmed they'd long since crossed Redis's `hash-max-listpack-entries` threshold and were stored as a full hash table internally rather than the compact listpack encoding small hashes get — meaning per-field memory overhead that had been negligible at a dozen fields became significant at four thousand.

The fix was mechanical once diagnosed: split the profile hash into a small, bounded "core profile" hash (identity, preferences — genuinely long-lived, genuinely small) and a separate per-session key with its own TTL for the transient fields, so the long-lived hash stayed under the listpack threshold and the transient data expired instead of accumulating forever. As a longer-term structural improvement, Redis 8.10's Compact Hashes encoding raises the practical field-count ceiling before a hash falls back to the expensive representation, and ships an `HIMPORT` command to migrate existing hashes into the compact form without an app-level rewrite — I flagged that as a candidate to revisit instead of the manual split, next time this class of drift happens on a hash we can't easily redesign.

Why does field count matter more than total hash size for this encoding threshold?

`hash-max-listpack-entries` and `hash-max-listpack-value` are both independently checked — either crossing its threshold flips the encoding, so a hash with many small fields can convert on field count alone even if total bytes are modest, while a hash with a few very large field values can convert on the value-size threshold instead. What if raising `hash-max-listpack-entries` instead of splitting the key had been the "fix" — what would have gone wrong later?

It would have papered over the real issue: an unbounded, ever-growing hash. Raising the threshold buys you a temporary reprieve at the cost of the listpack representation itself becoming O(N) per field access on a genuinely large hash — you'd trade a memory problem for a latency problem, on the same key, later.

At what field count would you now proactively split a hash, before it becomes a problem?

I treat a couple hundred fields as the point to ask "is this genuinely one entity, or several things sharing a key by accident" — well below the default listpack threshold, because the question is a modeling one, not purely a memory one, and it's cheaper to ask it early.

What did you trade away by splitting into a core-profile hash plus a separate per-session key?

One extra round trip for code paths that genuinely needed both core and session data together, and a bit more application-level complexity in knowing which field lives where. I judged that acceptable because it made the two lifetimes (long-lived identity, ephemeral session state) explicit instead of silently mixed.

How would Compact Hashes and HIMPORT have changed your approach if they'd been available at the time?

I'd likely have tried the encoding migration first, since it needs no application-level schema change — `HIMPORT` moves an existing hash into the compact representation in place. I'd still keep the schema split as the long-term fix for the unbounded-growth root cause, but Compact Hashes would have bought time to do that split calmly instead of under a memory-pressure alert.

I'd only reach for that if fixed-window's boundary-burst behavior (up to 2x the limit across a window edge) were actually a problem for this client, not by default.

Rather than just fixing the line, I used it as a teaching moment, because the underlying mechanism generalizes far past Redis. `.GetAwaiter().GetResult()` (or `.Result`, or `.Wait()`) on a `Task` blocks the calling thread until that task completes — fine if the task is running on a different thread already, dangerous when the ASP.NET Core synchronization context or a constrained thread pool means the task's continuation needs a thread from the same limited pool the caller is blocking. Under load, every request blocks a pool thread waiting on a Redis call, while the Redis call's own async continuation is queued waiting for a pool thread to run on — and if there aren't enough spare threads, that's a deadlock, or at least a severe stall that looks like one under load, even though everything is "working" at low traffic when there's always a spare thread lying around.

Why does BCAST need a prefix pattern rather than tracking every key automatically?

There's a narrow window between a write happening and the invalidation message reaching every subscribed client, during which a stale local read is possible — RESP3 push-based invalidation is fast but not instantaneous. If a keyspace is write-heavy relative to reads, the invalidation traffic itself can approach or exceed the round-trip cost you're trying to save, and the local cache rarely gets to serve a request before being invalidated again — client-side caching earns its complexity specifically on read-heavy, relatively slow-changing data, which is exactly the "hot, rarely-changing product" profile this endpoint had.

Some memory overhead per app instance — BCAST invalidation for a whole prefix means the server tracks that prefix's subscription regardless of per-client read history, and each instance may end up locally caching keys it didn't specifically request, versus default mode's tighter per-client tracking. I judged that acceptable because the prefix was small and bounded (a few hundred hot products), not the whole keyspace.

If most product keys were cold and only a genuinely unpredictable subset ran hot at any given time, `OPTIN` (only cache keys explicitly marked via `CLIENT CACHING YES` before the read) would let the app decide per-request which reads are worth caching, rather than a static prefix rule — more precise, more application-level bookkeeping. This triage pattern generalizes well beyond licensing — security mandates, compliance deadlines, and platform migrations all fit this shape.

Follow-up drill chain

Why does AGPLv3 matter here — isn't Redis still "less open" than before the relicensing?

The 2024 relicensing moved Redis off the fully-permissive BSD-3 license to SSPL/RSAL-only, which was genuinely restrictive and prompted the Valkey fork — but Redis 8.0's tri-license reintroduced AGPLv3 as an option, which is a real, OSI-recognized open-source license with no hosting restriction; it just carries copyleft obligations (source-sharing requirements) that mainly bite if you're distributing modified Redis source, not if you're simply running it as internal infrastructure. The nuance leadership missed was treating "not BSD anymore" as equivalent to "not open-source at all", which conflates two different things.

What if leadership had insisted on the blanket timeline anyway, after hearing your analysis?

I'd have complied — pushing back with substance is different from refusing a decision once made — but I'd have documented the risk trade-off explicitly (the engineering cost of an unhurried migration compressed into a quarter, across teams with no real license exposure) so the cost of the decision was visible and owned at the level that made it, not silently absorbed by the teams executing it.

At what point would migrating to Valkey be the right call purely on technical merits, independent of licensing?

If Valkey's own roadmap or community momentum overtook Redis's for features we actually needed, or if our vendor/hosting relationship made Valkey meaningfully cheaper or better-supported for our use case — that's a normal build-vs-buy-style evaluation I'd run on its own timeline, not a five-week compliance sprint, because the two questions (license exposure, technical fit) have completely different urgency profiles and shouldn't be forced onto the same clock.

What did you trade away by proposing the triage instead of just complying with the blanket mandate?

Some political capital and a slightly uncomfortable conversation with leadership about a directive they'd already committed to publicly — I judged that worth it because executing a rushed, unnecessary migration across dozens of internal-use instances would have cost far more engineering time than the conversation risked, for zero actual risk reduction.

How would you validate that StackExchange.Redis actually works correctly against Valkey before recommending it, even for the unhurried subset?

Valkey maintains RESP protocol compatibility deliberately, and I'd still run our own integration test suite against a Valkey target explicitly, including RESP3-specific features (client-side caching, the newer command set) rather than assuming compatibility from protocol-level claims alone — "protocol compatible" and "behaves identically for every command and edge case our code depends on" aren't guaranteed to be the same thing until verified.

22 Night-before cheat sheet

~10 sentencesSpeak these out loud once

Read this once, out loud, the night before. Not new material — just the sentences you want loaded and ready to say without groping for the words mid-answer.

  1. Redis executes commands on a single thread per shard; the I/O-threading work since Redis 8.0 parallelizes reading and writing bytes off the socket, not command execution — so any O(N) command (KEYS, unbounded SMEMBERS, SORT) blocks everyone else on that shard for its full duration.
  2. SCAN/HSCAN/SSCAN/ZSCAN trade a weaker guarantee (a key present the whole scan is returned at least once, not exactly once) for never blocking — that trade is almost always worth it in production.
  3. Redis Cluster splits the keyspace into 16,384 hash slots via CRC16(key) mod 16384; multi-key operations across slots fail with CROSSSLOT unless the keys share a hash tag like {user123}.
  4. ACL key patterns restrict commands that take a key argument — they do not restrict database-wide commands like FLUSHALL, which must be stripped explicitly, usually by denying the @dangerous category.
  5. The persistence default, appendfsync everysec, accepts up to about a second of write loss on a hard crash; that's the right choice for most workloads, but it should be a deliberate decision per instance, not an inherited default, for anything holding data that exists nowhere else.
  6. Client-side caching (Tracking) has two shapes: default mode invalidates only keys a client itself read; broadcasting (BCAST) invalidates by key-prefix regardless of read history — pick based on whether access patterns overlap across clients.
  7. Redis relicensed off BSD in 2024 (SSPL/RSAL-only), which is what prompted the Linux Foundation's Valkey fork; Redis 8.0 (GA 2025-05-02) reintroduced a genuinely open option by going tri-license — RSALv2, SSPLv1, or AGPLv3 — and AGPLv3 has no hosting restriction, it's only copyleft.
  8. StackExchange.Redis 3.0 rewrote the I/O core, defaults to RESP3, and is roughly 2.3x throughput on the vendor's own benchmark over 2.x — the sync-over-async trap (.Result, .GetAwaiter().GetResult()) is unrelated to the client version and will starve the thread pool on any version if you write it that way.
  9. Streams give consumer groups, per-message ack (XACK) and replay via XPENDING/claiming — Pub/Sub is fire-and-forget with no replay, so the two are not interchangeable despite both being "publish something, subscribers react".
  10. Compact Hashes (Redis 8.10) raise the practical field-count ceiling before a hash falls back to the expensive hash-table encoding, with HIMPORT to migrate an existing hash in place — but the better fix for an unbounded, ever-growing hash is usually a schema split, not a bigger threshold.
  11. INCREX (Redis 8.8) folds "increment, and set a TTL only if this is a new key" into one atomic server-side command — the primitive most hand-rolled Lua fixed-window rate limiters exist to approximate.
  12. Sorted sets (ZADD/ZREVRANGE/ZREVRANK) are the default fit for ranking and leaderboards; when a requirement (per-member independent reset windows, say) stops mapping onto one global sorted set cleanly, that's the signal to ask whether the requirement is actually firm before redesigning around it.
