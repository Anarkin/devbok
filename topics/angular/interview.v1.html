01Components, templates and the modern authoring model

This is the compulsory opener: almost every loop starts by checking whether you write Angular the way it is written in 2026 — standalone components, built-in control flow, signal-based inputs — or the way it was written in 2019. Nothing here is hard, but a mid-level answer to the first three questions caps the whole interview, because everything later (change detection, forms, performance) assumes this vocabulary. At mid level you are expected to write the code fluently; at senior to explain why each replacement exists and what it costs; at principal to plan the migration of a large codebase without freezing feature work.

screenerWhat is a standalone component, and what happened to NgModules?

Answer

A standalone component declares its own template dependencies in an imports array instead of being declared by an NgModule. Standalone arrived in v14, became production-ready in v15, and since v19 standalone: true is the default — you only write standalone: false to keep a component inside an NgModule. NgModules are not removed and not deprecated at the framework level, but they are no longer the unit of composition: bootstrapping is bootstrapApplication() with provideX() functions, routing is provideRouter(), and lazy loading is a plain dynamic import() of a component or a routes array. The practical benefit is that the compiler and bundler can see exactly what a component uses, so tree-shaking and lazy boundaries get much sharper, and a component is readable on its own without hunting for the module that declared it.

Example

// main.ts — no AppModule anywhere
bootstrapApplication(App, {
  providers: [provideRouter(routes), provideHttpClient()],
});

@Component({
  selector: 'app-invoice',
  imports: [InvoiceRow, CurrencyPipe],   // standalone: true is the default since v19
  template: `@for (row of rows(); track row.id) { <app-invoice-row [row]="row" /> }`,
})
export class Invoice { rows = input.required<Row[]>(); }

Follow-ups

  • Are NgModules deprecated? — No. They still work and still exist for libraries and legacy code; they are simply no longer how new code is organised.
  • How do you migrate an existing app? — ng generate @angular/core:standalone, run in three passes (convert declarations, remove unnecessary modules, switch bootstrap), each pass a separate commit.
  • Where do providers live now? — Root providers in bootstrapApplication, route-scoped providers in a route's providers array, component-scoped in the component's providers.

Common wrong answer

"NgModules are deprecated and removed." They are neither, and saying so signals you have only read blog headlines. The honest answer is that they are legacy for application code, still supported, and still the shape of most published libraries you will consume.

screenerWhy did Angular replace *ngIf / *ngFor with @if / @for, and why does @for force you to write track?

Answer

Built-in control flow arrived in v17 and is stable since v18; it is compiled directly into the template instructions instead of going through structural directives, so there is no CommonModule import, no directive instantiation per branch, and the compiler can type-narrow inside a block. It is also measurably faster — the Angular team measured up to roughly 90% faster rendering on list-heavy benchmarks, mostly from the new diffing algorithm. track is mandatory because the old trackBy was optional and everyone skipped it, which meant every array reference change destroyed and recreated every DOM node. Making it a required expression turns "correct list rendering" into the default rather than an optimisation you remember on your third performance bug.

Example

@if (user(); as u) {
  <p>{{ u.name }}</p>      <!-- u is narrowed to User, not User | null -->
} @else {
  <app-login />
}

@for (item of items(); track item.id) {
  <li>{{ item.label }}</li>
} @empty {
  <li class="muted">Nothing here yet</li>
}

Follow-ups

  • What do you track when items have no id? — track $index is legitimate for static, append-only lists; never track a mutable field, and never track the object itself if the array is rebuilt from JSON.
  • What is NG0955? — The runtime error for duplicate track keys; it means your key is not unique and Angular cannot match nodes to items.
  • Is *ngIf deprecated? — The directives still work; the CLI migration ng generate @angular/core:control-flow converts a codebase automatically.
  • What does @empty give you? — A built-in empty-state branch, which used to need a second *ngIf over length === 0.

Common wrong answer

"It's just nicer syntax / sugar for the same directives." It is not sugar: the block form compiles to different instructions, ships no directive code, and uses a different list-diffing algorithm. Candidates who call it cosmetic usually also miss why track is required.

midCompare @Input()/@Output() with input(), output() and model().

Answer

Signal-based inputs and outputs landed in v17.1–17.2 as developer preview and are stable since v19. input() returns a read-only signal, so consuming code reacts to it through computed() or effect() instead of ngOnChanges; input.required<T>() makes the input mandatory at compile time, which the decorator could never express without a runtime check. output() is a plain function returning an OutputEmitterRef — it is not an EventEmitter, is not an Observable, and unsubscribes automatically with the component. model() creates a writable two-way input, replacing the value/valueChange pair that made banana-in-a-box work. The reason this matters beyond ergonomics: signal inputs participate in the reactive graph, so a component reading them can be fully OnPush-correct and zoneless-safe with no manual markForCheck.

Example

@Component({ selector: 'app-price', template: `{{ formatted() }}` })
export class Price {
  amount = input.required<number>();
  currency = input('EUR');
  precision = input(2, { transform: numberAttribute });   // string -> number from the DOM
  changed = output<number>();                              // OutputEmitterRef, not EventEmitter
  qty = model(1);                                          // two-way: [(qty)]

  formatted = computed(() =>
    new Intl.NumberFormat('de-DE', { style: 'currency', currency: this.currency() })
      .format(this.amount() * this.qty()));
}

Follow-ups

  • Do signal inputs replace ngOnChanges? — For reacting to a value, yes: use computed or effect. ngOnChanges is not called for signal inputs' previous/current comparison in the way people expect, so do not mix the two on one input.
  • When is a signal input first readable? — After construction; reading a required input in the constructor/field initialiser throws NG0950. Read it in computed(), effect() or ngOnInit.
  • Why is output() not an Observable? — Because emitting is a one-way notification, and dropping EventEmitter removes RxJS from the component contract entirely; use outputFromObservable() if you genuinely have a stream.
  • Is there a migration? — Yes: ng generate @angular/core:signal-input-migration (and matching output/query migrations).

Common wrong answer

"output() is just EventEmitter with a new name, so I can call .subscribe() and .complete() on it." It is a different type with only emit() and subscribe() for interop; treating it as an RxJS Subject leads to code that will not compile — and it hints you never actually used it.

midExplain @defer: what it does, its triggers, and what the compiler does with it.

Answer

Deferrable views (v17, stable in v18) let a template declare a lazy boundary without touching the router or writing a dynamic import by hand: the components, directives and pipes used only inside a @defer block are split into a separate chunk at build time and fetched when a trigger fires. The block has four states — the main content, @placeholder (rendered eagerly, must be lightweight), @loading (shown while the chunk is in flight, with minimum/after to avoid flicker) and @error. Triggers are declarative: on idle (the default), on viewport, on interaction, on hover, on timer(...), on immediate, plus when <expression>; prefetch runs the fetch on a different trigger than the render. In v22, on idle(timeout) accepts a millisecond bound so you can cap how long you wait for idle. The key constraint is that a deferred dependency must not be referenced outside the block, or it lands in the eager chunk and the whole thing silently does nothing.

Example

@defer (on viewport; prefetch on idle) {
  <app-comments [postId]="id()" />
} @placeholder (minimum 200ms) {
  <div class="skeleton"></div>
} @loading (after 100ms; minimum 300ms) {
  <app-spinner />
} @error {
  <p>Comments failed to load.</p>
}

Follow-ups

  • How do you verify the split actually happened? — Build and look for a new lazy chunk in the stats output; if the component still sits in the main chunk, something references it eagerly.
  • How does @defer behave under SSR? — With incremental hydration (on by default in v22) a deferred block can be server-rendered and hydrated only when its trigger fires, using hydrate on ...; without it, deferred content renders its placeholder on the server.
  • Which trigger for a below-the-fold widget? — on viewport with prefetch on idle, so the chunk is warm before the user scrolls.

Common wrong answer

"@defer delays rendering, so it makes the page faster." Only if the deferred code actually leaves the initial bundle. Candidates who cannot say what determines the split — that the symbols must be used exclusively inside the block — have used it in a demo, not in a codebase.

midWhat replaced @ViewChild, and when is a signal query resolved?

Answer

Signal queries — viewChild(), viewChildren(), contentChild(), contentChildren() — are stable since v19 and return signals instead of being assigned by the framework at a lifecycle moment. That removes the entire { static: true | false } question: a view query signal returns undefined until the view has been created, and reading it inside a computed() or effect() gives you a value the moment it exists. Use viewChild.required() when the element is unconditionally present and you want a compile-time guarantee instead of a null check. The decorator forms still work, but they force you to pick a lifecycle hook (ngAfterViewInit for dynamic children) and then manually trigger change detection if you write to state there — the classic source of NG0100.

Example

export class Chart {
  canvas = viewChild.required<ElementRef<HTMLCanvasElement>>('cv');
  rows = contentChildren(Row);            // Signal<readonly Row[]>

  constructor() {
    effect(() => {
      const ctx = this.canvas().nativeElement.getContext('2d');
      draw(ctx, this.rows().map(r => r.value()));
    });
  }
}

Follow-ups

  • Why did static: true exist? — To read a query in ngOnInit when the element is not inside any conditional; it was a workaround for query timing that signal queries make unnecessary.
  • What does contentChildren see that viewChildren does not? — Projected content passed through <ng-content>, not the component's own template.
  • Do queries include elements inside @if blocks? — Yes, and the signal updates when the block is created or destroyed, which is exactly why the signal form is better than the decorator.

Common wrong answer

"I read viewChild() in the constructor." It is undefined there. Worse is claiming signal queries are "the same thing with different syntax" — the timing semantics are the entire point.

seniorHow do you bind to the host element today, and why did the host object come back into fashion?

Answer

The recommended form is the host object in the decorator metadata: host: { 'class.active': 'isActive()', '(click)': 'onClick($event)', '[attr.aria-expanded]': 'expanded()' }. It keeps every host binding in one visible place next to the selector, works identically for components and directives, and the Angular style guide now prefers it over scattering @HostBinding/@HostListener across fields. Functionally they are equivalent — both compile to host binding instructions evaluated during the host element's change detection — but the decorators are easy to lose in a 400-line class and interact awkwardly with inheritance. One thing candidates miss: host bindings are evaluated as part of the host component's change-detection pass, so a host binding that reads a signal is fine, while one that calls an expensive method runs on every check of the parent.

Example

@Directive({
  selector: '[appTooltip]',
  host: {
    '[attr.aria-describedby]': 'id',
    '[class.tip-open]': 'open()',
    '(mouseenter)': 'open.set(true)',
    '(mouseleave)': 'open.set(false)',
    '(keydown.escape)': 'open.set(false)',
  },
})
export class Tooltip { readonly open = signal(false); readonly id = `tip-${nextId++}`; }

Follow-ups

  • Why not :host in CSS instead? — :host is styling only; host bindings drive attributes, classes and listeners from component state.
  • What is the cost of a host listener? — A real DOM listener per instance; for high-frequency events on many instances, delegate from a parent or use @HostListener with a passive/throttled handler.
  • Can a directive set a host binding a component also sets? — Yes, and static class/style bindings merge, but two dynamic bindings on the same property conflict — the last one applied wins, which is a real bug source in design systems.

Common wrong answer

"I write to nativeElement.classList in ngAfterViewInit." It works until you server-render (no DOM), or until change detection overwrites it. Direct DOM mutation is the answer that ends the "do you understand rendering abstractions" line of questioning badly.

seniorWhat does strictTemplates buy you, and what changed in template type checking recently?

Answer

With strictTemplates: true (on by default in new apps for years now) the compiler type-checks input bindings, $event types, template reference variables, pipe argument and return types, and the safe-navigation results — instead of treating templates as any. This is what makes renaming a model property a compile error rather than a blank cell in production. Angular 22 pushed template expressions further towards TypeScript semantics: object and array spread in template expressions, arrow functions with implicit returns, instanceof checks, multiple @case labels falling through to the same block, @default never; and the never(...) helper for exhaustiveness over discriminated unions, and — importantly — ?. now follows JavaScript semantics and yields undefined rather than Angular's older null coercion, with proper narrowing after a truthiness check. v22 also requires TypeScript 6.

Example

@switch (event.kind) {
  @case ('created') @case ('restored') { <app-badge tone="ok" /> }   <!-- v22 fall-through -->
  @case ('deleted') { <app-badge tone="warn" /> }
  @default never;   <!-- compile error if a new union member is added -->
}

Follow-ups

  • What is fullTemplateTypeCheck? — The older, weaker flag; strictTemplates supersedes it and turning the old one on alone gives a false sense of safety.
  • How do you type a generic component's input? — Generic components infer from the bound expression under strictTemplates; for tricky cases use ngTemplateContextGuard and input type-narrowing static guards.
  • Downside? — Turning it on in a legacy app produces hundreds of errors at once; enable it per-project in a monorepo, or fix by directory with a temporary // @ts-expect-error budget you actually burn down.

Common wrong answer

"Templates are type-checked anyway, the flag just adds strict null checks." Without strictTemplates input bindings are effectively unchecked — a wrong type flows straight through. Underselling this suggests you have never migrated a codebase onto it.

seniorWhen would you still reach for ng-template and ngTemplateOutlet now that control flow is built in?

Answer

@if/@for replaced the structural directive use of templates, but ng-template is still the mechanism for passing a chunk of rendering to someone else. The three cases that survive: customisation slots in a library component (a table that lets the consumer supply the cell template), recursion (a tree that renders itself with ngTemplateOutlet), and deferred/conditional rendering driven by TypeScript rather than the template — ViewContainerRef.createEmbeddedView(). Templates also carry a typed context, so let-row can be strongly typed via ngTemplateContextGuard, which is how well-typed table libraries work. Rule of thumb for a lead: use control flow blocks for your own conditionals, ng-template only when the rendering decision belongs to the caller.

Example

<!-- library -->
<tbody>
  @for (row of rows(); track row.id) {
    <tr><ng-container *ngTemplateOutlet="cell(); context: { $implicit: row }" /></tr>
  }
</tbody>

<!-- consumer -->
<app-table [rows]="orders()">
  <ng-template #cell let-row><td>{{ row.total | currency }}</td></ng-template>
</app-table>

Follow-ups

  • Template vs content projection? — ng-content when the consumer's markup is rendered once, as-is; ng-template when it must be rendered N times or with context.
  • Cost? — Each embedded view is a real view with its own change detection; a table with a template per cell in a 10k-row grid is why you virtualise.
  • How do you type the context? — A static ngTemplateContextGuard on the directive that consumes the template.

Common wrong answer

"ng-template is legacy now that we have @if." That confuses the structural-directive syntax with the primitive. Any component library you build will use templates for its slots.

principalYou inherit a 300-component Angular 16 app on NgModules, *ngIf and decorators. How do you get it to the modern authoring model without freezing feature work?

Answer

Sequence it as version upgrades first, style migrations second, and never both in one PR. Step one is getting to a supported version — v16 is long out of support (18-month window: 6 months active, 12 LTS), so run ng update one major at a time, in its own merge, with the app deployable after each. Step two is the mechanical migrations, in this order because each shrinks the next: control flow, then standalone, then signal inputs/queries, then inject(). All four ship as CLI schematics, so the diff is machine-generated and reviewable by sampling rather than line-by-line. Step three is the semantic ones you cannot automate — zoneless and OnPush — which you do feature-area by feature-area behind a route boundary, because they change runtime behaviour. Throughout, the guardrails matter more than the speed: bundle-size budgets in angular.json that fail CI, a lint rule banning new NgModules and new *ngIf, and a per-area owner so the migration has a name attached, not a wiki page.

Example

ng update @angular/core@17 @angular/cli@17   # one major per PR, deployable each time
ng generate @angular/core:control-flow       # mechanical, huge diff, low risk
ng generate @angular/core:standalone         # 3 passes: convert, prune modules, bootstrap
ng generate @angular/core:signal-input-migration
ng generate @angular/core:inject-migration
# only then, area by area:
ng generate @angular/core:signals            # OnPush / zoneless readiness

Follow-ups

  • How do you keep the team shipping? — Time-box migration PRs to one per sprint per area, merge them first thing Monday, and require the schematic's diff to be reviewed by sampling plus a green e2e run.
  • How do you prove it was worth it? — Track initial bundle size, LCP/INP from RUM, and CI time before and after; those three move visibly and are what a VP will ask about.
  • What if a critical third-party library is NgModule-only? — Standalone components can import NgModules, so it never blocks you; wrap it once and isolate the dependency.
  • What do you deliberately not migrate? — Code scheduled for deletion, and anything with no tests where the risk is not repaid.

Common wrong answer

"We'd do a big-bang rewrite on a branch." Long-lived migration branches on a 300-component app lose to the mainline within a month and get abandoned — most interviewers have personally lived through that, and it is the single fastest way to fail a principal-level question.

principalA team member wants to hold off on a component-library refactor "until selectorless lands". What do you tell them?

Answer

That we are not waiting, because selectorless is not coming on a schedule anyone can plan against. It was a serious prototype — merged as experimental compiler work in April 2025, letting you write <MatButton:a> and @Tooltip(...) and reference components by class name instead of a CSS selector — but it was removed from the public roadmap and put on hold, with the team explaining in the April 2026 monthly Q&A that introducing a second template authoring syntax would fragment ecosystem adoption right when tooling and AI assistants are converging on the current one. So it is not experimental, not developer preview, and not in v22. The transferable lesson for the team is the rule I would want them to apply generally: architect against what is stable today, treat roadmap items as options with no delivery date, and make sure a refactor's value does not depend on a feature you cannot ship without.

Example

// The prototype syntax (April 2025) — NOT available in v22:
// <MatButton:a href="/next">Next</MatButton:a>
// @HasRipple @Tooltip('Save now')

// What you ship today: an explicit imports array, which is already
// refactor-safe because the symbol is a real TypeScript import.
@Component({ selector: 'app-toolbar', imports: [MatButton, Tooltip], template: `...` })
export class Toolbar {}

Follow-ups

  • What was the actual pain it addressed? — Multi-selector directives (selector: 'a[mat-button], button[mat-button]') and the fact that a template symbol is not a TypeScript reference, so IDE rename and dead-code detection are weaker than they should be.
  • Where do you check status like this? — angular.dev/roadmap plus the release blog; both are explicit about stable / developer preview / experimental labels.
  • How do you keep the option open? — Keep imports arrays explicit and per-component, avoid barrel re-exports, and keep selectors consistent; that is what any future migration would key off.

Common wrong answer

"Selectorless is in Angular 22, we should adopt it." Several vendor blogs claimed exactly that ahead of the release, and repeating it is the clearest possible signal that you read summaries rather than the release notes. Saying "I'm not sure of its current status, and here is how I'd check" scores far better than a confident wrong claim.

02Signals and the reactivity model

Signals are the centre of gravity of modern Angular, and interviewers use them as the fastest proxy for "has this person shipped anything since 2024". The questions start easy — what is a signal — and move quickly to the parts that bite in production: when effects run, why writing to a signal inside an effect is a smell, how computed stays glitch-free, and how async fits in via resource. At mid level you must be fluent with signal/computed/effect; at senior you should be able to explain the pull-based graph and defend a rule for when not to use an effect; at principal you are expected to define the team-wide boundary between signals and RxJS and justify it.

screenerWhat is a signal, and how is it different from a BehaviorSubject?

Answer

A signal is a wrapper around a value that knows which computations and views read it, so when it changes it can notify exactly those consumers. You read it by calling it — count() — and write it with set() or update(). Signals became stable in v17 for signal/computed, with effect and linkedSignal stable in v20. Compared with a BehaviorSubject: a signal always has a value and is read synchronously with no subscription, it has no completion or error channel, it never leaks because there is nothing to unsubscribe, and — the framework-level difference — the template's dependency on it is tracked automatically, which is what makes zoneless change detection possible. A BehaviorSubject is a push-based multicast stream with an explicit lifecycle; a signal is pull-based state with automatic dependency tracking.

Example

// signal
readonly count = signal(0);
readonly doubled = computed(() => this.count() * 2);
inc() { this.count.update(c => c + 1); }   // template re-renders; nothing to unsubscribe

// BehaviorSubject equivalent
readonly count$ = new BehaviorSubject(0);
readonly doubled$ = this.count$.pipe(map(c => c * 2));
inc() { this.count$.next(this.count$.value + 1); }   // needs async pipe or manual teardown

Follow-ups

  • Does a signal replace RxJS? — No: signals model state, RxJS models events over time. Debounce, retry, websockets and cancellation still want operators.
  • Can a signal be async? — Not directly; use resource()/httpResource() (stable in v22) or toSignal() over an Observable.
  • What happens if you read a signal outside a reactive context? — You just get the value; nothing is tracked. That is why reading in a plain method does not create a subscription.

Common wrong answer

"A signal is Angular's version of an Observable." That framing makes every follow-up harder, because it implies subscriptions, completion and operators. The distinction interviewers listen for is state (always has a value, pull-based) versus events (push-based, may complete).

screenerWhen do you use computed() and when do you use effect()?

Answer

computed() is for derived values: it is lazy, memoised, and only recomputes when a dependency it actually read has changed and someone asks for the value. effect() is for side effects that must happen when state changes and that Angular cannot see — logging, analytics, syncing to localStorage, driving a third-party chart library. The rule I would give a team: if you are tempted to write to a signal inside an effect, you almost certainly wanted a computed or a linkedSignal. Effects are also scheduled, not synchronous: they run as part of change detection after the current synchronous block, so you cannot rely on an effect having run immediately after a set(). And an effect created in an injection context is destroyed with its component, which is why you rarely need manual cleanup.

Example

readonly query = signal('');
readonly results = signal<Row[]>([]);

// derived value -> computed
readonly resultCount = computed(() => this.results().length);

// side effect outside Angular -> effect
constructor() {
  effect((onCleanup) => {
    const chart = renderChart(this.results());
    onCleanup(() => chart.destroy());
  });
}

Follow-ups

  • Is computed eager? — No. If nothing reads it, it never runs; that laziness is what makes deep derivation chains cheap.
  • Where must effect() be created? — In an injection context (field initialiser or constructor), or pass an explicit { injector }; otherwise NG0203.
  • How do you clean up? — The onCleanup callback runs before each re-run and on destroy; that is the correct place to tear down timers and third-party instances.

Common wrong answer

"I use an effect to keep two signals in sync." That is the single most common signal anti-pattern: it creates a second source of truth, runs a change-detection cycle later than you think, and is exactly what linkedSignal and computed exist to prevent.

midHow does a computed know what it depends on, and why is the graph called "glitch-free"?

Answer

Dependency tracking is dynamic and happens at read time: while a computed's function executes, Angular records every signal it reads in that particular run, so a branch that was not taken creates no dependency. Propagation is push-then-pull: writing a signal marks dependents dirty (cheap, no computation), and the value is only recomputed when something actually reads it. That two-phase design is what makes it glitch-free — a consumer never observes an intermediate state where one derived value has updated and another has not, because nothing recomputes until the read, at which point the whole chain is resolved consistently. There is also value-equality short-circuiting: if a computed recomputes to a value equal to its previous one, its own dependents are not re-marked, so an unrelated change upstream does not cascade into a re-render.

Example

const showDetails = signal(false);
const user = signal({ name: 'Ada' });
const heavy = signal(bigThing);

// depends on showDetails always, on user only when showDetails is true,
// and never on heavy unless the branch runs
const label = computed(() => showDetails() ? user().name : 'hidden');

Follow-ups

  • What if a dependency changes during the computation? — Not possible: writes inside a computed throw. Computeds must be pure.
  • How do you read a signal without depending on it? — untracked(() => s()), typically to read configuration inside an effect without re-triggering it.
  • Do computeds ever run when nobody reads them? — No, and that includes the initial run; a computed that logs is a computed you will find confusing.

Common wrong answer

"You declare dependencies in an array, like React's useMemo." Angular tracks them automatically at runtime; there is no dependency array, and there is no stale-closure class of bug as a result.

midYou set() a signal to an object you mutated and nothing re-renders. Why?

Answer

Signals compare with Object.is by default. If you mutate an object or push into an array and then call set() with the same reference, the equality check says "unchanged" and no dependent is notified. The fix is to treat signal values as immutable — update(list => [...list, item]) — or, if you genuinely need reference-stable mutation, pass a custom equal function. A custom equal is also the right tool in the opposite direction: for a signal holding a large array from an API, equal: (a, b) => a.id === b.id or a shallow comparison avoids re-rendering when a refetch returns identical data. Note that equal affects notification, not storage: the new value is still stored, it just does not wake anyone up.

Example

const rows = signal<Row[]>([]);

rows().push(newRow); rows.set(rows());          // ❌ same reference, no notification
rows.update(list => [...list, newRow]);         // ✅

// deliberate: ignore refetches that produce an equivalent page
const page = signal<Page>(empty, { equal: (a, b) => a.etag === b.etag });

Follow-ups

  • What was mutate()? — An early API removed before signals went stable, precisely because it encouraged this bug; do not mention it as current.
  • Cost of immutable updates on a 10k-row list? — Copying the array is cheap next to re-rendering; if it ever matters, keep the identity map in a separate signal rather than deep-cloning.
  • Does equal run on every read? — No, only on write, comparing the new value with the current one.

Common wrong answer

"Signals do deep comparison, so mutating is fine." They do reference comparison via Object.is. Deep-equality assumptions are how teams end up with an app that renders correctly only after an unrelated click.

midWhat problem does linkedSignal solve that computed cannot?

Answer

linkedSignal (developer preview in v19, stable in v20) is writable state that resets when a source changes — the classic "selected item derived from a list, but the user can also change it" case. A computed cannot be written to, and hand-rolling this with an effect that calls set() is exactly the anti-pattern everyone warns about. The linked form keeps one source of truth and expresses the reset declaratively: when the source signal changes, the computation reruns and overwrites the local value; until then, user writes stick. The richer overload gives you the previous value so you can preserve a selection if it still exists in the new list, and v22 added a set callback so a write can be pushed back into the source rather than held locally.

Example

const options = signal<Option[]>([]);

// resets to the first option when options change, but keeps a still-valid selection
const selected = linkedSignal<Option[], Option | undefined>({
  source: options,
  computation: (opts, prev) =>
    opts.find(o => o.id === prev?.value?.id) ?? opts[0],
});

selected.set(someOption);   // writable, unlike computed()

Follow-ups

  • When is computed still right? — Whenever the value is purely derived and nobody writes to it. Reach for linkedSignal only when there is genuine local override.
  • How does this show up in forms? — A dirty field that must reset when the loaded record changes; Signal Forms handles that internally with the same primitive.
  • What was the v22 addition? — A set option, so writing the linked signal can update the upstream source instead of shadowing it.

Common wrong answer

"I'd use an effect that sets the selection when the list changes." It works in the demo and then produces a flash of the old selection, an extra change-detection pass, and — if two effects touch the same signal — an ordering bug nobody can reproduce.

seniorWhy is writing to a signal inside an effect discouraged, and what do you do when you genuinely must?

Answer

Because it turns a one-way data flow into a feedback loop: the write dirties consumers, which schedules another change-detection pass, and if the effect reads what it writes you get an infinite loop that Angular has to defend against. It also hides the derivation — the value's rule lives in a side effect rather than in the value's own definition — which makes it invisible in tests and in the DevTools signal graph. Angular's API reflects this: writing inside an effect was originally guarded by allowSignalWrites, and the whole design pushes you towards computed (pure derivation), linkedSignal (derived-but-writable) or resource (derived-from-async). The legitimate cases are narrow: bridging to something outside the reactive graph — a third-party widget's callback, a router navigation triggered by state — and there you should wrap the read in untracked() so the effect does not re-arm itself.

Example

// ❌ derivation hidden in a side effect
effect(() => this.total.set(this.items().reduce((s, i) => s + i.price, 0)));

// ✅ derivation where it belongs
readonly total = computed(() => this.items().reduce((s, i) => s + i.price, 0));

// ✅ genuine bridge: react to state, read config without depending on it
effect(() => {
  const id = this.selectedId();
  const mode = untracked(() => this.viewMode());
  this.router.navigate(['/item', id], { queryParams: { mode } });
});

Follow-ups

  • What does untracked() actually do? — Runs a function with dependency tracking disabled, so reads inside it do not become dependencies.
  • How do you spot the loop in review? — Any effect whose body contains .set( or .update( on a signal it also reads; that is a mechanical lint-able rule.
  • What is the testing consequence? — Effects need TestBed.tick() (or a flush) to run, so logic hidden in effects makes tests async and flaky; computeds are synchronous and trivially testable.

Common wrong answer

"It's fine as long as you don't create a cycle." The cycle is only the loudest failure. The quieter cost — untestable derivation, extra CD passes, ordering dependence between effects — is what a senior interviewer is probing for.

seniorExplain resource() and rxResource(): what they give you over calling a service in ngOnInit.

Answer

A resource is async state expressed as signals: you give it a reactive params (or request) function and a loader, and you get back value(), status(), error(), isLoading(), plus reload(). It became stable in v22 after two versions as experimental. The three things it does that a manual ngOnInit fetch does not: it re-runs automatically when a signal used in the params changes, it cancels the in-flight request when that happens — switchMap semantics, so no out-of-order responses overwriting newer data — and it exposes loading and error as first-class state instead of two extra booleans you forget to reset. rxResource is the same thing with an Observable loader, which is the bridge when your service layer is still RxJS.

Example

readonly userId = signal<string | undefined>(undefined);

readonly user = resource({
  params: () => this.userId(),                       // reactive: refetches on change
  loader: ({ params, abortSignal }) =>               // abortSignal cancels the old request
    fetch(`/api/users/${params}`, { signal: abortSignal }).then(r => r.json()),
});

// template
// @if (user.isLoading()) { <app-spinner /> }
// @else if (user.error()) { <app-error [err]="user.error()" /> }
// @else { {{ user.value()?.name }} }

Follow-ups

  • What happens if params returns undefined? — The loader does not run; that is the idiomatic way to express "not ready yet".
  • Is it a cache? — No. It is per-instance async state. If you need cross-component caching or deduplication, that is still a service (or TanStack Query-style layer) around it.
  • How do you mutate optimistically? — Feed the resource's value into a linkedSignal, or use v22's resource snapshots (resourceFromSnapshots()) to derive a modified view without changing the load logic.
  • What replaced request:? — The option was renamed params during the experimental period; older blog posts still show request.

Common wrong answer

"resource() caches responses, so it replaces a state library." It has no shared cache, no invalidation across components and no persistence. Overselling it is the fastest way into a follow-up you cannot answer.

seniorYou need to measure a DOM element after it renders. Which API, and why not effect()?

Answer

Use afterNextRender() for a one-shot post-render read, or afterRenderEffect() (v19) when it must re-run reactively. Both accept phase callbacks — earlyRead, write, mixedReadWrite, read — and Angular batches all the writes and all the reads of a cycle together, which avoids layout thrashing when several components measure at once. A plain effect() is the wrong tool for two reasons: it can run before the DOM for the current state has been committed, and — crucially — render callbacks do not run on the server, whereas an effect does, so an effect that touches offsetHeight is an SSR crash waiting for its first deploy. This is also the correct home for integrating imperative libraries: create in afterNextRender, destroy in the cleanup.

Example

export class Sticky {
  private el = viewChild.required<ElementRef<HTMLElement>>('bar');
  height = signal(0);

  constructor() {
    afterRenderEffect({
      read: () => this.height.set(this.el().nativeElement.offsetHeight),
    });
  }
}

Follow-ups

  • Why do the phases exist? — To separate reads from writes so the browser does one layout pass instead of one per component (layout thrashing).
  • What about ngAfterViewInit? — Still valid for one-time setup, but it runs on the server too and gives you no phase control.
  • Do these run in tests? — Yes, once change detection runs; TestBed flushes them with the fixture's detectChanges/tick.

Common wrong answer

"I'd use setTimeout(0) inside an effect." That is the pre-signals workaround; it fires at an arbitrary time relative to rendering, breaks under SSR, and in a zoneless app no longer even triggers change detection the way people assume.

seniorImplement a debounced type-ahead search with signals. What did v22 add here?

Answer

v22 added debounced(), which wraps a signal (or a resource) and returns one that only updates after a quiet period — so the canonical type-ahead no longer needs an RxJS pipeline at all: bind the input to a signal, debounce it, and feed the debounced signal into an httpResource, which cancels the in-flight request whenever the params change. Before v22 the idiomatic answer was toObservable(query).pipe(debounceTime(300), distinctUntilChanged(), switchMap(...)) and back through toSignal(), and that is still a perfectly good answer if the pipeline needs retry or backoff. The property to name unprompted is cancellation: without it, a slow response for "ang" can land after "angular" and repaint stale results — the bug interviewers are actually listening for.

Example

readonly query = signal('');
readonly debouncedQuery = debounced(this.query, 300);            // v22

readonly results = httpResource<Row[]>(() => {
  const q = this.debouncedQuery().trim();
  return q.length < 2 ? undefined : `/api/search?q=${encodeURIComponent(q)}`;
});

// pre-v22 equivalent, still valid when you need retry/backoff:
// readonly results = toSignal(toObservable(this.query).pipe(
//   debounceTime(300), distinctUntilChanged(), switchMap(q => this.api.search(q))), { initialValue: [] });

Follow-ups

  • Why return undefined for short queries? — A resource whose params are undefined does not load; it is the built-in "don't fetch yet" signal.
  • Where does distinctUntilChanged go in the signal version? — Signals already short-circuit on Object.is equality, so a repeated identical query does not re-trigger.
  • How do you cancel on component destroy? — Automatically; the resource is tied to the injection context.

Common wrong answer

"Use mergeMap so no request is wasted" — or the signals equivalent, firing a fetch per keystroke and taking whichever returns last. That is the exact race the question is testing; the answer must contain cancellation or last-write-wins ordering.

principalYour team is split on "signals everywhere" versus "keep RxJS". What rule do you set, and how do you enforce it?

Answer

I would set a boundary rather than a preference: signals own state, RxJS owns events. Anything a template renders, or that another component asks "what is it now", is a signal — component state, derived view models, form values, feature-store fields. Anything that is a sequence over time with operators that genuinely matter — websocket streams, retry with backoff, request coordination, rate limiting, cross-tab messaging — stays an Observable, converted at the edge with toSignal(). The reason to be explicit is not aesthetics: mixed conventions cost you in reviews, in onboarding, and in bugs where the same value exists as both a subject and a signal. Enforcement is boring on purpose — a written convention in the repo, a lint rule banning .subscribe() in components, service APIs that return signals or resources rather than raw subjects, and code review that asks "who owns this value" rather than "which API is better".

Example

// service edge: RxJS in, signals out
@Injectable({ providedIn: 'root' })
export class Prices {
  private socket$ = this.ws.connect('/prices').pipe(
    retry({ delay: 1_000 }), throttleTime(100), shareReplay({ bufferSize: 1, refCount: true }));

  readonly latest = toSignal(this.socket$, { initialValue: {} as PriceMap });  // components see a signal
}

Follow-ups

  • What about existing NgRx? — Keep it; NgRx exposes signal selectors, so components can move to signals without touching the store.
  • Do you ban RxJS in components? — I ban manual subscribe() in components, not RxJS; the async pipe and toSignal cover the rest.
  • How do you handle the learning curve? — Codify five patterns (state, derived, async fetch, event stream, effect-at-the-edge) as examples in the repo; people copy examples, not documents.
  • What would change your rule? — A codebase whose domain genuinely is streams (trading, telemetry) tilts further towards RxJS; the boundary moves, the principle of one owner per value does not.

Common wrong answer

"RxJS is legacy, we should remove it." The Angular team has never said that, rxResource and the rxjs-interop package exist precisely to keep both, and a blanket ban produces hand-rolled debounce and retry code that is worse than the operators it replaced.

03Change detection, OnPush and zoneless

This is where Angular interviews separate people who can use the framework from people who can debug it. Every loop has at least one change-detection question, and since v21 made zoneless the default for new apps and v22 made OnPush the default strategy, the question has shifted from "what does OnPush do" to "what does your app do now that Zone.js is gone". At mid level, explain what marks a component dirty; at senior, explain what Zone.js patched and what stops working without it; at principal, plan a zoneless migration for an app you cannot pause.

screenerWhat triggers change detection in Angular — before and after zoneless?

Answer

Classically, Zone.js monkey-patched the browser's async APIs — addEventListener, setTimeout, Promise, XMLHttpRequest — and told Angular "something async finished" after every one of them, at which point Angular checked the whole component tree from the root. That is why an unrelated setInterval could re-render your entire app. In a zoneless app (stable since v20.2, the default for new apps in v21) there is no global notifier: Angular schedules a change-detection pass when something explicitly tells it state changed — a signal that a template read was written, an async pipe emitting, a host or template event listener firing, markForCheck(), or a deferred block resolving. The mental shift is from "check everything after any async work" to "refresh the views that depend on the thing that changed".

Example

// v21+ new apps: no zone.js in polyfills, and:
bootstrapApplication(App, { providers: [provideZonelessChangeDetection()] });

// Opt back into Zone.js (legacy apps, or a third-party lib that needs it):
bootstrapApplication(App, { providers: [provideZoneChangeDetection({ eventCoalescing: true })] });

Follow-ups

  • What does a pass actually do? — Walks dirty views, re-evaluates their bindings, compares with the previous value, and updates the DOM where they differ.
  • What is ApplicationRef.tick()? — The entry point that runs one synchronous change-detection pass over all attached views; Zone.js used to call it for you.
  • Is Zone.js removed from Angular? — No. It is still supported and still present in upgraded apps; new apps simply do not include it.

Common wrong answer

"Angular uses dirty checking like AngularJS did with $digest." Superficially similar, but AngularJS re-evaluated watchers until they stabilised, in any order; Angular checks each view exactly once per pass, top-down, and throws NG0100 if a binding changes after being checked. Confusing the two invites the NG0100 question next, and you will answer it wrong.

screenerWhat does OnPush do, and what changed in Angular 22?

Answer

OnPush tells Angular that a component's view only needs re-checking when something it can see changed: a reference change on an @Input, an event fired from its own template, an async pipe emitting, a signal it reads being written, or an explicit markForCheck(). Under the old default strategy every component was re-checked on every pass, regardless. In v22 the default flipped: components are OnPush unless you say otherwise, and the previous default was renamed ChangeDetectionStrategy.Eager and deprecated. Existing apps are not silently changed — ng update annotates components with Eager to preserve behaviour, so the migration is opt-in per component and you burn the annotations down over time. The practical implication for interviews: "we use OnPush everywhere" is no longer a differentiator, and "we still rely on Eager here, and here is why" is now the interesting answer.

Example

// v22: nothing to write — this is OnPush
@Component({ selector: 'app-row', template: `{{ row().label }}` })
export class RowCmp { row = input.required<Row>(); }

// legacy behaviour, added by ng update, deprecated:
@Component({ selector: 'app-legacy', changeDetection: ChangeDetectionStrategy.Eager, template: `...` })
export class Legacy {}

Follow-ups

  • Why deprecate Eager rather than remove it? — Because millions of components depend on mutation-based rendering; removal would break them, deprecation gives a signal plus a migration path.
  • Does OnPush skip children? — It skips the whole subtree unless a child is itself marked dirty; that is the source of both the performance win and the "why is my child stale" confusion.
  • How does a signal wake an OnPush component? — Reading a signal in a template registers that view as a consumer, so writing it marks precisely that view dirty.

Common wrong answer

"OnPush means the component only updates when inputs change." Incomplete in a way interviewers pounce on: template events, async pipes, signal reads and markForCheck() also mark it dirty — and an input that is mutated rather than replaced does not.

midAn OnPush component shows stale data after a service updates an array. Walk me through the diagnosis.

Answer

The service almost certainly mutated the array in place — push, splice, or assigning to an element — so the input's reference is unchanged and Angular has no reason to re-check the view. There are three good fixes, in preference order: make the state a signal so the read/write relationship is tracked and mutation is not how you update it; keep the value immutable and replace the reference; or, as a last resort in legacy code, inject ChangeDetectorRef and call markForCheck() after the mutation. The diagnostic path in a real app is: confirm the value in the service is correct, put a breakpoint or a console.count in the template expression to see whether the view is being checked at all, and if it is not, look at what is supposed to mark it dirty. In Angular DevTools the profiler shows the components checked in each pass, which answers the same question faster.

Example

// ❌ mutation: OnPush child never re-renders
add(item: Item) { this.items.push(item); }

// ✅ signals: the child's template read is the subscription
readonly items = signal<Item[]>([]);
add(item: Item) { this.items.update(list => [...list, item]); }

// legacy escape hatch
constructor(private cdr: ChangeDetectorRef) {}
add(item: Item) { this.items.push(item); this.cdr.markForCheck(); }

Follow-ups

  • markForCheck() vs detectChanges()? — markForCheck marks the path from this view to the root dirty for the next pass; detectChanges synchronously re-checks this view and its children now.
  • When is detach()/reattach() justified? — Very rarely: a high-frequency widget (a live chart) you check on your own schedule.
  • Would zoneless have changed this? — Yes: with a signal there is no stale case; with mutation, zoneless makes the bug appear sooner and more consistently, which is an argument for it.

Common wrong answer

"Call detectChanges() in the child." It papers over the bug, runs an extra synchronous pass, and will throw ExpressionChangedAfterItHasBeenChecked in dev if called at the wrong moment. Reaching for ChangeDetectorRef first, instead of asking why the view was not marked dirty, reads as cargo-culting.

midWhat causes NG0100 ExpressionChangedAfterItHasBeenCheckedError, and how do you fix it properly?

Answer

In development Angular runs a second verification pass after each change-detection cycle; if a binding produces a different value the second time, it throws NG0100, because that means the DOM you just produced was already out of date. The usual causes are a parent binding written to from a child's ngAfterViewInit or ngOnInit, a getter that returns a new object or array literal every call ([config]="{ a: 1 }"), or a service emitting synchronously during the checking phase. The proper fixes are structural: move the write earlier (ngOnInit of the owner, not the child's after-view hook), make the value a signal or a memoised computed, or hoist the object literal into a field so the reference is stable. The famous "fix" of wrapping the write in setTimeout or Promise.resolve().then() defers it into the next task, which silences the error without addressing the double-render.

Example

<!-- ❌ new object every check: throws NG0100 in dev, re-renders forever in prod -->
<app-widget [config]="{ mode: 'compact' }" />

<!-- ✅ stable reference -->
<app-widget [config]="widgetConfig" />      <!-- readonly widgetConfig = { mode: 'compact' } -->

Follow-ups

  • Why only in dev? — The verification pass is stripped in production builds, so the bug becomes a silent inconsistency instead of an error.
  • Does zoneless change this? — The error still exists; what changes is that fewer accidental passes hide the problem, so it surfaces earlier.
  • Is setTimeout ever the right fix? — Only when integrating a genuinely external system that reports state after render; even then afterNextRender is the honest API.

Common wrong answer

"It's a false positive from Angular's dev mode, we wrap it in setTimeout." Interviewers hear that as "I do not understand the unidirectional data flow rule"; the error is telling you a value changed after it was rendered, which is real in production too.

seniorWhat exactly is Zone.js patching, and what stops working when you remove it?

Answer

Zone.js patches the async surface of the browser — event listeners, timers, promises, XHR, MutationObserver, requestAnimationFrame — so it can maintain an execution context across async boundaries and notify Angular when the microtask queue drains. Remove it and three things stop happening automatically: change detection after arbitrary async callbacks (a setTimeout that mutates a plain field no longer re-renders), NgZone.onStable/isStable based logic (some SSR and testing utilities, plus third-party libraries that wait for stability), and zone-based test helpers such as fakeAsync/tick and waitForAsync for zone-driven flushing. The fix for the first is signals — anything the template reads should be a signal. The others are the actual migration work: audit third-party libraries for NgZone usage, and move tests to await fixture.whenStable() and Vitest's fake timers. Note the cost you also remove: about 13 KB of polyfill and a global patch layer that broke source maps and confused profiling.

Example

// zone-era pattern that silently stops updating the view without zone.js
setTimeout(() => { this.label = 'done'; }, 1000);          // ❌ plain field, no notification

// zoneless-safe
readonly label = signal('pending');
setTimeout(() => this.label.set('done'), 1000);            // ✅ signal write schedules CD

// still valid, and now unnecessary in most cases:
this.ngZone.runOutsideAngular(() => requestAnimationFrame(loop));

Follow-ups

  • What was runOutsideAngular for? — Escaping the zone for high-frequency work (animation loops, scroll handlers) so it did not trigger a global pass per frame; in a zoneless app the problem largely disappears.
  • How do you find zone dependencies? — grep for NgZone, onStable, fakeAsync, and run the app with the zoneless provider in a canary environment; the failures are visible, not silent, for anything the template renders.
  • What about provideZoneChangeDetection({ eventCoalescing: true })? — The intermediate step for zone apps: it coalesces multiple events into one pass and typically cuts CD count noticeably before you go zoneless.

Common wrong answer

"Zoneless just means better performance." The performance is a side effect; the substance is a different notification model, and it is a breaking change for any code that relied on implicit re-rendering after async work. A candidate who cannot name a single thing that breaks has not done the migration.

seniorAn app "feels slow" on a list page. How do you determine whether change detection is the cause?

Answer

Measure before theorising. Angular DevTools' profiler records change-detection cycles and shows, per pass, which components were checked and how long each took — that immediately distinguishes "too many passes" from "one very expensive component". A cheap first check in the console is ng.profiler.timeChangeDetection(), which reports the cost of a single pass. Then look at the shape of the problem: hundreds of tiny checks means the tree is being re-checked globally (Eager components, or Zone.js triggering on every event), while one long check means an expensive binding — a method call in a template, a pipe that is not pure, or a huge @for without effective tracking. Cross-check with the browser's own performance panel for layout and scripting split, because "slow" is often layout thrash from a component measuring the DOM, not change detection at all.

Example

<!-- ❌ runs on every check, for every row -->
@for (row of rows(); track row.id) { <td>{{ formatTotal(row) }}</td> }

<!-- ✅ derived once per change, memoised -->
@for (row of decoratedRows(); track row.id) { <td>{{ row.total }}</td> }

Follow-ups

  • Why are method calls in templates expensive? — They are re-evaluated on every check of that view and cannot be memoised by the framework; a pure pipe or a computed can.
  • What do you do about 10k rows? — Virtual scrolling (CDK), plus deriving the view model outside the template.
  • How do you stop the regression coming back? — Bundle and runtime budgets in CI, and a Lighthouse/RUM check on INP for the page in question.

Common wrong answer

"Add OnPush everywhere and it will be fast." Since v22 that is already the default, and it does nothing for the case where a single view is expensive. Optimisation without a profile is the thing senior interviewers screen against.

seniorHow do signals interact with OnPush internally — what actually gets marked dirty?

Answer

Each view is a consumer in the reactive graph. When a template expression reads a signal during a check, that view is registered as a dependent of that signal. Writing the signal marks the view dirty and, since Angular still walks the tree top-down, marks its ancestors as "has dirty descendant" so the pass can find it — this is why an OnPush parent does not block a signal-driven child from updating, which is the big behavioural difference from the input-reference model. Angular then schedules a change-detection pass (a microtask-level scheduler; multiple writes in the same tick coalesce into one pass). The important consequence for design: signal granularity is view granularity, so splitting a big component into smaller ones genuinely reduces the amount of re-checked template when a single field changes.

Example

// Parent is OnPush and never re-checked, yet this child updates when `tick` changes,
// because the child's own view is a consumer of the signal.
@Component({ selector: 'app-clock', template: `{{ tick() }}` })
export class Clock {
  readonly tick = inject(ClockService).tick;   // Signal<number>
}

Follow-ups

  • Do multiple writes cause multiple passes? — No; writes in the same synchronous block coalesce into one scheduled pass.
  • What about a signal read inside a computed used by the template? — Same thing transitively: the view depends on the computed, the computed on the signal.
  • Does this make markForCheck() obsolete? — For signal-driven state, yes; it survives for interop with non-signal sources.

Common wrong answer

"Signals re-render only the DOM node that changed, like fine-grained frameworks." Not yet — the unit of refresh is still the view (component template), not the individual binding. Claiming per-node updates is a detail interviewers who know the internals will pick up on immediately.

seniorWhat does async pipe do for change detection, and is it still the right default?

Answer

The async pipe subscribes to an Observable, calls markForCheck() on every emission, and unsubscribes when the view is destroyed — which is why it was the safe default in the OnPush + RxJS era, and why manual subscribe() in components has always been discouraged. It still works in a zoneless app, because it marks the view dirty explicitly rather than relying on Zone.js. What has changed is that for state you would rather have a signal: toSignal() gives you synchronous reads, no | async repetition when the same stream is used three times in a template, no *ngIf="x$ | async as x" dance, and it composes with computed. My default now is toSignal() at the boundary, with async pipe kept for one-off streams and in code that has not migrated.

Example

// legacy but valid
// <p>{{ (user$ | async)?.name }}</p>

// modern boundary conversion
readonly user = toSignal(this.userService.user$, { initialValue: null });
// <p>{{ user()?.name }}</p>

Follow-ups

  • What does toSignal do about subscriptions? — Subscribes in the injection context and unsubscribes on destroy; use { requireSync: true } for a stream you know emits synchronously (like a BehaviorSubject) to avoid an undefined initial value.
  • Multiple | async on the same stream? — Each creates its own subscription unless the stream is shared; a classic double-fetch bug that toSignal removes.
  • Errors? — toSignal rethrows the error on read; the async pipe throws in the template. Neither is a substitute for handling it in the stream.

Common wrong answer

"The async pipe doesn't work without Zone.js." It does — it calls markForCheck() itself. Getting this wrong suggests you believe every update path goes through Zone.js, which is precisely the model zoneless replaces.

principalPlan the zoneless migration for a 5-year-old app with 40 developers and a third-party charting library that uses NgZone.

Answer

I would treat it as a readiness programme, not a switch. Phase one is instrumentation and cheap wins while still on Zone.js: turn on provideZoneChangeDetection({ eventCoalescing: true }), record CD counts and INP as a baseline, and enable the CLI's zoneless-readiness lint so new code cannot add zone dependencies. Phase two is signal adoption where it matters: every value a template renders becomes a signal or comes through toSignal, and the CLI migrations (signal inputs, queries, inject) run area by area. Phase three is the audit: grep for NgZone, onStable, fakeAsync, whenStable, and for the charting library specifically, wrap it in one adapter component so its zone dependency has exactly one home — if it needs stability notifications, that adapter can keep a local NgZone shim or the library can be replaced there and only there. Phase four flips the provider behind an environment flag, ships to an internal canary and then a small traffic percentage, watching error rates and INP. Rollback is a one-line provider change, which is why the flag is worth the effort.

Example

// one adapter owns the library's zone assumptions
@Component({ selector: 'app-chart', template: `<div #host></div>` })
export class ChartAdapter {
  private host = viewChild.required<ElementRef>('host');
  data = input.required<Series[]>();
  constructor() {
    afterNextRender(() => { const c = legacyChart(this.host().nativeElement);
      effect(() => c.setData(this.data())); });
  }
}

Follow-ups

  • What is the riskiest class of bug? — Views that stopped updating rather than views that error: silent staleness. Mitigate with e2e coverage on the top user journeys, not unit tests.
  • How do you sequence with feature work? — Readiness lint plus migrations are background work; the provider flip is a single dated event with an owner and a rollback plan.
  • What do you tell the business? — Two numbers: interaction latency (INP) and bundle size, plus the fact that new Angular defaults assume zoneless, so staying is a growing tax, not a stable state.
  • When would you not do it? — An app in maintenance with no roadmap and no performance complaints; there the right answer is to stay on a supported version and spend the effort elsewhere.

Common wrong answer

"Add provideZonelessChangeDetection() and fix what breaks." On a large app that produces a long tail of views that quietly stop updating in production, discovered by users. The interviewer is testing for staged rollout with a rollback, not for knowledge of the provider name.

04Dependency injection and injectors

DI is the part of Angular that has changed least in shape and most in syntax, so it is a reliable interview filter: everyone can say "Angular has DI", but few can explain the two injector trees or scope a service to a route. Expect a screener on providedIn: 'root', a mid-level question on inject(), and at senior level a scoping or lifecycle question — where a service instance lives, when it is destroyed, and how you avoid one shared singleton accumulating state for the life of the tab.

screenerHow does Angular's DI work, and what does providedIn: 'root' actually do?

Answer

Angular resolves a dependency by walking a chain of injectors looking for a provider keyed by a token — usually the class itself, sometimes an InjectionToken. providedIn: 'root' registers the service with the root environment injector, which gives you a single instance for the application and, importantly, makes it tree-shakable: because the provider is declared on the service rather than in a module's providers array, a service nobody injects is dropped from the bundle. That was the whole reason the syntax replaced listing services in NgModule.providers. Angular 22 adds an ergonomic shorthand, the @Service() decorator, which is root-provided by default (@Service({ autoProvided: false }) when you want to provide it manually), while @Injectable remains fully supported.

Example

@Injectable({ providedIn: 'root' })
export class Telemetry { track(e: string) { /* ... */ } }

// v22 shorthand — same effect, less ceremony
@Service()
export class Telemetry2 { track(e: string) { /* ... */ } }

// consumer
export class Checkout { private telemetry = inject(Telemetry); }

Follow-ups

  • What are the other providedIn values? — 'platform' (shared across multiple apps on a page) and 'any' (one instance per lazy-loaded injector); both are rare and usually a smell if you reach for them casually.
  • When is a root service destroyed? — When the application is destroyed; ngOnDestroy on a root service effectively only runs in tests and on app teardown.
  • How do you provide a value, not a class? — InjectionToken plus { provide: TOKEN, useValue: ... }; generic tokens keep it type-safe.

Common wrong answer

"providedIn: 'root' means it is a singleton, full stop." It is a singleton in the root environment injector; a component or route that also provides the class gets its own instance, and lazy-loaded route injectors change the picture again. That nuance is the entire next question.

midConstructor injection or inject() — which do you use, and why did inject() win?

Answer

inject() (stable since v14) is the current style guide recommendation, and the CLI ships a migration for it. It wins for concrete reasons, not fashion: it works in field initialisers, so dependencies are available before the constructor body and can be used to build other fields; it composes into reusable functions — a injectPageParams() helper is just a function that calls inject() — which is how functional guards, interceptors and resolvers are written; it removes the need for @Inject(), @Optional(), @Self() decorators in favour of an options object; and it plays better with inheritance, since a subclass no longer has to repeat the parent's constructor parameters. The one rule to state: it must be called in an injection context — field initialiser, constructor, or a factory — otherwise you get NG0203.

Example

export class Orders {
  private http = inject(HttpClient);
  private route = inject(ActivatedRoute);
  private logger = inject(Logger, { optional: true });      // replaces @Optional()

  readonly id = toSignal(this.route.paramMap.pipe(map(p => p.get('id'))));
}

// composable: a reusable injectable function
export function injectFeatureFlag(name: string) {
  const flags = inject(FeatureFlags);
  return computed(() => flags.all()[name] ?? false);
}

Follow-ups

  • Is constructor injection deprecated? — No, and it is still what most existing code looks like; the migration is ng generate @angular/core:inject-migration.
  • What is NG0203? — "inject() must be called from an injection context" — you called it in a lifecycle hook, a callback or a plain function.
  • How do you inject outside a context deliberately? — Capture an Injector and use runInInjectionContext(injector, () => ...).

Common wrong answer

"They're identical, it's a style preference." They differ in where they can be used and in composability; a candidate who says they are identical usually has not written a functional guard or interceptor, which is now the only supported style.

midExplain the two injector hierarchies and what happens on NG0201.

Answer

Angular has two parallel trees. The environment injector hierarchy holds application-wide providers: the root injector from bootstrapApplication, plus a child injector per lazy-loaded route that declares providers. The element injector hierarchy follows the component tree: a component's providers array creates an injector on that element, visible to it and its descendants (including projected content, which surprises people). Resolution walks the element injectors from the requesting element up to the root element, then hops to the environment chain. NG0201 — "No provider for X" — means the walk ended without a match: the service has no providedIn, it is provided only in a sibling branch, or you are in a lazy route whose provider you assumed was global. The modifiers control the walk: { self: true } stops at the current injector, { skipSelf: true } starts at the parent, { host: true } stops at the host component boundary.

Example

// one FilterState per grid instance, shared with its children
@Component({
  selector: 'app-grid',
  providers: [FilterState],
  template: `<app-grid-toolbar /><app-grid-body />`,
})
export class Grid {}

// child gets the grid's instance, not the root one
export class GridToolbar { private filters = inject(FilterState); }

Follow-ups

  • When is a component-provided service destroyed? — With the component instance, which is exactly why it is the right scope for per-instance state.
  • What does route-level providers give you? — An environment injector for that route subtree, destroyed when you navigate away — v21.1 added withExperimentalAutoCleanupInjectors() to tighten that teardown.
  • Why does projected content see the outer injector? — Because the element injector follows the declaration tree, not the rendering position.

Common wrong answer

"There is one injector tree and it follows the component hierarchy." Missing the environment/element split makes lazy-route provider bugs unexplainable, and it is the question that most often separates a mid answer from a senior one.

midWhat are InjectionToken and multi-providers for?

Answer

An InjectionToken gives you a type-safe key for something that has no class to use as a token — configuration objects, strings, feature flags, functions. With a factory it also stays tree-shakable. multi: true lets many providers contribute to one token and injects the collected array; that is how Angular itself models HTTP interceptors and app initializers, and it is the extension point you want when a feature needs to register plugins without the core knowing about them. The modern idiom is to wrap both behind a provideX() function so consumers never see the token, which is exactly what provideRouter, provideHttpClient and friends do.

Example

export const APP_CONFIG = new InjectionToken<AppConfig>('app.config', {
  providedIn: 'root', factory: () => ({ apiUrl: '/api', pageSize: 25 }),
});

export const VALIDATOR = new InjectionToken<Rule[]>('rules');

export function provideRule(rule: Rule): Provider {
  return { provide: VALIDATOR, useValue: rule, multi: true };
}
// consumer: inject(VALIDATOR) === [rule1, rule2, ...]

Follow-ups

  • useFactory vs useValue? — Factory when construction needs other dependencies or must be lazy; value for constants.
  • What replaced APP_INITIALIZER? — provideAppInitializer(() => ...) (v19), a function-based form of the same multi-provider.
  • Why is a string token bad? — No type safety and collisions across libraries; InjectionToken is identity-based.

Common wrong answer

"You can just inject an interface." TypeScript interfaces vanish at runtime, so there is no token — this is the single most common DI mistake for people coming from C# or Java.

seniorA service holds state for one feature. Root, route or component scope — how do you choose?

Answer

Choose by lifetime and by how many instances the state should have. Root scope is right for genuinely global, stateless or cache-like services (HTTP wrappers, auth, telemetry); its risk is that stateful root services leak between users of the same tab — the "why does the previous customer's filter still apply" class of bug. Route scope, via a route's providers array, gives one instance per activation of that route subtree, destroyed on navigation away, which is the right home for feature state that should reset when you leave the feature. Component scope gives one instance per component instance, which is what you want for anything that must be independent per widget on the page. The default I recommend to teams: global services are stateless; anything holding user-visible state is route- or component-scoped, so its lifetime is visible in the code rather than in a mental model.

Example

export const routes: Routes = [{
  path: 'orders',
  providers: [OrdersStore, provideOrdersFeature()],   // fresh store per visit
  loadChildren: () => import('./orders/routes').then(m => m.ORDER_ROUTES),
}];

Follow-ups

  • How do you reset a root-scoped store on logout? — Explicitly: a reset() called by the auth flow. If you find yourself writing many of those, the scope is wrong.
  • What breaks if two routes share a scoped service? — Each activation gets its own injector, so cross-route state must live one level up — deliberately, not accidentally.
  • Any v22 change here? — injectAsync() lets a route-scoped service itself be lazily loaded, so a heavy feature service is not in the initial chunk.

Common wrong answer

"Always providedIn: 'root', it's simpler." It is simpler until you have a state leak across navigations or a service that must be per-instance; then it is a refactor across the feature. Interviewers ask this specifically to hear you reason about lifetime.

seniorWhat is injectAsync() (v22) and when would you use it?

Answer

injectAsync() lazily injects a dependency behind a dynamic import, returning a promise for the instance, so a heavy service — a PDF exporter, a charting engine wrapper, a rules engine — does not sit in the chunk that loads with the route. It takes a prefetch option with helpers such as onIdle({ timeout }), so you can warm the chunk during idle time rather than at the moment of the click. It is the DI-level counterpart to what @defer does for templates, and it closes a real gap: previously you could lazily load a component but its injected services still came along eagerly. Use it for genuinely optional, genuinely heavy capabilities; using it for a 2 KB service just adds a promise to your call sites.

Example

export class ReportPage {
  private exporter = injectAsync(
    () => import('./report-exporter').then(m => m.ReportExporter),
    { prefetch: onIdle({ timeout: 2_000 }) },
  );

  async export() { (await this.exporter()).toPdf(this.rows()); }
}

Follow-ups

  • What did people do before? — A manual import() inside the method plus a cached instance, or pushing the whole feature behind a lazy route.
  • What is the risk? — Every call site becomes async; do not use it for something on a synchronous rendering path.
  • How do you verify the win? — Chunk analysis before/after; if the symbol still appears in the parent chunk, something imports it statically.

Common wrong answer

"It makes DI faster." It changes when code is downloaded, not how fast injection is. Framing it as a speed-up rather than a bundle-boundary tool suggests you have not measured a chunk graph.

seniorYou are publishing an internal library. How do you expose its configuration — forRoot() or something else?

Answer

A provideX() function, not forRoot(). The modern shape is a function returning EnvironmentProviders, with optional "features" as additional arguments — exactly how provideHttpClient(withInterceptors([...])) and provideRouter(routes, withComponentInputBinding()) are built. It composes with bootstrapApplication, works at route level for per-feature configuration, is tree-shakable because unused features are never referenced, and gives you type-safe opt-in instead of a config object with fifteen optional fields. forRoot() was the NgModule-era answer to the same problem and only existed because providers had to live on a module; keep it only as a thin wrapper if you must support NgModule consumers.

Example

export function provideMaps(config: MapsConfig, ...features: MapsFeature[]): EnvironmentProviders {
  return makeEnvironmentProviders([
    { provide: MAPS_CONFIG, useValue: config },
    MapsService,
    ...features.flatMap(f => f.providers),
  ]);
}
export function withOfflineTiles(): MapsFeature { /* ... */ }

// consumer
bootstrapApplication(App, { providers: [provideMaps({ key }, withOfflineTiles())] });

Follow-ups

  • Why makeEnvironmentProviders? — It produces an opaque EnvironmentProviders so consumers cannot accidentally put environment-level providers on a component.
  • How do you support both worlds? — Ship the function; add a tiny NgModule with forRoot() delegating to it for legacy consumers.
  • How do libraries stay tree-shakable? — Feature functions plus providedIn factories; avoid barrel files that pull the whole library into one import.

Common wrong answer

"Export an NgModule with forRoot(), that's the Angular way." It was, until v15. Publishing that today marks the library — and the author — as a version behind, and it forces standalone consumers to import a module for no reason.

principalHow do you keep DI from becoming a hidden global-state graph in a large app?

Answer

By treating injection as an architectural boundary rather than a convenience. Three rules do most of the work. First, ownership: every piece of state has exactly one owner service, at the narrowest scope that fits — global services are stateless, stateful ones are route- or component-scoped. Second, direction: features depend on shared kernel services, never on each other; a feature that needs another feature's data gets it through a router boundary, a shared contract token, or an event, and this is enforceable with lint rules (Nx tags, or ESLint import restrictions). Third, visibility: prefer explicit provideX() composition at the composition root over providedIn: 'root' for anything domain-specific, so that reading main.ts and the route config tells you what the app is made of. The failure mode I am guarding against is the 3000-line DataService that everything injects — which no amount of testing discipline fixes, because the coupling is the problem.

Example

// contract in a shared kernel, implementations swapped per app/shell
export const PAYMENTS = new InjectionToken<PaymentsApi>('payments');

// feature never imports the concrete class
export class CheckoutFlow { private payments = inject(PAYMENTS); }

// composition root decides
providers: [{ provide: PAYMENTS, useClass: StripePayments }]

Follow-ups

  • How do you enforce it? — Module-boundary lint rules in CI, plus a dependency graph check in review; conventions without enforcement decay within two quarters.
  • Does this hurt testability? — It improves it: a token boundary is trivially faked, and route-scoped state means tests do not leak between cases.
  • Where do you allow exceptions? — Cross-cutting infrastructure (auth, telemetry, config), which is global by nature and should be small and stateless.
  • What metric tells you it is going wrong? — Fan-in on a single service, and the number of files touched by an average feature change.

Common wrong answer

"We use NgRx, so state isn't in services." A store is one owner, not an architecture: a single global store with 200 unrelated slices has the same coupling problem in a different file layout. Interviewers want the boundary reasoning, not a library name.

05RxJS and async interop

RxJS questions have not disappeared, they have changed register: instead of "explain switchMap", the modern loop asks "what still belongs in RxJS now that signals exist, and how do you convert at the boundary". Fluency in the four flattening operators is still table stakes — a wrong choice is a production race condition — and leaks, shareReplay and error handling remain reliable senior questions. At principal level you are asked to set the convention for a codebase with a decade of pipelines in it.

screenerIn a signals-first Angular app, what is RxJS still for?

Answer

Time and coordination. Signals model "what is the value now"; Observables model "a sequence of things happening over time", and they carry the operators for anything involving when: debounce and throttle, retry with backoff, timeouts, combining and racing streams, cancelling in-flight work, buffering, and long-lived push sources such as websockets, server-sent events, cross-tab broadcast and browser event streams. They also remain the interface of large parts of the framework and ecosystem — the router's events, HttpClient, NgRx effects. The idiomatic layering today is: RxJS at the edges and in services where the semantics are genuinely temporal, converted to signals with toSignal() at the component boundary so templates read synchronous values.

Example

private readonly online$ = merge(
  fromEvent(window, 'online').pipe(map(() => true)),
  fromEvent(window, 'offline').pipe(map(() => false)),
).pipe(startWith(navigator.onLine));

readonly online = toSignal(this.online$, { requireSync: true });

Follow-ups

  • Is RxJS being removed from Angular? — No. It is no longer required for basic state, and output() dropped EventEmitter, but HttpClient, the router and rxResource all keep it first-class.
  • What about bundle size? — Operators are tree-shaken individually; the cost is real but small if you import from rxjs and avoid pulling in the whole library through a barrel.
  • Which direction do you convert? — toSignal() for consumption; toObservable() when a signal must feed an operator pipeline.

Common wrong answer

"Signals replaced RxJS, we removed it." Teams that say this usually re-implement debounceTime and retry by hand, badly. The framework's own rxResource and rxjs-interop package exist precisely because both models are wanted.

midswitchMap, mergeMap, concatMap, exhaustMap — give me a real case for each.

Answer

switchMap cancels the previous inner subscription when a new value arrives: type-ahead search, or reloading a detail view when the route id changes — anything where only the latest matters. mergeMap runs everything concurrently with no ordering guarantee: independent fire-and-forget work such as sending analytics events. concatMap queues, preserving order and running one at a time: sequential writes where order is the correctness property, like applying edits to a document. exhaustMap ignores new values while one is in flight: the double-click-submit guard on a form. The reason interviewers love this question is that each wrong choice has a specific production symptom — stale results overwriting fresh ones (mergeMap where switchMap belonged), duplicate orders (mergeMap instead of exhaustMap), or a queue that never drains (concatMap on a firehose).

Example

// only the latest search matters
search$ = this.query$.pipe(debounceTime(300), switchMap(q => this.api.search(q)));

// one submit at a time; extra clicks ignored
submit$ = this.click$.pipe(exhaustMap(() => this.api.createOrder(this.form.value)));

// order matters, run sequentially
save$ = this.edits$.pipe(concatMap(edit => this.api.applyEdit(edit)));

Follow-ups

  • What does cancellation mean for an HTTP request? — Unsubscribing aborts the underlying fetch/XHR, so the browser cancels it and the server may still have processed it — relevant for non-idempotent calls.
  • Which does resource() use? — switch semantics: a new params value aborts the in-flight load.
  • What if you need bounded concurrency? — mergeMap(fn, 4), the second argument is the concurrency limit.

Common wrong answer

"I use mergeMap because it doesn't cancel anything, so nothing is lost." Nothing is lost except correctness: responses arrive out of order and the older one can win. This is the most common cause of "the list shows the previous search" bugs.

midHow do you avoid subscription leaks today?

Answer

Preferably by not subscribing manually at all: the async pipe and toSignal() both tear down with the view. When you do need an imperative subscription — a side effect, not a rendered value — use takeUntilDestroyed() from @angular/core/rxjs-interop (v16), which ties the subscription to the current injection context's DestroyRef; outside a field initialiser, pass the DestroyRef explicitly. That replaced the old takeUntil(this.destroy$) boilerplate with its Subject and ngOnDestroy. Two rules I would put in a review checklist: never call .subscribe() in a component without a teardown mechanism visible in the same expression, and remember that takeUntilDestroyed must be the last operator before subscribe or later operators can resurrect emissions.

Example

export class Live {
  private destroyRef = inject(DestroyRef);

  ngOnInit() {
    this.socket.messages$
      .pipe(takeUntilDestroyed(this.destroyRef))   // explicit ref: not a field initialiser
      .subscribe(m => this.handle(m));
  }
}

Follow-ups

  • Do HTTP subscriptions leak? — They complete after one emission, so they self-unsubscribe; the leak risk is with long-lived sources and with shareReplay holding a reference.
  • What did people do before? — A destroy$ = new Subject() field plus ngOnDestroy; you will still see it everywhere.
  • How do you detect leaks? — Heap snapshots after repeated navigation, and a rising count of detached views/components in DevTools.

Common wrong answer

"Angular unsubscribes automatically when the component is destroyed." It does for the async pipe, toSignal, and its own APIs — not for a subscription you created. Believing otherwise is how apps end up with dozens of live websocket handlers after twenty navigations.

midWhat are the gotchas of toSignal() and toObservable()?

Answer

toSignal() subscribes immediately and unsubscribes on destroy, so it must be created in an injection context. Its initial value is undefined unless you pass initialValue, or requireSync: true for a source you know emits synchronously (a BehaviorSubject or a startWith pipeline) — get that wrong and you either have a spurious undefined in the type, or a runtime error. Errors are rethrown when the signal is read, which surprises people who expect a silent undefined. toObservable() goes the other way, using an internal effect, so it emits asynchronously on the next change-detection tick rather than synchronously on write, and intermediate values written in the same tick are coalesced — that matters when you are testing or when you assumed every write produces an emission.

Example

readonly user = toSignal(this.user$, { initialValue: null });        // no undefined in the type
readonly cfg  = toSignal(this.cfgSubject$, { requireSync: true });   // BehaviorSubject: sync

// signal -> stream, then back
readonly results = toSignal(
  toObservable(this.query).pipe(debounceTime(300), switchMap(q => this.api.search(q))),
  { initialValue: [] as Row[] });

Follow-ups

  • Why does toObservable not emit synchronously? — It is effect-based, and effects are scheduled; treat it as "eventually consistent with the signal".
  • Does toSignal replay for late readers? — It holds the latest value like a BehaviorSubject; the underlying stream is subscribed once.
  • What if the observable completes? — The signal keeps the last value; completion is not observable through the signal API.

Common wrong answer

"toObservable(sig) emits every value I set." Two writes in the same tick produce one emission. Tests written on the opposite assumption fail intermittently, which is exactly the kind of detail a senior interviewer probes.

seniorWhen is shareReplay right, and how does it leak?

Answer

shareReplay multicasts a source and replays the last N values to late subscribers — the standard way to make an expensive HTTP call or a websocket shared rather than repeated per subscriber. The leak comes from the default configuration: shareReplay(1) without refCount: true keeps the source subscribed forever even after every consumer has unsubscribed, which for an interval, a websocket, or a stream holding a large payload means the subscription and the buffered value live for the life of the app. Use shareReplay({ bufferSize: 1, refCount: true }) for anything long-lived; the non-refCount form is only appropriate for a deliberately cached, application-lifetime value such as bootstrap configuration. In a signals world, a lot of what people used shareReplay for is better expressed as a signal or a resource in a service.

Example

// ❌ keeps the websocket open after the last subscriber leaves
prices$ = this.ws.connect().pipe(shareReplay(1));

// ✅ tears down when nobody is listening, replays the last price to newcomers
prices$ = this.ws.connect().pipe(shareReplay({ bufferSize: 1, refCount: true }));

Follow-ups

  • Difference from share()? — share() multicasts without replay; a late subscriber sees only future values.
  • Why does a cached HTTP call still fire twice? — Because HttpClient observables are cold: each subscription is a new request unless you multicast.
  • Signal alternative? — A service-level signal or resource holding the value, which has no subscription semantics to get wrong.

Common wrong answer

"shareReplay(1) is the caching operator, just add it." It is also the most common memory leak in Angular codebases; naming refCount unprompted is what distinguishes someone who has debugged it from someone who copied it from Stack Overflow.

seniorWhere do you put catchError, and how do you implement retry with backoff?

Answer

Placement determines whether the outer stream survives. catchError inside the inner pipeline of a switchMap keeps the outer stream alive — one failed search does not kill the search box — whereas catchError at the end of the outer pipe swallows the error and completes the whole stream, which is why a page stops updating after the first failure. For retries, retry({ count, delay }) with a delay function gives exponential backoff and lets you decide per error whether to retry at all: retry idempotent GETs on 5xx and network errors, never on 4xx, and never blindly on POSTs. Add a jitter term so a thousand clients do not retry in lockstep after an outage, and give the whole thing an upper bound so the UI can show a real error instead of spinning forever.

Example

this.query$.pipe(
  switchMap(q => this.api.search(q).pipe(
    retry({ count: 3, delay: (err, n) =>
      err.status >= 500 ? timer(2 ** n * 200 + Math.random() * 100) : throwError(() => err) }),
    catchError(err => { this.error.set(toMessage(err)); return of([] as Row[]); }),  // inner!
  )),
).subscribe(rows => this.rows.set(rows));

Follow-ups

  • What is the equivalent with a resource? — Handle it in the loader (or an interceptor) and surface it through resource.error(); the resource itself does not retry for you.
  • Where do cross-cutting retries belong? — An HTTP interceptor, so policy is one place and not sprinkled through features.
  • Why not retry POSTs? — They are usually not idempotent; retry only with an idempotency key the server honours.

Common wrong answer

"Put catchError at the end of the pipe so nothing crashes." That is the bug: the outer stream completes and the component silently stops reacting to any further input. The interviewer is checking whether you know inner versus outer placement.

seniorWhy is the same HttpClient call firing twice, and what does "cold" mean here?

Answer

HttpClient returns a cold observable: the request is not sent until something subscribes, and every subscription sends its own request. So two | async pipes over the same observable produce two network calls, and so does subscribing in both a component and a resolver. The fixes are to multicast (shareReplay({ bufferSize: 1, refCount: true })), to subscribe once and store the result — a signal, a resource, or a service-level cache — or to restructure so there is a single consumer. Coldness is also a feature: it is what makes retry and cancellation meaningful, because re-subscribing genuinely re-issues the request. In 2026 the cleanest answer for read paths is usually httpResource(), which owns the single fetch and exposes it as signals, so there is no subscription count to reason about.

Example

<!-- ❌ two subscriptions, two GETs -->
<h1>{{ (user$ | async)?.name }}</h1>
<img [src]="(user$ | async)?.avatar">

<!-- ✅ one -->
@if (user(); as u) { <h1>{{ u.name }}</h1><img [src]="u.avatar"> }

Follow-ups

  • Does the browser dedupe them? — Not reliably; HTTP caching may, but you cannot design on that.
  • What about SSR? — Transfer state (provideClientHydration(withHttpTransferCacheOptions(...)), and httpResource integrates with it in v22) prevents the client repeating the server's fetch.
  • Hot equivalents? — Subjects, fromEvent, websockets: they emit regardless of subscribers.

Common wrong answer

"Observables are like promises, so it runs once." Promises are eager and single-shot; cold observables re-execute per subscriber. This misunderstanding produces duplicate POSTs, which is a considerably more expensive version of the same bug.

principalYour codebase has 400 RxJS pipelines written over eight years. What is your convention going forward, and do you rewrite?

Answer

I would not rewrite working pipelines: they are tested, they encode real edge cases, and a mechanical translation to signals buys nothing while risking behaviour changes. The policy I would set is directional — new code follows the boundary (signals for state, RxJS for time and coordination), and existing pipelines are converted only when they are being changed anyway, or when they are the source of a class of bug we keep paying for (leaked subscriptions, shareReplay without refCount, mergeMap where switchMap belonged). What I would invest in immediately is the boundary layer: services expose signals or resources, components stop calling subscribe(), and a lint rule enforces it. That gets most of the benefit — no leaks, synchronous template reads, OnPush/zoneless correctness — without touching the pipelines themselves, and it means the eventual conversions are local rather than architectural.

Example

// service keeps its battle-tested pipeline, exposes a signal at the edge
@Injectable({ providedIn: 'root' })
export class Positions {
  private stream$ = this.ws.connect().pipe(
    bufferTime(50), filter(b => b.length > 0), scan(reduceBatch, initial),
    shareReplay({ bufferSize: 1, refCount: true }));

  readonly current = toSignal(this.stream$, { initialValue: initial });
}

Follow-ups

  • How do you handle NgRx in this picture? — Keep it; expose selectors as signals so components look identical whether state comes from a store or a service.
  • What would make you rewrite sooner? — A measured defect cluster, or an RxJS major upgrade forcing changes anyway.
  • How do you upskill 40 people? — Five canonical examples in the repo, a review checklist, and pairing on the first conversion in each area; documents alone do not change habits.
  • How do you know the policy worked? — Fewer subscription-leak bugs, and new features shipping without subscribe() in components — both are countable in CI and in review.

Common wrong answer

"We'd convert everything to signals in a dedicated quarter." A quarter spent on a no-user-visible-change rewrite is the kind of proposal that ends principal interviews; the expected answer names a boundary, a lint rule, and an opportunistic conversion policy.

06Forms: signal, reactive and template-driven

Forms are the most common "real work" question in an Angular loop, because every enterprise app is mostly forms. The landscape changed in v22: Signal Forms went stable, so there are now three supported approaches and the interesting question is which you would pick and why. At mid level you must be fluent in typed reactive forms and custom validators; at senior level you need ControlValueAccessor, dynamic schema-driven forms, and the performance behaviour of a 200-field form; at principal, whether and how you would migrate an existing forms codebase at all.

screenerTemplate-driven, reactive, or Signal Forms — which do you use in a new app, and why?

Answer

For a new app on v22 I would default to Signal Forms, which went stable in v22 after being experimental in v21: form state is signals, the model is your own data object, validation is a schema function, and it composes with everything else signal-based including zoneless change detection. Reactive forms remain fully supported and are the right answer for existing codebases and for teams whose component library is built on ControlValueAccessor — they are typed since v14 and are not going anywhere. Template-driven forms are for genuinely trivial cases — a search box, a settings toggle — where ngModel is less ceremony than anything else; they get criticised for being hard to test and validate, which is fair beyond about five fields. The honest framing in an interview: three supported models, one recommendation for greenfield, and no urgency to rewrite what works.

Example

// Signal Forms (v22 stable)
readonly model = signal({ email: '', password: '' });
readonly loginForm = form(this.model, (f) => {
  required(f.email, { message: 'Email is required' });
  email(f.email);
  required(f.password);
});

// Reactive (v14+ typed) — still entirely valid
readonly rf = new FormGroup({
  email: new FormControl('', { nonNullable: true, validators: [Validators.required, Validators.email] }),
});

Follow-ups

  • Are reactive forms deprecated? — No. Signal Forms are an addition, with an official interop path (compatForm(), SignalFormControl) rather than a replacement schedule.
  • What makes template-driven hard to test? — The state lives in directives created by the template, so unit tests need a rendered fixture and a tick before values settle.
  • Which one for a design system? — Whichever your controls implement; CVA-based libraries are reactive-forms shaped, and v22 provides the compat layer so signal forms can drive them.

Common wrong answer

"Signal Forms replace reactive forms, we should migrate everything." Nothing in the release says that, the team shipped an explicit interop layer, and proposing a mass rewrite of the most business-critical code in an app is the answer that costs you the senior-level credit.

midWalk me through the Signal Forms API: form(), fields, validation and submission.

Answer

form(model, schema) takes a writable signal holding your data and a schema function, and returns a FieldTree — a structure mirroring the model where every property is a field with its own state signals (value, valid, touched, errors). You bind a field in the template with the Control directive ([control]="f.email"), so there is no separate form-control object to keep in sync with your model — the model is the state. Validation is declarative inside the schema: built-ins such as required(), email(), min(), custom predicates, and validateStandardSchema() to plug in Zod or Valibot. Conditional behaviour uses disabled(), readonly() and hidden() with a when predicate, and submission goes through submit(), which coordinates validation, an async action, and server-returned errors mapped back onto fields.

Example

readonly model = signal({ name: '', country: 'DE', vatId: '' });

readonly f = form(this.model, (path) => {
  required(path.name);
  disabled(path.vatId, { when: ({ value }) => value().country !== 'DE' });
  validateStandardSchema(path, VatSchema);            // Zod / Valibot
});

async save() {
  await submit(this.f, {
    action: async (form) => this.api.save(form().value()),   // server errors map back to fields
  });
}

Follow-ups

  • Where does the value live? — In your model signal; the field tree is a view over it, which is why patchValue-style plumbing disappears.
  • How do CSS state classes work? — Configured with provideSignalFormsConfig({ classes: ... }) (v21.2), with an NG_STATUS_CLASSES compat import to keep the legacy ng-invalid/ng-touched names.
  • Async validation? — Supported in the schema, and the submit API distinguishes client-side invalid from server-rejected via onInvalid and ignoreValidators.
  • Arrays? — The field tree follows the model, so an array of items is an array of field trees; no FormArray bookkeeping.

Common wrong answer

"It's ngModel with signals." The template-driven feel is deliberate, but validation is a typed schema, state is a signal tree you can derive from, and submission is a first-class API — describing it as two-way binding misses everything an interviewer wants to hear.

midIn reactive forms, what does "typed forms" mean, and what are the traps with FormControl nullability?

Answer

Since v14 reactive forms are generically typed: FormGroup infers a value type from its controls, and form.value is a typed partial while getRawValue() gives the complete object including disabled controls. The trap is nullability: a FormControl('') is FormControl<string | null> because reset() sets it back to null. Pass { nonNullable: true } (or use NonNullableFormBuilder) and reset returns to the initial value instead, giving you FormControl<string>. The second trap is that form.value excludes disabled controls, so a "save" that reads value silently drops fields you disabled for UX reasons — a bug that reaches production regularly. Untyped forms still exist as UntypedFormGroup, which is what the v14 migration inserted; leaving those in place forever is how a codebase keeps the old behaviour by accident.

Example

private fb = inject(NonNullableFormBuilder);

readonly form = this.fb.group({
  email: this.fb.control('', [Validators.required, Validators.email]),
  plan: this.fb.control<'free' | 'pro'>('free'),
});

save() {
  const payload = this.form.getRawValue();   // includes disabled controls; typed, non-null
}

Follow-ups

  • setValue vs patchValue? — setValue requires every control and throws otherwise (safer); patchValue silently ignores unknown keys, which hides typos.
  • What is updateOn? — 'change' | 'blur' | 'submit', set per control or per group; 'blur' is the standard fix for validation firing on every keystroke.
  • How do you type a FormArray? — FormArray<FormControl<string>>, or a FormArray of typed groups; the inference works but the declarations get verbose.

Common wrong answer

"form.value gives me the form's data." Not for disabled controls, and not with the nullability you expect. This is the single most common reactive-forms bug and interviewers ask it precisely because it is easy to get wrong after years of use.

midWrite a cross-field validator and an async uniqueness validator. Where do they attach?

Answer

A cross-field rule attaches to the group, not the control, because it needs both values: a function taking AbstractControl and returning ValidationErrors | null. An async rule — "is this email already taken" — is an AsyncValidatorFn returning an Observable or Promise; attach it as the third argument of the control, and pair it with updateOn: 'blur' so you are not calling the API on every keystroke. In Signal Forms both are expressed in the schema, with the async form using the resource machinery, so cancellation of superseded requests is handled for you. The design point worth stating: put the error on the field the user must fix, not on the group, or your template needs a special case to display it.

Example

const passwordsMatch: ValidatorFn = (g) =>
  g.get('password')!.value === g.get('confirm')!.value ? null : { mismatch: true };

const uniqueEmail = (api: Api): AsyncValidatorFn => (c) =>
  timer(300).pipe(switchMap(() => api.emailTaken(c.value)),
                  map(taken => taken ? { taken: true } : null), first());

form = new FormGroup({
  email: new FormControl('', { nonNullable: true, updateOn: 'blur',
    validators: [Validators.required], asyncValidators: [uniqueEmail(this.api)] }),
  password: new FormControl(''), confirm: new FormControl(''),
}, { validators: [passwordsMatch] });

Follow-ups

  • What is the control's status during async validation? — PENDING; a submit button gated only on invalid will happily submit during that window.
  • How do you avoid hammering the API? — updateOn: 'blur', a leading timer/debounce inside the validator, and first() so the observable completes.
  • Server-side errors? — Map them onto controls with setErrors after the response; in Signal Forms, submit() does that mapping for you.

Common wrong answer

"I'd subscribe to valueChanges and call the API from there." That bypasses form status entirely: the form reports valid while the check is in flight, the subscription leaks unless you manage it, and rapid typing produces out-of-order responses.

seniorWhen do you implement ControlValueAccessor, and what does it cost?

Answer

You implement CVA when a custom component must behave as a form control — a date picker, a tag input, a currency field — so that formControlName, validation state and ngModel work against it. The contract is four methods: writeValue (model → view), registerOnChange and registerOnTouched (view → model), and setDisabledState. The costs are real: an extra indirection layer, a provider with NG_VALUE_ACCESSOR and forwardRef, easy-to-forget touched propagation (which breaks error display), and disabled-state handling that people routinely skip. In v22 Signal Forms interoperate with existing CVAs, and ngNoCva lets you opt a field out when a component implements CVA but you want to bind it directly — which is useful when a library control fights your model. For a purely internal component with no forms integration requirement, a signal model() input is far cheaper.

Example

@Component({
  selector: 'app-tags',
  providers: [{ provide: NG_VALUE_ACCESSOR, multi: true, useExisting: forwardRef(() => Tags) }],
  template: `...`,
})
export class Tags implements ControlValueAccessor {
  readonly tags = signal<string[]>([]);
  private onChange: (v: string[]) => void = () => {};
  private onTouched = () => {};

  writeValue(v: string[] | null) { this.tags.set(v ?? []); }
  registerOnChange(fn: (v: string[]) => void) { this.onChange = fn; }
  registerOnTouched(fn: () => void) { this.onTouched = fn; }
  setDisabledState(isDisabled: boolean) { this.disabled.set(isDisabled); }
}

Follow-ups

  • Why forwardRef? — The class is referenced in its own decorator metadata before it is defined; forwardRef defers the lookup.
  • What breaks if you skip onTouched? — touched never becomes true, so error messages gated on it never appear.
  • Signal Forms alternative? — Bind the field directly and skip CVA (ngNoCva when the component has one), or keep CVA for compatibility with both worlds.

Common wrong answer

"I use @Input/@Output and it works the same." It works until someone puts your component in a reactive form: no formControlName, no validation state, no disabled handling. Not knowing why CVA exists is a senior-level miss for anyone who has built a design system.

seniorThe server returns a form definition as JSON. How do you render and validate it?

Answer

Two layers. Rendering: map each field descriptor to a component through a registry — a Record<FieldType, Type<unknown>> plus a dynamic host, or a @switch in a renderer component if the set is small and closed. Validation: translate the descriptor's rules into a schema rather than hand-building validator arrays; in v22 that is validateStandardSchema() with a Zod schema built from the JSON, which gets you both runtime validation and inferred types instead of any. Signal Forms fit this case particularly well because the model is just an object, so a form whose shape is only known at runtime does not require constructing and disposing control instances as the definition changes. The parts to name unprompted: versioning of the definition, a whitelist of allowed field types (never render server-supplied HTML or evaluate server-supplied expressions), and a fallback for unknown types so a new server field does not blank the page.

Example

const schema = z.object(Object.fromEntries(def.fields.map(f => [
  f.name, f.required ? z.string().min(1) : z.string().optional(),
])));

readonly model = signal(defaults(def));
readonly f = form(this.model, (path) => validateStandardSchema(path, schema));

// template: @for (field of def.fields; track field.name) { <app-field [def]="field" [control]="f[field.name]" /> }

Follow-ups

  • How do you keep it type-safe? — Infer from the Zod schema (z.infer); the model is typed even though the shape came from the server.
  • Conditional fields? — hidden()/disabled() with a when predicate reading other field values, rather than rebuilding the form.
  • Reactive-forms equivalent? — Build a FormGroup from the definition and add/remove controls as conditions change, remembering to clean up subscriptions and stale values.

Common wrong answer

"Use eval or a template compiled from the server string for the conditions." That is a remote-code-execution hole, and it is the answer that ends the security portion of the interview before it starts.

seniorA 200-field form janks on every keystroke. What is happening and how do you fix it?

Answer

Typically three compounding causes. First, valueChanges on the root group fires per keystroke, and any subscriber doing work — recomputing a summary, calling an API, revalidating everything — pays that cost 200 fields deep. Second, validation runs on 'change' by default, so every keystroke revalidates the control and bubbles status up the group. Third, the template re-renders more than it needs: expensive expressions or method calls in field templates, or a form built with Eager change detection so the whole page is re-checked. The fixes, in order of payoff: set updateOn: 'blur' (or 'submit') for expensive validators, debounce or throttle valueChanges subscribers and never do IO in them directly, split the form into child components with their own views so only the edited section is re-checked, and virtualise or lazily render sections behind @defer or a stepper. Measure with the DevTools profiler first — the jank is often one summary computation, not the form machinery.

Example

this.form = this.fb.group({ /* ... */ }, { updateOn: 'blur' });

this.form.valueChanges.pipe(
  debounceTime(200), distinctUntilChanged(isEqual), takeUntilDestroyed(),
).subscribe(v => this.autosave(v));

Follow-ups

  • Why does splitting into child components help? — Change detection works per view, so a keystroke only re-checks the section's view rather than a single 200-field template.
  • Does Signal Forms change this? — The state is per-field signals, so updates are naturally granular, but an expensive derived summary is still expensive — computed memoisation is the tool.
  • What about autosave? — Debounce, coalesce, and use exhaustMap or a version token so overlapping saves cannot reorder.

Common wrong answer

"Add ChangeDetectionStrategy.OnPush." It is already the default in v22, and it does nothing about validation running on every keystroke or a subscriber doing work per emission. Reaching for a strategy flag instead of profiling is the tell.

principalYou own 60 reactive-forms screens. Signal Forms are stable. What do you do?

Answer

Nothing wholesale. I would adopt Signal Forms for new screens and for any screen already being rewritten, and keep the 60 as they are — they encode years of validation edge cases and are the highest-risk code in the product. The concrete plan: pick one or two new forms as a pilot, agree a shared pattern (model signal, schema module, submit helper, error display component), and write it down as the reference implementation. Then invest in the seam rather than the rewrite: v22 ships compatForm() and SignalFormControl, which let a signal form drive existing CVA-based controls, so the design system does not have to fork. Two guardrails: no screen may be half-migrated (mixed state models are worse than either), and every migrated screen must ship with the same test coverage as the original, so we are converting risk into evidence. If after two quarters the pilot has not reduced form code or defects, we stop — the goal is fewer bugs and less boilerplate, not framework fashion.

Example

// the seam: existing CVA controls, new signal-forms model
readonly model = signal<Invoice>(empty);
readonly f = form(this.model, invoiceSchema);
// <app-legacy-datepicker [control]="f.dueDate" />   // CVA still works via compat layer

Follow-ups

  • How do you decide screen by screen? — Migrate where the form is changing anyway or where defect density is high; leave stable, rarely touched screens alone.
  • What is the risk of two models in one codebase? — Cognitive load and inconsistent error display; mitigate with a shared error component and a single documented pattern per model.
  • What would make you move faster? — A measurable class of bug the new model eliminates — for instance the disabled-controls-dropped-from-value family.
  • What do you tell an engineer who wants to migrate everything? — Show me the defect and cost data for three screens first; if it holds, we scale it.

Common wrong answer

"Reactive forms are legacy now, we migrate all 60 this year." Angular has not deprecated them, the migration touches the most business-critical code in the app, and a plan with no pilot, no metric and no stopping rule is the pattern interviewers are screening against at principal level.

07Router, guards and lazy loading

Routing questions are where interviewers check that you can structure an application, not just a component. Expect a screener on lazy loading, a mid-level question on guards and route params, and at senior level a scenario: protect an admin area, resolve data before navigation, or explain why a deep link renders an empty page. Angular 22 also changed a router default that will bite an upgrading app, which makes for a good "are you current" question.

screenerHow do you configure routing and lazy loading in a standalone app?

Answer

provideRouter(routes) in the application providers, and the routes array is plain data. Lazy loading is a dynamic import in the route: loadComponent for a single standalone component, loadChildren for a child routes array (which no longer needs to be an NgModule — it can export a Routes constant). Router features are opt-in functions: withComponentInputBinding() to bind route params straight to component inputs, withInMemoryScrolling(), withPreloading(PreloadAllModules), withViewTransitions(). Each lazy route boundary is also a bundle boundary and an injector boundary, so a route with providers gets its own environment injector destroyed on navigation away — that is the mechanism behind feature-scoped state.

Example

export const routes: Routes = [
  { path: '', loadComponent: () => import('./home/home').then(m => m.Home) },
  {
    path: 'orders',
    providers: [OrdersStore],
    loadChildren: () => import('./orders/routes').then(m => m.ORDER_ROUTES),
    canMatch: [hasRole('orders.read')],
  },
  { path: '**', component: NotFound },
];

bootstrapApplication(App, {
  providers: [provideRouter(routes, withComponentInputBinding(), withViewTransitions())],
});

Follow-ups

  • What is withComponentInputBinding()? — Route params, query params and data are bound to matching component inputs, so a page component needs no ActivatedRoute at all.
  • Does the order of routes matter? — Yes, first match wins; the wildcard must be last, and v21.1 added mid-path wildcards like 'foo/**/bar'.
  • How do you preload? — withPreloading(PreloadAllModules) or a custom strategy that preloads only routes flagged in data.

Common wrong answer

"Lazy loading needs loadChildren with an NgModule." That has not been true since v14; saying it dates your experience immediately and usually comes with a RouterModule.forRoot answer as well.

midGuards: functional vs class-based, and CanActivate vs CanMatch?

Answer

Guards are plain functions now — CanActivateFn, CanMatchFn, CanDeactivateFn, ResolveFn — using inject() for their dependencies; the class-based interfaces were deprecated in v15.2 and exist only for legacy code. The functional form composes: a guard can be a factory returning a guard, so hasRole('admin') is idiomatic rather than a class per permission. CanActivate runs after the route has matched and the lazy chunk has been loaded, and answers "may this user open this route". CanMatch runs during matching, before the chunk is downloaded, and answers "does this route even apply" — so it both avoids shipping code the user may not use, and lets two routes share a path with different guards (an admin dashboard and a user dashboard at /dashboard). Return true, false, or a UrlTree to redirect, which is preferable to calling router.navigate() inside a guard.

Example

export const hasRole = (role: string): CanMatchFn => () => {
  const auth = inject(Auth), router = inject(Router);
  return auth.roles().includes(role) ? true : router.parseUrl('/forbidden');
};

export const unsavedChanges: CanDeactivateFn<EditPage> = (cmp) =>
  !cmp.dirty() || confirm('Discard changes?');

Follow-ups

  • Why return a UrlTree? — It makes the redirect part of the same navigation, avoiding a cancelled navigation followed by a second one (and the flicker that comes with it).
  • Do guards run on every child route? — canActivate on a parent runs once for the subtree; canActivateChild runs per child navigation.
  • Async guards? — Return a Promise or Observable; the router waits, so a slow auth check blocks navigation — show a loading indicator via router events.

Common wrong answer

"I'd use CanActivate to hide the admin area." It hides the page but the admin chunk is already downloaded and readable. CanMatch is the answer, alongside the point that no client-side guard is a security control — the server must enforce it.

midRoute parameters: snapshot or observable, and what changed in v22?

Answer

route.snapshot.paramMap reads the value once, which is wrong whenever the same component instance is reused for a different param — navigating from /item/1 to /item/2 does not recreate the component, so the snapshot is stale. The stream form (route.paramMap) handles that, and today the cleanest version is either withComponentInputBinding(), which binds params directly to inputs, or toSignal() over the param stream. The v22 change to know: paramsInheritanceStrategy now defaults to 'always' instead of 'emptyOnly', so child routes inherit parent params and data even when the child has its own params — no migration is provided, so an upgrading app can suddenly see a parent's id where it previously saw undefined. Restore the old behaviour with withRouterConfig({ paramsInheritanceStrategy: 'emptyOnly' }) if a route relied on it.

Example

// cleanest: inputs bound by the router
@Component({ /* ... */ })
export class ItemPage {
  id = input.required<string>();                       // from /item/:id
  item = httpResource<Item>(() => `/api/items/${this.id()}`);
}

// or explicitly
readonly id = toSignal(this.route.paramMap.pipe(map(p => p.get('id'))));

Follow-ups

  • Why is the component reused? — The router reuses a component when only parameters change; RouteReuseStrategy controls it, and onSameUrlNavigation affects re-navigation.
  • Query params vs matrix params? — Query params are global to the URL and survive route changes; matrix params attach to a segment.
  • What is isActive() (v22)? — A signal telling you whether a path is active, with options for paths/query/fragment matching — no more subscribing to router events for an active flag.

Common wrong answer

"Snapshot is fine, the component is recreated on navigation." It is not, when only the parameter changes — this is the classic "detail page shows the previous record" bug and the reason the question is asked at all.

midResolvers or load-in-the-component: which, and why?

Answer

My default is to load in the component with a resource, and use a resolver only when the data must exist before the route activates. Resolvers block navigation, so a slow API means the user sits on the old page with no feedback unless you wire router events into a progress bar; they also complicate error handling, because a failed resolve cancels the navigation and you must decide where the user lands. Loading in the component gives you an immediate shell with skeletons, per-section loading states, and a natural retry — which is usually better perceived performance for the same total time. The legitimate resolver cases: data needed to decide the page's identity (a redirect based on the record's type), SEO-critical content that must be in the server-rendered HTML, and permissions where rendering anything at all would leak information.

Example

// resolver: only when navigation genuinely depends on the data
export const orderResolver: ResolveFn<Order> = (route) =>
  inject(Api).order(route.paramMap.get('id')!);

// preferred default: resource in the component, with a skeleton while loading
readonly order = httpResource<Order>(() => `/api/orders/${this.id()}`);

Follow-ups

  • How do you show progress for a resolver? — Subscribe to router events (NavigationStart/NavigationEnd) and drive a top-loading bar.
  • What if the resolve fails? — The navigation is cancelled; handle it in the resolver by returning a UrlTree to an error route, or catch and return a sentinel.
  • Does SSR change the answer? — Yes: for indexable content, resolvers (or server route render modes) put data in the initial HTML.

Common wrong answer

"Always resolve, it avoids flicker." It replaces flicker with an unexplained pause on the previous page, which measures worse on perceived performance and is the trade-off the interviewer wants you to name.

seniorA deep link renders a blank page but clicking through works. How do you debug it?

Answer

Blank on deep link, fine on in-app navigation, is almost always one of four things. First, server configuration: with PathLocationStrategy the server must rewrite unknown paths to index.html, otherwise the deep link is a 404 that the SPA never sees. Second, a guard or resolver that depends on state only populated by an earlier page — an auth check that assumes a token already in memory rather than in storage, which then cancels the navigation silently. Third, a route ordering or match problem — the wildcard route catching it, or a canMatch failing on a cold start. Fourth, under SSR, a hydration mismatch or a server-side error that leaves an empty shell. My debugging order: check the network response for the document, then turn on withDebugTracing() to see the navigation lifecycle and where it cancels, then check for a NavigationCancel/NavigationError event, then look at the server logs if SSR is involved.

Example

provideRouter(routes, withDebugTracing());   // logs every navigation event, dev only

inject(Router).events.pipe(takeUntilDestroyed())
  .subscribe(e => { if (e instanceof NavigationCancel) console.warn(e.reason, e.url); });

Follow-ups

  • What does NavigationCancel.reason tell you? — Which guard rejected and whether it was a redirect, which is the fastest path to the culprit.
  • Hash strategy? — withHashLocation() avoids the server rewrite entirely; the cost is uglier URLs and weaker SEO.
  • Does this differ under SSR? — Yes; the server actually renders the route, so a guard needing localStorage throws server-side. Guard code must be platform-aware.

Common wrong answer

"It must be a routing config bug in the app." Half the time it is the web server or CDN not rewriting to index.html; a candidate who never considers the deployment layer is a candidate who has not shipped a SPA to production.

seniorHow do you keep UI state (filters, tabs, pagination) in the URL, and why bother?

Answer

Put anything the user would expect to survive a refresh or a shared link into query params: filters, sort, page, active tab. The mechanics are router.navigate([], { relativeTo: route, queryParams, queryParamsHandling: 'merge', replaceUrl: true }) — merge so you do not drop other params, replaceUrl so typing in a filter box does not create fifty history entries. Read them back as signals so components stay declarative. The reasons to bother are concrete: shareable links, working back button, state that survives a reload and an SSR round trip, and — often overlooked — support and analytics, because a bug report with a URL is reproducible. The limit is size and sensitivity: URLs are logged by proxies and analytics, so never put tokens or personal data in them, and put genuinely large state (a complex query builder) in storage with a short id in the URL.

Example

readonly page = toSignal(this.route.queryParamMap.pipe(map(p => +(p.get('page') ?? 1))),
                         { initialValue: 1 });

setPage(page: number) {
  this.router.navigate([], { relativeTo: this.route, queryParams: { page },
                             queryParamsHandling: 'merge', replaceUrl: true });
}

Follow-ups

  • How do you avoid a navigation loop? — Write only on user action, read only from the URL; never sync both directions with an effect.
  • What about the scroll position? — withInMemoryScrolling({ scrollPositionRestoration: 'enabled', anchorScrolling: 'enabled' }).
  • Where does this interact with SSR? — Server-rendered content can honour the filters directly, so the first paint is correct rather than a default view that jumps.

Common wrong answer

"Keep it in a service so it survives navigation." It survives navigation but not a refresh or a shared link, and it makes the back button do nothing useful — which users read as a broken app.

seniorDesign the auth flow: guards, interceptors, token refresh, and what happens on 401.

Answer

Separate the three responsibilities. Routing decisions belong in CanMatch guards, so an unauthorised user never downloads the chunk and is redirected via a UrlTree carrying a returnUrl. Attaching credentials belongs in a functional HTTP interceptor, which adds the token only to requests for your own API origins — never blanket-attach to third-party URLs. Refresh belongs in the same interceptor as a single-flight operation: on 401, one refresh runs while other 401s wait for its result and then retry, which is where most implementations go wrong and stampede the refresh endpoint. On failure of the refresh, clear the session once, redirect to login with the return URL, and make that path idempotent so five concurrent failures produce one redirect. State the boundary unprompted: client-side guards are UX, the server is the security boundary, and tokens live in memory or an httpOnly cookie, not in localStorage.

Example

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(Auth);
  const request = auth.token() && isOwnApi(req.url)
    ? req.clone({ setHeaders: { Authorization: `Bearer ${auth.token()}` } }) : req;

  return next(request).pipe(catchError(err =>
    err.status === 401 && isOwnApi(req.url)
      ? auth.refreshOnce().pipe(switchMap(() => next(request.clone(/* new token */))))
      : throwError(() => err)));
};

Follow-ups

  • How do you implement "refresh once"? — A shared in-flight observable in the service (shareReplay({ bufferSize: 1, refCount: true })), so concurrent callers await the same refresh.
  • Why not localStorage for tokens? — Any XSS reads it; httpOnly cookies with CSRF protection or in-memory tokens limit the blast radius.
  • What about SSR? — The server has no browser storage; auth must come from cookies forwarded to the server render, and guard code must not touch window.

Common wrong answer

"The guard checks localStorage for the token, so the route is protected." That is a UX gate, not protection — the chunk is downloadable and the API is the real boundary. It also breaks under SSR, where localStorage does not exist.

principalFive teams ship into one Angular app. How do you structure routing and boundaries?

Answer

I would make the route the ownership boundary before I consider anything more exotic. Each team owns a top-level route with its own lazy-loaded routes file, its own route-scoped providers, and its own bundle budget enforced in CI — so a team's regression is visible in their number, not in a shared total. Cross-team communication goes through a thin shared kernel: contract tokens, a design system, and URL-based navigation rather than direct imports, with module-boundary lint rules (Nx tags or ESLint restricted imports) making violations a build failure rather than a review conversation. I would deliberately not reach for micro-frontends (Module Federation, native federation) unless there is a hard requirement — independent deploy cadence, or teams on different framework versions — because they buy independence at the price of duplicated runtimes, version-skew bugs, and much harder shared-state and auth stories. A monorepo with strict boundaries gets most of the isolation with none of that, and it is the answer most staff-plus interviewers are hoping to hear before they ask "and when would you federate?".

Example

// shell routes: one entry per team, nothing shared but the kernel
export const routes: Routes = [
  { path: 'billing',  loadChildren: () => import('@acme/billing').then(m => m.ROUTES) },
  { path: 'catalog',  loadChildren: () => import('@acme/catalog').then(m => m.ROUTES) },
  { path: 'admin',    canMatch: [hasRole('admin')],
                      loadChildren: () => import('@acme/admin').then(m => m.ROUTES) },
];

Follow-ups

  • When would you federate? — Independent release trains, or an acquisition on a different stack; then isolate at the route level and pin a shared version contract for Angular itself.
  • How do you keep the design system from becoming a bottleneck? — Versioned package, additive changes, and a contribution model instead of a request queue.
  • How do you handle shared state across teams? — Prefer the URL and the server; a shared client store across five teams becomes a coupling surface nobody owns.
  • How do you prevent bundle creep? — Per-route budgets failing CI, plus a periodic chunk-graph review; without it, shared imports quietly pull every team's code into the initial chunk.

Common wrong answer

"Micro-frontends with Module Federation, so each team is independent." Offered without a triggering requirement, it signals architecture-by-fashion; the follow-up — how do you handle two Angular versions, shared auth, and a design-system upgrade across five bundles — is where the answer usually collapses.

08HttpClient, resources and data fetching

Every app talks to a backend, so this sub-area is asked in nearly every loop — usually as "how do you fetch and cache data", then as an interceptor question, then as an error-handling scenario. Angular 22 moved several defaults here (fetch backend, stable httpResource), which makes it easy for an interviewer to tell whether your answer is from 2021. At senior level the question is really about the shape of your data-access layer, not the API surface.

screenerHow do you set up HttpClient today, and what changed in v22?

Answer

provideHttpClient() in the application providers, with features as arguments: withInterceptors([...]) for functional interceptors, withFetch(), withXsrfConfiguration(...). HttpClientModule was deprecated in v18 and should not appear in new code. The v22 changes worth naming: fetch is now the default backend, so withFetch() is deprecated as redundant, and if you need upload progress you must opt back into XHR with withXhr() because the fetch backend cannot report it; reportProgress was also split into reportDownloadProgress and reportUploadProgress. Fetch as the default matters for SSR too — it is the same primitive the server runtime uses, which removes a class of Node-vs-browser differences.

Example

bootstrapApplication(App, {
  providers: [
    provideHttpClient(
      withInterceptors([authInterceptor, retryInterceptor, telemetryInterceptor]),
      // withFetch() — deprecated in v22: fetch is the default
      // withXhr() — only if you need upload progress
    ),
  ],
});

Follow-ups

  • Why were functional interceptors introduced? — They use inject(), compose as plain functions, are tree-shakable and can be registered per-request-context; the class form with HTTP_INTERCEPTORS is legacy.
  • Do interceptors run in order? — Yes, in array order on the way out and in reverse on the way back — which matters when combining auth and retry.
  • Legacy interop? — withInterceptorsFromDi() keeps class-based interceptors working during a migration.

Common wrong answer

"Import HttpClientModule in the app module." Deprecated since v18 and impossible in a standalone bootstrap; it is the single fastest way to reveal that your Angular knowledge stops around v13.

midWhen do you use httpResource() and when plain HttpClient?

Answer

httpResource() (stable in v22) is for reads that belong to a view: you give it a reactive request function, it fetches when the dependencies change, cancels superseded requests, and exposes value(), isLoading(), error() and status() as signals — plus, in v22, it participates in SSR transfer state so the client does not refetch what the server already fetched. Plain HttpClient stays the tool for commands and for anything you must sequence or compose: POST/PUT/DELETE, retries with custom policy, uploads, or a pipeline that coordinates several calls. A rule that survives follow-ups: resources for declarative reads bound to state, HttpClient (usually inside a service method returning a promise or observable) for imperative writes.

Example

// read: declarative, cancels on param change, hydration-aware
readonly filters = signal<Filters>(defaults);
readonly rows = httpResource<Row[]>(() => ({
  url: '/api/rows', params: { ...this.filters() },
}));

// write: imperative
async archive(id: string) {
  await firstValueFrom(this.http.post(`/api/rows/${id}/archive`, {}));
  this.rows.reload();
}

Follow-ups

  • How do you refetch after a mutation? — reload(), or make the resource depend on a version signal you bump.
  • Typed responses? — httpResource<T>(); for runtime safety add a parser (Zod) in the loader, because a generic parameter is not validation.
  • What about rxResource? — Same model with an Observable loader; use it when the fetch already lives in an RxJS service method.

Common wrong answer

"httpResource replaces the whole service layer." It has no shared cache, no cross-component invalidation and no write story; positioning it as a data layer invites the follow-up "so how do two components share one fetch", which it does not answer on its own.

midWrite an interceptor that adds a correlation id, retries idempotent failures, and logs slow calls.

Answer

Functional interceptors are just functions of (req, next), so each concern is its own function and the array order defines the pipeline. Two things to get right: requests are immutable, so you must clone() to modify, and retry policy must be conditional — only idempotent methods, only on 5xx or network errors, with backoff and a cap. Logging goes on the response side with a timer started before next(). Keep them small and single-purpose; a single "http.interceptor.ts" doing five things is impossible to test and to reason about when the order matters.

Example

export const correlationInterceptor: HttpInterceptorFn = (req, next) =>
  next(req.clone({ setHeaders: { 'X-Correlation-Id': crypto.randomUUID() } }));

export const retryInterceptor: HttpInterceptorFn = (req, next) => {
  const idempotent = ['GET', 'HEAD', 'OPTIONS'].includes(req.method);
  return idempotent
    ? next(req).pipe(retry({ count: 2, delay: (e, n) =>
        e.status >= 500 || e.status === 0 ? timer(2 ** n * 250) : throwError(() => e) }))
    : next(req);
};

export const timingInterceptor: HttpInterceptorFn = (req, next) => {
  const started = performance.now();
  return next(req).pipe(tap({ finalize: () => {
    const ms = performance.now() - started;
    if (ms > 1_000) inject(Telemetry).slowCall(req.urlWithParams, ms);
  } }));
};

Follow-ups

  • Why is HttpRequest immutable? — Because interceptors form a chain and a shared mutable request would make ordering effects unpredictable.
  • How do you skip an interceptor for one call? — HttpContext tokens: set a flag on the request and check it in the interceptor.
  • Where does inject() work here? — Inside the interceptor function body, which runs in the injection context of the request.

Common wrong answer

"Retry everything three times to be resilient." Retrying a POST duplicates orders and payments, and blanket retries amplify an outage into a self-inflicted DDoS. The expected answer names idempotency and backoff without prompting.

seniorWhat is your error-handling strategy across the whole app?

Answer

Three layers with different jobs. At the transport layer, an interceptor normalises HttpErrorResponse into a typed domain error — status, code, correlation id, user-safe message — so no component ever pattern-matches on raw HTTP. At the feature layer, expected errors are state: a resource's error() or an explicit error signal drives an inline message with a retry, because a 404 on one panel should not blank the page. At the app layer, a custom ErrorHandler catches the unexpected, reports to the monitoring backend with the correlation id, and shows a generic fallback — and for rendering failures specifically, an error boundary at the route level so one broken widget does not take the shell down. The two rules I would state unprompted: never show raw server messages to users (information disclosure), and always keep the correlation id in both the log and the UI so support can join them.

Example

@Injectable()
export class AppErrorHandler implements ErrorHandler {
  private telemetry = inject(Telemetry);
  handleError(err: unknown) {
    this.telemetry.capture(err);                  // Sentry/OTel etc.
    if (!(err instanceof HttpErrorResponse)) inject(Toast).show('Something went wrong');
  }
}
providers: [{ provide: ErrorHandler, useClass: AppErrorHandler }]

Follow-ups

  • How do you avoid a toast storm? — Deduplicate by error code within a time window, and never toast from inside a retry loop.
  • What about errors during SSR? — They must be caught server-side and turned into a rendered error page or a fallback to client rendering, not a 500.
  • Where do you handle offline? — Status 0 in the normaliser, plus a global online/offline signal driving a banner.

Common wrong answer

"catchError in each component and show a toast." That produces inconsistent messages, duplicated logic, no telemetry correlation, and — because the outer stream often completes — components that stop updating after the first error.

seniorThree components need the same data on one page. How do you avoid three requests?

Answer

Give the data one owner. The simplest correct answer is a service that fetches once and exposes the result as a signal or a resource, injected by all three components — one fetch, synchronous reads, no subscription semantics. If the data must stay an observable, multicast it with shareReplay({ bufferSize: 1, refCount: true }) and hand out the shared stream, never the raw http.get. For genuinely cache-shaped needs — many keys, invalidation, background refresh, stale-while-revalidate — I would put a small caching layer in the service (a Map of key to resource, with a TTL) or adopt an existing query library rather than reinvent it. Under SSR, add transfer state so the client does not repeat the server's fetch; httpResource integrates with it in v22, and provideClientHydration(withHttpTransferCacheOptions(...)) covers HttpClient GETs.

Example

@Injectable({ providedIn: 'root' })
export class Customers {
  private cache = new Map<string, ReturnType<typeof httpResource<Customer>>>();

  get(id: string) {
    if (!this.cache.has(id)) {
      this.cache.set(id, httpResource<Customer>(() => `/api/customers/${id}`,
        { injector: this.injector }));
    }
    return this.cache.get(id)!;
  }
  private injector = inject(Injector);
}

Follow-ups

  • How do you invalidate? — Explicitly after mutations (reload()), by TTL, or by a version signal the resources depend on; pick one and document it.
  • Memory? — An unbounded cache in a root service is a leak; bound it (LRU) or scope it to the route.
  • Why not just prop-drill from a parent? — Perfectly fine and often best for one page; the service matters when the consumers are not siblings.

Common wrong answer

"The browser HTTP cache handles it." It depends on server headers you may not control, it does not dedupe concurrent in-flight requests reliably, and it does nothing for POST-based reads. Designing on it is a bet you cannot verify from the client.

seniorImplement upload with a progress bar. What is the v22 gotcha?

Answer

Use reportUploadProgress with observe: 'events' and map HttpUploadProgressEvent into a percentage signal. The v22 gotcha is that the default backend is now fetch, and fetch cannot report upload progress — so an upload that showed a progress bar on v21 will silently report nothing after the upgrade unless you opt back into XHR with withXhr(). That is exactly the kind of "did you actually upgrade an app" detail interviewers like. Beyond the API: send large files as multipart or in chunks with a resumable protocol, guard with a size and MIME check client-side (and again server-side, since the client check is only UX), and make cancellation real by unsubscribing, which aborts the request.

Example

provideHttpClient(withXhr());   // v22: required for upload progress

readonly progress = signal(0);

upload(file: File) {
  const body = new FormData(); body.append('file', file);
  return this.http.post('/api/files', body, {
    reportUploadProgress: true, observe: 'events',
  }).pipe(tap(e => {
    if (e.type === HttpEventType.UploadProgress && e.total)
      this.progress.set(Math.round(100 * e.loaded / e.total));
  }));
}

Follow-ups

  • How do you cancel? — Unsubscribe (or destroy the component); the underlying request is aborted.
  • Download progress? — reportDownloadProgress works with the fetch backend; only upload needs XHR.
  • Very large files? — Presigned URLs directly to object storage, so the file never transits your API.

Common wrong answer

"Set reportProgress: true and it works." That option was split in v22, and with the fetch default the upload half reports nothing — a bug that looks like the progress bar being stuck at zero for everyone after an upgrade.

principalDesign the data-access layer for a large Angular app. What do you standardise?

Answer

I standardise five things and leave the rest to teams. One: a generated or hand-written typed client per backend (OpenAPI-generated where possible), so nobody writes URL strings in components and a backend change becomes a compile error. Two: a normalisation boundary — every response validated or at least parsed at the edge, and every error mapped to a domain error type. Three: read/write asymmetry — reads through resources bound to view state, writes through explicit service methods that also declare what they invalidate. Four: cross-cutting policy in interceptors, not features: auth, correlation ids, retry, timeouts, telemetry. Five: caching policy chosen deliberately per data class — per-view, per-session, or none — and written down, because uncontrolled caching is where "why is the user seeing stale data" tickets come from. What I explicitly avoid standardising is a single god-service or a store for everything; the data layer's job is to make the boundary uniform, not to centralise all state.

Example

// generated client + thin domain service; components never see URLs
@Injectable({ providedIn: 'root' })
export class OrdersApi {
  private http = inject(OrdersClient);            // OpenAPI-generated
  list(f: () => Filters) { return httpResource<Order[]>(() => this.http.listUrl(f())); }
  async cancel(id: string, reason: string) {
    await this.http.cancel(id, { reason });       // declares its invalidation in one place
    this.invalidate(id);
  }
}

Follow-ups

  • Generated clients — worth it? — Yes when the backend publishes a spec: it removes an entire class of drift bugs and makes breaking changes visible in CI.
  • Do you validate every response? — At least at boundaries you do not control; a schema parser costs microseconds and turns a silent undefined into a reported error.
  • How do you handle backend versioning? — Version the client package, keep adapters at the boundary, and never let a version-specific field shape leak into components.
  • How do you keep teams aligned? — One reference feature implementing all five rules, plus lint rules for the mechanical parts (no HttpClient in components).

Common wrong answer

"Every component calls HttpClient directly, it's simpler." It is, for the first ten screens; then you cannot change an endpoint, add a header, or find who calls what, and the migration cost lands on whoever comes next.

09Component API design, projection and lifecycle

This sub-area shows up as "design a reusable X" — a modal, a table, a combobox — and it is where interviewers assess taste rather than recall. The mechanics (projection, host directives, dynamic components) are the vocabulary; the actual signal is whether you can decide what a component owns, what the caller owns, and how the API stays stable while the implementation changes. Fundamentals like lifecycle hooks still appear, but mostly as "which of these still matter now that signals exist".

midExplain content projection: single slot, multi-slot, and fallback content.

Answer

<ng-content> renders markup the caller passed in, in place. Multi-slot projection uses select with a CSS selector — <ng-content select="[header]" /> — and everything unmatched falls into the bare <ng-content>; ngProjectAs lets the caller route an element to a slot when its real selector does not match. Since v18, <ng-content> supports fallback content: children of the ng-content element are rendered when nothing is projected, which removes the old workaround of an *ngIf over a ContentChild. The two facts that trip people up: projected content is created and change-detected in the caller's context (its injector, its bindings), and it is instantiated even if the slot is inside an @if that is false — unless you project into a template instead.

Example

<!-- card.html -->
<div class="card">
  <header><ng-content select="[card-title]">Untitled</ng-content></header>
  <ng-content />
  <footer><ng-content select="[card-actions]" /></footer>
</div>

<!-- caller -->
<app-card>
  <h2 card-title>Invoice 42</h2>
  <p>Body text</p>
  <button card-actions>Pay</button>
</app-card>

Follow-ups

  • Why does a projected component's DI resolve to the caller? — Element injectors follow the declaration tree, not the render tree.
  • How do you avoid instantiating expensive projected content? — Take an ng-template and render it conditionally, rather than projecting eagerly.
  • How do you style projected content? — ::ng-deep is deprecated; expose CSS custom properties or use ViewEncapsulation.None deliberately in a design-system layer.

Common wrong answer

"Projected content belongs to the child component, so it uses the child's providers." It does not — this misunderstanding produces "NG0201: no provider" errors that look impossible until you know which tree the injector walks.

midWhich lifecycle hooks still matter in a signal-based component?

Answer

Fewer than before, and that is the point. ngOnInit survives as the place for one-time imperative setup that needs inputs — though with signal inputs a computed usually replaces it. ngOnDestroy survives for imperative cleanup, and DestroyRef.onDestroy() covers the same need without implementing the interface. ngOnChanges is largely obsolete for signal inputs; use computed/effect. ngAfterViewInit/ngAfterContentInit are replaced for most cases by signal queries plus afterNextRender, and the latter is strictly better because it does not run on the server. ngDoCheck and ngAfterViewChecked are performance traps — they run on every check and are almost always a sign that something should have been a signal. The senior-level framing: the hook list was a scheduling API, and signals replaced most of the scheduling with dependency tracking.

Example

export class Panel {
  private destroyRef = inject(DestroyRef);
  size = input.required<'sm' | 'lg'>();

  // instead of ngOnChanges:
  readonly cssClass = computed(() => `panel panel--${this.size()}`);

  constructor() {
    const t = setInterval(() => this.poll(), 30_000);
    this.destroyRef.onDestroy(() => clearInterval(t));   // instead of ngOnDestroy
  }
}

Follow-ups

  • Order of hooks? — ngOnChanges → ngOnInit → ngDoCheck → content hooks → view hooks → ngOnDestroy; still worth knowing for legacy debugging.
  • Do hooks run on the server? — Yes, up to ngOnInit/content/view init; render callbacks do not, which is the practical difference.
  • What runs on route reuse? — No hooks re-run when only params change; that is why param streams exist.

Common wrong answer

Reciting all eight hooks in order as the answer. The question is which ones you still use and why; a list without a point of view reads as textbook recall, which at senior level counts against you.

midWhat are host directives, and what problem do they solve?

Answer

Host directives (v15) let a component or directive declare that other directives are applied to its host element, with explicit input/output mapping — composition instead of inheritance or copy-paste. The classic use is a design system: a Button component that composes Ripple, FocusRing and Cdk behaviours without the consumer having to remember to add three directives, and without a base class hierarchy that only works for one axis of variation. The mapping matters: inputs: ['color: buttonColor'] re-exposes a host directive's input under your own name, so your public API does not leak the composition. Constraints to name: host directives must be standalone, they cannot be added conditionally, and they apply to the host element only.

Example

@Component({
  selector: 'app-button',
  hostDirectives: [
    { directive: Ripple, inputs: ['rippleColor: color'] },
    FocusRing,
  ],
  template: `<ng-content />`,
})
export class Button {}

Follow-ups

  • Why not inheritance? — Single inheritance cannot compose two behaviours, and a base class couples lifecycle and DI in ways that break subclasses.
  • Can host directives be conditional? — No; if you need conditional behaviour, put the decision inside the directive.
  • How do they affect DI? — They are directives on the same element, so they share the element injector — which is how they can talk to each other.

Common wrong answer

"Same as extending a base component." Inheritance gives you one parent and drags its lifecycle along; host directives compose N behaviours with an explicit public API. Interviewers building design systems care about this distinction specifically.

seniorDesign the API for a reusable data table used by six teams. What do you expose?

Answer

I would keep the table's own state small and push everything domain-specific to the caller. Inputs: rows (already fetched — the table does not fetch), columns as a typed descriptor list, plus display options (density, selection mode). Rendering extensibility through templates rather than configuration: a cell template per column with a typed context, a row-detail template, an empty-state slot — configuration objects always run out of expressiveness, and then you get a cellRenderer: (r) => string that cannot contain a component. Outputs for intent, not for implementation: sortChange, pageChange, selectionChange, so server-side paging and client-side paging are both the caller's choice. State ownership stated explicitly: sorting/paging/selection are inputs with change outputs (controlled), not internal state, so the caller can put them in the URL. And I would version the descriptor type, because six teams means breaking changes need a deprecation path, not a coordinated release.

Example

export interface ColumnDef<T> { key: keyof T & string; header: string; sortable?: boolean; }

@Component({ selector: 'app-table', /* ... */ })
export class DataTable<T> {
  rows = input.required<readonly T[]>();
  columns = input.required<ColumnDef<T>[]>();
  sort = model<Sort | null>(null);          // controlled: caller can persist it in the URL
  cell = contentChild<TemplateRef<{ $implicit: T; column: ColumnDef<T> }>>('cell');
  rowActivate = output<T>();
}

Follow-ups

  • Why not let the table fetch? — It couples a UI component to your API, breaks reuse, and makes SSR and caching decisions the table's problem.
  • Controlled vs uncontrolled? — Controlled by default with sensible defaults; uncontrolled convenience wrappers can be built on top, not the other way round.
  • Accessibility? — Real table semantics or explicit ARIA grid roles; @angular/aria (v21) provides headless patterns such as ngGrid so you are not inventing keyboard navigation.
  • How do you evolve it? — Additive inputs, deprecation warnings for one minor, and a codemod for breaking renames.

Common wrong answer

"Take a config object with callbacks for everything." Configuration-driven components hit a wall the first time someone needs a component inside a cell, and then they grow a second, template-based API alongside the first — which is the mess the question is testing you to avoid.

seniorHow do you render a component whose type is only known at runtime?

Answer

Two supported ways. Declaratively, <ng-container *ngComponentOutlet="cmp; inputs: data" /> — since v16/17 it takes inputs, a content projection array and an injector, which covers most plugin-style cases with no imperative code. Imperatively, ViewContainerRef.createComponent(Type, { injector, environmentInjector }), then ref.setInput('x', v) for each input (never assign to ref.instance.x — that bypasses change detection and input transforms) and ref.destroy() on teardown. The imperative route is right when you need the ComponentRef itself: a modal service, a toast host, a canvas-driven overlay. Pair it with a lazy import() so the dynamic component is not in the eager bundle — otherwise you have paid the bundle cost for something you may never render.

Example

export class ModalService {
  private vcr = inject(ViewContainerRef);
  async open<T>(load: () => Promise<Type<T>>, inputs: Partial<T>) {
    const ref = this.vcr.createComponent(await load());
    for (const [k, v] of Object.entries(inputs)) ref.setInput(k, v);
    return { ref, close: () => ref.destroy() };
  }
}

Follow-ups

  • Why setInput? — It marks the view dirty and runs input transforms; a direct property write does neither.
  • What replaced ComponentFactoryResolver? — Nothing is needed: since Ivy you pass the component type directly; the resolver was deprecated in v13.
  • Where does the component get its providers? — From the injector you pass, which is how you scope a dynamically created component to a feature.

Common wrong answer

"Use ComponentFactoryResolver to resolve a factory." Deprecated in v13 and removed from the modern API surface; it is a reliable signal that the candidate's last Angular project ended around 2021.

seniorExplain view encapsulation and how you let consumers theme a component.

Answer

Default encapsulation is Emulated: Angular rewrites your component's CSS with generated attributes so styles do not leak out, and outside styles do not leak in except through inherited properties. ShadowDom uses real shadow roots — stronger isolation, but you inherit shadow-DOM constraints for global styles, fonts and third-party CSS. None makes the styles global, which is occasionally right for a top-level theme file and almost never right for a component. For theming, the durable answer is CSS custom properties: they pierce emulated encapsulation and shadow DOM by design, so a component exposes a documented set of variables (--app-button-bg) and consumers set them from outside. ::ng-deep is deprecated and should not be the theming strategy — it reaches into another component's internals and locks you to its DOM structure, which is exactly what breaks on the next library upgrade.

Example

/* button.css — the component's contract */
.btn { background: var(--app-button-bg, #dd0031); color: var(--app-button-fg, #fff); }

/* consumer, anywhere up the tree */
.theme-dark { --app-button-bg: #ff5278; }

Follow-ups

  • Does :host-context() still work? — Yes, and it is the supported way to react to an ancestor class (a theme wrapper) from inside a component.
  • Downside of ShadowDom? — Global stylesheets, some third-party widgets and form autofill behave differently; test before committing a design system to it.
  • How do you stop consumers depending on internals? — Document the custom properties, and treat class names as private; a lint rule can ban ::ng-deep in app code.

Common wrong answer

"Use ::ng-deep, it's the standard way to style child components." It is deprecated, it is not scoped without an accompanying :host, and it creates coupling to another component's DOM that breaks silently on upgrade.

principalYou own the design system for eight teams. How do you version and evolve it without breaking everyone?

Answer

Treat it as a product with a contract. Semantic versioning where "breaking" is defined explicitly — a removed input, a changed default, a DOM structure change that consumers were told is public — and a deprecation policy: two minors of warnings, a codemod where mechanically possible, and a documented migration note per breaking change. Keep the public surface small and intentional: inputs, outputs, template slots, CSS custom properties; everything else is private, and I would enforce that with an API-extractor snapshot in CI so accidental exports fail the build. Distribution matters as much as design: publish a versioned package rather than sharing source, so teams upgrade on their own schedule, but keep the window narrow (no more than two minors behind) or you end up supporting five variants. Finally, make contribution possible — a design-system team that is a request queue becomes the bottleneck, and teams route around it with local copies, which is how you end up with four button components anyway.

Example

// deprecation with a mechanical migration path
export class Button {
  /** @deprecated since 4.2, use `variant`. Removed in 5.0. */
  kind = input<'primary' | 'ghost' | undefined>(undefined);
  variant = input<Variant>('primary');
  protected readonly effective = computed(() => this.variant() ?? mapLegacy(this.kind()));
}

Follow-ups

  • How do you catch breakage before release? — Visual regression tests on a component gallery, plus building the top three consumer apps against the release candidate in CI.
  • Angular version skew? — Support the current and previous major, and state the policy; peer dependencies make the constraint explicit rather than implicit.
  • How do you keep accessibility consistent? — Build on headless primitives (@angular/aria, CDK) and make an a11y test part of the component's definition of done.
  • How do you measure success? — Adoption percentage, number of local re-implementations, and time-to-upgrade across consumer apps.

Common wrong answer

"We keep it in the monorepo so everyone always gets the latest." That makes every change a synchronised, all-teams event, so nobody dares change anything; the intent — one version everywhere — is right, but without a deprecation contract it produces paralysis instead of consistency.

10Performance, bundles and deferred loading

Performance questions separate people who have shipped to real users from people who have read about optimisation. The reliable pattern is a scenario — "the dashboard takes six seconds on a mid-range phone, what do you do" — where the expected answer starts with measurement, not with a list of techniques. At senior level you are expected to know the bundle tooling and the Core Web Vitals; at principal, how you stop regressions from re-entering after you fix them.

midWhat do you measure, and what budgets do you set?

Answer

Three field metrics and two build metrics. In the field: LCP (when the main content is visible, target under 2.5 s), INP (interaction responsiveness, target under 200 ms — it replaced FID as a Core Web Vital in March 2024) and CLS (layout stability, under 0.1), collected from real users rather than from a laptop on office wifi. In the build: initial bundle size and per-route lazy chunk sizes, enforced by the budgets section of angular.json so CI fails on regression rather than a human noticing months later. The reason to insist on RUM over lab numbers is that Angular apps skew towards logged-in, data-heavy pages on mixed devices; a Lighthouse score on a fast machine routinely hides a 4-second LCP for the 25th percentile of your actual users.

Example

"budgets": [
  { "type": "initial", "maximumWarning": "500kB", "maximumError": "700kB" },
  { "type": "anyComponentStyle", "maximumWarning": "4kB", "maximumError": "8kB" },
  { "type": "bundle", "name": "checkout", "maximumError": "250kB" }
]

Follow-ups

  • Why is INP often bad in Angular apps? — Long tasks: a click triggers a large change-detection pass plus data transformation on the main thread; zoneless and OnPush shrink the first part, memoisation and workers the second.
  • Transferred vs raw size? — Budgets measure raw; what users pay is compressed transfer plus parse/execute — always check both.
  • What is a reasonable initial bundle? — Under ~200 kB compressed for a consumer app is a good target; internal tools can afford more, but state the target rather than "as small as possible".

Common wrong answer

"We run Lighthouse and aim for 90+." A lab score on a synthetic device is a smoke test, not a measurement of your users' experience; leading with it suggests you have never watched a p75 field metric move.

midWhat does NgOptimizedImage do, and when is it worth it?

Answer

NgOptimizedImage (stable since v15) is a directive you apply with ngSrc; it enforces the practices that actually move LCP: it requires explicit width/height (or fill) so the browser reserves space and CLS stays low, it lazy-loads by default, it generates a srcset so phones do not download desktop-sized images, and it warns in dev when an image is oversized or when the LCP image is lazy-loaded. Mark the hero image priority and it gets a preload link and eager loading. It also has loaders for common CDNs (Cloudflare, Imgix, Cloudinary…), so the CDN does format negotiation and resizing. It is worth it on any image-heavy page — which is most marketing and commerce pages — and it is one of the few optimisations that is genuinely close to free.

Example

<img ngSrc="/hero.jpg" width="1200" height="600" priority alt="Product hero">
<img ngSrc="/thumb.jpg" width="120" height="120" alt="">   <!-- lazy by default -->

Follow-ups

  • Why does it insist on dimensions? — Without them the browser cannot reserve layout space, which is the main source of CLS on image pages.
  • What does priority change? — Eager loading plus fetchpriority=high and a preload hint; use it only for the LCP image, never for many.
  • What about background images? — Not covered; either convert them to real images or preload them manually.

Common wrong answer

"It compresses the images for you." It does not touch the bytes; it orchestrates loading and (with a loader) asks your CDN for the right variant. Claiming otherwise leads to a follow-up about where the resizing happens that you cannot answer.

midLazy routes, @defer, or injectAsync — how do you choose?

Answer

By what the boundary is. A lazy route is the right unit when a whole area of the app is optional to the current user journey — it splits the bundle, gets its own injector, and matches how people navigate. @defer is for a region inside a page: a comments section, a chart, a rich editor that most users never open; it also gets you placeholder/loading/error states and viewport or interaction triggers for free. injectAsync (v22) is for a heavy service that only some code paths need — a PDF generator, a rules engine — where the component itself is small but its dependency is not. They compose: a lazy route containing deferred blocks whose services are injected asynchronously. The mistake to avoid is deferring things that are needed immediately, which just adds a network round trip to the critical path.

Example

// route: whole feature
{ path: 'reports', loadChildren: () => import('./reports/routes').then(m => m.ROUTES) }

// in-page region
// @defer (on viewport; prefetch on idle) { <app-report-chart /> } @placeholder { ... }

// heavy dependency of a small component
private pdf = injectAsync(() => import('./pdf').then(m => m.PdfEngine), { prefetch: onIdle() });

Follow-ups

  • How do you avoid a waterfall? — Prefetch: prefetch on idle or a route preloading strategy warms chunks before the interaction.
  • How many chunks is too many? — When request overhead and HTTP/2 concurrency start to dominate; measure, but dozens is fine, hundreds of tiny chunks is not.
  • What breaks lazy loading silently? — A static import of the lazy symbol somewhere else, which pulls it back into the eager chunk.

Common wrong answer

"Defer everything below the fold." Deferring the content that constitutes the LCP element makes LCP worse, and deferring dozens of tiny blocks trades bundle size for round trips. The expected answer names the boundary, not the technique.

seniorA grid with 5,000 rows is unusable. Walk me through fixing it.

Answer

Rendering 5,000 rows means 5,000 views, each with bindings, listeners and DOM — no change-detection strategy makes that fast. The fix is to stop rendering them: virtual scrolling (CDK's cdk-virtual-scroll-viewport for fixed-size rows, or a windowing implementation for variable heights) so only the visible window plus a buffer exists. Then remove per-row work: derive the display model once with a computed instead of calling formatting methods in the template, track by a stable id, and avoid per-row host listeners by delegating events at the viewport level. If sorting and filtering are done client-side, move them into a memoised computed — or to the server with paging — because re-sorting 5,000 objects on every keystroke is its own long task. Finally, verify with the profiler that the remaining cost is layout rather than change detection; if it is layout, the answer is simpler DOM per row, not more Angular tuning.

Example

<cdk-virtual-scroll-viewport itemSize="44" class="grid">
  <div *cdkVirtualFor="let row of rows(); trackBy: byId" class="row">
    {{ row.formatted }}   <!-- precomputed, no method call -->
  </div>
</cdk-virtual-scroll-viewport>

Follow-ups

  • Variable row heights? — Autosize strategy or a measured windowing library; fixed-size virtual scroll assumes uniform height.
  • Why not pagination? — Often the better product answer; say so — interviewers like candidates who question the requirement.
  • Where does a web worker help? — Filtering/sorting large datasets off the main thread, which directly improves INP.

Common wrong answer

"Use trackBy and OnPush." Both are necessary and neither is sufficient: you still create 5,000 views on first render. The interviewer is checking whether you know that the fix is rendering fewer things, not checking them more cleverly.

seniorThe initial bundle grew 400 kB in a quarter. How do you find out why?

Answer

Build with stats and read the chunk graph: ng build --stats-json plus source-map-explorer (or the esbuild metafile analyser) shows exactly which modules occupy the initial chunk. The usual culprits, in order of frequency: a utility library imported wholesale (a date or lodash-style package pulled in through a barrel file), a component that was supposed to be lazy but is statically imported somewhere — often in a shared index.ts, which is why barrels are a bundle-size hazard — a polyfill or locale set that nobody trimmed, and duplicated dependencies from mismatched versions in the lockfile. Then compare against the previous release's stats to see the delta rather than the absolute, and put a budget in CI so the next 400 kB fails a build instead of surviving a quarter.

Example

ng build --configuration production --stats-json
npx source-map-explorer dist/app/browser/*.js
# and in CI, fail on regression:
#   "budgets": [{ "type": "initial", "maximumError": "700kB" }]

Follow-ups

  • Why do barrel files hurt? — Importing one symbol from an index.ts can pull in the module graph of everything it re-exports, defeating the lazy boundary.
  • How do you find duplicates? — The stats output shows the same package at two versions; npm ls <pkg> confirms, and resolutions/overrides fix it.
  • Does tree-shaking always work? — Only for side-effect-free ESM; a package without "sideEffects": false or written in CommonJS often survives intact — the CLI warns about CommonJS dependencies for exactly this reason.

Common wrong answer

"Turn on production mode and AOT." Both have been the default for years. Answering with settings rather than with a measurement workflow suggests you have never actually opened a bundle analysis.

seniorUsers report the app "feels laggy" when typing and clicking, though load time is fine. What is your approach?

Answer

That is an INP problem: individual interactions are producing long tasks on the main thread. I would capture it in the field first (RUM with INP attribution tells you which element and which script), then reproduce with the browser's performance panel, looking for tasks over 50 ms and what dominates them — change detection, JSON parsing, a synchronous layout read, or a third-party script. Angular-specific fixes, in order: make the interaction's state a signal so only the affected views are checked, memoise derived data with computed instead of recomputing in templates, break up long synchronous work (chunking, requestIdleCallback, or a web worker for genuinely heavy transforms), and defer non-critical work with afterNextRender so it does not run inside the interaction. If a third-party analytics or chat widget owns the long task, the fix is loading strategy, not Angular. And remember hydration: on an SSR app, an interaction before hydration completes is queued — event replay (withEventReplay(), on by default for SSR apps since v20) is what stops those clicks being lost.

Example

// heavy transform off the main thread
const worker = new Worker(new URL('./filter.worker', import.meta.url), { type: 'module' });
readonly filtered = signal<Row[]>([]);
apply(filters: Filters) { worker.postMessage(filters); }   // worker posts back the result

Follow-ups

  • What is a "long task"? — Over 50 ms of uninterrupted main-thread work; a handful per interaction is what users feel as lag.
  • How does zoneless help? — Fewer, smaller change-detection passes per event, so the interaction's task is shorter.
  • When is a worker not worth it? — When the payload is large: structured-clone cost can exceed the computation you moved.

Common wrong answer

"Debounce the input." That hides the symptom on one field while every other interaction stays slow, and it makes the UI feel unresponsive in a different way. The expected answer identifies long tasks and their cause.

principalHow do you make performance a property of the team, not a project?

Answer

By making regressions fail loudly and cheaply, and by giving the numbers an owner. Concretely: bundle budgets per route in angular.json that fail CI, a synthetic performance check on the top three journeys in the pipeline, and RUM with p75 LCP/INP per route on a dashboard reviewed in the same meeting as error rates — a metric nobody looks at weekly is not a metric. Then a small number of rules that prevent the common regressions: no new eager dependency over a size threshold without a review, images through NgOptimizedImage, and new features that add to the initial chunk must justify it. Culturally, the thing that actually works is attribution: when a release moves p75 INP, the team that shipped it hears about it within a day, with the specific interaction named. Performance work that lives in a quarterly "perf sprint" always decays by the next quarter, because the incentive to add code never stops.

Example

# CI gate: build, budget, and a journey check
- run: ng build --configuration production            # budgets fail the build
- run: npx lhci autorun --collect.url=$PREVIEW/checkout
- run: node scripts/compare-bundle-stats.mjs base.json head.json --max-delta 25kB

Follow-ups

  • What if a budget blocks an urgent release? — Budgets have an override with an expiry and a ticket; a permanent override is a deleted budget.
  • How do you prioritise between features and performance? — Tie it to a business metric on one journey (conversion, task completion); "it feels slow" loses arguments, "checkout INP p75 is 480 ms" wins them.
  • How do you handle third-party scripts? — A review gate for anything loaded on the critical path, and a measured budget for the tag manager; it is usually the largest single regression source.
  • What is the first thing you would set up? — RUM per route. Without field data, every other decision is guesswork.

Common wrong answer

"We'd schedule a performance sprint each quarter." It is a treadmill: the app regresses between sprints and the same wins are re-won. The interviewer is listening for automation, ownership and continuous measurement.

11SSR, hydration and render modes

Server-side rendering shows up in about half of Angular loops and in nearly all of them for consumer-facing products. The questions are practical: what hydration is, why the console shows a hydration mismatch, and how you decide which routes are server-rendered at all. Angular's SSR story changed shape in v19–v22 — per-route render modes, event replay, and incremental hydration on by default in v22 — so an answer stuck on "we use Angular Universal" dates you by several years.

midWhat does Angular SSR actually give you, and how do you enable it?

Answer

ng add @angular/ssr (or ng new --ssr) sets up a server build and a Node server entry; the old "Angular Universal" naming was retired when the packages moved into @angular/ssr. What you get is HTML rendered on the server for the first response, which improves perceived load and makes content indexable by crawlers that do not execute JavaScript well, plus prerendering (SSG) for routes that do not depend on the request. What you do not get is a faster app overall: the JavaScript still downloads and hydrates, and a badly configured SSR setup can make INP worse because the page looks interactive before it is. The decision is therefore per product: content and commerce pages benefit, an internal dashboard behind a login usually does not.

Example

// app.config.server.ts
export const serverConfig: ApplicationConfig = {
  providers: [provideServerRendering(withRoutes(serverRoutes))],
};

// app.config.ts (client)
providers: [provideClientHydration()]   // v22: incremental hydration is on by default

Follow-ups

  • SSR vs prerender? — Prerender at build time for content that is the same for everyone; SSR per request when the HTML depends on the user or on fresh data.
  • What runs on the server? — Constructors, ngOnInit, content/view init hooks and effects; render callbacks (afterNextRender) do not.
  • Deployment shape? — A Node process (or an edge/serverless runtime); the CLI emits a server bundle plus the static browser assets.

Common wrong answer

"SSR makes the app faster." It improves first contentful paint and SEO; total interactivity time can get worse. Claiming a blanket speed-up invites the follow-up about hydration cost, which is where the answer usually falls apart.

midWhat is hydration, and what causes NG0500-family hydration errors?

Answer

Hydration is the client reusing the server-rendered DOM instead of throwing it away and re-rendering — "non-destructive" hydration, the default since v17 with provideClientHydration(). Angular walks the existing nodes and attaches its own view structures to them, which avoids the flash of re-rendered content and preserves scroll and focus. Mismatch errors (NG0500 and neighbours) mean the DOM the client expected does not match what the server produced. The usual causes: direct DOM manipulation on the server or before hydration, invalid HTML that the browser silently corrects (a <div> inside a <p>, or table markup without tbody), content that differs by environment such as Date.now(), Math.random() or a locale-dependent format, and third-party scripts mutating the DOM before Angular hydrates. The escape hatch is ngSkipHydration on the offending element, which re-renders that subtree destructively — useful for a stubborn third-party widget, and a smell everywhere else.

Example

<!-- third-party widget mutates its own DOM: skip it rather than fight it -->
<div ngSkipHydration><app-legacy-map /></div>

Follow-ups

  • Why is invalid HTML a problem? — The browser's parser fixes it, so the client DOM differs structurally from the string the server produced.
  • How do you handle time-dependent content? — Render a stable placeholder on the server and fill it in afterNextRender, or pass the server's timestamp through transfer state.
  • What is event replay? — withEventReplay() records clicks that happen before hydration and replays them afterwards; it is on by default for SSR apps since v20.

Common wrong answer

"Add ngSkipHydration to the app root." That disables hydration for the whole application, which throws away the benefit while keeping all of SSR's cost — and it is exactly what a rushed team does when it does not want to find the mismatch.

midExplain per-route render modes.

Answer

Since v19 (developer preview) and stable in v20, you declare a rendering strategy per route in a serverRoutes config: RenderMode.Prerender for build-time static generation (with getPrerenderParams for parameterised routes), RenderMode.Server for per-request SSR, and RenderMode.Client for routes that should not be server-rendered at all. That last one is the important addition: a logged-in dashboard or an admin area gains nothing from SSR and costs server CPU, so you opt it out explicitly rather than server-rendering the whole app. This replaces the old all-or-nothing Universal setup and lets a single app be part static site, part SSR, part SPA — which is what most real products actually want.

Example

export const serverRoutes: ServerRoute[] = [
  { path: '', renderMode: RenderMode.Prerender },
  { path: 'blog/:slug', renderMode: RenderMode.Prerender,
    getPrerenderParams: async () => (await getSlugs()).map(slug => ({ slug })) },
  { path: 'search', renderMode: RenderMode.Server },
  { path: 'app/**', renderMode: RenderMode.Client },   // authenticated SPA area
];

Follow-ups

  • How do you cache SSR responses? — At the CDN with a short TTL for anonymous traffic; per-user HTML must not be shared, so vary correctly or mark it private.
  • What about 404s and redirects? — Server routes can return status codes and headers, so the server render can respond correctly rather than rendering a client-side 404 with a 200.
  • Prerender with thousands of pages? — Prerender the top N and serve the tail with SSR plus caching; build time is the constraint.

Common wrong answer

"SSR is on or off for the whole app." True in the Universal era, not since v19. It is a good marker question because the fix — opting authenticated routes out — is the first thing a team does once they know it exists.

seniorWhat is incremental hydration, and what changed in v22?

Answer

Incremental hydration lets a server-rendered region stay dehydrated — visible HTML, no attached JavaScript — until a trigger fires, at which point Angular hydrates just that region and loads its chunk. It is expressed on @defer blocks with hydrate on interaction, hydrate on viewport, hydrate on idle, hydrate never, and it was developer preview in v19, stable in v20. In v22 it is enabled by default — provideClientHydration() activates it, and you opt out with withNoIncrementalHydration(). The payoff is exactly the INP problem SSR usually creates: instead of hydrating the whole page (and downloading all its JavaScript) before anything is interactive, you hydrate the parts users touch. hydrate never is the quiet winner for static content such as footers and marketing copy, which then costs nothing on the client at all.

Example

@defer (hydrate on interaction) {
  <app-comments [postId]="id()" />      <!-- server-rendered, JS loads on first click -->
} @placeholder {
  <p>Loading comments…</p>
}

@defer (hydrate never) { <app-footer /> }   <!-- rendered once on the server, never hydrated -->

Follow-ups

  • What is the risk of hydrate never? — Anything interactive inside it stays dead; use it only for genuinely static regions.
  • How does it interact with event replay? — Replay captures the click that triggers hydration so the interaction is not lost.
  • How do you verify it works? — DevTools network waterfall: the region's chunk should load on interaction, not on load.

Common wrong answer

"It's the same as lazy loading the component." Lazy loading means the HTML is not there either; incremental hydration ships the rendered HTML immediately and defers only the JavaScript — that difference is the entire point for LCP.

seniorYour app crashes on the server with "window is not defined". How do you structure code for SSR?

Answer

Treat browser globals as a platform capability, not an ambient assumption. Anything touching window, document, localStorage, navigator or a DOM measurement belongs either in afterNextRender/afterRenderEffect (which do not run on the server) or behind an explicit platform check with isPlatformBrowser(inject(PLATFORM_ID)). Third-party libraries that touch the DOM at import time must be loaded dynamically inside those callbacks. Beyond crashes, three SSR-specific concerns: state transfer, so the client does not refetch what the server already fetched (httpResource integrates with transfer state in v22); per-request isolation, because a service that caches into a module-level variable now shares data between users — a genuine security bug, not just a leak; and auth, because there is no browser storage on the server, so credentials must come from cookies forwarded into the render.

Example

export class Analytics {
  private isBrowser = isPlatformBrowser(inject(PLATFORM_ID));
  constructor() {
    afterNextRender(async () => {                       // browser only, post-render
      const { init } = await import('./vendor-sdk');
      init({ id: 'abc' });
    });
  }
  track(e: string) { if (this.isBrowser) window.dataLayer?.push({ e }); }
}

Follow-ups

  • Why is a module-level cache dangerous on the server? — The process is shared across requests, so user A's data can be served to user B; caches must be request-scoped.
  • How do you debug server-only failures? — Run the SSR build locally with source maps and reproduce with the same request headers; the browser will never show you the error.
  • What about setTimeout on the server? — Pending timers delay or block the render; keep timers browser-only.

Common wrong answer

"Wrap it in typeof window !== 'undefined'." It stops the crash and hides the design problem: the code still runs in both environments with different behaviour, and the SSR-specific bugs (state leakage, missing transfer state) remain. The platform token and render callbacks exist to make the boundary explicit.

principalShould we adopt SSR? Give me the decision framework.

Answer

I would start from what SSR is for: content that must be indexable, shareable with rich previews, or visible fast on a slow device for users who have not visited before. If the app is behind a login and used repeatedly by the same people, SSR buys almost nothing and adds a server tier, a second runtime environment, hydration bugs and a new class of security concern (per-request isolation). So the framework is: identify the routes where first-visit paint or crawlability has business value, apply SSR or prerender to exactly those with per-route render modes, and leave the authenticated app client-rendered. Then cost it honestly — infrastructure, on-call, build complexity and the engineering time hydration issues will take — and compare against the cheaper alternatives first: better bundle splitting, an edge-cached static shell, and image optimisation often deliver most of the perceived-performance win with none of the operational surface. If we do adopt it, prerender before SSR wherever the content allows, because static files have no runtime failure mode.

Example

// the shape most products end up with
export const serverRoutes: ServerRoute[] = [
  { path: '',            renderMode: RenderMode.Prerender },  // marketing: static
  { path: 'product/:id', renderMode: RenderMode.Server },     // indexable, fresh
  { path: 'account/**',  renderMode: RenderMode.Client },     // authenticated: no SSR
];

Follow-ups

  • What is the operational cost? — A Node/edge tier to scale, deploy and monitor; server render latency becomes part of your TTFB budget.
  • How do you measure whether it worked? — p75 LCP and organic traffic on the SSR routes, compared with the pre-SSR baseline; if neither moves, reconsider.
  • What is the biggest hidden risk? — Per-request state leakage between users; it must be an explicit review item, not an assumption.
  • Any middle ground? — Prerendering plus a static shell; it captures much of the SEO and first-paint value with no server runtime.

Common wrong answer

"Yes — SSR is best practice for modern apps." It is a trade, not a default, and for a logged-in product it is usually a net cost. A principal-level answer names the routes, the metric and the operational bill.

12Testing

Testing questions are asked less often than change detection but they are highly diagnostic: what someone tests, and what they refuse to test, says more about their engineering judgment than any API question. The Angular specifics moved recently — Vitest replaced Karma as the default runner in v21 and zoneless changed how you wait for stability — so this is another place where a 2021 answer is visible immediately.

midWhat is the current test setup for a new Angular app?

Answer

Since v21 the default is Vitest via the @angular/build:unit-test builder; Karma was deprecated in v20 and is no longer the generated default. Practically that means ESM-native, much faster startup, watch mode that only re-runs affected tests, first-class fake timers (vi.useFakeTimers()), snapshot testing, and the option of browser mode with Playwright when you need a real browser rather than jsdom. Jasmine-style specs largely carry over, and there is a migration schematic (ng g @schematics/angular:refactor-jasmine-vitest) for the mechanical differences — jasmine.createSpy to vi.fn, and so on. TestBed itself is unchanged, so the framework-level knowledge transfers; what changes is the runner, the mocking API and the speed.

Example

import { TestBed } from '@angular/core/testing';
import { describe, it, expect, vi } from 'vitest';

describe('Counter', () => {
  it('increments', async () => {
    const fixture = TestBed.createComponent(Counter);
    await fixture.whenStable();
    fixture.componentInstance.inc();
    await fixture.whenStable();
    expect(fixture.nativeElement.textContent).toContain('1');
  });
});

Follow-ups

  • Is Jest supported? — Widely used in the community and via third-party builders, but the CLI's own path is Vitest; Angular's experimental Jest builder was superseded.
  • What about E2E? — Protractor was deprecated in v12 and removed in v16; the CLI integrates Playwright/Cypress/WebdriverIO through third-party builders.
  • Browser mode or jsdom? — jsdom for speed; browser mode when you test layout, real events, or anything jsdom stubs badly.

Common wrong answer

"We use Karma and Jasmine, that's the Angular standard." It was the standard for a decade and is now deprecated and not the default. Saying it without noting the change is a clean date-stamp on your last project.

midHow do you test a component that uses signals and httpResource?

Answer

Configure the TestBed with provideHttpClient() and provideHttpClientTesting(), create the component, then drive it: set input signals with fixture.componentRef.setInput(), flush the expected request through HttpTestingController, and await stability before asserting on the DOM. The important difference from the old style is the awaiting: with signals and zoneless, you wait for fixture.whenStable() rather than calling detectChanges() synchronously and hoping. Assert through the rendered output where the behaviour is user-visible, and directly on computed() values where the logic is pure — computeds are synchronous and are the cheapest thing in the codebase to test. Finish with httpTesting.verify() so an unexpected extra request fails the test rather than passing silently.

Example

TestBed.configureTestingModule({
  providers: [provideHttpClient(), provideHttpClientTesting()],
});
const httpTesting = TestBed.inject(HttpTestingController);
const fixture = TestBed.createComponent(UserCard);
fixture.componentRef.setInput('userId', '42');
await fixture.whenStable();

httpTesting.expectOne('/api/users/42').flush({ name: 'Ada' });
await fixture.whenStable();
expect(fixture.nativeElement.textContent).toContain('Ada');
httpTesting.verify();

Follow-ups

  • Why setInput and not assigning the field? — It goes through the input machinery (transforms, dirty marking); assigning bypasses both.
  • Do effects run in tests? — Only once change detection runs; await fixture.whenStable() (or TestBed.tick()) flushes them, which is why logic in effects makes tests harder.
  • How do you test a service's resource? — Create it inside TestBed.runInInjectionContext() so it has an injector, then flush as above.

Common wrong answer

"Mock the whole service with a spy that returns a hard-coded signal." Sometimes right, but as a default it tests your mock: the request URL, the params and the error path — the parts that actually break — are never exercised.

midWhat changed about async testing in a zoneless app?

Answer

fakeAsync/tick and waitForAsync are Zone.js features: they work by patching and draining the zone's task queues, so in a zoneless app they no longer do what people expect. The replacement is await fixture.whenStable(), which resolves when Angular has finished its pending work, combined with the runner's own timer control (vi.useFakeTimers() plus vi.advanceTimersByTime()) when you need to control time explicitly. fixture.detectChanges() still exists, but with signals you rarely need it — whenStable covers scheduling, effects and rendering in one await. Practically this makes tests read more like the application: no magic tick counts, and no tests that pass only because a tick(1) happened to land in the right place.

Example

vi.useFakeTimers();
const fixture = TestBed.createComponent(Debounced);
fixture.componentInstance.query.set('ang');
vi.advanceTimersByTime(300);          // control time explicitly
await fixture.whenStable();           // let Angular settle
expect(fixture.componentInstance.results()).toHaveLength(3);

Follow-ups

  • Does fakeAsync still work at all? — In apps that still use Zone.js, yes; it is not a general tool any more.
  • What about flushMicrotasks? — Same story; prefer awaiting real promises plus whenStable.
  • How do you test something driven by afterNextRender? — It runs during change detection in the browser test environment; await stability and assert afterwards.

Common wrong answer

"Wrap everything in fakeAsync and add tick() until it passes." That was already a bad habit under Zone.js and is now simply broken; tests that pass by tuning tick counts are the classic source of a flaky suite.

seniorWhat do you test at the component level, and what do you not?

Answer

I test behaviour that a user or a caller can observe: given inputs and interactions, what is rendered, what is emitted, what request is made. I do not test implementation details — private methods, which lifecycle hook ran, whether a specific internal signal has a value — because those tests break on every refactor while catching nothing. Pure logic (a computed, a formatter, a reducer) gets fast unit tests with no TestBed at all; interaction-level behaviour gets a component test that queries the DOM the way a user would (accessible role and text, not CSS classes); and cross-page journeys get a small number of E2E tests. Component test harnesses (from the CDK, and provided by Angular Material) are worth naming: they give a stable API for driving a component in tests so an internal DOM change does not break every consumer's suite.

Example

// behaviour, not internals
const button = fixture.nativeElement.querySelector('button[type=submit]');
button.click();
await fixture.whenStable();
expect(saved).toHaveBeenCalledWith({ email: 'a@b.c' });   // observable outcome

Follow-ups

  • Why query by role/text? — It survives markup refactors and asserts something a user could actually perceive; class selectors couple tests to styling.
  • What is a harness? — A test-facing API over a component (MatButtonHarness and friends) so consumers do not reach into its DOM.
  • How much E2E? — Enough to cover the money paths; they are the slowest and flakiest layer, so their value has to be paid for in coverage of things unit tests cannot see.

Common wrong answer

"Aim for 100% coverage of every component." Coverage as a target produces tests written for the metric — asserting that a setter sets — while the real risk sits in integration. Interviewers ask this to hear a risk-based strategy, not a number.

seniorHow do you test guards, interceptors and resolvers now that they are functions?

Answer

Because they are functions that call inject(), you run them inside an injection context: TestBed.runInInjectionContext(() => myGuard(route, state)) with the dependencies provided or faked in the TestBed. That is simpler than the class era, where you instantiated the guard with mocked constructor arguments. For interceptors, the more valuable test is an integration one: configure provideHttpClient(withInterceptors([authInterceptor])) together with provideHttpClientTesting(), make a request, and assert on the intercepted request that HttpTestingController captures — which verifies the header, the URL matching and the retry behaviour together rather than the function in isolation. Guards returning a UrlTree are asserted by comparing router.serializeUrl(result) with the expected path.

Example

TestBed.configureTestingModule({
  providers: [provideHttpClient(withInterceptors([authInterceptor])), provideHttpClientTesting(),
              { provide: Auth, useValue: { token: () => 'tok' } }],
});
TestBed.inject(HttpClient).get('/api/me').subscribe();
const req = TestBed.inject(HttpTestingController).expectOne('/api/me');
expect(req.request.headers.get('Authorization')).toBe('Bearer tok');

Follow-ups

  • How do you fake ActivatedRouteSnapshot? — A minimal object literal cast to the type; guards usually read only paramMap and data.
  • Testing a resolver's error path? — Provide a failing service and assert the returned UrlTree or thrown error.
  • Do you test route configuration itself? — Lightly, with the RouterTestingHarness, for guard wiring and redirects — the parts that fail silently in production.

Common wrong answer

"Call the guard function directly with mock arguments." It throws NG0203 the moment it calls inject(); needing the injection context is the whole difference from the class-based era.

principalDefine the test strategy for a 200k-line Angular app with a slow, flaky suite.

Answer

First, measure the suite like a product: runtime, flake rate per spec, and which specs fail most often. Then act on the shape rather than the total. Typically you find a heavy middle — thousands of component tests that mount half the app because of a shared testing module — and a thin, slow E2E layer that everyone distrusts. My plan: quarantine flaky specs immediately (tagged, tracked, with an owner and a deadline — not deleted, not left failing), because a suite people ignore has zero value; move pure logic out of components so it can be tested without TestBed; replace deep mounting with shallow tests plus harnesses; and cut E2E to the money paths, run on a schedule and on release branches rather than blocking every PR. Structurally, upgrading to the Vitest builder is worth doing for the wall-clock alone, and running affected-only tests (Nx or a similar graph) keeps PR feedback under a few minutes. The target I would state out loud: PR feedback under 10 minutes, flake rate under 1%, and no test that nobody can explain the purpose of.

Example

# PR: fast, affected-only. Nightly: full suite + E2E on the money paths.
npx nx affected -t test --parallel=4
npx playwright test --project=chromium tests/e2e/checkout.spec.ts

Follow-ups

  • How do you handle a flaky test nobody owns? — Quarantine with an expiry; if the deadline passes with no owner, delete it and record the coverage gap. Permanently quarantined tests are technical debt with a false sense of safety.
  • How do you stop the middle growing back? — A convention that components are thin, plus review attention on any new test that mounts more than its subject.
  • What about contract tests with the backend? — Generate the client from the spec and test against recorded fixtures; it catches drift that mocks never will.
  • How do you show it worked? — Suite runtime, flake rate, and escaped-defect count per release — three numbers on the same dashboard as performance.

Common wrong answer

"Add more E2E tests so we catch real bugs." Scaling the slowest, flakiest layer makes the trust problem worse; the expected answer rebalances the pyramid and treats flakiness as a first-class defect.

13State management and app architecture

Once you are interviewing above mid level, "how do you manage state" is asked in every Angular loop, and the expected answer is no longer a library name. Since signals landed, the honest position is that most apps need far less global state machinery than they used to, and the interesting judgment is where each piece of state lives and who owns it. Expect a scenario — optimistic updates, cross-feature data, undo — rather than a definition.

midNgRx, a signal store, or plain services — how do you choose?

Answer

Start from the problem, not the library. Most state in an app is either server state (data you fetched, which wants caching, invalidation and loading/error status — resources or a query layer, not a store) or local UI state (which panel is open — a signal in the component). What is left is genuinely shared client state: a shopping cart, a multi-step wizard, an editor's undo stack. For that, a service with signals is usually enough and is what I would default to now. NgRx earns its ceremony when you need what it uniquely provides: a serialisable action log for time-travel debugging and audit, strict unidirectional flow across many teams, or complex effect orchestration; NgRx SignalStore is the modern middle ground, giving store structure with signal ergonomics and far less boilerplate than the classic actions/reducers/selectors triad. The failure mode to name unprompted: putting server data in a global store, which turns caching into a hand-rolled reimplementation of HTTP semantics.

Example

// the default I reach for: a scoped service with signals
@Injectable()
export class CartStore {
  private readonly items = signal<CartItem[]>([]);
  readonly lines = this.items.asReadonly();
  readonly total = computed(() => this.items().reduce((s, i) => s + i.price * i.qty, 0));
  readonly count = computed(() => this.items().length);

  add(item: CartItem) { this.items.update(list => [...list, item]); }
  remove(id: string)  { this.items.update(list => list.filter(i => i.id !== id)); }
}

Follow-ups

  • What does asReadonly() buy you? — The write API stays inside the owner; consumers cannot bypass its invariants.
  • When is NgRx clearly right? — Auditable action history, many teams touching the same state, or existing investment and expertise.
  • Does NgRx work with signals? — Yes: selectors are exposed as signals, so components look identical either way — which means the migration decision is not urgent.

Common wrong answer

"Every Angular app should use NgRx for consistency." That was common advice in 2018 and produced enormous boilerplate for CRUD apps. Interviewers now treat an unconditional store recommendation as a lack of judgment, not as rigour.

midWhat does a signal-based store look like, and what does it have to guarantee?

Answer

Structurally: private writable signals for state, public read-only signals and computeds for the view, and methods that are the only way to change anything — a small, testable object with no framework ceremony. The guarantees that make it a store rather than a bag of signals: one owner per piece of state, invariants enforced in the methods (you cannot set a negative quantity), derived values as computed so they cannot drift, and a defined lifetime — root for genuinely global, route-provided for feature state that should reset. NgRx SignalStore formalises the same shape with signalStore(), withState, withComputed, withMethods, plus entity helpers, which is worth adopting when you have many similar stores and want consistency. The test for whether it is a good store: can you unit-test it with no TestBed and no DOM? A signal store should be a plain class you construct and assert on.

Example

export const WizardStore = signalStore(
  { providedIn: 'root' },
  withState({ step: 0, answers: {} as Record<string, string> }),
  withComputed(({ step }) => ({ isLast: computed(() => step() === STEPS.length - 1) })),
  withMethods((store) => ({
    answer(key: string, value: string) {
      patchState(store, (s) => ({ answers: { ...s.answers, [key]: value } }));
    },
    next() { patchState(store, (s) => ({ step: Math.min(s.step + 1, STEPS.length - 1) })); },
  })),
);

Follow-ups

  • How do you handle async in a signal store? — Methods returning promises, or a resource inside the store; keep the loading state in the store so views do not each invent one.
  • How do you debug it? — Angular DevTools' signal graph (v22 improved the inspection UI); for action-level history you need a store that records actions.
  • Deep state? — Keep it shallow and normalised; nested object updates with spread are where signal stores get ugly.

Common wrong answer

"Expose the writable signals publicly, it's less code." Then any component can write, invariants live nowhere, and the "who changed this" question becomes unanswerable — the exact failure that made people adopt stores in the first place.

seniorWhere does server data belong, and what makes it different from client state?

Answer

Server data is a cache of something you do not own, and that is the distinction people miss. It can be stale, it needs refetching, deduplication, loading and error status, and invalidation after mutations — none of which are properties of client state like "which tab is open". Treating it as client state means hand-writing cache invalidation inside reducers, which is how apps end up with a 2,000-line store and a bug queue about stale data. So: server data lives in a data-access layer built on resources or a query library, keyed by its request; client state lives in signals owned by a component, a scoped service, or a store. The interaction between them should be explicit — a mutation calls the API and then invalidates or reloads the affected resources — rather than the store trying to keep its own copy in sync with the server.

Example

// server data: keyed, reloadable, has status
readonly order = httpResource<Order>(() => `/api/orders/${this.id()}`);

// client state: owned locally
readonly selectedLines = signal<Set<string>>(new Set());

async cancel() {
  await this.api.cancel(this.id());
  this.order.reload();                     // explicit invalidation
  this.selectedLines.set(new Set());       // client state reset is a separate decision
}

Follow-ups

  • How do you keep two views consistent after a mutation? — Invalidate the shared resource key, or bump a version signal both depend on; never copy the value into two places.
  • Do you ever put server data in the store? — When it is genuinely part of a client workflow (an editable draft), it becomes client state once the user starts editing — that transition should be explicit.
  • Real-time updates? — Push into the same owner (a websocket updating the resource's value), so there is still exactly one source.

Common wrong answer

"Everything goes in the store so there's one source of truth." The server is the source of truth; the store is a copy that must now be invalidated by hand. Interviewers ask this specifically to see whether you distinguish caching from state.

seniorImplement an optimistic update with rollback. What can go wrong?

Answer

Apply the change locally immediately, keep the previous value, call the server, and on failure restore and tell the user. The parts people miss: concurrency, where two optimistic updates overlap and a rollback restores a value that a later update already changed — so you version the state or apply rollbacks as inverse operations rather than snapshots; idempotency, so a retry does not double-apply; and reconciliation, because the server's response is authoritative and may differ from your optimistic guess (a computed total, a normalised address). Also decide what "failure" looks like in the UI: a silent revert confuses people, so revert plus an explicit, dismissible message with a retry is the usable pattern. When there are many overlapping mutations — a drag-and-drop board, a collaborative editor — the honest answer is that you want a proper sync layer with operation logs, not per-call optimism.

Example

async toggleDone(id: string) {
  const before = this.items();
  this.items.update(list => list.map(i => i.id === id ? { ...i, done: !i.done } : i));
  try {
    const saved = await this.api.toggle(id);       // server is authoritative
    this.items.update(list => list.map(i => i.id === id ? saved : i));
  } catch (e) {
    this.items.set(before);                        // rollback
    this.toast.error('Could not save — try again');
  }
}

Follow-ups

  • Why is a whole-state snapshot risky? — It reverts unrelated changes made while the request was in flight; per-item rollback or an inverse operation is safer.
  • When do you skip optimism? — Money, irreversible actions, and anything where showing a wrong intermediate state is worse than a spinner.
  • How do you test it? — Force the failure path in tests; the rollback branch is exactly the code that is never exercised manually.

Common wrong answer

"Update the UI and refetch the list afterwards." Refetching hides the failure until the next render, produces a visible flicker, and on a slow connection lets the user act on state that was never persisted.

seniorHow do you structure a large Angular codebase — folders, boundaries, shared code?

Answer

By feature, with explicit boundaries, and with "shared" kept deliberately small. A structure that scales: features/<name> owning its routes, components, state and data access; shared/ui for presentational components with no domain knowledge; core (or a kernel library) for cross-cutting infrastructure — auth, config, telemetry, error handling. The rules that matter more than the folder names: features never import from other features, everything crossing a boundary goes through a public entry point (index.ts that is genuinely the API, not a barrel of everything), and the boundary is enforced by lint (Nx tags, or ESLint no-restricted-imports) so it fails in CI rather than in review. The classic anti-pattern to name: a SharedModule or shared barrel that everything imports, which grows until it is effectively the whole app and destroys lazy loading — every lazy chunk pulls it in.

Example

src/app/
  core/            auth, config, http interceptors, error handling
  shared/ui/       presentational components, no domain imports
  features/
    orders/        routes.ts, pages/, data/, state/, ui/   (public API: index.ts)
    catalog/
  app.routes.ts    only lazy references to features

Follow-ups

  • Where do types shared by two features live? — A domain-model library both depend on, not in one of the features.
  • How do you keep shared from growing? — A rule that anything domain-aware cannot live there, plus periodic review of what actually has more than one consumer.
  • Nx or plain CLI? — Nx buys enforced boundaries, affected-only CI and generators; a plain CLI workspace with lint rules is fine for a single team.

Common wrong answer

"Group by type: components/, services/, pipes/." It works up to about thirty files and then every change touches four directories, code review loses locality, and nothing tells you what the app does. Interviewers see this as a sign of never having worked in a large codebase.

principalA five-year-old NgRx codebase, 300 actions, and the team says state is unmaintainable. What do you do?

Answer

Diagnose before prescribing: "unmaintainable" usually means one of three specific things, and each has a different fix. If the pain is boilerplate per feature, the fix is createFeature/entity adapters or NgRx SignalStore — same architecture, far less typing, no migration of behaviour. If the pain is that server data lives in the store and cache invalidation is hand-written across dozens of effects, the fix is to move server data out to a resource/query layer feature by feature, which typically deletes the majority of the actions. If the pain is that nobody can find where a value changes, the fix is boundaries — split one global store into feature stores with owners — not a different library. I would pick the highest-pain feature, do one of these end to end, and measure: lines removed, time to add a field, bugs in that area. Only then decide whether to scale it. What I would not do is a wholesale rewrite to signals: 300 actions represent years of edge cases, and a translation project has no user-visible outcome to defend when it runs late.

Example

// typical result of the "server data leaves the store" step:
// deleted: loadOrders, loadOrdersSuccess, loadOrdersFailure, selectOrders,
//          selectOrdersLoading, selectOrdersError, ordersEffects
readonly orders = httpResource<Order[]>(() => ({ url: '/api/orders', params: this.filters() }));

Follow-ups

  • How do you avoid two paradigms confusing people? — Migrate whole features, never half a feature, and document which layer owns what.
  • What if the team just dislikes NgRx? — Preference is not a business case; ask for the three numbers (time to add a feature, defect density, onboarding time) and let them decide the priority.
  • How do you keep time-travel debugging if you lose it? — Most teams never used it; if it is genuinely load-bearing for audit, keep the store for that domain.
  • What is the stopping rule? — If the pilot feature does not measurably improve, stop and fix the boilerplate instead.

Common wrong answer

"Replace NgRx with signals across the app this quarter." It is a rewrite of the most stateful code in the product with no user-facing benefit, and it is the answer that most reliably fails a principal-level architecture question.

14Build tooling, CLI and upgrades

Tooling questions are a proxy for whether you have owned an app rather than just written components: can you keep a codebase on a supported version, do you know what the build actually does, and can you explain why CI takes eleven minutes. Angular's build story changed completely between v16 and v22 — esbuild/Vite replaced webpack as the default, and webpack builders were deprecated in v22 — so this is fertile ground for "are you current" questions.

midWhat builds an Angular app today, and what happened to webpack?

Answer

The @angular/build:application builder — esbuild for bundling, Vite for the dev server and HMR — has been the default for new apps since v17 and is what ng build and ng serve run. In v22 the webpack-based builders are deprecated, including @angular-devkit/build-angular and @ngtools/webpack, so remaining webpack apps are now on a clock rather than in a supported steady state. Practically, the migration is usually a builder swap in angular.json plus rework of anything that depended on a custom webpack config (ngx-build-plus, custom loaders, Module Federation setups). What you get is dramatically faster cold builds and rebuilds, plus a single build pipeline for browser, server and prerendered output. On the roadmap, the team is prototyping the TypeScript compiler port (tsgo) for a further 5–10× type-checking speedup — worth mentioning as direction, not as something to depend on.

Example

"architect": {
  "build": {
    "builder": "@angular/build:application",
    "options": { "browser": "src/main.ts", "server": "src/main.server.ts",
                 "outputMode": "server", "ssr": { "entry": "src/server.ts" } }
  }
}

Follow-ups

  • What breaks in the migration? — Custom webpack configs, some polyfill and CommonJS assumptions, and Module Federation setups that need the native-federation equivalent.
  • Is AOT still a thing? — Yes, and it has been the default for production and development since v9; there is no JIT path to choose in a normal app.
  • What is ng serve doing differently? — Vite dev server with native ESM and on-demand transformation, which is why the first paint after a change is near-instant.

Common wrong answer

"Angular uses webpack." True until v16 and false for every new app since; combined with a mention of ng eject (removed years ago) it dates a candidate precisely.

midHow does the Angular release and support cycle work, and how do you upgrade?

Answer

Two major releases a year, roughly May and November, each with 6 months of active support and 12 months of LTS — an 18-month window. So on today's calendar, v22 (GA 2026-06-03) is in active support, v21 and v20 are in LTS, and anything v19 or older is out of support and receiving no security patches. Upgrading is ng update @angular/core@N @angular/cli@N, one major at a time, never skipping — the schematics for each version run in sequence and do the mechanical work. The practices that make it uneventful: upgrade in its own PR with no feature changes, keep the app deployable after each major, read the update guide's "breaking changes" for your version pair before starting, and do it on a cadence (every release, not every third) because the cost of three majors at once is far more than three times one.

Example

npx @angular/cli@22 update @angular/core@22 @angular/cli@22
# then, separately:
ng update @angular/material@22
npm run test && npm run e2e

Follow-ups

  • What if a dependency is not compatible? — --force is a last resort; better to pin, fork, or replace the dependency, and to weight compatibility when choosing libraries.
  • How do you handle Node and TypeScript? — Each major sets minimums; v22 requires TypeScript 6 and drops Node 20, so the toolchain upgrade is part of the plan.
  • What does the update guide give you? — A version-pair diff of breaking changes and required actions at angular.dev/update-guide.

Common wrong answer

"We skip versions and jump straight from 17 to 22." The migrations are sequential; jumping means running none of the intermediate schematics and debugging the compound result by hand. Interviewers ask this because it is the difference between a two-day upgrade and a two-month one.

seniorCI takes 25 minutes for a one-line change. What do you do?

Answer

Break the number down first — install, lint, test, build, e2e — because the fix differs entirely by segment. Typical wins in order of payoff: cache dependencies and build artefacts properly (a cold npm ci on every job is often minutes); run only what the change affects (Nx or a similar task graph with affected, plus remote caching so a build another PR already produced is reused); parallelise across shards; move E2E off the PR path onto merge queues or nightly, keeping only a smoke subset blocking; and switch the unit suite to the Vitest builder if it is still Karma, which alone tends to halve it. Then make it stay fast: a CI duration budget with an alert, because the same erosion that grows bundles grows pipelines.

Example

npx nx affected -t lint test build --parallel=4   # only projects touched by the change
# with remote cache configured, unchanged projects are restored, not rebuilt

Follow-ups

  • What makes caching miss? — Non-deterministic inputs: timestamps, install-time codegen, environment variables baked into the build.
  • Is a monorepo the cause? — Only without a task graph; with one, a monorepo is what makes affected-only builds possible.
  • How fast is fast enough? — Under 10 minutes for PR feedback is the usual threshold before people start context-switching away.

Common wrong answer

"Buy bigger CI machines." It helps a little and hides the structural problem; running the whole suite for every one-line change is the actual defect, and hardware does not fix an O(repo) pipeline.

seniorWhat tooling does the Angular CLI ship for AI-assisted development, and would you use it?

Answer

The CLI ships an MCP server (ng mcp), expanded in v21, exposing tools such as search_documentation, find_examples, get_best_practices, list_projects, an ai_tutor, and migration helpers including onpush_zoneless_migration and an experimental modernize tool — so an assistant can consult current Angular documentation and run official migrations rather than reproducing 2019 patterns from its training data. v22 also adds experimental WebMCP support (provideExperimentalWebMcpTools(), provideExperimentalWebMcpForms()), which exposes app-level tools and Signal Forms to in-browser agents. My position for a team: yes for the documentation and migration tools, because the failure mode of AI-generated Angular is confidently outdated patterns and this directly addresses it; treat WebMCP as experimental and think about the security surface before exposing application tools to an agent — anything an agent can invoke is something a prompt-injected page can try to invoke.

Example

ng mcp                       # start the MCP server for your editor/assistant
ng mcp --experimental-tool modernize
ng update @angular/core@22 --dry-run   # still the source of truth for migrations

Follow-ups

  • Why does this exist? — Angular's API surface changed faster than model training data; the team's stated roadmap goal is improving the AI development experience.
  • What do you still review by hand? — Anything touching change detection, security, or public API of shared libraries.
  • Risk of WebMCP? — It gives agents in the page the ability to act; treat it as an authenticated capability surface, not a convenience.

Common wrong answer

"We don't use AI tooling, it writes bad Angular." Often true of a bare model, which is exactly the gap the CLI's MCP tools close. A flat rejection reads as incuriosity; the credible answer names where you trust it and where you do not.

principalHow do you keep a portfolio of Angular apps permanently on a supported version?

Answer

Make upgrading routine and boring rather than a project. Concretely: a standing calendar commitment — every major, within a fixed window of its release, owned by a named engineer on rotation; a shared upgrade runbook so it is not rediscovered each time; and dependency policy that keeps the path clear (prefer libraries that track Angular releases, and treat "not yet compatible" as a procurement issue rather than a surprise). Automate what can be automated: Renovate/Dependabot for patches, a canary app that upgrades first and surfaces breakage for everyone else, and CI running the next version's release candidate weekly so incompatibilities appear before the release, not after. Then make status visible: a dashboard of app versus supported version, reviewed alongside security posture, because "out of support" is a security fact and not merely a tidiness one. The reason to be this deliberate is arithmetic — 18 months of support means an app that upgrades once a year is always fine and an app that upgrades every two years is permanently behind.

Example

v22  GA 2026-06-03  active support -> ~Dec 2026, LTS -> ~Jun 2028
v21  GA 2025-11-19  LTS
v20  GA 2025-05-28  LTS (ends ~Nov 2026)
v19 and older       unsupported: no security patches

Follow-ups

  • What about an app nobody owns? — Assign an owner or schedule its decommissioning; an unowned production app on an unsupported version is a risk item, not a neutral state.
  • How do you fund it? — As a fixed cost of ownership, budgeted like on-call, not as feature work competing for priority.
  • How do you handle a blocking third-party library? — Fork or replace it; make compatibility with the Angular release cadence a selection criterion going forward.
  • What is the leading indicator of trouble? — Time since last major upgrade per app; anything over 12 months is heading for a painful jump.

Common wrong answer

"We upgrade when we need a new feature." That is how apps end up four majors behind, at which point the upgrade is a quarter of work and the security exposure has been real for a year. The expected answer is a cadence with an owner.

15Security

Security questions in a frontend interview are usually one XSS question and one "where do you keep the token" question, and both have a right answer that many candidates miss. What raises the score is separating what the framework protects you from automatically, what it cannot protect you from, and what must be enforced on the server regardless of anything the client does.

midHow does Angular protect against XSS, and where does that protection stop?

Answer

Angular treats all values as untrusted by default and sanitises them per context: interpolation escapes HTML, and binding to [innerHTML], [style], [href] or [src] runs the value through a contextual sanitiser that strips scripts, event handlers and dangerous URLs. That covers the overwhelming majority of real cases, which is why XSS in Angular apps is usually the result of someone deliberately opting out. The protection stops at four places: bypassSecurityTrustHtml and its siblings, which disable sanitisation for that value; direct DOM manipulation (nativeElement.innerHTML, document.write), which never reaches the sanitiser; dynamically constructed templates or server-supplied expressions, which is code execution by design; and third-party libraries that inject markup themselves. The rule I would give a team: any call to bypassSecurityTrust* needs a comment justifying it and a review, because that is where the vulnerability will be.

Example

// ✅ sanitised automatically
// <div [innerHTML]="userSuppliedHtml"></div>

// ❌ opts out of sanitisation — must be justified
readonly trusted = this.sanitizer.bypassSecurityTrustHtml(userSuppliedHtml);

// ✅ if you must render rich text, sanitise with an allow-list first
readonly safe = this.sanitizer.sanitize(SecurityContext.HTML, dompurify.sanitize(input));

Follow-ups

  • What is Trusted Types? — A browser policy (enforced via CSP) that blocks assignment of raw strings to dangerous DOM sinks; Angular supports it, and it converts "someone bypassed the sanitiser" from a code-review issue into a browser-enforced one.
  • Does sanitisation run on the server? — Yes, SSR output is sanitised the same way; the risk with SSR is injecting unsanitised server data into the HTML shell yourself.
  • What about URLs? — javascript: URLs are stripped in href/src bindings; building URLs by string concatenation from user input is still your problem.

Common wrong answer

"Angular sanitises everything, so XSS isn't possible." It is precisely possible through the bypass APIs and direct DOM access — and a candidate who believes the framework is a complete defence is the one who will approve the PR that introduces it.

midWhere do you store auth tokens, and how does CSRF protection work here?

Answer

The safest option is an httpOnly, Secure, SameSite cookie issued by the server, because JavaScript — including injected JavaScript — cannot read it. The trade is that cookies are attached automatically, so you need CSRF protection: Angular's HttpClient supports the double-submit pattern out of the box, reading a cookie (default XSRF-TOKEN) and sending it as a header (default X-XSRF-TOKEN) on mutating same-origin requests, configurable through withXsrfConfiguration(). If you must use bearer tokens, keep the access token in memory with a short lifetime and the refresh token in an httpOnly cookie; localStorage is the option to argue against, because any XSS — including one in a third-party script you did not write — reads it and exfiltrates a long-lived credential. Say the boundary out loud: the server validates every request regardless; nothing the client stores or checks is a security control.

Example

provideHttpClient(
  withXsrfConfiguration({ cookieName: 'XSRF-TOKEN', headerName: 'X-XSRF-TOKEN' }),
);

Follow-ups

  • Why does SameSite matter? — Lax/Strict blocks most cross-site cookie sending, which removes a large part of the CSRF surface — but not all of it, so keep the token check.
  • Cross-origin API? — Cookies need CORS with credentials and a matching origin allow-list; that is often why teams reach for bearer tokens instead.
  • What about SSR? — The server render must forward the request's cookies to the API; there is no browser storage on the server.

Common wrong answer

"localStorage is fine as long as we prevent XSS." Every app with third-party scripts has an XSS surface it does not fully control, and a token in localStorage is readable by all of them. The expected answer names httpOnly cookies first and treats in-memory as the fallback.

seniorHow do you deploy an Angular app under a strict Content Security Policy?

Answer

The main friction is styles: Angular injects component styles at runtime, so a policy without 'unsafe-inline' for style-src needs a nonce — set ngCspNonce on the app root element (or provide CSP_NONCE) and have the server generate a per-response nonce that appears in both the header and the attribute. Scripts should be nonce- or hash-based with no 'unsafe-inline' and no 'unsafe-eval' — Angular does not need eval in AOT builds, which is one more reason JIT is not used in production. Beyond that: lock connect-src to your API origins so an injected script cannot exfiltrate freely, frame-ancestors to prevent clickjacking, and add require-trusted-types-for 'script' if you want the browser to enforce the sanitiser bypasses you missed. Roll it out in report-only mode first and read the violation reports; a CSP shipped blind breaks third-party widgets on the first day.

Example

<app-root ngCspNonce="{{ requestNonce }}"></app-root>
<!-- Content-Security-Policy: default-src 'self';
     script-src 'self' 'nonce-{{requestNonce}}'; style-src 'self' 'nonce-{{requestNonce}}';
     connect-src 'self' https://api.example.com; frame-ancestors 'none';
     require-trusted-types-for 'script' -->

Follow-ups

  • Why not just allow unsafe-inline? — It removes most of CSP's value against injected scripts; the nonce exists precisely to avoid it.
  • Does a nonce work with static hosting? — Not really: a nonce must be per response, so you need SSR or an edge worker to inject it; hashes are the static alternative.
  • What breaks first? — Analytics, tag managers and chat widgets; inventory them before enforcing.

Common wrong answer

"CSP isn't relevant, Angular sanitises." They defend different layers: sanitisation is your code's discipline, CSP is a browser-enforced backstop for everything you got wrong, including third-party code.

seniorWhat security risks does SSR add that a client-only app does not have?

Answer

Three that matter. First, cross-request state leakage: the server process is shared, so a module-level cache, a service accidentally instantiated once per process, or a global in a third-party library can serve one user's data to another — a real breach, and the reason per-request injector scoping matters. Second, server-side request forgery and injection surfaces: your render now makes outbound calls with server credentials, so a URL derived from user input can be turned into a request to an internal service. Third, error and data disclosure: server stack traces or full API responses embedded in transfer state end up in the HTML delivered to the user, which is how internal fields leak. Add the operational ones — the Node tier is now part of your attack surface and patch schedule, and SSR responses cached at a CDN must never mix authenticated content into a shared cache entry.

Example

// ❌ module-level cache: shared across every request on this server
const cache = new Map<string, User>();

// ✅ request-scoped through DI, destroyed with the render
@Injectable()                       // provided per request in the server config
export class UserCache { private cache = new Map<string, User>(); }

Follow-ups

  • How do you audit for leakage? — Grep for module-level mutable state, and test with two concurrent requests carrying different identities.
  • What goes into transfer state? — Only what the client needs; it is visible in the page source, so never internal fields or other users' data.
  • CDN caching? — Cache anonymous renders only; authenticated responses must be private/no-store with a correct Vary.

Common wrong answer

"SSR is safer because the code runs on the server." The rendering code is the same code with more privileges and shared process state; the risks are additive, not reduced.

principalWhat is on your security checklist for a frontend release?

Answer

I would keep it short enough that people actually run it, and automated wherever possible. Build and dependencies: lockfile-based installs, vulnerability scanning with a triage SLA, provenance/integrity for third-party scripts (SRI or self-hosting), and no unreviewed additions to the tag manager — supply chain is where frontend incidents actually come from now. Runtime: CSP enforced with reports monitored, Trusted Types where feasible, no bypassSecurityTrust* without a comment and a reviewer, tokens in httpOnly cookies, and a check that no secrets are baked into the bundle (they are all public by definition). Data: PII never in URLs or logs, transfer state audited, error messages user-safe. Process: authorisation asserted server-side for every route a guard protects, a periodic review that client-side gates match server policy, and a rehearsed path to revoke sessions. And one cultural item — the frontend is not a security boundary, and any design that relies on it being one is a finding, not a trade-off.

Example

- run: npm ci && npm audit --audit-level=high
- run: node scripts/assert-no-secrets-in-bundle.mjs dist/
- run: node scripts/check-csp-headers.mjs $PREVIEW_URL
- run: npx eslint . --rule 'no-restricted-syntax: [error, bypassSecurityTrust*]'

Follow-ups

  • How do you handle a vulnerable transitive dependency with no fix? — Assess exploitability in context, pin or patch, and set a review date; blanket "must be zero criticals" policies generate noise and get ignored.
  • Who owns frontend security? — The team, with a security partner for review; ownership handed entirely to a central team produces checklists nobody understands.
  • What do you do after an incident? — Blameless review, one systemic fix (not just the specific bug), and a detection test so the same class fails CI next time.
  • Biggest real-world risk? — Third-party scripts on the critical path; they run with full privileges in your origin and change without your release.

Common wrong answer

"We run a pen test before launch." A point-in-time test with no continuous controls catches a snapshot; the release-by-release risks — a new npm dependency, a new tag-manager script — arrive weekly.

16Internals: compiler, Ivy and the reactive graph

These questions are rare and almost never disqualifying, but they are how an interviewer finds the ceiling of a strong candidate. Nobody expects you to recite instruction names; they want to see whether you have a mental model of what the compiler produces and why the runtime behaves as it does — the model that lets you debug something genuinely strange.

seniorWhat is Ivy, and what did it actually change?

Answer

Ivy is the compiler and runtime that became the default in v9 and the only option from v13. Three properties matter. Locality: each component compiles independently from its own decorator metadata, so you no longer need the global metadata (metadata.json, ngfactory) that made libraries painful and builds slow — this is why libraries can ship compiled code and why incremental rebuilds are fast. Tree-shakability: templates compile to calls into a runtime of small instructions, so the bundler can drop the parts of the framework you do not use, which is where the big size reductions came from. Debuggability: because a component's compiled output is local and readable, error messages point at your code, and the ng global in dev builds can inspect a component from a DOM node. Ivy is also the substrate that made everything since possible — standalone components, control-flow blocks, deferred views and signal-driven refresh all depend on locality and instruction-level compilation.

Example

// in a dev build, from the browser console:
const cmp = ng.getComponent(document.querySelector('app-row'));
ng.applyChanges(cmp);           // force a refresh of that component
ng.getOwningComponent(el);      // who declared this element

Follow-ups

  • What was View Engine's problem? — Global compilation and ngfactory files: slow builds, large output, and the "library must be compiled with the same version" pain.
  • What is ngcc? — The compatibility compiler that converted View Engine libraries for Ivy; it is gone, and libraries now ship in the Ivy partial-compilation format.
  • Does Ivy change what I write? — No, and that was the design goal; it changes what is possible for the framework to add.

Common wrong answer

"Ivy is the new renderer that made Angular faster." Half right and too vague to survive a follow-up; the substance is locality, tree-shakability and better diagnostics, and those are what enabled the last five years of features.

seniorWhat does the compiler emit for a component template?

Answer

A template compiles into a template function on the component's compiled definition, invoked in two modes: a create pass that builds elements and bindings, and an update pass that re-evaluates expressions and updates only what changed. The function body is a sequence of instructions from the runtime — element creation, text nodes, property binding, listeners, and blocks for control flow — and each binding is compared against the previous value stored in the view's data array before touching the DOM. That data array is the other half: a view is a flat array of nodes, bindings and child views, which is why checking a view is cheap and why bindings are positional (and why @for needs track to match items to positions). The practical consequences you can use: the DOM is only written when a binding's value actually changed, expressions run once per check per view, and moving work out of the template into a memoised computed is what removes it from the update pass.

Example

// roughly what `<p title="x">{{ name }}</p>` becomes (names simplified):
// create:  elementStart(0, 'p'); text(1); elementEnd();
// update:  property('title', ctx.x); textInterpolate(ctx.name);

Follow-ups

  • Why are template expressions restricted? — They are compiled, type-checked and re-run every update; assignment and complex statements would make that unpredictable (though v22 widened what is allowed).
  • Where does the "previous value" live? — In the view's data array, which is also what the dev-mode second pass compares against for NG0100.
  • How do signals fit in? — The view registers as a reactive consumer during the update pass, so writing a signal marks that specific view for refresh.

Common wrong answer

"Angular uses a virtual DOM and diffs it." It does not — there is no VDOM; bindings are compared value by value against the previous values stored per view. Getting this wrong undermines every performance answer you gave earlier.

principalDescribe the signal graph's internals: how is a stale computed detected without recomputing everything?

Answer

Producers (signals, computeds) and consumers (computeds, effects, views) form a bipartite graph with versioned edges. Writing a producer bumps its version and marks dependent consumers dirty by walking edges — cheap, because nothing is computed. When a consumer is read, it checks its recorded dependency versions: if none changed, it returns the cached value; if some did, it recomputes and then compares the result with its own previous value, and only if that differs does it propagate dirtiness further. That last step is why an upstream change often stops before reaching the DOM — a computed whose output is unchanged does not wake its dependents. Dependencies are re-recorded on every evaluation, so a branch not taken drops its edge, and consumers are classified live or lazy: a view or effect is live and gets scheduled, while an unread computed simply stays dirty until someone asks. The design consequence worth stating: cost is proportional to what is read, not to what is written, which is the opposite of the zone-based model it replaced.

Example

const raw = signal(1);
const parity = computed(() => raw() % 2);      // 1 -> 1
const label  = computed(() => parity() ? 'odd' : 'even');

raw.set(3);      // raw version bumps; parity dirty; label dirty
label();         // parity recomputes -> 1, equal to before -> label is NOT recomputed

Follow-ups

  • How does this avoid glitches? — Nothing recomputes on write, so no consumer can observe a half-updated graph; resolution happens at read time, in dependency order.
  • What makes a consumer "live"? — Being an effect or a view: it is scheduled when dirtied instead of waiting to be read.
  • Where does equal fit? — It is the comparison used both for signal writes and for a computed's own output, which is the propagation cut-off.

Common wrong answer

"Every write recomputes the dependent computeds immediately." That would be eager evaluation with all the wasted work and glitch potential the design avoids; the two-phase mark-then-pull model is the entire point.

principalWhere is Angular heading, and how does that affect decisions you make today?

Answer

The current roadmap has three stated goals — improving the AI development experience, developer experience and performance — and the concrete items behind them are visible: WebMCP for in-browser agent tooling (experimental), the tsgo TypeScript compiler port being prototyped for a 5–10× type-checking speedup, promoting the Karma-to-Vitest migration tool to stable, expanding @angular/aria headless accessibility primitives, and cross-framework interoperability. Equally informative is what left: selectorless was removed from the roadmap and put on hold to avoid fragmenting template authoring while AI tooling converges on the current syntax. How that shapes decisions today: bet on signals, standalone and zoneless, because everything shipping is built on them; treat experimental items as options with no date and never as a reason to defer work; and keep the codebase on a current version, because the entire direction assumes you are close to head. The general principle I would state: architect for what is stable, plan for what is deprecated, and stay curious but uncommitted about what is experimental.

Example

stable today, safe to build on : signals, standalone, zoneless, signal forms, resources,
                                 per-route render modes, incremental hydration
deprecated, plan the exit      : webpack builders, ChangeDetectionStrategy.Eager,
                                 withFetch(), Karma, HttpClientModule, class-based guards
experimental, watch only       : WebMCP, tsgo, auto-cleanup injectors
on hold, do not plan around    : selectorless templates

Follow-ups

  • How do you keep a team informed without chasing every release? — One person reads each release note and posts a five-line summary with "what this means for us"; that is enough.
  • What would change your architecture? — A stable change to the component authoring model or the reactivity primitives; nothing on the current roadmap is that.
  • How do you handle pressure to adopt an experimental feature? — Prototype behind a flag, in one place, with a documented exit.

Common wrong answer

Confidently describing a roadmap item as shipped. The selectorless case is the live example: several vendor articles announced it as an Angular 22 feature while it was actually on hold — repeating that is worse than saying "I would check the roadmap".

Docs: Roadmap · DevTools and the signal graph · Angular blog (release notes)

17Legacy Angular you will meet

Rarely asked directly, but it comes up whenever the role involves an existing codebase — which is most senior roles. The interviewer wants to know you can work in a v14 app without visible disdain, recognise the patterns, and sequence a modernisation. Being fluent in both eras is the actual differentiator here; "I'd rewrite it" is not an answer anyone can act on.

midYou open a 2019-era Angular app. What patterns do you expect, and which are actually problems?

Answer

Expect: NgModules everywhere including a giant SharedModule, constructor injection, *ngIf/*ngFor with | async, class-based guards and interceptors, HttpClientModule, @ViewChild(..., { static: true }), RxJS pipelines with takeUntil(this.destroy$), Karma/Jasmine, and possibly ngx-bootstrap or a hand-rolled component library. Most of that is merely old, not broken, and works fine on a current version. The genuine problems are narrower: a SharedModule imported by every lazy chunk (which defeats lazy loading), manual subscriptions without teardown (leaks), shareReplay(1) without refCount, mutation-based state with Default change detection (which will break when you go OnPush or zoneless), and any use of an unsupported Angular version. Naming that distinction — old versus harmful — is what the question is testing; a candidate who calls all of it "legacy garbage" is telling you they will spend the first quarter rewriting instead of shipping.

Example

// the pattern you will see most, and its modern equivalent
private destroy$ = new Subject<void>();
ngOnInit() { this.svc.data$.pipe(takeUntil(this.destroy$)).subscribe(d => this.data = d); }
ngOnDestroy() { this.destroy$.next(); this.destroy$.complete(); }

// today
readonly data = toSignal(this.svc.data$);

Follow-ups

  • What do you fix first? — Whatever is causing incidents; then version support; then the mechanical migrations, cheapest first.
  • Why is a big SharedModule harmful? — Every lazy chunk imports it, so its whole graph lands in every chunk and the lazy boundaries stop meaning anything.
  • How do you avoid a culture problem? — Do not editorialise about the previous team's choices; most of them were correct for their version.

Common wrong answer

"It's all legacy, we should rewrite it in the modern style." Interviewers hear a cost with no benefit attached. The credible answer separates what is dangerous from what is merely dated, and migrates the former.

midWhich deprecated APIs will you still find, and what replaced them?

Answer

The ones that come up in nearly every older codebase: HttpClientModule (deprecated v18 → provideHttpClient()), class-based guards and CanActivate interfaces (deprecated v15.2 → functional guards), ComponentFactoryResolver (deprecated v13 → ViewContainerRef.createComponent with the type), entryComponents (removed v13, unnecessary under Ivy), @ViewChild(..., { static }) (→ signal queries), TestBed.get (→ TestBed.inject), ::ng-deep (deprecated → CSS custom properties), Karma (deprecated v20 → Vitest), and now ChangeDetectionStrategy.Default, renamed Eager and deprecated in v22, plus withFetch() and the webpack builders in the same release. Protractor is a special case: deprecated in v12 and removed in v16, so an app still using it has an unsupported E2E stack. Most have CLI migrations; the ones that do not (the router's paramsInheritanceStrategy default change in v22) are the ones to read release notes for.

Example

// before
@Injectable() export class AuthGuard implements CanActivate {
  constructor(private auth: Auth, private router: Router) {}
  canActivate() { return this.auth.isLoggedIn() ? true : this.router.parseUrl('/login'); }
}
// after
export const authGuard: CanActivateFn = () =>
  inject(Auth).isLoggedIn() ? true : inject(Router).parseUrl('/login');

Follow-ups

  • How do you find them? — Build warnings, the deprecation list in the update guide, and a lint rule per item once you have migrated it.
  • Do deprecated APIs get removed quickly? — Angular's policy is at least two majors of deprecation, so there is normally a year of warning.
  • Which deprecation should you act on first? — Anything with a behaviour change rather than a rename — Eager and the router default matter more than TestBed.get.

Common wrong answer

"Deprecated means it still works, so we can ignore it." Until the removal release, at which point it blocks the upgrade — and upgrades are how you stay in support. Deprecations are a schedule, not an opinion.

seniorThere is an AngularJS 1.x app still in production. What are the options?

Answer

AngularJS reached end of life on 31 December 2021 — no patches, no security fixes — so "leave it" is a risk decision that needs to be made explicitly, not by default. The classic incremental path is ngUpgrade (the @angular/upgrade package), running both frameworks in one page with a hybrid bootstrap, downgrading Angular components into AngularJS and upgrading AngularJS services into Angular, migrating route by route. It works, and it is heavy: two frameworks in the bundle, two change-detection models, and a migration that must actually finish or you pay the cost forever. The alternatives are often better in 2026: a route-level strangler where a reverse proxy sends some paths to a new Angular app and the rest to the old one (no shared runtime, clean boundary, independent deploys), or a rewrite if the app is small enough that a hybrid's overhead exceeds the rewrite. The deciding factors are size, how much shared state crosses screens, and whether anyone still understands the AngularJS code.

Example

strangler at the edge (usually preferred)
  /legacy/*     -> AngularJS app (frozen, security-patched by proxy rules only)
  /app/*        -> new Angular app, route by route
  shared auth via cookies, shared design via CSS tokens, no shared runtime

Follow-ups

  • How do you keep users from noticing? — Shared visual language and a hard navigation between the two; users tolerate a full page load far better than a broken feature.
  • What is the biggest risk with ngUpgrade? — A migration that stalls: you now maintain two frameworks permanently, which is worse than either endpoint.
  • How do you sequence? — Highest-change-rate screens first, so the new stack pays back immediately; leave stable, rarely touched screens for last.

Common wrong answer

"Use ngUpgrade, it's the official path." It is an official path, designed when both frameworks were current; recommending it without weighing a route-level strangler or the app's size ignores a decade of migration experience.

seniorAn app is on Angular 15, unsupported. Leadership asks whether it is urgent. What do you say?

Answer

I would frame it as risk with a number, not as engineering preference. Unsupported means no security patches for the framework or its toolchain, so any published vulnerability in Angular, its build dependencies or the Node version it pins stays open until we upgrade — and the upgrade gets more expensive every quarter as the gap grows. I would quantify three things: the current gap (v15 to v22 is seven majors, roughly a multi-week effort with schematics, more if third-party libraries block), the exposure (which dependencies are unpatched today, from a scan), and the ongoing cost (people cannot use current documentation or tooling, and hiring is harder). Then I would propose the smallest credible plan: get to the current LTS in a series of one-major PRs with the app deployable throughout, before adopting any new features. And I would be honest about the alternative: if the app is scheduled for retirement within a year, the right answer may be to isolate it — restrict access, put it behind a WAF, freeze it — rather than to spend the upgrade budget.

Example

v15  -> v16 -> v17 -> v18 -> v19 -> v20 -> v21 -> v22
       one PR per major, deployable after each, no feature work in the same PR
       expect the real cost in: third-party libs, tests, and the v17 builder change

Follow-ups

  • What if a library is abandoned? — Fork, replace or vendor it; it is the most common blocker and it needs a decision, not a workaround.
  • How do you reduce risk during the upgrade? — Strong e2e coverage on the money paths first; the schematics are reliable, the surprises are in behaviour.
  • How do you prevent recurrence? — A named owner and a cadence, otherwise the app is back here in three years.

Common wrong answer

"It works fine, so it's not urgent." "It works" is not a security posture, and it is the argument that keeps apps out of support for years. Equally weak is "we must upgrade immediately" with no cost, no plan and no risk quantification.

Docs: Update guide · Support policy · ngUpgrade

18Judgment calls

These have no single right answer — the interviewer is listening for how you reason, which trade-offs you name without being asked, and whether you can be decisive without being dogmatic. The pattern that scores: state your default, name the two or three conditions that would change it, and say what evidence you would collect. Each block below says what a strong answer demonstrates at the highest level.

principalShould we go zoneless now, or wait?

What a strong answer demonstrates

That you treat it as a readiness question rather than a switch. Strong answers separate new apps (zoneless by default since v21 — there is nothing to decide) from existing apps, where the work is signal adoption and a dependency audit, and the flip is the last step, not the first. They name a staged rollout with a flag and a rollback, and they identify the silent failure mode — views that stop updating rather than views that error — which is why e2e coverage on the main journeys matters more than unit tests here.

Trade-offs to name unprompted

  • Benefit is INP and predictability, not raw throughput; the 13 KB polyfill saving is real but minor.
  • Cost lands in third-party libraries that depend on NgZone/onStable, and in tests using fakeAsync.
  • Intermediate step available: provideZoneChangeDetection({ eventCoalescing: true }) gets part of the win with none of the risk.
  • Doing nothing has a growing cost: every new Angular default assumes zoneless.
  • A maintenance-mode app with no performance complaints is a legitimate "not now".
principalWhere exactly do you draw the line between signals and RxJS?

What a strong answer demonstrates

A rule that a team can apply without you in the room. The strongest version is ownership-based — signals own state, RxJS owns events and time — plus a boundary convention (services expose signals or resources; components never call subscribe()). What separates principal from senior is enforcement and evolution: a lint rule, five canonical examples in the repo, and an explicit statement of what would move the line (a domain that genuinely is streams).

Trade-offs to name unprompted

  • Mixed conventions cost more than either convention alone; consistency is the actual deliverable.
  • Banning RxJS produces hand-rolled debounce/retry that is worse than the operators.
  • Conversion at the boundary (toSignal) is cheap; converting whole pipelines is not, and rarely pays.
  • Signals do not carry errors or completion, so a stream's failure semantics must be handled before conversion.
principalA new, form-heavy product: Signal Forms or reactive forms?

What a strong answer demonstrates

Willingness to pick, with a stated risk position. Signal Forms are stable as of v22 and are the direction of travel, so for greenfield they are a defensible default; the counter-argument is maturity of the surrounding ecosystem — your component library, your validation helpers, the team's muscle memory — and a strong answer weighs that rather than treating "stable" as the end of the discussion. Best answers propose a spike on the two hardest forms in the product before committing, because form edge cases are where a model either holds up or does not.

Trade-offs to name unprompted

  • Signal Forms: less boilerplate, model-as-source-of-truth, schema validation (Zod/Valibot), fits zoneless naturally; smaller body of community patterns.
  • Reactive forms: enormous ecosystem, CVA-based libraries, years of known answers; more plumbing, and the value-excludes-disabled-controls class of bug.
  • Interop exists (compatForm()), so this is not a one-way door — but mixing both inside one screen is.
  • Hiring and onboarding: which model your team can review competently matters as much as the API.
principalMicro-frontends or a monorepo with enforced boundaries?

What a strong answer demonstrates

That you know micro-frontends solve an organisational problem (independent deployment, autonomy, version divergence) at a significant technical cost, and that most teams asking for them actually want enforced boundaries. A strong answer starts with route-level ownership plus lint-enforced import rules, and names the specific triggers that would justify federation: independent release trains, an acquired app on a different stack, or teams that genuinely cannot coordinate an upgrade.

Trade-offs to name unprompted

  • Federation costs: duplicated framework runtimes, version-skew bugs, harder shared auth and state, much harder debugging across bundles.
  • Monorepo costs: coordinated upgrades, CI scale, and boundaries that decay without automated enforcement.
  • Shared design system is the hardest thing to version in either model.
  • You can start with route-level splits and federate later; the reverse is much harder.
principalSSR, prerender, or a plain SPA for the new product?

What a strong answer demonstrates

Route-level thinking rather than an app-level verdict — since v20 you choose per route, and most products end up with prerendered marketing, server-rendered public detail pages and a client-rendered authenticated area. Strong answers tie the choice to a business outcome (organic traffic, first-visit conversion) and cost it operationally, and they mention that cheaper alternatives — bundle splitting, an edge-cached shell, image optimisation — often deliver most of the perceived win.

Trade-offs to name unprompted

  • SSR improves LCP and crawlability; it can worsen INP through hydration, which incremental hydration mitigates.
  • Operational cost: a Node/edge tier to run, scale, patch and monitor; TTFB becomes yours.
  • New failure modes: hydration mismatches, per-request state leakage, CDN cache poisoning of authenticated content.
  • Prerender first where content allows: static files have no runtime failure mode.
principalAdopt Angular Material, another library, or build our own components?

What a strong answer demonstrates

An honest estimate of what a component library actually costs to own — accessibility, keyboard interaction, RTL, theming, browser quirks, testing, documentation, versioning — and a hybrid recommendation: build on headless primitives (the CDK and @angular/aria, which shipped in v21) and own the visual layer, rather than either adopting a fully styled library you must fight or writing an accessible combobox from scratch. Strong answers also ask about design ambition: if the brand demands a distinctive look, styled libraries become a cost, not a saving.

Trade-offs to name unprompted

  • Material gives accessibility, testing harnesses and upgrade alignment with Angular releases; theming beyond its system is real work.
  • Third-party suites can lag Angular majors — that lag becomes your upgrade blocker.
  • Homegrown libraries usually under-invest in a11y and keyboard behaviour; that debt surfaces in an audit, not in a demo.
  • Whatever you choose, the versioning and deprecation policy matters more than the initial component set.
principalDo we need a state management library at all?

What a strong answer demonstrates

The server-state/client-state distinction, and the observation that most "state management" pain in Angular apps was actually cache management for server data. A strong answer defaults to scoped services with signals, reserves a store for genuinely shared client workflows or auditability requirements, and treats NgRx SignalStore as the pragmatic middle. It also acknowledges team context: an experienced NgRx team with a working codebase should not be moved for architectural fashion.

Trade-offs to name unprompted

  • Stores buy uniformity, tooling and an auditable action log; they cost boilerplate and indirection.
  • Server data in a store means hand-writing invalidation you get for free from a resource/query layer.
  • Signal services scale down beautifully and scale up only with discipline (ownership, invariants, lifetime).
  • Whatever you choose, one owner per value is the property that actually prevents bugs.
principalHow much of the test budget goes to unit, component and E2E?

What a strong answer demonstrates

Risk-based allocation and a clear position on flakiness. Strong answers push logic out of components so it can be unit-tested cheaply, use component tests for user-visible behaviour with accessible queries, and keep E2E small and reserved for the money paths — with an explicit flake budget and a quarantine process, because a suite people do not trust has negative value. They give targets (PR feedback under ten minutes, flake under 1%) rather than a coverage percentage.

Trade-offs to name unprompted

  • Coverage as a target produces tests written for the metric; risk-based selection produces tests that catch things.
  • E2E finds integration bugs nothing else can, and costs the most in time and trust.
  • Deep component tests that mount half the app are the usual hidden cost in a slow suite.
  • Contract tests against a generated API client catch backend drift that mocks hide.
principalWhen is Angular the wrong choice?

What a strong answer demonstrates

That you can argue against your own tool credibly. Angular's strengths — batteries included, opinionated structure, first-party router/forms/HTTP/i18n/testing, predictable upgrades with schematics, strong typing — are worth most in long-lived, large, multi-team applications. It is a poor fit for a tiny widget embedded in someone else's page, for a content site where the JavaScript is incidental, for teams with no TypeScript appetite, and for products whose hiring market is entirely React. A strong answer says this plainly and does not treat the question as a loyalty test.

Trade-offs to name unprompted

  • Baseline bundle and conceptual overhead are real for small surfaces; islands or a static-site generator may be right.
  • Ecosystem size favours React for niche third-party components; Angular's first-party coverage reduces how often you need them.
  • Upgrade discipline is a strength only if the organisation will fund it; otherwise the app drifts out of support.
  • Team familiarity beats framework benchmarks nearly every time.
principalHow do you decide when to adopt a new Angular feature?

What a strong answer demonstrates

A stability policy rather than an appetite. Strong answers distinguish Angular's own labels — stable, developer preview, experimental — and apply different rules to each: stable features may be adopted when they solve a problem you have; developer preview only behind a boundary you can revert; experimental only in a prototype. They also cite the corollary: never defer work waiting for an unreleased feature, with selectorless as the live example of a feature that was widely announced and then put on hold.

Trade-offs to name unprompted

  • Early adoption buys ergonomics and costs churn; the API can change between preview and stable.
  • Consistency has value: two ways of writing the same thing in one codebase is its own tax.
  • Migrations shipped as CLI schematics are a strong signal the team intends a smooth path.
  • The strongest reason to adopt is a problem you can name; "it is the new way" is not one.

19Design exercises

Angular connects to system design through the browser side of the architecture: rendering strategy, data flow, caching, bundle boundaries and the contracts between teams. These three are the exercises that actually come up for senior and above. Read the prompt, ask the clarifying questions out loud, sketch for ten minutes, and only then open the solution — the value is in attempting it first.

Exercise 1 — Real-time operations dashboard

Prompt. Build a dashboard for an operations team: about 40 widgets on one screen (tables, sparklines, status tiles) fed by a websocket delivering roughly 500 updates per second across 5,000 entities. It must stay responsive on a five-year-old laptop, users keep it open for eight-hour shifts, and they filter and drill down constantly.

Clarifying questions you should ask

  • How fresh must each widget be — is 250 ms batching acceptable, or is any widget genuinely tick-by-tick?
  • How many of the 5,000 entities are visible at once, and how many are merely subscribed?
  • Are updates deltas or full snapshots, and is ordering guaranteed?
  • What happens on reconnect — replay, snapshot, or silent gap?
  • Is this authenticated and single-tenant, and does it need SSR at all? (Almost certainly not.)
principalSolution outline and expected trade-offs

Design

Zoneless, signal-driven, with the socket owned by one service. The socket stream is buffered (bufferTime(100) or animation-frame batching) and reduced into an entity map held in signals — one signal per entity, or a map signal with per-entity computeds — so an update touches only the views that read that entity. Widgets read narrow computeds, never the whole map, which keeps change detection proportional to what changed rather than to the number of widgets. The visible table is virtualised, so only ~50 rows exist regardless of the 5,000 entities. Filtering and sorting of the full set run in a web worker, posting back only the visible slice, keeping long tasks off the main thread. Reconnect logic lives in the service: exponential backoff, a snapshot request on reconnect, and a sequence number so gaps are detected rather than silently rendered. For an eight-hour session, memory discipline matters more than anything clever: bounded history buffers, no unbounded arrays of ticks, and teardown of per-widget subscriptions on drill-down close.

Sketch

@Injectable({ providedIn: 'root' })
export class Feed {
  private entities = new Map<string, WritableSignal<Entity>>();

  constructor() {
    this.ws.stream$.pipe(
      bufferTime(100), filter(b => b.length > 0), takeUntilDestroyed(),
    ).subscribe(batch => {
      for (const delta of collapse(batch)) {       // last write wins per entity
        this.signalFor(delta.id).set(applyDelta(this.signalFor(delta.id)(), delta));
      }
    });
  }
  signalFor(id: string) { /* create on demand, bounded LRU */ }
}

Trade-offs you are expected to name

  • Batching window vs perceived freshness: 100 ms batching cuts render work by an order of magnitude and is invisible to humans; a genuinely tick-critical widget can subscribe unbatched, and only that one pays.
  • Per-entity signals vs one map signal: per-entity gives precise invalidation at the cost of bookkeeping and memory; one map signal is simpler but wakes every consumer.
  • Worker vs main thread: workers remove long tasks but add structured-clone cost; worth it above a few thousand rows, not below.
  • Zoneless is effectively required here: under Zone.js, 500 messages per second means 500 global change-detection passes.
  • Memory over an 8-hour session is the failure mode that actually gets reported; bound every buffer and test with a soak run.

Exercise 2 — Multi-tenant platform with tenant-specific features

Prompt. A SaaS admin platform serving 200 tenants. Every tenant gets the core product; some buy optional modules; a few large ones have bespoke screens. Tenants have their own branding. One deployment serves everyone. Design the frontend architecture.

Clarifying questions you should ask

  • Are bespoke screens built by us or by tenants/partners? (This decides plugin architecture versus feature flags.)
  • How is entitlement determined — at login, per request, and can it change mid-session?
  • How far does branding go: colours and logo, or layout and component behaviour?
  • Is there a hard requirement that tenant A never downloads tenant B's code?
  • What is the release cadence — one deploy for everyone, or per-tenant rollout?
principalSolution outline and expected trade-offs

Design

One application, entitlement-driven routing, lazy everything. At bootstrap, an app initializer fetches the tenant profile (entitlements plus theme) and stores it in a root config service. Routes for optional modules are guarded with canMatch so an unentitled tenant never downloads the chunk — this is where canMatch earns its place over canActivate. Bespoke screens are modelled as a registry: a map from screen key to a lazy loader function, so a tenant's configuration selects a component to render, loaded on demand via injectAsync/dynamic import and instantiated with createComponent or ngComponentOutlet. Branding is CSS custom properties set from the tenant profile on the root element — no per-tenant builds, no style rebuilds; the design system exposes tokens and nothing else. Everything tenant-specific is data, not code paths, which keeps the core testable. If a tenant genuinely needs partner-authored code, that is where you draw the line and use a federated remote with a strict contract, accepting the version-skew cost for that case only.

Sketch

provideAppInitializer(async () => {
  const tenant = await inject(Api).tenantProfile();
  inject(TenantConfig).set(tenant);
  applyTheme(tenant.theme);                      // sets CSS custom properties
});

export const routes: Routes = [
  { path: 'billing', canMatch: [entitled('billing')],
    loadChildren: () => import('./billing/routes').then(m => m.ROUTES) },
  { path: 'custom/:key', component: CustomHost }, // registry-driven, lazy per tenant
];

Trade-offs you are expected to name

  • Entitlement in the client is UX, not security: the API must enforce it independently, and the interviewer will check that you say so.
  • Registry vs federation: a lazy registry keeps one runtime and one upgrade path; federation buys partner autonomy at the cost of duplicated runtimes and version skew.
  • CSS variables vs per-tenant builds: variables mean one artefact and instant theming; per-tenant builds allow deeper divergence but multiply build and release cost by 200.
  • Bootstrap latency: the entitlement fetch is on the critical path — cache it, and make the shell render before it resolves where possible.
  • Testing matrix: entitlement combinations explode; test the core plus a representative matrix, not every permutation.

Exercise 3 — Public product catalogue with SEO and a performance budget

Prompt. A public catalogue: 50,000 product pages that must rank in search, plus faceted search and an authenticated account area. Mobile traffic dominates and much of it is on slow connections. Target LCP under 2.5 s at p75 and INP under 200 ms.

Clarifying questions you should ask

  • How often does product content change — hourly, daily, or on merchandising pushes?
  • Are prices and stock per user or per region, and can they be cached publicly?
  • What is the crawl budget and which pages must be indexed (all 50k, or the top slice)?
  • Is there an existing CDN and edge compute, or would SSR mean new infrastructure?
  • What is on the page above the fold, and which element is the LCP element?
principalSolution outline and expected trade-offs

Design

Per-route render modes are the backbone. Prerender the stable, high-traffic slice (home, categories, the top few thousand products) at build time; server-render the long tail on demand with CDN caching keyed by path plus region, and a short TTL with stale-while-revalidate so a merchandising change propagates without a rebuild; client-render the account area explicitly with RenderMode.Client so it costs no server CPU. Per-user data — cart badge, personalised recommendations, live stock — is fetched client-side after hydration and rendered into placeholders, which keeps the HTML publicly cacheable; that split between cacheable shell and personalised fragments is the central decision. Hydration is incremental (default in v22): the product gallery and the buy box hydrate on interaction or viewport, the footer and marketing copy use hydrate never. Images go through NgOptimizedImage with the hero marked priority and a CDN loader for format and size negotiation. Facets update the URL as query params so results are shareable and back works. Enforce the outcome with CI: per-route bundle budgets, a Lighthouse check on the product template, and RUM p75 LCP/INP per route on a dashboard.

Sketch

export const serverRoutes: ServerRoute[] = [
  { path: '', renderMode: RenderMode.Prerender },
  { path: 'c/:category', renderMode: RenderMode.Prerender,
    getPrerenderParams: () => topCategories() },
  { path: 'p/:sku', renderMode: RenderMode.Server },     // CDN-cached, SWR
  { path: 'account/**', renderMode: RenderMode.Client },
];
// @defer (hydrate on viewport) { <app-recommendations [sku]="sku()" /> }
// @defer (hydrate never) { <app-footer /> }

Trade-offs you are expected to name

  • Prerender vs SSR: prerendering 50k pages costs build time and goes stale; SSR costs runtime and infrastructure. Split by traffic distribution rather than choosing one.
  • Cacheability vs personalisation: anything per-user in the HTML makes the response uncacheable; keep personalised fragments client-side.
  • Freshness of price and stock: a cached page showing a wrong price is a business problem, not a performance one — fetch those client-side or keep the TTL very short.
  • Incremental hydration risk: hydrate never on anything interactive silently breaks it; it needs an explicit review rule.
  • SEO specifics: canonical URLs, structured data, and status codes from server routes (a real 404, not a 200 with an error component).
  • Budget enforcement is the durable part: without CI gates the page regresses within two quarters regardless of how well it launches.

20Night-before cheat sheet

The ten questions most likely to be asked in some form, with the one-sentence answer to have ready. If you read nothing else the night before, read these and the "common wrong answer" boxes in units 01–03.

  1. What is a signal, and how does it differ from a BehaviorSubject? A signal is pull-based state with automatic dependency tracking, always has a value, has no completion or error channel and nothing to unsubscribe — a BehaviorSubject is a push-based stream with an explicit lifecycle.
  2. What triggers change detection now that apps are zoneless? Explicit notifications — a signal read by a template being written, an async pipe emitting, a template or host event, markForCheck() — instead of Zone.js reporting every async callback.
  3. What changed with OnPush in Angular 22? OnPush is now the default strategy; the previous default was renamed ChangeDetectionStrategy.Eager and deprecated, and ng update annotates existing components to preserve behaviour.
  4. Why does @for require track? Because the old optional trackBy was routinely omitted, so lists were destroyed and recreated on every array change; making the key mandatory makes correct, minimal DOM updates the default.
  5. computed or effect? computed for derived values (lazy, memoised, testable); effect only for side effects outside the reactive graph — writing a signal inside an effect means you wanted computed or linkedSignal.
  6. What is a standalone component, and are NgModules dead? A component that declares its own template dependencies via imports, the default since v19; NgModules are legacy for app code but neither deprecated nor removed.
  7. switchMap or mergeMap for a type-ahead? switchMap, because it cancels the superseded request — mergeMap lets a slow response for an older query overwrite the newer results.
  8. How do you avoid subscription leaks? Prefer the async pipe or toSignal(); for imperative subscriptions use takeUntilDestroyed() with the current DestroyRef.
  9. What does resource()/httpResource() give you? Async state as signals — value, isLoading, error, status — with automatic refetch when reactive params change and cancellation of the in-flight request; stable since v22, and not a cache.
  10. Where do you store the auth token? In an httpOnly, Secure, SameSite cookie with CSRF protection (Angular's XSRF support), or in memory as a fallback — never localStorage — and the server enforces authorisation regardless.
