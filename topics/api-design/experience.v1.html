01 · The endpoint that fetched half the internet

MidPerformance problem diagnosed
EXAMPLE — replace with your own

Our mobile app called GET /orders/{id} to show a single order screen. The handler had grown a ?expand=all default nobody remembered enabling, so it eagerly loaded the customer, every line item, each item's product, and each product's warehouse stock across three regions. One retailer's account had eleven thousand historical line items on a single "order" that was really a running tab. That request serialised a 38 MB JSON body and took 4.1 seconds server-side before the client even started downloading it; on a 3G connection in the field it just timed out. Support tickets called it "the app that eats data plans."

GET /orders/8841?expand=all HTTP/1.1
Host: api.example.com

HTTP/1.1 200 OK
Content-Length: 39821004
Content-Type: application/json

I profiled it with a request-scoped EF Core logging interceptor and found six separate N+1 patterns stacked on top of the oversized payload — the expand flag was triggering lazy-load chains, not eager includes. The fix had three parts: sparse fieldsets (?fields=id,status,total returns only named top-level properties, default response shrinks from "everything" to a documented minimal shape), server-side pagination on the line-items sub-collection with a next link instead of embedding it, and replacing the ad-hoc ?filter=... string clients had started bolting onto GET for complex line-item queries with a dedicated QUERY /orders/8841/line-items request — RFC 10008, standardised in June 2026, defines QUERY as a safe, cacheable, idempotent method that takes a body, so a filter that no longer fits comfortably in a query string doesn't have to abuse POST or truncate at a URL length limit.

What I'd do differently: I'd have caught the eager-load chain in code review with a "no unbounded include" rule enforced by an EF Core analyzer, instead of finding it via a field incident three months after the flag shipped.

What the interviewer is really probing

Whether you diagnose from evidence (profiler, logs, request timing) rather than guessing, and whether "fix the N+1" is where your story stops or whether you also fixed the contract that let it happen again — pagination, field selection, response-size budgets as a standing constraint, not a one-off patch.

Follow-up drill chain

At what point does embedding related data in a response stop being convenient and start being a design smell?

Roughly: when the embedded collection's size is unbounded by the resource itself (line items on a "tab" that never closes), when two different clients want different subsets of the same embed, or when the embed changes independently of the parent (versioning it separately gets hard once it's inline). The tell is a client that discards 90% of what you send it.

Why did you reach for sparse fieldsets rather than just building a second, mobile-specific endpoint?

A second endpoint duplicates the resource model and doubles the maintenance surface; sparse fieldsets keep one resource, one set of business rules, and let each client declare its own shape. The trade-off is server complexity — you need a projection layer that can honestly omit expensive-to-compute fields, not just filter a fully-materialised object after the fact (otherwise you've "fixed" the wire format but not the database round-trip).

RFC 10008's QUERY method is safe and idempotent like GET, but takes a body like POST. What breaks if a caching proxy in front of your API doesn't understand QUERY yet?

An unrecognised method is typically treated as non-cacheable and passed straight through, which is safe but slow — you lose the caching benefit until the proxy is updated, you don't get wrong answers. The bigger risk is a strict allow-list gateway that rejects unknown methods outright with a 405; you'd check that before relying on QUERY in a hybrid client/gateway estate, and keep a POST-to-a-search-endpoint fallback until the whole path supports it.

How would you retrofit a response-size budget onto an API that has never had one?

Instrument first — log response byte size per route in the APM before changing anything, so you know which endpoints are actually at risk rather than guessing. Then set a soft budget (a logged warning) before a hard one (a 413 or forced pagination), because a hard cutoff shipped without data will break some legitimate caller you didn't know about.

If the client team refuses to adopt field selection because "it's just one more query param to remember," how do you get compliance without a mandate?

Make the lazy path the fast one: ship a smaller default response and require an explicit ?expand= to get the old heavy shape, rather than requiring an explicit opt-in to the light shape. Most clients never touch the default, so the size problem fixes itself at the source without anyone having to remember a new parameter.

02 · REST, gRPC, or GraphQL for the pricing service

SeniorHard architectural trade-off
EXAMPLE — replace with your own

We were splitting a monolithic pricing module into its own service, called by four consumers: the checkout web app (needs one quote at a time, browser-facing), a batch nightly repricer (needs millions of SKUs, internal), the mobile app (flaky networks, needs small payloads), and a partner integration (external, needs a stable public contract). I ran a half-day spike against all three styles with the same three endpoints — quote-one-item, quote-a-basket, stream-repriced-catalog — before we committed.

ConcernREST/JSONgRPCGraphQL
Public partner contractBest — ubiquitous tooling, human-readable, OpenAPI-describableWeak — needs a gateway to transcode, partners rarely have protobuf toolingWorkable but partners must adopt a query language just to call one operation
Internal batch throughput (millions of SKUs)Weak — HTTP/JSON overhead per call, chunky paginationBest — server-streaming RPC, binary framing, one long-lived callWeak — not built for bulk streaming
Mobile, flaky network, small payloadOK — sparse fieldsets help but still request/response per field groupGood — small binary frames, built-in deadlines/retriesBest — client asks for exactly the fields it needs in one round trip
Browser checkout (no proxy layer yet)Best — no gateway neededNeeds grpc-web or a Connect-protocol proxy to reach a browser directlyGood, but adds a query-planning layer for a single simple call

No single style won every row, so we didn't pick one — we picked a boundary. REST/JSON with OpenAPI stayed the public and browser contract (rows the partner and checkout app cared about). The batch repricer got a gRPC server-streaming endpoint behind the same service, because throughput mattered more than tooling ubiquity for a call nothing outside our network ever makes. Mobile kept REST but with sparse fieldsets rather than adding GraphQL, because introducing a second query paradigm for one client wasn't worth the schema-governance overhead for a three-person team. GraphQL lost every row on its own merits here, but I flagged it as the right call if a fifth consumer showed up wanting composed, cross-service reads.

What I'd do differently: I'd have written down the decision as an ADR with the comparison table before implementation started, not after a teammate asked "wait, why do we have two protocols" three weeks in.

What the interviewer is really probing

Whether you evaluate against actual consumer requirements instead of technology preference, whether you're willing to run more than one protocol when the evidence supports it (vs. dogmatically picking one "true" style), and whether you can articulate the cost of that plurality (two contracts to version, two sets of tooling) as a deliberate trade rather than an accident.

Follow-up drill chain

What's the actual cost of running two protocols for one service, beyond "two things to maintain"?

Two auth models to keep consistent, two sets of observability tooling (your REST APM dashboards don't automatically show gRPC status codes), two places a breaking change can hide, and — the one people forget — two on-call runbooks. It's worth it only when the consumer needs are genuinely incompatible, not merely "different teams have different preferences."

A partner asks why you won't just expose the gRPC endpoint to them directly instead of maintaining a REST facade. What's your answer?

gRPC's tooling assumes a shared proto registry and a client stack partners rarely run (browser callers need grpc-web or Connect, and most partner integration teams have HTTP/JSON tooling, not protobuf codegen in their pipeline). Exposing it directly also couples your internal wire format to an external contract — see story 20 for the sharper version of this argument.

How do you decide when GraphQL's "one round trip, exactly the fields you need" benefit is worth the schema-governance cost?

It pays off when a client genuinely composes data from several resources in one screen and the alternative is three or four chained REST calls — the classic backend-for-frontend problem. It doesn't pay off for a single client hitting a single resource; sparse fieldsets on REST get you 80% of the benefit for a fraction of the governance overhead (schema review, resolver N+1 risk, query-cost limiting).

Your batch repricer's gRPC stream needs to survive a network blip without losing progress. How does gRPC help, and what do you still have to build yourself?

gRPC gives you deadlines, cancellation, and structured status codes out of the box, and streaming means you're not restarting a whole HTTP request per SKU. What you still build: idempotent resumption (a checkpoint of the last SKU successfully priced) and your own retry/backoff policy around stream reconnects — the protocol doesn't checkpoint application state for you.

If your team were three people, not enough to own two protocol stacks, what would you have done differently?

Picked REST for everything and accepted the batch job's lower throughput ceiling, or picked REST with a background job queue instead of a streaming RPC for the bulk case — trading raw throughput for operational simplicity, because a team that size can't afford the tooling tax of a second protocol regardless of which one is theoretically better for one workload.

03 · The double-charge the idempotency key was for

StaffProduction incident / outage
EXAMPLE — replace with your own

Our payments endpoint accepted an Idempotency-Key header and, on a retry with the same key, was supposed to return the original result instead of charging again. During a provider outage, client timeouts spiked and the mobile app's retry logic fired aggressively. Over four hours, 212 customers were charged twice. The bug: we stored the idempotency key after the downstream charge succeeded, not before we started it — so two near-simultaneous retries with the same key both saw "no existing record," both proceeded, both charged.

// before — the race window
var existing = await _store.GetAsync(idempotencyKey);   // both retries: null
if (existing != null) return existing.Response;
var result = await _paymentGateway.ChargeAsync(request); // both retries: charge!
await _store.SaveAsync(idempotencyKey, result);           // too late
// after — claim the key first, atomically
var claimed = await _store.TryClaimAsync(idempotencyKey, ttl: TimeSpan.FromHours(24));
if (!claimed) {
    var existing = await _store.WaitForResultAsync(idempotencyKey, timeout: TimeSpan.FromSeconds(30));
    return existing ?? Conflict("request already in flight");
}
var result = await _paymentGateway.ChargeAsync(request);
await _store.CompleteAsync(idempotencyKey, result);

The fix was an atomic claim (a conditional insert in the idempotency store, keyed on the header value, with a request fingerprint so the same key with a different body is rejected as a conflict rather than silently replayed) and a "request in flight" response for the second retry to poll instead of racing ahead. We also learned, while researching how other APIs did this, that there is no finished IETF standard for idempotency-key semantics — draft-ietf-httpapi-idempotency-key-header expired in October 2025 without becoming an RFC — so the exact conflict/replay semantics are still something every API designs for itself, and we documented ours explicitly rather than assuming callers would infer them correctly.

What I'd do differently: I'd have written a concurrency test — two simultaneous requests, same key — into the original PR. It's an obvious test in hindsight and nobody thought to write it because the happy path worked.

What the interviewer is really probing

Whether you understand idempotency at the level of "claim before you act, not record after," whether you handled the customer-facing fallout (refunds, comms) as seriously as the code fix, and whether you know this area lacks a settled standard — so blind trust in "we added an idempotency key" without checking the store's actual atomicity is itself a red flag they're listening for.

STAR/CARL scaffold

Situation

Task

Action
The race condition you found, the atomic-claim fix, and how you handled the already-double-charged customers.
Result

Differently

Hint: Redis with a conditional SET, a unique DB constraint, or a dedicated idempotency table — the guarantee lives in whether the claim step is atomic.

Hint: client-side exponential backoff misconfigured, or a downstream timeout that was shorter than the actual processing time.

What's a "same key, different body" conflict you've had to design a response for?

Hint: a 409 with a fingerprint mismatch reason is the common shape — did yours have one?

Follow-up drill chain

Why claim-then-act instead of act-then-record? Walk through exactly where the original code's race window was.

Act-then-record leaves a window between "start the side effect" and "record that we started it" where a second identical request sees no record and proceeds. Claim-then-act closes the window by making the record's existence itself the gate — the second request's claim attempt fails atomically, before either request has touched the payment gateway a second time.

How would you design the response for a request that's still in flight when a retry with the same key arrives?

Either block briefly and poll for the original's completion (bounded by a timeout, then fail safe with a 409 or 425), or return immediately with a distinct status telling the caller to retry later — the choice depends on whether the caller can tolerate a longer synchronous wait. What you must not do is let the second request proceed independently.

How long should an idempotency key live, and what happens when it expires mid-retry-sequence?

Long enough to outlast any plausible client retry window plus clock skew — 24 hours is a common default. If it expires between retries, you've silently reopened the race window, so the TTL should be tied to (and longer than) the client's documented retry policy, and you should log an alert if a request with an expired-then-reused key ever shows up, since that usually signals a client bug, not a normal retry.

Given there's no finished RFC for idempotency-key semantics, how do you decide what your API's contract should be without a standard to copy?

I look at what the major payment APIs (which have run this in production for years) converged on independently — claim-first, fingerprint the body, scope the key to the endpoint or resource type, return a conflict rather than silently ignoring a mismatched replay — and document our specific choices explicitly in the API reference rather than assuming "idempotency key" means one universally understood thing.

Would a database-level unique constraint have been enough, without a separate idempotency store?

Only if the operation itself has a natural uniqueness key you can constrain on (e.g., a unique index on (customer_id, order_id) for the charge row) — that can work and avoids a second moving part. It falls short when the same idempotency key needs to guard multiple downstream side effects atomically, or when you need to return the original response body on replay, not just prevent a duplicate row.

How do you test this class of bug so it doesn't ship again?

A concurrency test that fires two (or more) simultaneous requests with the same key against a real or in-memory store and asserts exactly one downstream side effect occurred — not a sequential test, since sequential requests never exercise the race. I'd also add a chaos-style test that delays the "record" step artificially to widen the window and confirm the claim still holds.

Further reading: draft-ietf-httpapi-idempotency-key-header (expired)

04 · Versioning the public API without breaking partners

SeniorMigration / version upgrade
EXAMPLE — replace with your own

We needed to change how our public API represented money — from a float to a minor-units integer plus currency code, after a rounding bug cost a partner real revenue. This was a breaking change touching every response with a price field, across 40+ external integrators, some of whom hadn't touched their integration code in two years.

We shipped v2 under a new URL prefix (/v2/...) rather than a header-based version, specifically because header-based versioning is invisible in a partner's browser history, their support tickets, and their own logs when something goes wrong — a URL segment is something a partner-side engineer can literally point at. v1 stayed fully functional. On every v1 response we added a Deprecation header (per RFC 9745, standardised March 2025) with the deprecation date, and a Sunset header (RFC 8594) with the date it would actually stop responding, plus a Link header pointing at the migration guide. We gave partners six months, sent three reminder emails keyed off which partners' traffic hadn't moved yet (tracked via a X-Api-Version usage dashboard, not guesswork), and only after that did v1 return 410 Gone.

HTTP/1.1 200 OK
Deprecation: @1751328000
Sunset: Wed, 15 Apr 2026 00:00:00 GMT
Link: <https://developer.example.com/migrate-v2>; rel="deprecation"

What I'd do differently: I'd have put the money-representation decision through an API design review before v1 ever shipped — a float for currency is the kind of mistake a five-minute review catches, and it cost us a year-long migration to fix after the fact.

What the interviewer is really probing

Whether you think about API versioning as a partner-communication problem as much as a technical one — deprecation isn't a header, it's a header plus a comms plan and a way to measure who's actually moved — and whether you understand why URL versioning is often chosen for external contracts even when header/content-negotiation versioning is "more RESTful" in theory.

Follow-up drill chain

Why URL versioning here instead of an Accept-header content-negotiation scheme?

Visibility to a non-engineer audience. A partner's support team can grep their logs for /v1/; they can't easily see a request header without tooling. For an internal-only API where every caller is your own client code, header-based versioning is often the better trade because it keeps the URL — and therefore caching and routing — stable across versions.

How do you decide the deprecation window length — what's it actually a function of?

Your slowest-moving consumer's release cadence, not your own. A partner who ships quarterly needs longer than one with continuous deployment; if you don't know their cadence, usage-trend extrapolation (how fast the old-version traffic share is declining) gives you a data-backed estimate instead of picking a round number.

What would you do if, at the sunset date, 3 of 40 partners still hadn't migrated?

Contact them directly and individually rather than sunsetting on schedule and breaking them — a hard cutover that breaks a paying partner is a worse outcome than a short extension. I'd extend for the stragglers specifically (not globally) while making it clear the extension is a one-time exception with a firm new date.

Is 410 Gone the right response for a sunset endpoint, or would you use something else?

410 Gone is correct and more informative than 404 — it tells the caller the resource used to exist and won't come back, versus 404's ambiguity about whether it ever existed or whether they mistyped the URL. I'd pair it with a response body pointing at the migration guide, since a bare 410 still leaves the caller guessing what to do next.

How would you version a breaking change to a field's type (float to integer-plus-currency) versus an additive change like a new optional field?

An additive optional field is non-breaking under Postel's-law-style clients and doesn't need a version bump at all — that's the whole point of designing clients to ignore unknown fields. A type change on an existing field is unconditionally breaking for any strongly-typed client, so it has no safe non-versioned path; the only question is whether you version the whole API or just that resource's representation (a media-type version via Accept can scope the blast radius to just the affected resource).

05 · Hypermedia purism vs. pragmatic REST

SeniorTechnical disagreement with a colleague
EXAMPLE — replace with your own

A newly-hired architect wanted our order-management API to be fully hypermedia-driven — every response carrying _links for every valid next action (cancel, refund, ship), clients navigating state transitions by following links rather than hardcoding URLs, full Richardson Maturity Level 3. I'd shipped a Level-2 API (proper resources and verbs, no hypermedia) for three years without a single client-coupling incident, and I pushed back — not against hypermedia in principle, but against paying its cost (every client needs a link-following HTTP client, every response gets heavier, every new action needs relations documented and versioned) for a problem we didn't have: our five consumers were internal, released in lockstep with the API, and nobody was breaking on a moved endpoint.

We didn't resolve it by seniority — we wrote down the actual failure mode HATEOAS solves (client hardcodes a URL or a valid-state-transition assumption that later becomes wrong, and breaks silently instead of discovering the new one) and checked our incident history for it. Zero instances in three years. We compromised: we added one hypermedia control — a _links.self plus a computed actions array listing which of cancel/refund/ship were valid right now given the order's state — because that specific piece (state-dependent action availability) was a real, recurring client bug (clients calling "cancel" on an already-shipped order and getting a confusing 409). We didn't adopt full HATEOAS link-following for navigation, because nothing in our history showed we needed it.

{
  "id": "ord_8841",
  "status": "shipped",
  "actions": ["refund"],
  "_links": { "self": "/orders/ord_8841" }
}

What I'd do differently: I'd have proposed the "check the incident history" framing myself, on day one of the disagreement, instead of three weeks of talking past each other about REST orthodoxy first.

What the interviewer is really probing

Whether you can disagree with a colleague on a genuinely debatable architectural question without it becoming a status fight, whether you understand HATEOAS well enough to state the specific problem it solves (not just "it's more RESTful"), and whether you can find a middle path that takes the real insight from the other side's position without adopting the whole framework.

If the consumers were external and released independently of the API (so URL or state-machine changes would silently break them), or if the state machine itself was large and frequently changing (so hardcoding valid transitions in five different clients would constantly drift out of sync with the server). Clients still have to know the URL structure for whichever action they take (we didn't give them a link to follow, just a name) — so a future URL restructuring would still be a breaking change for them. Implemented it, but pushed to timebox and measure it — ship the hypermedia layer, then check six months later whether it actually caught the failure mode it was meant to prevent. The calculus flips substantially — external partners you don't control the release cadence of are exactly the audience most likely to hardcode assumptions that later break, and you have far less visibility into how they're calling you. If ten new rows get inserted before the sort position while the partner is between page 1 and page 2, page 2 now starts ten rows later than it should — the ten rows that shifted into what used to be page 1's tail are never seen again for that pass. ​
​// keyset/cursor pagination: "after" anchors to a row's actual position,
// immune to inserts anywhere except exactly at the cursor

The fix was keyset (cursor-based) pagination: instead of a numeric offset, the client passes the last item's key (created_at + id as a tiebreaker) and the server returns rows strictly after that anchor. A burst allowance layered on top of the sustained rate (token bucket naturally supports this — a bucket capacity larger than the refill rate lets you absorb a burst then throttle back to the sustained rate) rather than raising the sustained limit itself, which would also raise their capacity to do sustained damage if the key were ever compromised.

  3. Offset pagination (?page=3&size=20) breaks under concurrent inserts — items shift between pages, causing skips or duplicates; keyset/cursor pagination (?after=<last-seen-key>) is stable because it anchors to a value, not a position.
  4. An idempotency key must be claimed atomically — reserve the key and the "in progress" state in one operation before any side effect runs — or a retry inside that same race window double-executes exactly the thing the key was meant to prevent.
  5. RFC 10008 (HTTP QUERY method, June 2026) gives complex, cacheable-in-principle read filters a body without hijacking POST's "not safe, not idempotent" semantics — the gap it fills has existed since REST got popular.
  6. Deprecation header (RFC 9745, March 2025) plus Sunset header (RFC 8594) let a version-retirement plan be machine-readable, not just a changelog entry — a client library can alert on it automatically.
  7. Mass assignment happens when a request body binds directly onto a persistence entity instead of an explicit, allow-listed DTO — any field the entity has but the endpoint never meant to expose becomes attacker-writable the moment someone adds a client-side hidden form field or a rogue JSON key.
  8. REST, gRPC and GraphQL solve different problems, not the same problem three ways: REST for cacheable, resource-shaped, loosely-coupled public contracts; gRPC for low-latency, strongly-typed internal service-to-service calls; GraphQL for client-driven aggregation across many resources in one round trip. Picking one for all three jobs is usually the actual mistake, not the protocol itself.
  9. A GraphQL field removal is a breaking change the moment any persisted/registered query references it, even if no client-visible query editor currently shows it — the risk is invisible until a client replays that exact persisted query and gets a validation error instead of data.
  10. OpenAPI 3.2.0 and 3.1.2 (both released 2025-09-19) are the current spec versions; ASP.NET Core 10 generates OpenAPI 3.1 documents by default and auto-includes XML doc comments, which is worth knowing cold if the interview is .NET-flavoured.
  11. A contract-diff CI gate (comparing today's OpenAPI spec against the last released one) catches an intentional-but-accidental breaking spec change before merge; it says nothing about whether the running service still honours a spec that never changed — that second gap needs schema-conformance testing against real traffic, not a spec diff.
