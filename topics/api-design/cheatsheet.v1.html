API design (REST, gRPC, GraphQL)

cheatsheet · OpenAPI 3.2.0 · released 2025-09-19

This card treats API design as a cross-cutting discipline rather than one product, so it anchors the version line on OpenAPI 3.2.0 (2025-09-19) — the contract format most of the rest hangs off — while naming the current RFCs, the GraphQL spec edition and the Protobuf generation alongside it; ASP.NET Core wiring (routing, filters, minimal API syntax) is assumed covered elsewhere, so this stays at the design and wire-contract level above it. It covers REST resource modeling and the Richardson Maturity Model, versioning, pagination/filtering, idempotency, Problem Details error contracts, OpenAPI, HATEOAS, rate limiting and deprecation, and REST vs gRPC vs GraphQL trade-offs. The most recent citable move: RFC 10008 standardized the HTTP QUERY method in June 2026 — a safe, idempotent, body-bearing sibling to GET that OpenAPI 3.2.0 already had an operation key waiting for, a full release ahead of the RFC.

01Resource modeling & maturity

docs: Fowler — Richardson Maturity Model
Richardson Maturity Model
L0 POX/RPC — one URI, one verb · L1 resources, still one verb · L2 HTTP verbs + status codes used correctly · L3 hypermedia controls (HATEOAS) — most production "REST" APIs stop at L2, by design, not by accident
Resource naming
plural nouns for collections — /orders, /orders/{id} — never a verb in the path
Nesting depth
keep to ≤2 levels — /orders/{id}/items, not /customers/{id}/orders/{id}/items/{id}/notes — flatten with a filter or a top-level resource instead
Actions beyond CRUD (Google AIP-136)
colon-suffixed custom method — POST /orders/{id}:cancel — reads as an action on the resource, not a bare verb route
Collection vs singleton
/users/{id}/profile (singleton, no id of its own) vs /users/{id}/addresses (collection)
State transition as its own resource
POST /orders/{id}/cancellations, not PATCH { "status": "cancelled" } — when the transition needs its own audit trail or side effects, model it, don't just flip a field
House style references
Google AIP (aip.dev) and the Microsoft REST API Guidelines are the two most-cited resource-design rulebooks — worth adopting one rather than inventing a third
Client-chosen id, idempotent create
PUT /orders/{clientGeneratedId} is safely retryable by construction — vs POST /orders, which mints the id server-side and isn't idempotent on its own; see unit 05

02HTTP semantics & status codes

docs: RFC 9110 — HTTP Semantics
MethodSafeIdempotentTypical body
GET / HEAD / OPTIONSyesyesnone
QUERY (RFC 10008)yesyesrequest body — the query itself
PUTnoyesfull representation
DELETEnoyesnone (usually)
PATCHnospec allows, most impls don't guaranteepartial/patch document
POSTnonoanything
200 / 201 / 202 / 204
200 OK (body) · 201 Created (+ Location) · 202 Accepted (async — poll or webhook) · 204 No Content (success, no body)
400 vs 422
400 malformed request (bad JSON, wrong type) · 422 Unprocessable Content — well-formed, semantically invalid — RFC 9110 renamed the reason phrase from RFC 4918's "Unprocessable Entity"
401 vs 403
401 no/invalid credentials · 403 authenticated but not authorized — don't let a hostile client distinguish "forbidden" from "doesn't exist" on a resource whose existence is itself sensitive
404 vs 410
404 not found (or hidden) · 410 Gone — permanently removed, tells the client to stop retrying
405 / 406 / 415
405 wrong verb for this resource (send Allow) · 406 can't satisfy Accept · 415 can't satisfy Content-Type
409 vs 412
409 Conflict — a business-rule clash · 412 Precondition Failed — If-Match/If-None-Match mismatch, optimistic concurrency
Optimistic concurrency
ETag: "abc123" on a GET; send If-Match: "abc123" on the write; 412 on mismatch — cheaper than a version column, no schema change needed
5xx triage
500 unhandled/unknown · 502 upstream returned garbage · 503 deliberately unavailable (shedding load) · 504 upstream too slow — 503 is the one worth automating a Retry-After on

03Versioning strategies

docs: Asp.Versioning (dotnet/aspnet-api-versioning)
URI path
/v1/orders — simplest to explain, cache-friendly, forces a URL change on every client; most common in the wild
Custom header
Api-Version: 2.0 / X-Api-Version: 2 — keeps URLs stable, invisible unless you know to add it
Media-type negotiation
Accept: application/vnd.myapi.v2+json — "most RESTful" to purists, least discoverable in practice
Query string
?api-version=2.0 — easy to forget on a client, easy to leak into logs/analytics as a stray dimension
Dated versions (Stripe-style)
pin an explicit dated version per account/request, e.g. Stripe-Version: 2025-10-29.clover — every account has an implicit default that can drift; pin it, don't rely on it
No versioning, evolve instead
add-only fields, additive enum members, deprecate before removing — GraphQL's default philosophy, see unit 10
.NET tooling
Asp.Versioning.Http / .Mvc / .OData / .OpenApi — URL segment, query string, header and media-type strategies out of the box — successor to the now-archived Microsoft.AspNetCore.Mvc.Versioning
Breaking vs non-breaking
adding an optional field or enum member is non-breaking under an additive contract; renaming, removing or narrowing a type is always breaking — vendors disagree on the boundary in practice; read the vendor's own definition before assuming

04Pagination, filtering & sorting

docs: JSON:API — pagination, filtering, sorting
Offset/page pagination
?page=3&pageSize=50 — simple, but drifts under concurrent inserts/deletes and gets slower with a large OFFSET
Cursor pagination (modern default)
?after={opaqueCursor}&limit=50 — stable under mutation; encode the sort key in the cursor, not just a row id
Link header (RFC 8288)
Link: <.../orders?after=abc>; rel="next", <...>; rel="prev" — lets a client page forward without knowing your cursor's shape
JSON:API pagination
page[cursor]=abc or page[number]=3&page[size]=50, with links.next/links.prev in the body instead of headers
Filtering
?filter[status]=paid&filter[createdAt][gte]=2026-01-01 — bracket-per-field beats one query-language param wherever a caching layer needs to reason about it
Sparse fieldsets
?fields[orders]=id,total,status — shrinks the payload; GraphQL gets this for free by design
Sorting
?sort=-createdAt,status — leading - for descending is the de facto convention, standardized by JSON:API
Total count is expensive
a X-Total-Count alongside cursor pagination often means a second COUNT(*) — make it opt-in, not the default

05Idempotency & retries

docs: IETF draft — The Idempotency-Key HTTP Header Field
Naturally idempotent
GET, PUT, DELETE, HEAD, and now QUERY (RFC 10008) — repeating the exact request is safe by definition
Not naturally idempotent
POST, and PATCH in practice — the spec permits an idempotent PATCH, most servers don't guarantee one
Idempotency-Key header
client-generated key on a POST; server caches the first response and replays it for a repeat with the same key — still only an IETF draft (httpapi WG, lapsed Oct 2025), but Stripe/Adyen/PayPal/GitHub already ship it as a de facto standard
Same key, different body
MUST be rejected (409/422), never silently accepted — a key is a promise about one exact request, not "retry this operation with new params"
Key scope & TTL
unique per credential/account, cached hours to ~2 weeks depending on the API — derive it from your own request id (order:{id}:attempt:{n}), don't mint a fresh GUID per HTTP-level retry
What it doesn't cover
dedupes the write at the API boundary, not your own downstream side effects — a webhook or queue consumer still needs its own dedupe key
Retry policy
exponential backoff + jitter on 5xx/timeouts and 429 (respect Retry-After); never blind-retry a 4xx except 409/429
Client-side double submit
disable the submit control on click; reuse the same idempotency key if the user fires the request twice anyway

06Error contracts & Problem Details

docs: RFC 9457 — Problem Details for HTTP APIs
Shape (RFC 9457)
type, title, status, detail, instance + extension members — media type application/problem+json
type
a URI identifying the problem kind, ideally dereferenceable to docs — about:blank is the explicit fallback when you don't have one yet
RFC 9457 vs RFC 7807
same wire shape; 9457 (2023) adds a type-URI registry and explicit guidance for returning multiple problems in one response — obsoletes 7807, safe to cite the new number without changing anything on the wire
Validation errors extension member
a per-field errors array/object is not in the base RFC — pick one shape per API and document it as an extension member
ASP.NET Core
builder.Services.AddProblemDetails() .NET 8+ wires the Problem Details shape into the default error responses and the IExceptionHandler pipeline — MVC and minimal APIs both speak RFC 9457 out of the box once it's registered
Don't leak internals
detail is for humans, never a stack trace or raw SQL error text in production — put diagnostics behind instance + a correlation id, log the rest server-side
One error shape across protocols
a REST 422, a gRPC status and a GraphQL error should map to the same conceptual fields (code, message, correlation id) even though the wire shape differs per protocol
{
  "type": "https://api.example.com/problems/insufficient-balance",
  "title": "Insufficient balance",
  "status": 422,
  "detail": "Account 7f3c has balance 30.00, charge requires 50.00",
  "instance": "/accounts/7f3c/charges/9f1a",
  "balance": 30.00
}

07OpenAPI & contract tooling

docs: OpenAPI Specification v3.2.0
Current spec
OpenAPI 3.2.0 2025-09-19 — first minor bump since 3.1.0 (2021); 3.1.2/3.0.4 patch releases shipped the same day
New in 3.2 — query operations
a query key alongside get/post/put/delete/… for the RFC 10008 QUERY method — OpenAPI supported the method a full release before it had an RFC number
New in 3.2 — streaming
sequential media types (text/event-stream, application/jsonl, …) described via itemSchema, for SSE and other streamed responses
New in 3.2 — nested tags
summary / parent / kind fields on a tag — replaces the flat, undifferentiated tag list from 3.0/3.1
New in 3.2 — $self
a document-root field giving the base URI used to resolve relative $refs — was implicit/ambiguous before
3.1 vs 3.0
3.1 2021 aligned schemas with JSON Schema 2020-12 and added webhooks and $ref siblings — the bigger of the two migrations if you're still on 3.0.x
.NET generation
Microsoft.AspNetCore.OpenApi ships in the framework .NET 9+ — builder.Services.AddOpenApi() / app.MapOpenApi() — no bundled UI; add Scalar.AspNetCore or Swashbuckle's Swagger UI package for an interactive page, dev-only
.NET 10 addition
IOpenApiDocumentProvider — inject the generated document outside an HTTP request, for codegen or contract tests — previously only reachable by hitting the live endpoint
Contract linting in CI
spectral lint openapi.json with extends: ["spectral:oas"] — fail the build on a missing operationId or description, not just the review

08HATEOAS & hypermedia

docs: RFC 8288 — Web Linking
Link header (RFC 8288)
Link: <https://api.example.com/orders/42/items>; rel="items" — generic, transport-level hypermedia, works on any media type
HAL
application/hal+json — an _links object per resource ({"self": {"href": "…"}, "next": {…}}) plus _embedded for inlined related resources
JSON:API links
links.self / links.related inside a relationship, plus top-level links.next/prev for pagination — see unit 04
Richardson level 3, the actual point
a response tells the client which transitions are currently legal — a "cancel" link appears only on an order that can still be cancelled — that's the payoff, not the link syntax itself
What it buys you
the server can change a URL or add a workflow step without every client hard-coding the old path — genuinely useful for long-lived, third-party-consumed APIs
What it usually doesn't buy you
most internal/BFF APIs ship one client per API, deployed together — the decoupling HATEOAS sells has no buyer there, so most teams stop at level 2 on purpose
HAL-FORMS / OpenAPI Links Object
attempts at describing available actions, not just resources, machine-readably — niche, low adoption outside a few hypermedia-committed shops
Pick one hypermedia format
Accept: application/hal+json vs application/vnd.api+json — don't let the choice drift per endpoint within one API

09Rate limiting & deprecation

docs: IETF draft — RateLimit header fields
429 Too Many Requests
pair with Retry-After: 30 (seconds or an HTTP-date) — 429 comes from RFC 6585; Retry-After itself is specified generally in RFC 9110
RateLimit / RateLimit-Policy (IETF draft)
Structured-Field response headers describing quota, window and partition key — still a draft (v11, 2026-05-23), not yet an RFC; field names can still move
Legacy, still everywhere
X-RateLimit-Limit / -Remaining / -Reset — non-standard, no registry, one vendor's convention copied by the next; keep it alongside the standard headers for older clients
Sunset header
Sunset: Sat, 01 Aug 2026 00:00:00 GMT RFC 8594, 2019 — a hard date the resource stops responding
Deprecation header
Deprecation: @1735689599 (a Structured-Field date) RFC 9745, 2025-03 — signals "deprecated as of this date", independent of when it actually goes away
Ordering rule
a response's Sunset date MUST NOT be earlier than its Deprecation date — enforced by RFC 9745 itself, easy to violate by accident when the two are set from different config
Point at the migration path
Link: <https://docs.example.com/migrate>; rel="deprecation" alongside the Deprecation header
Deprecation policy shape
announce (header + docs) → warn (a visible signal in responses/logs) → sunset (Sunset header, still 200s) → retire (410 Gone) — skipping a stage is what breaks integrators, not the timeline's length

HTTP cachingworks out of the box (ETag, Cache-Control)none — roll your ownmostly none out of the box; client-side normalized caches (Apollo/Relay) do the work
.NET toolingminimal/MVC + Microsoft.AspNetCore.OpenApiGrpc.AspNetCore + Grpc.Tools codegenHotChocolate is the mainstream .NET server
Protobuf Editions
edition = "2024"; replaces syntax = "proto3"; at the top of a .proto file — 2023 was the baseline (merged proto2+proto3 into one model), 2024 the latest, roughly yearly cadence going forward
gRPC status codes ≠ HTTP status codes
OK/NOT_FOUND/ALREADY_EXISTS/FAILED_PRECONDITION/RESOURCE_EXHAUSTED/UNAVAILABLE/… carried in trailers, distinct from the transport's HTTP 200
Connect protocol
one Protobuf schema, servers/clients that speak gRPC, gRPC-Web and a JSON-friendly Connect protocol over HTTP/1.1, HTTP/2 and HTTP/3 — increasingly replaces a hand-rolled grpc-web + Envoy proxy for browser clients
GraphQL, September 2025 edition
@oneOf input objects ("input unions"), schema coordinates as a standard cross-tool identifier, broader @deprecated coverage (arguments, input fields) — the first spec update since October 2021
N+1 is the GraphQL tax
a naive resolver re-queries per parent row — DataLoader-style batching/caching per request is not optional at any real scale
Picking one
public/partner surface, caching, simple CRUD → REST + OpenAPI · internal service-to-service, low-latency, polyglot → gRPC · one UI aggregating many backends with varying field needs → GraphQL, usually behind a BFF rather than as every service's own API
