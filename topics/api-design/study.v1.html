01 Resources and the shape of REST

Docs: Fielding's dissertation, ch. 5 · Microsoft REST API guidelines

Start from the thing almost everyone gets slightly wrong: REST is not a protocol and it is not "JSON over HTTP." It is a set of architectural constraints Roy Fielding named in his 2000 dissertation to describe why the web itself scales — client-server separation, statelessness, cacheability, a uniform interface, layered systems, and (optionally) code-on-demand. Almost every API that calls itself RESTful today implements a small, useful subset of that: resources addressed by URIs, manipulated through a small fixed set of HTTP methods, represented as JSON. That subset is enormously productive, but naming it precisely matters at lead level, because "is this RESTful?" is really several separable questions — is it resource-oriented, is it stateless, does it use HTTP semantics correctly, is it hypermedia-driven — and a candidate who collapses them into one yes/no misses the interviewer's actual point.

The running example

Keep one picture through this unit: an order-management API. An Order has an id, a customer, a status, and a list of OrderLines. The very first design decision — and the one that predicts almost everything downstream — is: what are the nouns? Not "cancel an order" or "apply a discount", which are verbs describing something happening to a resource, but the resources themselves: orders, customers, order-lines. Once you have the nouns, HTTP's verbs (unit 02) tell you what you can do to them, and you almost never need to invent your own.

The Richardson Maturity Model

Leonard Richardson's model (popularized by Martin Fowler around 2010) is the fastest way to locate any API on the spectrum from RPC-over-HTTP to Fielding's full vision, and it is asked about directly in most senior interviews:

LevelWhat it meansWhat you'll see
0One URI, one method (usually POST). HTTP is just a transport.SOAP-style RPC, most GraphQL-over-HTTP endpoints, gRPC tunneled through a gateway
1Multiple URIs, one per resource — but still mostly one method.POST /getOrder, POST /cancelOrder — resources exist, verbs don't
2HTTP verbs and status codes used for their actual semantics.Where the overwhelming majority of real "REST APIs" live, including most .NET Web APIs
3Hypermedia controls (HATEOAS): responses carry the links to what you can do next.Rare in the wild — Stripe's API and some banking/hypermedia-heavy APIs are the usual examples cited

The honest, lead-level answer to "is your API RESTful" is almost always "level 2, deliberately" — level 3 buys discoverability and evolvability at the cost of client complexity that most consumers don't want, and the ecosystem largely solved the same problem a different way: a published OpenAPI contract plus semantic versioning tells the client what it can do without parsing links out of every response.

Naming and shaping resources

A handful of conventions do most of the work. Use plural nouns for collections (/orders, not /order), and let the URI hierarchy express genuine containment, not every relationship: /customers/{id}/orders is a customer's orders (containment-ish, a filtered view), but /orders/{id}/customer is usually wrong — a customer isn't owned by an order, so model it as a field or a link, not a nested collection. Cap nesting at two levels; beyond that, flatten and filter instead: /order-lines?orderId=5&status=shipped reads better and scales better than /orders/5/lines/3/discounts/7/history. Prefer opaque, non-guessable identifiers for anything customer-facing — a sequential integer id leaks your order volume to competitors and invites enumeration attacks; a GUID is safe but unindexable-looking and un-sortable; a ULID or a Snowflake-style id gives you both opacity and a roughly time-sortable, database-friendly key, which is why most modern platform APIs (Stripe, GitHub's newer resources) have moved to prefixed opaque ids like ord_01HZ....

The place candidates struggle most is actions that aren't CRUD: cancelling an order, approving a request, sending an email. Three real options, in the order I reach for them:

  • State transition via PATCH on the resource itself — PATCH /orders/5 { "status": "cancelled" } — works when the action is really just "move this resource to a new state" and there's one obvious status field.
  • A sub-resource that represents the event — POST /orders/5/cancellations — models the action as a new noun (a "cancellation" is a thing that now exists, with its own id, reason, and timestamp), which is the more RESTful shape and the one that scales when the action needs its own audit trail or can be applied more than once conceptually.
  • An RPC-flavoured verb endpoint — POST /orders/5:cancel or POST /orders/5/cancel — pragmatic, common in real codebases (Google's AIP style guide formalizes the colon syntax), and the right call when forcing a state-machine or sub-resource model would be more ceremony than clarity for an action with no interesting side data.

Content-Type: application/json

{ "reason": "customer_request" }

HTTP/1.1 201 Created
Location: /orders/5/cancellations/9f2c

HATEOAS: what it buys, and why it's rare

The fourth constraint — hypermedia as the engine of application state — says a client should be able to navigate an API by following links in responses, the way a browser navigates the web by following <a> tags, rather than by hard-coding URI templates. Done fully, it means the server can change its URI structure, add new capabilities, or gate an action behind a business rule (an order can only be cancelled while status is pending) purely by adding or omitting a link — and a well-built client just checks for the link's presence instead of re-implementing that business rule itself.

{
  "id": "5", "status": "pending", "total": 129.90,
  "_links": {
    "self":   { "href": "/orders/5" },
    "cancel": { "href": "/orders/5/cancellations", "method": "POST" },
    "customer": { "href": "/customers/42" }
  }
}

Formats like HAL (_links, as above), JSON:API, and Siren standardize the envelope so tooling can consume it generically. In practice, adoption stalled: most client code hard-codes URIs anyway because it's simpler to write and test, mobile clients ship months after the API and can't discover new capabilities at runtime regardless, and the discoverability HATEOAS promises is mostly delivered today by a published OpenAPI document plus good SDKs. Where hypermedia still earns its keep is exactly the case above — gating whether an action is currently allowed without the client re-implementing server-side state rules — which is why you still see partial HATEOAS (a couple of conditional links, not a fully navigable graph) in mature payment and banking APIs.

Interview trap

"My API is RESTful because it returns JSON over HTTP." That's level 0 dressed up. The tell-tale sign is a single /api/execute endpoint or a pile of verb-shaped URIs (/getUser, /updateOrder) — the client and server have agreed on a shared vocabulary of remote procedures, which is RPC, not resource orientation. It's not automatically wrong — plenty of successful internal APIs are RPC-shaped and that's a legitimate choice — but calling it REST in an interview when it's level 0 or 1 signals you haven't looked past the wire format. The stronger answer names the level deliberately: "we're level 2 — verbs and status codes carry real semantics — and we chose not to go to level 3 because our clients are internal services that already share our OpenAPI contract."

Try it — model one action three ways

Exercise. Take "approve a expense report" in an internal tools API. Design the endpoint three ways: (a) a PATCH status transition, (b) a sub-resource (/expense-reports/{id}/approvals), (c) an RPC-style action endpoint. For each, write the request/response shape and note what breaks first if requirements grow (e.g., reports need multiple approvers, or approvals need to be reversible).

Solution sketch

(a) breaks first: a single status field can't represent "approved by two of three required approvers" without smuggling more state into one field, and there's nowhere natural to attach a rejection reason per approver. (b) scales best for this case — each POST /expense-reports/9/approvals creates a record with an approver id and timestamp, multiple approvals naturally coexist, and a DELETE on one approval models "reversed" cleanly. (c) is the simplest to build today and is fine if you're confident the rule will always be "one approver, one decision, never reversed" — but that's a bet on the business not changing, and expense-approval rules almost always grow multi-approver logic within a year.

Interview Q&A · resources and REST

What is REST, precisely — not "JSON over HTTP"?

REST is Roy Fielding's set of architectural constraints for distributed hypermedia systems: client-server separation, statelessness between requests, cacheability, a uniform interface (a small fixed set of methods applied to named resources), a layered system, and optionally code-on-demand. What the industry calls "a REST API" is almost always a pragmatic subset — resource-oriented URIs, HTTP verbs and status codes used semantically, JSON payloads — without full hypermedia. I'm precise about that distinction in interviews because it shows I know REST is a design philosophy with degrees, not a checkbox.

Explain the Richardson Maturity Model and where most production APIs actually sit.

It's a four-level scale, 0 to 3. Level 0 is a single endpoint tunneling everything through one method — RPC in HTTP's clothing. Level 1 gives every resource its own URI but still leans on one method. Level 2 is where verbs (GET/POST/PUT/PATCH/DELETE) and status codes carry real, HTTP-spec-conformant meaning — this is where the vast majority of real APIs live, including most well-built .NET Web APIs. Level 3 adds hypermedia controls so clients navigate via links rather than hard-coded URI templates. Almost nobody ships full level 3; it's mostly used as a design ideal and, partially, in domains like payments where conditionally showing an action link is genuinely valuable.

How do you decide the URI shape for a non-CRUD action, like "cancel an order"?

I ask whether the action produces something worth its own identity and audit trail. If yes — a cancellation with a reason, timestamp, and maybe a refund reference — I model it as a sub-resource, POST /orders/5/cancellations, which is the most RESTful and most extensible shape. If the action is genuinely just "flip a status field" with no interesting side data, a PATCH on the resource's status is simpler and fine. I reach for a bare RPC-style verb endpoint, POST /orders/5/cancel, only when I'm confident the action will never need its own history or metadata — and I say so explicitly in the design doc, because that assumption is the first thing that breaks.

What is HATEOAS and why do so few real APIs implement it?

Hypermedia as the engine of application state: responses include links describing what the client can do next, so the client navigates the API the way a browser navigates the web, rather than hard-coding URI templates. It buys discoverability and lets the server encode business rules — "this order can be cancelled" — as the presence or absence of a link. Adoption is low because most of that value is delivered more cheaply another way today: a published OpenAPI contract, generated SDKs, and semantic versioning. Full hypermedia clients are also genuinely harder to write and test than "call this known URL." Where I do still reach for a link is exactly the conditional-action case — a cancel link that's present only while an order is cancellable — because that saves the client from re-implementing my state machine.

How deep should resource nesting go, and what do you do when it wants to go deeper?

I cap it at two levels — /customers/{id}/orders is fine, /customers/{id}/orders/{id}/lines/{id}/discounts is not. Past that, I flatten to a top-level collection and use query parameters to express the relationship: /discounts?orderLineId=7. Deep nesting couples URI structure to a data model that will change, makes routing and caching harder, and usually signals that "discount" deserves to be a first-class resource with its own lifecycle rather than a leaf five levels down someone else's tree.

Sequential integer ids, GUIDs, or something else, for public resource identifiers?

Sequential integers leak business volume (competitors can estimate your order count) and invite enumeration. A GUID fixes both but is unsortable and doesn't compress well in logs or URLs. My default now is a ULID or Snowflake-style id, optionally with a type prefix like Stripe's ord_01HZ... — opaque, roughly time-ordered so database indexes stay happy, and self-describing in logs. I reserve raw auto-increment integers for internal-only resources nobody outside the team ever sees in a URL.

When is an RPC-style API — not resource-oriented at all — the right choice over REST?

When the domain is genuinely a set of actions rather than a set of things — a calculation service, a workflow-orchestration API, most internal service-to-service calls — forcing nouns onto it adds ceremony without buying anything, and gRPC or a plain RPC-over-HTTP contract is more honest. I also reach for it when the client and server are both mine and change together, since REST's main payoff — a stable, cacheable, evolvable public contract — matters most when I don't control the client. The trade I'm making is losing HTTP-native caching and the uniform interface's teachability in exchange for a tighter, often more efficient contract.

A junior engineer proposes /api/getUserOrders?userId=5. What's your review comment?

I'd point out it's level 1 at best — the verb is in the URI instead of the HTTP method — and propose GET /users/5/orders, which lets GET's own semantics (safe, cacheable, idempotent) do the work the verb-in-the-name was trying to do manually. I'd frame it as a question first, though, not a rewrite demand: is this endpoint part of a public or partner-facing contract, where the convention matters for consistency and caching, or a narrow internal RPC call where the team has already decided to accept that trade-off? The comment changes tone depending on the answer, but the technical point — HTTP already gives you a verb, stop encoding a second one in the path — stands either way.

How do you model a relationship that isn't strict containment — say, an order's customer?

Not as a nested collection under the order, because the customer doesn't belong to the order and existed before it. I'd expose it as a field with either the full sub-object or, more scalably, a link/id plus a sideloadable relationship — { "customerId": "42", "_links": { "customer": { "href": "/customers/42" } } } — so the client fetches the customer only when it needs to, and the order representation doesn't balloon when a customer has thousands of historical orders. If the API supports it, letting the client ask for expansion (?include=customer, in the style of JSON:API) covers the common "give me both in one round trip" case without permanently embedding one resource inside another.

What's the actual cost of going to full Richardson level 3, and when is it worth paying?

The cost is mostly on the client: a hypermedia-aware client is more code, harder to unit test (you're now asserting on link presence and href templates, not just fixed URLs), and most HTTP client libraries and codegen tools don't help you with it, so you're often hand-rolling the navigation logic. It's worth it when the API genuinely needs to evolve its capability surface without a version bump and without every client redeploying — long-lived, third-party-integrated systems like payment processing or banking, where "can I do X right now" is a real per-resource, per-state question the client shouldn't have to re-derive. For a typical internal or partner API where you control the release cadence of both sides, a versioned OpenAPI contract gets you most of the same safety far more cheaply.

02 HTTP as a contract

Docs: RFC 9110 — HTTP Semantics · RFC 10008 — the HTTP QUERY method

HTTP's methods are not a naming convention — they're a set of promises the protocol makes to every intermediary between client and server: caches, proxies, load balancers, retry logic in HTTP clients, browsers. Two properties matter more than any other and get tested constantly in interviews because they're so often misapplied: safety (does the request change server state?) and idempotency (does repeating the exact same request produce the same end state as doing it once?). Get these right and a whole category of production incidents — double-charged customers, duplicate orders, cache poisoning — simply can't happen; get them wrong and you've built something that looks like REST but lies about what it will do.

MethodSafe?Idempotent?Typical use

QUERYYesYesComplex read with a request body (RFC 10008, June 2026) — "GET with a payload"

PATCHNoNot by defaultPartial update — idempotent only if you design it that way (unit 05)

Safety and why caches trust GET

"Safe" means the request is not expected to change anything observable server-side beyond logging and metrics — a client, cache, or search-engine crawler can issue it freely, retry it on timeout, or prefetch it speculatively. This is the entire reason browsers preload links and CDNs cache GET responses by default: the protocol promises they can't cause harm. The moment a GET handler has a side effect — a "delete" link implemented as GET /orders/5/delete, the classic mistake — that promise is broken, and something upstream that assumed safety (a link prefetcher, an antivirus scanner following links, a browser's "restore session") can delete data nobody asked it to delete. This was a real, repeated class of bug in the mid-2000s web and it is exactly why "make destructive actions a `GET`" is still one of the fastest ways to fail a code review.

Idempotency and why PUT ≠ POST

Idempotent means: send the request once, or five times because your retry logic panicked, and the server ends up in the same state either way. PUT /orders/5 with a full representation is naturally idempotent — replacing a resource with the same data twice is a no-op the second time. POST /orders is naturally not — each call is a request to create a new order, so five retried calls plausibly create five orders. That's not a flaw to work around case-by-case; it's why idempotency keys exist as a first-class pattern (unit 05) rather than something you improvise per endpoint.

The new arrival: HTTP QUERY

For twenty-five years REST had a real gap: how do you do a safe, cacheable, idempotent read when the query itself doesn't fit in a URL? A search across ten filter fields, a geo bounding box, a GraphQL-style structured query — all of that technically works as query-string parameters, but hits URL length limits, ugly encoding, and the fact that many API gateways and browsers still cap URLs around 8KB. Teams have quietly used POST for "searches" for years, which works but lies: a search is safe and idempotent by nature, and marking it POST tells every cache and retry mechanism in the stack that it isn't. RFC 10008, published by the IETF in June 2026 after years as an internet-draft, closes the gap with a new method, QUERY: safe, idempotent, cacheable, and carries a request body. OpenAPI 3.2.0 (released 2025-09-19, ahead of the RFC) already added first-class support for describing it. Client and proxy support is still catching up as of late 2026 — this is the freshest thing in this whole guide, and the honest answer in an interview is "the semantics are exactly right, the ecosystem is mid-migration."

QUERY /orders HTTP/1.1
Content-Type: application/json
Accept: application/json

{ "filter": { "status": "pending", "totalGte": 100 }, "sort": ["-createdAt"] }

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=30

{ "items": [ ... ], "count": 42 }

Status codes as the other half of the contract

Gotcha

The 401-vs-403 mix-up is the single most common status-code mistake in real codebases, including production ones from teams who know better. The mnemonic that sticks: 401 is "who are you?" (send credentials, or better ones), 403 is "I know who you are, and the answer is no." A request with no Authorization header, or an expired token, gets 401. A request from a properly authenticated user who simply lacks the permission gets 403. Returning 403 for an expired token is a common source of confusing "access denied" messages that are actually just "please log in again" — and returning 401 for a permissions failure trains client code to retry a login flow that will never fix the problem.

Try it — audit a real endpoint's status codes

Exercise. Pick any endpoint you've shipped or reviewed recently. List every status code it can return, and for each one, what a well-behaved HTTP client (browser fetch, a typed SDK, a retry-with-backoff library) would infer and do next. Flag any code that would make the client do the wrong thing.

What people usually find

The two recurring findings: (1) a generic 500 covering both "our server crashed, retry later" and "you sent bad data, retrying won't help" — clients can't distinguish, so they either retry forever against a bad request or give up on a transient blip; (2) a 200 with {"success": false, "error": "..."} inside — any client, cache, or monitoring dashboard that reads only the status code reports this as a healthy 200, silently swallowing real failures.

Interview Q&A · HTTP as a contract

Define "safe" and "idempotent" precisely, and give one method that is one but not the other.

Safe means the request isn't expected to produce an observable server-side change beyond logging — a client or intermediary can issue it speculatively without consequence. Idempotent means repeating the identical request N times leaves the server in the same state as issuing it once — it says nothing about read-vs-write. DELETE is the clean example of idempotent-but-not-safe: deleting an already-deleted resource still ends with it gone, so repeating the call is harmless, but the first call definitely changed state.

Why is GET /orders/5/delete a real production risk, not just a style nitpick?

Because everything upstream of your handler — browser prefetchers, antivirus link scanners, CDNs, search crawlers, HTTP client retry logic — is entitled to assume GET is safe and can issue it without asking. A GET that deletes breaks that contract silently: something that thought it was being cautious (following a link to see where it goes) triggers real data loss. This was a genuine, repeated bug class in the mid-2000s and is still the fastest way to fail a senior code review today.

What problem does the new HTTP QUERY method solve that POST-for-search didn't?

POST for search "works" mechanically but lies about semantics: it tells caches, CDNs, and retry logic that the request is unsafe and non-idempotent when a search genuinely is neither. That blocks safe caching of search results and safe automatic retries. QUERY (RFC 10008, finalized June 2026, described in OpenAPI 3.2.0 ahead of the RFC) gives searches a request body — solving the URL-length problem GET had — while keeping the safe, idempotent, cacheable semantics GET always had. The honest caveat: client and proxy support is still maturing as of late 2026, so most production code is still choosing between imperfect GET and semantically-wrong POST today.

Is PATCH idempotent?

Not by default, and that surprises people because PUT (also a partial-update-flavored verb in people's minds) is. A JSON-merge-patch style body — set specific fields to specific values — is idempotent: applying it twice gives the same result. A JSON Patch operation like "increment counter by 1" or "append to array" is not: applying it twice doubles the effect. Whether your PATCH is idempotent is a property of what the patch document says, not of the method itself — I say this explicitly whenever I design one.

401 or 403 — and why does the distinction actually matter to a client?

401 means "I don't know who you are, or don't trust the credentials you sent" — the fix is authenticating again. 403 means "I know exactly who you are, and you're not allowed" — re-authenticating won't help. A client seeing 401 typically triggers a re-login flow; a client seeing 403 shows a permissions error instead. Conflating them either sends a properly-logged-in user into a pointless login loop, or tells someone who's actually unauthenticated that no amount of logging in will help.

When would you choose 202 Accepted over blocking until the work is done?

Whenever the operation genuinely takes longer than a client should wait on an open connection — generating a report, provisioning infrastructure, bulk-processing an upload. 202 plus a Location pointing at a status resource (GET /jobs/9f2c) lets the client poll or, better, subscribe to a webhook, instead of holding a connection open against a load balancer's timeout. The trade-off is real: the client now has to implement polling or webhook-handling logic instead of a simple request/response, so I reserve it for operations where that complexity is clearly worth it.

Client complains "we get 500 constantly, but half of them are our own bad requests." What do you fix?

The server is collapsing client errors and server errors into one bucket, which breaks retry logic on both sides — a client can't tell "fix your payload" apart from "try again in a minute." I'd audit every throw site that maps to a bare 500 and split it: validation and business-rule failures become 400/409/422, and only genuine unhandled exceptions or dependency failures stay 500/503. This is usually a missing exception-to-status-code mapping layer, not a design flaw in the API shape itself.

A teammate returns 404 for a resource that exists but the caller isn't authorized to see. Good idea or bad?

It depends on what you're protecting. For a resource whose mere existence is sensitive — another tenant's private data, a user enumeration surface — returning 404 instead of 403 is a deliberate, defensible choice: it avoids confirming the resource exists at all. For an internal API where existence isn't sensitive, I'd push back — 403 gives the caller (and your logs) a clearer signal, and swallowing every authorization failure into "not found" makes debugging permission bugs unnecessarily hard.

Should a successful DELETE return 200, 202, or 204?

204 No Content is the default for "deleted, nothing more to say" — the resource is gone and there's no representation left to return. 200 with a body is right if you're returning something useful, like a summary of what was deleted or a soft-delete record. 202 is right only if the delete is genuinely asynchronous — soft-delete now, hard-delete via a background job later — and you want the client to know it's pending rather than final.

Why does the safe/idempotent table matter for load balancers and retries, concretely?

An HTTP client library or an API gateway that implements automatic retry-on-timeout has to know whether resending a request is safe. It can retry a timed-out GET or PUT without asking, because idempotency guarantees the same end state. Retrying a timed-out POST blind is how you get duplicate orders or double-sent emails when the original request actually succeeded server-side and only the response was lost — the client has no way to know that without an idempotency key (unit 05). This is precisely why libraries like typical HTTP clients auto-retry GET/PUT/DELETE by default but not POST.

How would you introduce HTTP QUERY to a team that's currently doing "search via POST" everywhere?

Not as a big-bang migration — client and intermediary support is still uneven in 2026, and I'd rather ship it where it earns its keep first. I'd pick one high-value, high-cache-potential search endpoint, add QUERY alongside the existing POST (both hitting the same handler), document it in the OpenAPI 3.2 spec, and measure whether clients that adopt it actually see cache and retry benefits before asking every team to switch. Framing it as "an additive, safer alias" rather than "deprecate your POST search" gets buy-in faster than a mandate would.

03 Representations and versioning

Docs: RFC 9110 — content negotiation · Microsoft API guidelines — versioning

A resource and its representation are different things, and the distinction is the whole reason content negotiation and versioning aren't the same problem wearing two hats. /orders/5 names a resource — a concept with an identity and a lifecycle. What you get back when you GET it is a representation: JSON today, maybe CSV for a bulk-export client, maybe an application/vnd.acme.order.v2+json media type tomorrow. The resource doesn't change when the representation does. Versioning strategy is really a question about which axis you let vary — the URL, a header, or the media type itself — and each answer has different blast radius when you need to change the contract.

The three versioning strategies

What actually counts as a breaking change

The single most valuable skill here isn't picking a versioning scheme — it's knowing what forces a new version at all, because over-versioning fragments your API into maintenance nightmares and under-versioning breaks clients silently.

A client written in a language with exhaustive pattern matching (a C# switch expression without a discard, a Rust match) can genuinely crash or misbehave when you add a new enum member it never saw at compile time. The safe default for evolving enums: document them as open sets from day one ("treat unknown values as `unknown`, don't assume this list is exhaustive") so adding a member is additive, not breaking — and if you can't retrofit that promise onto an existing enum, adding a member to it is a breaking change in practice even though it looks purely additive on paper.

Deriving version numbers, and choosing a scheme deliberately

Most REST APIs use a single incrementing integer (v1, v2) rather than semver, because a public REST API only has one axis that matters to consumers — "is my existing code still going to work" — and semver's minor/patch distinction doesn't map cleanly onto a contract that's either compatible or isn't. Where semver-like thinking does show up is in how long you support old versions and how aggressively you deprecate (unit 09); GitHub's REST API, for example, has stayed on a single major version (v3-equivalent, now unversioned in the URL) for years, evolving additively and reserving breaking changes for genuinely rare, opt-in "API version" headers with dated values (X-GitHub-Api-Version: 2022-11-28) rather than incrementing integers — a date-based scheme that's gained real traction (Stripe does the same) because it communicates "here's exactly what behavior you're pinned to" more precisely than an opaque integer ever could.

Interview trap

"We version everything, so we're safe." Versioning schemes protect you from announced breaking changes — they do nothing for the silent kind. The two dangerous patterns: changing a field's semantics without changing its name or type (a total field that used to exclude tax and now includes it — same JSON shape, completely different meaning, and no client-side error will ever fire), and adding enum values to a field clients pattern-match on exhaustively. Neither trips a schema validator. The fix isn't more versioning discipline, it's documenting fields' meaning precisely enough that a semantic change is recognizably a breaking change in the first place, and treating enums as open sets by contract.

Interview Q&A · representations and versioning

What's the difference between a resource and a representation, and why does it matter for versioning?

The resource is the stable concept — /orders/5 — the representation is the specific bytes returned for it, shaped by format and version. Keeping them conceptually separate is what makes header- and media-type-based versioning coherent: the URI names the thing, the Accept header or a version header picks which representation of that thing you want. URI-path versioning collapses the distinction for pragmatic reasons — it's easier to route and cache — at the cost of technically making /v1/orders/5 and /v2/orders/5 two different resources pointing at the same underlying entity.

Why do most public APIs version in the URL despite header/media-type versioning being more "correct"?

Because discoverability and operability at scale beat theoretical purity. A version in the path is visible in every log line, every browser address bar, every curl command, and every API gateway's routing rule without any special tooling. Header and media-type versioning require every consumer to know to look — and across thousands of external integrators, "invisible unless you read the docs closely" reliably becomes "half of them get the default version and don't realize it." Stripe, GitHub, and Twilio all default to URL or a simple header for exactly this reason.

Is adding a new required field to a response body a breaking change?

It's the debatable case, and my answer depends on the client population. Loosely-typed consumers (dynamic languages, JSON.parse-and-poke) don't care. Strictly-typed consumers using codegen'd clients from your OpenAPI schema often do — many codegen tools produce classes that fail deserialization on an unexpected shape mismatch depending on settings, and schema validators enforcing "additionalProperties: false"-style strictness will reject it outright. I treat it as breaking by default for any API with a published OpenAPI contract and generated SDKs, and only relax that for internal APIs where I know exactly how lenient every consumer is.

Your team adds a new enum value to a widely-consumed status field. A client crashes. Whose bug is it?

Both, and I'd say so in the postmortem rather than assign blame to just the client. If the field was ever documented as an open, extensible set of values, the crash is squarely a client bug — an exhaustive switch with no default on a documented-open enum is a latent bug waiting for exactly this. If it wasn't documented that way, it's on the API team: adding a value to what looked like a closed contract is a breaking change dressed as an addition. Going forward, every enum in a public contract should say explicitly whether it's open or closed.

Explain the difference between a semantic change and a structural change, with an example.

Structural changes alter the shape — a field's name, type, or presence — and are mechanically detectable by a schema diff. Semantic changes keep the shape identical but change what the value means: a total field that silently switches from tax-exclusive to tax-inclusive is still a number named total, so no diff tool flags it, but every client that displays or sums that field is now wrong. Semantic changes are more dangerous precisely because tooling can't catch them — the only defense is precise field-level documentation and treating any meaning change as equivalent to a rename for versioning purposes.

What's the case for date-based API versions (like Stripe's or GitHub's) over incrementing integers?

A date pins a client to the exact behavioral snapshot the API had on that day, which is more precise than an opaque integer that might quietly bundle several unrelated behavior tweaks under one number. It also naturally documents itself in support conversations — "you're on the 2022-11-28 behavior" is unambiguous in a way "v3" often isn't once v3 has accreted a year of additive changes. The trade-off is you need infrastructure to keep many dated behavior snapshots alive simultaneously, which is more operationally demanding than serving two or three integer versions.

How would you version a GraphQL API, where there's traditionally no version number at all?

GraphQL's convention is to avoid versioning altogether and evolve the schema additively instead: add new fields and types freely, and deprecate old fields with @deprecated(reason: "...") rather than removing them, so every client keeps working against one continuously-evolving schema. It works because GraphQL clients request exactly the fields they use, so unused deprecated fields cost nothing to keep around, and clients that adopt a new field do so at their own pace. The real discipline shifts from "when do we cut v2" to "how long do we tolerate a deprecated field before it's safe to actually delete it" — which is a lifecycle question (unit 09), not a versioning scheme.

A client says "the API changed under us and nothing broke, but our numbers are wrong." What do you look for first?

A semantic change with no structural signature — the exact "tax-inclusive total" trap. I'd diff recent deploys' changelog for anything touching calculated fields, not schema-changing fields, since a schema diff will show nothing. This is also the strongest argument for including a human-readable, dated changelog alongside any OpenAPI diff tooling: machine-readable schema diffs are necessary but not sufficient to catch this class of bug.

When, if ever, would you deliberately choose to break a contract without bumping the version?

Essentially never for a documented, external contract — that's the one thing versioning exists to prevent. The narrow exception is fixing a bug where the previous behavior was never the documented contract in the first place — say, a field that was supposed to be an ISO-8601 date but a bug made it emit a Unix timestamp for six months. Restoring the documented behavior is a bug fix, not a version bump, but I'd still announce it loudly, because whatever fraction of clients adapted to the buggy behavior will experience it as a break regardless of what I call it.

How do you decide how many versions of an API to support concurrently?

It's a cost/risk trade, not a technical question alone: each live version is code, tests, and on-call knowledge that has to keep working, so I want the smallest number that doesn't strand paying or contractually-committed consumers. Two concurrent major versions is a comfortable norm for most B2B APIs — enough runway to migrate without an emergency, not so many that the team is maintaining a museum. I pair the version count with an explicit sunset policy (unit 09) from the day a new version ships, not after the old one starts causing pain.

Content negotiation via Accept exists for versioning — why doesn't your team use it, if it's the "more correct" approach?

Because correctness on paper doesn't help if the people integrating against the API don't reach for it. Most engineers testing an API by hand use a URL in a browser or a quick curl without custom headers, so a version that only lives in Accept is invisible until something's already broken. I'd reach for it specifically inside an ecosystem I control end-to-end — internal service-to-service calls where every caller is a known, disciplined client — where the purity payoff (one stable URI, negotiated representation) is worth the discoverability cost.

04 Pagination, filtering, querying

Docs: JSON:API — pagination · Google AIP-158 — pagination

Every collection endpoint eventually meets a table with a million rows, and how you paginate it is a decision with real database consequences, not just an API-shape preference. The two dominant strategies — offset and cursor — trade off simplicity for correctness under concurrent writes, and picking wrong shows up as a production bug ("page 2 is missing rows that were on page 1 a second ago") that's genuinely hard to diagnose after the fact.

The failure mode that makes this concrete: an offset-paginated feed, page size 20, someone deletes a row that was item #15 on page 1 while a client is mid-scroll. Every row after it shifts up by one, so page 2 (offset 20) now starts at what was previously item #21 — item #20 is silently skipped and never shown. The pageInfo/endCursor shape above is the Relay/GraphQL convention, but the same idea applies verbatim to REST: return an opaque cursor, not a raw id, so you're free to change what the cursor encodes later (composite sort keys, an encoded timestamp+id pair) without breaking clients who correctly treat it as opaque. The trap is a team leaking the encoding by using a bare integer id as the cursor — clients start assuming "cursor + 1 is the next page," which breaks the moment you change sort order or add soft-deletes.

Filtering, sorting, and sparse fieldsets

Three genuinely different query concerns get mixed together constantly. Filtering narrows the result set (?status=pending); sorting orders it (?sort=-createdAt,customerName, a leading - for descending is the widely-copied convention from JSON:API); sparse fieldsets shrink each item's payload (?fields=id,status,total). Query languages range from flat key-value pairs (fine for simple equality) to structured operators for anything richer:

# flat, equality only
GET /orders?status=pending&customerId=42

# operator-suffix convention for ranges
GET /orders?totalGte=100&totalLte=500&createdAfter=2026-01-01

# RSQL / FIQL-style expression string, for genuinely complex filters
GET /orders?filter=status==pending and total=ge=100

The operator-suffix style (totalGte, createdAfter) is the pragmatic default for most APIs — no new parsing infrastructure, self-documenting in an OpenAPI schema as ordinary named parameters. A structured filter expression language (RSQL, OData's $filter) earns its complexity only when consumers genuinely need arbitrary boolean combinations ((status=pending OR status=processing) AND total>100) that named parameters can't express without combinatorial explosion — at that point HTTP QUERY (unit 02) with a structured JSON body is often a cleaner fit than a filter mini-language crammed into a query string.

Interview trap

"We use offset pagination because it's simpler for the frontend — page numbers, easy." That's a legitimate trade-off for a small admin table, and a real liability for anything customer-facing at scale: skipped or duplicated rows under concurrent writes, and a query plan that gets linearly slower as users page deeper (OFFSET 50000 still has to walk past 50,000 rows in most databases before returning anything). The stronger answer names the trade explicitly — "offset for the low-traffic internal admin views where jump-to-page-9 matters more than perfect consistency; cursor for the public orders feed" — rather than picking one scheme globally and hoping it doesn't matter.

Interview Q&A · pagination and querying

Why does cursor pagination avoid the skip/duplicate bug that offset pagination has?

An offset is a position relative to the current state of the collection — "the 21st row right now" — so when rows are inserted or deleted before that position, every subsequent offset now points at a different row than the client expects. A cursor instead anchors to a specific row's key ("everything after order ord_40"), which stays well-defined no matter what happens elsewhere in the collection, because it's not a position, it's a reference point.

Why is OFFSET 100000 a performance problem even when the query otherwise uses an index?

Most databases implement OFFSET by scanning and discarding rows up to that point before returning results — the index helps with ordering but not with skipping, so the cost grows roughly linearly with the offset regardless of how small the final page is. Deep pagination (page 5000 of an admin export) can turn a sub-millisecond indexed query into a multi-second one. Keyset/cursor pagination avoids this because "everything after key X" is a direct index seek, constant-time regardless of how deep into the collection X is.

Should a pagination cursor be a raw database id, or opaque?

Opaque, always — typically a base64-encoded token wrapping whatever the server actually needs internally (an id, a composite sort key, a timestamp). Exposing a raw id invites clients to assume things about it — that incrementing it gets the next page, that it's stable across a sort-order change — and any of those assumptions breaks the moment the server's internal representation evolves. Treating it as an opaque blob the client passes back unmodified is what lets you change the encoding later without a breaking change.

When is offset pagination still the right choice?

Small or slow-changing collections where the dataset genuinely doesn't grow past what a UI needs jump-to-page navigation for — an admin table of a few hundred product categories, a settings list. The two things offset buys you that cursors don't — jump to an arbitrary page, show a total page count — matter more than consistency-under-concurrent-writes exactly when the collection is small enough that neither problem (staleness, deep-offset cost) is likely to bite.

How do you design a filter query language that scales from simple to complex needs without becoming its own mini-language nobody can read?

I start with flat named parameters and operator suffixes (totalGte, statusIn) because they're self-documenting in OpenAPI and need zero custom parsing. I only reach for a structured filter expression (RSQL, OData $filter) when consumers demonstrably need arbitrary boolean combinations that named parameters can't express — and even then I'd consider whether HTTP QUERY with a structured JSON filter body is a cleaner fit than cramming boolean logic into a query string, since a JSON body can express AND/OR/NOT as actual nested structure instead of a string a client has to build correctly by hand.

What does sparse fieldsets (?fields=id,status) actually save, and when does it matter?

It saves payload size and, more importantly, backend cost when some fields are expensive to compute or fetch — a field that requires a join, an external service call, or a heavy aggregation shouldn't be paid for by every caller if only a fraction need it. It matters most for mobile clients on constrained bandwidth and for list endpoints returning hundreds of items, where trimming each item's payload by even a few fields compounds. I treat it as an optimization to add when profiling shows it's worth the added combinatorial testing surface, not a default every endpoint needs from day one.

A consumer wants a total count alongside a cursor-paginated list. What's the tension?

COUNT(*) over the same filter is often nearly as expensive as the query itself on a large table, and it's exactly the cost cursor pagination was designed to avoid paying repeatedly. I'd either make the count optional and separately cached/approximate (many search UIs show "about 4,200 results" rather than an exact count for this reason), or, if an exact count is a hard requirement, maintain it incrementally in a counter table rather than computing it per request. Promising an exact live count on every paginated response is a performance commitment worth pushing back on until it's confirmed to be genuinely needed.

How would you paginate a GraphQL API, and how does it differ from REST cursor pagination?

The Relay cursor connection spec is the de facto standard: a field returns a Connection type with edges (each an opaque cursor plus a node) and a pageInfo with hasNextPage/endCursor. Mechanically it's the same cursor idea as REST — same reasons, same opacity requirement — the difference is mostly ecosystem convention: GraphQL clients like Apollo and Relay have built-in support for walking a connection and merging pages into a local cache, so adopting the standard shape gets you client-side infrastructure for free in a way a bespoke REST cursor shape doesn't.

Sort stability: a client pages through results sorted by createdAt, and two orders have the identical timestamp. What can go wrong?

If the sort key isn't unique, the database is free to return those two rows in either order on different requests, which can put a row on both page N and page N+1, or on neither, depending on where the arbitrary tie-break lands relative to the page boundary. The fix is a compound sort key that's guaranteed unique — ORDER BY createdAt, id — and a cursor that encodes both fields, not just the timestamp. This is a common, subtle bug precisely because it only appears under real concurrent write volume, not in a small test dataset with obviously distinct timestamps.

How do you communicate "there are more results" to a client, and what's the trade-off between hasNextPage and just checking if the page came back full?

An explicit hasNextPage (or hasMore) boolean is unambiguous and costs one extra check server-side — usually fetching limit + 1 rows and trimming. Inferring "there's more" from "the page was full" is a false economy: it's wrong whenever the result set size happens to be an exact multiple of the page size, silently telling the client to stop one page early. I always return the explicit flag; the extra-row-fetch trick to compute it cheaply is worth knowing but not worth skipping the flag over.

Design review: an endpoint accepts both ?page= and ?after= parameters "for flexibility." What's your comment?

I'd flag it as a maintenance and correctness hazard rather than flexibility — the two schemes have fundamentally different consistency guarantees, and a client mixing them (grabbing an after cursor, then later switching to page=3) gets undefined, likely wrong, behavior with no error to warn them. If both audiences genuinely exist — a UI needing page numbers and an integration needing stable cursors — I'd rather see two distinct endpoints or a clearly documented "pick one mode, don't mix" contract than one parameter set trying to serve both semantics at once.

05 Idempotency and safe retries

Docs: RFC 9110 — idempotent methods · Stripe — idempotent requests

Unit 02 established that POST is neither safe nor idempotent by design — every call is a request to create something new. That's correct and unavoidable for the happy path, and a real production hazard the moment a network hiccups: a client sends POST /charges, the server processes it and charges the card, the response is lost to a timeout before the client sees it, and the client's retry logic — reasonably, since it never got confirmation — sends the exact same POST again. Without help, the server has no way to know "this is a retry of a request I already handled" versus "this is a genuinely new charge," and the customer gets billed twice.

The idempotency key pattern

The fix, standardized in practice by Stripe over a decade ago and now table stakes for any payments-adjacent API, is a client-generated idempotency key sent with the request: the server remembers which keys it has already processed and, on a repeat, returns the original response instead of doing the work again.

POST /charges HTTP/1.1
Idempotency-Key: 6a26a1e2-9f2c-4b1a-8e3e-1f0c9b7a2d55
Content-Type: application/json

{ "amount": 2999, "currency": "usd", "customerId": "cus_42" }

# retry with the SAME key after a timeout —
# server returns the ORIGINAL response, does not charge again
HTTP/1.1 201 Created
Idempotency-Key: 6a26a1e2-9f2c-4b1a-8e3e-1f0c9b7a2d55
{ "id": "ch_9f2c", "amount": 2999, "status": "succeeded" }

The mechanics that make this work, and the parts candidates usually skip over: the key is generated by the client, not the server — a UUID per logical operation, reused across retries of that same operation and never across two different operations. The server stores a mapping from key to the full response (status code, body, and ideally a hash of the request body) with a time-to-live — Stripe's is 24 hours — long enough to cover realistic retry windows, short enough not to accumulate forever. If a retry arrives with the same key but a different request body, that's a client bug (reusing a key for a different logical operation), and the correct server behavior is to reject it with a 409 rather than silently returning the stale first response for a request that was never actually issued.

Where idempotency keys go wrong in practice

MistakeWhat breaks

Making PATCH idempotent by construction

Unit 02 noted PATCH isn't idempotent by default — it depends on what the patch document says. You can make it idempotent deliberately by choosing a representation where repetition is a no-op: "set status to cancelled" is idempotent (applying it twice leaves the same status), "increment retryCount by 1" is not. JSON Merge Patch (RFC 7396) — a partial document of field:value pairs to set — is idempotent by construction, because it's expressed as "the field ends up equal to this," not "apply this delta." JSON Patch (RFC 6902) — a sequence of operations like add/remove/replace at a path — can express both idempotent operations (replace) and non-idempotent ones (test-then-add patterns, or anything modeling a delta), so its idempotency is per-document, not guaranteed by the format.

Gotcha

An idempotency key protects against duplicate submission of the same request — it does nothing for concurrent, different requests racing on the same resource. Two simultaneous PATCH /orders/5 calls from two different browser tabs, each setting a different field, aren't duplicates; they're a genuine concurrency conflict, and idempotency keys are the wrong tool for it. That's what optimistic concurrency control is for: an ETag/If-Match pair (or a version number in the body) that makes the second writer's request fail with 412 Precondition Failed if the resource changed since it last read it. Conflating the two — thinking an idempotency key somehow also solves concurrent-edit conflicts — is a common design gap that surfaces as "lost update" bugs in code review.

Try it — design the storage for idempotency keys

Exercise. Sketch the schema (or a Redis key shape) you'd use to store idempotency keys for a payments endpoint, including how you'd guarantee the atomic "check-and-reserve" step under concurrent retries, and how you'd detect a key reused with a different request body.

Solution sketch

A table (or Redis key) keyed on idempotency_key, with columns for a hash of the request body, the response status/body, a status of in_progress/completed, and an expiry timestamp. The atomic reserve step is a unique-constraint insert of (key, status=in_progress) — if the insert fails on the unique constraint, a concurrent request got there first, so you either return 409 (still processing, try again shortly) or block briefly and re-check. On completion, update the row with the real response and flip status. On a repeat request, compare the incoming body's hash against the stored one: match → return the stored response; mismatch → 409, this key was reused for a different operation.

Interview Q&A · idempotency and safe retries

Walk through exactly what goes wrong without an idempotency key, step by step.

Client sends POST /charges; server processes it, charges the card, and starts writing the 201 response; the connection drops before the client receives it. The client's retry logic sees a timeout, not a failure — it has no evidence either way — and resends the identical request. Without a key, the server has no memory that this "new" charge request is actually a duplicate of one it already fulfilled, so it processes it again and the customer is billed twice. The bug isn't in the retry logic, which is behaving correctly given what it knows — it's the missing mechanism for the server to recognize a retry as a retry.

Why must the idempotency key be generated by the client, not the server?

The whole point is that the client needs to be able to resend the same key on a retry of a request whose response it never received. If the server generated and returned the key, the client would need that response to learn the key — but the response is exactly what got lost. The client has to commit to a key before the first attempt, independent of whether that attempt succeeds.

What should the server do if the same key arrives with a different request body?

Reject with 409 Conflict, not silently return the original response. Returning the stale response would mean the caller for a genuinely different operation gets an answer that has nothing to do with what they asked — worse than an error, because it looks successful. Detecting this requires storing a hash (or the full body) of the original request alongside the response, specifically to compare against retries.

Two identical requests with the same idempotency key arrive within milliseconds of each other. What prevents both from executing the underlying operation?

An atomic "reserve" step — typically a unique constraint on the key column in a relational store, or a SETNX-style atomic check-and-set in Redis — so that only one of the two concurrent inserts succeeds. The loser sees the constraint violation and knows a sibling request got there first; it then either waits and polls for the result or returns a "still processing" response, rather than proceeding to do the underlying work a second time.

Do you need an idempotency key on a PUT endpoint?

No, not for the duplicate-retry problem — PUT is idempotent by the method's own semantics, so replaying the same PUT twice already lands in the same end state. Idempotency keys earn their keep specifically on methods that aren't idempotent by default: POST always, and PATCH when its patch document isn't inherently idempotent. Adding one to PUT anyway isn't harmful, just unnecessary complexity solving a problem that doesn't exist there.

How is an idempotency key different from an ETag/If-Match optimistic-concurrency check, and when do you need both?

An idempotency key deduplicates retries of the same logical request from the same caller. An ETag/If-Match pair detects that a resource changed since a client last read it, protecting against lost updates from different, legitimately concurrent requests. A payments endpoint typically needs both: the idempotency key so a network retry doesn't double-charge, and optimistic concurrency (where the endpoint modifies existing state rather than just creating something new) so two different actors editing the same order don't silently clobber each other's changes.

What TTL would you pick for stored idempotency keys, and what determines it?

Long enough to outlast realistic client retry/backoff windows including a plausible outage-recovery scenario, short enough to bound storage growth — Stripe's well-known choice is 24 hours, which I'd treat as a reasonable default rather than a universal law. The real driver is your own retry policy: if a client library is configured to give up after 5 minutes of exponential backoff, a much shorter TTL might be defensible, but I'd still pad generously, because the failure mode of expiring too early (a legitimate late retry becomes a duplicate charge) is far worse than the failure mode of expiring too late (a few extra rows in a table).

Is JSON Merge Patch always idempotent, and is JSON Patch never idempotent?

JSON Merge Patch is idempotent by construction — it's a set of "this field equals this value" assertions, and asserting the same value twice is a no-op the second time. JSON Patch isn't inherently one or the other; it's a sequence of operations, and whether a given document is idempotent depends on what those operations are — a replace at a fixed path is idempotent, an add that appends to an array, or a test-guarded conditional operation modeling a delta, generally isn't. I check the actual operations in a PATCH document before claiming idempotency, rather than assuming it from the format name.

Should idempotency keys be scoped per-endpoint, per-customer, or globally unique?

Globally unique in practice — a UUID per logical operation carries enough entropy that collision risk is negligible without needing endpoint or customer scoping to avoid clashes. What I do scope is the lookup: storing the key alongside the endpoint (or operation type) it was used for means a key accidentally reused across two different endpoints is caught as a mismatch rather than silently treated as a valid retry of the wrong operation.

A junior engineer asks: "why not just make everything idempotent instead of adding this key mechanism?" How do you answer?

Some operations are inherently non-idempotent by what they mean, not by an implementation choice — "create a new order" fundamentally means "make a new thing," so calling it twice creating two things is the correct behavior for two genuinely separate create requests. The idempotency key doesn't change that semantic; it solves a narrower, different problem — distinguishing "this is the same request replayed" from "this is a second, deliberate request that happens to look identical" — which is a client-intent question no amount of clever endpoint design can answer on the server's own. You need the client to tell you which situation you're in, and the key is how it does that.

How would you retrofit idempotency keys onto an existing POST /orders endpoint without breaking current clients?

Make the header optional at first — clients that send an Idempotency-Key get deduplication protection, clients that don't behave exactly as before, so nothing breaks on rollout. I'd ship the storage and lookup logic behind that optional header, update official SDKs to generate and send one automatically, and only after adoption data shows most traffic is covered would I consider whether to eventually require it for new API versions — mirroring how Stripe itself introduced the pattern without an initial hard requirement.

06 Error contracts and Problem Details

Docs: RFC 9457 — Problem Details for HTTP APIs · ASP.NET Core — error handling

Every team reinvents an error JSON shape at least once before discovering RFC 9457 already solved it — {"error": "..."}, then {"error": {"code": "...", "message": "..."}}, then someone adds a details array, and three services in the same company end up with three incompatible shapes that every client has to special-case. Problem Details (originally RFC 7807 in 2016, obsoleted and clarified by RFC 9457 in 2023) is the standardized answer: one JSON shape for errors, extensible per-problem-type, with a registered media type, application/problem+json, that tells clients "parse me as an error, not as your normal resource."

{
  "type": "https://api.example.com/problems/insufficient-funds",
  "title": "Insufficient funds",
  "status": 402,
  "detail": "Account bal_9f2c has insufficient balance for a 2999-cent charge.",
  "instance": "/charges/ch_2b3c",
  "balance": 1500,
  "currency": "usd"
}

Five members are standard — type (a URI identifying the problem kind, dereferenceable to human-readable docs, not necessarily to anything machine-fetched), title (a short, human-readable summary that should be constant for a given type), status (mirrors the HTTP status code, included because intermediaries sometimes strip or the body is inspected independently of the status line), detail (a human-readable explanation of this specific occurrence, not a template), and instance (a URI identifying this specific occurrence, useful for correlating with logs). Everything else — balance, currency above — is a problem-type-specific extension member — the whole reason the format scales from "just tell the client it failed" to "tell the client precisely what to show the end user," without every team inventing its own top-level shape to do it.

Validation errors: the one place Problem Details needs an extension

The base format handles "this request failed" well but says nothing about "these three fields failed validation, here's why for each." RFC 9457 doesn't standardize a validation-errors shape, but the convention that's become near-universal — and the one ASP.NET Core's built-in ValidationProblemDetails implements — is an errors extension member mapping field names to arrays of messages:

{
  "type": "https://api.example.com/problems/validation-failed",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "email": ["The Email field is required."],
    "amount": ["Amount must be greater than 0."]
  }
}

ASP.NET Core has shipped this by default since .NET Core 3.0's [ApiController] attribute — an unhandled model-validation failure on a controller action returns exactly this shape with no code written, and ProblemDetails/ValidationProblemDetails are first-class types in Microsoft.AspNetCore.Mvc that any custom exception handler can construct and return for non-validation failures too.

Designing the type URI space

The most common mistake is treating type as decoration and leaving it as the RFC's own placeholder, "about:blank" — valid per the spec (it means "no further semantics beyond the HTTP status code"), but it throws away the format's actual value, which is giving clients a stable, machine-matchable string to branch on instead of parsing detail text. A good type URI space is a small, deliberately curated catalog — /problems/insufficient-funds, /problems/order-already-cancelled, /problems/validation-failed — documented once, referenced by every error that's that kind of failure. Clients that care can switch on type; clients that don't can fall back to just showing title/detail to a human. What type should never become is one unique URI per error instance (that's what instance is for) or a direct mirror of internal exception class names (that's an abstraction leak that couples your API contract to your codebase's exception hierarchy).

Interview trap

"We return Problem Details, so our error contract is standardized." Adopting the JSON shape is the easy 20%. The value that actually matters — clients being able to branch reliably on error kind — depends entirely on discipline around type: a stable, documented, small catalog of type URIs that doesn't change across releases and doesn't leak internal exception names. Teams that adopt the shape but let type drift (different microservices inventing their own URI per exception class, or omitting it and leaving about:blank everywhere) get RFC-9457-shaped JSON with none of the actual interoperability benefit — clients are back to parsing detail strings, just now inside a standardized envelope.

Interview Q&A · error contracts

What problem does RFC 9457 actually solve, given that everyone already returns *some* JSON on error?

It's not about whether you return JSON on error — everyone does — it's about interoperability across services and clients that don't share a codebase. Without a standard, every team's error shape differs just enough that generic tooling (an API gateway that wants to log error kinds uniformly, a client SDK generator, a monitoring dashboard) can't handle errors generically and needs per-service special-casing. Problem Details gives everyone the same envelope — type/title/status/detail/instance — plus a registered media type, application/problem+json, so a client can detect "this response is a structured error" from the Content-Type alone, before even parsing the body.

What's the difference between title and detail, precisely?

title is generic to the problem type — it should read the same every time that type occurs, like a static label ("Insufficient funds"). detail is specific to this occurrence — it can and should include the concrete numbers, ids, or context relevant to this particular failure ("Account bal_9f2c has insufficient balance for a 2999-cent charge"). Getting this backwards — templating dynamic data into title — breaks any client logic that expects title to be a stable string per problem type.

Why shouldn't type be a 1:1 mirror of your internal exception class names?

Because it couples a public, versioned contract to an implementation detail that changes far more often and for reasons that have nothing to do with the API's behavior — a refactor that splits one exception class into two, or renames one for internal clarity, would otherwise force a breaking API change. The type catalog should be a small, deliberately curated, independently-versioned vocabulary of externally-meaningful problem kinds, translated from whatever internal exception structure produced them, not generated automatically from it.

How do you extend Problem Details for field-level validation errors, since the base RFC doesn't define that shape?

The de facto standard, and what ASP.NET Core's ValidationProblemDetails implements out of the box, is an errors extension member: an object mapping field name to an array of message strings for that field. It's not part of RFC 9457 itself, but it's become universal enough across frameworks (ASP.NET Core, Spring's equivalent, several Node frameworks) that treating it as a de facto convention is safe, rather than inventing a bespoke validation-error shape.

Should a Problem Details response ever include a stack trace or internal exception message?

Not by default, and never in production. Stack traces and raw exception messages leak implementation details — file paths, library versions, sometimes even fragments of connection strings — that are a real security and information-disclosure concern. ASP.NET Core's developer exception page includes this by design, but it's explicitly meant for local development only; the production exception handler should map any unhandled exception to a generic 500 Problem Details response with a correlation id in instance, and let the actual stack trace go to server-side logs, correlated by that id.

A client asks for a machine-readable error code in addition to type, since type is a URI and awkward to use as an enum key in their code. What do you tell them?

That's a reasonable ask and a common extension — nothing in RFC 9457 prevents adding a short, stable extension member like code (a bare string, e.g. "insufficient_funds") alongside type specifically for easy programmatic matching, while type stays a dereferenceable URI for humans who follow it to documentation. Several real-world APIs do exactly this — type for the spec-compliant identifier, a shorter sibling field for ergonomic switch statements — and it costs nothing to support both as long as they're kept in lockstep from the same catalog.

Is status inside the Problem Details body redundant with the actual HTTP status line?

Usually, but not always, and that's exactly why the RFC keeps it. Intermediaries occasionally rewrite status codes (some overzealous API gateways normalize everything to 200 with the "real" status in the body — a bad but real practice), and some client tooling inspects the response body independently of the transport-level status line. Including status in the body gives you a self-describing document that doesn't depend on the status line surviving intact through every hop, at the minor cost of one field that, in the common case, just repeats what the client already has.

How would you migrate an existing API with three inconsistent error shapes onto Problem Details without breaking every current client at once?

Introduce it behind content negotiation or a new API version rather than rewriting every error response overnight — clients that send Accept: application/problem+json (or hit the new version) get the standardized shape, existing clients keep receiving the legacy shape until they migrate on their own schedule. I'd build the new shape from a single internal error-mapping layer from day one, so the two output formats are two thin serializers over one source of truth rather than two independently-maintained error paths that drift apart.

Does adopting Problem Details mean giving up custom, product-specific error metadata?

No — that's the entire point of extension members. The five standard fields are a floor, not a ceiling: a payments API can add balance and currency, an inventory API can add availableQuantity, without breaking the base contract, because generic Problem-Details-aware tooling only ever needs the standard five and safely ignores what it doesn't recognize. Teams that think adopting the RFC means losing their domain-specific error richness usually haven't looked past the five required members to the explicitly open-ended extension mechanism.

What HTTP status would you use for "the order exists, the request is well-formed, but the order is already cancelled and can't be cancelled again" — and what type?

409 Conflict — the request is syntactically and semantically valid in isolation, but conflicts with the resource's current state, which is exactly 409's definition. I'd give it its own type, something like /problems/order-already-cancelled, distinct from a generic conflict, so a client can specifically detect "this is a stale-state issue, refresh and re-check" rather than treating it the same as an unrelated 409 like a duplicate unique key.

07 OpenAPI and contract-first design

Docs: OpenAPI Specification 3.2.0 · ASP.NET Core — OpenAPI document generation

OpenAPI (formerly "Swagger" before the specification was donated to the Linux Foundation in 2015) is a machine-readable contract describing an HTTP API's paths, operations, parameters, request/response schemas, and auth requirements — in JSON or YAML. Its value compounds: one document drives interactive docs, generated client SDKs in a dozen languages, mock servers for frontend teams to build against before the backend exists, contract tests that fail a build when implementation drifts from spec, and API gateway configuration. The version that matters most right now is 3.2.0, released 19 September 2025 — the first meaningful spec revision since 3.1 in 2021 — adding native description of the HTTP QUERY method (unit 02), an additionalOperations map for describing arbitrary/custom HTTP methods, hierarchical and typed tags for organizing large APIs, and itemSchema for describing streamed responses (Server-Sent Events, NDJSON) without contorting them into a single monolithic schema.

The industry's practical center of gravity for internal and small-team APIs has shifted code-first over the last several years, mostly because tooling caught up: generating an accurate spec from code got dramatically easier, while hand-authoring and keeping a separate YAML file in sync got relatively harder to justify. Large, multi-team, or public-facing APIs still lean contract-first specifically because the spec review — "does this shape make sense" — needs to happen before any code exists, when it's cheapest to change.

The .NET landscape, precisely

Microsoft.AspNetCore.OpenApi has been the built-in, first-party OpenAPI document generator since .NET 9 — builder.Services.AddOpenApi() and app.MapOpenApi() in a handful of lines, no third-party package required, generating a spec by reflecting over minimal API/MVC endpoint metadata. As of late 2026 it targets OpenAPI 3.1, not the newer 3.2 — a gap worth naming precisely if asked "does .NET support the latest OpenAPI" (no, not yet, though 3.1→3.2 is a much smaller jump than 3.0→3.1 was). Swashbuckle (Swashbuckle.AspNetCore), the long-standing community package that was the de facto default for years before .NET 9, still exists and is still maintained, also capped at OpenAPI 3.1 — it remains the better choice specifically when you need its richer set of customization filters and UI options that the newer first-party generator doesn't yet replicate. Neither ships a bundled Swagger UI by default anymore in the new templates; teams typically wire in Swagger UI, Scalar, or Redoc themselves as a separate, deliberate choice rather than getting one out of the box.

builder.Services.AddOpenApi();          // Microsoft.AspNetCore.OpenApi, built in since .NET 9

app.MapOpenApi();                        // serves /openapi/v1.json

   .WithName("GetOrder")
   .WithSummary("Fetch a single order by id")
   .Produces(StatusCodes.Status200OK)
   .ProducesProblem(StatusCodes.Status404NotFound);

app.Run();

Keeping the contract honest: linting and contract testing

A spec that isn't validated against anything is documentation fiction waiting to happen. Two complementary practices close the gap: linting (Spectral is the widely-used open-source tool) checks the spec itself for style and correctness — every operation has a summary, every error response uses Problem Details, naming conventions are consistent — independent of whether the implementation matches it. Contract testing checks the other direction: does the running implementation's actual behavior match what the spec promises? For code-first APIs this risk is smaller by construction (the spec is generated from the same code that serves requests), but examples, descriptions, and anything hand-annotated can still drift from reality; for contract-first APIs it's essential, because nothing structurally prevents the implementation from silently diverging from a hand-written spec over time.

Interview trap

"We have OpenAPI docs, so our contract is documented." A generated spec with every parameter typed as string, no examples, no error responses described, and a one-line summary copied across fifty endpoints is technically an OpenAPI document and nearly useless as a contract — it won't produce a usable generated SDK, a meaningful mock server, or a client that can distinguish a 404 from a 409 without reading source code. The stronger signal in an interview is naming the specific things that make a spec actually useful: real request/response examples, every non-2xx response documented with its Problem Details type, and enough parameter-level description that a consumer never has to ask a human what a field means.

Try it — spot the useless spec

Exercise. Generate (or imagine) an OpenAPI document for a minimal ASP.NET Core endpoint with no .WithSummary(), no .Produces<T>() calls, and a bare string return type. List everything a client-SDK generator or a mock-server tool would get wrong or have to guess at from that spec alone.

What's typically missing

Response schema (the SDK generator sees "returns 200, body type unknown," so a typed client either falls back to object/dynamic or fails to generate a method at all), every non-200 status code the endpoint can actually return (so error handling in the generated client is nonexistent), parameter descriptions (a mock server can return syntactically valid but semantically meaningless fake data), and any indication of authentication requirements on that specific operation. The fix in ASP.NET Core is almost entirely a matter of adding the metadata calls (.Produces<T>(), .ProducesProblem(), .WithSummary()) that the framework already supports — the gap is discipline, not tooling capability.

Interview Q&A · OpenAPI and contract-first design

What's actually new in OpenAPI 3.2.0, and why does it matter?

Released 2025-09-19, it's the first real spec revision since 3.1 (2021). The headline additions: native support for describing the HTTP QUERY method, an additionalOperations extension point for arbitrary/custom HTTP methods beyond the fixed set the spec used to assume, hierarchical and typed tags for organizing large multi-team APIs, and itemSchema for describing streamed response bodies (SSE, NDJSON) as a stream of typed items rather than one contorted monolithic schema. It matters because it's evidence the spec is still evolving to track where HTTP itself is moving — QUERY support landed in the spec before the RFC that formalizes the method was even finalized.

Contract-first or code-first — how do you actually decide, for a specific team?

I look at who needs to review the shape before it's built, and how many independent consumers exist. A public API or one consumed by several other teams benefits from contract-first, because the review that matters — "does this endpoint shape make sense" — happens on a document, before any code investment, and a frontend or partner team can start against a mock server immediately. A small, fast-moving internal API where the same team owns both sides doesn't get much from that ceremony, and code-first with strong endpoint metadata gets you an accurate spec for free as a byproduct of writing the code once.

Is .NET's built-in OpenAPI support current with the latest spec version?

Not quite — Microsoft.AspNetCore.OpenApi, built in since .NET 9, targets OpenAPI 3.1, and as of late 2026 hasn't caught up to 3.2.0 (released September 2025). Swashbuckle, the older community package, is in the same position. It's a gap worth naming precisely rather than glossing over — the jump from 3.1 to 3.2 is much smaller than 3.0 to 3.1 was, but if a team specifically needs to describe an HTTP QUERY operation or a streaming response using 3.2's new constructs, neither of .NET's mainstream generators supports that natively yet.

What's the difference between Microsoft.AspNetCore.OpenApi and Swashbuckle, and when would you still pick Swashbuckle on a new .NET 9+ project?

Microsoft.AspNetCore.OpenApi is the newer, first-party, minimal generator — no extra package, reflects endpoint metadata into a spec, designed to be extended via document/operation transformers. Swashbuckle is the older, community-maintained package with a much larger, longer-established set of customization filters, richer XML-comment integration, and its own bundled Swagger UI. I'd still reach for Swashbuckle on a new project specifically if I need a customization it supports that the first-party generator doesn't yet, or if the team already has Swashbuckle-specific tooling and conventions built up elsewhere that migrating would cost more to replace than it's worth.

Neither .NET OpenAPI generator ships a UI by default anymore — what changed, and what do teams do instead?

Newer ASP.NET Core project templates generate only the OpenAPI document endpoint (AddOpenApi()/MapOpenApi()), with no Swagger UI wired up automatically the way older templates did. Teams now deliberately choose and add a UI themselves — Swagger UI (the traditional choice, still fine), Scalar (a newer, popular alternative many teams reach for), or Redoc — as an explicit package reference and a couple of lines of middleware, rather than inheriting one by default. I'd frame this as the framework giving you the document as the primitive and treating the UI as a separable, swappable concern.

How does a mock server generated from an OpenAPI spec help a frontend team, concretely?

It lets frontend development start the moment the contract is agreed, rather than waiting for a working backend — a tool reads the spec's schemas and examples and serves syntactically valid fake responses matching them, so frontend code can be written and even partially tested against realistic shapes before a single backend line exists. It also forces the spec's examples to be good enough to be useful, which is a healthy side pressure: a spec with no examples produces a mock server returning garbage, which surfaces the documentation gap immediately rather than months later.

What does a linter like Spectral actually check that a schema validator doesn't?

A schema validator confirms the OpenAPI document is syntactically valid per the OpenAPI meta-schema — it won't complain about a spec that's valid but low-quality. A linter enforces house style and completeness rules on top of validity: every operation has a summary and an operationId, every non-2xx response is documented, naming conventions are consistent (camelCase everywhere, not a mix), security requirements are declared where expected. It's the difference between "this YAML parses as OpenAPI" and "this spec is actually good enough to generate a usable SDK from."

For a code-first API, do you still need contract testing?

Less urgently for structural drift — path shapes, parameter types, and status codes can't diverge from the code, because the spec is generated from it. But hand-maintained pieces still rot: examples that were accurate when written and are now stale, prose descriptions that describe old behavior, and anything generated from attributes a developer forgot to update alongside a behavior change. I'd still add a lighter-weight check — CI that flags example/description staleness against recent changes — even on a fully code-first pipeline, just calibrated to a smaller risk than a hand-authored contract-first spec carries.

Should every field in a request/response schema be documented with a description, or is that overkill?

Every field a consumer could plausibly misinterpret, yes — anything with units, a non-obvious enum, or a name that doesn't fully disambiguate its meaning (total — does it include tax? unit 03's exact trap). Self-evident fields like a resource's own id don't need a paragraph. I calibrate to "would a new engineer on a different team, reading only this spec, get this field right without asking someone" — that bar catches the fields that matter and doesn't demand prose for every trivial one.

How would you introduce OpenAPI to a team of five internal services that currently has zero API documentation?

Start code-first on the highest-traffic or most-integrated service first, since that's where the payoff is most visible fastest — wire up Microsoft.AspNetCore.OpenApi, add summaries and typed responses incrementally rather than all at once, and get a Scalar or Swagger UI in front of it so the team can see the immediate benefit (interactive docs, a way to try requests without Postman collections passed around by hand). I'd defer contract testing and strict linting until the spec habit is established — introducing all the rigor at once alongside the tooling itself is a common way to make the whole initiative feel like ceremony rather than a clear win.

What's the risk of generating client SDKs directly from an OpenAPI spec without human review?

The generated SDK is only as good as the spec's precision — a loosely-typed parameter, a missing required field, or an enum with no described semantics produces a technically-working but poorly-ergonomic client (everything typed as object, no IntelliSense-useful names, error handling that can't distinguish failure kinds). It also silently ships any spec mistake straight into consumer code with no human catching it in between — a typo'd field name in the spec becomes a typo'd property in every generated client simultaneously. I treat spec review as a gate before SDK generation for anything public-facing, precisely because that step has no other safety net once generation is automated.

08 Rate limiting and backpressure

Docs: IETF — RateLimit header fields draft · RFC 6585 — 429 Too Many Requests

Rate limiting exists to protect the server from being overwhelmed — by a genuine traffic spike, a buggy client retry-looping without backoff, or deliberate abuse — and to keep one noisy tenant from starving every other tenant sharing the same infrastructure. It's also, less obviously, a form of communication: a well-designed rate limit tells clients exactly how much room they have and when it refills, so well-behaved clients can self-throttle instead of finding the limit by repeatedly hitting it.

Token bucket vs. leaky bucket vs. fixed/sliding window

The fixed-window boundary flaw is the one interviewers most often probe, because it's a genuine, easy-to-miss correctness gap: a "100 requests per minute" fixed window reset at :00 lets a client send 100 requests at 0:59 and another 100 at 1:00 — 200 requests in two seconds, well within the letter of the rule and wildly outside its spirit. Token bucket avoids this by tracking a continuously-refilling balance rather than a clock-aligned counter, which is the main reason it's the default choice for anything where burst-at-the-boundary is a real concern rather than a theoretical one.

Communicating limits: the headers, and their unsettled state

RFC 6585 standardized the 429 status code back in 2012, but left the actual limit-communication headers to convention — which produced exactly the fragmentation you'd expect: GitHub's X-RateLimit-Limit/X-RateLimit-Remaining/X-RateLimit-Reset, Twitter's own variant, Stripe's Retry-After alone. The IETF has an active draft — RateLimit and RateLimit-Policy header fields, at version 11 as of May 2026 — standardizing a cleaner shape, but it has been in draft for several years now and still hasn't reached RFC status. State that precisely if asked: it's the closest thing to a standard, it's what a new API should probably emit, but it is not yet a ratified RFC, and the older X-RateLimit-* convention remains what most existing production APIs actually send.

HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit: limit=100, remaining=0, reset=30
RateLimit-Policy: 100;w=60

{
  "type": "https://api.example.com/problems/rate-limited",
  "title": "Rate limit exceeded",
  "status": 429,
  "detail": "Limit of 100 requests per 60s exceeded; retry after 30s."
}

Two things every rate-limited response should carry regardless of which header convention you pick: Retry-After (an actual RFC 9110 standard header, unambiguous, universally understood by HTTP clients and CDNs) so a client that ignores everything else at least knows when to try again, and a Problem Details body (unit 06) so the failure is self-describing rather than a bare 429 the client has to already know the meaning of.

What to key the limit on, and per-endpoint vs. global

The choice of key changes what the limit actually protects against: per-API-key or per-user limiting protects other tenants from one noisy customer; per-IP limiting protects against unauthenticated abuse but punishes every user behind a shared NAT or corporate proxy identically; a global limit protects the server itself regardless of who's asking, useful as a last-resort circuit breaker but useless for fairness between tenants. Real production setups layer more than one: a per-API-key limit for fairness, plus a global limit as a backstop, is a common combination. Endpoint-specific limits matter too — a cheap, cacheable GET /orders/5 and an expensive POST /reports/generate that spins up a background job have wildly different real costs to the server, and a single blanket "1000 requests per minute" number either starves the expensive endpoint or wastes headroom on the cheap one.

Gotcha

A rate limit with no Retry-After and no rate-limit headers at all is worse than no rate limit for well-behaved clients — it turns "back off" into a guessing game. A client that receives a bare 429 with nothing else has to invent a retry strategy (fixed delay? exponential backoff? how long?) with zero information from the server about what would actually work, and different client implementations will guess differently, which is precisely the kind of uncoordinated retry storm that makes an already-stressed server's day worse, not better. If you ship rate limiting, shipping the headers that make self-throttling possible isn't optional polish — it's the mechanism that makes the limit work as intended instead of as a blunt wall clients bounce off unpredictably.

Interview Q&A · rate limiting and backpressure

Explain the fixed-window boundary flaw and why token bucket doesn't have it.

A fixed window resets its counter at a hard clock boundary, so a client can exhaust a full quota just before the reset and a full quota again just after, achieving up to double the nominal rate in a short span straddling the boundary. Token bucket has no hard reset — tokens refill continuously at a steady rate and the bucket has a capacity ceiling — so the maximum burst is bounded by the bucket size, not multiplied by a boundary coincidence, and the long-run average rate genuinely converges to the configured rate regardless of when a client happens to send its requests.

Is the IETF RateLimit header draft an RFC yet? What should you say if you don't know the exact current status?

As of the most recent draft I'm aware of (version 11, May 2026), no — it's still an internet-draft, not a ratified RFC, despite being in development for years. The honest answer names the uncertainty precisely: it's the closest thing to an emerging standard and worth adopting for a new API, but it's not yet something you can call "the RFC-standard rate limit header" without a caveat, and the older vendor-specific X-RateLimit-* headers remain far more common in APIs already shipped.

Why key a rate limit on API key rather than IP address?

IP-based limiting punishes everyone sharing an address identically — a corporate NAT, a university network, or a mobile carrier's shared IP pool can put many unrelated users behind one IP, so one heavy user's traffic can exhaust a shared quota for everyone else on that IP. API-key (or authenticated user id) limiting attributes usage to the actual tenant responsible for it, which is both fairer and a more accurate signal of who's actually generating load. IP-based limiting still has a role — it's the only lever you have against genuinely unauthenticated traffic, like a login endpoint being brute-forced before any key exists.

Why is Retry-After worth including even if you also send vendor-specific rate-limit headers?

It's an actual RFC 9110 standard, universally understood by generic HTTP clients, browsers, and CDNs with no special integration needed — a client that has never heard of your X-RateLimit-* convention still knows what to do with Retry-After. Vendor-specific headers add richer detail (how much quota remains, when the window resets) for clients sophisticated enough to use them, but Retry-After is the baseline that guarantees even the simplest client backs off correctly.

A single global rate limit versus per-tenant limits — what does each actually protect against?

A global limit protects the server's own capacity regardless of who's asking — it's a last-resort circuit breaker against total overload, useful even in a single-tenant system. Per-tenant (per-API-key or per-user) limits protect fairness between tenants sharing that capacity — without one, a single misbehaving customer can consume the entire global budget and starve everyone else, even though the server as a whole never technically exceeded its global limit. Production systems serving multiple customers typically need both, layered.

Should an expensive, async report-generation endpoint share the same rate limit bucket as a cheap GET lookup?

No — a blanket limit sized for the cheap endpoint either starves the expensive one (10 report generations per minute might be too few if that's genuinely the endpoint's real capacity) or, sized for the expensive endpoint, wastes headroom that lets the cheap endpoint be hammered far past what's healthy. I'd give expensive, resource-intensive operations their own, tighter bucket, keyed the same way (per API key) but with limits calibrated to that endpoint's actual backend cost rather than a single number applied uniformly across the whole API surface.

How would you rate-limit a GraphQL endpoint, where every request hits the same single URL regardless of what it actually asks for?

Counting raw requests is close to meaningless for GraphQL, since one request can be a trivial single-field query or a deeply nested query fanning out into dozens of resolver calls. The common approach is query-cost analysis: assign each field or resolver a cost, compute a total cost per incoming query before executing it, and rate-limit (or reject outright) based on cumulative cost rather than request count — treating the limit as a budget of "resolver work," not "number of HTTP calls."

What's the risk of an aggressive rate limit with no headers, from the server's own perspective, not just the client's?

Clients with no signal about when to retry tend to guess, and a common bad guess is a short fixed delay retried by many clients simultaneously — which synchronizes into a retry storm hitting the server in lockstep right as it's trying to recover from whatever caused the limiting in the first place. Providing Retry-After with some jitter guidance, or letting well-behaved client libraries implement exponential backoff with jitter using the headers you provide, is partly a self-protective measure for the server, not purely a courtesy to clients.

Leaky bucket vs. token bucket — when would you actually pick leaky bucket?

Leaky bucket is the right choice when the goal is smoothing traffic into a steady downstream rate regardless of how bursty the input is — for example, throttling outbound calls to a downstream third-party API that has its own strict, non-burst-tolerant rate limit, where you'd rather queue and drain evenly than let your own bursts pass straight through and immediately trip the downstream limit. Token bucket, by contrast, is the right default when the goal is protecting your own server while still being generous to legitimately bursty, well-behaved clients — most public-facing API rate limiting is this second case, which is why token bucket is the more common default.

How do you rate-limit fairly across a fleet of API gateway instances without a shared bottleneck?

A rate limiter that's purely local to each instance under-limits in aggregate — a client hitting N instances round-robin effectively gets N times the intended quota. The standard fix is a shared, fast store (Redis is the near-universal choice) holding the counter or token bucket state, so every instance checks and decrements against the same source of truth; the trade-off is that store becoming a new dependency and potential latency/availability concern in the hot request path, which is why the token-bucket check is usually implemented as a single cheap atomic Lua script or similar, not a multi-round-trip transaction.

A partner team asks "just tell us the limit so we can build to it" — what's the risk of publishing an exact static number?

Publishing a specific static number invites clients to build right up to that exact edge, leaving zero margin for legitimate traffic variance, and it commits you to that number in a way that's awkward to lower later even if it turns out to be too generous for your actual capacity. I'd rather communicate limits dynamically via headers on every response (so clients that adapt automatically never need the static number at all) and, if a partner genuinely needs a documented ceiling for capacity planning, frame it as "your current allocation, subject to change with notice" rather than a permanent contractual number.

09 Deprecation and API lifecycle

Docs: RFC 9745 — the Deprecation HTTP header field · RFC 8594 — the Sunset HTTP header field

Every API design decision made in units 01–08 eventually needs to be un-made — a field renamed, an endpoint replaced, a whole version retired. What separates a mature API program from one that breaks its consumers by surprise is not that it never changes, it's that every change is announced, dated, and given a runway long enough for consumers to react before it's enforced. Two purpose-built HTTP headers now exist specifically to make that announcement machine-readable rather than something buried in a changelog nobody's client reads.

Deprecation vs. Sunset: two headers, two moments

HeaderRFCSaysValue

They're complementary, not redundant, and using them together tells a client both "this is already old" and "here's exactly how much runway you have left" — a distinction that matters because a resource can be deprecated for a long time with no sunset date fixed yet (still safe to use, but on notice), and conflating the two into one signal loses that nuance.

GET /v1/orders/5 HTTP/1.1

Link: ; rel="deprecation"
Content-Type: application/json

{ "id": "5", "status": "pending" }

The Link header with rel="deprecation" pointing at a migration guide is the piece that turns a machine-readable signal into something an actual engineer can act on without first finding your docs site manually — a well-built HTTP client or API monitoring tool can surface that link directly to whoever's on call for that integration.

The lifecycle, end to end

A responsible deprecation isn't a single event, it's a sequence with distinct, separately-communicated stages: announce (a new version or replacement ships, the old path starts returning Deprecation, the changelog and docs explain why and what to migrate to) → warn with a date (once the replacement has had time to stabilize, add Sunset with a concrete future date — not "eventually," a real date consumers can put on their own roadmap) → escalate as the date nears (proactive emails to registered API-key holders, dashboard warnings, sometimes a temporary artificial slowdown or occasional synthetic error on the deprecated path to make silent non-migration painful before it's fatal) → retire (the sunset date arrives; the endpoint returns 410 Gone, or is removed from routing entirely, depending on how much residual signal you want to give latecomers).

It costs nothing extra to distinguish and saves real debugging time on the other end.

How long is long enough

There's no universal number — the right runway scales with how disruptive the migration is and who's affected. A internal service-to-service API where you control both sides might reasonably sunset in weeks, since coordinating the migration is a Slack message away. A public API with thousands of independent integrators, especially ones without dedicated engineering teams watching your changelog, needs months at minimum — GitHub and Stripe both typically give a year or more notice for major version sunsets specifically because their consumer base is large, heterogeneous, and includes plenty of "set it up once in 2019, nobody's touched it since" integrations that won't notice a shorter warning until it's too late.

Interview trap

"We deprecated it in the changelog, so consumers were warned." A changelog is something a consumer has to actively go read; a Deprecation/Sunset header is something their own tooling can detect automatically, on every single response, without anyone remembering to check a docs site. The gap between "we told people" and "people actually got told" is exactly what machine-readable headers close — and the strongest version of this answer also mentions actively notifying registered API-key holders directly (email, dashboard), because even the best headers only reach clients whose engineers built monitoring for them, which by no means describes every integrator, especially smaller or less sophisticated ones.

Interview Q&A · deprecation and lifecycle

What's the practical difference between the Deprecation and Sunset headers, and why send both?

Deprecation (RFC 9745) is a statement about the past — "this has been deprecated as of this date" — and can exist with no end date attached at all, signaling "on notice, still safe, no fixed deadline yet." Sunset (RFC 8594) is a commitment about the future — "this will stop working on this date." Sending only Deprecation tells a client to start planning; sending both tells them exactly how much time they have, which is the information that actually drives when a migration gets prioritized on someone else's roadmap.

Why prefer 410 Gone over 404 Not Found for a retired endpoint?

404 is ambiguous between "never existed," "you mistyped the URL," and "this used to exist and was removed" — a consumer debugging a sudden failure has to investigate to figure out which. 410 removes that ambiguity: it specifically means "this resource existed and has been deliberately, permanently removed," which immediately points a confused integrator at "check whether I missed a migration" rather than "check my code for typos." It's a small, essentially free signal that saves real debugging time on the consumer's side.

How would you decide the length of a deprecation window for a specific breaking change?

I scale it to two things: how many independent consumers are affected and how disruptive the migration actually is for them. A change affecting a handful of internal services you can coordinate with directly might need only weeks. A public API change affecting thousands of external integrators — many of whom aren't actively watching a changelog — needs months at minimum, and a genuinely major version sunset (the kind GitHub or Stripe do) often gets a year or more, specifically because the long tail of "set it up once, forgot about it" integrations needs that much lead time to even notice.

Is publishing a changelog entry sufficient notice for a breaking change?

Not on its own — a changelog requires the consumer to actively check it, and most don't until something breaks. Machine-readable headers (Deprecation/Sunset) that appear on every actual response are detectable by automated tooling without anyone remembering to look, and direct notification (email to registered API-key holders, dashboard warnings) reaches even integrators with no automated monitoring at all. A mature deprecation process layers all three — changelog for the record, headers for tooling, direct outreach for humans — rather than relying on any single channel.

Should a deprecated endpoint's behavior degrade before its sunset date — intentionally slower, or occasional synthetic errors — to encourage migration?

It's a legitimate, if aggressive, tool for the final stretch before a sunset date, specifically aimed at consumers who've ignored every earlier signal — a small, clearly-flagged rate of synthetic 429s or added latency makes continuing to ignore the deprecation actively uncomfortable rather than free. I'd only reach for it close to the deadline, always alongside a clear message explaining why (never a silent degradation that looks like an unrelated bug), and never as the first or only signal — it should escalate a warning that's already been given multiple times through cleaner channels, not substitute for one.

How do you deprecate a single field in a response body, as opposed to a whole endpoint or version?

There's no dedicated HTTP header for field-level deprecation the way there is for whole resources, so this is where documentation and schema-level signaling carry more weight — OpenAPI supports a deprecated: true flag on individual schema properties, which SDK generators can surface as compiler warnings or deprecated-attribute annotations in generated client code, giving developers an IDE-level nudge without anything breaking yet. GraphQL has the cleaner native answer here: @deprecated(reason: "...") directly on a field, which tooling like GraphQL introspection and IDE plugins already understand out of the box.

A consumer complains they had no idea an endpoint they depend on was sunset. Your logs show the Deprecation header was present for eight months. What do you actually learn from this?

That header presence alone isn't proof of effective notice — it proves the signal was sent, not that anyone received or acted on it. I'd treat it as a gap in the outreach layer, not evidence the consumer is entirely at fault: did they have a registered contact we actually emailed, did our dashboard surface the warning anywhere a human would see it, was the migration guide linked from the header actually useful? The postmortem question isn't "did we technically warn them," it's "was our warning actually detectable by someone who wasn't already looking for it."

What's the argument for versioning at the level of the whole API rather than deprecating individual fields and endpoints piecemeal forever?

Piecemeal, field-by-field deprecation without ever cutting a new version can leave an API in a permanent state of "half old, half new," where a consumer integrating today has no clean, single point-in-time contract to build against — they inherit years of accumulated deprecated-but-still-present cruft alongside the current design. A periodic major version gives both the API team and consumers a clean cutover point: everything deprecated up to that point actually gets removed, rather than lingering indefinitely because removing any one piece never feels urgent enough on its own.

How would you handle a customer on a contractually-committed SLA who says they can't migrate off a sunsetting version in time?

That's a business negotiation as much as a technical one, and I'd treat it that way rather than unilaterally deciding on the engineering side — options include a paid extended-support exception for that specific account, a dedicated migration assistance engagement, or, if genuinely necessary, pushing the sunset date for the whole version if enough large accounts are in the same position that the original timeline was simply too aggressive. What I wouldn't do is quietly let one account's non-migration indefinitely block retiring the version for everyone else — that turns a dated sunset into a suggestion, and every future deprecation announcement loses credibility once consumers learn the dates aren't real.

Does GraphQL's "never remove, only deprecate" philosophy (unit 03) mean it never needs a sunset process at all?

It defers the problem, it doesn't eliminate it — a schema that only ever adds and marks-deprecated, never removes, accumulates permanent cruft: resolver code for fields nobody should use anymore, query-cost budget spent maintaining backward compatibility for things with zero remaining legitimate traffic. Mature GraphQL API programs still run a real, if less urgent, sunset process for long-deprecated fields — tracking usage analytics per field, confirming near-zero traffic, and eventually removing them — it's just decoupled from any single "version cutover" moment the way REST's version-based deprecation usually is.

10 REST vs gRPC vs GraphQL

Docs: grpc.io — introduction to gRPC · graphql.org — introduction to GraphQL

These three solve overlapping problems with different bets about who the client is and what they need. REST bets on a uniform, cacheable, human-readable interface that any HTTP-aware tool already understands. gRPC bets on performance and strict typing for service-to-service calls where both ends are code you control. GraphQL bets on giving the client precise control over exactly what data comes back, at the cost of most of HTTP's own caching semantics. None of the three is "better" in the abstract — the right choice falls out of who's calling, how, and how often, which is exactly the framing a lead-level answer should lead with instead of a technology preference.

gRPC: contracts and performance by construction

gRPC's .proto file isn't optional documentation the way OpenAPI often ends up being for REST — it's the actual source of code generation for both client and server stubs in whichever languages you target, so client and server are structurally incapable of disagreeing about the shape of a call the way two independently-maintained REST implementations can. Protocol Buffers serialize to a compact binary format, meaningfully smaller and faster to (de)serialize than JSON for the same data, which is why gRPC is the default choice inside most large microservice fleets doing high-volume internal service-to-service calls where every millisecond and every byte across the network adds up.

service OrderService {
  rpc GetOrder(GetOrderRequest) returns (Order);
  rpc StreamOrderUpdates(StreamRequest) returns (stream OrderEvent);
}

message Order {
  string id = 1;
  string status = 2;
  double total = 3;
}

The trade-off is real, not just a rough edge: binary payloads aren't human-inspectable with curl or a browser devtools network tab the way JSON is, and gRPC's native reliance on HTTP/2 trailers for status codes means browsers can't speak it directly at all — gRPC-Web requires a proxy translation layer, and increasingly teams reach instead for the Connect protocol (from the makers of Buf, now under the CNCF), which is wire-compatible with gRPC but also speaks plain HTTP/1.1 with JSON directly, no separate proxy needed — a meaningfully simpler deployment story that's gained real adoption specifically to sidestep gRPC-Web's proxy requirement.

GraphQL: one endpoint, client-shaped responses

GraphQL flips REST's model: instead of the server defining fixed-shape resources at fixed URLs, the client sends a query describing exactly which fields it wants, across however many related types, and gets back exactly that shape — nothing more, nothing less. This directly solves two REST pain points that show up constantly at scale: over-fetching (a mobile client that only needs an order's status and total still receiving the full representation with every field) and under-fetching, better known as the N+1 problem (fetching an order, then separately fetching its customer, then separately fetching each line item's product — three or more round trips for what's conceptually one screen's worth of data).

query {
  order(id: "5") {
    status
    total
    customer { name }
    lines { productName quantity }
  }
}

The cost is that almost everything HTTP gives REST for free has to be rebuilt: caching (a single query can request a different field combination every time, so a CDN can't cache by URL the way it caches a REST GET — GraphQL clients like Apollo build their own normalized, object-identity-based client-side cache instead), and query complexity (a client can, deliberately or accidentally, request a deeply nested query that fans out into an enormous number of resolver calls server-side — the query-cost-analysis rate limiting from unit 08 exists specifically because of this). Federation — splitting one logical GraphQL schema across multiple backend services, each owning a subgraph, stitched together by a gateway — is how GraphQL scales past a single monolithic resolver layer at large organizations; Apollo Federation v2 is the dominant specification for this, and as of Hot Chocolate/Fusion 16.5 (2026), the .NET GraphQL ecosystem's leading server implementation reached 100% compliance with it, which is a meaningfully recent milestone worth citing if the topic of .NET-side GraphQL federation comes up.

Interview trap

"GraphQL solves REST's over-fetching problem, so it's strictly better for our public API." It solves over-fetching for the specific client that wrote that specific query — at the direct cost of HTTP-native caching, which for a public, high-read API serving the same handful of query shapes repeatedly to thousands of consumers is often worth far more in practice than per-client field selection. A public REST API behind a CDN can serve a popular GET /orders/5 from cache thousands of times without touching the origin server at all; the equivalent GraphQL query, POSTed with a body, isn't a cacheable GET by the CDN's own logic without extra, non-default infrastructure (persisted queries mapped to cacheable GETs, a purpose-built GraphQL CDN layer). The stronger answer names exactly which problem each technology optimizes for, rather than treating "more flexible for the client" as automatically "better."

Interview Q&A · REST vs gRPC vs GraphQL

If gRPC is faster and more strictly typed, why isn't it the default choice for public APIs too?

Because its advantages are specifically the advantages of a client and server you both control: strict typing from a shared .proto file assumes both sides regenerate stubs from the same source, and the binary wire format assumes nobody needs to inspect traffic with a browser or curl. A public API's consumers are heterogeneous, often unsophisticated about your specific tooling, and benefit enormously from HTTP-native caching and human-readable payloads — exactly what gRPC trades away for performance. Browsers also can't speak native gRPC at all without a translation layer, which rules it out directly for any public API with browser-based consumers.

What specifically does GraphQL solve that REST's sparse fieldsets (?fields=, unit 04) don't?

Sparse fieldsets solve over-fetching on a single flat resource — trimming fields off one object. GraphQL additionally solves under-fetching across relationships in one round trip: a single query can pull an order, its customer, and its line items' product details together, which sparse fieldsets on a REST endpoint can't express without either embedding everything by default (defeating the point) or the client making several separate requests. The N+1-round-trip problem, not just payload size, is the piece GraphQL actually targets that a REST querying convention alone doesn't.

Why can't a CDN cache a typical GraphQL query the way it caches a REST GET?

Standard GraphQL sends the query as a POST body, and CDN caching keys on the URL — a POST to one fixed endpoint with an arbitrary body isn't cacheable by that mechanism at all, regardless of whether the same query is repeated by thousands of clients. Workarounds exist — persisted queries that map a known query to a short id sent as a GET parameter, letting a CDN cache by that id — but they're additional infrastructure, not something you get by default the way REST's GET caching is essentially free.

What is GraphQL Federation, and why does a large org need it instead of one big resolver layer?

Federation splits one logical GraphQL schema across multiple backend services, each owning and resolving its own subgraph, stitched together at query time by a gateway — Apollo Federation v2 is the dominant specification for this. A large org needs it because a single monolithic GraphQL server resolving every type across every domain becomes both an organizational bottleneck (every team's schema changes go through one codebase) and a technical one (one service now depends on every other domain's data access patterns). Federation lets each team own its slice of the schema independently while still presenting one unified graph to clients.

Is it true that .NET's GraphQL ecosystem can't do federation properly?

That was a fair criticism years ago but is stale now — Hot Chocolate, the leading .NET GraphQL server, together with its Fusion gateway, reached 100% compliance with the Apollo Federation v2 specification as of the 16.5 release in 2026. It's worth citing precisely because it's recent enough that someone relying on older information might still believe .NET lags here; as of today it doesn't.

How would you explain the choice between gRPC-Web and Connect to a team building a browser client against an internal gRPC service?

Native gRPC relies on HTTP/2 trailers for its status mechanism, which browsers' fetch/XHR APIs can't produce or read directly, so browsers can't speak it at all without translation. gRPC-Web solves that with a dedicated proxy that translates between what browsers can send and native gRPC — functional, but it's another piece of infrastructure to deploy and operate. Connect (from the Buf team, now under the CNCF) is wire-compatible with gRPC but can also speak plain HTTP/1.1 with JSON directly to a browser with no separate proxy, which is why I'd recommend it by default for a new browser-facing service today over the older gRPC-Web-plus-proxy setup.

Can you mix these three within one system, or does picking one mean picking it everywhere?

Mixing is common and often the right call, not a compromise — a typical large system might use gRPC for internal service-to-service calls where both ends are your own code, expose a REST API at the edge for public/partner integration and caching, and layer a GraphQL gateway on top of several REST or gRPC backends specifically to serve a mobile app's need for tailored, minimal payloads. The mistake would be picking one technology as an organizational mandate and forcing every use case through it regardless of fit, rather than matching each boundary to what it actually needs.

A team wants to replace their REST API with GraphQL purely to "future-proof" it. What questions do you ask before agreeing?

What specific pain are they solving — is over/under-fetching actually a measured problem today, or a hypothetical one? Who are the consumers, and how much do they currently rely on HTTP caching that a GraphQL migration would need to replace with something else? Does the team have (or is willing to build) the query-cost-analysis and rate-limiting infrastructure GraphQL needs that a REST API might not have needed as urgently? "Future-proofing" without a concrete current pain point is often a sign the migration cost — rebuilding caching, tooling, and team GraphQL fluency — hasn't been weighed against a real, quantified benefit yet.

How do you debug a gRPC service in production without the easy curl/browser-devtools workflow REST gives you for free?

grpcurl is the direct equivalent of curl for gRPC, capable of introspecting a service (if server reflection is enabled) and issuing calls from the terminal. Beyond that, I'd lean on structured logging and distributed tracing (OpenTelemetry spans around each RPC) more heavily than I would for REST, precisely because the binary wire format removes the option of just eyeballing a captured network request — observability has to do more of the work that human-readability used to do for free.

Does choosing GraphQL mean giving up on a formal contract the way REST APIs without OpenAPI sometimes do?

No — the opposite, actually: GraphQL's SDL schema is mandatory and strongly typed by construction, so a GraphQL API can never ship without a contract the way an under-documented REST endpoint can. What GraphQL doesn't give you for free is REST's optional-but-common OpenAPI tooling ecosystem (generated SDKs in every language, Spectral-style linting, contract testing) — the GraphQL equivalent tooling exists (schema linting, codegen from the SDL) but is a separate ecosystem you have to deliberately adopt, not bundled with the spec the way REST increasingly bundles OpenAPI by convention.

11 The big Q&A

Everything that isn't a core building block, but comes up constantly: security boundaries, performance, tooling, legacy reality, and judgment calls.

Security and trust boundaries

Authentication is covered elsewhere — what's specifically an API design concern about auth, versus an implementation concern?

Design decides where the trust boundary sits and what it costs a client to cross it: which endpoints require auth at all, whether auth is per-request (a bearer token on every call, stateless, horizontally scalable) or session-based, and how scopes/permissions map onto resources — does orders:read mean all orders or only the caller's own. Implementation (covered in a separate auth-focused topic) is how you verify a JWT signature or manage a session store. Getting the design half wrong — an overly coarse scope model, or auth checks scattered per-endpoint instead of centralized — creates security gaps no amount of correct token-verification code fixes.

Should API keys or resource ids be guessable/sequential? What's the actual risk?

No — sequential ids on a resource anyone outside your org can reach invite both enumeration (iterate ids to discover how many orders exist, or scrape every one you can access) and a specific authorization bug class called insecure direct object reference, where an endpoint checks that a valid token was presented but forgets to check that this token's owner is allowed to see this specific id — trivially exploitable when ids are sequential and guessable. Opaque, unguessable ids (unit 01) don't fix a missing authorization check, but they remove the easy reconnaissance step that usually precedes exploiting one.

How does mass assignment become an API design vulnerability, not just an implementation bug?

It happens when a PATCH/PUT endpoint naively binds an entire incoming JSON body onto a domain model, including fields the client was never supposed to set directly — a client sending {"role": "admin"} on their own profile update, if the endpoint blindly maps every field, silently self-escalates privilege. It's a design concern because the fix is architectural: explicit allow-lists of which fields a given endpoint accepts (a dedicated request DTO per operation, not the full domain entity), decided when the endpoint's contract is designed, not patched in after the fact.

What API-shape choices make an API easier or harder to audit for security after the fact?

Consistent, predictable authorization semantics per resource type make audits tractable — if every collection endpoint enforces ownership the same way, an auditor can verify the pattern once and spot-check exceptions, rather than re-deriving the logic per endpoint. The opposite — ad hoc authorization checks written slightly differently in every handler, actions modeled as bespoke RPC-style endpoints with their own one-off permission logic — multiplies the surface area an audit has to cover linearly with endpoint count instead of with resource-type count.

Performance and debugging

An API is "fast" by every server-side metric but customers report it feels slow. What API-design factors, not infrastructure, could explain that?

Chatty designs that force many sequential round trips for one logical operation — fetch an order, then separately fetch its customer, then separately fetch each line's product — where each call is individually fast but the total latency is the sum, dominated by network round-trip time rather than server processing time. This is exactly the under-fetching problem unit 10 covers: the fix is either designing REST endpoints to return commonly-needed related data together (at the cost of some over-fetching for callers who didn't want it), offering an ?include= expansion parameter, or reaching for GraphQL where client-composed queries collapse the round trips into one.

How do you design an API so it's debuggable in production, before anything goes wrong?

A correlation/trace id in every response (surfaced in the Problem Details instance field on errors, and ideally on success responses too) that a client can hand to support and that maps directly to your own logs and traces. Consistent, predictable status codes and Problem Details types so a monitoring dashboard can classify failures by kind automatically instead of by parsing free-text messages. Structured, versioned request/response logging (with sensitive fields redacted) that lets you replay what a specific failing call actually looked like, rather than reconstructing it from incomplete metrics.

What's the N+1 query problem, and how is it different from — but related to — the API-level under-fetching problem?

N+1 is a data-access-layer symptom: fetching a list of N orders, then issuing one additional query per order to fetch its customer, for N+1 total queries instead of one join or one batched fetch. It's related to API-level under-fetching because a naively-designed API surface (an endpoint returning bare order ids with no easy batch-fetch for their customers) practically forces callers into the N+1 pattern at the HTTP level too, mirroring the same anti-pattern one layer up. Fixing it at either layer — a proper join/dataloader server-side, or a well-designed batch/expand endpoint at the API layer — addresses the same root cause: fetching related data one-at-a-time instead of in bulk.

How would you diagnose whether a slow endpoint's problem is pagination, N+1 queries, or something else entirely?

Start with a trace of one real slow request: if it shows one query taking most of the time, that's a database/query problem, not an API design one — check for a missing index or a genuinely expensive aggregation. If it shows many small, similar queries fired in sequence, that's the N+1 pattern regardless of what the API contract looks like. If it shows one query that's fast but the total request time is dominated by OFFSET cost at a high page number (unit 04), that's specifically the offset-pagination performance trap, and the fix is migrating that endpoint to cursor pagination rather than optimizing the query further.

Tooling and ecosystem

What's actually different about Postman-style manual API testing versus contract testing in CI?

Manual exploration (Postman, Insomnia, or an OpenAPI-driven "try it out" UI) is for a human building intuition about an API or debugging a specific case — valuable, but it only tests what a human remembered to try, and it doesn't run automatically. Contract testing in CI runs the same, exhaustive set of assertions against the spec on every change, catching drift the moment it's introduced rather than whenever a human happens to notice. The two aren't competing — manual tools are for exploration and debugging, automated contract tests are for regression prevention — and a mature API program has both.

What role does an API gateway play that the API itself shouldn't have to handle?

Cross-cutting concerns that apply uniformly across many endpoints and often many backend services: authentication token validation, rate limiting, request/response logging, and sometimes protocol translation (a gRPC backend exposed as REST at the edge, or the Connect protocol's own HTTP/JSON compatibility). Centralizing these at the gateway keeps individual services focused on their actual domain logic instead of each reimplementing rate limiting or auth slightly differently — the same "don't repeat this per-endpoint" argument that motivates centralized authorization checks over ad hoc per-handler ones.

How do you keep client SDKs (hand-written or generated) from drifting out of sync with a frequently-changing API?

Generate them directly from the OpenAPI or .proto contract as part of the same release pipeline that ships the API itself, rather than maintaining them as a separately-scheduled, manually-updated artifact — that structurally ties SDK freshness to API deploys instead of to someone remembering to update a second repository. For hand-maintained SDKs where full generation isn't practical, a contract test that fails CI when the SDK's assumptions about the API's shape no longer match the live spec catches drift early instead of at a customer's integration.

Legacy reality and migration

You inherit an API where every endpoint is POST, verbs are in the URL (/api/getOrder, /api/updateOrder), and there's no OpenAPI spec. What's your actual first move?

Not a rewrite — I'd generate an OpenAPI spec from the existing behavior first (even a rough one, hand-authored from observing real traffic if there's no code-first tooling available for the stack), purely to get a documented baseline of what currently exists before changing anything. Rewriting URIs and methods on a live API with unknown consumers, before you even know who those consumers are or what they depend on, risks breaking things you don't know exist. Once there's a documented baseline, a new version with proper resource-oriented URIs can be introduced alongside the old one, with the deprecation lifecycle (unit 09) managing the transition rather than a big-bang cutover.

A legacy API returns 200 for everything, with success/failure indicated by a {"success": bool} field in the body. Fixing it properly would break every existing client. What do you actually do?

I wouldn't flip the existing endpoints' status codes outright — that's a breaking change with a huge, likely-unknown blast radius given how deeply "check the body, not the status" client code would be baked in. I'd fix it going forward: new endpoints and a new API version use correct status codes and Problem Details from day one, and I'd treat migrating the legacy ones as a deliberate, versioned, deprecation-lifecycle project (unit 09) rather than a quick patch — the underlying design flaw is real, but the fix has to respect that every existing consumer built their error handling around the wrong contract on purpose, because it was the only contract they had.

How do you introduce OpenAPI, Problem Details, or any of these modern patterns to a skeptical team that's shipped fine without them for years?

Lead with a concrete, recent pain point their own team already felt — a debugging session that took an hour longer than it should have because an error had no structured type to grep for, a frontend team blocked for a sprint waiting on a backend that a mock server would have unblocked immediately. Abstract "best practice" arguments rarely move a team that's shipped successfully without them; a specific incident they remember does. I'd also pilot on one new endpoint or service rather than proposing a wholesale retrofit — a visible, low-risk win is what earns the credibility to propose adopting it more broadly.

What's the honest trade-off of adopting HTTP QUERY or OpenAPI 3.2 today, given how new both are?

You're an early adopter of infrastructure that's still catching up — client libraries, API gateways, and even .NET's own first-party OpenAPI generator (still on 3.1, unit 07) don't fully support the newest pieces yet. The upside is designing correctly from day one instead of building on a workaround (POST-for-search) you'll want to migrate away from later. I'd adopt selectively: use QUERY where a team controls both client and server end-to-end and can verify support directly, rather than mandating it broadly across a public API where you can't control or verify every consumer's HTTP client capabilities.

Judgment and scenario questions

You're reviewing a PR that adds a new field by overloading an existing one's meaning based on another field's value ("if type is 'refund', amount means something different"). What do you flag?

That's a semantic-versioning trap waiting to happen (unit 03) disguised as a clever reuse of an existing field — any client that learned amount's original meaning now silently misinterprets it for one type value, with no schema-level signal that anything changed. I'd push for a distinct, clearly-named field instead (refundAmount, or a nested object specific to the refund case), even at the cost of a slightly larger schema — the alternative saves a few bytes and creates exactly the kind of undetectable-by-tooling bug this guide keeps returning to.

A product manager wants an endpoint to "just return everything the frontend might ever need" to avoid future round trips. How do you respond?

I'd separate the reasonable instinct (avoid chatty round trips) from the actual proposal (an unbounded, ever-growing response). Unbounded "just in case" fields balloon payload size for every caller regardless of need, couple the backend to speculative future frontend requirements, and tend to accrete unused, stale fields nobody remembers to remove. The better answer is usually a deliberate ?include= expansion mechanism (unit 01/04) or, if the real problem is genuinely varied per-client data needs, revisiting whether GraphQL (unit 10) is a better fit for that specific surface — giving the client the tool to ask for exactly what it needs, rather than the server guessing at "everything."

How would you explain to a non-technical stakeholder why "just add a version number to fix everything" isn't free?

Every additional API version the team supports concurrently is code, tests, and on-call knowledge that has to keep working correctly, indefinitely, for as long as any consumer depends on it — it's not a one-time cost, it's an ongoing maintenance burden that compounds with every version left running. I'd frame the real trade-off in business terms: shipping v2 quickly is easy, but the actual cost is how long v1 has to stay alive afterward, and that's directly a function of how proactively we manage deprecation (unit 09) rather than how many versions we're willing to create.

You're asked to design the very first version of a brand-new public API. What decisions do you deliberately make easy to change later, and what do you get right the first time because changing it later is expensive?

Cheap to change later: specific field names and optional fields, additive endpoints, response field ordering, most things unit 03 classifies as non-breaking. Expensive to change later: the resource model and URI structure (renaming/restructuring resources is effectively a new API to every existing consumer), the versioning strategy itself (switching from URI-path to header-based versioning after consumers have built around URLs is its own painful migration), and the identifier format (moving from sequential ids to opaque ones after the fact means every existing stored/bookmarked id becomes invalid). I'd spend deliberate design time on those three specifically, and move fast on everything else.

12 Night-before cheat sheet

Docs: OpenAPI 3.2.0 · RFC 9457 — Problem Details

Ten sentences you can say out loud, in this order, and be right. Each one is a hook you can expand into two minutes if they follow up.

  1. "Richardson's maturity model has four levels — plain RPC-over-HTTP, resources, HTTP verbs used correctly, and HATEOAS — and almost nothing calling itself REST actually reaches level 3; level 2 with a solid resource model is a perfectly good, honest target." Naming the level you're actually aiming for, and why, reads as more senior than claiming "full REST."
  2. "Safe means no side effects, idempotent means repeating it changes nothing further: GET and HEAD are both; PUT and DELETE are idempotent but not safe; POST is neither by default — and the new HTTP QUERY method, finalized as RFC 10008 in June 2026, gives GET-shaped semantics to a request that needs a body." That's the table every interviewer probes, plus the one fact that shows you're current.
  3. "Pick a versioning strategy and mean it — URI-path is the most common and most visible, header-based keeps URLs stable, media-type versioning is the most correct and least loved — but the real skill is classifying a change as breaking or not before shipping it, not the mechanism you version with." The tax-inclusive-total trap — a field whose meaning changes silently with no shape change — is the example that shows you've been burned by this for real.
  4. "Cursor pagination beats offset at any real scale: offset re-counts and re-skips rows on every page and duplicates or drops items when the underlying set changes between requests; a cursor is an opaque pointer to 'the row after this one' and doesn't have either problem." Offset is fine for a small, static admin table — it's not fine for anything a client can page through while writes are happening.
  5. "An idempotency key is a client-generated id sent on a POST that lets a retried request return the original result instead of creating a second order — it's a different mechanism from ETag/If-Match, which protects against a lost update, not a duplicate create." Both matter; conflating them is the tell that someone's memorized the term without having built it.
  6. "RFC 9457 Problem Details gives every error the same five members — type, title, status, detail, instance — plus an errors array by convention for field-level validation failures; the type URI is a stable identifier a client can switch on, and it should never be about:blank on purpose." A consistent error contract is the single highest-leverage thing an API can ship, because every client-side error handler gets to be generic instead of bespoke per endpoint.
  7. "OpenAPI hit 3.2.0 on 19 September 2025 — QUERY support, additionalOperations, typed tags, itemSchema for streaming — but both .NET generators, the first-party Microsoft.AspNetCore.OpenApi and Swashbuckle, are still capped at 3.1, and neither bundles a UI by default anymore; you wire in Scalar or Swagger UI yourself." That gap — spec ahead of tooling — is exactly the kind of precise, dated fact that separates "read the docs once" from "actually current."
  8. "Fixed-window rate limiting lets a client burst up to double the nominal rate right at the window boundary; token bucket doesn't, because it tracks a continuously-refilling balance instead of a hard reset — and always send Retry-After even if your fancier headers follow the still-unratified IETF RateLimit draft, at v11 as of May 2026." Naming that the draft still isn't an RFC after years is a small, precise flex.
  9. "Deprecation (RFC 9745, March 2025) says 'this is already old'; Sunset (RFC 8594) says 'this stops working on this date' — send both, retire with 410 not 404 so a confused caller knows it was intentional, and a changelog entry alone is not notice because nobody's client reads changelogs automatically." The lifecycle — announce, warn with a date, escalate, retire — is the answer whenever someone asks how you'd manage a breaking change responsibly.
  10. "REST, gRPC, and GraphQL optimize for different callers, not different quality bars: REST for broad, cache-friendly, human-inspectable reach; gRPC for fast, strictly-typed calls between services you control; GraphQL for a client that needs to shape its own response across several related resources in one round trip — and picking one doesn't rule out the other two at different boundaries of the same system." Ending on "it depends on the caller" is the framing that makes the rest of this guide sound like judgment, not a features list.
