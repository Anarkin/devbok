System design (.NET full-stack)

interview · .NET 10 (LTS) · released 2025-11-11

A system design loop does not test whether you can name Kafka; it tests whether you can turn a vague sentence into requirements, put numbers on them, choose a shape, and then defend the two or three decisions that actually decide whether the system survives. For a full-stack .NET candidate the loop is wider than the classic "design Twitter" script: expect the same interviewer to push on an index choice, an idempotency key, a cache invalidation story, a hydration cost on the front end, and a rollback plan — often inside one hour. Work the map below in frequency order: sub-areas 01–08 appear in nearly every loop and carry about two thirds of this bank, 09–13 are where a .NET full-stack loop diverges from a generic one, and 14–17 are the ceiling questions plus the modernisation work you will actually be hired to run. Every answer is written to be spoken in 30–60 seconds and to survive one follow-up, and each block ends with the plausible wrong answer that gets candidates rejected — read those even when you skip the answers. Assumptions, stated once: "system design" here means the interview discipline, not a specific product, and the stack anchor is .NET 10 (current LTS, released 2025-11-11) with Aspire 13.4, EF Core 10, React 19.2 / Next.js 16, PostgreSQL 18 and SQL Server 2025; where a claim is version-sensitive the version is named in the text.

01Requirements, scoping and estimation

This is the sub-area that decides the interview before any box is drawn. Interviewers are watching whether you convert a deliberately vague prompt into a scoped problem with numbers attached, because that is the skill that separates someone who builds the right system from someone who builds an impressive one. At mid level you are expected to ask clarifying questions and state assumptions; at senior to derive load and storage numbers that then constrain your design; at principal to say out loud what you are not building and why, and to name which decisions are reversible.

screenerHow do you open a system design interview — what happens in the first five minutes?

Answer

I spend the first five minutes turning the prompt into a contract, not drawing anything. I restate the problem in one sentence and get agreement, then list the functional requirements as concrete user actions, then pin the non-functional ones as numbers: expected users, read/write ratio, latency target, availability target, data retention. I ask two or three scoping questions that genuinely change the design — "is this global or single-region?", "how stale can this read be?", "do writes need to be durable before we acknowledge?" — and explicitly declare what is out of scope. Then I write the numbers in a corner of the board and refer back to them, because every later decision has to be justified against them. The whole point is that the interviewer and I are designing the same system.

Example

Prompt: "Design a URL shortener."
Contract in 5 minutes:
  FR   create short link, resolve short link, per-link click stats
  NFR  100M links total, 10k redirects/s peak, 100:1 read:write
       redirect p99 < 50ms, availability 99.99%, stats may lag 5 min
  Out  custom vanity domains, billing, abuse/ML detection
  Open single region or global? (assume: global reads, single-region writes)

Follow-ups

  • What if the interviewer refuses to answer a clarifying question? — State an assumption, write it down, and design against it; the assumption itself is the answer they were testing for.
  • How many clarifying questions is too many? — Past about four minutes you are stalling; ask only questions whose answer changes a box on the diagram.
  • What do you draw first? — The API surface, not the boxes: the endpoints force you to name the entities and the read/write paths.

Common wrong answer

Starting with the architecture — "so we'll have a load balancer, some app servers, a database and a cache" — before any requirement exists. It is the single most common rejection reason at senior level, because that diagram is identical for every prompt and demonstrates nothing.

screenerFunctional versus non-functional requirements — which one actually drives the design?

Answer

Functional requirements decide what components exist; non-functional requirements decide what shape they take, and they are what makes the design hard. "Users can post a message" tells me I need a write path and a store; "10k posts/second, fan-out visible within two seconds, never lose a post" tells me whether that store is a single Postgres instance or a partitioned log with async fan-out. In practice I treat five non-functionals as the ones that bend architecture: load and its shape (peak versus average), latency target at a percentile, consistency tolerance, durability, and availability. Everything else — compliance, cost, operability — matters but usually constrains rather than reshapes. If a candidate never states a percentile latency or a consistency tolerance, they have not really started designing.

Follow-ups

  • Which non-functional is most often ignored by candidates? — Peak-to-average ratio; a 10× spike at 09:00 changes capacity and autoscaling far more than the daily average does.
  • Is cost a functional or non-functional requirement? — Non-functional, and at principal level it is a first-class one: an architecture the business cannot afford is not a valid design.

Common wrong answer

"Non-functional requirements are scalability, availability, maintainability" — the textbook list recited without a single number. The interviewer is not checking that you know the word; they are checking whether you can say 99.95% and p99 under 200 ms and then live with it.

midDo a back-of-the-envelope estimate for a feed with 50M daily active users. Where do you start?

Answer

I start from one number the interviewer gave me and derive everything else in visible steps, rounding aggressively. DAU times actions per user per day gives daily operations; divide by 86,400 for average per second; multiply by a peak factor of 2–5 for the daily peak. Then storage: bytes per record times records per day times retention, plus a replication factor and an index overhead of roughly 20–50%. Then bandwidth: bytes per response times reads per second. I keep the arithmetic in powers of ten and say the assumptions out loud, because the interviewer is grading the derivation, not the digits. The reason it matters is that the numbers immediately rule things out: 300 GB/day is not "just put it in Postgres and keep it forever".

Example

50M DAU, each reads the feed 10x/day, posts 0.2x/day
reads  500M/day  ≈ 5.8k/s avg  → peak x3 ≈ 17k/s
writes  10M/day  ≈ 115/s avg   → peak x3 ≈ 350/s
read:write ≈ 50:1  → read-optimised design, cache the feed

post ≈ 300 B row + 1 KB media pointer/metadata
writes/day 10M x 1.3 KB ≈ 13 GB/day ≈ 4.7 TB/year
x3 replicas + 30% index ≈ 18 TB/year → partition by user, tier cold data

feed response 20 posts x 1.3 KB ≈ 26 KB
17k/s x 26 KB ≈ 440 MB/s egress ≈ 3.5 Gbps → CDN/edge cache is not optional

Follow-ups

  • What peak factor do you use? — 2–3× for a global consumer product, 5–10× for a business app with a working-hours spike, and I say which and why.
  • How precise should the numbers be? — One significant figure; being wrong by 2× is fine, being wrong by 100× means the architecture is wrong.
  • What do you do when the estimate says "this fits on one machine"? — Say so, loudly, and design the simple thing; that answer scores higher than an unnecessary distributed system.

Common wrong answer

Computing a wall of numbers and then never using them. If the estimate does not change a decision later — "440 MB/s means the CDN carries the images, the origin only serves JSON" — it was theatre, and interviewers notice.

midThe requirement says "it should be fast". How do you turn that into something you can design against?

Answer

I convert it into a percentile latency budget per user-visible operation, measured where the user is, and then split that budget across hops. "Fast" becomes something like: search results p95 under 300 ms and p99 under 800 ms, measured server-side at the edge, with a client budget of 2.5 s to Largest Contentful Paint. Then I decompose: 30 ms TLS and edge, 20 ms gateway, 150 ms service including database, 50 ms serialisation and network back. That decomposition is what lets me say "the database has 150 ms, so a query plan that does a sequential scan is out of budget" instead of arguing about feelings. I always ask about the tail rather than the average, because averages hide the queueing behaviour that actually generates complaints.

Example

Budget: GET /api/search  p99 = 400 ms server-side
  edge/TLS/routing        40 ms
  auth + rate limit       15 ms
  query planning + cache  25 ms   (hit ratio target 80%)
  search backend          250 ms  (p99, enforced by a timeout at 300 ms)
  response shaping        30 ms
  headroom                40 ms
Timeout at each hop < remaining budget; exceeding the budget = fail fast, not queue.

Follow-ups

  • Why p99 and not the average? — At 100 dependent calls per page, a p99 of 1 s means most pages hit it at least once; tail latency is the user-visible latency.
  • Server-side or client-side measurement? — Both, and know the gap: server p99 of 200 ms with a client p99 of 3 s means the problem is the front end or the network, not your service.
  • What is a latency budget good for beyond design? — It becomes the timeout configuration and the alert threshold, so the design and the runbook agree.

Common wrong answer

"We'll target sub-second response times." No percentile, no measurement point, no per-hop split — so nothing in the design can be falsified, and the first production incident finds a hop with no timeout at all.

seniorSLI, SLO, SLA and error budgets — how does an error budget change a design decision?

Answer

An SLI is a measured quantity (fraction of requests under 300 ms), an SLO is the internal target for it (99.9% over 28 days), and an SLA is the external contract with money attached, always set looser than the SLO. The error budget is the inverse of the SLO — 0.1% of requests, or about 43 minutes a month — and it is the part that changes designs, because it converts reliability from an argument into an allowance. Concretely: if a dependency's own availability is 99.9% and I call it synchronously on the critical path, I have spent my entire budget on one hop, so the design must either make the call optional with a fallback, or move it off the request path. It also drives release policy — budget left means ship, budget burned means freeze — which is a lead-level answer interviewers listen for.

Example

Target: 99.9% availability for POST /orders  (budget 43 min/month)
Synchronous dependencies and their own SLOs:
  auth        99.99%  → 4 min    (required, cached tokens reduce exposure)
  inventory   99.9%   → 43 min   (required → budget already gone)
  pricing     99.9%   → 43 min   (make optional: fall back to list price)
  loyalty     99.5%   → 3.6 h    (must be async: publish an event, apply later)
Serial availability ≈ product of the parts → remove hops or make them optional.

Follow-ups

  • Why is an SLA looser than an SLO? — So the team gets paged and fixes it before a customer is entitled to a refund; equal numbers mean every SLO miss is a contractual breach.
  • What is a good SLI for an async pipeline? — Freshness (age of the newest processed record) and completeness, not uptime; "the consumer is running" is not a user-visible property.
  • How do you pick the SLO number? — From measured current behaviour and what users actually notice, never from a round number chosen in a meeting; 99.99% on a service nobody watches is expensive vanity.

Common wrong answer

"We'll aim for five nines." Five nines is 26 seconds of downtime a month — it forbids manual failover, most deployment strategies and any single-region dependency. Claiming it without naming that cost tells the interviewer you have never owned a target.

seniorHow do you decide what to leave out of the design in a 45-minute interview?

Answer

I rank candidate topics by how much they change the shape of the system and how likely the interviewer is to probe them, then spend the time on the top three and explicitly park the rest. The core write path, the core read path and the one hard constraint (usually consistency or fan-out) get real depth; auth, deployment, and CI get a single sentence each with an offer to expand. I say the parking out loud — "I'd normally cover multi-region failover here; I'm deferring it because the read path is where the interesting constraint is, happy to come back" — because unspoken omissions read as gaps while spoken ones read as prioritisation. Managing the clock is itself part of what is being graded at lead level; running out of time before touching the data model is a failure regardless of how good the diagram looked.

Example

45 min budget
 5  scope + numbers            (non-negotiable)
 5  API surface + entities
10  data model + partitioning  (usually where the design is won or lost)
10  read path: cache, fan-out, hot keys
 8  write path: consistency, idempotency, failure
 5  ops: what breaks, how you see it, how you roll back
 2  what I left out and why
Parked by default: auth details, CI/CD, GDPR, admin tooling, analytics.

Follow-ups

  • What if the interviewer keeps dragging you into a side topic? — Follow them; they are steering toward what they want to grade, and resisting reads as rigidity.
  • Do you draw a diagram at all? — Yes, but a small one that grows; a big upfront diagram costs five minutes and communicates less than an evolving one.

Common wrong answer

Trying to cover everything evenly, so nothing gets past the first layer. The signal an interviewer needs — can this person go three levels deep on a hard decision — never appears, and the feedback is "broad but shallow".

seniorEstimate storage and cost for retaining five years of events at 50k events/second.

Answer

Fifty thousand events a second is 4.3 billion a day; at a modest 500 bytes serialised that is about 2.2 TB a day, or 780 TB a year raw, close to 4 PB over five years before replication. That number immediately kills "keep it all in the operational database" and forces a tiering answer: hot data in the operational store for days, warm in object storage in a columnar format such as Parquet with partition pruning, cold in archive tiers with retrieval latency measured in hours. Compression is the biggest lever — columnar plus zstd routinely gets 5–10× on event data, taking 4 PB to roughly 400–800 TB — followed by dropping fields nobody queries and aggregating beyond 90 days. At current cloud object-storage list prices of roughly $0.02/GB/month for standard and about a tenth of that for archive, the difference between "keep everything hot" and a tiered plan is the difference between six figures a year and a rounding error, which is exactly the trade-off a principal candidate is expected to put numbers on.

Example

50,000/s x 86,400 = 4.32e9 events/day
x 500 B          ≈ 2.16 TB/day  ≈ 790 TB/year  ≈ 3.9 PB / 5 years (raw)
Parquet + zstd (~8x)             ≈ 100 TB/year ≈ 490 TB / 5 years

Tier plan
  0-7 d    hot, queryable, operational store + index    ~15 TB
  7-90 d   object storage, Parquet, partitioned by day  ~23 TB
  90 d-5 y aggregated to 1-minute rollups (~1% of rows) ~5 TB
  raw beyond 90 d → archive tier, restore on request
Retention is a product decision; ask for it, do not assume "forever".

Follow-ups

  • What breaks first, storage or ingest? — Ingest: 50k/s of small writes is an index and fsync problem long before capacity is; batch and append rather than row-by-row insert.
  • Where does GDPR erasure fit in a tiered plan? — It is a design constraint on the cold tier: either keyed deletion (Iceberg/Delta-style row deletes) or crypto-shredding by per-subject key, decided upfront.
  • Why Parquet rather than compressed JSON? — Columnar layout skips columns and row groups entirely; typical analytical queries read 5–10% of the bytes.

Common wrong answer

"We'll put it all in Elasticsearch." At petabyte scale the index is often larger than the data and the cluster cost dominates the entire product budget. Search indexes are for the slice people actually search, not for retention.

principalHow do you scope a system whose requirements you know will change substantially within six months?

Answer

I separate decisions by reversibility and only spend design effort on the irreversible ones. Data model, partition key, public API contract, and the tenancy model are expensive to change once there is production data — those I decide slowly, with the widest plausible requirement in mind. Framework choice, cache topology, queue technology, and internal service boundaries are comparatively cheap to change, so I pick the boring option and move on. Concretely that means writing the storage layer behind an interface I control, keeping event schemas additive-only from day one, and putting a version in the public contract before I need it. The principal-level part is saying which unknowns I am deliberately deferring and what evidence would trigger revisiting them — "if per-tenant volume exceeds X we split the shared table; here is the migration we have already rehearsed".

  • Is that not just "build it flexible"? — No: flexibility everywhere is its own cost. I am buying optionality only where change is expensive, and accepting rigidity elsewhere.
  • How do you record these decisions? — Lightweight ADRs with the context and the trigger for revisiting; six months later the trigger is what the team actually needs.
  • What is the most common irreversible mistake? — Choosing a partition key that matches today's access pattern (say, timestamp) and creating a permanent hotspot.

Common wrong answer

"We'll build it generic so it can handle anything later." Generic plugin architectures built before the second use case exist are the classic principal-level trap: they cost delivery speed now for flexibility along axes that turn out to be wrong.

02API design and contracts

Every design ends up with an API surface, and interviewers use it as the fastest probe of whether you think in contracts or in code. What is tested is resource modelling, idempotency, pagination, versioning and error semantics — plus, for a lead, whether you understand that a published contract is a liability you carry for years. At mid level you should design a clean REST surface without prompting; at senior you should choose between REST, gRPC and GraphQL for stated reasons and defend a compatibility policy; at principal you should be able to describe how a contract changes across dozens of consumers you do not control.

screenerDesign the REST API for the system you just described. What are the rules you follow?

Answer

I model nouns, not verbs: resources with stable identifiers, standard methods for the CRUD-shaped part, and sub-resources for relationships. Collection endpoints are plural and pageable, single resources are addressable by an opaque id, and anything that is genuinely an operation rather than a state change on a resource becomes a sub-resource that itself has state — POST /orders/{id}/cancellations rather than POST /cancelOrder, because the operation then has an id, a status and a retry story. Status codes carry meaning: 201 with a Location header for creation, 202 when the work continues asynchronously, 409 for a state conflict, 422 for a semantically invalid but well-formed body. And I decide the representation shape once — camelCase JSON, ISO-8601 UTC timestamps, monetary amounts as minor units with a currency code — because inconsistency there costs every consumer forever.

Example

// ASP.NET Core 10 minimal APIs; validation is built in since .NET 10
var orders = app.MapGroup("/api/v1/orders").WithTags("Orders");

orders.MapGet("/", (int? limit, string? cursor, IOrderQueries q) =>
        q.PageAsync(limit ?? 50, cursor));                       // 200 + nextCursor
orders.MapGet("/{id}", async (Guid id, IOrderQueries q) =>
        await q.FindAsync(id) is { } o ? Results.Ok(o) : Results.NotFound());
orders.MapPost("/", async (CreateOrder cmd, IOrderService s) =>
{
    var id = await s.PlaceAsync(cmd);
    return Results.Created($"/api/v1/orders/{id}", new { id });  // 201 + Location
});
orders.MapPost("/{id}/cancellations", async (Guid id, IOrderService s) =>
        Results.AcceptedAtRoute("cancellation", new { id }));    // 202, has its own state

Follow-ups

  • What about actions that are not resources at all, like "search"? — POST /searches when the query is large or must be stored; a GET with query parameters when it is cacheable and short.
  • Do you use HATEOAS? — Rarely; it costs payload and tooling for benefits almost no real client uses. I say so rather than pretending.
  • Where do you put the version? — In the path for a public API (visible, cacheable, greppable), in a header only when the consumers are all internal and disciplined.

Common wrong answer

An RPC-over-HTTP surface — POST /api/getUserOrders, POST /api/updateOrderStatus — described as REST. It is not that RPC is wrong; it is that calling it REST tells the interviewer you inherited the style without understanding what caching, idempotency and status codes buy you.

screenerWhich HTTP methods are idempotent, and why does the interviewer care?

Answer

GET, HEAD, PUT and DELETE are defined as idempotent; POST and PATCH are not. It matters because every layer between the client and your service — the browser, a mobile client on flaky mobile data, an HTTP client with automatic retries, a load balancer, a service mesh — will happily retry an idempotent method on a timeout, and a timeout is indistinguishable from a lost response. So the real question behind it is: what happens when the same request arrives twice? For PUT the answer is free, because setting a resource to the same value twice is the same as once. For POST it has to be engineered, normally with a client-supplied idempotency key stored alongside the result. Note that idempotent does not mean side-effect free — a DELETE that returns 404 the second time is still idempotent in state, which is the distinction interviewers probe.

Example

// POST made safely retryable with a client-supplied key
orders.MapPost("/", async (CreateOrder cmd, [FromHeader(Name = "Idempotency-Key")] string key,
                           IIdempotencyStore store, IOrderService svc) =>
{
    if (await store.TryGetAsync<OrderCreated>(key) is { } prior)
        return Results.Ok(prior);                    // replay the first result, do not re-charge

    var result = await svc.PlaceAsync(cmd);          // same tx as the store write below
    await store.SaveAsync(key, result, TimeSpan.FromHours(24));
    return Results.Created($"/api/v1/orders/{result.Id}", result);
});

Follow-ups

  • Is PATCH idempotent? — Not by definition; JSON Merge Patch usually is in practice, but a patch containing "count": {"$inc": 1} is not.
  • How long do you keep idempotency keys? — Long enough to cover the client's retry window plus a margin: 24 hours is a common, defensible answer for payments.
  • What if the second request has a different body but the same key? — 409: the key identifies one intended operation, and silently accepting a different body is how double-charges happen.

Common wrong answer

"POST creates, PUT updates." That is a mnemonic, not the definition, and it collapses on PUT of a new resource at a known id. The property the interviewer is after is retry-safety, not create-versus-update.

midHow do you paginate a large collection — and when does offset pagination break?

Answer

Offset pagination (?page=500&size=50) is simple and fine for small, stable collections, but it breaks in two predictable ways: the database still has to walk and discard every skipped row, so page 10,000 is a full scan, and rows inserted or deleted between pages cause items to be skipped or duplicated. Keyset — or cursor — pagination fixes both: you order by a stable, unique key, and each page carries an opaque cursor encoding the last key seen, so the next query is a range seek that uses the index and is unaffected by inserts earlier in the order. The cost is that you lose random access to page N and sorting is constrained to the key you paginate on, which is almost always an acceptable trade. In practice I expose limit plus cursor, cap limit at something like 100, and return the next cursor in the body rather than making clients construct it.

Example

-- offset: the database sorts and discards 500,000 rows every time
SELECT * FROM orders WHERE tenant_id = $1 ORDER BY created_at DESC, id DESC
OFFSET 500000 LIMIT 50;

-- keyset: an index seek, constant cost regardless of depth
SELECT * FROM orders
WHERE  tenant_id = $1
  AND  (created_at, id) < ($2, $3)     -- cursor = last row of the previous page
ORDER BY created_at DESC, id DESC
LIMIT 50;
-- index: (tenant_id, created_at DESC, id DESC)

Follow-ups

  • Why include id in the ordering? — created_at is not unique; without a tiebreaker rows with the same timestamp are skipped or repeated at a page boundary.
  • How do you show a total count? — Usually you do not: an exact count is as expensive as the scan you just avoided. Offer an approximate count or "more results" instead.
  • Can clients still jump to page 50? — Not with keyset. If the product genuinely needs it, that is a search/aggregate use case, not a list endpoint.

Common wrong answer

"Offset is fine, we just add an index." An index does not help OFFSET: the engine must still traverse and discard the skipped rows. The symptom in production is a list endpoint whose p99 grows linearly with how deep power users scroll.

midREST, gRPC or GraphQL — how do you choose, and what does each cost?

Answer

I choose by consumer and by traffic shape. REST over JSON is the default for anything public or browser-facing: it is cacheable by HTTP infrastructure, debuggable with curl, and every client already speaks it. gRPC wins for internal service-to-service calls at volume — binary Protobuf, HTTP/2 multiplexing, generated clients, and first-class streaming — at the cost of browser support needing gRPC-Web or Connect and of proxies that cannot see into the payload. GraphQL earns its place when many different clients need different shapes of the same graph and over-fetching is a measured problem, but it moves the cost to the server: query complexity limits, persisted queries, the N+1 problem solved with DataLoader-style batching, and caching that HTTP no longer does for you. The honest senior answer is that most systems end up with REST at the edge and gRPC inside, and reach for GraphQL only when the client diversity justifies the operational tax.

  • What stops a GraphQL query from taking down the database? — Depth and complexity limits, persisted (allow-listed) queries in production, per-field cost weights, and batching at the data layer.
  • Can you use gRPC from a browser in 2026? — Only via gRPC-Web or Connect, both of which need a proxy or a compatible server; native browser gRPC still does not exist.
  • What about server-sent events? — For one-way server push over plain HTTP it is the cheapest option, and ASP.NET Core 10 added TypedResults.ServerSentEvents so it no longer needs hand-rolled framing.

Common wrong answer

"GraphQL, because clients can ask for exactly what they need." True and irrelevant on its own: without persisted queries and complexity limits you have handed every client the ability to write an arbitrarily expensive query against your production database, which is the failure mode teams actually hit.

midHow do you version an API, and what counts as a breaking change?

Answer

My default is: version the API in the URL path at a major level only, and make every change within a major version additive. Breaking is anything that can make a conforming existing client fail — removing or renaming a field, narrowing a type, making an optional request field required, changing the meaning of a value, changing an error code, or tightening validation. Non-breaking is adding an optional request field, adding a response field, adding a new endpoint, or adding a new enum value if clients were told to tolerate unknown values. That last one is the trap: enum extension breaks strict deserialisers, so the tolerance has to be documented on day one. When a genuine break is unavoidable I run both versions in parallel with a published sunset date, measure per-version traffic, and contact the remaining callers by name rather than announcing a deprecation into the void.

  • URL path or header versioning? — Path for public APIs; it is visible in logs, caches and support tickets. Header versioning is elegant and hard to operate.
  • How many versions do you keep alive? — Two, with a written sunset policy; three means every change costs triple and nobody migrates.
  • How do you know when it is safe to remove v1? — Per-version request metrics with the caller identity attached, not a calendar date alone.

Common wrong answer

"We bump the version whenever we change anything" — leading to v7 within a year, seven code paths, and no consumer ever migrating. Versions are for breaks; everything else is additive evolution.

seniorDesign the error contract. What does a caller get when something goes wrong?

Answer

One machine-readable shape for every error, used by every endpoint, with a stable error code that clients can branch on. In .NET that means RFC 9457 ProblemDetails — the update to the older RFC 7807 — with type, title, status, detail, instance, plus extensions for a stable code, a correlation/trace id, and structured field errors for validation. The important distinctions are: is this the caller's fault (4xx, do not retry), my fault (5xx, retry with backoff), or a transient conflict (409/429, retry with guidance)? A 429 or 503 should carry Retry-After, because otherwise every client invents its own retry policy and they synchronise into a thundering herd. Two rules I hold: never leak internal exception detail or stack traces to an untrusted caller, and never encode the reason only in the human-readable message, because clients then parse English and break when you fix a typo.

Example

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/insufficient-inventory",
  "title": "Order cannot be fulfilled",
  "status": 422,
  "detail": "2 of 5 requested units of SKU-8841 are available.",
  "instance": "/api/v1/orders/9f2c...",
  "code": "INSUFFICIENT_INVENTORY",
  "traceId": "00-4bf92f...-00f067aa0ba902b7-01",
  "errors": { "lines[0].quantity": ["requested 5, available 2"] }
}

Follow-ups

  • 400 or 422? — 400 for a malformed request the parser rejects, 422 for a well-formed request that violates a business rule; be consistent, because clients branch on it.
  • Should the trace id be returned to the public? — Yes, a correlation id is worth it: support tickets become one log query instead of a fishing expedition. Return the id, not the internals.
  • How does this work with minimal APIs? — ASP.NET Core 10 routes minimal-API validation failures through IProblemDetailsService, so you customise the shape in one place rather than per endpoint.

Common wrong answer

"We return 200 with { success: false, message: ... }." It defeats every retry policy, circuit breaker, cache and monitoring dashboard between you and the caller, all of which key off status codes. It also hides real outages: your error rate stays at zero while the product is broken.

seniorHow do you rate-limit an API, and where does the limiter live?

Answer

I pick the algorithm from the traffic shape and the enforcement point from the threat. Token bucket is the usual choice because it permits a burst up to the bucket size while bounding the sustained rate; fixed windows are simpler but produce a 2× spike across a window boundary, and sliding-window counters fix that at a small memory cost. The limiter belongs at the edge for coarse protection — per IP, per API key, cheap and stateless — and inside the service for per-tenant and per-endpoint quotas, because only the service knows that a report export costs a hundred times a profile read. Distributed enforcement needs shared state, normally Redis or Valkey with an atomic script, and I accept slight over-admission rather than adding a synchronous round trip to every request. Finally the response has to teach the client: 429 with Retry-After and RateLimit headers, so well-behaved clients back off instead of hammering.

Example

// ASP.NET Core built-in rate limiting: per-tenant token bucket, queue nothing
builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    o.OnRejected = async (ctx, ct) =>
    {
        ctx.HttpContext.Response.Headers.RetryAfter = "1";
        await ctx.HttpContext.Response.WriteAsync("rate limit exceeded", ct);
    };
    o.AddPolicy("per-tenant", http => RateLimitPartition.GetTokenBucketLimiter(
        http.User.FindFirst("tenant_id")?.Value ?? "anonymous",
        _ => new TokenBucketRateLimiterOptions
        {
            TokenLimit = 200,                       // burst
            TokensPerPeriod = 50,                   // sustained: 50/s
            ReplenishmentPeriod = TimeSpan.FromSeconds(1),
            QueueLimit = 0                          // fail fast, do not build a queue
        }));
});

Follow-ups

  • Why QueueLimit = 0? — Queuing at the limiter converts a rate problem into a latency problem and consumes memory; rejecting fast is kinder to the client and to you.
  • What do you limit on for anonymous traffic? — IP plus a coarse fingerprint, knowing both are weak; the real defence for abuse is authentication and a WAF, not a counter.
  • How do you avoid the limiter itself becoming the bottleneck? — Local token buckets sized to global/instance count with periodic reconciliation; exact global limits are rarely worth a synchronous hop.

Common wrong answer

"One global limit of N requests per second." A single limit lets one aggressive tenant consume the entire allowance and starve everyone else — the noisy-neighbour outage that per-tenant partitioning exists to prevent.

seniorTwo teams own two services. How do you keep their contract from breaking in production?

Answer

I make the contract an artefact with an owner and a test, not a document. The schema — OpenAPI for HTTP, .proto for gRPC, an event schema in a registry for messages — lives in version control, is generated from or validated against the implementation in CI, and is published on every merge. Consumers write consumer-driven contract tests (Pact-style) that the provider runs in its own pipeline, so the provider learns it broke someone before deploy rather than from an incident. On top of that I enforce compatibility mechanically: a schema-diff gate that fails the build on a backward-incompatible change unless a major version bump is declared. The organisational half matters as much: expand-then-contract as the standard change ritual, and a rule that a provider never deploys a removal until consumer telemetry shows nobody uses the field.

Example

Expand / migrate / contract, for renaming a field
1 expand    provider writes BOTH orderDate and placedAt; contract adds placedAt (optional)
2 migrate   consumers switch to placedAt; provider logs reads of orderDate with caller id
3 verify    orderDate read count = 0 for 2 weeks across all callers
4 contract  remove orderDate; schema-diff gate now permits it; announce in changelog

CI gates
  openapi-diff old.yaml new.yaml --fail-on-incompatible
  pact-verify  (provider runs every consumer's expectations)

Follow-ups

  • Contract tests or end-to-end tests? — Contract tests: they are fast, run per-service, and pinpoint the breaking side; full E2E environments become the bottleneck they were meant to remove.
  • What about event schemas? — Same rules, plus a registry with a compatibility mode (backward for consumers that lag, full when both sides move independently).
  • Who owns the contract when the teams disagree? — The provider owns the schema, the consumers own the expectations; the diff gate is the referee so it does not become a meeting.

Common wrong answer

"We keep a shared DTO library so both sides always match." A shared type package couples deployment: the consumer must upgrade in lockstep, which is exactly the independent-deployability property that made you split the services. It also hides breaks until runtime for anyone not on the latest package.

principalYou own a public API with hundreds of integrators you cannot contact. How do you evolve it?

Answer

I accept that the contract is effectively permanent and change strategy accordingly: additive-only evolution, with a written and published lifecycle policy that says how long a version lives, how deprecation is announced, and what "sunset" means in practice. Every response gains a deprecation signal that machines can read — the Deprecation and Sunset headers plus a Link to the migration guide — because the only channel that reliably reaches an unknown integrator is the response they are already parsing. I instrument per-consumer usage down to the field level where I can (sampled response-shaping telemetry, or a proxy that records requested GraphQL fields) so the decision to remove something is evidence-based. Then I run the removal as a staged experiment: brownouts — deliberately failing the deprecated path for an hour at a time on an announced schedule — surface the remaining callers far more effectively than any email. And I budget for the long tail: some integrators never move, so the last step is often a permanent compatibility shim in front of the new service rather than a true removal, and saying that out loud is the realistic principal answer.

  • Is a brownout not just a deliberate outage? — Yes, and that is the point: announced, bounded and reversible, versus an unannounced permanent one at sunset.
  • How do you handle an integrator who simply will not migrate? — Commercially, not technically: price the legacy path, or keep a shim and account for its cost explicitly rather than pretending it is free.
  • What would you do differently at v1 knowing this? — Ship a version in the path, tolerate-unknown-fields in the documented client contract, and per-field usage telemetry from day one.

Common wrong answer

"We'll email everyone six months ahead and then remove it." Email reaches the person who signed up, not the contractor who wrote the integration and left. Without machine-readable signals, usage telemetry and brownouts, sunset day is an incident.

03Data modelling and choosing a store

Most system design interviews are won or lost here, because the data model is the decision that outlives every other one: services get rewritten, partition keys do not. Interviewers probe whether you can justify a store from access patterns rather than fashion, design indexes for the queries you actually wrote, and migrate a schema while the system is serving traffic. At mid level, model the entities and index the queries; at senior, defend a partition key against a three-year load model and explain replication lag to a product owner; at principal, decide when a second store is worth its permanent operational cost.

screenerRelational or NoSQL for this system — how do you decide?

Answer

I start from the access patterns and the shape of the consistency requirement, not from the data volume. Relational wins when entities have relationships you will query in more than one direction, when you need multi-row transactions, and when the query set will grow in ways you cannot predict — which describes most business systems, and is why my default is PostgreSQL or SQL Server unless something rules it out. A document or wide-column store wins when the access pattern is genuinely known and singular (fetch this aggregate by this key), when the write volume exceeds what a single primary can absorb, or when the schema is legitimately heterogeneous. The honest framing for an interview is that modern relational engines have absorbed most of the reasons people left them: PostgreSQL 18 has native JSONB with GIN indexing, partitioning, and logical replication; SQL Server 2025 added a native VECTOR type with VECTOR_DISTANCE. So the question is rarely "SQL or NoSQL" and usually "can one relational cluster serve this, and if not, which specific pattern forces me out".

Example

SignalPoints toWhy
Multi-entity invariants (order + inventory + payment)relationalOne transaction beats a saga you now have to operate
Unknown future queries, reporting, ad-hoc joinsrelationalThe optimiser adapts; a denormalised document does not
Single-key access to a self-contained aggregatedocument (Cosmos, Mongo)No join needed; horizontal partitioning is trivial
Write volume beyond one primary (>~50k writes/s sustained)partitioned/wide-columnRelational scale-out means sharding you build yourself
Time-series / append-only at high ratetime-series or columnarRow stores pay index maintenance you do not need
Key-value, sub-millisecond, disposableRedis / ValkeyIt is a cache or a session store, not a system of record

Follow-ups

  • What is the real cost of choosing a document store? — You commit to the access pattern at design time; a new query shape later means a migration or a second copy of the data.
  • How far does one PostgreSQL instance go? — Comfortably tens of thousands of reads/s and low thousands of writes/s on modern hardware with tuned indexes; say "we measure and revisit", not a memorised number.
  • When is "just use Postgres for everything" wrong? — When you need true multi-region active-active writes, or petabyte analytical scans; both are different products, not a bigger instance.

Common wrong answer

"NoSQL because it scales." Scale is a property of partitioning, not of a data model, and relational engines partition too. The answer signals that the candidate has not paid the real price of a document store: every access pattern you did not anticipate becomes a full scan or a second copy.

screenerWhen do you denormalise, and what does it cost you?

Answer

I normalise by default because normalisation makes correctness cheap: one place to write a fact, so it cannot disagree with itself. I denormalise deliberately when a specific read is hot, its join is measurably expensive, and the duplicated value changes rarely — a product name copied onto an order line, a counter maintained alongside the aggregate. The cost is always the same and always underestimated: every copy needs an update path, and the moment the update path is asynchronous you have a window where the copies disagree, which becomes a support ticket. So my rule is that denormalisation is allowed when the duplicated field is either immutable by definition (the price at the time of purchase is not the current price — that is a snapshot, not a duplicate) or when I can point at the code that keeps it in sync and the job that repairs drift.

Example

-- Bad denormalisation: a live copy with no repair path
order_lines(order_id, sku, product_name, unit_price)   -- product renamed → stale everywhere

-- Good: a snapshot, correct by definition, plus a normalised reference
order_lines(order_id, sku, name_at_purchase, price_at_purchase_minor, currency)
products(sku, name, current_price_minor)               -- the live truth lives once

-- Good: a maintained aggregate with an explicit repair job
threads(id, ..., reply_count)                          -- updated in the same tx as the insert
-- nightly: UPDATE threads t SET reply_count = (SELECT count(*) FROM replies r WHERE r.thread_id = t.id)

Follow-ups

  • Counter in the same transaction or via an event? — Same transaction if the counter must be exact on read; via an event if approximate is fine and write throughput matters more.
  • How do you detect drift? — A periodic reconciliation job that compares and emits a metric; drift you cannot measure is drift you find out about from a customer.
  • Does a materialised view count as denormalisation? — Yes, but with a supported refresh path, which is exactly why it is usually the better version of the idea.

Common wrong answer

"We denormalise for performance" with no measurement and no sync path. Nine times out of ten the join was fine and the missing index was the problem; the duplicated column then quietly rots and produces two different answers on two screens.

midHere is a slow query. What index do you create, and how do you know it will be used?

Answer

I read the query's predicates in order: equality columns first, then the range or sort column, then anything I want to cover. That ordering matters because a B-tree can only seek on a prefix — an index on (created_at, tenant_id) is nearly useless for WHERE tenant_id = ? AND created_at > ?, while (tenant_id, created_at) turns it into a single range seek. Then I check selectivity: an index on a column with three distinct values across ten million rows will be ignored, and rightly so. If the query returns a small set of columns I add them as included columns to make it covering, which removes the key lookup back to the heap or clustered index. Finally I verify rather than assert: EXPLAIN (ANALYZE, BUFFERS) in PostgreSQL or the actual execution plan in SQL Server, checking that the operator is a seek rather than a scan and that the estimated and actual row counts are within an order of magnitude — a big gap means stale statistics, which is a different fix entirely.

Example

-- Query
SELECT id, status, total_minor
FROM   orders
WHERE  tenant_id = $1 AND status = 'pending' AND created_at >= $2
ORDER BY created_at DESC
LIMIT 50;

-- Index: equality cols, then the range/sort col, then covered payload
CREATE INDEX ix_orders_tenant_status_created
  ON orders (tenant_id, status, created_at DESC) INCLUDE (total_minor);

-- Verify, do not assume
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
--  want: Index Scan using ix_orders_tenant_status_created  (actual rows=50)
--  bad:  Seq Scan on orders  (actual rows=4,182,551)  → predicate not sargable or stats stale

Follow-ups

  • What makes a predicate non-sargable? — Wrapping the column in a function or an implicit type conversion: WHERE lower(email) = $1 needs an expression index; nvarchar compared to varchar silently converts and scans.
  • What does an index cost? — Write amplification and storage: every insert and every update of an indexed column maintains it, so six indexes on a hot write table is a throughput problem.
  • Partial index — when? — When the query always filters a small subset: WHERE status = 'pending' as an index predicate keeps the index tiny even as the table grows.

Common wrong answer

"Add an index on each column in the WHERE clause." Single-column indexes rarely combine as well as one correctly ordered composite; the engine either picks one and filters the rest, or does an expensive bitmap combination. It also multiplies write cost for no read benefit.

midYou need to shard. How do you choose the partition key?

Answer

I pick the key that appears in the overwhelming majority of queries, distributes writes evenly, and keeps entities that must be transactional together on the same partition. Those three pull against each other, and naming the tension is the answer. Tenant id is the usual winner in B2B systems because it satisfies all three — until one tenant is a thousand times larger than the rest, at which point I need a composite key or a dedicated shard for the whale. Anything monotonic — a timestamp, an auto-increment id — is the classic mistake, because all current writes land on the newest partition and you have built a single-writer system with extra steps. I also decide upfront how re-sharding happens: consistent hashing with virtual nodes, or a directory/lookup table mapping logical shards to physical ones, so growing capacity is a data move rather than a rewrite of every key.

Example

Candidate keys for an orders table
  created_at        even reads, terrible writes  → all inserts hit one partition
  order_id (uuidv4) perfect spread, but every tenant query fans out to all shards
  tenant_id         queries are single-shard, transactions work, but whales create hotspots
  hash(tenant_id) + bucket(order_id % 8)   ← composite: whales spread over 8, small tenants stay local

Growth plan
  1024 logical shards → mapped to N physical nodes via a directory table
  adding capacity = moving logical shards, not rehashing keys
  PostgreSQL 18 note: uuidv7() gives time-ordered ids — great for index locality,
  and exactly wrong as a shard key for the same reason.

Follow-ups

  • What breaks when a query does not include the shard key? — Scatter-gather across every shard, so the p99 becomes the slowest shard's p99 and capacity is consumed N times per query.
  • How do you handle cross-shard transactions? — Avoid them by design; where unavoidable, a saga with compensations, and you say out loud that atomicity is gone.
  • When do you shard at all? — After vertical scaling, read replicas, partitioning within one engine and archiving are exhausted; sharding is the last resort because it is irreversible in practice.

Common wrong answer

"Shard by user id with modulo N." Modulo bakes the node count into every key, so adding the eleventh node rehashes almost everything — the exact migration that consistent hashing or a shard directory exists to avoid.

midRoll out a schema change on a 500M-row table with zero downtime. Walk me through it.

Answer

Expand, migrate, contract — with the application deployed in between, never in the same release. First expand: add the new nullable column or new table, never rename, never drop; deploy code that writes both and reads the old one. Then backfill in bounded batches with a delay between them, keyed on a range so it is resumable and never takes a long lock — tens of thousands of rows per batch, watching replication lag as the throttle signal. Then flip reads to the new column behind a feature flag, verify with a comparison metric, and only in a later release drop the old column. The engine-specific details matter and interviewers check them: PostgreSQL 18 can add a NOT NULL constraint without a full table scan when a matching check constraint exists, and index creation must be CREATE INDEX CONCURRENTLY; in SQL Server, online index rebuilds and WITH (ONLINE = ON) serve the same role. The rule underneath all of it: every migration must be safe with both the old and the new application version running simultaneously, because during a rolling deploy they always are.

Example

-- 1 expand (release N):   instant, no rewrite
ALTER TABLE orders ADD COLUMN placed_at timestamptz NULL;
CREATE INDEX CONCURRENTLY ix_orders_placed_at ON orders (placed_at);

-- 2 backfill (background job, resumable, throttled)
UPDATE orders SET placed_at = created_at
WHERE  placed_at IS NULL AND id > $last_id AND id <= $last_id + 20000;
-- sleep 200ms between batches; abort if replica lag > 5s

-- 3 read flip (release N+1): feature flag, compare old vs new for a week

-- 4 contract (release N+2): only after zero reads of the old column
ALTER TABLE orders DROP COLUMN created_at;

Follow-ups

  • Which DDL statements are dangerous? — Anything taking an ACCESS EXCLUSIVE lock behind a queue of queries: even a fast ALTER blocks everything once one long-running query holds a conflicting lock. Always set a short lock_timeout and retry.
  • Can EF Core migrations do this? — Generate the migration, then read and edit the SQL; the default scaffolding will happily emit a rename or a blocking index build.
  • How do you make the backfill safe to re-run? — Make it idempotent (WHERE placed_at IS NULL) and range-keyed so a crash resumes rather than restarts.

Common wrong answer

"We take a maintenance window and run the migration." Sometimes legitimate — but as a default it hides the real skill being tested, and on a 500M-row table the window is measured in hours, during which a rollback is not possible because the old code cannot read the new schema.

seniorYou add read replicas and users start seeing their own writes disappear. What happened and what do you do?

Answer

Replication is asynchronous, so a read routed to a replica milliseconds after a write on the primary can legitimately return the pre-write state — the user saves a profile, the redirect reads a replica, and the old value comes back. The fix is to decide per read path what consistency it needs rather than flipping a global switch. Read-your-writes is the usual requirement, and the cheapest implementation is a short sticky window: after a write, pin that user's reads to the primary for a few seconds, using a cookie or a token in the session. A more precise version uses the replication position — capture the LSN at commit and have the replica wait until it has applied at least that position, which PostgreSQL supports directly and which trades a little latency for correctness. Everything that does not need it — search results, dashboards, listings — goes to replicas happily. I also monitor replica lag as a first-class SLI and route away from a replica that exceeds a threshold, because lag is not constant: it spikes during backfills and long-running transactions precisely when traffic is heaviest.

Example

// Route by intent, not by chance
public sealed class RoutingDbContextFactory(IHttpContextAccessor http, IClock clock)
{
    // after any write we set: ctx.Response.Cookies["rw"] = clock.UtcNow.AddSeconds(5)
    public string ConnectionFor(QueryIntent intent) =>
        intent is QueryIntent.MustSeeOwnWrites || InStickyWindow()
            ? Primary
            : Replica;                        // dashboards, search, reports
}
// PostgreSQL alternative, exact rather than heuristic:
//   on commit:  SELECT pg_current_wal_lsn();          → carry the LSN in the session
//   on replica: SELECT pg_wal_replay_wait('0/16B3748');  (wait until applied)

Follow-ups

  • How long should the sticky window be? — p99 of measured replica lag plus a margin; if p99 lag is 300 ms, five seconds is generous and cheap.
  • What is monotonic-read consistency and why does it bite? — Two consecutive reads hitting different replicas can go backwards in time; pin a user's session to one replica to avoid it.
  • Do replicas help write throughput? — No. They offload reads, which frees primary capacity, but the write ceiling is unchanged — a distinction interviewers deliberately test.

Common wrong answer

"Use synchronous replication so replicas are always current." That converts every write into a distributed commit: write latency now includes the slowest replica, and losing a replica can stall writes entirely. It is a real option for two nodes in one region, not a default.

seniorHow does your data model change because EF Core is in front of it?

Answer

It should not change the model, but it changes what I must be explicit about, and interviewers use this to find out whether you have operated an ORM at scale rather than just used one. Three things dominate. First, N+1: any lazy-loaded navigation inside a loop becomes one query per row, so I use projection to a DTO with Select — which also stops the ORM from materialising columns nobody reads — and AsSplitQuery when a legitimate include would otherwise produce a cartesian explosion. Second, tracking: read paths get AsNoTracking, because the change tracker is pure overhead when nothing is written. Third, the model itself: EF Core 10 makes value objects natural with complex types — including structs — mapped either inline or to JSON columns, and adds LeftJoin/RightJoin as real LINQ operators, which retires the old GroupJoin + DefaultIfEmpty + SelectMany incantation you will still find all over existing codebases. What I will not do is let the ORM decide the schema for a hot table; I write the index and check the generated SQL.

Example

// modern (EF Core 10): real left join, projection, no tracking
var rows = await db.Orders
    .AsNoTracking()
    .Where(o => o.TenantId == tenantId)
    .LeftJoin(db.Shipments, o => o.Id, s => s.OrderId, (o, s) => new OrderRow(
        o.Id, o.Status, o.Total.Amount, s == null ? null : s.TrackingCode))
    .OrderByDescending(r => r.Id)
    .Take(50)
    .ToListAsync(ct);

// legacy shape you will still meet in existing code
var legacy = from o in db.Orders
             join s in db.Shipments on o.Id equals s.OrderId into g
             from s in g.DefaultIfEmpty()
             select new { o, s };

// value object without a table of its own (EF Core 10 complex types)
modelBuilder.Entity<Order>().ComplexProperty(o => o.Total);   // Money { Amount, Currency }

Follow-ups

  • How do you catch N+1 before production? — Log the query count per request and fail the test above a threshold; EF Core's QueryExecuting event or an interceptor makes it a one-line assertion.
  • When do you drop to raw SQL or Dapper? — Reporting queries, bulk operations, and anything where the plan matters more than the mapping; mixing them in one codebase is normal, not a failure.
  • JSON column or a child table? — JSON when the payload is read as a whole and never queried across rows; a table the moment you need to filter, join or index inside it — though PostgreSQL's GIN indexes blur that line.

Common wrong answer

"EF Core is slow, we'd use Dapper." Framing it as a framework race misses the point: the slow thing is almost always a missing index, a tracked read path or an N+1, all of which reproduce faithfully in Dapper with more hand-written SQL to maintain.

seniorOne tenant is 100× larger than the rest and is degrading everyone. What do you do?

Answer

First I confirm which resource the whale is actually consuming — connections, IOPS, buffer cache, lock contention or a single hot partition — because the remedy differs and guessing wastes a week. Then I apply the cheapest containment that fits: per-tenant rate limits and connection quotas stop one tenant monopolising the pool; a separate connection pool or a dedicated read replica isolates their heavy reporting queries. If the problem is data volume rather than request volume, the answer is a composite partition key so their rows spread across buckets, or moving them to their own database entirely — the "pods" or "shard-per-large-tenant" pattern, where the tenant directory maps tenant to physical location so the application does not care. The lead-level part is that this is a product decision as much as a technical one: dedicated capacity has a cost, and the cleanest resolution is often a tier in the pricing model that pays for it, with the isolation being what the customer is buying.

Example

Diagnose         → per-tenant metrics: queries/s, rows read, lock waits, connection seconds
Contain (hours)  → per-tenant rate limit + connection quota; move their reports to a replica
Isolate (weeks)  → composite key hash(tenant_id, bucket) so their writes spread over 16 buckets
Separate (month) → whale gets its own database; tenant directory maps tenant → cluster
                   app resolves the connection at request start; no code path knows the difference
Commercial       → "dedicated capacity" tier; isolation becomes a feature, not an emergency

Follow-ups

  • How do you spot this before it becomes an incident? — Emit tenant id as a dimension on request and query metrics; without it every dashboard averages the whale away.
  • Does a bigger instance fix it? — Temporarily, and it is often the right first move to buy time — but it raises the shared ceiling without changing the shared-fate structure.
  • What breaks when you move one tenant to its own database? — Anything cross-tenant: global search, aggregate reporting, and any migration tooling that assumed one connection string.

Common wrong answer

"We'd add caching." Caching helps read-heavy hotspots and does nothing for a tenant generating write volume, lock contention or connection exhaustion — and a cache keyed without the tenant dimension can make the noisy-neighbour problem worse by evicting everyone else's entries.

principalWhen is it right to add a second data store, and what does it commit the organisation to?

Answer

A second store is justified when a specific access pattern is fundamentally hostile to the first one and the workaround has a measurable cost — full-text relevance ranking, vector similarity, time-series rollups over billions of points, or graph traversals many hops deep. What it commits you to is permanent and usually underestimated: a second consistency story, a second backup and restore procedure you must actually rehearse, a second set of failure modes and on-call knowledge, a second upgrade treadmill, and a synchronisation pipeline that will drift and needs a reconciliation job with a metric. My rule is that I must be able to name the query that the primary store cannot serve at the required latency, and show that the equivalent feature in the primary — PostgreSQL full-text search or pgvector, SQL Server 2025's native VECTOR type, a materialised rollup table — has been tried and measured. That framing matters in 2026 precisely because relational engines have absorbed so many of the specialist use cases: adding Elasticsearch for a feature that tsvector handles is a cost the team pays every quarter for a benefit it stopped needing.

  • What is the exit plan if the second store was a mistake? — It only exists if the source of truth stayed authoritative; a derived store you can rebuild is reversible, a divergent second master is not.

Common wrong answer

"Use the right tool for the job" as a complete answer. It is true and it is where the reasoning should start; stated alone it skips the part interviewers grade — the recurring cost of every additional tool, and the evidence that the first one genuinely could not do it.

04Caching

Caching appears in nearly every design because it is the cheapest way to buy latency and capacity — and it is where candidates most reliably reveal shallow experience, because the easy part is adding a cache and the hard parts are invalidation, stampedes, and what happens when the cache is empty. At mid level you should place caches at the right layers and pick a write strategy; at senior you should handle stampedes, hot keys and staleness bounds explicitly; at principal you should be able to say when a cache has quietly become load-bearing infrastructure that the system can no longer survive without.

screenerWhere would you put caches in this system, and what goes in each layer?

Answer

I think in layers from the user inwards, because each layer serves a different traffic profile and the cheapest hit is the one closest to the user. Browser and HTTP caches hold immutable assets with content-hashed filenames and a one-year max-age; a CDN holds public, shareable responses and static media; an in-process memory cache holds small, hot, read-mostly data with microsecond access; a distributed cache such as Redis or Valkey holds shared state that must be consistent across instances — sessions, computed views, rate-limit counters; and the database has its own buffer pool, which is why "add a cache" sometimes fixes nothing. The two questions I answer for each layer are what the key is and what makes an entry stale. In .NET the modern default for the application layers is HybridCache, which is exactly this L1-plus-L2 arrangement with stampede protection built in rather than assembled by hand.

Follow-ups

  • Why not just cache everything in-process? — Ten instances mean ten independent copies with independent staleness, and an eviction storm after every deploy because each starts cold.
  • What should never go in a shared cache? — Anything whose loss changes correctness rather than latency: a cache is an optimisation, and treating it as a store is how data disappears on a failover.
  • What is the first thing you check before adding a cache? — Whether the underlying query is slow because of a missing index; caching a bad query hides the cost until the hit ratio drops.

Common wrong answer

"Put Redis in front of the database." Stated as a single undifferentiated layer, it ignores that most of the win is usually at the edge, and it silently makes Redis a hard dependency of every read path — with no answer for what happens when it restarts empty.

screenerCache-aside, write-through, write-behind — which do you use and why?

Answer

Cache-aside (lazy loading) is my default: the application checks the cache, misses, loads from the database, populates the cache, and on write it updates the database and deletes the key rather than updating it. It is simple, tolerates cache loss cleanly, and only caches what is actually read. Write-through populates the cache on every write, which keeps it warm and consistent at the cost of caching data nobody reads and of coupling write latency to cache availability. Write-behind (write-back) buffers writes in the cache and flushes asynchronously — the fastest and the only one that can lose acknowledged data, so it belongs to metrics and counters, not orders. The detail that separates candidates is the delete-versus-update choice on write: updating the cache from application code creates a race where two concurrent writers interleave and leave the older value cached, while deleting means the next read re-derives the truth.

Example

// cache-aside with HybridCache (.NET 9+, the current default in ASP.NET Core)
public async Task<Product?> GetAsync(string sku, CancellationToken ct) =>
    await cache.GetOrCreateAsync(
        $"product:{sku}",
        async token => await repo.LoadAsync(sku, token),          // only one caller runs this
        new HybridCacheEntryOptions { Expiration = TimeSpan.FromMinutes(10),
                                      LocalCacheExpiration = TimeSpan.FromSeconds(30) },
        tags: [$"tenant:{tenantId}", "products"],
        cancellationToken: ct);

public async Task UpdateAsync(Product p, CancellationToken ct)
{
    await repo.SaveAsync(p, ct);                                  // database first
    await cache.RemoveAsync($"product:{p.Sku}", ct);              // delete, do not overwrite
}

Follow-ups

  • Delete before or after the database write? — After, and accept a small stale window; deleting first leaves a race where a concurrent read repopulates the old value before the write lands.
  • What if the delete fails? — TTL is your backstop, which is why every entry gets one even when you invalidate explicitly.
  • When is write-through actually right? — When a cold cache cannot be tolerated — a leaderboard or a pricing table that must be warm the instant it changes.

Common wrong answer

"On write, update the database and set the new value in the cache." It looks obviously correct and it is the classic race: writer A sets v1, writer B sets v2, B's cache write lands first, A's lands second, and the cache serves v1 until the TTL expires — with no error anywhere.

midHow do you invalidate a cache entry that is derived from five different rows?

Answer

By tagging rather than by key arithmetic. If a cached dashboard depends on orders, inventory and pricing for one tenant, I store it under tags for each contributing entity, and any write to one of them evicts everything carrying that tag — which is precisely what HybridCache's tag support, added in .NET 10, and CDN surrogate keys both give you. The alternative — computing every dependent key at write time — works until someone adds a sixth input and forgets, which is how caches quietly start lying. Where tagging is not available, I use a version-stamp trick: keep a per-entity version counter and include it in the cache key, so bumping the counter makes all derived keys unreachable without deleting anything. Whatever the mechanism, every entry also gets a TTL as a backstop, because the only invalidation strategy that never fails is time.

Example

// tag-based: one write evicts every derived view that depends on it
await cache.GetOrCreateAsync(key, factory, options,
    tags: [$"tenant:{t}", $"order:{orderId}", "dashboard"]);

await cache.RemoveByTagAsync($"order:{orderId}", ct);   // evicts every view built from it

// version-stamp alternative when tags are unavailable
var v = await cache.GetOrCreateAsync($"ver:catalog:{t}", _ => ValueTask.FromResult(1L));
var key = $"catalog:{t}:v{v}:page:{page}";               // bump v → all pages unreachable at once

Follow-ups

  • What TTL do you pick? — The longest staleness the product can defend, stated as a requirement: "prices may be up to 60 seconds old" is a decision, "5 minutes because that felt right" is not.
  • How does this work at the CDN? — Surrogate-key headers on the response and a purge-by-key API call on write; the pattern is identical, the vocabulary differs per vendor.
  • What about negative caching? — Cache the "not found" too, with a short TTL, or a missing-key lookup becomes a free path to your database for anyone enumerating ids.

Common wrong answer

"We just use a short TTL, so invalidation is not a problem." Short TTLs trade one problem for two: staleness you cannot bound below the TTL, and a miss rate high enough that the origin now carries most of the traffic — the cache costs money without doing its job.

midA popular cache key expires and the database falls over. What happened, and how do you prevent it?

Answer

That is a cache stampede: the moment a hot key expires, every concurrent request misses simultaneously and they all run the same expensive query, so the origin sees the full unshielded load at once. Three mechanisms fix it, and I usually want all three. First, request coalescing: only one caller executes the factory while the others await its result — this is built into HybridCache and is the main reason to prefer it over hand-rolled IDistributedCache code. Second, jittered expiry, so a thousand keys populated together do not all expire in the same second; adding a random ±10% to every TTL removes the synchronised cliff. Third, early or probabilistic refresh: refresh an entry in the background before it expires so the hot path never sees a miss at all. As a backstop I serve stale-while-revalidate — return the expired value and refresh behind it — which turns an origin outage into slightly old data rather than an error page.

Example

// 1 coalescing is automatic in HybridCache: N concurrent callers, one factory execution
// 2 jitter the TTL so keys do not expire in lockstep
static HybridCacheEntryOptions Jittered(TimeSpan baseTtl) => new()
{
    Expiration = baseTtl * (0.9 + Random.Shared.NextDouble() * 0.2),   // ±10%
    LocalCacheExpiration = TimeSpan.FromSeconds(20)
};

// 3 stale-while-revalidate at the edge, for the same failure at the CDN layer
// Cache-Control: public, max-age=60, stale-while-revalidate=600, stale-if-error=3600

Follow-ups

  • Does a distributed lock solve it? — It solves the duplicate work but adds a failure mode: if the lock holder dies, everyone waits for the lease to expire. Coalescing per instance plus jitter is usually enough.
  • What is the related failure when the cache is empty? — Cold start after a cache restart or deploy: every key misses at once. Warm critical keys on startup and ramp traffic in.
  • What about cache penetration? — Requests for keys that never exist bypass the cache entirely; cache the negative result or put a Bloom filter in front.

Common wrong answer

"Increase the TTL." It reduces how often the stampede happens without changing what happens when it does — and it makes the eventual cold start worse, because more traffic now depends on entries that all vanish together.

midDesign the HTTP caching for a page that is mostly public but has a personalised header.

Answer

I split the response so the cacheable part stays cacheable. The page shell and its content are public with a real Cache-Control: public, max-age=… and an ETag, so the CDN serves it to everyone; the personalised fragment — name, cart count, notifications — is fetched separately by the client, or injected at the edge, and marked private, no-store. Mixing them in one response forces Cache-Control: private on the whole page and throws away the entire CDN hit ratio for a few dozen bytes. Vary is the other trap: Vary: Cookie effectively means "cache nothing", because every user has a distinct cookie, so I keep personalisation out of headers the cache keys on. For revalidation I prefer ETag over Last-Modified, because it is exact and works for generated content; a 304 costs bytes on the wire but still saves the origin's rendering work.

Example

GET /products/8841                      → shared, at the edge
  Cache-Control: public, max-age=60, stale-while-revalidate=600
  ETag: "v3-8841-2026-09-01"
  Surrogate-Key: product-8841 tenant-42  → purge target on write
  Vary: Accept-Encoding                  (NOT Vary: Cookie)

GET /api/me/header                      → per user, never shared
  Cache-Control: private, no-store

Immutable assets
  /assets/app.9f3c1a.js  Cache-Control: public, max-age=31536000, immutable

Follow-ups

  • What does immutable add over a long max-age? — It stops the browser revalidating on a manual refresh, which is otherwise a burst of 304s on every reload.
  • When is no-cache not the same as no-store? — no-cache allows storage but forces revalidation; no-store forbids storage entirely and is what sensitive responses need.
  • How do you purge after a write? — By surrogate key from the write path, and accept that propagation takes seconds; design the UI to tolerate it rather than promising instant global consistency.

Common wrong answer

"Set Vary: Cookie so each user gets their own cached copy." That is technically correct and operationally a disaster: the cache key now includes a unique value per user, so the hit ratio collapses to roughly zero while you pay for the storage.

seniorWhat does HybridCache give you that IDistributedCache did not, and when would you still not use it?

Answer

HybridCache — shipped in .NET 9 and extended in .NET 10 — replaces the pattern almost every team hand-wrote badly: it combines an in-process L1 with a distributed L2, does request coalescing so a hot key cannot stampede, handles serialisation with pluggable serialisers, and in .NET 10 supports tag-based invalidation across both layers. With IDistributedCache you wrote the get-miss-load-set dance yourself, every instance duplicated it, and nothing stopped a hundred concurrent misses from running a hundred identical queries. The L1 is what changes the performance profile: a hit never leaves the process, so the p99 stops depending on a network round trip to Redis, at the cost of a per-instance staleness window you must choose deliberately with LocalCacheExpiration. I would still not use it when the cached data must be strictly consistent across instances within a request — the L1 makes that impossible by construction — or when what I actually need is a distributed data structure (a counter, a sorted set, a stream) rather than a cache, in which case I talk to Redis or Valkey directly.

Example

builder.Services.AddStackExchangeRedisCache(o => o.Configuration = redis);  // L2
builder.Services.AddHybridCache(o =>
{
    o.MaximumPayloadBytes = 1024 * 1024;          // reject accidental giants
    o.DefaultEntryOptions = new HybridCacheEntryOptions
    {
        Expiration            = TimeSpan.FromMinutes(10),  // L2 lifetime
        LocalCacheExpiration  = TimeSpan.FromSeconds(20)   // L1 staleness window — a choice
    };
});

// .NET 10: invalidate across L1 and L2 by tag
await cache.RemoveByTagAsync("tenant:42", ct);

Follow-ups

  • How does an L1 on ten instances stay coherent? — It does not, within LocalCacheExpiration; that window is the price of skipping the network, so keep it short for anything users compare across tabs.
  • What happens if Redis is down? — L1 keeps serving and the L2 path degrades; that is the failure mode to test explicitly, because it is the difference between slow and down.
  • Is the old IDistributedCache deprecated? — No, and it is still what the Redis package implements; HybridCache sits on top of it, so existing registrations keep working.

Common wrong answer

"It is just a wrapper over IMemoryCache and Redis." The wrapper is not the point — coalescing, tag invalidation and a bounded L1 staleness window are — and describing it as sugar suggests you have not hit the stampede that motivates it.

seniorYour cache has a 60% hit ratio and the team wants a bigger Redis. Is that the right move?

Answer

Only if evictions are actually the cause, and usually they are not. I look at three numbers before spending money: the eviction rate, the key-space cardinality against the working set, and the TTL distribution. A 60% hit ratio with near-zero evictions means the misses are TTL expiries or genuinely long-tail keys, and more memory changes nothing — the fixes are longer or jittered TTLs, early refresh, or accepting that the tail is uncacheable. If evictions are high, then the working set genuinely exceeds memory, and the choices are more memory, a smaller value representation (cache ids and hydrate, rather than whole documents), or a better eviction policy — allkeys-lru versus volatile-ttl matters more than people expect. I also check the value size distribution, because a handful of megabyte entries can evict thousands of useful small ones, and the hot-key case, where one key takes so much traffic that a single shard saturates regardless of total memory.

Example

Before buying memory, read these
  evicted_keys/s        ~0    → not a capacity problem; look at TTLs and long-tail keys
  expired_keys/s        high  → TTL too short, or no early refresh
  keyspace_hits/misses  60%   → compare against the theoretical ceiling: what fraction

  used_memory vs maxmemory, and the p99 value size

Follow-ups

  • What is a good hit ratio? — There is no universal number; the useful target is the fraction of requests that are repeatable at all, measured, and 60% may already be the ceiling.
  • Redis or Valkey in 2026? — Both are viable: Redis 8 returned to open source under AGPLv3 in 2025, while Valkey stayed BSD-3 under the Linux Foundation and is the default on several managed cache services. Choose on managed-service support and licence policy, not on features.
  • Which eviction policy? — allkeys-lru for a pure cache; volatile-* only when the instance also holds keys that must not be evicted — which is itself a smell.

Common wrong answer

"Scale up the cache to raise the hit ratio." Without an eviction rate to justify it, that is money spent on a metric that will not move — and it delays finding the real cause, which is often a key that includes a timestamp or a request id and is therefore never hit twice.

principalYour cache went from optimisation to load-bearing. How do you find out, and what do you do about it?

Answer

You find out by testing it, not by reasoning about it: run a game day that flushes or disables the cache in a production-like environment under real traffic and watch what the origin does. Nearly always the answer is that the database cannot serve 100% of read traffic any more, because capacity planning silently assumed the hit ratio — and that is the definition of load-bearing. Once you know, there are three legitimate responses and you pick per path. Accept it and treat the cache as a tier-1 dependency: replicate it, alert on it, put it in the DR plan, and rehearse recovery including the cold-start ramp. Or remove the dependency for the paths that matter, by making the origin able to serve them — a read replica, a materialised view, a smaller payload. Or degrade deliberately: a documented reduced-functionality mode where the origin serves a cheaper response under a load shed, so a cold cache produces a worse product rather than an outage. The principal-level detail is the recovery ramp: a cold cache plus full traffic is a stampede, so restoration means admitting traffic gradually, and that mechanism has to exist before you need it.

Example

Game day: "cache is empty at peak"
  measured  origin read QPS 4k → 31k on flush; database p99 40ms → 9s; error rate 22%
  verdict   load-bearing

Response
  1 classify   which read paths must survive a cold cache (checkout: yes; recommendations: no)
  2 capacity   size the origin for must-survive paths at 100% miss
  3 degrade    recommendations return a static fallback under load shed (feature flag)
  4 recovery   admit traffic in steps (1%, 5%, 25%, 100%) while the cache refills
  5 rehearse   repeat quarterly; the runbook is only true if it was executed

Warm-start on deploy: replay the top-N keys from the previous instance's access log.

Follow-ups

  • Is it wrong for a cache to be load-bearing? — Not inherently; it is wrong for it to be load-bearing accidentally, with no redundancy, alerting or recovery plan.
  • How do you stop it happening again? — Capacity planning states the assumed hit ratio explicitly, and the load test runs at least once with caching disabled.
  • What is the cheapest partial mitigation? — A short-TTL in-process L1 on the hottest keys: it survives an L2 outage entirely and costs nothing but memory.

Common wrong answer

"Redis is highly available with replicas, so it will not be empty." Availability is not the same as warmth: a failover promotes a replica whose memory may be fine, but a version upgrade, a configuration change, a key-schema change or an eviction storm all produce a cold cache with the cluster perfectly healthy.

05Scaling, load balancing and state

This sub-area is where the diagram gets its second box, and interviewers use it to check whether you understand what makes horizontal scaling possible rather than just drawing more rectangles. The real content is state: what has to be shared, what can be per-instance, and what happens at the edges — connections, queues, autoscaling signals and regions. At mid level, explain statelessness and pick a load-balancing strategy; at senior, size a connection pool and design for backpressure; at principal, decide multi-region posture and defend a service-boundary strategy against the organisation that has to run it.

screenerVertical or horizontal scaling — and what makes a service horizontally scalable at all?

Answer

Vertical scaling is a bigger machine: no code changes, immediate, and the correct first move far more often than interviews suggest, because a modern server with hundreds of gigabytes of RAM absorbs an enormous amount of load. Its limits are a hard ceiling, a restart to resize, and no redundancy — one machine is one failure domain. Horizontal scaling removes both limits but only works if the service is stateless in the sense that matters: any instance can serve any request, because nothing needed to serve it lives only in that process. That means sessions in a shared store or a signed token, uploads to object storage rather than local disk, background schedules coordinated by a leader election or a distributed lock, and no in-memory caches that are treated as authoritative. The honest framing is that horizontal scaling moves the bottleneck rather than removing it: ten application instances all point at one database, so the interesting question immediately becomes what happens at the shared tier.

Example

What breaks horizontal scaling (find these before adding instances)
  in-memory session / auth state        → Redis, or a signed token
  local file writes (uploads, exports)  → object storage
  in-process timers/cron                → leader election, or an external scheduler
  static ["singleton"] counters         → shared store, or accept per-instance semantics
  sticky assumptions ("the same user
    always hits the same server")       → design for none, allow it as an optimisation only

Order of moves, cheapest first
  1 fix the query / add the index        (often the whole problem)
  2 scale up                             (minutes, no code)
  3 add read replicas / caching          (read-heavy)
  4 scale out                            (needs statelessness)
  5 partition or shard                   (last, and hard to undo)

Follow-ups

  • Is a stateless service really stateless? — No: it holds connections, caches and in-flight work. "Stateless" means no state whose loss changes correctness for another request.
  • What about sticky sessions? — Acceptable as a latency optimisation, never as a correctness requirement; the moment an instance dies, someone loses their session.
  • When is vertical scaling the right final answer? — When the estimate says the whole workload fits on one machine with headroom, and a warm standby covers availability. Say it out loud; it scores well.

Common wrong answer

"Horizontal scaling is always better because it is elastic and fault tolerant." It is better if the state problem is solved and the shared tier can take the load. Adding instances in front of a saturated database makes things worse: more connections, more lock contention, same throughput.

screenerWhat does the load balancer actually do here — layer 4 or layer 7, and which algorithm?

Answer

A layer-4 balancer forwards TCP connections without looking inside, which makes it fast, protocol-agnostic and unable to do anything content-aware. A layer-7 balancer terminates HTTP, so it can route by path or header, retry idempotent requests, enforce timeouts, inject correlation ids, and multiplex HTTP/2 streams — which is why it is the normal choice in front of an API and why service meshes are L7. The algorithm matters less than people think, with one exception: round robin is fine when requests are uniform, but least-outstanding-requests (least connections) is materially better when they are not, because it naturally steers away from an instance that has slowed down. The real work of the balancer is health checking, and that is where designs go wrong: the check must exercise the dependencies the instance actually needs, but must not cascade — if every instance reports unhealthy because one shared database is slow, the balancer removes the entire fleet and turns a degradation into an outage.

Example

// ASP.NET Core: separate the two health questions
app.MapHealthChecks("/health/live",  new() { Predicate = _ => false });     // process is alive
app.MapHealthChecks("/health/ready", new() { Predicate = c => c.Tags.Contains("ready") });

builder.Services.AddHealthChecks()
    .AddNpgSql(conn, name: "db", tags: ["ready"])          // needed to serve traffic
    .AddRedis(redis, name: "cache", failureStatus: HealthStatus.Degraded);
//        ^ cache down = degraded, NOT unready: do not remove the fleet because Redis blinked

// Load balancer: liveness → restart, readiness → route or not. Never one endpoint for both.

Follow-ups

  • Why not check the database in the liveness probe? — Because a slow database would restart every pod in the cluster simultaneously, which is the worst possible response to a slow database.
  • How does the balancer know an instance is draining? — Readiness flips to false first, the balancer stops sending new work, then the process finishes in-flight requests and exits — that ordering is the whole of graceful shutdown.
  • Where does TLS terminate? — At the edge for throughput, re-encrypted inside if the network is untrusted; say which, because "TLS everywhere" without a termination point is hand-waving.

Common wrong answer

"Round robin, and health checks hit /health which pings the database." One shared dependency plus one shared health endpoint means correlated failure: the balancer marks every instance unhealthy at once and the system goes from slow to entirely unavailable.

midWhere does session and auth state live once you have twenty instances?

Answer

I default to a signed, short-lived token for identity and a shared store only for what genuinely cannot be a claim. A JWT or equivalent carries user id, tenant and coarse roles, is verified without a round trip, and expires in minutes with a refresh token held server-side — so revocation is possible via the refresh path and a small deny-list, which is the standard answer to "you cannot revoke a JWT". Anything mutable, large or sensitive — a shopping cart, a wizard's progress, feature-flag overrides — goes into a distributed store keyed by session id, because putting it in the token makes every request carry it and makes changes invisible until the token is reissued. In .NET the second thing that must be shared is the data-protection key ring: without PersistKeysToStackExchangeRedis or an equivalent, each instance generates its own keys and anti-forgery tokens, auth cookies and protected payloads break the moment a request lands on a different instance — an outage that only appears after you scale out, which is why interviewers like it.

Example

builder.Services.AddDataProtection()
    .PersistKeysToStackExchangeRedis(redis, "dp-keys")   // shared key ring across instances
    .SetApplicationName("checkout");                     // same name = same purpose chain

builder.Services.AddStackExchangeRedisCache(o => o.Configuration = redisConn);
builder.Services.AddSession(o =>
{
    o.IdleTimeout = TimeSpan.FromMinutes(30);
    o.Cookie.HttpOnly = true; o.Cookie.IsEssential = true;
    o.Cookie.SecurePolicy = CookieSecurePolicy.Always;
});

Follow-ups

  • How do you revoke a JWT before it expires? — Keep access tokens short (5–15 min), revoke the refresh token, and maintain a small deny-list of jti values for emergencies.
  • What goes in the token versus a lookup? — Only stable, small, non-sensitive claims; permissions that change often belong behind a cached authorisation call, or every change waits for token expiry.
  • What is the failure mode if the session store is down? — Decide it explicitly: log everyone out, or run degraded read-only. An undecided answer means the first Redis restart logs out every user mid-checkout.

Common wrong answer

"Use sticky sessions so the state stays in memory." It works until an instance is replaced — which happens on every deploy, every autoscale-in and every crash — and it defeats even load distribution because long-lived sessions pin users to instances that are already busy.

midWhat signal do you autoscale on, and why is CPU usually the wrong one?

Answer

I scale on the signal that correlates with user-visible saturation, which for an I/O-bound web service is concurrency or queue depth, not CPU. An ASP.NET Core service waiting on a database can sit at 20% CPU while every request queues, so a CPU-based rule never fires and latency climbs anyway; conversely a garbage-collection spike can trigger a scale-out that does nothing. Useful primary signals are in-flight requests per instance, request queue length, and p95 latency against the budget; for a consumer, the queue backlog and its rate of change. Then I configure the dynamics honestly: scale out fast and scale in slowly, with a cooldown longer than the instance's warm-up time, because thrash is worse than being slightly over-provisioned. And I state the ceiling — the shared tier — because autoscaling application instances into a database with a fixed connection limit is a way to convert a latency problem into a total outage.

Example

Signals, in order of usefulness for a .NET API
  in-flight requests / instance      (saturation, direct)
  p95 latency vs budget              (user-visible)
  queue depth + age (consumers)      (backlog, predicts the future)
  CPU                                (only for genuinely CPU-bound work)
  memory                             (a leak detector, not a scaling signal)

Dynamics
  scale out  +50% capacity, cooldown 60s   (fast: being late costs users)
  scale in   -10% capacity, cooldown 600s  (slow: thrash costs more than a spare instance)
  min instances ≥ 2 always; max bounded by the database connection budget

Trap: 20 instances x 100-connection pool = 2000 connections into a 500-connection Postgres.

Follow-ups

  • How do you handle a predictable 09:00 spike? — Schedule the capacity; reactive autoscaling is always late by the warm-up time, which is exactly when the spike happens.
  • What is the danger of scaling on latency alone? — Latency rises for reasons scaling cannot fix (a slow dependency), so you scale into the wall; pair it with a saturation signal.
  • What must be true before a new instance takes traffic? — Readiness passes, JIT/warm-up done, connection pool primed, caches warmed enough; otherwise scale-out briefly makes latency worse.

Common wrong answer

"Scale when CPU exceeds 70%." It is the platform default, not a design decision, and for I/O-bound services it is a rule that never fires during the incident you built it for.

midHow do you size a database connection pool, and what happens when you get it wrong?

Answer

Connections are a scarce server-side resource, not a client convenience: each PostgreSQL backend is a process with its own memory, and SQL Server workers contend similarly, so more connections past a point reduces throughput. The useful sizing rule is small — on the order of cores × 2 plus a little for effective disk parallelism per instance, typically 10–30, not 100 — because a pool that is larger than the database can usefully execute just moves the queue from your process to the database, where it is invisible and where it holds locks. The failure mode when it is too small is a wait for a free connection that surfaces as a timeout, so I always look at pool wait time as a metric rather than guessing. When it is too big, the symptom is worse and less obvious: the database is at 100% CPU with thousands of context switches, every query is slow, and adding instances makes it deteriorate further. Above a certain fleet size the right answer stops being pool tuning and becomes an external pooler — PgBouncer in transaction mode — so the total connection count is decoupled from the number of application instances.

  • Why do connection-pool timeouts look like database problems? — The exception is thrown by the client before any SQL runs, so database dashboards look healthy while the application times out. Check pool metrics first.
  • What silently exhausts a pool? — A long-running transaction holding a connection across an external HTTP call, and any DbContext whose lifetime escaped the request scope.
  • Does serverless change this? — Drastically: many short-lived instances each opening connections is exactly the pathology poolers exist for, which is why serverless database offerings ship a proxy.

Common wrong answer

"We increased the pool size to fix the timeouts." It is the natural reaction and it usually makes things worse: the timeouts were the database being saturated, and raising the pool just lets more work pile onto a server that is already the bottleneck.

seniorThe business wants multi-region. Active/passive or active/active — and what does each really cost?

Answer

I start by asking what they are buying, because "multi-region" is three different projects: lower latency for distant users, survival of a regional outage, or a data-residency requirement. For latency, read replicas or edge caching in the second region gets most of the benefit at a fraction of the cost, with writes still going home. For availability, active/passive with asynchronous replication is the honest default: define RTO and RPO explicitly, accept that failover loses the replication lag worth of writes, and — critically — rehearse the failover, because an untested one takes hours and usually fails on DNS or a forgotten dependency. Active/active with writes in both regions is a different order of difficulty: you need either partitioned ownership (each region owns a set of tenants and forwards writes it does not own) or genuine conflict resolution, and the moment you allow concurrent writes to the same entity you have chosen eventual consistency for the whole product, which is a business decision, not an infrastructure one. My default recommendation is partitioned active/active if it is required at all, because it gives regional independence without inventing a merge policy for every entity.

  • What fails first in a real failover? — DNS TTLs, a dependency that only existed in the primary region (a secret store, a queue, a licence server), and the cold cache behind the promoted database.

  • Does multi-region improve availability automatically? — No: it adds failure modes (cross-region links, replication) and can lower availability if failover is manual and untested.

Common wrong answer

"Deploy to two regions with a global database and let it handle consistency." The managed product handles the mechanics; it does not decide what your application does when two regions accept conflicting writes to the same order. That policy is yours, and skipping it is the tell.

seniorTraffic doubles unexpectedly. How does the system degrade instead of collapsing?

Answer

By shedding load deliberately at the edge before queues grow, because an overloaded system that accepts everything serves nothing: latency rises past every client timeout, clients retry, and the retries become the new load — congestive collapse. The mechanics are a bounded queue with a rejection policy (fail fast with 429 or 503 plus Retry-After), a concurrency limit per instance sized to what it can actually process, and priority classes so that when capacity is short, checkout succeeds while recommendations and analytics are dropped. Backpressure has to propagate: a consumer that cannot keep up must stop pulling rather than buffering into memory, which is what makes a broker's backlog the honest signal instead of a heap that eventually OOMs. Two things make this work in practice: clients must implement exponential backoff with jitter and respect Retry-After, and retries must be budgeted — a retry rate cap, so a struggling dependency is not amplified threefold by its callers.

Example

// Bounded concurrency + fail fast; queueing is the thing you are avoiding
builder.Services.AddRateLimiter(o => o.AddConcurrencyLimiter("shed", l =>
{
    l.PermitLimit = 64;      // measured: what one instance actually processes
    l.QueueLimit  = 0;       // reject rather than queue; the client can retry
}));

// Priority classes when capacity is short
app.MapPost("/checkout", ...).RequireRateLimiting("critical");    // never shed
app.MapGet("/recommendations", ...).RequireRateLimiting("shed");  // shed first

// Retry budget: cap retries at ~10% of primary traffic, not "3 attempts always"

Follow-ups

  • What is congestive collapse? — Throughput falls as offered load rises, because the system spends its capacity on work whose callers have already timed out.
  • Where should load shedding happen? — As early as possible: at the edge, before authentication and database work is spent on a request you will drop anyway.
  • How do you pick what to shed? — By product value, decided in advance and encoded as a priority tag; deciding during an incident means shedding whatever is easiest to find.

Common wrong answer

"Queue the excess requests so nothing is lost." An unbounded queue converts an availability problem into a latency problem and then back into an availability problem: by the time a request is dequeued, the client gave up and retried, so you serve responses nobody is listening for while the heap grows.

principalShould this be a monolith or microservices — and how do you defend that to a team that wants the other one?

Answer

I decide on organisational and operational grounds, not technical ones, because both architectures can be made to perform. The question is how many teams need to deploy independently, and whether the organisation has the operational maturity — distributed tracing, contract testing, per-service on-call, automated deployment — to pay for a distributed system. My default for a new product is a modular monolith with hard internal boundaries: separate modules, no cross-module database access, communication through explicit in-process interfaces that could become network calls later. It gives you the boundary discipline without the distributed-system tax, and it makes extraction cheap when a boundary proves real. I extract a service when there is a specific pressure: a component with a genuinely different scaling profile, a team that is blocked by another team's release cadence, or a compliance boundary. Defending that to a team wanting microservices means naming the costs they will pay on day one — every in-process call becomes a network call that can fail partially, every transaction becomes a saga, every debugging session becomes a tracing exercise — and offering the modular monolith as the version of their goal that can be delivered this quarter.

06Messaging and event-driven design

Once a design has more than one service, the interviewer will push you onto the asynchronous path, and this is where hand-waving is most visible: everyone can draw a queue, far fewer can explain what happens when the same message arrives twice, out of order, or not at all. At mid level you should choose between synchronous and asynchronous deliberately and know the delivery guarantees; at senior you must solve the dual-write problem, handle poison messages and evolve event schemas; at principal you should be able to say when event-driven architecture is making a system harder to reason about than the coupling it removed.

screenerWhen do you put a queue between two components instead of calling directly?

Answer

When the caller does not need the result to answer its own request, and when the two sides have different availability or throughput profiles. A queue buys three specific things: temporal decoupling, so the producer succeeds while the consumer is down or slow; load levelling, so a spike is absorbed as backlog instead of as failures; and independent scaling of the consumer. It costs you the ability to tell the user the outcome immediately, so the API becomes 202 Accepted plus a way to observe the result, and it introduces a whole class of problems — duplicates, ordering, poison messages, backlog — that a synchronous call does not have. My rule: if the user must see the outcome to continue, keep it synchronous; if the work is a consequence rather than part of the answer — send the email, update the search index, recalculate the recommendation — make it asynchronous, and do it by publishing a fact rather than by queuing an instruction.

Example

Order placement, split by what the user must see

synchronous (must succeed before the 201)
  validate cart · reserve inventory · authorise payment · persist order

asynchronous (consequences, published as facts)
  OrderPlaced → email confirmation
             → warehouse pick list
             → search index update
             → loyalty points
             → analytics

API: POST /orders → 201 with the order id and status=confirming
     GET  /orders/{id} → the user observes progress; no long-polling of a queue

Follow-ups

  • What does the user see while the async work runs? — An explicit intermediate state in the resource, not a spinner that lies; "processing" is a real status with its own UI.
  • Does a queue improve reliability by itself? — Only if the producer's write and the publish are atomic; otherwise it adds a way to lose work (see the outbox question).
  • When is a queue the wrong answer? — When the caller immediately polls for the result: you have rebuilt a synchronous call with extra latency, extra components and worse error reporting.

Common wrong answer

"Put everything on a queue to decouple the services." Decoupling in time is not decoupling in logic: if the consumer must run before the user can proceed, you have kept the coupling and lost the error message, the stack trace and the ability to say what went wrong.

screenerMessage broker or event log — Service Bus/RabbitMQ versus Kafka. How do you choose?

Answer

A broker is a work queue: messages are dispatched to consumers, acknowledged, and then gone, with per-message operations like scheduled delivery, dead-lettering and selective retry. A log is a durable, ordered, replayable sequence: consumers track their own offset, messages persist for a retention period regardless of consumption, and several independent consumers read the same partition at their own pace. That difference decides the choice. If the semantics are "this task must be done once by someone", a broker — Azure Service Bus, RabbitMQ, SQS — is a better fit and dramatically simpler to operate. If the semantics are "this happened, and any number of current and future consumers may care", a log — Kafka, or its managed equivalents — is right, and replay is the killer feature: a new consumer can rebuild its state from history. Worth knowing for 2026: Kafka 4.0 removed ZooKeeper entirely in favour of KRaft, and Kafka 4.2 (February 2026) took share groups — queue-like semantics per message, KIP-932 — to production readiness, which narrows the gap from the log side.

  • Can you do work queues on Kafka? — Yes, and since 4.2 share groups make it first-class rather than a workaround — but a broker is still simpler if that is all you need.
  • Where do Azure Event Hubs / AWS Kinesis sit? — Log-shaped: partitioned, offset-based, replayable within retention; Event Hubs even speaks the Kafka protocol.
  • What is the operational difference? — Kafka is a stateful cluster you size for disk and partitions; a managed broker is closer to a service you configure. That cost is a legitimate deciding factor.

Common wrong answer

"Kafka, because it is faster and scales." Kafka's throughput is real and almost never the constraint at the volumes in question; choosing it for speed while the actual need is "run this task once, retry it, and dead-letter it after five attempts" buys a cluster to operate and loses the features that mattered.

midAt-least-once, at-most-once, exactly-once — which do you get, and how do you live with it?

Answer

In practice you design for at-least-once and make consumers idempotent, because that is what every real broker gives you once acknowledgements and networks are involved. At-most-once means acknowledging before processing: no duplicates, but work is lost if the consumer dies mid-handler, which is only acceptable for telemetry. Exactly-once delivery is not achievable end-to-end — the classic two-generals result — but exactly-once processing is, within a boundary, by making the effect idempotent or by committing the offset and the side effect in one transaction. Kafka's transactional producer plus read-committed consumers achieves that within Kafka; the moment the side effect is an external database or a payment, you are back to idempotency keys. So the answer I give is: assume duplicates, give every message a stable id, and either deduplicate on that id in the same transaction as the effect, or make the effect naturally idempotent — a set rather than an increment, an upsert rather than an insert.

Example

// Idempotent consumer: dedupe row and effect in ONE transaction
await using var tx = await db.Database.BeginTransactionAsync(ct);

var first = await db.ProcessedMessages
    .Where(m => m.MessageId == msg.MessageId)
    .ExecuteUpdateAsync(_ => _, ct) == 0;          // or INSERT ... ON CONFLICT DO NOTHING
if (!first) { await tx.CommitAsync(ct); return; }  // duplicate: ack and move on

db.ProcessedMessages.Add(new(msg.MessageId, DateTimeOffset.UtcNow));
await ApplyEffectAsync(msg, ct);                   // same DbContext, same transaction
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);                          // effect + dedupe commit together

Follow-ups

  • How long do you keep the dedupe table? — Longer than the broker's maximum redelivery window plus your longest outage; partition it by day and drop old partitions.
  • What if the side effect is an external API call? — Pass an idempotency key to it and record the outcome; if it does not support one, you must accept possible duplicates and design a reconciliation.
  • Does Kafka's exactly-once help you? — Within Kafka-to-Kafka pipelines, yes. It says nothing about the database write your consumer performs.

Common wrong answer

"We enable exactly-once semantics on the broker, so duplicates cannot happen." It is the single most common misconception in this area, and it usually means the consumer has no dedupe path — so the first redelivery after a rebalance sends the customer a second email or a second charge.

midYou save an order and publish OrderPlaced. The publish fails. Now what?

Answer

That is the dual-write problem: two systems, no shared transaction, so any ordering leaves a window where they disagree — publish first and the message may describe an order that was never saved; save first and the event may never be published. The standard fix is the transactional outbox: write the event into an outbox table in the same database transaction as the order, then have a separate relay poll or tail the table and publish, marking rows as sent. The write is atomic because it is one transaction; publication becomes at-least-once, which is fine because consumers are idempotent. The variant worth naming is CDC-based publishing, where the relay reads the database's replication log — logical replication in PostgreSQL, Debezium and friends — so there is no polling at all and no chance of an unpublished row. The inverse pattern, the inbox, does the same on the consumer side. In .NET this is not something you hand-roll any more: MassTransit, NServiceBus and Wolverine all ship an outbox that hooks into the EF Core transaction.

Example

-- one transaction: business state and the intent to publish
BEGIN;
  INSERT INTO orders (id, tenant_id, total_minor, status) VALUES ($1, $2, $3, 'placed');
  INSERT INTO outbox (id, aggregate_id, type, payload, occurred_at)
       VALUES (gen_random_uuid(), $1, 'OrderPlaced', $4, now());
COMMIT;

-- relay (separate process): at-least-once publish, ordered per aggregate
SELECT * FROM outbox WHERE published_at IS NULL
ORDER BY occurred_at LIMIT 100 FOR UPDATE SKIP LOCKED;
-- publish, then: UPDATE outbox SET published_at = now() WHERE id = ANY($1);

Follow-ups

  • Why FOR UPDATE SKIP LOCKED? — It lets several relay instances work the same table concurrently without blocking each other or double-publishing a row.
  • Outbox or CDC? — Outbox when you want to control the event shape (it is a published contract, not your table schema); CDC when you want zero application involvement and can live with row-shaped events.
  • What is the ordering guarantee? — Per aggregate if you publish in occurred_at order per aggregate id; global ordering is not offered and should not be relied on.

Common wrong answer

"Wrap the database save and the publish in a distributed transaction." Two-phase commit across a database and a broker is either unsupported, or supported and operationally awful: a coordinator failure leaves locks held and the system blocked. The outbox exists precisely because 2PC was tried and abandoned.

midMessages arrive out of order and the consumer computes the wrong state. How do you fix it?

Answer

First, restrict where ordering is required: global ordering is neither available nor necessary, but ordering per entity almost always is. Both models give you that the same way — partition by the entity key, so every event for one order goes to the same partition or session and is processed by one consumer in sequence. In Kafka that is the message key; in Azure Service Bus it is a session id; in RabbitMQ it is a consistent-hash exchange plus a single consumer per queue. Second, make the consumer resilient anyway, because retries and redeliveries can still reorder within a partition: carry a version or sequence number on the entity and discard any event whose version is not the next one, or write the state idempotently so applying an older event is a no-op. The trade-off to name unprompted is that ordering costs parallelism — one consumer per partition means a slow message blocks its partition, so the partition count becomes your maximum consumer concurrency and a poison message stalls a whole key range.

Example

// Kafka: key by the entity so all its events share a partition
await producer.ProduceAsync("orders", new Message<string, byte[]>
{
    Key   = order.Id.ToString(),      // partition = hash(key) → per-order ordering
    Value = Serialize(evt)
});

// Consumer: version guard, because ordering is necessary but not sufficient
if (evt.Version != current.Version + 1)
{
    if (evt.Version <= current.Version) return;      // already applied, drop
    await BufferOrRequeueAsync(evt, ct);             // gap: wait for the missing one
    return;
}
Apply(evt);

Follow-ups

  • What limits your consumer parallelism? — The partition count: one active consumer per partition per group, so partitions must be provisioned for peak concurrency and are awkward to increase later.
  • What happens to ordering when you add partitions? — Existing keys can rehash to different partitions, so events for one entity may briefly be split across two — plan a drain, or use a sticky mapping.
  • Does a timestamp solve ordering? — No: clocks disagree across producers, so timestamps break ties badly. Use a per-entity sequence number issued by a single writer.

Common wrong answer

"Use a single partition so everything stays ordered." It is correct and it caps your throughput at one consumer forever — a design that works in the interview and falls over the first time volume grows, with no incremental way out.

seniorA message fails every time it is delivered. Design the retry and dead-letter policy.

Answer

I separate transient from permanent failures, because they need opposite treatment. Transient — a timeout, a 503 from a dependency, a deadlock — gets a bounded retry with exponential backoff and jitter, ideally as a delayed redelivery rather than an in-process sleep, so the consumer is not holding a slot while it waits. Permanent — a validation error, a missing referenced entity, a deserialisation failure — should not be retried at all: it goes straight to the dead-letter queue with the exception and the full message context, because retrying it burns capacity and delays everything behind it. The dead-letter queue is only useful if someone looks at it, so it gets an alert on depth and age, a documented owner, and a supported way to fix and replay a message after the bug is deployed. The subtlety senior candidates are expected to raise is head-of-line blocking: in an ordered partition, a poison message stalls every message behind it, so the policy must have a hard cap after which the message is parked and the partition advances — losing ordering for that key deliberately rather than stalling the system accidentally.

Example

// MassTransit: retry transient, never retry permanent, delay between attempts
cfg.ReceiveEndpoint("order-placed", e =>
{
    e.UseMessageRetry(r =>
    {
        r.Ignore<ValidationException>();                 // permanent → straight to DLQ
        r.Ignore<JsonException>();
        r.Exponential(5, TimeSpan.FromSeconds(1),
                         TimeSpan.FromMinutes(5),
                         TimeSpan.FromSeconds(2));       // 1s, 2s, 8s, 30s, 2m (+jitter)
    });
    e.UseScheduledRedelivery(r => r.Intervals(
        TimeSpan.FromMinutes(15), TimeSpan.FromHours(1), TimeSpan.FromHours(6)));
    e.ConfigureConsumer<OrderPlacedConsumer>(ctx);
});
// Alerts: dlq_depth > 0 for 15 min, and oldest_message_age > 1h → page the owning team.

Follow-ups

  • In-process retry or scheduled redelivery? — Short retries in process (sub-second transients), longer ones as scheduled redelivery so the consumer slot is released.
  • How do you replay from the DLQ safely? — Through the same idempotent consumer path, in small batches, after the fix is deployed — never by editing the message body by hand.
  • What if the DLQ fills with thousands of identical failures? — That is a circuit-breaker signal: stop consuming, alert, and fix; draining a broken consumer into the DLQ at full rate helps nobody.

Common wrong answer

"Retry indefinitely until it succeeds." An infinite retry on a permanent failure is an infinite loop with a network hop in it: it consumes the consumer's capacity, blocks its partition, and hides the bug because nothing ever reaches a dead-letter queue for anyone to notice.

seniorHow do you evolve an event schema when you do not control the consumers?

Answer

The same discipline as a public API, plus one extra decision: how much state the event carries. Events are additive-only — add optional fields, never remove or repurpose one, never change a type or the meaning of a value — and consumers are contractually required to ignore unknown fields, which has to be written down before the first consumer exists. A schema registry with an enforced compatibility mode (backward, so new producers work with old consumers) turns that from a convention into a build failure. The extra decision is between event notification — a thin "OrderPlaced { orderId }" that makes consumers call back for detail, keeping the contract tiny but coupling them to your API — and event-carried state transfer, a fat event with everything a consumer needs, which decouples them at the cost of a much bigger contract you can never shrink. For anything replayed or consumed outside your team, I lean to a deliberately chosen middle: the identifiers plus the fields that define the business fact, and nothing that is merely convenient. Real breaks get a new event type, published alongside the old one, with the old one deprecated on a schedule — never an in-place change.

Example

// v1 — additive evolution, never a rename
{
  "specversion": "1.0",                       // CloudEvents envelope
  "type": "com.example.order.placed.v1",      // version in the type, not the payload
  "source": "/orders",
  "id": "0f9a...",                            // stable id → consumer dedupe key
  "time": "2026-09-08T09:41:07Z",
  "subject": "order/8841",
  "data": {
    "orderId": "8841", "tenantId": "42",
    "totalMinor": 12999, "currency": "EUR",
    "placedAt": "2026-09-08T09:41:06Z"
    // added later: "channel": "web"   ← optional, consumers ignoring it stay correct
  }
}
// Breaking change → publish com.example.order.placed.v2 in parallel; deprecate v1 on a date.

Follow-ups

  • Why CloudEvents rather than your own envelope? — Standard metadata (id, type, source, time, subject) that tooling, brokers and tracing already understand; the payload stays yours.
  • What compatibility mode do you set in the registry? — Backward by default (consumers lag producers); full when you cannot control deployment order in either direction.
  • Is an internal event a contract? — The moment a second team consumes it, yes — and replayed logs make old events immortal, so "internal" ages badly.

Common wrong answer

"We publish the domain entity as the event." Serialising your table or aggregate makes every internal refactor a breaking change for every consumer, and it leaks fields you never intended to expose. The event is a contract; the entity is an implementation detail.

seniorConsumer lag is growing and the backlog is at two million messages. What do you do?

Answer

First establish whether this is a throughput problem or a stuck problem, because the responses are different: if lag grows steadily, the consumer is slower than the producer; if it grows in a step and the rate is near zero, something is blocked — a poison message, a rebalance loop, a dependency down. For a throughput problem I look at per-message processing time before adding consumers, since the usual cause is a per-message database round trip that batching fixes ten-fold, and adding consumers past the partition count does nothing at all. Then I scale: more partitions if the cap is structural, more consumer instances if not, and prefetch tuned so instances are not idle between fetches. While recovering, I care about two numbers: the drain rate and the projected catch-up time, because the business question is "when is it current" and that requires consumption rate to exceed production rate with margin. If the backlog is old and the events are idempotent state updates rather than commands, an option worth naming is skipping ahead — reset to the latest offset and backfill state separately — which trades completeness for recovery time and must be an explicit, reversible decision.

Example

Triage
  lag rate > 0, consume rate ~normal   → throughput; producer outpaced the consumer
  lag rate > 0, consume rate ~0        → stuck: poison message, rebalance storm, dep down
  lag on ONE partition only            → hot key, or that partition's consumer is wedged

Fix throughput, in order of leverage
  1 batch the database work        200 single upserts → 1 bulk upsert  (often 10-20x)
  2 remove per-message I/O         cache lookups, reuse connections
  3 raise prefetch / max.poll.records so consumers stay busy
  4 add consumers                  (capped by partition count!)
  5 add partitions                 (needs a rebalance; keys may move)

Report: drain rate 12k/s vs produce 4k/s → 8k/s net → 2M / 8k ≈ 4 min to current.

Follow-ups

  • What is a rebalance storm? — Consumers repeatedly exceeding the poll interval get evicted, triggering a rebalance, which pauses everyone and causes the next timeout; raise the interval or shrink the batch.
  • Which metric do you alert on — lag or age? — Age of the oldest unprocessed message; lag in message count means nothing when the rate varies by an order of magnitude across the day.
  • Can you scale consumers beyond partitions? — Not within a consumer group in classic Kafka; share groups (KIP-932, production-ready in Kafka 4.2) change that by allowing multiple consumers per partition.

Common wrong answer

"Add more consumer instances." If the topic has twelve partitions, the thirteenth consumer sits idle — and if the handler does one database round trip per message, the fix was batching, not instances. Scaling before measuring per-message cost is the reflex interviewers are checking for.

principalYour event-driven system is now impossible to reason about. What went wrong and how do you recover it?

Answer

The usual root cause is choreography without a map: every service publishes and subscribes, business processes exist only as emergent behaviour across a dozen handlers, and no single artefact says what happens when an order is placed. That is fine at three services and unmanageable at thirty — nobody can answer "why did this order not ship" without reading every consumer. My recovery has three parts. First, make the process explicit where the process matters: introduce orchestration — a saga or workflow with a durable state machine — for the small number of business-critical flows, so there is one place that knows the steps, the timeouts and the compensations, while keeping choreography for genuine broadcast facts like analytics and search indexing. Second, restore observability: correlation ids propagated through message headers, distributed tracing spanning producer and consumer, and a per-flow dashboard showing where instances are stuck. Third, tighten the contracts: an event catalogue with owners and consumers, so the blast radius of a change is knowable. The principal-level judgment is admitting that the coupling never disappeared — it moved from code, where a compiler and a call graph could see it, into runtime, where only tooling can — and that some of it should move back.

  • How do you find the flows worth orchestrating? — Follow the incidents and the support tickets: the flows people ask "where is it?" about are exactly the ones that need explicit state.

07Consistency, transactions, distributed data

This is the theory sub-area that interviewers use to separate people who have read about distributed systems from people who have shipped one. The questions look academic — CAP, isolation levels, sagas — but the grading is practical: can you say what a user actually sees, and what the code does when two writers collide. At mid level you must know isolation levels and optimistic concurrency; at senior you design sagas with real compensations and explain eventual consistency to a product owner without jargon; at principal you decide whether patterns like CQRS and event sourcing are worth their permanent complexity.

screenerExplain CAP, and what it means for the system you just designed.

Answer

CAP says that when a network partition occurs, a distributed system must choose between remaining consistent (refusing operations it cannot make safe) and remaining available (answering anyway, possibly with stale or conflicting data). The part people get wrong is that it is only about the partition case: with no partition you can have both, so "we chose AP" is not a licence for permanent inconsistency. PACELC is the more useful framing for design work — else, when there is no partition, you still trade latency against consistency, and that trade is the one you make every day, not once. Concretely for a typical system: the orders database is CP, because I would rather reject a write during a partition than take two conflicting payments; the product catalogue and search index are AP, because serving a slightly stale product page is obviously better than serving an error. Saying which components sit where, and why, is what the question is actually testing.

Orders / paymentsCP — reject writesA double charge costs more than a failed request
Inventory reservationCP within a regionOverselling is a business liability; use a single writer per SKU
Catalogue, search indexAP — serve staleA 5-minute-old price beats a 500 error

Follow-ups

  • What does PACELC add? — The no-partition case: even when healthy, cross-region strong consistency costs a round trip, so most systems choose latency in the common case and consistency during partitions.
  • Is a single-node database CA? — The label is meaningless there: with no partition possible, CAP has nothing to say. It is a distributed-systems theorem.
  • Where does "eventually consistent" actually land? — Ask for the bound: eventual with a measured p99 convergence of 200 ms is a design; eventual with no bound is an excuse.

Common wrong answer

"Pick two of three — we chose availability and partition tolerance." Partition tolerance is not a choice; networks partition whether or not you consented. The real statement is "during a partition we prefer availability", and the follow-up is always "for which data".

screenerWhich isolation level do you run at, and what anomaly does that let through?

Answer

I run at the engine's practical default and then design around its specific gap. PostgreSQL's default is read committed, which prevents dirty reads but allows non-repeatable reads and phantoms; its repeatable read is actually snapshot isolation, which additionally prevents those but still permits write skew — two transactions each reading a consistent snapshot and making decisions that are invalid together. SQL Server's default is also read committed, but by default with locking rather than versioning, so readers block writers until you enable read-committed snapshot isolation, which nearly every serious deployment does. The point is not to recite the table but to name the anomaly that matters for the operation at hand: if the invariant is "at most one active subscription per account", read committed will let two concurrent requests both see zero and both insert. The fix is either a unique constraint (let the database enforce it), an explicit lock on the row you are deciding about, or serialisable isolation for that specific transaction — and choosing between them is the interesting part.

Example

-- Write skew under snapshot isolation: both transactions see 2 doctors on call,
-- both allow one to go off duty, and the shift ends with zero.
BEGIN ISOLATION LEVEL REPEATABLE READ;
  SELECT count(*) FROM shifts WHERE on_call AND ward = 3;   -- returns 2 in BOTH
  UPDATE shifts SET on_call = false WHERE doctor_id = $me;  -- no conflict detected
COMMIT;

-- Fixes, cheapest first
--  1 constraint:  a partial unique index / CHECK the database can enforce
--  2 lock the decision row:  SELECT ... FOR UPDATE on a ward row
--  3 SERIALIZABLE for this transaction only + retry on 40001 serialization_failure

Follow-ups

  • What does SERIALIZABLE cost in PostgreSQL? — Not locks but aborts: SSI detects dangerous structures and raises a serialization failure, so the application must retry. Cheap under low contention, painful under high.
  • Why is RCSI the standard setting in SQL Server? — Without it readers take shared locks and block writers, producing blocking chains that look like a performance problem and are actually an isolation choice.
  • Where do NOLOCK hints belong? — Almost nowhere: they permit dirty reads and, worse, missing or duplicated rows during page splits. Use RCSI instead.

Common wrong answer

"We use transactions, so the data is consistent." A transaction guarantees atomicity and the isolation level you asked for — nothing more. Most real bugs in this area happen at the default level, inside a perfectly valid transaction, because the invariant spanned rows the transaction never locked.

midTwo users edit the same record at once. Optimistic or pessimistic concurrency?

Answer

Optimistic by default, pessimistic when the conflict rate is genuinely high or the work before the write is expensive to redo. Optimistic means carrying a version — a row version, an xmin, a timestamp — and making the update conditional on it; if zero rows were affected, someone else won and the caller gets a 409 with the current state so a human or the client can merge. It costs nothing when there is no contention, which is the normal case. Pessimistic means taking a lock (SELECT ... FOR UPDATE) for the duration of the transaction, which is correct but serialises access and is dangerous the moment the transaction is long or spans an external call — a lock held across an HTTP request is how connection pools die. In a web application there is a third case worth naming: a long-lived edit spanning minutes cannot hold a database lock at all, so it becomes an application-level advisory lease with a TTL and a visible "being edited by" indicator, which is a product decision as much as a technical one.

Example

// EF Core optimistic concurrency: version token on the entity
modelBuilder.Entity<Document>().Property(d => d.Version).IsRowVersion();

try
{
    doc.Title = input.Title;
    await db.SaveChangesAsync(ct);          // UPDATE ... WHERE id = @id AND version = @v
}
catch (DbUpdateConcurrencyException ex)
{
    var current = await ex.Entries[0].GetDatabaseValuesAsync(ct);
    return Results.Conflict(new { message = "modified by someone else", current });
}

// Pessimistic, only for short transactions with no external calls
// var row = await db.Accounts.FromSql($"SELECT * FROM accounts WHERE id = {id} FOR UPDATE")...

Follow-ups

  • What does the user see on a 409? — The design question that matters: a diff and a merge for documents, "refresh and retry" for simple forms, automatic retry for machine callers.
  • Does optimistic concurrency work across services? — Yes, and better than locking does: pass the version as an If-Match ETag and let the owning service reject stale writes.
  • When is a lost update acceptable? — When fields are independent: patching only changed fields turns most conflicts into non-conflicts without any locking at all.

Common wrong answer

"Lock the row when the user opens the edit form." That lock is held for however long the user takes — including forever, if they close the tab — so the database transaction spans human think-time. It exhausts connections and blocks unrelated queries within minutes.

midA business transaction spans three services. There is no distributed transaction. Now what?

Answer

A saga: the process becomes a sequence of local transactions, each committing in its own service, with a compensating action defined for every step that can be undone. Order matters — do the reversible and cheap steps first and the irreversible ones last, so that failure late in the sequence costs less. Every step must be idempotent because retries are certain, and every compensation must also be idempotent and must be able to run against a state it did not create. The important honesty is that a compensation is not a rollback: refunding a payment is a new fact, not the erasure of the old one, and if a confirmation email has been sent you cannot un-send it — so the design must include steps that are semantically undoable rather than pretending atomicity. Between the two styles, I use orchestration for anything business-critical, so the state machine is explicit and I can query where an instance is stuck, and reserve choreography for broadcast side effects.

Example

Place order — orchestrated saga (state persisted at every transition)

  1 reserve inventory      compensate: release reservation      (cheap, reversible)
  2 authorise payment      compensate: void authorisation       (reversible ~7 days)
  3 create shipment        compensate: cancel shipment          (reversible until picked)
  4 capture payment        compensate: refund                   (a NEW fact, not an undo)
  5 send confirmation      compensate: none possible            (irreversible → last)

Failure at 3 → compensate 2, then 1; saga ends in "failed", order shows "could not be placed".
Timeouts are states too: "awaiting payment" for > 15 min → compensate and notify.
Each step carries the saga id as an idempotency key; retries re-enter the same step safely.

Follow-ups

  • What is the hardest part of a saga in practice? — Timeouts and stuck instances: every step needs a deadline and an owner, or you accumulate orders in limbo that only surface via support tickets.
  • Where does the saga state live? — In a durable store owned by the orchestrator (a workflow engine, MassTransit's saga persistence, or a table), never in memory.
  • How do users see this? — As explicit intermediate statuses. "Pending" is a legitimate, designed state, not a UI failure.

Common wrong answer

"Use two-phase commit across the services." Even where it is technically available, 2PC blocks: a coordinator crash between prepare and commit leaves participants holding locks with no safe unilateral action, so the outage lasts until a human intervenes. That property, not the protocol's complexity, is why the industry moved to sagas.

seniorProduct says "the number is wrong on this screen" and the cause is eventual consistency. How do you handle it?

Answer

I treat it as a UX and contract problem rather than a database one, because the underlying lag is usually correct and cheap while removing it is expensive. First I quantify: what is the measured p50 and p99 convergence time, and is the complaint about a five-second window or a five-minute one — because the second is a bug and the first is a design. Then I decide per screen. For the user's own actions I guarantee read-your-writes, since the intolerable case is nearly always "I did something and it did not appear": that is worth pinning reads to the primary or optimistically rendering the local change. For aggregate numbers other people's actions produce, I make the staleness visible and honest — "as of 09:41", a refresh affordance — which converts a bug report into an understood property. Finally I add the guardrail: a monitored convergence lag with an alert, so when the number really is wrong because the pipeline is stuck, the team learns it from a page rather than from the same product manager.

Example

Triage for "the number is wrong"

              expected 200 ms / 2 s   observed 4 min  → this is a stuck pipeline, not design
2 classify    the user's own write?      → read-your-writes required (pin to primary)
              someone else's aggregate?  → staleness is acceptable IF shown

Follow-ups

  • What if product insists on real-time? — Price it: strong consistency on that read means primary reads or synchronous projection, and name the latency and cost it adds. Usually "within 5 seconds, visibly timestamped" wins.
  • How do you do optimistic UI safely? — Render the expected outcome, reconcile when the server responds, and design the rollback path — including what the user sees when the write is rejected.
  • Is a "refresh" button an admission of failure? — No; it is an explicit contract with the user and far better than a screen that silently disagrees with another screen.

Common wrong answer

"Make that read strongly consistent." Sometimes right, usually a reflex: it moves load back onto the primary, raises latency for every user, and does not fix the cases where the lag was a stuck projection rather than replication.

seniorYou need exactly one instance to run a job. How do you implement a distributed lock — and what breaks?

Answer

My first move is to avoid needing one: make the job idempotent so running it twice is harmless, or partition the work so each instance owns a disjoint slice, which removes the lock entirely. When mutual exclusion is genuinely required, the correct implementation depends on how bad a double-run is. For scheduling convenience — a nightly report, a cleanup — a lease in the database (SELECT ... FOR UPDATE SKIP LOCKED or an advisory lock) or a Redis key with a TTL and a unique owner token is fine, and the failure mode is an occasional duplicate run. For anything where a double-run is a correctness violation, a TTL-based lock is not safe: the holder can be paused by a long GC pause or a hypervisor stall past the lease expiry, another instance acquires the lock, and now two processes believe they hold it. The mitigations are a fencing token — a monotonically increasing number checked by the resource being protected, which rejects the stale holder's writes — or a real consensus-backed lock from etcd, ZooKeeper or a Kubernetes lease. Naming that distinction, rather than reaching for Redlock, is what the question is testing.

Example

// Convenience lease (fine for "usually once"): unique token, TTL, safe release
var token = Guid.NewGuid().ToString();
if (await redis.StringSetAsync("lock:nightly", token, TimeSpan.FromMinutes(5), When.NotExists))
{
    try { await RunAsync(ct); }
    finally
    {
        // release only if we still own it — never a plain DEL
        await redis.ScriptEvaluateAsync(
            "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end",
            ["lock:nightly"], [token]);
    }
}

// Correctness-critical: fencing token checked by the protected resource
// acquire → token 42; every write carries 42; the store rejects any write with token < 42.

Follow-ups

  • Is Redlock safe? — It is contested, and the honest answer is: adequate for efficiency (avoid duplicate work), not sufficient for correctness without fencing. Say which of the two you need.
  • What is the .NET-native option? — On Kubernetes, a Lease object; in an ASP.NET Core service, a hosted service that acquires a database advisory lock at startup and renews it.
  • What happens when the lock holder dies? — The TTL expires and someone else takes over — which means the TTL is also your maximum downtime for that job, so choose it against the job's tolerance.

Common wrong answer

"Use a Redis SETNX lock — that guarantees only one runs." It guarantees only one acquires. A stop-the-world GC pause longer than the TTL is enough for two processes to believe they hold it, and without fencing the resource cannot tell which one is stale.

seniorWould you use CQRS here? What does splitting reads from writes actually buy?

Answer

CQRS at its cheapest is just separate models for reading and writing in the same database, and that version I use routinely: a rich domain model for commands with its invariants, and flat projected DTOs for queries, built by SQL that ignores the aggregate structure entirely. That alone removes most of the pain of trying to make one model serve both, and it costs nothing. The expensive version — a separate read store, updated asynchronously from write-side events — buys independent scaling, read models shaped exactly per screen, and the ability to add a new view without touching the write path. It costs eventual consistency that the UI must handle, a projection pipeline that can lag, break or drift, and a rebuild procedure you must actually be able to run. So I apply it selectively: a read-heavy area with expensive joins and a tolerable staleness window gets a projection; the rest of the system does not. Applying full CQRS everywhere is the classic overcorrection, and interviewers are listening for whether you scope it.

Example

// Cheap CQRS: one database, two models. This is the default, not an architecture.
public async Task<Guid> Handle(PlaceOrder cmd, CancellationToken ct)   // rich aggregate
{
    var order = Order.Place(cmd.Lines, cmd.CustomerId);                // invariants live here
    db.Orders.Add(order);
    await db.SaveChangesAsync(ct);
    return order.Id;
}

public Task<OrderListItem[]> Handle(ListOrders q, CancellationToken ct) =>  // flat read model
    db.Database.SqlQuery<OrderListItem>(
        $"""
         SELECT o.id, o.status, o.total_minor, c.display_name, s.tracking_code
         FROM orders o JOIN customers c ON c.id = o.customer_id
         LEFT JOIN shipments s ON s.order_id = o.id
         WHERE o.tenant_id = {q.TenantId} ORDER BY o.created_at DESC LIMIT 50
         """).ToArrayAsync(ct);

// Expensive CQRS adds: a separate read store + a projection worker + a rebuild command.

Follow-ups

  • What must exist before you add a separate read store? — A rebuild path that can recreate it from the source of truth, tested; a projection you cannot rebuild is a second master.
  • How do you monitor a projection? — Lag in seconds and a periodic consistency check against the source; both as metrics, both alerted.
  • Does CQRS require event sourcing? — No, and conflating them is the most common misunderstanding: CQRS is about models, event sourcing is about how state is stored.

Common wrong answer

"CQRS means a command database and a query database." That is one deployment of it, and the expensive one. Describing it that way suggests the pattern was adopted from a diagram rather than from a read path that was actually hurting.

principalA team proposes event sourcing for the core domain. Do you approve it?

Answer

Only for a domain where the history is the product — ledgers, trading, insurance policies, anything auditable where "how did we get to this balance" is a business question rather than a debugging one. There the append-only log is not overhead, it is the requirement, and temporal queries and audit come free. Everywhere else I push back, because the costs are permanent and land on people who did not choose them: schema evolution now means versioning every event ever written plus an upcasting layer, since old events are immutable and must still be replayable; deleting personal data conflicts directly with immutability, so GDPR erasure needs crypto-shredding designed in from the start; snapshots become mandatory once aggregates accumulate thousands of events; and every developer who joins must learn a model that most tooling does not understand. My approval conditions are concrete: name the business requirement that plain audit tables cannot meet, show the erasure strategy, show the event versioning strategy, and scope it to the one bounded context that needs it rather than the whole system. If those cannot be answered, the right answer is usually an audit log alongside a conventional model — 90% of the benefit for 10% of the cost.

  • How long may a rebuild take? — Whatever you can tolerate during an incident; measure it at production volume before approving, because "we can always replay" is only true if replay finishes.
  • What is the strongest argument in favour? — Bugs in projections become recoverable: fix the code, rebuild the read model, and the corrected state is derivable — which conventional systems cannot do.

Common wrong answer

"Event sourcing gives you a full audit log for free." Audit is the cheap part and an audit table delivers it. What you actually buy is a different storage model with permanent versioning, erasure and rebuild obligations — and presenting it as free is the tell that those have not been thought through.

08Reliability and failure modes

Every design question eventually becomes "what happens when that breaks", and this is the sub-area where lead and principal candidates are separated most sharply, because the answers come from having been paged rather than from reading. Interviewers look for specific mechanisms — timeouts, budgets, breakers, bulkheads, degradation — and for the judgment to know that partial failure is the normal state of a distributed system. At mid level, put a timeout and a bounded retry on every call; at senior, reason about slow dependencies and cascading failure; at principal, own the incident, the blast radius and the culture that makes both smaller next time.

screenerWhat timeout do you set on that call, and what happens when it fires?

Answer

Every outbound call gets an explicit timeout, derived from the request's latency budget rather than picked from the air, and it must be shorter than the caller's own deadline so the failure surfaces where it can be handled. The default is almost always wrong in the dangerous direction: HttpClient defaults to 100 seconds and a raw SqlConnection command to 30, which means a single slow dependency can pin your entire thread pool and connection pool for a minute and a half while clients have long given up. I set the timeout at roughly the dependency's p99 plus headroom, then decide explicitly what happens when it fires — fail the request, serve a cached or default value, or queue the work — because a timeout with no defined behaviour is just a slower error. At scale the right shape is a deadline propagated down the call chain rather than an independent timeout per hop, so a slow first hop shrinks what later hops may spend and nothing downstream outlives the client.

Example

// .NET 8+: resilience handler; the defaults are sane and explicit
builder.Services.AddHttpClient<PricingClient>(c =>
{
    c.BaseAddress = new Uri("https://pricing.internal/");
    c.Timeout = TimeSpan.FromSeconds(2);              // NOT the 100s default
})
.AddStandardResilienceHandler(o =>
{
    o.AttemptTimeout.Timeout      = TimeSpan.FromSeconds(1);   // per attempt
    o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(3);   // whole operation
});

// Database: set it per command, from the budget, not from the default
cmd.CommandTimeout = 5;   // seconds; a report query gets its own, larger, deliberate value

Follow-ups

  • How do you pick the number? — Measure the dependency's p99 and add margin; a timeout below p99 turns normal slowness into a manufactured error rate.
  • What is deadline propagation? — Passing the remaining budget downstream (gRPC deadlines natively, or a header over HTTP) so hops cannot each restart the clock.
  • Does a timeout cancel the work? — Only if you flow the CancellationToken; otherwise the server keeps working on a response nobody will read, which is wasted capacity during an incident.

Common wrong answer

"We use the defaults, they are reasonable." The HttpClient default of 100 seconds is the reason a slow dependency becomes a total outage: threads and connections accumulate on calls that will never be useful, and the service stops serving anything at all.

screenerDesign the retry policy. When do you not retry?

Answer

Retries are only safe for idempotent operations against transient failures, and both halves matter. Transient means a timeout, a connection reset, a 429, a 503, or a database deadlock — conditions that are likely to succeed on a second attempt. Never retry a 400, a 401, a 403, a 404 or a validation error: the request is wrong and repeating it wastes capacity and confuses metrics. The mechanics are exponential backoff with jitter — full jitter, not a fixed doubling — because synchronised retries from thousands of clients recreate the spike that caused the failure. Attempts should be few, typically three, and bounded by a total budget rather than an attempt count, since three attempts at a two-second timeout can exceed the caller's deadline anyway. The part candidates miss is the retry budget across the fleet: a global cap of about 10% extra traffic, so a struggling dependency is never amplified 3× by its callers at exactly the moment it needs less load.

Example

// Polly v8 / Microsoft.Extensions.Resilience
new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddRetry(new HttpRetryStrategyOptions
    {
        MaxRetryAttempts = 3,
        BackoffType      = DelayBackoffType.Exponential,
        UseJitter        = true,                       // essential, not optional
        Delay            = TimeSpan.FromMilliseconds(200),
        ShouldHandle     = args => ValueTask.FromResult(
            args.Outcome.Result is { StatusCode: HttpStatusCode.RequestTimeout
                                              or HttpStatusCode.TooManyRequests
                                              or >= HttpStatusCode.InternalServerError }
            || args.Outcome.Exception is HttpRequestException or TimeoutRejectedException)
    })
    .Build();
// Do NOT retry: 400, 401, 403, 404, 409, 422 — the request will not become valid.

Follow-ups

  • Why jitter? — Without it, all clients that failed together retry together; the dependency sees a periodic square wave of load and never recovers between pulses.
  • Retry a POST? — Only with an idempotency key; otherwise a timeout you retry is how a customer gets charged twice.
  • Where should retries live? — At one layer only. Retries at the client, the gateway and the service multiply: three layers of three attempts is 27 requests for one call.

Common wrong answer

"Retry three times with a one-second delay." Fixed delays synchronise, and a blanket retry ignores whether the failure was transient at all — so 4xx responses are retried, the error rate looks like a dependency problem, and the actual bug stays hidden.

midWhat do a circuit breaker and a bulkhead do, and where do you put them?

Answer

A circuit breaker stops you from making calls that are almost certainly going to fail: after a failure ratio over a sampling window, it opens, fails fast for a break duration, then allows a trial request (half-open) and closes if it succeeds. The value is twofold — the caller stops wasting its own threads and deadlines on a dead dependency, and the dependency gets a chance to recover instead of being hammered while it restarts. A bulkhead limits how much of your resources any single dependency can consume: a concurrency cap per downstream so that one slow service cannot occupy every thread, connection or slot in the process. They solve different halves of the same problem, which is why the AddStandardResilienceHandler pipeline in .NET includes both plus timeout and retry in a deliberate order. Two configuration details interviewers probe: the breaker should be keyed per dependency (and often per endpoint), not global, and the half-open probe must be a single request, or the reopening moment becomes its own thundering herd.

Example

// The standard pipeline order matters: rate limiter → total timeout → retry
//                                      → circuit breaker → attempt timeout
builder.Services.AddHttpClient<RecommendationClient>()
    .AddStandardResilienceHandler(o =>
    {
        o.CircuitBreaker.FailureRatio      = 0.5;                        // 50% failing
        o.CircuitBreaker.MinimumThroughput = 20;                         // ...of at least 20
        o.CircuitBreaker.SamplingDuration  = TimeSpan.FromSeconds(30);
        o.CircuitBreaker.BreakDuration     = TimeSpan.FromSeconds(15);
        o.RateLimiter.DefaultRateLimiterOptions.PermitLimit = 50;        // bulkhead
    });

// When the breaker is open: return the fallback immediately, do not queue.
// recommendations → static "popular items"; checkout → 503, never a silent fallback.

Follow-ups

  • What does the caller do when the breaker is open? — Whatever you designed: a fallback, a degraded response, or a fast error. An open breaker with no fallback is just a faster failure — which is still better than a slow one.
  • Global breaker or per-host? — Per dependency and per host: one bad instance behind a load balancer should not trip the whole dependency.
  • Do breakers belong in the mesh instead? — They can, and a mesh gives you them uniformly — but application-level breakers know which fallback is correct, which the mesh cannot.

Common wrong answer

"Add a circuit breaker to protect the downstream service." Its primary job is protecting you — your threads, connections and latency budget. Framing it as downstream protection usually comes with a global breaker and no fallback, which converts a partial failure into a total one.

midA non-critical dependency is down. How does the product degrade rather than fail?

Answer

By classifying every dependency as required or optional at design time, and building the optional path before the incident. Optional means there is a defined fallback: the last cached value, a static default, an empty state with an honest message, or a queued deferral so the work happens later. Recommendations fall back to a curated popular list; a personalisation service falls back to the anonymous experience; an address-validation service falls back to accepting the address with a flag for later review. The two rules that make this safe are that fallbacks must be fast — the whole point is to not wait — and that they must be visible, both to the user where it matters and to monitoring always, because a silent fallback that runs for three weeks is how a broken integration goes unnoticed. I also want the degradation to be testable: a feature flag or fault injection that forces the fallback path in staging, since a fallback that has never executed is a hypothesis, not a mitigation.

  • How do you know a fallback is active? — A metric per fallback path with an alert on sustained use; the incident is often "the fallback has been on since Tuesday".
  • Should the user always be told? — When it changes what they can rely on, yes; when it is cosmetic, no. Silence about stale reviews is a small lie that erodes trust.
  • How do you test it? — Fault injection in a pre-production environment and, ideally, a scheduled game day; a fallback path that has never run in anger usually does not compile against reality.

Common wrong answer

"Wrap the call in a try/catch and return an empty list." Without a timeout it does not help at all — you still wait 100 seconds — and without a metric nobody learns the dependency is down. Swallowing the exception converts an outage into silent data loss.

midWhat is your backup and restore story, and what are RTO and RPO here?

Answer

RPO is how much data you can afford to lose, RTO is how long you can afford to be down, and both are business decisions that then dictate the technology. An RPO of five minutes means continuous log shipping or streaming replication, not a nightly dump; an RTO of thirty minutes means the restore must be automated and rehearsed, because restoring a multi-terabyte database from cold object storage takes hours regardless of how good the backup is. So the real content of a good answer is the restore, not the backup: backups that have never been restored are unverified, and the standard failure is discovering during an incident that the backup excluded a schema, or that the encryption key lived only in the environment that is gone. I want point-in-time recovery so a logical disaster — a bad migration, a bad DELETE — is recoverable to the second before it, immutable or write-once copies so ransomware cannot delete them, at least one copy in another region or account, and a scheduled restore drill that measures the actual time to a working system rather than to a restored file.

Example

Tiering by data class (do not apply one policy to everything)
  orders/payments  RPO 0-5 min   RTO 30 min   PITR + cross-region replica, drilled monthly
  user content     RPO 1 h       RTO 4 h      snapshots + object versioning
  derived indexes  RPO n/a       RTO 2 h      rebuild from source; do not back up at all
  analytics        RPO 24 h      RTO 48 h     daily snapshot to archive tier

Restore drill (quarterly, timed, on a schedule someone owns)
  t+0   declare, pick a point in time
  t+8   database restored to a new instance
  t+22  app pointed at it, smoke tests green   ← this is the real RTO, not t+8
  record the number; if it exceeds the promised RTO, the promise is wrong, not the drill

Follow-ups

  • Is a replica a backup? — No. Replication faithfully copies your DELETE FROM orders within milliseconds; only a point-in-time copy protects against logical damage.
  • What is the most common restore failure? — Something outside the database: the key that decrypts the backup, a missing schema or extension, or credentials that only existed in the dead environment.
  • How do backups interact with GDPR erasure? — Document the retention window and the process for re-applying erasures after a restore; "we cannot delete from backups" is only acceptable if it is written down and bounded.

Common wrong answer

"We take nightly backups to blob storage." That is an RPO of up to 24 hours nobody has agreed to, an unmeasured RTO, and — usually — no evidence a restore has ever succeeded. The backup is the easy half; the interviewer is asking about the other one.

seniorA dependency is not down, it is slow. Why is that worse, and what do you do?

Answer

Slow is worse than down because failure is fast and slowness is contagious. When a dependency returns errors immediately, your breaker opens, your fallback runs, and your capacity is unaffected. When it takes eight seconds instead of eighty milliseconds, every in-flight request holds a thread, a connection and a slot in the queue for a hundred times longer, so concurrency — which is throughput times latency — explodes and your service saturates while its CPU sits at 15%. That is why the mitigation is a concurrency limit per dependency rather than only a timeout: the bulkhead caps how much of you the slow dependency can occupy. Alongside it, the breaker must trip on latency, not just on errors — a slow-call ratio threshold — and the timeout must be near the dependency's normal p99, so slow becomes failed quickly and predictably. In .NET specifically I watch thread-pool queue length and the connection-pool wait time, because those two are where "a dependency got slow" turns into "our own service stopped responding to everything".

Example

Little's law makes it concrete
  normal   200 req/s x 0.08 s = 16 concurrent  → fine on a pool of 100
  slow     200 req/s x 8.00 s = 1600 concurrent → pool exhausted, everything queues
                                                  including calls to healthy dependencies

Mitigations, in the order they take effect
  timeout at p99 + margin        turns slow into failed, fast
  bulkhead (concurrency cap 50)  bounds the damage to one dependency
  breaker on slow-call ratio     stops calling it at all for a while
  fallback                       keeps the product usable
  load shed at the edge          protects what is left

Watch: ThreadPool queue length, connection-pool wait p99, in-flight requests per dependency.

Follow-ups

  • Why does thread-pool starvation still happen in modern .NET? — Any synchronous block on async work (.Result, .Wait()) inside a request path; under latency the pool grows only about one thread per second, so recovery is glacial.
  • What metric warns you earliest? — In-flight requests per dependency; latency and error rate both move later.
  • Is a breaker on latency risky? — It can trip during a legitimate slow period; use a slow-call ratio over a window with a minimum throughput, not a single slow call.

Common wrong answer

"The circuit breaker will catch it." Most breakers count failures, and a slow success is not a failure — so without a timeout converting slow into failed, or a slow-call threshold, the breaker never opens and the service saturates with the breaker sitting closed and healthy.

seniorOne service degrades and the whole platform goes down. How do you bound the blast radius?

Answer

Cascading failure happens because everything shares something — a thread pool, a database, a cache, a retry-amplified network — so I design explicit boundaries around each shared resource. Cell-based architecture is the strongest version: partition users or tenants into independent cells, each with its own full stack, so a failure takes out one cell instead of the platform, and deployments roll cell by cell. Short of that, the practical measures are per-dependency bulkheads so one slow call cannot consume the process, per-tenant quotas so one customer cannot exhaust shared capacity, separate connection pools and separate instances for critical versus non-critical paths, and retry budgets to stop callers amplifying the failure threefold. Load shedding at the edge with priority classes is the last resort that keeps checkout alive while recommendations are dropped. The measurable goal is that no single component failure can take more than a defined fraction of users offline, and the way to know is fault injection: kill a dependency in production-like conditions and observe how far the damage travels.

Example

Blast-radius controls, from cheapest to strongest

  bulkheads          per-dependency concurrency caps (one slow dep ≠ whole process)
  pool separation    critical paths get their own instances and connection pool
  retry budget       fleet-wide cap ~10% of primary traffic
  per-tenant quota   noisy neighbour cannot exhaust shared capacity
  priority shedding  checkout > browse > recommendations, decided in advance
  cells              tenants 1-1000 → cell A (own db, cache, app); 1001-2000 → cell B
                     blast radius = 1/N users; deploys roll cell by cell

Verify by injection, not by argument: kill the reviews service in staging at peak load
and measure how many endpoints degrade. The answer is usually more than expected.

Follow-ups

  • What is the cost of cells? — Operational multiplication: N of everything to deploy, monitor and migrate, plus a routing layer and a story for cross-cell features like global search.
  • How do retries cause cascades? — Amplification: each layer retrying three times turns one request into 27, so a service recovering from a blip is hit with far more load than caused the blip.
  • What single change helps most in a shared monolith? — Separating the critical path onto its own instances: a reporting query storm then cannot take checkout with it.

Common wrong answer

"Microservices contain failures because each one is isolated." Only if the boundaries carry bulkheads, timeouts and fallbacks. Without them a synchronous chain of services is less resilient than a monolith: the availability of a serial chain is the product of its parts, and now the network can fail between every pair.

principalYou are the incident commander at 03:00 and nobody knows what is wrong. What do you do?

Answer

I separate the roles first, because the most common failure at 03:00 is five engineers debugging in parallel with nobody communicating. I take incident command explicitly and stop doing hands-on work: I assign one operations lead who makes changes, a communications lead who updates the status page and stakeholders on a fixed cadence, and a scribe who timestamps every action in the channel. Then mitigation before diagnosis — the goal is restoring service, not understanding it, so the first questions are what changed recently and can it be reverted, and the default action is to roll back the most recent deploy or flip the feature flag even without proof of causation. One change at a time, announced before it is made, with the effect observed, because parallel unverified changes make the system unanalysable. I set a decision deadline for escalation ("if not improving in twenty minutes, we fail over to the secondary region") so there is no drift, and I rotate people out before fatigue makes it worse. Afterwards the postmortem is blameless and produces a small number of owned, dated actions — and I check that those actions actually shipped, because the surest sign of a weak engineering culture is a folder of postmortems whose action items were never done.

Example

First 10 minutes
  0-2  declare; open a channel; state severity and user impact in one sentence
  2-4  assign roles: command (me, not typing), ops lead, comms, scribe
  4-6  "what changed?" — deploys, flags, config, certs, dependency status pages
  6-10 mitigate: roll back / flip the flag / fail over. One change at a time, announced.

Discipline
  no parallel unverified changes         (otherwise nothing is attributable)
  comms every 20 min even with no news   (silence is filled with worse guesses)
  a decision deadline per hypothesis     (prevents 3 hours on a favourite theory)
  rotate the ops lead at 90 minutes

After: blameless postmortem within 5 working days
  timeline · contributing factors (plural) · what made detection or recovery slow
  3-5 actions with a named owner and a date; reviewed at the next ops meeting
  the ONE metric worth tracking: percentage of postmortem actions completed on time

Follow-ups

  • Why should the commander not debug? — Attention is the scarce resource: someone must hold the timeline, the comms and the escalation decision, and that cannot be the person deep in a stack trace.
  • What if a rollback is not possible? — That is a finding for the postmortem in itself; in the moment, disable the feature, shed the traffic, or degrade — and note that irreversible deploys are a reliability defect.
  • How do you keep a postmortem blameless without losing accountability? — Blame the conditions, own the actions: name the missing guardrail rather than the person who hit it, and put a name and a date on every fix.

Common wrong answer

"We find the root cause and fix it properly." At 03:00 that is the wrong objective and often the wrong noun — complex outages have contributing factors, not a single root cause. Diagnosing before mitigating extends the outage while you build understanding you could have built from logs afterwards.

09.NET application architecture at scale

This is where a .NET system design loop diverges from a generic one: the interviewer stops asking about boxes and starts asking how the service is actually built, hosted and operated. The questions are about structure, dependency lifetimes, configuration, background work and runtime behaviour — the things that decide whether a service survives its second year. At mid level, structure a solution and get DI lifetimes right; at senior, reason about hosting, startup, GC and the thread pool under load; at principal, make one architecture repeatable across many teams without becoming a bottleneck yourself.

screenerHow do you structure the solution — layers, clean architecture, or vertical slices?

Answer

I organise by feature first and by layer second, because the unit of change is a feature and the unit of a classic layered solution is a technology. In practice that means a folder or module per capability — Orders, Catalogue, Billing — each containing its endpoints, handlers, domain types and data access, with a shared kernel for genuinely cross-cutting concerns. That is the vertical-slice idea, and its practical benefit is that a change touches one directory instead of five projects. I keep the one rule from clean architecture that actually pays: the domain does not reference infrastructure, so business rules can be tested without a database or a broker. What I avoid is the ceremonial version — a repository interface per entity that wraps DbContext, which is already a repository and a unit of work, plus an application service that only forwards calls. At scale the boundary that matters is the module, enforced mechanically: no module reads another module's tables, and cross-module calls go through a published interface, so the extraction into a separate service later is a deployment change rather than a rewrite.

Example

src/
  Shop.Api/                      host: DI, middleware, endpoint registration only
  Modules/
    Orders/
      Endpoints/PlaceOrder.cs    endpoint + request/response + validation
      Domain/Order.cs            invariants; no EF, no HttpClient
      Data/OrdersDbContext.cs    owns the "orders" schema, nothing else touches it
      Contracts/OrderPlaced.cs   the published event — a contract, versioned
      OrdersModule.cs            AddOrders(IServiceCollection) / MapOrders(IEndpointRouteBuilder)
    Catalogue/  ...
  Shared/Kernel/                 Result, Money, clock, correlation — small and boring

Rules enforced in CI (an architecture test, not a wiki page)
  Domain must not reference Microsoft.EntityFrameworkCore or System.Net.Http
  Modules.* must not reference another module's Data or Domain namespaces

Follow-ups

  • One DbContext or one per module? — One per module, each owning its tables; it makes the boundary real and makes a later split possible without untangling a shared context.
  • Do you use MediatR? — Only where the indirection earns something (pipeline behaviours for validation, logging, transactions). Since its move to a commercial licence many teams use a small in-house dispatcher or call handlers directly — either is defensible.
  • How do you stop the structure eroding? — Architecture tests in the build (NetArchTest or equivalent); conventions that are not enforced decay within two quarters.

Common wrong answer

"Api, Application, Domain, Infrastructure — four projects, clean architecture." It is not wrong, it is unexamined: the layered split optimises for swapping a database nobody ever swaps, while every feature change still touches four projects. Interviewers want the trade-off, not the diagram.

screenerSingleton, scoped or transient — and what is a captive dependency?

Answer

Singleton is one instance for the process lifetime, scoped is one per request (or per explicitly created scope), transient is a new one every time it is resolved. The rule that matters is that a service may only depend on something with an equal or longer lifetime: a singleton holding a scoped dependency captures it, so the same DbContext is reused for the life of the process by every request — which means a change tracker that never resets, concurrent use of a non-thread-safe object, and a connection that is never returned. That is the captive-dependency bug, and .NET's default container catches the common shape at startup when scope validation is on, which it is in Development. The way out when a singleton genuinely needs scoped work is to inject IServiceScopeFactory and create a scope per unit of work — which is exactly what a BackgroundService must do, since it is a singleton and has no ambient request scope. In a system design context this matters because the symptom appears only under concurrency: it passes every test and fails in production.

Example

// WRONG: singleton captures a scoped DbContext
public sealed class OrderCache(AppDbContext db) { }        // registered as singleton
builder.Services.AddSingleton<OrderCache>();               // ← throws at startup in Dev

// RIGHT: create a scope per unit of work
public sealed class OrderSyncWorker(IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using var scope = scopes.CreateScope();                       // fresh scope
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            await ProcessBatchAsync(db, ct);
            await Task.Delay(TimeSpan.FromSeconds(5), ct);
        }
    }
}
// builder.Host.UseDefaultServiceProvider(o => { o.ValidateScopes = true;
//                                               o.ValidateOnBuild = true; }); in ALL envs

Follow-ups

  • Why is HttpClient the classic counter-example? — Injected directly it is transient-looking but holds sockets; IHttpClientFactory pools handlers with a rotation lifetime, solving both socket exhaustion and stale DNS.
  • Is transient ever wrong? — When the object is expensive or holds a connection; transient means "cheap to create and safe to discard", not "safest default".
  • How do you catch this before production? — Turn on ValidateOnBuild and ValidateScopes in every environment, not just Development; the startup failure is far cheaper than the incident.

Common wrong answer

"Register everything as singleton for performance." Object allocation is not the bottleneck in a web service, and singletons carry thread-safety obligations most classes do not meet. It is also how a captured DbContext ends up serving every request in the process.

midHow does configuration and secret management work across dev, staging and production?

Answer

One configuration model, layered sources, no secrets in the repository. The layers go from least to most specific — appsettings.json for defaults, appsettings.{Environment}.json for per-environment differences, environment variables for anything the platform injects, and a secret store for credentials — with later sources overriding earlier ones. Locally that is user-secrets; in production it is Key Vault, AWS Secrets Manager or the platform's own mechanism, mounted or fetched at startup, with rotation supported. I bind configuration to strongly typed options with IOptions<T> and validate them at startup with ValidateOnStart, because a service that fails to boot with a clear message about a missing connection string is enormously better than one that starts and fails on the first request at 2am. Two details worth stating: use IOptionsMonitor<T> only where you actually want live reload, and never log the configuration object, because that is how connection strings end up in a log aggregator that half the company can read.

Example

builder.Services.AddOptions<PricingOptions>()
    .Bind(builder.Configuration.GetSection("Pricing"))
    .ValidateDataAnnotations()
    .Validate(o => o.TimeoutMs is > 0 and <= 10_000, "Pricing:TimeoutMs must be 1..10000")
    .ValidateOnStart();                       // fail at boot, not at first request

// Source order (last wins): appsettings.json → appsettings.{Env}.json
//                           → user-secrets (Dev) / Key Vault (Prod) → env vars
if (!builder.Environment.IsDevelopment())
    builder.Configuration.AddAzureKeyVault(vaultUri, new DefaultAzureCredential());

Follow-ups

  • Config change without a redeploy? — Use a feature-flag service for behaviour that must change at runtime; hot-reloading arbitrary configuration makes the running state untraceable.
  • How do you rotate a secret with zero downtime? — Support two valid credentials at once, roll the new one in, then retire the old; rotation that requires a restart is rotation nobody performs.
  • Where do feature flags belong? — Outside appsettings: a flag service with targeting and an audit trail, so a flag flip during an incident is one action, logged.

Common wrong answer

"Connection strings go in appsettings.Production.json, which is not committed." Not-committed files drift, get pasted into chat, and live on someone's laptop. The failure mode is not theoretical: the file is eventually committed by accident, and the credential is then in git history forever.

midWhere does background work run — and why not just fire and forget inside the request?

Answer

Because Task.Run inside a request has no durability, no retry and no observability: if the process recycles — a deploy, a scale-in, a crash — the work simply vanishes, and nothing recorded that it was owed. The options in ascending order of guarantee are: BackgroundService in the same process for work that is cheap to redo and tolerant of loss; a queue plus a separate consumer for anything that must survive a restart; and a durable scheduler or workflow engine for anything with retries, delays and multi-step state. For in-process work I also need graceful shutdown to be right — honour the stopping token, and configure HostOptions.ShutdownTimeout to be longer than the longest unit of work, or Kubernetes will terminate mid-batch. The other thing interviewers probe is scheduling in a scaled-out deployment: five instances each running a BackgroundService timer means the nightly job runs five times, so it needs a leader election, a distributed lease, or — usually simplest — to be idempotent so duplicate runs do not matter.

Example

Warm a cache, flush metricsBackgroundServiceno — and that is fine
Send the confirmation emailoutbox → queue → consumeryes
Generate a 5-minute reportqueue + worker, status on the resourceyes
Nightly reconciliationscheduler + lease, or idempotent jobyes, runs once
Multi-step with timeoutssaga / durable workflowyes, resumable
_ = Task.Run(...) in a controller—no. Never do this.

Follow-ups

  • What is the risk of a long ShutdownTimeout? — Slow deploys and slow scale-in; size it to the real unit of work and make units small enough to finish inside it.
  • How do you observe background work? — Same telemetry as requests: a span per unit, a duration histogram, a failure counter, and a queue-age gauge. Invisible workers are how backlogs grow for a week.
  • Web app and worker in one process? — Convenient and common, but it couples scaling and blast radius; split them once the worker's load or failure profile diverges.

Common wrong answer

"Fire and forget with Task.Run, the request returns faster." It does, and roughly one unit of work per deploy is lost silently, with no error, no metric, and no way to identify which customers were affected. Worse, an unobserved exception in that task takes the process down in some hosting configurations.

midWhat problem does Aspire solve, and would you use it in production?

Answer

Aspire — renamed from .NET Aspire with 13.0 in November 2025, and at 13.4 as of mid-2026 — is an orchestration and composition model for multi-service applications. Its app host describes the whole system in C# (or now TypeScript): services, their dependencies, the Postgres and Redis containers they need, the connection strings wired between them. Locally it starts everything with one command and gives you a dashboard with logs, traces and metrics across all of it, which removes the usual "seven terminals and a docker-compose file nobody understands" problem. Its integrations also configure the boring things consistently: OpenTelemetry, health checks, resilience handlers and service discovery, so every service gets them without each team reinventing them. In production the honest framing is that Aspire is a development-time orchestrator and a deployment generator: it publishes manifests — Kubernetes, Azure Container Apps — that your existing pipeline deploys, rather than running your production cluster itself. So my answer is yes for local development and for generating deployment artefacts, with the production runtime remaining Kubernetes or a managed container platform.

"Aspire is just docker-compose for .NET." The composition overlap is real, but the point is the integration layer — telemetry, health, resilience and service discovery configured identically everywhere — plus a deployment manifest that stays in sync with the code that describes it.

seniorMinimal APIs or controllers, and does Native AOT change the answer?

Answer

Minimal APIs are my default for new services: less ceremony, better fit with vertical slices, lower per-request overhead, and since .NET 10 they have the last thing they were missing — built-in validation with DataAnnotations, AOT-compatible and routed through IProblemDetailsService so error shapes stay consistent. Controllers remain the right choice when you rely on what MVC provides — model binding conventions, filters, views, or a large existing surface — and "we already have 300 controllers" is a perfectly good reason not to migrate. Native AOT is a separate decision driven by startup time and memory rather than throughput: it removes JIT warm-up, so cold start drops from hundreds of milliseconds to tens, and memory footprint falls substantially, which matters for serverless, scale-to-zero and very dense deployments. The cost is real: no runtime reflection or dynamic code, so EF Core's traditional query pipeline, some serialisation and many libraries do not work, and you must use source-generated JSON. So the honest split is minimal APIs almost always, AOT only where cold start or density is the actual constraint.

Example

// .NET 10: validation is built in for minimal APIs — no MVC, no manual checks
builder.Services.AddValidation();

app.MapPost("/api/v1/orders", (CreateOrder cmd, IOrderService svc) => svc.PlaceAsync(cmd));

public sealed record CreateOrder(
    [property: Required] string CustomerId,
    [property: Range(1, 100)] int Quantity);
// invalid → 400 with ProblemDetails, shaped by IProblemDetailsService

// AOT-friendly serialisation (required under PublishAot)
[JsonSerializable(typeof(CreateOrder))]
[JsonSerializable(typeof(OrderCreated))]
internal partial class ApiJsonContext : JsonSerializerContext { }

Follow-ups

  • When is cold start worth optimising? — Scale-to-zero, per-request billing, and rapid autoscaling where new instances must serve immediately; a long-running service that starts twice a week gains nothing.
  • Does AOT improve throughput? — Usually not much and sometimes slightly less, because the JIT's tiered and dynamic PGO optimisation is unavailable. Startup and memory are the wins.
  • Can you use EF Core with AOT? — With significant constraints; for AOT services a lighter data layer (Dapper, or compiled queries where supported) is the usual pragmatic answer.

Common wrong answer

"Minimal APIs are for small projects; real applications use controllers." Size is not the axis. The differences are ceremony, filter/binding conventions and AOT compatibility — and since .NET 10's validation support the main functional gap that motivated that opinion is gone.

seniorYour service is at 100% CPU with normal traffic. How do you diagnose it in .NET?

Answer

I collect evidence before touching anything, because the three usual causes look identical from a dashboard and have opposite fixes. First, counters: dotnet-counters for GC pause percentage, allocation rate, gen-2 collections, thread-pool queue length and lock contention. High time-in-GC with a high allocation rate points to allocation pressure — large object heap traffic, string concatenation, unnecessary materialisation of query results — and the fix is in the code, not the configuration. A growing thread-pool queue with low CPU points to starvation from synchronous blocking on async work, which is a different problem entirely and gets worse when you scale up. Genuinely CPU-bound work shows as a hot stack, so a dotnet-trace or continuous profiler sample identifies it in minutes. The configuration items worth checking are server GC (which should be on for a server workload and off for dense containers where per-container heaps multiply), whether the container's CPU limit is visible to the runtime, and whether tiered compilation is still warming up after a restart. What I do not do is guess and restart, because a restart resets the evidence and the problem returns an hour later.

Example

dotnet-counters monitor -p 1 System.Runtime Microsoft.AspNetCore.Hosting

  % Time in GC                    38%     ← allocation pressure, not "needs more CPU"
  Allocation Rate                 1.2 GB/s
  Gen 2 GC Count                  14/min  ← promotion; look for LOH / large buffers
  ThreadPool Queue Length         0        (starvation would show a growing queue)
  Monitor Lock Contention Count   90k/s   ← a hot lock; find it with dotnet-trace

Then:  dotnet-trace collect -p 1 --profile cpu-sampling   → open in a profiler
Common causes, in the order they actually occur
  1 per-request allocation in a hot path (LINQ over large sets, string building)
  2 sync-over-async (.Result / .Wait()) → thread-pool starvation, CPU looks busy
  3 serialisation of large payloads (fix the payload, not the serialiser)
  4 workstation GC in a container with many cores, or a CPU limit the runtime cannot see

Follow-ups

  • Server GC or workstation GC? — Server GC for throughput on a dedicated instance; in small containers it allocates per-core heaps and can waste memory, so measure rather than assume.
  • What tells you it is starvation rather than CPU? — Thread-pool queue length rising while CPU is moderate, and latency that improves when you remove a blocking call, not when you add instances.
  • How do you find allocations in production? — A continuous profiler, or dotnet-gcdump for a heap snapshot; both are safe enough to run under load if used briefly.

Common wrong answer

"Scale out — add more instances." It sometimes masks the symptom and it is the wrong instinct when the cause is allocation pressure or starvation: more instances means more heaps and more database connections, and the per-request cost that caused the problem is unchanged.

principalFifteen teams, fifteen slightly different .NET services. How do you get consistency without becoming the bottleneck?

Answer

By making the consistent thing the easiest thing, and by putting almost nothing in a document. Concretely: a service template that generates a new service with telemetry, health checks, resilience, authentication, structured logging and a deployment pipeline already wired; a small set of shared packages that provide those defaults with sane configuration; and CI checks that enforce the handful of rules that genuinely matter — correlation propagation, no secrets in code, contract compatibility — rather than a style guide nobody reads. Aspire's ServiceDefaults is a good example of the shape: one project every service references, so a change to the observability setup ships to everyone through a package bump. The organisational half is a golden path rather than a mandate: teams may deviate, but the deviation costs them work and must be recorded as a decision, which keeps the exception rate low without an architecture-review queue. I also keep a deliberately small architecture group that reviews decisions asynchronously through ADRs and spends most of its effort on the template and the tooling, because a review board that approves designs becomes the bottleneck the question is about. The measure of success is that a new service reaches production in days and looks like every other one without anyone having asked me.

          current ServiceDefaults version (adoption is the real measure of the platform)

Follow-ups

  • How do you get teams to upgrade the shared package? — Make upgrades cheap and boring (semantic versioning, no behavioural surprises), automate the PR with a dependency bot, and publish an adoption dashboard.
  • What belongs in a shared library versus the template? — Cross-cutting behaviour that must be identical goes in the library; anything a team will legitimately change goes in the template, where they own the copy.
  • When is deviation right? — When the service has a genuinely different profile — an AOT-compiled edge function, a data-heavy worker — and the ADR says so; the failure mode is silent divergence, not divergence.

Common wrong answer

"We publish architecture standards and review every design." Documents do not change behaviour and a review queue makes you the bottleneck you were asked to avoid. Consistency comes from templates, shared defaults and CI gates — the paths of least resistance — not from approval.

10Frontend architecture and delivery

A full-stack loop will spend real time here, and it is where back-end-leaning candidates lose points by treating the browser as a thin client. What is tested is whether you can reason about rendering strategy, the network between the browser and your API, authentication that is actually safe in a browser, and the performance budget a real user experiences on a mid-range phone. At mid level, choose a rendering strategy and design the client-server contract; at senior, own auth, caching and real-time transport decisions; at principal, judge whether organisational structure justifies splitting the front end at all.

screenerServer-rendered, client-rendered or static — how do you choose for this product?

Answer

I choose per route, not per application, because the same product usually wants all three. Static generation for content that is the same for everyone and changes rarely — marketing pages, documentation — served from a CDN with near-zero latency. Server rendering for pages where first paint and SEO matter and the data is per-request: product pages, search results, anything a crawler or a slow phone must see quickly. Client rendering for authenticated, interaction-heavy application shells where SEO is irrelevant and the user pays the JavaScript cost once, then navigates instantly. Modern React frameworks blur the line deliberately — React Server Components let one route render mostly on the server and ship only the interactive islands, which is the current default posture in Next.js 16 with its Cache Components model. The trade-off I state unprompted is that server rendering moves cost from the user's device to your servers and adds a hydration step whose cost people forget: a fast first paint followed by three seconds of unresponsive page is worse than an honest spinner.

Follow-ups

  • What does hydration actually cost? — The browser re-runs component code to attach handlers; on a mid-range phone that can be seconds, which is why islands and server components exist.
  • Does SSR help Core Web Vitals automatically? — It helps LCP and often hurts INP if the JavaScript payload is unchanged; the win comes from shipping less client code, not from rendering location alone.
  • What about Blazor in a .NET shop? — Blazor Server gives a tiny download at the cost of a persistent circuit and latency-sensitive interactions; Blazor WebAssembly moves that to a large initial download. Both are defensible; say which constraint decided it.

Common wrong answer

"SSR, because it is faster." It is faster to first paint and slower to interactive if the bundle is unchanged, and it converts a static asset served from an edge cache into a compute cost per request. Naming which metric improves is the whole answer.

screenerWhy put a backend-for-frontend between the browser and your services?

Answer

Because the browser's needs are different from a service's, and pushing that difference into the front end produces chatty, fragile clients. A BFF aggregates several internal calls into one response shaped for a screen, so the browser makes one request over a high-latency mobile connection instead of six sequential ones; it trims the payload to what the view needs; it holds the tokens so the browser never does; and it lets internal services evolve without every change becoming a client release. The cost is a component to own and the temptation to let it grow business logic, which it must not — a BFF orchestrates and shapes, it does not decide. In a .NET shop it is normally a small ASP.NET Core service per client type (web, mobile), owned by the team that owns that client, and it pairs naturally with the token-handling story: the BFF exchanges the session cookie for internal credentials, keeping access tokens entirely out of the browser.

Without a BFF (mobile, 150 ms RTT)

  GET /api/shipments?order=   150 ms

Follow-ups

  • Is a BFF not just an API gateway? — A gateway is generic (routing, auth, rate limits, one for everyone); a BFF is client-specific and shapes responses. Most systems have both.
  • Does GraphQL remove the need for one? — It solves the shaping problem and not the token-custody or aggregation-policy problem; many teams run GraphQL as the BFF.
  • What happens when the BFF grows logic? — Two sources of truth for the same rule, discovered when web and mobile behave differently. Guard it in review; it is the main failure mode.

Common wrong answer

"It adds an unnecessary hop — let the client call the services directly." Direct calls put internal service topology, token custody and aggregation policy in the browser, where you can neither change nor secure them; the extra in-datacentre hop costs single-digit milliseconds against hundreds saved on the client's network.

midHow does authentication work for a SPA — where do the tokens live?

Answer

Not in localStorage. The current recommended pattern is the BFF, sometimes called token-mediating backend: the browser holds only an HttpOnly, Secure, SameSite=Lax session cookie, the OAuth authorisation-code flow with PKCE happens between the BFF and the identity provider, and the access and refresh tokens stay server-side. The browser can then never leak a token to a cross-site script, because JavaScript cannot read the cookie at all, and CSRF is handled with SameSite plus an anti-forgery token on state-changing requests. The alternative — a public SPA client doing PKCE itself and storing tokens in memory — is acceptable when there is no backend to host the session, but any XSS on the page can exfiltrate the token, and refresh tokens in a browser are a standing risk that rotation only partially mitigates. Whichever you choose, access tokens are short-lived (5–15 minutes), refresh happens silently, and revocation goes through the refresh path. The implicit flow is dead: it was deprecated in the OAuth 2.0 security best current practice and should never appear in a 2026 design.

Example

// BFF pattern in ASP.NET Core: cookie for the browser, tokens server-side
builder.Services.AddAuthentication(o =>
{
    o.DefaultScheme          = CookieAuthenticationDefaults.AuthenticationScheme;
    o.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;
})
.AddCookie(o =>
{
    o.Cookie.HttpOnly     = true;                       // JS cannot read it
    o.Cookie.SecurePolicy = CookieSecurePolicy.Always;
    o.Cookie.SameSite     = SameSiteMode.Lax;
    o.ExpireTimeSpan      = TimeSpan.FromHours(8);
    o.SlidingExpiration   = true;
})
.AddOpenIdConnect(o =>
{
    o.ResponseType = "code";                            // authorisation code + PKCE
    o.UsePkce = true;
    o.SaveTokens = true;                                // stored server-side, not sent to the browser
    o.Scope.Add("offline_access");
});

Follow-ups

  • Does HttpOnly stop XSS? — No: it stops token theft. An attacker with script execution can still act as the user through the API, which is why CSP and output encoding remain essential.
  • What about CSRF with a cookie? — SameSite=Lax covers most of it; add an anti-forgery token for state-changing requests and never rely on SameSite=None without a reason.
  • How do you sign out everywhere? — Server-side session invalidation plus refresh-token revocation; with browser-held JWTs you cannot, which is itself an argument for the BFF.

Common wrong answer

"Store the JWT in localStorage and send it in an Authorization header." It is still the most common SPA implementation and it means any injected script — including from a compromised npm dependency — can read the token and use it from anywhere until it expires.

midThe page is slow on a mid-range phone. What do you measure and what do you fix?

Answer

I measure field data first, because lab numbers on a developer laptop are systematically optimistic: real-user monitoring of the Core Web Vitals — LCP, INP, CLS — at p75, segmented by device class and connection. Then I attack in order of impact. LCP is usually an image or a font: serve modern formats, size them correctly, preload the hero, and avoid render-blocking. INP — which replaced FID as the responsiveness metric in 2024 — is almost always too much JavaScript on the main thread, so the fixes are code splitting per route, removing heavy dependencies (a date library and a full icon set can be a third of a bundle), and deferring anything not needed for the first interaction. CLS is layout shift from images without dimensions, injected banners and late-loading fonts. Then I make it stick with a performance budget enforced in CI — a maximum bundle size per route that fails the build — because performance work without a ratchet regresses within two releases. The systems-level point worth making is that third-party scripts are frequently the largest single cost and the one engineering does not control, so governing them is part of the architecture.

Example

  initial JS per route     ≤ 170 KB gzipped
  LCP image                ≤ 150 KB, AVIF/WebP, width-appropriate, preloaded
  third-party scripts      ≤ 2, loaded after interactive, each with an owner
  fonts                    ≤ 2 families, self-hosted, font-display: swap

Follow-ups

  • Why p75 rather than the average? — It is the threshold Core Web Vitals is assessed on and it represents the slow quarter of your users, who are the ones abandoning.
  • Lab or field data? — Both: field to know what users experience, lab (Lighthouse in CI) to catch regressions before they ship.
  • What does the back end contribute? — TTFB: a slow API delays everything downstream, so server-side latency budgets and edge caching are frontend performance work too.

Common wrong answer

"Lighthouse gives us 95, so performance is fine." Lighthouse is a simulated run on one page from one location with a throttled profile; it misses the slow devices, the cold cache, the ad script that loads only in production and the route your users actually land on.

midThe UI must show live updates. Polling, SSE or WebSocket?

Answer

I pick the cheapest transport that meets the freshness requirement, and I ask for that requirement in seconds before choosing. Polling is underrated: for freshness of thirty seconds or more with modest client counts it is stateless, cache-friendly, survives any proxy, and costs nothing to operate — and conditional requests with ETags make most polls a cheap 304. Server-sent events are the right middle: one-way server push over ordinary HTTP with automatic reconnection and last-event-id resumption, no special infrastructure, and now first-class in ASP.NET Core 10 via TypedResults.ServerSentEvents. WebSockets are for genuinely bidirectional, high-frequency interaction — collaborative editing, trading, chat with typing indicators — and they cost you a stateful connection per client, which changes load balancing, deployment (every deploy disconnects everyone) and scale-out, since a message must reach whichever instance holds that client's socket. In .NET that last problem is what SignalR's backplane solves, and it is the detail interviewers probe: without Redis or a similar backplane, a scaled-out SignalR app silently drops messages to clients on other instances.

Example

// ASP.NET Core 10: server-sent events, no library, no WebSocket
app.MapGet("/api/orders/{id}/events", (Guid id, IOrderEvents events, CancellationToken ct) =>
    TypedResults.ServerSentEvents(events.StreamAsync(id, ct), eventType: "order-status"));

// Scaled-out SignalR needs a backplane, or messages never leave the origin instance
builder.Services.AddSignalR().AddStackExchangeRedis(redisConnection);

Choosing quickly. Freshness ≥ 30 s and one-way → poll with ETags. Seconds, one-way, many clients → SSE. Sub-second and bidirectional → WebSocket/SignalR, and budget for the backplane, sticky routing and reconnect storms after every deploy.

Follow-ups

  • What is a reconnect storm? — Every client reconnecting simultaneously after a deploy or a network blip; without jittered backoff on the client it is a self-inflicted DDoS at exactly the wrong moment.
  • Do SSE connections have limits? — Over HTTP/1.1 browsers cap connections per origin (about six), which SSE consumes; over HTTP/2 multiplexing removes the problem.
  • How do you scale a million connections? — Dedicated connection-holding instances separate from request-serving ones, plus a backplane or a managed service, so a deploy of the API does not drop every socket.

Common wrong answer

"WebSockets, because they are real-time and efficient." Efficiency per message is real; what it hides is the operational cost of stateful connections — sticky routing, a backplane, disconnects on every deploy, and reconnect storms — bought for a feature that a 15-second poll would have satisfied.

seniorHow do you manage server state in the client, and what does optimistic UI require?

Answer

I separate server state from client state, because conflating them is the root of most front-end complexity. Server state is a cache of something you do not own — it can be stale, it needs revalidation, deduplication, retries and invalidation — and it belongs in a query library (TanStack Query, RTK Query, or a framework's own data layer), not in a global store that someone hand-synchronises. Client state is genuinely local — form drafts, which panel is open, the current filter — and stays in component or URL state, with the URL preferred for anything shareable or restorable. Optimistic UI sits on top: apply the expected result immediately, keep the previous value, and reconcile when the server answers — which means you must design the rollback, including what the user sees when the write is rejected, and you must make the mutation idempotent so a retry after a timeout cannot double-apply. The rule I hold is that optimistic updates are for actions that essentially always succeed and are cheap to reverse — a like, a rename, a reorder — and never for a payment, where a hopeful UI that then reverses is worse than a two-second spinner.

Example

// TanStack Query: optimistic update with an explicit rollback path
useMutation({
  mutationFn: (title) => api.rename(docId, title, { idempotencyKey }),
  onMutate: async (title) => {
    await qc.cancelQueries({ queryKey: ['doc', docId] });     // stop in-flight refetches
    const previous = qc.getQueryData(['doc', docId]);          // keep it for rollback
    qc.setQueryData(['doc', docId], (d) => ({ ...d, title })); // apply immediately
    return { previous };
  },
  onError: (_err, _vars, ctx) => {
    qc.setQueryData(['doc', docId], ctx.previous);             // roll back
    toast.error('Rename failed — restored the previous title');
  },
  onSettled: () => qc.invalidateQueries({ queryKey: ['doc', docId] }), // server wins
});

Follow-ups

  • Why not put server data in Redux? — You then own caching, invalidation, deduplication and retries by hand; that is the library's whole job and it is more subtle than it looks.
  • What belongs in the URL? — Anything a user might share, bookmark or reach with the back button: filters, pagination, the selected tab. It is free state persistence.
  • How do you avoid an over-fetching waterfall? — Prefetch on hover or on route entry, and let the server component or BFF return the whole screen's data in one round trip.

Common wrong answer

"Keep everything in a global store as the single source of truth." The server is the source of truth; a global mirror of it means every mutation needs hand-written invalidation, and the bugs are the ones where two screens show different values for the same entity.

seniorShould the front end be split into micro-frontends?

Answer

Only for an organisational reason, and only when the seams are genuinely independent. The legitimate case is several teams that must release independently into one product surface — a large portal where checkout, catalogue and account are owned by different groups with different cadences — and where a shared release train has become a measurable bottleneck. The costs are heavier than the back-end equivalent because everything ships to one browser: duplicated framework code unless you share it (and sharing it recouples the versions), a shared design system that must be versioned carefully, cross-fragment routing and state, a performance budget that is now everyone's and no one's, and a much harder debugging story. The route-level split — each team owns whole pages, composed at the edge or by the router — captures most of the independence with a fraction of the complexity, and it is what I recommend first. Composing several teams' fragments inside a single page is the version that needs Module Federation or web components and a real platform team behind it. If there is one team, the answer is no: micro-frontends solve a coordination problem you do not have.

11Observability and production operations

Interviewers reach this sub-area when they want to know whether you have operated what you designed. The tell is specificity: naming the three or four metrics you would put on the wall, the alert you would actually page on, and how you follow one user's request across an asynchronous hop. At mid level, instrument properly and correlate; at senior, design alerting that does not train people to ignore it, and control telemetry cost; at principal, define what "healthy" means from the user's side and make that the thing the organisation watches.

screenerWhat do you instrument, and what goes in logs versus metrics versus traces?

Answer

Metrics answer "is it healthy and how much", cheaply and continuously: request rate, error rate, duration histograms, saturation of every pool and queue. Traces answer "where did this one request spend its time" across services, which is the only practical way to debug latency in a distributed system. Logs answer "what exactly happened in this case", with the detail metrics cannot afford to keep. The mistake is using one for another's job — deriving rates by counting log lines is expensive and slow, and putting a stack trace in a metric label is impossible. In .NET this is now largely built in: Microsoft.Extensions.Telemetry and the ASP.NET Core, HttpClient and EF Core instrumentation emit OpenTelemetry-compliant metrics and activities out of the box, with the HTTP conventions declared stable, so most of the work is exporting them and adding domain-specific instruments. What I add by hand is business telemetry — orders placed, payments failed, queue age — because that is what tells you the product is broken when every technical metric looks fine.

Example

builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService("shop-api", serviceVersion: BuildInfo.Version))
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()          // http.server.request.duration (stable)
        .AddHttpClientInstrumentation()          // http.client.request.duration
        .AddRuntimeInstrumentation()             // GC, thread pool, exceptions
        .AddMeter("Shop.Orders")                 // your own
        .AddOtlpExporter())
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation()
        .AddOtlpExporter());

// Business instruments: what tells you the PRODUCT is broken
static readonly Meter Meter = new("Shop.Orders");
static readonly Counter<long> Placed = Meter.CreateCounter<long>("orders.placed");
static readonly Histogram<double> Value = Meter.CreateHistogram<double>("orders.value.eur");

Follow-ups

  • What are the four signals to start from? — Latency, traffic, errors, saturation (the golden signals); RED for services, USE for resources — pick one vocabulary and use it consistently.
  • Why OpenTelemetry rather than a vendor SDK? — One instrumentation, swappable backends, and the semantic conventions mean dashboards and alerts port between vendors.
  • What is the one metric people forget? — Saturation: queue depth, pool utilisation, thread-pool queue length. Latency and errors tell you it already broke; saturation tells you it is about to.

Common wrong answer

"We log everything and search it when there is a problem." Log search is a debugging tool, not a monitoring system: it is too slow and too expensive to alert on, and "everything" means the signal you need is buried in gigabytes of noise you pay to store.

midA customer reports a failure at 14:32. How do you find that one request across five services?

Answer

With a trace id that was propagated everywhere and stamped on every log line. The mechanism is W3C Trace Context: the traceparent header flows across HTTP calls automatically in .NET because HttpClient and ASP.NET Core participate in Activity, and the same id must be copied into message headers when the path goes through a queue, otherwise the trace stops at the broker — which is the single most common gap. I make the trace id part of the error response the user sees, so a support ticket carries it and the investigation starts with one query instead of a timestamp and a guess. Logs are structured, so trace_id is a field rather than text in a message, and every log written inside a request automatically carries it via the logging scope. Then the workflow is: search by trace id, look at the waterfall to find which span failed or was slow, and read the logs correlated to that span. What makes this work is discipline about identifiers — a trace id for the technical path, plus a business correlation id (order id, tenant id) as a span attribute, because customers describe problems in business terms.

Example

// Trace context across an async hop — the place it usually breaks
public async Task PublishAsync<T>(T message, CancellationToken ct)
{
    var headers = new Dictionary<string, string>();
    Propagators.DefaultTextMapPropagator.Inject(
        new PropagationContext(Activity.Current!.Context, Baggage.Current),
        headers, (h, k, v) => h[k] = v);        // writes traceparent/tracestate
    await bus.SendAsync(message, headers, ct);
}

// Consumer: Extract() before starting the activity, or the trace begins anew.

// Structured logging: trace_id is a field, not prose
logger.LogWarning("Payment declined {Reason} for {OrderId}", reason, orderId);
// → { "level":"Warning", "reason":"insufficient_funds", "orderId":"8841",
//     "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736", "span_id":"00f067aa0ba902b7" }

Follow-ups

  • What if only 5% of traces are sampled? — Use tail sampling so all errors and slow requests are kept, or head sampling with a forced-sample flag for known-interesting requests.
  • Why not just log the user id everywhere? — Do both: the trace id links the technical path, the business id makes the ticket searchable. Neither replaces the other.
  • What breaks correlation most often? — Queues without propagation, background jobs started outside a request, and any hand-rolled HttpClient that copies headers selectively.

Common wrong answer

"Each service logs its own request id." Five unrelated ids means five searches joined by timestamp guessing, which fails precisely when traffic is high — the moment you most need it. One id, propagated, is the entire point.

midWhat do you page someone for at 03:00 — and what do you deliberately not?

Answer

I page on symptoms that users experience, not on causes that may be harmless. That means alerts on the SLO: error rate and latency breaching the objective for a real service, request success rate for a critical journey like checkout, and a small number of "the system cannot recover on its own" conditions — a queue whose oldest message is hours old, a failed failover, a certificate expiring within days. What I do not page on is CPU at 85%, a single instance restarting, one slow query, or a node going away, because those are things the platform handles and the paging teaches people to ignore alerts. The refinement worth naming is multi-window burn-rate alerting: page when the error budget is being consumed fast enough to exhaust it soon (a fast burn over an hour, confirmed by a slower window to suppress blips), and open a ticket rather than a page for slow burns. Every alert must satisfy three tests: it is urgent, it is actionable, and there is a runbook — anything failing one of those becomes a dashboard or a ticket.

Example

Page (wake someone)
  checkout success rate < 99% for 5 min                 user-visible, urgent
  SLO burn rate > 14.4x over 1 h AND > 6x over 5 min    budget gone in ~2 days
  oldest unprocessed message > 1 h                      will not self-heal
  TLS certificate expires in < 7 days                   deterministic, preventable
  failover attempted and failed                         needs a human now

Ticket (working hours)
  slow SLO burn (30 d window), disk 70%, deprecated dependency, flaky test rate

Never an alert
  CPU 85%, one pod restarted, a single 500, cache hit ratio dipped
  (these are dashboards; if the platform can self-heal, let it)

Test every alert: urgent? actionable? runbook? — if any answer is no, it is not a page.

Follow-ups

  • Why two windows in a burn-rate alert? — The long window gives significance, the short one gives freshness; together they fire on a real burn and stay quiet for a 30-second blip.
  • How do you handle alert fatigue? — Measure it: pages per on-call shift, and the fraction that were actionable. Anything below roughly half means people have stopped reading.
  • Who owns an alert? — The team that can fix the underlying thing; an alert routed to a team without the authority to act is just noise with a nicer address.

Common wrong answer

"Alert when CPU is over 80% and memory over 90%." Cause-based thresholds fire when nothing is wrong and stay silent when everything is — a service can be entirely broken at 5% CPU. After two weeks of false pages, the real one is muted.

seniorYour observability bill has doubled. What do you cut, and how do you avoid cutting what you need?

Answer

I attack cardinality first, because it is almost always the cause and it is invisible until the invoice arrives. A metric's cost is the number of unique label combinations, so one dimension with high cardinality — user id, order id, raw URL path with ids in it, a full error message — multiplies every series by that dimension's size and can turn a cheap counter into millions of time series. The fix is to move those to trace attributes or logs, where per-item detail belongs, and keep metric labels to bounded sets: route template rather than URL, status class rather than message, tenant tier rather than tenant id. Second, sampling: tail-based sampling that always keeps errors and slow traces while sampling successful ones at 1–5% typically cuts trace volume by an order of magnitude without losing anything you would have looked at. Third, log levels and retention tiering: Information in production rather than Debug, thirty days hot and the rest to cheap object storage that you can query occasionally. The discipline that prevents the recurrence is an OpenTelemetry Collector in front of the vendor, where sampling, attribute dropping and redaction are enforced centrally instead of relying on every team to be careful.

Example

Cardinality arithmetic (the reason the bill doubled)
  http.server.request.duration
    route(40) x method(5) x status(6)               =   1,200 series   fine
    + tenant_id(5,000)                              = 6,000,000 series  expensive
    + user_id(2,000,000)                            = astronomic        never do this

Rules
  metric labels        bounded, low cardinality, known at design time
  trace attributes     per-request identifiers live here (tenant, order, user)
  logs                 free-form detail, sampled and tiered

Collector-side controls (one place, all teams)
  tail_sampling: keep 100% errors, 100% > 2 s, 3% of the rest
  attributes/drop: remove request bodies, auth headers, PII
  retention: 30 d hot, 12 mo cold object storage

Follow-ups

  • How do you find the offending metric? — Most backends expose per-metric series counts; sort descending and the top three are usually one recent commit.
  • Is head or tail sampling better? — Tail, because the decision is made after you know whether the trace was interesting; it costs a buffering collector, which is worth it.
  • What must never be sampled away? — Anything used to compute an SLI: sample traces, never the metrics your objectives and alerts are derived from.

Common wrong answer

"Reduce the retention period." It saves the least and hurts the most: retention is a small part of the cost compared with ingest and cardinality, and shortening it removes exactly the historical baseline you need to say whether today is abnormal.

seniorEvery dashboard is green and customers are complaining. How is that possible?

Answer

Because the dashboards measure the parts and the customer experiences the whole. Several patterns produce it, and I check them in order. Averaging: a p50 that looks fine while p99 is catastrophic, or a global success rate that hides one tenant, one region or one API version failing entirely — which is why every core metric needs a small set of dimensions and why I look at the worst segment, not the aggregate. Coverage: the failing path is not instrumented at all, typically a client-side error, a third-party script or a CDN issue that never reaches your servers, which is what real-user monitoring and synthetic checks from outside your network exist to catch. Semantics: the service returns 200 with an error body, so error-rate panels see nothing. And staleness: the pipeline feeding the dashboard is itself broken, so green means "no data" rather than "no problem". The fix is to have at least one user-journey signal that fails when the customer's experience fails — a synthetic transaction that logs in, adds to cart and checks out on a schedule from outside — because that is the only check that spans every component including the ones you do not own.

Example

Checklist when "everything is green"
  1 segment      by tenant, region, API version, client version, device class
                 (one tenant at 0% success can hide inside 99.4% overall)
  2 percentile   look at p99 and max, not the average
  3 coverage     is the failing hop even instrumented? client-side? CDN? third party?
  4 semantics    200-with-error-body, or a fallback silently serving stale data

Follow-ups

  • Why a synthetic check when you have real-user monitoring? — RUM needs traffic; synthetics catch a 03:00 break before the first real user does, and they test a fixed journey so a change is unambiguous.
  • What single dimension is most often missing? — Tenant (or customer segment): without it, per-customer outages are mathematically invisible in a healthy-looking aggregate.
  • How do you know the monitoring is alive? — A dead-man's-switch alert: page if the heartbeat metric stops arriving, so silence is treated as failure rather than as health.

Common wrong answer

"Then the customers must be wrong, or it is their network." Occasionally true, and as a first response it is the reasoning that keeps outages alive for hours. The default assumption should be that the gap is in the instrumentation, because that is where it almost always is.

principalHow do you make an organisation care about operability rather than only about features?

Answer

By making reliability a budget rather than a virtue, so it competes with features on the same terms instead of losing every planning meeting. That is what error budgets do: the SLO is agreed with the business, the budget is the allowed unreliability, and the policy is written down in advance — budget remaining means ship fast, budget exhausted means the next sprint is reliability work. It converts an argument about values into an arithmetic fact nobody has to win. Alongside that I make the people who build a service also carry it, because ownership changes design more than any review does; and I make the operational cost visible in the same forum as the feature roadmap — pages per week, toil hours, the fraction of postmortem actions completed. Then I remove the excuses: a golden-path template where telemetry, health checks and pipelines come for free, so operability is the default rather than extra work a team must justify. The principal-level part is protecting it politically — being the person who says "we are out of budget, the release waits" the first time it happens, because the policy is only real once it has cost something.

  • How do you avoid this becoming bureaucracy? — One SLO per user-facing journey, not per service; a handful of numbers people can recite beats a catalogue nobody reads.
  • What is the strongest cultural lever? — The team that writes it carries the pager. Every argument about operability ends faster when the author is woken by it.

Common wrong answer

"We will allocate 20% of every sprint to technical debt." It is the first thing cut under pressure because it has no external commitment behind it. An error budget survives because the trigger is a measured number agreed with the business, not an intention.

12Security, identity and multi-tenancy

Security shows up in system design interviews as a design constraint rather than a checklist: how identity flows through the system, how one tenant is kept away from another's data, and what an attacker gets if one component is compromised. At mid level you should model authentication and authorisation correctly and pick a tenancy isolation model; at senior you should design service-to-service identity and threat-model your own API; at principal you should be able to say how compliance and residency requirements reshape the architecture rather than being bolted on.

screenerWalk me through how a user gets authenticated and how the API knows who they are.

Answer

Identity is delegated to an identity provider using OpenID Connect on top of OAuth 2.0, with the authorisation code flow plus PKCE — the only browser-appropriate flow in 2026, since implicit is deprecated and the password grant is forbidden by the security best current practice. The user authenticates at the provider, the application receives a code, exchanges it server-side for an ID token (who the user is) and an access token (what the caller may do), and from then on the API validates the access token on every request: signature against the provider's published keys, issuer, audience, expiry, and any required scopes or claims. The distinction interviewers listen for is that the ID token is for the client and the access token is for the API — sending an ID token as a bearer credential is a common and wrong shortcut. Tokens are short-lived, refresh happens through a refresh token held server-side, and the API is stateless with respect to sessions, which is what makes horizontal scaling possible.

Example

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.Authority = "https://login.example.com/";     // keys fetched and cached from here
        o.Audience  = "api://shop";                     // must match, or anyone's token works
        o.TokenValidationParameters = new()
        {
            ValidateIssuer = true, ValidateAudience = true,
            ValidateLifetime = true, ClockSkew = TimeSpan.FromSeconds(30)
        };
    });

builder.Services.AddAuthorization(o =>
    o.AddPolicy("orders:write", p => p.RequireClaim("scope", "orders.write")));

app.MapPost("/api/v1/orders", ...).RequireAuthorization("orders:write");

Follow-ups

  • Why validate the audience? — Without it, a token issued for any other application by the same provider is accepted — a complete authentication bypass that looks like working code.
  • What is the machine-to-machine equivalent? — Client credentials for a confidential client, or better, workload identity so there is no shared secret to leak.
  • Where does the .NET-native option fit? — ASP.NET Core Identity for first-party accounts; since .NET 10 it also supports passkeys (WebAuthn/FIDO2), which is the current direction for passwordless.

Common wrong answer

"We validate the JWT signature, so the token is trusted." Signature alone proves the provider issued it — not that it was issued for you, that it has not expired, or that the user still has the rights it claims. Missing audience validation is the specific hole that turns this into a breach.

screenerHow do you model authorisation — and where is it enforced?

Answer

Roles decide what kind of thing you may do; the resource decides whether you may do it to this one, and both checks are needed. Coarse permissions — "may cancel orders" — fit role- or scope-based checks in middleware or an attribute. Instance-level questions — "may cancel this order, which belongs to another tenant" — must be evaluated against the resource, which means the check happens where the data is loaded, not at the edge. That is why my default is to filter by tenant in the data-access layer itself, using a global query filter or a row-level security policy, so an endpoint that forgets the check still cannot return another tenant's rows. For anything more expressive — sharing, delegation, hierarchical ownership — attribute-based or relationship-based authorisation (a Zanzibar-style service) is the right shape, and I keep the policy out of scattered if statements so it can be audited and tested. Enforcement is always server-side and always at the last hop before data: UI-level hiding is a usability feature, never a control.

Example

// Defence in depth: coarse policy at the edge, tenant filter at the data layer
app.MapDelete("/api/v1/orders/{id}", Cancel).RequireAuthorization("orders:write");

// EF Core global filter — an endpoint that forgets the check still cannot leak
modelBuilder.Entity<Order>().HasQueryFilter(o => o.TenantId == _tenant.Current);

// Instance-level: resource-based authorisation, evaluated against the loaded entity
var order = await db.Orders.FindAsync([id], ct);          // already tenant-filtered
if (order is null) return Results.NotFound();             // not 403 — do not confirm existence
var ok = await authz.AuthorizeAsync(user, order, "CanCancel");
if (!ok.Succeeded) return Results.Forbid();

Follow-ups

  • 404 or 403 for someone else's resource? — 404, so the response does not confirm that the id exists; 403 leaks enumeration information.
  • Where do permissions live? — Coarse ones in the token as scopes; fine-grained ones behind a cached authorisation call, because putting them all in the token makes revocation wait for expiry.
  • How do you test authorisation? — Automated tests that call every endpoint as the wrong tenant and assert 404/403; broken object-level authorisation is the top OWASP API risk precisely because it is rarely tested.

Common wrong answer

"We check the role in the controller." Role checks answer the wrong question: a user with the "manager" role still must not cancel another tenant's order. Missing object-level checks — an id in the URL that nobody verifies ownership of — is the most common real-world API breach.

midHow do you isolate tenants — shared tables, schema per tenant, or database per tenant?

Answer

The decision is a trade between isolation strength and per-tenant cost, and it is very hard to change later, so it belongs in the first design conversation. A shared table with a tenant column is cheapest and scales to many thousands of small tenants; the isolation is only as strong as your filtering discipline, which is why it must be enforced by the database (row-level security) or at least by a global query filter rather than by remembering a WHERE clause. Schema per tenant gives clearer separation and per-tenant migrations at the cost of thousands of schemas your migration tooling must handle. Database per tenant gives the strongest isolation — separate backups, separate restore, separate encryption keys, easy per-tenant residency — and costs the most per tenant, so it fits enterprise deployments with dozens or hundreds of customers. In practice the mature answer is a hybrid: shared tables by default, with a tenant directory that maps a tenant to its physical location, so the large or regulated customers can be moved to a dedicated database without any application code knowing.

  • How do you migrate one tenant to its own database? — Via the directory: export, restore, flip the mapping, drain. That path must exist from day one or the hybrid model is fiction.
  • What about per-tenant encryption keys? — Only realistic at database-per-tenant granularity, and it is exactly what makes crypto-shredding a viable erasure story.

Common wrong answer

"Add a TenantId column and filter on it in the repository." One forgotten filter in one query is a cross-tenant data leak, and it is a class of bug that code review catches unreliably. The filter belongs where it cannot be forgotten: row-level security, or a global query filter plus a test that proves it.

midHow is sensitive data protected at rest and in transit, and what counts as sensitive?

Answer

In transit: TLS everywhere, including inside the datacentre, because the flat internal network is an assumption attackers rely on; modern TLS versions only, HSTS at the edge, and certificates rotated automatically so nobody's calendar reminder is load-bearing. At rest: full-disk or storage-level encryption is table stakes and protects against a stolen disk, but not against an attacker with a valid database connection — which is the realistic threat — so anything genuinely sensitive gets application-level encryption with keys in a managed key service, or tokenisation so the sensitive value never enters your system at all. Payment card data is the clearest case: use a provider's hosted fields so the number never touches your servers, which removes most of the PCI scope. For personal data I classify first, because you cannot protect what nobody has enumerated: an inventory of what is stored, where, why and for how long, driving retention and deletion. And I keep secrets out of code and configuration files entirely, with rotation that works without downtime.

Example

  internal        aggregate metrics                  access control only
  personal        name, email, address               encrypted at rest, retention policy,

  sensitive       health, financial, government id   + application-level encryption,

Follow-ups

  • Why encrypt inside the datacentre? — Because a compromised pod, a misconfigured mesh or a mirrored port makes plaintext internal traffic readable; assume the network is hostile.
  • What does field-level encryption break? — Querying: you cannot index or range-search an encrypted column; searchable encryption or a deterministic hash for equality lookups is a deliberate trade.
  • How do you handle right-to-erasure with immutable logs? — Crypto-shredding, plus a documented retention window for backups; "we cannot delete it" is only acceptable if it is bounded and written down.

Common wrong answer

"The database has transparent data encryption, so the data is encrypted." TDE protects the files. Any application, backup export or SQL injection with a valid connection reads plaintext — which covers essentially every real breach scenario.

seniorHow do services authenticate to each other, and what does an attacker get from one compromised pod?

Answer

Every service has its own identity, and no service trusts another because of where it sits on the network. In practice that means workload identity issued by the platform — a Kubernetes service account projected as a short-lived token, a SPIFFE identity, or a managed identity on a cloud provider — so there is no long-lived shared secret to steal, and mutual TLS between services, usually provided by a mesh, so both ends are authenticated and the traffic is encrypted. Authorisation is then per-caller and least-privilege: the pricing service may call the catalogue, nothing may call the payment service except the order service, enforced with network policies and per-service scopes rather than a flat network. The blast-radius question is the one worth answering explicitly: from one compromised pod an attacker gets that workload's identity and its permissions, for the lifetime of a token measured in minutes — and nothing more, if the design is right. That is why I care about credential lifetime, per-service scoping, egress restrictions and audit logging of service-to-service calls, and why "it is inside the VPC" is not an authorisation model.

Example

Zero-trust internals, concretely
  identity      workload identity (K8s projected SA token / SPIFFE / managed identity)
                no static client secrets in config or a vault the app reads at will
  transport     mTLS between services (mesh or library), certificates rotated hourly
  authorisation per-caller scopes: order-svc → payment-svc:charge  (nothing else can)
  network       default-deny NetworkPolicy; explicit allow per pair; egress restricted
  audit         every service-to-service call logged with caller identity

Blast radius from one compromised pod
  ✓ that workload's identity, for the token's remaining minutes
  ✓ what that workload is authorised to call, and nothing else
  ✗ NOT a shared secret usable by any service
  ✗ NOT lateral movement to unrelated services (default-deny)
  ✗ NOT the database directly, if credentials are per-service and scoped

Follow-ups

  • How do you propagate the end user's identity? — A separate token or a signed assertion alongside the service identity; do not let a service impersonate a user by asserting a user id in a header.
  • Is a service mesh required? — No — libraries can do mTLS — but a mesh gives it uniformly without every team implementing it, which is usually why it wins.
  • What about database credentials? — Per-service, least-privilege (no DDL, no access to other schemas), issued dynamically where the platform supports it.

Common wrong answer

"Internal services are behind the firewall, so they trust each other." That single assumption converts any one vulnerability — a dependency, an SSRF, a leaked pod — into full lateral movement across the platform. It is the flat-network assumption every significant breach report describes.

seniorThreat-model the API you just designed. What are the three most likely attacks?

Answer

I work from the attacker's goals against this specific design rather than reciting a list. For a typical multi-tenant business API the three most likely are, in order: broken object-level authorisation — changing an id in a URL to read someone else's resource, which is the most commonly exploited API flaw and the one that automated tests catch cheaply; injection and SSRF through anything that takes a URL, a file or a query fragment from the caller, where the impact is reading cloud metadata endpoints or internal services; and business-logic abuse — replaying a request, racing two concurrent requests to spend the same credit twice, or enumerating resources through an endpoint with no rate limit. I then structure it properly with STRIDE per trust boundary, because the value of a model is that it is repeatable, and I write mitigations as testable requirements: an authorisation test per endpoint, an allow-list for outbound URLs, idempotency keys and per-tenant rate limits. The last part is supply chain, which in 2026 belongs in every threat model: pinned dependencies, an SBOM, scanning in CI, and a plan for the day a package you depend on is compromised.

  • What is the highest-value automated control? — Authorisation tests generated per endpoint, because the top risk is also the easiest to regress silently.

Common wrong answer

"We follow the OWASP Top 10." That is a list of categories, not an analysis of your system: it will not tell you that this endpoint takes a tenant id from a header, or that this webhook field lets a caller reach your metadata service. The specificity is the whole exercise.

principalA regulator requires EU customer data to stay in the EU. How does that change the architecture?

Answer

It turns a deployment question into a data-flow question, and the first step is an inventory: every store, log, backup, queue, cache, analytics pipeline and third-party processor that personal data touches — because residency is usually broken not by the main database but by an observability vendor in another region, a support tool, or a nightly export. Then I choose the model. Full regional isolation — a complete stack per region with a routing layer that sends a customer to their home region — is the strongest and most expensive, and it is what genuinely strict interpretations require; it forces per-region deployment, per-region operations, and a decision about what global data (the tenant directory, the identity provider, the product catalogue) may be replicated. The lighter model keeps a single control plane with regional data planes, so only personal data is pinned while shared, non-personal metadata stays global — usually the right balance, but it must be defensible in an audit rather than convenient. Either way the cross-cutting work is the same: pseudonymise before anything leaves the region, keep the key in-region, and treat every third party as a processor with a location, a contract and a review. What I say plainly to the business is the cost — engineering time, duplicated infrastructure, slower global features — so that residency is a priced decision rather than an assumed one.

  • What is the most commonly missed leak? — Telemetry: a user's email in a log message shipped to a vendor in another region is a residency violation nobody notices until an audit.
  • Can a global identity provider stay global? — Often yes if it holds only pseudonymous identifiers, but that is a legal determination — get it in writing rather than assuming.
  • How do you keep new features compliant? — Make the region a first-class parameter in the platform template, so a new service is regional by default and going global requires a decision.

"We deploy the application in an EU region." The application is rarely where the data escapes: logs, traces, backups, analytics exports and SaaS sub-processors are, and every one of them is outside the scope of "we changed the deployment region".

13Deployment, environments and release

Interviewers ask about deployment because it reveals whether your architecture is one you have actually shipped: how a change reaches production, how it is rolled back, and what happens to the database in between. At mid level, describe a zero-downtime deployment and separate deploy from release; at senior, design probes, resource limits and a test strategy that does not depend on a shared staging environment; at principal, change an organisation's release cadence without breaking it.

screenerHow do you deploy without downtime — rolling, blue/green or canary?

Answer

Rolling is the default and the cheapest: replace instances a few at a time, with readiness probes gating each batch, so capacity stays sufficient throughout. Its consequence — which is the part that matters — is that both versions run simultaneously, so every change must be backward compatible with the previous version, including the database schema and any message contract. Blue/green runs a complete second environment and switches traffic at once, which gives an instant rollback and a clean cut, at the cost of double infrastructure and a shared database that still has to work with both versions. Canary sends a small percentage of traffic to the new version and promotes it automatically if error rate and latency stay within bounds — the best risk reduction of the three, and my preference for anything user-facing, because it catches problems that no pre-production environment reproduces. Whichever the mechanism, the rollback path must be tested and fast, and the deployment must not require a human to watch a dashboard.

  • What makes a rollback impossible? — A migration that dropped or rewrote a column the previous version needs. Expand/contract exists so rollback stays available for at least one release.
  • How long should a canary bake? — Long enough to cover the slowest signal you care about — usually 15–60 minutes, or one full traffic cycle for a business with a daily pattern.
  • Who decides to promote? — Automated analysis on error rate, latency and a business metric; a human watching a dashboard at 18:00 on Friday is not a control.

Common wrong answer

"Blue/green gives instant rollback, so it is safest." The application flips instantly; the database does not. If the new version migrated the shared schema, flipping back leaves the old code reading a schema it does not understand — the rollback that fails exactly when you need it.

midHow do you ship a half-finished feature without a long-lived branch?

Answer

Separate deploying code from releasing behaviour. The code merges to trunk continuously behind a feature flag that is off, so it is built, deployed and exercised by tests but invisible to users; the release then becomes a flag change, targeted first at internal users, then a percentage, then everyone — with an instant off switch that does not require a deploy. That removes the real cost of long-lived branches, which is not merge conflicts but the fact that integration problems are discovered weeks after they were created. For structural changes the equivalent technique is branch by abstraction: introduce an interface over the thing being replaced, build the new implementation behind it, switch by configuration, and delete the old one afterwards. The discipline that keeps this from becoming a mess is flag hygiene: every flag has an owner and an expiry date, release flags are deleted once fully rolled out, and only genuinely long-lived flags — per-tenant entitlements, operational kill switches — are permanent. Otherwise you accumulate hundreds of flags whose combinations nobody has ever tested.

Example

// Microsoft.FeatureManagement: the flag decides, not the branch
if (await features.IsEnabledAsync("NewPricingEngine", user))
    return await newEngine.PriceAsync(cart, ct);
return await legacyEngine.PriceAsync(cart, ct);

// Rollout: internal → 1% → 10% → 50% → 100%, each step observed
// Kill switch: flip to false, effective in seconds, no deploy, no rollback needed

// Flag hygiene (enforce it, or it rots)
//   every flag: owner, created date, expiry date, type (release | ops | entitlement)
//   release flags removed within 2 sprints of 100%
//   a CI check fails the build on a release flag older than its expiry

Follow-ups

  • How do you test flag combinations? — You cannot test all of them, so keep the number of simultaneous release flags small and test the on and off paths of each; that is a reason for hygiene, not a reason to avoid flags.
  • What about database changes for a flagged feature? — Ship the schema first, additively, so the flag can be turned on and off freely without a migration in the loop.
  • Are flags a rollback mechanism? — For behaviour, yes, and a much better one than a redeploy — which is why risky changes should be flagged even when the branch is short.

Common wrong answer

"We use a develop branch and merge to main at release." Long-lived branches defer integration pain rather than removing it: the merge is large, the conflicts are semantic rather than textual, and the code has never run alongside what everyone else built until the riskiest possible moment.

midDesign the pipeline from commit to production. What gates what?

Answer

One pipeline, one artefact, promoted rather than rebuilt. The build produces a single immutable image tagged with the commit; every environment deploys that same image with different configuration, because rebuilding per environment means the thing you tested is not the thing you shipped. Gates go from fast and cheap to slow and expensive: compile and unit tests in a couple of minutes, then static analysis, secret scanning and dependency vulnerability checks, then integration tests against real dependencies in containers — Testcontainers, or Aspire's test host, so a database test uses a real Postgres rather than an in-memory fake that behaves differently. Contract tests run here too, so a provider learns it broke a consumer before deploying. Then automated deployment to a pre-production environment, smoke tests, and a canary in production with automated analysis. What I insist on is that the pipeline is the only path to production, that it takes under fifteen minutes to the first deployable artefact, and that a rollback is one command — because a slow pipeline is not a safety feature, it is the reason people batch changes, which is what makes releases risky.

  • Where do migrations run? — As a distinct pipeline step before the application deploy, expand-only, so both versions work; never as a side effect of application startup, which races across instances.
  • What about a manual approval gate? — Keep it for genuinely irreversible actions; for everything else it adds latency and a false sense of control, since the approver rarely has information the pipeline lacks.
  • How do you keep the pipeline fast? — Parallelise, cache dependencies, and move slow suites off the critical path into a post-deploy stage; over fifteen minutes and people start batching.

Common wrong answer

"We build in each environment from the environment's branch." Then staging tested a different binary than production runs, and the classic incident follows: a dependency version resolved differently at build time, and the bug only exists in the artefact nobody tested.

seniorWhat does this service need to be a good Kubernetes citizen?

Answer

Four things, and each has a specific failure if you get it wrong. Separate liveness and readiness probes: liveness restarts a wedged process and must not check dependencies, or a slow database restarts the whole fleet; readiness gates traffic and should check what the instance needs to serve. Graceful shutdown: handle SIGTERM by failing readiness first, draining in-flight requests, then exiting — with HostOptions.ShutdownTimeout in .NET set above the longest request and below the pod's terminationGracePeriodSeconds, plus a preStop sleep so the load balancer notices before the process stops accepting. Resource requests and limits: requests drive scheduling, limits cap usage, and for .NET the important detail is that the runtime reads cgroup limits, so a container with a low CPU limit gets throttled in ways that look like random latency spikes — and a memory limit below the GC's working set produces an OOMKill with no exception and no log. Fourth, a pod disruption budget and more than one replica, so a node drain does not take the service down. On top I want the image to be small and non-root — the chiselled or distroless .NET images give a much smaller attack surface than the full runtime image.

Example

livenessProbe:  { httpGet: { path: /health/live,  port: 8080 }, periodSeconds: 10 }
readinessProbe: { httpGet: { path: /health/ready, port: 8080 }, periodSeconds: 5 }
lifecycle:
  preStop: { exec: { command: ["sleep", "5"] } }   # let the LB deregister first
terminationGracePeriodSeconds: 45                   # > ShutdownTimeout (30s) in the app
resources:
  requests: { cpu: "250m", memory: "256Mi" }        # scheduling
  limits:   { cpu: "1000m", memory: "512Mi" }       # throttling / OOMKill boundary
env:
  - { name: DOTNET_gcServer, value: "1" }
  - { name: DOTNET_GCHeapHardLimitPercent, value: "4B" }   # ~75% of the memory limit

Follow-ups

  • Why the preStop sleep? — Endpoint removal and pod termination are concurrent; without a short delay the pod stops accepting while the load balancer is still sending, producing a burst of 502s on every deploy.
  • What happens at a CPU limit in .NET? — cgroup throttling: the process is stopped for part of every period, which shows as unexplained tail latency rather than as high CPU.
  • Should containers be scaled up or out? — Prefer more small instances for resilience, but not so small that per-instance overhead (GC heaps, connection pools, caches) dominates.

Common wrong answer

"We set liveness and readiness to the same endpoint that checks the database." One database blip then fails liveness on every pod simultaneously, Kubernetes restarts the entire fleet, and a degradation becomes a full outage with a thundering herd of cold starts on the way back.

seniorHow many environments do you need, and what do you test in each?

Answer

Fewer than most organisations have, because every shared environment is a queue and a source of false confidence. My model is: ephemeral per-branch environments spun up by the pipeline for integration and manual review then destroyed, one pre-production environment that is configured identically to production for smoke tests and performance runs, and production itself, where the real verification happens behind flags and canaries. What I move away from is the chain of long-lived shared environments — dev, test, uat, staging — where each is subtly different, all of them are broken half the time, and a bug found in uat costs a week of coordination. The testing strategy follows: most confidence comes from unit and integration tests running against real dependencies in containers, contract tests replace end-to-end suites between services, and the remaining end-to-end coverage is a small number of critical journeys run against pre-production and as synthetics against production. The honest principle is that production is the only environment that is truly production-like, so the goal is not to simulate it better but to make changes safe to release there — flags, canaries, fast rollback, good observability.

Example

Environments
  ephemeral PR env   created per pull request, seeded, destroyed on merge   (no queue)
  pre-production     production-like config, anonymised data subset;
                     smoke tests + performance runs + migration rehearsal
  production         canaries, flags, synthetics — where verification actually happens

Test pyramid for a distributed system
  many   unit tests                         milliseconds, no I/O
  many   integration tests (Testcontainers) real Postgres/Redis/broker, per service
  some   contract tests                     replace cross-service E2E
  few    end-to-end journeys                5-10 critical paths, pre-prod + synthetics
  always production verification            canary analysis, feature-flag rollout, RUM

Anti-pattern: a shared "integration" environment every team must book to test in.

Follow-ups

  • How do you get realistic data without copying production? — Anonymised or synthetic datasets generated to match production's shape and skew; copying production data into a lower environment is a breach waiting to happen.
  • Where do performance tests run? — Pre-production at production-like scale for regression detection, plus load tests against production during a controlled window for the real answer.
  • Is testing in production irresponsible? — Only without guardrails. With flags, canaries, and the ability to roll back in seconds, it is the most accurate testing available.

Common wrong answer

"We need a full staging environment identical to production." It never is — different data volume, different traffic shape, different third parties, different scale — and maintaining the illusion consumes effort that would buy far more safety spent on canaries and observability.

principalThe organisation releases monthly and every release is an event. How do you get to daily?

Answer

By attacking the reason batches exist rather than mandating a cadence. Monthly releases are almost always a rational response to a slow, risky path to production: manual regression testing, a manual change-approval board, database changes that cannot be rolled back, and a deployment that requires downtime. Each of those is fixable, and the order matters because the first fix has to reduce risk visibly enough to buy permission for the next. I start by making rollback fast and boring, then automate the regression suite for the critical journeys, then introduce feature flags so the release of behaviour is decoupled from the deployment of code, then expand/contract migrations so schema changes stop blocking rollback, then replace the approval board with automated evidence — the pipeline demonstrates the tests, the scan and the canary analysis. Smaller batches then become obviously safer, and the data supports it: change failure rate and time to restore both improve as batch size falls, which is the argument that persuades management. I would pilot with one team and one service, measure the four delivery metrics before and after, and let that result do the convincing rather than an architecture memo.

Example

Sequence (each step buys permission for the next)
  1 make rollback fast and rehearsed          risk drops before anything else changes
  2 automate the top 10 regression journeys   removes the 3-day manual test window
  3 feature flags                             deploy ≠ release; incomplete work can ship
  4 expand/contract migrations                schema stops blocking rollback
  5 canary + automated analysis               evidence replaces the approval meeting
  6 shrink the batch                          weekly → daily → on merge

Measure before and after (this is the argument, not the opinion)
  deployment frequency · lead time for change · change failure rate · time to restore
  Pilot on ONE team and ONE service; publish the numbers; let other teams opt in.

Expect the real blocker to be organisational: the change board exists because a
release once broke production badly. Replace the control, do not just remove it.

Follow-ups

  • What if the change board is a compliance requirement? — Then satisfy it with automated evidence: the pipeline record — who, what, tests, scans, approvals in code review — is a stronger audit trail than a meeting.
  • What breaks first when cadence increases? — Whatever was manual and unmeasured: usually the migration process and the regression suite's flakiness.
  • How do you handle a team that resists? — Find out what they are protecting against; resistance is usually memory of a specific incident, and naming the control that now prevents it is more effective than advocacy.

Common wrong answer

"Mandate continuous deployment and remove the approval gate." Removing the control without replacing the safety it provided produces exactly the incident that justifies reinstating it — and the second time, the freeze lasts far longer.

14Cost, capacity and performance

Cost questions appear late in senior and principal loops, and they are a fast way to tell whether someone has owned a system rather than designed one. The interviewer wants to see that you know roughly what things cost, where cloud bills actually go, how to plan capacity from a load model, and how to make a system faster without guessing. At senior level, plan capacity and run a load test that means something; at principal, treat cost per transaction as a design constraint alongside latency and availability.

midRoughly what does this design cost to run per month?

Answer

I build it up from the load model rather than from a price list, in four buckets: compute, data stores, data transfer and managed services. Compute comes from the peak concurrency and per-instance capacity I already estimated, plus headroom and a non-production environment. Data comes from the storage estimate plus IOPS and the replica count — and the managed database is usually the single largest line, often more than all the application instances together, which surprises people. Transfer is where bills hide: egress to the internet is billed per gigabyte and cross-availability-zone traffic is billed in both directions, so a chatty service mesh spread across three zones can cost more than the compute it connects. Managed services — the broker, the cache, the search cluster, the observability vendor — are each individually reasonable and collectively significant, which is the real argument for not adding a second data store casually. I give the number to one significant figure and say which assumption dominates, because the value of the estimate is knowing which lever matters, not the total.

Example

Order of magnitude, mid-size B2B SaaS (~2k req/s peak, 5 TB hot data)

  application compute   12 instances x ~$120       ≈ $1,400   (+ ~40% for non-prod)
  managed Postgres      HA primary + replica       ≈ $2,500   ← usually the biggest line
  cache (Redis/Valkey)  32 GB, HA                  ≈   $600
  broker                managed, 3 brokers         ≈ $1,200
  object storage        20 TB standard             ≈   $450
  CDN + egress          8 TB internet egress       ≈   $700   ← check first when it spikes
  observability         ingest + retention         ≈ $1,200   ← grows with cardinality
  ---------------------------------------------------------------
  total                                            ≈ $8,000/month, ±50%

Then: cost per 1,000 requests, and cost per active tenant — those are the numbers that
tell you whether the product's unit economics work.

Follow-ups

  • What is usually the biggest surprise? — Cross-zone data transfer and observability ingest; neither appears in an architecture diagram and both scale with chattiness.
  • How do you make cost visible to teams? — Tag everything by service and team, and report cost per unit of business value (per tenant, per 1,000 requests) rather than a total nobody can act on.
  • Reserved capacity or on demand? — Reserve the steady baseline, burst on demand; committing 100% removes the elasticity you are paying a premium for.

Common wrong answer

"That depends on the cloud provider's pricing." True and evasive: the interviewer wants to see that you know the shape of the bill — that the database and the network usually dominate, and that compute is rarely the lever people assume.

midThe bill doubled and traffic did not. Where do you look?

Answer

I look for the things that scale with something other than user traffic, because those are what change without warning. The usual suspects, in the order I check them: a data-transfer change — a new cross-zone call path, a cache miss rate that pushed traffic to the origin, or a CDN misconfiguration serving from the origin instead of the edge; observability volume, where one new high-cardinality label or a log level left at Debug can double ingest overnight; storage that grew because a retention or lifecycle policy is missing, so every temporary artefact is kept forever; and orphaned resources — a load test environment left running, unattached volumes, snapshots from a migration. Then I check whether autoscaling is thrashing or a minimum was raised during an incident and never lowered. The way to make this diagnosable rather than archaeological is tagging and per-service cost allocation from day one, plus an anomaly alert on daily spend, so the question is "what changed on Tuesday" instead of "what does this account do".

Example

Checklist, in the order that finds it fastest
  1 diff the bill by service and by day         which line moved, and when
  2 correlate with deploys and config changes   the cause is nearly always a change
  3 data transfer      new cross-AZ path? cache hit ratio dropped? CDN bypassed?
  4 telemetry          new metric label? log level? trace sampling rate?
  5 storage growth     missing lifecycle rule, orphaned snapshots, unbounded table
  6 idle resources     load-test cluster, unattached disks, an old replica
  7 autoscaling        min instances raised during an incident and never restored

Preventive: cost tags per service/team, a budget alert per service, and a monthly
review that treats a 20% unexplained rise as a defect with an owner.

Follow-ups

  • Why does a lower cache hit ratio cost money? — Every miss becomes origin compute, database I/O and often egress; a hit-ratio regression is a cost incident as much as a latency one.
  • What is the cheapest structural fix? — Lifecycle policies on storage and sampling on telemetry: both are one-time configuration that keeps paying.
  • Should engineers see cost dashboards? — Yes, per service and in the same review as latency and errors; cost owned by finance alone is cost nobody can reduce.

Common wrong answer

"We would ask the cloud provider for a discount." Commitment discounts are real and they are the last step, not the first: applying one to unexamined waste locks in the waste for one to three years.

seniorHow do you plan capacity for a launch you have never seen traffic for?

Answer

I turn the business forecast into a load model, measure what one instance actually does, and then decide how much headroom to buy. The load model is not just a request rate: it is the mix of endpoints, the read/write ratio, the payload sizes and the peak-to-average shape, because a launch spike behaves nothing like steady state. Then I measure a single instance's saturation point with a load test that ramps until latency breaks, giving me requests per second per instance at an acceptable p99 — and critically the shared-tier limits, since the application usually is not the ceiling. From there capacity is arithmetic with headroom: I plan for peak times a safety factor, typically 2×, because the forecast will be wrong and autoscaling is late by the warm-up time. For a launch specifically I add two things that are not arithmetic: a load-shedding path so exceeding the plan degrades rather than collapses, and a rehearsed rollback of the launch itself — a flag that returns the feature to a waiting list. And I identify the bottleneck in advance, because knowing that the database connection budget caps you at eighteen instances is worth more than any average.

Example

1 Load model from the forecast
    50k signups week 1 · 30% active daily · 12 actions each · peak 3x average
    → peak ≈ 60 req/s API, 5 req/s writes, with a 10x spike at the launch email

2 Measure one instance (ramp until p99 exceeds the budget)
    140 req/s at p99 220 ms   → saturation
    plan at 60% of saturation = 85 req/s/instance

3 Capacity = peak x safety / per-instance
    600 req/s (spike) x 2 / 85 ≈ 15 instances, min 4, max 25

4 Check the SHARED tier — usually the real ceiling
    15 x pool 20 = 300 connections vs max_connections 500  ✓
    write throughput 50/s vs measured primary ceiling ~800/s  ✓
    cache 8 GB working set vs 16 GB provisioned  ✓

5 Not arithmetic: load shedding, a launch kill switch, and someone watching the first hour.

Follow-ups

  • Why 60% of saturation? — Latency degrades non-linearly near saturation, so the last 40% of theoretical capacity is unusable in practice and leaves nothing for a failed instance.
  • What does a good load test include? — Realistic data volume and cache state, a realistic endpoint mix, and think time; a hot-loop benchmark of one endpoint against an empty database measures nothing you care about.
  • How do you validate the plan? — A game day at 2× projected load in pre-production, and a staged launch (waiting list, region by region) so the real numbers arrive before everyone does.

Common wrong answer

"Autoscaling handles it." Autoscaling reacts after saturation and takes as long as an instance takes to become ready — a minute or more — which is the entire duration of a launch-email spike. It also scales the tier that is usually not the bottleneck.

seniorThe system is too slow. In what order do you attack it?

Answer

Measure, find the dominant term, fix that, repeat — and resist the temptation to optimise what is easy to optimise. In a typical .NET web system the cost is nearly always concentrated in a small number of places, so I start with a trace waterfall of a slow request to find where the time goes, and it is usually the database: a missing index, an N+1, or a query returning far more data than the response needs. Next is the number of round trips, because latency compounds — five sequential calls at 40 ms is 200 ms that parallelising or batching removes. Then payload size, since serialisation and network time scale with bytes and most APIs return fields nobody reads. Only after those do I look at algorithmic and allocation-level work in the application, which is where developers instinctively start and where the smallest wins usually are. Caching goes near the end deliberately: it is a way to avoid work, so it should come after the work itself is not absurd, otherwise you have cached an inefficient query and made the cold path a cliff.

Example

Typical slow endpoint, measured (trace waterfall, p99 1,850 ms)

  auth                     8 ms
  query: load order      620 ms   ← missing composite index
  query: load lines (x40) 780 ms   ← N+1
  http: pricing service  260 ms   ← sequential, could be parallel with the above
  serialise + write      180 ms   ← returns 60 fields, the screen renders 9

Fixes in order of value
  1 index (tenant_id, created_at)          620 → 12 ms
  2 projection instead of N+1              780 → 25 ms
  3 parallelise the pricing call           260 → overlapped, ~0 added
  4 trim the response payload              180 → 40 ms
                                          p99 ≈ 1,850 → 95 ms, no cache added
  5 NOW consider caching, if it is still worth it — on a query that is already sane.

Follow-ups

  • Why not cache first? — Caching a bad query hides the cost until the hit ratio drops, and the cold-start cliff is then far worse than the original problem.
  • When is the application code actually the bottleneck? — Serialisation of large payloads, regex on hot paths, and per-request allocation; a profiler tells you in minutes and speculation does not.
  • How do you keep it fast? — Latency SLOs per endpoint with alerts, plus a performance test in the pipeline for the critical paths, so the regression is caught by the build rather than by users.

Common wrong answer

"Add a cache and scale out." Both can help and neither addresses a query doing a sequential scan or an N+1 — you have paid for more instances that each do the same wasteful work, and the database, which was the bottleneck, now receives more connections.

principalInfrastructure cost is growing faster than revenue. What do you change?

Answer

I reframe it from a cost problem into a unit-economics problem, because total cost growing with a growing business is expected and cost per unit growing is the actual defect. So the first artefact is cost per tenant, per transaction and per active user over time, segmented by service — which usually shows that the growth is concentrated in one or two places rather than spread. From there the levers are architectural, not procurement: a data-retention and tiering policy, because storage that is never deleted compounds; a payload and chattiness reduction, since cross-zone and egress traffic scale with design choices; telemetry sampling and cardinality limits; right-sizing against measured utilisation rather than the number someone picked at launch; and removing a redundant data store, which is often the cleanest single saving because it removes an operational burden too. The organisational half is making cost a visible attribute of a service alongside latency and availability — showback per team, a cost line in the design review, and an alert when cost per transaction regresses — so the ratchet is continuous rather than an annual panic. And I am explicit about the trade: some of this cost buys reliability and speed of delivery, so the goal is not the minimum bill but a defensible cost per unit of value.

Example

Diagnose in unit terms, not totals
  cost / 1,000 requests   $0.42 → $0.71 over 6 months   ← the real problem
  cost / active tenant    $18   → $31
  by service: search cluster +180%, telemetry +140%, everything else roughly flat

Levers, by typical saving and by risk
  retention + lifecycle policies      high saving   low risk   (do first)
  telemetry sampling + cardinality    high          low
  right-size from measured usage      medium        low
  remove a redundant data store       high          medium     (also removes toil)
  reduce cross-AZ chattiness          medium        medium     (co-locate, batch)
  commitment discounts on the stable baseline  medium  low     (do LAST, after cleanup)

Make it stick: cost per transaction as a tracked metric with an owner, a cost line in
every design review, and an alert on unit-cost regression — not just on total spend.

Follow-ups

  • What if the business wants a 50% cut now? — Name what is bought with each block of cost: reliability (replicas, multi-AZ), speed (non-production environments), and insight (telemetry). Cuts are choices among those, and the choice belongs to the business once it is stated plainly.
  • How do you stop teams over-provisioning? — Showback with a default that is right-sized, and make scaling up easy and reversible; over-provisioning is usually fear of a slow path back.
  • Is serverless the answer? — Sometimes for spiky or low-volume workloads; for steady high volume it is usually more expensive per request, so it is a shape decision, not a savings strategy.

Common wrong answer

"Move to cheaper instance types and negotiate the contract." That is a one-time percentage against a growth rate that continues compounding. If cost per transaction is rising, the architecture is the cause and procurement only postpones the conversation.

15Real-time, streaming and long-running work

Interviewers use this sub-area to see whether you can design the parts of a product that do not fit the request/response shape: a ten-minute export, a scheduled reconciliation, a stream of events with late arrivals, a multi-gigabyte upload, a notification fan-out. It is asked less often than the core sub-areas but comes up in nearly every product with real users, and the answers are largely about state, resumability and honesty with the user about progress.

midA user requests an export that takes ten minutes. Design the whole interaction.

Answer

The request creates a resource that represents the job, not the result. POST /exports validates, persists a job row with status queued, enqueues the work and returns 202 with a Location pointing at /exports/{id}, which the client polls or subscribes to for progress. The worker processes in resumable chunks, updating progress and a heartbeat so a stalled job is detectable, and writes the output to object storage rather than into the database. When it finishes, the job resource carries a short-lived pre-signed download URL, so the file never passes through the API and the download is not limited by your instances' bandwidth. The details that matter: the job must be idempotent on retry (a request id so a double submit does not produce two exports), it must have a terminal failure state with a reason the user can read, it needs a timeout after which it is marked failed rather than sitting in running forever, and the artefact needs a lifecycle policy so exports do not accumulate for years.

Example

POST /api/v1/exports            { "type": "orders", "from": "...", "to": "..." }
  → 202 Accepted
    Location: /api/v1/exports/7f3a
    { "id": "7f3a", "status": "queued", "createdAt": "..." }

GET /api/v1/exports/7f3a
  { "status": "running", "progress": 0.42, "rowsWritten": 412000,
    "heartbeatAt": "2026-09-08T09:41:59Z" }
  ...
  { "status": "succeeded", "rowCount": 980412, "bytes": 141_204_889,
    "downloadUrl": "https://blob.../exports/7f3a.csv.gz?sig=...", "expiresAt": "+1h" }

  { "status": "failed", "error": { "code": "RANGE_TOO_LARGE",
                                   "message": "Narrow the date range to 90 days." } }

Worker: chunked + resumable (checkpoint the last key), heartbeat every 30 s,
        hard timeout at 30 min → failed, artefact lifecycle: delete after 7 days.

Follow-ups

  • Poll or push? — Poll with a sensible interval is fine and simplest; SSE or a WebSocket is worth it only when many jobs are watched at once or progress must feel live.
  • How do you stop one user monopolising the workers? — Per-tenant concurrency limits and a separate queue or priority class for large jobs, so a 10-million-row export cannot starve everyone's small ones.
  • Why pre-signed URLs? — The download bypasses your service entirely: no bandwidth cost on your instances, no long-lived connection holding a thread, and expiry is enforced by the storage layer.

Common wrong answer

"Run it in the request and increase the timeout." Ten minutes exceeds nearly every proxy, load balancer and browser timeout, holds a thread and a connection throughout, produces nothing on failure, and cannot be resumed — and a deploy in the middle loses the work with no record it was ever requested.

midHow do you run scheduled work reliably across a scaled-out deployment?

Answer

Two problems have to be solved: exactly one instance should start the job, and the job must survive the instance disappearing. For the first, a timer in every replica means N runs, so I use a lease — a database advisory lock, a Kubernetes Lease, or a scheduler outside the application (a CronJob, or a managed scheduler that enqueues a message). My preference is the last one, because it separates the trigger from the work: the scheduler publishes a message, the normal consumer machinery handles retries, dead-lettering and observability, and no application instance needs to know it is special. For the second, the job is designed to be idempotent and resumable — checkpointed progress and a natural key — so a re-run after a crash completes rather than duplicating. Then there are the operational details that separate an answer from experience: what happens if a run overlaps the previous one (skip, queue, or run concurrently — decide explicitly), what happens to a missed run during an outage (catch up, or skip and alert), time zones and daylight saving for anything business-scheduled, and monitoring on absence — an alert when the job has not completed in its expected window, because silent non-execution is the failure nobody notices.

Example

Preferred shape
  scheduler (K8s CronJob / managed scheduler)  →  publishes "RunNightlyReconciliation"
  normal consumer                              →  retries, DLQ, tracing, metrics for free

If it must live in the app: lease + idempotent job
  advisory lock:  SELECT pg_try_advisory_lock(hashtext('nightly-recon'))
  the loser does nothing; the winner runs, checkpoints, releases

Decide explicitly (these are the questions that get asked)
  overlap        skip if the previous run is active (usual), or allow concurrency
  missed run     catch up (backfill window) or skip + alert
  time zone      business-local with DST handled, or UTC — say which and why
  observability  alert on ABSENCE: "no successful run in 26 h" — not just on failure

Follow-ups

  • Why is "alert on absence" so often missing? — Because monitoring is built around failures, and a job that never starts emits nothing at all; a dead-man's-switch alert is the fix.
  • What if the job takes longer than the interval? — Then the interval is wrong or the job must be partitioned; overlapping runs of a non-idempotent job is a classic duplicate-data incident.
  • How do you test a scheduled job? — Make the trigger a message so the job can be invoked on demand in any environment; jobs testable only by waiting for a clock are jobs nobody tests.

Common wrong answer

"Use a BackgroundService with a timer." In a single instance it works; at three replicas it runs three times, and with a non-idempotent job that means triple invoices, triple emails, or a reconciliation that fights itself.

seniorDesign a pipeline that aggregates events per minute. What do you do about late data?

Answer

I separate event time from processing time and window on event time, because a mobile client that was offline for an hour will deliver events with old timestamps, and windowing on arrival silently attributes them to the wrong minute. Windows then need a watermark — a moving estimate of how far event time has progressed — and a lateness allowance: emit a result when the watermark passes the window's end, keep the window open for a configured grace period, and either update the result when a late event arrives or route anything beyond the allowance to a side output for reconciliation. That forces the design decision the question is really about: are downstream consumers able to handle a restatement of a published number, or must the number be final when published? If restatement is acceptable, emit early and correct; if not, delay publication by the lateness allowance and accept the latency. Alongside that I keep the aggregation idempotent and keyed, so reprocessing a partition after a bug produces the same result rather than double-counting — which is the property that makes the pipeline recoverable at all.

Example

Windowing on event time
  window        1 min tumbling, keyed by (tenant, metric)
  watermark     max(event_time seen) - 30 s     (tolerate mild out-of-order)
  allowed late  5 min                            → window stays open, result updated
  beyond late   → side output "late_events" topic + a metric; reconciled hourly

Publication contract — decide this explicitly
  A "early + restate"   publish at watermark, revise for 5 min   (dashboards: fine)
  B "final only"        publish at watermark + 5 min             (billing: required)

Idempotent aggregation so replay is safe
  upsert into agg(tenant, metric, minute) values (...) on conflict do update
  set value = excluded.value      -- recomputed value, not value + excluded.value

Watch: watermark lag, late-event rate, and the gap between event time and processing time.

Follow-ups

  • Tumbling, hopping or session windows? — Tumbling for periodic metrics, hopping for smoothed moving figures, session for user-activity boundaries with an inactivity gap.
  • What if a client's clock is wrong? — Clamp event times to a plausible range against server receipt time and count the clamped events; a device set to 2019 otherwise poisons a window forever.
  • Where does exactly-once fit? — Within the stream processor it is achievable; at the sink it comes from idempotent upserts keyed by window, which is why the aggregate is written as a replace rather than an increment.

Common wrong answer

"Bucket events by arrival time — it is close enough." It is close enough until a mobile client reconnects, a consumer lags, or a partition is replayed; then an hour of traffic lands in one minute and the chart shows a spike that never happened, which erodes trust in every number the system produces.

seniorUsers upload 2 GB video files. Design the upload path.

Answer

The bytes never touch my API. The client asks for an upload authorisation, the service validates entitlement and quota and returns a pre-signed URL — or a multipart upload session — scoped to one key and expiring in minutes; the client then uploads directly to object storage, in parts, so a dropped connection resumes from the last completed part instead of restarting a two-gigabyte transfer. When the upload completes, the client calls back or the storage layer emits an event, and only then does the service create the durable record and enqueue processing: virus scanning, format validation, transcoding, thumbnailing — each as a job with its own retry, because a 4K transcode is minutes of CPU that must not happen inside a request. The security details are the ones interviewers probe: the pre-signed URL must be narrowly scoped and short-lived, the content type and size limits must be enforced by the storage policy rather than trusted from the client, the file must be treated as hostile until scanned (quarantine bucket, then promote), and it must never be served back from a domain that shares cookies with your application.

Example

1  POST /api/v1/uploads          { filename, sizeBytes, contentType }
     → server checks quota/entitlement, generates a key, returns:
       { uploadId, parts: [{ partNumber, url, expiresAt }], maxPartSize }
       constraints enforced in the signed policy: max size, allowed content type

2  client → object storage, direct, multipart, parallel, resumable
     (retry a failed part only; no bytes through the API, no thread held)

3  POST /api/v1/uploads/{id}/complete   { parts: [{ n, etag }] }
     → storage assembles; service creates the record with status "scanning"

4  pipeline: quarantine bucket → AV scan → validate → transcode → promote → "ready"
     each step a queued job with retries; failure states visible on the resource

Serving: separate domain (no shared cookies), signed URLs or a CDN token,
         Content-Disposition and a sanitised content type — never the client's.

Follow-ups

  • Why not proxy through the API? — It ties up a connection and thread per upload for minutes, caps throughput at your instances' bandwidth, and gives no resumability.
  • How do you enforce a size limit with direct upload? — In the signed policy (a content-length range condition), because anything checked only by the client is not checked.
  • What about orphaned uploads? — A lifecycle rule that aborts incomplete multipart uploads after a few days; otherwise you pay storage for parts nobody ever completed.

Common wrong answer

"Accept the file in the API and stream it to storage." It works in a demo and fails in production: a 2 GB upload over mobile takes long enough to hit proxy timeouts, cannot resume, and a deploy mid-upload loses it entirely — while each in-flight upload occupies a request slot for the duration.

seniorDesign notifications: one event, potentially millions of recipients across email, push and in-app.

Answer

I separate the decision to notify from the delivery of a notification, with a queue in between, because the fan-out is the expensive part and it must not run inside whatever produced the event. The producing service publishes a domain fact; a notification service resolves recipients, applies preferences and quiet hours, deduplicates, and enqueues one delivery job per recipient-channel. Delivery workers are per channel because their constraints differ wildly: an email provider has a sending rate and a reputation to protect, push has token expiry and per-platform batching, in-app is just a write. Three properties do the real work. Idempotency: a delivery key of event id plus recipient plus channel, checked before sending, so a retry cannot send twice. Rate control: per-provider throttling and per-user frequency caps with digesting, so a burst of a thousand events does not send a thousand emails to one person. And preference and consent enforcement at delivery time, not at enqueue time, because an unsubscribe between the two must be honoured. Fan-out to millions is then a batching problem — chunk the recipient query with keyset pagination and enqueue in batches rather than materialising a million-row list.

Example

event: PriceDropped(productId)            published by the catalogue service
   ↓
notification service
   resolve recipients   keyset-paged query, 1,000 at a time (never one big list)
   filter               preferences, consent, quiet hours, frequency cap
   dedupe key           sha256(eventId | userId | channel)
   enqueue              one job per recipient-channel, batched
   ↓
per-channel workers
   email   provider rate limit, bounce/complaint handling, suppression list
   push    token refresh + invalid-token pruning, per-platform batch APIs
   in-app  a row write; the cheapest channel, so it is the fallback

Guardrails
   frequency cap        max 3 emails/user/day → excess becomes a daily digest
   kill switch          per campaign and global; a bad send is unrecallable
   canary               send to 1% of recipients, check bounce/complaint rate, then continue

Follow-ups

  • What is the worst failure mode? — A retry loop that re-sends: notifications are irreversible, so the dedupe check must happen before the provider call, not after.
  • How do you handle a provider outage? — Queue with a long retention and back off; delayed notification is usually acceptable, duplicated notification is not.
  • How do you test a million-recipient send? — Shadow mode: run the full fan-out with delivery disabled, and assert on counts and per-user caps before ever enabling the channel.

Common wrong answer

"Loop over the users and send." It materialises a million-row result in memory, blocks whatever triggered it, has no retry that is not a duplicate, ignores rate limits until the provider blocks your domain, and cannot be stopped once started.

16Search, analytics and AI features

These come up rarely as the main prompt and often as a follow-up — "now add search", "now the business wants a dashboard", "now add a semantic assistant" — and they test whether you can bolt a new access pattern onto an existing system without corrupting it. The recurring theme is derived data: a second representation of the truth that must be kept in sync, rebuilt when it drifts, and paid for. In 2026 the AI question is standard in senior loops, and what is graded is the engineering around the model, not the model.

midAdd search to the product catalogue. What do you build?

Answer

I start by asking what "search" means here, because the answers differ by an order of magnitude in cost. If it is filtered browsing — category, price range, brand, sorted by relevance-free criteria — that is a query with the right composite indexes, and no search engine is needed. If it is text matching over names and descriptions with stemming, then PostgreSQL's tsvector with a GIN index or SQL Server full-text search handles a catalogue of hundreds of thousands of items comfortably, keeps everything in one store, and stays transactional. A dedicated search engine earns its place when you need relevance tuning, typo tolerance, faceted counts over large result sets, synonyms and multi-language analysers — features whose absence users notice, and which are genuinely hard to reproduce. Whichever I choose, the design questions are the same: what the index document contains (denormalised, per-locale, with the fields facets are computed over), how it is kept in sync, and what happens when it is unavailable — which should be a degraded but working browse experience, not an error page.

Example

-- Stage 1: often enough. One store, transactional, no sync problem.
ALTER TABLE products ADD COLUMN search tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(name, '')),        'A') ||
    setweight(to_tsvector('english', coalesce(description, '')), 'B')
  ) STORED;
CREATE INDEX ix_products_search ON products USING GIN (search);

SELECT id, name, ts_rank(search, q) AS rank
FROM   products, websearch_to_tsquery('english', $1) q
WHERE  tenant_id = $2 AND search @@ q
ORDER BY rank DESC LIMIT 20;

-- Stage 2 (only when needed): a search engine, for typo tolerance, synonyms,
-- learned relevance and facet counts over millions of documents.

Follow-ups

  • How do you evaluate search quality? — With judged queries and metrics (click-through, zero-result rate, position of the first click), not by trying a few searches by hand.
  • Where do facets come from? — Aggregations over the index; computing them in the transactional database over a large result set is the query that takes the site down.
  • What is the fallback when search is down? — Category browse and exact-id lookup from the primary store, with a visible message; losing search should not lose the catalogue.

Common wrong answer

"Add Elasticsearch." It may well be right, and stated first it skips the two questions that decide: does the requirement actually need relevance ranking, and who will operate a second stateful cluster including its version upgrades, its capacity and its sync pipeline.

midThe business wants dashboards over live data. Do you query the production database?

Answer

Not the primary, no. Analytical queries scan large ranges and hold long transactions, which is the opposite of what an OLTP primary is tuned for — they evict the buffer cache the transactional workload depends on, and in PostgreSQL a long-running report also delays vacuum, which causes bloat that outlives the query. The progression I follow is: start with a read replica, which is cheap, isolates the scans and is often the whole answer for a modest business; add materialised views or summary tables refreshed on a schedule when the same expensive aggregation is requested repeatedly; and move to a real analytical store — a columnar warehouse fed by CDC or a scheduled export — when the query set is genuinely analytical, the volumes exceed what a replica can scan in time, or the business wants to join across systems. On the replica I also set a statement timeout and route reports through a separate connection pool, so a runaway dashboard query cannot consume the connections the application needs. And I agree the freshness requirement explicitly: "yesterday's data by 07:00" is a completely different system from "within a minute".

Example

Progression, cheapest first
  1 read replica            separate pool + statement_timeout 30s + report role
                            good to roughly hundreds of GB and a handful of analysts
  2 materialised views      pre-aggregate the repeated queries; refresh on a schedule
                            "revenue by day by tenant" computed once, read thousands of times
  3 columnar warehouse      CDC or nightly export; joins across systems; years of history
                            (this is when a second store is genuinely justified)

Ask for the freshness requirement first — it decides everything
  "yesterday by 07:00"      nightly batch, simplest, cheapest
  "within an hour"          micro-batch, or CDC with hourly compaction
  "within a minute"         streaming aggregation — a different system, priced accordingly

Follow-ups

  • Why does a long report query cause bloat in PostgreSQL? — It holds a snapshot, so vacuum cannot reclaim rows newer than it; a two-hour report on a busy table leaves bloat that outlasts the report by days.
  • Can the replica be the warehouse? — For a while. It stops working when queries need a columnar layout or the scan volume competes with replication apply.
  • How do you stop analysts writing terrible queries? — Do not police them; give them the views and the timeouts. Curated models plus a resource limit beats a review process.

Common wrong answer

"It is fine, we will run reports at night." Business dashboards get refreshed during the day, someone adds an hourly schedule, and the query that was fine on last year's data volume is not this year — with no isolation, the first symptom is checkout latency.

seniorHow do you keep a search index or read model in sync with the source of truth?

Answer

Never with dual writes from application code, because there is no transaction spanning the database and the index — the failure between them leaves them permanently disagreeing with nothing to detect it. The two correct mechanisms are the transactional outbox, where the intent to index is committed with the data and a relay publishes it, and change data capture, where a connector reads the database's replication log and emits changes without the application participating at all. Either way the indexer is idempotent and version-aware: each document carries the source row's version, and an update with an older version is discarded, which makes out-of-order delivery harmless. On top of the pipeline I need two operational capabilities. A reconciliation job that samples or sweeps both sides, compares versions, and emits a drift metric — because drift is not a possibility, it is a certainty over a long enough period. And a full rebuild that can run against a new index and swap an alias when complete, because a rebuild you cannot perform means a schema change or a bug becomes permanent. The freshness target is a stated requirement with an alert on lag, not an aspiration.

Example

Pipeline
  source of truth (Postgres)
    ├─ outbox row in the same transaction   OR   logical replication slot (CDC)
    └─ relay/connector → topic "product.changed" (keyed by product id → ordered per product)
                       → indexer: upsert document, version = row.updated_version
                                  discard if incoming version <= indexed version

Operational must-haves
  lag metric        p99 seconds from commit to searchable; alert at > 60 s
  drift check       nightly: compare counts + sample versions; metric "index_drift_rows"
  rebuild           write to products_v7, verify, then swap the alias "products" → v7
                    measured: full rebuild takes 38 min at current volume

Never: repo.Save(product); await search.IndexAsync(product);   ← the failure between
       these two lines is silent, permanent, and invisible until a customer complains.

Follow-ups

  • Outbox or CDC? — Outbox when the event shape should be a deliberate contract; CDC when you want zero application changes and can consume row-shaped changes.
  • How do deletes work? — They must be captured too: a hard delete with CDC emits a tombstone; with an outbox you must write the delete intent in the same transaction, which is the case people forget.
  • How do you handle a bad index deploy? — Alias swapping: the previous index is still there, so a rollback is one alias change rather than a rebuild.

Common wrong answer

"We update the index right after saving." It is the dual-write problem with a friendly name: a crash, a timeout or a rollback between the two leaves the index wrong forever, and the drift accumulates silently because nothing compares the two sides.

seniorAdd a semantic search or assistant feature over the customer's own documents. What is the architecture?

Answer

Retrieval-augmented generation, with the engineering effort in retrieval rather than in the model. Ingestion: documents are chunked with overlap, embedded, and stored with their tenant id and access-control metadata alongside the vector — that metadata is not optional, because the retrieval filter is the only thing preventing one tenant's documents from being surfaced in another's answers. Query: embed the question, retrieve candidates with a filter that always includes the tenant and the user's permissions, and prefer hybrid retrieval — combining vector similarity with keyword search and fusing the rankings — because pure vector search misses exact identifiers, product codes and names, which is what users actually search for. Then re-rank the top candidates, assemble a bounded context, and call the model with instructions to answer only from the supplied context and to cite the chunks it used. As of 2026 the vector store no longer has to be a separate product: pgvector is mature, SQL Server 2025 ships a native VECTOR type with VECTOR_DISTANCE, and EF Core 10 supports vector search plus reciprocal rank fusion for hybrid queries — so for tens of millions of chunks or fewer, keeping vectors in the primary store removes an entire sync problem.

Example

Ingest   document → chunk (≈500 tokens, 15% overlap) → embed → store
         row: (tenant_id, doc_id, chunk_no, acl_group[], text, embedding vector(1536))
         re-embed on document change; version the embedding MODEL, because changing it
         invalidates every stored vector (plan the re-index before you need it)

Query    embed(question)
         → retrieve top 50 WHERE tenant_id = @t AND acl_group && @userGroups
           hybrid: vector similarity + BM25/full-text, fused (RRF)
         → re-rank to top 8  → assemble context (bounded tokens)
         → model: "answer only from the context; if it is not there, say so; cite chunk ids"
         → validate: every citation resolves; refuse rather than guess

Guardrails    per-tenant rate + spend caps · PII redaction before the model call ·
              prompt-injection defence: treat retrieved document text as DATA, never as
              instructions · log question, retrieved ids and answer for evaluation

Follow-ups

  • Why hybrid rather than pure vector? — Embeddings are weak on exact tokens: order numbers, SKUs, surnames and error codes. Keyword search catches precisely what vectors blur.
  • What happens when you change the embedding model? — Every vector must be recomputed, so store the model version per row and support a dual-read during migration; teams that skip this discover it when quality silently degrades.
  • How does tenancy break here? — Through the retrieval filter. Vector similarity has no notion of permissions, so the filter must be enforced in the query — and tested, the same way object-level authorisation is.

Common wrong answer

"Put the documents in a vector database and query it." That is one component of five, and it omits the ones that determine quality and safety: chunking, hybrid retrieval, re-ranking, the tenancy filter, and treating retrieved text as data rather than as instructions to the model.

seniorYou are putting an LLM call on a user-facing path. What changes in your design?

Answer

I treat it as an unusually slow, unusually expensive, non-deterministic third-party dependency, and every one of those adjectives changes something. Slow: responses take seconds, so the interaction must stream — token by token to the user — and everything else runs on a strict timeout with a fallback, because a synchronous multi-second call inside a request path is a capacity problem. Expensive: cost is per token and scales with usage rather than with infrastructure, so I need per-tenant and per-user spend caps, a cheaper model for easy cases with escalation for hard ones, caching of identical or near-identical requests, and cost per request as a tracked metric. Non-deterministic: the output cannot be trusted structurally, so I constrain it — structured output or tool schemas — and validate before anything downstream consumes it, and I never let model output become an action without a check. Then the things that only appear in production: prompt injection through any user or retrieved content, which means treating that content as data and keeping privileged actions behind explicit authorisation; an evaluation suite with golden cases run in CI, because a prompt change is a deployment with no compiler; and versioning of prompt and model together, so a regression can be traced and rolled back like any other release.

Example

Treat it like any other dependency, with four extra columns

  latency        p50 2 s, p99 12 s   → stream tokens; hard timeout 20 s; fallback path
  cost           $/1k tokens         → per-tenant daily cap, cheap-model-first routing,
                                       response cache on normalised input, cost metric
  determinism    none                → structured output + schema validation before use;
                                       never execute model output directly
  trust          untrusted           → retrieved/user text is DATA; privileged tools
                                       require separate authorisation, not model intent

Ship it like code
  prompt + model version pinned and released together; changing either is a deploy
  golden-set evaluation in CI (accuracy, refusal rate, format compliance, cost/latency)
  canary a prompt change on 5% of traffic with the same analysis as any other release
  log input, retrieval ids, output and cost — evaluation and incidents both need them

Follow-ups

  • How do you test something non-deterministic? — A golden set with assertions on properties rather than exact strings (schema valid, contains the cited id, refuses when the answer is absent), plus a scored comparison against a baseline.
  • What is the failure mode people miss? — Silent quality regression: nothing errors, the output is just worse. Only an evaluation suite and user-feedback telemetry detect it.
  • Where does the model call belong architecturally? — Behind your own service, never called from the browser: keys, spend caps, redaction, logging and rate limits all live server-side.

Common wrong answer

"Call the API and return the response." It skips every property that makes the feature operable — timeout and fallback, spend caps, output validation, injection defence and evaluation — and the first incident is either a bill, a leaked instruction, or a quietly wrong answer shown to a customer.

17Migration and legacy modernisation

Lead and principal loops ask about migration because it is what the job usually is: very few senior hires design a system from nothing, and most inherit one that works, earns money, and cannot be stopped. The questions test sequencing, risk control and the ability to keep a business running while its foundations are replaced — plus the political skill of funding work whose value is invisible from outside engineering.

midHow do you replace a legacy system that cannot be switched off?

Answer

Incrementally, with a facade in front of both. The strangler-fig approach puts a routing layer — a reverse proxy, a gateway, or a thin service — in front of the legacy system so that every request passes through something I control. Then I move one capability at a time: build the replacement, route a small percentage of traffic to it, compare results, increase the percentage, and finally delete the legacy path for that capability. The routing layer is what makes each step reversible, which is the entire value: a bad migration step is a routing change back, not a rollback of a two-year programme. The order of capabilities matters — I start with something with real but bounded value and low coupling to prove the pattern and build confidence, not with the hardest core. The part that decides success is data: while both systems are live, either one owns the data and the other reads it, or you run a synchronisation with a defined direction. Two systems writing the same data with no owner is where these programmes fail.

Example

          ┌──────────── facade / routing layer (added first, changes nothing) ─────────┐
requests →│  /orders/*      → legacy  (100%)                                           │
          │  /catalogue/*   → new     (100%)   ← migrated, legacy path deleted         │
          │  /pricing/*     → new     (10%)    ← in progress, comparing outputs        │
          └───────────────────────────────────────────────────────────────────────────┘

Per capability
  1 route through the facade with no behaviour change   (prove the seam is safe)
  2 build the replacement; run in shadow mode: both execute, only legacy responds,
    outputs compared and differences logged            (finds the undocumented rules)
  3 ramp 1% → 10% → 50% → 100%, reversible at every step
  4 delete the legacy path — the step teams skip, which is why nothing ever shrinks

Data: one owner per entity at all times. If both must write, define direction and
      reconciliation explicitly, and treat divergence as an incident.

Follow-ups

  • What is shadow mode worth? — Enormous: it surfaces the undocumented behaviour that the legacy system encodes, which is the actual specification nobody wrote down.
  • How do you keep the facade from becoming permanent? — It often should be, as the API gateway; what must not be permanent is the dual implementation behind it.
  • What if the legacy system has no seams? — Create one at the edge (HTTP, or the database boundary) and accept a coarser first slice; the seam is the prerequisite, not an optimisation.

Common wrong answer

"Build the new system in parallel and cut over when it is ready." The big-bang rewrite: it takes longer than planned while the legacy system keeps changing, the two diverge, and the cutover is a single unrecoverable event with no partial value delivered until the end. It is the most reliably documented failure mode in the industry.

midA .NET Framework 4.8 application needs to move to modern .NET. How do you sequence it?

Answer

I do as much as possible before the port, because most of the risk is in the incompatible dependencies rather than in the language. First, an inventory with the upgrade assistant and API portability analysis to find what genuinely does not exist on modern .NET — typically WCF servers, WebForms, remoting, App Domains, and anything touching System.Web. Then the preparatory work that is safe on 4.8: migrate to SDK-style project files, move packages to PackageReference, replace HttpContext.Current and other ambient statics with injected abstractions, and target .NET Standard 2.0 for shared libraries so they can be referenced from both worlds. Then port bottom-up — libraries first, then the host — and choose the replacement for each blocker deliberately: WCF services become gRPC or HTTP APIs (or CoreWCF if the contract must stay), WebForms becomes MVC/Razor Pages or a separate front end, and System.Web-dependent code moves to ASP.NET Core middleware. If it is a large application I do not do it in one branch: I put a proxy in front and migrate route by route, which turns a single terrifying release into a series of ordinary ones. The target is the current LTS, .NET 10, released November 2025 — and the reason to move is not novelty but that Framework 4.8 receives only security fixes and every modern library, tooling and hosting improvement now assumes modern .NET.

Example

Sequence (each step ships independently)
  0 inventory      .NET Upgrade Assistant + dependency scan; list the true blockers
  1 on 4.8         SDK-style projects, PackageReference, remove ambient statics
                   (HttpContext.Current, ConfigurationManager, AppDomain)
  2 on 4.8         extract shared logic to .NET Standard 2.0 libraries — referenced by BOTH
  3 port           libraries → workers → web host, bottom-up
  4 blockers       WCF server  → gRPC / HTTP API (or CoreWCF to keep the contract)
                   WebForms    → Razor Pages / MVC, or a JS front end + API
                   System.Web  → ASP.NET Core middleware
  5 cut over       YARP in front; migrate route by route; both hosts live during the move
  6 target         .NET 10 (LTS, 2025-11-11) — not an interim version

Do not combine with a redesign. One variable at a time, or you cannot attribute a regression.

Follow-ups

  • What surprises teams most? — Behavioural differences rather than compile errors: default JSON serialisation, culture and encoding defaults, and configuration binding semantics.
  • Should you rewrite while porting? — No. Port first, keeping behaviour identical, then refactor; combining them makes every regression ambiguous.
  • What if a blocker has no replacement? — Keep that component on Framework behind the proxy and migrate the rest; a hybrid deployment is a legitimate long-term state.

Common wrong answer

"Retarget the projects to .NET 10 and fix the compile errors." It works for a small library and fails for an application, because the hard parts are the missing subsystems and the behavioural differences that compile perfectly and behave differently in production.

seniorMove a 4 TB production database to a new engine with no downtime. Plan it.

Answer

Five phases, each reversible until the last. First, dual-write preparation: the application writes through an abstraction so a second target can be added without touching business code. Second, backfill: copy historical data in chunks with a resumable checkpoint, throttled so it does not affect production, which for terabytes runs for days and must survive restarts. Third, change data capture keeps the target current from the point the backfill started, so the two converge rather than the copy going stale. Fourth, verification: run reads against both and compare — row counts, checksums per partition, and a sampled field-level comparison — and expect real differences from type mapping, collation, time zones and floating point, which is exactly what this phase exists to find. Fifth, cut over reads first, gradually, with the old system still authoritative and easy to switch back to; then cut over writes, which is the one irreversible step, done during a low-traffic window with a rehearsed rollback and a short freeze if needed. I keep the old system readable for weeks afterwards, because the problems you find on day three are the ones nobody predicted.

Example

Phase                          Duration   Reversible?   Key risk
1 write abstraction in code     1-2 wk     yes           none — pure refactor
2 backfill (chunked, throttled) 3-10 d     yes           lag on the source; checkpointing
3 CDC keeps target current      ongoing    yes           schema drift between the two
4 dual-read verification        1-2 wk     yes           real diffs: collation, types,
                                                         time zones, rounding, NULL order
5a cut over READS (1%→100%)     1 wk       yes           latency/plan differences
5b cut over WRITES              1 window   NO            the only irreversible step

Verification is the phase people shorten and the one that finds the bugs
  count(*) per table · checksum per partition · sampled field-level comparison
  application-level: run the same query on both and diff the response payloads

After: keep the old system readable and in sync for 2-4 weeks. Do not delete early.

Follow-ups

  • What differs most between engines? — Collation and sort order, date/time semantics and time-zone handling, numeric precision, identity/sequence behaviour, and NULL ordering — all of which change query results, not just performance.
  • Do you need a write freeze? — A short one for the write cutover is honest and usually acceptable; claiming a truly zero-downtime write cutover normally hides an unresolved consistency question.
  • What about the query plans? — Expect regressions: different optimisers make different choices, so the dual-read phase must compare latency per query shape, not only correctness.

Common wrong answer

"Dump, restore, and point the connection string at the new database." For 4 TB the dump alone takes hours during which writes continue, so the restored copy is stale before it starts — and there is no verification, no gradual cutover and no way back once the application has written to the new engine.

seniorYou are extracting the first service out of a monolith. Which one, and how?

Answer

I pick a component with a real pressure behind it and the fewest data entanglements — usually something at the edge of the domain with a different scaling profile or a different release cadence, such as notifications, document generation, or a public integration surface. What I avoid first is the core aggregate everything joins to, because extracting it means untangling every foreign key in the system in the first attempt. The method is: establish the module boundary inside the monolith first, so all access goes through an interface and no other code touches its tables; verify that boundary holds by moving the module's tables into their own schema and revoking access; and only then deploy it as a separate process, replacing the in-process call with a network call. That sequence means the risky part — the boundary — is proven while a rollback is trivial. The data question decides the difficulty: the new service owns its tables, and anyone who needs its data gets it via API or via events, which usually means replacing a few joins with denormalised copies. I also set the exit criteria in advance: if the extraction does not deliver the independent deployment or scaling it promised, that is evidence against extracting the next one.

Example

Choosing the first extraction (score candidates honestly)
  notifications      few joins · different scaling · low correctness risk   ← good first
  document/PDF gen   CPU-bound, spiky, isolated                            ← good first
  reporting/exports  read-only, heavy, separate SLO                        ← good first
  orders/customers   joined to everything, transactional core              ← NOT first

Method (each step independently revertible)
  1 module boundary in-process: one interface, no other code touches its tables
  2 move its tables to their own schema; revoke cross-schema access → CI fails on violation
  3 replace remaining joins with API calls or an event-fed local copy
  4 deploy as a separate process; the in-process interface becomes an HTTP/gRPC client
  5 measure against the reason you did it (deploy independence? scaling? isolation?)

If step 2 is impossible, the boundary is not real — stop, and fix the coupling first.

Follow-ups

  • What if other code needs the extracted service's data in a join? — Either the join belongs inside the service (call it), or the consumer keeps an event-fed read model. Both are more work than a join, and that cost is part of the decision.
  • How do you know the extraction succeeded? — The two deploy independently and neither release blocks the other; if they always ship together, the boundary was cosmetic.
  • Should the new service share the database temporarily? — It is a common transitional step and it must be temporary and dated, because a shared database is the coupling you were removing.

Common wrong answer

"Start with the core domain, because that is where the value is." It is also where every foreign key, every transaction and every invariant lives. Failing on the first extraction usually ends the whole programme, so the first one is chosen to succeed.

principalYou inherit a system that works but is unmaintainable. How do you fund and sequence the fix?

Answer

By translating the engineering problem into business terms and then buying the modernisation with delivery rather than with a separate budget. First I measure what "unmaintainable" costs: lead time for a typical change, change failure rate, incident frequency and hours, onboarding time, and the specific features the business asked for and did not get. Those numbers turn "the code is bad" — which no executive can act on — into "a two-day change takes six weeks and one in four releases causes an incident", which they can. Then I sequence by pain rather than by architectural purity: fix the deployment and rollback path first because it makes everything else safer and shows a result in weeks, then observability so problems are diagnosable, then the highest-churn areas, because effort spent on code nobody touches returns nothing. Crucially I attach the work to features: every roadmap item that touches a bad area pays for improving that area, so modernisation is continuous and does not need a separate approval each time. I would ask for one dedicated slice — a quarter, a small team — only for a specific structural change with a defined end, never as an open-ended "cleanup". And I publish the metrics monthly, because the programme survives on evidence that it is working.

  Q4+ boundaries and extraction        only where a pressure justifies it

Funding model
  80%  attached to feature work in the same area ("we touch it, we improve it")
  20%  a standing allowance, defended by the metrics above
  one-off dedicated slice only for a specific structural change with a defined end

Follow-ups

  • What if leadership will not fund any of it? — Start with what needs no permission: deployment, tests and observability inside the team's own work, then show the metric change. Evidence buys the next conversation.
  • How do you avoid the second-system trap? — No parallel rewrite, no architecture that only exists in a document, and every step must deliver a working improvement to the running system.
  • How do you keep the team motivated? — Sequence for early visible wins and make the metrics theirs; a two-year programme with no result until the end loses its people long before it finishes.

Common wrong answer

"We need a technical-debt sprint every quarter." It is the first thing dropped when a deadline appears, it treats the problem as episodic rather than structural, and it has no measurable outcome attached — so after two cancelled sprints, nobody proposes a third.

18Judgment calls

These have no single right answer, and interviewers ask them precisely because the reasoning is the signal. They appear as "what would you do if…", as a challenge to something you just proposed, or as a disagreement the interviewer stages to see whether you hold a position under pressure. The hidden part of each block says what a strong answer demonstrates at the top of the IC ladder and which trade-offs a principal candidate names without being prompted.

seniorThe team wants to introduce Kubernetes. You have four engineers and one product. What do you say?

What a strong answer demonstrates

That you evaluate operational cost against team capacity rather than against technical merit, and that you can say no without dismissing the motivation. The strong version asks what problem it solves today — multi-environment consistency, autoscaling, bin-packing cost — and then compares against a managed container platform that provides most of it with a fraction of the operational surface. It names the real cost: cluster upgrades, networking, RBAC, storage classes, and an on-call rotation that must now understand all of it, on a team of four. It also acknowledges the legitimate pull (portability, ecosystem, hiring) and offers a path: containerise now, which is the portable part, and defer the orchestrator until the constraint that needs it exists.

Trade-offs to name unprompted

  • Operational surface versus flexibility — a managed platform trades control for a smaller thing to run.
  • Team capacity as a first-class constraint: four engineers cannot carry a cluster and a product roadmap.
  • Lock-in is real but usually overstated; the container image is the portable asset, not the manifests.
  • Career motivation is legitimate and should be addressed openly rather than argued away.
  • The reversal trigger: name what would change your mind — several services, real bin-packing savings, or a platform team.
seniorShip on time with a known scaling ceiling, or delay six weeks to do it properly?

What a strong answer demonstrates

That you reason about the cost of being wrong in each direction rather than defaulting to either craftsmanship or speed. The strong version asks when the ceiling is actually reached given the real growth forecast — if it is eighteen months away, ship; if it is at the launch spike, that is not a ceiling, it is a defect. It then asks whether the shortcut is reversible: a missing index is a day's work later, while a wrong partition key with production data is a migration project, and those two deserve opposite answers. It names what makes shipping safe — a documented ceiling with a monitored metric and an alert well before it, plus a written plan for the fix — so the decision is deliberate rather than forgotten.

Trade-offs to name unprompted

  • Reversibility is the deciding axis, not effort: cheap-to-fix-later beats correct-and-late.
  • Time-to-market has real value — six weeks of learning from users often outweighs the rework.
  • Undocumented shortcuts become permanent; the mitigation is a metric and an alert, not a promise.
  • Opportunity cost of the six weeks: what does the team not build?
  • Who carries the risk — if it is the on-call team rather than the person deciding, say so.
seniorA senior engineer's design is workable but not what you would do. How do you handle it in review?

What a strong answer demonstrates

That you distinguish between "wrong" and "different", and that you understand your influence changes the conversation. The strong version separates the three categories explicitly: things that are unsafe or irreversible (data model, security, public contracts), where you insist and say why; things that are genuinely a matter of taste, where you defer and say so out loud, because a lead who wins every stylistic argument stops getting real proposals; and things you are simply unsure about, where you ask questions rather than assert. It also shows awareness that a principal engineer's stated preference is heard as a decision, so preferences must be labelled as preferences. The best answers mention writing the disagreement down — an ADR with the alternatives — so the reasoning survives whichever way it goes.

Trade-offs to name unprompted

  • Team autonomy and ownership versus consistency and your own judgment.
  • The asymmetry of seniority: your suggestion is not received as a suggestion.
  • Cost of being wrong — insist where the mistake is expensive and hard to reverse, defer elsewhere.
  • Disagree and commit is a real option, and saying it explicitly is stronger than silent acquiescence.
  • Written decisions outlive the argument and prevent relitigating it every quarter.
principalBuy or build? The team wants to build an internal feature-flag service.

What a strong answer demonstrates

That you evaluate total cost of ownership over years rather than the initial build estimate, and that you know which questions actually decide it. The strong version asks whether this is a differentiator (build) or a commodity (buy), what the multi-year operational cost is including on-call and the features you will inevitably need — targeting, audit, SDKs for every language, an evaluation path that survives the provider being down — and what happens when the person who built it leaves. It also names the genuine reasons to build: data residency or compliance constraints, a cost curve that breaks at your scale, or a requirement no vendor meets. And it names the hybrid: adopt an open-source implementation you self-host, which is often the honest middle. Strong candidates also mention the exit — how hard it is to leave the vendor — because that is what "lock-in" should mean concretely.

Trade-offs to name unprompted

  • Build cost is the small part; the multi-year maintenance and on-call cost is the decision.
  • Opportunity cost — the same engineers could be building the product's differentiator.
  • Vendor risk: pricing changes, acquisition, deprecation — mitigated by a thin abstraction and a documented exit.
  • Compliance and residency can legitimately override the economics.
  • The bus factor of an internal tool with one enthusiastic author.
principalProduct wants a feature that will make the system meaningfully harder to operate. How do you decide?

What a strong answer demonstrates

That you do not treat operability as a veto or as a tax to be silently absorbed, but as a price to be quoted. The strong version quantifies: this feature adds a stateful component, an extra on-call surface and roughly this much recurring cost, and here is the cheaper version that delivers most of the user value. It offers options rather than a refusal — full version, reduced version, or a manual/assisted version to validate demand first — and lets the business choose with the cost visible. It also names the conditions that would make the full version right later, so the answer is "not yet, and here is the trigger" rather than "no". Underneath, it shows that the engineer understands the product's goal well enough to propose an alternative that meets it, which is what separates a principal from a gatekeeper.

Trade-offs to name unprompted

  • Recurring operational cost versus one-off build cost — the former is what compounds.
  • Complexity is paid by whoever is on call, and often not by the team that shipped it.
  • A cheaper 80% version that validates demand before the expensive 100% version exists.
  • Reversibility: can this be withdrawn if it is not used, or does it become permanent surface area?
  • The counterfactual — what does not get built because this does.
principalTwo teams need conflicting things from one shared service. How do you resolve it?

What a strong answer demonstrates

That you look for the structural cause rather than mediating the symptom. The strong version first asks whether the conflict is about capacity (solvable with quotas, isolation or priority), about the roadmap (solvable with ownership and a published backlog), or about the boundary itself — because a service that two teams keep pulling in opposite directions usually has a boundary in the wrong place, and the real fix is a split or a clearer ownership model. It names the escalation path and, importantly, who decides, because "we will align" without a decider means the conflict recurs monthly. Strong answers also mention the option of letting one team fork or own their own copy when the shared abstraction is costing more than the duplication would, which is an unfashionable but frequently correct call.

Trade-offs to name unprompted

  • Shared service efficiency versus team autonomy and delivery speed.
  • Duplication is sometimes cheaper than the wrong abstraction — say it explicitly.
  • An owner with a published roadmap beats a committee; a service owned by everyone is owned by no one.
  • Contribution model: can the requesting team contribute the change under the owner's review?
  • Whether the conflict is really about Conway's law — the boundary versus the org chart.
principalHow much consistency do you enforce across teams before it becomes bureaucracy?

What a strong answer demonstrates

That you distinguish between things that must be uniform because they cross boundaries and things that only affect one team. The strong version enforces a small set — observability and correlation, security and identity, deployment and rollback capability, contract compatibility — because those determine whether the system can be operated and debugged as a whole. Everything else, including internal architecture, testing style and library choices, belongs to the team. It emphasises enforcement through tooling and templates rather than review boards: make the compliant path the easy path, put the few hard rules in CI, and let deviation be allowed but recorded. And it names the failure modes on both sides — chaos, where every service is a novel operational problem, and paralysis, where a review queue makes the platform team the bottleneck for everyone.

Trade-offs to name unprompted

  • Autonomy accelerates teams; uniformity accelerates operations and mobility between teams.
  • Golden path over mandate — deviation allowed, but it costs work and must be recorded.
  • Enforcement in CI and templates scales; enforcement by review does not.
  • Every standard has a maintenance cost; a standard nobody updates becomes an obstacle.
  • Measure adoption rather than compliance: if teams avoid the platform, the platform is wrong.
principalYou disagree with a decision your director has already announced. What do you do?

What a strong answer demonstrates

Judgment about when and how to escalate, and an understanding that being right is not sufficient. The strong version first checks whether the disagreement is about facts the director may not have (in which case supply them privately, quickly, and in their terms — cost, risk, timeline), about values or priorities (in which case it is their call), or about a genuine safety or ethical problem (in which case escalation is obligatory and the tone should be factual, not adversarial). It distinguishes reversible decisions, where committing and gathering evidence is usually better than fighting, from irreversible ones, where the case must be made now and in writing. It also shows awareness of the audience: the objection is delivered privately first, and publicly only if the private path fails and the stakes justify it.

Trade-offs to name unprompted

  • Reversibility again: commit and measure for reversible decisions, escalate for irreversible ones.
  • The cost of being right too loudly — organisational capital is finite and spending it has a price.
  • Disagree and commit is a real, honourable outcome, not a defeat.
  • Translation: framing the objection in cost, risk and timeline rather than in engineering aesthetics.
  • Documenting the concern once, factually, so the record exists without relitigating it.
principalWhen is "good enough" architecture actually good enough?

What a strong answer demonstrates

That you have a defensible standard rather than either perfectionism or resignation. The strong version defines good enough as: it meets the current requirements with headroom for the realistic growth horizon, its failure modes are known and bounded, it can be changed by someone who did not write it, and the decisions that are hard to reverse have been made deliberately. Everything else — elegance, symmetry, future-proofing for scenarios nobody has committed to — is optional. It names the specific asymmetry: over-engineering costs delivery speed now and is usually invisible in incident reports, while under-engineering shows up as incidents and rewrites, so the two errors are not symmetric and should not be weighted equally. And it holds the line on the few things that must be right the first time, because those are the ones "good enough" cannot include.

Trade-offs to name unprompted

  • YAGNI versus irreversibility: skip the speculative feature, not the partition key.
  • Growth horizon as an explicit parameter — 10× is a design target, 1000× is usually fantasy.
  • Comprehensibility is a first-class quality attribute; clever architecture nobody understands is a liability.
  • Over- and under-engineering fail differently and are noticed differently, which biases teams.
  • Good enough is a decision with a review date, not a permanent state.
principalThe system you inherited makes a trade-off you would not have made. Do you change it?

What a strong answer demonstrates

Humility with a bias toward evidence. The strong version starts by assuming the original decision was rational given information you do not have — Chesterton's fence — and goes looking for that context in commit history, incident records, ADRs and the people who were there. Then it tests whether the constraint still holds, because most inherited oddities are correct answers to a question that has since changed. Only then does it evaluate the cost of changing against the cost of living with it, including the risk that the replacement recreates the original problem in a new form. Crucially, it does not confuse "I would have done it differently" with "this is wrong", and it recognises that changing a working system to match personal preference is one of the most expensive things a new senior hire can do.

Trade-offs to name unprompted

  • Unknown context is the default assumption, not incompetence.
  • Cost of change includes risk and lost delivery, not just engineering hours.
  • Team trust: an early rewrite of someone's work is read as a judgment on them.
  • Some constraints have expired and some have not — verify rather than assume either way.
  • If you do change it, say why in writing, so the next person inherits your reasoning too.

19Design exercises

Three full exercises that connect this topic to a whiteboard session. Each gives the prompt as an interviewer would, the clarifying questions worth asking in the first five minutes, and — in a collapsed block, so you can attempt it first — a strong solution outline plus the trade-offs you are expected to raise without being asked. Work them on paper with a timer; the value is in producing the structure under time pressure, not in reading the answer.

Exercise A — Multi-tenant B2B invoicing platform

Prompt

"Design a SaaS invoicing platform for small businesses. Customers create invoices, send them to their clients, and get paid through an integrated payment provider. There is a web application and a public API for integrations. Assume 20,000 business customers, growing to 100,000, with a handful of very large customers processing thousands of invoices a day."

Clarifying questions to ask

  • Money and correctness — Is an invoice immutable once sent? What is the audit requirement, and how long is retention?
  • Tenancy and residency — Do any customers require their data in a specific region or a dedicated database?
  • Payments — Do we hold card data (hopefully not), and are we responsible for reconciliation with the provider?
  • Load shape — Is invoicing spiky (month-end)? That decides capacity far more than the average.
  • Public API — How many integrators, and can we change the contract? That decides how much versioning discipline is needed.

Solution outline

Shape: modular monolith (ASP.NET Core, .NET 10) + workers; split only under pressure
  modules  Invoicing · Payments · Notifications · Integrations(public API) · Reporting
  data     PostgreSQL 18, one schema per module, row-level security on tenant_id
  tenancy  shared tables + tenant directory → whales/regulated move to their own database
           without an application change (the directory is the seam, built on day one)

Write path (invoice send — the correctness-critical flow)
  1 invoice becomes immutable on send; corrections are credit notes, never edits
  2 numbering is per-tenant and gapless → a sequence table with a row lock per tenant,
    NOT a global identity (legal requirement in many jurisdictions; also a hotspot to name)
  3 the send is a saga: render PDF → store in object storage → email → record delivery
    each step idempotent, keyed by invoice id; failures are visible states on the invoice
  4 outbox in the same transaction publishes InvoiceSent for notifications/reporting

Payments
  hosted fields / redirect at the provider → no card data in scope
  provider webhooks are the source of truth for payment state, verified by signature,
  deduplicated by event id, and idempotent (they WILL be delivered more than once)
  a nightly reconciliation job compares our ledger with the provider's; drift = an alert

Money handling
  minor units as integers + currency code; never floating point
  an append-only ledger table for every state change (audit is a requirement, not a bonus)

Reads and reporting
  read replica for dashboards; materialised revenue-by-day-by-tenant refreshed hourly
  month-end spike: batch PDF rendering and emailing through the queue, per-tenant fairness

Public API
  /api/v1 in the path, ProblemDetails errors, idempotency keys on POST,
  keyset pagination, per-tenant rate limits, OpenAPI 3.1 published from the code

Ops
  canary deploys, expand/contract migrations, per-tenant metrics, PITR + rehearsed restore

Trade-offs to name unprompted

  • Modular monolith over microservices — one product, one team-sized system; the module boundary and the tenant directory keep extraction cheap when a pressure appears.
  • Shared tables with RLS versus database-per-tenant — cost and operability now, with a proven migration path for the large or regulated customers rather than a choice made once for everyone.
  • Gapless per-tenant numbering is a deliberate hotspot — it serialises sends per tenant; that is legally required and it is the right place to spend contention, but say it out loud.
  • Immutability plus credit notes over editable invoices — simpler audit and no update anomalies, at the cost of a UX that must explain corrections.
  • Webhooks as the payment source of truth — the provider is authoritative; our state is a projection, and reconciliation is mandatory, not optional.
  • Month-end peak, not average — capacity, queue depth and fairness are designed for the spike; per-tenant fairness stops one large customer starving the rest.

Exercise B — Product page read path for a high-traffic storefront

Prompt

"Design the read path for the product detail page of a large e-commerce site. Ten thousand requests per second at peak, global audience, and the page shows price, stock availability, reviews and recommendations. Stock must not be wrong in a way that lets customers buy things we do not have. It must render fast on a mid-range phone and rank well in search."

Clarifying questions to ask

  • Freshness per element — How stale may price be? Stock? Reviews? These almost certainly differ, and that difference is the design.
  • Personalisation — Is any part of the page per-user? If yes, it must be split out or the whole page becomes uncacheable.
  • Catalogue size and change rate — 10k products or 10M? How many price changes per minute?
  • Overselling — Is it a hard failure, or acceptable with a cancellation flow? Retailers differ, and it changes the architecture.
  • Geography — Is stock regional? Global stock and regional stock are different problems.
seniorShow a strong solution outline and the trade-offs I should name unprompted

Solution outline

Split the page by freshness — this is the whole answer

  shell + description + images   changes rarely   → static/ISR at the CDN, TTL hours,
                                                    purged by surrogate key on publish
  price                           seconds-minutes  → server-rendered into the page,
                                                    edge TTL 60 s + purge on price change
  stock                           near-real-time   → NOT in the cached HTML; a small
                                                    client fetch to a stock endpoint,
                                                    cached 5-10 s, served from a region-local
                                                    read model fed by CDC from inventory
  reviews                         minutes-hours    → cached fragment, TTL 15 min
  recommendations                 best effort      → async, optional, static fallback

Delivery
  server-rendered shell (React Server Components / Next.js 16) at the edge,
  hydrating only the interactive islands; images AVIF/WebP, sized, hero preloaded
  budget: ≤170 KB initial JS/route, LCP ≤2.5 s p75 on mid-range Android — enforced in CI

Origin
  ASP.NET Core product-page BFF: one call returns the composed view model
  HybridCache (L1 20 s in-process, L2 Redis/Valkey 5 min), tag invalidation per product
  read model = denormalised product document, kept in sync by CDC from the catalogue
  origin sized for the must-survive paths at a realistic cold-cache miss rate

Correctness on stock — the part that must not be hand-waved
  the product page is ADVISORY: "in stock" is a hint with a staleness of seconds
  the AUTHORITATIVE check is a reservation at add-to-cart / checkout, single-writer
  per SKU, transactional, with a short TTL on the reservation
  overselling is therefore bounded by design, not by cache freshness

Failure behaviour
  stock endpoint down → show "check availability at checkout", never block the page
  reviews/recommendations down → omit the section, log the fallback, page still renders
  cache cold → origin serves at reduced payload under load shed; ramp traffic on recovery

Trade-offs to name unprompted

  • Cacheability versus freshness, decided per element — one TTL for the whole page forces the strictest element's freshness onto everything and destroys the hit ratio.
  • Advisory display, authoritative reservation — the only honest way to have a fast cached page and no meaningful overselling; naming this distinction is the point of the exercise.
  • Edge rendering versus origin cost — SSR at the edge improves latency and SEO but is compute per request; static plus a small dynamic fetch is cheaper where it is acceptable.
  • Personalisation is quarantined — anything per-user is a separate private request, or the CDN hit ratio collapses to zero.
  • Cold-cache capacity is a stated assumption — the origin cannot serve 10k/s at 100% miss, so degradation and traffic ramping are part of the design, not an afterthought.
  • Client budget is a design constraint — a technically perfect back end behind a 900 KB bundle still loses the customer on a mid-range phone.

Exercise C — Telemetry ingestion and reporting at 50k events/second

Prompt

"Our product emits usage events from customer applications — 50,000 per second at peak, from tens of thousands of tenants. Customers want dashboards over their own data with a few minutes of latency, we want internal analytics over everything, and finance wants an accurate monthly usage number for billing. Design it."

Clarifying questions to ask

  • Billing accuracy — Is the billing number allowed to be restated, or must it be final when published? This is the hardest constraint in the prompt.
  • Retention — How long must raw events be kept, and is that a contractual or a regulatory number?
  • Loss tolerance — May we drop events under overload, and does the answer differ for billing events versus dashboard events?
  • Query shape — Are customer dashboards fixed views, or arbitrary ad-hoc queries? That decides whether pre-aggregation is enough.
  • Residency and PII — Do events contain personal data, and must EU tenants' events stay in the EU?
principalShow a strong solution outline and the trade-offs I should name unprompted

Solution outline

Sizing first (this drives every later decision)
  50k/s x 500 B ≈ 2.2 TB/day raw ≈ 790 TB/year
  Parquet + zstd (~8x) ≈ 100 TB/year → tiering is mandatory, not an optimisation

Ingest
  thin HTTP/gRPC collector: authenticate, validate shape, stamp receive_time,
  write to a partitioned log (Kafka), ack — nothing else on the hot path
  partition key = tenant_id  → per-tenant ordering, and per-tenant lag is visible
  client SDK: batch, compress, retry with jittered backoff, bounded local buffer
  overload: shed non-billing events first (priority classes), never block ingest on
  a downstream store

Three consumers off ONE log (this is why a log, not a queue)
  1 real-time rollups  → stream processor, event-time windows, 1-minute tumbling,
                         watermark -30 s, allowed lateness 5 min
                         → per-tenant aggregates in a serving store for dashboards
                         → contract: "counts may be restated for 5 minutes"
  2 raw archive        → Parquet in object storage, partitioned by day/tenant-bucket,
                         compacted hourly; the source of truth for reprocessing
  3 warehouse load     → columnar store for internal analytics; can lag hours

Billing — treated separately, because the constraint is different
  computed from the ARCHIVE, not from the real-time rollups, after a closing window
  (e.g. 24 h after month end), so late events are included and the number is final
  idempotent aggregation keyed by (tenant, period) so reruns are safe
  published as an immutable statement with the input watermark recorded

Customer dashboards
  pre-aggregated per tenant per minute/hour/day; ad-hoc drill-down against the warehouse
  with per-tenant row limits and query timeouts

Residency and privacy
  regional collectors and regional storage; PII stripped at the collector,
  pseudonymised identifiers only beyond the region

Operations
  alert on: ingest error rate, consumer lag AGE (not count), watermark lag,
  late-event rate, rollup-vs-archive reconciliation drift, cost per million events

Trade-offs to name unprompted

  • One log, three consumers — replayability is the reason to choose a log over a queue: a bug in the rollup is fixed by reprocessing, not by lost data.
  • Fast-and-restatable versus slow-and-final — dashboards get the first, billing gets the second; using one pipeline for both means either wrong invoices or useless dashboards.
  • Event time versus processing time — clients buffer and retry, so late events are normal; windowing on arrival silently corrupts every number.
  • Storage tiering is the cost decision — raw retention is the dominant line item, so retention length is a product decision with a price attached.
  • Shedding policy is explicit — under overload, dashboard events are dropped before billing events, decided in advance rather than during the incident.
  • Per-tenant fairness — one tenant emitting ten times the volume must not delay everyone else's dashboards; partitioning and quotas are part of the design.

20Night-before cheat sheet

The ten questions this bank's map says you are most likely to be asked, each with the one sentence that has to come out first. If you can say these ten cleanly and then go one level deeper on any of them, you will not be caught flat in the opening twenty minutes of a loop.

  1. How do you start a system design interview? Restate the problem, list functional requirements as user actions, pin the non-functionals as numbers (load, read/write ratio, latency percentile, availability, retention), state what is out of scope — then design against those numbers and refer back to them.
  2. SQL or NoSQL? Start from access patterns and consistency needs, not volume: relational unless a specific pattern rules it out, because modern engines have absorbed JSON, full text and vectors, and the cost of a second store is permanent.
  3. How do you scale reads? Index the query first, then cache at the layer closest to the user, then read replicas — and say which reads need read-your-writes, because that is what replicas break.
  4. What breaks when you add a cache? Invalidation and the cold start: delete keys on write rather than updating them, jitter the TTLs, rely on request coalescing for stampedes, and know whether the origin can survive 100% misses.
  5. You save to the database and publish an event — what if the publish fails? The transactional outbox: write the event in the same transaction as the data and let a relay publish at-least-once, with idempotent consumers; never a distributed transaction across a database and a broker.
  6. At-least-once or exactly-once? You get at-least-once, so every consumer is idempotent — a stable message id deduplicated in the same transaction as the effect, or an effect that is naturally idempotent.
  7. How do you handle a business transaction across services? A saga of local transactions with compensations, ordered so irreversible steps come last, every step idempotent and every step with a timeout — orchestrated when the flow matters, choreographed only for broadcast facts.
  8. What happens when a dependency fails? Timeout from the latency budget, bounded retry with jittered backoff for transients only, a circuit breaker and a per-dependency concurrency limit — and a defined fallback, because slow is worse than down.
  9. What do you page someone for? User-visible symptoms and SLO burn rate, never CPU or a single instance restart — every alert must be urgent, actionable and have a runbook.
  10. How do you deploy without downtime? Rolling or canary with both versions running simultaneously, which means expand/contract migrations and backward-compatible contracts, feature flags separating release from deploy, and a rollback that has actually been tested.

Two habits that score more than any fact. Put a number on everything — "p99 under 300 ms", "17k reads per second", "43 minutes of budget a month" — and name the trade-off before the interviewer asks for it. Almost every rejection at this level is written up as "described components, did not reason about trade-offs".
