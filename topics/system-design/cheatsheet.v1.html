System design (.NET full-stack)

cheatsheet · reference stack .NET 10.0.11 (LTS) · released 2026-08-11

The numbers, formulas, contracts, commands and failure modes reached for when designing or reviewing a distributed .NET system — capacity and SLO math, API and data decisions, caching, messaging, consistency, resilience, delivery topology, the browser tier, and the diagnostic commands that settle an argument. System design has no version of its own, so every row is anchored to the current stable stack it would be built on today: .NET 10.0.11 / EF Core 10 (LTS, GA 2025-11-11), PostgreSQL 18.x, SQL Server 2025, Redis 8.2 / Valkey 9.1, Kafka 4.2, Kubernetes 1.36, React 19.2 with Next.js 16.3. Rows carry a version marker where the answer changed recently; anything labelled .NET 11 or PostgreSQL 19 is still pre-GA on 2026-09-08 and is direction, not deployment.

01Napkin numbers & SLOs

docs: Google SRE, service level objectives
Latency ladder
L1 ~1 ns · main memory ~100 ns · NVMe read 50–100 µs · same-AZ RTT ~0.5 ms · cross-AZ ~1 ms · EU↔US-East ~80–100 ms · TLS 1.3 handshake 1 RTT
Little's Law
concurrency = throughput × latency — 2 000 rps × 50 ms = 100 requests in flight; that is your thread/connection/pod budget
Utilisation vs wait
wait ≈ service × ρ/(1−ρ) — at ρ=0.8 queueing is 4× service time, at 0.95 it is 19×. Design steady state at 60–70%
Service throughput anchor
1 vCPU ASP.NET Core pod: ~5–15k rps trivial JSON, ~1–3k rps cached, 100–500 rps DB-bound. Size from the DB, not the web tier
Availability budget
99.9% = 43m50s/month · 99.95% = 21m54s · 99.99% = 4m23s · 99.999% = 26s. Chained dependencies multiply: 4 × 99.9% = 99.6%
Error budget burn
budget = 1 − SLO. Multiwindow alert: 14.4× burn over 1h (2% of a 30-day budget), 6× over 6h, 1× over 3d
Tail amplification
a request fanning out to 10 backends sees roughly each backend's p99.9. Fan-out of 100 makes p99 of a dependency the common case
Storage math
1 KB row × 10M/day = 10 GB/day = 3.6 TB/yr; +25–40% for indexes, ×replicas, ×backup retention
Bandwidth math
1 Gbps = 125 MB/s ≈ 125k × 1 KB msgs/s. Cross-AZ and egress are billed — chatty service meshes show up on the invoice
Connection budget
DB pool ≈ cores × 2 + effective_spindles; Npgsql/SqlClient default Max Pool Size=100 per process — 40 pods × 100 = 4 000 connections, well past a stock Postgres max_connections=100
SLI shape
latency SLI = "% of requests < 300 ms", never "average latency". Percentiles do not average — aggregate histograms, not p99s
Cost per request
rough: (monthly infra) ÷ (rps × 2.6M). If a design cannot state cost per request, it cannot defend a cache or a region

Capacity in five lines (write these on the whiteboard, in this order):
  1. peak rps       = DAU × actions/day × peak_factor(3–10×) / 86 400
  2. concurrency    = peak rps × p50 latency            # Little's Law
  3. pods           = concurrency / per-pod concurrency + 30% headroom
  4. storage/yr     = rows/day × row bytes × 365 × 1.35 × replicas
  5. DB connections = pods × pool size  → must be < max_connections (use PgBouncer)

Say the number, then the unit of failure. "2 000 rps peak, 100 in flight, 6 pods, one AZ loss costs 33% capacity" beats any amount of box-drawing. Every quantity above is a claim you can be asked to defend — round aggressively and show the arithmetic.

02API & contract design

docs: minimal APIs · RFC 9457 Problem Details
Style choice
REST/JSON for public + browser · gRPC for internal chatty/streaming (HTTP/2, contract-first) · GraphQL only when clients genuinely differ in shape · webhooks + SSE for push out
Status codes that matter
201+Location · 202 for accepted-async · 409 conflict · 412/428 preconditions · 422 semantic validation · 429+Retry-After · 503+Retry-After on shed
Errors
builder.Services.AddProblemDetails(); → RFC 9457 application/problem+json with a stable type URI and a traceId; never a bare 500 string
Idempotency
client sends Idempotency-Key: <uuid>; server stores key → (status, body) for 24h and replays it. Mandatory for payments, retries and at-least-once callers
Optimistic concurrency
ETag + If-Match → 412; EF Core .IsRowVersion() / xmin on Postgres — catches lost updates without locks
Pagination
keyset: WHERE (created, id) < (@c, @id) ORDER BY created DESC, id DESC LIMIT 50, opaque cursor. OFFSET 100000 scans 100 000 rows every time
Versioning
additive-only inside a version; break = new major (/v2 or Asp.Versioning.Http). Never repurpose a field, never tighten validation in place
OpenAPI
AddOpenApi() + app.MapOpenApi() .NET 9, emits OpenAPI 3.1 by default with YAML at /openapi/v1.yaml .NET 10 — Swashbuckle is no longer the default template
Validation
builder.Services.AddValidation(); .NET 10 — data-annotation and IValidatableObject validation for minimal APIs, AOT-friendly, returns 400 + problem details
Long-running work
202 Accepted + Location: /operations/{id}, poll or webhook. Never hold an HTTP request open across a workflow
Bulk & chatty
batch endpoint or ?include= expansion beats 50 round trips at 1 ms cross-AZ; cap batch size and document partial-failure semantics (207-style per-item results)
Contract testing
consumer-driven contract or OpenAPI diff in CI; the schema is the deploy gate, not a wiki page
Payload rules
UTC ISO-8601 with offset · money as minor units or decimal string, never float · enums as strings · nullable ≠ absent · document the max page size
// Minimal API: validation, problem details, idempotency, optimistic concurrency, keyset paging.
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddProblemDetails();
builder.Services.AddValidation();                 // .NET 10: built-in minimal-API validation
builder.Services.AddOpenApi();                    // .NET 10: OpenAPI 3.1, JSON + YAML
var app = builder.Build();
app.MapOpenApi();

app.MapPost("/orders", async (CreateOrder cmd, [FromHeader(Name = "Idempotency-Key")] Guid key,
                              IOrders orders, CancellationToken ct) =>
{
    if (await orders.TryReplayAsync(key, ct) is { } prior) return prior;      // same key, same answer
    var id = await orders.CreateAsync(cmd, key, ct);
    return TypedResults.Created($"/orders/{id}", new { id });
});

app.MapGet("/orders", (DateTime? cursorAt, Guid? cursorId, IOrders o, CancellationToken ct) =>
    o.PageAsync(cursorAt, cursorId, size: 50, ct));                           // keyset, never OFFSET

app.MapPut("/orders/{id}", async (Guid id, UpdateOrder cmd,
                                  [FromHeader(Name = "If-Match")] string etag,
                                  IOrders o, CancellationToken ct) =>
    await o.UpdateAsync(id, cmd, etag, ct)
        ? Results.NoContent()
        : TypedResults.Problem(statusCode: 412, title: "Order was modified by someone else"));

03Data & storage

docs: PostgreSQL 18 · docs: what's new in EF Core 10
Pick the store
relational OLTP (Postgres 18 / SQL Server 2025) is the default · KV/cache (Redis 8.2, Valkey 9.1) · log (Kafka 4.2) · blob + CDN for files · search (OpenSearch) · columnar (ClickHouse) for analytics · one exotic store per design, justified
Primary keys
Guid.CreateVersion7() .NET 9 / uuidv7() PG 18 — time-ordered, so inserts stay at the right edge of the B-tree; random v4 GUIDs fragment the index and bloat WAL
Index rule of thumb
composite order = equality, then range, then sort; add INCLUDE columns to make it covering; every FK used in a delete/join needs one
Isolation defaults
Postgres: Read Committed (MVCC, readers never block). SQL Server: Read Committed with locks — turn on ALTER DATABASE db SET READ_COMMITTED_SNAPSHOT ON; or live with blocking
Write skew
only SERIALIZABLE stops it (PG uses SSI and throws 40001 — the app must retry); the cheaper fix is a unique constraint or an explicit SELECT … FOR UPDATE
Online DDL
CREATE INDEX CONCURRENTLY · ADD COLUMN … NOT NULL DEFAULT is metadata-only PG 11+ · ALTER TABLE … ADD NOT NULL … NOT VALID then VALIDATE without a full scan PG 18 · always SET lock_timeout first
Schema change dance
expand → backfill → dual-write/dual-read → contract, each a separate deploy. A migration that must ship with its code is an outage waiting for traffic
EF Core 10 essentials
LeftJoin(…) instead of GroupJoin/SelectMany/DefaultIfEmpty · complex types mapped to a JSON column and queried in LINQ · ExecuteUpdateAsync(s => s.SetProperty(…)) now takes a plain lambda EF 10
EF read path
AsNoTracking() on every query you do not save · AsSplitQuery() when two collection includes multiply rows · projections (Select) over full entities · compiled models for cold start
Connection pooling
PgBouncer in transaction mode (no session state, no prepared statements unless PgBouncer 1.21+) or Npgsql multiplexing; Pooling=true;Max Pool Size=… tuned per pod, not per developer
Partition & shard
range-partition by time for retention (DETACH beats DELETE); shard only when one node's write path is the wall — pick a key with no hot tenant, and plan resharding before the first shard
Replicas & lag
read replicas serve reports, not read-your-writes; route a user to the primary for N seconds after their write, or read from the write's returned snapshot/LSN
Vector / hybrid search
pgvector with HNSW index inside the OLTP DB, or SQL Server 2025 native vector type + VECTOR_DISTANCE() (type GA, DiskANN index still preview) 2025-11-18 — a separate vector DB is now the exception
Retention & PII
state a retention per table on day one; PII in a separate schema with crypto-shredding keys makes "delete me" a key drop, not a table scan
-- Keyset page + covering index: the two things that keep a list endpoint flat as data grows.
CREATE INDEX CONCURRENTLY ix_orders_customer_created
  ON orders (customer_id, created_at DESC, id DESC) INCLUDE (status, total_cents);

SELECT id, status, total_cents, created_at
FROM orders
WHERE customer_id = $1 AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 50;

-- Read your own write without pinning every read to the primary.
SELECT pg_current_wal_lsn();                    -- on the primary, after commit
SELECT pg_last_wal_replay_lsn() >= $1;          -- on the replica, before serving

04Caching layers

docs: HybridCache · RFC 9111 HTTP caching
The five layers
browser → CDN/edge → output cache (per response) → in-process L1 → distributed L2 (Redis/Valkey) → DB buffer pool. Name which one you mean before arguing about invalidation
Default choice
builder.Services.AddHybridCache(); .NET 9 — L1 memory + L2 IDistributedCache, stampede protection built in, tag invalidation via RemoveByTagAsync. Replaces the hand-rolled IDistributedCache + double-check pattern
Output caching
AddOutputCache() + .CacheOutput(p => p.Expire(TimeSpan.FromSeconds(30)).Tag("orders")) .NET 7, server-side and invalidatable — unlike the older client-driven ResponseCaching middleware
Patterns
cache-aside (default, explicit) · read-through (inside the client library) · write-through (consistent, slower writes) · write-behind (fast, loses data on crash — needs a durable buffer)
TTL and jitter
TTL plus ±10–20% random jitter, always. Identical TTLs set at deploy time expire together and hand the database a synchronised stampede
Stampede control
single-flight per key (HybridCache does this), plus stale-while-revalidate: serve the stale value and refresh in the background rather than blocking N callers
Invalidation
prefer TTL plus event-driven eviction on the write path; version the key (order:v3:{id}) to invalidate a whole shape at deploy; tags for cross-cutting groups. Never KEYS-scan to invalidate
Negative caching
cache 404 and empty results for 5–30 s or a missing-key flood becomes a database scan; keep the TTL short so a later creation is not shadowed
HTTP headers
Cache-Control: public, max-age=60, stale-while-revalidate=300 for shared data · private, no-store for anything per-user · ETag + If-None-Match → 304 · always set Vary when content negotiates
Static assets
content-hashed filenames + Cache-Control: public, max-age=31536000, immutable; app.MapStaticAssets() .NET 9 does the fingerprinting, pre-compression and headers at build time
Redis / Valkey commands
SET k v EX 60 NX (set-if-absent lease) · SCAN 0 MATCH order:* COUNT 500 — never KEYS in production · INFO stats for keyspace_hits/misses · SLOWLOG GET 10 · redis-cli --latency-history
Eviction policy
maxmemory-policy allkeys-lru for a pure cache; noeviction if the instance also holds queues or sessions — one instance doing both is the design smell
Hit-rate math
90% at 1 ms + 10% at 50 ms = 5.9 ms mean, but the p99 is still the miss path. A cache moves the mean; only capacity moves the tail
What not to cache
anything you cannot afford to serve stale (balances, permissions, stock at checkout), and anything cheaper to compute than to fetch over the network
// One call: L1 + L2, single-flight per key, tag-based invalidation. .NET 9+
public sealed class Orders(HybridCache cache, IOrderRepo repo)
{
    public ValueTask<Order> GetAsync(Guid id, CancellationToken ct) =>
        cache.GetOrCreateAsync($"order:v3:{id}",
            factory: async token => await repo.LoadAsync(id, token),
            options: new HybridCacheEntryOptions
            {
                Expiration = TimeSpan.FromMinutes(5),           // L2, distributed
                LocalCacheExpiration = TimeSpan.FromSeconds(20) // L1, bounds per-node drift
            },
            tags: ["orders", $"customer:{id}"], cancellationToken: ct);

    public ValueTask InvalidateCustomerAsync(Guid customerId, CancellationToken ct) =>
        cache.RemoveByTagAsync($"customer:{customerId}", ct);
}

05Messaging & workflow

docs: Apache Kafka · pattern: transactional outbox
Queue or log?
broker queue (Azure Service Bus, SQS, RabbitMQ): competing consumers, per-message ack, native DLQ, scheduled delivery. Log (Kafka): ordered partitions, replay from an offset, many independent readers, retention as a feature
Kafka today
4.0 removed ZooKeeper — KRaft only 2025-03-18; share groups (KIP-932) give per-message, queue-style consumption on a topic and reached production-ready Kafka 4.2, 2026-02-17, so "we also need a separate queue broker" is a weaker argument than it was
Delivery semantics
at-least-once is what you get. "Exactly once" in practice = at-least-once + an idempotent consumer. Kafka EOS transactions hold only inside Kafka — the moment you write to SQL you are back to idempotency
Outbox
write the row and the message in one database transaction; a relay publishes and marks it sent. The alternative is CDC (Debezium) off the WAL. Dual-writing to DB and broker loses messages on every crash in between
Idempotent consumer
INSERT INTO processed(msg_id) VALUES (@id) ON CONFLICT DO NOTHING in the same transaction as the effect; if it inserted 0 rows, skip. Prune the table by time
Ordering
partition or session key = the aggregate id (order id, tenant id). Ordering survives a retry only while it stays in the same partition — a retry topic or DLQ breaks it, deliberately
Poison messages
bounded retries with backoff, then DLQ (Service Bus MaxDeliveryCount, Kafka a *.DLQ topic). A DLQ with no alert and no replay tool is a data-loss queue
Backpressure
bound prefetch / max.poll.records / concurrent handlers; queue depth and consumer lag are the autoscaling signal (KEDA), not CPU
Sagas
choreography (events, no coordinator, hard to see) vs orchestration (MassTransit state machine, Dapr Workflow, Azure Durable Functions, Temporal). Every step needs a compensation, and compensations must be idempotent too
Schema evolution
a registry with backward compatibility (Avro, Protobuf, JSON Schema); add optional fields only, never renumber or repurpose. Consumers deploy before producers
In-process pipelines
System.Threading.Channels for bounded in-memory hand-off (BoundedChannelFullMode.Wait) drained by a BackgroundService. Fine inside a process, never a substitute for durability
Kafka sizing
partitions ≥ maximum consumers; treat ~10 MB/s as a comfortable partition; replication.factor=3, min.insync.replicas=2, acks=all for anything you cannot lose
Ops commands
kafka-topics.sh --create --partitions 12 --replication-factor 3 · kafka-consumer-groups.sh --describe --group billing (the LAG column) · --reset-offsets --to-datetime … --execute · kafka-configs.sh --alter --add-config retention.ms=…
// Outbox: one transaction, no dual write. The relay is the only thing that talks to the broker.

db.Orders.Add(order);
db.Outbox.Add(new OutboxMessage(
    Id: Guid.CreateVersion7(),                    // time-ordered id, so the relay scans in order
    Type: "order.placed.v1",
    Key: order.Id.ToString(),                     // partition key = aggregate id
    Payload: JsonSerializer.Serialize(evt)));
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);

if (first == 0) return;                           // already handled: ack and move on
await ApplyAsync(msg, ct);
await db.SaveChangesAsync(ct);

06Consistency & coordination

reference: Jepsen consistency models
PACELC beats CAP
if Partitioned, choose A or C; Else choose Latency or Consistency. The everyday trade-off is the "else" half — CAP only describes the bad day
The ladder
linearizable → sequential → causal → read-your-writes → monotonic reads → eventual. Name the level per use case: balance = linearizable, feed = eventual, profile edit = read-your-writes
Quorums
R + W > N for overlap (N=3, W=2, R=2). Losing a node then costs latency, not correctness; W=1 is a data-loss setting with a flattering p99
Distributed transactions
avoid 2PC across services — the coordinator failing blocks every participant's locks. Use a saga with compensations, or move the boundary so the transaction is local again
Locks and leases
every distributed lock needs a TTL and a monotonically increasing fencing token that the resource checks; without it a GC pause or a stalled pod produces two live writers
Leader election
Kubernetes Lease objects, blob-lease singletons, etcd or ZooKeeper. Single-writer-per-shard turns most consistency problems back into local ones
Clocks
NTP skew is milliseconds and unbounded during failure — never order events by wall clock. Use sequence numbers, LSNs, hybrid logical clocks, or the database's own ordering
Anomalies to name
lost update (fix: ETag/rowversion) · write skew (fix: SERIALIZABLE or a constraint) · phantom read · read-your-writes violation on a replica · duplicate effect from at-least-once delivery
Uniqueness at scale
a unique index is a distributed lock you already own. "Check then insert" across two services is a race — let the constraint fail and map 23505 / 2627 to 409
Event ordering
per-key ordering is achievable and usually enough; global ordering costs a single writer. Decide which one is required before choosing a broker
Convergence
last-write-wins loses data silently; prefer append-only plus a fold, or a CRDT (counters, sets, collaborative text) when offline or multi-region writes are a real requirement
Cross-region writes
one writable region with failover is the honest default; active-active makes conflict resolution a product decision, not a database setting

07Resilience & traffic control

docs: HTTP resilience (Polly v8) · docs: rate limiting middleware
Standard handler
services.AddHttpClient<T>().AddStandardResilienceHandler(); .NET 8 — rate limiter → total timeout → retry → circuit breaker → attempt timeout, in that order, on Polly v8 pipelines
Timeout budget
every hop gets a timeout, and a hop's retries must fit inside the caller's budget: a 1 s caller cannot afford 3 attempts of 300 ms plus backoff. HttpClient.Timeout defaults to 100 s, which is never the right answer
Retry rules
idempotent operations only (or with an idempotency key), exponential backoff with jitter, 2–3 attempts, and a retry budget under ~10% of traffic. Never retry a 4xx except 408 and 429
Circuit breaker
typical: failure ratio 0.1, sampling 30 s, minimum throughput 100, break 5 s, half-open probe. It exists to stop you hammering a sick dependency, not to heal it
Bulkheads
separate pools and queues per dependency and per tenant class, so one slow downstream cannot consume every thread and connection in the process
Rate limiting
AddRateLimiter .NET 7: fixed window, sliding window, token bucket, concurrency. Partition by API key or tenant, keep QueueLimit small, reject with 429 + Retry-After
Load shedding
shed at the edge on queue depth or latency, cheapest requests first; a fast 503 protects the SLO for the traffic you keep. An unbounded queue only relocates the outage
Health checks
MapHealthChecks("/health/live") = process only; "/health/ready" = dependencies, filtered by Predicate = c => c.Tags.Contains("ready"). A liveness probe that pings the database restarts the whole fleet during a database blip
Graceful shutdown
HostOptions.ShutdownTimeout longer than the longest request, plus a Kubernetes preStop sleep and terminationGracePeriodSeconds, so the load balancer stops sending before the app stops listening
Server-side timeouts
app.UseRequestTimeouts() with [RequestTimeout(2000)] .NET 8 — a request nobody is waiting for should not keep holding a connection and a DB transaction
Fallbacks
stale cached value, degraded feature, or queue-for-later. Decide per endpoint what "degraded" means; returning 500 counts as a decision only when it was made deliberately
Failure modes to name
retry storm · thundering herd on cache expiry · cascading failure through a shared pool · metastable failure (load sustains itself after the trigger is gone; only shedding or a restart exits) · gray failure (healthy to probes, broken for users)
Prove it
load test to the knee (k6 run --vus 200 --duration 5m), then run a game day: kill an AZ, inject 200 ms of latency, return 500s. Untested failover is a hypothesis
// Explicit beats default when the budget matters: 1 s end-to-end, 2 retries, jittered.
builder.Services.AddHttpClient<PricingClient>(c => c.BaseAddress = new(cfg["Pricing:Url"]!))
    .AddResilienceHandler("pricing", b => b
        .AddTimeout(TimeSpan.FromSeconds(1))                            // total budget
        .AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 2, BackoffType = DelayBackoffType.Exponential,
            UseJitter = true, Delay = TimeSpan.FromMilliseconds(100)
        })
        .AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio = 0.1, SamplingDuration = TimeSpan.FromSeconds(30),
            MinimumThroughput = 100, BreakDuration = TimeSpan.FromSeconds(5)
        })
        .AddTimeout(TimeSpan.FromMilliseconds(300)));                   // per attempt

builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    o.AddTokenBucketLimiter("per-tenant", t =>
    {
        t.TokenLimit = 200; t.TokensPerPeriod = 100;                    // 100 rps sustained, burst 200
        t.ReplenishmentPeriod = TimeSpan.FromSeconds(1); t.QueueLimit = 0;
    });
});

08Scale-out & delivery

docs: Kubernetes autoscaling · docs: YARP reverse proxy
Scale order
vertical first (a bigger node is free engineering time) → stateless horizontal → read replicas → cache → shard/partition → multi-region. Skipping to the last is how a design fails a review
Stateless services
no in-process session, no local files, no in-memory scheduler singleton. Sticky sessions are for WebSockets only, and even then with a backplane
Load balancing
L4 for raw TCP, L7 for routing/retries/mTLS. Prefer least-outstanding-requests over round robin: it routes around a slow instance, which is what actually kills the tail
Gateway / BFF
YARP as the .NET reverse proxy and BFF (routing, transforms, rate limits, auth offload); it is the current answer where Ocelot or IIS ARR used to be
Protocols
HTTP/1.1 at the edge, HTTP/2 for gRPC, HTTP/3 (QUIC) where the network is lossy — Kestrel supports HTTP/3 .NET 7. Set EnableMultipleHttp2Connections = true on SocketsHttpHandler so one connection's stream limit is not the ceiling
Autoscaling signal
HPA on CPU lags an IO-bound API by minutes; scale on rps, in-flight concurrency or queue lag (KEDA scalers for Service Bus, Kafka, Redis). Always set requests/limits and a PodDisruptionBudget
Pod sizing (.NET)
containers see limits automatically .NET 6+; below ~1.5 vCPU consider ServerGarbageCollection=false, and prefer more small pods over few large ones for failure granularity
Kubernetes facts
1.36 "Haru" 2026-04-22, patch 1.36.4 (2026-08-20); supported: 1.34–1.36. Native sidecar containers (restartable init) are stable 1.33 — the right home for a proxy or dotnet-monitor
Deployment strategy
rolling by default; canary with metric gates (Argo Rollouts, Flagger) for risky changes; blue-green when a fast rollback matters more than cost. Feature flags (Microsoft.FeatureManagement) decouple deploy from release
Migrations and deploys
never ship a breaking migration with the code that needs it — expand/contract across two releases keeps rollback possible. dotnet ef migrations bundle for a reviewable, idempotent artefact
Multi-region
active-passive with stated RPO/RTO and a rehearsed failover, or cell-based architecture: many small independent cells, shuffle-shard tenants across them so one bad tenant cannot take down everyone
Local composition
Aspire AppHost for local orchestration, service discovery and OTel wiring (Aspire 13, 2025-11, dropped the ".NET" from its name; 13.5.x current) — replaces hand-written compose files for dev
Cost levers
right-size requests · spot/burstable for stateless workers · same-AZ pinning for chatty pairs · cache before compute · retention policies. Cost per request belongs in the design doc

09Front end, edge & auth

docs: Core Web Vitals · docs: Blazor render modes
Rendering choice
SSG/ISR for content · SSR + streaming for first paint with data · CSR for app shells behind a login · React Server Components (React 19, Next 16) to keep data-fetching off the client · Blazor static SSR → Server → WebAssembly → Auto, chosen per component .NET 8
Core Web Vitals
at p75 on mobile: LCP ≤ 2.5 s, INP ≤ 200 ms (replaced FID in March 2024), CLS ≤ 0.1. These are the numbers a product owner will quote back at you
Budgets
~170–200 KB compressed JS for the initial route on mobile; route-level code splitting; preconnect to the API origin; images as AVIF/WebP with explicit dimensions to protect CLS
Current versions

11Gotchas that sink designs

library: Amazon Builders' Library
  • Retries without jitter and a budget synchronise into a storm; the system then stays down after the trigger is gone — a metastable failure that only shedding or a restart exits.
  • Alerting on averages hides the tail: a 40 ms mean can contain a 4 s p99 that is 100% of one tenant's traffic.
  • HPA on CPU for an IO-bound API scales after the queue has already backed up; scale on concurrency, rps or lag.
  • Default HttpClient.Timeout is 100 s, so one slow dependency silently holds threads, connections and memory for two minutes.
  • new HttpClient() per request exhausts sockets; use IHttpClientFactory or a static client with PooledConnectionLifetime so DNS changes are still picked up.
  • Connection maths: 40 pods × Max Pool Size=100 = 4 000 connections against a Postgres that allows 100. PgBouncer or a smaller pool, decided before launch.
  • OFFSET pagination degrades linearly and double-counts under concurrent inserts; keyset pagination does neither.
  • Uniform TTLs expire together. Jitter every TTL, or accept a periodic self-inflicted DDoS on the database.
  • Dual-writing to the database and the broker loses messages on any crash in between — outbox or CDC, no third option.
  • An at-least-once consumer without a dedupe table will eventually charge a customer twice; it is a matter of redeliveries, not of luck.
  • Reading from a replica right after a write shows the user an empty list and generates the support ticket titled "my order disappeared".
  • A missing index on a foreign key turns a delete into a table scan and a lock convoy.
  • EF Core: a missing AsNoTracking() on read paths, lazy loading in a loop (N+1), and two collection Includes without AsSplitQuery() are the three that show up in every profile.
  • PostgreSQL SERIALIZABLE raises 40001 and expects the application to retry; without that loop, serializable is just an error generator.
  • Chatty cross-AZ calls: 200 sequential 1 ms hops is 200 ms of pure network, invisible in every single-service profile.
  • Kafka consumers that process longer than max.poll.interval.ms get kicked out, triggering a rebalance storm that looks like a broker problem.
  • Sticky sessions as a scaling crutch produce uneven load and painful deploys; keep session state out of the process.
  • Unbounded queues convert an overload into an out-of-memory kill; bound the queue and shed at the edge.
  • A liveness probe that checks the database turns a 30-second database blip into a full-fleet restart.
  • A distributed lock without a fencing token allows two writers after a GC pause or a network partition — the TTL alone does not protect the resource.
  • Promising "exactly once" end-to-end without idempotent effects; the phrase is a design smell in every interview and every incident review.
  • Multi-region active-active in front of a single writable database is active-passive with extra latency and a bigger bill.
  • High-cardinality metric tags (customer id, URL with ids) explode the time series and the invoice; put those on spans and logs instead.
  • No dead-letter alert and no replay tool: the DLQ becomes the place data goes to be forgotten.
  • Shipping a breaking migration together with the code that needs it removes the ability to roll back — the one control you always want during an incident.
